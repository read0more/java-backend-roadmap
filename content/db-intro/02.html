    이 회차의 질문: "데이터베이스를 만든다"는 한 줄 뒤에서 일어나는 일

    앞 회차에서는 데이터를 파일에 직접 저장하지 않고 데이터베이스 관리 시스템(DBMS)에 맡기는 이유와, 관계형 모델의 기본 용어인 테이블·행·열·키를 보았다. 이제 손을 움직일 차례다. MySQL 서버에 접속하고, 데이터베이스를 하나 만들고, 그 안에 테이블을 만들어 행을 넣고 다시 읽어 본다. 필요한 명령은 몇 줄이면 된다. CREATE DATABASE, CREATE TABLE, INSERT, SELECT 네 가지만 알면 첫 데이터를 저장하고 되읽을 수 있다.

    이 회차가 지면을 쓰는 곳은 그 몇 줄의 아래다. CREATE DATABASE를 실행하면 서버의 디스크에는 무엇이 생기는가. Book과 book이 어떤 서버에서는 같은 테이블이고 어떤 서버에서는 다른 테이블인 이유는 무엇인가. INT(11)의 11은 무엇이고, VARCHAR(100)의 100은 바이트인가 글자인가. PRIMARY KEY를 붙이는 순간 InnoDB는 행을 어떤 순서로 저장하는가. 이 질문들은 모두 실무에서 장애나 설계 실수의 형태로 돌아온다.

    순서는 이렇다. 먼저 MySQL이 클라이언트-서버 프로그램이라는 사실에서 출발해 접속과 세션을 본다. 다음으로 데이터베이스와 테이블을 만들고 행을 넣고 읽으며, 각 문장이 서버 안에서 어떤 경로를 지나는지 따라간다. 그다음 SQL이라는 언어의 성격과 문장의 네 갈래를 정리한다. 후반부는 자료형과 제약 조건이다. 자료형은 "어떤 바이트로 저장하고, 어디까지 허용하며, 어떻게 비교하는가"에 대한 약속으로 읽고, 제약 조건은 "DBMS가 대신 지켜 주는 규칙"으로 읽는다. 모든 내용은 MySQL 8.0 이상과 InnoDB 스토리지 엔진을 기준으로 하며, 버전에 따라 달라지는 동작은 그때마다 버전을 밝힌다.

    MySQL은 서버 프로그램이다: 접속과 세션

    MySQL 레퍼런스 매뉴얼은 MySQL을 클라이언트/서버 시스템으로 소개한다. 중심에는 멀티스레드 SQL 서버 프로그램인 mysqld가 있고, 그 주위에 여러 클라이언트 프로그램과 라이브러리가 있다. 터미널에서 쓰는 mysql 명령, GUI 관리 도구, 자바 애플리케이션이 쓰는 JDBC 드라이버(MySQL Connector/J)는 모두 같은 자리, 곧 클라이언트다. 데이터 파일을 직접 열고 읽고 쓰는 것은 서버 프로세스뿐이다. 클라이언트는 서버에 문장을 보내고 결과를 받는 일만 한다.

    이 구조는 HTTP 권에서 본 웹 서버와 같은 모양이다. 서버 프로세스가 네트워크 포트에서 연결을 기다리고, 클라이언트가 연결을 맺은 뒤 요청을 보낸다. MySQL의 기본 TCP 포트는 3306이다. 다만 유닉스 계열 운영체제에는 예외가 하나 있다. 클라이언트가 호스트 이름으로 localhost를 쓰면 MySQL 프로그램은 TCP/IP 대신 유닉스 소켓 파일(Unix socket file)로 접속한다. 같은 컴퓨터 안의 프로세스끼리 파일 시스템 경로 하나를 통해 통신하는 방식이다. 그래서 매뉴얼은 유닉스에서 --host=localhost와 함께 준 포트 번호는 무시된다고 경고한다. 로컬 서버에 굳이 TCP로 붙어야 한다면 --host=127.0.0.1이나 --protocol=TCP를 쓴다.

    # 유닉스에서 localhost: 유닉스 소켓 파일로 접속한다
mysql -u root -p

# TCP/IP로 접속한다(포트 3306)
mysql -h 127.0.0.1 -P 3306 -u root -p

    -p 뒤에 값을 붙이지 않으면 클라이언트가 비밀번호를 화면에 표시하지 않고 따로 묻는다. 매뉴얼은 명령줄에 비밀번호를 직접 적으면 ps 같은 프로세스 목록 명령으로 다른 사용자가 볼 수 있다고 경고한다. 접속에 성공하면 mysql> 프롬프트가 나온다. 여기에 SQL 문을 입력하고 세미콜론(;)으로 끝낸 뒤 Enter를 누르면 클라이언트가 그 문장을 서버로 보낸다. 세미콜론 대신 \G로 끝내면 결과를 열 이름과 값이 한 줄씩 짝지어진 세로 형식으로 보여 준다. 즉 세미콜론은 mysql 클라이언트가 "여기까지가 한 문장"을 판단하는 구분자다. 여러 줄에 걸쳐 입력해도 세미콜론이 나오기 전까지는 한 문장으로 모인다.

    연결 하나에 스레드 하나, 그리고 세션

    서버 쪽에서는 연결 관리자 스레드(connection manager thread)가 접속 요청을 받는다. 매뉴얼에 따르면 모든 플랫폼에서 관리자 스레드 하나가 TCP/IP 접속 요청을 처리하고, 유닉스에서는 같은 스레드가 소켓 파일 접속 요청도 처리한다. 관리자 스레드는 각 클라이언트 연결에 그 연결 전용 스레드를 붙이고, 이 스레드가 그 연결의 인증과 요청 처리를 맡는다. 새 스레드를 만드는 비용을 줄이려고 먼저 스레드 캐시(thread cache)에 재사용할 스레드가 있는지 보고, 연결이 끝나면 캐시에 여유가 있을 때 스레드를 캐시에 돌려놓는다. 스프링 MVC 권에서 본 서블릿 컨테이너가 요청을 처리할 때 스레드 풀의 스레드를 쓰는 것과 닮았지만 단위가 다르다. MySQL에서는 연결이 살아 있는 동안 그 연결에 스레드가 붙어 있다. (MySQL Enterprise Edition에는 많은 연결을 더 적은 스레드로 처리하는 스레드 풀 플러그인이 별도로 있다.)

    연결이 유지되는 동안 서버는 그 연결의 상태를 기억한다. 이것을 세션(session)이라 한다. 지금 어떤 데이터베이스를 기본으로 쓰고 있는지(USE로 바꾼다), 어떤 SQL 모드로 동작하는지(sql_mode), 어느 시간대 기준인지(time_zone), 자동 커밋이 켜져 있는지(autocommit) 같은 값이 세션마다 따로 있다. 같은 서버에 붙은 두 클라이언트가 똑같은 문장을 보내도 세션 설정이 다르면 결과가 달라질 수 있다는 뜻이다. 이 회차 후반의 엄격 모드와 TIMESTAMP 시간대 변환이 정확히 이 세션 변수에 달려 있다. 나중에 스프링 DB 권에서 커넥션 풀을 다룰 때 "커넥션 하나가 DB 세션 하나"라는 관계가 다시 중요해진다. 풀에서 빌린 커넥션의 세션 설정을 바꿔 놓고 반납하면 다음에 그 커넥션을 빌린 코드가 바뀐 설정을 그대로 물려받기 때문이다.

    여러 클라이언트가 서로 다른 방식으로 하나의 mysqld에 접속하고, 서버 안에서 연결마다 전용 스레드와 세션이 생기며, 그 아래에 서버 계층과 스토리지 엔진 계층이 있다는 것을 보여 준다. 깔끔한 기술 구조도. 왼쪽 위에 세 개의 클라이언트 아이콘을 세로로 배치하고 각각 "mysql 클라이언트", "자바 앱(JDBC)", "GUI 도구" 라벨을 붙인다. 첫 번째 클라이언트에서 오른쪽으로 점선 화살표를 그리고 "유닉스 소켓" 라벨, 나머지 두 클라이언트에서는 실선 화살표에 "TCP 3306" 라벨을 붙인다. 화살표는 모두 오른쪽의 큰 상자 "mysqld"로 들어간다. 큰 상자 안 위쪽에 작은 상자 "연결 관리자 스레드"가 있고, 거기서 세 개의 작은 스레드 상자로 갈라지는 화살표가 있으며 각 스레드 옆에 "세션" 라벨이 붙은 작은 메모 카드가 있다. 큰 상자 안 가운데에 가로로 긴 띠 "서버 계층: 해석 → 최적화 → 실행", 그 아래 띠 "스토리지 엔진: InnoDB"가 있다. 큰 상자 아래쪽으로 화살표가 나가 원통 모양 디스크 "데이터 디렉터리"에 닿는다. 색은 차분한 파랑과 회색 위주. 클라이언트는 문장을 보내고 결과를 받을 뿐이고, 데이터 파일을 다루는 것은 서버 프로세스다. 연결마다 전용 스레드와 세션 상태가 생긴다.
    일상에서 가져온 비유도서관의 대출 창구와 사서

    도서관 이용자는 서고에 직접 들어가지 않고 창구에서 사서에게 요청한다. 창구마다 담당 사서가 한 명씩 붙고(연결 전용 스레드), 사서는 이 이용자가 어느 열람실 자료를 찾는 중인지 기억한다(세션). 서고에 들어가는 사람이 사서뿐이므로 책의 배치와 대출 규칙이 한 곳에서 지켜진다. 이 비유가 깨지는 지점은 동시성이다. 실제 사서는 서로의 일을 기다려 주지만, MySQL에서는 수많은 연결 스레드가 같은 테이블의 같은 행을 동시에 읽고 쓰려 한다. 그 충돌을 정리하는 잠금과 MVCC는 데이터베이스 기본편의 트랜잭션 회차에서 다룬다.

    데이터베이스를 만든다는 것: 디렉터리와 데이터 사전

    접속했다면 데이터베이스부터 만든다.

    CREATE DATABASE bookstore;
SHOW DATABASES;
USE bookstore;
SELECT DATABASE();

    CREATE DATABASE는 이름이 bookstore인 데이터베이스를 만든다. MySQL에서 CREATE SCHEMA는 CREATE DATABASE의 동의어다. 다른 DBMS에서는 "스키마"가 데이터베이스 안의 한 단계 아래 이름 공간을 가리키기도 하지만, MySQL에서는 데이터베이스와 스키마가 같은 것이다. 같은 이름의 데이터베이스가 이미 있으면 오류가 나고, CREATE DATABASE IF NOT EXISTS bookstore처럼 쓰면 오류 없이 넘어간다. USE는 현재 세션의 기본 데이터베이스를 바꾼다. 이후 테이블 이름만 쓰면 이 데이터베이스에서 찾고, 다른 데이터베이스의 테이블은 bookstore.book처럼 데이터베이스 이름을 앞에 붙여 가리킨다. SELECT DATABASE()는 현재 세션의 기본 데이터베이스 이름을 돌려준다.

    SHOW DATABASES를 처음 실행하면 직접 만들지 않은 이름이 몇 개 보인다. mysql, information_schema, performance_schema, sys다. mysql은 시스템 스키마로, 서버가 동작하는 데 필요한 정보를 담는다. 매뉴얼은 그 내용을 데이터베이스 객체의 메타데이터를 저장하는 데이터 사전 테이블과, 그 밖의 운영 목적에 쓰는 시스템 테이블로 나눈다. information_schema는 그 메타데이터를 SQL로 조회하는 창구다. performance_schema와 sys는 서버 내부의 실행 상황을 관찰하기 위한 스키마다. 이 시스템 스키마들은 지우거나 직접 고치는 대상이 아니다.

    디스크에 생기는 것

    매뉴얼은 CREATE DATABASE를 이렇게 설명한다. MySQL의 데이터베이스는 그 데이터베이스의 테이블에 대응하는 파일들을 담은 디렉터리로 구현된다. 막 만든 데이터베이스에는 테이블이 없으므로 CREATE DATABASE는 데이터 디렉터리 아래에 디렉터리 하나만 만든다. 데이터 디렉터리의 위치는 설치 방식마다 다르므로 SELECT @@datadir;로 확인한다. 매뉴얼은 반대 방향, 즉 데이터 디렉터리 아래에 mkdir로 디렉터리를 직접 만들어 데이터베이스를 만드는 일은 MySQL 8.0에서 지원하지 않는다고 못 박는다. 디렉터리와 파일은 서버가 관리하게 두어야 하며, 직접 건드리면 불일치가 생긴다.

    이 데이터베이스에 InnoDB 테이블을 만들면 InnoDB는 기본적으로 테이블마다 파일 하나짜리 테이블스페이스(file-per-table tablespace)를 만든다. 테이블 하나의 데이터와 인덱스가 모두 테이블 이름을 딴 .ibd 파일 하나에 들어가고, 이 파일은 데이터베이스 디렉터리 안에 생긴다. 이 동작은 innodb_file_per_table 변수가 정하며, 매뉴얼은 InnoDB가 기본적으로 테이블을 이 방식으로 만든다고 적는다. 그래서 bookstore 데이터베이스에 book 테이블을 만들면 데이터 디렉터리 아래에 bookstore/book.ibd가 생긴다.

    SELECT @@datadir 가 가리키는 디렉터리
 |
 +-- mysql.ibd          <- mysql 시스템 테이블 + 데이터 사전 테이블 (InnoDB 테이블스페이스)
 |
 +-- bookstore/         <- CREATE DATABASE bookstore 가 만든 디렉터리
 |     +-- book.ibd     <- CREATE TABLE book 이 만든 파일 (book의 데이터 + 인덱스)
 |
 +-- (그 밖에 InnoDB 시스템 테이블스페이스, 로그 파일 등 서버가 관리하는 파일들)

    그렇다면 테이블의 정의, 곧 열 이름과 자료형과 제약 조건은 어디에 있을까. MySQL 8.0은 트랜잭션을 지원하는 데이터 사전(transactional data dictionary)을 도입했다. 매뉴얼에 따르면 이전 릴리스에서는 사전 정보가 메타데이터 파일, 트랜잭션을 지원하지 않는 테이블, 스토리지 엔진별 사전에 흩어져 있었다. 8.0에서는 mysql 시스템 테이블과 데이터 사전 테이블이 데이터 디렉터리의 mysql.ibd라는 InnoDB 테이블스페이스 파일 하나에 함께 들어간다. 사전이 InnoDB 테이블에 저장되므로 사전 변경도 트랜잭션의 보호를 받는다. 매뉴얼은 데이터 사전이 가져온 이점으로 파일 기반 메타데이터 저장의 제거, 트랜잭션과 충돌 안전(crash-safe)을 갖춘 사전 저장, 원자적 DDL(atomic DDL)을 꼽는다.

    데이터 사전 테이블은 보이지 않는다. 매뉴얼에 따르면 SELECT로 읽을 수 없고, SHOW TABLES에도, INFORMATION_SCHEMA.TABLES에도 나오지 않는다. SELECT * FROM mysql.schemata;처럼 직접 읽으려 하면 접근이 거부된다는 오류가 난다. MySQL 8.4.13과 8.0.46에서 실행하면 ERROR 3554 (HY000): Access to data dictionary table 'mysql.schemata' is rejected.가 나온다. 대신 대부분의 사전 정보에는 대응하는 INFORMATION_SCHEMA 테이블이 있어서 그것을 조회한다. 지금 만든 데이터베이스의 기본 문자 집합과 콜레이션은 이렇게 확인한다.

    SELECT SCHEMA_NAME, DEFAULT_CHARACTER_SET_NAME, DEFAULT_COLLATION_NAME
FROM information_schema.SCHEMATA
WHERE SCHEMA_NAME = 'bookstore';

    문자 집합을 지정하지 않고 만들었으므로 서버의 기본값을 물려받는다. MySQL 8.0의 서버 기본 문자 집합은 utf8mb4, 기본 콜레이션은 utf8mb4_0900_ai_ci다. 매뉴얼은 서버 수준의 문자 집합과 콜레이션이 CREATE DATABASE에서 지정하지 않았을 때의 기본값으로 쓰이며 그 밖의 용도는 없다고 적는다. 그 아래의 테이블은 데이터베이스의 기본값을, 열은 테이블의 기본값을 다시 물려받는다. 문자 집합과 콜레이션이 정확히 무엇을 정하는지는 문자열 자료형에서 자세히 본다.

    CREATE DATABASE는 디렉터리를, CREATE TABLE은 .ibd 파일과 데이터 사전 항목을 만든다는 것, 그리고 사용자는 데이터 사전을 INFORMATION_SCHEMA를 통해서만 본다는 것을 보여 준다. 왼쪽에 SQL 문 두 개가 적힌 카드가 위아래로 있다: 위 카드 "CREATE DATABASE bookstore", 아래 카드 "CREATE TABLE book". 오른쪽에는 폴더 트리 그림이 있다. 맨 위 폴더 "데이터 디렉터리" 아래에 파일 아이콘 "mysql.ibd"와 폴더 "bookstore/"가 있고, "bookstore/" 안에 파일 아이콘 "book.ibd"가 있다. 위 카드에서 "bookstore/" 폴더로 화살표, 아래 카드에서 "book.ibd"로 화살표 하나와 "mysql.ibd"로 화살표 하나를 그린다. "mysql.ibd" 옆에 자물쇠 아이콘과 작은 라벨 "데이터 사전(직접 조회 불가)"을 붙인다. 그림 아래쪽에 돋보기 아이콘이 달린 상자 "INFORMATION_SCHEMA"가 있고, 이 상자에서 "mysql.ibd" 쪽으로 점선 화살표와 라벨 "조회 창구"를 그린다. 평면적인 일러스트, 흰 배경. 데이터베이스는 디렉터리, InnoDB 테이블은 .ibd 파일이고, 정의는 mysql.ibd 안의 데이터 사전에 기록된다. 사용자는 INFORMATION_SCHEMA로 사전을 본다.

    이름의 대소문자: 파일 시스템이 결정한다

    데이터베이스가 디렉터리이고 테이블이 파일이라는 사실은 눈에 띄는 결과를 하나 낳는다. 매뉴얼에 따르면 데이터베이스, 테이블, 트리거 이름에는 대응하는 디렉터리나 파일이 있기 때문에, 운영체제 파일 시스템의 대소문자 구분 여부가 이 이름들의 대소문자 구분에 영향을 준다. 이 이름들은 윈도우에서는 대소문자를 구분하지 않고, 대부분의 유닉스에서는 구분한다. 매뉴얼은 유닉스 계열인 macOS가 보통 대소문자를 구분하지 않는 파일 시스템을 쓴다는 점도 따로 짚는다. 즉 SQL이라는 언어의 규칙이 아니라 저장 방식이 이름 규칙을 결정하는 셈이다.

    서버 쪽에서 이 차이를 정리하는 변수가 lower_case_table_names다.

    값이름 저장이름 비교이 값이 기본인 플랫폼
    0CREATE 문에 쓴 그대로대소문자 구분유닉스
    1소문자로 바꿔 저장대소문자 구분 안 함윈도우
    2쓴 그대로 저장, 찾을 때 소문자로 변환대소문자 구분 안 함macOS

    MySQL 8.0에서 이 변수는 서버를 초기화할 때만 설정할 수 있다. 매뉴얼은 초기화 이후에 값을 바꾸는 것을 금지한다고 명시한다. 그러니 운영 서버를 처음 설치할 때 정해야 하는 값이다. 한편 열 이름은 모든 플랫폼에서 대소문자를 구분하지 않는다. 열 별칭, 인덱스 이름, 저장 루틴 이름도 마찬가지다. 대소문자 구분이 파일 시스템에서 오는 것이므로, 파일과 관계없는 이름은 영향을 받지 않는 것이다.

    이 규칙이 실무에서 사고로 이어지는 전형적인 경로가 있다. 개발자가 macOS 노트북(기본값 2)에서 테이블을 book으로 만들고 SQL에는 Book이라고 섞어 써도 잘 동작한다. 그런데 리눅스 운영 서버(기본값 0)에 배포하면 같은 SQL이 "테이블이 없다"는 오류를 낸다. 매뉴얼은 InnoDB를 쓴다면 모든 플랫폼에서 lower_case_table_names=1을 쓰라고 권한다. 이 값과 무관하게 가장 단순한 방어는 데이터베이스, 테이블 이름을 처음부터 소문자와 밑줄로만 짓는 습관이다.

    테이블을 만들고, 행을 넣고, 읽기

    이제 테이블을 만들어 첫 데이터를 넣는다. 일부러 아무 규칙도 붙이지 않은 테이블에서 시작한다.

    CREATE TABLE book (
    book_id BIGINT,
    title   VARCHAR(100),
    price   INT
);

INSERT INTO book (book_id, title, price) VALUES (1, 'Database Primer', 25000);
INSERT INTO book (book_id, title, price) VALUES (2, 'SQL Basics', 18000);

SELECT * FROM book;
    +---------+-----------------+-------+
| book_id | title           | price |
+---------+-----------------+-------+
|       1 | Database Primer | 25000 |
|       2 | SQL Basics      | 18000 |
+---------+-----------------+-------+
2 rows in set (0.00 sec)

    CREATE TABLE은 테이블 이름과 열 목록을 정한다. 열마다 이름과 자료형을 쓴다. INSERT는 행 하나를 넣으며, 괄호 안의 열 목록과 VALUES 뒤의 값은 위치로 짝지어진다. SELECT *는 모든 열을 돌려준다. 결과 마지막 줄 괄호 안의 시간은 실행마다 다르다. 이 작은 예에서는 행이 넣은 순서대로 나왔지만, ORDER BY가 없는 한 SQL은 결과 행의 순서를 약속하지 않는다. 정렬은 4회에서 다룬다. 결과가 ASCII 표 모양인 것은 서버가 아니라 mysql 클라이언트가 그린 것이다. 매뉴얼은 이 클라이언트가 대화형으로 쓰일 때는 표 형식으로, 비대화형으로 쓰일 때(예: 스크립트 파일을 입력으로 줄 때)는 탭으로 구분한 형식으로 결과를 출력한다고 설명한다.

    이 네 문장을 서버 안에서 따라가 보자. CREATE TABLE에서 서버는 문장을 해석한 뒤 데이터 사전에 book 테이블의 정의를 기록하고, 스토리지 엔진에게 테이블을 만들게 한다. ENGINE 절을 생략했으므로 MySQL 8.0의 기본 스토리지 엔진인 InnoDB가 쓰이고, InnoDB는 bookstore/book.ibd를 만든다. SHOW CREATE TABLE book;을 실행하면 생략한 부분이 채워진 정의가 나오는데, 끝부분에 ENGINE=InnoDB, DEFAULT CHARSET=utf8mb4, COLLATE=utf8mb4_0900_ai_ci가 붙어 있다. 서버가 기본값으로 무엇을 골랐는지 확인하는 가장 확실한 방법이다.

    첫 번째 INSERT에서는 트랜잭션이 등장한다. 매뉴얼에 따르면 InnoDB에서는 모든 사용자 활동이 트랜잭션 안에서 일어난다. MySQL은 새 연결의 세션을 자동 커밋(autocommit)이 켜진 상태로 시작하므로, 각 SQL 문이 그 자체로 하나의 트랜잭션이 되고, 문장이 오류 없이 끝나면 서버가 그 자리에서 커밋한다. 그래서 INSERT 한 줄을 실행하고 나면 다른 연결에서도 그 행이 보인다. 그 행이 book.ibd 안 어디에 놓이는지는 뒤에서 기본 키를 다룰 때 본다. 미리 말하면 이 테이블처럼 기본 키가 없으면 InnoDB가 숨겨진 열을 만들어 그 값의 순서로 행을 배치한다.

    SELECT는 서버가 테이블에서 행을 읽어 결과 집합(result set)으로 만들고 연결을 통해 클라이언트로 보낸다. 자바에서 JDBC로 같은 문장을 실행하면 ResultSet 객체로 이 결과를 한 행씩 넘겨 가며 읽는다. 클라이언트가 터미널 프로그램이든 자바 애플리케이션이든 서버가 하는 일은 같다.

    이 테이블은 무엇이든 받아들인다

    방금 만든 테이블에 다음 두 문장을 실행해 보자.

    INSERT INTO book (book_id, title, price) VALUES (1, NULL, -500);
INSERT INTO book (book_id, title, price) VALUES (NULL, 'No Id', NULL);

    두 문장 모두 성공한다. 이제 테이블에는 book_id가 1인 행이 두 개 있고, 제목이 없는 책과 가격이 음수인 책과 식별자가 없는 책이 있다. 매뉴얼에 따르면 열 정의에 NULL도 NOT NULL도 쓰지 않으면 NULL을 쓴 것처럼 취급한다. 즉 이 테이블은 모든 열에 값이 없어도 된다고 선언한 셈이다. 테이블에 구조는 있지만 규칙은 없다.

    "그런 검사는 애플리케이션 코드에서 하면 되지 않는가"라고 물을 수 있다. 문제는 두 가지다. 첫째, 데이터를 쓰는 경로가 하나가 아니다. 같은 테이블에 웹 애플리케이션, 배치 작업, 다른 팀의 서비스, 운영자가 직접 실행하는 SQL이 모두 쓴다. 어느 한 경로의 검사가 빠지면 잘못된 행이 들어온다. 둘째, 동시성이다. 두 요청이 거의 같은 순간에 "이 번호의 책이 이미 있는가"를 조회하고 둘 다 "없다"는 답을 받은 뒤 각자 INSERT하면, 조회와 저장 사이의 틈 때문에 중복이 생긴다. DBMS가 행을 쓰는 순간에 직접 검사하면 쓰는 경로와 무관하게, 그리고 동시에 들어온 요청 사이에서도 규칙이 지켜진다. 이것이 후반부에서 다룰 자료형과 제약 조건의 출발점이다.

    SQL 한 문장이 서버 안에서 지나는 길

    지금까지 실행한 문장들이 서버 안에서 지나는 길을 한 번 정리해 두자. 세부 구현은 버전마다 다르지만, 큰 단계는 다음과 같다.

    단계가 나뉘어 있다는 것은 오류 메시지만 봐도 알 수 있다. SELEC * FROM book;처럼 키워드를 틀리면 ERROR 1064 (42000): You have an error in your SQL syntax로 시작하는 오류가 난다. 해석 단계에서 걸린 것이다. 문법은 맞는데 없는 테이블을 쓰면, 예를 들어 SELECT * FROM books;라고 쓰면 ERROR 1146 (42S02): Table 'bookstore.books' doesn't exist라는 오류가 난다. 문장 구조는 통과했지만 이름 확인에서 걸린 것이다. 두 경우 모두 데이터는 한 바이트도 읽히지 않는다. 반대로 자료형 범위나 제약 조건 위반은 실행 단계, 즉 실제로 행을 쓰려는 순간에 걸린다.

    이 흐름에서 가장 중요한 경계는 서버 계층과 스토리지 엔진 계층 사이다. 매뉴얼은 MySQL의 플러그형 스토리지 엔진 아키텍처(pluggable storage engine architecture)를 설명하며, 스토리지 엔진을 "물리적 서버 수준에서 유지되는 기반 데이터에 실제로 작업을 수행하는 구성 요소"라고 부른다. SQL을 이해하고 실행 방법을 고르는 일은 서버 계층이, 데이터를 디스크와 메모리에 어떤 구조로 두고 어떻게 읽고 쓰는지는 엔진이 맡는다. 엔진은 서버나 스키마 전체가 아니라 테이블마다 지정할 수 있다. 매뉴얼은 대부분 InnoDB 테이블을 쓰면서 스프레드시트로 내보낼 테이블 하나는 CSV 엔진으로, 임시 작업용 테이블 몇 개는 MEMORY 엔진으로 두는 구성을 예로 든다.

    MySQL 8.0의 기본 엔진인 InnoDB에 대해 매뉴얼은 이렇게 요약한다. 트랜잭션에 안전한(ACID를 준수하는) 엔진으로 커밋, 롤백, 충돌 복구 기능이 있고, 행 단위 잠금과 잠금 없는 일관된 읽기로 동시성을 높이며, 사용자 데이터를 클러스터형 인덱스에 저장하고, FOREIGN KEY 참조 무결성 제약을 지원한다. 이 목록이 알려 주는 것은 트랜잭션도, 외래 키도 "SQL이 원래 갖고 있는 기능"이 아니라 엔진의 능력이라는 사실이다. 같은 SQL을 써도 엔진이 다르면 지켜지는 것이 달라진다. 이 강좌가 InnoDB를 기준으로 삼는 이유다.

    SQL이라는 언어: 무엇을 원하는지만 말한다

    SQL은 Structured Query Language의 약자다. 매뉴얼은 SQL이 ANSI/ISO SQL 표준으로 정의되며, 이 표준이 1986년부터 발전해 왔고 여러 버전이 있다고 설명한다. 표준이 있다고 해서 모든 DBMS가 똑같이 동작하는 것은 아니다. 각 벤더는 표준을 바탕으로 구현하되 표준의 일부를 다르게 처리하거나 자기만의 확장을 더한다. MySQL만 해도 매뉴얼에 표준과의 차이를 따로 정리한 절이 있다. 예를 들어 표준은 외래 키 검사를 문장 전체가 처리된 뒤로 미루는 것을 기본으로 정하지만, MySQL은 외래 키 제약을 즉시 검사하고 트랜잭션 커밋 시점으로 미루지 않는다고 적는다. 표준에 정의된 "열 정의 안에 쓰는 REFERENCES"를 MySQL 8.0과 8.4가 파싱만 하고 무시하는 것도 그런 차이다(MySQL 9.0.0부터는 받아들여 강제한다). 이 차이가 실제로 어떤 함정이 되는지는 제약 조건 절에서 본다.

    SQL의 가장 중요한 성격은 선언형(declarative) 언어라는 점이다. 원하는 결과가 어떤 조건을 만족해야 하는지만 쓰고, 그 결과를 어떻게 구할지는 DBMS가 정한다. 자바와 나란히 놓으면 차이가 분명하다.

    // 자바: 결과를 "어떻게" 만드는지까지 쓴다
List titles = new ArrayList<>();
for (Book book : books) {          // 처음부터 끝까지 하나씩 본다
    if (book.price() >= 20000) {   // 조건을 검사한다
        titles.add(book.title());  // 맞으면 담는다
    }
}
    -- SQL: "무엇을" 원하는지만 쓴다
SELECT title FROM book WHERE price >= 20000;

    자바 코드는 "목록을 처음부터 끝까지 하나씩 보면서 조건을 검사해 새 목록에 담는다"는 방법까지 정한다. 목록이 10개든 1억 개든 같은 방법을 쓴다. SQL 문장에는 방법이 없다. 테이블이 10행이든 1억 행이든, price에 인덱스가 있든 없든 문장은 같고, 어떻게 읽을지는 옵티마이저가 그때의 인덱스와 통계를 보고 고른다. 같은 SQL이 데이터가 늘면서 갑자기 느려지기도 하고, 문장을 한 글자도 고치지 않았는데 인덱스 하나를 추가하자 빨라지기도 하는 이유가 여기에 있다. 실행 계획을 읽는 방법은 인덱스를 다루는 이후 권에서 본다.

    또 하나의 성격은 집합 단위로 동작한다는 점이다. UPDATE book SET price = price + 1000 WHERE price < 20000;은 조건을 만족하는 모든 행을 한 문장으로 바꾼다. 행을 하나씩 꺼내 고치는 반복문을 쓸 필요가 없다. 관계형 모델에서 테이블은 행의 집합이고, SQL 문은 집합을 받아 집합을 돌려주는 연산이다. 이 관점은 뒤의 회차에서 조회, 집계, 조인을 배울 때 계속 쓰인다.

    SQL 문장의 네 갈래: DDL, DML, DCL, TCL

    SQL 문은 하는 일에 따라 보통 네 갈래로 나눈다.

    분류하는 일대표 문장MySQL 매뉴얼의 묶음
    DDL (Data Definition Language)데이터베이스, 테이블, 인덱스 같은 객체의 구조를 정의하고 바꾼다CREATE, ALTER, DROP, TRUNCATE, RENAMEData Definition Statements
    DML (Data Manipulation Language)테이블 안의 행을 조회하고 넣고 고치고 지운다SELECT, INSERT, UPDATE, DELETEData Manipulation Statements
    DCL (Data Control Language)사용자에게 권한을 주고 빼앗는다GRANT, REVOKEDatabase Administration Statements 안의 Account Management Statements
    TCL (Transaction Control Language)여러 문장을 하나의 트랜잭션으로 묶고 확정하거나 취소한다START TRANSACTION, COMMIT, ROLLBACK, SAVEPOINTTransactional and Locking Statements

    DDL·DML·DCL·TCL이라는 이름은 업계에서 널리 쓰는 관례이고, MySQL 매뉴얼의 SQL 문 장(chapter)은 표의 마지막 열처럼 묶는다. SELECT는 매뉴얼에서 데이터 조작 문 안에 있다. 교재에 따라 SELECT만 따로 DQL(Data Query Language)로 떼어 다섯 갈래로 나누기도 한다. 분류 이름은 중요하지 않다. 중요한 것은 갈래에 따라 서버의 동작이 다르다는 사실이다.

    경계에 있는 문장 하나가 그 점을 잘 보여 준다. TRUNCATE TABLE은 테이블의 모든 행을 지운다는 점에서 DELETE와 비슷하지만, 매뉴얼은 이것을 DML이 아니라 DDL로 분류한다. 이유는 동작에 있다. 매뉴얼에 따르면 TRUNCATE TABLE은 행을 하나씩 지우는 대신 테이블을 삭제했다가 다시 만들기 때문에 큰 테이블에서 훨씬 빠르다. 대신 암묵적 커밋을 일으키므로 롤백할 수 없고, AUTO_INCREMENT 값을 시작값으로 되돌리며, 다른 테이블의 외래 키가 이 테이블을 참조하고 있으면 InnoDB 테이블에서는 실패한다. 겉보기 효과가 같아도 "구조를 다시 만드는 문장"이냐 "행을 고치는 문장"이냐에 따라 트랜잭션과의 관계가 완전히 달라진다.

    갈래가 동작을 가른다: 암묵적 커밋

    매뉴얼은 일부 문장이 실행되기 전에 현재 세션의 활성 트랜잭션을 마치 COMMIT을 실행한 것처럼 끝낸다고 적는다. 이것을 암묵적 커밋(implicit commit)이라 한다. 해당하는 문장은 크게 세 무리다. 첫째, 데이터베이스 객체를 정의하거나 바꾸는 DDL(CREATE DATABASE, ALTER TABLE, DROP TABLE, CREATE VIEW, TRUNCATE TABLE 등)이다. 둘째, mysql 데이터베이스의 테이블을 암묵적으로 쓰거나 고치는 문장(GRANT, REVOKE, CREATE USER, DROP USER 등)이다. 셋째, 트랜잭션 제어·잠금 문장(BEGIN, START TRANSACTION, LOCK TABLES 등)이다. 앞의 표로 말하면 DDL(아래 노트의 임시 테이블 문장은 예외)과 DCL 전체, TCL의 일부가 여기에 들어간다.

    START TRANSACTION;
INSERT INTO book (book_id, title, price) VALUES (3, 'Draft', 1000);
CREATE TABLE memo (id INT);   -- DDL: 실행 전에 앞의 INSERT가 커밋된다
ROLLBACK;                     -- 되돌릴 것이 남아 있지 않다
SELECT * FROM book WHERE book_id = 3;

    한 줄씩 따라가 보자. START TRANSACTION으로 자동 커밋과 무관하게 명시적 트랜잭션이 시작된다. INSERT로 'Draft' 행이 들어가지만 아직 커밋되지 않았으므로, 이 시점에는 ROLLBACK하면 사라질 수 있는 상태다. 다음 줄의 CREATE TABLE은 DDL이므로 실행되기 전에 서버가 활성 트랜잭션을 커밋한다. 'Draft' 행은 이 순간 확정된다. 그 뒤 memo 테이블이 만들어진다. 이어지는 ROLLBACK은 열려 있는 트랜잭션이 없으므로 되돌릴 것이 없다. 마지막 SELECT는 'Draft' 행 하나를 돌려준다. memo 테이블도 남아 있다.

    이 동작은 애플리케이션에서 더 알아차리기 어렵다. 스프링의 트랜잭션 안에서 실행되는 코드가 중간에 DDL을 한 번이라도 실행하면, 이후에 예외가 나서 스프링이 롤백을 요청해도 DDL 이전의 변경은 이미 커밋되어 있다. 프레임워크의 트랜잭션은 결국 이 연결의 세션에 COMMIT이나 ROLLBACK을 보내는 것이므로, 서버가 중간에 커밋해 버린 것은 되돌릴 수 없다. 운영 중인 서비스의 트랜잭션 코드에 테이블 생성이나 변경 같은 DDL을 섞지 않는 이유다. 트랜잭션의 원자성과 격리 수준은 데이터베이스 기본편에서 본격적으로 다룬다.

    이와 반대로 CREATE TEMPORARY TABLE과 DROP TEMPORARY TABLE은 암묵적 커밋을 일으키지 않는다. 매뉴얼은 대신 이 문장들 자체도 롤백되지 않는다고 적는다. 연습 문제에서 이 차이를 직접 추적해 본다.

    자료형은 저장 형식, 허용 범위, 비교 규칙의 약속이다

    열마다 자료형(data type)을 정하는 이유를 세 가지로 나눠 보자. 첫째는 저장이다. 자료형은 값을 몇 바이트로, 어떤 인코딩으로 디스크와 메모리에 놓을지 정한다. 둘째는 검증이다. 자료형은 허용 범위를 정하고, 범위 밖의 값이 들어오면 거부하거나 고친다. 셋째는 의미다. 같은 글자 '10'과 '9'도 문자열로 비교하면 첫 글자 '1'이 '9'보다 앞서므로 '10'이 작고, 숫자로 비교하면 10이 크다. 정렬, 비교, 산술이 모두 자료형을 따른다.

    크기는 성능과도 이어진다. InnoDB는 데이터를 기본 16KB 크기의 페이지 단위로 디스크와 메모리 사이에서 옮긴다. 행이 작으면 한 페이지에 더 많은 행이 들어가고, 같은 크기의 버퍼 풀에 더 많은 행이 올라간다. 인덱스도 열 값을 복사해 담는 구조이므로 열이 작으면 인덱스도 작아진다. 그래서 "넉넉하게 BIGINT, 넉넉하게 VARCHAR(1000)"이 늘 공짜는 아니다. 반대로 너무 작게 잡으면 몇 년 뒤 범위를 넘는 값이 들어오는 순간 장애가 난다. 자료형 선택은 이 두 비용 사이의 판단이다.

    엄격 SQL 모드: 범위 밖의 값을 거부할 것인가 고칠 것인가

    자료형의 검증이 실제로 어떻게 동작하는지는 세션의 SQL 모드(SQL mode)가 정한다. 매뉴얼에 따르면 MySQL 8.0의 기본 SQL 모드는 ONLY_FULL_GROUP_BY, STRICT_TRANS_TABLES, NO_ZERO_IN_DATE, NO_ZERO_DATE, ERROR_FOR_DIVISION_BY_ZERO, NO_ENGINE_SUBSTITUTION의 여섯 가지를 포함한다. 이 중 STRICT_TRANS_TABLES가 엄격 모드(strict mode)다. 엄격 모드가 켜져 있으면 트랜잭션을 지원하는 테이블(InnoDB)에 잘못된 값이나 빠진 값을 넣는 데이터 변경 문은 오류를 내고 중단되며 롤백된다. 엄격 모드가 꺼져 있으면 MySQL은 값을 조정해 넣고 경고만 남긴다.

    이 차이는 작지 않다. 엄격 모드가 꺼진 서버에서는 잘못된 값이 오류 없이 "조금 다른 값"으로 저장되고, 애플리케이션은 성공 응답을 받는다. 경고는 클라이언트가 SHOW WARNINGS로 직접 물어보지 않으면 대개 아무도 보지 않는다. 기본값이 엄격 모드이긴 하지만 설정 파일에서 sql_mode를 바꿔 둔 서버도 있으므로, 처음 다루는 서버라면 SELECT @@sql_mode;로 확인하는 습관이 필요하다. 이후 이 회차의 예제는 모두 기본값인 엄격 모드를 가정한다.

    정수형: 바이트 수가 범위를 정한다

    MySQL의 정수형은 다섯 가지이고, 저장 바이트 수가 범위를 결정한다.

    자료형저장 바이트부호 있음(SIGNED) 범위UNSIGNED 범위같은 크기의 자바 정수형
    TINYINT1-128 ~ 1270 ~ 255byte
    SMALLINT2-32768 ~ 327670 ~ 65535short
    MEDIUMINT3-8388608 ~ 83886070 ~ 16777215없음
    INT4-2147483648 ~ 21474836470 ~ 4294967295int
    BIGINT8-9223372036854775808 ~ 92233720368547758070 ~ 18446744073709551615long

    n바이트는 2의 8n제곱 가지 값을 표현한다. 부호 있는 형은 그 절반을 음수에, 나머지를 0과 양수에 쓰므로 범위가 -28n-1부터 28n-1-1까지다. UNSIGNED를 붙이면 같은 바이트로 0부터 28n-1까지 표현한다. 자바의 byte, short, int, long과 바이트 수와 부호 있는 범위가 정확히 같다는 점을 눈여겨보자. 음수를 2의 보수로 표현하는 방식도 같다. 다만 자바에는 부호 없는 기본형이 없으므로, INT UNSIGNED의 최댓값 4294967295는 자바 int에 담기지 않는다. 그래서 MySQL Connector/J는 INT UNSIGNED를 java.lang.Long으로, BIGINT UNSIGNED를 java.math.BigInteger로 매핑한다.

    INT(11)의 11은 범위가 아니다

    오래된 스키마에는 INT(11), BIGINT(20) 같은 표기가 흔하다. 괄호 안의 숫자는 표시 너비(display width)이며, 매뉴얼은 표시 너비가 열에 저장할 수 있는 값의 범위를 제한하지 않는다고 강조한다. 매뉴얼의 예로, SMALLINT(3)은 여전히 -32768부터 32767까지의 값을 저장하고, 세 자리를 넘는 값도 잘리지 않고 그대로 표시된다. 그리고 MySQL 8.0.17부터 정수형의 표시 너비와 ZEROFILL 속성은 사용 중단(deprecated)되었고 향후 버전에서 제거될 예정이다. 새로 만드는 테이블에는 괄호 없이 INT, BIGINT라고 쓴다.

    범위를 넘는 값: 거부할 것인가, 끝값으로 자를 것인가

    매뉴얼의 예를 그대로 따라가 보자. 부호 있는 TINYINT 열과 TINYINT UNSIGNED 열에 둘 다 256을 넣는다. 주석은 MySQL 8.4.13과 8.0.46에서 실제로 실행한 결과다.

    CREATE TABLE t1 (i1 TINYINT, i2 TINYINT UNSIGNED);

-- 엄격 모드
SET sql_mode = 'TRADITIONAL';
INSERT INTO t1 (i1, i2) VALUES (256, 256);
-- ERROR 1264 (22003): Out of range value for column 'i1' at row 1
-- 테이블은 비어 있다

-- 엄격 모드를 끈 경우
SET sql_mode = '';
INSERT INTO t1 (i1, i2) VALUES (256, 256);
-- 성공, 경고 2개(1264)
SELECT * FROM t1;
-- i1 = 127, i2 = 255

    엄격 모드에서는 표준이 정한 대로 범위 밖의 값을 오류로 거부하고 아무것도 저장하지 않는다. 엄격 모드가 아니면 MySQL은 값을 그 자료형 범위의 가까운 끝값으로 잘라(clip) 저장한다. 256은 부호 있는 TINYINT의 최댓값 127로, TINYINT UNSIGNED의 최댓값 255로 바뀐다. 경고 두 개가 남지만 문장은 성공한다. 만약 이 열이 재고 수량이었다면, 엄격 모드가 꺼진 서버는 오류 없이 엉뚱한 재고를 기록한 것이다.

    열에 저장할 때와 별개로, 식을 계산하는 도중의 오버플로는 SQL 모드와 무관하게 오류다. 매뉴얼은 SELECT 9223372036854775807 + 1;이 범위 초과 오류를 낸다고 보여 준다. MySQL 8.4.13과 8.0.46에서 실행하면 ERROR 1690 (22003): BIGINT value is out of range in '(9223372036854775807 + 1)'이 나온다. 자바의 long이었다면 같은 계산이 조용히 음수로 넘어갔을 것이다. 이 대비는 아래의 자바 비교 절에서 실행 결과로 확인한다.

    고정소수점과 부동소수점: DECIMAL과 FLOAT·DOUBLE

    DECIMAL(M,D)는 정확한 값을 저장하는 고정소수점(fixed-point) 자료형이다. M은 전체 자릿수(정밀도, precision)이고 1부터 65까지, D는 소수점 아래 자릿수(스케일, scale)이고 0부터 30까지이며 M보다 클 수 없다. D를 생략하면 0, M을 생략하면 10이므로 그냥 DECIMAL은 DECIMAL(10,0)이다. MySQL에서 NUMERIC은 DECIMAL로 구현되어 있어 둘은 같다. 매뉴얼의 예로 DECIMAL(5,2)는 전체 다섯 자리 중 소수 둘째 자리까지이므로 -999.99부터 999.99까지를 저장한다. 정수부에 허용되는 자릿수는 M-D다. 매뉴얼은 이 자료형을 금액처럼 정확한 정밀도를 지켜야 하는 데이터에 쓴다고 설명한다.

    DECIMAL은 10진수 아홉 자리를 4바이트에 담는다

    DECIMAL이 정확한 이유는 저장 방식에 있다. 매뉴얼에 따르면 DECIMAL 값은 10진수 아홉 자리를 4바이트에 담는 이진 형식으로 저장되고, 정수부와 소수부의 저장 공간은 따로 계산한다. 아홉 자리 묶음마다 4바이트를 쓰고, 아홉 자리에 못 미치는 나머지 자리는 다음 표만큼의 바이트를 쓴다.

    나머지 자릿수01~23~45~67~8
    바이트01234

    계산해 보자. DECIMAL(10,2)는 정수부 8자리, 소수부 2자리다. 정수부 8자리는 아홉 자리 묶음이 없고 나머지가 8이므로 4바이트, 소수부 2자리는 1바이트, 합계 5바이트다. 매뉴얼의 예인 DECIMAL(18,9)는 양쪽이 아홉 자리씩이라 4바이트씩, 합계 8바이트다. 최대인 DECIMAL(65,30)은 정수부 35자리가 아홉 자리 묶음 셋(12바이트)과 나머지 8자리(4바이트)로 16바이트, 소수부 30자리가 묶음 셋(12바이트)과 나머지 3자리(2바이트)로 14바이트, 합계 30바이트다. 핵심은 10진수 자릿수를 그대로 보존한다는 점이다. 0.1은 소수부에 "1"이라는 10진수 숫자로 들어가며, 근삿값으로 바뀌지 않는다. 매뉴얼은 DECIMAL 값의 사칙연산이 65자리 정밀도로 수행된다고 적는다.

    스케일보다 긴 소수가 들어오면 어떻게 될까. 매뉴얼은 DECIMAL이나 정수 열에 값을 넣을 때는 대상이 정확한 자료형이므로, 넣는 값이 정확한 값이든 근삿값이든 "0에서 먼 쪽으로 반올림(round half away from zero)" 규칙을 쓴다고 설명한다. 매뉴얼의 예에서 DECIMAL(10,0) 열에 2.5와 2.5E0을 넣으면 둘 다 3이 되고, 행마다 Note 1265 Data truncated가 남는다. 이 소수 자릿수 조정은 엄격 모드에서도 오류가 아니다. 그러니 DECIMAL(10,2) 열에 12.345를 넣으면 오류 없이 12.35가 저장된다. 반면 정수부 자릿수를 넘는 값, 예를 들어 DECIMAL(5,2)에 1000.00을 넣는 것은 범위 초과이므로 엄격 모드에서 거부된다. 소수부는 반올림되고 정수부는 거부된다는 비대칭을 기억해 두자.

    FLOAT와 DOUBLE은 2진 근삿값이다

    FLOAT는 단정밀도로 10진수 약 7자리, DOUBLE은 배정밀도로 약 15자리까지 정확하다고 매뉴얼은 설명한다. REAL과 DOUBLE PRECISION은 DOUBLE의 동의어다(REAL_AS_FLOAT 모드에서는 REAL이 FLOAT). 표준 호환용 문법인 FLOAT(p)는 p가 0~24이면 FLOAT, 25~53이면 DOUBLE이 된다. 비표준 문법인 FLOAT(M,D), DOUBLE(M,D)는 8.0.17부터 사용 중단되었다. 같은 버전부터 FLOAT, DOUBLE, DECIMAL에 붙이는 UNSIGNED도 사용 중단되었고, 매뉴얼은 대신 CHECK 제약을 쓰라고 권한다.

    이 두 자료형은 자바의 float, double과 같은 2진 부동소수점이다. 2진 부동소수점은 0.1 같은 10진 소수를 정확히 표현하지 못하고 가장 가까운 2진수 근삿값을 저장한다. 그 결과 0.1과 0.2를 더해도 정확히 0.3이 되지 않는다(아래 자바 실행 결과 참고). MySQL에서는 반올림 함수에서도 차이가 보인다. 매뉴얼의 예로 SELECT ROUND(2.5), ROUND(25E-1);은 3과 2를 돌려준다. 2.5는 정확한 값 리터럴이라 0에서 먼 쪽으로 반올림되고, 25E-1은 근삿값 리터럴이라 C 라이브러리의 규칙(많은 시스템에서 "가장 가까운 짝수로")을 따르기 때문이다. 금액, 수량, 비율처럼 10진수로 정확해야 하는 값은 DECIMAL로, 측정값처럼 근사가 허용되고 범위가 넓어야 하는 값만 FLOAT나 DOUBLE로 저장한다.

    문자열: CHAR와 VARCHAR, 문자 집합과 콜레이션

    CHAR(M)은 고정 길이, VARCHAR(M)은 가변 길이 문자열이다. 두 경우 모두 M은 바이트가 아니라 글자 수다. CHAR의 M은 0부터 255까지, VARCHAR의 M은 0부터 65,535까지 쓸 수 있지만, VARCHAR의 실제 상한은 뒤에서 볼 행 크기 제한과 문자 집합에 따라 더 작아진다. 매뉴얼은 1바이트 문자 집합(latin1 등)을 가정한 다음 표로 두 자료형의 저장 차이를 보여 준다.

    넣은 값CHAR(4)에 저장된 값저장 바이트VARCHAR(4)에 저장된 값저장 바이트
    ''' '4''1
    'ab''ab '4'ab'3
    'abcd''abcd'4'abcd'5
    'abcdefgh''abcd'4'abcd'5

    CHAR(4)는 값이 짧으면 오른쪽을 공백으로 채워 항상 4글자를 저장한다. VARCHAR(4)는 실제 값만 저장하고 앞에 길이 접두사(length prefix)를 붙인다. 빈 문자열도 길이 0이라는 정보 1바이트가 필요하므로 1바이트, 'abcd'는 4바이트에 접두사 1바이트를 더해 5바이트다. 마지막 행은 엄격 모드가 아닐 때만 해당한다. 엄격 모드에서 공백이 아닌 글자가 잘려 나가야 하는 값은 오류로 거부되고 저장되지 않는다. CHAR에 채운 공백은 꺼낼 때 제거된다(PAD_CHAR_TO_FULL_LENGTH 모드를 켜지 않는 한). 그래서 CHAR(4)에 'ab '처럼 끝에 공백이 있는 값을 넣으면 꺼낼 때 'ab'가 나오지만, VARCHAR(4)는 넣은 공백을 그대로 돌려준다.

    VARCHAR(4) 에 'ab' 저장 (latin1, 1글자 = 1바이트)
  +------+-----+-----+
  | 0x02 |  a  |  b  |        길이 접두사 1바이트 + 데이터 2바이트 = 3바이트
  +------+-----+-----+

CHAR(4) 에 'ab' 저장 (latin1)
  +-----+-----+-----+-----+
  |  a  |  b  | ' ' | ' ' |   항상 4바이트, 남는 자리는 공백으로 채움
  +-----+-----+-----+-----+   (꺼낼 때 끝 공백 제거)
    같은 값 'ab'가 CHAR(4)에서는 공백으로 채운 고정 4칸, VARCHAR(4)에서는 길이 접두사 1칸과 데이터 2칸으로 저장된다는 것을 칸 그림으로 보여 준다. 위아래 두 줄의 바이트 칸 그림. 위쪽 줄 제목 "CHAR(4)": 같은 크기의 칸 4개가 가로로 이어져 있고 차례로 "a", "b", "공백", "공백"이 적혀 있으며 공백 칸 두 개는 연한 회색으로 칠한다. 줄 오른쪽에 라벨 "항상 4바이트". 아래쪽 줄 제목 "VARCHAR(4)": 칸 3개가 이어져 있고 첫 칸은 주황색으로 칠한 "길이 2", 다음 두 칸은 "a", "b"이다. 첫 칸 위에 작은 말풍선 "길이 접두사"를 달고, 줄 오른쪽에 라벨 "3바이트". 두 줄 사이 왼쪽에 큰 따옴표로 묶인 입력값 "'ab'"를 두고 양쪽 줄로 화살표를 그린다. 흰 배경, 단순한 평면 도식. CHAR는 선언한 길이만큼 공백으로 채우고, VARCHAR는 실제 길이를 접두사에 기록한다.

    utf8mb4: 한 글자가 1~4바이트

    이제 글자 수와 바이트 수가 갈라지는 지점이다. MySQL 8.0의 기본 문자 집합 utf8mb4는 완전한 UTF-8이다. 매뉴얼에 따르면 문자 하나에 최대 4바이트를 쓰며, 기본 다국어 평면(BMP)의 문자와 이모지 같은 보충 문자(supplementary character)를 모두 지원한다. UTF-8 인코딩에서 ASCII 문자는 1바이트, 한글 음절은 3바이트, 이모지는 4바이트다. 주의할 것은 이름이 비슷한 utf8이다. MySQL 8.0에서 utf8은 utf8mb4가 아니라 utf8mb3의 별칭이며 사용 중단 상태다. utf8mb3는 문자당 최대 3바이트로 BMP 문자만 저장할 수 있으므로 이모지를 담지 못한다. MySQL 8.4.13과 8.0.46에서 CHARSET utf8로 테이블을 만들면 경고 3719('utf8' is currently an alias for the character set UTF8MB3, ...)가 남고 SHOW CREATE TABLE에는 DEFAULT CHARSET=utf8mb3로 기록되며, 그 열에 이모지를 넣으면 ERROR 1366 (HY000): Incorrect string value: '\xF0\x9F\x98\x80' ...으로 거부된다. 새 스키마에는 항상 utf8mb4를 명시하거나 기본값을 그대로 쓴다.

    길이 접두사의 크기는 그 열의 값이 차지할 수 있는 최대 바이트 수로 정해진다. 매뉴얼에 따르면 값이 0~255바이트 범위에 들면 1바이트, 255바이트를 넘을 수 있으면 2바이트다. utf8mb4에서 VARCHAR(63)은 최대 63×4=252바이트이므로 접두사가 1바이트, VARCHAR(64)는 최대 256바이트이므로 2바이트다. 흔히 쓰는 VARCHAR(100)은 최대 400바이트라 2바이트 접두사를 쓴다.

    VARCHAR의 상한이 65,535글자가 아닌 이유는 행 크기 제한에 있다. 매뉴얼은 스토리지 엔진이 더 큰 행을 지원하더라도 MySQL 테이블의 내부 표현에서 행 하나의 최대 크기가 65,535바이트이고, 이 한도를 모든 열이 나눠 쓴다고 설명한다. BLOB과 TEXT 열은 이 한도에 9~12바이트만 차지한다. 그래서 매뉴얼은 utf8mb4 VARCHAR를 최대 16,383글자까지 선언할 수 있다고 적는다. 계산이 맞아떨어진다. 다른 열이 없을 때 16,383글자×4바이트=65,532바이트에 길이 접두사 2바이트를 더하면 65,534바이트로 한도 안이고, 16,384글자면 65,536바이트만으로 이미 한도를 넘는다. MySQL 8.4.13과 8.0.46에서 VARCHAR(16384) 열 하나짜리 utf8mb4 테이블을 만들려 하면 ERROR 1074 (42000): Column length too big for column 'a' (max = 16383); use BLOB or TEXT instead가 난다. 이보다 긴 텍스트는 TEXT 계열(TEXT는 216바이트 미만, MEDIUMTEXT는 224바이트 미만, LONGTEXT는 232바이트 미만)을 쓴다. 참고로 CHAR(M)의 저장 공간은 원칙적으로 M×(문자 집합의 최대 바이트 수)이지만, 매뉴얼은 InnoDB의 COMPACT 계열 행 형식이 utf8mb4 같은 가변 길이 문자 집합의 CHAR 저장을 최적화한다고 덧붙인다.

    콜레이션: 무엇이 같고 무엇이 앞서는지 정하는 규칙

    문자 집합(character set)이 글자를 어떤 바이트로 저장할지 정한다면, 콜레이션(collation)은 두 문자열을 비교하고 정렬하는 규칙을 정한다. 기본 콜레이션 utf8mb4_0900_ai_ci의 이름은 그 규칙을 그대로 드러낸다. 0900은 유니코드 정렬 알고리즘(UCA) 9.0.0을 기반으로 한다는 뜻이고, ai는 악센트를 구분하지 않음(accent-insensitive), ci는 대소문자를 구분하지 않음(case-insensitive)이다. 그래서 이 콜레이션의 열에서 WHERE name = 'kim'은 'Kim', 'KIM'인 행도 찾는다. 자바의 String.equals()가 대소문자를 구분하는 것과 다르다.

    이 규칙은 조회에서 끝나지 않고 제약 조건에도 적용된다. 이메일 열에 UNIQUE를 걸어 두었고 콜레이션이 대소문자를 구분하지 않으면, 'Kim@example.com'이 있을 때 'kim@example.com'은 중복으로 거부된다. 이메일을 대소문자 구분 없이 하나로 보려는 서비스라면 바라던 동작이고, 구분하려는 서비스라면 장애다. 끝 공백도 콜레이션의 몫이다. 매뉴얼에 따르면 대부분의 MySQL 콜레이션은 PAD SPACE 속성이라 비교할 때 끝 공백을 무시하지만, UCA 9.0.0 이상을 기반으로 한 유니코드 콜레이션은 NO PAD 속성이라 끝 공백도 다른 글자처럼 비교한다. 기본 콜레이션 utf8mb4_0900_ai_ci는 후자다. 어떤 콜레이션의 속성인지는 INFORMATION_SCHEMA.COLLATIONS의 PAD_ATTRIBUTE 열로 확인한다.

    날짜와 시간: DATE, DATETIME, TIMESTAMP

    자료형지원 범위저장 바이트 (MySQL 5.6.4 이후)시간대 변환
    DATE'1000-01-01' ~ '9999-12-31'3없음
    DATETIME'1000-01-01 00:00:00' ~ '9999-12-31 23:59:59'5 + 소수 초 저장분없음
    TIMESTAMP'1970-01-01 00:00:01' UTC ~ '2038-01-19 03:14:07' UTC4 + 소수 초 저장분저장할 때 세션 시간대에서 UTC로, 꺼낼 때 UTC에서 세션 시간대로

    DATETIME과 TIMESTAMP는 소수 초를 최대 6자리(마이크로초)까지 저장할 수 있다. DATETIME(3)처럼 괄호 안에 소수 자릿수를 쓰며, 추가 저장 공간은 0자리면 0바이트, 1~2자리면 1바이트, 3~4자리면 2바이트, 5~6자리면 3바이트다. 따라서 DATETIME(6)은 5+3=8바이트, TIMESTAMP(3)은 4+2=6바이트다. 자바의 LocalDateTime은 나노초까지 담을 수 있지만, MySQL 열에는 마이크로초까지만 남는다는 점을 기억해 두자.

    TIMESTAMP의 상한 '2038-01-19 03:14:07' UTC는 우연한 날짜가 아니다. 1970-01-01 00:00:00 UTC부터 센 초가 231-1, 곧 2,147,483,647초가 되는 순간이 정확히 이 시각이다. 자바에서 Instant.ofEpochSecond(Integer.MAX_VALUE)를 출력하면 2038-01-19T03:14:07Z가 나온다. 4바이트짜리 자료형이 부호 있는 32비트 정수의 한계와 같은 경계를 갖는 것이다. 서비스가 2038년 이후의 날짜(만료일, 장기 계약 종료일 등)를 저장해야 한다면 TIMESTAMP는 처음부터 후보가 아니다.

    TIMESTAMP는 세션 시간대를 따라 움직인다

    두 자료형의 더 중요한 차이는 시간대 처리다. 매뉴얼에 따르면 MySQL은 TIMESTAMP 값을 저장할 때 현재 세션의 시간대에서 UTC로 바꾸고, 꺼낼 때 UTC에서 현재 세션의 시간대로 바꾼다. DATETIME에는 이런 변환이 없다. 세션 시간대는 time_zone 세션 변수로 연결마다 정할 수 있다.

    CREATE TABLE event_log (
    dt DATETIME,
    ts TIMESTAMP
);

SET time_zone = '+09:00';
INSERT INTO event_log VALUES ('2026-11-16 09:00:00', '2026-11-16 09:00:00');

SET time_zone = '+00:00';
SELECT dt, ts FROM event_log;
    +---------------------+---------------------+
| dt                  | ts                  |
+---------------------+---------------------+
| 2026-11-16 09:00:00 | 2026-11-16 00:00:00 |
+---------------------+---------------------+

    추적해 보자. 세션 시간대가 +09:00일 때 넣은 ts 값 09:00은 UTC로 바뀌어 00:00으로 저장된다. dt는 받은 글자 그대로 09:00으로 저장된다. 세션 시간대를 +00:00으로 바꾸고 읽으면 ts는 저장된 UTC 00:00을 +00:00 기준으로 보여 주므로 00:00이 되고, dt는 여전히 09:00이다. 같은 시간대에서 넣고 읽는 한 두 열은 같은 값을 돌려주지만, 연결마다 시간대 설정이 다르면 TIMESTAMP는 같은 순간을 다른 벽시계 시각으로 보여 준다. TIMESTAMP는 "세계 어디서나 같은 한 순간"을, DATETIME은 "시간대 정보 없는 달력과 시계의 숫자"를 저장한다고 보면 정확하다. 매뉴얼에 따르면 8.0.19부터는 '2026-11-16 09:00:00+09:00'처럼 리터럴에 시간대 오프셋을 붙여 넣을 수도 있다.

MySQL의 FLOAT, DOUBLE과 자바의 float, double은 같은 2진 근삿값의 세계에 있고, DECIMAL과 BigDecimal은 같은 10진 정확값의 세계에 있다. Connector/J가 DECIMAL을 BigDecimal로 매핑하는 이유이며, 금액을 DECIMAL 열에 저장해 놓고 자바에서 double로 받는 순간 정확성이 사라진다.

    다음 세 줄은 정수 오버플로다. 자바의 int 덧셈은 범위를 넘으면 오류 없이 2의 보수로 감겨 -2147483648이 된다. Math.addExact를 써야 예외(integer overflow)로 알 수 있다. MySQL은 엄격 모드에서 범위를 넘는 값을 열에 넣으면 오류를 내고, 식 계산의 오버플로도 오류로 처리한다. 그리고 INT UNSIGNED의 최댓값 4294967295를 int로 억지로 바꾸면 -1이 된다. 32비트가 모두 1인 비트 패턴을 부호 있는 정수로 읽은 결과다. 부호 없는 열을 Long으로 받아야 하는 이유가 이것이다.

MySQL의 VARCHAR(M)은 문자 수를 세며 utf8mb4에서 이모지 하나는 한 글자(4바이트)다. 그런데 자바의 String.length()는 UTF-16 코드 단위 수를 세므로 이모지 하나가 2가 된다. 코드 포인트 수(codePointCount)가 MySQL의 글자 수와 맞는다. 애플리케이션에서 length()로 길이를 검사하면, 이모지가 섞인 입력은 실제보다 길게 계산되어 DB가 받아 줄 값을 애플리케이션이 먼저 거부하게 된다. 한글은 자바에서도 MySQL에서도 한 글자지만 utf8mb4로는 3바이트라는 점도 바이트 계산에 필요하다.

    제약 조건: DBMS가 대신 지켜 주는 규칙

    자료형이 "이 열에 올 수 있는 값의 모양"을 정한다면, 제약 조건(constraint)은 "테이블 전체가 지켜야 할 규칙"을 정한다. 값이 비어 있으면 안 된다, 값이 겹치면 안 된다, 다른 테이블에 있는 값만 쓸 수 있다, 이 조건을 만족해야 한다. 앞에서 본 규칙 없는 book 테이블을 지우고, 규칙을 담아 다시 만든다.

    DROP TABLE book;

CREATE TABLE author (
    author_id BIGINT      NOT NULL AUTO_INCREMENT,
    name      VARCHAR(50) NOT NULL,
    PRIMARY KEY (author_id)
);

CREATE TABLE book (
    book_id    BIGINT        NOT NULL AUTO_INCREMENT,
    isbn       CHAR(13)      NOT NULL,
    title      VARCHAR(200)  NOT NULL,
    price      DECIMAL(10,2) NOT NULL,
    stock      INT           NOT NULL DEFAULT 0,
    author_id  BIGINT,
    created_at DATETIME      NOT NULL DEFAULT CURRENT_TIMESTAMP,
    PRIMARY KEY (book_id),
    UNIQUE (isbn),
    CONSTRAINT book_price_chk CHECK (price >= 0),
    FOREIGN KEY (author_id) REFERENCES author (author_id)
);

INSERT INTO author (name) VALUES ('Kim');   -- author_id = 1

    ①성공book_id는 AUTO_INCREMENT로 1, stock은 DEFAULT로 0, created_at은 현재 시각, price는 25000.00으로 저장된다.

    ④실패(엄격 모드)title은 NOT NULL인데 DEFAULT가 없어 채울 값이 없다. 엄격 모드가 아니면 문자열의 암묵적 기본값 ''가 경고와 함께 들어간다.

    NOT NULL과 DEFAULT

    NOT NULL은 그 열에 NULL을 허용하지 않는다. NULL은 0도 빈 문자열도 아닌 "값이 없음 또는 알 수 없음"을 나타내는 표시다. NULL과의 비교가 참도 거짓도 아닌 UNKNOWN이 되는 3값 논리는 조회를 다루는 4회에서 자세히 본다. 여기서는 열을 정의할 때 기본이 "NULL 허용"이라는 점이 중요하다. 매뉴얼은 NULL도 NOT NULL도 지정하지 않은 열을 NULL을 지정한 것처럼 취급한다. 반드시 있어야 하는 값이라면 직접 NOT NULL을 써야 한다.

    DEFAULT는 INSERT가 그 열의 값을 주지 않았을 때 쓸 값을 정한다. 매뉴얼에 따르면 MySQL 8.0.13부터는 리터럴뿐 아니라 괄호로 감싼 식도 기본값으로 쓸 수 있다. 예를 들어 DEFAULT (CURRENT_DATE + INTERVAL 1 YEAR)처럼 쓴다. 예외로 TIMESTAMP와 DATETIME 열은 CURRENT_TIMESTAMP를 괄호 없이 쓸 수 있고, 위 예제의 created_at이 그 경우다. BLOB, TEXT, JSON 열은 리터럴이라도 식 형태(괄호)로 써야만 기본값을 가질 수 있다.

    DEFAULT를 쓰지 않은 열은 어떻게 될까. 매뉴얼에 따르면 NULL을 허용하는 열은 DEFAULT NULL을 가진 것으로 본다. NOT NULL 열에는 명시적 기본값이 없다. 이런 열을 INSERT에서 빼면, 엄격 모드에서는 오류가 나고 트랜잭션 테이블에서는 그 문장이 롤백된다. 엄격 모드가 아니면 자료형의 암묵적 기본값을 넣는다. 숫자형은 0, ENUM을 뺀 문자열형은 빈 문자열, TIMESTAMP를 뺀 날짜·시간형은 그 자료형의 "0" 값이다. 표의 ④가 이 규칙이다. 엄격 모드가 꺼진 서버에서는 제목 없는 책이 빈 문자열 제목으로 조용히 저장된다는 뜻이다.

    UNIQUE: 인덱스가 중복을 막는다

    UNIQUE 제약은 유니크 인덱스(unique index)로 구현된다. 매뉴얼은 UNIQUE 인덱스를 "인덱스의 모든 값이 서로 달라야 한다는 제약"이라고 정의하고, 기존 행과 같은 키 값을 가진 행을 넣으려 하면 오류가 난다고 설명한다. 제약을 지키는 장치가 인덱스라는 점이 중요하다. 정렬된 인덱스에서 같은 값이 있는지 찾는 것은 테이블 전체를 훑는 것보다 훨씬 싸다. 그래서 UNIQUE를 거는 순간 그 열에는 인덱스가 생기고, 그 인덱스는 중복 검사뿐 아니라 그 열로 찾는 조회에도 쓰인다.

    함정이 하나 있다. 매뉴얼에 따르면 모든 엔진에서 UNIQUE 인덱스는 NULL을 허용하는 열에 여러 개의 NULL을 허용한다. NULL은 "알 수 없는 값"이므로 두 NULL이 같다고 판정하지 않는 것이다. 예를 들어 CREATE TABLE t (a INT UNIQUE)에는 (NULL), (NULL)을 넣을 수 있지만 (1), (1)은 오류다. "값이 있다면 겹치면 안 되고, 없을 수는 있다"는 규칙이면 이대로 좋고, "반드시 하나씩 있어야 하고 겹치면 안 된다"면 NOT NULL UNIQUE를 함께 써야 한다. 그리고 앞에서 본 대로 중복 판정은 열의 콜레이션을 따른다.

    PRIMARY KEY: 테이블의 물리적 순서를 정한다

    매뉴얼은 PRIMARY KEY를 "모든 키 열이 NOT NULL이어야 하는 유니크 인덱스"라고 정의한다. 키 열을 NOT NULL로 선언하지 않았으면 MySQL이 암묵적으로(그리고 조용히) NOT NULL로 선언하며, 테이블에는 PRIMARY KEY가 하나만 있을 수 있다. 여기까지는 "UNIQUE에 NOT NULL을 더한 것"으로 보인다. 그러나 InnoDB에서 기본 키는 그 이상이다.

    매뉴얼에 따르면 InnoDB는 테이블에 PRIMARY KEY를 정의하면 그것을 클러스터형 인덱스(clustered index)로 쓴다. 클러스터형 인덱스는 행 데이터 자체를 키 순서로 정렬해 담는 인덱스다. 즉 InnoDB 테이블은 기본 키 순서로 정렬된 하나의 인덱스 구조이고, 그 맨 아래에 행의 모든 열이 들어 있다. 기본 키가 아닌 인덱스, 예를 들어 UNIQUE (isbn)이 만든 인덱스는 보조 인덱스(secondary index)다. 매뉴얼은 InnoDB의 보조 인덱스 레코드마다 보조 인덱스 열과 함께 그 행의 기본 키 열이 들어 있고, InnoDB가 이 기본 키 값으로 클러스터형 인덱스에서 행을 찾는다고 설명한다.

    (book_id 값은 설명을 위한 예시다)

클러스터형 인덱스 (PRIMARY KEY = book_id 순서로 정렬, 행의 모든 열을 담는다)
  [ book_id=1 | isbn=9780000000001 | title=Database Primer | price=25000.00 | ... ]
  [ book_id=2 | isbn=9780000000006 | title=Anonymous       | price=1000.00  | ... ]
  [ book_id=3 | isbn=9780000000007 | title=Rounded         | price=12.35    | ... ]

보조 인덱스 (UNIQUE (isbn)이 만든 인덱스, isbn 순서로 정렬)
  [ isbn=9780000000001 | book_id=1 ]
  [ isbn=9780000000006 | book_id=2 ]  <- 보조 인덱스 레코드에는 기본 키 값이 들어 있다
  [ isbn=9780000000007 | book_id=3 ]

WHERE isbn = '9780000000006' 의 경로 (값은 설명을 위한 예시)
  1) 보조 인덱스에서 isbn 을 찾는다           -> book_id=2 를 얻는다
  2) 클러스터형 인덱스에서 book_id=2 를 찾는다 -> 행 전체를 얻는다

    이 구조에서 두 가지 설계 지침이 바로 나온다. 첫째, 매뉴얼이 직접 말하듯 기본 키가 길면 모든 보조 인덱스가 그 긴 값을 레코드마다 담으므로 공간을 더 쓴다. 짧은 기본 키가 유리하다. BIGINT는 8바이트지만, 36글자 문자열을 기본 키로 쓰면 보조 인덱스 레코드마다 그 문자열이 복사된다. 둘째, 기본 키로 찾는 조회는 클러스터형 인덱스 한 번으로 행 전체에 닿지만, 보조 인덱스로 찾는 조회는 보조 인덱스와 클러스터형 인덱스를 차례로 거친다. 이 인덱스들이 B+Tree라는 구조로 어떻게 생겼고 몇 번의 페이지 읽기로 행에 닿는지는 데이터베이스 기본편의 인덱스 회차에서 다룬다.

    그렇다면 처음에 만든 규칙 없는 book 테이블처럼 기본 키가 없으면 어떻게 될까. 매뉴얼에 따르면 InnoDB는 PRIMARY KEY가 없으면 모든 키 열이 NOT NULL인 첫 번째 UNIQUE 인덱스를 클러스터형 인덱스로 쓴다. 그것도 없으면 행 ID 값을 담는 합성 열 위에 GEN_CLUST_INDEX라는 숨겨진 클러스터형 인덱스를 만든다. 이 행 ID는 6바이트 필드로, 새 행이 들어올 때마다 단조 증가한다. 그래서 숨겨진 인덱스의 행은 물리적으로 넣은 순서대로 놓인다. 사용자는 이 열로 행을 가리킬 수 없으므로, 기본 키 없는 테이블은 "행을 확실히 하나만 가리키는 수단"이 없는 테이블이다. 처음 예제에서 book_id = 1인 행이 두 개 생겨도 막을 방법이 없었던 이유다.

    테이블 자체가 기본 키 순서로 정렬된 클러스터형 인덱스이고, 보조 인덱스는 기본 키 값을 들고 있다가 클러스터형 인덱스를 다시 찾아간다는 두 단계 경로를 보여 준다. 좌우 두 개의 세로 목록 그림. 오른쪽 큰 목록의 제목은 "클러스터형 인덱스 (기본 키 순서)"이며 가로로 긴 행 카드 세 장이 위에서부터 "book_id=1 | 9780000000001 | Database Primer", "book_id=2 | 9780000000006 | Anonymous", "book_id=3 | 9780000000007 | Rounded"로 쌓여 있고 카드마다 끝에 "…"가 있어 모든 열을 담고 있음을 나타낸다. 왼쪽 작은 목록의 제목은 "보조 인덱스 (isbn 순서)"이며 짧은 카드 세 장이 "9780000000001 → 1", "9780000000006 → 2", "9780000000007 → 3"으로 쌓여 있다. 맨 왼쪽 위에 돋보기 아이콘과 라벨 "isbn으로 찾기"를 두고, 돋보기에서 왼쪽 목록의 두 번째 카드로 번호 "1"이 붙은 화살표, 그 카드에서 오른쪽 목록의 두 번째 카드로 번호 "2"가 붙은 굵은 화살표를 그린다. 왼쪽 카드의 오른쪽 끝 숫자 부분을 주황색으로 강조하고 작은 라벨 "기본 키 값"을 단다. 차분한 색, 흰 배경. InnoDB 테이블은 기본 키 순서의 클러스터형 인덱스다. 보조 인덱스는 기본 키 값을 담고 있어서, 보조 인덱스로 찾은 뒤 클러스터형 인덱스를 한 번 더 찾는다.

    AUTO_INCREMENT: 기본 키 값을 서버가 만든다

    기본 키 값을 애플리케이션이 매번 고르기는 번거롭고, 동시에 들어온 두 요청이 같은 값을 고를 위험도 있다. AUTO_INCREMENT는 서버가 새 행에 다음 번호를 붙이게 한다. 매뉴얼의 규칙은 이렇다. 시퀀스는 1부터 시작한다. 테이블에 AUTO_INCREMENT 열은 하나만 있을 수 있고, 그 열은 인덱스가 있어야 하며, DEFAULT 값을 가질 수 없다. 양수 값만 담을 때 제대로 동작한다. 번호에 빈틈이 생길 수 있다는 점도 알아 두자. MySQL 8.4.13과 8.0.46에서 위 ①~⑨를 차례로 실행하면 ⑦과 ⑧의 행은 book_id 2와 3이 아니라 4와 5를 받는다. 실패한 INSERT 가운데 일부가 이미 받은 자동 증가 값을 되돌려 놓지 않기 때문이다. 앞의 클러스터형 인덱스 그림에서 book_id 값을 설명을 위한 예시라고 적은 이유다. 앞에서 본 대로 TRUNCATE TABLE은 이 값을 시작값으로 되돌린다. 매뉴얼에는 SERIAL이라는 별칭도 있는데, BIGINT UNSIGNED NOT NULL AUTO_INCREMENT UNIQUE를 뜻한다. 나중에 JPA에서 엔티티의 식별자 생성 전략을 GenerationType.IDENTITY로 정하면, 바로 이 데이터베이스의 자동 증가 열이 값을 만든다.

    FOREIGN KEY: 다른 테이블에 있는 값만 허용한다

    외래 키(foreign key)는 자식 테이블의 열 값이 부모 테이블의 열 값 중 하나여야 한다는 참조 무결성(referential integrity) 규칙이다. 위 예제에서 book.author_id는 author.author_id에 있는 값이거나 NULL이어야 한다. 이 검사는 양쪽에서 일어난다. 자식 쪽에 행을 넣거나 외래 키 값을 바꿀 때는 부모에 그 값이 있는지 확인하고(표의 ⑥), 부모 쪽 행을 지우거나 키 값을 바꿀 때는 그 값을 참조하는 자식이 있는지 확인한다(표의 ⑨).

    이 확인을 매번 테이블 전체를 훑어 할 수는 없으므로 인덱스가 필요하다. 매뉴얼에 따르면 자식 테이블에는 외래 키 열이 같은 순서로 맨 앞에 오는 인덱스가 있어야 하고, 없으면 MySQL이 자동으로 만든다. InnoDB에서는 부모 테이블에도 참조되는 열이 맨 앞에 오는 인덱스가 있어야 한다. MySQL 8.0 매뉴얼은 부모 열이 반드시 UNIQUE나 NOT NULL일 필요는 없다고 하면서도(이것은 표준 SQL이 아니라 InnoDB의 확장이다), 비유일 키나 NULL을 담은 키를 참조할 때의 동작은 잘 정의되어 있지 않으니 UNIQUE(기본 키 포함)이면서 NOT NULL인 키만 참조하라고 권한다. MySQL 8.4에서는 이 확장이 사용 중단되었고, 기본값이 ON인 restrict_fk_on_non_standard_key 변수 때문에 비유일 키나 부분 키를 참조하는 외래 키는 기본적으로 거부된다. 일반 인덱스만 있는 열을 참조하는 외래 키를 만들어 보면 MySQL 8.0.46은 받아들이지만, MySQL 8.4.13은 ERROR 6125 (HY000): Failed to add the foreign key constraint. Missing unique key for constraint 'chi_ibfk_1' in the referenced table 'par'로 거부한다(par, chi는 확인용으로 만든 부모·자식 테이블이다).

    부모 행을 지우거나 바꿀 때 자식이 있으면 무엇을 할지는 참조 동작(referential action)으로 정한다.

    참조 동작InnoDB에서의 의미
    RESTRICT부모 행의 삭제·변경을 거부한다.
    NO ACTION표준 SQL의 키워드. InnoDB에서는 RESTRICT와 같아서 관련 자식이 있으면 즉시 거부한다. ON DELETE, ON UPDATE를 생략했을 때의 기본값이다.
    CASCADE부모 행을 지우거나 바꾸면 일치하는 자식 행도 함께 지우거나 바꾼다.
    SET NULL부모 행을 지우거나 바꾸면 자식의 외래 키 열을 NULL로 바꾼다. 자식 열이 NOT NULL이면 안 된다.
    SET DEFAULT파서는 인식하지만 InnoDB는 이 동작을 수행하지 않는다. 매뉴얼은 InnoDB가 이 동작이 든 테이블 정의를 거부한다고 적지만, MySQL 8.4.13과 8.0.46에서 실행해 보면 ON DELETE SET DEFAULT를 쓴 테이블은 오류 없이 만들어지고 SHOW CREATE TABLE에도 그대로 남는다. 그 상태에서 자식이 있는 부모 행을 지우면 자식 열을 기본값으로 바꾸지 않고 ERROR 1451로 삭제를 거부한다. 쓸 이유가 없는 동작이다.

    표의 ⑦에서 외래 키가 NULL인 행이 들어간 이유도 매뉴얼에 있다. MySQL은 사실상 MATCH SIMPLE의 의미를 구현하므로, 외래 키가 전부 또는 일부 NULL인 자식 행은 부모의 어떤 행과도 일치하지 않아도 넣을 수 있다. 같은 절에서 매뉴얼은 InnoDB를 포함한 어떤 엔진도 MATCH 절을 인식하거나 강제하지 않으며, MATCH 절을 명시하면 효과가 없을 뿐 아니라 ON DELETE와 ON UPDATE 절까지 무시되게 만든다고 경고한다. 앞에서 말한 대로 MySQL은 외래 키를 즉시 검사하고 커밋 시점으로 미루지 않는다.

    외래 키에서 가장 흔한 함정은 문법이다. MySQL 8.0과 8.4 매뉴얼에 따르면 MySQL은 열 정의 안에 쓴 "인라인 REFERENCES"를 파싱하지만 무시하고, 별도의 FOREIGN KEY 절로 쓴 것만 받아들인다. 이 동작은 MySQL 9.0.0에서 바뀌어, 그 이후 버전은 인라인 REFERENCES도 외래 키로 받아들여 강제한다.

    -- MySQL 8.0·8.4: 오류 없이 만들어지지만 외래 키는 생기지 않는다(인라인 REFERENCES는 무시)
CREATE TABLE book_wrong (
    book_id   BIGINT PRIMARY KEY,
    author_id BIGINT REFERENCES author (author_id)
);

-- 외래 키가 생긴다
CREATE TABLE book_right (
    book_id   BIGINT PRIMARY KEY,
    author_id BIGINT,
    FOREIGN KEY (author_id) REFERENCES author (author_id)
);

    MySQL 8.4.13과 8.0.46에서 실행해 보면 두 테이블 모두 오류 없이 만들어지지만, INFORMATION_SCHEMA.REFERENTIAL_CONSTRAINTS에는 book_right_ibfk_1만 나오고, book_wrong에는 author에 없는 author_id 999를 넣어도 오류가 나지 않는다. 첫 번째 테이블은 오류 없이 만들어지므로, 외래 키가 있다고 믿은 채 운영하다가 존재하지 않는 저자를 가리키는 행이 쌓인 뒤에야 알게 된다. 제약을 만든 뒤에는 SHOW CREATE TABLE로 실제로 FOREIGN KEY가 정의에 있는지 확인하는 습관이 이런 사고를 막는다. 마지막으로 foreign_key_checks 시스템 변수는 외래 키 검사를 켜고 끈다. 기본으로 켜져 있고, 덤프 파일을 순서와 무관하게 다시 넣을 때처럼 잠시 끄는 용도로 쓴다. 매뉴얼은 다시 켤 때 기존 데이터를 검사하지 않으므로, 꺼져 있는 동안 들어온 행의 무결성은 보장되지 않는다고 적는다.

    CHECK: 행이 만족해야 할 조건

    CHECK는 행마다 평가할 조건식을 정한다. 매뉴얼에 따르면 MySQL은 8.0.16부터 CHECK 제약을 모든 스토리지 엔진에서 실제로 강제한다. 그 이전 버전은 CHECK 문법을 받아들이되 파싱만 하고 무시했다. 같은 CREATE TABLE 문이 8.0.15 서버에서는 아무 검사도 하지 않는다는 뜻이므로, 서버 버전을 확인하지 않고 CHECK에 의존하면 안 된다. NOT ENFORCED를 붙이면 제약을 만들되 강제하지 않는다. 이름을 주지 않으면 MySQL이 테이블 이름, _chk_, 순번을 이어 book_chk_1 같은 이름을 만든다. CHECK 제약 이름은 스키마 안에서 유일해야 하므로, 위 예제처럼 테이블 이름을 앞에 붙여 직접 짓는 편이 충돌을 피하기 쉽다.

    평가 규칙에서 가장 중요한 것은 NULL이다. 매뉴얼은 조건식이 각 행에 대해 TRUE이거나 UNKNOWN(NULL 값 때문에)이어야 하고, FALSE일 때만 위반이라고 정한다. 그래서 c INT CHECK (c > 0) 열에 NULL을 넣으면 NULL > 0이 UNKNOWN이므로 통과한다. 위 예제의 price는 NOT NULL이라 문제가 없지만, NULL을 허용하는 열에 CHECK를 걸 때는 "값이 없으면 검사도 없다"는 점을 함께 설계해야 한다. 즉 CHECK는 "값이 있다면 이 조건을 만족해야 한다"는 규칙이고, "값이 있어야 한다"는 NOT NULL의 몫이다.

    조건식에 쓸 수 있는 것에도 제한이 있다. 매뉴얼에 따르면 리터럴, 결정적(deterministic) 내장 함수, 연산자는 쓸 수 있지만 NOW(), CURRENT_USER(), CONNECTION_ID() 같은 비결정적 함수, 저장 함수, 서브쿼리, 변수, 다른 테이블의 열, AUTO_INCREMENT 열은 쓸 수 없다. 이유를 생각해 보면 자연스럽다. CHECK는 "이 행이 지금 규칙을 만족하는가"를 행 안의 값만으로 판정할 수 있어야 한다. 실행 시각이나 다른 테이블의 상태에 따라 결과가 바뀐다면, 어제 통과한 행이 오늘은 규칙 위반이 되는 모순이 생긴다. 다른 테이블과의 관계는 외래 키가, 시점에 따라 달라지는 규칙은 애플리케이션이 맡는다.

    이 장의 핵심

    MySQL에서 데이터베이스는 디렉터리이고, InnoDB 테이블은 기본 키 순서로 정렬된 클러스터형 인덱스이며, 그 정의는 데이터 사전에 있다. 자료형은 값의 바이트 표현과 허용 범위와 비교 규칙을 정하고, 제약 조건은 쓰기 순간에 서버가 직접 검사하는 규칙이다. 이 둘이 실제로 얼마나 엄격하게 지켜지는지는 SQL 모드, 콜레이션, 서버 버전, 스토리지 엔진에 따라 달라지므로, "선언했다"와 "지켜진다"를 구분해 확인해야 한다.

    흔한 오해와 함정

    • "INT(11)은 11자리까지 저장한다." 괄호 안은 표시 너비일 뿐 범위와 무관하고, 8.0.17부터 사용 중단되었다. INT의 범위는 4바이트가 정한다.
    • "VARCHAR(100)은 100바이트다." 100은 글자 수다. utf8mb4에서는 최대 400바이트까지 차지할 수 있고, 그래서 길이 접두사도 2바이트다. 한글 100자는 300바이트다.
    • "문자 집합을 utf8로 하면 모든 유니코드를 저장한다." MySQL 8.0에서 utf8은 utf8mb3의 별칭이며, 4바이트 문자(이모지 등)를 저장하지 못한다. utf8mb4를 쓴다.
    • "UNIQUE면 NULL도 하나만 들어간다." UNIQUE 인덱스는 NULL을 여러 개 허용한다. 반드시 있어야 한다면 NOT NULL을 함께 쓴다.
    • "열 옆에 REFERENCES를 썼으니 외래 키가 있다." MySQL 8.0·8.4에서 인라인 REFERENCES는 파싱만 되고 무시된다(9.0.0부터는 강제된다). FOREIGN KEY (...) REFERENCES ... 절로 써야 한다.
    • "CHECK를 썼으니 규칙이 지켜진다." 8.0.16 이전 서버는 무시한다. 8.0.16 이후에도 조건이 UNKNOWN이면 통과하므로 NULL은 걸러지지 않는다.
    • "트랜잭션 안에서 실행했으니 ROLLBACK으로 모두 되돌릴 수 있다." DDL, 계정 관리 문 등은 실행 전에 암묵적 커밋을 일으킨다. 그 앞의 변경은 이미 확정된다.
    • "금액은 DOUBLE로 충분하다." 2진 부동소수점은 0.1조차 정확히 담지 못한다. 금액은 DECIMAL, 자바에서는 BigDecimal로 다룬다.
    • "잘못된 값을 넣으면 당연히 오류가 난다." 엄격 모드일 때만 그렇다. 엄격 모드가 꺼진 서버는 값을 끝값으로 자르거나 암묵적 기본값을 넣고 경고만 남긴다. 그리고 소수 자릿수 반올림은 엄격 모드에서도 오류가 아니다.

    이 회차의 내용이 다시 쓰이는 곳

    바로 다음 회차는 이 회차의 문장들을 본격적으로 쓴다. 테이블을 만들고 바꾸고 지우는 DDL과, 행을 넣고 고치고 지우는 DML, 그리고 제약 조건을 실제 상황에 적용하는 연습이 이어진다. 4회의 조회와 정렬에서는 이 회차에서 미뤄 둔 NULL의 3값 논리와 ORDER BY 없는 결과 순서의 문제가 중심이 되고, 5회와 6회의 데이터 가공과 집계에서는 자료형에 따라 함수와 연산의 결과가 달라지는 모습을 보게 된다.

    더 멀리 보면, 클러스터형 인덱스와 보조 인덱스의 관계는 데이터베이스 기본편의 인덱스 회차에서 B+Tree 구조와 함께 다시 나오고, 자동 커밋과 암묵적 커밋은 같은 권의 트랜잭션 회차와 스프링 DB 권에서 커넥션, 세션, 트랜잭션 관리자의 관계로 이어진다. JPA 권에서는 엔티티의 식별자가 이 회차의 기본 키와 AUTO_INCREMENT에, 엔티티 필드의 자바 타입이 이 회차의 자료형 매핑에 대응한다. 어느 단계에서든 "선언한 것이 실제로 어떻게 저장되고 검사되는가"라는 이 회차의 질문을 다시 던지게 된다.
    클라이언트/서버 구조
    데이터 파일을 다루는 것은 mysqld 서버 프로세스이고, mysql 명령·JDBC 드라이버는 문장을 보내고 결과를 받는 클라이언트다. 연결마다 전용 스레드와 세션 상태(기본 DB, sql_mode, time_zone, autocommit)가 생긴다.
    데이터베이스 = 디렉터리
    CREATE DATABASE는 데이터 디렉터리 아래에 디렉터리를 만들고, InnoDB 테이블은 기본적으로 테이블마다 .ibd 파일이 된다. 그래서 테이블 이름의 대소문자 구분이 파일 시스템과 lower_case_table_names를 따른다.
    데이터 사전
    MySQL 8.0은 테이블 정의 같은 메타데이터를 mysql.ibd 안의 InnoDB 테이블에 트랜잭션으로 저장한다. 사전 테이블은 직접 조회할 수 없고 INFORMATION_SCHEMA로 본다.
    SQL의 분류와 암묵적 커밋
    SQL은 원하는 결과만 기술하는 선언형 언어이고, 문장은 DDL·DML·DCL·TCL로 나뉜다. DDL과 계정 관리 문 등은 실행 전에 활성 트랜잭션을 커밋하므로 롤백으로 되돌릴 수 없다.
    엄격 SQL 모드
    8.0 기본값에 포함된 STRICT_TRANS_TABLES는 잘못된 값을 오류로 거부한다. 꺼져 있으면 범위 밖 값은 끝값으로 잘리고 빠진 값은 암묵적 기본값이 되며 경고만 남는다.
    수치 자료형
    정수형은 바이트 수가 범위를 정하고 INT(11)의 11은 범위와 무관하다. DECIMAL은 10진수 아홉 자리를 4바이트에 담아 정확하고, FLOAT·DOUBLE은 2진 근삿값이다.
    문자열과 콜레이션
    CHAR(M)·VARCHAR(M)의 M은 글자 수이며 utf8mb4에서 한 글자는 1~4바이트다. 콜레이션이 비교와 중복 판정 규칙을 정하고, 기본 utf8mb4_0900_ai_ci는 대소문자를 구분하지 않는다.
    DATETIME과 TIMESTAMP
    DATETIME은 시간대 정보 없는 값을 그대로, TIMESTAMP는 세션 시간대와 UTC 사이를 변환해 저장한다. TIMESTAMP의 상한은 2038-01-19 03:14:07 UTC다.
    제약 조건과 클러스터형 인덱스
    NOT NULL·DEFAULT·UNIQUE·PRIMARY KEY·FOREIGN KEY·CHECK는 쓰기 순간 서버가 검사한다. InnoDB에서 기본 키는 행을 정렬해 담는 클러스터형 인덱스이고, 보조 인덱스는 기본 키 값을 담는다.

    실무에서 자료형과 기본 키를 고를 때 이 회차의 계산이 그대로 쓰인다. InnoDB의 보조 인덱스는 레코드마다 기본 키 값을 담으므로, 기본 키의 크기는 그 테이블의 모든 인덱스 크기에 곱해진다. 그래서 대리 키로 BIGINT AUTO_INCREMENT를 쓰는 선택이 흔하다. 외부에 노출할 식별자로 UUID 같은 긴 문자열이 필요하다면, 그것을 기본 키로 둘지 아니면 별도의 UNIQUE 열로 두고 기본 키는 짧게 유지할지를 이 구조를 근거로 판단한다. 반대로 정수형을 너무 작게 잡는 실수도 있다. INT로 만든 자동 증가 키가 2,147,483,647에 닿으면 더 이상 행을 넣을 수 없고, 운영 중인 큰 테이블의 자료형 변경은 그 자체로 큰 작업이 된다.

    시간 자료형은 서비스가 다루는 시간의 의미로 고른다. 여러 지역의 사용자가 같은 한 순간을 공유하는 이벤트 시각이라면 TIMESTAMP의 UTC 변환이 편리하지만, 2038년 상한과 "연결마다 다른 세션 시간대" 문제를 함께 떠안는다. 커넥션 풀의 모든 커넥션이 같은 시간대로 설정되어 있는지 확인해야 한다. DATETIME을 쓰고 애플리케이션이 항상 UTC로 변환해 넣는 정책을 정하는 팀도 많다. 어느 쪽이든 핵심은 "이 열의 값이 어느 시간대 기준인가"를 스키마 설계 시점에 문서로 못 박는 것이다.

    외래 키를 데이터베이스에 둘지는 팀마다 판단이 갈린다. 외래 키는 어떤 경로로 쓰든 참조 무결성을 보장하지만, 자식 행을 쓸 때마다 부모를 확인하고 양쪽에 인덱스를 요구하며, 대량 적재나 테이블 분리 작업에서 foreign_key_checks를 꺼야 하는 경우가 생긴다. 다시 켜도 기존 데이터를 검사하지 않는다는 점은 그 작업 뒤에 별도의 검증이 필요하다는 뜻이다. 외래 키를 쓰지 않기로 했다면 그 무결성을 누가 어떻게 지킬지를 대신 정해야 한다.

    마지막으로, 레거시 서버를 넘겨받으면 먼저 SELECT @@sql_mode;와 SELECT VERSION();을 확인한다. 엄격 모드가 꺼져 있으면 지금까지 "잘 동작하던" INSERT 중 일부는 사실 값을 자르거나 빈 값을 넣고 있었을 수 있고, 엄격 모드를 켜는 순간 그 문장들이 오류로 바뀐다. 8.0.16 미만 서버라면 스키마에 적힌 CHECK는 아무것도 지키지 않고 있다. 선언된 규칙과 실제로 지켜지는 규칙의 차이를 아는 것이 장애 분석의 출발점이다.
  • DECIMAL(5,2), DECIMAL(12,4), DECIMAL(20,6) 열 하나가 각각 몇 바이트를 차지하는지 정수부와 소수부를 나눠 계산하라. 그리고 DECIMAL(5,2) 열에 999.995를 넣으면 어떻게 될지 예측하라.

DECIMAL(20,6)은 정수부 14자리가 아홉 자리 묶음 하나(4바이트)와 나머지 5자리(3바이트)로 7바이트, 소수부 6자리가 3바이트이므로 합계 10바이트다. 999.995는 소수 둘째 자리로 맞추면서 0에서 먼 쪽으로 반올림되어 1000.00이 되는데, 이 값은 정수부 4자리라 DECIMAL(5,2)의 최댓값 999.99를 넘는다. 따라서 엄격 모드에서는 범위 초과 오류로 거부된다. 소수부 반올림 자체는 오류가 아니지만, 반올림 결과가 정수부 범위를 넘으면 범위 검사에 걸린다는 점이 핵심이다.

     자동 커밋이 켜진 세션에서 START TRANSACTION; INSERT INTO t VALUES (1); ALTER TABLE t ADD COLUMN c INT; INSERT INTO t (id) VALUES (2); ROLLBACK;을 차례로 실행했다(t는 InnoDB 테이블). 끝난 뒤 테이블 t의 상태로 옳은 것은? 두 행 모두 없고 열 c도 없다. ROLLBACK이 트랜잭션 전체를 되돌린다. 행 2만 있고 열 c가 있다. ROLLBACK이 ALTER TABLE 이전의 행 1을 되돌린다. 행 1과 행 2가 모두 있고 열 c가 있다. 행 1만 있고 열 c는 없다. ALTER TABLE은 DDL이므로 실행 전에 활성 트랜잭션을 암묵적으로 커밋해 행 1이 확정되고, 이어서 열 c가 추가된다. 그 뒤에는 START TRANSACTION으로 연 트랜잭션이 이미 끝났으므로 세션은 자동 커밋 상태로 돌아가 있고, 두 번째 INSERT는 문장 하나가 곧 트랜잭션이 되어 즉시 커밋된다. 따라서 마지막 ROLLBACK은 되돌릴 것이 없다. 보기 0은 암묵적 커밋을 무시했고, 보기 3은 DDL도 롤백된다고 본 것이다. 보기 1은 방향을 거꾸로 이해했다. 암묵적 커밋이 확정하는 것은 ALTER TABLE 이전의 변경이고, 두 번째 INSERT가 남는 이유는 트랜잭션이 끝난 뒤 자동 커밋으로 돌아갔기 때문이다. MySQL 8.0.16 이상에서 CREATE TABLE p (price DECIMAL(10,2) CHECK (price >= 0));로 만든 테이블에 INSERT INTO p VALUES (NULL);을 실행하면? CHECK 위반 오류가 난다. NULL은 0 이상이 아니기 때문이다. 성공한다. 조건이 UNKNOWN이면 CHECK는 위반으로 보지 않는다. 성공하지만 price에 0이 저장된다. 테이블 생성 단계에서 오류가 난다. NULL을 허용하는 열에는 CHECK를 걸 수 없다. 매뉴얼은 CHECK 조건이 TRUE 또는 UNKNOWN이면 통과하고 FALSE일 때만 위반이라고 정한다. NULL >= 0은 UNKNOWN이므로 행이 들어가고 price는 NULL이다. 값의 존재를 강제하려면 NOT NULL을 따로 붙여야 한다. NULL을 0으로 바꾸는 규칙은 없고, NULL 허용 열에도 CHECK를 걸 수 있다. InnoDB 테이블은 언제나 클러스터형 인덱스로 저장된다. 엄격 모드가 켜진 MySQL 8.0에서 n INT(3)으로 정의한 열에 12345를 넣으면? 12345가 그대로 저장된다. 범위 초과 오류가 나서 저장되지 않는다. 999로 잘려 저장되고 경고가 남는다. 123으로 잘려 저장된다. INT(3)의 3은 표시 너비이며 매뉴얼은 표시 너비가 저장 가능한 값의 범위를 제한하지 않는다고 명시한다. 범위는 INT의 4바이트가 정하므로 12345는 범위 안이고 그대로 저장된다. 표시 너비 문법은 8.0.17부터 사용 중단되었다. 끝값으로 자르는 동작은 자료형 범위를 넘을 때, 그것도 엄격 모드가 아닐 때의 이야기다. 문자 집합이 utf8mb4인 VARCHAR(10) 열에 한글 10글자로 된 문자열을 저장하면 그 값은 몇 바이트를 차지하는가? 11바이트 31바이트 32바이트 41바이트 저장할 수 없다. 10바이트를 넘기 때문이다. VARCHAR(10)의 10은 글자 수이므로 한글 10글자는 허용된다. UTF-8에서 한글 음절은 3바이트라 데이터는 30바이트다. 길이 접두사는 열의 최대 바이트 수로 정해지는데, 10글자×최대 4바이트=40바이트로 255 이하이므로 1바이트다. 합계 31바이트다. 32바이트는 접두사를 2바이트로, 41바이트는 데이터를 글자당 4바이트로 잘못 센 값이다.
    스키마(schema)
    테이블 등 데이터베이스 객체를 묶는 이름 공간. MySQL에서는 데이터베이스와 같은 말이며 CREATE SCHEMA는 CREATE DATABASE의 동의어다.
    데이터 사전(data dictionary)
    테이블 정의 같은 데이터베이스 객체의 메타데이터를 저장하는 곳. MySQL 8.0에서는 mysql.ibd 안의 InnoDB 테이블로 트랜잭션 보호를 받으며, INFORMATION_SCHEMA를 통해 조회한다.
    스토리지 엔진(storage engine)
    데이터를 디스크와 메모리에 실제로 저장하고 읽고 쓰는 MySQL의 구성 요소. 테이블마다 지정할 수 있고 8.0의 기본은 InnoDB다.
    세션(session)
    연결 하나가 유지되는 동안 서버가 기억하는 그 연결의 상태. 기본 데이터베이스, sql_mode, time_zone, autocommit 같은 세션 변수를 포함한다.
    암묵적 커밋(implicit commit)
    DDL, 계정 관리 문 등이 실행되기 전에 현재 트랜잭션을 COMMIT한 것처럼 끝내는 동작. 그 앞의 변경은 ROLLBACK으로 되돌릴 수 없다.
    엄격 SQL 모드(strict SQL mode)
    STRICT_TRANS_TABLES 또는 STRICT_ALL_TABLES가 켜진 상태. 잘못된 값이나 빠진 값을 조정하지 않고 오류로 거부한다.
    콜레이션(collation)
    문자열의 비교·정렬 규칙. 대소문자와 악센트를 구분하는지, 끝 공백을 무시하는지(PAD SPACE와 NO PAD)를 정하며 UNIQUE 중복 판정에도 쓰인다.
    클러스터형 인덱스(clustered index)
    행 데이터 자체를 키 순서로 정렬해 담는 인덱스. InnoDB에서는 기본 키가 클러스터형 인덱스이고, 보조 인덱스 레코드는 기본 키 값을 담는다.
    참조 무결성(referential integrity)
    자식 테이블의 외래 키 값이 부모 테이블에 존재하는 값(또는 NULL)이어야 한다는 규칙. FOREIGN KEY 제약과 참조 동작으로 지킨다.
    고정소수점(fixed-point)
    10진 자릿수를 정해 두고 정확한 값을 저장하는 수 표현. MySQL의 DECIMAL이 해당하며, 근삿값을 저장하는 2진 부동소수점(FLOAT, DOUBLE)과 대비된다.
