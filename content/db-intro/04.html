    이 회차의 질문: 저장된 행 가운데 필요한 것만 꺼내기

    03회에서 CREATE TABLE로 그릇을 만들고 INSERT, UPDATE, DELETE로 내용을 바꿨다. 데이터를 넣는 이유는 결국 꺼내 쓰기 위해서다. 그런데 꺼내는 일은 넣는 일보다 훨씬 다양하다. 한 테이블에서 "재고가 있는 IT 책을 비싼 순으로 세 권", "할인율이 아직 정해지지 않은 책", "저자 목록을 중복 없이"처럼 같은 데이터를 수십 가지 모양으로 꺼낸다. 이 회차는 그 꺼내는 문장, 즉 SELECT 문의 기본 절들을 다룬다.

    자바 개발자에게 익숙한 방식으로 먼저 같은 일을 해 보자. 책 목록이 힙의 List에 있다면 스트림으로 거르고, 정렬하고, 개수를 자른다.

    import java.util.Comparator;
import java.util.List;

public class Main {
    record Book(String title, String category, int price) {}

    public static void main(String[] args) {
        List books = List.of(
                new Book("데이터베이스 첫걸음", "IT", 28000),
                new Book("바다의 시간", "소설", 14000),
                new Book("네트워크 바닥부터", "IT", 35000));

        List result = books.stream()
                .filter(b -> b.category().equals("IT"))
                .sorted(Comparator.comparingInt(Book::price).reversed())
                .limit(3)
                .toList();
        result.forEach(b -> System.out.println(b.title() + " " + b.price()));
    }
}

    같은 요구를 SQL로 쓰면 한 문장이다.

    SELECT title, price
FROM book
WHERE category = 'IT'
ORDER BY price DESC
LIMIT 3;

    두 코드는 겉모양이 비슷하지만 성격이 다르다. 스트림 코드는 모든 원소를 힙에 올려 둔 상태에서 "이 순서로 이렇게 처리하라"는 절차를 적는다. SQL 문은 "이런 조건을 만족하는 행을 이 순서로 이만큼 달라"는 결과의 모양만 적고, 그 결과를 어떻게 만들지는 데이터베이스 서버가 정한다. 이런 언어를 선언적 언어(declarative language)라고 한다. 서버는 테이블을 처음부터 끝까지 읽을 수도 있고, 인덱스를 따라 IT 책만 골라 읽을 수도 있으며, 인덱스가 이미 가격 순으로 정렬되어 있다면 정렬을 건너뛰고 세 행만 읽고 멈출 수도 있다.

    이 차이에서 이 회차의 모든 주제가 나온다. 결과의 모양만 약속하기 때문에 약속하지 않은 것, 예를 들어 ORDER BY를 쓰지 않았을 때의 행 순서는 보장되지 않는다. 실행 방법을 서버가 고르기 때문에 같은 뜻의 조건이라도 쓰는 형태에 따라 인덱스를 쓰기도 하고 못 쓰기도 한다. 그리고 SQL에는 자바에 없는 "알 수 없음"이라는 세 번째 진릿값이 있어서, 자바의 filter처럼 생각하고 쓴 조건이 행을 조용히 빠뜨리기도 한다. 이 회차는 SELECT, WHERE, ORDER BY, LIMIT, DISTINCT, NULL을 차례로 다루면서 각 절이 결과에 무엇을 약속하고 서버 안에서 어떤 일을 일으키는지 따라간다. 문자열·숫자·날짜를 가공하는 함수는 05회, GROUP BY와 집계 함수는 06회의 몫이므로 여기서는 필요한 만큼만 언급한다.

    조회 실습 데이터 준비: 함정이 들어 있는 열 개의 행

    조회를 연습할 테이블을 만든다. 행은 열 개뿐이지만 일부러 함정을 심었다. 같은 분류의 책이 여러 권 있어 정렬에서 동점이 생기고, 같은 저자가 여러 번 나와 중복 제거를 확인할 수 있으며, 할인율 열에는 NULL과 0이 섞여 있다. 제목 하나에는 LIKE의 와일드카드 문자인 %가 들어 있다. 이 예제는 이 강좌를 위해 새로 만든 것이다.

    설계에서 눈여겨볼 점이 세 가지 있다. 첫째, discount_rate만 NULL을 허용한다. 이 테이블에서 NULL은 "할인율을 아직 정하지 않았다"는 뜻이고, 0은 "할인하지 않기로 정했다"는 뜻이다. 둘은 업무적으로 완전히 다른 상태이며, 이 회차의 뒷부분에서 SQL이 둘을 얼마나 다르게 다루는지 보게 된다. 재고 stock이 0인 책(2번, 7번)은 "재고가 없다는 것을 안다"는 값이지 모르는 값이 아니다.

    둘째, 기본 키 외에 보조 인덱스(secondary index)를 두 개 만들었다. idx_category_price는 분류와 가격을 묶은 복합 인덱스이고, idx_published_on은 출간일 인덱스다. 03회에서 본 대로 InnoDB 테이블의 행은 기본 키 순서로 정렬된 클러스터형 인덱스(clustered index)의 리프에 저장되고, 보조 인덱스의 리프에는 인덱스 열 값과 기본 키 값이 들어 있다. 이 구조가 WHERE와 ORDER BY의 비용을 정한다. 다만 행이 열 개뿐인 테이블에서는 옵티마이저가 인덱스보다 전체 스캔을 고르는 경우가 많다. 옵티마이저는 비용을 추정해 실행 방법을 고르는데, 페이지 하나에 다 들어가는 테이블은 그냥 다 읽는 편이 싸기 때문이다. 이 회차에서 인덱스 이야기는 행이 수십만 건 이상인 테이블을 머리에 두고 읽으면 된다.

    셋째, 문자 집합과 콜레이션(collation)을 지정하지 않았다. MySQL 8.0 서버의 기본 문자 집합은 utf8mb4, 기본 콜레이션은 utf8mb4_0900_ai_ci다. 데이터베이스나 테이블에서 따로 지정하지 않으면 이 값을 물려받는다. 콜레이션 이름의 ai는 악센트를 구분하지 않음(accent-insensitive), ci는 대소문자를 구분하지 않음(case-insensitive)을 뜻한다. 문자열 비교와 정렬의 결과가 이 설정에 따라 달라지므로, 뒤에서 WHERE와 ORDER BY를 다룰 때 다시 꺼낸다.

    SELECT: 무엇을 꺼낼지 선언한다

    가장 단순한 조회는 테이블의 모든 열과 모든 행을 가져오는 것이다.

    SELECT * FROM book;

    SELECT 뒤에 오는 것을 선택 목록(select list)이라고 한다. 여기에 열 이름을 나열하면 그 열만 결과에 남는다. 관계형 모델의 용어로는 이 연산을 투영(projection)이라고 부른다. 테이블이라는 입체를 특정 열이라는 면에 비추어 그림자만 남긴다는 뜻이다. 재미있는 점은 관계 대수에서 행을 고르는 연산은 선택(selection) 또는 제한(restriction)이라고 부르는데, SQL에서 그 일을 하는 것은 SELECT가 아니라 WHERE라는 사실이다. SQL의 SELECT 키워드는 이름과 달리 열을 고르고, 행을 고르는 일은 WHERE가 한다.

    SELECT title, price * stock AS stock_amount
FROM book
WHERE category = '역사';

| title       | stock_amount |
+-------------+--------------+
| 조선의 시장 |       110000 |
| 실록 읽기   |       234000 |
+-------------+--------------+

    선택 목록에는 열 이름만이 아니라 식(expression)도 올 수 있다. price * stock은 행마다 계산되어 새 열이 되고, AS stock_amount로 그 열에 별칭(alias)을 붙였다. 별칭은 결과 열의 이름일 뿐 테이블에 저장되지 않는다. 별칭에 공백이나 예약어를 쓰고 싶다면 MySQL의 식별자 인용 문자인 백틱(`)으로 감싼다. 결과의 두 행 순서는 이 문장이 보장하지 않는다는 점도 기억해 두자. 위 출력은 한 가지 가능한 순서일 뿐이며, 이유는 ORDER BY에서 다룬다.

    비교식도 값이다. MySQL에서 비교 연산의 결과는 1(참), 0(거짓), NULL(알 수 없음) 중 하나이므로 선택 목록에 그대로 쓸 수 있다.

    SELECT title, price, price >= 30000 AS expensive
FROM book
WHERE category = 'IT'
ORDER BY book_id;

| title               | price | expensive |
+---------------------+-------+-----------+
| 데이터베이스 첫걸음 | 28000 |         0 |
| 자바 메모리 구조    | 32000 |         1 |
| 네트워크 바닥부터   | 35000 |         1 |
| SQL 100% 활용       | 30000 |         1 |
+---------------------+-------+-----------+

    테이블 없이 식만 계산할 수도 있다. SELECT 1 + 1;은 2를 돌려준다. 모든 SELECT에 FROM이 있어야 한다고 생각하는 사람을 위해 MySQL은 DUAL이라는 가짜 테이블 이름을 허용하지만(SELECT 1 + 1 FROM DUAL;), 참조하는 테이블이 없으면 FROM을 생략해도 된다. 접속한 서버의 버전을 확인하는 SELECT VERSION();도 같은 형태다.

    SELECT *를 쓰지 말라는 말의 근거

    SELECT *는 편하지만 실무 코드에서는 피하라는 조언을 자주 듣는다. 이 조언에는 막연한 취향이 아니라 구체적인 근거가 있다. 첫째, 필요 없는 열까지 서버에서 읽고, 네트워크로 보내고, 애플리케이션 메모리에 올린다. 긴 TEXT 열이 하나 섞여 있으면 차이가 커진다. 둘째, 커버링 인덱스(covering index)를 쓸 기회를 잃는다. 필요한 열이 모두 한 인덱스 안에 있으면 MySQL은 테이블 행을 다시 찾아가지 않고 인덱스만 읽어 답할 수 있는데, EXPLAIN의 Extra 열에 Using index로 표시된다. 예를 들어 SELECT category, price FROM book WHERE category = 'IT'는 idx_category_price만으로 답할 수 있지만, *를 쓰면 제목과 저자를 가져오러 클러스터형 인덱스까지 가야 한다.

    셋째, 애플리케이션이 테이블 구조 변경에 묶인다. 열이 추가되거나 순서가 바뀌면 열의 위치로 값을 읽는 코드는 엉뚱한 값을 읽는다. MySQL 매뉴얼은 *에 관한 세부 규칙도 적어 두었다. 보이지 않는 열(invisible column)은 *에 포함되지 않고 이름으로 직접 적어야 하며, SELECT id, * FROM t1처럼 수식어 없는 *를 다른 항목과 섞으면 구문 오류가 날 수 있으므로 SELECT id, t1.* FROM t1처럼 테이블 이름을 붙여 쓰라고 한다. 반대로 대화형으로 데이터를 둘러볼 때는 *가 가장 빠른 도구다. 규칙은 "프로그램에 박아 넣는 쿼리에는 필요한 열을 적는다"로 기억하면 된다.

    조회 결과도 테이블이다

    SELECT의 결과는 열 이름과 행으로 이루어진 표다. 입력도 테이블이고 출력도 테이블이므로, 한 SELECT의 결과를 다른 SELECT의 입력으로 쓸 수 있다. 이 성질이 나중에 서브쿼리와 파생 테이블을 가능하게 한다. 다만 SQL의 테이블은 관계형 모델의 릴레이션과 두 가지가 다르다. 릴레이션은 집합이라 같은 튜플이 두 번 있을 수 없고 순서도 없다. SQL의 조회 결과는 같은 행이 여러 번 나올 수 있는 다중 집합(multiset)이고, ORDER BY를 쓰면 순서를 가진다. 같은 행이 여러 번 나오는 것을 막으려면 DISTINCT를, 순서가 필요하면 ORDER BY를 명시해야 한다. 이 회차의 절반이 이 두 가지 차이에서 나온다.

    논리적 처리 순서: 쓰는 순서와 의미가 정해지는 순서

    SELECT 문의 절은 정해진 순서로 써야 한다. SELECT, FROM, WHERE, GROUP BY, HAVING, ORDER BY, LIMIT이다. 그런데 이 순서는 결과의 의미가 정해지는 순서와 다르다. 결과의 의미는 다음 순서로 각 절을 적용했다고 생각할 때 정확히 맞아떨어진다. 이것을 논리적 처리 순서(logical processing order)라고 부른다.

    쓰는 순서                     논리적 처리 순서 (결과의 의미를 정하는 순서)

SELECT   ⑤ ⑥                 ① FROM      어느 테이블의 행에서 출발하는가
FROM     ①                   ② WHERE     행마다 조건을 따져 참인 행만 남긴다
WHERE    ②                   ③ GROUP BY  남은 행을 묶는다            (06회)
GROUP BY ③                   ④ HAVING    묶음을 거른다              (06회)
HAVING   ④                   ⑤ SELECT    선택 목록의 식을 계산하고 별칭을 붙인다
ORDER BY ⑦                   ⑥ DISTINCT  같은 행을 하나만 남긴다
LIMIT    ⑧                   ⑦ ORDER BY  행을 정렬한다
                              ⑧ LIMIT     앞에서부터 정해진 개수만 남긴다

    이 순서는 외우라고 있는 표가 아니라 여러 규칙을 한 번에 설명하는 모델이다. 가장 먼저 부딪히는 규칙은 "WHERE에서 SELECT의 별칭을 쓸 수 없다"는 것이다.

    SELECT title, price * stock AS stock_amount
FROM book
WHERE stock_amount > 200000;
    ERROR 1054 (42S22): Unknown column 'stock_amount' in 'where clause'

    MySQL 매뉴얼은 이 제약의 이유를 "WHERE 절이 실행될 때는 그 열의 값이 아직 정해지지 않았을 수 있기 때문"이라고 설명한다. 논리적 순서로 보면 WHERE는 ②, 별칭이 생기는 SELECT는 ⑤다. 아직 존재하지 않는 이름을 앞 단계에서 부를 수는 없다. 고치려면 WHERE에 식을 그대로 다시 쓴다(WHERE price * stock > 200000). 반대로 ORDER BY는 ⑦이므로 별칭을 쓸 수 있다. ORDER BY stock_amount DESC는 정상 동작한다.

    같은 모델이 DISTINCT와 ORDER BY의 관계도 설명한다. DISTINCT(⑥)가 먼저 중복 행을 합친 뒤에 ORDER BY(⑦)가 정렬하므로, 선택 목록에 없는 열로 정렬하려 하면 "합쳐진 여러 행 중 누구의 값으로 정렬하느냐"는 문제가 생긴다. 이 문제는 DISTINCT 절에서 MySQL이 실제로 어떻게 반응하는지와 함께 다시 본다. LIMIT(⑧)가 맨 마지막이라는 사실은 "정렬된 결과에서 앞의 몇 개"라는 의미를 만든다. LIMIT이 정렬보다 먼저라면 "아무 행 세 개를 고른 뒤 정렬"이 되어 버린다.

    논리적 처리 순서는 결과가 무엇이어야 하는지를 정할 뿐, 서버가 실제로 그 순서로 일한다는 뜻이 아니다. 옵티마이저는 결과가 같기만 하면 순서를 바꾸고 단계를 합친다. 인덱스가 이미 정렬된 순서로 행을 내주면 ⑦의 정렬은 아예 일어나지 않고, ⑧의 LIMIT을 미리 알고 있으면 필요한 행만 읽고 멈춘다.
    SQL을 쓰는 순서와 결과의 의미가 정해지는 순서가 다르다는 것, 그리고 행 집합이 단계를 지날 때마다 줄어들고 바뀌는 모습을 보여 준다. 가로로 긴 다이어그램. 왼쪽 위에 작은 회색 상자 "쓰는 순서: SELECT → FROM → WHERE → ORDER BY → LIMIT". 그 아래 본체로 왼쪽에서 오른쪽으로 이어지는 여섯 개의 둥근 사각형 단계가 화살표로 연결된다. 단계 라벨은 순서대로 "① FROM", "② WHERE", "⑤ SELECT", "⑥ DISTINCT", "⑦ ORDER BY", "⑧ LIMIT". 각 단계 아래에 작은 표 아이콘이 있고 행 수가 줄어든다: FROM 아래는 10줄, WHERE 아래는 4줄, SELECT 아래는 4줄이지만 열이 2개로 좁아짐, DISTINCT 아래는 3줄, ORDER BY 아래는 3줄이 정렬된 화살표와 함께, LIMIT 아래는 2줄. WHERE 상자 위에 빨간 점선 화살표가 SELECT 상자에서 거꾸로 오다가 X 표시로 막혀 있고 라벨 "별칭은 아직 없다". 흰 배경, 파란 계열 단색, 깔끔한 플랫 스타일. 절을 쓰는 순서와 달리 결과의 의미는 FROM → WHERE → SELECT → DISTINCT → ORDER BY → LIMIT 순으로 정해진다.

    01회에서 MySQL 서버가 연결을 처리하는 부분, SQL을 해석하고 실행 계획을 세우는 SQL 계층, 실제로 데이터를 읽고 쓰는 저장 엔진(InnoDB)으로 나뉜다는 것을 보았다. 조회 한 문장이 이 계층들을 어떻게 지나가는지 따라가 보면, 뒤에서 다룰 인덱스와 정렬 비용 이야기가 어디서 생기는지 알 수 있다.

    MySQL 5.7까지 있던 쿼리 캐시(query cache)는 8.0에서 제거되었으므로, 8.0에서는 같은 SELECT를 두 번 보내도 결과를 통째로 재사용하지 않고 매번 위 과정을 밟는다. 대신 두 번째 실행은 첫 실행 때 버퍼 풀에 올라온 페이지를 다시 쓰므로 디스크 읽기가 줄어든다. "같은 쿼리를 두 번 돌리면 두 번째가 빠르다"는 경험은 결과 캐시가 아니라 이 페이지 캐시의 효과다.

    이 경로에서 비용을 좌우하는 것은 ③에서 정해지는 접근 방법이다. InnoDB의 데이터는 기본 페이지 크기 16KB의 페이지 단위로 읽힌다. 테이블 전체를 읽는 계획이면 클러스터형 인덱스의 리프 페이지를 처음부터 끝까지 지나가며 모든 행을 실행기에 넘기고, 실행기는 행마다 조건을 따진다. 인덱스로 범위를 읽는 계획이면 B+Tree를 루트에서 리프까지 내려가 조건의 시작점을 찾고, 조건이 끝나는 곳까지만 리프를 따라 읽는다. 백만 행 테이블에서 조건에 맞는 행이 열 개라면 두 계획이 읽는 페이지 수는 자릿수가 달라질 만큼 차이가 난다.

    WHERE 기본 검색: 행마다 참·거짓·모름을 묻는다

    WHERE는 FROM이 내놓은 행 하나하나에 조건식을 계산해서 결과가 참인 행만 남긴다. 조건식에 가장 많이 쓰는 것은 비교 연산자다.

    연산자뜻예
    =같다category = 'IT'
    <>, !=다르다category <> 'IT'
    <, <=작다, 작거나 같다price < 20000
    >, >=크다, 크거나 같다published_on >= '2023-01-01'

    여기서 "참인 행만"이라는 말을 정확히 이해해야 한다. 자바의 조건식은 true나 false 둘 중 하나지만, MySQL의 비교 연산은 1(참), 0(거짓), NULL 셋 중 하나를 돌려준다. 비교하는 값 중 하나라도 NULL이면 결과도 NULL이다. WHERE는 결과가 1인 행만 남기고, 0인 행과 NULL인 행은 모두 버린다. 이 세 번째 경우가 NULL 절에서 다룰 함정의 출발점이다. 지금은 discount_rate처럼 NULL을 허용하는 열에 조건을 걸면 NULL인 행은 조건의 참·거짓과 상관없이 빠진다는 것만 기억해 두자.

    조건 여러 개는 AND, OR, NOT으로 엮는다. 여기서 연산자 우선순위가 문제를 일으킨다. MySQL 8.0 매뉴얼의 우선순위 표에서 이 넷 가운데 비교 연산자가 가장 높고, 그 아래로 NOT, AND, OR 순서다. 즉 AND가 OR보다 먼저 묶인다. 수학에서 곱셈이 덧셈보다 먼저인 것과 같다.

    -- 의도: 소설이나 역사 중에서 20000원 이상인 책
SELECT book_id, category, price
FROM book
WHERE category = '소설' OR category = '역사' AND price >= 20000
ORDER BY book_id;
    +---------+----------+-------+
| book_id | category | price |
+---------+----------+-------+
|       3 | 소설     | 14000 |
|       4 | 소설     | 15000 |
|       5 | 역사     | 22000 |
|       7 | 소설     | 13000 |
|       8 | 역사     | 26000 |
+---------+----------+-------+

    20000원 미만인 소설 세 권이 섞여 나왔다. 서버는 이 조건을 category = '소설' OR (category = '역사' AND price >= 20000)으로 읽었기 때문이다. 소설은 가격과 상관없이 모두 통과하고, 역사만 가격 조건을 받았다. 의도대로 하려면 괄호로 묶는다.

    SELECT book_id, category, price
FROM book
WHERE (category = '소설' OR category = '역사') AND price >= 20000
ORDER BY book_id;
    +---------+----------+-------+
| book_id | category | price |
+---------+----------+-------+
|       5 | 역사     | 22000 |
|       8 | 역사     | 26000 |
+---------+----------+-------+

    이 버그는 문법 오류가 아니라서 서버가 아무 경고 없이 실행한다. 데이터가 적은 개발 환경에서는 우연히 맞는 결과가 나오다가 운영 데이터에서 엉뚱한 행이 섞여 나오는 식으로 늦게 발견된다. AND와 OR를 섞을 때는 우선순위를 믿지 말고 항상 괄호를 쓰는 습관이 가장 싸다. NOT은 비교 연산자보다 우선순위가 낮으므로 NOT price > 20000은 NOT (price > 20000)으로 읽힌다.

    MySQL은 AND, OR, NOT 대신 &&, ||, !도 받아 주지만, 매뉴얼은 이 세 기호를 8.0.17부터 사용 중단(deprecated) 대상으로 표시하고 표준 키워드를 쓰라고 한다. 특히 ||는 SQL 모드 PIPES_AS_CONCAT이 켜져 있으면 논리합이 아니라 문자열 연결 연산자가 된다. 자바 습관대로 &&를 쓰지 말고 AND를 쓰자.

    문자열 비교는 콜레이션이 정한다

    자바의 "IT".equals("it")는 false다. 그런데 이 테이블에서 WHERE category = 'it'를 실행하면 IT 책 네 권이 모두 나온다. 열의 콜레이션이 기본값 utf8mb4_0900_ai_ci이고, ci가 대소문자를 구분하지 않는다는 뜻이기 때문이다. MySQL 매뉴얼도 문자열 비교는 기본적으로 대소문자를 구분하지 않는다고 적고 있다. 이메일 주소처럼 대소문자를 무시해도 되는 값에는 편하지만, 대소문자가 의미를 갖는 토큰이나 코드 값을 저장하는 열이라면 대소문자를 구분하는 콜레이션(utf8mb4_0900_as_cs나 utf8mb4_bin)을 열에 지정해야 한다. 유니크 제약도 같은 콜레이션으로 비교하므로, 기본 콜레이션 열에서는 'Kim'과 'kim'이 중복으로 취급된다.

    문자열 끝의 공백도 콜레이션마다 다르게 다룬다. MySQL 매뉴얼에 따르면 대부분의 콜레이션은 패드 속성이 PAD SPACE여서 비교할 때 끝 공백을 무시하지만, UCA 9.0.0 이상에 기반한 유니코드 콜레이션은 NO PAD여서 끝 공백도 다른 문자와 똑같이 비교에 참여한다. 매뉴얼의 예로 utf8mb4_bin(PAD SPACE)에서는 'a ' = 'a'가 1이고, utf8mb4_0900_bin(NO PAD)에서는 0이다. 기본 콜레이션 utf8mb4_0900_ai_ci도 UCA 9.0.0 기반이다. 어떤 콜레이션의 패드 속성은 INFORMATION_SCHEMA.COLLATIONS 테이블의 PAD_ATTRIBUTE 열로 직접 확인할 수 있다. 다른 데이터베이스에서 옮겨 온 데이터나 사용자 입력에 끝 공백이 섞여 있다면, 같은 쿼리가 서버의 콜레이션 설정에 따라 다른 결과를 낼 수 있다는 뜻이다.

    문자열과 숫자를 비교하면 숫자 비교가 된다

    비교하는 두 값의 타입이 다르면 MySQL은 형 변환 규칙을 적용한다. 매뉴얼의 규칙을 요약하면, 둘 다 문자열이면 문자열로, 둘 다 정수면 정수로 비교하고, 문자열과 숫자를 비교하는 경우를 포함한 "그 밖의 모든 경우"에는 둘 다 배정밀도 부동소수점 수(double)로 바꿔 비교한다. 문자열을 숫자로 바꿀 때는 앞에서부터 숫자로 읽을 수 있는 데까지만 읽는다. 매뉴얼에 실린 예는 다음과 같다.

    SELECT 1 > '6x';   -- 0  ('6x'는 6으로 바뀐다)
SELECT 7 > '6x';   -- 1
SELECT 0 > 'x6';   -- 0  ('x6'은 숫자로 시작하지 않아 0이 된다)
SELECT 0 = 'x6';   -- 1

    MySQL 8.4.13과 8.0.46에서 실행하면 결과는 주석과 같고, 문자열을 숫자로 끝까지 읽지 못하고 잘라 낸 비교마다 Warning (Code 1292): Truncated incorrect DOUBLE value: '6x' 같은 경고가 붙는다. 경고일 뿐 오류가 아니므로 문장은 그대로 실행된다.

    이 규칙은 실무에서 두 가지 문제를 만든다. 하나는 정확성이다. 회원 코드나 우편번호처럼 숫자로 보이지만 VARCHAR로 저장한 열에 WHERE code = 1이라고 쓰면 '1'만이 아니라 ' 1', '1a', '01'처럼 숫자로 바꿨을 때 1이 되는 모든 문자열이 일치한다. 다른 하나는 성능이다. 매뉴얼은 바로 이 이유, 즉 숫자 1로 바뀌는 문자열이 여러 가지라는 이유로 문자열 열을 숫자와 비교하면 그 열의 인덱스로 값을 빠르게 찾을 수 없다고 적고 있다. 인덱스는 문자열 순서로 정렬되어 있는데, 숫자 1에 해당하는 문자열들은 그 순서에서 한곳에 모여 있지 않다. 결국 전체 스캔이 된다. 애플리케이션에서 문자열 열에 숫자 타입 파라미터를 바인딩해도 같은 일이 일어날 수 있으므로, 열 타입과 같은 타입의 값을 넘기는 것이 원칙이다.

    WHERE와 인덱스: 조건의 모양이 읽을 행의 수를 정한다

    WHERE 조건은 결과의 의미를 정하는 동시에 서버가 읽어야 하는 페이지 수도 정한다. 인덱스가 없으면 서버가 할 수 있는 일은 하나뿐이다. 클러스터형 인덱스의 리프 페이지를 처음부터 끝까지 읽으며 행마다 조건을 계산하는 전체 스캔(full table scan)이다. EXPLAIN에서는 type이 ALL로 나온다. 조건에 맞는 행이 한 건이어도 읽는 양은 테이블 전체다.

    조건이 걸린 열에 B+Tree 인덱스가 있으면 사정이 달라진다. 인덱스는 열 값의 순서로 정렬되어 있으므로, 조건이 "이 값부터 저 값까지"라는 연속된 구간으로 표현되기만 하면 트리를 루트에서 내려가 구간의 시작점을 찾고, 리프를 옆으로 따라가다 구간이 끝나면 멈춘다. 예를 들어 WHERE category = 'IT'는 idx_category_price에서 category가 'IT'인 첫 항목으로 내려가 값이 바뀔 때까지 읽는다. 보조 인덱스의 리프에는 기본 키가 들어 있으므로, 선택 목록에 인덱스에 없는 열(예: title)이 있으면 항목마다 그 기본 키로 클러스터형 인덱스를 한 번 더 내려가 행을 가져온다.

    MySQL 매뉴얼은 B-tree 인덱스를 쓸 수 있는 비교를 =, >, >=, <, <=, BETWEEN, 그리고 와일드카드로 시작하지 않는 상수 문자열과의 LIKE로 정리한다. 공통점은 모두 "정렬된 순서에서 연속된 구간"으로 바뀐다는 것이다. 복합 인덱스 (category, price)는 전화번호부처럼 먼저 category로, 같은 category 안에서 price로 정렬되어 있다. 그래서 category = 'IT' AND price >= 30000은 한 구간으로 바뀌지만, price >= 30000만 주면 가격 30000 이상인 항목이 분류마다 흩어져 있어 한 구간이 되지 않는다. 인덱스의 앞쪽 열부터 조건을 줘야 한다는 이 규칙을 왼쪽 접두어 규칙(leftmost prefix rule)이라고 한다.

    조건의 열에 함수나 연산을 씌우면 같은 이유로 구간을 만들 수 없다. 2023년에 출간된 책을 찾는 두 쿼리를 비교해 보자.

    -- (가) 열에 함수를 씌웠다
SELECT book_id, title FROM book
WHERE YEAR(published_on) = 2023;

-- (나) 열을 그대로 두고 상수 쪽으로 범위를 표현했다
SELECT book_id, title FROM book
WHERE published_on >= '2023-01-01' AND published_on < '2024-01-01';

    두 쿼리는 같은 행(4번, 6번)을 돌려주지만 idx_published_on을 범위 검색에 쓸 수 있는 것은 (나)다. 인덱스에 저장된 것은 published_on의 값과 그 순서이지 YEAR(published_on)의 값이 아니다. 옵티마이저는 (가)를 "출간일이 이 구간에 있는 행"으로 바꿔 주지 않으므로, 모든 행에 대해 함수를 계산해 보는 수밖에 없다. WHERE price * 1.1 > 33000도 마찬가지이고, 열은 맨몸으로 두고 계산은 상수 쪽으로 옮기는(WHERE price > 30000) 것이 원칙이다. 이런 형태의 조건을 흔히 사거블(sargable, search-argument-able)하다고 부른다. 함수를 꼭 써야 한다면 MySQL 8.0.13부터 지원하는 함수 기반 키 파트(functional key part)로 식 자체를 인덱싱하는 방법이 있다. 매뉴얼은 이 경우 쿼리의 식이 인덱스에 정의한 식과 일치해야 인덱스를 쓸 수 있다고 설명한다.

    일상에서 가져온 비유가나다순 출석부와 "이름이 세 글자인 학생"

    가나다순으로 정렬된 출석부에서 "박"으로 시작하는 학생은 해당 페이지를 펴서 한 번에 찾는다. 하지만 "이름의 마지막 글자가 '준'인 학생"이나 "이름이 세 글자인 학생"은 정렬 기준과 상관없는 성질이라 출석부를 처음부터 끝까지 넘겨야 한다. 열에 함수를 씌운 조건, 앞에 와일드카드가 붙은 LIKE가 바로 이 경우다. 비유가 깨지는 지점도 있다. 사람은 출석부를 넘기는 속도가 일정하지만, 데이터베이스는 이미 버퍼 풀에 올라와 있는 페이지와 디스크에서 읽어야 하는 페이지의 비용이 크게 다르다.

    인덱스를 쓸 수 있다고 해서 옵티마이저가 반드시 쓰는 것도 아니다. 보조 인덱스로 찾은 항목마다 클러스터형 인덱스를 다시 내려가야 하므로, 조건에 맞는 행이 테이블의 상당 부분이라면 차라리 전체를 순서대로 읽는 편이 싸다. 옵티마이저는 통계로 이 비용을 추정해 고른다. 앞에서 행이 열 개인 테이블은 전체 스캔이 자주 선택된다고 한 것도 이 때문이다. 그러니 "인덱스를 만들었는데 왜 안 쓰지?"라는 질문에는 먼저 조건의 모양이 구간이 되는지, 그다음으로 구간이 테이블의 얼마만큼인지를 차례로 따져 보면 된다.

    WHERE 편리한 조건 검색: BETWEEN, IN, LIKE

    비교 연산자와 AND, OR만으로도 모든 조건을 쓸 수 있지만, 자주 쓰는 모양에는 더 짧은 표현이 있다. 짧은 표현은 편의 문법이면서 동시에 저마다 경계 조건을 갖고 있으므로, 각각이 정확히 무엇과 같은지 알아 두어야 한다.

    BETWEEN: 양 끝을 포함하는 구간

    expr BETWEEN min AND max는 매뉴얼에 따르면 세 인자의 타입이 같을 때 (min <= expr AND expr <= max)와 같다. 양 끝을 포함한다는 점이 핵심이다.

    SELECT book_id, price
FROM book
WHERE price BETWEEN 15000 AND 26000
ORDER BY book_id;
    +---------+-------+
| book_id | price |
+---------+-------+
|       4 | 15000 |
|       5 | 22000 |
|       8 | 26000 |
|      10 | 18000 |
+---------+-------+

    정확히 15000원인 4번과 정확히 26000원인 8번이 모두 들어왔다. 두 값의 순서를 바꿔 BETWEEN 26000 AND 15000이라고 쓰면 어떻게 될까. 위의 동치식에 넣으면 26000 <= price AND price <= 15000이 되는데, 이를 만족하는 수는 없으므로 결과는 빈 집합이다. 매뉴얼의 예에서도 2 BETWEEN 3 AND 1은 0이다. 서버가 작은 쪽과 큰 쪽을 알아서 바꿔 주지 않는다.

    양 끝 포함은 날짜와 시각에서 함정이 된다. 이 테이블의 published_on은 시각이 없는 DATE라서 BETWEEN '2023-01-01' AND '2023-12-31'이 2023년 전체를 정확히 덮는다. 하지만 주문 시각처럼 DATETIME 열이라면 이야기가 다르다. 매뉴얼의 형 변환 규칙에 따르면 DATETIME 열을 상수와 비교할 때 상수가 시각 값으로 바뀌는데, '2023-12-31'은 '2023-12-31 00:00:00'이 된다. 그러면 12월 31일 0시 정각보다 뒤의 주문은 모두 빠진다. 시각이 있는 열에는 ordered_at >= '2023-01-01' AND ordered_at < '2024-01-01'처럼 끝을 열어 둔 반개구간을 쓰는 것이 안전하다. 이 형태는 정밀도가 초든 마이크로초든 상관없이 정확하다.

    IN: 목록 중 하나와 같다

    expr IN (v1, v2, ...)는 목록의 값 중 하나와 같으면 1을 돌려준다. 같은 열에 대한 = 조건을 OR로 이은 것과 같은 뜻이고, 앞에서 본 우선순위 실수를 원천적으로 막아 준다.

    SELECT book_id, title, author
FROM book
WHERE author IN ('박서연', '정유나')
ORDER BY book_id;
    +---------+-------------------+--------+
| book_id | title             | author |
+---------+-------------------+--------+
|       3 | 바다의 시간       | 박서연 |
|       4 | 작은 별의 기록    | 박서연 |
|       7 | 겨울 정원         | 정유나 |
|      10 | 별 헤는 밤의 과학 | 정유나 |
+---------+-------------------+--------+

    매뉴얼은 IN 목록에 따옴표가 있는 값과 없는 값을 섞지 말라고 경고한다. 앞에서 본 것처럼 문자열과 숫자의 비교 규칙이 달라서 결과가 일관되지 않을 수 있기 때문이다. 그리고 IN에는 NULL과 관련된 중요한 규칙이 하나 있다. 표준을 따르기 위해 IN()은 왼쪽 값이 NULL일 때뿐 아니라, 목록에서 일치하는 값을 찾지 못했고 목록 안에 NULL이 있을 때도 NULL을 돌려준다. 이 규칙이 NOT IN을 위험하게 만드는데, NULL 절에서 직접 확인한다.

    LIKE: 패턴 일치

    LIKE는 문자열이 패턴과 일치하는지 본다. 패턴에는 와일드카드 두 개를 쓴다. %는 0개 이상의 아무 문자와, _는 정확히 한 문자와 일치한다.

    SELECT book_id, title
FROM book
WHERE title LIKE '%의%'
ORDER BY book_id;
    +---------+-------------------+
| book_id | title             |
+---------+-------------------+
|       3 | 바다의 시간       |
|       4 | 작은 별의 기록    |
|       5 | 조선의 시장       |
|      10 | 별 헤는 밤의 과학 |
+---------+-------------------+

    LIKE '자바%'는 "자바"로 시작하는 제목(2번), LIKE '%기록'은 "기록"으로 끝나는 제목(4번), LIKE '__ 정원'은 두 글자 다음에 공백과 "정원"이 오는 제목(7번)과 일치한다. _는 바이트가 아니라 문자 하나와 일치하므로 한글 한 글자도 _ 하나다.

    9번 책의 제목 "SQL 100% 활용"처럼 와일드카드 문자 자체를 찾고 싶을 때는 이스케이프 문자를 앞에 붙인다. 매뉴얼에 따르면 ESCAPE를 지정하지 않으면 백슬래시(\)가 이스케이프 문자다. 그런데 백슬래시는 MySQL 문자열 리터럴 자체의 이스케이프 문자이기도 해서 읽는 사람이 헷갈리기 쉽다. ESCAPE 절로 다른 문자를 지정하면 의도가 분명해진다.

    SELECT book_id, title
FROM book
WHERE title LIKE '%100!%%' ESCAPE '!';
    +---------+---------------+
| book_id | title         |
+---------+---------------+
|       9 | SQL 100% 활용 |
+---------+---------------+

    패턴 '%100!%%'는 "아무 문자열, 100, 문자 그대로의 %, 아무 문자열"이라는 뜻이다. 사용자가 검색창에 입력한 문자열을 LIKE 패턴에 넣을 때는 이 처리가 필수다. 사용자가 %나 _를 입력하면 그대로 와일드카드로 해석되어 의도하지 않은 행까지 일치하기 때문이다.

    LIKE에는 =와 다른 성질이 두 가지 더 있다. 첫째, 매뉴얼에 따르면 LIKE는 표준에 따라 문자 단위로 일치를 보며, 끝 공백은 콜레이션과 상관없이 항상 의미가 있다. 둘째, 대소문자 구분은 콜레이션을 따르므로 기본 콜레이션에서 'abc' LIKE 'ABC'는 1이다. 그리고 expr나 패턴 중 하나라도 NULL이면 결과는 NULL이다.

    인덱스 관점에서 LIKE는 패턴이 어떻게 시작하느냐가 전부다. 매뉴얼은 key_col LIKE 'Patrick%'는 'Patrick' <= key_col < 'Patricl' 구간만 보면 되므로 인덱스를 쓸 수 있고, '%Patrick%'는 와일드카드로 시작해서 쓸 수 없다고 설명한다. 앞 절의 출석부 비유 그대로다. 위의 '%의%' 검색은 제목에 인덱스가 있었더라도 전체 스캔이 된다. 본문 어디에나 있을 수 있는 단어를 큰 테이블에서 찾아야 한다면 LIKE가 아니라 InnoDB의 FULLTEXT 인덱스나 별도의 검색 엔진을 검토해야 하는데, 이 강좌의 범위를 넘는다.

    세 연산자 모두 앞에 NOT을 붙여 NOT BETWEEN, NOT IN, NOT LIKE로 쓸 수 있다. 매뉴얼은 각각을 NOT (expr BETWEEN ...), NOT (expr IN (...)), NOT (expr LIKE ...)와 같다고 정의한다. 뜻은 단순한 부정이지만, 안쪽 결과가 NULL이면 NOT을 씌워도 NULL이라는 점 때문에 NULL이 섞인 열에서는 직관과 다른 결과가 나온다.

    ORDER BY: 순서는 요청해야만 생긴다

    MySQL 매뉴얼의 튜토리얼은 ORDER BY 없이 조회한 결과를 두고 "결과 행이 특별한 순서 없이 표시된다"고 적는다. 많은 사람이 ORDER BY가 없으면 기본 키 순서나 입력 순서로 나온다고 믿는데, 그것은 특정 실행 계획에서 우연히 관찰되는 순서일 뿐이다. 전체 스캔이면 클러스터형 인덱스를 따라 읽으므로 기본 키 순서로 나오는 경우가 많다. 하지만 같은 쿼리라도 옵티마이저가 보조 인덱스를 고르면 그 인덱스의 순서로 나오고, 데이터가 늘어 통계가 바뀌면 계획도 바뀐다. SQL의 결과는 순서 없는 다중 집합이라는 앞의 설명을 떠올리자. 순서가 필요하면 ORDER BY로 요청해야 하고, 요청하지 않은 순서에 기대는 코드는 언젠가 깨진다.

    SELECT book_id, category, price
FROM book
ORDER BY category, price DESC;
    +---------+----------+-------+
| book_id | category | price |
+---------+----------+-------+
|       6 | IT       | 35000 |
|       2 | IT       | 32000 |
|       9 | IT       | 30000 |
|       1 | IT       | 28000 |
|      10 | 과학     | 18000 |
|       4 | 소설     | 15000 |
|       3 | 소설     | 14000 |
|       7 | 소설     | 13000 |
|       8 | 역사     | 26000 |
|       5 | 역사     | 22000 |
+---------+----------+-------+

    정렬 방향은 오름차순 ASC가 기본이고 내림차순은 DESC다. 여러 열을 쉼표로 나열하면 앞의 열로 먼저 정렬하고, 앞의 열 값이 같은 행끼리만 다음 열로 정렬한다. 매뉴얼이 강조하듯 DESC는 바로 앞의 열 하나에만 적용된다. 위 쿼리에서 category는 오름차순, price만 내림차순이다. 문자열 정렬 순서는 콜레이션이 정하는데, 기본 콜레이션에서 라틴 문자로 된 'IT'가 한글보다 앞에 오고, 한글은 가나다순(과학, 소설, 역사)으로 정렬된다.

    ORDER BY에는 열 이름 외에 식과 SELECT의 별칭도 쓸 수 있다. ORDER BY price * stock DESC나 ORDER BY stock_amount DESC가 모두 가능하다. 별칭을 쓸 수 있는 이유는 논리적 처리 순서에서 ORDER BY가 SELECT 뒤에 있기 때문이다. ORDER BY 2처럼 선택 목록의 위치 번호로 정렬하는 문법도 동작하지만, 매뉴얼은 이 문법이 SQL 표준에서 제거되었으므로 사용 중단 대상이라고 적고 있다. 선택 목록의 순서를 바꾸면 정렬 기준이 조용히 바뀌는 문제도 있으니 쓰지 않는다.

    동점은 순서가 정해지지 않는다

    ORDER BY category만으로 정렬하면 IT 책 네 권 사이의 순서는 어떻게 될까. 매뉴얼의 LIMIT 최적화 절은 이렇게 답한다. ORDER BY 열의 값이 같은 행이 여러 개면 서버는 그 행들을 어떤 순서로든 돌려줄 수 있고, 전체 실행 계획에 따라 다르게 돌려줄 수도 있다. 즉 정렬하지 않은 열에 대해서는 순서가 비결정적(nondeterministic)이다. 매뉴얼은 같은 쿼리에 LIMIT을 붙였느냐 아니냐만으로도 동점 행의 순서가 달라질 수 있다는 예를 보여 주며, 그래도 두 결과 모두 ORDER BY 열로는 정렬되어 있으므로 SQL 표준이 요구하는 것은 다 지킨 것이라고 덧붙인다.

    해결책도 매뉴얼에 있다. 순서를 결정적으로 만들려면 ORDER BY에 열을 더 넣는다. 가장 확실한 방법은 마지막에 기본 키처럼 고유한 열을 붙이는 것이다. ORDER BY category, book_id라고 쓰면 모든 행의 순서가 하나로 정해진다. 화면에 보여 주기만 하는 목록이라면 동점의 순서가 바뀌어도 큰일이 아니지만, 다음 절의 페이지 나누기와 결합하면 같은 행이 두 페이지에 나오거나 어느 페이지에도 나오지 않는 버그가 된다.

    NULL은 오름차순에서 맨 앞에 온다

    MySQL 매뉴얼에 따르면 ORDER BY에서 NULL은 ASC일 때 맨 앞에, DESC일 때 맨 뒤에 온다. 정렬할 때 NULL끼리는 모두 같은 값으로 취급된다. ORDER BY discount_rate, book_id의 결과는 2, 4, 8번(NULL)이 먼저 나오고, 이어서 3, 9번(0), 10번(5), 1, 6번(10), 5번(20), 7번(30)이다. 할인율이 정해진 책을 먼저 보고 싶다면 NULL 여부를 첫 번째 정렬 키로 쓴다. discount_rate IS NULL은 NULL이면 1, 아니면 0이므로 오름차순에서 NULL이 아닌 행이 먼저 온다.

    SELECT book_id, discount_rate
FROM book
ORDER BY discount_rate IS NULL, discount_rate, book_id;
-- 결과 순서: 3, 9, 10, 1, 6, 5, 7, 2, 4, 8

    NULL을 앞에 둘지 뒤에 둘지는 데이터베이스마다 기본값이 다르다. 다른 제품으로 옮기거나 여러 제품을 함께 쓴다면 이 기본값에 기대지 말고 위처럼 명시하는 편이 안전하다.

    한 층 아래: 인덱스 순서와 filesort

    정렬은 비싸다. 서버가 ORDER BY를 처리하는 방법은 크게 두 가지다. 하나는 이미 정렬된 인덱스를 순서대로 읽는 것이고, 다른 하나는 행을 모아 따로 정렬하는 것이다. MySQL은 후자를 filesort라고 부르며, EXPLAIN의 Extra에 Using filesort가 보이면 인덱스로 정렬을 해결하지 못하고 정렬 단계를 따로 거친다는 뜻이다. 이름에 file이 들어 있지만 항상 파일을 쓰는 것은 아니다.

    인덱스로 정렬을 대신할 수 있는 조건은 매뉴얼에 이렇게 정리되어 있다. 인덱스에서 ORDER BY에 쓰이지 않은 부분과 ORDER BY에 추가로 나온 열이 모두 WHERE 절에서 상수로 고정되어 있으면 된다. 이 테이블로 보면 WHERE category = 'IT' ORDER BY price는 idx_category_price에서 category가 'IT'로 고정되어 있고 그 안에서 price가 이미 정렬되어 있으므로, 인덱스를 따라 읽기만 하면 정렬된 결과가 나온다. 반면 WHERE 없이 ORDER BY price만 쓰면 이 인덱스는 분류별로 가격이 정렬되어 있을 뿐 전체 가격 순서가 아니므로 쓸 수 없고 filesort가 필요하다. 매뉴얼은 이 밖에도 서로 다른 인덱스의 열로 정렬하거나, 열의 앞부분만 인덱싱한 접두어 인덱스로 정렬하려는 경우 인덱스로 정렬을 끝낼 수 없다고 적는다.

    filesort는 정렬 버퍼에서 일한다. 버퍼 크기의 상한은 시스템 변수 sort_buffer_size이고, MySQL 8.0.12부터는 이 크기를 처음부터 통째로 잡지 않고 필요한 만큼 점진적으로 할당한다. 정렬할 데이터가 버퍼에 다 들어가지 않으면 정렬된 조각을 임시 디스크 파일에 쓰고 나중에 병합한다. 매뉴얼이 sort_buffer_size를 두고 "결과 전체가 정렬 버퍼에 들어갈 만큼 크면 디스크 쓰기와 병합 단계를 피할 수 있다"고 쓴 것이 이 뜻이다. 그렇다고 이 값을 크게 올리는 것이 정답은 아니다. 정렬 버퍼는 정렬하는 세션마다 따로 잡히므로, 동시에 정렬하는 커넥션이 많으면 메모리 사용량이 그만큼 곱해진다. 정렬 비용을 줄이는 근본적인 방법은 정렬할 행 자체를 줄이거나(WHERE로 먼저 좁히기), 인덱스 순서로 정렬을 대신하게 하는 것이다.

    LIMIT: 개수 제한과 페이지 나누기

    LIMIT은 결과에서 앞부분의 일정 개수만 남긴다. MySQL은 세 가지 형태를 받는다.

    SELECT * FROM book ORDER BY published_on DESC LIMIT 3;           -- 처음 3행
SELECT * FROM book ORDER BY published_on DESC LIMIT 3, 3;        -- 4번째 행부터 3행
SELECT * FROM book ORDER BY published_on DESC LIMIT 3 OFFSET 3;  -- 위와 같다

    인자가 하나면 앞에서부터 가져올 최대 행 수이고, LIMIT n은 LIMIT 0, n과 같다. 인자가 둘이면 첫 번째가 건너뛸 행 수(오프셋), 두 번째가 가져올 최대 행 수다. 매뉴얼은 첫 행의 오프셋이 1이 아니라 0이라고 강조하며 LIMIT 5,10은 6번째부터 15번째 행을 가져온다고 설명한다. 순서가 헷갈리기 쉬우므로 PostgreSQL과 호환되는 LIMIT n OFFSET m 형태가 읽기 쉽다. LIMIT의 인자는 음이 아닌 정수 상수여야 하며, 예외로 준비된 문장(prepared statement)에서는 ? 자리 표시자를 쓸 수 있다. 그래서 서버 측 준비된 문장에서도 LIMIT 값을 ?로 바인딩할 수 있다.

    출간일 최신순으로 세 권씩 페이지를 나누면 다음과 같다. 페이지 번호를 1부터 센다면 p번째 페이지의 오프셋은 (p - 1) × 3이다.

    페이지쿼리 끝부분결과(book_id, 출간일)
    1LIMIT 3 OFFSET 09 (2024-04-01), 6 (2023-09-30), 4 (2023-02-10)
    2LIMIT 3 OFFSET 32 (2022-07-01), 8 (2022-01-18), 10 (2021-08-08)
    3LIMIT 3 OFFSET 61 (2021-03-15), 5 (2020-05-05), 3 (2019-11-20)
    4LIMIT 3 OFFSET 97 (2018-12-24)

    여기서는 출간일이 모두 달라 순서가 하나로 정해진다. 만약 ORDER BY category LIMIT 3처럼 동점이 많은 열로만 정렬하고 페이지를 나누면, IT 책 네 권 중 어느 세 권이 첫 페이지에 올지 정해져 있지 않다. 첫 페이지 요청과 두 번째 페이지 요청은 서로 다른 SQL 실행이므로, 첫 페이지에 나온 책이 두 번째 페이지에 또 나오고 어떤 책은 어디에도 나오지 않을 수 있다. 앞에서 본 대로 매뉴얼은 LIMIT의 유무만으로도 동점의 순서가 달라질 수 있다고 하니, 오프셋만 다른 두 쿼리의 동점 순서가 같다는 보장은 더더욱 없다. 페이지를 나눌 때는 정렬 키 끝에 고유한 열을 반드시 붙인다.

    LIMIT이 서버의 일을 줄이는 방식

    LIMIT은 결과를 자르는 것 이상으로 실행 방법에 영향을 준다. 매뉴얼의 LIMIT 최적화 절에 따르면, ORDER BY와 LIMIT을 함께 쓰면 MySQL은 정렬된 결과의 첫 n행을 찾는 즉시 정렬을 멈춘다. 인덱스로 정렬하는 경우라면 인덱스를 n개 항목만큼만 읽으면 되므로 매우 빠르다. 반면 filesort가 필요하다면 LIMIT이 없을 때 조건에 맞는 모든 행을 먼저 골라야 하고, 그 대부분 또는 전부를 정렬한 뒤에야 첫 n행이 정해진다. 이때도 LIMIT이 있으면 병합 파일 없이 메모리 안의 filesort로 처리할 수 있는 경우가 있다. 또한 클라이언트에 필요한 행을 다 보내면 쿼리를 중단한다. LIMIT 0은 빈 결과를 바로 돌려주므로 쿼리 문법이 맞는지나 결과 열의 타입을 확인하는 데 쓸 수 있다.

    이 차이가 인덱스 설계와 연결된다. 출간일 최신순 목록의 첫 페이지 ORDER BY published_on DESC LIMIT 3은 idx_published_on을 큰 값 쪽에서부터 거꾸로 세 항목 읽으면 끝난다. B+Tree의 리프 페이지는 양쪽으로 연결되어 있어 역방향으로도 읽을 수 있다. 같은 목록을 인덱스 없는 열로 정렬하면 테이블 전체를 읽고 정렬해야 비로소 세 행이 정해진다. 테이블이 백만 행이면 앞의 경우는 수십 바이트짜리 항목 몇 개를, 뒤의 경우는 백만 행을 처리한다.

    깊은 오프셋의 비용과 키셋 페이지네이션

    오프셋 방식에는 구조적인 약점이 있다. LIMIT 20 OFFSET 100000은 "앞의 10만 행을 건너뛰고 20행"이라는 뜻인데, 건너뛸 10만 행이 어디서 끝나는지 알려면 정렬된 순서로 10만 행을 하나씩 지나가야 한다. B+Tree는 "N번째 항목"으로 바로 뛰어가는 기능이 없다. InnoDB는 테이블의 행 수도 내부에 따로 세어 두지 않는데, MySQL 매뉴얼은 그 이유를 동시에 실행되는 트랜잭션마다 보이는 행 수가 다를 수 있기 때문이라고 설명한다. 그래서 오프셋 방식은 뒤 페이지로 갈수록 읽는 양이 페이지 번호에 비례해 늘어난다. 관리자 화면의 마지막 페이지 버튼이 유독 느린 이유가 대개 이것이다.

    오프셋 방식에는 정확성 문제도 있다. 1페이지(9, 6, 4번)를 본 사용자가 2페이지로 넘어가기 전에 출간일이 2024-10-01인 11번 책이 새로 등록되었다고 하자. 이제 최신순 정렬은 11, 9, 6, 4, 2, 8, ...이 되므로 OFFSET 3의 2페이지는 4, 2, 8번이다. 사용자는 4번 책을 두 번 보게 된다. 반대로 행이 삭제되면 어떤 행은 어느 페이지에서도 보이지 않는다.

    두 문제를 함께 해결하는 방법이 키셋 페이지네이션(keyset pagination, seek method라고도 한다)이다. "몇 개를 건너뛸까" 대신 "마지막으로 본 행 다음부터"를 조건으로 쓴다. 1페이지의 마지막 행은 4번(2023-02-10)이었다. 정렬 키를 (published_on DESC, book_id DESC)로 고유하게 만들고 다음과 같이 조회한다.

    SELECT book_id, title, published_on
FROM book
WHERE published_on < '2023-02-10'
   OR (published_on = '2023-02-10' AND book_id < 4)
ORDER BY published_on DESC, book_id DESC
LIMIT 3;
    +---------+-------------------+--------------+
| book_id | title             | published_on |
+---------+-------------------+--------------+
|       2 | 자바 메모리 구조  | 2022-07-01   |
|       8 | 실록 읽기         | 2022-01-18   |
|      10 | 별 헤는 밤의 과학 | 2021-08-08   |
+---------+-------------------+--------------+

    결과는 오프셋 방식의 2페이지와 같다. 하지만 11번 책이 그사이에 추가되어도 조건이 "4번 책보다 뒤"이므로 결과가 바뀌지 않는다. 그리고 인덱스에서 시작점을 바로 찾아 내려가 거기서부터 세 항목만 읽으므로 몇 번째 페이지든 비용이 같다. 대가는 "37페이지로 바로 가기" 같은 임의 접근을 할 수 없다는 것이다. 무한 스크롤이나 "더 보기" 버튼처럼 앞으로만 나아가는 화면에 잘 맞는다. 이 예에서 동점 처리용 열로 book_id를 붙인 것은, idx_published_on 같은 InnoDB 보조 인덱스의 리프에 기본 키가 함께 들어 있으므로 인덱스 순서 자체가 사실상 (published_on, book_id) 순이라는 03회의 구조와도 맞아떨어진다.

    같은 B+Tree 인덱스의 리프 페이지 줄 위에서, 오프셋 방식은 처음부터 건너뛸 행을 모두 지나가고 키셋 방식은 시작점으로 바로 내려간다는 차이를 보여 준다. 위아래 두 단으로 나뉜 비교 그림. 각 단에는 작은 삼각형 모양의 B+Tree(루트 하나, 중간 노드 둘)와 그 아래 가로로 길게 이어진 리프 페이지 열 개가 양방향 화살표로 연결되어 있다. 위 단 제목 "오프셋 방식: LIMIT 20 OFFSET 100000". 위 단에서는 맨 왼쪽 리프부터 빨간 굵은 화살표가 리프를 하나씩 지나 아홉 번째 리프까지 이어지고, 지나간 리프들은 회색 빗금으로 칠해져 라벨 "읽고 버리는 10만 행"이 붙고, 마지막 리프 하나만 초록색으로 "돌려주는 20행". 아래 단 제목 "키셋 방식: WHERE 키 < 마지막으로 본 값". 아래 단에서는 루트에서 중간 노드를 거쳐 아홉 번째 리프로 바로 내려가는 파란 화살표가 있고 라벨 "시작점으로 바로 내려감", 아홉 번째 리프만 초록색으로 "돌려주는 20행". 흰 배경, 플랫 스타일. 오프셋 방식은 건너뛸 행을 모두 지나가야 하므로 뒤 페이지일수록 느려지고, 키셋 방식은 인덱스에서 시작점을 바로 찾는다.

    뒤의 권에서 다룰 Spring Data의 페이지 기능도 결국 이 SQL로 번역된다. 페이지 번호와 크기를 받는 방식은 LIMIT과 OFFSET이 되고, 전체 페이지 수까지 알려 주는 Page는 이를 위해 별도의 COUNT 쿼리를 한 번 더 실행한다. 행 수를 따로 세어 두지 않는 InnoDB에서 이 COUNT 쿼리가 큰 테이블에서 얼마나 비쌀 수 있는지는 위의 설명으로 짐작할 수 있다.

    DISTINCT: 중복 행을 하나로

    SQL의 조회 결과는 같은 행이 여러 번 나올 수 있다. 저자 목록을 뽑으면 김하늘, 이도윤, 박서연, 최민준, 정유나가 각각 두 번씩 나온다. DISTINCT는 결과에서 완전히 같은 행을 하나만 남긴다. 매뉴얼에 따르면 기본값은 중복을 포함해 모든 행을 돌려주는 ALL이고, DISTINCT는 결과 집합에서 중복 행을 제거하며, DISTINCTROW는 DISTINCT의 동의어다.

    SELECT DISTINCT category, author
FROM book
ORDER BY category, author;
    +----------+--------+
| category | author |
+----------+--------+
| IT       | 김하늘 |
| IT       | 이도윤 |
| 과학     | 정유나 |
| 소설     | 박서연 |
| 소설     | 정유나 |
| 역사     | 최민준 |
+----------+--------+

    가장 흔한 오해는 DISTINCT가 바로 뒤의 열 하나에만 적용된다는 생각이다. DISTINCT는 선택 목록 전체, 즉 행 단위로 중복을 판단한다. 위 결과에서 정유나는 과학과 소설에 한 번씩, 두 번 나온다. (과학, 정유나)와 (소설, 정유나)는 다른 행이기 때문이다. SELECT DISTINCT(category), author처럼 괄호를 쳐도 결과는 같다. 이 괄호는 함수 호출이 아니라 식을 묶는 평범한 괄호일 뿐이고, DISTINCT는 여전히 선택 목록 전체에 걸린다. 분류만 중복 없이 보고 싶다면 선택 목록에 category만 두어야 한다.

    NULL은 DISTINCT에서 서로 같은 값으로 취급된다. 매뉴얼은 DISTINCT, GROUP BY, ORDER BY에서 모든 NULL 값을 같은 것으로 본다고 적고 있다. 비교 연산에서는 NULL = NULL이 참이 아닌데, 중복 제거에서는 같다고 보는 것이다. SELECT DISTINCT discount_rate FROM book ORDER BY discount_rate의 결과는 NULL, 0, 5, 10, 20, 30의 여섯 행이고, NULL은 세 개가 아니라 한 번만 나온다.

    DISTINCT는 GROUP BY의 특수한 경우다

    서버가 중복을 찾으려면 같은 값끼리 모아야 한다. MySQL 매뉴얼은 대부분의 경우 DISTINCT를 GROUP BY의 특수한 경우로 볼 수 있다고 하며, SELECT DISTINCT c1, c2, c3 FROM t1 WHERE c1 > const와 SELECT c1, c2, c3 FROM t1 WHERE c1 > const GROUP BY c1, c2, c3가 동치라는 예를 든다. 선택한 모든 열로 그룹을 만들고 그룹마다 한 행씩 내보내는 것이다. 그룹을 만드는 방법은 두 가지다. 인덱스가 그 열들의 순서로 정렬되어 있다면 인덱스를 순서대로 읽으면서 값이 바뀔 때만 행을 내보내면 된다. 그렇지 않으면 이미 본 값을 기억해 둘 임시 테이블이 필요하다. EXPLAIN의 Using temporary가 이 경우다. 매뉴얼은 DISTINCT와 ORDER BY를 함께 쓰면 많은 경우 임시 테이블이 필요하다고 적고 있다. 또한 LIMIT과 함께 쓰면 MySQL은 고유한 행을 n개 찾는 즉시 멈춘다.

    DISTINCT를 GROUP BY로 보면 06회에서 배울 그룹핑과 자연스럽게 이어진다. 차이는 목적이다. DISTINCT는 "어떤 값들이 있는가"를 묻고, GROUP BY는 그에 더해 "그룹마다 몇 개인가, 합이 얼마인가"를 묻는다. 집계가 필요하면 GROUP BY를, 고유한 조합의 목록만 필요하면 DISTINCT를 쓴다.

    DISTINCT와 ORDER BY가 부딪히는 경우

    "저자 목록을 중복 없이, 그 저자의 책 가격 순으로" 뽑고 싶어서 다음과 같이 쓰면 MySQL은 이 쿼리를 거부한다.

    SELECT DISTINCT author
FROM book
ORDER BY price;   -- 거부된다: price가 선택 목록에 없다
    ERROR 3065 (HY000): Expression #1 of ORDER BY clause is not in SELECT list, references column 'm_db_intro_04.book.price' which is not in SELECT list; this is incompatible with DISTINCT

    오류 문구의 m_db_intro_04는 실습에 쓴 데이터베이스 이름이다. 문구 그대로 "ORDER BY의 첫 번째 식이 선택 목록에 없는 price 열을 참조하므로 DISTINCT와 함께 쓸 수 없다"는 뜻이다.

    논리적 처리 순서로 이유를 따라가 보자. DISTINCT(⑥)가 먼저 일어나 이도윤의 두 행(32000원, 30000원)이 한 행으로 합쳐진다. 그다음 ORDER BY(⑦)가 price로 정렬하려는데, 합쳐진 이도윤 행의 가격은 32000인가 30000인가. 어느 쪽을 고르느냐에 따라 정렬 결과가 달라지므로 결과가 정의되지 않는다. MySQL 매뉴얼은 정확히 이 상황을 예로 들어, DISTINCT와 ORDER BY가 있는 쿼리에서 ORDER BY의 식이 선택 목록의 식과 같지도 않고, 그 식이 참조하는 열이 모두 선택 목록에 있지도 않으면 그 쿼리를 잘못된 것으로 거부한다고 설명한다. 이 설명은 기본으로 켜져 있는 SQL 모드 ONLY_FULL_GROUP_BY를 다루는 절에 있다. 원하는 결과가 "저자별 최고가 순"이라면 그것은 집계의 문제이고, GROUP BY author ORDER BY MAX(price)처럼 쓰는데 06회에서 다룬다.

    마지막으로 DISTINCT가 습관처럼 붙어 있는 쿼리를 보면 의심해 볼 만하다. 나중에 여러 테이블을 조인하면 한 행이 여러 번 복제되어 나오는 일이 생기는데, 원인을 고치지 않고 DISTINCT로 덮는 경우가 많다. 그러면 서버는 필요 없는 행을 만들어 낸 뒤 임시 테이블로 다시 지우는 이중의 일을 한다. 중복이 왜 생기는지 먼저 이해하고, DISTINCT는 "정말로 고유한 값의 목록"이 필요할 때 쓴다.

    NULL: 알 수 없는 값과 3값 논리

    MySQL 매뉴얼은 NULL을 개념적으로 "빠져 있는 알 수 없는 값(a missing unknown value)"이라고 설명한다. NULL은 0도 아니고 빈 문자열도 아니다. 매뉴얼의 예를 빌리면 전화번호 열에 NULL을 넣는 것은 "전화번호를 모른다"는 뜻이고, 빈 문자열을 넣는 것은 "전화가 없다는 것을 안다"는 뜻이다. 이 테이블의 discount_rate도 같다. NULL은 "할인율을 아직 정하지 않았다", 0은 "할인하지 않기로 정했다"이다. NOT NULL 열에도 0이나 빈 문자열은 얼마든지 넣을 수 있다. 그것들은 값이고, NULL은 "값이 없음"이기 때문이다.

    NULL은 전파된다

    매뉴얼에 따르면 NULL이 들어간 식은 연산자나 함수의 설명에 따로 적혀 있지 않은 한 항상 NULL을 만든다. 1 + NULL도, CONCAT('Invisible', NULL)도 NULL이다. 모르는 값에 무엇을 더해도 결과는 여전히 모른다. 할인가를 계산해 보자.

    SELECT book_id, price, discount_rate,
       price * (100 - discount_rate) DIV 100 AS sale_price
FROM book
WHERE category = 'IT'
ORDER BY book_id;
    +---------+-------+---------------+------------+
| book_id | price | discount_rate | sale_price |
+---------+-------+---------------+------------+
|       1 | 28000 |            10 |      25200 |
|       2 | 32000 |          NULL |       NULL |
|       6 | 35000 |            10 |      31500 |
|       9 | 30000 |             0 |      30000 |
+---------+-------+---------------+------------+

    할인율이 0인 9번은 정가가 그대로 나오지만, 할인율이 NULL인 2번은 판매가도 NULL이다. 업무적으로 "할인율 미정이면 정가로 판다"는 규칙이 있다면 그 규칙을 쿼리에 명시해야 한다. NULL을 다른 값으로 바꾸는 IFNULL(), COALESCE() 같은 함수는 05회에서 다룬다. DIV는 정수 나눗셈 연산자이고, *와 우선순위가 같아 왼쪽부터 계산되므로 위 식은 (price * (100 - discount_rate)) DIV 100이다.

    = NULL은 아무 행도 찾지 못한다

    비교도 마찬가지다. 매뉴얼의 예에서 1 = NULL, 1 <> NULL, 1 < NULL, 1 > NULL은 모두 NULL이고, NULL = NULL도 NULL이다. "모르는 값이 1과 같은가"의 답은 "모른다"이고, "모르는 값 둘이 같은가"의 답도 "모른다"다. 그래서 다음 쿼리는 할인율이 NULL인 책이 세 권 있는데도 아무것도 돌려주지 않는다.

    SELECT book_id FROM book WHERE discount_rate = NULL;      -- 0행
SELECT book_id FROM book WHERE discount_rate IS NULL;     -- 2, 4, 8
SELECT book_id FROM book WHERE discount_rate IS NOT NULL; -- 나머지 7행

    NULL인지 확인하려면 비교 연산자가 아니라 IS NULL, IS NOT NULL을 쓴다. 이 둘은 피연산자가 NULL이어도 NULL이 아니라 1이나 0을 돌려주는 연산자다. MySQL에는 NULL을 안전하게 비교하는 <=> 연산자도 있다. 매뉴얼에 따르면 =처럼 비교하되 양쪽이 모두 NULL이면 NULL 대신 1을, 한쪽만 NULL이면 0을 돌려주며, 표준 SQL의 IS NOT DISTINCT FROM과 같은 뜻이다. discount_rate <=> NULL은 2, 4, 8번을 찾는다. 바인딩한 파라미터가 NULL일 수도 있는 비교, 예를 들어 "이 열이 주어진 값과 같거나, 주어진 값이 NULL이면 열도 NULL인 행"을 한 조건으로 쓰고 싶을 때 유용하다.

    3값 논리: 참, 거짓, 모름

    NULL이 비교 결과로 나오면서 SQL의 논리는 참(TRUE)·거짓(FALSE)·모름(UNKNOWN)의 세 값을 갖게 된다. MySQL에서는 이들이 1, 0, NULL로 표현된다. 매뉴얼의 정의를 표로 정리하면 다음과 같다. AND는 피연산자 중 하나라도 거짓이면 다른 쪽을 몰라도 거짓이고, OR는 하나라도 참이면 다른 쪽을 몰라도 참이다. 그 밖에 모름이 섞이면 결과도 모름이다.

    ABA AND BA OR BNOT A
    참참참참거짓
    참거짓거짓참거짓
    참모름모름참거짓
    거짓거짓거짓거짓참
    거짓모름거짓모름참
    모름모름모름모름모름

    여기에 WHERE의 규칙, "결과가 참인 행만 남긴다"를 더하면 NULL에 관한 거의 모든 함정을 계산할 수 있다. 할인율로 확인해 보자. 열 권 중 discount_rate = 10은 1, 6번의 두 권이다. 그렇다면 discount_rate <> 10은 나머지 여덟 권일까?

    SELECT book_id FROM book WHERE discount_rate <> 10;
-- 3, 5, 7, 9, 10  (다섯 권)

    다섯 권뿐이다. NULL인 2, 4, 8번에서는 NULL <> 10이 모름이므로 걸러졌다. 같다(2권) + 다르다(5권) + 모름(3권) = 10권이다. 자바의 filter에서는 어떤 조건과 그 부정이 원소를 정확히 둘로 나누지만, SQL에서는 세 갈래로 나눈다. NOT을 씌워도 마찬가지다. discount_rate > 5는 1, 5, 6, 7번의 네 권이고, NOT (discount_rate > 5)는 3, 9, 10번의 세 권이다. 모름에 NOT을 씌우면 여전히 모름이므로 NULL인 세 권은 어느 쪽에도 들어가지 않는다. "할인율이 5% 이하이거나 아직 정해지지 않은 책"을 원한다면 NOT (discount_rate > 5) OR discount_rate IS NULL처럼 NULL을 명시적으로 포함시켜야 한다.

    조건 discount_rate <> 10이 열 개의 행을 참·거짓·모름 세 갈래로 나누고, WHERE는 참인 갈래만 통과시킨다는 것을 보여 준다. 왼쪽에 세로로 쌓인 카드 열 장, 각 카드에 책 번호와 할인율이 적혀 있다: "1: 10", "2: NULL", "3: 0", "4: NULL", "5: 20", "6: 10", "7: 30", "8: NULL", "9: 0", "10: 5". 가운데에 깔때기 모양 필터와 라벨 "WHERE discount_rate <> 10". 깔때기에서 오른쪽으로 세 갈래 길이 나간다. 위쪽 초록 길 라벨 "참 → 결과에 포함", 도착한 카드 3, 5, 7, 9, 10. 가운데 회색 길 라벨 "거짓 → 버림", 도착한 카드 1, 6. 아래쪽 주황 점선 길 라벨 "모름(NULL) → 버림", 도착한 카드 2, 4, 8. 흰 배경, 플랫 일러스트 스타일. SQL의 조건은 행을 참·거짓·모름 세 갈래로 나누고, WHERE는 참인 행만 남긴다. NULL인 행은 조건과 그 부정 어느 쪽에서도 빠진다.

    NOT IN과 NULL: 결과가 통째로 사라진다

    가장 위험한 경우는 NOT IN 목록에 NULL이 섞일 때다. 앞에서 본 규칙대로 IN은 일치하는 값이 없고 목록에 NULL이 있으면 NULL을 돌려준다. 따라서 다음 쿼리는 0행을 돌려준다.

    SELECT book_id FROM book WHERE discount_rate NOT IN (10, NULL);   -- 0행

    3값 논리로 풀어 보자. x NOT IN (10, NULL)은 NOT (x = 10 OR x = NULL)이고, 드모르간 법칙으로 x <> 10 AND x <> NULL이다. 뒤쪽 x <> NULL은 x가 무엇이든 모름이다. 참 AND 모름은 모름이고, 거짓 AND 모름은 거짓이므로, 어떤 행도 참이 될 수 없다. 직접 NULL을 목록에 쓰는 사람은 없겠지만, 뒤에서 배울 서브쿼리로 목록을 만들 때(WHERE x NOT IN (SELECT y FROM ...)) 그 열에 NULL이 하나라도 있으면 정확히 이 일이 일어난다. 오류도 경고도 없이 결과가 빈 집합이 된다. NOT LIKE도 비슷하다. 매뉴얼은 NULL NOT LIKE expr가 항상 NULL이라는 점을 지적하며, NULL인 행까지 세려면 OR bar IS NULL을 붙이라고 안내한다.

    정리하면, NULL과 만나는 연산 가운데 "같은 것으로 본다"는 쪽과 "모른다"는 쪽이 갈린다. DISTINCT, GROUP BY, ORDER BY에서 NULL끼리는 같은 값으로 취급되고, 비교와 논리 연산에서는 모름이 된다. 06회에서 다룰 집계 함수는 또 다르다. 매뉴얼에 따르면 COUNT(), MIN(), SUM() 같은 집계 함수는 NULL을 무시하며, 행 자체를 세는 COUNT(*)만 예외다.

    한 층 아래: NULL은 어떻게 저장되고 인덱싱되는가

    "모른다"는 값을 디스크에는 어떻게 적을까. InnoDB의 기본 행 형식은 DYNAMIC이고(시스템 변수 innodb_default_row_format의 기본값), DYNAMIC은 저장 방식에서 COMPACT 형식의 특성을 그대로 따른다. MySQL 매뉴얼은 COMPACT 형식의 레코드 헤더에 NULL 열을 표시하는 비트 벡터가 있다고 설명한다. 인덱스에서 NULL이 될 수 있는 열이 N개면 이 비트 벡터는 CEILING(N/8)바이트를 차지하고, NULL인 열은 이 비트 하나 외에 공간을 쓰지 않는다. book 테이블에서 NULL을 허용하는 열은 discount_rate 하나뿐이므로 각 행의 비트 벡터는 1바이트이고, 할인율이 NULL인 행은 4바이트 정수 자리를 아예 쓰지 않는다. NULL은 "특별한 값을 열에 써 두는 것"이 아니라 "값이 없다고 헤더에 표시하는 것"이다.

    NULL을 허용하는 열에도 인덱스를 만들 수 있다. 매뉴얼에 따르면 MyISAM, InnoDB, MEMORY 저장 엔진은 NULL이 될 수 있는 열의 인덱스를 지원하고, col_name IS NULL 검색은 그 열에 인덱스가 있으면 인덱스를 쓴다. 인덱스 안에서 NULL 항목은 모두 같은 값으로 취급되어 한곳에 모여 있으므로 하나의 구간으로 찾을 수 있다. WHERE col = ? OR col IS NULL 형태는 EXPLAIN에서 ref_or_null로 나타나는데, 값으로 한 번 찾고 NULL로 한 번 더 찾는다는 뜻이다.

    자바의 null과 SQL의 NULL

    자바의 null은 "참조가 아무 객체도 가리키지 않는다"는 뜻이고, null == null은 true다. SQL의 NULL은 "값을 모른다"는 뜻이고, NULL = NULL은 모름이다. 이름은 같지만 의미가 다르며, 경계에서 사고가 난다. 대표적인 곳이 JDBC다. ResultSet.getInt()의 Javadoc은 값이 SQL NULL이면 0을 돌려준다고 적고 있다. 원시 타입 int에는 "모름"을 담을 자리가 없기 때문이다. 그래서 getInt("discount_rate")로 읽으면 할인율 미정(NULL)과 할인 없음(0)이 구별되지 않는다. 구별하려면 읽은 직후 wasNull()을 호출해 마지막으로 읽은 열이 SQL NULL이었는지 확인해야 한다. 뒤의 권에서 JPA 엔티티를 설계할 때 NULL을 허용하는 열을 int가 아닌 Integer 같은 래퍼 타입으로 매핑하는 이유가 여기에 있다.

    적용 연습: 요구사항을 쿼리로 옮기기

    지금까지의 절을 조합해 요구사항 몇 개를 쿼리로 옮겨 보자. 요구사항을 읽을 때마다 "어느 행을 남기는가(WHERE), 어떤 열을 보이는가(SELECT), 중복을 없애는가(DISTINCT), 어떤 순서인가(ORDER BY), 몇 개인가(LIMIT)"를 차례로 묻고, NULL을 허용하는 열이 조건에 등장하면 NULL인 행을 어디에 넣을지 따로 결정한다.

    요구 1. "재고가 있는 IT·과학 책 가운데 2021년 이후 출간된 책을 비싼 순으로 두 권." 분류는 IN으로, 재고 조건은 stock > 0으로, 출간일은 열을 그대로 둔 범위 조건으로 쓴다. 가격이 같은 책이 생길 수 있으니 고유한 열을 정렬 키 끝에 붙인다.

    SELECT book_id, title, price
FROM book
WHERE category IN ('IT', '과학')
  AND stock > 0
  AND published_on >= '2021-01-01'
ORDER BY price DESC, book_id
LIMIT 2;
    +---------+-------------------+-------+
| book_id | title             | price |
+---------+-------------------+-------+
|       6 | 네트워크 바닥부터 | 35000 |
|       9 | SQL 100% 활용     | 30000 |
+---------+-------------------+-------+

    후보는 1, 6, 9, 10번이다. 2번은 IT이고 2021년 이후 출간이지만 재고가 0이라 빠졌다. 후보를 가격 내림차순으로 세우면 6(35000), 9(30000), 1(28000), 10(18000)이고, 앞의 두 권이 결과다.

    요구 2. "할인율이 아직 정해지지 않았거나 10% 미만인 책." discount_rate < 10만 쓰면 NULL인 행이 모름으로 빠지므로, 요구사항이 NULL을 포함하라고 말하는 이상 IS NULL을 명시한다.

    SELECT book_id, discount_rate
FROM book
WHERE discount_rate IS NULL OR discount_rate < 10
ORDER BY book_id;
-- 결과: 2(NULL), 3(0), 4(NULL), 8(NULL), 9(0), 10(5)

    요구 3. "책을 낸 적이 있는 저자 목록을 이름순으로." 저자가 여러 번 나오므로 DISTINCT를 쓰고, 정렬 열이 선택 목록에 있으니 DISTINCT와 ORDER BY가 충돌하지 않는다.

    SELECT DISTINCT author
FROM book
ORDER BY author;
-- 결과: 김하늘, 박서연, 이도윤, 정유나, 최민준

    요구 4. "최신 출간순 목록의 두 번째 페이지(페이지당 세 권)." 오프셋 방식이면 ORDER BY published_on DESC, book_id DESC LIMIT 3 OFFSET 3이고 결과는 2, 8, 10번이다. 첫 페이지의 마지막 행(4번, 2023-02-10)을 알고 있다면 키셋 방식으로 같은 결과를 얻을 수 있으며, 그 쿼리는 LIMIT 절에서 본 것과 같다. 정렬 키 끝의 book_id DESC는 지금 데이터에서는 결과를 바꾸지 않지만, 출간일이 같은 책이 등록되는 순간부터 페이지 경계를 지켜 준다.

    정리: 이 회차의 지식이 다시 쓰이는 곳

    이 회차의 내용은 SELECT 문의 절 여섯 개로 요약된다. 하지만 각 절 뒤에는 선언적 언어라는 성격이 있었다. SQL은 결과의 모양만 약속하므로, 약속하지 않은 순서는 보장되지 않고(ORDER BY, 동점), 약속을 지키는 방법은 서버가 고른다(인덱스 범위 검색, 전체 스캔, filesort, 임시 테이블). 쿼리를 쓰는 사람이 할 일은 원하는 결과를 정확히 약속하는 것, 그리고 서버가 싼 방법을 고를 수 있도록 조건의 모양을 다듬는 것이다.

    이 지식은 앞으로 여러 곳에서 다시 쓰인다. 05회의 함수는 SELECT 목록과 WHERE에 들어가는데, 함수를 WHERE의 열에 씌우면 인덱스를 못 쓴다는 이 회차의 원칙이 그대로 적용된다. 06회의 GROUP BY와 HAVING은 논리적 처리 순서의 ③, ④ 자리를 채우고, 집계 함수가 NULL을 무시한다는 규칙은 3값 논리와 짝을 이룬다. 뒤의 권에서 JPA를 쓰면 JPQL의 WHERE, ORDER BY, IS NULL이 결국 여기서 본 SQL로 번역되고, 페이지 처리는 LIMIT과 OFFSET이 된다. 그때 생성된 SQL을 로그로 보며 "이 조건은 인덱스 구간이 되는가, 이 정렬은 결정적인가, 이 열은 NULL을 허용하는가"를 묻는 습관이 성능 문제와 데이터 누락 버그를 미리 막는다.

    이 장의 핵심

    SELECT 문은 FROM → WHERE → SELECT → DISTINCT → ORDER BY → LIMIT의 논리적 순서로 의미가 정해지고, 서버는 그 의미를 지키는 한 가장 싼 실행 방법을 고른다. 순서는 ORDER BY로 요청하고 고유한 키로 동점을 깨야만 결정적이다. 조건은 열을 맨몸으로 둔 구간 형태일 때 인덱스를 쓴다. 그리고 NULL이 들어간 비교는 참도 거짓도 아닌 모름이 되어 WHERE에서 조용히 빠지므로, NULL을 허용하는 열에 조건을 걸 때마다 NULL인 행의 행방을 따로 정해야 한다.
    논리적 처리 순서
    SELECT 문의 의미는 FROM → WHERE → (GROUP BY → HAVING) → SELECT → DISTINCT → ORDER BY → LIMIT 순으로 정해진다. 그래서 WHERE에서는 SELECT의 별칭을 쓸 수 없고 ORDER BY에서는 쓸 수 있다. 실제 실행 순서는 옵티마이저가 정한다.
    WHERE와 3값 논리
    비교 결과는 1, 0, NULL 중 하나이고 WHERE는 1인 행만 남긴다. NULL과의 비교는 모름이 되어 조건과 그 부정 어느 쪽에서도 빠진다.
    연산자 우선순위
    AND가 OR보다 먼저 묶인다. AND와 OR를 섞을 때는 항상 괄호를 쓴다.
    인덱스를 쓰는 조건
    B-tree 인덱스는 =, 대소 비교, BETWEEN, 와일드카드로 시작하지 않는 LIKE처럼 정렬 순서에서 연속된 구간이 되는 조건에 쓰인다. 열에 함수를 씌우거나 문자열 열을 숫자와 비교하면 구간이 되지 않는다.
    BETWEEN, IN, LIKE
    BETWEEN은 양 끝을 포함한다. IN은 = 조건의 OR와 같고 목록에 NULL이 있으면 NOT IN이 아무 행도 돌려주지 않는다. LIKE의 %는 0개 이상, _는 정확히 한 문자와 일치한다.
    ORDER BY와 동점
    ORDER BY가 없으면 순서가 없고, 정렬 키가 같은 행끼리의 순서는 실행 계획에 따라 달라진다. 고유한 열을 정렬 키 끝에 붙여야 결정적이다. MySQL에서 NULL은 ASC일 때 맨 앞이다.
    filesort
    인덱스 순서로 정렬을 대신할 수 없을 때 정렬 버퍼(sort_buffer_size)에서 따로 정렬하는 단계다. 버퍼를 넘으면 임시 파일과 병합을 쓴다.
    LIMIT과 키셋 페이지네이션
    LIMIT n OFFSET m은 m행을 지나간 뒤 n행을 돌려주므로 오프셋이 클수록 느리고 데이터 변경에 따라 행이 중복·누락된다. 마지막으로 본 키 다음부터 읽는 키셋 방식은 두 문제를 피한다.
    DISTINCT
    선택 목록 전체를 기준으로 같은 행을 하나만 남기며 GROUP BY의 특수한 경우다. NULL끼리는 같은 값으로 본다. 선택 목록에 없는 열로 정렬하면 결과가 정의되지 않아 거부된다.

    실무에서 가장 자주 만나는 조회 장애는 "개발 환경에서는 빨랐는데 운영에서 느리다"이다. 개발 데이터는 몇 백 행이라 전체 스캔과 filesort가 아무 문제가 되지 않다가, 운영 데이터가 수백만 행이 되면 같은 쿼리가 수 초씩 걸린다. 이때 확인할 순서는 이 회차의 내용 그대로다. EXPLAIN의 type이 ALL인지, Extra에 Using filesort나 Using temporary가 있는지 보고, WHERE의 열에 함수가 씌워져 있지 않은지, 문자열 열에 숫자를 바인딩하고 있지 않은지, LIKE가 와일드카드로 시작하지 않는지 본다. 같은 조건이라도 열을 맨몸으로 두도록 다시 쓰는 것만으로 범위 검색이 되는 경우가 많다.

    두 번째로 흔한 것은 오류 없이 틀린 결과를 내는 쿼리다. 무한 스크롤 목록에서 같은 상품이 두 번 보인다는 문의는 대개 동점이 있는 정렬 키에 OFFSET 페이지를 붙인 결과이고, 고유 키를 정렬에 추가하거나 키셋 방식으로 바꾸면 해결된다. "제외 목록에 없는 회원에게 알림 보내기" 배치가 아무에게도 보내지 않았다면 NOT IN의 목록에 NULL이 섞였는지 먼저 의심한다. 할인 대상 집계에서 숫자가 맞지 않는다면 NULL을 허용하는 열에 부등호 조건을 걸어 NULL인 행이 빠졌는지 본다. 이런 버그는 실행 결과만 보면 그럴듯해서 데이터를 손으로 세어 보기 전까지 드러나지 않는다.

    판단이 달라지는 조건도 기억해 두자. 페이지 번호로 임의 이동이 꼭 필요한 관리자 화면이라면 OFFSET 방식을 유지하되 정렬 키를 고유하게 만들고, 깊은 페이지 접근을 제한하는 식으로 절충한다. 행 수가 적고 앞으로도 늘지 않는 코드성 테이블이라면 인덱스나 정렬 비용을 고민할 이유가 거의 없다. NULL 허용 여부는 테이블을 만들 때 결정하는데, "모름"이라는 상태가 업무적으로 정말 필요한 열에만 NULL을 허용하고 나머지는 NOT NULL과 기본값으로 막아 두면 이 회차의 함정 대부분이 처음부터 생기지 않는다.
  • SELECT book_id FROM book WHERE discount_rate <> 0과 SELECT book_id FROM book WHERE NOT (discount_rate <> 0)의 결과를 각각 예측하라. 두 결과의 행 수를 더하면 10이 되는가? 되지 않는다면 빠진 행이 무엇이고 왜 빠졌는지 3값 논리로 설명하라.
  • 다음 쿼리는 "재고가 있는 IT 책과 과학 책"을 찾으려고 쓴 것이다. SELECT book_id FROM book WHERE category = 'IT' OR category = '과학' AND stock > 0의 실제 결과를 예측하고, 의도와 다른 이유를 우선순위로 설명한 뒤 고쳐라.
  • SELECT DISTINCT author FROM book ORDER BY price를 MySQL이 거부하는 이유를 논리적 처리 순서와 이 테이블의 실제 데이터(이도윤의 두 책)를 들어 설명하라.
  • 어떤 화면이 SELECT * FROM book ORDER BY category LIMIT 3 OFFSET 0으로 1페이지를, ... LIMIT 3 OFFSET 3으로 2페이지를 보여 준다. 같은 책이 두 페이지에 모두 나오거나 어느 페이지에도 나오지 않을 수 있는 이유를 설명하고, 이를 막도록 쿼리를 고쳐라.
  • idx_published_on이 있을 때 다음 세 조건 가운데 인덱스 범위 검색을 쓸 수 있는 것은 무엇인가? (가) YEAR(published_on) = 2023 (나) published_on BETWEEN '2023-01-01' AND '2023-12-31' (다) DATE_FORMAT(published_on, '%Y') = '2023'. 만약 열 타입이 DATETIME이라면 (나)를 어떻게 바꿔야 하는지도 답하라.

    1. discount_rate <> 0은 할인율이 NULL도 0도 아닌 1(10), 5(20), 6(10), 7(30), 10(5)번의 다섯 행이다. NOT (discount_rate <> 0)은 할인율이 0인 3, 9번의 두 행이다. 합은 7로, 10이 되지 않는다. 빠진 것은 할인율이 NULL인 2, 4, 8번이다. 이 행에서 NULL <> 0은 모름이고, 모름에 NOT을 씌워도 모름이다. WHERE는 참인 행만 남기므로 두 쿼리 어디에도 들어가지 않는다.

    투영(projection)
    테이블에서 특정 열만 남기는 관계 연산. SQL에서는 SELECT의 선택 목록이 이 일을 한다.
    선택·제한(selection, restriction)
    조건을 만족하는 행만 남기는 관계 연산. SQL에서는 WHERE가 이 일을 한다.
    논리적 처리 순서(logical processing order)
    SELECT 문의 각 절이 결과의 의미에 적용되는 개념상의 순서. 실제 실행 순서와는 다를 수 있다.
    콜레이션(collation)
    문자열을 비교하고 정렬하는 규칙. MySQL 8.0 기본값 utf8mb4_0900_ai_ci는 대소문자와 악센트를 구분하지 않고 끝 공백을 구분한다(NO PAD).
    사거블 조건(sargable predicate)
    열을 가공하지 않고 상수와 비교해 인덱스의 연속된 구간으로 바꿀 수 있는 형태의 조건.
    filesort
    인덱스 순서로 정렬을 대신할 수 없을 때 MySQL이 정렬 버퍼와 필요하면 임시 파일을 써서 행을 정렬하는 단계. EXPLAIN에 Using filesort로 나타난다.
    커버링 인덱스(covering index)
    쿼리가 필요로 하는 열을 모두 담고 있어 테이블 행을 다시 찾아가지 않고 인덱스만으로 답할 수 있는 인덱스. EXPLAIN에 Using index로 나타난다.
    키셋 페이지네이션(keyset pagination)
    건너뛸 행 수 대신 마지막으로 본 행의 정렬 키 값을 조건으로 다음 페이지를 읽는 방식. seek method라고도 한다.
    3값 논리(three-valued logic)
    참·거짓·모름(UNKNOWN)의 세 진릿값을 쓰는 논리. SQL에서 NULL이 섞인 비교와 논리 연산이 이 규칙을 따른다.
    NULL 안전 동등 비교(NULL-safe equal)
    MySQL의 <=> 연산자. 양쪽이 모두 NULL이면 1, 한쪽만 NULL이면 0을 돌려주며 표준 SQL의 IS NOT DISTINCT FROM과 같은 뜻이다.
