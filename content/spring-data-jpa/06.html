    이 회차의 질문: 인터페이스만 있는데 누가 일을 하는가

    지금까지 이 권에서는 JpaRepository를 상속한 인터페이스 하나만 선언하면 저장, 조회, 삭제, 페이징, 쿼리 메서드가 모두 동작한다는 사실을 당연하게 써 왔다. 자바에서 인터페이스는 메서드의 모양만 정할 뿐 몸체가 없다. 그런데도 memberRepository.save(member)를 호출하면 INSERT가 나가고, findById를 호출하면 SELECT가 나간다. 누군가 이 인터페이스를 구현한 객체를 만들어 빈으로 등록했고, 그 객체 안에서 진짜 일이 일어난다. 2회차에서 공통 인터페이스를 다루며 "스프링 데이터 JPA가 구현 클래스를 대신 만든다"고 짧게 상기했다면, 이번 회차는 그 구현을 직접 열어 본다.

    열어 봐야 하는 이유는 호기심 때문만이 아니다. 실무에서 스프링 데이터 JPA 때문에 생기는 장애의 상당수는 "save()가 내부에서 무엇을 하는지"를 모른 채 쓰는 데서 나온다. 저장 한 번에 SELECT가 먼저 나가는 이유, save()로 새 행을 만들려 했는데 기존 행이 조용히 덮어써지는 이유, save()가 돌려준 객체와 넘긴 객체가 다른 객체라서 이후 변경이 반영되지 않는 이유, 서비스 메서드에 @Transactional을 빼먹었는데도 저장은 되는 이유가 모두 같은 곳에서 출발한다. 그 출발점이 SimpleJpaRepository라는 클래스와, 이 클래스를 감싼 프록시다.

    이 회차는 두 부분으로 나뉜다. 앞부분은 "구현체 분석"이다. 리포지토리 빈의 정체가 JDK 동적 프록시라는 것을 실험으로 확인하고, 그 프록시에 끼워진 인터셉터들이 어떤 순서로 무슨 일을 하는지, 그리고 최종 목적지인 SimpleJpaRepository의 각 메서드가 EntityManager의 어떤 메서드로 번역되는지 따라간다. 트랜잭션 속성이 어디서 오는지, readOnly = true가 하이버네이트에게 실제로 무엇을 시키는지도 여기서 다룬다. 뒷부분은 "새로운 엔티티를 구별하는 방법"이다. save()는 엔티티가 새것이면 persist, 아니면 merge를 호출하는데, 그 "새것"의 판단 규칙과 규칙이 틀렸을 때 일어나는 일을 소스와 실행 결과로 확인한다.

    이 장의 핵심

    리포지토리 빈은 인터페이스를 구현한 JDK 동적 프록시이고, 호출은 메타데이터 기록, 예외 변환, 트랜잭션, 쿼리 메서드 실행 인터셉터를 차례로 지난 뒤 SimpleJpaRepository에 도달한다. SimpleJpaRepository.save()는 판별 결과에 따라 persist나 merge를 부를 뿐이므로, 판별이 틀리면 불필요한 SELECT, 기존 행 덮어쓰기, 예외가 생긴다. 판별 규칙은 Persistable 구현 여부, 래퍼 타입 버전 필드, 식별자 값의 순서로 정해진다.

    실험 환경과 프록시의 정체

    인터셉터 여섯 개: 호출 한 번이 지나가는 길

    스프링 AOP의 ProxyFactory에 어드바이스를 추가하면, 먼저 추가된 것이 바깥쪽에 놓인다. 프록시의 메서드가 호출되면 ReflectiveMethodInvocation이 인터셉터 목록을 앞에서부터 하나씩 호출하고, 각 인터셉터는 invocation.proceed()를 불러 다음 인터셉터에게 넘기거나, 부르지 않고 직접 결과를 돌려준다. 그래서 위 출력의 순서가 곧 호출이 지나가는 순서다. 이 순서가 어떻게 정해지는지는 Spring Data Commons 3.5.13의 RepositoryFactorySupport.getRepository()를 읽으면 나온다.

    getRepository()는 먼저 타깃 객체(SimpleJpaRepository)를 만들고, ProxyFactory를 생성해 타깃과 인터페이스(우리의 리포지토리 인터페이스, Repository, TransactionalProxy)를 지정한다. 그다음 조건부 어드바이스 두 개를 검사한다. 리포지토리 인터페이스가 널 허용성 검사 대상이면(NullnessMethodInvocationValidator.supports가 판단한다) 인자와 반환값을 검사하는 MethodInvocationValidator를, 메타데이터 노출이 켜져 있으면 ExposeMetadataInterceptor를 추가한다. 실험의 인터페이스에는 둘 다 해당하지 않아 목록에 없다. 이어서 등록된 RepositoryProxyPostProcessor들을 차례로 실행하는데, 이 후처리기들이 앞쪽 세 개의 인터셉터를 넣는다. 그 뒤에 인터페이스에 default 메서드가 있으면 DefaultMethodInvokingMethodInterceptor를, 마지막으로 QueryExecutorMethodInterceptor와 ImplementationMethodExecutionInterceptor를 무조건 추가한다.

    후처리기의 순서는 두 곳에서 정해진다. JpaRepositoryFactory의 생성자가 먼저 CrudMethodMetadataPostProcessor를 등록하고, 이어서 "인터페이스에 Stream을 반환하는 메서드나 @Procedure 메서드가 있으면 SurroundingTransactionDetectorMethodInterceptor를 추가하는" 람다를 등록한다. 실험의 인터페이스에는 그런 메서드가 없어서 이 인터셉터도 빠졌다. 그 뒤 TransactionalRepositoryFactoryBeanSupport.createRepositoryFactory()가 팩토리를 만든 다음 예외 변환 후처리기와 트랜잭션 후처리기를 이 순서로 덧붙인다. 그래서 메타데이터 기록이 가장 바깥, 그 안쪽에 예외 변환, 그 안쪽에 트랜잭션이 놓인다.

    순서인터셉터누가 넣는가하는 일
    1CrudMethodMetadataPopulatingMethodInterceptorJpaRepositoryFactory 생성자지금 호출된 메서드 정보를 스레드 로컬에 올려 둔다. SimpleJpaRepository가 그 메서드에 붙은 @Lock, @QueryHints, @EntityGraph를 읽는 통로다.

    4DefaultMethodInvokingMethodInterceptorgetRepository()(default 메서드가 있을 때)인터페이스의 default 메서드가 호출되면 그 몸체를 직접 실행한다. JpaRepository에는 deleteInBatch 같은 default 메서드가 있어서 항상 들어간다.

    6ImplementationMethodExecutionInterceptorgetRepository()리포지토리 조각(fragment)들의 조합에서 메서드를 구현한 객체를 찾아 호출한다. 기본 조각이 SimpleJpaRepository다.

    다섯 번째 인터셉터의 동작은 소스로 확인해 둘 가치가 있다. QueryExecutorMethodInterceptor.doInvoke()는 hasQueryFor(method)로 이 메서드에 대응하는 쿼리 객체가 있는지 보고, 있으면 그 쿼리를 실행해 결과를 반환한다. 없으면 invocation.proceed()를 호출해 다음 인터셉터로 넘긴다. 쿼리 객체는 이 인터셉터의 생성자에서, 즉 리포지토리 프록시를 만드는 시점(기본 설정에서는 애플리케이션 시작 시점)에 만들어진다. 3회차에서 본 메서드 이름 해석과 @Query 파싱이 바로 이 쿼리 객체를 만드는 과정이고, 잘못된 메서드 이름이 애플리케이션 시작 단계에서 실패하는 이유도 여기에 있다. 따라서 findByName은 다섯 번째 인터셉터에서 처리가 끝나 SimpleJpaRepository까지 내려가지 않는다. 반대로 save, findById처럼 JpaRepository가 정의한 메서드는 대응하는 쿼리 객체가 없으므로 여섯 번째 인터셉터를 거쳐 SimpleJpaRepository에 도달한다.

    여섯 번째 인터셉터가 "조각들의 조합"을 뒤진다는 점은 5회차에서 다룬 사용자 정의 리포지토리와 연결된다. getRepository()는 사용자 정의 구현 조각들 뒤에 RepositoryFragment.implemented(target), 즉 SimpleJpaRepository를 덧붙여 조합을 만든다. 메서드를 찾을 때 앞의 조각부터 보므로, 사용자 정의 구현이 같은 시그니처의 메서드를 제공하면 그것이 기본 구현보다 먼저 선택된다. 이 회차에서는 조각이 기본 구현 하나뿐인 상황을 다룬다.

    SimpleJpaRepository: 클래스 선언이 말해 주는 것

    이제 타깃 클래스를 열어 보자. Spring Data JPA 3.5.13의 SimpleJpaRepository는 다음과 같이 선언되어 있다(필드 일부는 생략했다).

    @Repository
@Transactional(readOnly = true)
public class SimpleJpaRepository implements JpaRepositoryImplementation {

    private final JpaEntityInformation entityInformation;
    private final EntityManager entityManager;
    private final PersistenceProvider provider;
    private @Nullable CrudMethodMetadata metadata;
    // ...

    public SimpleJpaRepository(JpaEntityInformation entityInformation, EntityManager entityManager) { /* ... */ }
    // ...
}

    클래스 선언에서 읽을 수 있는 사실이 세 가지 있다. 첫째, 클래스 수준에 @Transactional(readOnly = true)가 붙어 있다. 메서드에 별도 애너테이션이 없으면 이 클래스 수준 설정이 적용되므로, 조회 메서드는 기본적으로 읽기 전용 트랜잭션 안에서 실행된다. 쓰기 메서드(save, delete, deleteById, saveAll, flush 등)에는 메서드마다 속성 없는 @Transactional이 다시 붙어 있어 클래스 설정을 덮어쓴다. 소스에서 확인하면 save, saveAndFlush, saveAll, saveAllAndFlush, flush, delete, deleteById, deleteAllById, deleteAllByIdInBatch, deleteAll, deleteAllInBatch, 그리고 Specification을 받는 delete에 메서드 수준 @Transactional이 있다.

    둘째, @Repository가 붙어 있다. 이 클래스가 데이터 접근 계층의 구성 요소라는 스테레오타입 표식이다. 다만 리포지토리 빈은 컴포넌트 스캔이 아니라 리포지토리 팩토리가 만들고, 예외 변환도 앞에서 본 것처럼 팩토리가 PersistenceExceptionTranslationInterceptor를 프록시에 직접 끼워 넣는 방식으로 이루어진다. 예외 변환 후처리기의 postProcess 메서드는 조건 없이 factory.addAdvice(interceptor) 한 줄이다.

    셋째, 생성자가 JpaEntityInformation과 EntityManager를 받는다. JpaEntityInformation은 도메인 타입에 대한 정보, 즉 식별자 속성, 버전 속성, 엔티티 이름을 JPA 메타모델에서 읽어 담아 둔 객체다. 뒤에서 볼 새 엔티티 판별이 바로 이 객체의 isNew()다. EntityManager는 진짜 하이버네이트 세션이 아니라 스프링이 만든 공유 엔티티 매니저 프록시다. 이 프록시는 메서드가 호출될 때마다 현재 스레드의 트랜잭션에 묶인 진짜 엔티티 매니저를 찾아 위임한다. 리포지토리 인터페이스 하나당 SimpleJpaRepository 객체는 하나만 만들어지고 모든 요청 스레드가 그것을 공유하는데도 영속성 컨텍스트가 섞이지 않는 이유가 이것이다. SimpleJpaRepository의 필드는 생성 후 바뀌지 않는 설정값뿐이고, 요청마다 달라지는 상태(영속성 컨텍스트, 호출된 메서드의 메타데이터)는 모두 스레드 로컬을 통해 찾는다.

    메서드별로 읽기: 조회, 존재 확인, 삭제

    SimpleJpaRepository의 메서드는 대부분 EntityManager 호출 한두 개로 번역된다. 이 번역을 알면 각 메서드가 영속성 컨텍스트와 어떻게 상호작용하는지, 몇 개의 SQL을 낼지 예측할 수 있다.

    findById(id)는 크루드 메타데이터가 없으면 entityManager.find(domainType, id)를, 있으면 메타데이터에서 꺼낸 락 모드와 힌트를 더해 find의 다른 오버로드를 부른다. find는 JPA 기본편에서 본 대로 먼저 영속성 컨텍스트의 1차 캐시를 보고, 없을 때만 SELECT를 낸다. 같은 트랜잭션 안에서 같은 식별자로 findById를 두 번 부르면 SQL은 한 번만 나가는 이유가 여기 있다. 4회차의 @Lock을 리포지토리 인터페이스에 다시 선언한 findById에 붙이면 동작하는 것도, 첫 번째 인터셉터가 올려 둔 메서드 정보를 이 지점에서 읽기 때문이다.

    getReferenceById(id)는 entityManager.getReference(getDomainClass(), id) 한 줄이다. 1차 캐시에 엔티티가 없으면 SQL 없이 프록시를 돌려주고, 프록시의 식별자가 아닌 필드를 처음 읽을 때 SELECT가 나간다. 연관관계를 걸 때 상대 엔티티의 식별자만 알면 될 때 쓰는 메서드다. 예전 이름인 getOne과 getById는 3.5.13에서 @Deprecated로 남아 있고 내부에서 getReferenceById를 그대로 호출한다.

    existsById(id)는 엔티티를 읽지 않는다. 엔티티 이름과 식별자 속성 이름으로 개수를 세는 형태의 JPQL을 만들어 실행하고, 결과로 존재 여부만 판단한다. 엔티티를 영속성 컨텍스트에 올리지 않으므로 존재 확인 뒤 엔티티가 필요하다면 결국 다시 조회해야 한다. 복합 키에서 키 속성 값의 타입이 파라미터 타입과 맞지 않으면 findById(id).isPresent()로 물러선다는 분기도 소스에 있다. count()는 미리 만들어 둔 카운트 JPQL을 실행한다.

    삭제 쪽은 조금 더 복잡하다. delete(entity)의 몸체를 그대로 옮기면 다음과 같다.

    @Override
@Transactional
public void delete(T entity) {
    Assert.notNull(entity, ENTITY_MUST_NOT_BE_NULL);

    if (entityInformation.isNew(entity)) {
        return;                                        // 새 엔티티는 지울 것이 없다
    }
    if (entityManager.contains(entity)) {
        entityManager.remove(entity);                  // 이미 관리 중이면 바로 삭제 예약
        return;
    }
    Class type = ProxyUtils.getUserClass(entity);
    T existing = (T) entityManager.find(type, entityInformation.getId(entity));
    if (existing != null) {
        entityManager.remove(entityManager.merge(entity));   // 준영속이면 병합 후 삭제
    }
}

    세 갈래가 있다. 판별 결과 새 엔티티라면 아무것도 하지 않는다. DB에 행이 있을 리 없다고 보는 것이다. 영속성 컨텍스트가 관리 중인 엔티티라면 remove로 삭제를 예약한다. 그 밖, 즉 다른 트랜잭션에서 읽어 와 준영속(detached) 상태인 엔티티라면 먼저 find로 DB에 있는지 확인하고, 있을 때만 merge로 관리 상태의 인스턴스를 얻어 remove한다. JPA의 remove는 관리 중인 엔티티만 받기 때문에 이런 우회가 필요하다. find가 이미 엔티티를 1차 캐시에 올렸으므로 이어지는 merge는 추가 SELECT 없이 1차 캐시의 인스턴스에 값을 복사한다. 여기서 delete도 isNew를 쓴다는 점을 기억해 두자. 판별이 틀리면 저장뿐 아니라 삭제도 엉뚱하게 동작한다.

    deleteById(id)는 3.5.13에서 findById(id).ifPresent(this::delete) 한 줄이다. 대상이 없으면 조용히 아무 일도 하지 않는다. 실험에서 존재하지 않는 식별자로 호출하자 SELECT 한 번 뒤에 예외 없이 끝났다. 이 동작은 버전에 따라 다르다. 2.7.18과 3.0.0, 3.0.1의 소스에서는 같은 메서드가 findById(id).orElseThrow(...)로 대상이 없으면 EmptyResultDataAccessException을 던졌고, 3.0.2의 소스부터 지금과 같은 형태다. 예전 버전 기준으로 작성된 코드가 이 예외를 잡아 "없는 데이터 삭제"를 처리하고 있었다면, 업그레이드 뒤 그 분기는 더 이상 실행되지 않는다.

    deleteAll()과 deleteAllInBatch()는 이름이 비슷하지만 전혀 다르다. deleteAll()은 findAll()로 전부 읽어 온 뒤 하나씩 delete를 부른다. 행이 N개면 SELECT 한 번과 DELETE N번이 나가고, 엔티티마다 영속성 컨텍스트를 거치므로 @PreRemove 같은 콜백과 연관관계의 영속성 전이도 동작한다. deleteAllInBatch()는 delete from 엔티티명 x 형태의 JPQL 한 줄을 executeUpdate()로 실행한다. SQL은 한 번이지만 영속성 컨텍스트를 거치지 않는 벌크 연산이므로, 4회차에서 본 벌크 수정과 같은 주의가 필요하다. 이미 1차 캐시에 올라와 있는 엔티티는 DB에서 사라진 뒤에도 메모리에 그대로 남는다.

    마지막으로 saveAll, deleteById, deleteAll이 내부에서 save, findById, delete를 부르는 방식을 보자. 이 호출들은 모두 this.save(...)처럼 같은 객체 안에서의 호출이므로 프록시를 거치지 않는다. 스프링 DB 2편에서 다룬 "프록시 내부 호출에는 AOP가 적용되지 않는다"는 규칙이 여기에도 적용된다. 그래도 문제가 없는 이유는 바깥 메서드(saveAll 등)에 이미 @Transactional이 붙어 있어 프록시 단계에서 트랜잭션이 시작되었기 때문이다. 내부의 save는 그 트랜잭션 안에서 실행된다. saveAll에 100개를 넘기면 트랜잭션은 하나, 영속성 컨텍스트도 하나다.

    findById 때와 달리 Creating new transaction 로그가 한 줄도 없다. 트랜잭션 없이 실행된 것이다. Spring Data JPA 참조 문서의 트랜잭션 장도 "선언된 쿼리 메서드(default 메서드 포함)에는 기본적으로 어떤 트랜잭션 설정도 적용되지 않는다"고 적고, 트랜잭션 안에서 실행하려면 리포지토리 인터페이스에 @Transactional을 붙이라고 안내한다. 인터페이스에 @Transactional(readOnly = true)를 붙이면 위 탐색의 마지막 단계에서 "메서드를 선언한 인터페이스"의 애너테이션으로 발견된다. @Modifying을 쓰는 수정 쿼리 메서드라면 그 메서드에 따로 @Transactional을 붙여 읽기 전용을 덮어쓴다.

    트랜잭션 없이 실행된 쿼리 메서드는 어떻게 동작했을까. 공유 엔티티 매니저 프록시는 트랜잭션에 묶인 엔티티 매니저를 찾지 못하면 그 호출을 위해 새 엔티티 매니저를 만들고, 쿼리 실행이 끝나면 닫는다. 그래서 쿼리는 실행되지만, 반환된 엔티티는 이미 닫힌 영속성 컨텍스트에서 나온 준영속 엔티티다. 지연 로딩 연관관계를 건드리면 초기화할 세션이 없다. 물론 실무에서는 대개 서비스 계층의 @Transactional 안에서 쿼리 메서드를 부르므로 이 차이가 드러나지 않는다. 그 경우 쿼리 메서드는 바깥 트랜잭션의 엔티티 매니저를 그대로 쓴다.

    바깥에 트랜잭션이 있을 때 리포지토리 메서드가 어떻게 동작하는지도 로그로 확인할 수 있다. 실험에서 TransactionTemplate으로 바깥 트랜잭션을 열고 그 안에서 items.save(...)를 호출했다.

    save의 @Transactional은 전파 속성 REQUIRED이므로, 프록시의 TransactionInterceptor는 스레드에 묶인 엔티티 매니저를 발견하고 "기존 트랜잭션에 참여한다"는 로그만 남긴다. 새 엔티티 매니저를 열지 않는다. 이 동작이 서비스 계층에서 여러 리포지토리 호출을 하나의 트랜잭션으로 묶는 기반이다. 반대로 서비스 메서드에 @Transactional이 없으면 리포지토리 호출 하나하나가 각자의 트랜잭션과 영속성 컨텍스트를 연다. 저장은 되니 겉으로는 잘 동작하는 것처럼 보이지만, 두 번째 호출이 실패해도 첫 번째 호출은 이미 커밋되어 있고, 첫 번째 호출이 돌려준 엔티티는 호출이 끝나는 순간 준영속이 되어 더티 체킹도 지연 로딩도 되지 않는다. 리포지토리의 기본 트랜잭션은 "단독 호출이 최소한 안전하게 동작하도록" 붙어 있는 것이지 업무 단위의 경계를 대신해 주지 않는다.

    @EnableJpaRepositories에는 enableDefaultTransactions 속성이 있고 기본값은 true다. 이것을 false로 바꾸면 위 탐색에서 SimpleJpaRepository 쪽 애너테이션을 보지 않게 되어, 인터페이스에 직접 붙인 @Transactional만 적용된다.

    readOnly = true가 실제로 바꾸는 것

    조회 메서드에 붙는 readOnly = true는 "읽기만 한다"는 선언이다. 그런데 이 선언을 받은 쪽이 실제로 무엇을 바꾸는지는 트랜잭션 매니저와 JPA 구현체의 몫이다. JpaTransactionManager는 트랜잭션을 시작할 때 JpaDialect.beginTransaction()을 호출하고, 하이버네이트를 쓸 때의 구현이 HibernateJpaDialect다. Spring Framework 6.2.19의 이 클래스가 읽기 전용 트랜잭션에서 하는 일은 세 가지다.

    1. 플러시 모드를 MANUAL로 바꾼다. prepareFlushMode(session, readOnly)가 읽기 전용이면 세션의 하이버네이트 플러시 모드를 FlushMode.MANUAL로 설정한다. MANUAL에서는 커밋 직전에도 자동 플러시가 일어나지 않는다. 엔티티를 고쳐도 UPDATE가 나갈 기회 자체가 없다.
    2. 세션의 기본 읽기 전용을 켠다. 트랜잭션 정의가 이 트랜잭션을 위해 새로 만든 엔티티 매니저(로컬 자원)라고 알려 주면 session.setDefaultReadOnly(true)를 호출한다. 하이버네이트 Session의 Javadoc은 이 설정에 대해 "읽기 전용 엔티티는 더티 체킹을 하지 않고 영속 상태의 스냅샷도 유지하지 않는다"고 설명한다. 1차 캐시에 올라온 엔티티마다 보관하던 비교용 스냅샷이 없어지므로 메모리도 덜 쓴다.
    3. JDBC 커넥션에 읽기 전용 힌트를 준다. 커넥션 준비 플래그가 켜져 있고(기본값) 하이버네이트의 커넥션 해제 모드가 세션 종료 시점(ON_CLOSE)이면, 물리 커넥션을 꺼내 DataSourceUtils.prepareConnectionForTransaction()에 넘기고, 이 메서드가 Connection.setReadOnly(true)를 호출한다. 스프링의 HibernateJpaVendorAdapter는 커넥션 준비 플래그가 켜져 있으면 하이버네이트의 커넥션 처리 모드를 DELAYED_ACQUISITION_AND_HOLD로 지정하므로, 일반적인 구성에서는 이 조건이 맞는다.

    플러시 모드는 MANUAL, 기본 읽기 전용은 true로 바뀌었고, 관리 중인 엔티티의 이름을 바꿨는데도 커밋 때 UPDATE가 나가지 않았다. 리포지토리의 findById가 읽기 전용 트랜잭션으로 실행된다는 것은 이 세 가지가 모두 적용된다는 뜻이다. 다만 이 효과는 "그 트랜잭션이 새로 시작될 때"에만 생긴다. 서비스 계층의 읽기-쓰기 트랜잭션 안에서 findById를 호출하면 리포지토리는 기존 트랜잭션에 참여할 뿐이므로, 읽기 전용 설정은 적용되지 않고 바깥 트랜잭션의 설정을 따른다.

    세 번째 항목의 Connection.setReadOnly(true)는 JDBC API 문서에 따르면 데이터베이스 최적화를 위해 드라이버에 주는 힌트(hint)다. 이 힌트로 실제로 무엇이 바뀌는지는 드라이버와 DB마다 다르다. 따라서 "readOnly 트랜잭션이면 DB가 쓰기를 거부한다"고 일반화할 수는 없다. 확실하게 말할 수 있는 것은 하이버네이트 수준의 효과, 즉 플러시가 일어나지 않고 더티 체킹을 하지 않는다는 점이다.

    save(): persist와 merge의 갈림길

    이제 두 번째 수업 주제인 "새로운 엔티티를 구별하는 방법"으로 넘어간다. 출발점은 save()의 몸체다. 3.5.13 소스에서 그대로 옮기면 다음 몇 줄이 전부다.

    @Override
@Transactional
public  S save(S entity) {

    Assert.notNull(entity, ENTITY_MUST_NOT_BE_NULL);

    if (entityInformation.isNew(entity)) {
        entityManager.persist(entity);
        return entity;
    } else {
        return entityManager.merge(entity);
    }
}

    이름은 하나지만 하는 일은 두 가지다. 새 엔티티라고 판단하면 persist를 호출하고 넘겨받은 객체를 그대로 돌려준다. 아니라고 판단하면 merge를 호출하고 merge가 돌려준 객체를 돌려준다. 두 연산의 의미는 Jakarta Persistence 명세가 정한다. 이 차이를 정확히 알아야 판별이 틀렸을 때의 증상을 이해할 수 있다.

    persist(X)는 새 엔티티 X를 관리 상태로 만든다. 넘긴 객체 X 자체가 영속성 컨텍스트에 등록되고, 1차 캐시의 키는 X의 식별자, 값은 X에 대한 참조다. 식별자 생성 전략이 시퀀스라면 이 시점에 시퀀스에서 값을 가져와 X의 식별자 필드에 넣는다. INSERT는 쓰기 지연 저장소에 쌓였다가 플러시 때 실행된다. 명세는 X가 준영속 객체일 때 persist를 부르면 그 자리에서 또는 플러시나 커밋 시점에 예외가 날 수 있다고 정한다. 즉 persist는 "DB에 아직 없는 객체"를 위한 연산이다.

    merge(X)는 X의 상태를 관리 중인 인스턴스로 복사하는 연산이다. 명세의 규칙을 정리하면, X가 준영속이면 같은 식별자의 관리 인스턴스 X'를 찾거나 만들고 X의 상태를 X'에 복사한 뒤 X'를 반환한다. X가 새 엔티티면 새로운 관리 인스턴스 X'를 만들어 상태를 복사한다. X가 이미 관리 중이면 merge 연산 자체는 X를 무시한다(연관관계의 cascade 설정에 따라 전이만 된다). 어느 경우든 반환되는 것은 관리 인스턴스이고, 넘긴 X가 준영속이나 새 객체였다면 X는 호출 뒤에도 관리 상태가 되지 않는다. 하이버네이트는 X'를 찾기 위해 먼저 1차 캐시를 보고, 없으면 DB에서 SELECT로 읽어 온다. DB에도 없으면 새로 INSERT할 대상으로 본다(단, 뒤에서 볼 하이버네이트 6.6의 예외 규칙이 있다).

    실험으로 확인하자. 식별자를 생성하는 Member와 식별자를 직접 넣는 Item을 각각 새 객체로 만들어 save하고, 반환값이 넘긴 객체와 같은 객체인지 ==로 비교했다.

Item은 식별자 "A-1"이 이미 채워져 있어 새 엔티티가 아니라고 판별되었고 merge가 호출됐다. 하이버네이트는 1차 캐시에 Item#A-1이 없으니 DB에서 SELECT로 찾아보고, 행이 없으니 새 관리 인스턴스를 만들어 상태를 복사한 뒤 INSERT를 예약했다. 반환값은 그 새 관리 인스턴스이므로 넘긴 객체와 다르다. INSERT에 들어간 값은 merge 시점에 y로 복사된 "original"이다. 반대로 Member처럼 persist로 저장된 엔티티는 넘긴 객체가 곧 관리 객체이므로 같은 코드가 잘 동작한다. 엔티티마다 다르게 동작하는 코드는 리뷰에서 잡아내기 어렵다. 그래서 "save()의 반환값을 받아서 그것을 계속 쓴다"를 습관으로 삼는 것이 안전하다. 반환값을 쓰면 persist든 merge든 항상 관리 인스턴스를 손에 쥐게 된다.

    일상에서 가져온 비유원본 장부와 신청서 사본

    persist는 내가 들고 간 서류철을 그대로 사무실 캐비닛에 꽂는 일이다. 이후 그 서류철에 쓰는 내용은 캐비닛 속 서류에 바로 적힌다. merge는 창구에 신청서를 내면 직원이 장부(없으면 새 장부)를 꺼내 내 신청서의 내용을 옮겨 적고, 신청서는 나에게 돌려주는 일이다. 돌려받은 신청서에 무엇을 더 쓰든 장부는 바뀌지 않는다. 장부에 반영하려면 직원이 건네준 장부 페이지(반환값)에 써야 한다. 비유가 깨지는 지점도 있다. 현실의 직원은 장부를 찾으러 창고에 가는 비용을 말해 주지 않지만, merge는 1차 캐시에 없으면 반드시 SELECT라는 비용을 치른다.

    새 엔티티 판별 규칙을 소스로 읽기

    save()와 delete()의 운명을 가르는 entityInformation.isNew(entity)를 읽어 보자. 먼저 entityInformation이 어떤 클래스의 객체인지가 리포지토리 생성 시점에 정해진다. JpaEntityInformationSupport.getEntityInformation()은 도메인 클래스가 Persistable을 구현했으면 JpaPersistableEntityInformation을, 아니면 JpaMetamodelEntityInformation을 만든다.

    // JpaEntityInformationSupport (3.5.13)
public static  JpaEntityInformation getEntityInformation(Class domainClass, EntityManager em) {
    // ... (인자 null 검사 생략)
    Metamodel metamodel = em.getMetamodel();
    PersistenceUnitUtil persistenceUnitUtil = em.getEntityManagerFactory().getPersistenceUnitUtil();

    if (Persistable.class.isAssignableFrom(domainClass)) {
        return new JpaPersistableEntityInformation(domainClass, metamodel, persistenceUnitUtil);
    } else {
        return new JpaMetamodelEntityInformation(domainClass, metamodel, persistenceUnitUtil);
    }
}

    JpaPersistableEntityInformation의 isNew는 return entity.isNew(); 한 줄이다. 판단을 엔티티에게 완전히 맡긴다. JpaMetamodelEntityInformation의 isNew는 버전 속성을 먼저 본다.

    // JpaMetamodelEntityInformation (3.5.13)
@Override
public boolean isNew(T entity) {

    if (versionAttribute.isEmpty()
            || versionAttribute.map(Attribute::getJavaType).map(Class::isPrimitive).orElse(false)) {
        return super.isNew(entity);
    }

    BeanWrapper wrapper = new DirectFieldAccessFallbackBeanWrapper(entity);

    return versionAttribute.map(it -> wrapper.getPropertyValue(it.getName()) == null).orElse(true);
}

    버전 속성이 없거나, 있더라도 자바 타입이 원시 타입(long, int 등)이면 부모 클래스의 식별자 기반 판별로 넘긴다. 버전 속성이 래퍼 타입(Long, Integer 등)이면 그 값이 null인지로 판별한다. 버전 값은 메타모델이 알려 준 속성 이름으로 DirectFieldAccessFallbackBeanWrapper를 통해 읽는데, 이 래퍼는 게터가 없으면 필드에 직접 접근한다. 원시 타입 버전을 판별에 쓰지 않는 이유는 참조 문서에 적혀 있다. JPA는 0을 엔티티의 첫 번째 저장 버전으로 보기 때문에, 원시 타입 버전의 기본값 0으로는 "아직 저장 안 됨"과 "한 번 저장됨"을 구별할 수 없다.

    // AbstractEntityInformation (Spring Data Commons 3.5.13)
@Override
public boolean isNew(T entity) {

    ID id = getId(entity);
    Class idType = getIdType();

    if (!idType.isPrimitive()) {
        return id == null;
    }

    if (id instanceof Number n) {
        return n.longValue() == 0L;
    }

    throw new IllegalArgumentException(String.format("Unsupported primitive id type %s", idType));
}

    식별자 기반 판별은 식별자 타입이 참조 타입이면 null인지, 원시 숫자 타입이면 0인지 본다. 원시 타입인데 숫자가 아니면(예를 들어 char) 예외를 던진다. 식별자 값을 읽는 getId도 한 번 볼 만하다. JpaMetamodelEntityInformation.getId는 먼저 넘어온 객체가 JPA 구현체의 프록시인지 확인해 프록시라면 구현체의 방식으로 식별자를 꺼내고, 단순 식별자라면 PersistenceUnitUtil.getIdentifier(entity)로 읽는다. 지연 로딩 프록시를 save나 delete에 넘겨도 식별자를 읽으려고 프록시를 초기화하지 않는 이유가 이것이다. 복합 키라면 키 속성들을 하나씩 읽어 하나라도 값이 있는지 본다.

    정리하면 판별은 다음 순서로 진행된다.

    이 규칙을 보면 기본 판별이 어떤 엔티티를 전제로 설계되었는지 드러난다. 식별자를 DB나 JPA 구현체가 생성하는 엔티티다. 그런 엔티티는 저장 전에는 식별자가 반드시 null이고 저장 뒤에는 반드시 값이 있으므로, 식별자만 보고도 판별이 정확하다. 문제는 이 전제가 깨질 때, 즉 애플리케이션이 식별자를 직접 넣을 때 생긴다.

    식별자를 직접 할당하면 생기는 일

    주문 번호, 상품 코드, 외부 시스템에서 받은 키처럼 식별자를 애플리케이션이 정하는 경우는 흔하다. 이런 엔티티는 생성자에서 이미 식별자가 채워지므로 기본 판별로는 항상 "새것이 아님"이 된다. 참조 문서도 버전 속성 없이 직접 할당 식별자를 쓰는 엔티티에는 기본 판별이 쓸모없다고 명시한다. 그 결과로 생기는 증상은 세 가지다.

    증상 1: 저장할 때마다 SELECT가 먼저 나간다

    앞의 B 시나리오가 그 예다. 새 Item을 저장했을 뿐인데 merge가 호출되어 SELECT 후 INSERT가 나갔다. 한 건이면 왕복 한 번이 늘어나는 정도지만, saveAll로 천 건을 넣으면 SELECT 천 번이 INSERT 앞에 붙는다. 영속성 컨텍스트가 비어 있으니 SELECT는 매번 DB까지 간다. 대량 적재 작업이 예상보다 훨씬 느릴 때 SQL 로그에서 이 패턴을 찾아보면 원인이 바로 보인다.

    증상 2: 새로 만들려던 행이 기존 행을 조용히 덮어쓴다

    이 증상은 성능보다 훨씬 위험하다. 실험에서 이미 "A-1" 행이 있는 상태로, 같은 식별자의 새 객체를 만들어 save했다.

    Item it2 = new Item("A-1", "pencil");
Item savedIt2 = items.save(it2);
System.out.println("same instance? " + (savedIt2 == it2));
    == E. same Item id again (existing row)
Hibernate: select i1_0.id,i1_0.name from Item i1_0 where i1_0.id=?
Hibernate: update Item set name=? where id=?
same instance? false

    기본 키 중복 오류가 나지 않았다. merge는 SELECT로 기존 행을 읽어 관리 인스턴스를 만들고, 넘긴 객체의 상태(name = "pencil")를 그 위에 복사했다. 플러시 때 더티 체킹이 스냅샷과 비교해 변경을 발견하고 UPDATE를 냈다. 코드를 쓴 사람의 의도가 "새 상품 등록"이었다면, 같은 코드가 이미 있을 때 기존 상품을 덮어쓰는 일이 오류 없이 일어난 것이다. 게다가 merge는 넘긴 객체의 모든 필드를 복사하므로, 넘긴 객체에서 비어 있던 필드는 기존 행의 값을 null로 지운다. 기본 키 제약이라는 DB의 안전장치가 있는데도 그 장치가 작동할 기회가 없었다는 점이 핵심이다. INSERT가 아니라 UPDATE가 나갔기 때문이다.

    증상 3: 생성 전략이 있는 엔티티에 식별자를 손으로 넣으면 예외가 난다

    세 번째는 반대 방향의 실수다. @GeneratedValue가 붙은 Member에 식별자를 직접 넣고 저장해 보았다. 테스트 데이터를 만들거나 다른 시스템에서 옮겨 온 값을 그대로 쓰려 할 때 생기는 상황이다.

    Member ghost = new Member("ghost");
ghost.setId(999L);              // DB에 없는 식별자를 직접 넣는다
Member r = members.save(ghost); // isNew: id != null 이므로 false -> merge

    식별자가 채워져 있으니 판별은 "새것 아님"이고 merge가 호출되었다. 하이버네이트는 SELECT로 행을 찾았지만 없었고, 이번에는 INSERT 대신 StaleObjectStateException을 던졌다. 이 예외는 트랜잭션 인터셉터를 지나며 롤백을 일으키고(로그의 Initiating transaction rollback), 그 바깥의 예외 변환을 거쳐 스프링의 ObjectOptimisticLockingFailureException이 되어 호출자에게 도착했다. 인터셉터 순서에서 트랜잭션이 예외 변환보다 안쪽에 있다는 것이 로그 순서로 드러난다.

    이 동작은 하이버네이트 6.6에서 바뀐 것이다. 하이버네이트 6.6 마이그레이션 가이드의 "Merge versioned entity when row is deleted" 항목은, 이전에는 일치하는 행이 없는 준영속 엔티티를 병합하면 INSERT가 나갔지만 이것이 낙관적 락의 규칙을 어기는 동작이었으므로, 이제는 엔티티가 확실히 준영속이라고 판단할 수 있는데 일치하는 행이 없으면 OptimisticLockException을 던진다고 설명한다. 그 판단이 가능하려면 엔티티에 생성되는 @Id나 원시 타입이 아닌 @Version이 있어야 하고, 둘 다 없는 엔티티는 새 인스턴스와 삭제된 준영속 인스턴스를 구별할 수 없으므로 동작이 이전과 같다고 덧붙인다. 위 실험의 Member는 생성되는 식별자를 가졌으므로 예외가 났고, B 시나리오의 Item은 둘 다 없으므로 예전처럼 INSERT가 나갔다. 6.5 이하에서 6.6으로 올리면서 "식별자를 손으로 넣은 저장" 코드가 갑자기 낙관적 락 예외를 내기 시작했다면 이 변경이 원인이다. 하이버네이트 입장에서 "생성 전략이 있는데 식별자가 이미 있다"는 것은 이미 저장된 적이 있다는 뜻이다. 그런데 행이 없으니 그사이 누군가 지운 것으로 본다. 예외 메시지 끝의 "unsaved-value mapping was incorrect"라는 문구가 바로 이 가능성, 즉 새 객체를 기존 객체로 잘못 판단했을 가능성을 가리킨다.

    판별을 바로잡는 방법: Persistable, @Version, 그 밖

    해법은 판별 규칙의 순서표를 거꾸로 읽으면 나온다. 식별자만으로 판단할 수 없다면, 그보다 앞서 검사되는 정보를 엔티티에 주면 된다.

    Persistable 구현

    참조 문서가 직접 할당 식별자 엔티티에 권하는 흔한 패턴은, 영속화되지 않는 플래그를 두고 JPA 생명주기 콜백으로 그 플래그를 뒤집는 것이다. 실험의 Book이 그 패턴이다.

    @Entity
public class Book implements Persistable {
    @Id String isbn;
    String title;
    @Transient private boolean isNew = true;     // 컬럼이 아니다. 새로 만든 객체는 true

    protected Book() {}
    public Book(String isbn, String title) { this.isbn = isbn; this.title = title; }

    @Override public String getId() { return isbn; }
    @Override public boolean isNew() { return isNew; }

    @PostPersist @PostLoad
    void markNotNew() { this.isNew = false; }    // 저장된 뒤, 또는 DB에서 읽힌 뒤에는 false
}
    == D. Persistable
Hibernate: insert into Book (title,isbn) values (?,?)
same instance? true, isNew after save=false

    SELECT 없이 INSERT 하나만 나갔고, 반환값은 넘긴 객체 그대로다. persist가 호출되었다는 증거다. 이 패턴에서 각 부분의 역할을 짚어 보자. 필드 초기값 true는 new로 만든 객체가 새것이라는 뜻이다. 하이버네이트가 DB에서 엔티티를 읽을 때도 기본 생성자를 호출하므로 이 초기값이 일단 true로 들어가지만, 로딩이 끝나면 @PostLoad가 호출되어 false로 바뀐다. 따라서 조회한 엔티티를 save나 delete에 넘기면 기존 엔티티로 올바르게 판별된다. @PostPersist는 INSERT가 실행된 뒤(쓰기 지연 때문에 대개 플러시 시점) 호출되어 플래그를 내린다. 실험 출력의 isNew after save=false는 save의 트랜잭션이 커밋된 뒤 찍은 값이다. 이 콜백이 없으면 저장이 끝난 객체가 계속 새것으로 판별되어, 다음 트랜잭션에서 그 객체를 delete에 넘기면 아무 일도 일어나지 않고 save에 넘기면 준영속 객체에 persist를 시도하게 된다. @Transient는 이 필드가 컬럼으로 매핑되지 않게 한다. 참조 문서는 같은 패턴을 @MappedSuperclass 기반 추상 클래스로 만들어 여러 엔티티가 상속하게 하는 예를 보여 준다.

    이 방식의 부수 효과도 알아 두자. 같은 ISBN의 행이 이미 있는데 new Book(...)으로 만든 객체를 저장하면 이제 persist가 호출되고, INSERT가 DB에 도달하면 기본 키 제약에 걸려 실패한다. 증상 2처럼 조용히 덮어쓰는 대신 오류가 나는 것이다. 대개는 이쪽이 원하는 동작이다. 기존 데이터를 수정하려는 코드라면 처음부터 조회해서 관리 엔티티를 고치는 방식으로 써야 한다.

    스프링 데이터 JPA는 AbstractPersistable이라는 기반 클래스도 제공하지만, 3.5.13 소스에서 이 클래스는 식별자에 @Id @GeneratedValue를 붙이고 isNew()를 null == getId()로 구현한다. 생성 전략을 쓰는 엔티티용이므로 직접 할당 식별자 문제의 해법은 아니다.

    래퍼 타입 @Version

    두 번째 방법은 판별 순서표의 2번을 이용하는 것이다. 래퍼 타입 버전 필드를 두면 식별자를 보기 전에 버전 값으로 판별한다.

    @Entity
public class Ticket {
    @Id String id;
    @Version Long version;        // 래퍼 타입. 새 객체에서는 null
    protected Ticket() {}
    public Ticket(String id) { this.id = id; }
}
    == C. assigned id + @Version Long
Hibernate: insert into Ticket (version,id) values (?,?)
same instance? true

    식별자가 채워져 있는데도 버전이 null이라 새 엔티티로 판별되어 persist가 호출되었다. 하이버네이트는 INSERT할 때 버전의 초기값을 채우고, 이후 이 엔티티를 조회하면 버전에는 항상 값이 있으므로 기존 엔티티로 판별된다. 이 방법은 낙관적 락이라는 덤을 준다. 동시에 두 트랜잭션이 같은 행을 고치면 나중에 커밋하는 쪽이 버전 불일치로 실패한다. 반대로 버전 필드를 원시 타입 long으로 선언하면 판별 순서의 2번을 건너뛰고 식별자 판별로 넘어가므로, 직접 할당 식별자 문제는 그대로 남는다. 타입 하나 차이로 동작이 갈리는 지점이니 주의한다.

    그 밖의 방법

    5회차에서 다룬 Auditing을 쓰고 있다면, 등록 시각 필드가 비어 있는지로 Persistable.isNew()를 구현하는 방법도 쓸 수 있다. 등록 시각은 엔티티가 처음 persist될 때 채워지므로, 판별 시점에 비어 있다면 아직 저장된 적이 없는 객체다. 참조 문서는 마지막 수단으로 JpaRepositoryFactory를 상속해 getEntityInformation(...)을 재정의하는 방법도 소개하지만, 그런 경우는 드물다고 적고 있다. 그리고 가장 단순한 해법을 잊지 말자. 식별자 생성 전략이 있는 엔티티라면 식별자를 손으로 넣지 않는 것이다.

    흔한 오해와 함정

    "엔티티를 고쳤으면 save()를 불러야 반영된다." 같은 트랜잭션 안에서 조회한 관리 엔티티라면 더티 체킹이 플러시 때 UPDATE를 만든다. 이때 save()를 부르면 판별 결과는 "새것 아님"이고 merge가 호출되는데, 명세상 관리 중인 엔티티에 대한 merge는 무시되므로 추가 SQL 없이 같은 객체가 돌아온다. 그래서 해롭지는 않다. 참조 문서도 트랜잭션 예제에서 이 save 호출이 JPA 관점에서 꼭 필요하지는 않지만 리포지토리 추상화와의 일관성을 위해 두라고 적는다. 문제는 준영속 엔티티(이전 트랜잭션에서 읽어 온 엔티티나, 요청 데이터로 새로 만든 객체)를 save할 때다. 그때는 진짜 merge가 일어나 SELECT와 전체 필드 덮어쓰기가 따라온다.

    "save()는 넘긴 객체를 저장하고 그 객체를 돌려준다." persist 경로에서만 그렇다. merge 경로에서는 다른 객체가 돌아오고, 넘긴 객체는 관리되지 않는다. 앞에서 넘긴 객체 x를 고친 실험처럼 반환값을 버리면 이후 변경이 사라진다.

    "리포지토리 조회 메서드는 모두 읽기 전용 트랜잭션으로 실행된다." SimpleJpaRepository에 구현이 있는 메서드(findById, findAll, count 등)만 그렇다. 인터페이스에 선언한 쿼리 메서드는 아무 트랜잭션 설정도 받지 않는다. 필요하면 리포지토리 인터페이스에 @Transactional(readOnly = true)를 붙인다.

    "readOnly = true면 쓰기가 원천 차단된다." 하이버네이트 수준에서 플러시가 일어나지 않고 더티 체킹을 하지 않는 것은 확실하다. 그러나 JDBC 커넥션에 전달되는 것은 힌트이고, DB가 실제로 쓰기를 거부하는지는 드라이버와 DB에 달려 있다. 또 읽기 전용 설정은 그 트랜잭션이 새로 시작될 때만 적용되므로, 읽기-쓰기 트랜잭션에 참여한 findById에는 효과가 없다.

    "기본 키를 직접 넣으면 중복될 때 DB가 막아 준다." 기본 판별을 쓰면 중복 키 저장은 INSERT가 아니라 UPDATE가 되어 DB 제약이 작동하지 않는다. 증상 2가 그것이다. Persistable이나 래퍼 타입 버전으로 판별을 바로잡아야 기본 키 제약이 다시 안전장치 역할을 한다.

    "deleteById는 대상이 없으면 예외를 던진다." 2.7.18과 3.0.0의 소스에서는 그랬지만 3.5.13에서는 조용히 무시한다. 버전을 올릴 때 예외에 기대던 코드를 점검해야 한다.

    다른 주제와의 연결

    이 회차에서 본 구조, 즉 프록시에 인터셉터를 순서대로 끼우고 마지막에 실제 구현 객체를 부르는 구조는 스프링 AOP의 ProxyFactory가 만드는 프록시의 표준 형태다. 프록시를 JDK 방식으로 만드느냐 CGLIB 방식으로 만드느냐는 그다음 문제다. 스프링 DB 1, 2편의 트랜잭션 AOP도 이 구조 위에서 동작했고, 로드맵 뒤쪽의 스프링 핵심 원리 고급편 권은 이 프록시 팩토리를 정면으로 다룬다. 리포지토리 프록시를 Advised로 캐스팅해 인터셉터 목록을 찍어 보는 방법은 다른 스프링 프록시를 조사할 때도 그대로 쓸 수 있다.

    새 엔티티 판별과 merge의 동작은 웹 계층과 만나는 지점에서 특히 중요하다. 요청 데이터를 엔티티 객체로 바로 받아 save하는 코드는, 식별자가 있으면 merge가 되어 요청에 없던 필드를 null로 덮어쓴다. JPA 활용 1권에서 변경 감지와 병합을 비교하며 확인한 원칙, 곧 변경은 조회한 관리 엔티티를 고치는 방식으로 한다는 원칙이 리포지토리 수준에서도 같은 이유로 성립한다.

    이 권의 다음 회차인 7회차는 SimpleJpaRepository가 함께 구현하는 나머지 기능들, 곧 Specifications, Query By Example, Projections, 네이티브 쿼리를 다룬다. 이 회차에서 본 프록시와 인터셉터 구조, 그리고 쿼리 메서드가 다섯 번째 인터셉터에서 처리된다는 사실을 알고 있으면 그 기능들이 어디서 실행되는지도 자연스럽게 따라갈 수 있다.
    리포지토리 프록시
    리포지토리 빈은 RepositoryFactorySupport.getRepository()가 ProxyFactory로 만든 JDK 동적 프록시이고, 타깃은 SimpleJpaRepository다.
    인터셉터 순서
    메서드 메타데이터 기록, 예외 변환, 트랜잭션, default 메서드 실행, 쿼리 메서드 실행, 구현 조각 위임 순으로 바깥부터 놓인다. 쿼리 메서드는 다섯 번째에서 끝난다.
    SimpleJpaRepository의 트랜잭션
    클래스에 @Transactional(readOnly = true), 쓰기 메서드에 속성 없는 @Transactional이 붙어 있다. 인터페이스에 선언한 쿼리 메서드는 아무 트랜잭션 설정도 받지 않는다.
    readOnly의 효과
    하이버네이트에서는 플러시 모드 MANUAL, 세션 기본 읽기 전용(더티 체킹과 스냅샷 없음), 조건이 맞으면 JDBC setReadOnly(true) 힌트가 적용된다. 새로 시작한 트랜잭션에만 해당한다.
    save()
    isNew가 참이면 persist 후 넘긴 객체를, 거짓이면 merge의 반환값(관리 인스턴스)을 돌려준다.
    새 엔티티 판별 순서
    Persistable이면 isNew(), 래퍼 타입 버전이 있으면 버전 null 여부, 그 외에는 식별자가 null(참조 타입) 또는 0(원시 숫자 타입)인지로 판단한다.
    직접 할당 식별자의 증상
    저장마다 SELECT가 붙고, 기존 행이 있으면 오류 없이 UPDATE로 덮어쓴다.
    하이버네이트 6.6의 merge
    생성 식별자나 래퍼 타입 버전이 있는 준영속 엔티티를 병합할 때 행이 없으면 INSERT 대신 낙관적 락 예외를 던진다.

    대량 적재 배치가 느리다는 보고를 받았을 때 가장 먼저 볼 것은 SQL 로그에서 INSERT 앞에 같은 키의 SELECT가 붙어 있는지다. 붙어 있다면 직접 할당 식별자 엔티티가 merge 경로를 타고 있다는 뜻이고, Persistable이나 래퍼 타입 @Version으로 판별을 바로잡으면 SELECT가 사라진다. 다만 판별을 바로잡은 뒤에는 중복 키가 UPDATE가 아니라 제약 위반 오류로 바뀌므로, 재실행 가능한 배치(같은 데이터를 다시 넣을 수 있는 작업)였다면 "있으면 수정, 없으면 추가"를 명시적으로 처리하는 코드가 따로 필요해진다. 어느 쪽이 맞는지는 업무 규칙이 정한다.

    하이버네이트 버전을 6.6 이상으로 올린 뒤 ObjectOptimisticLockingFailureException이 갑자기 늘었다면, 동시성 문제가 생겼다고 단정하기 전에 생성 식별자를 가진 엔티티에 식별자를 손으로 넣어 save하는 코드가 있는지 찾아본다. 테스트 픽스처나 데이터 이관 코드에 흔하다. 예외 메시지의 "unsaved-value mapping was incorrect"가 그 단서다.

    서비스 계층에 @Transactional을 붙일지 판단할 때는 리포지토리의 기본 트랜잭션이 "호출 하나"의 범위라는 점을 기준으로 삼는다. 두 개 이상의 리포지토리 호출이 함께 성공하거나 함께 실패해야 하거나, 조회한 엔티티를 고쳐서 더티 체킹으로 반영하려 한다면 서비스 메서드에 트랜잭션이 있어야 한다. 조회 위주의 서비스라면 readOnly = true로 시작해 플러시와 스냅샷 비용을 줄이고, 쿼리 메서드만 쓰는 리포지토리에도 트랜잭션이 필요하다면 인터페이스 수준에 붙인다.
  • 다음 네 엔티티를 각각 new로 만들어 식별자 필드에 값을 넣지 않은 채(단, (b)와 (d)는 생성자에서 식별자를 넣는다) save했을 때 persist와 merge 중 무엇이 호출되는지 판별 순서에 따라 답하라. (a) @Id @GeneratedValue long id (b) @Id String code와 @Version long version (c) @Id @GeneratedValue Long id와 @Version Integer version (d) @Id String code를 가지고 Persistable을 구현하며 isNew()가 getId() == null을 반환
  • 트랜잭션이 없는 서비스 메서드에서 Item item = itemRepository.findById("A-1").orElseThrow(); item.name = "new";만 실행했다. UPDATE가 나가는가? 각 호출이 어떤 트랜잭션과 영속성 컨텍스트에서 실행되는지 근거로 설명하라.
  • @Transactional 서비스 메서드 안에서 Order o = new Order("O-1"); orderRepository.save(o); o.setStatus(PAID);를 실행했더니 상태가 DB에 반영되지 않았다. Order는 직접 할당 식별자만 가지고 버전 필드는 없다. 원인과 두 가지 수정 방법을 말하라.
  • SimpleJpaRepository.save 안에서 예외가 발생했다. 트랜잭션 롤백과 예외 변환 중 무엇이 먼저 일어나는가? 프록시의 인터셉터 순서로 설명하라.
  • 인터페이스에 List findByName(String name)만 선언하고, 트랜잭션 없는 컨트롤러에서 이 메서드로 받은 회원의 지연 로딩 연관관계(팀)를 읽었다. OSIV가 꺼져 있다면 무슨 일이 일어나는가? 그리고 리포지토리 인터페이스에 @Transactional(readOnly = true)를 붙이면 해결되는가?

    1번. (a)는 Persistable이 아니고 버전 필드가 없으므로 식별자 판별로 간다. 식별자 타입이 원시 long이고 기본값이 0이므로 새것, persist다. (b)는 버전 필드가 원시 타입이라 판별 2번을 건너뛰고 식별자 판별로 간다. 생성자에서 넣은 code가 null이 아니므로 새것이 아니고 merge가 호출된다. 그래서 SELECT 후 INSERT가 나간다. (c)는 래퍼 타입 버전이 있으므로 버전 값으로 판별한다. 새 객체의 버전은 null이므로 persist다. (d)는 Persistable이므로 엔티티의 isNew()를 따른다. 생성자에서 code를 넣었으니 getId() == null은 거짓이고 merge가 호출된다. Persistable을 구현했다고 해서 저절로 해결되지 않는다. isNew()의 구현이 직접 할당 식별자의 사정을 반영해야 한다.

    2번. UPDATE는 나가지 않는다. 서비스에 트랜잭션이 없으므로 findById는 프록시의 트랜잭션 인터셉터가 연 읽기 전용 트랜잭션에서 실행되고, 메서드가 반환되는 순간 커밋되고 엔티티 매니저가 닫힌다. 반환된 item은 준영속이다. 이후 item.name을 바꿔도 감시하는 영속성 컨텍스트가 없다. 설령 같은 영속성 컨텍스트였더라도 그 트랜잭션은 읽기 전용이라 플러시 모드가 MANUAL이었다. 서비스 메서드에 @Transactional을 붙이면 findById는 그 트랜잭션에 참여하고, 서비스 메서드가 끝날 때 플러시에서 더티 체킹이 UPDATE를 만든다.

    3번. 식별자가 채워져 있고 버전이 없으므로 save는 merge를 호출했다. merge는 새 관리 인스턴스를 만들어 o의 상태를 복사하고 그것을 반환한다. o는 관리 대상이 아니므로 o.setStatus(PAID)는 플러시에 잡히지 않는다. 수정 방법은 (1) Order saved = orderRepository.save(o); saved.setStatus(PAID);처럼 반환값을 쓰는 것, (2) Order가 Persistable(일시적 플래그와 @PostPersist, @PostLoad)을 구현하거나 래퍼 타입 @Version을 갖게 해 persist 경로를 타게 하는 것이다. (2)를 적용하면 SELECT도 사라지고 o 자체가 관리 객체가 된다.

    4번. 롤백이 먼저다. 인터셉터는 바깥부터 메타데이터 기록, 예외 변환, 트랜잭션 순으로 놓여 있으므로, 안쪽에서 올라온 예외는 먼저 TransactionInterceptor를 지난다. 여기서 롤백 규칙에 따라 트랜잭션이 롤백되고 예외가 다시 던져진다. 그다음 바깥의 PersistenceExceptionTranslationInterceptor가 그 예외를 스프링의 DataAccessException 계층으로 바꾼다. 이 회차 실험에서 Initiating transaction rollback 로그가 찍힌 뒤에 ObjectOptimisticLockingFailureException이 호출자에게 도착한 것이 그 순서다.

    5번. findByName은 쿼리 메서드라 아무 트랜잭션 설정도 받지 않는다. 공유 엔티티 매니저 프록시는 호출을 위해 임시 엔티티 매니저를 열어 쿼리를 실행하고 닫으므로, 반환된 회원들은 준영속이다. 팀 프록시를 초기화할 세션이 없어 LazyInitializationException이 난다. 인터페이스에 @Transactional(readOnly = true)를 붙이면 쿼리 메서드가 읽기 전용 트랜잭션 안에서 실행되지만, 그 트랜잭션은 리포지토리 메서드가 반환될 때 끝난다. 컨트롤러에서 연관관계를 읽는 시점에는 이미 닫혀 있으므로 문제는 그대로다. 해결은 연관관계를 읽는 코드까지 포함하는 서비스 트랜잭션을 두거나, 4회차의 @EntityGraph나 페치 조인으로 필요한 연관관계를 쿼리에서 함께 읽어 오는 것이다.

     @Id String id(직접 할당)만 있고 버전 필드가 없는 엔티티를 새로 만들어 식별자를 넣고 save했다. DB에는 아직 그 식별자의 행이 없다. Hibernate 6.6 기준으로 어떤 SQL이 나가는가? INSERT 하나 SELECT 하나, 그다음 INSERT 하나 SELECT 하나 뒤 낙관적 락 예외 UPDATE 하나 식별자가 채워져 있으므로 기본 판별은 "새것 아님"이고 merge가 호출된다. 하이버네이트는 SELECT로 행을 찾고, 없으므로 INSERT한다. 6.6의 예외 규칙은 생성되는 식별자나 래퍼 타입 버전이 있는 엔티티에만 적용되므로 이 엔티티에는 해당하지 않는다. UPDATE는 행이 이미 있을 때의 결과다. 리포지토리 인터페이스에 애너테이션 없이 Optional findByEmail(String email)을 선언했다. 서비스 계층에 트랜잭션이 없는 상태에서 이 메서드를 호출하면 어떤 트랜잭션 속성으로 실행되는가? SimpleJpaRepository의 클래스 수준 설정을 물려받아 readOnly 트랜잭션 속성 없는 @Transactional과 같은 읽기-쓰기 트랜잭션 트랜잭션 없이 실행 항상 REQUIRES_NEW로 새 트랜잭션 트랜잭션 속성 탐색은 구현 클래스에 대응 메서드가 있을 때만 SimpleJpaRepository 쪽을 본다. 쿼리 메서드는 대응 메서드가 없으므로 인터페이스 메서드와 인터페이스의 애너테이션만 보고, 둘 다 없으면 속성이 없다. 참조 문서도 선언된 쿼리 메서드에는 기본 트랜잭션 설정이 없다고 명시한다. @Id @GeneratedValue Long id와 @Version long version(원시 타입)을 가진 엔티티에서, 새 엔티티 판별은 무엇으로 결정되는가? 식별자가 null인지 버전이 0인지 버전이 null인지 DB에 같은 식별자의 행이 있는지 SELECT로 확인 JpaMetamodelEntityInformation.isNew는 버전 속성이 없거나 원시 타입이면 식별자 판별로 넘긴다. 식별자가 참조 타입 Long이므로 null 여부로 판별한다. 원시 타입 버전은 JPA가 0을 첫 저장 버전으로 보기 때문에 판별에 쓰이지 않는다. 판별 자체는 SELECT를 하지 않는다. 스프링의 JpaTransactionManager와 하이버네이트를 쓸 때, 새로 시작된 readOnly = true 트랜잭션에 대한 설명으로 옳은 것은? DB가 모든 쓰기 SQL을 거부하므로 UPDATE를 실행하면 반드시 SQL 오류가 난다. 읽기 전용은 표식일 뿐이라 하이버네이트의 동작에는 아무 변화가 없다. 1차 캐시를 쓰지 않으므로 같은 식별자로 두 번 조회하면 SELECT가 두 번 나간다. 세션의 플러시 모드가 MANUAL이 되고 기본 읽기 전용이 켜져, 관리 엔티티를 고쳐도 커밋 때 UPDATE가 나가지 않는다. HibernateJpaDialect는 읽기 전용 트랜잭션에서 플러시 모드를 MANUAL로 바꾸고, 로컬 자원 트랜잭션이면 setDefaultReadOnly(true)를 호출한다. 실험에서도 엔티티를 고쳤지만 UPDATE가 나가지 않았다. JDBC의 setReadOnly는 드라이버에 주는 힌트라 DB의 쓰기 거부를 보장하지 않으며, 1차 캐시는 그대로 동작한다. 리포지토리 프록시의 인터셉터 체인에서 findByName 같은 쿼리 메서드 호출은 어디에서 처리가 끝나는가? TransactionInterceptor가 쿼리를 직접 실행한다. SimpleJpaRepository가 메서드 이름을 그때그때 해석해 실행한다. QueryExecutorMethodInterceptor가 시작 시점에 만들어 둔 쿼리 객체를 실행하고 반환한다. DefaultMethodInvokingMethodInterceptor가 인터페이스의 default 구현을 호출한다. QueryExecutorMethodInterceptor.doInvoke는 메서드에 대응하는 쿼리 객체가 있으면 그것을 실행해 반환하고, 없을 때만 proceed()로 넘긴다. 쿼리 객체는 애플리케이션 시작 시점에 메서드 이름 해석이나 @Query 파싱으로 만들어진다. SimpleJpaRepository에는 쿼리 메서드에 대응하는 메서드가 없다.
    JDK 동적 프록시(JDK dynamic proxy)
    java.lang.reflect.Proxy가 실행 중에 생성하는, 지정한 인터페이스들을 구현한 클래스의 객체. 모든 메서드 호출을 하나의 호출 핸들러로 보낸다.
    메서드 인터셉터(MethodInterceptor)
    스프링 AOP에서 메서드 호출을 감싸는 어드바이스. proceed()로 다음 단계에 넘기거나 직접 결과를 반환한다.
    리포지토리 조각(repository fragment)
    리포지토리 인터페이스의 메서드를 구현하는 객체 단위. 사용자 정의 구현 조각들 뒤에 기본 구현인 SimpleJpaRepository가 놓여 하나의 조합을 이룬다.
    엔티티 정보(EntityInformation)
    도메인 타입의 식별자, 버전, 엔티티 이름을 담고 isNew, getId를 제공하는 스프링 데이터의 추상화. JPA에서는 메타모델에서 정보를 읽는다.
    병합(merge)
    넘긴 객체의 상태를 같은 식별자의 관리 인스턴스로 복사하고 그 관리 인스턴스를 반환하는 JPA 연산. 넘긴 객체는 관리 상태가 되지 않는다.
    준영속(detached)
    식별자를 가지고 있고 DB에 대응하는 행이 있을 수 있지만, 현재 어떤 영속성 컨텍스트도 관리하지 않는 엔티티의 상태.
    Persistable
    Spring Data Commons의 인터페이스. getId()와 isNew()를 구현하면 리포지토리가 새 엔티티 판별을 엔티티에게 맡긴다.
    플러시 모드(flush mode)
    영속성 컨텍스트의 변경을 언제 SQL로 내보낼지 정하는 설정. 하이버네이트의 MANUAL은 명시적으로 flush()를 호출할 때만 플러시한다.
