    이 회차의 질문: 두 번째 리포지토리를 쓸 때 무엇을 복사하는가

    JPA를 다룬 앞의 권들에서 리포지토리는 늘 같은 모양이었다. 클래스에 @Repository를 붙이고, EntityManager를 주입받고, persist, find, remove, 그리고 JPQL 몇 줄로 저장·조회·삭제를 구현했다. 엔티티가 하나일 때는 이 방식에 불만이 없다. 문제는 두 번째, 세 번째 엔티티가 생길 때 드러난다. 회원 리포지토리를 다 쓰고 팀 리포지토리를 만들려고 하면 손이 가장 먼저 하는 일은 회원 리포지토리를 통째로 복사하는 것이다.

    복사가 나쁜 이유는 단순히 지루해서가 아니다. 복사된 코드는 같은 결함도 함께 복사한다. 삭제 메서드에 준영속 엔티티를 넘기면 예외가 나는 문제를 회원 리포지토리에서 고쳤다면, 팀 리포지토리와 주문 리포지토리에서도 같은 수정을 기억해서 해야 한다. 엔티티가 스무 개라면 스무 번이다. 공통 코드가 한곳에 모여 있지 않으면 수정의 비용은 엔티티 수에 비례해 커진다.

    스프링 데이터 JPA의 공통 인터페이스는 이 반복을 없애는 장치다. 그런데 "인터페이스만 선언하면 구현이 생긴다"는 설명은 결과만 말해 줄 뿐 과정을 말해 주지 않는다. 이 회차는 과정을 따라간다. 먼저 순수 JPA로 리포지토리 두 개를 만들어 무엇이 반복되는지 눈으로 확인한다. 다음으로 그 반복을 직접 공통화해 보다가 자바의 타입 소거(type erasure)라는 벽에 부딪힌다. 그 벽을 스프링 데이터가 어떻게 넘는지 본 뒤, 공통 인터페이스를 설정하고 적용하고, 마지막으로 인터페이스 계층과 메서드 하나하나가 실제로 하는 일을 실행 로그로 분석한다.

    이 회차의 모든 실험은 Spring Boot 3.5.16, Spring Framework 6.2.19, Spring Data JPA 3.5.13, Hibernate ORM 6.6.53.Final, H2 인메모리 데이터베이스, JDK 21에서 실행했다. 클래스 내부 동작에 대한 서술은 같은 버전의 jar를 javap로 열어 확인한 것이다. 예제 도메인은 설명에 필요한 만큼만 만든 최소 모델로, 식별자와 이름 필드 하나씩만 가진 Member와 Team 두 엔티티다.

    순수 JPA 기반 리포지토리 만들기

    출발점은 스프링 데이터 없이 EntityManager만으로 만든 리포지토리다. 엔티티부터 보자. 식별자는 @GeneratedValue로 생성하고, 이름을 바꾸는 메서드를 하나 둔다. 세터를 열지 않고 의도가 드러나는 변경 메서드를 두는 이유는 JPA 활용 권에서 다뤘다.

    @Entity
public class Member {
    @Id @GeneratedValue
    private Long id;
    private String username;

    protected Member() {}                       // JPA 명세가 요구하는 기본 생성자
    public Member(String username) { this.username = username; }

    public Long getId() { return id; }
    public String getUsername() { return username; }
    public void changeUsername(String username) { this.username = username; }
}

    리포지토리는 다섯 가지 일을 한다. 저장, 삭제, 전체 조회, 식별자로 단건 조회, 개수 세기다.

    @Repository
public class MemberJpaRepository {
    @PersistenceContext
    private EntityManager em;

    public Member save(Member member) { em.persist(member); return member; }
    public void delete(Member member) { em.remove(member); }
    public List findAll() {
        return em.createQuery("select m from Member m", Member.class).getResultList();
    }
    public Optional findById(Long id) { return Optional.ofNullable(em.find(Member.class, id)); }
    public long count() {
        return em.createQuery("select count(m) from Member m", Long.class).getSingleResult();
    }
}

    표에 "수정" 메서드가 없다는 점이 눈에 띈다. 빠뜨린 것이 아니다. JPA에서 수정은 트랜잭션 안에서 영속 상태 엔티티의 필드를 바꾸는 것으로 끝난다. 플러시 시점에 하이버네이트가 엔티티를 처음 읽었을 때 떠 둔 스냅샷과 현재 값을 비교해 UPDATE를 만든다. 이것이 변경 감지(dirty checking)다. 그래서 순수 JPA 리포지토리에도, 뒤에서 볼 스프링 데이터의 공통 인터페이스에도 update라는 메서드는 없다.

    이 리포지토리가 실제로 어떤 SQL을 어떤 순서로 내보내는지 테스트로 확인하자. 테스트 메서드에 트랜잭션을 걸었으므로 테스트가 끝나면 롤백된다.

    반복을 해부하기: 무엇이 같고 무엇이 다른가

    이제 팀 리포지토리를 만든다. 예상대로 회원 리포지토리를 복사해 이름만 바꾸면 끝난다.

    @Repository
public class TeamJpaRepository {
    @PersistenceContext
    private EntityManager em;

    public Team save(Team team) { em.persist(team); return team; }
    public void delete(Team team) { em.remove(team); }
    public List findAll() {
        return em.createQuery("select t from Team t", Team.class).getResultList();
    }
    public Optional findById(Long id) { return Optional.ofNullable(em.find(Team.class, id)); }
    public long count() {
        return em.createQuery("select count(t) from Team t", Long.class).getSingleResult();
    }
}

    두 클래스를 나란히 놓고 달라진 글자만 골라내면 세 종류다. 첫째, 메서드 시그니처에 등장하는 타입 이름(Member와 Team). 둘째, em.find와 createQuery에 넘기는 클래스 리터럴(Member.class와 Team.class). 셋째, JPQL 문자열 안의 엔티티 이름("Member"와 "Team"). 그런데 셋째는 둘째에서 계산할 수 있다. 엔티티 이름은 기본적으로 클래스의 단순 이름이기 때문이다. 식별자 타입(Long)까지 더하면, 결국 달라지는 정보는 엔티티 클래스와 식별자 타입 두 가지뿐이다.

    이 관찰이 이 회차 전체의 열쇠다. 실행 시점에 "이 리포지토리가 다루는 엔티티 클래스"를 알 수만 있다면 나머지 코드는 모든 엔티티에 대해 똑같다. 그렇다면 공통 코드를 한 클래스에 두고 엔티티 클래스만 바꿔 끼우면 된다. 직접 해 보자.

    직접 공통화해 보기: 제네릭 베이스 클래스와 타입 소거

    가장 먼저 떠오르는 방법은 타입 변수를 쓰는 추상 클래스다. 엔티티 타입을 T, 식별자 타입을 ID로 두고, em.find(T.class, id)처럼 쓰고 싶다. 그런데 이 코드는 컴파일되지 않는다.

    class GenericRepo {
    Class domain() { return T.class; }
}

    이유는 자바 제네릭의 구현 방식에 있다. 자바 언어 명세(JLS §4.6)는 컴파일러가 제네릭 타입을 지우는 규칙, 곧 타입 소거를 정의한다. 타입 변수는 그 상한(bound)으로, 매개변수화된 타입은 원시 타입(raw type)으로 바뀐다. 상한을 적지 않은 T의 상한은 Object다. 그래서 바이트코드 수준에서 GenericRepo와 GenericRepo은 같은 클래스 하나이고, 그 클래스의 코드 안에는 "지금 T가 무엇인지"를 담은 값이 어디에도 없다. T.class는 존재하지 않는 값을 달라는 요청이므로 컴파일러가 거부한다.

    소거는 객체에도 흔적을 남기지 않는다. 다음 실험이 그것을 보여 준다.

    List list = new ArrayList<>();
System.out.println(Arrays.toString(list.getClass().getTypeParameters()));
System.out.println(list.getClass() == new ArrayList().getClass());
    [E]
true

    객체가 아는 것은 자기 클래스가 E라는 타입 변수를 선언했다는 사실뿐이고, 그 E가 이번에 String이었다는 정보는 없다. HotSpot 기준으로 힙에 있는 ArrayList 객체의 헤더가 가리키는 클래스 메타데이터는 ArrayList이든 ArrayList이든 같은 하나다.

    그래서 직접 공통화하려면 엔티티 클래스를 값으로 넘겨받아야 한다. Class 객체를 생성자 인자로 받는 방법, 흔히 타입 토큰(type token)이라 부르는 방법이다.

    public abstract class JpaGenericRepository {
    protected final EntityManager em;
    private final Class domainClass;          // 소거된 T 대신 값으로 들고 있는 엔티티 클래스

    protected JpaGenericRepository(EntityManager em, Class domainClass) {
        this.em = em;
        this.domainClass = domainClass;
    }

    public T save(T entity) { em.persist(entity); return entity; }
    public void delete(T entity) { em.remove(entity); }
    public Optional findById(ID id) { return Optional.ofNullable(em.find(domainClass, id)); }
    public List findAll() {
        String jpql = "select e from " + domainClass.getSimpleName() + " e";
        return em.createQuery(jpql, domainClass).getResultList();
    }
    public long count() {
        String jpql = "select count(e) from " + domainClass.getSimpleName() + " e";
        return em.createQuery(jpql, Long.class).getSingleResult();
    }
}

    이제 회원 리포지토리는 JpaGenericRepository을 상속하고 생성자에서 super(em, Member.class)만 호출하면 된다. 꽤 좋아졌지만 여전히 엔티티마다 클래스 하나를 만들어야 하고, 그 클래스를 빈으로 등록하고, 트랜잭션과 예외 변환을 어떻게 걸지도 각자 정해야 한다. 그리고 Member라는 정보를 extends JpaGenericRepository에 한 번, Member.class에 또 한 번, 두 번 적고 있다. 같은 정보를 두 번 적는다는 것은 둘이 어긋날 수 있다는 뜻이다.

    소거되지 않는 곳: 선언에 남는 Signature 속성

    여기서 질문을 바꿔 보자. 객체에서는 타입 인자가 지워진다. 그렇다면 클래스 선언에서는 어떨까. interface MemberRepo extends Repo처럼 상위 타입에 구체적인 타입 인자를 적어 넣은 선언을 컴파일한 뒤 javap -v로 열어 보면 답이 나온다.

    클래스 파일에는 Signature라는 속성이 있다(JVMS §4.7.9). 바이트코드 실행에는 쓰이지 않지만, 소스에 적힌 제네릭 선언을 그대로 보존해 리플렉션과 컴파일러가 읽을 수 있게 한다. 위의 문자열은 "MemberRepo의 상위 클래스는 Object이고, 상위 인터페이스는 String과 Long으로 매개변수화된 Repo다"라는 뜻이다. 자바 리플렉션 API는 이 속성을 getGenericInterfaces()로 돌려준다.

    ParameterizedType p = (ParameterizedType) MemberRepo.class.getGenericInterfaces()[0];
System.out.println(p.getRawType());
System.out.println(Arrays.toString(p.getActualTypeArguments()));
    interface Repo
[class java.lang.String, class java.lang.Long]

    정리하면 이렇다. 타입 인자는 객체에서는 지워지지만, 어떤 타입이 자신의 상위 타입을 구체적인 타입 인자로 선언했다면 그 선언은 클래스 파일에 남는다. 그러니 엔티티 클래스를 알아내는 가장 확실한 방법은 객체를 들여다보는 것이 아니라, "Member를 타입 인자로 박아 넣은 선언"을 하나 받아서 그 Signature를 읽는 것이다.

    이 장의 핵심

    스프링 데이터 JPA의 리포지토리 인터페이스 interface MemberRepository extends JpaRepository은 바로 그 "타입 인자를 박아 넣은 선언"이다. 스프링 데이터는 이 인터페이스의 Signature를 읽어 엔티티 클래스와 식별자 타입을 알아내고, 그 정보로 공통 구현체 하나를 엔티티마다 따로 만들어 붙인다. 개발자가 Member를 적는 곳은 한 번뿐이다.

    실제로 스프링 데이터 커먼즈 3.5.13의 DefaultRepositoryMetadata 생성자를 javap -c로 읽으면 이 일을 하는 코드가 그대로 보인다. 리포지토리 인터페이스로 TypeInformation.of(repositoryInterface)를 만들고, getRequiredSuperTypeInformation(Repository.class)로 Repository까지 거슬러 올라간 상위 타입 정보를 얻은 뒤, getTypeArguments()의 0번을 도메인 타입, 1번을 식별자 타입으로 삼는다. 해석하지 못하면 "Could not resolve domain type of %s"라는 메시지로 실패하도록 되어 있다. 이 회차의 실험 애플리케이션에서 리포지토리 팩토리 빈이 들고 있는 메타데이터를 꺼내 보면 다음과 같이 나온다.

    generic ifaces = [org.springframework.data.jpa.repository.JpaRepository]
domainType = demo.Member, idType = java.lang.Long

    공통 인터페이스 설정: @EnableJpaRepositories와 스프링 부트의 자동 구성

    스프링 데이터 JPA가 리포지토리 인터페이스를 찾아 구현을 붙이려면 먼저 "어디서 찾을지"를 알아야 한다. 스프링 부트 없이 순수 스프링으로 구성한다면 설정 클래스에 @EnableJpaRepositories를 붙인다.

    @Configuration
@EnableJpaRepositories(basePackages = "demo.repository")
@EnableTransactionManagement
class JpaConfig {
    // EntityManagerFactory, DataSource, PlatformTransactionManager 빈 정의 ...
}

    스프링 데이터 JPA 레퍼런스는 기본 패키지를 지정하지 않으면 설정 클래스가 있는 패키지를 쓴다고 설명한다. 이 애너테이션에는 패키지 외에도 리포지토리 생성 방식을 정하는 속성이 많다. Spring Data JPA 3.5.13의 클래스 파일에서 각 속성의 기본값(AnnotationDefault)을 읽으면 다음과 같다.

    속성기본값의미와 다루는 회차
    basePackages빈 배열비어 있으면 애너테이션이 붙은 설정 클래스의 패키지
    entityManagerFactoryRef"entityManagerFactory"리포지토리가 쓸 EntityManagerFactory 빈 이름

    스프링 부트를 쓰면 이 애너테이션을 직접 붙이지 않아도 된다. 자동 구성 클래스 JpaRepositoriesAutoConfiguration이 대신 붙여 주기 때문이다. Spring Boot 3.5.16의 이 클래스를 javap -v로 열면 적용 조건이 애너테이션으로 붙어 있다.

    @AutoConfiguration(after = { HibernateJpaAutoConfiguration.class, TaskExecutionAutoConfiguration.class })
@ConditionalOnBean(DataSource.class)
@ConditionalOnClass(JpaRepository.class)
@ConditionalOnMissingBean({ JpaRepositoryFactoryBean.class, JpaRepositoryConfigExtension.class })
@ConditionalOnBooleanProperty(name = "spring.data.jpa.repositories.enabled", matchIfMissing = true)
@Import(JpaRepositoriesImportSelector.class)

    조건을 하나씩 읽어 보자. DataSource 빈이 있어야 하고, 클래스패스에 JpaRepository가 있어야 하며(스프링 데이터 JPA 스타터를 넣었다는 뜻이다), spring.data.jpa.repositories.enabled 속성이 꺼져 있지 않아야 한다. 눈여겨볼 것은 @ConditionalOnMissingBean이다. 개발자가 직접 @EnableJpaRepositories를 붙여 리포지토리를 등록하면 JpaRepositoryFactoryBean 빈이 생기므로, 자동 구성은 물러난다. 둘이 겹쳐 같은 리포지토리를 두 번 등록하는 일이 없도록 한 장치다.

    그러면 자동 구성은 어느 패키지를 뒤지는가. 임포트되는 등록기 JpaRepositoriesRegistrar는 내부에 @EnableJpaRepositories가 붙은 설정 클래스(EnableJpaRepositoriesConfiguration)를 하나 품고 있고, 기본 패키지는 상위 클래스 AbstractRepositoryConfigurationSourceSupport의 getBasePackages()가 정한다. 바이트코드에서 이 메서드는 AutoConfigurationPackages.get(beanFactory)를 호출한다. 자동 구성 패키지는 @SpringBootApplication에 들어 있는 @AutoConfigurationPackage가 등록하는 패키지, 곧 메인 클래스가 있는 패키지다. 스프링 부트 레퍼런스도 자동 구성을 쓰면 "자동 구성 패키지에서 리포지토리를 찾는다"고 적고 있다. 실험 애플리케이션에서 이 값을 출력하면 메인 클래스의 패키지 하나가 나온다.

    autoconfig packages = [demo]

    여기서 실무적인 결론이 하나 나온다. 리포지토리 인터페이스를 메인 클래스 패키지의 바깥(예를 들어 형제 패키지)에 두면 스캔 대상이 아니므로 빈이 생기지 않고, 그 리포지토리를 주입받는 쪽에서 빈을 찾지 못해 애플리케이션 시작이 실패한다. 이때는 패키지 구조를 고치거나 @EnableJpaRepositories(basePackages = ...)로 위치를 직접 지정해야 한다. 엔티티 스캔도 같은 자동 구성 패키지를 기준으로 하므로(레퍼런스의 Entity Classes 절), 엔티티를 바깥에 두었다면 @EntityScan도 함께 필요하다.

    부트스트랩 모드도 짚어 두자. 스프링 부트 3.5.16의 설정 메타데이터에서 spring.data.jpa.repositories.bootstrap-mode의 기본값은 default다. 스프링 데이터 JPA 레퍼런스는 기본 모드에서 리포지토리가 싱글톤으로 즉시 초기화되고, 이 과정에서 검증과 메타데이터 분석을 위해 이미 EntityManager와 상호작용한다고 설명한다. 그래서 리포지토리 선언에 문제가 있으면 첫 호출 때가 아니라 애플리케이션 시작 시점에 실패한다. 뒤에서 @NoRepositoryBean을 빠뜨린 실험이 시작 단계에서 실패하는 것도 이 때문이다. deferred와 lazy는 이 초기화를 뒤로 미루는 모드다.

    한 층 아래 1: 구현 클래스 없는 인터페이스가 빈 정의가 되기까지

    스프링의 일반적인 컴포넌트 스캔은 인터페이스를 빈으로 만들지 않는다. ClassPathScanningCandidateComponentProvider의 기본 후보 판정은 독립적인 구체 클래스를 요구하기 때문이다. 인터페이스는 new로 만들 수 없으니 당연하다. 스프링 데이터는 이 스캐너를 상속한 RepositoryComponentProvider로 자기만의 규칙을 적용한다. Spring Data Commons 3.5.13의 바이트코드에서 읽은 규칙은 다음과 같다.

    • 포함 필터 두 개: Repository를 상속한 인터페이스를 고르는 InterfaceTypeFilter(Repository.class), 그리고 @RepositoryDefinition이 붙은 타입을 고르는 AnnotationTypeFilter.
    • 제외 필터 하나: @NoRepositoryBean이 붙은 타입은 후보에서 뺀다.
    • 후보 판정 재정의: isCandidateComponent는 클래스 이름이 org.springframework.data.repository.Repository 자신인 경우를 걸러 내고, 다른 클래스 안에 중첩된 인터페이스는 considerNestedRepositories가 켜져 있을 때만 받아들인다.

    스캔이 클래스를 읽는 방식도 알아 둘 만하다. 스프링 프레임워크 6.2.19의 SimpleMetadataReader는 스프링이 내장한 ASM의 ClassReader로 .class 파일의 바이트를 직접 해석한다. 즉 스캔 단계에서는 후보 클래스를 JVM에 로드하지 않고, 클래스 파일에 적힌 애너테이션과 상위 타입 이름 같은 메타데이터만 읽는다. 패키지 아래 수백 개의 클래스를 훑어도 정적 초기화 블록이 실행되거나 메타스페이스에 클래스가 쌓이지 않는 이유다.

    후보로 뽑힌 인터페이스마다 RepositoryConfigurationDelegate가 빈 정의(BeanDefinition)를 하나씩 등록한다. 핵심은 이 빈 정의의 클래스가 인터페이스 자신이 아니라는 점이다. 실험 애플리케이션에서 memberRepository 빈 정의를 꺼내 보면 다음과 같다.

    beanClassName = org.springframework.data.jpa.repository.support.JpaRepositoryFactoryBean
ctor arg value = demo.MemberRepository
&memberRepository = org.springframework.data.jpa.repository.support.JpaRepositoryFactoryBean
repo class = jdk.proxy2.$Proxy96

    빈 정의의 클래스는 JpaRepositoryFactoryBean이고, 생성자 인자 0번에 리포지토리 인터페이스의 이름이 들어 있다. 빈 이름은 인터페이스의 단순 이름을 소문자로 시작하게 바꾼 memberRepository다. JpaRepositoryFactoryBean은 스프링의 FactoryBean이다. 스프링 컨테이너는 FactoryBean 타입의 빈을 만나면, 그 이름으로 빈을 요청받았을 때 팩토리 자신이 아니라 팩토리의 getObject()가 돌려준 객체를 내준다. 팩토리 자체가 필요하면 이름 앞에 &를 붙여 요청한다. 위 출력에서 &memberRepository로는 팩토리 빈이, memberRepository로는 JDK 동적 프록시가 나온 것이 그 결과다.

    팩토리 빈이 프록시를 만드는 시점은 초기화 콜백 afterPropertiesSet()이다. 이 경로는 실패하는 리포지토리를 일부러 만들어 보면 스택 트레이스로 정확히 드러난다(뒤의 @NoRepositoryBean 실험). 아래에서 위로 읽으면 다음 순서다.

    org.hibernate...JpaMetamodelImpl.managedType

    스프링 컨테이너가 빈 초기화 메서드를 호출하면, 팩토리 빈은 RepositoryFactorySupport.getRepository()로 리포지토리를 만든다. 이 과정에서 JPA 모듈의 JpaRepositoryFactory.getTargetRepository()가 프록시 뒤에 둘 실제 객체를 만드는데, 그 전에 앞에서 본 메타데이터의 도메인 타입으로 하이버네이트 메타모델에 엔티티 정보를 묻는다(JpaMetamodelEntityInformation). 식별자 속성이 무엇인지, 엔티티 이름이 무엇인지 같은 정보가 여기서 모인다. 그렇게 만들어진 대상 객체가 SimpleJpaRepository이고, ProxyFactory가 이 대상과 인터셉터들을 묶어 프록시를 만든다. 프록시 안에서 인터셉터들이 호출을 어떤 순서로 처리하는지는 스프링 DB 2편에서 자세히 따라갔으므로, 여기서는 결과물을 열어 보는 데 집중한다.

    공통 인터페이스 적용: 리포지토리를 인터페이스 한 줄로 바꾸기

    이제 순수 JPA 리포지토리 두 개를 스프링 데이터 JPA로 바꾼다. 코드는 이것이 전부다.

    public interface MemberRepository extends JpaRepository {
}

public interface TeamRepository extends JpaRepository {
}

    구현 클래스도, @Repository도, EntityManager 주입도 없다. 첫 번째 타입 인자는 엔티티 타입, 두 번째는 그 엔티티의 식별자 타입이다. 앞 절에서 본 대로 이 두 인자가 Signature 속성에 남고, 스프링 데이터가 그것을 읽는다. 식별자 타입은 엔티티의 @Id 필드 타입과 맞춰야 한다. Member의 식별자가 Long이므로 Long이다.

    앞의 테스트를 그대로 옮겨 스프링 데이터 리포지토리로 실행해 보자. 같은 테스트가 통과한다면 공통 인터페이스가 순수 JPA 리포지토리를 대신할 수 있다는 뜻이다. SQL이 어디서 나가는지 보려고 구분선을 출력하게 했다.

    @Autowired MemberRepository memberRepository;

@Test
void springDataCrud() {
    Member member1 = memberRepository.save(new Member("member1"));
    Member member2 = memberRepository.save(new Member("member2"));

    assertThat(memberRepository.findById(member1.getId()).get()).isSameAs(member1);
    List all = memberRepository.findAll();
    assertThat(all).hasSize(2);
    System.out.println("--- before count");
    assertThat(memberRepository.count()).isEqualTo(2);

    memberRepository.delete(member1);
    memberRepository.delete(member2);
    System.out.println("--- before count2");
    assertThat(memberRepository.count()).isEqualTo(0);
    System.out.println("--- end");
}

    흐름은 순수 JPA 버전과 똑같다. 저장은 쓰기 지연되었다가 findAll의 JPQL 직전에 플러시되고, findById는 1차 캐시에서 같은 객체를 돌려주며(isSameAs 통과), 삭제는 다음 JPQL 직전에 플러시된다. 테스트 메서드의 트랜잭션 안에서 리포지토리 메서드들이 호출되었으므로 모두 하나의 영속성 컨텍스트를 공유했기 때문이다. 리포지토리 메서드에도 트랜잭션 설정이 붙어 있지만, 이미 진행 중인 트랜잭션이 있으면 기본 전파 속성(REQUIRED)에 따라 거기에 참여할 뿐 새로 시작하지 않는다.

    달라진 곳은 한 줄이다. 직접 쓴 JPQL select count(m) from Member m은 count(m1_0.id)가 되었고, 스프링 데이터의 count()는 count(*)가 되었다. 이유는 SimpleJpaRepository가 JPQL을 만드는 방식에 있다. Spring Data JPA 3.5.13의 QueryUtils에는 COUNT_QUERY_STRING = "select count(%s) from %s x"라는 상수가 있고, 첫 번째 자리에는 JPA 구현체마다 다른 자리표시자가 들어간다. 하이버네이트용 PersistenceProvider의 getCountQueryPlaceholder()는 "*"를 돌려준다. 그래서 실제로 실행되는 JPQL은 select count(*) from Member x이고, 하이버네이트는 이것을 그대로 count(*)로 번역한다. 두 쿼리의 결과는 같다. 식별자 컬럼은 NULL일 수 없으므로 count(id)와 count(*)는 같은 행 수를 센다.

Advised와 DecoratingProxy는 스프링 AOP의 ProxyFactory가 기본으로 덧붙이는 인터페이스로, 위 실험처럼 프록시의 설정과 원래 대상 클래스를 조회할 수 있게 해 준다.

    대상은 SimpleJpaRepository다.     어드바이스 목록에는 예외 변환 인터셉터(PersistenceExceptionTranslationInterceptor)가 두 번 나온다. 첫 번째는 리포지토리 팩토리가 프록시를 조립할 때 넣은 것이다. 마지막 것은 어디서 왔을까. 같은 애플리케이션을 spring.dao.exceptiontranslation.enabled=false로 실행하면 컨텍스트에서 PersistenceExceptionTranslationPostProcessor 빈이 사라지고, 어드바이스 목록도 마지막 줄 없이 여섯 개로 줄어든다. 즉 마지막 인터셉터는 스프링 부트가 등록한 빈 후처리기가 완성된 프록시에 덧붙인 것이다. 이 후처리기는 @Repository가 붙은 빈을 대상으로 하는데, javap -v로 보면 SimpleJpaRepository 클래스 자체에 @Repository가 붙어 있다. 어느 쪽이든 결론은 하나다. 리포지토리 인터페이스에 @Repository를 붙이지 않아도 JPA 예외는 스프링의 DataAccessException 계층으로 변환된다. 인터페이스에 그 애너테이션을 붙이는 것은 아무것도 더하지 않는다.

    공통 인터페이스 분석 1: 계층 구조와 모듈의 경계

    JpaRepository를 상속하면 수십 개의 메서드가 생긴다. 이 메서드들은 한 인터페이스에 다 들어 있지 않고 여러 층에 나뉘어 있다. Spring Data 3.5.13(Commons와 JPA)의 클래스 파일을 javap로 열어 상속 관계를 그리면 다음과 같다.

    CrudRepository는 저장소 종류와 무관한 기본 CRUD를 정의한다. 3.5.13에서 추상 메서드는 save, saveAll, findById, existsById, findAll, findAllById, count, deleteById, delete, deleteAllById, deleteAll(Iterable), deleteAll()의 열두 개다. 여러 건을 돌려주는 메서드의 반환 타입은 Iterable이다. ListCrudRepository의 Javadoc에 적힌 @since 3.0대로 버전 3.0부터 ListCrudRepository가 추가되어, 같은 메서드를 List로 돌려받을 수 있다. JpaRepository는 ListCrudRepository를 상속하므로 findAll()의 반환 타입이 List다. 실험에서 실제 반환 객체는 java.util.ArrayList였다.

    페이징 쪽 계층에서 눈여겨볼 것은 PagingAndSortingRepository가 CrudRepository가 아니라 Repository를 바로 상속한다는 점이다. 3.5.13의 클래스 파일에서 이 인터페이스의 상위 타입은 Repository 하나뿐이다. 따라서 페이징과 정렬만 상속한 리포지토리에는 save가 생기지 않는다. CRUD와 페이징을 모두 원하면 둘을 함께 상속해야 하고, JpaRepository는 실제로 ListCrudRepository와 ListPagingAndSortingRepository를 모두 상속한다. 페이징의 동작 원리와 count 쿼리는 04회차에서 다룬다.

    두 모듈의 경계도 중요하다. Repository부터 ListPagingAndSortingRepository까지는 spring-data-commons의 org.springframework.data.repository 패키지에, QueryByExampleExecutor는 같은 모듈의 하위 패키지 org.springframework.data.repository.query에 있다. 이 모듈은 JPA만이 아니라 MongoDB, Redis 같은 다른 저장소 모듈이 함께 쓰는 공통 기반이다. 그래서 여기 있는 메서드는 어떤 저장소에서도 의미가 통하는 것들뿐이다. 반면 JpaRepository는 spring-data-jpa의 org.springframework.data.jpa.repository 패키지에 있고, 여기에만 있는 메서드는 모두 JPA 고유의 개념에 기대고 있다. flush와 saveAndFlush는 쓰기 지연 저장소를 비우는 영속성 컨텍스트의 개념이고, getReferenceById는 EntityManager.getReference가 돌려주는 프록시 참조의 개념이며, deleteAllInBatch는 JPQL 벌크 연산의 개념이다. 메서드가 어느 인터페이스에 있는지를 보면 그 메서드가 저장소 일반의 약속인지 JPA에 묶인 약속인지 알 수 있다.

    이 경계는 클래스패스에 저장소 모듈이 둘 이상 있을 때 실제로 쓰인다. 레퍼런스에 따르면 스프링 데이터는 여러 저장소 모듈을 감지하면 엄격한(strict) 설정 모드에 들어가고, 리포지토리가 모듈 전용 인터페이스(예를 들어 JpaRepository)를 상속했는지, 또는 도메인 클래스에 모듈 전용 애너테이션(예를 들어 @Entity)이 붙었는지를 보고 어느 모듈이 그 리포지토리를 맡을지 정한다. Repository나 CrudRepository만 상속한 리포지토리는 인터페이스만으로는 어느 모듈에 묶일지 구분되지 않는다.

    바이트코드에 숨은 메서드: 공변 반환 타입과 브리지 메서드

    반환된 객체의 클래스는 하이버네이트가 Member를 상속해 만든 프록시 클래스다. 프록시는 식별자를 이미 알고 있으므로 getId()에는 SQL이 필요 없다. SELECT는 식별자가 아닌 필드에 처음 접근하는 getUsername()에서야 나간다. 이 지연 때문에 두 가지 결과가 생긴다. 첫째, 존재하지 않는 식별자로 참조를 얻어도 그 순간에는 아무 일도 일어나지 않고, 처음 접근할 때 예외가 난다. 실험에서는 jakarta.persistence.EntityNotFoundException: Unable to find demo.Member with id 999였다. JpaRepository의 Javadoc도 구현에 따라 거의 항상 인스턴스를 돌려주고 첫 접근 때 EntityNotFoundException을 던질 가능성이 높다고 적고 있다. 둘째, 트랜잭션 밖에서 참조를 얻고 나중에 접근하면 초기화할 영속성 컨텍스트가 이미 닫혀 있다. 실험 결과는 org.hibernate.LazyInitializationException: Could not initialize proxy [demo.Member#1] - no session이었다.

    그럼 getReferenceById는 어디에 쓰는가. 엔티티의 내용은 필요 없고 식별자만으로 연관관계를 걸고 싶을 때다. 예를 들어 주문을 만들면서 회원 식별자만 알고 있다면, 회원을 조회하지 않고 참조만 얻어 외래 키를 채울 수 있다. 외래 키 컬럼에 들어갈 값은 식별자뿐이므로 프록시로 충분하다. 존재 여부를 확인해야 하는 곳에서는 쓰면 안 된다. 같은 역할의 getOne과 getById는 3.5.13에서 @Deprecated이고, 바이트코드를 보면 둘 다 내부에서 getReferenceById를 호출할 뿐이다. Javadoc에 따르면 getReferenceById는 2.7부터 있다.

    deleteById와 delete: 없는 것을 지우면

    deleteById(999L)를 실행하면 SELECT 한 번만 나가고 예외 없이 끝난다. 바이트코드가 findById(id).ifPresent(this::delete)이기 때문이다. CrudRepository의 Javadoc도 엔티티를 찾지 못하면 조용히 무시한다고 명시한다. 삭제 결과를 확인해야 하는 업무라면 반환값이 없는 이 메서드 대신 먼저 조회해 존재를 확인하는 코드를 직접 써야 한다.

    delete(entity)는 순수 JPA의 em.remove보다 너그럽다. em.remove는 준영속 엔티티를 받으면 IllegalArgumentException을 던지지만, SimpleJpaRepository.delete는 먼저 em.contains(entity)로 영속 상태인지 확인하고, 아니면 같은 식별자로 em.find를 해 본다. 행이 있으면 em.merge로 영속 상태의 인스턴스를 얻어 그것을 remove한다. 트랜잭션 밖에서 읽어 온 준영속 엔티티를 넘긴 실험의 로그가 이 순서를 보여 준다.

    Hibernate: select m1_0.id,m1_0.username from member m1_0 where m1_0.id=?   ← 테스트 코드의 findById (첫 트랜잭션)
Hibernate: select m1_0.id,m1_0.username from member m1_0 where m1_0.id=?   ← delete 안의 em.find (두 번째 트랜잭션)
Hibernate: delete from member where id=?                                  ← merge로 얻은 영속 인스턴스를 remove, 커밋 때 플러시

    em.find가 이미 같은 식별자의 엔티티를 영속성 컨텍스트에 올려 두었으므로, 이어지는 merge는 추가 SELECT 없이 그 인스턴스에 준영속 객체의 값을 복사한다. 만약 find가 null을 돌려주면(다른 트랜잭션이 이미 지웠다면) 아무것도 하지 않고 끝난다.

    deleteAll과 deleteAllInBatch: 엔티티 단위인가, SQL 한 방인가

    이름만 보면 둘 다 "전부 지운다"지만 동작은 완전히 다르다. 행 네 개가 있는 상태에서 deleteAll(), 다시 행 세 개를 넣고 deleteAllInBatch()를 실행한 로그다.

    -- deleteAll
Hibernate: select m1_0.id,m1_0.username from member m1_0
Hibernate: delete from member where id=?
Hibernate: delete from member where id=?
Hibernate: delete from member where id=?
Hibernate: delete from member where id=?
-- deleteAllInBatch
Hibernate: delete from member m1_0

    deleteAll()은 모든 엔티티를 메모리로 읽어 영속성 컨텍스트에 올린 다음 하나씩 remove한다. 행이 N개면 SELECT 1번에 DELETE N번이고, N개의 엔티티 객체와 그 스냅샷이 힙에 올라간다. 대신 엔티티 단위로 지우므로 cascade 설정과 엔티티 생명주기 콜백(@PreRemove 등)이 모두 동작한다. deleteAllInBatch()는 영속성 컨텍스트를 거치지 않고 JPQL 벌크 DELETE를 한 번 실행한다. QueryUtils의 상수 DELETE_ALL_QUERY_STRING = "delete from %s x"에 엔티티 이름을 넣은 것이다. 빠르지만 대가가 있다. JpaRepository의 Javadoc은 엔티티 목록을 받는 deleteAllInBatch(Iterable)에 대해, 이런 배치 삭제가 JPA의 1차 캐시와 DB를 어긋나게 남기며 cascade 의미를 따르지 않고 생명주기 이벤트도 발생시키지 않는다고 경고한다. 인자 없는 deleteAllInBatch()도 같은 JPQL 벌크 DELETE이므로 사정이 같다. 이미 영속성 컨텍스트에 올라와 있던 엔티티는 DB에서 사라진 뒤에도 메모리에 그대로 남는다. 벌크 연산과 영속성 컨텍스트의 이 어긋남은 04회차의 벌크성 수정 쿼리에서 다시 다룬다.

    count와 existsById: 행을 가져오지 않고 세기

    count()는 앞에서 본 select count(*) from Member x다. existsById는 3.5.13에서 엔티티를 읽어 오지 않고 where 조건을 붙인 count 쿼리를 실행한 뒤 결과가 0보다 큰지 본다. 실험 로그는 select count(*) from member m1_0 where m1_0.id=?였다. 엔티티 전체를 영속성 컨텍스트에 올리는 findById(id).isPresent()보다 가볍다. 다만 이 쿼리는 1차 캐시를 보지 않으므로, 같은 트랜잭션에서 방금 persist했지만 아직 플러시되지 않은 엔티티가 있다면 그 결과는 자동 플러시 여부에 좌우된다. 하이버네이트의 기본 AUTO 플러시 모드에서는 JPQL 실행 전에 플러시가 일어난다는 점을 앞의 테스트에서 확인했다.

    호출 하나가 트랜잭션 하나: 리포지토리 메서드의 경계

    지금까지의 실험 가운데 일부는 트랜잭션 밖에서 리포지토리를 호출했다. 그래도 저장과 삭제가 DB에 반영되었다. 리포지토리 메서드 자체에 트랜잭션이 걸려 있기 때문이다. 3.5.13의 SimpleJpaRepository 클래스에는 @Transactional(readOnly = true)가 붙어 있고, save, saveAll, delete, deleteById, deleteAll, deleteAllInBatch, flush 같은 변경 메서드에는 속성 없는 @Transactional이 다시 붙어 있다. 이 설정이 어떤 이유로 이렇게 되어 있고 읽기 전용이 무엇을 바꾸는지는 06회차의 구현체 분석에서 자세히 본다. 여기서는 이 설정이 만드는 결과 하나만 실험으로 확인한다.

    // 트랜잭션 밖
Member x = repo.findById(id1).get();
Member y = repo.findById(id1).get();
System.out.println("outside tx same? " + (x == y));

// 트랜잭션 안
tx.executeWithoutResult(s -> {
    Member p = repo.findById(id1).get();
    Member q = repo.findById(id1).get();
    System.out.println("inside tx same? " + (p == q));
});
    Hibernate: select m1_0.id,m1_0.username from member m1_0 where m1_0.id=?
Hibernate: select m1_0.id,m1_0.username from member m1_0 where m1_0.id=?
outside tx same? false
Hibernate: select m1_0.id,m1_0.username from member m1_0 where m1_0.id=?
inside tx same? true

    트랜잭션 밖에서는 같은 식별자를 두 번 조회했는데 SELECT가 두 번 나가고 서로 다른 객체가 나왔다. 호출마다 프록시의 트랜잭션 인터셉터가 트랜잭션을 새로 시작하고, JpaTransactionManager가 그 트랜잭션을 위해 EntityManager를 새로 만들었다가 트랜잭션이 끝날 때 닫기 때문이다. 영속성 컨텍스트가 호출마다 새로 생기고 사라지니 1차 캐시가 공유될 수 없다. 반환된 엔티티는 이미 닫힌 영속성 컨텍스트에서 나온 준영속 상태다. 트랜잭션 안에서는 두 호출이 바깥 트랜잭션에 참여해 하나의 영속성 컨텍스트를 공유하므로 SELECT는 한 번이고 같은 객체가 나온다.

    이 차이는 변경 감지에서 그대로 결과의 차이가 된다. 트랜잭션 밖에서 findById로 꺼낸 엔티티의 이름을 바꾸고 다시 조회하면 바뀌기 전 값이 나온다. 변경을 감지할 영속성 컨텍스트가 이미 없기 때문이다. 같은 일을 트랜잭션 안에서 하면 커밋 때 update member set username=? where id=?가 나가고 다시 조회한 값이 바뀌어 있다. 실험의 출력은 각각 reloaded = before와 reloaded2 = after였다. 서비스 계층에 트랜잭션을 두어야 한다는 규칙은 스프링 데이터 JPA를 쓴다고 사라지지 않는다. 오히려 리포지토리 메서드마다 트랜잭션이 따로 걸려 있다는 사실 때문에, 서비스에 트랜잭션이 없으면 메서드 호출 사이에서 영속성 컨텍스트가 끊긴다는 점을 더 분명히 의식해야 한다.

    필요한 메서드만 드러내기: Repository 직접 상속과 @NoRepositoryBean

    JpaRepository를 상속하면 삭제 메서드까지 모두 열린다. 읽기 전용이어야 할 엔티티라면 deleteAllInBatch 같은 메서드가 리포지토리에 있다는 것 자체가 위험이다. 레퍼런스는 메서드를 골라서 노출하고 싶으면 Repository를 상속하고 CrudRepository의 메서드 중 원하는 것만 자기 인터페이스에 옮겨 적으라고 안내한다. 여러 리포지토리가 공유할 중간 인터페이스를 만들 때는 @NoRepositoryBean을 붙인다.

    @NoRepositoryBean
interface ReadOnlyRepository extends Repository {
    Optional findById(ID id);
    List findAll();
    long count();
}

public interface MemberReadRepository extends ReadOnlyRepository {
}

    실험 애플리케이션에서 이 리포지토리를 호출하면 findAll, count, findById가 각각 SimpleJpaRepository와 똑같은 SQL을 낸다(count도 select count(*) from member m1_0였다). 선언한 메서드의 시그니처가 공통 구현체의 메서드와 일치하므로 쿼리 메서드로 해석되지 않고 구현체로 위임된 것이다. MemberReadRepository.class.getMethods()에 save는 없다. 컨텍스트의 Repository 타입 빈 이름을 출력하면 teamRepository, memberReadRepository, memberRepository가 나오고 ReadOnlyRepository는 없다. 제외 필터가 동작한 것이다.

    그렇다면 @NoRepositoryBean을 빠뜨리면 어떻게 될까. 별도 패키지에 다음 인터페이스 하나만 두고 애플리케이션을 시작해 보았다.

    public interface BaseRepository extends JpaRepository {
}

  defined in bad.BaseRepository defined in @EnableJpaRepositories declared on
  JpaRepositoriesRegistrar.EnableJpaRepositoriesConfiguration: Not a managed type: class java.lang.Object
Caused by: java.lang.IllegalArgumentException: Not a managed type: class java.lang.Object

    이 메시지는 이 회차의 앞부분과 정확히 이어진다. BaseRepository는 Repository를 상속한 인터페이스이므로 스캔 필터에 걸렸고, 빈 정의가 등록되었다. 팩토리 빈이 초기화되며 Signature에서 도메인 타입을 읽으려 했지만, 이 선언의 타입 인자는 구체적인 클래스가 아니라 타입 변수 T 그대로다. 해석할 실제 타입이 없으니 T는 그 상한인 Object로 처리되었고, 하이버네이트 메타모델에 Object라는 엔티티가 있을 리 없으므로 실패했다. 레퍼런스도 @NoRepositoryBean이 필요한 이유를 "여전히 제네릭 타입 변수를 포함하고 있어 엔티티를 결정할 수 없기 때문"이라고 설명한다. 기본 부트스트랩 모드에서는 리포지토리를 즉시 초기화하므로 이 실패가 첫 호출이 아니라 시작 단계에서 드러난다.

    인터페이스를 상속하지 않고 싶다면 @RepositoryDefinition을 쓸 수도 있다. 이 애너테이션의 속성은 domainClass와 idClass 두 개로, 상속 선언 대신 애너테이션 속성으로 엔티티 타입과 식별자 타입을 알려 준다. 스캔의 두 번째 포함 필터가 바로 이 애너테이션을 찾는 것이었다.

    흔한 오해와 함정

    • "리포지토리 인터페이스에 @Repository를 붙여야 예외가 변환된다." 그렇지 않다. 실험에서 본 대로 리포지토리 팩토리가 예외 변환 인터셉터를 프록시에 넣고, 스프링 부트의 빈 후처리기가 하나를 더 붙인다. 컴포넌트 스캔 대상이 되게 하려는 의도라면 그것도 필요 없다. 리포지토리는 컴포넌트 스캔이 아니라 스프링 데이터 자신의 스캔으로 등록된다.
    • "값을 바꾼 뒤 save를 불러야 UPDATE가 나간다." 트랜잭션 안의 영속 엔티티라면 변경 감지로 충분하다. 반대로 트랜잭션 밖에서 꺼낸 준영속 엔티티는 값을 바꿔도 반영되지 않는다. 이 경우 save를 부르면 merge로 반영되지만, 그것은 변경 감지가 아니라 병합이며 병합의 함정(값이 없는 필드가 null로 덮이는 문제)을 그대로 가진다.
    • "deleteAll()은 DELETE 한 번이다." 행 수만큼 DELETE가 나가고 그 전에 전체를 읽는다. SQL 한 번이 필요하면 deleteAllInBatch()이지만, 그 대가로 1차 캐시와 DB가 어긋날 수 있고 cascade와 콜백이 동작하지 않는다.
    • "getReferenceById로 존재 여부를 확인할 수 있다." 호출 시점에는 DB에 가지 않으므로 없는 식별자에도 객체가 나온다. 예외는 처음 필드에 접근할 때, 트랜잭션 밖이라면 LazyInitializationException의 모습으로 나온다.
    • "deleteById는 대상이 없으면 예외를 던진다." 3.5.13은 조용히 넘어간다. Javadoc이 이 동작을 명시한다.
    • "리포지토리 인터페이스는 프로젝트 어디에 두어도 찾아진다." 스프링 부트에서는 자동 구성 패키지, 곧 메인 클래스의 패키지와 그 하위만 찾는다.
    • "프록시 클래스 이름으로 리포지토리를 구분할 수 있다." $Proxy96의 번호는 생성 순서일 뿐이다. 대상 클래스가 필요하면 AopUtils.getTargetClass나 Advised로 꺼내야 한다.

    이 회차의 지식이 다시 쓰이는 곳

    이 회차에서 프록시 안의 갈림길은 한쪽만 따라갔다. 공통 메서드는 마지막 인터셉터를 거쳐 SimpleJpaRepository에 도착한다. 다른 쪽 갈래, 곧 findByUsername처럼 공통 구현체에 없는 메서드를 쿼리 실행 인터셉터가 메서드 이름이나 @Query로 처리하는 길은 03회차에서 다룬다. 이 회차에서 @EnableJpaRepositories의 기본값으로 본 CREATE_IF_NOT_FOUND가 그때 다시 나온다.

    계층 그림의 PagingAndSortingRepository와 findAll(Pageable), 그리고 deleteAllInBatch에서 본 벌크 연산과 영속성 컨텍스트의 어긋남은 04회차의 페이징과 벌크성 수정 쿼리로 이어진다. 기본 설정 표의 repositoryImplementationPostfix = "Impl"은 05회차의 사용자 정의 리포지토리가 구현 조각을 찾는 규칙이다. 그리고 이 회차에서 "06회차에서 다룬다"고 미뤄 둔 두 가지, SimpleJpaRepository의 트랜잭션 설정과 save의 새 엔티티 판단은 06회차에서 구현체의 소스를 직접 읽으며 정리한다.

    더 넓게 보면 이 회차의 기법은 스프링 생태계 곳곳에서 반복된다. 클래스 파일을 로드하지 않고 메타데이터만 읽는 스캔, FactoryBean으로 복잡한 객체 생성을 감추는 등록, 인터페이스만 있는 타입을 JDK 동적 프록시로 구현하는 방식은 스프링 핵심 원리 고급편에서 프록시와 빈 후처리기를 다룰 때 일반적인 형태로 다시 만난다. 그리고 타입 소거를 피해 선언의 Signature에서 타입 인자를 읽는 기법은 스프링이 제네릭 타입으로 빈을 주입하거나 메시지 컨버터가 List 같은 타입을 다룰 때도 쓰이는 같은 원리다.
    순수 JPA 리포지토리의 반복
    EntityManager로 직접 쓴 리포지토리는 엔티티마다 거의 같다. 달라지는 정보는 엔티티 클래스와 식별자 타입 두 가지뿐이며, 엔티티 이름도 클래스에서 계산된다.
    타입 소거와 Signature 속성
    타입 인자는 객체에서 지워지므로 T.class는 컴파일되지 않는다. 하지만 상위 타입을 구체적인 타입 인자로 선언하면 그 선언은 클래스 파일의 Signature 속성에 남고, 스프링 데이터는 리포지토리 인터페이스에서 이것을 읽어 도메인 타입과 식별자 타입을 얻는다.
    설정과 기본 패키지
    순수 스프링에서는 @EnableJpaRepositories를 붙이고, 패키지를 생략하면 설정 클래스의 패키지를 쓴다. 스프링 부트는 JpaRepositoriesAutoConfiguration이 자동 구성 패키지(메인 클래스의 패키지)를 기준으로 같은 일을 한다.
    스캔과 빈 정의
    RepositoryComponentProvider가 ASM으로 클래스 파일을 읽어 Repository 상속 인터페이스와 @RepositoryDefinition을 고르고 @NoRepositoryBean을 뺀다. 인터페이스마다 클래스가 JpaRepositoryFactoryBean인 빈 정의가 등록된다.
    프록시의 정체
    주입되는 객체는 SimpleJpaRepository를 대상으로 하는 JDK 동적 프록시다. 예외 변환과 트랜잭션 인터셉터가 이미 들어 있으므로 인터페이스에 @Repository를 붙일 필요가 없다.
    인터페이스 계층
    Repository(마커) 아래에 CrudRepository와 PagingAndSortingRepository가 나란히 있고, 3.0부터 각각의 List 반환 버전이 있다. JpaRepository는 이들을 모두 상속하고 flush, 배치 삭제, 참조 조회 같은 JPA 고유 메서드를 더한다.
    이름이 비슷한 메서드의 차이
    findById는 즉시 조회, getReferenceById는 프록시 참조를 돌려준다. deleteAll은 읽고 하나씩 지우며, deleteAllInBatch는 영속성 컨텍스트를 건너뛴 벌크 DELETE 한 번이다. deleteById는 대상이 없으면 조용히 넘어간다.
    호출 하나가 트랜잭션 하나
    공통 구현체에 트랜잭션이 걸려 있어 트랜잭션 밖의 호출은 매번 새 영속성 컨텍스트에서 실행된다. 그래서 같은 식별자도 다른 객체로 나오고, 꺼낸 엔티티의 변경은 감지되지 않는다.

    실무에서 이 회차의 지식이 가장 먼저 쓰이는 곳은 "리포지토리 빈을 찾을 수 없다"는 시작 실패다. 멀티 모듈 프로젝트에서 리포지토리를 공용 모듈의 다른 패키지로 옮기거나, 메인 클래스를 하위 패키지로 옮긴 직후에 자주 생긴다. 원인은 거의 항상 자동 구성 패키지와 리포지토리 위치의 불일치다. 이때 @EnableJpaRepositories를 추가하면 자동 구성이 물러나므로, 엔티티 스캔(@EntityScan)도 함께 맞춰야 한다는 점까지 한 번에 판단할 수 있어야 한다. 반대로 "Not a managed type" 같은 메시지를 보면 도메인 타입 해석이 실패한 것이므로, 공통 부모 인터페이스에 @NoRepositoryBean이 빠졌는지, 엔티티가 엔티티 스캔 범위 안에 있는지를 먼저 본다.

    두 번째는 대량 삭제의 선택이다. 관리 화면에서 "전체 삭제"를 deleteAll()로 구현하면 행이 몇 개일 때는 아무 문제가 없다가, 수십만 행이 쌓인 운영 환경에서 전체를 메모리로 읽고 행마다 DELETE를 보내며 트랜잭션이 길어진다. 그렇다고 무조건 deleteAllInBatch()로 바꾸면 자식 엔티티의 cascade 삭제나 @PreRemove에 걸어 둔 감사 로그가 조용히 빠진다. 판단 기준은 "엔티티 단위의 부수 효과가 필요한가"이다. 필요하다면 엔티티 단위 삭제를 나누어 실행하고, 필요 없다면 벌크 삭제를 쓰되 같은 트랜잭션에서 이미 읽은 엔티티가 영속성 컨텍스트에 남는다는 점을 처리해야 한다.

    세 번째는 트랜잭션 경계다. 스프링 데이터 JPA를 처음 쓰면 리포지토리 메서드가 알아서 트랜잭션을 거니 서비스의 @Transactional을 빼도 된다고 생각하기 쉽다. 저장 한 번, 조회 한 번처럼 단일 호출로 끝나는 일이라면 실제로 동작한다. 그러나 조회한 엔티티를 바꾸는 순간 변경이 사라지고, 두 번의 저장 중 두 번째가 실패하면 첫 번째는 이미 커밋된 뒤다. 리포지토리 메서드 하나하나가 트랜잭션 하나라는 사실은 편의가 아니라 경계에 대한 정보로 읽어야 한다. 여러 리포지토리 호출이 하나의 업무 규칙을 이루면 그 묶음의 경계는 서비스가 정한다.
  • 트랜잭션이 없는 서비스 메서드에서 Member a = memberRepository.findById(1L).get();과 Member b = memberRepository.findById(1L).get();를 연달아 실행한다. a == b의 결과와 실행되는 SELECT의 개수를 예측하고, 서비스 메서드에 @Transactional을 붙이면 둘이 어떻게 바뀌는지 영속성 컨텍스트의 수명으로 설명하라.
  • 다음 코드는 회원 이름이 바뀌지 않는다는 버그 보고를 받았다. public void rename(Long id, String name) { Member m = memberRepository.findById(id).get(); m.changeUsername(name); } (클래스와 메서드에 @Transactional 없음). 원인을 설명하고, 변경 감지로 반영되게 하는 수정과 그 수정이 왜 동작하는지 써라.
  • 스프링 부트 애플리케이션에서 ctx.getBean("memberRepository")와 ctx.getBean("&memberRepository")가 각각 어떤 클래스의 객체를 돌려주는지, 그리고 memberRepository.save(...) 호출이 최종적으로 어느 클래스의 어떤 메서드에서 EntityManager의 어떤 메서드로 이어지는지 그림으로 그려라.
  • 공통 부모 인터페이스 interface BaseRepository extends JpaRepository에 @NoRepositoryBean을 붙이지 않았을 때 시작 단계에서 Not a managed type: class java.lang.Object가 나는 과정을 스캔, 빈 정의 등록, 팩토리 빈 초기화의 순서로 설명하라. 왜 하필 Object인가?
  • 회원 행이 1,000개인 테이블에서 같은 트랜잭션 안에 findAll()을 한 번 실행한 뒤 deleteAll()을 호출하는 경우와 deleteAllInBatch()를 호출하는 경우, 각각 실행되는 SQL의 개수와 호출 직후 영속성 컨텍스트에 남아 있는 엔티티의 상태를 비교하라.
    •

    1. a == b는 false이고 SELECT는 두 번 나간다. 서비스에 트랜잭션이 없으면 각 findById 호출이 리포지토리 프록시의 트랜잭션 인터셉터에서 각자 트랜잭션을 시작한다. JpaTransactionManager는 트랜잭션마다 새 EntityManager를 만들고 끝날 때 닫으므로, 두 호출은 서로 다른 영속성 컨텍스트에서 실행된다. 1차 캐시가 공유되지 않으니 두 번 다 DB에 가고, 서로 다른 인스턴스가 나온다. 서비스에 @Transactional을 붙이면 두 호출이 기본 전파 속성 REQUIRED로 바깥 트랜잭션에 참여하고 하나의 영속성 컨텍스트를 공유한다. 두 번째 findById는 em.find가 1차 캐시에서 첫 번째 객체를 돌려주므로 SELECT는 한 번, a == b는 true다. 이 회차의 실험에서 각각 outside tx same? false와 inside tx same? true로 확인했다.

    2. findById의 트랜잭션은 리포지토리 메서드가 반환될 때 끝나고, 그 영속성 컨텍스트도 닫힌다. 돌아온 m은 준영속 상태이므로 changeUsername으로 필드를 바꿔도 스냅샷과 비교해 UPDATE를 만들 주체가 없다. 수정은 rename 메서드(또는 서비스 클래스)에 @Transactional을 붙이는 것이다. 그러면 findById가 서비스의 트랜잭션에 참여해 같은 영속성 컨텍스트에서 엔티티를 읽고, 필드 변경 후 메서드가 끝나 커밋될 때 플러시가 일어나며 변경 감지가 update member set username=? where id=?를 만든다. 실험에서 트랜잭션 밖의 변경은 reloaded = before, 안의 변경은 reloaded2 = after였다. save(m)를 추가로 호출하는 것도 반영은 되지만 그것은 merge에 의한 병합이며 변경 감지가 아니다.

    3. getBean("memberRepository")는 JpaRepositoryFactoryBean.getObject()가 돌려준 JDK 동적 프록시(jdk.proxy2.$Proxy96 같은 이름, 번호는 환경마다 다름)를, getBean("&memberRepository")는 JpaRepositoryFactoryBean 자신을 돌려준다. save 호출은 프록시의 InvocationHandler(JdkDynamicAopProxy)로 들어가 어드바이스 체인을 차례로 지난다. 예외 변환, 트랜잭션(여기서 트랜잭션이 없으면 새로 시작), 기본 메서드 처리, 쿼리 실행 인터셉터(쿼리 메서드가 아니므로 통과), 구현 위임 인터셉터를 거쳐 대상인 SimpleJpaRepository.save에 도착한다. 그 안에서 isNew가 참이면 EntityManager.persist, 거짓이면 EntityManager.merge로 이어진다. 그림에는 컨테이너, 두 이름, 팩토리 빈, 프록시, 체인, 대상과 그 대상이 들고 있는 엔티티 정보와 EntityManager가 들어가야 한다.

    4. BaseRepository는 Repository를 상속한 인터페이스이므로 RepositoryComponentProvider의 포함 필터에 걸린다. @NoRepositoryBean이 없으니 제외 필터에도 걸리지 않는다. 그래서 baseRepository라는 이름으로 클래스가 JpaRepositoryFactoryBean인 빈 정의가 등록된다. 기본 부트스트랩 모드에서 컨테이너가 이 빈을 즉시 초기화하면 afterPropertiesSet이 getRepository를 호출하고, 메타데이터가 인터페이스의 Signature에서 도메인 타입을 읽으려 한다. 그런데 이 선언에서 JpaRepository의 타입 인자는 구체 클래스가 아니라 타입 변수 T다. 구체적인 타입이 정해진 적이 없으므로 T는 그 상한인 Object로 해석된다. 상한을 적지 않은 타입 변수의 상한은 Object다. 이어서 JpaMetamodelEntityInformation이 하이버네이트 메타모델에 Object의 정보를 묻고, 그런 엔티티는 없으므로 IllegalArgumentException: Not a managed type: class java.lang.Object가 난다.

    5. deleteAll()은 내부에서 findAll()을 다시 호출하므로 SELECT 1번이 나가고(앞의 findAll()까지 치면 2번), 1,000개의 엔티티를 하나씩 remove하므로 플러시 때 DELETE가 1,000번 나간다. 호출 직후 엔티티들은 영속성 컨텍스트 안에서 삭제 예정 상태이고, 플러시가 끝나면 컨텍스트에서 제거된다. deleteAllInBatch()는 delete from member m1_0 한 번으로 끝난다. 그러나 영속성 컨텍스트를 거치지 않으므로 앞의 findAll()로 올라온 1,000개의 엔티티는 DB에서 지워진 뒤에도 영속성 컨텍스트에 관리 상태로 그대로 남는다. 같은 트랜잭션에서 그 엔티티를 findById로 다시 찾으면 1차 캐시에서 이미 지워진 엔티티가 나온다. Javadoc이 경고하는 1차 캐시와 DB의 불일치가 이것이며, 필요하면 벌크 삭제 뒤에 영속성 컨텍스트를 비워야 한다.

     스프링 데이터 JPA가 interface MemberRepository extends JpaRepository을 보고 도메인 타입이 Member임을 알아내는 방법으로 옳은 것은? 프록시 객체를 만든 뒤 그 객체의 런타임 타입 인자를 읽는다. 개발자가 application.properties에 엔티티 클래스 이름을 적어 두어야 한다. 리포지토리 인터페이스의 클래스 파일에 남은 Signature 속성(제네릭 상위 타입 선언)을 리플렉션으로 읽는다. 인터페이스 이름에서 Repository를 뗀 Member를 엔티티 이름으로 추측한다. 타입 인자는 객체에서 지워지므로 객체(프록시든 무엇이든)를 들여다봐서는 알 수 없다. 그러나 상위 타입을 구체적인 타입 인자로 선언하면 그 선언은 클래스 파일의 Signature 속성에 남는다. 스프링 데이터의 DefaultRepositoryMetadata는 인터페이스에서 Repository까지 거슬러 올라간 상위 타입 정보의 타입 인자를 읽는다. 별도 설정은 필요 없고, 인터페이스 이름은 빈 이름을 정할 뿐 엔티티 타입 결정과 무관하다. 스프링 부트 3.5 애플리케이션에서 memberRepository 빈에 대한 설명으로 옳은 것은? 빈 정의의 클래스가 SimpleJpaRepository이고, 주입되는 객체도 SimpleJpaRepository 인스턴스다. 빈 정의의 클래스는 JpaRepositoryFactoryBean이고, 이름으로 요청하면 팩토리가 만든 JDK 동적 프록시가 나온다. 컴포넌트 스캔이 인터페이스에 붙은 @Repository를 보고 등록한 빈이다. 스프링 데이터가 컴파일 시점에 MemberRepositoryImpl 소스를 생성해 등록한 빈이다. 실험에서 빈 정의의 클래스는 JpaRepositoryFactoryBean, 생성자 인자는 인터페이스 이름이었다. FactoryBean이므로 이름으로 요청하면 getObject()의 결과인 프록시(jdk.proxy2.$Proxy...)가 나오고, SimpleJpaRepository는 그 프록시의 대상일 뿐이다. 등록은 컴포넌트 스캔이 아니라 스프링 데이터의 RepositoryComponentProvider가 하며 @Repository는 필요 없다. 소스 생성은 일어나지 않는다. 프록시는 실행 시점에 만들어진다. 트랜잭션 안에서 존재하지 않는 식별자 999로 memberRepository.getReferenceById(999L)를 호출했다(Hibernate 6.6 기준). 언제 무엇이 일어나는가? 호출 즉시 SELECT가 실행되고 null이 반환된다. 호출 즉시 SELECT가 실행되고 Optional.empty()가 반환된다. 호출 즉시 EmptyResultDataAccessException이 발생한다. 프록시가 반환되고, 식별자가 아닌 필드에 처음 접근할 때 SELECT가 실행되며 EntityNotFoundException이 발생한다. getReferenceById는 em.getReference를 호출하며, 하이버네이트는 DB에 가지 않고 식별자만 아는 프록시를 돌려준다. 실험에서 getId()에는 SQL이 없었고, 다른 필드에 처음 접근할 때 SELECT가 나간 뒤 행이 없으므로 EntityNotFoundException: Unable to find demo.Member with id 999가 발생했다. Optional.empty()는 findById의 동작이다. Spring Data 3.5에서 interface MemberPagingRepository extends PagingAndSortingRepository만 선언했다. 이 리포지토리에 대한 설명으로 옳은 것은? findAll(Pageable)과 findAll(Sort)는 있지만 save나 findById는 없다. PagingAndSortingRepository가 CrudRepository를 상속하므로 save도 함께 생긴다. JpaRepository를 상속하지 않았으므로 페이징 메서드가 동작하지 않는다. findAll()의 반환 타입이 List다. 3.5.13의 클래스 파일에서 PagingAndSortingRepository의 상위 타입은 Repository 하나뿐이다. 따라서 CRUD 메서드는 딸려 오지 않으며, 필요하면 CrudRepository(또는 ListCrudRepository)를 함께 상속해야 한다. 공통 메서드는 SimpleJpaRepository가 구현하므로 JpaRepository를 상속하지 않아도 동작한다. 인자 없는 findAll()은 이 인터페이스에 선언되어 있지 않다. 스프링 부트 애플리케이션의 메인 클래스가 com.example.app 패키지에 있고, 리포지토리 인터페이스를 com.example.repo 패키지에 두었다. 별도 설정이 없을 때 일어나는 일로 옳은 것은? 스프링 데이터는 클래스패스 전체를 스캔하므로 문제없이 주입된다. 리포지토리 빈은 등록되지만 트랜잭션이 적용되지 않는다. 자동 구성 패키지(com.example.app) 밖이므로 리포지토리가 스캔되지 않고, 그것을 주입받는 쪽에서 빈을 찾지 못해 시작이 실패한다. 리포지토리 인터페이스에 @Repository를 붙이면 컴포넌트 스캔으로 구현 없이 등록된다. 스프링 부트의 JpaRepositoriesAutoConfiguration은 AutoConfigurationPackages가 돌려주는 패키지, 곧 메인 클래스의 패키지와 그 하위만 스캔한다. 형제 패키지는 범위 밖이다. 컴포넌트 스캔은 구현 없는 인터페이스를 빈으로 만들지 못하므로 @Repository는 해결책이 아니다. @EnableJpaRepositories(basePackages = ...)로 위치를 지정하거나 패키지 구조를 바꿔야 하며, 엔티티도 밖에 있다면 @EntityScan이 필요하다.
    공통 인터페이스(common repository interface)
    스프링 데이터가 제공하는 CrudRepository, JpaRepository 같은 인터페이스. 상속만 하면 공통 구현체 SimpleJpaRepository가 그 메서드를 구현한다.
    타입 소거(type erasure)
    컴파일러가 제네릭 타입 정보를 지우는 규칙(JLS §4.6). 타입 변수는 상한으로, 매개변수화된 타입은 원시 타입으로 바뀌므로 실행 중인 객체는 자신의 타입 인자를 모른다.
    Signature 속성(Signature attribute)
    클래스 파일에 제네릭 선언을 보존하는 속성(JVMS §4.7.9). 실행에는 쓰이지 않지만 리플렉션의 getGenericInterfaces() 등이 이것을 읽는다.
    FactoryBean
    스프링 컨테이너에 등록되어 자신 대신 getObject()가 만든 객체를 빈으로 내주는 객체. 팩토리 자신은 빈 이름 앞에 &를 붙여 얻는다.
    자동 구성 패키지(auto-configuration package)
    @AutoConfigurationPackage가 등록한 패키지. 스프링 부트에서는 보통 @SpringBootApplication이 붙은 메인 클래스의 패키지이며, 리포지토리와 엔티티 스캔의 기준이 된다.
    JDK 동적 프록시(JDK dynamic proxy)
    지정한 인터페이스들을 구현하는 클래스를 런타임에 생성하고 모든 호출을 InvocationHandler로 넘기는 JDK 기능. 스프링 데이터 리포지토리 프록시가 이 방식으로 만들어진다.
    브리지 메서드(bridge method)
    공변 반환 타입이나 제네릭 오버라이딩 때문에 디스크립터가 달라진 메서드를 잇기 위해 컴파일러가 생성하는 합성 메서드. ACC_BRIDGE, ACC_SYNTHETIC 플래그가 붙는다.
    마커 인터페이스(marker interface)
    메서드 없이 타입 표식으로만 쓰이는 인터페이스. 스프링 데이터의 Repository는 다룰 타입을 붙잡고 스캔 대상을 고르는 데 쓰인다.
