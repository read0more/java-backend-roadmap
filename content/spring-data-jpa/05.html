    이 회차의 질문: 인터페이스 밖으로 나가야 할 때

    지금까지 이 권에서 본 스프링 데이터 JPA는 인터페이스 하나로 많은 것을 해결했다. JpaRepository를 상속하면 저장, 조회, 삭제가 생기고, 메서드 이름이나 @Query로 쿼리를 선언하면 구현 없이도 실행된다. 페이징과 벌크 수정, @EntityGraph까지 앞 회차에서 다뤘다. 그런데 실무 코드를 쓰다 보면 이 틀에 맞지 않는 요구가 곧 나온다. 조건이 화면 입력에 따라 달라지는 동적 쿼리, JDBC를 직접 써야 하는 대량 처리, 이름 규칙으로는 도저히 표현되지 않는 복잡한 조회가 그런 예다.

    문제는 리포지토리 바깥에도 있다. 거의 모든 테이블에 "언제 만들어졌고 언제 마지막으로 바뀌었는가, 누가 만들고 누가 바꿨는가"를 남기고 싶다. 엔티티마다 같은 필드를 선언하고 저장과 수정 코드마다 시각을 넣는 일은 지루하고, 한 곳만 빠뜨려도 데이터가 틀어진다. 웹 계층에서는 컨트롤러마다 경로 변수로 받은 식별자로 findById를 부르고, page와 size와 sort 파라미터를 꺼내 검사하고 PageRequest를 만드는 코드가 반복된다.

    스프링 데이터는 이 세 종류의 문제에 각각 확장 기능을 준비해 두었다. 이 회차는 그것들을 하나씩 다루되, 사용법보다 각 기능이 어떤 기존 메커니즘 위에 올라가 있는가에 무게를 둔다. 그래야 기능이 기대와 다르게 움직일 때 원인을 찾을 수 있다. 아래 표가 이 회차의 지도다.

    출발점: 리포지토리 프록시 안의 호출 경로

    사용자 정의 리포지토리를 이해하려면 먼저 "인터페이스 메서드를 부르면 무엇이 실행되는가"를 정확히 알아야 한다. 주입받은 리포지토리 객체를 Advised로 캐스팅하면 스프링 AOP 프록시의 구성을 들여다볼 수 있다. 아래는 ArticleRepository를 주입받아 클래스, 구현 인터페이스, 대상 객체, 어드바이스 목록을 출력한 결과다.

interfaces = [interface lab.ArticleRepository, interface org.springframework.data.repository.Repository,
              interface org.springframework.transaction.interceptor.TransactionalProxy,
              interface org.springframework.aop.framework.Advised, interface org.springframework.core.DecoratingProxy]
target = class org.springframework.data.jpa.repository.support.SimpleJpaRepository

    프록시 클래스 이름 jdk.proxy3.$Proxy138은 JDK 동적 프록시라는 뜻이고, 뒤의 번호는 그 JVM에서 프록시 클래스가 만들어진 순서에 따라 달라진다. 대상(target)은 SimpleJpaRepository 인스턴스 하나다. 그 앞에 일곱 개의 어드바이스가 순서대로 서 있다. 호출은 위에서 아래로 흐르고, 각 어드바이스는 자기 일을 한 뒤 proceed()로 다음 어드바이스에 넘기거나, 스스로 결과를 만들어 돌아간다. 예외 변환 인터셉터(PersistenceExceptionTranslationInterceptor)는 목록에 두 번 나타난다.

    이 회차에 중요한 것은 아래쪽 두 개다. QueryExecutorMethodInterceptor는 호출된 메서드가 쿼리 메서드인지 본다. 메서드 이름으로 유도한 쿼리나 @Query로 선언한 쿼리처럼, 리포지토리를 만들 때 미리 준비해 둔 쿼리 객체가 있으면 그것을 실행하고 체인을 끝낸다. 쿼리 메서드가 아니면 다음으로 넘긴다. 그 다음인 ImplementationMethodExecutionInterceptor는 호출을 RepositoryComposition에 맡긴다. 이 "조합"이 바로 구현 조각(fragment)들의 목록이고, 사용자 정의 구현 클래스와 기본 구현인 SimpleJpaRepository가 모두 이 안에서 메서드 시그니처로 찾아진다.

      articleRepository.findPopular(10)
          │
          ▼
  JDK 동적 프록시 ($Proxy138)
          │  어드바이스 체인 (위 → 아래)
          ├─ CrudMethodMetadataPopulatingMethodInterceptor
          ├─ PersistenceExceptionTranslationInterceptor   ← 예외를 DataAccessException으로
          ├─ TransactionInterceptor                       ← 메서드별 트랜잭션 속성 조회
          ├─ DefaultMethodInvokingMethodInterceptor       ← 인터페이스 default 메서드
          ├─ QueryExecutorMethodInterceptor               ← 쿼리 메서드면 여기서 실행하고 끝

                    ▼

              ├─ ArticleRepositoryCustomImpl   ← 사용자 정의 조각
              └─ SimpleJpaRepository           ← 기본 구현

    정리하면 리포지토리 인터페이스의 메서드는 세 부류로 나뉜다. 쿼리 메서드는 QueryExecutorMethodInterceptor가 처리하고, 인터페이스의 default 메서드는 DefaultMethodInvokingMethodInterceptor가 처리하며, 나머지는 조각 중 하나가 구현하고 있어야 한다. 사용자 정의 리포지토리는 이 세 번째 부류에 우리가 직접 만든 조각을 끼워 넣는 기능이다.

    리포지토리 메서드 호출이 프록시의 어드바이스 체인을 지나 쿼리 실행 또는 조각 조합으로 갈라지는 구조를 보여 준다. 가로 16:9 구조도. 왼쪽에 "articleRepository.findPopular(10)"라고 적힌 호출 화살표가 들어온다. 가운데에 세로로 긴 상자 "리포지토리 프록시"가 있고, 그 안에 위에서 아래로 작은 띠 다섯 개가 쌓여 있다: "예외 변환", "트랜잭션", "default 메서드", "쿼리 메서드 실행", "구현 조각 실행". "쿼리 메서드 실행" 띠에서 오른쪽 위로 화살표가 나가 "미리 만든 쿼리 객체" 상자로 간다. "구현 조각 실행" 띠에서 오른쪽 아래로 화살표가 나가 "RepositoryComposition" 상자로 가며, 그 상자 안에 위에서 아래로 "사용자 정의 조각"과 "SimpleJpaRepository" 두 칸이 있다. 사용자 정의 조각 칸이 위에 있고 굵은 테두리로 우선순위가 높음을 표시한다. 차분한 파랑·회색 톤, 평면 벡터 스타일. 쿼리 메서드가 아닌 호출은 조각 조합으로 넘어가고, 사용자 정의 조각이 기본 구현보다 먼저 검사된다.

    사용자 정의 리포지토리: 조각 인터페이스와 Impl 클래스

    사용자 정의 조각은 인터페이스 하나와 구현 클래스 하나로 만든다. 먼저 직접 구현할 메서드만 모은 조각 인터페이스(fragment interface)를 선언한다. 아래 예제는 조회수가 기준 이상인 게시글을 많이 읽힌 순서로 돌려주는 조회와, 트랜잭션 동작을 실험하기 위한 저장 메서드 두 개를 담았다.

    public interface ArticleRepositoryCustom {
    List
     findPopular(int minViews);
    Article insertDirect(String title);
    Article insertDirectTx(String title);
}

    구현 클래스의 이름은 조각 인터페이스 이름 뒤에 Impl을 붙인 것이어야 한다. 이 클래스는 평범한 스프링 빈으로 등록되므로 생성자로 EntityManager나 JdbcTemplate, 다른 빈을 주입받을 수 있다. 주입되는 EntityManager는 스프링이 만든 공유 프록시이고, 실제 호출 시점의 트랜잭션에 묶인 영속성 컨텍스트로 위임한다는 점은 앞 권들에서 본 그대로다.

    public class ArticleRepositoryCustomImpl implements ArticleRepositoryCustom {
    private final EntityManager em;

    public ArticleRepositoryCustomImpl(EntityManager em) { this.em = em; }

    @Override
    public List
     findPopular(int minViews) {
        return em.createQuery(
                "select a from Article a where a.views >= :min order by a.views desc", Article.class)
            .setParameter("min", minViews)
            .getResultList();
    }

    @Override
    public Article insertDirect(String title) {          // 트랜잭션 없음
        Article article = new Article(title, 0);
        em.persist(article);
        return article;
    }

    @Override
    @Transactional
    public Article insertDirectTx(String title) {        // 구현 클래스에 직접 선언
        Article article = new Article(title, 0);
        em.persist(article);
        return article;
    }
}

    마지막으로 리포지토리 인터페이스가 조각 인터페이스를 함께 상속한다. 이것으로 끝이다. 클라이언트 코드는 articleRepository.findPopular(10)처럼 다른 메서드와 똑같이 부른다.

    public interface ArticleRepository extends JpaRepository, ArticleRepositoryCustom {
}

    구현 클래스는 어떻게 찾아지는가

    스프링 데이터 공식 문서(Custom Repository Implementations)가 정한 규칙은 다음과 같다. 리포지토리 인프라는 리포지토리를 찾은 패키지 아래를 스캔해서, 조각 인터페이스 이름에 접미사를 붙인 이름의 클래스를 구현으로 감지한다. 접미사의 기본값은 Impl이고 @EnableJpaRepositories(repositoryImplementationPostfix = "…")로 바꿀 수 있다. 스캔 범위가 리포지토리 기본 패키지로 한정되므로, 다른 패키지나 외부 jar에 있는 조각은 spring.factories에 등록하는 별도 방법을 써야 한다고 문서는 덧붙인다. 같은 이름의 구현 클래스가 서로 다른 패키지에서 여러 개 발견되면 빈 이름으로 어느 것을 쓸지 결정한다.

    실험에서 구현 클래스는 articleRepositoryCustomImpl이라는 이름의 빈으로 등록되었다. 문서도 조각 인터페이스 이름에 Impl을 붙인 빈 이름을 예로 든다. 그런데 이 빈의 실제 클래스를 출력하면 lab.ArticleRepositoryCustomImpl$$SpringCGLIB$$0이 나온다. insertDirectTx에 @Transactional을 붙였기 때문에, 이 구현 빈 자체도 스프링의 자동 프록시 생성기에 의해 CGLIB 프록시로 감싸진 것이다. 즉 사용자 정의 구현은 "리포지토리 프록시의 조각"이면서 동시에 "AOP가 적용되는 평범한 빈"이다. 이 이중 신분이 뒤에서 볼 트랜잭션 동작의 열쇠다.

    예전 방식도 있다. 조각 인터페이스 이름이 아니라 리포지토리 인터페이스 이름에 Impl을 붙인 클래스(ArticleRepositoryImpl implements ArticleRepositoryCustom)를 구현으로 쓰는 방식이다. Spring Data JPA 3.5.13에서 구현 클래스 이름만 이렇게 바꿔 실행해 보면 여전히 동작했다(빈 이름 articleRepositoryImpl). 다만 공식 문서는 이 단일 사용자 정의 구현 명명을 "deprecated로 간주한다"고 적고, 조각 기반 모델로 옮길 것을 권한다. 새 코드는 조각 인터페이스 이름 + Impl 규칙을 따르는 편이 맞다. 그래야 조각 인터페이스를 여러 개 두고 리포지토리마다 골라 조합할 수 있다.

    조각의 우선순위: 기본 구현의 메서드를 덮어쓰기

    같은 문서는 조각의 순서에 대해 두 가지를 말한다. 리포지토리는 여러 사용자 정의 구현으로 조합될 수 있고 선언 순서대로 들어간다. 그리고 사용자 정의 구현은 기본 구현과 리포지토리 애스펙트보다 우선순위가 높다. 따라서 기본 구현에 있는 메서드와 같은 시그니처를 조각에 선언하면, 기본 구현의 메서드 대신 조각의 메서드가 호출된다. 이를 확인하기 위해 제네릭 조각을 하나 만들어 Memo 리포지토리에 붙였다.

    public interface CustomizedSave {
     S save(S entity);
}

public class CustomizedSaveImpl implements CustomizedSave {
    private final EntityManager em;

    public CustomizedSaveImpl(EntityManager em) { this.em = em; }

    @Override
    @Transactional

    사용자 정의 리포지토리를 쓸 곳과 쓰지 않을 곳

    반대로 특정 화면 하나를 위한 복잡한 조회, 여러 엔티티를 가로질러 DTO를 조립하는 조회까지 모두 리포지토리 조각으로 밀어 넣으면, 핵심 엔티티의 리포지토리가 화면의 요구에 따라 계속 불어난다. 이런 조회는 조각으로 만들 필요 없이 @Repository를 붙인 별도 조회 클래스로 분리하는 편이 낫다. 그 클래스는 사용자 정의 조각이 아니므로 이름 규칙의 제약을 받지 않고, 빈이므로 주입과 AOP는 똑같이 누린다. 사용자 정의 리포지토리는 "인터페이스 하나로 쓰게 해 주는 편의"이지 모든 쿼리 코드가 들어가야 하는 자리가 아니다.

    Auditing 1: JPA 엔티티 콜백으로 직접 만들기

    이제 두 번째 확장 기능으로 넘어간다. 등록일과 수정일을 자동으로 남기는 일은 스프링 데이터 없이 JPA만으로도 할 수 있다. JPA는 엔티티의 생명주기 사건에 맞춰 호출되는 콜백 메서드(lifecycle callback)를 정의한다. @PrePersist, @PostPersist, @PreUpdate, @PostUpdate, @PreRemove, @PostRemove, @PostLoad가 그것이다. 공통 필드와 콜백을 @MappedSuperclass에 모아 두면 상속받는 모든 엔티티가 같은 동작을 얻는다.

    @MappedSuperclass
public abstract class JpaBaseEntity {
    @Column(updatable = false)
    private LocalDateTime createdDate;
    private LocalDateTime updatedDate;

    @PrePersist
    public void prePersist() {
        LocalDateTime now = LocalDateTime.now();
        createdDate = now;
        updatedDate = now;
        System.out.println("[callback] @PrePersist");
    }

    @PreUpdate
    public void preUpdate() {
        updatedDate = LocalDateTime.now();
        System.out.println("[callback] @PreUpdate");
    }
    // getter ...
}

@Entity
public class Memo extends JpaBaseEntity {
    @Id @GeneratedValue
    private Long id;
    private String text;
    // 생성자, changeText(String) ...
}

    콜백이 정확히 언제 불리는지 보려고, 한 트랜잭션 안에서 persist와 여러 번의 flush를 섞어 실행했다. 두 번째 플러시는 아무것도 바꾸지 않은 상태, 그 다음은 changeText("hello")로 원래와 같은 값을 다시 넣은 상태, 마지막은 실제로 값을 바꾼 상태다.

    -- persist
select next value for memo_seq
[callback] @PrePersist
after persist created? true
-- flush 1
insert into memo (created_date,text,updated_date,id) values (?,?,?,?)
-- flush 2 (no change)
-- flush 2b (same value)
-- flush 3 (changed)
[callback] @PreUpdate
update memo set text=?,updated_date=? where id=?

    네 가지를 읽을 수 있다. 첫째, @PrePersist는 persist() 호출 안에서 실행되었고 INSERT는 그보다 늦게 플러시 때 나갔다. Jakarta Persistence 3.1 명세 3.5.3절은 PrePersist 콜백이 해당 엔티티에 대한 persist 연산이 실행되기 전에 호출된다고 정한다. 콜백은 "SQL 직전"이 아니라 "연산 직전"에 묶여 있다. 둘째, 이 실행에서는 시퀀스 값을 먼저 가져온 뒤 콜백이 불렸다. 명세는 생성된 기본 키 값이 PostPersist에서 사용 가능하다고만 보장하므로, PrePersist에서 식별자가 채워져 있는지는 구현체와 식별자 전략에 달린 문제이고 거기에 기대는 코드는 쓰지 않는 편이 안전하다.

    셋째, @PreUpdate는 값이 실제로 바뀐 플러시에서만 불렸다. 아무것도 바꾸지 않은 플러시와 같은 값을 다시 넣은 플러시에서는 콜백도 UPDATE도 없었다. Hibernate는 플러시 때 엔티티의 현재 상태를 로딩 시점의 스냅샷과 비교하는 변경 감지(dirty checking)로 UPDATE 대상을 고르고, @PreUpdate는 그 UPDATE가 결정된 엔티티에 대해 호출된다. 명세 3.5.3절도 PreUpdate와 PostUpdate가 데이터베이스 갱신 연산의 앞뒤에서 일어나며, 그 갱신은 상태가 바뀌는 시점에 일어날 수도 있고 플러시 시점(트랜잭션 끝일 수도 있다)에 일어날 수도 있다고 적는다. 넷째, UPDATE 문에 created_date가 없다. @Column(updatable = false)가 그 컬럼을 UPDATE 문에서 빼 버렸기 때문이다.

    이 방식으로도 등록일과 수정일은 충분히 관리된다. 부족한 것은 "누가"다. 등록자와 수정자를 남기려면 콜백 안에서 현재 사용자를 알아야 하는데, 엔티티는 스프링 빈이 아니어서 인증 정보를 가진 빈을 주입받을 수 없다. 스프링 데이터 JPA의 Auditing은 바로 이 지점을 메워 준다.

    Auditing 2: 스프링 데이터 JPA의 감사 기능

    스프링 데이터는 감사 정보를 표시하는 애너테이션 네 개를 제공한다. 생성 시각 @CreatedDate, 마지막 수정 시각 @LastModifiedDate, 생성자 @CreatedBy, 마지막 수정자 @LastModifiedBy다. 공식 문서에 따르면 시각 애너테이션은 JDK 8 날짜·시간 타입, long/Long, 레거시 Date와 Calendar 타입 필드에 붙일 수 있다. 엔티티 쪽 준비는 이 애너테이션을 단 필드와, 엔티티 리스너 등록 하나다.

    @MappedSuperclass
@EntityListeners(AuditingEntityListener.class)
public abstract class BaseTimeEntity {
    @CreatedDate
    @Column(updatable = false)
    private LocalDateTime createdDate;

    @LastModifiedDate
    private LocalDateTime lastModifiedDate;
    // getter ...
}

@MappedSuperclass
public abstract class BaseEntity extends BaseTimeEntity {
    @CreatedBy
    @Column(updatable = false)
    private String createdBy;

    @LastModifiedBy
    private String lastModifiedBy;
    // getter ...
}

@Entity
public class Article extends BaseEntity {
    @Id @GeneratedValue
    private Long id;
    private String title;
    private int views;
    // 생성자, changeTitle(String), getter ...
}

    시각만 필요한 테이블과 사용자까지 필요한 테이블이 섞여 있는 경우가 많아서, 위처럼 시각만 담은 BaseTimeEntity와 사용자까지 담은 BaseEntity로 계층을 나누면 엔티티마다 필요한 쪽을 고를 수 있다. 설정 쪽에서는 @EnableJpaAuditing으로 기능을 켜고, 등록자·수정자를 채울 AuditorAware 빈을 하나 등록한다.

    @SpringBootApplication
@EnableJpaAuditing
public class LabApplication {
    public static void main(String[] args) { SpringApplication.run(LabApplication.class, args); }

    @Bean
    AuditorAware auditorProvider() {
        return () -> Optional.of("user-1");   // 실제로는 현재 요청의 인증 정보에서 꺼낸다
    }
}

    AuditorAware는 Optional을 돌려주는 메서드 getCurrentAuditor() 하나뿐인 인터페이스다. 공식 문서는 이 타입의 빈을 애플리케이션 컨텍스트에 노출하면 감사 인프라가 자동으로 찾아 쓴다고 설명하고, 여러 개라면 @EnableJpaAuditing(auditorAwareRef = "…")로 고르라고 한다. 이제 앞 절과 같은 순서로 게시글을 저장하고 플러시하며 값을 관찰했다.

    before save: created=null
select next value for article_seq
after save: created=true, modified==created true, by=user-1/user-1
-- flush 1
insert into article (created_by,created_date,last_modified_by,last_modified_date,title,views,id) values (?,?,?,?,?,?,?)
-- flush 2 (no change)
modified changed? false
after setter, modified changed? false
-- flush 3 (title changed)
update article set last_modified_by=?,last_modified_date=?,title=?,views=? where id=?
after flush, modified changed? true

    저장 직후 네 필드가 모두 채워졌고, 수정 시각은 생성 시각과 같은 값이며 수정자도 생성자와 같다. 생성 시점에 수정 정보까지 채우는 것은 @EnableJpaAuditing의 modifyOnCreate 속성 때문이다. 애너테이션 클래스의 바이트코드로 확인한 기본값은 true이고, @EnableJpaAuditing(modifyOnCreate = false)로 바꿔 같은 실험을 하면 저장 직후 결과가 modified=null, by=user-1/null로 바뀌었다. 수정 시각 컬럼이 "생성 이후 한 번도 수정되지 않았으면 null"이기를 원하는지, "항상 값이 있어 정렬과 비교가 쉬운 편"을 원하는지에 따라 고르면 된다. 대부분은 기본값처럼 생성 시 함께 채우는 쪽이 조회 조건을 단순하게 만든다.

    나머지 줄은 순수 JPA 콜백과 같은 이야기를 한다. 아무것도 바꾸지 않은 플러시는 수정 시각을 바꾸지 않았다. changeTitle을 호출한 직후에도 수정 시각은 그대로였고, 실제로 바뀐 것은 플러시 때 UPDATE가 결정된 뒤였다. 즉 기록되는 수정 시각은 setter를 부른 시각이 아니라 플러시 시각이다. 그리고 UPDATE 문에는 last_modified_by와 last_modified_date가 실려 있지만 updatable = false를 붙인 created_* 컬럼은 없다.

    시각은 어디서 오는가. 공식 문서는 시각을 주는 객체가 DateTimeProvider이고 기본은 CurrentDateTimeProvider이며, dateTimeProviderRef 속성이나 별도 빈으로 바꿀 수 있다고 설명한다. Spring Data Commons 3.5.13의 CurrentDateTimeProvider.getNow()를 역어셈블하면 LocalDateTime.now()를 Optional.of로 감싸 돌려주는 것이 전부다. 시스템 기본 시간대의 지역 시각이라는 뜻이므로, 서버 시간대가 서로 다른 환경에서는 그 차이가 그대로 저장된다. 테스트에서 시각을 고정하고 싶을 때도 이 DateTimeProvider를 갈아 끼우는 것이 정해진 방법이다.

    엔티티마다 @EntityListeners를 붙이기 싫다면 META-INF/orm.xml에 기본 엔티티 리스너로 등록할 수 있다. 공식 문서가 제시하는 형태는 다음과 같고, 이렇게 하면 영속성 단위의 모든 엔티티에 리스너가 적용된다.

    AuditingEntityListener는 스프링 빈을 어떻게 얻는가

    앞 절 끝에서 엔티티는 스프링 빈이 아니라서 현재 사용자를 알 수 없다고 했다. 엔티티 리스너도 사정이 비슷하다. 리스너 인스턴스를 만들어 콜백을 부르는 쪽은 JPA 구현체이고, 명세 3.5.1절은 엔티티 리스너 클래스에 public 기본 생성자가 있어야 한다고 정한다. 그런데 AuditingEntityListener는 어떻게 스프링 빈인 AuditorAware에 도달하는가. AuditorAware 람다 안에서 스택을 한 번 찍어 보면 호출 경로가 보인다.

    주입할 내용은 @EnableJpaAuditing이 가져오는 JpaAuditingRegistrar가 준비한다. 바이트코드를 보면 이 등록기는 org.springframework.context.config.internalBeanConfigurerAspect라는 이름으로 AnnotationBeanConfigurerAspect 빈을 등록하고, AuditingEntityListener 클래스 이름을 id로 하는 빈 정의에 auditingHandler 속성(핸들러를 지연 조회하는 ObjectFactory)을 넣어 둔다. @Configurable 객체는 기본적으로 자기 클래스의 완전한 이름과 같은 빈 정의를 설정 정보로 쓰므로, 리스너가 생성되면 이 빈 정의대로 핸들러가 꽂힌다. 등록기 안에는 애스펙트 클래스를 찾지 못했을 때 쓰는 문구 "spring-aspects.jar is not on the classpath"도 들어 있다. 공식 문서가 Auditing에 spring-aspects.jar가 필요하다고 적는 이유가 이것이다. 스프링 부트를 쓰면 따로 챙길 필요는 없다. spring-boot-starter-data-jpa 3.5.16의 POM이 spring-aspects를 직접 의존성으로 선언하고 있다.

    Auditing이 기록하지 못하는 변경

    Auditing은 JPA 엔티티 콜백 위에 올라간 기능이다. 이 한 문장에서 Auditing의 한계가 모두 나온다. 콜백은 영속성 컨텍스트가 관리하는 엔티티의 persist와 플러시 UPDATE에서만 불린다. 영속성 컨텍스트를 거치지 않는 변경은 감사 정보도 남기지 않는다.

    가장 흔한 예가 04회에서 본 벌크 수정이다. 앞의 실험 끝에 JPQL 벌크 수정을 실행하면 Hibernate가 보낸 SQL은 다음 한 줄이었다.

    -- bulk update
update article a1_0 set views=(a1_0.views+1)

    SQL에 last_modified_date도 last_modified_by도 없다. 벌크 연산은 엔티티를 하나씩 로딩해 바꾸는 것이 아니라 SQL 하나로 데이터베이스를 직접 바꾸므로, 엔티티 단위 콜백이 끼어들 자리가 없다. 네이티브 쿼리, JdbcTemplate, 다른 애플리케이션이나 DBA의 직접 수정도 마찬가지다. 벌크 수정 후에도 수정 시각이 정확해야 한다면 JPQL에 set a.lastModifiedDate = :now처럼 직접 넣어야 하고, 그 값은 스프링 데이터가 아니라 코드가 책임진다.

    둘째, 앞에서 본 대로 수정 시각은 플러시 시각이다. 긴 트랜잭션 초반에 값을 바꾸고 끝에서 커밋하면, 기록되는 시각은 커밋 직전 플러시의 시각이다. 대개 차이는 무시할 만하지만, "사용자가 버튼을 누른 시각" 같은 업무상 의미가 있는 시각을 수정 시각 컬럼으로 대신해서는 안 되는 이유가 된다. 업무 시각은 업무 필드로 따로 둔다.

    셋째, 같은 값을 다시 넣거나 아무것도 바꾸지 않으면 UPDATE가 없으므로 수정 시각도 수정자도 그대로다. "저장 버튼을 눌렀으면 수정 시각이 바뀌어야 한다"는 요구라면 변경 감지에 기대서는 안 된다. 넷째, AuditorAware는 콜백이 실행되는 스레드, 곧 생성 때는 persist를, 수정 때는 플러시를 실행하는 스레드에서 호출된다. 흔히 현재 사용자는 요청 스레드에 묶인 스레드 로컬(스프링 시큐리티의 보안 컨텍스트 같은 것)에서 꺼내는데, 저장과 플러시가 다른 스레드에서 일어나는 구조(예: 비동기 작업에서 엔티티를 저장)라면 그 스레드에는 사용자 정보가 없을 수 있다. 이 경우 Optional.empty()를 돌려주면 수정자 필드는 채워지지 않는다.

    마지막으로 updatable = false의 의미를 짚어 두자. 실행 기록의 UPDATE 문에서 생성 시각과 생성자 컬럼이 빠진 것은 이 설정 때문이다. 어떤 이유로든 엔티티의 createdDate 필드 값이 바뀌어도(예를 들어 생성 필드를 모르는 DTO에서 값을 복사해 병합했을 때) 그 변경은 SQL에 실리지 않는다. 생성 정보는 한 번 쓰면 바뀌지 않아야 하므로, 엔티티 매핑에서 그 불변성을 데이터베이스 쪽까지 지키는 장치로 쓰는 것이다.

    Web 확장 1: 도메인 클래스 컨버터

    세 번째 확장은 웹 계층의 반복을 줄인다. 경로 변수로 식별자를 받아 리포지토리에서 찾는 컨트롤러 코드는 거의 모든 프로젝트에 있다. 도메인 클래스 컨버터를 쓰면 메서드 파라미터 타입을 엔티티로 선언하는 것만으로 이 조회가 끝난다.

    @GetMapping("/articles/{id}")
public String findOne(@PathVariable("id") Article article) {
    return article.getId() + ":" + article.getTitle();
}

    무엇이 이 변환을 하는가. 스프링 부트 3.5.16의 SpringDataWebAutoConfiguration은 클래스에 @EnableSpringDataWebSupport를 달고 있다(바이트코드로 확인). 공식 문서에 따르면 이 애너테이션은 몇 가지 구성 요소를 등록하는데, 그중 하나가 리포지토리가 관리하는 도메인 클래스를 요청 파라미터나 경로 변수에서 바로 얻게 해 주는 DomainClassConverter이고, 또 하나가 다음 절에서 볼 Pageable·Sort 인자 해석기다. DomainClassConverter는 스프링 MVC가 쓰는 ConversionService에 자신을 등록한다. 그래서 @PathVariable이나 @RequestParam의 문자열 값을 파라미터 타입으로 바꾸는 평범한 타입 변환 단계에서 끼어들 수 있다.

    변환 자체는 내부 클래스 DomainClassConverter.ToEntityConverter가 한다. Spring Data Commons 3.5.13의 convert 메서드가 호출하는 메서드들을 바이트코드에서 뽑아 보면 순서가 드러난다.

    1. 원본 값이 비었으면(StringUtils.hasText가 false) 바로 null을 돌려준다.
    2. Repositories에서 대상 도메인 타입(여기서는 Article)을 관리하는 리포지토리 정보를 찾고, 그 리포지토리의 식별자 타입(Long)을 얻는다.
    3. ConversionService로 문자열을 식별자 타입으로 바꾼다. "1"이 1L이 된다.
    4. RepositoryInvoker.invokeFindById(id)로 리포지토리의 findById를 부르고, 결과 Optional에 orElse(null)을 적용한다.

    공식 문서는 리포지토리가 CrudRepository를 구현해야 변환 대상으로 발견된다고 적는다. 반대 방향, 즉 엔티티를 식별자로 바꾸는 ToIdConverter도 같은 클래스 안에 들어 있다. 이제 세 가지 요청을 보내 결과를 보자.

    [one]       GET /articles/1      status=200 body=1:a1
[missing]   GET /articles/999999 status=400
            ex=MissingPathVariableException: Required URI template variable 'id' for method parameter type Article
               is present but converted to null
[notNumber] GET /articles/abc    status=400
            ex=MethodArgumentTypeMismatchException: Method parameter 'id': Failed to convert value of type
               'java.lang.String' to required type 'lab.Article'; Failed to convert from type [java.lang.String]

    존재하는 식별자는 SELECT 한 번으로 엔티티가 되어 들어왔다. 존재하지 않는 식별자는 변환 결과가 null이었고, 필수 경로 변수가 "있는데 변환 결과가 null"이라는 이유로 MissingPathVariableException이 나며 400 응답이 되었다. 숫자가 아닌 값은 식별자 타입 변환 단계에서 실패해 MethodArgumentTypeMismatchException, 역시 400이다. 존재하지 않는 리소스는 보통 404로 응답하는 것이 맞으므로, 이 기본 동작을 그대로 API 응답으로 내보낼지는 따로 판단해야 한다. 컨버터를 쓰더라도 404가 필요하면 예외 처리기에서 이 예외를 404로 바꾸거나, 컨버터 대신 식별자를 받아 직접 조회하는 편이 의도를 더 잘 드러낸다.

    컨버터로 받은 엔티티를 고치면 무슨 일이 생기는가

    도메인 클래스 컨버터에 대해 흔히 "조회용으로만 쓰라"는 조언을 듣는다. 이유를 추측하지 말고 실험으로 보자. 컨버터로 받은 게시글의 제목을 컨트롤러에서 바꾸고, 그 다음 트랜잭션이 걸린 서비스 메서드를 하나 부른다. 서비스 메서드는 게시글과 무관한 일, 여기서는 count()만 한다.

    @PostMapping("/articles/{id}/title")
public String rename(@PathVariable("id") Article article, @RequestParam("title") String title) {
    boolean managed = em.contains(article);
    String readOnly = managed ? String.valueOf(em.unwrap(Session.class).isReadOnly(article)) : "n/a";
    article.changeTitle(title);
    articleService.touch();                 // @Transactional, 내부에서 articleRepository.count()

}

    스프링 부트의 기본값(spring.jpa.open-in-view=true, 메타데이터의 기본값도 True)으로 실행한 결과다.

    컨트롤러에서 바꾼 제목이 데이터베이스에 저장되었다. 감사 필드까지 갱신되어 마치 정상적인 수정처럼 기록이 남았다. 서비스 메서드는 게시글을 건드리지도 않았는데 UPDATE가 나간 것이다. UPDATE가 count 쿼리보다 먼저 나온 것은 Hibernate가 쿼리를 실행하기 전에, 그 쿼리가 읽는 테이블에 걸린 변경을 먼저 플러시했기 때문이다(플러시 모드 AUTO).

    왜 이렇게 되는가. JPA 활용 2에서 본 대로 OSIV(Open Session In View)가 켜져 있으면 OpenEntityManagerInViewInterceptor가 요청이 시작될 때 EntityManager를 만들어 스레드에 묶고, 요청이 끝날 때 닫는다. 컨버터가 부른 findById는 SimpleJpaRepository의 읽기 전용 트랜잭션 안에서 실행되지만, 그 트랜잭션은 이미 스레드에 묶인 EntityManager를 그대로 쓴다. 트랜잭션이 끝나도 EntityManager는 닫히지 않으니 게시글은 여전히 영속 상태다(managed=true). 이후 같은 요청에서 시작되는 쓰기 트랜잭션도 같은 EntityManager를 쓰므로, 그 트랜잭션의 플러시가 컨트롤러에서 바뀐 게시글을 변경 감지로 찾아낸다.

    그렇다면 findById가 읽기 전용 트랜잭션이었다는 점은 아무 효과가 없었나. 실험의 readOnly=false가 그렇다고 말한다. Spring Framework 6.2.19의 바이트코드에서 원인을 찾을 수 있다. HibernateJpaDialect.beginTransaction은 Hibernate 세션에 setDefaultReadOnly(true)를 거는데, 그 조건이 세 가지다. 트랜잭션 정의가 ResourceTransactionDefinition이고, 그 isLocalResource()가 참이며, 읽기 전용일 것. 그리고 JpaTransactionManager.doBegin은 이 정의(JpaTransactionDefinition)를 만들 때 localResource 자리에 isNewEntityManagerHolder(), 즉 "이 트랜잭션을 위해 EntityManager를 새로 만들었는가"를 넘긴다. OSIV 아래에서는 EntityManager가 미리 묶여 있으므로 이 값이 거짓이고, 세션 기본 읽기 전용 설정이 적용되지 않는다. 그래서 그 트랜잭션에서 로딩한 엔티티도 스냅샷을 가진 보통의 관리 엔티티가 된다.

    대조 실험을 두 개 더 했다. 같은 컨트롤러에서 서비스 메서드를 @Transactional(readOnly = true)로 바꾸면 UPDATE가 나가지 않았고 데이터베이스의 제목도 그대로였다. 읽기 전용 트랜잭션은 커밋 때 플러시하지 않기 때문이다. 하지만 엔티티는 여전히 바뀐 채 영속성 컨텍스트에 남아 있으므로, 같은 요청에서 나중에 쓰기 트랜잭션이 하나라도 시작되면 앞의 실험과 같은 일이 생긴다. 다음으로 spring.jpa.open-in-view=false로 같은 요청을 보냈다.

    select a1_0.id, ... from article a1_0 where a1_0.id=?
select count(*) from article a1_0
body=managed=false, readOnly=n/a
db title = orig

    이번에는 findById의 트랜잭션이 자기 EntityManager를 새로 만들었다가 끝날 때 닫았으므로, 컨트롤러가 받은 게시글은 준영속 상태다(managed=false). 제목을 바꿔도 아무도 추적하지 않으니 변경은 조용히 사라졌다. 두 결과를 합치면 결론이 분명하다. 컨버터로 받은 엔티티를 수정하면, OSIV 설정과 그 뒤에 어떤 트랜잭션이 이어지는지에 따라 "의도치 않게 저장되거나" "아무 말 없이 버려진다". 어느 쪽도 코드만 보고는 예측하기 어렵다. 도메인 클래스 컨버터는 단순 조회 화면이나 API에서 읽기 전용으로만 쓰고, 수정은 식별자를 서비스로 넘겨 트랜잭션 안에서 다시 조회해 바꾸는 정석을 따르는 이유가 여기에 있다.

    하나의 요청 동안 같은 EntityManager가 컨버터의 읽기 전용 트랜잭션과 서비스의 쓰기 트랜잭션에 공유되어, 컨트롤러에서 바꾼 엔티티가 서비스 트랜잭션의 플러시로 저장되는 흐름을 보여 준다. 가로 16:9 시퀀스 다이어그램. 맨 위에 가로로 긴 띠 "요청 하나 동안 열린 EntityManager (OSIV)"가 그림 전체 폭을 덮는다. 그 아래 생명선 네 개: "도메인 클래스 컨버터", "컨트롤러", "서비스 (@Transactional)", "데이터베이스". 순서대로 화살표: 컨버터 → 데이터베이스 라벨 "findById (읽기 전용 트랜잭션)", 데이터베이스 → 컨버터 라벨 "Article 영속 상태", 컨트롤러 안에 작은 메모 "제목 변경", 컨트롤러 → 서비스 라벨 "touch()", 서비스 → 데이터베이스 빨간색 화살표 라벨 "UPDATE (자동 플러시)". 띠와 각 단계의 Article 아이콘을 같은 색 점선으로 이어 같은 영속성 컨텍스트임을 표시한다. 흰 배경, 회색 선, 빨간 강조 하나. OSIV가 켜져 있으면 컨버터가 로딩한 엔티티는 요청 끝까지 영속 상태이고, 뒤이은 쓰기 트랜잭션의 플러시가 그 변경을 저장한다.

    Web 확장 2: 요청 파라미터가 Pageable이 되기까지

    네 번째 확장은 페이징과 정렬이다. 04회에서 리포지토리 메서드에 Pageable을 넘기면 페이지 쿼리와 count 쿼리가 나가고 Page가 돌아오는 것을 보았다. 웹 확장은 그 Pageable을 요청 파라미터에서 만들어 컨트롤러 파라미터로 넣어 준다. 컨트롤러는 그것을 리포지토리에 그대로 넘기고, 결과를 DTO로 바꿔 반환하면 된다.

    @GetMapping("/articles")
public Page list(Pageable pageable) {
    return articleRepository.findAll(pageable).map(ArticleDto::new);
}

public record ArticleDto(Long id, String title, int views) {
    public ArticleDto(Article a) { this(a.getId(), a.getTitle(), a.getViews()); }
}

    이 일을 하는 것은 스프링 MVC의 인자 해석기(HandlerMethodArgumentResolver)인 PageableHandlerMethodArgumentResolver와 SortHandlerMethodArgumentResolver다. 앞 절의 @EnableSpringDataWebSupport가 이 둘을 등록하고, 스프링 부트의 자동 구성은 PageableHandlerMethodArgumentResolverCustomizer와 SortHandlerMethodArgumentResolverCustomizer 빈을 만들어 설정 프로퍼티 값을 해석기에 적용한다. 공식 문서가 정한 파라미터는 세 개다. page는 0부터 세는 페이지 번호로 기본값 0, size는 페이지 크기로 기본값 20, sort는 property,property(,ASC|DESC)(,IgnoreCase) 형식이며 방향을 바꾸려면 sort를 여러 번 쓴다.

    Spring Data Commons 3.5.13의 PageableHandlerMethodArgumentResolverSupport에서 상수를 확인하면 기본 파라미터 이름 page와 size, 한정자 구분자 _, 최대 페이지 크기 DEFAULT_MAX_PAGE_SIZE = 2000, 그리고 크기 20으로 만든 기본 Pageable이 들어 있다. 스프링 부트 3.5.16은 이 값들을 spring.data.web.* 프로퍼티로 노출한다(부트 jar의 설정 메타데이터로 확인).

    프로퍼티기본값의미

    @PageableDefault와 한정자

    메서드마다 기본값이 다르면 파라미터에 @PageableDefault를 붙인다. 공식 문서는 기본 Pageable이 PageRequest.of(0, 20)과 같고 이 애너테이션으로 바꿀 수 있다고 설명한다. 한 화면에 목록이 둘이라 Pageable이 두 개 필요하면 @Qualifier로 구분하고, 요청 파라미터에는 한정자_ 접두사를 붙인다.

    @GetMapping("/articles/default")
public String withDefault(
        @PageableDefault(size = 5, sort = "title", direction = Sort.Direction.DESC) Pageable pageable) {
    return pageable.toString();
}

@GetMapping("/articles/pair")
public String pair(@Qualifier("left") Pageable left, @Qualifier("right") Pageable right) {
    return left + " | " + right;
}

    요청에 sort가 오면 애너테이션의 기본 정렬은 합쳐지지 않고 통째로 대체되었다(title DESC가 사라지고 views ASC만 남았다). 한정자가 붙은 Pageable은 접두사 없는 page=9를 무시했고, 값이 오지 않은 right의 크기는 기본값 20이 되었다.

    page, size, sort 파라미터가 인자 해석기에서 보정되어 Pageable이 되고, 리포지토리의 페이지 쿼리와 count 쿼리를 거쳐 Page와 JSON이 되는 흐름을 보여 준다. 가로 16:9 순서도. 왼쪽 끝에 "?page=1&size=5000&sort=views,desc"라고 적힌 요청 카드. 오른쪽으로 화살표를 따라 상자들이 이어진다: "인자 해석기", "Pageable", "리포지토리 findAll", "Page", "JSON 응답". "인자 해석기" 상자 아래에 작은 말풍선 두 개를 단다: "size 최대 2000으로 보정", "잘못된 숫자는 기본값". "리포지토리 findAll" 상자에서 아래로 두 갈래 화살표가 나가 각각 "페이지 쿼리"와 "count 쿼리" 상자로 간다. "JSON 응답" 상자 아래에 말풍선 "PagedModel 권장". 평면 벡터 스타일, 파랑 계열, 흰 배경. Pageable은 컨트롤러에 도착하기 전에 이미 보정되어 있고, 응답 형식은 별도로 정해야 한다.

    정렬 파라미터는 검증되지 않은 채 들어온다

    공식 문서는 요청 파라미터에서 해석된 Sort.Order가 속성 이름을 그대로 담은 전달 객체일 뿐 도메인 모델에 대해 검증되지 않으며, 원치 않는 정렬을 막을 책임은 애플리케이션에 있다고 경고한다. 실제로 존재하지 않는 속성으로 요청해 보면, 인자 해석은 아무 문제 없이 끝나고 실패는 쿼리를 만들 때 일어난다.

    스프링 데이터 JPA가 정렬 속성을 엔티티의 속성 경로로 해석하다가 실패했으므로, 존재하지 않는 이름이 SQL에 그대로 박히지는 않았다. 하지만 이 예외는 어떤 예외 처리기도 응답 코드로 바꾸지 않아 MockMvc 테스트까지 ServletException으로 올라왔다. 실제 서버라면 클라이언트 입력 실수가 500 오류가 된다. 더 신경 쓰이는 것은 존재하는 속성이다. 클라이언트가 인덱스가 없는 컬럼이나 노출하고 싶지 않은 속성(예: 작성자 식별 정보)으로 정렬을 요청하면 그대로 실행된다. 대용량 테이블에서 인덱스 없는 정렬은 정렬 작업 자체가 부하가 된다.

    해법은 허용 목록이다. 정렬 가능한 속성을 정해 두고 그 밖의 요청은 400으로 거절한다. 아래 코드는 실험 프로젝트에서 컴파일하고 실행한 것이다.

    private static final Set SORTABLE = Set.of("title", "views", "createdDate");

static Pageable checkSort(Pageable pageable) {
    for (Sort.Order order : pageable.getSort()) {
        if (!SORTABLE.contains(order.getProperty())) {
            throw new ResponseStatusException(HttpStatus.BAD_REQUEST, "정렬할 수 없는 속성: " + order.getProperty());
        }
    }
    return pageable;
}

@GetMapping("/articles/safe")
public Page safeList(Pageable pageable) {
    return articleRepository.findAll(checkSort(pageable)).map(ArticleDto::new);
}

    이 JSON은 PageImpl 객체의 게터를 Jackson이 그대로 직렬화한 결과다. 공식 문서는 PageImpl이 도메인 타입이라서 관련 없는 이유로 API가 바뀔 수 있고, 그러면 JSON 표현이 깨질 수 있으므로 이 방식을 강하게 권하지 않는다고 설명한다. 실제로 같은 실험을 두 번 돌리는 동안 필드의 등장 순서가 달라진 출력도 있었다. API 응답은 클라이언트와의 계약이므로, 계약의 모양이 라이브러리 내부 클래스의 게터 목록에 묶여서는 안 된다.

    권장 방식은 PagedModel이다. 컨트롤러가 new PagedModel<>(page)를 반환해도 되고, 전역으로 바꾸려면 @EnableSpringDataWebSupport(pageSerializationMode = VIA_DTO)를 쓴다. 스프링 부트에서는 spring.data.web.pageable.serialization-mode=via-dto 프로퍼티가 같은 일을 한다. 이 프로퍼티를 켜고 같은 컨트롤러를 호출한 결과는 다음과 같다.

    {"content":[{"id":1,"title":"b1","views":1},{"id":2,"title":"b2","views":2},{"id":3,"title":"b3","views":3}],
 "page":{"size":3,"number":0,"totalElements":7,"totalPages":3}}

    콘텐츠와 페이지 메타데이터 네 개(size, number, totalElements, totalPages)만 남은 단순한 구조다. 컨트롤러 코드는 여전히 Page를 반환하고, 직렬화 단계에서 형식이 바뀐다. 이미 DIRECT 형식에 맞춰 개발된 클라이언트가 있다면 응답 구조가 바뀌는 변경이므로, 전환은 API 버전 관리 계획과 함께 해야 한다.

    one-indexed-parameters의 함정

    화면의 페이지 번호는 보통 1부터 시작하므로 spring.data.web.pageable.one-indexed-parameters=true로 요청을 1부터 받고 싶어진다. 이 설정을 켜고(응답은 VIA_DTO) 일곱 건에 대해 세 가지 요청을 보냈다.

    요청해석된 Pageable응답의 page.number내용
    page=1&size=3number: 00b1, b2, b3
    page=0&size=3number: 00b1, b2, b3
    page=3&size=3number: 22b7

    요청은 1부터 해석되었지만(page=1 → 0번 페이지), 응답의 페이지 번호는 여전히 0부터다. 클라이언트가 1페이지를 요청하면 응답에는 "0번 페이지"라고 적혀 돌아온다. 이 설정은 요청 파라미터의 해석만 바꿀 뿐 Page 객체와 그 직렬화는 바꾸지 않는다. 또 page=0은 -1이 되어 앞에서 본 보정 규칙대로 0번 페이지가 되었으므로, 1페이지와 같은 결과가 나왔다. 응답 번호까지 1부터 보이고 싶다면 이 설정에 기대지 말고 응답 DTO를 직접 만들어 number + 1을 넣는 쪽이 일관된다. 요청과 응답을 모두 0 기준으로 두고 화면에서 1을 더하는 것도 똑같이 타당한 선택이다. 중요한 것은 요청과 응답의 기준이 어긋난 상태로 API를 내보내지 않는 것이다.

    마지막 행의 실행 기록에는 하나 더 볼 것이 있다. 7건 중 마지막 페이지(1건)를 요청했을 때는 페이지 쿼리만 나가고 count 쿼리가 나가지 않았다. 결과가 페이지 크기보다 적은 마지막 페이지라면 전체 개수를 오프셋과 결과 수로 계산할 수 있기 때문인데, 이 count 쿼리 최적화는 페이징을 다룬 04회의 주제다.

    다른 주제와의 연결

    이 회차의 네 기능은 모두 새 메커니즘을 만든 것이 아니라 이미 있는 메커니즘에 꽂혀 있다. 사용자 정의 리포지토리는 리포지토리 프록시의 인터셉터 체인과 조각 조합에, Auditing은 JPA 엔티티 콜백과 AspectJ 의존성 주입에, 도메인 클래스 컨버터는 스프링 MVC의 타입 변환과 findById에, 페이징 바인딩은 스프링 MVC의 인자 해석기에 올라가 있다. 그래서 각 기능의 한계도 그 아래 메커니즘의 한계를 그대로 물려받는다. 사용자 정의 메서드가 SimpleJpaRepository의 트랜잭션 설정을 받지 못하는 것, 벌크 수정이 감사 정보를 남기지 않는 것, OSIV 아래에서 컨버터 엔티티가 요청 끝까지 관리되는 것이 모두 그렇다.

    다음 회차(06회)는 이 회차에서 여러 번 이름만 나온 SimpleJpaRepository를 직접 연다. 클래스 수준 @Transactional(readOnly = true)가 메서드마다 어떻게 적용되는지, save()가 새 엔티티를 어떻게 판단하는지, 그 판단을 바꾸는 Persistable이 무엇인지가 거기서 다뤄진다. 여기서 본 Auditing의 createdDate는 그 판단 로직과도 연결된다. 07회는 명세, Query By Example, Projections, 네이티브 쿼리 같은 나머지 기능을 다룬다.

    로드맵의 다음 권인 Querydsl에서는 사용자 정의 리포지토리가 다시 등장한다. 동적 쿼리를 Querydsl로 작성해 조각 구현 클래스에 넣고, 클라이언트는 여전히 리포지토리 인터페이스 하나만 쓰는 구성이 그것이다. 이 회차에서 본 이름 규칙, 트랜잭션 비대칭, 예외 변환이 그대로 적용된다. 리포지토리 프록시와 @Configurable이 쓰는 AOP 자체, 즉 JDK 동적 프록시와 CGLIB, 어드바이스 체인, AspectJ 위빙의 차이는 스프링 핵심 원리 고급편에서 더 깊이 다룬다.
    리포지토리 조각 조합
    리포지토리 프록시는 쿼리 메서드가 아닌 호출을 RepositoryComposition에 넘기고, 사용자 정의 조각과 기본 구현(SimpleJpaRepository) 중 그 시그니처를 구현한 조각이 실행된다. 사용자 정의 조각이 기본 구현보다 우선한다.
    Impl 이름 규칙
    구현 클래스는 조각 인터페이스 이름 + Impl(접미사 변경 가능)이어야 하고 리포지토리 기본 패키지 아래에 있어야 한다. 찾지 못하면 그 메서드가 쿼리 메서드로 취급되어 "No property … found for type" 오류로 시작이 실패한다.
    사용자 정의 메서드의 트랜잭션
    SimpleJpaRepository의 @Transactional 설정은 사용자 정의 메서드에 적용되지 않았다. 쓰기가 필요하면 구현 메서드나 호출하는 서비스에 @Transactional을 둔다.
    JPA 엔티티 콜백
    @PrePersist는 persist 연산 직전에, @PreUpdate는 변경 감지로 UPDATE가 결정된 엔티티에 대해 플러시 때 호출된다. 값이 바뀌지 않으면 불리지 않는다.
    스프링 데이터 JPA Auditing
    @EnableJpaAuditing과 AuditingEntityListener가 @CreatedDate, @LastModifiedDate, @CreatedBy, @LastModifiedBy 필드를 채운다. 사용자는 AuditorAware, 시각은 DateTimeProvider(기본 LocalDateTime.now())에서 온다.
    Auditing의 경계
    벌크 수정, 네이티브 SQL, JDBC 직접 수정은 콜백을 거치지 않아 감사 정보가 갱신되지 않는다. 기록되는 수정 시각은 플러시 시각이다.
    도메인 클래스 컨버터
    문자열을 식별자 타입으로 바꾼 뒤 리포지토리의 findById로 엔티티를 찾는다. 없으면 null이 되어 경로 변수라면 400 응답이 된다. OSIV 아래에서는 받은 엔티티가 요청 끝까지 영속 상태이므로 조회용으로만 쓴다.
    Pageable 바인딩
    page(0부터), size(기본 20, 최대 2000), sort 파라미터가 해석되며, 범위를 벗어나거나 숫자가 아닌 값은 오류 없이 보정된다. 정렬 속성은 검증되지 않으므로 허용 목록으로 걸러야 한다.
    Page 직렬화
    PageImpl을 그대로 직렬화하면 구조가 보장되지 않는다는 경고가 나온다. PagedModel(VIA_DTO 모드)을 쓰고, one-indexed 설정은 요청만 바꾸고 응답 번호는 바꾸지 않는다는 점에 주의한다.

    사용자 정의 리포지토리는 "인터페이스 하나로 모든 데이터 접근을 노출한다"는 편의를 주지만, 그 편의에는 숨은 규칙이 따라온다. 실무에서 자주 만나는 장애는 이름 규칙 위반으로 인한 시작 실패와, 테스트나 배치처럼 서비스 계층을 거치지 않는 호출에서 사용자 정의 쓰기 메서드만 TransactionRequiredException을 내는 상황이다. 두 경우 모두 오류 메시지가 원인을 직접 말하지 않으므로, 리포지토리 프록시가 메서드를 쿼리 메서드·default 메서드·조각 메서드로 나눈다는 구조를 알고 있어야 빨리 찾는다. 화면 전용 조회가 늘어나면 조각에 계속 넣을지, 별도 조회 클래스로 분리할지를 리포지토리의 응집도 기준으로 다시 판단한다.

    Auditing은 켜 두면 잊어버리는 기능이라서, 한계를 모르면 데이터를 믿게 된다. 벌크 수정으로 대량 갱신한 행의 수정 시각이 그대로라 "이 데이터는 언제 바뀌었나"를 추적하지 못하는 일이 대표적이다. 감사 정보가 규정 준수나 정산의 근거로 쓰이는 시스템이라면 엔티티 콜백만으로는 부족하고, 데이터베이스 트리거나 변경 이력 테이블, 변경 데이터 캡처 같은 영속성 컨텍스트 밖의 장치를 함께 고려해야 한다. 반대로 화면 표시와 대략적인 추적이 목적이라면 BaseTimeEntity/BaseEntity 정도로 충분하다.

    도메인 클래스 컨버터와 Pageable 바인딩은 컨트롤러 코드를 줄이지만, 그만큼 입력 처리의 결정을 프레임워크 기본값에 넘긴다. 존재하지 않는 식별자가 400이 되는 것, 잘못된 크기 값이 조용히 기본값이 되는 것, 존재하지 않는 정렬 속성이 500이 되는 것, 1부터 받은 페이지 번호가 0으로 응답되는 것은 모두 API 계약의 일부다. 외부에 공개하는 API라면 이 기본값을 그대로 쓸지, 명시적인 검증과 응답 DTO로 감쌀지를 처음에 정해 두는 것이 나중에 계약을 바꾸는 것보다 훨씬 싸다. 그리고 OSIV를 켜 둔 애플리케이션에서 컨버터로 받은 엔티티를 수정하는 코드는 리뷰에서 반드시 걸러야 한다.
  • 조각 인터페이스 ArticleSearch를 만들고 구현 클래스 이름을 ArticleSearchImplV2로 지었다. ArticleRepository가 ArticleSearch를 상속하고 있고, 조각의 메서드 이름은 searchByKeyword(String keyword)다. 애플리케이션을 시작하면 어떤 일이 일어나는지, 그 이유를 리포지토리 프록시가 메서드를 분류하는 방식으로 설명하라.
  • 한 트랜잭션 안에서 다음을 순서대로 실행한다. (1) 새 Article을 save, (2) flush, (3) changeTitle로 원래 제목과 같은 문자열을 넣음, (4) flush, (5) JPQL update Article a set a.title = 'x' 실행. 각 단계 뒤 lastModifiedDate 필드 값과 데이터베이스 컬럼 값이 어떻게 되는지, 실행되는 SQL과 함께 예측하라(modifyOnCreate는 기본값).
  • spring.jpa.open-in-view=true인 애플리케이션에서 컨트롤러가 @PathVariable("id") Article article로 받은 게시글의 조회수를 1 올린 뒤, @Transactional이 붙은 auditLogService.write(...)(감사 로그 테이블에 한 행을 INSERT)를 호출한다. 게시글 조회수는 데이터베이스에 반영되는가? OSIV를 끄면 어떻게 달라지는가?
  • 기본 설정에서 GET /articles?page=2&size=3000&sort=title,views,desc&sort=createdDate로 들어온 요청이 만드는 Pageable의 페이지 번호, 크기, 정렬을 쓰라. 같은 요청을 one-indexed-parameters=true에서 보내면 무엇이 달라지는가?
    •

    1. 이름이 조각 인터페이스 이름 + Impl(ArticleSearchImpl)이 아니므로 인프라가 이 클래스를 조각 구현으로 감지하지 못한다. 그러면 조합 안에 searchByKeyword를 맡을 조각이 없고, 이 메서드는 기본 구현에도 default 메서드에도 해당하지 않으므로 쿼리 메서드로 분류된다. 리포지토리 빈을 만들 때 메서드 이름을 해석해 쿼리를 미리 만들려 하는데, searchByKeyword는 search…By 형태라서 By 뒤의 Keyword를 Article의 속성으로 찾으려다 실패한다. 결과는 본문 실험과 같은 종류의 QueryCreationException/PropertyReferenceException("No property … found for type 'Article'" 형태)이고, 컨텍스트 시작이 실패한다. 오류 메시지가 쿼리 이름을 가리키더라도 고칠 곳은 구현 클래스 이름이다.

    2. (1) save 안의 persist에서 @PrePersist 콜백이 돌아 createdDate와 lastModifiedDate가 같은 값으로 채워진다. 시퀀스 전략이므로 이 시점에는 시퀀스 조회만 나가고 INSERT는 아직 없다. (2) 플러시에서 INSERT가 나가며 두 컬럼에 같은 값이 저장된다. (3) 같은 값을 넣었으므로 필드는 그대로다. (4) 변경 감지가 스냅샷과 같다고 판단해 UPDATE가 없고, @PreUpdate도 불리지 않아 수정 시각은 그대로다. (5) 벌크 수정은 update article set title='x' 형태의 SQL 하나로 실행되고 감사 컬럼은 SQL에 없으므로, 데이터베이스의 제목은 바뀌지만 last_modified_date는 처음 값 그대로다. 영속성 컨텍스트의 엔티티 필드는 벌크 연산이 건드리지 않으므로 제목도 수정 시각도 이전 값으로 남는다(04회의 벌크 수정과 영속성 컨텍스트 불일치).

    3. 반영된다. OSIV가 켜져 있으면 컨버터의 findById가 요청에 묶인 EntityManager를 쓰므로 게시글은 요청 끝까지 영속 상태이고, 미리 묶인 EntityManager라서 읽기 전용 세션 설정도 적용되지 않는다. 이어서 시작된 auditLogService.write의 쓰기 트랜잭션이 같은 EntityManager로 플러시할 때 변경 감지가 게시글의 조회수 변경을 찾아 UPDATE를 보낸다(감사 필드도 함께 갱신된다). OSIV를 끄면 findById의 트랜잭션이 끝날 때 EntityManager가 닫혀 게시글은 준영속이 되고, 감사 로그 트랜잭션은 새 EntityManager를 쓰므로 게시글 변경은 어디에도 반영되지 않고 사라진다. 어느 쪽이든 의도가 코드에 드러나지 않으므로, 조회수 증가는 식별자를 서비스로 넘겨 트랜잭션 안에서 처리해야 한다.

    4. 페이지 번호 2, 크기는 최대값으로 깎여 2000, 정렬은 첫 sort의 방향 desc가 그 안의 두 속성에 모두 적용되어 title: DESC, views: DESC, 두 번째 sort는 방향이 없으므로 createdDate: ASC다. one-indexed-parameters=true에서는 요청 번호에서 1을 빼므로 페이지 번호가 1이 되고, 크기와 정렬은 같다. 응답의 페이지 번호는 그 설정과 관계없이 0 기준으로 직렬화되므로 응답에는 1이 찍힌다. 요청한 "2페이지"와 응답의 "1"이 어긋나는 것이다.

     조각 인터페이스 ArticleRepositoryCustom의 구현 클래스 이름을 ArticleRepositoryCustomImp로 잘못 지었다. 애플리케이션 시작 시 나타나는 현상으로 가장 정확한 것은? 구현 클래스가 빈으로 등록되지 않을 뿐, 해당 메서드를 처음 호출할 때 UnsupportedOperationException이 난다. 스프링 데이터가 인터페이스를 구현한 클래스를 타입으로 찾아 자동으로 연결하므로 정상 동작한다. 그 메서드가 쿼리 메서드로 취급되어, 리포지토리 빈 생성 중 메서드 이름 해석이 실패하며 "No property … found for type" 형태의 오류로 시작이 중단된다. 컴파일 단계에서 구현 클래스 이름이 규칙에 맞지 않는다는 오류가 난다. 구현 감지는 이름 규칙(조각 인터페이스 이름 + 접미사)으로 이루어지므로 타입이 맞아도 연결되지 않는다. 조각이 없는 메서드는 쿼리 메서드로 분류되고, 쿼리는 리포지토리 빈을 만들 때 미리 생성되므로 오류는 첫 호출이 아니라 시작 시점에 난다. 이름 규칙은 스프링 데이터의 런타임 규칙이라 컴파일러는 알지 못한다. 트랜잭션 없이 테스트 코드에서 articleRepository.findById(1L)와 사용자 정의 메서드 articleRepository.insertDirect("x")(구현에 @Transactional 없음, 내부에서 em.persist)를 차례로 호출했다. 결과로 옳은 것은? 둘 다 SimpleJpaRepository의 클래스 수준 트랜잭션 설정을 받아 정상 실행된다. findById는 정상이지만 insertDirect는 실제 트랜잭션이 없어 persist를 처리할 수 없다는 예외가 나며, 호출자는 이를 InvalidDataAccessApiUsageException으로 받는다. insertDirect는 리포지토리 프록시가 쓰기 트랜잭션을 자동으로 시작하므로 정상 저장된다. insertDirect는 예외 없이 끝나지만 INSERT가 나가지 않는다. SimpleJpaRepository의 트랜잭션 애너테이션은 그 클래스의 메서드에 대한 것이고, 조각에만 있는 메서드는 트랜잭션 속성을 얻지 못해 트랜잭션 없이 실행되었다. 공유 EntityManager는 트랜잭션 없는 persist에 TransactionRequiredException을 던지고, 리포지토리 프록시의 예외 변환 인터셉터가 이를 InvalidDataAccessApiUsageException으로 바꾼다. 조용히 무시되는 것이 아니라 예외가 난다. 스프링 데이터 JPA Auditing을 켠 엔티티에 대해 수정 시각(@LastModifiedDate)이 갱신되는 경우는? JPQL 벌크 수정으로 해당 행의 컬럼을 바꿨을 때 영속 엔티티의 필드에 원래와 같은 값을 다시 넣고 플러시했을 때 JdbcTemplate으로 해당 행을 UPDATE했을 때 영속 엔티티의 필드를 다른 값으로 바꾸고 트랜잭션을 커밋했을 때 Auditing은 JPA 엔티티 콜백(@PreUpdate)으로 동작하고, 콜백은 플러시 때 변경 감지가 UPDATE를 결정한 엔티티에만 불린다. 커밋 직전 플러시에서 바뀐 필드가 감지되면 콜백이 수정 시각을 채운다. 벌크 수정과 JDBC 직접 수정은 영속성 컨텍스트를 거치지 않고, 같은 값을 넣으면 변경으로 감지되지 않는다. OSIV가 켜진 상태에서 도메인 클래스 컨버터가 로딩한 엔티티가 읽기 전용 세션 설정을 받지 않은(변경 감지 대상인) 이유로 가장 정확한 것은? 요청에 미리 묶인 EntityManager를 트랜잭션이 재사용하므로 "트랜잭션을 위해 새로 만든 리소스"가 아니고, 스프링은 그런 경우 Hibernate 세션에 기본 읽기 전용을 걸지 않기 때문이다. findById는 트랜잭션 없이 실행되기 때문이다. 도메인 클래스 컨버터가 findById 대신 JPQL을 직접 실행하기 때문이다. Hibernate는 읽기 전용 트랜잭션이라는 개념을 지원하지 않기 때문이다. findById는 SimpleJpaRepository의 읽기 전용 트랜잭션에서 실행된다. JpaTransactionManager는 트랜잭션 정의의 localResource에 "EntityManager를 새로 만들었는가"를 넘기고, HibernateJpaDialect는 그것이 참이고 읽기 전용일 때만 setDefaultReadOnly(true)를 건다. OSIV는 EntityManager를 미리 묶어 두므로 이 조건이 거짓이 된다. 컨버터는 RepositoryInvoker.invokeFindById로 리포지토리의 findById를 부른다. spring.data.web.pageable.one-indexed-parameters=true와 VIA_DTO 직렬화를 켠 뒤 GET /articles?page=1&size=3을 보냈다. 응답 JSON의 page.number 값과 그 이유로 옳은 것은? 1. 설정이 요청과 응답의 페이지 번호를 모두 1 기준으로 바꾸기 때문이다. 2. 요청의 1이 1을 더한 값으로 해석되기 때문이다. 0. 설정은 요청 파라미터 해석에서 1을 뺄 뿐이고, Page와 그 직렬화는 0 기준을 유지하기 때문이다. 오류가 난다. VIA_DTO 모드에서는 one-indexed 설정을 쓸 수 없기 때문이다. 실험에서 page=1은 0번 페이지로 해석되었고 응답의 page.number는 0이었다. one-indexed 설정은 인자 해석기의 동작만 바꾸므로, 응답 번호까지 1 기준으로 보이려면 응답 DTO를 직접 만들어야 한다.
    조각 인터페이스(fragment interface)
    리포지토리 인터페이스가 함께 상속하는, 직접 구현할 메서드만 모은 인터페이스. 이름 + Impl 클래스가 그 구현으로 감지된다.
    RepositoryComposition
    리포지토리 프록시가 쿼리 메서드가 아닌 호출을 넘기는 구현 조각의 목록. 사용자 정의 조각이 기본 구현보다 먼저 검사된다.
    엔티티 리스너(entity listener)
    JPA 생명주기 콜백 메서드를 엔티티 밖의 별도 클래스에 둔 것. @EntityListeners나 orm.xml로 등록하며 public 기본 생성자가 필요하다.
    AuditorAware
    현재 사용자(감사 주체)를 Optional로 돌려주는 스프링 데이터의 SPI. @CreatedBy, @LastModifiedBy 값을 공급한다.
    @Configurable
    스프링 컨테이너가 만들지 않은 객체에도 의존성을 주입하도록 표시하는 애너테이션. AspectJ로 엮인 생성자 코드가 AnnotationBeanConfigurerAspect를 통해 주입을 수행한다.
    DomainClassConverter
    스프링 MVC의 ConversionService에 등록되어 문자열 식별자를 리포지토리 findById로 조회한 엔티티로 바꿔 주는 변환기.
    HandlerMethodArgumentResolver
    스프링 MVC가 컨트롤러 메서드의 파라미터 값을 만들 때 쓰는 전략 인터페이스. Pageable, Sort를 요청 파라미터에서 만드는 해석기가 그 구현이다.
    PagedModel
    Page를 콘텐츠와 페이지 메타데이터(크기, 번호, 전체 개수, 전체 페이지 수)만 가진 안정된 JSON 구조로 감싸는 스프링 데이터의 DTO.
