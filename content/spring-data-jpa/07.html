    이 회차의 질문: 조건이 실행 시점에야 정해질 때

    지금까지 이 권에서 만든 쿼리는 모두 컴파일 시점에 모양이 정해져 있었다. 3회차의 쿼리 메서드는 메서드 이름이 곧 WHERE 절이었고, @Query는 문자열 상수였다. 그런데 실제 화면은 그렇게 친절하지 않다. 직원 검색 화면에 이름, 최소 나이, 부서 이름이라는 세 개의 입력칸이 있고 사용자가 아무 칸이나 비워 둘 수 있다고 해 보자. 조건 세 개가 각각 "있음/없음"이므로 WHERE 절의 모양은 2의 3제곱, 여덟 가지다. 쿼리 메서드로 이것을 덮으려면 findByName, findByAgeGreaterThanEqual, findByNameAndDepartmentName 같은 메서드를 여덟 개 만들어야 하고, 조건이 하나 늘 때마다 그 수가 두 배가 된다.

    문자열을 이어 붙여 JPQL을 만드는 방법도 있다. 하지만 그렇게 만든 문자열은 실행해 보기 전까지 문법이 맞는지 알 수 없고, 사용자 입력을 문자열에 직접 섞는 순간 주입(injection) 공격의 통로가 된다. 공백 하나, and 하나를 빠뜨리는 실수도 실행 시점에야 드러난다. 필요한 것은 "조건 하나"를 객체로 만들고, 그 객체들을 실행 시점에 조립해서 쿼리를 완성하는 방법이다. 이 회차의 앞부분이 다루는 두 기능, 명세(Specification)와 예시 기반 조회(Query By Example)가 바로 그 방법이다.

    뒷부분은 질문이 조금 다르다. 조건이 아니라 "무엇을 가져올 것인가"다. 엔티티를 통째로 읽는 대신 필요한 열만 읽는 프로젝션(Projections), 그리고 JPQL이라는 추상화를 아예 벗어나 데이터베이스에 SQL을 그대로 보내는 네이티브 쿼리(native query)를 다룬다. 네 기능은 서로 달라 보이지만 공통점이 있다. 모두 6회차에서 열어 본 SimpleJpaRepository와 쿼리 실행 객체 안에서, 결국 하이버네이트에게 넘길 쿼리 객체를 만드는 방식의 변형이라는 점이다. 이 회차는 각 기능이 그 쿼리 객체를 어떻게 만들고, 그 과정의 어느 지점에서 함정이 생기는지를 실험으로 따라간다. 이번 회차가 이 권의 마지막이다.

    이 장의 핵심

    Specification은 SQL이 아니라 "술어를 만드는 함수"이고, 스프링 데이터 JPA는 쿼리를 만들 때마다 그 함수를 다시 호출한다. 그래서 페이징 조회에서는 본문 쿼리와 count 쿼리에서 두 번 불리고, 함수 안의 부수 효과(조인, 페치, 정렬)가 count 쿼리에도 새어 들어간다. Query By Example은 probe 객체를 읽어 같은 Specification을 자동으로 만드는 장치다. 프로젝션은 SELECT 목록을 줄이고 결과를 튜플과 프록시로 감싸며, 네이티브 쿼리는 JPQL 검증과 엔티티 이름 번역을 포기하는 대신 SQL을 그대로 보내고, 그 대가로 페이징과 정렬은 문자열 재작성으로 처리된다.

    실험 환경과 예제 데이터

    이 회차의 실행 결과는 모두 직접 돌려서 얻었다. 6회차와 같은 조합인 Spring Framework 6.2.19, Spring Data JPA 3.5.13, Hibernate ORM 6.6.53.Final, H2 2.3.232, JDK 21을 썼고, 스프링 부트 없이 @EnableJpaRepositories와 LocalContainerEntityManagerFactoryBean을 직접 구성했다. 이 버전 조합이 Spring Boot 3.5.16의 의존성 관리와 같다는 점은 6회차에서 확인했다. 하이버네이트 설정은 hibernate.hbm2ddl.auto=create와 hibernate.show_sql=true뿐이고, 본문에 나오는 SQL은 그 로그를 그대로 옮긴 것이다. 부트를 쓰지 않았으므로 물리 이름 전략은 하이버네이트 기본값이라 테이블 이름이 엔티티 이름 그대로 Employee, Department가 된다. H2는 따옴표 없는 식별자의 대소문자를 구분하지 않으므로 네이티브 SQL에서 employee라고 써도 같은 테이블을 가리킨다.

    도메인은 1회차와 4회차에서 쓴 부서와 직원이다. 직원은 이름, 나이, 소속 부서를 가진다. 나이를 일부러 기본형 int로 둔 데에는 이유가 있다. Query By Example에서 이 선택이 결과를 바꾸는 장면을 보게 된다.

    명세 ①: 명세 패턴과 Criteria API의 세 재료

    스프링 데이터 JPA 문서는 명세가 에릭 에반스의 『Domain Driven Design』에 나오는 명세(specification) 개념에 바탕을 둔다고 밝힌다. 명세 패턴의 핵심은 "어떤 객체가 조건을 만족하는가"라는 판단을 독립된 객체로 떼어 내고, 그 객체들을 AND, OR, NOT으로 조합할 수 있게 하는 것이다. 스프링 데이터 JPA는 이 판단을 자바 메모리 안에서 하지 않고, JPA Criteria API의 술어(Predicate)로 번역해 데이터베이스가 하게 만든다. 그래서 인터페이스의 유일한 추상 메서드가 Criteria API의 객체 세 개를 받는다.

    // Spring Data JPA 3.5.13의 Specification (주석과 일부 메서드 생략)
@FunctionalInterface
public interface Specification extends Serializable {

    @Nullable
    Predicate toPredicate(Root root, @Nullable CriteriaQuery query, CriteriaBuilder criteriaBuilder);

    default Specification and(@Nullable Specification other) { ... }
    default Specification or(@Nullable Specification other) { ... }
    static  Specification not(@Nullable Specification spec) { ... }
    static  Specification allOf(Specification... specifications) { ... }
    static  Specification anyOf(Specification... specifications) { ... }
    // ...
}

    세 매개변수의 역할을 SQL에 대응시키면 이해가 쉽다. Root는 FROM 절에 놓인 엔티티이자 경로 탐색의 출발점이다. root.get("name")은 "이 루트의 name 속성"이라는 경로 식(path expression)이 되고, root.join("department")는 조인을 하나 추가하고 그 조인을 새 경로의 출발점으로 돌려준다. CriteriaQuery는 지금 조립 중인 쿼리 그 자체로, SELECT 목록, WHERE, ORDER BY, DISTINCT를 담는다. CriteriaBuilder는 식과 술어를 만드는 공장이다. equal, greaterThanOrEqualTo, like, and, not 같은 메서드가 모두 여기에 있다. 명세가 해야 할 일은 이 재료로 술어 하나를 만들어 돌려주는 것뿐이고, 그 술어를 쿼리의 WHERE에 붙이는 일은 호출하는 쪽이 한다.

    예제 검색 조건 세 개를 명세로 만들면 다음과 같다. 입력이 비어 있으면 null을 돌려주는데, 이것이 "이 조건은 없음"을 뜻하는 약속이다. 바로 다음 절에서 조합 규칙이 이 null을 어떻게 다루는지 본다.

    public class Specs {
    public static Specification nameEq(String name) {
        return (root, query, cb) -> name == null ? null : cb.equal(root.get("name"), name);
    }
    public static Specification ageGoe(Integer age) {
        return (root, query, cb) -> age == null ? null : cb.greaterThanOrEqualTo(root.get("age"), age);
    }
    public static Specification deptName(String dept) {
        return (root, query, cb) -> {
            if (dept == null) return null;
            Join d = root.join("department", JoinType.INNER);
            return cb.equal(d.get("name"), dept);
        };
    }
}

    세 재료의 실제 클래스: 하이버네이트 6의 SQM

    Root, CriteriaQuery, CriteriaBuilder는 Jakarta Persistence가 정한 인터페이스다. 실제 객체는 JPA 구현체가 만든다. 명세 안에서 세 객체와 만들어진 술어의 클래스 이름을 찍어 보면 하이버네이트가 무엇으로 이 인터페이스를 구현했는지 드러난다.

      root    = org.hibernate.query.sqm.tree.from.SqmRoot
  query   = org.hibernate.query.sqm.tree.select.SqmSelectStatement
  builder = org.hibernate.query.sqm.internal.SqmCriteriaNodeBuilder
  predicate = org.hibernate.query.sqm.tree.predicate.SqmComparisonPredicate
Hibernate: select e1_0.id,e1_0.age,e1_0.department_id,e1_0.name from Employee e1_0 where e1_0.name=?

    패키지 이름에 공통으로 들어간 sqm은 하이버네이트 6의 의미 쿼리 모델(Semantic Query Model)이다. Criteria API로 쿼리를 조립한다는 것은 이 SQM 트리의 노드를 하나씩 만들어 붙이는 일이다. 흥미로운 점은 JPQL 문자열도 같은 곳에 도착한다는 것이다. 같은 실험 환경에서 em.createQuery("select e from Employee e where e.name = 'kim'")로 만든 쿼리 객체와, Criteria로 조립해 em.createQuery(criteriaQuery)로 만든 쿼리 객체를 비교했다. 둘 다 QuerySqmImpl이었고, 안에 든 문장 객체도 둘 다 SqmSelectStatement였다. JPQL은 파서가 문자열을 읽어 SQM 트리를 만들고, Criteria API는 개발자가 트리를 직접 만든다. 출발점만 다를 뿐 그 뒤로 SQL을 만드는 경로는 하나다.

    이 실험에서 한 가지 더 확인한 사실이 있다. em.createQuery(criteriaQuery)가 품고 있는 SQM 문장은 넘겨준 criteriaQuery와 같은 객체가 아니었다(== 비교가 false). 하이버네이트가 쿼리를 만들면서 트리를 복사해 두었다는 뜻이다. 그래서 쿼리 객체를 만든 뒤에 원래의 CriteriaQuery를 고쳐도 이미 만든 쿼리에는 영향이 없다. 스프링 데이터가 count 쿼리를 만들 때 원래 쿼리를 고쳐 쓰지 않고 CriteriaQuery를 처음부터 새로 만드는 것과도 맞아떨어지는 모습이다.

    한 층 아래: 람다 명세는 바이트코드에서 무엇인가

    Specification은 @FunctionalInterface이므로 위처럼 람다로 쓸 수 있다. 그런데 이 인터페이스는 Serializable을 상속한다. 직렬화 가능한 함수형 인터페이스를 대상으로 하는 람다는 javac가 다르게 컴파일한다. javap -c -p -v로 Specs 클래스를 열어 보면 ageGoe의 몸체는 단 세 줄이다.

    public static Specification ageGoe(java.lang.Integer);

     1: invokedynamic #11,  0   // InvokeDynamic #1:toPredicate:(Ljava/lang/Integer;)Lorg/springframework/data/jpa/domain/Specification;
     6: areturn

private static java.lang.Object $deserializeLambda$(java.lang.invoke.SerializedLambda);
...
BootstrapMethods: ... LambdaMetafactory.altMetafactory ...

    첫 줄은 매개변수 age를 스택에 올리고, invokedynamic은 그 값을 받아 Specification 객체를 만들어 돌려준다. 호출 지점의 서술자 (Ljava/lang/Integer;)Lorg/.../Specification;가 말해 주듯, 람다가 캡처한 age는 이 시점에 람다 객체 안에 담긴다. 조건 판단의 몸체는 컴파일러가 만든 별도의 private static 메서드에 있고, 그 메서드는 나중에 toPredicate가 불릴 때 실행된다. 부트스트랩 메서드가 일반 람다의 metafactory가 아니라 altMetafactory라는 점, 그리고 클래스에 $deserializeLambda$라는 메서드가 생겼다는 점이 직렬화 가능한 람다의 표시다.

    이 바이트코드가 알려 주는 핵심은 "명세를 만드는 시점"과 "술어를 만드는 시점"이 분리되어 있다는 것이다. ageGoe(26)을 호출하면 SQL은커녕 Criteria 노드도 아직 하나도 없다. 값 26을 품은 작은 객체 하나가 생길 뿐이다. 술어는 누군가 toPredicate를 구체적인 Root, CriteriaQuery와 함께 호출할 때 비로소 만들어진다. 그래서 같은 명세 객체를 여러 쿼리에 재사용할 수 있고, 반대로 쿼리가 여러 개면 명세가 여러 번 실행된다. 이 성질이 뒤에서 count 쿼리 문제로 이어진다.

    명세 ②: and, or, not 그리고 null의 의미

    조합 메서드는 생각보다 단순하다. and와 or는 둘 다 SpecificationComposition.composed를 부르고, 이 메서드는 두 명세를 차례로 실행해 나온 술어를 CriteriaBuilder::and나 CriteriaBuilder::or로 묶는 새 람다를 돌려준다. 3.5.13 소스를 거의 그대로 옮기면 다음과 같다.

    static  Specification composed(@Nullable Specification lhs, @Nullable Specification rhs,
        Combiner combiner) {
    return (root, query, builder) -> {
        Predicate thisPredicate = toPredicate(lhs, root, query, builder);   // 명세가 null이면 null
        Predicate otherPredicate = toPredicate(rhs, root, query, builder);
        if (thisPredicate == null) {
            return otherPredicate;
        }
        return otherPredicate == null ? thisPredicate : combiner.combine(builder, thisPredicate, otherPredicate);
    };
}

    이 코드에서 읽어 낼 규칙은 세 가지다. 첫째, 조합도 지연된다. a.and(b)는 a와 b를 실행하지 않고, 실행할 때 둘을 차례로 부르는 새 명세를 만들 뿐이다. 둘째, 한쪽 술어가 null이면 그쪽은 없는 것으로 치고 다른 쪽만 남긴다. 셋째, 양쪽이 모두 null이면 결과도 null이고, 리포지토리는 null 술어를 받으면 WHERE 절을 아예 붙이지 않는다. 검색 화면의 "비어 있는 입력칸은 조건에서 뺀다"는 요구가 이 세 규칙만으로 해결된다. 실험 결과를 보자.

    == ageGoe(26).and(deptName("dev"))
select ... from Employee e1_0 join Department d1_0 on d1_0.id=e1_0.department_id where e1_0.age>=? and d1_0.name=?
-> [kim]

    세 번째 경우는 두 명세가 모두 null을 돌려 WHERE가 사라진 것이고, 네 번째 경우는 nameEq(null)만 빠지고 나이 조건만 남은 것이다. 생성된 SQL의 바인딩 자리표시자(?)를 보면 사용자 입력이 SQL 문자열에 섞이지 않고 모두 매개변수로 바인딩된다는 것도 확인할 수 있다. 문자열 조립 방식이 가진 주입 위험이 구조적으로 사라지는 이유다.

    not()이 "나머지 전부"가 아닌 이유

    Specification.not(deptName("dev"))은 "dev 부서가 아닌 직원"처럼 들린다. 데이터에서 dev가 아닌 직원은 park, jung, Kimberly 세 명이다. 그런데 실제 결과는 두 명이다.

    select ... from Employee e1_0 join Department d1_0 on d1_0.id=e1_0.department_id where d1_0.name<>?
-> [park, Kimberly]

    jung이 빠진 이유는 두 겹이다. 첫 번째 겹은 조인이다. not은 안쪽 명세가 만든 술어에 builder.not을 씌울 뿐, 안쪽 명세가 root.join으로 추가한 내부 조인은 그대로 남는다. 부서가 없는 jung은 내부 조인 단계에서 이미 사라진다. 두 번째 겹은 SQL의 3값 논리(three-valued logic)다. 조인을 외부 조인으로 바꿔도 jung의 행에서 d1_0.name은 NULL이고, NULL <> 'dev'의 결과는 참도 거짓도 아닌 UNKNOWN이다. WHERE 절은 참인 행만 통과시키므로 jung은 여전히 빠진다. "dev가 아닌 모든 직원"을 원한다면 외부 조인을 쓰고 cb.isNull(d.get("id"))를 OR로 함께 걸어야 한다. 명세의 조합은 집합 연산이 아니라 술어의 조합이고, 술어는 SQL의 NULL 규칙을 그대로 따른다는 점을 잊지 말자.

    버전에 따라 달라진 출발점

    예전 코드에서는 Specification.where(nameEq(name)).and(...)처럼 where로 조합을 시작하는 모습을 자주 본다. 3.5.13 소스에서 이 메서드는 @Deprecated(since = "3.5.0", forRemoval = true)로 표시되어 있고, 주석은 "null 명세를 더는 지원하지 않으려 한다"는 이유를 밝힌다. 대신 "제한 없음"을 뜻하는 Specification.unrestricted()가 3.5.2에 추가되었다. 4.0으로 넘어가면 변화가 더 크다. 4.x 문서는 쿼리 종류에 묶이지 않는 PredicateSpecification이 Spring Data JPA 4.0에서 도입되었다고 설명하고, 갱신과 삭제를 위한 UpdateSpecification, DeleteSpecification도 함께 소개한다. 로컬에 있는 4.0.7 jar를 javap로 열어 보면 이 세 인터페이스가 실제로 들어 있고, Specification의 and, or, where에 PredicateSpecification을 받는 오버로드가 추가되어 있다. 이 강좌의 기준인 부트 3.x에서는 Specification 하나로 충분하다.

    명세 ③: 명세가 쿼리가 되기까지, 그리고 두 번의 호출

    이제 리포지토리 안으로 들어가 보자. JpaSpecificationExecutor는 findOne, findAll(목록, 정렬, 페이지), count, exists, delete, 그리고 3.0에서 추가된 findBy(플루언트 API)를 선언한다. 구현은 6회차에서 본 SimpleJpaRepository에 있다. 모든 경로가 거치는 핵심 메서드는 applySpecificationToCriteria다.

    // SimpleJpaRepository (3.5.13, 발췌)
private  Root applySpecificationToCriteria(@Nullable Specification spec,
        Class domainClass, CriteriaQuery query) {
    Root root = query.from(domainClass);          // FROM Employee
    if (spec == null) {
        return root;
    }
    CriteriaBuilder builder = entityManager.getCriteriaBuilder();
    Predicate predicate = spec.toPredicate(root, query, builder);   // 여기서 명세가 실행된다
    if (predicate != null) {
        query.where(predicate);
    }
    return root;
}

protected  TypedQuery getCountQuery(@Nullable Specification spec, Class domainClass) {
    CriteriaBuilder builder = entityManager.getCriteriaBuilder();
    CriteriaQuery query = builder.createQuery(Long.class);   // 새 쿼리
    Root root = applySpecificationToCriteria(spec, domainClass, query);   // 명세를 다시 실행
    if (query.isDistinct()) {
        query.select(builder.countDistinct(root));
    } else {
        query.select(builder.count(root));
    }
    // Remove all Orders the Specifications might have applied
    query.orderBy(Collections.emptyList());
    return applyRepositoryMethodMetadataForCount(entityManager.createQuery(query));
}

    목록 조회 경로(getQuery)는 builder.createQuery(Employee.class)로 쿼리를 만들고, 위 메서드로 FROM과 WHERE를 채운 뒤 query.select(root)로 엔티티 전체를 고르고, Sort가 있으면 orderBy를 붙인다. 그리고 entityManager.createQuery(query)로 TypedQuery를 얻은 다음 6회차에서 본 락 모드와 힌트를 적용한다. count 경로는 CriteriaQuery을 처음부터 새로 만들고 같은 명세를 다시 실행한다. 명세가 정렬을 걸었을 수도 있으니 정렬은 지우고, 명세가 query.distinct(true)를 걸었다면 count 대신 countDistinct를 쓴다. count 쿼리가 명세 안에서 무슨 일이 일어났는지 알 수 있는 단서는 이 두 가지뿐이다.

    정말 두 번 불리는지 확인해 보자. nameEq에 호출 횟수를 세는 카운터와, 넘어온 query.getResultType()을 찍는 줄을 넣고 nameEq(null).and(ageGoe(26))을 PageRequest.of(0, 2, Sort.by("age"))로 조회했다.

    findAll(spec, pageable) 한 번에 명세의 toPredicate가 서로 다른 두 CriteriaQuery에 대해 호출된다는 것을 보여 준다. 가로 16:9 시퀀스 다이어그램. 왼쪽부터 세로 생명선 네 개: "리포지토리 프록시", "SimpleJpaRepository", "명세(Specification)", "하이버네이트". 첫 화살표는 "리포지토리 프록시"에서 "SimpleJpaRepository"로 가며 라벨 "findAll(spec, pageable)". 위쪽 구간(파란색 배경)에 "본문 쿼리: CriteriaQuery(Employee)" 박스, 그 안에서 "SimpleJpaRepository"가 "명세"로 "toPredicate ①" 화살표, 돌아오는 점선 "Predicate", 이어서 "하이버네이트"로 "select ... offset/fetch" 화살표. 아래쪽 구간(주황색 배경)에 "count 쿼리: CriteriaQuery(Long)" 박스, 그 안에서 다시 "명세"로 "toPredicate ②" 화살표, "하이버네이트"로 "select count(...)" 화살표, 옆에 작은 메모 "정렬 제거". 마지막으로 "SimpleJpaRepository"에서 "리포지토리 프록시"로 점선 "Page". 두 toPredicate 화살표를 빨간 원으로 강조. 깔끔한 기술 문서 스타일, 흰 배경. 명세는 쿼리마다 다시 실행된다. 페이징 조회에서는 본문 쿼리와 count 쿼리, 두 번이다.

    count, exists, delete가 만드는 SQL

    나머지 메서드도 같은 틀을 쓴다. count(spec)는 위의 getCountQuery를 그대로 실행하고, exists(spec)는 CriteriaQuery에 상수 1을 고르게 한 뒤 최대 결과 수를 1로 제한한다. 존재 여부만 알면 되므로 개수를 세지 않고 첫 행 하나만 찾는다.

    명세 ④: 조인을 만드는 명세의 함정

    명세가 매번 다시 실행된다는 성질은 조인과 만나면 문제를 만든다. 첫 번째 문제는 조인의 중복이다. root.join(...)은 호출할 때마다 새 조인을 추가한다. 이미 같은 경로의 조인이 있는지 찾아서 재사용하지 않는다. 그래서 부서를 조인하는 명세 두 개를 and로 묶으면 조인이 두 번 생긴다.

    select ... from Employee e1_0
  join Department d1_0 on d1_0.id=e1_0.department_id
  join Department d2_0 on d2_0.id=e1_0.department_id
  where d1_0.name=? and d2_0.name=?
-> [kim, lee]

    다대일 조인이라 결과는 맞지만 데이터베이스는 같은 테이블을 두 번 조인하는 일을 한다. 일대다 컬렉션을 조인하는 명세라면 결과 행이 컬렉션 원소 수만큼 불어나고, 명세 두 개가 각자 컬렉션을 조인하면 곱으로 불어난다. 이때는 명세 안에서 query.distinct(true)를 걸게 되는데, 앞에서 본 것처럼 count 쿼리도 이를 보고 countDistinct로 바뀐다. 여러 명세가 같은 조인을 공유해야 한다면 root.getJoins()에서 이미 만든 조인을 찾아 쓰는 식으로 직접 관리해야 한다.

    페치 조인 명세는 count 쿼리에서 깨진다

    return (root, query, cb) -> { root.fetch("department", JoinType.LEFT); return null; };

    명세가 맞지 않는 곳

    명세의 한계도 분명하다. root.get("name")의 속성 이름은 문자열이므로 오타는 컴파일러가 잡지 못하고 실행 시점에야 실패한다. JPA 명세는 이를 위해 애너테이션 처리기로 만드는 정적 메타모델(static metamodel) 클래스, 즉 Employee_.name 같은 타입 안전한 속성 참조를 정의해 두었지만, 그래도 Criteria 코드는 길고 읽기 어렵다. 조건 세 개를 표현하는 데 람다, 조인 변수, 빌더 호출이 겹겹이 쌓이고, 조건이 복잡해질수록 그 코드가 어떤 SQL이 될지 머릿속으로 그리기가 어렵다. 다음 권에서 다루는 Querydsl은 같은 "동적 조건의 객체화"를 JPQL과 닮은 문법으로 풀어낸다. 이 회차에서는 명세가 어떤 원리로 동작하는지, 그리고 그 원리가 만드는 함정이 무엇인지만 확실히 잡아 두자.

    Query By Example ①: 예시 객체로 묻는다

    명세가 "조건을 코드로 쓴다"면, Query By Example(QBE)은 "찾고 싶은 것과 닮은 객체를 하나 보여 준다". 검색 화면의 입력값을 엔티티 객체에 그대로 채워 넣고, 그 객체와 닮은 행을 찾아 달라고 요청하는 방식이다. 스프링 데이터 문서는 QBE를 네 부품으로 설명한다. 필드가 채워진 실제 도메인 객체인 probe, 필드별 일치 방식을 담는 ExampleMatcher, 이 둘을 묶어 쿼리 생성에 쓰이는 Example, 그리고 정렬이나 프로젝션 같은 추가 설정을 위한 플루언트 API FetchableFluentQuery다.

    QBE를 쓰려고 따로 인터페이스를 상속할 필요는 없다. 3.5.13의 JpaRepository를 javap로 열어 보면 ListCrudRepository, ListPagingAndSortingRepository와 함께 QueryByExampleExecutor를 상속한다. QueryByExampleExecutor는 JPA 모듈이 아니라 스프링 데이터 커먼즈에 정의된 저장소 중립 인터페이스이고, findOne(Example), findAll(Example), count(Example), exists(Example), findBy(Example, ...)를 선언한다. 즉 지금까지 만든 모든 JpaRepository 리포지토리는 이미 QBE 메서드를 갖고 있었다.

    Employee probe = new Employee("kim", 0, null);       // 이름이 kim인 직원과 "닮은" 행
List r1 = repo.findAll(Example.of(probe));  // 기본 매처: ExampleMatcher.matching()

ExampleMatcher matcher = ExampleMatcher.matching().withIgnorePaths("age");
List r2 = repo.findAll(Example.of(probe, matcher));

    구현을 열어 보면 QBE가 별도의 쿼리 엔진이 아니라는 사실이 드러난다. SimpleJpaRepository.findAll(Example)의 몸체는 한 줄이다. getQuery(new ExampleSpecification<>(example, escapeCharacter), example.getProbeType(), Sort.unsorted()).getResultList(). 예시를 ExampleSpecification이라는 명세로 감싸서 앞 절에서 본 명세 경로에 그대로 태운다. 이 명세의 toPredicate는 QueryByExamplePredicateBuilder.getPredicate(root, cb, example, escapeCharacter)를 부를 뿐이다. 그러니 앞에서 본 성질, 즉 페이징 조회에서 본문과 count 쿼리에 대해 두 번 실행된다는 것, exists가 select 1 ... fetch first가 된다는 것이 QBE에도 그대로 적용된다. QBE는 "probe 객체를 읽어서 명세를 자동으로 만들어 주는 장치"라고 이해하면 정확하다.
