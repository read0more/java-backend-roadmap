    이 회차의 질문: 몸체 없는 메서드가 어떻게 SQL이 되는가

    앞 회차(02회)에서는 JpaRepository 같은 공통 인터페이스를 상속하기만 하면 저장, 단건 조회, 전체 조회, 삭제가 동작하는 것을 보았다. 그 메서드들은 사실 몸체가 있다. Spring Data JPA가 미리 구현해 둔 SimpleJpaRepository라는 클래스가 있고, 리포지토리 프록시가 호출을 그 객체로 넘겨 줄 뿐이다. 이 구조의 내부는 06회에서 자세히 다룬다.

    이번 회차의 메서드는 다르다. findByAuthorAndPriceGreaterThan(String author, int price)라고 인터페이스에 적으면, 이 메서드를 구현한 클래스는 세상 어디에도 없다. 그런데도 호출하면 where author=? and price>?라는 SQL이 나간다. 누군가 메서드 이름을 읽고, 엔티티의 필드와 대조하고, 쿼리를 조립해서 실행한 것이다. 이 회차는 그 "누군가"가 언제, 무엇을, 어떤 순서로 하는지를 추적한다.

    공개된 커리큘럼에서 이 회차가 맡는 수업 주제는 여섯 가지다. 메서드 이름으로 쿼리 생성, JPA NamedQuery, @Query로 리포지토리 메서드에 쿼리 정의하기, @Query로 값과 DTO 조회하기, 파라미터 바인딩, 반환 타입이다. 같은 섹션의 뒷부분인 페이징과 정렬, 벌크성 수정 쿼리, @EntityGraph, 힌트와 락은 04회의 몫이다.

    이 회차의 실험은 모두 Spring Data JPA 3.5.13(Spring Data Commons 3.5.13) + Spring Framework 6.2.19 + Hibernate ORM 6.6.53.Final + H2 2.3.232 + JDK 21에서 직접 실행했다. Spring Boot 3.5 계열이 쓰는 조합이다. 스프링 부트 없이 AnnotationConfigApplicationContext와 @EnableJpaRepositories만으로 컨테이너를 띄웠고, Hibernate의 hibernate.show_sql로 실제 SQL을 찍었다. SQL의 별칭(b1_0)과 행 제한 구문은 데이터베이스 방언(dialect)에 따라 달라지므로 MySQL에서는 모양이 다를 수 있다. 내부 클래스 이름과 메시지는 위 버전의 jar를 javap로 열어 확인한 것이며, 다른 버전에서는 달라질 수 있다.

    기동 시점에 일어나는 일: 메서드마다 쿼리 객체를 미리 만든다

    첫 번째 사실부터 확인하자. 메서드 이름을 해석하는 일은 메서드를 처음 호출할 때가 아니라 리포지토리 빈을 만들 때 일어난다. 이를 보려면 일부러 틀린 메서드를 하나 만들어 보면 된다. 필드 이름 title을 titel로 잘못 쓴 메서드만 가진 리포지토리를 따로 만들고 컨테이너를 띄우면, 아무 메서드도 호출하지 않았는데 컨테이너 기동 자체가 실패한다.

    이 구조가 주는 실무적 의미는 분명하다. 메서드 이름의 오타나 존재하지 않는 프로퍼티는 애플리케이션이 뜨는 순간 실패로 드러난다. 운영 중에 그 메서드가 처음 불릴 때까지 숨어 있지 않는다. 자바 컴파일러는 메서드 이름이라는 문자열의 의미를 모르므로 컴파일 단계에서는 잡을 수 없지만, 테스트에서 스프링 컨텍스트를 한 번만 띄워도 잡힌다. 다만 기동 때 검증되지 않는 실수도 있다. 이 회차 뒤쪽의 파라미터 이름 문제가 그 예다.

    기동 시점에 인터셉터가 메서드별 쿼리 객체를 만들고, 조회 전략이 @Query → 이름 있는 쿼리 → 메서드 이름 파생 순으로 시도하는 흐름을 보여 준다. 왼쪽에서 오른쪽으로 다섯 개의 세로 생명선이 있는 시퀀스 다이어그램. 생명선 라벨은 차례로 "스프링 컨테이너", "JpaRepositoryFactoryBean", "QueryExecutorMethodInterceptor", "JpaQueryLookupStrategy", "PartTree". 컨테이너에서 팩토리 빈으로 "afterPropertiesSet" 화살표, 팩토리 빈에서 인터셉터로 "생성" 화살표, 인터셉터에서 조회 전략으로 메서드마다 반복되는 "resolveQuery(메서드)" 화살표(반복 구간을 점선 상자로 감싸고 "쿼리 메서드마다" 라벨). 조회 전략 생명선 옆에 세 갈래 분기 상자: 위에서부터 "① @Query", "② 이름 있는 쿼리", "③ 메서드 이름 파생". ③에서 PartTree로 "이름 해석" 화살표. 인터셉터 아래에 표 모양 상자 "Method → RepositoryQuery 맵". 맨 아래 빨간 번개 아이콘과 "오류는 기동 시점에 드러난다" 라벨. 흰 배경, 단순한 선, 파란 계열 강조. 쿼리 메서드는 호출 시점이 아니라 리포지토리 빈을 만들 때 해석되어 맵에 저장된다.

    조회 전략: 선언된 쿼리가 먼저, 이름 파생은 마지막

    5단계의 조회 전략(query lookup strategy)은 세 가지가 있다. CREATE는 메서드 이름에서만 쿼리를 만들고, USE_DECLARED_QUERY는 선언된 쿼리만 찾으며 없으면 기동 때 실패한다. 기본값인 CREATE_IF_NOT_FOUND는 둘을 합친 것으로, 선언된 쿼리를 먼저 찾고 없을 때만 메서드 이름으로 만든다. 전략은 @EnableJpaRepositories(queryLookupStrategy = ...)로 바꿀 수 있지만 기본값을 바꿀 일은 드물다.

    "선언된 쿼리를 찾는다"의 내부 순서는 문서보다 바이트코드가 더 정확하게 보여 준다. 3.5.13의 JpaQueryLookupStrategy$DeclaredQueryLookupStrategy.resolveQuery를 javap -c로 열면 다음 순서로 검사한다.

    1. 메서드가 저장 프로시저 쿼리(@Procedure)인가.
    2. @Query에 쿼리 문자열이 있는가. 있으면 그것을 쓴다. 이때 @Query(name = ...)까지 함께 지정되어 있으면 "Query method %s is annotated with both, a query and a query name; Using the declared query"라는 경고를 남기고 문자열 쪽을 쓴다.
    3. Spring Data의 속성 파일 방식 이름 있는 쿼리(기본 위치 META-INF/jpa-named-queries.properties)에 그 이름이 있는가.
    4. JPA의 이름 있는 쿼리(@NamedQuery 또는 orm.xml)에 그 이름이 있는가. NamedQuery.lookupFrom이 이 일을 한다.

    넷 다 없으면 CreateIfNotFoundQueryLookupStrategy가 메서드 이름 파생으로 넘어간다. 앞의 오타 예제의 스택 트레이스에 CreateIfNotFoundQueryLookupStrategy와 CreateQueryLookupStrategy가 차례로 찍힌 것이 바로 이 흐름이다. 이 순서 때문에 Spring Data JPA 문서는 "메서드에 붙인 @Query가 @NamedQuery나 orm.xml의 이름 있는 쿼리보다 우선한다"고 적는다.

    이 순서에서 중요한 결론이 하나 나온다. 메서드 이름이 파생 쿼리 규칙에 맞는다고 해서 반드시 파생 쿼리가 실행되는 것은 아니다. findByAuthor는 이름만 보면 where author = ?로 파생될 것 같지만, 엔티티에 Book.findByAuthor라는 이름 있는 쿼리가 있으므로 그쪽이 먼저 잡힌다. 실험에서 두 메서드를 나란히 불러 보면 SQL이 다르다.

    메서드 이름 해석 ①: 주어와 술어로 자르기

    이제 선언된 쿼리가 없어서 이름 파생으로 넘어온 경우를 보자. 메서드 이름을 해석하는 클래스는 Spring Data Commons의 PartTree다. 이름 그대로 메서드 이름을 부분(Part)들의 트리로 바꾼다. 트리의 뿌리는 두 갈래다. 앞쪽의 주어(subject)는 "무엇을, 몇 개, 어떤 형태로" 가져올지, 뒤쪽의 술어(predicate)는 "어떤 조건으로, 어떤 순서로" 가져올지를 정한다. 경계는 처음 나오는 By다.

    이 경계를 찾는 정규식이 클래스 상수로 들어 있다. 3.5.13의 PartTree를 javap -constants로 열면 다음 문자열을 볼 수 있다.

    QUERY_PATTERN  = "find|read|get|query|search|stream"
COUNT_PATTERN  = "count"
EXISTS_PATTERN = "exists"
DELETE_PATTERN = "delete|remove"
접두사 판별:  ^(find|read|get|query|search|stream|count|exists|delete|remove)((\p{Lu}.*?))??By
조회 주어:    ^(find|read|get|query|search|stream)(Distinct)?(First|Top)(\d*)?(\p{Lu}.*?)??By
개수 주어:    ^count(\p{Lu}.*?)??By
존재 주어:    ^(exists)(\p{Lu}.*?)??By
삭제 주어:    ^(delete|remove)(\p{Lu}.*?)??By

    여기서 몇 가지가 곧바로 읽힌다. 첫째, 조회 접두사는 find, read, get, query, search, stream 여섯 개가 모두 같은 의미다. getByTitle과 findByTitle은 같은 쿼리를 만든다. 둘째, 접두사와 By 사이의 대문자로 시작하는 문자열 (\p{Lu}.*?)??는 Distinct, First, Top이 아니면 그냥 무시된다. 문서도 이 부분을 "설명용(descriptive)" 텍스트라고 부른다. 그래서 findBooksByAuthor의 Books, findOptionalByTitle의 Optional, findListByTitle의 List는 쿼리에 아무 영향이 없다. 이름에 Optional이라고 썼다고 Optional이 반환되는 것이 아니라, 반환 타입이 Optional이어서 그렇게 되는 것이다. 셋째, First와 Top 뒤의 숫자 (\d*)는 생략할 수 있고, 생략하면 1건으로 제한된다.

    By를 찾는 부분이 게으른 수량자 ??와 .*?로 되어 있다는 점도 의미가 있다. 정규식이 가능한 한 짧게 일치하려 하므로 처음 나오는 By에서 주어가 끝난다. findByOrderByPriceDesc처럼 By가 두 번 나오는 이름에서는 첫 By가 주어와 술어를 나누고, 두 번째 By는 술어 안의 OrderBy의 일부가 된다.

    술어 쪽은 두 번 잘린다. 먼저 Or로 자르고, 잘린 조각을 다시 And로 자른다. 자르는 키워드는 (%s)(?=(\p{Lu}|\P{InBASIC_LATIN}))라는 템플릿으로 만든 정규식이라서, 키워드 바로 뒤에 대문자(또는 기본 라틴 문자가 아닌 글자)가 와야만 키워드로 인정된다. 그래서 Order라는 프로퍼티의 Or는 뒤에 소문자 d가 오므로 잘리지 않는다. 술어 끝에 OrderBy가 있으면 그 뒷부분은 정렬로 따로 떼어 낸다. 정렬 블록은 (?<=Asc|Desc)(?=\p{Lu})로 다시 잘려 PriceDescTitleAsc가 PriceDesc와 TitleAsc 두 정렬 조건이 된다.

    Or로 먼저 자르고 And로 나중에 자른다는 것은, 결과가 항상 "And 묶음들의 Or" 모양이 된다는 뜻이다. 논리식으로 말하면 논리합 표준형(disjunctive normal form)이다. 괄호를 쓸 방법은 없다. 실험의 findByAuthorOrPriceLessThanAndTitleStartingWith("lee", 29000, "SQL")은 이렇게 해석되고 실행된다.

    author SIMPLE_PROPERTY (1) or price LESS_THAN (1) and title STARTING_WITH (1)

select ... from Book b1_0 where b1_0.author=? or b1_0.price> [Book(Java Threads, lee, 32000), Book(SQL Tuning, park, 28000)]

    SQL에서 AND는 OR보다 먼저 결합하므로 이 조건은 author = 'lee' OR (price < 29000 AND title LIKE 'SQL%')이다. 결과의 첫 행은 앞쪽 조건으로, 둘째 행은 뒤쪽 And 묶음으로 걸렸다. 만약 "(작가가 lee이거나 가격이 29000 미만) 그리고 제목이 SQL로 시작"을 원했다면 메서드 이름으로는 표현할 수 없다. 분배 법칙으로 펼쳐 findByAuthorAndTitleStartingWithOrPriceLessThanAndTitleStartingWith처럼 쓸 수는 있지만, 이 정도가 되면 @Query로 직접 쓰는 편이 읽기 쉽다.

    하나의 긴 메서드 이름이 첫 By를 경계로 주어와 술어로 나뉘고, 술어가 Or → And 순서로 쪼개져 Part가 되는 모습을 보여 준다. 맨 위에 가로로 긴 상자 하나에 메서드 이름 "findDistinctTop3ByAuthorOrPriceLessThanAndTitleStartingWithOrderByPriceDesc"를 고정폭 글꼴로 쓴다. 첫 "By" 위치에 빨간 세로 점선을 긋고 라벨 "첫 By". 왼쪽 가지는 "주어" 노드로 내려가며 하위에 작은 칩 "Distinct", "Top 3". 오른쪽 가지는 "술어" 노드로 내려가고, 술어에서 두 개의 "Or 묶음" 노드로 갈라진다. 첫 Or 묶음 아래에 Part 상자 하나 "author =", 두 번째 Or 묶음 아래에 "And"로 연결된 Part 상자 두 개 "price <", "title like 'x%'". 술어 노드 오른쪽 끝에서 따로 "정렬" 노드로 가는 가지, 그 아래 "price desc". 각 Part 상자 오른쪽 아래에 작은 숫자 배지로 "인자 1"을 표시. 흰 배경, 트리 선은 회색, 주어는 주황, 술어는 파랑, 정렬은 초록. 메서드 이름은 첫 By에서 주어와 술어로 나뉘고, 술어는 Or 다음 And 순서로 쪼개진다. 결과는 항상 And 묶음들의 Or다.

    메서드 이름 해석 ②: 조건 키워드와 인자 개수

    And로 잘린 조각 하나가 Part다. Part는 생성될 때 두 가지를 정한다. 어떤 비교인가(Part.Type)와 어떤 프로퍼티인가(PropertyPath)다. 비교 종류는 조각의 끝부분을 보고 정한다. Part.Type.fromProperty는 미리 정해 둔 타입 목록을 순서대로 돌며 String.endsWith로 키워드를 대조하고, 처음 맞는 타입을 고른다. 아무것도 맞지 않으면 마지막 기본값인 단순 동등 비교(SIMPLE_PROPERTY)가 된다. 비교 종류가 정해지면 조각의 첫 글자를 소문자로 바꾸고(Introspector.decapitalize) 끝의 키워드를 잘라 낸 나머지를 프로퍼티 이름으로 쓴다.

    인자 개수는 생각보다 중요하다. 파생 쿼리의 파라미터 바인딩은 이름이 아니라 순서로 이루어진다. 트리를 왼쪽부터 훑으며 각 Part가 자기 몫의 인자 개수만큼 메서드 인자를 차례로 가져간다. Between은 두 개, IsNull과 True는 0개를 가져간다. 그래서 파생 쿼리에는 @Param이 필요 없고, 메서드 파라미터의 이름이 무엇이든 상관없다. 대신 인자의 순서를 바꾸면 조용히 다른 조건에 값이 들어간다. 타입이 맞지 않으면 기동 때 잡히는 경우도 있다. PartTreeJpaQuery에는 "Method %s expects at least %d arguments but only found %d"로 시작하는 메시지와 "Operator %s on %s requires a %s argument, found %s in method %s"라는 메시지가 들어 있어서, 인자가 모자라거나 In에 컬렉션이 아닌 인자를 주는 식의 불일치를 쿼리 생성 단계에서 거부한다.

    대소문자 무시도 Part 단위의 속성이다. findBooksByAuthorIgnoreCase를 해석한 PartTree.toString()은 그 Part에 ALWAYS를 찍고, findByTitleAndAuthorAllIgnoreCase는 모든 Part에 WHEN_POSSIBLE을 찍는다. 앞의 것은 그 프로퍼티에 무조건 적용하고, 뒤의 것은 문자열처럼 적용할 수 있는 프로퍼티에만 적용한다는 뜻이다. 실제 SQL에서는 양쪽에 upper()를 씌운다.

    끝부분 일치가 만드는 함정

    "끝부분이 키워드로 끝나면 그 키워드로 본다"는 규칙은 프로퍼티 이름이 우연히 키워드로 끝날 때 문제를 일으킨다. 체크인 여부를 나타내는 boolean checkedIn 필드를 가진 Guest 클래스에 대해 PartTree를 직접 만들어 보면 다음과 같다.

    findByCheckedIn     -> PropertyReferenceException: No property 'checked' found for type 'Guest'; Did you mean 'checkedIn'
findByCheckedInIs   -> checkedIn SIMPLE_PROPERTY (1): [Is, Equals]
findByCheckedInTrue -> checkedIn TRUE (0): [IsTrue, True]

    CheckedIn은 In으로 끝나므로 IN 비교로 해석되고, 키워드를 잘라 낸 checked라는 프로퍼티를 찾다가 실패한다. 타입 목록에서 IN이 단순 비교보다 앞에 있기 때문이다. 이때는 뒤에 Is를 붙여 끝부분을 바꾸거나, boolean이면 True/False 키워드를 쓰면 된다. 둘 다 원래 의도한 checkedIn 프로퍼티로 해석된다. 오류 메시지의 "Did you mean 'checkedIn'"이 해결의 실마리를 준다.

    메서드 이름 해석 ③: 프로퍼티 경로 찾기

    Part에서 키워드를 떼어 낸 나머지 문자열은 엔티티의 프로퍼티 경로(property path)로 해석된다. 단순한 경우는 Title → title처럼 한 단계지만, countByPublisherCity의 PublisherCity처럼 연관을 따라 들어가는 경우가 있다. Spring Data 문서가 설명하는 해석 알고리즘은 다음과 같다. 먼저 조각 전체(publisherCity)를 프로퍼티 이름으로 보고 찾는다. 없으면 낙타 표기(camel case)의 경계에서 오른쪽부터 잘라 머리(head)와 꼬리(tail)로 나눈다. 머리에 해당하는 프로퍼티가 있으면 그 타입 안에서 꼬리를 같은 방식으로 다시 찾는다. 첫 분할이 실패하면 분할 지점을 한 칸 왼쪽으로 옮겨 다시 시도한다.

    문서의 예는 AddressZipCode다. 전체 이름 addressZipCode가 없으면 AddressZip + Code로 나눠 보고, 그것도 안 되면 Address + ZipCode로 나눈다. 이 회차의 PublisherCity는 경계가 하나뿐이라 Publisher + City로 바로 나뉘고, Book.publisher의 타입인 Publisher에서 city를 찾는다. 이 탐색은 "전체 이름 먼저"이므로, 만약 Book에 publisherCity라는 문자열 필드가 따로 있었다면 연관을 따라가지 않고 그 필드가 선택된다. 이런 모호함을 피하려고 밑줄(_)로 경계를 직접 지정할 수 있다. findByPublisher_City는 "publisher 안의 city"라고 못 박는다. 문서는 밑줄을 예약 문자로 취급하므로 필드 이름에는 밑줄 대신 낙타 표기를 쓰라고 권한다.

    이 해석이 엔티티 매핑이 아니라 자바 타입 정보로 이루어진다는 점도 짚어 둘 만하다. 앞의 Guest 예제는 @Entity조차 붙지 않은 평범한 클래스였는데 PartTree가 문제없이 동작했다. PartTree와 PropertyPath는 Spring Data Commons에 있는, 저장소와 무관한 코드다. 같은 해석기를 Spring Data MongoDB나 Redis 모듈도 쓴다. 저장소별 모듈은 이렇게 만들어진 트리를 받아 자기 쿼리 언어로 옮기는 일만 한다. JPA 모듈에서 그 일을 하는 것이 다음 절의 JpaQueryCreator다.

    연관을 따라가는 파생 쿼리는 SQL에 조인을 만든다. 실험에서 countByPublisherCity("Paju")와 findDistinctByPublisherName("North Press")는 다음 SQL을 냈다.

    select count(b1_0.id) from Book b1_0 left join Publisher p1_0 on p1_0.id=b1_0.publisher_id where p1_0.city=?
>> 2

select distinct b1_0.id,b1_0.author,b1_0.price,b1_0.publisher_id,b1_0.title from Book b1_0
  left join Publisher p1_0 on p1_0.id=b1_0.publisher_id where p1_0.name=?
>> [Book(JPA Basics, kim, 30000), Book(Spring Data, kim, 25000)]

    3.5.13의 파생 쿼리는 연관 경로를 따라갈 때 외부 조인(left join)을 만들었다. 다만 where p1_0.city=?가 출판사 쪽 컬럼을 비교하므로, 출판사가 없어서 null로 채워진 행은 이 조건을 통과하지 못한다. 그래서 결과 집합은 내부 조인을 썼을 때와 같다. Distinct 키워드는 SQL의 select distinct로 그대로 옮겨졌다. 조회 대상이 출판사가 아니라 책이고, 다대일 조인은 책 한 건당 많아야 한 행만 붙으므로 이 쿼리에서는 distinct가 없어도 중복이 생기지 않는다. 일대다 컬렉션을 따라갈 때라면 이야기가 달라진다.

    파생 쿼리가 SQL이 되기까지

    PartTreeJpaQuery는 만들어질 때 PartTree를 하나 갖고, 실행될 때 그 트리를 JPA 쿼리로 바꾼다. 3.5.13의 JpaQueryCreator를 javap로 열면 AbstractQueryCreator<CriteriaQuery<?>, Predicate>를 상속하고 CriteriaBuilder와 Root를 필드로 가진다. 즉 3.x의 파생 쿼리는 JPA Criteria API 객체로 조립된다. 각 Part가 Criteria의 Predicate 하나가 되고, And 묶음은 builder.and로, Or 묶음은 builder.or로 합쳐지며, 마지막에 정렬이 붙는다. 이 Criteria 객체를 Hibernate가 내부 표현(SQM)을 거쳐 SQL로 바꾼다.

    같은 클래스를 Spring Data JPA 4.0.7 jar에서 열어 보면 AbstractQueryCreator<String, JpqlQueryBuilder.Predicate>를 상속한다. 4.0 계열(Spring Boot 4 세대)에서는 파생 쿼리를 Criteria 객체 대신 JPQL 문자열로 렌더링한다는 뜻이다. 이 회차의 기준 버전인 3.5 계열은 Criteria 방식이다.

    실험에서 나온 SQL을 메서드 이름과 나란히 놓으면 Part 하나하나가 어디로 갔는지 보인다.

    메서드(인자)실행된 SQL의 핵심 부분결과

    표의 몇 줄은 따로 볼 만하다. Containing은 SQL에 like ?만 남기고, 바인딩하는 값 쪽에 %를 앞뒤로 붙인다. 이때 사용자가 넘긴 값 안에 %나 _ 같은 와일드카드 문자가 있으면 이스케이프 문자로 무력화하는데, 그 이스케이프 문자가 SQL의 escape '\'로 함께 전달된 것이다. IgnoreCase는 컬럼과 값 양쪽에 upper()를 씌웠다. 컬럼에 함수를 씌우면 그 컬럼의 일반 인덱스를 범위 탐색에 그대로 쓰기 어렵다는 점은 데이터베이스 권에서 본 대로다. Top2는 SQL의 행 제한 구문이 되었다. H2 방언은 표준 문법인 fetch first ? rows only를 쓰고, MySQL 방언이라면 limit 절로 바뀐다. exists 접두사는 엔티티 전체가 아니라 식별자 하나만 고르고 한 행으로 제한하는 쿼리가 되었다. 한 행이라도 있으면 true다.

    null 인자는 조건을 지우지 않는다

    마지막 줄이 실무에서 가장 자주 사고를 낸다. findBooksByAuthor(null)은 "작가 조건 없이 전부"가 아니라 where author is null이 되었다. SQL에서 author = NULL은 어떤 행에도 참이 되지 않으므로 Spring Data는 null 인자를 is null로 바꿔 준다. 문서의 키워드 표도 Is/Equals에 "인자가 null이면 IS NULL"이라고 적는다. 검색 화면에서 비어 있는 입력을 null로 넘기면 "조건을 무시한다"가 아니라 "그 컬럼이 비어 있는 행만 찾는다"가 되는 것이다. 조건이 있을 수도 없을 수도 있는 동적 검색은 메서드 이름 파생으로 표현할 수 없다.

    null 여부에 따라 SQL의 모양이 바뀐다는 사실은 내부 구현에도 흔적을 남긴다. PartTreeJpaQuery 안의 QueryPreparer는 cachedCriteriaQuery라는 필드에 미리 만든 Criteria 쿼리를 보관해 두고 재사용한다. 그런데 createQuery의 바이트코드를 보면, 캐시가 없거나 인자 중에 바인딩할 null 값이 있으면(hasBindableNullValue()) 캐시를 쓰지 않고 쿼리 생성기를 새로 만들어 Criteria를 다시 조립한다. null이 들어온 호출은 매번 쿼리를 새로 조립하는 비용을 치른다.

    파생 삭제 쿼리는 지우기 전에 읽는다

    deleteByTitle처럼 delete나 remove로 시작하는 파생 쿼리는 DELETE 문 하나를 보내지 않는다. 실험에서 트랜잭션 안에서 호출하면 다음 두 SQL이 순서대로 나갔다.

    select b1_0.id,b1_0.author,b1_0.price,b1_0.publisher_id,b1_0.title from Book b1_0 where b1_0.title=?
delete from Book where id=?
>> deleteByTitle(tx) = 1

    조건에 맞는 엔티티를 먼저 조회해서 영속성 컨텍스트에 올리고, 한 건씩 EntityManager.remove를 호출한 것이다. 그래서 엔티티의 생명주기 콜백과 영속성 전이(cascade)가 동작하지만, 대상이 만 건이면 조회 한 번에 DELETE 만 번이다. 트랜잭션 없이 호출하면 SELECT는 실행된 뒤 remove 단계에서 "No EntityManager with actual transaction available for current thread - cannot reliably process 'remove' call"이라는 InvalidDataAccessApiUsageException으로 실패했다. 한 문장으로 대량 삭제하는 벌크 쿼리는 04회의 주제이고, 리포지토리 메서드의 기본 트랜잭션 설정은 06회에서 다룬다.

    JPA NamedQuery: 이름으로 찾아오는 정적 쿼리

    이름 있는 쿼리(named query)는 JPA 표준 기능이다. 엔티티 클래스에 @NamedQuery(name = ..., query = ...)로 JPQL에 이름을 붙여 두고, 순수 JPA에서는 em.createNamedQuery("Book.findByAuthor", Book.class)로 불러 쓴다. Spring Data JPA는 이 이름을 메서드와 자동으로 연결한다. 연결 규칙은 QueryMethod.getNamedQueryName()의 바이트코드에 그대로 있다. "%s.%s" 형식 문자열에 도메인 클래스의 getSimpleName()과 메서드의 getName()을 넣는다. BookRepository.findByAuthor는 Book.findByAuthor를 찾는 것이다. 이 규칙을 따르지 않는 이름을 쓰고 싶으면 메서드에 @Query(name = "...")로 직접 지정한다.

    이름 있는 쿼리의 가장 큰 장점은 검증 시점이다. Hibernate는 영속성 유닛을 만들 때, 즉 EntityManagerFactory를 만들 때 모든 이름 있는 쿼리를 해석해 본다. 필드 이름을 bodi로 잘못 쓴 이름 있는 쿼리를 가진 엔티티로 실험하면, 리포지토리는커녕 EntityManagerFactory 생성 단계에서 실패한다.

    PersistenceException: [PersistenceUnit: default] Unable to build Hibernate SessionFactory;
  nested exception is org.hibernate.query.NamedQueryValidationException: Errors in named queries:
  [1] Error in query named 'Memo.findByBody': Could not resolve attribute 'bodi' of 'demo2.Memo'
      [select m from Memo m where m.bodi = :body]

    오류 보고가 모든 이름 있는 쿼리를 모아 번호를 붙여 보여 준다는 점도 눈여겨볼 만하다. 하나 고치고 다시 띄우고를 반복하지 않아도 된다.

    단점은 거리다. 쿼리는 엔티티에, 그 쿼리를 쓰는 메서드는 리포지토리에 있다. 둘을 잇는 것은 "클래스 단순 이름.메서드 이름"이라는 문자열 규칙뿐이고, 컴파일러는 이 연결을 모른다. 더 위험한 것은 앞의 조회 순서와 결합할 때다. 누군가 리포지토리의 findByAuthor를 getByAuthor로 이름만 바꾸면, Book.getByAuthor라는 이름 있는 쿼리는 없으므로 CREATE_IF_NOT_FOUND 전략은 조용히 메서드 이름 파생으로 넘어간다. getByAuthor는 파생 규칙에도 맞는 이름이라 기동도 성공한다. 그 결과 order by price desc가 사라진 쿼리가 실행되지만 아무 오류도 나지 않는다. 이름 있는 쿼리를 쓴다면 이 연결이 깨지지 않았는지 테스트로 확인해야 하는 이유다.

    이 단점 때문에 실무에서는 이름 있는 쿼리 대신 다음 절의 @Query를 주로 쓴다. 이름 있는 쿼리가 주던 기동 시점 검증을 @Query도 똑같이 주면서, 쿼리를 메서드 바로 위에 둘 수 있기 때문이다.

    @Query: 메서드 위에 JPQL을 직접 쓴다

    @Query에 JPQL을 적으면 조회 전략의 두 번째 단계에서 잡혀 SimpleJpaQuery라는 쿼리 객체가 된다. 이 객체는 생성자에서 쿼리를 검증한다. 3.5.13의 SimpleJpaQuery에는 "Query '%s' validation failed for method %s"라는 메시지가 들어 있고, 검증은 쿼리 문자열을 EntityManager에 넘겨 실제로 JPA 쿼리를 만들어 보는 방식이다. 필드 이름을 틀린 @Query로 실험하면 이렇게 실패한다.

    QueryCreationException: Could not create query for ... findByTitleQuery(java.lang.String);
  Reason: Query 'select b from Book b where b.titel = :title' validation failed for method ...
 └ IllegalArgumentException: org.hibernate.query.sqm.UnknownPathException:
       Could not resolve attribute 'titel' of 'demo.Book' [select b from Book b where b.titel = :title]
    └ PathElementException: Could not resolve attribute 'titel' of 'demo.Book'

    바깥 두 겹은 Spring Data의 예외이고, 안쪽은 Hibernate의 JPQL 해석기가 낸 예외다. Hibernate는 JPQL 문자열을 구문 분석해 SQM(Semantic Query Model)이라는 트리로 만들고, 그 과정에서 b.titel이라는 경로를 Book의 메타모델에서 찾지 못해 멈췄다. 이 검증 역시 리포지토리 빈을 만들 때 일어나므로 애플리케이션 기동이 실패한다. 오류를 발견하는 시점을 정리하면 쿼리를 어디에 두느냐에 따라 다음과 같이 갈린다.

    쿼리를 두는 곳오류가 드러나는 시점검사하는 주체

    @NamedQueryEntityManagerFactory 생성 때Hibernate(이름 있는 쿼리 검증)

    @Query 문자열은 Hibernate에 곧바로 전달되지 않는다. Spring Data JPA가 먼저 문자열을 자기 나름대로 읽는다. 어떤 파라미터가 쓰였는지(이름 기반인지 위치 기반인지), Spring Data 고유의 확장 문법이 들어 있는지 알아야 하기 때문이다. 이 일을 하는 StringQuery는 패키지 전용 클래스라서, 실험에서는 같은 패키지 이름으로 작은 클래스를 만들어 직접 불러 보았다. 결과는 뒤의 「컬렉션 바인딩과 LIKE 바인딩」 절에서 다시 본다. nativeQuery = true로 SQL을 직접 쓰는 네이티브 쿼리도 같은 애너테이션을 쓰지만, 그 차이는 07회에서 다룬다.

    @Query로 값과 DTO 조회하기

    @Query의 select 절에는 엔티티만 올 수 있는 것이 아니다. 엔티티의 필드 하나만 고르면 그 값의 타입으로 결과가 나온다. 실험의 findTitles()는 select b.title from Book b order by b.price이고, 반환 타입은 List<String>이다.

    select b1_0.title from Book b1_0 order by b1_0.price
>> findTitles = [Spring Data, SQL Tuning, JPA Basics, Java Threads]

    SQL을 보면 title 컬럼 하나만 읽는다. 결과 목록의 원소는 String이고, 엔티티가 아니므로 영속성 컨텍스트에 아무것도 올라가지 않는다. 컬럼을 둘 이상 고르면 JPA 표준대로 한 행이 Object[] 하나가 된다. select b.title, b.price from Book b where b.author = :author order by b.price를 List<Object[]>로 받으면 [Spring Data, 25000], [JPA Basics, 30000] 두 배열이 나왔다. 배열 칸의 순서는 select 절의 순서이고 타입은 컴파일러가 확인해 주지 않으므로, 꺼낼 때마다 캐스팅해야 한다.

    캐스팅을 없애는 방법이 생성자 표현식(constructor expression)이다. select 절에 new와 클래스 이름, 생성자 인자를 적으면 JPA 제공자가 행마다 그 생성자를 호출해 객체를 만든다. Jakarta Persistence 3.1 명세 4.8.2절은 두 가지를 정한다. "생성자 이름은 완전한 이름(fully qualified)이어야 한다", 그리고 "지정한 클래스는 엔티티이거나 데이터베이스에 매핑되어 있을 필요가 없다". 실험에서는 레코드를 DTO로 썼다.

    package demo;

public record BookSummary(String title, String publisherName) {}

// BookRepository
@Query("select new demo.BookSummary(b.title, p.name) from Book b join b.publisher p order by b.price")
List findSummaries();
    select b1_0.title,p1_0.name from Book b1_0 join Publisher p1_0 on p1_0.id=b1_0.publisher_id order by b1_0.price
>> [BookSummary[title=Spring Data, publisherName=North Press], BookSummary[title=SQL Tuning, publisherName=River Books],
    BookSummary[title=JPA Basics, publisherName=North Press], BookSummary[title=Java Threads, publisherName=River Books]]

    여기서 두 가지를 확인할 수 있다. 첫째, SQL은 DTO에 필요한 두 컬럼만 읽는다. 엔티티로 조회했다면 책의 모든 컬럼을 읽고, 출판사 이름을 보려고 지연 로딩 프록시를 건드리는 순간 출판사 SELECT가 따로 나갔을 것이다. 둘째, JPQL에서 join b.publisher p라고 명시적으로 쓴 조인은 내부 조인(join)이 되었다. 앞 절의 파생 쿼리가 만든 left join과 대비된다. 쿼리를 직접 쓰면 조인의 종류도 직접 정한다.

    명세의 "완전한 이름" 규칙은 실제로 강제된다. 패키지를 빼고 new BookSummary(...)라고 쓴 리포지토리로 컨테이너를 띄우면, @Query 검증 단계에서 Hibernate가 "Could not resolve class 'BookSummary' named for instantiation"이라는 SemanticException을 내고 기동이 실패한다. JPQL 문자열은 자바 소스의 import 문을 보지 못하므로, 클래스를 찾을 단서는 문자열 안의 이름뿐이다. 이름이 길어지는 것이 불편하지만 패키지를 옮기면 문자열도 함께 고쳐야 한다는 점을 기억해 두자. 잘못 고치면 그 역시 기동 때 드러난다.

    메모리 관점에서 엔티티 조회와 DTO 조회의 차이를 정리하면 이렇다. 엔티티로 조회한 결과는 영속성 컨텍스트가 관리한다. 같은 식별자의 엔티티는 한 번만 만들어지고(1차 캐시의 동일성 보장), 변경 감지를 위해 로딩 시점의 상태도 함께 보관된다. DTO는 그 어느 것에도 해당하지 않는 평범한 자바 객체다. 조회 후 필드를 바꿔도 아무 SQL도 나가지 않고, 같은 데이터를 두 번 조회하면 서로 다른 DTO 객체 두 개가 생긴다. 화면에 보여 주기만 할 데이터라면 DTO가 읽는 컬럼도, 관리 비용도 적다. 인터페이스나 클래스를 반환 타입으로 선언해 Spring Data가 select 절을 대신 만들어 주는 방식(Projections)은 07회에서 다룬다.

    파라미터 바인딩: 위치, 이름, 그리고 클래스 파일

    JPQL의 입력 파라미터(input parameter)는 두 가지 표기가 있다. 위치 기반(positional)은 물음표 뒤에 정수를 붙인 ?1, ?2이고, 명세 4.6.4.1절에 따라 1부터 센다. 이름 기반(named)은 콜론 뒤에 식별자를 붙인 :author다. 명세 4.6.4.2절은 같은 파라미터를 쿼리 안에서 여러 번 써도 된다고 하고, 3.10.12절은 한 쿼리에 이름 기반과 위치 기반을 섞는 것이 유효하지 않다고 한다. 입력 파라미터는 where 절과 having 절(그리고 update 문의 set 값)에만 올 수 있다.

    Spring Data JPA에서 위치 기반 ?1은 메서드의 첫 번째 인자와 짝지어진다. 실험의 findPositional("kim", 28000)은 where b1_0.author=? and b1_0.price>=?로 실행되어 JPA Basics 한 권을 돌려주었다. 위치 기반의 약점은 리팩터링이다. 메서드 인자의 순서를 바꾸면 쿼리의 번호는 그대로이므로 값이 엉뚱한 조건에 들어간다. 타입이 같으면(String 두 개처럼) 기동도 실행도 성공한 채 결과만 틀린다. 그래서 이름 기반을 권한다. findCheap(@Param("author") String author, @Param("price") int price)처럼 @Param으로 이름을 붙이면 인자 순서와 무관하게 이름으로 연결된다.

    어느 쪽이든 SQL에는 값이 아니라 ?가 들어간다는 점이 본질이다. Hibernate는 JDBC의 PreparedStatement를 만들고 값은 따로 설정한다. SQL 문장과 값이 분리되어 데이터베이스로 가므로, 값 안에 ' or '1'='1 같은 문자열이 들어 있어도 그것은 그냥 비교할 문자열일 뿐 SQL 구조를 바꾸지 못한다. 문자열을 이어 붙여 JPQL을 만들면 이 보호가 사라진다. 같은 쿼리를 값만 바꿔 여러 번 실행할 때 SQL 문자열이 매번 같다는 점도 바인딩의 이점이다.

    @Param을 생략하면 무슨 일이 생기는가

    Spring Data JPA 문서는 자바 컴파일러의 -parameters 옵션을 쓰면 이름 기반 파라미터에서 @Param을 생략할 수 있다고 한다. 이것을 실험으로 확인해 보자. @Query("select b from Book b where b.title = :title")를 붙이고 인자에 @Param을 붙이지 않은 메서드를, 옵션 없이 컴파일하고 실행했다.

    === context started: noparam
=== FAILED: org.springframework.dao.InvalidDataAccessApiUsageException
  cause: For queries with named parameters you need to provide names for method parameters;
         Use @Param for query method parameters, or when on Java 8+ use the javac flag -parameters

    눈여겨볼 것은 첫 줄이다. 컨테이너는 정상적으로 떴다. 실패는 메서드를 호출하는 순간에 났다. 쿼리 문자열 자체는 올바르므로 @Query 검증은 통과했고, 파라미터 이름을 알아야 하는 바인딩 단계에서야 문제가 드러난 것이다. 이 회차에서 본 오류 중 거의 유일하게 기동 시점에 잡히지 않는 종류다. 같은 소스를 javac -parameters로 다시 컴파일하면 같은 호출이 where b1_0.title=?로 정상 실행된다.

        org.springframework.data.jpa.repository.Query(
          value="select b from Book b where b.title = :title"

    JVM 명세(JVMS) 4.7절의 표에 따르면 MethodParameters는 메서드(method_info)에 붙는 속성이고 클래스 파일 버전 52.0, 즉 Java SE 8에서 도입되었다. 반면 디버그 정보(javac -g)로 남는 LocalVariableTable은 메서드의 Code 속성 안에 붙는 속성이다. 그리고 JVMS 4.1절은 ACC_ABSTRACT나 ACC_NATIVE가 아닌 메서드에만 그 메서드를 구현하는 JVM 명령어가 주어진다고 한다. 인터페이스의 추상 메서드에는 Code 속성이 없으니 LocalVariableTable이 붙을 자리도 없다. 리포지토리 인터페이스의 메서드 파라미터 이름이 런타임에 남는 길은 MethodParameters 하나뿐이다.

    리플렉션으로도 확인된다. 인터페이스 메서드 find(String title)를 -g로만 컴파일하면 Parameter.isNamePresent()는 false이고 getName()은 arg0을 돌려준다. -parameters로 컴파일하면 true와 title이 나온다. Spring Data는 이 정보를 스프링의 ParameterNameDiscoverer를 통해 읽는다. 참고로 Spring Framework 6.1은 바이트코드의 LocalVariableTable을 읽어 이름을 추측하던 LocalVariableTableParameterNameDiscoverer를 제거했고, 릴리스 노트에서 -parameters로 컴파일하라고 안내한다. 이 변화는 구체 클래스의 메서드(컨트롤러 등)에 영향을 준 것이고, 인터페이스 메서드는 처음부터 -parameters 없이는 이름을 얻을 수 없었다.

    실무에서는 대개 이 문제를 겪지 않는다. Spring Boot Gradle 플러그인은 자바 플러그인이 적용되면 모든 JavaCompile 태스크에 -parameters 인자를 설정한다고 문서에 적혀 있다. 그러나 빌드 도구 설정을 거치지 않는 컴파일 경로가 있다면 이 옵션이 빠질 수 있고, 그때는 위의 실패가 기동이 아니라 호출 시점에 나타난다. @Param을 명시하는 습관은 컴파일 옵션에 기대지 않는 가장 확실한 방법이다.

    구체 메서드와 추상 메서드의 method_info 구조를 나란히 놓고, 파라미터 이름이 LocalVariableTable과 MethodParameters 중 어디에 남는지 비교한다. 좌우 두 열의 구조도. 왼쪽 제목 "구체 메서드", 오른쪽 제목 "인터페이스 추상 메서드". 각 열에 큰 상자 "method_info"를 그린다. 왼쪽 method_info 안에 두 개의 작은 상자: "Code 속성"(그 안에 더 작은 상자 "LocalVariableTable (javac -g)")과 "MethodParameters (javac -parameters)". 오른쪽 method_info 안에는 "Code 속성" 자리가 회색 점선 빈 상자로 그려져 있고 라벨 "Code 없음 (ACC_ABSTRACT)", 그 아래 실선 상자 "MethodParameters (javac -parameters)". 오른쪽 MethodParameters 상자에서 바깥 오른쪽으로 화살표가 나가 "Spring Data: :title ↔ title" 라벨이 붙은 말풍선으로 연결. 맨 아래 가로 띠에 "추상 메서드의 이름은 -parameters로만 남는다". 흰 배경, 차분한 회색과 파랑. 인터페이스의 추상 메서드에는 Code 속성이 없으므로 파라미터 이름은 MethodParameters 속성으로만 남는다.

    컬렉션 바인딩과 LIKE 바인딩

    파라미터에 컬렉션을 넘기면 in 절에 쓸 수 있다. 실험의 findByTitles(@Param("titles") Collection<String> titles)는 where b.title in :titles다. 원소 두 개짜리 리스트와 빈 리스트를 넘긴 결과는 다음과 같다.

    -- List.of("JPA Basics", "SQL Tuning")
select ... from Book b1_0 where b1_0.title in (?,?)
>> [Book(JPA Basics, kim, 30000), Book(SQL Tuning, park, 28000)]

-- List.of()
select ... from Book b1_0 where 1=0
>> []

    JPQL에서는 파라미터가 하나였지만 SQL에는 원소 수만큼 ?가 펼쳐졌다. JDBC의 ? 하나에는 값 하나만 묶을 수 있으므로, Hibernate가 컬렉션 크기를 보고 SQL을 다시 렌더링한 것이다. 이 말은 원소 수가 달라질 때마다 SQL 문자열이 달라진다는 뜻이다. 원소가 1개, 2개, 3개인 호출은 서로 다른 SQL이다. Hibernate는 이를 줄이려고 원소 수를 2의 거듭제곱으로 맞춰 채우는 hibernate.query.in_clause_parameter_padding 설정을 제공한다. 빈 컬렉션에 대해서는 Hibernate 6.6.53이 H2 방언에서 항상 거짓인 1=0을 렌더링했다. in ()처럼 비어 있는 괄호는 SQL 문법 오류가 되므로 그것을 피한 것이다.

    LIKE는 Spring Data JPA가 JPQL에 얹은 확장 문법이 있는 곳이다. @Query("select b from Book b where b.title like %:kw%")처럼 파라미터 앞뒤에 %를 붙여 쓸 수 있다. 문서는 이 동작을 이렇게 설명한다. LIKE 구분 문자 %를 인식해 %를 제거한 유효한 JPQL로 바꾸고, 실행할 때 메서드 인자에 앞서 인식한 패턴을 덧붙인다. StringQuery를 직접 불러 보면 바뀐 쿼리와 바인딩 정보를 볼 수 있다.

    select b from Book b where b.title like %:kw%
  -> select b from Book b where b.title like :kw
     binding: LikeBinding [identifier: kw, ..., type: CONTAINING (1): [IsContaining, Containing, Contains]]

select b from Book b where b.author = ?1 and b.title like ?2%
  -> select b from Book b where b.author = ?1 and b.title like ?2
     binding: ParameterBinding [identifier: [1], ...]
     binding: LikeBinding [identifier: [2], ..., type: STARTING_WITH (1): [IsStartingWith, StartingWith, StartsWith]]

select b from Book b where b.title = :t or b.author = :t
  -> select b from Book b where b.title = :t or b.author = :t
     binding: ParameterBinding [identifier: t, ...]

    Hibernate가 받는 것은 화살표 오른쪽의 평범한 JPQL이다. %:kw%는 바인딩 정보 쪽에 CONTAINING이라는 종류로 기록되는데, 이것은 파생 쿼리의 Containing 키워드와 같은 Part.Type이다. 메서드 이름 해석기와 선언 쿼리 해석기가 "값을 어떻게 감쌀 것인가"라는 개념을 공유하는 셈이다. 실제 실행에서 searchTitle("Data")는 where b1_0.title like ? escape ''로 나가 Spring Data를 찾았다. 세 번째 예처럼 같은 이름 파라미터 :t를 두 번 쓰면 바인딩 정보는 하나로 합쳐진다. 사용자 입력을 그대로 LIKE 패턴에 넣을 때 입력 안의 %와 _를 무력화하려면, 문서가 안내하는 SpEL 함수 escape()와 escapeCharacter()를 쿼리에 함께 쓴다.

    반환 타입: 같은 쿼리, 다른 실행

    쿼리 메서드의 반환 타입은 단순한 형 변환 정보가 아니다. 어떤 실행 전략을 쓸지를 고른다. 3.5.13의 jar에는 JpaQueryExecution의 하위 클래스로 CollectionExecution, SingleEntityExecution, StreamExecution, SlicedExecution, PagedExecution, ScrollExecution, ModifyingExecution, DeleteExecution, ExistsExecution, ProcedureExecution이 있다. 쿼리 객체는 메서드의 반환 타입과 애너테이션을 보고 이 중 하나를 고르고, 해당하는 것이 없으면 마지막에 SingleEntityExecution으로 간다.

    같은 모양의 쿼리(where title=?, 또는 where author=?)를 반환 타입만 바꿔 실행한 결과를 모아 보자.

    메서드결과 0건결과 2건
    List<Book> findListByTitle(String)빈 리스트 []2개짜리 리스트
    Book findOneByAuthor(String)nullIncorrectResultSizeDataAccessException
    Optional<Book> findOptionalByTitle(String)Optional.emptyIncorrectResultSizeDataAccessException(문서 기준)
    Stream<Book> streamByPriceGreaterThan(int)빈 스트림트랜잭션 안에서만 소비 가능

    단건 반환의 내부를 따라가 보자. SingleEntityExecution은 JPA의 Query.getSingleResult()를 호출한다. JPA 명세에서 getSingleResult는 결과가 없으면 NoResultException, 둘 이상이면 NonUniqueResultException을 던진다. 순수 JPA라면 결과 없음이 예외인 것이다. 그런데 Spring Data JPA의 상위 클래스 JpaQueryExecution.execute의 예외 테이블을 javap -c로 보면, doExecute 호출 구간에 jakarta/persistence/NoResultException 처리기가 걸려 있고 그 처리기는 null을 반환한다. 결과 없음을 예외에서 null로 바꾸는 곳이 여기다. 반환 타입이 Optional이면 그 null을 Spring Data Commons의 결과 처리기(QueryExecutionResultHandler)가 Optional.empty()로 감싼다.

    결과가 둘 이상일 때는 바꿔 줄 값이 없으므로 예외가 그대로 올라온다. 실험에서 findOneByAuthor("kim")은 이렇게 끝났다.

    select b1_0.id,b1_0.author,b1_0.price,b1_0.publisher_id,b1_0.title from Book b1_0 where b1_0.author=?
=== single result error: org.springframework.dao.IncorrectResultSizeDataAccessException:
      Query did not return a unique result: 2 results were returned
  cause: org.hibernate.NonUniqueResultException: Query did not return a unique result: 2 results were returned

    SQL에 행 제한이 없다는 점을 보자. 단건 반환이라고 해서 limit 1을 붙이지 않는다. 일단 조건에 맞는 행을 받아 온 뒤 개수가 둘 이상이면 실패하는 것이다. 원인 예외는 Hibernate의 NonUniqueResultException이고, 리포지토리 프록시의 예외 변환 단계가 이것을 스프링의 데이터 접근 예외 계층인 IncorrectResultSizeDataAccessException으로 바꿨다. 스프링 DB 권에서 본 예외 추상화가 여기서도 동작한다. 첫 번째 것 하나만 원한다면 이름에 First나 Top을 넣어 SQL 단계에서 행을 제한하는 것이 의도를 정확히 드러낸다.

    컬렉션 반환 타입은 결과가 없어도 null이 아니라 빈 컬렉션을 돌려준다. 실험의 findListByTitle("nothing")은 []였다. 호출하는 쪽에서 null 검사를 할 필요가 없다는 뜻이다. 반대로 단건 반환 타입 Book은 null이 올 수 있으므로, 결과가 없을 수 있는 조회에는 Optional<Book>을 쓰는 편이 호출하는 쪽에 그 가능성을 타입으로 알려 준다.

    Stream은 성격이 다르다. 리스트는 모든 행을 읽어 메모리에 담은 뒤 돌려주지만, 스트림은 아직 열려 있는 결과 집합(JDBC ResultSet)을 감싼 채로 돌려준다. 그래서 커넥션이 스트림을 다 쓸 때까지 살아 있어야 한다. 트랜잭션 없이 호출한 실험은 이렇게 거부되었다.

    === stream error: org.springframework.dao.InvalidDataAccessApiUsageException:
  You're trying to execute a streaming query method without a surrounding transaction that keeps the
  connection open so that the Stream can actually be consumed; Make sure the code consuming the stream
  uses @Transactional or any other way of declaring a (read-only) transaction

    트랜잭션 안에서 try (Stream<Book> st = repo.streamByPriceGreaterThan(29000))로 감싸 소비하면 [JPA Basics, Java Threads]가 나온다. 문서는 스트림이 사용 후 반드시 닫아야 하는 자원을 감싸고 있다고 하고, 동시에 Stream을 쓴다고 해서 JPA 제공자나 JDBC 드라이버가 점진적으로 가져온다는 보장은 없다고 덧붙인다. 드라이버가 결과 전체를 먼저 받아 두는 경우라면 메모리 사용량은 리스트와 다르지 않을 수 있다. 문서가 큰 결과 집합에는 제공자별 fetch size 힌트를 함께 쓰라고 안내하는 이유다.

    그 밖에 공식 문서의 반환 타입 표에는 void, 기본형과 래퍼 타입, Iterator, Collection, Streamable, Vavr 컬렉션, @Async와 함께 쓰는 Future/CompletableFuture, 그리고 Pageable이 필요한 Slice/Page, ScrollPosition이 필요한 Window가 있다. count 접두사는 long, exists 접두사는 boolean을 돌려준다는 것을 앞의 실험에서 보았다. Page와 Slice가 count 쿼리를 어떻게 만들고 쓰는지는 04회의 중심 주제다.

    쿼리 실행 후 결과 행 수(0, 1, 2 이상)와 반환 타입(T, Optional, List)에 따라 최종 반환값이 어떻게 갈리는지 한눈에 보여 준다. 왼쪽에 원통형 데이터베이스 아이콘과 "SQL 실행" 라벨. 오른쪽으로 화살표가 "결과 행 수"라는 마름모로 들어간다. 마름모에서 세 갈래 화살표: "0건", "1건", "2건 이상". 각 갈래 오른쪽에 세 개의 열로 된 표 형태 칸이 있고 열 머리는 "반환 타입 T", "Optional", "List". 0건 행의 칸 내용: "null", "Optional.empty", "[ ]". 1건 행: "엔티티", "Optional.of", "[엔티티]". 2건 이상 행: 빨간 칸 "IncorrectResultSizeDataAccessException", 빨간 칸 "IncorrectResultSizeDataAccessException", 초록 칸 "[엔티티, 엔티티]". 0건 행 왼쪽에 작은 메모 "NoResultException → null 변환". 흰 배경, 표 선은 회색. 결과 없음은 Spring Data JPA가 null로 바꾸지만, 결과 여러 건은 단건 반환 타입에서 예외가 된다.

    흔한 오해와 다른 회차와의 연결

    오해 1: "find와 By 사이에 쓴 단어가 결과 형태를 정한다." 정규식에서 보았듯 그 자리는 Distinct, First, Top이 아니면 무시된다. findOptionalByTitle이 Optional을 돌려준 것은 반환 타입 때문이다. 반대로 findAllByAuthor의 All도 아무 의미가 없으므로 findByAuthor와 같은 쿼리다. 이름에서 설명용 단어를 쓰는 것은 자유지만, 그것이 동작을 바꾼다고 기대하면 안 된다.

    오해 2: "쿼리 문자열의 오류는 그 메서드를 호출해야 드러난다." @Query, @NamedQuery, 메서드 이름 파생 모두 기동 시점에 검증된다. 이 회차에서 본 예외는 메서드 호출 없이 컨테이너를 띄우기만 해서 나온 것이다. 예외는 이름 기반 파라미터의 이름을 찾지 못하는 경우로, 이것은 호출 시점에 드러났다. "컨텍스트를 띄우는 테스트 하나"가 쿼리 오타를 거의 다 잡아 주지만 바인딩 문제까지 잡으려면 메서드를 실제로 호출해야 한다.

    오해 3: "파생 쿼리에 null을 넘기면 그 조건이 빠진다." 조건은 빠지지 않고 is null로 바뀐다. 결과가 비어 있는데 오류는 없으니 원인을 찾기 어렵다. 조건이 선택적인 검색은 메서드를 여러 개로 나누거나, 동적 쿼리를 조립할 수 있는 도구를 써야 한다. 로드맵에서 이 권 다음에 오는 Querydsl이 그 문제를 다룬다.

    오해 4: "단건 반환 메서드는 결과가 여러 개면 첫 번째를 준다." SQL에 행 제한이 없고, 두 건 이상이면 예외다. 데이터가 적은 개발 환경에서는 늘 한 건이라 통과하다가 운영 데이터에서 터지는 전형적인 경우다. 유일성이 데이터베이스 제약(유니크 인덱스)으로 보장되는 컬럼으로 조회할 때만 단건 반환 타입을 쓰는 것이 안전하다.

    오해 5: "메서드 이름의 And와 Or는 쓴 순서대로 왼쪽부터 묶인다." 언제나 Or가 바깥, And가 안쪽이다. 괄호를 표현할 방법이 없으므로 조건이 세 개를 넘어가고 Or가 섞이면 @Query로 옮기는 것이 읽는 사람에게도 안전하다.

    오해 6: "이름 있는 쿼리의 이름이 메서드와 어긋나면 기동이 실패한다." 실패하지 않는다. 기본 전략은 선언된 쿼리를 못 찾으면 메서드 이름 파생으로 넘어가고, 이름이 파생 규칙에 맞으면 다른 쿼리가 조용히 실행된다.

    이 회차에서 만든 그림은 다음 회차들의 바탕이 된다. 04회는 같은 쿼리 메서드에 Pageable과 Sort를 더해 count 쿼리와 정렬이 어떻게 덧붙는지, @Modifying을 붙인 벌크 수정 쿼리가 영속성 컨텍스트를 건너뛰는 문제, @EntityGraph로 파생 쿼리에 페치 조인을 얹는 방법을 다룬다. 05회의 사용자 정의 리포지토리는 이름 파생과 @Query로 표현할 수 없는 쿼리를 직접 구현해 프록시에 끼워 넣는 방법이다. 06회는 이 회차에서 "맵에 없으면 넘어간다"고만 말한 SimpleJpaRepository와 트랜잭션 설정을, 07회는 Projections와 네이티브 쿼리를 다룬다.

    이 장의 핵심

    쿼리 메서드는 리포지토리 빈이 만들어질 때 해석되어 메서드별 쿼리 객체로 저장된다. 조회 순서는 @Query, 이름 있는 쿼리, 메서드 이름 파생이고, 이름 파생은 첫 By에서 주어와 술어를 나눈 뒤 Or와 And로 자르고 키워드를 끝부분에서 찾는다. 이름 기반 바인딩은 클래스 파일의 MethodParameters 속성이나 @Param이 있어야 하며, 반환 타입은 실행 전략을 골라 결과 0건과 여러 건의 처리를 바꾼다.
    쿼리 메서드의 해석 시점
    쿼리 메서드는 호출할 때가 아니라 리포지토리 빈을 만들 때 해석된다. QueryExecutorMethodInterceptor가 메서드마다 RepositoryQuery를 만들어 Map에 저장하고, 실행 중에는 이 맵을 찾아 쓴다.
    조회 전략 CREATE_IF_NOT_FOUND
    기본 전략은 선언된 쿼리를 먼저 찾고(@Query → 속성 파일 이름 있는 쿼리 → JPA @NamedQuery), 없을 때만 메서드 이름에서 쿼리를 파생한다. 그래서 파생 규칙에 맞는 이름이라도 같은 이름의 이름 있는 쿼리가 있으면 그쪽이 실행된다.
    PartTree의 주어와 술어
    메서드 이름은 처음 나오는 By에서 주어와 술어로 나뉜다. 주어의 접두사(find, read, get, query, search, stream, count, exists, delete, remove)와 Distinct, First/Top만 의미가 있고, 그 사이의 다른 단어는 설명용으로 무시된다.
    Or와 And의 결합
    술어는 먼저 Or로, 다음에 And로 잘리므로 결과는 언제나 "And 묶음들의 Or"다. 괄호를 표현할 방법이 없어서 Or가 섞인 복잡한 조건은 @Query로 쓰는 편이 정확하다.
    Part.Type과 인자 개수
    각 조건의 비교 종류는 조각의 끝부분 키워드로 정해지고, 종류마다 소비하는 인자 개수가 다르다(Between 2, IsNull·True 0, 나머지 대부분 1). 파생 쿼리의 바인딩은 이름이 아니라 이 순서를 따른다. null 인자는 조건을 지우지 않고 is null이 된다.
    프로퍼티 경로 해석
    조건 조각에서 키워드를 뗀 나머지는 전체 이름을 먼저 찾고, 없으면 낙타 표기 경계에서 오른쪽부터 잘라 연관을 따라 들어간다. 밑줄(Publisher_City)로 경계를 직접 지정할 수 있다.
    @Query와 이름 있는 쿼리의 검증
    @NamedQuery는 EntityManagerFactory를 만들 때 Hibernate가, @Query는 리포지토리 빈을 만들 때 SimpleJpaQuery가 Hibernate에 넘겨 검증한다. 어느 쪽이든 문법·경로 오류는 기동 시점에 드러난다.
    값·DTO 조회
    select 절에 필드 하나를 고르면 그 타입으로, 여러 개를 고르면 Object[]로 결과가 나온다. 생성자 표현식 new 완전한.클래스이름(...)은 영속성 컨텍스트가 관리하지 않는 평범한 객체를 행마다 만든다.
    이름 기반 바인딩과 MethodParameters
    추상 메서드에는 Code 속성이 없어 LocalVariableTable이 붙을 수 없으므로, 인터페이스 메서드의 파라미터 이름은 -parameters로 만든 MethodParameters 속성으로만 남는다. 이것도 @Param도 없으면 기동은 성공하고 호출 시점에 실패한다.
    반환 타입과 실행 전략
    반환 타입이 JpaQueryExecution 하위 클래스를 고른다. 단건 반환은 결과 없음을 null(또는 Optional.empty())로 바꾸지만 결과 여러 건은 IncorrectResultSizeDataAccessException이 된다. 컬렉션은 빈 컬렉션을, Stream은 트랜잭션 안에서만 소비할 수 있는 열린 결과를 돌려준다.

    실무에서 가장 먼저 내리는 판단은 "이 조회를 메서드 이름으로 쓸 것인가, @Query로 쓸 것인가"다. 조건이 한두 개이고 연산자가 단순하면 메서드 이름 파생이 가장 짧고, 기동 시점에 프로퍼티 이름까지 검증되므로 안전하다. 그러나 조건이 세 개를 넘거나 Or가 섞이면 이름이 문장처럼 길어지고, 이 회차에서 본 것처럼 결합 순서가 "And 묶음들의 Or"로 고정되어 의도와 다른 조건이 조용히 만들어질 수 있다. 그 지점에서 @Query로 옮기는 것이 읽는 사람과 실행되는 SQL을 일치시키는 방법이다. 조건이 입력에 따라 붙었다 빠졌다 하는 검색이라면 둘 다 맞지 않는다. 파생 쿼리는 null을 is null로 바꾸고, @Query는 문자열이 고정되어 있기 때문이다. 이런 요구는 05회의 사용자 정의 리포지토리나 로드맵 다음 권의 Querydsl로 넘긴다.

    오류를 언제 발견하는지도 설계 판단에 들어간다. 이 회차의 실험에서 메서드 이름 오타, @Query의 경로 오류, @NamedQuery의 경로 오류는 모두 메서드를 한 번도 호출하지 않고 컨테이너를 띄우기만 해서 드러났다. 그러니 스프링 컨텍스트를 실제로 띄우는 테스트 하나를 CI에 두는 것만으로 쿼리 오타의 대부분을 배포 전에 걸러 낼 수 있다. 반대로 기동 검증을 통과하는 실수도 분명히 있다. 이름 기반 파라미터의 이름을 찾지 못하는 문제는 호출 시점에야 드러났고, 위치 기반 파라미터의 순서가 뒤바뀌거나 이름 있는 쿼리와 메서드 이름의 연결이 끊어지는 문제는 아예 오류 없이 다른 결과를 낸다. 이런 종류는 메서드를 실제 데이터로 호출해 결과를 검사하는 테스트만 잡는다. 이 차이를 알면 "컨텍스트가 떴으니 쿼리는 맞다"는 잘못된 안심을 피할 수 있다.

    반환 타입은 장애와 직접 이어진다. 단건 반환 타입(T, Optional)은 SQL에 행 제한을 붙이지 않고 결과를 받은 뒤 두 건 이상이면 예외를 던진다. 개발 데이터에서는 늘 한 건이라 통과하던 조회가 운영 데이터에서 같은 값을 가진 행이 하나 더 생기는 순간 실패한다. 그래서 단건 반환 타입은 유니크 제약으로 유일성이 보장되는 컬럼에만 쓰고, "여러 건 중 하나"가 의도라면 First/Top과 정렬을 이름에 넣어 SQL 단계에서 제한한다. Stream 반환은 메모리를 아끼는 도구처럼 보이지만, 스트림을 다 소비할 때까지 트랜잭션과 그 트랜잭션이 붙잡은 커넥션이 반환되지 않는다는 점이 먼저다. 스트림을 소비하면서 느린 외부 호출을 섞으면 커넥션 풀이 그만큼 오래 묶인다. Jakarta Persistence 3.1 명세의 Query.getResultStream() 기본 구현은 getResultList().stream()이므로, 명세만으로는 점진적 조회가 보장되지 않는다는 점도 함께 기억해 둘 만하다.

    파라미터 바인딩에서는 두 가지를 판단한다. 하나는 @Param을 명시할지 여부다. 빌드 도구가 -parameters를 켜 주는 환경이라면 생략해도 동작하지만, 그 보장은 소스가 아니라 빌드 설정에 있다. 컴파일 경로가 하나라도 다르면 실패가 기동이 아니라 호출 시점으로 밀려나므로, 공용 모듈처럼 여러 빌드에서 컴파일되는 코드라면 명시하는 편이 안전하다. 다른 하나는 in 절에 넘기는 컬렉션의 크기다. 원소 수가 달라질 때마다 SQL 문자열이 달라지므로, 문자열 단위로 문장을 캐시하는 계층에서는 서로 다른 문장이 늘어난다. 원소 수의 편차가 큰 조회라면 Hibernate의 hibernate.query.in_clause_parameter_padding 설정을 검토하고, 빈 컬렉션이 들어올 수 있는지도 미리 확인해 둔다.

Order By price: DESC로 찍히고 isDistinct()는 true, getMaxResults()는 3이다. 바인딩은 트리를 왼쪽부터 훑으며 순서대로 가져가므로 author 인자가 작가 조건에, min과 max가 BETWEEN의 아래·위 경계에 들어간다. 파라미터 이름은 아무 역할도 하지 않는다. 인자 순서를 (int min, int max, String author)로 바꾸면 작가 조건이 첫 번째 인자를 가져가므로 의도와 다른 바인딩이 된다.

    2번. 술어는 먼저 Or로 잘려 Author와 TitleAndPriceLessThan 두 묶음이 되고, 뒤의 묶음이 다시 And로 잘린다. 3.5.13의 PartTree.toString()도 키워드 목록과 대소문자 무시 표시를 빼고 보면 author SIMPLE_PROPERTY (1) or title SIMPLE_PROPERTY (1) and price LESS_THAN (1) 순서로 찍는다. 그러므로 실제 조건은 author = 'kim' OR (title = 'SQL Tuning' AND price < 29000)이다. kim의 책 두 권(JPA Basics 30000, Spring Data 25000)은 앞 조건으로, SQL Tuning(28000)은 뒤 묶음으로 걸려 3권이 나온다. 의도한 조건 (author = 'kim' OR title = 'SQL Tuning') AND price < 29000이라면 JPA Basics는 30000이라 빠지고 Spring Data와 SQL Tuning 2권이어야 한다. 차이는 JPA Basics 한 권이고, 원인은 메서드 이름에 괄호가 없어 Or가 항상 바깥에서 묶인다는 데 있다. 의도한 조건을 이름으로 쓰려면 분배 법칙으로 펼쳐 findByAuthorAndPriceLessThanOrTitleAndPriceLessThan처럼 써야 하고 인자도 네 개가 필요하다. @Query로 괄호를 직접 쓰는 편이 낫다. 결과 순서는 order by가 없으므로 보장되지 않는다.

Hibernate가 EntityManagerFactory를 만들면서 모든 이름 있는 쿼리를 해석하므로, 리포지토리를 만들기도 전에 NamedQueryValidationException으로 실패한다. (가)와 (나)는 리포지토리 빈 생성 때 드러난다. (가)는 PartTree가 PropertyPath로 titel을 찾다가 PropertyReferenceException을 내고, (나)는 SimpleJpaQuery가 생성자에서 쿼리를 Hibernate에 넘겨 검증하다가 UnknownPathException을 받는다. (라)는 쿼리 문자열이 올바르므로 기동은 성공하고, 메서드를 호출해 이름으로 값을 묶으려는 순간 파라미터 이름을 알 수 없어 InvalidDataAccessApiUsageException이 난다. (마)는 끝까지 오류가 없다. Book.getByAuthor라는 이름 있는 쿼리가 없으므로 CREATE_IF_NOT_FOUND 전략이 메서드 이름 파생으로 넘어가고, getByAuthor는 파생 규칙에 맞는 이름이어서 기동도 호출도 성공한다. 다만 이름 있는 쿼리에 있던 order by b.price desc가 사라진 SQL이 실행된다.

    4번. 위치 기반 파라미터 ?1은 메서드의 첫 번째 인자, ?2는 두 번째 인자와 짝지어진다. 파라미터 이름 author, title은 바인딩에 쓰이지 않는다. 그래서 find("kim", "JPA Basics")는 title = 'kim' and author = 'JPA Basics'가 되고, 그런 행은 없으므로 빈 리스트가 나온다. 오류가 없었던 이유는 세 겹이다. JPQL 문자열은 올바르므로 기동 시점의 @Query 검증을 통과하고, 두 인자가 모두 String이라 바인딩할 때 타입 불일치도 없으며, 결과가 0건인 것은 조회 쿼리에서 정상적인 결과다. 고치는 방법은 이름 기반으로 바꾸는 것이다. @Query("select b from Book b where b.title = :title and b.author = :author") List find(@Param("author") String author, @Param("title") String title)로 쓰면 인자의 순서와 무관하게 이름으로 연결되고, @Param을 명시했으므로 -parameters 컴파일 옵션에도 기대지 않는다.

    5번. (가) park의 책은 SQL Tuning 한 권이므로 그 엔티티가 반환된다. (나) choi의 책은 없다. 단건 실행은 JPA의 getSingleResult()를 쓰고, 이것이 던진 NoResultException을 Spring Data JPA의 JpaQueryExecution.execute가 잡아 null로 바꾸므로 null이 반환된다. (다) kim의 책은 두 권이다. 메서드 이름의 Optional은 설명용 단어라 무시되고, SQL에는 행 제한이 붙지 않는다. 두 행이 돌아오면 Hibernate의 NonUniqueResultException이 나고 이것이 IncorrectResultSizeDataAccessException으로 변환된다. Optional은 "없을 수 있음"을 표현할 뿐 "여러 건 중 하나"를 뜻하지 않는다. (라) First는 결과를 1건으로 제한하는 키워드이고, OrderByPriceDesc가 가격 내림차순 정렬을 붙인다. SQL에 정렬과 행 제한 구문(H2 방언에서는 본문에서 본 fetch first ? rows only)이 붙어 데이터베이스가 한 행만 돌려주므로 예외 없이 Optional[JPA Basics]가 나온다. (마) 컬렉션 반환 타입은 결과가 없으면 빈 리스트 []를 돌려준다. (다)와 (라)의 차이는 반환 타입이 아니라 SQL에 있다. (라)는 행 제한이 SQL 단계에서 걸리고, (다)는 제한 없이 받은 뒤 개수를 검사한다.

     엔티티 Book에 title 필드만 있는데 리포지토리에 List findByTitel(String title)를 선언했다. 이 오타는 언제 드러나는가? 자바 컴파일 단계에서 컴파일 오류로 리포지토리 빈을 만들 때, 즉 애플리케이션 기동 시점에 그 메서드를 처음 호출할 때 트랜잭션이 커밋되어 SQL이 실행될 때 쿼리 메서드는 리포지토리 빈을 만들 때 QueryExecutorMethodInterceptor가 메서드마다 쿼리 객체를 만들면서 해석된다. 이때 PartTree가 PropertyPath로 titel을 찾다가 PropertyReferenceException을 내고 빈 생성이 실패한다. 컴파일러는 메서드 이름의 의미를 모르므로 컴파일 단계에서는 잡지 못하고, 기동 때 이미 실패하므로 호출이나 커밋 시점까지 가지 않는다. findByAuthorOrPriceLessThanAndTitleStartingWith(a, p, t)가 만드는 조건으로 옳은 것은? (author = a OR price < p) AND title LIKE 't%' author = a AND price < p AND title LIKE 't%' author = a OR (price < p AND title LIKE 't%') Or와 And가 섞여 있어 기동 시점에 거부된다 PartTree는 술어를 먼저 Or로, 그다음 And로 자르므로 결과는 항상 "And 묶음들의 Or"다. 이 이름은 Author 묶음과 PriceLessThanAndTitleStartingWith 묶음의 Or가 된다. 메서드 이름에는 괄호를 쓸 방법이 없으므로 첫 번째 보기처럼 Or를 안쪽으로 묶을 수 없고, Or와 And를 섞는 것 자체는 허용된다. 리포지토리 인터페이스 메서드에 @Param 없이 :title을 쓰면 javac -g로 디버그 정보를 넣어도 실패하고 -parameters로 컴파일해야 동작한다. 이유로 가장 정확한 것은? Spring Data는 리플렉션을 쓰지 않고 소스 파일을 직접 읽기 때문이다 추상 메서드에는 Code 속성이 없어 LocalVariableTable이 붙을 수 없고, 이름이 남는 길은 MethodParameters 속성뿐이기 때문이다 JPQL 명세가 이름 기반 파라미터를 금지하기 때문이다 -g는 클래스 파일 버전을 낮춰 애너테이션을 지우기 때문이다 JVMS 4.7절에 따르면 LocalVariableTable은 Code 속성 안에, MethodParameters는 method_info에 붙는 속성이다. 추상 메서드에는 JVM 명령어가 없으므로 Code 속성도 없고, 그래서 -g가 만드는 LocalVariableTable이 붙을 자리가 없다. JPQL은 이름 기반 파라미터를 정식으로 지원하고, -g는 애너테이션을 지우지 않는다. 엔티티 Book에 @NamedQuery(name = "Book.findByAuthor", query = "... order by b.price desc")가 있고, BookRepository에 @Query 없이 List findByAuthor(@Param("author") String author)를 선언했다. 기본 조회 전략에서 실행되는 쿼리는? 메서드 이름에서 파생된 where author = ? 쿼리(정렬 없음) 이름 있는 쿼리 Book.findByAuthor(정렬 포함) 두 쿼리가 충돌해 기동이 실패한다 두 쿼리의 결과를 합쳐서 돌려준다 기본 전략 CREATE_IF_NOT_FOUND는 선언된 쿼리를 먼저 찾는다. @Query가 없으므로 "도메인 클래스 단순 이름.메서드 이름"인 Book.findByAuthor를 이름 있는 쿼리에서 찾고, 있으므로 그것을 쓴다. 메서드 이름 파생은 선언된 쿼리가 없을 때만 시도되므로 충돌이 일어나지 않는다. 작가가 kim인 책이 두 권일 때 Book findOneByAuthor("kim")을 호출하면 어떻게 되는가? SQL에 행 제한이 붙어 첫 번째 행 하나가 반환된다 결과가 하나로 정해지지 않으므로 null이 반환된다 행 제한 없는 SQL로 두 행을 받은 뒤 IncorrectResultSizeDataAccessException이 발생한다 이름의 One 때문에 기동 시점에 거부된다 단건 반환 타입은 getSingleResult()로 실행되고 SQL에 행 제한을 붙이지 않는다. 두 행이 오면 Hibernate의 NonUniqueResultException이 나고 리포지토리 프록시의 예외 변환이 이를 IncorrectResultSizeDataAccessException으로 바꾼다. null로 바뀌는 것은 결과가 없을 때(NoResultException)뿐이고, One은 find와 By 사이의 설명용 단어라 무시된다.
    쿼리 메서드(query method)
    리포지토리 인터페이스에 선언만 하고 구현하지 않은 조회 메서드. Spring Data가 메서드 이름이나 선언된 쿼리로부터 실행할 쿼리를 만든다.
    조회 전략(query lookup strategy)
    쿼리 메서드에 쓸 쿼리를 어디서 얻을지 정하는 규칙. CREATE, USE_DECLARED_QUERY, CREATE_IF_NOT_FOUND(기본값)가 있다.
    PartTree
    Spring Data Commons에서 메서드 이름을 주어(Subject)와 술어(Predicate)로 나누고, 술어를 Or 묶음과 And 조건(Part)의 트리로 바꾸는 클래스. 저장소 종류와 무관하게 공통으로 쓰인다.
    프로퍼티 경로(property path)
    조건 조각이 가리키는 엔티티 프로퍼티의 경로. PublisherCity처럼 연관을 따라 들어가는 경로도 있으며, 낙타 표기 경계나 밑줄로 나뉜다.
    이름 있는 쿼리(named query)
    JPA 표준의 @NamedQuery나 orm.xml로 JPQL에 이름을 붙여 둔 정적 쿼리. Hibernate는 EntityManagerFactory를 만들 때 이를 모두 검증한다.
    생성자 표현식(constructor expression)
    JPQL select 절의 new 완전한.클래스이름(...). 행마다 그 생성자를 호출해 엔티티가 아닌 객체를 만든다(Jakarta Persistence 3.1 §4.8.2).
    입력 파라미터(input parameter)
    JPQL에서 값을 나중에 묶을 자리. 위치 기반 ?1(1부터 센다)과 이름 기반 :name이 있고 한 쿼리에 섞어 쓸 수 없다.
    MethodParameters 속성
    클래스 파일의 method_info에 붙어 메서드 파라미터의 이름과 플래그를 기록하는 속성. 클래스 파일 버전 52.0(Java SE 8)에서 도입되었고 javac -parameters로 생성된다.
    실행 전략(JpaQueryExecution)
    쿼리 객체가 반환 타입과 애너테이션에 따라 고르는 실행 방식. 컬렉션, 단건, 스트림, 페이지, 수정, 삭제, 존재 여부 등 하위 클래스로 나뉜다.
