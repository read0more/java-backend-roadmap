    이 회차의 질문: 바꾼 값이 왜 안 보이는가

    앞의 두 회차에서 스레드의 생명 주기를 다뤘다. join으로 다른 스레드가 끝나기를 기다리는 법, 인터럽트로 잠든 스레드를 깨워 작업을 멈추게 하는 법, yield로 실행 기회를 양보하는 법이다. 이번 회차는 방향을 바꿔 스레드 사이에서 값이 어떻게 전달되는지를 묻는다. 스레드 하나가 필드에 값을 썼을 때 다른 스레드는 언제 그 값을 보는가. 대부분의 사람은 "곧바로"라고 답한다. 같은 프로세스 안의 스레드는 힙을 공유하고, 필드는 힙에 있으니 한 스레드가 쓰면 다른 스레드도 같은 자리를 읽을 것이라고 생각하기 때문이다.

    이 직관은 단일 스레드 프로그램에서는 늘 맞는다. 한 스레드 안에서는 앞에서 쓴 값을 뒤에서 읽으면 반드시 그 값이 나온다. 그런데 두 스레드가 끼어들면 이야기가 달라진다. 자바 언어 명세(JLS) 17장은 이 문제를 정면으로 다루는데, 그 결론은 놀랍게도 "아무 장치 없이 다른 스레드가 쓴 값을 읽는다면, 그 값을 언제 볼지는커녕 볼 수 있을지조차 보장하지 않는다"이다. 이것이 메모리 가시성(memory visibility) 문제다.

    이 회차는 다음 순서로 진행한다. 먼저 끝나지 않는 루프를 실제로 만들어 문제를 눈으로 본다. 그 원인을 두 층에서 찾는다. 하나는 하드웨어(CPU 캐시와 저장 버퍼)이고, 다른 하나는 컴파일러(JIT)다. 그다음 해결책인 volatile이 무엇을 바꾸는지, 얼마의 비용이 드는지, 무엇은 해결하지 못하는지 본다. 마지막으로 이 모든 것을 언어 차원에서 정리한 규칙, 자바 메모리 모델(Java Memory Model, JMM)과 그 핵심인 happens-before 관계를 세운다. 다음 회차의 synchronized, 그 뒤의 Lock, CAS, 동시성 컬렉션은 모두 이 규칙 위에 서 있다.

    이 회차의 실험은 모두 Apple M1(ARM64, 코어 8개) 위의 Temurin OpenJDK 21.0.13에서 직접 돌린 것이다. 동시성 실험의 결과는 실행할 때마다, 기계와 JVM 버전마다 달라질 수 있다. 본문에서는 관찰한 결과를 그대로 적되, 어디까지가 명세의 보장이고 어디부터가 이 기계에서 우연히 관찰된 것인지를 구분해 적는다.

    실험: 멈추지 않는 스레드

    가장 단순한 형태로 문제를 만들어 보자. 작업 스레드는 공유 플래그 running이 참인 동안 숫자를 센다. main 스레드는 1초 기다렸다가 플래그를 거짓으로 바꾸고, 작업 스레드가 끝나기를 최대 2초 기다린 뒤 그 상태를 출력한다. 작업 스레드를 데몬 스레드로 만든 것은, 작업 스레드가 끝나지 않더라도 main이 끝나면 JVM이 종료되게 하려는 것이다.

    public class FlagLoop {
    static boolean running = true;

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long count = 0;
            while (running) {
                count++;
            }
            System.out.println("worker: 루프 종료, count>0 = " + (count > 0));
        }, "worker");
        worker.setDaemon(true);
        worker.start();

        Thread.sleep(1000);
        running = false;
        System.out.println("main: running = false 로 바꿨다");

        worker.join(2000);
        System.out.println("main: 2초 뒤 worker 상태 = " + worker.getState());
    }
}
    main: running = false 로 바꿨다
main: 2초 뒤 worker 상태 = RUNNABLE

    main은 분명히 running = false를 실행했다. 그 뒤로 2초가 지났는데도 작업 스레드는 RUNNABLE 상태로 여전히 루프를 돌고 있고, "루프 종료"는 끝내 출력되지 않는다. 작업 스레드가 데몬이 아니었다면 이 프로그램은 영원히 끝나지 않았을 것이다. 03회에서 본 스레드 상태로 말하면, 이 스레드는 대기(WAITING)나 블록(BLOCKED)이 아니라 CPU 위에서 실제로 명령을 실행하고 있다. 다만 바뀐 플래그를 보지 못하고 있을 뿐이다.

    같은 코드에서 필드 선언 한 줄만 static volatile boolean running = true;로 바꾸면 결과가 달라진다.

    main: running = false 로 바꿨다
worker: 루프 종료, count>0 = true
main: 2초 뒤 worker 상태 = TERMINATED

    키워드 하나로 결과가 바뀌었다. 이 회차의 나머지는 전부 "왜"에 대한 답이다. 왜 바꾼 값이 안 보였고, volatile은 정확히 무엇을 바꿨는가.

    첫 번째 층: CPU 캐시와 메인 메모리

    흔히 드는 첫 번째 설명은 CPU 캐시다. CPU 코어가 연산하는 속도에 비해 메인 메모리(DRAM)에 다녀오는 일은 훨씬 느리다. 그래서 프로세서는 코어 가까이에 작고 빠른 메모리, 즉 캐시(cache)를 여러 단계로 둔다. 일반적인 멀티코어 프로세서에서 가장 작은 L1 캐시는 코어마다 따로 있고, 더 큰 단계의 캐시는 여러 코어가 함께 쓰는 구조가 많다. JSR-133(자바 5에서 메모리 모델을 새로 정의한 작업) FAQ도 메모리 모델을 설명하며 프로세서가 하나 이상의 캐시 계층을 두어 데이터 접근을 빠르게 한다는 점에서 출발한다.

      코어 0 (main 스레드)          코어 1 (worker 스레드)
 ┌────────────────────┐       ┌────────────────────┐
 │ 레지스터            │       │ 레지스터            │
 │ 저장 버퍼           │       │ 저장 버퍼           │
 │ L1 캐시             │       │ L1 캐시             │
 │  running = false ◀─┼─ 씀   │  running = true  ◀─┼─ 계속 읽음
 └─────────┬──────────┘       └─────────┬──────────┘
           │                            │
 ┌─────────┴────────────────────────────┴──────────┐
 │                공유 캐시 / 메인 메모리             │
 │                running = ?                      │
 └─────────────────────────────────────────────────┘

    이 그림대로라면 이야기는 이렇게 흘러간다. worker 스레드가 돌고 있는 코어 1은 running을 자기 캐시에 올려 두고 거기서 계속 읽는다. main 스레드가 도는 코어 0은 false를 자기 캐시에 쓴다. 코어 0의 캐시에 쓴 값이 메인 메모리로, 다시 코어 1의 캐시로 전달되기 전까지 코어 1은 옛 값 true를 본다. 그래서 루프가 끝나지 않는다.

    비유각자 들고 다니는 공지 사본

    회사 게시판(메인 메모리)에 "오늘 야근 없음"이라는 공지가 붙는다. 그런데 직원들은 아침에 게시판을 한 번 보고 공지를 수첩(캐시)에 옮겨 적은 뒤, 하루 종일 수첩만 들여다본다. 누군가 게시판의 공지를 바꿔도 수첩을 다시 고쳐 쓰기 전까지는 옛 공지대로 움직인다. 이 비유는 "각자 사본을 들고 있다"는 직관을 주지만, 실제 하드웨어와는 중요한 점에서 다르다. 실제 멀티코어 프로세서에는 한 코어가 값을 바꾸면 다른 코어의 사본을 무효로 만들어 주는 하드웨어 장치가 있다. 수첩이 영원히 옛 값으로 남는 일은 하드웨어만으로는 잘 일어나지 않는다. 이 점은 바로 다음 절의 실험에서 확인한다.

    여기서 짚어 둘 것이 있다. 현대 멀티코어 프로세서는 캐시 일관성(cache coherence)을 하드웨어로 유지한다. 한 코어가 어떤 주소에 쓰면 다른 코어 캐시에 있는 같은 주소의 사본은 무효가 되고, 다음에 읽을 때 새 값을 가져온다. 그러니 "캐시에 옛 값이 영원히 남아 있다"는 설명은 정확하지 않다. 하드웨어 수준에서 지연을 만드는 것은 캐시 자체보다는 쓰기가 캐시에 반영되기 전에 잠시 머무는 저장 버퍼(store buffer, write buffer)와, 명령을 순서 없이 실행하는 비순차 실행(out-of-order execution) 쪽이다. 이 지연은 보통 아주 짧다. 그렇다면 2초가 넘도록 값이 안 보인 이유는 무엇인가. 범인은 한 층 위, 소프트웨어에 있었다.

    두 코어가 각자 레지스터·저장 버퍼·L1 캐시를 갖고, 아래에서 공유 캐시와 메인 메모리로 연결되는 구조. 한 코어의 쓰기가 다른 코어에 보이기까지 거치는 경로를 보여 준다. 가로로 긴 기술 구조도. 위쪽에 나란한 두 개의 둥근 사각형 상자, 왼쪽 상자 제목 "코어 0 · main 스레드", 오른쪽 상자 제목 "코어 1 · worker 스레드". 각 상자 안에는 위에서 아래로 세 개의 얇은 띠: "레지스터", "저장 버퍼", "L1 캐시". 왼쪽 상자의 저장 버퍼 띠 안에 작은 메모 카드 "running = false"가 있고, 오른쪽 상자의 L1 캐시 띠 안에 "running = true" 카드가 있다. 두 상자 아래에 넓은 가로 상자 "공유 캐시 / 메인 메모리". 왼쪽 저장 버퍼에서 아래 공유 상자로 점선 화살표가 내려가고 라벨 "나중에 반영", 공유 상자에서 오른쪽 L1 캐시로 점선 화살표가 올라가고 라벨 "무효화 후 다시 읽음". 오른쪽 상자 옆에 순환 화살표와 라벨 "계속 읽는 루프". 차분한 파랑과 회색 톤, 평면적인 다이어그램 스타일, 그림자 없음. 코어마다 레지스터·저장 버퍼·캐시를 따로 갖는다. 한 코어의 쓰기는 이 경로를 거쳐야 다른 코어에 보인다.

    두 번째 층: 이 기계에서 범인은 JIT 컴파일러였다

    같은 FlagLoop를 JVM 옵션만 바꿔 다시 실행해 보자. -Xint는 JIT 컴파일을 끄고 바이트코드 인터프리터로만 실행하게 하는 옵션이고, -XX:TieredStopAtLevel=1은 계층형 컴파일(tiered compilation)에서 가볍게 최적화하는 C1 컴파일러까지만 쓰고 공격적으로 최적화하는 C2 컴파일러는 쓰지 않게 하는 옵션이다.

    java FlagLoop                          # 기본: 인터프리터 → C1 → C2
java -Xint FlagLoop                    # 인터프리터만
java -XX:TieredStopAtLevel=1 FlagLoop  # C1까지만
    실행 방식2초 뒤 worker 상태"루프 종료" 출력
    기본 (C2까지 사용)RUNNABLE없음
    -Xint (인터프리터만)TERMINATED있음
    -XX:TieredStopAtLevel=1 (C1까지)TERMINATED있음
    필드를 volatile로 선언 (기본 옵션)TERMINATED있음

    CPU와 캐시는 네 경우 모두 같다. 달라진 것은 바이트코드를 기계어로 바꾸는 방식뿐이다. 하드웨어만의 문제였다면 인터프리터로 실행해도 루프가 끝나지 않았어야 한다. 그런데 인터프리터와 C1에서는 루프가 곧바로 끝났고, C2가 개입했을 때만 끝나지 않았다. 이 기계에서 2초가 넘는 "영원한 비가시성"을 만든 것은 C2 컴파일러다.

    먼저 바이트코드를 보자. javap -c -p FlagLoop로 람다 본문(lambda$main$0)을 출력하면 다음과 같다.

      private static void lambda$main$0();
    Code:
       0: lconst_0
       1: lstore_0
       2: getstatic     #31   // Field running:Z
       5: ifeq          15
       8: lload_0
       9: lconst_1
      10: ladd
      11: lstore_0
      12: goto          2
      15: getstatic     #37   // Field java/lang/System.out:Ljava/io/PrintStream;
      ...

    바이트코드 수준에서 루프는 정직하다. 2번 위치의 getstatic이 running을 읽고, 5번의 ifeq가 0(거짓)이면 15번으로 빠져나가며, 12번의 goto 2가 다시 2번으로 돌아간다. 즉 바이트코드는 반복할 때마다 필드를 새로 읽으라고 말한다. 인터프리터는 이 명령을 하나씩 그대로 실행하므로 매번 메모리에서 필드를 읽고, main이 쓴 false를 금방 보게 된다.

    흥미로운 것은 volatile 버전의 바이트코드다. 두 클래스를 javap -c -p로 출력해 클래스 이름을 지우고 비교하면, 차이는 필드 선언 한 줄뿐이다. 명령어 순서는 한 글자도 다르지 않다. volatile은 바이트코드 명령을 바꾸지 않고, 클래스 파일의 필드 정보에 ACC_VOLATILE 플래그(값 0x0040)를 하나 켤 뿐이다.

      static volatile boolean running;
    descriptor: Z
    flags: (0x0048) ACC_STATIC, ACC_VOLATILE

    같은 getstatic이 플래그 하나 때문에 다르게 동작한다는 것은, 그 차이가 바이트코드를 실행하고 컴파일하는 쪽, 곧 JVM에서 만들어진다는 뜻이다. 그럼 C2는 언제 개입했는가. -XX:+PrintCompilation 옵션은 JIT 컴파일이 일어날 때마다 한 줄씩 기록을 남긴다.

    70   33 %     3       FlagLoop::lambda$main$0 @ 2 (38 bytes)
74   34 %     4       FlagLoop::lambda$main$0 @ 2 (38 bytes)
75   33 %     3       FlagLoop::lambda$main$0 @ 2 (38 bytes)   made not entrant
77   35       4       FlagLoop::lambda$main$0 (38 bytes)

    첫 열은 JVM 시작 후 경과 시간(밀리초), 둘째 열은 컴파일 번호, %는 OSR(on-stack replacement) 컴파일을, 그다음 숫자는 계층(3은 프로파일링을 포함한 C1, 4는 C2)을 뜻한다. @ 2는 OSR 진입 지점이 바이트코드 2번, 바로 루프 머리의 getstatic이라는 뜻이다. OSR은 이미 실행 중인 메서드의 루프를 멈추지 않고 그 자리에서 컴파일된 코드로 갈아타게 하는 기법이다. 람다는 한 번 호출되어 영원히 루프를 도는 메서드라서, 메서드 호출 횟수가 아니라 루프 반복 횟수 때문에 컴파일된다. 이 실행에서는 JVM 시작 후 약 74밀리초 만에 C2가 만든 루프 코드로 바뀌었다. main이 1초 뒤 플래그를 바꿀 때 worker는 이미 C2 코드 안에 있었다.

    main이 1초가 아니라 1밀리초만 기다렸다가 플래그를 바꾸게 고친 실험도 해 보았다. 스무 번 실행해 두 번은 worker가 정상 종료되었고, 나머지 열여덟 번은 1초 버전처럼 멈추지 않았다. 위의 PrintCompilation 기록에서 보듯 C1 OSR 컴파일에서 C2 OSR 컴파일까지는 몇 밀리초밖에 걸리지 않는다. 플래그가 바뀐 순간 worker가 아직 인터프리터나 C1 코드에서 돌고 있었다면 루프가 끝나고, 이미 C2 코드로 갈아탄 뒤였다면 끝나지 않는다. 같은 코드가 타이밍에 따라 멈추기도 하고 멈추지 않기도 한다. 동시성 버그가 개발 환경에서는 안 보이다가 운영에서 오래 돌아간 뒤에야 나타나는 이유 중 하나가 이것이다.

    C2가 한 일: 루프 불변 코드 이동

    C2가 정확히 어떤 기계어를 만들었는지는 HotSpot용 디스어셈블러 플러그인(hsdis) 없이는 기호로 된 어셈블리로 바로 볼 수 없다(우회하는 방법은 다음 절에서 쓴다). 우선 관찰된 동작만 보면 다음 변환과 같다. 컴파일러 입장에서 이 루프 안에는 running에 쓰는 코드가 없다. 그렇다면 running은 루프 안에서 변하지 않는 값(루프 불변식, loop invariant)이고, 매번 메모리에서 읽을 필요 없이 루프 밖에서 한 번만 읽어도 이 스레드 혼자서는 결과가 같다. 이 최적화를 루프 불변 코드 이동(loop-invariant code motion), 또는 읽기를 루프 밖으로 끌어올린다고 해서 호이스팅(hoisting)이라고 부른다.

    // 원래 코드
while (running) {
    count++;
}

// 컴파일러가 해도 되는 변환 (의사 코드)
boolean r = running;      // 루프 밖에서 한 번만 읽는다
if (r) {
    while (true) {        // 다시 읽지 않으므로 영원히 돈다
        count++;
    }
}

    이 변환이 버그처럼 보이지만, JLS는 이것을 명시적으로 허용한다. JLS 17.3은 non-volatile 필드 this.done을 검사하며 Thread.sleep(1000)을 반복하는 루프를 예로 들고, 컴파일러가 이 필드를 단 한 번만 읽고 그 값을 루프마다 재사용해도 되며 그 결과 다른 스레드가 값을 바꿔도 루프가 끝나지 않을 수 있다고 설명한다. 같은 절은 Thread.sleep과 Thread.yield에는 어떤 동기화 의미도 없다고 강조한다. 즉 컴파일러는 sleep이나 yield 호출 전에 레지스터에 있는 쓰기를 메모리로 내보낼 의무도, 호출 뒤에 값을 다시 읽어 올 의무도 없다.

    실제로 루프 안에 Thread.sleep(1)을 넣은 변형을 이 기계에서 돌려 보면 worker는 멈췄다. 하지만 이것은 HotSpot이 이 경우에 읽기를 끌어올리지 않았다는 관찰일 뿐, 명세가 보장하는 동작이 아니다. "sleep을 넣었더니 고쳐졌다", "println을 넣었더니 고쳐졌다"는 경험담이 위험한 이유가 여기에 있다. 증상이 사라진 것이지 원인이 사라진 것이 아니다. 다른 JVM, 다른 버전, 다른 최적화 상황에서는 다시 나타날 수 있다.

    왼쪽은 반복마다 필드를 읽는 원래 루프, 오른쪽은 한 번만 읽고 영원히 도는 변환된 루프. 가운데에 C2 컴파일러가 변환을 수행한다. 좌우 비교 다이어그램. 왼쪽 패널 제목 "바이트코드 / 인터프리터", 안에 순서도: 상자 "running 읽기" → 마름모 "참인가?" → 예: 상자 "count++" → 다시 "running 읽기"로 돌아가는 화살표, 아니오: 상자 "루프 종료". 오른쪽 패널 제목 "C2 컴파일 후", 안에 순서도: 상자 "running 한 번 읽기" → 마름모 "참인가?" → 예: 상자 "count++"가 자기 자신으로 돌아가는 작은 순환 화살표(라벨 "다시 읽지 않음"). 두 패널 사이에 굵은 오른쪽 화살표, 라벨 "루프 불변 코드 이동". 오른쪽 패널 아래 작은 메모 "다른 스레드의 쓰기를 영영 못 본다". 흰 배경, 파랑·주황 강조, 깔끔한 선. 루프 안에서 아무도 쓰지 않는 non-volatile 필드라면, 컴파일러는 읽기를 루프 밖으로 옮겨도 된다.

    기계어로 확인하기: hsdis 없이 C2의 루프 읽기

    앞 절의 변환은 관찰된 동작에서 거꾸로 짐작한 것이었다. 이번에는 C2가 실제로 만든 기계어를 열어 확인해 보자. HotSpot은 -XX:CompileCommand=print,FlagLoop::lambda$main$0처럼 메서드를 지정하면 그 메서드가 컴파일될 때마다 결과 코드를 출력한다. hsdis가 없으면 JVM은 Loading hsdis library failed 경고를 남기고, 명령어를 기호로 풀지 못한 채 코드 영역을 16진수 그대로 덤프한다. 그래도 길이 막힌 것은 아니다. AArch64 명령어는 모두 4바이트 고정 길이라서 덤프의 4바이트 묶음 하나가 곧 명령어 하나다. 덤프는 메모리의 바이트 순서대로 찍히므로 1f20 03d5를 리틀 엔디언으로 뒤집으면 명령어 값 0xd503201f(nop)가 된다. 이 값들을 어셈블리 파일에 .long 0xd503201f처럼 한 줄씩 옮겨 적고, clang --target=arm64-apple-macos -c로 목적 파일을 만든 뒤 objdump -d로 디스어셈블하면 기호로 된 명령어를 얻는다(이 실험 환경인 macOS와 Xcode 명령줄 도구 기준).

    아래 목록은 그렇게 풀어 낸 C2 OSR 코드의 핵심 부분이다. 오른쪽 주석에는 덤프에 JVM이 직접 붙여 준 주석과 해석을 함께 적었다. 주소와 오프셋은 이 실행에서 나온 값이고, 레이블 이름(loop, trap)은 읽기 쉽게 붙인 것이다.

        mov   x19, #0x3da8            ; x19 ← 상수 주소. JVM 주석: oop(a 'java/lang/Class' = 'FlagLoop')
    movk  x19, #0x1061, lsl #16
    movk  x19, #0x70, lsl #32
    ldrb  w11, [x19, #0x70]       ; running 을 읽는다 (루프 밖, 단 한 번)
    cbz   w11, trap               ; 0(false)이면 uncommon trap 으로
loop:
    ldr   x11, [x28, #0x458]      ; x28 = 현재 스레드. 폴링 페이지 주소를 읽는다
    add   x20, x20, #0x1          ; count++ (count 는 레지스터 x20 에만 있다)
    ldr   wzr, [x11]              ; 세이프포인트 폴. JVM 주석: {poll}
    b     loop                    ; running 을 다시 읽지 않고 돌아간다

    한 줄씩 읽어 보자. 처음 세 명령은 64비트 상수를 16비트씩 조립해 x19에 넣는다. JVM은 이 상수가 FlagLoop 클래스의 java.lang.Class 객체라고 주석을 달았다. HotSpot은 클래스의 static 필드를 그 클래스를 나타내는 java.lang.Class 인스턴스, 곧 미러(mirror) 안에 둔다. HotSpot 소스 instanceMirrorKlass.hpp의 주석은 이 인스턴스가 Class의 일반 필드에 더해 그 클래스의 static 필드를 담는다고 설명한다. 그래서 [x19, #0x70]이 running이고, boolean 필드를 1바이트로 읽는 ldrb가 그 읽기다. 이 읽기는 loop 레이블보다 앞에 있다. 루프 본문 네 명령 가운데 running의 주소를 건드리는 것은 하나도 없다. 심지어 처음 읽은 값이 들어 있던 w11(x11의 아래 32비트)은 루프의 첫 명령에서 폴링 페이지 주소로 덮어쓰인다. 첫 검사를 통과한 뒤의 루프는 running과 아무 관계가 없는, 조건 없는 무한 루프다. 앞 절에서 의사 코드로 그린 호이스팅이 기계어에 그대로 있다.

    루프 안에 남은 두 ldr은 세이프포인트 폴(safepoint poll)이다. x28은 AArch64 HotSpot이 현재 JavaThread를 담아 두는 레지스터다(assembler_aarch64.hpp의 rthread = r28). 첫 ldr은 스레드마다 따로 두는 폴링 페이지 주소를 읽고, 두 번째 ldr wzr는 그 주소에서 읽기만 하고 결과는 버린다(wzr는 읽으면 항상 0이고 쓰면 버려지는 레지스터다). safepointMechanism.cpp를 보면 HotSpot은 시작할 때 페이지 두 장을 마련해 하나는 읽기 가능(good), 하나는 접근 금지(bad, MEM_PROT_NONE)로 보호해 두고, 세이프포인트나 핸드셰이크가 필요하면 스레드의 폴링 페이지 값을 접근 금지 페이지 쪽으로 바꾼다(arm). 그러면 이 읽기가 메모리 보호 위반을 일으키고, 스레드는 VM의 세이프포인트 처리로 넘어간다. 이 루프는 GC를 막지 않는다는 뜻이다. 멈출 수는 있다. 하지만 멈췄다가 다시 달려도 running을 다시 읽지는 않는다.

    실험으로 확인해 보자. FlagLoop에서 running = false 바로 뒤에 System.gc() 한 줄을 넣은 FlagLoopGc를 -Xlog:safepoint로 실행했다. 로그가 보여 주듯 이 GC(G1의 전체 GC)는 세이프포인트에서 실행된다.

    [info][safepoint] Safepoint "G1CollectFull", Time since last: 1015698708 ns, Reaching safepoint: 37500 ns, ... Total: 2352833 ns
main: running = false, System.gc() 완료
main: 2초 뒤 worker 상태 = RUNNABLE

    Reaching safepoint가 약 37마이크로초라는 것은 루프를 돌던 worker까지 모든 자바 스레드가 그 시간 안에 폴에 걸려 멈췄다는 뜻이다. GC가 끝난 뒤 worker는 다시 달렸지만 여전히 RUNNABLE이다. 운영체제 수준에서도 마찬가지다. worker가 스케줄러에 의해 CPU에서 내려졌다가 다시 올라가더라도(컨텍스트 스위칭), 커널은 스레드의 레지스터를 저장했다가 그대로 복원할 뿐 그 스레드의 기계어를 바꾸지 않는다. "스레드가 잠깐 멈추면 캐시가 비워져 언젠가는 새 값을 본다"는 기대가 성립하지 않는 이유다. 문제는 캐시에 남은 옛 값이 아니라, 읽기 자체가 사라진 기계어의 모양에 있다. 덤프에서 폴 지점에 붙은 OopMap(그 지점에서 GC가 추적해야 할 객체 참조가 어느 레지스터에 있는지 적은 표)이 {}로 비어 있다는 점도 같은 사실을 말한다. GC가 보기에도 이 루프는 FlagLoop의 Class 객체를 더 이상 참조하지 않는다.

    cbz가 뛰어가는 trap 쪽은 루프 뒤의 출력문이 아니라 uncommon trap이다. C2는 프로파일상 일어나지 않던 경로를 컴파일하지 않고 그 자리에 uncommon trap을 둔다. 실행이 그곳에 닿으면 컴파일된 코드를 버리고(역최적화, deoptimization) 인터프리터로 돌아가 이어서 실행한다. 트랩을 부르기 직전에 w1에 넣는 값 -138은 Deoptimization::make_trap_request가 사유(reason)와 조치(action)를 비트로 묶은 값의 보수이고, deoptimization.hpp의 정의대로 풀면 사유는 Reason_predicate, 소스 주석으로는 "컴파일러가 만든 술어(predicate) 검사가 실패함"이다. 같은 방식으로 뒤에 볼 volatile 버전의 값(-187)을 풀면 unstable_if가 나오는데, 그 버전을 -Xlog:deoptimization=debug로 실행하면 플래그가 바뀐 순간 실제로 unstable_if 사유로 역최적화된 기록이 찍혀 이 해석 방식이 맞다는 것을 교차 확인할 수 있다. 실험 삼아 -XX:-UseLoopPredicate를 주어 루프 술어화(loop predication)를 끄고 다시 실행해 보아도 결과는 같았다. 읽기는 여전히 루프 밖에 한 번뿐이었고(이번 트랩 사유는 unstable_if), worker는 멈추지 않았다. 최적화 하나를 끈다고 사라지는 현상이 아니다. 루프 안에 running에 쓰는 코드가 없다는 사실 하나로 여러 최적화 단계가 같은 결론에 닿는다.

    이제 필드만 volatile로 바꾼 버전의 같은 람다를 같은 방법으로 풀어 보자.

        add   x20, x19, #0x70         ; running 의 주소를 미리 계산해 둔다
    b     check
loop:
    ldr   x10, [x28, #0x458]      ; 폴링 페이지 주소
    add   x21, x21, #0x1          ; count++
    ldr   wzr, [x10]              ; 세이프포인트 폴
check:
    ldarb w11, [x20]              ; running 을 매 반복 읽는다 (load-acquire)
    cbnz  w11, loop               ; true 면 다시 루프
    ...                           ; false 면 uncommon trap(unstable_if) → 인터프리터가 루프 뒤를 실행

    이번에는 읽기가 루프 안에 있다. 게다가 일반 ldrb가 아니라 ldarb(Load-Acquire Register Byte)다. 이 명령이 왜 쓰였는지는 "volatile의 비용" 절 뒤에서 HotSpot 소스와 함께 본다. 폴 지점의 OopMap도 달라졌다. 이번에는 {r19=Oop resp=Derived_oop_r19}로, x19의 Class 객체와 거기서 계산한 주소 x20(덤프에는 인터프리터가 쓰는 별칭 resp로 찍힌다. assembler_aarch64.hpp의 esp = r20)을 GC가 추적한다. GC가 객체를 옮기면 이 두 레지스터 값도 고쳐야 하기 때문이다. 바이트코드는 같았고 달라진 것은 필드의 ACC_VOLATILE 플래그 하나였다. 그 플래그 하나가 C2에게 이 읽기를 루프 밖으로 옮기지 못하게 했다.

    volatile이 바꾼 것

    필드에 volatile을 붙이면 무엇이 달라지는가. JLS 8.3.1.4는 필드를 volatile로 선언하면 자바 메모리 모델이 모든 스레드가 그 변수의 일관된 값을 보도록 보장한다고 쓰고, 정확한 규칙은 17.4로 넘긴다. 그 규칙은 뒤에서 다루고, 여기서는 실행 관점에서 일어나는 일만 정리한다.

    • 읽기와 쓰기를 생략하거나 합치지 않는다. 소스 코드가 volatile 필드를 반복마다 읽으라고 하면 실행도 반복마다 읽는다. JSR-133 FAQ는 컴파일러와 런타임이 volatile 필드를 레지스터에 할당하는 것이 금지된다고 설명한다. 그래서 위의 호이스팅은 volatile 필드에 대해서는 일어날 수 없다.
    • 순서를 바꾸는 데 제약이 생긴다. volatile 쓰기 앞에 있던 메모리 접근은 그 쓰기 뒤로 넘어갈 수 없고, volatile 읽기 뒤에 있던 메모리 접근은 그 읽기 앞으로 올라올 수 없다. 이 제약은 컴파일러에도, 하드웨어에도 걸린다. 하드웨어에 대해서는 JVM이 메모리 배리어(memory barrier, fence) 명령이나 순서 보장이 붙은 읽기·쓰기 명령을 넣어 지킨다.
    • 다른 스레드와의 사이에 순서 관계가 생긴다. 어떤 스레드가 volatile 필드에 쓴 값을 다른 스레드가 volatile 읽기로 보면, 쓴 스레드가 그 쓰기 전에 한 모든 일이 읽은 스레드에게 보인다. 이것이 뒤에서 볼 happens-before의 한 형태다.

    첫째 항목만 보면 volatile은 "캐시를 쓰지 말고 메인 메모리에서 직접 읽어라"는 지시처럼 보이고, 실제로 그렇게 설명하는 글이 많다. 그러나 이 설명은 반만 맞는다. 하드웨어가 캐시 일관성을 유지하는 프로세서에서 volatile 읽기는 여전히 캐시를 거친다. volatile의 본질은 저장 위치가 아니라 순서다. 컴파일러와 CPU가 이 읽기와 쓰기를 생략·합치기·재배치하지 못하게 막고, 그 결과로 다른 스레드의 쓰기가 정해진 순서대로 보이게 한다. 다음 절의 실험은 가시성 문제가 단순히 "늦게 보인다"가 아니라 "순서가 뒤집혀 보인다"는 형태로도 나타난다는 것을 보여 준다.

    가시성의 다른 얼굴: 재정렬

    JLS 17.4는 메모리 모델을 소개하면서 직관에 어긋나는 예를 하나 든다. 처음에 A == B == 0이고, 스레드 1은 r2 = A; B = 1;을, 스레드 2는 r1 = B; A = 2;를 실행한다. 직관적으로는 r2 == 2이면서 r1 == 1인 결과는 불가능해 보인다. 명세는 컴파일러가 한 스레드 안에서 그 스레드 혼자의 실행 결과를 바꾸지 않는 한 명령의 순서를 바꿀 수 있고, 스레드 1의 두 문장이 뒤바뀌면 이 결과가 쉽게 나온다고 설명한다. 그리고 이 코드가 "올바르게 동기화되지 않은" 코드라는 점을 짚는다. 한 스레드의 쓰기와 다른 스레드의 읽기 사이에 동기화로 정해진 순서가 없기 때문이다.

    명세 예제와 같은 구조를 실제로 관찰할 수 있는지 실험해 보자. 이번에는 "쓰고 나서 읽기"다. 두 스레드가 각자 자기 변수에 1을 쓰고 상대 변수를 읽는다.

    처음: x = 0, y = 0

  스레드 A           스레드 B
  x = 1;   (A1)      y = 1;   (B1)
  r1 = y;  (A2)      r2 = x;  (B2)

질문: (r1, r2) = (0, 0) 이 나올 수 있는가?

    네 문장이 어떤 순서로 끼어들든(interleaving) 각 스레드 안의 순서만 지킨다면 (0, 0)은 나올 수 없다. 네 문장 중 가장 마지막에 실행되는 것은 반드시 읽기(A2 또는 B2)다. 각 스레드에서 읽기가 쓰기보다 뒤에 있기 때문이다. 마지막 문장이 A2라면 그때는 B1이 이미 끝났으므로 r1 = 1이고, 마지막이 B2라면 A1이 이미 끝났으므로 r2 = 1이다. 이처럼 모든 스레드의 문장을 각 스레드의 순서를 지키며 하나의 줄로 세울 수 있다는 가정을 순차 일관성(sequential consistency)이라고 한다. 순차 일관성 아래에서 가능한 결과는 (0, 1), (1, 0), (1, 1) 셋뿐이다.

    다음은 이 실험을 백만 번 반복하는 프로그램이다. 매 회차 main이 x와 y를 0으로 되돌리고, volatile 변수 start에 회차 번호를 써서 두 스레드를 거의 동시에 출발시킨다. 두 스레드는 일을 마치면 AtomicInteger로 완료를 알리고, main은 둘 다 끝난 것을 확인한 뒤 결과를 센다.

    import java.util.concurrent.atomic.AtomicInteger;

public class Reorder {
    static int x, y;          // 공유 변수: volatile 아님
    static int r1, r2;        // 각 스레드가 읽은 값
    static volatile int start = -1;
    static final AtomicInteger done = new AtomicInteger();

    public static void main(String[] args) throws InterruptedException {
        final int trials = 1_000_000;
        Thread a = new Thread(() -> {
            for (int i = 0; i < trials; i++) {
                while (start != i) { }
                x = 1;
                r1 = y;
                done.incrementAndGet();
            }
        });
        Thread b = new Thread(() -> {
            for (int i = 0; i < trials; i++) {
                while (start != i) { }
                y = 1;
                r2 = x;
                done.incrementAndGet();
            }
        });
        a.start(); b.start();

        int[][] seen = new int[2][2];
        for (int i = 0; i < trials; i++) {
            x = 0; y = 0;
            start = i;                          // 두 스레드 출발
            while (done.get() != 2 * (i + 1)) { }
            seen[r1][r2]++;
        }
        a.join(); b.join();
        System.out.println("(r1,r2)=(0,1): " + seen[0][1]);
        System.out.println("(r1,r2)=(1,0): " + seen[1][0]);
        System.out.println("(r1,r2)=(1,1): " + seen[1][1]);
        System.out.println("(r1,r2)=(0,0): " + seen[0][0]);
    }
}

    실험 장치 자체가 옳은지 먼저 확인하자. main의 x = 0; y = 0;은 volatile 쓰기 start = i보다 앞에 있고, 두 스레드는 volatile 읽기로 start == i를 확인한 뒤에 일을 시작한다. 그러니 두 스레드는 이번 회차의 0을 확실히 보고 출발한다. 두 스레드가 r1, r2에 쓴 값도 incrementAndGet(volatile 쓰기와 같은 효과가 있다)보다 앞에 있으므로, done.get()으로 완료를 확인한 main에게 보인다. 이 "앞에 있던 쓰기까지 함께 보인다"는 성질이 이 회차 후반부의 주제인데, 실험 장치가 이미 그것에 기대고 있다. 이 기계에서 한 번 실행한 결과는 다음과 같다.

(r1,r2)=(1,0): 1073

    순차 일관성에서는 불가능한 (0, 0)이 백만 번 중 99만 번 넘게 나왔다. 더 중요한 것은 두 번째 결과다. JIT를 끈 인터프리터에서도 (0, 0)이 96만 번 넘게 나왔다. 인터프리터는 바이트코드를 순서대로 하나씩 실행하므로 컴파일러가 순서를 바꾼 것이 아니다. 이번에는 하드웨어가 순서를 바꿨다. 반면 x, y를 volatile로 선언하자 (0, 0)은 한 번도 나오지 않았다. 이것은 우연이 아니라 명세가 보장하는 결과인데, 그 증명은 happens-before를 세운 뒤에 다시 한다.

    저장 버퍼: 쓰기가 잠시 머무는 곳

    하드웨어가 순서를 바꾸는 대표적인 원인이 저장 버퍼다. 코어가 메모리에 값을 쓸 때, 그 쓰기를 캐시에 반영하려면 다른 코어 캐시의 사본을 무효로 만드는 등 시간이 드는 절차가 필요하다. 코어는 그 절차가 끝날 때까지 멈춰 있지 않고, 쓰기를 자기 저장 버퍼에 넣어 둔 채 다음 명령으로 넘어간다. 저장 버퍼에 있는 값은 그 코어 자신은 읽을 수 있지만(같은 코어의 뒤따르는 읽기는 버퍼에서 값을 가져온다) 다른 코어에는 아직 보이지 않는다. Doug Lea의 JSR-133 Cookbook도 메모리 배리어 명령이 직접 다루는 대상이 CPU와 캐시, 그리고 메모리로 내보내질 쓰기를 붙잡고 있는 쓰기 버퍼 사이의 상호작용이라고 설명한다.

    시간 →
코어 A: [x=1 을 저장 버퍼에 넣음] [y 를 캐시에서 읽음 → 0] ...... [x=1 이 캐시에 반영]
코어 B: [y=1 을 저장 버퍼에 넣음] [x 를 캐시에서 읽음 → 0] ...... [y=1 이 캐시에 반영]

각 코어 입장에서 자기 쓰기는 먼저 일어났다.
하지만 상대 코어에게는 "읽기가 먼저, 쓰기가 나중"으로 보인다 → (r1, r2) = (0, 0)

    두 스레드가 거의 동시에 출발하면 위 그림처럼 둘 다 자기 쓰기를 버퍼에 넣고 곧바로 상대 변수를 읽는다. 상대의 쓰기는 아직 버퍼에 있으니 둘 다 0을 읽는다. 이 실험에서 (1, 1)이 거의 나오지 않고 (0, 0)이 압도적으로 많이 나온 것은, 두 스레드가 겹쳐 실행될 때마다 이 일이 일어났다는 뜻이다. 이렇게 "앞선 쓰기보다 뒤의 읽기가 먼저 효과를 내는" 재정렬을 저장-적재 재정렬(store-load reordering)이라고 한다.

    이 재정렬은 ARM만의 이야기가 아니다. 비교적 강한 메모리 순서를 보장하는 x86 계열도 Intel 소프트웨어 개발자 매뉴얼(SDM) 3권의 메모리 순서 절에 "적재는 다른 위치에 대한 앞선 저장과 재정렬될 수 있다(Loads May Be Reordered with Earlier Stores to Different Locations)"는 규칙을 두고 있다. JSR-133 Cookbook의 프로세서 표에서도 x86은 네 종류의 배리어 가운데 StoreLoad만 실제 명령(mfence나 lock 접두사가 붙은 명령)이 필요하고 나머지 셋은 아무것도 하지 않는(no-op) 플랫폼으로 정리되어 있다. 하드웨어마다 허용하는 재정렬의 종류는 다르지만, 이 실험이 보여 준 종류는 오늘날 널리 쓰이는 프로세서에서 공통으로 일어난다고 보면 된다. Cookbook은 머리말에서 스스로 이제 역사적 관심사일 뿐인 문서이고 프로세서 지원에 관한 일부 설명은 낡았다고 밝히고 있으므로, 개별 프로세서의 세부는 해당 제조사 문서로 확인해야 한다.

    이런 실험은 손으로 만든 장치로는 결과가 쉽게 흔들린다. 출발 타이밍, 코어 배치, JIT 상태에 따라 수치가 크게 달라진다. OpenJDK는 이런 동시성 테스트를 체계적으로 돌리기 위한 도구 jcstress를 별도로 제공한다. 여기서 중요한 것은 수치가 아니라 "(0, 0)이 나올 수 있다"와 "volatile이면 나올 수 없다"라는 두 사실이다.
    두 코어가 각자 쓰기를 저장 버퍼에 넣은 채 상대 변수를 캐시에서 읽어 둘 다 0을 얻는 과정을 시간 순서로 보여 준다. 세로 시퀀스 다이어그램. 위쪽에 세 개의 생명선 머리: 왼쪽 "코어 A", 가운데 "공유 캐시", 오른쪽 "코어 B". 코어 A와 코어 B 생명선 옆에 각각 작은 상자 "저장 버퍼". 위에서 아래로 순서대로: ① 코어 A에서 자기 저장 버퍼로 짧은 화살표, 라벨 "x = 1 보관". ② 코어 B에서 자기 저장 버퍼로 짧은 화살표, 라벨 "y = 1 보관". ③ 코어 A에서 공유 캐시로 화살표, 되돌아오는 점선 화살표 라벨 "y 읽음 → 0". ④ 코어 B에서 공유 캐시로 화살표, 되돌아오는 점선 화살표 라벨 "x 읽음 → 0". ⑤ 두 저장 버퍼에서 공유 캐시로 늦게 내려가는 화살표, 라벨 "나중에 반영". 아래쪽 결과 상자 "(r1, r2) = (0, 0)". 흰 배경, 단색 선, 번호 원형 배지. 각 코어의 쓰기가 저장 버퍼에 머무는 동안 상대 코어는 옛 값을 읽는다. 순차 일관성에서는 불가능한 (0, 0)이 이렇게 나온다.

    volatile의 비용

    순서를 지키게 하는 데는 대가가 따른다. 단일 스레드에서 일반 long 필드와 volatile long 필드를 각각 1억 번 증가시키는 시간을 재 보자.

    public class Cost {
    static long plain;
    static volatile long vol;

    static void plainLoop(int n) { for (int i = 0; i < n; i++) plain++; }
    static void volatileLoop(int n) { for (int i = 0; i < n; i++) vol++; }

    public static void main(String[] args) {
        int n = 100_000_000;
        for (int round = 1; round <= 3; round++) {
            long t0 = System.nanoTime();
            plainLoop(n);
            long t1 = System.nanoTime();
            volatileLoop(n);
            long t2 = System.nanoTime();
            System.out.printf("round %d: plain %d ms, volatile %d ms%n",
                    round, (t1 - t0) / 1_000_000, (t2 - t1) / 1_000_000);
        }
        System.out.println(plain + " " + vol);
    }
}
    round 1: plain 4 ms, volatile 609 ms
round 2: plain 3 ms, volatile 626 ms
round 3: plain 2 ms, volatile 606 ms
300000000 300000000

    숫자 자체보다 해석이 중요하다. 일반 필드 쪽은 1억 번 증가에 몇 밀리초가 걸렸다. 한 번에 0.04나노초 미만인데, 수 GHz로 도는 CPU의 클럭 한 주기는 0.2~0.5나노초 정도다. 한 주기보다 짧은 시간에 메모리 쓰기를 한 번씩 했을 리가 없다. 컴파일러가 루프를 바꿔 버린 것이다. 필드 값을 레지스터에 올려 두고 증가시키다가 마지막에 한 번만 쓰거나, 아예 루프 전체를 덧셈 한 번으로 바꿀 수 있다. 단일 스레드에서 결과가 같으니 허용되는 변환이다. 앞 절의 호이스팅과 같은 종류의 자유다.

    volatile 쪽은 그 자유가 없다. 1억 번의 증가는 1억 번의 volatile 읽기와 1억 번의 volatile 쓰기로 실제로 수행되고, 쓰기마다 순서를 보장하기 위한 장치가 따라붙는다. Cookbook은 네 종류의 배리어 중 "쓰기 뒤의 읽기"를 막는 StoreLoad 배리어가 거의 모든 최신 멀티프로세서에서 필요하고 보통 가장 비싼 종류라고 설명한다. 저장 버퍼에서 값을 꺼내 읽는 지름길을 막아야 하고, 이것이 버퍼를 완전히 비우는 식으로 구현될 수 있기 때문이다. Cookbook의 구현 지침은 volatile 쓰기마다 그 뒤에 StoreLoad 배리어를 두는 것이다.

    이 차이를 "volatile은 느리니 쓰지 말라"로 읽으면 안 된다. 이 측정은 volatile 접근만 1억 번 반복하는 극단적인 경우다. 종료 플래그처럼 가끔 쓰이고 루프 조건에서 읽히는 변수에 volatile을 붙이는 비용은 대부분의 프로그램에서 문제가 되지 않는다. 판단 기준은 반대 방향이다. 여러 스레드가 공유하는 변수에 동기화 장치를 빼서 얻는 성능은, 그 대가로 프로그램의 정확성을 잃은 것이다. 성능을 이야기하기 전에 먼저 맞아야 한다.

    한 층 더 아래: HotSpot이 volatile을 기계어로 옮기는 방법

    앞에서 본 비용 차이와 ldarb의 정체를 OpenJDK 21 HotSpot의 소스와 이 기계(AArch64)의 기계어로 확인해 보자. HotSpot에서 바이트코드를 실행하는 주체는 템플릿 인터프리터, C1, C2 셋이다. 같은 필드를 어떤 스레드는 인터프리터로, 어떤 스레드는 C2 코드로 접근할 수 있으므로, 셋 모두 같은 규칙을 지켜야 하고 서로 섞여도 규칙이 깨지지 않아야 한다. 여기서는 C2와 인터프리터를 본다.

    C2: 배리어 노드를 거쳐 ldar/stlr로

    C2는 바이트코드를 먼저 자체 중간 표현(ideal graph)으로 바꾼다. 필드 접근을 이 그래프로 옮기는 공통 코드는 src/hotspot/share/gc/shared/c2/barrierSetC2.cpp의 BarrierSetC2::store_at·load_at이고, 배리어 노드는 두 함수가 맨 처음 만드는 C2AccessFence 객체가 넣는다(생성자가 접근 앞, 소멸자가 접근 뒤). 접근이 volatile이면(소스에서는 MO_SEQ_CST 장식자로 표시된다) 쓰기 앞에 MemBarRelease 노드를, 쓰기 뒤에 MemBarVolatile 노드를 넣고, 읽기 뒤에는 MemBarAcquire 노드를 넣는다. 쓰기 앞 배리어에 붙은 소스 주석은 그 목적을 "뒤따르는 메모리 연산이 volatile 쓰기 아래로 흘러 내려가지 못하게 막는 것"이라고 적는다. 즉 이 노드들은 먼저 최적화기에게 거는 제약이고, 명령어 선택 단계에 가서야 플랫폼마다 실제 CPU 명령으로 바뀌거나 아무 명령도 남기지 않는다. 같은 클래스에는 support_IRIW_for_not_multiple_copy_atomic_cpu라는 분기도 있어서, 이 값이 참인 플랫폼에서는(globalDefinitions.hpp에 따르면 OpenJDK 21에서는 한 코어의 쓰기가 모든 다른 코어에 동시에 보인다는 성질, 곧 multiple-copy atomicity가 없는 아키텍처 가운데 PPC64 하나뿐이다) 무거운 MemBarVolatile을 쓰기 뒤가 아니라 volatile 읽기 앞에 둔다. 규칙은 하나지만 구현 위치는 하드웨어에 따라 옮겨 다닌다.

    AArch64의 명령어 선택 규칙 파일 src/hotspot/cpu/aarch64/aarch64.ad에는 "Optimizaton of volatile gets and puts"(철자는 원문 그대로)라는 긴 주석이 있다. 요지는 이렇다. AArch64에는 volatile 읽기와 쓰기 구현에 안전하게 쓸 수 있는 ldar(load-acquire)와 stlr(store-release) 계열 명령이 있어서 volatile 읽기는 ldar 하나, volatile 쓰기는 stlr 하나면 된다. 다른 방법은 일반 명령에 배리어를 붙이는 것으로, 읽기는 ldr 뒤에 dmb ishld, 쓰기는 dmb ish, str, dmb ish 순서다. C2는 앞의 배리어 노드 배치가 volatile 접근을 옮길 때만 생기는 고유한 "서명"이라는 점을 이용한다. needs_acquiring_load, unnecessary_acquire, unnecessary_volatile 같은 술어 함수로 그 서명을 알아보면, 배리어 노드는 빈 명령으로 처리하고 접근 자체를 ldar/stlr로 낸다. 앞 절 루프의 ldarb가 바로 이것이다.

    Cost의 두 루프도 같은 방법으로 풀어 보면 차이가 그대로 드러난다. 아래는 일반(OSR이 아닌) C2 컴파일 코드에서 펼친 본문만 옮긴 것이다.

    ; plainLoop: 16번 펼친(unroll) 본문. plain 의 값은 레지스터 x13 에 있다
    add   x14, x13, #0xf
    add   x13, x13, #0x10         ; 16번의 증가를 덧셈 한 번으로
    str   x14, [x10, #0x70]
    add   w12, w12, #0x10         ; i += 16
    str   x13, [x10, #0x70]
    cmp   w12, w16
    b.lt  (본문 처음으로)

; volatileLoop: 8번 펼친 본문. 증가마다 읽기-더하기-쓰기가 그대로 남는다
    ldar  x2, [x12]               ; vol 읽기 (load-acquire)
    add   x2, x2, #0x1
    stlr  x2, [x11]               ; vol 쓰기 (store-release)
    ldar  x2, [x14]
    add   x2, x2, #0x1
    stlr  x2, [x13]
    ...                           ; 같은 세 줄이 모두 8벌
    add   w6, w6, #0x8            ; i += 8

    volatile 쪽의 x11, x12, x13, x14 같은 레지스터는 모두 미리 같은 주소(Class 객체 + 0x78, 곧 vol)로 채워 둔 것이다. 일반 필드 쪽은 루프를 16번 펼치고 16번의 증가를 레지스터 덧셈 한 번으로 합쳤다. 메모리에는 16번 증가마다 저장 두 번만 남았다. "volatile의 비용" 절에서 1억 번 증가가 몇 밀리초에 끝난 이유가 이것이다. volatile 쪽도 루프를 8번 펼쳤지만, 펼친 본문 안에 ldar-add-stlr이 8벌 그대로 있다. 합치지도, 레지스터에 두지도 못한다. 눈여겨볼 점은 dmb가 하나도 없다는 것이다. Cookbook의 지침은 volatile 쓰기 뒤에 StoreLoad 배리어를 두라고 하지만, 이 기계의 C2는 그것을 별도 명령으로 내지 않고 aarch64.ad 주석대로 stlr과 ldar의 순서 의미에 맡겼다. 이 기계에서 600밀리초를 쓴 것은 배리어 명령이 아니라, 생략도 병합도 할 수 없는 1억 쌍의 순서 보장 읽기·쓰기였다.

    인터프리터: 실행할 때 volatile 플래그를 검사한다

    인터프리터는 사정이 다르다. 템플릿 인터프리터의 getstatic·getfield 코드는 JVM이 시작할 때 한 번 만들어져 모든 필드 접근에 쓰이므로, 필드가 volatile인지는 실행할 때 상수 풀 캐시(constant pool cache) 항목의 플래그 비트를 보고 판단한다. src/hotspot/cpu/aarch64/templateTable_aarch64.cpp의 getfield_or_static과 putfield_or_static은 그 비트가 꺼져 있으면 건너뛰는 분기(tbz) 뒤에 배리어를 둔다. 진단 옵션 -XX:+UnlockDiagnosticVMOptions -XX:+PrintInterpreter로 템플릿을 덤프해 앞의 방법으로 풀면, 이 기계에서 실제로 나오는 명령은 다음과 같다.

    접근소스에 적힌 배리어이 기계에서 나온 명령 (volatile일 때만 실행)
    volatile 읽기 (getstatic)읽기 앞 membar(AnyAny), 읽기 뒤 membar(LoadLoad | LoadStore)dmb ish → ldrb 등 → dmb ishld
    volatile 쓰기 (putstatic)쓰기 앞 membar(StoreStore | LoadStore), 쓰기 뒤 membar(StoreLoad | StoreStore)dmb ish → strb 등 → dmb ish

    배리어 이름이 어떤 dmb로 바뀌는지도 소스에 있다. assembler_aarch64.hpp는 LoadLoad와 LoadStore를 ISHLD로, StoreStore를 ISHST로, StoreLoad와 AnyAny를 ISH로 정의하고, 여러 종류를 함께 요구하면 그 값들을 비트 OR로 합친다. ISHLD(0b1001)와 ISHST(0b1010)를 합치면 ISH(0b1011)가 되므로, StoreStore와 LoadStore를 함께 요구한 쓰기 앞 배리어는 전체 배리어 dmb ish가 된다. 인터프리터는 C2처럼 ldar/stlr을 쓰지 않고 aarch64.ad 주석이 "다른 방법"으로 든 일반 명령과 dmb의 조합을 쓰는 셈인데, 읽기 앞의 dmb ish 하나가 더 붙어 있다.

    그 읽기 앞 배리어에는 버그 번호 8179954가 붙은 주석이 달려 있다. 내용을 옮기면, volatile 접근을 위해 만든 코드는 STLR·LDAR과 섞여도 순차 일관적인 연산 집합을 이뤄야 하는데, 이 배리어가 없으면 읽기는 LDR과 DMB로, 쓰기는 STLR로 이뤄질 때 단순한 Dekker 테스트가 실패할 수 있고, 이것은 C2가 한 메서드의 쓰기를 컴파일하고 다른 메서드의 읽기는 인터프리터가 실행할 때 일어날 수 있다는 것이다. Dekker 테스트는 이 회차의 Reorder와 같은 구조, 곧 각자 자기 변수에 쓰고 상대 변수를 읽는 코드다. 뒤의 happens-before 절에서 x, y가 volatile이면 (0, 0)이 명세상 불가능하다는 것을 증명하는데, 그 증명은 두 스레드가 어떤 방식으로 실행되고 있는지 묻지 않는다. 그래서 HotSpot은 한 스레드는 C2 코드(stlr)로, 다른 스레드는 인터프리터로 같은 변수에 접근하는 혼합 상황에서도 (0, 0)이 나오지 않도록 배리어를 하나 더한 것이다. 이 앞쪽 배리어는 C2나 JVMCI 컴파일러를 쓸 수 있는 구성에서만 생성되고, -Xint처럼 인터프리터만 쓰거나 C1만 쓰는 구성에서는 빠진다(소스의 !CompilerConfig::is_c1_or_interpreter_only_no_jvmci() 조건).

    반대로 volatile이 아닌 필드에서는 tbz가 배리어를 모두 건너뛰므로 인터프리터도 일반 ldr·str만 실행한다. 재정렬 실험을 -Xint로 돌려도 (0, 0)이 96만 번 넘게 나온 이유가 여기서 확인된다. 인터프리터는 바이트코드 순서대로 명령을 냈지만 그 사이에 순서를 강제하는 명령이 하나도 없었고, 그러니 저장 버퍼가 만드는 저장-적재 재정렬을 막을 것이 없었다.

    volatile이 해 주지 않는 것: 원자성

    volatile이 가시성과 순서를 보장한다면, 두 스레드가 volatile 카운터를 함께 증가시키면 정확한 값이 나올까.

    public class VolatileCounter {
    static volatile int count = 0;

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            for (int i = 0; i < 1_000_000; i++) {
                count++;
            }
        };
        Thread t1 = new Thread(task);
        Thread t2 = new Thread(task);
        t1.start(); t2.start();
        t1.join(); t2.join();
        System.out.println("count = " + count + " (기대값 2000000)");
    }
}
    count = 1310395 (기대값 2000000)
count = 1160418 (기대값 2000000)
count = 1362854 (기대값 2000000)

    200만이 나와야 할 자리에 110만~130만대가 나왔다. 수십만 번의 증가가 사라졌다. 원인은 바이트코드에서 바로 보인다. count++는 한 줄짜리 문장이지만 명령 하나가 아니다.

           8: getstatic     #28   // Field count:I     ① 읽는다
      11: iconst_1                                 ② 1을 올린다
      12: iadd                                     ③ 더한다
      13: putstatic     #28   // Field count:I     ④ 쓴다

    읽기(①)와 쓰기(④)가 각각 volatile 접근이라는 것은, 각각이 개별적으로 순서와 가시성을 지킨다는 뜻이다. 그러나 ①과 ④ 사이에 다른 스레드가 끼어드는 것은 막지 않는다. 두 스레드가 다음 순서로 끼어들면 증가 한 번이 사라진다.

    순서스레드 t1스레드 t2메모리의 count
    1getstatic → 10을 읽음10
    2getstatic → 10을 읽음10
    3iadd → 1110
    4putstatic 1111
    5iadd → 1111
    6putstatic 1111

    두 번 증가했는데 값은 1만 늘었다. 이 실행에서 volatile 규칙은 하나도 어겨지지 않았다. 2번 시점에 t2가 읽은 10은 그 시점에 가장 최근에 쓰인 값이 맞다. volatile은 "읽는 순간의 최신 값"을 보장할 뿐, "읽고-계산하고-쓰는" 세 단계를 하나로 묶어 주지 않는다. 이렇게 여러 단계로 된 연산이 중간에 끊기지 않고 한 번에 일어나는 성질을 원자성(atomicity)이라고 하고, 이 문제를 경합 조건(race condition)이라고 한다. 원자성을 얻는 방법은 다음 회차부터 차례로 다룬다. 06회의 synchronized는 임계 영역을 한 번에 한 스레드만 실행하게 해서, 10회의 CAS와 AtomicInteger는 "비교 후 교환"을 하드웨어가 제공하는 원자적 명령으로 처리해서 이 문제를 푼다.

    그렇다면 volatile이 정확히 맞는 자리는 어디인가. 기준은 단순하다. 쓰는 값이 그 변수의 현재 값에 의존하지 않고, 그 변수가 다른 변수와 함께 지켜야 하는 불변식에 묶여 있지 않을 때다. 종료 플래그(running = false), 한 스레드만 갱신하고 여러 스레드가 읽는 상태 값, 완성된 객체를 다른 스레드에 넘기는 참조가 전형적인 예다. 반대로 count++, if (x == null) x = ...처럼 읽은 값을 보고 쓰는 코드는 volatile만으로는 안전하지 않다.

    예외 하나: long과 double의 찢어진 쓰기

    원자성과 관련해 volatile이 직접 해 주는 일이 하나 있다. JLS 17.7은 메모리 모델에서 non-volatile long이나 double에 대한 쓰기 한 번을 32비트 절반씩 두 번의 쓰기로 취급한다고 정한다. 그래서 한 스레드가 어떤 쓰기의 앞 32비트와 다른 쓰기의 뒤 32비트를 섞어서 보는 일이 명세상 허용된다. 같은 절은 volatile long과 double의 읽기와 쓰기는 항상 원자적이라고 정한다. 64비트 JVM에서 이 찢어짐을 실제로 보기는 어렵지만, 명세가 보장하지 않는 것에 기대지 않으려면 여러 스레드가 공유하는 long·double은 volatile로 선언하거나 락으로 보호한다. 이 원자성은 단일 읽기와 단일 쓰기에 대한 것이고, ++ 같은 복합 연산은 여전히 원자적이지 않다.

    자바 메모리 모델이 필요한 이유

    지금까지 본 현상을 정리하면, 다른 스레드의 쓰기가 보이는 시점과 순서는 세 층에서 바뀔 수 있다. 소스 코드를 바이트코드로 바꾸는 javac, 바이트코드를 기계어로 바꾸는 JIT 컴파일러, 그리고 기계어를 실행하는 CPU다. 이 세 층은 각자 "한 스레드 안에서 결과가 같다면" 순서를 바꾸고, 읽기를 생략하고, 쓰기를 합친다. 그 자유 덕분에 단일 스레드 프로그램이 빨라진다. 문제는 그 자유가 다른 스레드에서 관찰될 때다.

    프로그래머가 이 세 층의 동작을 모두 알고 코드를 짜는 것은 불가능하다. JIT 최적화는 버전마다 달라지고, CPU 메모리 순서 규칙은 아키텍처마다 다르다. 자바는 "한 번 작성하면 어디서나 실행된다"를 약속하는 언어이므로, 어떤 하드웨어에서 어떤 JIT로 돌든 같은 의미를 갖는 규칙이 필요하다. 그 규칙이 자바 메모리 모델이다. JLS 17.4는 메모리 모델을 이렇게 정의한다. 프로그램과 그 실행 추적(execution trace)이 주어졌을 때 그 실행이 허용되는 실행인지 판정하는 것이고, 실행 추적의 각 읽기가 관찰한 쓰기가 규칙에 맞는지 검사하는 방식으로 동작한다.

    이 정의가 말하는 바를 풀어 보자. 메모리 모델은 "CPU 캐시를 이렇게 동기화하라" 같은 구현 지시가 아니다. 어떤 읽기가 어떤 쓰기의 값을 볼 수 있는지를 정하는 규칙이다. JVM 구현자는 그 규칙을 지키는 한 어떤 최적화든 할 수 있고, 프로그래머는 그 규칙만 알면 구현을 몰라도 된다. 메모리 모델은 이 둘 사이의 계약이다. 자바 5에서 JSR-133을 통해 이 계약이 지금의 모습으로 다시 쓰였고, JSR-133 FAQ는 그때 volatile의 의미가 동기화에 가까운 수준까지 크게 강화되었다고 설명한다.

    JLS 17.4의 기본 개념

    JLS 17.4는 몇 개의 정의를 쌓아 올려 규칙을 만든다. 순서대로 보자.

    공유 변수와 충돌하는 접근. 스레드 사이에 공유될 수 있는 메모리, 즉 힙에 있는 인스턴스 필드, static 필드, 배열 원소를 공유 변수라고 한다. 지역 변수와 메서드 매개변수는 스레드마다 자기 스택에 있으므로 공유되지 않고 메모리 모델의 영향을 받지 않는다. 같은 변수에 대한 두 접근 가운데 적어도 하나가 쓰기이면, 두 접근은 충돌한다(conflicting)고 한다(17.4.1).

    동기화 동작. 17.4.2는 스레드 사이에 영향을 주는 동작 중 일부를 동기화 동작(synchronization action)으로 분류한다. volatile 읽기, volatile 쓰기, 모니터 잠금(lock), 모니터 해제(unlock), 스레드의 (가상의) 첫 동작과 마지막 동작, 그리고 스레드를 시작하는 동작과 스레드가 종료되었음을 감지하는 동작이다. 일반 필드의 읽기와 쓰기는 동기화 동작이 아니다.

    프로그램 순서. 각 스레드 안에서 동작들이 소스 코드의 의미대로 놓이는 순서를 프로그램 순서(program order)라고 한다(17.4.3). 같은 절에 순차 일관성의 정의도 있다. 모든 동작이 프로그램 순서와 일치하는 하나의 전체 순서로 일어나고, 각 읽기는 그 순서에서 가장 최근의 쓰기를 보는 실행이다. 앞의 (0, 0) 실험이 보여 주듯 실제 실행은 순차 일관적이지 않을 수 있다.

    동기화 순서. 17.4.4는 모든 실행에 동기화 순서(synchronization order)가 있다고 정한다. 동기화 순서는 그 실행의 모든 동기화 동작에 대한 전체 순서(total order)이고, 각 스레드 안에서는 프로그램 순서와 일치한다. 일반 읽기·쓰기는 스레드 사이에서 순서가 정해지지 않을 수 있지만, 동기화 동작들은 모든 스레드가 동의하는 하나의 줄로 세워진다는 뜻이다.

    synchronizes-with. 동기화 순서 위에서 특정한 쌍이 "synchronizes-with" 관계를 맺는다. 17.4.4가 정하는 쌍은 다음과 같다.

    • 모니터 m의 해제(unlock)는 동기화 순서상 그 뒤에 오는 m의 모든 잠금(lock)과 synchronizes-with 관계다.
    • volatile 변수 v에 대한 쓰기는 동기화 순서상 그 뒤에 오는, 어느 스레드의 것이든 v에 대한 모든 읽기와 synchronizes-with 관계다.
    • 스레드를 시작하는 동작은 시작된 스레드의 첫 동작과 synchronizes-with 관계다.
    • 각 변수에 기본값(0, false, null)을 쓰는 동작은 모든 스레드의 첫 동작과 synchronizes-with 관계다.
    • 스레드 T1의 마지막 동작은, 다른 스레드 T2가 T1의 종료를 감지하는 동작(T1.isAlive()나 T1.join())과 synchronizes-with 관계다.
    • T1이 T2를 인터럽트하면, 그 인터럽트는 어떤 스레드든(T2 자신 포함) T2가 인터럽트되었음을 확인하는 지점(InterruptedException이 던져지거나 Thread.interrupted, isInterrupted를 호출하는 지점)과 synchronizes-with 관계다.

    목록을 보면 03회와 04회에서 다룬 start, join, 인터럽트가 모두 들어 있다. 그때는 이 메서드들의 동작만 봤지만, 메모리 모델 관점에서 이 메서드들은 스레드 사이에 값을 안전하게 전달하는 통로이기도 하다.

    happens-before: 보이는 것의 규칙

    이제 핵심 관계를 세울 수 있다. 17.4.5는 두 동작이 happens-before 관계로 순서 지어질 수 있고, 한 동작이 다른 동작보다 happens-before이면 앞의 것이 뒤의 것에 보이고 순서상 앞선다고 정한다. x가 y보다 happens-before인 것을 hb(x, y)로 쓴다. 규칙은 네 가지다.

    1. x와 y가 같은 스레드의 동작이고 프로그램 순서에서 x가 y보다 앞이면 hb(x, y)다.
    2. 객체 생성자의 끝에서 그 객체의 종료자(finalizer) 시작까지 happens-before 간선이 있다.
    3. x가 y와 synchronizes-with 관계이면 hb(x, y)다.
    4. hb(x, y)이고 hb(y, z)이면 hb(x, z)다(이행성).

    그러면 어떤 읽기는 어떤 쓰기를 볼 수 있는가. 17.4.5는 변수 v에 대한 읽기 r이 v에 대한 쓰기 w를 관찰하는 것이 허용되는 조건을 둘로 정한다. 첫째, r이 w보다 happens-before가 아니어야 한다. 아직 일어나지도 않은 미래의 쓰기를 볼 수는 없다는 뜻이다. 둘째, w와 r 사이에 끼어드는 다른 쓰기 w'(hb(w, w')이고 hb(w', r)인 쓰기)가 없어야 한다. 명세는 이것을 "읽기를 막는 happens-before 순서가 없다면 읽기는 쓰기의 결과를 볼 수 있다"고 풀어 쓴다.

    이 정의를 거꾸로 읽는 것이 중요하다. happens-before는 "무엇을 반드시 보게 되는가"를 정한다. hb(w', r)인 쓰기 w'가 있으면, r은 w'보다 앞선 쓰기들을 볼 수 없으므로 w'나 그 뒤의 쓰기를 봐야 한다. 반대로 어떤 쓰기와 읽기 사이에 happens-before가 없으면, 읽기는 그 쓰기를 볼 수도 있고 그보다 옛날 값을 볼 수도 있다. 명세는 어느 쪽인지 정하지 않는다. 처음의 FlagLoop가 정확히 이 경우다. main의 running = false와 worker의 running 읽기 사이에는 아무 happens-before가 없었다. 그래서 worker가 영원히 초기값 true를 보는 실행도 허용된 실행이었고, C2는 그 허용 범위 안에서 최적화했을 뿐이다.

    이제 데이터 경합(data race)을 정의할 수 있다. 17.4.5에 따르면 프로그램에 happens-before 관계로 순서 지어지지 않은 두 충돌하는 접근이 있으면, 그 프로그램은 데이터 경합을 포함한다. 그리고 메모리 모델의 가장 중요한 약속이 이어진다. 순차 일관적인 실행이 모두 데이터 경합을 갖지 않는 프로그램을 올바르게 동기화되었다(correctly synchronized)고 하며, 올바르게 동기화된 프로그램의 모든 실행은 순차 일관적인 것처럼 보인다. 17.4.3은 같은 내용을 "데이터 경합이 없는 프로그램의 모든 실행은 순차 일관적인 것처럼 보인다"고 쓴다.

    이 장의 핵심

    공유 변수에 대한 모든 충돌하는 접근 쌍을 happens-before로 묶어 두면(데이터 경합이 없으면), 컴파일러와 CPU가 내부에서 무슨 재정렬을 하든 프로그램은 모든 문장이 순서대로 하나씩 실행되는 것처럼 동작한다. 묶지 않은 쌍이 하나라도 있으면 그 접근에 대해서는 직관이 통하지 않는다. 프로그래머의 일은 재정렬을 상상하는 것이 아니라, 공유 변수에 대한 모든 충돌하는 접근이 happens-before로 연결되어 있는지 확인하는 것이다.

    이것으로 앞의 실험 결과를 설명할 수 있다. x, y를 volatile로 선언한 실험에서 (0, 0)이 불가능한 이유를 증명해 보자. 네 동작 A1(x = 1), A2(r1 = y), B1(y = 1), B2(r2 = x)는 모두 volatile 접근이므로 동기화 동작이고, 하나의 동기화 순서에 놓인다. 이 순서는 각 스레드의 프로그램 순서와 일치하므로 A1은 A2보다, B1은 B2보다 앞이다. 두 쓰기 A1과 B1 중 동기화 순서에서 먼저 오는 것을 A1이라고 하자. 그러면 순서는 A1, B1, B2가 이 순서대로 놓인다. 즉 B2(x 읽기)는 A1(x 쓰기)보다 뒤이므로 A1은 B2와 synchronizes-with 관계이고 hb(A1, B2)다. x의 초기값 0을 쓴 동작은 A1보다 happens-before이므로, B2와 초기값 쓰기 사이에 A1이 끼어든다. 따라서 B2는 초기값 0을 볼 수 없고 r2 = 1이다. B1이 먼저인 경우는 대칭으로 r1 = 1이다. 어느 경우든 (0, 0)은 나올 수 없다. 실험에서 0번이 나온 것은 운이 아니라 명세의 결과다.

    volatile에 올라타기: 이행성이 만드는 안전한 전달

    happens-before의 이행성은 volatile 변수 하나로 그 앞의 일반 변수들까지 안전하게 전달할 수 있게 한다. 다음 코드에서 data는 volatile이 아니다.

    public class Piggyback {
    static int data;                    // volatile 아님
    static volatile boolean ready;      // volatile

    public static void main(String[] args) throws InterruptedException {
        Thread reader = new Thread(() -> {
            while (!ready) { }          // (3) volatile 읽기가 true를 볼 때까지
            System.out.println("data = " + data);   // (4)
        });
        reader.start();

        Thread.sleep(100);
        data = 42;                      // (1) 일반 쓰기
        ready = true;                   // (2) volatile 쓰기
        reader.join();
    }
}
    data = 42

    reader가 data = 0을 출력할 수 없는 이유를 규칙으로 따져 보자.

    이 패턴은 volatile을 "깃발"로 쓰고 실제 데이터는 그 깃발에 올라타서(piggyback) 전달되게 한다. JSR-133 FAQ도 같은 구조의 예를 들어, 읽는 쪽이 volatile 변수에서 true를 봤다면 그 앞에 쓴 42도 반드시 보게 된다고 설명하고, 옛 메모리 모델에서는 이것이 보장되지 않았다고 덧붙인다. 자바 5에서 volatile의 의미가 강화되었다는 말이 바로 이것이다.

    이 보장에는 조건이 둘 있다. 첫째, 순서가 중요하다. main에서 ready = true;를 먼저 쓰고 data = 42;를 나중에 쓰면 사슬의 첫 고리(hb(1, 2))가 끊긴다. 그러면 reader는 ready가 참인 것을 보고도 data는 0을 볼 수 있다. volatile 쓰기는 그 앞의 쓰기들만 함께 내보낸다. 둘째, 같은 volatile 변수를 써야 한다. 쓰는 쪽은 ready에, 읽는 쪽은 다른 volatile 변수를 읽는다면 synchronizes-with 관계가 생기지 않는다.

    main 스레드와 reader 스레드 두 생명선 위에 (1)~(4) 네 동작을 놓고, 프로그램 순서·synchronizes-with·이행성 간선을 서로 다른 화살표로 보여 준다. 두 개의 세로 생명선. 왼쪽 "main 스레드", 오른쪽 "reader 스레드". 왼쪽 생명선 위쪽에 점 "(1) data = 42", 그 아래 점 "(2) ready = true (volatile 쓰기)". 오른쪽 생명선의 더 아래쪽에 점 "(3) ready 읽기 → true", 그 아래 점 "(4) data 읽기". (1)에서 (2)로 짧은 실선 화살표 라벨 "프로그램 순서", (2)에서 (3)으로 대각선 굵은 주황 화살표 라벨 "synchronizes-with", (3)에서 (4)로 짧은 실선 화살표 라벨 "프로그램 순서". (1)에서 (4)로 길게 휘어진 점선 파란 화살표 라벨 "이행성: (1)이 (4)에 보인다". 아래쪽 결과 상자 "출력: data = 42". 흰 배경, 단순한 선, 번호 라벨은 원 안에. volatile 쓰기 앞의 일반 쓰기도, 그 volatile 값을 읽은 스레드에게는 함께 보인다.

    java.util.concurrent가 확장하는 보장

    실무에서 happens-before를 직접 만드는 일은 생각보다 드물다. 표준 라이브러리가 이미 만들어 두었기 때문이다. java.util.concurrent 패키지 문서의 "Memory Consistency Properties" 절은 이 패키지와 하위 패키지의 모든 클래스가 언어의 보장을 더 높은 수준의 동기화로 확장한다고 밝히고, 대표적인 경우를 나열한다.

    앞선 동작 (스레드 A)happens-before뒤의 동작 (스레드 B)
    동시성 컬렉션에 객체를 넣기 전의 동작→다른 스레드에서 그 원소에 접근하거나 꺼낸 뒤의 동작
    Executor에 Runnable을 제출하기 전의 동작→그 작업의 실행 시작 (ExecutorService에 제출한 Callable도 같다)
    Future가 나타내는 비동기 계산의 동작→다른 스레드에서 Future.get()으로 결과를 받은 뒤의 동작
    Lock.unlock, Semaphore.release, CountDownLatch.countDown 같은 "해제" 메서드 전의 동작→같은 동기화 객체에서 Lock.lock, Semaphore.acquire, Condition.await, CountDownLatch.await 같은 "획득"에 성공한 뒤의 동작
    CyclicBarrier.await 호출 전의 동작→배리어 동작, 그리고 그 뒤 await에서 돌아온 다른 스레드들의 동작

    이 표가 뜻하는 바는 크다. 작업을 스레드 풀에 넘길 때, 그 작업 객체의 필드가 volatile이 아니어도 작업 스레드는 제출 전에 설정된 값을 정확히 본다. Future.get()으로 받은 결과 객체의 내부 상태도 마찬가지다. 이 보장은 각 클래스가 내부에서 volatile 변수와 CAS를 써서 만들어 낸 것이고, 그 구현은 07회(Lock), 10회(CAS), 11회(동시성 컬렉션), 12~13회(스레드 풀)에서 차례로 들여다본다.

    형식 정의 한 걸음 더: happens-before 일관성과 인과성 요구

    앞에서는 17.4.5의 "읽기가 볼 수 있는 쓰기" 규칙까지 다뤘다. JLS는 거기서 멈추지 않고, 실행(execution) 자체를 수학적 대상으로 정의한 뒤 어떤 실행이 합법인지 판정하는 조건을 몇 겹 더 쌓는다. 이 절은 그 나머지를 따라가며 happens-before만으로는 왜 부족한지 본다.

    실행은 튜플이고, 핵심은 "어느 쓰기를 보았는가"다

    17.4.6은 실행 E를 튜플 < P, A, po, so, W, V, sw, hb >로 정의한다. P는 프로그램, A는 동작의 집합, po는 프로그램 순서, so는 동기화 순서다. W는 각 읽기 r에 대해 그 읽기가 본 쓰기 W(r)를 돌려주는 함수(write-seen function)이고, V는 각 쓰기가 쓴 값을 돌려주는 함수다. sw와 hb는 synchronizes-with와 happens-before인데, 명세는 이 둘이 나머지 성분과 well-formed 실행의 규칙으로 유일하게 정해진다고 덧붙인다. 그러니 실행 하나를 고른다는 것은 본질적으로 W, 곧 "각 읽기가 어느 쓰기를 보았는가"를 고르는 일이다. 메모리 모델은 W의 후보 가운데 어떤 것이 허용되는지를 정하는 규칙이다.

    17.4.7은 따져 볼 실행을 well-formed 실행으로 제한하고, 그 조건을 나열한다. 각 읽기는 같은 변수에 대한 쓰기를 본다. volatile 변수에 대한 읽기·쓰기는 volatile 동작이다. hb는 synchronizes-with와 프로그램 순서의 이행적 폐포로 주어지는 부분 순서다. 스레드 내 일관성(intra-thread consistency)이 지켜진다. 각 읽기가 본 값을 넣고 그 스레드를 혼자 프로그램 순서대로 실행했을 때 만들어질 동작과 실제 동작이 같다는 뜻이다. happens-before 일관성이 지켜진다. 마지막으로 동기화 순서 일관성이 지켜진다. volatile 읽기 r은 동기화 순서상 자기보다 뒤의 쓰기를 볼 수 없고, W(r)과 r 사이에 동기화 순서상 끼어든 같은 변수의 쓰기가 있어서도 안 된다. 동기화 순서는 전체 순서이므로, volatile 읽기는 동기화 순서에서 자기 바로 앞에 놓인 같은 변수의 쓰기를 본다는 말과 같다.

    happens-before 일관성: 실행 순서상 뒤의 쓰기를 보는 것도 허용된다

    17.4.5는 동작 집합 A가 happens-before 일관적(happens-before consistent)이라는 것을 이렇게 정의한다. A의 모든 읽기 r에 대해 hb(r, W(r))가 아니고, hb(W(r), w)이면서 hb(w, r)인 같은 변수의 쓰기 w도 A에 없다. 앞에서 본 "읽기가 볼 수 있는 쓰기" 조건을 모든 읽기에 한꺼번에 요구하는 것이다. 명세가 드는 예(Table 17.4.5-A)는 Reorder 실험과 같은 모양이다. A == B == 0에서 출발해 스레드 1은 B = 1; r2 = A;를, 스레드 2는 A = 2; r1 = B;를 실행한다. 동기화가 없으므로 각 읽기는 초기값이나 상대 스레드의 쓰기 어느 쪽이든 볼 수 있고, r2 == 0, r1 == 0인 실행은 happens-before 일관적이다. 명세는 한 걸음 더 나가, 두 읽기가 먼저 놓이고 두 쓰기가 나중에 놓인 실행 순서에서 r2 = A가 A = 2를, r1 = B가 B = 1을 보는 실행도 happens-before 일관적이라고 보여 준다. 읽기가 실행 순서상 뒤에 오는 쓰기를 본다는 것은 실제로는 그 쓰기가 일찍 수행되었다는 뜻이라고 명세는 설명한다. 컴파일러와 CPU의 재정렬이 모델 안에서는 이런 모습으로 나타난다.

    happens-before 일관성은 허공에서 값을 만들어 낸다

    문제는 "뒤의 쓰기를 보는" 자유가 지나칠 수 있다는 것이다. 17.4.8의 Example 17.4.8-1이 그 예다.

    처음: x = 0, y = 0

  스레드 1                     스레드 2
  r1 = x;                      r2 = y;
  if (r1 != 0) y = 1;          if (r2 != 0) x = 1;

질문: r1 == r2 == 1 이 나올 수 있는가?

    먼저 이 코드가 올바르게 동기화되었는지 판정해 보자. 동기화 동작이 하나도 없으니 아니라고 답하기 쉽지만, 명세는 이 코드가 올바르게 동기화되었다고 말한다. 정의를 다시 보면 이유가 보인다. 올바른 동기화의 조건은 순차 일관적인 실행들에 데이터 경합이 없다는 것이다. 순차 일관적으로 실행하면 두 읽기는 모두 초기값 0을 보고 두 if는 거짓이 되어 쓰기가 한 번도 일어나지 않는다. 쓰기가 없으니 충돌하는 접근도, 데이터 경합도 없다. 그러므로 이 프로그램에 허용되는 결과는 순차 일관적인 결과, r1 == r2 == 0뿐이어야 한다.

    그런데 다음 실행은 happens-before 일관적이다. r1 = x가 x = 1을 보고, 그래서 y = 1이 실행되고, r2 = y가 그 y = 1을 보고, 그래서 x = 1이 실행된다. 각 읽기와 그것이 본 쓰기 사이에 이를 막는 happens-before 순서가 없으므로 앞의 정의를 모두 통과한다. 결과는 r1 == r2 == 1이다. 읽기가 쓰기를 일으키고 쓰기가 다시 읽기를 일으키는 순환이고, 첫 원인이 없다. 명세는 이런 값을 "허공에서 나온(out of thin air)" 값이라 부르고 받아들일 수 없는 결과로 규정한다. Example 17.4.8-1의 제목이 결론을 그대로 말한다. happens-before 일관성은 필요하지만 충분하지 않다.

    인과성 요구: 동작을 하나씩 확정하며 정당화한다

    이것을 막는 장치가 17.4.8의 인과성 요구(causality requirements)다. 실행 E가 합법임을 보이려면, E의 동작들을 빈 집합 C0에서 출발해 C1, C2, ...로 조금씩 확정(commit)해 나가 결국 전부를 확정할 수 있어야 한다. 각 단계 Ci마다 그 단계를 정당화하는 well-formed 실행 Ei가 있어야 하고, Ei에서 Ci의 동작들은 E에서와 같은 happens-before 순서, 동기화 순서, 쓴 값을 가져야 한다. 핵심 조건은 읽기에 걸린다. 직전 단계까지 확정되지 않은 읽기는 Ei에서 자기보다 happens-before인 쓰기만 볼 수 있다. 이번 단계에 새로 확정되는 읽기는 이미 확정된(Ci-1에 있는) 쓰기만 볼 수 있다. 명세는 이를 비형식적으로, 어떤 데이터 경합이 일어난다고 가정하지 않고도 일어날 수 있음을 아는 동작만 일찍 확정할 수 있다고 풀어 쓴다.

    위 예에 적용해 보자. y = 1을 확정하려면 그 쓰기가 실제로 일어나는 정당화 실행이 필요하다. 그러려면 r1 = x가 1을 봐야 하는데, 아직 확정되지 않은 읽기는 자기보다 happens-before인 쓰기, 곧 초기값 0만 볼 수 있다. 그 실행에서 if는 거짓이고 y = 1은 일어나지 않는다. x = 1도 대칭이다. 두 쓰기 모두 상대 쓰기가 먼저 확정되어야만 확정될 수 있으니 어느 쪽도 확정되지 않고, r1 == r2 == 1인 실행은 합법이 아니다. 명세의 표현으로는, 이 두 쓰기는 읽기가 데이터 경합의 결과를 보지 않는 한 일어날 수 없으므로 일찍 수행할 수 없다.

    이 정의가 실무에 남기는 것

    세 가지로 정리된다. 첫째, 데이터 경합이 있는지는 순차 일관적인 실행만 놓고 판정한다. 17.4.5는 이것이 프로그래머에게 매우 강한 보장이라고 강조한다. 코드에 데이터 경합이 있는지 판단하려고 재정렬을 따질 필요가 없고, 일단 올바르게 동기화되었다고 판정하고 나면 재정렬이 코드에 영향을 줄까 걱정할 필요가 없다는 것이다. 위 예처럼 공유 변수를 건드리는 코드가 있더라도, 순차 일관적인 실행에서 그 코드가 경합을 만들지 않으면 프로그램은 올바르게 동기화된 것이다.

    둘째, 데이터 경합이 있는 프로그램이라고 아무 값이나 볼 수 있는 것은 아니다. JSR-133 FAQ는 새 메모리 모델의 목표로 타입 안전성 같은 기존 보장을 지키는 것을 들고, 그 예로 변수의 값이 허공에서 만들어지지 않는다는 것, 곧 어떤 스레드가 관찰한 값은 어떤 스레드가 그 자리에 놓을 수 있었던 값이어야 한다는 것을 든다. 잘못 동기화된 프로그램의 의미도 보안상 위험이 최소가 되도록 정의한다는 목표가 함께 적혀 있다. FlagLoop의 worker가 본 값도 누군가 실제로 쓴 값(초기값 true)이었다. 경합은 "언제 어느 쓰기를 볼지"를 열어 둘 뿐, 아무도 쓰지 않은 값을 만들어 내지는 않는다.

    셋째, 컴파일러에 대한 제약이다. 위 예의 if (r1 != 0) y = 1;을 "일단 y = 1을 쓰고 r1이 0이면 y = 0으로 되돌린다"는 투기적 쓰기로 바꾸었다고 하자. 단일 스레드에서는 최종 결과가 같다. 하지만 그 잠깐의 1을 스레드 2가 읽으면 x = 1이 실행되고, 그 값을 스레드 1의 r1 = x가 보면 되돌리기가 일어나지 않아 r1 == r2 == 1이 된다. 명세가 금지한 결과를 만들 수 있으므로 이 변환은 이 코드에 적용할 수 없다. 앞에서 본 호이스팅은 "한 스레드 안에서 결과가 같다"는 이유로 허용되었지만, 그 기준만으로 모든 변환이 정당화되지는 않는다는 것을 이 예가 보여 준다.

    흔한 오해 바로잡기

    "volatile은 CPU 캐시를 건너뛰고 메인 메모리를 직접 읽고 쓴다"

    입문 설명으로는 그림이 쉬워서 자주 쓰이지만, 명세는 캐시나 메인 메모리라는 말을 쓰지 않는다. JLS는 어떤 읽기가 어떤 쓰기를 볼 수 있는가만 정한다. 구현 관점에서도 캐시 일관성을 하드웨어가 유지하는 프로세서에서 volatile 접근은 캐시를 거치고, JVM이 하는 일은 컴파일러의 재배치와 레지스터 보관을 막고 필요한 위치에 메모리 배리어를 넣는 것이다. 이 회차의 실험이 보여 주었듯 "보이지 않음"의 원인은 컴파일러(호이스팅)일 수도 있고 하드웨어(저장 버퍼)일 수도 있다. 원인이 무엇이든 volatile이 지키는 것은 같은 규칙, happens-before다.

    "테스트에서 잘 돌았으니 괜찮다"

    데이터 경합이 있는 코드는 "잘 돌 수도 있는" 코드다. FlagLoop는 main이 1밀리초 뒤에 플래그를 바꾸면 정상 종료되기도 하고 멈추기도 했고, 1초 뒤에 바꾸면 멈추지 않았다. 같은 코드가 JIT 컴파일 시점이라는, 프로그래머가 통제하지 않는 요인에 따라 다르게 동작했다. 재정렬 실험의 수치도 인터프리터와 C2에서 크게 달랐다. x86에서 드러나지 않는 재정렬이 다른 아키텍처에서 드러날 수도 있다. 테스트 통과는 데이터 경합이 없다는 증거가 되지 못한다. 증거는 공유 변수의 모든 충돌하는 접근이 happens-before로 묶여 있다는 논증뿐이다.

    "sleep이나 println을 넣으면 해결된다"

    JLS 17.3이 명시적으로 부정한다. Thread.sleep과 Thread.yield에는 동기화 의미가 없다. 이 기계에서 루프에 sleep(1)을 넣었을 때 루프가 끝난 것은 HotSpot이 그 상황에서 호이스팅을 하지 않았기 때문이지, 명세가 그렇게 하라고 해서가 아니다. 출력문도 마찬가지다. 출력 메서드 내부에 어떤 동기화가 있는지는 라이브러리 구현의 세부이고, 그 동기화가 우리 플래그 변수에 대한 happens-before를 만들어 준다는 보장은 어디에도 없다.

    "volatile이면 스레드 안전하다"

    VolatileCounter가 반례다. volatile은 개별 읽기와 쓰기를 순서대로 보이게 할 뿐, 읽고-고치고-쓰는 복합 연산을 원자적으로 만들지 않는다. "스레드 안전"이라는 말은 가시성과 원자성과 순서를 모두 포함하는데, volatile은 그중 앞의 일부만 책임진다.

    "생성자가 끝난 객체는 다른 스레드에게도 다 만들어진 상태로 보인다"

    참조를 데이터 경합으로 넘기면 이 말은 성립하지 않는다. 다음은 지연 초기화를 락 없이 빠르게 하려는 이중 검사 잠금(double-checked locking)이다.

    public class Settings {
    private static Settings instance;      // volatile이 아니면 문제가 된다
    private int timeoutMillis;

    private Settings() {
        timeoutMillis = 3000;
    }

    public static Settings getInstance() {
        if (instance == null) {                    // ① 락 없이 읽는다
            synchronized (Settings.class) {
                if (instance == null) {
                    instance = new Settings();     // ② 생성 후 참조를 쓴다
                }
            }
        }
        return instance;
    }

    public int timeoutMillis() { return timeoutMillis; }
}

    ②에서 생성자의 timeoutMillis = 3000과 참조 쓰기 instance = ...는 같은 스레드 안의 일반 쓰기 둘이다. ①에서 락 없이 instance를 읽는 다른 스레드와 이 쓰기들 사이에는 happens-before가 없다. 그러니 그 스레드는 null이 아닌 참조를 보면서도 timeoutMillis는 기본값 0을 볼 수 있다. JSR-133 FAQ는 새 메모리 모델에서 instance 필드를 volatile로 선언하면 이 문제가 해결된다고 설명한다. 피기백 예제와 같은 원리다. 생성자 안의 쓰기는 volatile 쓰기보다 프로그램 순서상 앞이고, volatile 읽기로 null이 아닌 참조를 본 스레드에게는 그 앞의 쓰기가 모두 보인다. 같은 FAQ는 대안으로 클래스 초기화를 이용하는 지연 초기화 홀더(Initialization On Demand Holder) 관용구를 권한다. 락 자체(synchronized)의 의미는 다음 회차에서 다룬다.

    final 필드에는 별도의 보장이 있다. JLS 17.5는 생성자가 끝나면 객체가 완전히 초기화된 것으로 보고, 완전히 초기화된 뒤에야 그 객체의 참조를 볼 수 있는 스레드는 그 객체의 final 필드가 올바르게 초기화된 값을 보도록 보장한다고 정한다. 위 예에서 timeoutMillis가 final이었다면, 참조가 경합으로 전달되더라도 그 필드만큼은 3000이 보인다. 다만 생성자 안에서 this를 다른 스레드에 넘기면 "완전히 초기화된 뒤에야 참조를 본다"는 조건이 깨진다. 불변 객체가 동시성에서 안전하다고 말하는 근거가 이 절이다.

    volatile보다 세밀한 단계: VarHandle의 접근 모드

    참고로 자바 9부터는 java.lang.invoke.VarHandle로 변수 접근의 메모리 순서를 더 잘게 고를 수 있다. Javadoc은 접근 모드를 네 단계로 설명한다. Plain 모드는 다른 스레드에 대해 아무 순서 제약을 두지 않는다(일반 필드 접근과 같다). Opaque 모드는 같은 변수에 대한 접근끼리 일관된 순서를 갖는다. Acquire/Release 모드는 Acquire 읽기와 그 뒤의 접근이, 짝이 되는 Release 쓰기와 그 앞의 접근보다 뒤에 오도록 순서를 정한다. Volatile 모드는 여기에 더해 모든 volatile 연산이 서로 전체 순서를 갖는다. 피기백 예제가 필요로 한 것은 사실 Release 쓰기와 Acquire 읽기만으로 충분하고, (0, 0) 실험을 막으려면 전체 순서를 주는 Volatile 모드가 필요하다. 애플리케이션 코드에서 이 단계를 직접 고를 일은 드물지만, java.util.concurrent의 내부 구현은 이 모드들과 compareAndSet 같은 원자적 갱신 연산으로 만들어져 있다. 10회에서 CAS를 다룰 때 다시 만난다.

    다른 주제와의 연결

    스프링 애플리케이션에서 이 회차의 내용이 가장 자주 문제가 되는 곳은 싱글톤 빈의 필드다. 스프링 핵심 원리 편에서 보았듯 기본 스코프의 빈은 컨테이너에 하나만 있고, 서블릿 컨테이너의 여러 요청 스레드가 같은 인스턴스를 동시에 쓴다. 빈에 상태를 담는 가변 필드를 두면 그 필드는 곧 공유 변수가 된다. 상태 없는(stateless) 빈을 권하는 이유를 그때는 "값이 섞인다"는 원자성 관점에서 봤다면, 이제는 "바꾼 값이 보이지 않거나 반쯤 만들어진 객체가 보일 수 있다"는 가시성 관점도 함께 볼 수 있다.

    컨테이너가 빈을 만들고 요청 스레드가 그 빈을 쓰는 과정이 안전한 것도 우연이 아니다. 컨테이너가 시작되며 만든 객체가 나중에 다른 스레드에서 쓰이려면 그 사이 어딘가에 happens-before가 있어야 한다. 스레드 시작(start), 락, 동시성 컬렉션, 스레드 풀 제출처럼 이 회차의 표에 나온 장치들이 그 다리 역할을 한다. 어떤 프레임워크가 어떤 장치를 쓰는지는 구현마다 다르지만, 원리는 같다.

    이 권의 남은 회차는 모두 이 회차의 규칙 위에 서 있다. 06회의 synchronized는 unlock-lock synchronizes-with 규칙으로 가시성을, 상호 배제로 원자성을 함께 제공한다. 07회의 ReentrantLock과 08~09회의 생산자-소비자 구현은 java.util.concurrent의 해제-획득 보장을 쓴다. 10회의 CAS는 volatile의 가시성에 하드웨어의 원자적 비교-교환을 더해 락 없이 원자성을 얻는다. 무엇을 배우든 "이 값은 어떤 happens-before 간선을 타고 저 스레드에 도착하는가"라는 질문 하나로 정리할 수 있다.
    메모리 가시성
    한 스레드가 쓴 값을 다른 스레드가 언제, 어떤 순서로 보느냐의 문제다. 동기화 없이 읽으면 명세는 그 값을 볼 시점은 물론 볼 수 있는지조차 보장하지 않는다.
    호이스팅(루프 불변 코드 이동)
    루프 안에서 쓰이지 않는 non-volatile 필드의 읽기를 루프 밖으로 옮기는 컴파일러 최적화다. JLS 17.3이 허용하며, 이 기계에서는 C2가 개입했을 때만 플래그 루프가 끝나지 않았다.
    저장 버퍼와 재정렬
    코어의 쓰기가 캐시에 반영되기 전 저장 버퍼에 머무는 동안 뒤의 읽기가 먼저 효과를 낸다. 그래서 순차 일관성에서는 불가능한 (0, 0)이 인터프리터에서도 관찰된다.
    volatile
    읽기·쓰기를 생략하거나 합치거나 재배치하지 못하게 하고, volatile 쓰기가 그 뒤의 읽기와 synchronizes-with 관계를 맺게 한다. 바이트코드는 같고 필드에 ACC_VOLATILE 플래그만 붙는다.
    원자성은 별개
    count++는 읽기·더하기·쓰기 세 단계라서 volatile이어도 증가가 사라진다. 원자성은 락이나 CAS로 얻는다. 다만 volatile long·double의 단일 읽기·쓰기는 원자적이다(JLS 17.7).
    happens-before
    프로그램 순서, synchronizes-with, 이행성으로 만들어지는 관계다. hb(w, r)이면 r은 w나 그 뒤의 쓰기를 봐야 하고, 관계가 없으면 무엇을 볼지 정해지지 않는다.
    데이터 경합과 DRF 보장
    happens-before로 묶이지 않은 충돌하는 두 접근이 데이터 경합이다. 데이터 경합이 없는 프로그램의 모든 실행은 순차 일관적인 것처럼 보인다.
    피기백
    volatile 쓰기 앞의 일반 쓰기들은 그 volatile 값을 읽은 스레드에게 함께 보인다. 쓰기 순서와 같은 변수를 쓰는지가 조건이다.
    기계어로 본 volatile (OpenJDK 21, AArch64)
    C2는 non-volatile 플래그를 루프 밖에서 ldrb로 한 번만 읽고 세이프포인트 폴만 남긴 무한 루프를 만들었고, volatile 플래그는 매 반복 ldarb로 읽었다. C2는 volatile 접근을 ldar/stlr로, 인터프리터는 일반 명령과 dmb로 구현한다.
    인과성 요구
    happens-before 일관성만으로는 읽기와 쓰기가 서로를 정당화하는 "허공에서 나온 값"을 막지 못한다. JLS 17.4.8은 동작을 하나씩 확정하며 정당화하도록 요구해 이를 금지한다.

    운영 중인 서버에서 "배포 후 몇 시간이 지나면 백그라운드 작업이 종료 신호를 무시한다"는 증상은 이 회차의 FlagLoop와 같은 구조일 가능성이 높다. 시작 직후에는 인터프리터나 C1 코드가 돌아 신호를 보지만, 루프가 충분히 뜨거워져 C2로 컴파일된 뒤에는 읽기가 끌어올려질 수 있다. 이런 증상을 만나면 먼저 루프 조건에 쓰이는 필드가 volatile이거나 락·Atomic 클래스로 보호되는지 확인한다. 인터럽트로 멈추게 하는 방식(04회)을 함께 쓰면, 인터럽트 자체도 synchronizes-with 규칙이 있는 통로이므로 블로킹 호출 중인 스레드까지 깨울 수 있다.

    volatile을 쓸지 다른 수단을 쓸지는 쓰기의 성격으로 판단한다. 한 스레드만 쓰고 여럿이 읽는 값, 현재 값과 무관하게 덮어쓰는 값, 완성된 불변 객체를 가리키는 참조는 volatile로 충분하다. 현재 값을 읽고 새 값을 계산하는 갱신(카운터, 상태 전이, "없으면 만든다")은 volatile로 부족하므로 Atomic 클래스나 락이 필요하다. 여러 필드가 함께 바뀌어야 하는 불변식이 있다면 필드 각각을 volatile로 만들어도 소용없고, 그 묶음을 락으로 보호하거나 불변 객체 하나로 묶어 참조를 통째로 교체하는 설계가 필요하다.

    성능을 이유로 동기화를 빼자는 제안이 나오면, 이 회차의 비용 측정이 보여 준 것을 기억한다. volatile 접근이 일반 접근보다 비싼 것은, 일반 접근이 컴파일러에게 "없애거나 합쳐도 되는" 자유를 주기 때문이다. 그 자유가 바로 다른 스레드에서 값이 안 보이는 원인이다. 공유 변수에서 그 자유를 사는 대가는 정확성이다. 실제 병목이 측정으로 확인되었다면 동기화를 빼는 대신 공유 자체를 줄이는 방향(스레드별 지역 상태, 불변 객체, 동시성 컬렉션)을 먼저 검토한다.

    코드 리뷰에서는 재정렬 시나리오를 상상하는 대신 질문 하나를 던지면 된다. "이 필드를 쓰는 스레드와 읽는 스레드 사이의 happens-before 간선은 무엇인가?" 답이 volatile, 락, start/join, 동시성 컬렉션, 스레드 풀 제출, Future.get 가운데 하나로 나오면 안전하고, 답이 "보통은 금방 보인다"이면 데이터 경합이다.
  • FlagLoop에서 main의 Thread.sleep(1000)을 Thread.sleep(1)로 바꾸면 이 기계에서는 worker가 정상 종료되는 실행이 있었다. 그런 실행을 보고 "1밀리초 안에 플래그를 바꾸면 안전하다"고 결론 내릴 수 없는 이유를, JIT 컴파일 시점과 JLS 17.3의 규정을 들어 설명하라.
  • 피기백 예제에서 main의 두 줄 순서를 바꿔 ready = true;를 먼저, data = 42;를 나중에 실행하게 했다. reader가 출력할 수 있는 값을 모두 들고, happens-before 사슬의 어느 고리가 끊겼는지 지적하라.
  • 다음 코드에서 main이 마지막에 출력하는 result는 항상 10인가? result는 volatile이 아닌 static int 필드다. happens-before 간선을 모두 그려서 답하라. Thread t = new Thread(() -> result = 10); t.start(); t.join(); System.out.println(result);
  • 두 스레드가 static volatile long total에 각자 100만 번씩 total += 2를 실행한다. 최종 값이 항상 400만이 되지 않는 이유를 바이트코드 단계로 설명하고, volatile long이라서 보장되는 것과 보장되지 않는 것을 구분하라.
  • 재정렬 실험(Reorder)에서 x만 volatile로 하고 y는 일반 필드로 두었다. (0, 0)이 명세상 여전히 가능한지 판정하라.

    1. 1밀리초 버전이 종료된 실행은 플래그가 바뀐 시점에 worker가 아직 인터프리터나 C1 코드에서 돌고 있던 경우다. 이 기계에서도 스무 번 중 열여덟 번은 멈추지 않았다. PrintCompilation 기록에서 C2 OSR 컴파일은 JVM 시작 후 수십 밀리초 무렵에 일어났지만, 그 시점은 기계 부하, JVM 버전, 옵션에 따라 달라진다. 더 근본적으로, main의 쓰기와 worker의 읽기 사이에 happens-before가 없으므로 이것은 데이터 경합이고, JLS 17.3이 보여 주듯 컴파일러는 필드를 한 번만 읽어도 된다. 명세상 처음부터 끝까지 옛 값을 보는 실행도 허용된다. 타이밍은 보장을 만들지 못한다.

    2. 0 또는 42를 출력할 수 있다. 사슬의 첫 고리가 끊겼다. 이제 data = 42는 프로그램 순서상 ready = true보다 뒤에 있으므로, volatile 쓰기 앞의 동작이 아니다. reader가 ready에서 true를 봐서 hb(ready = true, reader의 읽기)가 생겨도, data = 42와 reader의 data 읽기 사이에는 happens-before가 없다. 그래서 reader는 기본값 0을 볼 수도 있고 42를 볼 수도 있다. 이 기계에서 42가 나왔다고 해도 보장은 아니다.

    3. 항상 10이다. 간선은 다음과 같다. main의 t.start()는 t의 첫 동작과 synchronizes-with 관계다. t 안에서 프로그램 순서로 첫 동작 다음에 result = 10이 오고, 그 뒤에 t의 마지막 동작이 온다. t의 마지막 동작은 main에서 t의 종료를 감지하는 t.join()과 synchronizes-with 관계다. main 안에서 join 뒤에 result 읽기가 온다. 이행성으로 hb(result = 10, main의 읽기)이고, 기본값 0을 쓴 동작과 이 읽기 사이에 result = 10이 끼어 있으므로 읽기는 0을 볼 수 없다. result가 volatile이 아니어도 start와 join이 다리를 놓는다.

    4. total += 2는 getstatic(읽기), ldc2_w 2(상수 적재), ladd(덧셈), putstatic(쓰기)로 나뉜다. 두 스레드가 같은 값을 읽은 뒤 각자 2를 더해 쓰면 한쪽의 증가가 덮여 사라진다. volatile long이라서 보장되는 것은 JLS 17.7에 따라 읽기 한 번과 쓰기 한 번이 각각 64비트 전체로 원자적이라는 것(앞 32비트와 뒤 32비트가 서로 다른 쓰기에서 섞이지 않는다)과, 각 읽기가 순서상 최신 쓰기를 본다는 것이다. 읽기와 쓰기 사이에 다른 스레드가 끼어들지 못하게 하는 것은 보장되지 않는다. 고치려면 AtomicLong.addAndGet(2)나 락을 쓴다.

    5. 여전히 가능하다. 증명에 쓴 논리는 네 동작이 모두 동기화 동작이어서 하나의 동기화 순서에 놓인다는 데서 출발했다. y가 일반 필드이면 A2(r1 = y)와 B1(y = 1)은 동기화 동작이 아니고, B1과 A2 사이에 happens-before가 생기지 않는다. 그러면 A2가 y의 기본값 0을 보는 것이 허용된다. 동시에 B2(r2 = x)도, A1(x = 1, volatile 쓰기)보다 B2가 동기화 순서상 앞에 오는 실행이라면 0을 볼 수 있다. volatile 읽기는 그 뒤의 접근이 앞으로 올라오는 것만 막고, 그 앞의 일반 쓰기 B1이 뒤로 밀리는 것은 막지 않는다는 점도 같은 결론을 가리킨다. 실제로 (0, 0)을 막으려면 네 접근 모두가 전체 순서에 참여해야 하므로 두 변수 모두 volatile이어야 한다.

C2는 volatile이 아닌 필드를 메인 메모리에 아예 쓰지 않기 때문에 main의 쓰기가 사라진다. main의 쓰기와 worker의 읽기 사이에 happens-before가 없으므로 컴파일러가 읽기를 루프 밖으로 옮기는 것이 허용되고, C2가 그 허용 범위 안에서 최적화했기 때문이다. 바이트코드에 읽기 명령이 루프 밖에 있기 때문이다. JLS 17.3은 non-volatile 필드를 한 번만 읽고 재사용하는 변환을 허용하며, 동기화가 없는 접근은 데이터 경합이라 어떤 값을 볼지 정해지지 않는다. 보기 0은 틀렸다. 인터프리터도 같은 CPU에서 캐시를 거쳐 실행된다. 보기 1은 쓰는 쪽(main)이 아니라 읽는 쪽(worker)의 문제다. 보기 3도 틀렸다. javap로 보면 getstatic은 루프 안(2번, goto 2로 돌아오는 위치)에 있다. static volatile int count를 두 스레드가 각자 100만 번 count++했더니 200만보다 작은 값이 나왔다. 이유로 옳은 것은? volatile 쓰기가 가끔 다른 스레드에게 보이지 않기 때문이다. count++는 읽기·더하기·쓰기로 나뉘고, volatile은 그 사이에 다른 스레드가 끼어드는 것을 막지 않기 때문이다. int는 32비트라서 volatile이어도 쓰기가 반으로 쪼개지기 때문이다. JIT 컴파일러가 volatile 필드의 증가를 루프 밖으로 끌어올려 한 번만 실행하기 때문이다. volatile은 각 읽기와 쓰기의 가시성·순서를 보장하지만 세 단계로 된 복합 연산을 원자적으로 만들지 않는다. 두 스레드가 같은 값을 읽고 각자 1을 더해 쓰면 증가 하나가 사라진다. 보기 0은 반대다. 사라진 것은 가시성이 아니라 원자성이다. 보기 2의 찢어진 쓰기는 non-volatile long·double에 관한 JLS 17.7의 이야기이고 int와는 관계없다. 보기 3은 volatile에 대해서는 금지된 변환이다. 스레드 A가 data = 42; ready = true;를 실행하고(ready만 volatile), 스레드 B가 if (ready) System.out.println(data);를 실행한다. B가 무언가를 출력했다면 그 값에 대해 옳은 것은? 0 또는 42가 나올 수 있다. data가 volatile이 아니기 때문이다. 42가 나오지만, x86에서만 보장되고 ARM에서는 보장되지 않는다. 42가 나오는 것은 ready와 data가 같은 캐시 라인에 있을 때뿐이다. 항상 42다. 프로그램 순서, volatile synchronizes-with, 프로그램 순서가 이행성으로 이어져 data = 42가 B의 읽기보다 happens-before이기 때문이다. B가 출력했다는 것은 volatile 읽기가 true를 봤다는 뜻이고, 그 쓰기와 읽기는 synchronizes-with 관계다. A 안에서 data = 42는 그 쓰기보다 앞이고, B 안에서 data 읽기는 그 읽기보다 뒤이므로 이행성으로 hb가 성립한다. 보기 0은 이 이행성을 놓친 답이다. 메모리 모델의 보장은 하드웨어나 캐시 배치와 무관하게 모든 플랫폼에서 같으므로 보기 1과 2도 틀렸다. 두 스레드가 각각 x = 1; r1 = y;와 y = 1; r2 = x;를 실행한다(처음에 x = y = 0). 옳은 설명은? x, y가 모두 volatile이면 (r1, r2) = (0, 0)은 불가능하다. 네 접근이 하나의 동기화 순서에 놓이고, 먼저 일어난 쓰기는 상대 스레드의 읽기보다 happens-before가 되기 때문이다. volatile이 아니어도 (0, 0)은 불가능하다. 각 스레드에서 쓰기가 읽기보다 먼저 있기 때문이다. (0, 0)은 JIT 컴파일러가 순서를 바꿀 때만 나오므로 -Xint로 실행하면 나오지 않는다. (0, 0)은 x86에서는 나올 수 없다. x86은 메모리 순서를 바꾸지 않기 때문이다. 보기 0은 본문의 증명이다. 보기 1은 순차 일관성을 가정한 추론이고, 데이터 경합이 있는 프로그램에는 그 가정이 성립하지 않는다. 보기 2는 이 회차의 실험이 반박한다. 인터프리터에서도 하드웨어(저장 버퍼)의 재정렬 때문에 (0, 0)이 많이 나왔다. 보기 3도 틀렸다. Intel SDM은 적재가 다른 위치에 대한 앞선 저장과 재정렬될 수 있다고 규정한다. JLS가 Thread.sleep에 대해 정한 것과 일치하는 것은? Thread.sleep 호출은 그 전의 모든 쓰기를 메모리로 내보내므로, sleep 뒤에 플래그를 읽으면 최신 값을 본다. Thread.sleep은 모니터를 잠시 놓기 때문에 unlock-lock 규칙의 happens-before를 만든다. Thread.sleep과 Thread.yield에는 동기화 의미가 없다. 컴파일러는 그 호출 전후로 레지스터의 값을 내보내거나 다시 읽을 의무가 없다. Thread.sleep은 인터럽트 상태를 확인하므로 모든 스레드의 쓰기를 보게 된다. JLS 17.3이 명시한 내용이 보기 2다. 같은 절은 non-volatile 필드를 검사하며 sleep하는 루프가 영원히 끝나지 않을 수 있다는 예를 든다. 보기 0과 1은 명세에 없는 보장이다. sleep은 락을 놓지도 않는다(그것은 wait의 동작이다). 보기 3의 인터럽트 규칙은 인터럽트한 스레드와 인터럽트를 확인한 지점 사이의 관계일 뿐, 임의의 쓰기를 보게 해 주지 않는다.
    메모리 가시성(memory visibility)
    한 스레드가 공유 변수에 쓴 값이 다른 스레드의 읽기에 보이는지, 언제 어떤 순서로 보이는지에 관한 성질이다.
    캐시 일관성(cache coherence)
    여러 코어의 캐시에 있는 같은 주소의 사본이 서로 어긋나지 않도록 하드웨어가 유지하는 성질이다. 이것이 있어도 저장 버퍼와 비순차 실행 때문에 재정렬은 일어난다.
    저장 버퍼(store buffer)
    코어가 쓰기를 캐시에 반영하기 전 잠시 보관하는 버퍼다. 그 코어 자신은 값을 읽을 수 있지만 다른 코어에는 아직 보이지 않아 저장-적재 재정렬의 원인이 된다.
    루프 불변 코드 이동(loop-invariant code motion)
    루프 안에서 값이 변하지 않는 계산이나 읽기를 루프 밖으로 옮기는 컴파일러 최적화다. 호이스팅이라고도 한다.
    OSR(on-stack replacement)
    이미 실행 중인 메서드의 루프를 멈추지 않고 그 자리에서 컴파일된 코드로 갈아타게 하는 JIT 기법이다. PrintCompilation 출력에서 %로 표시된다.
    메모리 배리어(memory barrier, fence)
    앞뒤 메모리 접근의 순서를 강제하는 명령이다. JVM은 volatile 같은 규칙을 지키기 위해 플랫폼에 맞는 배리어를 넣는다.
    happens-before
    JLS 17.4.5가 정의하는 동작 사이의 부분 순서다. hb(x, y)이면 x의 결과가 y에 보이고 x가 y보다 앞선다.
    synchronizes-with
    동기화 순서 위에서 특정 동작 쌍(volatile 쓰기와 그 뒤의 읽기, unlock과 그 뒤의 lock, start와 첫 동작 등)이 맺는 관계로, happens-before 간선을 만든다.
    데이터 경합(data race)
    같은 변수에 대한, 적어도 하나가 쓰기인 두 접근이 happens-before로 순서 지어지지 않은 상태다.
    순차 일관성(sequential consistency)
    모든 스레드의 동작이 각 스레드의 프로그램 순서를 지키는 하나의 전체 순서로 실행되고, 각 읽기가 그 순서에서 가장 최근의 쓰기를 보는 실행 모델이다.
    load-acquire / store-release (ldar / stlr)
    AArch64의 순서 보장 읽기·쓰기 명령이다. OpenJDK 21의 C2는 AArch64에서 volatile 읽기를 ldar 계열로, volatile 쓰기를 stlr 계열로 내고 별도의 dmb를 생략한다.
    허공에서 나온 값(out-of-thin-air value)
    읽기와 쓰기가 순환적으로 서로를 정당화해야만 나타나는 값이다. happens-before 일관성은 이를 허용하지만 JLS 17.4.8의 인과성 요구가 금지한다.
