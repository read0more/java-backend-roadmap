    한 줄짜리 코드는 한 번에 실행되는가

    지금까지 이 권은 여러 스레드가 같은 데이터를 건드릴 때 생기는 문제를 락으로 풀어 왔다. 6회차의 synchronized는 객체의 모니터를 잡은 스레드 하나만 임계 영역에 들여보냈고, 7회차의 ReentrantLock은 같은 일을 API로 하면서 대기를 인터럽트하거나 시간 제한을 둘 수 있게 했다. 8~9회차의 생산자 소비자 문제에서는 락 위에 대기와 신호(wait/notify, Condition)를 얹었다. 이 방법들은 모두 같은 전략을 쓴다. 한 스레드가 작업하는 동안 나머지 스레드를 세워 둔다.

    세워 두는 데에는 비용이 든다. 락을 얻지 못한 스레드는 BLOCKED나 WAITING 상태로 바뀌고, 운영체제는 그 스레드를 CPU에서 내리고 다른 스레드를 올리는 컨텍스트 스위칭을 한다(1회차). 보호해야 할 일이 "정수 하나를 1 늘린다"처럼 아주 작을 때, 그 일을 하는 시간보다 줄을 세우고 깨우는 시간이 더 길어질 수 있다. 그래서 이 회차는 질문을 바꾼다. 다른 스레드를 세워 두지 않고도 공유 변수 하나를 안전하게 바꾸는 방법이 있는가. 그 답이 원자적 연산과, 그것을 하드웨어 명령 하나로 제공하는 CAS다.

    원자적 연산(atomic operation)은 더 이상 나눌 수 없는 연산이다. 정확히 말하면, 다른 스레드가 관찰할 때 그 연산이 시작되기 전의 상태이거나 완전히 끝난 뒤의 상태 둘 중 하나만 보이고, 중간 상태는 결코 보이지 않는 연산이다. 중요한 것은 "코드가 한 줄인가"가 아니라 "그 사이에 다른 스레드가 끼어들 틈이 있는가"다. 소스 코드에서 한 줄로 보이는 문장도 실제로는 여러 단계로 실행될 수 있고, 그 단계 사이가 바로 틈이다.

    자바 언어 명세는 어떤 읽기와 쓰기가 원자적인지를 정해 둔다. JLS 17.7은 volatile이 아닌 long이나 double에 대한 쓰기 한 번을 메모리 모델의 관점에서 32비트씩 나뉜 두 번의 쓰기로 취급한다고 하고, 그 결과 한 스레드가 서로 다른 두 쓰기에서 온 앞쪽 32비트와 뒤쪽 32비트를 섞어 볼 수 있다고 명시한다. 같은 절은 volatile long/double의 읽기와 쓰기, 그리고 참조의 읽기와 쓰기는 언제나 원자적이라고 정한다. 쪼개질 수 있다고 따로 지목된 것은 64비트 값뿐이므로, int나 boolean 필드에 값을 한 번 쓰는 것은 하나의 쓰기 동작이다. 실제로 64비트 JVM 구현이 long을 쪼개 쓰는지는 구현의 자유이고, 명세는 공유하는 64비트 값을 volatile로 선언하거나 올바르게 동기화하라고 권한다.

    표의 아래 두 줄이 이 회차의 주인공이다. 둘 다 "값을 읽고, 그 값을 근거로 무언가를 정하고, 다시 쓴다"는 같은 모양을 하고 있다. 이것을 읽기-수정-쓰기(read-modify-write)라고 부르고, 검사 후 행동(check-then-act)은 그 한 변형이다. 각각의 읽기와 쓰기는 원자적이어도 세 단계를 합친 전체는 원자적이지 않다. 원자성과 가시성도 다른 문제라는 점을 기억해 두자. 5회차에서 본 가시성은 "한 스레드가 쓴 값을 다른 스레드가 언제 보는가"의 문제였고, 원자성은 "여러 단계로 된 연산 중간에 다른 스레드가 끼어들 수 있는가"의 문제다.

    value++를 바이트코드로 쪼개 보기

    먼저 증가 연산이 실제로 몇 단계인지 눈으로 확인하자. 이 회차의 실험에서는 정수 하나를 늘리는 카운터를 여러 방식으로 구현해 비교할 것이므로, 공통 인터페이스부터 둔다. 아무 보호도 하지 않는 가장 단순한 구현이 PlainCounter다.

    public interface Counter {
    void increment();
    int get();
}
    public class PlainCounter implements Counter {
    private int value;
    @Override public void increment() { value++; }
    @Override public int get() { return value; }
}

    한 줄씩 읽어 보자. aload_0은 지역 변수 0번 칸에 있는 this 참조를 피연산자 스택에 올린다. dup은 그 참조를 하나 더 복사한다. 하나는 값을 읽는 getfield가, 다른 하나는 값을 쓰는 putfield가 소비하기 때문이다. getfield는 힙에 있는 객체의 value 필드를 읽어 피연산자 스택에 올린다. iconst_1이 상수 1을 올리고, iadd가 스택의 두 값을 꺼내 더한 결과를 다시 올린다. 마지막으로 putfield가 그 결과를 힙의 value 필드에 쓴다.

    핵심은 getfield와 putfield 사이다. 그 사이에 값은 힙이 아니라 그 스레드의 JVM 스택 프레임 안, 피연산자 스택에만 있다. 피연산자 스택은 스레드마다 따로 있으므로 다른 스레드는 이 값을 볼 수도 없고, 이 스레드가 지금 무엇을 계산 중인지도 모른다. 그리고 putfield는 쓰기 직전에 "힙의 값이 내가 읽었을 때 그대로인가"를 확인하지 않는다. 그냥 덮어쓴다. 참고로 지역 변수 int i에 대한 i++는 iinc라는 명령 하나(예: 1번 칸의 변수라면 iinc 1, 1)로 컴파일되지만, 지역 변수는 그 스레드의 프레임에만 있으므로 애초에 공유되지 않는다. 문제가 되는 것은 힙에 있는 필드, 즉 여러 스레드가 함께 보는 변수다.

    실험: 네 스레드가 40만 번 더하면

    추적표가 실제로도 일어나는지 확인하자. 아래 프로그램은 네 개의 스레드가 같은 카운터를 각각 10만 번씩 증가시킨다. 순서가 어떻게 섞이든 증가는 모두 40만 번 일어나므로, 카운터가 올바르다면 결과는 반드시 400000이어야 한다. 비교를 위해 앞으로 설명할 네 가지 구현(아무 보호 없음, volatile, synchronized, AtomicInteger)을 한꺼번에 돌린다. 나머지 세 구현의 코드는 각 절에서 보인다.

    import java.util.ArrayList;
import java.util.List;

public class CounterMain {
    static final int THREADS = 4;
    static final int PER_THREAD = 100_000;

    public static void main(String[] args) throws InterruptedException {
        run(new PlainCounter());
        run(new VolatileCounter());
        run(new SyncCounter());
        run(new AtomicCounter());
    }

    static void run(Counter counter) throws InterruptedException {
        List threads = new ArrayList<>();
        for (int i = 0; i < THREADS; i++) {
            Thread t = new Thread(() -> {
                for (int j = 0; j < PER_THREAD; j++) {
                    counter.increment();
                }
            });
            threads.add(t);
            t.start();
        }
        for (Thread t : threads) {
            t.join();
        }
        System.out.printf("%-16s 기대값=%d, 실제값=%d%n",
                counter.getClass().getSimpleName(), THREADS * PER_THREAD, counter.get());
    }
}

    같은 프로그램을 세 번 돌렸을 때 PlainCounter는 109664, 169067, 113814를, VolatileCounter는 146968, 121838, 125218을 냈다. 구체적인 숫자는 실행마다 다르고 기계마다 다르다. 일정한 것은 두 가지다. 보호하지 않은 두 카운터는 매번 400000보다 작고, SyncCounter와 AtomicCounter는 매번 정확히 400000이다. 결과가 400000보다 크게 나오는 일은 없다는 점도 눈여겨보자. 갱신 손실은 증가를 "잃어버리는" 방향으로만 일어난다. 덮어쓰기는 다른 스레드의 증가를 지울 수는 있어도 없던 증가를 만들어 내지는 않기 때문이다.

    main이 각 스레드에 join()을 호출한 뒤에 counter.get()을 읽는다는 점도 짚어 두자. JLS 17.4.5는 한 스레드의 모든 동작이, 다른 스레드가 그 스레드에 대한 join()에서 성공적으로 돌아오는 것보다 먼저 일어난다(happens-before)고 정한다. 그래서 마지막 출력에서 main이 보는 값은 네 스레드가 남긴 최종 상태이고, 400000보다 작은 숫자는 "아직 덜 보여서"가 아니라 정말로 증가가 사라졌기 때문이다. 이제 표의 각 줄이 왜 그렇게 나왔는지 하나씩 보자.

    volatile을 붙이면: 가시성과 원자성은 다른 문제다

    5회차에서 volatile을 배운 사람이 가장 먼저 떠올리는 해법은 필드에 volatile을 붙이는 것이다. 한 스레드가 쓴 값을 다른 스레드가 바로 보게 되니, 낡은 값을 읽어서 생기는 문제가 사라질 것 같다.

    public class VolatileCounter implements Counter {
    private volatile int value;
    @Override public void increment() { value++; }
    @Override public int get() { return value; }
}

    그러나 실험 결과는 PlainCounter와 마찬가지로 400000에 한참 못 미쳤다. 이유는 바이트코드에서 바로 보인다. VolatileCounter의 increment를 javap -c로 보면 aload_0, dup, getfield, iconst_1, iadd, putfield로 PlainCounter와 한 글자도 다르지 않다. 달라진 것은 javap -v로 볼 수 있는 필드 정보뿐이다.

      private volatile int value;
    descriptor: I
    flags: (0x0042) ACC_PRIVATE, ACC_VOLATILE

    ACC_VOLATILE 플래그는 JVM에게 "이 필드에 대한 읽기와 쓰기 하나하나를 volatile 규칙에 따라 다루라"고 알린다. JLS 17.4.5에 따르면 volatile 필드에 대한 쓰기는 그 필드에 대한 이후의 모든 읽기보다 먼저 일어난다(happens-before). 그래서 각 getfield는 그 시점까지 마지막으로 쓰인 값을 보고, 컴파일러와 CPU는 이 읽기와 쓰기를 레지스터에 묶어 두거나 앞뒤로 옮기지 못한다. 하지만 이 규칙이 말하는 것은 "개별 읽기와 쓰기의 순서와 가시성"이다. getfield와 putfield 사이에 다른 스레드가 끼어들지 못하게 한다는 말은 어디에도 없다.

    앞의 추적표를 volatile 필드에 대해 다시 읽어 보면 이 점이 분명해진다. 시점 2에서 B가 0을 읽는 것은 volatile 규칙을 전혀 어기지 않는다. 그 시점까지 마지막으로 쓰인 값은 정말로 0이었기 때문이다. 시점 5에서 A가 쓴 1을 시점 6의 B가 덮어쓰는 것도 규칙 위반이 아니다. 각 읽기는 최신 값을 봤고, 각 쓰기는 즉시 보였다. 그런데도 증가 하나가 사라졌다. volatile은 각각의 동작을 원자적이고 보이게 만들 뿐, 여러 동작을 묶어 하나로 만들지는 않는다. 바로 이것이 가시성과 원자성이 다른 문제라는 말의 구체적인 의미다.

    volatile은 "한 스레드만 쓰고 여러 스레드가 읽는" 변수에는 충분하다. 쓰는 스레드가 하나뿐이면 읽기-수정-쓰기가 엇갈릴 상대가 없기 때문이다. 5회차의 종료 플래그가 그런 예다. 여러 스레드가 같은 변수를 읽고 고쳐 쓰는 순간 volatile만으로는 부족해진다.

    원자성이 필요하면 세 단계를 하나로 묶어야 한다. 6회차의 도구가 바로 그 일을 한다.

    public class SyncCounter implements Counter {
    private int value;
    @Override public synchronized void increment() { value++; }
    @Override public synchronized int get() { return value; }
}

    이 클래스의 increment 바이트코드 역시 앞의 두 클래스와 똑같고, 메서드에 ACC_SYNCHRONIZED 플래그가 붙은 것만 다르다. JVM은 이 메서드에 들어가기 전에 this의 모니터를 잡고 나올 때 놓는다. 따라서 어떤 스레드가 getfield부터 putfield까지 실행하는 동안 다른 스레드는 이 객체의 모니터를 얻지 못해 BLOCKED 상태로 기다리고, 추적표의 시점 2 같은 끼어들기가 원천적으로 불가능해진다. 가시성도 함께 해결된다. JLS 17.4.5는 모니터의 해제(unlock)가 같은 모니터에 대한 이후의 모든 획득(lock)보다 먼저 일어난다고 정하므로, 다음에 모니터를 얻은 스레드는 앞 스레드가 쓴 value를 반드시 본다. 그래서 실험 결과가 매번 400000이었다.

    정확성은 얻었지만 대가가 있다. 경합이 생기면 HotSpot은 객체에 ObjectMonitor를 붙이고(6회차의 팽창), 락을 못 얻은 스레드를 대기열에 넣어 재운다. 정수 하나를 늘리는 데 필요한 것은 덧셈 한 번인데, 그 앞뒤로 줄 서기와 깨우기가 붙는다. 그래서 다음 질문이 나온다. 다른 스레드를 재우지 않고, 읽기-수정-쓰기를 하나로 묶을 수는 없을까.

    AtomicInteger: 원자적 연산을 제공하는 클래스

    자바 5에서 추가된 java.util.concurrent.atomic 패키지가 그 답을 제공한다. 패키지 문서는 이 패키지를 단일 변수에 대한 락 없는(lock-free) 스레드 안전 프로그래밍을 지원하는 작은 클래스 모음이라고 소개한다. AtomicInteger, AtomicLong, AtomicBoolean, AtomicReference와 배열판(AtomicIntegerArray 등), 기존 클래스의 volatile 필드를 원자적으로 다루는 필드 업데이터(AtomicIntegerFieldUpdater 등), 그리고 자바 8에서 추가된 LongAdder 같은 누산기가 들어 있다. 이 회차는 그중 AtomicInteger를 중심으로 본다.

    import java.util.concurrent.atomic.AtomicInteger;

public class AtomicCounter implements Counter {
    private final AtomicInteger value = new AtomicInteger();
    @Override public void increment() { value.incrementAndGet(); }
    @Override public int get() { return value.get(); }
}

    이 구현에는 synchronized도, 락 객체도 없다. 그런데 실험에서 매번 400000을 냈다. incrementAndGet()이 "읽고, 1을 더하고, 쓰는" 세 단계를 다른 스레드가 끼어들 수 없는 하나의 연산으로 실행하기 때문이다. 자주 쓰는 메서드를 정리하면 다음과 같다. 이름의 규칙은 단순하다. get이 앞에 있으면 바꾸기 전 값을, 뒤에 있으면 바꾼 뒤 값을 돌려준다.

    메서드하는 일돌려주는 값

    이 클래스가 어떻게 그 일을 하는지 OpenJDK 21의 소스(lib/src.zip의 java/util/concurrent/atomic/AtomicInteger.java)를 열어 보자. 필요한 부분만 옮기면 다음과 같다.

    public class AtomicInteger extends Number implements java.io.Serializable {
    /*
     * This class intended to be implemented using VarHandles, but there
     * are unresolved cyclic startup dependencies.
     */
    private static final Unsafe U = Unsafe.getUnsafe();
    private static final long VALUE
        = U.objectFieldOffset(AtomicInteger.class, "value");

    private volatile int value;

    public final boolean compareAndSet(int expectedValue, int newValue) {
        return U.compareAndSetInt(this, VALUE, expectedValue, newValue);
    }

    public final int incrementAndGet() {
        return U.getAndAddInt(this, VALUE, 1) + 1;
    }
    // ...
}

    세 가지가 보인다. 첫째, 실제 값은 private volatile int value 필드 하나에 있다. AtomicInteger는 volatile 필드 하나를 감싼 얇은 껍데기다. 그래서 get()과 set()은 보통의 volatile 읽기·쓰기와 같은 의미를 가진다. 둘째, VALUE는 AtomicInteger 객체 안에서 value 필드가 놓인 위치, 즉 객체 시작 주소로부터의 바이트 오프셋이다. 클래스가 로딩될 때 한 번 계산해 두고, 이후로는 "이 객체(this)의 시작 주소 + VALUE"로 필드의 메모리 위치를 직접 가리킨다. 셋째, 실제 원자적 연산은 jdk.internal.misc.Unsafe의 compareAndSetInt와 getAndAddInt에 맡긴다. 이 Unsafe는 java.base 모듈의 내부 패키지에 있어서 일반 애플리케이션 코드에서는 쓸 수 없다.

    주석은 원래 이 클래스를 VarHandle(자바 9에서 추가된, 변수에 대한 원자적 접근을 공식 API로 제공하는 클래스)로 구현하려 했지만 JDK 시작 과정의 순환 의존 때문에 Unsafe를 쓴다고 설명한다. 같은 패키지의 AtomicBoolean은 실제로 VarHandle을 쓰며, 값도 boolean이 아니라 private volatile int value에 0과 1로 저장한다. 어느 쪽이든 원자적 연산의 메모리 의미는 같다. AtomicInteger.compareAndSet의 Javadoc은 그 메모리 효과가 VarHandle.compareAndSet에 명시된 것과 같다고 적고 있고, 그 내용은 뒤의 CAS 절에서 본다.

    패키지 문서는 원자 클래스가 java.lang.Integer를 대신하는 범용 클래스가 아니라고 못박는다. equals, hashCode, compareTo를 정의하지 않으며, 값이 바뀌는 것이 전제이므로 해시 테이블의 키로 쓰기에 나쁘다. 두 AtomicInteger를 equals로 비교하면 값이 아니라 객체 동일성을 비교한다.

    성능 테스트: 원자성의 값은 얼마인가

    정확성만 따지면 SyncCounter와 AtomicCounter는 같다. 그럼 비용은 어떨까. 먼저 스레드 하나로 각 카운터를 1억 번씩 증가시키고 걸린 시간을 재 보자. 경합이 전혀 없는 상황에서 각 방식의 "기본 요금"을 보는 실험이다.

    public class PerfMain {
    static final int COUNT = 100_000_000;

    public static void main(String[] args) {
        test(new PlainCounter());
        test(new VolatileCounter());
        test(new SyncCounter());
        test(new AtomicCounter());
    }

    static void test(Counter counter) {
        long start = System.nanoTime();
        for (int i = 0; i < COUNT; i++) {
            counter.increment();
        }
        long ms = (System.nanoTime() - start) / 1_000_000;
        System.out.printf("%-16s 값=%d, 소요=%dms%n",
                counter.getClass().getSimpleName(), counter.get(), ms);
    }
}
    PlainCounter     값=100000000, 소요=5ms
VolatileCounter  값=100000000, 소요=618ms
SyncCounter      값=100000000, 소요=980ms
AtomicCounter    값=100000000, 소요=773ms

    시간 값은 실행마다, 기계마다 다르다. 같은 프로그램을 세 번 돌렸을 때 PlainCounter는 세 번 모두 5ms, VolatileCounter는 594~618ms, SyncCounter는 959~1006ms, AtomicCounter는 706~773ms였다. 이 숫자들을 다른 환경의 기준으로 삼으면 안 되고, 여기서 읽을 것은 숫자의 크기가 아니라 순서와 그 이유다.

    가장 이상한 것은 PlainCounter의 5ms다. 1억 번에 5ms면 한 번에 0.05나노초인데, 클록이 수 GHz인 CPU의 한 사이클은 0.2~0.5나노초 정도다. 반복 한 번을 한 사이클보다 빨리 실행할 수는 없으므로, JIT 컴파일러가 이 반복문을 한 번씩 실행하지 않고 다른 형태로 바꿨다는 뜻이다. 실제로 java -Xint PerfMain으로 JIT를 끄고 인터프리터만으로 돌리면 PlainCounter는 3091ms가 걸렸다. volatile이 아닌 필드에 대해서는 컴파일러가 반복마다 메모리를 읽고 쓸 의무가 없기 때문에 이런 변형이 허용된다. 5회차에서 종료 플래그 읽기가 반복문 밖으로 끌어올려진 것과 같은 자유다. 반면 VolatileCounter는 그 자유가 없어서 매 반복 실제로 읽고 쓴다. 이렇게 JIT가 측정 대상 자체를 바꿔 버리는 일 때문에, 제대로 된 마이크로벤치마크는 OpenJDK의 JMH 같은 도구로 작성한다.

    AtomicCounter는 VolatileCounter보다 조금 느리고 SyncCounter보다 빨랐다. volatile 읽기 후 volatile 쓰기는 각각 평범한 메모리 접근에 순서 제약을 더한 것이고, 원자적 덧셈은 뒤에서 볼 LOCK이 붙은 명령이나 그에 해당하는 원자 명령이다. 이 측정에서는 후자가 조금 더 비쌌다. synchronized는 그보다 더 비싸다. 6회차에서 본 것처럼 HotSpot은 경합이 없을 때도 모니터에 들어갈 때 객체 헤더의 마크 워드를 CAS로 바꾸고, 나올 때 원래 헤더를 되돌려 놓는다. 즉 락은 내부에서 이미 CAS를 쓰고 있고, 거기에 잠금 기록 관리 같은 일이 더 붙는다. "원자적 연산 하나"로 끝나는 AtomicInteger가 "원자적 연산 + 락 관리"인 synchronized보다 싼 이유다.

    -Xint로 돌렸을 때의 전체 결과는 한 가지를 더 알려 준다.

    PlainCounter     값=100000000, 소요=3091ms
VolatileCounter  값=100000000, 소요=3037ms
SyncCounter      값=100000000, 소요=3253ms
AtomicCounter    값=100000000, 소요=22569ms

    JIT가 없으면 AtomicCounter가 다른 셋보다 일곱 배 넘게 느려진다. AtomicInteger의 빠르기가 JIT 컴파일러의 특별한 처리에서 온다는 증거다. Unsafe.getAndAddInt에는 @IntrinsicCandidate 애너테이션이 붙어 있는데, 이것은 JVM이 이 메서드의 자바 코드를 실행하는 대신 미리 준비한 기계어 조각으로 바꿔 넣을 수 있다는 표시다. 이렇게 바꿔 넣는 것을 인트린식(intrinsic)이라고 한다. java -XX:+UnlockDiagnosticVMOptions -XX:+PrintIntrinsics PerfMain으로 실행하면 C2 컴파일러가 인라이닝 과정에서 다음과 같이 인트린식을 적용했다고 출력한다.

    @ 8   jdk.internal.misc.Unsafe::getAndAddInt (27 bytes)   (intrinsic)

    인터프리터는 이 대체를 하지 않으므로 getAndAddInt의 자바 코드(뒤에서 볼 CAS 반복문)를 그대로 실행하고, 그 안의 네이티브 메서드 호출 비용을 매번 치른다. 마지막으로 경합이 있는 경우를 보자. 아래는 네 스레드가 2500만 번씩, 합계 1억 번을 증가시킨 결과다(코드는 CounterMain의 run에 시간 측정을 붙인 것과 같다).

AtomicCounter    값=100000000, 소요=2793ms   (2761ms)

    여전히 AtomicCounter가 빠르다. 그런데 둘 다 스레드 하나로 1억 번 할 때(약 1초, 약 0.7초)보다 훨씬 느리다. 코어 네 개가 일을 나눠 했는데 전체 시간은 오히려 늘었다. 네 스레드가 모두 같은 메모리 위치 하나를 두고 다투기 때문이다. CAS는 스레드를 재우지 않을 뿐 경합 자체를 없애지는 못한다. 왜 그런지는 CAS가 CPU에서 어떻게 실행되는지 본 뒤에 다시 설명한다.

    CAS 연산 1: 비교 후 교환이라는 하나의 명령

    CAS는 비교 후 교환(compare-and-swap, compare-and-set)의 줄임말이다. 메모리 위치 하나와 두 값, 기대값(expected value)과 새 값(new value)을 받아 다음 일을 한 번에 한다. 현재 값이 기대값과 같으면 새 값으로 바꾸고 성공을 알린다. 다르면 아무것도 바꾸지 않고 실패를 알린다. 의미만 의사코드로 적으면 다음과 같다. 이 전체가 하나의 원자적 단계로 실행된다는 것이 핵심이며, 실제로 이렇게 자바 코드로 쓰면 원자적이지 않다.

    compareAndSet(expected, newValue):       ← 이 상자 전체가 쪼갤 수 없는 한 단계
  ┌────────────────────────────────────────┐
  │ if (현재값 == expected) {               │
  │     현재값 = newValue;                  │
  │     return true;                        │
  │ } else {                                │
  │     return false;   // 아무것도 안 바꿈 │
  │ }                                       │
  └────────────────────────────────────────┘

    VarHandle.compareAndSet의 Javadoc은 이 동작을 더 정확하게 정의한다. 변수의 현재 값(이를 목격값, witness value라고 부른다)이 기대값과 ==이면 변수를 새 값으로 원자적으로 설정하는데, 현재 값은 getVolatile의 메모리 의미로 읽고, 새 값은 setVolatile의 메모리 의미로 쓴다. 즉 CAS는 원자성과 함께 volatile 읽기와 volatile 쓰기의 가시성·순서 보장을 모두 가진다. 이 성질은 뒤에서 CAS로 락을 만들 때 결정적인 역할을 한다.

    바로 써 보자. compareAndExchange는 자바 9에 추가된 변형으로, 성공 여부 대신 목격값 자체를 돌려준다.

    import java.util.concurrent.atomic.AtomicInteger;

public class CasMain {
    public static void main(String[] args) {
        AtomicInteger atomic = new AtomicInteger(0);
        System.out.println("시작 값 = " + atomic.get());

        boolean r1 = atomic.compareAndSet(0, 1);
        System.out.println("CAS(0 -> 1) 결과 = " + r1 + ", 값 = " + atomic.get());

        boolean r2 = atomic.compareAndSet(0, 1);
        System.out.println("CAS(0 -> 1) 결과 = " + r2 + ", 값 = " + atomic.get());

        int witness = atomic.compareAndExchange(5, 9);
        System.out.println("CAE(5 -> 9) 목격값 = " + witness + ", 값 = " + atomic.get());
    }
}
    시작 값 = 0
CAS(0 -> 1) 결과 = true, 값 = 1
CAS(0 -> 1) 결과 = false, 값 = 1
CAE(5 -> 9) 목격값 = 1, 값 = 1

    첫 CAS는 현재 값 0이 기대값 0과 같으므로 1로 바꾸고 true를 돌려준다. 두 번째 CAS는 같은 인자로 호출했지만 이제 현재 값이 1이어서 기대값 0과 다르므로 아무것도 바꾸지 않고 false를 돌려준다. 세 번째 compareAndExchange(5, 9)는 현재 값 1이 5와 다르므로 실패하고, 실패했을 때 실제로 본 값 1을 돌려준다. 실패한 쪽이 "그럼 지금 값은 무엇이었나"를 다시 읽지 않아도 된다는 것이 이 변형의 장점이다.

    이 동작이 왜 갱신 손실을 막는지 생각해 보자. putfield는 무조건 덮어썼다. CAS는 "내가 읽었던 값이 아직 그대로일 때만" 쓴다. 다른 스레드가 그사이 값을 바꿨다면 CAS는 실패하고, 실패를 알게 된 스레드는 자기가 계산한 결과를 버리고 다시 하면 된다. 검사와 쓰기가 하나로 붙어 있어서, 검사가 통과한 뒤 쓰기 전에 다른 스레드가 끼어드는 틈이 없다. 그런데 소프트웨어만으로는 이 "붙어 있음"을 만들 수 없다. 검사와 쓰기를 자바 코드 두 줄로 쓰면 다시 그 사이가 틈이 된다. 그래서 CAS는 CPU가 명령 하나로 제공해야 한다.

    x86에서 그 명령은 CMPXCHG다. 인텔의 명령어 설명에 따르면 이 명령은 누산기 레지스터(EAX 등)의 값을 목적지 피연산자(메모리)와 비교해, 같으면 원본 피연산자를 목적지에 넣고, 다르면 목적지의 값을 누산기에 넣는다. 결과는 ZF 플래그로 알린다. 그리고 앞에서 말했듯이 LOCK 접두어와 함께 써야 원자적으로 실행된다. 누산기에 기대값을 넣고 실행하면, 실패했을 때 누산기에 남는 값이 바로 목격값이다. compareAndExchange가 목격값을 돌려줄 수 있는 것은 하드웨어가 원래 그 값을 주기 때문이다.

    HotSpot이 실제로 이 명령을 쓰는지 OpenJDK 21의 C2 컴파일러 규칙 파일 x86_64.ad에서 확인할 수 있다. 이 파일은 C2의 중간 표현 노드를 어떤 기계어로 바꿀지 정의한다.

    instruct compareAndSwapI(rRegI res,
                         memory mem_ptr,
                         rax_RegI oldval, rRegI newval,
                         rFlagsReg cr)
%{
  match(Set res (CompareAndSwapI mem_ptr (Binary oldval newval)));
  match(Set res (WeakCompareAndSwapI mem_ptr (Binary oldval newval)));
  effect(KILL cr, KILL oldval);

  format %{ "cmpxchgl $mem_ptr,$newval\t# "
            "If rax == $mem_ptr then store $newval into $mem_ptr\n\t"
            "sete    $res\n\t"
            "movzbl  $res, $res" %}
  ins_encode %{
    __ lock();
    // ...

instruct xaddI( memory mem, rRegI newval, rFlagsReg cr) %{
  match(Set newval (GetAndAddI mem newval));
  effect(KILL cr);
  format %{ "XADDL  [$mem],$newval" %}
  ins_encode %{
    __ lock();
    __ xaddl($mem$$Address, $newval$$Register);
  %}
  ins_pipe( pipe_cmpxchg );
%}

    첫 규칙은 int CAS 노드를 lock 접두어가 붙은 cmpxchgl로 바꾸고, 결과 플래그를 sete로 0 또는 1의 boolean 값으로 옮긴다. 기대값이 rax 레지스터에 있어야 한다는 제약(rax_RegI oldval)은 CMPXCHG가 누산기를 쓰는 명령이기 때문이다. 두 번째 규칙은 더 흥미롭다. getAndAddInt가 인트린식으로 바뀌어 생긴 GetAndAddI 노드는 CAS 반복문이 아니라 lock xaddl 명령 하나가 된다(반환값을 쓰지 않고 더하는 값이 상수이면 같은 파일의 xaddI_no_res 규칙이 골라져 lock addl 명령 하나가 된다). XADD는 메모리 값에 더하고 원래 값을 돌려주는 원자적 덧셈 명령이다. 즉 C2가 컴파일한 x86 코드에서 incrementAndGet()은 재시도 반복문조차 없이 명령 하나로 끝난다.

    이 원고를 실험한 Apple M1은 x86이 아니라 AArch64(ARM 64비트)다. ARM은 원래 CAS 명령 하나 대신, 값을 읽으며 그 주소를 "감시"하는 독점 적재(load-exclusive, LDXR)와 그사이 다른 코어가 그 주소에 썼다면 실패하는 독점 저장(store-exclusive, STXR)의 짝으로 원자적 연산을 만들었다. ARMv8.1에서 LSE(Large System Extensions)라는 확장으로 CAS, LDADD 같은 단일 원자 명령이 추가되었다. HotSpot의 macroAssembler_aarch64.cpp는 두 경우를 모두 처리한다.

      if (UseLSE) {
    mov(result, expected);
    lse_cas(result, new_val, addr, size, acquire, release, /*not_pair*/ true);
    compare_eq(result, expected, size);
    // ...
  } else {
    Label retry_load, done;
    prfm(Address(addr), PSTL1STRM);
    bind(retry_load);
    load_exclusive(result, addr, size, acquire);
    compare_eq(result, expected, size);
    br(Assembler::NE, done);
    store_exclusive(rscratch1, new_val, addr, size, release);
    if (weak) {
      cmpw(rscratch1, 0u);  // If the store fails, return NE to our caller.
    } else {
      cbnzw(rscratch1, retry_load);
    }
    bind(done);
  }

    UseLSE가 켜져 있으면 LSE의 CAS 명령 하나를 내보내고, 꺼져 있으면 독점 적재로 읽어 비교하고 독점 저장을 시도하는 반복을 내보낸다. 이 원고의 환경에서 java -XX:+PrintFlagsFinal -version으로 확인한 UseLSE는 true였다(소스의 기본값은 false이고, JVM이 시작할 때 CPU가 LSE를 지원하는지 보고 켠다). 같은 파일의 ATOMIC_OP 매크로는 원자적 덧셈도 LSE가 있으면 ldadd 계열 명령, 없으면 ldxr/stxr 반복으로 만들도록 정의되어 있다. 그리고 비LSE 경로의 if (weak) 분기를 기억해 두자. 독점 저장이 실패했을 때 다시 시도하지 않고 바로 실패를 돌려주는 이 분기가, 뒤에서 볼 "약한 CAS의 가짜 실패"의 정체다.

    CAS 연산 2: CAS로 증가 연산을 직접 만들기

    CAS 명령 하나는 "값이 그대로면 바꾼다"까지만 해 준다. 실패했을 때 어떻게 할지는 프로그램이 정한다. 가장 흔한 선택은 다시 읽고 다시 계산해 다시 시도하는 것이다. compareAndSet만으로 원자적 증가를 직접 만들어 보자.

    static int incrementWithCas(AtomicInteger atomic) {
    int current;
    int next;
    do {
        current = atomic.get();      // 1. 현재 값을 스냅숏으로 읽는다
        next = current + 1;          // 2. 내 스택 안에서만 새 값을 계산한다
    } while (!atomic.compareAndSet(current, next));   // 3. 그대로일 때만 반영한다
    return next;
}

    경합이 없을 때 이 메서드가 어떻게 실행되는지 따라가 보자. 값이 5인 상태에서 호출하면, 1단계의 get()이 5를 읽어 지역 변수 current에 담는다. 2단계에서 next는 6이 된다. 이 두 변수는 이 스레드의 스택 프레임에만 있으므로 아직 아무에게도 영향을 주지 않는다. 3단계의 compareAndSet(5, 6)은 현재 값이 여전히 5이므로 성공해 true를 돌려주고, while의 조건 !true는 거짓이므로 반복을 빠져나와 6을 반환한다. 경합이 없으면 반복은 한 번으로 끝나고, 비용은 volatile 읽기 한 번과 CAS 한 번이다.

    이 모양은 앞에서 본 AtomicInteger.incrementAndGet()이 부르는 Unsafe.getAndAddInt의 자바 코드와 거의 같다. OpenJDK 21의 jdk/internal/misc/Unsafe.java에는 다음과 같이 적혀 있다.

    @IntrinsicCandidate
public final int getAndAddInt(Object o, long offset, int delta) {
    int v;
    do {
        v = getIntVolatile(o, offset);
    } while (!weakCompareAndSetInt(o, offset, v, v + delta));
    return v;
}

    읽고(getIntVolatile), 계산하고(v + delta), 조건부로 반영하는(weakCompareAndSetInt) 세 단계가 그대로 있다. 차이는 두 가지다. 강한 CAS 대신 약한 CAS를 쓴다는 점(이유는 다음 절에서 본다), 그리고 @IntrinsicCandidate가 붙어 있어서 C2가 이 반복문 전체를 x86의 lock xadd 하나로 바꿀 수 있다는 점이다. 앞의 -Xint 실험에서 AtomicCounter가 유독 느렸던 것은 인터프리터가 이 자바 반복문을 글자 그대로 실행했기 때문이다.

    이 세 단계 구조에는 이름이 있다. 락은 "충돌이 일어날 것이라고 보고 미리 막는" 비관적(pessimistic) 방식이다. 들어가기 전에 문을 잠그므로, 다른 스레드는 충돌이 실제로 일어나든 아니든 기다린다. CAS 반복은 "충돌이 드물 것이라고 보고 일단 진행한 뒤, 반영할 때 충돌 여부를 확인하는" 낙관적(optimistic) 방식이다. 계산하는 동안 아무도 기다리지 않고, 충돌이 났을 때만 계산을 버리고 다시 한다. 충돌이 드물면 낙관적 방식이 유리하고, 충돌이 잦으면 버려지는 계산이 늘어 불리해진다.

    일상에서 가져온 비유공유 문서의 편집 충돌 검사

    여러 사람이 고치는 위키 문서를 떠올려 보자. 편집 화면을 열 때 문서의 판 번호를 기억해 두고, 저장 버튼을 누를 때 서버가 "그사이 다른 사람이 저장했는가"를 확인한다. 아무도 안 했으면 저장되고, 누가 먼저 저장했으면 거부된다. 거부된 사람은 최신 판을 다시 열어 고친 뒤 다시 저장한다. 편집하는 동안 문서를 잠그지 않으니 다른 사람도 동시에 편집할 수 있다. 비유가 깨지는 지점도 있다. 위키는 판 번호로 "누가 손댔는가"를 확인하지만, CAS는 값만 비교한다. 누가 값을 바꿨다가 원래대로 돌려 놓으면 CAS는 그 사실을 모른다. 이것이 뒤에서 볼 ABA 문제다.

    같은 생각은 이 로드맵의 앞선 권에서도 만났다. JPA의 @Version을 이용한 낙관적 락은 엔티티를 읽을 때 버전 값을 기억해 두고, 수정할 때 UPDATE ... WHERE id = ? AND version = ?처럼 버전이 그대로일 때만 갱신한다. 갱신된 행이 0건이면 다른 트랜잭션이 먼저 고쳤다는 뜻이므로 예외를 던진다. 데이터베이스 행 하나를 대상으로 한 CAS인 셈이다. 메모리의 CAS는 CPU 명령 하나로, 데이터베이스의 낙관적 락은 조건부 UPDATE 문 하나로 "검사와 쓰기를 붙인다"는 같은 원리를 구현한다.

    같은 CAS의 세 갈래 길: 인터프리터, C1, C2

    성능 테스트에서 -Xint로 JIT를 끄면 AtomicCounter만 유독 일곱 배 넘게 느려졌다. getAndAddInt의 자바 코드를 보았으니 그 차이가 어디서 오는지 한 단계 더 따라가 보자. HotSpot은 메서드를 처음에는 인터프리터로 실행하고, 호출이 쌓이면 C1 컴파일러로, 더 쌓이면 C2 컴파일러로 기계어를 만든다. 이것을 계층형 컴파일(tiered compilation)이라고 한다. 같은 incrementAndGet()이라도 지금 어느 단계에서 실행되느냐에 따라 CPU의 원자 명령까지 가는 길이 다르다.

    먼저 인터프리터의 길이다. OpenJDK 21의 Unsafe.java에서 getIntVolatile과 compareAndSetInt는 native 메서드이고, weakCompareAndSetInt는 본문이 return compareAndSetInt(o, offset, expected, x); 한 줄인 자바 메서드다. HotSpot의 템플릿 인터프리터가 전용 진입점을 따로 두는 메서드는 abstractInterpreter.hpp의 MethodKind 열거형에 정해져 있다. Math.sin, CRC32.update, Thread.currentThread 같은 것들이고, Unsafe의 CAS는 그 목록에 없다. 그래서 인터프리터는 이 둘을 보통의 네이티브 메서드로 호출하고, 그 구현은 HotSpot의 src/hotspot/share/prims/unsafe.cpp에 있다.

    UNSAFE_ENTRY(jboolean, Unsafe_CompareAndSetInt(JNIEnv *env, jobject unsafe, jobject obj, jlong offset, jint e, jint x)) {
  oop p = JNIHandles::resolve(obj);
  volatile jint* addr = (volatile jint*)index_oop_from_field_offset_long(p, offset);
  return Atomic::cmpxchg(addr, e, x) == e;
} UNSAFE_END

    세 줄이 하는 일은 AtomicInteger가 자바 쪽에서 준비한 것을 그대로 쓰는 것이다. JNI 핸들로 넘어온 객체 참조를 실제 객체(oop)로 풀고, 거기에 VALUE 오프셋을 더해 필드 주소를 만들고, 그 주소에 CAS를 한다. 비용은 그 앞뒤에서 생긴다. UNSAFE_ENTRY는 JVM_ENTRY로 정의되어 있고, JVM_ENTRY는 함수에 들어가자마자 ThreadInVMfromNative 객체를 만들어 스레드 상태를 "네이티브 코드 실행 중"에서 "VM 내부 실행 중"으로 바꾸며, 함수를 나갈 때 되돌린다(interfaceSupport.inline.hpp). macOS AArch64 빌드에서는 같은 매크로가 스레드의 W^X(쓰기와 실행을 동시에 허용하지 않는 코드 메모리 보호) 모드를 쓰기 쪽으로 맞추는 ThreadWXEnable 객체도 만든다. CAS를 실제로 하는 Atomic::cmpxchg는 메모리 순서 인자를 생략하면 memory_order_conservative가 기본값이다(atomic.hpp). 이 원고의 환경인 macOS/AArch64용 구현은 그 순서를 다음과 같이 처리한다.

      if (order == memory_order_conservative) {
    T value = compare_value;
    FULL_MEM_BARRIER;
    __atomic_compare_exchange(dest, &value, &exchange_value, /*weak*/false,
                              __ATOMIC_RELAXED, __ATOMIC_RELAXED);
    FULL_MEM_BARRIER;
    return value;

    C++ 컴파일러의 내장 원자 함수로 순서 제약이 없는(relaxed) CAS를 하고, 그 앞뒤를 전체 메모리 장벽으로 감싼다. 정리하면 인터프리터에서 incrementAndGet() 한 번은, getAndAddInt 반복문이 한 바퀴 돌 때마다 네이티브 호출 두 번(getIntVolatile, compareAndSetInt)과 그때마다의 VM 진입·이탈, 장벽 두 개로 감싼 CAS를 치른다.

    C1부터는 사정이 다르다. src/hotspot/share/c1/c1_Compiler.cpp의 Compiler::is_intrinsic_supported는 _getAndAddInt(CPU가 4바이트 원자적 덧셈을 지원할 때), _compareAndSetInt, _onSpinWait(CPU가 지원할 때) 등을 C1도 인트린식으로 처리하는 목록에 넣어 두었다. C1으로 컴파일된 코드부터는 네이티브 호출 없이 원자 명령이 코드 안에 바로 들어간다는 뜻이다. 실험으로 확인해 보자. 스레드 하나가 AtomicInteger.incrementAndGet()을 2천만 번 호출하는 반복문을, 실행 단계를 제한하는 옵션별로 세 번씩 돌렸다.

    옵션거치는 실행 단계소요 시간(3회)
    -Xint인터프리터만4284, 4077, 4216ms
    -XX:TieredStopAtLevel=1인터프리터 → C1141, 143, 142ms

    CAS 연산 3: 두 스레드가 동시에 CAS를 시도할 때

    이제 경합이 있을 때 CAS 반복문이 어떻게 갱신 손실을 피하는지 눈으로 확인하자. 아래 프로그램은 앞의 incrementWithCas에 로그를 붙이고, 읽기와 CAS 사이를 100ms 벌려서 두 스레드가 같은 값을 읽도록 유도한다.

    import java.util.concurrent.atomic.AtomicInteger;

public class CasLoopMain {
    static final AtomicInteger value = new AtomicInteger(0);

    public static void main(String[] args) throws InterruptedException {
        Runnable task = () -> {
            int result = incrementWithCas(value);
            log("결과 = " + result);
        };
        Thread a = new Thread(task, "A");
        Thread b = new Thread(task, "B");
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println("최종 값 = " + value.get());
    }

    static int incrementWithCas(AtomicInteger atomic) {
        int current;
        int next;
        do {
            current = atomic.get();
            log("읽은 값 = " + current);
            sleep(100); // 읽기와 CAS 사이를 일부러 벌린다
            next = current + 1;
        } while (!casAndLog(atomic, current, next));
        return next;
    }

    static boolean casAndLog(AtomicInteger atomic, int expected, int next) {
        boolean ok = atomic.compareAndSet(expected, next);
        log("CAS(" + expected + " -> " + next + ") = " + ok);
        return ok;
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); }
    }

    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }
}

    경합이 심하면 재시도가 얼마나 늘어나는가

    위 예에서 B는 한 번 실패하고 한 번 재시도했다. 경합이 심하면 재시도는 얼마나 될까. 직접 세기 위해 updateAndGet을 쓴다. 이 메서드는 현재 값을 받아 새 값을 돌려주는 함수를 인자로 받는데, 그 함수 안에서 호출 횟수를 세면 CAS가 몇 번 다시 시도됐는지 알 수 있다. 호출 횟수는 많은 스레드가 동시에 더해도 정확해야 하므로 LongAdder로 센다.

    import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.atomic.LongAdder;

public class UpdateMain {
    public static void main(String[] args) throws InterruptedException {
        AtomicInteger value = new AtomicInteger();
        LongAdder calls = new LongAdder();          // 함수가 몇 번 호출됐는지 센다
        List threads = new ArrayList<>();
        for (int i = 0; i < 4; i++) {
            Thread t = new Thread(() -> {
                for (int j = 0; j < 100_000; j++) {
                    value.updateAndGet(v -> {
                        calls.increment();
                        return v + 1;
                    });
                }
            });
            threads.add(t);
            t.start();
        }
        for (Thread t : threads) t.join();
        System.out.println("최종 값     = " + value.get());
        System.out.println("함수 호출 수 = " + calls.sum());
    }
}

    public final int updateAndGet(IntUnaryOperator updateFunction) {
    int prev = get(), next = 0;
    for (boolean haveNext = false;;) {
        if (!haveNext)
            next = updateFunction.applyAsInt(prev);
        if (weakCompareAndSetVolatile(prev, next))
            return next;
        haveNext = (prev == (prev = get()));
    }
}

    CAS가 실패하면 마지막 줄이 값을 다시 읽어 prev에 넣고, 다시 읽은 값이 이전 prev와 같은지를 haveNext에 기록한다. 값이 그대로인데도 실패했다면(바로 뒤에서 볼 약한 CAS의 가짜 실패) 이미 계산한 next를 재사용하고, 값이 바뀌어 있으면 함수를 다시 호출한다. 그러니 함수 호출 수에서 400000을 뺀 수는, 다른 스레드가 먼저 값을 바꿔서 계산을 버려야 했던 횟수다. 이 메서드의 Javadoc이 함수는 부수 효과가 없어야 한다(side-effect-free)고, 경합으로 갱신이 실패하면 다시 적용될 수 있기 때문이라고 적어 둔 이유가 여기 있다. 이 실험에서는 일부러 부수 효과(호출 수 세기)를 넣어 재시도를 관찰했지만, 실제 코드에서 함수 안에 로그 기록, 메시지 발송, 다른 카운터 증가 같은 일을 넣으면 그 일이 예측할 수 없는 횟수만큼 반복된다.

    약한 CAS와 가짜 실패

    getAndAddInt와 updateAndGet이 모두 강한 compareAndSet이 아니라 약한 CAS(weakCompareAndSetInt, weakCompareAndSetVolatile)를 쓰는 데에는 이유가 있다. VarHandle.weakCompareAndSet의 Javadoc은 이 연산이 목격값이 기대값과 같더라도 가짜로 실패할 수 있다(may fail spuriously)고, 그 원인은 대개 메모리 경합이라고 적는다. 강한 CAS는 값이 같으면 반드시 성공해야 하지만, 약한 CAS는 값이 같아도 실패할 수 있다.

    이런 연산이 필요한 이유는 앞에서 본 AArch64의 비LSE 경로에 있다. 독점 적재와 독점 저장으로 CAS를 만들 때, 값 비교는 통과했는데 독점 저장이 실패하는 경우가 생긴다. 강한 CAS는 이때 cbnzw(rscratch1, retry_load)로 처음부터 다시 시도해 "값이 같으면 반드시 성공"이라는 약속을 지킨다. 약한 CAS는 if (weak) 분기에서 재시도 없이 실패를 돌려준다. 호출하는 쪽이 어차피 실패하면 다시 읽고 다시 시도하는 반복문 안에 있다면, 하드웨어 수준에서 한 번 더 도는 것은 중복이다. 그래서 반복문 안의 CAS는 약한 것으로 충분하다. LSE의 CAS 명령이나 x86의 lock cmpxchg처럼 명령 하나로 끝나는 하드웨어에서는 강한 CAS와 약한 CAS가 같은 명령이 되며, 앞에서 본 x86 규칙 파일에서도 CompareAndSwapI와 WeakCompareAndSwapI가 같은 규칙에 연결되어 있었다.

    AtomicInteger.weakCompareAndSet(int, int)는 자바 9부터 사용 중단(deprecated)되었고, 같은 동작이 weakCompareAndSetPlain이라는 이름으로 남았다. 이름의 Plain이 뜻하듯 이 메서드는 원자성만 주고 volatile의 순서 보장은 주지 않는다. 순서 보장까지 필요하면 weakCompareAndSetVolatile을 쓴다.

    ABA 문제

    CAS는 값만 비교한다. 그래서 스레드 1이 값 A를 읽은 뒤, 스레드 2가 값을 A에서 B로 바꿨다가 다시 A로 돌려 놓으면, 스레드 1의 CAS는 아무 일도 없었던 것처럼 성공한다. 이것을 ABA 문제라고 한다. 카운터에서는 문제가 되지 않는다. 정수 값이 같다면 그 값에 이르기까지의 이력은 결과에 아무 영향이 없기 때문이다.

    문제가 되는 것은 값이 "다른 무언가를 가리키는 참조"이고, 그 참조가 같아도 가리키는 대상의 상태가 달라졌을 수 있는 경우다. CAS로 만든 연결 리스트 스택을 생각해 보자. 스택 꼭대기가 노드 X이고 그 아래가 Y다. 스레드 1이 꺼내기(pop)를 하려고 top = X, X.next = Y를 읽고 CAS(top, X, Y)를 준비한다. 그사이 스레드 2가 X를 꺼내고, Y를 꺼내고, 다시 X를 넣는다. 이제 top은 다시 X이고 X 아래에는 Y가 없다. 스레드 1의 CAS(top, X, Y)는 꼭대기가 여전히 X이므로 성공하고, 이미 스택에서 빠진 Y가 꼭대기로 돌아온다. 자바에서는 스레드 1이 X의 참조를 쥐고 있는 동안 X가 GC로 회수되어 같은 자리에 다른 객체가 들어서는 일은 일어나지 않는다. 그러나 이 예처럼 프로그램이 같은 객체를 다시 넣거나 노드를 재사용하면 ABA는 그대로 생긴다.

    해법은 값과 함께 "몇 번째 변경인가"를 비교하는 것이다. java.util.concurrent.atomic의 AtomicStampedReference는 참조 하나에 정수 하나를 묶어 두는데, 패키지 문서는 이 정수를 일련의 갱신에 대응하는 버전 번호로 쓸 수 있다고 설명한다. compareAndSet(expectedReference, newReference, expectedStamp, newStamp)는 참조와 스탬프가 모두 기대값과 같을 때만 바꾸므로, X로 돌아왔더라도 스탬프가 올라가 있으면 실패한다. 비유에서 위키의 판 번호가 하던 일을 스탬프가 하는 셈이다.

    한 층 아래: 캐시 일관성과 경합의 비용

    성능 실험에서 남겨 둔 질문으로 돌아가자. 왜 네 스레드가 나눠서 더했는데 스레드 하나보다 느렸을까. 답은 CPU 캐시에 있다. 5회차에서 보았듯이 각 코어는 메인 메모리의 내용을 자기 캐시에 복사해 두고 작업한다. 캐시는 바이트 단위가 아니라 캐시 라인(cache line)이라는 고정 크기 덩어리 단위로 데이터를 주고받는다. 여러 코어가 같은 주소를 캐시에 두고 있을 때 서로 다른 값을 보는 일이 없도록, 멀티코어 CPU는 캐시 일관성(cache coherence) 프로토콜로 각 코어의 캐시를 맞춘다.

    널리 쓰이는 무효화 기반 일관성 프로토콜에서, 한 코어가 어떤 캐시 라인에 쓰려면 먼저 그 라인을 독점해야 한다. 다른 코어들이 가진 같은 라인의 사본은 무효화되고, 그 코어들이 다음에 그 주소를 읽으려면 독점한 코어로부터 최신 내용을 다시 받아 와야 한다. 원자적 읽기-수정-쓰기 명령(lock cmpxchg, lock xadd, LSE의 cas, ldadd)이 원자적일 수 있는 것은, 코어가 라인을 독점한 상태에서 읽기·비교·쓰기를 끝낼 때까지 다른 코어가 그 라인을 가져가지 못하게 하기 때문이다. 앞에서 의사코드로 그린 "쪼갤 수 없는 상자"를 하드웨어는 이렇게 만든다.

    CAS 반복문은 여기에 재시도 비용이 더해진다. 값을 읽은 뒤 CAS를 하기 전에 다른 코어가 라인을 가져가 값을 바꾸면 CAS가 실패하고, 다시 읽고 다시 CAS해야 한다. updateAndGet 실험에서 본 수십만 번의 재시도가 바로 그것이다. 강한 CAS의 실패는 그사이 다른 스레드의 갱신이 성공했다는 뜻이므로 시스템 전체로 보면 언제나 누군가는 앞으로 나아간다. 이런 성질을 락 프리(lock-free)라고 부른다. 그러나 개별 스레드로 보면 운이 나쁜 스레드는 계속 지고 계속 재시도할 수 있다. 모든 스레드가 유한한 단계 안에 끝난다는 더 강한 보장(wait-free)은 CAS 반복문이 주지 않는다.

    하나의 변수에 경합이 몰리는 것이 문제라면, 변수를 나누는 방법이 있다. 자바 8에서 추가된 LongAdder가 그렇게 한다. Javadoc에 따르면 LongAdder는 합을 함께 유지하는 하나 이상의 변수로 이루어지고, 갱신이 스레드 사이에서 경합하면 경합을 줄이기 위해 변수 집합을 동적으로 늘린다. sum()은 그 변수들을 합쳐 돌려준다. 같은 문서는 통계 수집처럼 여러 스레드가 공통 합계를 갱신하는 용도라면 대개 AtomicLong보다 낫고, 경합이 적을 때는 둘이 비슷하지만 경합이 심할 때는 공간을 더 쓰는 대신 기대 처리량이 훨씬 높다고 설명한다. 대신 sum()은 원자적 스냅숏이 아니어서, 합을 계산하는 동안 일어난 갱신은 반영되지 않을 수 있다. 그래서 문서는 이 클래스가 세밀한 동기화 제어용이 아니라고 적는다. 앞의 UpdateMain이 호출 횟수를 LongAdder로 센 것도 그 때문이다. 모든 스레드가 끝난 뒤에 한 번 읽는 통계 값이었다.

    메모리 순서도 짚고 넘어가자. 앞에서 본 대로 compareAndSet은 volatile 읽기와 volatile 쓰기의 메모리 의미를 함께 가진다. 따라서 CAS로 값을 바꾼 스레드가 그 CAS 이전에 한 모든 쓰기는, 그 CAS가 쓴 값을 volatile 읽기(또는 다른 CAS)로 본 스레드에게 보인다. 원자성만이 아니라 happens-before 관계까지 만들어 준다는 것이고, 이 성질 덕분에 CAS 하나로 락을 만들 수 있다.

    CAS의 메모리 순서: 접근 모드와 저장 버퍼링 실험

    바로 앞 문단에서 compareAndSet은 volatile 읽기와 쓰기의 메모리 의미를 함께 가진다고 했다. 그런데 자바 9부터 AtomicInteger에는 같은 변수를 이보다 약한 순서로 다루는 메서드들이 함께 들어 있다. setPlain/getPlain, setOpaque/getOpaque, setRelease/getAcquire, 그리고 compareAndExchangeAcquire, weakCompareAndSetRelease 같은 CAS 변형이다. 자바 6부터 있던 lazySet도 이 무리에 속한다. OpenJDK 21 소스에서 lazySet의 본문은 U.putIntRelease(this, VALUE, newValue)로, setRelease와 글자 하나 다르지 않다. 각 메서드의 Javadoc은 메모리 효과를 VarHandle의 같은 이름 메서드에 맡기므로 기준은 VarHandle 클래스 문서다.

    VarHandle 문서는 접근 모드(access mode)를 네 층으로 정의한다. 요지를 옮기면 이렇다. Plain 읽기·쓰기는 참조와 32비트 이하 기본형에 대해서만 비트 단위로 원자적이고, 실행 중인 스레드 바깥에서 관찰할 수 있는 순서 제약이 없다. Opaque는 비트 단위로 원자적이며, 같은 변수에 대한 접근끼리는 일관된(coherent) 순서를 가진다. Acquire 읽기와 그 뒤의 접근은, 짝이 되는 Release 쓰기와 그 앞의 접근보다 뒤에 놓인다. Volatile은 여기에 더해 모든 volatile 연산끼리 전체 순서(total order)를 가진다. 같은 문서의 메서드별 설명은 setVolatile이 C/C++의 memory_order_seq_cst와, getAcquire와 setRelease가 각각 memory_order_acquire, memory_order_release와 호환되는 순서 효과를 가진다고 덧붙인다.

    Acquire/Release와 Volatile을 가르는 것은 마지막 한 줄, 전체 순서뿐이다. 이 한 줄이 실제로 무엇을 막는지는 저장 버퍼링(store buffering)이라고 불리는 고전적인 패턴에서 드러난다. 두 변수 x와 y가 0에서 시작하고, 각 스레드가 "내 변수에 먼저 쓰고 나서 상대 변수를 읽는다".

    초기값  x = 0, y = 0

  스레드 1              스레드 2
  x에 1을 쓴다          y에 1을 쓴다
  r1 = y를 읽는다       r2 = x를 읽는다

질문: r1 == 0 이면서 r2 == 0 인 결과가 나올 수 있는가?

    네 동작이 모두 volatile이면 (0, 0)은 불가능하다는 것을 JLS로 증명할 수 있다. JLS 17.4.4에 따르면 한 실행의 모든 동기화 동작(volatile 읽기와 쓰기가 여기에 든다)에는 동기화 순서라는 전체 순서가 있고, 각 스레드 안에서는 이 순서가 프로그램 순서와 일치한다. 그리고 17.4.7의 동기화 순서 일관성(synchronization-order consistency)은 volatile 읽기가 동기화 순서에서 자기보다 앞선 같은 변수의 쓰기 가운데 마지막 것을 보도록 요구한다. 이제 r1이 0이었다고 하자. 스레드 1의 y 읽기가 0을 봤다면 그 읽기는 동기화 순서에서 스레드 2의 y 쓰기보다 앞이어야 한다(뒤였다면 1을 봤어야 한다). 여기에 각 스레드의 프로그램 순서를 이으면 "x 쓰기 → y 읽기 → y 쓰기 → x 읽기"가 되므로, 스레드 2의 x 읽기는 x 쓰기보다 뒤에 있어 1을 본다. r1과 r2가 동시에 0일 수는 없다. Acquire/Release에는 이런 전체 순서가 없다. Release 쓰기 뒤에 오는 Acquire 읽기가 그 쓰기보다 먼저 수행된 것처럼 보이는 것을 막는 규칙이 없으므로 (0, 0)이 허용된다.

    규칙이 허용한다는 것과 실제로 일어난다는 것은 다른 이야기이므로 직접 돌려 보자. 아래 프로그램은 1024개의 x/y 쌍을 새로 만들고, 두 스레드가 시작 신호를 받으면 같은 순서로 배열을 훑으며 각 쌍에 대해 위의 두 줄을 실행한다. 두 스레드가 거의 같은 순간에 같은 쌍을 건드리게 하려는 구조다. 이것을 2만 라운드, 접근 모드별로 반복해 결과 네 가지를 센다.

    import java.util.concurrent.atomic.AtomicInteger;

public class StoreBuffer {
    static final int BATCH = 1024;
    static final int ROUNDS = 20_000;

    static final class Pair {
        final AtomicInteger x = new AtomicInteger();
        final AtomicInteger y = new AtomicInteger();
        int r1, r2;
    }

    public static void main(String[] args) throws Exception {
        for (String mode : new String[]{"plain", "release/acquire", "volatile", "getAndAdd"}) {
            run(mode);
        }
    }

    static void run(String mode) throws Exception {
        Pair[] pairs = new Pair[BATCH];
        AtomicInteger start = new AtomicInteger();   // 라운드 시작 신호
        AtomicInteger done = new AtomicInteger();    // 라운드를 끝낸 스레드 수
        long[] histogram = new long[4];              // 인덱스 = r1*2 + r2

        Thread t1 = new Thread(() -> {
            for (int round = 1; round <= ROUNDS; round++) {
                while (start.get() != round) Thread.onSpinWait();
                for (Pair p : pairs) p.r1 = actor(mode, p.x, p.y);
                done.incrementAndGet();
            }
        });
        Thread t2 = new Thread(() -> {
            for (int round = 1; round <= ROUNDS; round++) {
                while (start.get() != round) Thread.onSpinWait();
                for (Pair p : pairs) p.r2 = actor(mode, p.y, p.x);
                done.incrementAndGet();
            }
        });
        t1.start();
        t2.start();
        for (int round = 1; round <= ROUNDS; round++) {
            for (int i = 0; i < BATCH; i++) pairs[i] = new Pair();
            done.set(0);
            start.set(round);
            while (done.get() != 2) Thread.onSpinWait();
            for (Pair p : pairs) histogram[p.r1 * 2 + p.r2]++;
        }
        t1.join();
        t2.join();
        System.out.printf("%-16s (0,0)=%d  (0,1)=%d  (1,0)=%d  (1,1)=%d%n",
                mode, histogram[0], histogram[1], histogram[2], histogram[3]);
    }

    // 내 변수에 1을 쓰고, 상대 변수를 읽는다
    static int actor(String mode, AtomicInteger mine, AtomicInteger other) {
        switch (mode) {
            case "plain":           mine.setPlain(1);   return other.getPlain();
            case "release/acquire": mine.setRelease(1); return other.getAcquire();
            case "volatile":        mine.set(1);        return other.get();
            default:                mine.getAndAdd(1);  return other.get();
        }
    }
}

    메인 스레드가 결과를 읽어도 되는 근거는 이 회차의 도구 그대로다. 각 작업 스레드의 p.r1, p.r2 쓰기는 프로그램 순서상 done.incrementAndGet()보다 앞이고, 메인 스레드는 그 CAS 계열 연산이 쓴 값을 done.get()으로 읽은 뒤에 결과를 센다. 다음 라운드의 새 Pair도 start.set(round)라는 volatile 쓰기 앞에서 만들어지므로 작업 스레드에게 안전하게 보인다.

    세 번 실행했을 때 release/acquire의 (0, 0)은 37266, 27750, 47944번이었고, volatile과 getAndAdd의 (0, 0)은 세 번 모두 0이었다. plain은 매번 절반이 훨씬 넘는 1500만~1800만 번이 (0, 0)이었다. 나머지 칸의 분포는 두 스레드가 얼마나 겹쳐 달렸느냐에 따라 실행마다 크게 달라진다. 이 결과를 읽는 방법은 분명히 해 두자. volatile 줄의 0은 실험이 증명한 것이 아니라 앞의 JLS 논증이 증명한 것이고, 실험은 그 논증과 어긋나지 않았을 뿐이다. 반대로 release/acquire 줄의 수만 번은, 명세가 허용하는 결과가 이 기계에서 실제로 일어난다는 것을 보여 준다. setRelease와 getAcquire를 "조금 싼 volatile"이라고 생각하고 이런 패턴에 쓰면 실제로 깨진다.

    x86에서 Release 쓰기와 Acquire 읽기에 아무 장벽이 필요 없는 것은 x86의 메모리 모델이 원래 강하기 때문이다. 인텔 개발자 매뉴얼 3권의 "Memory Ordering in P6 and More Recent Processor Families" 절이 정한 재배치 규칙에서 허용되는 것은 사실상 "뒤의 읽기가 앞의 다른 주소 쓰기보다 먼저 수행되는 것" 하나뿐이고, 이것이 정확히 저장 버퍼링이다. 그래서 HotSpot은 volatile 쓰기 뒤에만 잠긴 명령 하나(lock addl)를 장벽으로 넣는다. 같은 매뉴얼은 읽기와 쓰기가 잠긴 명령을 넘어 재배치되지 않는다고 정하므로, lock cmpxchg와 lock xadd는 그 자체로 이 장벽 역할까지 한다. AArch64에서는 aarch64.ad의 주석이 volatile 읽기는 ldar, volatile 쓰기는 stlr 하나로 구현할 수 있다고 설명하고, 실제로 storeI_volatile 규칙은 stlrw, loadI_volatile 규칙은 ldarw를 내보낸다. volatile 쓰기 뒤에 별도의 장벽이 없어도 되는 것은 ARMv8이 Store-Release(stlr) 뒤의 Load-Acquire(ldar)가 그보다 앞서 관찰되지 않게 보장하기 때문이다. 반면 setRelease는 stlr을 쓰는 규칙의 조건(needs_releasing_store: 쓰기 뒤에 짝이 되는 장벽이 있을 것)을 만족하지 못해 dmb ish와 보통의 str이 되고, 보통의 str에는 그런 보장이 없다. 실험에서 본 수만 번의 (0, 0)은 이 차이와 맞아떨어진다.

    그렇다면 약한 모드는 언제 쓰는가. "Release 쓰기로 데이터를 내놓고 Acquire 읽기로 받아 가는" 한 방향의 전달만 필요하고, 위와 같은 쓰고-나서-읽기의 대칭 패턴이 없다는 것을 증명할 수 있을 때다. JDK 자신도 그렇게 쓴다. 다음 절의 Striped64는 셀과 base의 갱신에 weakCompareAndSetRelease를 쓴다. 증명할 자신이 없으면 기본 메서드(volatile 모드)를 쓰는 것이 맞다. 이 회차의 스핀 락이 올바른 근거도 volatile 모드의 compareAndSet과 set에 있었다.

    LongAdder의 안쪽: Striped64의 셀 배열과 @Contended

    캐시 일관성 절에서 LongAdder는 경합이 생기면 변수 집합을 늘린다는 Javadoc의 설명까지만 보았다. 실제로 어떻게 늘리는지는 부모 클래스인 패키지 전용 java.util.concurrent.atomic.Striped64에 있다(LongAccumulator, DoubleAdder, DoubleAccumulator도 같은 부모를 쓴다). 이 클래스는 이 회차에서 본 도구, 즉 CAS 재시도, 약한 CAS, CAS로 만든 스핀 락을 한곳에서 모두 쓴다. 필드는 셋이다. 경합이 없을 때 쓰는 volatile long base, 경합이 생기면 만드는 volatile Cell[] cells, 그리고 표를 만들거나 늘릴 때 쓰는 스핀 락 volatile int cellsBusy다. LongAdder.add의 빠른 경로는 다음과 같다.

    public void add(long x) {
    Cell[] cs; long b, v; int m; Cell c;
    if ((cs = cells) != null || !casBase(b = base, b + x)) {
        int index = getProbe();
        boolean uncontended = true;
        if (cs == null || (m = cs.length - 1) < 0 ||
            (c = cs[index & m]) == null ||
            !(uncontended = c.cas(v = c.value, v + x)))
            longAccumulate(x, null, uncontended, index);
    }
}

    한 줄씩 보자. 셀 표가 아직 없으면 base에 CAS를 한 번 한다. 성공하면 끝이다. 경합이 없는 동안 LongAdder는 CAS 한 번으로 끝난다는 점에서 AtomicLong과 같다. base의 CAS가 실패했다는 것, 즉 다른 스레드와 부딪쳤다는 사실이 표를 쓰기 시작하는 신호다. 표가 있으면 스레드마다 다른 해시값인 프로브(probe)로 칸을 고른다. 프로브는 Thread 객체의 threadLocalRandomProbe 필드에 있고 ThreadLocalRandom이 관리한다. 고른 칸의 셀에 CAS를 해서 성공하면 끝이고, 칸이 비어 있거나 CAS가 실패하면 longAccumulate로 넘어간다. 주석에 따르면 표의 크기는 처음 경합 때 2로 만들어지고, 경합이 계속되면 CPU 수 이상인 가장 가까운 2의 거듭제곱에 이를 때까지 두 배씩 늘어난다(NCPU = Runtime.getRuntime().availableProcessors()). 상한에 이른 뒤에 충돌하면 표를 늘리는 대신 xorshift로 그 스레드의 프로브를 바꿔 다른 칸을 찾는다.

    cellsBusy는 이 회차에서 만든 CasSpinLock과 같은 구조의 락이다. casCellsBusy()가 CELLSBUSY.compareAndSet(this, 0, 1)로 잡고, finally에서 volatile 필드에 cellsBusy = 0을 써서 놓는다. CAS로 획득하고 volatile 쓰기로 해제하니, 앞에서 따진 happens-before 논증이 그대로 적용된다. 다른 점은 기다리는 방식이다. 클래스 주석은 막는 락이 필요 없다고, 락을 잡을 수 없으면 스레드는 다른 칸이나 base를 시도한다고 적는다. 실제로 longAccumulate는 cellsBusy가 잡혀 있으면 그 자리에서 돌며 기다리지 않고 프로브를 바꾸거나 base에 CAS를 시도한다. 스핀 락의 약점인 "기다리는 동안 코어를 버리는 일"을, 기다리는 대신 다른 곳에 더하는 것으로 피한 셈이다.

    셀 하나는 volatile long value 필드 하나뿐인 작은 클래스인데, @jdk.internal.vm.annotation.Contended가 붙어 있다. 주석의 설명은 이렇다. 대부분의 원자 객체는 메모리에 흩어져 있어 서로 방해하지 않으므로 채워 넣기(padding)가 과하지만, 배열에 담긴 원자 객체는 메모리에서 서로 붙어 놓이기 쉽고, 그러면 대부분 같은 캐시 라인을 나눠 쓰게 되어 성능에 큰 손해를 본다. 서로 다른 변수인데 같은 캐시 라인에 있어서, 한 코어의 쓰기가 다른 코어의 사본을 무효화하는 현상을 거짓 공유(false sharing)라고 한다. HotSpot의 fieldLayoutBuilder.cpp는 @Contended가 붙은 클래스의 필드 앞에 ContendedPaddingWidth 바이트의 패딩 블록을 넣고, 필드 뒤에도 같은 크기의 꼬리 패딩을 넣는다. 이 플래그의 기본값은 128이고, 이 원고의 환경에서도 128이었다. 이 애너테이션은 java.base의 내부 패키지에 있고, 신뢰된 클래스에만 허용한다는 RestrictContended 플래그도 기본값이 true다.

    CAS 락 구현 1: 검사와 설정을 나누면 생기는 일

    락의 핵심은 "비어 있으면 내가 잡는다"는 동작이다. 이것을 그대로 코드로 옮기면 다음과 같은 락이 된다. 잠겨 있으면 다시 확인하기를 반복하며 기다리므로, 이런 락을 스핀 락(spin lock)이라고 한다. 가시성 문제를 피하려고 locked는 volatile로 선언했다. 문제를 잘 드러내기 위해 검사와 설정 사이를 100ms 벌려 두었다.

    public class NaiveSpinLock {
    private volatile boolean locked = false;

    public void lock() {
        log("락 획득 시도");
        while (true) {
            if (!locked) {          // 1. 검사: 비어 있나?
                sleep(100);         //    검사와 설정 사이를 일부러 벌린다
                locked = true;      // 2. 설정: 내가 잡는다
                break;
            }
            // 이미 잠겨 있으면 다시 확인한다
        }
        log("락 획득 완료");
    }

    public void unlock() {
        locked = false;
        log("락 반납 완료");
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); }
    }

    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }
}
    public class NaiveSpinMain {
    public static void main(String[] args) throws InterruptedException {
        NaiveSpinLock lock = new NaiveSpinLock();
        Runnable task = () -> {
            lock.lock();
            try {
                NaiveSpinLock.log("임계 영역 시작");
                NaiveSpinLock.sleep(500);
                NaiveSpinLock.log("임계 영역 끝");
            } finally {
                lock.unlock();
            }
        };
        Thread a = new Thread(task, "A");
        Thread b = new Thread(task, "B");
        a.start(); b.start(); a.join(); b.join();
    }
}

    고치는 방법도 같다. 검사와 설정을 CAS 하나로 붙이면 된다. "false이면 true로 바꾼다"는 동작이 하나의 원자적 단계가 되면, 두 스레드가 동시에 시도해도 성공하는 쪽은 정확히 하나다.

    import java.util.concurrent.atomic.AtomicBoolean;

public class CasSpinLock {
    private final AtomicBoolean locked = new AtomicBoolean(false);

    public void lock() {
        log("락 획득 시도");
        while (!locked.compareAndSet(false, true)) {
            log("락 획득 실패 - 스핀 대기");
        }
        log("락 획득 완료");
    }

    public void unlock() {
        locked.set(false);
        log("락 반납 완료");
    }

    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }
}
    public class CasSpinMain {
    public static void main(String[] args) throws InterruptedException {
        CasSpinLock lock = new CasSpinLock();
        Runnable task = () -> {

                lock.unlock();

    첫 번째 실행에서는 A가 먼저 CAS에 성공했고, B는 A가 락을 놓을 때까지 CAS 실패를 반복하다가 A의 반납 직후 성공했다. "스핀 대기" 줄이 몇 번 찍히는지는 실행마다 다르다. 각 스핀에서 System.out.println을 호출하는데 이 출력이 상대적으로 느려서 스핀 횟수가 적게 보일 뿐, 출력이 없으면 같은 시간 동안 CAS를 훨씬 많이 반복한다.

    두 번째 실행은 언뜻 이상해 보인다. A가 "락 반납 완료"를 찍기 전에 B가 "락 획득 완료"를 찍었다. 락이 깨진 것일까. unlock()을 다시 보면, locked.set(false)로 락을 먼저 놓고 그다음에 로그를 찍는다. A가 락을 놓은 순간과 A의 로그가 찍히는 순간 사이에 B가 CAS에 성공하고 자기 로그를 먼저 찍은 것이다. 임계 영역 실행은 여전히 겹치지 않았다. A의 "임계 영역 실행"이 B의 "락 획득 완료"보다 앞에 있다. 로그의 순서는 사건의 순서가 아니라 "로그 문장이 실행된 순서"라는 점을 보여 주는 예다. 동시성 버그를 로그로 추적할 때 이 차이를 놓치면 엉뚱한 결론을 내리게 된다.

    이 락이 임계 영역 안의 데이터에 대해서도 올바른 이유를 메모리 모델로 확인해 두자. A가 임계 영역에서 공유 데이터에 쓴 내용은 프로그램 순서상 A의 locked.set(false)보다 앞이다. set은 volatile 쓰기다. B의 compareAndSet(false, true)는 volatile 읽기의 의미로 그 false를 읽고 성공한다. JLS 17.4.5의 규칙에 따라 volatile 쓰기는 그 값을 읽는 이후의 읽기보다 먼저 일어나고, happens-before는 이어지므로, A의 임계 영역 안의 쓰기는 B의 임계 영역보다 먼저 일어난다. synchronized에서 "모니터 해제가 다음 획득보다 먼저 일어난다"는 규칙이 하던 일을, 여기서는 volatile 쓰기와 CAS의 volatile 읽기가 한다. 원자성은 CAS가, 가시성은 CAS와 volatile 쓰기의 메모리 의미가 맡는다.

    CAS 락 구현 2: 기다리는 동안 무엇을 하는가

    스핀 락은 락을 기다리는 동안 스레드를 재우지 않는다. 계속 CAS를 시도하며 CPU 위에서 돈다. 이것이 스레드 상태에서 어떻게 보이는지 확인해 보자. 아래 프로그램은 세 가지 방식으로 기다리는 스레드를 동시에 만들고, 500ms 뒤에 각각의 상태를 출력한다.

    import java.util.concurrent.atomic.AtomicBoolean;
import java.util.concurrent.locks.ReentrantLock;

public class StateMain {
    public static void main(String[] args) throws InterruptedException {
        AtomicBoolean spin = new AtomicBoolean(true);           // main이 이미 잡은 상태
        ReentrantLock rlock = new ReentrantLock();
        Object monitor = new Object();
        rlock.lock();

        Thread spinner = new Thread(() -> {
            while (!spin.compareAndSet(false, true)) {
                Thread.onSpinWait();
            }
        }, "spinner");
        Thread parker = new Thread(rlock::lock, "parker");
        Thread blocker = new Thread(() -> { synchronized (monitor) { } }, "blocker");

        synchronized (monitor) {
            spinner.start();
            parker.start();
            blocker.start();
            Thread.sleep(500);
            System.out.println("spinner = " + spinner.getState());
            System.out.println("parker  = " + parker.getState());
            System.out.println("blocker = " + blocker.getState());
        }
        spin.set(false);
        rlock.unlock();
        spinner.join(); parker.join(); blocker.join();
    }
}
    spinner = RUNNABLE
parker  = WAITING
blocker = BLOCKED

    세 스레드 모두 락을 얻지 못해 기다리는 중이지만 상태는 셋 다 다르다. synchronized를 기다리는 blocker는 BLOCKED, ReentrantLock을 기다리는 parker는 LockSupport.park로 잠들어 WAITING이다(3~4회차, 7회차). 두 스레드는 운영체제 스케줄러의 실행 대상에서 빠져 있어서 CPU를 쓰지 않는다. 반면 CAS로 스핀하는 spinner는 RUNNABLE이다. 자바의 관점에서도 운영체제의 관점에서도 이 스레드는 "실행 중이거나 실행할 준비가 된" 스레드이고, 실제로 코어 하나를 차지하고 CAS를 계속 반복한다. 500ms 동안 이 코어는 아무 쓸모 있는 일도 하지 않았다.

    그렇다고 스핀이 언제나 나쁜 것은 아니다. 재우는 쪽에도 비용이 있다. 스레드를 재우면 운영체제는 그 스레드를 실행 대상에서 빼고 다른 스레드로 컨텍스트를 바꾼다. 락이 풀려 깨어날 때는 다시 실행 대상에 넣고, 차례가 오면 레지스터를 복원하고, 그사이 다른 스레드가 쓰면서 캐시에서 밀려난 데이터를 다시 불러와야 한다(1회차). 임계 영역이 명령 몇 개로 끝나서 락이 곧 풀린다면, 잠들고 깨는 데 드는 시간이 그냥 몇 번 더 CAS를 시도하는 시간보다 길다. 이 경우에는 스핀이 낫다. 반대로 임계 영역이 길거나 그 안에서 I/O나 sleep처럼 오래 걸리는 일을 하면, 스핀은 그 시간 내내 코어를 낭비한다.

    기다리는 스레드 수가 코어 수보다 많다위험: 스핀하는 스레드가 락을 가진 스레드의 실행 시간을 빼앗을 수 있다안전

    표의 셋째 줄은 특히 위험하다. 락을 가진 스레드가 타임 슬라이스를 다 써서 CPU에서 내려간 상태라면, 그 스레드가 다시 실행되어 락을 놓기 전까지는 모든 스핀이 헛수고다. 그런데 스핀하는 스레드들이 코어를 차지하고 있으니 락을 가진 스레드가 다시 실행될 기회는 오히려 줄어든다.

    스핀 반복문 안에서 쓸 수 있는 도구가 하나 있다. 자바 9에서 추가된 Thread.onSpinWait()다. Javadoc은 이 메서드를 "호출한 쪽이 다른 활동이 무언가를 할 때까지 잠시 진행할 수 없다"는 것을 런타임에 알리는 메서드로 설명한다. 스핀 반복의 매 회차에 호출하면 런타임이 그 반복을 더 효율적으로 처리할 수 있지만, 호출하지 않아도 코드의 정확성은 같다는 점도 함께 적혀 있다. 소스에서 이 메서드의 본문은 비어 있고 @IntrinsicCandidate만 붙어 있다. 실제 효과는 JIT가 무엇으로 바꾸느냐에 달렸다. OpenJDK 21의 x86 규칙 파일 x86.ad에서 OnSpinWait 노드는 pause 명령이 된다. 인텔이 스핀 대기 반복을 위해 마련한 힌트 명령이다. 반면 AArch64에서는 OnSpinWaitInst라는 진단용 옵션이 어떤 명령을 쓸지 정하는데, 이 원고의 환경에서 확인한 기본값은 none이었다. 즉 이 환경의 OpenJDK 21에서는 이 힌트가 아무 명령도 만들지 않는다. "힌트"라는 이름 그대로, 플랫폼마다 효과가 다르다.

    실제 락은 스핀과 파킹을 섞는다

    실무에서 쓰는 락은 둘 중 하나를 고르지 않고 둘을 섞는다. HotSpot의 synchronized를 구현하는 objectMonitor.cpp에는 "Adaptive spin-then-block"이라는 제목의 주석이 있다. 모니터를 얻지 못한 스레드는 곧바로 잠들지 않고 먼저 일정 시간 스핀(TrySpin)한다. 주석에 따르면 이 스핀 시간은 모니터마다 따로 관리되고 최근 스핀 시도의 성공률에 따라 늘었다 줄었다 하며, 대략 컨텍스트 스위칭 한 번 왕복하는 시간을 넘지 않도록 상한이 정해져 있다. 최근에 스핀으로 락을 얻은 적이 많으면 더 오래 스핀하고, 그렇지 않으면 빨리 포기하고 잠든다. 스핀으로 기다리는 비용이 재우는 비용을 넘지 않게 하려는 설계다.

    7회차의 ReentrantLock도 같은 구조다. OpenJDK 21에서 비공정 락의 첫 시도(NonfairSync.initialTryLock)는 compareAndSetState(0, 1), 즉 락 상태를 0에서 1로 바꾸는 CAS 하나다. 소스 주석은 이 첫 시도에 "first attempt is unguarded"라고 적어 두었다. 대기열이 있든 없든 일단 CAS부터 해 본다는 뜻이다. 공정 락(FairSync)은 같은 CAS를 하기 전에 기다리는 스레드가 있는지(hasQueuedThreads())를 먼저 확인한다. 첫 CAS가 실패하면 AbstractQueuedSynchronizer.acquire로 넘어가, 대기열의 꼬리를 CAS(casTail)로 바꿔 자신을 대기열에 넣고 LockSupport.park로 잠든다. 대기열 맨 앞의 스레드는 깨어난 뒤 다시 잠들기 전에 Thread.onSpinWait()를 섞어 가며 몇 번 더 시도하고, 그 횟수는 깨어날 때마다 (postSpins << 1) | 1로 1, 3, 7처럼 늘어난다. 결국 실무의 락은 "CAS로 빠르게 시도 → 잠깐 스핀 → 대기열에 넣고 파킹"이라는 층을 쌓은 것이고, 이 회차에서 만든 스핀 락은 그 첫 두 층만 떼어 낸 것이다.

    그래서 CasSpinLock은 원리를 보여 주는 예제일 뿐, 실제 코드에서 synchronized나 ReentrantLock 대신 쓸 물건이 아니다. 빠진 것을 꼽아 보면 그 이유가 분명해진다.

    • 재진입이 안 된다. 같은 스레드가 lock()을 두 번 부르면 두 번째 CAS는 영원히 실패한다. 락을 가진 스레드 자신이 그 락을 기다리며 영원히 스핀하는 자기 교착 상태가 된다. synchronized와 ReentrantLock은 소유 스레드와 재진입 횟수를 기록해 이를 허용한다(앞의 initialTryLock에서 getExclusiveOwnerThread() == current인 경우가 그 처리다).
    • 소유자를 확인하지 않는다. 락을 잡지 않은 스레드도 unlock()을 불러 남의 락을 풀 수 있다. ReentrantLock.unlock()은 이 경우 IllegalMonitorStateException을 던진다.
    • 공정성이 없다. 대기열이 없으므로 누가 먼저 기다렸는지와 무관하게 CAS 경주에서 이긴 스레드가 락을 얻는다. 운이 나쁜 스레드는 오래 굶을 수 있다.
    • 인터럽트와 시간 제한이 없다. 스핀 중인 스레드는 인터럽트되어도 반복문이 인터럽트 상태를 확인하지 않으므로 계속 돈다.
    • 조건 대기가 없다. 8~9회차의 wait/notify나 Condition에 해당하는 기능이 없다.

    흔한 오해와 함정

    "volatile을 붙였으니 ++도 안전하다"

    이 회차의 실험이 직접 반박했다. volatile은 각 읽기와 쓰기의 가시성과 순서를 보장하지만, 읽기와 쓰기 사이에 다른 스레드가 끼어드는 것은 막지 않는다. volatile 필드에 대한 ++, +=, 검사 후 설정은 모두 경합 조건이다. 쓰는 스레드가 하나뿐인 경우가 아니라면 AtomicInteger나 락이 필요하다.

    "AtomicInteger 안에는 숨은 락이 있다"

    소스와 기계어가 보여 주듯 AtomicInteger의 연산은 CPU의 원자 명령(lock xadd, lock cmpxchg, LSE의 cas와 ldadd)이나 그것을 반복하는 CAS 반복문이다. 스레드를 대기열에 넣거나 재우는 일은 없다. 다만 "락이 없다"가 "기다림이 없다"는 뜻은 아니다. 하드웨어는 같은 캐시 라인에 대한 원자적 연산을 한 번에 하나씩 처리하고, CAS 반복문은 경합 속에서 여러 번 재시도한다.

    "CAS는 언제나 락보다 빠르다"

    경합이 적고 갱신이 짧을 때는 대체로 그렇다. 그러나 경합이 심하면 재시도로 버려지는 계산이 늘어나고, 갱신 함수가 무거울수록 버려지는 일도 무거워진다. 그리고 CAS의 단위는 변수 하나다. 여러 변수가 함께 지켜야 하는 불변식이 있으면, 변수마다 원자 클래스를 쓰는 것으로는 부족하다. 아래 클래스는 하한과 상한을 각각 AtomicInteger로 들고, "하한은 상한보다 클 수 없다"는 불변식을 검사한다.

    import java.util.concurrent.atomic.AtomicInteger;

public class BrokenRange {
    private final AtomicInteger lower = new AtomicInteger(0);
    private final AtomicInteger upper = new AtomicInteger(10);

    // 불변식: lower <= upper
    public void setLower(int v) {
        if (v > upper.get()) throw new IllegalArgumentException("lower > upper");
        lower.set(v);
    }

    public void setUpper(int v) {
        if (v < lower.get()) throw new IllegalArgumentException("upper < lower");
        upper.set(v);
    }
}

    범위가 (0, 10)일 때 스레드 A가 setLower(5)를, 스레드 B가 setUpper(4)를 동시에 부른다고 하자. A가 5 > upper.get(), 즉 5 > 10을 검사해 통과한다. B가 4 < lower.get(), 즉 4 < 0을 검사해 통과한다. A가 lower를 5로, B가 upper를 4로 쓴다. 범위는 (5, 4)가 되어 불변식이 깨진다. 각 get과 set은 원자적이었지만, 다른 변수를 검사하고 이 변수를 쓰는 동작 전체는 원자적이지 않았다. 이럴 때는 두 메서드를 synchronized로 묶거나, 두 값을 하나의 불변 객체에 담아 그 참조 하나를 CAS로 바꾼다.

    import java.util.concurrent.atomic.AtomicReference;

public class Range {
    private record Bounds(int lower, int upper) {}

    private final AtomicReference bounds =
            new AtomicReference<>(new Bounds(0, 10));

    public void setLower(int v) {
        while (true) {
            Bounds cur = bounds.get();
            if (v > cur.upper()) throw new IllegalArgumentException("lower > upper");
            Bounds next = new Bounds(v, cur.upper());
            if (bounds.compareAndSet(cur, next)) return;
        }
    }

    public void setUpper(int v) {
        while (true) {
            Bounds cur = bounds.get();
            if (v < cur.lower()) throw new IllegalArgumentException("upper < lower");
            Bounds next = new Bounds(cur.lower(), v);
            if (bounds.compareAndSet(cur, next)) return;
        }
    }
}

    이제 검사의 근거가 된 cur가 그대로일 때만 새 범위가 반영된다. 앞의 시나리오에서 A와 B 중 먼저 CAS에 성공한 쪽이 범위를 바꾸면, 다른 쪽의 CAS는 실패하고 새 범위를 다시 읽어 검사하므로 예외를 던지게 된다. 여기서 주의할 점이 하나 있다. AtomicReference.compareAndSet은 equals가 아니라 ==, 즉 같은 객체인지를 비교한다(앞에서 본 VarHandle의 정의 그대로다). record는 값이 같으면 equals가 참이지만, bounds.compareAndSet(new Bounds(0, 10), ...)처럼 새로 만든 객체를 기대값으로 넘기면 값이 같아도 실패한다. 그래서 반드시 get()으로 읽은 그 참조를 기대값으로 넘긴다.

    "CAS가 실패하면 오류다"

    CAS의 실패는 예외 상황이 아니라 정상적인 신호다. "네가 읽은 뒤에 누군가 먼저 바꿨다"는 정보이고, CAS 반복문은 그 정보를 받아 다시 시도하도록 설계되어 있다. compareAndSet의 반환값을 무시하는 코드가 오히려 버그다. 반환값을 확인하지 않으면 실패한 갱신이 조용히 사라지는데, 이것은 이 회차 처음에 본 갱신 손실과 같은 결과다.

    정리: 원자성을 얻는 세 가지 길

    이 회차에서 얻은 것을 정리하자. 읽기-수정-쓰기를 여러 스레드가 동시에 하면 갱신이 사라진다. 이것을 막으려면 세 단계를 하나로 묶어야 한다. 묶는 방법은 크게 두 가지다. 락으로 다른 스레드를 세워 두거나, CPU의 원자 명령으로 검사와 쓰기를 붙이는 것이다.

    이 장의 핵심

    value++는 읽기·더하기·쓰기 세 단계여서, 두 스레드가 같은 값을 읽으면 하나의 증가가 덮어써져 사라진다. volatile은 각 단계를 보이게 할 뿐 묶지 못한다. CAS는 "내가 읽은 값이 그대로일 때만 쓴다"를 CPU 명령 하나(x86의 lock cmpxchg, AArch64 LSE의 cas)로 실행해, 끼어들기를 막는 대신 끼어들기를 감지하게 만든다. 실패한 쪽은 다시 읽고 다시 계산한다. 이 낙관적 재시도는 경합이 적을 때 락보다 싸지만, 경합이 심하면 재시도와 캐시 라인 이동으로 비싸진다. 그리고 실제 락(synchronized, ReentrantLock)도 내부에서는 CAS로 시작해 짧게 스핀한 뒤에야 잠든다.

    CAS는 이 권의 나머지에서도 계속 등장한다. 다음 회차의 동시성 컬렉션에서 ConcurrentHashMap은 비어 있는 버킷에 첫 노드를 넣을 때 락 대신 casTabAt이라는 CAS를 쓴다. 12~13회차의 ThreadPoolExecutor는 풀의 실행 상태와 작업 스레드 수를 AtomicInteger 하나(ctl)에 함께 담아 CAS로 바꾼다. 두 값을 정수 하나에 담는 것은, 위의 Range에서 두 값을 객체 하나에 담은 것과 같은 이유다. CAS가 한 번에 바꿀 수 있는 것은 변수 하나뿐이기 때문이다.
    원자적 연산
    다른 스레드가 볼 때 시작 전 상태나 완료 후 상태만 보이고 중간 상태는 보이지 않는 연산. 소스 코드의 한 줄이 원자적이라는 보장은 없다.
    갱신 손실
    value++의 getfield·iadd·putfield 사이에 다른 스레드가 같은 값을 읽고 덮어써서 증가가 사라지는 현상. 결과는 기대값보다 작은 쪽으로만 틀린다.
    volatile의 한계
    각 읽기·쓰기의 가시성과 순서(happens-before)를 보장할 뿐, 읽기-수정-쓰기 전체를 원자적으로 만들지 않는다. 쓰는 스레드가 하나일 때만 충분하다.
    CAS
    현재 값(목격값)이 기대값과 같을 때만 새 값으로 바꾸는 원자적 연산. volatile 읽기와 쓰기의 메모리 의미를 함께 가지며, x86의 lock cmpxchg, AArch64 LSE의 cas 같은 명령으로 실행된다.
    AtomicInteger의 구조
    private volatile int value를 감싸고 Unsafe로 원자 연산을 한다. incrementAndGet은 getAndAddInt를 부르고, C2는 이를 인트린식으로 바꿔 x86에서는 lock xadd 하나가 된다.
    CAS 재시도 반복문
    읽기 → 계산 → 조건부 반영을 성공할 때까지 반복하는 낙관적 방식. 경합이 심하면 재시도가 늘고, updateAndGet의 함수는 여러 번 호출될 수 있으므로 부수 효과가 없어야 한다.
    경합의 하드웨어 비용
    원자적 연산을 하는 코어는 캐시 라인을 독점해야 하므로, 여러 코어가 같은 변수를 두고 경합하면 라인이 코어 사이를 오간다. 경합이 심한 합계에는 LongAdder가 맞다.
    스핀 락
    CAS로 false → true를 시도하며 반복하는 락. 기다리는 스레드는 RUNNABLE로 코어를 쓰므로 아주 짧은 임계 영역에만 맞다. 실무의 락은 CAS 시도와 짧은 스핀 뒤에 파킹한다.
    접근 모드와 전체 순서
    setRelease/getAcquire는 짝 맞는 쓰기·읽기 사이의 순서만 주고, volatile 모드(set, get, compareAndSet)만 모든 연산의 전체 순서를 준다. 그래서 "쓰고 나서 상대를 읽는" 패턴에서 release/acquire는 (0, 0)을 허용하고, 실험에서도 실제로 나왔다. C2에서는 volatile 쓰기 뒤의 MemBarVolatile(StoreLoad 장벽) 하나가 둘을 가른다.

    요청 수를 세는 카운터가 가끔 실제보다 적게 나온다는 보고를 받았다고 하자. 필드에 volatile이 붙어 있고 count++로 증가시키고 있다면 원인은 이 회차의 갱신 손실이다. 이런 버그는 부하가 낮은 개발 환경에서는 잘 드러나지 않고, 여러 요청이 동시에 들어오는 운영 환경에서만 나타난다. AtomicLong으로 바꾸면 정확해진다. 수많은 스레드가 쉬지 않고 증가시키는 통계용 카운터이고 값은 가끔 읽기만 한다면 LongAdder가 경합을 덜 받는다. 반대로 "현재 값을 보고 다음 동작을 정해야 하는" 값, 예를 들어 순번 발급이나 재고 차감처럼 증가 결과를 바로 써야 하는 경우에는 LongAdder의 sum()이 원자적 스냅숏이 아니므로 맞지 않는다.

    1번. 세 CAS는 각각 원자적이므로 어떤 순서로 실행되든 한 번에 하나씩 일어난 것처럼 보인다. A가 B보다 먼저 실행되면 값은 11이 되고 B는 목격값 11 ≠ 10이라 실패한다. 이후 C가 실행되면 목격값 11이 기대값 11과 같으므로 12가 된다. C가 A보다 먼저 실행됐다면 C는 목격값 10 ≠ 11로 실패하므로 최종 값은 11이다. B가 A보다 먼저 실행되면 값은 20이 되고 A(기대값 10)와 C(기대값 11)는 모두 실패해 최종 값은 20이다. 따라서 가능한 최종 값은 12(A → C 순서로 둘 다 성공), 11(A만 성공, C가 A보다 먼저 실행됨), 20(B만 성공) 셋이다. A와 B는 같은 기대값을 갖고 있으므로 둘 중 정확히 하나만 성공한다. 이것이 CAS가 "같은 값을 본 경쟁자 중 하나만 이긴다"는 성질이다.

CAS에 실패한 스레드가 WAITING 상태로 잠들었다가 깨어나는 컨텍스트 스위칭 비용 때문이다. 스레드를 4개 만들고 시작하는 비용이 증가 연산 1억 번보다 크기 때문이다. 원자적 연산을 하려면 코어가 그 변수의 캐시 라인을 독점해야 해서, 연산마다 라인이 코어 사이를 오가며 결국 한 번에 하나씩 처리되기 때문이다. 같은 변수에 대한 원자적 연산은 그 캐시 라인을 독점한 코어에서만 일어나므로, 경합하면 라인이 코어 사이를 계속 오가고 연산은 직렬화된다. 스레드 하나일 때는 라인이 한 코어에 머물러 이 왕복이 없다. AtomicInteger에는 락으로 전환하는 기능이 없다(0번 오답). CAS에 실패한 스레드는 잠들지 않고 바로 재시도하며 RUNNABLE 상태를 유지한다(1번 오답). 스레드 4개를 만드는 비용은 수천만 번의 연산에 비해 작다(2번 오답). while (!locked.compareAndSet(false, true)) { }로 락을 잡고 locked.set(false)로 놓는 스핀 락에서, 앞 스레드가 임계 영역에서 쓴 데이터를 다음 스레드가 반드시 보게 되는 근거는? set(false)는 volatile 쓰기이고 CAS는 그 값을 volatile 읽기의 의미로 읽으므로, happens-before가 성립해 앞 스레드의 임계 영역 쓰기가 다음 스레드보다 먼저 일어난다. CAS는 원자적이므로 원자성이 가시성을 자동으로 보장한다. 스핀하는 스레드는 RUNNABLE 상태여서 다른 스레드의 쓰기를 즉시 본다. 보장되지 않는다. 임계 영역 안의 데이터도 모두 volatile로 선언해야 한다. JLS 17.4.5에 따라 volatile 쓰기는 그 값을 읽는 이후의 읽기보다 먼저 일어나고, 프로그램 순서와 이어져 앞 스레드의 임계 영역 안의 모든 쓰기가 다음 스레드의 임계 영역보다 먼저 일어난다. compareAndSet은 getVolatile/setVolatile의 메모리 의미를 가진다. 원자성과 가시성은 별개의 성질이며 이 경우 가시성을 주는 것은 CAS의 메모리 의미다(1번 오답). 스레드 상태는 메모리 가시성과 관계가 없다(2번 오답). happens-before가 이어지므로 임계 영역의 데이터까지 volatile일 필요는 없다(3번 오답). AtomicInteger x, y가 0에서 시작한다. 스레드 1은 x.setRelease(1); r1 = y.getAcquire();를, 스레드 2는 y.setRelease(1); r2 = x.getAcquire();를 실행한다. r1 == 0 && r2 == 0인 결과에 대한 설명으로 옳은 것은? 불가능하다. release/acquire는 volatile과 같은 순서 보장을 더 싸게 제공할 뿐이다. 가능하다. release/acquire는 짝이 맞는 쓰기와 읽기 사이의 순서만 보장하고 모든 연산의 전체 순서는 volatile 모드만 보장하므로, 뒤의 읽기가 앞의 쓰기보다 먼저 수행된 것처럼 보일 수 있다. 가능하다. getAcquire는 원자적이지 않아서 32비트 값이 찢어져 읽힐 수 있다. 불가능하다. AtomicInteger의 모든 메서드는 내부적으로 CAS를 쓰기 때문이다. VarHandle 문서에서 전체 순서는 Volatile 모드만의 성질이다. 이 저장 버퍼링 패턴에서 (0, 0)을 막으려면 앞의 쓰기와 뒤의 읽기 사이의 순서(StoreLoad)가 필요한데, release/acquire는 그것을 주지 않는다. 이 원고의 실험에서도 2천만 번 남짓 중 수만 번 나왔다. release/acquire는 volatile보다 약한 보장이지 같은 보장의 싼 판이 아니다(0번 오답). Opaque 이상의 모드는 비트 단위로 원자적이다(2번 오답). setRelease와 getAcquire는 CAS가 아니라 순서 제약이 붙은 보통의 쓰기와 읽기다(3번 오답).
    원자적 연산(atomic operation)
    다른 스레드가 볼 때 중간 상태 없이 시작 전 또는 완료 후 상태로만 관찰되는 연산.
    읽기-수정-쓰기(read-modify-write)
    값을 읽고 그 값을 근거로 새 값을 계산해 다시 쓰는 연산 형태. x++, 검사 후 설정이 대표적이며 각 단계 사이가 경합 조건의 틈이 된다.
    갱신 손실(lost update)
    두 스레드가 같은 값을 읽고 각자 계산한 결과를 써서, 한쪽의 갱신이 다른 쪽에 덮어써져 사라지는 현상.
    비교 후 교환(CAS, compare-and-swap)
    현재 값이 기대값과 같을 때만 새 값으로 바꾸는 원자적 연산. 자바에서는 compareAndSet, 하드웨어에서는 x86 lock cmpxchg, AArch64 LSE cas 등이다.
    목격값(witness value)
    CAS가 비교할 때 실제로 읽은 변수의 현재 값. compareAndExchange는 이 값을 돌려준다.
    약한 CAS(weak compare-and-set)
    목격값이 기대값과 같아도 가짜로 실패할 수 있는 CAS. 재시도 반복문 안에서 쓰며, 독점 적재/저장으로 CAS를 만드는 하드웨어에서 더 싸다.
    ABA 문제(ABA problem)
    값이 A에서 B로 갔다가 다시 A로 돌아오면 CAS가 그 변화를 알아채지 못하고 성공하는 문제. 버전 번호(스탬프)를 함께 비교해 해결한다.
    스핀 락(spin lock)
    락을 얻을 때까지 스레드를 재우지 않고 반복해서 획득을 시도하는 락. 대기 중인 스레드는 CPU를 계속 쓴다.
    락 프리(lock-free)
    어떤 스레드가 멈추거나 지더라도 시스템 전체로는 누군가 진행하는 것이 보장되는 성질. 개별 스레드의 완료 시간까지 보장하지는 않는다.
    인트린식(intrinsic)
    JVM이 특정 메서드의 자바 코드 대신 미리 준비한 기계어로 바꿔 넣는 처리. @IntrinsicCandidate로 표시된다.
    거짓 공유(false sharing)
    논리적으로 다른 변수가 같은 캐시 라인에 놓여, 한 코어의 쓰기가 다른 코어의 사본을 무효화하는 현상. Striped64의 Cell은 @Contended 패딩으로 이를 피한다.
    접근 모드(access mode)
    VarHandle과 원자 클래스가 제공하는 메모리 순서의 등급. Plain, Opaque, Acquire/Release, Volatile 순으로 강해지며, Volatile만 모든 연산의 전체 순서를 보장한다.
