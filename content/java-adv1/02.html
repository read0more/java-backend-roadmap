    실행 흐름을 하나 더 만든다는 것

    앞 회차에서 프로세스와 스레드를 나눠 보았다. 프로세스는 운영체제가 자원(메모리 주소 공간, 열린 파일)을 나눠 주는 단위이고, 스레드는 그 안에서 CPU를 배정받아 명령어를 실행하는 흐름이다. 한 프로세스 안의 스레드들은 주소 공간을 함께 쓰고, 운영체제의 스케줄러가 이 스레드들을 CPU 코어에 번갈아 올려 실행한다. 이 회차는 그 이론을 자바 코드로 옮긴다. 자바 프로그램에서 스레드 하나를 "만든다"는 말이 정확히 무엇을 만드는 일인지가 이 회차의 질문이다.

    지금까지 쓴 모든 자바 프로그램은 실행 흐름이 하나였다. java 명령으로 프로그램을 띄우면 JVM이 main 메서드를 호출하고, 그 안에서 부른 메서드는 모두 같은 흐름 위에서 차례로 실행된다. 메서드 A가 메서드 B를 부르면 B가 끝날 때까지 A는 다음 줄로 가지 못한다. 파일을 내려받는 동안 화면이 멈추고, 한 요청을 처리하는 동안 다음 요청이 기다리는 이유가 여기에 있다. 일을 동시에 진행하려면 이 흐름 자체를 하나 더 만들어야 한다.

    자바 언어 명세(JLS) 17장은 이 점을 분명하게 적어 둔다. 스레드는 Thread 클래스로 표현되고, 사용자가 스레드를 만드는 유일한 방법은 이 클래스의 객체를 만드는 것이며, 스레드는 그 객체의 start()가 호출될 때 시작된다. 이 짧은 규정 안에 이 회차 전체의 구조가 들어 있다. 객체를 만드는 단계와 시작하는 단계가 분리되어 있다는 점, 그리고 시작하는 방법은 start() 하나뿐이라는 점이다.

    이 분리는 세 개의 층으로 보면 이해하기 쉽다. 가장 위에는 자바 코드가 다루는 java.lang.Thread 객체가 있다. 그 아래에는 JVM이 스레드를 관리하려고 만드는 내부 자료 구조(HotSpot에서는 C++ 클래스 JavaThread)와 스레드마다 하나씩 생기는 JVM 스택이 있다. 가장 아래에는 운영체제 커널이 스케줄링하는 네이티브 스레드가 있다. new Thread()는 맨 위층의 객체만 만든다. 아래 두 층은 start()가 호출될 때 비로소 생긴다. 이 회차의 실험은 대부분 이 사실을 여러 각도에서 확인하는 일이다.

    첫 번째 스레드: Thread를 상속하고 start()를 부른다

    스레드를 만드는 첫 번째 방법은 Thread를 상속하고 run()을 재정의하는 것이다. run()은 새 스레드가 실행할 코드를 담는 자리다. 아래 예제는 run()에서 지금 이 코드를 실행하는 스레드의 이름을 찍는다. Thread.currentThread()는 이 메서드를 호출한 스레드 자신의 Thread 객체를 돌려주는 정적 메서드다.

    package create;

public class GreetingThread extends Thread {

    @Override
    public void run() {
        System.out.println(Thread.currentThread().getName() + ": run() 실행");
    }
}
    package create;

public class StartMain {

    public static void main(String[] args) {
        System.out.println(Thread.currentThread().getName() + ": main() 시작");

        GreetingThread t = new GreetingThread();
        System.out.println("생성 직후: name=" + t.getName() + ", state=" + t.getState());

        t.start();

        System.out.println(Thread.currentThread().getName() + ": main() 끝");
    }
}
    main: main() 시작
생성 직후: name=Thread-0, state=NEW
main: main() 끝
Thread-0: run() 실행

    한 줄씩 따라가 보자. 첫 줄의 main은 JVM이 main 메서드를 실행하려고 쓰는 스레드의 이름이다. 우리가 만든 적은 없지만, 자바 프로그램은 처음부터 이 스레드 하나를 가지고 시작한다. Thread API 문서는 JVM이 시작할 때 보통 데몬이 아닌 스레드 하나가 있고, 그것이 대개 애플리케이션의 main을 호출하는 스레드라고 설명한다.

    둘째 줄에서 new GreetingThread()가 만든 객체의 이름은 Thread-0이고 상태는 NEW다. 이름을 주지 않으면 Thread 생성자가 이름을 지어 준다. OpenJDK 21의 Thread.java를 보면 생성자에서 name이 null일 때 genThreadName()을 부르고, 이 메서드는 "Thread-" + ThreadNumbering.next()를 돌려준다. 번호는 JVM 전체에서 하나뿐인 정적 카운터에서 나오고, 이름을 직접 준 스레드는 이 카운터를 소비하지 않는다. 상태 NEW는 아직 시작하지 않은 스레드를 뜻한다. 이 시점의 t는 힙에 놓인 평범한 자바 객체일 뿐이고, 운영체제는 이 객체의 존재를 모른다.

    셋째 줄과 넷째 줄이 핵심이다. t.start()를 호출하면 새 스레드가 생기고, 그 스레드가 run()을 실행한다. 그런데 start()는 run()이 끝날 때까지 기다리지 않고 곧바로 돌아온다. 그 순간부터 main 스레드와 Thread-0은 서로 독립적으로 진행한다. 위 결과에서는 main() 끝이 먼저 찍혔지만, 이것은 이번 실행에서 그렇게 되었을 뿐이다. 운영체제가 두 스레드를 어떤 순서로 CPU에 올리느냐에 따라 Thread-0: run() 실행이 먼저 찍힐 수도 있다. 두 줄의 순서는 프로그램이 정하지 않는다.

    "실행 결과 (한 예)"라고 적은 출력은 실행할 때마다 순서가 달라질 수 있는 출력이다. 이 회차부터는 출력 순서가 보장되는지 아닌지를 늘 구분해서 읽어야 한다. 같은 스레드 안에서 찍은 줄끼리의 순서는 보장되고, 서로 다른 스레드가 찍은 줄 사이의 순서는 보장되지 않는다.

    여기서 첫 번째 원리가 나온다. 하나의 스레드 안에서는 코드가 적힌 순서대로 실행되지만, 서로 다른 스레드 사이의 실행 순서는 정해져 있지 않다. main 스레드 입장에서 main() 시작, 생성 직후, main() 끝은 언제나 이 순서로 찍힌다. Thread-0의 한 줄이 그 사이 어디에 끼어들지는 스케줄러가 정한다. 단, Thread-0의 줄이 생성 직후보다 먼저 찍히는 일은 없다. run()은 start()가 호출된 뒤에야 실행될 수 있고, start()는 생성 직후를 찍은 다음 줄에 있기 때문이다.

    스택은 스레드마다 하나씩 생긴다

    새 스레드가 생긴다는 것이 메모리에서는 무엇을 뜻할까. 자바 가상 머신 명세(JVMS) 2.5절은 런타임 데이터 영역을 두 부류로 나눈다. 하나는 스레드마다 따로 생기는 영역이고, 다른 하나는 모든 스레드가 공유하는 영역이다. JVMS 2.5.1은 JVM이 여러 실행 스레드를 동시에 지원할 수 있으며 각 스레드가 자기 pc(program counter) 레지스터를 가진다고 정한다. 2.5.2는 각 JVM 스레드가 자기만의 JVM 스택을 가지며, 이 스택은 스레드와 같은 시점에 만들어진다고 정한다. 반면 2.5.3의 힙은 모든 JVM 스레드가 공유하며, 모든 클래스 인스턴스와 배열이 여기서 할당된다.

    네이티브 메서드 스택스레드마다 하나(구현이 제공하는 경우)네이티브 메서드 실행에 쓰는 스택
    힙모든 스레드가 공유객체와 배열. Thread 객체 자신도 여기 있다
    메서드 영역모든 스레드가 공유클래스별 런타임 상수 풀, 필드와 메서드 정보, 바이트코드

    JVMS 2.6은 메서드가 호출될 때마다 새 프레임(frame)이 만들어지고, 메서드가 끝나면 그 프레임이 사라진다고 정한다. 프레임은 그것을 만든 스레드의 스택에 쌓이고, 한 스레드의 프레임에 담긴 지역 변수는 다른 스레드가 볼 수 없다. 따라서 "스레드를 하나 더 만든다"는 말은 메모리 관점에서 프레임을 쌓을 스택을 하나 더 만들고, 그 스택의 맨 아래에 run() 프레임을 놓는다는 뜻이다. main 스레드 스택의 맨 아래에는 main() 프레임이 있고, 새 스레드 스택의 맨 아래에는 run() 프레임이 있다. 두 스택은 서로 독립적으로 자라고 줄어든다.

    run()을 직접 부르면 스레드는 생기지 않는다

    처음 스레드를 배울 때 가장 흔한 실수는 start() 대신 run()을 부르는 것이다. 코드는 문제없이 컴파일되고, run() 안의 코드도 실행된다. 그래서 잘못을 알아채기 어렵다. 스택이 스레드마다 따로라는 사실을 이용하면 두 호출의 차이를 눈으로 확인할 수 있다. 예외 객체를 만들면 생성 시점의 호출 스택이 기록되므로, 이를 출력하면 지금 어느 스레드의 스택 위에 있는지가 보인다. 아래 예제는 이 방법으로 같은 run()을 두 가지 방식으로 실행해 본다.

    package create;

public class StackThread extends Thread {

    @Override
    public void run() {
        String who = Thread.currentThread().getName();
        new Throwable(who + "의 스택").printStackTrace(System.out);
    }
}
    package create;

public class RunVsStartMain {

    public static void main(String[] args) throws InterruptedException {

    두 번째 스택 트레이스는 다르다. 스레드 이름이 Thread-0이고, 스택에 프레임이 StackThread.run 하나뿐이다. main 프레임이 보이지 않는 이유는 이것이 main 스레드의 스택이 아니기 때문이다. start()가 새로 만든 스택의 맨 아래에 run()이 놓였다. 그 아래에는 JVM의 네이티브 코드가 있지만 자바 스택 트레이스에는 나오지 않는다. 같은 객체의 같은 메서드라도 어느 스레드가 실행하느냐에 따라 완전히 다른 스택 위에서 돈다.

    마지막 두 줄은 스레드의 일회성을 보여 준다. run()이 끝난 스레드의 상태는 TERMINATED이고, 여기에 다시 start()를 부르면 IllegalThreadStateException이 던져진다. API 문서는 스레드를 많아야 한 번 시작할 수 있고, 특히 종료된 스레드를 다시 시작할 수 없다고 정한다. OpenJDK 21의 구현은 이렇다.

    public void start() {
    synchronized (this) {
        // zero status corresponds to state "NEW".
        if (holder.threadStatus != 0)
            throw new IllegalThreadStateException();
        start0();
    }
}

private native void start0();

    threadStatus는 JVM이 직접 갱신하는 필드이고 0이 NEW를 뜻한다. 한 번 시작하면 이 값이 0이 아닌 값으로 바뀌고 다시는 0으로 돌아오지 않으므로 두 번째 start()는 반드시 실패한다. 메서드 전체가 synchronized (this) 안에 있는 것도 눈여겨볼 만하다. 두 스레드가 같은 Thread 객체에 동시에 start()를 불러도 검사와 시작이 한 덩어리로 실행되어 둘 중 하나만 성공한다. synchronized의 의미는 06회에서 자세히 다룬다. 실제 일은 네이티브 메서드 start0()이 한다. 이제 그 안으로 내려가 보자.

    한 층 아래: start()가 운영체제 스레드를 만들기까지

    여기서부터는 명세가 아니라 구현의 영역이다. JLS와 JVMS는 스레드가 운영체제 스레드와 어떻게 대응되어야 하는지 정하지 않는다. Thread API 문서도 플랫폼 스레드(platform thread)가 "보통" 커널 스레드에 1:1로 대응된다고만 적는다. 아래 내용은 OpenJDK 21(jdk21u 저장소)의 HotSpot 소스를 읽어 확인한 것이고, 다른 JVM 구현에서는 다를 수 있다.

    첫 연결 고리는 start0이라는 네이티브 메서드다. java.base 모듈의 네이티브 코드 Thread.c에는 자바 메서드 이름과 JVM 함수를 짝지은 표가 있고, 거기에 {"start0", "()V", (void *)&JVM_StartThread}라는 항목이 있다. 즉 start0()을 호출하면 HotSpot의 C++ 함수 JVM_StartThread(파일 prims/jvm.cpp)가 실행된다. 이 함수가 하는 일을 순서대로 정리하면 다음과 같다.

HotSpot 소스의 주석은 그 이유를 스레드가 출발한 뒤에는 그 스레드가 이미 어떤 상태(잠자기, 모니터 대기 등)에 있을지 알 수 없기 때문이라고 설명한다. 따라서 start()가 돌아온 뒤 getState()가 NEW를 돌려주는 일은 없다.

    넷째, 운영체제 스레드를 만드는 데 실패할 수 있다. 메모리가 부족하거나 프로세스당 스레드 수 한도에 걸리면 pthread_create가 실패하고, JVM_StartThread는 OutOfMemoryError를 던진다. 이때 메시지는 HotSpot 소스에 정의된 unable to create native thread: possibly out of memory or process/resource limits reached다. 힙이 넉넉한데도 OutOfMemoryError가 나는 상황이 있다는 것, 그리고 그 원인이 힙이 아니라 스레드라는 것을 이 메시지로 구별할 수 있다. 스레드 하나하나가 운영체제 자원과 스택 메모리를 차지하는 비싼 객체라는 사실은 12회의 스레드 풀이 존재하는 이유가 된다.

    부모 스레드가 start0, JVM_StartThread, pthread_create를 거쳐 새 운영체제 스레드를 만들고, 새 스레드가 초기화 후 신호를 받아 run()을 호출하는 순서를 보여 준다. HotSpot이 pthread_create로 만든 스레드가 아니라, java 런처가 이미 가지고 있던 네이티브 스레드를 JVM에 붙인 것이다(os::create_main_thread가 os::create_attached_thread를 부른다). 우리가 만든 스레드는 before start 다음에 started로 찍힌다. 이 줄은 부모 스레드가 pthread_create가 성공한 직후에 남기는 로그이고, 괄호 안은 pthread_create에 넘긴 속성이다. 소스에서 HotSpot이 직접 정하는 속성은 둘뿐이다. pthread_attr_setdetachstate(&attr, PTHREAD_CREATE_DETACHED)와 pthread_attr_setstacksize다. macOS의 pthread_attr_setdetachstate 매뉴얼은 분리된(detached) 스레드의 ID로는 pthread_join()을 쓸 수 없다고 적는다. 즉 자바의 Thread.join()은 운영체제의 pthread_join으로 구현된 것이 아니다. 어떻게 구현되는지는 다음 회차에서 본다.

    이 줄에서 스레드 이름이 worker가 아니라 Unknown thread로 찍힌 것도 우연이 아니다. HotSpot의 JavaThread::name()은 이름을 자바 Thread 객체에서 읽는데(get_thread_name_string), 아직 자바 객체와 연결되지 않아 threadObj()가 비어 있으면 기반 클래스 Thread::name()의 기본값을 돌려준다. 그 값이 "Unknown thread"다. 앞 절의 흐름에서 자바 객체와 JavaThread를 연결하는(set_threadOopHandles) prepare는 os::create_thread가 끝난 뒤에 온다. 로그의 이름 하나가 그 순서를 그대로 보여 준다. 다음 줄 Thread is alive는 새 스레드가 찍는다. thread_native_entry에서 이 로그는 부모의 출발 신호를 기다리는 반복문 바로 뒤에 있으므로, 이 줄이 찍혔다는 것은 부모가 Thread::start로 신호를 보냈다는 뜻이다. 그 뒤에 run()이 실행되고, run()이 끝나면 JavaThread exiting, 진입 함수가 돌아오면 Thread finished가 찍힌다.

    마지막 두 줄은 main()이 끝난 뒤의 일이다. 같은 tid 6147이 JVM에서 떨어졌다가(detaching) 곧바로 다시 붙는다. 런처 소스(libjli/java.c)의 LEAVE() 매크로는 DetachCurrentThread를 부른 다음 DestroyJavaVM을 부르고, HotSpot의 jni_DestroyJavaVM은 현재 스레드를 "DestroyJavaVM"이라는 이름으로 다시 붙인다. 뒤의 스레드 덤프 절에서 main과 같은 운영체제 번호를 가진 DestroyJavaVM 스레드를 보게 되는데, 그 스레드가 여기서 생긴다.

    로그에는 실패했을 때의 정보도 남는다. os::create_thread는 pthread_create가 EAGAIN을 돌려주면 세 번까지 다시 시도한다. macOS 매뉴얼에서 EAGAIN은 스레드를 하나 더 만들 자원이 없거나 프로세스의 스레드 수 한도를 넘는 경우다. 그래도 실패하면 HotSpot은 Failed to start thread ... pthread_create failed (EAGAIN)를 경고로 찍고, 같은 태그의 정보 수준 로그로 그 시점의 JVM 스레드 수, 자원 한도(rlimit), 메모리 정보를 덧붙인다. 앞 절에서 본 unable to create native thread 오류의 원인을 좁힐 때 -Xlog:os+thread를 켜 두면 이 정보를 얻을 수 있다.

    2MB를 예약하지만 2MB를 쓰지는 않는다

    로그의 stacksize: 2048k는 앞에서 본 ThreadStackSize(-Xss) 값이다. os::Posix::get_initial_stack_size가 자바 스레드에 이 값을 쓰고 페이지 크기의 배수로 올림한다. guardsize: 16k는 HotSpot이 정한 값이 아니라 macOS pthread가 스택 끝에 두는 보호 페이지의 기본 크기이고, 16KB는 이 컴퓨터의 페이지 크기(pagesize 명령의 출력 16384)와 같다.

    HotSpot은 그 위에 자기만의 보호 영역을 하나 더 만든다. 새 스레드가 자바 코드를 실행하기 전에 JavaThread::run()이 create_stack_guard_pages()를 불러, 스택의 낮은 주소 끝에 레드(red), 옐로(yellow), 예약(reserved) 영역을 접근 금지 상태로 만든다. 크기를 정하는 플래그는 StackRedPages=1, StackYellowPages=2, StackReservedPages=1인데, stackOverflow.cpp의 주석대로 이 값은 4KB 단위이고 실제 페이지 크기의 배수로 올림된다. 16KB 페이지에서는 세 영역이 각각 16KB가 되어 모두 48KB다. -Xlog:os+thread=debug로 실행하면 stack guard pages activated: 0x000000016db2c000-0x000000016db38000 같은 줄이 찍히는데, 두 주소의 차이 0xC000이 정확히 48KB다(주소는 실행마다 다르다). stackOverflow.hpp의 설명에 따르면 JVM은 스택 포인터보다 앞쪽 메모리를 미리 건드려(stack banging) 보고, 옐로 영역에 닿으면 StackOverflowError를 만들어 던지면서 예외 처리기가 돌 수 있게 옐로 영역의 보호를 잠시 푼다. 레드 영역에 닿으면 복구할 수 없는 상황으로 보고 오류 보고서를 남기며 JVM을 끝낸다. JVMS 2.5.2의 스레드별 StackOverflowError는 HotSpot에서 이렇게 스레드마다 있는 보호 페이지로 구현된다.

    그러면 스레드 하나는 메모리를 얼마나 쓸까. 60초를 자는 데몬 스레드를 0개와 200개 띄운 프로세스를 같은 컴퓨터에서 시작 몇 초 뒤 ps로 비교했다. 스레드 수와 VSZ는 여러 번 재도 거의 같았고, RSS는 각각 다섯 번 잰 값의 범위다.

    같은 실험을 Native Memory Tracking(-XX:NativeMemoryTracking=summary, jcmd PID VM.native_memory summary)으로 보면 macOS에서는 스레드 218개의 스택이 reserved=449080KB, committed=449080KB로 찍힌다. 예약한 만큼 모두 커밋된 것처럼 보이지만 실제 상주 메모리와는 맞지 않는다. OpenJDK 21의 os.cpp에서 리눅스와 윈도가 아닌 플랫폼의 os::committed_in_range는 주어진 범위 전체를 커밋된 것으로 돌려주기 때문이다. macOS에서 NMT의 스레드 스택 커밋 값은 실제 사용량으로 읽으면 안 된다.

    실행 순서는 누구도 약속하지 않는다

    첫 예제에서 main() 끝과 run() 실행의 순서가 정해져 있지 않다고 했다. 이것을 "대부분 이 순서이니 괜찮다"로 받아들이면 안 된다. 순서를 정하는 것은 운영체제 스케줄러이고, 스케줄러의 판단은 그 순간 실행 가능한 스레드 수, CPU 코어 수, 다른 프로세스의 부하, 타이머 인터럽트의 시점 같은 프로그램 바깥의 요인에 좌우된다. 개발자의 노트북에서는 천 번을 돌려도 같은 순서가 나오다가, 코어 수가 다른 서버에서 처음으로 다른 순서가 나올 수 있다. 실행 결과가 한 번 맞았다는 사실은 동시성 코드가 옳다는 증거가 되지 못한다.

    그렇다면 두 스레드 사이에 보장되는 것은 아무것도 없을까. 하나 있다. JLS 17.4.5는 어떤 스레드에 대한 start() 호출이 시작된 스레드의 모든 동작보다 먼저 일어난다(happens-before)고 정한다. 쉽게 말해 start()를 부르기 전에 부모 스레드가 해 둔 일은 새 스레드가 run()을 시작할 때 모두 반영되어 보인다. 앞의 예제에서 Thread-0의 출력이 생성 직후 줄보다 먼저 나올 수 없다고 한 것도, 생성자에서 정한 필드 값을 run()에서 믿고 읽을 수 있는 것도 이 규칙 덕분이다. 반대로 start() 이후에 부모가 바꾼 값은 이런 보장이 없다. "먼저 일어난다"의 정확한 의미와 CPU 캐시 때문에 값이 안 보이는 현상은 05회 메모리 가시성에서 다룬다.

    일상에서 가져온 비유주방장과 보조 요리사

    주방장(main)이 보조 요리사에게 레시피 카드(Runnable)를 건네며 "시작해"라고 말하는 장면을 생각해 보자. 카드를 건네기 전에 적어 둔 내용은 보조가 반드시 읽는다. 이것이 start()의 happens-before 보장이다. 그러나 말을 마친 뒤 주방장이 무엇을 먼저 하고 보조가 어느 재료부터 손질할지는 정해져 있지 않다. 이 비유는 한 사람이 한 번에 한 가지 일만 한다는 점에서 단일 코어의 스레드와 닮았지만, 실제 CPU에서는 운영체제가 한 사람의 일을 언제든 강제로 멈추고 다른 사람에게 자리를 넘긴다는 점에서 다르다.

    데몬 스레드: JVM은 언제 끝나는가

    첫 예제에서 main()이 먼저 끝났는데도 Thread-0의 출력은 정상적으로 찍혔다. main 메서드가 끝나면 프로그램도 끝난다고 생각했다면 이 결과가 이상해 보일 것이다. 프로그램의 끝을 정하는 것은 main 메서드가 아니라 살아 있는 사용자 스레드가 남았는가다. 이 규칙을 이해하려면 스레드를 두 종류로 나눠야 한다.

    JLS 12.8은 프로그램이 하나 이상의 실행 스레드로 이루어지고, 각 스레드는 데몬이 아닌 스레드(non-daemon thread, 흔히 사용자 스레드라고 부른다), 데몬 스레드(daemon thread), 종료 훅(shutdown hook) 중 하나라고 정한다. 그리고 프로그램이 끝나는 상황 중 첫 번째로 "데몬이 아닌 스레드가 모두 종료되고, 그 결과 JVM이 시작한 종료 훅이 있다면 그것도 모두 종료되었을 때"를 든다. Runtime 클래스 문서는 같은 내용을 종료 시퀀스(shutdown sequence)라는 이름으로 설명한다. 종료 시퀀스는 살아 있는 데몬이 아닌 스레드의 수가 처음으로 0이 될 때, System.exit나 Runtime.exit가 처음 호출될 때, 또는 운영체제의 신호 같은 외부 사건이 있을 때 시작된다.

    규칙에서 데몬 스레드는 아예 등장하지 않는다는 점이 핵심이다. 데몬 스레드가 몇 개 살아 있든 JVM의 종료를 막지 못한다. 그럼 종료 시점에 아직 일하던 데몬 스레드는 어떻게 될까. JLS 12.8은 프로그램이 끝날 때 아직 종료되지 않은 스레드는 데몬이든 아니든 더는 자바 코드를 실행하지 않으며, 현재 메서드는 정상적으로도 비정상적으로도 완료되지 않고, finally 절도 잡히지 않은 예외 처리기도 실행되지 않는다고 정한다. Runtime 문서는 여기에 try-with-resources로 연 자원도 닫히지 않는다는 점을 덧붙인다. 데몬 스레드는 정리할 기회 없이 그 자리에서 사라진다.

    package create;

public class DaemonMain {

    public static void main(String[] args) {
        boolean daemon = args.length > 0 && args[0].equals("daemon");

        Thread worker = new Thread(() -> {
            System.out.println("worker 시작, daemon=" + Thread.currentThread().isDaemon());
            try {
                Thread.sleep(2000);
                System.out.println("worker 2초 대기 끝");
            } catch (InterruptedException e) {
                System.out.println("worker 인터럽트");
            } finally {
                System.out.println("worker finally");
            }
        }, "worker");

        worker.setDaemon(daemon);
        worker.start();

        System.out.println("main 끝");
    }
}

    두 번째 생성자 인자 "worker"는 스레드 이름이다. Thread.sleep(2000)은 지금 스레드를 약 2초 동안 재우는 메서드이고, 이 메서드가 던질 수 있는 검사 예외 InterruptedException을 run() 밖으로 던질 수 없어서 try로 잡았다. 왜 던질 수 없는지는 다음 회차에서 메서드 재정의 규칙으로 설명한다.

    사용자 스레드로 실행하면 main이 끝난 뒤에도 JVM은 기다린다. 살아 있는 데몬이 아닌 스레드(worker)가 남아 있기 때문이다. worker가 2초를 자고 finally까지 마치면 그때 살아 있는 사용자 스레드 수가 0이 되고, 종료 시퀀스가 시작된다. 데몬으로 실행하면 main이 끝나는 순간 사용자 스레드가 하나도 남지 않으므로 JVM은 곧바로 종료 시퀀스에 들어간다. 이 실행에서는 worker 시작조차 찍히지 않았다. 새 스레드가 첫 줄을 출력하기 전에 JVM이 끝났다는 뜻이다. 실행에 따라 worker 시작 줄은 찍힐 수도 있다. 그러나 2초를 자는 동안 JVM이 끝나므로 worker finally는 찍히지 않는다. 앞에서 본 JLS 12.8의 규칙 그대로다.

    데몬 여부에는 몇 가지 규칙이 더 있다. 모두 OpenJDK 21의 API 문서와 소스로 확인한 것이다.

    • 시작 전에만 바꿀 수 있다. setDaemon은 스레드가 시작되기 전에 호출해야 하고, 살아 있는 스레드에 호출하면 IllegalThreadStateException이 던져진다. 소스는 if (isAlive()) throw new IllegalThreadStateException();이다. 운영체제 스레드가 이미 달리고 있는 상태에서 종료 규칙을 바꾸는 것을 허용하지 않는다.
    • 만든 스레드에게서 물려받는다. 플랫폼 스레드는 데몬 여부와 우선순위를 자기를 만든 스레드에게서 물려받는다. 생성자 소스는 parent.isDaemon()을 새 스레드의 초기값으로 쓴다. main 스레드는 데몬이 아니므로 main에서 만든 스레드는 기본적으로 사용자 스레드이고, 데몬 스레드 안에서 만든 스레드는 기본적으로 데몬이다.
    • 시작하지 않은 스레드는 종료를 막지 않는다. Thread 문서는 시작하지 않은 데몬이 아닌 스레드는 종료 시퀀스의 시작을 막지 않는다고 적는다. 종료 규칙이 세는 것은 Thread 객체가 아니라 살아 있는 스레드다.
    • 가상 스레드는 항상 데몬이다. Java 21에서 정식 기능이 된 가상 스레드(virtual thread)는 데몬 여부가 늘 true이고, setDaemon(false)를 부르면 IllegalArgumentException이 던져진다. 이 강좌의 고급 1편은 플랫폼 스레드를 다룬다.

    데몬 스레드는 "있으면 좋지만 프로그램의 끝을 붙잡을 만큼 중요하지는 않은" 일에 쓴다. 주기적으로 캐시를 비우거나 상태를 감시하는 보조 작업이 그런 예다. 반대로 파일 쓰기, 데이터베이스 기록, 메시지 전송처럼 중간에 끊기면 데이터가 망가지는 일은 데몬 스레드에 맡기면 안 된다. JVM이 끝날 때 그 스레드는 finally도 실행하지 못한 채 멈추기 때문이다.

    두 개의 타임라인을 위아래로 놓고, 사용자 스레드가 남아 있으면 JVM이 기다리고 데몬 스레드만 남으면 그 자리에서 끝난다는 차이를 보여 준다.     스레드 덤프로 JVM 안의 스레드 보기

    데몬 스레드는 우리가 만들지 않아도 이미 JVM 안에 여럿 있다. 이것을 직접 보려면 실행 중인 JVM의 스레드 덤프를 찍으면 된다. 아래 프로그램은 6초를 자는 사용자 스레드 worker를 띄우고 main은 2.5초 뒤에 끝난다. 실행 중에 다른 터미널에서 jcmd로 덤프를 두 번 찍었다. 한 번은 main이 살아 있을 때(1초 무렵), 한 번은 main이 끝난 뒤(4초 무렵)다.

    package create;

public class LingerMain {

    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            try {
                Thread.sleep(6000);
            } catch (InterruptedException e) {
                // 이 예제에서는 무시한다
            }
        }, "worker");
        worker.start();
        Thread.sleep(2500);
    }
}

Runtime 문서의 구현 노트는 그 역할을 설명한다. JVM을 띄운 네이티브 코드(java 런처)는 JNI 호출 API의 DestroyJavaVM 함수를 불러 JVM의 종료를 기다리고, 이 함수가 살아 있는 데몬이 아닌 스레드 수가 처음 0이 될 때 종료 시퀀스를 시작할 책임을 진다. DestroyJavaVM 스레드는 worker가 끝나기를 기다리는 중이다.

    HotSpot은 마지막 사용자 스레드를 어떻게 알아채는가

    JLS 12.8과 Runtime 문서는 "살아 있는 데몬이 아닌 스레드 수가 처음 0이 될 때"라는 조건만 정한다. 그 수를 누가 세고, 0이 된 것을 누가 알아채며, 남은 데몬 스레드를 어떻게 멈추는지는 구현의 몫이다. 아래는 OpenJDK 21의 runtime/threads.cpp와 runtime/javaThread.cpp에서 확인한 HotSpot의 방식이다.

    세는 쪽부터 보자. HotSpot에는 Threads::_number_of_non_daemon_threads라는 정적 카운터가 있다. start() 경로의 prepare 단계가 Threads_lock을 잡은 채 Threads::add를 부르면, 이 함수는 자바 Thread 객체의 데몬 필드를 읽어 데몬이 아니면 카운터를 하나 올린다. 스레드가 끝날 때는 JavaThread::exit가 다시 데몬 여부를 읽어 Threads::remove에 넘기고, 이 함수가 카운터를 하나 내린다. 데몬 여부가 등록할 때와 지울 때 똑같아야 카운터가 맞는다. setDaemon이 살아 있는 스레드에 대해 예외를 던지는 것은 API의 규약이기도 하지만, 이 카운터의 정합성을 지키는 장치이기도 하다. 시작하지 않은 Thread 객체가 종료를 막지 않는 이유도 여기서 분명해진다. Threads::add는 start() 안에서만 불리므로, 시작하지 않은 객체는 카운터에 아예 들어가지 않는다.

    알아채는 쪽은 앞에서 본 DestroyJavaVM 스레드다. 런처가 부른 jni_DestroyJavaVM은 Threads::destroy_vm()을 실행하고, 이 함수는 맨 처음에 다음과 같이 기다린다.

    void Threads::destroy_vm() {
  JavaThread* thread = JavaThread::current();
  ...
  bool daemon = java_lang_Thread::is_daemon(thread->threadObj());
  int expected = daemon ? 0 : 1;
  {
    MonitorLocker nu(Threads_lock);
    while (Threads::number_of_non_daemon_threads() > expected)
      // This wait should make safepoint checks, wait without a timeout.
      nu.wait(0);
  }
  ...
  // run Java level shutdown hooks
  thread->invoke_shutdown_hooks();

  before_exit(thread);

  thread->exit(true);
  ...

    DestroyJavaVM 스레드 자신도 데몬이 아닌 스레드로 붙어 있으므로 기다리는 기준은 1이다. 카운터가 1보다 크면 Threads_lock에서 시간 제한 없이 잠든다. 깨우는 것은 Threads::remove다. 데몬이 아닌 스레드를 지운 뒤 카운터가 1 이하가 되면 notify_all을 부른다. 앞의 덤프에서 DestroyJavaVM이 worker가 끝나기를 기다리고 있던 장면이 이 반복문이다. 다른 스레드가 0.1초마다 카운터를 확인하는 식의 폴링은 없다. 마지막 사용자 스레드가 끝나는 바로 그 순간 그 스레드가 기다리는 쪽을 깨운다.

    깨어난 뒤의 순서는 destroy_vm 위의 주석에 정리되어 있다. 먼저 invoke_shutdown_hooks가 자바 메서드 java.lang.Shutdown.shutdown()을 호출하고, 여기서 Runtime.addShutdownHook으로 등록한 종료 훅이 실행된다. JDK 21의 ApplicationShutdownHooks.runHooks는 등록된 훅 스레드를 모두 start()한 다음 하나씩 join()한다. 훅끼리도 동시에 돈다는 뜻이다. 이어서 before_exit가 VM 수준의 정리(소스 주석에 따르면 감시 스레드와 시그널 처리 스레드를 멈추고 JVMTI에 종료 이벤트를 알리는 일 등)를 하고, 이 스레드는 스레드 목록에서 빠진다. 그다음 VM 스레드(VM Thread)가 JVM 전체를 마지막 세이프포인트(safepoint)로 데려간 채 끝나는데, 이 세이프포인트는 다시는 풀리지 않는다. 소스의 주석은 그 결과를 이렇게 적는다. 자바 코드나 VM 코드를 실행하던 데몬 스레드는 세이프포인트에서 멈추고, 네이티브 코드를 실행하던 데몬 스레드는 네이티브에서 자바나 VM으로 돌아오는 경계에서 멈춘다. 그 뒤 destroy_vm이 돌아오면 런처가 프로세스를 끝내고, 멈춘 채 남아 있던 운영체제 스레드는 프로세스와 함께 사라진다.

    이것이 데몬 스레드의 finally가 실행되지 않는 구체적인 이유다. HotSpot은 데몬 스레드에 예외를 던지거나 스택을 풀어 주지 않는다. 그 자리에 세워 둔 채 다시 출발시키지 않을 뿐이다. 그리고 그 전까지, 즉 종료 훅이 도는 동안에는 데몬 스레드도 계속 달린다. Runtime 문서도 종료 훅이 종료 시퀀스 시작 시점에 살아 있던 데몬·비데몬 스레드와 동시에 실행된다고 적는다. 0.1초마다 한 줄씩 찍는 데몬 스레드와 0.35초 동안 자는 종료 훅으로 확인해 보자.

    package create;

public class HookMain {

            try {
                for (int i = 1; ; i++) {

    main이 끝나 사용자 스레드가 0이 되자 종료 훅이 시작되었고, 훅이 자는 동안 데몬 스레드는 tick 4, 5, 6을 계속 찍었다. 훅이 끝난 뒤에는 아무것도 찍히지 않았다. daemon 인터럽트도 daemon finally도 없다. 같은 프로그램을 -Xlog:os+thread로 실행하면 종료 훅 스레드에 대해서는 JavaThread exiting과 Thread finished가 찍히지만, ticker 스레드의 tid로는 끝났다는 줄이 끝내 찍히지 않는다. 앞의 소스대로 멈춘 채 프로세스와 함께 사라졌기 때문이다. 종료 훅 안에서 데몬 스레드가 일을 마치기를 기다리는 코드를 쓰면 이 사이에 정리할 기회를 줄 수 있지만, 그 시간만큼 JVM의 종료가 늦어진다는 점도 함께 생각해야 한다.

    System.exit로 끝나는 경로는 조금 다르다. destroy_vm 위의 주석은 두 경로가 완전히 같지는 않지만 자바 수준의 Shutdown.shutdown()과 VM 수준의 before_exit(), VM_Exit 연산을 공유한다고 설명한다. System.exit를 부르면 데몬이 아닌 스레드가 남아 있어도 종료 시퀀스가 시작되고, 종료 훅이 끝나면 그 사용자 스레드들도 데몬 스레드와 마찬가지로 더는 자바 코드를 실행하지 못한다. Runtime 문서가 JVM이 끝날 때 데몬이든 아니든 모든 스레드가 즉시 자바 코드 실행을 멈춘다고 적은 것과 같은 이야기다.

    Runnable: 할 일과 실행하는 스레드를 나눈다

    Thread를 상속하는 방식에는 구조적인 문제가 있다. 자바 클래스는 하나의 클래스만 상속할 수 있으므로, Thread를 상속한 클래스는 다른 클래스를 상속할 수 없다. 더 근본적인 문제는 "무엇을 할 것인가"(작업)와 "어떻게 실행할 것인가"(스레드)가 한 클래스에 묶인다는 점이다. 같은 작업을 새 스레드가 아니라 현재 스레드에서, 또는 나중에 배울 스레드 풀에서 실행하고 싶어지면 작업 코드를 Thread에서 떼어 내야 한다.

    그래서 자바는 처음부터 작업만 표현하는 인터페이스를 두었다. java.lang.Runnable은 1.0부터 있었고, 메서드는 void run() 하나뿐이다. Java 8부터는 @FunctionalInterface가 붙어 람다로 만들 수 있다. Thread 자신도 Runnable을 구현한다. 그리고 Thread의 생성자 중 상당수가 Runnable을 받는다.

    package create;

public class PrintTask implements Runnable {

    @Override
    public void run() {
        String who = Thread.currentThread().getName();
        new Throwable(who + "의 스택").printStackTrace(System.out);
    }
}
    package create;

public class RunnableMain {

    public static void main(String[] args) {
        Runnable task = new PrintTask();
        Thread t = new Thread(task);
        t.start();
    }
}

	at create.PrintTask.run(PrintTask.java:8)
	at java.base/java.lang.Thread.run(Thread.java:1583)

    이번 스택에는 프레임이 둘이다. 맨 아래가 Thread.run이고 그 위가 PrintTask.run이다. 앞에서 본 대로 JVM은 새 스레드에서 언제나 Thread 객체의 run()을 가상 호출한다. 이번에는 Thread를 상속하지 않았으므로 재정의되지 않은 Thread.run() 자체가 실행되고, 이 메서드가 생성자로 받은 작업을 대신 실행한다. OpenJDK 21의 소스는 다음과 같다.

    @Override
public void run() {
    Runnable task = holder.task;
    if (task != null) {
        Object bindings = scopedValueBindings();
        runWith(bindings, task);
    }
}

@Hidden
@ForceInline
final void runWith(Object bindings, Runnable op) {
    ensureMaterializedForStackWalk(bindings);
    op.run();
    Reference.reachabilityFence(bindings);
}

    생성자로 받은 Runnable은 holder.task라는 final 필드에 저장된다. holder는 플랫폼 스레드용 필드를 모아 둔 내부 객체(FieldHolder)로, 스레드 그룹, 작업, 스택 크기, 우선순위, 데몬 여부, 그리고 start()에서 본 threadStatus가 여기 있다. run()은 작업이 있으면 runWith를 거쳐 task.run()을 부르고, 없으면 아무것도 하지 않는다. 스택 트레이스에서 runWith 프레임이 보이지 않는 이유는 이 메서드에 붙은 JDK 내부 애너테이션 @Hidden 때문이다. 출력의 Thread.java:1583은 실험한 JDK 21.0.13 소스에서 runWith(bindings, task)를 부르는 줄의 번호이며, JDK 버전이 바뀌면 달라질 수 있다. scopedValueBindings는 Java 21에서 미리 보기(preview) 기능이었던 스코프 값(scoped value)을 위한 장치로, 이 회차의 범위 밖이다.

    정리하면 Thread를 상속하는 방식과 Runnable을 넘기는 방식은 같은 장치의 두 가지 사용법이다. JVM은 어느 경우든 Thread.run()을 부른다. 상속 방식은 그 메서드를 재정의해 작업을 직접 넣고, Runnable 방식은 재정의하지 않은 기본 run()이 필드에 담긴 작업에 일을 넘긴다. 이 차이는 설계에서 큰 차이를 만든다.

    상속다른 클래스를 상속할 수 없다다른 클래스를 상속하면서 구현할 수 있다
    작업과 실행의 관계작업 객체가 곧 스레드다작업 객체를 어느 실행 수단에든 넘길 수 있다(새 스레드, 현재 스레드, 스레드 풀)
    한 작업을 여러 스레드가스레드마다 객체가 따로 있어야 한다작업 인스턴스 하나를 여러 Thread에 넘길 수 있다
    재사용스레드는 한 번만 시작되므로 객체도 일회용이다작업 객체는 몇 번이든 다시 넘길 수 있다

    마지막 줄이 특히 중요하다. 스레드는 한 번 끝나면 다시 시작할 수 없지만 Runnable은 그런 제약이 없다. 12회에서 다룰 ExecutorService는 바로 이 성질을 이용한다. 스레드 몇 개를 미리 만들어 두고, 작업(Runnable이나 Callable)만 계속 받아서 이미 만든 스레드에게 실행시킨다. 작업과 스레드를 분리해 두지 않았다면 불가능한 구조다. 실무에서 Thread를 상속하는 코드를 보기 어려운 이유도 여기에 있다.

    둘을 섞으면 어떻게 될까. Thread의 하위 클래스가 run()을 재정의하면서 생성자에 Runnable도 넘기면, JVM이 가상 호출로 고르는 것은 하위 클래스의 run()이다. 재정의한 run()이 super.run()을 부르지 않는 한 넘긴 작업은 실행되지 않는다. 실제로 new Thread(() -> System.out.println("task")) { public void run() { System.out.println("subclass run"); } } 형태의 객체를 시작하면 subclass run만 찍힌다. 이 결과는 앞의 두 소스 발췌만으로 예측할 수 있다.

    스레드 이름을 남기는 로거 만들기

    여러 스레드가 동시에 출력하기 시작하면 어느 줄을 누가 찍었는지, 언제 찍었는지가 중요해진다. 매번 Thread.currentThread().getName()을 문자열에 붙이는 것은 번거롭고 빠뜨리기 쉽다. 이 강좌의 이후 예제에서 함께 쓸 작은 출력 도구를 하나 만든다. 시각, 스레드 이름, 메시지를 한 줄에 찍는다.

    package util;

import java.time.LocalTime;
import java.time.format.DateTimeFormatter;

public final class ThreadLog {

    private static final DateTimeFormatter TIME = DateTimeFormatter.ofPattern("HH:mm:ss.SSS");

    private ThreadLog() {
    }

    public static void log(Object message) {
        String now = LocalTime.now().format(TIME);
        String thread = Thread.currentThread().getName();
        System.out.printf("%s [%9s] %s%n", now, thread, message);
    }
}

    설계에서 생각한 점을 짚어 보자. 클래스를 final로 하고 생성자를 private으로 막은 것은 정적 메서드만 가진 도구 클래스라서 객체를 만들 이유가 없기 때문이다. DateTimeFormatter를 정적 상수 하나로 두고 모든 스레드가 함께 쓰는 것은 이 클래스가 불변(immutable)이고 스레드 안전(thread-safe)하다고 API 문서에 명시되어 있어서 가능한 선택이다. 여러 스레드가 동시에 접근할 객체를 고를 때는 언제나 이 성질을 확인해야 한다. 예를 들어 예전 API인 SimpleDateFormat은 문서에 동기화되지 않는다고 적혀 있어 같은 방식으로 공유하면 안 된다. %9s는 스레드 이름을 9칸 오른쪽 정렬로 맞춰 줄이 가지런해지게 한다. 메시지 인자를 Object로 받은 것은 문자열이 아닌 값도 그대로 넘기기 위해서다. printf의 %s가 toString()을 불러 준다.

    정적 메서드를 import static util.ThreadLog.log;로 가져오면 호출 쪽에서 log("...")만 쓰면 된다. 아래 예제는 이 로거로 두 작업 스레드가 숫자를 세게 한다.

    package create;

import static util.ThreadLog.log;

public class CountTask implements Runnable {

    private final String label;

    public CountTask(String label) {
        this.label = label;
    }

    @Override
    public void run() {
        for (int i = 1; i <= 3; i++) {
            log(label + " " + i);
        }
    }
}
    package create;

        Thread b = new Thread(new CountTask("B"), "worker-B");
        a.start();
        b.start();
        log("main() 끝");
    }
}

OpenJDK 21의 PrintStream은 println이나 printf 한 번의 호출 전체를 락으로 감싸서 실행한다(System.out 같은 일반 PrintStream은 기본적으로 JDK 내부 락을, 하위 클래스는 synchronized (this)를 쓴다). 그래서 한 번의 호출로 찍은 한 줄은 다른 스레드의 출력에 쪼개지지 않는다. 다만 이것은 API 문서가 약속하는 동작이 아니라 구현의 성질이며, 한 줄을 여러 번의 print로 나눠 찍으면 그 사이에 다른 스레드의 출력이 끼어들 수 있다.

    여러 스레드 만들기

    스레드를 여러 개 만드는 것은 앞의 과정을 반복하는 것이다. 다만 여러 스레드가 같은 객체를 받으면 무엇이 공유되고 무엇이 공유되지 않는지를 정확히 알아야 한다. 아래 예제는 Runnable 인스턴스 하나를 만들어 세 스레드에 똑같이 넘긴다.

    package create;

import static util.ThreadLog.log;

public class SharedTaskMain {

    public static void main(String[] args) {
        Runnable task = () -> {
            int local = 0;            // 이 변수는 실행하는 스레드의 스택에 생긴다
            for (int i = 0; i < 3; i++) {
                local++;
            }
            log("local=" + local);
        };
        for (int i = 0; i < 3; i++) {
            new Thread(task).start(); // 같은 task 인스턴스를 세 스레드가 공유한다
        }
    }
}
    01:42:19.744 [ Thread-2] local=3
01:42:19.744 [ Thread-1] local=3
01:42:19.746 [ Thread-0] local=3

    세 스레드 모두 local=3을 찍는다. 순서는 매번 달라도 값은 언제나 3이다. 작업 객체는 힙에 하나뿐이지만, run()이 호출될 때마다 그것을 실행하는 스레드의 스택에 새 프레임이 생기고, 지역 변수 local과 i는 그 프레임 안에 있다. 세 스레드는 같은 코드를 실행하지만 각자 자기 스택의 local을 증가시키므로 서로 간섭할 방법이 없다. 지역 변수는 그 자체로 스레드에 갇혀 있다.

    만약 local을 지역 변수가 아니라 작업 객체의 인스턴스 필드로 바꾸면 이야기가 완전히 달라진다. 필드는 힙의 객체 안에 하나만 있으므로 세 스레드가 같은 칸을 동시에 읽고 쓰게 된다. 이때 결과가 9가 될지, 그보다 작을지는 보장되지 않는다. 이것이 06회에서 다룰 경합 조건(race condition)이다. 지금은 "작업 인스턴스 하나를 여러 스레드에 넘기는 순간, 그 인스턴스의 필드는 공유 자원이 된다"는 경계만 그어 두자.

    이름을 지정하지 않은 세 스레드는 Thread-0, Thread-1, Thread-2가 되었다. 앞에서 본 정적 카운터가 생성 순서대로 번호를 매긴 것이다. 번호는 new Thread를 호출한 순서이지 실행된 순서가 아니므로, 출력에서 Thread-2가 먼저 나와도 이상할 것이 없다. 실무에서는 이름을 직접 붙이는 편이 좋다. 장애가 났을 때 스레드 덤프에 Thread-37이라고 찍힌 것보다 order-sync-1이라고 찍힌 것이 훨씬 많은 것을 알려 준다.

    여러 스레드를 다룰 때 알아 둘 것이 하나 더 있다. 한 스레드에서 잡히지 않은 예외는 그 스레드만 끝낸다. 아래 예제에서 작업 스레드는 예외를 던지고 죽지만, main은 그와 상관없이 다음 줄을 실행한다.

    package create;

public class FailMain {

    public static void main(String[] args) throws InterruptedException {
        Thread t = new Thread(() -> {
            throw new IllegalStateException("작업 실패");
        });
        t.start();
        t.join();
        System.out.println("main은 계속 실행된다. t.state=" + t.getState());
    }
}

    예외가 run() 밖으로 빠져나가면 JVM은 그 스레드의 잡히지 않은 예외 처리기(UncaughtExceptionHandler)를 부른다. 따로 지정하지 않았다면 스레드 그룹(ThreadGroup)이 그 역할을 맡는다. OpenJDK 21의 ThreadGroup.uncaughtException은 부모 그룹이 있으면 부모에게 넘기고, 최상위에서는 기본 처리기가 지정되어 있지 않을 때 System.err에 Exception in thread "이름"을 찍고 스택 트레이스를 출력한다. 위 출력의 첫 줄이 그것이다. 처리기가 끝나면 스레드는 종료된다. JLS 12.8이 스레드의 종료를 "run이 정상 완료되거나, 비정상 완료된 뒤 해당 잡히지 않은 예외 처리기가 완료될 때"라고 정의한 것과 정확히 맞물린다. 스택 트레이스의 lambda$main$0은 다음 절에서 설명할, 람다 본문을 담은 메서드의 이름이다.

    이 동작은 실무에서 조용한 장애의 원인이 된다. 예외가 표준 에러에 한 번 찍히고 스레드가 사라질 뿐, 다른 스레드는 아무 일도 없었다는 듯 계속 돈다. 로그 수집이 표준 에러를 놓치고 있다면 작업 스레드가 죽은 사실을 아무도 모를 수 있다. 작업 안에서 예외를 직접 잡아 기록하거나, setUncaughtExceptionHandler로 처리기를 지정하는 습관이 필요하다.

    Runnable을 만드는 여러 방법과 그 결과물

    Runnable을 만드는 방법은 넷이다. 최상위 클래스로 만들기, 다른 클래스 안에 정적 중첩 클래스(static nested class)로 만들기, 익명 클래스(anonymous class)로 만들기, 람다식(lambda expression)으로 만들기다. 앞의 둘은 클래스 파일이 하나씩 생기는 평범한 클래스다. 정적 중첩 클래스는 Outer$Task.class처럼 바깥 클래스 이름이 붙은 파일이 될 뿐, 바이트코드 수준에서는 최상위 클래스와 다를 것이 없다. 흥미로운 것은 뒤의 둘이다. 두 방식은 소스에서 비슷해 보이지만 컴파일러가 만드는 결과물이 전혀 다르다. 같은 지역 변수를 쓰는 두 작업을 만들어 비교해 보자.

    package create;

public class RunnableWays {

    public static void main(String[] args) {
        String msg = "hello";

        Runnable anonymous = new Runnable() {
            @Override
            public void run() {
                System.out.println("anonymous: " + msg);
            }
        };

        Runnable lambda = () -> System.out.println("lambda: " + msg);

        new Thread(anonymous).start();
        new Thread(lambda).start();

        System.out.println(anonymous.getClass().getName());
        System.out.println(lambda.getClass().getName() + " hidden=" + lambda.getClass().isHidden());
    }
}

    익명 클래스Outer$1.class컴파일러가 만든 val$이름 필드에 복사익명 클래스의 인스턴스
    람다클래스 파일 없음. 본문은 lambda$메서드$번호 메서드, 실행 시 숨은 클래스 생성본문 메서드의 매개변수로 전달바깥 클래스의 인스턴스(람다 자신이 아니다)

    표의 마지막 열은 람다가 새 스코프를 만들지 않는다는 JLS 15.27.2의 규칙에서 나온다. 익명 클래스 안의 this는 익명 클래스 객체를 가리키지만, 람다 본문의 this는 람다를 감싼 바깥 객체를 가리킨다. 스레드 작업 안에서 this의 필드를 쓰는 코드라면 이 차이가 "어느 객체의 필드가 공유되는가"를 바꾼다는 점을 기억해 두자.

    람다 객체는 언제, 몇 개 만들어지는가

    앞 절에서 람다는 invokedynamic과 LambdaMetafactory로 실행 시점에 연결된다고 했다. 이 연결이 언제 몇 번 일어나는지, 그리고 연결된 결과로 생기는 객체가 무엇을 가지는지를 알면 "람다를 스레드에 넘긴다"는 일이 메모리에서 정확히 무엇인지 보인다. 캡처하지 않는 람다와 캡처하는 람다를 돌려주는 메서드를 각각 두 번씩 불러 비교해 보자.

    package create;

public class LambdaIdentity {

    static Runnable noCapture() {
        return () -> System.out.println("no capture");
    }

    static Runnable capture(String msg) {
        return () -> System.out.println(msg);
    }

    public static void main(String[] args) {
        System.out.println("noCapture 같은 객체? " + (noCapture() == noCapture()));
        System.out.println("capture   같은 객체? " + (capture("a") == capture("a")));
        System.out.println("capture   같은 클래스? " + (capture("a").getClass() == capture("b").getClass()));
    }
}

    이 부트스트랩 메서드는 몇 번 호출될까. JVMS 6.5의 invokedynamic 설명은 기호 참조가 "이 특정한 invokedynamic 명령에 대해" 해석되어 CallSite 객체를 얻고, 그 CallSite가 이 명령에 묶인다(bound)고 정한다. 묶인 뒤에 그 명령을 다시 실행하면 부트스트랩을 다시 부르지 않고 CallSite가 가리키는 대상 메서드 핸들만 호출한다. 그러니 부트스트랩은 람다를 평가할 때마다가 아니라 소스에 람다가 적힌 자리(호출 지점, call site)마다 한 번 실행된다. 정확히는, 아직 묶이지 않은 같은 명령을 여러 스레드가 동시에 처음 실행하면 부트스트랩이 여러 번 돌 수 있지만, java.lang.invoke 패키지 문서에 따라 JVM은 그중 하나의 결과만 골라 모든 스레드에 보이게 묶고 나머지 결과는 버린다. OpenJDK에서는 반복문 안의 람다 하나로 스레드를 천 개 만들어도 숨은 클래스는 하나다. 위 결과의 세 번째 줄이 이것을 보여 준다.

    객체의 수를 정하는 것은 그 대상 메서드 핸들이다. OpenJDK 21의 InnerClassLambdaMetafactory.buildCallSite()는 먼저 spinInnerClass()로 인터페이스를 구현하는 클래스의 바이트코드를 만들고, 이를 호출한 클래스의 숨은 네스트메이트(hidden nestmate)로 정의한다. 그다음 factoryType의 매개변수가 0개이면, 즉 캡처가 없으면, 그 자리에서 인스턴스를 하나 만들어 두고 늘 그 객체를 돌려주는 상수 핸들(MethodHandles.constant)로 ConstantCallSite를 만든다. 소스의 주석은 이를 캡처 없는 람다의 연결을 최적화하려고 인스턴스 하나를 미리 계산해 둔다고 설명한다. 매개변수가 있으면 생성자를 가리키는 핸들을 대상으로 삼으므로 평가할 때마다 새 객체가 생긴다. 첫 줄이 true, 둘째 줄이 false인 이유다.

    단, 이것은 구현의 선택이지 언어의 약속이 아니다. JLS 15.27.4는 람다식을 평가하면 새 인스턴스가 할당되거나 이미 있는 인스턴스가 참조된다고만 정하고, 그래서 람다 평가 결과의 동일성(identity)은 예측할 수 없으며 참조 비교(==), 객체 잠금(synchronized), System.identityHashCode 같은 동일성에 의존하는 연산은 구현에 따라, 같은 구현 안에서도 평가할 때마다 결과가 다를 수 있다고 명시한다. 여러 스레드가 람다 객체 자체를 락으로 쓰거나 맵의 키로 써서 "같은 작업"을 구별하는 코드는 이 규정 때문에 성립하지 않는다.

    람다 캡처와 반복문 변수

    여러 스레드를 반복문으로 만들 때 거의 반드시 한 번은 만나는 컴파일 오류가 있다. 반복 변수를 람다 안에서 쓰려고 할 때다.

    for (int i = 0; i < 3; i++) {
    Thread t = new Thread(() -> System.out.println("task " + i)); // 컴파일 오류
    t.start();
}
    error: local variables referenced from a lambda expression must be final or effectively final
            Thread t = new Thread(() -> System.out.println("task " + i));

    람다나 익명 클래스가 쓰는 바깥 지역 변수는 final이거나 사실상 final(effectively final), 즉 선언 뒤 한 번도 값이 바뀌지 않는 변수여야 한다(JLS 15.27.2, 4.12.4). 반복 변수 i는 i++로 계속 바뀌므로 이 조건을 어긴다. 앞에서 본 컴파일 결과를 떠올리면 이 규칙이 왜 필요한지 보인다. 캡처는 변수를 공유하는 것이 아니라 값을 복사하는 것이다. 새 스레드는 복사본을 읽는데, 원래 변수가 그 뒤에 바뀔 수 있다면 개발자는 어느 시점의 값이 복사되었는지 헷갈리게 된다. 바뀌지 않는 변수만 허용하면 복사본과 원본이 언제나 같으므로 이 혼란이 원천적으로 사라진다. 해결은 반복마다 새 지역 변수를 만들어 그것을 캡처하는 것이다.

    for (int i = 0; i < 3; i++) {
    int id = i;   // 반복마다 새로 선언되고 다시 대입되지 않으므로 사실상 final
    new Thread(() -> System.out.println("task " + id), "task-" + id).start();
}

    id는 반복의 본문 블록 안에서 선언되므로 반복할 때마다 새 변수이고, 선언 뒤 다시 대입되지 않으므로 사실상 final이다. 세 람다는 각자 0, 1, 2를 복사해 가진다. 이 코드는 task 0, task 1, task 2를 하나씩 찍지만 그 순서는 보장되지 않는다.

    Java 21의 Thread.Builder

    Java 21은 가상 스레드를 정식 기능으로 도입하면서 스레드를 만드는 빌더 API도 함께 정식으로 추가했다. Thread.ofPlatform()은 플랫폼 스레드용 빌더를, Thread.ofVirtual()은 가상 스레드용 빌더를 돌려준다. 빌더로 만든 플랫폼 스레드도 지금까지 본 것과 똑같은 Thread 객체이고, 생성자 대신 메서드 체인으로 이름, 데몬 여부, 우선순위를 정할 뿐이다.

Thread t1 = builder.start(() -> System.out.println(Thread.currentThread().getName()));
t1.join();

Thread t2 = builder.unstarted(() -> System.out.println(Thread.currentThread().getName()));
System.out.println(t2.getState());
t2.start();
t2.join();
    worker-0
NEW
worker-1

    name("worker-", 0)은 접두사와 시작 번호를 정하고, 이 빌더로 스레드를 만들 때마다 번호가 하나씩 올라간다. start(task)는 만들고 바로 시작하며, unstarted(task)는 NEW 상태의 스레드만 돌려준다. 시작 전에 이름과 데몬 여부를 정해야 한다는 규칙을 API 모양으로 강제한 셈이다. 빌더는 factory()로 ThreadFactory를 만들어 주기도 하는데, 이것은 12회에서 스레드 풀에 스레드 생성 방식을 넘길 때 다시 만난다.

    흔한 오해 바로잡기

    이 회차의 내용을 오해하기 쉬운 형태로 다시 모아 본다.

    • "new Thread()를 하면 스레드가 생긴다." 생기는 것은 힙의 자바 객체뿐이다. 운영체제 스레드, JVM 스택, HotSpot의 JavaThread는 start()에서 생긴다. 시작하지 않은 Thread 객체는 다른 객체처럼 가비지 컬렉션의 대상이 될 수 있고, JVM 종료를 막지도 않는다.
    • "run()을 호출하면 새 스레드에서 실행된다." run()은 평범한 메서드라서 호출한 스레드의 스택 위에서 실행된다. 새 실행 흐름을 만드는 메서드는 start()뿐이다. 스택 트레이스와 Thread.currentThread().getName()으로 언제든 확인할 수 있다.
    • "start()가 돌아오면 run()이 이미 실행 중이다." start()는 출발 신호를 보내고 돌아올 뿐이다. 새 스레드가 언제 첫 명령을 실행할지는 스케줄러가 정한다. 보장되는 것은 start() 이전에 한 일이 새 스레드에 보인다는 것뿐이다.
    • "main이 끝나면 프로그램이 끝난다." 프로그램은 살아 있는 사용자 스레드가 모두 끝날 때 끝난다. main 스레드는 그중 하나일 뿐이다. 반대로 데몬 스레드는 아무리 많아도 프로그램을 붙잡지 못하고, 종료 시점에 finally도 실행하지 못한다.
    • "끝난 스레드를 다시 start()하면 재사용할 수 있다." 스레드는 한 번만 시작할 수 있다. 다시 실행하고 싶은 것은 스레드가 아니라 작업이므로, 작업을 Runnable로 분리해 새 스레드에 넘기거나 스레드 풀을 쓴다.
    • "람다와 익명 클래스는 같은 것이다." 둘 다 바깥 지역 변수의 값을 복사해 쓰고 사실상 final 규칙을 따르지만, 익명 클래스는 컴파일 시점의 클래스 파일이고 람다는 invokedynamic으로 실행 시점에 연결된다. this가 가리키는 대상도 다르다.

    다음 회차와의 연결

    이 회차에서 스레드의 처음(NEW에서 start()로)과 끝(run()의 완료, 잡히지 않은 예외, JVM 종료)을 보았다. 그 사이에서 스레드는 잠들고, 다른 스레드를 기다리고, 락을 기다리며 여러 상태를 오간다. 다음 두 회차는 Thread.State의 여섯 상태와 그 전이, sleep과 join, 인터럽트를 다룬다. 이 회차에서 잠깐 쓰고 넘어간 join(), InterruptedException을 run() 밖으로 던질 수 없는 이유가 거기서 설명된다.

    "스택은 따로, 힙은 함께"라는 구도는 이 권 전체의 뼈대다. 05회는 힙에 있는 같은 필드를 두 스레드가 볼 때 CPU 캐시 때문에 서로 다른 값을 볼 수 있다는 문제를, 06회와 07회는 같은 필드를 동시에 고칠 때 생기는 경합 조건과 그것을 막는 락을, 12회와 13회는 비싼 운영체제 스레드를 미리 만들어 두고 Runnable만 갈아 끼우는 스레드 풀을 다룬다. 스프링 MVC를 배울 때 보았던 서블릿 컨테이너의 요청 처리도 같은 원리 위에 있다. 요청 하나를 스레드 하나가 맡고, 컨트롤러의 지역 변수는 그 스레드의 스택에, 싱글톤 빈의 필드는 모두가 함께 쓰는 힙에 있다.

    이 장의 핵심

    스레드를 만든다는 것은 힙에 Thread 객체를 만들고(new), 그 객체로 운영체제 스레드와 전용 JVM 스택을 만들어 맨 아래에 run()을 놓는 것(start())이다. 지역 변수는 스레드의 스택에 갇히고 객체는 힙에서 공유된다. 스레드 사이의 실행 순서는 정해져 있지 않으며, JVM은 사용자 스레드가 모두 끝날 때 종료되고 그 순간 남은 데몬 스레드는 정리 없이 멈춘다.
    new Thread()와 start()
    new Thread()는 힙에 자바 객체만 만든다. 운영체제 스레드와 JVM 스택은 start()가 호출될 때 생기고, 새 스레드는 그 스택의 맨 아래에서 run()을 실행한다.
    run() 직접 호출
    평범한 메서드 호출이므로 호출한 스레드의 스택 위에서 실행된다. 새 스레드는 생기지 않는다.
    스레드별 영역과 공유 영역
    JVMS 2.5에 따라 pc 레지스터와 JVM 스택은 스레드마다 생기고, 힙과 메서드 영역은 공유된다. 지역 변수는 스레드에 갇히고 객체의 필드는 공유된다.
    start()의 구현 경로
    OpenJDK 21에서 start0 → JVM_StartThread → JavaThread 생성 → pthread_create → 출발 신호 → thread_entry가 Thread.run()을 가상 호출한다. start()는 run()을 기다리지 않는다.
    한 번만 시작
    threadStatus가 NEW가 아니면 start()는 IllegalThreadStateException을 던진다. 끝난 스레드는 다시 시작할 수 없다.
    데몬 스레드
    JVM 종료를 막지 않는 스레드. 살아 있는 사용자 스레드가 0이 되면 종료 시퀀스가 시작되고, 남은 데몬 스레드는 finally도 실행하지 못하고 멈춘다. 시작 전에만 설정할 수 있고 만든 스레드에게서 물려받는다.
    Runnable
    작업만 표현하는 함수형 인터페이스. Thread.run()의 기본 구현이 생성자로 받은 작업을 실행한다. 작업과 실행 수단을 분리해 스레드 풀 같은 구조를 가능하게 한다.
    익명 클래스와 람다
    익명 클래스는 Outer$1.class가 되고 캡처한 값을 val$ 필드에 복사한다. 람다는 invokedynamic과 LambdaMetafactory로 실행 시점에 숨은 클래스가 만들어지고, 본문은 lambda$main$0 같은 메서드가 된다.
    HotSpot의 종료 판정
    start() 때 Threads::add가 비데몬 카운터를 올리고 스레드가 끝날 때 Threads::remove가 내린다. DestroyJavaVM 스레드가 카운터가 1이 될 때까지 기다렸다가 종료 훅을 실행하고, 마지막 세이프포인트에서 남은 데몬 스레드를 멈춘 채 끝낸다.
    람다의 연결과 동일성

JVM은 데몬 스레드에 인터럽트를 보내고, 데몬 스레드가 끝날 때까지 기다린다. 데몬 스레드가 살아 있는 한 JVM은 종료되지 않는다. JLS 12.8은 프로그램 종료 시 아직 끝나지 않은 스레드는 데몬이든 아니든 더 이상 자바 코드를 실행하지 않고, 어떤 finally 절도 실행되지 않는다고 정한다. 데몬 스레드는 종료 조건의 계산에 들어가지 않으므로 JVM이 기다려 주지도 않는다. 인터럽트를 보내는 동작은 명세에 없다. 메서드 안에서 String msg를 캡처하는 익명 Runnable과 람다를 각각 만들어 컴파일했다. 결과물에 대한 설명으로 옳은 것은? 둘 다 Outer$1.class, Outer$2.class처럼 클래스 파일이 하나씩 생긴다. 둘 다 바깥 메서드의 지역 변수 슬롯을 직접 참조하므로, 바깥 메서드가 끝나면 값을 읽을 수 없다. 람다 본문의 this는 람다 객체 자신을 가리킨다. 익명 클래스는 캡처한 값을 val$msg 필드에 복사하고, 람다는 invokedynamic으로 연결되어 실행 시점에 숨은 클래스가 만들어지며 본문은 lambda$... 메서드에 있다. javap로 확인한 대로 익명 클래스는 Outer$1.class와 final 필드 val$msg를 가지며, 람다는 클래스 파일 없이 LambdaMetafactory를 부트스트랩 메서드로 하는 invokedynamic으로 만들어진다. 둘 다 값을 복사하므로 바깥 메서드가 끝나도 문제없다. 람다는 새 스코프를 만들지 않으므로 this는 바깥 객체다. Thread의 하위 클래스가 run()을 재정의했고, 생성자에서 super(task)로 Runnable도 넘겼다. 재정의한 run()은 super.run()을 부르지 않는다. start()하면 무엇이 실행되는가? 넘긴 task.run()만 실행된다. Runnable이 우선한다. 하위 클래스의 run()만 실행되고 task는 실행되지 않는다. 둘 다 실행되며 순서는 정해져 있지 않다. 컴파일 오류가 난다. HotSpot의 thread_entry는 Thread 객체의 run()을 가상 호출하므로 실제 클래스의 재정의된 run()이 선택된다. task를 실행하는 코드는 Thread.run()의 기본 구현 안에만 있으므로, 재정의한 메서드가 super.run()을 부르지 않으면 task는 실행되지 않는다.
    플랫폼 스레드(platform thread)
    운영체제의 스레드를 감싼 자바 스레드. Thread 문서는 보통 커널 스레드와 1:1로 대응된다고 설명하며, HotSpot은 pthread_create 등으로 만든다.
    데몬 스레드(daemon thread)
    JVM의 종료를 막지 않는 스레드. 살아 있는 데몬이 아닌 스레드가 모두 끝나면 남은 데몬 스레드와 상관없이 종료 시퀀스가 시작된다.
    종료 시퀀스(shutdown sequence)
    JVM이 끝나기 전에 거치는 과정. 사용자 스레드가 모두 끝나거나 System.exit가 호출되는 등의 사건으로 시작되고, 등록된 종료 훅이 모두 끝나면 마친다.
    JVM 스택(Java Virtual Machine stack)
    스레드마다 하나씩, 스레드와 함께 만들어지는 영역. 메서드 호출마다 프레임이 쌓이고, 프레임에는 지역 변수와 피연산자 스택이 있다.
    Runnable
    반환값 없는 작업 하나를 표현하는 함수형 인터페이스. 메서드는 void run() 하나다. Thread에 넘기면 Thread.run()의 기본 구현이 이를 실행한다.
    사실상 final(effectively final)
    final로 선언하지 않았지만 초기화 뒤 한 번도 다시 대입되지 않는 지역 변수. 람다와 내부 클래스는 이런 변수만 캡처할 수 있다.
    숨은 클래스(hidden class)
    클래스 파일 없이 실행 중에 만들어지며 다른 클래스가 이름으로 직접 참조할 수 없는 클래스. 람다 객체의 클래스가 이렇게 만들어진다(Class.isHidden()이 true).
    스레드 덤프(thread dump)
    한 시점에 JVM 안의 모든 스레드의 이름, 식별자, 상태, 호출 스택을 찍은 출력. jcmd PID Thread.print로 얻는다.
    세이프포인트(safepoint)
    HotSpot이 자바 스레드들을 알려진 지점에 멈춰 세우는 상태. JVM 종료 시 VM 스레드가 마지막 세이프포인트를 풀지 않고 끝나므로, 남은 데몬 스레드는 그 자리에 멈춘 채 다시 실행되지 않는다.
    스택 가드 영역(stack guard zone)
    HotSpot이 스레드 스택의 끝에 접근 금지로 만들어 두는 레드·옐로·예약 영역. 옐로 영역에 닿으면 StackOverflowError가 던져지고, 레드 영역에 닿으면 JVM이 오류 보고서를 남기고 끝난다.
