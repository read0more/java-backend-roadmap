    생산자 소비자 문제: 속도가 다른 두 흐름 사이의 버퍼

    앞 회차까지 우리는 여러 스레드가 같은 데이터를 동시에 고치지 못하게 막는 방법을 배웠다. synchronized와 ReentrantLock은 임계 영역에 한 번에 한 스레드만 들어가게 한다. 그런데 멀티스레드 프로그램에서 자주 만나는 상황은 "동시에 고치지 마라"에서 끝나지 않는다. 한 스레드가 만든 결과를 다른 스레드가 받아서 처리해야 하고, 받을 것이 아직 없으면 생길 때까지 기다려야 한다. 이 회차는 그런 협력, 즉 조건이 맞을 때까지 기다리고 조건을 바꾼 쪽이 기다리는 쪽을 깨우는 문제를 다룬다.

    가장 대표적인 형태가 생산자 소비자 문제(producer-consumer problem)다. 등장인물은 셋이다. 생산자(producer)는 데이터를 만들어 넣는 스레드다. 소비자(consumer)는 데이터를 꺼내 처리하는 스레드다. 둘 사이에는 데이터를 잠시 담아 두는 버퍼(buffer)가 있다. 버퍼가 있는 이유는 두 쪽의 속도가 다르기 때문이다. 생산자가 잠깐 몰아서 많이 만들 때 버퍼가 그 차이를 흡수하고, 소비자는 자기 속도대로 꺼내 간다. 버퍼가 없다면 생산자는 소비자가 받을 준비가 될 때마다 일일이 맞춰 주어야 한다.

    현실의 버퍼는 크기에 한계가 있다. 메모리가 무한하지 않으므로 버퍼에 담을 수 있는 개수에 상한을 둔다. 그래서 이 문제를 유한 버퍼 문제(bounded-buffer problem)라고도 부른다. 상한이 있으면 상황이 두 가지 생긴다. 생산자가 넣으려는데 버퍼가 가득 찬 경우, 그리고 소비자가 꺼내려는데 버퍼가 빈 경우다. 생산자 소비자 문제의 핵심은 이 두 경계에서 스레드가 무엇을 해야 하느냐다.

    이 구조는 교과서 속 예제가 아니다. 이 권의 뒤쪽에서 다룰 스레드 풀이 바로 이 모양이다. ThreadPoolExecutor는 생성자에서 BlockingQueue 형태의 작업 큐를 받는데, 작업을 제출하는 스레드가 생산자, 풀의 작업 스레드가 소비자, 작업 큐가 버퍼다. 웹 서버가 들어온 요청을 큐에 쌓아 두고 작업 스레드가 꺼내 처리하는 구조, 로그를 큐에 넣고 별도 스레드가 파일에 쓰는 비동기 로거도 같은 구조다. 그러니 이 회차에서 손으로 만들어 보는 버퍼의 동작 원리는 나중에 그 도구들의 설정값(큐 크기, 거절 정책)을 판단할 때 그대로 쓰인다.

    일상에서 가져온 비유주방과 배식대

    주방(생산자)이 음식을 만들어 배식대(버퍼)에 올리고, 손님(소비자)이 배식대에서 가져간다. 배식대에 놓을 자리가 다 찼는데 주방이 음식을 또 만들었다면 어떻게 할까. 버린다, 자리가 날 때까지 계속 들여다본다, 아니면 손을 놓고 쉬다가 누가 가져가면 불러 달라고 한다. 손님 쪽도 마찬가지로 빈 배식대 앞에서 그냥 돌아가거나, 서서 계속 지켜보거나, 음식이 나오면 불러 달라고 할 수 있다. 이 회차의 세 예제는 이 세 가지 선택을 차례로 코드로 옮긴 것이다. 비유가 깨지는 지점도 있다. 실제 배식대는 여러 사람이 동시에 볼 수 있지만, 우리가 만들 버퍼는 락으로 보호되므로 한 번에 한 스레드만 들여다볼 수 있다. 이 차이가 두 번째 예제를 멈춰 세운다.

    왼쪽 생산자 세 개가 가운데 용량 2의 버퍼에 넣고 오른쪽 소비자 세 개가 꺼내는 구조, 그리고 가득 참과 비어 있음이라는 두 경계 상황을 보여 준다. 가로로 긴 개념도. 왼쪽에 사람 모양 아이콘 세 개가 세로로 서 있고 각각 "P1", "P2", "P3" 라벨, 그 위에 "생산자" 제목. 오른쪽에 같은 모양 아이콘 세 개 "C1", "C2", "C3", 그 위에 "소비자" 제목. 가운데에 칸이 두 개인 가로 상자(큐)가 있고 상자 위에 "버퍼 (용량 2)" 라벨, 칸 안에 "data1", "data2" 카드가 들어 있다. 왼쪽 아이콘들에서 상자로 향하는 화살표에 "put", 상자에서 오른쪽 아이콘들로 향하는 화살표에 "take" 라벨. 상자 왼쪽 위에 빨간 말풍선 "가득 차면?", 상자 오른쪽 아래에 파란 말풍선 "비어 있으면?". 상자 전체를 감싸는 점선 테두리에 자물쇠 아이콘과 "락으로 보호" 라벨. 흰 배경, 단순한 평면 일러스트. 생산자 소비자 문제의 구조. 핵심은 버퍼가 가득 찼을 때와 비었을 때 스레드가 무엇을 하느냐다.

    이제 같은 인터페이스를 세 가지 방식으로 구현하면서, 각 방식이 실제로 어떻게 동작하는지 실행 결과와 스레드 상태로 확인해 보자. 모든 실험은 macOS의 OpenJDK 21.0.13(Temurin)에서 돌렸다.

    예제 1: 가득 차면 버리고, 비어 있으면 빈손으로 돌아온다

    먼저 세 예제가 공유할 뼈대를 만든다. 버퍼의 계약은 넣기(put)와 꺼내기(take) 두 가지다. 뒤의 예제에서 대기 중에 인터럽트를 받을 수 있도록 두 메서드 모두 InterruptedException을 선언해 둔다. 로그에는 시각을 찍지 않고 스레드 이름만 붙인다. 시각은 실행마다 달라지지만, 이 회차에서 확인하려는 것은 순서와 상태이기 때문이다.

    public interface Buffer {
    void put(String data) throws InterruptedException;
    String take() throws InterruptedException;
}

public final class Log {
    public static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }
}

    첫 번째 구현은 가장 단순한 선택을 한다. 가득 차 있으면 넣으려던 데이터를 버리고 돌아오고, 비어 있으면 null을 들고 돌아온다. 두 메서드 모두 synchronized이므로 큐를 동시에 고치는 일은 없다. 내부 저장소는 ArrayDeque다. ArrayDeque는 스레드 안전하지 않은 컬렉션이지만 모든 접근이 같은 객체의 모니터 락 아래에서 일어나므로 여기서는 문제가 되지 않는다.

    import java.util.ArrayDeque;
import java.util.Queue;

public class DropBuffer implements Buffer {
    private final Queue queue = new ArrayDeque<>();
    private final int capacity;

    public DropBuffer(int capacity) {
        this.capacity = capacity;
    }

    @Override
    public synchronized void put(String data) {
        if (queue.size() == capacity) {
            Log.log("put: 가득 참, 버림 " + data + " " + queue);
            return;
        }
        queue.offer(data);
        Log.log("put: 저장 " + data + " " + queue);
    }

    @Override
    public synchronized String take() {
        String data = queue.poll();          // 비어 있으면 null
        Log.log("take: 꺼냄 " + data + " " + queue);
        return data;
    }
}

    실행기는 생산자 세 개(P1~P3, 각각 data1~data3를 하나씩 넣는다)와 소비자 세 개(C1~C3, 각각 하나씩 꺼낸다)를 만든다. 두 번째 인자가 p면 생산자를 먼저, c면 소비자를 먼저 시작한다. 스레드를 하나 시작할 때마다 100ms를 쉬어 시작 순서가 눈에 보이게 벌려 놓았다. 모든 스레드를 데몬으로 만든 이유는 다음 예제에서 영원히 멈추는 스레드가 생겨도 main이 끝나면 JVM이 종료되게 하기 위해서다. 마지막에는 1초를 기다린 뒤 각 스레드의 상태를 찍는다.

    import java.util.ArrayList;
import java.util.List;

public class Run {
    public static void main(String[] args) throws InterruptedException {
        Buffer buffer = switch (args[0]) {
            case "drop"  -> new DropBuffer(2);
            case "sleep" -> new SleepBuffer(2);
            default      -> new WaitBuffer(2);
        };
        List threads = new ArrayList<>();
        if (args[1].equals("p")) {
            startProducers(buffer, threads);
            startConsumers(buffer, threads);
        } else {
            startConsumers(buffer, threads);
            startProducers(buffer, threads);
        }
        Thread.sleep(1000);
        for (Thread t : threads) {
            System.out.println(t.getName() + ": " + t.getState());
        }
    }

    static void startProducers(Buffer buffer, List threads) throws InterruptedException {
        for (int i = 1; i <= 3; i++) {
            String data = "data" + i;
            start(new Thread(() -> {
                try { buffer.put(data); } catch (InterruptedException e) { }
            }, "P" + i), threads);
        }
    }

    static void startConsumers(Buffer buffer, List threads) throws InterruptedException {
        for (int i = 1; i <= 3; i++) {
            start(new Thread(() -> {
                try { buffer.take(); } catch (InterruptedException e) { }
            }, "C" + i), threads);
        }
    }

    static void start(Thread t, List threads) throws InterruptedException {
        t.setDaemon(true);   // 멈춘 스레드가 있어도 main이 끝나면 JVM이 종료되게
        threads.add(t);
        t.start();
        Thread.sleep(100);   // 시작 순서를 눈에 보이게 벌려 둔다
    }
}

    로그를 모두 synchronized 메서드 안에서 찍는다는 점에 주목하자. 락 안의 로그는 락을 얻은 순서대로만 찍힐 수 있으므로, 출력 순서가 곧 임계 영역에 들어간 순서다. 락 밖에서 로그를 찍었다면 다른 스레드의 로그와 줄이 뒤섞일 수 있어 순서를 해석하기 어려워진다. 다만 100ms 간격은 순서를 사실상 고정할 뿐 보장하지는 않는다. 운영체제 스케줄러가 어떤 스레드를 언제 실행할지는 자바 명세가 정하지 않는다.

    예제 1 분석: 데이터는 사라지고 소비자는 빈손이다

    생산자 우선

    [P1] put: 저장 data1 [data1]
[P2] put: 저장 data2 [data1, data2]
[P3] put: 가득 참, 버림 data3 [data1, data2]
[C1] take: 꺼냄 data1 [data2]
[C2] take: 꺼냄 data2 []
[C3] take: 꺼냄 null []
P1: TERMINATED
P2: TERMINATED
P3: TERMINATED
C1: TERMINATED
C2: TERMINATED
C3: TERMINATED

    한 줄씩 따라가 보자. 0ms쯤 P1이 put에 들어가 버퍼 모니터의 락을 얻는다. 큐 크기 0이 용량 2보다 작으므로 data1을 넣고 메서드를 빠져나오며 락을 놓는다. 100ms쯤 P2가 같은 과정으로 data2를 넣는다. 200ms쯤 P3가 들어왔을 때 큐 크기는 2이고 용량과 같다. DropBuffer는 이 상황에서 할 일이 정해져 있다. 로그를 남기고 그냥 돌아온다. data3는 어디에도 저장되지 않고 P3의 스택 프레임이 사라지면서 함께 사라진다.

    300ms부터 소비자가 차례로 들어온다. C1은 data1, C2는 data2를 꺼낸다. ArrayDeque는 FIFO이므로 넣은 순서대로 나온다. C3가 들어왔을 때 큐는 비어 있고 poll()은 null을 돌려준다. 결과적으로 생산자는 세 개를 만들었고 소비자는 세 번 꺼냈는데, 실제로 전달된 데이터는 두 개뿐이다. 하나는 버려졌고, 소비자 하나는 빈손이다. 두 사건 사이의 시간 차는 고작 100ms다. P3가 조금만 기다렸다면 C1이 자리를 비워 주었을 것이다.

    소비자 우선

    [C1] take: 꺼냄 null []
[C2] take: 꺼냄 null []
[C3] take: 꺼냄 null []
[P1] put: 저장 data1 [data1]
[P2] put: 저장 data2 [data1, data2]
[P3] put: 가득 참, 버림 data3 [data1, data2]
C1: TERMINATED
...
P3: TERMINATED

    순서를 뒤집으면 결과는 더 나쁘다. 소비자 셋이 먼저 와서 빈 버퍼를 보고 모두 null을 들고 돌아간다. 그 뒤 생산자가 와서 data1, data2를 넣고, data3는 가득 차서 버린다. 프로그램이 끝났을 때 버퍼에는 [data1, data2]가 남아 있지만 이것을 꺼내 갈 소비자는 이미 모두 종료되었다. 전달된 데이터는 0개다. 같은 코드가 시작 순서만 바뀌었을 뿐인데 결과가 2개에서 0개로 바뀌었다. 멀티스레드 프로그램에서 실행 순서에 따라 결과가 달라지는 것은 경합 조건(race condition)의 전형적인 증상이다. 다만 이번에는 데이터 자체가 깨진 것이 아니라, 스레드들이 서로를 기다려 주지 않아서 생긴 문제다.

    synchronized가 해결해 준 것과 해결하지 못한 것

    DropBuffer는 스레드 안전하다. 큐의 내부 배열이 깨지지 않고, 한 스레드가 넣은 데이터는 다른 스레드가 정확히 본다. JLS 17.4.4는 모니터 m의 unlock 동작이 그 뒤에 오는 m의 모든 lock 동작과 synchronizes-with 관계를 이룬다고 정한다. 그래서 P1이 put을 빠져나오며 락을 놓기 전에 한 쓰기는, 나중에 같은 락을 얻은 C1에게 보인다. 5회차에서 다룬 가시성 문제는 여기서 일어나지 않는다.

    그런데도 프로그램은 원하는 대로 동작하지 않는다. 동시성 제어에는 성격이 다른 두 가지 요구가 있기 때문이다. 첫째는 상호 배제(mutual exclusion)다. 공유 자료를 한 번에 한 스레드만 고치게 하는 것이고, 락이 이것을 해결한다. 둘째는 조건 동기화(condition synchronization)다. "버퍼에 빈자리가 생길 때까지", "버퍼에 데이터가 들어올 때까지"처럼 공유 상태가 어떤 조건을 만족할 때까지 스레드를 멈춰 두는 것이다. 락은 첫째만 준다. 조건이 맞지 않을 때 무엇을 할지는 락이 알려 주지 않는다. DropBuffer는 그 질문에 "포기한다"고 답했고, 그 결과가 데이터 유실과 빈손 소비자다.

    포기가 옳은 답인 경우도 있다. 오래된 데이터가 의미 없는 센서 측정값이나, 넘치면 버려도 되는 통계 이벤트라면 버리는 편이 시스템 전체를 보호한다. 실제로 스레드 풀의 거절 정책 가운데에는 새 작업을 조용히 버리는 정책도 있다. 하지만 대부분의 업무 데이터는 버릴 수 없다. 그렇다면 남은 선택은 기다리는 것이다. 문제는 어떻게 기다리느냐다.

    예제 2: 락을 쥔 채 자면서 기다린다

    가장 먼저 떠오르는 기다리는 방법은 조건이 맞을 때까지 확인을 반복하는 것이다. 가득 찼으면 1초 자고 다시 확인하고, 비었으면 1초 자고 다시 확인한다. 4회차에서 본 Thread.sleep을 반복문에 넣기만 하면 된다.

    import java.util.ArrayDeque;
import java.util.Queue;

public class SleepBuffer implements Buffer {
    private final Queue queue = new ArrayDeque<>();
    private final int capacity;

    public SleepBuffer(int capacity) {
        this.capacity = capacity;
    }

    @Override
    public synchronized void put(String data) throws InterruptedException {
        while (queue.size() == capacity) {
            Log.log("put: 가득 참, 1초 자고 다시 확인 " + data);
            Thread.sleep(1000);              // 락을 쥔 채로 잔다
        }
        queue.offer(data);
        Log.log("put: 저장 " + data + " " + queue);
    }

    @Override
    public synchronized String take() throws InterruptedException {
        while (queue.isEmpty()) {
            Log.log("take: 비어 있음, 1초 자고 다시 확인");
            Thread.sleep(1000);              // 락을 쥔 채로 잔다
        }
        String data = queue.poll();
        Log.log("take: 꺼냄 " + data + " " + queue);
        return data;
    }
}

[P2] put: 저장 data2 [data1, data2]
[P3] put: 가득 참, 1초 자고 다시 확인 data3
[P3] put: 가득 참, 1초 자고 다시 확인 data3
P1: TERMINATED
P2: TERMINATED
P3: TIMED_WAITING
C1: BLOCKED
C2: BLOCKED
C3: BLOCKED
    [C1] take: 비어 있음, 1초 자고 다시 확인
[C1] take: 비어 있음, 1초 자고 다시 확인
C1: TIMED_WAITING

    두 경우 모두 진전이 없다. 생산자 우선에서는 P3가 200ms쯤 들어와 가득 참을 보고 잠들고, 1200ms쯤 깨어나 다시 확인하지만 여전히 가득 차 있어 또 잠든다. 그동안 소비자 셋은 한 줄의 로그도 남기지 못했다. 소비자 우선에서도 C1만 혼자 "비어 있음"을 반복하고 생산자 셋은 아무것도 넣지 못했다. 실행기가 데몬 스레드를 쓰지 않았다면 이 프로그램은 영원히 끝나지 않는다. JVM은 데몬이 아닌 스레드가 모두 끝나야 종료되는데, P3(또는 C1)는 반복문을 빠져나올 방법이 없기 때문이다.

    출력에 찍힌 마지막 로그 횟수도 추적과 맞는다. 생산자 우선에서 P3는 200ms와 1200ms에 로그를 남겼고, main은 마지막 스레드를 시작한 500ms에 100ms를 더 쉬고 1초를 더 기다린 약 1600ms에 상태를 찍었다. 그 사이 2200ms의 세 번째 확인은 아직 오지 않았다. 이 시각들은 sleep이 보장하는 최소 시간을 기준으로 한 대략적인 값이다.

    예제 2 분석: 잠든 스레드가 문을 잠그고 있다

    상태 값이 이미 원인을 말해 준다. P3는 TIMED_WAITING이고 소비자 셋은 BLOCKED다. 3회차에서 본 대로 BLOCKED는 모니터 락을 얻으려고 기다리는 상태다. 소비자들은 take에 들어가려고 하지만 들어갈 수 없다. 누가 그 락을 쥐고 있는지는 스레드 덤프가 보여 준다. 생산자 우선 실행을 30초 동안 붙잡아 두고 jcmd Thread.print를 찍은 결과에서 관련 부분만 옮기면 다음과 같다.

    덤프를 읽는 법은 단순하다. P3의 스택에서 SleepBuffer.put 프레임 바로 아래 - locked <0x...7488> (a SleepBuffer)가 있다. 이 프레임이 그 객체의 모니터를 쥐고 있다는 뜻이다. 그 위 프레임은 Thread.sleep이고 상태는 TIMED_WAITING (sleeping)이다. 한편 C1의 take 프레임 아래에는 - waiting to lock <0x...7488>이 있다. 주소가 같다. 같은 버퍼 객체의 락을 P3는 쥔 채 자고 있고, 소비자 셋은 그 락을 기다린다.

    왜 자는 동안에도 락을 쥐고 있을까. Thread.sleep의 API 문서는 잠든 스레드가 어떤 모니터의 소유권도 잃지 않는다(does not lose ownership of any monitors)고 분명히 적어 두었다. JLS 17.3은 한 걸음 더 나아가 Thread.sleep과 Thread.yield에는 어떤 동기화 의미도 없다고 말한다. sleep은 "이 스레드를 일정 시간 스케줄링 대상에서 빼 달라"는 요청일 뿐, 락에 대해서는 아무것도 하지 않는다. synchronized 메서드 안에서 잠들면 메서드를 빠져나가기 전까지 락은 계속 그 스레드 것이다.

    그러면 고리가 만들어진다. P3가 반복문을 빠져나가려면 큐에 빈자리가 생겨야 한다. 빈자리를 만들 수 있는 것은 take를 실행하는 소비자뿐이다. 소비자가 take를 실행하려면 P3가 쥔 락이 필요하다. P3는 조건을 기다리며 락을 놓지 않고, 소비자들은 락을 기다리며 조건을 바꾸지 못한다. 서로가 서로를 기다리는 이 고리는 넓은 의미의 교착 상태(deadlock)다. 하지만 락 하나와 조건 하나로 만들어진 고리라서, 두 스레드가 두 락을 서로 반대 순서로 잡는 고전적인 교착 상태와 모양이 다르다.

    모양이 다르다는 점은 실무에서 중요하다. HotSpot의 스레드 덤프는 모니터 락끼리 순환 대기가 생기면 덤프 끝에 "Found one Java-level deadlock"이라는 절을 붙여 알려 준다. 이번 덤프에는 그런 절이 없다. 실제로 위 실행의 덤프에서 "deadlock"이라는 단어를 찾으면 한 번도 나오지 않는다. P3는 락을 기다리는 것이 아니라 자고 있을 뿐이어서, 락 소유와 락 대기로 이루어진 순환이 없기 때문이다. 이런 멈춤은 도구가 자동으로 찾아 주지 않으므로, 덤프에서 "같은 주소를 locked로 쥔 채 sleeping인 스레드"와 "그 주소를 waiting to lock하는 다수의 스레드"를 사람이 직접 짝지어야 한다.

    버퍼 모니터 안에 P3가 잠든 채 들어가 있고, 문밖에 C1~C3가 BLOCKED로 줄 서 있는 장면. 조건과 락이 서로를 기다리는 고리를 보여 준다. 방 하나를 위에서 내려다본 그림. 방 이름표 "SleepBuffer 모니터". 방 안에 큐 상자 "[data1, data2]"가 있고, 그 옆에 침대에서 자는 사람 아이콘 "P3", 머리 위에 "TIMED_WAITING (sleeping)" 말풍선, 손에 열쇠 아이콘과 "락 보유" 라벨. 방의 문은 닫혀 있고 자물쇠가 걸려 있다. 문밖 복도에 사람 아이콘 세 개가 줄 서 있고 각각 "C1", "C2", "C3", 줄 옆에 "BLOCKED" 라벨. P3에서 복도 쪽으로 향하는 점선 화살표에 "빈자리가 생기길 기다림", 복도의 줄에서 열쇠로 향하는 점선 화살표에 "락을 기다림". 두 화살표가 원을 이루도록 배치하고 가운데에 "서로를 기다리는 고리" 라벨. 흰 배경, 평면 일러스트. sleep은 락을 놓지 않는다. 조건을 바꿀 수 있는 스레드가 락 밖에서 막혀 있으므로 아무도 진전하지 못한다.

    락을 놓고 자면 되지 않을까: 폴링의 비용

    문제가 "락을 쥔 채 잔다"는 데 있으니, 자기 전에 락을 놓으면 된다. 조건 확인과 수정만 락 안에서 하고, 잠은 락 밖에서 잔다.

    public void put(String data) throws InterruptedException {
    while (true) {
        synchronized (this) {
            if (queue.size() < capacity) {
                queue.offer(data);
                return;
            }
        }
        Thread.sleep(10);   // 락 밖에서 잔다
    }
}

    이 코드는 멈추지 않는다. 생산자가 자는 동안 락은 비어 있으므로 소비자가 들어와 꺼내 갈 수 있고, 생산자는 다음 확인 때 빈자리를 발견한다. 정확성 문제는 해결되었다. 남는 것은 비용이다. 이 방식을 폴링(polling)이라고 부르는데, 조건이 언제 바뀌는지 모르기 때문에 정해진 간격으로 계속 확인한다. 간격을 짧게 잡으면 조건이 바뀌지 않았는데도 스레드가 계속 깨어나 락을 얻고 확인하고 다시 잔다. 깨어날 때마다 운영체제는 스레드를 실행 대기열에 올리고 CPU를 배정해야 하며, 대기 스레드가 많으면 그 확인이 락 경합까지 만든다. 간격을 길게 잡으면 낭비는 줄지만, 조건이 바뀐 직후에도 다음 확인 때까지 반응하지 못한다. 짧게 잡으면 CPU를 버리고 길게 잡으면 응답이 늦는다. 어느 값도 정답이 아니다.

    우리가 정말 원하는 것은 다음과 같은 동작이다. 조건이 맞지 않으면 락을 놓고 잠든다. 잠든 동안에는 CPU를 전혀 쓰지 않는다. 다른 스레드가 조건을 바꾸면 그 스레드가 잠든 쪽을 깨운다. 깨어난 쪽은 락을 다시 얻은 다음 조건을 확인한다. 그리고 이 중 "조건 확인 후 락을 놓고 잠드는" 부분은 그 틈에 신호가 끼어들 수 없게 하나의 동작이어야 한다. 마지막 요구가 왜 필요한지는 잠시 뒤에 본다. 자바는 이 동작을 모든 객체에 기본으로 넣어 두었다. Object의 wait, notify, notifyAll이다.

    모니터의 나머지 절반: 대기 집합과 wait/notify

    6회차에서 모든 객체에는 모니터 락이 하나씩 있다고 했다. JLS 17.2는 여기에 하나를 더 붙인다. 모든 객체는 모니터와 함께 대기 집합(wait set)을 하나 가진다. 대기 집합은 스레드들의 집합이고, 객체가 처음 만들어질 때는 비어 있다. 스레드를 대기 집합에 넣고 빼는 기본 동작은 원자적이며, 대기 집합을 조작하는 수단은 Object.wait, Object.notify, Object.notifyAll 세 메서드뿐이다. 스레드의 인터럽트 상태도 대기 집합에 영향을 준다. 그러니 자바의 객체 모니터는 "한 번에 한 스레드만 들어가게 하는 락"과 "조건을 기다리는 스레드들이 머무는 대기실"의 두 부분으로 이루어져 있고, 이 회차에서 새로 쓰는 것은 두 번째 부분이다.

    JLS 17.2.1이 정한 wait의 동작을 그대로 따라가 보자. 스레드 t가 객체 m에 대해 wait를 호출했고, t가 m에 대해 수행한 lock 동작 중 아직 unlock과 짝지어지지 않은 횟수를 n이라고 하자. 같은 스레드가 synchronized를 중첩해 같은 객체의 락을 세 번 얻었다면 n은 3이다.

    두 번째 단계가 예제 2에 빠져 있던 것이다. wait는 잠들기 전에 락을 놓는다. 그것도 n번 전부 놓는다. 그래서 다른 스레드가 같은 객체의 synchronized 영역에 들어가 상태를 바꿀 수 있다. 네 번째 단계도 중요하다. 깨어난 스레드는 곧바로 다음 줄을 실행하는 것이 아니라 락을 다시 얻은 다음에야 wait에서 돌아온다. 따라서 wait에서 돌아온 직후의 코드는 여전히 임계 영역 안에 있고, 락을 쥔 상태에서 공유 상태를 다시 확인할 수 있다.

    놓는 락은 그 객체의 락뿐이다. Object.wait의 API 문서는 이 객체에 대한 락만 놓이고, 현재 스레드가 동기화하고 있는 다른 객체들은 기다리는 동안에도 잠긴 채로 남는다고 명시한다. 버퍼 A의 synchronized 안에서 다른 객체 B의 synchronized로 들어가 B에 대해 wait하면 B의 락은 놓이지만 A의 락은 그대로다. A의 락이 필요한 다른 스레드는 예제 2의 소비자처럼 막힌다. 이런 구조를 만들지 않는 것이 wait를 쓰는 기본 규칙이다.

    알림 쪽 규칙(JLS 17.2.2)은 짧다. notify나 notifyAll을 부르는 스레드도 그 객체의 락을 갖고 있어야 하며, 아니면 역시 IllegalMonitorStateException이다. notify는 대기 집합이 비어 있지 않으면 그중 한 스레드 u를 골라 제거한다. 명세는 어느 스레드가 선택되는지 아무것도 보장하지 않는다. 그리고 u가 락을 다시 얻는 동작은 알린 스레드가 락을 완전히 놓을 때까지 성공할 수 없다. notifyAll은 대기 집합의 모든 스레드를 제거하는데, 깨어난 스레드들은 한 번에 하나씩만 락을 다시 얻는다. 대기 집합이 비어 있을 때 notify를 부르면 아무 일도 일어나지 않는다. 알림은 저장되지 않는다. 나중에 wait를 부른 스레드는 그 전에 지나간 알림을 받지 못한다.

    인터럽트와의 관계(JLS 17.2.3, 17.2.4)도 4회차의 내용과 이어진다. 대기 집합에 있는 스레드를 인터럽트하면 그 스레드는 대기 집합에서 제거되고, 락을 다시 얻은 뒤 InterruptedException을 던진다. 명세는 인터럽트 때문에 알림이 사라지지 않는다는 것도 보장한다. 대기 집합의 스레드들 중 하나가 알림과 인터럽트를 동시에 받아 InterruptedException으로 빠져나갔다면, 그 알림은 대기 집합의 다른 스레드에게 가야 한다. InterruptedException이 선언되어 있어서 우리 Buffer 인터페이스도 이 예외를 던지도록 만들었던 것이다.

    락 없이 부르면 어떻게 되는지 직접 확인해 보자.

    public class NoOwner {
    public static void main(String[] args) throws InterruptedException {
        Object lock = new Object();
        try {
            lock.notify();
        } catch (IllegalMonitorStateException e) {
            System.out.println(e);
        }
        try {
            lock.wait();
        } catch (IllegalMonitorStateException e) {
            System.out.println(e);
        }
    }
}

    컴파일은 된다. wait와 notify는 Object의 평범한 public final 메서드이고, 컴파일러는 호출 지점이 synchronized 안인지 검사하지 않는다. 검사는 실행 중에 JVM이 한다. 현재 스레드가 그 객체 모니터의 소유자가 아니면 예외가 난다.

    왜 락을 쥔 상태에서만 wait를 부를 수 있는가

    이 제약은 귀찮은 형식 규칙처럼 보이지만, 생산자 소비자 문제를 올바르게 풀기 위한 필수 조건이다. 만약 락 없이 wait를 부를 수 있다고 가정해 보자. 소비자는 "버퍼가 비었으면 기다린다"를 다음처럼 쓸 것이다.

    // 가상의 코드: 실제 자바에서는 IllegalMonitorStateException이 난다
if (queue.isEmpty()) {     // ① 비어 있음을 확인했다
                           //    ← 이 틈에 생산자가 데이터를 넣고 notify를 부른다
    queue.wait();          // ② 잠든다
}

    ①과 ② 사이에 틈이 있다. 소비자가 비어 있음을 확인한 직후, 아직 대기 집합에 들어가기 전에 생산자가 데이터를 넣고 notify를 부를 수 있다. 그 순간 대기 집합은 비어 있으므로 알림은 아무도 깨우지 않고 사라진다. 그다음 소비자가 ②에서 잠든다. 버퍼에는 데이터가 있는데 소비자는 잠들어 있고, 생산자는 이미 알림을 보냈으므로 다시 보내지 않는다. 다른 생산자가 오지 않으면 소비자는 영원히 잔다. 이것을 신호 유실(lost wake-up)이라고 부른다. 확인하고 행동하기(check-then-act) 사이의 경합 조건이 대기와 알림에서 나타난 모습이다.

    자바의 규칙은 이 틈을 두 겹으로 막는다. 첫째, 소비자는 락을 쥔 채로 조건을 확인하고, wait는 "대기 집합에 들어가기"와 "락 놓기"를 이 순서로 한 번에 처리한다. 대기 집합에 이미 들어간 다음에야 락이 풀리므로, 생산자가 락을 얻어 notify를 부르는 시점에는 소비자가 반드시 대기 집합 안에 있다. 둘째, 생산자도 락을 쥐어야 notify를 부를 수 있으므로, 상태 변경과 알림이 같은 임계 영역 안에서 일어난다. 소비자가 조건을 확인하는 중에 생산자의 상태 변경이 끼어들 수 없다. 결국 "조건 확인 → 대기 집합 진입"과 "상태 변경 → 알림"이 같은 락으로 직렬화되어, 둘의 순서는 "확인 전에 변경됨(그러면 소비자는 기다리지 않는다)"이거나 "대기 집합 진입 후 알림(그러면 소비자가 깨어난다)" 둘 중 하나가 된다. 그 사이는 없다.

    이 장의 핵심

    조건 동기화의 정확성은 "조건을 확인하는 일"과 "조건을 바꾸는 일"이 같은 락 아래에 있다는 데서 나온다. wait가 락을 요구하고, 대기 집합에 들어간 뒤 그 락을 놓으며, 돌아오기 전에 그 락을 다시 얻는 것은 모두 이 한 가지를 지키기 위한 장치다.

    가시성도 같은 장치에서 나온다. 생산자가 큐에 데이터를 넣고 notify를 부른 뒤 synchronized를 빠져나가며 락을 놓는다. 깨어난 소비자는 wait에서 돌아오기 전에 같은 락을 다시 얻는다. 앞에서 본 JLS 17.4.4의 규칙에 따라 그 unlock은 이 lock과 synchronizes-with 관계이므로, 생산자가 넣은 데이터는 소비자에게 보인다. wait나 notify가 따로 메모리 장벽을 약속하는 것이 아니라, 둘을 감싼 락의 unlock과 lock이 happens-before를 만든다.

    스레드 상태로 본 wait와 notify

    대기 집합에 있는 스레드와 락을 다시 얻으려는 스레드는 상태가 다르다. 짧은 실험으로 확인하자. 두 스레드를 같은 객체에서 wait하게 하고, main이 락을 쥔 채 notify를 한 번 부른 뒤 잠시 락을 놓지 않는다.

    public class WaitStates {
    public static void main(String[] args) throws InterruptedException {
        Object lock = new Object();
        Runnable waiter = () -> {
            synchronized (lock) {
                try {
                    lock.wait();
                } catch (InterruptedException e) {
                    return;
                }
            }
        };
        Thread w1 = new Thread(waiter, "W1");
        Thread w2 = new Thread(waiter, "W2");
        w1.setDaemon(true);
        w2.setDaemon(true);
        w1.start();
        Thread.sleep(100);
        w2.start();
        Thread.sleep(100);
        System.out.println("1) 둘 다 wait 중     : W1=" + w1.getState() + ", W2=" + w2.getState());

        synchronized (lock) {
            lock.notify();
            Thread.sleep(100);
            System.out.println("2) notify, 락은 main: W1=" + w1.getState() + ", W2=" + w2.getState());
        }
        Thread.sleep(100);
        System.out.println("3) main이 락을 놓은 뒤: W1=" + w1.getState() + ", W2=" + w2.getState());
    }
}
    1) 둘 다 wait 중     : W1=WAITING, W2=WAITING
2) notify, 락은 main: W1=BLOCKED, W2=WAITING
3) main이 락을 놓은 뒤: W1=TERMINATED, W2=WAITING

    1)에서 두 스레드는 WAITING이다. Thread.State 문서는 시간 제한 없는 Object.wait를 WAITING에 들어가는 첫 번째 경우로 든다. 2)에서 main이 notify를 불렀지만 아직 락을 쥐고 있다. 깨어난 W1은 대기 집합에서는 빠졌지만 락을 다시 얻지 못해 BLOCKED가 되었다. BLOCKED의 문서 정의가 바로 이 경우를 포함한다. 모니터 락을 얻어 synchronized 블록에 들어가려고 기다리는 스레드뿐 아니라, Object.wait를 부른 뒤 synchronized 블록에 다시 들어가려고 기다리는 스레드도 BLOCKED다. 3)에서 main이 락을 놓자 W1은 락을 얻어 wait에서 돌아오고 람다를 끝내 TERMINATED가 되었다. W2는 알림을 받지 못했으므로 여전히 WAITING이다.

    예제 3: wait와 notify로 다시 만든 버퍼

    이제 버퍼를 다시 만든다. 조건이 맞지 않으면 sleep 대신 wait를 부르고, 상태를 바꾼 뒤에는 notify로 기다리는 스레드 하나를 깨운다. 생산자가 데이터를 넣으면 버퍼가 비어 있지 않게 되므로 기다리던 소비자에게 알려야 하고, 소비자가 데이터를 꺼내면 빈자리가 생기므로 기다리던 생산자에게 알려야 한다. 그런데 이 객체의 대기 집합은 하나뿐이고 notify는 그 안의 누구를 깨울지 고르지 못한다. 이 점은 일단 그대로 두고 동작을 먼저 보자.

    import java.util.ArrayDeque;
import java.util.Queue;

public class WaitBuffer implements Buffer {
    private final Queue queue = new ArrayDeque<>();
    private final int capacity;

    public WaitBuffer(int capacity) {
        this.capacity = capacity;
    }

    @Override
    public synchronized void put(String data) throws InterruptedException {
        while (queue.size() == capacity) {
            Log.log("put: 가득 참, wait " + data);
            wait();                          // 락을 놓고 대기 집합으로
            Log.log("put: 깨어남 " + queue);
        }
        queue.offer(data);
        Log.log("put: 저장 " + data + " " + queue + ", notify");
        notify();
    }

    @Override
    public synchronized String take() throws InterruptedException {
        while (queue.isEmpty()) {
            Log.log("take: 비어 있음, wait");
            wait();
            Log.log("take: 깨어남 " + queue);
        }
        String data = queue.poll();
        Log.log("take: 꺼냄 " + data + " " + queue + ", notify");
        notify();
        return data;
    }
}

    wait()와 notify() 앞에 아무것도 없으니 this.wait(), this.notify()다. synchronized 인스턴스 메서드가 잠그는 객체도 this이므로, 락과 대기 집합이 같은 객체의 것이 된다. 바이트코드로 확인해 보자. 로그를 뺀 용량 1짜리 버퍼를 따로 만들어 javap -c로 보면 구조가 잘 보인다. 이 Box는 뒤의 한계 절에서도 다시 쓴다.

[C2] take: 비어 있음, wait
[P2] put: 저장 data2 [data2], notify
[C3] take: 깨어남 [data2]
[C3] take: 꺼냄 data2 [], notify
[C2] take: 깨어남 []
[C2] take: 비어 있음, wait
[P3] put: 저장 data3 [data3], notify
[C2] take: 깨어남 [data3]
[C2] take: 꺼냄 data3 [], notify
C1: TERMINATED
...

    이번에도 결과는 올바르다. 그런데 과정이 흥미롭다. 대기 집합의 변화를 한 줄씩 적으면 다음과 같다. 대괄호 안은 대기 집합에 있는 스레드이고, 왼쪽이 먼저 들어온 쪽이다.

      사건                                         대기 집합        큐
  C1 비어 있음 → wait                          [C1]             []
  C2 비어 있음 → wait                          [C1, C2]         []
  C3 비어 있음 → wait                          [C1, C2, C3]     []
  P1 data1 저장, notify → C1 선택              [C2, C3]         [data1]
  C1 깨어나 data1 꺼냄, notify → C2 선택       [C3]             []        ← 소비자가 소비자를 깨움
  C2 깨어났지만 비어 있음 → 다시 wait          [C3, C2]         []        ← 헛걸음
  P2 data2 저장, notify → C3 선택              [C2]             [data2]
  C3 깨어나 data2 꺼냄, notify → C2 선택       []               []        ← 또 소비자가 소비자를 깨움
  C2 깨어났지만 비어 있음 → 다시 wait          [C2]             []        ← 헛걸음
  P3 data3 저장, notify → C2 선택              []               [data3]
  C2 깨어나 data3 꺼냄, notify → (대기자 없음)  []               []

    C1이 데이터를 꺼낸 뒤 부른 notify의 의도는 "빈자리가 생겼다"는 소식을 생산자에게 전하는 것이다. 그러나 대기 집합에는 소비자밖에 없었고, notify는 소비자 C2를 깨웠다. C2는 락을 다시 얻고, 조건을 다시 검사하고, 여전히 비어 있음을 확인하고, 다시 대기 집합으로 돌아갔다. 이 헛걸음이 두 번 일어났다. 결과는 맞지만 쓸모없는 깨어남과 락 획득, 그에 따른 컨텍스트 스위칭이 생긴 것이다. 이 예제에서는 생산자가 100ms 간격으로 오기 때문에 이 헛걸음이 결과를 망치지 않았다. 하지만 뒤에서 보듯 조건이 조금만 바뀌면 같은 헛걸음이 프로그램 전체를 멈춰 세운다.

    깨어난 순서가 C1, C2, C3처럼 먼저 기다린 순서와 같다는 것도 눈에 띈다. 이것은 명세가 보장한 결과가 아니다. 명세는 선택이 임의라고만 한다. 이 순서가 어디서 나왔는지는 HotSpot의 구현을 보면 알 수 있다.

    HotSpot 안에서: ObjectMonitor의 대기 집합과 진입 목록

    HotSpot은 경합이 생기거나 wait가 필요한 객체 모니터를 C++ 객체 ObjectMonitor로 표현한다. OpenJDK 21의 objectMonitor.hpp에서 이 회차와 관련된 필드는 다음과 같다. _owner는 락을 쥔 스레드를 가리킨다. _recursions는 재진입 횟수이며 처음 진입하면 0이다. _cxq와 _EntryList는 락을 얻으려고 막힌 스레드들이 머무는 두 목록이다. 주석에 따르면 _cxq는 최근에 도착한 스레드들의 연결 리스트이고, _EntryList는 진입 또는 재진입 때문에 막힌 스레드들의 목록이다. 그리고 _WaitSet이 wait() 중인 스레드들의 목록, 즉 JLS가 말한 대기 집합의 실체다. _WaitSet은 _WaitSetLock이라는 단순한 스핀 락으로 보호된다.

                          ObjectMonitor (객체 하나당 하나, 필요할 때 만들어진다)
  ┌──────────────────────────────────────────────────────────────────────────┐
  │  _owner      = 락을 쥔 스레드                                             │
  │  _recursions = 재진입 횟수 (첫 진입이면 0)                                │
  │                                                                          │
  │  _cxq / _EntryList : 락을 기다리는 스레드들          → 상태 BLOCKED      │
  │       ▲  (진입 대기, 그리고 notify로 옮겨진 재진입 대기)                  │
  │       │ notify / notifyAll 이 옮긴다                                      │
  │  _WaitSet   : wait() 중인 스레드들 (원형 이중 연결 리스트) → WAITING     │
  └──────────────────────────────────────────────────────────────────────────┘

    wait의 경로는 ObjectSynchronizer::wait에서 시작한다. 이 함수는 가장 먼저 객체의 모니터를 팽창(inflate)시킨다. HotSpot은 경합이 없는 락을 ObjectMonitor 없이 객체 헤더(마크 워드)와 스레드 쪽 잠금 기록만으로 처리하는 가벼운 방식으로 시작하는데, 대기 집합은 그런 가벼운 락 상태에 담을 자리가 없다. 그래서 wait를 부르는 순간 그 객체에는 ObjectMonitor가 붙는다. 반대로 notify 쪽 코드에는, 객체가 아직 팽창하지 않은 가벼운 락 상태라면 대기자가 있을 수 없으므로 바로 돌아간다는 분기가 있다.

    ObjectMonitor::wait는 JLS의 단계를 거의 그대로 구현한다. 현재 스레드를 나타내는 대기 노드를 만들고 AddWaiter로 _WaitSet에 넣는다. 이 함수의 주석은 노드를 큐의 끝(원형 이중 연결 리스트의 꼬리)에 넣는다고 적는다. 그다음 현재 재진입 횟수 _recursions를 지역 변수 save에 저장하고 0으로 만든 뒤 exit로 모니터를 빠져나간다. JLS가 말한 "n번의 unlock"이 이것이다. 재진입 횟수를 따로 저장해 두었다가 한 번에 놓는 것이다. 그리고 스레드는 park로 잠든다. 알림으로 깨어난 뒤에는 ReenterI로 락을 다시 얻고, 저장해 둔 save를 _recursions에 되돌린다. 재진입 횟수가 복원되므로 synchronized를 몇 겹으로 중첩했든 wait가 끝난 뒤의 락 상태는 호출 전과 같다.

    notify는 먼저 현재 스레드가 소유자인지 검사한다. 아니면 여기서 IllegalMonitorStateException이 난다. _WaitSet이 비어 있으면 그냥 반환한다. 대기자가 있으면 INotify가 DequeueWaiter로 대기 집합의 맨 앞 노드를 꺼낸다. 함수 주석이 "맨 처음 대기자를 꺼낸다"고 적어 두었다. 꺼낸 노드는 _EntryList가 비어 있으면 그곳에, 아니면 _cxq의 맨 앞에 넣는다. 꼬리에 넣고 머리에서 꺼내므로 OpenJDK 21의 HotSpot에서 notify는 대기 집합 안에서 가장 오래 기다린 스레드를 고른다. 예제 3에서 C1, C2, C3 순서로 깨어난 것은 이 구현 때문이다. 하지만 이것은 구현의 선택일 뿐이다. 명세는 선택이 임의라고 하고, 깨어난 스레드가 락을 다시 얻는 순서는 다른 스레드의 진입 경쟁에 따라 또 달라진다. 이 순서에 기대는 코드는 명세상 틀린 코드다.

    주목할 점이 하나 더 있다. notify는 깨운 스레드를 즉시 실행시키지 않는다. 대기 노드를 진입 목록으로 옮기기만 하고, 실제로 그 스레드를 unpark하는 것은 나중에 알린 스레드가 모니터를 빠져나갈 때의 exit다. 소스의 설명 주석은 그 이유를 이렇게 설명한다. notify 안에서 곧바로 깨우면, 깨어난 스레드는 알린 스레드가 아직 쥐고 있는 락에 부딪혀 다시 막힐 가능성이 크므로 비효율적이다. 앞의 실험에서 notify 직후 W1이 WAITING에서 BLOCKED로 바뀐 것은 대기 노드가 _WaitSet에서 진입 목록으로 옮겨진 모습이다. notifyAll은 _WaitSet이 빌 때까지 INotify를 반복한다. 소스 주석에 따르면 이렇게 하나씩 앞에 붙이는 방식에서는 대기 순서가 뒤집혀 진입 목록에 들어갈 수 있다. 이것 역시 구현의 사정이며, 프로그램이 의존해서는 안 된다.

    스레드가 진입 목록에서 소유자 자리로, 소유자 자리에서 wait로 대기 집합으로, notify로 대기 집합에서 진입 목록으로 옮겨 가는 경로와 각 위치의 Thread.State를 보여 준다. 가운데에 큰 직사각형 "객체 모니터". 그 안을 세 구역으로 나눈다. 왼쪽 구역 "진입 목록 (EntryList / cxq)"에는 사람 아이콘 두 개와 라벨 "BLOCKED". 가운데 구역은 작은 방 모양 "소유자 (_owner)"이고 사람 아이콘 한 개와 라벨 "RUNNABLE", 방 문에 열쇠 아이콘. 오른쪽 구역 "대기 집합 (WaitSet)"에는 사람 아이콘 세 개가 원형으로 서 있고 라벨 "WAITING". 화살표 네 개: 진입 목록에서 소유자로 "락 획득", 소유자에서 대기 집합으로 "wait(): 락을 모두 놓음", 대기 집합에서 진입 목록으로 "notify / notifyAll", 소유자에서 바깥 오른쪽 아래로 "synchronized 종료: 락 해제". 직사각형 바깥 왼쪽에서 진입 목록으로 들어오는 화살표 "synchronized 진입 시도". 흰 배경, 깔끔한 다이어그램 스타일. notify는 대기 집합의 스레드를 진입 목록으로 옮길 뿐이다. 그 스레드는 락을 다시 얻어야 wait에서 돌아온다.

    한 층 더 아래: wait가 잠들고 돌아오는 길

    앞 절에서는 ObjectMonitor::wait가 대기 집합에 들어가 모니터를 빠져나간 뒤 "park로 잠든다"고만 했다. 6회차에서 본 것처럼 BLOCKED 스레드는 자기 ParkEvent(POSIX 계열에서는 정수 _event 하나와 pthread 뮤텍스·조건 변수 한 쌍으로 된 PlatformEvent)에서 잠들고, 락을 놓는 exit가 후계자 하나를 골라 깨운다. wait도 같은 ParkEvent를 쓴다. 이 절에서는 그 위에서 wait에만 해당하는 부분, 즉 잠들기 직전의 준비, park에서 돌아온 뒤의 판단, 그리고 notify와 실제 깨움 사이의 거리를 따라간다. 모두 OpenJDK 21(jdk21u) HotSpot 소스와 이 실험 환경(macOS, Apple Silicon) 기준이며, 명세가 아니라 구현의 사정이다.

    네이티브 스택으로 본 wait

    먼저 wait 중인 스레드가 실제로 어디에 있는지 보자. macOS에 기본으로 들어 있는 sample 명령은 지정한 프로세스의 모든 스레드 스택을 네이티브 프레임까지 반복해서 채집한다.

    public class Park {
    public static void main(String[] args) throws Exception {
        Object lock = new Object();
        Thread w = new Thread(() -> {
            synchronized (lock) {
                try { lock.wait(); } catch (InterruptedException e) { }
            }
        }, "W");
        w.setDaemon(true);
        w.start();
        Thread.sleep(8000);
    }
}

    Object.wait0 네이티브 메서드가 JVM_MonitorWait로 들어가고, ObjectSynchronizer::wait가 모니터를 팽창시켜 ObjectMonitor::wait를 부르고, 그것이 PlatformEvent::park()를 거쳐 pthread 조건 변수에서 커널로 들어간다. 6회차의 BLOCKED 스레드와 같은 바닥이지만 한 가지가 다르다. 진입 대기 스레드는 경우에 따라 시간 제한이 있는 park_nanos로 주기적으로 깨어나 락을 다시 확인하는데, 시간 제한 없는 wait()는 인자 없는 park()를 부른다. 깨워 주는 쪽이 오기 전에는 스스로 일어날 이유가 없다. 1초 동안 837번 채집했는데 모두 이 프레임에 있었고, 같은 시점의 jcmd 출력에서 W의 누적 CPU 시간은 cpu=0.03ms였다. 자바의 WAITING은 운영체제에게는 조건 변수에서 잠들어 스케줄링 대상에서 빠진 스레드다.

    잠들기 직전: 남은 허가를 지운다

    PlatformEvent는 허가(permit) 하나짜리 세마포어다. unpark가 park보다 먼저 오면 _event가 1로 남고, 다음 park는 그 허가를 쓰고 잠들지 않은 채 곧바로 돌아온다. 신호 유실을 막는 성질이지만, wait에게는 함정이 될 수 있다. 같은 ParkEvent는 모니터 진입 대기와 인터럽트에도 쓰이므로, 지난번에 받은 unpark가 허가로 남아 있다면 이번 wait의 park는 알림도 없이 즉시 돌아올 것이다. ObjectMonitor::wait는 대기 노드를 만들면서 _ParkEvent->reset()으로 _event를 0으로 되돌리고, 메모리 펜스를 친 뒤 대기 집합에 들어간다. 남아 있던 허가는 여기서 지워지고, 이번 park는 그 뒤에 온 unpark에만 반응한다. 소스 주석은 reset 뒤 park 전에 대기 중인 인터럽트를 반드시 확인해야 한다고 강조하고, 실제로 모니터를 빠져나온 뒤 park 직전에 인터럽트 상태를 한 번 더 본다. 인터럽트 상태가 이미 켜져 있으면 park를 건너뛴다. 허가를 지운 탓에 그 사이 들어온 인터럽트를 놓치는 일이 없게 하려는 순서다.

    park에서 돌아온 뒤: 알림인지 스스로 확인한다

    ObjectMonitor::wait는 park를 반복문으로 감싸지 않는다. 알림을 아직 받지 않았으면(node._notified == 0) 시간 제한에 따라 park()나 park(millis)를 한 번 부르고, 돌아오면 자기 노드의 상태를 본다. 노드가 아직 대기 집합에 있다면(TS_WAIT) 알림 때문에 깨어난 것이 아니다. 이때 스레드는 _WaitSetLock을 잡고 스스로 대기 집합에서 빠진 뒤(DequeueSpecificWaiter) 락 재획득 단계로 넘어간다. 시간 만료와 인터럽트가 이 길로 나오고, 그 밖의 이유로 _ParkEvent가 깨워져도 같은 길을 탄다. 노드가 이미 진입 목록(TS_ENTER/TS_CXQ)에 있다면 알림을 받은 것이고, ReenterI로 락을 다시 얻는다. 소스에는 이 부분을 while (!timeout && !interrupted && _notified == 0) park() 형태의 반복으로 바꾸자는 TODO 주석이 그대로 남아 있다.

    이것을 아래층과 나란히 놓으면 구조가 보인다. PlatformEvent::park는 pthread_cond_wait를 _event가 음수인 동안 반복해 운영체제 수준의 가짜 깨어남을 걸러 낸다(소스 주석: "OS-level spurious wakeups are ignored"). 반면 그 위의 ObjectMonitor::wait는 park가 돌아온 이유를 따지지 않고, 알림이 아니면 그냥 wait를 끝낸다. park.hpp의 주석도 park()는 이유 없이 돌아올 수 있으며 부르는 쪽이 그것을 견뎌야 한다고 적는다. 정리하면 OpenJDK 21에서 wait가 알림 없이 돌아오는 경로는 코드에 실제로 존재하고, 그 경로를 견디는 책임은 맨 위의 자바 코드, 즉 우리가 쓰는 while 반복문에 있다. JLS 17.2.1이 가짜 깨어남을 허용하고 API 문서가 while을 요구하는 것은 추상적인 경고에 그치지 않는다. 다만 이 경로가 실제로 얼마나 자주 쓰이는지는 이 실험에서 관찰하지 못했으므로, 여기서는 경로가 있다는 사실까지만 적는다.

    notify와 실제 깨움 사이: notifyAll은 사슬로 이어진다

    notify가 부르는 INotify는 대기 노드를 진입 목록으로 옮기고, 노드에 _notified = 1과 알린 스레드의 ID(_notifier_tid)를 적을 뿐 unpark를 부르지 않는다. 운영체제 수준의 깨움은 알린 스레드가 모니터를 빠져나갈 때 exit가 진입 목록에서 후계자 한 스레드를 골라 그 스레드의 ParkEvent를 unpark할 때 일어난다(exit의 동작은 6회차에서 보았다). notifyAll도 다르지 않다. 소스에서 notifyAll은 _WaitSet이 빌 때까지 INotify를 반복하는 것이 전부이고, 바로 위의 주석은 대기자들을 한 번에 하나씩 옮기며 이때 순서가 뒤집힐 수 있다고 적는다.

    그러니 OpenJDK 21에서 notifyAll은 대기자 N명을 한꺼번에 운영체제에서 깨우지 않는다. N개의 노드를 진입 목록에 옮겨 놓을 뿐이고, 그 뒤로는 모니터를 빠져나가는 exit가 한 번에 많아야 한 스레드씩 깨운다. 이미 깨워 둔 후계자(_succ)가 아직 락을 얻지 못한 상태라면 exit는 아무도 깨우지 않고 돌아간다. 깨어난 스레드가 락을 얻어 조건을 확인하고, 거짓이면 다시 wait로 대기 집합에 들어가며 모니터를 빠져나가면, 그 exit가 다음 후계자를 깨우는 식으로 사슬처럼 이어진다. JLS 17.2.2의 "깨어난 스레드들은 한 번에 하나씩 락을 다시 얻는다"가 구현에서는 이런 모양이다. 그렇다고 비용이 사라지지는 않는다. N명 각자가 결국 unpark 한 번, 커널에서 돌아오기, 락 재획득, 조건 재확인, 다시 park를 한 바퀴씩 치른다. 이 비용을 직접 세어 보는 일은 한계 절 뒤로 미룬다.

    JFR로 보는 알림의 주인: 누가 누구를 깨웠나

    앞 절에서 INotify가 대기 노드에 알린 스레드의 ID를 적어 둔다고 했다. 이 값은 어디에 쓰일까. ObjectMonitor::wait는 락을 다시 얻기 직전에 JFR(JDK Flight Recorder) 이벤트 jdk.JavaMonitorWait를 기록하는데, 그때 이 ID를 "알린 스레드"로, 시간 만료 여부를 "timedOut"으로 넘긴다. 즉 JFR은 wait 한 번마다 누가 기다렸고, 얼마나 기다렸고, 누가 깨웠는지를 남긴다. 예제 3의 소비자 우선 실행에서 손으로 그렸던 대기 집합 표를 JVM이 직접 기록한 데이터로 확인해 보자.

    몇 가지 세부를 알아 두면 실무에서 이 이벤트를 읽기 쉽다. 첫째, JDK에 들어 있는 기본 설정 파일은 이 이벤트에 문턱값을 둔다. 이 실험 환경의 JDK에서 lib/jfr/default.jfc는 20ms, profile.jfc는 10ms다. 그보다 짧은 wait는 기록되지 않으므로, 위 실험에서는 문턱값을 0ms로 내렸다. 둘째, 알림이 아닌 이유로 끝난 wait에는 알린 스레드가 없다. 아무도 알리지 않는 lock.wait(50)을 같은 방법으로 녹화하면 notifier = N/A, timeout = 50.0 ms, timedOut = true로 기록된다. 소스에서 _notifier_tid를 채우는 곳이 INotify뿐이므로, 인터럽트로 끝난 wait도 알린 스레드가 비어 있다. 셋째, 스레드 덤프가 "지금 이 순간 누가 어디서 기다리는가"를 보여 준다면, 이 이벤트는 "지난 시간 동안 누가 누구를 깨웠는가"를 보여 준다. 대기 시간이 긴 wait가 많은데 그 알린 스레드가 대부분 같은 역할(예: 소비자가 소비자를)이라면, 예제 3과 같은 헛걸음이 일어나고 있다는 증거가 된다.

    if가 아니라 while이어야 하는 이유

    예제 3에서 wait를 while로 감쌌다. if로 바꿔도 될 것 같지만 그렇지 않다. 가장 짧게 보여 주는 실험부터 하자. 빈 버퍼에서 소비자 두 개가 기다리고, 생산자가 데이터 하나를 넣은 뒤 notifyAll을 부른다. 소비자는 if로 한 번만 검사한다.

    import java.util.ArrayDeque;
import java.util.Queue;

public class IfDemo {
    private final Queue queue = new ArrayDeque<>();

    synchronized void put(String data) {
        queue.offer(data);
        notifyAll();
    }

    synchronized String take() throws InterruptedException {
        if (queue.isEmpty()) {     // 잘못: while이어야 한다
            wait();
        }
        return queue.remove();     // 비어 있으면 NoSuchElementException
    }

    public static void main(String[] args) throws InterruptedException {
        IfDemo buffer = new IfDemo();
        Runnable consumer = () -> {
            try {
                Log.log("받음 " + buffer.take());
            } catch (InterruptedException e) {
                return;
            }
        };
        Thread c1 = new Thread(consumer, "C1");
        Thread c2 = new Thread(consumer, "C2");
        c1.start();
        c2.start();
        Thread.sleep(100);
        buffer.put("x");
        c1.join();
        c2.join();
    }
}

    notifyAll은 두 소비자를 모두 대기 집합에서 꺼낸다. 둘은 한 번에 하나씩 락을 다시 얻는다. 먼저 얻은 C1은 x를 꺼내 간다. 뒤이어 락을 얻은 C2는 wait에서 돌아온 뒤 if 블록을 빠져나가 곧바로 remove()를 부른다. 조건을 다시 보지 않았으므로 빈 큐에서 꺼내려다 예외가 난다. while이었다면 C2는 비어 있음을 다시 확인하고 대기 집합으로 돌아갔을 것이다. 두 줄의 출력 순서는 실행마다 바뀔 수 있다. 예외 메시지는 C2의 기본 예외 처리기가, "받음" 로그는 C1이 각자 찍기 때문이다.

    정리하면 wait에서 돌아온 스레드가 조건이 거짓인 상태를 보게 되는 경로는 적어도 네 가지다.

    1. 여러 스레드가 함께 깨어난다. notifyAll은 대기 집합 전체를 깨우지만, 바뀐 상태는 그중 일부만 쓸 수 있다. 위의 실험이 이 경우다.
    2. 다른 스레드가 끼어든다. notify로 한 스레드만 깨워도, 그 스레드가 락을 다시 얻기 전에 대기 집합 밖에 있던 다른 스레드가 먼저 락을 얻어 상태를 바꿀 수 있다. notify의 API 문서가 깨어난 스레드는 다음 락 획득에서 믿을 만한 우선권도 불이익도 없다고 적은 것이 이 뜻이다. 소비자 A가 알림을 받고 락을 기다리는 사이 새로 도착한 소비자 B가 먼저 들어와 데이터를 가져가면, A가 돌아왔을 때 버퍼는 다시 비어 있다.
    3. 가짜 깨어남(spurious wakeup). JLS 17.2.1은 구현이 알림이나 인터럽트, 시간 만료 없이도 스레드를 대기 집합에서 제거하는 것을 허용한다(권장하지는 않는다). 명세는 바로 이 조항 때문에 wait를 조건이 참이 될 때만 끝나는 반복문 안에서만 쓰는 관행이 필요하다고 덧붙인다. Object.wait의 API 문서도 실제로는 드물지만 애플리케이션은 이것에 대비해야 한다고 말한다.
    4. 엉뚱한 종류의 스레드가 깨어난다. 대기 집합이 하나뿐이므로, 소비자가 생산자를 깨우려고 부른 notify가 다른 소비자를 깨울 수 있다. 예제 3의 소비자 우선 실행에서 C2가 두 번 깨어났지만 큐는 비어 있었다. 그 코드가 if였다면 C2는 첫 번째 헛걸음에서 빈 큐의 poll()을 불러 null을 받아 갔을 것이다.

    그래서 Object.wait의 API 문서는 기다리는 조건을 wait 호출을 둘러싼 while 반복문에서 검사하라고 권하고, 다음 형태를 예로 든다. wait에서 돌아온다는 것은 "조건이 참이 되었다"가 아니라 "조건이 바뀌었을지도 모르니 다시 확인하라"는 뜻으로 읽어야 한다.

    synchronized (obj) {
    while (/* 조건이 아직 성립하지 않음 */) {
        obj.wait();
    }
    // 조건이 성립한 상태에서 할 일
}

    wait/notify의 한계

    깨울 대상을 고를 수 없다

    예제 3의 버퍼에는 서로 다른 두 조건을 기다리는 스레드들이 있다. 생산자는 "가득 차 있지 않음"을, 소비자는 "비어 있지 않음"을 기다린다. 그런데 객체 하나에 대기 집합은 하나뿐이어서 두 종류가 한 방에 섞여 있다. notify는 그 방에서 한 명을 임의로 고를 뿐 "생산자 중에서" 같은 조건을 붙일 수 없다. 생산자가 데이터를 넣고 부른 notify가 다른 생산자를 깨우면, 깨어난 생산자는 여전히 가득 찬 버퍼를 보고 다시 잔다. 소비자 쪽도 마찬가지다. 앞에서 본 헛걸음이 이것이다. 헛걸음은 낭비에서 끝나지 않을 수 있다. 알림 하나를 엉뚱한 스레드가 받아 버리면, 정작 그 알림이 필요했던 스레드는 아무도 깨워 주지 않는다.

    모두가 잠드는 실행

    용량 1인 Box에 생산자 둘과 소비자 둘이 반복해서 넣고 꺼내는 상황을 손으로 추적해 보자. 아래 순서는 명세가 허용하는 실행 중 하나다. notify가 누구를 고를지, 깨어난 스레드와 새로 도착한 스레드 중 누가 먼저 락을 얻을지는 명세가 정하지 않으므로, 각 단계의 선택은 모두 합법적이다.

    단계사건item대기 집합
    1C1 take: 비어 있음 → waitnull[C1]
    2C2 take: 비어 있음 → waitnull[C1, C2]
    3P1 put x, notify → C1이 대기 집합에서 빠짐(락은 아직 못 얻음)x[C2]
    4P1이 다음 반복에서 C1보다 먼저 락을 얻음: 가득 참 → waitx[C2, P1]
    5P2 put: 가득 참 → waitx[C2, P1, P2]
    6C1이 락을 다시 얻어 x를 꺼냄, notify → C2가 선택됨null[P1, P2]
    7C1이 다음 반복에서 C2보다 먼저 락을 얻음: 비어 있음 → waitnull[P1, P2, C1]
    8C2가 락을 다시 얻음: 비어 있음 → wait (알림을 보내지 않는다)null[P1, P2, C1, C2]

    8단계가 끝나면 네 스레드 모두 대기 집합에 있다. 깨워 줄 스레드가 하나도 남지 않았으므로 이 상태는 영원히 계속된다. 결정적인 실수는 6단계다. C1이 상자를 비우고 보낸 알림은 생산자에게 가야 했지만 소비자 C2가 받았고, C2는 할 일이 없어 그대로 다시 잠들었다. 알림이 사라진 것이다. 앞 절의 신호 유실은 락 없이 기다릴 때 생겼지만, 이번에는 모든 규칙을 지켰는데도 알림이 엉뚱한 스레드에게 소비되어 사라졌다. OpenJDK의 objectMonitor.cpp에도 notifyAll이 맞는 자리에 notify를 쓰는 것이 드물지 않은 동기화 버그이며, 스레드들이 오도 가도 못하게 되는(stranded) 신호 유실의 한 예라는 주석이 달려 있다.

    손으로 만든 시나리오가 실제로도 일어나는지 확인해 보자. 네 스레드가 각각 10만 번씩 넣거나 꺼낸다.

    import java.util.List;

public class Stranded {
    public static void main(String[] args) throws InterruptedException {
        int rounds = 100_000;
        Box box = new Box();
        List threads = List.of(
            new Thread(() -> loop(() -> box.put("x"), rounds), "P1"),
            new Thread(() -> loop(() -> box.put("y"), rounds), "P2"),
            new Thread(() -> loop(box::take, rounds), "C1"),
            new Thread(() -> loop(box::take, rounds), "C2"));
        for (Thread t : threads) {
            t.setDaemon(true);
            t.start();
        }
        for (Thread t : threads) {
            t.join(5000);
        }
        for (Thread t : threads) {
            System.out.println(t.getName() + ": " + t.getState());
        }
    }

    interface Action { void run() throws InterruptedException; }

    static void loop(Action action, int rounds) {
        try {
            for (int i = 0; i < rounds; i++) action.run();
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }
}

    넣는 횟수와 꺼내는 횟수가 똑같이 20만 번이므로 정상이라면 네 스레드 모두 TERMINATED로 끝나야 한다. 실제로는 네 스레드 모두 WAITING, 즉 Box의 대기 집합에 갇혔다. 몇 번째 반복에서 갇히는지는 실행마다 다르고, 이 결과는 이 환경(OpenJDK 21.0.13, macOS)에서 관찰한 것이다. 다른 환경에서 끝까지 실행되는 경우가 있더라도 코드가 옳다는 뜻은 아니다. 명세가 허용하는 실행 중에 멈추는 실행이 있다는 사실만으로 이 코드는 틀렸다. 이때 스레드 덤프에도 "deadlock"이라는 말은 나오지 않는다. 네 스레드 모두 - waiting on 같은 객체로 대기 집합에 있을 뿐, 락을 쥐고 다른 락을 기다리는 순환이 없기 때문이다.

    P1, P2, C1, C2 네 개의 생명선과 Box를 두고, 표의 8단계를 화살표로 보여 준다. 6단계에서 C1의 notify가 C2에게 가는 화살표를 강조한다. 시퀀스 다이어그램. 위쪽에 생명선 머리 다섯 개를 가로로 배치: "P1", "P2", "Box (용량 1)", "C1", "C2". 위에서 아래로 시간 흐름. C1과 C2에서 Box로 "wait" 화살표가 먼저 내려가고 두 생명선이 회색으로 바뀐다. P1에서 Box로 "put x + notify" 화살표, Box에서 C1으로 짧은 화살표. 이어서 P1과 P2에서 Box로 "wait" 화살표가 가고 둘의 생명선이 회색이 된다. C1에서 Box로 "take + notify" 화살표가 있고, Box에서 C2로 가는 빨간 굵은 화살표에 "알림이 소비자에게 감" 라벨. 마지막에 C1과 C2가 다시 "wait"로 회색이 된다. 맨 아래에 네 생명선이 모두 회색인 구역을 가로지르는 빨간 띠와 "모두 WAITING: 깨워 줄 스레드 없음" 라벨. 흰 배경, 단순한 선 스타일. 알림 하나가 같은 종류의 스레드에게 소비되면, 그 알림이 필요했던 스레드들은 아무도 깨우지 않는다.

    notifyAll: 맞게 동작하지만 모두를 깨운다

    가장 단순한 해결책은 notify를 notifyAll로 바꾸는 것이다. Box의 두 notify()만 notifyAll()로 바꾸고 나머지는 그대로 둔 채 같은 실험을 돌리면 네 스레드가 모두 TERMINATED로 끝난다. 이 환경에서는 JVM 시작까지 포함해 매번 몇 초 안에 끝났다(소요 시간은 실행마다, 기계의 부하에 따라 다르다). 이유는 간단하다. 상태를 바꾼 스레드가 대기 집합 전체를 깨우므로, 그 안에 있던 반대 종류의 스레드도 반드시 깨어난다. 같은 종류의 스레드들은 while로 조건을 다시 보고 도로 잠들 뿐이다. notifyAll을 쓰더라도 while이 없으면 앞의 IfDemo처럼 깨진다는 점에 주의하자. notifyAll과 while은 짝으로 써야 한다.

    대가는 효율이다. 대기 집합에 스레드가 N개 있으면 알림 한 번에 N개가 모두 깨어나고, 락을 한 번에 하나씩 다시 얻으며, 대부분은 조건이 거짓임을 확인하고 다시 잠든다. 깨어난 스레드마다 운영체제 수준의 깨움과 스케줄링, 그리고 모니터 경합이 생긴다. 대기자가 몇 개뿐이면 문제가 되지 않지만, 대기자가 많은 시스템에서는 알림 한 번이 많은 스레드를 한꺼번에 흔든다.

    그렇다면 notify로 충분한 경우는 언제일까. 위의 실패 분석에서 거꾸로 조건을 얻을 수 있다. 첫째, 대기 집합의 모든 스레드가 같은 조건을 기다리고 깨어나서 같은 일을 해야 한다. 그래야 누가 깨어나든 상관없다. 둘째, 한 번의 상태 변경이 최대 한 스레드만 진행할 수 있게 해야 한다. 그래야 한 명만 깨워도 손해가 없다. 생산자와 소비자가 한 대기 집합에 섞인 버퍼는 첫째 조건을 어기므로 notify가 위험하다. 반면 생산자 하나와 소비자 하나뿐이라면 이야기가 다르다. 연습 문제에서 그 경우를 따져 본다.

    공정성과 기아

    명세는 notify가 누구를 고를지, 깨어난 스레드들이 어떤 순서로 락을 얻을지 보장하지 않는다. 따라서 이론적으로는 특정 스레드가 계속 선택받지 못하거나, 깨어날 때마다 다른 스레드에게 락을 빼앗겨 조건이 거짓인 상태만 보게 될 수 있다. 이런 현상을 기아(starvation)라고 한다. OpenJDK 21의 HotSpot 구현은 대기 집합에서 가장 오래 기다린 스레드를 고르지만, 락 재획득 단계에서는 새로 도착한 스레드가 끼어들 수 있으므로 구현을 근거로도 순서를 약속할 수 없다. notifyAll도 이 문제를 해결하지 못한다. 모두 깨어나지만 누가 먼저 락을 얻을지는 여전히 정해져 있지 않다.

    그 밖의 제약

    wait(long)은 반환값이 없다. 돌아왔을 때 알림을 받아서인지, 시간이 다 되어서인지, 가짜 깨어남인지를 메서드가 알려 주지 않는다. 그래서 시간 제한을 두고 기다리려면 마감 시각을 직접 계산하고, 깨어날 때마다 조건과 남은 시간을 함께 다시 확인해야 한다. API 문서의 권장 예제가 반복문 안에서 시간 제한 값을 다시 계산하는 모양인 이유다. 또한 7회차에서 본 것처럼 synchronized의 락 획득 자체는 인터럽트로 중단하거나 시간 제한을 둘 수 없으므로, wait에서 깨어나 락을 다시 얻는 구간도 같은 제약을 받는다.

    가상 스레드와 함께 쓸 때의 사정도 버전에 따라 다르다. JEP 444(Java 21)는 JDK의 일부 블로킹 연산이 가상 스레드를 캐리어에서 떼어 내지 못하고 캐리어와 OS 스레드까지 붙잡는다며 그 예로 Object.wait()를 들고, 이를 보상하려고 스케줄러의 병렬성을 일시적으로 늘린다고 설명한다. JDK 21의 Object.wait(long)이 Blocker.begin()으로 호출을 감싸는 것이 그 보상 장치다. 이 제약은 JEP 491(Java 24)에서 바뀌어, Object.wait()가 기다리는 동안과 모니터를 다시 얻으려고 막힌 동안 가상 스레드를 캐리어에서 떼어 낼 수 있게 되었다. 기준 버전인 Java 21에서는 가상 스레드에서 wait를 많이 쓰면 캐리어 스레드가 묶인다는 점을 기억해 두자.

    근본 원인은 하나로 모인다. 락 하나에 대기 집합이 하나뿐이라는 구조다. 생산자용 대기실과 소비자용 대기실을 따로 둘 수 있다면, 데이터를 넣은 생산자는 소비자 대기실에만, 데이터를 꺼낸 소비자는 생산자 대기실에만 알릴 수 있다. 그러면 notify로 한 명만 깨워도 반드시 맞는 종류가 깨어나고, 모두를 깨우는 낭비도 없다. 다음 회차에서 다룰 Lock과 Condition이 이 구조를 제공하며, 자바 표준 라이브러리의 BlockingQueue 구현들이 그 위에 만들어져 있다. JEP 491도 Condition API를 Object.wait()와 Object.notify()에 대응하는 것으로 소개한다.

    대기 비용을 숫자로: 잠든 스레드, 폴링, 스핀, 그리고 notifyAll의 헛걸음

    이 회차에서 비용에 관한 주장을 여러 번 했다. 폴링은 CPU를 버리고, wait로 잠든 스레드는 CPU를 쓰지 않으며, notifyAll은 정확하지만 많은 스레드를 깨운다. 이 주장들을 이 환경에서 직접 재어 보자. 아래 수치는 모두 이 Mac(Apple Silicon, 논리 CPU 8개, macOS, OpenJDK 21.0.13)에서 얻은 것이고, 실행마다, 기계마다 달라진다. 숫자 자체보다 크기의 차이와 경향을 보아야 한다.

    3초 동안 바뀌지 않는 조건을 기다리는 세 가지 방법

    같은 조건(ready가 참이 됨)을 세 스레드가 서로 다른 방법으로 기다린다. waiter는 wait로, poller는 락 밖에서 1ms씩 자는 폴링으로, spinner는 쉬지 않고 확인하는 스핀으로 기다린다. 3초 뒤 각 스레드가 쓴 CPU 시간을 ThreadMXBean.getThreadCpuTime으로 읽고, 그다음에 조건을 참으로 바꾼다.

    import java.lang.management.ManagementFactory;
import java.lang.management.ThreadMXBean;

public class Cost {
    static final Object lock = new Object();
    static boolean ready = false;              // lock으로 보호
    static long waitReturns, pollChecks, spinChecks;

    public static void main(String[] args) throws InterruptedException {
        Thread waiter = new Thread(() -> {
            synchronized (lock) {
                while (!ready) {
                    try { lock.wait(); } catch (InterruptedException e) { return; }
                    waitReturns++;
                }
            }
        }, "waiter");
        Thread poller = new Thread(() -> {
            while (true) {
                synchronized (lock) {
                    if (ready) return;
                    pollChecks++;
                }
                try { Thread.sleep(1); } catch (InterruptedException e) { return; }
            }
        }, "poller");
        Thread spinner = new Thread(() -> {
            while (true) {
                synchronized (lock) {
                    if (ready) return;
                    spinChecks++;
                }
                Thread.onSpinWait();
            }
        }, "spinner");
        waiter.start(); poller.start(); spinner.start();

        Thread.sleep(3000);                    // 조건은 3초 동안 바뀌지 않는다
        ThreadMXBean mx = ManagementFactory.getThreadMXBean();
        for (Thread t : new Thread[]{waiter, poller, spinner}) {
            System.out.printf("%-8s %-14s cpu=%,d us%n", t.getName(), t.getState(),
                    mx.getThreadCpuTime(t.threadId()) / 1000);
        }
        synchronized (lock) {
            ready = true;
            lock.notifyAll();
        }
        waiter.join(); poller.join(); spinner.join();
        System.out.printf("waitReturns=%d pollChecks=%,d spinChecks=%,d%n",
                waitReturns, pollChecks, spinChecks);
    }
}

poller   TIMED_WAITING  cpu=38,156 us

waitReturns=1 pollChecks=2,371 spinChecks=326,884,561

    세 번 실행하는 동안 waiter의 CPU 시간은 37~71µs, poller는 24~38ms, spinner는 3.00~3.01초였다. waiter의 수십 µs는 스레드가 시작해 락을 얻고 wait에 들어가기까지의 비용이고, 3초 동안 잠든 시간은 거의 0이다. waitReturns=1은 wait에서 마지막 notifyAll로 단 한 번 돌아왔다는 뜻이다. 앞에서 sample로 본 대로 그동안 이 스레드는 커널의 조건 변수에서 자고 있었다. spinner는 3초 내내 CPU 하나를 다 썼다. 3억 번 넘게 확인했지만 조건은 한 번도 바뀌지 않았으므로 모두 버려진 일이다.

    poller는 그 중간이다. 세 번 모두 3초 동안 약 2,370~2,380번 확인했는데, 1ms 간격이라면 3,000번이어야 한다. Thread.sleep(1)은 API 문서상 시스템 타이머와 스케줄러의 정밀도에 따르고 HotSpot에서는 1ms가 다 지나야 돌아올 뿐이며, 깨어나서 다시 스케줄링되고 락을 얻는 시간이 더해져 한 바퀴가 평균 1.26ms쯤 걸린 것이다. 확인할 때마다 커널에서 깨어나고, 락을 얻고, 다시 잠드는 일을 반복했으므로 waiter보다 수백 배 많은 CPU 시간을 썼다. 기다리는 스레드가 수백 개라면 이 비용도 그만큼 곱해진다. 한 가지 단서가 있다. spinner가 거의 쉬지 않고 같은 락을 잡으므로, 위 수치에는 poller와 waiter가 그 락을 놓고 경합한 비용도 섞여 있다. 그래도 세 방법 사이의 크기 차이(µs, ms, 초)는 그 경합으로 설명되는 수준을 훨씬 넘는다.

    notifyAll의 헛걸음을 세어 보기

    이번에는 용량 1인 버퍼에서 wait를 몇 번 불렀고, 그중 깨어났는데 조건이 여전히 거짓이었던 "헛걸음"이 몇 번이었는지 센다. 카운터는 모두 락 안에서만 고치므로 정확하다. 전달하는 원소 수는 20만 개로 고정하고, 생산자·소비자 쌍의 수만 바꾼다.

    import java.util.ArrayList;
import java.util.List;

public class Futile {
    private String item;                      // 용량 1인 버퍼
    private long waits, futile;               // 락 안에서만 고친다
    private final boolean all;

    Futile(boolean all) { this.all = all; }

    synchronized void put(String data) throws InterruptedException {
        while (item != null) {
            waits++;
            wait();
            if (item != null) futile++;       // 깨어났지만 여전히 가득 참
        }
        item = data;
        if (all) notifyAll(); else notify();
    }

    synchronized String take() throws InterruptedException {
        while (item == null) {
            waits++;
            wait();
            if (item == null) futile++;       // 깨어났지만 여전히 비어 있음
        }
        String data = item;
        item = null;
        if (all) notifyAll(); else notify();
        return data;
    }

    public static void main(String[] args) throws InterruptedException {
        boolean all = args[0].equals("all");
        int pairs = Integer.parseInt(args[1]);
        int total = 200_000;                  // 전달할 원소 수(모든 경우 같다)
        int each = total / pairs;
        Futile box = new Futile(all);
        List ts = new ArrayList<>();
        for (int i = 0; i < pairs; i++) {
            ts.add(new Thread(() -> { try { for (int k = 0; k < each; k++) box.put("x"); } catch (InterruptedException e) { } }));
            ts.add(new Thread(() -> { try { for (int k = 0; k < each; k++) box.take(); } catch (InterruptedException e) { } }));
        }
        long t0 = System.nanoTime();
        for (Thread t : ts) t.start();
        for (Thread t : ts) t.join();
        long ms = (System.nanoTime() - t0) / 1_000_000;
        synchronized (box) {
            System.out.printf("%-9s 생산자·소비자 %d쌍: wait %,d회, 헛걸음 %,d회 (전달 1건당 %.2f), %d ms%n",
                    all ? "notifyAll" : "notify", pairs, box.waits, box.futile,
                    (double) box.futile / (each * pairs), ms);
        }
    }
}

    먼저 한 쌍일 때를 보자. 헛걸음은 notify든 notifyAll이든 0이다. 연습 문제 5에서 따져 볼 논증, 즉 생산자 하나와 소비자 하나뿐이면 대기 집합에 한 번에 많아야 한 스레드만 있다는 사실이 숫자로 드러난다. 그런데 wait 횟수는 약 40만 번, 전달 1건당 거의 2번이다. 용량이 1이라 생산자는 넣고 나면 다음 반복에서 거의 매번 가득 참을 보고 잠들고, 소비자도 꺼낸 뒤 거의 매번 비어 있음을 보고 잠든다. 헛걸음은 없지만 원소 하나를 넘길 때마다 양쪽이 한 번씩 park와 unpark를 주고받는 셈이다. 버퍼의 용량은 두 스레드가 서로를 기다리지 않고 각자 일할 수 있는 여유이고, 그 여유가 1이면 매번 손에서 손으로 건네야 한다.

    쌍이 늘면 notifyAll의 헛걸음이 생기고 커진다. 두 번의 실행에서 전달 1건당 헛걸음은 2쌍일 때 0.26~0.38, 4쌍일 때 0.81~1.07, 8쌍일 때 1.53~2.07, 16쌍일 때 1.62~3.01이었다. 쌍의 수에 정확히 비례하지 않고 실행마다 크게 흔들리는 이유는, 알림 순간에 대기 집합에 몇 명이 들어가 있는지가 스케줄링에 따라 달라지기 때문이다. 대기 집합에 있는 스레드가 많을수록 notifyAll 한 번이 만드는 헛걸음도 많다. 앞에서 HotSpot 소스로 본 대로 헛걸음 하나는 진입 목록에서 차례를 기다렸다가 exit의 unpark로 깨어나고, 커널에서 돌아와 락을 얻고, 조건을 확인하고, 다시 wait로 대기 집합에 들어가 park하는 한 바퀴다. 전체 소요 시간도 쌍이 늘수록 길어졌다(측정값은 기계의 부하에 따라 달라진다). notifyAll이 "정확하지만 비싸다"는 말의 근거가 이것이고, 같은 종류의 스레드를 깨우지 않으려면 대기실 자체를 나누어야 한다는 결론으로 이어진다.

    생산자 소비자 문제
    데이터를 만드는 스레드와 처리하는 스레드가 유한 버퍼를 사이에 두고 협력하는 문제다. 핵심은 버퍼가 가득 찼을 때와 비었을 때 스레드가 무엇을 하느냐다.
    상호 배제와 조건 동기화
    락은 한 번에 한 스레드만 임계 영역에 들어가게 할 뿐, 조건이 맞을 때까지 기다리게 하지는 않는다. 예제 1은 스레드 안전했지만 데이터를 잃었다.
    sleep은 락을 놓지 않는다
    Thread.sleep은 모니터 소유권을 유지하고 JLS상 동기화 의미가 없다. synchronized 안에서 조건을 기다리며 자면 조건을 바꿀 스레드가 BLOCKED로 막혀 영원히 멈추고, 덤프의 deadlock 탐지에도 걸리지 않는다.
    대기 집합과 wait
    모든 객체는 모니터와 함께 대기 집합을 가진다. wait는 락 소유를 요구하고, 대기 집합에 들어간 뒤 그 객체의 락을 재진입 횟수만큼 모두 놓으며, 제거된 뒤 락을 다시 얻어야 돌아온다.
    notify와 notifyAll
    notify는 대기 집합에서 임의의 한 스레드를, notifyAll은 모두를 제거한다. 깨어난 스레드는 알린 스레드가 락을 놓을 때까지 BLOCKED이며, 대기자가 없을 때의 알림은 저장되지 않는다.
    락 없이 wait를 부를 수 없는 이유
    조건 확인과 대기 진입 사이, 상태 변경과 알림 사이에 틈이 있으면 알림이 사라진다. 같은 락이 둘을 직렬화해 신호 유실을 막는다.
    while 재확인
    notifyAll, 끼어들기, 가짜 깨어남, 엉뚱한 종류의 깨어남 때문에 wait에서 돌아왔을 때 조건이 거짓일 수 있다. 깨어남은 다시 확인하라는 신호일 뿐이다.
    notify의 한계
    대기 집합이 하나라 깨울 대상을 고를 수 없다. 같은 종류의 스레드가 알림을 받으면 헛걸음이 생기고, 반복 실행에서는 모든 스레드가 대기 집합에 갇힐 수 있다. notifyAll은 정확하지만 모두를 깨운다.
    wait의 바닥과 깨움의 사슬(OpenJDK 21)
    wait는 남은 허가를 지운 뒤 자기 ParkEvent에서 잠들고(시간 제한 없는 wait()는 인자 없는 park()), park가 알림 없이 돌아와도 스스로 대기 집합에서 빠져 wait를 끝낸다. notify와 notifyAll은 노드를 옮기기만 하며, 실제 unpark는 exit가 후계자 하나씩에게 한다. JFR의 jdk.JavaMonitorWait는 wait마다 알린 스레드를 기록한다.
    HotSpot ObjectMonitor
    OpenJDK 21에서 wait는 모니터를 팽창시키고 _WaitSet 꼬리에 들어가며, notify는 머리를 꺼내 진입 목록으로 옮긴다. 실제 깨움은 알린 스레드의 exit에서 일어난다. 순서는 구현 사항일 뿐 명세의 보장이 아니다.

    운영 중인 서버가 CPU를 거의 쓰지 않는데 요청이 처리되지 않는다면, 가장 먼저 스레드 덤프를 찍어 상태별로 묶어 본다. BLOCKED 스레드가 잔뜩 있고 모두 같은 주소를 waiting to lock하고 있다면, 그 주소를 locked로 쥔 스레드를 찾는다. 그 스레드가 sleeping이거나 네트워크 응답, 다른 큐를 기다리고 있다면 예제 2와 같은 구조다. 락을 쥔 채 오래 걸리는 일을 하고 있는 것이다. 반대로 많은 스레드가 같은 객체에서 waiting on 상태로 WAITING이고 아무도 그 객체의 락을 쥐고 있지 않다면, 알림이 사라졌거나 알림을 보낼 쪽이 이미 죽은 경우를 의심한다. 두 경우 모두 JVM의 deadlock 탐지가 아무것도 알려 주지 않는다는 점이 중요하다. "deadlock 없음"은 "멈춤 없음"이 아니다.

    새로 코드를 쓸 때 wait와 notify를 직접 쓰는 일은 드물어야 한다. 이 회차에서 본 것처럼 정확하게 쓰려면 같은 락, while 재확인, 알릴 대상의 종류, 인터럽트 처리를 모두 맞춰야 하고, 하나만 어긋나도 테스트에서는 잘 통과하다가 부하가 걸린 날 멈춘다. Object.wait의 API 문서도 이 주제의 더 깊은 논의를 위해 『Java Concurrency in Practice』와 『Effective Java』를 가리킨다. 실무에서는 java.util.concurrent의 BlockingQueue 같은 검증된 도구를 먼저 쓴다. 다만 그 도구를 쓸 때도 원리는 그대로 남는다. 큐의 용량을 무한으로 두면 예제 1~3의 "가득 참" 경계가 사라지는 대신 메모리가 경계가 되고, 용량을 작게 잡으면 생산자가 막히는 시간이 늘어난다.

    기존 코드에서 wait/notify를 만났다면 세 가지를 점검한다. 모든 wait가 while 안에 있는가. 대기 집합에 서로 다른 조건을 기다리는 스레드가 섞일 수 있는데 notify를 쓰고 있지는 않은가. 섞일 수 있다면 notifyAll로 바꾸는 것이 가장 작은 수정이고, 깨움 비용이 실제로 문제가 될 때 다음 회차의 Condition으로 대기실을 나눈다. 그리고 Java 21에서 가상 스레드를 도입할 계획이라면, synchronized와 wait가 캐리어 스레드를 붙잡는다는 점을 함께 고려해야 한다.

     스레드 A가 객체 m의 synchronized 블록 안에서 m.notify()를 호출했고, 대기 집합에 있던 스레드 B가 선택되었다. A는 아직 블록 안에서 다른 작업을 하고 있다. 이 순간 B의 상태로 옳은 것은? RUNNABLE: notify를 받으면 즉시 wait 다음 줄을 실행한다. BLOCKED: 대기 집합에서는 빠졌지만 A가 락을 놓을 때까지 락을 다시 얻을 수 없다. WAITING: A가 블록을 빠져나갈 때 비로소 대기 집합에서 제거된다. TIMED_WAITING: 락을 다시 얻을 때까지 정해진 시간만큼 기다린다. JLS 17.2.2에 따라 notify는 B를 대기 집합에서 제거하지만, B의 lock 동작은 A가 모니터를 완전히 놓은 뒤에야 성공한다. 그동안 B는 BLOCKED이며 덤프에는 "waiting to re-lock in wait()"로 보인다. 실험에서도 notify 직후 W1이 BLOCKED였다. 즉시 실행되지 않으므로 0번이 틀렸고, 대기 집합 제거는 notify 시점에 일어나므로 2번이 틀렸다. 시간 제한과는 관계가 없으므로 3번도 틀렸다. synchronized 메서드 안에서 버퍼가 빌 때까지 Thread.sleep(1000)을 반복하는 소비자가 있다. 생산자가 아무리 많아도 데이터가 들어오지 않는 이유로 가장 정확한 것은? sleep 중인 스레드에게는 다른 스레드의 쓰기가 보이지 않기 때문이다. JVM이 sleep 중인 스레드를 deadlock으로 판단해 생산자를 멈추기 때문이다. sleep은 모니터 소유권을 놓지 않으므로, 생산자들이 같은 객체의 synchronized 메서드에 들어가지 못하고 BLOCKED가 되기 때문이다. sleep이 끝날 때마다 소비자가 락을 새로 얻는데, 생산자보다 우선권이 있기 때문이다. Thread.sleep의 API 문서는 잠든 스레드가 어떤 모니터의 소유권도 잃지 않는다고 적는다. 소비자는 메서드를 빠져나가지 않았으므로 락을 계속 쥐고 있고, 생산자들은 진입하지 못한다. 가시성은 생산자가 들어가지도 못하므로 쟁점이 아니다. JVM은 이 상황을 deadlock으로 탐지하지 않으며 스레드를 멈추지도 않는다. 소비자는 락을 놓은 적이 없으니 "새로 얻는" 일도 없다. while (queue.isEmpty()) wait();를 if (queue.isEmpty()) wait();로 바꾸면 안 되는 이유가 아닌 것은? wait에서 돌아올 때 락을 다시 얻지 않으므로, 다른 스레드가 큐를 고치는 중일 수 있다. notifyAll로 함께 깨어난 다른 소비자가 먼저 데이터를 가져갔을 수 있다. notify로 깨어난 뒤 락을 다시 얻기 전에 새로 도착한 소비자가 끼어들어 데이터를 가져갔을 수 있다. JLS가 알림 없이 스레드를 깨우는 가짜 깨어남을 허용한다. wait는 돌아오기 전에 반드시 락을 다시 얻는다(JLS 17.2.1의 n번 lock 단계). 그러므로 0번의 전제는 틀렸고, wait 직후의 코드는 임계 영역 안에 있다. 나머지 셋은 모두 깨어난 시점에 조건이 거짓일 수 있는 실제 경로이며, 그래서 조건을 반복문으로 다시 검사해야 한다. 생산자 둘, 소비자 둘이 용량 1 버퍼를 반복해서 쓰는데, 상태를 바꾼 뒤 notify()를 부르고 조건은 while로 다시 검사한다. 가끔 네 스레드가 모두 WAITING으로 멈춘다. 근본 원인은? while 대신 if를 써야 깨어난 스레드가 바로 진행할 수 있다. notify를 synchronized 밖에서 불러야 신호가 사라지지 않는다. wait가 락을 놓지 않아 다른 스레드가 상태를 바꾸지 못한다. 대기 집합이 하나라서, 반대 종류에게 가야 할 알림을 같은 종류의 스레드가 받아 소비하고 다시 잠들 수 있다. 생산자와 소비자가 한 대기 집합에 섞여 있고 notify는 그중 임의의 하나만 깨운다. 소비자가 보낸 알림이 다른 소비자에게 가면 그 소비자는 조건이 거짓임을 보고 알림 없이 다시 잠들고, 생산자들은 영영 깨어나지 못한다. if로 바꾸면 다른 오류가 생기고, synchronized 밖의 notify는 IllegalMonitorStateException이며, wait는 락을 놓는다. 해결은 notifyAll, 또는 대기실을 나누는 Condition이다. OpenJDK 21 HotSpot에서 대기 집합에 스레드 다섯 개가 있을 때 한 스레드가 notifyAll()을 부르고 곧바로 synchronized 블록을 빠져나갔다. 운영체제 수준에서 일어나는 일로 옳은 것은? notifyAll 안에서 다섯 스레드의 조건 변수에 차례로 signal을 보내므로, 다섯 스레드가 동시에 깨어나 락을 놓고 경쟁한다. notifyAll은 대기 집합을 비우지 않고 표시만 해 두며, 각 스레드는 자기 park 시간 제한이 끝나야 깨어난다. notifyAll은 다섯 노드를 진입 목록으로 옮기기만 하고, 모니터를 빠져나가는 exit가 후계자 하나를 unpark한다. 나머지는 이후의 exit에서 하나씩 깨워진다. notifyAll은 다섯 스레드의 상태를 바로 RUNNABLE로 바꾸고, 락 재획득 없이 wait에서 돌아가게 한다. HotSpot 21의 notifyAll은 _WaitSet이 빌 때까지 INotify를 반복할 뿐이고, INotify는 노드를 진입 목록으로 옮기고 _notified와 알린 스레드 ID만 기록한다. 실제 unpark는 exit가 고른 후계자 하나에게만 ExitEpilog에서 한다. 그래서 깨움이 사슬처럼 하나씩 이어진다. notifyAll 안에서 signal을 보내지 않으므로 0번이 틀렸고, 시간 제한과는 관계가 없으므로 1번이 틀렸다. JLS 17.2.1에 따라 wait는 락을 다시 얻어야 돌아오며, 깨어난 직후 상태는 BLOCKED이므로 3번도 틀렸다.
    생산자 소비자 문제(producer-consumer problem)
    데이터를 만드는 스레드와 소비하는 스레드가 공유 버퍼를 통해 협력할 때, 버퍼의 경계(가득 참, 비어 있음)에서의 대기와 알림을 올바르게 다루는 문제다.
    유한 버퍼(bounded buffer)
    담을 수 있는 원소 수에 상한이 있는 버퍼다. 상한이 있어 생산자도 기다려야 하는 상황이 생긴다.
    조건 동기화(condition synchronization)
    공유 상태가 특정 조건을 만족할 때까지 스레드를 멈춰 두는 동기화다. 상호 배제와 구분되며, 자바에서는 wait/notify나 Condition으로 구현한다.
    대기 집합(wait set)
    JLS 17.2가 정의한, 모든 객체에 딸린 스레드 집합이다. wait로 들어가고 notify, notifyAll, 인터럽트, 시간 만료, 가짜 깨어남으로 빠진다.
    신호 유실(lost wake-up)
    알림이 그것을 기다리는 스레드에게 닿지 못하고 사라져 스레드가 계속 잠들어 있는 현상이다. 조건 확인과 대기 사이의 틈, 또는 엉뚱한 스레드가 알림을 소비하는 경우에 생긴다.
    가짜 깨어남(spurious wakeup)
    알림, 인터럽트, 시간 만료 없이 스레드가 대기 집합에서 제거되는 것이다. JLS가 허용하므로 wait는 반복문 안에서 써야 한다.
    폴링(polling)
    조건이 바뀌었는지 정해진 간격으로 반복해서 확인하는 방식이다. 간격에 따라 CPU 낭비와 응답 지연을 맞바꾼다.
    모니터 팽창(monitor inflation)
    HotSpot에서 ObjectMonitor 없이 객체 헤더와 스레드 쪽 잠금 기록으로 처리하던 가벼운 락을 ObjectMonitor 구조로 바꾸는 것이다. wait는 대기 집합이 필요하므로 모니터를 팽창시킨다.
    ParkEvent
    HotSpot이 자바 스레드마다 하나씩 두는 재우기·깨우기 장치로, synchronized 진입 대기와 wait가 쓴다. POSIX 계열에서는 허가 하나짜리 정수와 pthread 뮤텍스·조건 변수로 구현된다. LockSupport.park가 쓰는 Parker와는 별개다.
