    스레드의 이름표: Thread 객체가 담은 기본 정보

    앞 회차에서 Thread를 만들고 start()로 새 실행 흐름을 시작했다. 스레드가 둘 이상 동시에 움직이기 시작하면 가장 먼저 부딪히는 문제는 "지금 이 코드를 누가 실행하고 있는가"다. 같은 메서드를 여러 스레드가 동시에 실행할 수 있으므로, 로그 한 줄이나 예외 하나가 어느 실행 흐름에서 나왔는지 알려면 스레드를 식별할 수단이 있어야 한다. 이 회차는 그 식별 정보에서 출발해, 스레드가 태어나서 끝날 때까지 거치는 상태, 그리고 다른 스레드가 끝나기를 기다리는 방법인 join까지 내려간다.

    식별의 출발점은 Thread.currentThread()다. 이 정적 메서드는 지금 이 코드를 실행하고 있는 스레드의 Thread 객체를 돌려준다. 같은 줄의 코드라도 어느 스레드가 실행하느냐에 따라 다른 객체가 나온다. OpenJDK 21 소스에서 이 메서드는 public static native Thread currentThread()로 선언되어 있고 @IntrinsicCandidate가 붙어 있다. 이 애너테이션은 HotSpot이 해당 메서드를 일반 네이티브 호출 대신 특별히 준비한 코드로 바꿔 넣을 수 있다(보장은 아니다)는 표시다. 로그를 찍을 때마다 부르는 메서드이므로 비용이 작아야 한다는 점을 생각하면 자연스러운 선택이다.

    먼저 main 메서드를 실행하는 스레드와 새로 만든 스레드 두 개의 정보를 찍어 보자.

    public class ThreadInfoDemo {
    public static void main(String[] args) {
        Thread main = Thread.currentThread();
        System.out.println("toString  = " + main);
        System.out.println("threadId  = " + main.threadId());
        System.out.println("name      = " + main.getName());
        System.out.println("priority  = " + main.getPriority());
        System.out.println("group     = " + main.getThreadGroup().getName());
        System.out.println("daemon    = " + main.isDaemon());
        System.out.println("state     = " + main.getState());

        Thread worker = new Thread(() -> {}, "worker-A");
        Thread anon = new Thread(() -> {});
        System.out.println(worker + " state=" + worker.getState() + " alive=" + worker.isAlive());
        System.out.println(anon + " state=" + anon.getState());
    }
}

    toString()의 형식은 JDK 21 소스에 그대로 있다. "Thread[#" 뒤에 스레드 ID, 이름, 우선순위, 스레드 그룹 이름을 쉼표로 이어 붙인다. 그러므로 Thread[#1,main,5,main]은 "ID 1, 이름 main, 우선순위 5, 그룹 main"으로 읽는다. 첫 번째 main은 스레드 이름이고 마지막 main은 그 스레드가 속한 그룹의 이름이다. 이름이 같아서 헷갈리기 쉬운 자리다. 이제 각 항목을 하나씩 들여다보자.

    스레드 ID: 생성할 때 정해지고 바뀌지 않는다

    threadId()는 Java 19에서 추가된 메서드다. API 문서는 스레드 ID를 "스레드가 생성될 때 만들어지는 양의 long 값이며, 고유하고 수명 동안 바뀌지 않는다"고 정의한다. 예전부터 있던 getId()는 Java 19부터 deprecated인데, 이유가 문서에 적혀 있다. getId()는 final이 아니어서 하위 클래스가 재정의해 엉뚱한 값을 돌려줄 수 있기 때문이다. threadId()는 final이고 내부 필드 tid를 그대로 돌려준다.

    main 스레드의 ID가 1인 것도 우연이 아니다. Thread 생성자 코드에는 "VM 초기화 단계에서 붙는(attached) 최초의 스레드이면 tid = 1"이라는 분기가 있고, 주석이 이 스레드를 primordial thread라고 부른다. 그 밖의 스레드는 모두 ThreadIdentifiers.next()라는 전역 카운터에서 번호를 받는다. 그렇다면 왜 새 스레드가 2가 아니라 20을 받았을까. JVM이 main 메서드를 부르기 전에 이미 여러 스레드를 만들었기 때문이다. Thread.getAllStackTraces()로 시작 직후의 스레드를 찍어 보면 다음과 같다.

    Thread[#1,main,5,main] daemon=false state=RUNNABLE
Thread[#9,Reference Handler,10,system] daemon=true state=RUNNABLE
Thread[#10,Finalizer,8,system] daemon=true state=WAITING
Thread[#11,Signal Dispatcher,9,system] daemon=true state=RUNNABLE
Thread[#18,Notification Thread,9,system] daemon=true state=RUNNABLE
Thread[#19,Common-Cleaner,8,InnocuousThreadGroup] daemon=true state=TIMED_WAITING

    번호 사이가 비어 있는 것은 이 목록에 나오지 않는 내부 스레드가 있기 때문이다. 같은 JDK로 실행한 다른 프로그램의 스레드 덤프(뒤에서 읽는 법을 다룬다)를 보면 Service Thread가 #12, Monitor Deflation Thread가 #13, C2 CompilerThread0이 #14, C1 CompilerThread0이 #17을 쓰고 있었다. JIT 컴파일러 스레드처럼 자바 코드에는 감춰진 스레드도 같은 카운터에서 번호를 받는다. 어떤 내부 스레드가 몇 개 만들어지는지는 JDK 버전, GC 종류, 실행 옵션에 따라 달라지므로, 사용자 스레드의 ID가 몇 번부터 시작하는지에 기대는 코드는 쓰지 않는다.

    이름: 없으면 Thread-N, 번호는 ID와 따로 센다

    이름은 생성자에서 줄 수 있고 나중에 setName()으로 바꿀 수도 있다. 이름을 주지 않으면 생성자가 genThreadName()을 불러 "Thread-" + ThreadNumbering.next()를 이름으로 쓴다. 소스 주석에 따르면 이 번호는 0부터 시작하고, "역사적인 이유로" 스레드 ID와 별개로 센다. 위 출력에서 이름 없이 만든 스레드가 ID는 21인데 이름은 Thread-0인 이유가 이것이다. 또 생성자 코드가 (name != null) ? name : genThreadName()이므로 이름을 준 worker-A는 번호를 소비하지 않는다. 그래서 그다음에 만든 익명 스레드가 Thread-1이 아니라 Thread-0이 되었다.

    ID와 이름의 성격은 다르다. ID는 JVM이 고유성을 보장하지만, 이름은 고유할 필요가 없다. 두 스레드에 같은 이름을 줘도 아무 검사가 없다. 그래서 이름은 사람이 읽기 위한 라벨이고, 프로그램이 스레드를 구분하는 열쇠로는 ID나 Thread 객체 참조를 쓴다. 그럼에도 실무에서 이름은 매우 중요하다. 로그와 스레드 덤프에 찍히는 것이 이름이기 때문이다. Thread-37보다 order-sync-3이 장애 상황에서 훨씬 많은 것을 알려 준다.

    우선순위: 1부터 10, 부모에게서 물려받는다

    우선순위(priority)는 MIN_PRIORITY(1)부터 MAX_PRIORITY(10) 사이의 정수이고 기본값은 NORM_PRIORITY(5)다. 새 플랫폼 스레드의 우선순위는 생성자에서 Math.min(parent.getPriority(), g.getMaxPriority())로 정해진다. 즉 만든 스레드(부모)의 우선순위를 물려받되 소속 스레드 그룹의 최대값을 넘지 못한다. setPriority()는 범위를 벗어난 값이면 IllegalArgumentException을 던지고, 그룹 최대값보다 큰 값은 최대값으로 잘라 저장한다. 가상 스레드의 우선순위는 항상 5이고 setPriority()의 인자는 무시된다.

    우선순위가 실제 실행 순서에 얼마나 영향을 주는지는 JDK 21의 Thread API 문서가 정하지 않는다. 문서가 정하는 것은 값의 범위, 기본값, 상속, 그룹 최대값과의 관계까지다. 실제 효과는 JVM이 이 값을 OS 스레드의 우선순위로 어떻게 옮기는지, OS 스케줄러가 그것을 어떻게 쓰는지에 달려 있다. 이 글을 쓰며 macOS에서 뜬 스레드 덤프에서는 자바 우선순위 10인 Reference Handler도, 5인 main도 OS 쪽 우선순위가 똑같이 os_prio=31로 찍혔다. 이 환경에서는 자바 우선순위 차이가 OS 수준의 차이로 이어지지 않았다는 뜻이다. 그러므로 프로그램의 정확성을 우선순위에 기대어서는 안 된다.

    스레드 그룹과 데몬 여부

    스레드 그룹(thread group)을 생성자에서 지정하지 않으면 부모 스레드의 그룹에 들어간다(보안 관리자가 없는 일반적인 경우). main 스레드가 만든 스레드가 모두 main 그룹에 속하는 이유다. JVM 내부 스레드는 system 그룹에 있고, main 그룹의 부모가 system 그룹이다. 오늘날 스레드 그룹을 직접 다룰 일은 거의 없지만, 뒤에서 보듯 처리되지 않은 예외를 받아 출력하는 기본 처리기가 바로 스레드 그룹이라는 점은 알아 둘 만하다. 데몬(daemon) 여부도 부모에게서 물려받는다(parent.isDaemon()). 시작된 비데몬 스레드가 모두 끝나야 JVM 종료 절차가 시작된다는 점은 앞 회차에서 다뤘다.

    Thread 객체 뒤에 있는 것: JVM의 스레드와 OS 스레드

    위 출력에서 worker-A는 NEW 상태였고 isAlive()는 false였다. 이 시점의 Thread는 힙에 있는 평범한 자바 객체일 뿐이고, 실행 흐름은 아직 존재하지 않는다. Thread API 문서는 플랫폼 스레드(platform thread)가 "보통 OS가 스케줄링하는 커널 스레드와 1:1로 대응한다"고 설명한다. 그렇다면 자바 객체와 커널 스레드는 어떻게 연결될까. 그 연결 고리가 Thread 클래스의 eetop 필드다.

    OpenJDK 21의 소스 주석은 eetop을 이렇게 설명한다. JVM 전용 필드이고, 역사적인 이름을 가진 이 필드는 그 스레드에 해당하는 VM 내부의 JavaThread 객체 주소를 담는다. 스레드가 시작되면 0이 아닌 값이 되고, 스레드가 끝나면 다시 0이 된다. 그리고 isAlive()의 구현은 정확히 eetop != 0이다. 정말 그런지 리플렉션으로 이 필드를 직접 읽어 보자(실험용 코드이며, java.lang 패키지를 열어 주는 --add-opens 옵션이 있어야 실행된다).

    import java.lang.reflect.Field;

public class EetopDemo {
    public static void main(String[] args) throws Exception {
        Field f = Thread.class.getDeclaredField("eetop");
        f.setAccessible(true);
        Thread t = new Thread(() -> {
            try { Thread.sleep(3000); } catch (InterruptedException e) { }
        }, "probe");
        System.out.println("before start: eetop=0x" + Long.toHexString(f.getLong(t)) + " alive=" + t.isAlive());
        t.start();
        System.out.println("running     : eetop=0x" + Long.toHexString(f.getLong(t)) + " alive=" + t.isAlive());
        System.out.println("pid=" + ProcessHandle.current().pid());
        t.join();
        System.out.println("after join  : eetop=0x" + Long.toHexString(f.getLong(t)) + " alive=" + t.isAlive());
    }
}

    세 줄의 출력이 생명 주기를 그대로 보여 준다. start() 전에는 0, 실행 중에는 어떤 주소, 끝난 뒤에는 다시 0이다. 그리고 실행 중에 jcmd로 뜬 스레드 덤프의 tid=0x0000007b60c2ea00이 eetop 값과 정확히 같다. 스레드 덤프가 tid라고 찍는 값은 자바의 threadId()가 아니라 VM 내부 JavaThread 객체의 주소이고, 자바 쪽 ID는 #20이다. 대괄호 안의 27139와 nid=27139는 OS가 그 스레드에 붙인 번호다.

    자바 힙의 Thread 객체가 eetop 필드로 VM 내부 JavaThread를 가리키고, JavaThread가 커널 스레드와 1:1로 대응하는 세 층 구조를 보여 준다. 가로로 세 개의 큰 영역을 나란히 그린 기술 구조도. 왼쪽 영역 제목 "자바 힙", 가운데 "HotSpot 네이티브 메모리", 오른쪽 "운영체제 커널". 왼쪽 영역 안에 "Thread 객체 (#20, probe)"라는 상자, 가운데 영역 안에 "JavaThread"라는 상자, 오른쪽 영역 안에 "커널 스레드 (nid 27139)"라는 상자를 둔다. 왼쪽 상자에서 가운데 상자로 굵은 화살표를 긋고 라벨 "eetop"을 붙인다. 가운데 상자에서 오른쪽 상자로 양방향 화살표를 긋고 라벨 "1:1"을 붙인다. 가운데 상자에서 왼쪽 상자로 가는 얇은 점선 화살표에 라벨 "상태 기록"을 붙인다. 그림 아래쪽에 회색 띠를 두고 "start() 전·종료 후: eetop = 0"이라고 쓴다. 평면 벡터 스타일, 흰 배경, 파란색과 회색 계열. Thread 객체는 eetop으로 VM의 JavaThread를 가리키고, JavaThread는 커널 스레드 하나와 대응한다. eetop이 0이 아닌 동안만 isAlive()가 true다.

    이 그림에서 기억할 것은 두 가지다. 첫째, Thread 객체는 OS 스레드보다 오래 산다. start() 전에도, 스레드가 끝난 뒤에도 객체는 남아 있고 이름이나 ID를 읽을 수 있다. 실행 흐름이 존재하는 구간은 start()부터 종료까지뿐이다. 둘째, 스레드 덤프에는 #번호가 없는 줄도 있다. 이 글을 쓰며 뜬 덤프 전체를 보면 "VM Thread", "GC Thread#0", "G1 Service" 같은 줄은 자바 스레드 ID 없이 찍혔다. 이들은 HotSpot이 자기 일을 위해 돌리는 내부 스레드여서 자바 코드에서 Thread 객체로 보이지 않는다. 덤프를 뜨는 순간 새로 생긴 "Attach Listener"(#27)도 볼 수 있는데, 이는 jcmd가 실행 중인 JVM에 붙을 때 그 요청을 받기 위해 만들어진 스레드다.

    여섯 가지 상태와 전이

    스레드가 태어나서 끝날 때까지 JVM은 그 스레드를 여섯 가지 상태 중 하나로 분류한다. 이 분류가 Thread.State 열거형이고, getState()가 돌려주는 값이다. API 문서는 "스레드는 한 시점에 한 상태에만 있을 수 있다"고 말하고, 바로 이어서 중요한 단서를 붙인다. 이 상태들은 가상 머신의 상태이며 어떤 OS 스레드 상태도 반영하지 않는다는 것이다. 이 단서가 왜 중요한지는 조금 뒤 RUNNABLE을 실험하며 확인한다. 우선 각 상태의 정의와 들어가는 방법을 표로 정리한다. 들어가는 방법의 목록은 Thread.State API 문서에 적힌 것 그대로다.

    상태뜻이 상태가 되는 경우빠져나가는 경우
    NEW아직 시작되지 않음new Thread(...) 직후start() 호출
    RUNNABLEJVM 안에서 실행 중. 단, CPU 같은 OS 자원을 기다리고 있을 수 있다start() 이후, 대기에서 풀려난 뒤아래 대기 상태로 가거나 run()이 끝남
    BLOCKED모니터 락을 기다림synchronized 블록·메서드에 들어가려는데 다른 스레드가 락을 쥐고 있음, 또는 Object.wait()에서 깨어나 락을 다시 얻으려 함락 획득
    WAITING다른 스레드의 특정 행동을 기한 없이 기다림시간 제한 없는 Object.wait(), Thread.join(), LockSupport.park()통지(notify), 대상 스레드 종료, unpark, 인터럽트
    TIMED_WAITING기한을 정해 기다림Thread.sleep, 시간 제한 있는 Object.wait, Thread.join, LockSupport.parkNanos, parkUntil시간 만료, 또는 WAITING과 같은 사건
    TERMINATED실행을 마침run()이 정상 종료하거나 예외로 끝남없음(되돌아갈 수 없다)

    전이를 화살표로 다시 적으면 다음과 같다. 모든 대기 상태는 RUNNABLE에서만 들어가고, 풀려나면 RUNNABLE로 돌아온다는 점이 핵심이다. 대기 상태끼리 바로 오가는 것은 wait()에서 깨어난 스레드가 락을 다시 얻기 위해 BLOCKED를 거치는 경우뿐이다.

    NEW ──start()──▶ RUNNABLE ──run() 끝(정상 또는 예외)──▶ TERMINATED

RUNNABLE ──synchronized 진입 실패──────────────────▶ BLOCKED
BLOCKED  ──모니터 락 획득──────────────────────────▶ RUNNABLE

RUNNABLE ──wait() / join() / park()───────────────▶ WAITING
WAITING  ──notify / 대상 종료 / unpark / 인터럽트──▶ RUNNABLE
           (wait()에서 깨어나면 BLOCKED를 거쳐 락을 다시 얻는다)

RUNNABLE ──sleep(ms) / wait(ms) / join(ms) / parkNanos──▶ TIMED_WAITING
TIMED_WAITING ──시간 만료 또는 WAITING과 같은 사건──────▶ RUNNABLE
    여섯 상태를 원으로 그리고, RUNNABLE을 중심에 두어 세 가지 대기 상태가 RUNNABLE과 오가는 구조와 NEW, TERMINATED의 일방향 전이를 보여 준다. 상태 전이도. 가운데에 큰 원 "RUNNABLE". 왼쪽 끝에 원 "NEW", 오른쪽 끝에 원 "TERMINATED". NEW에서 RUNNABLE로 화살표, 라벨 "start()". RUNNABLE에서 TERMINATED로 화살표, 라벨 "run() 종료". RUNNABLE 아래쪽에 원 세 개를 나란히 둔다: "BLOCKED", "WAITING", "TIMED_WAITING". RUNNABLE과 각 원 사이에 왕복 화살표 한 쌍씩. BLOCKED 쪽 내려가는 화살표 라벨 "synchronized 대기", WAITING 쪽 "wait / join / park", TIMED_WAITING 쪽 "sleep / join(ms)". 올라오는 화살표 세 개에는 라벨을 붙이지 않는다. WAITING에서 BLOCKED로 가는 짧은 점선 화살표 하나, 라벨 "락 재획득". TERMINATED 원은 회색으로 칠한다. 평면 벡터 스타일, 흰 배경. 세 가지 대기 상태는 모두 RUNNABLE과 오간다. NEW와 TERMINATED는 한 번씩만 지나가는 상태다.

    BLOCKED라는 이름에 속기 쉽다. 이 상태는 모니터 락(synchronized)을 기다릴 때만 쓰인다. 7회에서 다룰 ReentrantLock은 내부적으로 LockSupport.park()로 스레드를 재우므로, 그 락을 기다리는 스레드는 BLOCKED가 아니라 WAITING으로 보인다. 소켓 읽기처럼 I/O를 기다리는 스레드도 BLOCKED가 아니다. 그 경우가 무엇으로 보이는지는 곧 실험으로 확인한다.

    TERMINATED에서는 다시 출발할 수 없다. start()의 구현은 synchronized (this) 안에서 상태 값이 0(NEW)이 아니면 IllegalThreadStateException을 던진다. 같은 일을 다시 하고 싶으면 새 Thread 객체를 만들어야 한다. 이 제약이 나중에 스레드 풀이 필요한 이유 중 하나가 된다. 스레드 풀은 끝난 스레드를 재시작하는 것이 아니라, 스레드를 끝내지 않고 다음 작업을 계속 가져다 실행시키는 방식으로 재사용한다(12회).

    상태를 코드로 관찰하기

    정의를 실제로 확인해 보자. 아래 프로그램은 0.5초 동안 잠드는 스레드 sleeper와, sleeper가 끝나기를 기다리는 스레드 joiner를 만들고, main이 중간중간 두 스레드의 상태를 찍는다.

    public class LifecycleDemo {
    public static void main(String[] args) throws InterruptedException {
        Thread sleeper = new Thread(() -> {
            System.out.println("[sleeper] 시작, 내 상태 = " + Thread.currentThread().getState());
            try {
                Thread.sleep(500);
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            }
            System.out.println("[sleeper] 깨어남, 내 상태 = " + Thread.currentThread().getState());
        }, "sleeper");

        System.out.println("[main] start 전: " + sleeper.getState());
        sleeper.start();
        Thread.sleep(100);
        System.out.println("[main] sleep 중: " + sleeper.getState());

        Thread joiner = new Thread(() -> {
            try {
                sleeper.join();
            } catch (InterruptedException e) {
                throw new RuntimeException(e);
            }
        }, "joiner");
        joiner.start();
        Thread.sleep(100);
        System.out.println("[main] joiner 상태: " + joiner.getState());

        sleeper.join();
        joiner.join();
        System.out.println("[main] 종료 후: " + sleeper.getState() + ", alive=" + sleeper.isAlive());
        try {
            sleeper.start();
        } catch (IllegalThreadStateException e) {
            System.out.println("[main] 다시 start: " + e);
        }
    }
}
    [main] start 전: NEW
[sleeper] 시작, 내 상태 = RUNNABLE
[main] sleep 중: TIMED_WAITING
[main] joiner 상태: WAITING
[sleeper] 깨어남, 내 상태 = RUNNABLE
[main] 종료 후: TERMINATED, alive=false
[main] 다시 start: java.lang.IllegalThreadStateException

    한 줄씩 따라가 보자. 첫 줄에서 sleeper는 객체만 있고 시작되지 않았으므로 NEW다. start() 뒤 sleeper는 자기 상태를 스스로 찍는데, 자기 코드를 실행하고 있는 스레드는 정의상 RUNNABLE이다. 자기 상태를 물어서 RUNNABLE 말고 다른 값을 얻을 수는 없다. 이어서 sleeper는 Thread.sleep(500)에 들어가고, 100ms 뒤 main이 본 상태는 TIMED_WAITING이다. 기한이 있는 대기이기 때문이다.

    joiner는 시간 제한 없는 sleeper.join()을 호출했으므로 WAITING이다. sleeper가 0.5초를 다 자고 나면 "깨어남"을 찍고 run()을 빠져나간다. 그 순간 joiner와 main의 join()이 풀린다. 마지막 두 줄은 끝난 스레드가 TERMINATED이고 isAlive()가 false이며, 다시 시작할 수 없다는 것을 보여 준다.

    이 예제의 출력 순서는 main의 sleep(100) 간격에 기대고 있다. 보통의 컴퓨터에서는 100ms면 다른 스레드가 sleep이나 join에 들어가기에 충분하지만, 언어가 그 순서를 보장하는 것은 아니다. 관찰용 코드와 정확성이 필요한 코드를 구분해야 하는 이유이며, 이 회차 후반의 주제이기도 하다.

    상태 값은 어디서 오는가

    getState()는 자바 코드로 상태를 계산하지 않는다. JDK 21에서 이 메서드는 jdk.internal.misc.VM.toThreadState(holder.threadStatus)를 돌려줄 뿐이다. threadStatus는 volatile int 필드이고, VM 클래스의 주석은 "HotSpot 구현에서는 상태가 바뀔 때 VM이 이 필드를 설정하며, 값은 JVM TI 명세의 GetThreadState 함수가 정한 비트 형식을 따른다"고 설명한다. toThreadState는 그 비트를 차례로 검사해 열거형 값으로 바꾼다.

    // OpenJDK 21 jdk.internal.misc.VM.toThreadState의 판정 순서를 요약한 것
if      ((s & RUNNABLE_BIT)          != 0) return RUNNABLE;       // 0x0004
else if ((s & BLOCKED_ON_MONITOR)    != 0) return BLOCKED;        // 0x0400
else if ((s & WAITING_INDEFINITELY)  != 0) return WAITING;        // 0x0010
else if ((s & WAITING_WITH_TIMEOUT)  != 0) return TIMED_WAITING;  // 0x0020
else if ((s & TERMINATED_BIT)        != 0) return TERMINATED;     // 0x0002
else if ((s & ALIVE_BIT)             == 0) return NEW;            // 0x0001이 없음
else                                       return RUNNABLE;

    여기서 두 가지를 읽어 낼 수 있다. 상태 값의 출처는 JVM 자신이며, 자바 코드는 그것을 읽어 해석할 뿐이다. 그리고 NEW는 "살아 있음(ALIVE) 비트가 없고 종료 비트도 없는 상태"이므로 상태 필드 값이 0이다. start()가 threadStatus != 0으로 "이미 시작했는가"를 검사할 수 있는 이유다.

    getState()의 API 문서에는 꼭 기억해야 할 문장이 있다. 이 메서드는 시스템 상태를 모니터링하기 위한 것이지 동기화를 제어하기 위한 것이 아니다. 상태는 읽는 순간의 스냅숏이고, 값을 받아 든 다음 줄에서는 이미 바뀌었을 수 있다. 예를 들어 if (t.getState() == State.WAITING) { ... } 안으로 들어왔을 때 t는 벌써 깨어났을 수 있다. 또 뒤에서 보겠지만 자바 메모리 모델(JLS 17.4.4)이 "다른 스레드의 종료를 감지하는 수단"으로 꼽는 것은 isAlive()와 join()이다. 다른 스레드가 남긴 결과를 읽어도 되는지 판단하는 데 getState()를 쓰지 않는다.

    RUNNABLE은 CPU에서 돌고 있다는 뜻이 아니다

    이제 API 문서가 "VM의 상태이지 OS의 상태가 아니다"라고 강조한 이유를 확인한다. 아래 프로그램은 여러 상태의 스레드를 한꺼번에 만들어 놓고 상태를 찍은 뒤, 3초 동안 살아 있으면서 밖에서 스레드 덤프를 뜰 시간을 준다. 눈여겨볼 것은 두 스레드다. acceptor는 아무도 연결해 오지 않는 서버 소켓의 accept()에서 기다리고, spinner는 아무 일도 하지 않는 계산 루프를 끝없이 돈다.

    import java.net.ServerSocket;

public class StatesSnapshot {
    static final Object LOCK = new Object();

    public static void main(String[] args) throws Exception {
        Thread sleeper = new Thread(() -> {
            try { Thread.sleep(60_000); } catch (InterruptedException e) { }
        }, "sleeper");

        Thread joiner = new Thread(() -> {
            try { sleeper.join(); } catch (InterruptedException e) { }
        }, "joiner");

        Thread timedJoiner = new Thread(() -> {
            try { sleeper.join(30_000); } catch (InterruptedException e) { }
        }, "timed-joiner");

        Thread holder = new Thread(() -> {
            synchronized (LOCK) {                       // 락을 쥔 채로 잔다
                try { Thread.sleep(60_000); } catch (InterruptedException e) { }
            }
        }, "holder");

        Thread blocked = new Thread(() -> {
            synchronized (LOCK) { }                     // holder가 쥔 락을 기다린다
        }, "blocked");

        Thread acceptor = new Thread(() -> {
            try (ServerSocket ss = new ServerSocket(0)) {
                ss.accept();                            // 연결이 올 때까지 기다린다
            } catch (Exception e) { }
        }, "acceptor");

        Thread spinner = new Thread(() -> {
            long x = 0;
            while (!Thread.currentThread().isInterrupted()) { x++; }   // CPU를 계속 쓴다
        }, "spinner");

        Thread[] all = {sleeper, joiner, timedJoiner, holder, blocked, acceptor, spinner};
        sleeper.start(); joiner.start(); timedJoiner.start(); holder.start();
        Thread.sleep(100);
        blocked.start(); acceptor.start(); spinner.start();
        Thread.sleep(300);
        for (Thread t : all) {
            System.out.printf("%-13s %s%n", t.getName(), t.getState());
        }
        System.out.println("pid=" + ProcessHandle.current().pid());
        System.out.flush();
        Thread.sleep(3_000);
        System.exit(0);                                 // 남은 비데몬 스레드와 상관없이 끝낸다
    }
}
    sleeper       TIMED_WAITING
joiner        WAITING
timed-joiner  TIMED_WAITING
holder        TIMED_WAITING
blocked       BLOCKED
acceptor      RUNNABLE
spinner       RUNNABLE
pid=4281

JVM이 보기에는 이 스레드가 네이티브 메서드를 실행하는 중이므로 RUNNABLE로 보고한다. RUNNABLE의 API 문서 설명이 정확히 이 상황을 포괄한다. "JVM 안에서 실행 중이지만 CPU 같은 OS 자원을 기다리고 있을 수 있다."

    한 층 아래: HotSpot은 스레드 상태를 세 군데에 적는다

    앞의 덤프를 다시 보면 스레드마다 상태처럼 보이는 표시가 두 번 나온다. 머리줄 끝의 runnable, waiting on condition, in Object.wait(), waiting for monitor entry가 하나이고, 둘째 줄의 java.lang.Thread.State: ...가 또 하나다. 둘은 같은 값을 두 번 찍은 것이 아니다. OpenJDK 21 HotSpot 소스(jdk21u 저장소)를 따라가 보면 스레드 하나의 "상태"는 서로 다른 세 필드에 따로 기록되고, 덤프는 그중 두 개를 찍는다. 이 절의 내용은 명세가 아니라 HotSpot의 구현이다.

    필드있는 곳값의 종류누가 읽는가
    threadStatus자바 힙의 Thread 객체(holder)JavaThreadStatus: NEW, RUNNABLE, SLEEPING, IN_OBJECT_WAIT, IN_OBJECT_WAIT_TIMED, PARKED, PARKED_TIMED, BLOCKED_ON_MONITOR_ENTER, TERMINATEDgetState(), 덤프의 둘째 줄
    OSThread::_stateHotSpot의 OSThread 객체(네이티브 메모리)ThreadState: ALLOCATED, INITIALIZED, RUNNABLE, MONITOR_WAIT, CONDVAR_WAIT, OBJECT_WAIT, SLEEPING, ZOMBIE 등덤프 머리줄 끝(OSThread::print_on)

    첫째 필드 threadStatus는 앞에서 getState()가 읽는다고 한 그 필드다. classfile/javaThreadStatus.hpp에 정의된 JavaThreadStatus의 각 값은 JVM TI 상태 비트를 더해서 만든다. 예를 들어 SLEEPING은 ALIVE, WAITING, WAITING_WITH_TIMEOUT, SLEEPING 네 비트의 합이다. 열거형 Thread.State는 여섯 개인데 이 값은 아홉 개다. 앞에서 본 toThreadState가 비트만 보고 SLEEPING, IN_OBJECT_WAIT_TIMED, PARKED_TIMED를 모두 TIMED_WAITING으로 접는다. 덤프가 TIMED_WAITING (sleeping)처럼 괄호 안에 더 자세한 이유를 붙일 수 있는 것은 열거형이 아니라 이 원래 값을 읽기 때문이다. javaClasses.cpp의 java_lang_Thread::thread_status_name이 SLEEPING을 "TIMED_WAITING (sleeping)"으로, IN_OBJECT_WAIT를 "WAITING (on object monitor)"로, PARKED를 "WAITING (parking)"으로 바꿔 돌려준다.

    그렇다면 threadStatus는 누가 언제 쓰는가. jdk21u에서 java_lang_Thread::set_thread_status를 호출하는 곳은 몇 군데뿐이다. 스레드를 시작할 때 RUNNABLE을 쓰는 Thread::start(runtime/thread.cpp), 최초의 main 스레드와 JNI로 붙는(attach) 스레드에 RUNNABLE을 쓰는 코드, 스레드가 끝날 때 TERMINATED를 쓰는 ensure_join(뒤의 「스레드가 끝나는 순간」 절), 그리고 services/threadService.hpp에 모인 상태 변경 클래스들이다. 이 클래스들은 C++ 지역 객체로 쓰인다. 생성자가 지금 상태를 저장한 뒤 새 상태를 쓰고, 블록을 벗어날 때 소멸자가 저장해 둔 상태로 되돌린다. 대기하는 코드를 이 객체로 감싸 두면 대기에 들어갈 때 상태가 바뀌고, 통지로 깨든 시간이 다 되든 예외로 빠져나오든 원래 상태(보통 RUNNABLE)로 돌아온다. 둘째 필드인 OSThread 상태도 runtime/osThread.hpp의 OSThreadWaitState, OSThreadContendState라는 같은 모양의 클래스가 바꾼다.

    표의 첫 줄에는 작은 반전이 있다. JVM_Sleep은 OSThread 상태를 SLEEPING으로 바꾸지만, 그 안에서 실제로 잠드는 sleep_nanos가 잠드는 구간을 OSThreadWaitState(false)로 감싸 CONDVAR_WAIT로 덮어쓴다. 그래서 OSThread::print_on에 "sleeping"이라는 문구가 준비되어 있는데도, 잠든 스레드의 덤프 머리줄은 "waiting on condition"으로 찍힌다. 앞의 holder와 EetopDemo의 probe가 정확히 그렇게 찍혔다. 셋째 줄에도 단서가 하나 있다. JavaThreadBlockedOnMonitorEnterState의 생성자는 모니터에 경합이 있을 때(contentions() > 0)만 상태를 바꾼다. 소스 주석에 따르면 경합 없이 바로 락을 얻는 경우에는 상태도 바꾸지 않는다. 실제로 ObjectMonitor::enter는 락이 비어 있거나 짧은 스핀(TrySpin)으로 락을 얻으면 이 객체를 만들기 전에 돌아온다. synchronized 블록에 들어가는 스레드가 모두 잠깐씩 BLOCKED를 거치는 것이 아니라는 뜻이다. 또 Thread.State 표의 "wait()에서 깨어나 락을 다시 얻으려 함"도 같은 클래스가 처리하는데, 이때는 notify를 부른 스레드가 깨울 대기자를 고르면서 ObjectWaiter::wait_reenter_begin으로 그 대기자의 상태를 BLOCKED_ON_MONITOR_ENTER로 바꿔 준다. 다른 스레드의 상태를 대신 써 주는 드문 경우다.

    표의 마지막 줄이 acceptor가 RUNNABLE이었던 이유의 구현상 답이다. 네이티브 메서드를 부르는 경로에는 threadStatus나 OSThread 상태를 바꾸는 장치가 없다. 그래서 accept 안에서 몇 시간을 기다려도 두 필드는 start() 때 기록된 RUNNABLE 그대로다. 이때 바뀌는 것은 셋째 필드 _thread_state뿐이다. utilities/globalDefinitions.hpp의 주석은 JavaThreadState를 "스레드가 코드의 어느 부분을 실행하고 있는지 추적하며, 세이프포인트(safepoint) 코드에 필요한 정보"라고 설명한다. 세이프포인트는 VM이 GC 같은 작업을 위해 자바 스레드들을 안전한 지점에 세우는 절차다. 같은 주석은 _thread_in_native를 "네이티브 코드 안. 모든 객체 참조가 jobject 핸들 안에 있으므로 세이프포인트 영역이다"라고 적는다. 즉 HotSpot도 내부적으로는 accept에 머문 스레드(_thread_in_native)와 계산 루프를 도는 스레드(_thread_in_Java)를 구분한다. 다만 그 구분은 VM 자신의 작업을 위한 것이고, getState()로는 드러나지 않는다.

    스택 내용에서는 세 가지를 읽을 수 있다. 첫째, sleeper, joiner, blocked는 Thread.State로는 TIMED_WAITING, WAITING, BLOCKED로 서로 다르고 HotSpot 안의 경로도 JVM_Sleep, JVM_MonitorWait, ObjectMonitor::enter로 다르지만, 맨 아래는 모두 HotSpot의 PlatformEvent를 거쳐 _pthread_cond_wait와 커널 호출 __psynch_cvwait에서 끝난다. POSIX 계열 OS용 HotSpot 코드(os/posix/os_posix.cpp)에서 시간 제한 없는 PlatformEvent::park는 pthread_cond_wait로, 시간 제한이 있는 park_nanos는 pthread_cond_timedwait로 잠들기 때문이다. sleeper와 blocked는 park_nanos를 거치는데도 스택에 pthread_cond_timedwait 프레임은 보이지 않고 바로 _pthread_cond_wait가 찍혔다. macOS의 libsystem_pthread에서는 두 함수가 이 내부 함수로 이어진다는 것을 스택이 보여 준다. 601개의 표본이 모두 같은 지점에 있었다는 것은 표본을 뜬 모든 순간에 이 스레드들이 같은 대기 지점에 머물러 있었다는 뜻이다. 커널에게 이 셋은 똑같이 "조건 변수에서 기다리는 스레드"이고, 어떤 이유로 기다리는지는 잠들기 전에 JVM이 자기 장부에 적어 둔 값으로만 구분된다.

    둘째, acceptor는 libnio의 네이티브 함수 Java_sun_nio_ch_Net_accept에서 accept 시스템 호출의 진입점 __accept로 들어가 커널 안에서 기다리고 있다. 커널의 관점에서는 앞의 세 스레드와 같은 부류, 즉 실행되지 않고 무언가를 기다리는 스레드다. 그런데도 getState()가 RUNNABLE을 돌려준 것은, 앞 절에서 본 대로 이 경로에 threadStatus를 바꾸는 장치가 없기 때문이다. 셋째, spinner의 스택에는 libjvm도 커널 함수도 없고 ???만 있다. 자바 코드를 실행하는 기계어(인터프리터와 JIT 컴파일러가 만든 코드)는 HotSpot이 확보한 코드 캐시에 있고 어떤 실행 파일 이미지에도 속하지 않으므로, sample이 이름을 붙이지 못한다. 대기 중인 스레드와 달리 표본이 서로 가까운 다섯 개의 주소에 흩어져 있다. 표본을 뜰 때마다 명령어 위치가 달랐다는 것, 즉 작은 루프를 실제로 실행하고 있었다는 것이다. 덤프의 cpu=1564.11ms와 같은 이야기다.

    같은 실험을 Linux에서 하면 도구와 커널 함수 이름이 다르다. 이 절의 스택은 macOS(이 실험 환경)에서 얻은 것이고, __psynch_cvwait는 macOS 커널의 조건 변수 대기 호출이다. 다만 PlatformEvent가 pthread_cond_wait와 pthread_cond_timedwait로 잠든다는 것은 POSIX 계열 OS가 함께 쓰는 os_posix.cpp의 코드다.

    run()은 체크 예외를 던질 수 없다

Runnable.run()에는 throws 절이 없으므로, 구현하는 run()이 선언할 수 있는 체크 예외는 하나도 없다.

    왜 이런 규칙이 있는가: 호출하는 쪽에서 보기

    이 규칙은 호출하는 쪽의 자리에 서면 당연해진다. 다음 메서드는 Runnable 목록을 받아 차례로 실행한다.

    static void runAll(java.util.List tasks) {
    for (Runnable r : tasks) {
        r.run();     // 컴파일러는 Runnable.run()의 선언만 보고 이 줄을 검사한다
    }
}

    이 코드를 컴파일하는 시점에 컴파일러는 목록에 어떤 구현 클래스가 들어올지 모른다. 알 수 있는 것은 변수의 선언 타입인 Runnable과 그 run()의 선언뿐이다. 선언에 체크 예외가 없으므로 컴파일러는 이 호출을 try 없이 허락한다. 만약 어떤 구현이 run() throws IOException이라고 선언할 수 있다면, 이 줄에서 IOException이 튀어나올 수 있는데도 컴파일러는 그것을 잡으라고 요구하지 못한다. 체크 예외라는 제도의 약속, 즉 "처리하지 않은 체크 예외가 있으면 컴파일되지 않는다"가 깨진다. 컴파일 시점에는 구현을 볼 수 없으니, 규칙은 구현 쪽에 걸 수밖에 없다. 하위 타입은 상위 타입이 약속한 것보다 더 나쁜 결과를 내놓으면 안 된다는 치환 원칙이 예외에 적용된 것이다.

    스레드의 경우에는 사정이 하나 더 있다. 앞의 스레드 덤프에서 작업 스레드 스택의 맨 아래는 항상 java.lang.Thread.run이었고, 그 위에 Thread.runWith, 그 위에 우리가 쓴 람다가 있었다. JDK 21의 Thread.run()은 생성자로 받은 작업(holder.task)이 있으면 runWith를 부르고, runWith는 op.run()을 부를 뿐이다. 어디에도 try-catch가 없다. 그리고 Thread.run 아래에는 자바 호출자가 없다. 새 스레드의 스택은 VM이 Thread.run을 부르는 것으로 시작하기 때문이다. 설령 체크 예외를 선언할 수 있다고 해도, 그것을 잡아 줄 자바 코드가 그 스레드의 스택에는 없다. main에 throws를 붙일 수 있는 것은 main이 정적 메서드라 무엇도 재정의하지 않기 때문이다.

    그래서 어떻게 처리하는가

    현실적인 선택지는 세 가지다. 첫째, run() 안에서 잡아 처리한다. 이 단계에서 가장 흔한 처리는 런타임 예외로 감싸 다시 던져 그 스레드를 끝내는 것이다. 둘째, 같은 try-catch가 여러 곳에 반복된다면 작은 도우미 메서드로 모은다. 셋째, 결과와 예외를 호출한 쪽에 돌려줘야 하는 작업이라면 run() 대신 call() throws Exception으로 선언된 Callable을 쓴다. Callable에서 던진 예외는 결과를 기다리던 스레드에게 Future.get()의 ExecutionException으로 전달되는데, 이는 12~13회의 주제다.

    public final class Pause {
    private Pause() { }

    public static void millis(long ms) {
        try {
            Thread.sleep(ms);
        } catch (InterruptedException e) {
            throw new RuntimeException(e);   // 인터럽트를 제대로 다루는 법은 다음 회차에서
        }
    }
}

    한 가지만 짚어 둔다. Thread.sleep의 API 문서에 따르면 InterruptedException이 던져질 때 현재 스레드의 인터럽트 상태(interrupted status)는 지워진다. 위 도우미는 예외를 감싸 던지므로 스레드는 그 자리에서 끝나고, 이 단계에서는 그것으로 충분하다. 하지만 예외를 잡고 아무 일 없다는 듯 계속 진행하는 코드라면 이야기가 달라진다. 인터럽트가 무엇을 요청하는 신호이고 이 예외를 받았을 때 무엇을 해야 하는지는 4회의 주제다.

    체크 예외는 컴파일러의 규칙이다

    run() 밖으로 빠져나간 예외는 어디로 가는가

    위 출력의 첫 줄 Exception in thread "sneaky"는 누가 찍었을까. Thread 클래스 문서는 스레드가 끝나는 경우를 이렇게 정의한다. run()이 정상적으로 끝나거나, run()이 예외로 갑자기 끝나고 해당 처리되지 않은 예외 처리기(uncaught exception handler)가 실행을 마치면 스레드는 종료된다. Thread.UncaughtExceptionHandler의 API 문서에 따르면, 스레드가 처리되지 않은 예외로 끝나려 할 때 JVM이 그 스레드에 처리기를 물어 호출한다. OpenJDK 21 소스에서는 "스레드가 예외로 끝날 때 호출된다"는 주석이 달린 dispatchUncaughtException(e)이 이 일을 하며, getUncaughtExceptionHandler().uncaughtException(this, e)를 호출한다.

    중요한 것은 예외가 다른 스레드로 전파되지 않는다는 점이다. 각 스레드는 자기 스택을 갖고, 예외는 그 스택을 따라서만 위로 올라간다. 작업 스레드의 스택 바닥은 Thread.run이고, 그 아래에 main의 프레임이 있는 것이 아니다. 그래서 작업 스레드에서 예외가 터져도 main은 아무 일 없다는 듯 계속 실행된다.

    join이 필요한 상황

    이제 이 회차의 두 번째 큰 주제로 넘어간다. 스레드를 쓰는 가장 흔한 이유 중 하나는 큰 일을 나눠 동시에 처리하는 것이다. 예를 들어 0부터 200만 미만까지의 소수(prime number)가 몇 개인지 세는 일을 두 구간으로 나눠, 0~100만 미만은 한 스레드가, 100만~200만 미만은 다른 스레드가 맡게 한다. 각 스레드는 결과를 자기 객체의 필드에 적고, main이 두 결과를 더한다. 문제는 "main이 언제 결과를 읽어도 되는가"다.

    public class PrimeCount {
    static class PrimeCounter implements Runnable {
        private final int from, to;   // [from, to) 구간
        int count;                    // 결과를 담는 평범한 필드

        PrimeCounter(int from, int to) { this.from = from; this.to = to; }

        @Override
        public void run() {
            int c = 0;
            for (int n = from; n < to; n++) {
                if (isPrime(n)) c++;
            }
            count = c;
        }

        static boolean isPrime(int n) {
            if (n < 2) return false;
            for (int d = 2; (long) d * d <= n; d++) {
                if (n % d == 0) return false;
            }
            return true;
        }
    }

    public static void main(String[] args) throws InterruptedException {
        PrimeCounter low = new PrimeCounter(0, 1_000_000);
        PrimeCounter high = new PrimeCounter(1_000_000, 2_000_000);
        Thread t1 = new Thread(low, "low");
        Thread t2 = new Thread(high, "high");

        long start = System.nanoTime();
        t1.start();
        t2.start();
        System.out.println("start 직후: " + low.count + " + " + high.count);

        t1.join();
        t2.join();
        long ms = (System.nanoTime() - start) / 1_000_000;
        System.out.println("join 후: " + low.count + " + " + high.count + " = " + (low.count + high.count));
        System.out.println("t1=" + t1.getState() + ", t2=" + t2.getState() + ", " + ms + "ms");
    }
}

t1=TERMINATED, t2=TERMINATED, 112ms

    100만 미만의 소수는 78,498개, 200만 미만은 148,933개이므로 결과는 맞다. 먼저 start 직후 줄을 보자. start()는 새 스레드에게 실행을 예약하고 곧바로 돌아온다. 그러므로 바로 다음 줄에서 읽은 count는 대개 아직 계산이 끝나지 않아 기본값 0이다. "대개"라고 쓴 이유가 있다. 이 읽기와 작업 스레드의 쓰기 사이에는 아무 순서 관계가 없어서, 언어 차원에서는 무엇이 읽힐지 보장되지 않는다. 이 실행에서 0이 나왔다는 것은 관찰일 뿐 약속이 아니다. 우리가 원하는 것은 "두 스레드가 다 끝난 뒤에 읽는다"는 약속이고, 그것을 주는 것이 join이다. 그 전에 흔히 먼저 떠올리는 방법부터 확인해 보자.

    sleep으로 기다리면 생기는 두 가지 문제

    가장 단순한 생각은 "계산이 끝날 만큼 잠깐 자고 나서 읽자"다. 기다릴 시간을 명령행 인자로 받아 여러 값으로 실험해 보았다.

    public class PrimeSleep {
    public static void main(String[] args) throws InterruptedException {
        long waitMs = Long.parseLong(args[0]);           // 기다릴 시간을 추측해서 넣는다
        PrimeCount.PrimeCounter low = new PrimeCount.PrimeCounter(0, 1_000_000);
        PrimeCount.PrimeCounter high = new PrimeCount.PrimeCounter(1_000_000, 2_000_000);
        Thread t1 = new Thread(low, "low");
        Thread t2 = new Thread(high, "high");
        t1.start();
        t2.start();
        Thread.sleep(waitMs);                             // "이 정도면 끝났겠지"
        System.out.println("sleep(" + waitMs + ") 후: " + low.count + " + " + high.count
                + " = " + (low.count + high.count));
    }
}
    기다린 시간이 글을 쓰며 실행한 결과
    50ms0 + 0 = 0
    80ms세 번 모두 78498 + 0 = 78498
    100ms여섯 번 중 한 번은 78498 + 0 = 78498, 다섯 번은 78498 + 70435 = 148933
    150ms, 300ms, 1000ms78498 + 70435 = 148933

    첫 번째 문제는 시간을 추측해야 한다는 것이다. 이 컴퓨터에서 두 계산이 끝나는 데는 대략 110ms 남짓이 걸렸다(join 버전의 측정값). 그보다 짧게 자면 결과가 틀리고, 경계 근처인 100ms에서는 같은 프로그램이 실행할 때마다 다른 답을 냈다. 넉넉하게 1000ms를 자면 답은 맞지만 900ms 가까이를 아무 이유 없이 버린다. 게다가 "넉넉한" 시간은 기계마다, 그 순간의 부하마다, JIT 컴파일이 얼마나 진행되었는지마다 다르다. 개발자의 노트북에서 넉넉했던 값이 운영 서버의 바쁜 시간대에는 모자랄 수 있다. 큰 구간(100만~200만)을 맡은 high가 늘 늦게 끝난다는 점도 보인다. 숫자가 클수록 소수 판정에 드는 나눗셈이 많아지기 때문이다.

    두 번째 문제는 더 근본적이다. 설령 충분히 오래 잤다고 해도, 자바 언어 명세는 잠에서 깬 스레드가 다른 스레드가 쓴 값을 본다고 약속하지 않는다. JLS 17.3은 "Thread.sleep도 Thread.yield도 어떤 동기화 의미(synchronization semantics)도 갖지 않는다"고 못 박는다. 이어서 컴파일러는 sleep 호출 전에 레지스터에 캐시된 쓰기를 공유 메모리로 내보낼 필요가 없고, sleep 호출 뒤에 레지스터에 캐시된 값을 다시 읽어 올 필요도 없다고 설명한다. 명세가 드는 예는 volatile이 아닌 boolean 필드 done에 대해 while (!this.done) Thread.sleep(1000);을 도는 코드다. 컴파일러는 done을 한 번만 읽고 그 값을 루프마다 재사용해도 되므로, 다른 스레드가 값을 바꿔도 이 루프는 끝나지 않을 수 있다.

    위 실험에서 시간이 충분할 때 늘 맞는 값이 나온 것은 이 JVM과 이 CPU에서 그렇게 동작했다는 관찰이다. 명세가 보장하는 성질은 아니다. 왜 값이 안 보일 수 있는지, CPU 캐시와 컴파일러 최적화가 각각 어떤 역할을 하는지는 5회 「메모리 가시성」에서 자세히 다룬다. 여기서 가져갈 결론은 하나다. 시간이 지났다는 사실은 다른 스레드의 작업이 끝났다는 증거도, 그 결과가 보인다는 보장도 아니다.

    join으로 기다리기와 happens-before

    t.join()은 "t가 끝날 때까지 현재 스레드를 기다리게 한다". 앞의 PrimeCount가 바로 이 방법을 썼다. main은 t1.join()에서 t1이 끝날 때까지 멈춰 있다가, t1이 끝나면 다음 줄로 가서 t2.join()을 부른다. 측정된 112ms는 계산이 실제로 걸린 시간과 거의 같다. 추측도 낭비도 없다.

    기다리는 동안 main은 어떤 상태일까. 앞의 StatesSnapshot에서 join()을 부른 joiner는 WAITING이었고, 덤프의 cpu=는 0.07ms였다. 기다리는 동안 CPU를 쓰지 않는다는 뜻이다. 이것을 while (t1.isAlive()) { } 같은 바쁜 대기(busy waiting)와 비교해 보자. 그 루프를 도는 스레드는 spinner처럼 RUNNABLE이고, 기다리는 내내 코어 하나를 차지해 정작 계산해야 할 작업 스레드와 CPU를 다툰다.

    join을 부르는 순서도 생각해 볼 만하다. t1.join(); t2.join();으로 차례로 기다리면 전체 대기 시간이 두 작업 시간의 합이 될 것 같지만 그렇지 않다. 두 스레드는 이미 동시에 실행 중이다. t1.join()이 돌아왔을 때 t2도 그동안 계산을 계속했으므로, t2.join()은 남은 시간만큼만 기다린다. t2가 먼저 끝났다면 t2.join()은 기다리지 않고 바로 돌아온다. 그러므로 전체 대기 시간은 둘 중 늦게 끝나는 쪽의 시간이고, 순서를 바꿔도 같다.

    join이 결과를 "보이게" 만든다

    join의 진짜 가치는 시간이 아니라 메모리 모델에 있다. JLS 17.4.5는 happens-before 관계를 만드는 규칙 가운데 스레드와 관련된 두 가지를 이렇게 정한다. 첫째, 어떤 스레드에 대한 start() 호출은 시작된 스레드의 모든 동작보다 먼저 일어난다(happens-before). 둘째, 한 스레드의 모든 동작은, 다른 스레드가 그 스레드에 대한 join()에서 성공적으로 돌아오는 것보다 먼저 일어난다. JLS 17.4.4는 같은 내용을 동기화 순서로 표현한다. 스레드 T1의 마지막 동작은 T1이 종료되었음을 감지하는 다른 스레드 T2의 동작과 동기화되며(synchronizes-with), T2는 T1.isAlive()나 T1.join()을 호출해 그것을 감지할 수 있다.

     main                                   t1 ("low")
 ────                                   ──────────
 low = new PrimeCounter(0, 1_000_000)
   from, to 필드 기록
 t1.start() ────── happens-before ─────▶ run() 시작: from, to를 읽는다 (보장됨)
 t2.start()                              ... 소수 판정 ...
                                         count = 78498
 t1.join() 대기 (WAITING)                run() 반환 → 종료
 t1.join() 반환 ◀── happens-before ──────  t1의 모든 동작
 low.count 읽기 → 78498 (보장됨)

    이 두 규칙이 PrimeCount의 정확성을 떠받친다. from과 to는 main이 생성자에서 기록했고 작업 스레드가 읽는다. start() 규칙 덕분에 작업 스레드는 그 값을 확실히 본다. count는 작업 스레드가 쓰고 main이 읽는다. join() 규칙 덕분에 main은 join()이 돌아온 뒤 그 값을 확실히 본다. count가 volatile도 아니고 synchronized로 보호되지도 않는 평범한 int 필드인데도 안전한 이유가 이것이다. 반대로 sleep 버전에는 이런 관계가 하나도 없다. 같은 값이 출력되었더라도 하나는 명세가 보장하는 프로그램이고, 다른 하나는 우연히 맞은 프로그램이다.

    위아래 두 개의 시간선으로, sleep은 작업 종료 시점과 무관하게 정해진 시간에 깨어나고 join은 작업 종료 시점에 정확히 깨어나며 happens-before 화살표가 생긴다는 것을 대비한다. 위아래로 두 개의 가로 타임라인 패널. 위 패널 제목 "sleep으로 기다리기", 아래 패널 제목 "join으로 기다리기". 각 패널에 두 줄의 가로 막대: 위 줄 "main", 아래 줄 "작업 스레드". 작업 스레드 막대는 두 패널 모두 같은 길이의 주황색 구간 "계산"으로 그리고 끝에 작은 깃발 "종료"를 단다. 위 패널의 main 막대에는 회색 구간 "sleep(추측한 시간)"을 그리는데, 계산이 끝나기 전에 끝나는 짧은 버전과 훨씬 늦게 끝나는 긴 버전 두 개를 점선으로 겹쳐 그리고 각각 "너무 짧음", "낭비"라는 라벨을 붙인다. 아래 패널의 main 막대에는 파란 구간 "WAITING"을 그려 작업 스레드의 종료 깃발과 정확히 같은 지점에서 끝나게 하고, 종료 깃발에서 main 막대로 내려오는 초록 화살표에 "happens-before"라는 라벨을 붙인다. 평면 벡터 스타일, 흰 배경. sleep은 작업이 언제 끝나는지 모른 채 정해진 시간에 깨어난다. join은 작업이 끝나는 순간 돌아오고, 그 순간까지의 쓰기가 보인다는 보장(happens-before)까지 함께 준다.

    join의 내부: Thread 객체 위의 wait 루프

    join은 어떻게 "상대가 끝나는 순간"을 알까. JDK 21의 join(long) API 문서에는 구현 노트가 붙어 있다. 플랫폼 스레드의 경우 구현은 this.isAlive를 조건으로 하는 this.wait 호출의 루프를 쓰고, 스레드가 종료될 때 this.notifyAll이 호출된다. 소스에서 플랫폼 스레드 경로를 추려 보면 구조가 그대로 드러난다(가상 스레드는 앞부분에서 별도의 경로로 빠진다).

    // OpenJDK 21 Thread.join(long millis)의 플랫폼 스레드 경로를 추린 것
public final void join(long millis) throws InterruptedException {
    if (millis < 0) throw new IllegalArgumentException("timeout value is negative");
    // ... 가상 스레드는 여기서 별도 구현으로 처리하고 return ...
    synchronized (this) {                       // 기다릴 대상 스레드 객체의 모니터
        if (millis > 0) {
            if (isAlive()) {
                long startTime = System.nanoTime();
                long delay = millis;
                do {
                    wait(delay);                // 남은 시간만큼만 잔다
                } while (isAlive() && (delay = millis - 경과한_밀리초) > 0);
            }
        } else {                                // millis == 0: 끝날 때까지
            while (isAlive()) {
                wait(0);
            }
        }
    }
}

    읽어 보면 join은 특별한 장치가 아니라 "기다릴 스레드의 Thread 객체를 모니터로 삼아 wait하고, 그 스레드가 죽으면 VM이 같은 객체에 notifyAll한다"는 약속 위에 지어진 평범한 코드다. main이 t1.join()을 부르면 main은 t1 객체의 모니터를 잡고, t1이 살아 있으면 t1.wait(0)으로 잠든다. 이때 상태가 WAITING이고, 덤프에 WAITING (on object monitor)와 in Object.wait()가 찍힌 이유다. t1이 끝나면 VM이 t1.notifyAll()을 불러 기다리던 스레드를 모두 깨운다. 깨어난 main은 모니터를 다시 얻고 루프 조건 isAlive()를 확인해, false이면 빠져나온다.

     main 스레드                     t1 객체의 모니터                  스레드 t1
 ──────────                     ───────────────                  ─────────
 t1.join()
  synchronized(t1) 진입 ───────▶ 소유자: main
  isAlive() → true
  t1.wait(0) ──────────────────▶ 모니터를 내려놓고                  run() 실행 중
  (WAITING)                       대기 집합에 main 등록                ...
                                                                   run() 반환
                                 ◀──────────── 종료 처리: isAlive()가 false가 되고
                                                VM이 t1.notifyAll() 호출
  깨어나 모니터 다시 획득 ◀───────
  isAlive() → false, 루프 탈출
  synchronized 블록 나옴
 join() 반환 → 다음 줄 실행

    두 스레드 모두 같은 주소 0x...615a80의 java.lang.Thread 객체, 즉 sleeper 스레드 객체 위에서 기다리고 있다. 그런데 둘 다 그 객체에 대해 - locked라고 찍혀 있다. 모니터 락은 한 번에 한 스레드만 가질 수 있으므로 두 스레드가 동시에 쥐고 있을 수는 없다. 이 줄은 "이 프레임이 synchronized로 그 모니터에 들어갔다"는 기록이고, 실제 락은 wait가 내려놓은 상태다. wait가 모니터를 내려놓기 때문에 여러 스레드가 같은 스레드를 동시에 join할 수 있고, 종료 처리 쪽도 그 객체에 notifyAll을 할 수 있다. 한편 시간 제한이 있는 timed-joiner는 같은 구조에서 wait(delay)를 쓰므로 TIMED_WAITING으로 보인다.

    루프가 필요한 이유와 거기서 나오는 주의 사항

    wait를 if가 아니라 while로 감싼 데는 이유가 있다. Object.wait의 API 문서는 스레드가 통지도, 인터럽트도, 시간 만료도 없이 깨어나는 가짜 깨어남(spurious wakeup)이 드물게 일어날 수 있으므로, 기다리던 조건을 다시 검사하며 루프 안에서 기다려야 한다고 말한다. 또 누군가 다른 이유로 같은 객체에 notifyAll을 할 수도 있다. 루프는 어떤 이유로 깨어나든 "정말 끝났는가"를 다시 확인한다. 이 설계가 성립하려면, 종료 처리에서 isAlive()가 false가 되는 것이 깨어난 스레드가 조건을 다시 볼 때 이미 보여야 한다. 그렇지 않으면 깨어난 스레드가 다시 잠들어 다시는 깨지 못한다. join이 끝난 스레드에 대해 항상 돌아온다는 사실이 그 순서가 지켜진다는 뜻이다.

    이 구현에서 실무 규칙 두 가지가 나온다. 첫째, API 문서가 권하듯 애플리케이션은 Thread 객체에 wait, notify, notifyAll을 쓰지 않는다. 스레드가 끝날 때 VM이 그 객체에 notifyAll을 부르므로, 같은 객체로 다른 신호를 주고받으면 엉뚱한 때에 깨어난다. 둘째, Thread 객체를 synchronized의 락으로도 쓰지 않는다. 위 소스에서 보듯 join과 start가 그 객체의 모니터를 잡으므로, 애플리케이션이 그 모니터를 오래 쥐고 있으면 join을 부른 스레드가 wait에 들어가기도 전에 BLOCKED로 묶인다. wait와 notify, 대기 집합(wait set)의 동작은 8~9회 「생산자 소비자 문제」에서 본격적으로 다룬다.

    main이 t1 객체의 모니터에서 wait하고, t1이 종료될 때 VM이 같은 객체에 notifyAll하여 main이 깨어나 isAlive()를 다시 확인하는 순서를 보여 준다. 세 개의 세로 생명선이 있는 시퀀스 다이어그램. 왼쪽 생명선 "main", 가운데 생명선 "t1 객체의 모니터", 오른쪽 생명선 "스레드 t1". 위에서 아래로: main에서 모니터로 화살표 "synchronized 진입", main 옆에 작은 상자 "isAlive() = true", main에서 모니터로 화살표 "wait(0)", 모니터 옆에 작은 메모 "대기 집합". main 생명선의 가운데 구간을 파란색으로 칠하고 "WAITING"이라고 표시. 오른쪽 t1 생명선에는 긴 주황색 구간 "run() 실행"이 있고 끝에 "종료" 표시. t1에서 모니터로 화살표 "notifyAll()". 모니터에서 main으로 화살표 "깨움". main 옆에 작은 상자 "isAlive() = false", 마지막으로 main 쪽에 "join() 반환". 평면 벡터 스타일, 흰 배경. join은 대상 스레드 객체의 모니터에서 wait하고, 대상이 종료되며 VM이 notifyAll을 부르면 깨어나 isAlive()를 다시 확인한다.

    한 층 아래: 스레드가 끝나는 순간 HotSpot이 하는 일

    앞 절에서 join은 "대상이 죽으면 VM이 그 Thread 객체에 notifyAll을 부른다"는 약속 위에 서 있다고 했다. 그 약속을 지키는 코드가 HotSpot의 JavaThread::exit와 그 안의 ensure_join이다(OpenJDK 21, runtime/javaThread.cpp). run()이 정상으로든 예외로든 돌아오면 진입 함수 thread_entry가 끝나고, JavaThread::run의 마지막 단계인 thread_main_inner가 돌아온 뒤 post_run이 exit(false)를 부른다. 이 모든 일은 끝나 가는 스레드 자신이 실행한다.

    핵심인 ensure_join은 열 줄 남짓이다. 주석을 한국어로 옮겨 발췌한다.

    static void ensure_join(JavaThread* thread) {
  // 자기 자신에 대한 작업이므로 Threads_lock은 필요 없다.
  Handle threadObj(thread, thread->threadObj());
  ObjectLocker lock(threadObj, thread);          // java.lang.Thread 객체의 모니터를 잡는다
  // 스레드가 끝나므로 threadStatus를 TERMINATED로 설정한다.
  java_lang_Thread::set_thread_status(threadObj(), JavaThreadStatus::TERMINATED);
  // 네이티브 스레드 참조를 지운다. 이로써 isAlive가 false를 돌려주고,
  // 아래 notify_all 뒤에 join이 끝날 수 있다. 자바 메모리 모델의
  // 요구를 지키기 위해 release가 필요하다.
  java_lang_Thread::release_set_thread(threadObj(), nullptr);   // eetop = 0
  lock.notify_all(thread);
  thread->clear_pending_exception();
}

    이 몇 줄이 이 회차의 여러 사실을 한꺼번에 설명한다. set_thread_status가 쓴 값은 getState()가 돌려주는 TERMINATED가 된다. release_set_thread(..., nullptr)는 eetop을 0으로 만들며, EetopDemo에서 join 뒤에 본 eetop=0x0 alive=false가 여기서 나온다. notify_all은 join 안에서 wait하던 스레드들을 깨운다. 순서도 중요하다. 상태와 eetop을 먼저 바꾸고 나서 통지하므로, 깨어난 스레드가 루프 조건 isAlive()를 다시 볼 때는 이미 false다. 앞 절에서 "이 설계가 성립하려면 종료 처리에서 isAlive()가 false가 되는 것이 깨어난 스레드에게 이미 보여야 한다"고 한 조건이 구현에서는 이렇게 지켜진다.

    왜 모니터를 잡고 통지하는가: 잃어버린 깨어남

    ensure_join이 ObjectLocker로 잡는 모니터는 join이 synchronized (this)로 잡는 바로 그 모니터다. 이것이 없으면 어떤 일이 생길 수 있는지 생각해 보자. 기다리는 쪽은 isAlive()가 true인 것을 확인한 뒤 wait()를 부른다. 만약 종료하는 쪽이 모니터 없이 이 두 동작 사이에 끼어들어 eetop을 지우고 notifyAll을 부른다면, 그 통지는 아직 대기 집합에 아무도 없을 때 지나가 버린다. 곧이어 wait()에 들어간 스레드를 깨워 줄 사람은 더 이상 없다. 이것을 잃어버린 깨어남(lost wakeup)이라고 한다.

    실제 구현에서는 이 끼어들기가 불가능하다. 기다리는 쪽은 모니터를 쥔 채 isAlive()를 확인하고 wait()를 부른다. JLS 17.2.1에 따르면 wait는 스레드를 그 객체의 대기 집합에 넣은 뒤에 모니터를 푼다. 종료하는 쪽은 같은 모니터를 얻어야 eetop을 지우고 통지할 수 있으므로, 가능한 순서는 둘뿐이다. 종료 처리가 먼저 끝나면 기다리는 쪽은 모니터를 얻은 뒤 isAlive()에서 false를 보고 아예 잠들지 않는다. 기다리는 쪽이 먼저 대기 집합에 들어가면 그 뒤에 온 notify_all이 그 스레드를 깨운다. wait와 notify를 모니터를 쥔 채로만 부를 수 있게 한 규칙이 무엇을 막는지는 8~9회에서 생산자-소비자 문제로 다시 다룬다.

    주석이 말하는 "메모리 모델의 요구"도 짚어 둔다. 자바 쪽 eetop은 private volatile long eetop으로 선언되어 있고, isAlive()는 이 필드가 0이 아닌지를 본다. VM은 이 필드를 0으로 만들 때 release_address_field_put, 즉 release 저장을 쓴다. JLS 17.4.4는 join()뿐 아니라 isAlive()로 종료를 감지한 경우에도 종료한 스레드의 마지막 동작과의 synchronizes-with를 보장하는데, isAlive()만 부르는 쪽은 모니터를 거치지 않는다. 그런 쪽에도 끝난 스레드의 쓰기가 보여야 하므로, 모니터와 별개로 이 필드 자체의 쓰기 순서가 지켜져야 하는 것이다.

    실험: join은 처리기가 끝날 때까지 기다린다

    위 순서에서 처리되지 않은 예외 처리기(2단계)는 ensure_join(5단계)보다 먼저 실행된다. 그렇다면 처리기가 오래 걸리면 join도 그만큼 늦게 돌아와야 한다. 처리기 안에서 500ms를 자게 해서 확인해 보자.

    public class ExitOrder {
    public static void main(String[] args) throws Exception {
        Thread t = new Thread(() -> {
            throw new IllegalStateException("작업 실패");
        }, "worker");
        t.setUncaughtExceptionHandler((th, e) -> {
            System.out.println("[handler] 실행 스레드=" + Thread.currentThread().getName());
            try { Thread.sleep(500); } catch (InterruptedException ie) { }
            System.out.println("[handler] 끝");
        });
        long t0 = System.nanoTime();
        t.start();
        Thread.sleep(100);
        System.out.println("[main] 100ms 시점: alive=" + t.isAlive() + ", state=" + t.getState());
        t.join();
        System.out.println("[main] join 반환: " + (System.nanoTime() - t0) / 1_000_000
                + "ms, alive=" + t.isAlive() + ", state=" + t.getState());
    }
}
    [handler] 실행 스레드=worker
[main] 100ms 시점: alive=true, state=TIMED_WAITING
[handler] 끝
[0.535s][debug][os,thread,timer] name='worker', exit-phase1=506, exit-phase2=0, exit-phase3=0, exit-phase4=0
[main] join 반환: 506ms, alive=false, state=TERMINATED

    100ms 시점에 worker의 run()은 이미 예외를 던지고 끝났지만, 스레드는 살아 있고(alive=true) 상태는 TIMED_WAITING이다. 처리기가 바로 그 스레드 위에서 실행되며 sleep 중이기 때문이다. main의 join()은 처리기가 끝난 뒤인 약 506ms에야 돌아왔다. VM 로그가 그 시간이 어디에 쓰였는지 보여 준다. -Xlog:os+thread+timer=debug는 JavaThread::exit의 네 구간을 밀리초로 찍는데, 소스에서 1구간(exit-phase1)은 exit의 시작부터 ensure_join 직전까지이고 2구간이 ensure_join이다. 1구간이 506ms, 2구간이 0ms다. 스레드가 끝나는 데 걸린 시간이 거의 전부 처리기와 Thread.exit() 쪽에 있었고, 기다리는 스레드를 깨우는 일 자체는 순식간이었다. -Xlog:os+thread로 실행하면 처리기 출력 뒤에 JavaThread exiting (tid: ...)과 Thread finished (tid: ..., pthread id: ...)가 찍힌다. 소스에서 앞의 줄은 ensure_join보다 뒤에 기록되므로, 그 시점에 join하던 스레드는 이미 깨어나 움직이고 있을 수 있다. 두 스레드의 출력이 섞이는 순서는 실행마다 다를 수 있다.

    실무에서 얻는 교훈은 두 가지다. 처리되지 않은 예외 처리기에서 네트워크로 알림을 보내는 것처럼 오래 걸리는 일을 하면, 그동안 그 스레드는 살아 있고 그 스레드를 join하는 쪽도 함께 기다린다. 그리고 처리기에서 다시 던진 예외는 위 2단계에서 본 한 줄 메시지만 남기고 버려진다. 처리기는 짧고 실패하지 않게 쓴다.

    정해진 시간만큼만 기다리기

    기다리는 대상이 영영 끝나지 않으면 어떻게 될까. 외부 서버의 응답을 기다리는 작업이 멈춰 버리면 join()을 부른 스레드도 함께 영원히 멈춘다. 그래서 join에는 기다릴 시간의 상한을 주는 판이 있다. JDK 21에는 네 가지 join이 있고, 경계 조건에서의 동작이 서로 조금씩 다르다.

    메서드기다리는 한도반환시작 전 스레드에 호출음수·0
    join()끝날 때까지void기다리지 않고 즉시 반환해당 없음
    join(long millis)millismsvoid즉시 반환0이면 끝날 때까지, 음수면 IllegalArgumentException
    join(long millis, int nanos)millisms + nanosnsvoid즉시 반환둘 다 0이면 끝날 때까지, nanos는 0~999999만 허용
    join(Duration) (Java 19+)주어진 기간boolean: 끝났으면 trueIllegalThreadStateException0 이하이면 기다리지 않고 종료 여부만 확인

    표에서 함정 두 개가 보인다. join(0)은 "기다리지 않음"이 아니라 "끝날 때까지 기다림"이다. 반대로 join(Duration.ZERO)는 기다리지 않고 확인만 한다. 같은 0이 정반대 뜻이다. 또 시작하지 않은 스레드에 대해 옛 메서드들은 조용히 돌아오지만, join(Duration)은 예외를 던진다. 옛 메서드에서는 start()를 빠뜨린 버그가 "기다렸는데 결과가 비어 있다"는 모습으로만 드러난다. 참고로 OpenJDK 21에서 플랫폼 스레드의 join(long, int)는 nanos가 0보다 크면 밀리초에 1을 더해 join(long)을 부른다. 나노초 단위로 정밀하게 기다려 주는 것은 아니다.

    import java.time.Duration;

public class JoinEdges {
    public static void main(String[] args) throws InterruptedException {
        Thread slow = new Thread(() -> {
            try { Thread.sleep(1000); } catch (InterruptedException e) { }
        }, "slow");

        long t0 = System.nanoTime();
        slow.join();   // 아직 start 전
        System.out.println("1) 시작 전 join(): " + (System.nanoTime() - t0) / 1_000_000 + "ms 만에 반환, state=" + slow.getState());
        try {
            slow.join(Duration.ofMillis(100));
        } catch (IllegalThreadStateException e) {
            System.out.println("2) 시작 전 join(Duration): " + e);
        }

        slow.start();
        t0 = System.nanoTime();
        slow.join(200);
        System.out.println("3) join(200) 반환: 약 " + (System.nanoTime() - t0) / 1_000_000 + "ms, alive=" + slow.isAlive());

        boolean done = slow.join(Duration.ofMillis(200));
        System.out.println("4) join(Duration 200ms) = " + done);

        done = slow.join(Duration.ofSeconds(5));
        System.out.println("5) join(Duration 5s) = " + done + ", state=" + slow.getState());

        t0 = System.nanoTime();
        Thread.currentThread().join(300);
        System.out.println("6) 자기 자신 join(300): 약 " + (System.nanoTime() - t0) / 1_000_000 + "ms 뒤 반환");
        try {
            slow.join(-1);
        } catch (IllegalArgumentException e) {
            System.out.println("7) join(-1): " + e);
        }
    }
}
    1) 시작 전 join(): 0ms 만에 반환, state=NEW
2) 시작 전 join(Duration): java.lang.IllegalThreadStateException: Thread not started
3) join(200) 반환: 약 210ms, alive=true
4) join(Duration 200ms) = false
5) join(Duration 5s) = true, state=TERMINATED
6) 자기 자신 join(300): 약 310ms 뒤 반환
7) join(-1): java.lang.IllegalArgumentException: timeout value is negative

    3번 줄이 가장 중요하다. join(200)은 약 200ms 뒤에 아무 말 없이 돌아왔고, 그때 slow는 여전히 살아 있었다. void를 반환하는 join(long)은 "끝나서 돌아왔는지, 시간이 다 돼서 돌아왔는지"를 알려 주지 않는다. 그래서 시간 제한 join 뒤에는 반드시 isAlive()로 확인해야 한다. 4번과 5번은 join(Duration)이 그 확인을 반환값으로 대신해 준다는 것을 보여 준다. 소스를 보면 이 메서드는 join(millis)로 기다린 뒤 isTerminated()를 반환한다.

    메모리 관점에서도 이 확인은 필수다. happens-before는 상대 스레드가 종료했음을 감지했을 때만 생긴다. 시간이 다 돼서 돌아온 join은 종료를 감지한 것이 아니므로, 그 뒤에 결과 필드를 읽으면 끝나지 않은 계산의 중간값을 읽을 수도 있고 명세상 무엇이 보일지 보장도 없다. 올바른 모양은 다음과 같다.

    worker.join(500);                       // 최대 0.5초만 기다린다
if (worker.isAlive()) {                 // 아직 안 끝났다: 결과를 읽지 않는다
    System.out.println("시간 초과, 기본값으로 응답한다");
    // 계속 기다릴지, 포기할지, 작업 중단을 요청할지(4회의 인터럽트) 정한다
} else {                                // 종료를 감지했다: JLS 17.4.4에 따라 결과가 보인다
    System.out.println("결과 = " + task.result);
}

    6번 줄은 경계 조건 하나를 보여 준다. 현재 스레드가 자기 자신을 join하면, 자신이 끝나기를 기다리는 동안에는 끝날 수 없으므로 시간 제한이 없는 Thread.currentThread().join()은 영원히 돌아오지 않는다. 시간 제한을 준 덕분에 300ms 뒤 돌아왔을 뿐이다. 이런 코드를 일부러 쓰지는 않겠지만, 스레드 참조를 잘못 넘겨 자기 자신을 기다리게 되는 버그는 실제로 생길 수 있다. 그때 덤프에는 자기 자신의 Thread 객체 위에서 WAITING인 스레드가 보인다.

    시간 제한 join을 부른 스레드는 그동안 TIMED_WAITING이다(덤프의 timed-joiner). 기다리던 스레드가 기한 전에 끝나면 notifyAll로 일찍 깨어나고, 아니면 기한이 지나 깨어난다. 둘 중 무엇이었는지를 구분하는 것은 앞서 말한 대로 isAlive()의 몫이다.

    흔한 오해와 함정

    이 회차의 내용을 오해의 형태로 다시 정리한다. 각 오해가 왜 그럴듯해 보이는지와 실제로는 어떤지를 함께 적는다.

    • "RUNNABLE이면 CPU를 쓰고 있다." 이름 때문에 그렇게 읽기 쉽다. 실제로는 네이티브 I/O에서 기다리는 스레드도 RUNNABLE이다(acceptor의 cpu=17.20ms). CPU 사용은 상태가 아니라 덤프의 cpu= 값이나 OS 도구로 판단한다.
    • "I/O를 기다리는 스레드는 BLOCKED다." 일상어의 "블로킹 I/O"와 이름이 같아서 생기는 오해다. BLOCKED는 모니터 락을 기다릴 때만 쓰인다.
    • "충분히 sleep한 뒤에 읽으면 안전하다." 실험에서는 대개 맞는 값이 나오므로 믿게 된다. JLS 17.3에 따르면 sleep은 아무 동기화 의미가 없고, 시간 추측은 환경마다 틀린다.
    • "join(1000)이 돌아오면 스레드는 끝났다." 시간 제한 join은 시간이 다 돼도 조용히 돌아온다. isAlive()로 확인하거나 join(Duration)의 반환값을 본다.
    • "join(0)은 기다리지 않는다." join(0)은 끝날 때까지 기다린다. 기다리지 않고 확인만 하려면 isAlive()나 join(Duration.ZERO)를 쓴다.
    • "작업 스레드의 예외는 main으로 전파된다." 예외는 그 스레드의 스택 안에서만 전파된다. 처리되지 않으면 처리기가 출력하고 그 스레드만 끝난다. 결과와 예외를 함께 돌려받으려면 Callable과 Future를 쓴다(12회).
    • "getState()를 확인한 뒤 행동하면 된다." 상태는 읽는 순간의 스냅숏이고, API 문서도 동기화 제어용이 아니라고 말한다.
    • "Thread 객체가 있으면 OS 스레드도 있다." OS 스레드는 start()부터 종료까지만 존재한다. 그 구간이 eetop != 0, 즉 isAlive()가 true인 구간이다.
    • "우선순위를 높이면 먼저 실행된다." API는 범위와 상속 규칙만 정한다. 실제 효과는 OS에 달려 있고, 이 글의 macOS 환경에서는 OS 수준 우선순위가 모두 같게 찍혔다.

    다음 회차들과의 연결

    이 회차에서 본 것들은 이 권의 거의 모든 회차에서 다시 쓰인다. 다음 회차 「스레드 제어와 생명 주기 2」는 이번에 계속 미뤄 둔 인터럽트와 yield를 다룬다. sleep과 join이 왜 InterruptedException을 던지는지, 대기 상태의 스레드를 어떻게 깨워 작업을 멈추게 하는지가 그 주제다. 5회 「메모리 가시성」은 sleep 버전이 명세상 틀린 이유를 CPU 캐시와 자바 메모리 모델로 설명하고, 이번에 만난 happens-before 규칙을 volatile과 함께 정리한다.

    BLOCKED 상태와 모니터 락은 6회 synchronized에서, LockSupport.park로 만들어지는 WAITING은 7회 ReentrantLock에서, join의 바탕이 된 wait/notifyAll과 대기 집합은 8~9회에서 다시 나온다. 12~13회의 Future.get()은 "다른 스레드의 작업이 끝나기를 기다렸다가 결과를 받는다"는 점에서 join을 일반화한 것이고, 시간 제한 판과 예외 전달 방식까지 갖추고 있다. 스레드 풀이 스레드를 재시작하지 않고 재사용하는 이유도 TERMINATED에서 되돌아갈 수 없다는 이번 회차의 사실에서 출발한다.

    이 권 밖에서도 마찬가지다. 서블릿 컨테이너는 요청마다 스레드 풀의 스레드 하나를 배정하므로, 운영 중인 스프링 애플리케이션이 응답하지 않을 때 가장 먼저 하는 일이 스레드 덤프를 떠서 요청 처리 스레드들이 어떤 상태로 어디에 멈춰 있는지 보는 것이다. 이번 회차에서 읽은 WAITING (on object monitor), BLOCKED와 waiting to lock, 소켓 읽기에서의 RUNNABLE이 그때 그대로 나타난다.

    이 장의 핵심

    Thread 객체는 OS 스레드의 이름표이고, 실행 흐름은 start()부터 종료까지만 존재한다. Thread.State는 JVM의 관점이어서 RUNNABLE이 CPU 사용을 뜻하지 않는다. 체크 예외는 컴파일러의 규칙이라 run()이 선언할 수 없고, 빠져나간 예외는 그 스레드 안에서 처리기로 끝난다. 다른 스레드의 결과를 기다릴 때는 sleep이 아니라 join을 쓴다. join은 대상 스레드 객체 위의 wait 루프이며, 종료를 감지했을 때만 결과가 보인다는 보장(happens-before)을 준다.
    스레드 기본 정보
    threadId()는 생성 시 정해지는 고유하고 불변인 값(main은 1)이고, 이름은 고유하지 않은 라벨이다. 이름이 없으면 ID와 별도로 세는 번호로 Thread-N이 붙는다. 우선순위와 데몬 여부, 그룹은 부모 스레드에게서 물려받는다.
    Thread 객체와 OS 스레드
    플랫폼 스레드는 보통 커널 스레드와 1:1로 대응한다. eetop 필드가 VM의 JavaThread를 가리키는 동안(start()부터 종료까지)만 isAlive()가 true다.
    Thread.State
    NEW, RUNNABLE, BLOCKED, WAITING, TIMED_WAITING, TERMINATED의 여섯 가지이며, OS 상태가 아니라 VM의 상태다. 값은 VM이 기록한 threadStatus 비트에서 온다.
    RUNNABLE의 의미
    JVM 안에서 실행 중이라는 뜻일 뿐, CPU를 쓰는지는 알려 주지 않는다. 네이티브 I/O에서 기다리는 스레드도 RUNNABLE이다.
    run()과 체크 예외
    JLS 8.4.8.3에 따라 재정의 메서드는 원래 메서드보다 넓은 체크 예외를 선언할 수 없고, Runnable.run()은 아무것도 선언하지 않는다. 체크 예외는 javac만 검사하며 JVM은 강제하지 않는다(JVMS 4.7.5).
    처리되지 않은 예외
    예외는 그 스레드의 스택 안에서만 전파되고, 바닥에 닿으면 처리기(기본은 스레드 그룹)가 처리한 뒤 그 스레드만 종료된다.
    sleep으로 기다리기의 결함
    시간을 추측해야 하고, JLS 17.3에 따라 sleep에는 동기화 의미가 없어 결과가 보인다는 보장도 없다.
    join
    대상 스레드가 끝날 때까지 기다린다(WAITING). 대상 스레드의 모든 동작은 join()의 성공적인 반환보다 먼저 일어난다(happens-before). 구현은 대상 Thread 객체 위의 wait 루프와 종료 시의 notifyAll이다.
    시간 제한 join
    join(long)은 시간이 다 돼도 조용히 돌아오므로 isAlive()로 확인해야 한다. join(Duration)은 종료 여부를 boolean으로 돌려준다. join(0)은 무한 대기다.
    HotSpot의 세 가지 상태 필드
    OpenJDK 21에서 threadStatus(getState()와 덤프 둘째 줄), OSThread 상태(덤프 머리줄 끝), JavaThread의 _thread_state(세이프포인트용)가 따로 기록된다. 대기 코드를 감싼 상태 변경 객체가 앞의 둘을 쓰며, 네이티브 호출 경로에는 그런 객체가 없어 RUNNABLE이 유지된다. macOS에서 네이티브 스택을 떠 보면 sleep, join, 락 대기가 모두 같은 pthread 조건 변수 대기로 끝난다.
    스레드 종료 처리(ensure_join)
    HotSpot의 JavaThread::exit는 처리기 호출과 Thread.exit() 뒤에 Thread 객체의 모니터를 잡고 TERMINATED 기록, eetop 0으로 지우기, notifyAll을 차례로 한다. 모니터 덕분에 잃어버린 깨어남이 없고, join은 처리기가 끝난 뒤에 돌아온다.

    운영 중인 서비스가 갑자기 응답하지 않을 때 가장 먼저 손에 쥘 증거는 스레드 덤프다. 이 회차에서 읽은 대로 덤프의 각 스레드는 상태와 대기 이유, 기다리는 객체의 주소, 쥐고 있는 락의 주소를 보여 준다. 요청 처리 스레드들이 같은 주소에 대해 waiting to lock으로 몰려 있다면 락 하나가 병목이고, 그 락을 locked로 쥔 스레드가 무엇을 하는지 따라가면 원인이 나온다. 반대로 대부분이 소켓 읽기에서 RUNNABLE이라면 우리 코드가 아니라 외부 시스템(DB, 다른 서버)의 응답이 느린 것일 가능성이 크다. 상태 이름만 보고 "RUNNABLE이 많으니 CPU가 바쁘다"고 판단하면 엉뚱한 곳을 고치게 된다. CPU 문제인지는 덤프를 여러 번 떠서 cpu=의 증가를 비교해 판단한다.

    작업을 나눠 스레드에 맡기는 코드를 검토할 때는 "결과를 읽는 쪽이 무엇으로 종료를 확인하는가"를 묻는다. sleep이나 상태 폴링으로 기다리는 코드는 테스트 환경에서 잘 돌다가 부하가 걸린 운영 환경에서 가끔 틀린 값을 내는, 가장 재현하기 어려운 종류의 버그를 만든다. join이나 이후 회차의 Future, CountDownLatch처럼 happens-before를 보장하는 도구로 바꾸는 것이 원칙이다. 시간 제한을 둔 대기라면 시간 초과 경로에서 결과를 읽지 않는지, 그리고 그때 남은 작업을 어떻게 할지(계속 둘지, 중단을 요청할지)가 정해져 있는지 확인한다.

    백그라운드 스레드를 직접 만드는 코드라면 두 가지를 습관으로 삼는다. 하나는 스레드에 역할이 드러나는 이름을 주는 것이다. 덤프와 로그에서 Thread-12는 아무것도 말해 주지 않는다. 다른 하나는 처리되지 않은 예외의 행방을 정하는 것이다. 기본 처리기는 표준 에러에 한 번 찍고 끝나므로, 로그 수집이 표준 에러를 보지 않는 환경에서는 스레드가 흔적 없이 사라진다. 처리기를 지정하거나 run()의 바깥쪽에서 예외를 잡아 기록하는 구조로 만든다. 스레드 풀을 쓰면 이 판단이 또 달라지는데, 그 차이는 12~13회에서 다룬다.

    4. 첫째, join(1000)은 1초가 지나면 작업이 끝나지 않았어도 조용히 돌아온다. 그 경우 result는 아직 계산되지 않은 값이다. 둘째, 시간이 다 돼서 돌아온 경우에는 종료를 감지하지 못했으므로 happens-before도 없어서, 어떤 값이 보일지 명세가 보장하지 않는다. 고친 모양은 t.join(1000); if (t.isAlive()) { /* 시간 초과 처리: 결과를 읽지 않는다 */ } else { return w.result; }이다. isAlive()가 false를 돌려주면 JLS 17.4.4의 종료 감지가 성립해 result를 안전하게 읽을 수 있다. boolean done = t.join(Duration.ofSeconds(1));로 바꿔 반환값을 검사해도 된다.

    5. JLS 8.4.8.3에 따라 재정의하는 메서드의 throws 절에 적힌 체크 예외마다 같은 클래스나 상위 클래스가 원래 메서드의 throws 절에 있어야 하는데, Runnable.run()에는 throws 절이 없다. IllegalStateException은 언체크 예외라 이 제한을 받지 않는다. 호출자 관점에서, Runnable 타입으로 run()을 부르는 코드는 선언만 보고 체크 예외가 없다고 컴파일되었으므로, 구현이 체크 예외를 추가할 수 있다면 그 호출자는 처리하지 못한 체크 예외를 만나게 된다. 그런데도 실행 중에 빠져나갈 수 있는 이유는 JVMS 4.7.5가 말하듯 던질 수 있는 예외에 대한 요구 사항이 JVM에서는 강제되지 않고 컴파일 시점에만 강제되기 때문이다. 제네릭 소거를 이용한 우회처럼 javac의 검사만 통과하면, JVM은 athrow로 어떤 Throwable이든 던지고 전파한다.

     서버 소켓의 accept()에서 연결을 기다리는 플랫폼 스레드에 대해 다른 스레드가 getState()를 호출했다. OpenJDK 21에서 관찰되는 값과 그 이유로 옳은 것은? BLOCKED: I/O를 기다리며 멈춰 있기 때문이다. RUNNABLE: 네이티브 메서드 안에서 OS를 기다리는 스레드도 JVM 관점에서는 실행 중이기 때문이다. WAITING: 다른 스레드(연결을 보낼 클라이언트)의 행동을 기다리기 때문이다. TIMED_WAITING: 소켓에는 기본 시간 제한이 있기 때문이다. Thread.State는 OS 상태가 아니라 VM의 상태이고, RUNNABLE의 정의는 "JVM 안에서 실행 중이지만 CPU 같은 OS 자원을 기다릴 수 있음"이다. 실험에서 acceptor는 RUNNABLE이었고 CPU 시간은 17ms에 그쳤다. BLOCKED는 모니터 락 대기에만, WAITING은 wait/join/park에만, TIMED_WAITING은 그 시간 제한 판과 sleep에만 쓰인다. 시간 제한을 주지 않은 accept()는 기한 없이 기다린다. 작업 스레드 t에 대해 t.join(500)이 예외 없이 돌아왔다. 이 시점에 확실히 말할 수 있는 것은? t는 종료되었다. t가 쓴 필드 값은 모두 현재 스레드에 보인다. t가 종료되었거나 약 500ms가 지났다. 어느 쪽인지는 isAlive()로 확인해야 한다. t는 아직 실행 중이다. join(long)은 void를 반환하며, 대상이 끝났을 때도 시간이 다 됐을 때도 똑같이 돌아온다. 구현은 isAlive()가 참이고 남은 시간이 있는 동안만 wait를 반복한다. happens-before는 종료를 감지했을 때만 생기므로, 시간 초과로 돌아온 경우에는 필드 값이 보인다는 보장이 없다. 확인은 isAlive()나 join(Duration)의 반환값으로 한다. class Task implements Runnable { public void run() throws InterruptedException { Thread.sleep(10); } }가 컴파일되지 않는 근본 이유는? 재정의하는 메서드는 재정의되는 메서드의 throws 절에 없는 체크 예외를 선언할 수 없는데, Runnable.run()에는 throws 절이 없다. JVM이 실행 중에 run()에서 체크 예외가 나오는지 검사해 막기 때문이다. Thread.sleep은 run() 안에서 호출할 수 없기 때문이다. Runnable이 함수형 인터페이스여서 throws 절을 쓸 수 없기 때문이다. JLS 8.4.8.3의 재정의 규칙 때문이다. Runnable 타입으로 run()을 부르는 코드는 선언만 보고 컴파일되므로, 구현이 체크 예외를 늘리면 그 호출자의 컴파일 시점 보장이 깨진다. JVM은 이 규칙을 강제하지 않는다(JVMS 4.7.5). 그래서 소거를 이용한 우회로 실제로 체크 예외를 던질 수 있었다. sleep은 try-catch로 감싸면 run() 안에서 문제없이 호출된다. 함수형 인터페이스라도 추상 메서드에 throws 절을 둘 수 있다(Callable.call() throws Exception이 그 예다). 작업 스레드가 volatile이 아닌 필드 result에 값을 쓰고 끝난다. main은 작업 스레드를 시작한 뒤 Thread.sleep(5000)을 하고 result를 읽는다. 작업은 1초면 끝난다. 자바 언어 명세 관점에서 옳은 설명은? 5초는 작업 시간보다 충분히 길므로 main은 항상 최종 값을 본다. sleep에서 깨어나는 순간 CPU 캐시가 비워지므로 최종 값을 본다. sleep은 내부적으로 join과 같은 wait 루프를 쓰므로 안전하다. JLS 17.3에 따르면 sleep에는 동기화 의미가 없으므로, 최종 값이 보인다는 보장이 없다. JLS 17.3은 Thread.sleep과 Thread.yield가 어떤 동기화 의미도 갖지 않으며, 컴파일러는 sleep 전후에 레지스터에 캐시된 값을 내보내거나 다시 읽을 필요가 없다고 명시한다. 실험에서 맞는 값이 나오더라도 그것은 특정 JVM과 하드웨어에서의 관찰이다. 보장을 얻으려면 join()(JLS 17.4.5)이나 isAlive()가 false를 돌려주는 것(JLS 17.4.4) 같은 happens-before 관계가 필요하다. sleep은 wait 루프가 아니라 네이티브 sleep0을 호출한다(덤프의 스택). 스레드 덤프에서 서로 다른 두 스레드가 같은 java.lang.Thread 객체에 대해 - waiting on과 - locked를 동시에 표시하고 있다. 이것이 가능한 이유는? 모니터 락은 여러 스레드가 동시에 소유할 수 있는 공유 락이기 때문이다. 두 스레드 모두 join 안에서 그 객체의 모니터에 들어간 뒤 wait로 모니터를 내려놓은 상태이고, - locked는 그 프레임이 모니터에 들어갔다는 기록이기 때문이다. Thread 객체의 모니터는 JVM이 특별히 다루어 락 규칙이 적용되지 않기 때문이다. 덤프를 뜨는 순간 JVM이 모든 락을 잠시 해제하기 때문이다. 모니터 락은 배타적이어서 동시에 한 스레드만 소유할 수 있다. join은 synchronized (this) 안에서 wait를 호출하고, wait는 모니터를 내려놓은 채 대기 집합에서 기다린다. 그래서 여러 스레드가 같은 스레드를 동시에 join할 수 있고, 종료 처리 쪽도 그 객체에 notifyAll을 할 수 있다. 덤프의 - locked 줄은 그 프레임이 synchronized로 진입했다는 표시로 읽어야 한다.
    스레드 ID(thread identifier)
    스레드가 생성될 때 정해지는 양의 long 값. 고유하고 수명 동안 바뀌지 않는다. Java 19부터 threadId()로 얻는다.
    플랫폼 스레드(platform thread)
    보통 OS 커널 스레드와 1:1로 대응하는 자바 스레드. new Thread(...)로 만든 스레드가 여기에 해당한다.
    스레드 상태(Thread.State)
    JVM이 스레드를 분류하는 여섯 가지 상태. OS의 스레드 상태를 반영하지 않는다.
    스레드 덤프(thread dump)
    한 시점에 JVM의 모든 스레드가 어떤 상태로 어떤 코드를 실행하는지, 어떤 락을 쥐고 기다리는지를 찍은 출력. jcmd 프로세스번호 Thread.print나 jstack으로 얻는다.
    체크 예외(checked exception)
    RuntimeException과 Error의 하위 클래스가 아닌 예외. 잡거나 throws로 선언해야 한다는 규칙을 javac가 검사하며, JVM은 이를 강제하지 않는다.
    처리되지 않은 예외 처리기(uncaught exception handler)
    스레드의 run() 밖으로 예외가 빠져나갔을 때 그 스레드 안에서 호출되는 처리기. 따로 지정하지 않으면 스레드 그룹이 이 역할을 한다.
    happens-before
    자바 메모리 모델이 정하는 순서 관계. A가 B보다 happens-before이면 A의 결과가 B에 보인다는 것이 보장된다. start()와 join()이 이 관계를 만든다.
    바쁜 대기(busy waiting)
    조건이 만족될 때까지 루프를 돌며 계속 검사하는 대기 방식. 기다리는 동안 CPU를 쓴다. join은 wait로 잠들어 CPU를 쓰지 않는다.
    가짜 깨어남(spurious wakeup)
    wait 중인 스레드가 통지, 인터럽트, 시간 만료 없이 깨어나는 현상. 그래서 wait는 조건을 다시 검사하는 루프 안에서 써야 한다.
    잃어버린 깨어남(lost wakeup)
    기다리는 쪽이 조건을 확인한 뒤 잠들기 직전에 통지가 먼저 지나가, 그 뒤로 아무도 깨워 주지 않게 되는 문제. 조건 확인과 wait, 상태 변경과 notify를 같은 모니터 안에서 하면 막힌다. HotSpot의 ensure_join이 모니터를 잡는 이유다.
