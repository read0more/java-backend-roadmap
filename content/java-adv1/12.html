    스레드를 직접 만들어 쓸 때 생기는 문제

    지금까지 이 권에서는 일을 시킬 때마다 new Thread(task).start()로 스레드를 직접 만들었다. 학습용으로는 이보다 투명한 방법이 없다. 그러나 서버처럼 짧은 작업이 끊임없이 들어오는 프로그램에서 "작업 하나에 스레드 하나를 새로 만든다"는 전략을 그대로 쓰면 세 가지 문제가 곧바로 드러난다. 스레드를 만드는 데 드는 비용, 스레드 수를 통제하지 못해 생기는 자원 관리 문제, 그리고 Runnable이라는 인터페이스 자체의 불편함이다. 이 회차는 이 세 문제를 차례로 풀어 가는 과정이다.

    첫 번째 문제는 비용이다. 자바의 Thread 객체는 힙에 놓인 평범한 객체처럼 보이지만, start()를 호출하는 순간 실체가 생긴다. Java 21의 Thread API 문서는 플랫폼 스레드(platform thread)를 "보통 운영체제가 스케줄링하는 커널 스레드와 1:1로 대응한다"고 설명하고, 오라클의 가상 스레드 안내서는 더 직접적으로 "플랫폼 스레드는 운영체제 스레드를 얇게 감싼 것"이라고 쓴다. 즉 start() 한 번은 JVM이 운영체제에 새 스레드를 만들어 달라고 요청하는 일이고, 운영체제는 커널 안에 스레드를 관리할 자료구조를 만들고 스케줄러에 등록해야 한다. JVM도 그 스레드를 위한 내부 자료구조를 준비한다. 이 과정은 메서드 호출 몇 번과는 비교할 수 없이 무겁다.

    스택도 비용이다. 1회와 3회에서 보았듯 스레드마다 자기만의 스택이 있고, 크기는 -Xss 옵션으로 정한다. JDK 21의 java 명령 문서에 적힌 기본값은 다음과 같다. Thread 생성자 문서는 스택 크기를 "가상 머신이 이 스레드의 스택에 할당할 주소 공간(address space)의 대략적인 바이트 수"라고 정의한다. 스레드를 하나 만들 때마다 이만큼의 주소 공간을 예약해야 한다는 뜻이다.

    작업 자체가 몇 밀리초 만에 끝나는 일이라면, 스레드를 만들고 없애는 비용이 작업보다 커질 수 있다. 요청 하나를 처리하는 데 10의 일을 하면서 그 일을 맡길 일꾼을 고용하고 해고하는 데 매번 더 큰 수고를 들이는 셈이다. 정확한 비용은 운영체제와 하드웨어에 따라 달라서 여기서 숫자를 제시하지는 않는다. 중요한 것은 비용의 성격이다. 스레드 생성 비용은 작업 내용과 상관없이 작업 개수에 비례해서 붙는다.

    두 번째 문제는 관리다. 요청이 몰려 1초에 수천 개의 작업이 들어오면, 작업마다 스레드를 만드는 전략은 그대로 수천 개의 스레드를 만든다. 스레드 수에 상한이 없으니 스택 주소 공간과 커널 자원이 계속 늘어난다. Thread 생성자 문서 자체가 "일부 플랫폼에서는 스택 크기를 줄이면 OutOfMemoryError 없이 더 많은 스레드를 동시에 둘 수 있다"고 적고 있는데, 거꾸로 말하면 스레드를 계속 늘리면 결국 그 오류를 만난다는 뜻이다. 그 전에도 문제는 생긴다. CPU 코어 수보다 훨씬 많은 스레드가 실행 가능 상태로 몰리면, 운영체제는 이들 사이를 오가느라 컨텍스트 스위칭(context switching)에 시간을 쓰고 CPU 캐시는 계속 식는다(1회). 스레드가 늘어날수록 일은 더 빨리 끝나지 않고 오히려 느려지는 구간이 온다.

    관리 문제에는 "종료"도 포함된다. 애플리케이션을 내릴 때 지금 실행 중인 작업은 끝까지 마치고, 새 작업은 받지 않고, 너무 오래 걸리는 작업은 인터럽트로 정리하고 싶다. 작업마다 스레드를 따로 만들어 흩어 놓으면 이런 정리를 하려면 만든 스레드를 모두 어딘가에 기록해 두었다가 하나씩 다뤄야 한다. 스레드를 한곳에서 관리하는 구조가 필요하다.

    세 번째 문제는 Runnable이다. run()은 반환형이 void이고 throws 절이 없다. 그래서 다른 스레드에서 계산한 결과를 돌려받으려면 공유 필드에 써 두고 join()으로 기다리는 우회로를 써야 하고, 작업 안에서 생긴 체크 예외는 작업 안에서 처리해야 한다. 이 문제는 뒤에서 Callable과 Future로 정면으로 다룬다.

    스레드는 다시 시작할 수 없다: 재사용은 "루프"로 한다

    스레드 생성 비용이 문제라면 해법은 분명하다. 한 번 만든 스레드를 버리지 말고 다시 쓰면 된다. 그런데 "다시 쓴다"는 것이 구체적으로 무엇일까? 실행을 마친 스레드를 다시 start()하는 것은 불가능하다. 3회에서 본 것처럼 run()이 끝난 스레드는 TERMINATED 상태가 되고, 이 상태는 되돌아갈 수 없는 종착점이다. 직접 확인해 보자.

        t.start();
        t.join();
        System.out.println(t.getState());
        t.start(); // 두 번째 start
    }
}

    스레드 객체는 일회용이다. 따라서 스레드를 재사용하려면 발상을 바꿔야 한다. 스레드의 run()이 끝나지 않게 만들고, 그 안에서 "다음 작업을 받아서 실행하고, 끝나면 또 다음 작업을 받는" 루프를 돌리는 것이다. 작업이 없을 때는 바쁜 대기로 CPU를 태우지 말고 잠들어 있어야 하며, 작업이 들어오면 깨어나야 한다. 이것은 8회와 9회에서 다룬 생산자 소비자 문제 그 자체다. 작업을 제출하는 쪽이 생산자, 풀의 스레드가 소비자, 둘 사이의 버퍼가 작업 큐다. 9회의 BlockingQueue를 쓰면 이 구조가 몇 줄로 완성된다.

    import java.util.concurrent.*;

public class MiniPool {
    private final BlockingQueue queue = new LinkedBlockingQueue<>();

    MiniPool(int nThreads) {
        for (int i = 1; i <= nThreads; i++) {
            Thread worker = new Thread(this::workLoop, "mini-" + i);
            worker.setDaemon(true); // 예제를 짧게 하려고 종료 처리 대신 데몬으로 둔다
            worker.start();
        }
    }

    private void workLoop() {
        try {
            while (true) {
                Runnable task = queue.take(); // 작업이 없으면 여기서 WAITING
                task.run();                    // 같은 스레드가 다음 작업을 이어서 실행
            }
        } catch (InterruptedException e) {
            // 인터럽트를 받으면 루프를 끝내고 스레드도 끝난다
        }
    }

    void execute(Runnable task) {
        queue.add(task);
    }

    public static void main(String[] args) throws InterruptedException {
        MiniPool pool = new MiniPool(2);
        for (int i = 1; i <= 5; i++) {
            int n = i;
            pool.execute(() -> System.out.println(
                    "task" + n + " by " + Thread.currentThread().getName()));
        }
        Thread.sleep(500);
    }
}

    다섯 개의 작업을 단 두 개의 스레드가 나눠 처리했다. 스레드는 처음 두 번만 만들어졌고, 이후의 작업은 이미 살아 있는 스레드가 루프를 한 바퀴 더 돌며 처리했다. 이것이 스레드 풀(thread pool)의 핵심 원리 전부다. 스레드 생성 비용은 풀을 만들 때 한 번만 치르고, 동시에 일하는 스레드 수는 풀 크기로 제한되며, 넘치는 작업은 큐에서 기다린다. 앞에서 말한 비용 문제와 관리 문제가 이 구조 하나로 함께 풀린다.

    이 예제에는 빠진 것이 많다. 풀을 종료하는 방법이 없고(그래서 데몬 스레드로 얼버무렸다), 작업이 예외를 던지면 workLoop를 빠져나가 스레드가 죽어 버리며, 그 스레드를 대신할 새 스레드도 만들지 않는다. 결과를 돌려받을 방법도 없다. 자바 표준 라이브러리의 Executor 프레임워크는 이 모든 빈틈을 메운 완성품이다. 그러나 그 심장부는 위의 workLoop와 다르지 않다는 것을 뒤에서 ThreadPoolExecutor의 소스로 확인할 것이다.

    일상에서 가져온 비유주문표 꽂이와 주방 직원

    손님이 올 때마다 요리사를 새로 고용하고 요리가 끝나면 해고하는 식당은 없다. 요리사 몇 명이 주방에 상주하고, 주문표는 꽂이에 순서대로 꽂히며, 손이 빈 요리사가 맨 앞 주문표를 뽑아 요리한다. 주문이 없으면 요리사는 쉬고 있다가 새 주문표가 꽂히면 움직인다. 꽂이가 작업 큐, 요리사가 워커 스레드다. 비유가 깨지는 지점도 있다. 사람 요리사는 요리 도중 급한 주문이 오면 손을 바꿀 수 있지만, 워커 스레드는 지금 실행 중인 작업의 run()이 돌아올 때까지 다른 작업을 집어 들지 않는다. 작업 하나가 오래 걸리면 그 스레드는 그동안 통째로 묶인다.

    스레드를 새로 만드는 대신, 소수의 워커 스레드가 큐에서 작업을 꺼내 실행하는 루프를 돈다는 것을 보여 준다. 왼쪽에 "작업 제출 스레드"라고 적힌 사람 모양 아이콘 두 개가 있고, 각각에서 오른쪽으로 화살표가 나가 가운데의 가로로 긴 상자 "작업 큐"로 들어간다. 작업 큐 안에는 "task3", "task4", "task5"라고 적힌 작은 카드 세 장이 왼쪽에서 오른쪽으로 줄지어 있다. 작업 큐의 오른쪽 끝에서 화살표 두 개가 나와 오른쪽의 두 원형 아이콘 "워커 스레드 1", "워커 스레드 2"로 간다. 각 워커 스레드 아래에는 원을 그리는 순환 화살표가 있고 그 옆에 "take → run → take"라고 적혀 있다. 워커 스레드 1 옆에는 "task1 실행 중", 워커 스레드 2 옆에는 "task2 실행 중"이라는 말풍선이 있다. 그림 아래쪽에 회색 글씨로 "스레드는 처음에만 만들고 계속 재사용"이라고 적는다. 평면적인 일러스트, 흰 배경, 파란색과 회색 위주. 워커 스레드는 끝나지 않는 루프 안에서 큐의 작업을 하나씩 꺼내 실행한다. 스레드 생성 비용은 처음 한 번만 든다.

    Executor 프레임워크의 구조

    자바 5에 들어온 java.util.concurrent 패키지는 스레드 풀을 몇 겹의 인터페이스와 클래스로 나눠 설계했다. 이 계층을 먼저 그려 두면 이후의 모든 API가 어디에 속하는지 길을 잃지 않는다.

              Executor                       void execute(Runnable)
              ▲
              │ extends
       ExecutorService                   생명 주기(shutdown, close ...)
              ▲                          결과 받는 제출(submit → Future)
              │ implements               묶음 처리(invokeAll, invokeAny)
   AbstractExecutorService               submit·invoke*를 execute 위에 구현
              ▲
              │ extends
     ThreadPoolExecutor                  워커 스레드 + 작업 큐 = 스레드 풀

     Executors (유틸리티 클래스)          newFixedThreadPool(n) 등 생성 편의 메서드

    맨 위의 Executor는 메서드가 void execute(Runnable command) 하나뿐인 인터페이스다. 이 인터페이스가 약속하는 것은 "작업을 넘기면 언젠가 실행된다"는 것뿐이고, 어느 스레드가 언제 실행하는지는 구현이 정한다. Executor의 API 문서에는 이 점을 보여 주는 예시 구현이 실려 있다. execute 안에서 r.run()을 그냥 호출해 호출한 스레드가 직접 실행하는 DirectExecutor, 작업마다 new Thread(r).start()를 하는 ThreadPerTaskExecutor, 작업을 하나씩 순서대로 다른 실행기에 넘기는 SerialExecutor다. 즉 Executor는 스레드 풀이 아니라 "작업을 제출하는 것"과 "작업을 실행하는 방식"을 분리하는 경계다. 작업을 만드는 코드는 execute만 알면 되고, 실행 전략(직접 실행, 매번 새 스레드, 풀)은 나중에 갈아 끼울 수 있다.

    ExecutorService는 Executor를 확장해 실무에 필요한 세 가지를 더한다. 첫째는 생명 주기 관리다. shutdown(), shutdownNow(), isShutdown(), isTerminated(), awaitTermination(...), 그리고 Java 19에 추가된 close()가 여기에 속한다. Java 19부터 ExecutorService가 AutoCloseable을 확장하므로 try-with-resources로 쓸 수 있다. 둘째는 결과를 돌려받는 제출이다. submit(Callable), submit(Runnable), submit(Runnable, T)는 모두 Future를 반환한다. 셋째는 작업 묶음 처리인 invokeAll과 invokeAny다.

    AbstractExecutorService는 submit과 invoke* 계열을 execute 하나만 있으면 동작하도록 미리 구현해 둔 추상 클래스다. 뒤에서 소스를 보겠지만 submit은 작업을 FutureTask로 감싸 execute에 넘기고 그 FutureTask를 돌려주는 세 줄짜리 메서드다. 그래서 실제 풀 구현인 ThreadPoolExecutor는 execute와 생명 주기 메서드에만 집중하면 된다.

    ThreadPoolExecutor의 가장 기본적인 생성자는 다섯 개의 인자를 받는다. 기본으로 유지할 스레드 수인 corePoolSize, 최대 스레드 수인 maximumPoolSize, 코어를 넘는 스레드가 일 없이 기다릴 수 있는 시간인 keepAliveTime과 그 단위, 그리고 작업을 담아 둘 BlockingQueue다. 이 값들이 서로 어떻게 맞물려 스레드를 늘리고 줄이는지, 큐가 가득 찼을 때 무슨 일이 일어나는지는 다음 회차에서 자세히 다룬다. 이번 회차에서는 코어와 최대를 같게 두어 크기가 고정된 풀만 쓴다.

    마지막으로 Executors는 자주 쓰는 설정의 풀을 만들어 주는 유틸리티 클래스다. 예를 들어 JDK 21의 Executors.newFixedThreadPool(n)은 소스가 단 한 줄이다.

    // JDK 21 java.util.concurrent.Executors
public static ExecutorService newFixedThreadPool(int nThreads) {
    return new ThreadPoolExecutor(nThreads, nThreads,
                                  0L, TimeUnit.MILLISECONDS,
                                  new LinkedBlockingQueue());
}

    코어와 최대가 같고, 크기 제한이 없는 LinkedBlockingQueue를 쓰는 풀이다. 이 회차의 예제는 대부분 이 메서드로 풀을 만든다.

    ExecutorService 코드로 시작하기

    이제 ThreadPoolExecutor를 직접 만들어 작업 네 개를 넣고, 풀의 상태가 어떻게 바뀌는지 관찰해 보자. 상태는 ThreadPoolExecutor가 제공하는 조회 메서드로 출력한다. getPoolSize()는 풀에 있는 스레드 수, getActiveCount()는 지금 작업을 실행 중인 스레드 수(API 문서는 근사값이라고 밝힌다), getQueue().size()는 큐에서 기다리는 작업 수, getCompletedTaskCount()는 완료된 작업 수다.

    import java.util.concurrent.*;

public class PoolBasic {
    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }

    static void printState(ThreadPoolExecutor pool) {
        log("pool=" + pool.getPoolSize()
                + ", active=" + pool.getActiveCount()
                + ", queued=" + pool.getQueue().size()
                + ", completed=" + pool.getCompletedTaskCount());
    }

    public static void main(String[] args) throws InterruptedException {
        ThreadPoolExecutor pool = new ThreadPoolExecutor(
                2, 2, 0, TimeUnit.MILLISECONDS, new LinkedBlockingQueue<>());
        printState(pool);

        for (int i = 1; i <= 4; i++) {
            String name = "task" + i;
            pool.execute(() -> {
                log(name + " 시작");
                try {
                    Thread.sleep(1000);
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
                log(name + " 완료");
            });
        }
        printState(pool);

        Thread.sleep(3000);
        printState(pool);

        pool.close();
        log("terminated=" + pool.isTerminated());
    }
}

    한 줄씩 추적해 보자. 실행마다 달라지는 부분은 따로 짚는다.

    1. 첫 줄 pool=0. 풀을 만들었지만 스레드는 아직 하나도 없다. ThreadPoolExecutor 문서의 "On-demand construction" 항목대로, 코어 스레드조차 작업이 도착할 때 비로소 만들어진다. 미리 만들어 두고 싶다면 prestartCoreThread()나 prestartAllCoreThreads()를 호출한다.
    2. task1, task2 제출. 스레드 수(0, 1)가 corePoolSize(2)보다 적으므로 제출할 때마다 새 워커 스레드가 만들어지고, 제출한 작업이 그 스레드의 첫 작업으로 바로 넘겨진다. 큐를 거치지 않는다.
    3. task3, task4 제출. 이미 스레드가 2개이므로 더 만들지 않고 큐에 넣는다. 두 번째 상태 출력이 pool=2, queued=2인 이유다. 같은 줄의 active는 출력하는 순간 워커가 작업을 시작했는지에 따라 2보다 작게 나올 수도 있다.
    4. 스레드 이름. pool-1-thread-1 같은 이름은 스레드 팩토리를 지정하지 않았을 때 쓰이는 Executors.defaultThreadFactory()가 붙인다. JDK 21 소스에서 이 팩토리는 이름을 "pool-" + 풀 번호 + "-thread-" + 스레드 번호로 짓는다.
    5. task2 완료 직후 같은 스레드가 task3 시작. pool-1-thread-2가 task2를 마치고 루프를 돌아 큐에서 task3을 꺼냈다. 앞에서 만든 MiniPool과 같은 일이 일어났다. 어느 스레드가 먼저 끝나 task3을 가져갈지는 실행마다 다르다.
    6. 마지막 상태 completed=4. 작업 네 개를 스레드 두 개가 처리했고 둘 다 지금은 쉬고 있다(active=0). 쉬는 동안에도 스레드는 사라지지 않고 pool=2로 남아 있다.
    7. close(). 새 작업 접수를 멈추고 제출된 작업이 모두 끝날 때까지 기다린 뒤 돌아온다. 그래서 다음 줄의 isTerminated()가 true다.

    마지막 줄의 close()를 빼고 실행하면 어떻게 될까? 결과는 똑같이 출력되지만 프로그램이 끝나지 않는다. 기본 스레드 팩토리는 만든 스레드를 명시적으로 데몬이 아닌(non-daemon) 스레드로 설정하고, Thread 문서에 따르면 JVM의 종료 절차는 시작된 비데몬 스레드가 모두 끝나야 시작된다. 그런데 풀의 워커 스레드는 큐에서 다음 작업을 기다리며 영원히 잠들어 있다. main이 끝나도 JVM이 살아 있는 이유다. 스레드 풀을 만들었으면 반드시 종료해야 하고, 종료의 세부 절차(shutdown과 shutdownNow의 차이, 우아한 종료)는 다음 회차의 주제다.

    Java 19 이상에서는 try-with-resources로 종료를 빠뜨리지 않게 할 수 있다. ExecutorService.close()의 기본 구현은 다음과 같다.

    // JDK 21 java.util.concurrent.ExecutorService (기본 메서드)
default void close() {
    boolean terminated = isTerminated();
    if (!terminated) {
        shutdown();
        boolean interrupted = false;
        while (!terminated) {
            try {
                terminated = awaitTermination(1L, TimeUnit.DAYS);
            } catch (InterruptedException e) {
                if (!interrupted) {
                    shutdownNow();
                    interrupted = true;
                }
            }
        }
        if (interrupted) {
            Thread.currentThread().interrupt();
        }
    }
}

    shutdown()으로 접수를 닫고, 끝날 때까지 하루 단위로 기다리기를 반복한다. 기다리는 도중 close()를 호출한 스레드가 인터럽트를 받으면 shutdownNow()로 실행 중인 작업에 인터럽트를 건 뒤에도 계속 기다리고, 마지막에 인터럽트 상태를 복구한다. 4회에서 본 "인터럽트를 삼키지 말고 복구한다"는 관례가 표준 라이브러리 안에서도 그대로 지켜지고 있다.

    한 층 아래: ThreadPoolExecutor 안에서 일어나는 일

    방금 관찰한 동작을 ThreadPoolExecutor의 소스로 확인해 보자. 처음 눈에 띄는 것은 풀의 상태를 담는 필드가 하나뿐이라는 점이다.

    // JDK 21 java.util.concurrent.ThreadPoolExecutor
private final AtomicInteger ctl = new AtomicInteger(ctlOf(RUNNING, 0));
private static final int COUNT_BITS = Integer.SIZE - 3;      // 29
private static final int COUNT_MASK = (1 << COUNT_BITS) - 1;

private static final int RUNNING    = -1 << COUNT_BITS;
private static final int SHUTDOWN   =  0 << COUNT_BITS;
private static final int STOP       =  1 << COUNT_BITS;
private static final int TIDYING    =  2 << COUNT_BITS;
private static final int TERMINATED =  3 << COUNT_BITS;

    ctl은 32비트 int 하나에 두 가지 정보를 함께 담는다. 상위 3비트는 풀의 실행 상태(runState)이고 하위 29비트는 워커 수(workerCount)다. RUNNING은 -1 << 29, 즉 16진수로 0xE0000000이라 상위 3비트가 모두 1이다. 소스 주석은 이렇게 담느라 워커 수의 상한을 (2^29)-1(약 5억)로 제한했다고 밝힌다. 굳이 두 값을 한 변수에 묶은 이유는 10회에서 다룬 CAS 때문이다. "풀이 아직 RUNNING이면 워커 수를 1 늘린다"는 판단은 두 값을 동시에 보고 동시에 바꿔야 하는데, 하나의 AtomicInteger에 들어 있으면 compareAndSet 한 번으로 원자적으로 처리할 수 있다. 락 없이 상태와 개수를 함께 다루는 장치다.

    실행 상태는 다섯 가지다. 소스 주석의 설명을 옮기면, RUNNING은 새 작업을 받고 큐의 작업도 처리하는 상태, SHUTDOWN은 새 작업은 받지 않지만 큐의 작업은 처리하는 상태, STOP은 새 작업도 받지 않고 큐의 작업도 처리하지 않으며 실행 중인 작업에 인터럽트를 거는 상태다. TIDYING과 TERMINATED는 모든 작업과 워커가 사라진 뒤 종료 훅을 실행하는 중간 단계와 최종 단계다. 앞의 예제에서 close()가 거친 길이 RUNNING → SHUTDOWN → TIDYING → TERMINATED다.

    워커: 스레드와 그 스레드가 도는 루프

    풀의 스레드는 Worker라는 내부 클래스가 감싼다.

    // JDK 21 ThreadPoolExecutor 내부 클래스 (발췌)
private final class Worker
    extends AbstractQueuedSynchronizer
    implements Runnable
{
    final Thread thread;          // 이 워커가 도는 스레드
    Runnable firstTask;           // 처음 맡은 작업 (없으면 null)
    volatile long completedTasks; // 이 워커가 끝낸 작업 수

    Worker(Runnable firstTask) {
        setState(-1); // inhibit interrupts until runWorker
        this.firstTask = firstTask;
        this.thread = getThreadFactory().newThread(this);
    }
    // run()은 바깥 클래스의 runWorker(this)를 호출한다
    // ...
}

    Worker는 두 가지 얼굴을 갖는다. 하나는 Runnable이다. 스레드 팩토리에 자기 자신을 넘겨 스레드를 만들므로, 그 스레드가 시작되면 Worker.run()이 실행되고 이것이 runWorker(this)를 부른다. 다른 하나는 AbstractQueuedSynchronizer(AQS)다. 7회에서 ReentrantLock의 바탕으로 본 바로 그 클래스로, 워커는 이것을 이용해 재진입하지 않는 단순한 락을 하나씩 갖는다. 워커는 작업 하나를 실행하는 동안 이 락을 잡고 있고, 그래서 "락이 잡혀 있는 워커 = 지금 일하는 워커"가 된다. 실제로 toString()과 getActiveCount()는 워커들을 돌며 락이 잡힌 워커의 수를 센다. 생성자에서 상태를 -1로 두는 것은 스레드가 루프에 들어가기 전에는 인터럽트 대상이 되지 않게 하려는 장치다.

    그리고 runWorker가 앞에서 직접 만든 workLoop의 완성판이다.

    // JDK 21 ThreadPoolExecutor.runWorker (주석 일부 생략)
final void runWorker(Worker w) {
    Thread wt = Thread.currentThread();
    Runnable task = w.firstTask;
    w.firstTask = null;
    w.unlock(); // allow interrupts
    boolean completedAbruptly = true;
    try {
        while (task != null || (task = getTask()) != null) {
            w.lock();
            // 풀이 STOP 이상이면 인터럽트를 보장하고,
            // 아니면 인터럽트 플래그를 지운다 (Thread.interrupted())
            if ((runStateAtLeast(ctl.get(), STOP) ||
                 (Thread.interrupted() &&
                  runStateAtLeast(ctl.get(), STOP))) &&
                !wt.isInterrupted())
                wt.interrupt();
            try {
                beforeExecute(wt, task);
                try {
                    task.run();
                    afterExecute(task, null);
                } catch (Throwable ex) {
                    afterExecute(task, ex);
                    throw ex;
                }
            } finally {
                task = null;
                w.completedTasks++;
                w.unlock();
            }
        }
        completedAbruptly = false;
    } finally {
        processWorkerExit(w, completedAbruptly);
    }
}

    구조는 MiniPool과 같다. 첫 작업(firstTask)이 있으면 그것부터 실행하고, 그다음부터는 getTask()로 큐에서 작업을 받아 실행하기를 반복한다. getTask()가 null을 돌려줄 때만 루프가 끝나고 스레드도 끝난다. 덧붙은 것은 세 가지다. 작업 전후에 하위 클래스가 끼어들 수 있는 훅인 beforeExecute와 afterExecute, 작업 실행 중임을 표시하는 워커 락, 그리고 루프를 벗어날 때 뒷정리를 하는 processWorkerExit다. 작업이 예외를 던지면 throw ex로 루프 밖까지 전파되어 스레드가 끝나는데, 이때 completedAbruptly가 true로 남아 processWorkerExit가 대체 워커를 새로 만든다. 이 동작은 뒤의 "Future와 예외"에서 실행 결과로 확인한다.

    인터럽트 처리 부분도 눈여겨볼 만하다. 풀이 STOP 상태가 아니라면 Thread.interrupted()를 호출해 인터럽트 플래그를 지우고 다음 작업을 시작한다. 앞 작업에서 남은 인터럽트가 다음 작업으로 새어 들어가 엉뚱한 작업이 InterruptedException을 맞는 일을 막는 장치다. 같은 스레드가 여러 작업을 이어서 실행하는 풀이라서 필요한 처리다.

    getTask()의 핵심은 큐에서 꺼내는 두 줄이다.

    // JDK 21 ThreadPoolExecutor.getTask (발췌)
boolean timed = allowCoreThreadTimeOut || wc > corePoolSize;
// ...
Runnable r = timed ?
    workQueue.poll(keepAliveTime, TimeUnit.NANOSECONDS) :
    workQueue.take();

    워커 수가 코어 이하이고 코어 스레드 타임아웃을 허용하지 않았다면 take()로 작업이 올 때까지 무기한 기다린다. 코어를 넘는 스레드라면 poll(keepAliveTime)으로 정해진 시간만 기다리고, 그동안 작업이 오지 않으면 null을 받아 스스로 퇴장한다. 코어 스레드는 남고 초과 스레드는 사라지는 이 규칙이 다음 회차에서 다룰 풀 크기 관리의 토대다.

    그렇다면 일이 없을 때 워커 스레드는 정확히 어떤 상태일까? 쉬고 있는 워커의 상태와 스택을 직접 찍어 보면 이 권에서 쌓아 온 도구들이 한 줄로 이어진다.

    pool-1-thread-1 상태=WAITING

  at java.base/java.util.concurrent.locks.LockSupport.park(LockSupport.java:371)

    아래에서 위로 읽으면 이렇다. 워커는 getTask()에서 LinkedBlockingQueue.take()를 호출했고, 큐가 비어 있어 9회에서 본 Condition.await()로 들어갔으며, 그 아래에서 7회의 LockSupport.park()로 스케줄링 대상에서 빠졌다. 그래서 상태가 WAITING이다. 쉬는 워커는 CPU를 전혀 쓰지 않고, 누군가 큐에 작업을 넣어 signal을 보내면 깨어난다. 스레드 풀은 새로운 마법이 아니라 이 권에서 지금까지 다룬 락·조건 변수·블로킹 큐를 조립한 결과다.

    마지막으로 execute가 작업을 어디로 보내는지 정리해 두자. JDK 21 소스의 execute는 세 단계로 판단한다. (1) 워커 수가 corePoolSize보다 적으면 그 작업을 첫 작업으로 하는 새 워커를 만든다. (2) 그렇지 않으면 큐에 넣는다(offer). (3) 큐에 넣지 못하면 maximumPoolSize까지 워커를 더 만들어 보고, 그것도 안 되면 작업을 거절한다. 앞 예제에서 task1·task2는 (1)로, task3·task4는 (2)로 처리되었다. (3)의 동작과 거절 정책은 다음 회차에서 다룬다.

    Runnable의 불편함과 Callable

    스레드 관리 문제는 풀로 풀었다. 남은 것은 세 번째 문제, Runnable이라는 인터페이스다. 시그니처를 다시 보자.

    public interface Runnable {
    void run();
}

    반환형이 void이므로 계산 결과를 돌려줄 수 없다. throws 절이 없으므로 체크 예외(checked exception)를 밖으로 던질 수도 없다. 자바 기본편에서 배운 규칙대로, 오버라이딩하는 메서드는 상위 메서드가 선언하지 않은 체크 예외를 던질 수 없기 때문이다. 람다도 예외가 아니다. 작업 안에서 Thread.sleep을 그냥 호출하면 컴파일이 되지 않는다.

    Runnable r = () -> {
    Thread.sleep(1000);
};
    RunnableCheck.java:4: error: unreported exception InterruptedException; must be caught or declared to be thrown
            Thread.sleep(1000);
                        ^
1 error

    그래서 Runnable로 결과를 얻으려면 작업 객체에 결과 필드를 두고, 작업을 실행한 스레드를 join()으로 기다린 뒤 그 필드를 읽는 방식을 써야 했다. 3회와 5회에서 보았듯 join()이 happens-before를 만들어 주기 때문에 이 방식이 안전했던 것이다. 그런데 스레드 풀에서는 이 방법조차 쓸 수 없다. 풀의 스레드는 작업이 끝나도 죽지 않으므로 join()으로 "작업이 끝났음"을 알 수 없다. 작업이 끝났다는 신호와 결과를 전달할 다른 장치가 필요하다.

    자바 5는 이 문제를 위해 Callable을 도입했다.

    public interface Callable {
    V call() throws Exception;
}

    두 가지가 달라졌다. 반환형이 타입 매개변수 V여서 결과를 돌려줄 수 있고, throws Exception이 선언되어 있어 어떤 체크 예외든 밖으로 던질 수 있다. Callable의 API 문서도 Runnable과 비슷하지만 Runnable은 "결과를 반환하지 않고 체크 예외를 던질 수 없다"는 점이 다르다고 설명한다.

    ExecutorService 내부에서는 모든 작업이 결국 Callable로 통일된다. submit(Runnable)으로 넘긴 작업은 Executors.callable(...)이 만드는 어댑터로 감싸진다. JDK 21 소스의 어댑터는 이렇게 단순하다.

    // JDK 21 Executors 내부 클래스
private static final class RunnableAdapter implements Callable {
    private final Runnable task;
    private final T result;
    RunnableAdapter(Runnable task, T result) {
        this.task = task;
        this.result = result;
    }
    public T call() {
        task.run();
        return result;
    }
    // ...
}

    Runnable을 실행하고 미리 정해 둔 값(submit(Runnable)이면 null)을 반환한다. 그래서 submit(Runnable)이 돌려준 Future의 get()은 작업이 정상 종료되면 null을 반환한다.

    람다를 넘기면 어느 submit이 호출되는가

    submit은 Runnable을 받는 버전과 Callable을 받는 버전으로 오버로딩되어 있다. 인자 없는 람다는 두 함수형 인터페이스 모두에 맞을 수 있으므로, 컴파일러가 어느 쪽을 고르는지 알아 둘 필요가 있다. 세 가지 람다를 넘기고 javap -c로 바이트코드에 기록된 호출 대상을 확인해 보았다.

    AtomicInteger counter = new AtomicInteger();

    반대로 몸체가 { Thread.sleep(1000); }처럼 값을 반환하지 않는 블록이면 Runnable에만 맞으므로, 앞에서 본 것과 같은 "unreported exception InterruptedException" 컴파일 오류가 난다. 같은 작업에 return null; 한 줄을 붙이면 Callable로 바뀌어 컴파일된다. 람다의 몸체 모양이 호출되는 메서드를 바꾼다는 것을 기억해 두면 이런 컴파일 오류를 만났을 때 당황하지 않는다.

    Future 소개: 아직 오지 않은 결과를 붙잡는 손잡이

    Callable로 결과를 반환할 수 있게 되었다. 그런데 그 결과는 다른 스레드에서 나중에 만들어진다. 작업을 제출한 스레드는 그 결과를 어떻게 받을까? submit이 작업이 끝날 때까지 기다렸다가 결과를 반환한다면, 제출한 스레드는 그동안 아무것도 못 하고 멈춰 있게 된다. 그러면 다른 스레드에 일을 맡긴 의미가 사라진다. 그래서 submit은 결과 대신 결과를 나중에 받을 수 있는 손잡이를 즉시 돌려준다. 그것이 Future다. API 문서의 표현대로 Future는 비동기 계산의 결과를 나타내며, 계산이 끝났는지 확인하고, 끝나기를 기다리고, 결과를 꺼내는 메서드를 제공한다.

    작업을 하나 제출하고, 결과를 기다리는 동안 main 스레드가 어떤 상태인지 관찰자 스레드로 들여다보자.

    import java.util.concurrent.*;

public class FutureBasic {
    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }

    public static void main(String[] args) throws Exception {
        ExecutorService es = Executors.newFixedThreadPool(1);
        Thread mainThread = Thread.currentThread();

        Future future = es.submit(() -> {
            log("작업 시작");
            Thread.sleep(2000);
            log("작업 완료");
            return 42;
        });
        log("submit 반환: " + future.getClass().getName() + ", state=" + future.state());

        Thread observer = new Thread(() -> {
            try { Thread.sleep(1000); } catch (InterruptedException e) { return; }
            log("main 상태=" + mainThread.getState());
            StackTraceElement[] st = mainThread.getStackTrace();
            for (int i = 0; i < 4 && i < st.length; i++) {
                log("  at " + st[i]);
            }
        }, "observer");
        observer.start();

        log("get() 호출");
        Integer result = future.get();
        log("결과=" + result + ", state=" + future.state() + ", isDone=" + future.isDone());
        observer.join();
        es.close();
    }
}

    이 출력에서 읽을 것이 네 가지다.

    • submit은 즉시 돌아온다. 작업은 2초가 걸리지만 main은 기다리지 않고 바로 다음 줄로 진행했다. 돌려받은 객체의 실제 클래스는 java.util.concurrent.FutureTask다.
    • 돌아온 시점의 상태는 RUNNING이다. Future.state()는 Java 19에 추가된 메서드로, 작업의 상태를 RUNNING, SUCCESS, FAILED, CANCELLED 네 가지 열거형 값으로 알려 준다. RUNNING은 "아직 끝나지 않았다"는 뜻이어서, 큐에서 차례를 기다리는 작업도 RUNNING으로 보고된다.
    • get()을 부른 main은 WAITING이 된다. 스택을 보면 FutureTask.get() → awaitDone() → LockSupport.park()다. 결과를 기다리는 일도 결국 7회의 park로 스레드를 재우는 일이다. BLOCKED가 아니라 WAITING인 이유도 모니터 락이 아니라 park로 멈췄기 때문이다.
    • 작업이 끝나면 main이 깨어나 결과 42를 받는다. 이때 상태는 SUCCESS, isDone()은 true다.

    정리하면 Future를 쓰는 흐름은 두 단계로 나뉜다. 제출은 즉시 끝나고 손잡이를 받는다. 회수(get)는 결과가 준비될 때까지 기다린다. 이 둘이 분리되어 있다는 것이 Future의 존재 이유이며, 제출과 회수 사이에 다른 일을 끼워 넣을 수 있다는 데서 성능 이득이 나온다. 이 점은 잠시 뒤 "Future가 필요한 이유"에서 실행 시간으로 확인한다.

    Future 분석: FutureTask의 내부

    이제 submit이 돌려준 FutureTask가 어떻게 만들어지고, 워커 스레드와 get()을 부른 스레드가 이 객체를 통해 어떻게 만나는지 소스로 따라가 보자. 출발점은 AbstractExecutorService.submit이다.

    // JDK 21 java.util.concurrent.AbstractExecutorService
protected  RunnableFuture newTaskFor(Callable callable) {
    return new FutureTask(callable);
}

public  Future submit(Callable task) {
    if (task == null) throw new NullPointerException();
    RunnableFuture ftask = newTaskFor(task);
    execute(ftask);
    return ftask;
}

    핵심은 FutureTask가 RunnableFuture, 즉 Runnable이면서 동시에 Future라는 점이다. 같은 객체 하나가 execute(ftask)를 통해 Runnable로서 작업 큐에 들어가 워커 스레드에게 전달되고, return ftask를 통해 Future로서 제출한 스레드에게도 전달된다. 워커는 이 객체의 run()을 부르고, 제출한 스레드는 이 객체의 get()을 부른다. 두 스레드가 만나는 장소가 바로 이 FutureTask 객체의 필드들이다.

      main 스레드                        FutureTask (힙)                     워커 스레드
  ──────────                     ┌────────────────────────┐            ──────────
  submit(callable) ── new ──────▶│ state    = NEW (volatile)│
        │                         │ callable = 작업          │
        │ execute(ftask) ── 큐 ──────────────────────────────────▶ take() → ftask.run()
        │                         │ runner   = 워커 (CAS)    │◀──── runner 기록
  ◀── return ftask                │ outcome  = (비어 있음)   │
        │                         │ waiters  = 스택 top      │
  get() ─ state가 NEW ──▶ WaitNode를 waiters에 push ─ park   │
        │      (WAITING)          │                          │      c.call() → 42
        │                         │ state NEW→COMPLETING(CAS)│◀──── set(42)
        │                         │ outcome  = 42            │
        │                         │ state    = NORMAL        │
        │  ◀────────────── unpark(main) ─ finishCompletion() ┘
  깨어나 state 확인 → NORMAL → outcome 42 반환

    FutureTask의 필드는 다섯 개다. JDK 21 소스의 주석과 함께 보면 다음과 같다.

    // JDK 21 java.util.concurrent.FutureTask (필드)
private volatile int state;      // 실행 상태, 처음은 NEW
private Callable callable;    // 실행할 작업, 실행 후 null로 비움
private Object outcome;          // non-volatile, protected by state reads/writes
private volatile Thread runner;  // callable을 실행 중인 스레드, run()에서 CAS로 기록
private volatile WaitNode waiters; // Treiber stack of waiting threads

    소스 맨 앞의 개정 메모에 따르면 예전 버전의 FutureTask는 AQS에 기대어 구현되었지만, 지금은 CAS로 갱신하는 state 필드와 대기 스레드를 담는 단순한 트라이버 스택(Treiber stack)으로 동기화한다. 트라이버 스택은 맨 위 노드를 CAS로 바꿔 끼우는 방식의 락 없는 연결 스택으로, 10회에서 본 CAS 루프를 자료구조에 적용한 것이다. get()을 부른 스레드는 자기 스레드를 담은 WaitNode를 만들어 이 스택 맨 위에 CAS로 올려놓고 park한다. 여러 스레드가 같은 Future의 get()을 불러도 모두 이 스택에 쌓였다가 함께 깨어난다.

    상태 기계

    state는 7개의 값을 갖는다. 소스 주석이 밝힌 가능한 전이는 네 갈래뿐이다.

    NEW(0) ──▶ COMPLETING(1) ──▶ NORMAL(2)          정상 완료: set(v)
NEW(0) ──▶ COMPLETING(1) ──▶ EXCEPTIONAL(3)     예외 발생: setException(t)
NEW(0) ──────────────────▶ CANCELLED(4)         cancel(false)
NEW(0) ──▶ INTERRUPTING(5) ──▶ INTERRUPTED(6)   cancel(true)

COMPLETING, INTERRUPTING : 잠깐 거쳐 가는 중간 상태
NORMAL, EXCEPTIONAL, CANCELLED, INTERRUPTED : 다시 바뀌지 않는 최종 상태

    모든 전이가 NEW에서 출발한다는 데 주목하자. 작업 완료(set), 예외(setException), 취소(cancel)는 모두 "state가 아직 NEW이면 다음 값으로 바꾼다"는 CAS로 시작한다. 그래서 셋 중 먼저 CAS에 성공한 쪽 하나만 결과를 확정할 수 있다. 작업이 끝나는 순간과 다른 스레드가 취소하는 순간이 겹쳐도 결과는 둘 중 하나로 깔끔하게 정해진다. 정상 완료 경로의 코드는 다음과 같다.

    // JDK 21 FutureTask.run (발췌)과 set
public void run() {
    if (state != NEW ||
        !RUNNER.compareAndSet(this, null, Thread.currentThread()))
        return;
    try {
        Callable c = callable;
        if (c != null && state == NEW) {
            V result;
            boolean ran;
            try {
                result = c.call();
                ran = true;
            } catch (Throwable ex) {
                result = null;
                ran = false;
                setException(ex);
            }
            if (ran)
                set(result);
        }
    } finally {
        runner = null;
        // ... (취소 인터럽트 처리)
    }
}

protected void set(V v) {
    if (STATE.compareAndSet(this, NEW, COMPLETING)) {
        outcome = v;
        STATE.setRelease(this, NORMAL); // final state
        finishCompletion();
    }
}

    run()의 첫 줄은 두 가지를 확인한다. 상태가 NEW가 아니면(이미 취소되었거나 끝났으면) 아무것도 하지 않고 돌아가고, runner를 CAS로 자기 스레드로 바꾸는 데 실패하면(다른 스레드가 이미 실행 중이면) 역시 돌아간다. 같은 작업이 두 번 실행되는 것을 막는 장치다. 그다음 call()을 실행해 결과를 set하거나, 예외를 잡아 setException한다. catch (Throwable ex)라는 점이 중요하다. 작업이 던진 것은 체크 예외든 런타임 예외든 Error든 모두 이 자리에서 잡혀 outcome에 저장된다. 이것이 뒤에서 볼 "submit한 작업의 예외가 사라지는 현상"의 원인이다.

    finishCompletion()은 waiters 스택을 CAS로 통째로 떼어 낸 뒤, 노드를 하나씩 따라가며 기다리던 스레드를 LockSupport.unpark로 깨운다. 그리고 하위 클래스가 완료를 통지받을 수 있는 done() 훅을 부르고, 더는 필요 없는 callable 참조를 null로 지워 메모리를 덜 붙잡게 한다. done() 훅은 표준 라이브러리 안에서도 쓰인다. 예를 들어 ExecutorCompletionService는 FutureTask를 상속한 내부 클래스에서 done()을 오버라이드해, 끝난 작업을 완료 큐에 넣는다.

    깨어난 get() 쪽은 상태를 다시 읽고 report(s)로 결과를 만든다.

    // JDK 21 FutureTask.report
private V report(int s) throws ExecutionException {
    Object x = outcome;
    if (s == NORMAL)
        return (V)x;
    if (s >= CANCELLED)
        throw new CancellationException();
    throw new ExecutionException((Throwable)x);
}

    정상이면 outcome을 결과로 반환하고, 취소 계열이면 CancellationException을, 예외로 끝났으면 저장해 둔 예외를 ExecutionException으로 감싸 던진다. get() 하나로 세 가지 결말이 모두 전달되는 구조다.

    outcome이 volatile이 아닌데 안전한 이유

    5회를 떠올리면 의문이 생긴다. 워커 스레드가 쓴 outcome을 main 스레드가 읽는데, outcome은 volatile이 아니다. main이 낡은 값(null)을 볼 위험은 없을까? 소스 주석이 답을 준다. outcome은 "state를 읽고 쓰는 것으로 보호된다". 순서를 보자. 워커는 (1) outcome = v를 쓰고 (2) state를 NORMAL로 바꾼다. 이 두 번째 쓰기는 setRelease, 즉 릴리스 의미를 갖는 쓰기여서 그 앞의 쓰기가 뒤로 밀리지 않는다. get() 쪽은 (3) volatile인 state를 읽어 NORMAL임을 확인한 뒤에야 (4) outcome을 읽는다. 프로그램 순서상 (1)은 (2)보다, (3)은 (4)보다 앞선다. (2)와 (3)을 잇는 근거는 엄밀히 말하면 5회의 volatile 규칙(JLS 17.4)이 아니다. setRelease는 volatile 모드 쓰기가 아니라 VarHandle의 릴리스 모드 쓰기이기 때문이다. 대신 VarHandle API 문서가 획득(acquire) 모드 읽기와 그 뒤의 접근은 짝이 되는 릴리스 모드 쓰기와 그 앞의 접근보다 뒤에 순서 지어진다고 정하고, volatile 읽기는 이 획득 모드의 성질을 함께 갖는다. (3)이 (2)가 쓴 값을 읽었으므로 (4)는 (1)보다 뒤에 순서 지어지고, 따라서 (1)의 쓰기는 (4)에서 반드시 보인다. volatile 변수 하나로 일반 필드의 가시성까지 실어 나르는, 5회에서 본 기법과 같은 발상이다.

    이 보장은 구현 세부에만 기대는 것이 아니라 API 계약으로도 명시되어 있다. java.util.concurrent 패키지 문서의 "Memory Consistency Properties" 절은 두 가지를 약속한다. 작업을 Executor에 제출하기 전에 제출한 스레드가 한 일은 그 작업의 실행이 시작되기 전에 일어난 것으로 보장되고(happen-before), Future가 나타내는 비동기 계산이 한 일은 다른 스레드에서 Future.get()으로 결과를 받은 뒤의 동작보다 앞서 일어난 것으로 보장된다. 그래서 작업에 넘길 데이터를 제출 전에 준비해 두거나, 작업이 만든 객체를 get() 이후에 읽는 코드는 volatile이나 synchronized 없이도 안전하다. 단, 이 보장은 "제출 전"과 "get() 후"라는 두 지점에서만 성립한다. 작업이 실행되는 도중에 다른 스레드와 공유하는 데이터는 여전히 6회와 7회의 도구로 보호해야 한다.

    main 스레드, FutureTask, 작업 큐, 워커 스레드 사이에서 submit부터 get 반환까지 일어나는 일을 시간 순서로 보여 준다. 가로로 네 개의 생명선이 있는 시퀀스 다이어그램. 왼쪽부터 "main 스레드", "FutureTask", "작업 큐", "워커 스레드". 위에서 아래로 시간이 흐른다. 1) main에서 FutureTask로 "submit: new FutureTask" 화살표. 2) FutureTask에서 작업 큐로 "execute" 화살표. 3) FutureTask에서 main으로 점선 반환 화살표 "Future 즉시 반환". 4) 작업 큐에서 워커 스레드로 "take" 화살표. 5) main에서 FutureTask로 "get()" 화살표, main 생명선의 이 지점부터 회색 막대로 "WAITING (park)" 구간 표시. 6) 워커 스레드 생명선에 "call() 실행" 막대. 7) 워커에서 FutureTask로 "set(결과): state = NORMAL" 화살표. 8) FutureTask에서 main으로 "unpark" 화살표, main의 회색 막대가 여기서 끝난다. 9) FutureTask에서 main으로 점선 "결과 반환". 흰 배경, 간결한 선, 라벨은 한국어 그대로. submit은 FutureTask를 즉시 돌려주고, get을 부른 스레드는 워커가 set으로 상태를 확정하고 unpark할 때까지 WAITING 상태로 기다린다.

    제출 쪽의 happens-before: 작업은 어떻게 워커에게 안전하게 건너가는가

    앞 절에서는 get() 쪽의 보장을 설명했다. 워커가 쓴 outcome이 기다리던 스레드에게 보이는 이유는 state 필드의 릴리스·획득 짝이었다. 패키지 문서가 약속하는 나머지 절반은 반대 방향이다. 제출한 스레드가 submit 전에 한 일은 작업 실행이 시작되기 전에 일어난 것으로 보장된다. 그런데 제출한 스레드와 워커 스레드는 서로 다른 스레드이고, FutureTask의 callable 필드도, Worker의 firstTask 필드도 volatile이 아니다. OpenJDK 21의 ThreadPoolExecutor가 이 약속을 실제로 어떤 장치로 지키는지 JLS 17.4의 규칙에 하나씩 대어 보자. 앞에서 본 execute의 판단에 따라 경로는 둘이다. 새 워커를 만들어 작업을 첫 작업으로 넘기는 경로와, 이미 쉬고 있는 워커에게 큐로 넘기는 경로다.

    첫 작업 경로: 스레드 시작 규칙

    새 워커를 만드는 addWorker는 new Worker(firstTask)로 작업을 일반 필드에 담고, 워커를 집합에 등록한 뒤 스레드를 시작한다. JDK 21에서는 공개 메서드 Thread.start()를 직접 부르지 않고 풀이 가진 스레드 컨테이너를 거친다.

    // JDK 21 ThreadPoolExecutor.addWorker (발췌)
w = new Worker(firstTask);          // firstTask는 일반 필드에 기록된다
final Thread t = w.thread;
// ... mainLock을 잡고 workers.add(w) ...
if (workerAdded) {
    container.start(t);             // SharedThreadContainer.start
    workerStarted = true;
}

// JDK 21 java.lang.Thread (패키지 내부 메서드, 발췌)
void start(ThreadContainer container) {
    synchronized (this) {
        if (holder.threadStatus != 0)
            throw new IllegalThreadStateException();
        // ... 스레드를 컨테이너에 묶는다 ...
        start0();                   // 공개 start()가 부르는 것과 같은 네이티브 메서드
    }
}

    SharedThreadContainer.start는 내부 접근 경로로 이 Thread.start(ThreadContainer)를 호출하고, 이 메서드는 공개 start()와 똑같이 start0()으로 스레드를 띄운다. JLS §17.4.4는 "스레드를 시작하는 동작은 그 스레드의 첫 동작과 동기화된다(synchronizes-with)"고 정하고, §17.4.5는 같은 내용을 "start() 호출은 시작된 스레드의 모든 동작보다 먼저 일어난다"는 happens-before 규칙으로 적는다. 사슬은 이렇게 이어진다. 제출 스레드 안에서 (1) 작업에 넘길 데이터 준비 → (2) firstTask 기록 → (3) 스레드 시작은 프로그램 순서다. (3)은 워커의 첫 동작과 동기화된다. 워커 안에서 (4) runWorker가 w.firstTask를 읽고 (5) 작업을 실행하는 것은 다시 프로그램 순서다. §17.4.5의 추이성(hb(x, y)이고 hb(y, z)이면 hb(x, z))에 따라 (1)은 (5)보다 먼저 일어난다.

    큐 경로: 락이 둘인데 무엇이 다리가 되는가

    워커가 이미 살아서 take()에서 쉬고 있다면 스레드 시작 규칙은 쓸 수 없다. 그 워커는 오래전에 시작되었다. 이때 다리를 놓는 것은 작업 큐다. BlockingQueue 문서는 원소를 큐에 넣기 전에 한 동작이 다른 스레드가 그 원소를 꺼낸 뒤의 동작보다 먼저 일어난다는 메모리 일관성 효과를 약속하고, ThreadPoolExecutor의 보장은 결국 이 약속 위에 서 있다. 그런데 9회에서 본 것처럼 LinkedBlockingQueue는 넣기와 꺼내기에 서로 다른 락(putLock, takeLock)을 쓴다. 6회의 모니터 규칙이나 7회의 라이브러리 락 규칙은 같은 락의 해제와 획득 사이에만 순서를 만든다. 서로 다른 두 락으로는 생산자와 소비자를 이을 수 없다. 생산자가 signalNotEmpty()에서 takeLock을 잠깐 잡기는 하지만, 그 일은 큐가 비어 있다가 원소가 생긴 경우에만 일어난다. 소스 주석은 늘 존재하는 다리가 무엇인지 직접 밝힌다. 원소를 넣을 때는 putLock을 잡고 count를 갱신하며, 읽는 쪽은 takeLock을 잡은 뒤 n = count.get()을 읽어 "처음 n개 원소에 대한 가시성"을 얻는다는 것이다.

    // JDK 21 LinkedBlockingQueue (발췌)
// 제출 스레드: offer
putLock.lock();
try {
    // ...
    enqueue(node);                  // last.next = node (일반 쓰기)
    c = count.getAndIncrement();    // AtomicInteger: volatile 쓰기 의미
    // ...
} finally {
    putLock.unlock();
}

// 워커 스레드: take
takeLock.lockInterruptibly();
try {
    while (count.get() == 0) {      // AtomicInteger: volatile 읽기 의미
        notEmpty.await();
    }
    x = dequeue();                  // node.item 읽기 (일반 읽기)
    // ...
} finally {
    takeLock.unlock();
}

    count는 AtomicInteger다. API 문서상 getAndIncrement()는 VarHandle.getAndAdd의 메모리 효과, 즉 setVolatile 의미의 쓰기를 갖고, get()은 getVolatile 의미의 읽기다. 내부 필드도 private volatile int value로 선언되어 있다. 여기서 쓰이는 것이 JLS §17.4.4의 "volatile 변수에 대한 쓰기는 이후 그 변수를 읽는 모든 읽기와 동기화된다"는 규칙이다. 워커의 count.get()이 제출 스레드가 증가시킨 값을 읽었다면, 그 증가보다 앞선 enqueue와 다시 그보다 앞서 제출 스레드가 한 모든 일이 워커의 dequeue와 그 뒤의 작업 실행에 보인다. while 조건이 0이 아님을 확인한 뒤에야 dequeue로 넘어가는 순서가 곧 "volatile 읽기 뒤에 일반 읽기"라는 획득 쪽 패턴이다.

    FutureTask 자신도 같은 패턴을 한 겹 더 갖는다. 생성자는 this.callable = callable; 다음 줄에서 volatile 필드에 this.state = NEW;를 쓰고, 그 줄의 주석은 "ensure visibility of callable"이다. 그리고 run()은 state를 먼저 읽은 뒤에 callable을 읽는다. 앞 절의 outcome과 똑같이, 일반 필드 쓰기 뒤에 volatile 쓰기를 두고 읽는 쪽은 volatile 읽기 뒤에 일반 필드를 읽는 배치다.

    이 사슬은 표준 구현이 만들어 준 것이지 "다른 스레드에 객체를 넘겼으니 당연히 보인다"는 성질이 아니다. Executor를 직접 구현하면서 작업을 동기화되지 않은 ArrayList 같은 자료구조에 넣고 다른 스레드가 꺼내 가게 하면, 넣는 쪽의 쓰기와 꺼내는 쪽의 읽기를 잇는 happens-before가 없다. JLS §17.4.5의 정의로는 데이터 경쟁(data race)이다. 또 이 보장은 제출 전의 쓰기에만 해당한다. 제출한 뒤 제출 스레드가 바꾼 값이 작업에 보인다는 보장은 위의 어느 규칙에서도 나오지 않는다.

    Future 활용과 Future가 필요한 이유

    이제 Future로 실제 이득을 얻어 보자. 1부터 100까지의 합을 두 구간으로 나눠 두 스레드에 맡긴다. 각 구간 계산이 2초씩 걸리는 무거운 일이라고 가정하고 sleep을 넣었다. 같은 일을 두 가지 방식으로 시켜 실행 시간을 비교한다.

    import java.util.concurrent.*;

public class SumTask {
    record RangeSum(int from, int to) implements Callable {
        @Override
        public Long call() throws InterruptedException {
            Thread.sleep(2000); // 오래 걸리는 계산이라고 가정
            long sum = 0;
            for (int i = from; i <= to; i++) sum += i;
            return sum;
        }
    }

    public static void main(String[] args) throws Exception {
        try (ExecutorService es = Executors.newFixedThreadPool(2)) {
            long start = System.nanoTime();
            Future f1 = es.submit(new RangeSum(1, 50));
            Future f2 = es.submit(new RangeSum(51, 100));
            long total = f1.get() + f2.get();
            long ms = (System.nanoTime() - start) / 1_000_000;
            System.out.println("올바른 사용: total=" + total + ", 약 " + (ms / 1000) + "초");

            start = System.nanoTime();
            long a = es.submit(new RangeSum(1, 50)).get();
            long b = es.submit(new RangeSum(51, 100)).get();
            ms = (System.nanoTime() - start) / 1_000_000;
            System.out.println("잘못된 사용: total=" + (a + b) + ", 약 " + (ms / 1000) + "초");
        }
    }
}
    올바른 사용: total=5050, 약 2초
잘못된 사용: total=5050, 약 4초

    call()이 throws InterruptedException을 선언하고 있다는 점부터 보자. Callable.call()이 throws Exception을 선언하므로 그 하위 예외를 던지는 것은 합법이다. Runnable이었다면 여기서 try/catch를 써야 했다. 합계는 1~50이 1275, 51~100이 3775로 둘 다 5050이다. 차이는 시간이다.

    올바른 사용에서는 두 작업을 먼저 모두 제출한 뒤 결과를 회수한다. submit은 즉시 돌아오므로 두 작업은 거의 같은 순간에 두 워커에서 동시에 시작된다. f1.get()에서 main이 2초쯤 기다리는 동안 f2도 함께 계산되고 있으므로, f1.get()이 돌아왔을 때 f2도 이미 끝났거나 거의 끝나 있다. 전체 시간은 두 작업 중 긴 쪽의 시간이다.

    잘못된 사용은 submit(...).get()을 한 줄에 붙여 썼다. 첫 작업을 제출하자마자 그 결과를 기다리므로, 두 번째 작업은 첫 작업이 끝난 뒤에야 제출된다. 스레드 풀과 두 개의 워커를 갖추고도 일은 한 번에 하나씩 진행되었고, 전체 시간은 두 작업 시간의 합이 되었다. 결과는 같고 코드는 더 짧아 보여서 이 실수는 리뷰에서도 놓치기 쉽다.

    올바른 사용 (제출 → 제출 → 회수 → 회수)
 thread-1 |■■■■■■■■ f1 (2초) ■■■■■■■■|
 thread-2 |■■■■■■■■ f2 (2초) ■■■■■■■■|
 main     |submit submit  get(f1)··········· get(f2)즉시|   → 약 2초

잘못된 사용 (제출 → 회수 → 제출 → 회수)
 thread-1 |■■■■■■■■ a (2초) ■■■■■■■■|
 thread-2 |                            |■■■■■■■■ b (2초) ■■■■■■■■|
 main     |submit get(a)···············submit get(b)···············|   → 약 4초

    이것이 Future가 존재하는 이유다. 만약 submit이 결과가 나올 때까지 막혀 있다가 값을 바로 돌려주는 API였다면, 모든 사용 방식이 위의 "잘못된 사용"과 같아졌을 것이다. 제출과 회수를 분리했기 때문에 "여러 작업을 먼저 다 맡겨 놓고 나중에 한꺼번에 기다리는" 사용법이 가능해진다. 거꾸로 말하면, Future의 이득을 얻으려면 get()을 가능한 한 늦게 부르는 것이 원칙이다. 제출할 수 있는 작업은 모두 먼저 제출하고, 결과가 정말 필요해지는 지점에서 get()을 부른다.

    회수 순서도 생각해 보자. 위 코드는 f1.get()을 먼저 부르는데, 만약 f2가 먼저 끝난다면 어떨까? 문제없다. f2의 결과는 FutureTask 안에 저장되어 기다리고 있다가, 나중에 f2.get()을 부르면 기다림 없이 즉시 반환된다(get()은 상태가 이미 최종 상태이면 awaitDone을 건너뛴다). 전체 시간은 어느 쪽을 먼저 회수하든 가장 오래 걸린 작업이 결정한다. 다만 "먼저 끝난 결과부터 처리하고 싶다"면 제출 순서대로 get()을 부르는 방식으로는 안 되고, 앞에서 언급한 ExecutorCompletionService처럼 완료 순서대로 결과를 꺼내 주는 도구가 필요하다.

    Future 정리: 메서드와 상태의 대응

    Future 인터페이스의 메서드를 FutureTask의 내부 상태와 짝지어 정리해 두자. Java 19에서 resultNow(), exceptionNow(), state()가 기본 메서드로 추가되었고, FutureTask는 이들을 내부 상태에 맞게 직접 구현한다.

    NEW에서 출발하는 네 갈래의 전이와, 각 최종 상태에서 get()이 무엇을 하는지 보여 준다. 상태 전이도. 왼쪽 가운데에 큰 원 "NEW". 오른쪽으로 네 갈래 화살표가 뻗는다. 위의 두 갈래는 작은 원 "COMPLETING"을 거쳐 각각 "NORMAL"과 "EXCEPTIONAL"로 간다. 화살표 라벨은 각각 "set(결과)"와 "setException(예외)". 세 번째 갈래는 곧장 "CANCELLED"로 가며 라벨은 "cancel(false)". 네 번째 갈래는 작은 원 "INTERRUPTING"을 거쳐 "INTERRUPTED"로 가며 라벨은 "cancel(true)". 최종 상태 원 네 개는 두꺼운 테두리로 그린다. 각 최종 상태 오른쪽에 회색 글씨로 get()의 결과를 적는다: NORMAL 옆 "값 반환", EXCEPTIONAL 옆 "ExecutionException", CANCELLED와 INTERRUPTED 옆 "CancellationException". 흰 배경, 깔끔한 선. 모든 전이는 NEW에서 CAS로 시작하므로, 완료·예외·취소 가운데 먼저 성공한 하나만 결과를 확정한다.

    get()이 기다리는 방법: awaitDone 루프와 대기 노드

    위의 표에서 get()은 "기다린다", get(timeout)은 "정해진 시간만 기다린다"고만 적었다. 기다리는 동안 무슨 일이 일어나는지, 시간 초과나 인터럽트로 기다림을 그만둔 스레드가 어떻게 빠져나오는지는 FutureTask.awaitDone 한 메서드에 모두 들어 있다. 먼저 get 자체를 보자.

    // JDK 21 FutureTask.get
public V get() throws InterruptedException, ExecutionException {
    int s = state;
    if (s <= COMPLETING)
        s = awaitDone(false, 0L);
    return report(s);
}

public V get(long timeout, TimeUnit unit)
    throws InterruptedException, ExecutionException, TimeoutException {
    if (unit == null)
        throw new NullPointerException();
    int s = state;
    if (s <= COMPLETING &&
        (s = awaitDone(true, unit.toNanos(timeout))) <= COMPLETING)
        throw new TimeoutException();
    return report(s);
}

    상태가 이미 최종 상태(COMPLETING보다 큰 값)이면 awaitDone을 부르지 않고 바로 report로 간다. 끝난 작업에 대한 get()은 대기 노드를 만들지도, 스레드를 재우지도 않는다. get(timeout)은 awaitDone이 돌려준 상태가 여전히 COMPLETING 이하일 때만 TimeoutException을 던진다. 기다려야 할 때 들어가는 awaitDone은 한 바퀴에 한 가지 일만 하는 루프다.

    // JDK 21 FutureTask.awaitDone (원본 주석 일부 생략)
private int awaitDone(boolean timed, long nanos) throws InterruptedException {
    long startTime = 0L;    // 0L은 아직 park한 적 없음을 뜻한다
    WaitNode q = null;
    boolean queued = false;
    for (;;) {
        int s = state;
        if (s > COMPLETING) {                 // (1) 끝났다
            if (q != null)
                q.thread = null;
            return s;
        }
        else if (s == COMPLETING)             // (2) 결과 기록 중
            Thread.yield();
        else if (Thread.interrupted()) {      // (3) 인터럽트
            removeWaiter(q);
            throw new InterruptedException();
        }
        else if (q == null) {                 // (4) 노드 만들기
            if (timed && nanos <= 0L)
                return s;
            q = new WaitNode();
        }
        else if (!queued)                     // (5) 스택에 push
            queued = WAITERS.weakCompareAndSet(this, q.next = waiters, q);
        else if (timed) {                     // (6a) 시간 제한 대기
            final long parkNanos;
            if (startTime == 0L) {
                startTime = System.nanoTime();
                if (startTime == 0L)
                    startTime = 1L;
                parkNanos = nanos;
            } else {
                long elapsed = System.nanoTime() - startTime;
                if (elapsed >= nanos) {
                    removeWaiter(q);
                    return state;
                }
                parkNanos = nanos - elapsed;
            }
            if (state < COMPLETING)
                LockSupport.parkNanos(this, parkNanos);
        }
        else                                  // (6b) 무기한 대기
            LockSupport.park(this);
    }
}

    매 바퀴는 state를 새로 읽는 데서 시작하고, 조건을 검사하는 순서가 곧 우선순위다.

    1. 최종 상태면 돌아간다. 자기 노드가 있으면 thread를 비워 더 이상 깨울 필요가 없는 노드로 표시한다.
    2. COMPLETING이면 Thread.yield()로 양보만 한다. 워커가 NEW → COMPLETING CAS에 성공한 뒤 outcome을 쓰고 최종 상태를 기록하기까지의 짧은 틈이다. 원본 주석은 이 상태의 작업에 대해 이미 isDone()으로 "끝났다"고 약속했을 수 있으므로 빈손으로 돌아가거나 InterruptedException을 던지지 않는다고 설명한다. 그래서 이 검사가 인터럽트 검사보다 앞에 있다.
    3. 인터럽트를 받았으면 노드를 치우고 InterruptedException을 던진다. Thread.interrupted()는 플래그를 확인하면서 지우므로, 4회에서 본 "예외로 알렸으면 플래그는 지운다"는 관례와 맞는다.
    4. 노드가 없으면 만든다. 단, 시간 제한이 0 이하이면 노드조차 만들지 않고 지금 상태를 그대로 돌려준다. 원본 주석이 밝힌 목표 가운데 하나가 "nanos가 0 이하이면 할당이나 nanoTime 호출 없이 즉시 돌아간다"이다.
    5. 스택에 아직 오르지 않았으면 CAS로 올린다. q.next = waiters로 현재 맨 위 노드를 가리키게 한 뒤, 맨 위를 자기 노드로 바꾼다. 트라이버 스택의 push다. 10회에서 본 약한 CAS라 가짜로 실패할 수 있지만, 실패하면 다음 바퀴에서 다시 시도한다. 그 사이 작업이 끝났다면 (1)에서 걸러진다.
    6. 잠든다. 시간 제한이 있으면 남은 시간만큼 parkNanos, 없으면 park다. 깨어나면 다시 (1)부터 검사한다. 7회에서 보았듯 park는 이유 없이 돌아올 수도 있으므로, 깨어난 이유를 따지지 않고 state를 다시 읽는 이 루프 구조가 꼭 필요하다. 시간 제한이 있는 경우 경과 시간이 다 차면 노드를 치우고 그 순간의 상태를 돌려준다. nanoTime 호출이 느릴 수 있어서 잠들기 직전에 state를 한 번 더 확인한다는 주석도 붙어 있다.

    두 가지를 눈여겨보자. 첫째, park(this)와 parkNanos(this, ...)에 넘기는 this는 블로커(blocker) 객체다. 이 객체는 스레드가 무엇을 기다리는지 기록하는 용도이고, LockSupport.getBlocker(thread)나 스레드 덤프로 확인할 수 있다. 둘째, 시간 초과와 인터럽트는 둘 다 removeWaiter를 부를 뿐 state에는 손대지 않는다. 기다림을 그만두는 것은 기다리던 스레드 자신의 일이고 작업의 결말과는 무관하다는 사실이 코드 구조에 그대로 드러난다.

    removeWaiter는 노드의 thread를 먼저 null로 만든 뒤, 스택을 맨 위부터 훑으며 thread가 빈 노드를 연결에서 뺀다. 원본 주석에 따르면 목적은 시간 초과나 인터럽트로 버려진 노드가 쓰레기로 쌓이지 않게 하는 것이다. 같은 Future에 get(timeout)을 반복해서 거는 코드가 있어도 시간 초과된 노드가 스택에 남아 늘어나지 않는다. 중간 노드는 CAS 없이 앞 노드의 next만 바꿔 빼는데, 주석은 깨우는 쪽이 이미 빠진 노드를 따라가더라도 해가 없기 때문이라고 설명한다. 실제로 finishCompletion은 thread가 null인 노드를 unpark하지 않고 지나간다. 맨 위 노드를 뺄 때만 CAS를 쓰고, 다른 스레드와 경쟁한 흔적이 보이면 처음부터 다시 훑는다.

    이 동작을 관찰해 보자. 1.5초 걸리는 작업 하나에 세 스레드가 동시에 get을 건다. A는 제한 없이, B는 300밀리초 제한으로, C는 제한 없이 기다리다가 도중에 인터럽트를 받는다. 대기 노드 수는 FutureTask의 private 필드 waiters에서 시작해 next를 따라가며 리플렉션으로 세었다. 관찰만을 위한 코드여서 실행할 때 --add-opens java.base/java.util.concurrent=ALL-UNNAMED 옵션이 필요하다.

    import java.lang.reflect.Field;
import java.util.concurrent.*;
import java.util.concurrent.locks.LockSupport;

public class Waiters {
    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }

    // FutureTask의 private 필드 waiters를 따라가며 대기 노드 수를 센다 (관찰용)
    static int countWaiters(Future f) throws Exception {
        Field w = FutureTask.class.getDeclaredField("waiters");
        w.setAccessible(true);
        Object node = w.get(f);
        int n = 0;
        while (node != null) {
            Field next = node.getClass().getDeclaredField("next");
            next.setAccessible(true);
            n++;
            node = next.get(node);
        }
        return n;
    }

    public static void main(String[] args) throws Exception {
        ExecutorService es = Executors.newFixedThreadPool(1);
        Future f = es.submit(() -> { Thread.sleep(1500); return "결과"; });

        Thread a = new Thread(() -> {
            try { log("get() → " + f.get()); }
            catch (Exception e) { log("get() → " + e); }
        }, "getter-A");
        Thread b = new Thread(() -> {
            try { f.get(300, TimeUnit.MILLISECONDS); }
            catch (TimeoutException e) { log("get(300ms) → TimeoutException, state=" + f.state()); }
            catch (Exception e) { log("get(300ms) → " + e); }
        }, "getter-B");
        Thread c = new Thread(() -> {
            try { f.get(); }
            catch (InterruptedException e) { log("get() → InterruptedException, state=" + f.state()); }
            catch (Exception e) { log("get() → " + e); }
        }, "getter-C");
        a.start(); b.start(); c.start();

        Thread.sleep(100);
        log("대기 노드 수=" + countWaiters(f)
                + ", A의 blocker=" + LockSupport.getBlocker(a).getClass().getSimpleName()
                + ", A 상태=" + a.getState() + ", B 상태=" + b.getState());

        Thread.sleep(400);   // B의 300ms 제한이 지난 뒤
        log("B 시간 초과 뒤 대기 노드 수=" + countWaiters(f));

        c.interrupt();
        c.join();
        log("C 인터럽트 뒤 대기 노드 수=" + countWaiters(f));

        a.join();
        log("완료 뒤 대기 노드 수=" + countWaiters(f) + ", state=" + f.state());
        es.close();
    }
}

    • 첫 줄. 세 스레드가 모두 스택에 올라 노드가 3개다. A의 블로커는 FutureTask 객체 자신이다. 제한 없이 park한 A는 WAITING, parkNanos로 잠든 B는 TIMED_WAITING이다.
    • B의 시간 초과. B는 TimeoutException을 받았지만 작업의 state()는 여전히 RUNNING이다. 루프의 (6a)가 removeWaiter로 B의 노드를 빼서 노드가 2개로 줄었다.
    • C의 인터럽트. interrupt()가 C를 park에서 깨웠고, 다음 바퀴의 (3)이 노드를 빼고 InterruptedException을 던졌다. 작업은 역시 RUNNING이다.
    • 작업 완료. 워커의 set이 부른 finishCompletion이 스택을 통째로 떼어 내고 남은 노드(A)를 unpark했다. 노드는 0개, 상태는 SUCCESS다.

    각 관찰 시점 사이에 수백 밀리초의 여유를 두었기 때문에 출력이 실행마다 같게 나왔다. 앞에서 말한 "get(timeout)의 시간 초과는 작업을 취소하지 않는다"는 사실이 여기서 내부 구조로 설명된다. 시간 초과는 기다리던 노드 하나를 스택에서 빼는 일일 뿐, 작업의 상태 기계에는 아무 흔적도 남기지 않는다. 인터럽트도 마찬가지다. 인터럽트를 받은 것은 get()을 부른 스레드이지 작업을 실행하는 워커가 아니다.

    Future 취소: cancel(true)와 cancel(false)

    작업을 맡겼는데 더 이상 결과가 필요 없어지는 경우가 있다. 사용자가 요청을 취소했거나, 다른 경로로 답을 이미 얻었거나, 시간 제한을 넘겼을 때다. cancel(boolean mayInterruptIfRunning)은 이럴 때 쓴다. 인자의 차이를 실행으로 확인하자. 0.4초마다 진행 상황을 찍으며 다섯 단계를 도는 작업을 1초 뒤에 취소한다.

    import java.util.concurrent.*;

public class CancelDemo {
    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }

    static Callable slowTask() {
        return () -> {
            for (int i = 1; i <= 5; i++) {
                log("작업 중 " + i);
                try {
                    Thread.sleep(400);
                } catch (InterruptedException e) {
                    log("인터럽트 받음 → 작업 중단");
                    return "중단됨";
                }
            }
            log("작업 끝까지 수행");
            return "완료";
        };
    }

    static void run(boolean mayInterrupt) throws Exception {
        log("===== cancel(" + mayInterrupt + ") =====");
        ExecutorService es = Executors.newFixedThreadPool(1);
        Future f = es.submit(slowTask());
        Thread.sleep(1000);
        boolean ok = f.cancel(mayInterrupt);
        log("cancel 반환=" + ok + ", isCancelled=" + f.isCancelled()
                + ", isDone=" + f.isDone() + ", state=" + f.state());
        try {
            f.get();
        } catch (CancellationException e) {
            log("get() → " + e.getClass().getSimpleName());
        }
        log("다시 cancel=" + f.cancel(mayInterrupt));
        es.close();
    }

    public static void main(String[] args) throws Exception {
        run(true);
        run(false);
    }
}

    cancel(true)에서는 소스의 이 경로를 탄다. state를 CAS로 NEW → INTERRUPTING으로 바꾸고, runner 필드에 기록된 워커 스레드에 interrupt()를 건 뒤, state를 INTERRUPTED로 확정하고 finishCompletion()으로 기다리는 스레드를 깨운다. 워커 스레드는 Thread.sleep(400) 안에서 자고 있었으므로 4회에서 본 대로 InterruptedException을 받고 깨어나 작업을 그만두었다. 작업은 "중단됨"을 반환했지만 이 값은 아무도 받지 못한다. set("중단됨")이 NEW → COMPLETING CAS를 시도하지만 상태가 이미 INTERRUPTED여서 실패하기 때문이다. get()은 report에서 CANCELLED 이상의 상태를 보고 CancellationException을 던진다.

    cancel(false)는 상태를 NEW → CANCELLED로 바꾸고 기다리는 스레드를 깨울 뿐, 워커에 인터럽트를 걸지 않는다. Future쪽에서 보면 결과는 똑같다. 즉시 취소된 것으로 보고되고 get()은 CancellationException을 던진다. 그러나 워커 스레드는 아무것도 모른 채 작업을 끝까지 수행했고(작업 중 4, 5, 끝까지 수행), 마지막 set("완료")는 CAS에 실패해 버려졌다. 그동안 그 워커 스레드는 다른 작업을 하지 못하고 묶여 있었다. 출력의 마지막 세 줄이 main의 줄들보다 뒤에 나오는 것도, es.close()가 이 작업이 끝날 때까지 기다렸기 때문이다.

    두 경우 모두 두 번째 cancel은 false를 반환했다. cancel의 첫 줄이 "상태가 NEW이고 CAS에 성공했는가"를 확인하기 때문이다. 이미 정상 완료된 작업, 예외로 끝난 작업, 이미 취소된 작업은 모두 NEW가 아니므로 취소할 수 없다.

    아직 시작하지 않은 작업의 취소

    큐에서 차례를 기다리던 작업을 취소하면 어떻게 될까? 상태는 즉시 CANCELLED가 되지만, 그 FutureTask 객체는 큐에서 빠지지 않는다. 나중에 워커가 큐에서 그 객체를 꺼내 run()을 부르면, run()의 첫 줄 if (state != NEW ...) return;에 걸려 아무 일도 하지 않고 돌아온다. 작업은 실행되지 않지만, 꺼낼 때까지 큐의 자리를 차지한다. 취소된 작업이 큐에 많이 쌓였다면 ThreadPoolExecutor.purge()로 큐에서 취소된 Future를 지울 수 있다.

    취소는 협조적이다

    cancel(true)가 하는 일은 결국 Thread.interrupt() 한 번이다. 4회에서 보았듯 인터럽트는 스레드를 강제로 멈추지 않는다. sleep, wait, join, BlockingQueue.take처럼 인터럽트에 반응하는 블로킹 메서드 안에 있으면 InterruptedException으로 깨어나고, 그렇지 않으면 인터럽트 플래그만 켜진다. 따라서 CPU만 쓰는 계산 루프가 Thread.currentThread().isInterrupted()를 확인하지 않는다면, cancel(true)를 불러도 작업은 끝까지 돈다. Future는 즉시 취소된 것으로 보고되므로 겉으로는 성공한 것처럼 보이지만 스레드는 여전히 묶여 있다. 오래 걸리는 작업을 취소 가능하게 만들려면 작업 쪽에서 주기적으로 인터럽트 상태를 확인하도록 써야 한다. 또 InterruptedException을 잡아 아무 일 없다는 듯 삼켜 버리는 작업은 취소 요청을 무시하는 셈이 된다.

    인터럽트가 다음 작업으로 새는 문제도 표준 구현이 막아 준다. 앞에서 본 runWorker는 풀이 멈추는 중이 아니면 다음 작업을 실행하기 전에 Thread.interrupted()로 플래그를 지운다. 그리고 FutureTask.run()의 마지막 부분은 상태가 INTERRUPTING이면 취소한 스레드가 interrupt()를 마칠 때까지 Thread.yield()로 기다린다. 취소한 쪽의 인터럽트가 작업이 끝난 뒤 늦게 도착해 다음 작업을 방해하는 일을 막기 위한 순서 맞춤이다.

    Future와 예외

    Callable이 예외를 던지면 그 예외는 어디로 갈까? 그리고 submit과 execute로 넘긴 작업은 예외를 똑같이 다룰까? 세 가지 경우를 한 번에 실행해 보자.

    import java.util.concurrent.*;

public class ExceptionDemo {
    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }

    public static void main(String[] args) throws Exception {
        ExecutorService es = Executors.newFixedThreadPool(1);

        // (1) Callable이 던진 예외
        Future f = es.submit(() -> {
            log("Callable 실행");
            throw new IllegalStateException("잘못된 상태");
        });
        try {
            f.get();
        } catch (ExecutionException e) {
            log("get() → " + e);
            log("cause → " + e.getCause());
        }
        log("state=" + f.state() + ", isDone=" + f.isDone()
                + ", exceptionNow=" + f.exceptionNow().getMessage());

        // (2) submit으로 넘긴 Runnable이 던진 예외
        Runnable boom = () -> { throw new RuntimeException("submit 예외"); };
        es.submit(boom);
        Thread.sleep(200);
        log("submit 예외는 어디에도 출력되지 않았다");

        // (3) execute로 넘긴 Runnable이 던진 예외
        es.execute(() -> { throw new RuntimeException("execute 예외"); });
        Thread.sleep(200);
        es.execute(() -> log("다음 작업"));
        Thread.sleep(200);
        es.close();
    }
}

    (1) Callable의 예외는 ExecutionException에 감싸여 get()을 부른 스레드로 전달된다. 워커 스레드에서 던져진 IllegalStateException은 FutureTask.run()의 catch (Throwable ex)에 잡혀 setException으로 outcome에 저장되고, 상태는 EXCEPTIONAL이 되었다. main이 get()을 부르자 report가 new ExecutionException(outcome)을 만들어 던졌다. 원래 예외는 getCause()로 꺼낸다. 예외가 스레드의 경계를 넘을 수 있는 이유는 예외 객체가 힙에 있는 평범한 객체이고, FutureTask가 그 참조를 보관했다가 다른 스레드에 넘겨주기 때문이다. 이렇게 감싸는 데는 이유가 있다. ExecutionException 자체의 스택 트레이스는 get()을 부른 스레드에서 만들어지고, 원인 예외의 스택 트레이스는 작업을 실행한 워커 스레드의 것이다. 두 스레드의 문맥이 한 예외 안에 함께 남는다. 또 get()의 시그니처에 ExecutionException 하나만 선언하면 작업이 어떤 예외를 던지든 받아낼 수 있다.

    (2) submit으로 넘긴 작업의 예외는 조용히 사라질 수 있다. submit(Runnable)도 결국 FutureTask로 감싸져 실행되므로, 예외는 똑같이 outcome에 저장된다. 워커 스레드 입장에서 FutureTask.run()은 정상적으로 돌아왔기 때문에 아무것도 출력되지 않는다. 누군가 그 Future의 get()을 불러야 비로소 예외가 드러나는데, 위 코드처럼 반환된 Future를 버렸다면 예외는 영원히 묻힌다. 실무에서 "작업이 실패했는데 로그가 하나도 없다"는 장애의 흔한 원인이다.

    (3) execute로 넘긴 작업의 예외는 워커 스레드를 죽인다. execute는 작업을 FutureTask로 감싸지 않고 그대로 runWorker에서 실행한다. 예외는 runWorker의 afterExecute(task, ex)를 거쳐 throw ex로 다시 던져지고, 루프를 빠져나가 스레드의 run()까지 전파된다. 처리되지 않은 예외로 스레드가 끝나면 기본 처리기가 표준 오류에 Exception in thread "pool-1-thread-1" ...를 찍는다. 스택 트레이스의 runWorker와 Worker.run 프레임이 앞에서 본 소스 그대로다. 그다음 processWorkerExit는 completedAbruptly가 true이므로 대체 워커를 새로 만든다. "다음 작업"을 실행한 스레드 이름이 pool-1-thread-2로 바뀐 것이 그 증거다. 풀 크기는 유지되지만, 스레드가 죽고 새로 만들어지는 비용이 예외마다 든다.

    정리하면, submit을 썼다면 반환된 Future의 get()을 반드시 호출해 실패를 확인하거나, 작업 안에서 예외를 직접 잡아 기록해야 한다. ThreadPoolExecutor를 상속해 afterExecute를 오버라이드하는 방법도 있지만, API 문서가 주의를 준다. submit처럼 작업이 FutureTask로 감싸진 경우에는 그 안에서 예외가 이미 잡혔기 때문에 afterExecute의 Throwable 인자로 넘어오지 않는다. 문서의 예시 코드는 그래서 인자가 null이면 작업이 Future인지 확인해 get()으로 예외를 다시 꺼낸다.

    ExecutorService로 작업 컬렉션 처리하기: invokeAll과 invokeAny

    작업 여러 개를 한꺼번에 맡기는 일은 흔하다. 앞의 합계 예제처럼 submit을 여러 번 부르고 Future를 모아 하나씩 get()해도 되지만, ExecutorService는 이 패턴을 메서드로 제공한다.

    • List> invokeAll(Collection> tasks): 모든 작업을 실행하고, 모두 끝날 때까지 기다린 뒤 Future 목록을 반환한다. 시간 제한을 받는 오버로드도 있다.
    • T invokeAny(Collection> tasks): 작업들을 실행하고, 가장 먼저 성공적으로 끝난 작업의 결과 하나를 반환한다. 나머지는 취소한다. 역시 시간 제한 오버로드가 있다.

    3초, 1초, 2초가 걸리는 작업 세 개를 스레드 세 개짜리 풀에 두 메서드로 각각 맡겨 보자.

    import java.util.*;
import java.util.concurrent.*;

public class InvokeDemo {
    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }

    static Callable task(int seconds) {
        return () -> {
            try {
                Thread.sleep(seconds * 1000L);
            } catch (InterruptedException e) {
                log(seconds + "초 작업 인터럽트로 취소");
                throw e;
            }
            log(seconds + "초 작업 완료");
            return seconds;
        };
    }

    public static void main(String[] args) throws Exception {
        try (ExecutorService es = Executors.newFixedThreadPool(3)) {
            List> tasks = List.of(task(3), task(1), task(2));

            long start = System.nanoTime();
            List> futures = es.invokeAll(tasks);
            log("invokeAll 반환, 약 " + (System.nanoTime() - start) / 1_000_000_000 + "초");
            for (Future f : futures) {
                log("결과=" + f.resultNow());
            }

            start = System.nanoTime();
            Integer first = es.invokeAny(tasks);
            log("invokeAny 반환=" + first + ", 약 " + (System.nanoTime() - start) / 1_000_000_000 + "초");
            Thread.sleep(100);
        }
    }
}

    // JDK 21 AbstractExecutorService.invokeAll (시간 제한 없는 버전)
ArrayList> futures = new ArrayList<>(tasks.size());
try {
    for (Callable t : tasks) {
        RunnableFuture f = newTaskFor(t);
        futures.add(f);
        execute(f);
    }
    for (int i = 0, size = futures.size(); i < size; i++) {
        Future f = futures.get(i);
        if (!f.isDone()) {
            try { f.get(); }
            catch (CancellationException | ExecutionException ignore) {}
        }
    }
    return futures;
} catch (Throwable t) {
    cancelAll(futures);
    throw t;
}

    앞에서 배운 원칙, "먼저 모두 제출하고 나중에 회수한다"를 그대로 구현했다. 첫 번째 루프에서 모든 작업을 FutureTask로 감싸 execute하고, 두 번째 루프에서 순서대로 get()한다. 작업이 던진 예외(ExecutionException)와 취소(CancellationException)는 무시하고 넘어간다. 즉 작업 하나가 실패해도 invokeAll 자체는 예외를 던지지 않는다. 실패는 반환된 목록의 해당 Future에 담겨 있으므로, 결과를 꺼낼 때 각각 get()으로 확인해야 한다. 반면 invokeAll을 부른 스레드가 기다리다 인터럽트를 받는 등 다른 예외가 생기면 cancelAll로 모든 작업을 cancel(true)한 뒤 예외를 던진다. 시간 제한이 있는 invokeAll(tasks, timeout, unit)은 시간이 다 되면 아직 끝나지 않은 작업을 모두 취소하고 목록을 반환한다.

    invokeAny는 1초 작업의 결과인 1을 약 1초 만에 반환했고, 남은 2초·3초 작업은 인터럽트를 받아 취소되었다. 구현은 조금 더 복잡하다. 내부에서 ExecutorCompletionService를 만들어, 끝난 작업이 완료 순서대로 나오는 큐를 이용한다. 소스 주석대로 "하나는 확실히 시작하고, 나머지는 점진적으로" 제출하는데, 다음 작업을 제출하기 전에 이미 끝난 작업이 있는지 먼저 확인한다. 끝난 작업이 나오면 get()으로 결과를 꺼내 바로 반환하고, 그 작업이 예외로 끝났다면 그 예외를 기억해 두고 다음 완료를 기다린다. 모든 작업이 실패하면 마지막으로 받은 ExecutionException을 던진다. 그리고 어떤 경로로 끝나든 finally에서 cancelAll(futures)를 불러 남은 작업을 모두 cancel(true)한다. 실행 결과의 "인터럽트로 취소" 두 줄이 그 결과다.

    invokeAny가 돌려주는 것은 "가장 먼저 끝난" 작업이 아니라 "가장 먼저 성공한" 작업의 결과라는 점에 주의하자. 1초 만에 예외로 끝난 작업이 있어도 그 예외는 기록만 되고, 2초 뒤에 성공한 작업의 결과가 반환된다. 여러 서버에 같은 요청을 보내 가장 빨리 온 정상 응답 하나만 쓰는 상황에 맞는 의미다. 또 남은 작업의 취소가 인터럽트로 이루어지므로, 인터럽트에 반응하지 않는 작업은 invokeAny가 반환된 뒤에도 계속 실행되며 풀의 스레드를 붙잡는다.

    같은 세 작업(3초, 1초, 2초)을 invokeAll과 invokeAny로 실행했을 때 반환 시점과 남은 작업의 운명을 비교한다. 위아래 두 개의 타임라인 패널. 가로축은 시간 0초부터 3초까지 눈금 "0초", "1초", "2초", "3초". 위 패널 제목 "invokeAll": 세 줄의 가로 막대 "3초 작업"(0~3초), "1초 작업"(0~1초), "2초 작업"(0~2초)이 모두 초록색으로 끝까지 칠해져 있고, 3초 지점에 세로 점선과 "모두 끝난 뒤 반환"이라는 라벨. 아래 패널 제목 "invokeAny": "1초 작업" 막대는 0~1초 초록색, "3초 작업"과 "2초 작업" 막대는 0~1초까지만 칠해지고 1초 지점에서 빨간 X 표시와 "cancel(true)" 라벨. 1초 지점에 세로 점선과 "첫 성공 결과 반환" 라벨. 흰 배경, 단순한 막대 그래프 스타일. invokeAll은 가장 긴 작업이 끝날 때 모든 Future를 입력 순서대로 돌려주고, invokeAny는 첫 성공 결과를 돌려주며 나머지를 인터럽트로 취소한다.

    완료 순서대로 받기: ExecutorCompletionService와 done() 훅

    앞에서 invokeAny가 내부에서 ExecutorCompletionService를 쓴다고 했고, 그보다 앞에서는 먼저 끝난 결과부터 처리하고 싶다면 이 도구가 필요하다고 했다. Future 목록을 제출 순서대로 get()하면, 첫 작업이 가장 느릴 때 이미 끝난 나머지 결과도 그 뒤에 묶인다. API 문서는 ExecutorCompletionService를 제출된 작업이 끝나면 take로 꺼낼 수 있는 큐에 놓이도록 배치하는 CompletionService라고 설명한다. 그 "끝나면 큐에 놓는" 장치가 앞에서 본 FutureTask의 done() 훅이다.

    // JDK 21 java.util.concurrent.ExecutorCompletionService (발췌)
private static class QueueingFuture extends FutureTask {
    QueueingFuture(RunnableFuture task,
                   BlockingQueue> completionQueue) {
        super(task, null);
        this.task = task;
        this.completionQueue = completionQueue;
    }
    private final Future task;
    private final BlockingQueue> completionQueue;
    protected void done() { completionQueue.add(task); }
}

public ExecutorCompletionService(Executor executor) {
    // ...
    this.aes = (executor instanceof AbstractExecutorService) ?
        (AbstractExecutorService) executor : null;
    this.completionQueue = new LinkedBlockingQueue>();
}

public Future submit(Callable task) {
    if (task == null) throw new NullPointerException();
    RunnableFuture f = newTaskFor(task);   // aes가 있으면 aes.newTaskFor(task)
    executor.execute(new QueueingFuture(f, completionQueue));
    return f;
}

public Future take() throws InterruptedException {
    return completionQueue.take();
}

    구조가 두 겹이다. submit은 작업을 안쪽 RunnableFuture로 감싸고, 그것을 다시 바깥쪽 QueueingFuture로 감싸 실행기에 넘긴다. 안쪽 객체는 실행기가 AbstractExecutorService이면 그 실행기의 newTaskFor로 만들어지므로, ExecutorCompletionService가 고른 클래스가 아닐 수 있다. 완료를 알아채는 것은 안쪽이 아니라 바깥 한 겹의 done()이다. 바깥쪽은 FutureTask의 (Runnable, V) 생성자를 쓰므로, 앞에서 본 RunnableAdapter를 통해 "안쪽의 run()을 호출하고 null을 반환하는" 작업이 된다. 워커가 바깥쪽을 실행하면 안쪽 run()이 돌아 안쪽의 결과나 예외가 확정되고, 이어서 바깥쪽이 null로 완료되며 finishCompletion → done()이 불린다. 이때 완료 큐에 들어가는 것은 바깥쪽이 아니라 안쪽 Future이고, submit이 호출한 쪽에 돌려준 것도 안쪽(return f)이다. 완료 큐는 기본으로 LinkedBlockingQueue이고, take()는 이 큐의 take()를 그대로 부른다.

    done()은 어느 스레드에서 불리는가

    done()을 부르는 finishCompletion은 최종 상태를 확정한 쪽이 호출한다. 앞에서 본 소스대로 정상 완료와 예외는 워커가 set·setException에서, 취소는 cancel을 부른 스레드가 직접 부른다. 따라서 done()이 실행되는 스레드도 결말에 따라 다르다. FutureTask를 상속해 done()에서 스레드 이름을 찍고, 이어서 완료 순서대로 꺼내는 동작을 확인해 보자.

    import java.util.concurrent.*;

public class Completion {
    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }

    static class LoggingTask extends FutureTask {
        LoggingTask(Callable c) { super(c); }
        @Override protected void done() {
            log("done() 호출, isCancelled=" + isCancelled());
        }
    }

    public static void main(String[] args) throws Exception {
        try (ExecutorService es = Executors.newFixedThreadPool(3)) {
            // (1) done()은 누가 부르는가
            LoggingTask ok = new LoggingTask(() -> "ok");
            es.execute(ok);
            ok.get();
            LoggingTask slow = new LoggingTask(() -> { Thread.sleep(5000); return "slow"; });
            es.execute(slow);
            Thread.sleep(100);
            slow.cancel(true);

            // (2) 완료 순서대로 꺼내기
            CompletionService cs = new ExecutorCompletionService<>(es);
            for (int ms : new int[]{300, 100, 200}) {
                cs.submit(() -> { Thread.sleep(ms); return ms; });
            }
            for (int i = 0; i < 3; i++) {
                log("take() → " + cs.take().get() + "ms 작업");
            }
        }
    }
}
    [pool-1-thread-1] done() 호출, isCancelled=false
[main] done() 호출, isCancelled=true
[main] take() → 100ms 작업
[main] take() → 200ms 작업
[main] take() → 300ms 작업

    정상 완료한 작업의 done()은 워커 스레드(pool-1-thread-1)에서, 취소한 작업의 done()은 cancel(true)를 부른 main에서 실행되었다. done()은 결말을 확정한 스레드가 그 자리에서 이어서 부르는 메서드라는 뜻이다. 정상 완료 쪽에서 보면 done() 안에서 오래 걸리는 일을 하면 그동안 워커가 다음 작업을 꺼내지 못한다. QueueingFuture의 done()은 completionQueue.add(task) 한 줄이고, 실행기만 받는 생성자가 만든 완료 큐는 크기 제한이 없는 LinkedBlockingQueue여서 add가 자리를 기다리며 막히는 일이 없다.

    두 번째 부분에서는 300·100·200밀리초 순서로 제출한 작업이 100·200·300 순서로 꺼내졌다. 워커가 작업을 끝내는 순간 그 워커 스레드에서 done()이 불려 안쪽 Future가 완료 큐에 들어가고, take()에서 잠들어 있던 main이 깨어나 그것을 꺼낸 것이다. 꺼낸 Future는 이미 끝났으므로 get()은 기다리지 않는다. 메모리 가시성도 계약으로 정해져 있다. CompletionService 문서는 작업을 제출하기 전의 동작이 그 작업의 동작보다, 작업의 동작은 대응하는 take()가 성공적으로 돌아온 뒤의 동작보다 먼저 일어난다고 약속한다.

    한 가지 함정이 있다. 큐에서 기다리던 안쪽 Future를 취소해도, 워커는 나중에 바깥쪽 QueueingFuture를 큐에서 꺼내 실행한다. 안쪽 run()은 상태가 NEW가 아니어서 곧바로 돌아오지만, 바깥쪽은 정상 완료되어 done()이 불리므로 취소된 Future도 완료 큐에 들어간다. 스레드 하나짜리 풀에서 A(300밀리초)를 제출하고, 큐에서 기다리는 B를 cancel(false)한 뒤 take()를 두 번 부르면 이렇게 나온다.

    B cancel=true
take → A, state=SUCCESS
take → B, state=CANCELLED

    그래서 완료 큐에서 꺼낸 Future의 get()은 ExecutionException뿐 아니라 CancellationException도 던질 수 있다고 보고 다뤄야 한다. invokeAny의 구현인 doInvokeAny도 이 큐를 그대로 쓴다. ecs.poll()로 이미 끝난 작업이 있는지 먼저 보고, 없을 때만 다음 작업을 제출하며, 더 제출할 작업이 없으면 ecs.take()에서 잠든다(시간 제한이 있는 invokeAny는 ecs.poll(nanos, NANOSECONDS)에서 기다린다). 꺼낸 Future의 get()이 ExecutionException을 던지면 그 예외를 기억해 두고 다음 완료를 기다린다. "가장 먼저 성공한 결과"를 고를 수 있는 것은 결과가 끝난 순서대로 나오는 이 큐 덕분이다.

    흔한 오해와 함정

    지금까지의 내용을 흔히 틀리는 믿음과 짝지어 정리해 보자. 각 항목의 "실제로는"은 모두 앞에서 실행 결과나 소스로 확인한 것이다.

    • "스레드 풀을 쓰면 스레드 생성 비용이 없어진다." 없어지는 것이 아니라 처음에 몰아서 치르고 이후로 나눠 쓰는 것이다. 게다가 ThreadPoolExecutor는 기본적으로 코어 스레드도 첫 작업이 올 때 만든다. 첫 요청들의 지연까지 줄이고 싶다면 prestartAllCoreThreads()를 고려한다.
    • "submit하면 작업이 끝날 때까지 기다린다." submit은 FutureTask를 만들어 execute에 넘긴 뒤 즉시 돌아온다. 기다리는 것은 get()이다. 그래서 submit(...).get()을 연달아 쓰면 병렬 처리가 직렬 처리로 바뀐다.
    • "get(timeout)이 시간 초과되면 작업도 멈춘다." TimeoutException은 기다리기를 그만두었다는 뜻일 뿐이다. 작업을 멈추려면 직접 cancel(true)를 불러야 하고, 그마저도 작업이 인터럽트에 협조해야 효과가 있다.
    • "cancel(true)가 true를 반환했으니 작업은 멈췄다." 반환값은 Future의 상태를 취소로 확정하는 데 성공했다는 뜻이다. 실행 중이던 코드가 실제로 멈췄는지는 그 코드가 인터럽트에 어떻게 반응하는지에 달려 있다.
    • "작업에서 예외가 나면 로그에 찍힌다." execute로 넘긴 작업은 그렇지만, submit으로 넘긴 작업의 예외는 Future 안에 갇힌다. get()을 부르지 않으면 아무도 모른다.
    • "isDone()이 true면 결과를 쓸 수 있다." 예외와 취소도 isDone() == true다. 결과가 정상인지는 get()이 예외 없이 돌아오는지, 또는 state() == SUCCESS인지로 판단한다.
    • "main이 끝나면 프로그램도 끝난다." 기본 스레드 팩토리가 만드는 워커는 비데몬 스레드이고, 쉬는 동안에도 take()에서 기다리며 살아 있다. 풀을 종료하지 않으면 JVM이 내려가지 않는다.

    다른 주제와의 연결

    스레드 풀은 이 권 밖에서도 계속 등장한다. 스프링 MVC 편에서 다룬 서블릿 컨테이너는 요청마다 스레드를 새로 만들지 않고 스레드 풀의 스레드에 요청 처리를 맡긴다. 이 회차에서 본 원리, 즉 생성 비용을 미리 치르고 동시에 일하는 스레드 수를 풀 크기로 제한한다는 원리가 그대로 적용된다. 스프링 DB 편의 커넥션 풀도 같은 발상이다. 만들기 비싼 자원(TCP 연결과 DB 세션)을 미리 만들어 두고 빌려주고 돌려받는다. 풀의 스레드가 오래 걸리는 작업에 묶이면 풀 전체가 마르고, 그 뒤의 요청이 큐에서 기다리다 지연이 폭증하는 장애 양상도 두 풀이 똑같다.

    Java 21은 가상 스레드(virtual thread)를 정식 기능으로 도입했고, Executors.newVirtualThreadPerTaskExecutor()(Java 21)는 작업마다 새 가상 스레드를 만드는 ExecutorService를 돌려준다. 오라클의 가상 스레드 안내서는 "모든 동시 작업을 가상 스레드로 표현하고, 가상 스레드는 절대 풀링하지 말라"는 제목의 절에서, 플랫폼 스레드는 희소하고 귀중한 자원이라고 설명한다. 이 회차에서 스레드를 풀로 관리한 이유가 바로 플랫폼 스레드의 이 희소성이었다. 가상 스레드에서는 전제가 달라지지만, ExecutorService·Future·invokeAll이라는 작업 제출과 회수의 모델은 그대로 쓰인다는 점이 Executor 프레임워크 설계의 힘이다. 작업 제출 코드는 실행 전략과 분리되어 있기 때문이다.

    Future.get()은 결국 기다리는 스레드를 멈춰 세운다. 결과가 준비되었을 때 이어서 할 일을 콜백으로 연결해 기다림 자체를 없애는 CompletableFuture(Java 8)는 이 권의 범위 밖이지만, 그 토대가 되는 "작업의 완료를 상태 기계와 대기 스택으로 표현한다"는 아이디어는 이 회차의 FutureTask에서 이미 보았다. 다음 회차에서는 이 회차에서 미뤄 둔 질문들을 다룬다. 풀을 어떻게 우아하게 종료하는가(shutdown, shutdownNow, awaitTermination), 코어·최대·큐가 어떻게 맞물려 스레드 수를 조절하는가, Executors가 제공하는 풀 전략들은 어떻게 다른가, 큐도 스레드도 꽉 찼을 때 작업을 어떻게 거절하는가.

    이 장의 핵심

    플랫폼 스레드는 운영체제 스레드라서 비싸고 한 번 끝나면 다시 시작할 수 없다. 그래서 스레드 풀은 끝나지 않는 루프 안에서 블로킹 큐의 작업을 꺼내 실행하는 방식으로 스레드를 재사용한다. 결과와 예외는 Runnable이 아니라 Callable로 돌려받고, submit은 그 결과를 담을 FutureTask를 즉시 돌려준다. FutureTask는 NEW에서 출발하는 CAS 상태 기계로 완료·예외·취소 중 하나만 확정하고, get()을 부른 스레드는 대기 스택에서 park했다가 깨어난다. 이득은 "모두 제출한 뒤 나중에 회수"할 때만 생기고, 취소는 인터럽트에 기대는 협조적 장치이며, submit한 작업의 예외는 get()을 불러야 드러난다.
    플랫폼 스레드의 비용
    플랫폼 스레드는 보통 커널 스레드와 1:1로 대응하고, 스레드마다 -Xss 크기의 스택 주소 공간을 예약한다. 작업마다 새로 만들면 비용이 작업 수에 비례하고 스레드 수도 통제되지 않는다.
    스레드 재사용의 원리
    종료된 스레드는 다시 start()할 수 없다(IllegalThreadStateException). 풀의 워커는 runWorker 루프에서 getTask()로 큐의 작업을 꺼내 실행하기를 반복하고, 작업이 없으면 take()에서 WAITING으로 쉰다.
    Executor 계층
    Executor는 제출과 실행 방식을 분리하는 경계, ExecutorService는 생명 주기·submit·invoke*를 더한 인터페이스, AbstractExecutorService는 이를 execute 위에 구현하고, ThreadPoolExecutor가 실제 풀이다.
    ctl과 Worker
    ctl은 실행 상태(상위 3비트)와 워커 수(하위 29비트)를 한 AtomicInteger에 담아 CAS로 함께 바꾼다. Worker는 AQS를 상속한 비재진입 락으로 "작업 실행 중"을 표시한다.
    Callable
    V call() throws Exception. 결과를 반환하고 체크 예외를 던질 수 있다. 인자 없는 람다가 값을 낼 수 있으면 JLS §15.12.2.5에 따라 submit(Callable)이 선택된다.
    Future와 FutureTask
    submit은 Runnable이자 Future인 FutureTask를 큐에 넣고 즉시 반환한다. get()을 부른 스레드는 트라이버 스택에 올라가 park하고, 워커가 결과를 확정하면 unpark된다.
    FutureTask 상태 기계
    NEW에서 COMPLETING을 거쳐 NORMAL/EXCEPTIONAL로, 또는 CANCELLED, INTERRUPTING을 거쳐 INTERRUPTED로 간다. 모든 전이가 NEW에서의 CAS로 시작하므로 먼저 성공한 하나만 확정된다.
    취소와 예외
    cancel(true)는 실행 스레드를 인터럽트하고 cancel(false)는 상태만 바꾼다. 둘 다 이후의 결과를 버린다. 작업의 예외는 outcome에 저장되어 get()에서 ExecutionException으로 나오며, execute로 넘긴 작업의 예외는 워커를 죽이고 대체 워커가 만들어진다.
    invokeAll과 invokeAny
    invokeAll은 모두 끝날 때까지 기다려 입력 순서의 Future 목록을 반환하고, invokeAny는 처음 성공한 결과를 반환한 뒤 나머지를 cancel(true)한다.
    제출 쪽의 happens-before
    새 워커의 첫 작업은 스레드 시작 규칙(JLS §17.4.4·§17.4.5)으로, 큐로 넘긴 작업은 LinkedBlockingQueue의 AtomicInteger count에 대한 volatile 쓰기·읽기로 워커에게 보인다. 넣기와 꺼내기가 다른 락을 쓰므로 다리는 락이 아니라 count다.
    awaitDone과 대기 노드
    끝나지 않은 작업의 get()은 WaitNode를 트라이버 스택에 CAS로 올리고 park한다. 시간 초과와 인터럽트는 removeWaiter로 자기 노드만 뺄 뿐 작업 상태는 건드리지 않는다. 완료 큐 방식의 ExecutorCompletionService는 done() 훅으로 끝난 Future를 큐에 넣는다.

    실무에서 스레드 풀 장애의 상당수는 "풀이 말랐다"로 요약된다. 모든 워커가 무언가를 기다리며 묶여 있고, 새 작업은 큐에서 하염없이 기다린다. 이때 스레드 덤프를 뜨면 이 회차의 지식이 바로 쓰인다. 쉬는 워커는 LinkedBlockingQueue.take 아래에서 WAITING (parking)이고, 일하는 워커는 각자 작업의 스택을 보인다. 일하는 워커들이 모두 외부 호출이나 다른 Future.get()에서 멈춰 있다면, 작업 안에서 시간 제한 없이 기다리는 코드가 원인이다. 특히 같은 풀에 하위 작업을 제출하고 그 결과를 get()으로 기다리는 작업은, 풀의 모든 스레드가 상위 작업으로 차 버리면 하위 작업을 실행할 스레드가 없어 서로를 영원히 기다리게 될 수 있다. 크기가 고정된 풀에서 작업 사이에 의존이 있다면 풀을 나누거나 기다림에 시간 제한을 두는 판단이 필요하다.

    예외 처리 방식은 submit과 execute 중 무엇을 쓰느냐로 갈린다. 결과가 필요 없는 "던져 놓고 잊는" 작업에 습관적으로 submit을 쓰면, 실패가 Future 안에 묻혀 아무 흔적도 남지 않는다. 이런 작업은 execute로 넘겨 처리되지 않은 예외가 최소한 출력되게 하거나, 작업 본문을 try/catch로 감싸 직접 기록하는 편이 낫다. 반대로 결과가 필요한 작업에서는 get()이 던지는 ExecutionException의 getCause()를 기록해야 원래 원인과 워커 쪽 스택 트레이스를 함께 볼 수 있다.

    시간 제한도 다시 판단할 지점이다. 외부 시스템을 호출하는 작업을 Future로 감싸고 get(timeout)을 거는 것은 호출한 쪽을 보호할 뿐 풀의 스레드를 보호하지 않는다. 시간이 지나면 cancel(true)까지 부르고, 작업이 쓰는 I/O 라이브러리가 인터럽트에 반응하는지, 아니면 자체 타임아웃 설정이 필요한지 확인해야 실제로 스레드가 풀려난다. 또 invokeAny로 여러 곳에 같은 요청을 보낼 때는, 취소된 나머지 작업이 인터럽트를 무시하면 반환 후에도 스레드를 계속 붙잡는다는 점을 함께 고려해야 한다.

    2번. submit(Runnable)은 작업을 FutureTask로 감싼다. FutureTask.run()은 c.call()을 catch (Throwable ex)로 감싸고 있어 NullPointerException을 잡아 setException으로 outcome에 저장하고 상태를 EXCEPTIONAL로 만든다. 워커 입장에서 run()은 정상 반환했으므로 처리되지 않은 예외 출력도 없다. 반환된 Future를 버렸기 때문에 아무도 예외를 꺼내지 않았다. 해결책은 (1) Future를 받아 get()을 호출하고 ExecutionException의 getCause()를 기록하거나, (2) 결과가 필요 없는 작업이면 execute로 넘겨 예외가 워커 밖으로 전파되어 출력되게 하는 것이다. 작업 본문을 직접 try/catch로 감싸 기록하는 방법이나, afterExecute에서 Future를 확인하는 방법도 있다.

    3번. B는 아직 큐에 있으므로 상태가 NEW다. cancel(false)는 STATE.compareAndSet(this, NEW, CANCELLED)에 성공해 true를 반환하고, finishCompletion()으로 기다리던 스레드(있다면)를 깨운다. 이 시점부터 B의 get()은 CancellationException을 던진다. B 객체는 큐에서 빠지지 않는다. 4초 뒤 A를 마친 워커가 getTask()로 B를 꺼내 run()을 부르면, 첫 줄 if (state != NEW || ...) return;에서 상태가 CANCELLED이므로 즉시 반환한다. call()은 한 번도 실행되지 않는다. 취소된 작업이 큐에 많다면 purge()로 미리 치울 수 있다.

    4번. 약 2초 뒤 "B"를 반환한다. 1초에 A가 먼저 끝나지만 예외로 끝났으므로 invokeAny는 그 ExecutionException을 기록만 하고 다음 완료를 기다린다. 2초에 B가 성공하면 그 결과를 반환하고, finally의 cancelAll이 C의 Future에 cancel(true)를 부른다. C의 Future는 즉시 취소 상태가 되지만, C의 코드는 인터럽트를 확인하지 않으므로 계속 돈다. 반환 직후 C를 실행하던 스레드는 인터럽트 플래그가 켜진 채 RUNNABLE 상태로 계산을 이어 가며, 5초에 끝났을 때 set("C")는 상태가 NEW가 아니어서 CAS에 실패해 버려진다. 남은 인터럽트 플래그는 다음 작업이 시작되기 전에 워커 루프에서 정리된다. 큐에서 기다리려던 take()가 InterruptedException을 내면 getTask()가 그것을 잡고 다시 시도하고, 작업을 얻은 뒤에는 runWorker가 Thread.interrupted()로 플래그를 지운다.

    5번. 워커 스레드 안에서 (1) outcome = v는 프로그램 순서상 (2) STATE.setRelease(this, NORMAL)보다 앞선다. 릴리스 쓰기는 앞선 쓰기가 그 뒤로 재배치되지 않게 한다. get()을 부른 스레드는 (3) volatile 필드 state를 읽어 NORMAL을 확인한 뒤에 (4) outcome을 읽는다. (2)에서 쓴 값을 (3)이 읽었으므로, VarHandle 문서의 릴리스·획득 규칙(volatile 읽기는 획득 모드의 성질을 갖는다)에 따라 (3)과 그 뒤의 접근은 (2)와 그 앞의 접근보다 뒤에 순서 지어진다. 이것이 프로그램 순서 (1)→(2), (3)→(4)와 이어져 (1)이 (4)보다 앞서는 사슬이 완성된다. 그래서 (4)는 (1)에서 쓴 값을 본다. 이 보장은 패키지 문서의 "비동기 계산이 한 일은 Future.get() 이후의 동작보다 먼저 일어난다"는 메모리 일관성 계약으로도 명시되어 있다.

     스레드 풀이 스레드를 "재사용"하는 실제 방법으로 옳은 것은? 작업이 끝나 TERMINATED가 된 스레드를 다시 start()한다. 워커 스레드의 run()이 끝나지 않는 루프를 돌며 큐에서 작업을 꺼내 실행하고, 작업이 없으면 큐의 take()에서 기다린다. JVM이 종료된 스레드의 운영체제 스레드를 캐시해 두었다가 새 Thread 객체에 연결한다. 작업마다 새 스레드를 만들되 스택 크기를 줄여 비용을 없앤다. 종료된 스레드에 start()를 다시 부르면 IllegalThreadStateException이 난다. ThreadPoolExecutor.runWorker는 getTask()가 null을 줄 때까지 작업을 꺼내 실행하는 루프이고, 쉬는 워커는 LinkedBlockingQueue.take() 아래에서 WAITING 상태다. 3번의 캐시는 이 회차에서 확인한 동작이 아니며, 4번은 재사용이 아니다. AtomicInteger counter가 0일 때 Future f = es.submit(() -> counter.incrementAndGet()); 후 f.get()은 무엇을 반환하는가? 항상 null. 인자 없는 람다는 Runnable로 해석된다. 컴파일 오류. Runnable과 Callable 사이에서 모호하다. 1. 몸체가 값을 낼 수 있는 식이므로 더 구체적인 submit(Callable)이 선택된다. 0. get()은 작업 시작 전의 값을 반환한다. counter.incrementAndGet()은 Runnable(문장으로 쓰인 식)과 Callable(값을 반환하는 식) 모두에 맞는다. 매개변수 없는 람다는 명시적 타입 람다이고(JLS §15.27.1), 이 경우 반환형이 void인 쪽보다 다른 쪽이 더 구체적이다(JLS §15.12.2.5). 그래서 javap로 보면 submit(Callable)이 호출되고, 결과는 증가된 값 1이다. f.get(1, TimeUnit.SECONDS)가 TimeoutException을 던졌다. 이 시점의 작업에 대한 설명으로 옳은 것은? 작업은 계속 실행 중이며 f.state()는 RUNNING이다. 멈추게 하려면 cancel(true)를 따로 불러야 한다. 작업은 자동으로 cancel(true)되어 f.isCancelled()가 true다. 작업은 FAILED 상태가 되고 exceptionNow()가 TimeoutException을 돌려준다. 풀이 해당 워커 스레드를 강제로 종료하고 대체 워커를 만든다. FutureTask.get(long, TimeUnit)는 awaitDone이 시간 안에 끝나지 않았다는 상태값을 받으면 TimeoutException을 던질 뿐, cancel을 호출하지도 상태를 바꾸지도 않는다. 상태는 여전히 NEW, 즉 RUNNING이다. 시간 초과는 기다리는 쪽의 사정일 뿐 작업의 결말이 아니다. 인터럽트를 전혀 확인하지 않는 CPU 계산 루프를 실행 중인 작업에 cancel(true)를 불렀다. 일어나는 일로 옳은 것은? cancel은 false를 반환한다. 실행 중인 작업은 취소할 수 없기 때문이다. 워커 스레드가 즉시 강제 종료되고 get()은 InterruptedException을 던진다. Future는 취소되지 않은 상태로 남고, 루프가 끝나면 결과가 정상적으로 get()에 전달된다. cancel은 true를 반환하고 get()은 즉시 CancellationException을 던지지만, 루프는 끝까지 실행되고 그 결과는 버려진다. cancel(true)는 상태를 NEW에서 INTERRUPTING으로 CAS한 뒤 실행 스레드에 interrupt()를 걸고 INTERRUPTED로 확정한다. Future 쪽은 즉시 취소로 끝난다. 그러나 인터럽트는 플래그를 켤 뿐 스레드를 멈추지 않으므로 루프는 계속 돌고, 마지막 set()은 상태가 NEW가 아니어서 CAS에 실패해 결과가 버려진다. 실행 중인 작업도 상태가 NEW이므로 취소는 성공한다. execute(task)로 넘긴 Runnable이 RuntimeException을 던졌다. 고정 크기 풀에서 일어나는 일로 옳은 것은? 예외가 FutureTask에 저장되어 아무것도 출력되지 않고 워커는 다음 작업을 계속 처리한다. 예외가 워커 스레드 밖으로 전파되어 처리되지 않은 예외로 출력되고, 그 워커는 끝나며 풀이 대체 워커를 새로 만든다. 풀 전체가 SHUTDOWN 상태로 바뀌어 더 이상 작업을 받지 않는다. execute를 호출한 스레드에서 같은 예외가 다시 던져진다. execute는 작업을 FutureTask로 감싸지 않는다. runWorker는 afterExecute(task, ex)를 부른 뒤 예외를 다시 던져 루프를 벗어나고, 스레드는 처리되지 않은 예외로 끝난다. processWorkerExit는 completedAbruptly가 true이므로 addWorker로 대체 워커를 만든다. 실행 결과에서 다음 작업의 스레드 이름이 pool-1-thread-2로 바뀐 것이 그 증거다. 1번은 submit의 동작이다.
    스레드 풀(thread pool)
    미리 만든 스레드들을 두고, 제출된 작업을 큐에 받아 그 스레드들이 차례로 꺼내 실행하게 하는 구조. 스레드 생성 비용을 줄이고 동시에 일하는 스레드 수를 제한한다.
    워커(worker)
    ThreadPoolExecutor 안에서 스레드 하나와 그 스레드가 도는 작업 루프를 묶은 내부 객체. AQS를 상속해 작업 실행 중임을 락으로 표시한다.
    Executor
    execute(Runnable) 하나만 가진 인터페이스로, 작업 제출과 실행 방식을 분리한다. 구현은 호출 스레드에서 바로 실행할 수도, 새 스레드를 만들 수도, 풀을 쓸 수도 있다.
    ExecutorService
    Executor에 생명 주기 관리(shutdown, close 등), Future를 돌려주는 submit, 묶음 처리(invokeAll, invokeAny)를 더한 인터페이스. Java 19부터 AutoCloseable이다.
    Callable
    V call() throws Exception을 가진 함수형 인터페이스. 결과를 반환하고 체크 예외를 던질 수 있는 작업을 표현한다.
    Future
    비동기 계산의 결과를 나타내는 인터페이스. 완료 확인, 대기, 결과 회수, 취소 메서드를 제공한다.
    FutureTask
    Runnable이자 Future인 표준 구현. volatile int state의 CAS 전이와 대기 스레드의 트라이버 스택으로 완료를 동기화한다.
    ExecutionException
    작업이 예외로 끝났을 때 get()이 던지는 체크 예외. 작업이 던진 원래 예외를 원인(getCause())으로 감싼다.
    CancellationException
    취소된 작업의 결과를 get()으로 꺼내려 할 때 던져지는 런타임 예외.
    ExecutorCompletionService
    제출한 작업을 done() 훅이 있는 FutureTask로 한 겹 더 감싸, 끝난 순서대로 Future를 완료 큐에 넣고 take()로 꺼내게 하는 CompletionService 구현. invokeAny의 내부에서도 쓰인다.
    트라이버 스택(Treiber stack)
    맨 위 노드 참조를 CAS로 바꿔 끼워 원소를 넣고 빼는 락 없는 연결 스택. FutureTask는 get()으로 기다리는 스레드들을 이 구조로 관리한다.
