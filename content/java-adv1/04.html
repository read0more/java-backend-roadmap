    이 회차의 질문: 다른 스레드에게 "그만"이라고 말하는 방법

    앞 회차에서 스레드의 생명 주기를 다뤘다. 스레드는 NEW로 태어나 start() 이후 RUNNABLE이 되고, 락을 기다리면 BLOCKED, 기한 없이 기다리면 WAITING, 기한을 두고 기다리면 TIMED_WAITING이 되며, run()이 끝나면 TERMINATED가 된다. 그리고 join()으로 다른 스레드가 끝나기를 기다리는 방법을 봤다. join()은 "네가 끝날 때까지 내가 기다리겠다"는 방향의 제어다.

    이번 회차는 반대 방향을 다룬다. "네가 하던 일을 그만두라"고 알리는 방법, 그리고 "지금은 내가 CPU를 쓰지 않아도 되니 다른 스레드에게 넘기겠다"고 알리는 방법이다. 앞의 것이 인터럽트(interrupt), 뒤의 것이 양보(yield)다. 둘 다 메서드 하나로 끝나는 API처럼 보이지만, 정확히 이해하려면 스레드가 "잠들어 있다"는 것이 운영체제와 JVM 안에서 무슨 상태인지까지 내려가야 한다.

    상황을 하나 정하자. 백그라운드 스레드가 3초마다 어떤 작업을 반복한다. 사용자가 취소 버튼을 눌렀고, main 스레드는 이 백그라운드 스레드를 멈추고 싶다. 가장 먼저 떠오르는 것은 Thread 클래스에 있는 stop() 메서드다. 그런데 Java 21에서 이 메서드를 부르면 아무 스레드도 멈추지 않고 UnsupportedOperationException이 던져진다. OpenJDK 21 소스의 본문은 throw new UnsupportedOperationException(); 한 줄이고, @Deprecated(since="1.2", forRemoval=true)가 붙어 있다. 1.2 때부터 쓰지 말라고 했고, 지금은 아예 동작하지 않는다.

    이유는 Javadoc의 폐기 설명에 적혀 있다. 원래의 stop()은 대상 스레드에 ThreadDeath를 던지게 했고, 그 예외가 스택을 거슬러 올라가며 그 스레드가 잡고 있던 모든 모니터 락을 풀었다. 문제는 락이 보호하던 객체가 수정 도중이었을 수 있다는 점이다. 계좌 A에서 돈을 빼고 계좌 B에 넣는 두 줄짜리 synchronized 블록을 생각해 보자. 첫 줄과 둘째 줄 사이에서 스레드가 강제로 멈추면 락은 풀리지만 돈은 A에서 빠지기만 하고 B에 들어가지 않은 상태가 다른 스레드에게 그대로 보인다. 밖에서 스레드를 강제로 끊으면, 끊긴 지점이 어디인지 아무도 고를 수 없다.

    그래서 자바의 스레드 종료는 협조적(cooperative)이다. 멈추라는 요청은 밖에서 보내지만, 실제로 멈추는 것은 대상 스레드 자신이다. 대상 스레드는 자기 코드에서 "멈춰도 안전한 지점"을 골라 요청을 확인하고, 정리할 것을 정리한 뒤 run()에서 정상적으로 빠져나온다. 이 회차의 절반은 이 요청을 어떻게 전달하고 어떻게 확인하는지에 관한 이야기다.

    첫 번째 시도: 공유 플래그로 멈추기

    요청을 전달하는 가장 단순한 방법은 두 스레드가 함께 보는 변수 하나를 두는 것이다. 작업 스레드는 반복할 때마다 그 변수를 확인하고, main 스레드는 멈추고 싶을 때 그 값을 바꾼다. 예제마다 시각과 스레드 이름을 찍기 위해 아래의 작은 로그 클래스를 같은 디렉터리에 두고 javac *.java로 함께 컴파일한다고 하자.

        String now = LocalTime.now().format(TIME);
        String name = Thread.currentThread().getName();
        System.out.printf("%s [%7s] %s%n", now, name, message);
    }
}

    코드에 volatile이 붙은 이유도 짚고 가자. 자세한 원리는 다음 회차(메모리 가시성)의 몫이지만, 이 자리에서 꼭 알아야 할 사실이 하나 있다. 자바 언어 명세 JLS §17.3은 Thread.sleep과 Thread.yield에 동기화 의미가 전혀 없다고 못 박는다. 컴파일러는 sleep 호출 전에 레지스터에 캐시한 쓰기를 공유 메모리로 내보낼 의무도, 호출 뒤에 값을 다시 읽어 올 의무도 없다. 명세는 volatile이 아닌 done 필드로 while (!this.done) Thread.sleep(1000);을 도는 코드를 "깨진(broken)" 예로 들고, 컴파일러가 필드를 한 번만 읽고 그 값을 계속 재사용해 루프가 끝나지 않을 수 있다고 설명한다. "자고 일어나면 새 값을 보겠지"라는 기대는 명세가 보장하지 않는다.

    인터럽트: 상태 하나와 깨우기

    인터럽트는 "다른 스레드의 잠을 밖에서 끊을 수 있는 공유 플래그"라고 이해하면 출발점으로 충분하다. t.interrupt()를 호출하면 두 가지가 일어난다. 첫째, 스레드 t의 인터럽트 상태(interrupt status)라는 불리언 값이 true가 된다. 둘째, t가 특정한 대기 메서드 안에서 멈춰 있다면 그 대기가 끊긴다. JLS §17.2.3은 인터럽트를 이렇게 정의한다. 스레드 t가 u.interrupt()를 호출하면 u의 인터럽트 상태가 true가 되고, u가 어떤 객체의 대기 집합(wait set)에 들어 있다면 거기서 빠져나오고, 그 객체의 모니터를 다시 잡은 뒤 InterruptedException을 던지며 wait에서 돌아온다. 대기 집합과 wait는 생산자-소비자 회차에서 자세히 다룬다.

    이름 때문에 생기는 오해부터 정리하자. 자바의 인터럽트는 CPU의 하드웨어 인터럽트나 운영체제의 시그널과 관계가 없다. 대상 스레드의 실행을 그 자리에서 가로채 다른 코드를 실행시키는 장치가 아니다. 자바 인터럽트는 자바 객체(Thread)에 기록되는 요청이고, 그 요청에 반응하는 것은 대상 스레드가 실행하는 코드다.

    어떤 대기가 끊기는지는 Thread.interrupt()의 Javadoc이 경우를 나눠 적어 두었다.

    public class InterruptSleep {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            try {
                while (true) {
                    Log.log("작업 중");
                    Thread.sleep(3000);
                }
            } catch (InterruptedException e) {
                Thread me = Thread.currentThread();
                Log.log("예외 메시지 = " + e.getMessage());
                Log.log("isInterrupted = " + me.isInterrupted());
                Log.log("state = " + me.getState());
            }
            Log.log("자원 정리 후 종료");
        }, "worker");
        worker.start();

        Thread.sleep(4000);
        Log.log("interrupt 전 worker 상태 = " + worker.getState());
        worker.interrupt();
        worker.join();
        Log.log("main 종료");
    }
}

    예외라는 형태를 택한 것에도 실익이 있다. sleep은 반환형이 void이고, 정상적으로 시간을 다 채운 경우와 중간에 끊긴 경우를 구분해 알려 줄 방법이 필요하다. 체크 예외로 만들어 두면 sleep을 부르는 모든 코드는 컴파일 단계에서 "끊기면 어떻게 할지"를 정하도록 강제된다. 앞 회차에서 본 대로 Runnable.run()은 체크 예외를 밖으로 던질 수 없으므로, run() 안에서 sleep을 부르면 반드시 그 자리에서 잡아야 한다. 그 catch 블록이 바로 "멈추라는 요청을 받았을 때의 정리 코드"가 들어갈 자리가 된다.

    깨어 있는 스레드에 인터럽트를 걸면: isInterrupted()와 Thread.interrupted()

    표의 마지막 줄, 대상 스레드가 대기 중이 아닐 때는 어떤가. 이때 인터럽트는 상태만 true로 바꾸고 아무것도 하지 않는다. 대상 스레드가 계산을 하고 있다면 계산은 그대로 이어진다. 그러니 계산 위주의 루프가 인터럽트에 반응하려면 스스로 상태를 확인해야 한다. 인스턴스 메서드 isInterrupted()가 그 용도다.

    public class InterruptRunning {
    public static void main(String[] args) throws InterruptedException {
        Thread worker = new Thread(() -> {
            long count = 0;
            while (!Thread.currentThread().isInterrupted()) {
                count++; // sleep 없이 계속 계산만 한다
            }
            Log.log("루프 탈출, count > 0 = " + (count > 0));
            Log.log("isInterrupted = " + Thread.currentThread().isInterrupted());
            try {
                Log.log("자원 정리 시작 (1초 걸림)");
                Thread.sleep(1000);
                Log.log("자원 정리 완료");
            } catch (InterruptedException e) {
                Log.log("자원 정리 실패: " + e.getMessage());
                Log.log("isInterrupted = " + Thread.currentThread().isInterrupted());
            }
        }, "worker");
        worker.start();

        Thread.sleep(100);
        Log.log("interrupt 전 worker 상태 = " + worker.getState());
        worker.interrupt();
        worker.join();
        Log.log("main 종료");
    }
}

    // OpenJDK 21 java.lang.Thread (발췌)
boolean getAndClearInterrupt() {
    boolean oldValue = interrupted;
    // We may have been interrupted the moment after we read the field,
    // so only clear the field if we saw that it was set and will return
    // true; otherwise we could lose an interrupt.
    if (oldValue) {
        interrupted = false;
        clearInterruptEvent();
    }
    return oldValue;
}

    주석이 짚는 경합을 따라가 보자. 만약 이 메서드가 "읽고 나서 무조건 false를 쓴다"면, 현재 스레드가 false를 읽은 직후 다른 스레드가 interrupt()로 true를 쓰고, 이어서 현재 스레드가 false를 덮어쓰는 순서가 가능하다. 그러면 호출자는 false를 받았는데 상태도 false가 되어, 방금 들어온 인터럽트가 흔적 없이 사라진다. true를 읽었을 때만 지우면, 지운 사실을 반환값 true로 호출자에게 반드시 알려 주므로 요청이 사라지지 않는다. 락 없이 상태 하나를 여러 스레드가 다룰 때 어떤 순서까지 고려해야 하는지 보여 주는 작은 예다. 이런 종류의 추론은 CAS 회차에서 본격적으로 다시 나온다.

    정적 메서드라는 점에서 생기는 함정도 하나 있다. 자바는 정적 메서드를 인스턴스 참조로 호출하는 것을 허용한다. 그래서 target.interrupted()라고 써도 컴파일되는데, 이것은 target을 검사하지 않고 지금 이 코드를 실행하는 스레드를 검사하고 지운다.

            }
        }, "target");
        target.setDaemon(true);
        target.start();
        Thread.sleep(100);

    한 층 아래: HotSpot에서 interrupt()가 잠든 스레드를 깨우는 길

    "상태를 true로 바꾸고 잠을 끊는다"는 설명에서 뒤쪽 절반이 어떻게 일어나는지 OpenJDK 21의 HotSpot 소스로 따라가 보자. 여기서부터는 명세가 아니라 구현이다. JLS와 Javadoc이 보장하는 것은 앞 절까지의 동작이고, 아래의 함수 이름과 구조는 OpenJDK 21(jdk21u) HotSpot의 선택이다.

    자바 쪽: 필드를 쓰고 VM에 알린다

    // OpenJDK 21 java.lang.Thread (발췌, 권한 검사 생략)
public void interrupt() {
    // ...
    // Setting the interrupt status must be done before reading nioBlocker.
    interrupted = true;
    interrupt0();  // inform VM of interrupt

    // thread may be blocked in an I/O operation
    if (this != Thread.currentThread()) {
        synchronized (interruptLock) {
            Interruptible b = nioBlocker;
            if (b != null) {
                b.interrupt(this);
            }
        }
    }
}

    세 단계다. 필드 interrupted에 true를 쓰고, 네이티브 메서드 interrupt0()로 VM에 알리고, 대상이 NIO 채널 I/O 중이면 그 채널 쪽 처리(nioBlocker)를 부른다. 마지막 부분이 Javadoc 표의 InterruptibleChannel 줄을 구현한다. 자바 코드에는 "잠을 깨우는" 코드가 없다. 그 일은 interrupt0() 너머에서 일어난다.

    네이티브 연결: interrupt0 → JVM_Interrupt → JavaThread::interrupt

    JDK의 Thread.c는 Thread의 네이티브 메서드를 VM 함수에 연결하는 표를 갖고 있다. 이 회차에 나오는 세 메서드는 interrupt0 → JVM_Interrupt, sleep0 → JVM_Sleep, yield0 → JVM_Yield로 연결된다. JVM_Interrupt는 대상 자바 스레드가 아직 살아 있는지(VM 내부의 JavaThread가 있는지) 확인하고, 살아 있으면 JavaThread::interrupt()를 부른다. 그 본문이 핵심이다.

    // OpenJDK 21 src/hotspot/share/runtime/javaThread.cpp (발췌)
void JavaThread::interrupt() {
  // For Windows _interrupt_event
  WINDOWS_ONLY(osthread()->set_interrupted(true);)

  // For Thread.sleep
  _SleepEvent->unpark();

  // For JSR166 LockSupport.park
  parker()->unpark();

  // For ObjectMonitor and JvmtiRawMonitor
  _ParkEvent->unpark();
}

    HotSpot의 자바 스레드 하나는 잠들 때 쓰는 "이벤트" 객체를 용도별로 갖고 있다. Thread.sleep은 _SleepEvent에서, LockSupport.park(뒤에서 볼 ReentrantLock과 동시성 라이브러리의 기반)는 parker()에서, Object.wait와 모니터 대기는 _ParkEvent에서 잔다. interrupt()는 대상이 지금 어느 것에서 자고 있는지 묻지 않고 세 이벤트를 모두 깨운다. 그 순간 자고 있지 않던 이벤트는 "신호가 와 있는" 상태로 남는다. 같은 파일의 is_interrupted() 주석은 이 때문에 Object.wait()와 LockSupport.park()가 드물게 가짜로 깨어나는(spurious wakeup) 일이 생길 수 있지만 그것은 허용된 동작이고 해롭지 않으며, sleep 쪽 이벤트는 잠들기 전에 명시적으로 초기화하므로 일찍 돌아오는 일이 없다고 적는다. wait()가 가짜로 깨어날 수 있다는 사실은 생산자-소비자 회차에서 "wait()는 반드시 조건을 다시 확인하는 루프 안에서 부른다"는 규칙의 근거로 다시 나온다.

    이벤트가 운영체제 수준에서 무엇인지도 확인해 두자. 리눅스와 macOS 같은 POSIX 계열에서 HotSpot의 이벤트(PlatformEvent, os_posix.cpp)는 pthread 뮤텍스와 조건 변수로 구현되어 있다. 시간을 정해 잠드는 park_nanos는 pthread_cond_timedwait를, 깨우는 unpark는 pthread_cond_signal을 부른다. 즉 자바 스레드가 sleep 중이라는 것은, 그 아래의 OS 스레드가 조건 변수에서 기다리느라 운영체제 스케줄러의 실행 후보에서 빠져 있다는 뜻이다. CPU를 전혀 쓰지 않는다. interrupt()는 그 조건 변수에 신호를 보내 OS 스레드를 실행 후보로 돌려놓는 일이다.

    잠드는 쪽: JVM_Sleep과 sleep_nanos

    // OpenJDK 21 src/hotspot/share/prims/jvm.cpp, JVM_Sleep (발췌)
if (thread->is_interrupted(true) && !HAS_PENDING_EXCEPTION) {
  THROW_MSG(vmSymbols::java_lang_InterruptedException(), "sleep interrupted");
}

  // ...
  if (!thread->sleep_nanos(nanos)) { // interrupted

    앞의 실행 결과에서 본 사실 세 가지가 여기서 설명된다. 첫째, 잠들기 전에 is_interrupted(true)로 상태를 확인하고 이미 true면 곧장 예외를 던진다. 인수 true는 "읽으면서 지워라"라는 뜻이다. 그래서 상태가 남아 있던 스레드의 정리용 sleep(1000)이 즉시 실패했고, 예외를 받은 뒤 상태가 false였다. 둘째, 예외 메시지 sleep interrupted가 이 문자열이다. 셋째, 잠자는 동안 VM 내부 상태는 SLEEPING이고, HotSpot은 이것을 자바의 Thread.State.TIMED_WAITING으로 보고한다. 스레드 덤프에서는 TIMED_WAITING (sleeping)으로 찍힌다(javaClasses.cpp의 상태 이름 표).

    실제로 잠드는 함수 JavaThread::sleep_nanos는 루프로 되어 있다. 먼저 _SleepEvent를 초기화(reset)하고 메모리 펜스(fence)를 친다. 소스 주석은 그 이유를 "스레드 인터럽트는 자바 메모리 모델에서 happens-before 순서를 만들기 때문에 인터럽트 상태와 동기화해야 한다"고 설명한다. 그다음 반복마다 ① 인터럽트 상태를 확인해 true면 지우고 false(인터럽트됨)를 돌려주고, ② 남은 시간이 없으면 true(시간 다 채움)를 돌려주고, ③ 아니면 남은 시간만큼 park_nanos로 잔다. 깨어나면 경과 시간을 다시 계산해 ①로 돌아간다. 소스 주석에 "interruption has precedence over timing out"이라고 적혀 있듯, 시간이 다 된 것과 인터럽트가 동시에 일어났으면 인터럽트가 우선이다.

    이 그림에서 눈여겨볼 점은 깨우는 신호와 상태 비트가 분리되어 있다는 것이다. 신호(unpark)는 그저 잠을 끊을 뿐이고, 잠에서 깬 스레드가 "왜 깼는가"를 판단하는 근거는 언제나 상태 비트다. 그래서 신호가 먼저 오고 상태 확인이 나중에 와도, 상태가 먼저 켜지고 잠이 나중에 시작되어도 결과가 같다. 잠들기 직전에 인터럽트가 들어온 경우는 JVM_Sleep 첫 줄의 확인이 잡고, 잠든 뒤 들어온 경우는 unpark와 루프 맨 위의 확인이 잡는다. 인터럽트 요청이 그 틈새로 새어 나갈 구멍이 없다. 플래그 방식으로는 만들 수 없는 성질이다.

    명세가 보장하는 것: 인터럽트의 happens-before

    HotSpot이 펜스를 치는 이유가 된 명세 조항은 JLS §17.4.4에 있다. 스레드 T1이 스레드 T2를 인터럽트하면, 그 인터럽트는 다른 어떤 스레드(T2 포함)가 "T2가 인터럽트되었음"을 알아내는 지점과 동기화된다(synchronizes-with). 알아내는 방법으로 명세는 InterruptedException이 던져지는 것, Thread.interrupted나 Thread.isInterrupted를 호출하는 것을 든다. 결과적으로 T1이 interrupt()를 부르기 전에 한 쓰기는, T2가 인터럽트를 감지한 뒤의 읽기에서 보인다는 것이 보장된다.

    // main 스레드
cancelReason = "사용자가 취소함";   // volatile이 아닌 일반 필드
worker.interrupt();

// worker 스레드
try {
    Thread.sleep(3000);
} catch (InterruptedException e) {
    Log.log(cancelReason);         // "사용자가 취소함"을 보는 것이 보장된다
}

    이 보장은 인터럽트를 감지한 경로에만 성립한다. 인터럽트와 관계없이 그냥 cancelReason을 읽는 다른 코드에는 아무 보장이 없다. happens-before가 정확히 무엇인지는 다음 회차에서 volatile과 함께 세운다. 여기서는 "인터럽트는 메모리 가시성 측면에서도 신호 역할을 한다"는 것만 기억해 두면 된다.

    자바 코드, JVM 네이티브 경계, HotSpot 내부, 운영체제의 네 층을 위에서 아래로 놓고, 호출하는 스레드와 잠든 스레드 사이의 경로를 보여 준다. 가로로 긴 네 개의 층을 위에서 아래로 쌓은 그림. 층 이름은 왼쪽 끝에 "자바 코드", "네이티브 경계", "HotSpot", "운영체제". 왼쪽 열은 "main 스레드", 오른쪽 열은 "worker 스레드". 왼쪽 열 위에서 아래로 상자 "interrupt()" → "interrupt0()" → "JavaThread::interrupt()" 가 화살표로 이어지고, 맨 위 상자 옆에 작은 깃발 아이콘과 라벨 "interrupted = true". "JavaThread::interrupt()" 상자에서 세 갈래 화살표가 오른쪽으로 뻗어 각각 작은 상자 "_SleepEvent", "parker", "_ParkEvent"에 닿음. "_SleepEvent" 상자 아래 운영체제 층에 "조건 변수"라는 상자가 있고 그 안에 잠든 스레드 아이콘(zZ). 오른쪽 열 맨 위 자바 코드 층에 상자 "catch (InterruptedException e)". 운영체제 층의 잠든 스레드에서 위로 올라가는 굵은 화살표가 그 catch 상자로 이어짐. 플랫한 다이어그램 스타일, 층마다 연한 다른 배경색. OpenJDK 21 HotSpot 기준. interrupt()는 상태 비트를 쓰고, 세 대기 이벤트를 모두 깨운다.

    인터럽트가 닿지 않는 곳

    Javadoc 표의 마지막 줄은 "위 어느 경우도 아니면 상태만 설정된다"였다. 이 줄에는 계산 중인 스레드만 들어가는 것이 아니다. 무언가를 기다리고 있지만 그 기다림이 인터럽트 가능한 목록에 없는 스레드도 들어간다. 대표적인 두 가지를 실험으로 확인해 보자. 하나는 synchronized 블록에 들어가려고 모니터 락을 기다리는 스레드, 다른 하나는 System.in.read()처럼 InputStream으로 입력을 기다리는 스레드다.

    public class NotWoken {
    static final Object lock = new Object();

    public static void main(String[] args) throws Exception {
        Thread reader = new Thread(() -> {
            try {
                int b = System.in.read();
                Log.log("read 반환 = " + b + ", isInterrupted = "
                        + Thread.currentThread().isInterrupted());
            } catch (java.io.IOException e) {
                Log.log("IOException " + e);
            }
        }, "reader");

        Thread blocked = new Thread(() -> {
            synchronized (lock) {
                Log.log("락 획득, isInterrupted = " + Thread.currentThread().isInterrupted());
            }
        }, "blocked");

        synchronized (lock) {
            reader.start();
            blocked.start();
            Thread.sleep(300);
            Log.log("reader 상태 = " + reader.getState());
            Log.log("blocked 상태 = " + blocked.getState());
            reader.interrupt();
            blocked.interrupt();
            Thread.sleep(1000);
            Log.log("1초 뒤 reader 상태 = " + reader.getState());
            Log.log("1초 뒤 blocked 상태 = " + blocked.getState());
        }
        blocked.join();
        reader.join();
        Log.log("main 종료");
    }
}

    main은 lock을 쥔 채로 두 스레드를 시작했다. blocked 스레드는 그 락을 얻지 못해 BLOCKED가 된다. 인터럽트를 보내도 1초 뒤 여전히 BLOCKED다. 모니터 락 획득은 인터럽트로 끊을 수 있는 대기가 아니다. main이 synchronized 블록을 나가 락을 놓은 뒤에야 blocked가 락을 얻었고, 그때 확인한 인터럽트 상태는 true다. 요청은 기록되어 있었지만 대기를 끊지는 못했다. 앞에서 본 JavaThread::interrupt()가 모니터용 이벤트까지 깨운다는 사실과 헷갈리지 말자. 깨우는 신호를 받는 것과 대기를 그만두는 것은 다르다. 모니터 락 획득은 락을 얻기 전에는 끝나지 않는 대기이므로, 겉으로 보이는 결과는 계속 BLOCKED다. 락을 기다리다가도 인터럽트에 반응하고 싶다면 ReentrantLock.lockInterruptibly()를 써야 하는데, 이것은 concurrent.Lock 회차에서 다룬다.

    reader 스레드는 더 흥미롭다. 입력이 오지 않아 read() 안에서 멈춰 있는데 상태는 RUNNABLE이다. 운영체제의 read 시스템 호출에서 기다리는 스레드를 자바는 RUNNABLE로 보고한다. Thread.State.RUNNABLE의 Javadoc이 "JVM 안에서 실행 중이지만 프로세서 같은 운영체제의 다른 자원을 기다리고 있을 수 있다"고 적어 둔 그대로다. 인터럽트는 이 대기도 끊지 못했다. 셸이 3초 뒤 x를 보내자 그제야 read()가 120('x'의 코드)을 돌려줬고, 인터럽트 상태는 true로 남아 있었다. InputStream은 InterruptibleChannel이 아니다.

    그러면 이런 대기는 어떻게 끝내는가. JDK 문서의 「Why are Thread.stop, Thread.suspend and Thread.resume Deprecated?」는 "인터럽트에 반응하지 않는 스레드는 어떻게 하는가"라는 질문에, 일반적으로 통하는 방법은 없고 상황에 맞는 수단을 써야 한다고 답하면서, 알려진 소켓에서 기다리는 스레드라면 그 소켓을 닫아 즉시 돌아오게 할 수 있다는 예를 든다. 대기의 종류마다 "깨우는 수단"이 따로 있다는 것을 기억해 두자. sleep, wait, join, park의 깨우는 수단이 인터럽트다.

    마지막으로 이미 끝난 스레드를 인터럽트하는 경우다. Javadoc은 "살아 있지 않은 스레드의 인터럽트는 아무 효과가 없어도 된다"고 하면서, 구현 노트(implNote)로 "JDK 참조 구현에서는 살아 있지 않은 스레드의 인터럽트도 요청이 있었다는 사실을 기록하고 interrupted()와 isInterrupted()로 보고한다"고 덧붙인다. 앞의 소스에서 본 대로 자바 필드에 먼저 true를 쓰고, JVM_Interrupt는 살아 있는 스레드에만 이벤트를 깨우기 때문이다. 실제로 join()으로 종료를 확인한 스레드에 interrupt()를 부른 뒤 isInterrupted()를 보면 OpenJDK 21에서 true가 나온다. 명세가 허용하는 범위 안의 구현 선택이므로, 이 값에 기대는 코드를 짜지는 말자.

    한 층 더 아래: 시스템 호출 안에서 막힌 스레드를 채널이 꺼내는 방법

    방금 System.in.read()에서 기다리던 스레드는 인터럽트로 깨어나지 않았다. 그런데 Javadoc 표의 둘째 줄은 InterruptibleChannel에 대한 I/O는 끊긴다고 했다. 두 경우 모두 스레드는 운영체제의 read 시스템 호출 안에서 기다린다. 앞에서 본 HotSpot의 대기 이벤트는 JVM이 만든 조건 변수라서 unpark로 깨울 수 있지만, 커널의 read 안에서 데이터를 기다리는 스레드는 그런 조건 변수에 있지 않다. JavaThread::interrupt()가 이벤트 세 개를 아무리 깨워도 그 스레드에는 닿지 않는다. 그러면 채널은 무슨 수로 그 스레드를 꺼내는가. 이 절의 클래스·함수 이름과 순서는 OpenJDK 21의 유닉스 계열 구현이고, 명세가 보장하는 것은 아래에 인용하는 InterruptibleChannel Javadoc의 동작까지다.

    명세부터 보자. InterruptibleChannel의 Javadoc은 두 문단으로 동작을 정한다. 인터럽트 가능한 채널의 I/O에서 막힌 스레드를 다른 스레드가 인터럽트하면 채널이 닫히고, 막힌 스레드는 ClosedByInterruptException을 받으며, 그 스레드의 인터럽트 상태는 설정된 채로 남는다. 그리고 인터럽트 상태가 이미 켜진 스레드가 채널에서 블로킹 I/O를 시작하면, 채널이 닫히고 그 스레드는 즉시 ClosedByInterruptException을 받으며 상태는 그대로 남는다. sleep과 정반대로 상태를 지우지 않는다는 점, 그리고 끊기는 것이 "이번 읽기"가 아니라 "채널 전체"라는 점이 눈에 띈다. 실험으로 확인하자.

    import java.nio.ByteBuffer;
import java.nio.channels.*;
import java.nio.file.*;

public class PipeInterrupt {
    public static void main(String[] args) throws Exception {
        Pipe pipe = Pipe.open();
        Pipe.SourceChannel source = pipe.source();   // 아무도 쓰지 않으므로 read는 영원히 막힌다

        Thread reader = new Thread(() -> {
            try {
                source.read(ByteBuffer.allocate(16));
                System.out.println("read 반환");
            } catch (Exception e) {
                System.out.println("reader 예외 = " + e.getClass().getName());
                System.out.println("reader isInterrupted = " + Thread.currentThread().isInterrupted());
            }
        }, "reader");
        reader.start();
        Thread.sleep(300);
        System.out.println("interrupt 전 reader 상태 = " + reader.getState());
        long t0 = System.nanoTime();
        reader.interrupt();
        reader.join();
        System.out.printf("interrupt -> reader 종료: %.1f ms%n", (System.nanoTime() - t0) / 1e6);
        System.out.println("source.isOpen() = " + source.isOpen());
        try {
            source.read(ByteBuffer.allocate(16));
        } catch (Exception e) {
            System.out.println("main이 같은 채널을 읽으면 = " + e.getClass().getName());
        }

        // 이미 인터럽트된 스레드가 파일 채널을 읽는 경우
        Path tmp = Files.createTempFile("intr", ".txt");
        Files.writeString(tmp, "hello");
        FileChannel fc = FileChannel.open(tmp);
        Thread.currentThread().interrupt();
        try {
            fc.read(ByteBuffer.allocate(16));
            System.out.println("파일 read 성공");
        } catch (ClosedByInterruptException e) {
            System.out.println("파일 read -> ClosedByInterruptException, fc.isOpen() = " + fc.isOpen()
                + ", isInterrupted = " + Thread.currentThread().isInterrupted());
        }
        Files.delete(tmp);
    }
}

    reader는 System.in.read() 때와 마찬가지로 시스템 호출 안에서 기다리므로 RUNNABLE로 보고된다. 그런데 이번에는 인터럽트를 보내자 몇 밀리초 만에 빠져나왔고, 받은 예외는 ClosedByInterruptException이며, 인터럽트 상태는 true로 남았다. 채널은 닫혔다. 그래서 인터럽트와 아무 관계없는 main이 같은 채널을 읽으려 하자 예외가 났다. 이름이 AsynchronousCloseException인 것은 구현의 세부 때문이다. 읽기 시작 단계의 ensureOpen()이 ClosedChannelException을 던지지만, finally에서 부르는 end(false)가 "완료되지 않았는데 채널이 닫혀 있다"를 보고 AsynchronousCloseException(ClosedChannelException의 하위 클래스)을 던져 앞의 예외를 덮어쓴다. 마지막 줄은 Javadoc의 둘째 문단이다. 파일 읽기는 막힐 일이 없는 작업인데도, 인터럽트 상태가 켜진 스레드가 시작하자 데이터를 한 바이트도 읽지 않고 채널이 닫혔다.

    등록: begin()이 스레드에 "나를 닫으면 된다"고 걸어 둔다

    장치의 출발점은 java.nio.channels.spi.AbstractInterruptibleChannel의 begin()/end() 쌍이다. 블로킹 I/O를 하는 채널 구현은 시스템 호출 직전에 begin()을, 직후에 finally에서 end()를 부른다. OpenJDK 21의 begin()은 "이 채널을 닫는" 일을 하는 Interruptible 객체를 만들어, 앞에서 본 Thread.interrupt()의 마지막 단계가 읽는 바로 그 필드, 현재 스레드의 nioBlocker에 걸어 둔다(blockedOn). 그다음 현재 스레드가 이미 인터럽트된 상태인지 확인하고, 그렇다면 그 자리에서 직접 채널을 닫는다.

    // OpenJDK 21 java.nio.channels.spi.AbstractInterruptibleChannel (발췌)
protected final void begin() {
    if (interruptor == null) {
        interruptor = new Interruptible() {
                public void interrupt(Thread target) {
                    synchronized (closeLock) {
                        if (closed)
                            return;
                        closed = true;
                        interrupted = target;          // 누가 인터럽트로 닫았는지 기록
                        try {
                            AbstractInterruptibleChannel.this.implCloseChannel();
                        } catch (IOException x) { }
                    }
                }};
    }
    blockedOn(interruptor);                            // Thread.nioBlocker = interruptor
    Thread me = Thread.currentThread();
    if (me.isInterrupted())
        interruptor.interrupt(me);
}

protected final void end(boolean completed) throws AsynchronousCloseException {
    blockedOn(null);
    Thread interrupted = this.interrupted;
    if (interrupted != null && interrupted == Thread.currentThread()) {
        this.interrupted = null;
        throw new ClosedByInterruptException();
    }
    if (!completed && closed)
        throw new AsynchronousCloseException();
}

    begin() 마지막의 자기 확인이 필요한 이유는 둘이다. 첫째, Thread.interrupt()는 this != Thread.currentThread()일 때만 nioBlocker를 부른다. 스스로를 인터럽트한 스레드에서는 채널이 닫히지 않으므로, 다음 I/O를 시작할 때 begin()이 확인해야 한다. 실험의 파일 채널이 이 경로다. 둘째, 다른 스레드의 인터럽트가 등록 직전에 도착하는 경합이다. interrupt()는 상태를 true로 쓴 뒤 interruptLock을 잡고 nioBlocker를 읽는다(소스 주석: "Setting the interrupt status must be done before reading nioBlocker"). blockedOn()도 같은 interruptLock을 잡고 nioBlocker를 쓰며, begin()은 그 뒤에 상태를 읽는다. 락을 먼저 잡은 쪽이 interrupt()라면 상태 쓰기가 락 해제 전에 끝났으므로 begin()의 상태 확인이 true를 본다. blockedOn()이 먼저라면 interrupt()가 등록된 Interruptible을 본다. 어느 순서든 둘 중 하나는 반드시 상대를 본다. 앞에서 JVM_Sleep이 잠들기 전에 상태를 확인하던 것과 같은 "틈 없애기"를 자바 코드로 한 것이다.

    깨우기: 파일 디스크립터를 바꿔치기하고 신호를 쏜다

    인터럽트를 받은 Interruptible은 채널의 implCloseChannel()을 부른다. 이 메서드의 계약(Javadoc)은 "이 채널의 I/O에서 막힌 다른 스레드가 즉시 돌아오도록 조치해야 한다"이다. 파이프의 읽기 쪽 구현인 sun.nio.ch.SourceChannelImpl은 블로킹 읽기를 시작할 때 읽는 스레드의 네이티브 스레드 식별자(NativeThread.current(), 유닉스에서는 pthread_self())를 기록해 둔다. 닫기 요청이 왔을 때 진행 중인 읽기가 있으면, 소스 주석대로 파일 디스크립터를 "미리 닫고(pre-close)" 읽는 스레드에 신호를 보낸 뒤, 진짜 close는 읽는 스레드가 빠져나갈 때까지 미룬다. 그 두 동작이 네이티브 코드에 있다.

    • 미리 닫기: UnixDispatcher.c는 초기화 때 socketpair()로 소켓 한 쌍을 만들고 한쪽을 바로 닫아, "상대가 닫힌 소켓" 하나를 preCloseFD로 보관해 둔다. preClose0은 dup2(preCloseFD, fd)로 채널의 fd 번호가 그 죽은 소켓을 가리키게 바꾼다. 번호는 그대로이고 가리키는 대상만 바뀐다.
    • 신호: NativeThread.c의 signal0은 기록해 둔 스레드에 pthread_kill(thread, INTERRUPT_SIGNAL)을 보낸다. 신호 번호는 macOS 같은 BSD 계열에서 SIGIO, 리눅스에서 SIGRTMAX - 2다. 이 신호의 처리기는 아무것도 하지 않는 nullHandler이고, sa_flags = 0, 즉 SA_RESTART 없이 설치된다. macOS의 sigaction(2) 매뉴얼은 SA_RESTART를 켜야 통신 채널이나 느린 장치에서의 read 같은 호출이 재시작된다고 설명하고, read(2) 매뉴얼은 데이터가 오기 전에 신호가 전달되면 EINTR로 실패한다고 적는다. 처리기가 하는 일이 없어도 "신호가 왔다"는 사실만으로 커널 안의 read가 끝나는 것이다.

    macOS와 리눅스(supportPendingSignals0()이 false인 플랫폼)에서 UnixDispatcher.implPreClose는 fd 바꿔치기를 먼저 하고 신호를 나중에 보낸다. 신호가 도착했을 때 스레드가 아직 read에 들어가기 전이었더라도, 그 fd 번호는 이미 상대가 닫힌 소켓을 가리키므로 이어지는 read는 데이터를 기다리지 않고 0(EOF)을 돌려준다. 그런데 이 Mac(macOS)에서 같은 두 동작을 C로 따로 시험해 보면, 파이프 read에서 막힌 스레드는 신호만 보내도 -1(errno는 EINTR)로 끝나고, 신호 없이 dup2만 해도 그 자리에서 0을 돌려주며 끝난다. 그러니 앞의 자바 실험에서 실제로 read를 끝낸 것이 둘 중 어느 쪽인지는 이 실험만으로는 말할 수 없다. 다행히 어느 쪽이든 결과는 같다. 이제 읽는 쪽으로 돌아가자. 파이프의 읽기는 SocketDispatcher.c의 read0이 하고, 그 반환값을 IOUtil.c의 convertReturnVal이 바꾼다. 0이면 IOS_EOF(-1), EINTR이면 IOS_INTERRUPTED(-3)다. SourceChannelImpl.read()의 블로킹 루프는 while (IOStatus.okayToRetry(n) && isOpen())인데, EOF는 재시도할 코드가 아니고, INTERRUPTED는 재시도해도 되는 코드지만 채널이 이미 닫혔으므로, 어느 쪽이든 루프를 나간다. finally의 endRead()가 미뤄 둔 진짜 close를 하고(tryFinishClose), 마지막으로 end()가 "나를 닫은 인터럽트의 대상이 바로 나"임을 확인해 ClosedByInterruptException을 던진다. 이 경로 어디에도 getAndClearInterrupt()가 없으므로 인터럽트 상태는 켜진 채 남는다. 실험에서 본 세 가지(빠른 탈출, 예외 종류, 남은 상태)가 모두 이렇게 설명된다.

    이제 System.in이 끊기지 않은 이유가 정확히 보인다. OpenJDK 21에서 System.in은 FileDescriptor.in의 FileInputStream을 감싼 BufferedInputStream이고, 실제 읽기를 하는 FileInputStream의 read 메서드들은 네이티브 메서드(read0(), readBytes())를 부를 뿐 begin()/end()로 nioBlocker를 등록하지 않는다(그 둘레의 Blocker.begin()은 가상 스레드가 막힐 때 스케줄러가 캐리어 스레드를 보충하게 하는 장치이고 인터럽트와는 관계가 없다). 그래서 interrupt()는 상태를 켜고 HotSpot의 이벤트를 깨우는 데서 끝나고, 커널 안의 read에 신호를 보낼 주체가 없다. 반대로 채널 쪽의 대가도 분명하다. 인터럽트 한 번에 채널 자체가 닫히므로, 여러 스레드가 함께 쓰는 FileChannel이 있다면 그중 한 스레드를 인터럽트하는 것만으로 다른 스레드들의 I/O까지 실패한다. 실험에서 main의 읽기가 실패한 것이 그 모습이다. 인터럽트로 작업을 취소하는 스레드 풀 위에서 공유 채널을 쓸 때 이 점을 알고 있어야 한다.

    InterruptedException을 받았을 때의 규칙: 다시 던지거나, 복원하거나

    인터럽트 상태는 "누군가 이 스레드에 멈추라고 요청했다"는 정보를 담은 유일한 통로다. 그런데 InterruptedException이 던져지는 순간 그 통로는 비워진다. 그러니 예외를 잡은 코드가 아무것도 하지 않으면 요청이 영영 사라진다. 이것이 인터럽트 관련 버그의 가장 흔한 모양이다.

    public class Swallow {
    // 나쁜 예: 인터럽트를 삼킨다
    static void pauseSwallow(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            // 아무것도 하지 않는다
        }
    }

    // 좋은 예: 인터럽트 상태를 복원한다
    static void pauseRestore(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        }
    }

    static Thread start(String name, boolean restore) {
        Thread t = new Thread(() -> {
            while (!Thread.currentThread().isInterrupted()) {
                if (restore) pauseRestore(500);
                else pauseSwallow(500);
            }
            Log.log("멈춤");
        }, name);
        t.setDaemon(true);
        t.start();
        return t;
    }

    public static void main(String[] args) throws InterruptedException {
        Thread swallow = start("swallow", false);
        Thread restore = start("restore", true);
        Thread.sleep(200);

        swallow.interrupt();
        restore.interrupt();
        swallow.join(2000);
        restore.join(2000);

        Log.log("swallow 살아 있음 = " + swallow.isAlive());
        Log.log("restore 살아 있음 = " + restore.isAlive());
    }
}

01:45:55.081 [   main] swallow 살아 있음 = true
01:45:55.081 [   main] restore 살아 있음 = false

    두 스레드는 같은 루프를 돈다. 차이는 sleep을 감싼 도우미 메서드 하나다. 200밀리초 시점의 인터럽트는 두 스레드 모두 sleep(500) 안에서 받는다. swallow 쪽은 예외가 상태를 지운 뒤 catch 블록이 아무것도 하지 않으므로, 루프 조건 isInterrupted()는 false를 보고 계속 돈다. 2초를 기다려도 살아 있다. restore 쪽은 catch 블록에서 Thread.currentThread().interrupt()로 상태를 다시 켜 두었으므로, 도우미 메서드를 부른 쪽의 루프 조건이 그 상태를 보고 멈춘다. (swallow 스레드는 데몬으로 만들어 main이 끝나면 JVM이 종료되게 했다.)

    규칙은 두 가지 중 하나다. 첫째, 내 메서드가 throws InterruptedException을 선언할 수 있다면 잡지 말고 그대로 던져 호출자가 판단하게 한다. 대기하는 메서드를 감싸는 라이브러리 메서드라면 대부분 이쪽이 맞다. 둘째, 시그니처 때문에 던질 수 없다면(Runnable.run()처럼 체크 예외를 허용하지 않는 메서드를 구현하는 경우 등) 상태를 복원한다. 앞에서 인용한 JDK 문서는 이것을 "다시 던지기(rethrow)"가 아니라 "다시 주장하기(reassert)"라고 부르며, 즉시 처리할 준비가 되지 않은 메서드가 이 예외를 잡았다면 Thread.currentThread().interrupt();로 "스스로를 다시 인터럽트"해야 한다고 말한다. 그렇게 하면 스레드가 다음에 대기하는 곳에서 InterruptedException이 다시 일어나 요청이 위로 전달된다.

    반대로 인터럽트를 받은 그 자리에서 요청을 "처리"하는 코드라면 복원할 필요가 없다. run()의 최상위에서 예외를 잡고 정리한 뒤 스레드를 끝내는 코드가 그렇다. 요청은 "멈춰라"였고, 스레드가 실제로 멈추므로 요청은 이행되었다. 앞의 InterruptSleep이 이 모양이다. 판단 기준은 하나다. 이 catch 블록이 스레드의 다음 행동을 결정할 권한을 가진 코드인가. 아니라면 결정권을 가진 코드에게 상태를 넘겨야 한다.

    catch 블록에서 throw new RuntimeException(e)로 감싸 던지면 run()이 예외로 끝나 스레드가 종료되므로 "멈춘다"는 결과는 같다. 다만 인터럽트 상태는 이미 지워졌고, 예외는 스레드의 미처리 예외 처리기로 넘어가 스택 트레이스가 출력된다. 정상적인 취소를 오류처럼 보이게 만들므로, 취소가 예상된 흐름이라면 정리 코드로 끝내는 편이 의도를 잘 드러낸다.

    프린터 예제 1: 플래그로 멈추는 프린터

    지금까지의 도구를 하나의 작은 프로그램에 적용해 보자. 사용자가 문서 이름을 입력하면 프린터 스레드가 하나씩 꺼내 출력한다. 출력 한 건에는 3초가 걸린다고 가정하고 sleep(3000)으로 흉내 낸다. 사용자가 q를 입력하면 프로그램을 끝낸다. main 스레드는 입력을 받아 대기열에 넣는 역할, 프린터 스레드는 대기열에서 꺼내 출력하는 역할이다. 첫 버전은 앞에서 본 플래그 방식으로 멈춘다.

    import java.util.Queue;
import java.util.Scanner;
import java.util.concurrent.ConcurrentLinkedQueue;

public class PrinterV1 {
    public static void main(String[] args) throws InterruptedException {
        Printer printer = new Printer();
        Thread printerThread = new Thread(printer, "printer");
        printerThread.start();

        Scanner scanner = new Scanner(System.in);
        while (scanner.hasNextLine()) {
            String input = scanner.nextLine();
            if (input.equals("q")) {
                Log.log("종료 요청");
                printer.work = false;
                break;
            }
            printer.submit(input);
        }
        printerThread.join();
        Log.log("main 종료");
    }

    static class Printer implements Runnable {
        volatile boolean work = true;
        private final Queue jobs = new ConcurrentLinkedQueue<>();

        void submit(String doc) {
            jobs.offer(doc);
            Log.log("접수: " + doc);
        }

        @Override
        public void run() {
            while (work) {
                if (jobs.isEmpty()) {
                    continue;
                }
                String doc = jobs.poll();
                Log.log("출력 시작: " + doc);
                try {
                    Thread.sleep(3000); // 출력에 3초 걸린다고 가정
                } catch (InterruptedException e) {
                    throw new RuntimeException(e);
                }
                Log.log("출력 완료: " + doc);
            }
            Log.log("프린터 종료, 남은 문서 " + jobs.size() + "개");
        }
    }
}

    대기열로는 ConcurrentLinkedQueue를 썼다. main이 넣고 프린터가 꺼내므로 두 스레드가 동시에 접근하는 자료 구조가 필요하고, 일반 ArrayDeque나 LinkedList는 여러 스레드가 동시에 고치는 것을 전제로 만들어지지 않았다. 이 큐가 락 없이 어떻게 안전한지는 CAS와 동시성 컬렉션 회차에서 다룬다. 지금은 "여러 스레드가 동시에 offer와 poll을 해도 되는 큐"로만 쓴다. work에 volatile을 붙인 이유는 앞의 JLS §17.3 이야기와 같다.

    사람이 직접 입력하면 시각을 맞추기 어려우므로 셸에서 시간차를 두고 입력을 흘려 넣어 실행했다. doc1, 0.5초 뒤 doc2, 다시 0.5초 뒤 doc3, 그리고 3초 뒤 q다.

    첫 두 줄의 순서가 이상해 보일 수 있다. "출력 시작"이 "접수"보다 먼저 찍혔다. submit()은 offer를 하고 나서 로그를 찍는데, 그 사이에 프린터 스레드가 큐에서 문서를 꺼내 자기 로그를 먼저 찍은 것이다. 두 스레드의 로그 순서는 실행마다 바뀔 수 있다. 같은 밀리초에 찍힌 두 줄은 동시에 일어난 일로 읽으면 된다.

    중요한 것은 끝부분이다. 41.528에 종료를 요청했는데, 프린터는 doc2의 출력을 끝까지 마친 43.555에야 루프 조건을 확인하고 멈췄다. 사용자는 q를 눌렀는데 문서가 한 장 더 나온 셈이다. 출력이 3초가 아니라 30분짜리였다면 30분을 기다려야 한다. 플래그 방식의 응답 지연이 그대로 드러난다.

    이 코드에는 문제가 하나 더 숨어 있다. 대기열이 비었을 때의 루프다. jobs.isEmpty()가 true면 continue로 곧장 while (work)로 돌아가 다시 isEmpty()를 부른다. 할 일이 없는데도 이 스레드는 쉬지 않고 같은 확인을 반복한다. 이런 형태를 바쁜 대기(busy waiting)라고 한다. 운영체제가 보기에 이 스레드는 언제나 실행할 준비가 된 스레드이므로 CPU 코어 하나를 계속 차지한다. 이 문제는 프린터 예제 4에서 다시 다룬다.

    yield: CPU를 양보한다는 것

    이제 바쁜 대기 문제로 넘어가기 전에 이 회차의 두 번째 도구를 세우자. 스케줄링의 기본부터 다시 떠올리자. 운영체제 스케줄러는 실행할 준비가 된 스레드들을 대기열에 두고, CPU 코어마다 하나씩 골라 일정 시간(타임 슬라이스) 실행시킨다. 자바의 RUNNABLE은 이 두 상태, 즉 "지금 코어 위에서 실행 중"과 "실행 대기열에서 차례를 기다리는 중"을 구분하지 않는다. 둘 다 RUNNABLE이다. Thread.State.RUNNABLE의 Javadoc이 "프로세서 같은 운영체제 자원을 기다리고 있을 수 있다"고 적은 것이 이 뜻이다.

    Thread.yield()는 실행 중인 스레드가 "지금 내 차례를 다른 스레드에게 넘겨도 된다"고 스케줄러에게 알리는 메서드다. Javadoc의 첫 문장은 이렇다. 현재 스레드가 프로세서 사용을 양보할 의향이 있다는 스케줄러에 대한 힌트이며, 스케줄러는 이 힌트를 무시해도 된다. 이어서 yield는 CPU를 과하게 쓰는 스레드들 사이의 상대적 진행을 개선하려는 경험적(heuristic) 시도이고, 실제로 원하는 효과가 있는지 프로파일링과 벤치마크로 확인해야 하며, 이 메서드를 쓰는 것이 적절한 경우는 드물다고 적는다. 쓸모가 있을 수 있는 곳으로는 경합 조건 버그를 재현하는 디버깅·테스트와 java.util.concurrent.locks 패키지 같은 동시성 제어 구조의 설계를 든다.

    yield는 자바 스레드 상태를 바꾸지 않는다. WAITING이나 TIMED_WAITING이 되는 메서드 목록에 yield는 없다. 양보한 스레드는 계속 RUNNABLE이고, 운영체제 수준에서 "실행 중"에서 "실행 대기열의 뒤쪽"으로 옮겨질 뿐이다. 다음 차례가 오면 바로 다시 실행된다. 이 점이 sleep과의 결정적인 차이다. sleep은 스레드를 TIMED_WAITING으로 만들고 정한 시간 동안 실행 후보에서 아예 빼 버린다.

    OpenJDK 21에서 yield가 하는 일

    // OpenJDK 21 java.lang.Thread
public static void yield() {
    if (currentThread() instanceof VirtualThread vthread) {
        vthread.tryYield();
    } else {
        yield0();
    }
}

    가상 스레드(virtual thread)는 자기만의 양보 경로(tryYield)를 갖고, 이 회차가 다루는 플랫폼 스레드는 네이티브 메서드 yield0()로 간다. yield0는 JVM_Yield로 연결되고, JVM_Yield는 os::naked_yield()를 부른다. OpenJDK 21 HotSpot에서 os::naked_yield()는 POSIX 계열(리눅스, macOS 등, os_posix.cpp)에서는 sched_yield() 시스템 호출 한 줄이고, 윈도우(os_windows.cpp)에서는 SwitchToThread() 호출이다. 결국 자바의 yield는 운영체제의 양보 기능에 그대로 위임된다.

    그러니 yield가 정확히 무엇을 하는지는 운영체제가 정한다. 리눅스의 sched_yield(2) 매뉴얼은 이 호출이 호출한 스레드를 그 정적 우선순위의 대기열 맨 뒤로 보내고 새 스레드가 실행되게 한다고 설명한다. 그리고 주의 사항(CAVEATS)에 두 가지를 적는다. 호출한 스레드가 그 시점에 가장 높은 우선순위 목록에 혼자 있다면 호출 뒤에도 계속 실행된다. 또 sched_yield()는 실시간 스케줄링 정책(SCHED_FIFO, SCHED_RR)에서 쓰도록 만든 것이고, SCHED_OTHER 같은 비결정적 정책에서 쓰는 것은 동작이 규정되어 있지 않다. sched(7) 매뉴얼에 따르면 SCHED_OTHER는 실시간 장치가 필요 없는 모든 스레드를 위한 리눅스의 기본 시분할 정책이다. 실시간 정책을 따로 지정하지 않은 보통의 스레드라면 yield의 정확한 효과는 운영체제 문서로도 보장되지 않는다는 뜻이고, Javadoc이 "힌트"라고 부르는 이유와 맞아떨어진다.

    이번 실행은 일부러 대기열이 빈 상태에서 종료를 요청했다. doc1 출력이 54.791에 끝나고 55.723에 q가 들어올 때까지 프린터는 빈 대기열 앞에서 yield하며 돌고 있었다. 이때 인터럽트가 오면 예외는 생기지 않는다. yield는 인터럽트에 반응하지 않기 때문이다. 대신 다음 반복의 Thread.interrupted()가 true를 보고 루프가 끝난다. "출력 도중 인터럽트" 로그가 없는 것이 그 증거다. 예제 3에서 말한 "루프를 빠져나오는 두 번째 길"이 바로 이것이다.

    yield를 넣은 효과는 무엇일까. 프린터가 양보하면, 같은 코어를 기다리던 다른 스레드(입력을 처리할 main이나 다른 프로세스)가 차례를 더 빨리 얻을 수 있다. 하지만 기다리는 다른 스레드가 없으면 sched_yield 매뉴얼대로 프린터는 곧바로 다시 실행된다. 바쁜 대기는 여전히 바쁜 대기다. 이것을 숫자로 확인해 보자. 아래 프로그램은 같은 루프를 네 가지 방식으로 1초 동안 돌리고, 그 스레드가 실제로 쓴 CPU 시간을 ThreadMXBean.getCurrentThreadCpuTime()으로 잰다.

    import java.lang.management.ManagementFactory;

public class SpinCost {
    static volatile boolean stop;

    public static void main(String[] args) throws InterruptedException {
        for (String mode : new String[] {"busy", "yield", "onSpinWait", "sleep"}) {
            stop = false;
            long[] result = new long[2]; // [0] 반복 횟수, [1] CPU 시간(ns)
            Thread t = new Thread(() -> {
                long loops = 0;
                while (!stop) {
                    loops++;
                    switch (mode) {
                        case "yield" -> Thread.yield();
                        case "onSpinWait" -> Thread.onSpinWait();
                        case "sleep" -> {
                            try {
                                Thread.sleep(10);
                            } catch (InterruptedException e) {
                                return;
                            }
                        }
                        default -> { }
                    }
                }
                result[0] = loops;
                result[1] = ManagementFactory.getThreadMXBean().getCurrentThreadCpuTime();
            }, mode);
            t.start();
            Thread.sleep(1000);
            stop = true;
            t.join();
            System.out.printf("%-10s 반복 %,14d회  CPU %4d ms (벽시계 약 1000 ms)%n",
                    mode, result[0], result[1] / 1_000_000);
        }
    }
}

yield      반복      6,789,801회  CPU  990 ms (벽시계 약 1000 ms)
onSpinWait 반복    479,400,333회  CPU 1007 ms (벽시계 약 1000 ms)

    작업 스레드가 result 배열에 쓴 값을 main이 읽는 것은 t.join() 뒤이므로 안전하다. join()으로 종료를 확인한 쪽은 그 스레드의 모든 쓰기를 볼 수 있다(이 규칙도 다음 회차의 happens-before에서 정리한다). 측정값의 절대 크기는 의미가 없고 형태만 보자. 이 실행에서 바쁜 대기, yield, onSpinWait 세 방식은 모두 1초 동안 CPU를 거의 1초 썼다. 코어 하나를 통째로 붙잡았다는 뜻이다. yield는 반복 횟수를 크게 줄였다. 반복마다 시스템 호출을 하고 스케줄러를 거치므로 한 번의 반복이 훨씬 비싸졌기 때문이다. 그러나 이 기계에는 이 스레드 말고 코어를 원하는 스레드가 별로 없었으므로, 양보한 차례는 곧장 자기에게 돌아왔다. CPU를 덜 쓴 것은 sleep뿐이다. 반복 횟수가 100회가 아니라 73회인 것은 sleep(10)이 정확히 10밀리초만 자는 것이 아니기 때문이다. Javadoc의 표현대로 sleep은 "시스템 타이머와 스케줄러의 정밀도와 정확도에 따른다".

    Thread.onSpinWait()는 Java 9에서 JEP 285로 들어온 메서드다. 호출자가 바쁜 대기 루프 안에 있다는 것을 런타임에 알리는 순수한 힌트이고, 아무것도 하지 않는 구현도 올바른 구현이다(OpenJDK 21의 자바 소스 본문은 실제로 비어 있고, @IntrinsicCandidate가 붙어 JIT가 대체할 수 있다). JEP 285는 동기로 x86 프로세서의 PAUSE 명령을 든다. 스핀 루프에 이 명령을 넣으면 스레드 사이의 왕복 지연이 줄어든다는 것이다. 즉 onSpinWait는 "CPU를 내려놓는" 도구가 아니라 "CPU를 붙잡고 기다리되 더 효율적으로 기다리는" 도구다. 측정 결과에서 CPU 시간이 그대로인 것과 맞는다. 아주 짧은 대기가 예상되어 잠들고 깨는 비용조차 아까울 때 쓰는 것이다.

    그러면 프린터에는 무엇이 맞는가. 문서가 언제 들어올지 모르는 상황에서 원하는 동작은 이렇다. 대기열이 비면 잠들어서 CPU를 전혀 쓰지 않고, 문서가 들어오는 바로 그 순간 깨어난다. sleep(n)은 앞의 것은 만족하지만, 문서가 들어와도 n이 지날 때까지 깨지 못하므로 뒤의 것을 만족하지 못한다. n을 줄이면 반응은 빨라지지만 그만큼 자주 깨어 확인하므로 다시 바쁜 대기에 가까워진다. yield와 onSpinWait는 앞의 것을 만족하지 못한다.

    두 조건을 함께 만족하려면 "문서를 넣는 쪽이 자고 있는 프린터를 깨우는" 장치가 필요하다. 인터럽트가 "멈추라"는 신호로 잠을 깨웠듯이, "일감이 생겼다"는 신호로 잠을 깨우는 장치다. 그것이 Object.wait()와 notify(), Condition, 그리고 이것들을 감싼 BlockingQueue다. 생산자-소비자 회차에서 이 프린터와 같은 구조를 그 도구들로 다시 만든다. 그래서 예제 4의 yield는 최종 해법이 아니라 "바쁜 대기를 조금 완화한 중간 단계"로 이해하는 것이 정확하다. Javadoc이 yield를 쓰는 것이 적절한 경우가 드물다고 한 것도 같은 맥락에서 읽을 수 있다.

    가상 스레드에서는: 같은 API, 전혀 다른 구현

    지금까지 따라간 JVM_Sleep, _SleepEvent, sched_yield()는 모두 플랫폼 스레드, 즉 OS 스레드 하나에 일대일로 붙은 자바 스레드의 이야기였다. 이 권의 본론도 플랫폼 스레드다. 그런데 Java 21에서는 Thread.yield() 소스에서 이미 본 것처럼 가상 스레드(virtual thread)라는 다른 갈래가 있고, sleep도 같은 갈림길을 둔다. 같은 메서드가 아래에서 완전히 다른 기계로 구현되는 모습을 보면, 앞에서 "명세"와 "HotSpot 구현"을 굳이 나눠 적은 이유가 실감 난다. 이 절의 내용은 모두 OpenJDK 21의 java.lang.VirtualThread 소스 기준이다.

    // OpenJDK 21 java.lang.Thread (발췌)
public static void sleep(long millis) throws InterruptedException {
    // ... 음수 검사
    long nanos = MILLISECONDS.toNanos(millis);
    // ... JFR 이벤트 준비(beforeSleep), afterSleep을 부르는 try-finally는 생략
    if (currentThread() instanceof VirtualThread vthread) {
        vthread.sleepNanos(nanos);   // 자바 코드로 구현된 잠
    } else {
        sleep0(nanos);               // 네이티브: JVM_Sleep
    }
}

// OpenJDK 21 java.lang.VirtualThread (발췌)
void sleepNanos(long nanos) throws InterruptedException {
    if (getAndClearInterrupt())
        throw new InterruptedException();
    if (nanos == 0) {
        tryYield();
    } else {
        try {
            long remainingNanos = nanos;
            long startNanos = System.nanoTime();
            while (remainingNanos > 0) {
                parkNanos(remainingNanos);
                if (getAndClearInterrupt()) {
                    throw new InterruptedException();
                }
                remainingNanos = nanos - (System.nanoTime() - startNanos);
            }
        } finally {
            setParkPermit(true);     // 소스 주석: 자는 동안 unpark되었을 수 있다
        }
    }
}

    구조를 JavaThread::sleep_nanos와 나란히 놓으면 뼈대가 같다. 잠들기 전에 상태를 확인해 켜져 있으면 지우고 예외를 던진다. 남은 시간만큼 잠들고, 깨어날 때마다 먼저 인터럽트를 확인한 뒤 남은 시간을 다시 계산한다. sleep(0)은 양보로 바뀐다. "틈 없이 확인한다"는 성질은 그대로 지켜졌다. 다른 것은 잠드는 방법이다. parkNanos는 조건 변수에서 OS 스레드를 재우지 않는다. 먼저 VirtualThread-unparker라는 이름의 ScheduledThreadPoolExecutor(기본 스레드 1개, 시스템 속성 jdk.unparker.maxPoolSize로 조절)에 "n 나노초 뒤에 이 가상 스레드를 unpark하라"는 작업을 예약한다. 그다음 상태를 TIMED_PARKING으로 바꾸고 Continuation.yield로 자기 실행 스택(continuation)을 캐리어 스레드(carrier thread)에서 떼어 낸다. 캐리어 스레드는 가상 스레드를 실어 나르는 플랫폼 스레드로, 기본 스케줄러인 ForkJoinPool(FIFO 모드, 병렬도는 기본값이 availableProcessors()이고 jdk.virtualThreadScheduler.parallelism으로 바꿀 수 있다)의 작업 스레드다. 가상 스레드가 떨어져 나간 캐리어는 곧장 다른 가상 스레드를 실행한다. 다만 소스 주석대로, 캐리어에 고정(pinned)되어 떼어 낼 수 없는 경우에는 남은 시간 동안 캐리어 스레드 자체를 park한다(parkOnCarrierThread가 Unsafe.park를 부른다). 이때는 앞 절에서 본 HotSpot의 parker로 OS 스레드가 잠든다.

    인터럽트 쪽도 자바 코드다. VirtualThread.interrupt()는 interrupted = true를 쓰고, nioBlocker가 있으면 앞 절의 채널 닫기를 부르고, 가상 스레드가 캐리어에 올라가 있으면 캐리어의 인터럽트 상태도 켠 뒤(setInterrupt()는 interrupt0()으로 VM에 알린다), 마지막으로 unpark()를 부른다. unpark()는 대상이 PARKED나 TIMED_PARKED면 CAS로 상태를 UNPARKED로 바꾸고 continuation을 스케줄러에 다시 제출한다. 어느 캐리어가 그 작업을 집어 실행하면 가상 스레드는 parkNanos에서 돌아오고, sleepNanos의 루프가 상태를 확인해 예외를 던진다. pthread_cond_signal은 어디에도 없다.

        vt.start();
        Thread.sleep(200);
        System.out.println("interrupt 전 vt 상태 = " + vt.getState());
        vt.interrupt();
        vt.join();

    자바 수준에서 관찰되는 것, 즉 TIMED_WAITING 상태, InterruptedException, 예외 뒤 지워진 상태는 플랫폼 스레드와 똑같다. 이것이 Javadoc이 정한 계약이기 때문이다. 다른 것은 예외 메시지다. 가상 스레드 쪽은 new InterruptedException()이라 메시지가 null이고, 플랫폼 스레드 쪽은 HotSpot이 넣은 sleep interrupted다. 메시지는 명세가 정하지 않은 구현 세부라는 것을 이보다 분명하게 보여 주는 예는 드물다. 예외 메시지 문자열로 분기하는 코드를 짜면 안 되는 이유다.

    "잠든 동안 OS 스레드를 쓰지 않는다"는 것도 실험으로 보자. 병렬도를 1로 고정하고(-Djdk.virtualThreadScheduler.parallelism=1) 가상 스레드 1만 개가 각각 sleep(1000)을 하게 한 뒤, 0.5초 시점에 상태와 플랫폼 스레드 수를 센다.

    import java.lang.management.ManagementFactory;
import java.util.*;

public class ManySleep {
    public static void main(String[] args) throws Exception {
        List list = new ArrayList<>();
        long t0 = System.nanoTime();
        for (int i = 0; i < 10_000; i++) {
            list.add(Thread.ofVirtual().start(() -> {
                try { Thread.sleep(1000); } catch (InterruptedException e) { }
            }));
        }
        Thread.sleep(500);
        Set carriers = new TreeSet<>();
        for (Thread t : Thread.getAllStackTraces().keySet()) {   // 플랫폼 스레드만 돌려준다
            if (t.getName().startsWith("ForkJoinPool") || t.getName().startsWith("VirtualThread")) carriers.add(t.getName());
        }
        System.out.println("자고 있는 가상 스레드 수 = " + list.stream().filter(t -> t.getState() == Thread.State.TIMED_WAITING).count());
        System.out.println("JVM의 플랫폼 스레드 수 = " + ManagementFactory.getThreadMXBean().getThreadCount());
        System.out.println("스케줄러 관련 플랫폼 스레드 = " + carriers);
        for (Thread t : list) t.join();
        System.out.printf("전체 소요 = %d ms%n", (System.nanoTime() - t0) / 1_000_000);
    }
}

    1만 개가 모두 TIMED_WAITING인데 JVM 전체의 플랫폼 스레드는 8개(main, 참조 처리, 시그널 처리 같은 JVM 기본 스레드 포함)이고, 그중 가상 스레드 스케줄링에 관련된 것은 캐리어 1개와 unparker 1개다. 캐리어가 하나뿐인데도 1만 개의 잠이 약 1초 만에 끝났다. 플랫폼 스레드로 같은 일을 하면 OS 스레드 1만 개가 각자 조건 변수에서 잠들어야 한다. 가상 스레드의 잠은 "OS 스레드를 재우는 것"이 아니라 "실행할 작업 목록에서 잠시 빠지는 것"이다.

    가상 스레드의 yield는 실제로 차례를 넘긴다

    yield에서 차이는 더 극적이다. 플랫폼 스레드의 yield는 sched_yield()라는 운영체제 힌트였고, 효과는 운영체제 문서로도 보장되지 않았다. 가상 스레드의 tryYield()는 상태를 YIELDING으로 바꾸고 Continuation.yield로 캐리어에서 내려온 뒤, afterYield()에서 상태를 YIELDED로 바꾸고 자기 continuation을 스케줄러에 다시 제출한다(캐리어의 로컬 작업 큐가 비어 있으면 ForkJoinPool.externalSubmit으로, 아니면 execute로). 양보한 가상 스레드는 스케줄러에 다시 제출되므로, 그사이 캐리어는 이미 제출되어 기다리던 다른 가상 스레드를 집어 실행할 수 있다. 캐리어 OS 스레드는 이 과정에서 sched_yield()를 부르지 않는다. 캐리어를 하나로 고정하고 두 가상 스레드가 세 번씩 기록을 남기게 해 보자.

    public class VirtualYield {
    public static void main(String[] args) throws Exception {
        boolean yield = args.length > 0;
        StringBuffer order = new StringBuffer();
        Runnable task = () -> {
            String name = Thread.currentThread().getName();
            for (int i = 1; i <= 3; i++) {
                order.append(name).append(i).append(' ');
                if (yield) Thread.yield();
            }
        };
        Thread a = Thread.ofVirtual().name("A").unstarted(task);
        Thread b = Thread.ofVirtual().name("B").unstarted(task);
        a.start();
        b.start();
        a.join();
        b.join();
        System.out.println((yield ? "yield 있음: " : "yield 없음: ") + order);
    }
}
    yield 없음: A1 A2 A3 B1 B2 B3
yield 있음: A1 B1 A2 B2 A3 B3

    캐리어가 하나뿐이므로 yield가 없으면 A가 끝날 때까지 B는 캐리어를 얻지 못한다. yield를 넣으면 A가 한 번 기록할 때마다 큐의 B에게 캐리어가 넘어가 둘이 번갈아 실행된다. 이 환경에서 yield를 넣은 경우를 20번 실행해 20번 모두 같은 순서가 나왔다. 그러나 이것은 OpenJDK 21의 스케줄러 구현과 병렬도 1이라는 조건이 만든 결과이고, Javadoc은 플랫폼 스레드와 가상 스레드를 구분하지 않고 yield를 스케줄러가 무시할 수 있는 힌트라고만 정한다. 병렬도를 기본값으로 두면 A와 B가 서로 다른 캐리어에서 동시에 돌 수 있으므로 이 순서는 나오지 않을 수 있다. 뒤의 흔한 오해 목록에 나오는 "yield하면 다른 스레드가 반드시 먼저 실행된다"는 가상 스레드에서도 오해다. 다만 "yield가 실제로 무엇을 하는가"의 답은 플랫폼 스레드(sched_yield, 효과는 OS 재량)와 가상 스레드(스케줄러 큐에 재제출)가 완전히 다르다.

    흔한 오해 바로잡기

    "interrupt()를 부르면 스레드가 멈춘다"

    멈추지 않는다. interrupt()가 하는 일은 상태 비트를 켜는 것과 인터럽트 가능한 대기를 끊는 것뿐이다. 계산 중인 스레드는 계속 계산하고, 대기에서 깨어난 스레드도 InterruptedException을 잡아 무시하면 계속 실행된다. 멈추는 것은 대상 스레드의 코드가 그렇게 짜여 있을 때뿐이다. 이것이 이 회차 첫머리에서 말한 협조적 취소의 뜻이다.

    "인터럽트하면 InterruptedException이 발생한다"

    예외는 sleep, join, wait처럼 인터럽트를 확인하도록 정의된 메서드 안에서만, 또는 그 메서드에 들어갈 때 상태가 이미 켜져 있을 때만 발생한다. 계산 중이거나 synchronized 락을 기다리거나 InputStream에서 읽는 중이면 상태만 켜지고 예외는 없다. 예외가 생기는 지점은 대상 스레드의 코드 안이지, 인터럽트를 보낸 쪽이 아니다.

    "t.interrupted()는 t의 상태를 확인한다"

    interrupted()는 정적 메서드이므로 어떤 참조로 부르든 현재 스레드를 검사하고, 게다가 상태를 지운다. 앞의 StaticCall 실행 결과처럼 엉뚱한 스레드의 인터럽트 요청을 소비해 버릴 수 있다. 다른 스레드를 관찰할 때는 t.isInterrupted()를 쓴다.

    "InterruptedException은 귀찮으니 잡아서 무시해도 된다"

    무시하는 순간 그 스레드에 대한 멈춤 요청이 사라진다. Swallow 예제의 스레드는 인터럽트를 받고도 영원히 돈다. 스레드 풀 같은 상위 구조가 인터럽트로 작업을 취소하려 할 때 이런 코드가 하나라도 있으면 취소가 동작하지 않는다. 던지거나, 복원하거나, 그 자리에서 스레드를 끝내거나 셋 중 하나를 고른다.

    "sleep이나 yield를 넣으면 다른 스레드가 바꾼 값을 다시 읽는다"

    JLS §17.3은 둘에 동기화 의미가 없다고 명시한다. sleep을 넣은 루프가 우연히 잘 동작하더라도 그것은 명세가 보장한 결과가 아니다. 여러 스레드가 함께 보는 플래그에는 volatile이나 다른 동기화가 필요하다. 인터럽트 상태처럼 JDK가 동기화를 보장하는 장치를 쓰면 이 고민을 덜 수 있다.

    "yield하면 다른 스레드가 반드시 먼저 실행된다"

    yield는 힌트이고 스케줄러는 무시해도 된다. 리눅스 매뉴얼은 같은 우선순위에 다른 후보가 없으면 호출한 스레드가 계속 실행된다고 적는다. 코어가 여러 개라면 다른 스레드는 이미 다른 코어에서 돌고 있을 수도 있다. yield에 순서를 맡기는 코드는 어떤 순서도 보장받지 못한다. 순서가 필요하면 join, 락, 조건 대기 같은 동기화 수단을 쓴다.

    정리: 이 회차가 다음 회차들과 이어지는 곳

    이 회차에서 세운 그림을 한 줄로 줄이면 이렇다. 스레드를 밖에서 멈추게 하는 안전한 방법은 요청을 남기고 깨우는 것뿐이며, 자바는 그 요청을 인터럽트 상태라는 불리언 하나와 대기 이벤트를 깨우는 신호로 구현한다. 그리고 양보는 스레드 상태를 바꾸지 않는 운영체제 수준의 힌트다. 이 두 가지는 이 권의 나머지 회차에서 계속 다시 나온다.

    • 메모리 가시성: 이 회차에서 "자세한 것은 다음 회차"라고 미뤄 둔 것들, 즉 플래그에 volatile이 필요한 이유, JLS §17.3의 "깨진 루프", 인터럽트와 join이 만드는 happens-before가 다음 회차의 본론이다.
    • 동기화와 Lock: synchronized 락을 기다리는 BLOCKED 스레드는 인터럽트로 깨울 수 없었다. ReentrantLock은 lockInterruptibly()로 이 제약을 푼다. 그 아래에 있는 LockSupport.park()는 이 회차에서 본 parker() 이벤트에서 잠들고, 인터럽트로 깨어난다.
    • 생산자-소비자: 프린터 예제 4에서 남긴 숙제인 "일감이 생기면 깨우기"를 wait/notify, Condition, BlockingQueue로 푼다. JLS §17.2.3이 말한 "대기 집합에서 빠져나와 InterruptedException을 던진다"는 규칙과, wait()의 가짜 깨어남이 그때 다시 나온다.
    • 스레드 풀과 Executor: ExecutorService.shutdownNow()의 Javadoc은 실행 중인 작업을 멈추려 최선을 다할 뿐 보장하지 않으며, 일반적인 구현은 Thread.interrupt로 취소하므로 인터럽트에 반응하지 않는 작업은 영원히 끝나지 않을 수 있다고 적는다. Future.cancel(true)의 mayInterruptIfRunning도 같은 장치다. 이 회차에서 배운 "인터럽트에 반응하는 작업을 짜는 법"이 그대로 스레드 풀을 우아하게 종료하는 조건이 된다.
    이 장의 핵심

    잠든 스레드는 어떤 코드도 실행하지 않으므로 공유 플래그를 확인할 수 없다. 인터럽트는 상태 비트를 켜고 sleep·wait·join·park의 대기를 깨워 이 틈을 메우며, 대기 메서드는 들어갈 때와 깨어날 때 모두 상태를 확인하므로 요청이 새어 나가지 않는다. 예외를 던질 때 상태가 지워지므로, 예외를 잡은 코드는 다시 던지거나 상태를 복원하거나 그 자리에서 스레드를 끝내야 한다. yield는 상태를 RUNNABLE로 둔 채 운영체제에 차례를 넘기겠다는 힌트일 뿐이어서, 바쁜 대기의 근본 해법은 깨워 주는 쪽이 있는 대기다.
    협조적 취소
    자바는 스레드를 밖에서 강제로 끊지 않는다. 밖에서는 요청만 보내고, 대상 스레드가 안전한 지점에서 요청을 확인해 스스로 정리하고 끝난다. Java 21의 Thread.stop()은 항상 UnsupportedOperationException을 던진다.
    플래그 방식의 한계
    잠든 스레드는 플래그를 확인하는 코드조차 실행하지 않으므로, 최악의 응답 지연은 잠자는 시간만큼이다. 플래그에는 volatile이 필요하다(JLS §17.3: sleep과 yield에는 동기화 의미가 없다).
    인터럽트 상태
    OpenJDK 21에서 Thread의 volatile boolean interrupted 필드. interrupt()가 켜고, InterruptedException 발생과 Thread.interrupted()가 지운다. isInterrupted()는 읽기만 한다.
    인터럽트로 끊기는 대기
    sleep, join, wait(예외), LockSupport.park(반환), InterruptibleChannel I/O, Selector. 모니터 락 획득(BLOCKED)과 InputStream 읽기는 끊기지 않는다.
    HotSpot의 깨우기 경로
    interrupt0 → JVM_Interrupt → JavaThread::interrupt()가 _SleepEvent, parker, _ParkEvent를 모두 unpark한다. JVM_Sleep은 잠들기 전과 깨어난 뒤에 상태를 확인하므로 요청이 새지 않는다.
    예외 처리 규칙
    InterruptedException을 잡았으면 다시 던지거나, Thread.currentThread().interrupt()로 상태를 복원하거나, 그 자리에서 스레드를 끝낸다. 무시하면 요청이 사라진다.
    인터럽트의 happens-before
    JLS §17.4.4: T1의 인터럽트는 T2가 인터럽트되었음을 감지하는 지점과 synchronizes-with 관계다. 인터럽트 전에 한 쓰기는 감지 후에 보인다.
    yield
    스케줄러에 대한 힌트이고 무시될 수 있다. 상태는 RUNNABLE을 유지한다. OpenJDK 21 플랫폼 스레드에서는 POSIX sched_yield(), 윈도우 SwitchToThread()로 위임된다. 인터럽트와 무관하다.
    인터럽트 가능한 채널
    OpenJDK 21에서 채널은 begin()으로 스레드의 nioBlocker에 "채널 닫기"를 걸어 두고, 인터럽트가 오면 fd를 죽은 소켓으로 dup2하고 신호(pthread_kill)를 보내 커널 안의 read를 끝낸다. 채널 전체가 닫히고 인터럽트 상태는 남는다.
    바쁜 대기
    조건을 쉬지 않고 확인하는 루프. yield와 onSpinWait를 넣어도 CPU를 계속 쓴다. 근본 해법은 조건이 바뀔 때 깨워 주는 대기(wait/notify, BlockingQueue)다.

    운영 중인 서비스에서 "배포할 때 애플리케이션이 종료되지 않고 강제 종료(kill -9)될 때까지 버틴다"는 증상을 만나면, 가장 먼저 의심할 곳이 인터럽트에 반응하지 않는 작업이다. 스레드 풀의 종료 과정은 작업 스레드에 인터럽트를 보내는 방식으로 취소를 시도하는데, 작업 코드 어딘가에 catch (InterruptedException e) {}가 있거나, 인터럽트로 끊기지 않는 블로킹 I/O에서 기다리고 있으면 요청이 닿지 않는다. 스레드 덤프를 떠서 남아 있는 스레드가 어디에서 무슨 상태로 멈춰 있는지 보면, 이 회차에서 본 구분(TIMED_WAITING (sleeping)인지, BLOCKED인지, I/O 안의 RUNNABLE인지)이 원인을 바로 좁혀 준다.

    라이브러리나 공통 유틸리티를 만들 때는 인터럽트 정책을 호출자에게 넘기는 것이 기본이다. 대기를 포함하는 메서드라면 throws InterruptedException을 선언하는 것이 가장 정직하다. 시그니처를 바꿀 수 없다면 상태를 복원한다. 반대로 스레드를 직접 소유하는 코드(자기가 만든 스레드의 run() 최상위)만이 "인터럽트를 받으면 끝낸다"는 결정을 내릴 수 있다. 이 구분이 흐려지면 공통 코드 한 곳의 빈 catch 블록이 시스템 전체의 취소를 망가뜨린다.

    yield를 보면 일단 의심하는 것이 맞다. 동시성 코드에서 yield가 문제를 "해결"한 것처럼 보이면, 대개 실행 순서를 우연히 바꿔 경합 조건이 덜 드러나게 만든 것이다. 그 경우 진짜 해법은 올바른 동기화다. 바쁜 대기를 완화하려고 yield를 넣었다면 CPU 사용량을 실제로 재 보고, 대부분은 깨워 주는 대기 구조로 바꾸는 편이 낫다. 다만 대기 시간이 매우 짧다고 확신할 수 있는 저수준 동기화 코드에서는 잠들고 깨는 비용을 피하려고 짧게 스핀하는 설계가 쓰이고, 그때 onSpinWait가 의미를 갖는다. 판단의 기준은 "기다리는 시간이 잠들고 깨는 비용보다 짧은가"다.

    1번. true, false, false다. 첫 Thread.interrupted()는 켜진 상태를 읽어 true를 돌려주면서 상태를 지운다(getAndClearInterrupt는 true를 읽었을 때만 지운다). 두 번째 호출은 지워진 상태를 읽으므로 false이고, 지울 것이 없으니 그대로 둔다. 마지막 isInterrupted()는 읽기만 하므로 false다. Javadoc의 "연속으로 두 번 부르면 두 번째는 false" 설명 그대로다.

    2번. 인터럽트는 대부분 sleep(1000) 중에 도착한다. 이때 InterruptedException이 던져지면서 상태가 false로 지워지고, catch 블록은 로그만 찍는다. 루프 조건 isInterrupted()는 false를 보고 계속 돈다. 고치는 방법 하나는 catch 블록에서 Thread.currentThread().interrupt();로 상태를 복원해 루프 조건이 보게 하는 것이고, 다른 하나는 try-catch를 루프 바깥으로 옮겨 예외가 루프 전체를 빠져나가게 하는 것이다(또는 catch에서 break). doWork() 실행 중에 인터럽트가 도착하는 경우는 상태가 남아 있으므로 다음 sleep이 즉시 예외를 던지고, 결국 같은 catch 블록에서 같은 문제가 생긴다.

    3번. 플래그 방식: worker는 0초, 5초, 10초에 깨어 플래그를 확인한다. main이 7초에 플래그를 내리므로 5초의 확인은 true, 10초의 확인에서 false를 보고 10초에 종료한다. 응답 지연 3초. 인터럽트 방식: 7초에 worker는 5초에 시작한 두 번째 잠 속에 있고, interrupt()가 잠을 즉시 끊으므로 7초에 종료한다(정확히는 깨우기와 스케줄링에 걸리는 아주 짧은 시간 뒤).

    4번. 인터럽트는 상태를 true로 켜고 이벤트를 깨운다. 아직 잠들지 않았으니 깨울 대상은 없다. 프린터가 이어서 Thread.sleep(3000)을 부르면 JVM_Sleep은 잠들기 전에 is_interrupted(true)로 상태를 확인하고, true이므로 상태를 지우고 곧바로 InterruptedException("sleep interrupted")을 던진다. 루프 바깥의 catch가 "출력 도중 인터럽트"를 찍고 프린터가 끝난다. 3초를 기다리지 않는다. PrinterV1이었다면 프린터는 이미 while (work)를 통과했으므로 3초를 다 자고 "출력 완료"를 찍은 뒤에야 플래그를 보고 멈춘다. 확인과 잠들기 사이의 틈을 인터럽트는 메우고 플래그는 메우지 못한다.

    5번. sched_yield는 호출한 스레드를 같은 우선순위 대기열의 뒤로 보낼 뿐, 실행 후보에서 빼지 않는다. 다른 실행 후보가 없으면 호출한 스레드가 곧바로 다시 실행되므로, 루프는 시스템 호출을 끼운 채 계속 돈다. SpinCost의 측정처럼 CPU 시간이 벽시계 시간과 비슷하게 나온다. 필요한 것은 대기열이 비면 실행 후보에서 빠져 잠들고(CPU 0), 문서를 넣는 쪽이 잠든 프린터를 깨워 주는 장치다. Object.wait()/notify(), Condition, BlockingQueue.take()가 그것이며 생산자-소비자 회차의 주제다.

     스레드 A가 Thread.sleep(5000) 중일 때 스레드 B가 a.interrupt()를 호출했다. A의 catch 블록 첫 줄에서 Thread.currentThread().isInterrupted()를 부르면 무엇이 반환되는가? true. 인터럽트를 받았으므로 상태가 켜져 있다. false. InterruptedException을 던지면서 인터럽트 상태가 지워졌다. B가 interrupt()를 부른 직후인지 아닌지에 따라 매번 다르다. isInterrupted()를 catch 블록에서 부르면 다시 InterruptedException이 발생한다. sleep의 Javadoc은 이 예외를 던질 때 현재 스레드의 인터럽트 상태를 지운다고 명시한다. HotSpot의 sleep_nanos도 is_interrupted(true)로 읽으면서 지운다. 따라서 catch 블록에서는 false다(그 사이에 누군가 다시 인터럽트하지 않았다면). 결과가 실행마다 달라지지 않으며, isInterrupted()는 예외를 던지지 않는 단순한 읽기다. 다음 중 다른 스레드가 interrupt()를 호출했을 때 대기가 즉시 끝나는 경우는? synchronized 블록에 들어가려고 모니터 락을 기다리는 BLOCKED 스레드 System.in.read()에서 입력을 기다리는 스레드 다른 스레드에 대해 join()을 호출하고 기다리는 스레드 긴 반복문으로 계산 중인 스레드 interrupt()의 Javadoc은 wait, join, sleep 중인 스레드가 InterruptedException을 받는다고 정한다. 모니터 락 획득은 그 목록에 없어 실험에서도 BLOCKED가 유지되었고, InputStream은 InterruptibleChannel이 아니어서 read()가 끊기지 않았다. 계산 중인 스레드는 상태만 켜지고, 코드가 직접 확인하지 않으면 계속 실행된다. main 스레드에서 worker.interrupt(); 다음 줄에 if (worker.interrupted()) { ... }라고 썼다. 이 조건식이 실제로 하는 일은? worker의 인터럽트 상태를 읽고 지운다. worker의 인터럽트 상태를 읽기만 한다. 컴파일 오류가 난다. 정적 메서드는 인스턴스로 부를 수 없다. main 스레드 자신의 인터럽트 상태를 읽고, 켜져 있었다면 지운다. interrupted()는 정적 메서드이고 현재 스레드를 검사한다. 자바는 정적 메서드를 인스턴스 참조로 부르는 것을 허용하므로 컴파일은 되며(-Xlint에서 경고), 참조 worker는 무시된다. 따라서 main의 상태를 읽고 지운다. worker의 상태를 읽기만 하려면 worker.isInterrupted()를 써야 한다. OpenJDK 21의 플랫폼 스레드에서 Thread.yield()에 대한 설명으로 옳은 것은? 스레드 상태는 RUNNABLE로 유지되고, POSIX 계열에서는 sched_yield()로 위임되며, 다른 실행 후보가 없으면 곧바로 다시 실행될 수 있다. 스레드 상태가 잠시 TIMED_WAITING이 되었다가 돌아온다. 인터럽트 상태가 켜져 있으면 InterruptedException을 던진다. 호출 전에 쓴 공유 변수의 값을 다른 스레드가 볼 수 있게 메모리에 반영한다. yield는 TIMED_WAITING이 되는 메서드 목록에 없고, JVM_Yield → os::naked_yield() → sched_yield()로 이어진다. sched_yield 매뉴얼은 같은 우선순위에 다른 스레드가 없으면 계속 실행된다고 적는다. yield는 체크 예외를 선언하지 않고 인터럽트 상태를 건드리지 않으며(실험에서 상태가 true로 남았다), JLS §17.3은 yield에 동기화 의미가 없다고 명시한다. 작업 스레드가 while (!stopRequested) { Thread.sleep(1000); }를 돈다. stopRequested는 volatile이 아닌 필드이고 다른 스레드가 true로 바꾼다. JLS §17.3에 비추어 옳은 설명은? sleep이 매번 메모리를 새로 읽게 하므로 늦어도 1초 안에 루프가 끝난다. sleep 때문에 컴파일 오류가 난다. sleep과 yield에는 동기화 의미가 없으므로, 컴파일러가 필드를 한 번만 읽고 재사용해 루프가 끝나지 않을 수 있다. sleep 중에는 캐시가 비워지므로 volatile이 없어도 항상 안전하다. JLS §17.3은 바로 이 형태의 코드를 "깨진" 예로 들며, 컴파일러가 sleep 전후로 레지스터의 값을 내보내거나 다시 읽을 의무가 없으므로 필드를 한 번만 읽어 루프가 끝나지 않을 수 있다고 설명한다. 해결책은 volatile 등 동기화이며, 그 원리는 메모리 가시성 회차의 주제다.
    인터럽트(interrupt)
    한 스레드가 다른 스레드에 작업 중단을 요청하는 자바의 장치. 대상의 인터럽트 상태를 켜고, 인터럽트 가능한 대기 중이면 그 대기를 끊는다. CPU 하드웨어 인터럽트와는 관계가 없다.
    인터럽트 상태(interrupt status)
    스레드마다 하나씩 있는 불리언 값. interrupt()가 켜고 Thread.interrupted()와 InterruptedException 발생이 지운다.
    InterruptedException
    sleep, join, wait 등이 인터럽트를 감지했을 때 던지는 체크 예외. 던져질 때 인터럽트 상태는 지워진다.
    협조적 취소(cooperative cancellation)
    취소를 요청하는 쪽은 신호만 보내고, 대상이 안전한 지점에서 신호를 확인해 스스로 멈추는 방식.
    양보(yield)
    실행 중인 스레드가 CPU 차례를 넘기겠다고 스케줄러에 알리는 힌트. 스레드 상태는 바뀌지 않으며 스케줄러는 무시할 수 있다.
    바쁜 대기(busy waiting)
    조건이 만족될 때까지 잠들지 않고 반복해서 확인하는 대기. 기다리는 동안 CPU를 계속 쓴다. 스핀(spin)이라고도 한다.
    실행 대기열(run queue)
    운영체제 스케줄러가 실행할 준비가 된 스레드를 모아 두는 자료 구조. 자바의 RUNNABLE은 실행 중인 스레드와 이 대기열의 스레드를 모두 포함한다.
    가짜 깨어남(spurious wakeup)
    통지나 인터럽트, 시간 만료 없이 대기가 끝나는 현상. Object.wait()와 LockSupport.park()에서 허용되므로 조건을 루프로 다시 확인해야 한다.
    캐리어 스레드(carrier thread)
    가상 스레드를 실어 실행하는 플랫폼 스레드. OpenJDK 21에서는 기본 스케줄러 ForkJoinPool의 작업 스레드이며, 가상 스레드가 sleep이나 yield로 내려오면 다른 가상 스레드를 실행한다.
    스핀 대기 힌트(Thread.onSpinWait)
    Java 9(JEP 285)에서 추가된, 바쁜 대기 루프 안에 있음을 런타임에 알리는 메서드. CPU를 내려놓지 않으며, 아무것도 하지 않는 구현도 허용된다.
