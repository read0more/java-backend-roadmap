    잔액 1000원, 두 번의 800원 출금

    앞 회차에서는 한 스레드가 쓴 값을 다른 스레드가 보지 못하는 메모리 가시성 문제를 다뤘다. volatile을 붙이면 쓰기와 읽기가 메인 메모리 수준에서 순서가 맞춰져, 한 스레드가 쓴 값을 다른 스레드가 확실히 보게 된다. 그런데 "보이기만 하면" 충분한 경우는 생각보다 적다. 여러 스레드가 같은 값을 읽고, 그 값을 근거로 판단하고, 다시 쓰는 순간 전혀 다른 종류의 문제가 생긴다. 이 회차는 그 문제를 은행 계좌의 출금이라는 가장 익숙한 장면에서 시작한다.

    규칙은 단순하다. 출금하려는 금액이 잔액보다 크면 출금을 거절하고, 그렇지 않으면 잔액에서 출금액을 뺀다. 잔액이 1000원인 계좌에서 800원을 한 번 빼면 200원이 남고, 두 번째 800원 출금은 잔액 부족으로 거절되어야 한다. 한 스레드로 실행하면 이 규칙은 언제나 지켜진다. 아래 코드는 이 규칙을 그대로 옮긴 계좌 클래스다. 검증과 출금 사이에 1초를 쉬게 한 것은, 실제 시스템에서 이 사이에 외부 시스템 호출이나 DB 접근 같은 시간이 드는 일이 끼어든다는 것을 흉내 낸 것이다.

    public class Account {
    private int balance;

    public Account(int initialBalance) {
        this.balance = initialBalance;
    }

    public boolean withdraw(int amount) {
        log("검증 시작: 출금액=" + amount + ", 잔액=" + balance);
        if (balance < amount) {
            log("검증 실패: 잔액 부족");
            return false;
        }
        log("검증 통과: 출금액=" + amount + ", 잔액=" + balance);
        sleep(1000); // 출금 처리에 시간이 걸린다고 가정
        balance = balance - amount;
        log("출금 완료: 출금액=" + amount + ", 잔액=" + balance);
        return true;
    }

    public int getBalance() {
        return balance;
    }

    static void sleep(long millis) {
        try {
            Thread.sleep(millis);
        } catch (InterruptedException e) {
            throw new RuntimeException(e);
        }
    }

    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }
}
    public class WithdrawMain {
    public static void main(String[] args) throws InterruptedException {
        Account account = new Account(1000);
        Runnable task = () -> account.withdraw(800);
        Thread t1 = new Thread(task, "t1");
        Thread t2 = new Thread(task, "t2");
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        System.out.println("최종 잔액: " + account.getBalance());
    }
}

    두 스레드는 같은 Account 인스턴스 하나를 공유한다. 람다 task가 지역 변수 account를 캡처하고, 두 Thread 객체가 같은 task를 받았으므로 둘 다 힙에 있는 같은 계좌 객체의 withdraw를 호출한다. join()은 두 스레드가 끝날 때까지 main 스레드를 기다리게 한다. 이 원고를 쓰며 JDK 21(Temurin 21.0.13, macOS arm64)에서 같은 프로그램을 세 번 실행했더니 결과가 두 가지로 갈렸다.

    무엇이 꼬였는가: 두 실행 순서의 추적

    결과가 왜 갈리는지 보려면 withdraw를 두 스레드가 실제로 어떤 순서로 실행했는지 한 줄씩 엇갈려 그려 봐야 한다. 먼저 두 결과에 공통인 앞부분이다. 두 스레드는 거의 동시에 시작해 둘 다 잔액 1000을 읽고, 둘 다 1000 < 800이 거짓이므로 검증을 통과한다. 그리고 둘 다 sleep(1000)에 들어간다. 이 시점에 이미 운명은 정해졌다. 두 스레드 모두 "잔액이 충분하다"는 판단을 마친 상태로 잠들었기 때문이다. 판단의 근거였던 잔액 1000은 곧 바뀌지만, 이미 내린 판단은 바뀌지 않는다.

    경합 조건: sleep을 빼도 문제는 남는다

    이처럼 여러 스레드가 공유 자원에 접근할 때 결과가 실행 순서(타이밍)에 따라 달라지는 상황을 경합 조건(race condition)이라고 한다. 예제의 sleep(1000)은 경합이 일어나는 틈을 1초로 크게 벌려, 거의 매번 문제를 재현하기 위한 장치다. 그렇다면 sleep을 지우면 문제가 사라질까. 사라지지 않는다. 틈이 1초에서 수 나노초로 좁아질 뿐이다. 운영체제의 스케줄러는 어느 명령어 사이에서든 스레드를 CPU에서 내릴 수 있고(1회차의 컨텍스트 스위칭), 멀티코어에서는 두 스레드가 아예 같은 순간에 서로 다른 코어에서 같은 코드를 실행한다. 틈이 좁으면 재현 빈도가 낮아지지만, 하루에 수백만 건을 처리하는 서버에서는 낮은 빈도도 결국 일어난다. 그리고 그때는 재현하기 어려운 장애로 나타난다.

    틈이 얼마나 좁아도 문제가 되는지는 숫자 하나를 세는 코드로 쉽게 확인할 수 있다. 앞 회차에서 배운 volatile을 붙인 필드를 두 스레드가 각각 100만 번씩 증가시킨다. 검증도, sleep도 없는, 덧셈 한 줄짜리 코드다.

    public class VolCounter {
    private volatile int count;

    public static void main(String[] args) throws InterruptedException {
        VolCounter c = new VolCounter();
        Runnable r = () -> {
            for (int i = 0; i < 1_000_000; i++) {
                c.count++;
            }
        };
        Thread t1 = new Thread(r), t2 = new Thread(r);
        t1.start(); t2.start();
        t1.join(); t2.join();
        System.out.println("count = " + c.count);
    }
}

    기대값 2,000,000에 한참 못 미친다. 정확한 값은 실행마다, 기계마다 다르므로 숫자 자체에는 의미가 없다. 의미 있는 것은 "2,000,000보다 작다"는 사실이다. count++ 역시 getfield, iconst_1, iadd, putfield로 나뉘는 읽기-수정-쓰기이고, 그 사이에 다른 스레드의 읽기와 쓰기가 끼어들면 증가분이 사라진다. 이 실험에서 javap -c로 람다 본문을 열면 실제로 getfield와 putfield 사이에 iconst_1과 iadd가 끼어 있는 것을 볼 수 있다.

    여기서 중요한 교훈은 volatile이 이 문제를 해결하지 못한다는 점이다. volatile은 각각의 읽기와 쓰기가 다른 스레드에 보이도록 보장할 뿐, "읽기부터 쓰기까지"를 하나로 묶어 주지는 않는다. t1이 읽은 뒤 쓰기 전에 t2가 읽는 것을 막는 장치가 volatile에는 없다. 앞 회차의 문제가 가시성(visibility)이었다면 이 회차의 문제는 원자성(atomicity)이다. 원자적(atomic)이라는 말은 어떤 연산이 중간 상태를 남기지 않고, 다른 스레드가 볼 때 "전혀 실행되지 않았거나 완전히 실행되었거나" 둘 중 하나로만 보인다는 뜻이다. 출금의 "검증부터 차감까지", 카운터의 "읽기부터 쓰기까지"를 원자적으로 만들어야 한다.

    경합 조건(race condition)과 데이터 경합(data race)은 다른 말이다. JLS 17.4.5는 데이터 경합을 happens-before 관계로 순서가 정해지지 않은 두 충돌 접근(같은 변수에 대한 접근 중 하나 이상이 쓰기)으로 정의한다. 데이터 경합이 없다고 해서 경합 조건까지 없어지는 것은 아니다. JLS 17.4.3은 순차 일관성이나 데이터 경합이 없다는 성질만으로는, 원자적으로 보여야 하는 여러 동작의 묶음이 원자적이지 않아서 생기는 오류를 막지 못한다고 적는다. 둘 다 없애야 프로그램이 올바르다.

    임계 영역: 한 번에 한 스레드만 들어가야 하는 구간

    문제를 해결하려면 먼저 "어디를" 보호해야 하는지 정확히 짚어야 한다. 여러 스레드가 함께 쓰는 자원(공유 자원)에 접근하며, 동시에 둘 이상의 스레드가 실행하면 결과가 깨지는 코드 구간을 임계 영역(critical section)이라고 한다. 임계 영역에 대한 요구 사항은 하나다. 어느 순간에도 그 구간을 실행하는 스레드는 최대 하나여야 한다. 이것을 상호 배제(mutual exclusion)라고 부른다. 상호 배제가 지켜지면 임계 영역 전체가 다른 스레드가 보기에 하나의 원자적 연산처럼 동작한다.

    임계 영역을 찾는 첫 단계는 "무엇이 공유되는가"를 판정하는 것이다. 2회차에서 본 JVM 런타임 데이터 영역의 구분이 그대로 판정 기준이 된다. 지역 변수와 매개변수는 그 메서드를 호출한 스레드의 JVM 스택 프레임에 있으므로 다른 스레드가 접근할 방법이 없다. 반면 인스턴스 필드는 힙의 객체 안에 있고, 정적 필드는 클래스에 하나뿐이므로 그 객체나 클래스에 닿을 수 있는 모든 스레드가 접근한다. 한 가지 주의할 점은 지역 변수가 "참조"를 담고 있을 때다. 참조 값 자체는 스레드 전용이지만, 그 참조가 가리키는 힙 객체는 다른 스레드도 같은 참조를 가지고 있다면 공유된다. 예제의 람다가 캡처한 account가 바로 그 경우다.

    인스턴스 필드힙의 객체 안그 객체를 참조하는 모든 스레드가 공유한다
    정적 필드클래스 단위로 하나모든 스레드가 공유한다

    두 번째 단계는 공유 자원에 대한 접근 중 "함께 묶여야 하는 범위"를 정하는 것이다. 출금 예제에서 공유 자원은 balance 하나다. 그런데 balance를 읽는 곳(검증)과 쓰는 곳(차감)을 각각 따로 보호하는 것으로는 부족하다. 검증에서 읽은 값이 차감할 때까지 유효해야 하기 때문이다. 그래서 임계 영역은 검증에서 balance를 처음 읽는 지점부터 차감 결과를 쓰는 지점까지다. 그 사이에 끼어 있는 sleep(1000)도 임계 영역 안에 포함된다. 반대로 첫 번째 로그(검증 시작)를 찍기 전의 일이나 출금이 끝난 뒤의 일은 balance와 무관하므로 임계 영역 밖에 두어도 된다.

    public boolean withdraw(int amount) {
    log("검증 시작 ...");                    ← balance를 읽어 로그에 쓰지만 판단에 쓰이지 않는다
  ┌─────────────────────────────────────── 임계 영역 시작
  │ if (balance < amount) { ... return false; }   ← 읽기 (판단의 근거)
  │ sleep(1000);
  │ balance = balance - amount;                ← 읽기-수정-쓰기
  └─────────────────────────────────────── 임계 영역 끝
    log("출금 완료 ...");
    return true;
}

    임계 영역을 정확히 정하는 것은 생각보다 어렵다. 너무 좁게 잡으면(예: 차감 한 줄만 보호) 검사 후 행동 경합이 남는다. 너무 넓게 잡으면(예: 메서드 전체와 그 메서드가 부르는 느린 외부 호출까지) 정확하기는 하지만 스레드들이 줄을 서서 하나씩 지나가게 되어 멀티스레드를 쓰는 의미가 줄어든다. 정확성이 먼저이고, 성능은 정확성을 지킨 범위 안에서 좁혀 가는 문제다. 이 균형은 뒤에서 synchronized 블록을 다룰 때 다시 본다.

    일상에서 가져온 비유열쇠가 하나뿐인 공용 회의실

    공용 회의실 문 옆에 열쇠가 하나 걸려 있다. 회의실을 쓰려면 열쇠를 가져가야 하고, 열쇠가 없으면 문 앞에서 기다린다. 다 쓴 사람이 열쇠를 걸어 두면 기다리던 사람 중 하나가 가져간다. 회의실 안이 임계 영역이고, 열쇠가 락이다. 이 비유가 깨지는 지점도 있다. 실제 회의실은 문이 잠겨 있어 열쇠 없이 들어갈 수 없지만, 자바의 락은 "열쇠를 가지러 오는 사람끼리만" 순서를 정한다. 락을 거치지 않는 코드는 아무 제약 없이 같은 필드를 읽고 쓸 수 있다. 또 기다리는 사람 중 누가 먼저 열쇠를 가져가는지는 정해져 있지 않다.

    모니터 락: 모든 객체에 붙어 있는 락

    자바는 상호 배제를 위한 가장 기본적인 장치를 언어 자체에 넣어 두었다. JLS 17.1은 스레드 사이의 통신 수단 중 가장 기본적인 것이 동기화(synchronization)이고, 이것이 모니터(monitor)로 구현된다고 적는다. 그리고 규칙을 다음처럼 정한다. 자바의 모든 객체는 모니터 하나와 연결되어 있고, 스레드는 그 모니터를 잠그거나(lock) 풀 수(unlock) 있다. 한 번에 한 스레드만 모니터의 락을 가질 수 있으며, 같은 모니터를 잠그려는 다른 스레드는 락을 얻을 수 있을 때까지 블록(block)된다.

    이 규칙에서 눈여겨볼 단어는 "모든 객체"다. 자바에서는 new Object()로 만든 아무 객체나, 계좌 객체 자신이나, 클래스를 나타내는 Class 객체나 모두 락으로 쓸 수 있다. 락을 위한 별도의 타입을 만들 필요가 없다는 것은 편리하지만, 대가가 있다. JVM은 모든 객체에 대해 "이 객체가 지금 잠겨 있는가, 누가 잠갔는가"를 기록할 자리를 어딘가에 마련해야 한다. HotSpot이 이 자리를 어떻게 마련하는지는 이 회차 뒷부분에서 객체 헤더를 열어 본다. 이 자리를 흔히 "객체의 모니터 락", "고유 락(intrinsic lock)"이라고 부른다. 이 강좌에서는 JLS의 표현을 따라 모니터 락이라고 부른다.

    JLS 17.1은 한 가지를 더 정한다. 스레드 t는 같은 모니터를 여러 번 잠글 수 있고, 각 unlock은 lock 한 번의 효과를 되돌린다. 즉 모니터 락은 "누가 가졌는가"와 함께 "몇 번 잠갔는가"라는 횟수를 가진다. 이미 락을 가진 스레드가 같은 락을 다시 요청하면 기다리지 않고 횟수만 늘어난다. 이 성질을 재진입(reentrancy)이라고 하며, 뒤에서 왜 이것이 꼭 필요한지 예제로 확인한다. 자바 언어에서 모니터를 잠그는 방법은 두 가지다. 메서드에 synchronized 수정자를 붙이는 방법과, synchronized (식) { ... } 문장을 쓰는 방법이다.

    synchronized 메서드

    먼저 메서드 쪽이다. 계좌 클래스의 withdraw와 getBalance에 synchronized만 붙인다. 나머지 코드는 한 글자도 바꾸지 않는다.

    public class SyncAccount {
    private int balance;

    public SyncAccount(int initialBalance) {
        this.balance = initialBalance;
    }

    public synchronized boolean withdraw(int amount) {
        log("검증 시작: 출금액=" + amount + ", 잔액=" + balance);
        if (balance < amount) {
            log("검증 실패: 잔액 부족");
            return false;
        }
        log("검증 통과: 출금액=" + amount + ", 잔액=" + balance);
        sleep(1000);
        balance = balance - amount;
        log("출금 완료: 출금액=" + amount + ", 잔액=" + balance);
        return true;
    }

    public synchronized int getBalance() {
        return balance;
    }

    // sleep(), log()는 Account와 같다
    // ...
}

    이번에는 t1의 로그 세 줄이 끝난 뒤에야 t2의 로그가 시작된다. 어느 스레드가 먼저 락을 잡을지는 실행마다 다를 수 있지만(t2가 먼저 잡으면 이름만 바뀐 같은 결과가 나온다), 한 스레드의 출금이 다른 스레드의 출금 중간에 끼어드는 일은 더 이상 일어나지 않는다. 그리고 나중에 들어간 스레드는 앞 스레드가 남긴 잔액 200을 보고 정확하게 출금을 거절한다. 최종 잔액은 항상 200이고, 출금 성공은 항상 한 번이다.

    JLS 17.1과 8.4.3.6은 synchronized 메서드가 잠그는 모니터를 이렇게 정한다. 인스턴스 메서드면 메서드가 호출된 그 인스턴스, 즉 본문에서 this가 될 객체의 모니터를 잠근다. static 메서드면 그 메서드가 정의된 클래스를 나타내는 Class 객체의 모니터를 잠근다. 그리고 본문이 정상적으로 끝나든 예외 등으로 갑자기(abruptly) 끝나든, 같은 모니터에 대해 unlock이 자동으로 수행된다. 이 정의에서 바로 따라 나오는 결론이 있다. 락은 메서드에 붙는 것이 아니라 객체에 붙는다. 같은 계좌 객체에 대해서는 withdraw와 getBalance가 같은 락(그 계좌의 모니터)을 쓰므로 서로를 배제하지만, 계좌 A의 withdraw와 계좌 B의 withdraw는 서로 다른 락을 쓰므로 동시에 실행된다.

    이 결론을 실험으로 확인해 보자. 정적 synchronized 메서드 하나와 인스턴스 synchronized 메서드 하나를 가진 클래스를 만들고, 서로 다른 조합으로 네 스레드를 띄워 0.1초 뒤 상태를 찍는다. 각 메서드는 락을 잡은 채 1초를 쉰다.

    public class TwoLocks {
    static synchronized void staticWork() { pause(); }   // TwoLocks.class 의 모니터
    synchronized void instanceWork() { pause(); }        // this 의 모니터

    public static void main(String[] args) throws Exception {
        TwoLocks a = new TwoLocks();
        TwoLocks b = new TwoLocks();
        Thread t1 = new Thread(TwoLocks::staticWork, "static");
        Thread t2 = new Thread(a::instanceWork, "a");
        Thread t3 = new Thread(b::instanceWork, "b");
        Thread t4 = new Thread(a::instanceWork, "a-again");
        t1.start(); t2.start(); t3.start();
        Thread.sleep(100);
        t4.start();
        Thread.sleep(100);
        for (Thread t : new Thread[]{t1, t2, t3, t4}) {
            System.out.println(t.getName() + " : " + t.getState());
        }
        System.exit(0);
    }

    static void pause() {
        try { Thread.sleep(1000); } catch (InterruptedException e) { }
    }
}
    static : TIMED_WAITING
a : TIMED_WAITING
b : TIMED_WAITING
a-again : BLOCKED

    정적 메서드를 실행하는 스레드, 객체 a의 메서드를 실행하는 스레드, 객체 b의 메서드를 실행하는 스레드는 서로 다른 세 모니터(TwoLocks.class, a, b)를 잠그므로 셋 다 동시에 메서드 안으로 들어가 sleep 중이다(TIMED_WAITING). 오직 a의 모니터를 두 번째로 요청한 a-again만 BLOCKED 상태로 기다린다. 정적 메서드와 인스턴스 메서드가 같은 클래스에 있다고 해서 서로를 배제하지 않는다는 점, 그리고 sleep은 락을 놓지 않는다는 점(Thread.sleep의 Javadoc과 JLS 17.3이 모두 "모니터의 소유권을 잃지 않는다"고 명시한다)을 함께 확인할 수 있다. 정적 필드를 인스턴스 synchronized 메서드로 보호하려는 실수가 바로 이 지점에서 생긴다. 인스턴스마다 락이 다르므로 정적 필드는 전혀 보호되지 않는다.

    getBalance에도 synchronized가 필요한 이유

    getBalance는 값을 읽기만 하는데 왜 synchronized를 붙였을까. 이유는 두 가지다. 첫째, JLS 14.19는 어떤 객체의 락을 얻는 것이 그 자체로는 다른 스레드가 그 객체의 필드에 접근하거나 synchronized가 아닌 메서드를 호출하는 것을 막지 않는다고 명시한다. 락은 "같은 락을 요청하는 코드끼리"의 약속이다. synchronized가 없는 getBalance는 출금이 진행되는 도중에도 언제든 실행될 수 있다. 둘째, 더 중요한 이유는 가시성이다. 뒤에서 자세히 보겠지만 synchronized가 보장하는 가시성은 "같은 모니터를 unlock한 스레드와 그 뒤에 lock한 스레드" 사이에서만 성립한다. 락을 거치지 않고 읽는 스레드는 다른 스레드가 쓴 최신 잔액을 본다는 보장을 받지 못한다. 앞 회차의 가시성 문제가 그대로 돌아오는 것이다.

    synchronized 메서드의 본문에는 락과 관련된 명령어가 하나도 없다. 앞에서 본 synchronized가 없는 출금 코드와 명령어가 똑같다. 차이는 메서드의 접근 플래그에 있다. flags에 ACC_SYNCHRONIZED(0x0020)가 켜져 있다. 0x0021은 ACC_PUBLIC(0x0001)과 이 플래그를 더한 값이고, 정적 메서드의 0x0029는 여기에 ACC_STATIC(0x0008)이 더해진 값이다.

    JVMS 2.11.10이 이 플래그의 의미를 정한다. 메서드 수준의 동기화는 메서드 호출과 반환의 일부로 암묵적으로 수행된다. 메서드 호출 명령어(invokevirtual 등)가 이 플래그를 확인하고, 플래그가 켜져 있으면 실행 중인 스레드가 모니터에 들어간 뒤 메서드를 실행하고, 메서드가 정상적으로 끝나든 갑자기 끝나든 모니터에서 나온다. 메서드가 처리하지 않은 예외가 던져지면, 그 예외가 메서드 밖으로 다시 던져지기 전에 모니터가 자동으로 해제된다. 어느 객체의 모니터인지는 언어 규칙과 같다. 인스턴스 메서드면 수신 객체(지역 변수 0번의 this), 정적 메서드면 그 클래스의 Class 객체다. 즉 synchronized 메서드에서 락을 잡고 놓는 일은 컴파일러가 아니라 JVM의 호출·반환 메커니즘이 책임진다.

    스레드 덤프나 스택 트레이스에서 synchronized 메서드의 프레임은 락을 기다리는 중에도 그 메서드 이름으로 찍힌다. 아래 덤프에서 락을 기다리는 t2의 맨 위 프레임이 withdraw로 보이는 이유다. 아직 본문의 첫 명령어도 실행하지 않았지만, JVMS가 말하는 대로 모니터 진입이 "호출의 일부"이기 때문이다.

    락을 기다리는 스레드: BLOCKED 상태

    synchronized 출금 예제에서 t1이 락을 잡고 1초를 쉬는 동안 t2는 무엇을 하고 있었을까. 3회차와 4회차에서 본 스레드 상태(Thread.State) 가운데 지금까지 자세히 다루지 않은 상태가 하나 있었다. 바로 BLOCKED다. Thread.State.BLOCKED의 Javadoc은 이 상태를 모니터 락을 기다리며 블록된 스레드의 상태로 정의하고, 구체적으로 synchronized 블록이나 메서드에 들어가려고 기다리는 경우와 Object.wait를 호출한 뒤 synchronized 블록에 다시 들어가려고 기다리는 경우를 든다. 뒤의 경우는 8회차(생산자 소비자 문제)에서 다룬다. 이 회차에서 만나는 것은 앞의 경우다.

    스레드 덤프로 직접 확인해 보자. 5초를 쉬는 synchronized 출금 메서드를 두 스레드가 0.1초 간격으로 호출하게 하고, 실행 1.5초쯤에 jstack으로 덤프를 찍었다. 아래는 두 스레드 부분만 발췌한 것이다(주소, 스레드 번호, 시간 값은 실행마다 다르다).

    BLOCKED는 3회차의 WAITING, TIMED_WAITING과 성격이 다르다. 가장 큰 차이는 인터럽트에 대한 반응이다. sleep이나 join으로 기다리는 스레드는 인터럽트를 받으면 InterruptedException과 함께 깨어난다. 모니터 락을 기다리는 스레드는 그렇지 않다. 다음 실험에서 holder 스레드가 락을 2초 동안 쥐고 있는 동안, 락을 기다리는 waiter 스레드를 인터럽트해 본다.

    public class BlockedMain {
    static final Object lock = new Object();

    public static void main(String[] args) throws Exception {
        Thread holder = new Thread(() -> {
            synchronized (lock) {
                sleep(2000);
            }
        }, "holder");
        Thread waiter = new Thread(() -> {
            synchronized (lock) {
                System.out.println("waiter 진입, interrupted=" + Thread.currentThread().isInterrupted());
            }
        }, "waiter");

        holder.start();
        Thread.sleep(100);
        waiter.start();
        Thread.sleep(100);
        System.out.println("holder=" + holder.getState() + ", waiter=" + waiter.getState());
        System.out.println("main holdsLock=" + Thread.holdsLock(lock));

        waiter.interrupt();
        Thread.sleep(100);
        System.out.println("interrupt 후 waiter=" + waiter.getState() + ", isInterrupted=" + waiter.isInterrupted());

        holder.join();
        waiter.join();
        System.out.println("끝: waiter=" + waiter.getState());
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); }
    }
}

    인터럽트를 받은 뒤에도 waiter는 여전히 BLOCKED다. 인터럽트 플래그는 켜졌지만(isInterrupted=true) 락을 기다리는 일은 중단되지 않는다. waiter는 holder가 2초를 다 쉬고 락을 놓은 뒤에야 블록 안으로 들어가고, 들어간 뒤에 플래그가 켜져 있음을 확인할 수 있을 뿐이다. Thread.holdsLock(obj)은 현재 스레드가 그 객체의 모니터 락을 가지고 있는지 알려 주는 정적 메서드로, main 스레드는 이 락을 가진 적이 없으므로 false다. 이 실험의 출력 순서는 각 단계 사이에 0.1초씩 쉬게 해 둔 덕분에 거의 항상 같지만, 엄밀히는 스케줄링에 따라 달라질 수 있다.

    정리하면 모니터 락을 기다리는 스레드에게는 두 가지 출구가 없다. 시간 제한이 없으므로 "1초만 기다려 보고 안 되면 포기한다"를 표현할 수 없고, 인터럽트로도 깨어나지 않으므로 바깥에서 기다림을 취소할 수 없다. 락을 쥔 스레드가 영원히 놓지 않으면(예를 들어 락을 쥔 채 응답 없는 외부 시스템을 기다리면) 기다리는 스레드도 영원히 기다린다. JLS 17.1은 자바 언어가 교착 상태(deadlock)를 막지도, 감지를 요구하지도 않는다고 명시한다. 이 한계는 다음 회차에서 ReentrantLock의 tryLock과 lockInterruptibly가 등장하는 이유가 된다.

    하나의 객체에 연결된 모니터가 소유 스레드 하나와 진입 대기 스레드들(BLOCKED)을 가진다는 것, 그리고 unlock 뒤 대기 스레드들이 다시 경쟁한다는 것을 보여 준다. A structural diagram on a white background.     synchronized 블록: 임계 영역만 잠근다

    synchronized 메서드는 메서드 전체를 임계 영역으로 만든다. 하지만 앞에서 정한 출금의 임계 영역은 메서드 전체가 아니라 "검증에서 차감까지"였다. 메서드 앞뒤에 임계 영역과 무관한 일(로그, 요청 파싱, 결과 변환)이 길게 붙어 있다면, 그 시간 동안에도 다른 스레드가 기다려야 한다. 이럴 때 쓰는 것이 synchronized 문(synchronized statement), 흔히 synchronized 블록이라 부르는 형태다. 잠글 객체를 괄호 안에 직접 지정하고, 중괄호 안의 코드만 임계 영역으로 만든다.

    public boolean withdraw(int amount) {
    log("거래 시작: 출금액=" + amount);
    synchronized (this) {
        log("검증 시작: 출금액=" + amount + ", 잔액=" + balance);
        if (balance < amount) {
            log("검증 실패: 잔액 부족");
            return false;
        }
        sleep(1000);
        balance = balance - amount;
        log("출금 완료: 출금액=" + amount + ", 잔액=" + balance);
    }
    log("거래 종료");
    return true;
}

    "거래 시작" 로그는 두 스레드가 동시에 찍는다. 이 줄은 블록 밖에 있어 락 없이 실행되기 때문이다. 반면 "검증 시작"부터 "출금 완료"까지는 한 스레드씩 차례로 실행된다. 이번 실행에서는 t2가 먼저 락을 잡았다. 어느 쪽이 먼저인지는 실행마다 다르지만, 결과는 항상 출금 한 번 성공, 한 번 거절이다. 또 하나 눈여겨볼 곳은 return false다. 블록 한가운데에서 메서드를 빠져나가는데, 락은 어떻게 풀릴까. JLS 14.19는 synchronized 문의 실행 규칙을 이렇게 정한다.

    1. 괄호 안의 식(Expression)을 먼저 평가한다. 식의 타입이 참조형이 아니면 컴파일 오류다.
    2. 식의 평가가 갑자기 끝나면(예외), synchronized 문도 같은 이유로 갑자기 끝난다. 값이 null이면 NullPointerException이 던져진다.
    3. 그렇지 않으면 그 값 V의 모니터를 잠그고 블록을 실행한다.
    4. 블록이 정상적으로 끝나면 모니터를 풀고 정상 완료한다. 블록이 어떤 이유로든(return, break, 예외) 갑자기 끝나면 모니터를 풀고 같은 이유로 갑자기 완료한다.

    그러니 return false로 빠져나가도 락은 풀린다. 그런데 앞에서 synchronized 메서드의 락 해제는 JVM의 호출·반환 메커니즘이 책임진다고 했다. 블록은 누가 책임질까. 바이트코드를 보면 답이 나온다.

JVMS 2.11.10은 synchronized 블록을 제대로 구현하려면 JVM을 대상으로 하는 컴파일러의 협력이 필요하다고 적는다. 그 협력의 내용이 바로 이것이다. 메서드 동기화는 JVM이 알아서 해제해 주지만, 블록 동기화는 javac가 모든 출구에 monitorexit를 직접 깔아 둔다. 같은 장은 "구조적 잠금(structured locking)"이라는 말로, 한 메서드 호출 동안 어떤 모니터에 대한 진입 횟수와 해제 횟수가 일치해야 한다는 규칙을 JVM이 강제해도 되지만 강제할 의무는 없다고 정한다. 자바 컴파일러가 만든 코드는 이 규칙을 항상 지킨다.

    무엇을 락으로 쓸 것인가

    블록은 잠글 객체를 마음대로 고를 수 있다는 점에서 메서드보다 유연하지만, 그만큼 잘못 고를 여지도 생긴다. 판단의 기준은 하나다. 같은 공유 자원을 보호하는 모든 코드는 같은 객체를 잠가야 한다. 출금 예제에서 synchronized (this)를 쓴 이유는 getBalance가 synchronized 메서드, 즉 this의 모니터를 쓰기 때문이다. 블록에서 다른 객체를 잠그면 출금과 잔액 조회가 서로를 배제하지 못한다.

    this를 잠그는 방식에는 약점이 하나 있다. 그 객체에 대한 참조를 가진 외부 코드도 같은 객체를 잠글 수 있다는 점이다. 누군가 계좌 객체를 받아 synchronized (account) { ... } 안에서 오래 걸리는 일을 하면, 그동안 계좌의 모든 synchronized 메서드가 멈춘다. 이를 막으려면 외부에 노출되지 않는 전용 락 객체를 둔다. private final Object lock = new Object();를 필드로 두고 모든 임계 영역에서 synchronized (lock)을 쓰는 방식이다. final로 선언하는 것은 락 필드에 다른 객체가 대입되어 스레드마다 다른 객체를 잠그는 사고를 막기 위해서다. 다만 이렇게 하면 메서드에 synchronized를 붙이는 방식과 섞어 쓸 수 없다는 점을 기억해야 한다. 메서드 수정자는 항상 this를 잠그기 때문이다.

    피해야 할 락 객체도 있다. 첫째는 Integer, Long 같은 박싱 클래스와 LocalDate 같은 값 기반 클래스(value-based class)의 인스턴스다. 이런 객체는 같은 값이면 같은 인스턴스가 재사용될 수 있어(예: Integer.valueOf의 캐시) 전혀 무관한 코드와 락을 공유하게 될 수 있다. JDK 21의 javac는 이런 코드에 대해 아무 옵션 없이도 경고를 낸다.

    둘째는 문자열 리터럴이다. 같은 내용의 문자열 리터럴은 서로 다른 클래스에 있어도 같은 String 인스턴스를 가리킨다. 실제로 클래스 A와 B에 각각 static final String LOCK = "LOCK";을 두고 두 참조를 ==로 비교하면 true가 나온다. 각자 자기 락이라고 생각한 두 코드가 사실은 같은 모니터를 두고 경쟁하게 된다. 셋째는 getClass()의 결과처럼 하위 클래스에서 다른 객체가 될 수 있는 식이다. 상속 구조에서 부모와 자식이 서로 다른 Class 객체를 잠가 배제가 깨진다. 정적 공유 자원을 보호할 때는 클래스 리터럴(Account.class)이나 정적 final 락 객체처럼 항상 같은 객체로 평가되는 식을 쓴다.

    재진입: 같은 스레드는 다시 들어갈 수 있다

    앞에서 JLS 17.1이 "스레드는 같은 모니터를 여러 번 잠글 수 있다"고 정한다고 했다. 이 규칙이 왜 필요한지는 synchronized 메서드가 같은 객체의 다른 synchronized 메서드를 호출하는 흔한 코드를 보면 알 수 있다.

    public class ReentrantMain {
    private int balance = 1000;

    public synchronized void transferOut(int amount) {
        System.out.println("transferOut: holdsLock=" + Thread.holdsLock(this));
        withdraw(amount);   // 같은 객체의 다른 synchronized 메서드
    }

    public synchronized void withdraw(int amount) {
        System.out.println("withdraw: holdsLock=" + Thread.holdsLock(this));
        balance -= amount;
    }

    public static void main(String[] args) {
        ReentrantMain a = new ReentrantMain();
        a.transferOut(300);
        System.out.println("balance=" + a.balance + ", 끝난 뒤 holdsLock=" + Thread.holdsLock(a));
    }
}
    transferOut: holdsLock=true
withdraw: holdsLock=true
balance=700, 끝난 뒤 holdsLock=false

    transferOut에 들어갈 때 main 스레드는 객체 a의 락을 얻었다. 그 안에서 withdraw를 호출하면 다시 a의 락을 요청한다. 만약 모니터 락이 "이미 잠겨 있으면 무조건 기다린다"는 규칙이었다면, main 스레드는 자기 자신이 쥔 락이 풀리기를 기다리며 영원히 멈췄을 것이다. 재진입 규칙 덕분에 락의 소유자가 자신이면 기다리지 않고 들어가며, 내부적으로는 잠근 횟수가 1에서 2로 늘어난다. withdraw가 끝나면 횟수가 1로, transferOut이 끝나면 0으로 줄고, 0이 되는 순간 락이 실제로 풀린다. 마지막 줄의 holdsLock=false가 그 결과다.

    JLS 14.19의 예제 14.19-1도 같은 객체에 대한 synchronized 블록을 두 겹으로 중첩한 프로그램이 정상적으로 출력한다는 것을 보이며, 한 스레드가 모니터를 두 번 이상 잠글 수 없었다면 이 프로그램은 교착 상태에 빠졌을 것이라고 덧붙인다. 재진입은 객체지향 코드에서 특히 중요하다. 부모 클래스의 synchronized 메서드를 자식 클래스가 재정의하고 그 안에서 super.method()를 부르는 것, synchronized 메서드가 헬퍼 메서드를 거쳐 다시 같은 객체의 synchronized 메서드에 닿는 것은 모두 같은 스레드가 같은 락을 다시 요청하는 일이다. 재진입은 synchronized만의 성질이 아니다. 다음 회차의 ReentrantLock은 이름부터 이 성질을 내세운다.

    한 층 아래: HotSpot은 락을 어디에 기록하는가

    지금까지는 JLS와 JVMS가 정한 규칙, 즉 "무엇이 보장되는가"를 보았다. 이제 HotSpot(OpenJDK 21)이 그 규칙을 "어떻게" 구현하는지 내려가 본다. 여기서부터는 명세가 아니라 구현이므로, JVM 구현이나 버전이 달라지면 바뀔 수 있는 내용이다. 출발점은 앞에서 던진 질문이다. 모든 객체가 락이 될 수 있다면, 락 상태는 어디에 적어 둘까.

    객체 헤더의 마크 워드

    HotSpot에서 힙의 모든 객체는 헤더(header)로 시작하고, 헤더의 첫 워드를 마크 워드(mark word)라고 부른다. OpenJDK 21 소스의 markWord.hpp 주석은 64비트 JVM에서 일반 객체의 마크 워드를 "사용하지 않는 25비트, 식별 해시코드 31비트, 사용하지 않는 1비트, GC 나이(age) 4비트, 사용하지 않는 1비트, 락 비트 2비트"로 그린다. 맨 아래 2비트가 락 상태를 나타내고, 상태에 따라 나머지 비트의 의미가 바뀐다.

    하위 2비트상태나머지 비트에 들어 있는 것 (markWord.hpp 주석 기준)
    01잠기지 않음(unlocked)정상 헤더: 해시코드, GC 나이
    00잠김(locked)스택 잠금(stack-locking)을 쓰면 스레드 스택에 옮겨 둔 원래 헤더를 가리키는 포인터. 새 경량 잠금(fast-locking)을 쓰면 원래 헤더가 그대로 남는다
    10모니터(monitor)팽창된(inflated) 락. 원래 헤더는 다른 곳으로 옮겨지고, ObjectMonitor를 가리키는 포인터가 들어간다
    11표시됨(marked)GC가 객체를 표시하는 데 쓴다

    락을 잡는 방법이 여러 가지인 이유는 비용 때문이다. 대부분의 락은 경합 없이 잡히고 풀린다. 한 스레드만 쓰는 객체의 synchronized 메서드를 부르는 경우가 그렇다. 이런 경우에 무거운 자료 구조를 만들고 운영체제의 도움을 받는 것은 낭비다. 그래서 HotSpot은 경합이 없는 동안에는 마크 워드만으로 락을 표현하고, 경합이 생기면 그때 별도의 ObjectMonitor 객체를 만들어 마크 워드가 그것을 가리키게 한다. 이 전환을 락 팽창(lock inflation)이라고 한다.

    OpenJDK 21에는 경합이 없을 때 쓰는 방식이 두 가지 있고, 실험용(experimental) 옵션 LockingMode로 고른다. JDK 21의 globals.hpp에 적힌 설명은 0이 모니터만 쓰는 방식(LM_MONITOR), 1이 모니터와 기존 스택 잠금(LM_LEGACY, 기본값), 2가 모니터와 새 경량 잠금(LM_LIGHTWEIGHT)이다. 이 원고의 실험 환경에서 java -XX:+UnlockExperimentalVMOptions -XX:+PrintFlagsFinal -version으로 확인한 값도 LockingMode = 1이었다. 아래 설명은 JDK 21의 기본값인 스택 잠금을 기준으로 한다.

    스택 잠금과 재진입의 기록

    OpenJDK 21의 synchronizer.cpp에 있는 ObjectSynchronizer::enter는 런타임이 락을 얻는 경로를 보여 준다. 스택 잠금 모드(LM_LEGACY)에서 이 함수가 하는 일은 다음과 같다.

    앞에서 "재진입하면 횟수가 늘어난다"고 했는데, 스택 잠금 상태에서는 그 횟수가 숫자로 따로 저장되지 않는다. 대신 스택에 쌓인 잠금 기록들이 횟수 역할을 한다. 첫 진입의 기록에는 원래 헤더가, 재진입한 기록에는 0이 들어 있다. 프레임이 끝나며 해제할 때 0이 든 기록은 아무것도 하지 않고, 원래 헤더가 든 기록이 그 헤더를 객체에 되돌려 놓으며 락이 풀린다. 팽창된 뒤에는 ObjectMonitor의 재진입 횟수 필드(_recursions, 소스 주석으로는 첫 진입이면 0인 재귀 횟수)가 이 역할을 맡는다.

    팽창이 실제로 경합 때 일어나는지는 HotSpot의 통합 로깅으로 볼 수 있다. 앞의 덤프 실험 프로그램(5초 쉬는 synchronized 출금을 두 스레드가 호출)을 -Xlog:monitorinflation=trace로 실행하고 팽창 기록만 골라내면 다음 줄이 보인다(시간과 주소는 실행마다 다르고, JDK 내부 객체의 줄은 생략했다).

    [0.134s][trace][monitorinflation] inflate(has_locker): object=0x0000007010614d20, mark=0x000000781ccacc42, type='DumpMain$Account'

    계좌 객체(DumpMain$Account)가 프로그램 시작 직후 t2가 락을 요청한 시점에 팽창되었다. has_locker는 팽창 직전에 이 객체가 스택 잠금 상태였다는 뜻이다. t1이 경합 없이 스택 잠금으로 락을 잡아 두었고, t2가 도착해 이미 잠긴 것을 보고 팽창시킨 것이다. 반면 같은 옵션으로 앞의 재진입 예제(ReentrantMain)를 실행하면 ReentrantMain 객체에 대한 팽창 기록은 나오지 않는다. 스레드 하나가 재진입까지 했지만 경합이 없었으므로 끝까지 스택 잠금만으로 처리된 것이다. 참고로 덤프 실험의 로그에는 java.lang.Thread 객체의 팽창도 찍히는데, JDK 21의 Thread.join이 플랫폼 스레드에 대해 synchronized (this) 안에서 wait를 쓰기 때문이다.

    ObjectMonitor: 소유자, 진입 대기열, 대기 집합

    팽창된 락의 실체인 ObjectMonitor는 C++ 객체다. OpenJDK 21의 objectMonitor.hpp에서 이 회차와 관련된 필드와 그 소스 주석은 다음과 같다.

    필드소스 주석의 뜻이 회차와의 연결
    _header옮겨 둔 객체 헤더(마크 워드)마크 워드 자리를 모니터 포인터가 차지했으므로 원래 해시코드·나이를 여기 보관한다
    _owner소유 스레드, 또는 BasicLock을 가리키는 포인터지금 락을 가진 스레드. Thread.holdsLock과 덤프의 locked가 보는 정보
    _recursions재귀(재진입) 횟수, 첫 진입이면 0재진입 카운트
    _cxq진입하려다 블록된, 최근 도착한 스레드들의 연결 리스트BLOCKED 스레드가 먼저 들어가는 곳
    _EntryList진입 또는 재진입하려다 블록된 스레드들BLOCKED 스레드의 대기열
    _WaitSetwait() 중인 스레드들의 연결 리스트8회차의 wait/notify가 쓰는 대기 집합

    objectMonitor.cpp 앞부분의 "동작 원리(Theory of operations)" 주석은 이 필드들이 어떻게 쓰이는지 설명한다. 스레드는 _owner 필드를 CAS로 null에서 자기 자신으로 바꾸는 데 성공하면 모니터를 소유한다. 경쟁하는 스레드는 CAS로 자신을 _cxq에 넣은 뒤 스핀하거나 파킹(park)한다. 실제 진입 코드도 대기열에 들어가기 전에 TrySpin으로 잠깐 돌며 락이 곧 풀리기를 기대해 본다. 파킹은 운영체제 수준에서 스레드를 재우는 것이고, 앞의 덤프에서 BLOCKED 스레드가 CPU를 거의 쓰지 않은 이유가 이것이다. 한 스레드는 어느 순간에도 _cxq, _EntryList, _WaitSet 중 최대 하나에만 들어 있다.

    락을 놓는 쪽의 동작이 공정성과 직결된다. 같은 주석에 따르면 락을 놓는 스레드는 _EntryList에서 "추정 후계자(heir presumptive)" 하나를 골라 깨우지만, 소유권을 그 스레드에게 넘겨주지는 않는다. 소유권을 놓고 후계자를 깨울 뿐이며, 깨어난 스레드는 다시 경쟁해서 락을 얻거나 못 얻으면 다시 잠든다. 주석은 이것을 경쟁적 인계(competitive handoff)라고 부른다. 깨어난 후계자가 CAS를 시도하기 전에 막 도착한 다른 스레드가 먼저 _owner를 차지할 수 있다는 뜻이다. JLS도 모니터를 기다리는 스레드들이 어떤 순서로 락을 얻는지 정하지 않는다. 그러니 synchronized는 오래 기다린 스레드가 먼저 들어간다는 보장, 즉 공정성(fairness)을 주지 않는다. 운이 나쁜 스레드가 계속 밀리는 기아(starvation)도 이론적으로 가능하다.

    사라진 최적화: 편향 잠금

    오래된 자료에서 synchronized의 구현을 설명할 때 자주 나오는 편향 잠금(biased locking)은 지금의 JDK에서는 찾을 수 없다. JEP 374에 따르면 편향 잠금은 경합 없는 락에서 CAS조차 피하려는 최적화로, 객체의 모니터를 처음 잠근 스레드 쪽으로 "편향"시켜 이후 같은 스레드의 잠금에서 원자적 명령어를 쓰지 않게 하는 기법이었다. JEP 374는 JDK 15에서 편향 잠금을 기본으로 끄고 관련 옵션을 모두 폐기 예정(deprecated)으로 만들었다. JEP는 그 이유로, 이득을 보던 것이 주로 모든 접근에 동기화를 거는 Hashtable, Vector 같은 초기 컬렉션 API를 쓰는 오래된 애플리케이션이며, 지금은 과거만큼 이득이 뚜렷하지 않고 유지 비용이 크다는 점을 든다. JDK 21에서는 옵션 자체가 없다. 이 원고의 실험 환경에서 java -XX:+UseBiasedLocking -version을 실행하면 Unrecognized VM option 'UseBiasedLocking'을 출력하고 JVM이 시작되지 않는다. 따라서 "synchronized는 편향 잠금, 경량 잠금, 중량 잠금의 세 단계를 거친다"는 설명은 JDK 21 기준으로는 맞지 않는다.

    ObjectMonitor::enter와 EnterI가 하는 일

    커널에 닿기까지 HotSpot은 잠들지 않으려고 여러 번 시도한다. OpenJDK 21의 objectMonitor.cpp에서 ObjectMonitor::enter는 가장 흔한 경우부터 차례로 검사한다. _owner를 CAS로 null에서 자기 자신으로 바꾸는 데 성공하면 바로 돌아간다. 이미 자신이 소유자면 _recursions를 1 늘리고 돌아간다. 소유자 칸에 자기 스택의 BasicLock 주소가 들어 있으면(스택 잠금 상태에서 팽창된 경우) 그것을 스레드 포인터로 바꾸고 재진입 횟수를 1로 둔다. 여기까지 해당하지 않으면 소스 주석이 말하는 "진짜 경합(genuine contention)"이다. 그래도 바로 잠들지 않고 TrySpin으로 한 차례 돌아 본다. 스핀은 모니터마다 둔 _SpinDuration 값만큼 돌며, 스핀으로 락을 얻으면 그 값을 늘리고 실패하면 줄이는 적응형(adaptive) 방식이다. 같은 파일의 초기화 코드는 프로세서가 하나뿐인 기계(os::is_MP()가 거짓)에서는 스핀 한도를 0으로 만든다. 소유자가 같은 CPU를 내놓기 전에는 락이 풀릴 수 없으니 도는 것이 순수한 낭비이기 때문이다.

    스핀까지 실패해야 비로소 스레드 상태가 바뀐다. enter는 JavaThreadBlockedOnMonitorEnterState라는 객체를 만들어 스레드 상태를 "모니터 진입을 기다리며 블록됨"으로 바꾸고, 기다리는 모니터를 스레드의 current_pending_monitor에 기록한다. Thread.getState()가 BLOCKED를 돌려주는 것은 이 시점부터다. 거꾸로 말하면 처음의 스핀으로 락을 얻은 스레드는 BLOCKED를 한 번도 거치지 않는다. 소스 주석도 초기 스핀으로 모니터를 얻으면 JVMTI 이벤트를 보내지 않는다고 적고 있고, JFR의 jdk.JavaMonitorEnter 이벤트 객체도 이 스핀 뒤에야 만들어진다. 따라서 짧게 끝나는 경합은 스레드 덤프에도 JFR 기록에도 잘 남지 않는다. 그다음 EnterI가 대기열에 들어가 잠드는 일을 맡는다.

    3단계의 책임 스레드(Responsible)가 왜 필요한지도 소스 주석에 설명되어 있다. 락을 놓는 쪽은 대기열이 비어 보이면 아무도 깨우지 않고 끝나는 빠른 경로를 탄다. 그런데 어떤 스레드가 대기열에 들어가는 순간과 소유자가 그 빠른 경로로 락을 놓는 순간이 엇갈리면, 락은 비어 있는데 모든 대기 스레드가 잠든 채 남는 "좌초(stranding)"가 생길 수 있다. 이를 복구하려고 대기 스레드 중 하나가 주기적으로 깨어나 _owner를 확인한다. 그 주기 recheckInterval은 1밀리초에서 시작해 깨어날 때마다 8배로 늘고, MAX_RECHECK_INTERVAL인 1000밀리초에서 멈춘다. 앞의 sample 출력에서 waiter가 기한 없는 park()가 아니라 park_nanos(long) 안에 있었던 이유가 이것이다. waiter는 혼자 기다렸으므로 책임 스레드였다. 대기 스레드를 둘로 늘려 다시 찍으면 차이가 드러난다.

    PlatformEvent: park와 unpark의 바닥

    HotSpot의 스레드는 저마다 ParkEvent를 하나씩 가진다. thread.hpp의 필드 주석은 이것이 객체 모니터와 JVMTI raw 모니터 등에 쓰인다고 적는다. POSIX 계열(macOS, Linux)에서 그 바닥은 os_posix.cpp의 PlatformEvent이고, 정수 하나(_event)와 pthread 뮤텍스·조건 변수 한 쌍으로 이루어진다. park()는 _event를 원자적으로 1 줄인다. 원래 값이 1이었다면(이미 누가 unpark해 두었다면) 잠들지 않고 바로 돌아간다. 0이었다면 -1이 되며, 뮤텍스를 잡고 _event가 음수인 동안 pthread_cond_wait를 반복한다. 시간 제한이 있는 park_nanos는 같은 고리에서 pthread_cond_timedwait를 쓰고, 시간이 다 되면 고리를 빠져나온다(앞의 sample 출력에서는 두 경우 모두 그 아래에 _pthread_cond_wait가 찍혔다). unpark()는 _event를 원자적 교환으로 1로 만들고, 원래 값이 -1(누군가 잠들었거나 잠들려는 중)일 때만 뮤텍스를 잡아 실제로 잠든 스레드 수(_nParked)를 확인한 뒤, 뮤텍스를 놓고 나서 pthread_cond_signal을 보낸다. 원래 값이 0이나 1이면 시스템 콜 없이 정수 하나만 바꾸고 끝나는 구조다. 소스 주석은 운영체제 수준의 가짜 깨어남(spurious wakeup)을 무시하려고 조건을 다시 검사한다고 밝힌다.

      park() 하는 쪽 (BLOCKED가 될 스레드)              unpark() 하는 쪽 (락을 놓는 스레드)
  ───────────────────────────────────              ─────────────────────────────────
  _event: 0 → -1 (원자적 감소)
  pthread_mutex_lock
  while (_event < 0)
      pthread_cond_wait  ──── 커널에서 잠듦 ────▶   _event: -1 → 1 (원자적 교환)
        (macOS: __psynch_cvwait)                    old == -1 이므로
                                                    pthread_cond_signal ──┐
      ◀────────────────────── 깨어남 ─────────────────────────────────────┘
  _event = 0, pthread_mutex_unlock
  → EnterI로 돌아가 TryLock. 실패하면 다시 park()

    이 실험은 macOS에서 했으므로 커널 진입점이 __psynch_cvwait로 찍혔다. Linux는 이 원고에서 실행해 보지 않았지만, futex(7) 매뉴얼은 리눅스 커널이 제공하는 futex가 뮤텍스와 조건 변수 같은 고수준 잠금의 재료이며, 대부분의 프로그램은 futex를 직접 쓰지 않고 그 위에 만들어진 NPTL(리눅스의 pthread 구현) 같은 시스템 라이브러리를 쓴다고 설명한다. 같은 매뉴얼은 경합이 없는 경우 futex 연산이 전부 사용자 공간에서 끝나고 커널은 경합이 있을 때만 개입한다고 적는다. HotSpot 쪽 코드(PlatformEvent)는 두 운영체제에서 같고, 그 아래의 pthread 구현이 각자의 커널 기능을 쓰는 구조다.

    인터럽트가 BLOCKED를 깨우지 못하는 이유, 코드로 보기

    앞의 BlockedMain 실험에서 인터럽트는 BLOCKED 스레드를 깨우지 못했다. 그런데 정확히 말하면 스레드는 잠깐 깨어난다. OpenJDK 21 javaThread.cpp의 JavaThread::interrupt는 대상 스레드의 이벤트 세 개를 모두 unpark한다. Thread.sleep용 _SleepEvent, LockSupport.park용 parker(), 그리고 주석에 "ObjectMonitor와 JvmtiRawMonitor용"이라고 적힌 _ParkEvent다. 그래서 모니터를 기다리던 스레드도 park에서 돌아온다. 하지만 위의 EnterI 고리는 깨어난 뒤 TryLock만 해 볼 뿐 인터럽트 상태를 전혀 검사하지 않는다. 락이 여전히 잡혀 있으니 헛깨어남 카운터를 1 늘리고 다시 잠든다. "인터럽트에 반응하지 않는다"는 동작은 이렇게 구현되어 있다.

    이 카운터는 HotSpot 성능 카운터 sun.rt._sync_FutileWakeups로 공개되어 있어 jcmd PerfCounter.print로 읽을 수 있다. holder가 락을 9초 쥐고, 0.1초 뒤 도착한 waiter가 혼자 기다리는 프로그램에서, 시작 약 4.1초 뒤에 카운터를 읽고 waiter를 20밀리초 간격으로 다섯 번 인터럽트한 뒤 다시 읽었다. 같은 프로그램을 세 번 실행했고 세 번 모두 값이 같았다.

    uptime≈4156ms sun.rt._sync_FutileWakeups=7
uptime≈4422ms sun.rt._sync_FutileWakeups=12

    첫 번째 값 7은 책임 스레드의 시간 제한 park로 설명된다. waiter가 대기열에 들어간 뒤 1, 8, 64, 512, 1000, 1000, 1000밀리초 간격으로 깨어났다면 깨어난 시각은 약 1, 9, 73, 585, 1585, 2585, 3585밀리초다. 4초쯤 지난 시점까지 일곱 번이고, 매번 락은 여전히 holder에게 있었으니 모두 헛깨어남이다. 두 번째 값은 정확히 5가 늘었다. 인터럽트 다섯 번이 _ParkEvent를 다섯 번 unpark했고, waiter는 다섯 번 깨어나 락을 확인하고 다섯 번 다시 잠들었다. 인터럽트 다섯 번을 보낸 0.3초 남짓한 구간에서 늘어난 값이 인터럽트 횟수와 정확히 같다.

    깨우는 쪽: exit와 대기열의 순서

    락을 놓는 ObjectMonitor::exit도 같은 파일에 있다. 재진입 횟수가 남아 있으면 1 줄이고 끝난다. 0이면 해제 의미(release)를 가진 저장으로 _owner를 비우고, 메모리 장벽(storeload) 뒤에 대기열을 본다. _cxq와 _EntryList가 모두 비었거나, 이미 깨어 있는 후계자(_succ, 예를 들어 스핀 중인 스레드)가 있으면 아무도 깨우지 않고 돌아간다. 깨워야 할 때는 락을 다시 잡은 뒤 _EntryList의 맨 앞 스레드를 고른다. _EntryList가 비어 있으면 _cxq를 통째로 떼어 와 _EntryList로 옮기는데, 이때 리스트의 순서를 뒤집지 않고 단방향 리스트를 양방향 리스트로 바꾸기만 한다. 그리고 ExitEpilog에서 그 스레드를 _succ로 표시하고, _owner를 비운 다음 그 스레드의 ParkEvent를 unpark한다.

    여기서 순서에 관한 결론이 하나 나온다. _cxq는 새로 온 스레드를 맨 앞에 끼우는 리스트(LIFO)이고, 옮길 때 순서를 유지하므로 _EntryList의 맨 앞에는 가장 늦게 도착한 스레드가 온다. 실제로 그런지 확인해 보았다. holder가 락을 1초 쥐는 동안 w1, w2, w3, w4가 0.1초 간격으로 차례로 도착해 BLOCKED가 되고, 각자 락을 얻으면 이름을 찍고 10밀리초 뒤에 놓는다. 다섯 번 실행한 결과가 모두 같았다.

    w4 w3 w2 w1

    도착한 순서와 정반대다. 이 결과를 synchronized의 규칙으로 받아들이면 안 된다. 스핀 중인 스레드나 막 도착한 스레드가 끼어들면 순서는 얼마든지 바뀌고, 이것은 OpenJDK 21 HotSpot의 현재 구현일 뿐 JLS는 어떤 순서도 약속하지 않는다. 이 실험이 보여 주는 것은 앞에서 말한 "공정성 없음"이 추상적인 가능성이 아니라는 점이다. 이 구현은 문맥 교환 횟수를 줄이는 것을 우선하며, 먼저 온 스레드를 먼저 들여보내는 장치는 이 경로에 없다.

    마지막으로, 스레드 덤프가 locked와 waiting to lock을 구분하는 방법도 이 구조 위에 있다. OpenJDK 21 vframe.cpp의 print_lock_info_on은 각 프레임에 기록된 잠금 기록 목록(인터프리터 프레임의 BasicObjectLock들, 컴파일된 프레임이면 디버그 정보)을 훑으며 객체마다 한 줄씩 찍는다. 그리고 맨 위 프레임의 첫 잠금 기록에 대해서만, 객체의 마크 워드가 모니터를 가리키고 그 모니터가 스레드의 current_pending_monitor와 같거나 스레드가 그 모니터의 소유자가 아니면 locked 대신 waiting to lock을 찍는다. 앞의 덤프에서 BLOCKED t2의 withdraw 프레임에 잠금 기록이 이미 있었던 것은, 스레드가 락을 얻기 전에 프레임에 잠금 기록 자리부터 마련하고 그 기록을 들고 monitorenter 런타임 함수로 들어가기 때문이다. 위 sample 출력의 InterpreterRuntime::monitorenter(JavaThread*, BasicObjectLock*)가 바로 그 모습이다.

    팽창한 모니터는 언제 돌아오는가: 비동기 수축

    경합 때문에 팽창한 락은 경합이 끝나면 어떻게 될까. 락이 풀리는 순간 마크 워드가 다시 "잠기지 않음"으로 돌아갈 것 같지만, OpenJDK 21에서는 그렇지 않다. 마크 워드는 락이 풀린 뒤에도 계속 ObjectMonitor를 가리키고, 이 연결을 끊고 원래 헤더를 되돌려 놓는 수축(deflation)은 MonitorDeflationThread라는 전용 JVM 스레드가 따로, 나중에 한다. 그동안 그 객체를 잠그는 스레드는 스택 잠금을 거치지 않고 바로 모니터 경로로 간다. synchronizer.cpp의 ObjectSynchronizer::enter는 마크 워드가 잠기지 않은 정상 상태일 때만 스택 잠금 CAS를 시도하고, 그 밖의 경우에는 inflate를 부르는데, inflate는 마크 워드가 이미 모니터를 가리키면 그 모니터를 그대로 돌려준다.

    수축 스레드가 언제 일하는지는 monitorDeflationThread.cpp와 ObjectSynchronizer::is_async_deflation_needed에 적혀 있다. 이 스레드는 GuaranteedSafepointInterval(1000), AsyncDeflationInterval(250), GuaranteedAsyncDeflationInterval(60000) 중 가장 작은 값, 즉 기본값으로는 250밀리초마다 깨어나 수축이 필요한지 검사한다(괄호 안은 이 실험 환경에서 -XX:+UnlockDiagnosticVMOptions -XX:+PrintFlagsFinal로 확인한 기본값이며 단위는 밀리초, 셋 다 진단용 옵션이다). 수축이 필요하다고 판단하는 경우는 세 가지다. 누군가 명시적으로 요청했을 때, 마지막 수축 뒤 AsyncDeflationInterval이 지났고 사용 중인 모니터 수가 상한(ceiling) 대비 MonitorUsedDeflationThreshold(90퍼센트)를 넘었을 때, 그리고 마지막 수축 뒤 GuaranteedAsyncDeflationInterval이 지났을 때다.

    모니터를 몇 개 쓰지 않는 작은 프로그램이라면 세 번째 조건만 걸린다는 뜻이다. 두 스레드가 계좌 객체를 놓고 0.3초 경합한 뒤 65초를 쉬는 프로그램을 -Xlog:monitorinflation=trace:file=defl.log:uptime으로 실행해 확인했다. 아래는 로그에서 계좌 객체와 관련된 줄과 수축 요약만 고른 것이다(주소는 실행마다 다르다).

    이 사실은 진단할 때 쓰인다. 경합이 한 번이라도 있었던 객체는 그 뒤 한동안 팽창된 모니터로 남는다. 그래서 -Xlog:monitorinflation 로그의 in_use_list 수치처럼 "사용 중인 모니터 수"를 볼 때는, 그 수가 지금 경합 중인 락의 수가 아니라 아직 수축되지 않은 모니터의 수라는 점을 감안해야 한다.

    JIT 컴파일러가 지우는 락: 탈출 분석과 락 생략

    지금까지 본 비용(스택 잠금 CAS, 팽창, park)은 모두 락 연산이 실제로 실행될 때의 이야기다. HotSpot의 C2 컴파일러는 한 걸음 더 나아가, 필요 없다고 증명할 수 있는 락 연산을 컴파일된 코드에서 아예 없앤다. 근거는 JLS 17.4.4의 정의에서 따라 나온다. 모니터 규칙이 만드는 synchronizes-with 관계는 모니터 m의 unlock과 그 뒤에 일어나는 같은 m의 lock 사이에만 생긴다. 어떤 객체가 그것을 만든 스레드 밖으로 한 번도 나가지 않는다면, 다른 스레드는 그 객체의 모니터를 잠글 수 없다. 그 락은 상호 배제할 상대도 없고, 다른 스레드와 이어지는 happens-before 관계도 만들지 못한다. 그런 락을 지워도 프로그램이 보일 수 있는 결과는 달라지지 않는다.

    객체가 스레드 밖으로 나가는지 판정하는 분석을 탈출 분석(escape analysis)이라고 한다. OpenJDK 21의 C2에서는 escape.cpp의 ConnectionGraph가 이 분석을 하고, callnode.cpp의 LockNode::Ideal이 그 결과를 쓴다. 해당 코드의 주석은 탈출하지 않은 객체를 잠그는 경우 lock/unlock이 불필요하다고 적고, 그런 락 노드에 "NonEscObj" 표시를 붙인다. 표시가 붙은 노드는 나중에 기계어로 펼쳐지지 않는다(macro.cpp의 eliminate_locking_node). 같은 소스는 락 노드의 종류를 Regular, NonEscObj, Coarsened, Nested 네 가지로 이름 붙인다. Coarsened는 같은 객체에 대한 unlock 바로 뒤에 lock이 이어질 때 두 연산을 함께 지워 두 임계 영역을 하나로 합치는 락 병합(lock coarsening)이고, Nested는 이미 잡은 락 안에서 같은 객체를 다시 잠그는 중첩 락을 지우는 것이다. 관련 옵션은 이 실험 환경에서 -XX:+PrintFlagsFinal로 확인한 대로 DoEscapeAnalysis, EliminateLocks, EliminateNestedLocks 모두 기본값 true인 C2 제품 옵션이다. c2_globals.hpp에 적힌 EliminateLocks의 설명은 "가능하면 락을 병합한다(Coarsen locks when possible)"인데, LockNode::Ideal은 탈출하지 않은 객체의 락 제거와 락 병합 둘 다 이 옵션이 켜져 있을 때만 시도한다.

    hsdis가 없어 이 환경에서는 JIT가 만든 기계어를 볼 수 없다. 그래도 락이 지워졌는지는 스레드 덤프로 확인할 수 있다. 앞에서 본 vframe.cpp의 print_lock_info_on은 컴파일된 프레임의 잠금 기록이 "제거됨"으로 표시되어 있으면 locked 대신 eliminated를 찍는다. 이를 이용해 다음 프로그램을 만들었다. work는 메서드 안에서만 쓰는 객체를 잠그고, 아주 가끔 그 안에서 Thread.sleep을 부른다. 처음 2초 동안은 0밀리초씩 쉬며 C2가 이 경로까지 포함해 컴파일하게 하고, 그 뒤에는 3초씩 쉬게 해 덤프를 찍을 틈을 만든다.

    public class Elim {
    static volatile boolean stop;
    static int sink;

    static void work(int i) throws InterruptedException {
        Object local = new Object();              // 이 메서드 밖으로 나가지 않는다
        synchronized (local) {
            sink += i;
            if ((i & 0xFFFF) == 0) {              // 가끔 이 경로도 지나가게 해 프로파일에 남긴다
                Thread.sleep(stop ? 3000 : 0);    // stop 뒤에는 덤프를 찍을 틈
            }
        }
    }

    public static void main(String[] args) throws Exception {
        Thread t = new Thread(() -> {
            try {
                for (int i = 0; ; i++) work(i);
            } catch (InterruptedException e) { }
        }, "worker");
        t.setDaemon(true);
        t.start();
        Thread.sleep(2000);                       // C2가 work를 컴파일할 시간
        stop = true;
        Thread.sleep(3500);
    }
}

    실행 3초쯤에 jstack으로 worker 스레드를 찍었다. 기본 옵션으로 세 번 실행해 세 번 모두 같은 결과가 나왔고, -XX:+PrintCompilation으로 Elim::work가 4단계(C2)로 컴파일된 것도 확인했다. 비교를 위해 락 제거를 끈 경우, 탈출 분석을 끈 경우, C1까지만 쓰게 한 경우를 함께 실었다.

    기본 옵션에서 worker는 synchronized 블록 안에서 잠들어 있는데도 덤프에는 locked가 없다. 대신 eliminated 가 찍혔다. 락이 지워졌을 뿐 아니라 잠글 객체 자체가 힙에 만들어지지 않았다는 뜻이다. 탈출하지 않는 객체를 필드 값들로 쪼개 지역 변수처럼 다루는 스칼라 치환(scalar replacement)이 함께 일어나, 덤프가 보여 줄 객체 주소가 없다. 락 제거를 끄거나(-XX:-EliminateLocks), 탈출 분석을 끄거나(-XX:-DoEscapeAnalysis), C2를 쓰지 않게 하면(-XX:TieredStopAtLevel=1) 같은 자리에 실제 힙 주소와 함께 locked가 찍힌다. 인터프리터와 C1으로 실행되는 동안에는 이 락이 매번 실제로 잡히고 풀린다는 뜻이다.

    이 실험을 만들다 겪은 일도 기록해 둔다. 처음에는 if (stop) Thread.sleep(3000);처럼 워밍업 동안 한 번도 지나가지 않는 분기를 썼는데, 그때는 기본 옵션에서도 덤프에 locked가 찍혔다. -Xlog:deoptimization=debug로 실행해 보니 stop을 바꾼 직후 Elim.work(I)V trap_bci=23 ... unstable_if reinterpret라는 역최적화(deoptimization) 기록이 남았다. C2는 한 번도 실행되지 않은 분기를 "여기 오면 인터프리터로 돌아간다"는 함정(uncommon trap)으로 컴파일해 두었고, 그 분기가 처음 실행되자 컴파일된 프레임을 인터프리터 프레임으로 바꾼 것이다. 이때 지워졌던 락은 그대로 사라지지 않는다. deoptimization.cpp에서 역최적화는 스칼라 치환된 객체를 먼저 힙에 다시 만들고(Deoptimization::realloc_objects), 이어서 Deoptimization::relock_objects가 컴파일된 프레임의 디버그 정보에 "제거됨"으로 남아 있던 잠금 기록을 찾아 그 객체를 실제로 잠근 뒤에 인터프리터로 넘긴다. 인터프리터는 블록 끝에서 monitorexit를 실제로 실행할 것이므로, 그에 맞는 lock이 먼저 있어야 하기 때문이다. 락 제거는 증명이 성립하는 동안만 유지되는 최적화이고, JVM은 그 증명이 깨지는 순간을 위해 원래 상태로 되돌릴 정보를 남겨 둔다.

    이 최적화를 믿고 코드를 쓸 이유는 없다. 락 제거는 C2가 컴파일한 뒤에야, 그리고 탈출 분석이 객체가 밖으로 나가지 않는다고 증명한 경우에만 일어난다. 객체를 정적 필드나 공유 객체의 필드에 저장하면 탈출한 것으로 판정되고, 메서드 호출 너머로 넘기는 경우에도 분석이 증명하지 못하면 락은 그대로 남는다. 이 실험이 보여 주는 것은 "스레드 하나에서만 쓰는 객체에 붙은 synchronized는 공짜일 수 있다"는 가능성과, 그 판단 근거가 JLS의 happens-before 정의에 있다는 점이다. 성능을 판단하려면 실제 코드에서 측정해야 한다.

    synchronized는 가시성도 보장한다

    synchronized를 상호 배제의 도구로만 이해하면 절반만 이해한 것이다. 앞 회차의 가시성 문제를 떠올려 보자. 한 스레드가 필드에 쓴 값을 다른 스레드가 언제 보는지는 그 두 동작 사이에 happens-before 관계가 있느냐로 결정된다. JLS 17.4.4는 모니터 m에 대한 unlock 동작이 그 뒤에 일어나는(동기화 순서상) m에 대한 모든 lock 동작과 동기화된다(synchronizes-with)고 정하고, 17.4.5는 이로부터 "모니터에 대한 unlock은 그 모니터에 대한 이후의 모든 lock보다 먼저 일어난다(happens-before)"는 규칙을 이끌어 낸다.

    이것이 출금 예제에서 무엇을 의미하는지 따라가 보자. t1은 withdraw 안에서 balance에 200을 쓰고, 메서드를 나가며 계좌의 모니터를 unlock한다. t2는 그 뒤에 같은 모니터를 lock하고 balance를 읽는다. 한 스레드 안의 동작은 프로그램 순서대로 happens-before 관계를 이루므로, "t1의 200 쓰기 → t1의 unlock → t2의 lock → t2의 읽기"가 하나의 happens-before 사슬로 이어진다. 따라서 t2는 반드시 200(또는 그 뒤에 쓰인 값)을 본다. 캐시에 남은 1000을 볼 가능성은 명세 수준에서 배제된다. synchronized 출금이 올바른 이유는 상호 배제와 이 가시성 보장이 함께 작동하기 때문이다.

         t1                                          t2
  ┌──────────────────────────┐
  │ lock(account)             │
  │ balance 읽기 (1000)        │
  │ balance = 200 쓰기  ───┐   │
  │ unlock(account) ───────┼──┼──── synchronizes-with ───┐
  └──────────────────────────┘ │                           ▼
                               │              ┌──────────────────────────┐
                               │              │ lock(account)             │
                               └─ hb ───────▶ │ balance 읽기 → 반드시 200   │
                                              │ ...                       │
                                              │ unlock(account)           │
                                              └──────────────────────────┘
  hb: happens-before. 프로그램 순서 + 모니터 규칙이 이어져 t1의 쓰기가 t2의 읽기보다 먼저 일어난다.

    이 규칙에는 조건이 붙어 있다. 같은 모니터여야 한다. 쓰는 쪽이 계좌 객체를 잠그고 읽는 쪽이 아무 락도 잡지 않거나 다른 객체를 잠그면 사슬이 이어지지 않는다. 앞에서 getBalance에도 synchronized를 붙인 이유가 여기서 명세 수준으로 정당화된다. 락 없이 읽는 쪽은 최신 값을 본다는 보장을 받지 못하고, 필드가 long이나 double이라면 상황이 더 나쁘다. JLS 17.7은 volatile이 아닌 long/double에 대한 한 번의 쓰기를 32비트 절반씩 두 번의 쓰기로 다룰 수 있게 허용하므로, 락 없이 읽는 스레드는 이론상 앞 절반은 새 값, 뒤 절반은 옛 값인 값을 볼 수도 있다.

    synchronized의 한계

    synchronized는 자바 1.0부터 있던, 언어에 내장된 동기화 수단이다. 해제를 언어가 보장하고, 문법이 간단하며, 앞에서 본 것처럼 경합이 없을 때의 비용을 줄이는 구현이 JVM 안에 들어 있다. 대부분의 단순한 상호 배제에는 이것으로 충분하다. 그러나 이 회차에서 확인한 성질들을 모아 보면 분명한 한계도 보인다.

    • 무한 대기: 락을 기다리는 데 시간 제한이 없다. "0.5초 안에 못 얻으면 다른 일을 한다"를 표현할 방법이 없다.
    • 인터럽트 불가: BLOCKED 상태의 스레드는 인터럽트로 깨어나지 않는다. 앞의 실험에서 인터럽트 플래그만 켜진 채 계속 기다렸다.
    • 공정성 없음: 오래 기다린 스레드가 먼저 들어간다는 보장이 없다. HotSpot 구현은 경쟁적 인계 방식이라 막 도착한 스레드가 먼저 락을 차지할 수 있다.
    • 블록 구조에 묶임: 락을 얻는 곳과 푸는 곳이 같은 블록(또는 메서드)이어야 한다. 한 메서드에서 잠그고 다른 메서드에서 푸는 식의 유연한 구조를 만들 수 없다. 해제를 보장하는 장점의 뒷면이다.
    • 대기 집합이 하나: 모니터마다 wait 대기 집합(_WaitSet)이 하나뿐이라, 조건이 다른 스레드들(예: 생산자와 소비자)을 따로 기다리게 할 수 없다. 이 문제는 8~9회차의 주제다.

    JDK 21에서는 가상 스레드(virtual thread)와 관련된 한계가 하나 더 있다. JEP 444(가상 스레드, JDK 21)는 가상 스레드가 synchronized 블록이나 메서드 안의 코드를 실행하는 동안에는 자신을 실행하는 플랫폼 스레드(캐리어, carrier)에서 내려올 수 없는 "고정(pinning)" 상태가 된다고 설명한다. 그 상태에서 I/O 같은 블로킹 작업을 하면 가상 스레드뿐 아니라 캐리어 플랫폼 스레드까지 묶인다. JEP 491은 그 원인을, JVM이 모니터의 소유자를 가상 스레드가 아니라 플랫폼 스레드 기준으로 기록하기 때문이라고 설명한다. 앞에서 본 _owner 필드에 기록되는 것이 바로 그 스레드다. JEP 444는 JDK 21에서 자주 실행되면서 긴 I/O를 감싸는 synchronized를 ReentrantLock으로 바꾸라고 권했고, JEP 491은 JDK 24에서 synchronized 안에서 블록되는 가상 스레드가 캐리어를 놓아줄 수 있도록 고쳤다. 기준 버전인 JDK 21에서는 고정이 일어난다는 점을 기억해 두자.

    이 한계들을 풀기 위해 자바 5는 java.util.concurrent.locks 패키지를 추가했다. 다음 회차에서 LockSupport의 park/unpark부터 시작해 ReentrantLock이 시간 제한, 인터럽트, 공정성을 어떻게 제공하는지 다룬다. 그 뒤 8~9회차의 생산자 소비자 문제에서는 wait/notify와 Condition을, 10회차에서는 락 없이 원자성을 얻는 CAS를, 11회차에서는 이 모든 것을 내부에 품은 동시성 컬렉션을 본다.

    적용 연습과 정리

    이 절은 이 회차의 원리를 처음 보는 코드에 적용하는 연습이다. 각 코드에서 공유 자원, 임계 영역, 사용한 락을 먼저 짚은 뒤 판정해 보자.

    연습 1. 지역 변수만 쓰는 메서드

    public int sumTo(int n) {
    int total = 0;
    for (int i = 1; i <= n; i++) {
        total += i;
    }
    return total;
}

    여러 스레드가 같은 객체의 sumTo를 동시에 호출해도 synchronized가 필요 없다. n, total, i는 모두 호출한 스레드의 스택 프레임에 있는 지역 변수이고, 스레드마다 별도의 프레임이 만들어진다. total += i도 읽기-수정-쓰기지만 다른 스레드가 이 total에 닿을 길이 없으니 경합이 없다. 공유 자원이 없으면 임계 영역도 없다.

    연습 2. 인스턴스 락으로 정적 필드를 보호하려는 코드

    public class Ticket {
    private static int issued = 0;

    public synchronized int issue() {
        issued++;
        return issued;
    }
}

    Ticket 객체를 여러 개 만들어 스레드마다 다른 객체로 issue()를 부르면 번호가 중복되거나 건너뛴다. synchronized 인스턴스 메서드는 각자의 this를 잠그므로, 객체가 다르면 락도 다르다. 그런데 보호하려는 issued는 정적 필드라 모든 객체가 공유한다. 앞의 TwoLocks 실험에서 객체 a와 b의 메서드가 동시에 실행된 것과 같은 상황이다. 고치려면 issue()를 static synchronized로 만들거나(Ticket.class의 모니터), 정적 final 락 객체를 두고 블록으로 잠근다. 또 return issued;를 블록 밖으로 빼면, 증가와 반환 사이에 다른 스레드의 증가가 끼어들어 내가 받은 번호가 아닌 값을 돌려줄 수 있으므로 반환할 값도 임계 영역 안에서 정해야 한다.

    연습 3. 쓰기만 잠그고 읽기는 잠그지 않는 코드

    public class Config {
    private long version;

    public synchronized void update(long v) { version = v; }

    public long current() { return version; }   // synchronized 없음
}

    쓰기는 잠갔으니 안전하다고 생각하기 쉽지만 읽는 쪽에 두 가지 문제가 있다. 첫째, current()는 모니터를 lock하지 않으므로 update의 unlock과 happens-before 관계가 없다. 다른 스레드의 갱신을 계속 보지 못할 수 있다. 둘째, version이 volatile이 아닌 long이므로 JLS 17.7에 따라 쓰기가 32비트씩 나뉘어 보일 수 있다. current()에도 synchronized를 붙이거나, 이 클래스처럼 필드 하나를 통째로 쓰고 읽기만 한다면 volatile long으로 선언하는 것으로 충분하다. 읽기-수정-쓰기가 없으므로 원자성은 필요 없고 가시성만 있으면 되기 때문이다.

    연습 4. 불변 객체

    모든 필드가 final이고 생성자 밖에서 상태를 바꾸는 메서드가 없는 객체는 여러 스레드가 동기화 없이 읽어도 된다. 바뀌는 상태가 없으니 경합 조건이 생길 수 없고, JLS 17.5는 생성자가 끝난 뒤에야 객체 참조를 볼 수 있는 스레드는 그 객체의 final 필드가 올바르게 초기화된 값을 본다고 보장한다. 단서는 "생성자가 끝난 뒤에야"다. 생성자 안에서 this를 다른 스레드에 넘기면(예: 생성자에서 스레드를 시작하며 this를 넘기기) 이 보장이 성립하지 않는다.

    이 장의 핵심

    여러 스레드가 공유하는 상태를 읽고-판단하고-쓰는 코드는 실행 순서에 따라 결과가 달라지는 경합 조건을 만든다. 그 구간이 임계 영역이고, 한 번에 한 스레드만 실행하도록 상호 배제해야 한다. 자바의 모든 객체는 모니터 락을 가지며, synchronized 메서드는 this(정적이면 Class 객체)를, synchronized 블록은 지정한 객체를 잠근다. 메서드는 ACC_SYNCHRONIZED 플래그로 JVM이, 블록은 monitorenter/monitorexit와 예외 테이블로 컴파일러가 해제를 보장한다. 같은 모니터의 unlock은 이후의 lock보다 먼저 일어나므로 synchronized는 원자성과 가시성을 함께 준다. 대신 락을 기다리는 스레드는 BLOCKED 상태로 시간 제한도, 인터럽트도, 순서 보장도 없이 기다린다.
    경합 조건(race condition)
    여러 스레드가 공유 자원에 접근할 때 결과가 실행 순서에 따라 달라지는 상황. 검사 후 행동(check-then-act)과 읽기-수정-쓰기(read-modify-write)가 대표적인 모양이다.
    원자성과 가시성
    volatile은 가시성만 주므로 count++ 같은 복합 동작은 여전히 깨진다. 여러 동작을 하나로 묶는 원자성은 상호 배제로 얻는다.
    임계 영역(critical section)
    공유 자원에 접근하며 동시에 둘 이상의 스레드가 실행하면 결과가 깨지는 구간. 판단의 근거를 읽는 지점부터 결과를 쓰는 지점까지를 하나로 잡아야 한다.
    모니터 락
    자바의 모든 객체에 연결된 락. 한 번에 한 스레드만 가질 수 있고, 같은 스레드는 여러 번 잠글 수 있다(재진입). 락은 메서드가 아니라 객체에 붙는다.
    synchronized 메서드
    인스턴스 메서드는 this, 정적 메서드는 Class 객체의 모니터를 잠근다. 바이트코드에는 ACC_SYNCHRONIZED 플래그만 붙고, 잠금과 해제는 JVM의 호출·반환이 처리한다.
    synchronized 블록
    지정한 객체의 모니터를 잠그고 블록만 임계 영역으로 만든다. javac가 monitorenter와 모든 출구의 monitorexit, any 예외 핸들러를 만들어 해제를 보장한다.
    BLOCKED 상태
    모니터 락을 기다리는 스레드의 상태. 시간 제한이 없고 인터럽트로 깨어나지 않으며, 대기 스레드들 사이의 순서도 보장되지 않는다.
    모니터 규칙(happens-before)
    같은 모니터의 unlock은 이후의 lock보다 먼저 일어난다. 그래서 같은 락으로 보호한 쓰기와 읽기 사이에는 가시성이 보장된다.
    HotSpot의 구현(OpenJDK 21)
    경합이 없으면 마크 워드와 스택의 잠금 기록으로 락을 표현하고, 경합이 생기면 ObjectMonitor로 팽창한다. 편향 잠금은 JDK 15에서 기본 비활성화되었고 JDK 21에는 옵션이 없다.
    BLOCKED의 바닥과 락 생략(OpenJDK 21)
    BLOCKED 스레드는 스핀 뒤 _cxq에 들어가 PlatformEvent의 pthread 조건 변수에서 잠들고, 인터럽트로 깨어나도 락만 다시 확인하고 또 잠든다. 반대로 탈출하지 않는 객체의 락은 C2가 탈출 분석으로 아예 지운다.

    실무에서 synchronized를 다시 만나는 첫 장면은 "가끔 숫자가 안 맞는다"는 장애다. 스프링의 빈은 기본적으로 싱글톤이고, 서블릿 컨테이너는 요청마다 스레드 풀의 스레드를 하나씩 붙여 같은 빈의 메서드를 동시에 호출한다. 이 구조에서 빈의 인스턴스 필드에 요청별 상태나 누적 카운터를 두면 이 회차의 출금 예제와 정확히 같은 경합이 생긴다. 해법은 먼저 공유 상태를 없애는 것(지역 변수로 옮기기, 불변 객체 쓰기)이고, 공유가 꼭 필요할 때에만 임계 영역을 정해 잠근다. 또 synchronized는 한 JVM 안의 스레드끼리만 배제한다는 점을 잊지 말아야 한다. 같은 애플리케이션을 서버 두 대에 띄우면 각 JVM의 계좌 객체는 서로 다른 객체이고 락도 다르다. 여러 서버가 같은 데이터를 고치는 문제는 데이터베이스의 락이나 트랜잭션 격리 수준처럼 공유 저장소 쪽의 장치로 풀어야 한다.

    두 번째 장면은 "서버가 느려지다 멈췄다"는 장애다. 이때 스레드 덤프를 몇 초 간격으로 여러 번 찍어, BLOCKED (on object monitor) 스레드들이 어떤 주소를 waiting to lock 하고 있는지, 그 주소를 locked로 쥔 스레드는 무엇을 하고 있는지를 짝지어 본다. 락을 쥔 스레드가 외부 API 호출이나 DB 쿼리, 파일 I/O에 걸려 있다면 임계 영역 설계가 원인이다. 느린 I/O는 임계 영역 밖으로 빼고, 꼭 안에 둬야 한다면 시간 제한을 걸 수 있는 다음 회차의 Lock을 검토한다. 두 스레드가 서로 상대가 쥔 락을 기다리고 있다면 교착 상태이며, 락을 얻는 순서를 일관되게 정하는 것이 일반적인 해법이다.

    판단이 달라지는 조건도 있다. 경합이 거의 없는 짧은 임계 영역이라면 synchronized는 단순하고 해제가 보장되므로 여전히 좋은 기본값이다. 반면 임계 영역 안에서 블로킹 I/O를 하는 코드를 JDK 21의 가상 스레드 위에서 돌린다면 캐리어 스레드가 고정되는 문제가 생기므로 ReentrantLock으로 바꾸는 것을 고려한다(이 고정은 JDK 24에서 JEP 491로 대부분 해소되었다). 단순한 카운터 하나라면 락 대신 10회차의 Atomic 클래스가, 맵 하나라면 11회차의 동시성 컬렉션이 더 맞는 선택일 수 있다.
  • 필드 count가 0인 객체에서 두 스레드가 각각 count++를 딱 한 번씩 실행한다(동기화 없음). 가능한 최종 값을 모두 쓰고, 각 값이 나오는 실행 순서를 getfield, iadd, putfield 단위로 엇갈려 그려라.
  • 어떤 클래스에 public synchronized void deposit(int x) { balance += x; }와 public void reset() { balance = 0; }이 있다. 한 스레드는 deposit을, 다른 스레드는 reset을 반복 호출한다. deposit이 synchronized이므로 이 클래스는 안전한가? JLS 14.19의 문장과 모니터 규칙을 근거로 판정하라.
  • 다음 메서드를 컴파일하면 monitorexit가 몇 개 생기는지 예측하고, 각각이 어느 경로를 위한 것인지 설명하라. int f(boolean flag) { synchronized (lock) { if (flag) return 1; count++; } return 2; }
  • 스레드 덤프에서 스레드 A는 - locked <0x1> (a Account)와 - waiting to lock <0x2> (a Account)를, 스레드 B는 - locked <0x2> (a Account)와 - waiting to lock <0x1> (a Account)를 보이며 둘 다 BLOCKED다. 무슨 일이 일어났는지, 이 상태가 저절로 풀릴 수 있는지, 인터럽트로 풀 수 있는지 설명하라.
  • 두 계좌 사이의 이체 transfer(Account from, Account to, int amount)를 만든다. synchronized (from)만 잡는 방식과 synchronized (from) { synchronized (to) { ... } } 방식의 문제를 각각 설명하고, 교착 상태 없이 두 계좌를 함께 잠그는 방법을 제시하라.
    •

    1. 가능한 최종 값은 2와 1이다. 한 스레드가 getfield(0) → iadd(1) → putfield(1)를 모두 마친 뒤 다른 스레드가 같은 과정을 거치면 두 번째 스레드는 1을 읽어 2를 쓴다. 반대로 t1이 0을 읽고, 쓰기 전에 t2도 0을 읽으면, 둘 다 1을 계산해 1을 쓰므로 최종 값은 1이다. 어떤 순서로 쓰든 나중에 쓴 1이 먼저 쓴 1을 덮는다. 3이나 0은 나올 수 없다. 각 스레드가 정확히 한 번 쓰고, 쓰는 값은 자기가 읽은 값(0 또는 1)에 1을 더한 값이기 때문이다. 이 작은 예가 갱신 손실의 최소 단위다.

    2. 안전하지 않다. JLS 14.19는 어떤 객체의 락을 얻는 것이 다른 스레드가 그 객체의 필드에 접근하거나 synchronized가 아닌 메서드를 호출하는 것을 막지 않는다고 명시한다. reset은 락을 요청하지 않으므로 deposit의 getfield와 putfield 사이에 언제든 끼어들 수 있다. 예를 들어 deposit이 100을 읽은 뒤 reset이 0을 쓰고, deposit이 110을 쓰면 초기화가 사라진다. 또 reset의 쓰기와 deposit의 읽기 사이에는 모니터 규칙에 의한 happens-before가 없으므로 가시성도 보장되지 않는다. 같은 필드를 다루는 모든 코드가 같은 락을 써야 하므로 reset에도 synchronized를 붙인다.

    3. 세 개다. return 1 직전에 락을 풀기 위한 것 하나, 블록의 정상 끝(count++ 다음)에서 풀기 위한 것 하나, 블록 안에서 예외가 났을 때 any 핸들러가 풀고 예외를 다시 던지기 위한 것 하나다. 본문의 블록 버전 출금 메서드가 같은 구조였고 실제로 monitorexit가 세 번 나왔다. return 2는 블록 밖이므로 그 앞에는 monitorexit가 필요 없다. 이미 블록의 정상 끝에서 풀었기 때문이다.

    4. 교착 상태(deadlock)다. A는 0x1을 쥐고 0x2를 기다리고, B는 0x2를 쥐고 0x1을 기다린다. 서로가 상대의 락이 풀리기를 기다리므로 어느 쪽도 진행할 수 없고, 락은 블록을 빠져나가야 풀리는데 둘 다 블록 안에서 멈춰 있으니 저절로 풀리지 않는다. BLOCKED 상태는 인터럽트로 깨어나지 않으므로 인터럽트로도 풀 수 없다. JLS 17.1이 말하듯 자바는 교착 상태를 막거나 감지해 주지 않으므로 설계로 피해야 한다. 이 상태의 JVM은 보통 재시작해야 한다.

    5. synchronized (from)만 잡으면 to의 잔액 갱신은 보호되지 않는다. 다른 스레드가 to에서 출금하거나 to를 from으로 하는 이체를 동시에 하면 to의 잔액에서 갱신 손실이 생긴다. 두 락을 중첩해 잡으면 이 문제는 사라지지만, 스레드 1이 transfer(a, b), 스레드 2가 transfer(b, a)를 동시에 호출하면 1은 a를 쥐고 b를, 2는 b를 쥐고 a를 기다리는 4번의 교착 상태가 된다. 해법은 락을 얻는 순서를 전역적으로 하나로 정하는 것이다. 예를 들어 계좌마다 고유한 번호를 두고, 이체 방향과 상관없이 항상 번호가 작은 계좌를 먼저 잠근 뒤 큰 계좌를 잠근다. 모든 스레드가 같은 순서로 잠그면 서로 상대의 락을 쥐고 기다리는 순환이 생길 수 없다.

     같은 클래스에 static synchronized void a()와 synchronized void b()가 있다. 스레드 1이 a()를, 스레드 2가 어떤 인스턴스의 b()를 동시에 호출하면? 같은 클래스의 synchronized 메서드이므로 한 스레드는 BLOCKED가 된다 둘 다 동시에 실행될 수 있다 정적 메서드가 먼저 실행되도록 JVM이 순서를 정한다 컴파일 오류가 난다 JLS 17.1과 8.4.3.6에 따라 정적 synchronized 메서드는 그 클래스의 Class 객체 모니터를, 인스턴스 synchronized 메서드는 this의 모니터를 잠근다. 서로 다른 객체의 모니터이므로 서로를 배제하지 않는다. 락은 메서드나 클래스가 아니라 객체에 붙는다. 실행 순서를 JVM이 정해 주는 규칙은 없고, 두 수정자를 한 클래스에 함께 쓰는 것은 합법이다. volatile int count를 두 스레드가 각각 100만 번 count++ 하면 결과가 200만보다 작게 나온다. 가장 정확한 이유는? volatile 변수의 쓰기가 다른 스레드에 보이지 않기 때문이다 JIT 컴파일러가 반복문을 최적화해 일부 증가를 지웠기 때문이다 count++는 읽기, 더하기, 쓰기의 세 단계이고, volatile은 각 읽기·쓰기의 가시성만 보장할 뿐 세 단계를 하나로 묶어 주지 않기 때문이다 int가 32비트라 쓰기가 두 번으로 나뉘기 때문이다 count++는 getfield, iadd, putfield로 나뉜다. 두 스레드가 같은 값을 읽어 각자 더한 뒤 쓰면 하나의 증가가 사라진다(갱신 손실). volatile은 가시성을 보장하므로 첫 번째 보기는 틀렸다. JIT가 어떤 최적화를 하든 결과는 메모리 모델이 예측할 수 있는 범위 안에 있어야 하고(JLS 17.4), 200만보다 작은 값은 최적화가 없어도 읽기와 쓰기 사이에 다른 스레드가 끼어드는 것만으로 나온다. JLS 17.7의 분할 쓰기는 volatile이 아닌 long/double에 관한 것이다. 스레드 A가 모니터 락을 쥔 채 10초 동안 sleep 중이고, 스레드 B는 같은 락을 기다리며 BLOCKED 상태다. 이때 다른 스레드가 B를 인터럽트하면? B는 인터럽트 플래그만 켜진 채 계속 BLOCKED로 기다리고, A가 락을 놓은 뒤에야 블록에 들어간다 B는 즉시 InterruptedException을 받고 기다림을 그만둔다 A가 대신 인터럽트되어 락을 놓는다 B는 RUNNABLE 상태로 바뀌어 락 없이 블록에 들어간다 모니터 락을 기다리는 동작은 인터럽트에 반응하지 않는다. 본문 실험에서 인터럽트 뒤에도 B의 상태는 BLOCKED였고, 블록에 들어간 뒤 isInterrupted()가 true였다. InterruptedException은 sleep, wait, join 같은 메서드가 던지는 것이다. A는 인터럽트되지 않았으므로 영향이 없고, 락 없이 블록에 들어가는 경우는 없다. synchronized (this) { ... } 블록을 javap로 보면 monitorexit가 두 번 이상 나오고 any 타입의 예외 테이블 항목이 있다. 그 이유는? JVM이 락을 두 번 풀어야 완전히 해제되기 때문이다 재진입을 지원하기 위해 항상 두 번 잠그기 때문이다 디버깅 정보이고 실행에는 쓰이지 않는다 블록이 정상으로 끝나는 경로와 예외로 끝나는 경로 모두에서 락을 풀어야 하므로, 컴파일러가 각 출구에 monitorexit를 넣고 모든 예외를 잡아 락을 푼 뒤 다시 던지는 핸들러를 만들기 때문이다 JLS 14.19는 블록이 정상이든 갑자기든 끝나면 모니터를 푼다고 정하고, JVMS 2.11.10은 synchronized 블록의 올바른 구현에 컴파일러의 협력이 필요하다고 적는다. monitorenter는 한 번뿐이고 각 monitorexit는 서로 다른 경로에서 하나만 실행된다. 예외 테이블은 실제 실행 흐름을 결정하는 정보다. 쓰기 메서드만 synchronized이고 읽기 메서드는 synchronized가 아닌 클래스에서, 읽는 스레드가 최신 값을 본다는 보장이 없는 이유로 가장 정확한 것은? 읽기 메서드가 BLOCKED 상태가 되기 때문이다 synchronized 메서드는 CPU 캐시를 쓰지 않기 때문이다 모니터 규칙의 happens-before는 같은 모니터를 unlock한 스레드와 그 뒤에 lock한 스레드 사이에서만 성립하는데, 읽는 쪽은 lock을 하지 않으므로 쓰기와 읽기 사이에 happens-before 관계가 없기 때문이다 읽기 메서드가 쓰기 메서드보다 먼저 컴파일되기 때문이다 JLS 17.4.4·17.4.5에 따라 unlock은 같은 모니터의 이후 lock과 동기화되어 happens-before를 만든다. 락을 거치지 않는 읽기는 이 사슬에 연결되지 않는다. 락 없는 읽기는 기다리지 않으므로 BLOCKED가 되지 않고, "캐시를 쓰지 않는다"는 것은 명세가 정한 설명이 아니다.
    경합 조건(race condition)
    여러 스레드가 공유 자원에 접근할 때 실행 순서(타이밍)에 따라 결과가 달라지는 상황.
    갱신 손실(lost update)
    두 스레드가 같은 옛 값을 읽어 각자 계산한 결과를 쓸 때, 나중에 쓴 쪽이 먼저 쓴 쪽의 갱신을 덮어 사라지게 하는 현상.
    임계 영역(critical section)
    공유 자원에 접근하며, 동시에 둘 이상의 스레드가 실행하면 결과가 깨지는 코드 구간.
    상호 배제(mutual exclusion)
    임계 영역을 어느 순간에도 최대 한 스레드만 실행하도록 하는 성질.
    모니터(monitor)
    JLS 17.1에서 자바의 모든 객체에 연결된 동기화 장치. 스레드가 lock/unlock하며, 한 번에 한 스레드만 락을 가진다.
    재진입(reentrancy)
    이미 락을 가진 스레드가 같은 락을 다시 요청하면 기다리지 않고 잠금 횟수만 늘리는 성질.
    BLOCKED
    모니터 락을 얻으려고(또는 wait 뒤 다시 얻으려고) 기다리는 스레드의 상태. 인터럽트로 깨어나지 않는다.
    마크 워드(mark word)
    HotSpot에서 객체 헤더의 첫 워드. 해시코드, GC 나이, 락 상태 비트를 담는다.
    락 팽창(lock inflation)
    HotSpot이 경합 등으로 인해 마크 워드만으로 표현하던 락을 별도의 ObjectMonitor로 옮기는 일.
    탈출 분석(escape analysis)
    객체가 만든 메서드나 스레드 밖으로 나가는지 판정하는 컴파일러 분석. HotSpot C2는 그 결과로 나가지 않는 객체의 락을 지우고(락 생략) 할당을 스칼라 치환한다.
