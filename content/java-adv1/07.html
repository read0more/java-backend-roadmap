    synchronized가 남긴 두 가지 문제

    앞 회차에서 synchronized로 임계 영역(critical section)을 보호했다. 모든 객체에 딸린 모니터 락을 한 스레드만 얻을 수 있게 하고, 블록을 벗어나면 정상 종료든 예외든 락이 자동으로 풀린다. 코드가 짧고 실수할 여지가 적다는 점에서 훌륭한 도구다. 그런데 실제 서버에서 이 도구만으로 버티다 보면 두 가지 벽에 부딪힌다. 하나는 무한 대기, 다른 하나는 공정성이다.

    무한 대기부터 보자. 모니터 락을 기다리는 스레드는 BLOCKED 상태가 되는데, 이 상태의 스레드는 락을 얻을 때까지 다른 어떤 방법으로도 기다림을 그만둘 수 없다. 시간 제한을 줄 문법이 없고, 인터럽트를 걸어도 반응하지 않는다. 직접 확인해 보자. main이 모니터를 쥔 채로 다른 스레드를 그 모니터 앞에 세워 두고 인터럽트를 건다.

    public class SyncInterrupt {
    static final Object monitor = new Object();

    public static void main(String[] args) throws Exception {
        Thread t;
        synchronized (monitor) {
            t = new Thread(() -> {
                synchronized (monitor) {
                    System.out.println("[t] 모니터 획득, interrupted="
                            + Thread.currentThread().isInterrupted());
                }
            }, "t");
            t.start();
            Thread.sleep(100);
            t.interrupt();
            Thread.sleep(100);
            System.out.println("[main] 인터럽트 후 t=" + t.getState());
        }
        t.join();
    }
}
    [main] 인터럽트 후 t=BLOCKED
[t] 모니터 획득, interrupted=true

    인터럽트를 받은 뒤에도 t는 여전히 BLOCKED다. 인터럽트는 플래그만 켜 두었을 뿐 대기를 끝내지 못했고, main이 블록을 빠져나가 모니터를 놓은 뒤에야 t가 들어가 켜진 플래그를 발견한다. 만약 모니터를 쥔 스레드가 느린 외부 호출에 걸려 몇 분씩 돌아오지 않는다면, 그 뒤에 줄 선 스레드들은 모두 그 시간만큼 꼼짝없이 묶인다. 요청을 처리하는 스레드 풀의 스레드가 이렇게 하나둘 묶이면 결국 풀 전체가 말라 버린다.

    두 번째 벽은 공정성(fairness)이다. 모니터 락이 풀렸을 때 기다리던 스레드 중 누가 다음 차례인지는 정해져 있지 않다. 먼저 와서 오래 기다린 스레드가 먼저 들어간다는 보장이 없으므로, 운이 나쁜 스레드는 계속 밀려 오래 굶을(starvation) 수 있다. synchronized에는 이 순서를 고를 수 있는 옵션이 없다.

    자바 5는 java.util.concurrent.locks 패키지로 이 두 문제에 답했다. 이 회차는 그 패키지의 가장 밑바닥 도구인 LockSupport에서 시작해, 그 위에 지어진 AbstractQueuedSynchronizer(AQS), 그리고 이를 이용한 ReentrantLock까지 아래에서 위로 쌓아 올린다. 무엇을 할 수 있는지보다 각 층이 어떻게 동작하는지에 지면을 더 쓴다.

    스레드를 세우고 깨우는 가장 낮은 도구: LockSupport

    락을 직접 만든다고 생각해 보자. 락이 이미 잡혀 있으면 지금 스레드를 멈춰 세워야 하고, 락이 풀리면 멈춘 스레드 중 하나를 깨워야 한다. "멈춘다"를 바쁜 루프로 구현하면 CPU를 태운다. 그렇다고 Thread.sleep으로 잠깐씩 자면 깨어날 시점을 추측해야 한다. 필요한 것은 "특정 스레드를 스케줄링 대상에서 빼고, 다른 스레드가 그 스레드를 콕 집어 다시 넣어 주는" 기본 연산이다. LockSupport가 바로 그것을 제공한다.

    • LockSupport.park(): 현재 스레드를 스레드 스케줄링 대상에서 뺀다(API 문서의 표현은 "disables the current thread for thread scheduling purposes"). 스레드 상태는 WAITING이 된다.
    • LockSupport.parkNanos(long nanos): 최대 주어진 나노초만큼만 멈춘다. 상태는 TIMED_WAITING이다. 0 이하를 넘기면 아무것도 하지 않고 바로 돌아온다.
    • LockSupport.parkUntil(long deadline): 에포크 기준 밀리초로 표현한 절대 시각까지 멈춘다. 상태는 역시 TIMED_WAITING이다.
    • LockSupport.unpark(Thread t): 지정한 스레드를 다시 스케줄링 대상으로 돌려놓는다. null을 넘기면 아무 일도 없다.

    Thread.State의 API 문서는 WAITING에 들어가는 호출로 Object.wait(), Thread.join()과 함께 LockSupport.park를 명시하고, TIMED_WAITING에 parkNanos와 parkUntil을 명시한다. 반면 BLOCKED는 "모니터 락을 기다리는 상태"로만 정의되어 있다. 이 구분이 뒤에서 스레드 덤프를 읽을 때 중요한 단서가 된다. 실제로 세 가지 깨어나는 경로를 실행해 보자.

    import java.util.concurrent.locks.LockSupport;

public class ParkBasics {
    public static void main(String[] args) throws Exception {
        // 1) unpark으로 깨우기
        Thread t1 = new Thread(() -> {
            System.out.println("[t1] park 진입");
            LockSupport.park();
            System.out.println("[t1] park 복귀, interrupted="
                    + Thread.currentThread().isInterrupted());
        }, "t1");
        t1.start();
        Thread.sleep(100);
        System.out.println("[main] t1 state=" + t1.getState());
        LockSupport.unpark(t1);
        t1.join();

        // 2) interrupt로 깨우기
        Thread t2 = new Thread(() -> {
            LockSupport.park();
            System.out.println("[t2] park 복귀, interrupted="
                    + Thread.currentThread().isInterrupted());
            LockSupport.park(); // 인터럽트 플래그가 켜져 있으면 즉시 복귀
            System.out.println("[t2] 두 번째 park도 바로 복귀");
        }, "t2");
        t2.start();
        Thread.sleep(100);
        System.out.println("[main] t2 state=" + t2.getState());
        t2.interrupt();
        t2.join();

        // 3) parkNanos
        Thread t3 = new Thread(() -> LockSupport.parkNanos(2_000_000_000L), "t3");
        t3.start();
        Thread.sleep(100);
        System.out.println("[main] t3 state=" + t3.getState());
        LockSupport.unpark(t3);
        t3.join();
        System.out.println("[main] t3 state=" + t3.getState());
    }
}
    [t1] park 진입
[main] t1 state=WAITING
[t1] park 복귀, interrupted=false
[main] t2 state=WAITING
[t2] park 복귀, interrupted=true
[t2] 두 번째 park도 바로 복귀
[main] t3 state=TIMED_WAITING
[main] t3 state=TERMINATED

    세 가지를 눈여겨보자. 첫째, park된 스레드는 BLOCKED가 아니라 WAITING이다. 둘째, 인터럽트를 받으면 park는 예외 없이 그냥 돌아온다. Thread.sleep이나 Object.wait처럼 InterruptedException을 던지지 않고, 인터럽트 플래그도 지우지 않는다. 그래서 t2가 복귀한 직후 isInterrupted()는 true이고, 플래그가 켜진 채로 다시 부른 두 번째 park는 멈추지 않고 즉시 돌아왔다. park를 쓰는 쪽은 돌아온 뒤 스스로 플래그를 확인하고 처리 방침을 정해야 한다는 뜻이다. 셋째, parkNanos로 2초를 예약했지만 unpark를 받자 시간을 다 채우지 않고 끝났다.

    API 문서는 park가 돌아오는 경우를 정확히 셋(시간 제한 버전은 넷)으로 나열한다. 누군가 이 스레드를 대상으로 unpark를 불렀을 때, 누군가 이 스레드를 인터럽트했을 때, (시간 제한 버전이면) 시간이 다 되었을 때, 그리고 아무 이유 없이(spuriously) 돌아올 때다. 그리고 "이 메서드는 이 중 무엇 때문에 돌아왔는지 알려 주지 않는다"고 못 박는다. 마지막 경우가 이상하게 들리겠지만, 뒤에서 HotSpot 구현을 보면 실제로 그런 경로가 있다는 것을 확인할 수 있다.

    허가(permit) 모델: 0 아니면 1

    LockSupport를 이해하는 열쇠는 API 문서 첫 문단의 허가(permit) 개념이다. 각 스레드에는 허가가 하나 딸려 있다고 생각한다. park는 허가가 있으면 그것을 소비하고 즉시 돌아오고, 없으면 멈출 수 있다. unpark는 허가를 "있음"으로 만든다. 문서는 세마포어와 다른 점도 분명히 적는다. 허가는 쌓이지 않으며 최대 한 개다. 다음 코드로 확인해 보자.

    import java.util.concurrent.locks.LockSupport;

public class PermitDemo {
    public static void main(String[] args) {
        Thread me = Thread.currentThread();
        LockSupport.unpark(me);
        LockSupport.unpark(me);               // 허가는 쌓이지 않는다
        long t0 = System.nanoTime();
        LockSupport.park();                   // 허가를 소비하고 즉시 복귀
        long t1 = System.nanoTime();
        LockSupport.parkNanos(500_000_000L);  // 허가가 없으므로 최대 0.5초 대기
        long t2 = System.nanoTime();
        System.out.println("first park waited >= 100ms ? " + (t1 - t0 >= 100_000_000L));
        System.out.println("second park waited >= 500ms ? " + (t2 - t1 >= 500_000_000L));
    }
}
    first park waited >= 100ms ? false
second park waited >= 500ms ? true

    unpark를 두 번 불렀지만 허가는 한 개만 남았다. 첫 번째 park는 그 허가를 먹고 즉시 돌아왔고, 두 번째 park는 허가가 없어서 실제로 멈췄다. 두 번째 줄이 true인 것은 이 실행에서 가짜 깨어남이 없었기 때문이며 문서상 보장은 아니다. 만약 허가가 세마포어처럼 쌓였다면 두 번째 park도 바로 돌아왔을 것이다. 정리하면 허가의 상태 전이는 단 두 칸이다.

              unpark()                       unpark()
   ┌──────────────────┐          ┌──────────────────┐
   │                  ▼          │                  │ (그대로 1)
 [허가 0] ─────────▶ [허가 1] ───┘
   ▲   park(): 멈춤     │
   │                    │ park(): 허가를 소비하고 즉시 복귀
   └────────────────────┘

    이 단순한 규칙이 해결하는 문제가 있다. 바로 깨우기 신호의 유실이다. 스레드 A가 "조건이 아직 아니니 멈추자"라고 판단한 직후, 실제로 멈추기 직전의 아주 짧은 틈에 스레드 B가 조건을 만들고 A를 깨운다고 해 보자. 깨우기가 "지금 멈춰 있는 스레드를 깨운다"는 의미라면, 아직 멈추지 않은 A에게 보낸 신호는 허공으로 사라지고 A는 그 뒤에 영영 잠든다. 허가 모델에서는 B의 unpark가 허가를 1로 만들어 두므로, 한발 늦게 park에 들어간 A는 허가를 소비하고 곧바로 돌아온다. 순서가 뒤바뀌어도 진행이 보장된다. API 문서가 park와 unpark 사이의 경쟁(race)이 "허가 덕분에 활성(liveness)을 유지한다"고 쓴 것이 이 뜻이다.

    같은 문단에서 문서는 Thread.suspend와 Thread.resume을 비교 대상으로 든다. 이 두 메서드는 오래전부터 deprecated였는데, Thread.suspend의 문서는 이유를 이렇게 설명한다. 모니터 락을 쥔 채 정지된 스레드가 있으면 그 스레드가 재개될 때까지 아무도 그 자원에 접근할 수 없고, 재개시킬 스레드가 resume을 부르기 전에 그 모니터를 잡으려 하면 교착 상태가 된다. LockSupport 문서는 park/unpark가 suspend/resume을 쓸 수 없게 만든 문제를 겪지 않는다고 하면서, 그 근거로 앞에서 본 허가 덕분의 활성 유지를 든다. JDK 21에서 이 두 메서드는 호출하는 즉시 UnsupportedOperationException을 던지도록 바뀌어 있다(JDK 21 소스로 확인). park/unpark는 그 자리를 대신하는 안전한 기본 연산이다.

    스레드마다 허가 칸이 하나 있고, unpark가 먼저 와도 park가 먼저 와도 결국 스레드가 진행한다는 것을 두 개의 시나리오로 나란히 보여 준다. 좌우 두 칸으로 나눈 시퀀스 다이어그램. 각 칸에 세로 생명선 두 개: 왼쪽 "스레드 A", 오른쪽 "스레드 B". 스레드 A 생명선 옆에 작은 사각형 "허가"가 붙어 있고 안에 숫자 0 또는 1을 적는다. 왼쪽 칸 제목 "park가 먼저": A에서 "park()" 표시 후 A 생명선이 점선(멈춤)으로 바뀌고 허가 0, B에서 A로 화살표 "unpark(A)", A 생명선이 다시 실선으로 돌아오며 "복귀". 오른쪽 칸 제목 "unpark가 먼저": B에서 A로 화살표 "unpark(A)", 허가 칸이 1로 바뀜, 그 뒤 A에서 "park()" 표시, 허가 칸이 0으로 바뀌고 A 생명선은 끊기지 않고 실선으로 이어지며 "즉시 복귀". 평면 벡터 스타일, 흰 배경, 파란색과 회색만 사용. 허가는 최대 하나다. 먼저 도착한 unpark도 허가로 남아 있으므로 깨우기 신호가 유실되지 않는다.

    가짜 깨어남과 올바른 사용 패턴

    허가 모델이 신호 유실은 막아 주지만, park가 돌아왔다고 해서 기다리던 조건이 만족되었다는 보장은 없다. 앞에서 본 것처럼 park는 인터럽트 때문에도, 아무 이유 없이도 돌아오며 이유를 알려 주지 않는다. 그래서 API 문서는 park를 다음 모양 안에서만 쓰도록 설계했다고 명시한다.

    while (!canProceed()) {
    // unpark 요청을 다른 스레드가 볼 수 있게 한 뒤
    LockSupport.park(this);
}

    조건을 확인하고, 아니면 park하고, 돌아오면 다시 조건을 확인한다. 돌아온 이유가 진짜 신호였다면 루프를 빠져나가고, 가짜 깨어남이나 다른 용도의 unpark였다면 다시 park한다. 문서의 또 한 가지 요구는 조건을 나타내는 변수를 volatile(또는 원자 변수)로 두라는 것이다. 문서는 "park와 unpark 호출의 순서는 volatile 변수 접근에 대해서는 유지되지만, volatile이 아닌 변수 접근에 대해서는 반드시 그렇지 않다"고 적는다. 5회차에서 본 대로 volatile이 아닌 필드는 다른 스레드의 쓰기가 언제 보일지 보장되지 않으므로, 깨어난 스레드가 낡은 값을 보고 다시 잠들 수 있다.

    이 규칙을 지켜 한 번만 열리는 문(gate)을 직접 만들어 보자. 기다리는 스레드는 하나라고 가정한다.

    import java.util.concurrent.locks.LockSupport;

public class OneShotGate {
    private volatile boolean open;
    private volatile Thread waiter;

    public void await() {
        waiter = Thread.currentThread();   // (1) 깨울 대상을 먼저 공개한다
        while (!open) {                    // (2) 조건 확인
            LockSupport.park(this);        // (3) 아니면 멈춘다. 돌아오면 (2)로
        }
    }

    public void open() {
        open = true;                       // (4) 조건을 만든다
        LockSupport.unpark(waiter);        // (5) 공개된 대상을 깨운다
    }

    public static void main(String[] args) throws Exception {
        OneShotGate gate = new OneShotGate();
        Thread t = new Thread(() -> {
            gate.await();
            System.out.println("[worker] 게이트 통과");
        }, "worker");
        t.start();
        Thread.sleep(100);
        System.out.println("[main] worker=" + t.getState()
                + ", blocker=" + LockSupport.getBlocker(t).getClass().getSimpleName());
        gate.open();
        t.join();
        System.out.println("[main] worker=" + t.getState());
    }
}
    [main] worker=WAITING, blocker=OneShotGate
[worker] 게이트 통과
[main] worker=TERMINATED

    이 짧은 코드가 왜 어떤 순서로 실행되어도 맞는지 따져 보자. 두 필드가 모두 volatile이므로 (1), (2), (4), (5)의 읽기·쓰기는 모든 스레드가 동의하는 하나의 순서(동기화 순서)에 놓인다. 경우는 둘이다. worker가 (2)에서 open을 true로 읽으면 멈추지 않고 통과한다. worker가 (2)에서 false를 읽었다면 그 읽기는 (4)의 쓰기보다 앞선 것이고, (1)은 (2)보다 앞서므로 (5)에서 읽는 waiter에는 worker가 들어 있다. 그러면 unpark가 worker에게 허가를 주므로, worker가 (3)에 들어가기 전이든 후든 결국 깨어나 (2)에서 true를 본다. 두 필드 중 하나라도 volatile이 아니면 이 논증의 첫 단추부터 무너진다.

    출력의 blocker=OneShotGate도 보자. park(Object blocker)는 넘긴 객체를 Thread의 parkBlocker 필드에 기록해 두었다가 복귀할 때 지운다(JDK 21 소스의 setBlocker). 진단 도구는 LockSupport.getBlocker(Thread)로 "이 스레드가 무엇 때문에 멈춰 있는가"를 알아낸다. API 문서는 blocker를 받지 않는 원래 형태보다 이 형태를 쓰라고 "강하게 권장"하며, 락 구현 안에서는 보통 this를 넘긴다고 한다. 뒤에서 볼 스레드 덤프의 "parking to wait for" 줄이 바로 이 값에서 나온다.

    API 문서는 "허가가 스레드당 하나뿐이므로, 중간에 끼어든 다른 park 사용(클래스 로딩을 통한 암묵적 사용 포함)이 응답하지 않는 스레드(lost unpark)를 만들 수 있다"고 경고한다. 그래서 문서의 예제 락은 정적 초기화 블록에서 LockSupport 클래스를 미리 로딩해 둔다. park는 이런 미묘함을 감수하고 동기화 도구를 만드는 사람을 위한 부품이며, 애플리케이션 코드에서 직접 쓰는 일은 드물다.

    한 층 아래: HotSpot의 Parker

    JDK 21 소스에서 LockSupport.park()는 현재 스레드가 가상 스레드인지 먼저 확인한다. 가상 스레드면 VirtualThreads.park()로 가고, 플랫폼 스레드면 Unsafe.park(false, 0L)를 부른다. parkNanos는 Unsafe.park(false, nanos), parkUntil은 Unsafe.park(true, deadline)이다. 첫 인자는 시간이 절대 시각인지 여부다. Unsafe.park는 네이티브 메서드이므로 그 뒤는 JVM 안이다. 뒤에서 볼 스레드 덤프에서도 park 중인 스레드의 맨 위 프레임은 jdk.internal.misc.Unsafe.park(Native Method)다.

    unpark는 더 단순하다. 뮤텍스를 잡고, 이전 _counter 값을 기억한 뒤 _counter = 1로 대입하고, 뮤텍스를 푼다. 이전 값이 1 미만이고 실제로 조건 변수에서 기다리는 스레드가 있으면 그 조건 변수에 신호를 보낸다. 증가가 아니라 대입이라는 점이 "허가는 쌓이지 않는다"의 구현이다. 다섯 번째 단계도 눈여겨보자. 뮤텍스를 얻지 못하면 허가를 확인하지도 않고 돌아온다. 호출한 쪽에서 보면 이유 없는 복귀, 즉 가짜 깨어남이다. 조건 변수 자체도 POSIX 규격상 가짜 깨어남을 허용한다. 문서의 "조건 재확인 루프" 요구는 이런 구현 현실을 반영한 계약이다.

    여기서 synchronized와 무엇이 다른지 정리할 수 있다. 모니터 락을 기다리는 스레드는 JVM의 모니터 구현이 관리하는 대기 목록에 들어가고 상태는 BLOCKED로 보고된다. 반면 java.util.concurrent의 락들은 대기열을 자바 코드로 직접 관리하고, 스레드를 세울 때만 park라는 공통 부품을 쓴다. 그래서 그 위에서 기다리는 스레드는 어떤 락을 기다리든 WAITING이나 TIMED_WAITING으로 보인다. 대기열이 자바 코드이므로 "시간이 지나면 줄에서 빠진다", "인터럽트를 받으면 줄에서 빠진다", "줄 선 순서대로 준다" 같은 정책을 라이브러리 수준에서 얼마든지 구현할 수 있다. 이것이 synchronized의 두 가지 벽을 넘는 방법이다.

    Lock 인터페이스와 ReentrantLock

    java.util.concurrent.locks.Lock 인터페이스는 락이 제공해야 할 연산을 정의한다. 메서드는 여섯 개다.

    인터페이스 문서는 synchronized와의 차이를 두 축으로 설명한다. 하나는 위 표의 확장된 획득 방식(기다리지 않기, 인터럽트 가능, 시간 제한)이다. 다른 하나는 구조의 자유다. synchronized는 락의 획득과 해제가 블록 구조를 따라야 해서, 여러 락을 잡으면 반대 순서로 풀어야 하고 같은 어휘 범위 안에서 풀어야 한다. Lock은 다른 메서드에서 풀어도 되고 순서도 자유롭다. 문서가 드는 예는 연결 리스트를 순회하며 A를 잡고 B를 잡은 뒤 A를 풀고 C를 잡는 "hand-over-hand" 잠금이다. 대가도 분명히 적혀 있다. 자동 해제가 없으므로 해제를 보장하는 책임이 프로그래머에게 넘어온다.

    문서에는 오해하기 쉬운 문장도 하나 있다. Lock 인스턴스도 평범한 객체이므로 synchronized (lock)의 대상이 될 수 있지만, 그 모니터를 잡는 것과 lock()을 부르는 것은 아무 관계가 없다. 둘은 서로 다른 락이다. 문서는 혼동을 피하려면 자기 구현 내부가 아니라면 이렇게 쓰지 말라고 권한다.

    ReentrantLock은 이 인터페이스의 대표 구현이다. 문서는 "synchronized로 접근하는 암묵적 모니터 락과 같은 기본 동작과 의미를 가지면서 확장된 기능을 가진 재진입 가능한 상호 배제 락"이라고 소개한다. 핵심 개념은 소유(ownership)와 보유 횟수(hold count)다. 락은 마지막으로 성공적으로 잠그고 아직 풀지 않은 스레드가 소유한다. 소유자가 다시 lock()을 부르면 기다리지 않고 보유 횟수만 1 늘어난다. 이것이 재진입(reentrancy)이다. unlock()은 보유 횟수를 1 줄이고, 0이 되었을 때 비로소 락이 풀린다.

    import java.util.concurrent.locks.ReentrantLock;

public class HoldCount {
    static final ReentrantLock lock = new ReentrantLock();

    public static void main(String[] args) throws Exception {
        lock.lock();
        lock.lock();
        System.out.println("hold=" + lock.getHoldCount() + " locked=" + lock.isLocked()
                + " mine=" + lock.isHeldByCurrentThread());
        lock.unlock();
        System.out.println("hold=" + lock.getHoldCount() + " locked=" + lock.isLocked());
        lock.unlock();
        System.out.println("hold=" + lock.getHoldCount() + " locked=" + lock.isLocked());
        try {
            lock.unlock();                       // 한 번 더 풀기
        } catch (IllegalMonitorStateException e) {
            System.out.println("extra unlock -> " + e);
        }
        lock.lock();
        Thread other = new Thread(() -> {
            System.out.println("other hold=" + lock.getHoldCount());
            try {
                lock.unlock();                   // 남의 락 풀기
            } catch (IllegalMonitorStateException e) {
                System.out.println("other unlock -> " + e);
            }
        });
        other.start();
        other.join();
        System.out.println(lock);
        lock.unlock();
        System.out.println(lock);
    }
}

    보유 횟수가 2에서 1로 줄어도 isLocked()는 여전히 true다. 두 번 잠갔으면 두 번 풀어야 한다. 풀린 락을 또 풀거나, 소유자가 아닌 스레드가 풀려고 하면 IllegalMonitorStateException이 난다. 다른 스레드에서 본 getHoldCount()가 0인 점도 보자. 보유 횟수는 "현재 스레드가" 이 락을 몇 번 쥐고 있는지를 돌려주는 값이다. 재진입 횟수에는 상한이 있는데, 문서에 따르면 같은 스레드가 최대 2147483647번까지 재귀적으로 잠글 수 있고 넘으면 잠금 메서드가 Error를 던진다. 이 숫자가 int의 최댓값이라는 데서 짐작할 수 있듯, 보유 횟수는 내부의 int 하나에 저장된다. 그 int가 무엇인지 보러 한 층 내려가자.

    그 밖의 공개 메서드도 정리해 둔다. isFair(), hasQueuedThreads(), hasQueuedThread(Thread), getQueueLength()는 공개 메서드이고, getOwner()와 getQueuedThreads()는 protected다. 문서는 이런 메서드 중 일부가 계측과 모니터링에만 쓸모 있다고 적는다. 대기 스레드 수 같은 값은 읽는 순간에도 바뀌므로 동기화 판단에 쓰면 안 된다.

    ReentrantLock의 내부: AQS의 state와 대기 큐

    ReentrantLock은 일을 거의 직접 하지 않는다. 필드는 private final Sync sync 하나뿐이고, 모든 공개 메서드는 이 sync에 위임한다. Sync는 AbstractQueuedSynchronizer(이하 AQS)를 상속한 내부 클래스이며, 다시 NonfairSync와 FairSync로 나뉜다. 기본 생성자는 NonfairSync를, new ReentrantLock(true)는 FairSync를 만든다. AQS는 Semaphore, CountDownLatch, ReentrantReadWriteLock 같은 동기화 도구들이 공유하는 뼈대다. 이 뼈대가 가진 핵심 상태는 세 가지다.

    • private volatile int state: 동기화 상태. 그 의미는 하위 클래스가 정한다. ReentrantLock의 Sync 주석은 "AQS state로 락의 보유 횟수를 표현한다"고 적는다. 0이면 풀린 상태, 1 이상이면 그 값이 보유 횟수다.
    • exclusiveOwnerThread: 상위 클래스 AbstractOwnableSynchronizer에 있는 필드로, 지금 락을 소유한 스레드다.
    • head, tail(둘 다 volatile): 락을 기다리는 스레드의 대기 큐. 소스 주석은 이 큐를 CLH(Craig, Landin, Hagersten) 락 큐의 변형이라고 부른다. 각 노드는 앞뒤 링크(prev, next), 기다리는 스레드(waiter), 상태(status)를 가진다.

    먼저 경합이 없는 경우다. lock()은 sync.lock()을 부르고, 이것은 initialTryLock()부터 시도한다. NonfairSync의 구현은 다음과 같다(JDK 21 소스, 주석은 원문).

    final boolean initialTryLock() {
    Thread current = Thread.currentThread();
    if (compareAndSetState(0, 1)) { // first attempt is unguarded
        setExclusiveOwnerThread(current);
        return true;
    } else if (getExclusiveOwnerThread() == current) {
        int c = getState() + 1;
        if (c < 0) // overflow
            throw new Error("Maximum lock count exceeded");
        setState(c);
        return true;
    } else
        return false;
}

    compareAndSetState(0, 1)은 "state가 0이면 1로 바꾸고 성공을, 아니면 아무것도 바꾸지 않고 실패를 돌려준다"는 원자적 연산(CAS)이다. CAS가 하드웨어 수준에서 어떻게 원자성을 얻는지는 10회차의 주제다. 여기서는 동시에 두 스레드가 시도해도 정확히 하나만 성공한다는 것만 알면 된다. 경합이 없으면 이 CAS 한 번과 소유자 기록 한 번으로 lock()이 끝난다. 대기 큐는 아예 만들어지지도 않는다. 소스 주석은 큐의 첫 더미 헤드 노드를 생성 시점이 아니라 "첫 경합이 일어날 때" 만든다고 설명한다. 경합이 없는 락에 쓸데없는 객체를 만들지 않기 위해서다. 두 번째 분기가 재진입이다. 이미 내가 소유자면 CAS 없이 setState(c)로 횟수만 올린다. 소유자 자신만 이 값을 바꿀 수 있는 상황이므로 원자적 연산이 필요 없다. c가 음수가 되는 오버플로가 앞에서 본 Error의 출처다.

    이제 경합이 있는 경우를 세 스레드로 추적해 보자. T1이 락을 쥐고 있고, T2와 T3가 차례로 lock()을 부른다. T2의 initialTryLock()은 CAS에 실패하고 소유자도 아니므로 false다. 그러면 AQS의 acquire(1)로 넘어가는데, 이 메서드는 tryAcquire를 한 번 더 시도한 뒤 실패하면 핵심 루프인 acquire(node, arg, shared, interruptible, timed, time)로 들어간다. 이 루프는 한 바퀴에 한 가지 준비 작업만 하고, 바퀴마다 자기가 맨 앞이거나 아직 줄에 서지 않았으면 tryAcquire를 다시 시도한다.     소스 주석은 이것을 "AQS 락은 스핀하지 않고, 대신 획득 시도를 장부 정리 단계와 번갈아 끼워 넣는다"고 설명한다. 노드를 만들고 줄을 서는 동안 T1이 락을 풀었다면 T2는 park할 필요 없이 중간에 얻어 간다. 네 번째 단계의 순서도 중요하다. "WAITING 표시 → 다시 시도 → park" 순서이므로, T1이 락을 푸는 시점이 어디든 둘 중 하나는 반드시 성립한다. T2의 마지막 시도가 풀린 state를 보고 성공하거나, T1이 해제하면서 T2의 WAITING 표시를 보고 unpark를 보낸다. unpark가 park보다 먼저 도착해도 허가가 남아 있으므로 T2는 잠들지 않는다. 주석은 이를 "Dekker 방식과 비슷한 구조"라고 부른다. 앞에서 본 허가 모델이 여기서 쓰인다.

    T3도 같은 과정을 거쳐 T2 노드 뒤에 줄을 선다. 다만 T3의 앞 노드는 head가 아니라 T2의 노드이므로 T3는 맨 앞이 아니고, 맨 앞이 아닌 노드는 tryAcquire를 시도하지 않는다. 이 시점의 메모리 상태는 다음과 같다.

    ReentrantLock
 └─ sync (NonfairSync)
      state = 1                 exclusiveOwnerThread = T1

      head                                            tail
       │                                               │
       ▼                                               ▼
   ┌────────┐  next   ┌──────────────┐  next   ┌──────────────┐
   │ 더미   │ ──────▶ │ waiter = T2  │ ──────▶ │ waiter = T3  │
   │        │ ◀────── │ status=WAITING│ ◀────── │ status=WAITING│
   └────────┘  prev   └──────────────┘  prev   └──────────────┘
                        (park 중)               (park 중)

    이제 T1이 unlock()을 부른다. unlock()은 sync.release(1)이고, release는 tryRelease(1)이 true를 돌려줄 때만 다음 노드를 깨운다.

    protected final boolean tryRelease(int releases) {
    int c = getState() - releases;
    if (getExclusiveOwnerThread() != Thread.currentThread())
        throw new IllegalMonitorStateException();
    boolean free = (c == 0);
    if (free)
        setExclusiveOwnerThread(null);
    setState(c);
    return free;
}

public final boolean release(int arg) {
    if (tryRelease(arg)) {
        signalNext(head);
        return true;
    }
    return false;
}

    소유자 검사가 앞의 IllegalMonitorStateException의 출처다. 보유 횟수가 0이 될 때만 소유자를 비우고 true를 돌려주므로, 재진입한 락을 한 번만 풀면 대기자는 깨어나지 않는다. 완전히 풀리면 signalNext(head)가 head 다음 노드(T2)의 status가 0이 아닌지 보고, WAITING 비트를 지운 뒤 LockSupport.unpark(T2)를 부른다. 깨어난 T2는 루프로 돌아와 자기가 맨 앞임을 확인하고 tryAcquire로 state를 0에서 1로 CAS한다. 성공하면 자기 노드를 새 head로 만들고(node.prev = null; head = node;), 이전 head와의 연결을 끊고, 노드의 waiter를 비운다. 즉 락을 얻은 스레드의 노드가 새 더미 헤드가 된다. 이제 T3의 앞 노드가 head이므로 T3가 맨 앞이 되고, T2가 락을 풀 때 깨워진다.

    대기 중에 포기하는 스레드가 생기면 어떻게 될까. 시간 초과나 인터럽트로 포기하는 스레드는 cancelAcquire에서 자기 노드의 status를 CANCELLED(음수)로 바꾸고 waiter를 비운 뒤 cleanQueue()로 큐에서 떼어 낸다. 떼어 낸 결과 새로 맨 앞이 된 노드가 있으면 그 노드를 깨운다. 뒤에서 getQueueLength()가 2에서 1로 줄어드는 실험이 이 과정을 보여 준다.

    ReentrantLock 객체가 Sync를 가리키고, Sync 안에 state와 소유 스레드, head·tail이 가리키는 대기 큐가 있으며, 해제 시 head 다음 노드가 unpark된다는 것을 보여 준다. 메모리 구조도. 왼쪽 위에 둥근 사각형 "ReentrantLock", 그 안에서 오른쪽으로 화살표가 나가 큰 사각형 "Sync (NonfairSync)"를 가리킨다. Sync 안 위쪽에 작은 칸 두 개: "state = 1", "owner = T1". Sync 안 아래쪽에 가로로 노드 세 개를 이어 그린다: 첫 노드 회색 "더미 head", 두 번째 노드 "T2 · WAITING", 세 번째 노드 "T3 · WAITING". 노드 사이에 위쪽 오른쪽 방향 화살표와 아래쪽 왼쪽 방향 화살표 한 쌍씩(next, prev). 첫 노드 위에 라벨 "head", 마지막 노드 위에 라벨 "tail". T2, T3 노드 아래에 작은 달 모양 아이콘과 라벨 "park". 오른쪽 바깥에 스레드 아이콘 "T1"이 있고, T1에서 T2 노드로 굵은 주황색 곡선 화살표, 라벨 "unlock → unpark". 평면 벡터 스타일, 흰 배경. 경합이 생기면 기다리는 스레드는 노드가 되어 줄을 서고 park한다. 해제하는 스레드는 head 다음 노드 하나만 깨운다.

    공정 락과 비공정 락: 끼어들기(barging)

    앞의 추적에서 지나친 틈이 하나 있다. T1이 state를 0으로 만들고 T2를 unpark한 순간부터, T2가 실제로 CPU를 받아 루프로 돌아와 CAS를 시도하기까지는 시간이 걸린다. 운영체제가 잠들어 있던 스레드를 실행 대기열에 올리고 코어를 배정하는 데 걸리는 시간이다. 그 사이에 줄을 서지 않은 새 스레드 T4가 lock()을 부르면 어떻게 될까. NonfairSync.initialTryLock()의 첫 줄은 주석대로 "아무 검사 없이(unguarded)" CAS를 시도한다. state가 0이므로 T4가 성공한다. 이것이 끼어들기(barging)다. 뒤늦게 깨어난 T2의 tryAcquire는 실패하고, T2는 다시 기다려야 한다.

    이렇게 운 나쁜 재대기가 반복되는 것을 완화하는 장치도 소스에 있다. park에서 깨어날 때마다 spins = postSpins = (byte)((postSpins << 1) | 1)로 재시도 횟수를 1, 3, 7, 15처럼 늘리고, 맨 앞 노드는 다시 park하기 전에 그 횟수만큼 Thread.onSpinWait()을 섞어 가며 재시도한다. 주석은 "깨어날 때마다 재시도를 지수적으로 늘린다(최대 256)"고 설명한다.

    FairSync는 이 끼어들기를 막는다. 두 메서드 모두 state가 0이어도 줄에 다른 스레드가 있으면 CAS를 시도하지 않는다.

    // FairSync
final boolean initialTryLock() {
    Thread current = Thread.currentThread();
    int c = getState();
    if (c == 0) {
        if (!hasQueuedThreads() && compareAndSetState(0, 1)) {
            setExclusiveOwnerThread(current);
            return true;
        }
    } else if (getExclusiveOwnerThread() == current) {
        // ... 재진입 처리는 NonfairSync와 같다
    }
    return false;
}

protected final boolean tryAcquire(int acquires) {
    if (getState() == 0 && !hasQueuedPredecessors() &&
        compareAndSetState(0, acquires)) {
        setExclusiveOwnerThread(Thread.currentThread());
        return true;
    }
    return false;
}

    공정 락에서 T4는 state가 0인 것을 보고도 hasQueuedThreads()가 true이므로 포기하고 T3 뒤에 줄을 선다. 그 결과 락은 줄 선 순서대로 넘어간다. 문서의 표현으로는 경합 상황에서 "가장 오래 기다린 스레드에게 접근을 주는 쪽을 선호한다".

    그런데 왜 기본값이 비공정일까. API 문서는 공정 락을 많은 스레드가 쓰는 프로그램이 "전체 처리량이 더 낮을 수 있다(즉 느리다, 종종 훨씬 느리다)"고 경고하고, 대신 락을 얻는 데 걸리는 시간의 편차가 작고 기아가 없다고 적는다. 이유는 앞에서 본 틈에 있다. 공정 락에서는 락이 풀릴 때마다 다음 차례가 이미 잠든 스레드로 정해져 있으므로, 그 스레드가 깨어나 CPU를 받을 때까지 락은 아무도 쓰지 않은 채 비어 있다. 비공정 락에서는 그 틈에 이미 CPU 위에서 달리고 있던 스레드가 락을 써 버리므로, 같은 시간에 더 많은 임계 영역이 실행된다. 공정성과 처리량은 이렇게 맞바꾸는 관계다.

    공정성의 범위에 대해서도 문서는 두 가지 단서를 단다. 첫째, 락의 공정성은 스레드 스케줄링의 공정성을 보장하지 않는다. 공정 락을 쓰는 여러 스레드 중 하나가 연속으로 여러 번 락을 얻는 동안 다른 스레드는 진행하지 못할 수 있다. 줄에 서지도 못할 만큼 CPU를 받지 못한 스레드는 순서를 주장할 수조차 없기 때문이다. 둘째, 시간 제한이 없는 tryLock()은 공정성 설정을 따르지 않는다. 소스에서 tryLock()은 Sync.tryLock()을 부르는데, 이 메서드는 공정이든 비공정이든 state가 0이면 곧장 CAS를 시도한다. 공정성을 지키며 즉시 시도하고 싶다면 문서의 권고대로 tryLock(0, TimeUnit.SECONDS)를 쓴다. 이 경로는 FairSync의 initialTryLock()과 tryAcquire를 거치기 때문이다.

    unlock 후 대기 스레드가 깨어나 CPU를 받기까지의 틈에, 비공정 락에서는 새로 온 스레드가 락을 얻고 공정 락에서는 줄 뒤로 간다는 차이를 시간축으로 보여 준다. 위아래 두 줄의 시간축 다이어그램. 가로축은 왼쪽에서 오른쪽으로 흐르는 시간. 위 줄 제목 "비공정 락(기본값)", 아래 줄 제목 "공정 락". 각 줄에 가로 막대 세 개를 위아래로 쌓는다: "T1", "T2", "T4". 두 줄 모두 T1 막대에 진한 색 구간 "락 보유" 후 점 "unlock" 표시. T2 막대에는 회색 구간 "park" 다음 노란 구간 "깨어나는 중". 위 줄: T1의 unlock 직후 T4 막대가 진한 색 "락 보유"로 바뀌고, T2의 노란 구간 끝에 빨간 X와 라벨 "획득 실패 → 다시 park". 아래 줄: T4 막대는 회색 "줄 서기", T2의 노란 구간 끝에서 진한 색 "락 보유"가 이어진다. 두 줄 사이에 작은 글씨 "깨어나는 틈". 평면 벡터 스타일, 흰 배경. 비공정 락은 깨어나는 틈을 이미 달리고 있는 스레드가 쓰게 해 처리량을 얻고, 공정 락은 그 틈을 비워 두는 대신 순서를 지킨다.

    공정성의 대가를 운영체제에서 재기: 소유권 이전과 컨텍스트 스위치

    문서는 공정 락이 "종종 훨씬 느리다"고만 적고 수치는 주지 않는다. 앞 절의 설명이 맞다면, 즉 공정 락은 락이 풀릴 때마다 잠든 스레드에게 락을 넘겨야 한다면, 두 가지가 관찰되어야 한다. 첫째, 락의 소유자가 바뀌는 횟수(소유권 이전, handoff)가 공정 락에서 훨씬 많아야 한다. 둘째, 이전할 때마다 잠든 스레드를 깨워야 하므로 운영체제가 수행하는 컨텍스트 스위치(context switch)도 그만큼 늘어야 한다. 네 스레드가 같은 락으로 아주 짧은 임계 영역을 20만 번씩 실행하게 하고, 임계 영역 안에서 직전 소유자와 지금 스레드가 다를 때마다 횟수를 세어 보자.

    import java.util.concurrent.locks.ReentrantLock;

public class FairCost {
    static long count, handoffs;
    static Thread lastOwner;

    public static void main(String[] args) throws Exception {
        boolean fair = Boolean.parseBoolean(args[0]);
        int threads = 4, perThread = 200_000;
        ReentrantLock lock = new ReentrantLock(fair);
        Thread[] ts = new Thread[threads];
        for (int i = 0; i < threads; i++) {
            ts[i] = new Thread(() -> {
                Thread me = Thread.currentThread();
                for (int k = 0; k < perThread; k++) {
                    lock.lock();
                    try {
                        count++;
                        if (lastOwner != me) { handoffs++; lastOwner = me; }
                    } finally {
                        lock.unlock();
                    }
                }
            });
        }
        long t0 = System.nanoTime();
        for (Thread t : ts) t.start();
        for (Thread t : ts) t.join();
        long ms = (System.nanoTime() - t0) / 1_000_000;
        System.out.printf("fair=%b count=%d handoffs=%d elapsed=%dms%n", fair, count, handoffs, ms);
    }
}

    count, handoffs, lastOwner는 volatile이 아니지만 모두 락 안에서만 읽고 쓰므로, 앞에서 본 대로 락의 happens-before가 가시성을 보장한다. 마지막의 출력은 join() 뒤에 있으므로 역시 최종 값을 본다. macOS의 /usr/bin/time -l로 실행하면 프로세스가 겪은 컨텍스트 스위치 수(rusage 구조체의 ru_nvcsw·ru_nivcsw)가 함께 나온다. 아래는 이 실험 환경(8코어 Mac, OpenJDK 21.0.13)에서 두 방식을 번갈아 두 번씩 실행한 결과다. 시간과 횟수는 실행마다, 기계마다 다르다. 이 도구는 스위치의 거의 전부를 "involuntary"로 분류해 보고했는데, 여기서는 분류는 따지지 않고 voluntary와 involuntary를 더한 값만 본다. 비교 기준으로, 한 줄을 출력하고 끝나는 프로그램을 같은 방법으로 재면 150~200회 정도였다.

    두 방식 모두 count는 정확히 800000이다. 상호 배제와 가시성은 똑같이 지켜졌다. 차이는 나머지 세 열에 있다. 비공정 락에서는 80만 번의 획득 가운데 소유자가 바뀐 것이 1만 5천 번 안팎, 2% 정도다. 락을 푼 스레드는 여전히 CPU 위에서 달리고 있으므로, 다음 반복의 lock()에서 initialTryLock()의 검사 없는 CAS에 곧바로 성공한다. 줄 선 스레드에게 넘기는 대신 자기 자신이 다시 끼어드는 일이 대부분이었다는 뜻이다. 그동안 줄 선 스레드들은 park한 채 잠들어 있으므로 커널이 할 일이 별로 없고, 컨텍스트 스위치는 기준값보다 수천 회 많은 데 그쳤다.

    공정 락에서는 80만 번 중 79만 9천여 번, 사실상 매번 소유자가 바뀌었다. 소스로 이유를 따라가 보자. T1이 unlock()하면 signalNext(head)가 맨 앞 노드의 WAITING 비트를 지우고 그 스레드를 unpark한다. 이때 깨운 노드는 아직 큐에 남아 있다. 깨어난 스레드가 락을 얻어 자기 노드를 head로 만들 때 비로소 빠진다. 그래서 T1이 곧바로 다시 lock()을 부르면, hasQueuedThreads()가 tail에서 head 쪽으로 훑다가 status가 0 이상인 그 노드를 발견해 true를 돌려주고, FairSync.initialTryLock()은 state가 0인데도 CAS를 시도하지 않는다. T1은 줄 끝에 서서 park하고, 락은 방금 깨운 스레드에게 간다. 이 과정이 매번 되풀이되므로 획득 한 번마다 "잠든 스레드를 커널이 깨워 코어에 올리고, 넘겨준 스레드는 잠든다"가 일어난다. 컨텍스트 스위치가 86만 회로 소유권 이전 횟수와 같은 자릿수까지 뛴 것이 그 흔적이다. 경과 시간이 100배 가까이 벌어진 것은 count++ 때문이 아니라 이 깨우고 재우는 비용 때문이다.

    이 실험에서 코어는 8개이고 스레드는 4개였다. CPU가 모자라서 생긴 차이가 아니라는 뜻이다. 공정 락의 비용은 "다음 차례가 항상 잠들어 있는 스레드"라는 구조에서 나온다. 그리고 비공정 락의 높은 처리량은 같은 스레드가 락을 연달아 다시 얻는 데서 나오므로, 그 대가로 특정 스레드가 한동안 락을 독차지할 수 있다. 문서가 말하는 처리량과 대기 시간 편차의 맞바꿈이 소유권 이전 횟수라는 숫자 하나에 그대로 드러난다.

    메모리 가시성: 라이브러리 락은 어떻게 happens-before를 만드는가

    5회차와 6회차에서 본 대로, 락이 하는 일은 상호 배제만이 아니다. JLS 17.4.4는 "모니터 m의 unlock 행동은 그 뒤에 오는 m의 모든 lock 행동과 synchronizes-with 관계"라고 정하고, 17.4.5는 이것을 happens-before로 이어 준다. 그래서 synchronized 블록 안에서 쓴 값은 같은 모니터로 다음에 들어오는 스레드에게 반드시 보인다. 그런데 ReentrantLock은 JVM이 특별 취급하는 모니터가 아니라 평범한 자바 클래스다. 이 락도 같은 보장을 줄까.

    Lock 인터페이스 문서의 "Memory Synchronization" 절이 답한다. 모든 Lock 구현은 내장 모니터 락과 같은 메모리 동기화 의미를 강제해야 한다. 성공한 lock은 JLS의 Lock 행동과, 성공한 unlock은 Unlock 행동과 같은 메모리 동기화 효과를 가진다. 문서는 실패한 잠금·해제와 재진입 잠금·해제에는 메모리 동기화 효과가 요구되지 않는다고 덧붙인다. 보장의 범위가 "성공한 획득과 해제"라는 점을 기억해 두자.

    구현이 이 약속을 지키는 방법은 앞에서 본 코드에 이미 들어 있다. AQS의 state는 volatile이다. JLS 17.4.4는 volatile 변수 v에 대한 쓰기가 그 뒤에 오는 모든 스레드의 v 읽기와 synchronizes-with 관계라고 정한다. T1의 흐름은 "임계 영역에서 공유 데이터 쓰기 → tryRelease의 setState(0)(volatile 쓰기)"이고, T2의 흐름은 "compareAndSetState(0, 1)(volatile 읽기와 쓰기의 효과를 가지는 CAS) → 임계 영역에서 공유 데이터 읽기"다. 프로그램 순서와 volatile 규칙을 이으면 T1의 쓰기는 T2의 읽기보다 happens-before다. JVM의 마법 없이, JLS가 정한 volatile 규칙과 AQS 문서가 compareAndSetState에 명시한 메모리 의미(volatile 읽기와 쓰기)만으로 라이브러리 락이 모니터 락과 같은 가시성을 얻는다. tryRelease가 소유자 필드를 비운 다음에 setState를 부르는 순서도 같은 이유다. volatile 쓰기 앞에 둔 일반 쓰기는 그 volatile 값을 읽는 쪽에 함께 보인다.

    이 장의 핵심

    ReentrantLock은 volatile int state 하나와 CAS로 소유권을 다투고, 진 스레드는 자바 코드로 관리하는 대기 큐에 줄을 서서 LockSupport.park로 잠든다. 해제는 state를 되돌리고 맨 앞 대기자 하나를 unpark한다. 대기열이 JVM 내부가 아니라 자바 코드에 있기 때문에 시간 제한, 인터럽트에 의한 포기, 공정한 순서 같은 정책을 고를 수 있고, volatile의 happens-before 규칙 덕분에 모니터 락과 같은 가시성을 보장한다.

    ReentrantLock 활용: lock-try-finally 관용구

    이제 실제 코드에 써 보자. 좌석이 한 개 남은 공연의 예매 창구를 생각한다. "남은 좌석 확인 → 결제 검증 → 좌석 차감"은 하나로 묶여야 하는 검사 후 행동(check-then-act)이다. 6회차에서 본 것처럼 이것을 보호하지 않으면 두 요청이 모두 "남은 좌석 1"을 보고 둘 다 성공해 좌석이 -1이 된다.

    import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.Lock;
import java.util.concurrent.locks.ReentrantLock;

public class SeatCounter {
    private final Lock lock = new ReentrantLock();
    private int remaining;

    public SeatCounter(int seats) {
        this.remaining = seats;
    }

    public boolean reserve() {
        String me = Thread.currentThread().getName();
        lock.lock();
        try {
            System.out.println("[" + me + "] 검사 시작, 남은 좌석=" + remaining);
            if (remaining <= 0) {
                System.out.println("[" + me + "] 매진");
                return false;
            }
            sleep(500);                 // 결제 검증 같은 느린 작업을 흉내 낸다
            remaining--;
            System.out.println("[" + me + "] 예매 성공, 남은 좌석=" + remaining);
            return true;
        } finally {
            lock.unlock();
        }
    }

    public boolean reserveOrGiveUp() {
        String me = Thread.currentThread().getName();
        if (!lock.tryLock()) {
            System.out.println("[" + me + "] 다른 요청 처리 중, 즉시 포기");
            return false;
        }
        try {
            sleep(500);
            if (remaining <= 0) return false;
            remaining--;
            System.out.println("[" + me + "] 예매 성공");
            return true;
        } finally {
            lock.unlock();
        }
    }

    public boolean reserveWithin(long millis) throws InterruptedException {
        String me = Thread.currentThread().getName();
        if (!lock.tryLock(millis, TimeUnit.MILLISECONDS)) {
            System.out.println("[" + me + "] " + millis + "ms 안에 락을 얻지 못해 포기");
            return false;
        }
        try {
            sleep(500);
            if (remaining <= 0) return false;
            remaining--;
            System.out.println("[" + me + "] 예매 성공");
            return true;
        } finally {
            lock.unlock();
        }
    }

    private static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    public static void main(String[] args) throws Exception {
        String mode = args.length > 0 ? args[0] : "lock";
        SeatCounter counter = new SeatCounter(1);
        Runnable task = switch (mode) {
            case "try" -> counter::reserveOrGiveUp;
            case "timed" -> () -> {
                try { counter.reserveWithin(100); } catch (InterruptedException e) { }
            };
            default -> counter::reserve;
        };
        Thread a = new Thread(task, "user-A");
        Thread b = new Thread(task, "user-B");
        a.start(); b.start();
        a.join(); b.join();
        System.out.println("최종 남은 좌석=" + counter.remaining);
    }
}
    [user-A] 검사 시작, 남은 좌석=1
[user-A] 예매 성공, 남은 좌석=0
[user-B] 검사 시작, 남은 좌석=0
[user-B] 매진
최종 남은 좌석=0

    reserve()의 모양이 문서가 권하는 관용구 그대로다. lock()을 부른 바로 다음 줄에서 try를 열고, finally에서 unlock()한다. 임계 영역 안에서 return false로 빠져나가든 예외가 나든 finally가 락을 풀어 준다. user-B는 user-A가 500ms 동안 결제를 검증하는 내내 lock()에서 기다렸다가, user-A가 푼 뒤에 들어와 이미 0이 된 좌석을 정확히 본다. 앞 절에서 본 happens-before 덕분에 user-A의 remaining--이 user-B에게 보인다.

    lock()을 try 밖에 두는 것도 이유가 있다. 다음 코드는 해제는 확실히 하겠다는 의도로 획득까지 try 안에 넣었다.

    import java.util.concurrent.locks.ReentrantLock;

public class LockInsideTry {
    public static void main(String[] args) {
        ReentrantLock lock = new ReentrantLock();
        Thread.currentThread().interrupt();
        try {
            try {
                lock.lockInterruptibly();   // 잘못된 위치: try 안
                System.out.println("작업");
            } finally {
                lock.unlock();
            }
        } catch (Exception e) {
            System.out.println("잡힌 예외: " + e);
        }
    }
}
    잡힌 예외: java.lang.IllegalMonitorStateException

    획득이 InterruptedException으로 실패했는데도 finally가 실행되어 가지지도 않은 락을 풀려고 했고, 거기서 난 IllegalMonitorStateException이 원래 예외를 덮어 버렸다. 호출자는 진짜 원인인 인터럽트를 알 길이 없다. lock() 자체는 인터럽트로 실패하지 않지만, 앞에서 본 재진입 한도 초과 Error처럼 획득 단계의 실패는 언제든 가능하다. "획득에 성공한 다음에만 해제를 약속한다"는 것이 관용구의 의미이고, 그래서 try는 획득 바로 다음 줄에서 시작한다.

    대기 중단 1: tryLock과 tryLock(timeout)

    이제 이 회차의 출발점이었던 무한 대기 문제를 풀 차례다. 같은 SeatCounter를 다른 모드로 실행한다. reserveOrGiveUp()은 tryLock()으로 락이 비어 있을 때만 들어가고, reserveWithin(100)은 최대 100ms까지만 기다린다.

    tryLock()은 기다림이 전혀 없다. 소스로 보면 Sync.tryLock()은 state가 0이면 CAS, 내가 소유자면 재진입, 둘 다 아니면 바로 false다. 대기 큐 근처에도 가지 않으므로 스레드가 멈출 일이 없다. "지금 바쁘면 다음에 하겠다"는 정책, 예를 들어 주기적인 캐시 갱신 작업이 이미 돌고 있으면 이번 회차는 건너뛰는 식의 처리에 맞다. 다만 반환값을 반드시 확인해야 한다. false를 받고도 임계 영역에 들어가거나, 얻지 못한 락을 finally에서 풀면 앞 절의 문제가 그대로 생긴다. 그래서 위 코드는 if (!lock.tryLock()) return으로 실패 경로를 먼저 끝내고, 성공한 뒤에야 try를 연다.

    tryLock(long, TimeUnit)은 그 중간이다. 소스에서 tryLockNanos는 인터럽트 확인, initialTryLock(), 그리고 AQS의 tryAcquireNanos로 이어지고, 결국 앞의 acquire 루프에 timed = true와 마감 시각(System.nanoTime() + nanosTimeout)을 넘긴다. 루프는 park 대신 LockSupport.parkNanos(this, 마감 - 현재)로 멈추고, 깨어났을 때 남은 시간이 0 이하이면 루프를 빠져나와 노드를 취소하고 false를 돌려준다. 남은 시간을 매번 마감 시각에서 다시 계산하므로, 가짜 깨어남이 여러 번 끼어도 총 대기 시간이 늘어나지 않는다. 이 메서드가 기다리는 동안 스레드 상태는 TIMED_WAITING이다. 시간이 0 이하이면 문서대로 전혀 기다리지 않는다.

    시간 제한 획득이 가장 빛나는 곳은 교착 상태(deadlock) 회피다. 두 창고 사이에 재고를 옮기는데, 한 스레드는 서울에서 부산으로, 다른 스레드는 부산에서 서울로 옮긴다고 하자. 두 락을 lock()으로 순서 없이 잡으면 서로가 가진 락을 기다리며 영원히 멈출 수 있다. synchronized라면 락 획득 순서를 전역적으로 정하는 것 말고는 방법이 없다. tryLock(timeout)을 쓰면 "둘 다 얻지 못하면 쥔 것을 내려놓고 다시 시도"할 수 있다.

    import java.util.concurrent.ThreadLocalRandom;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class StockMover {
    static class Warehouse {
        final ReentrantLock lock = new ReentrantLock();
        int stock;
        Warehouse(int stock) { this.stock = stock; }
    }

    // 두 창고의 락을 모두 얻어야만 옮긴다. 하나라도 못 얻으면 쥔 것을 놓고 다시 시도한다.
    static void move(Warehouse from, Warehouse to, int qty) throws InterruptedException {
        while (true) {
            if (from.lock.tryLock(10, TimeUnit.MILLISECONDS)) {
                try {
                    if (to.lock.tryLock(10, TimeUnit.MILLISECONDS)) {
                        try {
                            from.stock -= qty;
                            to.stock += qty;
                            return;
                        } finally {
                            to.lock.unlock();
                        }
                    }
                } finally {
                    from.lock.unlock();
                }
            }
            // 둘 다 같은 박자로 재시도하지 않도록 잠깐 무작위로 쉰다
            Thread.sleep(ThreadLocalRandom.current().nextInt(1, 5));
        }
    }

    public static void main(String[] args) throws Exception {
        Warehouse seoul = new Warehouse(1000), busan = new Warehouse(1000);
        Thread t1 = new Thread(() -> {
            try { for (int i = 0; i < 1000; i++) move(seoul, busan, 1); } catch (InterruptedException e) { }
        });
        Thread t2 = new Thread(() -> {
            try { for (int i = 0; i < 1000; i++) move(busan, seoul, 1); } catch (InterruptedException e) { }
        });
        t1.start(); t2.start();
        t1.join(); t2.join();
        System.out.println("seoul=" + seoul.stock + ", busan=" + busan.stock
                + ", total=" + (seoul.stock + busan.stock));
    }
}

    대기 중단 2: 인터럽트와 lockInterruptibly

    시간 제한 말고 다른 스레드가 "그만 기다려"라고 신호를 줄 수도 있어야 한다. 서버를 종료할 때, 사용자가 요청을 취소했을 때가 그렇다. 3, 4회차에서 본 대로 자바에서 그 신호는 인터럽트다. lock()과 lockInterruptibly()가 인터럽트에 어떻게 다르게 반응하는지 한 번에 확인해 보자.

    import java.util.concurrent.locks.ReentrantLock;

public class InterruptDemo {
    static final ReentrantLock lock = new ReentrantLock();

    public static void main(String[] args) throws Exception {
        lock.lock();
        try {
            // (1) lock(): 인터럽트를 받아도 계속 기다린다
            Thread a = new Thread(() -> {
                lock.lock();
                try {
                    System.out.println("[a] 락 획득, interrupted="
                            + Thread.currentThread().isInterrupted());
                } finally {
                    lock.unlock();
                }
            }, "a");
            // (2) lockInterruptibly(): 인터럽트를 받으면 대기를 포기한다
            Thread b = new Thread(() -> {
                try {
                    lock.lockInterruptibly();
                    try {
                        System.out.println("[b] 락 획득");
                    } finally {
                        lock.unlock();
                    }
                } catch (InterruptedException e) {
                    System.out.println("[b] " + e + ", interrupted="
                            + Thread.currentThread().isInterrupted());
                }
            }, "b");
            a.start();
            b.start();
            Thread.sleep(100);
            a.interrupt();
            b.interrupt();
            Thread.sleep(100);
            System.out.println("[main] a=" + a.getState() + ", b=" + b.getState()
                    + ", queueLength=" + lock.getQueueLength());
        } finally {
            lock.unlock();
        }
        Thread.sleep(100);

        // (3) 진입 시점에 이미 인터럽트 상태면, 락이 비어 있어도 예외
        Thread.currentThread().interrupt();
        try {
            lock.lockInterruptibly();
            System.out.println("[main] 획득");
            lock.unlock();
        } catch (InterruptedException e) {
            System.out.println("[main] 비어 있는 락인데도 " + e);
        }
        // (4) tryLock()은 인터럽트 상태와 무관하게 동작한다
        Thread.currentThread().interrupt();
        boolean ok = lock.tryLock();
        System.out.println("[main] tryLock()=" + ok + ", interrupted=" + Thread.interrupted());
        if (ok) lock.unlock();
    }
}

    한 줄씩 해석하자. b는 인터럽트를 받자 InterruptedException으로 대기를 포기했고, 예외를 받은 시점에 인터럽트 플래그는 꺼져 있다. 블로킹 메서드가 인터럽트를 예외로 바꿔 알릴 때 플래그를 지우는 관례 그대로이며, lockInterruptibly()의 문서도 "예외를 던지고 인터럽트 상태를 지운다"고 적는다. 대기 큐 길이가 2에서 1로 줄었다는 것은 b의 노드가 취소되어 큐에서 떨어져 나갔다는 뜻이다. 반면 a는 같은 인터럽트를 받고도 여전히 WAITING이다. main이 락을 풀자 a가 락을 얻었고, 그때 인터럽트 플래그가 켜져 있다.

    이 차이는 AQS acquire 루프의 park 직후 두 줄에서 나온다.

    LockSupport.park(this);
node.clearStatus();
if ((interrupted |= Thread.interrupted()) && interruptible)
    break;

    park는 인터럽트를 받으면 그냥 돌아온다. 루프는 Thread.interrupted()로 플래그를 읽으면서 지우고, 그 사실을 지역 변수 interrupted에 기억한다. lockInterruptibly()에서 온 호출이면 interruptible이 true이므로 루프를 빠져나가 노드를 취소하고, 호출자인 acquireInterruptibly가 InterruptedException을 던진다. lock()에서 온 호출이면 루프를 계속 돈다. 플래그를 지웠으므로 다음 park는 다시 정상적으로 멈춘다. 그리고 마침내 락을 얻으면 if (interrupted) current.interrupt();로 지웠던 플래그를 되살려 놓는다. 인터럽트를 무시하되 삼키지는 않는 것이다. 인터럽트 신호를 처리할 책임은 락을 얻은 뒤의 코드에 넘어간다.

    세 번째와 네 번째 결과도 의미가 있다. lockInterruptibly()는 락이 비어 있어도 진입 시점에 플래그가 켜져 있으면 획득을 시도하지 않고 예외를 던진다. 소스에서 Sync.lockInterruptibly()의 첫 줄이 if (Thread.interrupted()) throw new InterruptedException();이다. 문서는 이 메서드가 명시적인 인터럽트 지점이므로 "정상적인 획득이나 재진입 획득보다 인터럽트에 응답하는 것을 우선한다"고 적는다. 반면 tryLock()은 인터럽트를 확인하지 않고 락을 얻었고 플래그도 그대로 두었다. tryLock(timeout)은 lockInterruptibly()와 같은 방식으로 진입 시점과 대기 중 모두 인터럽트에 반응하며, 문서는 이 경우 시간 초과 보고보다도 인터럽트 응답을 우선한다고 적는다.

    획득 방법대기 중 스레드 상태대기 중 인터럽트진입 시 플래그가 켜져 있으면시간 초과
    synchronizedBLOCKED무시, 계속 대기무시하고 획득 시도없음
    lock()WAITING무시하고 계속 대기, 획득 후 플래그 복원무시하고 획득 시도없음
    lockInterruptibly()WAITINGInterruptedException, 플래그 지움즉시 InterruptedException없음
    tryLock()기다리지 않음해당 없음무시하고 획득 시도즉시 false

    락이 잡혀 있을 때 lock, lockInterruptibly, tryLock, tryLock(timeout)이 각각 어떤 길로 끝나는지를 한 장의 분기도로 보여 준다. 왼쪽에서 오른쪽으로 흐르는 순서도. 맨 왼쪽 마름모 "락이 비어 있나?". 위쪽 "예" 화살표는 초록 상자 "획득"으로 간다. 아래쪽 "아니오"에서 네 갈래로 갈라지는 가로 레인 네 개: 레인 1 "lock()" → 회색 상자 "park" → 인터럽트 번개 아이콘에서 다시 "park"로 돌아오는 고리 화살표 → 초록 상자 "획득 + 플래그 복원". 레인 2 "lockInterruptibly()" → 회색 상자 "park" → 번개 아이콘 → 빨간 상자 "InterruptedException". 레인 3 "tryLock()" → 바로 주황 상자 "false". 레인 4 "tryLock(시간)" → 회색 상자 "parkNanos" → 모래시계 아이콘 → 주황 상자 "false", 같은 회색 상자에서 번개 아이콘 → 빨간 상자 "InterruptedException". 평면 벡터 스타일, 흰 배경. lock()만 인터럽트를 무시하고 끝까지 기다린다. 나머지는 기다리지 않거나, 시간이나 인터럽트로 대기를 끝낼 수 있다.

    관찰하기: 스레드 덤프와 교착 상태 탐지

    운영 중인 서버가 느려졌을 때 가장 먼저 보는 것이 스레드 덤프다. 락의 종류에 따라 덤프에 보이는 모습이 다르므로 차이를 알아 두어야 한다. 다음 프로그램은 main이 모니터와 ReentrantLock을 모두 쥔 채, 세 스레드를 각각 synchronized, lock(), tryLock(10초)로 기다리게 한다.

    import java.util.concurrent.TimeUnit;
import java.util.concurrent.locks.ReentrantLock;

public class StateCompare {
    static final Object monitor = new Object();
    static final ReentrantLock lock = new ReentrantLock();

    public static void main(String[] args) throws Exception {
        synchronized (monitor) {
            lock.lock();
            try {
                Thread a = new Thread(() -> { synchronized (monitor) { } }, "sync-waiter");
                Thread b = new Thread(() -> { lock.lock(); lock.unlock(); }, "lock-waiter");
                Thread c = new Thread(() -> {
                    try {
                        if (lock.tryLock(10, TimeUnit.SECONDS)) lock.unlock();
                    } catch (InterruptedException e) { }
                }, "trylock-waiter");
                a.start(); b.start(); c.start();
                Thread.sleep(200);
                System.out.println(a.getName() + " : " + a.getState());
                System.out.println(b.getName() + " : " + b.getState());
                System.out.println(c.getName() + " : " + c.getState());
                System.out.println("queueLength=" + lock.getQueueLength()
                        + " hasQueuedThread(b)=" + lock.hasQueuedThread(b));
                if (args.length > 0) Thread.sleep(Long.parseLong(args[0]));
            } finally {
                lock.unlock();
            }
        }
    }
}

    ???로 찍힌 줄은 JVM이 실행 중에 만든 인터프리터·JIT 코드, 즉 자바 메서드의 프레임이다. sample은 이 코드의 심볼을 모르므로 이름을 붙이지 못한다. 그 아래가 JVM 런타임(libjvm.dylib)이다. 경로는 다르다. sync-waiter는 이 실행에서 인터프리터가 monitorenter 바이트코드를 처리하다가 InterpreterRuntime::monitorenter로 런타임에 들어왔고, ObjectMonitor::enter와 EnterI를 거쳐 스레드마다 하나씩 있는 PlatformEvent로 잠들었다. lock-waiter는 자바 코드인 AQS가 큐 관리를 모두 끝낸 뒤 Unsafe.park로 내려와 Parker로 잠들었다. 그런데 맨 아래 두 줄은 세 스레드 모두 같다. POSIX 조건 변수 대기인 _pthread_cond_wait, 그리고 그것이 부르는 __psynch_cvwait다. __psynch_cvwait는 macOS 커널(XNU)의 시스템 콜 표 bsd/kern/syscalls.master에 305번 psynch_cvwait로 등록된 시스템 콜의 사용자 공간 진입점이다. 모니터 대기, park, sleep이 이 환경에서는 모두 커널의 같은 조건 변수 대기로 끝난다.

    sync-waiter의 프레임이 시간 제한이 있는 park_nanos인 것도 소스로 설명된다. OpenJDK 21의 objectMonitor.cpp에서 EnterI는 짧은 시도(TryLock, TrySpin)가 실패하면 자기를 나타내는 ObjectWaiter 노드를 모니터의 _cxq 리스트 맨 앞에 CAS로 밀어 넣는다. 이때 _cxq와 _EntryList가 모두 비어 있던 상태에서 처음 줄을 선 스레드는 "Responsible" 스레드로 지정된다. 소스 주석에 따르면 이 스레드는 모니터가 풀렸는데도 기다리던 스레드가 모두 잠든 채 남는 상황(stranding)을 막기 위해 무기한 park 대신 시간 제한 park를 쓴다. 대기 시간은 1밀리초에서 시작해 깨어날 때마다 8배씩 늘고 1000밀리초(MAX_RECHECK_INTERVAL)에서 멈춘다. 이 실험의 sync-waiter는 유일한 경쟁자였으므로 Responsible이 되었고, 그래서 park_nanos로 잠들어 있었다. 정리하면 모니터 락에도 대기 큐가 있다. 다만 그 큐가 JVM 안의 C++ 자료구조(_cxq, _EntryList)이고, 순서와 깨우기 정책이 JVM 코드에 고정되어 있을 뿐이다.

    그렇다면 BLOCKED와 WAITING이라는 이름은 어디서 오는가. 답은 잠들기 직전에 JVM이 붙이는 이름표다. java.lang.Thread 객체에는 JVM이 관리하는 threadStatus 정수 필드가 있고(JDK 21에서는 Thread.holder 객체 안), 플랫폼 스레드의 getState()는 jdk.internal.misc.VM.toThreadState(holder.threadStatus)로 이 값의 비트를 검사해 열거값을 돌려줄 뿐이다. 값을 쓰는 쪽은 HotSpot이다. unsafe.cpp의 Unsafe_Park는 Parker::park를 부르기 전에 JavaThreadParkedState jtps(thread, time != 0);를 만들어 상태를 PARKED(시간이 있으면 PARKED_TIMED)로 바꾸고, 블록을 벗어날 때 원래 값으로 되돌린다.     가상 스레드의 park: 커널에서 잠드는 대신 캐리어를 내놓는다

    앞에서 LockSupport.park()가 가상 스레드일 때 VirtualThreads.park()로 갈라진다고만 했다. JDK 21의 java.lang.VirtualThread.park()를 열어 보면 같은 허가 모델이 자바 코드로 다시 구현되어 있다. 허가는 private volatile boolean parkPermit 필드다. park는 먼저 getAndSetParkPermit(false)로 허가를 소비해 보고, 허가가 있었거나 인터럽트 상태면 즉시 돌아온다. 아니면 상태를 PARKING으로 바꾸고 yieldContinuation(), 즉 Continuation.yield로 자기 실행 스택을 떼어 내 캐리어 스레드에서 내려온다(unmount). 내려온 뒤 afterYield()가 상태를 PARKED로 바꾸는데, 그 사이에 unpark가 와서 허가가 켜져 있으면 곧바로 다시 실행되도록 스케줄러에 제출한다. 플랫폼 스레드의 Parker가 뮤텍스를 쥐고 허가를 다시 확인하던 것과 같은 목적의 장치다.

    unpark()는 getAndSetParkPermit(true)로 허가를 켜고, 대상이 PARKED 상태면 CAS로 UNPARKED로 바꾼 뒤 submitRunContinuation()으로 이어서 실행할 작업을 스케줄러(ForkJoinPool)에 넣는다. 커널의 조건 변수에 신호를 보내는 것이 아니라, 작업 큐에 일감 하나를 넣는 것이다. 예외는 고정(pinned)된 경우다. synchronized 안이라서 yieldContinuation()이 실패하면 park는 parkOnCarrierThread로 가서 상태를 PINNED로 표시하고 U.park, 즉 캐리어 플랫폼 스레드의 Parker로 잠든다. 그러면 캐리어도 함께 커널에서 잠들고, unpark도 U.unpark(carrier)로 캐리어를 깨운다. 캐리어를 하나만 두고 두 경우를 비교해 보자.

    import java.util.concurrent.locks.ReentrantLock;

public class VtPark {
    static final ReentrantLock lock = new ReentrantLock();
    static final Object monitor = new Object();

    public static void main(String[] args) throws Exception {
        boolean useSync = args.length > 0 && args[0].equals("sync");
        long t0 = System.nanoTime();
        Runnable holdAndSleep = () -> {
            if (useSync) {
                synchronized (monitor) { sleep(500); }
            } else {
                lock.lock();
                try { sleep(500); } finally { lock.unlock(); }
            }
        };
        Thread holder = Thread.ofVirtual().start(holdAndSleep);
        Thread.sleep(50);                                  // holder가 먼저 락을 잡게 한다
        Thread[] waiters = new Thread[100];
        for (int i = 0; i < waiters.length; i++) {
            waiters[i] = Thread.ofVirtual().start(() -> {
                if (useSync) { synchronized (monitor) { } }
                else { lock.lock(); lock.unlock(); }
            });
        }
        Thread ticker = Thread.ofVirtual().start(() ->
                System.out.printf("ticker ran at %dms%n", (System.nanoTime() - t0) / 1_000_000));
        ticker.join();
        holder.join();
        for (Thread w : waiters) w.join();
        System.out.printf("%s: all done at %dms%n", useSync ? "synchronized" : "ReentrantLock",
                (System.nanoTime() - t0) / 1_000_000);
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); }
    }
}

    기본 선택은 여전히 synchronized다. 짧고, 해제를 잊을 수 없고, 바이트코드가 보여 주듯 해제 경로를 컴파일러가 책임진다. ReentrantLock은 표의 가운데 줄들, 즉 시간 제한, 인터럽트에 의한 포기, 공정성, 여러 대기 조건 중 하나가 실제로 필요할 때 고른다. 그 대가로 finally를 매번 정확히 써야 하는 책임을 진다.

    가상 스레드(virtual thread)를 쓰는 환경에서는 판단 기준이 하나 더 있다. Java 21 공식 가이드는 가상 스레드가 synchronized 블록이나 메서드 안에서 실행 중이면 캐리어 스레드에 고정(pinned)되어, 그 안에서 블로킹이 일어나도 캐리어를 놓아 주지 못한다고 설명한다. 그리고 자주, 오래 고정되는 곳에서는 긴 I/O를 ReentrantLock으로 보호하도록 고치라고 권한다. 앞에서 본 대로 LockSupport.park는 가상 스레드일 때 VirtualThreads.park()로 분기하므로, AQS 기반 락에서 기다리는 가상 스레드는 이 문제를 겪지 않는다. JDK 24부터는 JEP 491로 synchronized 안에서 블로킹하는 가상 스레드도 캐리어를 놓아 줄 수 있게 되었지만, Java 21 기준으로 작성하는 이 강좌에서는 21의 동작을 기준으로 삼는다.

    이 회차에서 만든 부품들은 남은 회차에서 계속 다시 쓰인다. 8회차와 9회차의 생산자 소비자 문제에서는 wait/notify의 한계를 보고, ReentrantLock.newCondition()으로 만든 Condition으로 생산자와 소비자의 대기 공간을 나누는 방법을 다룬다. Condition.await() 역시 내부적으로 AQS의 조건 큐와 park를 쓴다. 10회차에서는 이 회차에서 "원자적으로 바꾼다"고만 말한 compareAndSetState의 정체인 CAS를, 12·13회차에서는 이 락들 위에 지어진 ThreadPoolExecutor를 다룬다.
    synchronized의 한계
    모니터 락을 기다리는 BLOCKED 스레드는 시간 제한도 인터럽트도 없이 락을 얻을 때까지 기다리고, 다음 차례를 정하는 공정성도 선택할 수 없다.
    LockSupport.park / unpark
    스레드를 스케줄링 대상에서 빼고(WAITING/TIMED_WAITING) 콕 집어 되돌리는 기본 연산. 인터럽트를 받으면 예외 없이 돌아오고 플래그를 지우지 않는다.
    허가(permit)
    스레드당 최대 하나이며 쌓이지 않는다. 먼저 도착한 unpark도 허가로 남으므로 깨우기 신호가 유실되지 않는다. HotSpot에서는 Parker의 _counter에 1을 대입하는 것으로 구현된다.
    조건 재확인 루프
    park는 이유 없이 돌아올 수 있고 이유를 알려 주지 않으므로, volatile 조건을 루프에서 다시 확인하는 형태로만 쓴다.
    AQS
    volatile int state, 소유 스레드, CLH 변형 대기 큐로 이루어진 동기화 뼈대. 실패한 스레드는 노드로 줄을 서서 park하고, 해제는 head 다음 노드 하나를 unpark한다.
    ReentrantLock의 보유 횟수
    AQS state가 곧 보유 횟수다. 소유자가 다시 잠그면 1 늘고, 0이 될 때 비로소 풀리며 대기자를 깨운다. 소유자가 아닌 스레드의 unlock은 IllegalMonitorStateException이다.
    공정 락과 비공정 락
    비공정 락(기본값)은 새로 온 스레드의 끼어들기를 허용해 처리량을 얻고, 공정 락은 줄이 있으면 CAS를 시도하지 않아 순서를 지킨다. tryLock()은 공정성 설정을 따르지 않는다.
    대기 중단
    tryLock()은 기다리지 않고, tryLock(t, unit)은 시간이 지나면 false, lockInterruptibly()는 인터럽트에 InterruptedException으로 응답한다. lock()은 인터럽트를 무시하고 획득 후 플래그를 복원한다.
    lock-try-finally 관용구
    획득 바로 다음 줄에서 try를 열고 finally에서 unlock한다. 획득을 try 안에 두면 실패 시 엉뚱한 예외가 원래 예외를 덮는다.
    공정성의 비용
    공정 락은 매 획득이 잠든 스레드로의 소유권 이전이 되어 이전마다 커널의 깨우기와 컨텍스트 스위치가 따른다. 이 실험 환경에서 이전 횟수는 약 50배, 경과 시간은 약 100배 차이가 났다.
    BLOCKED와 WAITING의 실체
    POSIX 계열 OS(Linux, macOS)의 OpenJDK 21 HotSpot에서(os_posix.cpp) 모니터 대기(ObjectMonitor::EnterI)와 park(Parker::park)는 모두 pthread 조건 변수 대기로 내려간다. 상태 이름은 잠들기 직전 JVM이 threadStatus에 써 두는 값에서 나온다.

    운영 중 응답이 멈춘 서버의 스레드 덤프를 받았는데 BLOCKED 스레드가 하나도 없다면, 다음으로 볼 것은 WAITING (parking) 스레드의 parking to wait for 줄이다. 대상이 ReentrantLock$NonfairSync나 ReentrantReadWriteLock의 동기화 객체라면 락 경합이고, -l 옵션의 Locked ownable synchronizers에서 같은 주소를 가진 스레드가 범인이다. 그 스레드의 스택이 네트워크 읽기에 걸려 있다면, 락을 쥔 채 외부 호출을 한 설계가 근본 원인이다. 대상이 LinkedBlockingQueue 같은 큐의 조건 객체라면 대부분 일감을 기다리며 쉬는 정상 스레드다. 상태 값 하나로 판단하지 말고 blocker와 스택을 함께 읽어야 한다.

    ReentrantLock으로 바꿀지는 "어떤 대기 정책이 필요한가"로 판단한다. 외부 시스템 호출을 보호하는 락이라 상대가 멈추면 내 스레드도 무한히 묶이는 구조라면 tryLock(timeout)으로 실패를 빨리 드러내는 편이 낫다. 실패했을 때 무엇을 돌려줄지(재시도, 오류 응답, 대체 값)를 함께 설계해야 하므로 단순 치환이 아니다. 종료나 취소 신호에 반응해야 하는 작업이라면 lockInterruptibly()를 쓰고, 받은 InterruptedException을 삼키지 말고 상위로 전달하거나 플래그를 복원한다. 이런 요구가 없다면 synchronized를 유지하는 쪽이 실수의 여지가 적다.

    공정 락은 "공정한 것이 좋아 보여서" 켜는 옵션이 아니다. 문서가 경고하듯 많은 스레드가 쓰는 락에서는 처리량이 크게 떨어질 수 있다. 특정 요청이 계속 밀려 응답 시간의 꼬리(tail latency)가 길어지는 것이 측정으로 확인되었고, 처리량 손실을 감수할 수 있을 때 고려한다. 가상 스레드를 Java 21에서 도입한다면, 긴 I/O를 감싼 synchronized가 고정을 일으키는지 jdk.tracePinnedThreads나 JFR의 jdk.VirtualThreadPinned 이벤트로 먼저 측정하고, 자주·오래 고정되는 곳만 ReentrantLock으로 바꾸는 것이 공식 가이드의 권고다.

    1번. 첫 unpark로 허가가 1이 되고, 첫 park는 허가를 소비하고 즉시 돌아온다(허가 0). 이어서 unpark를 두 번 불러도 허가는 1에 머문다. 두 번째 park는 허가를 소비하고 즉시 돌아오고, 세 번째 park는 허가가 0이므로 멈춘다. 깨워 줄 다른 스레드가 없으므로 가짜 깨어남이 없다면 프로그램은 거기서 멈춰 있다. 허가가 대입(_counter = 1)으로 구현되어 쌓이지 않기 때문이다.

    2번. (1) T1의 두 번째 lock() 뒤: state=2, 소유자=T1, 큐 없음(head, tail 모두 null). 경합이 없었으므로 큐가 만들어지지 않았다. (2) T2의 lock() 뒤: CAS 실패, 소유자 아님 → acquire 루프에서 더미 헤드를 만들고 자기 노드를 붙인 뒤 WAITING 표시, park. state=2, 소유자=T1, 큐는 [더미] ⇄ [T2, WAITING], T2는 WAITING. (3) T1의 첫 unlock(): tryRelease에서 c=1이므로 free=false, 소유자 유지, signalNext를 부르지 않는다. state=1, T2는 여전히 park 중. (4) T1의 두 번째 unlock(): c=0, 소유자를 null로, state=0, signalNext(head)가 T2를 unpark. T2가 깨어나 CAS로 state=1, 소유자=T2가 되고 T2의 노드가 새 더미 헤드가 된다. 재진입한 락은 보유 횟수만큼 풀어야 대기자가 깨어난다는 것이 핵심이다.

    3번. 첫째, tryLock이 false를 돌려주거나 InterruptedException이 나도 finally가 unlock()을 부르므로, 가지지 않은 락을 풀다 IllegalMonitorStateException이 난다. 둘째, InterruptedException을 빈 catch로 삼켜 인터럽트 신호가 사라진다. 고친 형태는 if (!lock.tryLock(1, TimeUnit.SECONDS)) { /* 실패 처리 */ return; } try { work(); } finally { lock.unlock(); }이고, 메서드 선언에 throws InterruptedException을 붙여 상위로 전달하거나, 전달할 수 없다면 catch에서 Thread.currentThread().interrupt()로 플래그를 복원한다.

    4번. open이 volatile이 아니면 open()의 쓰기와 await()의 읽기 사이에 happens-before가 없다. worker는 unpark로 깨어난 뒤에도 낡은 false를 읽고 다시 park할 수 있고, 그 뒤로 깨워 줄 unpark가 없으므로 영원히 멈출 수 있다. API 문서가 park/unpark 순서는 volatile 접근에 대해서만 유지된다고 한 이유다. 대기자가 둘 이상이면 waiter 필드에 마지막으로 쓴 스레드만 남으므로, open()은 한 스레드만 unpark하고 나머지는 영원히 잠든다. 여러 대기자를 다루려면 AQS처럼 대기 스레드를 큐에 모아야 한다.

    5번. tryLock()은 Sync.tryLock()을 부르고, 이 메서드는 공정 여부와 관계없이 state가 0이면 곧장 CAS를 시도한다. 따라서 대기자가 있어도 성공한다(끼어들기). tryLock(0, TimeUnit.SECONDS)는 tryLockNanos를 거쳐 FairSync.initialTryLock()을 부르는데, 여기서 hasQueuedThreads()가 true이므로 CAS를 시도하지 않는다. 이어지는 tryAcquireNanos도 FairSync.tryAcquire의 hasQueuedPredecessors()에 막히고, 시간이 0이므로 기다리지 않고 false를 돌려준다. 문서가 공정성을 지키는 즉시 시도로 tryLock(0, TimeUnit.SECONDS)를 권하는 이유이며, 이 형태는 인터럽트도 확인한다는 점이 다르다.

     lock.lock()에서 기다리던 스레드에 다른 스레드가 interrupt()를 호출했다. 이후 일어나는 일로 옳은 것은? 즉시 InterruptedException이 발생하고 대기 큐에서 빠진다. 계속 기다리다가 락을 얻은 뒤 인터럽트 플래그가 켜진 상태로 lock()에서 돌아온다. 계속 기다리다가 락을 얻고, 인터럽트 플래그는 꺼진 상태로 돌아온다. 스레드 상태가 BLOCKED로 바뀌고 인터럽트는 무시된다. AQS의 acquire 루프는 park에서 돌아올 때마다 Thread.interrupted()로 플래그를 읽어 지역 변수에 기억하고, lock() 경로에서는 대기를 계속한다. 락을 얻으면 current.interrupt()로 플래그를 복원한다. 예외로 대기를 포기하는 것은 lockInterruptibly()의 동작이고, 플래그를 지운 채 돌아오면 신호가 사라진다. BLOCKED는 모니터 락 전용 상태라 ReentrantLock 대기자는 WAITING이다. 스레드 A가 아직 park하기 전에 다른 스레드가 LockSupport.unpark(A)를 세 번 호출했다. 그 뒤 A가 LockSupport.park()를 두 번 연속 호출하면(다른 개입이 없다고 가정)? 두 번 모두 멈춘다. unpark는 이미 멈춰 있는 스레드에게만 효과가 있다. 두 번 모두 즉시 돌아온다. 허가가 세 개 쌓여 있기 때문이다. 첫 번째는 즉시 돌아오고 두 번째는 멈춘다. 첫 번째는 멈추고 두 번째는 즉시 돌아온다. 허가는 스레드당 최대 하나이고 쌓이지 않는다. 먼저 도착한 unpark도 허가로 남으므로 첫 park는 그것을 소비하고 즉시 돌아온다. 두 번째 park 때는 허가가 없으므로 멈춘다. 허가가 쌓인다고 보는 것은 세마포어와 혼동한 것이고, 멈춘 스레드에게만 효과가 있다고 보는 것은 신호 유실을 막는 허가 모델의 목적을 놓친 것이다. 장애 시점의 스레드 덤프에 BLOCKED 스레드는 없고, 요청 처리 스레드 200개가 WAITING (parking)이며 모두 parking to wait for <0x...> (a java.util.concurrent.locks.ReentrantLock$NonfairSync)로 같은 주소를 가리킨다. 가장 타당한 해석은? 하나의 ReentrantLock에 경합이 몰렸다. -l 옵션의 Locked ownable synchronizers에서 그 주소를 가진 스레드를 찾아 무엇을 하고 있는지 봐야 한다. BLOCKED가 없으므로 락 경합은 없고, 스레드들은 일감을 기다리며 쉬는 중이다. JVM이 교착 상태를 감지해 스레드들을 자동으로 park시켰다. 공정 락을 쓰고 있다는 증거다. 비공정 락이면 BLOCKED로 표시된다. ReentrantLock의 대기자는 LockSupport.park(this)로 멈추므로 WAITING (parking)으로 보이고, blocker로 Sync 객체가 찍힌다. 같은 주소에 200개가 몰렸다면 한 락의 경합이다. BLOCKED는 모니터 락 전용이므로 BLOCKED가 없다는 것은 락 경합이 없다는 근거가 되지 못한다. JVM은 교착 상태를 탐지해 보고할 뿐 스레드를 park시키지 않으며, 공정 여부는 상태 표시와 무관하다(이름도 NonfairSync다). 비공정 ReentrantLock(기본값)이 공정 락보다 일반적으로 처리량이 높은 이유로 가장 정확한 것은? 비공정 락은 대기 큐를 사용하지 않기 때문이다. 비공정 락은 CAS 대신 일반 대입으로 state를 바꾸기 때문이다. 비공정 락은 메모리 가시성 보장을 생략하기 때문이다. 락이 풀린 뒤 대기자가 깨어나 CPU를 받는 동안, 이미 실행 중인 스레드가 끼어들어 락을 쓸 수 있어 락이 비어 있는 시간이 줄기 때문이다. 두 방식 모두 같은 AQS 대기 큐와 CAS를 쓰고, Lock 문서가 요구하는 메모리 동기화 의미도 같다. 차이는 state가 0일 때 줄이 있어도 CAS를 시도하느냐(NonfairSync)와 줄이 있으면 양보하느냐(FairSync의 hasQueuedThreads/hasQueuedPredecessors 검사)다. 공정 락은 잠든 다음 차례가 깨어날 때까지 락을 비워 두므로 같은 시간에 실행되는 임계 영역이 줄어든다. macOS에서 OpenJDK 21로 실행한 프로그램의 네이티브 스택을 보니, synchronized 진입을 기다리는 스레드와 ReentrantLock.lock()을 기다리는 스레드가 모두 _pthread_cond_wait → __psynch_cvwait에서 멈춰 있었다. 그런데도 getState()가 각각 BLOCKED와 WAITING을 돌려주는 이유로 옳은 것은? 커널이 두 스레드를 서로 다른 대기열에 넣고, JVM이 커널에 그 종류를 물어보기 때문이다. BLOCKED 스레드는 스핀하며 CPU를 쓰고, WAITING 스레드만 커널에서 잠들기 때문이다. 잠들기 직전에 HotSpot이 각 경로에서 Thread의 threadStatus에 서로 다른 값(BLOCKED_ON_MONITOR_ENTER, PARKED)을 써 두고, getState()는 그 값만 읽기 때문이다. getState()가 호출 시점의 스택 트레이스를 분석해 Unsafe.park가 있으면 WAITING으로 판단하기 때문이다. ObjectMonitor::enter의 경합 경로는 JavaThreadBlockedOnMonitorEnterState로, Unsafe_Park는 JavaThreadParkedState로 상태 값을 바꾼 뒤 잠든다. getState()는 VM.toThreadState(holder.threadStatus)로 그 비트를 검사할 뿐 커널에 묻지도, 스택을 분석하지도 않는다. 샘플이 보여 주듯 두 스레드 모두 커널의 같은 조건 변수 대기에 있으므로 BLOCKED가 스핀한다는 보기도 틀렸다.
    파킹(park)
    LockSupport.park 계열 메서드로 현재 스레드를 스케줄링 대상에서 빼는 것. 스레드 상태는 WAITING 또는 TIMED_WAITING이 된다.
    허가(permit)
    LockSupport가 스레드마다 두는 0 또는 1의 값. unpark가 1로 만들고 park가 소비한다. 쌓이지 않는다.
    가짜 깨어남(spurious wakeup)
    unpark, 인터럽트, 시간 초과 어느 것도 아닌데 대기 메서드가 돌아오는 것. 그래서 조건을 루프에서 재확인한다.
    블로커(blocker)
    park(Object)에 넘겨 Thread.parkBlocker에 기록되는 객체. 스레드 덤프의 "parking to wait for"와 LockSupport.getBlocker로 진단에 쓰인다.
    AQS(AbstractQueuedSynchronizer)
    int state와 FIFO 대기 큐를 기반으로 락과 동기화 도구를 만드는 추상 클래스. ReentrantLock, Semaphore, CountDownLatch가 이것으로 구현된다.
    CLH 큐(CLH queue)
    Craig, Landin, Hagersten의 이름을 딴 락 대기 큐 구조. AQS는 이를 변형해 prev/next 링크와 status를 더하고, 스핀 대신 park로 기다린다.
    재진입(reentrancy)
    락을 소유한 스레드가 같은 락을 다시 획득할 수 있는 성질. 획득할 때마다 보유 횟수가 늘고, 같은 횟수만큼 풀어야 해제된다.
    끼어들기(barging)
    대기 큐에 줄 선 스레드보다 새로 도착한 스레드가 먼저 락을 얻는 것. 비공정 락이 허용하며 처리량을 높이는 대신 순서를 보장하지 않는다.
    공정성(fairness)
    경합 시 가장 오래 기다린 스레드에게 락을 주는 성질. new ReentrantLock(true)로 켠다. 스레드 스케줄링의 공정성까지 보장하지는 않는다.
    고정(pinning)
    가상 스레드가 캐리어 스레드에서 내려오지 못하는 상태. Java 21에서는 synchronized 안이나 네이티브 메서드 실행 중에 생긴다.
    소유권 이전(handoff)
    락의 소유자가 직전과 다른 스레드로 바뀌는 것. 다음 소유자가 잠들어 있으면 깨우는 비용이 들기 때문에, 이전 횟수가 락의 처리량을 크게 좌우한다.
    threadStatus
