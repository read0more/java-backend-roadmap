    스레드 풀은 저절로 꺼지지 않는다

    앞 회차에서 우리는 스레드를 작업마다 새로 만들지 않고 미리 만들어 둔 스레드에 작업을 맡기는 Executor 프레임워크를 만났다. ExecutorService에 Runnable이나 Callable을 넘기면 풀의 스레드가 그것을 꺼내 실행하고, 결과는 Future로 돌아온다. 이 회차는 그 풀의 끝과 모양을 다룬다. 풀을 어떻게 끄는가, 그리고 풀 안의 스레드 수와 큐가 어떤 규칙으로 늘고 줄며, 감당할 수 없는 작업이 오면 무슨 일이 벌어지는가.

    먼저 끄는 문제부터 보자. 자바 언어 명세(Java SE 21 JLS §12.8 Program Exit)는 프로그램이 끝나는 상황을 다섯 가지로 나열하는데, 이 회차와 관련된 것은 그중 둘이다. 데몬이 아닌 스레드가 모두 끝나거나, 어떤 스레드가 System.exit나 Runtime.exit를 호출하는 경우다(나머지 셋은 Runtime.halt 호출과, 운영체제 신호처럼 JVM 바깥에서 오는 사건이다). 그런데 Executors가 기본으로 쓰는 스레드 팩토리(Executors.defaultThreadFactory())는 Javadoc에 적힌 대로 데몬이 아닌(non-daemon) 스레드를 만든다. 그래서 main 메서드가 마지막 줄까지 실행되어도, 풀의 스레드가 하나라도 살아 있으면 JVM은 끝나지 않는다. 처음 스레드 풀을 써 본 사람이 "프로그램이 안 끝나요"라고 당황하는 이유가 이것이다.

    살아 있는 풀 스레드는 무엇을 하고 있을까. 할 일이 없을 때 풀의 작업 스레드는 작업 큐의 take()에서 기다린다. 8~9회차에서 만든 생산자 소비자 구조의 소비자와 정확히 같은 자리다. 큐가 비어 있으면 소비자는 WAITING 상태로 잠들고, 새 작업이 들어와야 깨어난다. 아무도 작업을 넣지 않으면 영원히 잠들어 있다. 고정 크기 풀의 스레드는 유휴 시간 제한도 없으므로 저절로 사라지지도 않는다. 결국 누군가 명시적으로 "이제 그만"이라고 말해 주어야 한다.

    서버 애플리케이션에서는 이 문제가 더 무겁다. 새 버전을 배포하거나 인스턴스를 줄일 때 프로세스는 반드시 내려가야 한다. 그 순간 풀 안에는 실행 중인 작업과 큐에서 차례를 기다리는 작업이 있다. 결제 결과를 기록하던 작업이 절반만 실행되고 끊기면 데이터가 어긋나고, 큐에 있던 작업은 흔적도 없이 사라진다. 그래서 필요한 것이 우아한 종료(graceful shutdown)다. 새 작업은 더 받지 않고, 이미 받은 작업은 가능한 한 끝까지 처리하며, 그래도 끝나지 않으면 정해 둔 시간이 지난 뒤 강제로 정리한다. 이 세 단계가 이 회차 전반부의 주제다.

    일상에서 가져온 비유식당의 마감

    식당이 문을 닫을 때를 떠올려 보자. 먼저 입구에 "주문 마감" 팻말을 건다(새 작업 거절). 이미 주문을 받은 손님의 음식은 끝까지 만들어 내고, 대기석에서 기다리던 손님도 받아 준다(큐에 남은 작업 처리). 그러고도 마감 시간이 한참 지났는데 일어나지 않는 손님이 있으면 정중히 나가 달라고 요청한다(인터럽트). 이 비유가 깨지는 지점이 바로 이 회차의 핵심이다. 식당 직원은 끝까지 버티는 손님을 결국 내보낼 수 있지만, 자바의 스레드 풀은 그럴 수 없다. 나가 달라는 요청(인터럽트)을 무시하는 작업은 스스로 끝날 때까지 아무도 끌어낼 수 없다.

    종료를 위한 메서드: 요청, 강제, 대기, 확인

    ExecutorService는 종료와 관련해 다섯 개의 메서드를 정의하고, Java 19부터 여섯 번째인 close()가 추가되었다. 각 메서드가 하는 일을 정확히 구분하는 것이 출발점이다. 특히 종료를 시작하는 메서드와 종료를 기다리는 메서드가 분리되어 있다는 점을 놓치면 안 된다.

    메서드새 작업큐에서 기다리던 작업실행 중인 작업호출 스레드반환
    shutdown()거절그대로 실행그대로 실행즉시 반환void
    shutdownNow()거절큐에서 꺼내 실행하지 않고 돌려줌인터럽트로 중단 시도즉시 반환List
    awaitTermination(t, unit)---종료되거나 시간이 지날 때까지 블로킹boolean
    close() (Java 19+)거절그대로 실행그대로 실행종료될 때까지 블로킹void
    isShutdown()종료가 시작되었는가(shutdown이나 shutdownNow가 호출되었는가)boolean
    isTerminated()종료 후 모든 작업과 스레드가 끝났는가boolean

    Javadoc의 표현을 그대로 옮기면 shutdown은 "이전에 제출된 작업은 실행되지만 새 작업은 받지 않는 질서 있는 종료를 시작한다." 그리고 바로 다음 문단에 "이 메서드는 이전에 제출된 작업의 완료를 기다리지 않는다"는 문장이 붙어 있다. shutdown()을 호출하고 바로 다음 줄에서 결과를 집계하면, 그 시점에는 작업이 아직 돌고 있을 수 있다는 뜻이다. 기다리려면 awaitTermination을 따로 불러야 한다.

    반대 방향의 착각도 흔하다. awaitTermination만 호출하면 풀이 알아서 정리될 것이라고 생각하는 경우다. 하지만 awaitTermination은 종료를 시작하지 않는다. Javadoc은 "isTerminated는 shutdown이나 shutdownNow가 먼저 호출되지 않는 한 결코 true가 되지 않는다"고 못박는다. 종료 요청 없이 awaitTermination(10, SECONDS)를 부르면 그 스레드는 10초를 그대로 기다린 뒤 false를 받는다. 그 사이 풀은 평소처럼 작업을 받고 있다.

    shutdownNow의 반환값은 "실행을 시작하지 못한 작업 목록"이다. ThreadPoolExecutor의 구현 Javadoc은 이 작업들이 메서드가 반환될 때 큐에서 제거(drain)된다고 적는다. 즉 그 목록을 받아서 무언가 하지 않으면 그 작업들은 그대로 사라진다. 이 목록으로 무엇을 해야 하는지는 조금 뒤에 실험으로 확인한다.

    우아한 종료 구현: 두 단계로 끈다

    ExecutorService의 Javadoc 사용 예에는 두 단계로 끄는 방법이 소개되어 있다. 첫 단계에서 shutdown으로 새 작업을 막고 정해진 시간 동안 기다린다. 그 시간 안에 끝나지 않으면 두 번째 단계에서 shutdownNow로 실행 중인 작업을 취소하고 다시 한 번 기다린다. 같은 구조를 실행 과정이 보이도록 로그를 넣어 새로 작성해 보자. 스레드 두 개짜리 고정 풀에 1초짜리 작업 세 개와 100초짜리 작업 하나를 넣고, 대기 시간은 3초로 잡는다.

    import java.util.List;
import java.util.concurrent.*;

public class ShutdownMain {
    static void log(String msg) {
        System.out.println(Thread.currentThread().getName() + ": " + msg);
    }

    static Runnable task(String name, long ms) {
        return () -> {
            log(name + " 시작");
            try {
                Thread.sleep(ms);
            } catch (InterruptedException e) {
                log(name + " 인터럽트 받음: " + e.getMessage());
                return;
            }
            log(name + " 완료");
        };
    }

    public static void main(String[] args) throws Exception {
        ExecutorService es = Executors.newFixedThreadPool(2);
        es.execute(task("taskA", 1000));
        es.execute(task("taskB", 1000));
        es.execute(task("taskC", 1000));
        es.execute(task("longTask", 100_000));
        Thread.sleep(100);
        log("shutdown 호출 전: " + es);
        shutdownAndAwaitTermination(es);
        log("최종: " + es + " isTerminated=" + es.isTerminated());
    }

    static void shutdownAndAwaitTermination(ExecutorService es) {
        es.shutdown();                                   // 1단계: 새 작업 거절
        log("shutdown 직후: isShutdown=" + es.isShutdown() + ", isTerminated=" + es.isTerminated());
        try {
            es.execute(task("late", 10));
        } catch (RejectedExecutionException e) {
            log("새 작업 거절: " + e.getMessage());
        }
        try {
            if (!es.awaitTermination(3, TimeUnit.SECONDS)) {   // 정상 종료를 기다린다
                log("3초 안에 끝나지 않음 -> shutdownNow");
                List notStarted = es.shutdownNow();    // 2단계: 강제 종료 시도
                log("실행되지 못한 작업 수: " + notStarted.size());
                if (!es.awaitTermination(3, TimeUnit.SECONDS)) {
                    log("서비스가 종료되지 않았다");
                }
            }
        } catch (InterruptedException e) {
            es.shutdownNow();                     // 기다리던 나 자신이 인터럽트되었다
            Thread.currentThread().interrupt();   // 인터럽트 상태를 복구한다
        }
    }
}

    시간 순서대로 따라가 보자. 0초에 네 작업이 제출된다. 풀의 스레드는 두 개뿐이므로 taskA와 taskB가 각각 스레드를 하나씩 차지하고, taskC와 longTask는 큐에 들어간다. 0.1초에 찍힌 toString()이 정확히 그 상태를 보여 준다: 스레드 2개, 실행 중 2개, 큐 2개. ThreadPoolExecutor.toString()은 이처럼 상태 문자열과 네 가지 숫자를 함께 출력하므로 디버깅에 쓸모가 있다.

    0.1초에 shutdown()이 호출된다. 메서드는 즉시 반환되고 isShutdown()은 true, isTerminated()는 false다. 이 시점에 "late"라는 새 작업을 넣으려 하자 RejectedExecutionException이 던져진다. 예외 메시지 안의 상태가 Running이 아니라 Shutting down으로 바뀐 것에 주목하자. 큐에 있는 두 작업은 여전히 queued tasks = 2로 남아 있다. 종료가 시작되었다고 큐가 비워지지는 않는다.

    1초쯤 taskA와 taskB가 끝나면, 두 스레드는 다음 작업을 찾으러 큐로 간다. 종료가 시작되었지만 큐가 비어 있지 않으므로 그대로 taskC와 longTask를 꺼내 실행한다. 2초쯤 taskC가 끝나고 그 스레드는 큐가 비었으니 종료된다. 하지만 longTask는 100초를 자야 하므로, main이 0.1초부터 기다리기 시작한 awaitTermination(3, SECONDS)는 3.1초쯤 false를 반환한다.

    이제 2단계다. shutdownNow()가 longTask를 실행하는 스레드에 인터럽트를 건다. Thread.sleep은 인터럽트에 반응하는 블로킹 메서드이므로 즉시 InterruptedException을 던지고, 메시지는 sleep interrupted다. 작업은 로그를 남기고 반환한다. 큐는 이미 비어 있었으므로 돌려받은 목록의 크기는 0이다. 두 번째 awaitTermination은 곧바로 true를 받고, 최종 상태는 Terminated, 스레드 0개다.

    마지막 줄의 completed tasks = 4도 짚어 둘 만하다. longTask는 중간에 끊겼지만 풀의 입장에서는 run() 호출이 끝났으므로 완료된 작업으로 센다(JDK 21 소스의 runWorker는 이 수를 finally 블록에서 올리므로, 작업이 예외로 끝나도 마찬가지다). 풀은 작업이 "제대로" 끝났는지 알지 못한다. 작업이 중단되었다는 사실을 바깥에 알려야 한다면, 그것은 작업 코드가 책임질 일이다.

    catch 블록이 하는 일

    예제의 catch (InterruptedException e)는 풀의 작업이 아니라 종료를 기다리던 호출 스레드 자신이 인터럽트되었을 때 실행된다. 예를 들어 애플리케이션 전체를 내리는 쪽에서 종료 절차를 수행하는 스레드를 인터럽트할 수 있다. 이때 두 가지를 한다. 첫째, 더 기다릴 수 없게 되었으므로 shutdownNow()로 남은 작업을 바로 취소한다. 둘째, Thread.currentThread().interrupt()로 인터럽트 상태를 되살린다. 3~4회차에서 보았듯 InterruptedException이 던져질 때 스레드의 인터럽트 플래그는 지워진다. 예외를 잡고 아무것도 하지 않으면 "중단해 달라"는 요청이 이 메서드에서 증발해, 이 메서드를 부른 상위 코드는 인터럽트가 있었다는 사실을 알 수 없게 된다.

    대기 시간을 얼마로 잡을지는 정답이 정해진 문제가 아니다. 1단계 대기 시간은 정상적인 작업 하나가 끝나는 데 걸리는 최대 시간보다 길어야 의미가 있다. 동시에 프로세스를 내리는 쪽(운영체제 서비스 관리자, 컨테이너 오케스트레이터 등)이 허락하는 전체 종료 시간 안에 두 단계가 모두 들어가야 한다. 그 시간을 넘기면 결국 프로세스가 바깥에서 강제로 죽고, 그때는 어떤 정리 코드도 실행되지 않는다.

    shutdownNow는 스레드를 죽이지 않는다

    이름만 보면 shutdownNow는 모든 것을 "지금 당장" 멈출 것 같다. 하지만 ExecutorService Javadoc은 이 메서드에 대해 "실행 중인 작업을 멈추려는 최선의 노력(best-effort) 이상은 보장하지 않는다"고 적고, 전형적인 구현은 Thread.interrupt로 취소하므로 "인터럽트에 반응하지 않는 작업은 결코 끝나지 않을 수 있다"고 경고한다. ThreadPoolExecutor의 구현 Javadoc도 같은 내용을 반복한다.

    왜 스레드를 강제로 죽이지 않을까. 자바에는 원래 Thread.stop()이 있었지만 1.2에서 이미 사용 중단(deprecated)되었다. 스레드를 아무 지점에서나 멈추면 그 스레드가 쥐고 있던 모니터 락이 풀리면서, 절반만 수정된 객체가 다른 스레드에 그대로 노출되기 때문이다. JDK 21 소스의 Thread.stop()은 아예 UnsupportedOperationException을 던지도록 바뀌어 있다. 남은 수단은 인터럽트뿐이고, 인터럽트는 대상 스레드의 플래그를 세우고 일부 블로킹 메서드를 깨우는 협력적(cooperative) 신호일 뿐이다. 작업 코드가 그 신호를 확인하지 않으면 아무 일도 일어나지 않는다.

    이것을 눈으로 확인해 보자. 스레드 하나짜리 풀에 3초 동안 인터럽트를 확인하지 않고 계산만 하는 작업을 넣고, 뒤에 두 작업을 더 넣는다. 하나는 execute로, 하나는 submit으로 넣는다.

    import java.util.List;
import java.util.concurrent.*;

public class NowMain {
    static void log(String msg) {
        System.out.println(Thread.currentThread().getName() + ": " + msg);
    }

    public static void main(String[] args) throws Exception {
        ExecutorService es = Executors.newFixedThreadPool(1);
        es.execute(() -> {
            log("stubborn 시작");
            long end = System.nanoTime() + TimeUnit.SECONDS.toNanos(3);
            while (System.nanoTime() < end) { /* 인터럽트를 확인하지 않는 계산 */ }
            log("stubborn 끝, interrupted=" + Thread.currentThread().isInterrupted());
        });
        es.execute(() -> log("q1"));
        Future f = es.submit(() -> log("q2"));
        Thread.sleep(100);

        List left = es.shutdownNow();
        log("shutdownNow 반환: " + left.size() + "개, 두 번째 원소 타입="
                + left.get(1).getClass().getSimpleName());
        log("awaitTermination(1s)=" + es.awaitTermination(1, TimeUnit.SECONDS));
        log("toString: " + es);
        log("awaitTermination(5s)=" + es.awaitTermination(5, TimeUnit.SECONDS));
        log("q2 future isDone=" + f.isDone() + ", isCancelled=" + f.isCancelled());
    }
}

main: awaitTermination(1s)=false
main: toString: java.util.concurrent.ThreadPoolExecutor@3d4eac69[Shutting down, pool size = 1, active threads = 1, queued tasks = 0, completed tasks = 0]

    세 가지를 읽을 수 있다. 첫째, shutdownNow는 인터럽트를 걸었지만 stubborn 작업은 그것을 확인하지 않으므로 3초를 다 채운다. 마지막에 찍힌 interrupted=true가 인터럽트 신호는 분명히 도착했다는 증거다. 플래그는 섰지만 아무도 보지 않았다. 그동안 awaitTermination(1s)은 false를 반환하고, 풀의 상태는 여전히 Shutting down이다. 만약 이 루프가 끝나지 않는 루프였다면 풀은 영원히 종료되지 않고, 이 스레드가 데몬이 아니므로 JVM도 끝나지 않는다.

    둘째, 반환된 목록의 두 번째 원소는 우리가 넘긴 람다가 아니라 FutureTask다. submit은 작업을 FutureTask로 감싼 뒤 execute에 넘기기 때문이다(앞 회차에서 본 AbstractExecutorService.submit의 구조). 큐에 들어 있던 것은 그 래퍼이므로 돌려받는 것도 래퍼다.

    셋째가 가장 위험하다. q2의 Future는 풀이 완전히 종료된 뒤에도 isDone=false, isCancelled=false다. 실행되지도, 취소되지도 않은 채 큐에서 빠져나와 목록에 담겼을 뿐이기 때문이다. 다른 스레드가 이 Future의 get()을 시간 제한 없이 호출하고 있었다면 그 스레드는 영원히 깨어나지 못한다. 그래서 shutdownNow가 돌려준 목록은 버리지 말고 처리해야 한다. 적어도 Future인 것은 취소해서 기다리는 쪽이 CancellationException을 받게 해 주어야 한다.

    List notStarted = es.shutdownNow();
for (Runnable r : notStarted) {
    if (r instanceof Future future) {
        future.cancel(false);   // 기다리던 쪽의 get()이 CancellationException으로 깨어난다
    }
    // 필요하면 로그를 남기거나, 다시 실행할 수 있도록 별도 저장소에 기록한다
}

    인터럽트에 반응하는 작업을 쓰는 법

    결국 우아한 종료의 마지막 단계가 실제로 동작하느냐는 작업 코드에 달려 있다. 오래 도는 루프라면 반복마다 Thread.currentThread().isInterrupted()를 확인해 빠져나와야 한다. sleep, wait, join, BlockingQueue.take, Lock.lockInterruptibly처럼 InterruptedException을 던지는 메서드를 쓴다면, 그 예외를 잡아서 삼키지 말고 작업을 끝내거나 인터럽트 상태를 복구해 위로 알려야 한다. catch (InterruptedException e) {}처럼 빈 블록으로 삼키는 코드가 루프 안에 있으면, 그 작업은 shutdownNow를 몇 번 호출해도 멈추지 않는다. 한편 synchronized 블록에 들어가려고 BLOCKED 상태로 기다리는 스레드는 인터럽트로 깨울 수 없고, 그래서 lockInterruptibly가 따로 있다는 점도 6~7회차에서 보았다. 소켓 읽기처럼 인터럽트에 반응하지 않는 입출력은 타임아웃을 거는 것이 현실적인 대안이다.

    Java 19의 close()와 try-with-resources

    Java 19부터 ExecutorService는 AutoCloseable을 확장하고 close()라는 기본 메서드(default method)를 갖는다(Javadoc의 "Since: 19"). 덕분에 풀을 try-with-resources로 쓸 수 있다. 블록을 빠져나올 때 close()가 자동으로 호출되어, 종료를 시작하고 모든 작업이 끝날 때까지 기다린다.

    try (ExecutorService es = Executors.newFixedThreadPool(2)) {
    es.execute(() -> System.out.println("작업 1"));
    es.execute(() -> System.out.println("작업 2"));
}   // 여기서 close(): shutdown() 후 두 작업이 모두 끝날 때까지 기다린다
System.out.println("풀이 완전히 종료된 뒤에 실행된다");

    JDK 21 소스에서 기본 구현이 하는 일을 순서대로 적으면 다음과 같다. ThreadPoolExecutor는 이 메서드를 재정의하지 않으므로 이 구현을 그대로 쓴다.

    이 흐름에서 중요한 성질은 close()에는 시간 상한이 없다는 점이다. 앞의 stubborn 작업처럼 인터럽트를 무시하는 작업이 끝없이 돈다면, close()를 부른 스레드도 끝없이 기다린다. 인터럽트를 받아 shutdownNow()로 넘어간 뒤에도 "실행 중인 작업이 끝날 때까지 계속 기다린다"는 것이 Javadoc의 설명이다. 그래서 close()는 짧은 범위에서 작업 묶음을 실행하고 모두 끝나기를 기다리는 용도에 잘 맞고, 정해진 시간 안에 반드시 내려가야 하는 서버 종료 절차에는 앞 절의 두 단계 방식이 맞다. 또 shutdownNow가 돌려주는 목록은 close() 안에서 버려지므로, 그 목록을 처리해야 한다면 역시 직접 쓰는 편이 낫다.

    한 층 아래: ThreadPoolExecutor의 상태 기계

    shutdown과 shutdownNow가 실제로 무엇을 바꾸는지 보려면 ThreadPoolExecutor 안으로 들어가야 한다. 이 클래스의 중심에는 ctl이라는 AtomicInteger 필드 하나가 있다. 소스 주석은 이것을 "두 개의 개념적 필드를 묶은 주 제어 상태"라고 부른다. 하나는 풀의 생명 주기를 나타내는 실행 상태(runState), 다른 하나는 살아 있는 작업 스레드의 수인 작업자 수(workerCount)다.

    32비트 정수 하나에 두 값을 넣기 위해, 위쪽 3비트에는 실행 상태를, 아래쪽 29비트에는 작업자 수를 둔다. 그래서 작업자 수의 상한은 229−1, 약 5억 3천만이다. 소스 주석은 이 상한이 언젠가 문제가 되면 AtomicLong으로 바꿀 수 있지만, 그 전까지는 int가 더 빠르고 단순하다고 설명한다.

    ctl (AtomicInteger, 32비트)
 ┌─────┬──────────────────────────────────────────┐
 │ 3비트│              29비트                        │
 │ 상태 │           workerCount                     │
 └─────┴──────────────────────────────────────────┘

 상태 상수 (COUNT_BITS = 29)            위쪽 3비트   정수로 보면
 RUNNING    = -1 << 29                  111          음수
 SHUTDOWN   =  0 << 29                  000          0
 STOP       =  1 << 29                  001          양수
 TIDYING    =  2 << 29                  010          더 큰 양수
 TERMINATED =  3 << 29                  011          가장 큰 양수

 runStateOf(c)    = c & ~COUNT_MASK      (아래 29비트를 지움)
 workerCountOf(c) = c &  COUNT_MASK      (위 3비트를 지움)
 예) 실행 중이고 스레드 3개 → ctl = RUNNING | 3

    상태 상수의 배치에는 의도가 있다. RUNNING만 음수이고 나머지는 0 이상이며, 뒤의 상태일수록 값이 크다. 그래서 "실행 중인가"는 c < SHUTDOWN 한 번의 비교로, "적어도 STOP 이후인가"는 c >= STOP 한 번의 비교로 판단할 수 있다. 작업자 수가 아래 비트에 더해져 있어도 위 3비트가 대소 관계를 결정하므로 비교 결과는 변하지 않는다. 소스의 runStateLessThan, runStateAtLeast, isRunning이 모두 이 단순 비교다.

    두 값을 한 정수에 묶은 더 중요한 이유는 원자성이다. 새 스레드를 추가하는 addWorker는 "아직 실행 중이고, 스레드 수가 한도 미만이면 수를 하나 늘린다"를 해야 한다. 상태와 수가 별도 변수라면 둘을 함께 검사하고 바꾸기 위해 락이 필요하다. 하나의 정수에 들어 있으면 10회차에서 배운 CAS 한 번(compareAndIncrementWorkerCount)으로 끝난다. 확인한 뒤 다른 스레드가 shutdown을 불러 상태가 바뀌었다면 ctl 값 자체가 달라졌으므로 CAS가 실패하고, addWorker는 상태를 다시 읽어 재시도한다.

    다섯 상태와 전이

    상태새 작업큐의 작업의미
    RUNNING받음처리정상 동작
    SHUTDOWN거절처리shutdown() 호출 이후
    STOP거절처리하지 않음shutdownNow() 호출 이후. 실행 중인 작업에 인터럽트
    TIDYING거절-모든 작업이 끝나고 작업자 수가 0. 이 상태로 바꾼 스레드가 terminated() 훅을 실행
    TERMINATED거절-terminated() 훅까지 끝남. awaitTermination이 깨어남

    소스 주석에 적힌 전이는 다섯 가지다. RUNNING → SHUTDOWN은 shutdown() 호출 시, RUNNING 또는 SHUTDOWN → STOP은 shutdownNow() 호출 시, SHUTDOWN → TIDYING은 큐와 풀이 모두 비었을 때, STOP → TIDYING은 풀이 비었을 때, TIDYING → TERMINATED는 terminated()가 끝났을 때 일어난다. 실행 상태는 시간이 지나며 단조 증가할 뿐 거꾸로 돌아가지 않는다. 한 번 종료를 시작한 풀은 다시 RUNNING이 될 수 없으므로 재사용할 수 없다.

    앞 실험의 toString() 출력과 연결해 두자. toString()은 RUNNING이면 Running, TERMINATED면 Terminated, 그 사이(SHUTDOWN, STOP, TIDYING)는 모두 Shutting down으로 표시한다. shutdownNow 직후인데도 Shutting down으로 찍힌 이유다. 그 중간 구간을 직접 확인하고 싶다면 ThreadPoolExecutor.isTerminating()을 쓸 수 있다. Javadoc은 종료 요청 후 충분한 시간이 지났는데도 이 값이 true라면 작업이 인터럽트를 무시하고 있을 수 있다는 신호로 쓰라고 설명한다.

    RUNNING에서 TERMINATED까지 다섯 상태와, 각 화살표를 일으키는 사건을 보여 준다. 상태는 되돌아가지 않는다. 가로로 긴 상태 전이도. 흰 배경, 둥근 사각형 다섯 개. 왼쪽에 "RUNNING", 그 오른쪽 위에 "SHUTDOWN", 오른쪽 아래에 "STOP", 그 오른쪽에 "TIDYING", 맨 오른쪽에 "TERMINATED". 화살표: RUNNING에서 SHUTDOWN으로 "shutdown()" 라벨, RUNNING에서 STOP으로 "shutdownNow()" 라벨, SHUTDOWN에서 STOP으로 "shutdownNow()" 라벨, SHUTDOWN에서 TIDYING으로 "큐와 풀이 비면", STOP에서 TIDYING으로 "풀이 비면", TIDYING에서 TERMINATED로 "terminated() 완료". 모든 화살표는 왼쪽에서 오른쪽 방향으로만 그리고 되돌아가는 화살표는 없다. TERMINATED 상자 아래에 작은 글씨 "awaitTermination 깨어남". 단색 선, 상태 상자는 연한 회색, TERMINATED만 진한 색. 실행 상태는 앞으로만 진행한다. 한 번 종료를 시작한 풀은 다시 쓸 수 없다.

    shutdown은 쉬는 스레드만 깨운다

    이제 shutdown과 shutdownNow의 소스가 무엇이 다른지 볼 차례다. 그 전에 작업 스레드를 감싸는 내부 클래스 Worker를 알아야 한다. Worker는 Runnable이면서 동시에 AbstractQueuedSynchronizer(AQS)를 상속한다. 7회차의 ReentrantLock 내부에 있던 바로 그 동기화 뼈대다. Worker는 이것으로 재진입이 안 되는 단순한 배타 락을 만든다(상태 0이 풀림, 1이 잠김). 작업 스레드의 주 루프인 runWorker는 작업 하나를 실행하기 직전에 w.lock()을 잡고, 실행이 끝나면 w.unlock()을 한다. 따라서 Worker의 락이 잠겨 있다는 것은 그 스레드가 지금 작업을 실행 중이라는 뜻이다. getActiveCount()도 잠긴 Worker의 수를 세어 계산한다.

    shutdown()은 내부 락(mainLock)을 잡고 상태를 SHUTDOWN으로 올린 뒤 interruptIdleWorkers()를 호출한다. 이 메서드는 모든 Worker를 돌면서 w.tryLock()을 시도하고, 성공한 경우에만 그 스레드를 인터럽트한다. 작업을 실행 중인 Worker는 자기 락을 쥐고 있으므로 tryLock()이 실패하고, 인터럽트를 받지 않는다. 결국 인터럽트를 받는 것은 큐 앞에서 다음 작업을 기다리며 쉬고 있던 스레드뿐이다. 실행 중인 작업을 방해하지 않으면서 잠든 스레드만 깨우는 장치가 락 하나로 구현되어 있다.

    깨어난 스레드는 어디로 갈까. 쉬는 스레드는 getTask() 안의 workQueue.take()나 workQueue.poll(keepAliveTime, ...)에서 잠들어 있었다. 인터럽트를 받으면 이 메서드들이 InterruptedException을 던지는데, getTask()는 이것을 잡아 루프를 처음부터 다시 돈다. 루프 첫머리의 검사는 이렇다: "상태가 SHUTDOWN 이상이고, (STOP 이상이거나 큐가 비어 있으면) 작업자 수를 하나 줄이고 null을 반환한다." 큐가 비어 있으면 null을 받은 runWorker의 루프가 끝나고 스레드가 종료된다. 큐에 작업이 남아 있으면 검사를 통과해 다시 큐에서 작업을 꺼낸다. SHUTDOWN 상태에서도 큐의 작업이 끝까지 처리되는 이유가 이 조건이다.

    인터럽트를 받지 않은, 작업을 실행 중이던 스레드는 작업을 마친 뒤 스스로 getTask()로 돌아와 같은 검사를 거친다. 큐가 비었으면 종료하고, 남아 있으면 계속 일한다. 한편 runWorker는 작업을 시작하기 전에 상태가 STOP 미만이면 Thread.interrupted()로 남아 있던 인터럽트 플래그를 지운다. shutdown이 쉬는 스레드를 깨우려고 건 인터럽트가 그 스레드가 다음에 꺼낸 작업에 새어 들어가 엉뚱한 InterruptedException을 일으키지 않도록 하는 처리다.

    shutdownNow()는 세 가지가 다르다. 상태를 STOP으로 올리고, interruptIdleWorkers() 대신 interruptWorkers()를 불러 시작된 모든 Worker에 락과 상관없이 인터럽트를 걸며, drainQueue()로 큐의 작업을 모두 꺼내 목록으로 돌려준다. 그리고 getTask()의 첫머리 검사에서 STOP 이상이면 큐를 볼 필요도 없이 null이 반환되므로, 작업을 마친 스레드는 다음 작업을 꺼내지 않고 바로 종료된다. 또 runWorker는 상태가 STOP 이상이면 작업 시작 전에 인터럽트 플래그가 반드시 서 있도록 보장한다.

    마지막 스레드가 문을 닫는다

    스레드가 종료될 때마다 processWorkerExit가 호출되고, 그 안에서 tryTerminate()가 실행된다. tryTerminate는 "실행 중이 아니고, (STOP이거나 큐가 비어 있고), 작업자 수가 0인가"를 확인한다. 아직 스레드가 남아 있으면 쉬고 있는 스레드 하나만 인터럽트해서(interruptIdleWorkers(ONLY_ONE)) 종료 신호를 다음 스레드로 전파한다. 소스 주석은 모든 스레드가 큐에서 잠들어 있는 경우에도 종료가 반드시 이어지도록 하는 장치라고 설명한다. 작업자 수가 0이면 mainLock을 잡고 CAS로 상태를 TIDYING으로 바꾼 뒤, terminated() 훅을 실행하고 상태를 TERMINATED로 설정한 다음 termination.signalAll()을 호출한다.

    이 termination은 mainLock에서 만든 Condition이다. awaitTermination의 구현은 mainLock을 잡고 "상태가 TERMINATED 미만인 동안 termination.awaitNanos(nanos)로 기다리고, 남은 시간이 0 이하가 되면 false를 반환한다"는 루프다. 7회차와 9회차에서 손으로 만든 "락 + 조건 변수 + while 재확인" 패턴이 JDK 안에서 그대로 쓰이고 있다. 종료를 기다리는 여러 스레드가 모두 깨어나야 하므로 signal이 아니라 signalAll이다.

    TERMINATED 뒤에 읽는 값: happens-before는 어디서 오는가

    종료 절차의 마지막 줄에서 흔히 하는 일이 있다. 작업들이 배열이나 일반 필드에 결과를 써 두고, main은 shutdown() 뒤 awaitTermination()이 true를 돌려주면 그 값을 읽어 집계한다. 이 코드가 옳은지는 "작업 스레드가 쓴 값이 main에 보이는가"라는 메모리 모델의 질문이다. 5회차에서 보았듯 답은 쓰기와 읽기 사이에 happens-before 관계가 있느냐로 정해진다. 그 관계가 어디서 오는지를 명세와 구현으로 나누어 따라가 보자.

    먼저 명세다. java.util.concurrent 패키지 문서의 "Memory Consistency Properties" 절은 이 패키지가 JLS 17장의 happens-before를 넓히는 경우를 나열한다. 동시성 컬렉션에 원소를 넣기 전의 동작은 다른 스레드가 그 원소를 꺼낸 뒤의 동작보다 앞선다. Executor에 작업을 제출하기 전의 동작은 그 작업의 실행 시작보다 앞서고, Future가 나타내는 계산의 동작은 Future.get()으로 결과를 받은 뒤의 동작보다 앞선다. Lock.unlock, Semaphore.release, CountDownLatch.countDown 같은 "해제" 메서드와 그 짝인 "획득" 메서드도 목록에 있다. ExecutorService Javadoc의 "Memory consistency effects" 문단도 제출 → 작업 → Future.get() 경로만 적는다. awaitTermination과 isTerminated는 어느 목록에도 없다. API 명세만으로는 "종료를 기다렸으니 작업이 쓴 값이 보인다"를 정당화할 수 없다는 뜻이다.

    그러면 OpenJDK 21의 ThreadPoolExecutor에서는 실제로 어떻게 되는가. JLS §17.4.4의 synchronizes-with 규칙 가운데 여기서 쓰이는 것은 "volatile 변수 v에 대한 쓰기는 (동기화 순서에서) 그 뒤에 오는 모든 v 읽기와 synchronizes-with 관계다"라는 규칙이다. ctl은 AtomicInteger이고, AtomicInteger Javadoc은 get(), set(), addAndGet(), compareAndSet()의 메모리 효과가 각각 VarHandle의 getVolatile, setVolatile, getAndAdd, compareAndSet을 따른다고 적는다. 즉 읽기는 volatile 읽기, 쓰기와 갱신은 volatile 쓰기의 효과를 갖는다. 이것을 앞 절에서 본 소스의 순서에 대입하면 다음 사슬이 나온다.

    3단계가 성립하는 이유를 조금 더 짚자. 작업자 수는 작업자가 생길 때 하나 늘고 끝날 때 하나 준다. T가 0을 읽었다면 그때까지 생긴 작업자가 모두 감소 쓰기를 마쳤다는 뜻이고, 그 쓰기들은 모두 같은 변수 ctl에 대한 것이어서 동기화 순서에서 T의 읽기보다 앞에 있다. 같은 사슬은 mainLock을 통해서도 한 번 더 생긴다. tryTerminate는 mainLock을 쥔 채 TERMINATED를 쓰고, awaitTermination은 mainLock을 잡은 다음 상태를 읽는다. Lock Javadoc은 모든 Lock 구현이 내장 모니터 락과 같은 메모리 동기화 의미를 가져야 한다고 정한다. 결론적으로 OpenJDK 21에서는 이 패턴에 필요한 happens-before 사슬이 실제로 존재한다. 다만 그 근거는 구현의 내부 구조이고, 명세가 약속한 것은 아니다. 명세에 기대려면 결과를 Future.get()(또는 invokeAll이 돌려준 Future들)로 받거나, ConcurrentHashMap 같은 동시성 컬렉션에 넣거나, CountDownLatch로 완료를 알리면 된다. 모두 위 목록에 있는 경로다.

    TERMINATED는 스레드가 사라졌다는 뜻이 아니다

    사슬의 4단계를 실행하는 스레드 T는 누구일까. tryTerminate는 shutdown()의 마지막 줄에서도, 각 작업자가 끝날 때 processWorkerExit에서도 호출되므로, 작업자 수를 0으로 본 쪽이 T가 된다. terminated()를 재정의해 실행 스레드의 이름을 찍어 보면 확인할 수 있다. 작업 두 개를 실행한 스레드 두 개짜리 풀을 shutdown하면 마지막으로 빠져나간 작업 스레드(pool-1-thread-1이나 pool-1-thread-2, 실행마다 다르다)에서 실행되었다. 작업을 하나도 받지 않아 스레드가 없는 풀을 shutdown하면 main에서 실행되었고, shutdown()이 반환된 시점에 이미 isTerminated()가 true였다.

    첫 번째 경우에는 짚을 점이 있다. TERMINATED를 쓰고 signalAll()을 부른 작업 스레드에게는 아직 할 일이 남아 있다. mainLock을 풀고, tryTerminate와 processWorkerExit에서 돌아와 runWorker를 빠져나가야 하고, 그 뒤에야 HotSpot이 그 자바 스레드의 종료 처리를 한다. 그러니 awaitTermination이 true를 돌려준 순간 마지막 작업 스레드가 아직 살아 있을 수 있다. 직접 세어 보았다.

    int rounds = 1000, aliveCount = 0;
for (int i = 0; i < rounds; i++) {
    List made = Collections.synchronizedList(new ArrayList<>());
    ThreadFactory tf = r -> { Thread t = new Thread(r); made.add(t); return t; };
    ExecutorService es = Executors.newFixedThreadPool(1, tf);
    es.execute(() -> {});
    es.shutdown();
    if (!es.awaitTermination(1, TimeUnit.SECONDS)) throw new AssertionError();
    if (made.get(0).isAlive()) aliveCount++;   // 풀은 TERMINATED인데 스레드는 살아 있는가
}
System.out.println("awaitTermination=true 직후 isAlive()==true: " + aliveCount + " / " + rounds);

    숫자는 실행마다 달라지고, 다시 돌려 보면 0이 나오는 실행도 있다. 요점은 0이 아닌 값이 나올 수 있다는 것이다. 풀의 TERMINATED는 "모든 작업이 끝났고 작업자 수가 0이다"라는 풀의 장부상 상태이지, 운영체제 스레드가 모두 사라졌다는 보증이 아니다. JLS §17.4.4에는 "스레드 T1의 마지막 동작은 T1이 끝났음을 감지한 다른 스레드의 동작과 synchronizes-with 관계이고, 감지는 isAlive()나 join()으로 한다"는 규칙이 따로 있다. 앞의 사슬은 이 규칙이 아니라 ctl과 mainLock으로 만들어진 것이다. 스레드가 정말로 끝났다는 사실이 필요하다면 ThreadFactory로 만든 스레드를 기억해 두었다가 join()해야 한다.

    스레드 풀 관리: 코어, 큐, 최대를 직접 관찰하기

    이제 회차의 후반부, 풀의 모양으로 넘어가자. Executors의 newFixedThreadPool, newCachedThreadPool, newSingleThreadExecutor는 모두 ThreadPoolExecutor의 생성자를 특정한 인자로 호출하는 지름길이다(newSingleThreadExecutor는 그 결과를 래퍼로 한 번 더 감싼다). 그러니 생성자 인자 일곱 개의 의미와, 그것들이 맞물려 스레드 수를 결정하는 규칙을 이해하면 이 팩토리 메서드들의 동작을 스스로 유도할 수 있다.

    인자의미
    corePoolSize유휴 상태여도 유지하는 스레드 수(allowCoreThreadTimeOut을 켜지 않은 경우). 이 수에 도달할 때까지는 큐보다 새 스레드를 우선한다.
    maximumPoolSize풀이 가질 수 있는 최대 스레드 수. 큐에 넣을 수 없을 때만 코어를 넘어 이 수까지 스레드를 만든다.
    keepAliveTime, unit코어 수를 넘는 스레드가 새 작업 없이 기다릴 수 있는 최대 시간. 지나면 그 스레드는 종료된다.
    workQueue실행을 기다리는 작업을 담는 BlockingQueue. 종류와 용량이 풀의 성격을 결정한다.
    threadFactory스레드를 만드는 팩토리. 생략하면 Executors.defaultThreadFactory()(이름 pool-N-thread-M, 데몬 아님, 보통 우선순위).
    handler거절된 작업을 처리하는 RejectedExecutionHandler. 생략하면 AbortPolicy.

    생성자는 인자를 검증한다. JDK 21 소스 기준으로 corePoolSize < 0, maximumPoolSize <= 0, maximumPoolSize < corePoolSize, keepAliveTime < 0 중 하나라도 해당하면 IllegalArgumentException을, 큐·팩토리·핸들러가 null이면 NullPointerException을 던진다. 예를 들어 코어 5, 최대 2로 만들면 생성 시점에 바로 예외가 난다.

    규칙을 말로 외우기 전에 직접 관찰해 보자. 코어 2, 최대 4, 유지 시간 3초, 용량 2인 ArrayBlockingQueue로 풀을 만들고, 1초짜리 작업 7개를 연달아 제출하면서 매번 풀의 상태를 출력한다. 상태는 getPoolSize()(현재 스레드 수), getActiveCount()(작업 실행 중인 스레드 수), getQueue().size()(큐에 쌓인 작업 수), getCompletedTaskCount()(완료된 작업 수)로 본다.

    import java.util.concurrent.*;

public class PoolStateMain {
    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    static String state(ThreadPoolExecutor es) {
        return "[pool=" + es.getPoolSize() + ", active=" + es.getActiveCount()
             + ", queued=" + es.getQueue().size() + ", completed=" + es.getCompletedTaskCount() + "]";
    }

    public static void main(String[] args) {
        ThreadPoolExecutor es = new ThreadPoolExecutor(
                2, 4, 3000, TimeUnit.MILLISECONDS, new ArrayBlockingQueue<>(2));
        System.out.println("생성 직후 " + state(es));
        for (int i = 1; i <= 7; i++) {
            String name = "task" + i;
            try {
                es.execute(() -> {
                    System.out.println(Thread.currentThread().getName() + " 시작 " + name);
                    sleep(1000);
                });
                System.out.println(name + " 제출 후 " + state(es));
            } catch (RejectedExecutionException e) {
                System.out.println(name + " 거절: " + e.getClass().getSimpleName());
            }
        }
        sleep(3000);
        System.out.println("작업 완료 후 " + state(es));
        sleep(3000);
        System.out.println("keepAlive 경과 후 " + state(es));
        es.close();
        System.out.println("close 후 " + state(es) + " terminated=" + es.isTerminated());
    }
}

    이 출력에서 결정적인 부분과 실행마다 달라지는 부분을 먼저 나누자. pool, queued의 값과 task7이 거절된다는 사실은 이 설정과 제출 속도에서 결정적이다(7개를 제출하는 데 1초보다 훨씬 짧게 걸리므로 그 사이에 끝나는 작업이 없다). 반면 제출 직후의 active 값은 실행마다 더 작게 찍힐 수 있다. execute가 반환된 순간 새 스레드가 아직 시작되지 않아 Worker의 락을 잡기 전일 수 있기 때문이다. Javadoc도 getActiveCount()를 "대략적인(approximate)" 값이라고 부른다. "시작" 줄이 제출 줄 사이 어디에 끼는지, task3과 task4를 어느 스레드가 가져가는지도 실행마다 다르다.

    분석: execute()의 세 단계

    관찰한 결과를 설명하는 규칙은 ThreadPoolExecutor.execute()의 소스 주석에 "3단계로 진행한다"고 적혀 있다. 이것을 그대로 옮기면 이렇다.

    1. 실행 중인 스레드가 corePoolSize보다 적으면, 넘겨받은 작업을 첫 작업으로 삼는 새 스레드를 시작한다(addWorker(command, true)). 다른 스레드가 놀고 있어도 새로 만든다.
    2. 그렇지 않으면 작업을 큐에 넣는다(workQueue.offer(command)). 넣는 데 성공하면 상태를 다시 확인해, 그 사이 풀이 종료되었으면 큐에서 되돌려 거절하고, 스레드가 하나도 없으면 첫 작업 없는 스레드를 하나 만든다.
    3. 큐에 넣을 수 없으면 최대 수 한도 안에서 새 스레드를 만든다(addWorker(command, false)). 그것마저 실패하면, 즉 종료되었거나 포화 상태라면 거절한다(reject(command)).
    execute(task)
   │
   ├─ 스레드 수 < core ? ──예──▶ 새 스레드 생성, task를 첫 작업으로 실행
   │        │아니오
   ├─ 실행 중이고 큐.offer(task) 성공 ? ──예──▶ 큐에서 대기
   │        │아니오                         (재확인: 종료됐으면 되돌려 거절,
   │        │                                 스레드가 0이면 빈 스레드 하나 생성)
   ├─ 스레드 수 < max 이고 새 스레드 생성 성공 ? ──예──▶ 새 스레드가 task를 바로 실행
   │        │아니오
   └─────▶ 거절: handler.rejectedExecution(task, executor)

    이 규칙으로 실험의 일곱 줄을 다시 읽어 보자. task1은 스레드가 0개(코어 2 미만)이므로 1단계에서 새 스레드 thread-1을 만들고 그 스레드의 첫 작업이 된다. task2도 같은 이유로 thread-2를 만든다. task3이 들어올 때 스레드는 2개로 코어 수에 도달했으므로 2단계로 가서 큐에 들어간다. task4도 큐에 들어가 큐가 가득 찬다(용량 2). task5는 큐의 offer가 실패하므로 3단계로 가서, 최대 4 한도 안에서 thread-3을 만들어 바로 실행된다. task6도 같은 방식으로 thread-4를 만든다. task7이 왔을 때는 큐가 가득 찼고 스레드 수도 최대치 4이므로 addWorker가 실패하고, 기본 핸들러 AbortPolicy가 RejectedExecutionException을 던진다.

    여기서 직관과 어긋나는 결과가 하나 보인다. task5와 task6이 task3과 task4보다 먼저 시작되었다. 3단계에서 만들어진 스레드는 넘겨받은 작업을 큐에 넣지 않고 첫 작업으로 바로 실행하기 때문이다. 큐에서 기다리던 task3과 task4는 1초 뒤 어떤 스레드가 일을 마치고 큐로 돌아와야 시작된다. 큐 자체는 FIFO지만 풀 전체로 보면 제출 순서대로 실행된다는 보장이 없다. 순서가 중요한 작업이라면 스레드 하나짜리 실행기를 쓰거나 순서를 작업 쪽에서 관리해야 한다.

    또 하나의 관찰은 코어를 넘는 스레드가 큐가 가득 찬 뒤에야 생긴다는 점이다. 많은 사람이 "코어가 바쁘면 최대까지 스레드를 늘리고, 그래도 부족하면 큐에 쌓는다"고 생각하지만, 실제 순서는 코어 → 큐 → 최대다. ThreadPoolExecutor Javadoc의 표현으로는 "코어 수 이상이 실행 중이면 Executor는 새 스레드를 추가하기보다 항상 큐에 넣기를 선호한다." 그래서 큐가 크면 클수록 추가 스레드는 늦게, 혹은 전혀 만들어지지 않는다. 이 성질이 뒤에서 볼 풀 전략들의 성격을 거의 다 결정한다.

    코어 스레드 생성, 큐 삽입, 최대 스레드까지 생성, 거절의 네 갈래를 위에서 아래로 보여 준다. 세로 순서도. 맨 위에 "작업 제출 execute()" 상자. 아래로 마름모 "스레드 수 < core?" 오른쪽 '예' 화살표가 "새 스레드 생성 (작업을 바로 실행)" 상자로. '아니오'는 아래 마름모 "큐에 넣을 수 있나?"로 연결, 오른쪽 '예' 화살표가 "큐에서 대기" 상자로. '아니오'는 아래 마름모 "스레드 수 < max?"로, 오른쪽 '예' 화살표가 "추가 스레드 생성 (작업을 바로 실행)" 상자로. '아니오'는 아래 빨간 테두리 상자 "거절 정책 실행"으로. 왼쪽 여백에 위에서 아래로 향하는 긴 회색 화살표와 "코어 → 큐 → 최대 → 거절" 라벨. 단순한 선화, 흰 배경. 코어를 넘는 스레드는 큐가 가득 찬 뒤에야 만들어진다.

    스레드는 필요할 때 만들어진다

    실험의 첫 줄에서 풀을 만든 직후의 스레드 수는 0이었다. Javadoc의 "On-demand construction" 항목대로, 코어 스레드조차 작업이 도착해야 만들어진다. 서버가 뜨자마자 첫 요청의 지연을 줄이고 싶다면 prestartCoreThread()나 prestartAllCoreThreads()로 미리 만들 수 있다. 코어 3인 풀에서 prestartAllCoreThreads()를 호출하면 3을 반환하고 getPoolSize()가 3이 되는 것을 확인했다. Javadoc은 비어 있지 않은 큐를 넘겨 풀을 만든 경우에도 미리 시작하는 것이 좋다고 적는다. 그 큐의 작업을 꺼내 갈 스레드가 아직 없기 때문이다.

    keepAliveTime과 '코어 스레드'라는 착각

    실험의 마지막 부분을 보자. 모든 작업이 끝난 직후에는 스레드가 4개였다가, 유지 시간 3초가 지난 뒤에는 2개로 줄었다. 코어 수를 넘는 두 스레드가 일거리 없이 3초를 기다리다 종료된 것이다. 그런데 어느 스레드가 살아남았을까? thread-1과 thread-2가 "코어 스레드"이고 thread-3과 thread-4가 "추가 스레드"이니 뒤의 둘이 죽었을까?

    그렇지 않다. ThreadPoolExecutor에는 어떤 스레드가 코어 스레드인지 표시하는 필드가 없다. 구분은 오직 숫자로 이루어진다. getTask()에서 스레드가 큐를 기다리는 방식을 정하는 줄은 boolean timed = allowCoreThreadTimeOut || wc > corePoolSize;다. 현재 작업자 수가 코어 수보다 많으면, 그 순간 큐를 기다리러 온 모든 스레드가 poll(keepAliveTime, ...)로 시간 제한을 두고 기다린다. 시간이 다 되도록 작업을 받지 못한 스레드는, 여전히 작업자 수가 코어보다 많으면 CAS로 수를 하나 줄이고 종료한다. 수가 코어 수까지 내려오면 나머지 스레드는 timed가 false가 되어 take()로 기한 없이 기다린다. 어느 스레드가 살아남는지는 누가 먼저 시간 초과를 맞았는지에 달려 있으므로 실행마다 다르다.

    스레드 덤프로 확인할 수 있다. 코어 1, 최대 2, 유지 시간 60초, 용량 1인 큐로 풀을 만들어 작업 세 개로 스레드를 2개까지 늘린 뒤, 작업이 끝나고 기다리는 동안 jstack을 찍으면 두 스레드 모두 다음과 같이 시간 제한 대기 상태다(JDK 21.0.13, 줄 일부 생략).

    유지 시간을 1초로 줄여 하나가 사라진 뒤 다시 찍으면, 남은 스레드는 WAITING (parking) 상태이고 스택 위쪽에 LockSupport.park가 보인다. 시간 제한 없는 take()로 바뀐 것이다. 덤프는 이 회차의 여러 층을 한 화면에 보여 준다. 풀의 작업 스레드(runWorker) → 작업 가져오기(getTask) → 블로킹 큐(ArrayBlockingQueue.poll) → 조건 변수(ConditionObject.awaitNanos) → LockSupport.parkNanos → Unsafe.park. 7회차에서 본 LockSupport와 9회차의 BlockingQueue가 스레드 풀의 맨 아래층을 이룬다.

    코어 스레드까지 유휴 시간이 지나면 정리되게 하려면 allowCoreThreadTimeOut(true)를 호출한다. 그러면 timed가 항상 true가 되어 유휴 상태가 길어지면 스레드 수가 0까지 줄 수 있다. 단, 유지 시간이 0이면 이 메서드는 IllegalArgumentException("Core threads must have nonzero keep alive times")을 던진다. 그리고 getTask()의 퇴출 조건에는 (wc > 1 || workQueue.isEmpty())가 붙어 있어서, 큐에 작업이 남아 있는 한 마지막 스레드는 시간 초과로 사라지지 않는다. 작업이 남았는데 처리할 스레드가 없어지는 상황을 막는 장치다.

    스레드가 시간 초과가 아니라 작업의 예외로 죽는 경우도 있다. execute로 넘긴 작업이 예외를 던지면 그 예외는 runWorker 밖으로 빠져나가 스레드를 끝낸다. 이때 processWorkerExit는 비정상 종료(completedAbruptly)를 감지해 풀이 STOP 이전이면 addWorker(null, false)로 대체 스레드를 만든다. newFixedThreadPool의 Javadoc이 "종료 전에 실행 중 실패로 스레드가 끝나면 필요할 때 새 스레드가 그 자리를 대신한다"고 적은 것이 이 동작이다. 풀의 크기는 유지되지만 스레드 이름의 번호가 계속 올라가므로, 로그에서 pool-1-thread-57처럼 큰 번호가 보인다면 작업 예외로 스레드가 반복해서 교체되고 있는지 의심해 볼 만하다.

    고정 풀 전략: newFixedThreadPool

    규칙을 알았으니 팩토리 메서드를 해부해 보자. JDK 21의 Executors.newFixedThreadPool(int nThreads)는 단 한 줄이다.

    return new ThreadPoolExecutor(nThreads, nThreads,
                              0L, TimeUnit.MILLISECONDS,
                              new LinkedBlockingQueue());

    코어와 최대가 같고, 유지 시간은 0이며, 큐는 용량을 지정하지 않은 LinkedBlockingQueue다. 용량을 주지 않은 LinkedBlockingQueue의 용량은 Integer.MAX_VALUE다. 실제로 newFixedThreadPool(3)을 ThreadPoolExecutor로 캐스팅해 값을 찍으면 core=3 max=3 keepAlive(ms)=0 queue=LinkedBlockingQueue remaining=2147483647가 나온다. 실무적으로는 무한한 큐다.

    세 단계 규칙에 대입하면 동작이 바로 나온다. 스레드가 n개가 될 때까지는 1단계로 스레드를 만든다. 그 뒤로는 2단계의 offer가 사실상 항상 성공하므로 모든 작업이 큐에 쌓이고, 3단계는 결코 실행되지 않는다. 최대 수가 코어와 같으니 어차피 늘어날 여지도 없다. 유지 시간 0도 의미가 없다. 작업자 수가 코어를 넘는 일이 없으니 timed가 true가 되지 않는다. 결국 스레드는 정확히 n개로 고정되고, 넘치는 작업은 모두 큐에서 기다린다. 실행 중인 동안에는 거절도 일어나지 않는다.

    fixed(10) 제출 직후 pool=10, queued=90, rejected=0, largest=10
fixed(10) 종료 completed=100

    장점은 예측 가능성이다. 스레드 수가 고정되어 있으므로 스레드가 쓰는 메모리와 CPU 경쟁이 상한을 갖는다. CPU를 계속 쓰는 계산 작업이라면 동시에 실행되는 스레드 수를 CPU 코어 수 근처에 묶는 것이 자연스럽고(Runtime.getRuntime().availableProcessors()가 JVM이 쓸 수 있는 프로세서 수를 알려 준다), 고정 풀이 바로 그 모양이다. 요청 수가 예측 가능하고 처리 속도가 그것을 넉넉히 따라가는 서비스에서 고정 풀은 가장 단순하고 안전한 선택이다.

    약점은 과부하에서 드러난다. 작업이 들어오는 속도가 처리 속도보다 꾸준히 빠르면, 스레드 수는 그대로인 채 큐만 끝없이 길어진다. Javadoc도 무한 큐 전략에 대해 "명령이 처리되는 것보다 평균적으로 빠르게 계속 도착하면 작업 큐가 무한히 커질 수 있다"고 경고한다. 큐에 쌓인 작업 객체는 힙을 차지하고, 큐 뒤쪽 작업의 대기 시간은 큐 길이에 비례해 늘어난다. 그리고 이 모든 일이 조용히 일어난다. 예외도, 거절도 없다. 사용자 입장에서는 응답이 점점 느려지다 시간 초과가 나고, 서버 입장에서는 CPU는 평소와 같은데 지연만 늘어나는 이상한 상태가 된다. 이미 응답 시간이 지나 의미가 없어진 요청까지 큐에 남아 순서를 기다리며 스레드를 쓴다.

    같은 풀 안에서 서로를 기다리면

    고정 풀에는 또 하나의 함정이 있다. 풀의 작업이 같은 풀에 다른 작업을 제출하고 그 결과를 기다리는 경우다. 스레드가 하나뿐인 고정 풀에서 바깥 작업이 안쪽 작업을 제출하고 get()을 호출하면, 안쪽 작업은 큐에 들어가지만 그것을 실행할 유일한 스레드가 바로 get()에서 기다리고 있다. 둘은 서로를 영원히 기다린다.

    ExecutorService es = Executors.newFixedThreadPool(1);
Future outer = es.submit(() -> {
    Future inner = es.submit(() -> "inner 결과");
    return "outer가 받은 값: " + inner.get();   // 유일한 스레드가 여기서 기다린다
});
try {
    System.out.println(outer.get(2, TimeUnit.SECONDS));
} catch (TimeoutException e) {
    System.out.println("2초 안에 끝나지 않음: " + es);
}
es.shutdownNow();   // 기다리는 스레드를 인터럽트해 풀어 준다
    2초 안에 끝나지 않음: java.util.concurrent.ThreadPoolExecutor@3d4eac69[Running, pool size = 1, active threads = 1, queued tasks = 1, completed tasks = 0]

    출력이 상황을 그대로 말해 준다. 스레드 1개는 바쁘고(active 1), 작업 1개는 큐에 있으며, 완료된 것은 없다. 스레드가 n개여도 동시에 n개의 바깥 작업이 안쪽 작업을 기다리면 같은 일이 생긴다. 이것을 스레드 기아 교착(thread starvation deadlock)이라고 부른다. ThreadPoolExecutor Javadoc이 직접 전달 큐(뒤에서 볼 SynchronousQueue)에 대해 "내부 의존성이 있는 요청 묶음을 처리할 때 멈춤(lockup)을 피한다"고 쓴 것이 이 문제를 가리킨다. 의존 관계가 있는 작업은 서로 다른 풀로 나누는 것이 기본 대책이다.

    스레드 하나짜리 실행기

    newSingleThreadExecutor()는 스레드 하나와 무한 큐라는 점에서 newFixedThreadPool(1)과 같지만, Javadoc은 "재설정해서 스레드를 늘릴 수 없도록 보장된다"는 차이를 적는다. JDK 21에서 이 메서드가 돌려주는 객체는 ThreadPoolExecutor를 감싼 래퍼(Executors$AutoShutdownDelegatedExecutorService)여서 ThreadPoolExecutor로 캐스팅할 수 없다. 래퍼 클래스의 이름은 구현 세부지만, setCorePoolSize 같은 재설정 메서드에 접근할 길을 막는다는 목적은 Javadoc이 보장하는 성질이다. 모든 작업이 제출된 순서대로 하나씩 실행되므로, 앞에서 본 순서 뒤바뀜이 없다.

    캐시 풀 전략: newCachedThreadPool

    정반대 전략이 newCachedThreadPool()이다. JDK 21 소스는 이렇다.

    return new ThreadPoolExecutor(0, Integer.MAX_VALUE,
                              60L, TimeUnit.SECONDS,
                              new SynchronousQueue());

    코어는 0, 최대는 Integer.MAX_VALUE, 유지 시간은 60초, 그리고 큐는 SynchronousQueue다. 이 큐가 이 전략의 열쇠다. SynchronousQueue의 Javadoc 첫 문장은 "각 삽입 연산이 다른 스레드의 대응하는 제거 연산을 기다려야 하고, 그 반대도 마찬가지인 블로킹 큐"다. 이어서 "내부 용량이 전혀 없다. 용량 1조차 없다"고 적는다. size()와 remainingCapacity()는 항상 0이다. 이름만 큐일 뿐, 실제로는 건네주는 쪽과 받는 쪽이 직접 만나는 손에서 손으로의 전달(direct handoff) 지점이다.

    이 큐의 offer(e)는 기다리지 않는 삽입이므로, 그 순간 다른 스레드가 poll이나 take로 받으려고 기다리고 있을 때만 성공한다. 이제 세 단계 규칙에 대입하자. 코어가 0이므로 1단계는 항상 건너뛴다. 2단계의 offer는 놀고 있는 스레드가 큐 앞에서 poll(60초)로 기다리고 있으면 성공해 그 스레드에 작업이 직접 넘어가고, 놀고 있는 스레드가 없으면 실패한다. 실패하면 3단계에서 최대 한도(사실상 무한) 안에서 새 스레드를 만든다. 결과적으로 놀고 있는 스레드가 있으면 재사용하고, 없으면 무조건 새로 만든다. 작업이 큐에서 기다리는 일은 없다.

    코어가 0이고 작업자 수가 항상 코어보다 많으므로, 모든 스레드가 timed 대기를 한다. 60초 동안 일거리를 받지 못한 스레드는 종료된다. Javadoc의 설명대로 "60초 동안 사용되지 않은 스레드는 종료되어 캐시에서 제거되므로, 충분히 오래 유휴 상태인 풀은 자원을 전혀 소비하지 않는다." 이름의 '캐시'가 가리키는 것이 이 재사용과 만료다.

    cached 제출 직후 pool=100, queued=0, rejected=0, largest=100
cached 종료 completed=100

    같은 100개의 작업이 고정 풀에서는 스레드 10개와 큐 90개로, 캐시 풀에서는 스레드 100개와 큐 0개로 처리된다. 모든 작업이 1초를 자므로 제출하는 동안 놀게 되는 스레드가 없고, 따라서 작업마다 새 스레드가 생긴다. 계산상 고정 풀은 100개를 처리하는 데 1초짜리 작업 열 바퀴, 즉 10초 남짓이 걸리고, 캐시 풀은 한 바퀴인 1초 남짓에 끝난다(실제 소요 시간은 실행 환경마다 조금씩 다르다). 짧은 작업이 많고 각 작업이 금방 끝나는 상황, 또는 작업 대부분이 입출력을 기다리느라 CPU를 거의 쓰지 않는 상황에서 캐시 풀이 빠른 이유다. Javadoc도 "수명이 짧은 비동기 작업을 많이 실행하는 프로그램의 성능을 대개 향상시킨다"고 설명한다.

    위험은 정확히 그 반대편에 있다. 고정 풀이 과부하에서 큐를 무한히 늘린다면, 캐시 풀은 스레드를 무한히 늘린다. Javadoc은 직접 전달 전략에 대해 "명령이 처리되는 것보다 평균적으로 빠르게 계속 도착하면 스레드가 무한히 늘어날 수 있다"고 경고한다. HotSpot에서 자바의 플랫폼 스레드(platform thread)는 운영체제 스레드 하나에 대응하고, 스레드마다 자기 네이티브 스택 메모리를 가진다. 스레드가 수천, 수만 개로 늘어나면 메모리와 운영체제의 스레드 한도가 먼저 바닥나고, 그러면 새 스레드 생성이 실패해 OutOfMemoryError가 발생한다. 그 전에도 실행 가능한 스레드가 CPU 코어 수보다 훨씬 많아지면 1회차에서 본 컨텍스트 스위칭 비용이 늘어나 모든 작업이 함께 느려진다. 과부하 때 일을 미루거나 거절하는 대신 모두 받아들여 시스템 전체를 무너뜨릴 수 있는 것이다.

    한 층 아래: SynchronousQueue는 어떻게 손에서 손으로 건네는가

    캐시 풀의 동작은 "offer는 기다리는 소비자가 있을 때만 성공한다"는 성질 하나에 달려 있었다. 용량이 0인 큐가 이 성질을 어떻게 구현하는지, 그리고 그 구현이 풀의 크기에 어떤 흔적을 남기는지 보자. 이 절의 소스는 Temurin 21.0.13의 src.zip 기준이다. openjdk/jdk21u 저장소의 태그별 소스를 비교하면, JDK 21 첫 릴리스(21 GA)와 21.0.1의 SynchronousQueue는 TransferStack/TransferQueue라는 내부 클래스로 되어 있었고, 21.0.2부터 JDK-8301341 수정이 백포트되면서 LinkedTransferQueue를 확장한 지금의 구조로 바뀌었다. 뒤에서 다룰 "비공정 모드는 스택(LIFO)"이라는 성질은 두 구현에 공통이다(이전 구현의 생성자도 비공정이면 new TransferStack()를 만든다).

    소스 첫머리 주석은 이 클래스가 Scherer와 Scott의 이중 스택·이중 큐(dual stack, dual queue) 알고리즘을 확장한 것이라고 밝힌다. 이중 자료구조는 어느 순간에나 두 종류 중 한 종류의 노드만 담는다. put이나 offer가 남긴 "데이터" 노드이거나, take나 poll이 남긴 "요청" 노드다. 반대 종류의 연산이 오면 새 노드를 쌓지 않고 맨 앞 노드와 짝을 맞춘(match) 뒤 그 노드를 걷어 낸다. 넣기와 꺼내기가 대칭이므로 공개 메서드가 모두 xfer(e, nanos) 하나로 모인다. e가 null이면 꺼내기, 아니면 넣기이고, nanos는 기다릴 시간이다.

    공개 메서드내부 호출 (JDK 21.0.13)짝이 없을 때
    offer(e)xfer(e, 0L)노드를 만들지 않고 즉시 false
    offer(e, timeout, unit)xfer(e, nanos)데이터 노드를 쌓고 시간만큼 기다림
    put(e)xfer(e, Long.MAX_VALUE)데이터 노드를 쌓고 무기한 기다림
    poll()xfer(null, 0L)즉시 null
    poll(timeout, unit)xfer(null, nanos)요청 노드를 쌓고 시간만큼 기다림
    take()xfer(null, Long.MAX_VALUE)요청 노드를 쌓고 무기한 기다림

    비공정 모드(기본 생성자이자 newCachedThreadPool이 쓰는 모드)의 xferLifo는 세 갈래로 움직인다. 스택 꼭대기(head)의 노드가 반대 종류라면, 그 노드의 item 필드를 CAS(compareAndExchange)로 바꿔 짝을 맞추고, 노드를 스택에서 빼고, 그 노드에서 기다리던 스레드를 LockSupport.unpark로 깨운다. 꼭대기가 같은 종류이거나 스택이 비었으면 짝이 없다. 이때 nanos가 0이면 노드를 만들지도 않고 실패를 돌려준다. 0이 아니면 자기 노드를 CAS로 꼭대기에 쌓고 기다린다. 캐시 풀의 두 동작이 정확히 여기에 대응한다.

    • 쉬는 작업 스레드: getTask()의 poll(60초)가 xfer(null, 60초)가 되어 요청 노드(item이 null)를 쌓고 기다린다.
    • execute()의 2단계: offer(task)가 xfer(task, 0)이 되어, 꼭대기에 요청 노드가 있으면 그 노드의 item을 null에서 task로 CAS하고 그 스레드를 깨운다. 없으면 즉시 false가 돌아오고, execute는 3단계로 넘어가 새 스레드를 만든다.

    기다리는 쪽의 코드(LinkedTransferQueue.DualNode.await)도 볼 만하다. 노드를 쌓은 스레드는 곧바로 잠들지 않는다. 스택이 비어 있었거나 꼭대기 노드에 기다리는 스레드가 없으면 최대 128번(SPINS = 1 << 7) Thread.onSpinWait()를 부르며 item이 바뀌었는지 확인한다. 그래도 짝이 없으면 waiter 필드에 자기 스레드를 적고 전체 메모리 펜스(VarHandle.fullFence())를 둔 뒤 LockSupport.parkNanos로 잠든다. 남은 시간이 1,024나노초(SPIN_FOR_TIMEOUT_THRESHOLD = 1L << 10)보다 짧으면 잠들지 않고 스핀한다. 가상 스레드이거나 프로세서가 하나뿐이면 처음의 스핀을 건너뛴다. 시간이 다 되거나 인터럽트되면 자기 노드의 item을 넣는 쪽이 결코 쓰지 않는 값(요청 노드라면 노드 자신)으로 CAS해 취소된 노드로 만들고, 스택에서 걷어 낸다. 넣는 쪽의 CAS와 취소하는 쪽의 CAS가 같은 필드를 두고 경쟁하므로, 작업이 전달되거나 시간 초과로 끝나거나 둘 중 하나만 일어난다. 작업이 전달되었는데 작업 스레드는 시간 초과로 사라지는 일은 생기지 않는다.

    캐시 풀에서 쉬고 있는 스레드의 덤프를 찍으면 이 경로가 그대로 보인다(JDK 21.0.13, 줄 일부 생략).

    LIFO라서 캐시 풀이 줄어든다

    비공정 모드가 스택이라는 사실은 캐시 풀의 크기에 직접 영향을 준다. SynchronousQueue Javadoc은 공정 모드(new SynchronousQueue<>(true))에서는 기다리는 스레드들이 FIFO 순서로 접근하고, 기본(비공정) 모드에서는 "이 순서가 보장되지 않는다"고만 적는다. 명세가 열어 둔 그 순서를 OpenJDK는 스택으로 구현했고, 소스 주석은 이유를 "캐시 스레드 풀 같은 자원 관리 상황에서는 시간적 지역성(temporal locality)이 좋아서 LIFO가 대개 낫다"고 설명한다. 가장 최근에 일을 마치고 쉬러 온 스레드가 스택 꼭대기에 있으므로 다음 작업은 그 스레드가 받는다. 오래 쉰 스레드는 스택 바닥에서 계속 기다리다 유지 시간이 다 되어 사라진다.

    실험으로 확인해 보자. 캐시 풀과 같은 모양(코어 0, 최대 무한, SynchronousQueue)에 유지 시간만 2초로 줄이고, 0.2초짜리 작업 10개로 스레드를 10개까지 늘린 뒤, 150ms마다 아주 짧은 작업을 하나씩 6초 동안 넣는다. 큐의 공정성만 바꿔 두 번 돌린다. 앞에는 SynchronousQueue 자체의 offer도 확인해 둔다.

    import java.util.*;
import java.util.concurrent.*;

public class HandoffMain {
    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    static void run(boolean fair) {
        ThreadPoolExecutor es = new ThreadPoolExecutor(          // 캐시 풀 모양, 유지 시간만 2초
                0, Integer.MAX_VALUE, 2, TimeUnit.SECONDS, new SynchronousQueue<>(fair));
        for (int i = 0; i < 10; i++) es.execute(() -> sleep(200)); // 몰림: 스레드 10개
        sleep(500);                                                  // 모두 쉬는 상태가 된다
        Set used = ConcurrentHashMap.newKeySet();
        for (int i = 0; i < 40; i++) {                               // 150ms마다 하나씩, 6초 동안
            es.execute(() -> used.add(Thread.currentThread().getName()));
            sleep(150);
        }
        System.out.println((fair ? "fair(FIFO) " : "기본(LIFO) ") + "6초 뒤 pool=" + es.getPoolSize()
                + ", 작업을 맡은 스레드 수=" + used.size());
        es.shutdown();
    }

    public static void main(String[] args) {
        SynchronousQueue q = new SynchronousQueue<>();
        System.out.println("받는 쪽 없이 offer: " + q.offer("x"));
        new Thread(() -> { try { q.take(); } catch (InterruptedException e) { } }).start();
        sleep(100);
        System.out.println("take 대기 중일 때 offer: " + q.offer("x") + ", size=" + q.size());
        run(false);
        run(true);
    }
}
    받는 쪽 없이 offer: false
take 대기 중일 때 offer: true, size=0
기본(LIFO) 6초 뒤 pool=1, 작업을 맡은 스레드 수=1
fair(FIFO) 6초 뒤 pool=10, 작업을 맡은 스레드 수=10

    첫 두 줄은 표의 첫 행 그대로다. 받는 쪽이 없으면 offer는 실패하고, take로 기다리는 스레드가 있으면 성공하지만 그 뒤에도 size()는 0이다. 원소는 큐에 머문 적 없이 상대 스레드로 넘어갔다.

    나머지 두 줄은 들어오는 부하가 똑같이 "150ms마다 작업 하나"인데 결과가 정반대다. 비공정(LIFO) 모드에서는 매번 방금 일을 마친 같은 스레드가 꼭대기에서 작업을 받으므로, 6초 동안 단 하나의 스레드만 일했고 나머지 아홉은 유지 시간이 지나 정리되었다. 공정(FIFO) 모드에서는 작업이 가장 오래 기다린 스레드에게 돌아가므로 스레드 10개가 1.5초(150ms × 10)마다 한 번씩 차례로 일을 받는다. 1.5초는 유지 시간 2초보다 짧으므로 어느 스레드도 시간 초과에 이르지 못하고, 스레드 하나면 충분한 부하에 10개가 계속 유지된다. 캐시 풀이 "부하가 줄면 스스로 줄어든다"는 성질은 Javadoc의 60초 규칙만으로 나오는 것이 아니라, 전달 순서가 LIFO라는 구현과 함께 성립한다. 이 수치는 타이밍에 기대는 실험의 결과이므로, CPU가 매우 바쁜 환경이라면 달라질 수 있다.

    스레드를 더 만들 수 없을 때: 거절 정책을 건너뛰는 OutOfMemoryError

    캐시 풀의 최대 스레드 수는 Integer.MAX_VALUE지만 운영체제는 그만큼의 스레드를 허락하지 않는다. 2회차에서 보았듯 Thread.start()는 HotSpot의 JVM_StartThread를 거쳐 pthread_create를 호출하고, 그것이 실패하면 OutOfMemoryError가 던져진다. 이 절의 질문은 그 실패가 스레드 풀 안에서 일어나면 어떻게 처리되느냐다. 풀이 더 이상 작업을 받을 수 없는 상황이니 거절 정책이 불릴 것 같지만, 소스는 다르게 말한다.

    addWorker는 두 단계로 일한다. 먼저 CAS로 ctl의 작업자 수를 하나 올려 자리를 예약한다. 그다음 Worker를 만들고(이때 ThreadFactory.newThread가 호출된다), mainLock 안에서 workers 집합에 넣고 largestPoolSize를 갱신한 뒤, 락 밖에서 스레드를 시작한다. JDK 21에서는 이 시작이 container.start(t)(SharedThreadContainer)를 거치지만 결국 Thread.start0()에 도착한다. 시작에 성공하지 못하면 finally의 addWorkerFailed(w)가 집합에서 Worker를 빼고, 작업자 수를 되돌리고, tryTerminate()를 부른다. 소스 주석은 이 경우를 "스레드 팩토리가 null을 돌려주거나 예외(전형적으로 Thread.start()의 OutOfMemoryError)로 스레드 생성이 실패하면 깔끔하게 되돌린다"고 설명한다. 갈림길은 되돌린 다음에 있다.

    • 팩토리가 null을 돌려준 경우: addWorker가 false를 반환하고, execute는 이것을 포화로 보고 reject(command)를 부른다. 항상 null을 돌려주는 팩토리로 만든 풀(코어 0, 최대 10, SynchronousQueue)에 작업을 넣자 RejectedExecutionException이 났고 pool=0, largest=0이었다. ThreadFactory.newThread의 Javadoc도 반환값을 "생성된 스레드, 또는 스레드 생성 요청이 거부되면 null"이라고 정의한다.
    • start()가 예외를 던진 경우: addWorker에는 이 예외를 잡는 catch가 없다. finally로 되돌리기만 하고, 예외는 그대로 execute 밖, 즉 작업을 제출한 스레드로 전파된다. 거절 정책은 불리지 않는다.

    운영체제의 한도를 실제로 넘겨 확인해 보자. 이 실험을 한 macOS에서 sysctl kern.num_taskthreads의 값은 4096이다. 캐시 풀과 같은 설정에 거절 횟수만 세는 핸들러를 달고, 래치가 열릴 때까지 끝나지 않는 작업을 계속 제출한다.

    import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class LimitMain {
    public static void main(String[] args) throws Exception {
        AtomicInteger rejected = new AtomicInteger();
        CountDownLatch release = new CountDownLatch(1);
        ThreadPoolExecutor es = new ThreadPoolExecutor(
                0, Integer.MAX_VALUE, 60, TimeUnit.SECONDS, new SynchronousQueue<>(),
                (r, ex) -> rejected.incrementAndGet());           // 거절되면 세기만 한다
        int submitted = 0;
        try {
            for (int i = 0; i < 10_000; i++) {
                es.execute(() -> {
                    try { release.await(); } catch (InterruptedException e) { }
                });
                submitted++;
            }
        } catch (Throwable t) {
            System.out.println("execute가 던진 것: " + t);
        }
        System.out.println("성공한 제출=" + submitted + ", pool=" + es.getPoolSize()
                + ", largest=" + es.getLargestPoolSize() + ", 거절 핸들러 호출=" + rejected.get());
        System.out.println("JVM 전체 스레드 수=" + Thread.getAllStackTraces().size());
        release.countDown();
        es.shutdown();
        System.out.println("awaitTermination=" + es.awaitTermination(10, TimeUnit.SECONDS));
    }
}

    largest=4069가 pool=4068보다 하나 큰 것도 소스로 설명된다. largestPoolSize는 스레드를 시작하기 전에 workers에 넣으면서 갱신되고, 시작이 실패해 addWorkerFailed가 그 Worker를 빼도 되돌려지지 않는다. 시작조차 못 한 스레드 하나가 이 값에 포함된 것이다. 래치를 연 뒤에는 풀이 정상적으로 종료되었다. 생성 실패가 풀의 장부(ctl의 작업자 수와 workers)를 어긋나게 하지 않았다는 뜻이다.

    실무에서 뜻하는 바는 두 가지다. 첫째, 최대 스레드 수가 사실상 무한한 풀에서는 "포화되면 거절 정책이 처리한다"는 설계가 운영체제 한도 앞에서 작동하지 않는다. OutOfMemoryError는 Error의 하위 클래스라서 catch (RejectedExecutionException e)는 물론 catch (Exception e)에도 잡히지 않는다. 위쪽 어디에서도 Throwable이나 Error를 잡지 않으면 요청을 처리하던 스레드가 그대로 끝난다. 둘째, 한도는 프로세스 전체가 함께 쓴다. 이 실험의 변형으로 한도에 닿은 상태에서 ProcessBuilder.start()를 호출해 보았더니, 우리 풀과 상관없는 JDK 내부의 process reaper 스레드를 만들지 못해 같은 OutOfMemoryError가 main에 던져졌다. 스택 트레이스는 ProcessImpl.initStreams → ProcessHandleImpl.completion → ThreadPoolExecutor.execute → addWorker → Thread.start0였다. JDK 내부의 그 풀도 같은 한도를 나눠 쓰는 것이다(이 변형 실행은 래치를 기다리는 데몬이 아닌 풀 스레드 4,068개가 남아 스스로 끝나지 않았고, 프로세스를 직접 종료했다). 상한 없는 풀 하나가 스레드를 다 쓰면 무관한 기능까지 함께 실패한다. 앞의 표에서 캐시 풀이 과부하에서 늘리는 것을 "스레드 수, 스택 메모리"라고 적은 것의 끝이 이 모습이다.

    사용자 정의 풀 전략: 평소, 급증, 초과를 나눠 설계한다

    두 기본 전략의 공통된 약점은 어딘가에 상한이 없다는 것이다. 운영 환경에서 과부하는 반드시 온다. 그때 시스템이 할 수 있는 선택은 늦게 처리하거나(큐), 더 많은 자원을 쓰거나(스레드), 거절하는 것이다. 사용자 정의 풀은 이 세 가지를 모두 유한하게 정해 두는 전략이다. Javadoc이 세 번째 큐 전략으로 소개하는 "유한 큐(bounded queue)"가 이것이다. Javadoc은 유한 큐가 유한한 최대 스레드 수와 함께 쓰일 때 자원 고갈을 막는 데 도움이 되지만 조정하기는 더 어렵다고 덧붙인다.

    코어 10, 최대 20, 유지 시간 60초, 용량 50인 ArrayBlockingQueue로 풀을 만들고 1초짜리 작업 100개를 연달아 제출해 보자.

    ThreadPoolExecutor es = new ThreadPoolExecutor(
        10, 20, 60, TimeUnit.SECONDS, new ArrayBlockingQueue<>(50));
    custom(10,20,q50) 제출 직후 pool=20, queued=50, rejected=30, largest=20
custom(10,20,q50) 종료 completed=70

    세 단계 규칙으로 계산한 값과 정확히 일치한다. 1~10번째 작업은 코어 스레드 10개를 만든다. 11~60번째 50개는 큐를 채운다. 61~70번째 10개는 큐가 가득 찼으므로 최대 20까지 추가 스레드를 만들어 바로 실행된다. 71~100번째 30개는 스레드도 최대이고 큐도 가득이므로 거절된다. 이 풀이 한순간에 받아들일 수 있는 작업의 총량은 최대 스레드 수 + 큐 용량 = 20 + 50 = 70이다.

    이 설정을 부하 구간으로 읽으면 설계 의도가 드러난다. 평소에는 동시에 들어오는 작업이 10개 이하라 코어 스레드만으로 처리한다. 급증하면 먼저 큐 50칸이 일시적인 몰림을 흡수하고, 그것마저 넘치면 스레드를 20개까지 늘려 처리 속도를 올린다. 몰림이 지나가면 늘어난 10개는 60초 뒤 정리된다. 그래도 감당할 수 없는 초과 상태에서는 더 받지 않고 거절해, 이미 받은 작업의 처리 시간과 서버 자원을 지킨다. 거절된 요청에는 바로 실패를 돌려주어 클라이언트가 재시도하거나 다른 서버로 가게 할 수 있다. 늦게 실패하는 것보다 빨리 실패하는 편이 전체 시스템에는 낫다는 판단이다.

    숫자를 고르는 기준

    세 숫자는 서로 연결되어 있다. 큐 용량은 곧 최악의 대기 시간이다. 예를 들어 작업 하나가 평균 100ms 걸리고 스레드가 10개라면 이 풀은 초당 약 100개를 처리하므로, 큐의 맨 뒤에 들어간 작업은 앞의 50개가 빠지는 약 0.5초를 기다린다(이 숫자는 계산을 보이기 위한 가정이다). 클라이언트가 허용하는 응답 시간이 1초라면 큐가 1,000칸이어도 될까? 맨 뒤 작업은 10초를 기다리게 되고, 그 사이 클라이언트는 이미 포기했을 것이다. 그 작업을 처리하는 것은 낭비다. 큐 용량은 "얼마나 기다리게 할 수 있는가"로부터 거꾸로 정해야 한다.

    최대 스레드 수는 작업이 무엇을 기다리는지에 따라 달라진다. Javadoc의 표현으로 "작업이 자주 블로킹된다면(예: 입출력에 묶여 있다면) 시스템은 허용한 것보다 더 많은 스레드에 시간을 배분할 수 있다." CPU만 쓰는 작업은 코어 수를 넘겨 봐야 이득이 없고, 입출력 대기가 대부분인 작업은 더 많은 스레드가 필요할 수 있다. 다만 입출력의 상대편, 예를 들어 데이터베이스 커넥션 풀이 10개라면 그 커넥션을 쓰는 작업 스레드를 100개로 늘려도 90개는 커넥션을 기다릴 뿐이다. 최대 스레드 수는 그 작업이 쓰는 가장 좁은 자원에 맞춰야 한다. 결국 이 숫자들은 공식으로 계산되기보다 측정(부하 테스트, 운영 지표)으로 정해진다. 지표를 볼 수 있도록 getPoolSize(), getActiveCount(), getQueue().size(), getLargestPoolSize(), getCompletedTaskCount()를 주기적으로 기록해 두면 판단의 근거가 된다.

    사용자 정의 풀에서 자주 하는 실수

    가장 흔한 실수는 최대 스레드 수를 크게 주면서 큐는 무한으로 두는 것이다. 코어 2, 최대 10에 용량 없는 LinkedBlockingQueue를 주고 300ms짜리 작업 50개를 넣으면 결과는 pool=2, queued=48이다. 큐가 결코 가득 차지 않으므로 3단계가 실행되지 않고, 최대 10은 아무 의미가 없다. Javadoc도 무한 큐에 대해 "corePoolSize보다 많은 스레드는 결코 만들어지지 않는다(따라서 maximumPoolSize 값은 아무 효과가 없다)"고 명시한다. 설정 파일에서 최대 스레드 수를 아무리 늘려도 처리량이 그대로인 이유가 이것인 경우가 많다.

    그 변형으로 코어 0과 무한 큐의 조합이 있다. 같은 실험을 코어 0, 최대 10, 무한 큐로 하면 스레드는 단 1개다(큐에는 49~50개가 남아 있고, 정확한 값은 첫 작업을 꺼내 갔는지에 따라 다르다). 1단계는 코어가 0이라 건너뛰고, 2단계의 offer는 성공한다. 이때 재확인 코드가 "작업자 수가 0이면 첫 작업 없는 스레드를 하나 만든다"를 실행해 스레드가 하나 생긴다. 그 뒤로는 offer가 계속 성공하고 작업자 수는 1이니 더 이상 스레드가 생기지 않는다. 캐시 풀이 코어 0이어도 잘 동작하는 것은 SynchronousQueue의 offer가 실패해 3단계로 넘어가기 때문이고, 무한 큐에서는 그 경로가 막힌다. 유휴 시에는 스레드를 모두 정리하면서 부하 때는 10개까지 쓰고 싶다면, 코어 10에 allowCoreThreadTimeOut(true)를 켜는 쪽이 의도에 맞다.

    예외 정책: 거절된 작업을 어떻게 할 것인가

    작업이 거절되는 경우는 두 가지다. ThreadPoolExecutor Javadoc에 따르면 Executor가 이미 종료(shutdown)되었을 때, 그리고 최대 스레드 수와 큐 용량이 모두 유한한 상태에서 포화되었을 때다. 어느 경우든 execute는 RejectedExecutionHandler의 rejectedExecution(Runnable r, ThreadPoolExecutor executor)를 호출한다. 이 핸들러가 거절된 작업의 운명을 정하는 거절 정책(rejection policy)이다. submit도 내부에서 execute를 호출하므로 같은 정책을 거친다. JDK는 네 가지 정책을 ThreadPoolExecutor의 정적 중첩 클래스로 제공한다.

    AbortPolicy (기본)RejectedExecutionException을 던진다예외
    DiscardPolicy아무것도 하지 않는다(조용히 버림)버림
    CallerRunsPolicyexecute를 호출한 스레드에서 r.run()을 직접 실행버림
    DiscardOldestPolicy큐의 맨 앞 작업을 poll()로 꺼내 버리고 execute(r)를 다시 시도버림

    네 정책을 같은 조건에서 비교해 보자. 코어 1, 최대 1, SynchronousQueue인 풀을 만들면 스레드 하나가 작업 중일 때 들어오는 작업은 큐에도 들어갈 수 없고 스레드도 늘릴 수 없으므로 즉시 거절된다. 0.5초짜리 작업으로 확인한다.

    import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;

public class RejectMain {
    static void log(String msg) {
        System.out.println(Thread.currentThread().getName() + ": " + msg);
    }

    static Runnable task(String name) {
        return () -> {
            log(name + " 실행");
            try { Thread.sleep(500); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
        };
    }

    static ThreadPoolExecutor pool(RejectedExecutionHandler h) {
        return new ThreadPoolExecutor(1, 1, 0, TimeUnit.SECONDS, new SynchronousQueue<>(), h);
    }

    public static void main(String[] args) throws Exception {
        System.out.println("== AbortPolicy ==");
        ThreadPoolExecutor a = pool(new ThreadPoolExecutor.AbortPolicy());
        a.execute(task("a1"));
        try { a.execute(task("a2")); }
        catch (RejectedExecutionException e) { log("예외: " + e.getClass().getName()); }
        a.close();

        System.out.println("== DiscardPolicy ==");
        ThreadPoolExecutor d = pool(new ThreadPoolExecutor.DiscardPolicy());
        d.execute(task("d1"));
        Future lost = d.submit(task("d2"));
        log("submit 반환됨, isDone=" + lost.isDone());
        try { lost.get(1, TimeUnit.SECONDS); }
        catch (TimeoutException e) { log("get 1초 대기 후 TimeoutException"); }
        d.close();

        System.out.println("== CallerRunsPolicy ==");
        ThreadPoolExecutor c = pool(new ThreadPoolExecutor.CallerRunsPolicy());
        c.execute(task("c1"));
        c.execute(task("c2"));
        log("c2 제출이 반환됨");
        c.close();

        System.out.println("== 사용자 정의 ==");
        AtomicInteger rejected = new AtomicInteger();
        ThreadPoolExecutor u = pool((r, ex) -> log("거절 기록 #" + rejected.incrementAndGet() + " " + ex));
        u.execute(task("u1"));
        u.execute(task("u2"));
        u.execute(task("u3"));
        u.close();
    }
}

    AbortPolicy 부분과 CallerRunsPolicy 부분의 처음 두 줄은 실행마다 순서가 바뀔 수 있다. 앞 작업(a1, c1)은 풀 스레드에서, 그다음 줄(예외 로그, c2)은 main에서 거의 동시에 출력되기 때문이다. 해시코드와 active threads 값도 실행마다 다를 수 있다.

    AbortPolicy: 실패를 호출자에게 알린다

    기본 정책이다. 거절되면 "Task " + r + " rejected from " + executor 형식의 메시지를 가진 RejectedExecutionException을 던진다. 앞의 종료 실험에서 본 메시지가 바로 이것이고, 메시지 안에 풀의 toString()이 들어 있어 거절 당시의 스레드 수와 큐 길이를 알 수 있다. RejectedExecutionException은 런타임 예외이므로 컴파일러가 처리를 강제하지 않는다. 작업을 제출하는 코드는 이 예외가 날 수 있다는 것을 알고, 잡아서 클라이언트에 "지금은 처리할 수 없음"을 돌려주거나 다른 경로로 보내야 한다. 잡지 않으면 제출한 스레드(예를 들어 요청을 처리하던 스레드)까지 예외로 끝난다.

    DiscardPolicy: 조용히 버린다, 그리고 Future는 영원히 기다린다

    거절된 작업을 아무 흔적 없이 버린다. Javadoc은 이 정책이 "작업의 완료에 결코 의존하지 않는 드문 경우를 위해서만 설계되었다"고 적는다. 실험에서 더 위험한 점이 드러났다. submit으로 제출했다면 submit은 예외 없이 Future를 돌려준다. 그런데 그 안의 FutureTask는 핸들러가 버렸으므로 실행되지도, 취소되지도 않는다. isDone()은 영원히 false이고, 시간 제한 없이 get()을 부른 스레드는 영원히 멈춘다. 실험에서는 1초 제한을 두었기에 TimeoutException으로 빠져나올 수 있었다. shutdownNow가 돌려준 작업을 버렸을 때와 같은 문제이고, 원인도 같다. Future를 완료 상태로 만드는 것은 그 작업을 실행하거나 취소하는 쪽인데, 아무도 그 일을 하지 않았다.

    CallerRunsPolicy: 제출한 스레드가 직접 실행한다

    거절된 작업을 execute를 호출한 스레드에서 바로 실행한다. 실험에서 c2가 main 스레드 이름으로 실행되었고, "c2 제출이 반환됨"은 c2의 0.5초 실행이 끝난 뒤에야 출력되었다. 작업이 버려지지 않는다는 것이 첫 번째 장점이다. 두 번째 장점이 더 중요하다. Javadoc의 표현으로 이 정책은 "새 작업이 제출되는 속도를 늦추는 간단한 피드백 제어 장치"다. 제출하던 스레드가 작업을 직접 실행하는 동안에는 새 작업을 제출할 수 없으므로, 풀이 포화되면 생산자의 속도가 저절로 소비자 속도에 맞춰진다. 이렇게 하류의 처리 능력이 상류의 공급 속도를 제어하는 것을 배압(back-pressure)이라고 부른다. 8~9회차의 생산자 소비자 문제에서 큐가 가득 차면 생산자를 멈추게 했던 것과 같은 효과를 거절 정책으로 얻는 셈이다.

    대가도 분명하다. 제출하는 스레드가 원래 하던 일을 멈추고 작업을 실행하므로, 그 스레드가 네트워크 연결을 받아들이는 스레드나 사용자 화면을 그리는 스레드라면 그 역할이 멈춘다. 작업은 풀의 스레드가 아니라 호출자의 스레드에서 실행되므로, 스레드 이름이나 ThreadLocal 값처럼 스레드에 묶인 문맥도 달라진다. 또 소스를 보면 if (!e.isShutdown()) r.run();이다. 풀이 종료된 뒤에 거절된 작업은 실행되지 않고 조용히 버려진다. 이름만 보고 "어떤 경우에도 실행된다"고 믿으면 안 된다.

    DiscardOldestPolicy: 가장 오래 기다린 작업을 버린다

    풀이 종료되지 않았다면 큐의 맨 앞, 즉 가장 오래 기다린 작업을 꺼내 버리고 새 작업으로 execute를 다시 시도한다. 재시도가 다시 실패하면 같은 과정이 반복될 수 있다. 오래된 데이터보다 최신 데이터가 중요한 경우(예: 최신 상태만 의미 있는 갱신 작업)를 위한 정책이지만, Javadoc은 이 정책이 "드물게만 받아들여진다"고 평가하고, 대부분의 경우 버리는 작업을 취소해 그 완료를 기다리는 쪽이 예외를 받게 하고 실패를 기록해야 한다고 권한다. 버려지는 작업이 FutureTask라면 DiscardPolicy와 똑같이 그 Future는 영원히 완료되지 않기 때문이다.

    사용자 정의 정책

    RejectedExecutionHandler는 메서드가 하나뿐인 인터페이스이므로 람다로 쓸 수 있다. 실험의 사용자 정의 정책은 거절 횟수를 원자적으로 세고 풀의 상태와 함께 로그를 남긴다. 실무에서는 여기에 지표(거절 횟수 카운터)를 기록하고, 원래 정책처럼 예외를 던지거나, 버리는 작업이 Future라면 cancel을 호출하는 식으로 조합한다. 거절은 "풀의 용량이 부족하다"는 가장 직접적인 신호이므로, 어떤 정책을 쓰든 거절이 일어났다는 사실은 반드시 관측 가능하게 남기는 것이 좋다. 조용히 버려지는 작업은 장애 분석 때 가장 찾기 어렵다.

    가득 찬 풀 앞에서 거절된 작업 하나가 네 정책에 따라 어디로 가는지 네 칸으로 나눠 보여 준다. 가로로 4칸을 나눈 개념도. 맨 위 가운데에 "가득 찬 스레드 풀" 상자(안에 바쁜 스레드 아이콘과 꽉 찬 큐), 그 앞에 주황색 작업 상자 하나와 "거절된 작업" 라벨. 아래 네 칸: 첫째 칸 "AbortPolicy" 제목, 작업 상자에서 빨간 번개 표시와 "예외를 던짐" 라벨. 둘째 칸 "DiscardPolicy" 제목, 작업 상자가 휴지통으로 들어가고 "조용히 버림" 라벨. 셋째 칸 "CallerRunsPolicy" 제목, 작업 상자를 제출한 사람 아이콘이 직접 들고 일하는 모습과 "호출한 스레드가 실행" 라벨. 넷째 칸 "DiscardOldestPolicy" 제목, 큐 맨 앞 상자가 휴지통으로 가고 새 상자가 큐 끝으로 들어가는 모습과 "가장 오래된 작업을 버림" 라벨. 흰 배경, 단순한 선화. 기본 정책은 AbortPolicy다. 버리는 정책은 submit의 Future를 영원히 미완료로 남길 수 있다.

    흔한 오해 바로잡기

    이 회차의 내용을 오해하기 쉬운 문장들로 다시 점검해 보자. 각 문장이 왜 그럴듯해 보이는지, 실제로는 어떤지 함께 적는다.

    • "shutdown()을 부르면 작업이 끝날 때까지 기다린다." 메서드 이름이 동작을 완결하는 것처럼 들리기 때문에 생기는 오해다. shutdown()은 상태를 바꾸고 쉬는 스레드를 깨운 뒤 즉시 반환된다. 기다리려면 awaitTermination이나 close()가 필요하다.
    • "awaitTermination을 부르면 풀이 정리된다." 반대 방향의 오해다. 종료 요청이 없으면 isTerminated()는 결코 true가 되지 않으므로 awaitTermination은 시간을 다 쓰고 false를 반환할 뿐이다.
    • "shutdownNow()는 스레드를 강제로 죽인다." 자바에는 스레드를 안전하게 강제 종료하는 수단이 없다. shutdownNow는 인터럽트를 걸 뿐이고, 인터럽트를 무시하는 작업은 끝까지 실행된다.
    • "코어가 바쁘면 최대까지 스레드를 늘리고 그다음 큐에 쌓는다." 실제 순서는 코어 → 큐 → 최대다. 무한 큐를 쓰면 최대 스레드 수는 효과가 없다.
    • "코어 스레드는 따로 정해진 특별한 스레드다." 코어 여부는 스레드에 붙은 표시가 아니라 현재 작업자 수와 corePoolSize의 비교로만 정해진다. 유지 시간이 지나 사라지는 스레드는 먼저 만들어진 것일 수도, 나중에 만들어진 것일 수도 있다.
    • "스레드 풀은 제출 순서대로 실행한다." 큐는 FIFO지만 3단계에서 만들어진 스레드는 넘겨받은 작업을 바로 실행하므로, 나중에 제출한 작업이 큐에서 기다리던 작업보다 먼저 시작될 수 있다.
    • "CallerRunsPolicy면 작업이 절대 유실되지 않는다." 풀이 종료된 뒤에 거절된 작업은 실행되지 않고 버려진다.
    • "getActiveCount()는 정확한 값이다." Javadoc이 "대략적인 수"라고 부른다. 스레드의 상태는 계산하는 동안에도 바뀌므로, 지표는 추세를 보는 용도로 쓴다.
    이 장의 핵심

    스레드 풀의 동작은 두 가지 규칙으로 거의 다 설명된다. 생명 주기는 ctl의 실행 상태가 RUNNING → SHUTDOWN/STOP → TIDYING → TERMINATED로 앞으로만 움직이는 상태 기계이고, 종료는 인터럽트라는 협력적 신호에 의존하므로 작업 코드가 그 신호에 반응해야 완성된다. 크기는 execute()의 코어 → 큐 → 최대 → 거절 순서로 정해지므로, 큐의 종류와 용량을 보면 과부하에서 큐가 늘어날지(고정 풀), 스레드가 늘어날지(캐시 풀), 거절할지(유한 큐의 사용자 정의 풀)를 예측할 수 있다.

    다른 주제와의 연결

    이 회차의 규칙은 스프링을 쓸 때 그대로 다시 나타난다. 스프링의 ThreadPoolTaskExecutor는 내부에서 ThreadPoolExecutor를 만들어 쓰는 래퍼이고, corePoolSize, maxPoolSize, keepAliveSeconds, queueCapacity 속성이 생성자 인자에 대응한다. Spring Framework Javadoc에 따르면 기본값은 코어 1, 최대 Integer.MAX_VALUE, 유지 시간 60초, 큐 용량 Integer.MAX_VALUE이고, 큐 용량이 양수면 LinkedBlockingQueue를, 그 밖의 값이면 SynchronousQueue를 쓴다. 같은 문서는 기본 설정이 "대략 Executors.newSingleThreadExecutor()와 같아서 모든 작업이 스레드 하나를 공유한다"고 설명한다. 이 회차의 규칙을 알면 이유가 보인다. 큐가 사실상 무한이니 코어 1을 넘는 스레드가 만들어지지 않는다. 최대 스레드 수만 올리고 큐 용량을 그대로 두면 아무 효과가 없다는 것도 같은 규칙에서 나온다. 문서 역시 allowCoreThreadTimeOut 설명에서 "최대 풀 크기는 큐가 가득 찬 뒤에야 늘어난다"고 적고 있다.

    웹 서버의 요청 처리 스레드 풀, 데이터베이스 커넥션 풀도 같은 질문을 던진다. 유한한 자원(스레드, 커넥션)을 몇 개 둘 것인가, 자원이 모자라면 요청을 어디서 얼마나 기다리게 할 것인가, 기다림의 한계를 넘으면 무엇을 할 것인가. 커넥션 풀에서 커넥션을 얻지 못한 요청이 정해진 시간만큼 기다리다 예외를 받는 것은, 이 회차의 유한 큐와 거절 정책을 다른 자원에 적용한 모양이다. 애플리케이션 종료 때 프레임워크가 실행기를 정리하는 절차도 결국 이 회차의 shutdown → awaitTermination → shutdownNow 구조 위에 있다.

    마지막으로 Java 21에는 Executors.newVirtualThreadPerTaskExecutor()가 추가되었다(Javadoc "Since: 21"). 작업마다 새 가상 스레드(virtual thread)를 만드는 실행기이고, Javadoc은 이 실행기가 만드는 스레드 수에 상한이 없다고 적는다. 스레드를 재사용하기 위한 풀이 아니므로 이 회차의 코어·큐·최대 규칙은 적용되지 않는다. 그 대신 동시에 실행되는 작업 수를 제한해야 한다면 그 제한은 다른 수단으로 따로 걸어야 한다. 그래도 종료의 원리는 같다. 이 실행기도 ExecutorService이므로 shutdown, awaitTermination, close의 의미가 그대로이고, 인터럽트에 반응하지 않는 작업은 여전히 스스로 끝날 때까지 멈출 수 없다.
    우아한 종료
    새 작업은 거절하고(shutdown), 받은 작업은 정해진 시간 동안 끝내게 기다린 뒤(awaitTermination), 남은 것은 인터럽트로 취소하는(shutdownNow) 두 단계 종료 절차다.
    shutdown과 shutdownNow
    shutdown은 큐의 작업까지 실행하고 쉬는 스레드만 깨운다. shutdownNow는 큐를 비워 실행되지 못한 작업 목록을 돌려주고 모든 작업 스레드를 인터럽트한다. 둘 다 즉시 반환된다.
    close() (Java 19+)
    shutdown 후 종료될 때까지 시간 상한 없이 기다리는 기본 메서드로, try-with-resources에 쓸 수 있다. 대기 중 인터럽트되면 shutdownNow를 한 번 호출하고 계속 기다린다.
    ctl과 실행 상태
    위 3비트에 실행 상태, 아래 29비트에 작업자 수를 담은 AtomicInteger다. 상태는 RUNNING → SHUTDOWN/STOP → TIDYING → TERMINATED로 앞으로만 진행한다.
    execute()의 세 단계
    스레드가 코어보다 적으면 새 스레드, 아니면 큐에 삽입, 큐가 거절하면 최대까지 새 스레드, 그것도 안 되면 거절 정책 실행.
    keepAliveTime
    작업자 수가 코어보다 많을 때 큐를 기다리는 모든 스레드가 poll(keepAliveTime)로 기다리고, 시간 초과된 스레드가 종료되어 수가 코어까지 줄어든다. 코어 스레드라는 표시는 없다.
    고정 풀과 캐시 풀
    고정 풀은 (n, n, 0, LinkedBlockingQueue)로 과부하에서 큐가 무한히 늘고, 캐시 풀은 (0, MAX_VALUE, 60s, SynchronousQueue)로 과부하에서 스레드가 무한히 는다.
    SynchronousQueue의 전달 순서
    OpenJDK 21의 비공정 모드는 이중 스택(LIFO)이라 가장 최근에 쉬러 온 스레드가 다음 작업을 받는다. 그래서 부하가 줄면 오래 쉰 스레드가 유지 시간 뒤 정리되어 캐시 풀이 줄어든다. 공정(FIFO) 모드에서는 이 효과가 사라질 수 있다.
    스레드 생성 실패
    addWorker는 Thread.start()의 OutOfMemoryError를 addWorkerFailed로 되돌리기만 하고 잡지 않으므로, 이 오류는 거절 정책을 거치지 않고 execute를 호출한 스레드로 간다.
    사용자 정의 풀
    유한한 최대 스레드와 유한 큐로 평소·급증·초과 구간을 나눈다. 동시에 받아들일 수 있는 작업은 최대 스레드 수 + 큐 용량이고, 그 이상은 거절 정책으로 간다.
    거절 정책
    AbortPolicy(기본, 예외), DiscardPolicy(버림), CallerRunsPolicy(호출자가 실행, 배압), DiscardOldestPolicy(가장 오래된 작업을 버리고 재시도)와 사용자 정의 핸들러가 있다.

    배포할 때마다 일부 작업이 사라진다는 장애를 만나면, 먼저 애플리케이션 종료 경로에 실행기 정리가 있는지 확인한다. 정리 코드가 없다면 프로세스가 바깥에서 강제로 내려가는 순간 큐의 작업은 모두 사라진다. 정리 코드가 있는데도 종료가 오래 걸리거나 끝나지 않는다면, 스레드 덤프에서 풀 스레드가 어디에 머물러 있는지 본다. RUNNABLE로 계산 루프를 돌고 있다면 인터럽트를 확인하지 않는 작업이고, 소켓 읽기에 머물러 있다면 타임아웃이 없는 입출력이다. 고쳐야 할 곳은 실행기 설정이 아니라 작업 코드다. 그리고 shutdownNow가 돌려준 작업 목록을 기록하지 않으면 "무엇이 사라졌는지"조차 알 수 없다는 점을 기억해 둔다.

    응답이 점점 느려지다 시간 초과가 나는데 CPU 사용률과 스레드 수는 평소와 같다면, 무한 큐에 작업이 쌓이고 있는 고정 풀을 의심한다. 반대로 순간적인 몰림 뒤에 메모리가 급증하고 스레드 수가 수천으로 치솟았다면 캐시 풀이나 상한 없는 실행기를 의심한다. 두 경우 모두 처방은 "어디에 상한을 둘 것인가"를 정하는 것이다. 이때 큐 용량은 클라이언트가 기다려 줄 수 있는 시간에서, 최대 스레드 수는 작업이 쓰는 가장 좁은 자원(데이터베이스 커넥션, 외부 API 동시 호출 한도, CPU 코어)에서 거꾸로 계산한다.

    거절 정책의 선택은 "이 작업이 실패하면 누가 알아야 하는가"에 달려 있다. 사용자의 요청을 직접 처리하는 작업이라면 AbortPolicy로 빨리 실패하고 호출자가 재시도하거나 오류를 돌려주게 하는 편이 낫다. 일괄 처리처럼 생산자의 속도를 늦춰도 되는 흐름이라면 CallerRunsPolicy가 별도 장치 없이 배압을 만든다. 단, 제출하는 스레드가 막혀서는 안 되는 스레드라면 피해야 한다. 버리는 정책은 결과가 정말 필요 없는 작업에만 쓰고, submit과 함께 쓰지 않으며, 거절 횟수만큼은 반드시 지표로 남긴다.

Executors.newFixedThreadPool(8)을 쓰는 서비스에 처리 속도보다 빠른 요청이 몇 시간째 계속 들어온다. 이 풀에서 일어날 일로 가장 정확한 것은? 스레드 수가 maximumPoolSize까지 늘어나 처리량이 올라간다. 큐가 가득 차면 RejectedExecutionException이 발생해 호출자가 알 수 있다. 60초 동안 쓰이지 않은 스레드가 정리되어 스레드 수가 줄어든다. 스레드는 8개로 유지되고 무한 큐에 작업이 계속 쌓여, 거절 없이 대기 시간과 힙 사용량만 늘어난다. 고정 풀은 (8, 8, 0ms, LinkedBlockingQueue)로 만들어지며 큐 용량이 Integer.MAX_VALUE다. 2단계의 offer가 사실상 항상 성공하므로 3단계(추가 스레드)와 거절에 도달하지 않는다. 최대도 8이라 늘어날 여지가 없고, 유지 시간 0은 작업자 수가 코어를 넘을 일이 없어 의미가 없다. 60초 정리는 캐시 풀의 특성이다. DiscardPolicy를 쓰는 포화된 풀에 Future f = pool.submit(task)로 작업을 제출했고, 이 작업이 거절되었다. 이후 다른 스레드가 f.get()(시간 제한 없음)을 호출하면 어떻게 되는가? 영원히 반환되지 않는다. 작업은 FutureTask로 감싸진 채 버려져 실행도 취소도 되지 않았으므로 완료 상태가 되지 않는다. 즉시 RejectedExecutionException이 던져진다. 즉시 CancellationException이 던져진다. null을 반환한다. submit은 작업을 FutureTask로 감싼 뒤 execute에 넘기고, 거절되면 핸들러가 그 FutureTask를 받는다. DiscardPolicy.rejectedExecution은 아무것도 하지 않으므로 FutureTask는 NEW 상태로 남고, isDone()은 계속 false다. 실험에서도 get(1, SECONDS)가 TimeoutException으로 끝났다. 예외가 나려면 AbortPolicy를 쓰거나, 핸들러에서 직접 cancel을 호출해야 한다. shutdown()이 작업을 실행 중인 스레드는 인터럽트하지 않고 큐에서 쉬고 있는 스레드만 인터럽트할 수 있는 이유는? 실행 중인 스레드는 RUNNABLE 상태라서 인터럽트가 전달되지 않기 때문이다. shutdown()이 스레드 상태를 검사해 WAITING인 스레드만 골라내기 때문이다. 각 Worker는 작업을 실행하는 동안 자기 락(AQS 기반, 재진입 불가)을 쥐고 있어서, interruptIdleWorkers의 tryLock()이 실행 중인 Worker에서는 실패하기 때문이다. 실행 중인 작업은 인터럽트 플래그를 무시하도록 JVM이 보호하기 때문이다. runWorker는 작업 하나를 실행하기 직전에 w.lock()을, 끝난 뒤 w.unlock()을 한다. interruptIdleWorkers는 w.tryLock()에 성공한 Worker만 인터럽트하므로 결과적으로 쉬는 스레드만 깨운다. RUNNABLE 스레드에도 인터럽트 플래그는 설정될 수 있고(shutdownNow가 그렇게 한다), shutdown은 스레드 상태를 검사하지 않으며, JVM이 인터럽트를 막는 장치도 없다.
    우아한 종료(graceful shutdown)
    새 작업을 받지 않고, 받은 작업은 가능한 한 끝까지 처리한 뒤, 정해진 시간이 지나면 남은 작업을 취소하고 자원을 정리하는 종료 방식.
    실행 상태(runState)
    ThreadPoolExecutor의 생명 주기 단계. RUNNING, SHUTDOWN, STOP, TIDYING, TERMINATED가 있으며 ctl의 위 3비트에 저장되고 앞으로만 진행한다.
    작업자(Worker)
    풀의 스레드 하나와 그 첫 작업을 묶은 내부 클래스. AQS로 만든 재진입 불가 락을 가지며, 작업 실행 중에만 그 락을 쥔다.
    작업 큐(work queue)
    스레드를 기다리는 작업을 담는 BlockingQueue. 종류와 용량이 풀이 과부하에서 큐를 늘릴지, 스레드를 늘릴지, 거절할지를 결정한다.
    직접 전달(direct handoff)
    내부 용량이 없는 SynchronousQueue를 통해 작업을 기다리는 스레드에 직접 넘기는 방식. 받을 스레드가 없으면 삽입이 실패한다.
    이중 스택·이중 큐(dual stack, dual queue)
    데이터 노드와 요청 노드 중 한 종류만 담고, 반대 종류의 연산이 오면 맨 앞 노드와 짝을 맞춰 걷어 내는 자료구조. SynchronousQueue는 이것으로 용량 0의 직접 전달을 구현한다.
    유지 시간(keepAliveTime)
    작업자 수가 코어 수보다 많을 때, 큐를 기다리는 스레드가 새 작업 없이 버틸 수 있는 최대 시간. 지나면 스레드가 종료된다.
    거절 정책(RejectedExecutionHandler)
    풀이 종료되었거나 포화되어 받을 수 없는 작업을 처리하는 핸들러. 기본은 예외를 던지는 AbortPolicy다.
    배압(back-pressure)
    하류의 처리 능력이 상류의 공급 속도를 제한하도록 되먹이는 것. CallerRunsPolicy는 제출 스레드가 직접 작업을 실행하게 해 이 효과를 낸다.
    스레드 기아 교착(thread starvation deadlock)
    풀의 모든 스레드가 같은 풀의 큐에 있는 작업의 결과를 기다려, 그 작업을 실행할 스레드가 남지 않아 영원히 진행하지 못하는 상태.
