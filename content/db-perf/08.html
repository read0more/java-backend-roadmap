    이 회차의 질문: 인덱스로 찾아 놓고 버리는 행

    07회의 상품 목록 쿼리를 다시 떠올려 보자. 첫 번째 해결 방안인 (category_id, created_at) 인덱스로 카테고리 7의 상품을 최신순으로 읽을 때, 26개 항목을 읽어서 20개를 돌려주고 6개를 버렸다. 버린 6개는 상태가 HIDDEN이나 SOLD_OUT인 상품이었는데, 인덱스에 상태가 없어서 클러스터형 인덱스까지 찾아가 행을 가져온 뒤에야 버릴 수 있었다. 6개면 아무 일도 아니다. 그런데 화면에 가격대 필터가 붙어 일치하는 상품이 드물어지면, 이 "찾아가서 확인하고 버리는" 일이 수천 번으로 불어난다. 06회에서 본 대로 커버링이 아닌 세컨더리 인덱스 조회의 비용은 대략 "읽은 인덱스 항목 수 × 클러스터형 인덱스 탐색 한 번"이고, 그 탐색 가운데 버려질 행을 위한 것은 순수한 낭비다.

    이 회차의 세 기법은 이 낭비를 서로 다른 방향에서 줄인다. 인덱스 컨디션 푸시다운(Index Condition Pushdown, ICP)은 버릴 항목을 클러스터형 인덱스에 가기 전에 인덱스 항목만 보고 버린다. 커버링 인덱스(covering index)는 쿼리에 필요한 열을 모두 인덱스에 담아 클러스터형 인덱스 조회 자체를 없앤다. 인덱스 스킵 스캔(index skip scan)은 방향이 조금 다르다. 선두 열에 조건이 없어 구간을 아예 만들 수 없던 복합 인덱스를, 선두 열의 값마다 작은 구간으로 나누어 쓸 수 있게 한다. 세 기법 모두 "세컨더리 인덱스 항목에는 인덱스 열과 기본 키만 있다"는 06회의 사실 하나에서 출발한다.

    순서는 이렇다. 먼저 조건이 원래 어디서 평가되는지를 서버와 스토리지 엔진의 경계에서 보고, ICP가 그 경계를 어떻게 옮기는지 8.4 소스를 따라 내려간다. 다음으로 ICP를 실행 계획에서 확인하고 효과를 재는 법, 그리고 07회의 튜닝 결과에 가격 조건을 더했을 때 ICP를 적용하려다 만나는 제약을 실제 쿼리로 따라간다. 이어서 커버링 인덱스를 ICP와 나란히 놓고 지연 조인으로 응용하며, 큰 데이터에서 무엇을 어떻게 재야 하는지 정리한다. 마지막으로 스킵 스캔의 알고리즘과 비용, 쓰이지 못하는 경우를 본다.

    설명의 기준은 MySQL 8.4와 InnoDB다. 소스 코드로 확인한 문장에는 "8.4 소스 기준"이라고 적는다. B+Tree와 클러스터형·세컨더리 인덱스의 구조는 05·06회, EXPLAIN과 EXPLAIN ANALYZE는 02·03회, filesort와 조기 종료는 07회에서 다뤘으므로 필요한 만큼만 상기한다. 인덱스 머지, MRR, 함수 기반 인덱스, 내림차순 인덱스의 자세한 동작, 옵티마이저 힌트의 체계는 09회, 통계와 히스토그램은 10회, 조인은 11회, GROUP BY의 루스 인덱스 스캔과 페이징은 12회의 몫이다. 실행 시간은 하드웨어와 버퍼 풀 상태에 따라 달라지므로 비교의 근거로 쓰지 않는다. 대신 데이터 생성 규칙에서 계산으로 정해지는 항목 수, 조회 수, 핸들러 카운터를 적는다. 이 회차의 실행 계획 출력과 핸들러 카운터는 MySQL 8.4.13에서 실제로 실행한 것이다. 출력에 함께 찍히는 actual time, cost, 예상 rows는 실행 환경과 통계에 따라 달라지는 값이고, 데이터로 정해지는 것은 실제 행 수(actual의 rows)다.

    출발점: 07회 끝의 product 테이블

    이 회차의 실습은 07회에서 만든 product 테이블 100만 행을 그대로 쓴다. 07회를 마친 시점의 인덱스는 기본 키와 두 개의 세컨더리 인덱스다.

    -- 07회를 마친 상태 (SHOW CREATE TABLE의 요지)
CREATE TABLE product (
  product_id  BIGINT       NOT NULL,
  category_id INT          NOT NULL,
  name        VARCHAR(100) NOT NULL,
  price       INT          NOT NULL,
  status      VARCHAR(20)  NOT NULL,
  created_at  DATETIME     NOT NULL,
  PRIMARY KEY (product_id),
  KEY idx_category_created (category_id, created_at),
  KEY idx_category_status_created (category_id, status, created_at)
) ENGINE = InnoDB;

    모든 값은 행 번호 n(1~1,000,000)에서 계산된다. 이 회차에서 쓰는 규칙만 다시 적는다. category_id는 n mod 100 + 1이라 카테고리 7은 n = 100k + 6(k = 0~9,999)인 1만 행이다. price는 (n mod 997 + 1) × 100원이다. status는 (n div 100) mod 10이 0~7이면 ON_SALE, 8이면 SOLD_OUT, 9이면 HIDDEN이다. created_at은 2023-01-01 00:00:00에 n분을 더한 값이고, 2023-01-01은 일요일이다. 카테고리 7의 행은 100분 간격으로 등록된 셈이고, product_id와 created_at은 같은 순서로 증가한다.

    06회에서 본 대로 InnoDB는 세컨더리 인덱스 항목 뒤에 기본 키를 덧붙인다. 그래서 두 세컨더리 인덱스의 리프 항목은 실제로 다음과 같은 모양이다. 이 그림이 이 회차 전체의 바탕이다. 인덱스 항목만 보고 알 수 있는 것은 이 열들뿐이고, name과 price는 클러스터형 인덱스에 가야만 알 수 있다.

    ICP 1: 조건은 원래 어디서 평가되는가

    새 요구가 들어왔다고 하자. 운영팀이 "카테고리 7에서 주말에 등록된 상품"의 목록을 보고 싶어 한다. MySQL의 DAYOFWEEK()는 일요일을 1, 토요일을 7로 돌려주므로 쿼리는 다음과 같다.

    SELECT product_id, name, price
FROM product
WHERE category_id = 7
  AND DAYOFWEEK(created_at) IN (1, 7);

    결과는 데이터에서 정확히 계산된다. 카테고리 7의 1만 행 가운데 등록 시각이 토요일이나 일요일인 행은 2,866개다. 이 쿼리에 쓸 수 있는 인덱스는 category_id로 시작하는 두 인덱스이고, 둘 다 created_at을 담고 있다. 하지만 created_at 조건은 구간을 좁히는 데 쓸 수 없다. 02·04회에서 본 대로 열을 함수로 감싸면 "이 값부터 저 값까지"라는 연속 구간이 만들어지지 않는다. 주말은 일주일마다 한 번씩 끊겨 나타나는 조각들이기 때문이다. 그래서 인덱스로 좁힐 수 있는 것은 category_id = 7까지이고, 카테고리 7의 항목 1만 개를 모두 훑어야 한다. 아래 설명은 idx_category_created가 선택되었다고 보고 진행한다. 다른 인덱스가 선택되어도 created_at을 담고 있다는 점이 같으므로 이야기는 달라지지 않는다.

    이제 질문은 "1만 개의 항목 각각에 대해 주말 조건을 누가, 언제 확인하는가"다. 01회에서 본 대로 MySQL은 SQL을 해석하고 실행 계획을 세우는 서버 계층과 데이터를 실제로 저장하고 읽는 스토리지 엔진 계층으로 나뉘고, 둘 사이는 핸들러 인터페이스(handler interface)라는 함수 호출 규약으로 이어진다. 서버의 실행기는 "이 인덱스에서 이 키로 첫 행을 달라"(index_read_map), "같은 키의 다음 행을 달라"(index_next_same)처럼 한 번에 한 행씩 요청하고, 엔진은 요청할 때마다 행 하나를 서버의 행 형식으로 만들어 버퍼에 채워 돌려준다. 엔진은 WHERE 절을 모른다. 알고 있는 것은 "category_id가 7인 구간을 읽으라"는 키뿐이다.

    ICP가 없다면 항목 하나에 대해 일어나는 일은 이렇다.

    이 경로로 1만 항목을 처리하면 클러스터형 인덱스 조회가 1만 번 일어나고, 그중 7,134번은 평일 행을 가져와 버리는 데 쓰인다. 07회에서 계산한 대로 카테고리 7의 행은 클러스터형 인덱스의 모든 리프 페이지에 하나 이상씩 들어 있으므로, 이 쿼리는 테이블 전체의 리프 페이지를 버퍼 풀로 불러들인다. 그런데 5단계의 판단에 필요한 정보는 created_at 하나이고, created_at은 1단계에서 읽은 인덱스 항목 안에 이미 있었다. 2단계의 조회는 name과 price를 얻기 위한 것인데, 그 둘은 주말 행에만 필요하다. 순서가 거꾸로 된 것이다. 조회 전에 확인할 수 있는 조건을 조회 뒤에 확인하고 있다.

    ICP를 끈 상태(SET optimizer_switch = 'index_condition_pushdown=off')에서 이 쿼리의 실행 계획은 다음과 같다. EXPLAIN은 주요 열만 옮겼다.

    EXPLAIN:     type: ref   key: idx_category_created   key_len: 4   ref: const   rows: 18798
             Extra: Using where

EXPLAIN ANALYZE:
-> Filter: (dayofweek(product.created_at) in (1,7))  (cost=15243 rows=18798) (actual time=11.4..78.7 rows=2866 loops=1)
    -> Index lookup on product using idx_category_created (category_id=7)  (cost=15243 rows=18798) (actual time=11.3..76.2 rows=10000 loops=1)

    Index lookup 노드가 1만 행을 위로 올렸고 Filter 노드가 2,866행만 통과시켰다. Index lookup이 올린 "행"은 클러스터형 인덱스에서 가져온 완성된 행이다. 노드 사이의 화살표 하나하나가 핸들러 경계를 넘는 호출이고, 그 아래에는 클러스터형 인덱스 조회가 하나씩 붙어 있다.

    ICP 2: 조건을 엔진 안으로 내려보내는 구조

    MySQL 매뉴얼은 ICP를 이렇게 설명한다. 인덱스로 테이블의 행을 읽을 때, WHERE 조건 가운데 인덱스의 열만으로 평가할 수 있는 부분이 있으면 서버가 그 부분을 스토리지 엔진에 넘기고, 엔진은 인덱스 항목으로 그 조건을 평가해 만족할 때만 테이블의 행을 읽는다. 매뉴얼은 그 효과를 엔진이 기본 테이블에 접근하는 횟수와 서버가 엔진에 접근하는 횟수를 함께 줄이는 것으로 정리한다. 앞의 다섯 단계에 대응시키면 5단계의 조건 평가를 1단계와 2단계 사이로 끌어올리는 것이다.

    이제 클러스터형 인덱스 조회는 2,866번으로 줄어든다. 인덱스 항목은 여전히 1만 개를 읽는다는 점에 주목하자. ICP는 읽는 인덱스 구간을 좁히는 기술이 아니다. 같은 구간을 읽되, 그 구간 안에서 버릴 항목이 클러스터형 인덱스까지 가는 길을 끊는 기술이다.

    위아래 두 단으로 같은 인덱스 항목 열이 처리되는 모습을 비교한다. 위쪽은 모든 항목이 클러스터형 인덱스를 거쳐 서버로 올라간 뒤 걸러지고, 아래쪽은 엔진 안에서 먼저 걸러져 일치 항목만 클러스터형 인덱스와 서버로 간다. 가로로 긴 그림을 위아래 두 단으로 나눈다. 각 단은 왼쪽부터 세 개의 세로 영역으로 나뉜다: 영역 라벨 "세컨더리 인덱스", "클러스터형 인덱스", "서버 실행기". 위 단 제목 "ICP 없음": 세컨더리 인덱스 영역에 작은 네모 10개가 세로로 쌓여 있고, 10개 모두에서 화살표가 클러스터형 인덱스 영역으로 갔다가 서버 실행기 영역으로 이어진다. 서버 실행기 영역에서 7개 화살표 끝에 회색 X 표시, 3개는 초록 체크 표시. 위 단 하단 라벨 "조회 10번, 7번은 버림". 아래 단 제목 "ICP 있음": 세컨더리 인덱스 영역 안에 작은 깔때기 아이콘과 라벨 "조건 평가". 10개 네모 중 7개는 깔때기에서 회색 X로 끝나고 3개만 화살표가 클러스터형 인덱스를 거쳐 서버 실행기로 간다. 아래 단 하단 라벨 "조회 3번". 평면 스타일, 흰 배경, 세 영역은 옅은 색으로 구분. ICP는 같은 인덱스 항목을 읽되, 조건에 맞지 않는 항목이 클러스터형 인덱스와 서버로 가는 길을 엔진 안에서 끊는다.

    서버 쪽: 무엇을 떼어 넘기는가

    8.4 소스 기준으로 ICP는 실행 계획을 다듬는 단계(make_join_readinfo)에서 결정된다. 접근 방법과 인덱스가 정해진 뒤, 서버는 테이블의 조건에서 "그 인덱스의 열만 참조하는 부분"을 떼어 낸다(make_cond_for_index). 그 부분을 핸들러의 idx_cond_push(keyno, idx_cond)로 엔진에 넘기면, 엔진은 자기가 맡지 못하는 나머지를 돌려준다. 서버는 원래 조건에서 인덱스로 처리할 부분을 뺀 나머지와 엔진이 돌려준 나머지를 합쳐 테이블 조건으로 남긴다. 이 판단의 대상은 선택된 인덱스 하나라는 점이 중요하다. 같은 테이블에 created_at을 담은 다른 인덱스가 있어도, 실제로 읽는 인덱스에 그 열이 없으면 조건은 내려가지 않는다.

    8.4 소스의 QEP_TAB::push_index_cond()는 ICP를 시도하는 조건을 주석으로 나열한다. 테이블에 조건이 있을 것, 스토리지 엔진이 ICP를 지원할 것, optimizer_switch의 index_condition_pushdown이 켜져 있고 NO_ICP 힌트로 꺼지지 않았을 것, 다중 테이블 UPDATE나 DELETE가 아닐 것, 보호 조건(guarded condition)을 가진 서브쿼리의 일부가 아닐 것, 접근 방법이 const나 system이 아닐 것, 인덱스가 클러스터형 인덱스가 아닐 것, 가상 생성 열 위의 인덱스가 아닐 것이다. 그리고 이 목록과 별도로 함수 첫머리에서 역방향 접근(reversed_access)이면 곧바로 돌아간다. 이 마지막 줄에는 "역사적인 제약이니 풀어야 한다"는 뜻의 할 일 주석이 붙어 있는데, 뒤의 적용 예제에서 이 줄이 결과를 바꾼다.

    매뉴얼은 사용자 관점에서 같은 범위를 정리한다. ICP는 행 전체를 읽어야 하는 range, ref, eq_ref, ref_or_null 접근에 쓰이고, InnoDB와 MyISAM(파티션 테이블 포함)이 지원한다. InnoDB에서는 세컨더리 인덱스에만 쓰인다. 클러스터형 인덱스는 레코드 전체가 이미 버퍼로 읽혀 있으므로 ICP로 줄일 I/O가 없기 때문이다. 가상 생성 열에 만든 세컨더리 인덱스에는 쓰이지 않는다. 서브쿼리를 참조하는 조건, 저장 함수를 참조하는 조건(스토리지 엔진이 저장 함수를 호출할 수 없다), 트리거된 조건은 내려보낼 수 없고, 시스템 변수를 참조하는 파생 테이블로도 조건을 내려보낼 수 없다.

    엔진 쪽: InnoDB는 조건을 어떻게 평가하는가

    "엔진이 조건을 평가한다"는 말을 엔진이 SQL을 이해한다는 뜻으로 받아들이면 안 된다. 8.4 소스 기준으로 InnoDB는 넘겨받은 조건을 질의 단위 구조체(row_prebuilt_t)의 idx_cond에 표시해 두고, 인덱스 레코드를 하나 읽을 때마다 row_search_idx_cond_check()를 부른다. 이 함수는 조건에 필요한 인덱스 열만 서버의 행 형식으로 옮긴 뒤 innobase_index_cond()를 통해 서버 쪽의 평가 코드를 호출한다. 조건식 자체는 여전히 서버가 만든 식 객체이고, 평가도 서버의 코드가 한다. 엔진이 바꾼 것은 그 코드를 부르는 시점, 곧 클러스터형 인덱스에 가기 전이라는 점이다. 그래서 내려갈 수 있는 조건에는 엔진의 레코드 탐색 루프 안에서 평가할 수 있어야 한다는 제약이 붙는다. 매뉴얼이 저장 함수를 참조하는 조건을 제외하면서 드는 이유도 스토리지 엔진이 저장 함수를 호출할 수 없다는 것이다.

    평가 결과는 세 가지 중 하나다. MySQL의 my_icp.h는 이를 ICP_RESULT 열거형으로 정의한다.

    첫 줄이 ICP의 이득이 생기는 곳이다. 8.4 소스의 row_search_mvcc()에는 커서 이동 직전에 이런 취지의 주석이 있다. 정방향으로 읽으면서 ICP를 쓰는 경우, 조건이 맞지 않는 동안에는 클러스터형 인덱스를 볼 필요도 행을 MySQL에 돌려줄 필요도 없으므로 커서를 다시 위치시키는 일을 피할 수 있고, 그래서 세컨더리 인덱스 전체를 미니 트랜잭션(mini-transaction) 하나 안에서 훑을 수도 있다. 리프 페이지를 넘어갈 때 앞 페이지의 고정은 풀리므로 커서가 놓인 리프 페이지 하나만 고정된 채로 남는다. 같은 주석은 역방향으로 읽을 때는 B+Tree 페이지를 바꿀 때마다 미니 트랜잭션을 커밋하고 다시 시작한다고 적는다. 불일치 항목이 핸들러 경계를 넘지 않는다는 것은 함수 호출 몇 번을 아끼는 데서 그치지 않는다. 주석이 말하듯 행을 돌려준 뒤 커서를 다시 위치시키는 일도 함께 피한다.

    InnoDB는 이 세 결과를 셀 수 있는 모니터 카운터도 갖고 있다. 8.4 소스의 카운터 정의에 icp 모듈과 네 카운터가 있다. icp_attempts는 푸시다운 조건 검사를 시도한 횟수, icp_no_match는 불일치, icp_out_of_range는 구간 이탈, icp_match는 일치한 횟수다. 검사 함수는 평가 전에 시도 횟수를 먼저 올리고, 평가 결과에 따라 나머지 셋 중 하나를 올린다. 네 카운터는 기본으로 꺼져 있어서 켜야 센다. 다음 절에서 이 카운터로 ICP의 효과를 잰다.

    ICP 도입: 계획에서 확인하고 효과를 재는 법

    ICP는 기본으로 켜져 있으므로 "도입"이라고 해서 따로 설정할 것은 없다. 실무에서 도입이란 두 가지 일이다. 내 쿼리에 ICP가 실제로 걸렸는지 확인하는 일, 그리고 그것이 얼마나 일을 줄였는지 재는 일이다. 앞의 주말 쿼리를 ICP가 켜진 상태로 다시 보자.

    EXPLAIN:     type: ref   key: idx_category_created   key_len: 4   ref: const   rows: 18798
             Extra: Using index condition

EXPLAIN ANALYZE:
-> Index lookup on product using idx_category_created (category_id=7), with index condition: (dayofweek(product.created_at) in (1,7))  (cost=5221 rows=18798) (actual time=0.453..4.83 rows=2866 loops=1)

    세 군데가 달라졌다. 첫째, Extra가 Using where에서 Using index condition으로 바뀌었다. 매뉴얼은 ICP가 쓰이면 Extra에 이 문구가 나타나고, 행 전체를 읽어야 하므로 Using index는 나타나지 않는다고 설명한다. 서버에 남은 조건이 있으면 둘이 함께 Using index condition; Using where로 나온다. 둘째, TREE 형식에서 Filter 노드가 사라지고 인덱스 접근 줄 끝에 with index condition:과 내려간 조건이 붙었다. 8.4 소스의 EXPLAIN 출력 코드는 인덱스 접근을 설명하는 문자열을 "Index 또는 Covering index, 접근 종류, 테이블, 인덱스 이름, 조회 조건, 구간, (reverse), with index condition" 순서로 조립한다. 셋째, Index lookup 노드의 실제 행 수가 10000에서 2866으로 줄었다.

    key_len은 4 그대로다. key_len은 인덱스의 어느 열까지를 써서 읽을 구간을 정했는가를 보여 주는 값이다. ICP로 검사한 created_at은 구간을 정하는 데 쓰이지 않았으므로 key_len에 들어가지 않는다. 04회에서 key_len으로 "범위 조건까지 구간에 썼는가"를 판정했던 것과 같은 원리다. ICP가 걸렸는지는 key_len이 아니라 Extra와 TREE의 with index condition으로 판단한다.

    옵티마이저 트레이스에서도 확인할 수 있다. 8.4 소스는 계획 다듬기 단계를 refine_plan이라는 배열로 기록하고, ICP를 적용하면 테이블마다 pushed_index_condition에 내려간 조건을, table_condition_attached에 서버에 남은 조건을 남긴다. MySQL 8.4.13에서 주말 쿼리의 트레이스를 보면 앞의 것에 (dayofweek(`product`.`created_at`) in (1,7))이 들어가고 뒤의 것은 null이다. 조건이 길고 복잡해서 무엇이 내려갔는지 Extra만으로 알 수 없을 때 이 두 값이 가장 정확한 답이다.

    켜고 끄기

    ICP의 효과를 비교하려면 끄는 법을 알아야 한다. 세션 전체에서는 optimizer_switch로, 문장 하나에서는 NO_ICP 힌트로 끈다. 매뉴얼에 따르면 NO_ICP는 테이블이나 인덱스 단위로 지정하는 인덱스 수준 힌트이고, ICP는 기본으로 후보 전략이므로 켜는 힌트는 따로 없다. 힌트의 문법과 적용 범위는 09회에서 정리한다.

    -- 세션 전체에서 끄고 다시 켜기
SET optimizer_switch = 'index_condition_pushdown=off';
SET optimizer_switch = 'index_condition_pushdown=on';

-- 이 문장의 product 테이블에서만 끄기
SELECT /*+ NO_ICP(product) */ product_id, name, price
FROM product
WHERE category_id = 7
  AND DAYOFWEEK(created_at) IN (1, 7);

-- 특정 인덱스에서만 끄기
SELECT /*+ NO_ICP(product idx_category_created) */ product_id, name, price
FROM product
WHERE category_id = 7
  AND DAYOFWEEK(created_at) IN (1, 7);

    효과를 숫자로 재기: 각 도구가 세는 것

    ICP의 효과를 잴 때 가장 흔한 실수는 도구가 무엇을 세는지 확인하지 않는 것이다. ICP가 걸러 낸 항목은 핸들러 경계를 넘지 않으므로, 경계 위쪽에서 세는 도구에는 아예 보이지 않는다. 주말 쿼리 하나를 ICP를 끄고 켠 상태로 실행했을 때 각 도구가 보여 주는 값을 계산해 보자. 핸들러 카운터는 07회에서 본 대로 정방향 ref 읽기의 첫 요청이 Handler_read_key를, 이후의 요청이 Handler_read_next를 하나씩 올리고, 마지막에 "더 없음"을 확인하는 요청이 한 번 더 있다. 표의 EXPLAIN ANALYZE 행 수와 핸들러 카운터는 MySQL 8.4.13에서 FLUSH STATUS 뒤 쿼리를 실행하고 SHOW SESSION STATUS로 잰 값과 같다. icp 카운터는 켜려면 SET GLOBAL이 필요하고 서버 전체에서 누적되는 값이라, 다른 작업이 함께 도는 실습 서버에서는 재지 않았다. 그 줄과 엔진 내부의 두 줄은 계산값이다.

    ICP를 켜면 EXPLAIN ANALYZE의 행 수도, 핸들러 카운터도 2,866으로 줄어든다. 이 숫자만 보면 "인덱스를 2,866개만 읽었다"고 착각하기 쉽다. 실제로는 엔진이 1만 개의 항목을 모두 확인했고, 그중 7,134개를 핸들러 경계 아래에서 버렸다. 그 7,134번의 확인은 INNODB_METRICS의 icp 카운터에만 남는다. 01회에서 본 슬로 쿼리 로그의 Rows_examined도 서버 계층이 검사한 행 수이므로 같은 사정이다. 인덱스에서 읽은 항목 수 자체를 알고 싶다면, 계산으로 추정하거나 icp 카운터를 함께 봐야 한다.

    -- icp 모듈의 카운터를 켠다 (서버 전체, 재시작하면 기본 상태로 돌아간다)
SET GLOBAL innodb_monitor_enable = 'module_icp';

-- 쿼리 실행 전후의 값을 비교한다
SELECT NAME, COUNT
FROM information_schema.INNODB_METRICS
WHERE SUBSYSTEM = 'icp';

    매뉴얼의 INNODB_METRICS 절에 따르면 카운터는 모듈 이름(module_icp)이나 와일드카드로 켜고 끌 수 있고, 켜는 설정만 설정 파일에 둘 수 있으며, 카운터의 켜짐 상태는 재시작하면 기본값으로 돌아간다. 이 카운터는 서버 전체에서 누적되므로 다른 쿼리가 함께 돌고 있는 운영 서버에서는 한 쿼리의 효과를 분리하기 어렵다. 실습 서버에서 쿼리 하나만 실행하고 전후 차이를 보는 것이 정확하다.

    ICP와 잠금, ICP와 MVCC

    ICP가 잠금 범위도 줄여 준다고 생각하기 쉽지만, 세컨더리 인덱스에 대해서는 그렇지 않다. 8.4 소스의 row_search_mvcc()에서 SELECT ... FOR UPDATE 같은 잠금 읽기는 레코드에 잠금을 거는 단계(sel_set_rec_lock)가 ICP 검사보다 앞에 있다. 즉 세컨더리 인덱스 레코드에는 먼저 잠금이 걸리고, 그다음에 조건을 확인한다. 불일치로 판정되면 try_unlock()을 부르는데, 그 선언의 주석은 이 함수가 READ COMMITTED나 READ UNCOMMITTED가 아니면 아무 일도 하지 않는다고 명시한다. 기본 격리 수준인 REPEATABLE READ에서는 ICP가 버린 세컨더리 인덱스 레코드의 잠금도 그대로 남는다. 다만 불일치 항목은 클러스터형 인덱스로 가지 않으므로 그 행의 클러스터형 레코드에는 잠금을 걸 기회가 없다. 잠금 범위를 결정하는 것은 어디까지나 인덱스에서 읽는 구간이고, 그것을 좁히는 수단은 ICP가 아니라 구간을 좁히는 인덱스 설계다.

    잠금 없는 일관된 읽기에서는 ICP가 한 가지 일을 더 한다. 06회에서 본 대로 세컨더리 인덱스 레코드에는 트랜잭션 ID가 없어서, 페이지가 읽기 뷰보다 새로운 트랜잭션에 의해 바뀌었다면 클러스터형 인덱스에서 행의 버전을 확인해야 한다. 8.4 소스의 해당 분기에는 "클러스터형 인덱스를 봐야 하지만, 잠금 없는 읽기이므로 세컨더리 인덱스 항목이 조건에 맞지 않으면 클러스터형 인덱스 조회를 건너뛸 수 있다"는 주석과 함께 ICP 검사가 먼저 놓여 있다. 쓰기가 몰리는 테이블에서 커버링 인덱스는 이런 페이지를 만나면 클러스터형 인덱스를 방문해야 하지만(06회), ICP가 걸린 쿼리는 불일치 항목에 대해서는 그 방문까지 피한다.

    ICP가 일하는 자리: 구간을 좁히지 못하는 인덱스 열

    ICP가 이득을 주는 조건에는 공통점이 있다. 조건의 열이 선택된 인덱스 안에 있지만, 그 인덱스의 구간을 좁히는 데는 쓰이지 못한다는 점이다. 인덱스 (a, b, c)를 놓고 구간을 좁히는 조건과 ICP로만 확인할 수 있는 조건을 나눠 보면 다음과 같다.

    인덱스 (a, b, c) + 기본 키

WHERE a = 1 AND b = 2 AND c > 5      a, b, c 모두 구간에 사용 (ICP로 거를 것이 없다)
WHERE a = 1 AND b > 2 AND c = 5      a, b는 구간에 사용, c는 범위 열 b 뒤라서 ICP로 확인
WHERE a = 1 AND c = 5                a만 구간에 사용, b를 건너뛴 c는 ICP로 확인
WHERE a = 1 AND MONTH(b) = 12        a만 구간에 사용, 함수로 감싼 b는 ICP로 확인
WHERE a = 1 AND b LIKE '%xyz%'       a만 구간에 사용, 앞이 와일드카드인 b는 ICP로 확인
WHERE a = 1 AND d = 5                a만 구간에 사용, 인덱스에 없는 d는 행을 가져온 뒤 서버가 확인

    두 번째 줄이 가장 흔한 경우다. 04회에서 본 대로 범위 조건이 걸린 열 뒤의 열은 구간을 좁히지 못한다. b가 2보다 큰 항목들 안에서 c는 b 값마다 따로 정렬되어 있기 때문이다. 하지만 c의 값은 각 항목 안에 들어 있으므로 확인은 할 수 있다. 04회의 (ordered_at, status) 인덱스에서 status 조건이 ICP로 걸러진 것이 바로 이 경우였다. 다섯 번째 줄은 매뉴얼이 ICP를 설명할 때 드는 예와 같은 구조다. 매뉴얼의 예는 INDEX (zipcode, lastname, firstname)이 있는 people 테이블에서 zipcode='95054' AND lastname LIKE '%etrunia%' AND address LIKE '%Main Street%'를 찾는데, zipcode로 구간을 정하고, lastname 조건은 ICP로 인덱스 항목에서 확인하고, 인덱스에 없는 address 조건은 행을 읽은 뒤에 확인한다.

    이 표에서 인덱스 설계의 원칙이 하나 나온다. 구간을 좁히는 열을 앞에 두는 것이 먼저이고, 구간을 좁히지 못하지만 자주 걸리는 거르기 조건의 열은 인덱스 뒤쪽에 덧붙여 ICP의 대상으로 만들 수 있다. 마지막 줄의 d를 인덱스 끝에 붙이면 d 조건이 클러스터형 조회 전에 확인된다. 대가는 06회에서 본 그대로다. 인덱스 항목이 넓어져 페이지당 항목 수가 줄고, d를 바꾸는 UPDATE가 이 인덱스에도 쓰기를 일으킨다.

    그리고 ICP는 차선책이라는 점을 기억하자. 조건을 구간으로 바꿀 수 있다면 그쪽이 낫다. 예를 들어 MONTH(created_at) = 12가 실제로 "2023년 12월"이라는 뜻이라면 created_at >= '2023-12-01' AND created_at < '2024-01-01'로 고쳐 쓰는 순간 created_at이 구간에 쓰이고, 읽는 항목 자체가 줄어든다. ICP는 같은 구간을 다 읽고 조회만 줄이지만, 구간 조건은 읽기와 조회를 함께 줄인다. 식을 구간으로 바꿀 수 없을 때는 09회의 함수 기반 인덱스가 다른 선택지가 된다.

    ICP의 이득이 작은 경우도 알아 두자. 내려간 조건이 대부분의 항목을 통과시키면 걸러지는 조회가 없으니 평가 비용만 더해진다. 인덱스가 이미 커버링이면 줄일 조회가 처음부터 없다. 이 마지막 경우는 실행 계획 결정 코드가 아예 ICP를 시도하지 않는데, 커버링 인덱스 절에서 소스와 함께 본다.

    ICP 적용 예제: 07회의 튜닝 결과에 가격 조건이 붙으면

    이제 07회의 실전 튜닝에 ICP를 적용해 보자. 07회는 "카테고리 7의 판매 중 상품을 최신순으로 20개"라는 쿼리를 idx_category_status_created (category_id, status, created_at)로 정확히 20개 항목만 읽게 만드는 데서 끝났다. 그런데 상품 목록 화면에는 가격대 필터가 있다. 사용자가 5만 원에서 5만 900원 사이를 고르면 쿼리는 이렇게 된다.

    SELECT product_id, name, price, created_at
FROM product
WHERE category_id = 7
  AND status = 'ON_SALE'
  AND price BETWEEN 50000 AND 50900
ORDER BY created_at DESC
LIMIT 20;

    결과는 계산으로 정해진다. 카테고리 7의 판매 중 상품 8,000개 가운데 가격이 이 범위에 드는 것은 81개다. 최신순으로 20개를 고르면 첫 행은 product_id 997,506, 스무 번째 행은 763,206이다. 07회의 표에서 본 대로 가격 규칙은 등록 순서와 얽혀 있지 않으므로 일치하는 행은 판매 중 상품 사이에 고르게 흩어져 있다.

    단계 0: 07회의 인덱스 그대로

    EXPLAIN:     type: ref   key: idx_category_status_created   key_len: 86   ref: const,const   rows: 14948
             Extra: Using where; Backward index scan

EXPLAIN ANALYZE:
-> Limit: 20 row(s)  (cost=3724 rows=20) (actual time=0.427..3.14 rows=20 loops=1)
    -> Filter: (product.price between 50000 and 50900)  (cost=3724 rows=1661) (actual time=0.416..3.13 rows=20 loops=1)
        -> Index lookup on product using idx_category_status_created (category_id=7, status='ON_SALE') (reverse)  (cost=3724 rows=14948) (actual time=0.402..3.03 rows=1894 loops=1)

    (7, 'ON_SALE') 구간을 끝에서부터 거꾸로 읽으며 항목마다 클러스터형 인덱스에서 행을 가져와 가격을 확인한다. 스무 번째 일치 행을 만나기까지 1,894개 항목을 읽고, 클러스터형 인덱스 조회도 1,894번 일어나며, 그중 1,874번은 가격이 맞지 않아 버려진다. 핸들러 카운터로는 Handler_read_key 1, Handler_read_prev 1,893이다. 07회의 첫 번째 인덱스 (category_id, created_at)로 같은 쿼리를 처리하면 상태도 행에서 확인해야 하므로 2,368개를 읽었다(FORCE INDEX (idx_category_created)로 실행하면 역방향 인덱스 노드가 rows=2368을 올린다). 상태 열을 인덱스에 넣은 덕분에 474번의 조회가 줄었지만, 남은 1,874번의 헛조회는 가격이 인덱스에 없어서 생긴다.

    단계 1: 인덱스 끝에 price를 붙인다 — 그리고 아무것도 바뀌지 않는다

    앞 절의 원칙을 그대로 적용하면 답은 분명해 보인다. price는 범위 조건이라 created_at 앞에 두면 정렬이 깨지므로(07회), 정렬 열 뒤, 인덱스의 끝에 붙인다. 구간을 좁히지는 못하지만 ICP로 클러스터형 조회 전에 가격을 확인할 수 있을 것이다.

    ALTER TABLE product
  ADD INDEX idx_cat_status_created_price (category_id, status, created_at, price);

    그런데 EXPLAIN을 보면 기대한 Using index condition이 없다. MySQL 8.4.13에서 실행해 보면 옵티마이저는 새 인덱스가 있어도 기존 idx_category_status_created를 그대로 고른다. FORCE INDEX (idx_cat_status_created_price)로 새 인덱스를 쓰게 하거나 기존 인덱스를 옵티마이저에게서 감춰 새 인덱스가 선택되게 해도 결과는 같다. Extra는 여전히 Using where; Backward index scan이고, EXPLAIN ANALYZE의 인덱스 조회 노드(Index lookup on product using idx_cat_status_created_price (category_id=7, status='ON_SALE') (reverse))는 여전히 1,894행을 올리며, Filter가 그 위에서 가격을 확인한다. 클러스터형 조회도 그대로 1,894번이다.

    원인은 앞에서 본 push_index_cond()의 첫머리에 있다. 8.4 소스는 역방향 접근이면 ICP를 시도하지 않고 돌아간다. 역방향 접근 표시는 ORDER BY를 처리하는 test_if_skip_sort_order()가 ref 접근을 역순으로 바꿀 때 붙이는데, 그 자리의 주석은 "현재의 역방향 ref 이터레이터 구현이 ICP와 잘 맞지 않고 실행 시간을 늘릴 수 있다"고 이유를 밝힌다. 07회에서 본 대로 역방향 ref 읽기 코드는 푸시다운 조건이 없다는 것을 전제로 짜여 있고, 조건이 엔진 안에 있으면 엔진이 언제 읽기를 멈춰야 할지 몰라 조건에 맞는 레코드가 없을 때 인덱스의 처음까지 읽어 갈 수 있다. ORDER BY ... DESC와 LIMIT으로 조기 종료를 얻은 쿼리는 바로 이 역방향 ref 접근을 쓰므로, 인덱스 끝에 붙인 열이 ICP의 대상이 되지 못한다.

    이 단계에는 함정이 하나 더 있다. 07회는 동률을 대비해 ORDER BY created_at DESC, product_id DESC로 순서를 하나로 정하라고 권했고, 인덱스 확장 덕분에 (category_id, status, created_at)의 항목은 실제로 (…, created_at, product_id) 순서라서 정렬 단계가 생기지 않았다. 새 인덱스의 항목은 (…, created_at, price, product_id) 순서다. created_at이 같은 행들 사이에서는 price가 먼저 순서를 정하므로, 이 인덱스로는 created_at DESC, product_id DESC의 순서가 나오지 않는다. 거르기용 열을 정렬 열 바로 뒤에 붙이면 기본 키가 담당하던 동률 처리 순서가 밀려난다. 이 실습 데이터는 created_at이 모두 달라 결과에 드러나지 않지만, 실제 서비스의 인덱스에서는 확인해야 할 부분이다.

    단계 2: 정방향으로 읽게 만든다 — 내림차순 인덱스

    ICP를 막는 것이 역방향 읽기라면 정방향으로 읽게 만들면 된다. MySQL 매뉴얼에 따르면 인덱스 정의의 DESC는 무시되지 않고 키 값을 내림차순으로 저장하게 하며, 내림차순 인덱스는 정방향으로 읽을 수 있어 역순 스캔보다 효율적이다. created_at을 DESC로 정의하면 (7, 'ON_SALE') 구간 안의 항목이 최신순으로 놓이므로, ORDER BY created_at DESC를 정방향 읽기로 얻는다. 내림차순 인덱스의 동작과 제약 전반은 09회에서 다루고, 여기서는 ICP와의 관계만 본다.

    ALTER TABLE product
  DROP INDEX idx_cat_status_created_price,
  ADD INDEX idx_cat_status_createddesc_price (category_id, status, created_at DESC, price);
    EXPLAIN:     type: ref   key: idx_cat_status_createddesc_price   key_len: 86   ref: const,const   rows: 15046
             Extra: Using index condition

EXPLAIN ANALYZE:
-> Limit: 20 row(s)  (cost=4322 rows=20) (actual time=2.91..2.91 rows=20 loops=1)
    -> Index lookup on product using idx_cat_status_createddesc_price (category_id=7, status='ON_SALE'), with index condition: (product.price between 50000 and 50900)  (cost=4322 rows=15046) (actual time=2.91..2.91 rows=20 loops=1)

    정방향 접근이므로 push_index_cond()가 첫머리에서 돌아가지 않고, 가격 조건이 엔진으로 내려간다. Backward index scan도 사라졌다. 이제 엔진은 (7, 'ON_SALE') 구간의 앞, 곧 최신 상품부터 항목을 읽으며 가격을 인덱스 항목에서 확인하고, 일치하는 항목에 대해서만 클러스터형 인덱스를 조회한다. 읽는 인덱스 항목은 단계 0과 같은 1,894개다. 일치 항목이 놓인 위치는 정렬 순서로 정해지고 그 순서는 바뀌지 않았기 때문이다. 바뀐 것은 클러스터형 조회가 1,894번에서 20번으로 줄었다는 점이다. 핸들러 카운터는 Handler_read_key 1, Handler_read_next 19로 20번의 호출만 남는다. icp 카운터는 계산상 icp_match 20, icp_no_match 1,874가 최소다. 다만 8.4 소스의 row_search_mvcc()는 조건을 만족한 행을 서버가 요청하기 전에 여러 개 미리 읽어 캐시에 채우므로(서버가 준 레코드 버퍼가 있으면 그 크기만큼, 없으면 최대 8행), LIMIT에서 멈춘 쿼리의 실제 icp 카운터 증가분과 클러스터형 조회 수는 이보다 클 수 있다. 이 회차에서 LIMIT 쿼리에 적은 조회 수는 모두 이 미리 읽기를 뺀 계산값이다.

    이 인덱스를 만들기 전에 실험 순서를 정리해 두자. 같은 접두사를 가진 인덱스가 여럿 있으면 옵티마이저가 어느 것을 쓰는지 매번 EXPLAIN으로 확인해야 하고, 비교가 흐려진다. 실제로 MySQL 8.4.13에서는 idx_category_status_created가 보이는 상태라면 내림차순 인덱스를 만들어도 옵티마이저가 기존 인덱스의 역방향 ref 접근(Using where; Backward index scan, 인덱스 노드 rows=1894)을 골랐다. 위의 계획은 기존 인덱스를 옵티마이저에게서 감춘 상태에서 얻은 것이다. 비교할 때는 후보를 하나씩만 남기는 편이 해석이 깔끔하다. 인덱스를 지우지 않고 옵티마이저의 눈에서만 감추는 방법은 09회에서 본다. 매뉴얼은 내림차순 키 열을 가진 세컨더리 인덱스에는 체인지 버퍼링이 지원되지 않는다고도 밝히는데, 06회에서 본 대로 8.4의 innodb_change_buffering 기본값이 이미 none이므로 8.4 기본 설정에서는 차이가 없다.

    단계 3: 다른 길 — price를 정렬 열 앞에 둔다

    ICP 말고 구간 자체를 좁히는 길도 있다. price를 created_at 앞에 두면 가격 조건이 구간을 정하는 데 쓰인다. 대신 07회의 규칙대로 범위 조건 열 뒤의 created_at은 순서를 주지 못하므로 정렬 단계가 생긴다.

    ALTER TABLE product

Using index condition은 "조건이 엔진으로 내려갔다"는 뜻일 뿐 "많이 걸러졌다"는 뜻이 아니다.

    커버링 인덱스 심화 1: ICP와 커버링은 같은 문제의 두 답이다

    06회에서 커버링 인덱스를 정의했다. 쿼리가 그 테이블에서 필요로 하는 모든 열, 곧 SELECT 목록뿐 아니라 WHERE, ORDER BY, GROUP BY, 조인 조건의 열까지 인덱스 안에 있으면 클러스터형 인덱스를 읽지 않고 인덱스만으로 답할 수 있고, 실행 계획의 Extra에는 Using index가 나온다. InnoDB에서는 세컨더리 인덱스에 기본 키가 붙어 있으므로 기본 키 열도 공짜로 포함된다. 그리고 쓰기가 몰려 페이지가 읽기 뷰보다 새로워지면 커버링이어도 클러스터형 인덱스를 방문하는 예외가 있었다. 이 절에서는 그 위에 두 가지를 더한다. ICP와의 관계, 그리고 커버링 안에서도 열 순서가 일의 양을 정한다는 사실이다.

    실행 계획은 둘 중 하나만 고른다

    8.4 소스의 make_join_readinfo()에서 ref 계열 접근(eq_ref, ref, ref_or_null 등)을 다듬는 부분은 이렇게 짜여 있다. 사용하는 인덱스가 이 테이블의 커버링 인덱스 집합(covering_keys)에 들어 있고 키 읽기가 금지되지 않았다면 키 읽기 모드(set_keyread(true))를 켜고, 그렇지 않을 때만 push_index_cond()를 부른다. range 접근도 같다. 인덱스가 커버링이면 키 읽기 모드를 켜고, 키 읽기 모드가 아닐 때만 ICP를 시도한다. 그래서 같은 테이블 접근에서 Using index와 Using index condition은 함께 나오지 않는다.

    이것은 설계상 당연한 선택이다. ICP의 목적은 행 전체를 읽으러 클러스터형 인덱스에 가는 횟수를 줄이는 것인데, 커버링 인덱스는 처음부터 그 길을 가지 않는다. 매뉴얼도 ICP가 쓰이면 행 전체를 읽어야 하므로 Using index가 표시되지 않는다고 설명한다. 그러면 커버링 인덱스에서 조건은 어디서 평가될까? 키 읽기 모드에서 엔진은 인덱스 항목에서 꺼낸 열만으로 행을 만들어 서버로 올리고, 서버가 조건을 평가한다. Extra에 Using where; Using index가 함께 나오는 것이 이 경우다. 세 경우의 일을 나란히 놓으면 차이가 분명해진다. N은 인덱스에서 읽는 구간의 항목 수, M은 조건을 만족하는 항목 수다.

    방식엔진이 확인하는 인덱스 항목핸들러 경계를 넘는 행클러스터형 인덱스 조회Extra
    커버링 아님, ICP 없음NNNUsing where
    커버링 아님, ICPNMMUsing index condition
    커버링NN0Using where; Using index

    커버링은 핸들러 경계를 넘는 행이 ICP보다 많지만, 그 행은 인덱스 항목에서 바로 만든 것이라 클러스터형 조회가 하나도 없다. 비싼 쪽을 없앤 것이다. 그래서 커버링이 가능하다면 대개 커버링이 낫고, ICP는 "모든 열을 인덱스에 담을 수는 없지만 거르는 조건의 열은 담을 수 있을 때" 쓰는 수단이라고 정리할 수 있다.

    커버링이라고 다 같은 커버링이 아니다

    커버링 여부는 "클러스터형 인덱스에 가는가"만 말해 줄 뿐, 인덱스를 얼마나 읽는지는 말해 주지 않는다. 가격 필터가 걸린 판매 중 상품의 개수를 세는 쿼리로 확인해 보자.

    SELECT COUNT(*)
FROM product
WHERE category_id = 7
  AND status = 'ON_SALE'
  AND price BETWEEN 50000 AND 50900;

    앞 절의 단계 1 인덱스 (category_id, status, created_at, price)와 단계 3 인덱스 (category_id, status, price, created_at)는 둘 다 이 쿼리의 커버링 인덱스다. 쿼리가 쓰는 열 넷이 모두 들어 있다. 그런데 앞의 것으로 처리하면 price가 구간을 좁히지 못하므로 ref 접근(key_len 86)으로 (7, 'ON_SALE') 구간의 항목 8,000개를 모두 읽고, 서버가 그중 81개를 센다. 뒤의 것으로 처리하면 range 접근(key_len 90)으로 81개 항목만 읽는다. 둘 다 Extra에 Using index가 찍히고 클러스터형 조회는 0번이지만, 읽는 항목은 100배 가까이 차이가 난다. MySQL 8.4.13에서 각 인덱스를 FORCE INDEX로 지정해 실행하면 앞의 것은 Covering index lookup 노드가 rows=8000을, 뒤의 것은 Covering index range scan 노드가 rows=81을 올리고, Extra는 둘 다 Using where; Using index다. 두 인덱스가 모두 있으면 옵티마이저는 뒤의 것을 고른다. 04회와 07회에서 세운 열 순서의 규칙, 곧 등치 조건 열을 앞에, 범위 조건 열을 그 뒤에 두라는 규칙은 커버링 인덱스에서도 그대로 작동한다.

    커버링은 읽는 방향을 가리지 않는다

    앞 절에서 역방향 ref 접근은 ICP를 쓰지 못했다. 커버링에는 그런 제약이 없다. 키 읽기 모드는 접근 방향과 무관하게 인덱스 항목에서 열을 꺼낼 뿐이다. 매뉴얼의 내림차순 인덱스 절에 실린 예에서도 역방향 스캔과 커버링이 함께 쓰인 계획의 Extra가 Backward index scan; Using index로 나온다. 이 사실이 다음 절의 지연 조인을 가능하게 한다.

    커버링의 값: 무엇을 인덱스에 넣을 것인가

    상품 목록 쿼리 자체를 커버링으로 만들려면 SELECT 목록의 name까지 인덱스에 넣어야 한다. name은 utf8mb4의 VARCHAR(100)이라 항목마다 최대 400바이트에 길이 정보가 붙는다. 06회의 판단 5에서 어림한 대로 세컨더리 인덱스 항목은 보통 수십 바이트이므로, name을 넣으면 항목이 몇 배로 넓어지고 페이지당 항목 수가 그만큼 줄며, 상품명을 고칠 때마다 이 인덱스에도 삭제 표시와 삽입이 일어난다. 화면에 보여 줄 열을 모두 인덱스에 담는 것은 대개 수지가 맞지 않는다. 거르고 정렬하는 데 필요한 좁은 열만 담고, 화면에 보여 줄 넓은 열은 최종 결과 행에 대해서만 가져오는 방법이 있다. 그것이 지연 조인이다.

    커버링 인덱스 심화 2: 지연 조인으로 조회를 마지막 20행에만

    지연 조인(deferred join)은 쿼리를 두 단계로 나눈다. 먼저 커버링 인덱스만으로 결과 행의 기본 키를 고르고, 그다음 고른 기본 키로 클러스터형 인덱스에서 행을 가져온다. 앞 절의 가격 필터 쿼리에 적용하면 다음과 같다. 안쪽 쿼리에 필요한 인덱스는 단계 1에서 만들었던 (category_id, status, created_at, price)다.

    ALTER TABLE product
  ADD INDEX idx_cat_status_created_price (category_id, status, created_at, price);

SELECT p.product_id, p.name, p.price, p.created_at
FROM (
    SELECT product_id, created_at
    FROM product
    WHERE category_id = 7
      AND status = 'ON_SALE'
      AND price BETWEEN 50000 AND 50900
    ORDER BY created_at DESC
    LIMIT 20
) AS t
JOIN product AS p ON p.product_id = t.product_id
ORDER BY t.created_at DESC;

    실행을 단계별로 따라가자.

    계획은 다음과 같다. 인덱스 접근 줄의 접두어가 Covering index로 바뀐 것에 주목하자. 8.4 소스의 EXPLAIN 출력 코드는 그 인덱스가 커버링인지에 따라 이 접두어를 Index와 Covering index 중에서 고른다. 전통적인 EXPLAIN에서는 이 파생 테이블 행(select_type DERIVED)의 Extra에 Using where; Backward index scan; Using index가 함께 나타난다.

    -> Nested loop inner join  (cost=379 rows=20) (actual time=11.3..13.4 rows=20 loops=1)
    -> Sort: t.created_at DESC  (cost=372..372 rows=20) (actual time=11.3..11.3 rows=20 loops=1)
        -> Table scan on t  (cost=358..361 rows=20) (actual time=1.88..1.88 rows=20 loops=1)
            -> Materialize  (cost=358..358 rows=20) (actual time=1.86..1.86 rows=20 loops=1)
                -> Limit: 20 row(s)  (cost=356 rows=20) (actual time=0.161..1.79 rows=20 loops=1)
                    -> Filter: (product.price between 50000 and 50900)  (cost=356 rows=1672) (actual time=0.16..1.79 rows=20 loops=1)
                        -> Covering index lookup on product using idx_cat_status_created_price (category_id=7, status='ON_SALE') (reverse)  (cost=356 rows=15046) (actual time=0.13..1.66 rows=1894 loops=1)
    -> Single-row index lookup on p using PRIMARY (product_id=t.product_id)  (cost=0.282 rows=1) (actual time=0.109..0.109 rows=1 loops=20)

    Materialize 아래가 안쪽 쿼리다. 인덱스 노드가 1,894행을 올리고 Filter가 20행을 통과시키며, 바깥의 기본 키 조회는 loops=20이다. 같은 쿼리의 핸들러 카운터는 Handler_read_key 21(안쪽 첫 위치 잡기 1번과 바깥 기본 키 조회 20번), Handler_read_prev 1,893, Handler_read_rnd_next 21(임시 테이블 t를 읽는 호출)이다.

    바깥의 ORDER BY t.created_at DESC는 빼면 안 된다. 안쪽 쿼리에 ORDER BY가 있으니 결과도 그 순서일 것 같지만, 매뉴얼에 따르면 옵티마이저가 파생 테이블의 ORDER BY를 바깥 쿼리로 전파하는 것은 바깥 쿼리가 그룹이나 집계를 하지 않고, DISTINCT·HAVING·ORDER BY가 없으며, 그 파생 테이블이 FROM 절의 유일한 원천일 때뿐이고, 그 밖에는 무시한다. 이 쿼리의 바깥에는 조인이 있으므로 안쪽의 순서는 결과 순서를 보장하지 않는다. 안쪽의 ORDER BY는 "어느 20개를 고를 것인가"를 정하는 데 쓰이고, 바깥의 ORDER BY가 "어떤 순서로 보여 줄 것인가"를 정한다. 바깥 정렬의 입력은 20행이므로 비용은 무시할 만하다.

    왼쪽에는 세컨더리 인덱스를 거꾸로 훑으며 기본 키만 모으는 안쪽 쿼리, 가운데에는 20행짜리 임시 테이블, 오른쪽에는 그 20개 기본 키로만 클러스터형 인덱스를 찾아가는 바깥 조인을 보여 준다. 왼쪽에 세로로 긴 띠 모양의 인덱스 리프 열, 상단 라벨 "세컨더리 인덱스 (category_id, status, created_at, price)". 띠의 아래쪽 끝에서 위쪽으로 향하는 굵은 화살표, 라벨 "역순으로 1,894개 확인". 띠 안의 칸들 대부분은 회색이고 일부 초록 칸에서 오른쪽으로 가는 가는 화살표가 가운데의 작은 표로 모인다. 가운데 작은 표의 라벨 "임시 테이블 t: 기본 키 20개". 오른쪽에 피라미드 모양의 B+Tree, 라벨 "클러스터형 인덱스". 가운데 표에서 피라미드의 리프로 화살표 20개, 라벨 "기본 키로 조회 20번". 왼쪽 띠와 피라미드 사이 위쪽에 X 표시가 된 점선 화살표, 라벨 "안쪽 쿼리는 테이블에 가지 않는다". 평면 스타일, 흰 배경. 지연 조인은 거르고 정렬하는 일을 좁은 커버링 인덱스 안에서 끝내고, 넓은 행은 최종 20행에 대해서만 가져온다.

    ICP 쪽은 SQL을 고치지 않아도 되고 서버로 올라가는 행도 적다. 지연 조인 쪽은 내림차순 인덱스 없이도 되고, 같은 인덱스를 오름차순 목록에도 쓸 수 있다. 쿼리를 고칠 수 있느냐, 오름차순과 내림차순 목록이 둘 다 있느냐에 따라 고르면 된다. 같은 원리를 애플리케이션 쪽에서 두 번의 쿼리로 나눠 구현할 수도 있다. 첫 쿼리로 커버링 인덱스만 써서 기본 키 20개를 얻고, 두 번째 쿼리에서 WHERE product_id IN (…)로 행을 가져온다. JPA에서는 첫 쿼리를 기본 키만 고르는 프로젝션으로, 두 번째를 엔티티 조회로 쓰는 식이다. 이때도 두 번째 쿼리의 결과 순서는 보장되지 않으므로 첫 쿼리의 순서대로 다시 맞춰야 한다. 지연 조인이 가장 큰 힘을 쓰는 곳은 OFFSET이 깊은 페이징인데, 그것은 12회에서 다룬다.

    대용량 성능 실측: 무엇을 어떻게 재는가

    지금까지의 비교는 모두 일의 양, 곧 읽은 항목 수와 조회 수로 했다. 실행 시간을 적지 않은 데는 이유가 있다. 같은 쿼리라도 시간은 버퍼 풀에 페이지가 올라와 있느냐, 디스크가 무엇이냐, CPU가 무엇이냐에 따라 몇 배씩 달라진다. 반면 일의 양은 데이터와 계획이 같으면 어디서 재도 같다. 큰 데이터에서 성능을 잴 때도 순서는 같다. 먼저 일의 양을 확인하고, 그다음 그 일이 디스크를 얼마나 건드렸는지를 보고, 마지막에 시간을 잰다.

    데이터를 키운다

    100만 행에서 내린 판단이 1,000만 행에서도 맞는지 보려면 같은 규칙으로 데이터를 키운다. 07회의 생성 쿼리를 행 번호에 100만 단위의 오프셋을 더하는 형태로 바꿔 아홉 번 실행하면 된다. 04회에서 본 매뉴얼의 권고대로 대량 적재를 할 때는 세컨더리 인덱스를 나중에 만드는 편이 전체 과정을 빠르게 할 수 있다.

    SET SESSION cte_max_recursion_depth = 1000000;

SET @b = 1;   -- 1부터 9까지 바꿔 가며 아홉 번 실행한다
INSERT INTO product (product_id, category_id, name, price, status, created_at)
WITH RECURSIVE seq (n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM seq WHERE n < 1000000
), num (m) AS (
  SELECT n + 1000000 * @b FROM seq
)
SELECT m,
       MOD(m, 100) + 1,
       CONCAT('상품', m),
       (MOD(m, 997) + 1) * 100,
       CASE WHEN MOD(m DIV 100, 10) < 8 THEN 'ON_SALE'
            WHEN MOD(m DIV 100, 10) = 8 THEN 'SOLD_OUT'
            ELSE 'HIDDEN' END,
       TIMESTAMP('2023-01-01') + INTERVAL m * 60 SECOND
FROM num;

ANALYZE TABLE product;

    계산으로 먼저 예측한다

    측정하기 전에 각 계획이 해야 할 일을 계산해 둔다. 측정값이 예측과 다르면 계획이 생각과 다르다는 신호다. 단, LIMIT에서 멈추는 계획의 엔진 안쪽 값(icp 카운터, 클러스터형 조회 수)은 앞에서 본 InnoDB의 미리 읽기만큼 예측보다 클 수 있다. 아래 표는 이 회차의 쿼리들을 생성 규칙에서 계산한 값이다. "항목"은 인덱스에서 확인하는 항목 수, "조회"는 클러스터형 인덱스 조회 수다.

    1,000만 행 열은 1,000만 행 전체를 만들지 않고, MySQL 8.4.13에서 같은 생성 규칙으로 카테고리 7의 행 10만 개(n = 100k + 6, k = 0~99,999)만 만들어 확인했다. 이 쿼리들은 카테고리 7의 행만 읽으므로 항목 수는 전체 테이블에서와 같다. 주말 행은 28,576개, 가격 범위에 드는 판매 중 상품은 801개였고, 단계 0의 역방향 인덱스 노드는 rows=2110을 올렸다. 단계 2와 지연 조인의 항목 수는 단계 0과 같은 순서를 읽으므로 같은 값이다.

    이 표에서 큰 데이터에 관한 세 가지 사실을 읽을 수 있다. 첫째, LIMIT이 없는 쿼리는 테이블과 함께 자란다. 주말 쿼리는 행이 10배가 되자 항목도 조회도 10배가 되었다. ICP가 줄이는 비율은 데이터 크기와 무관하게 거의 같다. 100만 행에서는 1만 번 가운데 7,134번, 1,000만 행에서는 10만 번 가운데 71,424번의 조회를 없앴다. 둘째, 조기 종료가 일어나는 LIMIT 쿼리는 테이블 크기가 아니라 일치 행의 밀도와 위치를 따른다. 테이블이 10배가 되어도 1,894개가 2,110개로 늘었을 뿐이다. 셋째, 그래서 작은 데이터에서 내린 판단이 큰 데이터에서 달라질 수 있다. 단계 3은 일치하는 행 집합 전체를 읽는 계획이라 테이블과 함께 81에서 801로 자랐다. 클러스터형 조회 수로 보면 단계 3은 81번에서 801번으로 열 배가 되었고, 단계 2와 지연 조인은 20번 그대로다. 100만 행에서 "읽는 항목이 가장 적다"는 이유로 단계 3을 골랐다면, 1,000만 행에서는 그 계획이 단계 2나 지연 조인보다 훨씬 많은 조회에 정렬까지 하는 계획이 된다. 개발 환경의 작은 데이터로 인덱스를 고르면 안 되는 이유가 여기에 있다.

    측정 절차

    버퍼 풀을 비운 상태를 재려고 서버를 재시작하는 경우가 많은데, 그것만으로는 버퍼 풀이 비지 않는다. 매뉴얼에 따르면 innodb_buffer_pool_dump_at_shutdown과 innodb_buffer_pool_load_at_startup이 기본으로 켜져 있어서, 종료할 때 최근에 쓴 페이지의 목록을 저장하고 시작할 때 그 페이지들을 다시 읽어 들인다. 저장하는 것은 데이터가 아니라 페이지를 찾는 데 필요한 테이블스페이스 ID와 페이지 ID뿐이고, 기본으로 가장 최근에 쓴 25%의 페이지(innodb_buffer_pool_dump_pct)를 대상으로 한다. 실습 서버에서 디스크 읽기 상태를 재려면 시작할 때의 적재를 끄거나, 버퍼 풀을 데이터보다 작게 잡는다.

    버퍼 풀이 테이블보다 작아지면 이 회차의 차이가 시간에 가장 크게 드러난다. 클러스터형 조회 하나하나가 디스크의 임의 위치를 읽는 랜덤 I/O가 될 수 있기 때문이다(06회). ICP를 끈 주말 쿼리는 카테고리 7의 모든 행을 조회하므로, 07회에서 계산한 대로 클러스터형 인덱스의 모든 리프 페이지를 건드린다.     인덱스 스킵 스캔 1: 선두 열을 건너뛰는 법

    이제 방향을 바꿔, 인덱스의 구간을 아예 만들 수 없던 쿼리를 보자. 04회의 주문 테이블에는 대시보드 쿼리를 위해 만든 idx_orders_status_ordered (status, ordered_at)가 있었다. 04회의 가정대로 주문은 100만 건, 상태는 PENDING, PAID, SHIPPED, DELIVERED, CANCELLED 다섯 가지, 최근 7일 주문은 약 1만 건이다(실험용 단일 열 인덱스는 지웠다고 하자). 여기에 상태와 무관한 "최근 7일 전체 주문 수" 카드가 추가된다.

    SELECT COUNT(*)
FROM orders
WHERE ordered_at >= '2026-11-10 00:00:00'
  AND ordered_at <  '2026-11-17 00:00:00';

    04회의 최좌측 접두사 규칙에 따르면 이 쿼리는 (status, ordered_at)로 구간을 만들 수 없다. 인덱스는 status로 먼저 정렬되어 있고, 최근 7일의 항목은 다섯 개의 상태 덩어리마다 흩어져 있다. 그래서 전통적인 선택지는 두 가지였다. 테이블 전체를 읽거나, 이 쿼리가 쓰는 열(ordered_at)이 모두 들어 있는 이 인덱스를 처음부터 끝까지 훑는 것(type: index)이다. 뒤의 것이 더 작은 대상을 읽지만, 어느 쪽이든 100만 항목을 읽어 1만 개를 센다.

    그런데 인덱스의 구조를 다시 보면 길이 보인다. 각 상태 덩어리 안에서는 ordered_at이 정렬되어 있으므로, 최근 7일의 항목은 덩어리마다 하나씩, 모두 다섯 개의 연속 구간을 이룬다. 덩어리가 다섯 개뿐이라면 덩어리마다 구간의 시작으로 뛰어 들어가 그 구간만 읽으면 된다. 이것이 스킵 스캔이다. 매뉴얼은 MySQL 8.0.13부터 옵티마이저가 선두 열의 값마다 하나씩 여러 번의 범위 스캔을 할 수 있고, 이 방법이 루스 인덱스 스캔과 비슷하다고 설명한다. 매뉴얼의 예를 이 쿼리에 대응시키면 실행은 다음과 같다. 상태 값은 문자열 순서로 CANCELLED, DELIVERED, PAID, PENDING, SHIPPED 차례로 놓여 있다.

    idx_orders_status_ordered (status, ordered_at) 리프 항목, 왼쪽에서 오른쪽으로 키 순서

|-- CANCELLED --------[7일]|-- DELIVERED -------[7일]|-- PAID ---------[7일]|-- PENDING -[7일]|-- SHIPPED ------[7일]|
 ^                    ====  ^                   ====  ^                ====  ^           ====  ^               ====
 |                     |    |                    |    |                 |    |            |    |                |
 첫 항목에서            구간   다음 접두사로         구간  ...                                                     구간
 CANCELLED 얻기        읽기   뛰기 (사이는 건너뜀)  읽기

전체 항목 약 1,000,000개 중 읽는 것: 구간 5개에 든 약 10,000개 + 접두사 찾기와 구간 위치 잡기를 위한 B+Tree 하강
    (status, ordered_at) 인덱스의 리프 항목이 상태별 다섯 덩어리로 나뉘어 있고, 각 덩어리 오른쪽 끝의 작은 구간만 읽히며 덩어리 사이는 위쪽 곡선 화살표로 건너뛰는 모습을 보여 준다. 가로로 긴 띠 하나를 다섯 구역으로 나눈다. 구역 라벨은 왼쪽부터 "CANCELLED", "DELIVERED", "PAID", "PENDING", "SHIPPED". 각 구역 안 오른쪽 끝 부분에 진한 파랑으로 칠한 짧은 구간이 있고 그 아래 라벨 "최근 7일". 각 구역의 나머지는 옅은 회색. 띠 위로 다섯 개의 곡선 화살표가 앞 구역의 파란 구간 끝에서 다음 구역의 시작으로 건너뛰며, 첫 화살표에 라벨 "다음 상태 값으로 점프". 띠 위쪽 중앙에 작은 피라미드 모양 B+Tree가 있고 피라미드에서 각 파란 구간 시작점으로 가는 점선 화살표, 라벨 "구간마다 다시 내려감". 띠 아래 오른쪽 라벨 "읽는 항목: 5개 구간만". 평면 스타일, 흰 배경. 스킵 스캔은 선두 열의 값마다 B+Tree를 다시 내려가 그 값 안의 범위 구간만 읽고, 덩어리 사이의 항목은 건너뛴다.

    소스로 본 스킵 스캔의 한 걸음

    8.4 소스의 IndexSkipScanIterator::Read()는 주석에서 알고리즘을 세 겹의 루프로 적는다. 바깥 루프는 등치 접두사(A 부분)의 값들을 돌고, 가운데 루프는 그 안의 서로 다른 접두사(B 부분)를 돌며, 안쪽에서 범위 조건(C 부분)으로 하위 구간을 스캔한다. 첫 접두사는 등치 접두사가 없으면 ha_index_first로 인덱스의 첫 항목을 읽어 얻는다. 하위 구간은 접두사 값 뒤에 C의 최솟값과 최댓값을 붙여 시작 키와 끝 키를 만들고, ha_read_range_first와 ha_read_range_next로 읽는다. 다음 접두사로 넘어갈 때는 index_next_different()를 부르는데, 스킵 스캔은 이 함수의 첫 인자를 false로 넘긴다. MySQL 개발 블로그에 실린 이 함수의 코드를 보면 이 경우 ha_index_read_map(..., HA_READ_AFTER_KEY)를 호출해 "현재 접두사 바로 뒤의 키"를 엔진이 찾게 한다. 같은 글은 이것이 사실상 임의 위치로의 접근이라고 설명한다. 곧 접두사가 바뀔 때마다 B+Tree를 루트에서 다시 내려간다.

    같은 함수를 첫 인자 true로 부르면 사정이 다르다. 그때는 ha_index_next로 항목을 하나씩 읽으며 서버가 접두사가 바뀌었는지 비교한다. 이것은 GROUP BY의 루스 인덱스 스캔에 있는 "스캔 변형"이 쓰는 방식으로, 점프하는 비용이 인덱스를 그냥 훑는 비용보다 클 때 고른다. 스킵 스캔은 언제나 점프하는 쪽이다. 루스 인덱스 스캔은 12회의 주제다.

    실행 계획에서의 모습과 쓰이는 조건

    스킵 스캔은 매뉴얼에서 범위 최적화 절의 한 접근 방법(Skip Scan Range Access Method)으로 다뤄지고, EXPLAIN의 Extra에 Using index for skip scan이 나타나면 쓰인 것이다. 매뉴얼은 인덱스가 스킵 스캔에 쓰일 수 있다면 possible_keys에도 그 인덱스가 보여야 한다고 덧붙인다. TREE 형식에서는 인덱스 접근 줄이 Covering index skip scan on 테이블 using 인덱스 over 구간 모양으로 나온다. 8.4 소스의 EXPLAIN 출력 코드에는 스킵 스캔이 현재 언제나 커버링이라는 주석이 있다. 옵티마이저 트레이스에서는 skip_scan_range 항목으로 나타난다.

    매뉴얼은 스킵 스캔이 쓰이는 조건을 인덱스 형태 ([A_1, …, A_k,] B_1, …, B_m, C [, D_1, …, D_n])로 설명한다. A와 D는 비어 있어도 되지만 B와 C는 비어 있으면 안 된다. 주문 예에서는 A가 비어 있고, B가 status, C가 ordered_at이다. 조건을 하나씩 이유와 함께 보자.

    매뉴얼의 조건의미와 이유
    테이블 하나만 참조한다조인이 있는 쿼리에는 쓰이지 않는다.
    GROUP BY나 DISTINCT를 쓰지 않는다그룹별로 건너뛰며 읽는 일은 루스 인덱스 스캔의 몫이다(12회).
    인덱스에 있는 열만 참조한다커버링이어야 한다. SELECT 목록이나 조건에 인덱스 밖의 열이 하나라도 있으면 쓰이지 않는다.
    A_1~A_k의 조건은 상수와의 등치다(IN 포함)바깥 루프가 돌 등치 접두사의 값들이 실행 전에 정해져야 한다.
    쿼리는 AND로 이어진 형태다각 열에 대한 조건(그 안의 OR는 허용)이 AND로 묶여야 한다.
    C에 범위 조건이 있어야 한다각 접두사 안에서 읽을 하위 구간을 만드는 조건이다.
    D의 조건은 C의 범위 조건과 AND로 묶이면 허용된다D는 구간을 정하는 데 쓰이지 않고 읽은 항목에서 확인된다.

    인덱스 스킵 스캔 2: 적용과 한계

    product 테이블에 적용해 보자. 07회 끝의 두 인덱스만 있는 상태에서 "최근 일주일 동안 등록된 상품 수"를 센다.

    SELECT COUNT(*)
FROM product
WHERE created_at >= '2024-11-18 00:00:00';

    결과는 10,721이다. product_id 989,280부터 1,000,000까지의 행이고, 100개 카테고리에 107개 또는 108개씩 나뉘어 있다. 두 인덱스 모두 스킵 스캔의 후보다. idx_category_created에서는 B가 category_id, C가 created_at이고 접두사가 100개다. idx_category_status_created에서는 B가 (category_id, status), C가 created_at이고 접두사가 300개다. 앞의 것으로 스킵 스캔을 하면 접두사 100개마다 다음 카테고리로 뛰는 하강 한 번과 구간 시작을 찾는 하강 한 번을 하고, 모두 10,721개의 항목을 읽는다. 커버링 인덱스 풀 스캔이라면 100만 개 항목을 모두 읽어야 한다.

    비용은 접두사의 개수가 정한다

    옵티마이저가 스킵 스캔을 고를지는 비용으로 정해진다. 8.4 소스의 cost_skip_scan()은 비용을 이렇게 어림한다. 먼저 접두사 그룹의 수를 인덱스 통계의 "키 값 하나당 레코드 수"(records_per_key)로 구한다. 등치 접두사가 없으면 테이블 전체 행 수를 그룹 하나의 크기로 나누고 1을 더한다. idx_category_created라면 category_id 하나에 1만 행이므로 1,000,000 ÷ 10,000 + 1 = 101개 그룹으로 본다. CPU 비용은 "트리 탐색 비용 × 그룹 수 × 2"에 읽을 행을 평가하고 비교하는 비용을 더한 값인데, 주석은 그룹마다 위치 잡기가 두 번 일어난다고 적는다. 트리 탐색 비용은 테이블 행 수의 log2를 올림한 횟수만큼의 키 비교로 잡으므로 100만 행이면 20번이다. I/O 비용은 그룹 수와 읽을 행 수로 인덱스 스캔 비용을 구한다. MySQL 8.4.13에서 이 쿼리의 트레이스를 보면 potential_skip_scan_indexes에 idx_category_created는 "num_groups": 102, idx_category_status_created는 "num_groups": 302로 나온다. 통계의 테이블 행 수와 records_per_key가 추정값이라 위의 계산값과 조금 다르다. 같은 항목의 "tree_travel_cost": 1은 키 비교 20번에 키 비교 하나의 비용 0.05(mysql.server_cost에 있는 key_compare_cost의 기본값)를 곱한 값과 맞는다.

    이 식에서 스킵 스캔의 성격이 드러난다. 비용의 핵심 변수는 B의 서로 다른 값의 수다. 접두사가 100개라면 하강 200번은 100만 항목을 훑는 것에 비해 작다. 하지만 B의 값이 50만 개라면 하강이 100만 번이고, 하강 한 번은 항목 하나를 옆으로 읽는 것보다 훨씬 비싸므로 인덱스를 그냥 훑는 것보다 나빠진다. 그래서 스킵 스캔은 선두 열의 카디널리티가 낮은 인덱스, 곧 상태 코드나 유형, 카테고리처럼 값의 종류가 적은 열로 시작하는 인덱스에서 힘을 쓴다. 통계가 그룹 수를 잘못 어림하면 판단도 틀어지는데, 통계와 그 갱신은 10회에서 다룬다.

    스킵 스캔이 거절되는 경우

    8.4 소스는 스킵 스캔 후보를 거를 때 이유를 옵티마이저 트레이스에 남긴다. 쿼리 전체가 자격이 없으면 skip_scan_range 항목에 "chosen": false와 이유(cause)를, 인덱스별로 자격이 없으면 potential_skip_scan_indexes 배열의 각 인덱스 항목에 "usable": false와 이유를 기록한다. 스킵 스캔이 기대대로 나오지 않을 때 이 이유 문자열이 가장 빠른 답이다.

    쿼리의 변화트레이스의 이유 (8.4 소스)설명
    SELECT COUNT(*), SUM(price) … WHERE created_at >= …query_references_nonkey_columnprice가 인덱스에 없어 커버링이 아니다.
    SELECT category_id, COUNT(*) … GROUP BY category_idhas_group_by그룹핑이 있는 쿼리는 스킵 스캔 대상이 아니다.
    SELECT DISTINCT category_id …has_select_distinctDISTINCT도 마찬가지다.
    ORDER BY로 역순을 요구함cannot_do_reverse_ordering스킵 스캔은 역방향으로 읽지 못한다.
    WHERE created_at < '2023-01-08' OR created_at >= '2024-11-18'range_predicate_too_complexC의 범위가 구간 두 개로 나뉜다. 소스는 범위가 둘 이상이면 거절한다.
    C 열에 조건이 없음no_range_predicate각 접두사 안에서 읽을 구간을 만들 수 없다.

    MySQL 8.4.13에서 확인해 보면 다섯 가지 이유가 트레이스에 그대로 나타난다. 인덱스에 없는 열, 구간 두 개짜리 범위, C 열에 조건이 없음(WHERE category_id = 7로 확인)은 두 인덱스 각각에 "usable": false와 함께, GROUP BY와 DISTINCT는 skip_scan_range에 "chosen": false와 함께 기록되었다. 역순 줄은 재현하지 못했다. ORDER BY category_id DESC나 ORDER BY category_id DESC, created_at DESC를 붙인 쿼리에서는 트레이스에 이 이유가 나타나지 않았고, 계획은 스킵 스캔을 그대로 쓰면서 Extra에 Using filesort를 더해 따로 정렬했다. 이 줄은 소스로만 확인한 내용이다.

    첫 줄이 실무에서 가장 자주 걸린다. 최근 일주일의 등록 수를 세다가 "금액 합계도 같이 보여 달라"는 요구가 붙는 순간, 쿼리는 커버링이 아니게 되고 스킵 스캔도 사라진다. 계획은 테이블 전체 스캔으로 돌아갈 수 있다. MySQL 8.4.13에서 SUM(price)를 더한 쿼리의 EXPLAIN은 type: ALL이었다. 04회의 주문 대시보드도 같다. COUNT(*)만 세면 스킵 스캔이 가능하지만 SUM(amount)를 더하면 amount가 인덱스 밖에 있어 불가능하다.

    힌트와 스위치

    스킵 스캔은 optimizer_switch의 skip_scan 플래그로 제어되고 기본값은 on이다. 문장 단위로는 SKIP_SCAN과 NO_SKIP_SCAN 힌트를 쓴다. 매뉴얼에 따르면 SKIP_SCAN에 인덱스를 지정하면 그 인덱스들로 스킵 스캔을 쓰도록 강제하고, 인덱스를 지정하지 않으면 가능한 인덱스 중 가장 싼 것을 고르며, 인덱스가 그 문장에 적용될 수 없으면 힌트가 무시될 수 있다. NO_SKIP_SCAN에 인덱스를 지정하지 않으면 그 테이블에서 스킵 스캔을 허용하지 않는다.

    -- idx_category_created로 스킵 스캔을 쓰게 한다
SELECT /*+ SKIP_SCAN(product idx_category_created) */ COUNT(*)
FROM product
WHERE created_at >= '2024-11-18 00:00:00';

-- 스킵 스캔을 막고 다른 계획과 비교한다
SELECT /*+ NO_SKIP_SCAN(product) */ COUNT(*)

WHERE created_at >= '2024-11-18 00:00:00';

    스킵 스캔은 설계 목표가 아니라 안전망이다

    스킵 스캔을 알게 되면 "선두 열을 신경 쓰지 않아도 되겠다"는 생각이 들 수 있다. 그렇지 않다. 같은 쿼리를 created_at으로 시작하는 인덱스로 처리하면 하강 한 번으로 구간의 시작을 찾고 10,721개 항목을 읽으면 끝난다. 스킵 스캔은 같은 항목을 읽되 하강을 200번 남짓 더 한다. 게다가 커버링이어야 하고, 테이블 하나여야 하고, 역순을 요구하면 안 된다는 조건이 붙는다. 자주 실행되는 중요한 쿼리라면 그 쿼리에 맞는 인덱스를 두는 것이 맞다. 스킵 스캔의 가치는 드물게 실행되는 쿼리, 예를 들어 하루 한 번 도는 통계나 운영자가 가끔 여는 화면을 위해 인덱스를 하나 더 만들지 않아도 되게 해 준다는 데 있다. 인덱스를 늘리면 쓰기 비용과 버퍼 풀 사용이 함께 늘기 때문이다(06·09회).

    같은 이유로 구간을 바로 만들 수 있는 인덱스가 있으면 스킵 스캔은 필요 없다. "카테고리 7에서 최근 일주일 동안 등록된 상품 수"(WHERE category_id = 7 AND created_at >= '2024-11-18 00:00:00')는 idx_category_status_created로 보면 A가 category_id, B가 status, C가 created_at인 스킵 스캔 후보다. 하지만 idx_category_created로는 두 열이 모두 구간에 쓰이는 평범한 range 접근(key_len 9)이 되어 하강 한 번으로 107개 항목을 읽는다. MySQL 8.4.13의 EXPLAIN도 이 계획을 골랐다(type: range, key: idx_category_created, key_len: 9, rows: 107, Extra: Using where; Using index). 스킵 스캔은 "구간을 만들 수 없을 때 쓸 수 있는 차선"이라는 위치를 기억하자.

    흔한 오해와 함정

    "Using index condition이면 인덱스만으로 처리한 것이다." 반대다. 인덱스만으로 처리하는 것은 Using index(커버링)이고, Using index condition은 행 전체를 읽어야 하는 접근에서 일부 조건을 클러스터형 조회 전에 확인한다는 뜻이다. 8.4 소스는 인덱스가 커버링이면 키 읽기 모드를 켜고 ICP를 시도하지 않으므로 같은 테이블 접근에 둘이 함께 나오지 않는다.

    "ICP가 걸리면 인덱스를 덜 읽는다." ICP는 읽는 구간을 바꾸지 않는다. key_len도 그대로다. 같은 항목을 읽되 불일치 항목의 클러스터형 조회를 없앤다. 읽는 항목 자체를 줄이려면 조건이 구간을 만들도록 열 순서를 바꾸거나 식을 구간 조건으로 고쳐야 한다.

    "EXPLAIN ANALYZE의 인덱스 노드 rows가 읽은 항목 수다." ICP가 걸린 접근에서 그 값은 ICP를 통과해 위로 올라간 행의 수다. 주말 쿼리에서 rows=2866이었지만 엔진은 1만 개의 항목을 확인했다. Handler_read_next와 슬로 쿼리 로그의 Rows_examined도 같은 사정이다. 걸러진 수는 INNODB_METRICS의 icp_no_match로 본다.

    "Using index condition이 보이니 ICP가 행을 많이 걸러 주고 있다." range 접근에서는 구간을 만든 조건이 그대로 내려가 Using index condition이 표시되는 일이 흔하다. 매뉴얼의 LIMIT 최적화 예에서도 id2 > 3 하나뿐인 range 계획에 이 표시가 붙는다. 구간 안의 항목은 모두 그 조건을 만족하므로 걸러지는 것은 없다. 효과는 표시가 아니라 icp 카운터로 판단한다.

    "인덱스 끝에 열을 붙이면 그 열의 조건은 언제나 ICP로 걸러진다." 세 가지 예외를 이 회차에서 보았다. 8.4에서 역방향 ref 접근(ORDER BY … DESC와 조기 종료의 흔한 조합)은 ICP를 시도하지 않는다. 인덱스가 커버링이 되면 ICP 대신 커버링으로 처리된다(이것은 더 좋은 쪽이다). 그리고 정렬 열 바로 뒤에 열을 붙이면 기본 키가 담당하던 동률 처리 순서가 밀려나, ORDER BY created_at DESC, product_id DESC 같은 정렬을 더 이상 인덱스로 처리하지 못한다.

    "ICP는 잠금도 줄인다." 8.4 소스에서 잠금 읽기는 세컨더리 인덱스 레코드에 잠금을 건 다음 ICP 조건을 확인한다. 불일치 레코드의 잠금을 푸는 것은 READ COMMITTED 이하에서만이다. 기본 격리 수준인 REPEATABLE READ에서는 ICP가 버린 세컨더리 레코드의 잠금도 남는다. 불일치 행의 클러스터형 레코드에 가지 않는다는 점만 다르다.

    "커버링 인덱스면 충분히 빠르다." 커버링은 클러스터형 조회를 없앨 뿐 인덱스를 얼마나 읽는지는 말해 주지 않는다. 가격 필터 개수 쿼리에서 두 커버링 인덱스는 8,000개와 81개를 읽었다. 열 순서의 규칙은 커버링에서도 그대로 적용된다.

    "스킵 스캔이 있으니 복합 인덱스의 선두 열은 아무거나 둬도 된다." 스킵 스캔은 커버링, 단일 테이블, GROUP BY·DISTINCT 없음, 구간 하나짜리 범위 조건, 낮은 선두 열 카디널리티가 모두 맞을 때만 쓸 만하다. 등치 조건 열을 앞에, 정렬·범위 열을 그 뒤에 두는 04·07회의 규칙이 먼저다.

    "InnoDB의 기본 키 조회에도 ICP가 도움이 된다." 매뉴얼과 8.4 소스 모두 InnoDB의 클러스터형 인덱스를 ICP 대상에서 뺀다. 클러스터형 인덱스는 레코드 전체가 이미 읽혀 있으므로 조회 전에 거를 것이 없다.

    이 장의 핵심

    세컨더리 인덱스 항목에는 인덱스 열과 기본 키만 있으므로, 그 밖의 열이 필요하면 항목마다 클러스터형 인덱스를 다시 내려가야 하고, 그중 조건에 맞지 않아 버려지는 조회가 낭비다. ICP는 인덱스 열만으로 판정할 수 있는 조건을 그 조회 앞에서 엔진이 확인하게 하고, 커버링 인덱스는 필요한 열을 모두 담아 조회 자체를 없애며, 스킵 스캔은 선두 열 조건이 없는 인덱스를 선두 열 값마다 구간으로 나누어 쓴다. 어느 기법이든 효과는 실행 계획의 표시가 아니라 읽은 항목 수와 조회 수로 확인해야 하고, 그 수는 데이터의 크기와 분포에 따라 달라진다.
    인덱스 컨디션 푸시다운(ICP)
    WHERE 조건 가운데 선택된 인덱스의 열만 참조하는 부분을 스토리지 엔진에 넘겨, 클러스터형 인덱스 조회 전에 인덱스 항목으로 확인하게 하는 최적화다. 읽는 구간은 같고 불일치 항목의 조회와 반환이 사라진다.
    ICP의 적용 범위
    range, ref, eq_ref, ref_or_null 접근에서 InnoDB 세컨더리 인덱스에 쓰인다. 클러스터형 인덱스, 가상 생성 열의 인덱스, 서브쿼리·저장 함수를 참조하는 조건은 제외되고, 8.4 소스에서는 역방향 접근이면 시도하지 않는다.
    ICP 효과의 측정
    ICP가 걸러 낸 항목은 핸들러 경계를 넘지 않으므로 EXPLAIN ANALYZE의 rows와 Handler 카운터에는 보이지 않는다. INNODB_METRICS의 icp_match, icp_no_match 카운터를 켜서 확인한다.
    ICP와 잠금
    잠금 읽기에서 InnoDB는 세컨더리 레코드에 잠금을 건 뒤 ICP를 확인하고, 불일치 레코드의 잠금은 READ COMMITTED 이하에서만 푼다.
    커버링 인덱스와 ICP
    인덱스가 커버링이면 키 읽기 모드가 켜지고 ICP는 시도되지 않는다. 커버링은 조회를 모두 없애므로 ICP보다 강하지만, 열 순서에 따라 읽는 항목 수는 크게 달라진다.
    지연 조인
    커버링 인덱스만으로 결과 행의 기본 키를 고르는 파생 테이블과, 그 기본 키로 행을 가져오는 바깥 조인으로 나눈 쿼리다. LIMIT이 있는 파생 테이블은 병합되지 않고, 결과 순서를 위해 바깥에 ORDER BY가 필요하다.
    인덱스 스킵 스캔
    복합 인덱스의 선두 열에 조건이 없을 때 선두 열의 서로 다른 값마다 B+Tree를 다시 내려가 범위 조건의 구간만 읽는 접근 방법이다. 8.0.13부터 있으며 커버링, 단일 테이블, GROUP BY·DISTINCT 없음 같은 조건이 붙는다.
    스킵 스캔의 비용
    그룹마다 위치 잡기를 두 번 하므로 비용은 선두 열의 서로 다른 값의 수에 비례해 커진다. 값의 종류가 적은 열로 시작하는 인덱스에서만 이득이 있다.

    실무에서 세컨더리 인덱스를 탔는데도 느린 쿼리를 만나면, 먼저 EXPLAIN ANALYZE에서 인덱스 노드가 올린 행과 그 위 Filter가 통과시킨 행을 비교한다. 그 차이만큼 클러스터형 인덱스를 다녀와서 버리고 있다. 이때 판단의 순서가 중요하다. 버리는 조건을 구간에 쓸 수 있게 만드는 것이 가장 강하고, 다음이 커버링으로 조회를 없애는 것이며, ICP는 그 둘이 어려울 때 거르는 열만 인덱스에 담아 조회를 줄이는 수단이다. ICP를 노리고 열을 추가했다면 반드시 EXPLAIN의 Using index condition과 icp 카운터로 확인한다. 이 회차에서 본 것처럼 8.4에서는 ORDER BY … DESC와 LIMIT으로 조기 종료를 얻은 쿼리가 역방향 ref 접근을 쓰면서 ICP를 시도하지 않으므로, "열을 붙였으니 걸러지겠지"라는 기대가 그대로 빗나간다. 이 제약은 소스의 할 일 주석이 말하듯 구현의 제약이므로, 버전을 올린 뒤에는 같은 쿼리의 계획을 다시 확인할 가치가 있다.

    지표를 읽는 습관도 바뀌어야 한다. ICP가 걸리면 Handler_read_next와 Rows_examined가 줄어 쿼리가 덜 읽은 것처럼 보이지만, 엔진은 같은 항목을 확인하고 있다. 반대로 커버링 쿼리는 Handler 카운터가 크게 나와도 클러스터형 조회가 하나도 없을 수 있다. 성능 회의에서 "읽은 행 수"를 근거로 말할 때는 그 숫자를 어느 계층에서 셌는지를 함께 밝혀야 오해가 생기지 않는다. 버퍼 풀이 테이블보다 작은 운영 환경에서는 조회 수의 차이가 곧 랜덤 I/O의 차이이므로, 실측에서는 Innodb_buffer_pool_reads의 증가분까지 보는 것이 좋다.

    인덱스를 고를 때는 화면의 쿼리 하나가 아니라 패턴을 본다. 가격 필터가 주로 넓게 쓰이는지 좁게 쓰이는지, 데이터가 앞으로 10배가 되는지에 따라 내림차순 인덱스와 ICP, price를 앞에 둔 범위 인덱스, 지연 조인 가운데 맞는 답이 달라졌다. 개발 환경의 작은 데이터에서는 거의 모든 계획이 빠르므로, 운영 규모로 키운 데이터에서 예측표를 먼저 만들고 측정으로 확인하는 절차를 남겨 두자. 스킵 스캔은 인덱스를 하나 덜 만들게 해 주는 안전망으로 여기고, 자주 도는 쿼리는 그 쿼리를 위한 인덱스로 처리한다. 인덱스를 늘리고 줄이는 운영상의 판단은 09회에서 이어진다.

(다) created_at >= '2023-12-01' AND created_at < '2024-01-01'로 고치면 created_at이 구간에 쓰여 range 접근(key_len 9)이 되고, 읽는 항목 자체가 446개로 준다. 다만 이것은 이 데이터에 12월이 한 번뿐이라서 같은 뜻이 된 것이다. 일반적으로 MONTH()=12는 모든 해의 12월이므로 해마다 하나씩 여러 구간으로 바꿔 써야 하고, 해의 범위를 알 수 없다면 고쳐 쓸 수 없다. 그때는 ICP나 함수 기반 인덱스(09회)가 선택지다.

    2. 8.4 소스에서 잠금 읽기는 세컨더리 인덱스 레코드에 잠금을 건 뒤 ICP를 확인한다. 따라서 ICP가 켜져 있으면 카테고리 7의 세컨더리 인덱스 레코드 1만 개에 모두 잠금이 걸리고, ICP를 통과한 2,866개만 클러스터형 인덱스로 가므로 클러스터형 레코드 잠금은 2,866개다. REPEATABLE READ에서 try_unlock()은 아무 일도 하지 않으므로 불일치 7,134개의 세컨더리 레코드 잠금도 남는다. ICP를 끄면 1만 개 모두 클러스터형 인덱스까지 방문하므로 클러스터형 레코드에도 1만 개의 잠금이 걸린 뒤 서버가 걸러 낸다. READ COMMITTED라면 ICP 불일치로 판정된 레코드에 대해 방금 건 잠금을 푸는 "작은 롤백"이 일어난다. 어느 경우든 잠금의 범위를 근본적으로 줄이는 것은 구간을 좁히는 인덱스이지 ICP가 아니다.

    3. a가 등치로 고정되고 ORDER BY b DESC, c DESC를 인덱스 역순으로 얻는 역방향 ref 접근이다. 8.4 소스의 push_index_cond()는 역방향 접근이면 시작하자마자 돌아가므로, d가 인덱스 안에 있어도 d 조건은 ICP로 내려가지 않고 행을 가져온 뒤 서버가 확인한다(Using where). 첫째 방법은 내림차순 인덱스로 정방향 읽기를 만드는 것이다. ALTER TABLE t ADD INDEX idx_x_desc (a, b DESC, c DESC, d)를 만들면 같은 순서를 정방향으로 얻으므로 d 조건이 ICP로 내려가고, 클러스터형 조회는 LIMIT 10 수준으로 준다. 둘째 방법은 지연 조인이다. SELECT t2.a, t2.b, t2.c, t2.e FROM (SELECT id, b, c FROM t WHERE a = 1 AND d > 100 ORDER BY b DESC, c DESC LIMIT 10) AS k JOIN t AS t2 ON t2.id = k.id ORDER BY k.b DESC, k.c DESC처럼 쓰면(id는 기본 키) 안쪽은 idx_x만으로 처리되는 커버링 역방향 스캔이 되고, e를 위한 조회는 10번뿐이다. 어느 방법이든 읽는 인덱스 항목 수는 d > 100을 만족하는 항목이 정렬 순서의 어디에 있느냐에 달려 있다.

    4. (가) 쓰일 수 있다. A는 비어 있고 B가 status, C가 ordered_at이며, 쿼리가 쓰는 열이 모두 인덱스에 있다. 다섯 상태마다 구간을 읽는다. (나) 쓰일 수 없다. amount가 인덱스에 없어 커버링이 아니다(query_references_nonkey_column). (다) 쓰일 수 없다. GROUP BY가 있다(has_group_by). 그룹별로 건너뛰며 읽는 일은 12회의 루스 인덱스 스캔의 영역이다. (라) 스킵 스캔이 필요 없다. status가 IN의 상수로 주어졌으므로 ('PAID', 날짜 이후)와 ('SHIPPED', 날짜 이후) 두 구간을 만드는 평범한 range 접근이 가능하다. 04회에서 본 대로 IN은 등치의 OR이다.

(가) 매뉴얼에 따르면 파생 테이블의 ORDER BY는 그 파생 테이블이 바깥 FROM 절의 유일한 원천일 때 등의 조건에서만 바깥으로 전파되고, 그 밖에는 무시된다. 이 쿼리의 바깥에는 조인이 있으므로 결과 순서가 보장되지 않는다. 지금 실행에서 우연히 최신순으로 나오더라도 계획이 바뀌면 순서가 바뀔 수 있다. 안쪽의 ORDER BY는 어느 20개를 고를지 정할 뿐이다. (나) name은 인덱스에 없으므로 안쪽 쿼리가 커버링이 아니게 된다. 안쪽은 1,894개 항목을 읽으며 항목마다 클러스터형 조회를 하게 되고, 역방향 ref라서 ICP도 시도되지 않는다. 바깥 조회 20번이 더해져 오히려 지연 조인 전보다 나빠진다. 지연 조인의 안쪽은 반드시 커버링이어야 한다.

     EXPLAIN의 Extra에 Using index condition이 표시되었다. 이 표시에 대한 설명으로 가장 정확한 것은? 쿼리에 필요한 열이 모두 인덱스에 있어 클러스터형 인덱스를 읽지 않는다. 조건의 일부가 엔진으로 내려가, 인덱스 항목에서 그 조건에 맞지 않는 것은 클러스터형 인덱스 조회 없이 버려진다. 조건이 인덱스의 구간을 좁히는 데 쓰였으므로 key_len이 그 열만큼 늘어난다. ICP가 인덱스 항목의 상당수를 걸러 냈다는 뜻이므로 효과가 보장된다. Using index condition은 ICP가 쓰였다는 표시로, 인덱스 열만 참조하는 조건을 엔진이 클러스터형 조회 전에 확인한다는 뜻이다. 0번은 Using index(커버링)의 설명이며, 커버링이면 ICP가 시도되지 않는다. 2번은 틀렸다. ICP로 확인한 열은 구간을 정하는 데 쓰이지 않으므로 key_len에 들어가지 않는다. 3번도 틀렸다. range 접근에서는 구간을 만든 조건 자체가 내려가 걸러지는 항목이 없는 경우가 흔하므로, 효과는 icp 카운터로 확인해야 한다. ICP가 걸린 쿼리의 EXPLAIN ANALYZE에서 인덱스 접근 노드의 rows가 20으로 나왔다. 엔진이 실제로 확인한 인덱스 항목 수를 알려면 무엇을 봐야 하는가? 같은 노드의 rows 값 20이 곧 확인한 항목 수다. Handler_read_next와 Handler_read_key의 합 슬로 쿼리 로그의 Rows_examined INNODB_METRICS에서 켜 둔 icp_match와 icp_no_match의 증가분 ICP가 걸러 낸 항목은 엔진 안의 루프에서 다음 항목으로 넘어가고 핸들러 경계를 넘지 않는다. 그래서 EXPLAIN ANALYZE의 rows, Handler 카운터, 서버 계층이 센 Rows_examined는 모두 ICP를 통과한 행만 반영한다. 엔진 안에서 확인한 항목은 icp 모듈의 카운터를 켜야 볼 수 있다. icp_match가 통과한 수, icp_no_match가 걸러진 수다. MySQL 8.4에서 (category_id, status, created_at, price) 인덱스를 만들고 WHERE category_id = 7 AND status = 'ON_SALE' AND price BETWEEN … ORDER BY created_at DESC LIMIT 20을 실행했더니 Extra가 Using where; Backward index scan이고 Using index condition이 없었다. 가장 직접적인 이유는? 내림차순 정렬을 위해 ref 접근을 역방향으로 읽게 되었고, 8.4는 역방향 접근에서 ICP를 시도하지 않는다. price가 범위 조건이라 ICP로 내려갈 수 없다. price가 인덱스의 마지막 열이라 ICP 대상이 아니다. LIMIT이 있는 쿼리에는 ICP가 쓰이지 않는다. 8.4 소스의 push_index_cond()는 역방향 접근이면 첫머리에서 돌아가고, ORDER BY를 처리하는 코드는 역방향 ref 이터레이터가 ICP와 잘 맞지 않는다는 주석과 함께 그렇게 표시한다. 범위 조건이나 마지막 열이라는 사실은 ICP를 막지 않는다. 오히려 구간을 좁히지 못하는 열이 ICP의 전형적인 대상이다. LIMIT도 ICP를 막지 않으며, 같은 쿼리를 내림차순 인덱스로 정방향으로 읽게 하면 Using index condition이 나타난다. 같은 테이블 접근에서 Using index와 Using index condition이 함께 표시되지 않는 이유로 옳은 것은? InnoDB는 커버링 인덱스에서 조건을 평가할 수 없기 때문이다. ICP는 클러스터형 인덱스에만 쓰이고 커버링은 세컨더리 인덱스에만 쓰이기 때문이다. 인덱스가 커버링이면 실행 계획이 키 읽기 모드를 켜고 ICP는 시도하지 않는데, 줄일 클러스터형 조회가 처음부터 없기 때문이다. EXPLAIN이 Extra 열에 한 가지 Using 표시만 출력하기 때문이다. 8.4 소스의 make_join_readinfo()는 사용하는 인덱스가 커버링이면 set_keyread(true)를 하고, 그렇지 않을 때만 push_index_cond()를 부른다. ICP의 목적이 행 전체를 읽는 조회를 줄이는 것이므로 커버링에서는 의미가 없다. 커버링에서 조건은 서버가 평가하며 Using where; Using index로 함께 표시된다. ICP는 InnoDB의 세컨더리 인덱스에만 쓰이고 클러스터형 인덱스에는 쓰이지 않는다. Extra에는 여러 표시가 함께 나올 수 있다. 인덱스 (category_id, created_at)만 있는 product 테이블에서 스킵 스캔이 쓰일 수 있는 쿼리는? SELECT COUNT(*), SUM(price) FROM product WHERE created_at >= '2024-11-18' SELECT product_id, created_at FROM product WHERE created_at >= '2024-11-18' SELECT category_id, COUNT(*) FROM product WHERE created_at >= '2024-11-18' GROUP BY category_id SELECT COUNT(*) FROM product WHERE created_at < '2023-01-08' OR created_at >= '2024-11-18' 1번은 product_id(세컨더리 인덱스에 붙은 기본 키)와 created_at만 쓰므로 커버링이고, 단일 테이블, GROUP BY 없음, created_at에 구간 하나짜리 범위 조건이라는 조건을 모두 만족한다. 0번은 price가 인덱스에 없어 커버링이 아니다. 2번은 GROUP BY가 있다. 3번은 created_at의 범위가 두 구간으로 나뉘어 8.4 소스가 range_predicate_too_complex로 거절한다.
    인덱스 컨디션 푸시다운(Index Condition Pushdown, ICP)
    WHERE 조건 중 인덱스 열만 참조하는 부분을 스토리지 엔진에 넘겨, 행 전체를 읽기 전에 인덱스 항목으로 확인하게 하는 MySQL의 최적화다.
    핸들러 인터페이스(handler interface)
    MySQL 서버 계층이 스토리지 엔진에 행 단위로 읽기·쓰기를 요청하는 함수 규약이다. index_read_map, index_next 같은 호출이 여기에 속하고 Handler_read_* 카운터가 이 호출을 센다.
    커버링 인덱스(covering index)
    쿼리가 그 테이블에서 쓰는 모든 열을 담고 있어 클러스터형 인덱스를 읽지 않고 답할 수 있는 인덱스다. InnoDB 세컨더리 인덱스에는 기본 키가 포함된다.
    키 읽기 모드(keyread)
    인덱스 항목에서 꺼낸 열만으로 행을 만들어 돌려주는 실행 방식이다. 인덱스가 커버링일 때 켜지며, 이때 ICP는 시도되지 않는다.
    지연 조인(deferred join)
    커버링 인덱스로 결과 행의 기본 키만 먼저 고르고, 고른 기본 키로 필요한 행을 나중에 가져오는 쿼리 작성 기법이다.
    인덱스 스킵 스캔(index skip scan)
    복합 인덱스의 선두 열에 조건이 없을 때 선두 열의 서로 다른 값마다 범위 스캔을 따로 하는 접근 방법이다. MySQL 8.0.13부터 지원한다.
    루스 인덱스 스캔(loose index scan)
    GROUP BY나 DISTINCT를 처리할 때 그룹마다 필요한 항목만 읽고 다음 그룹으로 건너뛰는 접근 방법이다. 스킵 스캔과 비슷하지만 그룹핑 쿼리에 쓰인다.
    미니 트랜잭션(mini-transaction, mtr)
    InnoDB가 페이지 래치와 리두 로그 기록을 묶어 처리하는 내부 작업 단위다. 사용자 트랜잭션과는 다른 개념이다.
    내림차순 인덱스(descending index)
    열 정의에 DESC를 붙여 키 값을 내림차순으로 저장하는 인덱스다. MySQL에서는 InnoDB의 B+Tree 인덱스가 지원하며, 내림차순 정렬을 정방향 스캔으로 얻게 해 준다.
