    이 회차의 질문: 조인의 비용은 "몇 번 찾아 들어가는가"로 정해진다

    관계형 데이터베이스는 정규화를 거쳐 데이터를 여러 테이블에 나눠 담고, 조회할 때 조인(join)으로 다시 붙인다. 나눠 담는 쪽의 이득, 즉 중복이 없고 갱신 이상이 생기지 않는다는 이득은 설계할 때 한 번 얻는다. 반면 다시 붙이는 비용은 조회할 때마다 치른다. 이 회차는 그 비용이 정확히 무엇으로 이루어지는지를 따진다.

    SQL로 쓴 조인은 집합 연산처럼 보인다. "두 테이블에서 조건을 만족하는 행 쌍의 집합"이라는 정의에는 순서도 반복도 없다. 그러나 MySQL의 실행기는 두 집합을 한꺼번에 들고 맞춰 보지 않는다. 한 테이블에서 행을 하나 꺼내고, 그 행과 짝이 될 행을 다른 테이블에서 찾아 들어간다. 그래서 조인의 비용은 거의 언제나 바깥에서 꺼낸 행의 수 × 안쪽에서 짝을 찾는 한 번의 비용이라는 곱으로 쓸 수 있다. 앞 회차들에서 단일 테이블 접근의 비용, 즉 풀 테이블 스캔·인덱스 레인지 스캔·클러스터형 인덱스 룩업이 각각 몇 페이지를 만지는지 세었다. 조인은 그 비용 앞에 곱셈이 하나 붙는 일이다.

    곱셈은 작은 낭비를 크게 키운다. 한 번에 몇 페이지만 더 읽는 비효율은 단일 행 조회에서는 보이지도 않지만, 그 접근이 바깥 루프에서 1만 번 반복되면 1만 배가 된다. 반대로 바깥 루프의 반복 횟수를 줄이거나 안쪽 접근을 한 단계 싸게 만들면 효과도 그만큼 곱해진다. 조인 튜닝이 결국 두 질문으로 모이는 이유다. 바깥 루프는 몇 번 도는가. 안쪽에서 한 번 찾을 때 몇 페이지를 만지는가.

    전반부에서는 MySQL이 조인을 실행하는 알고리즘을 바닥부터 세운다. 중첩 루프 조인(nested-loop join, NLJ)의 동작, 안쪽 테이블에 인덱스가 있을 때와 없을 때의 차이, 인덱스가 없을 때 MySQL 8.0이 쓰는 해시 조인(hash join), 그리고 어느 테이블을 바깥에 둘지 옵티마이저가 정하는 방식이다. 후반부에서는 회원별 주문 통계 쿼리 하나를 진단한다. 이 쿼리의 실행 계획은 겉보기에 흠잡을 데가 없다. 접근 유형은 ref이고 예상 행 수는 9다. 그런데도 느린 이유가 세컨더리 인덱스에서 클러스터형 인덱스로 되돌아가는 룩업에 숨어 있고, 그것을 커버링 인덱스로 걷어내는 과정을 끝까지 따라간다. 결과를 정렬하고 그룹을 만드는 단계의 최적화는 12회의 주제이므로 여기서는 조인까지만 다룬다.

    실습 스키마와 데이터: 한 회원의 주문이 흩어져 있게 만든다

    이 회차의 예제는 아래 두 테이블로 설명한다. 01회와 같은 방식으로 재귀 CTE를 써서 일련번호 n을 만들고 모든 열을 n의 식으로 채우므로, 행 수와 값은 누가 만들어도 똑같다. 인덱스는 데이터를 다 넣은 뒤에 붙인다. 테이블 이름은 01회와 같지만 구조가 다르므로 별도의 데이터베이스 join_lab에 만든다.

    CREATE DATABASE join_lab DEFAULT CHARACTER SET utf8mb4;
USE join_lab;

CREATE TABLE member (
  member_id BIGINT      NOT NULL,
  name      VARCHAR(50) NOT NULL,
  region    VARCHAR(20) NOT NULL,
  PRIMARY KEY (member_id)
) ENGINE = InnoDB;

CREATE TABLE orders (
  order_id   BIGINT       NOT NULL,
  member_id  BIGINT       NOT NULL,
  status     VARCHAR(20)  NOT NULL,
  amount     INT          NOT NULL,
  ordered_at DATETIME     NOT NULL,
  memo       VARCHAR(200) NULL,
  PRIMARY KEY (order_id)
) ENGINE = InnoDB;

SET SESSION cte_max_recursion_depth = 1000000;

INSERT INTO member (member_id, name, region)
WITH RECURSIVE seq (n) AS (
  SELECT 1 UNION ALL SELECT n + 1 FROM seq WHERE n < 100000
)
SELECT n,
       CONCAT('회원', LPAD(n, 6, '0')),
       CASE MOD(n, 10)
         WHEN 0 THEN '서울' WHEN 1 THEN '서울' WHEN 2 THEN '서울'
         WHEN 3 THEN '경기' WHEN 4 THEN '경기' WHEN 5 THEN '경기'
         WHEN 6 THEN '부산' WHEN 7 THEN '대구' WHEN 8 THEN '광주'
         ELSE '대전' END
FROM seq;

INSERT INTO orders (order_id, member_id, status, amount, ordered_at, memo)
WITH RECURSIVE seq (n) AS (
  SELECT 1 UNION ALL SELECT n + 1 FROM seq WHERE n < 1000000
)
SELECT n,
       MOD(n * 7919, 100000) + 1,
       IF(MOD(n, 7) = 0, 'CANCELED', 'DELIVERED'),
       (MOD(n, 97) + 1) * 1000,
       TIMESTAMP('2024-01-01') + INTERVAL n MINUTE,
       CONCAT('배송 메모 ', REPEAT('-', 100))
FROM seq;

ALTER TABLE orders
  ADD INDEX idx_orders_member  (member_id),
  ADD INDEX idx_orders_ordered (ordered_at);

ANALYZE TABLE member, orders;

    이 데이터에서 계산으로 확정되는 사실을 정리해 두자. 뒤의 모든 예제가 이 목록을 근거로 행 수를 맞힌다.

    • 회원은 100,000명이고, 지역은 회원 번호의 끝자리로 정해진다. 부산 회원은 끝자리가 6인 회원, 곧 6, 16, 26, …, 99996번의 정확히 10,000명이다.
    • 주문은 1,000,000건이고 주문의 회원 번호는 n × 7919를 100,000으로 나눈 나머지에 1을 더한 값이다. 7919는 소수이고 100,000 = 25 × 55와 서로소이므로, n을 100,000으로 나눈 나머지가 다르면 회원 번호도 다르다. 연속한 100,000개의 n은 모든 회원을 정확히 한 번씩 거치고, n이 1부터 1,000,000까지이므로 회원마다 주문이 정확히 10건이다. 부산 회원의 주문은 100,000건이다.
    • n과 n + 100000은 100,000으로 나눈 나머지가 같으므로 같은 회원의 주문이다. 즉 한 회원의 주문 10건은 주문 번호가 100,000씩 떨어져 있다. 6번 회원의 주문 번호는 88395, 188395, 288395, …, 988395이고, 16번 회원은 65185, 165185, …, 26번 회원은 41975, 141975, …이다. 회원 번호가 이웃해도 주문 번호는 서로 멀다.
    • 6번 회원의 주문 금액 합계는 460,000원, 16번은 578,000원, 26번은 405,000원이다. 회원마다 금액이 다르게 나오도록 금액은 n을 97로 나눈 나머지로 만들었다.
    • 주문 시각은 2024-01-01 00:01부터 1분씩 늦어진다. 1월과 2월(윤년)을 합하면 60일, 곧 86,400분이므로 2024-03-01 하루의 주문은 n이 86,400부터 87,839까지인 1,440건이다.
    • 상태는 n이 7의 배수일 때만 CANCELED이고 나머지는 DELIVERED다. 취소 주문은 142,857건이며, 회원마다 1건 또는 2건이다.

    주문 번호, 곧 기본 키는 시간 순서로 매겨지는데 회원 번호는 주문 번호와 무관하게 뒤섞여 있다. 실제 서비스의 주문 테이블도 대체로 이렇다. 주문은 들어온 순서대로 기본 키를 받고, 한 회원의 주문은 몇 달, 몇 년에 걸쳐 띄엄띄엄 들어온다. 클러스터형 인덱스는 기본 키 순서로 행을 저장하므로, 한 회원의 주문들은 클러스터형 인덱스 여기저기에 흩어져 있다. 이 성질이 후반부 진단의 핵심이다.

    조인의 동작 원리: 중첩 루프 조인(NLJ)

    MySQL 매뉴얼은 중첩 루프 조인을 이렇게 정의한다. 첫 번째 테이블에서 행을 한 번에 하나씩 읽고, 그 행을 다음 테이블을 처리하는 중첩된 루프에 넘긴다. 조인할 테이블이 남아 있는 만큼 이 과정을 반복한다. 바깥 루프의 테이블을 드라이빙 테이블(driving table), 그 안쪽에서 짝을 찾아 들어가는 테이블을 드리븐 테이블(driven table)이라고 부른다. 외부 테이블(outer table)과 내부 테이블(inner table)이라고도 한다. 아래 쿼리를 예로 들자.

    SELECT m.member_id, m.name, o.order_id, o.amount
FROM member m
JOIN orders o ON o.member_id = m.member_id
WHERE m.region = '부산';

    member를 드라이빙 테이블로 삼으면 실행은 다음 의사 코드와 같다.

    for each row m in member:                              -- 바깥 루프 (드라이빙)
    if m.region != '부산': continue                     -- 드라이빙 쪽 조건
    for each row o in orders where o.member_id = m.member_id:   -- 안쪽 루프 (드리븐)
        send (m.member_id, m.name, o.order_id, o.amount) to client

    한 줄씩 따라가 보자. 바깥 루프가 1번 회원을 꺼낸다. 지역이 서울이므로 안쪽 루프에 들어가지 않고 다음 행으로 넘어간다. 2번부터 5번 회원도 마찬가지다. 6번 회원은 부산이므로 안쪽 루프가 시작된다. 안쪽 루프는 orders에서 회원 번호가 6인 주문을 찾아 88395번, 188395번, …, 988395번 주문을 차례로 내놓고, 그때마다 결합된 행이 하나씩 클라이언트 쪽으로 흘러간다. 10건을 다 내놓으면 안쪽 루프가 끝나고 바깥 루프는 7번 회원으로 넘어간다. 이렇게 100,000명을 다 훑으면 안쪽 루프는 부산 회원 수만큼, 곧 10,000번 시작되고 결과는 100,000행이 된다.

    이 실행에는 세 가지 성질이 있다. 첫째, 안쪽 루프가 시작되는 횟수는 드라이빙 쪽 조건을 통과한 행의 수다. 드라이빙 테이블 전체 행 수가 아니다. 그래서 드라이빙 쪽 조건은 조인 전에 최대한 먼저 적용되어야 하고, MySQL 옵티마이저도 한 테이블만 참조하는 조건을 그 테이블을 읽는 단계로 밀어 넣는다. 둘째, 결합된 행은 만들어지는 즉시 위로 흘러간다. 중간 결과를 어딘가에 모아 두지 않으므로 필요한 메모리가 일정하고, 첫 행이 빨리 나온다. 03회에서 본 것처럼 LIMIT이 있으면 필요한 행 수가 채워지는 순간 바깥 루프까지 멈출 수 있다. 셋째, 드리븐 테이블은 여러 번 읽힌다. 매뉴얼도 NLJ가 바깥 루프에서 안쪽 루프로 행을 하나씩 넘기므로 안쪽 루프에서 처리하는 테이블을 대개 여러 번 읽는다고 적고 있다. 이 셋째 성질 때문에 드리븐 쪽 한 번의 접근 비용이 전체 비용을 좌우한다.

    드라이빙 테이블의 행이 위에서 아래로 하나씩 꺼내지고, 조건을 통과한 행마다 드리븐 테이블의 인덱스로 화살표가 내려가 짝을 찾는 반복 구조를 보여 준다. 왼쪽에 세로로 긴 표 "member (드라이빙)"을 그리고 행 여섯 개에 "1 서울", "2 서울", "…", "6 부산", "…", "16 부산"을 적는다. 부산 행 두 개만 진한 색으로 강조한다. 오른쪽에 B+Tree 모양의 삼각형 "orders.idx_orders_member (드리븐)"을 그린다. 강조된 "6 부산" 행에서 오른쪽 트리의 루트로 화살표를 긋고, 화살표가 루트에서 리프로 내려가 "member_id = 6 항목 10개"라는 묶음에 닿게 한다. "16 부산" 행에서도 같은 모양의 두 번째 화살표를 긋는다. 서울 행 옆에는 회색 글씨로 "조건 불통과: 안쪽 루프 없음"을 적는다. 그림 아래에 큰 글씨로 "비용 = 조건 통과 행 수 × 드리븐 1회 탐색 비용"이라는 수식을 넣는다. 배경은 흰색, 선은 단순한 평면 스타일. 드라이빙 쪽 조건을 통과한 행 하나가 드리븐 쪽 탐색 한 번을 일으킨다. 조인 비용은 이 반복의 횟수와 한 번의 비용을 곱한 것이다.

    테이블이 셋 이상이면 루프가 한 겹씩 더 중첩된다. 매뉴얼의 예처럼 t1은 범위 접근, t2는 참조 키 접근, t3은 풀 스캔으로 읽는 조인이라면, t1에서 범위에 맞는 행 하나를 꺼낼 때마다 t2에서 키가 맞는 행들을 찾고, 그 조합 하나마다 다시 t3을 훑는다. 02회에서 EXPLAIN의 행 순서가 이 중첩 순서와 같다고 했다. 같은 id를 가진 행들은 위에서 아래로, 바깥 루프에서 안쪽 루프 순서로 읽는다.

    반복 횟수는 EXPLAIN에서 곱셈으로 읽어 낸다. 매뉴얼은 rows가 살펴볼 것으로 예상하는 행 수이고, rows × filtered가 다음 테이블과 조인될 행 수라고 설명한다. 그러므로 어떤 테이블의 접근이 몇 번 반복되는지는 그보다 위에 있는 모든 행의 rows × filtered / 100을 곱한 값이다. 위 쿼리에서 member 행이 rows 100,000, filtered 10.00으로 예상되었다면 orders의 접근은 약 10,000번 반복될 것으로 예상된 것이다. orders 행의 rows가 10이라는 것은 "한 번 찾아 들어갈 때 10행"이라는 뜻이지 "전부 해서 10행"이라는 뜻이 아니다. EXPLAIN ANALYZE에서는 같은 곱이 실측으로 나온다. 03회에서 본 것처럼 안쪽 이터레이터의 rows는 한 번 실행할 때의 평균이고 loops가 실행 횟수이므로, 둘을 곱해야 그 단계에서 처리한 전체 행 수가 된다.

    비용을 식으로 적어 두자. 드라이빙 테이블을 읽는 비용을 Couter, 드라이빙 쪽 조건을 통과한 행 수를 N, 드리븐 테이블에서 짝을 한 번 찾는 비용을 Cinner라고 하면 두 테이블 NLJ의 비용은 대략 Couter + N × Cinner다. 조인 최적화의 거의 모든 기법은 이 식의 어느 항을 줄이는가로 분류할 수 있다. 드라이빙 쪽을 인덱스로 좁히는 것은 Couter와 N을 줄이고, 드리븐 쪽에 인덱스를 두는 것은 Cinner를 줄이고, 조인 순서를 바꾸는 것은 N과 Cinner의 조합 자체를 바꾼다.

    이 식이 실제로 어떤 차이를 만드는지 작은 자바 모형으로 세어 보자. 아래 코드는 MySQL의 구현이 아니다. 회원 1,000명과 주문 10,000건을 메모리에 만들고, 조인 방식마다 "몇 번 비교했는가", "몇 번 찾아 들어갔는가"만 센다. TreeMap은 B+Tree가 아니라 레드블랙 트리지만 "정렬된 키로 찾아 들어간다"는 점만 흉내 내면 충분하다. 회원 번호 공식은 위 SQL과 같은 모양이고, 7919가 1,000과 서로소이므로 회원마다 주문이 정확히 10건이다.

    import java.util.*;

public class JoinDemo {
    record Member(long id, String name, String region) {}
    record Order(long id, long memberId, int amount) {}

    public static void main(String[] args) {
        int memberCount = 1_000, orderCount = 10_000;

        List members = new ArrayList<>();
        for (long n = 1; n <= memberCount; n++) {
            members.add(new Member(n, "회원" + n, n % 10 == 6 ? "부산" : "기타"));
        }
        // 클러스터형 인덱스 흉내: 주문 번호(PK) 순서로 정렬된 맵
        TreeMap clustered = new TreeMap<>();
        for (long n = 1; n <= orderCount; n++) {
            clustered.put(n, new Order(n, (n * 7919) % memberCount + 1, (int) (n % 97 + 1) * 1000));
        }

        // 1) 인덱스 없는 NLJ: 드라이빙 행마다 orders 전체를 훑는다
        long compares = 0, sum1 = 0;
        for (Member m : members) {
            if (!m.region().equals("부산")) continue;
            for (Order o : clustered.values()) {
                compares++;
                if (o.memberId() == m.id()) sum1 += o.amount();
            }
        }
        System.out.printf("NLJ(인덱스 없음)   비교 %,d회, 합계 %,d%n", compares, sum1);

        // 2) 세컨더리 인덱스 NLJ: member_id -> [order_id...] 를 찾고, PK로 다시 클러스터형 인덱스를 찾는다
        TreeMap> secondary = new TreeMap<>();
        for (Order o : clustered.values()) {
            secondary.computeIfAbsent(o.memberId(), k -> new ArrayList<>()).add(o.id());
        }
        long indexLookups = 0, pkLookups = 0, sum2 = 0;
        for (Member m : members) {
            if (!m.region().equals("부산")) continue;
            indexLookups++;
            for (long orderId : secondary.getOrDefault(m.id(), List.of())) {
                pkLookups++;
                sum2 += clustered.get(orderId).amount();
            }
        }
        System.out.printf("NLJ(세컨더리)      인덱스 탐색 %,d회, PK 룩업 %,d회, 합계 %,d%n", indexLookups, pkLookups, sum2);

        // 3) 커버링 인덱스 NLJ: 인덱스 항목에 amount 가 들어 있어 PK 룩업이 없다
        TreeMap> covering = new TreeMap<>();
        for (Order o : clustered.values()) {
            covering.computeIfAbsent(o.memberId(), k -> new ArrayList<>()).add(o.amount());
        }
        long coverLookups = 0, sum3 = 0;
        for (Member m : members) {
            if (!m.region().equals("부산")) continue;
            coverLookups++;
            for (int amount : covering.getOrDefault(m.id(), List.of())) sum3 += amount;
        }
        System.out.printf("NLJ(커버링)        인덱스 탐색 %,d회, PK 룩업 0회, 합계 %,d%n", coverLookups, sum3);

        // 4) 해시 조인: 걸러낸 member 로 해시 테이블을 만들고(빌드), orders 를 한 번 훑으며 찾는다(프로브)
        Map hash = new HashMap<>();
        for (Member m : members) {
            if (m.region().equals("부산")) hash.put(m.id(), m);
        }
        long probes = 0, matches = 0, sum4 = 0;
        for (Order o : clustered.values()) {
            probes++;
            if (hash.containsKey(o.memberId())) { matches++; sum4 += o.amount(); }
        }
        System.out.printf("해시 조인          빌드 %,d행, 프로브 %,d회, 일치 %,d행, 합계 %,d%n", hash.size(), probes, matches, sum4);
    }
}
    NLJ(인덱스 없음)   비교 1,000,000회, 합계 48,956,000
NLJ(세컨더리)      인덱스 탐색 100회, PK 룩업 1,000회, 합계 48,956,000
NLJ(커버링)        인덱스 탐색 100회, PK 룩업 0회, 합계 48,956,000
해시 조인          빌드 100행, 프로브 10,000회, 일치 1,000행, 합계 48,956,000

    네 방식 모두 같은 답을 낸다. 부산 회원은 100명이고 각자 주문이 10건이므로 일치하는 행은 1,000개다. 다른 것은 답에 이르는 일의 양이다. 인덱스 없는 NLJ는 100명 × 10,000건 = 1,000,000번 비교한다. 세컨더리 인덱스를 쓰는 NLJ는 인덱스를 100번 찾아 들어가지만, 찾은 항목에는 주문 번호만 있으므로 금액을 얻으려고 기본 키로 다시 1,000번 찾아 들어간다. 커버링 인덱스는 이 두 번째 룩업을 없앤다. 해시 조인은 걸러낸 회원 100명으로 해시 테이블을 만든 뒤 주문 10,000건을 한 번씩만 훑는다. 이 네 줄이 이 회차 전체의 지도다. 지금부터 각 줄이 InnoDB 안에서는 어떤 페이지 접근이 되는지 하나씩 내려가 본다.

    NLJ와 인덱스: 드리븐 테이블의 생명줄

    먼저 드리븐 테이블의 조인 열에 인덱스가 없다고 해 보자. 의사 코드의 안쪽 루프 for each row o in orders where o.member_id = m.member_id를 실행할 방법이 테이블 전체를 훑는 것밖에 없다. 실습 데이터라면 부산 회원 10,000명 각각에 대해 orders 1,000,000행을 훑는다. 비교 횟수는 10,000 × 1,000,000 = 100억 번이고, 가정한 크기로 페이지를 세면 10,000번 × 리프 10,000페이지 = 1억 번의 페이지 접근이다. 버퍼 풀에 다 들어 있다 해도 감당할 수 없는 양이다. 이 단순한 형태의 NLJ는 드리븐 테이블이 아주 작을 때가 아니면 쓸모가 없고, 실제로 MySQL은 이런 경우에 다른 알고리즘으로 바꾼다. 그 이야기는 다음 절에서 한다.

    드리븐 테이블의 조인 열에 인덱스가 있으면 안쪽 루프 한 번이 "B+Tree를 루트에서 리프까지 내려가 키가 같은 항목들을 읽는 일"로 바뀐다. 05회에서 본 것처럼 B+Tree의 높이는 데이터가 크게 늘어도 거의 늘지 않는다. 가정한 idx_orders_member는 높이 3이므로 한 번 찾아 들어갈 때 루트, 중간 노드, 리프 세 페이지를 만지고, 한 회원의 항목 10개는 (member_id, order_id) 순으로 붙어 있으므로 대개 리프 한 페이지 안에서 끝난다. Cinner가 "테이블 전체"에서 "페이지 세 개 남짓"으로 줄어든 것이다. 같은 10,000번 반복이라도 1억 번의 페이지 접근이 3만 번 남짓이 된다. 드리븐 테이블의 조인 열 인덱스를 "생명줄"이라고 부르는 이유가 이 차이다.

    EXPLAIN은 드리븐 쪽 인덱스 접근을 두 가지 유형으로 보여 준다. 매뉴얼의 정의를 옮기면 이렇다.

    type뜻이 회차의 예
    eq_ref앞 테이블들의 행 조합 하나마다 이 테이블에서 한 행만 읽는다. 조인이 인덱스의 모든 부분을 쓰고, 그 인덱스가 PRIMARY KEY이거나 UNIQUE NOT NULL일 때 쓰인다.orders가 드라이빙이고 member를 기본 키로 찾을 때
    ref앞 테이블들의 행 조합 하나마다 인덱스 값이 일치하는 모든 행을 읽는다. 키의 왼쪽 접두사만 쓰거나, 키가 기본 키나 유니크 인덱스가 아닐 때 쓰인다.member가 드라이빙이고 orders를 idx_orders_member로 찾을 때

    eq_ref는 "찾으면 반드시 한 행"이므로 첫 행을 찾는 즉시 그 탐색을 끝낼 수 있다. ref는 일치하는 행이 몇 개일지 모르므로 다음 항목의 키가 달라질 때까지 리프를 따라 읽는다. 어느 쪽이든 EXPLAIN의 ref 열에는 인덱스에 대 본 값의 출처가 나온다. 드라이빙 테이블의 열이면 join_lab.m.member_id처럼 데이터베이스·테이블·열 이름이, 상수면 const가, 식의 결과면 func가 나온다.

    인덱스는 어느 쪽에 있어야 하는가

    조인 조건 o.member_id = m.member_id는 대칭으로 보이지만 인덱스의 쓸모는 대칭이 아니다. 안쪽 루프에서 "찾아 들어가는" 쪽, 곧 드리븐 테이블의 조인 열에 인덱스가 있어야 Cinner가 줄어든다. 드라이빙 테이블의 조인 열은 바깥 루프에서 순서대로 읽어 나가는 값일 뿐이므로, 거기에 인덱스가 있어도 이 조인의 반복 비용은 줄지 않는다. 회원과 주문 같은 일대다 관계에서 member.member_id는 기본 키라서 언제나 인덱스가 있다. 그래서 orders가 드라이빙이 되는 계획은 늘 eq_ref를 쓸 수 있다. 반대로 member가 드라이빙이 되는 계획은 orders.member_id에 인덱스가 있어야만 성립한다. 01회에서 언급했듯이 MySQL은 외래 키를 선언할 때 참조하는 쪽 열에 인덱스가 없으면 자동으로 만든다. 외래 키를 선언하지 않는 설계라면 이 인덱스를 직접 챙겨야 한다.

    조인 열의 인덱스를 무력하게 만드는 조건

    인덱스가 있어도 조인 조건의 모양 때문에 인덱스로 찾아 들어가지 못하는 경우가 있다. 04회에서 단일 테이블 조건이 범위를 만들지 못하는 경우를 보았는데, 조인 조건도 원리가 같다. 인덱스로 찾으려면 드리븐 쪽 인덱스 열이 변형되지 않은 채로 비교되어야 하고, 비교하는 값이 그 열의 정렬 순서와 같은 규칙으로 비교될 수 있어야 한다.

    • 타입이 다른 열끼리의 비교. 매뉴얼은 문자열 열과 숫자 열처럼 서로 다른 종류의 열을 비교하면 변환 없이 직접 비교할 수 없어 인덱스 사용이 막힐 수 있다고 설명한다. 숫자 1은 문자열 '1', ' 1', '00001'과 모두 같다고 비교될 수 있으므로, 문자열 열의 인덱스에서 한 구간으로 찾아 들어갈 수 없다. 회원 번호를 한 테이블은 BIGINT, 다른 테이블은 VARCHAR로 저장하는 설계가 위험한 이유다.
    • 문자 집합이 다른 문자열 열. 매뉴얼은 비이진 문자열 열끼리 비교할 때 두 열이 같은 문자 집합을 써야 한다고 하고, utf8mb4 열과 latin1 열을 비교하면 인덱스를 쓸 수 없다고 예를 든다. 매뉴얼은 또 같은 타입과 크기로 선언된 열끼리 조인할 때 인덱스를 더 효율적으로 쓸 수 있다고 적는다.
    • 드리븐 쪽 열에 씌운 함수나 연산. ON DATE(o.ordered_at) = d.day처럼 드리븐 쪽 열을 변형하면 인덱스의 정렬 순서로 찾아 들어갈 수 없다. 반면 변형이 드라이빙 쪽 값에만 걸려 있으면 그 결과를 계산해 인덱스에 대 보면 되므로 인덱스를 쓸 수 있고, 이때 EXPLAIN의 ref 열에 func가 보인다.

    드리븐 쪽에 조인 조건 말고 다른 조건도 있다면 복합 인덱스로 함께 처리할 수 있다. 예를 들어 ON o.member_id = m.member_id AND o.status = 'DELIVERED'라면 (member_id, status) 인덱스에서 두 열이 모두 등치로 비교되므로 한 번의 탐색으로 두 조건을 만족하는 항목 구간에 바로 들어간다. 이때 ref 열에는 join_lab.m.member_id,const가 나오고, key_len은 BIGINT NOT NULL 8바이트와 VARCHAR(20) NOT NULL utf8mb4의 20 × 4 + 2 = 82바이트를 더한 90이 된다. MySQL 8.4.13과 8.0.46에서 실습 데이터에 (member_id, status) 인덱스를 만들어 확인하면 두 버전 모두 o 행이 ref, key_len 90, ref 열이 m_db_perf_11.m.member_id,const(실습 서버의 데이터베이스 이름)로 나온다. 조인 조건도 결국 "앞 테이블에서 온 상수"와의 등치 비교이므로, 04회의 열 순서 원칙(등치 조건 열을 앞에, 범위 조건 열을 뒤에)이 그대로 적용된다.

    블록 중첩 루프에서 해시 조인으로: 인덱스가 없을 때

    드리븐 테이블에 쓸 인덱스가 없다면 반복마다 테이블을 다시 훑는 것을 피해야 한다. MySQL 8.0.18 이전에 쓰던 답은 블록 중첩 루프(Block Nested-Loop, BNL) 조인이었다. 매뉴얼의 설명은 이렇다. 바깥 루프에서 읽은 행들을 조인 버퍼(join buffer)에 모아 두었다가, 버퍼가 차면 안쪽 테이블을 한 번 훑으면서 읽은 행 하나를 버퍼에 든 모든 행과 비교한다. 행 10개를 버퍼에 담으면 안쪽 테이블을 읽는 횟수가 한 자릿수 줄어든다. 조인 버퍼에는 행 전체가 아니라 조인에 필요한 열만 담기고, 버퍼 크기는 join_buffer_size가 정한다. 버퍼에 담긴 조합 하나의 크기가 S, 조합의 수가 C일 때 안쪽 테이블을 훑는 횟수는 매뉴얼의 식으로 (S × C) / join_buffer_size + 1이다.

    BNL은 디스크 읽기를 줄이지만 비교 횟수는 줄이지 못한다. 안쪽 테이블의 행 하나를 버퍼의 모든 행과 하나씩 비교하므로, 부산 회원 10,000명과 주문 1,000,000건을 BNL로 조인하면 테이블을 훑는 횟수는 몇 번으로 줄어도 비교는 여전히 100억 번이다. 이 한계를 해결한 것이 해시 조인이다. 버퍼에 담은 행들을 조인 키로 해시 테이블에 넣어 두면, 안쪽 테이블의 행 하나에 대해 버퍼 전체를 훑는 대신 해시 값으로 한 칸만 들여다보면 된다.

    버전별 경과는 매뉴얼에 다음과 같이 정리되어 있다. 이 차이는 같은 8.0 안에서도 마이너 버전에 따라 실행 계획이 달라진다는 뜻이므로 정확히 알아 두어야 한다.

    버전변화
    8.0.18각 조인에 등치 조건이 있고 조인 조건에 쓸 인덱스가 없는 쿼리에 해시 조인을 쓴다. 이 버전에서만 optimizer_switch의 hash_join 플래그와 HASH_JOIN, NO_HASH_JOIN 힌트가 동작했다.
    8.0.19hash_join 플래그와 HASH_JOIN·NO_HASH_JOIN 힌트가 더 이상 효과가 없다.
    8.0.20블록 중첩 루프를 더 이상 쓰지 않고, 예전에 BNL을 쓰던 모든 경우에 해시 조인을 쓴다. 등치 조건이 없는 내부 조인, 외부 조인, 세미조인, 안티조인에도 해시 조인을 쓴다. 해시 조인 여부는 BNL·NO_BNL 힌트나 optimizer_switch의 block_nested_loop 플래그로 켜고 끈다.

    빌드 단계와 프로브 단계

    해시 조인은 두 단계로 실행된다. 빌드 단계(build phase)에서는 한쪽 입력의 행을 모두 읽어 조인 열을 키로 하는 메모리 해시 테이블에 넣는다. 이쪽을 빌드 입력(build input)이라고 한다. MySQL 공식 블로그의 해시 조인 소개 글은 서버가 두 입력 중 행 수가 아니라 바이트로 잰 크기가 작은 쪽을 빌드 입력으로 고르는 것이 이상적이라고 설명한다. 해시 테이블에 담기는 것은 행 전체가 아니라 필요한 열뿐이므로 행 수와 바이트 크기는 다를 수 있다. 프로브 단계(probe phase)에서는 다른 쪽 입력, 곧 프로브 입력(probe input)을 한 행씩 읽으면서 그 행의 조인 열 값으로 해시 테이블을 찾고, 일치하는 행이 있으면 결합된 행을 내보낸다. 결과적으로 두 입력을 각각 한 번씩만 읽고, 짝을 찾는 일은 해시 테이블 조회 한 번으로 끝난다.

    빌드 단계                                 프로브 단계

member (region = '부산'인 10,000행)        orders (1,000,000행을 처음부터 끝까지 한 번)
   │ 조인 키 member_id 로 해시                 │ 행마다 o.member_id 로 해시
   ▼                                          ▼
┌───────────── 해시 테이블 ─────────────┐     ┌──────────────────────────┐
│ 버킷 a: 6 → (6, '회원000006')         │ ◀── │ o(88395, member_id=6)    │ → 일치: 내보냄
│ 버킷 b: 16 → (16, '회원000016')       │ ◀── │ o(1, member_id=7920)     │ → 없음: 버림
│ ...                                   │     │ ...                      │
└───────────────────────────────────────┘     └──────────────────────────┘
  join_buffer_size 안에서 메모리를 쓴다          첫 결과는 빌드가 끝나야 나온다

    이 구조에서 해시 조인의 성격이 바로 나온다. 첫째, 인덱스가 필요 없다. 양쪽을 한 번씩 순차로 읽기만 하면 된다. 둘째, 비용이 두 입력의 크기에 비례한다. 결과가 몇 행이든 프로브 입력은 처음부터 끝까지 읽힌다. 셋째, 빌드가 끝나기 전에는 결과가 한 행도 나오지 않는다. NLJ는 첫 짝을 찾는 즉시 내보내지만 해시 조인은 빌드 입력을 전부 읽어야 첫 프로브를 할 수 있다. 그래서 LIMIT 10처럼 앞의 몇 행만 필요한 쿼리에서는 NLJ의 조기 종료를 따라가지 못한다. 넷째, 해시 테이블은 같음만 찾을 수 있다. 해시 값은 크기 순서를 보존하지 않으므로 t1.c1 < t2.c1 같은 비등치 조건으로는 버킷을 고를 수 없다. 매뉴얼의 예에서 비등치 조인은 Inner hash join (no condition) 위에 Filter: (t1.c1 < t2.c1)가 얹힌 계획으로 나온다. 조건 없이 모든 조합을 만든 뒤 걸러 낸다는 뜻이다.

    메모리가 모자랄 때: 디스크로 넘치는 해시 조인

    해시 테이블의 크기는 join_buffer_size로 제한된다. 매뉴얼은 해시 조인이 이 값보다 많은 메모리를 쓸 수 없다고 하고, 이 변수의 기본값은 262,144바이트(256KB)다. 8.0.18부터 해시 조인용 버퍼는 필요한 만큼 점진적으로 할당되므로, 값을 크게 잡아도 작은 쿼리가 그만큼의 메모리를 한꺼번에 차지하지는 않는다. 빌드 입력이 이 한도를 넘으면 해시 조인은 디스크의 파일을 쓴다. 해시 조인이 도입된 8.0.18 무렵 공식 블로그가 설명한 과정은 다음과 같다.

    청크를 나눌 때와 해시 테이블에 넣을 때는 서로 다른 해시 함수를 쓴다. 같은 함수를 쓰면 한 청크 파일에 든 행들은 모두 같은 규칙으로 걸러져 들어온 것이므로, 그 청크를 해시 테이블에 다시 올릴 때 행들이 소수의 버킷에 몰려 해시 테이블이 극도로 나빠진다. 블로그의 설명이 바로 이 점이다. 넘침에는 두 가지 대가가 따른다. 하나는 디스크 쓰기와 다시 읽기의 비용이고, 다른 하나는 열린 파일 수다. 매뉴얼은 해시 조인이 open_files_limit보다 많은 파일을 만들게 되면 조인이 실패할 수 있다고 경고하고, 대책으로 join_buffer_size나 open_files_limit를 늘리는 방법을 든다. 실습 데이터로 감을 잡아 보자. 부산 회원 10,000명을 빌드 입력으로 삼으면 행마다 회원 번호 8바이트와 이름 문자열이 담긴다. 이름은 한글 두 글자(utf8mb4에서 글자당 3바이트)와 숫자 여섯 자리라 12바이트다. 자료만 세어도 10,000 × 20바이트 남짓, 곧 200KB 안팎이고 해시 테이블 자체의 부가 공간도 있으므로, 기본값 256KB 안에 다 들어간다고 장담할 수 없다. 빌드 입력이 작은 쪽이 되도록 조건을 먼저 걸러 내는 것이 해시 조인에서도 중요한 이유다.

    실행 계획에서 해시 조인 알아보기

    8.0.20부터는 전통 형식의 EXPLAIN에서도 해시 조인을 볼 수 있다. 매뉴얼의 예에서 t1 JOIN t2 ON t1.c1 = t2.c1(두 테이블 모두 인덱스 없음)의 두 번째 행은 type이 ALL이고 Extra가 Using where; Using join buffer (hash join)이다. 매뉴얼은 이 표시를 "앞선 조인의 테이블을 조인 버퍼에 나눠 읽고, 버퍼의 행으로 현재 테이블과 조인한다"고 설명한다. 즉 이 표시가 붙은 테이블이 프로브 쪽이고, 그보다 위의 테이블들이 버퍼(해시 테이블)에 담긴다. 트리 형식에서는 Inner hash join (t2.c1 = t1.c1) 아래에 두 자식이 나오고, Hash라는 노드 아래에 있는 쪽이 빌드 입력이다.

    -> Inner hash join (t2.c1 = t1.c1)  (cost=0.7 rows=1)
    -> Table scan on t2  (cost=0.35 rows=1)
    -> Hash
        -> Table scan on t1  (cost=0.35 rows=1)

    실습 쿼리에서 해시 조인을 일부러 보고 싶다면 조인 조건에 쓸 인덱스를 막으면 된다. 아래처럼 인덱스 힌트로 idx_orders_member를 무시하게 하면 orders에는 조인 조건에 쓸 인덱스가 남지 않는다. 이때 옵티마이저가 member를 먼저 읽는 순서를 고른다면 member가 빌드 입력, orders의 풀 스캔이 프로브 입력이 되고, orders 행의 Extra에 Using join buffer (hash join)이 붙는다. 실제로 어느 순서가 선택되었는지는 EXPLAIN으로 확인해야 하는데, 실습 데이터에서 확인해 보면 이 힌트만으로는 해시 조인이 나오지 않는다.

    EXPLAIN FORMAT=TREE
SELECT m.member_id, m.name, o.order_id, o.amount
FROM member m
JOIN orders o IGNORE INDEX (idx_orders_member) ON o.member_id = m.member_id
WHERE m.region = '부산';

-- 해시 조인 자체를 끄고 싶을 때(8.0.20 이상)
SELECT /*+ NO_BNL(o) */ ...

    MySQL 8.4.13과 8.0.46 모두 위 쿼리에 orders를 먼저 풀 스캔하고 행마다 member를 기본 키로 찾는 계획을 골랐다. 트리 형식으로는 Nested loop inner join 아래에 Table scan on o와 Single-row index lookup on m using PRIMARY (member_id=o.member_id)가 나오고, 전통 형식으로는 o가 ALL, m이 eq_ref다. idx_orders_member를 막아도 member 쪽에는 조인 조건에 쓸 기본 키가 남아 있으므로, 순서를 뒤집으면 인덱스를 쓰는 NLJ가 여전히 가능하기 때문이다. 해시 조인을 보려면 /*+ JOIN_ORDER(m, o) */를 더해 member를 먼저 읽게 하거나, member m IGNORE INDEX (PRIMARY)로 그 길까지 막아야 한다. 그러면 두 버전 모두 아래 계획이 나온다. 비용과 예상 행 수는 실행 환경과 통계에 따라 달라진다.

    -> Inner hash join (o.member_id = m.member_id)  (cost=990e+6 rows=99589)
    -> Table scan on o  (cost=6.64 rows=988856)
    -> Hash
        -> Filter: (m.region = '부산')  (cost=10152 rows=10008)
            -> Table scan on m  (cost=10152 rows=100082)

    Hash 아래의 member가 빌드 입력, orders의 풀 스캔이 프로브 입력이다. 같은 쿼리의 전통 형식 EXPLAIN에서는 o 행이 type ALL, Extra Using where; Using join buffer (hash join)으로 나온다. 여기에 NO_BNL(o)까지 주어 해시 조인을 끄면, 두 버전 모두 member의 부산 회원 행마다 orders를 풀 스캔하는 단순 NLJ(Filter: (o.member_id = m.member_id) 아래 Table scan on o)가 되고 비용 추정은 1.04e+9(8.0.46은 1.06e+9)로 뛴다.

    공식 블로그는 조인 조건에 쓸 인덱스가 있으면 MySQL이 인덱스 룩업을 쓰는 중첩 루프 쪽을 택하는 경향이 있다고 적고 있다. 두 알고리즘을 나란히 놓으면 왜 그런 선택이 합리적인지 보인다.

    드라이빙 테이블은 누가 정하는가

    내부 조인에서 FROM 절에 테이블을 쓴 순서는 실행 순서와 관계가 없다. MySQL에서 JOIN, CROSS JOIN, INNER JOIN은 문법적으로 같은 것이고(매뉴얼의 표현으로 서로 바꿔 쓸 수 있다), 내부 조인은 교환 법칙과 결합 법칙이 성립하므로 어느 테이블을 바깥에 두어도 결과는 같다. 그래서 순서는 옵티마이저가 정한다. 옵티마이저는 가능한 조인 순서들을 탐색하면서 순서마다 각 테이블의 접근 방법과 비용, 그리고 다음 테이블로 넘어갈 예상 행 수를 누적해 가장 싼 순서를 고른다. 앞 절의 식 Couter + N × Cinner를 테이블 수만큼 이어 붙여 비교하는 셈이다.

    탐색해야 할 순서의 수는 테이블 수의 계승으로 늘어난다. 테이블이 3개면 6가지, 5개면 120가지, 10개면 3,628,800가지다. 매뉴얼은 조인 쿼리에서 옵티마이저가 조사하는 계획의 수가 테이블 수에 따라 지수적으로 늘고, 테이블이 대략 7~10개보다 적으면 문제가 되지 않는다고 설명한다. 이 탐색을 조절하는 변수가 둘 있다. optimizer_prune_level(기본값 1)은 중간 계획이 읽을 행 수를 기준으로 가망 없는 부분 계획을 잘라 내는 휴리스틱을 켠다. 0으로 끄면 완전 탐색을 한다. optimizer_search_depth(기본값 62)는 탐색의 최대 깊이다. 쿼리의 테이블 수보다 크면 더 좋은 계획을 찾지만 계획을 만드는 데 오래 걸리고, 작으면 빨리 끝나지만 계획이 최적과 멀 수 있으며, 0이면 서버가 적당한 값을 고른다. 조인 테이블이 아주 많은 쿼리에서 실행보다 계획 수립에 시간이 더 걸리는 현상이 있다면 이 두 변수를 의심한다.

    비용 비교 1: 같은 쿼리, 두 가지 순서

    비용 비교 2: 큰 테이블이 드라이빙이 되는 경우

    이번에는 2024년 3월 1일 하루의 주문과 주문한 회원의 이름을 구하는 쿼리다.

    SELECT o.order_id, o.amount, m.name

    추정이 틀리면 순서가 틀린다

    옵티마이저의 비교는 실제 행 수가 아니라 통계로 추정한 행 수 위에서 이루어진다. 인덱스가 있는 열의 조건은 인덱스를 직접 살펴보거나 인덱스 통계로 비교적 잘 추정하지만, 인덱스도 히스토그램도 없는 열의 조건은 근거가 약한 추정에 기댄다. 조인에서 이 오차는 곱해진다. 첫 테이블의 통과 행 수를 2배 틀리면 둘째 테이블의 반복 횟수 추정도 2배 틀리고, 둘째 테이블의 통과율까지 2배 틀리면 셋째 테이블에서는 4배가 된다. 테이블이 많을수록 뒤쪽 추정은 실제와 크게 멀어질 수 있고, 그 결과로 좋지 않은 순서가 선택된다. EXPLAIN ANALYZE에서 예상 행 수와 실제 행 수가 크게 다른 단계를 찾는 03회의 방법, 그리고 인덱스가 없는 열의 분포를 옵티마이저에게 알려 주는 10회의 히스토그램이 바로 이 문제를 다루는 도구다.

    옵티마이저가 순서를 마음대로 바꾸지 못하는 경우

    순서 선택에는 제약도 있다. 첫째, EXPLAIN의 type이 system이나 const인 테이블은 일치하는 행이 많아야 하나라서 쿼리 시작 시점에 먼저 읽히고, 그 행의 값은 나머지 최적화에서 상수처럼 취급된다. 둘째, 외부 조인에는 의존 관계가 있다. 매뉴얼은 A LEFT JOIN B를 구현할 때 B가 A에 의존하도록 설정하고, 모든 표준 조인 최적화를 하되 테이블은 항상 자신이 의존하는 테이블들을 다 읽은 뒤에 읽는다고 설명한다. 즉 LEFT JOIN의 왼쪽 테이블이 오른쪽 테이블보다 먼저, 바깥 루프에 놓인다. 오른쪽 테이블에 아주 선택적인 조건이 있어도 왼쪽부터 읽어야 하므로 비효율적인 계획이 강제될 수 있다.

    그런데 이 제약이 풀리는 경우가 있다. 매뉴얼은 WHERE 조건이 널 거부(null-rejected) 조건이면 외부 조인을 내부 조인으로 바꾼다고 설명한다. 널 거부 조건이란 외부 조인이 만들어 낸 "NULL로 채운 행"에 대해 FALSE나 UNKNOWN이 되는 조건이다. 예를 들어 FROM member m LEFT JOIN orders o ON o.member_id = m.member_id WHERE o.status = 'CANCELED'에서 주문이 없는 회원의 행은 o.status가 NULL이므로 WHERE에서 반드시 탈락한다. 그렇다면 결과는 내부 조인과 같고, 옵티마이저는 이 쿼리를 내부 조인으로 바꾼 뒤 orders를 먼저 읽는 순서도 고려할 수 있다. 매뉴얼의 예도 변환 전에는 T1, T2, T3 순서만 평가하던 계획이 변환 후에는 T3, T1, T2 순서까지 고려하게 된다고 보여 준다.

    서브쿼리도 조인이 된다: 세미조인

    02회에서 DEPENDENT SUBQUERY는 바깥 행마다 서브쿼리를 다시 실행한다고 했다. 이것은 "바깥 쿼리를 드라이빙으로 고정한 NLJ"와 같은 모양이다. MySQL은 WHERE m.member_id IN (SELECT o.member_id FROM orders o WHERE ...) 같은 서브쿼리를 세미조인(semijoin)으로 변환해 이 고정을 푼다. 세미조인은 매뉴얼의 표현으로 준비 단계의 변환이고, 바깥 테이블의 행 중 서브쿼리와 짝이 맞는 행을 한 번씩만 돌려주는 연산이다. 일단 조인이 되면 옵티마이저는 서브쿼리 쪽 테이블을 드라이빙으로 두는 순서까지 비교할 수 있다. 문제는 일대다 관계에서 조인을 하면 바깥 행이 여러 번 나온다는 것이고, 이 중복을 어떻게 없애느냐에 따라 실행 전략이 갈린다.

    순서를 직접 지정하는 방법과 그 대가

    옵티마이저의 선택이 틀렸다고 확신할 때는 순서를 지정할 수 있다. t1 STRAIGHT_JOIN t2는 매뉴얼의 표현으로 JOIN과 같되 왼쪽 테이블을 항상 오른쪽 테이블보다 먼저 읽는다. SELECT STRAIGHT_JOIN은 FROM 절에 나열한 순서대로 모든 테이블을 조인한다. 8.0의 옵티마이저 힌트로는 더 세밀하게 지정할 수 있다.

    힌트뜻
    JOIN_FIXED_ORDER()FROM 절에 나온 순서대로 조인한다. SELECT STRAIGHT_JOIN과 같다.
    JOIN_ORDER(t1, t2, ...)지정한 테이블들을 그 순서로 조인한다. 지정하지 않은 테이블은 그 사이 어디에든 놓일 수 있다.
    JOIN_PREFIX(t1, t2, ...)지정한 테이블들을 계획의 맨 앞에 그 순서로 놓는다.
    JOIN_SUFFIX(t1, t2, ...)지정한 테이블들을 계획의 맨 뒤에 그 순서로 놓는다.
    SELECT /*+ JOIN_ORDER(o, m) */ o.order_id, o.amount, m.name
FROM member m
JOIN orders o ON o.member_id = m.member_id
WHERE o.ordered_at >= '2024-03-01' AND o.ordered_at < '2024-03-02';

    힌트에는 두 가지 함정이 있다. 하나는 조용히 무시될 수 있다는 것이다. 매뉴얼은 지정한 조인 종류와 충돌하는 힌트는 경고 없이 무시된다고 하고, FROM t2 LEFT JOIN t1에 JOIN_PREFIX(t1, t2)를 준 예를 든다. 왼쪽 조인이 요구하는 순서와 충돌하기 때문이다. 힌트를 넣었으면 반드시 EXPLAIN으로 실제 순서를 확인한다. 다른 하나는 힌트가 오늘의 데이터에 대한 판단을 코드에 못 박는다는 것이다. 데이터 분포가 바뀌어 다른 순서가 더 좋아져도 힌트는 따라가지 않는다. 힌트는 통계를 바로잡고 인덱스를 고친 뒤에도 옵티마이저가 틀릴 때 쓰는 마지막 수단이다.

    정리: 조인 계획을 읽고 판단하는 순서

    전반부에서 세운 원리를 실행 계획을 읽는 순서로 묶어 두자. 후반부의 진단도 이 순서를 그대로 따른다.

    이 장의 핵심

    조인 비용은 드라이빙 쪽 조건을 통과한 행 수와 드리븐 쪽 한 번의 접근 비용의 곱이다. 드리븐 쪽 조인 열의 인덱스는 그 한 번의 비용을 테이블 크기에서 트리 높이로 줄이고, 인덱스가 없을 때 MySQL 8.0은 두 입력을 한 번씩 읽는 해시 조인으로 곱셈 자체를 피한다. 어느 테이블을 바깥에 둘지는 옵티마이저가 추정한 행 수 위에서 비용을 비교해 정하므로, 계획이 틀렸다면 먼저 추정과 인덱스를 의심한다.

    실전 진단: 회원별 주문 통계

    이제 실전 쿼리 하나를 진단한다. 아래 시나리오는 설명을 위해 이 원고에서 정한 가정이다. 영업 지원 화면에 "지역별 회원 주문 통계" 메뉴가 있고, 지역을 고르면 그 지역 회원마다 주문 건수와 주문 총액을 보여 준다. 화면 뒤의 SQL은 이렇다.

    SELECT m.member_id, m.name,
       COUNT(*)      AS order_count,
       SUM(o.amount) AS total_amount
FROM member m
JOIN orders o ON o.member_id = m.member_id
WHERE m.region = '부산'
GROUP BY m.member_id, m.name;

    결과는 부산 회원 10,000명의 10,000행이다. 실습 데이터라면 6번 회원의 행은 (6, '회원000006', 10, 460000), 16번은 (16, '회원000016', 10, 578000), 26번은 (26, '회원000026', 10, 405000)이다. ORDER BY가 없으므로 행의 순서는 보장되지 않는다. 증상은 이렇다. 개발 서버에서는 금방 끝나던 쿼리가 운영 서버에서는 오래 걸리고, 쿼리가 도는 동안 Innodb_buffer_pool_reads가 눈에 띄게 늘어난다. 같은 시간대에 다른 쿼리들의 응답도 함께 나빠진다.

    1단계: 실행 계획은 멀쩡해 보인다

    EXPLAIN의 핵심 열은 다음과 같다. MySQL 8.4.13에서 실행한 결과이고 8.0.46도 같았다. 예상 행 수(rows)와 filtered는 실행 환경과 통계에 따라 달라지고, ref 열의 데이터베이스 이름은 원고의 join_lab으로 바꿔 적었다.

    tabletypekeykey_lenrefrowsfilteredExtra
    mALLNULLNULLNULL10008210.00Using where; Using temporary
    orefidx_orders_member8join_lab.m.member_id9100.00NULL

    전반부의 순서대로 읽어 보자. 드라이빙은 member이고 풀 스캔이다. 회원 100,000명 중 부산을 고르는 조건에는 인덱스가 없지만, 결과에 10%가 남는 조건이라 풀 스캔 자체가 터무니없는 선택은 아니다. 드리븐인 orders는 ref로 조인 열의 인덱스를 쓰고, 한 번에 9행을 예상한다(트리 형식으로는 9.95행, 실제는 정확히 10행). key_len 8은 BIGINT 하나를 다 썼다는 뜻이다. m 행의 Using temporary는 GROUP BY 집계를 내부 임시 테이블로 처리한다는 표시이고, 이 부분은 12회에서 다룬다. "조인 열에 인덱스가 없다"거나 "해시 조인으로 테이블을 통째로 읽는다" 같은 눈에 띄는 문제는 없다. EXPLAIN ANALYZE로 실제 반복을 확인하면 다음과 같다. MySQL 8.4.13에서 실행한 결과이고, 맨 위 두 줄이 그룹 집계 노드, 그 아래가 조인 부분이다. 비용과 시간은 실행 환경과 통계에 따라 달라진다. 행 수와 루프 수는 데이터로 결정되는 값이며 8.0.46에서도 같았다.

    -> Table scan on   (actual time=2270..2272 rows=10000 loops=1)
    -> Aggregate using temporary table  (actual time=2270..2270 rows=10000 loops=1)
        -> Nested loop inner join  (cost=84216 rows=99589) (actual time=0.995..2197 rows=100000 loops=1)
            -> Filter: (m.region = '부산')  (cost=10096 rows=10008) (actual time=0.331..35.8 rows=10000 loops=1)
                -> Table scan on m  (cost=10096 rows=100082) (actual time=0.31..19.5 rows=100000 loops=1)
            -> Index lookup on o using idx_orders_member (member_id=m.member_id)  (cost=6.41 rows=9.95) (actual time=0.214..0.215 rows=10 loops=10000)

    마지막 줄이 이 쿼리의 무게 중심이다. 인덱스 탐색이 10,000번 반복되고 한 번에 10행씩, 모두 100,000행이 나온다. 여기까지는 계획표와 실측이 잘 맞는다. 그런데 이 한 줄 안에서 InnoDB가 실제로 하는 일은 한 가지가 아니다.

    2단계: 한 줄 안에 숨은 두 번째 탐색

    06회에서 본 것처럼 InnoDB의 세컨더리 인덱스 항목에는 인덱스 열과 기본 키만 들어 있다. 매뉴얼의 표현으로 세컨더리 인덱스의 각 레코드는 그 행의 기본 키 열과 세컨더리 인덱스에 지정한 열을 담고, InnoDB는 이 기본 키 값으로 클러스터형 인덱스에서 행을 찾는다. idx_orders_member의 항목은 (member_id, order_id)뿐이다. 그런데 이 쿼리는 SUM(o.amount)를 계산해야 하고, amount는 이 인덱스에 없다. 그러므로 Index lookup on o가 내놓는 100,000행 하나하나마다 InnoDB는 항목의 order_id로 클러스터형 인덱스를 루트부터 다시 내려가 행 전체가 든 리프 레코드를 읽는다. 금액 4바이트를 얻으려고 메모까지 든 150바이트 남짓의 행이 있는 페이지를 통째로 버퍼 풀에 올리는 것이다.

    이 두 번째 탐색은 실행 계획에 별도의 줄로 나오지 않는다. 계획에서 그것을 알려 주는 단서는 없는 것 하나뿐이다. o 행의 Extra에 Using index가 없다는 사실이다. 매뉴얼은 Using index를 "실제 행을 읽으려고 추가로 탐색하지 않고 인덱스 트리의 정보만으로 열 정보를 가져온다"는 표시로 정의한다. 그 표시가 없는 ref 접근은, 찾은 항목마다 클러스터형 인덱스로 되돌아간다는 뜻이다. 그러므로 이 쿼리의 실제 반복 구조는 이렇다.

    for each m in member (풀 스캔, 100,000행):            ← 1회, 리프 약 300페이지를 순서대로
    if m.region != '부산': continue                    ← 10,000행 통과
    idx_orders_member 를 루트부터 탐색 (member_id = m) ← 10,000회, 회당 약 3페이지
    for each 항목 (member_id, order_id):               ← 회당 10항목, 모두 100,000항목
        클러스터형 인덱스를 루트부터 탐색 (order_id)    ← 100,000회, 회당 약 3페이지  ★
        amount 를 꺼내 집계에 넘긴다

    3단계: 카운터로 숨은 탐색을 드러내기

    01회에서 쓴 두 종류의 카운터를 같이 보면 이 숨은 탐색이 드러난다. 세션 범위의 Handler_read_*는 SQL 계층이 스토리지 엔진에 보낸 행 읽기 요청을 센다. 매뉴얼의 정의로 Handler_read_key는 키로 행을 읽으라는 요청 수이고 Handler_read_next는 키 순서로 다음 행을 읽으라는 요청 수다. 조인만 놓고 보면 Handler_read_rnd_next가 회원 풀 스캔의 약 100,000, Handler_read_key가 인덱스 탐색 시작의 약 10,000, Handler_read_next가 이어 읽은 항목의 약 100,000 규모로 늘어날 것이다. 여기에 GROUP BY를 처리하는 임시 테이블의 읽기가 더해진다.

    FLUSH STATUS;
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';   -- 실행 전 값

SELECT m.member_id, m.name, COUNT(*), SUM(o.amount)
FROM member m JOIN orders o ON o.member_id = m.member_id
WHERE m.region = '부산'
GROUP BY m.member_id, m.name;

SHOW SESSION STATUS LIKE 'Handler_read%';
SHOW GLOBAL STATUS LIKE 'Innodb_buffer_pool_read%';   -- 실행 후 값, 차이를 본다
    +-----------------------+--------+
| Variable_name         | Value  |
+-----------------------+--------+
| Handler_read_first    | 1      |
| Handler_read_key      | 110001 |
| Handler_read_last     | 0      |
| Handler_read_next     | 100000 |
| Handler_read_prev     | 0      |
| Handler_read_rnd      | 0      |
| Handler_read_rnd_next | 110002 |
+-----------------------+--------+

    Handler_read_next는 정확히 100,000이지만 Handler_read_key와 Handler_read_rnd_next는 어림보다 각각 100,000과 10,000가량 많다. GROUP BY를 뺀 같은 조인(SELECT m.member_id, m.name, o.order_id, o.amount ...)을 같은 방식으로 재면 Handler_read_key 10,001, Handler_read_next 100,000, Handler_read_rnd_next 100,001로 어림과 맞는다. 차이는 집계 단계에서 생긴 것으로, 조인 행 100,000개를 그룹별로 임시 테이블에 모으고 그룹 10,000개를 다시 읽는 일이 이 카운터들에 더해진 것이다. 이처럼 Handler_read_*에는 조인 바깥의 단계도 섞이므로, 조인만 보고 싶으면 집계를 뺀 쿼리와 비교한다. 버퍼 풀 카운터는 서버 전체의 값이라 여러 작업이 함께 도는 실습 서버에서는 재지 않았다.

    여기서 중요한 사실은 Handler_read_*에는 클러스터형 인덱스로 되돌아가는 룩업이 따로 잡히지 않는다는 것이다. SQL 계층은 "다음 행을 달라"고 한 번 요청했을 뿐이고, 그 요청을 처리하려고 InnoDB가 세컨더리 인덱스와 클러스터형 인덱스를 차례로 탐색한 것은 엔진 내부의 일이다. 반면 InnoDB의 Innodb_buffer_pool_read_requests는 버퍼 풀에 대한 논리적 읽기 요청을 세므로, 엔진 안에서 만진 페이지가 모두 반영된다. 이 카운터는 서버 전체의 누적값이라 다른 연결의 일도 섞이므로, 다른 작업이 없는 실습 서버에서 전후의 차이를 본다. 가정한 크기로 이 쿼리의 논리적 읽기를 어림하면 다음과 같다. 실측이 아니라 가정에서 나온 어림이고, 실제 값은 페이지 채움 정도와 트리 높이에 따라 달라지고, InnoDB가 자주 찾는 페이지에 대해 필요할 때 만드는 적응형 해시 인덱스(adaptive hash index)가 트리 하강의 일부를 대신하면 더 적게 나올 수 있다.

    단계횟수논리적 페이지 접근(어림)
    member 풀 스캔1회약 300
    idx_orders_member 탐색10,000회10,000 × 3 = 약 30,000
    클러스터형 인덱스 룩업100,000회100,000 × 3 = 약 300,000
    합계약 330,000, 그중 약 90%가 클러스터형 인덱스 룩업

    EXPLAIN에서 보이지 않던 단계가 일의 대부분을 차지한다. 다만 페이지 접근 수만으로는 아직 "왜 운영 서버에서만 느린가"가 설명되지 않는다. 루트와 중간 노드는 늘 버퍼 풀에 있으므로 그 접근은 싸다. 비싼 것은 리프 페이지가 버퍼 풀에 없을 때의 디스크 읽기이고, 그것은 리프를 어떤 순서로 건드리느냐에 달려 있다.

    4단계: 왜 무작위 접근인가

    세컨더리 인덱스의 항목은 (member_id, order_id) 순으로 정렬되어 있다. 드라이빙 쪽 풀 스캔은 member의 클러스터형 인덱스를 기본 키 순서로 읽으므로 회원은 6, 16, 26, … 순으로 나오고, 세컨더리 인덱스 탐색도 이 순서를 따라 앞에서 뒤로 진행한다. 세컨더리 인덱스 쪽은 접근에 지역성이 있다. 문제는 그 항목들이 가리키는 주문 번호다. 가정대로 리프 한 페이지에 주문 100행이 들어간다면, 주문 번호를 100으로 나눈 몫이 그 주문이 든 리프의 대략적인 순번이다.

    idx_orders_member 리프 (member_id 순)        가리키는 orders 클러스터형 인덱스 리프 순번 (order_id ÷ 100)

(6,  88395) (6, 188395) … (6, 988395)    →    883, 1883, 2883, 3883, 4883, 5883, 6883, 7883, 8883, 9883
(16, 65185) (16,165185) … (16,965185)    →    651, 1651, 2651, 3651, 4651, 5651, 6651, 7651, 8651, 9651
(26, 41975) (26,141975) … (26,941975)    →    419, 1419, 2419, 3419, 4419, 5419, 6419, 7419, 8419, 9419
   …                                            …
세컨더리 쪽: 앞에서 뒤로 한 방향                클러스터형 쪽: 10,000개 리프 전체를 이리저리 오간다

    회원 한 명의 주문 10건이 리프 1,000개 간격으로 흩어져 있고, 다음 회원의 주문은 또 다른 10개 리프에 흩어져 있다. 부산 회원 10,000명을 처리하는 동안 100,000번의 룩업이 가정한 리프 10,000페이지 전체를 고르게, 그러나 순서 없이 건드린다. 리프 하나가 평균 10번 쓰이지만 그 10번은 시간적으로 멀리 떨어져 있다. 리프 전체가 160MB라면 기본 크기 128MB의 버퍼 풀, 그것도 다른 테이블과 나눠 쓰는 버퍼 풀에 다 머물 수 없으므로, 한 번 읽은 리프가 다음 쓰임 전에 밀려났다가 다시 디스크에서 읽히는 일이 반복된다. 최악이면 물리적 읽기가 룩업 수인 100,000번에 가까워지고, 그 읽기는 모두 서로 떨어진 위치를 읽는 무작위 읽기다.

    개발 서버에서 빨랐던 이유도 여기서 나온다. 개발 데이터가 작으면 테이블 전체가 버퍼 풀에 들어가므로 100,000번의 룩업이 모두 메모리에서 끝난다. 논리적 읽기는 똑같이 많지만 물리적 읽기가 거의 없다. 운영 데이터가 버퍼 풀을 넘는 순간 같은 계획이 디스크 무작위 읽기의 연속으로 바뀌고, 그동안 다른 쿼리들이 쓰던 페이지까지 버퍼 풀에서 밀어내므로 다른 쿼리도 함께 느려진다. 진단의 결론은 이렇다. 조인의 반복 횟수(10,000번)는 적절하지만, 반복 하나하나가 클러스터형 인덱스로 10번씩 무작위로 되돌아가는 것이 비용의 대부분이다.

    위쪽의 세컨더리 인덱스 리프는 왼쪽에서 오른쪽으로 차례대로 읽히는데, 각 항목에서 아래쪽 클러스터형 인덱스 리프로 내려가는 화살표들이 넓게 교차하며 흩어지는 대비를 보여 준다. 화면을 위아래로 나눈다. 위쪽에 가로로 긴 띠 "idx_orders_member 리프 (member_id 순)"를 그리고 칸 세 개에 "회원 6의 항목 10개", "회원 16의 항목 10개", "회원 26의 항목 10개"를 적는다. 띠 위에 왼쪽에서 오른쪽으로 향하는 굵은 화살표와 라벨 "차례대로 읽음"을 둔다. 아래쪽에 작은 사각형 20개가 늘어선 긴 띠 "orders 클러스터형 인덱스 리프 (order_id 순)"를 그린다. 위쪽 각 칸에서 아래쪽 띠의 멀리 떨어진 여러 사각형으로 가는 가는 화살표를 칸마다 서로 다른 색으로 여러 개 그려 화살표들이 넓게 교차하게 한다. 아래쪽 띠 옆에 "무작위 룩업 100,000회"라는 라벨을 붙이고, 오른쪽 구석에 작은 상자 "버퍼 풀 128MB"와 그 안에 넘쳐 나가는 페이지 아이콘 몇 개를 그린다. 평면적이고 깔끔한 다이어그램 스타일. 세컨더리 인덱스는 회원 순서대로 읽히지만, 항목이 가리키는 주문은 클러스터형 인덱스 전체에 흩어져 있어 룩업이 무작위 접근이 된다.

    해결 방안 1: 드리븐 테이블을 커버링 인덱스로

    진단이 가리키는 처방은 클러스터형 인덱스로 되돌아갈 이유를 없애는 것이다. 쿼리가 orders에서 쓰는 열은 조인 열 member_id와 집계할 amount 둘뿐이고, COUNT(*)는 행이 있다는 사실만 필요하다. 두 열을 모두 담은 인덱스가 있으면 08회에서 다룬 커버링 인덱스(covering index)가 되어 인덱스 항목만으로 쿼리를 처리할 수 있다.

    ALTER TABLE orders ADD INDEX idx_orders_member_amount (member_id, amount);

    열 순서에는 이유가 있다. 조인에서 이 인덱스로 찾아 들어가려면 등치로 비교되는 member_id가 맨 앞에 있어야 한다. (amount, member_id)로 만들면 두 열을 모두 담고 있어도 최좌측 접두사가 amount이므로 회원 번호로 찾아 들어갈 수 없다. 인덱스 전체를 훑는 데는 쓸 수 있겠지만 조인의 반복마다 그럴 수는 없다. amount는 찾는 데가 아니라 "들고 나오는" 데 쓰이는 열이므로 뒤에 둔다. 새 인덱스의 항목은 (member_id, amount, order_id)가 된다. 기본 키 order_id는 InnoDB가 자동으로 붙이므로 따로 적지 않아도 된다.

    MySQL 8.4.13과 8.0.46에서 새 인덱스를 만들고 EXPLAIN을 다시 보면, 옵티마이저는 새 인덱스를 고르고 o 행은 이렇게 바뀐다(ref 열의 데이터베이스 이름은 원고에 맞춰 적었다).

    tabletypekeykey_lenrefrowsExtra
    orefidx_orders_member_amount8join_lab.m.member_id9Using index

    바뀐 것은 key와 Extra뿐이다. 조인 순서, 접근 유형, key_len, 예상 행 수가 모두 같고, EXPLAIN ANALYZE의 행 수와 루프 수도 같다. Handler_read_*도 그대로다. 두 버전에서 재 보면 커버링 전과 똑같이 Handler_read_key 110,001, Handler_read_next 100,000, Handler_read_rnd_next 110,002였다. 여전히 인덱스 탐색 10,000번과 항목 100,000개를 읽기 때문이다. 줄어드는 것은 Innodb_buffer_pool_read_requests다. 어림으로 다시 세면 회원 풀 스캔 약 300과 인덱스 탐색 10,000 × 3 = 약 30,000을 더한 약 30,300으로, 원래의 약 330,000에서 11분의 1 남짓이 된다. 트리 형식에서는 버전에 따라 이 접근이 Covering index lookup으로 표시되기도 하는데, 8.0.46과 8.4.13은 둘 다 그렇게 표시한다. 이처럼 계획의 모양은 그대로이고 카운터 하나만 크게 바뀌는 개선이라서, 효과를 확인할 때도 EXPLAIN보다 버퍼 풀 카운터와 실제 시간을 함께 본다.

    -> Table scan on   (actual time=242..243 rows=10000 loops=1)
    -> Aggregate using temporary table  (actual time=242..242 rows=10000 loops=1)
        -> Nested loop inner join  (cost=30461 rows=98958) (actual time=0.747..182 rows=100000 loops=1)
            -> Filter: (m.region = '부산')  (cost=10340 rows=10008) (actual time=0.692..37.4 rows=10000 loops=1)
                -> Table scan on m  (cost=10340 rows=100082) (actual time=0.682..27.9 rows=100000 loops=1)
            -> Covering index lookup on o using idx_orders_member_amount (member_id=m.member_id)  (cost=1.02 rows=9.89) (actual time=0.0127..0.0137 rows=10 loops=10000)

    행 수와 루프 수는 커버링 전과 똑같다. 이 실행에서는 조인 노드의 실제 시간이 2,197ms에서 182ms로 줄었지만, 실습 서버는 다른 작업과 버퍼 풀을 나눠 쓰고 있었으므로 이 비율을 일반적인 효과로 읽어서는 안 된다. 시간은 실행 환경과 버퍼 풀 상태에 따라 크게 달라진다.

    왼쪽은 세컨더리 인덱스를 내려간 뒤 클러스터형 인덱스를 다시 내려가는 두 단계 경로, 오른쪽은 커버링 인덱스 하나만 내려가고 끝나는 한 단계 경로를 나란히 비교한다. 화면을 좌우로 나눈다. 왼쪽 제목 "전: idx_orders_member", 오른쪽 제목 "후: idx_orders_member_amount". 왼쪽에는 작은 삼각형 트리 "세컨더리 인덱스"와 그 옆의 큰 삼각형 트리 "클러스터형 인덱스"를 그린다. 위에서 내려온 화살표가 세컨더리 트리의 리프 항목 "(6, 88395)"에 닿고, 거기서 다시 클러스터형 트리의 루트로 올라가 리프의 "주문 88395 전체 행"까지 내려가는 꺾인 경로를 빨간색으로 그리고 "PK 룩업"이라고 라벨을 붙인다. 오른쪽에는 삼각형 트리 하나 "커버링 인덱스"만 그리고, 화살표가 리프 항목 "(6, 29000, 88395)"에 닿은 뒤 바로 "amount 획득"이라는 초록색 체크 표시로 끝나게 한다. 아래쪽에 왼쪽은 "탐색 1만 회 + PK 룩업 10만 회", 오른쪽은 "탐색 1만 회"라는 비교 라벨을 둔다. 깔끔한 평면 스타일. 커버링 인덱스는 조인의 반복 횟수를 바꾸지 않는다. 반복 하나하나에서 클러스터형 인덱스로 되돌아가는 두 번째 탐색을 없앤다.

    물리적 읽기는 더 크게 줄어든다. 이유는 두 가지다. 첫째, 인덱스가 작다. 항목이 회원 번호 8바이트, 금액 4바이트, 기본 키 8바이트에 레코드 헤더를 더한 크기이므로, 리프 한 페이지에 400항목 정도가 들어간다고 가정하면 100만 항목이 리프 약 2,500페이지, 약 40MB다. 실습 서버(8.4.13, 8.0.46)에서 잰 실제 값은 이보다 작은 리프 1,570페이지(전체 1,828페이지), 약 25MiB였다. 메모가 든 클러스터형 인덱스 160MB와 달리 기본 크기의 버퍼 풀에도 여유 있게 머문다. 둘째, 접근 순서가 한 방향이다. 드라이빙 행은 회원 번호 순으로 나오고 이 인덱스도 회원 번호 순으로 정렬되어 있다. 부산 회원 6, 16, 26, …의 항목 묶음은 그 사이에 낀 회원 9명의 항목 90개를 사이에 두고 100항목 간격으로 놓여 있으므로, 연달아 나오는 부산 회원 네댓 명이 같은 리프에서 처리되고 다음 리프로 넘어간다. 리프 하나를 한 번 읽어 와서 다 쓰고 다음으로 가는 접근이다. 원래 계획에서 무작위였던 부분이 통째로 사라지고, 남은 부분은 순서가 맞는 접근이 되었다.

    기존 인덱스 정리하기

    새 인덱스의 최좌측 접두사가 member_id이므로 idx_orders_member로 할 수 있는 일은 새 인덱스로 모두 할 수 있다. 두 인덱스를 다 두면 쓰기마다 두 인덱스를 고쳐야 하고, 옵티마이저가 둘 중 무엇을 고를지 헷갈릴 여지도 남는다. 다만 바로 지우기보다 MySQL 8.0의 보이지 않는 인덱스(invisible index)로 먼저 감춰 두는 것이 안전하다. 보이지 않는 인덱스는 옵티마이저가 쓰지 않지만 데이터 변경에 맞춰 계속 유지되므로, 문제가 생기면 곧바로 되돌릴 수 있다. 인덱스를 추가하고 지우는 작업 자체의 비용과 검증 절차는 04회에서 다뤘다.

    ALTER TABLE orders ALTER INDEX idx_orders_member INVISIBLE;
-- 운영 쿼리들의 실행 계획과 느린 쿼리 로그를 지켜본 뒤
ALTER TABLE orders DROP INDEX idx_orders_member;
-- 문제가 생기면: ALTER TABLE orders ALTER INDEX idx_orders_member VISIBLE;

    커버링이 깨지는 순간

    커버링 인덱스는 쿼리가 쓰는 열이 인덱스 안에 모두 있다는 조건이 성립하는 동안만 효과가 있다. 그 조건은 쿼리가 조금만 바뀌어도 조용히 깨진다. 통계 화면에 "취소 주문은 빼 달라"는 요구가 들어와 AND o.status <> 'CANCELED'가 붙었다고 하자. status는 idx_orders_member_amount에 없으므로 InnoDB는 조건을 검사하려고 다시 항목마다 클러스터형 인덱스로 되돌아가고, Extra에서 Using index가 사라진다. MySQL 8.4.13과 8.0.46에서 확인하면 o 행은 key와 key_len이 그대로인 채 Extra가 Using where로 바뀐다. 에러도 경고도 없이 원래의 무작위 룩업 100,000번이 돌아온다. 대응은 인덱스를 (member_id, status, amount)로 바꾸는 것이다. 이러면 조인 열로 찾아 들어간 뒤 각 항목의 status를 인덱스 안에서 검사하고 amount를 꺼낼 수 있어 다시 커버링이 된다. 조건이 o.status = 'DELIVERED'처럼 등치라면 두 열로 바로 찾아 들어가므로 ref가 join_lab.m.member_id,const, key_len이 8 + 82 = 90이 된다.

    "최근 주문일"을 보여 달라며 MAX(o.ordered_at)가 추가되어도 같은 일이 생긴다. 요구가 늘 때마다 열을 덧붙이면 인덱스는 점점 테이블을 닮아 가고, 크기가 커지는 만큼 버퍼 풀에서 차지하는 자리와 쓰기 비용도 늘어난다. orders에 행이 들어오거나 해당 열이 바뀔 때마다 이 인덱스도 고쳐야 하기 때문이다. 통계용으로 들고 나와야 하는 열이 계속 늘어난다면, 조회 시점에 매번 집계하는 대신 집계 결과를 따로 저장해 두는 설계를 검토할 때다. 그 사전 집계 테이블은 12회에서 다룬다. 반대로 기본 키는 공짜다. COUNT(o.order_id)를 쓰거나 o.order_id를 함께 조회해도 기본 키가 항목에 이미 들어 있으므로 커버링은 유지된다.

    해결 방안 2: 반복의 모양을 바꾸기

    방안 1은 조인의 모양을 그대로 두고 드리븐 쪽 한 번의 비용 Cinner를 줄였다. 방안 2는 식의 다른 항을 건드린다. 드라이빙 쪽 Couter를 줄이는 방법, 조인과 집계의 순서를 바꿔 N을 줄이는 방법, 그리고 반복 자체를 다른 알고리즘으로 바꾸는 방법이다. 어느 것이 좋은지는 쿼리와 데이터에 따라 달라지므로 각각이 이기는 조건을 함께 따진다.

    드라이빙 쪽 정리: 곱해지지 않는 항의 이득은 작다

    방안 1 이후 남은 일은 회원 풀 스캔(리프 약 300페이지, 100,000행 검사)과 커버링 인덱스 탐색 10,000번이다. 드라이빙 쪽에도 인덱스를 두면 회원 100,000행을 다 검사하지 않아도 된다. 그런데 (region) 하나짜리 인덱스는 생각만큼 좋지 않다. 이름을 얻으려고 부산 회원 10,000명마다 member의 클러스터형 인덱스로 되돌아가야 하고, 높이 2의 트리를 10,000번 내려가면 약 20,000번의 페이지 접근이다. 리프 300페이지를 한 번 순서대로 읽는 풀 스캔보다 오히려 많다. 04회에서는 결과의 10%를 남기는 조건이라면 옵티마이저가 이런 인덱스를 두고도 풀 스캔을 고를 수 있다고 했다. 그러나 MySQL 8.4.13에서 실습 데이터에 (region) 인덱스를 만들어 EXPLAIN을 보면 옵티마이저는 이 인덱스를 고른다. m 행이 type ref, key_len 82, ref const이고, 예상 행 수는 실제 10,000보다 많은 19,228이다(실행 환경과 통계에 따라 달라진다). 위의 페이지 접근 어림과 옵티마이저의 비용 모델이 늘 같은 답을 내지는 않으므로, 이런 선택이 실제로 나은지는 EXPLAIN ANALYZE의 실제 시간과 버퍼 풀 카운터로 따로 확인해야 한다.

    ALTER TABLE member ADD INDEX idx_member_region_name (region, name);

    드라이빙 쪽도 커버링으로 만들면 이야기가 달라진다. (region, name)의 항목에는 기본 키 member_id가 붙으므로, 부산 회원의 항목 10,000개를 연속된 구간으로 읽는 것만으로 번호와 이름이 모두 나온다. 이때 m 행은 type이 ref, ref가 const, key_len이 VARCHAR(20) utf8mb4의 82, Extra가 Using index가 된다. MySQL 8.4.13에서 방안 1의 인덱스와 함께 만들어 확인하면 m 행의 Extra는 집계용 표시까지 붙은 Using index; Using temporary이고, o 행은 그대로 idx_orders_member_amount의 ref에 Using index다. 다만 이득의 크기를 정직하게 보자. 줄어드는 것은 리프 300페이지가 수십 페이지로, 검사하는 행 100,000개가 10,000개로 바뀌는 정도다. 반복 횟수 N은 그대로 10,000이고, 비용의 대부분인 드리븐 쪽 탐색 10,000번도 그대로다. 곱해지는 항을 먼저 고치고, 곱해지지 않는 항은 그다음에 고친다는 순서가 여기서 나온다.

    드라이빙 쪽 인덱스에는 눈여겨볼 부수 효과가 하나 있다. 드라이빙 행이 나오는 순서가 드리븐 쪽 접근의 지역성을 정한다는 점이다. 풀 스캔은 회원을 번호 순으로 내놓았고, 그래서 회원 번호 순으로 정렬된 드리븐 인덱스를 한 방향으로 훑을 수 있었다. (region, name) 인덱스는 같은 지역 안에서 이름, 그다음 기본 키 순으로 정렬되어 있다. 이 실습 데이터는 이름이 회원 번호를 0으로 채운 문자열이라 이름 순서와 번호 순서가 우연히 같지만, 실제 이름이라면 드라이빙 행이 회원 번호와 무관한 순서로 나오고 드리븐 인덱스 탐색은 그만큼 이리저리 뛰게 된다. 인덱스가 작아서 버퍼 풀에 다 머문다면 문제가 되지 않지만, 드리븐 쪽 인덱스가 버퍼 풀보다 크다면 드라이빙 쪽 인덱스를 바꾼 것이 드리븐 쪽 물리 읽기를 늘리는 결과가 될 수 있다.

    집계 후 조인: 조인이 행을 불리기 전에 줄이기

    이번에는 같은 화면에서 "전체 지역"을 고른 경우를 생각해 보자. 지역 조건이 없으므로 회원 100,000명이 모두 드라이빙 행이 되고, 커버링 인덱스 탐색이 100,000번 반복되어 조인 결과 1,000,000행이 만들어진 뒤에야 집계가 100,000행으로 줄인다. 조인이 행을 10배로 불렸다가 집계가 다시 10분의 1로 줄이는 모양이다. 이럴 때는 집계를 조인보다 먼저 할 수 있다.

    SELECT m.member_id, m.name, s.order_count, s.total_amount
FROM (
  SELECT member_id, COUNT(*) AS order_count, SUM(amount) AS total_amount
  FROM orders
  GROUP BY member_id
) AS s
JOIN member m ON m.member_id = s.member_id;

    FROM 절의 서브쿼리, 곧 파생 테이블(derived table)에 GROUP BY와 집계 함수가 있으면 바깥 쿼리에 병합(merge)될 수 없다. 매뉴얼은 병합을 막는 구성 요소로 집계 함수, DISTINCT, GROUP BY, HAVING, LIMIT, UNION 등을 든다. 그래서 이 파생 테이블은 먼저 구체화(materialization)되어 회원별 한 행씩 100,000행의 내부 임시 테이블이 된다. 그 안쪽의 집계는 idx_orders_member_amount를 처음부터 끝까지 한 번 순서대로 읽으면 된다. 매뉴얼은 GROUP BY의 모든 열이 같은 인덱스의 열이고 그 인덱스가 키를 순서대로 저장하는 것을 인덱스로 그룹을 처리하는 가장 중요한 전제 조건으로 드는데, 이 경우가 그렇다. 실제로 그룹핑용 임시 테이블이 생겼는지는 EXPLAIN의 Using temporary로 확인하고, 그룹핑 최적화의 자세한 내용은 12회에서 다룬다. 이어지는 조인은 100,000행짜리 구체화 결과와 member의 조인이다. 매뉴얼에 따르면 옵티마이저는 구체화된 파생 테이블에 인덱스를 만들어 ref 접근을 할 수 있고, member 쪽은 기본 키로 eq_ref 접근을 할 수 있다. 어느 순서든 조인이 다루는 행은 주문 1,000,000행이 아니라 그룹 100,000행이다. MySQL 8.4.13에서 방안 1의 인덱스와 앞 절의 (region, name) 인덱스가 있는 상태로 EXPLAIN을 보면, DERIVED 행은 orders를 idx_orders_member_amount로 처음부터 끝까지 읽는 type index에 Extra가 Using index뿐이고 Using temporary는 없다. 바깥 조인은 member를 커버링 인덱스 idx_member_region_name 전체로 읽고(type index, Using index), 구체화된 를 자동 생성 인덱스 의 ref로 찾는 순서를 골랐다.

    그런데 같은 모양을 부산 쿼리에 적용하면 오히려 나빠진다. 파생 테이블 안에는 지역 조건을 넣을 수 없다. region은 member에 있는 열이고 orders에는 없기 때문이다. 그래서 파생 테이블은 전체 회원 100,000명의 집계를 다 만든 뒤 조인에서 90%를 버린다. 방안 1의 계획이 커버링 인덱스 항목 100,000개만 읽는 데 비해, 집계 후 조인은 1,000,000개를 모두 읽는다. 정리하면 집계 후 조인은 결과에 대부분의 그룹이 남을 때, 그리고 조인이 행을 크게 불린 다음 집계가 다시 줄이는 모양일 때 유리하다. 조인 상대 쪽의 조건이 그룹을 크게 줄인다면 조인으로 먼저 좁히는 쪽이 낫다.

    해시 조인으로 바꾸기: 무작위 룩업을 순차 읽기 한 번으로

    커버링 인덱스를 만들 수 없는 경우도 있다. 드리븐 쪽에서 들고 나와야 하는 열이 많아 인덱스가 테이블만큼 커지거나, 쓰기 부담 때문에 인덱스를 더 늘릴 수 없는 경우다. 이때 원래 계획의 문제는 "같은 테이블의 리프 10,000페이지를 100,000번 무작위로 오간다"는 것이었다. 해시 조인은 이 테이블을 처음부터 끝까지 한 번 순차로 읽는다. 부산 회원 10,000명으로 해시 테이블을 만들고 주문 1,000,000건을 차례로 프로브하면, 페이지 접근은 회원 쪽 약 300과 주문 쪽 약 10,000이다. 논리적 읽기만 보면 원래 계획의 약 330,000보다 훨씬 적고 접근도 순차다.

    대가도 분명하다. 해시 조인은 결과에 쓰이지 않을 90%의 주문까지 모두 읽고 1,000,000행을 하나씩 프로브하므로, 비용이 결과가 아니라 orders 테이블의 크기에 비례한다. 주문이 1,000만 건으로 늘면 부산 회원 수가 그대로여도 비용은 10배가 된다. 빌드 입력이 join_buffer_size를 넘으면 디스크로 넘치고, 결과의 첫 행은 빌드가 끝나야 나온다. 그리고 공식 블로그가 말하듯 조인 조건에 쓸 인덱스가 있으면 옵티마이저는 대개 인덱스 NLJ를 택하므로, 해시 조인을 원하면 앞서 본 IGNORE INDEX 같은 힌트로 인덱스 사용을 막아야 한다. 힌트로 고정한 계획은 데이터가 변해도 따라가지 않는다는 점까지 감수해야 하는 선택이다. 커버링 인덱스를 만들 수 있다면 방안 1이 거의 언제나 낫다.

    BKA: 룩업은 그대로 두고 순서만 정렬하기

    NLJ를 유지하면서 무작위 룩업의 순서만 바꾸는 방법도 있다. 배치 키 접근(Batched Key Access, BKA)이다. 매뉴얼의 설명으로 BKA는 BNL처럼 조인 버퍼에 첫 번째 피연산자가 만든 행의 필요한 열을 모은 뒤, 버퍼의 모든 행에 대해 조인할 테이블을 찾을 키를 만들어 09회에서 본 다중 범위 읽기(Multi-Range Read, MRR) 인터페이스로 엔진에 한꺼번에 넘긴다. InnoDB 같은 디스크 기반 엔진에서는 MRR이 행을 기본 키 순서로 가져오므로, 무작위 순서가 아니라 디스크 순서로 읽게 된다. 부산 쿼리라면 한 번에 모은 회원들의 주문 룩업이 주문 번호 순으로 정렬되어 클러스터형 인덱스를 한 방향으로 훑는다. 룩업의 수는 줄지 않지만 같은 리프를 멀리 떨어진 시점에 다시 읽는 일이 줄어든다.

    -- BKA는 기본적으로 꺼져 있다. MRR이 필요하고, MRR 비용 추정이 비관적이라 mrr_cost_based도 꺼야 한다
SET optimizer_switch = 'mrr=on,mrr_cost_based=off,batched_key_access=on';
-- 문장 하나에만 적용하려면 SET_VAR 힌트로 같은 값을 준다
SELECT /*+ SET_VAR(optimizer_switch = 'mrr=on,mrr_cost_based=off,batched_key_access=on') */ ...

    매뉴얼에 따르면 기본값은 batched_key_access=off이고, BKA를 쓰려면 mrr이 켜져 있어야 하며 MRR의 비용 추정이 지나치게 비관적이라 mrr_cost_based도 꺼야 한다. 사용 여부는 EXPLAIN에서 type이 ref나 eq_ref이면서 Extra에 Using join buffer (Batched Key Access)가 붙는지로 확인한다. MySQL 8.4.13에서 커버링 인덱스를 만들기 전의 진단 쿼리에 위 SET_VAR 힌트를 주면, 순서와 접근은 원래대로(m이 ALL, o가 idx_orders_member의 ref)이고 o 행의 Extra만 Using join buffer (Batched Key Access)로 바뀐다. 기본으로 꺼져 있는 기능을 서버 전체에서 켜는 일은 다른 쿼리의 계획까지 바꾸므로, 쓰더라도 SET_VAR 힌트로 문장 하나에만 적용하는 편이 안전하다.

    방안 비교

    부산 쿼리를 기준으로 지금까지의 방안을 한 표에 모으면 다음과 같다. 모든 숫자는 앞에서 정한 크기 가정에서 나온 어림이고, 실측이 아니다. 최종 판단은 실습 서버에서 Innodb_buffer_pool_read_requests, Innodb_buffer_pool_reads, EXPLAIN ANALYZE의 실제 시간으로 한다.

    방안 1: 드리븐 커버링인덱스 탐색 1만약 3만한 방향, 작은 인덱스부산 회원 수 × 주문 수쿼리에 열이 늘면 조용히 깨진다
    방안 1 + 드라이빙 커버링같음약 3만 (드라이빙 300 → 수십)같음같음이득이 작고, 드라이빙 순서가 바뀔 수 있다
    집계 후 조인커버링 인덱스 전체를 한 번약 2,500 + 조인순차전체 주문 수부산처럼 그룹 대부분을 버리면 손해
    해시 조인orders 전체를 한 번약 1만순차전체 주문 수빌드 메모리, 첫 행 지연, 힌트 필요
    BKA탐색 1만 + 클러스터형 룩업 10만(기본 키 순)룩업 수는 원래와 같다기본 키 순으로 정렬부산 회원 수 × 주문 수기본 꺼짐, 조인 버퍼 사용

    표에서 논리적 페이지 접근이 가장 적은 것은 해시 조인과 집계 후 조인이지만, 둘은 비용이 전체 주문 수에 비례한다. 방안 1은 비용이 결과 규모, 곧 부산 회원 수에 비례한다. 데이터가 계속 쌓이는 주문 테이블에서 이 차이는 시간이 갈수록 벌어진다. 04회에서 "결과에 비례하는 계획과 테이블에 비례하는 계획"을 구분했던 기준이 조인에서도 그대로 판단의 축이 된다.

    흔한 오해와 함정

    "EXPLAIN의 rows가 작으니 빠를 것이다." 드리븐 테이블의 rows는 한 번 찾아 들어갈 때의 예상 행 수다. 위쪽 테이블들의 rows × filtered를 곱한 반복 횟수를 곱해야 전체 규모가 된다. 이 회차의 진단 쿼리도 rows는 10이었지만 실제로는 100,000행과 100,000번의 룩업이었다.

    "조인 열 양쪽에 인덱스를 만들어 두면 된다." 반복을 줄이는 것은 드리븐 쪽 조인 열의 인덱스다. 드라이빙 쪽 조인 열의 인덱스는 그 테이블이 드리븐이 되는 다른 순서에서만 쓸모가 있다. 인덱스는 공짜가 아니므로 어느 순서로 실행될지 생각하고 만든다.

    "FROM 절에 먼저 쓴 테이블이 드라이빙이다." 내부 조인에서는 아니다. 옵티마이저가 비용으로 정한다. 외부 조인에서는 왼쪽 테이블이 먼저 읽혀야 한다는 제약이 있지만, WHERE의 널 거부 조건 때문에 내부 조인으로 바뀌면 그 제약도 사라진다. 반대로 결과가 내부 조인과 같은데 습관적으로 LEFT JOIN을 쓰고 오른쪽 테이블의 조건을 ON 절에만 두면, 외부 조인이 유지되어 옵티마이저가 고를 수 있는 순서가 줄어든다.

    "해시 조인이 생겼으니 조인 인덱스는 덜 중요하다." 해시 조인은 인덱스가 없을 때 최악을 막아 주는 장치다. 비용이 테이블 크기에 비례하고 첫 행이 늦으므로, 화면 하나에 필요한 결과를 빨리 돌려줘야 하는 쿼리에서는 드리븐 쪽 인덱스를 쓰는 NLJ를 대신하지 못한다. 반대로 대량 데이터를 한꺼번에 조인하는 배치나 분석 쿼리에서는 해시 조인이 더 나을 수 있다.

    "Handler 카운터로 엔진이 한 일을 다 셀 수 있다." Handler_read_*는 SQL 계층이 엔진에 보낸 요청의 수다. 세컨더리 인덱스 항목에서 클러스터형 인덱스로 되돌아가는 룩업은 엔진 내부의 일이라 여기에 따로 잡히지 않는다. 커버링 인덱스 전후로 Handler_read_*는 거의 같고 Innodb_buffer_pool_read_requests만 크게 달라지는 것이 그 증거다.

    "개발 서버에서 빨랐으니 계획은 괜찮다." 무작위 룩업의 비용은 대상이 버퍼 풀에 들어가느냐에 따라 극적으로 달라진다. 데이터가 작은 개발 환경에서는 논리적 읽기가 아무리 많아도 디스크를 거의 건드리지 않는다. 계획을 평가할 때는 시간보다 논리적 읽기 수와 접근 모양을 먼저 보고, 운영 규모의 데이터에서 그 읽기가 몇 번의 디스크 접근이 될지 어림한다.

    다른 주제와의 연결: 애플리케이션의 N+1도 중첩 루프다

    JPA를 쓸 때 자주 만나는 N+1 문제는 이 회차의 NLJ를 애플리케이션이 직접 실행하는 모양이다. 회원 목록을 조회하는 쿼리 한 번이 바깥 루프이고, 회원마다 주문을 조회하는 쿼리가 안쪽 루프다. DB 안의 NLJ에서는 안쪽 루프 한 번이 B+Tree 탐색 한 번이지만, 애플리케이션의 N+1에서는 안쪽 루프 한 번이 네트워크 왕복, SQL 파싱과 실행, 결과 전송을 모두 포함한다. 반복 횟수가 같아도 한 번의 비용이 비교할 수 없이 크다. 페치 조인은 이 루프를 DB 안으로 옮겨 한 문장의 NLJ나 해시 조인으로 바꾸는 일이고, 여러 회원의 식별자를 모아 IN 절 하나로 조회하는 배치 페치는 키를 모아 한꺼번에 넘긴다는 점에서 BKA와 같은 발상이다.

    커버링 인덱스도 JPA와 직접 이어진다. 기본 설정에서 엔티티를 조회하면 Hibernate는 매핑된 열을 모두 SELECT 절에 넣는다. 이 회차의 통계 쿼리를 Order 엔티티 목록을 읽어 자바 코드에서 합산하는 식으로 구현하면, memo를 포함한 모든 열이 필요해지므로 어떤 커버링 인덱스도 성립하지 않는다. 통계처럼 몇 개의 열만 필요한 조회는 DTO 프로젝션이나 집계 쿼리로 필요한 열만 요청해야 DB가 인덱스만으로 답할 기회가 생긴다. 프로젝션이 단지 코드의 편의만을 위한 기능이 아니라는 뜻이다.

    다음 회차는 조인 다음 단계의 비용을 다룬다. 이 회차의 진단 쿼리에서 생략했던 GROUP BY 집계가 임시 테이블을 쓰는지, 인덱스 순서를 이용해 흘려보내며 집계할 수 있는지, 그리고 매번 집계하는 대신 집계 결과를 미리 저장하는 사전 집계 테이블이 언제 필요한지를 정렬·페이징 최적화와 함께 살펴본다.
    중첩 루프 조인(NLJ)
    드라이빙 테이블에서 행을 하나씩 꺼내 드리븐 테이블에서 짝을 찾는다. 비용은 드라이빙 쪽 조건을 통과한 행 수 × 드리븐 쪽 한 번의 접근 비용이며, 결과가 즉시 흘러가 LIMIT에서 일찍 멈출 수 있다.
    드리븐 쪽 조인 열 인덱스
    안쪽 루프 한 번을 테이블 전체 스캔에서 트리 높이만큼의 탐색으로 줄인다. 반복을 줄이는 것은 드리븐 쪽 인덱스이며, 타입·문자 집합이 다르거나 드리븐 열을 변형하면 쓸 수 없다.
    반복 횟수 읽기
    EXPLAIN에서는 위쪽 행들의 rows × filtered / 100을 곱하고, EXPLAIN ANALYZE에서는 loops를 읽는다. 드리븐 행의 rows는 한 번 탐색할 때의 값이다.
    해시 조인
    8.0.18에 도입되고 8.0.20부터 BNL을 완전히 대체했다. 작은 입력으로 해시 테이블을 만들고(빌드) 다른 입력을 한 번 읽으며 찾는다(프로브). 메모리는 join_buffer_size로 제한되고, 넘치면 청크 파일로 나눠 처리한다.
    드라이빙 테이블 결정
    옵티마이저가 추정 행 수 위에서 순서별 비용을 비교해 정한다. 기준은 테이블 크기가 아니라 조건을 거친 뒤의 행 수와 상대 테이블에 찾아 들어가는 비용이며, 외부 조인의 의존 관계가 순서를 제약한다.
    숨은 클러스터형 룩업
    세컨더리 인덱스로 찾은 항목에 필요한 열이 없으면 항목마다 기본 키로 클러스터형 인덱스를 다시 탐색한다. 계획에서는 Extra에 Using index가 없다는 것으로만 드러나고, Innodb_buffer_pool_read_requests로 확인한다.
    드리븐 커버링 인덱스
    조인 열을 앞에, 들고 나올 열을 뒤에 둔 인덱스로 클러스터형 룩업을 없앤다. 반복 횟수는 그대로이고 한 번의 비용과 무작위 접근이 사라지며, 쿼리에 열이 추가되면 조용히 깨진다.
    반복의 모양 바꾸기
    집계 후 조인은 그룹 대부분이 남을 때, 해시 조인은 커버링이 불가능하고 드라이빙 행이 많을 때, BKA는 룩업을 기본 키 순으로 정렬하고 싶을 때 쓴다. 앞의 둘은 비용이 테이블 크기에 비례한다.

    실무에서 조인이 느리다는 신고를 받으면 가장 먼저 할 일은 "반복이 몇 번이고, 반복 한 번이 무엇을 하는가"를 실행 계획에서 분리해 읽는 것이다. 반복 횟수가 비정상적으로 많다면 드라이빙 쪽 조건이나 조인 순서의 문제이고, 통계 추정이 틀린 것은 아닌지 EXPLAIN ANALYZE의 예상과 실제를 비교한다. 반복 횟수는 적절한데 느리다면 반복 한 번의 비용이 문제이고, 그중에서도 ref 접근인데 Using index가 없는 드리븐 테이블이 가장 흔한 범인이다. 이 경우 EXPLAIN은 정상처럼 보이므로 버퍼 풀 카운터와 실제 시간을 같이 보지 않으면 놓치기 쉽다.

    판단이 달라지는 조건은 주로 데이터의 크기와 버퍼 풀의 관계다. 드리븐 테이블이 버퍼 풀에 다 들어간다면 클러스터형 룩업은 메모리 접근이라 비교적 싸고, 커버링 인덱스의 이득은 CPU와 래치 비용 정도로 줄어든다. 테이블이 버퍼 풀보다 크고 룩업이 흩어져 있다면 같은 계획이 디스크 무작위 읽기의 연속이 되고, 그 쿼리 하나가 버퍼 풀의 다른 페이지를 밀어내 서버 전체를 느리게 만든다. 그래서 같은 쿼리라도 데이터가 쌓이는 어느 시점부터 갑자기 문제가 되는 경우가 많고, 그 시점을 미리 어림하려면 테이블과 인덱스의 리프 페이지 수를 알아 두어야 한다.

    처방을 고를 때는 비용이 무엇에 비례하는지를 기준으로 삼는다. 커버링 인덱스와 인덱스 NLJ는 결과 규모에 비례하므로 데이터가 늘어도 버티지만, 인덱스를 늘리는 만큼 쓰기 비용과 저장 공간을 내야 하고 쿼리 변경에 취약하다. 해시 조인과 집계 후 조인은 인덱스 없이도 순차 읽기로 끝나지만 비용이 테이블 크기에 비례한다. 화면용 OLTP 쿼리라면 전자를, 하루 한 번 도는 정산 배치라면 후자를 먼저 검토하는 식으로, 쿼리가 얼마나 자주 돌고 결과가 얼마나 빨리 필요한지가 최종 결정을 좌우한다.
  • 세 테이블 조인의 EXPLAIN에서 첫 행은 rows 2,000, filtered 50.00, 둘째 행은 ref 접근으로 rows 5, filtered 20.00, 셋째 행은 eq_ref 접근으로 rows 1이다. 둘째 테이블과 셋째 테이블의 접근은 각각 몇 번 반복될 것으로 예상된 것인가? EXPLAIN ANALYZE에서 셋째 테이블의 loops가 40,000으로 나왔다면 어느 단계의 추정이 얼마나 틀렸을 가능성이 있는가?

    1. 둘째 테이블의 반복은 첫 행의 rows × filtered / 100 = 2,000 × 0.5 = 1,000번으로 예상된 것이다. 셋째 테이블의 반복은 그 1,000번에 둘째 행의 5 × 0.2 = 1을 곱한 1,000번이다. 실제 loops가 40,000이라면 셋째 테이블 앞까지 넘어온 행이 예상의 40배다. 첫 테이블의 통과 행 수나 둘째 테이블의 rows·filtered 중 어디서 틀렸는지는 EXPLAIN ANALYZE에서 첫째와 둘째 이터레이터의 실제 rows × loops를 각각 예상과 비교해 찾는다. 예를 들어 첫 테이블의 실제 통과 행이 1,000이고 둘째 테이블이 한 번에 실제로 40행을 내놓았다면 둘째 테이블의 추정(5행, 20%)이 틀린 것이다. 조인에서는 이런 오차가 곱해지므로 앞쪽의 작은 오차도 뒤쪽에서 커진다.

    2. status가 인덱스에 없으므로 Extra에서 Using index가 사라진다. 조건을 검사하려고 항목마다 기본 키로 클러스터형 인덱스를 다시 탐색하는 룩업 100,000번이 돌아온다. 접근 유형과 key_len, 예상 행 수는 그대로라서 EXPLAIN만 봐서는 놓치기 쉽다. 인덱스를 (member_id, status, amount)로 바꾸면 회원 번호로 찾아 들어간 뒤 각 항목의 status를 인덱스 안에서 검사하고 amount를 꺼낼 수 있어 다시 커버링이 된다. member_id는 조인에서 등치로 찾아 들어가는 열이라 맨 앞이어야 하고, status는 조건 검사에, amount는 들고 나오는 데만 쓰이므로 뒤에 둔다. 등치 조건 o.status = 'DELIVERED'라면 두 열로 찾아 들어가므로 key_len은 BIGINT NOT NULL 8 + VARCHAR(20) NOT NULL utf8mb4의 20 × 4 + 2 = 82, 합계 90이다.

    3. 복합 인덱스의 항목은 첫 열인 amount로 먼저 정렬되고, 같은 금액 안에서만 member_id 순서다. 회원 6번의 항목은 금액별로 인덱스 여기저기에 흩어져 있으므로, 회원 번호 하나로 찾아 들어갈 연속 구간이 없다. 최좌측 접두사 규칙 때문에 이 인덱스는 member_id = ? 탐색에 쓸 수 없고, 쓸 수 있는 것은 인덱스 전체를 훑는 방법뿐이다. 반복마다 전체를 훑을 수는 없으므로 조인의 반복은 빨라지지 않는다. 열을 담는 것과 그 열로 찾아 들어갈 수 있는 것은 다른 문제다.

    4. orders를 먼저 읽는 순서는 범위 접근을 할 수 없으므로 orders 1,000,000행을 풀 스캔해 하루치 1,440행을 걸러 낸 뒤 member를 기본 키로 1,440번 찾는다. member를 먼저 읽는 순서는 원래와 같이 회원 100,000명마다 idx_orders_member로 10행씩 찾고 행마다 클러스터형 인덱스에서 ordered_at을 확인하므로, 인덱스 탐색 100,000번과 클러스터형 룩업 1,000,000번이 든다. 앞의 순서는 순차 풀 스캔 한 번과 기본 키 탐색 1,440번, 뒤의 순서는 무작위 룩업 1,000,000번이므로 앞의 순서가 훨씬 싸다. 옵티마이저도 ordered_at 조건의 선택도를 제대로 추정한다면 orders를 드라이빙으로 두고 member를 eq_ref로 찾는 NLJ를 고를 가능성이 크다. 드리븐 쪽인 member에는 기본 키라는 인덱스가 있으므로 해시 조인이 필요한 상황이 아니다. 다만 ordered_at에 인덱스가 없으면 그 조건의 선택도는 히스토그램이 없는 한 근거가 약한 추정에 기대므로, 실제 선택은 EXPLAIN으로 확인해야 한다. MySQL 8.4.13에서 IGNORE INDEX (idx_orders_ordered)로 확인하면 옵티마이저는 실제로 o를 ALL로 먼저 읽고 m을 PRIMARY의 eq_ref로 찾는 NLJ를 골랐다. 이때 o 행의 filtered는 11.11, 트리 형식의 필터 예상 행 수는 109,742로 실제 1,440과 크게 다르다(값은 실행 환경과 통계에 따라 달라진다). 인덱스도 히스토그램도 없는 범위 조건에 기본 추정치가 쓰였다는 뜻이고, 이 경우에는 순서가 맞았지만 추정 자체는 근거가 약하다.

    5. member가 빌드 입력이면 부산 회원 10,000행에서 조인 키와 필요한 열(회원 번호 8바이트, 이름 12바이트 안팎)만 담기므로 자료만 200KB 안팎이다. 해시 테이블의 부가 공간을 더하면 256KB에 들어갈 수도, 조금 넘칠 수도 있는 경계의 크기다. 넘친다면 남은 빌드 행이 청크 파일로 나뉘고 프로브 행도 같은 공식으로 청크에 기록된 뒤 청크 쌍 단위로 다시 처리된다. orders가 빌드 입력이면 1,000,000행에서 회원 번호와 금액만 담아도 12MB 이상이므로 확실히 디스크로 넘치고, 청크 파일 수 상한(입력당 128개)과 open_files_limit까지 신경 써야 한다. 그래서 바이트 크기가 작은 쪽을 빌드 입력으로 고르는 것이 중요하고, 빌드 쪽 조건을 먼저 걸러 크기를 줄이는 것이 해시 조인에서도 효과가 있다.

     EXPLAIN에서 member m 행이 type ALL, rows 100,000, filtered 10.00이고, 그 아래 orders o 행이 type ref, rows 10이다. orders의 인덱스 탐색은 몇 번 반복될 것으로 예상된 것인가? 10번 약 10,000번 약 100,000번 1,000,000번 드리븐 테이블의 반복 횟수는 위쪽 행의 rows × filtered / 100 = 100,000 × 0.1 = 10,000이다. orders 행의 rows 10은 한 번 탐색할 때 나올 행 수이므로 반복 횟수가 아니다. 100,000은 반복 횟수에 한 번의 행 수를 곱한 전체 조인 행 수이고, 1,000,000은 주문 테이블 전체 행 수다. 진단 쿼리(부산 회원별 주문 건수와 금액 합계)에서 orders의 클러스터형 인덱스 룩업 100,000번을 없애는 변경은 무엇인가? member에 (region) 인덱스를 추가한다 join_buffer_size를 크게 늘린다 orders에 (member_id, amount) 인덱스를 추가한다 orders에 (amount, member_id) 인덱스를 추가한다 (member_id, amount)는 조인 열로 찾아 들어갈 수 있고 집계에 필요한 amount까지 담고 있어 항목만으로 처리가 끝난다(Using index). member의 인덱스는 드라이빙 쪽 비용만 바꾸고 드리븐 쪽 룩업은 그대로다. join_buffer_size는 인덱스 NLJ의 룩업과 관계가 없다. (amount, member_id)는 두 열을 담고 있지만 최좌측 열이 amount라서 회원 번호로 찾아 들어갈 수 없다. MySQL 8.0.20 이상의 해시 조인에 대한 설명으로 옳은 것은? 빌드 입력을 모두 읽어 해시 테이블을 만든 뒤에야 프로브를 시작하므로, 첫 결과 행이 나오는 시점이 NLJ보다 늦을 수 있다. 조인 조건에 등치 비교가 하나도 없으면 해시 조인을 쓸 수 없고 블록 중첩 루프로 돌아간다. 해시 테이블이 join_buffer_size를 넘으면 쿼리가 오류로 중단된다. 해시 조인을 끄려면 NO_HASH_JOIN 힌트를 쓴다. 해시 조인은 빌드 단계가 끝나야 프로브를 할 수 있으므로 첫 행이 늦다. 8.0.20부터는 등치 조건이 없는 조인에도 해시 조인을 쓰며(조건 없는 해시 조인 위에 필터) BNL은 더 이상 쓰이지 않는다. 메모리를 넘으면 청크 파일로 디스크를 쓴다(파일 수가 open_files_limit을 넘으면 실패할 수는 있다). HASH_JOIN·NO_HASH_JOIN 힌트는 8.0.18에서만 동작했고, 이후에는 BNL·NO_BNL 힌트를 쓴다. SELECT ... FROM member m LEFT JOIN orders o ON o.member_id = m.member_id WHERE o.status = 'CANCELED'에 대해 옳은 것은? LEFT JOIN이므로 member가 반드시 드라이빙 테이블이 된다. WHERE 조건이 오른쪽 테이블에 있으므로 주문이 없는 회원도 NULL로 채워져 결과에 남는다. 옵티마이저는 orders를 먼저 읽을 수 없으므로 JOIN_PREFIX(o, m) 힌트를 주면 오류가 난다. NULL로 채운 행은 WHERE에서 반드시 탈락하므로 내부 조인으로 바뀌고, orders를 먼저 읽는 순서도 고려할 수 있다. o.status = 'CANCELED'는 NULL로 채운 행에 대해 UNKNOWN이 되는 널 거부 조건이다. 매뉴얼에 따라 MySQL은 이런 외부 조인을 내부 조인으로 바꾸고, 그러면 왼쪽 테이블을 먼저 읽어야 한다는 제약이 사라진다. 주문이 없는 회원의 행은 결과에 남지 않는다. 외부 조인이 유지되는 경우라도 충돌하는 조인 순서 힌트는 오류 없이 무시된다. 커버링 인덱스를 추가하기 전과 후에 진단 쿼리의 카운터를 비교했다. 가장 크게 달라지는 것은 무엇이고, 그 이유는? Handler_read_next. 커버링 인덱스는 읽는 항목 수를 줄이기 때문이다. Innodb_buffer_pool_read_requests. 클러스터형 인덱스 룩업은 엔진 내부에서 일어나 Handler 카운터에는 따로 잡히지 않고 버퍼 풀 접근에만 나타나기 때문이다. Handler_read_key. 조인의 반복 횟수가 줄기 때문이다. EXPLAIN ANALYZE의 loops. 커버링 인덱스는 드라이빙 행 수를 줄이기 때문이다. 커버링 인덱스는 반복 횟수(10,000)도, 한 번에 읽는 항목 수(10)도 바꾸지 않으므로 Handler_read_key, Handler_read_next, loops는 거의 그대로다. 바뀌는 것은 항목마다 클러스터형 인덱스를 다시 내려가던 페이지 접근이고, 이것은 버퍼 풀의 논리적 읽기 요청 수에만 나타난다.
    중첩 루프 조인(nested-loop join, NLJ)
    바깥 테이블에서 행을 하나씩 읽어 안쪽 테이블에서 짝을 찾는 조인 알고리즘. MySQL의 기본 조인 방식이다.
    드라이빙 테이블(driving table)
    중첩 루프의 바깥 루프에서 읽는 테이블. 이 테이블의 조건 통과 행 수가 안쪽 접근의 반복 횟수가 된다.
    드리븐 테이블(driven table)
    바깥 행마다 짝을 찾아 들어가는 안쪽 테이블. 조인 열의 인덱스가 한 번의 접근 비용을 정한다.
    블록 중첩 루프(Block Nested-Loop, BNL)
    바깥 행을 조인 버퍼에 모아 안쪽 테이블을 훑는 횟수를 줄이던 알고리즘. 8.0.20부터 쓰이지 않고 해시 조인으로 대체되었다.
    해시 조인(hash join)
    한 입력으로 조인 키의 해시 테이블을 만들고(빌드), 다른 입력을 읽으며 해시 테이블을 찾는(프로브) 조인. 인덱스 없이 두 입력을 한 번씩 읽는다.
    조인 버퍼(join buffer)
    BNL, BKA, 해시 조인이 앞 테이블의 필요한 열을 담아 두는 메모리. 크기는 join_buffer_size로 정하며 기본값은 256KB다.
    세미조인(semijoin)
    바깥 행 중 서브쿼리와 짝이 맞는 행을 한 번씩만 돌려주는 연산. MySQL은 IN·EXISTS 서브쿼리를 세미조인으로 변환해 조인 순서와 중복 제거 전략을 비용으로 고른다.
    널 거부 조건(null-rejected condition)
    외부 조인이 만든 NULL 채움 행에 대해 FALSE나 UNKNOWN이 되는 조건. WHERE에 있으면 외부 조인이 내부 조인으로 바뀐다.
    배치 키 접근(Batched Key Access, BKA)
    조인 버퍼에 모은 키를 MRR로 엔진에 한꺼번에 넘겨, 드리븐 테이블의 행을 기본 키 순서로 읽게 하는 조인 방식. 기본으로 꺼져 있다.
    커버링 인덱스(covering index)
    쿼리가 그 테이블에서 쓰는 열을 모두 담고 있어 클러스터형 인덱스로 되돌아가지 않고 처리할 수 있는 인덱스. EXPLAIN의 Extra에 Using index로 나타난다.
