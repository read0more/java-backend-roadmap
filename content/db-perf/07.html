    이 회차의 질문: 스무 개를 보여 주려고 몇 개를 읽는가

    쇼핑몰의 상품 목록 화면을 떠올려 보자. 사용자가 카테고리를 고르면 판매 중인 상품을 최신순으로 20개씩 보여 준다. SQL로 쓰면 WHERE에 카테고리와 판매 상태, ORDER BY에 등록 시각, 끝에 LIMIT 20이 붙는 평범한 쿼리다. 서비스 초기에는 아무 문제가 없다. 그런데 상품이 늘어날수록 이 화면만 점점 느려진다. 이상한 일이다. 화면에 나가는 행은 언제나 20개인데, 왜 응답 시간은 카테고리의 크기를 따라 늘어나는가?

    답은 실행 계획의 한 단어에 들어 있다. EXPLAIN의 Extra 열에 Using filesort가 찍혀 있다면, MySQL은 조건에 맞는 행을 일단 모두 모은 뒤 정렬해서 앞의 20개를 고른다. 정렬이라는 작업은 입력을 다 보기 전에는 1등을 확정할 수 없으므로, LIMIT 20은 정렬이 끝난 뒤에야 힘을 쓴다. 읽는 양은 카테고리 크기에 비례하고, 돌려주는 양만 20으로 고정된다. 반대로 인덱스가 이미 원하는 순서로 행을 늘어놓고 있다면 정렬 단계가 없어지고, 앞에서부터 20개를 찾는 순간 읽기를 멈출 수 있다. 이것이 이 회차의 제목에 있는 조기 종료(early termination)다.

    이 회차는 하나의 상품 검색 쿼리를 따라간다. 먼저 EXPLAIN과 EXPLAIN ANALYZE로 증상을 진단하고, filesort가 실제로 무슨 일을 하는지 내려가 본다. 다음으로 인덱스가 정렬을 대신할 수 있는 조건을 B+Tree의 항목 순서에서 끌어내고, 첫 번째 해결책으로 복합 인덱스를 만들어 조기 종료가 일어나는 과정을 한 행씩 추적한다. 그런 다음 조기 종료가 언제 오히려 손해가 되는지, 옵티마이저는 그 판단을 어떤 가정으로 내리는지 본다. 마지막으로 두 번째 해결책으로 등치 조건 열을 인덱스에 넣어 읽기를 정확히 20행으로 줄이고, IN과 범위 조건이 끼어들 때 생기는 선택의 문제를 정리한다.

    설명의 기준은 MySQL 8.4와 InnoDB다. 내부 동작을 소스 코드로 확인한 문장에는 "8.4 소스 기준"이라고 적는다. EXPLAIN의 열은 02회, EXPLAIN ANALYZE의 측정값과 Top-N 정렬은 03회, B+Tree와 클러스터형·세컨더리 인덱스는 05·06회에서 다뤘으므로 여기서는 필요한 만큼만 상기한다. 인덱스 조건 푸시다운(ICP)과 커버링 인덱스는 08회, 내림차순 인덱스와 옵티마이저 힌트는 09회, 통계와 히스토그램은 10회, 조인이 낀 정렬은 11회, filesort의 메모리와 디스크 동작과 키셋 페이징은 12회의 몫이다.

    실습 테이블: 상품 100만 건

    실습용 상품 테이블을 만든다. 이 테이블은 이 회차의 설명을 위해 새로 설계한 것이다. 01회의 방식대로 난수를 쓰지 않고 행 번호 n에서 계산되는 규칙으로 모든 값을 정한다. 그래야 "이 쿼리는 몇 행을 읽어야 하는가"를 실행하기 전에 계산으로 맞힐 수 있고, 실행 계획이 보여 주는 숫자가 맞는지 판단할 수 있다.

    USE perf_lab;

CREATE TABLE product (
  product_id  BIGINT       NOT NULL,
  category_id INT          NOT NULL,
  name        VARCHAR(100) NOT NULL,
  price       INT          NOT NULL,
  status      VARCHAR(20)  NOT NULL,
  created_at  DATETIME     NOT NULL,
  PRIMARY KEY (product_id),
  KEY idx_category (category_id)
) ENGINE = InnoDB;

SET SESSION cte_max_recursion_depth = 1000000;

INSERT INTO product (product_id, category_id, name, price, status, created_at)
WITH RECURSIVE seq (n) AS (
  SELECT 1
  UNION ALL
  SELECT n + 1 FROM seq WHERE n < 1000000
)
SELECT n,
       MOD(n, 100) + 1,
       CONCAT('상품', n),
       (MOD(n, 997) + 1) * 100,
       CASE WHEN MOD(n DIV 100, 10) < 8 THEN 'ON_SALE'
            WHEN MOD(n DIV 100, 10) = 8 THEN 'SOLD_OUT'
            ELSE 'HIDDEN' END,
       TIMESTAMP('2023-01-01') + INTERVAL n * 60 SECOND
FROM seq;

ANALYZE TABLE product;

    규칙에서 바로 계산되는 사실을 정리하자. 뒤의 모든 숫자는 이 표에서 나온다.

    열규칙결과
    product_idn1~1,000,000, 등록 순서와 같다
    category_idn mod 100 + 1카테고리 100개에 정확히 10,000행씩. 카테고리 7은 n mod 100 = 6인 행, 즉 n = 100k + 6 (k = 0~9,999)
    name'상품' + n이름의 숫자 부분이 곧 product_id다
    price(n mod 997 + 1) × 100100~99,700원. 997은 100과 서로소인 소수라 카테고리와 얽히지 않는다
    status(n div 100) mod 10으로 결정0~7이면 ON_SALE, 8이면 SOLD_OUT, 9이면 HIDDEN. 전체 80% / 10% / 10%
    created_at2023-01-01 + n분n이 클수록 늦다. 모든 행이 서로 다르다

    카테고리 7의 행만 따로 보자. n = 100k + 6이므로 n div 100은 정확히 k이고, 상태는 k mod 10으로 정해진다. k를 큰 쪽부터, 즉 최신 상품부터 거꾸로 세면 상태는 "HIDDEN(k=9999), SOLD_OUT(k=9998), ON_SALE 8개(k=9997~9990), HIDDEN, SOLD_OUT, ON_SALE 8개, …"처럼 10개 주기로 반복된다. 카테고리 7은 ON_SALE 8,000행, SOLD_OUT 1,000행, HIDDEN 1,000행이다. 가장 최신 상품은 n = 999,906(2024-11-25 09:06:00 등록)이다.

    이 데이터에는 의도적으로 넣은 성질이 하나 있다. product_id와 created_at이 같은 순서로 증가한다. 실제 서비스에서 AUTO_INCREMENT 기본 키와 등록 시각이 함께 늘어나는 모습을 흉내 낸 것인데, 이 성질이 진단과 해결 방안에서 두 번 등장한다. 한 번은 "데이터로는 이미 정렬되어 있는데 왜 정렬하는가"라는 질문으로, 또 한 번은 "정렬 기준을 기본 키로 바꾸면 어떻게 되는가"라는 선택지로 나온다.

    실전 진단 1: 상품 검색 쿼리와 EXPLAIN

    진단할 쿼리는 이것이다. 카테고리 7의 판매 중 상품을 최신순으로 20개 가져온다.

    SELECT product_id, name, price, created_at
FROM product
WHERE category_id = 7
  AND status = 'ON_SALE'
ORDER BY created_at DESC
LIMIT 20;

    결과는 계산으로 정해진다. 최신 상품부터 ON_SALE인 것만 고르면 k = 9997, 9996, …, 9990(8개), 9987~9980(8개), 9977~9974(4개)이고, 첫 행은 product_id 999,706, 스무 번째 행은 997,406이다. MySQL 8.4.13에서 실행한 결과도 이 20행과 같다. 이제 EXPLAIN을 보자. 아래는 MySQL 8.4.13에서 실행한 결과이고, rows와 filtered 같은 예상치는 실행 환경과 통계에 따라 달라진다.

               id: 1
  select_type: SIMPLE
        table: product
   partitions: NULL
         type: ref
possible_keys: idx_category
          key: idx_category
      key_len: 4
          ref: const
         rows: 17918
     filtered: 10.00
        Extra: Using where; Using filesort

    02회에서 익힌 순서대로 읽는다. type: ref와 ref: const는 idx_category에서 category_id = 7인 항목을 상수 하나로 찾아 읽는다는 뜻이다. key_len: 4는 NOT NULL INT 열 하나, 즉 category_id만 썼다는 뜻이다. rows는 그렇게 읽을 것으로 예상하는 행 수다. 이 실행에서는 17,918이 나왔는데, 실제 카테고리 크기는 10,000이다. 이 값은 행을 세어 본 것이 아니라 인덱스 통계로 추정한 값이라 실제와 어긋날 수 있다(10회). filtered: 10.00은 status 조건을 통과할 비율을 10%로 본 것인데, status에는 인덱스도 히스토그램도 없어 옵티마이저가 등치 조건의 기본 추정치를 쓴 결과다. 실제 통과율은 80%다. Extra의 Using where는 인덱스로 찾은 행에 대해 서버가 조건을 더 평가한다는 뜻이고, 여기서 평가하는 조건은 status = 'ON_SALE'이다. idx_category에는 status가 없으므로 이 조건은 행을 클러스터형 인덱스에서 가져온 뒤에야 확인할 수 있다.

    그리고 Using filesort다. MySQL 매뉴얼은 이 표시를 "정렬된 순서로 행을 가져오는 방법을 알아내기 위해 한 번 더 처리해야 한다"고 설명한다. 접근 방법에 따라 행을 모두 훑으면서 WHERE 조건에 맞는 행의 정렬 키를 모으고, 키를 정렬한 다음 그 순서로 행을 돌려준다는 것이다. 이름에 file이 들어 있지만 파일을 쓴다는 뜻은 아니다. 매뉴얼의 ORDER BY 최적화 절은 filesort가 결과가 메모리에 다 들어가지 않을 때만 임시 디스크 파일을 쓴다고 설명하고, EXPLAIN은 정렬이 메모리 안에서 끝났는지를 구별하지 않는다고 밝힌다. Using filesort는 "인덱스로 순서를 얻지 못해 별도의 정렬 단계가 있다"는 뜻으로 읽어야 한다.

    데이터로는 이미 정렬되어 있는데 왜 정렬하는가

    여기서 짚어 볼 것이 있다. idx_category는 category_id 하나짜리 인덱스지만, 06회에서 본 것처럼 InnoDB의 세컨더리 인덱스 항목에는 기본 키가 붙어 있다. 매뉴얼의 "인덱스 확장" 절은 InnoDB가 모든 세컨더리 인덱스 뒤에 기본 키 열을 덧붙인다고 설명한다. 그러니 idx_category의 항목은 실제로 (category_id, product_id) 순서로 놓여 있고, 카테고리 7의 항목은 product_id 오름차순으로 나란하다. 이 데이터에서는 product_id 순서가 곧 created_at 순서이므로, idx_category를 거꾸로 읽기만 해도 최신순이 나온다.

    그런데도 옵티마이저는 정렬한다. 옵티마이저는 인덱스의 정의와 ORDER BY의 식을 비교할 뿐, 두 열의 값이 우연히 같은 순서로 증가한다는 사실은 알 수 없기 때문이다. ORDER BY에 적힌 열은 created_at이고 idx_category에는 created_at이 없다. 이 판단은 데이터가 아니라 선언에 근거한다. 이 점은 해결 방안에서 정반대의 방향으로 쓰인다. ORDER BY를 product_id로 바꾸면 같은 인덱스가 정렬을 대신할 수 있게 된다. 다만 그것은 "등록 순서와 기본 키 순서가 같다"는 업무 규칙을 SQL에 새기는 일이므로 따로 따져 볼 문제다.

    실전 진단 2: EXPLAIN ANALYZE로 읽는 낭비

    EXPLAIN은 계획만 보여 준다. 실제로 몇 행을 읽었는지는 EXPLAIN ANALYZE로 본다. 아래는 MySQL 8.4.13에서 실행한 결과다. 시간과 cost, 예상 rows는 실행 환경과 통계에 따라 달라지고, 데이터로 정해지는 것은 actual 쪽의 행 수와 루프 수다.

    -> Limit: 20 row(s)  (cost=4238 rows=20) (actual time=799..799 rows=20 loops=1)
    -> Sort: product.created_at DESC, limit input to 20 row(s) per chunk  (cost=4238 rows=17918) (actual time=799..799 rows=20 loops=1)
        -> Filter: (product.`status` = 'ON_SALE')  (cost=4238 rows=17918) (actual time=55.4..797 rows=8000 loops=1)
            -> Index lookup on product using idx_category (category_id=7)  (cost=4238 rows=17918) (actual time=55.4..795 rows=10000 loops=1)

    아래에서 위로 읽는다. Index lookup이 카테고리 7의 인덱스 항목 10,000개를 읽고, 항목마다 클러스터형 인덱스에서 행을 가져와 위로 올렸다. Filter가 그중 ON_SALE인 8,000행을 통과시켰다. Sort는 8,000행을 모두 받은 뒤 created_at 내림차순으로 앞의 20행만 남겼고, Limit이 그 20행을 돌려줬다. Sort 줄의 limit input to 20 row(s) per chunk는 03회에서 본 대로 LIMIT 값이 정렬에 전달되었다는 표시다. 8.4 소스의 EXPLAIN 출력 코드는 정렬 경로에 한도가 있을 때만 이 문구를 붙인다.

    이 출력에서 낭비를 세 가지 숫자로 읽을 수 있다.

    • 읽은 행과 돌려준 행의 비율: 맨 아래에서 10,000행을 읽었고 맨 위에서 20행을 돌려줬다. 500 대 1이다. 카테고리가 10만 행으로 커지면 읽는 양도 10만이 되지만 돌려주는 양은 여전히 20이다.
    • Sort의 첫 행 시간: 03회에서 본 대로 8.4 소스의 SortingIterator는 첫 Read() 전에 입력을 모두 읽고 정렬을 끝낸다. 그래서 Sort의 actual time=a..b에서 첫 행 시간 a가 이미 아래쪽 읽기 시간 전체를 포함하고, a와 b가 서로 가깝게 찍힌다. 위 실행에서도 Filter가 55.4..797인데 Sort는 799..799다. 정렬이 파이프라인을 끊었다는 표시다.
    • Filter의 통과율: 10,000행 중 8,000행이 통과했다. 2,000행은 클러스터형 인덱스까지 찾아가 행을 가져온 뒤 버려졌다. 상태 조건을 인덱스에서 확인할 수 없기 때문이다.

    10,000번의 클러스터형 인덱스 조회는 어디를 건드리는가

    Index lookup이 읽은 항목 하나는 클러스터형 인덱스 조회 한 번으로 이어진다. 06회에서 본 대로 세컨더리 인덱스 항목에는 기본 키 값만 있으므로, name, price, status, created_at을 얻으려면 기본 키로 클러스터형 인덱스의 루트부터 리프까지 다시 내려가야 한다. 카테고리 7의 기본 키는 6, 106, 206, …처럼 100 간격으로 흩어져 있다. 이 테이블의 행은 100바이트가 되지 않으므로(8바이트 기본 키, 숨은 열 13바이트, 짧은 문자열 두 개와 정수·날짜 몇 개) 16KB 리프 페이지 하나에 100행이 넘게 들어간다. MySQL 8.4.13에서 데이터를 넣은 뒤 mysql.innodb_index_stats를 보면 PRIMARY의 리프 페이지(n_leaf_pages)는 3,977개로, 페이지당 평균 250행쯤이다. 연속된 기본 키 100개 안에는 n mod 100 = 6인 값이 정확히 하나 있으므로, 카테고리 7의 행은 클러스터형 인덱스의 모든 리프 페이지에 하나 이상씩 들어 있다. 화면에 20행을 보여 주려고 테이블 전체의 리프 페이지를 버퍼 풀로 올리는 셈이다.

    이 실습 데이터에서는 카테고리 7의 항목이 기본 키 오름차순으로 읽히므로 조회도 리프 페이지를 앞에서 뒤로 차례로 방문한다. 실제 서비스에서는 같은 카테고리의 상품이 기본 키 순서와 무관하게 흩어져 있는 경우가 많고, 그러면 조회는 페이지 사이를 건너뛰는 랜덤 접근이 된다. 어느 쪽이든 읽기 양이 카테고리 크기에 비례한다는 사실은 변하지 않는다.

    숫자로 확인하는 다른 도구들

    EXPLAIN ANALYZE 말고도 읽기 양을 세는 방법이 있다. 세션의 핸들러 상태 변수는 서버가 스토리지 엔진에 보낸 읽기 요청의 수를 센다. FLUSH STATUS로 세션 카운터를 0으로 만든 뒤 쿼리를 실행하고 SHOW SESSION STATUS LIKE 'Handler_read%'로 확인한다. 매뉴얼은 Handler_read_key를 키로 행을 읽은 요청 수, Handler_read_next를 키 순서로 다음 행을 읽은 요청 수, Handler_read_prev를 키 순서로 이전 행을 읽은 요청 수로 설명하고, 마지막 것은 주로 ORDER BY ... DESC를 최적화하는 데 쓰인다고 적는다.

    8.4 소스로 이 쿼리가 일으키는 요청을 세어 보자. 정방향 ref 읽기는 첫 행을 ha_index_read_map()으로, 이후를 ha_index_next_same()으로 읽는다. InnoDB 핸들러는 앞의 호출에서 Handler_read_key를, 뒤의 호출에서 Handler_read_next를 하나씩 올린다. 카테고리 7의 항목 10,000개를 읽으려면 키 읽기 1번과 다음 행 읽기 9,999번이 필요하고, 마지막으로 "더 없음"을 확인하는 다음 행 읽기가 1번 더 있다. 이 쿼리의 실행만 놓고 보면 Handler_read_key가 1, Handler_read_next가 10,000 늘어난다. MySQL 8.4.13에서 FLUSH STATUS 뒤 이 쿼리를 실행하고 확인한 값도 Handler_read_key 1, Handler_read_next 10000이었고 나머지 Handler_read%는 0이었다. 해결 방안을 적용한 뒤 이 숫자가 어떻게 바뀌는지 비교할 것이다.

    운영 중인 서버에서 정렬을 많이 하는 쿼리를 찾을 때는 sys 스키마의 sys.statements_with_sorting 뷰가 출발점이 된다. 매뉴얼은 이 뷰를 정렬을 수행한 정규화된 문장의 목록으로 설명하고, 실행 횟수, 총 지연 시간, 병합 패스 수, 정렬한 행 수(rows_sorted) 같은 열을 제공한다. 한 가지 주의할 점이 있다. 8.4 소스의 filesort는 LIMIT이 있을 때 정렬 행 수를 상태 변수 Sort_rows에 더하기 직전에 LIMIT 값으로 잘라 낸다. 이 쿼리라면 정렬 단계에 들어간 행은 8,000개인데 Sort_rows에는 20이 더해진다. MySQL 8.4.13에서 실행해 보면 세션의 Sort_rows는 20, 성능 스키마 events_statements_history에 남은 이 문장의 SORT_ROWS도 20이다. 8.4 소스에서 같은 함수가 성능 스키마의 문장별 정렬 행 수도 같은 값으로 올리므로, 그 값을 모아 보여 주는 rows_sorted도 사정이 같다. 정렬 행 수만 보고 "20행 정렬이니 가볍다"고 판단하면 틀린다. 정렬에 들어간 입력의 크기는 EXPLAIN ANALYZE에서 Sort 바로 아래 노드의 행 수로 확인해야 한다.

    filesort는 무엇을 하는가

    진단 결과를 정확히 해석하려면 filesort 내부를 한 번 내려가 볼 필요가 있다. 03회에서 Top-N 우선순위 큐를 다뤘으니, 여기서는 그 바깥의 큰 흐름과 정렬 버퍼에 무엇이 담기는지를 본다. 아래 흐름은 8.4 소스의 filesort() 함수를 따라 정리한 것이다.

    핵심은 두 번째 단계다. 정렬 결과의 첫 행은 입력의 마지막 행일 수도 있으므로, filesort는 자식이 더 줄 행이 없다고 말할 때까지 읽기를 멈출 수 없다. 우선순위 큐는 메모리와 비교 횟수를 줄여 줄 뿐 읽는 양은 줄이지 못한다. 매뉴얼의 LIMIT 최적화 절도 같은 말을 한다. ORDER BY와 LIMIT을 함께 쓸 때 인덱스로 순서를 얻으면 매우 빠르지만, filesort를 해야 한다면 LIMIT이 없을 때 조건에 맞는 행을 모두 고르고 그 대부분 또는 전부를 정렬해야 첫 N행이 정해진다.

    정렬 버퍼에 담기는 것: 열 값이냐 행 위치냐

    매뉴얼은 정렬 버퍼에 담기는 튜플의 모양을 세 가지로 설명하고, 옵티마이저 트레이스의 filesort_summary에서 sort_mode로 확인하라고 안내한다. 는 정렬 키와 원래 행의 위치만 담는다. 정렬이 끝난 뒤 그 위치로 테이블을 다시 읽어야 하므로 행마다 추가 조회가 생긴다. 는 정렬 키와 쿼리가 참조하는 열 값을 함께 담는다. 정렬이 끝나면 버퍼에서 바로 결과를 만들 수 있다. 는 그 열 값들을 고정 길이 대신 실제 길이로 빽빽하게 채운 형태다. 8.4 소스는 이 문자열의 앞부분을 fixed_sort_key 또는 varlen_sort_key로 찍어 정렬 키가 고정 길이인지 가변 길이인지도 함께 보여 준다.

    어느 쪽을 쓸지는 실행 시점에 정해진다. 8.4 소스의 SortWillBeOnRowId()는 쿼리가 읽는 열 가운데 최대 길이가 70,000바이트를 넘는 BLOB 계열 열, 곧 MEDIUMBLOB·LONGBLOB과 그에 해당하는 MEDIUMTEXT·LONGTEXT가 있으면 행 위치로 정렬하게 한다. 소스 주석은 그런 열을 버퍼에 끌어 올리는 것은 매우 비효율적일 수 있다고 이유를 적는다. 전문 검색(MATCH)이 걸린 테이블도 행 위치로 정렬하는데, 이쪽은 MATCH가 엔진에 현재 행을 직접 묻기 때문에 행이 제자리에 위치해 있어야 한다는 다른 이유에서다. 상품 테이블에 MEDIUMTEXT 상세 설명 열이 있고 목록 쿼리를 SELECT *로 쓴다면, 정렬 방식이 행 위치로 바뀌어 정렬 뒤에 결과 행마다 테이블을 다시 읽는다. 목록 화면에 필요 없는 큰 열을 SELECT에서 빼는 것은 네트워크 전송량만이 아니라 정렬 방식에도 영향을 준다.

    트레이스로 정렬을 들여다보기

    옵티마이저 트레이스를 켜고 쿼리를 실행하면 실행 단계에 filesort_summary 객체가 남는다. 매뉴얼의 예시는 rows, examined_rows, number_of_tmp_files 같은 이름을 보여 주는데, 8.4 소스가 실제로 쓰는 이름은 조금 다르다. 8.4 소스 기준으로 주요 항목은 사용 가능한 메모리(memory_available), 정렬 키와 행의 크기(key_size, row_size), 정렬에 들어간 행 수(num_rows_found), 디스크로 내보낸 초기 청크 수(num_initial_chunks_spilled_to_disk), 최대 메모리 사용량(peak_memory_used), 정렬 알고리즘(sort_algorithm), 그리고 sort_mode다. 우리 쿼리라면 num_rows_found가 8,000이다. 앞에서 본 Sort_rows와 달리 이 값은 LIMIT으로 잘리기 전의 수다.

    실제로 num_rows_found는 8,000이고, 디스크로 내보낸 청크는 0개다. max_rows_per_buffer가 21이라 버퍼에는 LIMIT 20행에 한 행을 더한 만큼만 담긴다. 정렬 방식은 로, 열 값을 함께 담되 압축하지 않은 형태다. 그 이유를 unpacked_addon_fields 항목이 using_priority_queue로 적고 있다. num_rows_estimate는 통계에서 온 예상치라 실행할 때마다 달라질 수 있다.

    정렬 버퍼의 크기 상한은 sort_buffer_size이고 기본값은 262,144바이트(256KB)다. 매뉴얼은 정렬이 필요한 세션마다 이 크기의 버퍼를 할당한다고 설명하는 한편, ORDER BY 최적화 절에서는 옵티마이저가 정렬 버퍼를 필요한 만큼 조금씩 늘려 가며 이 값까지 할당한다고 밝힌다. 그래서 값을 키워도 작은 정렬이 메모리를 낭비하지는 않는다. 하지만 이 값을 키우는 것은 이 회차의 문제를 풀지 못한다. 버퍼가 아무리 커도 filesort는 입력을 모두 읽어야 하고, 우리 쿼리의 비용은 정렬이 아니라 그 입력 10,000행을 읽는 데 있기 때문이다. 정렬이 메모리를 넘쳐 디스크로 병합하는 경우와 그 튜닝은 12회에서 다룬다.

    왼쪽은 Sort가 아래에서 10,000행을 모두 받은 뒤 20행을 내보내는 모습, 오른쪽은 인덱스를 역순으로 읽다가 20행을 채우는 순간 읽기가 멈추는 모습을 나란히 보여 준다. 좌우 두 패널. 왼쪽 패널 제목 "filesort 계획". 아래에서 위로 쌓인 네 개의 상자: 맨 아래 "인덱스 조회 10,000행", 그 위 "필터 8,000행", 그 위 "정렬", 맨 위 "LIMIT 20". 아래 상자에서 위로 굵은 화살표가 여러 개 올라가고, 정렬 상자 앞에 행들이 쌓여 있는 더미가 그려져 있다. 정렬 상자 옆에 라벨 "입력을 다 받아야 첫 행". 오른쪽 패널 제목 "인덱스 순서 계획". 아래에서 위로 세 개의 상자: "역순 인덱스 조회 26행", "필터 20행", "LIMIT 20". 아래 상자 옆에 긴 인덱스 띠가 있고 위쪽 끝 일부만 칠해져 있으며 그 경계에 정지 표시와 라벨 "여기서 멈춤". 평면 스타일, 흰 배경, 두 패널은 같은 높이. 정렬이 있으면 LIMIT은 정렬이 끝난 뒤에야 작동한다. 인덱스가 순서를 주면 LIMIT이 아래쪽 읽기를 직접 멈춘다.

    정렬을 없애는 원리: 인덱스는 이미 정렬된 목록이다

    정렬 단계를 없애려면 행이 처음부터 원하는 순서로 나오면 된다. 05회에서 본 B+Tree의 리프 페이지는 키 순서로 항목을 담고, 리프 페이지끼리 앞뒤로 연결되어 있다. 인덱스를 한쪽 끝에서 다른 쪽 끝으로 따라가면 키의 오름차순이, 거꾸로 따라가면 내림차순이 나온다. 인덱스는 저장 구조이기 이전에 항상 정렬 상태로 유지되는 목록이다. 정렬 비용은 행을 넣고 고칠 때 이미 치렀다.

    복합 인덱스의 순서는 사전식(lexicographic)이다. (category_id, created_at) 인덱스라면 항목은 먼저 category_id로 정렬되고, category_id가 같은 항목끼리는 created_at으로, 그것마저 같으면 InnoDB가 덧붙인 product_id로 정렬된다. 사전에서 첫 글자가 같은 단어끼리 둘째 글자로 정렬되는 것과 같다. 이 인덱스의 리프 항목을 몇 개만 적어 보면 다음과 같다.

    idx_category_created 리프 항목 (category_id, created_at, [product_id])

  ...
  (6, 2024-11-25 09:05:00, 999905)
  (7, 2023-01-01 00:06:00,      6)   ← 카테고리 7의 첫 항목
  (7, 2023-01-01 01:46:00,    106)
  (7, 2023-01-01 03:26:00,    206)
  ...                                   카테고리 7 안에서는 created_at 오름차순
  (7, 2024-11-25 05:46:00, 999706)
  (7, 2024-11-25 07:26:00, 999806)
  (7, 2024-11-25 09:06:00, 999906)   ← 카테고리 7의 마지막 항목 (역순 읽기의 출발점)
  (8, 2023-01-01 00:07:00,      7)
  ...

    WHERE에 category_id = 7이 있으면 읽는 구간은 카테고리 7의 항목들로 좁혀지고, 그 구간 안에서 category_id는 모두 7이라는 상수다. 상수인 열은 순서에 아무 영향을 주지 않으므로, 이 구간을 읽는 순서는 곧 created_at의 순서다. 매뉴얼의 ORDER BY 최적화 절이 바로 이 경우를 예로 든다. (key_part1, key_part2) 인덱스가 있을 때 WHERE key_part1 = constant ORDER BY key_part2는 인덱스로 정렬을 피할 수 있다. 매뉴얼은 더 일반적으로, ORDER BY가 인덱스와 정확히 일치하지 않더라도 인덱스에서 쓰지 않는 부분과 ORDER BY의 추가 열이 모두 WHERE에서 상수로 고정되면 인덱스를 쓸 수 있다고 정리한다.

    이 원리에서 판정 규칙이 나온다. 인덱스의 열을 앞에서부터 보면서, WHERE에서 등치 조건으로 상수가 된 열은 건너뛸 수 있다. 건너뛰고 남은 열들이 ORDER BY의 열과 같은 순서로, 빈틈없이 이어지면 인덱스가 정렬을 대신한다. 방향은 모두 같거나(전부 ASC 또는 전부 DESC), 인덱스에 정의된 방향의 조합과 맞아야 한다. 모두 DESC라면 오름차순 인덱스를 거꾸로 읽으면 된다.

    일상에서 가져온 비유지역별로 묶인 전화번호부

    지역별로 나뉘고 지역 안에서는 이름순으로 정렬된 전화번호부가 있다고 하자. "부산 사람을 이름순으로 20명"이라면 부산 장을 펴서 앞에서 20명을 읽으면 끝이다. 하지만 "부산과 대구 사람을 이름순으로 20명"이라면 두 장을 나란히 펴 놓고 번갈아 비교해야 하고, "부산 사람을 나이순으로 20명"이라면 이 책의 순서는 쓸모가 없어 부산 장 전체를 옮겨 적은 뒤 다시 정렬해야 한다. 비유가 깨지는 지점도 있다. 사람은 두 장을 번갈아 보며 병합할 수 있지만, MySQL은 여러 구간에서 읽은 행을 병합해 순서를 만들지 않고 정렬 단계를 둔다.

    해결 방안 1: (category_id, created_at) 복합 인덱스

    규칙을 우리 쿼리에 적용하자. 등치 조건 열은 category_id와 status, 정렬 열은 created_at이다. 가장 먼저 떠오르는 인덱스는 (category_id, created_at)이다. category_id를 상수로 고정하면 다음 열 created_at이 ORDER BY와 일치한다. status는 인덱스에 없으므로 여전히 행을 가져온 뒤 확인해야 하지만, 정렬은 없어진다.

    ALTER TABLE product
  ADD INDEX idx_category_created (category_id, created_at),
  DROP INDEX idx_category;

    idx_category를 함께 지운 데는 이유가 있다. 새 인덱스의 첫 열이 category_id이므로, category_id만으로 찾는 쿼리는 새 인덱스의 왼쪽 부분(leftmost prefix)으로 똑같이 처리할 수 있다. 같은 앞부분을 가진 인덱스를 둘 다 두면 행을 넣고 고칠 때마다 두 B+Tree를 모두 갱신해야 하고 버퍼 풀도 나눠 써야 한다. 이 실습에서는 옵티마이저가 고를 후보를 하나로 줄여 실행 계획을 분명하게 보려는 목적도 있다.

             type: ref
possible_keys: idx_category_created
          key: idx_category_created
      key_len: 4
          ref: const
         rows: 18798
     filtered: 10.00
        Extra: Using where; Backward index scan

    Extra에서 Using filesort가 사라지고 Backward index scan이 나타났다. 접근 방법은 이전과 같은 ref이고, key_len도 4로 같다. 인덱스에서 찾는 데 쓴 열은 여전히 category_id 하나뿐이다. 바뀐 것은 그 구간을 읽는 방향이다. ORDER BY가 DESC이므로 카테고리 7 구간의 끝에서부터 거꾸로 읽는다. MySQL의 내림차순 인덱스 작업 문서(WL#1074)는 전통적인 EXPLAIN이 역방향 인덱스 스캔을 쓸 때 Extra에 "Backward index scan"을 표시하고, 정방향일 때는 아무것도 표시하지 않는다고 적는다. Extra 항목의 순서가 "Using where; Backward index scan"인 것은 8.4 소스의 EXPLAIN 코드가 조건 표시를 먼저, 역방향 표시를 그다음에 붙이기 때문이다.

    -> Limit: 20 row(s)  (cost=3918 rows=20) (actual time=0.453..0.46 rows=20 loops=1)
    -> Filter: (product.`status` = 'ON_SALE')  (cost=3918 rows=1880) (actual time=0.448..0.454 rows=20 loops=1)
        -> Index lookup on product using idx_category_created (category_id=7) (reverse)  (cost=3918 rows=18798) (actual time=0.425..0.43 rows=26 loops=1)

    Sort 노드가 없고, 인덱스 조회 줄 끝에 (reverse)가 붙었다. 8.4 소스의 EXPLAIN 출력 코드는 인덱스 접근 경로가 역방향일 때 인덱스 이름과 조회 조건 뒤에 이 표시를 붙인다. 그리고 맨 아래 행 수가 10,000에서 26으로 줄었다. 26이라는 숫자는 데이터에서 정확히 계산된다. 역순으로 읽기 시작하는 항목은 k = 9999(HIDDEN), 다음은 k = 9998(SOLD_OUT), 그다음 k = 9997부터 9990까지 ON_SALE 8개다. 이 10행 주기를 두 번 돌면 ON_SALE이 16개, 세 번째 주기에서 HIDDEN과 SOLD_OUT을 지나 ON_SALE 4개를 더 읽으면 20개가 찬다. 마지막으로 읽은 항목은 k = 9974, 곧 product_id 997,406이다. 9999부터 9974까지 26개의 항목을 읽었고, 그중 6개는 Filter에서 버려졌다.

    조기 종료: 누가 읽기를 멈추는가

    읽기를 멈춘 주체는 Limit 노드다. 03회에서 본 대로 MySQL의 실행기는 위쪽 이터레이터가 아래쪽 이터레이터의 Read()를 불러 행을 하나씩 끌어 올리는 풀(pull) 방식으로 돈다. 정렬이 없으면 행은 읽히는 즉시 위로 흘러가고, Limit은 스무 번째 행을 받은 다음부터 아래쪽의 Read()를 더 부르지 않는다. 아래쪽 이터레이터는 "그만 읽으라"는 신호를 받는 것이 아니라 그냥 더 이상 불리지 않는다. 호출 순서를 펼쳐 보면 다음과 같다.

    핸들러 카운터로도 같은 결과를 확인할 수 있다. 8.4 소스의 InnoDB 핸들러는 역방향 첫 읽기(index_read_last)를 일반 키 읽기로 처리해 Handler_read_key를 올리고, 이후의 index_prev 호출마다 Handler_read_prev를 올린다. 26개 항목을 읽었으니 이 쿼리의 실행만 놓고 보면 Handler_read_key가 1, Handler_read_prev가 25 늘어난다. MySQL 8.4.13에서 측정한 값도 같았다. 해결 전에는 키 읽기 1번과 다음 행 읽기 10,000번, 모두 10,001번의 읽기 요청이 있었으니 그것이 26번으로 줄었다. 클러스터형 인덱스 조회도 26번이다. 기본 키 999,906부터 997,406까지 100 간격의 26개 행이므로 리프 페이지 몇 개 안에 들어 있다.

    옵티마이저가 왜 정렬을 생략했는지는 트레이스에서 볼 수 있다. 8.4 소스는 ORDER BY를 처리할 때 reconsidering_access_paths_for_index_ordering이라는 단계를 기록하고, 그 안의 index_order_summary에 인덱스가 순서를 제공하는지(index_provides_order), 방향이 무엇인지(order_direction가 asc 또는 desc), 접근 계획을 바꿨는지(plan_changed)를 남긴다. MySQL 8.4.13에서 우리 쿼리의 트레이스를 보면 index가 idx_category_created, access_type이 ref, index_provides_order가 true, order_direction이 desc, plan_changed가 true로 기록된다.

    역방향 읽기는 공짜가 아니다

    Backward index scan은 문제의 신호가 아니다. 조기 종료가 일어나고 있다는 점에서 오히려 좋은 신호다. 다만 같은 항목 수라면 정방향보다 일이 조금 많다. WL#1074는 내림차순 인덱스가 필요한 이유로 "역방향 인덱스 스캔이 정방향보다 눈에 띄게 느리다"는 점을 들고, 순서를 주는 인덱스를 고르는 옵티마이저 함수가 역방향보다 정방향 스캔을 우선하도록 바꿨다고 적는다. WL#1074는 그 원인을 적지 않지만, 역방향 이동에 드는 추가 작업 하나를 InnoDB 페이지의 구조에서 확인할 수 있다. 페이지 안의 레코드는 키 오름차순의 단방향 연결 목록으로 이어져 있고, 레코드마다 다음 레코드의 위치만 기록한다. 8.4 소스의 page_rec_get_prev_const()는 이전 레코드를 찾기 위해, 현재 레코드를 소유한 페이지 디렉터리 슬롯을 찾은 뒤 그 앞 슬롯이 가리키는 레코드에서 출발해 현재 레코드에 닿을 때까지 다음 포인터를 따라 걷는다. 한 칸 뒤로 가려고 몇 칸을 앞으로 걷는 셈이다. 내림차순 정렬이 핵심인 쿼리라면 열을 DESC로 정의한 내림차순 인덱스를 만들어 정방향으로 읽게 할 수 있는데, 이것은 09회에서 다룬다.

    역방향 읽기에는 기능상의 제약도 하나 있다. 8.4 소스의 옵티마이저는 ref 접근을 역방향으로 바꿀 때, 현재의 역방향 ref 구현이 인덱스 조건 푸시다운(ICP)과 잘 맞지 않아 실행 시간이 늘 수 있다는 주석과 함께 이미 붙인 푸시다운 조건을 취소한다. 역방향 ref 읽기 코드 자체도 푸시다운 조건이 없다는 것을 전제로 하고, 그 이유로 스토리지 엔진이 언제 읽기를 멈춰야 할지 몰라 조건에 맞는 레코드가 없으면 인덱스의 처음까지 읽어 갈 수 있다는 점을 든다. 08회에서 ICP를 다룰 때 이 제약을 다시 만난다.

    (category_id, created_at) 인덱스 리프 항목이 가로로 늘어서 있고, 카테고리 7 구간의 오른쪽 끝에서 왼쪽으로 화살표가 진행하다가 26번째 항목에서 멈추며, 항목마다 상태 색이 다르게 칠해져 통과와 버림이 구별되는 그림. 가로로 긴 띠 모양의 B+Tree 리프 페이지 열. 띠는 세 구간으로 나뉘고 라벨은 왼쪽부터 "카테고리 6", "카테고리 7", "카테고리 8". 카테고리 7 구간 안의 작은 칸들 위에 왼쪽 끝 "오래된 상품", 오른쪽 끝 "최신 상품" 라벨. 카테고리 7 구간 오른쪽 끝에서 시작해 왼쪽으로 향하는 굵은 화살표, 라벨 "역순 읽기". 화살표가 지나간 칸은 26개이며 초록 칸(라벨 "ON_SALE 통과")과 회색 칸(라벨 "HIDDEN·SOLD_OUT 버림")이 섞여 있다. 26번째 칸 왼쪽에 빨간 세로선과 라벨 "20행 채움, 멈춤". 그 왼쪽의 나머지 칸들은 흐리게 그리고 라벨 "읽지 않은 9,974개". 평면 스타일, 흰 배경. 카테고리 7 구간은 이미 등록 시각 순서로 놓여 있으므로, 끝에서부터 읽다가 판매 중 상품 20개가 차는 순간 멈출 수 있다.

    조기 종료의 비용은 일치하는 행이 어디에 있는가에 달려 있다

    26이라는 숫자는 ON_SALE이 80%나 되기 때문에 나왔다. 조건을 통과하는 행이 드물면 20개를 채우기까지 더 많이 읽어야 한다. 그렇다면 얼마나 더 읽는가? 상품 검색 화면에는 가격대나 검색어 같은 조건이 자주 붙으므로, idx_category_created를 역순으로 읽는 같은 계획에 조건을 하나씩 더해 보자. 아래 표의 숫자는 모두 생성 규칙에서 계산한 값이고, 앞의 두 열은 MySQL 8.4.13에서 COUNT(*)와 EXPLAIN ANALYZE의 Index lookup actual rows로 확인한 값과 모두 같다. 여섯 쿼리 모두 idx_category_created를 역순으로 읽는 같은 계획으로 실행되었다. "균등 가정 예상"은 일치하는 행이 카테고리 안에 고르게 퍼져 있다고 보고 20을 일치 비율로 나눈 값이다.

    status = 'ON_SALE'에 더한 조건카테고리 7에서 조건을 모두 만족하는 행20행을 채우기까지 읽은 항목균등 가정 예상
    (없음)8,0002625
    price BETWEEN 10000 AND 20000811198약 247
    price BETWEEN 50000 AND 50900812,368약 2,469
    name LIKE '상품9%'88826약 225
    name LIKE '상품1%'8898,026약 225
    price = 99700810,000 (8행만 돌려줌)20행이 안 됨

    가격 조건의 세 줄은 균등 가정과 실제가 거의 맞는다. 가격 규칙이 n mod 997로 정해져 등록 시각과 얽히지 않으므로, 일치하는 행이 정말로 카테고리 안에 고르게 흩어져 있기 때문이다. 일치 비율이 8,000분의 1만큼 떨어질 때마다 읽는 양이 그만큼 늘어난다는, 예상할 수 있는 관계다.

    이름 조건의 두 줄이 이 절의 핵심이다. 두 조건은 일치하는 행의 수가 888과 889로 사실상 같다. 그런데 읽은 항목은 26과 8,026으로 300배 넘게 차이가 난다. 이름의 숫자 부분이 product_id이고 product_id는 등록 순서이므로, '상품9'로 시작하는 카테고리 7의 상품은 대부분 가장 최근에 등록된 900,006~999,906 구간에 있고, '상품1'로 시작하는 상품은 대부분 100,006~199,906 구간, 곧 오래된 쪽에 있다. 역순 읽기는 최신 쪽에서 출발하므로 앞의 조건은 출발하자마자 일치 행을 만나고, 뒤의 조건은 그보다 새로운 8,000개 항목을 모두 지나야 첫 일치 행을 만난다. 조기 종료의 비용은 일치하는 행의 개수가 아니라 정렬 순서 위에서의 위치로 정해진다. 정렬 열과 조건 열 사이에 상관관계가 있으면 균등 가정은 어느 쪽으로든 크게 빗나간다.

    마지막 줄은 최악의 경우다. 조건에 맞는 행이 20개보다 적으면 Limit은 끝내 한도에 닿지 못하고, 역순 읽기는 카테고리 7의 구간을 끝까지 읽는다. 읽은 양은 10,000으로, 처음의 filesort 계획과 같아진다. 여기서 중요한 관찰이 하나 나온다. 인덱스 구간이 카테고리로 묶여 있는 한, 조기 종료 계획의 최악은 그 구간 전체를 읽는 것이고, 그것은 filesort 계획이 매번 하던 일이다. 같은 구간 안에서라면 조기 종료 계획은 정렬을 하지 않는 만큼 손해를 보지 않는다.

    구간이 넓어지면 이야기가 달라진다

    위험해지는 것은 순서를 주는 인덱스의 구간이 필터 인덱스의 구간보다 넓을 때다. 정렬 열 하나로만 만든 인덱스를 생각해 보자. idx_created (created_at)만 있고 카테고리 인덱스가 없다면, 이 인덱스로 최신순 20개를 얻으려면 테이블 전체에 걸친 인덱스를 역순으로 읽으며 카테고리와 상태를 하나하나 확인해야 한다. 카테고리 7은 100행에 하나씩 나오고 그중 80%가 ON_SALE이므로, 계산하면 product_id 1,000,000부터 997,406까지 2,595개 항목을 읽어 20행을 채운다. MySQL 8.4.13에서 idx_created를 만들어 FORCE INDEX로 실행해 보면 Index scan on product using idx_created (reverse)가 실제로 2,595행을 읽는다. 균등 가정 예상 20 ÷ (0.01 × 0.8) = 2,500과 비슷하다. 하지만 이 인덱스로 상품이 30개뿐인 작은 카테고리를 조회하면 사정이 다르다. 그 30개가 테이블 전체에 고르게 흩어져 있다면 스무 번째 일치 행을 만나기까지 전체의 약 3분의 2, 곧 수십만 개 항목을 읽고, 일치 행이 20개도 안 되면 100만 항목을 모두 읽는다. 같은 쿼리를 카테고리 인덱스로 처리했다면 30행을 읽고 30행을 정렬하면 끝났을 일이다. 조기 종료 계획의 최악은 "순서를 주는 인덱스에서 읽게 되는 구간 전체"이고, 그 구간이 넓을수록 최악도 커진다.

    같은 개수의 일치 행이 정렬 순서의 최신 쪽에 몰린 경우와 오래된 쪽에 몰린 경우를 위아래 두 띠로 놓고, 역순 읽기가 각각 어디까지 가야 20행을 채우는지 대비한다. 위아래로 놓인 두 개의 긴 가로 띠. 두 띠 모두 왼쪽 끝 라벨 "오래된 상품", 오른쪽 끝 라벨 "최신 상품". 위쪽 띠 제목 "name LIKE '상품9%'", 일치 행을 뜻하는 진한 점들이 오른쪽 끝 10% 구간에 몰려 있고, 오른쪽 끝에서 왼쪽으로 짧은 화살표가 나가 곧바로 멈추며 라벨 "26개 읽고 멈춤". 아래쪽 띠 제목 "name LIKE '상품1%'", 진한 점들이 왼쪽에서 두 번째 10% 구간에 몰려 있고, 오른쪽 끝에서 왼쪽으로 긴 화살표가 그 구간까지 가서 멈추며 라벨 "8,026개 읽고 멈춤". 두 띠 사이 가운데에 라벨 "일치 행 수는 거의 같다". 평면 스타일, 흰 배경. 일치하는 행이 888개와 889개로 같아도, 정렬 순서에서 어디에 있느냐에 따라 조기 종료가 읽는 양은 300배 넘게 달라진다.

    옵티마이저는 어떻게 고르는가: LIMIT과 순서를 주는 인덱스

    인덱스가 여러 개 있으면 옵티마이저는 "조건으로 행을 좁혀 주는 인덱스로 읽고 정렬한다"와 "순서를 주는 인덱스로 읽다가 일찍 멈춘다" 사이에서 골라야 한다. 매뉴얼의 LIMIT 최적화 절은 LIMIT으로 몇 행만 고를 때 MySQL이 평소라면 풀 테이블 스캔을 했을 쿼리에서 인덱스를 쓸 수 있다고 밝히고, ORDER BY나 GROUP BY에 LIMIT이 붙은 쿼리에서는 그것이 더 빠를 것 같을 때 순서가 있는 인덱스를 선호한다고 설명한다. 이 동작은 optimizer_switch의 prefer_ordering_index 플래그가 제어한다. 기본값은 on이다.

    매뉴얼의 플래그 설명은 이 최적화의 약점을 스스로 밝힌다. 이 판단을 내리는 알고리즘은 데이터 분포가 늘 대체로 균일하다고 가정하는 탓에 모든 경우를 다룰 수 없고, 그래서 이 최적화가 바람직하지 않은 경우가 있다는 것이다. MySQL 8.0.21 이전에는 이 최적화를 끌 수 없었고, 8.0.21부터는 기본 동작은 그대로 두되 플래그를 off로 해서 끌 수 있다.

    그 가정이 어디에 들어 있는지 8.4 소스에서 볼 수 있다. 순서를 주는 더 싼 인덱스를 찾는 test_if_cheaper_ordering()의 주석은 이렇게 적는다. 검사하는 인덱스가 현재 조건 인덱스(ref_key)와 상관관계가 없다고 가정하므로, 처음 N개의 행을 고르려면 N ÷ 선택도(ref_key)개의 인덱스 항목을 훑어야 하고, 선택도는 조건 인덱스로 읽을 행 수를 테이블 전체 행 수로 나눈 값이다. 앞 절의 균등 가정 예상과 같은 계산이다. 이 식에 카테고리 조건만 넣어 보면, idx_category가 1만 행을 고르고 테이블이 100만 행이므로 idx_created를 역순으로 읽을 때 20 × 1,000,000 ÷ 10,000 = 2,000개 항목이면 된다고 본다. 실제로는 상태 조건까지 겹쳐 2,595개였다.

    이 정도 차이는 문제가 되지 않는다. 문제는 상관관계가 있을 때다. 카테고리 7의 상품 1만 개가 모두 서비스 초기에 등록된 가장 오래된 1만 개라고 해 보자. 식은 여전히 2,000개쯤 읽으면 된다고 계산하지만, idx_created를 최신 쪽부터 읽으면 나머지 99만 개 항목을 모두 지나야 첫 일치 행을 만난다. 앞 절의 '상품1%' 조건과 같은 구조가 테이블 전체 규모로 일어나는 것이다. 이런 계획은 EXPLAIN만 보면 그럴듯하다. 인덱스를 쓰고 filesort도 없다. 하지만 EXPLAIN ANALYZE의 맨 아래 행 수가 진실을 보여 준다.

    매뉴얼은 이 플래그의 효과를 예제로 보여 준다. 기본 키가 id1이고 (id2, c1) 인덱스 i가 있는 테이블에서 SELECT c2 FROM t WHERE id2 > 3 ORDER BY id1 ASC LIMIT 2를 실행하면, 플래그가 켜져 있을 때는 기본 키를 순서대로 훑는 계획(type: index, key: PRIMARY, Extra Using where)을 고른다. 플래그를 끄면 인덱스 i로 범위를 읽고 정렬하는 계획(type: range, key: i, Extra Using index condition; Using filesort)으로 바뀐다. 어느 쪽이 빠른지는 id2 > 3인 행이 기본 키 순서의 어디에 있는가에 달려 있고, 그것은 통계만으로는 알 수 없다.

    -- 세션 전체에서 끄기 (MySQL 8.0.21 이상)
SET optimizer_switch = 'prefer_ordering_index=off';

-- 이 문장에서만 끄기: SET_VAR 힌트
SELECT /*+ SET_VAR(optimizer_switch = 'prefer_ordering_index=off') */
       product_id, name, price, created_at
FROM product
WHERE category_id = 7 AND status = 'ON_SALE'
ORDER BY created_at DESC
LIMIT 20;

    플래그를 끄는 것은 넓은 범위에 영향을 주는 결정이므로, 대개는 문제가 된 쿼리 하나에만 힌트를 붙이거나 인덱스 설계를 바꿔 선택지 자체를 정리하는 편이 낫다. 옵티마이저 힌트와 인덱스 힌트는 09회, 옵티마이저가 선택도를 추정하는 통계와 히스토그램은 10회에서 자세히 다룬다. 여기서 기억할 것은 진단의 순서다. LIMIT이 있는 쿼리가 느리다면 EXPLAIN ANALYZE에서 맨 아래 노드가 몇 행을 읽었는지 보고, 그것이 LIMIT보다 훨씬 크다면 원인이 정렬(filesort 계획)인지 일치 행의 희소함이나 위치(조기 종료 계획)인지를 구별한다.

    해결 방안 2: 등치 조건 열을 정렬 열 앞에 둔다

    해결 방안 1에서 남은 낭비는 Filter가 버린 6행이다. 상태를 인덱스에서 확인할 수 없어서 HIDDEN과 SOLD_OUT 상품까지 클러스터형 인덱스에서 가져와 본 뒤에 버렸다. 상태 조건도 등치 조건이므로 인덱스에 넣을 수 있다. 판정 규칙을 다시 떠올리면, 등치 조건으로 상수가 된 열은 정렬 순서에 영향을 주지 않으므로 정렬 열 앞에 몇 개를 두어도 된다.

    ALTER TABLE product
  ADD INDEX idx_category_status_created (category_id, status, created_at);
             type: ref
possible_keys: idx_category_created,idx_category_status_created
          key: idx_category_status_created
      key_len: 86
          ref: const,const
         rows: 14948
     filtered: 100.00
        Extra: Backward index scan

    key_len 86은 category_id의 4바이트에 status의 82바이트를 더한 값이다. status는 utf8mb4의 VARCHAR(20)이므로 20자 × 최대 4바이트 = 80바이트에 길이 정보 2바이트가 붙고, NOT NULL이라 NULL 표시 바이트는 없다. 인덱스의 앞 두 열을 모두 썼다는 뜻이고, ref: const,const가 같은 사실을 보여 준다. 그리고 Extra에서 Using where가 사라졌다. 8.4 소스의 옵티마이저는 ref 접근이 이미 보장하는 열 = 값 조건을 남은 조건에서 지우는데, 이진(BINARY·VARBINARY) 문자열 열이나 NO PAD 콜레이션의 CHAR 열처럼 인덱스 값과 테이블 값의 비교가 달라질 수 있는 경우만 예외로 남긴다. status는 그런 예외가 아니므로 두 조건이 모두 인덱스 조회에 흡수되어, 서버가 따로 평가할 조건이 없다.

    -> Limit: 20 row(s)  (cost=10376 rows=20) (actual time=54.3..54.5 rows=20 loops=1)
    -> Index lookup on product using idx_category_status_created (category_id=7, status='ON_SALE') (reverse)  (cost=10376 rows=14948) (actual time=54.3..54.3 rows=20 loops=1)

    Filter 노드도 없어졌고, 인덱스 조회가 정확히 20행을 읽었다. (7, 'ON_SALE') 구간의 항목들은 created_at 순서로 놓여 있고 모두 조건을 만족하므로, 끝에서부터 20개를 읽으면 그것이 답이다. 핸들러 카운터로는 Handler_read_key 1, Handler_read_prev 19이고(MySQL 8.4.13에서 측정한 값도 같다), 클러스터형 인덱스 조회도 20번이다. 결과 행에 필요한 name과 price가 인덱스에 없으니 조회 자체는 피할 수 없다. 이 마지막 조회까지 없애는 커버링 인덱스는 08회의 주제다.

    지금까지의 과정을 표로 모으면 다음과 같다. 모두 카테고리 7의 판매 중 상품 최신순 20개를 구하는 같은 쿼리다.

    인덱스Extra읽은 인덱스 항목정렬에 들어간 행버린 행
    idx_category (category_id)Using where; Using filesort10,0008,0002,000(필터) + 7,980(정렬)
    idx_category_created (category_id, created_at)Using where; Backward index scan2606(필터)
    idx_category_status_created (category_id, status, created_at)Backward index scan2000

    등치, 정렬, 그다음: 열 순서의 규칙

    이 결과를 일반화하면 정렬이 있는 쿼리의 인덱스 열 순서에 대한 규칙이 된다. 첫째, WHERE에서 등치 조건으로 하나의 값에 고정되는 열을 앞에 둔다. 둘째, 그 뒤에 ORDER BY의 열을 ORDER BY에 적힌 순서대로 둔다. 셋째, 범위 조건이나 그 밖의 조건에 쓰이는 열은 필요하면 그 뒤에 둔다. 뒤에 둔 열은 인덱스의 탐색 구간을 좁히지는 못하지만, 인덱스 항목만 보고 조건을 확인할 수 있게 해 준다. 그 확인을 스토리지 엔진 안에서 해 주는 것이 08회의 ICP다. 다만 앞에서 본 대로 8.4 소스는 역방향 ref 읽기에서 ICP를 취소하므로, 내림차순 정렬과 함께 쓰려면 09회의 내림차순 인덱스가 필요해질 수 있다.

    IN이 끼어들면 순서가 깨진다

    화면에 "품절 상품 포함" 옵션이 생겨 조건이 status IN ('ON_SALE', 'SOLD_OUT')가 되었다고 하자. 이제 status는 하나의 값으로 고정되지 않는다. idx_category_status_created에서 (7, 'ON_SALE') 구간과 (7, 'SOLD_OUT') 구간은 각각 created_at 순서로 놓여 있지만, 두 구간은 인덱스에서 앞뒤로 떨어져 있다. 두 구간을 차례로 읽으면 "판매 중 상품의 최신순, 그다음 품절 상품의 최신순"이 나올 뿐 전체 최신순이 아니다. 앞의 비유에서 본 대로 MySQL은 여러 구간을 병합해 순서를 만들지 않으므로 정렬 단계가 다시 생기고, 두 구간의 9,000행을 모두 읽어 정렬해야 한다.

    반면 idx_category_created로는 이 쿼리도 조기 종료로 처리할 수 있다. 상태를 Filter에서 확인하면 되고, 이제 10행 주기에서 9행이 통과하므로 계산하면 23개 항목을 읽어 20행을 채운다. 같은 인덱스 집합에서 조건 하나가 등치에서 IN으로 바뀌었을 뿐인데, 좋은 인덱스가 뒤바뀐다. 이 두 계획 가운데 무엇이 선택되는지는 옵티마이저의 비용 판단에 달려 있으므로 EXPLAIN으로 확인해야 한다. MySQL 8.4.13에서 두 인덱스를 모두 둔 채 실행해 보면 옵티마이저는 idx_category_created를 역순으로 읽는 계획(Extra Using where; Backward index scan)을 골랐고, EXPLAIN ANALYZE의 Index lookup은 23행을 읽었다. FORCE INDEX (idx_category_status_created)로 다른 쪽을 쓰게 하면 두 구간을 범위 스캔(Index range scan ... over (category_id = 7 AND status = 'ON_SALE') OR (category_id = 7 AND status = 'SOLD_OUT'))으로 9,000행 읽은 뒤 Sort가 붙는다. 이 선택은 통계에 따라 달라질 수 있다.

    한 인덱스가 모든 화면을 맡을 수는 없다

    관리자 화면에서는 상태와 관계없이 카테고리의 전체 상품을 최신순으로 본다고 하자. WHERE category_id = 7 ORDER BY created_at DESC LIMIT 20이다. idx_category_status_created는 이 쿼리의 정렬을 대신하지 못한다. status가 WHERE에서 고정되지 않았으므로 category_id 다음 열인 status를 건너뛸 수 없고, created_at은 status 값마다 따로 정렬되어 있을 뿐이다. 이 쿼리에는 idx_category_created가 맞다. 결국 인덱스 설계는 쿼리 하나가 아니라 서비스의 쿼리 패턴 전체를 보고 정한다. 인덱스를 하나 더 둘 때마다 INSERT, UPDATE, DELETE가 갱신해야 할 B+Tree가 하나 늘고 버퍼 풀과 디스크를 더 쓴다. 자주 실행되고 느린 쿼리에 맞는 인덱스를 두되, 왼쪽 부분이 같은 인덱스가 여럿이면 하나로 합칠 수 있는지 검토한다.

    정렬 열의 범위 조건은 괜찮다

    범위 조건이라고 모두 순서를 깨는 것은 아니다. 다음 페이지를 가져오는 쿼리를 생각해 보자. 첫 페이지의 마지막 행은 product_id 997,406이고 등록 시각은 2024-11-23 15:26:00이었다.

    SELECT product_id, name, price, created_at
FROM product
WHERE category_id = 7
  AND status = 'ON_SALE'
  AND created_at < '2024-11-23 15:26:00'
ORDER BY created_at DESC
LIMIT 20;

    범위 조건이 걸린 열이 바로 정렬 열이다. (7, 'ON_SALE') 구간 안에서 created_at이 그 값보다 작은 부분은 인덱스에서 연속된 한 구간이고, 그 구간도 created_at 순서로 놓여 있다. 매뉴얼의 ORDER BY 최적화 절도 WHERE key_part1 = constant1 AND key_part2 > constant2 ORDER BY key_part2를 인덱스로 정렬을 피할 수 있는 예로 든다. 이 쿼리는 경계 바로 앞의 항목부터 역순으로 20개를 읽고 멈춘다. 같은 두 번째 페이지를 LIMIT 20 OFFSET 20으로 가져오면 앞 페이지의 20개를 읽고 버린 뒤 20개를 더 읽어 40개를 읽고, idx_category_created로 처리하면 버리는 행까지 50개를 읽는다. 페이지가 깊어질수록 OFFSET이 버리는 양이 늘어난다. 정렬 값이 같은 행이 있을 때 이 방식을 안전하게 만드는 법과 OFFSET 페이징의 비용은 12회에서 다룬다.

    또 하나의 선택지: 정렬 기준을 기본 키로 바꾸기

    진단에서 본 "데이터로는 이미 정렬되어 있다"는 관찰로 돌아가자. 업무 규칙상 등록 순서와 product_id의 순서가 같다고 확신할 수 있다면, ORDER BY product_id DESC로 써도 같은 결과가 나온다. 이렇게 바꾸면 인덱스 확장 덕분에 처음의 idx_category만으로도 정렬이 사라진다. idx_category의 항목은 실제로 (category_id, product_id) 순서이므로 category_id가 상수인 구간은 product_id 순서로 놓여 있다. 매뉴얼은 옵티마이저가 확장된 세컨더리 인덱스를 ref·range 접근과 함께 정렬 최적화에도 쓴다고 밝힌다. 새 인덱스를 만들지 않고도 조기 종료를 얻는 셈이다. MySQL 8.4.13에서 idx_category로 이 쿼리를 실행하면 Extra가 Using where; Backward index scan이고, EXPLAIN ANALYZE의 Index lookup on product using idx_category (category_id=7) (reverse)가 26행을 읽는다.

    대가는 업무 규칙을 SQL에 새긴다는 점이다. 기본 키 순서와 등록 시각 순서는 여러 이유로 어긋날 수 있다. 데이터를 이관하면서 기본 키를 직접 넣을 수 있고, 등록 시각을 나중에 고칠 수 있고, AUTO_INCREMENT 값을 먼저 받은 트랜잭션이 더 늦게 커밋될 수도 있다. "최신순"이 화면의 약속이라면 created_at으로 정렬하는 쪽이 의미가 분명하다. 기본 키 정렬은 그 어긋남이 허용되는 화면에서 고를 수 있는 선택지로 남겨 둔다.

    정렬 순서를 하나로 정하기: 동률과 기본 키

    실습 데이터의 created_at은 모든 행이 다르다. 실제 데이터는 그렇지 않다. 상품을 일괄 등록하면 같은 초에 수십 개가 들어간다. 정렬 값이 같은 행, 곧 동률이 있으면 LIMIT의 결과가 하나로 정해지지 않는다. 매뉴얼의 LIMIT 최적화 절은 ORDER BY 열의 값이 같은 행들을 서버가 어떤 순서로 돌려줘도 되며, 그 순서는 전체 실행 계획에 따라 달라질 수 있다고 명시한다. LIMIT이 실행 계획에 영향을 주므로 LIMIT이 있을 때와 없을 때의 순서가 다를 수 있다는 예도 든다. 인덱스를 추가해 계획이 filesort에서 인덱스 순서로 바뀌는 순간, 동률인 행들의 순서가 조용히 바뀔 수 있다는 뜻이다.

    매뉴얼이 권하는 해법은 유일한 열을 ORDER BY에 덧붙여 순서를 하나로 정하는 것이다. 우리 쿼리라면 ORDER BY created_at DESC, product_id DESC다. 여기서 인덱스 확장이 다시 힘을 쓴다. idx_category_status_created의 항목은 실제로 (category_id, status, created_at, product_id)이므로, 덧붙인 product_id도 인덱스의 순서 안에 이미 들어 있다. 두 열이 모두 DESC이므로 같은 인덱스를 역순으로 읽으면 되고 정렬 단계는 생기지 않는다.

    방향을 섞으면 이야기가 달라진다. ORDER BY created_at DESC, product_id ASC는 오름차순 인덱스를 어느 방향으로 읽어도 나오지 않는다. 정방향으로 읽으면 둘 다 오름차순이고, 역방향으로 읽으면 둘 다 내림차순이다. 매뉴얼은 ORDER BY의 두 열이 같은 방향이든 반대 방향이든, 인덱스를 쓰려면 인덱스가 같은 동질성(homogeneity)을 가져야 하고 실제 방향까지 같을 필요는 없다고 설명한다. 섞인 방향을 인덱스로 처리하려면 열마다 방향을 지정한 내림차순 인덱스가 필요하고, 이것이 09회의 주제다. 동률 처리용 열은 다른 정렬 열과 같은 방향으로 붙이는 습관을 들이자.

    인덱스가 정렬을 대신하지 못하는 경우

    진단할 때 쓸 수 있도록 인덱스가 ORDER BY를 처리하지 못하는 경우를 모아 두자. 앞의 여덟 줄은 MySQL 매뉴얼의 ORDER BY 최적화 절에 실린 경우이고, 마지막 줄은 이 회차에서 인덱스의 항목 순서로 확인한 경우다. 매뉴얼은 이런 경우에도 WHERE 조건에 맞는 행을 찾는 데는 인덱스를 쓸 수 있다고 덧붙인다. 정렬만 따로 하게 될 뿐이다.

    경우예이유
    서로 다른 인덱스의 열로 정렬ORDER BY key1, key2한 인덱스의 순서로는 두 열의 조합 순서가 나오지 않는다
    인덱스의 연속되지 않은 부분으로 정렬ORDER BY key1_part1, key1_part3건너뛴 part2가 상수가 아니면 part3은 part2 값마다 따로 정렬되어 있다
    행을 찾는 인덱스와 정렬 열의 인덱스가 다름WHERE key2 = c ORDER BY key1key2로 찾은 행은 key1 순서로 나오지 않는다
    열이 아닌 식으로 정렬ORDER BY ABS(key), ORDER BY -key인덱스는 열 값의 순서를 담을 뿐 식의 순서는 담지 않는다
    조인에서 첫 번째 비상수 테이블이 아닌 테이블의 열로 정렬드라이빙 테이블이 아닌 쪽의 열로 ORDER BY결과 행의 순서는 바깥 테이블을 읽는 순서를 따른다(11회)
    ORDER BY와 GROUP BY의 식이 다름GROUP BY a ORDER BY b그룹을 만드는 순서와 출력 순서가 다르다(12회)
    정렬 열에 접두사 인덱스만 있음CHAR(20) 열의 앞 10바이트만 인덱스인덱스가 10바이트 이후를 구별하지 못한다
    행을 순서대로 저장하지 않는 인덱스MEMORY 테이블의 HASH 인덱스해시는 순서를 보존하지 않는다
    정렬 열 앞의 열이 IN이나 범위 조건(a, b) 인덱스에 WHERE a IN (1, 2) ORDER BY ba 값마다 따로 정렬된 구간 여러 개를 읽게 되고, MySQL은 이를 병합해 순서를 만들지 않는다

    목록의 네 번째 줄은 실무에서 자주 걸린다. 날짜별로 묶어 보여 주려고 ORDER BY DATE(created_at) DESC라고 쓰면 created_at 인덱스가 있어도 정렬이 생긴다. 매뉴얼은 SELECT 목록의 별칭에도 같은 원리가 적용된다고 예를 든다. SELECT ABS(a) AS a FROM t1 ORDER BY a에서 ORDER BY의 a는 별칭, 곧 ABS(a)를 가리키므로 t1.a의 인덱스를 쓸 수 없다. 반대로 SELECT ABS(a) AS b FROM t1 ORDER BY a에서 a는 t1의 열을 가리키므로 인덱스를 쓸 수 있다. 정렬 결과는 당연히 ABS(a)의 순서와 다르다.

    흔한 오해와 함정

    "Using filesort가 보이면 디스크에서 정렬한다." 매뉴얼은 결과가 메모리에 들어가지 않을 때만 임시 디스크 파일을 쓴다고 설명하고, EXPLAIN은 메모리 정렬인지 디스크 정렬인지 구별하지 않는다. 디스크를 썼는지는 옵티마이저 트레이스의 청크 수나 Sort_merge_passes 상태 변수로 확인한다. 이 회차의 쿼리가 느린 원인도 정렬의 장소가 아니라 정렬 전에 읽어야 하는 입력의 양이었다.

    "Using filesort는 무조건 없애야 한다." 정렬할 입력이 수십 행이라면 filesort는 아무 문제가 아니다. 상품이 30개인 카테고리를 카테고리 인덱스로 읽고 정렬하는 쪽이, 정렬 열 하나짜리 인덱스로 테이블 전체를 거꾸로 훑는 쪽보다 훨씬 싸다. 판단 기준은 Extra의 단어가 아니라 Sort 아래 노드가 읽은 행 수와 LIMIT의 비율이다. 인덱스를 늘리면 쓰기 비용도 늘어난다.

    "LIMIT 20이 있으니 20행 근처만 읽는다." LIMIT이 읽기를 줄이려면 두 조건이 필요하다. 정렬 단계처럼 입력을 다 소비해야 하는 연산자가 Limit과 읽기 사이에 없어야 하고, 읽는 순서에서 조건에 맞는 행이 앞쪽에 충분히 있어야 한다. 앞의 조건이 깨지면 filesort 계획이 되고, 뒤의 조건이 깨지면 이름 조건 '상품1%'처럼 조기 종료가 늦게 일어나거나 일어나지 않는다.

    "정렬 열에 인덱스를 만들면 정렬 문제가 해결된다." created_at 하나짜리 인덱스는 테이블 전체의 최신순을 줄 뿐, 카테고리별 최신순은 주지 않는다. 그 인덱스를 쓰면 카테고리 조건은 읽은 뒤에 거르는 필터가 되고, 읽기 양은 카테고리의 비율과 위치에 달린다. 등치 조건 열을 정렬 열 앞에 둔 복합 인덱스여야 구간이 카테고리 안으로 좁혀진다.

    "Backward index scan은 피해야 할 경고다." 역방향 읽기는 정방향보다 항목당 일이 조금 많을 뿐, 조기 종료의 이득은 그대로다. 10,000행을 읽어 정렬하던 쿼리가 26행을 거꾸로 읽게 되었다면 개선이다. 내림차순이 핵심인 쿼리를 정방향으로 읽게 만드는 방법은 09회에서 본다.

    "목록 쿼리를 고쳤으니 페이지 수 계산도 빨라졌다." 화면에 "전체 8,000개"를 표시하려고 COUNT(*)를 따로 실행한다면, 그 쿼리에는 조기 종료가 없다. 조건에 맞는 항목을 모두 세어야 하기 때문이다. idx_category_status_created가 있으면 (7, 'ON_SALE') 구간의 항목 8,000개를 세는 것으로 끝나 행을 가져올 필요는 없지만, 읽는 양은 여전히 카테고리 크기에 비례한다. 인덱스만으로 답하는 이 방식은 08회의 커버링 인덱스에서, 개수를 미리 모아 두는 방법은 12회의 사전 집계에서 다룬다.

    정리: 진단에서 해결까지

    이 회차에서 따라간 과정을 순서로 정리한다. 같은 순서를 다른 쿼리에도 그대로 쓸 수 있다.

    이 장의 핵심

    정렬은 입력을 모두 받아야 첫 행을 내놓는 연산이라서, 정렬 단계가 있는 한 LIMIT은 읽는 양을 줄이지 못한다. 인덱스는 이미 정렬된 목록이므로, 등치 조건으로 고정한 열 바로 뒤에 ORDER BY 열이 이어지는 복합 인덱스를 두면 정렬 단계가 사라지고 Limit이 아래쪽 읽기를 직접 멈춘다. 그렇게 얻은 조기 종료의 비용은 남은 필터를 통과하는 행이 읽는 순서의 어디에 있는가로 정해지며, 옵티마이저는 그 위치를 균등 분포로 가정해 추정한다.
    Using filesort
    인덱스로 정렬 순서를 얻지 못해 별도의 정렬 단계를 둔다는 표시다. 메모리 안에서 끝날 수도 있고, EXPLAIN은 디스크를 썼는지 구별하지 않는다.
    정렬과 파이프라인
    filesort는 자식이 행을 다 줄 때까지 읽은 뒤에야 첫 행을 내놓는다. 그래서 LIMIT은 정렬하는 양과 메모리를 줄일 수 있어도 읽는 양은 줄이지 못한다.
    정렬 버퍼의 튜플
    정렬 키와 함께 쿼리가 쓰는 열 값을 담거나(additional fields) 행 위치만 담는다(row ID). 8.4 소스는 70,000바이트를 넘는 BLOB 계열 열을 읽는 쿼리에서 행 위치 정렬을 쓴다.
    복합 인덱스의 순서
    항목은 열 순서대로 사전식으로 정렬되고 InnoDB 세컨더리 인덱스는 끝에 기본 키가 붙는다. 앞쪽 열이 등치 조건으로 고정되면 그다음 열의 순서가 곧 읽는 순서다.
    조기 종료
    정렬 단계가 없으면 Limit이 한도에 도달한 뒤 아래 이터레이터를 더 부르지 않아 읽기가 멈춘다. 역순 정렬은 Backward index scan과 (reverse)로 표시된다.
    일치 행의 밀도와 위치
    조기 종료가 읽는 양은 필터를 통과하는 행이 읽는 순서에서 얼마나 앞에 있는가로 정해진다. 개수가 같아도 위치에 따라 수백 배 달라질 수 있다.
    prefer_ordering_index
    ORDER BY나 GROUP BY에 LIMIT이 있을 때 순서를 주는 인덱스를 선호하게 하는 옵티마이저 플래그로 기본값은 on이다. 균등 분포 가정에 의존하므로 빗나갈 수 있고, 8.0.21부터 끌 수 있다.
    등치, 정렬, 그다음
    등치 조건 열을 앞에, ORDER BY 열을 그 뒤에 두고, 범위나 기타 조건 열은 필요하면 마지막에 둔다. 정렬 열 앞의 열에 IN이나 범위 조건이 걸리면 정렬 단계가 다시 생긴다.

    목록 화면이 "데이터가 늘수록 느려진다"는 보고를 받으면 먼저 화면에 나가는 행 수와 쿼리가 읽는 행 수가 함께 늘어나는지를 본다. 돌려주는 행은 그대로인데 읽는 행이 데이터 크기를 따라 늘어난다면, 정렬 단계가 LIMIT을 무력하게 만들고 있을 가능성이 크다. 이때 정렬 버퍼를 키우거나 서버 사양을 올리는 것은 비용의 기울기를 바꾸지 못한다. 인덱스가 순서를 주게 해서 읽기 양을 데이터 크기와 떼어 놓아야 기울기가 사라진다.

    조기 종료 계획을 도입한 뒤에는 평균이 아니라 최악의 입력으로 다시 확인해야 한다. 인기 카테고리와 기본 상태처럼 일치 행이 많은 조건에서는 놀랄 만큼 빠르지만, 거의 쓰이지 않는 가격대나 검색어, 오래전에만 등록되던 종류의 상품처럼 일치 행이 드물거나 먼 쪽에 몰린 조건에서는 구간 전체를 읽는다. 특히 순서를 주는 인덱스가 카테고리 같은 등치 조건으로 좁혀지지 않은 단일 열 인덱스라면 그 최악은 테이블 전체다. 이런 쿼리는 평소에는 잘 돌다가 특정 사용자의 특정 조건에서만 느려지므로, 슬로 쿼리 로그에 같은 쿼리가 드문드문 나타나는 모양으로 드러나는 경우가 많다.

    인덱스를 설계할 때의 판단은 화면마다 달라진다. 조건이 등치로만 이루어진 사용자 화면에는 등치 열과 정렬 열을 담은 인덱스가 가장 좋다. 상태 필터가 옵션으로 여러 값을 받거나 관리자 화면처럼 상태를 고정하지 않는 쿼리에는 상태를 뺀 인덱스가 조기 종료를 지켜 준다. 두 인덱스를 다 둘지는 쓰기 빈도와 저장 공간을 보고 정한다. 정렬 기준을 기본 키로 바꿔 인덱스를 아끼는 방법은 등록 순서와 기본 키 순서가 어긋나도 되는 화면에서만 고른다.
  • idx_category_created만 있는 상태에서 WHERE category_id = 7 AND status = 'SOLD_OUT' ORDER BY created_at DESC LIMIT 20을 실행한다. EXPLAIN ANALYZE의 Index lookup 줄과 Filter 줄에 찍힐 actual rows를 계산하고, 마지막으로 읽은 항목의 product_id를 구하라.
  • 인덱스 (category_id, status, created_at)가 있을 때 다음 네 쿼리가 정렬 단계 없이 처리될 수 있는지 판정하고 이유를 적어라. (가) WHERE category_id = 7 AND status = 'ON_SALE' ORDER BY created_at (나) WHERE category_id = 7 ORDER BY status, created_at DESC (다) WHERE category_id = 7 AND status = 'ON_SALE' ORDER BY created_at DESC, product_id DESC (라) WHERE category_id IN (3, 7) AND status = 'ON_SALE' ORDER BY created_at DESC
  • idx_category_created만 있는 상태에서 판매 중 상품의 두 번째 페이지를 LIMIT 20 OFFSET 20으로 가져올 때 EXPLAIN ANALYZE의 맨 아래 노드가 읽는 항목 수를 계산하라. 같은 페이지를 idx_category_status_created로 가져오면 몇 개를 읽는가?
  • 동료가 "운영 서버의 sys.statements_with_sorting에서 상품 목록 쿼리의 avg_rows_sorted가 20이라 정렬은 문제가 아니다"라고 말한다. 이 판단의 오류를 8.4 소스의 동작으로 설명하고, 정렬 입력의 실제 크기를 확인하는 방법을 제시하라.
  • 카테고리 7의 상품 가운데 '여름 특가' 태그가 붙은 상품만 보여 주는 화면을 만든다. 태그가 붙은 상품은 카테고리 7에 200개이고 모두 2023년에 등록되었다. idx_category_created를 역순으로 읽는 계획과, 태그 조건을 먼저 좁히는 인덱스로 읽고 정렬하는 계획 가운데 무엇이 나은지 이 회차의 원리로 판단하라.

    1번. 카테고리 7에서 SOLD_OUT은 k mod 10 = 8인 행이다. 역순으로 읽으면 k = 9998이 첫 번째, 9988이 두 번째, …, 9998 − 10 × 19 = 9808이 스무 번째다. 읽기는 k = 9999에서 시작하므로 9999부터 9808까지 192개 항목을 읽는다. Index lookup의 actual rows는 192, Filter는 20, Limit도 20이다. 마지막으로 읽은 항목은 n = 100 × 9808 + 6 = 980,806이다. 일치 비율이 10%라 균등 가정 예상은 200인데, 일치 행이 10행마다 규칙적으로 있고 첫 일치 행이 두 번째 항목이라 실제는 그보다 조금 적다.

    2번. (가)는 된다. 앞의 두 열이 등치 조건으로 고정되어 created_at 순서가 읽는 순서이고, 오름차순이므로 정방향으로 읽는다. (나)는 안 된다. category_id가 고정된 구간은 (status, created_at) 순서로 놓여 있으므로 열의 구성만 보면 ORDER BY의 두 열이 인덱스의 다음 두 열과 일치한다. 하지만 방향이 status는 ASC, created_at은 DESC로 섞여 있고, 모두 오름차순인 이 인덱스는 정방향으로 읽으면 둘 다 오름차순, 역방향으로 읽으면 둘 다 내림차순이 나올 뿐이다. 동질성 조건을 만족하지 못하므로 정렬 단계가 생긴다. 방향을 ORDER BY status DESC, created_at DESC나 둘 다 ASC로 맞추면 인덱스로 처리된다. (다)는 된다. 인덱스 확장으로 항목 끝에 product_id가 있고 두 열 모두 DESC라 역순으로 읽으면 된다. (라)는 안 된다. category_id가 두 값이라 (3, 'ON_SALE')과 (7, 'ON_SALE') 두 구간을 읽게 되고, 각 구간 안에서만 created_at 순서이므로 정렬 단계가 필요하다.

    3번. OFFSET 20이면 Limit/Offset이 처음 20행을 버리고 다음 20행을 돌려주므로 Filter를 통과해야 하는 행은 40개다. ON_SALE은 10행 주기에서 앞의 2행(HIDDEN, SOLD_OUT) 다음 8행이므로, 40개를 채우려면 다섯 주기, 곧 k = 9999부터 9950까지 50개 항목을 읽는다. idx_category_status_created라면 (7, 'ON_SALE') 구간에서 40개 항목을 읽는다. 어느 쪽이든 페이지 번호에 비례해 읽는 양이 늘어난다는 점은 같다.

    4번. 8.4 소스의 filesort는 LIMIT이 있을 때 정렬한 행 수를 상태 변수와 성능 스키마에 더하기 직전에 LIMIT 값으로 잘라 낸다. 그래서 8,000행을 정렬에 넣고 20행을 남긴 쿼리도 정렬 행 수는 20으로 기록되고, sys.statements_with_sorting의 rows_sorted와 avg_rows_sorted도 그 값을 모은 것이다. 실제 입력 크기는 EXPLAIN ANALYZE에서 Sort 바로 아래 노드의 actual rows로 보거나, 옵티마이저 트레이스의 filesort_summary에 있는 num_rows_found로 본다. 총 지연 시간이 큰데 정렬 행 수가 작다면 오히려 Top-N 정렬로 큰 입력을 처리하고 있다는 신호로 읽어야 한다.

    5번. 역순 읽기는 최신 상품부터 출발하는데 태그 상품은 모두 2023년, 곧 오래된 쪽에 몰려 있다. 2024년에 등록된 카테고리 7의 상품을 모두 지나야 첫 일치 행을 만나므로, 일치 행이 200개로 20개보다 충분히 많아도 조기 종료는 늦게 일어난다. 균등 가정으로는 20 ÷ (200 / 10,000) = 1,000개쯤 읽으면 된다고 계산되지만 실제는 그보다 훨씬 많다. 실습 데이터의 등록 시각 규칙이라면 2024년에 등록된 카테고리 7의 상품(n ≥ 525,600, 곧 k = 5256~9999)만 4,744개이므로 첫 일치 행을 만나기 전에 최소 4,744개를 읽는다. 태그 조건으로 먼저 200행으로 좁힌 뒤 정렬하면 읽기 200행과 Top-N 정렬로 끝나고, 이 양은 태그 상품의 등록 시기와 무관하다. 이 경우는 filesort가 있는 계획이 낫다. 옵티마이저가 순서를 주는 인덱스를 고른다면 EXPLAIN ANALYZE로 확인한 뒤 힌트나 prefer_ordering_index로 바로잡는다.

     WHERE category_id = 7 AND status = 'ON_SALE' ORDER BY created_at DESC LIMIT 20의 실행 계획에 Using filesort가 있고, EXPLAIN ANALYZE의 맨 아래 인덱스 조회가 10,000행을 읽었다. LIMIT 20이 읽는 양을 줄이지 못한 이유로 가장 정확한 것은? sort_buffer_size가 작아 정렬이 디스크로 넘쳤기 때문에 정렬 결과의 첫 행은 입력의 어느 행이든 될 수 있어서, 정렬 단계는 입력을 모두 받은 뒤에야 첫 행을 내놓기 때문에 MySQL은 LIMIT을 정렬 단계에 전달하지 않기 때문에 Using where가 함께 있어서 조건 평가가 정렬보다 나중에 일어나기 때문에 정렬은 파이프라인을 끊는 연산이다. 어느 행이 1등인지는 마지막 입력을 보기 전까지 확정되지 않으므로 filesort는 자식을 끝까지 읽는다. 버퍼 크기는 메모리 안에서 끝나는지를 바꿀 뿐 읽는 양은 바꾸지 못한다. LIMIT은 "limit input to 20 row(s) per chunk"처럼 정렬에 전달되지만 정렬하는 양을 줄일 뿐이다. 조건 평가는 Filter 노드에서 정렬 전에 일어난다. 인덱스 (category_id, status, created_at)만 있는 InnoDB 테이블에서 정렬 단계 없이 처리될 수 있는 쿼리는? WHERE category_id = 7 ORDER BY created_at DESC LIMIT 20 WHERE category_id = 7 AND status IN ('ON_SALE', 'SOLD_OUT') ORDER BY created_at DESC LIMIT 20 WHERE category_id = 7 AND status = 'ON_SALE' ORDER BY created_at DESC, product_id ASC LIMIT 20 WHERE category_id = 7 AND status = 'ON_SALE' AND created_at < '2024-06-01' ORDER BY created_at DESC LIMIT 20 네 번째는 앞의 두 열이 등치로 고정되고 범위 조건이 정렬 열 자체에 걸려 있어 한 구간이 created_at 순서로 읽힌다. 첫 번째는 status가 고정되지 않아 created_at이 status 값마다 따로 정렬되어 있다. 두 번째는 IN 때문에 두 구간을 읽어야 하고 MySQL은 이를 병합해 순서를 만들지 않는다. 세 번째는 인덱스 확장으로 product_id가 들어 있지만 DESC와 ASC가 섞여 오름차순 인덱스의 어느 방향으로도 그 순서가 나오지 않는다. (category_id, created_at) 인덱스를 역순으로 읽고 조건 하나를 Filter로 거르는 같은 계획에서, 조건 A와 조건 B는 카테고리 안에서 일치하는 행의 수가 똑같다. 그런데 LIMIT 20을 채우기까지 읽은 항목 수는 A가 26, B가 8,026이었다. 이 차이를 가장 잘 설명하는 것은? B의 조건식이 더 복잡해서 평가에 시간이 걸렸다. B의 조건은 인덱스 통계가 없어 옵티마이저가 다른 인덱스를 골랐다. B를 만족하는 행이 created_at 순서의 오래된 쪽에 몰려 있어, 최신 쪽부터 읽는 스캔이 그보다 새로운 항목을 모두 지나야 했다. B를 만족하는 행은 클러스터형 인덱스에서 다른 페이지에 있다. 두 조건은 같은 계획이므로 옵티마이저의 선택은 관계가 없고, 조건식의 복잡도는 읽은 항목 수를 바꾸지 않는다. 조기 종료는 읽는 순서에서 일치하는 행 20개를 만날 때 멈추므로, 일치 행의 개수가 같아도 그 행들이 순서의 어디에 있느냐에 따라 읽는 양이 정해진다. 정렬 열과 조건 열에 상관관계가 있으면 균등 분포를 가정한 예상이 크게 빗나간다. MySQL 매뉴얼이 prefer_ordering_index 최적화가 바람직하지 않을 수 있다고 밝힌 이유는? 순서를 주는 인덱스를 고르는 판단이 데이터 분포가 대체로 균일하다는 가정에 기대기 때문에 역방향 인덱스 스캔이 결과를 틀리게 만들 수 있기 때문에 순서를 주는 인덱스를 쓰면 정렬 버퍼를 더 많이 쓰기 때문에 이 최적화가 켜져 있으면 LIMIT이 무시되기 때문에 매뉴얼은 이 판단을 내리는 알고리즘이 데이터 분포가 늘 대체로 균일하다고 가정하는 탓에 모든 경우를 다룰 수 없다고 설명한다. 8.4 소스의 주석도 조건 인덱스와 순서 인덱스 사이에 상관관계가 없다고 가정하고 N ÷ 선택도만큼 읽는다고 계산한다. 역방향 스캔은 느릴 수 있어도 결과는 정확하고, 순서를 주는 인덱스를 쓰면 정렬 버퍼를 쓰지 않으며, LIMIT은 오히려 이 최적화의 전제다.
    filesort
    인덱스로 순서를 얻지 못할 때 MySQL이 수행하는 정렬 단계다. 정렬 버퍼에서 정렬하고, 넘치면 정렬된 덩어리를 임시 파일에 써서 병합한다.
    조기 종료(early termination)
    LIMIT이 있는 쿼리에서 필요한 행을 다 얻은 즉시 아래쪽 읽기를 멈추는 것이다. 읽기와 LIMIT 사이에 입력을 모두 소비하는 연산자가 없어야 일어난다.
    역방향 인덱스 스캔(backward index scan)
    인덱스를 키의 내림차순으로 거꾸로 읽는 접근이다. EXPLAIN의 Extra에 Backward index scan으로, 트리 형식에서는 인덱스 이름 뒤의 (reverse)로 표시된다.
    인덱스 확장(index extension)
    InnoDB가 세컨더리 인덱스 끝에 기본 키 열을 덧붙이고, 옵티마이저가 그 열을 접근과 정렬 최적화에 함께 고려하는 것이다.
    사전식 순서(lexicographic order)
    첫 열로 정렬하고, 첫 열이 같으면 둘째 열로, 그것도 같으면 셋째 열로 정렬하는 순서다. 복합 인덱스의 항목이 이 순서로 놓인다.
    정렬 버퍼(sort buffer)
    filesort가 정렬 키와 열 값 또는 행 위치를 담는 메모리 영역이다. sort_buffer_size까지 필요한 만큼 늘려 가며 할당된다.
    동질성(homogeneity)
    ORDER BY의 열들이 모두 같은 방향인지, 섞인 방향인지의 성질이다. 인덱스로 정렬하려면 인덱스 열의 방향 조합이 이 성질과 맞아야 한다.
    prefer_ordering_index
    ORDER BY나 GROUP BY에 LIMIT이 있을 때 순서를 주는 인덱스를 선호하게 하는 optimizer_switch 플래그다.
