    실행 계획이 필요한 이유: SQL은 "무엇"만 말한다

    SQL은 선언형 언어다. SELECT * FROM orders WHERE member_id = 42 ORDER BY ordered_at라는 문장은 "42번 회원의 주문을 주문 시각 순서로 달라"는 결과의 모양만 말한다. 어느 인덱스를 탈지, 테이블 전체를 훑을지, 정렬을 메모리에서 할지 인덱스 순서를 빌릴지는 한 글자도 적혀 있지 않다. 같은 결과를 만드는 방법은 여러 가지이고, 그중 하나를 고르는 일은 데이터베이스의 몫이다. MySQL에서 그 일을 하는 부품이 옵티마이저(optimizer)이고, 옵티마이저가 고른 방법을 단계별로 적어 놓은 것이 실행 계획(query execution plan)이다.

    01회에서 본 MySQL의 구조를 한 번만 떠올려 보자. MySQL 서버는 SQL을 해석하고 계획을 세우는 서버 계층과, 실제로 데이터를 페이지 단위로 저장하고 읽는 스토리지 엔진(InnoDB)으로 나뉜다. 문장 하나는 파서가 문법 트리로 바꾸고, 이름과 권한을 확인한 뒤, 옵티마이저가 접근 방법과 조인 순서를 정하고, 실행기가 그 계획대로 스토리지 엔진에 "다음 행을 달라"는 요청을 반복해 결과를 만든다. 서버 계층과 엔진 사이에는 핸들러(handler) API라는 경계가 있어서, 서버는 "이 인덱스로 이 키 값의 첫 행을 찾아라", "다음 행을 달라" 같은 요청만 보내고 페이지를 어떻게 읽는지는 엔진에 맡긴다. EXPLAIN은 이 흐름에서 옵티마이저가 계획을 다 세운 시점에 멈추고, 그 계획을 사람이 읽을 수 있는 표로 꺼내 보여 주는 명령이다.

 └──────────┘   └──────────────┘   └──────┬───────┘   └──────┬───────┘

    SQL이 파서, 해석, 옵티마이저, 실행기를 거쳐 InnoDB에 도달하는 경로에서, EXPLAIN은 옵티마이저 출력에서 갈라져 계획 표를 내보내고 실행기로는 가지 않는다는 점을 보여 준다. 왼쪽에서 오른쪽으로 이어지는 가로 흐름도. 둥근 사각형 네 개가 화살표로 연결되어 있다: "파서", "이름·권한 해석", "옵티마이저", "실행기". 실행기 아래로 굵은 화살표가 내려가 원통 모양의 "InnoDB" 상자에 닿고, 그 화살표 옆에 "핸들러 API" 라벨이 붙어 있다. InnoDB 원통 안에는 작은 격자 사각형 여러 개가 "페이지"라는 라벨과 함께 그려져 있다. 옵티마이저 상자 아래로 주황색 점선 화살표가 갈라져 나가 종이 문서 아이콘에 닿고, 문서에 "실행 계획 표" 라벨과 "EXPLAIN" 꼬리표가 붙어 있다. 맨 왼쪽 시작점에 "SQL 문자열" 라벨이 있다. 흰 배경, 파란 계열 상자, 주황색 강조 하나. EXPLAIN은 옵티마이저가 세운 계획을 꺼내 보여 줄 뿐, 실행기가 그 계획대로 행을 읽어 결과를 만드는 단계로는 넘어가지 않는다.

    왜 계획 하나가 그렇게 중요한가. 데이터는 InnoDB 안에서 기본값 16KB짜리 페이지에 담겨 있고, 페이지가 버퍼 풀에 없으면 디스크에서 읽어 와야 한다. 쿼리의 비용은 결국 "몇 개의 페이지를, 어떤 순서로 만지는가"로 정해진다. 숫자로 감을 잡아 보자. 아래는 계산을 위해 정한 가정일 뿐 실제 측정값이 아니다. orders 테이블에 100만 행이 있고 한 페이지에 평균 100행이 들어간다면, 테이블 전체는 대략 1만 개의 리프 페이지다.

    • 전체를 훑는 경우: 1만 개 페이지를 키 순서대로 이어서 읽는다. 페이지마다 100행을 한꺼번에 얻으므로 페이지 하나의 비용이 100행에 나뉜다.
    • 세컨더리 인덱스로 30만 행(30%)을 찾는 경우: 인덱스 리프는 순서대로 읽지만, 인덱스 항목 하나마다 기본 키로 클러스터형 인덱스를 다시 찾아 들어가 행 전체를 가져와야 한다(06회에서 자세히 다룬다). 최악이면 30만 번의 페이지 접근이 흩어진 위치에서 일어난다. 같은 페이지를 다시 만나면 버퍼 풀이 흡수해 주지만, 접근 횟수 자체가 풀 스캔의 페이지 수 1만을 훌쩍 넘을 수 있다.
    • 42번 회원의 주문 20건을 찾는 경우: 인덱스에서 루트부터 리프까지 몇 페이지를 내려가고, 20건에 대해 많아야 20번 클러스터형 인덱스를 찾아 들어간다. 풀 스캔의 1만 페이지와 비교하면 차이가 수백 배다.

    같은 "인덱스를 탄다"는 말이 어떤 조건에서는 압도적으로 빠르고, 어떤 조건에서는 풀 스캔보다 느리다. 어느 쪽인지는 SQL 문장에 있지 않고 데이터의 분포에 있다. 그래서 옵티마이저는 통계를 보고 각 방법의 비용을 추정해 가장 싸 보이는 것을 고른다. 이것을 비용 기반 최적화(cost-based optimization)라고 한다. 결과적으로 같은 SQL이라도 데이터가 바뀌거나 통계가 갱신되면 계획이 바뀔 수 있다. 개발자가 SQL만 보고 "이건 인덱스를 타겠지"라고 짐작하는 것은 위험하고, 실제로 옵티마이저가 무엇을 골랐는지 확인해야 한다. 그 확인 수단이 EXPLAIN이다.

    일상에서 가져온 비유도서관의 색인 카드와 서가 훑기

    책 한 권을 찾을 때는 색인 카드에서 청구기호를 확인하고 그 서가로 걸어가는 편이 빠르다. 하지만 "2000년 이후에 나온 모든 소설"처럼 장서의 절반을 모아야 한다면, 카드를 한 장씩 넘기며 책마다 서가 사이를 오가는 것보다 소설 코너의 서가를 처음부터 끝까지 훑는 편이 낫다. 옵티마이저는 이 판단을 수치로 하는 사서다. 비유가 깨지는 지점도 있다. 도서관은 걷는 거리가 비용이지만, 데이터베이스는 이미 버퍼 풀에 올라온 페이지라면 "멀리 있는" 페이지도 거의 공짜로 읽는다. 그래서 실제 비용은 접근 횟수뿐 아니라 그 페이지가 메모리에 있느냐에도 좌우된다.

    실행 계획에서 읽어 낼 수 있는 것은 크게 네 가지다. 첫째, 테이블마다 어떤 방식으로 접근하는가(인덱스를 쓰는가, 어느 인덱스를 어디까지 쓰는가). 둘째, 각 단계에서 몇 행을 읽으리라 예상하는가. 셋째, 정렬이나 임시 테이블 같은 추가 작업이 있는가. 넷째, 여러 테이블을 어떤 순서로 조인하는가. 반대로 EXPLAIN이 알려 주지 않는 것도 분명히 해 두자. 실제로 걸린 시간과 실제로 읽은 행 수는 EXPLAIN에 없다. EXPLAIN의 숫자는 모두 옵티마이저의 예상이다. 예상과 실제를 나란히 보는 EXPLAIN ANALYZE는 03회의 주제다.

    EXPLAIN 기본 사용법

    사용법 자체는 간단하다. 확인하고 싶은 문장 앞에 EXPLAIN을 붙인다. MySQL 8.0에서 EXPLAIN은 SELECT, DELETE, INSERT, REPLACE, UPDATE에 쓸 수 있고, 8.0.19부터는 TABLE 문에도 쓸 수 있다. DESCRIBE와 DESC는 EXPLAIN과 완전히 같은 명령이다. 관례상 DESC 테이블명은 테이블 구조를 볼 때, EXPLAIN 쿼리는 계획을 볼 때 쓰지만 파서에게는 차이가 없다.

    -- 기본(표 형식)
EXPLAIN SELECT * FROM orders WHERE member_id = 42;

-- mysql 클라이언트에서 \G로 끝내면 열을 세로로 늘어놓아 읽기 쉽다
EXPLAIN SELECT * FROM orders WHERE member_id = 42\G

-- 출력 형식 지정
EXPLAIN FORMAT=TRADITIONAL SELECT ...;   -- 표 형식, 기본값
EXPLAIN FORMAT=JSON        SELECT ...;   -- 비용 정보까지 담은 JSON
EXPLAIN FORMAT=TREE        SELECT ...;   -- 8.0.16부터, 실행기 구조를 트리로

-- 옵티마이저가 다시 쓴 쿼리 보기
EXPLAIN SELECT ...;
SHOW WARNINGS;

-- 다른 연결에서 지금 실행 중인 문장의 계획 보기
EXPLAIN FOR CONNECTION 1234;

    세 가지 형식은 같은 계획을 다른 각도에서 보여 준다. TRADITIONAL은 테이블 하나를 한 행으로 늘어놓은 표다. 가장 오래되었고 자료와 도구가 가장 많아서, 이 회차의 대부분은 이 형식의 열을 읽는 법에 쓴다. JSON은 표에 없는 정보를 더 담는다. cost_info 안에 read_cost, eval_cost, prefix_cost 같은 비용 추정치가 있고, 쿼리 전체의 query_cost가 있으며, 복합 인덱스에서 실제로 쓴 열 이름을 used_key_parts로 직접 보여 준다. 조건이 어디에 붙었는지는 attached_condition에 식 그대로 나온다. TREE는 8.0.16에 추가된 형식으로, 실행기가 실제로 조립하는 반복자(iterator)의 트리를 들여쓰기로 보여 준다. "어떤 연산이 어떤 연산의 입력이 되는가"가 가장 잘 드러나는 형식이고, EXPLAIN ANALYZE는 항상 이 형식으로 출력된다. 8.0.32부터는 explain_format 시스템 변수로 FORMAT을 생략했을 때의 기본 형식을 바꿀 수 있고, 변수의 기본값은 TRADITIONAL이다.

    SHOW WARNINGS는 EXPLAIN 직후에 실행하면 확장 정보를 보여 준다. 코드 1003의 Note 메시지에 옵티마이저가 이름을 어떻게 한정했고 문장을 어떻게 다시 썼는지가 담긴다. 서브쿼리가 세미조인으로 바뀌었는지, 상수 전파로 조건이 어떻게 단순해졌는지, ref 열에 func가 나왔을 때 그 함수가 무엇인지를 여기서 확인한다. 다만 이 텍스트에는 , , 같은 내부 표식이 섞여 있어서 그대로 실행할 수 있는 SQL이 아니다. 매뉴얼은 8.0.12부터 확장 정보가 DELETE, INSERT, REPLACE, UPDATE에도 제공된다고 적으면서, 같은 절에서 SHOW WARNINGS로 볼 수 있는 확장 정보는 SELECT에 대해서만 만들어지고 나머지 문장에서는 빈 결과가 나온다고도 적는다. 실제로 MySQL 8.0.46과 8.4.13에서 EXPLAIN UPDATE orders SET amount = amount WHERE member_id = 42 뒤에 SHOW WARNINGS를 실행하면 빈 결과가 아니라 코드 1003의 Note에 update `m_db_perf_02`.`orders` set `m_db_perf_02`.`orders`.`amount` = `m_db_perf_02`.`orders`.`amount` where (`m_db_perf_02`.`orders`.`member_id` = 42)처럼 이름을 한정한 문장이 나온다. EXPLAIN DELETE와 EXPLAIN INSERT도 마찬가지였다. 매뉴얼의 뒤쪽 문장은 이 버전들의 동작과 맞지 않으므로, 앞쪽 문장대로 SELECT가 아닌 문장에도 확장 정보가 나온다고 알아 두면 된다.

    EXPLAIN FOR CONNECTION은 다른 연결에서 지금 실행 중인 문장의 계획을 보여 준다. 운영 중에 SHOW PROCESSLIST로 오래 도는 쿼리를 찾았을 때, 같은 SQL을 다시 EXPLAIN 하는 대신 그 연결이 실제로 쓰고 있는 계획을 들여다볼 수 있다. 다른 사용자의 연결을 보려면 PROCESS 권한이 필요하다. EXPLAIN 자체에 필요한 권한은 설명하려는 문장을 실행하는 데 필요한 권한과 같고, 뷰가 들어 있으면 그 뷰에 대한 SHOW VIEW 권한이 더 필요하다.

    EXPLAIN은 무엇을 실행하고 무엇을 실행하지 않는가

    EXPLAIN은 매뉴얼의 표현대로 MySQL이 문장을 "어떻게 처리할 것인지"를 설명한다. 실행기를 돌려 결과 행을 만들지 않으므로, EXPLAIN UPDATE나 EXPLAIN DELETE도 데이터를 바꾸지 않는다. 그렇다고 아무 데이터도 읽지 않는 것은 아니다. 옵티마이저는 계획을 세우는 도중에 const 테이블(기본 키나 유니크 인덱스의 상수 비교로 많아야 한 행만 나오는 테이블)을 미리 읽어 그 값을 상수처럼 쓴다. MySQL 8.0 소스(sql/sql_optimizer.cc)의 주석도 이렇게 뽑아낸 테이블은 실제 실행이 시작되기 전에 행을 읽는다고 적고 있다. 그래서 존재하지 않는 기본 키로 EXPLAIN을 하면 Extra에 no matching row in const table이 나온다. 행을 실제로 찾아봤기 때문에 알 수 있는 사실이다. 이 덕분에 EXPLAIN은 대부분 아주 싸지만, "EXPLAIN은 디스크를 전혀 건드리지 않는다"고 단정하면 틀린다.

    출력의 한 행은 "테이블 하나에 대한 접근 하나"다. 그리고 행의 순서에는 뜻이 있다. 매뉴얼은 EXPLAIN이 테이블을 MySQL이 문장을 처리하면서 읽을 순서대로 나열한다고 설명한다. 첫 번째 테이블에서 한 행을 읽고, 두 번째 테이블에서 그에 맞는 행을 찾고, 다시 세 번째 테이블로 내려가는 식이다. 마지막 테이블까지 맞는 행을 찾으면 결과를 내보내고, 되돌아와 다음 후보를 이어서 찾는다. 이것이 중첩 루프 조인(nested-loop join)의 모양이고, 같은 id를 가진 행들은 위에서 아래로 바깥 루프에서 안쪽 루프로 읽으면 된다. 맨 위의 테이블을 흔히 드라이빙 테이블(driving table), 그 안쪽을 드리븐 테이블(driven table)이라고 부른다.

1행: o  (orders)       for o in orders where o.status = 'PAID':      ← 바깥 루프
2행: m  (member)           for m in member where m.id = o.member_id: ← 안쪽 루프

    id는 SELECT의 번호다. 서브쿼리나 UNION이 있으면 SELECT가 여러 개가 되고 번호가 갈린다. 조인만 있는 문장은 SELECT가 하나이므로 모든 행의 id가 1이다. UNION의 결과를 합치는 행처럼 특정 SELECT에 속하지 않는 행은 id가 NULL이고, 이때 table 열에는 처럼 합쳐진 SELECT 번호가 나온다. 비슷하게 는 id가 2인 SELECT의 결과로 만든 파생 테이블(FROM 절 서브쿼리)이고, 는 id가 2인 서브쿼리를 구체화(materialize)한 결과다. 별칭을 쓰면 table에는 테이블 이름 대신 별칭이 나온다.

    system: InnoDB 일반 테이블에서는 보기 어려운 이유

    system은 테이블에 행이 하나뿐일 때의 유형으로, 매뉴얼은 이를 const의 특수한 경우라고 설명한다. 그런데 InnoDB 테이블에 행을 하나만 넣고 EXPLAIN을 해 봐도 보통 system이 나오지 않는다. MySQL 8.0.46과 8.4.13에서 행 하나짜리 InnoDB 테이블 one (id INT PRIMARY KEY, v INT)에 EXPLAIN SELECT * FROM one을 실행하면 type은 ALL, rows는 1로 나온다. 이유는 옵티마이저 소스에 있다. MySQL 8.0의 JOIN::extract_const_tables()는 행이 0개나 1개인 테이블을 상수 테이블로 뽑을 때, 엔진이 HA_STATS_RECORDS_IS_EXACT(행 수 통계가 정확하다)라는 능력 플래그를 내세우는지를 조건으로 건다. InnoDB는 일반 테이블에 이 플래그를 켜지 않는다. 매뉴얼은 그 이유를 이렇게 설명한다. InnoDB는 동시에 실행되는 트랜잭션들이 같은 순간에 서로 다른 행 수를 "볼" 수 있기 때문에 테이블의 행 수를 내부에 따로 세어 두지 않는다. MVCC 아래에서는 "이 테이블의 정확한 행 수"라는 것이 트랜잭션마다 다르다는 뜻이다. 반면 InnoDB 소스(ha_innobase::table_flags())는 임시 테이블에 대해서는 행 수가 정확하다며 이 플래그를 켠다. 그래서 system은 정확한 행 수를 아는 엔진이나 임시 테이블에서 볼 수 있는 유형이고, 일반 InnoDB 테이블을 튜닝할 때는 거의 신경 쓸 일이 없다.

    const: 계획을 세우면서 미리 읽어 버리는 테이블

    const는 기본 키나 유니크 인덱스의 모든 열을 상수와 비교해서 결과가 많아야 한 행으로 정해질 때 나온다. 옵티마이저는 이런 테이블을 쿼리 시작 시점에 한 번 읽고, 그 행의 열 값을 나머지 최적화 과정에서 상수로 취급한다. 한 번만 읽으므로 매우 빠르다.

    EXPLAIN SELECT * FROM member WHERE id = 1\G
               id: 1
  select_type: SIMPLE
        table: member
   partitions: NULL
         type: const
possible_keys: PRIMARY

    한 줄씩 읽어 보자. 테이블 member에 const로 접근하고, 후보도 선택도 PRIMARY다. key_len 8은 BIGINT NOT NULL 열 하나의 길이이고, ref의 const는 인덱스에 상수를 대 보았다는 뜻이다. rows 1은 유니크 조건이므로 추정이 아니라 구조상 확정이다. 유니크 인덱스 uk_member_email로 WHERE email = 'a@example.com'을 조회해도 그 이메일의 행이 있다면 같은 모양이 나오고, 다만 key가 uk_member_email, key_len이 402가 된다(뒤에서 계산한다). 반대로 복합 기본 키 (a, b)에서 a만 상수로 주면 한 행이라는 보장이 사라지므로 const가 아니라 ref가 된다. "모든 열"이 조건이라는 점을 놓치지 말자.

    앞에서 말했듯 const 테이블은 최적화 도중에 실제로 읽힌다. 그래서 WHERE id = 999999999처럼 없는 키를 주면, 계획 표의 접근 정보 대신 Extra에 no matching row in const table이 나온다. const 테이블의 값이 상수가 되면 그 값을 쓰는 다른 조건도 미리 계산되는데, 그 결과 WHERE가 항상 거짓으로 판명되면 Impossible WHERE noticed after reading const tables가 나온다. 매뉴얼은 const나 system 테이블의 열을 쓰는 식이 옵티마이저에 의해 일찍 평가되어 SHOW WARNINGS의 다시 쓴 문장에 나타나지 않는다고도 적고 있다. 모두 "계획 단계에서 이미 읽었다"는 같은 사실의 다른 얼굴이다.

    eq_ref: 조인의 안쪽에서 한 행씩 정확히

    eq_ref는 조인에서만 나온다. 앞 테이블의 행 하나가 정해질 때마다, 이 테이블에서는 기본 키나 UNIQUE NOT NULL 인덱스의 모든 열을 =로 비교해 정확히 한 행만 읽는다. 매뉴얼은 이것을 system과 const 다음으로 가장 좋은 유형이라고 부른다. 주문을 회원과 조인하는 전형적인 쿼리에서 회원 쪽이 이렇게 읽힌다.

    EXPLAIN
SELECT o.id, o.amount, m.email
FROM orders o
JOIN member m ON m.id = o.member_id
WHERE o.status = 'PAID';

    옵티마이저가 orders를 먼저 읽는 순서를 골랐다면 member 행은 type: eq_ref, key: PRIMARY, key_len: 8, ref: shop.o.member_id, rows: 1로 나온다. ref에 상수 대신 데이터베이스.별칭.열 형태의 이름이 나온 것은 "앞 테이블 o의 member_id 값을 인덱스에 대 보았다"는 뜻이다. 그리고 여기서의 rows: 1은 쿼리 전체에서 한 행이라는 뜻이 아니라 앞 테이블 행 하나당 한 행이라는 뜻이다. orders에서 5천 행이 넘어오면 member의 기본 키 트리를 5천 번 내려간다. 이 "행당"이라는 감각은 뒤의 rows 절에서 다시 중요해진다.

    type 2: 여러 행과 구간, 그리고 스캔

    ref와 ref_or_null: 같은 값이 여러 개인 인덱스

    ref는 유니크가 아닌 인덱스에 동등 비교(= 또는 <=>)를 할 때, 또는 유니크 인덱스라도 왼쪽 일부 열만 비교할 때 나온다. 같은 키 값을 가진 항목이 여러 개일 수 있으므로, InnoDB는 B+Tree를 내려가 그 값의 첫 항목에 도달한 뒤 키 값이 달라질 때까지 리프를 오른쪽으로 걸어간다. 세컨더리 인덱스라면 항목마다 기본 키로 클러스터형 인덱스를 찾아 들어가 행 전체를 가져온다. 매뉴얼은 이 키로 맞는 행이 몇 개뿐이라면 좋은 유형이라고 말한다. 뒤집어 말하면, 맞는 행이 많으면 ref라도 느리다.

    EXPLAIN SELECT * FROM orders WHERE member_id = 42\G
               id: 1
  select_type: SIMPLE
        table: orders
   partitions: NULL
         type: ref
possible_keys: idx_orders_member
          key: idx_orders_member
      key_len: 8
          ref: const
         rows: 10
     filtered: 100.00
        Extra: NULL

    ref_or_null은 ref와 같지만 NULL인 항목까지 함께 찾는다. WHERE nickname = 'kim' OR nickname IS NULL처럼 "이 값이거나 비어 있거나"를 묻는 조건에서, idx_member_nickname을 쓰기로 했다면 이 유형이 나온다. InnoDB 인덱스에서 NULL 항목도 한곳에 모여 있으므로, 값의 구간과 NULL의 구간 두 군데를 읽는 셈이다. 매뉴얼은 이 유형이 서브쿼리를 처리할 때 자주 쓰인다고 덧붙인다. fulltext는 FULLTEXT 인덱스로 MATCH ... AGAINST를 처리할 때 나온다.

    index_merge, unique_subquery, index_subquery

    index_merge는 인덱스 하나로는 조건을 감당할 수 없을 때 인덱스 여러 개를 각각 읽고 그 결과를 합집합이나 교집합으로 합치는 방식이다. 이때 key에는 쓰인 인덱스가 여러 개 나열되고, key_len에는 인덱스마다 쓴 가장 긴 길이가 나열되며, Extra에 Using union(...), Using intersect(...), Using sort_union(...) 중 어떤 병합 알고리즘인지가 나온다. 언제 이 방식이 유리하고 언제 함정인지는 09회에서 다룬다. unique_subquery는 value IN (SELECT primary_key FROM single_table WHERE ...) 꼴의 서브쿼리를 기본 키 조회 함수로 바꿔 끼운 것이고, index_subquery는 같은 일을 유니크가 아닌 인덱스로 하는 것이다. 둘 다 바깥 행마다 인덱스 조회를 한 번씩 하는 구조라는 점에서 eq_ref, ref의 서브쿼리 판이라고 보면 된다.

    range: 인덱스의 한 구간

    range는 인덱스를 써서 정해진 구간의 행만 읽는다. MySQL 매뉴얼의 range 최적화 절은 단일 열 인덱스에서 어떤 조건이 구간 조건이 되는지를 정의한다. B-Tree 인덱스에서는 키 열을 상수와 =, <=>, IN(), IS NULL, IS NOT NULL, >, <, >=, <=, BETWEEN, !=, <>로 비교하거나, 와일드카드로 시작하지 않는 상수 문자열과 LIKE로 비교하는 것이 구간 조건이다. 여러 구간 조건을 AND나 OR로 묶어도 구간 조건이다. 여기서 "상수"에는 쿼리 문자열의 상수뿐 아니라 같은 조인의 const·system 테이블의 열, 상관관계가 없는 서브쿼리의 결과, 그리고 이것들로만 이루어진 식이 포함된다.

    -- 주석의 결과는 MySQL 8.0.46·8.4.13에서 실행한 것

-- 기본 키의 구간
EXPLAIN SELECT * FROM orders WHERE id BETWEEN 1000 AND 2000;
--   type: range, key: PRIMARY, key_len: 8, ref: NULL

-- IN 목록도 "점 구간" 여러 개라서 range다
EXPLAIN SELECT * FROM orders WHERE status IN ('PAID', 'SHIPPED');
--   두 값이 30%인 이 데이터에서는 type: ALL (possible_keys: idx_orders_status_ordered)
--   FORCE INDEX (idx_orders_status_ordered)로 인덱스를 쓰게 하면
--   type: range, key: idx_orders_status_ordered, key_len: 82, ref: NULL

-- 접두사 LIKE는 구간이 되지만, 와일드카드로 시작하면 구간이 될 수 없다
EXPLAIN SELECT * FROM member WHERE email LIKE 'kim%';   -- type: range, key: uk_member_email, key_len: 402
EXPLAIN SELECT * FROM member WHERE email LIKE '%kim';   -- type: ALL, possible_keys: NULL

    range에서는 ref 열이 항상 NULL이다. 인덱스에 "값 하나"를 대 보는 것이 아니라 구간의 경계를 정하는 것이기 때문이다. key_len은 쓰인 키 부분 중 가장 긴 길이를 보여 준다. IN 목록이 ref가 아니라 range로 나오는 것도 기억해 두자. status = 'PAID'는 값 하나를 대 보는 ref지만, status IN ('PAID', 'SHIPPED')는 점 구간 두 개를 차례로 읽는 range 접근이다. 구간 조건은 원래 WHERE보다 느슨할 수 있다는 점도 매뉴얼이 강조하는 부분이다. 옵티마이저는 구간을 만들 수 없는 조건을 버리는 것이 아니라 TRUE로 바꿔 구간을 넓게 잡고, 읽어 온 행에 원래 WHERE를 다시 적용해 걸러 낸다. 이 "다시 걸러 내기"가 뒤에서 볼 Using where의 정체 가운데 하나다.

    index와 ALL: 처음부터 끝까지

    index는 이름 때문에 가장 많이 오해받는 유형이다. 인덱스를 "잘 쓴다"는 뜻이 아니라 인덱스 전체를 처음부터 끝까지 읽는다는 뜻이다. 매뉴얼은 두 가지 경우를 든다. 하나는 쿼리에 필요한 열이 모두 그 인덱스 안에 있어서 인덱스만 훑으면 되는 경우로, 이때 Extra에 Using index가 함께 나온다. 세컨더리 인덱스는 보통 테이블보다 작으므로 같은 행 수를 훑어도 읽는 페이지가 적다. 다른 하나는 인덱스 순서대로 테이블 행을 읽으면서 전체를 훑는 경우로, 이때는 Using index가 나오지 않는다.

    -- member_id만 필요하므로 idx_orders_member 하나로 답할 수 있다
EXPLAIN SELECT member_id FROM orders;
--   MySQL 8.0.46·8.4.13에서 실행:
--   type: index, possible_keys: NULL, key: idx_orders_member, Extra: Using index

    이 예에는 흥미로운 점이 하나 있다. WHERE가 없으니 인덱스 후보를 뜻하는 possible_keys는 NULL인데, key에는 인덱스가 나온다. 매뉴얼은 이런 경우를 명시한다. possible_keys에 없는 인덱스라도 그 인덱스가 선택한 열을 모두 담고 있으면, 행을 찾는 데는 쓰지 못해도 데이터 행을 훑는 것보다 인덱스를 훑는 편이 싸기 때문에 key로 고를 수 있다.

    ALL은 테이블 전체를 읽는 풀 테이블 스캔(full table scan)이다. InnoDB에서 테이블은 곧 기본 키로 정렬된 클러스터형 인덱스이므로, ALL은 클러스터형 인덱스의 리프 페이지를 왼쪽 끝부터 오른쪽 끝까지 이어서 읽는 일이다. 매뉴얼은 ALL이 상수가 아닌 첫 테이블이라면 보통 좋지 않고, 그 밖의 경우라면 대개 매우 나쁘다고 말한다. 조인의 안쪽 테이블이 ALL이면 앞 테이블의 행 조합마다 테이블 전체를 읽는다는 뜻이기 때문이다. 그러나 드라이빙 테이블의 ALL은 맥락에 따라 정답일 수 있다. 앞에서 본 계산처럼 테이블의 상당 부분을 가져와야 한다면, 세컨더리 인덱스를 거쳐 흩어진 위치를 수십만 번 찾아가는 것보다 순서대로 한 번 훑는 편이 싸다. 수십 행짜리 코드 테이블이라면 인덱스를 만들 이유조차 없다.

    이 절의 핵심

    type의 순서는 "접근 한 번이 얼마나 좁은가"의 순서이지 쿼리 속도의 순위표가 아니다. 90%의 행을 읽는 range는 ALL보다 느릴 수 있고, 백만 행이 같은 값을 가진 ref는 거의 풀 스캔이다. type은 반드시 rows, filtered와 함께 읽어야 한다.

    possible_keys와 key: 후보와 선택

    possible_keys는 이 테이블의 행을 찾는 데 MySQL이 고를 수 있었던 인덱스 후보다. 매뉴얼은 이 열이 EXPLAIN에 나온 테이블 순서와 무관하게 정해진다고 강조한다. 즉 후보 중 일부는 실제로 선택된 조인 순서에서는 쓸 수 없는 것일 수 있다. 앞의 주문·회원 조인에서 orders의 후보에는 idx_orders_status_ordered와 함께 idx_orders_member도 나올 수 있다. 조인 조건 m.id = o.member_id가 있으니 회원을 먼저 읽는 순서라면 o.member_id로 찾아 들어갈 수 있기 때문이다. 하지만 주문을 먼저 읽는 계획에서는 그 시점에 비교할 회원 값이 아직 없으므로 이 후보는 쓰이지 않는다. possible_keys가 NULL이면 조건에 쓸 만한 인덱스가 하나도 없다는 뜻이고, 매뉴얼은 이때 WHERE에 쓰인 열을 살펴 인덱스를 검토하라고 권한다. 테이블에 어떤 인덱스가 있는지는 SHOW INDEX FROM orders로 확인한다.

    key는 그 후보 중에서 실제로 고른 인덱스다. 후보가 있는데 key가 NULL이고 type이 ALL이라면, 옵티마이저가 인덱스를 몰라서가 아니라 인덱스를 쓰는 비용이 더 크다고 추정했다는 뜻이다. 앞에서 계산한 것처럼 조건에 맞는 행이 테이블의 큰 비율을 차지하면, 세컨더리 인덱스를 거쳐 행마다 클러스터형 인덱스를 다시 찾아가는 것보다 한 번 훑는 편이 싸다. 이 판단을 사람이 뒤집고 싶다면 USE INDEX, FORCE INDEX, IGNORE INDEX 같은 인덱스 힌트를 쓸 수 있다. 다만 힌트는 오늘의 데이터 분포에 맞춘 결정을 문장 안에 못 박는 일이어서, 데이터가 바뀐 뒤에는 오히려 나쁜 계획을 강요할 수 있다. 힌트의 종류와 운영상 주의점은 09회에서 다룬다.

    인덱스가 후보에서 빠지는 네 가지 경우

    후보에 들었지만 비용 때문에 선택되지 않는 것과, 애초에 후보가 될 수 없는 것은 다른 문제다. 후자는 옵티마이저의 판단이 아니라 인덱스의 정렬 구조가 그 조건을 지원하지 못하는 경우다. B+Tree 인덱스는 키 값의 정렬 순서로 항목을 늘어놓은 구조이고, 인덱스를 "탄다"는 것은 정렬 순서 위에서 조건을 만족하는 연속된 구간의 시작점을 찾아 내려가는 일이다. 연속 구간을 만들 수 없는 조건은 인덱스로 찾아 들어갈 수 없다.

    첫째, 복합 인덱스의 왼쪽 열을 건너뛴 경우. idx_orders_status_ordered의 리프는 먼저 status로, 같은 status 안에서는 ordered_at으로 정렬되어 있다.

    idx_orders_status_ordered 의 리프 (정렬 순서대로, 값은 예시)

 (CANCELED, 2024-12-02) (CANCELED, 2025-02-11) (CANCELED, 2025-05-30)
 (PAID,     2024-11-17) (PAID,     2025-01-02) (PAID,     2025-03-01) (PAID, 2025-06-09)
 (SHIPPED,  2024-10-08) (SHIPPED,  2025-01-20) ...

 WHERE status = 'PAID' AND ordered_at >= '2025-01-01'
   → (PAID, 2025-01-02)부터 (PAID, 끝)까지 한 덩어리의 연속 구간

 WHERE ordered_at >= '2025-01-01'
   → CANCELED 묶음 안에 조금, PAID 묶음 안에 조금, SHIPPED 묶음 안에 조금…
     조건을 만족하는 항목이 상태마다 흩어져 있어 하나의 구간으로 묶을 수 없다

    그래서 WHERE ordered_at >= ... 하나만으로는 이 인덱스로 찾아 들어갈 수 없다. 매뉴얼의 복합 인덱스 절은 이것을 최좌측 접두사(leftmost prefix) 규칙으로 설명한다. 인덱스 (col1, col2, col3)은 (col1), (col1, col2), (col1, col2, col3)에 대한 조회에 쓸 수 있고, 열들이 인덱스의 왼쪽 접두사를 이루지 않으면 조회에 쓸 수 없다. 같은 이유로 매뉴얼은 last_name='Jones' OR first_name='John'처럼 첫 열과 둘째 열을 OR로 묶은 조건도 인덱스 (last_name, first_name)으로 찾을 수 없다고 예를 든다. 8.0.13부터는 첫 열의 서로 다른 값마다 구간을 나눠 뛰어다니는 스킵 스캔(skip scan)이라는 예외가 생겼지만, 적용 조건이 까다롭다. 08회에서 따로 다룬다.

    둘째, 인덱스 열을 함수나 연산으로 가공한 경우. 인덱스는 email의 값 순서로 정렬되어 있지 LOWER(email)의 순서로 정렬되어 있지 않다. range 최적화 절이 정의하는 구간 조건은 "키 열과 상수의 비교"이므로, WHERE LOWER(email) = 'kim@example.com'은 uk_member_email로 찾아 들어가는 조건이 되지 못한다. 날짜도 마찬가지다. YEAR(ordered_at) = 2025는 "2025-01-01 이상, 2026-01-01 미만"이라는 구간과 뜻이 같지만, 옵티마이저는 함수의 의미를 풀어 구간으로 바꿔 주지 않는다. 사람이 처음부터 구간으로 써야 한다.

    -- 인덱스로 찾아 들어갈 수 없는 형태
WHERE LOWER(email) = 'kim@example.com'
WHERE status = 'PAID' AND YEAR(ordered_at) = 2025

-- 같은 뜻을 열 그대로 비교하는 형태
WHERE email = 'kim@example.com'
WHERE status = 'PAID' AND ordered_at >= '2025-01-01' AND ordered_at < '2026-01-01'

    LOWER의 경우는 사정이 하나 더 있다. MySQL 8.0의 utf8mb4 기본 콜레이션은 utf8mb4_0900_ai_ci이고, 이름 끝의 ci는 대소문자를 구분하지 않는 비교(case-insensitive)라는 뜻이다. 이 콜레이션의 열이라면 email = 'KIM@example.com'만으로 대소문자가 다른 값도 같다고 비교되므로 LOWER를 씌울 이유가 처음부터 없다. 정말로 가공한 값으로 찾아야 한다면 8.0.13부터 지원하는 함수 기반 키 파트(functional key part), 예컨대 CREATE INDEX idx_lower_email ON member ((LOWER(email)))처럼 가공한 값 자체를 인덱스로 만드는 방법이 있다.

    셋째, 타입 변환이 끼어든 경우. phone은 VARCHAR(20)인데 따옴표를 빠뜨려 WHERE phone = 01012345678이라고 쓰면, 오른쪽은 숫자 상수(앞의 0이 사라진 1012345678)가 된다. 매뉴얼의 타입 변환 절은 문자열 열과 숫자를 비교하면 그 열의 인덱스로 값을 빠르게 찾을 수 없다고 명시하고, 이유를 이렇게 든다. 숫자 1로 변환되는 문자열은 '1', ' 1', '1a'처럼 여러 가지가 있기 때문이다. 문자열과 숫자의 비교는 결국 부동소수점 수의 비교로 이루어지고, 인덱스의 정렬 순서(문자열 순서)와 비교의 기준(숫자 크기)이 달라 구간을 만들 수 없다. MySQL 8.0 소스는 이런 상황을 EXPLAIN에서 경고로 알려 준다. sql_optimizer.cc와 range 분석 코드가 EXPLAIN 중이면 다음 형식의 경고를 남기도록 되어 있다.

    EXPLAIN SELECT * FROM member WHERE phone = 01012345678;
SHOW WARNINGS;

Warning | 1739 | Cannot use range access on index 'idx_member_phone' due to type or collation conversion on field 'phone'
Note    | 1003 | /* select#1 */ select `m_db_perf_02`.`member`.`id` AS `id`, ... from `m_db_perf_02`.`member` where (`m_db_perf_02`.`member`.`phone` = 1012345678)

    같은 EXPLAIN의 계획 표는 possible_keys에 idx_member_phone이 있는데도 type: ALL, key: NULL이다. Note에 다시 쓴 조건이 phone = 1012345678로 나와 앞의 0이 사라진 숫자 상수와 비교한다는 점도 확인할 수 있다.

    메시지에 "collation conversion"이 함께 적혀 있는 것도 눈여겨보자. 소스의 주석은 서로 다른 콜레이션의 문자열을 비교하는 경우도 같은 경고의 대상이라고 예를 든다. 조인하는 두 테이블의 문자열 열이 서로 다른 문자 집합이나 콜레이션으로 만들어져 있으면, 조인 조건이 있어도 안쪽 테이블의 인덱스로 찾아 들어가지 못하는 일이 생긴다. 실행 계획에서 기대한 인덱스가 보이지 않을 때 SHOW WARNINGS를 먼저 확인하는 습관이 필요한 이유다.

    넷째, 서로 다른 열을 OR로 묶은 경우. WHERE member_id = 42 OR status = 'PAID'는 어느 인덱스 하나의 연속 구간으로도 표현되지 않는다. 각 열에 인덱스가 따로 있다면 옵티마이저는 두 인덱스를 각각 읽어 합치는 index_merge를 시도할 수 있고, 그 비용이 크다고 보면 풀 스캔을 고른다.

    key_len: 인덱스를 몇 바이트까지 썼는가

    key_len은 MySQL이 사용하기로 한 키의 길이를 바이트로 보여 준다. 매뉴얼은 이 값으로 복합 인덱스의 몇 번째 부분까지 실제로 쓰였는지 알 수 있다고 설명한다. key가 NULL이면 key_len도 NULL이다. 복합 인덱스를 설계하고 검증할 때 가장 정확한 단서가 이 열이다. "인덱스를 탔다"는 사실만으로는 부족하고, 인덱스의 어디까지가 찾아 들어가는 데 쓰였는가를 알아야 하기 때문이다.

    계산 규칙: 소스에서 확인한 세 항목

    매뉴얼은 키 저장 형식 때문에 NULL을 허용하는 열은 NOT NULL 열보다 키 길이가 1 크다고만 적는다. 나머지 규칙은 MySQL 8.0 소스에서 확인할 수 있다. sql/table.cc는 키를 이루는 각 열의 길이(store_length)를 계산할 때, 열 자체의 키 길이에서 시작해 NULL을 허용하면 HA_KEY_NULL_LENGTH를 더하고, 열이 VARCHAR·BLOB·GEOMETRY 계열이면 HA_KEY_BLOB_LENGTH를 더한다. 두 상수는 sql/handler.h에 각각 1과 2로 정의되어 있다. 열 자체의 키 길이는 고정 길이 타입이면 저장 크기(INT 4, BIGINT 8, DATE 3, DATETIME 5바이트에 소수 초 정밀도에 따라 0~3바이트 추가)이고, 문자열이면 선언한 글자 수에 문자 집합의 글자당 최대 바이트 수를 곱한 값이다. utf8mb4는 글자당 최대 4바이트다.

    key_len(키 부분 하나) =  데이터의 최대 바이트 수
                       + 1   ← NULL 허용 열이면 (NULL 여부 표시)
                       + 2   ← VARCHAR 등 가변 길이 열이면 (실제 길이 표시)

key_len(전체)         =  실제로 쓰인 키 부분들의 합

    가변 길이 열에 늘 2를 더한다는 점은 한 번 짚고 넘어갈 만하다. 저장 요구량 절에 따르면 VARCHAR 값은 행에 저장될 때 최대 바이트 수가 255 이하면 길이를 1바이트로, 그보다 크면 2바이트로 적는다. 그런데 key_len은 언제나 2를 더한다. key_len이 디스크에 저장된 인덱스 항목의 크기가 아니라, 서버 계층이 키 값을 담아 엔진에 넘기고 비교하는 키 버퍼 형식의 길이이기 때문이다. 그래서 key_len을 인덱스 크기를 추정하는 데 쓰면 안 되고, "어느 키 부분까지 쓰였는가"를 판별하는 데만 써야 한다.

    복합 인덱스 사용 범위 읽기

    이제 같은 인덱스에 조건을 바꿔 가며 key_len을 예측해 보자. 모두 옵티마이저가 idx_orders_status_ordered를 쓰기로 했을 때의 값이다.

    -- 주석은 SELECT * FROM orders WHERE ...로 MySQL 8.0.46·8.4.13에서 실행한 결과
-- (4)는 이 데이터에서 옵티마이저가 ALL을 골라 FORCE INDEX로 이 인덱스를 쓰게 했다
-- (1) 첫 열만 동등 비교
WHERE status = 'PAID'                                    -- ref,   key_len 82, ref const
-- (2) 첫 열 동등 + 둘째 열 구간
WHERE status = 'PAID' AND ordered_at >= '2025-01-01'     -- range, key_len 87
-- (3) 첫 열 동등 + 둘째 열을 함수로 가공
WHERE status = 'PAID' AND YEAR(ordered_at) = 2025        -- ref,   key_len 82, Using index condition
-- (4) 첫 열이 구간
WHERE status >= 'P' AND ordered_at >= '2025-01-01'       -- range, key_len 87 (used_key_parts는 status뿐)
-- (5) 인덱스에 없는 열의 조건 추가
WHERE status = 'PAID' AND amount > 10000                 -- ref,   key_len 82, Using where

    (1)과 (2)의 5바이트 차이가 곧 "ordered_at 조건이 읽을 구간을 좁히는 데 쓰였는가"의 차이다. (3)은 (2)와 같은 뜻의 조건이지만 ordered_at을 함수로 감쌌기 때문에 구간을 좁히지 못하고, status = 'PAID'인 항목 전체를 읽는다. YEAR(ordered_at) = 2025 조건은 그 뒤에 따로 검사된다. 이 조건은 인덱스에 들어 있는 열만 참조하므로 InnoDB가 행 전체를 읽기 전에 인덱스 항목에서 먼저 검사할 수 있는데(인덱스 컨디션 푸시다운, 08회), 그래도 읽는 인덱스 구간 자체는 줄지 않는다.

    (4)는 매뉴얼의 range 최적화 절에 나오는 규칙 그대로다. B-Tree 인덱스에서 옵티마이저는 키 부분을 =, <=>, IS NULL로 비교하는 동안에만 다음 키 부분을 구간에 이어 붙이고, >, <, BETWEEN, LIKE 같은 비교를 만나면 그 키 부분까지만 쓰고 더 뒤의 키 부분은 고려하지 않는다. 앞의 정렬 그림으로 보면 이유가 분명하다. status >= 'P'는 PAID, SHIPPED 같은 여러 상태 묶음을 포함하고, 각 묶음 안에서 ordered_at은 처음부터 다시 정렬되므로 "2025-01-01 이후"는 하나의 연속 구간이 아니다. 그런데 실제로 실행해 보면 (4)의 key_len은 82가 아니라 87로 나온다. 하한이 >=로 닫혀 있으면 옵티마이저가 구간의 시작점을 ('P', '2025-01-01')로 잡으면서 ordered_at까지 이어 붙이기 때문이다. EXPLAIN FORMAT=TREE에도 over ('P' <= status AND '2025-01-01 00:00:00' <= ordered_at)로 나온다. 하지만 구간의 끝은 열려 있어서 PAID나 SHIPPED 묶음의 2024년 항목도 모두 구간 안에 들어가므로, ordered_at이 읽을 구간을 좁혔다고 볼 수 없다. EXPLAIN FORMAT=JSON의 used_key_parts는 status 하나만 보여 주고, ordered_at 조건은 index_condition(인덱스 컨디션 푸시다운)으로 검사된다. 같은 조건을 status > 'P'로 바꾸면 key_len은 82다. 뒤에서 말할 "예상보다 많은 키 부분"의 한 예다. (5)의 amount는 인덱스에 없는 열이므로 key_len에 영향을 주지 못하고, 행을 읽은 뒤 서버가 거른다.

    예외도 하나 알아 두자. 매뉴얼은 key_len이 예상보다 많은 키 부분을 보여 줄 수 있다고 적는다. key_part1 >= 1 AND key_part2 < 2 같은 조건이 내부적으로 key_part1 >= 1 AND key_part2 IS NOT NULL로 바뀌어, 두 열이 모두 NULL을 허용하면 두 부분의 길이가 함께 잡힐 수 있다는 것이다. 이런 혼동 없이 쓰인 열을 이름으로 보고 싶다면 EXPLAIN FORMAT=JSON의 used_key_parts를 보면 된다. 소수 초 정밀도가 있는 시간 타입은 길이가 달라진다는 점도 주의한다. 저장 요구량 절에 따라 DATETIME(3)은 5 + 2 = 7바이트, DATETIME(6)은 5 + 3 = 8바이트다.

    ref: 인덱스에 무엇을 대 보았는가

    ref 열은 key에 나온 인덱스와 비교한 값이 무엇인지 보여 준다. MySQL 8.0 소스(opt_explain.cc)는 쓰인 키 부분마다 하나씩 값을 적고, 키 부분이 여럿이면 쉼표로 이어 붙인다. 나올 수 있는 값은 네 가지다.

    • const: 상수와 비교했다. WHERE member_id = 42처럼 쿼리에 적힌 값이거나, 상수로 정해진 값이다. 키 부분 두 개를 모두 상수로 비교하면 const,const처럼 나온다.
    • 데이터베이스.테이블.열: 조인에서 앞 테이블의 열 값과 비교했다. 앞의 예에서 shop.o.member_id가 그것이다. 테이블 자리에는 별칭이 나온다.
    • func: 함수나 연산의 결과와 비교했다. 매뉴얼은 어떤 함수인지 보려면 EXPLAIN 직후 SHOW WARNINGS로 다시 쓴 문장을 보라고 안내한다.
    • NULL: 값 하나를 대 보는 접근이 아니다. range, index, ALL에서는 항상 NULL이다.

    const가 꼭 쿼리에 적힌 상수만은 아니라는 점이 흥미롭다. 다음 쿼리를 보자.

    EXPLAIN
SELECT *
FROM member m
JOIN orders o ON o.member_id = m.id
WHERE m.id = 42;

    회원 쪽은 기본 키 상수 비교이므로 const로 읽힌다. 주문 쪽의 조인 조건은 o.member_id = m.id로 다른 테이블의 열과 비교하는 것처럼 보이지만, m.id는 이미 42로 확정된 const 테이블의 열이다. range 최적화 절의 "상수" 정의에 const 테이블의 열이 들어 있는 것과 같은 원리로, 옵티마이저는 이 비교를 o.member_id = 42와 같게 취급한다. 그래서 주문 쪽 행은 type: ref, key: idx_orders_member, ref: const로 나온다. 계획 단계에서 미리 읽은 값이 다음 테이블의 접근 방법까지 바꾼 것이다.

    func는 비교 대상 쪽에 연산이 들어간 경우다. 조인 조건이 m.id = ABS(o.member_id)처럼 앞 테이블 열을 가공한 값이라면, 회원 쪽은 여전히 기본 키로 찾아 들어갈 수 있고 ref에는 func가 나온다. 소스의 store_key::name()은 비교 값이 열이면 열 이름을, 열이 아니면 "func"를 돌려주도록 되어 있다. 여기서 원리 하나를 정리할 수 있다. 가공이 인덱스 쪽 열에 붙으면 인덱스로 찾아 들어갈 수 없고, 상대편 값에 붙으면 문제가 없다. 인덱스로 찾아 들어간다는 것은 "이 값"을 정렬된 트리에서 찾는 일이고, 그 값을 어떻게 계산했는지는 트리와 무관하기 때문이다. WHERE ordered_at >= NOW() - INTERVAL 7 DAY가 인덱스를 쓸 수 있고 WHERE ordered_at + INTERVAL 7 DAY >= NOW()가 쓸 수 없는 것도 같은 이유다.

    rows: 살펴볼 행 수의 예상

    rows는 MySQL이 이 접근에서 살펴봐야 한다고 믿는 행 수다. 매뉴얼은 InnoDB 테이블에서 이 값이 추정치이며 항상 정확하지는 않다고 분명히 적는다. 두 가지를 오해하지 말아야 한다. 첫째, rows는 결과로 돌려줄 행 수가 아니라 살펴볼(examine) 행 수다. 나머지 조건으로 걸러지기 전의 수다. 둘째, 조인의 안쪽 테이블에서 rows는 앞 테이블의 행 조합 하나당 살펴볼 행 수다. JSON 형식의 이름이 rows_examined_per_scan인 것이 이 뜻을 정확히 드러낸다.

    이 추정치는 어디서 오는가. 비교 값이 쿼리에 상수로 주어진 경우, range 최적화 절에 따르면 옵티마이저는 인덱스 다이브(index dive), 즉 구간의 양쪽 끝으로 실제 인덱스를 내려가 보는 방법으로 그 사이의 행 수를 추정하거나, 인덱스 통계를 쓴다. 다이브가 더 정확하지만 IN 목록의 값이 많아질수록 느려지므로, 값의 개수가 eq_range_index_dive_limit 시스템 변수에 이르면 통계 쪽으로 넘어간다. 반면 조인 조건처럼 비교 값이 실행 중에야 정해지는 경우에는 미리 인덱스를 내려가 볼 값이 없으므로, "키 값 하나당 평균 몇 행"이라는 인덱스 통계에 기댈 수밖에 없다. ALL의 rows는 테이블 전체 행 수의 추정치다. 앞에서 본 것처럼 InnoDB는 정확한 행 수를 따로 세어 두지 않으므로, 매뉴얼의 표현대로 SHOW TABLE STATUS의 행 수도 SQL 최적화에 쓰는 대략적인 추정일 뿐이다. 통계는 ANALYZE TABLE로 갱신할 수 있고, 통계가 어떻게 모이고 언제 갱신되는지는 10회에서 다룬다.

    매뉴얼은 조인 전체의 작업량을 가늠하는 방법도 제시한다. EXPLAIN의 rows 값을 모두 곱하면 쿼리를 실행하는 데 살펴볼 행 조합 수의 대략적인 값이 된다. 매뉴얼의 예제에서는 네 테이블이 모두 ALL로 읽히던 계획의 곱이 74 × 2,135 × 74 × 3,872 = 45,268,558,720이었고, 조인 열의 타입을 맞추고 ANALYZE TABLE을 실행한 뒤에는 세 테이블이 eq_ref로 바뀌어 풀 스캔이 3,872행짜리 테이블 하나만 남았다. 곱셈이라는 점이 핵심이다. 안쪽 테이블 하나의 rows가 1에서 100으로 늘어나면 전체 작업량이 100배가 된다.

    filtered: 살펴본 행 중 몇 퍼센트가 남는가

    filtered는 이 테이블에서 살펴본 행 가운데 테이블 조건을 통과할 것으로 예상하는 비율(퍼센트)이다. 최댓값 100은 걸러지는 행이 없다는 뜻이고, 값이 작을수록 많이 걸러진다. 매뉴얼은 rows × filtered가 다음 테이블과 조인될 행 수라고 설명하고, rows가 1000이고 filtered가 50.00이면 1000 × 50% = 500행이 다음 테이블로 넘어간다는 예를 든다. JSON 형식에서는 이 곱을 rows_produced_per_join으로 바로 보여 준다.

    어떤 조건이 filtered에 반영되는가. 매뉴얼의 조건 필터링(condition filtering) 절은 세 가지를 모두 만족하는 조건만 기여한다고 정의한다. 현재 테이블을 참조하고, 상수나 조인 순서상 앞 테이블의 값에만 의존하며, 접근 방법이 이미 반영하지 않은 조건이어야 한다. 마지막 조건이 중요하다. MySQL 8.0 소스(sql_planner.cc)의 주석은 ref나 range 접근이라면 그 조건은 이미 rows 추정에 들어 있으므로, 접근에 쓴 열은 filtered에 기여하지 않는다고 적고 있다. 그래서 WHERE member_id = 42 하나뿐인 ref 접근의 filtered는 100.00이다. 걸러 낼 조건이 접근 조건 말고는 없기 때문이다.

    비율은 어떻게 추정되는가: 통계, 히스토그램, 기본값

    소스를 따라가 보면 filtered의 추정은 세 단계로 이루어진다. 첫째, 범위 최적화기가 접근에 쓰이지 않은 다른 인덱스로 해당 조건의 행 수를 추정해 두었다면 그 값을 쓴다. 소스 주석은 범위 최적화기의 추정이 인덱스 통계보다 정확하기 때문이라고 이유를 단다. 둘째, 해당 열에 히스토그램이 있으면 히스토그램으로 선택도를 계산한다. 셋째, 둘 다 없으면 연산자별 기본값을 쓴다. 기본값은 sql/item.h에 정의되어 있다.

    조건 형태소스의 상수기본 비율
    col = 값COND_FILTER_EQUALITY0.1 (10%)
    col > 값, <, >=, <=COND_FILTER_INEQUALITY0.3333 (33.33%)
    col BETWEEN a AND bCOND_FILTER_BETWEEN0.1111 (11.11%)
    col LIKE '...'BETWEEN과 같은 값을 씀0.1111 (11.11%)
    col != 값1 − 동등 비율0.9 (90%)

    여기에 두 가지 보정이 붙는다. 기본값은 연산자와 관계없이 max(1 / 테이블 행 수 추정치, 기본값)로 쓰이므로, 테이블이 아주 작으면 기본값보다 큰 비율이 나온다. ENUM이나 BIT처럼 가질 수 있는 값의 개수가 정해진 타입은 그 개수도 고려한다. 조건이 여럿이면 AND는 각 비율을 곱하고(소스 주석의 표현으로 "독립 사건의 교집합"), OR는 P(A) + P(B) − P(A)·P(B)로 합친다. 마지막으로 전체 비율이 테이블에서 적어도 한 행은 남는 값보다 작아지지 않게 하한을 둔다.

    -- amount, memo에는 인덱스도 히스토그램도 없다고 하자
-- 주석은 MySQL 8.0.46·8.4.13에서 실행한 결과(rows는 8.4.13 값, 8.0.46은 99764)
EXPLAIN SELECT * FROM orders WHERE amount > 10000;
--   type: ALL, rows: 99783, filtered: 33.33, Extra: Using where

EXPLAIN SELECT * FROM orders WHERE memo = '선물 포장';
--   type: ALL, filtered: 10.00, Extra: Using where

EXPLAIN SELECT * FROM orders WHERE amount > 10000 AND memo = '선물 포장';
--   type: ALL, filtered: 3.33        ← 0.3333 × 0.1 = 0.03333

    이 표를 알고 나면 실행 계획에서 filtered가 정확히 10.00, 33.33, 11.11, 3.33 같은 값으로 나올 때 그 의미를 읽을 수 있다. 옵티마이저가 데이터를 보고 계산한 비율이 아니라, 아무 정보가 없어서 연산자 모양만 보고 정한 값일 가능성이 높다는 신호다. 실제 amount > 10000을 만족하는 주문이 1%든 99%든 추정은 33.33%다. 그리고 AND를 곱셈으로 합치는 것은 두 조건이 서로 독립이라는 가정인데, "도시가 서울"과 "우편번호가 서울 지역"처럼 서로 강하게 얽힌 조건이라면 곱셈은 실제보다 훨씬 작은 비율을 만든다. 이런 오차가 조인 순서를 잘못 고르게 만드는 대표적인 원인이고, 히스토그램은 이 문제를 줄이기 위한 도구다(10회).

    인덱스가 있는 열이라면 사정이 다르다. 조건 필터링 절의 예제는 직원 1,024명과 부서 12개를 조인하면서 first_name = 'John'(8행)을 ref 접근에 쓰고, 인덱스가 있는 hire_date의 BETWEEN 조건으로 필터를 추정한다. 조건 필터링이 꺼져 있으면 filtered가 100.00이어서 다음 테이블로 8행이 넘어간다고 추정하지만, 켜져 있으면 휴리스틱으로 16.31%를 추정해 8 × 16.31% ≈ 1.3행으로 계산한다. 예제 데이터에서 두 조건을 모두 만족하는 행은 실제로 1행이어서, 필터링을 반영한 쪽이 실제에 더 가깝다. 이 기능은 optimizer_switch의 condition_fanout_filter 플래그로 켜고 끄며 기본값은 켜짐이다. 필터 추정이 오히려 나쁜 계획을 만든다면 세션 단위로 끄거나, /*+ SET_VAR(optimizer_switch = 'condition_fanout_filter=off') */ 힌트로 문장 하나에서만 끌 수 있다.

    rows와 filtered로 조인을 어림하기

    두 열을 함께 쓰면 조인의 작업량을 단계별로 따라갈 수 있다. 아래 숫자는 계산을 보여 주기 위한 가정이다. 주문을 먼저 읽는 계획에서 orders의 rows가 6,000이고 filtered가 33.33이라면, 다음 테이블로 넘어가는 행은 6,000 × 0.3333 ≈ 2,000행이다. member가 eq_ref로 rows 1이면, 기본 키 조회가 약 2,000번 일어나고 결과도 약 2,000행이다. 만약 회원을 먼저 읽는 순서였다면 member 전체(예를 들어 10만 행)를 ALL로 훑으면서 행마다 idx_orders_member로 주문을 찾아 들어가야 하므로 인덱스 조회만 10만 번이다. 옵티마이저는 이런 식으로 테이블마다 넘겨주는 행 수(prefix rows)와 비용을 누적해 조인 순서를 비교한다. 그래서 filtered 하나가 틀리면 조인 순서 전체가 뒤집힐 수 있다.

    드라이빙 테이블에서 rows만큼 읽고 filtered 비율로 줄어든 행이 다음 테이블로 넘어가, 넘어온 행 하나마다 안쪽 테이블을 rows만큼 읽는 흐름을 깔때기 모양으로 보여 준다. 위에서 아래로 흐르는 깔때기 흐름도. 맨 위에 넓은 가로 막대 "orders · rows 6,000"이 있고, 그 아래 좁아지는 깔때기 모양에 "filtered 33.33%" 라벨이 붙어 있다. 깔때기 출구에서 나온 중간 막대에 "약 2,000행 → 다음 테이블로" 라벨. 그 막대에서 오른쪽으로 화살표가 나가 작은 원통 "member PRIMARY"에 닿고, 화살표 위에 "행마다 eq_ref · rows 1" 라벨. 맨 아래에 결과 막대 "결과 약 2,000행". 왼쪽 여백에 세로로 "rows × filtered = 다음 테이블로 넘어가는 행" 메모가 있다. 오른쪽 아래 구석에 작은 회색 글씨로 "숫자는 예시". 흰 배경, 파란색과 회색, 강조는 주황색 하나. rows는 살펴볼 행, rows × filtered는 다음 단계로 넘어가는 행이다. 안쪽 테이블의 rows는 넘어온 행 하나당 값이다.

    Extra: 행을 가져온 뒤에 무엇을 더 하는가

    Extra 열은 앞의 열들로 표현되지 않는 추가 정보를 담는다. 값의 종류가 많지만 성격별로 나누면 정리가 쉽다. 아래 분류는 매뉴얼의 Extra 목록을 이 회차의 관점에서 묶은 것이다.

    조건을 어디서 검사하는가Using where, Using index condition서버 계층에서 거르는가, 엔진이 인덱스 항목에서 먼저 거르는가

    Using where: 서버 계층의 필터

    매뉴얼의 정의로 Using where는 WHERE 절이 다음 테이블과 맞춰 볼 행이나 클라이언트로 보낼 행을 제한하는 데 쓰였다는 뜻이다. 구조로 보면 이렇다. 실행기가 핸들러 API로 엔진에 다음 행을 요청하고, 엔진이 행을 돌려주면, 서버 계층이 그 행에 남은 조건(JSON의 attached_condition)을 평가해 통과한 행만 다음 단계로 넘긴다. 즉 Using where는 "인덱스를 못 썼다"는 뜻이 아니라 "엔진이 준 행을 서버가 한 번 더 거른다"는 뜻이다. 앞의 (5)번 예처럼 ref로 잘 찾아 들어간 뒤에도 인덱스에 없는 열의 조건이 있으면 나온다. 매뉴얼은 반대 방향의 경고도 한다. 테이블의 모든 행을 가져오거나 검사하려는 의도가 아닌데 type이 ALL이나 index이고 Extra에 Using where가 없다면, 쿼리에 문제가 있을 수 있다. 조건 없이 전체를 읽고 있다는 뜻이기 때문이다.

    Using index: 테이블을 건너뛰는 커버링 인덱스

    Using index는 필요한 열을 인덱스 트리에서만 읽고 실제 행은 읽지 않았다는 뜻이다. 이런 인덱스를 그 쿼리에 대한 커버링 인덱스(covering index)라고 한다. InnoDB에서 세컨더리 인덱스로 행을 가져오려면 항목마다 기본 키로 클러스터형 인덱스를 다시 찾아 들어가야 하는데, 커버링이면 이 두 번째 탐색이 통째로 사라진다. 앞에서 계산한 "30만 번의 흩어진 접근"이 없어진다는 뜻이다. 매뉴얼은 InnoDB의 세컨더리 인덱스가 각 항목에 기본 키 값을 함께 저장하므로, 기본 키 열을 함께 조회해도 세컨더리 인덱스가 쿼리를 커버할 수 있다고 적는다.

    -- idx_orders_member의 항목은 (member_id, id)를 담고 있다
EXPLAIN SELECT id, member_id FROM orders WHERE member_id = 42;
--   type: ref, key: idx_orders_member, Extra: Using index

-- amount가 필요해지면 행을 읽으러 가야 한다
EXPLAIN SELECT id, amount FROM orders WHERE member_id = 42;
--   type: ref, key: idx_orders_member, Extra: NULL

    여기서 type: index와 Extra: Using index를 혼동하지 말자. 전자는 "인덱스 전체를 훑는다"는 접근 범위의 이야기이고, 후자는 "행을 읽지 않고 인덱스만으로 끝낸다"는 읽는 대상의 이야기다. 둘은 독립적이다. ref나 range에 Using index가 붙을 수 있고, type: index인데 Using index가 없을 수도 있다. 커버링 인덱스의 설계는 08회에서 깊이 다룬다.

    Using index condition: 엔진에게 넘긴 조건

    Using index condition은 인덱스 컨디션 푸시다운(Index Condition Pushdown, ICP)이 쓰였다는 표시다. 매뉴얼은 ICP가 없을 때와 있을 때의 차이를 이렇게 설명한다. ICP가 없으면 엔진은 인덱스 항목으로 행 전체를 찾아 읽어 서버에 넘기고, 서버가 WHERE 조건을 검사한다. ICP가 있으면 서버가 조건 가운데 인덱스 열만으로 검사할 수 있는 부분을 엔진에 넘기고, 엔진은 인덱스 항목에서 그 조건을 먼저 검사해 통과한 항목에 대해서만 행 전체를 읽는다. InnoDB에서는 세컨더리 인덱스에만 적용된다. 클러스터형 인덱스는 이미 행 전체를 버퍼로 읽은 상태이므로 ICP로 줄일 I/O가 없기 때문이다. 앞의 (3)번 예에서 YEAR(ordered_at) = 2025가 이렇게 검사될 수 있다.

    Using filesort와 Using temporary: 별도 단계가 붙는다

    Using filesort는 결과를 정해진 순서로 내보내기 위해 정렬 단계가 한 번 더 필요하다는 뜻이다. 예를 들어 SELECT * FROM orders WHERE member_id = 42 ORDER BY ordered_at는 idx_orders_member로 42번 회원의 주문을 찾을 수 있지만, 이 인덱스 안에서 같은 member_id의 항목은 기본 키 순서로 놓여 있지 ordered_at 순서가 아니다. 그래서 읽은 뒤 정렬해야 하고, Extra에 Using filesort가 붙는다. 이름에 "file"이 들어 있지만 반드시 디스크를 쓴다는 뜻은 아니다. 정렬할 데이터가 정렬 버퍼(sort_buffer_size)에 들어가면 메모리 안에서 끝나고, 넘칠 때 임시 파일을 쓴다. Using temporary는 결과를 담기 위해 내부 임시 테이블이 필요하다는 뜻으로, 매뉴얼은 GROUP BY와 ORDER BY가 서로 다른 열을 나열하는 경우를 전형적인 예로 든다. 매뉴얼은 쿼리를 가능한 한 빠르게 만들고 싶다면 이 두 값을 주의해서 보라고 한다. 정렬과 그 회피는 07회, 그룹핑과 임시 테이블은 12회의 주제다.

    Using join buffer (hash join)은 앞 테이블들의 행을 조인 버퍼에 모아 두었다가 현재 테이블과 맞추는 방식이 쓰였다는 뜻이다. 해시 조인은 8.0.18부터 쓸 수 있고, 매뉴얼에 따르면 8.0.20 이후에는 예전의 블록 중첩 루프(Block Nested-Loop) 알고리즘이 쓰이지 않는다. 조인 알고리즘의 내부는 11회에서 다룬다.

    계획 단계에서 끝나는 경우와 그 밖의 값

    몇몇 값은 테이블을 읽을 필요가 없다는 사실을 계획 단계에서 알아냈다는 뜻이다. WHERE 1 = 0처럼 항상 거짓인 조건이면 Impossible WHERE, SELECT NOW()처럼 FROM이 없으면 No tables used, LIMIT 0이면 Zero limit이 나온다. SELECT MIN(id) FROM orders에는 Select tables optimized away가 나오는데, 매뉴얼의 설명대로 결과가 많아야 한 행이고 그 행을 최적화 도중에 만들어 낼 수 있어서 실행 단계에서는 테이블을 읽지 않는다는 뜻이다. 정렬된 B+Tree에서 최솟값은 가장 왼쪽 항목이므로 한 번 내려가면 끝난다.

    Range checked for each record (index map: N)은 미리 정할 만한 좋은 인덱스는 없지만, 앞 테이블의 행 값이 정해지면 그때마다 range나 index_merge를 쓸 수 있을지도 모르는 상황이다. 옵티마이저는 앞 테이블의 행 조합마다 인덱스를 쓸지 다시 판단한다. N은 후보 인덱스를 나타내는 비트 마스크로, 매뉴얼의 예에서 0x19(이진수 11001)는 SHOW INDEX 순서로 1, 4, 5번 인덱스가 후보라는 뜻이다. 그 밖에 Using index for skip scan은 08회, Using MRR과 Using union(...) 같은 인덱스 머지 표시는 09회, FirstMatch·LooseScan·Start temporary 같은 세미조인 전략은 11회, Using index for group-by는 12회에서 각각 다시 만난다.

    한 계획을 처음부터 끝까지 읽기

    지금까지의 열을 모두 모아 하나의 계획을 읽어 보자. 결제 완료된 5만 원 이상 주문과 그 회원의 이메일을 가져오는 쿼리다.

    EXPLAIN
SELECT o.id, o.amount, m.email
FROM orders o
JOIN member m ON m.id = o.member_id
WHERE o.status = 'PAID'
  AND o.amount >= 50000\G
    *************************** 1. row ***************************
           id: 1
  select_type: SIMPLE
        table: o
   partitions: NULL
         type: ref
possible_keys: idx_orders_member,idx_orders_status_ordered
          key: idx_orders_status_ordered
      key_len: 82
          ref: const
         rows: 20232
     filtered: 33.33
        Extra: Using where
*************************** 2. row ***************************
           id: 1
  select_type: SIMPLE
        table: m
   partitions: NULL
         type: eq_ref
possible_keys: PRIMARY
          key: PRIMARY
      key_len: 8
          ref: m_db_perf_02.o.member_id
         rows: 1
     filtered: 100.00
        Extra: NULL

    같은 계획을 TREE 형식으로 보면 구조가 더 직접적으로 드러난다. 아래는 MySQL 8.0.46에서 실행한 결과이고, 비용과 행 수는 실행 환경과 통계에 따라 달라진다. 8.4.13에서는 문구와 행 수가 같고 비용만 위에서부터 9235, 1923, 1923, 0.984로 나왔다. TREE의 rows=6743은 TRADITIONAL 표의 20232 × 33.33%에 해당한다. 트리의 각 줄 앞의 ->는 반복자 하나이고, 들여쓰기된 줄은 바로 위 반복자의 입력이다. 중첩 루프 조인 반복자의 첫 번째 자식이 바깥 루프, 두 번째 자식이 안쪽 루프다. 문구 형식은 MySQL 8.0 소스(explain_access_path.cc)에서 확인한 것이다.

    -> Nested loop inner join  (cost=8194 rows=6743)
    -> Filter: (o.amount >= 50000)  (cost=987 rows=6743)
        -> Index lookup on o using idx_orders_status_ordered (status='PAID')  (cost=987 rows=20232)
    -> Single-row index lookup on m using PRIMARY (id=o.member_id)  (cost=0.969 rows=1)

    TRADITIONAL 표의 Using where가 TREE에서는 Filter: (o.amount >= 50000)라는 별도의 반복자로 보이고, eq_ref는 "Single-row index lookup", ref는 "Index lookup"으로 표현된다. 커버링 인덱스였다면 "Covering index lookup"처럼 앞에 Covering이 붙는다. 표는 테이블 단위의 요약이고 트리는 실행기의 실제 조립 구조라는 차이를 기억해 두면, 03회에서 TREE 위에 실제 실행 시간과 행 수가 덧붙는 EXPLAIN ANALYZE를 읽기가 쉬워진다.

    이 계획을 개선할 여지가 있는가를 묻는 것까지가 실행 계획 읽기다. 'PAID' 주문이 매우 많고 그중 5만 원 이상이 적다면, amount 조건이 찾아 들어가는 단계에서 쓰이지 못하고 서버에서 버려지는 행이 많다는 뜻이다. 인덱스의 열 구성을 바꾸는 판단에는 실제 행 수와 분포가 필요하고, 그것은 04회의 튜닝 실습에서 이어 간다.

    흔한 오해와 함정

    • "type이 ALL이면 무조건 나쁘다." 테이블의 상당 부분을 읽어야 하거나 테이블이 작다면 풀 스캔이 가장 싼 방법일 수 있다. 문제가 되는 것은 조인의 안쪽 테이블이 ALL이어서 바깥 행마다 전체를 읽는 경우, 그리고 소수의 행만 필요한데 ALL인 경우다.
    • "key에 인덱스가 나오면 빠르다." 같은 값이 수십만 개인 ref는 인덱스를 타면서도 수십만 번의 행 조회를 한다. key는 rows, filtered와 함께 읽어야 한다.
    • "rows는 결과 행 수다." 살펴볼 행 수의 추정이고, 안쪽 테이블에서는 바깥 행 하나당 값이다. 결과 행 수에 가까운 것은 rows × filtered를 단계별로 곱한 값이다.
    • "type: index와 Using index는 같은 말이다." 전자는 인덱스 전체를 훑는다는 접근 범위, 후자는 행을 읽지 않는다는 읽기 대상이다.
    • "Using where가 보이면 인덱스를 못 쓴 것이다." 엔진이 돌려준 행을 서버가 한 번 더 거른다는 뜻일 뿐이다. ref나 range와 함께 나오는 일이 흔하다.
    • "Using filesort는 디스크 정렬이다." 정렬 단계가 따로 있다는 뜻이고, 정렬 버퍼에 들어가면 메모리에서 끝난다.
    • "같은 SQL의 실행 계획은 늘 같다." 통계가 갱신되거나 데이터 분포가 바뀌면 계획도 바뀐다. 개발 환경의 작은 데이터에서 본 계획이 운영 환경의 계획이라는 보장은 없다.
    • "EXPLAIN은 데이터를 전혀 읽지 않는다." 실행 단계로 넘어가지 않을 뿐, const 테이블은 계획 단계에서 실제로 읽는다.

    정리: 실행 계획을 읽는 순서

    실행 계획은 열이 많아 처음에는 어디부터 봐야 할지 막막하다. 이 회차의 내용을 하나의 읽기 순서로 묶으면 다음과 같다. 순서 자체보다 각 단계에서 던지는 질문이 중요하다.

    이 점검표는 이 권의 나머지 회차와 그대로 연결된다. 03회는 이 추정치들을 실제 값과 나란히 놓는 EXPLAIN ANALYZE를, 04회는 풀 스캔 진단과 복합 인덱스 설계를 다룬다. 05회와 06회는 이 회차에서 "트리를 내려간다", "클러스터형 인덱스를 다시 찾아간다"라고만 말한 B+Tree와 InnoDB 인덱스 구조를 바닥부터 설명하고, 07회는 Using filesort를, 08회와 09회는 ICP·커버링·스킵 스캔·인덱스 머지·MRR을, 10회는 rows와 filtered의 근거가 되는 통계와 히스토그램을, 11회와 12회는 조인과 정렬·페이징·그룹핑의 최적화를 다룬다. 실행 계획은 그 모든 주제를 관찰하는 창이다.
    실행 계획
    옵티마이저가 통계로 비용을 추정해 고른 처리 방법이다. 같은 SQL이라도 데이터 분포와 통계가 바뀌면 달라질 수 있어, 짐작하지 말고 EXPLAIN으로 확인해야 한다.
    EXPLAIN의 형식
    TRADITIONAL은 테이블당 한 행의 표, JSON은 비용과 used_key_parts 같은 세부 정보, TREE(8.0.16+)는 실행기 반복자의 구조를 보여 준다. SHOW WARNINGS로 다시 쓴 문장과 인덱스 사용 불가 경고를 볼 수 있다.
    type(접근 유형)
    system·const·eq_ref는 한 행, ref는 같은 값 묶음, range는 인덱스 구간, index는 인덱스 전체, ALL은 테이블 전체를 읽는다. 속도의 순위가 아니라 접근 한 번의 범위를 나타낸다.
    possible_keys와 key
    후보와 실제 선택이다. 후보는 조인 순서와 무관하게 정해지고, 커버링이 가능하면 후보에 없는 인덱스가 key가 될 수도 있다. 왼쪽 열 생략, 열 가공, 타입·콜레이션 변환은 인덱스를 후보에서 빼 버린다.
    key_len
    쓰인 키 부분의 길이 합이다. 데이터 최대 바이트에 NULL 허용이면 1, VARCHAR 등 가변 길이면 2를 더하며, 복합 인덱스의 몇 번째 열까지 찾아 들어가는 데 썼는지 알려 준다.
    ref
    인덱스에 대 본 값이 상수(const), 앞 테이블의 열, 함수 결과(func) 중 무엇인지 보여 준다. range·index·ALL에서는 NULL이다.
    rows와 filtered
    rows는 살펴볼 행 수의 추정(안쪽 테이블은 바깥 행당 값), filtered는 그중 나머지 조건을 통과할 비율의 추정이다. rows × filtered가 다음 테이블로 넘어가는 행 수다.
    Extra
    Using where는 서버 계층 필터, Using index는 커버링, Using index condition은 엔진의 인덱스 조건 검사, Using filesort와 Using temporary는 정렬·임시 테이블이라는 별도 단계를 뜻한다.

    실무에서 실행 계획이 가장 자주 쓰이는 순간은 "어제까지 빠르던 쿼리가 오늘 느려졌다"는 장애다. SQL도 코드도 바뀌지 않았는데 느려졌다면, 데이터가 늘었거나 분포가 바뀌었거나 통계가 갱신되어 옵티마이저가 다른 계획을 고른 경우가 많다. 이때 할 일은 지금의 계획을 EXPLAIN으로 확인하고, 운영 중인 연결이라면 EXPLAIN FOR CONNECTION으로 실제로 쓰이는 계획을 보는 것이다. type이 ref에서 ALL로 바뀌었는지, key가 다른 인덱스로 바뀌었는지, 안쪽 테이블의 rows가 커졌는지를 비교하면 원인의 방향이 잡힌다. 개발 환경의 수천 행짜리 데이터로 본 계획을 운영 환경의 계획으로 믿으면 안 되는 이유도 같다.

    JPA나 Querydsl을 쓰는 애플리케이션에서는 실행 계획을 볼 SQL이 코드에 직접 보이지 않는다. 로그로 실제 SQL과 바인딩 값을 확인한 뒤 그 SQL을 EXPLAIN 해야 한다. 특히 타입 변환 함정은 매핑에서 자주 생긴다. 열은 VARCHAR인데 엔티티 필드를 숫자 타입으로 매핑하면, 문자열 열과 숫자 파라미터를 비교하는 SQL이 되어 인덱스가 후보에서 빠진다. 조인하는 두 테이블의 문자 집합이나 콜레이션이 다른 경우도 같다. 이런 문제는 SQL 문장만 눈으로 읽어서는 보이지 않고, EXPLAIN 뒤의 SHOW WARNINGS에서 드러난다.

    판단이 달라지는 지점도 분명히 하자. 수십 행짜리 코드 테이블의 ALL은 고칠 대상이 아니고, 배치 작업이 테이블 대부분을 읽는 쿼리의 ALL도 정상일 수 있다. 반대로 화면 하나가 20건을 보여 주는데 계획에 수십만 rows가 찍혀 있다면, 결과가 맞더라도 데이터가 늘수록 느려질 쿼리다. 그리고 rows와 filtered는 어디까지나 추정이므로, 중요한 판단을 내리기 전에는 03회의 EXPLAIN ANALYZE로 실제 값과 맞춰 보는 단계를 거쳐야 한다.
  • 테이블 t (a INT NULL, b VARCHAR(10) NOT NULL, c DATETIME(3) NOT NULL), 문자 집합 utf8mb4에 인덱스 idx_abc (a, b, c)가 있다. 서로 다른 세 쿼리의 EXPLAIN에서 이 인덱스의 key_len이 5, 47, 54로 나왔다. 각각 몇 번째 열까지 쓰였는지 계산 과정과 함께 답하라.
  • 실습 스키마에서 다음 쿼리의 type을 예측하고 이유를 말하라. 옵티마이저가 인덱스를 쓸 수 있다면 쓴다고 가정한다. (가) SELECT * FROM member WHERE email = 'kim@example.com' (나) SELECT * FROM orders WHERE member_id IN (1, 2, 3) (다) SELECT * FROM orders WHERE ordered_at >= '2025-01-01' (라) SELECT id FROM orders WHERE member_id = 7의 type과 Extra (마) SELECT * FROM member WHERE phone = 1012345678
  • orders의 amount와 memo에 인덱스도 히스토그램도 없다. SELECT * FROM orders WHERE amount BETWEEN 10000 AND 20000 AND memo LIKE '선물%'의 EXPLAIN에서 filtered는 얼마로 나오겠는가? 실제로 두 조건을 모두 만족하는 행이 테이블의 20%라면, 이 추정은 조인에서 어떤 문제를 일으킬 수 있는가?
  • 두 테이블 A, B의 조인에 대해 두 계획이 있다. 계획 1: A가 드라이빙(rows 50,000, filtered 2.00), B는 eq_ref(rows 1). 계획 2: B가 드라이빙(rows 3,000, filtered 100.00), A는 ref(rows 40, filtered 2.00). 각 계획에서 안쪽 테이블에 대한 인덱스 조회 횟수와 안쪽 테이블에서 살펴보는 행 수를 계산하라.
  • 어떤 쿼리의 EXPLAIN에서 possible_keys에 idx_orders_member가 있는데 key는 NULL, type은 ALL이다. 이런 계획이 나오는 이유를 두 가지 이상 들고, 각각을 어떻게 확인할지 말하라.
    •

    1번. 열마다 길이를 구한다. a는 INT 4바이트에 NULL 허용 1을 더해 5. b는 10글자 × 4바이트 = 40에 가변 길이 2를 더해 42(NOT NULL이라 1은 없다). c는 DATETIME 5바이트에 소수 초 3자리의 2바이트를 더해 7. 따라서 5는 a만, 5 + 42 = 47은 a, b까지, 47 + 7 = 54는 세 열 모두 쓰인 것이다. 47이 나온 쿼리는 a와 b가 동등 비교이고 c에 조건이 없거나, b가 b > 'x' 같은 구간 조건이어서 그 뒤의 c를 구간에 붙이지 못한 경우일 수 있다. MySQL 8.0.46·8.4.13에서 실행해 보면 이 세 값이 그대로 나오지만, a = 1 AND b >= 'x' AND c >= '2025-01-01'처럼 b의 하한이 닫혀 있으면 c가 구간의 시작점에 붙어 54가 나온다. 본문 (4)와 같은 경우다.

    2번. (가) uk_member_email의 모든 열을 상수와 비교하므로 const, key_len 402. 다만 그런 이메일의 행이 없으면 const 테이블을 미리 읽은 결과로 Extra에 no matching row in const table만 나온다. (나) 값이 여러 개인 IN은 점 구간 여러 개이므로 range, key_len 8, ref NULL. (다) ordered_at은 idx_orders_status_ordered의 둘째 열이라 왼쪽 열 status를 건너뛰었고, SELECT *라서 인덱스만으로 끝낼 수도 없으므로 ALL. 이 인덱스는 연속 구간을 만들 수 없다. (라) ref이고, 세컨더리 인덱스 항목에 기본 키 id가 들어 있으므로 행을 읽지 않고 끝나 Extra에 Using index. (마) 문자열 열 phone을 숫자와 비교하므로 인덱스로 찾아 들어갈 수 없어 ALL이고, SHOW WARNINGS에 type or collation conversion 경고가 남는다. 따옴표로 감싸 문자열로 비교해야 한다.

    3번. 인덱스도 히스토그램도 없으므로 기본값을 쓴다. BETWEEN은 0.1111, LIKE도 BETWEEN과 같은 0.1111이고 AND는 곱하므로 0.1111 × 0.1111 ≈ 0.0123, 즉 filtered는 1.23으로 나온다. 실제 비율 20%와 비교하면 약 16배 작게 추정한 것이다. 이 테이블이 드라이빙이라면 옵티마이저는 다음 테이블로 넘어가는 행을 실제의 약 16분의 1로 보고, 안쪽 테이블을 풀 스캔이나 비싼 접근으로 읽어도 반복 횟수가 적다고 판단해 그런 조인 순서나 접근 방법을 고를 수 있다. 실행해 보면 안쪽 접근이 예상의 16배 반복된다. 히스토그램으로 실제 분포를 알려 주는 것이 해결 방향이다.

    4번. 계획 1: A에서 50,000행을 살펴보고 2%인 1,000행이 B로 넘어간다. B의 기본 키 조회 1,000번, B에서 살펴보는 행 1,000 × 1 = 1,000행. 계획 2: B에서 3,000행을 살펴보고 모두 A로 넘어간다. A의 인덱스 조회 3,000번, A에서 살펴보는 행 3,000 × 40 = 120,000행. 드라이빙 테이블에서 살펴보는 행까지 더하면 계획 1은 약 51,000행, 계획 2는 약 123,000행을 살펴본다. 행 수만 보면 계획 1이 유리하지만, 실제 비용은 각 접근이 순차인지 랜덤인지와 페이지가 버퍼 풀에 있는지에 따라 달라지므로, 옵티마이저는 행 수가 아니라 비용 모델로 비교한다.

    5번. 첫째, 조건에 맞는 행이 많다고 추정한 경우다. 그 인덱스로 찾으면 행마다 클러스터형 인덱스를 다시 찾아가야 하므로 풀 스캔보다 비싸다고 판단했다. 같은 조건으로 실제 행 수를 세어 보거나 03회의 EXPLAIN ANALYZE로 추정과 실제를 비교해 확인한다. 둘째, 후보가 조인 순서와 무관하게 정해지기 때문이다. idx_orders_member는 회원을 먼저 읽을 때만 쓸 수 있는데 주문이 드라이빙이 된 계획이라면 쓰일 수 없다. 행 순서를 보고 이 테이블이 몇 번째로 읽히는지 확인한다. 셋째, 통계가 실제와 크게 다를 수 있다. ANALYZE TABLE로 통계를 갱신한 뒤 계획이 달라지는지 본다.

     인덱스 idx_orders_status_ordered (status VARCHAR(20) NOT NULL, ordered_at DATETIME NOT NULL), 문자 집합 utf8mb4. EXPLAIN에서 key가 이 인덱스이고 key_len이 82다. 옳은 해석은? 두 열 모두 찾아 들어가는 데 쓰였다. status 열까지만 찾아 들어가는 데 쓰였고, ordered_at에 조건이 있었다면 구간을 좁히는 데는 쓰이지 않았다. ordered_at 열만 쓰였다. 이 인덱스의 항목 하나가 디스크에서 82바이트를 차지한다. status는 20 × 4 + 2 = 82, ordered_at은 5바이트이므로 82는 status까지, 87이어야 두 열이다. key_len은 첫 열부터의 누적 길이라서 둘째 열만 쓰인 값은 나올 수 없고, 디스크 크기가 아니라 서버의 키 버퍼 형식 길이다. EXPLAIN에서 type이 index이고 Extra에 Using index가 있다. 이 접근이 실제로 하는 일은? 인덱스로 필요한 행 하나를 정확히 찾아 들어간다. 인덱스의 일부 구간만 읽고 나머지는 건너뛴다. 인덱스 전체를 처음부터 끝까지 훑되, 필요한 열이 모두 인덱스에 있어 테이블 행은 읽지 않는다. 테이블 전체를 훑은 뒤 인덱스로 정렬한다. type: index는 인덱스 전체를 읽는다는 접근 범위이고, Using index는 행을 읽지 않고 인덱스만으로 끝낸다는 뜻이다. 한 행을 찾아 들어가는 것은 const·eq_ref, 구간만 읽는 것은 range다. 조인의 첫 테이블이 rows 1000, filtered 20.00이고 두 번째 테이블이 eq_ref, rows 1이다. 두 번째 테이블에 대한 기본 키 조회는 대략 몇 번 일어날 것으로 예상되는가? 약 200번 1번 약 1000번 약 20번 다음 테이블로 넘어가는 행은 rows × filtered = 1000 × 20% = 200이고, eq_ref의 rows 1은 넘어온 행 하나당 1행이므로 조회는 약 200번이다. 안쪽 테이블의 rows는 쿼리 전체가 아니라 바깥 행당 값이다. 행이 하나뿐인 일반 InnoDB 테이블을 기본 키 상수 조건 없이 조회해도 EXPLAIN의 type에 system이 보통 나오지 않는 이유는? system은 MySQL 8.0에서 제거된 유형이기 때문이다. InnoDB는 행이 하나인 테이블도 항상 풀 스캔하도록 정해져 있기 때문이다. system은 기본 키가 없는 테이블에만 쓰이기 때문이다. InnoDB는 MVCC 때문에 트랜잭션마다 보이는 행 수가 달라 정확한 행 수를 따로 세어 두지 않고, 옵티마이저는 행 수가 정확하다고 알리는 엔진에서만 그 테이블을 상수 테이블로 뽑기 때문이다. 8.0 소스의 상수 테이블 추출은 엔진이 HA_STATS_RECORDS_IS_EXACT를 내세우는지를 조건으로 건다. InnoDB는 매뉴얼이 밝힌 대로 동시 트랜잭션이 서로 다른 행 수를 볼 수 있어 행 수를 세어 두지 않고, 일반 테이블에는 이 플래그를 켜지 않는다(임시 테이블에는 켠다). system은 8.0에도 있는 유형이다. phone VARCHAR(20) 열에 인덱스가 있는데 WHERE phone = 01012345678로 조회하면 인덱스로 찾아 들어가지 못한다. 가장 정확한 이유는? 숫자 상수는 인덱스에 대 볼 수 없도록 문법에서 막혀 있기 때문이다. 문자열과 숫자의 비교는 숫자로 바꿔 이루어지는데, 같은 숫자로 바뀌는 문자열이 여럿('1', ' 1', '1a' 등)이라 문자열 순서로 정렬된 인덱스에서 하나의 구간을 정할 수 없기 때문이다. 앞자리 0이 사라져 값이 달라졌으므로 결과가 항상 비기 때문이다. VARCHAR 열의 인덱스는 동등 비교를 지원하지 않기 때문이다. 매뉴얼의 타입 변환 절이 든 이유다. 비교 기준(숫자 크기)과 인덱스 정렬 기준(문자열 순서)이 달라 구간을 만들 수 없다. 결과가 비는 것과 인덱스 사용 가능 여부는 별개 문제이고, VARCHAR 인덱스는 문자열 상수와의 동등 비교를 지원한다.
    실행 계획(query execution plan)
    옵티마이저가 고른 문장 처리 방법. 테이블별 접근 방법, 조인 순서, 정렬·임시 테이블 같은 추가 단계로 이루어진다.
    옵티마이저(optimizer)
    통계를 바탕으로 가능한 처리 방법들의 비용을 추정하고 가장 싸 보이는 계획을 고르는 MySQL 서버 계층의 부품.
    접근 유형(access type)
    EXPLAIN의 type 열이 보여 주는 테이블 접근 방식. const, eq_ref, ref, range, index, ALL 등이 있다.
    드라이빙 테이블(driving table)
    중첩 루프 조인에서 바깥 루프로 먼저 읽히는 테이블. EXPLAIN에서 같은 id의 첫 행이다.
    커버링 인덱스(covering index)
    쿼리에 필요한 열을 모두 담고 있어 테이블 행을 읽지 않고 답할 수 있는 인덱스. Extra에 Using index로 나타난다.
    최좌측 접두사(leftmost prefix)
    복합 인덱스는 왼쪽 열부터 연속된 열에 대한 조건으로만 찾아 들어갈 수 있다는 규칙.
    인덱스 다이브(index dive)
    구간의 양 끝으로 실제 인덱스를 내려가 그 사이의 행 수를 추정하는 방법.
    조건 필터링(condition filtering)
    접근 방법에 쓰이지 않은 조건이 행을 얼마나 걸러 낼지 추정해 filtered에 반영하는 옵티마이저 기능.
    const 테이블(const table)
    많아야 한 행만 나오는 것이 확정되어 계획 단계에서 미리 읽고, 그 값을 상수로 쓰는 테이블.
