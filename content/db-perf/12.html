    이 회차의 질문: 스무 줄짜리 화면은 몇 행을 만지는가

    관리자 화면 두 개를 떠올려 보자. 하나는 결제 완료 주문을 최신순으로 20건씩 보여 주고 아래에 페이지 번호를 늘어놓는 주문 목록이다. 다른 하나는 회원별로 올해 주문 건수와 금액을 회원 번호순으로 20명씩 보여 주는 통계 화면이다. 두 화면 모두 클라이언트가 받는 것은 스무 줄이다. 그런데 데이터베이스가 그 스무 줄을 만들려고 하는 일은 쿼리 모양과 인덱스에 따라 수십 행에서 수십만 행까지 벌어진다. 04회에서 세운 질문, 곧 "결과 한 줄을 만들려고 몇 개의 행과 페이지를 만졌는가"를 이 회차에서는 정렬, 페이징, 그룹핑이라는 세 연산에 던진다.

    세 연산에는 공통점이 있다. 셋 다 순서에 기대는 연산이다. 정렬은 순서를 만드는 일이고, 페이징은 순서 위의 위치를 찾는 일이며, 그룹핑은 같은 값끼리 이웃하게 모으는 일이다. 데이터를 이미 원하는 순서로 읽을 수 있으면 세 연산은 모두 B+Tree를 한 번 내려간 뒤 리프를 옆으로 읽는 일로 끝나고, 필요한 만큼 읽었을 때 멈출 수 있다. 원하는 순서로 읽을 수 없으면 입력을 끝까지 받아 정렬하거나, 임시 테이블에 모으거나, 앞부분을 읽고 버려야 한다. 03회에서 본 말로 하면 앞의 것은 행을 받는 대로 위로 흘려보내는 파이프라인(pipelined) 연산이고, 뒤의 것은 입력을 다 받아야 첫 행을 내놓는 차단(blocking) 연산이다. 이 회차의 처방은 대부분 차단 연산을 파이프라인 연산으로 바꾸는 일이다.

    filesort: 메모리 안의 정렬과 디스크로 넘친 정렬

    07회에서 filesort의 큰 흐름과 정렬 버퍼에 담기는 튜플의 모양(sort_mode)을, 03회에서 LIMIT이 있을 때의 우선순위 큐를 보았다. 여기서는 그 회차들이 미뤄 둔 질문, 곧 정렬할 데이터가 정렬 버퍼에 다 들어가지 않으면 무슨 일이 일어나는가를 소스 코드 수준에서 따라간다. 아래 설명은 MySQL 8.0과 8.4의 sql/filesort.cc, sql/merge_many_buff.h, sql/sql_sort.h를 읽고 정리한 것이며, 두 버전에서 이 부분의 코드는 같다.

    정렬 버퍼 하나에 다 들어갈 때

    filesort가 쓰는 메모리의 상한은 sort_buffer_size이고 기본값은 262,144바이트(256KB)다. 매뉴얼은 MySQL 8.0.12부터 옵티마이저가 이 크기를 처음부터 한꺼번에 잡지 않고 필요한 만큼 조금씩 늘려 가며 상한까지 할당한다고 설명한다. 8.0.12 이전에는 정렬할 때마다 sort_buffer_size 바이트를 미리 잡았다. 그래서 8.0.12 이후에는 이 값을 키워도 작은 정렬이 메모리를 낭비하지 않는다. filesort.cc 머리 주석은 전체 알고리즘을 이렇게 요약한다. 버퍼에 더 들어갈 자리가 없을 때까지 행을 읽고, 그 내용을 STL의 정렬 알고리즘으로 정렬해 디스크에 쓰며(그래서 이름이 filesort다), 행이 더 없으면 청크들을 재귀적으로 병합한다. 같은 주석은 모든 행이 청크 하나에 들어가면 데이터가 디스크에 닿지 않고 RAM에 남는다고 덧붙인다.

    메모리 안에서 끝나는 경우는 단순하다. read_all_rows()가 자식 이터레이터에서 행을 끝까지 받아 행마다 정렬 키를 만들어 버퍼에 넣는다. 입력이 끝났을 때 디스크로 내보낸 청크가 하나도 없으면 버퍼 안에서 한 번 정렬하고 그 결과를 그대로 위로 돌려준다. 옵티마이저 트레이스의 filesort_summary에는 이때 쓴 정렬 알고리즘이 sort_algorithm(std::sort 또는 std::stable_sort)으로, 정렬 중 한순간에 가장 많이 쓴 메모리가 peak_memory_used로 남는다. 매뉴얼은 peak_memory_used가 sort_buffer_size까지 올라갈 수 있지만 반드시 그만큼 되는 것은 아니라고 설명한다.

    버퍼가 넘칠 때: 청크와 병합

    입력이 버퍼보다 크면 이야기가 달라진다. read_all_rows()는 새 행의 정렬 키를 버퍼에 넣지 못하면 소스 주석 그대로 "자리가 없으니 청크를 디스크로 내보낸다". 지금까지 버퍼에 쌓인 레코드를 정렬해 임시 파일에 이어 쓰고, 그 덩어리가 파일의 어디서 시작하고 몇 행인지 적은 청크 기술자(Merge_chunk)를 별도의 청크 파일에 기록한 뒤 버퍼를 비운다. sql_sort.h는 병합 청크를 "임시 파일에 쓰인, 미리 정렬된 레코드의 연속"이라고 정의한다. 입력이 끝나면 마지막으로 버퍼에 남은 레코드도 청크 하나로 내보낸다. 이렇게 해서 임시 파일에는 각각 안에서만 정렬된 청크 k개가 남는다. 임시 파일은 tmpdir 시스템 변수가 가리키는 디렉터리에 만들어진다.

    이제 k개의 정렬된 줄을 하나의 정렬된 줄로 합쳐야 한다. 이것이 외부 병합 정렬(external merge sort)의 병합 단계다. MySQL은 청크를 한 번에 다 합치지 않는다. sql_sort.h에는 MERGEBUFF = 7과 MERGEBUFF2 = 15라는 두 상수가 있고, merge_many_buff()는 청크 수가 15보다 많은 동안 다음 일을 되풀이한다. 원래 임시 파일에서 청크를 일곱 개씩 묶어 병합한 결과를 두 번째 임시 파일에 새 청크로 쓰고, 한 바퀴가 끝나면 두 파일의 역할을 바꾼다. 청크가 15개 이하가 되면 루프를 빠져나오고, 마지막으로 merge_index()가 남은 청크 전부를 한 번에 병합해 출력 파일을 만든다. 머리 주석의 표현으로는 "일곱 개씩 재귀적으로 병합하되, 그렇게 해서 한 바퀴를 덜 돌 수 있다면 마지막 바퀴에서는 15개까지 한꺼번에 병합한다".

    루프 안쪽을 조금 더 정확히 보자. 한 바퀴에서 묶음을 만드는 반복문은 for (i = 0; i < num_chunks - MERGEBUFF * 3U / 2U; i += MERGEBUFF)다. MERGEBUFF * 3 / 2는 정수 나눗셈으로 10이므로, 남은 청크가 10개를 넘는 동안 일곱 개씩 병합하고, 그 뒤에 남은 청크는 크기와 상관없이 한 묶음으로 병합한다. 마지막 묶음이 너무 작아지지 않게 하려는 장치다. 청크가 40개인 경우를 손으로 돌려 보자.

Sort_merge_passes 증가량 = 7

    상태 변수 Sort_merge_passes가 무엇을 세는지도 소스로 정확히 알 수 있다. 증가시키는 코드 thd->inc_status_sort_merge_passes()는 merge_buffers() 함수의 첫머리에 있다. 이 함수는 청크 묶음 하나를 병합할 때마다 한 번 불리므로, 이 값은 "데이터 전체를 몇 바퀴 돌았는가"가 아니라 "병합 작업을 몇 번 했는가"다. 위의 40청크 정렬은 데이터 전체로 보면 두 바퀴(중간 병합 한 바퀴, 마지막 병합 한 바퀴)지만 Sort_merge_passes는 7 늘어난다. 청크가 15개 이하라면 중간 병합 없이 마지막 병합 한 번으로 끝나 1만 늘어난다. 그러니 이 값이 0이 아니라는 것은 정렬 버퍼가 넘쳐 디스크 병합이 일어났다는 확실한 신호이고, 값의 크기는 청크 수에 따라 커진다.

    디스크 입출력으로 환산해 보면 비용이 분명해진다. 40청크 정렬에서 모든 레코드는 처음 청크로 내보낼 때 한 번, 중간 병합 결과로 한 번, 마지막 병합 결과로 한 번, 모두 세 번 디스크에 쓰이고, 병합할 때마다 다시 읽힌다. 병합은 여러 청크의 앞부분을 동시에 메모리에 올려 두고 가장 작은 레코드를 하나씩 꺼내는 방식이므로, 병합에 쓰는 버퍼를 묶음 안의 청크들이 나눠 쓴다. 매뉴얼이 sort_buffer_size는 적어도 정렬 버퍼에 튜플 15개가 들어갈 만큼은 되어야 한다고 적은 것과, 마지막 병합의 최대 청크 수 MERGEBUFF2가 15인 것은 같은 숫자다. 15개 청크를 한 번에 병합하려면 각 청크에서 적어도 한 레코드씩은 동시에 메모리에 있어야 하기 때문이다.

    입력 행이 정렬 버퍼를 채울 때마다 정렬된 청크가 임시 파일로 나가고, 청크가 15개를 넘으면 일곱 개씩 묶어 두 번째 파일로 병합하며, 마지막에 남은 청크를 한 번에 병합해 출력 파일을 만드는 세 단계를 보여 준다. 왼쪽에서 오른쪽으로 진행하는 3단 흐름도. 1단: 위에서 내려오는 행 아이콘 줄이 "정렬 버퍼"라는 라벨의 직사각형 상자로 들어가고, 상자에서 오른쪽으로 짧은 막대 40개가 쌓이며 그 묶음에 라벨 "청크 40개 (임시 파일 1)". 2단: 40개 막대가 일곱 개씩 묶인 다섯 묶음과 다섯 개짜리 한 묶음으로 나뉘고, 각 묶음에서 화살표가 모여 더 긴 막대 하나가 되어 총 6개의 긴 막대가 생긴다. 이 단계 위에 라벨 "중간 병합: 7개씩 (임시 파일 2)". 3단: 긴 막대 6개가 하나의 아주 긴 막대로 합쳐지고 라벨 "마지막 병합 (15개 이하)" 와 "출력 파일". 화면 아래쪽에 계수기 모양의 상자 "Sort_merge_passes +7". 평면 다이어그램, 흰 배경, 막대는 파랑 계열. 버퍼가 넘칠 때마다 정렬된 청크가 임시 파일로 나간다. 청크가 15개를 넘는 동안 일곱 개씩 병합하고, 마지막에 남은 청크를 한 번에 병합한다. Sort_merge_passes는 병합 작업 한 번마다 1씩 늘어난다.

    EXPLAIN은 정렬이 메모리에서 끝났는지 디스크를 썼는지 알려 주지 않는다. 매뉴얼도 EXPLAIN이 메모리 안의 filesort 여부를 구별하지 않는다고 명시한다. 확인하는 길은 두 가지다. 첫째, 옵티마이저 트레이스의 filesort_summary다. 8.0과 8.4 소스가 실제로 기록하는 항목에는 디스크로 내보낸 초기 청크 수 num_initial_chunks_spilled_to_disk, 정렬한 행 수 num_rows_found, 레코드 하나의 크기 row_size, 버퍼에 담을 수 있는 최대 행 수 max_rows_per_buffer, peak_memory_used가 있다(매뉴얼의 예시는 number_of_tmp_files 같은 다른 이름을 보여 주므로 실제 출력의 이름을 기준으로 읽는다). 초기 청크 수가 0이면 디스크에 닿지 않았다. 둘째, 쿼리 전후의 SHOW SESSION STATUS LIKE 'Sort_merge_passes' 차이다.

    SHOW SESSION STATUS LIKE 'Sort%';          -- 실행 전 값
SELECT member_id, amount, ordered_at
FROM orders
ORDER BY amount DESC, order_id;            -- 인덱스가 없는 열로 100만 행 정렬
SHOW SESSION STATUS LIKE 'Sort%';          -- Sort_merge_passes, Sort_rows의 증가분을 본다

    실습 데이터로 실제로 돌려 보자. 아래는 MySQL 8.4.13에서 sort_buffer_size 기본값(262,144)으로 위 쿼리를 실행한 뒤의 세션 상태 변수(실행 전에는 모두 0)와, 옵티마이저 트레이스를 켜고 같은 쿼리를 돌려 얻은 filesort_summary다. MySQL 8.0.46에서도 num_rows_estimate(994,566) 하나만 다르고 나머지 값은 모두 같았다. 추정 행 수는 실행 환경과 통계에 따라 달라진다.

    레코드 하나가 41바이트인 100만 행이 256KB 버퍼를 넘쳐 초기 청크 209개로 디스크에 나갔다. 이 209개에 앞의 반복 규칙을 그대로 적용하면, 1바퀴는 i가 199보다 작은 동안 일곱 개씩 29번 병합하고 남은 6개를 한 번 더 병합해 30번(청크 30개), 2바퀴는 i가 20보다 작은 동안 3번 병합하고 남은 9개를 한 번 병합해 4번(청크 4개), 마지막 병합 1번으로 모두 35번이다. 실제 Sort_merge_passes 35와 정확히 맞는다. 하나 덧붙이면, 이 실행에서 peak_memory_used는 285,288로 sort_buffer_size보다 조금 컸다. 디스크 병합이 일어나는 정렬에서는 이 값이 버퍼 크기를 넘을 수 있다는 뜻이다.

    병합이 보이면 가장 먼저 떠오르는 처방은 sort_buffer_size를 키우는 것이다. 매뉴얼은 이상적으로는 결과 전체가 정렬 버퍼에 들어갈 만큼 키워 디스크 쓰기와 병합 패스를 피하라고 하면서도, 같은 변수 설명에서 몇 가지 단서를 단다. 정렬이 필요한 세션마다 이 크기의 버퍼를 할당하고, 전역으로 필요 이상 크게 잡으면 정렬하는 쿼리 대부분이 오히려 느려지며, 필요한 세션에서만 세션 값으로 늘리는 것이 가장 좋다. 또 리눅스에서는 256KB와 2MB에 메모리 할당이 크게 느려질 수 있는 경계가 있으니 둘 중 하나의 아래에 머무는 것을 고려하라고 적는다. 동시에 정렬하는 세션이 수백 개라면 세션당 버퍼가 곱해진다는 점도 함께 따져야 한다. 문장 하나에만 값을 주고 싶다면 매뉴얼의 예처럼 SELECT /*+ SET_VAR(sort_buffer_size = 16M) */ ... 힌트를 쓴다. SET_VAR는 시스템 변수의 세션 값을 문장 하나가 실행되는 동안만 바꾼다.

    버퍼 말고도 손잡이가 있다. 매뉴얼은 정렬 버퍼에 들어가는 열 값의 크기가 max_sort_length의 영향을 받으므로 이 값을 키우면 튜플이 커진다고 경고하고, tmpdir을 여유 공간이 큰 전용 파일 시스템으로 옮기거나 콜론(윈도우는 세미콜론)으로 구분한 여러 경로를 주어 차례로 돌려 쓰게 할 수 있다고 안내한다. 이때 경로들은 같은 디스크의 다른 파티션이 아니라 서로 다른 물리 디스크에 있어야 한다. 그러나 이 모든 손잡이는 정렬할 양이 정해진 뒤의 이야기다. 정렬 튜플을 작게 하는 것(필요한 열만 SELECT 하기), 정렬 전에 행을 줄이는 것(조건을 인덱스로 먼저 걸기), 그리고 무엇보다 정렬 자체를 없애는 것이 버퍼 튜닝보다 앞선다. 다음 절이 그 마지막 길이다.

    인덱스를 활용한 정렬 최적화: 순서를 공짜로 얻는 조건과 값

    07회에서 정리했듯이 B+Tree의 리프는 키 순서로 연결되어 있으므로, 쿼리가 원하는 순서가 인덱스의 순서와 같으면 정렬 단계 자체가 사라진다. 등치 조건으로 고정된 앞쪽 열 뒤에 ORDER BY 열이 이어지면 되고, 모든 열이 같은 방향이면 인덱스를 거꾸로 읽어 DESC도 처리한다. 인덱스가 정렬을 대신하지 못하는 경우(다른 인덱스의 열, 식으로 감싼 열, 정렬 열 앞의 IN·범위 조건, 조인의 첫 테이블이 아닌 열, ORDER BY와 다른 GROUP BY 등)의 목록도 07회에 표로 모아 두었다. 여기서는 그 규칙이 이 회차의 페이징과 그룹핑에서 어떤 값을 갖는지, 그리고 그 순서가 언제 공짜가 아닌지를 본다.

    주문 목록 첫 페이지를 보자.

    SELECT order_id, member_id, amount, ordered_at
FROM orders
WHERE status = 'PAID'
ORDER BY ordered_at DESC, order_id DESC
LIMIT 20;

    status = 'PAID'가 인덱스의 첫 열을 고정하고, 그 구간 안에서 항목은 (ordered_at, order_id) 순서로 놓여 있다. 두 정렬 열이 모두 DESC이므로 PAID 구간의 오른쪽 끝에서 왼쪽으로 읽으면 원하는 순서가 그대로 나온다. 07회에서 본 것처럼 동률 처리를 위해 덧붙인 order_id도 인덱스 확장 덕분에 이미 순서 안에 들어 있다. 실행은 B+Tree를 한 번 내려가 PAID 구간의 마지막 항목을 찾고, 거기서부터 20개의 항목을 읽어 항목마다 기본 키로 클러스터형 인덱스를 찾아가 행을 만든 뒤 멈춘다. 읽는 인덱스 항목은 20개, 클러스터형 인덱스 룩업도 20번이다. 정렬이 없으니 LIMIT이 아래쪽 읽기를 직접 멈춘다.

    이 순서가 공짜가 아닌 경우가 있다. 매뉴얼의 ORDER BY 최적화 절은 인덱스가 쿼리가 접근하는 모든 열을 담고 있지 않으면 인덱스 접근이 다른 방법보다 쌀 때만 그 인덱스를 쓴다고 말한다. 같은 쿼리에서 LIMIT을 빼고 PAID 7만 건을 모두 최신순으로 달라고 하면, 인덱스 순서로 읽는 계획은 7만 번의 룩업을 치른다. PAID 주문은 주문 번호 100개마다 7개씩 흩어져 있으므로 이 룩업들은 클러스터형 인덱스의 거의 모든 리프 페이지를 하나씩 건드린다. 반대로 테이블을 처음부터 끝까지 순차로 읽고 7만 행을 정렬하는 계획은 룩업이 없다. 둘 중 어느 쪽이 싼지는 옵티마이저의 비용 계산(10회)이 정한다. 순서를 주는 인덱스가 확실히 이기는 것은 LIMIT으로 일찍 멈출 수 있을 때, 또는 인덱스가 필요한 열을 모두 담아 룩업이 없을 때(커버링 인덱스, 08회)다. 매뉴얼의 LIMIT 최적화 절은 ORDER BY나 GROUP BY와 LIMIT이 함께 있으면 옵티마이저가 기본적으로 순서를 주는 인덱스를 고르려 하며, 8.0.21부터는 optimizer_switch의 prefer_ordering_index 플래그로 이 동작을 끌 수 있다고 설명한다.

    이 절에서 기억할 것은 하나다. 인덱스 순서로 읽는다는 것은 "몇 번째 행인가"와 "그 다음 행은 무엇인가"를 B+Tree가 이미 알고 있다는 뜻이다. 정렬을 없애는 것은 그 성질의 첫 번째 쓰임일 뿐이다. 남은 절들에서 이 성질을 세 번 더 쓴다. 지연 조인은 순서를 따라 위치를 찾는 일을 가벼운 인덱스에서만 하게 만들고, 키셋 페이징은 위치를 숫자 대신 키 값으로 가리켜 B+Tree 탐색 한 번으로 그 위치에 도착하며, 스트리밍 집계는 같은 그룹이 이웃해 있다는 사실로 임시 테이블을 없앤다.

    OFFSET 페이징의 함정

    첫 페이지는 싸다. 문제는 깊은 페이지다. 1,000번째 페이지는 이렇게 가져온다.

    SELECT order_id, member_id, amount, ordered_at
FROM orders
WHERE status = 'PAID'
ORDER BY ordered_at DESC, order_id DESC
LIMIT 20 OFFSET 19980;                    -- (1000 - 1) × 20

    03회에서 LimitOffsetIterator의 소스로 확인했듯이, OFFSET은 앞의 행을 건너뛰는 특별한 접근 방법이 아니다. 첫 Read()에서 자식 이터레이터의 Read()를 OFFSET 횟수만큼 불러 그 행들을 버리고, 그다음 행부터 위로 올린다. 자식은 버려질 행인지 알지 못하므로 버릴 행도 똑같이 만든다. 이 쿼리의 자식은 idx_orders_status_ordered를 거꾸로 읽는 인덱스 접근이고, SELECT 목록에 member_id와 amount가 있어 인덱스만으로는 행을 만들 수 없으므로 항목마다 클러스터형 인덱스 룩업을 한다. 결국 20행을 돌려주려고 인덱스 항목 20,000개를 읽고 룩업을 20,000번 한다. 그중 19,980번은 버리기 위한 룩업이다. MySQL 8.4.13에서 이 쿼리를 EXPLAIN ANALYZE로 보면 Limit/Offset: 20/19980 row(s) 아래의 Index lookup on orders using idx_orders_status_ordered (status='PAID') (reverse) 노드가 실제로 rows=20000을 돌려준다.

    룩업 20,000번이 건드리는 페이지 수도 따져 보자. 02회와 04회의 가정대로 클러스터형 인덱스 리프 한 페이지에 행이 100개쯤 들어 있다면, 주문 번호 100개 구간마다 PAID가 7개이므로 최신 PAID 20,000건은 주문 번호로 약 285,700개(20,000 ÷ 7 × 100) 구간에 퍼져 있고, 리프 페이지로는 약 2,860개다. 1,000번째 페이지 하나를 보여 주려고 데이터 페이지 2,860개 남짓을 버퍼 풀로 끌어올려야 한다는 뜻이다. 버퍼 풀에 없다면 그만큼의 디스크 읽기가 생기고, 이 페이지들이 버퍼 풀의 자리를 차지하면서 다른 쿼리가 쓰던 페이지를 밀어낸다.

    비용이 페이지 번호에 비례한다는 것은 "처음부터 끝까지 넘겨 보는" 작업에서 더 극적으로 드러난다. 배치 작업이 OFFSET으로 PAID 주문 7만 건을 20건씩 전부 읽는다면 페이지 p에서 20p개의 항목을 읽으므로, 전체로는 20 × (1 + 2 + … + 3,500) = 20 × 3,500 × 3,501 ÷ 2 = 122,535,000개의 항목을 읽는다. 7만 건을 내보내려고 1억 2천만 번을 읽는, 데이터 양의 제곱에 비례하는 작업이다. 정렬을 인덱스로 하지 못하는 쿼리라면 사정이 더 나쁘다. 03회에서 본 대로 filesort는 OFFSET과 LIMIT을 더한 개수를 남겨야 하므로, 깊은 페이지일수록 우선순위 큐에 담을 행이 늘어나고 결국 우선순위 큐를 쓸 수 없는 크기가 된다.

    비용만이 아니라 정확성의 문제

    OFFSET 페이징에는 비용과 별개로 결과가 어긋나는 문제가 있다. 자동 커밋 상태에서 페이지 요청은 각각 별도의 문장이고 별도의 트랜잭션이므로, 각 페이지는 서로 다른 시점의 데이터를 본다. 사용자가 1페이지를 보는 사이 새 PAID 주문 3건이 들어오면, 최신순 목록 전체가 3칸씩 뒤로 밀린다. 2페이지를 OFFSET 20으로 가져오면 1페이지의 마지막 3건이 2페이지 맨 앞에 다시 나온다. 반대로 그사이 주문 3건이 다른 상태로 바뀌어 목록에서 빠지면 목록이 3칸 당겨져, 원래 2페이지 앞에 있어야 할 3건을 아무도 보지 못한다. OFFSET은 "앞에서 몇 번째"라는 위치를 가리키는데, 그 위치의 의미가 요청 사이에 바뀌기 때문이다. 07회에서 본 동률 문제도 있다. 정렬 열의 값이 같은 행들은 서버가 어떤 순서로 돌려줘도 되므로, 정렬 키가 유일하지 않으면 페이지 경계에서 같은 행이 두 번 나오거나 빠질 수 있다.

    페이지 번호 목록을 그리려면 전체 건수도 필요하다. SELECT COUNT(*) FROM orders WHERE status = 'PAID'에는 조기 종료가 없다. 매뉴얼의 COUNT() 설명은 InnoDB가 테이블의 행 수를 내부에 따로 보관하지 않는다고 명시한다. 동시에 실행 중인 트랜잭션들이 같은 순간에 서로 다른 행 수를 "볼" 수 있기 때문이다. 그래서 COUNT(*)는 현재 트랜잭션에 보이는 행을 실제로 세며, 조건이 없으면 가장 작은 세컨더리 인덱스를 훑는다. 우리 쿼리라면 idx_orders_status_ordered의 PAID 구간 7만 항목을 세게 된다. 스프링 데이터 JPA의 Page 반환 타입이 바로 이 일을 한다. 스프링 데이터 문서는 Page가 전체 개수를 알기 위해 카운트 쿼리를 실행하며 이것이 비쌀 수 있으니 다음 묶음이 있는지만 아는 Slice를 대신 쓸 수 있다고 안내하고, 오프셋 기반 쿼리는 오프셋이 너무 크면 데이터베이스가 여전히 전체 결과를 만들어야 하므로 비효율적이 된다고 적는다. 건수를 미리 모아 두는 방법은 이 회차 끝의 사전 집계에서 다룬다.

    지연 조인: 버릴 행은 인덱스 안에서만 버린다

    OFFSET 페이징의 비용을 다시 나눠 보자. 1,000번째 페이지의 비용은 인덱스 항목 20,000개 읽기와 클러스터형 인덱스 룩업 20,000번이다. 두 비용은 크기가 전혀 다르다. 인덱스 항목은 리프 페이지 안에 촘촘히 붙어 있어 한 페이지를 읽으면 수백 개가 한꺼번에 따라오지만, 룩업은 항목마다 클러스터형 인덱스를 루트부터 다시 내려가고 앞에서 계산한 대로 서로 다른 데이터 페이지 수천 개를 건드린다. 그런데 버려질 19,980행에 대해 룩업이 하는 일, 곧 member_id와 amount를 가져오는 일은 전혀 쓸모가 없다. 위치를 세는 데는 인덱스 항목만 있으면 된다. 지연 조인(deferred join)은 이 관찰을 쿼리로 옮긴 것이다. 먼저 인덱스만으로 20개의 기본 키를 고르고, 행 전체는 그 20개에 대해서만 가져온다.

    SELECT o.order_id, o.member_id, o.amount, o.ordered_at
FROM (
    SELECT order_id
    FROM orders
    WHERE status = 'PAID'
    ORDER BY ordered_at DESC, order_id DESC
    LIMIT 20 OFFSET 19980
) AS page
JOIN orders o ON o.order_id = page.order_id
ORDER BY o.ordered_at DESC, o.order_id DESC;

    안쪽 쿼리는 order_id만 고른다. idx_orders_status_ordered의 항목에는 status, ordered_at, order_id가 모두 들어 있으므로 이 쿼리는 커버링 인덱스로 처리할 수 있다(08회). 인덱스 항목 20,000개를 읽고 19,980개를 버리지만 룩업은 한 번도 하지 않는다. 바깥쪽은 고른 20개의 기본 키로 orders를 다시 찾아가므로 룩업은 정확히 20번이다.

    이 쿼리가 의도대로 실행되는 데는 옵티마이저의 규칙 하나가 걸려 있다. 매뉴얼의 파생 테이블 최적화 절은 옵티마이저가 FROM 절의 서브쿼리(파생 테이블)를 바깥 쿼리에 병합(merge)하거나 내부 임시 테이블로 구체화(materialize)한다고 설명하고, 병합을 막는 구성 요소로 집계 함수, DISTINCT, GROUP BY, HAVING, LIMIT, UNION 등을 든다. 안쪽 쿼리에 LIMIT이 있으므로 병합되지 않고, 먼저 실행되어 20행짜리 임시 테이블이 된다. 병합된다면 LIMIT의 의미가 바깥 조인 결과에 걸려 버리므로 병합하지 않는 것이 당연하다. 이어서 이 20행을 바깥 테이블로 삼아 orders의 기본 키로 한 행씩 찾아가는 조인이 돈다. MySQL 8.4.13에서 EXPLAIN ANALYZE로 실행하면 다음과 같이 나온다. 비용(cost), 추정 행 수, 실행 시간은 실행 환경과 통계에 따라 달라진다. MySQL 8.0.46의 EXPLAIN FORMAT=TREE도 같은 노드 구성이었고 비용 값만 달랐다.

    -> Sort: o.ordered_at DESC, o.order_id DESC  (actual time=4.28..4.28 rows=20 loops=1)
    -> Stream results  (cost=20880 rows=20) (actual time=4.16..4.19 rows=20 loops=1)
        -> Nested loop inner join  (cost=20880 rows=20) (actual time=4.15..4.17 rows=20 loops=1)
            -> Table scan on page  (cost=15875..15878 rows=20) (actual time=4.11..4.11 rows=20 loops=1)
                -> Materialize  (cost=15875..15875 rows=20) (actual time=4.11..4.11 rows=20 loops=1)
                    -> Limit/Offset: 20/19980 row(s)  (cost=15873 rows=20) (actual time=4.07..4.08 rows=20 loops=1)
                        -> Covering index lookup on orders using idx_orders_status_ordered (status='PAID') (reverse)  (cost=15873 rows=142360) (actual time=0.181..3.58 rows=20000 loops=1)
            -> Single-row index lookup on o using PRIMARY (order_id=`page`.order_id)  (cost=0.25 rows=1) (actual time=0.00281..0.00284 rows=1 loops=20)

    안쪽의 Covering index lookup이 항목 20,000개(rows=20000)를 돌려주고, 바깥의 Single-row index lookup on o using PRIMARY는 loops=20, 곧 정확히 20번 실행되었다. 조인과 바깥 정렬 사이의 Stream results는 행을 쌓아 두지 않고 아래에서 받은 행을 위로 넘기는 노드다.

    바깥 쿼리의 ORDER BY를 빼면 안 된다. SQL은 ORDER BY가 없는 쿼리의 결과 순서를 보장하지 않으며, 파생 테이블 안의 ORDER BY는 그 안의 LIMIT이 어떤 20행을 고를지 정할 뿐 바깥 결과의 순서를 약속하지 않는다. 다행히 바깥 정렬은 20행짜리이므로 비용이 거의 없다. 효과를 숫자로 정리하면, 1,000번째 페이지에서 일반 OFFSET은 인덱스 항목 20,000개와 데이터 페이지 약 2,860개를 건드렸다. 지연 조인은 같은 인덱스 항목 20,000개를 읽지만, 세컨더리 인덱스 항목이 상태 문자열과 시각, 주문 번호에 레코드 헤더를 더해 수십 바이트 정도라면 한 페이지에 수백 개가 들어가므로 인덱스 리프 페이지 수십 개와 데이터 페이지 20개 이하로 끝난다.

    지연 조인의 한계도 분명하다. 버리는 일을 가볍게 했을 뿐 버리는 양은 그대로다. 마지막 페이지에서는 여전히 인덱스 항목 7만 개를 읽는다. 또 비슷해 보이는 WHERE order_id IN (SELECT order_id FROM ... LIMIT 20 OFFSET 19980)은 MySQL에서 실행되지 않는다. 매뉴얼의 서브쿼리 제약 절은 IN/ALL/ANY/SOME 서브쿼리 안의 LIMIT을 지원하지 않으며 ERROR 1235 (42000): This version of MySQL doesn't yet support 'LIMIT & IN/ALL/ANY/SOME subquery'가 난다고 적는다. MySQL 8.4.13에서 실행해 보아도 정확히 이 오류가 난다. 그래서 파생 테이블과 조인하는 형태를 쓴다. 애플리케이션에서는 같은 생각을 두 번의 쿼리로 나눌 수도 있다. 먼저 커버링 인덱스로 order_id 20개만 조회하고, 그 20개로 WHERE order_id IN (...) 조회를 한 뒤 애플리케이션에서 첫 쿼리의 순서대로 다시 늘어놓는다. 위치를 세는 비용 자체를 없애려면 위치를 숫자로 가리키는 방식을 버려야 한다.

    커서 기반 페이징 1: 마지막으로 본 키에서 다시 내려간다

    OFFSET이 비싼 근본 이유는 "앞에서 19,980번째"라는 위치를 B+Tree가 한 번에 찾아갈 방법이 없다는 데 있다. 05회에서 본 B+Tree의 내부 노드는 키 값으로 자식을 고르는 구조이지, 각 서브트리에 항목이 몇 개 있는지는 저장하지 않는다. 그래서 n번째 항목은 처음부터 세어 가는 수밖에 없다. 반면 "이 키 값 바로 다음"이라는 위치는 루트에서 리프까지 한 번 내려가면 찾는다. 키셋 페이징(keyset pagination) 또는 커서 기반 페이징(cursor-based pagination)은 다음 페이지의 시작 위치를 숫자 대신 직전 페이지 마지막 행의 정렬 키 값으로 가리키는 방식이다.

    1페이지의 20행 가운데 마지막 행은 주문 999,791번이다. 최신 PAID 주문은 999,996번부터 999,990번까지 7건, 999,896번부터 999,890번까지 7건, 그리고 999,796번부터 999,791번까지 6건이므로 20번째가 999,791번이고, 주문 시각은 2024-12-30 00:20:33이다. 2페이지는 "정렬 순서에서 (2024-12-30 00:20:33, 999791)보다 뒤에 오는 PAID 주문 20건"이다. 정렬이 ordered_at DESC, order_id DESC이므로 "뒤에 온다"는 것은 시각이 더 이르거나, 시각이 같다면 주문 번호가 더 작다는 뜻이다.

    SELECT order_id, member_id, amount, ordered_at
FROM orders
WHERE status = 'PAID'
  AND (ordered_at < '2024-12-30 00:20:33'
       OR (ordered_at = '2024-12-30 00:20:33' AND order_id < 999791))
ORDER BY ordered_at DESC, order_id DESC
LIMIT 20;

    이 쿼리가 B+Tree에서 하는 일을 따라가 보자. 인덱스 확장으로 idx_orders_status_ordered는 (status, ordered_at, order_id) 순서이므로, WHERE 조건은 이 키 공간에서 두 개의 이웃한 구간이 된다. 하나는 ('PAID', ordered_at < '2024-12-30 00:20:33')이고, 다른 하나는 ('PAID', '2024-12-30 00:20:33', order_id < 999791)이다. 둘을 이어 붙이면 "PAID 구간의 시작부터 커서 바로 앞까지"라는 연속된 하나의 범위다. 옵티마이저는 이 범위의 위쪽 끝, 곧 커서 바로 앞에서 B+Tree를 한 번 내려가 리프에 도착한 뒤 왼쪽으로 20개를 읽고 멈춘다. 읽는 항목은 페이지 번호와 상관없이 20개이고 룩업도 20번이다. 1,000번째 페이지도, 마지막 페이지도 같은 비용이다.

    같은 B+Tree 위에서 OFFSET은 리프의 한쪽 끝부터 19,980개를 세며 지나간 뒤 20개를 가져오고, 키셋은 루트에서 커서 위치로 곧장 내려가 20개만 읽는다는 차이를 보여 준다. 위아래 두 패널. 각 패널에 같은 모양의 3단 B+Tree(루트 1개, 내부 노드 3개, 리프 12개가 가로로 연결됨)를 그린다. 위 패널 제목 "OFFSET 19980". 리프 줄의 오른쪽 끝에서 왼쪽으로 긴 주황색 화살표가 리프 9개를 지나가고 그 구간에 라벨 "읽고 버림 19,980개", 이어지는 짧은 초록색 구간에 라벨 "돌려줌 20개". 주황 구간의 리프 각각에서 아래쪽 작은 원통으로 가는 가는 점선 화살표 여러 개, 원통 라벨 "클러스터형 인덱스 룩업". 아래 패널 제목 "키셋: 커서 (00:20:33, 999791)". 루트에서 내부 노드 하나를 거쳐 리프 하나로 곧장 내려가는 굵은 파란 화살표, 라벨 "B+Tree 한 번 내려가기". 도착한 리프에서 짧은 초록 구간 라벨 "20개만 읽음". 흰 배경, 평면 스타일. OFFSET은 n번째 위치를 처음부터 세어 찾아가고, 키셋은 키 값으로 위치를 가리켜 루트에서 곧장 내려간다. 키셋의 비용은 페이지 깊이와 무관하다.

    왜 행 생성자 비교 대신 풀어 쓴 조건인가

    같은 조건을 행 생성자(row constructor)로 (ordered_at, order_id) < ('2024-12-30 00:20:33', 999791)처럼 쓰면 훨씬 짧다. 의미도 같다. 그런데 매뉴얼의 행 생성자 표현식 최적화 절은 이런 비교가 인덱스 사용을 덜 완전하게 만들 수 있음을 예로 보여 준다. 기본 키가 (c1, c2, c3)인 테이블에서 WHERE c1 = 1 AND (c2, c3) > (1, 1)은 기본 키의 c1만 써서 key_len이 4인 ref 접근이 되었고, 같은 조건을 c1 = 1 AND (c2 > 1 OR ((c2 = 1) AND (c3 > 1)))로 풀어 쓰자 세 열을 모두 쓰는 range 접근(key_len 12)이 되었다. 매뉴얼의 결론은 행 생성자와 AND/OR 표현식을 섞지 말고 둘 중 하나만 쓰라는 것이다. 우리의 키셋 조건은 정확히 그 섞인 모양(status = 'PAID' AND (행 생성자 비교))이므로 풀어 쓴 형태를 쓴다.

    풀어 쓴 조건을 쓰더라도 결과는 실행 계획으로 확인한다. 볼 것은 세 가지다. key가 idx_orders_status_ordered이고 type이 range인가, Extra에 Using filesort가 없는가, 그리고 EXPLAIN ANALYZE에서 인덱스 접근 노드가 실제로 돌려준 행 수가 페이지 크기 수준인가. 마지막 것이 가장 확실한 증거다. EXPLAIN의 rows는 LIMIT으로 일찍 멈추기 전의 범위 전체를 추정한 값일 수 있지만, EXPLAIN ANALYZE의 실제 행 수(03회)는 이터레이터가 실제로 돌려준 행을 센다. 이 값이 페이지 번호에 따라 커진다면 어딘가에서 키셋 조건이 범위로 쓰이지 못하고 필터로만 쓰이고 있다는 뜻이다.

    실습 데이터로 두 형태를 직접 비교해 보았다. MySQL 8.4.13에서 풀어 쓴 2페이지 쿼리는 type range, key idx_orders_status_ordered, key_len 95(세 열을 모두 범위에 씀), Extra는 Using index condition; Backward index scan이었고 Using filesort는 없었다. EXPLAIN의 rows는 141,941로 범위 전체를 추정한 값이었지만, EXPLAIN ANALYZE에서 Index range scan 노드의 실제 행 수는 rows=20이었다. 같은 조건을 행 생성자로 쓰면 매뉴얼의 예가 그대로 재현된다. 아래는 그 행 생성자 형태의 EXPLAIN ANALYZE다(MySQL 8.0.46에서도 같은 구성이었다).

    -> Limit: 20 row(s)  (cost=19471 rows=20) (actual time=1.61..1.62 rows=20 loops=1)
    -> Filter: ((orders.ordered_at,orders.order_id) < ('2024-12-30 00:20:33',999791))  (cost=19471 rows=142360) (actual time=1.6..1.61 rows=20 loops=1)
        -> Index lookup on orders using idx_orders_status_ordered (status='PAID') (reverse)  (cost=19471 rows=142360) (actual time=1.57..1.58 rows=40 loops=1)

    인덱스는 status='PAID'만 쓰는 ref 접근(key_len 82)이 되었고, 행 생성자 비교는 그 위의 Filter로 밀려났다. PAID 구간의 오른쪽 끝부터 읽으며 커서 앞의 20개를 버리느라 2페이지에서 이미 항목 40개를 읽는다. 커서를 ('2024-06-01 00:00:00', 999791)로 옮겨 깊은 페이지를 흉내 내면 이 노드의 실제 행 수는 rows=20390이 된다. 키셋처럼 보이지만 비용은 OFFSET처럼 페이지 깊이에 비례하는 것이다. 비용과 실행 시간 값은 실행 환경과 통계에 따라 달라진다.

    커서 기반 페이징 2: 동률, 방향, 그리고 화면 설계

    키셋 페이징의 원리는 단순하지만 실제 화면에 붙이면 따져야 할 것이 여럿 생긴다. 첫째는 정렬 키가 유일해야 한다는 조건이다. 우리 실습 데이터는 주문 시각이 63초 간격이라 중복이 없지만, 실제 서비스에서는 같은 초에 주문이 여러 건 들어온다. 주문 501, 502, 503번이 모두 10:00:00에 들어왔고, 정렬이 ordered_at DESC, order_id DESC라서 이 셋이 503, 502, 501 순서로 놓여 있으며, 한 페이지가 하필 503번에서 끝났다고 하자. 다음 페이지 조건을 ordered_at < '10:00:00'으로만 쓰면 502번과 501번은 어느 페이지에도 나오지 않는다. 겁이 나서 <=로 바꾸면 이번에는 503번이 다음 페이지 맨 앞에 다시 나온다. 동률 묶음 안의 위치까지 가리키려면 커서에 유일한 열이 들어가야 하고, 그래서 앞 절의 조건은 (ordered_at, order_id) 두 값을 함께 쓴다. 이 마지막 열은 ORDER BY에도, 인덱스의 순서에도 같은 방향으로 들어 있어야 한다.

    둘째는 다음 페이지가 있는지와 이전 페이지다. 다음 페이지 버튼을 그릴지 정하려면 LIMIT을 한 개 더 크게, 곧 21로 주고 21번째 행이 왔는지만 본다. 21번째 행은 화면에 보이지 않고 버려진다. 스프링 데이터의 Slice가 쓰는 방법과 같은 생각이다. 이전 페이지는 비교 방향과 정렬 방향을 함께 뒤집어 가져온 뒤 애플리케이션에서 순서를 다시 뒤집는다. 현재 페이지의 첫 행이 커서가 된다.

    -- 현재 페이지의 첫 행이 (2024-12-30 00:20:33, 999791)일 때, 그 앞의 20건
SELECT order_id, member_id, amount, ordered_at
FROM orders
WHERE status = 'PAID'
  AND (ordered_at > '2024-12-30 00:20:33'
       OR (ordered_at = '2024-12-30 00:20:33' AND order_id > 999791))
ORDER BY ordered_at ASC, order_id ASC     -- 커서에 가까운 쪽부터 읽는다
LIMIT 20;                                  -- 받은 20행을 애플리케이션에서 뒤집어 보여 준다

    이 쿼리는 같은 인덱스를 이번에는 정방향으로 읽는다. 커서 위치로 한 번 내려간 뒤 오른쪽으로 20개를 읽으므로 비용은 다음 페이지와 같다. ORDER BY를 DESC 그대로 두고 LIMIT 20을 걸면 커서에서 가장 먼, 곧 목록 맨 앞의 20건이 나오므로 틀린다. 커서에서 가까운 쪽부터 읽어야 한다는 점이 핵심이다.

    셋째는 정렬 열의 NULL이다. 매뉴얼은 ORDER BY에서 NULL이 ASC일 때 맨 앞에, DESC일 때 맨 뒤에 온다고 설명한다. 그런데 col < ? 같은 비교는 col이 NULL이면 참이 아니므로, NULL을 가진 행은 키셋 조건을 영원히 통과하지 못하고 목록에서 사라진다. 스프링 데이터 문서도 키셋 기반 쿼리의 결과에 null 값이 있으면 대부분의 데이터 저장소에서 잘 동작하지 않는다고 경고한다. 정렬 열을 NOT NULL로 정의하거나, NULL 구간을 따로 처리하는 조건(OR col IS NULL)을 커서의 위치에 맞춰 덧붙여야 한다. 넷째는 사용자가 정렬 기준을 고르는 화면이다. 정렬 기준마다 "등치 필터 열 + 정렬 열 + 유일한 꼬리 열" 모양의 인덱스가 하나씩 필요하고, 열마다 방향이 섞인 정렬은 09회의 내림차순 인덱스가 있어야 정렬 없이 처리된다. 정렬 선택지를 늘릴 때마다 인덱스가 늘어나 쓰기 비용이 커진다는 점을 함께 따져야 한다.

    키셋 페이징이 동시 변경에 어떻게 반응하는지도 OFFSET과 비교해 보자. 커서는 위치를 "앞에서 몇 번째"가 아니라 "이 키의 바로 다음"으로 가리키므로, 사용자가 1페이지를 보는 사이 더 최신 주문이 들어와도 2페이지는 영향을 받지 않는다. 목록에서 빠진 행은 그냥 나오지 않을 뿐 다른 행을 밀거나 당기지 않는다. 다만 정렬 키 값 자체가 바뀌어 커서를 가로질러 이동한 행은 두 번 보이거나 한 번도 안 보일 수 있다. 이것은 여러 요청에 걸쳐 하나의 스냅숏을 유지하지 않는 한 어떤 페이징 방식으로도 피할 수 없다.

    대가도 있다. 키셋은 "다음"과 "이전"만 안다. 37페이지로 바로 건너뛰는 버튼은 37페이지의 시작 키를 모르므로 만들 수 없고, 전체 페이지 수도 따로 세야 한다. 그래서 키셋은 무한 스크롤, 다음 버튼만 있는 목록, 그리고 무엇보다 배치 작업에 잘 맞는다. 앞에서 OFFSET으로 PAID 주문 7만 건을 전부 넘기면 항목을 1억 2천만 개 읽어야 했다. 키셋으로 넘기면 3,500번의 트리 탐색과 7만 개의 항목 읽기로 끝난다. 대량 데이터를 나눠 처리하는 배치, 테이블을 구간별로 옮기는 마이그레이션, 사전 집계 테이블을 다시 만드는 작업은 모두 이 방식으로 구간을 나눠야 한다. 스프링 데이터도 Window와 KeysetScrollPosition으로 키셋 스크롤을 지원하는데, 문서는 키셋 기반 쿼리가 효율적으로 동작하려면 알맞은 인덱스 구조가 필요하고, 결과가 모든 정렬 키를 노출해야 한다고 적는다. 프레임워크가 쿼리를 만들어 주어도 그 쿼리가 B+Tree를 한 번 내려가는 range 접근이 되는지는 인덱스가 정한다.

    GROUP BY 최적화 1: 임시 테이블로 묶는 기본 방법

    이제 세 번째 연산인 그룹핑으로 넘어간다. 매뉴얼의 GROUP BY 최적화 절은 GROUP BY를 처리하는 가장 일반적인 방법을 이렇게 설명한다. 테이블 전체를 읽으면서 각 그룹의 행이 연속해서 모이는 새 임시 테이블을 만들고, 그 임시 테이블로 그룹을 찾아 집계 함수를 적용한다. 그리고 경우에 따라서는 인덱스 접근으로 임시 테이블 생성을 피할 수 있다고 덧붙인다. 먼저 일반적인 방법이 실행기 안에서 정확히 어떻게 돌아가는지 보자.

    SELECT member_id, COUNT(*) AS order_count, SUM(amount) AS total_amount
FROM orders
WHERE ordered_at >= '2024-01-01' AND ordered_at < '2025-01-01'
GROUP BY member_id;

    8.0 소스에서 이 일을 맡는 것은 TemptableAggregateIterator다. 소스 주석은 이 이터레이터를 "정렬되지 않은 데이터를 임시 테이블로 집계하며, 갱신 연산으로 집계 중간값을 유지한다. 그 뒤에는 임시 테이블을 훑을 수 있게 해 준다"고 설명한다. 임시 테이블에는 그룹 키에 대한 유일 인덱스가 있다. 소스 주석에 따르면 이 키는 GROUP BY 열 자체이거나, 그 열들의 해시 값을 담은 숨은 필드(hash_field)다. 입력 행 하나가 올라올 때마다 이터레이터는 그 행의 그룹 키로 임시 테이블을 찾아본다(ha_index_read_map). 찾으면 집계 값을 새 행 기준으로 고쳐 쓰고(ha_update_row), 못 찾으면 새 그룹 행을 넣는다(ha_write_row). 입력이 끝나면 위쪽 노드가 임시 테이블을 처음부터 훑어 결과 행을 하나씩 가져간다. 작은 입력으로 손으로 돌려 보면 이렇다.

    입력 순서 (member_id, amount)   임시 테이블 (member_id → 건수, 합계)        연산
(7, 3000)                        7 → (1, 3000)                                 찾기 실패 → 삽입
(2, 5000)                        7 → (1, 3000)   2 → (1, 5000)                 찾기 실패 → 삽입
(7, 1000)                        7 → (2, 4000)   2 → (1, 5000)                 찾음 → 갱신
(4, 2000)                        7 → (2, 4000)   2 → (1, 5000)   4 → (1, 2000) 찾기 실패 → 삽입
(2, 4000)                        7 → (2, 4000)   2 → (2, 9000)   4 → (1, 2000) 찾음 → 갱신
입력 끝 → 이제야 임시 테이블을 훑어 세 행을 내보낸다

    실습 데이터에 적용하면 2024년 주문 499,429행이 올라오고, 2024년에 주문한 회원이 99,991명이므로 그룹도 99,991개다. 임시 테이블 찾기가 499,429번, 삽입이 99,991번, 갱신이 그 차이인 399,438번 일어난다. MySQL 8.4.13에서 FLUSH STATUS 뒤 이 쿼리를 실행하고 세션 카운터를 보면 Handler_write 99,991, Handler_update 399,438, Handler_read_key 499,430(계산보다 1 많다), Created_tmp_tables 1이었다. 원본 테이블은 읽기만 하므로 쓰기와 갱신 카운터는 모두 임시 테이블에서 나온 값이다. 그리고 이 모든 일이 끝나기 전에는 결과 행이 하나도 나가지 않는다. 회원 1번의 그룹이 완성되려면 그 회원의 마지막 2024년 주문이 올라와야 하는데, 01회에서 본 대로 한 회원의 주문은 주문 번호가 99,991씩 떨어져 테이블 전체에 퍼져 있으므로, 주문 번호 순서로 읽는 한 어느 그룹도 마지막 행 근처에 가서야 닫힌다. 임시 테이블 집계는 전형적인 차단 연산이다.

    임시 테이블은 어디에 만들어지는가

    매뉴얼의 내부 임시 테이블 절에 따르면 8.0에서 메모리 안의 내부 임시 테이블은 기본적으로 TempTable 스토리지 엔진으로 만들어진다(internal_tmp_mem_storage_engine의 기본값 TempTable, 다른 선택지는 MEMORY). 크기 한도는 여러 층이다. 8.0.28부터 tmp_table_size가 TempTable 엔진이 만드는 개별 임시 테이블 하나의 최대 크기를 정하고, 기본값은 16MiB다. 이 한도에 닿으면 MySQL은 메모리 안의 임시 테이블을 InnoDB 디스크 임시 테이블로 자동 변환한다. 소스에서도 이 과정을 볼 수 있다. 갱신이나 삽입이 "테이블이 가득 찼다"는 오류로 실패하면 move_table_to_disk()로 테이블을 디스크로 옮기고, 새 테이블에서 해당 그룹 행을 다시 찾아 갱신을 재시도한다. 8.0.16부터 디스크 내부 임시 테이블은 InnoDB로만 만들어지며 MyISAM은 더 이상 쓰이지 않는다.

    그 위에 TempTable 엔진 전체가 쓰는 메모리의 한도 temptable_max_ram이 있다. 여기서 8.0과 8.4가 다르다. 8.0에서 기본값은 1GiB이고, 이 한도를 넘으면 기본적으로 메모리 매핑 파일(memory-mapped file)에서 공간을 할당받는다(temptable_use_mmap 기본 ON, 8.0.23에 도입된 temptable_max_mmap 기본 1GiB). 8.4에서는 temptable_max_ram을 따로 정하지 않으면 서버 전체 메모리의 3%(최소 1GB, 최대 4GB)가 되고, temptable_max_mmap의 기본값이 0이라 메모리 매핑 파일을 쓰지 않는다. 내부 임시 테이블 엔진으로 MEMORY를 고르면 한도는 tmp_table_size와 max_heap_table_size 가운데 작은 값이다. 메모리 안에 만들 수 없는 경우도 있다. 매뉴얼은 BLOB이나 TEXT 열이 있는 경우(TempTable 엔진은 8.0.13부터 이를 지원한다), UNION에서 SELECT 목록에 최대 길이 512를 넘는 문자열 열이 있는 경우를 든다.

    임시 테이블이 만들어졌는지는 EXPLAIN의 Extra에 Using temporary가 있는지로 본다. 트리 형식에서는 Aggregate using temporary table 노드와 그 위의 Table scan on 로 나타난다(MySQL 8.4.13과 8.0.46에서 실행해 확인한 이름이다). 실행 중에 몇 개가 만들어졌는지는 상태 변수 Created_tmp_tables(메모리든 디스크든 내부 임시 테이블을 만들 때마다 증가)와 Created_tmp_disk_tables(디스크에 만들 때 증가)로 본다. 함정이 하나 있다. 매뉴얼은 알려진 제약으로 Created_tmp_disk_tables가 메모리 매핑 파일에 만든 임시 테이블을 세지 않는다고 적는다. 8.0의 기본 설정에서는 TempTable이 넘친 데이터가 바로 그 메모리 매핑 파일로 가므로, 이 카운터가 0이어도 디스크를 쓰지 않았다고 단정할 수 없다. 매뉴얼은 Performance Schema의 memory/temptable/physical_ram과 memory/temptable/physical_disk 계측을 함께 보라고 안내하며, 메모리 매핑 파일을 쓰는 설정에서 physical_disk가 0이 아니면 어느 시점엔가 TempTable 메모리 한도에 닿았다는 뜻이라고 설명한다.

    GROUP BY만 임시 테이블을 만드는 것은 아니다. 매뉴얼은 ORDER BY와 다른 GROUP BY가 함께 있을 때, ORDER BY나 GROUP BY가 조인 순서의 첫 테이블이 아닌 테이블의 열을 쓸 때, DISTINCT와 ORDER BY를 함께 쓸 때, COUNT(DISTINCT)나 GROUP_CONCAT()을 계산할 때, 파생 테이블과 CTE, UNION을 계산할 때 등을 내부 임시 테이블이 생기는 경우로 든다. 결과 순서에 관한 변화도 기억해 두자. 매뉴얼의 ORDER BY 최적화 절은 5.7 이하에서는 GROUP BY가 일정한 조건에서 암묵적으로 정렬했지만 8.0에서는 더 이상 그렇지 않으므로, 예전처럼 정렬을 막으려고 ORDER BY NULL을 붙일 필요가 없고 대신 특정 순서가 필요하면 ORDER BY를 써야 한다고 설명한다. 8.0.13부터는 GROUP BY 열에 ASC/DESC를 붙이는 비표준 문법도 허용되지 않는다. 그러니 임시 테이블 집계 결과를 회원 번호순으로 보여 주려면 ORDER BY가 필요하고, 그 ORDER BY는 그룹 결과를 다시 정렬하는 단계를 하나 더 붙인다. 마지막으로, 매뉴얼은 SQL_BIG_RESULT 수정자를 주면 MySQL이 GROUP BY 열을 키로 하는 임시 테이블 대신 정렬을 선호한다고 설명한다. 먼저 그룹 키로 정렬한 뒤, 같은 키가 이웃하게 된 행을 다음 절의 방식으로 흘려보내며 집계하는 것이다. 정렬 기반 집계와 임시 테이블 기반 집계는 같은 문제를 푸는 두 방법이고, 어느 쪽이든 입력 전체를 받아야 한다는 점은 같다.

    GROUP BY 최적화 2: 인덱스 순서로 흘려보내는 스트리밍 집계

    임시 테이블이 필요한 이유는 같은 그룹의 행이 흩어져 도착하기 때문이다. 같은 그룹의 행이 이웃해서 도착한다면 그룹을 기억해 둘 테이블이 필요 없다. 지금 처리 중인 그룹 하나의 중간값만 들고 있다가, 그룹 키가 바뀌는 순간 그 그룹을 내보내고 다음 그룹을 시작하면 된다. 8.0 소스에서 이 일을 하는 것은 AggregateIterator다. 소스 주석은 이 이터레이터가 "같은 그룹에 속해야 하는 행들이 입력 스트림에서 이웃해 있는 경우"를 처리하며, 그렇게 되는 이유로 행이 미리 정렬되었거나, 그룹에 맞는 순서를 주는 인덱스를 훑고 있거나, 그룹이 아예 없는 경우를 든다. 주석은 또 이 이터레이터가 다음 그룹의 첫 행을 보기 전에는 그룹이 끝났는지 알 수 없으므로, 그 행을 잠시 따로 보관해 두고 이전 그룹의 결과를 내보낸 뒤 보관한 행으로 새 그룹을 시작한다고 설명한다. 앞의 작은 입력을 그룹 키 순서로 바꿔 넣으면 이렇게 된다.

    입력 순서 (member_id, amount)   들고 있는 그룹        내보내는 결과
(2, 5000)                        2 → (1, 5000)
(2, 4000)                        2 → (2, 9000)
(4, 2000)   ← 키가 바뀜           4 → (1, 2000)        (2, 2건, 9000)
(7, 3000)   ← 키가 바뀜           7 → (1, 3000)        (4, 1건, 2000)
(7, 1000)                        7 → (2, 4000)
입력 끝                                                (7, 2건, 4000)

메모리: 그룹 하나 분량.  첫 결과: 세 번째 입력 행에서 이미 나간다.

    이 방식에는 두 가지 이점이 있다. 하나는 메모리다. 그룹이 10만 개든 1억 개든 들고 있는 것은 그룹 하나뿐이므로 임시 테이블도, 디스크로 넘칠 일도 없다. 다른 하나는 파이프라인이다. 첫 그룹의 결과가 입력 초반에 이미 위로 올라가므로, 위에 LIMIT이 있으면 필요한 그룹 수를 채우는 순간 아래쪽 읽기가 멈춘다. 매뉴얼의 LIMIT 최적화 절도 GROUP BY를 인덱스를 순서대로 읽어 처리하고 인덱스 값이 바뀔 때마다 요약을 계산하는 경우에는 LIMIT이 불필요한 GROUP BY 값을 계산하지 않는다고 적는다. EXPLAIN의 트리 형식에서 이 노드는 Group aggregate: count(0), sum(orders.amount)처럼 나타난다(COUNT(*)는 출력에서 count(0)으로 표시된다). Using temporary도, Aggregate using temporary table도 없다는 것이 확인 포인트다.

    타이트 인덱스 스캔이 성립하는 조건

    인덱스가 그룹 순서를 주려면 무엇이 필요한가. 매뉴얼은 인덱스로 GROUP BY를 처리하기 위한 가장 중요한 전제로 모든 GROUP BY 열이 같은 인덱스의 열이어야 하고, 그 인덱스가 키를 순서대로 저장해야 한다(BTREE는 그렇고 HASH는 아니다)는 두 가지를 든다. 그 위에서 인덱스를 처음부터 또는 범위 안에서 차례로 읽으며 그룹을 만드는 방법을 타이트 인덱스 스캔(Tight Index Scan)이라고 부른다. 매뉴얼은 이 방법이 WHERE 절이 정한 범위 안의 키를 모두 읽고, 범위 조건이 없으면 인덱스 전체를 읽는다고 설명한다. 성립 조건은 GROUP BY 열이 인덱스의 최좌측 접두사를 이루거나, 그 앞이나 사이에 빠진 키 부분이 있으면 그 부분이 모두 상수 등치 조건으로 채워지는 것이다. 매뉴얼은 이를 상수가 검색 키의 "빈틈"을 메워 완전한 접두사를 만든다고 표현한다. idx (c1, c2, c3)에서 WHERE c2 = 'a' GROUP BY c1, c3와 WHERE c1 = 'a' GROUP BY c2, c3가 매뉴얼의 예다.

    실습 테이블에 대어 보자. 인덱스 (status, member_id, amount)가 있다고 할 때, 아래 표는 각 쿼리에서 같은 그룹이 이웃해 도착하는지를 따진 것이다.

    쿼리그룹이 이웃해 오는가이유
    WHERE status = 'PAID' GROUP BY member_id예상수 등치가 첫 열을 고정하고, 그 구간 안에서 항목은 member_id 순서다
    GROUP BY status, member_id예GROUP BY가 최좌측 접두사다(범위 조건이 없으니 인덱스 전체를 읽는다)
    GROUP BY member_id (status 조건 없음)아니요member_id는 status 값마다 따로 정렬되어 있어 같은 회원이 네 군데에 흩어진다
    WHERE status IN ('PAID', 'SHIPPED') GROUP BY member_id아니요두 구간이 이어 붙어 member_id 순서가 PAID 구간 끝에서 처음으로 되돌아간다

    마지막 줄이 특히 헷갈린다. IN은 등치처럼 보이지만 상수 하나가 아니라 구간 두 개를 만든다. PAID 구간을 다 읽으면 member_id는 가장 큰 값까지 갔다가 SHIPPED 구간에서 다시 1부터 시작하므로, 같은 회원이 두 번 나타난다. 07회에서 정렬 열 앞의 IN이 인덱스 정렬을 깨는 것과 같은 이유다. 또 하나 따져야 할 것은 룩업이다. 인덱스가 그룹 순서를 주더라도 집계에 필요한 열이 인덱스에 없으면 항목마다 클러스터형 인덱스를 찾아가야 한다(06회). 위 인덱스에 amount를 넣어 둔 것은 SUM(amount)까지 인덱스 안에서 끝내기 위해서다. 스트리밍 집계를 노리는 인덱스는 거의 언제나 커버링 인덱스로 설계한다.

    왼쪽은 회원 번호가 뒤섞여 들어와 임시 테이블의 여러 칸을 오가며 갱신되고 입력이 끝나야 결과가 나가는 모습, 오른쪽은 같은 회원끼리 이웃해 들어와 그룹 하나만 들고 있다가 키가 바뀔 때마다 결과가 바로 위로 나가는 모습을 보여 준다. 좌우 두 패널. 왼쪽 패널 제목 "임시 테이블 집계". 아래에서 위로 올라가는 행 카드 줄(카드에 숫자 "7", "2", "7", "4", "2")이 표 모양의 상자 "임시 테이블"로 들어가고, 카드마다 표의 서로 다른 칸으로 가는 화살표가 엇갈린다. 표 위에 자물쇠가 걸린 출구와 라벨 "입력이 끝나야 출력". 표 옆에 작은 디스크 아이콘과 점선 화살표, 라벨 "tmp_table_size 초과 시 디스크". 오른쪽 패널 제목 "스트리밍 집계". 카드 줄이 "2", "2", "4", "7", "7" 순서로 올라가고, 위에 작은 상자 하나 "현재 그룹"이 있다. 카드 "4"가 들어오는 순간 상자 위로 결과 카드 "(2, 2건)"이 튀어 나가는 화살표, 라벨 "키가 바뀌면 바로 출력". 맨 위에 "LIMIT" 표지판과 라벨 "필요한 만큼 채우면 멈춤". 흰 배경, 평면 스타일. 그룹이 흩어져 오면 모든 그룹을 임시 테이블에 들고 있어야 하고, 입력이 끝나야 첫 결과가 나간다. 인덱스가 그룹 순서를 주면 그룹 하나만 들고 있다가 키가 바뀔 때마다 결과를 흘려보낸다.

    GROUP BY 최적화 3: 루스 인덱스 스캔, DISTINCT, 그리고 HAVING

    타이트 인덱스 스캔은 그룹의 행을 하나도 빠짐없이 읽는다. 그런데 어떤 집계는 그룹의 행을 다 볼 필요가 없다. 회원별 마지막 주문 시각, 곧 MAX(ordered_at)는 (member_id, ordered_at) 순서의 인덱스에서 각 회원 구간의 마지막 항목 하나만 보면 된다. 루스 인덱스 스캔(Loose Index Scan)은 이 성질을 이용해 그룹마다 B+Tree를 다시 내려가 필요한 항목만 읽고 다음 그룹으로 건너뛴다. 매뉴얼이 정리한 조건은 다음과 같다. 쿼리가 테이블 하나만 대상으로 할 것, GROUP BY가 인덱스의 최좌측 접두사인 열만 나열할 것(DISTINCT도 마찬가지), SELECT 목록의 집계 함수는 MIN()과 MAX()뿐이고 모두 같은 열을 가리키며 그 열이 인덱스에서 GROUP BY 열 바로 뒤에 올 것, GROUP BY 열이 아닌 인덱스의 나머지 부분은 MIN()/MAX()의 인자를 빼고 모두 상수 등치일 것, 그리고 열의 일부가 아니라 전체 값이 인덱스되어 있을 것. 성립하면 EXPLAIN의 Extra에 Using index for group-by가 나타나고, 8.0 소스의 트리 형식 출력은 이 접근을 Covering index skip scan for grouping이라고 부른다.

    지금 있는 인덱스로 바로 해 볼 수 있는 예가 있다. 상태별 가장 최근 주문 시각이다.

    SELECT status, MAX(ordered_at) AS last_ordered_at
FROM orders
GROUP BY status;                           -- idx_orders_status_ordered (status, ordered_at)

    조건을 하나씩 대어 보면 테이블 하나, GROUP BY status는 첫 열, 집계는 MAX(ordered_at) 하나이고 ordered_at은 status 바로 뒤의 열이며, 두 열 모두 전체 값이 인덱스되어 있다. 그룹은 넷뿐이다. 타이트 인덱스 스캔이라면 인덱스 항목 100만 개를 모두 읽어야 하지만, 루스 인덱스 스캔은 상태마다 다음 그룹의 시작과 그 구간의 끝을 찾아 B+Tree를 몇 번 내려가는 것으로 끝난다. MySQL 8.4.13에서 실행하면 EXPLAIN은 type range, Extra Using index for group-by이고, 트리 형식은 Covering index skip scan for grouping on orders using idx_orders_status_ordered였다(8.0.46도 같다). FLUSH STATUS 뒤 세션 카운터는 Handler_read_key 10, Handler_read_first 1, Handler_read_last 1, Handler_read_next 0으로, 네 그룹을 인덱스 탐색 열두 번으로 끝냈다. 그룹이 적고 그룹마다 행이 많을수록 이득이 크다. 반대로 회원별 MAX(ordered_at)처럼 그룹이 99,991개이고 그룹마다 행이 10개 남짓이면, 그룹마다 루트부터 다시 내려가는 비용이 같은 리프 안에서 열 개를 옆으로 읽는 비용보다 나을 것이 없다. 루스 인덱스 스캔을 쓸지는 옵티마이저가 비용으로 고르며, 그 비용을 가르는 것이 바로 그룹당 행 수다.

    이 접근은 08회의 스킵 스캔과 비슷해 보이지만 다른 장치다. 매뉴얼은 스킵 스캔의 조건으로 쿼리가 GROUP BY나 DISTINCT를 쓰지 않을 것을 명시한다. 그룹핑이 있는 쿼리에서 "건너뛰며 읽기"를 하는 것은 루스 인덱스 스캔이다. 매뉴얼은 GROUP BY가 없을 때 COUNT(DISTINCT), SUM(DISTINCT), AVG(DISTINCT)에도 루스 인덱스 스캔을 쓸 수 있다고 적고, SELECT COUNT(DISTINCT c1), SUM(DISTINCT c1) FROM t1을 예로 든다. 반대로 매뉴얼이 루스 인덱스 스캔을 쓸 수 없는 예로 든 첫 번째가 SELECT c1, SUM(c2) FROM t1 GROUP BY c1이다. SUM과 COUNT는 그룹의 모든 행을 봐야 하므로 건너뛸 수 없다.

    WHERE에 둘 것과 HAVING에 둘 것

    그룹핑 쿼리에서 조건을 어디에 쓰느냐는 인덱스 사용과 직결된다. 매뉴얼의 SELECT 절은 HAVING이 거의 마지막, 곧 결과를 클라이언트로 보내기 직전에 최적화 없이 적용되며 LIMIT은 HAVING 다음에 적용된다고 설명하고, WHERE에 있어야 할 항목에 HAVING을 쓰지 말라고 분명히 적는다. ... GROUP BY member_id HAVING member_id <= 1000은 99,991개 그룹을 모두 만든 뒤 1,000개만 남긴다. 같은 조건을 WHERE member_id <= 1000으로 옮기면 그룹을 만들기 전에 입력이 줄고, 인덱스가 있다면 범위 접근이 된다. HAVING에는 HAVING SUM(amount) >= 300000처럼 집계가 끝나야 계산할 수 있는 조건만 남긴다.

    집계 값으로 정렬하는 쿼리, 예를 들어 ORDER BY total_amount DESC LIMIT 10은 그룹핑 방식과 상관없이 정렬 단계가 하나 더 붙는다. 집계 값은 어떤 인덱스에도 들어 있지 않으므로 그룹을 모두 만든 뒤에야 순서를 정할 수 있다. 그나마 LIMIT이 있으면 03회의 우선순위 큐로 상위 몇 개만 들고 정렬할 수 있다. 이 "모든 그룹을 만든 뒤에야"라는 조건이 실전 튜닝의 마지막 벽이 된다.

    실전 튜닝 4 (1): 남은 문제, GROUP BY가 만든 임시 테이블

    앞선 실전 튜닝 회차들은 풀 테이블 스캔(04회), 정렬(07회), 조인의 랜덤 액세스(11회)를 차례로 걷어냈다. 이번 화면은 회원별 통계다. 관리자는 회원 번호순으로 20명씩 넘기며 각 회원의 2024년 주문 건수, 금액 합계, 마지막 주문 시각을 본다. 화면 위쪽에는 2024년 구매 금액 상위 10명 카드도 있다.

    -- Q1: 회원별 통계 목록, 첫 페이지
SELECT member_id,
       COUNT(*)        AS order_count,
       SUM(amount)     AS total_amount,
       MAX(ordered_at) AS last_ordered_at
FROM orders
WHERE ordered_at >= '2024-01-01' AND ordered_at < '2025-01-01'
GROUP BY member_id
ORDER BY member_id
LIMIT 20;

-- Q2: 구매 금액 상위 10명
SELECT member_id, SUM(amount) AS total_amount
FROM orders
WHERE ordered_at >= '2024-01-01' AND ordered_at < '2025-01-01'
GROUP BY member_id
ORDER BY total_amount DESC
LIMIT 10;

    출발점의 인덱스로 Q1을 진단해 보자. 우선 행을 찾는 단계다. idx_orders_status_ordered는 ordered_at을 두 번째 열로 갖지만, 첫 열 status에 조건이 없으므로 ordered_at의 범위로 내려갈 수 없다. 08회의 스킵 스캔이라면 status 값마다 범위를 만들 수 있겠지만, 앞에서 본 대로 스킵 스캔은 GROUP BY가 있는 쿼리에 쓰이지 않는다. 게다가 조건에 맞는 행이 테이블의 절반(499,429행)이라, 범위로 찾을 수 있다 해도 행마다 룩업을 하느니 테이블을 순차로 읽는 편이 싸다. 결국 클러스터형 인덱스를 처음부터 끝까지 100만 행 읽는 풀 테이블 스캔이 된다. 다음은 그룹핑 단계다. 행이 주문 번호 순서로 올라오고 회원 번호는 그 순서와 무관하게 흩어져 있으니 같은 그룹이 이웃할 리가 없다. 임시 테이블 집계로 99,991개 그룹을 만들고, ORDER BY member_id 때문에 그 그룹들을 다시 정렬해 앞의 20개를 고른다. 실행 계획에서 확인할 것은 type이 ALL이고 Extra에 Using temporary가 있다는 것이며, 그룹 결과를 다시 정렬하는 단계가 붙으면 Using filesort도 함께 보인다. 흐름을 그림으로 그리면 이렇다.

    Limit 20
 └ 정렬 (member_id 순, 상위 20개)          ← 그룹 99,991개가 모두 만들어진 뒤에야 시작
    └ 임시 테이블 스캔
       └ 임시 테이블 집계 (그룹 99,991개)   ← 찾기 499,429번, 삽입 99,991번, 갱신 399,438번
          └ 필터: 2024년                    ← 499,429행 통과
             └ 테이블 풀 스캔               ← 1,000,000행

20행을 보여 주려고 100만 행을 읽고, 10만 개 그룹을 만들고, 그 그룹을 정렬한다.

    MySQL 8.4.13에서 실제로 확인하면 EXPLAIN은 type ALL, key NULL, Extra Using where; Using temporary; Using filesort이고, EXPLAIN ANALYZE는 아래와 같다. 실행 시간과 비용, 추정 행 수는 실행 환경과 통계에 따라 달라진다.

    -> Limit: 20 row(s)  (actual time=460..460 rows=20 loops=1)
    -> Sort: orders.member_id, limit input to 20 row(s) per chunk  (actual time=460..460 rows=20 loops=1)
        -> Table scan on   (actual time=442..451 rows=99991 loops=1)
            -> Aggregate using temporary table  (actual time=442..442 rows=99991 loops=1)
                -> Filter: ((orders.ordered_at >= TIMESTAMP'2024-01-01 00:00:00') and (orders.ordered_at < TIMESTAMP'2025-01-01 00:00:00'))  (cost=101081 rows=110541) (actual time=116..250 rows=499429 loops=1)
                    -> Table scan on orders  (cost=101081 rows=995071) (actual time=0.313..186 rows=1e+6 loops=1)

    EXPLAIN ANALYZE로 보면 03회에서 본 차단 연산의 신호가 그대로 나온다. 맨 위 노드의 첫 행 시간이 마지막 행 시간과 거의 같고(위 출력에서 둘 다 460ms), 그 시간 대부분이 아래쪽 풀 스캔과 임시 테이블 집계에 들어 있다(Aggregate using temporary table이 끝난 시점이 442ms). 2페이지를 열면 member_id > 20 조건을 더해도 사정이 같다. 그 조건은 풀 스캔의 필터일 뿐이라 100만 행을 다시 읽는다. 임시 테이블의 크기도 따져 봐야 한다. 그룹 하나는 회원 번호, 건수, 합계, 최대 시각에 그룹 키 인덱스의 몫까지 담으므로, 99,991개 그룹이 tmp_table_size(기본 16MiB) 안에 들어가는지는 행 형식과 엔진의 저장 방식에 달려 있다. 추측하지 말고 쿼리 전후의 Created_tmp_disk_tables와 Performance Schema의 TempTable 메모리 계측으로 확인한다. 이 회차의 실행 환경(MySQL 8.4.13, tmp_table_size 16MiB, temptable_max_ram 1GiB, temptable_max_mmap 0)에서 Q1을 실행한 뒤의 세션 값은 Created_tmp_tables 1, Created_tmp_disk_tables 0이었다. 메모리 매핑 파일을 쓰지 않는 설정이므로 이 경우에는 디스크 임시 테이블로 넘어가지 않았다고 읽을 수 있다. Performance Schema 계측은 다른 세션의 작업과 섞이는 서버 전체 값이라 여기서는 확인하지 않았다. 화면을 여는 관리자가 여럿이고 기간 조건을 바꿔 가며 조회한다면, 이 임시 테이블들은 동시에 서버 메모리를 나눠 쓴다.

    Q2도 같은 길을 걷고, 마지막 단계만 다르다. 99,991개 그룹을 모두 만든 뒤 합계 내림차순으로 상위 10개를 고른다. 여기에는 숨은 문제가 하나 더 있다. 실습 데이터로 계산해 보면 2024년 합계의 최댓값은 325,000원인데, 이 값을 가진 회원이 1,025명이다(MySQL 8.4.13에서 세어 보아도 같고, 실제로 Q2를 실행하면 열 줄이 모두 325,000원이다). "상위 10명"이 1,025명 가운데 어느 10명인지 정해지지 않는다는 뜻이고, 매뉴얼이 설명하는 대로 동률인 행의 순서는 실행 계획에 따라 달라질 수 있다. 랭킹 화면이라면 ORDER BY total_amount DESC, member_id처럼 동률을 가르는 기준을 먼저 정해야 한다. 성능 이전에 정의의 문제다.

    실전 튜닝 4 (2): 인덱스 정렬을 바꿔 스트리밍 집계로

    Q1의 근본 원인은 "행이 그룹 키 순서로 오지 않는다"는 것이었다. 그렇다면 그룹 키 순서로 정렬된 인덱스를 만들어 그 순서로 읽게 하면 된다. 그룹 키 member_id를 첫 열에 두고, 집계에 필요한 ordered_at과 amount를 뒤에 붙여 커버링 인덱스로 만든다.

    ALTER TABLE orders
  ADD INDEX idx_orders_member_ordered (member_id, ordered_at, amount);

    열 순서에는 이유가 있다. member_id가 맨 앞이어야 같은 회원의 항목이 이웃한다. 두 번째를 ordered_at으로 둔 것은 "특정 회원의 특정 기간 주문"처럼 회원을 등치로 고정하고 기간을 범위로 거는 쿼리가 이 인덱스로 range 접근을 할 수 있게 하기 위해서이고, 회원별 MAX(ordered_at)가 각 회원 구간의 마지막 항목이 되게 하기 위해서이기도 하다. amount는 SUM을 위해 들어갔다. 숨은 네 번째 열 order_id까지 합치면 Q1이 참조하는 열이 모두 인덱스에 있으므로 클러스터형 인덱스 룩업은 한 번도 일어나지 않는다.

    새 인덱스로 Q1이 실행되는 과정을 실습 데이터로 정확히 세어 보자. 인덱스는 회원 1번의 주문 10건(주문 시각순), 회원 2번의 10건, … 순서로 놓여 있다. 회원 1번부터 20번까지는 모두 주문이 10건이고 그중 5건이 2024년이다. 실행기는 인덱스를 처음부터 읽으며 항목마다 2024년 조건을 검사하고, 통과한 항목을 스트리밍 집계로 올린다. 회원 1번의 항목 10개를 읽는 동안 앞의 5개(2023년)는 걸러지고 뒤의 5개가 그룹을 이룬다. 회원 2번의 첫 2024년 항목이 올라오는 순간 회원 1번의 그룹(5건, 238,000원)이 위로 나간다. 이렇게 20번째 그룹이 나가려면 회원 21번의 첫 2024년 항목이 올라와야 하는데, 회원 21번도 앞의 5건이 2023년이므로 그 항목은 회원 21번 구간의 여섯 번째다. 따라서 읽는 인덱스 항목은 20 × 10 + 6 = 206개이고, 집계로 올라간 항목은 101개, 클러스터형 인덱스 룩업은 0번이다. ORDER BY가 GROUP BY와 같고 인덱스 순서와도 같으므로 정렬 단계도 없다.

    Limit 20                                    ← 20개를 채우면 아래쪽에 Read()를 더 부르지 않는다
 └ 스트리밍 집계 (Group aggregate)           ← 그룹 키가 바뀔 때마다 한 행씩 위로
    └ 필터: 2024년                           ← 101개 통과
       └ 커버링 인덱스 스캔 idx_orders_member_ordered (member_id 순)
                                              ← 206개 항목을 읽고 멈춤

전: 100만 행 읽기 + 그룹 99,991개짜리 임시 테이블 + 그룹 정렬
후: 인덱스 항목 206개 읽기, 임시 테이블 없음, 정렬 없음

    이 계산은 실제 실행과 정확히 맞는다. MySQL 8.4.13에서 새 인덱스를 만든 뒤 Q1을 실행하면 EXPLAIN은 type index, key idx_orders_member_ordered, Extra Using where; Using index로 Using temporary와 Using filesort가 사라지고, EXPLAIN ANALYZE는 아래와 같다. FLUSH STATUS 뒤 실행한 세션 카운터도 Handler_read_first 1, Handler_read_next 205로 인덱스 항목 206개, Created_tmp_tables 0이었고, 결과의 첫 줄은 회원 1번, 5건, 238,000원이었다. MySQL 8.0.46에서도 행 수가 모두 같았다. 비용과 실행 시간은 실행 환경과 통계에 따라 달라진다.

    -> Limit: 20 row(s)  (cost=2.03 rows=1.49) (actual time=0.0757..0.123 rows=20 loops=1)
    -> Group aggregate: count(0), sum(orders.amount), max(orders.ordered_at)  (cost=2.03 rows=1.49) (actual time=0.0695..0.117 rows=20 loops=1)
        -> Filter: ((orders.ordered_at >= TIMESTAMP'2024-01-01 00:00:00') and (orders.ordered_at < TIMESTAMP'2025-01-01 00:00:00'))  (cost=1.8 rows=2.22) (actual time=0.036..0.0752 rows=101 loops=1)
            -> Covering index scan on orders using idx_orders_member_ordered  (cost=1.8 rows=20) (actual time=0.0219..0.0528 rows=206 loops=1)

    2페이지는 키셋으로 연다. 첫 페이지의 마지막 회원 번호가 20이므로 WHERE member_id > 20 AND ordered_at >= '2024-01-01' AND ordered_at < '2025-01-01'을 주면, 이번에는 member_id가 인덱스의 첫 열이라 회원 21번의 첫 항목으로 B+Tree를 곧장 내려가는 range 접근이 된다. 어느 페이지든 대략 회원 21명 분량의 항목만 읽는다. MySQL 8.4.13에서 이 2페이지 쿼리는 type range(key_len 8)이었고, EXPLAIN ANALYZE에서 Covering index range scan on orders using idx_orders_member_ordered over (20 < member_id) 노드의 실제 행 수는 1페이지와 똑같이 rows=206이었다. 앞 절들에서 익힌 세 도구, 곧 순서를 주는 인덱스, 키셋, 스트리밍 집계가 한 쿼리 안에서 함께 일한다. 실행 계획에서 확인할 것은 key가 새 인덱스이고 Extra에 Using index가 있으며 Using temporary와 Using filesort가 사라졌는지, 그리고 EXPLAIN ANALYZE에서 인덱스 접근 노드의 실제 행 수가 수백 개 수준인지다. 옵티마이저가 새 인덱스를 고르지 않는다면 10회에서 본 통계와 비용 계산을 의심하고 트레이스로 비교 장면을 확인한다.

    Q2에 같은 인덱스를 쓰면 무엇이 달라지는가. 임시 테이블은 사라진다. 커버링 인덱스 전체를 회원 순서로 읽으며 그룹을 흘려보내고, 위의 정렬 노드가 99,991개 그룹 결과 가운데 상위 10개만 우선순위 큐로 들고 있으면 된다. 읽는 대상도 행 전체가 아니라 그보다 작은 인덱스 항목이다. 그러나 읽는 개수는 줄지 않는다. 합계 상위 10명을 알려면 모든 회원의 합계를 알아야 하므로, 인덱스 항목 100만 개를 매번 끝까지 읽는다. MySQL 8.4.13에서 확인하면 EXPLAIN ANALYZE의 Covering index scan 노드가 rows=1e+6, 그 위의 Group aggregate: sum(orders.amount)가 rows=99991이고, 맨 위는 Sort: total_amount DESC, limit input to 10 row(s) per chunk다. 세션의 Created_tmp_tables는 0, Sort_rows는 10이었다. 다만 전통적인 EXPLAIN의 Extra에는 이 경우에도 Using where; Using index; Using temporary; Using filesort가 표시되었다. Using temporary만 보고 임시 테이블 집계라고 단정하지 말고 트리 형식에서 Aggregate using temporary table 노드가 있는지를 확인해야 하는 이유다. 스트리밍 집계가 없앤 것은 임시 테이블이지 입력의 크기가 아니다. 이 쿼리가 요청마다 치르는 비용은 여전히 테이블 크기에 비례하고, 데이터가 쌓일수록 같이 늘어난다.

    새 인덱스의 값도 따져 두자. 09회에서 본 대로 인덱스 하나는 주문이 들어올 때마다 B+Tree 하나에 항목을 하나 더 넣는 비용과 디스크 공간, 버퍼 풀의 자리를 요구한다. 그리고 인덱스 하나는 정렬 기준 하나다. 기간으로 범위를 좁히는 순서(ordered_at이 앞)와 회원으로 묶는 순서(member_id가 앞)를 한 인덱스에 동시에 담을 수는 없다. 그래서 목록 화면과 키셋 페이징을 위해 idx_orders_status_ordered는 그대로 두고, 그룹핑을 위해 새 인덱스를 하나 더 들인 것이다. 화면 하나를 위한 인덱스가 쌓이기 시작하면, 그다음 선택지는 읽을 때 계산하던 것을 미리 계산해 두는 것이다.

    사전 집계 테이블: 읽을 때 하던 계산을 쓸 때와 배치로 옮긴다

    Q2가 매번 100만 개를 읽는 이유는 질문이 "모든 회원의 합계"를 요구하기 때문이다. 이 답은 주문이 들어오거나 바뀔 때만 달라진다. 그렇다면 조회할 때마다 계산하지 말고, 회원별 합계를 테이블에 저장해 두었다가 주문이 바뀔 때 고치면 된다. 이것이 사전 집계 테이블(summary table)이다. MySQL 8.0의 CREATE VIEW에는 결과를 저장해 두는 선택지가 없다. 뷰의 처리 방식(ALGORITHM)은 UNDEFINED, MERGE, TEMPTABLE이고, 매뉴얼의 내부 임시 테이블 절은 TEMPTABLE 알고리즘의 뷰를 평가할 때 임시 테이블이 만들어진다고 적는다. 곧 뷰는 조회할 때마다 계산된다. 결과를 저장하려면 일반 테이블을 만들고 갱신을 직접 책임져야 한다.

    CREATE TABLE member_yearly_stats (
  stat_year    SMALLINT NOT NULL,
  member_id    BIGINT   NOT NULL,
  order_count  INT      NOT NULL,
  total_amount BIGINT   NOT NULL,
  PRIMARY KEY (stat_year, member_id),
  KEY idx_year_total (stat_year, total_amount)
) ENGINE = InnoDB;

-- Q2를 다시 쓰면
SELECT member_id, total_amount
FROM member_yearly_stats
WHERE stat_year = 2024
ORDER BY total_amount DESC, member_id DESC
LIMIT 10;

    요약 테이블에도 지금까지의 원리가 그대로 적용된다. idx_year_total의 항목은 인덱스 확장으로 (stat_year, total_amount, member_id)를 담고 있으므로, 위 쿼리는 stat_year = 2024 구간의 끝에서 거꾸로 10개를 읽고 멈춘다. SELECT 목록의 두 열이 모두 항목 안에 있어 룩업도 없다. 1,025명의 동률은 member_id DESC가 가른다. 이 꼬리 열이 인덱스의 순서 안에 같은 방향으로 들어 있으니 정렬 단계도 생기지 않는다. 100만 개를 읽던 질문이 항목 10개를 읽는 질문이 되었다. MySQL 8.4.13에서 아래의 배치 쿼리로 요약 테이블을 채운 뒤(99,991행) 확인하면, 이 쿼리의 EXPLAIN은 type ref, key idx_year_total, Extra Backward index scan; Using index로 Using filesort가 없고, 결과는 325,000원인 회원 가운데 번호가 큰 99964, 99931, 99898, … 순서로 열 명이다. 요약 테이블에 인덱스를 거는 일은 집계 값으로 정렬하는 문제, 곧 "모든 그룹을 만든 뒤에야 정렬할 수 있다"는 벽을 넘는 유일한 방법이기도 하다. 집계 값이 저장된 열이 되었으므로 B+Tree가 그 순서를 미리 들고 있을 수 있다.

    요약 테이블을 설계할 때 먼저 확인할 것은 압축률이다. 요약 테이블이 원본보다 훨씬 작아야 의미가 있다. 2024년의 회원별 요약은 99,991행으로 원본 499,429행의 5분의 1이다. 그런데 같은 데이터로 회원별·일별 요약을 만들면 어떻게 될까. 한 회원의 주문은 약 73일(99,991 × 63초)에 한 번꼴이므로, 회원·날짜 조합 하나에 주문이 거의 한 건뿐이다. 실제로 MySQL 8.4.13에서 2024년의 회원·날짜 조합을 세어 보면 499,429개로 원본 행 수와 똑같다. 요약 행 수가 원본과 같아져 얻는 것이 없다. 반대로 날짜·상태별 요약은 하루 약 1,371건(86,400 ÷ 63)이 네 행으로 줄어든다. 전체 100만 행이 2,920행(730일 × 4)이 된다. 요약의 단위(grain)는 데이터 모양이 아니라 화면이 묻는 질문에서 정하고, 그 단위로 원본이 충분히 줄어드는지를 계산해 확인한다.

    갱신 방식 1: 원본과 같은 트랜잭션에서 즉시 반영

    주문을 넣는 트랜잭션 안에서 요약 행도 함께 고치면 요약은 항상 원본과 일치한다. MySQL에서는 INSERT ... ON DUPLICATE KEY UPDATE로 "없으면 넣고 있으면 더한다"를 한 문장에 쓴다. 매뉴얼에 따르면 8.0.19부터 VALUES 절 뒤에 AS로 행 별칭을 붙여 새 값을 가리킬 수 있고, 예전 방식인 VALUES() 함수로 새 값을 가리키는 것은 8.0.20부터 사용 중단(deprecated)되었다. 영향받은 행 수는 새로 넣으면 1, 기존 행을 고치면 2, 기존 값과 같은 값으로 고치면 0이다. 행 별칭을 쓸 때는 UPDATE 절의 오른쪽에서 기존 값을 테이블 이름으로 한정해야 한다. order_count = order_count + new.order_count처럼 열 이름만 쓰면, 그 order_count가 테이블의 열인지 별칭 new의 열인지 모호해져 MySQL 8.4.13과 8.0.46 모두 ERROR 1052 (23000): Column 'order_count' in field list is ambiguous로 실패한다.

    START TRANSACTION;
INSERT INTO orders (member_id, status, amount, ordered_at)
VALUES (42, 'PAID', 35000, '2024-06-01 10:00:00');

INSERT INTO member_yearly_stats (stat_year, member_id, order_count, total_amount)
VALUES (2024, 42, 1, 35000) AS new
ON DUPLICATE KEY UPDATE order_count  = member_yearly_stats.order_count  + new.order_count,
                        total_amount = member_yearly_stats.total_amount + new.total_amount;
COMMIT;

    MySQL 8.4.13에서 요약 테이블을 채워 둔 상태로 이 트랜잭션을 실행하면 요약 문장은 Query OK, 2 rows affected(기존 행 갱신)를 돌려주고, 행이 없는 키(예: 2025년)로 같은 문장을 실행하면 1 row affected, 같은 값으로 덮어쓰면 0 rows affected다. 옛 방식인 VALUES(total_amount)를 쓰면 Warning (Code 1287): 'VALUES function' is deprecated and will be removed in a future release.로 시작하는 경고가 붙는다.

    이 방식의 비용은 잠금에서 나온다. 매뉴얼의 InnoDB 잠금 절은 INSERT ... ON DUPLICATE KEY UPDATE가 중복 키 오류가 나는 경우 갱신할 행에 공유 잠금이 아니라 배타 잠금을 걸며, 중복된 값이 기본 키이면 배타 인덱스 레코드 잠금을 건다고 설명한다. 이 잠금은 트랜잭션이 끝날 때까지 유지된다. 회원별 요약 행이라면 같은 회원의 주문이 동시에 들어올 때만 서로 기다리므로 경합이 드물다. 그런데 "오늘 결제 완료 건수"처럼 모든 주문이 같은 요약 행을 고치는 설계라면 이야기가 다르다. 모든 주문 트랜잭션이 그 한 행의 배타 잠금을 차례로 얻어야 하므로, 주문 처리가 그 행 하나에서 줄을 서게 된다. 처리량의 상한이 "그 행의 잠금을 쥐고 있는 시간", 곧 트랜잭션 하나의 길이로 정해지는 것이다. 주문 상태가 바뀔 때 두 요약 행(이전 상태 −1, 새 상태 +1)을 고친다면, 트랜잭션마다 두 행을 잠그는 순서가 다를 경우 교착 상태(deadlock)도 생길 수 있다. 요약 행의 total_amount가 바뀔 때마다 idx_year_total의 항목도 지우고 새로 넣어야 한다는 점도 쓰기 비용에 더해진다.

    갱신 방식 2: 배치로 다시 계산

    두 번째 방식은 원본 트랜잭션을 건드리지 않고 주기적으로 요약을 다시 계산하는 것이다. 이때 핵심은 멱등성(idempotency)이다. 증가분을 더하지 말고 그 구간의 값을 처음부터 다시 계산해 덮어쓰면, 배치가 중간에 실패해도 다시 돌리기만 하면 된다. 매뉴얼은 INSERT ... SELECT에 ON DUPLICATE KEY UPDATE를 붙일 때 GROUP BY 쿼리의 열을 참조하려면 SELECT를 파생 테이블로 감싸라고 안내한다.

    SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;   -- 이유는 아래에서

INSERT INTO member_yearly_stats (stat_year, member_id, order_count, total_amount)
SELECT s.stat_year, s.member_id, s.cnt, s.amt
FROM (
    SELECT 2024 AS stat_year, member_id, COUNT(*) AS cnt, SUM(amount) AS amt
    FROM orders
    WHERE member_id BETWEEN 1 AND 5000                      -- 회원 구간을 나눠 여러 번 실행
      AND ordered_at >= '2024-01-01' AND ordered_at < '2025-01-01'
    GROUP BY member_id
) AS s
ON DUPLICATE KEY UPDATE order_count = s.cnt, total_amount = s.amt;

    안쪽 집계는 앞 절의 idx_orders_member_ordered로 스트리밍 집계가 되고, member_id 구간 조건이 range 접근을 만든다. 구간을 나누는 것은 트랜잭션 하나가 너무 커지지 않게 하려는 것으로, 키셋 페이징과 같은 생각이다. 문장 맨 위의 격리 수준 설정이 중요하다. 매뉴얼의 InnoDB 잠금 절은 INSERT INTO T SELECT ... FROM S WHERE ...가 READ COMMITTED에서는 S를 잠금 없는 일관된 읽기로 읽지만, 그 밖의 격리 수준에서는 S에서 읽은 행에 공유 넥스트 키 잠금(shared next-key lock)을 건다고 설명한다. 기본 격리 수준인 REPEATABLE READ로 이 배치를 돌리면, 배치가 훑은 주문 행들과 그 사이의 간격이 배치 트랜잭션이 끝날 때까지 잠긴다. 그동안 그 주문들의 상태를 바꾸는 UPDATE는 배타 잠금을 얻지 못해 기다리고, 잠긴 간격에 들어가야 하는 INSERT도 기다린다. 운영 중인 주문 테이블에서 요약 배치가 주문 처리를 멈춰 세우는 장애가 이렇게 생긴다. 복제 환경이라면 매뉴얼이 INSERT ... SELECT ... ON DUPLICATE KEY UPDATE를 문장 기반 복제에 안전하지 않은 문장으로 표시하며, MIXED 모드에서는 행 기반 형식으로 바이너리 로그에 기록한다는 점도 알아 둔다.

    배치 방식은 대신 신선도를 내준다. 요약은 마지막 배치 시점의 값이다. 화면에 "2025-01-01 03:00 기준" 같은 기준 시각을 함께 보여 주어, 사용자가 무엇을 보고 있는지 알게 하는 것이 정직한 설계다. 또 원본의 과거 행이 바뀌는 경우를 처리해야 한다. 주문은 PAID에서 SHIPPED, DELIVERED로 상태가 바뀌고 취소되기도 한다. 상태별 일별 요약이라면 지난 날짜의 숫자도 계속 변하므로, 배치는 "어제 하루"가 아니라 상태가 아직 바뀔 수 있는 최근 며칠을 매번 다시 계산해야 한다. 주기적으로 원본에서 직접 계산한 값과 요약을 비교하는 검증 쿼리를 돌려 두면, 갱신 로직의 버그가 조용히 쌓이는 것을 막을 수 있다. 배치를 서버 안에서 돌리고 싶다면 이벤트 스케줄러를 쓸 수 있다. 매뉴얼에 따르면 8.0에서 event_scheduler의 기본값은 ON이다. 애플리케이션의 스케줄러로 돌리는 경우가 많지만, 어느 쪽이든 위의 격리 수준과 구간 나누기는 똑같이 필요하다.

    OFFSET 페이징에서 미뤄 둔 전체 건수 문제도 같은 틀에서 풀린다. 페이지 번호를 그리려고 요청마다 PAID 7만 건을 세는 대신, 상태별 건수를 요약에서 읽을 수 있다. 다만 상태별 건수를 주문 트랜잭션마다 즉시 고치면 앞에서 본 핫 행 문제가 그대로 생기므로, 대개는 배치로 계산한 근사값("약 7만 건")을 보여 주거나 건수 표시를 포기하고 키셋의 "다음" 버튼만 두는 쪽을 택한다. 정확한 실시간 건수가 꼭 필요한지는 기술이 아니라 화면 요구 사항의 질문이다.

    주문 트랜잭션이 요약 행을 즉시 고치는 경로와 배치가 구간별로 다시 계산해 덮어쓰는 경로를 나란히 보여 주고, 각 경로의 대가(핫 행 잠금, 신선도와 넥스트 키 잠금)를 표시한다. 가운데 왼쪽에 큰 원통 "orders (100만 행)", 가운데 오른쪽에 작은 원통 "member_yearly_stats (99,991행)". 위쪽 경로: 왼쪽 위의 사람 아이콘들 "주문 트랜잭션"에서 orders로 가는 화살표와, 같은 트랜잭션에서 요약 원통으로 곧장 가는 빨간 화살표, 라벨 "즉시 반영: ON DUPLICATE KEY UPDATE". 빨간 화살표 위에 자물쇠 아이콘과 라벨 "같은 행이면 줄을 선다". 아래쪽 경로: 시계 아이콘 "배치"에서 orders를 구간별로 읽는 점선 화살표(구간 세 칸으로 나뉜 막대 표시)와 요약 원통으로 덮어쓰는 파란 화살표, 라벨 "다시 계산해 덮어쓰기 (READ COMMITTED)". 파란 경로 옆에 작은 시계 라벨 "기준 시각". 오른쪽 끝에 화면 아이콘 "상위 10명 카드"가 요약 원통에서 화살표를 받으며 라벨 "항목 10개 읽기". 흰 배경, 평면 스타일. 사전 집계는 읽을 때의 계산을 쓰기나 배치로 옮긴다. 즉시 반영은 요약 행의 잠금 경합을, 배치는 신선도와 원본 테이블의 잠금 영향을 대가로 치른다.

    쿼리 튜닝의 전체 여정

    이 권의 실전 튜닝 네 번을 한 줄로 이으면 하나의 질문을 네 번 던진 것이다. 결과를 만들려고 몇 개의 행과 페이지를 만졌는가, 그리고 그 수가 결과의 크기에 가까운가, 테이블의 크기에 가까운가. 각 회차는 이 수를 테이블의 크기에서 결과의 크기 쪽으로 한 걸음씩 옮겼다.

    그리고 튜닝은 한 번에 끝나지 않는다. 오늘 고른 계획은 오늘의 데이터 분포와 통계 위에서 고른 것이다(10회). 데이터가 쌓이면 범위의 크기가 변하고, 옵티마이저가 다른 인덱스를 고르기 시작하며, 어제는 메모리에 들어가던 정렬과 임시 테이블이 디스크로 넘친다. 그래서 이 권에서 익힌 도구는 한 번 쓰고 마는 해결책이 아니라 계속 돌려 보는 점검표다. 쿼리가 원하는 순서를 B+Tree가 이미 들고 있는가, 필요한 만큼 읽고 멈출 수 있는가, 읽은 항목에서 행을 다시 찾아가고 있지는 않은가, 그리고 이 질문은 정말로 매번 계산해야 하는 질문인가.

    청크 묶음 하나를 병합하는 merge_buffers() 호출마다 1씩 는다. 0이 아니면 디스크 병합이 있었다는 뜻이고, 처방은 세션 단위로 버퍼를 키우기 전에 정렬 입력을 줄이거나 정렬을 없애는 것이다.
    OFFSET 페이징
    OFFSET만큼의 행을 실제로 만들어 버리므로 비용이 페이지 번호에 비례하고, 요청 사이에 데이터가 바뀌면 행이 중복되거나 빠진다. 전체 건수용 COUNT(*)도 조기 종료 없이 보이는 행을 모두 센다.
    지연 조인
    커버링 인덱스로 기본 키만 골라 위치를 센 뒤 고른 행만 다시 읽는다. LIMIT이 있는 파생 테이블은 병합되지 않고 구체화되며, 버리는 양은 그대로이고 버리는 비용만 줄어든다.
    키셋(커서) 페이징
    직전 페이지 마지막 행의 정렬 키로 다음 위치를 가리켜 B+Tree를 한 번 내려간 뒤 페이지 크기만큼 읽는다. 정렬 키는 유일해야 하고, 조건은 행 생성자 대신 풀어 쓴 OR 형태로 써서 실행 계획으로 확인한다.
    임시 테이블 집계
    입력 행마다 그룹 키로 임시 테이블을 찾아 갱신하거나 삽입하는 차단 연산이다. TempTable 엔진의 메모리 한도를 넘으면 InnoDB 디스크 임시 테이블로 바뀐다.
    스트리밍 집계(타이트 인덱스 스캔)
    그룹 키 순서의 인덱스를 읽으면 같은 그룹이 이웃해 오므로 그룹 하나만 들고 있다가 키가 바뀔 때 내보낸다. GROUP BY 열이 최좌측 접두사이거나 빈틈이 상수 등치로 채워져야 하며, LIMIT에서 일찍 멈출 수 있다.
    루스 인덱스 스캔
    MIN()/MAX()만 쓰는 그룹핑에서 그룹마다 필요한 항목만 읽고 건너뛴다. 그룹이 적고 그룹당 행이 많을수록 이득이 크며 Using index for group-by로 나타난다.
    사전 집계 테이블
    읽을 때 하던 전체 집계를 쓰기 시점이나 배치로 옮긴다. 화면의 질문에서 단위를 정하고 압축률을 확인하며, 즉시 반영은 잠금 경합을, 배치는 신선도와 원본 잠금 문제를 관리해야 한다.

    목록 화면이 "뒤쪽 페이지에서만 느리다"는 신고를 받으면 먼저 OFFSET 값과 실행 계획을 함께 본다. 첫 페이지와 깊은 페이지의 EXPLAIN ANALYZE를 나란히 놓고 인덱스 접근 노드의 실제 행 수가 OFFSET만큼 늘어나는지 확인하면 원인이 확정된다. 처방은 화면 요구 사항에 따라 달라진다. 페이지 번호로 건너뛰는 기능이 꼭 필요하고 깊은 페이지가 드물다면 지연 조인으로 버리는 비용만 줄이는 것으로 충분할 수 있다. 무한 스크롤이나 다음 버튼으로 바꿀 수 있다면 키셋이 근본 해결이다. 배치와 마이그레이션은 예외 없이 키셋으로 나눈다.

    집계 쿼리에서 Using temporary를 보았다고 곧바로 인덱스를 만들 일은 아니다. 그룹이 몇 개인지, LIMIT으로 일찍 멈출 수 있는 쿼리인지가 판단을 가른다. 그룹이 네 개뿐인 상태별 집계라면 임시 테이블은 작고 싸서, 범위 조건으로 입력을 줄이는 인덱스가 더 중요하다. 그룹이 수만 개 이상이고 그룹 키 순서로 페이지를 넘기는 화면이라면 그룹 키를 앞에 둔 커버링 인덱스가 큰 차이를 만든다. 반대로 집계 값으로 순위를 매기는 화면은 인덱스만으로는 전체 읽기를 피할 수 없으므로, 요청 빈도와 허용되는 지연을 따져 사전 집계로 넘어갈지를 정한다.

    사전 집계를 도입할 때의 장애는 대개 성능이 아니라 잠금과 정합성에서 난다. 모든 트랜잭션이 고치는 카운터 행은 동시 주문이 몰리는 순간 처리량을 그 행 하나에 묶어 버리고, 기본 격리 수준으로 돌린 INSERT ... SELECT 배치는 원본 행에 공유 넥스트 키 잠금을 걸어 주문 상태 변경을 멈춰 세울 수 있다. 도입 전에 갱신 경로마다 "어떤 행을 누가 언제 잠그는가"를 적어 보고, 배치는 READ COMMITTED와 구간 나누기로, 요약 값은 주기적인 원본 대조로 지킨다. 숫자가 틀린 대시보드는 느린 대시보드보다 나쁘다.
  • 정렬 버퍼가 넘쳐 청크가 16개 생겼다. merge_many_buff()의 반복 규칙(15개를 넘는 동안, 남은 청크가 10개를 넘으면 일곱 개씩 병합하고 나머지는 한 묶음으로 병합)을 따라 병합 작업을 순서대로 적고, 쿼리 한 번에 Sort_merge_passes가 얼마나 늘어나는지 계산하라. 청크가 15개일 때와 0개일 때도 답하라.
  • PAID 주문 목록(SELECT order_id, member_id, amount, ordered_at, 최신순, 20건씩)의 500번째 페이지를 OFFSET, 지연 조인, 키셋으로 가져올 때 각각 읽는 인덱스 항목 수와 클러스터형 인덱스 룩업 수를 구하라. 또 PAID 주문 7만 건 전체를 20건씩 넘기는 배치를 키셋으로 돌릴 때 읽는 항목 수를 OFFSET의 122,535,000개와 비교하라.
  • 같은 초 10:00:00에 들어온 주문 501, 502, 503번이 있고 정렬은 ordered_at DESC, order_id DESC다. 한 페이지가 503번에서 끝났을 때, 다음 페이지 조건을 (a) ordered_at < '10:00:00', (b) ordered_at <= '10:00:00'으로 쓰면 각각 어떤 행이 잘못되는지 설명하고, 올바른 조건을 써라.

(a) SELECT member_id, SUM(amount) FROM orders WHERE status = 'PAID' GROUP BY member_id (b) SELECT member_id, SUM(amount) FROM orders WHERE status IN ('PAID', 'SHIPPED') GROUP BY member_id (c) SELECT status, MAX(member_id) FROM orders GROUP BY status (d) SELECT status, member_id, SUM(amount) FROM orders GROUP BY status, member_id
  • 주문 트랜잭션마다 daily_order_stats의 (오늘, 'PAID') 행에 order_count = order_count + 1을 하도록 만들었더니, 행사 시간에 주문 API의 응답 시간이 길어지고 교착 상태 로그도 보였다. 잠금 관점에서 원인을 설명하고, 이 설계를 바꾸는 방법을 두 가지 이상 제시하라.
    •

    1번. 16 > 15이므로 루프에 들어간다. 반복문 조건은 i < 16 - 10 = 6이므로 i = 0에서 c0~c6 일곱 개를 병합하고(1회), i = 7은 6보다 크므로 반복을 끝낸다. 나머지 c7~c15 아홉 개를 한 묶음으로 병합하면(2회) 청크가 2개가 되어 루프를 빠져나오고, 마지막으로 merge_index()가 두 청크를 병합한다(3회). 따라서 Sort_merge_passes는 3 늘어난다. 마지막 바퀴 앞의 묶음이 아홉 개인 것은 남은 청크가 너무 적은 묶음으로 쪼개지지 않게 하는 반복 조건 때문이다. 청크가 15개면 루프에 들어가지 않고 마지막 병합 한 번만 하므로 1, 청크가 0개면(모두 메모리에 들어감) 병합 자체가 없으므로 0이다.

    2번. 500번째 페이지의 OFFSET은 499 × 20 = 9,980이다. OFFSET 방식은 인덱스 항목 10,000개를 읽고 항목마다 룩업을 하므로 룩업도 10,000번이다. 지연 조인은 안쪽 커버링 인덱스 쿼리에서 항목 10,000개를 읽지만 룩업은 바깥쪽의 20번뿐이다. 키셋은 B+Tree를 한 번 내려간 뒤 항목 20개를 읽고 룩업 20번을 한다. 전체 배치를 키셋으로 돌리면 3,500페이지 각각이 트리 탐색 한 번과 항목 20개를 읽으므로 항목은 모두 70,000개(+ 탐색 3,500번)다. OFFSET의 122,535,000개와 비교하면 약 1,750분의 1이며, 데이터가 늘어날 때 OFFSET은 제곱으로, 키셋은 선형으로 늘어난다.

    3번. 같은 초의 세 행은 정렬에서 503, 502, 501 순서다. (a) ordered_at < '10:00:00'은 10:00:00인 행을 모두 제외하므로 아직 보여 주지 않은 502번과 501번이 어느 페이지에도 나오지 않는다. (b) <=는 503번까지 다시 포함하므로 503번이 다음 페이지 맨 앞에 중복으로 나온다. 커서에 유일한 꼬리 열을 넣어 status = ? AND (ordered_at < '10:00:00' OR (ordered_at = '10:00:00' AND order_id < 503))으로 쓰고, ORDER BY에도 order_id DESC를 넣어야 한다. 인덱스가 (status, ordered_at)이어도 InnoDB의 인덱스 확장으로 order_id가 순서 안에 있으므로 정렬 단계는 생기지 않는다.

    4번. (a) 상수 등치 status = 'PAID'가 첫 열의 빈틈을 메우므로 타이트 인덱스 스캔으로 스트리밍 집계가 가능하다. SUM이 있으므로 루스 인덱스 스캔은 아니다. (b) IN이 두 구간을 만들어 member_id 순서가 PAID 구간 끝에서 처음으로 돌아가므로 같은 그룹이 이웃해 오지 않는다. 인덱스로 그룹 순서를 얻을 수 없어 임시 테이블 집계(또는 정렬 후 집계)가 된다. (c) GROUP BY가 첫 열이고 집계가 바로 다음 열의 MAX 하나뿐이므로 루스 인덱스 스캔의 조건을 만족한다. 상태마다 구간의 마지막 항목만 읽으면 된다. (d) GROUP BY가 최좌측 접두사 두 열이므로 인덱스 전체를 읽는 타이트 인덱스 스캔이 가능하다. SUM이 있어 루스는 아니다. 어느 경우든 성립 조건은 "가능하다"는 뜻이고, 실제 선택은 비용으로 정해지므로 EXPLAIN으로 확인한다. 실습 데이터에 이 인덱스를 만들어 MySQL 8.4.13에서 확인하면 (a)는 Covering index lookup 위의 Group aggregate(Extra Using index), (b)는 Aggregate using temporary table(Extra Using where; Using index; Using temporary), (c)는 Covering index skip scan for grouping(Extra Using index for group-by), (d)는 Covering index scan 위의 Group aggregate(Extra Using index)로, 판정과 같았다.

    5번. UPDATE는 갱신할 행에 배타 잠금을 걸고 트랜잭션이 끝날 때까지 유지한다. 오늘의 PAID 행 하나를 모든 주문 트랜잭션이 고치므로, 동시에 들어온 주문들은 그 행의 잠금을 차례로 얻으려고 줄을 선다. 처리량의 상한이 트랜잭션 하나의 길이로 정해지고, 트랜잭션 안에 다른 작업(재고 차감, 외부 호출)이 있을수록 더 나빠진다. 상태 변경 시 두 요약 행을 서로 다른 순서로 잠그는 트랜잭션이 섞이면 교착 상태가 생긴다. 바꾸는 방법은 (1) 요약을 주문 트랜잭션에서 떼어 배치로 다시 계산하고 기준 시각을 표시하기, (2) 요약 행을 여러 칸으로 나눠(예: 슬롯 열을 두고 주문 번호로 칸을 골라 더한 뒤 읽을 때 합산) 같은 행에 몰리는 쓰기를 분산하기, (3) 변경 이벤트를 큐에 쌓아 하나의 작업자가 모아서 반영하기 등이다. 여러 행을 잠가야 한다면 항상 같은 순서(예: 키 순서)로 잠그는 것도 교착 상태를 줄인다.

     어떤 정렬 쿼리를 실행한 뒤 세션의 Sort_merge_passes가 정확히 1 늘었다. 이 사실에서 확실히 말할 수 있는 것은? 정렬 버퍼 안에서 모든 정렬이 끝났다. 정렬 버퍼가 넘쳐 청크가 디스크로 나갔고, 청크 수가 15개 이하라 마지막 병합 한 번으로 끝났다. 데이터 전체를 디스크에서 정확히 한 번 읽었으므로 청크는 정확히 두 개였다. LIMIT 때문에 우선순위 큐를 써서 병합이 한 번 필요했다. Sort_merge_passes는 merge_buffers()가 불릴 때마다 증가한다. 모든 행이 메모리에 들어가면 병합 자체가 없어 0이다. 1이라면 청크가 디스크로 나갔고, 15개를 넘지 않아 중간 병합 없이 merge_index()의 마지막 병합 한 번으로 끝났다는 뜻이다. 청크가 2개인지 15개인지는 이 값만으로 알 수 없다. 우선순위 큐는 상위 N개를 메모리에 들고 정렬하는 방식으로, 병합을 만들어 내는 원인이 아니다. PAID 주문 목록의 1,000번째 페이지를 OFFSET 대신 지연 조인으로 바꿨다. 줄어드는 것은 무엇인가? 읽는 세컨더리 인덱스 항목의 수 OFFSET으로 건너뛰는 행의 수 버려질 행 때문에 일어나던 클러스터형 인덱스 룩업 최종 결과를 정렬하는 단계 지연 조인의 안쪽 쿼리는 커버링 인덱스로 기본 키만 고르므로, 위치를 세며 버리는 19,980행에 대해 클러스터형 인덱스를 찾아가지 않는다. 룩업은 바깥쪽의 20번만 남는다. 그러나 인덱스 항목은 여전히 20,000개를 읽고 건너뛰는 행 수도 그대로다. 바깥 쿼리에는 오히려 20행짜리 정렬이 하나 붙는다. 건너뛰는 양 자체를 없애려면 키셋 페이징이 필요하다. 키셋 조건을 WHERE status = 'PAID' AND (ordered_at, order_id) < (?, ?) 대신 WHERE status = 'PAID' AND (ordered_at < ? OR (ordered_at = ? AND order_id < ?))로 쓰라고 권하는 이유로 가장 알맞은 것은? 매뉴얼의 예처럼 행 생성자를 AND와 섞으면 인덱스의 앞 열만 쓰이는 등 인덱스 사용이 덜 완전해질 수 있고, 풀어 쓴 형태는 더 많은 키 부분을 범위에 쓸 수 있기 때문이다. MySQL은 행 생성자 비교를 문법 오류로 거부하기 때문이다. 두 형태는 의미가 달라서, 행 생성자 형태는 동률인 행을 중복으로 돌려주기 때문이다. 풀어 쓴 형태는 인덱스 확장을 꺼서 기본 키 열이 범위에 쓰이지 않게 하기 때문이다. 두 형태는 의미가 같고 행 생성자 비교도 문법적으로 허용된다. 매뉴얼의 행 생성자 최적화 절은 c1 = 1 AND (c2, c3) > (1, 1)이 기본 키의 c1만 써서 ref 접근이 된 반면, 풀어 쓴 형태는 세 열을 모두 쓰는 range 접근이 된 예를 보여 주며 행 생성자와 AND/OR를 섞지 말라고 권한다. 인덱스 확장은 오히려 order_id를 범위에 쓰게 해 주는 장치다. 회원별 통계 목록 쿼리(GROUP BY member_id ORDER BY member_id LIMIT 20)에 (member_id, ordered_at, amount) 인덱스를 추가하자 100만 행을 읽던 쿼리가 수백 개 항목만 읽게 되었다. 이 변화의 핵심 이유는? 인덱스가 그룹별 합계를 미리 저장하고 있어서 읽기만 하면 된다. 루스 인덱스 스캔이 그룹마다 항목 하나씩만 읽기 때문이다. 임시 테이블이 메모리에 들어가게 되어 디스크 I/O가 사라졌기 때문이다. 같은 회원의 항목이 이웃해 와서 스트리밍 집계가 그룹을 하나씩 바로 내보내고, LIMIT이 20개를 채우는 순간 아래쪽 읽기를 멈추기 때문이다. 인덱스는 합계를 저장하지 않는다. 합계는 여전히 그룹의 항목을 모두 읽어 계산한다. SUM과 COUNT가 있으므로 루스 인덱스 스캔의 조건(MIN/MAX만)도 만족하지 않는다. 이 계획에는 임시 테이블 자체가 없다. 그룹 키 순서로 읽으니 집계가 파이프라인이 되었고, 위의 LIMIT이 필요한 그룹 수를 채우면 더 읽지 않는 것이 핵심이다. 실습 데이터에서 첫 페이지는 인덱스 항목 206개로 끝난다. 요약 테이블을 다시 만드는 INSERT INTO summary SELECT ... FROM orders WHERE ... GROUP BY ... 배치를 기본 격리 수준(REPEATABLE READ)으로 돌렸더니, 배치가 도는 동안 주문 상태 변경이 대기에 걸렸다. 가장 직접적인 원인은? INSERT ... SELECT는 항상 테이블 전체에 테이블 잠금을 걸기 때문이다. 요약 테이블의 기본 키에 걸린 배타 잠금이 orders에도 전파되기 때문이다. READ COMMITTED가 아닌 격리 수준에서는 InnoDB가 원본 테이블에서 읽은 행에 공유 넥스트 키 잠금을 걸어, 그 행을 바꾸려는 UPDATE가 배치 트랜잭션이 끝날 때까지 기다리기 때문이다. GROUP BY가 임시 테이블을 만들면서 orders를 잠그기 때문이다. 매뉴얼의 InnoDB 잠금 절에 따르면 INSERT INTO T SELECT ... FROM S는 READ COMMITTED에서는 S를 잠금 없는 일관된 읽기로 읽고, 그 밖의 격리 수준에서는 S의 행에 공유 넥스트 키 잠금을 건다. 상태를 바꾸는 UPDATE는 배타 잠금이 필요하므로 공유 잠금이 풀릴 때까지 기다린다. 테이블 잠금이나 잠금의 전파, 임시 테이블이 원본을 잠그는 동작은 이 현상의 원인이 아니다. 배치 세션을 READ COMMITTED로 돌리고 구간을 나눠 트랜잭션을 짧게 하는 것이 처방이다.
    외부 병합 정렬(external merge sort)
    메모리에 다 들어가지 않는 데이터를 버퍼 크기만큼씩 정렬해 청크로 디스크에 쓴 뒤, 정렬된 청크들을 병합해 전체 순서를 만드는 정렬 방식. MySQL filesort가 버퍼를 넘칠 때 쓴다.
    병합 패스(merge pass)
    여러 정렬된 청크를 하나로 합치는 작업. MySQL의 Sort_merge_passes는 청크 묶음 하나를 병합할 때마다 1씩 증가한다.
    지연 조인(deferred join)
    커버링 인덱스로 필요한 행의 기본 키만 먼저 고르고, 고른 행만 기본 키로 다시 읽어 행 전체를 만드는 쿼리 작성 기법.
    키셋 페이징(keyset pagination)
    직전 페이지 마지막 행의 정렬 키 값을 커서로 삼아, 그 값 바로 다음부터 페이지 크기만큼 읽는 페이징 방식. 커서 기반 페이징이라고도 한다.
    파생 테이블(derived table)
    FROM 절에 쓴 서브쿼리의 결과 테이블. 옵티마이저는 이를 바깥 쿼리에 병합하거나 내부 임시 테이블로 구체화하며, LIMIT이나 집계가 있으면 병합하지 않는다.
    내부 임시 테이블(internal temporary table)
    서버가 쿼리 처리 중에 스스로 만드는 임시 테이블. 8.0에서는 메모리에서 TempTable 엔진으로 만들고, 한도를 넘으면 InnoDB 디스크 테이블로 바꾼다.
    타이트 인덱스 스캔(tight index scan)
    그룹 키 순서의 인덱스를 범위 안에서 빠짐없이 읽으며 그룹을 만드는 GROUP BY 처리 방식. 같은 그룹이 이웃해 오므로 스트리밍 집계가 된다.
    루스 인덱스 스캔(loose index scan)
    MIN()/MAX()만 필요한 그룹핑에서 그룹마다 필요한 인덱스 항목만 읽고 다음 그룹으로 건너뛰는 처리 방식. EXPLAIN에 Using index for group-by로 나타난다.
    스트리밍 집계(streaming aggregation)
    그룹 키 순서로 정렬된 입력을 받아 현재 그룹 하나의 중간값만 들고 있다가 키가 바뀔 때 결과를 내보내는 집계. MySQL 실행기에서는 AggregateIterator가 맡는다.
    사전 집계 테이블(summary table)
    원본 데이터의 집계 결과를 미리 저장해 두는 일반 테이블. 원본이 바뀔 때 즉시 또는 배치로 갱신해야 하며, 그 갱신 경로와 정합성은 애플리케이션이 책임진다.
