    이번 회차에서 하는 일

    지금까지 이 권은 로그 추적기를 들고 한 층씩 내려왔다. 05회에서는 ProxyFactory가 JDK 동적 프록시와 CGLIB 중 하나를 골라 프록시를 만들고, 포인트컷(어디에)과 어드바이스(무엇을)를 묶은 어드바이저(advisor)를 받는 구조를 봤다. 06회에서는 빈 후처리기(BeanPostProcessor)가 컨테이너에 등록되는 빈을 가로채 프록시로 바꿔 치우는 과정을, 07회에서는 @Aspect가 붙은 클래스가 자동 프록시 생성기에 의해 어드바이저로 바뀐다는 사실과 조인 포인트·포인트컷·어드바이스·애스펙트·위빙 같은 AOP 용어를 정리했다.

    이번 회차는 그 위에서 애스펙트를 직접 여러 번 고쳐 쓰는 회차다. 애스펙트 하나에 @Around 하나로 시작해서, 포인트컷을 이름 붙여 떼어 내고, 어드바이스를 하나 더 붙이고, 포인트컷을 다른 클래스로 옮기고, 애스펙트 둘의 순서를 정하고, 마지막으로 다섯 가지 어드바이스 종류를 모두 써 본다. 단계마다 코드가 조금씩 바뀌는데, 그때마다 두 가지 질문을 던진다. 출력이 왜 이 순서로 나오는가, 그리고 컨테이너 안에서 무엇이 달라졌는가.

    이 두 질문의 답은 결국 한 가지 구조로 모인다. 애스펙트 클래스의 어드바이스 메서드 하나하나가 어드바이저 하나가 되고, 어드바이저들이 정해진 규칙으로 정렬되어 프록시 안에서 인터셉터 체인(interceptor chain)을 이루며, 메서드 호출 하나가 그 체인을 앞에서부터 한 칸씩 통과한다. "어드바이스 순서"와 "어드바이스 종류"라는 두 주제는 따로 외울 규칙이 아니라 이 체인이 만들어지는 방식과 체인 안에서 각 인터셉터가 proceed()를 부르는 위치에서 나오는 결과다. 이번 회차의 목표는 그 연결을 실행 결과와 소스 코드로 확인하는 것이다.

    이 회차의 실행 결과는 원고를 쓰면서 JDK 21.0.13(Temurin), 스프링 프레임워크 6.2.19(spring-aop, spring-context), AspectJ 1.9.25.1(aspectjweaver)로 직접 돌려 얻었다. 부트 애플리케이션 대신 AnnotationConfigApplicationContext에 @EnableAspectJAutoProxy(proxyTargetClass = true)를 붙여 실행했는데, 이 설정은 아래에서 보듯 스프링 부트 3.5의 AOP 자동 구성이 기본으로 켜는 것과 같다. 스프링 내부 클래스의 소스는 7.0.10 소스 JAR에서 읽었고, 6.2.19에서도 같게 동작하는지는 실행 결과와 바이트코드로 확인했다. 내부 클래스 이름과 구조는 공개 API가 아니므로 버전에 따라 달라질 수 있다.

    프로젝트 준비 — 의존성 한 줄이 가져오는 것

    스프링 부트 3.x 프로젝트에서 @Aspect를 쓰려면 빌드 파일에 스타터 하나를 추가한다. 스프링 부트 4.0부터는 이 스타터의 이름이 바뀌었다. 4.0 마이그레이션 가이드는 쓰임새를 분명히 하려고 spring-boot-starter-aop를 spring-boot-starter-aspectj로 바꿨다고 적고 있다.

    // plugins { ... } 는 생략: org.springframework.boot, io.spring.dependency-management, java
dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-aop'      // 부트 3.x
    // implementation 'org.springframework.boot:spring-boot-starter-aspectj' // 부트 4.x
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

    이 한 줄이 실제로 끌어오는 것을 보자. Maven Central에 올라간 spring-boot-starter-aop 3.5.0의 POM을 열면 의존성은 셋뿐이다. spring-boot-starter, spring-aop, 그리고 org.aspectj:aspectjweaver다. spring-aop는 05회부터 써 온 ProxyFactory, 어드바이저, 자동 프록시 생성기가 들어 있는 스프링 자신의 모듈이다. 새로 들어오는 것은 aspectjweaver 하나인데, 이름에 "weaver"가 들어 있어서 오해를 부르기 쉽다.

    스프링 AOP는 이 JAR에서 컴파일러나 위버를 쓰지 않는다. 스프링 레퍼런스는 @AspectJ 지원을 설명하면서 스프링이 AspectJ 5와 같은 애노테이션을 해석하고 포인트컷 파싱과 매칭에 AspectJ가 제공하는 라이브러리를 쓰지만, "The AOP runtime is still pure Spring AOP"(Spring Framework Reference, @AspectJ support)라고 못 박는다. 실제로 이 JAR에서 스프링이 가져다 쓰는 것을 꼽아 보면 세 가지다.

    • 애노테이션과 조인 포인트 타입: @Aspect, @Around, @Pointcut 같은 애노테이션(org.aspectj.lang.annotation)과 JoinPoint, ProceedingJoinPoint(org.aspectj.lang)가 모두 aspectjweaver JAR 안에 있다. 이 JAR가 없으면 애스펙트 클래스가 컴파일되지 않는다.
    • 포인트컷 식의 파서와 매처: 스프링의 AspectJExpressionPointcut은 org.aspectj.weaver.tools 패키지의 파서로 문자열을 해석하고, 클래스와 메서드가 식에 맞는지 판정한다.
    • 부분 순서 정렬: 어드바이저를 정렬하는 AspectJAwareAdvisorAutoProxyCreator가 org.aspectj.util.PartialOrder를 쓴다. 이 정렬은 뒤에서 어드바이스 순서를 다룰 때 다시 나온다.

    다음은 부트의 자동 구성이다. 스프링 부트 3.5.16의 AopAutoConfiguration을 javap로 열어 붙어 있는 조건을 읽으면 아래 표가 된다. 부트 레퍼런스도 같은 내용을 "AspectJ가 클래스패스에 있으면 @EnableAspectJAutoProxy가 필요 없고, 기본은 CGLIB 프록시이며, JDK 프록시를 쓰려면 spring.aop.proxy-target-class를 false로 둔다"는 문장으로 설명한다.

    조건결과
    spring.aop.auto가 true이거나 없음(기본 true)AopAutoConfiguration 전체가 활성화된다.
    클래스패스에 org.aspectj.weaver.Advice가 있음(aspectjweaver가 있음)@EnableAspectJAutoProxy가 붙은 설정이 켜져 AnnotationAwareAspectJAutoProxyCreator가 등록된다. @Aspect 빈이 처리되는 것은 이 경우뿐이다.
    위 조건에서 spring.aop.proxy-target-class가 true이거나 없음(기본 true)proxyTargetClass = true가 되어 인터페이스가 있는 빈도 CGLIB 하위 클래스 프록시로 만든다.
    org.aspectj.weaver.Advice가 없고 spring.aop.proxy-target-class가 true이거나 없음AopConfigUtils.registerAutoProxyCreatorIfNecessary로 인프라용 자동 프록시 생성기만 등록하고 클래스 프록시를 강제한다. @Transactional 같은 스프링 내장 어드바이저는 동작하지만 @Aspect 클래스는 처리되지 않는다.

    마지막으로 컴파일 옵션 하나를 짚어 둔다. 어드바이스 메서드의 매개변수는 뒤에서 보듯 이름으로 값을 받는 경우가 있다(returning = "result" 같은 속성). 자바 컴파일러는 기본적으로 매개변수 이름을 클래스 파일의 MethodParameters 속성에 남기지 않고, javac -parameters를 줘야 남긴다. 스프링 부트 그레이들 플러그인은 자바 플러그인이 적용되면 모든 JavaCompile 태스크에 -parameters를 붙이도록 구성한다(Spring Boot Gradle Plugin Reference, Reacting to the Java Plugin). 이 회차의 실험도 -parameters로 컴파일했다. 이 옵션이 없어도 스프링이 포인트컷 식과 returning·throwing 속성에서 이름을 추론하는 탐색기(AspectJAdviceParameterNameDiscoverer)를 마지막 수단으로 갖고 있지만, 레퍼런스가 권하는 방법은 -parameters다.

    예제 도메인 — 두 계층과 예외 경로

    예제는 재고 예약을 흉내 내는 두 클래스다. 서비스가 리포지토리를 호출하는 두 계층 구조를 가져야 포인트컷이 어느 계층에 걸리는지 보이고, 특정 입력에서 예외를 던져야 예외 흐름에서 어드바이스가 어떻게 움직이는지 보인다. 그래서 "ghost"라는 상품 코드가 들어오면 리포지토리가 예외를 던지게 했다.

    package lab.inventory;

import org.springframework.stereotype.Repository;

@Repository
public class StockRepository {
    public String reserve(String sku) {
        System.out.println("  [repository] reserve 실행 sku=" + sku);
        if (sku.equals("ghost")) {
            throw new IllegalArgumentException("없는 상품: " + sku);
        }
        return "reserved:" + sku;
    }

    public int count(String sku) {
        return 7;
    }
}
    package lab.inventory;

import org.springframework.stereotype.Service;

@Service
public class StockService {
    private final StockRepository repository;

    public StockService(StockRepository repository) {
        this.repository = repository;
    }

    public String place(String sku) {
        System.out.println("  [service] place 실행 sku=" + sku);
        return repository.reserve(sku);
    }
}

    실험 하네스는 컨테이너를 만들 때마다 애스펙트 클래스를 바꿔 끼울 수 있게 했다. 컨테이너에 두 도메인 클래스와 설정 클래스, 그리고 인자로 받은 애스펙트 클래스를 등록하고 refresh()를 부른다. register()로 넘긴 클래스는 컴포넌트 스캔 없이 곧바로 빈이 된다.

    package lab;

import lab.inventory.StockRepository;
import lab.inventory.StockService;
import org.springframework.aop.support.AopUtils;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableAspectJAutoProxy;

public class Main {
    @Configuration
    @EnableAspectJAutoProxy(proxyTargetClass = true) // 부트 자동 구성이 해 주는 일
    static class Config {}

    static AnnotationConfigApplicationContext ctx(Class... aspects) {
        AnnotationConfigApplicationContext c = new AnnotationConfigApplicationContext();
        c.register(Config.class, StockRepository.class, StockService.class);
        if (aspects.length > 0) c.register(aspects); // 빈 배열을 넘기면 register()가 예외를 던진다
        c.refresh();
        return c;
    }

    static void run(Class... aspects) {
        try (var c = ctx(aspects)) {
            StockService s = c.getBean(StockService.class);
            System.out.println("proxy? " + AopUtils.isAopProxy(s) + " class=" + s.getClass().getName());
            System.out.println("-- 성공");
            System.out.println("result=" + s.place("apple"));
            System.out.println("-- 실패");
            try { s.place("ghost"); } catch (Exception e) { System.out.println("caller got " + e); }
        }
    }
    // main()은 각 절에서 run(애스펙트 클래스...)를 부른다
}

    애스펙트 없이 실행하면 서비스 빈은 원래 클래스 그대로다. proxy? false class=lab.inventory.StockService가 찍히고, 그 뒤로 [service]와 [repository] 두 줄만 나온다. 이제 이 상태에서 애스펙트를 하나씩 더해 간다.

    첫 번째 애스펙트 — @Around 하나

    가장 단순한 애스펙트는 어드바이스 메서드 하나로 이루어진다. 아래 클래스는 lab.inventory 패키지와 그 하위 패키지에 있는 모든 메서드 실행 앞에 시그니처를 찍고, 진짜 메서드를 호출한 결과를 그대로 돌려준다.

    package lab.aop;

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;

@Aspect
public class TraceAspectV1 {
    @Around("execution(* lab.inventory..*(..))")
    public Object trace(ProceedingJoinPoint joinPoint) throws Throwable {
        System.out.println("[trace] " + joinPoint.getSignature());
        return joinPoint.proceed();
    }
}

    코드의 각 부분이 하는 일을 정리하면 이렇다. @Aspect는 이 클래스가 애스펙트라는 표시다. @Around의 값은 포인트컷 식이고, 이 식에 맞는 메서드 실행이 이 어드바이스의 적용 대상이 된다. 어라운드 어드바이스는 첫 번째 매개변수로 ProceedingJoinPoint를 받아야 하며, 그 객체의 proceed()를 불러야 다음 어드바이스나 진짜 메서드로 넘어간다. proceed()의 반환값을 돌려주는 것도 중요하다. 레퍼런스의 말대로 어라운드 어드바이스가 돌려준 값이 곧 호출자가 받는 반환값이기 때문이다.

    클래스 이름의 $$SpringCGLIB$$0은 04회에서 본 CGLIB 하위 클래스다. 뒤의 숫자는 같은 클래스에 대해 몇 번째로 만든 프록시인지에 따라 붙으므로 실행 환경과 순서에 따라 달라진다. 서비스와 리포지토리 둘 다 포인트컷에 걸리므로 둘 다 프록시가 되었고, 그래서 [trace]가 계층마다 한 번씩 찍혔다. 서비스 프록시가 원본 서비스에 호출을 넘기면, 원본 서비스 안의 repository 필드에는 리포지토리 프록시가 주입되어 있으므로 리포지토리 호출에서도 어드바이스가 실행된다.

    @Aspect만으로는 빈이 되지 않는다

    위 실험은 register()로 애스펙트 클래스를 직접 빈으로 등록했다. 컴포넌트 스캔에 맡긴다면 사정이 다르다. 레퍼런스는 @Aspect 애노테이션만으로는 클래스패스 자동 감지에 충분하지 않으니 @Component를 따로 붙이라고 적고 있다. @Aspect는 AspectJ 라이브러리의 애노테이션이고, 스프링의 컴포넌트 스캐너가 찾는 것은 @Component와 그것을 메타 애노테이션으로 가진 스테레오타입이기 때문이다. 실제로 @Aspect만 붙인 클래스를 스캔 대상 패키지에 두고 @ComponentScan으로 컨테이너를 띄우면, 그 타입의 빈 이름 목록은 빈 배열([])이고 서비스는 프록시가 되지 않았다. 애스펙트를 빈으로 만드는 방법은 셋이다. 클래스에 @Component를 붙이거나, 설정 클래스의 @Bean 메서드로 등록하거나, @Import로 가져온다.

    컨테이너 안에서 일어난 일

    06·07회에서 본 흐름을 이번 실험에 맞춰 다시 짚는다. 이번 회차에서 중요한 것은 3단계와 4단계, 즉 어드바이저를 고르고 정렬하는 부분이다.

    2단계에서 하나 더 볼 것이 있다. 애스펙트 빈 자신은 프록시 대상에서 빠진다. AnnotationAwareAspectJAutoProxyCreator는 isInfrastructureClass()를 재정의해 @Aspect 타입을 인프라 클래스로 취급한다. 레퍼런스도 스프링 AOP에서는 애스펙트가 다른 애스펙트의 어드바이스 대상이 될 수 없고, @Aspect가 붙은 클래스는 자동 프록시에서 제외된다고 적는다. 이것을 확인하려고 execution(* lab..*(..))처럼 애스펙트 클래스 자신의 패키지까지 덮는 포인트컷을 가진 애스펙트를 만들어 봤다. 애스펙트 빈에 AopUtils.isAopProxy를 물으면 false였고, 애스펙트의 다른 공개 메서드를 불러도 어드바이스는 실행되지 않았다. 같은 컨테이너의 리포지토리 메서드에는 정상적으로 적용됐다.

    포인트컷 분리 — @Pointcut으로 이름 붙이기

    첫 번째 애스펙트에서 포인트컷 식은 어드바이스 애노테이션 안에 문자열로 박혀 있다. 어드바이스가 늘어나 같은 식을 여러 번 써야 하면 오타 하나가 적용 범위를 바꾼다. 그래서 식에 이름을 붙여 따로 선언하는 방법이 있다.

    @Aspect
public class TraceAspectV2 {
    @Pointcut("execution(* lab.inventory..*(..))")
    private void inventory() {} // 포인트컷 시그니처

    @Around("inventory()")
    public Object trace(ProceedingJoinPoint joinPoint) throws Throwable {
        System.out.println("[trace] " + joinPoint.getSignature());
        return joinPoint.proceed();
    }
}

    실행 결과는 첫 번째 애스펙트와 글자 하나까지 같다(프록시 클래스 이름의 숫자만 다르다). 달라진 것은 선언 방식이다. 레퍼런스는 포인트컷 선언이 두 부분으로 이루어진다고 설명한다. 이름과 매개변수로 이루어진 시그니처(signature), 그리고 관심 있는 메서드 실행을 정확히 고르는 포인트컷 식(pointcut expression)이다. @AspectJ 방식에서는 일반 메서드 정의가 시그니처 역할을 하고, 그 메서드에 붙인 @Pointcut의 값이 식이 된다. 시그니처로 쓰는 메서드는 반환 타입이 반드시 void여야 한다.

    이 메서드의 본문은 실행되지 않는다. 메서드는 오직 이름표로만 쓰이기 때문이다. 스프링 소스에서도 이 점이 드러난다. ReflectiveAspectJAdvisorFactory는 애스펙트 클래스의 메서드를 훑을 때 @Pointcut이 붙은 메서드를 처음부터 걸러 낸다(소스의 주석이 "Exclude @Pointcut methods"다). 따라서 @Pointcut 메서드는 어드바이저가 되지 않고, 프록시 체인에도 들어가지 않는다. 남는 것은 "inventory()라는 이름은 이 식을 뜻한다"는 정보뿐이고, 이 정보는 AspectJ 파서가 "inventory()"라는 참조를 해석할 때 쓰인다.

    접근 제어자는 참조할 수 있는 범위를 정한다. 레퍼런스는 이름으로 포인트컷을 참조할 때 보통의 자바 가시성 규칙이 적용된다고 적는다. private 포인트컷은 같은 타입 안에서, protected는 상속 계층에서, public은 어디서나 볼 수 있다. 그리고 가시성은 포인트컷 매칭에는 영향을 주지 않는다. 포인트컷 메서드를 private으로 선언했다고 해서 private 메서드만 고르게 되는 것이 아니라는 뜻이다. 무엇을 고르는지는 오직 식이 정한다.

    식을 아주 조금만 읽어 두기

    포인트컷 식의 문법은 09회에서 지정자별로 자세히 다룬다. 이번 회차에서 쓰는 식을 읽을 수 있을 만큼만 정리하면, execution(반환타입 선언타입.메서드이름(매개변수)) 꼴이고 *는 아무 이름 하나, 매개변수 자리의 (..)는 개수와 타입을 따지지 않는다는 뜻이다. 패키지 자리의 ..는 하위 패키지까지 포함한다. 이 차이를 AspectJExpressionPointcut에 직접 물어보면 결과가 이렇다.

    execution(* lab.inventory.*.*(..))truetruefalse

    마지막 식의 *..*Service는 "어느 패키지에 있든 이름이 Service로 끝나는 타입"이다. 다음 절에서 이 식으로 서비스 계층만 골라 낸다.

    어드바이스 추가 — 두 번째 @Around와 포인트컷 조합

    로그 추적 말고 트랜잭션 흉내를 내는 어드바이스를 하나 더 붙여 보자. 진짜 트랜잭션이 아니라, 시작·커밋·롤백·정리 시점을 출력만 하는 어드바이스다. 적용 범위는 "lab.inventory 아래이면서 이름이 Service로 끝나는 타입"으로 좁힌다. 이름 붙인 포인트컷은 &&(그리고), ||(또는), !(아님)으로 조합할 수 있다.

    @Aspect
public class TraceTxAspectV3 {
    @Pointcut("execution(* lab.inventory..*(..))")
    private void inventory() {}

    @Pointcut("execution(* *..*Service.*(..))")
    private void service() {}

    @Around("inventory()")
    public Object trace(ProceedingJoinPoint joinPoint) throws Throwable {
        System.out.println("[trace] " + joinPoint.getSignature());
        return joinPoint.proceed();
    }

    @Around("inventory() && service()")
    public Object tx(ProceedingJoinPoint joinPoint) throws Throwable {
        try {
            System.out.println("[tx] 시작 " + joinPoint.getSignature());
            Object result = joinPoint.proceed();
            System.out.println("[tx] 커밋 " + joinPoint.getSignature());
            return result;
        } catch (Exception e) {
            System.out.println("[tx] 롤백 " + joinPoint.getSignature());
            throw e;
        } finally {
            System.out.println("[tx] 정리 " + joinPoint.getSignature());
        }
    }
}

    결과를 한 줄씩 읽어 보자. 서비스 메서드에는 두 어드바이스가 모두 걸리고, 리포지토리 메서드에는 trace만 걸린다. 리포지토리는 service() 조건을 만족하지 못하기 때문이다. 실패 흐름에서는 리포지토리가 던진 예외가 리포지토리 프록시를 지나 원본 서비스로, 다시 서비스 프록시 안의 tx 어드바이스로 올라온다. tx의 catch가 "롤백"을 찍고 예외를 다시 던지고, finally가 "정리"를 찍은 뒤, 예외는 trace를 그대로 지나 호출자에게 도착한다. trace에는 try가 없으므로 예외가 지나갈 때 아무것도 찍지 않는다.

    왜 trace가 tx보다 먼저 실행됐는가

    여기서 질문 하나가 생긴다. 서비스 메서드에서 [trace]가 [tx] 시작보다 먼저 찍혔다. 즉 trace가 바깥, tx가 안쪽에서 실행됐다. 소스에서 trace를 먼저 선언했기 때문일까? 그렇지 않다. 같은 애스펙트 안에서 어드바이스 메서드의 순서는 스프링이 리플렉션으로 메서드를 모은 뒤 정렬해서 정한다. ReflectiveAspectJAdvisorFactory의 정적 초기화 블록에 그 비교자가 있다.

    // spring-aop 7.0.10 ReflectiveAspectJAdvisorFactory 에서 발췌(제네릭 인자와 람다 본문은 줄임)
Comparator adviceKindComparator = new ConvertingComparator<>(
        new InstanceComparator<>(
                Around.class, Before.class, After.class, AfterReturning.class, AfterThrowing.class),
        method -> { /* 메서드에 붙은 AspectJ 어드바이스 애노테이션을 찾는다 */ });
Comparator methodNameComparator = new ConvertingComparator<>(Method::getName);
adviceMethodComparator = adviceKindComparator.thenComparing(methodNameComparator);

    첫 번째 기준은 어드바이스 종류이고, 종류가 같으면 메서드 이름의 사전순이 두 번째 기준이다. trace와 tx는 둘 다 @Around이므로 이름으로 갈리는데, 두 번째 글자 r이 x보다 앞이라 trace가 먼저 온다. 6.2.19의 바이트코드에도 같은 비교자(InstanceComparator와 Method.getName 호출)가 들어 있다. 이를 확인하려고 @Around 메서드 두 개를 b, a 순서로 선언한 애스펙트를 실행해 봤더니 출력은 선언 순서와 반대로 [a], [b]였다.

    그렇다면 이름을 잘 지어 순서를 정하면 될까? 레퍼런스의 답은 분명하다. 같은 @Aspect 클래스 안에서 같은 종류의 어드바이스 두 개가 같은 조인 포인트에 적용될 때 순서는 정의되어 있지 않다. 이유도 적혀 있다. javac로 컴파일한 클래스에서는 리플렉션으로 소스의 선언 순서를 알아낼 방법이 없기 때문이다. 실제로 Class.getDeclaredMethods()의 Javadoc은 돌려주는 배열의 원소가 정렬되어 있지 않고 특정한 순서도 없다고 적고 있다. 스프링 소스의 주석은 5.2.7 이전에는 메서드 목록에서의 위치를 선언 순서처럼 썼지만, JDK가 더는 소스 순서대로 메서드를 돌려주지 않아 이 값을 모든 어드바이스에 대해 0으로 고정했다고 설명한다. 메서드 이름 비교는 실행할 때마다 순서가 흔들리지 않게 하려는 구현상의 장치일 뿐 문서가 약속한 계약이 아니다.

    이 절의 핵심

    같은 애스펙트 안에서 어드바이스 사이의 순서를 통제할 수단은 없다. 순서가 의미 있는 두 부가 기능(예: 트랜잭션 바깥에서 로그를 남겨야 한다)이라면, 레퍼런스가 권하는 대로 하나의 어드바이스로 합치거나 별도의 애스펙트 클래스로 나눠 애스펙트 단위로 순서를 준다.

    포인트컷 참조 — 포인트컷을 모아 두는 클래스

    포인트컷을 이름으로 분리하니 한 애스펙트 안에서는 중복이 사라졌다. 하지만 애스펙트가 여러 개가 되면 "lab.inventory 아래 전부"나 "서비스 계층" 같은 정의를 애스펙트마다 다시 쓰게 된다. 레퍼런스는 이런 경우 자주 쓰는 이름 붙은 포인트컷을 모아 두는 전용 클래스를 따로 만들라고 권하고, 그 클래스의 완전한 이름(fully-qualified name)과 @Pointcut 메서드 이름을 이어 쓰면 포인트컷 식이 필요한 어디서든 참조할 수 있다고 설명한다.

    package lab.aop;

import org.aspectj.lang.annotation.Pointcut;

public class Pointcuts {
    @Pointcut("execution(* lab.inventory..*(..))")
    public void inventory() {}

    @Pointcut("execution(* *..*Service.*(..))")
    public void service() {}

    @Pointcut("inventory() && service()")
    public void inventoryService() {}
}
    @Aspect
public class TraceTxAspectV4 {
    @Around("lab.aop.Pointcuts.inventory()")
    public Object trace(ProceedingJoinPoint joinPoint) throws Throwable {
        System.out.println("[trace] " + joinPoint.getSignature());
        return joinPoint.proceed();
    }

    @Around("lab.aop.Pointcuts.inventoryService()")
    public Object tx(ProceedingJoinPoint joinPoint) throws Throwable {
        // ... (본문은 TraceTxAspectV3의 tx와 같다)
    }
}

    위의 tx 본문은 지면을 아끼려고 주석으로 대신했다. 실제로 실행한 코드에는 V3와 같은 try·catch·finally 본문이 들어 있고, 출력도 V3와 줄 단위로 같았다. 이 클래스에는 눈여겨볼 점이 세 가지 있다.

    첫째, Pointcuts는 애스펙트가 아니다. @Aspect도 없고 빈으로 등록하지도 않았다. 포인트컷 참조는 컨테이너가 빈을 찾아 연결하는 것이 아니라, 애스펙트를 어드바이저로 바꿀 때 AspectJ 파서가 문자열 "lab.aop.Pointcuts.inventory()"를 해석하면서 그 이름이 가리키는 메서드의 @Pointcut 식으로 풀어내는 일이다. 그래서 포인트컷을 담은 클래스는 클래스패스에 있기만 하면 된다. 둘째, 다른 클래스에서 참조하려면 포인트컷 메서드가 public이어야 한다. 앞에서 본 가시성 규칙 그대로다. 셋째, inventoryService()처럼 포인트컷 클래스 안에서 다른 포인트컷을 조합해 새 이름을 만들 수 있다. 같은 클래스 안이므로 짧은 이름으로 참조했다.

    이렇게 모아 두면 "서비스 계층"의 정의가 바뀌었을 때 고칠 곳이 한 군데다. 반대로 위험도 한 군데에 모인다. 포인트컷 클래스의 식 하나가 잘못되면 그 이름을 참조하는 모든 애스펙트의 적용 범위가 한꺼번에 바뀐다. 그리고 뒤의 "조용히 실패하는 설정" 절에서 보겠지만, 참조하는 이름에 오타가 있어도 6.2.19에서는 컨테이너가 기동에 실패하지 않는다. 포인트컷 클래스를 둔다면 그 포인트컷이 의도한 메서드에 걸리는지 확인하는 테스트도 함께 두는 것이 좋다.

    어드바이스 순서 — 애스펙트 단위로만 정할 수 있다

    앞에서 같은 애스펙트 안의 두 @Around는 순서를 통제할 수 없다는 것을 봤다. 트랜잭션이 로그 추적보다 바깥에서 먼저 시작해야 한다면 둘을 서로 다른 애스펙트 클래스로 나누고, 클래스에 순서를 붙인다. 아래는 하나의 바깥 클래스 안에 static 중첩 클래스 두 개로 애스펙트를 나눈 모습이다. static 중첩 클래스는 바깥 클래스의 인스턴스 없이 생성할 수 있으므로 각각 독립된 빈이 될 수 있다.

    public class AspectV5 {

    @Aspect
    @Order(2)
    public static class TraceAspect {
        @Around("lab.aop.Pointcuts.inventory()")
        public Object trace(ProceedingJoinPoint joinPoint) throws Throwable {
            System.out.println("[trace] " + joinPoint.getSignature());
            return joinPoint.proceed();
        }
    }

    @Aspect
    @Order(1)
    public static class TxAspect {
        @Around("lab.aop.Pointcuts.inventoryService()")
        public Object tx(ProceedingJoinPoint joinPoint) throws Throwable {
            // ... (V3의 tx와 같은 본문)
        }
    }
}

    이번에는 [tx] 시작이 [trace]보다 먼저 찍혔다. 레퍼런스의 규칙은 이렇다. 서로 다른 애스펙트에 정의된 어드바이스가 같은 조인 포인트에 적용될 때, 따로 지정하지 않으면 실행 순서는 정의되어 있지 않다. 순서를 정하려면 애스펙트 클래스가 org.springframework.core.Ordered를 구현하거나 @Order를 붙인다. 두 애스펙트 중 더 작은 값을 가진 쪽의 우선순위가 높다. 그리고 우선순위가 높은 어드바이스는 "들어갈 때" 먼저 실행되고 "나올 때" 마지막에 실행된다. 들어갈 때 먼저라는 것은 바깥쪽에 있다는 뜻이고, 바깥쪽에 있으니 나올 때는 가장 늦게 빠져나온다. tx가 커밋과 정리를 trace보다 늦게 찍은 이유다(리포지토리 호출의 [trace]는 서비스 안쪽에서 따로 일어난 호출이다).

    순서 값이 작은 애스펙트가 바깥 껍질이 되어 들어갈 때 먼저, 나올 때 나중에 실행된다는 것을 양파 모양의 동심원으로 보여 준다. 흰 배경의 평면 다이어그램. 왼쪽 끝에 "호출자" 상자, 오른쪽으로 동심원 세 겹이 있다. 가장 바깥 원은 파란색 테두리에 "TxAspect @Order(1)" 라벨, 그 안의 원은 초록색 테두리에 "TraceAspect @Order(2)" 라벨, 가장 안쪽 원은 회색으로 채우고 "원본 StockService.place()" 라벨. 호출자에서 출발한 실선 화살표가 바깥 원 → 안쪽 원 → 가운데로 들어가며 화살표 위에 "들어갈 때: 1 → 2" 라벨. 가운데에서 나오는 점선 화살표가 안쪽 원 → 바깥 원 → 호출자로 돌아가며 "나올 때: 2 → 1" 라벨. 아래쪽에 작은 글씨로 "값이 작을수록 바깥쪽" 라벨. 라벨은 모두 한국어 그대로. @Order 값이 작은 애스펙트일수록 바깥쪽에서 감싼다. 들어갈 때 먼저, 나올 때 나중이다.

    순서 값은 어디서 읽히는가

    "클래스에 붙인다"는 규칙이 왜 그런지는 순서 값을 읽는 코드를 보면 바로 보인다. 어드바이저를 정렬하는 AspectJAwareAdvisorAutoProxyCreator.sortAdvisors()는 각 어드바이저를 AspectJPrecedenceComparator로 비교하는데, 이 비교자의 첫 번째 기준은 스프링의 일반적인 순서 비교자(AnnotationAwareOrderComparator)가 어드바이저에게 물어본 순서 값이다. @Aspect에서 만들어진 어드바이저(InstantiationModelAwarePointcutAdvisorImpl)는 getOrder()를 애스펙트 인스턴스 팩토리에 그대로 위임하고, 그 팩토리(BeanFactoryAspectInstanceFactory)의 getOrder()는 이렇게 생겼다.

    // spring-aop 7.0.10 BeanFactoryAspectInstanceFactory.getOrder()
Class type = this.beanFactory.getType(this.name);
if (type != null) {
    if (Ordered.class.isAssignableFrom(type) && this.beanFactory.isSingleton(this.name)) {
        return this.beanFactory.getBean(this.name, Ordered.class).getOrder();
        // (빈이 Ordered가 아닌 경우의 예외 처리는 줄임)
    }
    return OrderUtils.getOrder(type, Ordered.LOWEST_PRECEDENCE);
}
return Ordered.LOWEST_PRECEDENCE;

    순서 값의 출처는 애스펙트 빈의 타입뿐이다. 그 타입이 Ordered를 구현했으면(싱글톤일 때) 그 값을, 아니면 타입에 붙은 @Order를, 둘 다 없으면 Ordered.LOWEST_PRECEDENCE를 쓴다. 한 애스펙트에서 나온 어드바이저는 모두 같은 팩토리를 공유하므로 모두 같은 순서 값을 갖는다. 어드바이스 메서드에 붙인 @Order는 이 경로 어디에서도 읽히지 않는다.

    이 결론을 두 가지 실험으로 확인했다. 첫째, 한 애스펙트 안의 @Around 메서드 a에 @Order(2)를, b에 @Order(1)을 붙였다. 메서드 단위 순서가 반영된다면 b가 먼저여야 하지만, 출력은 이름순 그대로 [a @Order(2)] 다음 [b @Order(1)]이었다. 둘째, @Order가 없는 애스펙트 클래스 X, Y를 설정 클래스의 @Bean 메서드로 등록하면서 @Bean 메서드 쪽에 X는 @Order(2), Y는 @Order(1)을 붙였다. 출력은 [X] 다음 [Y]였다. 위 코드가 OrderUtils.getOrder(type, ...)로 클래스의 애노테이션만 보기 때문에, 팩토리 메서드에 붙인 @Order는 애스펙트의 우선순위에 반영되지 않았다(두 애스펙트가 모두 가장 낮은 우선순위라 순서는 정의되지 않은 상태이고, 이 실행에서는 우연히 X가 앞섰다). 애스펙트의 순서를 정하려면 클래스에 @Order를 붙이거나 클래스가 Ordered를 구현해야 한다.

    같은 순서 값끼리는 어떻게 될까? AspectJPrecedenceComparator는 순서 값이 같고 두 어드바이저가 같은 애스펙트에서 왔을 때만 애스펙트 안의 선언 순서를 추가로 비교한다. 그런데 앞에서 봤듯 그 선언 순서가 모두 0으로 고정되어 있으므로 결과는 "같음"이 되고, 어드바이스 종류에 따른 순서는 그 앞 단계(어드바이저를 만들 때의 메서드 정렬)에서 이미 정해진 것이 유지된다. 서로 다른 애스펙트인데 순서 값이 같으면, 특히 둘 다 순서를 지정하지 않아 LOWEST_PRECEDENCE라면, 레퍼런스의 말대로 순서는 정의되지 않는다.

    어드바이스 종류 — 다섯 가지를 한 애스펙트에

    지금까지는 @Around만 썼다. 어라운드 어드바이스는 진짜 메서드 호출 앞뒤를 모두 쥐고 있어서 다른 모든 어드바이스가 하는 일을 혼자 할 수 있다. 나머지 네 종류는 그 능력 중 일부만 떼어 낸 것이다. 다섯 가지를 한 애스펙트에 모두 넣고 서비스 계층에만 걸어 보자.

    @Aspect
public class AllAdviceAspect {
    @Around("lab.aop.Pointcuts.inventoryService()")
    public Object around(ProceedingJoinPoint joinPoint) throws Throwable {
        System.out.println("[around] 진입 " + joinPoint.getSignature().getName());
        try {
            Object result = joinPoint.proceed();
            System.out.println("[around] 정상 반환 " + result);
            return result;
        } catch (Exception e) {
            System.out.println("[around] 예외 " + e.getClass().getSimpleName());
            throw e;
        } finally {
            System.out.println("[around] finally");
        }
    }

    @Before("lab.aop.Pointcuts.inventoryService()")
    public void before(JoinPoint joinPoint) {
        System.out.println("[before] " + joinPoint.getSignature().getName());
    }

    @AfterReturning(value = "lab.aop.Pointcuts.inventoryService()", returning = "result")
    public void afterReturning(JoinPoint joinPoint, Object result) {
        System.out.println("[afterReturning] " + result);
    }

    @AfterThrowing(value = "lab.aop.Pointcuts.inventoryService()", throwing = "ex")
    public void afterThrowing(JoinPoint joinPoint, Exception ex) {
        System.out.println("[afterThrowing] " + ex.getMessage());
    }

    @After("lab.aop.Pointcuts.inventoryService()")
    public void after(JoinPoint joinPoint) {
        System.out.println("[after] " + joinPoint.getSignature().getName());
    }
}

    종류실행 시점받을 수 있는 것할 수 있는 일과 없는 일
    @Around메서드 실행 전체를 감싼다ProceedingJoinPoint(첫 번째 매개변수로 필수)proceed()를 0번·1번·여러 번 부를 수 있고, 인자를 바꿔 넘기거나, 반환값을 바꾸거나, 예외를 삼키거나 바꿀 수 있다. proceed()를 잊으면 진짜 메서드가 실행되지 않는다.
    @Before진짜 메서드 호출 직전JoinPoint다음으로 넘어가는 것은 프레임워크가 한다. 호출을 막으려면 예외를 던지는 수밖에 없다.
    @AfterReturning정상 반환 직후JoinPoint, returning으로 지정한 반환값반환값을 읽을 수 있지만 다른 참조로 바꿔 돌려줄 수는 없다. 매개변수 타입이 반환값과 맞지 않으면 실행되지 않는다.
    @AfterThrowing예외가 던져진 직후JoinPoint, throwing으로 지정한 예외예외를 관찰할 뿐 삼키지 못한다. 어드바이스가 끝나면 원래 예외가 다시 던져진다. 매개변수 타입에 맞는 예외일 때만 실행된다.
    @After정상이든 예외든 끝난 뒤(finally)JoinPoint반환값도 예외도 받지 못한다. 자원 정리처럼 결과와 무관한 일에 쓴다.

    출력에서 눈여겨볼 곳은 두 군데다. 하나는 [before]가 [around] 진입보다 뒤에 있다는 점, 다른 하나는 [after]가 [afterReturning]·[afterThrowing]보다 뒤에 있다는 점이다. 레퍼런스는 같은 애스펙트 안의 우선순위를 높은 것부터 @Around, @Before, @After, @AfterReturning, @AfterThrowing 순으로 정해 두었다고 적고, 동시에 @After는 AspectJ의 "after finally" 의미를 따르므로 실제로는 같은 애스펙트의 @AfterReturning·@AfterThrowing보다 나중에 호출된다고 덧붙인다. 우선순위에서는 @After가 앞인데 실행은 뒤라니 모순처럼 들린다. 이 모순은 어드바이스가 프록시 안에서 어떤 모양의 객체로 바뀌는지를 보면 풀린다.

    한 층 아래 — 어드바이스는 MethodInterceptor 체인이 된다

    먼저 프록시가 들고 있는 어드바이저 목록을 직접 꺼내 보자. 스프링 AOP 프록시는 Advised 인터페이스를 함께 구현하므로, 프록시를 그 타입으로 캐스팅해 getAdvisors()를 부르면 정렬이 끝난 목록이 나온다.

    ExposeInvocationInterceptor
AspectJAroundAdvice           ← around()
AspectJMethodBeforeAdvice     ← before()
AspectJAfterAdvice            ← after()
AspectJAfterReturningAdvice   ← afterReturning()
AspectJAfterThrowingAdvice    ← afterThrowing()

    다섯 개의 어드바이스 메서드가 정확히 앞에서 본 비교자의 순서(Around, Before, After, AfterReturning, AfterThrowing)로 늘어섰고, 맨 앞에 우리가 만들지 않은 ExposeInvocationInterceptor가 하나 더 있다. 같은 실험에서 리포지토리 빈은 Advised로 캐스팅할 수 없었다. 서비스 계층에만 걸리는 포인트컷이라 리포지토리는 프록시가 되지 않았기 때문이다.

    어드바이저 하나는 프록시가 메서드를 처음 호출할 때 MethodInterceptor로 바뀌어 체인에 들어간다. 스프링의 DefaultAdvisorAdapterRegistry.getInterceptors()는 어드바이스가 이미 MethodInterceptor이면 그대로 쓰고, 아니면 등록된 어댑터(MethodBeforeAdviceAdapter, AfterReturningAdviceAdapter, ThrowsAdviceAdapter)로 감싼다. AspectJ 방식 어드바이스 다섯 종이 각각 어떤 인터셉터가 되고 그 인터셉터의 invoke()가 무엇을 하는지를 소스에서 옮기면 다음과 같다.

    어드바이스 클래스체인에 들어가는 인터셉터invoke(mi)의 골격
    AspectJAroundAdvice자기 자신(MethodInterceptor 구현)어드바이스 메서드를 ProceedingJoinPoint와 함께 호출하고 그 반환값을 돌려준다. 다음으로 넘어갈지는 어드바이스 메서드가 정한다.
    AspectJMethodBeforeAdviceMethodBeforeAdviceInterceptor로 감쌈advice.before(...) 다음 return mi.proceed()
    AspectJAfterAdvice자기 자신try { return mi.proceed(); } finally { 어드바이스 호출 }
    AspectJAfterReturningAdviceAfterReturningAdviceInterceptor로 감쌈retVal = mi.proceed(); 반환값 타입이 맞으면 어드바이스 호출, return retVal
    AspectJAfterThrowingAdvice자기 자신try { return mi.proceed(); } catch (Throwable ex) { 타입이 맞으면 어드바이스 호출; throw ex; }

    이 체인이 실제로 그렇게 구성되었는지 확인하려고, 실행 중인 체인을 리플렉션으로 꺼내 출력하는 @Before 어드바이스를 하나 더 붙여 봤다. 그 어드바이스 자신이 MethodBeforeAdviceInterceptor 하나로 3번 칸에 끼어든 것을 빼면, 체인은 0번부터 ExposeInvocationInterceptor, AspectJAroundAdvice, MethodBeforeAdviceInterceptor, AspectJAfterAdvice, AfterReturningAdviceInterceptor, AspectJAfterThrowingAdvice 순서였다. 실행을 이끄는 객체는 ReflectiveMethodInvocation이었다. 6.2.19의 CGLIB 프록시는 호출을 받으면 CglibAopProxy의 내부 클래스 DynamicAdvisedInterceptor에서 이 메서드에 해당하는 체인을 가져오고(메서드별로 캐시된다), 체인이 비어 있으면 대상 메서드를 바로 호출하며, 비어 있지 않으면 new ReflectiveMethodInvocation(...)을 만들어 proceed()를 부른다.

    // spring-aop 7.0.10 ReflectiveMethodInvocation.proceed()에서 핵심만
public Object proceed() throws Throwable {
    // 인덱스는 -1에서 시작해 먼저 증가시킨다
    if (this.currentInterceptorIndex == this.interceptorsAndDynamicMethodMatchers.size() - 1) {
        return invokeJoinpoint();              // 체인의 끝: 진짜 메서드 호출
    }
    Object interceptor = this.interceptorsAndDynamicMethodMatchers.get(++this.currentInterceptorIndex);
    // (실행 시점 매칭이 필요한 경우의 분기는 줄임)
    return ((MethodInterceptor) interceptor).invoke(this);   // 다음 칸에게 "나 자신"을 넘긴다
}

    구조는 단순하다. proceed()는 인덱스를 하나 올리고 그 칸의 인터셉터에게 this를 넘긴다. 인터셉터는 자기 일을 하다가 적당한 때에 다시 mi.proceed()를 부르고, 그러면 인덱스가 또 하나 올라간다. 인덱스가 마지막 칸을 지나면 진짜 메서드가 호출된다. 각 인터셉터의 invoke()는 자바 호출 스택에 한 프레임씩 쌓이므로, 체인은 결국 메서드 호출의 중첩이다. 앞 칸일수록 바깥 프레임이고, 바깥 프레임일수록 먼저 시작해 나중에 끝난다.

    체인의 0~5번 칸이 호출 스택처럼 아래로 쌓였다가 진짜 메서드에서 되돌아 올라오며, 각 칸이 proceed() 앞과 뒤 중 어디에서 일을 하는지 보여 준다. 세로로 긴 계단식 시퀀스 다이어그램. 맨 위 왼쪽에 "프록시 place()" 상자. 그 아래로 오른쪽으로 한 칸씩 들여쓰며 상자 6개가 계단처럼 내려간다: "[0] ExposeInvocationInterceptor", "[1] AspectJAroundAdvice", "[2] MethodBeforeAdviceInterceptor", "[3] AspectJAfterAdvice", "[4] AfterReturningAdviceInterceptor", "[5] AspectJAfterThrowingAdvice". 맨 아래 가장 오른쪽에 회색 상자 "원본 메서드". 내려가는 실선 화살표마다 "proceed()" 라벨. 원본 메서드에서 위로 되돌아가는 점선 화살표 계단. [2] 상자 왼쪽(내려가는 쪽)에 작은 말풍선 "before 실행", [4] 상자 오른쪽(올라오는 쪽)에 "afterReturning 실행", [3] 상자 오른쪽에 "after 실행(finally)". 상자 이름은 영문 그대로, 말풍선은 한국어 그대로. 단색 계열, 깔끔한 선. 체인의 앞 칸이 바깥 호출 프레임이다. 그래서 [3]의 after는 [4]의 afterReturning이 끝난 뒤에 실행된다.

    성공 흐름을 한 칸씩 따라가기

    이제 place("apple") 호출을 처음부터 끝까지 추적해 보자. 출력 순서가 왜 그렇게 나왔는지가 여기서 전부 설명된다.

    1. 호출자가 프록시의 place("apple")을 부른다. DynamicAdvisedInterceptor가 체인을 가져와 ReflectiveMethodInvocation을 만들고 proceed()를 부른다. 인덱스가 -1에서 0이 된다.
    2. [0] ExposeInvocationInterceptor가 현재 호출 객체를 ThreadLocal에 저장하고 proceed()를 부른다. 인덱스 1.
    3. [1] AspectJAroundAdvice가 around() 메서드를 호출한다. [around] 진입 place가 찍히고, 어드바이스 안의 joinPoint.proceed()가 체인을 이어 간다. 인덱스 2.
    4. [2] MethodBeforeAdviceInterceptor가 before()를 호출해 [before] place를 찍은 뒤 proceed(). 인덱스 3.
    5. [3] AspectJAfterAdvice가 try 블록 안에서 proceed(). 아직 아무것도 찍지 않는다. 인덱스 4.
    6. [4] AfterReturningAdviceInterceptor가 반환값을 받으려고 proceed(). 인덱스 5.
    7. [5] AspectJAfterThrowingAdvice가 try 블록 안에서 proceed(). 인덱스가 마지막 칸이므로 invokeJoinpoint()가 원본 StockService.place()를 호출한다. [service], [repository]가 찍히고 "reserved:apple"이 돌아온다.
    8. [5]로 돌아온다. 예외가 없으므로 catch는 건너뛰고 값을 그대로 돌려준다.
    9. [4]로 돌아온다. 반환값 타입이 매개변수 타입(Object)과 맞으므로 afterReturning()을 호출해 [afterReturning] reserved:apple을 찍는다.
    10. [3]으로 돌아온다. finally가 실행되어 [after] place를 찍는다.
    11. [2]는 할 일이 없으므로 값을 돌려준다. [1]의 around() 안으로 돌아와 [around] 정상 반환 reserved:apple, [around] finally를 찍고 값을 돌려준다.
    12. [0]이 finally에서 ThreadLocal을 이전 값으로 되돌린다. 프록시가 반환값을 검사(뒤에서 볼 기본형 null 검사)한 뒤 호출자에게 돌려준다.

    이제 "우선순위는 @After가 앞인데 실행은 뒤"라는 모순이 풀린다. 우선순위가 높다는 것은 체인에서 앞 칸, 즉 바깥 프레임에 놓인다는 뜻이다. @After는 @AfterReturning보다 바깥에 있고, 바깥 프레임의 finally는 안쪽 프레임이 모두 끝난 뒤에야 실행된다. 반대로 @AfterThrowing은 가장 안쪽에 있어서 진짜 메서드가 던진 예외를 가장 먼저 본다. ReflectiveAspectJAdvisorFactory 소스의 주석도 같은 설명을 한다. @After가 앞에 정렬되어 있어도, AspectJAfterAdvice.invoke()가 proceed()를 try에서 부르고 어드바이스 메서드는 finally에서 부르기 때문에 실제로는 뒤에 실행된다는 것이다.

    예외 흐름

    place("ghost")에서는 7단계에서 원본 리포지토리가 IllegalArgumentException을 던진다. 리포지토리는 이 실험에서 프록시가 아니므로 예외는 원본 서비스를 거쳐 곧바로 [5]로 올라온다. [5]의 catch가 예외 타입을 확인한다. throwing 매개변수 타입이 Exception이고 IllegalArgumentException은 그 하위 타입이므로 afterThrowing()이 호출되어 [afterThrowing] 없는 상품: ghost가 찍히고, 같은 예외가 다시 던져진다. [4]에서는 proceed()가 예외로 끝났으므로 afterReturning()을 부르는 줄에 도달하지 못한다. [3]의 finally가 [after] place를 찍는다. [2]를 지나 [1]의 around() 안에서 catch가 [around] 예외 IllegalArgumentException을, finally가 [around] finally를 찍고 예외를 다시 던진다. [0]이 ThreadLocal을 되돌리고, 호출자가 원래 예외를 받는다.

    같은 체인에서 정상 반환과 예외 발생 시 어떤 어드바이스가 실행되고 어떤 것이 건너뛰어지는지 두 줄의 타임라인으로 비교한다. 가로 타임라인 두 줄을 위아래로 배치. 위 줄 제목 "정상 반환", 아래 줄 제목 "예외 발생". 두 줄 모두 왼쪽에서 오른쪽으로 원형 마커가 이어진다. 위 줄 마커 순서: "around 진입", "before", "원본 메서드", "afterReturning", "after", "around 정상 반환". 아래 줄 마커 순서: "around 진입", "before", "원본 메서드 예외", "afterThrowing", "after", "around 예외". 아래 줄의 "원본 메서드 예외" 마커는 빨간색, 위 줄 "afterReturning" 자리 바로 아래에 회색 점선 원과 작은 글씨 "건너뜀". 마커 라벨은 한국어·영문 그대로. 배경은 흰색, 두 줄의 같은 단계는 세로로 정렬. 예외가 나면 afterReturning 자리를 건너뛰고 afterThrowing이 실행된다. after는 두 경우 모두 실행된다.

    ExposeInvocationInterceptor와 ThreadLocal

    체인 맨 앞의 ExposeInvocationInterceptor는 왜 필요할까. MethodBeforeAdviceInterceptor가 감싼 before() 호출을 보면, 어댑터는 어드바이스에게 메서드·인자·대상 객체만 넘긴다. 그런데 우리의 before(JoinPoint)는 JoinPoint를 받는다. 그 JoinPoint는 AbstractAspectJAdvice.currentJoinPoint()가 만드는데, 이 메서드는 ExposeInvocationInterceptor.currentInvocation()으로 현재 스레드에 저장된 호출 객체를 꺼내 그것을 감싼다. ExposeInvocationInterceptor의 저장소는 private static final ThreadLocal이다. 01회에서 본 ThreadLocal이 여기서 프레임워크 내부의 전달 통로로 쓰인다. 그래서 AspectJAwareAdvisorAutoProxyCreator.extendAdvisors()는 AspectJ 방식 어드바이스가 하나라도 있는 체인에 이 인터셉터를 맨 앞에 넣는다. 이 인터셉터의 순서 값은 PriorityOrdered.HIGHEST_PRECEDENCE + 1이고, currentInvocation()이 값을 찾지 못했을 때 내는 예외 메시지는 HIGHEST_PRECEDENCE 순서의 어드바이스는 이 인터셉터보다 먼저 실행된다는 점과, 같은 스레드에서 호출해야 한다는 점을 경고한다. 01회에서 본 것처럼 finally에서 이전 값으로 되돌려 놓기 때문에 스레드 풀의 스레드가 재사용되어도 값이 남지 않는다.

    JoinPoint와 ProceedingJoinPoint

    레퍼런스는 모든 어드바이스 메서드가 첫 번째 매개변수로 org.aspectj.lang.JoinPoint를 선언할 수 있고, 어라운드 어드바이스는 그 하위 타입인 ProceedingJoinPoint를 첫 번째 매개변수로 선언해야 한다고 적는다. 스프링 소스의 AbstractAspectJAdvice.calculateArgumentBindings()도 정확히 그렇게 동작한다. 매개변수 배열의 0번 타입이 JoinPoint, ProceedingJoinPoint, JoinPoint.StaticPart 중 하나인지만 보고, 나머지 매개변수는 이름으로 묶는다. ProceedingJoinPoint를 어라운드가 아닌 어드바이스에서 받으면 이 바인딩 단계에서 "ProceedingJoinPoint is only supported for around advice"라는 IllegalArgumentException이 난다. 다만 6.2.19에서 이 예외는 호출자에게 전달되지 않았다. ReflectiveAspectJAdvisorFactory.getAdvisor()가 이 예외를 잡아 "Ignoring incompatible advice method" 디버그 로그만 남기고 그 어드바이스를 어드바이저로 만들지 않았으며, 컨테이너는 정상 기동했다.

    JoinPoint가 주는 정보를 서비스 메서드에서 모두 찍어 보면 다음과 같다.

    proceed()는 복제본으로 체인을 잇는다

    ProceedingJoinPoint의 스프링 구현인 MethodInvocationProceedingJoinPoint.proceed()는 한 줄이다. return this.methodInvocation.invocableClone().proceed(); 즉 현재 호출 객체의 얕은 복제본을 만들어 거기서 체인을 이어 간다. 복제본은 인터셉터 목록과 현재 인덱스를 그대로 물려받고, 인자 배열은 따로 복사한다. 앞의 체인 출력 실험에서 ThreadLocal에 저장된 원래 호출 객체의 인덱스를 3번 칸의 어드바이스 안에서 읽어 봤더니 1이었다. 체인은 3번 칸까지 진행했지만, 그 진행은 [1]의 어라운드가 만든 복제본에서 일어났고 원래 객체는 어라운드 칸에 머물러 있었던 것이다.

    이 구조 덕분에 레퍼런스가 말하는 "proceed는 0번, 1번, 여러 번 호출할 수 있다"가 실제로 가능하다. 호출할 때마다 같은 위치에서 새 복제본이 출발하기 때문이다. 아래는 리포지토리 호출이 IllegalArgumentException으로 실패하면 한 번 더 시도하는 어드바이스다.

    @Aspect
public class RetryAspect {
    @Around("execution(* lab.inventory.StockRepository.reserve(..))")
    public Object retry(ProceedingJoinPoint joinPoint) throws Throwable {
        for (int i = 1; ; i++) {
            try {
                return joinPoint.proceed();
            } catch (IllegalArgumentException e) {
                System.out.println("[retry] " + i + "회 실패");
                if (i == 2) throw e;
            }
        }
    }
}

    반환값과 예외의 경계

    어드바이스 종류를 고를 때 가장 자주 부딪히는 질문은 "이 어드바이스로 결과를 바꿀 수 있는가"다. 앞의 체인 구조에서 답이 그대로 나온다.

    @AfterReturning은 반환값을 바꿀 수 없다

    AfterReturningAdviceInterceptor.invoke()는 retVal = mi.proceed()로 값을 받아 어드바이스에 넘기고, 어드바이스가 끝나면 자기가 받아 둔 retVal을 돌려준다. 어드바이스 메서드의 반환 타입이 void이기도 하지만, 설령 무언가를 돌려줘도 인터셉터가 그 값을 쓰지 않는다. 레퍼런스도 after returning 어드바이스로는 완전히 다른 참조를 돌려줄 수 없다고 적는다. 다만 넘겨받은 객체가 가변 객체라면 그 내부 상태를 바꾸는 것은 막을 수 없다. 참조는 같고 객체가 바뀐 것이기 때문이다.

    returning으로 묶은 매개변수의 타입은 필터 역할도 한다. 레퍼런스는 returning 절이 지정한 타입의 값을 반환하는 메서드 실행으로 매칭을 제한한다고 설명한다. 리포지토리의 reserve()(반환 타입 String)에 매개변수 타입만 다른 @AfterReturning 두 개, 하나는 Integer result, 다른 하나는 String result를 걸어 봤다. 출력에는 [afterReturning String] reserved:apple 한 줄만 나왔고, Integer 쪽은 오류도 없이 실행되지 않았다. AspectJAfterReturningAdvice.afterReturning()은 반환값이 선언된 타입에 맞는지(shouldInvokeOnReturnValueOf) 먼저 확인하고 맞을 때만 어드바이스 메서드를 부른다. 매개변수 타입을 Object로 두면 언제나 실행된다.

    @Around는 반환값을 바꿀 수 있지만 타입은 지켜야 한다

    어라운드 어드바이스는 proceed()가 돌려준 값 대신 다른 값을 돌려줄 수 있다. 하지만 어드바이스 메서드의 반환 타입이 Object라서 컴파일러가 실제 메서드의 반환 타입을 검사해 주지 못한다. 검사는 실행 중에 프록시가 한다. int를 돌려주는 count()에 null만 돌려주는 어라운드 어드바이스를 걸면 이렇게 된다.

    org.springframework.aop.AopInvocationException: Null return value from advice does not match primitive return type for: public int lab.inventory.StockRepository.count(java.lang.String)

    이 예외는 CglibAopProxy(JDK 프록시라면 JdkDynamicAopProxy)가 체인 실행이 끝난 뒤 반환값을 처리하는 단계에서 던진다. 반환값이 null이고 메서드의 반환 타입이 void가 아닌 기본형이면, null을 int로 언박싱할 방법이 없으므로 더 진행하지 않는 것이다. 기본형이 아닌 타입이 어긋나는 경우는 이 검사에 걸리지 않는다. String을 반환하는 reserve()에 proceed()를 부른 뒤 42를 돌려주는 어라운드 어드바이스를 걸었더니, 기동과 체인 실행은 문제없이 지나가고 호출자가 java.lang.ClassCastException: class java.lang.Integer cannot be cast to class java.lang.String을 받았다. 04회에서 본 것처럼 프록시 클래스의 메서드는 인터셉터가 돌려준 Object를 자기 반환 타입으로 바꿔 돌려줘야 하고, 그 지점에서 타입이 맞지 않음이 드러난 것이다.

    @AfterThrowing은 예외를 삼키지 못한다

    AspectJAfterThrowingAdvice.invoke()의 catch 블록은 어드바이스를 부른 뒤 무조건 throw ex로 끝난다. 그래서 @AfterThrowing은 예외를 기록하거나 알림을 보낼 수는 있어도 예외를 정상 반환으로 바꿀 수는 없다. 예외를 바꾸거나 삼키려면 @Around가 필요하다. 이 어드바이스도 throwing 매개변수의 타입이 필터가 된다. 던져진 예외가 그 타입의 인스턴스일 때만(getDiscoveredThrowingType().isAssignableFrom(ex.getClass())) 어드바이스가 실행된다. 레퍼런스는 또 하나의 경계를 긋는다. @AfterThrowing은 일반적인 예외 처리 콜백이 아니며, 조인 포인트(사용자가 선언한 대상 메서드) 자체에서 나온 예외만 받도록 되어 있고 같은 애스펙트의 @After·@AfterReturning 메서드가 던진 예외는 받지 않는다. 체인 구조로 보면 당연하다. @AfterThrowing은 가장 안쪽 칸이고, @After와 @AfterReturning은 그보다 바깥 칸에서 실행되기 때문이다.

    어드바이스 메서드 자체가 예외를 던지면 어떻게 될까. 어드바이스 메서드는 리플렉션(Method.invoke)으로 호출되므로 그 안에서 던진 예외는 원래 InvocationTargetException에 싸여 나온다. AbstractAspectJAdvice.invokeAdviceMethodWithGivenArgs()는 이것을 잡아 getTargetException()으로 원래 예외를 꺼내 다시 던진다. 그래서 호출자는 포장되지 않은 예외를 받는다.

    @Before가 호출을 막는 유일한 방법

    MethodBeforeAdviceInterceptor는 before()를 부른 다음 무조건 mi.proceed()를 부른다. 어드바이스가 "진행하지 마라"를 표현할 수단은 예외뿐이다. 리포지토리의 reserve()에 빈 문자열이 들어오면 예외를 던지는 @Before를 걸고 place(" ")를 호출했더니, [service] place 실행 sku= 다음에 [repository] 줄 없이 바로 IllegalArgumentException: 빈 sku가 호출자에게 전달됐다. 이 어드바이스는 포인트컷에 && args(sku)를 붙여 메서드 인자를 어드바이스의 String sku 매개변수로 받았다. args 같은 지정자는 09회에서 다룬다.

    이 장의 핵심

    다섯 어드바이스의 능력 차이는 각 인터셉터의 invoke()가 proceed()를 어디서 부르고 그 결과를 어떻게 다루는지의 차이다. proceed()를 어드바이스 메서드에게 맡기는 것은 @Around뿐이고, 나머지 넷은 프레임워크가 proceed()를 대신 부르고 정해진 시점에만 어드바이스를 끼워 넣는다. 그래서 나머지 넷은 실수할 여지가 적고, 대신 할 수 있는 일도 적다.

    조용히 실패하는 설정들

    AOP 설정의 실수는 컴파일 오류로 드러나지 않는 경우가 많다. 이 회차의 실험(스프링 6.2.19)에서 오류 없이 기동했지만 어드바이스가 적용되지 않은 경우를 모아 둔다.

    • 포인트컷 이름의 오타: @Around("lab.aop.Pointcuts.inventry()")처럼 없는 포인트컷을 참조해도 컨테이너는 정상 기동했고 어드바이스는 어디에도 적용되지 않았다. 디버그 로그에만 Pointcut parser rejected expression [lab.aop.Pointcuts.inventry()]: java.lang.IllegalArgumentException: error at ::0 can't find referenced pointcut inventry가 남았다.
    • 포인트컷 식의 문법 오류: 닫는 괄호를 빠뜨린 execution(* lab.inventory..*(..)도 마찬가지였다. 디버그 로그는 Pointcut is not well-formed: expecting ')' at character position 0이었다.
    • JoinPoint를 첫 번째가 아닌 자리에 둔 경우: bad(String sku, JoinPoint joinPoint)처럼 선언하고 포인트컷에서 args(sku)로 sku만 묶었더니, 스프링은 joinPoint도 이름으로 묶어야 할 매개변수로 취급했고 결과적으로 formal unbound in pointcut 오류가 디버그 로그에 남은 채 어드바이스가 적용되지 않았다.
    • @Aspect만 붙이고 @Component를 빠뜨린 경우: 앞에서 본 대로 애스펙트가 빈이 되지 않아 아무 일도 일어나지 않는다.

    앞의 세 경우가 조용히 지나가는 이유는 7.0.10 소스에서 볼 수 있다. AspectJExpressionPointcut이 클래스 매칭 중에 식을 파싱하다 IllegalArgumentException 등이 나면 pointcutParsingFailed를 표시하고 디버그 로그만 남긴 뒤 "맞지 않음"(false)을 돌려준다. 어드바이저는 존재하지만 어떤 빈에도 맞지 않는 어드바이저가 되는 것이다. 버전마다 이 처리 방식이 달라질 수 있으므로, 사용하는 버전에서 직접 확인하는 것이 안전하다. 확실한 방어는 테스트다. 애스펙트를 만들었다면 대상 빈에 AopUtils.isAopProxy()가 true인지, 어드바이스의 효과(로그, 호출 횟수)가 실제로 나타나는지를 확인하는 테스트를 함께 둔다. 부트 애플리케이션이라면 logging.level.org.springframework.aop=debug로 위의 디버그 로그를 볼 수도 있다.

    애스펙트는 싱글톤 빈이다

    어드바이스 메서드를 호출할 때 스프링은 BeanFactoryAspectInstanceFactory.getAspectInstance()로 애스펙트 인스턴스를 얻는데, 이 메서드는 beanFactory.getBean(name)이다. 기본 스코프의 애스펙트는 컨테이너에 하나뿐이고, 모든 요청 스레드가 같은 인스턴스의 어드바이스 메서드를 동시에 실행한다. 01회에서 본 필드 공유 문제가 그대로 적용된다. @Before에서 시작 시각을 필드에 저장하고 @After에서 꺼내 쓰는 식의 설계는 동시 요청에서 값이 뒤섞인다. 레퍼런스가 어라운드 어드바이스를 두고 "메서드 실행 전후에 상태를 스레드 안전하게 공유해야 할 때, 예를 들어 타이머를 시작하고 멈출 때 자주 쓴다"고 설명하는 이유가 여기에 있다. 어라운드 어드바이스 안의 지역 변수는 그 호출을 처리하는 스레드의 스택 프레임에만 있으므로 다른 스레드와 섞이지 않는다.

    정리 — 가장 약한 어드바이스를 고른다

    레퍼런스는 요구를 만족하는 가장 약한(least powerful) 형태의 어드바이스를 쓰라고 권한다. before 어드바이스로 충분한데 around 어드바이스를 쓰지 말라는 것이다. 이 회차의 체인 구조를 알고 나면 이 권고의 이유가 구체적으로 보인다. @Around는 proceed()를 부를지, 몇 번 부를지, 무엇을 돌려줄지를 전부 어드바이스 코드에 맡긴다. 그 자유는 proceed() 누락, 반환값 누락(void가 아닌 메서드에서 null 반환), 예외 삼키기 같은 실수를 만들 자유이기도 하다. @Before·@AfterReturning·@AfterThrowing·@After는 프레임워크가 정해진 자리에서 proceed()를 부르므로 이런 실수가 구조적으로 일어나지 않고, 코드를 읽는 사람도 어드바이스 이름만 보고 무엇을 하는지 안다.

    정리하면 판단 기준은 이렇다. 호출 전에 검사하거나 기록만 하면 @Before, 정상 결과를 관찰만 하면 @AfterReturning, 예외를 관찰만 하면 @AfterThrowing, 결과와 무관하게 정리해야 하면 @After를 쓴다. 호출 여부나 횟수를 정해야 하거나(재시도, 캐시), 반환값이나 예외를 바꿔야 하거나, 호출 전후에 걸친 상태(시간 측정, 트랜잭션)를 지역 변수로 들고 있어야 할 때만 @Around를 쓴다.

    이 회차에서 만든 구조는 다음 회차들에서 계속 쓰인다. 09회는 이번에 execution과 args 정도만 쓰고 넘어간 포인트컷 지정자를 하나씩 해부한다. 10회는 실전 예제와 함께, getThis()와 getTarget()의 차이에서 잠깐 본 프록시 내부 호출 문제를 다룬다. 그리고 스프링의 @Transactional도 이 회차와 같은 체인 위에서 동작하는 어드바이저 하나다. @EnableTransactionManagement의 order 속성 기본값은 Ordered.LOWEST_PRECEDENCE(6.2.19 바이트코드에서 2147483647로 확인)이므로, 순서를 지정하지 않은 내 애스펙트와 트랜잭션 어드바이저의 앞뒤는 정해져 있지 않다. 로그나 재시도가 트랜잭션 바깥에서 돌아야 한다면 애스펙트 클래스에 순서를 명시해야 한다.

    애스펙트 클래스의 메서드 중 @Pointcut은 빠지고, 어드바이스 메서드가 종류와 이름순으로 정렬되어 어드바이저가 되며, 애스펙트 순서로 다시 정렬된 뒤 맨 앞에 ExposeInvocationInterceptor가 붙는 과정을 보여 준다. 왼쪽에서 오른쪽으로 흐르는 4단계 흐름도. 1단계 상자 "애스펙트 클래스 메서드" 안에 작은 행 다섯 개: "@Pointcut inventory()", "@After after()", "@Before before()", "@Around around()", "@AfterReturning afterReturning()". 첫 행에는 빨간 X 표시와 "제외" 라벨. 화살표 라벨 "종류 → 이름순 정렬". 2단계 상자 "어드바이저 목록" 안에 "Around", "Before", "After", "AfterReturning" 네 행. 화살표 라벨 "애스펙트 @Order로 정렬". 3단계 상자 "정렬된 어드바이저"에 위쪽 파란 묶음 "TxAspect @Order(1)", 아래 초록 묶음 "LogAspect @Order(2)". 화살표 라벨 "맨 앞에 추가". 4단계 상자 "프록시 체인" 맨 위 행 "ExposeInvocationInterceptor"가 강조색, 그 아래로 3단계 행들이 이어진다. 라벨은 그대로 표기. 같은 애스펙트 안의 순서는 어드바이스 종류가, 애스펙트 사이의 순서는 클래스의 @Order가 정한다.
    aspectjweaver의 역할
    스프링 AOP는 이 JAR에서 애노테이션·JoinPoint 타입, 포인트컷 파서와 매처, 부분 순서 정렬만 가져다 쓴다. 위빙은 하지 않고 실행은 순수한 프록시 기반이다.
    @Pointcut 시그니처
    반환 타입이 void인 메서드가 포인트컷의 이름이 되고, 본문은 실행되지 않는다. @Pointcut 메서드는 어드바이저가 되지 않는다.
    포인트컷 참조
    다른 클래스의 포인트컷은 패키지.클래스.메서드()의 완전한 이름으로 참조하며, 자바 가시성 규칙에 따라 public이어야 한다. &&, ||, !로 조합할 수 있다.
    애스펙트 순서
    순서 값은 애스펙트 빈의 타입(클래스의 @Order 또는 Ordered 구현)에서만 읽힌다. 메서드나 @Bean 메서드의 @Order는 반영되지 않았다. 값이 작을수록 바깥쪽이다.
    같은 애스펙트 안의 순서
    종류별로 Around, Before, After, AfterReturning, AfterThrowing 순이다. 같은 종류끼리는 문서상 정의되지 않으며, 현재 구현은 메서드 이름순으로 정렬한다.
    인터셉터 체인
    어드바이저는 MethodInterceptor가 되어 체인을 이루고, ReflectiveMethodInvocation.proceed()가 인덱스를 하나씩 올리며 다음 칸을 호출한다. 앞 칸이 바깥 호출 프레임이다.
    @After가 @AfterReturning보다 늦은 이유
    @After는 체인에서 더 바깥 칸에 있고 finally에서 실행되므로 안쪽 칸의 @AfterReturning·@AfterThrowing이 끝난 뒤 실행된다.
    ExposeInvocationInterceptor
    AspectJ 방식 어드바이스가 있으면 체인 맨 앞에 들어가 현재 호출을 ThreadLocal에 둔다. @Before 등이 JoinPoint를 얻는 통로다.
    ProceedingJoinPoint.proceed()
    현재 호출의 얕은 복제본에서 체인을 잇는다. 그래서 0번, 1번, 여러 번 호출할 수 있고, proceed(Object[])로 인자를 바꿀 수 있다.

    실무에서 애스펙트가 말썽을 부리는 장면은 대개 "적용되지 않았는데 아무도 몰랐다"이다. 이 회차의 실험에서 포인트컷 이름 오타, 식의 괄호 누락, JoinPoint 위치 실수가 모두 기동 실패 없이 디버그 로그 한 줄로만 남았다. 감사 로그나 권한 검사처럼 빠지면 안 되는 부가 기능을 애스펙트로 만든다면, 대상 빈이 프록시인지와 어드바이스의 효과가 나타나는지를 확인하는 테스트를 기능 테스트와 같은 무게로 둬야 한다. 애스펙트는 코드를 한 줄도 건드리지 않고 동작을 바꾸므로, 반대로 동작하지 않을 때도 코드에는 흔적이 없다.

    순서 문제는 트랜잭션과 엮일 때 장애가 된다. 재시도 애스펙트가 트랜잭션 안쪽에서 돌면 이미 롤백 표시가 된 트랜잭션 안에서 다시 시도하게 되고, 바깥쪽에서 돌아야 매 시도가 새 트랜잭션으로 시작된다. @EnableTransactionManagement의 기본 순서는 가장 낮은 우선순위이므로, 순서를 지정하지 않은 애스펙트와의 앞뒤는 문서상 정해져 있지 않다. 테스트 환경에서 우연히 원하는 순서로 동작했더라도, 클래스에 순서를 명시해 두지 않았다면 그것은 보장된 동작이 아니다.

    어드바이스 종류의 선택은 코드 리뷰의 기준이 된다. @Around를 보면 proceed()를 모든 경로에서 정확히 의도한 횟수만큼 부르는지, 반환값을 빠짐없이 돌려주는지, 예외를 삼키는 catch가 없는지를 확인해야 한다. 같은 일을 @Before나 @AfterReturning으로 할 수 있다면 그쪽이 리뷰할 것이 적다. 반대로 실행 전후에 걸친 값을 들고 있어야 한다면, 싱글톤 애스펙트의 필드를 쓰는 대신 @Around의 지역 변수로 들고 있어야 동시 요청에서 안전하다.

    애스펙트(aspect)
    포인트컷과 어드바이스를 하나의 클래스로 묶은 모듈. 스프링에서는 @Aspect가 붙은 빈이며, 어드바이스 메서드 하나가 어드바이저 하나로 바뀐다.
    포인트컷 시그니처(pointcut signature)
    @Pointcut이 붙은 void 메서드. 이름과 매개변수가 포인트컷의 이름이 되고, 다른 식에서 이름()으로 참조한다.
    어라운드 어드바이스(around advice)
    메서드 실행 전체를 감싸는 어드바이스. ProceedingJoinPoint.proceed()로 다음 단계를 직접 호출하며 반환값과 예외를 바꿀 수 있다.
    인터셉터 체인(interceptor chain)
    한 메서드에 적용되는 MethodInterceptor들의 정렬된 목록. 각 인터셉터가 proceed()로 다음 칸을 부르며, 끝에서 대상 메서드가 호출된다.
    ReflectiveMethodInvocation
    스프링 AOP에서 체인 실행을 이끄는 객체. 현재 인덱스를 들고 있다가 proceed()마다 하나씩 올리며 다음 인터셉터를 호출한다.
    ExposeInvocationInterceptor
    현재 메서드 호출 객체를 ThreadLocal에 노출하는 인터셉터. AspectJ 방식 어드바이스가 있는 체인의 맨 앞에 자동으로 추가된다.
    우선순위(precedence)
    같은 조인 포인트에 적용되는 어드바이스 사이의 순서. 높을수록 들어갈 때 먼저, 나올 때 나중에 실행된다. 애스펙트 사이에서는 @Order·Ordered 값이 작을수록 높다.
