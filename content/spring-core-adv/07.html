    06회까지 오면 애플리케이션 코드에는 추적 코드가 한 줄도 남지 않는다. 남은 일은 어드바이저를 빈으로 등록하는 것뿐이다. 그런데 그 등록 코드를 다시 보면 성격이 다른 세 조각이 서로 다른 곳에 있다. 지금까지의 도구만으로 로그 추적 어드바이저를 쓰면 대략 다음과 같은 모양이 된다.

    // 부가 기능: MethodInterceptor 구현 클래스
public class CallTraceInterceptor implements MethodInterceptor {

    private final CallTracer tracer;

    public CallTraceInterceptor(CallTracer tracer) {
        this.tracer = tracer;
    }

    @Override
    public Object invoke(MethodInvocation invocation) throws Throwable {
        TraceScope scope = null;
        try {
            scope = tracer.begin(invocation.getMethod().getName());
            Object result = invocation.proceed();
            tracer.end(scope);
            return result;
        } catch (Exception e) {
            tracer.fail(scope, e);
            throw e;
        }
    }
}

    이 회차의 앞부분은 이 세 조각을 애너테이션이 붙은 클래스 하나로 모으는 @Aspect를 다룬다. 겉으로는 새 기능처럼 보이지만, 컨테이너 안에서는 06회에서 본 것과 똑같은 어드바이저로 바뀐다. 그 변환이 어디에서 어떻게 일어나는지가 이 회차의 첫 번째 질문이다. 뒷부분에서는 한 걸음 물러나, 지금까지 만든 것을 AOP(Aspect-Oriented Programming, 관점 지향 프로그래밍)라는 이름 아래 정리한다. 부가 기능이 왜 객체지향만으로는 잘 모이지 않는지, 부가 기능을 핵심 코드에 끼워 넣는 방식에는 무엇이 있는지, 그리고 AOP 용어가 실제로 어떤 객체를 가리키는지를 본다.

    @Aspect 프록시 — 적용

    앞의 세 조각을 애스펙트(aspect) 클래스 하나로 옮기면 다음과 같다. 추적기 인터페이스 CallTracer와 TraceScope는 01회에서 만든 것을 그대로 쓴다. 추적 대상 코드는 hello.app 패키지 아래에 있다고 하자.

    package hello.trace.aspect;

import hello.trace.CallTracer;
import hello.trace.TraceScope;
import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;

@Aspect
public class CallTraceAspect {

            Object result = joinPoint.proceed();
            tracer.end(scope);
            return result;
        } catch (Exception e) {

        }
    }

    한 줄씩 보자. 클래스에 붙은 @Aspect는 "이 클래스는 애스펙트다"라는 표시다. import 문을 보면 이 애너테이션은 스프링이 아니라 org.aspectj.lang.annotation 패키지에 있다. AspectJ 프로젝트가 AspectJ 5에서 도입한 애너테이션 방식(이른바 @AspectJ 스타일)을 스프링이 그대로 받아들인 것이다. 스프링 레퍼런스는 이 관계를 분명히 적는다. 스프링은 AspectJ 5와 같은 애너테이션을 해석하고 포인트컷의 파싱과 매칭에는 AspectJ가 제공하는 라이브러리를 쓰지만, AOP 실행 자체는 여전히 순수한 스프링 AOP이며 AspectJ 컴파일러나 위버에 의존하지 않는다. 그래서 애플리케이션 클래스패스에 AspectJ의 org.aspectj:aspectjweaver 라이브러리(1.9 이상)가 있어야 한다. 이름에 "weaver"가 들어 있지만 여기서 쓰는 것은 애너테이션과 ProceedingJoinPoint 같은 API 타입, 포인트컷 표현식의 파서와 매처이고, 바이트코드를 바꾸는 위빙 기능은 쓰지 않는다.

    메서드에 붙은 @Around("execution(* hello.app..*(..))")는 두 가지를 한꺼번에 선언한다. 괄호 안의 문자열이 포인트컷이고, 메서드 본문이 어드바이스다. 06회의 설정 코드에서 AspectJExpressionPointcut에 setExpression으로 넣던 문자열이 그대로 애너테이션 속성으로 옮겨 왔다. 표현식은 "hello.app 패키지와 그 하위 패키지에 있는 모든 타입의, 반환 타입·이름·매개변수가 무엇이든 상관없는 모든 메서드 실행"이라는 뜻이다. 표현식 문법은 09회에서 자세히 다루므로 여기서는 이 뜻만 기억하자.

    어드바이스 메서드가 받는 ProceedingJoinPoint는 05회의 MethodInvocation과 같은 자리에 있다. proceed()를 부르면 다음 어드바이스나 실제 대상 메서드가 실행되고 그 반환값이 돌아온다. 그 앞뒤에 무엇을 하든 어드바이스의 자유지만, 그 자유에는 책임이 따른다. 스프링 레퍼런스는 어라운드 어드바이스를 "조인 포인트로 진행할지, 아니면 자기 반환값을 돌려주거나 예외를 던져 대상 메서드 실행을 건너뛸지 고르는 책임이 있는" 어드바이스로 정의한다. proceed() 호출을 빠뜨리면 대상 메서드는 아예 실행되지 않고, return result 대신 return null을 쓰면 호출한 쪽은 대상이 무엇을 반환했든 null을 받는다. 예외를 기록한 뒤 같은 객체를 다시 던지는 이유는 01회에서 본 것과 같다. 추적기는 관찰자이므로 호출 결과를 바꾸면 안 된다.

    마지막 행이 중요하다. 애스펙트는 스프링 빈이어야 동작한다. 위 예제처럼 @Bean으로 등록하거나, 컴포넌트 스캔으로 등록하려면 @Aspect와 함께 @Component를 붙여야 한다. 스프링 레퍼런스는 @Aspect 애너테이션만으로는 클래스패스 자동 감지에 충분하지 않다고 명시한다. @Aspect는 메타 애너테이션으로 @Component를 갖고 있지 않기 때문에, 스캔 범위 안에 @Aspect만 붙인 클래스를 두면 빈이 되지 않고 아무 일도 일어나지 않는다. 오류도 나지 않으므로 "애스펙트를 만들었는데 로그가 안 찍힌다"는 상황에서 가장 먼저 확인할 곳이다.

    설정 클래스의 @EnableAspectJAutoProxy는 @AspectJ 지원을 켜는 스위치다. 스프링 부트를 쓴다면 이 애너테이션을 직접 붙일 필요가 없다. 부트 3.5.16의 AopAutoConfiguration 소스를 보면, 클래스패스에 org.aspectj.weaver.Advice 클래스(즉 aspectjweaver)가 있을 때 @EnableAspectJAutoProxy(proxyTargetClass = true)가 붙은 내부 설정 클래스가 활성화된다. spring.aop.proxy-target-class 속성을 false로 주면 대신 proxyTargetClass = false인 설정이 쓰이고, spring.aop.auto=false면 자동 구성 전체가 꺼진다. 부트 3.x에서 aspectjweaver를 끌어오는 의존성은 spring-boot-starter-aop("Starter for aspect-oriented programming with Spring AOP and AspectJ")이고, 부트 4.1 문서의 스타터 목록에서는 이 자리에 spring-boot-starter-aspectj가 있다. aspectjweaver가 없으면 부트는 클래스 기반 프록시만 강제하는 다른 구성을 쓰는데, 이 경우 등록되는 자동 프록시 생성기는 InfrastructureAdvisorAutoProxyCreator여서 인프라 역할로 등록된 어드바이저 빈(트랜잭션 어드바이저 같은 것)만 처리하고 @Aspect 클래스는 읽지 않는다.

    포인트컷 범위를 정할 때 흔히 하는 실수가 있다. 표현식이 추적기 자신(CallTracer 구현 빈)까지 덮으면, 추적기 빈도 프록시가 되고 애스펙트에 주입되는 것도 그 프록시다. 그러면 어드바이스가 tracer.begin()을 부를 때마다 그 호출이 다시 어드바이스를 실행하고, 그 어드바이스가 또 tracer.begin()을 부른다. 원고를 쓰며 같은 구조(애스펙트가 주입받은 빈이 같은 포인트컷에 걸리는 구성)를 만들어 실행해 보니 주입된 빈의 클래스는 ...$$SpringCGLIB$$0였고 첫 호출에서 StackOverflowError가 났다. 포인트컷은 업무 코드 패키지로 좁히고, 부가 기능이 쓰는 객체는 그 밖에 둔다.

    @Aspect 프록시 — 설명 ①: 자동 프록시 생성기는 하나뿐이다

    @EnableAspectJAutoProxy가 하는 일은 생각보다 작다. 이 애너테이션에는 @Import(AspectJAutoProxyRegistrar.class)가 붙어 있고, 속성은 proxyTargetClass와 exposeProxy 두 개뿐이며 기본값은 둘 다 false다. 설정 클래스를 처리하는 단계에서 AspectJAutoProxyRegistrar가 호출되면, 이 클래스는 AopConfigUtils.registerAspectJAnnotationAutoProxyCreatorIfNecessary(registry)를 부르고, 속성값에 따라 프록시 생성기의 설정 값(proxyTargetClass, exposeProxy)을 바꾼다. 결국 이 애너테이션의 본업은 AnnotationAwareAspectJAutoProxyCreator의 빈 정의 하나를 등록하는 것이다.

    AopConfigUtils를 열어 보면 자동 프록시 생성기를 등록하는 방법이 하나로 모여 있다. 등록 메서드는 세 가지이고 각각 다른 클래스를 등록하려 한다.

    이 설계 덕분에 트랜잭션(@EnableTransactionManagement)과 @Aspect를 함께 써도 자동 프록시 생성기는 하나만 생긴다. 트랜잭션 쪽이 먼저 InfrastructureAdvisorAutoProxyCreator를 등록했더라도, 뒤이어 @EnableAspectJAutoProxy가 처리되면 같은 이름의 빈 정의가 AnnotationAwareAspectJAutoProxyCreator로 승격된다. 순서가 반대여도 낮은 쪽은 높은 쪽을 끌어내리지 못한다. 생성기가 둘이었다면 한 빈이 두 번 감싸져 프록시의 프록시가 생길 수 있지만, 생성기가 하나이므로 트랜잭션 어드바이저와 우리 애스펙트의 어드바이저는 한 프록시의 한 체인에 함께 들어간다. 한 빈에 어드바이저가 여러 개 해당해도 프록시는 하나만 만든다는 자동 프록시 생성기의 성질이, 기능의 출처(트랜잭션 설정, 캐시 설정, 우리 애스펙트)가 달라도 유지되는 이유가 여기 있다.

    @Aspect 프록시 — 설명 ②: 애스펙트 클래스를 어드바이저로 바꾸기

    06회에서 자동 프록시 생성기는 "후보 어드바이저를 모두 찾고, 그중 이 빈에 적용할 수 있는 것을 고른 뒤, 하나라도 있으면 프록시를 만든다"는 순서로 일했다. AnnotationAwareAspectJAutoProxyCreator가 바꾸는 것은 그중 첫 단계, 후보를 찾는 findCandidateAdvisors() 하나다. 소스는 다음과 같이 짧다.

    // AnnotationAwareAspectJAutoProxyCreator (spring-aop)
@Override
protected List findCandidateAdvisors() {
    // Add all the Spring advisors found according to superclass rules.
    List advisors = super.findCandidateAdvisors();
    // Build Advisors for all AspectJ aspects in the bean factory.
    if (this.aspectJAdvisorsBuilder != null) {
        advisors.addAll(this.aspectJAdvisorsBuilder.buildAspectJAdvisors());
    }
    return advisors;
}

    상위 클래스의 구현은 컨테이너에서 Advisor 타입의 빈을 모두 찾아 온다. 06회의 방식이 그대로 살아 있다. 여기에 BeanFactoryAspectJAdvisorsBuilder.buildAspectJAdvisors()의 결과, 즉 @Aspect 빈에서 만들어 낸 어드바이저들을 덧붙인다. 그러니까 @Aspect는 어드바이저와 경쟁하는 다른 메커니즘이 아니라, 어드바이저를 만드는 또 하나의 방법이다. 변환은 다음 순서로 일어난다.

    이 첫 호출은 동기화 블록 안에서 이중 확인(double-checked locking)으로 한 번만 실행된다. aspectBeanNames가 채워진 뒤의 호출은 모든 빈을 다시 훑지 않고 캐시에서 어드바이저 목록을 꺼내 합치기만 한다. 첫 호출이 언제 일어나는지도 소스에서 따라갈 수 있다. 자동 프록시 생성기는 빈이 생성되기 직전(postProcessBeforeInstantiation)과 초기화된 직후(postProcessAfterInitialization)에 "이 빈은 건너뛸 대상인가"를 묻는 shouldSkip을 호출하는데, 상위 클래스 AspectJAwareAdvisorAutoProxyCreator의 shouldSkip이 맨 처음에 findCandidateAdvisors()를 부른다. 따라서 생성기가 등록된 뒤 인프라 클래스가 아닌 빈이 처음 만들어질 때 그 생성 과정에서 애스펙트 변환이 일어나고, 그 뒤로는 캐시가 쓰인다.

    다섯 번째 단계의 getAdvisors를 조금 더 들여다보자. 이 메서드는 애스펙트 클래스(상위 클래스 포함)에서 사용자가 선언한 메서드를 모으되 @Pointcut이 붙은 메서드는 뺀다. 그리고 모은 메서드를 어드바이스 종류 순서(@Around, @Before, @After, @AfterReturning, @AfterThrowing), 같은 종류 안에서는 메서드 이름 순서로 정렬한다. 소스 주석에 따르면 5.2.7 이전에는 메서드를 찾은 순서를 "애스펙트 안의 선언 순서"로 썼는데, 자바 7부터 JDK가 선언된 메서드를 소스 순서대로 돌려주지 않아 그 값을 믿을 수 없었다. 그래서 지금은 그 값을 모두 0으로 고정하고, JVM을 다시 띄워도 같은 순서가 나오도록 위의 정렬에 맡긴다. 원고를 쓰며 이름순으로는 반대가 되도록 aBefore(@Before)와 zAround(@Around)를 가진 애스펙트를 만들어 보니, 어드바이저 목록에는 zAround가 먼저 나왔다. 정렬된 메서드마다 getAdvisor를 부르고, getAdvisor는 메서드에서 AspectJ 애너테이션을 찾는다. 애너테이션이 없는 보통 메서드(도우미 메서드 등)는 여기서 null이 되어 버려진다. 애너테이션이 있으면 그 속성 문자열로 AspectJExpressionPointcut을 만들고, 포인트컷과 메서드를 묶어 InstantiationModelAwarePointcutAdvisorImpl을 만든다. 실험 출력의 InstantiationModelAwarePointcutAdvisor: expression [...]; advice method [...]가 바로 이 객체의 toString이다.

    어드바이저 안의 어드바이스 객체는 애너테이션 종류에 따라 정해진다. ReflectiveAspectJAdvisorFactory.getAdvice는 애너테이션 종류로 분기하는 switch문이고, 싱글톤 애스펙트라면 어드바이저 생성자에서 바로 호출된다.

    애너테이션만들어지는 어드바이스 클래스구현하는 스프링 AOP 인터페이스
    @AroundAspectJAroundAdviceMethodInterceptor
    @BeforeAspectJMethodBeforeAdviceMethodBeforeAdvice
    @AfterAspectJAfterAdviceMethodInterceptor, AfterAdvice
    @AfterReturningAspectJAfterReturningAdviceAfterReturningAdvice, AfterAdvice
    @AfterThrowingAspectJAfterThrowingAdviceMethodInterceptor, AfterAdvice
    @Pointcut(없음, 어드바이스가 아니다)-

    표의 셋째 열이 05회와 이어지는 지점이다. 어떤 애너테이션으로 쓰든 결과물은 05회에서 본 스프링 AOP의 어드바이스 타입이다. MethodBeforeAdvice와 AfterReturningAdvice는 MethodInterceptor가 아니지만, 프록시가 체인을 만들 때 DefaultAdvisorAdapterRegistry에 등록된 어댑터가 이것들을 인터셉터로 감싼다. 결국 프록시가 실행하는 것은 언제나 MethodInterceptor의 줄이다. 어드바이스 종류별 쓰임새와 순서는 08회에서 다룬다. 이 밖에 애스펙트 클래스의 필드에 @DeclareParents가 붙어 있으면 DeclareParentsAdvisor가 만들어지는데, 이것은 뒤의 용어 정리에서 볼 인트로덕션이다.

    애스펙트 클래스의 메서드 각각이 포인트컷+어드바이스 한 쌍(어드바이저)으로 변환되고, 어드바이저 빈과 합쳐져 후보 목록이 된다는 것을 보여 준다. 흰 배경의 깔끔한 기술 흐름도, 왼쪽에서 오른쪽으로 진행. 맨 왼쪽에 코드 카드 모양의 상자 "@Aspect CallTraceAspect"가 있고, 그 안에 세로로 세 줄이 있다: 첫 줄 "@Around trace()", 둘째 줄 "@Before check()", 셋째 줄은 흐린 회색 글씨 "helper()". 가운데에 톱니바퀴 아이콘이 붙은 둥근 상자 "ReflectiveAspectJAdvisorFactory"가 있다. 첫 줄과 둘째 줄에서 이 상자로 실선 화살표가 들어가고, 셋째 줄에서는 짧은 점선이 나와 작은 X 표시에서 끝난다. 가운데 상자의 오른쪽으로 두 개의 알약 모양 상자가 나온다. 각 알약은 왼쪽 반이 파란색 "포인트컷", 오른쪽 반이 주황색 "어드바이스"로 나뉘어 있고, 알약 위에 "어드바이저"라는 작은 라벨이 있다. 아래쪽 별도 줄에 회색 상자 "Advisor 빈"이 있고 위로 화살표가 올라간다. 두 알약과 "Advisor 빈"이 맨 오른쪽의 세로 목록 상자 "후보 어드바이저"로 모인다. 목록 상자 옆에 작은 원통 아이콘과 "캐시"라는 라벨. 파랑, 주황, 회색 위주의 단정한 색. 애스펙트의 어드바이스 메서드 하나가 어드바이저 하나가 되고, 애너테이션이 없는 메서드는 버려진다. 결과는 Advisor 빈과 합쳐져 후보 목록이 된다.

    @Aspect 프록시 — 설명 ③: 빈 하나가 프록시가 되는 순간

    후보 어드바이저가 준비된 뒤, 각 빈이 초기화를 마치면 postProcessAfterInitialization이 wrapIfNecessary(bean, beanName, cacheKey)를 부른다. 06회에서 본 흐름에 @Aspect가 더한 것만 표시하며 따라가 보자.

    먼저 isInfrastructureClass로 프록시를 만들면 안 되는 빈을 거른다. 기본 구현은 빈 클래스가 Advice, Pointcut, Advisor, AopInfrastructureBean 중 하나의 하위 타입이면 참을 돌려준다. 부가 기능을 이루는 부품 자체에 부가 기능을 붙이면 순환이 생길 수 있기 때문이다. AnnotationAwareAspectJAutoProxyCreator는 이 메서드를 재정의해 애스펙트 클래스도 인프라로 취급한다. 소스 주석에 그 이유가 적혀 있다. 애스펙트를 프록시로 만들면 어드바이스 호출이 프록시를 거치게 되고, 애스펙트가 Ordered 같은 인터페이스를 구현한 경우 그 인터페이스로 JDK 프록시가 만들어져 어드바이스 메서드를 찾지 못하고 실행 중에 실패한다는 것이다. 앞의 실험에서 애스펙트 빈이 원래 클래스 그대로였던 것이 이 재정의의 결과다.

    다음은 findEligibleAdvisors다. 네 단계로 이루어진다.

    1. 후보 수집: 앞 절의 findCandidateAdvisors(). 어드바이저 빈과 애스펙트에서 변환한 어드바이저가 모두 들어 있다.
    2. 적용 가능성 검사: AopUtils.canApply가 어드바이저마다 포인트컷의 ClassFilter로 빈 클래스를 먼저 검사하고, 통과하면 그 클래스와 그 클래스가 구현한 모든 인터페이스에 선언된 메서드를 하나씩 MethodMatcher에 넣어 본다. 하나라도 맞으면 그 어드바이저는 이 빈에 적용 가능하다. 포인트컷은 여기서 "프록시를 만들 것인가"를 정하는 데 한 번 쓰이고, 나중에 프록시가 호출될 때 "이 메서드에 어떤 인터셉터를 적용할 것인가"를 정하는 데 다시 쓰인다.
    3. 목록 확장: extendAdvisors가 AspectJProxyUtils.makeAdvisorChainAspectJCapableIfNecessary를 부른다. 고른 목록에 AspectJ 방식의 어드바이스가 하나라도 있으면 목록 맨 앞(인덱스 0)에 ExposeInvocationInterceptor.ADVISOR를 끼워 넣는다. 실험 출력에서 우리가 등록하지 않은 어드바이저가 맨 앞에 있었던 이유다.
    4. 정렬: sortAdvisors가 AspectJPrecedenceComparator로 순서를 정한다. 애스펙트 사이의 순서를 @Order로 정하는 방법은 08회에서 다룬다.

    결과 목록이 비어 있지 않으면 createProxy가 05회의 ProxyFactory를 만들어 타깃과 어드바이저를 넣고 프록시를 얻는다. 이때 proxyTargetClass 설정과 빈이 구현한 인터페이스를 보고 JDK 프록시와 CGLIB 프록시 중 하나가 정해진다. 프록시가 컨테이너에 원래 빈 대신 등록되고, 이 빈을 주입받는 모든 곳에는 프록시가 들어간다. 실험에서 OrderServiceImpl이 주입받은 stock 필드도 CGLIB 프록시였기 때문에 order 안에서 부른 stock.reserve에도 로그가 찍혔다.

    그렇다면 맨 앞에 끼워 넣은 ExposeInvocationInterceptor는 무슨 일을 할까? 소스는 단순하다.

    // ExposeInvocationInterceptor (spring-aop), 일부
private static final ThreadLocal invocation =
        new NamedThreadLocal<>("Current AOP method invocation");

@Override
public Object invoke(MethodInvocation mi) throws Throwable {
    MethodInvocation oldInvocation = invocation.get();
    invocation.set(mi);
    try {
        return mi.proceed();
    }
    finally {
        invocation.set(oldInvocation);
    }
}

    01회의 ThreadLocal이 여기서 다시 나온다. 이 인터셉터는 지금 진행 중인 메서드 호출 객체를 현재 스레드의 칸에 넣고, 체인의 나머지를 실행한 뒤, finally에서 이전 값으로 되돌린다. 값을 지우지 않고 이전 값으로 되돌리는 이유는 호출이 중첩되기 때문이다. 실험에서 order의 어드바이스가 실행되는 도중에 reserve의 프록시 호출이 다시 이 인터셉터를 지나는데, 안쪽 호출이 끝나면 칸에는 바깥 호출의 객체가 다시 들어 있어야 한다. 이 칸을 읽는 쪽은 AspectJ 방식의 어드바이스다. @Before 어드바이스로 변환된 AspectJMethodBeforeAdvice는 before(method, args, target)라는 시그니처로 불리므로 MethodInvocation을 직접 받지 못한다. 그런데 어드바이스 메서드가 JoinPoint를 매개변수로 원하면 그것을 만들어 줘야 한다. 그래서 AbstractAspectJAdvice.currentJoinPoint()는 ExposeInvocationInterceptor.currentInvocation()으로 이 칸을 읽어 조인 포인트 객체를 만든다. 체인 맨 앞에 이 인터셉터가 있어야 하는 이유다.

    클라이언트 호출이 프록시, ReflectiveMethodInvocation, ExposeInvocationInterceptor, AspectJAroundAdvice, 애스펙트 메서드를 차례로 지나 타깃에 도착하고, 반환값이 같은 길로 돌아가는 것을 보여 준다. 흰 배경의 세로 생명선 시퀀스 다이어그램. 왼쪽부터 생명선 7개가 있고 머리 상자 라벨은 차례로 "클라이언트", "프록시 ($Proxy / $$SpringCGLIB$$)", "ReflectiveMethodInvocation", "ExposeInvocationInterceptor", "AspectJAroundAdvice", "TraceAspect.trace()", "타깃 객체"이다. 위에서 아래로 실선 화살표가 오른쪽으로 한 칸씩 이어진다: "클라이언트"에서 "프록시"로 "order(book)", "프록시"에서 "ReflectiveMethodInvocation"으로 "proceed()", 거기서 "ExposeInvocationInterceptor"로 "invoke(mi)", "ExposeInvocationInterceptor" 옆에 작은 사물함 아이콘과 "ThreadLocal에 mi 저장" 메모, 다시 "ReflectiveMethodInvocation"을 거쳐 "AspectJAroundAdvice"로 "invoke(mi)", 거기서 "TraceAspect.trace()"로 "Method.invoke", "TraceAspect.trace()"에서 "ReflectiveMethodInvocation"으로 되돌아가는 화살표 "pjp.proceed()", 마지막으로 "ReflectiveMethodInvocation"에서 "타깃 객체"로 "Method.invoke". 아래쪽에는 점선 화살표가 오른쪽에서 왼쪽으로 "ok:book" 반환값을 클라이언트까지 되돌린다. 단정한 선, 파랑과 회색 위주, 반환 화살표는 초록 점선. 프록시는 체인 객체에 호출을 넘기고, 체인은 인덱스를 하나씩 올리며 인터셉터를 부른다. 애스펙트의 proceed()는 그 체인을 한 칸 더 진행시킨다.

    정리 — 로그 추적기가 걸어온 일곱 단계

    @Aspect까지 오면서 로그 추적기는 한 번도 "새로운 원리"로 갈아타지 않았다. 각 단계는 앞 단계의 한계 하나를 고치면서 앞 단계를 부품으로 삼았다. 표로 정리해 보면 각 회차의 도구가 최종 구조의 어느 층에 남아 있는지 보인다.

    회차도구해결한 것남긴 한계최종 구조에서의 자리
    01ThreadLocal싱글톤 추적기의 요청별 문맥모든 메서드에 추적 코드CallTracer 구현, ExposeInvocationInterceptor
    02템플릿 메서드·전략·템플릿 콜백시작·종료·예외 뼈대의 중복호출 지점은 여전히 원본 코드 안인터셉터와 proceed()의 구조
    03프록시·데코레이터원본 코드 수정 없이 기능 추가클래스마다 프록시 클래스컨테이너에 등록되는 프록시 객체

    마지막 열을 위에서 아래로 읽으면 @Aspect 한 줄이 실행될 때 일어나는 일이 된다. 애스펙트 클래스가 어드바이저로 바뀌고(07), 자동 프록시 생성기가 빈마다 적용 가능한 어드바이저를 골라(06), ProxyFactory로(05) JDK 프록시나 CGLIB 프록시를 만들고(04), 그 프록시가 원래 빈 대신 주입되며(03), 호출이 오면 인터셉터 체인이 템플릿처럼 앞뒤를 감싸고(02), 추적 문맥은 ThreadLocal로 이어진다(01). @Aspect는 편리한 문법이지만, 그 아래에는 이 회차까지 쌓아 온 모든 층이 그대로 있다.

    그러면 이 구조에 붙은 이름은 무엇인가. "부가 기능을 한 곳에 모아 두고, 어디에 적용할지를 선언하면, 프레임워크가 그것을 대상 코드에 엮어 준다"는 생각 자체를 AOP라고 부른다. 지금부터는 코드에서 한 걸음 떨어져, 그 생각이 무엇을 해결하려는 것인지, 그리고 스프링이 택한 프록시 방식이 AOP의 여러 구현 방식 가운데 어디에 있는지를 본다.

    AOP 소개 — 핵심 기능과 부가 기능

    애플리케이션의 기능은 성격에 따라 둘로 나눌 수 있다. 핵심 기능(core concern)은 그 객체가 존재하는 이유다. 대출 서비스라면 "이 회원이 이 책을 빌릴 수 있는가를 검사하고 대출 기록을 남긴다"가 핵심 기능이다. 부가 기능은 핵심 기능을 보조하기 위해 덧붙는 기능이다. 이 권에서 계속 다룬 로그 추적이 그렇고, 실행 시간 측정, 트랜잭션의 시작과 커밋·롤백, 호출 권한 확인, 예외 변환도 그렇다. 부가 기능에는 두 가지 성질이 있다. 하나는 그것만 따로 떼어서는 의미가 없다는 것이다. 로그 추적은 추적할 메서드가 있어야 의미가 있다. 다른 하나는 특정 기능 하나에 속하지 않고 여러 기능에 공통으로 걸친다는 것이다. 로그 추적은 대출 기능에도, 회원 기능에도, 결제 기능에도 똑같이 필요하다.

    두 번째 성질 때문에 부가 기능을 횡단 관심사(cross-cutting concern)라고 부른다. 클래스들을 세로로 세워 놓고 부가 기능을 가로줄로 그으면, 가로줄 하나가 여러 클래스를 관통한다. 텍스트로 그리면 이런 모양이다.

                        로그 추적    트랜잭션    권한 확인    │ 핵심 로직
                  ──────────────────────────────────────┼──────────────────
LoanController    ■                         ■           │ 대출 요청 받기
LoanService       ■            ■                        │ 대출 규칙 검사
MemberService     ■            ■            ■           │ 회원 등급 변경
LoanRepository    ■                                     │ 대출 기록 저장
                  ──────────────────────────────────────┼──────────────────
                  ↑ 세로 한 줄(관심사 하나)이              ↑ 가로 한 줄(클래스 하나)이
                    여러 클래스를 관통한다                    여러 관심사를 품는다

    이 그림에서 문제가 두 방향으로 보인다. 세로로 읽으면 같은 관심사의 코드가 여러 클래스에 흩어진다(scattering). 로그 형식을 바꾸려면 ■가 있는 모든 클래스를 고쳐야 하고, 한 곳이라도 빠뜨리면 로그가 어긋난다. 가로로 읽으면 한 클래스, 한 메서드 안에 여러 관심사가 뒤엉킨다(tangling). 부가 기능을 핵심 코드에 직접 쓰면 메서드는 다음과 같이 된다.

    public Loan borrow(String memberId, String bookId) {
    TraceScope scope = tracer.begin("LoanService.borrow()");                   // 로그 추적
    TransactionStatus tx = txManager.getTransaction(new DefaultTransactionDefinition()); // 트랜잭션
    try {
        authChecker.requireMember(memberId);                                    // 권한 확인
        Loan loan = loanPolicy.check(memberId, bookId);                         // 핵심 로직
        loanRepository.save(loan);                                              // 핵심 로직
        txManager.commit(tx);                                                   // 트랜잭션
        tracer.end(scope);                                                      // 로그 추적
        return loan;
    } catch (RuntimeException e) {
        txManager.rollback(tx);                                                 // 트랜잭션
        tracer.fail(scope, e);                                                  // 로그 추적
        throw e;
    }
}
// tracer, txManager, authChecker, loanPolicy, loanRepository 필드 선언은 생략

    열다섯 줄 남짓한 메서드에서 이 메서드만의 일은 두 줄이다. 나머지는 다른 수십 개 메서드에도 똑같이 들어 있는 줄이다. 읽는 사람은 핵심 로직을 찾으려고 부가 기능 코드를 걷어 내며 읽어야 하고, 테스트하는 사람은 대출 규칙 하나를 확인하려고 트랜잭션 관리자와 추적기를 준비해야 한다. 순서에도 함정이 숨어 있다. 위 코드에서 권한 확인이 실패하면 예외가 catch로 가서 롤백되고 실패 로그가 남는데, 권한 확인을 트랜잭션 시작 앞으로 옮기면 그렇지 않다. 부가 기능 사이의 순서라는 결정까지 모든 메서드에 복제되는 셈이다.

    객체지향의 도구로 이 문제를 풀어 보려 한 것이 01~02회다. 공통 코드를 추적기 객체로 뽑고(위임), 뼈대를 템플릿으로 모았다(템플릿 메서드, 템플릿 콜백). 그러면 부가 기능의 본문은 한 곳에 모인다. 하지만 "이 메서드에 로그 추적을 적용한다"는 적용 결정, 즉 템플릿을 호출하는 코드는 여전히 각 메서드 안에 남는다. 이것은 객체지향이 잘못되어서가 아니라, 객체지향이 프로그램을 나누는 축이 하나이기 때문이다. 클래스는 "무엇에 대한 책임인가"(대출, 회원, 결제)라는 축으로 나뉜다. 횡단 관심사는 그 축을 가로지르므로, 어떤 클래스에 담든 다른 클래스들이 그 클래스를 불러야 하고, 부르는 코드가 흩어진다.

    03~06회는 방향을 뒤집었다. 핵심 클래스가 부가 기능을 부르는 대신, 부가 기능 쪽이 "나는 이 클래스들의 이 메서드들 앞에 선다"고 선언하고, 컨테이너가 그 선언대로 프록시를 세웠다. 이렇게 하면 LoanService의 코드는 로그 추적의 존재를 전혀 모른다. 적용 결정이 핵심 코드 밖의 한 곳으로 옮겨 간 것이다. 이것이 AOP가 하려는 일의 전부다.

    AOP 소개 — 애스펙트

    스프링 레퍼런스는 AOP 장을 이렇게 시작한다. AOP는 프로그램 구조를 생각하는 또 다른 방법을 제공해 객체지향 프로그래밍(OOP)을 보완한다. OOP에서 모듈화의 핵심 단위는 클래스이고, AOP에서는 애스펙트(aspect)다. 애스펙트는 여러 타입과 객체에 걸치는 관심사(예: 트랜잭션 관리)를 모듈화할 수 있게 해 주며, 그런 관심사를 AOP 문헌에서는 흔히 "횡단(crosscutting)" 관심사라고 부른다.

    앞의 표로 말하면, 애스펙트는 세로줄 하나를 통째로 들어 한 곳에 모은 모듈이다. 그 모듈에는 두 가지 정보가 있어야 한다. 무엇을 할 것인가(어드바이스)와 어디에 할 것인가(포인트컷)다. 어디에가 빠지면 부가 기능은 아무 데도 붙지 않고, 무엇을이 빠지면 붙일 것이 없다. 05회의 어드바이저가 바로 이 둘의 최소 묶음이었다. 스프링 레퍼런스도 "스프링에서 어드바이저는 포인트컷 표현식과 연결된 어드바이스 객체 하나만 가진 애스펙트"라고 정의한다. @Aspect 클래스는 여기서 한 걸음 더 나가, 여러 어드바이스와 포인트컷을 한 클래스에 담을 수 있는 애스펙트다. 앞에서 본 것처럼 컨테이너 안에서는 어드바이스 메서드 수만큼의 어드바이저로 풀린다.

    애스펙트라는 단위가 생기면 앞의 그림이 달라진다. 로그 추적 열의 ■들이 사라지고, 그 자리에 CallTraceAspect 하나가 "hello.app 아래의 모든 메서드"라는 범위를 들고 선다. 트랜잭션 열도 마찬가지로 트랜잭션 애스펙트 하나가 된다. 실제로 스프링의 @Transactional은 트랜잭션 어드바이저(포인트컷은 "@Transactional이 붙은 메서드나 클래스", 어드바이스는 트랜잭션 인터셉터)로 구현되어 있어서, 앞에서 본 자동 프록시 생성기의 승격 덕분에 우리 애스펙트와 같은 프록시의 같은 체인에 들어간다. 스프링 레퍼런스가 AOP의 쓰임새로 가장 먼저 꼽는 것도 선언적 트랜잭션 관리다.

    AOP가 OOP를 대체하는 것은 아니라는 점도 짚어 두자. 애스펙트 자신도 클래스이고, 필드와 메서드를 갖고, 다른 빈을 주입받는다. 핵심 로직은 여전히 객체와 메시지로 설계한다. AOP는 객체지향의 축으로 잘 나뉘지 않는 관심사만 별도의 단위로 떼어 낼 뿐이다. 그리고 그 대가도 있다. LoanService의 소스만 읽어서는 그 메서드에 무엇이 덧붙는지 알 수 없다. 동작이 코드 밖에서 결정되므로, 앞의 호출 스택처럼 실행 경로에 낯선 프레임이 끼고, 포인트컷이 의도보다 넓거나 좁으면 조용히 잘못 동작한다. 애스펙트를 쓸 때는 적용 범위를 좁고 분명하게 쓰는 것이 이 대가를 줄이는 방법이다.

    AOP를 자바에서 가장 완전하게 구현한 것이 AspectJ다. AspectJ는 자바에 애스펙트 문법을 더한 언어이자 그 컴파일러(ajc)와 위버(weaver)를 포함하는 도구다. 처음에는 aspect라는 전용 키워드를 쓰는 문법만 있었고, AspectJ 5에서 일반 자바 클래스에 애너테이션을 붙여 애스펙트를 쓰는 @AspectJ 스타일이 도입됐다. 스프링이 읽는 @Aspect, @Around가 바로 그 애너테이션이다. 스프링 레퍼런스는 스프링 AOP가 AspectJ와 경쟁하려는 것이 아니며, 프록시 기반 프레임워크와 AspectJ 같은 완전한 프레임워크는 경쟁이 아니라 서로 보완하는 관계라고 설명한다. 둘의 차이는 결국 "부가 기능을 핵심 코드에 언제, 어떻게 엮는가"에서 나온다.

    AOP 적용 방식 — 부가 기능을 언제 끼워 넣는가

    애스펙트를 대상 코드에 엮는 일을 위빙(weaving)이라고 한다. 스프링 레퍼런스의 정의는 "애스펙트를 다른 애플리케이션 타입이나 객체와 연결해 어드바이스가 적용된 객체를 만드는 것"이고, 이 일은 컴파일 시점, 로드 시점, 런타임에 할 수 있으며, 스프링 AOP는 다른 순수 자바 AOP 프레임워크처럼 런타임에 위빙한다. AspectJ 개발 가이드는 AspectJ 위버가 클래스 파일을 입력으로 받아 클래스 파일을 출력한다고 설명하면서, 위빙이 일어날 수 있는 시점을 컴파일 시점, 컴파일 후(post-compile), 로드 시점 셋으로 나눈다. 자바 클래스 하나가 소스에서 실행 중인 객체가 되기까지의 길 위에 이 시점들을 올려 보면 다음과 같다.

      .java 소스 ──javac/ajc──▶ .class 파일 ──jar──▶ 클래스 로더 ──▶ 메서드 영역의 클래스 ──new──▶ 힙의 객체
      │                         │                     │                                         │
  ① 컴파일 시점             ② 컴파일 후            ③ 로드 시점                                 ④ 런타임
  ajc가 소스를 컴파일하며    ajc가 이미 만든        에이전트가 바이트 배열을                    원본 클래스는 그대로,
  애스펙트를 엮는다          .class·jar를 엮는다     JVM에 넘기기 직전에 바꾼다                  앞에 프록시 객체를 세운다
  └────────────── 대상 클래스의 바이트코드가 바뀐다 ──────────────┘                   └─ 바이트코드는 그대로 ─┘

    컴파일 시점 위빙은 javac 대신 AspectJ 컴파일러 ajc로 소스를 컴파일하면서 애스펙트를 엮는다. AspectJ 가이드는 이것을 가장 단순한 방법이라고 부른다. 결과로 나온 .class 파일에는 이미 어드바이스 호출이 들어 있으므로, 실행할 때는 특별한 설정이 필요 없다. 대신 빌드에 ajc를 넣어야 한다. 컴파일 후 위빙(바이너리 위빙)은 이미 컴파일된 클래스 파일이나 jar를 ajc에 넣어 엮는다. 소스가 없는 라이브러리에도 적용할 수 있다.

    로드 시점 위빙(load-time weaving, LTW)은 AspectJ 가이드의 표현으로 "클래스 로더가 클래스 파일을 로드하는 시점까지 미뤄 둔 바이너리 위빙"이다. JVM을 -javaagent:경로/aspectjweaver.jar 옵션으로 띄우면, 이 에이전트가 클래스 로딩을 가로채 바이트 배열이 클래스로 정의되기 직전에 바꾼다. 어떤 애스펙트를 어떤 클래스에 엮을지는 클래스패스의 META-INF/aop.xml로 정한다. 빌드는 그대로 두고 실행 방식만 바꾸면 된다는 장점이 있지만, JVM 실행 옵션을 바꿔야 한다. 스프링도 @EnableLoadTimeWeaving과 spring-instrument 에이전트로 이 방식을 지원한다.

    런타임 위빙은 스프링 AOP가 쓰는 방식이고, 이 권에서 지금까지 한 것이 전부 여기에 속한다. 대상 클래스의 바이트코드는 한 글자도 바뀌지 않는다. 대신 대상과 같은 타입의 새 클래스(JDK 프록시나 CGLIB 하위 클래스)를 실행 중에 만들고, 그 인스턴스를 대상 앞에 세운다. 스프링 레퍼런스는 이 방식이 순수 자바로 구현되어 특별한 컴파일 과정이 필요 없고, 클래스 로더 계층을 제어할 필요도 없어 서블릿 컨테이너나 애플리케이션 서버에서 쓰기 알맞다고 설명한다. 그 대신 부가 기능이 붙는 것은 "프록시를 통해 들어오는 호출"뿐이다. 이 제약이 무엇을 뜻하는지는 바이트코드를 실제로 바꾸는 방식과 나란히 놓아야 잘 보인다.

    소스에서 객체까지 이어지는 한 줄의 흐름 위에서, 앞의 세 시점은 클래스 자체를 바꾸고 마지막 런타임 방식은 클래스를 그대로 둔 채 앞에 프록시를 세운다는 대비를 보여 준다. 흰 배경의 가로 타임라인 그림. 왼쪽에서 오른쪽으로 다섯 개의 아이콘이 화살표로 이어진다: 문서 아이콘 ".java", 상자 아이콘 ".class", 깔때기 모양 "클래스 로더", 서랍장 모양 "메서드 영역", 동그란 객체 아이콘 "힙의 객체". 각 화살표 아래에 번호 원과 라벨이 있다: ".java"와 ".class" 사이에 "① 컴파일 시점 (ajc)", ".class" 아래에 "② 컴파일 후", "클래스 로더" 아래에 "③ 로드 시점 (-javaagent)", "힙의 객체" 아래에 "④ 런타임 (프록시)". ①②③ 아래에는 같은 주황색 띠가 이어져 있고 띠 안에 "클래스의 바이트코드를 바꾼다"라고 적는다. ④ 아래에는 파란색 띠가 있고 "원본은 그대로, 앞에 프록시"라고 적으며, 객체 아이콘 앞에 반투명한 방패 모양 객체가 겹쳐 서 있다. 단정한 선, 주황과 파랑의 대비. ①~③은 대상 클래스의 바이트코드를 바꾸고, ④(스프링 AOP)는 대상 클래스를 그대로 둔 채 앞에 프록시 객체를 세운다.

    프록시 방식이 닿는 곳과 닿지 않는 곳

    두 실험의 결과를 조인 포인트별로 정리하면 다음과 같다. 스프링 쪽 근거는 실험과 스프링 레퍼런스이고, AspectJ 쪽 근거는 로드 타임 위빙 실험과 스프링 레퍼런스의 포인트컷 지정자 목록이다.

    대상스프링 AOP(런타임, 프록시)AspectJ(바이트코드 위빙)
    스프링 빈의 메서드를 다른 객체가 빈 참조로 호출적용된다적용된다
    같은 객체 안에서 this.method()로 호출적용되지 않는다(프록시를 거치지 않는다)적용된다(실험의 check)
    private 메서드적용되지 않는다적용된다
    final 메서드적용되지 않는다(재정의할 수 없다)적용된다(실험)
    static 메서드적용되지 않는다(객체를 거치지 않는다)적용된다(실험)
    컨테이너 밖에서 new로 만든 객체적용되지 않는다적용된다(실험의 PlainMain)
    객체 초기화, 필드 읽기·쓰기, 예외 핸들러, 정적 초기화조인 포인트가 아니다. 이를 고르는 initialization, get, set, handler, staticinitialization 지정자를 쓰면 IllegalArgumentException조인 포인트로 지원한다

    스프링 레퍼런스는 이 한계를 직접 밝힌다. 스프링 AOP는 현재 메서드 실행 조인 포인트(스프링 빈의 메서드 실행에 대한 어드바이스)만 지원하고, 필드 가로채기는 구현되어 있지 않다. 프록시 기반이라는 성질 때문에 대상 객체 안에서 일어나는 호출은 정의상 가로채지 않는다. JDK 프록시에서는 프록시를 통한 public 인터페이스 메서드 호출만, CGLIB에서는 프록시를 통한 public과 protected 메서드 호출(필요하면 패키지 가시성 메서드까지)만 가로챌 수 있다. 그리고 final 메서드는 재정의할 수 없으므로 어드바이스를 적용할 수 없다. AspectJ에는 있지만 스프링 AOP가 지원하지 않는 포인트컷 지정자(call, get, set, preinitialization, staticinitialization, initialization, handler, adviceexecution, withincode, cflow, cflowbelow, if, @this, @withincode)를 스프링 AOP가 해석하는 표현식에 쓰면 IllegalArgumentException이 난다.

    이 표의 모든 "적용되지 않는다"는 하나의 원인에서 나온다. 프록시는 호출 경로 위에 서는 객체이므로, 호출이 그 객체를 지나지 않으면 아무 일도 하지 않는다. this.check()는 프록시가 아니라 타깃 자신의 참조로 부르는 호출이고, static 메서드 호출에는 지나갈 객체가 없으며, new로 만든 객체에는 앞에 선 프록시가 없다. 반대로 바이트코드 위빙은 실행되는 코드 자체를 바꾸므로 호출 경로와 상관없다. 이 중 내부 호출 문제는 실무에서 가장 자주 부딪히는 함정이어서 10회에서 원인과 해결책을 따로 다룬다. JDK 프록시와 CGLIB 프록시를 고르는 일이 타입 캐스팅과 의존관계 주입에 미치는 영향도 10회에서 본다.

    그렇다면 왜 스프링은 기능이 적은 쪽을 기본으로 택했을까? 스프링 레퍼런스는 스프링 AOP의 목표가 가장 완전한 AOP 구현이 아니라 AOP 구현과 스프링 IoC의 긴밀한 통합이라고 말한다. 엔터프라이즈 애플리케이션에서 부가 기능이 필요한 지점, 즉 트랜잭션 경계, 보안 검사, 로그 추적, 실행 시간 측정은 대부분 서비스 객체의 public 메서드 경계다. 그 경계에 있는 객체는 거의 모두 스프링 빈이고, 다른 빈이 주입받은 참조로 호출한다. 프록시 방식은 그 경계를 정확히 덮으면서, ajc도 에이전트도 클래스 로더 설정도 요구하지 않는다. 같은 문서는 반대로 매우 잘게 나뉜 객체(대표적으로 도메인 객체)에 어드바이스를 적용하는 일은 스프링 AOP로 쉽거나 효율적으로 할 수 없고, 그런 경우에는 AspectJ가 최선이라고 말한다. 컨테이너 밖에서 new나 ORM이 만든 도메인 객체에 의존관계를 주입하는 스프링의 @Configurable 지원이 AspectJ 위빙을 요구하는 것이 그 예다.

    AOP 용어 정리

    마지막으로 지금까지 써 온 말들을 정리하자. 용어는 AspectJ에서 시작해 스프링이 이어받은 것이어서, 정의는 넓고 스프링에서의 실체는 좁은 경우가 많다. 그 차이를 실험으로 확인해 보려고 StockRepository의 메서드에 걸리는 애스펙트에서 ProceedingJoinPoint의 값을 찍어 봤다.

    @Around("execution(* demo.app.StockRepository.*(..))")
public Object inspect(ProceedingJoinPoint jp) throws Throwable {
    System.out.println("kind      = " + jp.getKind());
    System.out.println("short     = " + jp.getSignature().toShortString());
    System.out.println("long      = " + jp.getSignature().toLongString());
    System.out.println("this      = " + jp.getThis().getClass().getName());
    System.out.println("target    = " + jp.getTarget().getClass().getName());
    System.out.println("args      = " + java.util.Arrays.toString(jp.getArgs()));
    System.out.println("jp class  = " + jp.getClass().getName());
    return jp.proceed();
}
    kind      = method-execution
short     = StockRepository.reserve(..)
long      = public java.lang.String demo.app.StockRepository.reserve(java.lang.String)
this      = demo.app.StockRepository$$SpringCGLIB$$0
target    = demo.app.StockRepository
args      = [book]
jp class  = org.springframework.aop.aspectj.MethodInvocationProceedingJoinPoint
  StockRepository.reserve(book)

    getKind()가 돌려준 method-execution은 이 조인 포인트의 종류이고, 스프링 AOP에서는 언제나 이 값이다. getThis()는 프록시를, getTarget()은 프록시 뒤의 원래 객체를 돌려줬다. 이 둘의 차이는 09회에서 볼 this, target 포인트컷 지정자의 차이로 그대로 이어진다. 이 값들을 옆에 두고 용어를 하나씩 정의한다. 정의 열은 스프링 레퍼런스의 "AOP Concepts" 절(어드바이저 행은 "Advisor API in Spring" 절과 스키마 기반 AOP의 "Advisors" 절)을 우리말로 옮긴 것이다.

    용어정의스프링에서의 실체 / 실험에서 본 것
    조인 포인트(join point)프로그램 실행 중의 한 지점. 메서드 실행이나 예외 처리 같은 것.스프링 AOP에서는 언제나 메서드 실행이다. getKind() = method-execution.
    포인트컷(pointcut)조인 포인트를 고르는 술어(predicate). 어드바이스는 포인트컷 표현식과 연결되어 그것이 고른 조인 포인트에서 실행된다.기본으로 AspectJ 포인트컷 표현식 언어를 쓴다. 실체는 ClassFilter와 MethodMatcher를 가진 Pointcut, @Aspect에서는 AspectJExpressionPointcut.
    어드바이스(advice)특정 조인 포인트에서 애스펙트가 하는 행동. around, before, after 등의 종류가 있다.스프링을 포함한 많은 AOP 프레임워크가 어드바이스를 인터셉터로 모델링하고 조인 포인트 둘레에 인터셉터 체인을 유지한다. 실험의 AspectJAroundAdvice와 체인.
    애스펙트(aspect)여러 클래스에 걸치는 관심사의 모듈화.스키마 기반의 일반 클래스나 @Aspect 클래스. 실험의 TraceAspect.
    어드바이저(advisor)스프링 고유 개념. 포인트컷과 연결된 어드바이스 하나만 가진 애스펙트.DefaultPointcutAdvisor, @Aspect에서 변환된 InstantiationModelAwarePointcutAdvisorImpl.
    대상 객체(target object)하나 이상의 애스펙트가 어드바이스를 적용하는 객체. "어드바이스가 적용된 객체"라고도 한다.스프링 AOP는 런타임 프록시로 구현되므로 대상 객체는 언제나 프록시가 감싼 객체다. getTarget() = StockRepository.
    AOP 프록시(AOP proxy)애스펙트의 계약(어드바이스 실행 등)을 구현하려고 AOP 프레임워크가 만든 객체.JDK 동적 프록시나 CGLIB 프록시. getThis() = StockRepository$$SpringCGLIB$$0.
    위빙(weaving)애스펙트를 다른 애플리케이션 타입이나 객체와 연결해 어드바이스가 적용된 객체를 만드는 것. 컴파일 시점, 로드 시점, 런타임에 할 수 있다.스프링 AOP는 런타임에 위빙한다. 실체는 자동 프록시 생성기가 프록시를 만드는 일.
    인트로덕션(introduction)타입을 대신해 메서드나 필드를 추가로 선언하는 것. AspectJ에서는 타입 간 선언(inter-type declaration)이라고 한다.스프링 AOP에서는 어드바이스가 적용된 객체에 새 인터페이스(와 구현)를 더할 수 있다. @DeclareParents 필드가 DeclareParentsAdvisor가 된다.

    용어를 외울 때 흔히 생기는 혼동이 둘 있다. 첫째, 조인 포인트와 포인트컷의 관계다. 조인 포인트는 "부가 기능을 붙일 수 있는 모든 자리"이고, 포인트컷은 그중 "실제로 붙일 자리를 고르는 조건"이다. 스프링 AOP에서 조인 포인트의 집합은 "스프링 빈 메서드의 실행"으로 이미 좁혀져 있고, 포인트컷은 그 안에서 다시 고른다. 그래서 포인트컷 표현식이 private 메서드나 내부 호출을 문법상 덮더라도, 그것들은 애초에 조인 포인트 집합에 없으므로 적용되지 않는다. 앞의 스프링 실험에서 check가 그랬다. 둘째, 애스펙트와 어드바이저의 관계다. 어드바이저는 애스펙트의 특수한 경우(어드바이스 하나, 포인트컷 하나)이고, 스프링 내부에서는 모든 애스펙트가 결국 어드바이저 목록으로 풀려 처리된다.

    정리와 흔한 오해

    이 회차의 뒷부분을 한 문단으로 묶으면 이렇다. 부가 기능은 객체지향의 축을 가로지르므로 코드에 흩어지고 핵심 로직과 뒤엉킨다. AOP는 그런 관심사를 애스펙트라는 단위로 모으고, "어디에"를 포인트컷으로 선언해 위빙으로 엮는다. 위빙은 컴파일 시점, 컴파일 후, 로드 시점에 바이트코드를 바꾸는 방식(AspectJ)과 런타임에 프록시를 세우는 방식(스프링 AOP)으로 나뉜다. 스프링 AOP는 조인 포인트를 스프링 빈의 메서드 실행으로 좁히는 대신, 특별한 컴파일러나 에이전트 없이 IoC 컨테이너와 하나로 동작한다.

    이 위에서 자주 생기는 오해를 바로잡아 두자.

    • "@Aspect를 쓰면 AspectJ가 동작한다." 아니다. 스프링은 AspectJ의 애너테이션과 포인트컷 파서만 빌려 쓴다. 실행은 프록시와 인터셉터 체인이 맡고, 바이트코드는 바뀌지 않는다. 그래서 포인트컷 문법이 같아도 적용 범위는 위 표만큼 다르다.
    • "@Aspect만 붙이면 동작한다." 애스펙트는 빈이어야 한다. 컴포넌트 스캔을 쓴다면 @Component가 함께 있어야 하고, @AspectJ 지원이 켜져 있어야 한다(부트에서는 aspectjweaver가 클래스패스에 있으면 자동으로 켜진다).
    • "포인트컷에 해당하면 어떻게 호출하든 적용된다." 스프링 AOP에서는 프록시를 거친 호출에만 적용된다. 내부 호출, private 메서드, 컨테이너 밖의 객체에는 적용되지 않는다.
    • "애스펙트끼리도 서로 적용된다." 스프링 AOP에서 @Aspect 클래스는 자동 프록시 대상에서 제외되므로 다른 애스펙트의 대상이 될 수 없다.
    • "AOP는 객체지향을 대체한다." 스프링 레퍼런스의 표현대로 AOP는 OOP를 보완한다. 애스펙트도 클래스이고, 핵심 로직의 설계는 여전히 객체지향의 몫이다.

    다음 회차들은 이 회차의 뼈대 위에 살을 붙인다. 08회는 @Before, @AfterReturning 같은 어드바이스 종류와 @Pointcut으로 포인트컷을 재사용하는 방법, 애스펙트 사이의 순서를 다루고, 09회는 execution을 비롯한 포인트컷 지정자의 문법을 다룬다. 10회는 이 회차의 표에서 "적용되지 않는다"로 남겨 둔 내부 호출 문제와 프록시 기술 선택의 실무적인 결과를 다룬다.
    @Aspect
    AspectJ 5가 도입한 애너테이션 방식의 애스펙트 선언. 스프링은 같은 애너테이션과 AspectJ의 포인트컷 파서를 쓰지만 실행은 순수한 스프링 AOP(프록시)가 맡는다. 애스펙트는 빈이어야 하며, 스캔으로 등록하려면 @Component가 필요하다.
    애스펙트에서 어드바이저로
    AnnotationAwareAspectJAutoProxyCreator의 findCandidateAdvisors()는 어드바이저 빈에 더해 BeanFactoryAspectJAdvisorsBuilder가 @Aspect 빈에서 만든 어드바이저를 합친다. 어드바이스 메서드 하나가 AspectJExpressionPointcut과 어드바이스 객체를 묶은 어드바이저 하나가 되고, 결과는 캐시된다.
    자동 프록시 생성기의 승격
    자동 프록시 생성기는 internalAutoProxyCreator라는 고정 이름으로 하나만 등록되고, 트랜잭션·캐시·@Aspect 설정이 겹치면 우선순위가 높은 클래스로 승격된다. 그래서 출처가 다른 어드바이저들이 한 프록시의 한 체인에 들어간다.
    ExposeInvocationInterceptor
    AspectJ 방식의 어드바이스가 있으면 체인 맨 앞에 추가되는 인터셉터. 현재 MethodInvocation을 ThreadLocal에 넣고 끝나면 이전 값으로 되돌려, MethodInvocation을 직접 받지 못하는 어드바이스가 조인 포인트를 만들 수 있게 한다.
    인터셉터 체인
    프록시는 ReflectiveMethodInvocation을 만들어 proceed()를 부르고, 이 객체는 인덱스를 올리며 인터셉터를 차례로 부른 뒤 마지막에 리플렉션으로 타깃 메서드를 부른다. 애스펙트 메서드도 Method.invoke로 호출된다.
    핵심 기능과 부가 기능
    핵심 기능은 객체가 존재하는 이유이고, 부가 기능은 그것을 보조하며 여러 클래스에 걸치는 횡단 관심사다. 직접 쓰면 코드가 흩어지고(scattering) 핵심 로직과 뒤엉킨다(tangling).
    위빙 시점
    컴파일 시점(ajc), 컴파일 후(바이너리), 로드 시점(-javaagent와 aop.xml)은 대상 클래스의 바이트코드를 바꾸고, 런타임(스프링 AOP)은 원본을 그대로 둔 채 프록시를 세운다.
    프록시 방식의 한계
    스프링 AOP의 조인 포인트는 스프링 빈 메서드의 실행뿐이고, 프록시를 거친 호출에만 적용된다. 내부 호출, private·final·static 메서드, 컨테이너 밖의 객체, 생성자와 필드 접근에는 적용되지 않는다.
    AOP 용어의 실체
    스프링에서 조인 포인트는 메서드 실행(method-execution), 타깃은 프록시 뒤의 원래 객체(getTarget()), AOP 프록시는 JDK·CGLIB 프록시(getThis()), 어드바이저는 포인트컷 하나와 어드바이스 하나를 가진 애스펙트다.

    "애스펙트를 만들었는데 아무 일도 일어나지 않는다"는 문의는 거의 항상 세 가지 중 하나로 풀린다. 애스펙트가 빈으로 등록되지 않았거나(@Component 누락, 스캔 범위 밖), @AspectJ 지원이 꺼져 있거나(부트 없이 @EnableAspectJAutoProxy를 빠뜨림, 부트에서 aspectjweaver가 빠짐), 호출이 프록시를 거치지 않는 경우다. 마지막 경우는 같은 클래스 안의 메서드를 부르거나, 빈이 아닌 객체를 쓰거나, private·final 메서드에 기대한 경우다. 이 회차에서 본 확인 방법이 그대로 진단 도구가 된다. 빈을 꺼내 getClass()가 $Proxy나 $$SpringCGLIB$$인지 보고, 프록시라면 Advised로 캐스팅해 어드바이저 목록에 내 애스펙트가 있는지 확인한다. 둘 다 맞는데도 동작하지 않으면 호출 경로를 의심한다.

    스프링 AOP로 충분한지, AspectJ 위빙이 필요한지는 "부가 기능을 붙일 지점이 빈의 public 메서드 경계에 있는가"로 판단한다. 트랜잭션, 보안, 로그 추적, 실행 시간 측정, 재시도처럼 서비스 경계에서 일어나는 일은 프록시로 충분하고, 빌드와 실행 환경에 아무것도 더하지 않는다는 장점이 크다. 반대로 엔티티처럼 컨테이너 밖에서 대량으로 만들어지는 객체, 필드 접근, 생성자, 같은 클래스 안의 호출까지 덮어야 한다면 AspectJ 위빙을 검토해야 한다. 그 경우 빌드에 ajc를 넣을지, 실행 옵션에 에이전트를 넣을지를 운영 환경이 허용하는지부터 확인한다. 실험에서 본 것처럼 로드 타임 위빙은 설정이 조금만 어긋나도(디버그 정보 없이 컴파일 등) 위빙 없이 그대로 실행될 수 있으므로, -showWeaveInfo로 실제로 엮였는지를 확인하는 절차를 둔다.

AbstractAspectJAdvice.currentJoinPoint()가 이 값을 읽어 조인 포인트를 만든다. 프록시 노출은 exposeProxy 설정의 일이고, 애스펙트 인스턴스는 인스턴스 팩토리가 얻으며, 포인트컷 검사는 체인을 만들 때(동적 매처라면 ReflectiveMethodInvocation.proceed 안에서) 이루어진다. AOP 용어와 스프링 AOP에서의 실체를 짝지은 것 중 틀린 것은? 조인 포인트 — 언제나 메서드 실행이며, JoinPoint.getKind()는 method-execution을 돌려준다. AOP 프록시 — JDK 동적 프록시나 CGLIB 프록시이며, getThis()가 이 객체를 돌려준다. 위빙 — 스프링 AOP는 클래스 로딩 시점에 대상 클래스의 바이트코드를 바꿔 위빙한다. 어드바이저 — 포인트컷 하나와 어드바이스 하나를 가진, 스프링 고유의 애스펙트 단위다. 스프링 레퍼런스는 스프링 AOP가 다른 순수 자바 AOP 프레임워크처럼 런타임에 위빙한다고 명시한다. 대상 클래스의 바이트코드는 바뀌지 않고, 자동 프록시 생성기가 프록시 객체를 만들어 대상 앞에 세운다. 클래스 로딩 시점의 위빙은 AspectJ의 로드 타임 위빙이다. 나머지 보기는 본문의 실험 값(method-execution, getThis()가 $$SpringCGLIB$$0)과 레퍼런스의 정의에 맞는다.
    애스펙트(aspect)
    여러 클래스에 걸치는 관심사를 모듈화한 단위. 무엇을 할지(어드바이스)와 어디에 할지(포인트컷)를 함께 담는다. 스프링에서는 @Aspect 클래스나 스키마 기반 설정으로 선언한다.
    횡단 관심사(cross-cutting concern)
    로그, 트랜잭션, 보안처럼 특정 기능에 속하지 않고 여러 기능에 공통으로 걸치는 관심사. 직접 구현하면 코드가 흩어지고 핵심 로직과 뒤엉킨다.
    위빙(weaving)
    애스펙트를 대상 타입이나 객체와 연결해 어드바이스가 적용된 객체를 만드는 일. 컴파일 시점, 컴파일 후, 로드 시점, 런타임에 할 수 있다.
    로드 타임 위빙(load-time weaving)
    클래스 로더가 클래스를 JVM에 정의하기 직전에 바이트코드를 바꿔 애스펙트를 엮는 방식. AspectJ에서는 -javaagent:aspectjweaver.jar와 META-INF/aop.xml로 설정한다.
    AnnotationAwareAspectJAutoProxyCreator
    @EnableAspectJAutoProxy가 등록하는 자동 프록시 생성기. 어드바이저 빈과 @Aspect 빈에서 만든 어드바이저를 모아 빈마다 적용 가능한 것을 고르고 프록시를 만든다.
    InstantiationModelAwarePointcutAdvisorImpl
    @Aspect의 어드바이스 메서드 하나가 변환된 어드바이저. AspectJExpressionPointcut과 애너테이션 종류에 맞는 어드바이스 객체(AspectJAroundAdvice 등)를 묶는다.
    ProceedingJoinPoint
    어라운드 어드바이스가 받는 조인 포인트. proceed()로 다음 어드바이스나 대상 메서드를 실행한다. 스프링에서는 MethodInvocationProceedingJoinPoint가 MethodInvocation을 감싸 구현한다.
    ExposeInvocationInterceptor
    AspectJ 방식 어드바이스가 있을 때 체인 맨 앞에 추가되는 인터셉터. 현재 MethodInvocation을 ThreadLocal로 노출한다.
    인트로덕션(introduction)
    대상 타입에 새 메서드나 필드, 인터페이스를 더하는 것. AspectJ에서는 타입 간 선언이라고 하고, @AspectJ에서는 @DeclareParents로 쓴다.
