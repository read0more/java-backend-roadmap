    프록시 클래스를 계속 손으로 쓸 수 있을까

    03회에서 프록시 패턴과 데코레이터 패턴으로 로그 추적 코드를 원래 코드 밖으로 꺼냈다. 원래 객체와 같은 인터페이스를 구현한 클래스를 하나 더 만들고, 그 클래스의 메서드가 부가 기능을 수행한 뒤 진짜 객체에게 호출을 넘기는 구조였다. 원래 코드를 한 줄도 고치지 않고 부가 기능을 붙일 수 있다는 점에서 분명한 진전이었다.

    그런데 그 방식에는 비용이 하나 남아 있다. 프록시를 적용할 클래스가 열 개면 프록시 클래스도 열 개를 써야 하고, 인터페이스에 메서드가 다섯 개면 프록시 클래스에도 거의 같은 메서드 다섯 개를 써야 한다. 그렇게 쓴 메서드들을 나란히 놓아 보면 차이는 단 한 줄이다. "시작 로그를 남긴다 → 대상의 어떤 메서드를 호출한다 → 종료 로그를 남긴다"에서 굵게 표시한 부분만 다르고 나머지는 글자 하나까지 같다.

    같은 코드가 반복되면 보통은 메서드로 뽑아낸다. 그런데 이번에는 달라지는 부분이 값이 아니라 호출할 메서드 자체다. 자바 코드에서 target.order(item)이라는 호출은 컴파일할 때 이미 "어느 타입의 어느 메서드"인지가 바이트코드에 박힌다. 이 부분을 매개변수로 받으려면 메서드를 값처럼 넘길 수 있어야 한다. 이것이 첫 번째 문제다.

    두 번째 문제는 클래스 자체다. 공통 로직을 메서드 하나로 모아도, 그 메서드를 호출해 줄 프록시 클래스는 여전히 인터페이스마다 하나씩 있어야 한다. OrderService를 구현하는 프록시, MemberService를 구현하는 프록시를 누군가는 써야 한다. 이 클래스를 사람이 아니라 프로그램이 실행 중에 써 준다면 문제가 사라진다.

    이 회차는 두 문제의 답을 차례로 본다. 메서드를 값으로 다루는 기술이 리플렉션(reflection)이고, 클래스를 실행 중에 만들어 내는 기술이 동적 프록시(dynamic proxy)다. 동적 프록시에는 JDK가 기본으로 제공하는 방식과 CGLIB라는 바이트코드 생성 라이브러리를 쓰는 방식이 있다. 둘 다 "실행 중에 클래스 파일을 만들어 JVM에 올린다"는 점은 같고, 무엇을 상속하고 무엇을 구현하느냐가 다르다. 그 차이가 나중에 스프링 AOP에서 타입 캐스팅이나 final 메서드 문제로 다시 나타난다.

    이 회차의 실행 결과는 원고를 쓰면서 JDK 21.0.13(Temurin)에서 직접 돌려 얻었다. CGLIB 예제는 스프링 프레임워크 6.2.19의 spring-core 안에 재패키징된 CGLIB(org.springframework.cglib)로 실행했다. 생성된 클래스의 바이트코드는 JDK와 CGLIB의 덤프 기능으로 파일에 저장한 뒤 javap로 읽었다. 본문에 나오는 JDK 내부 클래스(DirectMethodHandleAccessor 등)와 CGLIB 내부 구조는 공개 API가 아니므로 버전에 따라 달라질 수 있다. 해시값, 걸린 시간처럼 실행마다 다른 값은 그렇다고 표시했다.

    리플렉션 — 메서드를 값으로 다루기

    자바에서 클래스가 로딩되면 JVM은 그 클래스를 나타내는 java.lang.Class 객체를 하나 만든다. 이 객체는 "이 클래스에는 어떤 필드와 메서드와 생성자가 있는가"를 프로그램이 물어볼 수 있는 창구다. HotSpot에서 클래스의 메타데이터(메서드 바이트코드, 상수 풀 등) 자체는 힙 바깥의 메타스페이스(Metaspace)에 있고, 힙에 있는 Class 객체는 그 메타데이터를 가리키는 손잡이 역할을 한다. 리플렉션은 이 손잡이를 통해 클래스의 구조를 읽고, 읽어 낸 메서드를 호출하는 기능이다.

    핵심 타입은 셋이다. Class는 타입 하나를, Method는 그 타입의 메서드 하나를, Field는 필드 하나를 나타낸다. Class.getMethod(이름, 매개변수 타입들)은 public 메서드를 상속받은 것까지 포함해 찾고, getDeclaredMethod는 접근 제어자와 상관없이 그 클래스에 직접 선언된 메서드만 찾는다. 찾은 Method 객체의 invoke(대상 객체, 인자들...)를 부르면 그 메서드가 실행된다. 즉 "어떤 메서드를 부를지"가 Method라는 값이 되고, 그 값을 매개변수로 넘길 수 있게 된다.

    예제로 확인해 보자. 조회 메서드 두 개와 예외를 던지는 메서드 하나, 그리고 자신이 어떤 경로로 호출되었는지 출력하는 메서드 하나를 가진 클래스다.

    public class OrderQuery {
    public String findOrder() {
        return "order-1";
    }

    public int countOrders() {
        return 3;
    }

    public String fail() {
        throw new IllegalStateException("조회 실패");
    }

    public void whoCalls() {
        StackTraceElement[] frames = new Throwable().getStackTrace();
        for (StackTraceElement f : frames) {
            System.out.println("  " + f.getClassName() + "." + f.getMethodName());
        }
    }
}

    이제 "시작 로그 → 메서드 호출 → 종료 로그"라는 공통 흐름을 메서드 하나로 만든다. 호출할 메서드는 Method로 받는다.

    import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;

public class ReflectionMain {

    static Object callWithLog(Object target, Method method) throws Exception {
        System.out.println("시작: " + method.getName());
        Object result = method.invoke(target);
        System.out.println("종료: " + method.getName() + " -> " + result);
        return result;
    }

    public static void main(String[] args) throws Exception {
        OrderQuery target = new OrderQuery();
        Class type = Class.forName("OrderQuery");

        callWithLog(target, type.getMethod("findOrder"));
        Object count = callWithLog(target, type.getMethod("countOrders"));
        System.out.println("반환 타입: " + count.getClass().getName());

        try {
            callWithLog(target, type.getMethod("fail"));
        } catch (InvocationTargetException e) {
            System.out.println("잡힌 예외: " + e.getClass().getSimpleName());
            System.out.println("원래 예외: " + e.getCause());
        }

        try {
            type.getMethod("findOrdr");
        } catch (NoSuchMethodException e) {
            System.out.println("잡힌 예외: " + e);
        }

        System.out.println("whoCalls 호출 경로:");
        type.getMethod("whoCalls").invoke(target);
        Method m1 = type.getMethod("findOrder");
        Method m2 = type.getMethod("findOrder");
        System.out.println("같은 Method 객체? " + (m1 == m2) + ", equals? " + m1.equals(m2));
    }
}

    결과를 한 줄씩 읽어 보자. 첫 네 줄은 의도대로다. callWithLog는 findOrder와 countOrders의 존재를 전혀 모르는 코드인데, 넘겨받은 Method에 따라 서로 다른 메서드를 호출했다. 03회의 프록시 클래스에서 메서드마다 반복되던 코드를 이렇게 한 곳으로 모을 수 있다.

    다섯째 줄은 countOrders가 int를 반환하는데 invoke의 결과는 java.lang.Integer라는 사실을 보여 준다. invoke의 반환 타입은 Object이므로 기본형 값은 래퍼 객체로 감싸져(boxing) 나온다. Method.invoke의 Javadoc도 반환값이 기본형이면 적절히 감싼다고 적고 있고, 반환 타입이 void면 null을 돌려준다고 적고 있다. 인자도 마찬가지로 Object...로 받으므로 기본형 인자는 박싱되어 배열에 담긴다. 리플렉션 호출은 이 박싱과 배열 생성을 매번 동반한다.

    예외는 한 겹 포장되어 나온다

    여섯째부터 여덟째 줄이 중요하다. fail()은 IllegalStateException을 던졌는데, callWithLog를 부른 쪽이 받은 것은 InvocationTargetException이다. 원래 예외는 그 안의 원인(cause)으로 들어 있다. Javadoc은 이 예외를 "호출된 메서드가 예외를 던진 경우"라고 정의한다. 리플렉션 쪽에서 생긴 문제(접근 권한이 없다, 인자 개수가 맞지 않는다)는 IllegalAccessException이나 IllegalArgumentException으로 직접 던지고, 대상 메서드가 던진 예외는 반드시 한 겹 감싸서 둘을 구별할 수 있게 한 것이다.

    이 구별은 설계상 합리적이지만, 리플렉션 위에 프록시를 쌓을 때 함정이 된다. 대상 메서드가 던진 IllegalStateException을 잡으려던 호출자는 InvocationTargetException을 받게 되고, 그 예외는 체크 예외라서 컴파일러가 처리를 강요한다. 이 포장을 누가 벗겨야 하는지는 뒤에서 JDK 동적 프록시를 만들 때 다시 본다.

    컴파일러가 하던 검사가 실행 시점으로 밀린다

    아홉째 줄은 오타의 결과다. type.getMethod("findOrdr")는 문자열로 메서드를 찾으므로 컴파일러는 이름이 맞는지 알 수 없다. 일반 호출 target.findOrdr()였다면 컴파일 오류로 끝났을 문제가, 리플렉션에서는 프로그램이 그 줄에 도달했을 때 NoSuchMethodException으로 드러난다. 인자 타입이 틀리는 경우, 대상 객체가 그 메서드를 가진 타입이 아닌 경우도 모두 실행 시점의 IllegalArgumentException이 된다.

    이것이 리플렉션의 본질적인 대가다. 메서드를 값으로 다룰 수 있게 된 대신, 타입 시스템이 컴파일할 때 보장하던 "이 호출은 반드시 존재하는 메서드에 올바른 타입의 인자로 간다"는 약속을 잃는다. 그래서 리플렉션은 애플리케이션 코드 곳곳에 쓰는 도구가 아니라, 프레임워크처럼 "대상 타입을 미리 알 수 없는" 좁은 영역에 가두어 쓰는 도구다. 동적 프록시가 바로 그런 영역이다.

    리플렉션 호출 한 번이 지나는 길

    마지막 출력인 whoCalls의 호출 경로를 보자. ReflectionMain.main이 Method.invoke를 부르고, 그 안에서 jdk.internal.reflect.DirectMethodHandleAccessor.invoke를 거쳐 OrderQuery.whoCalls에 도착했다. 리플렉션 호출이 JVM의 어떤 특수한 명령으로 바로 가는 것이 아니라, 자바로 쓰인 몇 단계의 중계 객체를 지난다는 뜻이다.

    OpenJDK 21의 Method.invoke 소스를 읽으면 순서가 보인다. 먼저 setAccessible(true)로 검사를 끄지 않았다면 호출한 클래스가 이 메서드에 접근할 수 있는지 검사한다. 다음으로 MethodAccessor라는 중계 객체를 가져오는데, 없으면 이때 만든다. 마지막으로 그 중계 객체의 invoke에 대상과 인자 배열을 넘긴다. 실제 호출 방법은 전부 이 중계 객체 안에 있다.

    이 중계 방식은 JDK 18에서 바뀌었다. JEP 416(Reimplement Core Reflection with Method Handles) 이전의 리플렉션은 처음 몇 번의 호출은 HotSpot의 네이티브 메서드로 처리하고, 호출 횟수가 쌓이면 그 메서드 전용 바이트코드를 생성해 이후 호출에 썼다. JEP 416은 Method::invoke, Constructor::newInstance, Field::get·set을 java.lang.invoke의 메서드 핸들 위에 다시 구현했고, VM 초기화 초기의 짧은 구간에만 네이티브 방식을 쓴다. 위 실행 결과에 DirectMethodHandleAccessor가 보이는 것이 그 결과다. JEP 416은 Method 객체를 static final 필드에 두어 JIT이 상수로 접을 수 있을 때 새 구현이 이전 구현보다 빠르고, final이 아닌 필드나 배열 원소처럼 상수로 접을 수 없는 곳에 두면 마이크로벤치마크에서 어느 정도 성능 저하가 있었다고 적는다.

    마지막 줄 같은 Method 객체? false, equals? true도 구현을 비춰 준다. getMethod는 부를 때마다 새 Method 객체를 돌려준다. OpenJDK 21의 Class는 내부에 캐시한 루트 Method를 복사해서 반환하고, 복사본은 루트를 가리켜 중계 객체를 공유한다. 사본을 만드는 이유는 setAccessible 같은 상태가 Method 객체마다 따로 있어서, 한 쪽에서 바꾼 접근 상태가 다른 호출자에게 새지 않게 하기 위해서다. 그래서 Method를 비교할 때는 ==가 아니라 equals를 써야 한다. Javadoc에 따르면 선언한 클래스, 이름, 매개변수 타입, 반환 타입이 같으면 같은 메서드다.

    하나 더 짚어 둘 것이 있다. 인터페이스에서 얻은 Method를 구현 객체에 대해 invoke하면 어떤 코드가 실행될까? Method.invoke의 Javadoc은 인스턴스 메서드를 JLS 15.12.4.4가 정한 동적 메서드 조회(dynamic method lookup)로 호출하므로 대상 객체의 실행 시점 타입에 따른 오버라이딩이 일어날 수 있다고 적는다. 즉 OrderService.class.getMethod("order", String.class)로 얻은 Method를 OrderServiceImpl 객체에 대해 호출하면 구현 클래스의 order가 실행된다. 일반 호출의 invokeinterface와 같은 규칙이다. 동적 프록시는 바로 이 성질에 기대어, 인터페이스의 Method 하나로 어떤 구현체든 호출한다.

    JDK 동적 프록시 — 소개

    리플렉션으로 첫 번째 문제(호출할 메서드를 값으로 넘기기)는 풀렸다. 두 번째 문제는 프록시 클래스를 누가 쓰느냐다. JDK는 1.3부터 java.lang.reflect.Proxy라는 답을 갖고 있다. 인터페이스 목록을 주면 그 인터페이스들을 구현한 클래스를 실행 중에 생성해서 객체까지 만들어 준다. 생성된 클래스의 모든 메서드는 같은 일을 한다. 호출을 받으면 "어떤 메서드가 어떤 인자로 불렸는지"를 InvocationHandler라는 객체 하나에 넘기는 것이다.

    // java.lang.reflect
public static Object newProxyInstance(ClassLoader loader,
                                      Class[] interfaces,
                                      InvocationHandler h)

public interface InvocationHandler {
    Object invoke(Object proxy, Method method, Object[] args) throws Throwable;
}

    세 인자의 역할은 이렇다. loader는 생성된 프록시 클래스를 정의할 클래스 로더다. 프록시 클래스도 결국 클래스이므로 어느 로더 소속인지가 정해져야 하고, 그 로더에서 인자로 준 인터페이스들이 보여야 한다. interfaces는 프록시가 구현할 인터페이스 목록이다. h는 모든 호출을 받아 처리할 핸들러다.

    핸들러의 invoke가 받는 세 값도 정확히 알아 두자. proxy는 호출을 받은 프록시 객체 자신이다. method는 호출된 인터페이스 메서드의 Method 객체다. args는 인자 배열인데, InvocationHandler Javadoc에 따르면 인자가 없는 메서드라면 빈 배열이 아니라 null이 오고, 기본형 인자는 Integer·Boolean 같은 래퍼로 감싸져 온다. 핸들러가 돌려준 값은 프록시 메서드의 반환값이 된다.

    이 구조에서 부가 기능 코드는 핸들러 하나에만 있다. 프록시가 구현하는 인터페이스가 무엇이든, 메서드가 몇 개든, 모든 호출이 같은 invoke로 모인다. 03회에서 인터페이스마다 쓰던 프록시 클래스를 JDK가 대신 쓰고, 우리는 "호출이 오면 무엇을 할지"만 한 번 쓰면 된다.

    일상에서 가져온 비유대표번호와 상담원

    회사의 대표번호는 어떤 부서로 거는 전화든 일단 받아서, "몇 번 내선을 찾는지"를 메모해 상담원 한 명에게 넘긴다. 상담원은 통화 기록을 남기고 해당 부서로 연결한다. 대표번호 교환기가 프록시 클래스, 상담원이 InvocationHandler, 내선 번호 메모가 Method 객체다. 비유가 깨지는 지점도 있다. 교환기는 미리 설치해 둔 장비지만 프록시 클래스는 첫 요청이 올 때 JDK가 그 자리에서 클래스 파일을 만들어 JVM에 올린다. 또 상담원이 실수로 "대표번호"로 다시 걸면 자기 자신에게 전화가 오는데, 이 문제는 뒤에서 실제로 무한 재귀로 확인한다.

    인터페이스와 구현 클래스를 하나씩 준비한다. 구현 클래스는 자기가 실행되었다는 표시만 출력한다.

    import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.util.Arrays;

public class LoggingHandler implements InvocationHandler {
    private final Object target;

    public LoggingHandler(Object target) {
        this.target = target;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        System.out.println("[핸들러] " + method.getName() + " 호출, 인자=" + Arrays.toString(args));
        Object result = method.invoke(target, args);
        System.out.println("[핸들러] " + method.getName() + " 반환=" + result);
        return result;
    }
}

    클래스 정보는 프록시의 정체를 보여 준다. 클래스 이름은 jdk.proxy1.$Proxy0이고 부모는 java.lang.reflect.Proxy, 구현한 인터페이스는 OrderService 하나, 수식자는 public final이다. Proxy Javadoc이 정한 성질 그대로다. 프록시 클래스는 final이고 추상 클래스가 아니며 Proxy를 상속한다. 이름의 앞부분은 명세가 정하지 않지만 $Proxy로 시작하는 이름은 프록시 클래스용으로 예약되어 있다.

    가장 실무적인 줄은 OrderServiceImpl 인가? false다. 프록시는 OrderService를 구현했을 뿐 OrderServiceImpl과는 아무 관계가 없다. 그래서 이 프록시를 OrderServiceImpl 타입 변수에 대입하려 하면 ClassCastException이 난다. 스프링이 JDK 동적 프록시로 빈을 감싸면 구현 클래스 타입으로 주입받을 수 없는 이유가 여기 있다. 이 문제는 10회에서 의존관계 주입과 함께 다시 다룬다.

    프록시 클래스는 어느 모듈, 어느 로더에 생기는가

    모듈: module jdk.proxy1은 처음 보면 낯설다. 자바 9의 모듈 시스템 이후 JDK는 프록시 클래스를 둘 모듈과 패키지를 직접 고른다. Proxy Javadoc의 규칙에 따르면, 프록시 인터페이스가 모두 public이고 export된(또는 open된) 패키지에 있으면 프록시 클래스는 무조건 export되지만 open되지는 않은 패키지의 public 클래스로 정의되고, 그 패키지와 모듈의 이름은 명세하지 않는다. OpenJDK 21의 구현은 이 패키지를 동적 모듈(dynamic module)에 둔다. 클래스 로더마다 동적 모듈을 하나 만들고 이름을 jdk.proxy에 일련번호를 붙여 짓는다. 우리 실행에서는 애플리케이션 클래스 로더의 첫 동적 모듈이 jdk.proxy1이었고, 프록시 클래스가 그 이름의 패키지에 들어갔다. 반대로 인터페이스 중 하나라도 public이 아니면 프록시 클래스는 그 인터페이스와 같은 패키지에 public이 아닌 클래스로 정의된다.

    같은 프록시 클래스? true는 캐시의 존재를 보여 준다. 두 번째 newProxyInstance는 핸들러도 대상 객체도 다르지만 같은 로더, 같은 인터페이스 목록을 넘겼다. Proxy Javadoc은 같은 로더가 같은 인터페이스 순열(permutation)에 대한 프록시 클래스를 이미 정의했다면 그 클래스를 반환한다고 하고, 같은 인터페이스라도 순서가 다르면 서로 다른 프록시 클래스가 된다고 명시한다. OpenJDK 21 소스에서는 ClassLoaderValue로 로더별 캐시를 두고, 인터페이스 목록을 키로 프록시 클래스의 생성자를 저장한다. 프록시 객체가 만 개여도 클래스는 하나다. 객체마다 다른 것은 생성자로 받은 핸들러뿐이다.

    생성된 클래스는 언제 사라질까? JLS 12.7은 클래스나 인터페이스가 언로드될 수 있는 경우를 그 클래스를 정의한 클래스 로더가 가비지 컬렉터에 회수될 수 있을 때로 한정한다. 애플리케이션 클래스 로더에 정의된 $Proxy0는 사실상 애플리케이션이 끝날 때까지 남는다. 캐시 덕분에 같은 조합으로는 클래스가 하나만 생기므로 보통은 문제가 되지 않지만, 인터페이스 조합을 끝없이 바꿔 가며 프록시를 만드는 코드가 있다면 클래스가 계속 늘어난다는 점은 알아 둘 만하다.

    equals 한 번에 핸들러가 두 번 불린 이유

    --- equals --- 아래 다섯 줄은 처음 보면 이상하다. proxy.equals(proxy)를 한 번 불렀을 뿐인데 핸들러 로그에 toString이 먼저 찍혔고, 결과는 false다. 자기 자신과 같지 않은 객체라니, equals의 반사성(reflexive) 규약이 깨진 것처럼 보인다.

    원인은 두 가지가 겹친 것이다. 첫째, Proxy Javadoc에 따르면 java.lang.Object에 선언된 hashCode, equals, toString을 프록시에 호출하면 인터페이스 메서드와 똑같이 핸들러의 invoke로 간다. 이때 핸들러가 받는 Method의 선언 클래스는 java.lang.Object다. 그래서 equals 호출이 LoggingHandler로 들어왔다.

    둘째, 핸들러의 첫 줄 Arrays.toString(args)가 인자 배열 안의 객체에 toString()을 부른다. 그런데 그 인자가 바로 프록시 자신이다. 프록시의 toString도 핸들러로 가므로 [핸들러] toString 호출이 먼저 찍혔고, 핸들러는 그것을 대상 객체의 toString에 넘겨 OrderServiceImpl@12edcd21을 받았다. 그 다음 원래 하던 equals 처리로 돌아와 method.invoke(target, args), 즉 target.equals(proxy)를 실행한다. OrderServiceImpl은 equals를 재정의하지 않았으므로 Object.equals의 참조 비교가 일어나고, 실제 객체와 프록시 객체는 다른 객체이므로 false다.

    교훈은 두 가지다. 핸들러 안에서 인자를 문자열로 바꾸거나 해시를 계산하는 코드는 인자 중에 프록시가 섞여 있으면 핸들러를 다시 부른다. 그리고 단순 위임 핸들러는 equals와 hashCode의 의미를 바꾼다. 프록시를 HashSet에 넣거나 비교에 쓰는 코드가 있다면 핸들러가 Object의 메서드를 따로 처리해야 한다. 스프링의 JDK 프록시 구현도 equals와 hashCode를 대상 객체에 그대로 넘기지 않고 별도로 처리하는데, 그 내부는 05회의 범위다.

    반면 마지막 줄 $Proxy0을 출력한 getClass()는 핸들러를 거치지 않았다. Proxy Javadoc은 Object에서 물려받은 나머지 public 메서드는 프록시 클래스가 재정의하지 않는다고 적는다. getClass, notify, wait는 Object에서 final로 선언되어 있어 애초에 재정의할 수도 없다. 그래서 프록시에 getClass()를 부르면 핸들러와 상관없이 언제나 프록시 클래스 자신이 나온다.

    정적 필드: 메서드마다 Method 객체 하나

    프록시 클래스에는 m0부터 m4까지 static final Method 필드가 다섯 개 있다. 인터페이스 메서드 두 개(order, stock)에 Object의 세 메서드(hashCode, equals, toString)를 더한 수다. 정적 초기화 블록(static {})을 보면 Class.forName("OrderService", false, 로더)로 인터페이스를 찾고 getMethod("order", String.class)로 Method를 얻어 m3(이 실행 기준)에 넣는다. 즉 핸들러가 받는 Method 객체는 호출 때마다 찾는 것이 아니라 클래스 초기화 때 한 번 찾아 정적 필드에 보관해 둔 것이다. 모든 프록시 객체가 이 다섯 개를 공유한다.

    메서드 본문: 호출을 데이터로 바꾸기

    order(String)의 바이트코드는 호출 한 번을 "핸들러에게 보내는 데이터"로 바꾸는 과정이다. 0~1번에서 자기 자신(aload_0)의 h 필드를 읽는다. 4번에서 this를 다시 올린다. 이것이 핸들러가 받는 proxy 인자다. 5번에서 정적 필드 m3을 읽는다. 8~15번은 크기 1인 Object[]을 만들고 0번 칸에 첫 번째 인자(aload_1, 즉 item)를 넣는다. 16번에서 InvocationHandler.invoke를 invokeinterface로 호출한다. 21번은 돌아온 Object를 String으로 checkcast하고, 24번에서 반환한다.

    stock처럼 반환 타입이 int인 메서드는 21번 자리가 checkcast Integer와 invokevirtual Integer.intValue()로 바뀐다. 앞 절에서 본 언박싱이 여기서 일어난다. 그래서 핸들러가 int 메서드에 null을 돌려주면 intValue() 호출에서 NullPointerException이 나고, 엉뚱한 타입을 돌려주면 checkcast에서 ClassCastException이 난다. InvocationHandler Javadoc이 정한 반환값 규칙(기본형 반환 메서드에 null을 돌려주면 NullPointerException, 호환되지 않는 값이면 ClassCastException)이 바이트코드에서는 이 두 명령으로 구현된 것이다.

    예외 표: UndeclaredThrowableException이 생기는 자리

    마지막의 예외 표(exception table)가 이 클래스에서 가장 중요한 부분이다. 0~25번 구간에서 Error나 RuntimeException이 나면 25번(athrow)으로 가서 그대로 다시 던진다. 그 밖의 Throwable, 즉 체크 예외는 26번으로 가서 UndeclaredThrowableException으로 감싸 던진다. order는 throws 절이 없으므로 체크 예외는 하나도 그대로 통과할 수 없다. 만약 인터페이스 메서드가 throws IOException을 선언했다면 IOException도 그대로 통과하는 항목이 예외 표에 추가된다.

    왜 이렇게 해야 할까? 핸들러의 invoke는 throws Throwable로 선언되어 있어 어떤 예외든 던질 수 있다. 하지만 프록시는 OrderService를 구현한 객체이고, OrderService.order를 부르는 코드는 컴파일러가 확인한 대로 "체크 예외가 나오지 않는다"고 믿고 작성되었다. 프록시가 선언되지 않은 체크 예외를 그대로 던지면 그 믿음이 깨진다. 그래서 JDK는 선언되지 않은 체크 예외를 언체크 예외인 UndeclaredThrowableException으로 바꿔 자바 언어의 예외 검사 규칙을 지킨다. Proxy와 InvocationHandler의 Javadoc이 정한 규칙이 바이트코드의 예외 표로 구현된 모습이다.

    클라이언트의 order 호출이 $Proxy0에서 h.invoke(this, m3, args)로 바뀌고, 핸들러가 method.invoke(target, args)로 실제 객체를 부른 뒤 값이 되돌아오는 흐름. public class ExceptionMain {
    static Payment wrap(Payment target, InvocationHandler h) {
        return (Payment) Proxy.newProxyInstance(
                Payment.class.getClassLoader(), new Class[]{Payment.class}, h);

    public static void main(String[] args) {
        Payment target = new CardPayment();

        // 1) 포장을 벗기지 않는 핸들러
        Payment naive = wrap(target, (proxy, method, a) -> method.invoke(target, a));
        try {
            naive.pay(-1);
        } catch (IllegalArgumentException e) {
            System.out.println("IllegalArgumentException 으로 잡힘");
        } catch (RuntimeException e) {
            System.out.println("잡힌 예외: " + e.getClass().getName());

            System.out.println("  cause.cause: " + e.getCause().getCause());

        Payment unwrapping = wrap(target, (proxy, method, a) -> {
            try {
                return method.invoke(target, a);
            } catch (InvocationTargetException e) {
                throw e.getCause();
            }
        });
        try {

        } catch (IllegalArgumentException e) {

        }

        Payment logging = wrap(target, (proxy, method, a) -> {
            System.out.println("[핸들러] " + method.getName() + ", default? " + method.isDefault());

        });
        System.out.println(logging.receipt(5000));

    1번: 예외가 두 겹으로 포장된다

    가장 흔하고 가장 해로운 실수다. 실제 객체는 IllegalArgumentException을 던졌고, 호출자는 바로 그 예외를 잡으려고 catch를 써 두었다. 그런데 그 catch는 실행되지 않았다. 과정을 따라가 보자. 실제 객체의 예외를 Method.invoke가 InvocationTargetException으로 감쌌다(첫 번째 포장). 핸들러는 그것을 그대로 던졌다. InvocationTargetException은 체크 예외이고 pay에는 throws 절이 없으므로, 프록시의 예외 표가 그것을 UndeclaredThrowableException으로 다시 감쌌다(두 번째 포장). 호출자 입장에서는 비즈니스 예외가 정체불명의 런타임 예외로 바뀐 것이다.

    이 실수가 해로운 이유는 평소에는 드러나지 않는다는 점이다. 정상 흐름에서는 아무 문제가 없고, 예외가 날 때만 예외 타입이 바뀐다. 예외 타입으로 롤백 여부나 HTTP 상태 코드를 정하는 코드는 그때 엉뚱하게 동작한다. 2번처럼 InvocationTargetException을 잡아 원인(getCause(), 같은 값을 돌려주는 getTargetException())을 다시 던지면 호출자는 원래 예외를 그대로 받는다. 원래 예외가 언체크 예외이거나 인터페이스가 선언한 체크 예외라면 프록시의 예외 표를 그대로 통과하기 때문이다.

    3·4번: default 메서드도 핸들러를 지난다

    receipt는 인터페이스의 default 메서드인데도 핸들러로 왔다. 프록시 클래스는 인터페이스의 메서드를 default 여부와 상관없이 모두 구현하기 때문이다. 핸들러가 method.invoke(target, a)를 부르면 대상 객체가 물려받은 default 구현이 실행된다.

    그렇다면 대상 객체가 아예 없는 프록시라면 default 메서드를 어떻게 실행할까? 4번처럼 대상을 null로 둔 프록시도 만들 수 있다. 인터페이스만 있고 구현은 핸들러가 전부 하는 경우다. 이때 default 메서드까지 핸들러가 직접 구현할 필요는 없다. JDK 16에 추가된 InvocationHandler.invokeDefault(proxy, method, args)는 프록시 인스턴스에 대해 인터페이스의 default 구현을 실행한다. Javadoc은 이것이 프록시 클래스에서 X.super.m(...)을 실행한 것처럼 동작한다고 설명한다. 대상 객체 없이 인터페이스만으로 동작하는 프록시는 스프링 데이터 JPA가 리포지토리 인터페이스만으로 객체를 만들어 주는 방식과 같은 계열의 기법이다.

    5번: 프록시에게 다시 위임하면 끝없이 돈다

    핸들러가 받는 첫 번째 인자 proxy와 생성자로 받은 target을 헷갈리면 method.invoke(proxy, a)를 쓰게 된다. 그러면 프록시의 pay가 다시 핸들러를 부르고, 핸들러가 다시 프록시의 pay를 부르는 재귀가 스택이 넘칠 때까지 반복된다. 결국 StackOverflowError가 나는데, 각 단계가 예외를 다시 포장하면서 올라오기 때문에 바깥에서 받은 예외는 수천 겹짜리 UndeclaredThrowableException이다. 포장 깊이는 실행마다 조금씩 다르고 스레드 스택 크기에 따라서도 크게 달라진다(기본 스택으로 다시 실행하면 3090, 3254처럼 바뀌었고, 같은 코드를 -Xss512k로 실행하면 672였다). proxy 인자는 호출을 받은 프록시가 누구인지 알려 주는 용도이고, 위임 대상이 아니다.

    import java.lang.reflect.InvocationHandler;
import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;
import org.springframework.util.PatternMatchUtils;

public class TraceHandler implements InvocationHandler {
    private final Object target;
    private final CallTracer tracer;
    private final String[] patterns;

    public TraceHandler(Object target, CallTracer tracer, String... patterns) {
        this.target = target;
        this.tracer = tracer;
        this.patterns = patterns;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        if (!PatternMatchUtils.simpleMatch(patterns, method.getName())) {
            return invokeTarget(method, args);
        }
        String message = method.getDeclaringClass().getSimpleName() + "." + method.getName() + "()";
        tracer.begin(message);
        try {
            Object result = invokeTarget(method, args);
            tracer.end(message, null);
            return result;
        } catch (Throwable e) {
            tracer.end(message, e);
            throw e;
        }
    }

    private Object invokeTarget(Method method, Object[] args) throws Throwable {
        try {
            return method.invoke(target, args);
        } catch (InvocationTargetException e) {
            throw e.getCause();
        }
    }
}

    TraceHandler의 첫 줄이 그 판단이다. 메서드 이름이 패턴 목록 중 어느 것과도 맞지 않으면 추적 없이 바로 대상에 위임한다. 패턴 비교에는 스프링 코어의 PatternMatchUtils.simpleMatch를 썼다. 이 메서드의 Javadoc과 소스(6.2.19)에 따르면 지원하는 형식은 정확히 일치, xxx*(접두사), *xxx(접미사), *xxx*(포함), xxx*yyy이고 별표 부분은 여러 개가 될 수 있다. 문자열이나 패턴이 null이면 false를 돌려주고, 패턴 배열 버전은 하나라도 맞으면 true다. 정규 표현식이 아니므로 .이나 ?는 특별한 의미가 없다.

    이 작은 필터에는 앞으로의 회차를 미리 보여 주는 구조가 들어 있다. 핸들러 안에는 성격이 다른 두 가지 일이 섞여 있다. 하나는 "어디에 적용할 것인가"(메서드 이름 패턴 검사)이고, 다른 하나는 "무엇을 할 것인가"(추적 로그)다. 지금은 둘이 한 클래스에 묶여 있어서, 적용 대상을 바꾸려면 패턴 문자열을 바꾸고, 적용 대상의 기준을 메서드 이름이 아니라 애노테이션이나 패키지로 바꾸려면 핸들러 코드를 고쳐야 한다. 스프링은 이 둘을 포인트컷(Pointcut)과 어드바이스(Advice)라는 별개의 객체로 나누고, 그 한 쌍을 어드바이저(Advisor)라고 부른다. 05회에서 이 분리를 보고, 09회에서 포인트컷 표현식을 본다.

    CGLIB — 소개

    JDK 동적 프록시에는 넘을 수 없는 전제가 있다. 프록시 클래스가 Proxy를 상속하고 인터페이스를 구현하는 방식이므로, 인터페이스가 있어야 한다. 자바 클래스는 부모를 하나만 가질 수 있는데 그 자리를 이미 Proxy가 차지하고 있으니, 구체 클래스를 상속하는 프록시는 이 방식으로 만들 수 없다. 그런데 실무 코드에는 인터페이스 없이 구체 클래스만 있는 빈이 많다.

    이 빈자리를 채우는 것이 CGLIB(Code Generation Library)다. CGLIB 저장소의 소개에 따르면 CGLIB는 자바 바이트코드를 생성하고 변환하는 고수준 API이며, AOP·테스트·데이터 접근 프레임워크가 동적 프록시 객체를 만들고 필드 접근을 가로채는 데 쓴다. 바이트코드를 직접 쓰는 일은 ASM이라는 저수준 라이브러리가 맡고, CGLIB는 그 위에서 "이 클래스를 상속한 프록시를 만들라" 같은 수준의 API를 제공한다. CGLIB가 만드는 프록시는 대상 클래스의 하위 클래스다. 부모 클래스의 메서드를 재정의해서, 호출이 오면 부가 기능을 끼워 넣은 뒤 부모의 원래 구현이나 별도의 대상 객체를 부른다.

    스프링을 쓸 때 CGLIB를 따로 의존성에 추가할 필요는 없다. spring-core의 org.springframework.cglib 패키지 문서는 이것을 CGLIB 3.3을 스프링 전용 패치와 함께 재패키징한 것이며 내부용이라고 설명하고, 이 패키지는 스프링 3.2부터 있었다. ASM도 org.springframework.asm으로 함께 재패키징되어 있다. 패키지 이름을 바꿔 넣은 이유는 애플리케이션이나 다른 라이브러리가 쓰는 CGLIB 버전과 충돌하지 않게 하기 위해서다. 한편 원래의 CGLIB 프로젝트 README는 CGLIB가 더 이상 유지보수되지 않으며 JDK 17 이상에서는 잘 동작하지 않을 수 있으니 ByteBuddy 같은 대안으로 옮기기를 권한다. 스프링은 재패키징한 사본에 직접 패치를 더해 가며 쓰고 있으므로, 스프링 사용자에게 의미가 있는 것은 스프링 안에 들어 있는 CGLIB다.

    CGLIB 프록시의 핵심 타입은 둘이다. Enhancer는 프록시 클래스를 만드는 생성기이고, MethodInterceptor는 JDK의 InvocationHandler에 해당하는 콜백이다.

    currency()는 인터셉터를 거치지 않았다. final 메서드는 하위 클래스에서 재정의할 수 없으므로, 프록시 클래스에는 currency()가 아예 없다. 호출은 부모 클래스의 currency()로 바로 간다. 이 예제에서는 결과가 같아서 티가 나지 않지만, 부모 쪽 구현이 필드를 읽는 메서드였다면 대상 객체의 필드가 아니라 프록시 객체 자신의 필드를 읽는다. 위임만 하는 프록시의 필드는 초기화되지 않은 경우가 많으므로, final 메서드가 엉뚱한 값을 돌려주는 원인이 된다. 스프링 레퍼런스가 final 메서드에는 어드바이스를 적용할 수 없다고 적는 이유가 이것이다.

    생성된 클래스는 어디에 정의되는가

    프록시 클래스 이름이 PriceCalculator$$...로, 대상 클래스와 같은 패키지에 있다는 점도 의미가 있다. 스프링 6.2.19에 재패키징된 CGLIB의 ReflectUtils.defineClass는 생성한 바이트 배열을 JVM에 올릴 때, 문맥 클래스(Enhancer의 경우 부모 클래스)의 클래스 로더가 대상 로더와 같으면 JDK 9부터 있는 MethodHandles.privateLookupIn(문맥 클래스, ...).defineClass(바이트)를 먼저 시도한다.     첫 번째 오류는 생성자 사슬 때문이다. 하위 클래스의 생성자는 부모 생성자 중 하나를 반드시 호출해야 하는데, create()는 인자 없는 생성자를 쓰겠다는 뜻이고 Fee에는 그런 생성자가 없다. create(인자 타입 배열, 인자 배열)로 부모 생성자에 넘길 값을 주면 만들 수 있지만, 그러면 프록시를 만들 때마다 부모 생성자에 넘길 의미 있는 값을 알아야 한다. 위임만 하는 프록시에게 그런 값은 대개 무의미하다. 스프링 AOP가 Objenesis로 생성자 호출 자체를 건너뛰는 이유가 여기 있다.

    실험 중에 관찰한 세부 하나를 덧붙인다. 같은 JVM에서 인자 없는 create()가 실패한 뒤, 같은 설정의 Enhancer로 인자 있는 create(...)를 부르면 그것도 처음과 같은 예외로 실패했다. 소스를 보면 CGLIB의 클래스 생성 캐시(LoadingCache)는 생성 작업을 FutureTask로 맵에 먼저 넣고, 성공했을 때만 결과로 바꿔 넣는다. 실패한 작업은 맵에 그대로 남아 같은 키로 다시 요청하면 같은 예외가 다시 나온다. 클래스 생성 키에는 생성자 인자 타입이 들어가지 않으므로 두 요청은 같은 키다. 위 표의 두 번째 줄은 그래서 별도의 JVM에서 실행한 결과다.

    final 클래스는 상속 자체가 불가능하니 프록시를 만들 수 없다. 자바의 record 클래스는 암묵적으로 final이므로 같은 이유로 CGLIB 프록시 대상이 될 수 없다. final 메서드는 더 조용한 문제다. 오류 없이 프록시가 만들어지고, 그 메서드만 부가 기능 없이 실행된다. private 메서드도 재정의할 수 없으므로 같은 운명이다. 스프링 레퍼런스는 CGLIB 프록시의 제약으로 final 클래스는 프록시할 수 없고 final 메서드와 private 메서드에는 어드바이스를 적용할 수 없다고 명시한다. CGLIB 프록시로 감싼 빈에서 final 메서드에 붙인 트랜잭션 애노테이션이 효과가 없는 것도 같은 이유다.

    정리 — 두 동적 프록시 기술 나란히 놓기

    지금까지 본 두 기술을 같은 기준으로 비교하면 다음과 같다. 모든 항목이 이 회차의 실행 결과나 문서로 확인한 내용이다.

    두 기술 모두 "실행 중에 클래스를 만든다"는 공통점이 있고, 만든 클래스는 각자의 캐시로 재사용된다. JDK는 클래스 로더별로 인터페이스 목록을 키로, CGLIB는 부모 클래스·인터페이스·콜백 타입 등을 묶은 키로 캐시한다. 그래서 프록시 객체를 많이 만들어도 클래스는 조합마다 하나다.

    남은 문제도 분명하다. 첫째, 같은 부가 기능(로그 추적)을 JDK 프록시용 InvocationHandler와 CGLIB용 MethodInterceptor로 두 번 써야 한다. 대상에 인터페이스가 있는지에 따라 어느 쪽을 쓸지도 직접 골라야 한다. 둘째, 적용 대상을 고르는 로직(메서드 이름 패턴)이 부가 기능 코드 안에 섞여 있다. 셋째, 빈마다 프록시를 만들어 등록하는 조립 코드가 필요하다. 스프링은 첫째와 둘째를 ProxyFactory와 어드바이스·포인트컷으로 풀고(05회), 셋째를 빈 후처리기로 풀며(06회), 그 위에 @Aspect를 얹는다(07~08회). JDK 프록시와 CGLIB의 차이가 의존관계 주입에서 일으키는 문제는 10회에서 다시 만난다.

    이 장의 핵심

    리플렉션은 "어떤 메서드를 부를지"를 Method라는 값으로 바꾸고, 동적 프록시는 그 값을 받아 줄 클래스를 실행 중에 생성한다. JDK 동적 프록시는 Proxy를 상속하고 인터페이스를 구현한 클래스를, CGLIB는 대상 클래스를 상속한 하위 클래스를 만든다. 두 경우 모두 생성된 메서드는 호출을 (프록시, 메서드, 인자)라는 데이터로 바꿔 콜백 하나에 넘길 뿐이다. 그래서 부가 기능을 한 번만 쓸 수 있고, 생성된 클래스의 구조(인터페이스 구현이냐 상속이냐)가 타입 캐스팅, final, 생성자, 예외 포장 같은 모든 제약을 결정한다.
    리플렉션(reflection)
    Class·Method·Field로 클래스 구조를 실행 중에 읽고 호출하는 기능이다. 호출할 메서드를 값으로 넘길 수 있게 되는 대신, 컴파일 시점의 타입 검사가 실행 시점의 예외로 밀린다.
    InvocationTargetException
    Method.invoke로 부른 대상 메서드가 던진 예외를 감싸는 체크 예외다. 프록시 핸들러가 벗기지 않으면 UndeclaredThrowableException으로 한 번 더 포장된다.
    JDK 18의 리플렉션 재구현
    JEP 416으로 Method.invoke 등이 메서드 핸들 위에 다시 구현되었다. JDK 21의 호출 경로에는 DirectMethodHandleAccessor가 보인다.
    JDK 동적 프록시
    Proxy.newProxyInstance가 Proxy를 상속하고 지정한 인터페이스를 구현한 final 클래스를 생성한다. 모든 인터페이스 메서드와 hashCode·equals·toString이 InvocationHandler.invoke로 모인다.
    생성된 $Proxy 클래스의 구조
    메서드마다 정적 Method 필드가 있고, 메서드 본문은 h.invoke(this, m, args)를 부른 뒤 반환값을 캐스팅·언박싱한다. 선언되지 않은 체크 예외는 예외 표에서 UndeclaredThrowableException으로 바뀐다.
    메서드 이름 필터
    프록시는 모든 메서드를 핸들러로 보내므로 적용 대상은 핸들러가 고른다. PatternMatchUtils.simpleMatch는 xxx*, *xxx, *xxx*, xxx*yyy 형식을 지원한다. 이 판단을 분리한 것이 포인트컷이다.
    CGLIB
    ASM 위에서 동작하는 바이트코드 생성 라이브러리로, 대상 클래스의 하위 클래스를 프록시로 만든다. 스프링은 3.2부터 spring-core에 org.springframework.cglib로 재패키징해 포함한다.
    MethodProxy와 FastClass
    MethodProxy.invoke는 원래 클래스의 메서드를, invokeSuper는 생성된 클래스의 CGLIB$... 메서드를 FastClass의 tableswitch로 직접 호출한다. 대상 메서드의 예외는 포장 없이 전달된다.
    상속에서 오는 제약
    CGLIB 프록시는 final 클래스를 만들 수 없고, final·private 메서드는 가로채지 못하며, 부모 생성자가 실행된다. 기본 생성자가 없으면 생성자 인자를 따로 줘야 한다.

    운영 중인 서비스에서 특정 예외만 골라 경고 알림을 보내는 코드가 있는데, 어느 날부터 알림이 오지 않는다고 하자. 로그를 보면 예외는 나고 있지만 타입이 UndeclaredThrowableException이다. 이 회차를 읽은 사람은 바로 "누군가 리플렉션 위에 프록시를 쌓고 InvocationTargetException을 벗기지 않았다"를 의심한다. 직접 만든 감사(audit) 로그 프록시, 사내 라이브러리의 재시도 래퍼처럼 InvocationHandler를 쓰는 코드를 찾으면 대개 원인이 나온다. 스택 트레이스의 Caused by를 끝까지 내려가 원래 예외를 찾는 습관도 같은 이유로 중요하다.

    프록시를 직접 만들지 판단할 때는 대상의 형태가 기준이 된다. 대상이 인터페이스로 노출되어 있고 구현 클래스 타입으로 주입받는 코드가 없다면 JDK 프록시로 충분하다. 구체 클래스를 감싸야 한다면 CGLIB를 써야 하고, 그때는 final 메서드, 생성자 부수 효과, 기본 생성자 유무를 먼저 점검해야 한다. 코틀린처럼 클래스와 메서드가 기본적으로 final인 언어에서 스프링 빈에 별도 설정 없이 프록시가 걸리지 않는 문제도 같은 원리에서 나온다.

    성능 판단도 원리에서 출발해야 한다. 프록시 호출은 인자 배열 생성, 박싱, 리플렉션 또는 FastClass 경유라는 고정 비용을 더한다. 이 비용은 메서드 호출 하나 단위의 비용이므로, 데이터베이스 왕복이나 네트워크 호출을 하는 서비스 계층 메서드에서는 보통 무시할 만하고, 아주 짧은 메서드를 반복문 안에서 수백만 번 부르는 경로에서는 의미가 생길 수 있다. 어느 쪽인지는 짐작이 아니라 측정으로 정해야 한다. 그리고 프록시 클래스는 클래스 로더가 살아 있는 동안 메타스페이스에 남으므로, 실행 중에 인터페이스 조합을 계속 바꿔 가며 프록시를 만드는 코드가 있다면 클래스 수가 늘어나는지 확인해 볼 필요가 있다.

    1번. JDK 프록시의 count() 본문은 핸들러가 돌려준 값을 checkcast Integer한 뒤 Integer.intValue()를 호출한다. null은 checkcast를 통과하지만 intValue() 호출에서 NullPointerException이 난다. InvocationHandler Javadoc이 정한 "기본형 반환 메서드에 null을 돌려주면 NullPointerException" 규칙이 이렇게 구현되어 있다. CGLIB 프록시의 생성된 메서드는 인터셉터의 반환값이 null인지 먼저 검사(ifnonnull)하고, null이면 iconst_0으로 0을 반환한다. 그래서 예외 없이 0이 나온다. 같은 실수가 한쪽에서는 즉시 드러나고 다른 쪽에서는 조용히 잘못된 값이 된다.

    2번. 대상의 IOException은 Method.invoke에서 InvocationTargetException으로 감싸진다. 핸들러가 그것을 그대로 던지면, read()가 선언한 예외는 IOException뿐이고 InvocationTargetException은 그 하위 타입이 아니므로 UndeclaredThrowableException으로 다시 감싸진다. 호출자의 catch (IOException e)는 실행되지 않는다. 핸들러가 e.getCause()를 던지면 원래의 IOException이 나오고, 프록시의 예외 표에 IOException을 그대로 다시 던지는 항목이 있으므로 호출자가 그대로 받는다. 예외 표는 Error, RuntimeException, IOException은 그대로 다시 던지고, 그 밖의 Throwable은 UndeclaredThrowableException으로 감싸는 네 항목이 된다. 실제로 throws IOException을 선언한 인터페이스의 프록시를 덤프해 보면 이 네 항목이 나온다.

    3번. 서비스가 실제 저장소를 직접 부르므로 MemberStore.insert() 두 줄이 사라지고, 컨트롤러와 서비스 두 단계만 찍힌다. 저장소 쪽 호출은 핸들러를 거치지 않기 때문이다. 프록시는 "참조를 바꿔치기한 곳"에서만 동작한다는 것을 보여 주는 예다. 프록시 객체는 컨트롤러용과 서비스용 두 개, 프록시 클래스도 SignupController용과 MemberService용 두 개가 만들어진다. 같은 원리가 08회 이후의 "프록시 내부 호출" 문제로 이어진다. 객체 내부에서 this로 부르는 호출도 프록시를 지나지 않는다.

    4번. Enhancer.create()는 인자 없는 생성자를 쓰므로 프록시 객체 자신의 value는 this(0)에 의해 0이다. proxy.next()는 재정의된 메서드라 인터셉터를 거쳐 target.next()가 실행되고, target의 value가 10에서 11이 되어 11을 반환한다. proxy.peek()은 final이라 재정의되지 않았으므로 부모 구현이 프록시 객체 자신에 대해 실행되어 프록시의 value, 즉 0을 반환한다. final 메서드가 오류 없이 엉뚱한 상태를 읽는 전형적인 경우다. 스프링 AOP처럼 Objenesis로 생성자를 건너뛰고 만든 프록시라면 생성자가 한 번도 실행되지 않으므로 value는 필드의 기본값 0이 된다.

     Proxy.newProxyInstance로 만든 프록시 객체 p(인터페이스 OrderService, 대상 OrderServiceImpl)에 대한 설명으로 옳은 것은? p instanceof OrderServiceImpl은 true다. 프록시는 대상 객체의 타입을 그대로 따른다. p.getClass().getSuperclass()는 java.lang.reflect.Proxy이고, p.getClass() 호출은 핸들러를 거치지 않는다. p.toString()은 Object의 메서드이므로 핸들러를 거치지 않는다. 핸들러를 다르게 주면 newProxyInstance를 부를 때마다 새로운 프록시 클래스가 생성된다. JDK 프록시 클래스는 Proxy를 상속하고 지정한 인터페이스만 구현하므로 구현 클래스와는 관계가 없다(0번 오답). getClass는 Object의 final 메서드라 재정의되지 않아 핸들러를 거치지 않는다(1번 정답). 반면 hashCode·equals·toString은 핸들러로 간다(2번 오답). 프록시 클래스는 클래스 로더와 인터페이스 목록(순서 포함)으로 캐시되며 핸들러는 생성자 인자일 뿐이므로 같은 클래스가 재사용된다(3번 오답). 핸들러가 return method.invoke(target, args);만 하는 JDK 프록시에서, 대상 메서드가 IllegalStateException을 던졌다. 인터페이스 메서드에는 throws 절이 없다. 호출자가 받는 예외는? IllegalStateException — 언체크 예외는 어디서든 그대로 전파된다. InvocationTargetException — Method.invoke가 감싼 그대로 나온다. UndeclaredThrowableException — 원인은 InvocationTargetException이고, 그 원인이 IllegalStateException이다. IllegalArgumentException — 리플렉션 호출이 실패했기 때문이다. Method.invoke는 대상 메서드가 던진 예외를 InvocationTargetException으로 감싼다. 이 예외는 체크 예외이고 인터페이스 메서드가 선언하지 않았으므로, 프록시 클래스의 예외 표가 UndeclaredThrowableException으로 한 번 더 감싼다. 원래 예외가 언체크라도 핸들러가 포장을 벗기지 않으면 그대로 나오지 않는다. IllegalArgumentException은 인자 개수·타입이 맞지 않는 등 리플렉션 호출 자체의 문제일 때 나온다. CGLIB(Enhancer)로 만든 프록시에 대한 설명으로 옳지 않은 것은? 생성된 프록시 클래스는 대상 클래스의 하위 클래스이므로 대상 클래스 타입 변수에 대입할 수 있다. final 메서드는 재정의되지 않으므로 인터셉터를 거치지 않고 부모의 구현이 실행된다. Enhancer.create()로 프록시를 만들면 부모 클래스의 인자 없는 생성자가 실행된다. MethodProxy.invoke(obj, args)에 인터셉터의 첫 인자(프록시 자신)를 넘기면 부모의 원래 구현이 실행된다. MethodProxy.invoke는 원래 클래스의 메서드를 주어진 객체에 대해 호출한다. 프록시 자신을 넘기면 재정의된 메서드가 다시 불려 인터셉터로 돌아오므로 무한 재귀 끝에 StackOverflowError가 난다. 부모 구현을 실행하려면 invokeSuper(obj, args)를 써야 하며, 이것은 생성된 클래스의 CGLIB$메서드$번호를 통해 invokespecial로 부모 메서드를 부른다. 나머지 셋은 실행 결과로 확인한 사실이다. JDK 동적 프록시와 CGLIB 프록시 중 하나를 골라야 한다. 대상은 인터페이스 없이 구체 클래스로만 되어 있고, 모든 public 메서드가 final로 선언되어 있다. 가장 정확한 판단은? JDK 프록시는 인터페이스가 없어 쓸 수 없고, CGLIB 프록시는 만들어지기는 하지만 final 메서드를 가로챌 수 없어 부가 기능이 적용되지 않는다. CGLIB는 바이트코드를 생성하므로 final 메서드도 재정의해서 가로챌 수 있다. JDK 프록시는 리플렉션을 쓰므로 인터페이스 없이도 구체 클래스의 메서드를 가로챌 수 있다. 두 방식 모두 프록시 생성 시점에 예외가 나므로 실행 전에 문제를 알 수 있다. JDK 프록시는 Proxy를 상속하고 인터페이스를 구현하는 클래스를 만들므로 인터페이스가 필수다. CGLIB는 하위 클래스를 만들기 때문에 자바의 상속 규칙을 벗어날 수 없고, final 메서드는 생성된 클래스에 재정의되지 않는다. 클래스 자체가 final이 아니면 프록시 생성은 성공하므로 오류가 나지 않고, 부가 기능만 조용히 빠진다. 바로 이 "조용한 실패"가 실무에서 위험하다. JDK 18 이후(예: JDK 21)의 Method.invoke에 대한 설명으로 옳은 것은? 모든 리플렉션 호출은 HotSpot의 네이티브 메서드로 처리되며, 일정 횟수 이후 전용 바이트코드가 생성된다. getMethod는 같은 메서드에 대해 항상 같은 Method 객체를 반환하므로 ==로 비교해도 된다. 대상 메서드 호출은 메서드 핸들 기반 중계 객체를 거치며, VM 초기화 초기에만 네이티브 방식이 쓰인다. 인터페이스에서 얻은 Method는 구현 객체에 대해 호출해도 인터페이스의 default 구현만 실행된다. JEP 416(JDK 18)은 Method::invoke 등을 메서드 핸들 위에 다시 구현했고, VM 초기화 초기에만 네이티브 리플렉션을 쓴다. 0번은 JDK 18 이전의 방식이다. getMethod는 매번 사본을 돌려주므로 ==는 false이고 equals로 비교해야 한다. Method.invoke는 인스턴스 메서드를 동적 메서드 조회로 호출하므로 구현 객체의 재정의된 메서드가 실행된다.
    리플렉션(reflection)
    실행 중에 클래스의 구조(필드, 메서드, 생성자)를 조회하고 그 멤버를 호출·변경하는 기능이다. 자바에서는 java.lang.reflect 패키지와 Class가 제공한다.
    동적 프록시(dynamic proxy)
    프록시 클래스를 소스 코드로 작성하지 않고 프로그램 실행 중에 생성해 쓰는 프록시다. JDK의 Proxy와 CGLIB가 대표적이다.
    InvocationHandler
    JDK 동적 프록시가 받은 모든 메서드 호출을 넘겨받는 콜백 인터페이스다. invoke(proxy, method, args) 하나로 이루어진다.
    UndeclaredThrowableException
    프록시의 핸들러가 인터페이스 메서드가 선언하지 않은 체크 예외를 던졌을 때, 그 예외를 감싸서 대신 던져지는 언체크 예외다.
    동적 모듈(dynamic module)
    JDK가 프록시 클래스를 정의하기 위해 실행 중에 만드는 모듈이다. OpenJDK 21에서는 클래스 로더마다 하나씩 jdk.proxyN 이름으로 만들어진다.
    CGLIB(Code Generation Library)
    ASM 위에서 바이트코드를 생성·변환하는 라이브러리다. 대상 클래스를 상속한 프록시 클래스를 만들 수 있고, 스프링은 이를 spring-core에 재패키징해 쓴다.
    Enhancer
    CGLIB에서 부모 클래스와 콜백을 받아 하위 클래스 프록시를 생성하는 클래스다.
    MethodProxy
    CGLIB 인터셉터에 전달되는 호출 도구다. FastClass를 통해 원래 메서드(invoke)나 부모 구현(invokeSuper)을 리플렉션 없이 호출한다.
    FastClass
    클래스의 메서드마다 번호를 매기고, 번호로 tableswitch해서 해당 메서드를 일반 바이트코드 호출로 부르는 CGLIB의 생성 클래스다.
