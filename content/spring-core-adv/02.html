    이 회차의 질문: 한 줄짜리 핵심 기능을 열 줄이 감싸고 있다

    01회에서 로그 추적기를 만들어 컨트롤러·서비스·리포지토리의 메서드마다 붙였고, 동시에 들어온 요청들이 추적 깊이 정보를 서로 덮어쓰는 문제를 ThreadLocal로 풀었다. 기능은 이제 원하는 대로 동작한다. 그런데 추적기를 붙인 코드를 다시 열어 보면 다른 종류의 문제가 보인다. 이 회차는 그 문제, 즉 모든 메서드에 똑같이 들어간 부가 코드를 어떻게 한곳으로 모을 것인가를 다룬다.

    이 회차의 예제는 도서 대출 흐름이다. 컨트롤러가 대출 요청을 받고, 서비스가 업무 규칙을 처리하고, 리포지토리가 대출 기록을 저장한다. 추적기는 아래의 최소 인터페이스로 본다. 이름과 시그니처는 이 회차의 설명을 위해 정한 것이며, 01회에서 만든 구현과 세부가 다를 수 있다.

    public interface Tracer {
    Span begin(String message);          // 시작 로그를 남기고 진행 정보를 돌려준다
    void end(Span span);                 // 정상 종료 로그(소요 시간 포함)
    void fail(Span span, Exception e);   // 예외 종료 로그
}

// 한 구간의 진행 정보: 트랜잭션 번호, 호출 깊이, 메시지, 시작 시각
public record Span(long txId, int depth, String message, long startNanos) {
}

    이 회차의 예제를 직접 돌려 볼 수 있도록 최소 구현도 하나 붙인다. 깊이와 트랜잭션 번호를 스레드마다 따로 두기 위해 ThreadLocal을 쓰고, 가장 바깥 구간이 끝나면 remove()로 비운다. 스레드 풀에서 remove()를 빠뜨리면 무엇이 새는지는 01회의 주제였다.

    import java.util.concurrent.atomic.AtomicLong;

public class ConsoleTracer implements Tracer {

    private static final AtomicLong TX_SEQ = new AtomicLong();
    private final ThreadLocal context = new ThreadLocal<>(); // {txId, depth}

    @Override
    public Span begin(String message) {
        long[] ctx = context.get();
        if (ctx == null) {
            ctx = new long[]{TX_SEQ.incrementAndGet(), -1};
            context.set(ctx);
        }
        ctx[1]++;
        Span span = new Span(ctx[0], (int) ctx[1], message, System.nanoTime());
        System.out.println("[tx=" + span.txId() + "] " + "  ".repeat(span.depth()) + "→ " + message);
        return span;
    }

    @Override
    public void end(Span span) {
        long ms = (System.nanoTime() - span.startNanos()) / 1_000_000;
        System.out.println("[tx=" + span.txId() + "] " + "  ".repeat(span.depth())
                + "← " + span.message() + " (" + ms + "ms)");
        release(span);
    }

    @Override
    public void fail(Span span, Exception e) {
        System.out.println("[tx=" + span.txId() + "] " + "  ".repeat(span.depth())
                + "x " + span.message() + " " + e);
        release(span);
    }

    private void release(Span span) {
        if (span.depth() == 0) {
            context.remove();          // 가장 바깥 구간이 끝나면 스레드에서 지운다
        } else {
            context.get()[1]--;
        }
    }
}

    이 추적기를 서비스 메서드 하나에 붙이면 다음과 같이 된다.

    public class LoanServiceV0 {

    private final LoanRepositoryV0 loanRepository;
    private final Tracer tracer;

    public LoanServiceV0(LoanRepositoryV0 loanRepository, Tracer tracer) {
        this.loanRepository = loanRepository;
        this.tracer = tracer;
    }

    public void borrow(String bookId) {
        Span span = tracer.begin("LoanServiceV0.borrow()");
        try {
            loanRepository.save(bookId);      // 핵심 기능은 이 한 줄
            tracer.end(span);
        } catch (Exception e) {
            tracer.fail(span, e);
            throw e;                          // 예외를 먹지 않고 다시 던진다
        }
    }
}

    메서드 본문은 아홉 줄인데 대출이라는 업무와 관련된 줄은 하나뿐이다. 나머지 여덟 줄은 추적을 위한 것이다. 이렇게 그 메서드가 존재하는 이유가 되는 코드를 핵심 기능(core concern), 핵심 기능을 보조하기 위해 덧붙인 코드를 부가 기능이라고 부르자. 부가 기능은 컨트롤러에도, 리포지토리에도, 다른 서비스의 모든 메서드에도 같은 모양으로 들어간다. 이렇게 여러 모듈을 가로질러 반복되는 관심사를 횡단 관심사(cross-cutting concern)라고 하며, 이 권의 후반부(07회 이후)에서 다룰 AOP가 정면으로 다루는 대상이다. 이 회차는 그보다 한참 앞 단계, 순수한 자바 객체 설계만으로 어디까지 정리할 수 있는지를 본다.

    예를 들어 추적 대상 메서드가 백 개라면 위의 여덟 줄이 백 벌 생긴다. 로그에 사용자 번호를 넣기로 하면, 또는 실패 로그를 남긴 뒤 예외를 감싸서 던지기로 하면 백 군데를 모두 고쳐야 한다. 한 군데라도 빠뜨리면 그 메서드만 다르게 동작한다. 단일 책임 원칙(Single Responsibility Principle)을 "클래스가 변경되는 이유는 하나여야 한다"로 읽으면, 지금의 borrow()는 대출 규칙이 바뀔 때도, 로그 형식이 바뀔 때도 고쳐야 하므로 변경 이유가 둘이다.

    메서드 추출로는 왜 안 되는가

    코드가 중복되면 가장 먼저 떠오르는 처방은 메서드 추출(extract method)이다. 반복되는 문장들을 메서드 하나로 옮기고, 원래 자리에서는 그 메서드를 호출한다. 그런데 메서드 추출은 반복되는 부분이 연속된 문장 덩어리일 때 통한다. 위 코드에서 반복되는 부분은 하나의 덩어리가 아니다. 핵심 기능의 앞(begin), 뒤(end), 그리고 예외 경로(fail과 재던지기)로 세 조각 나 있고, 그 조각들을 try/catch라는 구조가 묶고 있다. 변하는 부분이 변하지 않는 부분의 한가운데에 끼어 있는 것이다.

      변하지 않는 부분          Span span = tracer.begin(...);
                             try {
  변하는 부분  ───────────▶      loanRepository.save(bookId);
                                 tracer.end(span);
  변하지 않는 부분           } catch (Exception e) {
                                 tracer.fail(span, e);
                                 throw e;
                             }

    begin 호출과 end 호출을 각각 작은 메서드로 뺄 수는 있다. 하지만 "앞에서 시작하고, 가운데를 실행하고, 성공하면 종료를 남기고, 실패하면 실패를 남긴 뒤 다시 던진다"는 모양 자체는 여전히 메서드마다 남는다. 이 모양을 한곳에 두려면 그 모양을 가진 메서드 하나가 "가운데에 들어갈 코드"를 인자로 받아야 한다. 자바의 메서드는 값을 인자로 받지 문장을 받지 않는다. 그래서 코드를 넘기려면 코드를 객체의 메서드로 포장해야 하고, 방법은 크게 두 가지다.

    • 상속: 뼈대를 가진 부모 클래스가 구멍을 추상 메서드로 남기고, 자식 클래스가 그 구멍을 채운다. 템플릿 메서드 패턴이다.
    • 위임: 뼈대를 가진 객체가 구멍에 들어갈 코드를 다른 객체로 받아서 호출한다. 그 객체를 필드로 받아 두면 전략 패턴, 실행할 때마다 인자로 받으면 템플릿 콜백 패턴이다.

    자바 8의 람다는 두 번째 방법을 짧게 쓰는 문법이다. 다만 겉모양만 짧아진 것이 아니라 컴파일 결과와 실행 시점의 동작도 익명 클래스와 다르다. 이 회차는 세 패턴을 차례로 만들면서 각 단계에서 JVM이 실제로 무엇을 하는지 한 층씩 내려가 본다.

    이 장의 핵심

    변하는 것과 변하지 않는 것을 분리한다. 변하지 않는 뼈대(시작, try/catch, 종료와 실패 처리)는 한곳에 두고, 변하는 핵심 기능은 각자의 자리에 둔다. 변하는 부분이 뼈대의 한가운데에 끼어 있기 때문에, 그 부분을 "끼워 넣을 수 있는 코드 조각", 즉 객체로 만드는 것이 이 회차 세 패턴의 공통 과제다.

    템플릿 메서드 패턴: 부모가 뼈대를, 자식이 구멍을 맡는다

    로그 추적기에 바로 적용하기 전에 더 작은 예로 구조를 보자. 두 작업이 있고, 둘 다 실행 시간을 재서 출력해야 한다.

    public class TimingBefore {

    public static void main(String[] args) {
        sendMail();
        chargeFee();
    }

    static void sendMail() {
        long start = System.nanoTime();
        System.out.println("메일 발송");                 // 핵심 기능
        long elapsedMs = (System.nanoTime() - start) / 1_000_000;
        System.out.println("sendMail 소요 시간=" + elapsedMs + "ms");
    }

    static void chargeFee() {
        long start = System.nanoTime();
        System.out.println("요금 청구");                 // 핵심 기능
        long elapsedMs = (System.nanoTime() - start) / 1_000_000;
        System.out.println("chargeFee 소요 시간=" + elapsedMs + "ms");
    }
}

    두 메서드는 가운데 한 줄만 다르다. 시간을 재는 앞뒤는 변하지 않는 부분이고, 가운데는 변하는 부분이다. 템플릿 메서드 패턴(Template Method pattern)은 변하지 않는 부분을 부모 클래스의 메서드 하나에 모으고, 변하는 부분을 추상 메서드로 비워 둔다. 이 뼈대를 가진 메서드를 템플릿 메서드라고 부른다.

    public abstract class TimedTemplate {

    public final void execute() {
        long start = System.nanoTime();
        call();                                        // 변하는 부분
        long elapsedMs = (System.nanoTime() - start) / 1_000_000;
        System.out.println(getClass().getName() + " 소요 시간=" + elapsedMs + "ms");
    }

    protected abstract void call();
}

public class SendMailTask extends TimedTemplate {
    @Override
    protected void call() {
        System.out.println("메일 발송");
    }
}

public class ChargeFeeTask extends TimedTemplate {
    @Override
    protected void call() {
        System.out.println("요금 청구");
    }
}
    TimedTemplate t1 = new SendMailTask();
t1.execute();
TimedTemplate t2 = new ChargeFeeTask();
t2.execute();

    소요 시간은 실행마다 다를 수 있다(작업이 너무 짧아 대개 0ms로 나온다). 출력에서 확인할 것은 두 가지다. 첫째, 시간을 재는 코드는 TimedTemplate 한 곳에만 있는데 두 작업 모두 측정된다. 둘째, 같은 execute() 코드 안의 getClass().getName()이 객체마다 다른 이름을 돌려준다. getClass()는 변수의 선언 타입이 아니라 객체가 실제로 만들어진 클래스를 돌려주기 때문이다.

    템플릿 메서드에 붙인 final은 장식이 아니다. 자식 클래스가 뼈대 자체를 재정의해 버리면 "변하지 않는 부분을 한곳에 둔다"는 목적이 깨진다. JLS §8.4.3.3에 따라 final 메서드는 재정의할 수 없으므로, 자식이 execute()를 재정의하려 하면 컴파일러가 막는다.

    Ovr.java:2: error: execute() in Ovr cannot override execute() in TimedTemplate
    @Override public void execute() {}
                          ^
  overridden method is final

    구멍인 call()은 protected로 두었다. 바깥 코드가 뼈대를 건너뛰고 call()을 직접 부르는 일을 줄이려는 의도다. 다만 자바의 protected는 하위 클래스뿐 아니라 같은 패키지의 모든 코드에도 열려 있으므로(JLS §6.6.1), 완전한 차단은 아니라는 점을 기억해 두자.

                     TimedTemplate  (abstract)
                 ├─ execute()  public final   ← 변하지 않는 뼈대: 시간 측정과 출력
                 └─ call()     protected abstract ← 비워 둔 구멍
                          ▲
                          │ extends
              ┌───────────┴───────────┐
        SendMailTask             ChargeFeeTask
        call(): "메일 발송"       call(): "요금 청구"

  호출 방향:  클라이언트 ──▶ execute() (부모 코드) ──▶ call() (자식 코드)
    부모 클래스가 뼈대 메서드를 갖고 자식 클래스가 구멍만 채우며, 실행 중에는 부모의 코드가 자식의 코드를 부른다는 방향을 한눈에 보여 준다. 왼쪽 절반은 UML 스타일 클래스 다이어그램. 맨 위에 상자 "TimedTemplate (추상)"이 있고 안에 두 줄 "execute() final"과 "call() abstract"가 있다. "call() abstract" 줄은 점선 테두리의 빈 칸처럼 표현한다. 아래에 상자 두 개 "SendMailTask"와 "ChargeFeeTask"가 있고 각각 속이 빈 삼각형 화살표로 부모를 가리킨다(상속). 각 자식 상자에는 "call(): 메일 발송", "call(): 요금 청구"라고 적는다. 오른쪽 절반은 세로 시퀀스 다이어그램. 생명선 세 개 "클라이언트", "execute() (부모 코드)", "call() (자식 코드)". 화살표 1: 클라이언트에서 execute로 "execute()". 화살표 2: execute 자기 자신에게 "시작 시각 기록". 화살표 3: execute에서 call로 "this.call()". 화살표 4: call에서 execute로 점선 반환. 화살표 5: execute 자기 자신에게 "소요 시간 출력". 오른쪽 위에 작은 말풍선 "부모가 자식을 부른다". 깔끔한 평면 스타일, 흰 배경, 파란색과 회색 계열. 뼈대(execute)는 부모에, 구멍(call)은 자식에 있다. 실행 중에는 부모의 코드가 자식의 코드를 호출한다.

    JVM 명세는 invokevirtual의 동작을 두 단계로 나눈다. 먼저 해석(resolution): 기호 참조 TimedTemplate.call:()V를 실제 메서드 선언에 연결한다. 이 결과는 호출 지점마다 한 번 정해진다. 다음은 선택(selection)으로, 호출이 일어날 때마다 수행된다. JVMS §5.4.6은 invokevirtual과 invokeinterface에서 실행할 메서드를 "스택 위 객체의 실행 시점 타입"과 "해석된 메서드"를 기준으로 고른다고 정한다. 규칙은 이렇다. 객체의 실제 클래스 C가 해석된 메서드를 재정의할 수 있는 선언을 갖고 있으면 그것을 고르고, 없으면 C의 직접 상위 클래스, 그 상위 클래스… 순으로 올라가며 찾는다.

    이 규칙을 예제에 대입하면, t1.execute()에서 this는 SendMailTask 객체이므로 C는 SendMailTask다. SendMailTask가 call()을 선언하고 있으므로 선택은 거기서 끝난다. 같은 바이트코드가 t2.execute()에서는 ChargeFeeTask.call()을 고른다. 코드는 하나인데 실행되는 메서드는 수신 객체마다 다르다. 이것이 가상 메서드 호출(virtual method invocation)이고, 템플릿 메서드 패턴은 이 메커니즘 위에 서 있다. 부모의 코드가 자식의 코드를 "알지 못한 채로" 부를 수 있는 이유는 결정을 컴파일 시점이 아니라 실행 시점, 그것도 객체가 가진 클래스 정보로 미루기 때문이다.

    명세는 무엇을 골라야 하는지만 정하고 어떻게 빨리 고를지는 구현에 맡긴다. HotSpot은 매 호출마다 상위 클래스를 거슬러 올라가며 이름을 비교하지 않는다. 클래스를 로드하고 링크하는 과정에서 클래스마다 가상 메서드 테이블(vtable)을 만들어 두는데, 자식 클래스의 테이블은 부모 테이블의 칸 배열을 그대로 물려받고, 재정의한 메서드는 같은 칸 번호의 내용을 자기 메서드로 바꾸고, 새로 추가한 가상 메서드는 뒤에 칸을 덧붙인다. 그러면 call()은 TimedTemplate을 상속한 모든 클래스에서 같은 칸 번호를 갖게 되고, 호출은 "객체 헤더의 클래스 포인터 → 그 클래스의 vtable → 정해진 칸"이라는 몇 번의 메모리 읽기로 끝난다.

    위 그림의 객체 헤더(마크 워드와 클래스 포인터)와 vtable은 HotSpot의 구현이지 JVMS가 정한 구조가 아니다. 명세가 보장하는 것은 §5.4.6의 선택 결과뿐이다. 한편 execute()는 final이므로 어떤 하위 클래스에서도 선택 결과가 바뀌지 않는다. 그래서 실행 엔진은 이 호출을 수신 객체의 타입과 상관없이 하나의 메서드로 고정해도 된다. 또 HotSpot의 JIT 컴파일러는 실행 중에 호출 지점마다 실제로 들어온 수신 타입을 기록하는데, 한 지점에서 한두 가지 타입만 관찰되면 타입 검사를 앞에 두고 그 메서드 본문을 호출 지점에 인라인할 수 있다. 템플릿 메서드의 구멍 호출이 "가상 호출이라 느리다"고 단정할 수 없는 이유다.

    같은 바이트코드 한 줄이 객체의 클래스 포인터와 vtable 칸을 따라가 객체마다 다른 메서드에 도착한다는 것을 보여 준다. 왼쪽에 세로로 긴 상자 "execute() 바이트코드"가 있고 그 안에 한 줄 "invokevirtual call:()V"가 강조되어 있다. 가운데에 힙 영역을 나타내는 둥근 사각형 "힙"이 있고 그 안에 작은 객체 상자 두 개 "SendMailTask 객체", "ChargeFeeTask 객체"가 있다. 각 객체 상자에는 "클래스 포인터" 칸이 있다. 오른쪽에 영역 "메타스페이스"가 있고 그 안에 표 두 개 "SendMailTask vtable", "ChargeFeeTask vtable"이 있다. 각 표의 같은 높이의 칸이 "k번 칸"으로 강조되어 있고, 첫 표의 k번 칸에는 "SendMailTask.call", 두 번째 표의 k번 칸에는 "ChargeFeeTask.call"이 적혀 있다. 화살표: 바이트코드 줄에서 "this"라는 라벨로 각 객체로 점선, 각 객체의 클래스 포인터에서 해당 vtable로 실선, vtable의 k번 칸에서 오른쪽 끝의 메서드 코드 상자로 실선. 아래쪽에 작은 주석 "HotSpot 구현 기준". 평면 스타일, 흰 배경. 바이트코드에는 TimedTemplate.call이라는 기호 참조만 있다. 실제로 실행할 메서드는 호출할 때마다 객체의 클래스에서 고른다.

    익명 내부 클래스: 자식 클래스를 쓰는 자리에서 만든다

    템플릿 메서드 패턴에는 불편한 점이 하나 있다. 구멍을 채우는 방법이 하나 늘 때마다 클래스 파일이 하나 는다. SendMailTask, ChargeFeeTask처럼 한 번만 쓰고 말 클래스를 위해 이름을 짓고 파일을 만드는 것은 번거롭다. 익명 내부 클래스(anonymous inner class)를 쓰면 클래스 선언과 객체 생성을 쓰는 자리에서 한 번에 할 수 있다.

    effectively final 규칙은 복사에서 나온다

    포획이 "복사"라는 사실에서 규칙 하나가 자연스럽게 나온다. 익명 객체를 만든 뒤에 원래 지역 변수를 바꾸면, 지역 변수와 익명 객체의 필드가 서로 다른 값을 갖게 된다. 프로그래머는 같은 변수라고 생각하는데 실제로는 두 벌이 된다. 그래서 자바는 내부 클래스나 람다가 쓰는 바깥 지역 변수가 final이거나, 선언 뒤에 다시 대입되지 않는 사실상 final(effectively final, JLS §4.12.4)이기를 요구한다.

    왜 복사할 수밖에 없는가도 짚어 두자. 지역 변수는 그 메서드의 스택 프레임에 있고, 메서드가 끝나면 프레임과 함께 사라진다. 반면 익명 객체는 힙에 있고, 필드에 저장되거나 다른 스레드에 넘겨져서 만든 메서드보다 오래 살 수 있다. JVM에는 다른 메서드의 프레임 안 지역 변수를 가리키는 참조라는 것이 없다. 따라서 객체가 그 값을 계속 쓰려면 복사해 갖고 있어야 한다. JLS §15.27.2는 람다에 대해 같은 제한을 설명하면서, 계속 바뀌는 지역 변수를 포획하면 동시성 문제를 일으킬 가능성이 높기 때문이라고 이유를 밝힌다. 지역 변수는 원래 한 스레드의 스택에만 있어 안전한데, 포획을 통해 여러 스레드가 공유하는 힙 객체로 새어 나가기 때문이다.

    로그 추적기에 템플릿 메서드 적용하기

    이제 로그 추적기에 적용한다. 변하지 않는 부분은 "begin → 핵심 기능 → 성공이면 end, 실패면 fail 후 재던지기"이고, 변하는 부분은 핵심 기능과 그 반환값이다. 메서드마다 반환 타입이 다르므로 제네릭 타입 매개변수 T로 받는다.

    public abstract class TraceTemplateBase {

    private final Tracer tracer;

    protected TraceTemplateBase(Tracer tracer) {
        this.tracer = tracer;
    }

    public final T execute(String message) {
        Span span = tracer.begin(message);
        try {
            T result = call();            // 변하는 부분: 핵심 기능
            tracer.end(span);
            return result;
        } catch (Exception e) {
            tracer.fail(span, e);
            throw e;
        }
    }

    protected abstract T call();
}

    세 계층에 적용한 코드다. 반환값이 없는 메서드는 타입 인자로 Void를 주고 return null;로 끝낸다. void는 타입이 아니라서 타입 인자로 쓸 수 없고, java.lang.Void는 인스턴스를 만들 수 없는 클래스라서 그 타입의 값으로는 null만 가능하기 때문이다.

    throw e는 왜 throws 절 없이 컴파일되는가

    execute()는 catch (Exception e)로 잡은 e를 다시 던지는데 메서드 선언에 throws Exception이 없다. Exception은 검사 예외(checked exception)의 상위 타입이니 컴파일 오류가 나야 할 것 같지만 그렇지 않다. JLS §11.2.2는 final이거나 effectively final인 catch 매개변수를 다시 던지는 throw 문이 던질 수 있는 예외를 "그 try 블록이 던질 수 있는 예외 중 이 catch가 잡는 것"으로 좁혀서 분석하도록 정한다(자바 7에서 들어온, 흔히 더 정밀한 재던지기라 부르는 규칙). try 블록 안의 tracer.end()와 call()은 검사 예외를 선언하지 않았으므로, 이 블록이 던질 수 있는 것은 비검사 예외뿐이다. 그래서 throw e도 비검사 예외만 던지는 것으로 분석되고, throws 절이 필요 없다.

    거꾸로 구멍 메서드를 protected abstract T call() throws Exception;으로 선언하면 try 블록이 Exception을 던질 수 있게 되므로, 같은 throw e에서 다음 오류가 난다. 구멍의 시그니처에 검사 예외를 넣을지는 템플릿 전체의 시그니처를 바꾸는 설계 결정이다. 뒤에서 스프링의 콜백 인터페이스들이 이 결정을 각자 다르게 내렸다는 것을 보게 된다.

    익명 클래스와 다이아몬드

    컨트롤러 코드의 new TraceTemplateBase<>(tracer) { ... }처럼 익명 클래스에 다이아몬드(<>)를 쓰는 것은 자바 9부터 허용된다. 같은 코드를 --release 8로 컴파일하면 javac가 '<>' with anonymous inner classes is not supported in -source 8이라는 이유와 함께 거부한다. JEP 213의 설명에 따르면, 익명 클래스는 컴파일러가 실제로 클래스 파일을 만들어야 하는데 다이아몬드로 추론된 타입이 클래스 파일의 시그니처 속성으로 표현할 수 없는 타입일 수 있어서 자바 7에서는 금지했고, 자바 9에서 추론된 타입이 소스에 적을 수 있는(denotable) 타입일 때에 한해 허용했다. 일반 생성자 호출의 다이아몬드보다 익명 클래스의 다이아몬드가 늦게 들어온 이유가 여기에 있다.

    결과를 평가해 보자. 로그 형식을 바꾸려면 이제 TraceTemplateBase 한 곳만 고치면 된다. 단일 책임 원칙의 관점에서 추적의 변경 이유는 한 클래스로 모였다. 하지만 각 메서드에는 여전히 익명 클래스 선언, @Override, 메서드 시그니처, return null; 같은 의식(ceremony)이 일곱 줄 정도 남는다. 그리고 그보다 근본적인 문제들이 상속이라는 선택 자체에서 나온다. 그것을 보기 전에 이 패턴의 정의부터 정리하자.

    템플릿 메서드 패턴의 정의, 그리고 이미 써 온 템플릿 메서드들

    템플릿 메서드 패턴은 GoF(Gamma, Helm, Johnson, Vlissides)의 『Design Patterns』(1994)에 실린 행위 패턴 중 하나다. 그 책이 밝힌 의도를 풀어 쓰면 이렇다. 한 연산 안에 알고리즘의 골격을 정의하고, 일부 단계를 하위 클래스로 미룬다. 하위 클래스는 알고리즘의 구조를 바꾸지 않고 특정 단계만 다시 정의할 수 있다. 지금까지 만든 것과 정확히 같다. 골격은 execute(), 미룬 단계는 call()이다.

    같은 책은 하위 클래스가 채우는 단계를 두 종류로 나눈다. 하나는 반드시 구현해야 하는 추상 연산(primitive operation)이고, 다른 하나는 기본 동작을 갖고 있어 필요할 때만 재정의하는 훅 연산(hook operation)이다. 훅은 흔히 아무것도 하지 않는 빈 메서드로 둔다. 예컨대 TraceTemplateBase에 protected void afterSuccess(T result) {} 같은 빈 메서드를 두고 end() 직전에 부르면, 대부분의 자식은 무시하고 일부 자식만 결과를 검사하는 데 쓸 수 있다. 추상 메서드는 "반드시 채워야 하는 구멍", 훅은 "원하면 끼워 넣을 수 있는 자리"다.

    이 패턴에서 제어의 방향을 다시 보자. 보통의 재사용에서는 내 코드가 라이브러리를 부른다. 템플릿 메서드에서는 부모(재사용되는 쪽)의 코드가 자식(재사용하는 쪽)의 코드를 부른다. 흐름의 주도권이 뒤집혀 있는 것이다. 이 역전된 제어 구조에는 "우리에게 전화하지 마세요, 우리가 전화하겠습니다"라는 할리우드 원칙(Hollywood principle)이라는 별명이 붙어 있다. 스프링을 "프레임워크"라고 부를 때의 핵심도 이것이다. 우리가 작성한 컨트롤러 메서드는 우리가 부르지 않는다. 프레임워크의 골격 코드가 적절한 때에 부른다.

    JDK와 서블릿, 스프링 안의 템플릿 메서드

    이 패턴은 이미 여러 번 써 왔다. java.util.AbstractList의 Javadoc은 수정할 수 없는 리스트를 만들려면 이 클래스를 상속해 get(int)와 size()만 구현하면 된다고 설명한다. 반복자, contains, indexOf, subList, toString 같은 나머지 기능은 모두 이 두 구멍 위에 지어진 골격이다. 직접 확인해 보자.

    입출력에도 같은 구조가 있다. java.io.InputStream의 Javadoc은 read(byte[], int, int)의 기본 구현이 한 바이트를 읽는 추상 메서드 read()를 반복해서 부른다고 적고 있다. 하위 클래스는 read()만 구현하면 배열 단위 읽기를 공짜로 얻고, 더 효율적으로 할 수 있으면 배열 단위 메서드도 재정의한다. 서블릿에서는 HttpServlet이 대표적이다. Jakarta Servlet의 HttpServlet Javadoc은 protected service(HttpServletRequest, HttpServletResponse)가 표준 HTTP 요청을 받아 doGet, doPost 같은 doXxx 메서드로 나누어 보낸다고 설명하고, 하위 클래스는 그중 적어도 하나를 재정의해야 하며 service를 재정의할 이유는 거의 없다고 적는다. 골격은 재정의하지 말고 구멍만 채우라는 템플릿 메서드의 사용 설명서 그대로다.

    스프링 MVC의 FrameworkServlet(Spring Framework 6.2 소스 기준)도 같다. doGet, doPost, doPut, doDelete를 final로 재정의해 모두 final 메서드 processRequest()로 모으고, 이 메서드가 요청 처리의 골격을 맡는다. 시작 시각을 기록하고, 로케일과 요청 속성을 스레드에 묶어 두는 홀더(LocaleContextHolder, RequestContextHolder)를 설정한 뒤, 추상 메서드 doService()를 부르고, finally에서 홀더를 이전 상태로 되돌리고 요청 처리 이벤트를 발행한다. doService()라는 구멍을 채우는 자식이 DispatcherServlet이다. 스레드에 묶은 상태를 finally에서 반드시 되돌리는 부분은 01회의 ThreadLocal 정리 규칙이 프레임워크 코드 안에서 템플릿의 "변하지 않는 부분"으로 들어가 있는 예다. 정리 코드를 각 컨트롤러에 맡기지 않고 골격에 두었기 때문에 누구도 빠뜨릴 수 없다.

    상속이 치르는 대가

    템플릿 메서드 패턴은 중복을 한곳에 모았지만, 그 수단이 상속이라는 데서 오는 비용이 있다. 하나씩 따져 보자.

    첫째, 자식은 쓰지도 않는 부모에 강하게 묶인다. LoanRepositoryV1 안의 익명 클래스는 TraceTemplateBase를 extends한다. 이 익명 클래스가 부모로부터 실제로 원하는 것은 "누군가 내 call()을 불러 주는 것"뿐인데, 상속은 부모의 필드(tracer), 생성자 시그니처, 모든 메서드를 통째로 물려받는다. 컴파일된 LoanRepositoryV1$1.class는 상위 클래스로 TraceTemplateBase를 이름으로 기록하고, 부모 생성자를 직접 호출하는 바이트코드를 갖는다. 부모에 추상 메서드가 하나 추가되면 모든 자식이 컴파일 오류가 나고, 부모 생성자의 인자가 바뀌면 모든 익명 클래스 생성 식을 고쳐야 한다. 부모의 내부 구현이 바뀌어 어떤 메서드가 다른 메서드를 부르는 순서가 달라지면, 그 메서드를 재정의한 자식의 동작이 조용히 바뀔 수도 있다. 흔히 깨지기 쉬운 기반 클래스(fragile base class) 문제라고 부르는 현상이다.

    둘째, 부모는 하나뿐이다. 자바 클래스는 하나의 클래스만 상속할 수 있다(JLS §8.1.4). 시간 측정 템플릿과 추적 템플릿을 둘 다 적용하고 싶어도 익명 클래스 하나가 두 부모를 가질 수는 없다. 하나를 다른 하나 안에 다시 감싸야 한다. 또 이미 다른 클래스를 상속하고 있는 클래스는 템플릿의 자식이 될 수 없다.

    셋째, 부모의 생성자에서 템플릿 메서드를 부르면 반쯤 만들어진 자식이 실행된다. JLS §12.5가 정한 객체 생성 순서에서 상위 클래스 생성자는 하위 클래스의 인스턴스 변수 초기화보다 먼저 실행된다. 그런데 그 사이에 호출된 가상 메서드는 이미 자식의 재정의 버전으로 선택된다(앞에서 본 §5.4.6의 선택은 생성 중인 객체에도 똑같이 적용된다). 그래서 부모 생성자가 템플릿 메서드를 부르면, 자식의 구멍 메서드는 자기 필드가 아직 기본값(null, 0)인 상태에서 실행된다. 앞에서 익명 클래스의 생성자가 포획한 값을 부모 생성자 호출 전에 저장하던 것은 이 위험을 javac가 스스로 피하는 장치였다. 직접 작성한 필드는 그런 보호를 받지 못한다(연습 문제 4에서 확인한다).

    넷째, 람다를 쓸 수 없다. 구멍이 메서드 하나뿐이니 람다로 채우고 싶어진다. 하지만 컴파일러는 거부한다.

                          ^

    JLS §9.8은 함수형 인터페이스(functional interface)를 "sealed로 선언되지 않았고 Object의 메서드를 제외하면 추상 메서드가 하나뿐인 인터페이스"로 정의하고, 람다 식의 대상 타입은 함수형 인터페이스여야 한다. 추상 메서드가 하나뿐이어도 추상 클래스는 해당되지 않는다. 이유는 람다의 구현 방식에 있다. 뒤에서 보겠지만 람다 객체는 실행 시점에 만들어지는 클래스의 인스턴스이고, 그 클래스는 Object를 상속하고 대상 인터페이스를 구현한다. 추상 클래스를 대상으로 하려면 그 클래스의 생성자 인자, 필드 초기화, 생성자 안의 부수 효과를 어떻게 처리할지 정해야 하는데, 인터페이스에는 그런 것이 없다.

    다섯째, 익명 클래스마다 클래스가 하나씩 생긴다. 템플릿을 쓰는 자리가 백 군데면 클래스 파일도 백 개가 생기고, 실행 중에 쓰이면 각각 로딩되어 메타스페이스에 클래스 메타데이터가 올라간다. 큰 비용은 아니지만 공짜도 아니다.

    이 다섯 가지는 모두 "구멍을 채우는 코드"와 "뼈대 코드"가 extends라는 한 줄로 같은 객체 안에 합쳐졌기 때문에 생긴다. 해결책은 둘을 서로 다른 객체로 떼어 놓고, 뼈대 객체가 구멍 객체를 인터페이스를 통해서만 부르게 하는 것이다. 상속(inheritance) 대신 위임(delegation), 흔히 하는 말로 "상속보다 합성(composition)"이다.

    전략 패턴: 구멍을 상속 대신 위임으로 채운다

    전략 패턴(Strategy pattern)은 변하지 않는 뼈대를 컨텍스트(Context)라는 객체에 두고, 변하는 부분을 전략(Strategy)이라는 인터페이스로 분리한다. 컨텍스트는 전략 인터페이스에만 의존하고, 실제 전략 객체는 바깥에서 받아 쓴다. GoF가 밝힌 의도를 풀어 쓰면, 알고리즘군을 정의하고 각각을 캡슐화해 서로 바꿔 쓸 수 있게 만들며, 그렇게 해서 알고리즘을 사용하는 클라이언트와 독립적으로 알고리즘을 바꿀 수 있게 한다는 것이다.

    public interface Strategy {
    void call();
}

public class FieldContext {

    private final Strategy strategy;

    public FieldContext(Strategy strategy) {      // 전략을 생성자로 받아 필드에 둔다
        this.strategy = strategy;
    }

    public void execute() {
        long start = System.nanoTime();
        strategy.call();                               // 위임
        long elapsedMs = (System.nanoTime() - start) / 1_000_000;
        System.out.println("소요 시간=" + elapsedMs + "ms");
    }
}

public class SendMailStrategy implements Strategy {
    @Override
    public void call() {
        System.out.println("메일 발송");
    }
}
    FieldContext context1 = new FieldContext(new SendMailStrategy());
context1.execute();

FieldContext context2 = new FieldContext(new Strategy() {
    @Override
    public void call() {
        System.out.println("요금 청구");
    }
});
context2.execute();

    템플릿 메서드와 비교하면 무엇이 달라졌는가. SendMailStrategy는 FieldContext를 전혀 모른다. 아무것도 상속하지 않고 메서드 하나짜리 인터페이스만 구현한다. FieldContext도 SendMailStrategy를 모르고 Strategy 인터페이스만 안다. 둘을 잇는 것은 바깥의 조립 코드다. 컨텍스트의 생성자 인자가 바뀌어도 전략 구현은 영향을 받지 않고, 전략 하나가 다른 클래스를 상속하고 있어도 상관없으며, 한 클래스가 여러 전략 인터페이스를 동시에 구현할 수도 있다.

    이 구조는 스프링 핵심 원리 기본편에서 본 의존관계 주입(dependency injection) 그대로다. 컨텍스트가 빈이고, 전략이 주입되는 의존 객체다. 스프링 컨테이너가 애플리케이션을 띄울 때 빈들을 조립해 두고, 그 뒤 요청이 오면 조립된 객체 그래프가 실행된다. 이 방식을 선 조립, 후 실행이라고 부르자. 조립은 시작할 때 한 번 일어나고, 실행 중에는 전략이 바뀌지 않는다.

    HotSpot에서 인터페이스 호출은 앞에서 본 vtable만으로는 처리할 수 없다. 클래스 상속은 한 줄로 이어지므로 같은 메서드가 모든 하위 클래스에서 같은 vtable 칸을 가질 수 있지만, 인터페이스는 서로 관계없는 여러 클래스가 각자의 상속 계층 안에서 구현하므로 모든 구현 클래스에 공통인 칸 번호를 정할 수 없다. 그래서 HotSpot은 클래스마다 구현한 인터페이스별 메서드 표(itable)를 따로 두고, 호출 시 해당 인터페이스의 표를 찾은 뒤 그 안의 칸을 쓴다. 다만 앞에서 말한 JIT의 수신 타입 기록과 인라인은 인터페이스 호출에도 적용되므로, 한 호출 지점에 들어오는 구현이 한두 가지라면 실제 비용 차이는 크지 않다.

    람다로 전략 넘기기, 그리고 람다의 정체

    Strategy는 추상 메서드가 하나뿐인 인터페이스, 즉 함수형 인터페이스다. 그러니 익명 클래스 대신 람다를 쓸 수 있다. 템플릿 메서드에서는 막혔던 길이 위임으로 바꾸자 열린 것이다.

    this는 누구인가

    익명 클래스와 람다의 차이가 가장 직접적으로 드러나는 곳은 this다. 익명 클래스는 진짜 클래스의 본문이므로 그 안의 this는 익명 객체 자신이다. 반면 람다 본문은 새 클래스의 본문이 아니라 바깥 메서드 본문의 일부로 취급된다. JLS §15.8.3은 람다 본문의 this가 둘러싼 문맥의 this와 같은 값이라고 정한다.

    전략을 필드에 둘 것인가, 실행할 때 넘길 것인가

    FieldContext는 전략을 생성자로 받아 필드에 둔다. 조립이 끝나면 전략은 바뀌지 않는다. 다른 전략으로 실행하려면 컨텍스트를 새로 만들어야 한다. 이번에는 전략을 필드가 아니라 execute()의 인자로 받아 보자.

    public class ParamContext {

    public void execute(Strategy strategy) {           // 실행할 때 전략을 받는다
        long start = System.nanoTime();
        strategy.call();
        long elapsedMs = (System.nanoTime() - start) / 1_000_000;
        System.out.println("소요 시간=" + elapsedMs + "ms");
    }
}
    ParamContext context = new ParamContext();
context.execute(() -> System.out.println("메일 발송"));
context.execute(() -> System.out.println("요금 청구"));

    컨텍스트 하나로 매번 다른 전략을 실행한다. ParamContext에는 필드가 하나도 없다. 이것이 사소해 보이지만 멀티스레드 환경에서는 결정적인 차이다. 스프링 빈은 기본이 싱글톤 스코프이므로, 컨텍스트를 빈으로 등록하면 그 객체 하나를 요청을 처리하는 모든 스레드(톰캣이라면 요청 처리 스레드 풀의 스레드들)가 동시에 쓴다.

    전략을 바꾸기 위해 필드 방식에 세터를 달았다고 해 보자.

    // 싱글톤으로 공유되는 객체에 이렇게 하면 안 된다
public class MutableContext {

    private Strategy strategy;

    public void setStrategy(Strategy strategy) {
        this.strategy = strategy;
    }

    public void execute() {
        long start = System.nanoTime();
        strategy.call();
        long elapsedMs = (System.nanoTime() - start) / 1_000_000;
        System.out.println("소요 시간=" + elapsedMs + "ms");
    }
}

    스레드 A가 setStrategy(a)를 부르고, execute()를 부르기 직전에 스레드 B가 setStrategy(b)를 부르면, A는 B의 전략을 실행한다. strategy 필드는 힙에 있는 하나의 객체 안에 있고, 모든 스레드가 같은 칸을 읽고 쓰기 때문이다. 01회에서 추적 깊이를 공유 필드에 두었을 때 생긴 문제와 같은 구조이고, 동기화 없이 공유 필드를 읽고 쓰면 실행 순서 문제에 더해 한 스레드의 쓰기가 다른 스레드에 언제 보이는지(가시성)도 보장되지 않는다. 이 가시성 문제는 로드맵 뒤쪽의 자바 고급 1편에서 자바 메모리 모델로 자세히 다룬다.

    파라미터 방식에서는 전략 참조가 어디에 있는가? execute(Strategy strategy)의 strategy는 매개변수, 즉 지역 변수다. 호출한 스레드의 스택에 새로 만들어진 execute() 프레임의 지역 변수 칸에 들어간다. 스레드마다 스택이 따로이므로 A의 프레임과 B의 프레임은 같은 컨텍스트 객체의 같은 메서드를 실행하면서도 서로의 전략을 볼 수 없다. 공유되는 것은 필드가 없는 컨텍스트 객체와 메서드 코드뿐이다. 변하는 것을 객체의 상태(필드)가 아니라 실행의 흐름(스택)에 실어 보내면, 공유 객체는 무상태가 되고 스레드 안전해진다.

      스레드 A의 스택                 힙                            스레드 B의 스택
  ┌──────────────────────┐                                      ┌──────────────────────┐
  │ execute() 프레임      │      ┌─────────────────────┐         │ execute() 프레임      │
  │  this ───────────────┼────▶ │ ParamContext 객체    │ ◀───────┼─ this                │
  │  strategy ──┐        │      │ (필드 없음)          │         │  strategy ──┐        │
  │  start = ...│        │      └─────────────────────┘         │  start = ...│        │
  └─────────────┼────────┘                                      └─────────────┼────────┘
                ▼                                                             ▼
        람다 객체 a ("메일 발송")                                    람다 객체 b ("요금 청구")

  공유되는 것: 상태 없는 ParamContext 객체 하나       스레드마다 따로인 것: 프레임, strategy, start

    물론 무상태 컨텍스트가 모든 것을 해결하지는 않는다. 람다가 포획한 객체 자체가 여러 스레드에서 공유되는 가변 객체라면 그 객체의 동시성 문제는 그대로 남는다. 파라미터 방식이 보장하는 것은 "컨텍스트가 어느 전략을 실행할지 헷갈리지 않는다"까지다.

    전략이 정해지는 때컨텍스트를 조립할 때(선 조립, 후 실행)execute()를 호출할 때마다
    전략 참조의 위치힙의 컨텍스트 객체 필드호출 스레드의 스택 프레임
    다른 전략으로 실행하려면컨텍스트를 새로 만든다인자만 바꾼다
    호출하는 쪽의 부담실행할 때 전략을 신경 쓰지 않는다호출할 때마다 전략을 넘겨야 한다
    잘 맞는 경우애플리케이션 시작 시 정해져 바뀌지 않는 정책(예: 할인 정책, 저장소 구현)호출마다 달라지는 코드 조각(예: 각 메서드의 핵심 기능)

    로그 추적기에 필요한 것은 어느 쪽인가. 변하는 부분은 "각 메서드의 핵심 기능"이고 메서드마다 다르다. 필드 방식이라면 메서드마다 컨텍스트 객체를 따로 만들어야 한다. 파라미터 방식이라면 추적 컨텍스트 하나를 빈으로 두고 모든 메서드가 공유하면서, 각자 자기 핵심 기능을 넘기면 된다. 답은 파라미터 방식이다.

    필드 방식에서는 두 스레드가 힙의 같은 필드 칸을 덮어쓰고, 파라미터 방식에서는 각 스레드의 스택 프레임에 전략 참조가 따로 있다는 대비를 보여 준다. 좌우로 나뉜 비교 그림. 왼쪽 제목 "필드에 둔 전략", 오른쪽 제목 "파라미터로 넘긴 전략". 왼쪽: 위쪽에 스레드 두 개를 세로 막대 "스레드 A 스택", "스레드 B 스택"으로 그리고, 가운데 아래 힙 영역에 객체 상자 "MutableContext"가 있으며 그 안에 칸 하나 "strategy 필드"가 빨간 테두리로 강조되어 있다. 두 스레드에서 같은 칸으로 화살표가 들어가고 라벨은 각각 "setStrategy(a)", "setStrategy(b)". 칸 옆에 경고 표시와 라벨 "덮어쓰기 경쟁". 오른쪽: 같은 두 스레드 스택 막대 안에 각각 프레임 상자 "execute() 프레임"이 있고 그 안에 칸 "strategy"가 있다. 각 칸에서 서로 다른 객체 "람다 a", "람다 b"로 화살표. 힙 가운데의 객체 상자 "ParamContext (필드 없음)"로 두 프레임의 "this" 화살표가 모인다. 오른쪽 아래 초록 체크 표시와 라벨 "무상태 공유". 평면 스타일, 흰 배경. 변하는 부분을 공유 객체의 필드에 두면 스레드끼리 경쟁하고, 실행 흐름(스택)에 실어 보내면 공유 객체는 무상태가 된다.

    템플릿 콜백 패턴

    콜백(callback)은 다른 코드에 인자로 넘겨져, 그 코드가 적절한 때에 실행해 주기를 기대하는 실행 가능한 코드 조각을 말한다. 내가 직접 부르는 것이 아니라, 받은 쪽이 나중에 "다시 불러 주기(call back)" 때문에 붙은 이름이다. 콜백을 받은 메서드가 반환하기 전에 콜백을 실행하면 동기 콜백, 메서드는 먼저 반환하고 나중에(다른 스레드에서일 수도 있다) 실행하면 비동기 콜백이라고 한다. CompletableFuture.thenApply에 넘기는 함수는 비동기 콜백의 예이고, 이 회차에서 다루는 것은 모두 동기 콜백이다. 템플릿의 execute()가 반환하기 전에 콜백이 실행되고 끝난다.

    앞 절의 ParamContext가 바로 이 구조다. 컨텍스트가 변하지 않는 뼈대(템플릿)를 갖고, 변하는 부분을 실행할 때 인자(콜백)로 받는다. 스프링 안에서는 이런 방식을 템플릿 콜백 패턴이라고 부르고, JdbcTemplate, TransactionTemplate, RestTemplate처럼 이름이 XxxTemplate인 클래스들이 이 구조로 만들어져 있다. GoF 책의 23개 패턴 목록에 있는 이름은 아니다. GoF의 용어로는 "전략을 실행 시점에 파라미터로 넘기는 전략 패턴"이고, 컨텍스트를 템플릿, 전략을 콜백이라고 바꿔 부른 것이다.

      전략 패턴의 이름          템플릿 콜백 패턴의 이름          로그 추적기에서
  ─────────────────         ───────────────────────          ─────────────────────
  Context                   Template                         TraceTemplate
  Strategy (인자로 전달)    Callback                         TraceCallback
  execute(strategy)         execute(callback)                execute(message, callback)

    이름을 템플릿 "메서드"와 혼동하지 말자. 템플릿 메서드 패턴은 상속으로, 템플릿 콜백 패턴은 위임으로 구멍을 채운다. 둘에 "템플릿"이라는 말이 공통으로 들어간 것은 둘 다 "변하지 않는 뼈대"를 가리키기 때문이다.

    로그 추적기에 템플릿 콜백 적용하기

    콜백 인터페이스와 템플릿을 만든다. 콜백은 핵심 기능의 반환값을 돌려줘야 하므로 제네릭 인터페이스로 만들고, 템플릿의 execute는 제네릭 메서드로 만든다.

    @FunctionalInterface
public interface TraceCallback {
    T call();
}

public class TraceTemplate {

    private final Tracer tracer;

    public TraceTemplate(Tracer tracer) {
        this.tracer = tracer;
    }

    public  T execute(String message, TraceCallback callback) {
        Span span = tracer.begin(message);
        try {
            T result = callback.call();   // 콜백: 넘겨받은 코드를 여기서 실행한다
            tracer.end(span);
            return result;
        } catch (Exception e) {
            tracer.fail(span, e);
            throw e;
        }
    }
}

    @FunctionalInterface는 없어도 람다를 쓸 수 있다. 이 애노테이션은 "이 인터페이스는 함수형 인터페이스로 쓰려는 것"이라는 의도를 밝히고, 누가 실수로 추상 메서드를 하나 더 추가하면 컴파일 오류가 나게 한다. 콜백 인터페이스처럼 람다로 쓰일 것이 확실한 인터페이스에 붙여 두면, 인터페이스를 고치는 사람이 람다를 쓰는 수많은 호출 지점을 한꺼번에 깨뜨리는 일을 막을 수 있다.

    TraceTemplate의 필드는 생성자에서 정해지는 tracer 하나뿐이고, 실행 중에는 바뀌지 않는다. 앞 절에서 본 무상태 컨텍스트다. 그래서 스프링에서는 TraceTemplate을 빈 하나로 등록해 모든 계층이 주입받아 공유하면 된다. 깊이와 트랜잭션 번호 같은 실행별 상태는 Tracer 구현 안의 ThreadLocal(스레드마다 따로)과 execute()의 지역 변수 span(호출마다 따로)에 있다.

    타입 추론과 Void

    execute의 타입 매개변수 T는 호출할 때 명시하지 않았다. 컴파일러가 람다의 반환문에서 추론한다. 컨트롤러의 람다는 "ok"를 반환하므로 T는 String이 되고, execute의 반환 타입도 String이 되어 return template.execute(...)가 그대로 컴파일된다. 서비스의 람다는 반환문이 return null;뿐이고 호출하는 쪽도 결과를 쓰지 않으므로 T는 Object로 추론된다. 반환값이 없는 콜백을 위해 Runnable을 받는 오버로드를 따로 둘 수도 있지만, 그러면 같은 이름의 메서드에 람다를 넘길 때 어느 오버로드인지 판단하는 규칙이 끼어든다. 한 가지 콜백 타입에 return null;을 쓰는 쪽이 단순하다.

    스프링의 콜백 인터페이스들도 이 결정을 각자 다르게 내렸다. TransactionCallback의 doInTransaction(TransactionStatus)은 검사 예외를 선언하지 않고 @FunctionalInterface가 붙어 있다. 반면 JdbcTemplate이 받는 ConnectionCallback의 doInConnection(Connection)은 throws SQLException, DataAccessException을 선언한다. JDBC 코드는 거의 모든 메서드가 SQLException을 던지므로 콜백 안에서 그것을 그대로 던지게 해 주고, 템플릿이 받아서 스프링의 DataAccessException 계층으로 변환해 준다. 콜백 시그니처의 throws 절은 "예외 처리라는 변하지 않는 부분을 누가 맡는가"를 정하는 자리다.

    스프링 안의 템플릿 콜백: TransactionTemplate과 JdbcTemplate

    스프링 DB 1편과 2편에서 쓴 두 템플릿을 이 회차의 눈으로 다시 보자. 아래는 Spring Framework 6.2의 TransactionTemplate.execute()에서 구조만 간추린 것이다(트랜잭션 매니저가 콜백 실행을 직접 맡겠다고 하는 특수한 경우의 분기는 뺐다).

    // TransactionTemplate.execute()의 구조 (Spring Framework 6.2 소스에서 간추림)
public  T execute(TransactionCallback action) throws TransactionException {
    TransactionStatus status = this.transactionManager.getTransaction(this);   // 앞부분: 트랜잭션 시작
    T result;
    try {
        result = action.doInTransaction(status);                               // 콜백
    }
    catch (RuntimeException | Error ex) {
        rollbackOnException(status, ex);                                        // 예외 경로: 롤백 후 재던지기
        throw ex;
    }
    catch (Throwable ex) {
        rollbackOnException(status, ex);
        throw new UndeclaredThrowableException(ex, "TransactionCallback threw undeclared checked exception");
    }
    this.transactionManager.commit(status);                                     // 뒷부분: 커밋
    return result;
}

    우리의 TraceTemplate과 모양이 같다. begin 대신 getTransaction, end 대신 commit, fail 대신 rollbackOnException이 들어갔을 뿐이다. RuntimeException과 Error는 롤백한 뒤 그대로 다시 던진다. doInTransaction은 검사 예외를 선언하지 않았는데도 Throwable을 한 번 더 잡는 것은, 선언되지 않은 검사 예외가 콜백에서 새어 나오는 경우(예외 메시지가 그 상황을 가리킨다)까지 롤백하고, 호출자에게는 비검사 예외인 UndeclaredThrowableException으로 감싸 전달하기 위해서다. 자바 컴파일러의 검사 예외 규칙은 javac가 강제하는 것이지 JVM이 강제하는 것이 아니어서, 다른 JVM 언어로 작성된 콜백 등은 선언 없이 검사 예외를 던질 수 있다.

    // transactionTemplate, loanRepository, stockRepository, bookId, memberId는 주변에 준비되어 있다고 가정한다
Long loanId = transactionTemplate.execute(status -> {
    Long id = loanRepository.insert(bookId, memberId);   // 핵심 기능
    stockRepository.decrease(bookId);
    return id;
});

    사용하는 쪽은 트랜잭션의 시작·커밋·롤백 코드를 한 줄도 쓰지 않는다. 그리고 이 람다는 execute()가 반환하기 전에, 같은 스레드에서 실행된다. 이 점이 중요하다. 스프링의 트랜잭션 동기화는 현재 트랜잭션의 커넥션을 스레드에 묶어 두는데(DataSourceUtils의 Javadoc은 현재 스레드에 묶인 커넥션을 인식한다고 설명한다), 동기 콜백이므로 콜백 안의 리포지토리 코드가 같은 스레드에서 그 커넥션을 찾아 쓸 수 있다. 콜백 안에서 다른 스레드로 작업을 넘기면 그 작업은 이 트랜잭션의 커넥션을 보지 못한다.

    JdbcTemplate은 콜백이 여러 겹으로 겹친 예다. query(String sql, RowMapper rowMapper)를 부르면 내부에서 다음 순서로 감싸진다(Spring Framework 6.2 소스 기준).

    여기서 RowMapper는 우리가 넘기는 가장 안쪽 콜백이고, RowMapperResultSetExtractor와 QueryStatementCallback은 스프링이 자기 내부에서 만들어 넘기는 콜백이다. 바깥 템플릿이 커넥션과 문장을, 가운데 콜백이 결과 집합을, 가장 안쪽 콜백이 한 행을 맡는다. 자원의 수명이 짧은 것일수록 안쪽에 있다. 우리가 작성하는 mapRow는 몇 번 불릴지, 언제 불릴지 스스로 정하지 않는다. 행이 열 개면 템플릿이 열 번 부른다. 할리우드 원칙이 데이터 접근 계층에서 구현된 모습이고, JDBC 연결을 직접 다루던 시절의 try/catch/finally 반복을 이 구조가 한곳으로 모았다. 스프링 자신도 콜백을 지역 클래스로 만들어 넘긴다는 점(QueryStatementCallback)도 눈여겨보자. 이 콜백은 StatementCallback과 함께 SqlProvider도 구현해 SQL 문자열을 돌려주는 두 번째 메서드(getSql())까지 가지므로 람다로는 만들 수 없고 클래스여야 한다. 함수형 인터페이스는 메서드가 하나일 때만 람다로 쓸 수 있다.

    그래도 해결되지 않은 것이 있다. 지금의 코드는 여전히 모든 대상 메서드를 고쳐야 한다. 컨트롤러·서비스·리포지토리의 메서드마다 핵심 기능을 template.execute(...)로 감싸는 코드를 넣어야 하고, 추적 대상 클래스가 백 개면 백 개를 수정해야 한다. 부가 기능의 "내용"은 한곳에 모았지만, 부가 기능을 "적용하는 코드"는 여전히 흩어져 있다. 원본 코드를 한 줄도 건드리지 않고 부가 기능을 붙이려면 호출하는 쪽과 호출되는 쪽 사이에 다른 객체를 끼워 넣어야 한다. 다음 03회의 프록시 패턴과 데코레이터 패턴이 그 출발점이고, 04회부터는 그 프록시를 클래스마다 손으로 만들지 않는 방법(동적 프록시, 스프링의 프록시 팩토리, 빈 후처리기, 스프링 AOP)으로 이어진다.
    변하는 것과 변하지 않는 것의 분리
    부가 기능 코드는 핵심 기능의 앞뒤와 예외 경로를 감싸므로 메서드 추출만으로는 모을 수 없다. 뼈대를 한곳에 두고 가운데에 들어갈 코드를 객체로 넘기는 것이 세 패턴의 공통 해법이다.
    템플릿 메서드 패턴
    부모 클래스의 final 메서드가 알고리즘의 골격을 갖고, 변하는 단계를 추상 메서드로 남겨 자식이 재정의한다. 부모의 코드가 자식의 코드를 부르는 역전된 제어 구조다.
    invokevirtual과 메서드 선택
    바이트코드에는 TimedTemplate.call 같은 기호 참조만 있고, 실행할 메서드는 호출 때마다 수신 객체의 실제 클래스에서 고른다(JVMS §5.4.6). HotSpot은 이를 vtable 칸 번호로 빠르게 처리한다.
    상속의 대가
    자식이 부모의 필드·생성자·메서드에 통째로 묶이고, 부모는 하나뿐이며, 생성자에서의 가상 호출 함정이 있고, 대상이 클래스라 람다를 쓸 수 없다.
    전략 패턴
    뼈대를 가진 컨텍스트가 전략 인터페이스에만 의존하고 실제 전략은 바깥에서 받는다. 필드로 받으면 선 조립 후 실행, 파라미터로 받으면 호출마다 다른 전략을 쓸 수 있다.
    변수 포획과 effectively final
    익명 클래스와 람다는 바깥 지역 변수의 값을 자기 필드에 복사해 간다. 복사본과 원본이 갈라지지 않도록 포획 대상은 final이거나 사실상 final이어야 한다.
    람다의 구현
    본문은 바깥 클래스의 private 메서드가 되고, 람다 식 자리는 invokedynamic이 된다. 처음 실행될 때 LambdaMetafactory가 인터페이스를 구현하는 숨은 클래스를 만들고, 평가 결과 객체의 정체성은 명세상 예측할 수 없다.
    템플릿 콜백 패턴
    전략을 실행 시점에 인자로 넘기는 전략 패턴을 스프링에서 부르는 이름이다. 템플릿이 무상태가 되어 싱글톤으로 공유할 수 있고, JdbcTemplate과 TransactionTemplate이 이 구조다.

    실무에서 "공통 처리"를 만들 일이 생기면 먼저 그 공통 처리가 핵심 코드의 어디에 붙는지 본다. 앞이나 뒤에만 붙는다면 메서드 추출이나 필터·인터셉터 같은 기존 확장 지점으로 충분하다. 핵심 코드를 감싸야 한다면(시작과 종료, 예외 시 롤백, 자원 획득과 반납) 템플릿 콜백이 가장 먼저 검토할 형태다. 이때 템플릿을 무상태로 만들어 싱글톤 빈으로 공유할 수 있는지, 실행별 상태는 지역 변수나 콜백 인자로 흘러가는지 확인하는 것이 핵심 점검 항목이다. 템플릿에 실행별 상태를 필드로 두는 순간 동시 요청에서 01회의 문제가 그대로 돌아온다.

    콜백 인터페이스를 설계할 때는 시그니처가 곧 계약이다. 검사 예외를 허용할지(ConnectionCallback처럼), 막을지(TransactionCallback처럼)에 따라 호출하는 쪽의 코드 모양이 달라진다. 반환값이 필요한지, 콜백이 같은 스레드에서 동기로 실행된다고 보장할 수 있는지도 정해야 한다. 트랜잭션처럼 스레드에 묶인 자원을 쓰는 템플릿에서 콜백 안의 작업을 다른 스레드로 넘기면, 콜백 코드는 템플릿이 준비한 자원을 보지 못한다. "콜백은 템플릿이 반환하기 전에 같은 스레드에서 끝난다"는 가정이 깨지는 코드를 리뷰에서 찾아내야 하는 이유다.

    템플릿 메서드 패턴이 나쁜 것은 아니다. 프레임워크가 확장 지점을 제공할 때, 특히 구멍이 여러 개이고 그 사이의 호출 순서와 기본 동작(훅)을 프레임워크가 엄격히 통제해야 할 때는 여전히 유효하다. HttpServlet, AbstractList, FrameworkServlet이 그런 예다. 판단 기준은 "구멍을 채우는 쪽이 부모의 다른 것을 얼마나 필요로 하는가"다. 구멍이 하나이고 부모의 다른 기능이 필요 없다면 위임과 람다가 낫다. 그리고 어느 쪽이든 대상 코드마다 적용 코드를 넣어야 한다는 한계는 남으므로, 적용 대상이 많아지면 03회 이후의 프록시와 AOP로 넘어갈 시점이다.

    템플릿 메서드 패턴(Template Method pattern)
    상위 클래스의 메서드에 알고리즘의 골격을 두고, 변하는 단계를 하위 클래스가 재정의하도록 추상 메서드나 훅 메서드로 남기는 패턴.
    훅 메서드(hook method)
    기본 동작(흔히 빈 구현)을 가진 채로 골격에서 호출되어, 하위 클래스가 원할 때만 재정의하는 메서드.
    전략 패턴(Strategy pattern)
    변하는 알고리즘을 인터페이스 뒤의 객체로 분리하고, 그것을 사용하는 컨텍스트가 인터페이스에만 의존하게 해 알고리즘을 바꿔 끼울 수 있게 하는 패턴.
    콜백(callback)
    다른 코드에 인자로 넘겨져 그 코드가 적절한 때에 실행해 주는 코드 조각. 받은 메서드가 반환하기 전에 실행되면 동기 콜백이다.
    가상 메서드 호출(virtual method invocation)
    실행할 메서드를 컴파일 시점이 아니라 실행 시점에 수신 객체의 실제 클래스로 고르는 호출. 바이트코드의 invokevirtual과 invokeinterface가 해당한다.
    변수 포획(variable capture)
    익명 클래스나 람다가 바깥 지역 변수의 값, 또는 바깥 객체 참조를 자기 필드로 복사해 가는 것.
    사실상 final(effectively final)
    final로 선언하지 않았어도 초기화 후 다시 대입되지 않는 변수. 내부 클래스와 람다는 이런 변수만 포획할 수 있다(JLS §4.12.4).
    invokedynamic
    처음 실행될 때 부트스트랩 메서드를 호출해 실제 동작을 연결하는 바이트코드 명령. 람다 객체 생성과 문자열 연결에 쓰인다.
    숨은 클래스(hidden class)
    프레임워크가 실행 중에 정의하는 클래스로, 이름으로 발견되지 않아 Class.forName으로 찾을 수 없다. JDK 15(JEP 371)에서 도입되었고 람다 클래스가 이것으로 만들어진다.
    함수형 인터페이스(functional interface)
    Object의 메서드를 제외하고 추상 메서드가 하나뿐인, sealed가 아닌 인터페이스. 람다 식과 메서드 참조의 대상 타입이 된다(JLS §9.8).
