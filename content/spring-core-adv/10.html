    도구는 모두 모였다 — 이제 진짜 요구사항에 붙여 본다

    이 권은 로그 추적기라는 작은 요구사항 하나에서 출발했다. 01회에서 동시성 문제를 ThreadLocal로 풀었고, 02회에서 반복되는 앞뒤 코드를 템플릿 메서드와 템플릿 콜백으로 떼어 냈고, 03~05회에서 원본을 고치지 않고 기능을 덧붙이는 프록시를 손으로, 다시 JDK 동적 프록시와 CGLIB로, 마지막에는 ProxyFactory와 어드바이저로 만들었다. 06회의 빈 후처리기는 프록시를 빈 등록 과정에 자동으로 끼워 넣었고, 07~09회에서는 @Aspect 한 장으로 어드바이저를 선언하고 AspectJ 포인트컷 표현식으로 적용 대상을 고르는 법을 봤다.

    이 회차는 두 부분으로 나뉜다. 앞부분은 지금까지의 도구로 실무에서 흔히 필요한 애스펙트 두 개를 끝까지 만들어 본다. 하나는 특정 메서드의 호출을 기록하는 로그 애스펙트, 다른 하나는 일시적인 장애가 나면 같은 호출을 몇 번 더 시도하는 재시도 애스펙트다. 둘 다 사용자 정의 애너테이션을 표식으로 쓰고, 둘을 함께 걸었을 때 순서가 결과를 어떻게 바꾸는지까지 본다.

    뒷부분은 스프링 AOP가 프록시 기반이라는 사실이 남기는 그림자를 다룬다. 같은 클래스 안에서 부른 메서드에는 어드바이스가 걸리지 않는 내부 호출 문제, JDK 동적 프록시를 구체 클래스 타입으로 캐스팅하거나 주입할 때 생기는 실패, CGLIB가 생성자와 final 때문에 겪던 제약과 스프링이 그것을 푼 방법이다. 모두 "어드바이스는 프록시를 거친 호출에만 적용된다"는 한 문장에서 나오는 결과이므로, 증상을 외우기보다 그 한 문장에서 각 증상을 끌어내는 연습을 하자.

    이 회차의 실행 결과는 원고를 쓰면서 JDK 21.0.13(Temurin), Spring Framework 6.2.19(spring-context, spring-aop), AspectJ weaver 1.9.25.1로 직접 돌려 얻었다. 스프링 부트 없이 AnnotationConfigApplicationContext로 컨테이너를 띄웠고, 부트의 기본값은 spring-boot-autoconfigure 3.5.16의 바이트코드와 부트 공식 문서로 따로 확인했다. 프록시 클래스 이름의 번호($$SpringCGLIB$$0, $Proxy19 등)는 실행 환경과 순서에 따라 달라진다.

    예제 만들기 — 가끔 실패하는 외부 호출

    예제의 무대는 택배사의 배송 조회 API를 부르는 서비스다. 외부 시스템을 네트워크 너머로 부르는 코드에는 두 가지 요구가 자주 붙는다. 첫째, 어떤 메서드가 어떤 인자로 불렸는지 기록하고 싶다. 장애가 났을 때 가장 먼저 보는 것이 이 기록이다. 둘째, 상대 서버가 잠깐 과부하였거나 연결이 순간 끊겨서 실패한 호출은 조금 뒤 다시 부르면 성공하는 경우가 많다. 이런 일시적 장애(transient failure)에는 재시도가 효과적이다.

    두 요구 모두 비즈니스 로직이 아니라 부가 기능이다. 배송 조회 코드 안에 로그 문장과 재시도 반복문을 직접 넣으면 01~02회에서 본 문제가 그대로 돌아온다. 그래서 이번에는 애너테이션을 표식으로 쓴다. 메서드에 @Trace를 붙이면 로그를 남기고, @Retry를 붙이면 재시도한다. 애너테이션 자체는 아무 일도 하지 않는다. 일은 애스펙트가 하고, 애너테이션은 "여기에 적용하라"는 표시일 뿐이다.

    package example.aop;

import java.lang.annotation.ElementType;
import java.lang.annotation.Retention;
import java.lang.annotation.RetentionPolicy;
import java.lang.annotation.Target;

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Trace {
}
    package example.aop;

// import 문은 Trace와 같다

@Target(ElementType.METHOD)
@Retention(RetentionPolicy.RUNTIME)
public @interface Retry {
    int value() default 3;   // 최대 시도 횟수(첫 시도 포함)
}

    @Target(ElementType.METHOD)는 이 애너테이션을 메서드에만 붙일 수 있게 컴파일러에게 알린다. @Retention(RetentionPolicy.RUNTIME)은 애너테이션을 클래스 파일에 기록하는 데서 그치지 않고 실행 중에도 JVM이 보관하게 한다. RetentionPolicy Javadoc의 표현대로 RUNTIME 애너테이션만 "리플렉션으로 읽을 수 있다". 재시도 애스펙트는 실행 중에 @Retry 객체를 받아 value()를 읽어야 하므로 RUNTIME이어야 한다. 기본값인 CLASS로 두면 Method.getAnnotation(Retry.class)는 null을 돌려준다.

    이제 외부 API 클라이언트를 흉내 내는 클래스다. 실제 네트워크 대신 호출 횟수를 세어 처음 두 번은 실패하고 세 번째부터 성공하게 했다. 실행 결과를 결정적으로 만들기 위해서다.

    package example.aop;

public class ShippingClient {

    private int calls = 0;   // 실험용: 몇 번째 호출인지 센다(스레드 안전하지 않다)

    @Trace
    @Retry(4)
    public String track(String trackingNo) {
        calls++;
        if (calls <= 2) {
            throw new IllegalStateException("일시 장애 #" + calls);
        }
        return trackingNo + ":배송중";
    }
}
    package example.aop;

public class ShippingService {

    private final ShippingClient client;

    public ShippingService(ShippingClient client) {
        this.client = client;
    }

    @Trace
    public String status(String trackingNo) {
        return client.track(trackingNo);
    }
}

    calls 필드에 붙인 주석을 지나치지 말자. 스프링 빈은 기본이 싱글톤이고, 싱글톤 하나를 여러 요청 스레드가 동시에 쓴다. calls++는 읽기·더하기·쓰기 세 동작이라 두 스레드가 겹치면 갱신이 사라진다. 01회에서 로그 추적기의 필드 하나가 동시 요청에서 엉킨 것과 같은 구조다. 여기서는 실험을 단일 스레드로만 돌리므로 문제가 드러나지 않을 뿐이다.

    설정은 07회와 같다. @EnableAspectJAutoProxy가 AnnotationAwareAspectJAutoProxyCreator라는 빈 후처리기를 등록하고, 이 후처리기가 @Aspect 빈을 찾아 어드바이저로 바꾼 다음, 다른 빈을 등록할 때 포인트컷에 걸리는 빈을 프록시로 바꿔 끼운다.

    package example.aop;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableAspectJAutoProxy;

@Configuration
@EnableAspectJAutoProxy
public class ShippingConfig {

    @Bean ShippingClient shippingClient() { return new ShippingClient(); }
    @Bean ShippingService shippingService(ShippingClient client) { return new ShippingService(client); }
    @Bean TraceAspect traceAspect() { return new TraceAspect(); }
    @Bean RetryAspect retryAspect() { return new RetryAspect(); }
}
    package example.aop;

import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class ShippingMain {
    public static void main(String[] args) {
        var context = new AnnotationConfigApplicationContext(ShippingConfig.class);
        ShippingService service = context.getBean(ShippingService.class);
        System.out.println("result = " + service.status("A-100"));
        System.out.println("class  = " + service.getClass().getName());
        context.close();
    }
}

    로그 출력 AOP — @Trace

    첫 번째 애스펙트는 @Trace가 붙은 메서드가 실행되기 직전에 시그니처와 인자를 출력한다.

    package example.aop;

import java.util.Arrays;
import org.aspectj.lang.JoinPoint;
import org.aspectj.lang.annotation.Aspect;
import org.aspectj.lang.annotation.Before;
import org.springframework.core.annotation.Order;

@Aspect
@Order(2)
public class TraceAspect {

    @Before("@annotation(example.aop.Trace)")
    public void trace(JoinPoint joinPoint) {
        System.out.println("[trace] " + joinPoint.getSignature().toShortString()
                + " args=" + Arrays.toString(joinPoint.getArgs()));
    }
}

    @annotation(example.aop.Trace)는 09회에서 본 포인트컷 지시자 가운데 하나로, "실행되는 메서드에 이 애너테이션이 붙어 있는 조인 포인트"를 고른다. execution(* example..*Client.*(..))처럼 이름 규칙으로 고르는 방식과 달리, 적용 여부를 코드를 쓰는 사람이 메서드마다 명시적으로 정한다. 이름 규칙은 새로 만든 클래스에도 자동으로 적용된다는 장점이 있지만 의도하지 않은 메서드까지 걸릴 수 있고, 애너테이션 방식은 빠뜨릴 위험이 있는 대신 적용 범위가 코드에 그대로 보인다. 로그나 재시도처럼 "이 메서드에만" 붙이고 싶은 부가 기능에는 애너테이션 방식이 자연스럽다.

    @Before 어드바이스는 대상 메서드보다 먼저 실행되고, 끝나면 호출은 자동으로 다음 단계로 넘어간다. 어드바이스가 예외를 던지지 않는 한 대상 메서드 호출을 막을 수 없다. 대상을 부를지 말지, 몇 번 부를지를 결정해야 하는 재시도에는 그래서 @Before가 아니라 @Around가 필요하다.

    JoinPoint는 지금 가로챈 호출의 정보를 담은 객체다. getSignature().toShortString()은 ShippingService.status(..)처럼 단순 클래스 이름과 메서드 이름을 돌려주고, getArgs()는 실제 인자 배열을 돌려준다. 애스펙트 클래스도 빈이고 기본이 싱글톤이므로, 모든 스레드가 같은 TraceAspect 인스턴스의 trace 메서드를 동시에 실행한다. 이 애스펙트에 필드가 하나도 없다는 점이 중요하다. 호출마다 달라지는 정보는 모두 매개변수 joinPoint와 지역 변수에만 있고, 이것들은 각 스레드의 스택 프레임에 따로 놓이므로 서로 섞이지 않는다. 애스펙트에 "현재 요청의 무엇"을 필드로 두는 순간 01회의 동시성 문제가 다시 생긴다.

    재시도 AOP — @Retry

    두 번째 애스펙트는 @Retry가 붙은 메서드가 예외로 끝나면, 애너테이션에 적힌 횟수만큼 다시 부른다.

    package example.aop;

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.core.annotation.Order;

@Aspect
@Order(1)
public class RetryAspect {

    @Around("@annotation(retry)")
    public Object doRetry(ProceedingJoinPoint joinPoint, Retry retry) throws Throwable {
        int maxAttempts = retry.value();
        Exception lastFailure = null;

        for (int attempt = 1; attempt <= maxAttempts; attempt++) {
            try {
                System.out.println("[retry] 시도 " + attempt + "/" + maxAttempts);
                return joinPoint.proceed();
            } catch (Exception e) {
                System.out.println("[retry] 실패: " + e.getMessage());
                lastFailure = e;
            }
        }
        throw lastFailure;
    }
}

    포인트컷 @annotation(retry)에는 애너테이션 타입 이름 대신 소문자 retry가 들어 있다. 이것은 타입 이름이 아니라 어드바이스 메서드의 매개변수 이름이다. 스프링은 포인트컷의 retry를 같은 이름의 매개변수와 연결하고, 그 매개변수의 타입 Retry를 보고 "@Retry가 붙은 메서드"라는 조건을 만든다. 그리고 실행할 때 대상 메서드에 붙은 @Retry 애너테이션 객체를 그 매개변수로 넘겨준다. 스프링 레퍼런스의 어드바이스 매개변수 절은 @annotation, @within, @target, @args로 애너테이션을 이렇게 바인딩할 수 있다고 설명한다. 덕분에 메서드마다 @Retry(4), @Retry(2)처럼 다른 횟수를 줄 수 있다.

    반복문 안의 return joinPoint.proceed();가 핵심이다. proceed()가 정상적으로 값을 돌려주면 그 값을 그대로 반환하며 반복이 끝난다. 예외가 나면 catch로 들어가 마지막 실패를 기억하고 다음 시도로 넘어간다. 모든 시도가 실패하면 마지막 예외를 던진다. 첫 번째 예외가 아니라 마지막 예외를 던지는 것은 선택이다. 진단에 첫 실패가 더 중요하다면 첫 예외를 던지고 나머지는 addSuppressed로 붙이는 방법도 있다.

    메서드 시그니처의 throws Throwable은 ProceedingJoinPoint.proceed()가 Throwable을 던지도록 선언되어 있기 때문이다. 반면 catch는 Exception만 잡는다. OutOfMemoryError 같은 Error는 다시 시도해서 나아질 상황이 아니므로 그대로 밖으로 내보내기 위해서다. 실무에서는 이보다 더 좁혀서, 다시 시도할 가치가 있는 예외(연결 실패, 타임아웃 등)만 재시도하는 것이 보통이다. 이 부분은 뒤에서 다시 다룬다.

    ShippingMain을 실행하면 다음과 같이 출력된다.

    [trace] ShippingService.status(..) args=[A-100]
[retry] 시도 1/4
[trace] ShippingClient.track(..) args=[A-100]
[retry] 실패: 일시 장애 #1
[retry] 시도 2/4
[trace] ShippingClient.track(..) args=[A-100]
[retry] 실패: 일시 장애 #2
[retry] 시도 3/4
[trace] ShippingClient.track(..) args=[A-100]
result = A-100:배송중
class  = example.aop.ShippingService$$SpringCGLIB$$0

    한 줄씩 따라가 보자. main이 받은 service는 마지막 줄이 보여 주듯 ShippingService를 상속한 CGLIB 프록시다. ShippingService는 인터페이스를 구현하지 않으므로 JDK 동적 프록시를 만들 수 없고, 스프링은 CGLIB를 쓴다. 프록시의 status가 불리면 status에 걸린 어드바이스, 즉 @Trace의 로그가 먼저 찍힌다(1행). status에는 @Retry가 없으므로 재시도 애스펙트는 끼어들지 않는다.

    예외는 트레이스 어드바이스를 그대로 통과해(@Before는 예외에 관여하지 않는다) 재시도 애스펙트의 catch에 잡힌다. 두 번째 시도도 같은 길을 밟아 실패하고(5~7행), 세 번째 시도에서 트레이스를 지나 대상이 정상 값을 돌려준다(8~9행). 이 값이 return joinPoint.proceed()로 재시도 애스펙트를 빠져나가고, 프록시를 거쳐 ShippingService.status로, 다시 main으로 돌아온다. 호출자인 main은 두 번의 실패를 전혀 모른다.

    눈여겨볼 점은 [trace] ShippingClient.track이 세 번 찍혔다는 것이다. 재시도 애스펙트가 proceed()를 세 번 불렀고, 그때마다 안쪽의 트레이스 어드바이스가 다시 실행되었다. 이것은 당연한 일이 아니다. 어떻게 같은 joinPoint로 체인의 같은 지점을 여러 번 다시 지날 수 있을까?

    트레이스 로그가 track에 대해 한 번만 찍혔다. 이제 체인은 [트레이스, 재시도] 순서이고, 트레이스가 바깥에서 한 번 실행된 뒤 재시도가 안쪽에서 대상만 세 번 부른다. 복제본은 재시도 위치에서 출발하므로 자기보다 바깥에 있는 트레이스를 다시 지나지 않는다.

    어느 쪽이 옳은지는 요구에 달렸다. "시도 하나하나를 기록하고 싶다"면 재시도가 바깥이어야 하고, "서비스 입장에서 호출 한 번은 한 번으로 기록하고 싶다"면 트레이스가 바깥이어야 한다. 중요한 것은 순서를 명시적으로 정해야 한다는 점이다. 레퍼런스의 어드바이스 순서 절은 서로 다른 애스펙트의 어드바이스가 같은 조인 포인트에 걸리면 "따로 지정하지 않는 한 실행 순서는 정의되지 않는다"고 적는다. 순서는 애스펙트 클래스에 Ordered를 구현하거나 @Order를 붙여 정하고, 값이 작을수록 우선순위가 높다. 우선순위가 높은 어드바이스는 "들어갈 때" 먼저 실행되고 "나올 때" 나중에 실행된다. 체인에서 바깥에 선다는 뜻이다.

    @Order는 애스펙트 클래스 단위로 적용된다. 한 애스펙트 클래스 안에 어드바이스 메서드가 여럿 있을 때 그 메서드들 사이의 순서를 @Order로 정할 수는 없다(08회). 순서를 따로 정해야 하는 어드바이스는 별도의 애스펙트 클래스로 나눈다.

    재시도를 실무에 붙일 때 — 순서, 트랜잭션, 멱등성

    예제의 재시도 애스펙트는 원리를 보이기에는 충분하지만, 실제 서비스에 붙이려면 세 가지를 더 따져야 한다. 트랜잭션과의 순서, 재시도해도 안전한 작업인지, 그리고 무엇을 언제 다시 시도할지다.

    트랜잭션보다 바깥에 둔다

    @Transactional도 스프링 DB 1편과 2편에서 본 대로 프록시와 어드바이스로 동작한다. 같은 메서드에 재시도와 트랜잭션이 함께 걸리면 둘의 순서가 결과를 바꾼다. 스프링 레퍼런스의 AOP 예제 절은 비관적 락 실패(교착 상태의 희생자 같은)를 재시도하는 애스펙트를 소개하면서, 이 애스펙트가 Ordered를 구현해 트랜잭션 어드바이스보다 우선순위를 높게 둔다고 설명한다. 이유는 "재시도할 때마다 새 트랜잭션을 원하기 때문"이다.

    재시도가 트랜잭션 안쪽에 있으면 모든 시도가 같은 트랜잭션, 같은 커넥션 안에서 일어난다. 그런데 재시도하고 싶은 실패 가운데에는 트랜잭션 자체가 망가진 경우가 많다. MySQL InnoDB는 교착 상태를 감지하면 관련 트랜잭션 하나 이상을 롤백해 교착을 푼다. 이미 롤백된 트랜잭션 안에서 같은 작업을 반복하는 것은 의미가 없고, 새 트랜잭션에서 처음부터 다시 해야 한다. 재시도가 바깥에 있으면 시도마다 트랜잭션 어드바이스를 새로 지나므로(앞에서 본 복제본 덕분이다) 시도마다 트랜잭션이 새로 시작되고 끝난다.

    트랜잭션 어드바이스의 순서는 @EnableTransactionManagement의 order 속성이 정한다. Spring 6.2.19의 spring-tx에서 이 속성의 기본값을 읽어 보면 2147483647, 즉 Ordered.LOWEST_PRECEDENCE다. 가장 낮은 우선순위, 다시 말해 가장 안쪽이다. 그러니 재시도 애스펙트에 그보다 작은 순서 값을 명시하면 트랜잭션보다 바깥에 선다. 반대로 재시도 애스펙트에 순서를 지정하지 않으면 둘 다 가장 낮은 우선순위가 되어 순서가 정의되지 않는다. "보통은 잘 되던" 재시도가 어느 날 트랜잭션 안쪽으로 들어가는 일을 막으려면 순서를 반드시 적는다.

    멱등한 작업만 재시도한다

    같은 레퍼런스 예제는 처음에 모든 서비스 메서드를 재시도하다가, "멱등한(idempotent) 작업만" 재시도하도록 @Idempotent 애너테이션과 @annotation 포인트컷으로 대상을 좁힌다. 멱등하다는 것은 같은 요청을 여러 번 보내도 한 번 보낸 것과 결과가 같다는 뜻이다. HTTP 명세(RFC 9110)도 GET, PUT, DELETE 같은 메서드를 멱등 메서드로 정의하고, 멱등 요청은 통신 실패 시 자동으로 재시도할 수 있다고 적는다.

    이 조건이 중요한 이유는 원격 호출의 실패가 두 종류로 구분되지 않기 때문이다. 요청이 상대에게 도착하지 못해 실패했을 수도 있고, 상대가 요청을 처리했는데 응답이 돌아오는 길에 연결이 끊겼을 수도 있다. 호출하는 쪽에서는 둘 다 똑같이 타임아웃이나 연결 예외로 보인다. 배송 조회는 몇 번을 반복해도 상태가 바뀌지 않으니 안전하다. 그러나 "결제 승인 요청"을 같은 방식으로 재시도하면, 첫 요청이 실제로는 처리되었을 경우 결제가 두 번 일어난다. 이런 작업을 재시도하려면 요청마다 고유한 키를 붙여 상대가 중복을 걸러 내게 하는 등, 작업 자체를 멱등하게 만드는 설계가 먼저다.

    무엇을, 언제 다시 시도할 것인가

    예제는 모든 Exception을 재시도한다. 하지만 인자가 잘못되어 생긴 예외나 권한 없음 같은 실패는 몇 번을 다시 해도 같은 결과가 나온다. 이런 실패를 재시도하면 응답만 늦어지고 상대 서버에 쓸데없는 부하를 준다. 실무 재시도에는 보통 "이 예외들만 재시도한다" 혹은 "이 예외들은 재시도하지 않는다"는 목록이 붙는다. @Retry에 Class[] 타입의 속성을 추가하고, 애스펙트의 catch에서 예외 타입을 검사하면 된다.

    시도 사이의 간격도 문제다. 예제는 실패하자마자 다시 부른다. 상대 서버가 과부하로 실패하는 중이라면, 모든 클라이언트가 즉시 재시도하는 순간 부하가 시도 횟수만큼 불어난다. 그래서 시도 사이에 대기 시간을 두고, 시도할수록 간격을 늘리며(지수 백오프), 여러 클라이언트의 재시도가 같은 순간에 몰리지 않도록 간격에 무작위 값을 섞는다(지터). 다만 애스펙트 안에서 Thread.sleep으로 기다리는 동안 그 요청 스레드는 아무 일도 못 하고 스레드 풀의 한 자리를 차지한다는 점을 기억하자. 대기 시간과 시도 횟수의 곱이 요청 하나가 붙잡을 수 있는 최대 시간이 된다.

    이런 요구를 매번 직접 구현할 필요는 없다. 별도 프로젝트인 Spring Retry가 오래전부터 이 기능을 제공해 왔고, Spring Framework 7.0의 spring-context에는 org.springframework.resilience.annotation.Retryable이 들어 있다(7.0.10 jar에서 확인했고, 6.2.19에는 이 패키지가 없다). 이 애너테이션의 속성을 javap로 보면 includes, excludes, maxRetries, delay, multiplier, jitter, maxDelay가 있다. 방금 말한 예외 선택, 횟수, 간격, 백오프, 지터가 그대로 속성 이름이 되어 있는 셈이다. 그리고 이런 애너테이션도 결국 프록시와 어드바이스로 동작하므로, 이 회차 뒷부분의 함정을 그대로 물려받는다.

    프록시와 내부 호출 — 문제

    이제 뒷부분이다. 다음 클래스는 보고서를 발행하는 publish와 본문을 만드는 render를 가졌고, 둘 다 @Trace가 붙어 있다. publish는 안에서 render를 부른다.

    package example.internal;

import example.aop.Trace;

public class ReportService {

    @Trace
    public String publish(String title) {
        System.out.println("  publish 실행 중, this = " + this.getClass().getSimpleName());
        return render(title);          // this.render(title) 와 같다
    }

    @Trace
    public String render(String title) {
        return "<" + title + ">";
    }
}

    이 클래스를 빈으로 등록하고 앞의 TraceAspect와 함께 띄운 다음, 컨테이너에서 꺼낸 빈의 publish("월간 보고")를 불렀다. 두 메서드 모두 @Trace가 붙었으니 트레이스 로그가 두 줄 나와야 할 것 같다.

    프록시와 대상은 서로 다른 객체다

    스프링 AOP 프록시는 대상 객체를 감싸는 별개의 객체다. 컨테이너에는 프록시가 빈으로 등록되고, 프록시는 안에 진짜 ReportService 인스턴스(대상, target)에 대한 참조를 들고 있다. 호출 흐름은 다음과 같다.

    CGLIB 프록시는 ReportService를 상속한 클래스이기 때문에 "프록시가 곧 대상 아닌가" 하고 착각하기 쉽다. 상속 관계만 보면 그럴듯하다. 프록시가 super.publish()를 부르는 방식이었다면 실행 중의 this는 프록시 자신이고, 안에서 부른 render도 가상 메서드 호출에 따라 프록시의 render로 가서 어드바이스가 걸렸을 것이다. 그러나 스프링의 CGLIB 프록시는 그렇게 만들어지지 않는다. 프록시 인스턴스와 대상 인스턴스는 따로 있고, 프록시는 호출을 대상 인스턴스에 넘긴다. 위 실행 결과의 this = ReportService가 그 증거이고, 뒤에서 볼 "프록시 객체의 필드는 모두 비어 있다"는 실험이 또 하나의 증거다.

      클라이언트
     │ publish()
     ▼
 ┌──────────────────────────────┐        ┌──────────────────────────────┐
 │ ReportService$$SpringCGLIB$$0│        │ ReportService (대상)          │
 │ (프록시, 빈으로 등록됨)        │ target │                              │
 │  publish() ─▶ [trace 어드바이스]──────▶│  publish() {                 │
 │  render()  ─▶ [trace 어드바이스]  ┐    │     this.render()  ──┐       │
 └──────────────────────────────┘   │    │  }                   │       │
                                    │    │  render() ◀──────────┘       │
               아무도 부르지 않는 길 ─┘    └──────────────────────────────┘
    클라이언트의 호출은 프록시와 어드바이스를 거쳐 대상에 도달하지만, 대상 안에서 this로 부른 메서드는 프록시를 거치지 않는다는 것을 보여 준다. 왼쪽에 사람 아이콘 "클라이언트". 가운데에 파란 상자 "프록시", 그 안에 작은 칸 두 개 "publish()"와 "render()", 각 칸 옆에 주황 방패 아이콘 "트레이스 어드바이스". 오른쪽에 회색 상자 "대상 ReportService", 그 안에 "publish()"와 "render()". 클라이언트에서 프록시의 publish()로 굵은 화살표, 프록시 publish()에서 방패를 지나 대상 publish()로 화살표. 대상 publish()에서 대상 render()로 휘어진 빨간 화살표, 라벨 "this.render() — 프록시를 거치지 않음". 프록시의 render() 칸은 흐리게 처리하고 라벨 "거치지 않는 길". 평면 벡터 스타일, 흰 배경. 어드바이스는 프록시에 붙어 있다. 대상 객체 안에서 this로 부른 호출은 프록시를 지나지 않으므로 어드바이스가 실행되지 않는다.

    스프링 레퍼런스의 프록시 메커니즘 절도 같은 말을 한다. 대상 객체 안에서 명시적이든 암묵적이든 this로 일어난 자기 호출(self-invocation)은 어드바이스를 우회한다. 그리고 AspectJ의 컴파일 시점 위빙이나 로드 시점 위빙에는 이 문제가 없다고 덧붙인다. 그 방식들은 프록시를 만드는 대신 어드바이스 코드를 대상 클래스의 바이트코드 안에 직접 넣기 때문이다. 어드바이스가 메서드 본문의 일부가 되면 누가 어떤 경로로 부르든 실행된다.

    이 문제는 로그 한 줄이 빠지는 것으로 끝나지 않는다. @Transactional도 같은 프록시 방식이다. 스프링 트랜잭션 문서는 프록시 모드(기본값)에서는 프록시를 통해 들어온 외부 호출만 가로채므로, 대상 객체 안에서 다른 메서드를 부르는 자기 호출은 그 메서드에 @Transactional이 붙어 있어도 실제 트랜잭션으로 이어지지 않는다고 명시한다. 트랜잭션이 없는 메서드가 트랜잭션이 필요한 메서드를 같은 클래스 안에서 부르면, 코드에는 @Transactional이 보이는데 실제로는 트랜잭션 없이 실행된다. 앞에서 만든 @Retry도 마찬가지다. 같은 클래스의 다른 메서드가 @Retry 메서드를 부르면 재시도는 일어나지 않는다. 그리고 어느 경우에도 예외나 경고는 나오지 않는다.

    해결 방향은 하나다. 호출이 프록시를 거치게 만든다. 그 방법으로 자기 자신을 주입받는 것, 필요할 때 컨테이너에서 꺼내 쓰는 것, 아예 구조를 바꿔 다른 객체를 부르게 하는 것 세 가지를 차례로 본다.

    대안1 — 자기 자신 주입

    첫 번째 대안은 대상 객체가 자기 자신의 프록시를 필드로 받아 두고, this 대신 그 필드로 부르는 것이다.

    package example.internal;

import example.aop.Trace;
import org.springframework.beans.factory.annotation.Autowired;

public class ReportServiceV1 {

    private ReportServiceV1 self;

    @Autowired
    public void setSelf(ReportServiceV1 self) {
        System.out.println("  setSelf 주입: " + self.getClass().getSimpleName());
        this.self = self;
    }

    @Trace
    public String publish(String title) {
        return self.render(title);     // 프록시를 거친다
    }

    @Trace
    public String render(String title) {
        return "<" + title + ">";
    }
}
      setSelf 주입: ReportServiceV1$$SpringCGLIB$$0
[trace] ReportServiceV1.publish(..) args=[월간 보고]
[trace] ReportServiceV1.render(..) args=[월간 보고]
result = <월간 보고>

    트레이스가 두 줄 찍혔다. 주목할 것은 첫 줄이다. 세터로 들어온 객체가 원본 ReportServiceV1이 아니라 프록시다. 그런데 생각해 보면 이상하다. 06회에서 본 대로 빈 후처리기는 객체를 만들고, 의존관계를 주입하고, 초기화까지 끝난 뒤에 postProcessAfterInitialization에서 프록시로 바꾼다. 세터 주입은 그 전에 일어난다. 아직 프록시가 만들어지기 전인데 어떻게 프록시가 주입되었을까?

    한 층 아래 — 생성 중인 빈의 이른 참조

    스프링의 싱글톤 레지스트리(DefaultSingletonBeanRegistry)에는 완성된 빈을 담는 singletonObjects 외에 earlySingletonObjects와 singletonFactories라는 맵이 더 있다. 순환 참조가 허용된 상태에서 컨테이너는 빈 인스턴스를 생성자로 만든 직후, 의존관계를 주입하기 전에 "이 빈의 이른 참조(early reference)를 달라는 요청이 오면 이렇게 만들어 주라"는 팩토리를 singletonFactories에 등록해 둔다. 이 팩토리는 getEarlyBeanReference를 호출하고, 그 안에서 SmartInstantiationAwareBeanPostProcessor들에게 이른 참조를 가공할 기회를 준다.

    자동 프록시 생성기의 부모인 AbstractAutoProxyCreator는 바로 이 인터페이스를 구현한다. 자기 자신을 주입받으려고 세터가 reportServiceV1 빈을 요청하면, 컨테이너는 생성 중인 그 빈의 팩토리를 꺼내 실행하고, 자동 프록시 생성기의 getEarlyBeanReference가 그 자리에서 프록시를 만들어 돌려준다. 생성기는 이렇게 일찍 프록시를 만든 빈을 earlyBeanReferences 맵에 기록해 둔다(Spring 6.2.19의 필드 이름). 나중에 초기화가 끝나 postProcessAfterInitialization이 불리면 이 기록을 보고 프록시를 또 만들지 않는다. 그 결과 세터로 주입된 프록시와 최종적으로 컨테이너에 등록되는 프록시가 같은 객체가 된다.

    이 장치가 있어야 자기 주입이 동작하므로, 자기 주입은 본질적으로 순환 참조다. 빈 A가 자기 자신인 A를 필요로 한다. 그래서 생성자 주입으로는 불가능하다. 생성자가 끝나기 전에는 인스턴스가 없고, 인스턴스가 없으면 이른 참조를 만들 대상도 없다. 세터나 필드 주입이어야 하는 이유다.

    스프링 부트 2.6부터는 기본으로 막힌다

    스프링 부트 2.6 릴리스 노트는 "빈 사이의 순환 참조가 이제 기본으로 금지된다"고 알린다. 다시 허용하려면 spring.main.allow-circular-references를 true로 설정해야 하고, 노트는 그보다 의존 관계의 순환을 끊도록 구성을 고치라고 강하게 권한다. 부트가 하는 일은 결국 빈 팩토리의 allowCircularReferences를 끄는 것이므로, 실험에서는 컨테이너에 setAllowCircularReferences(false)를 호출해 같은 상황을 만들었다.

    BeanCurrentlyInCreationException: Error creating bean with name 'reportServiceV1':
Requested bean is currently in creation: Is there an unresolvable circular reference
or an asynchronous initialization dependency?

    바깥 예외는 UnsatisfiedDependencyException이고 메시지에 "Unsatisfied dependency expressed through method 'setSelf' parameter 0"이 함께 나온다. 이른 참조 팩토리가 등록되지 않으니, 생성 중인 빈을 다시 요청하는 순간 컨테이너는 "지금 만들고 있는 빈을 또 달라고 한다"는 사실만 확인하고 실패한다. 애플리케이션이 시작조차 되지 않는다.

    스프링 레퍼런스의 @Autowired 절은 자기 주입을 이렇게 평가한다. 자기 참조는 대체(fallback) 수단이며, 다른 컴포넌트에 대한 정상적인 의존이 항상 우선한다. 그리고 실무에서는 같은 인스턴스의 다른 메서드를 트랜잭션 프록시를 통해 부르는 경우처럼 "최후의 수단으로만" 쓰고, 그런 상황에서는 해당 메서드를 별도의 위임 빈으로 빼는 것을 고려하라고 덧붙인다. 순환 참조 허용을 켜야 하고, 의존 그래프에 자기 자신으로 돌아오는 고리가 생긴다는 점에서 자기 주입은 가장 먼저 꺼낼 카드가 아니다.

    대안2 — 지연 조회

    자기 주입이 막힌 이유를 다시 보자. 문제는 "자기 자신을 원한다"는 것 자체가 아니라 언제 원하느냐다. 빈을 만드는 도중에 자기 자신을 요구하니 아직 완성품이 없다. 그런데 실제로 프록시가 필요한 시점은 publish가 실행될 때다. 그때는 빈 생성이 오래전에 끝났고, 컨테이너에는 완성된 프록시가 등록되어 있다. 그렇다면 주입받는 것을 프록시 자체가 아니라 "프록시를 나중에 꺼내 주는 도구"로 바꾸면 된다. 이것이 지연 조회(lazy lookup)다.

    package example.internal;

import example.aop.Trace;
import org.springframework.beans.factory.ObjectProvider;

public class ReportServiceV2 {

    private final ObjectProvider selfProvider;

    public ReportServiceV2(ObjectProvider selfProvider) {
        this.selfProvider = selfProvider;
    }

    @Trace
    public String publish(String title) {
        ReportServiceV2 self = selfProvider.getObject();   // 호출 시점에 컨테이너에서 꺼낸다
        System.out.println("  getObject() = " + self.getClass().getSimpleName());
        return self.render(title);
    }

    @Trace
    public String render(String title) {
        return "<" + title + ">";
    }
}
    [trace] ReportServiceV2.publish(..) args=[월간 보고]
  getObject() = ReportServiceV2$$SpringCGLIB$$0
[trace] ReportServiceV2.render(..) args=[월간 보고]
result = <월간 보고>

    순환 참조를 금지한 컨테이너에서도 정상으로 시작되고, 트레이스가 두 줄 찍혔다. 생성자로 주입되는 ObjectProvider는 스프링 핵심 원리 기본편의 프로토타입 스코프 이야기에서 본 그 도구로, 그 자체는 ReportServiceV2 빈이 아니라 컨테이너에 빈을 요청하는 작은 창구다. 생성 시점에는 창구만 받아 두므로 순환이 생기지 않는다. publish가 실행되는 시점에 getObject()를 부르면 컨테이너는 이미 등록된 싱글톤, 즉 프록시를 돌려준다. 싱글톤이므로 매번 같은 객체이고 새로 만드는 비용은 없다.

    같은 원리를 다른 모양으로 쓸 수도 있다. ApplicationContext를 주입받아 getBean(ReportServiceV2.class)로 꺼내는 방법도 실험에서 같은 결과를 냈다. 다만 필요한 것은 빈 하나인데 컨테이너 전체에 의존하게 되므로 ObjectProvider보다 범위가 넓다. 또 하나는 주입 지점에 @Lazy를 붙이는 방법이다. @Lazy Javadoc에 따르면 @Autowired 주입 지점에 붙은 @Lazy는 대상 의존성에 대한 지연 해석 프록시(lazy-resolution proxy)를 만들어 주입하고, 싱글톤이면 처음 접근할 때 실제 빈을 찾아 캐시한다. ObjectFactory나 Provider의 대안이라고 Javadoc이 직접 적고 있다. @Autowired @Lazy ReportServiceV2 self;로 바꿔도 순환 참조 금지 상태에서 시작되고 트레이스가 두 줄 찍히는 것을 확인했다. 코드 모양은 자기 주입과 같지만 실제로 주입되는 것은 "나중에 찾아 주는 프록시"라서 순환이 생기지 않는다. 대신 Javadoc이 경고하듯, 대상이 없더라도 시작 시점에는 드러나지 않고 호출할 때 예외로 알게 된다.

    AopContext.currentProxy()

    스프링 레퍼런스가 소개하는 또 하나의 방법은 대상 코드 안에서 AopContext.currentProxy()로 현재 프록시를 꺼내는 것이다.

    @Trace
public String publish(String title) {
    return ((ReportService) AopContext.currentProxy()).render(title);
}

    이 방법은 설정을 하나 더 요구한다. @EnableAspectJAutoProxy(exposeProxy = true)처럼 프록시를 노출하도록 켜야 하고, 기본값은 false다(6.2.19의 애너테이션 기본값으로 확인). 켜지 않은 상태에서 부르면 다음 예외가 난다.

    java.lang.IllegalStateException: Cannot find current proxy: Set 'exposeProxy' property on Advised
to 'true' to make it available, and ensure that AopContext.currentProxy() is invoked in the same
thread as the AOP invocation context.
