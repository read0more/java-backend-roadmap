    프록시를 만들 줄 아는데도 남는 문제

    05회에서 스프링의 ProxyFactory를 다뤘다. 대상 객체를 넘기면 인터페이스가 있으면 JDK 동적 프록시로, 없으면 CGLIB로 프록시를 만들어 주고, 부가 기능은 어드바이스(advice)로, 적용 대상은 포인트컷(pointcut)으로, 그 둘을 묶은 것은 어드바이저(advisor)로 표현했다. 프록시 기술의 차이를 감추는 추상화가 생겼으니 프록시를 "만드는" 문제는 사실상 풀렸다.

    그런데 만든 프록시를 스프링 컨테이너에 넣는 문제가 남아 있다. 지금까지의 방식대로라면 설정 클래스의 @Bean 메서드 안에서 실제 객체를 만들고, ProxyFactory로 감싸고, 그 프록시를 반환해야 한다. 빈이 100개면 이런 @Bean 메서드도 100개다. 각 메서드는 "실제 객체 생성 → 프록시 생성 → 반환"이라는 같은 모양을 반복하고, 실제 객체를 만들 때 필요한 의존관계도 손으로 넘겨야 한다. 05회에서 프록시 클래스를 손으로 쓰지 않게 됐는데, 이번에는 프록시 설정 코드를 손으로 쓰게 된 셈이다.

    더 근본적인 문제는 컴포넌트 스캔이다. @Service, @Repository가 붙은 클래스는 컨테이너가 직접 찾아 객체를 만들고 곧바로 등록한다. 그 과정에 개발자가 쓴 코드가 끼어들 자리가 없다. @Bean 메서드에서는 반환값을 바꿔치기할 수 있었지만, 스캔된 빈은 컨테이너가 만든 실제 객체가 그대로 저장소에 들어간다. 이 상태로는 스캔된 빈에 프록시를 적용할 방법이 없다.

    두 문제의 공통점은 "컨테이너가 객체를 만들고 등록하는 과정 중간에 끼어들 수 없다"는 것이다. 스프링은 바로 그 중간 지점을 확장 지점으로 열어 두었다. 컨테이너가 객체를 만든 뒤 저장소에 넣기 전에, 그 객체를 넘겨받아 조작하거나 다른 객체로 바꿔 돌려줄 수 있는 훅이다. 이것이 빈 후처리기(bean post processor)다. 이 회차는 빈 후처리기를 직접 만들어 보고, 스프링이 이 장치 위에 얹어 둔 자동 프록시 생성기(auto proxy creator)가 어드바이저 빈만 등록하면 프록시를 알아서 만들어 주는 원리까지 내려간다.

    이 회차의 실행 결과는 원고를 쓰면서 JDK 21.0.13(Temurin), Spring Framework 6.2.19(spring-context, spring-aop), AspectJ Weaver 1.9.25.1로 직접 돌려 얻었다. 스프링 부트 없이 AnnotationConfigApplicationContext로 실행했고, 스프링 부트의 동작은 Spring Boot 3.5.16의 spring-boot-autoconfigure 소스로 확인했다. 스프링 내부 클래스의 메서드 이름과 필드는 공개 API가 아니므로 버전에 따라 달라질 수 있다. 일부 내부 코드는 7.0.10 소스를 읽고 6.2.19 바이너리를 javap로 열어 같은 구조인지 대조했다.

    빈 후처리기 — 소개

    스프링 컨테이너가 빈을 등록하는 과정을 아주 거칠게 나누면 "객체 생성 → 저장소에 등록"이다. 빈 후처리기는 이 두 단계 사이에 끼어든다. 컨테이너는 객체를 만든 뒤 등록된 모든 빈 후처리기에게 그 객체를 차례로 넘기고, 마지막 후처리기가 돌려준 객체를 저장소에 넣는다. 후처리기는 넘겨받은 객체를 그대로 돌려줄 수도, 필드를 바꾸거나 메서드를 호출한 뒤 돌려줄 수도, 완전히 다른 객체를 돌려줄 수도 있다. 마지막 경우가 이 회차의 핵심이다. 컨테이너는 돌려받은 객체가 원래 객체인지 확인하지 않는다. 그 객체가 곧 그 이름의 빈이 된다.

    인터페이스는 org.springframework.beans.factory.config.BeanPostProcessor이고 메서드는 두 개다.

    public interface BeanPostProcessor {
    default Object postProcessBeforeInitialization(Object bean, String beanName) throws BeansException {
        return bean;
    }
    default Object postProcessAfterInitialization(Object bean, String beanName) throws BeansException {
        return bean;
    }
}

    이름의 "Initialization"은 빈의 초기화 콜백(@PostConstruct, InitializingBean.afterPropertiesSet(), @Bean(initMethod=...))을 가리킨다. 앞의 메서드는 초기화 콜백이 불리기 전에, 뒤의 메서드는 후에 호출된다. Spring Framework 6.2.19 소스에서 두 메서드는 모두 받은 객체를 그대로 돌려주는 기본(default) 메서드여서, 필요한 쪽만 재정의하면 된다. 프록시처럼 "완성된 객체를 감싸는" 작업은 초기화가 다 끝난 뒤인 postProcessAfterInitialization에서 하는 것이 자연스럽다. 초기화 전에 감싸 버리면 초기화 콜백이 프록시를 통해 호출되는 등 의도와 다른 일이 생길 수 있기 때문이다.

    일상에서 가져온 비유출고 전 검수대

    공장에서 만든 제품이 창고로 들어가기 전에 검수대를 지난다고 하자. 검수원은 제품에 스티커를 붙이기도 하고, 포장 상자를 씌우기도 하고, 불량이면 다른 제품으로 바꿔 넣기도 한다. 창고 관리자는 검수대를 통과해 나온 것을 그대로 받아 선반에 올린다. 빈 후처리기가 검수대, 싱글톤 저장소가 창고다. 다만 실제 검수대는 제품마다 다르게 배치할 수 있지만, 빈 후처리기는 컨테이너 안의 모든 빈이 지나간다는 점이 다르다. 그래서 후처리기는 대개 "내가 처리할 빈인가"를 스스로 걸러야 한다.

    컨테이너가 만든 객체가 후처리기 여러 개를 차례로 통과하며 다른 객체(프록시)로 바뀐 뒤 저장소에 들어가는 모습. 왼쪽에서 오른쪽으로 흐르는 가로 흐름도. 맨 왼쪽에 "스프링 컨테이너"라는 큰 상자, 그 안에서 작은 정육면체 아이콘 "원본 객체"가 나온다. 화살표를 따라 세로로 긴 필터 모양의 상자 세 개가 나란히 있고 각각 "후처리기 1", "후처리기 2", "후처리기 3"이라고 적는다. 두 번째 필터를 지난 뒤 정육면체가 반투명한 껍데기에 싸인 모양으로 바뀌고 그 위에 "프록시"라는 라벨을 단다. 맨 오른쪽에 서랍장 모양의 "싱글톤 저장소"가 있고, 서랍 하나에 "loanService"라는 이름표가 붙어 그 안에 프록시가 들어간다. 저장소 아래에 점선 화살표로 "주입·조회는 이 객체를 받는다"라는 설명. 배경은 흰색, 선은 짙은 회색, 프록시만 청록색으로 강조. 후처리기가 돌려준 마지막 객체가 그 이름의 빈이 된다. 원본은 등록되지 않는다.

    컨테이너가 빈 하나를 만드는 과정 — 한 층 아래

    후처리기가 언제 불리는지 정확히 알려면 컨테이너가 싱글톤 빈 하나를 만드는 코드 경로를 봐야 한다. 일반 빈의 생성은 AbstractAutowireCapableBeanFactory의 createBean에서 시작한다. Spring Framework 6.2.19 소스를 따라가면 큰 줄기는 다음과 같다.

    createBean(beanName, mbd, args)
 ├─ resolveBeforeInstantiation()          ← InstantiationAwareBeanPostProcessor
 │     postProcessBeforeInstantiation()       가 객체를 반환하면 여기서 끝(생성 생략)
 └─ doCreateBean()
     ├─ createBeanInstance()              ← 생성자 또는 팩토리 메서드 호출 (new 에 해당)
     ├─ applyMergedBeanDefinitionPostProcessors()
     │                                      (@Autowired, @PostConstruct 위치를 미리 수집)
     ├─ addSingletonFactory(beanName, () -> getEarlyBeanReference(...))
     │                                      (순환 참조 대비: "만들다 만 객체"를 꺼낼 통로)
     ├─ populateBean()                     ← 의존관계 주입
     │     InstantiationAwareBeanPostProcessor.postProcessProperties()
     │     (AutowiredAnnotationBeanPostProcessor 가 @Autowired 를 여기서 처리)
     └─ initializeBean()
         ├─ invokeAwareMethods()           BeanNameAware, BeanClassLoaderAware, BeanFactoryAware
         ├─ applyBeanPostProcessorsBeforeInitialization()   ← 모든 BPP 의 before
         ├─ invokeInitMethods()            afterPropertiesSet(), initMethod
         └─ applyBeanPostProcessorsAfterInitialization()    ← 모든 BPP 의 after
                                            반환값 = 최종 빈 (exposedObject)

    눈여겨볼 점이 셋 있다. 첫째, 의존관계 주입조차 후처리기가 한다. @Autowired를 처리하는 AutowiredAnnotationBeanPostProcessor는 SmartInstantiationAwareBeanPostProcessor를 구현하고, populateBean 단계에서 postProcessProperties로 필드와 세터에 값을 넣는다. 둘째, @PostConstruct도 후처리기가 부른다. CommonAnnotationBeanPostProcessor의 부모인 InitDestroyAnnotationBeanPostProcessor가 postProcessBeforeInitialization에서 @PostConstruct 메서드를 호출한다. 그래서 @PostConstruct는 afterPropertiesSet()보다 먼저 실행된다. 셋째, 컨테이너가 최종적으로 저장하는 객체는 initializeBean의 반환값이다. doCreateBean은 생성한 객체(bean)와 노출할 객체(exposedObject)를 별개 변수로 다루며, 후처리기가 다른 객체를 반환하면 둘이 달라진다.

    후처리기를 차례로 적용하는 코드도 단순하다. 6.2.19의 applyBeanPostProcessorsAfterInitialization은 등록된 후처리기 목록을 순회하면서 processor.postProcessAfterInitialization(result, beanName)의 반환값을 다음 입력으로 넘기고, 어떤 후처리기가 null을 반환하면 그 시점까지의 결과를 즉시 반환하고 나머지 후처리기를 건너뛴다. null로 "빈을 없앤다"는 동작은 없다. 실수로 null을 반환하는 후처리기를 만들면 그 뒤의 후처리기, 예를 들어 자동 프록시 생성기가 조용히 생략될 수 있다는 뜻이다.

    이 순서를 실행으로 확인해 보자. 생성자, @Autowired 세터, BeanNameAware, @PostConstruct, afterPropertiesSet, 사용자 정의 초기화 메서드에 모두 출력을 넣고, 후처리기 하나가 이 빈이 지나갈 때 앞뒤로 출력하게 했다. (@PostConstruct를 처리하려면 클래스패스에 jakarta.annotation-api가 있어야 한다. 실험에는 2.1.1을 썼다.)

    public class LifecycleMain {

    static class Clock {}

    static class Probe implements BeanNameAware, InitializingBean {
        Probe() { System.out.println("1 constructor"); }

        @Autowired
        void setClock(Clock clock) { System.out.println("2 @Autowired setter"); }

        @Override
        public void setBeanName(String name) { System.out.println("3 setBeanName(" + name + ")"); }

        @PostConstruct
        void postConstruct() { System.out.println("5 @PostConstruct"); }

        @Override
        public void afterPropertiesSet() { System.out.println("6 afterPropertiesSet"); }

        void customInit() { System.out.println("7 initMethod"); }
    }

    static class Watcher implements BeanPostProcessor {
        @Override
        public Object postProcessBeforeInitialization(Object bean, String beanName) {
            if (bean instanceof Probe) System.out.println("4 BPP before");
            return bean;
        }

        @Override
        public Object postProcessAfterInitialization(Object bean, String beanName) {
            if (bean instanceof Probe) System.out.println("8 BPP after");
            return bean;
        }
    }

    @Configuration
    static class Config {
        @Bean Clock clock() { return new Clock(); }
        @Bean(initMethod = "customInit") Probe probe() { return new Probe(); }
        @Bean static Watcher watcher() { return new Watcher(); }
    }

    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(Config.class)) {
            System.out.println("-- registered BeanPostProcessors, in order:");
            var bf = (AbstractBeanFactory) ctx.getBeanFactory();
            bf.getBeanPostProcessors().forEach(p -> System.out.println("  " + p.getClass().getName()));
        }
    }
}

    번호가 1부터 8까지 어긋남 없이 찍혔다. 2번(주입)이 3번(Aware)보다 먼저인 것은 populateBean이 initializeBean보다 앞이기 때문이고, 4번이 5번보다 먼저인 것은 후처리기 목록에서 Watcher가 CommonAnnotationBeanPostProcessor보다 앞에 있기 때문이다. 둘 다 postProcessBeforeInitialization에서 일하는데, 목록 순서대로 불리므로 Watcher의 before가 먼저 실행되고 그다음 CommonAnnotationBeanPostProcessor의 before가 @PostConstruct를 부른다. 6번과 7번은 invokeInitMethods 안에서 정해진 순서다. 마지막 8번이 프록시를 만들기에 가장 좋은 자리다. 객체가 주입도 초기화도 끝난 완성품이 된 직후다.

    실행 결과에 보이는 후처리기 목록의 순서, 즉 사용자가 만든 후처리기가 스프링 내장 후처리기보다 앞에 있는 이유는 뒤의 "후처리기는 어떻게 등록되고 정렬되는가"에서 다룬다.
    doCreateBean 안의 단계(생성, 주입, Aware, before, 초기화, after)를 가로 타임라인으로 놓고 각 단계에서 일하는 후처리기를 표시한다. 가로로 긴 타임라인 한 줄. 왼쪽부터 칸 여섯 개를 순서대로 배치: "객체 생성", "의존관계 주입", "Aware 콜백", "before 후처리", "초기화 콜백", "after 후처리". 각 칸 아래에 작은 말풍선으로 그 단계에서 일하는 주체를 적는다: "의존관계 주입" 아래에 "AutowiredAnnotationBeanPostProcessor", "before 후처리" 아래에 "@PostConstruct 호출", "after 후처리" 아래에 "자동 프록시 생성기". 마지막 칸 오른쪽으로 굵은 화살표가 나가 "최종 빈 등록"이라는 상자에 닿는다. "after 후처리" 칸만 청록색으로 칠하고 나머지는 연회색. 깔끔한 플랫 스타일, 흰 배경. 프록시는 모든 초기화가 끝난 뒤 after 후처리 단계에서 만들어진다.

    이 장의 핵심

    빈 후처리기는 컨테이너가 만든 객체를 넘겨받아 반환값으로 대체할 수 있는 훅이다. 컨테이너는 반환된 객체를 검증 없이 그 이름의 빈으로 저장하고, 이후 주입과 타입 조회는 모두 그 객체의 실제 타입을 기준으로 한다. 프록시를 컨테이너에 넣는 길이 바로 이것이다.

    후처리기는 어떻게 등록되고 정렬되는가

    후처리기도 빈이다. 그런데 일반 빈과 똑같이 만들면 문제가 생긴다. 후처리기는 다른 빈이 만들어질 때 이미 준비되어 있어야 하기 때문이다. 그래서 컨테이너는 후처리기를 일반 빈보다 먼저, 별도의 단계에서 만든다. AbstractApplicationContext.refresh()의 6.2.19 코드에서 단계 순서는 다음과 같다.

    3단계의 정렬 규칙은 PostProcessorRegistrationDelegate.registerBeanPostProcessors에 있다. 먼저 PriorityOrdered를 구현한 후처리기를 만들어 정렬해 등록하고, 다음에 Ordered를 구현한 것, 마지막으로 순서를 밝히지 않은 것을 등록한다. 그런 다음 MergedBeanDefinitionPostProcessor를 구현한 "내부" 후처리기들을 정렬해 다시 등록한다. AbstractBeanFactory.addBeanPostProcessor는 이미 목록에 있는 후처리기를 지운 뒤 맨 뒤에 붙이므로, 이 재등록은 내부 후처리기를 목록 끝으로 옮기는 효과를 낸다. 앞의 실행 결과에서 사용자가 만든 Watcher가 CommonAnnotationBeanPostProcessor와 AutowiredAnnotationBeanPostProcessor보다 앞에 있던 이유가 이것이다. 두 내장 후처리기는 PriorityOrdered이면서 MergedBeanDefinitionPostProcessor이기 때문에 처음에는 맨 앞에 등록됐다가 마지막 단계에서 뒤로 옮겨졌다. 맨 끝의 ApplicationListenerDetector도 같은 방식으로 마지막에 다시 붙는다.

    이 등록 단계에는 함정이 있다. 3단계에서 후처리기 A를 만들 때, A가 다른 빈 B에 의존하면 B도 그 자리에서 만들어진다. 그런데 그 순간 목록에는 아직 일부 후처리기만 들어 있다. B는 나머지 후처리기를 지나가지 못한 채 완성되어 저장소에 들어간다. 자동 프록시 생성기가 아직 등록되지 않았다면 B는 프록시가 되지 못한다. 스프링은 이런 빈을 발견하면 경고를 남기는 BeanPostProcessorChecker를 3단계의 맨 처음에 등록해 둔다. 실행 결과의 후처리기 목록 세 번째에 있던 그 클래스다.

    public class TraceAdvice implements MethodInterceptor {
    private final String label;

    public TraceAdvice(String label) {
        this.label = label;
    }

    @Override
    public String toString() {
        return "TraceAdvice" + label;
    }

    @Override
    public Object invoke(MethodInvocation invocation) throws Throwable {
        String sig = invocation.getMethod().getDeclaringClass().getSimpleName()
                + "." + invocation.getMethod().getName() + "()";
        System.out.println(label + " --> " + sig);
        try {
            return invocation.proceed();
        } finally {
            System.out.println(label + " <-- " + sig);
        }
    }

    public class TracingPostProcessor implements BeanPostProcessor {
    private final String basePackage;
    private final Advisor advisor;

    public TracingPostProcessor(String basePackage, Advisor advisor) {
        this.basePackage = basePackage;
        this.advisor = advisor;
    }

    @Override
    public Object postProcessAfterInitialization(Object bean, String beanName) {
        String packageName = bean.getClass().getPackageName();
        if (!packageName.startsWith(basePackage)) {
            return bean;                       // 대상 패키지가 아니면 원본 그대로
        }
        ProxyFactory factory = new ProxyFactory(bean);
        factory.addAdvisor(advisor);

    프록시 클래스 이름에서 05회의 규칙을 다시 확인할 수 있다. ProxyFactory의 기본 설정(proxyTargetClass=false)에서는 인터페이스가 있는 MemoryLoanRepository는 JDK 동적 프록시(jdk.proxy2.$Proxy12)가 되고, 인터페이스가 없는 서비스와 컨트롤러는 CGLIB 하위 클래스가 된다. $Proxy 뒤의 번호와 jdk.proxy2 같은 모듈 이름은 JVM이 그때그때 붙이는 것이라 실행 환경에 따라 다를 수 있다. 추적 출력에서 리포지토리 메서드가 LoanRepository.save()로 찍힌 것도 JDK 프록시이기 때문이다. JDK 프록시는 인터페이스의 Method 객체로 호출을 전달하므로 getDeclaringClass()가 인터페이스를 가리킨다.

    마지막 줄의 ping()은 추적되지 않았다. LoanService 객체는 분명 프록시인데도 그렇다. 후처리기는 "어떤 빈을 프록시로 만들지"를 패키지로 정했고, 프록시 안의 어드바이저는 "어떤 메서드에 어드바이스를 적용할지"를 메서드 이름 포인트컷으로 정했다. 두 판단이 서로 다른 장소에서, 서로 다른 기준으로 이루어진다는 점을 기억해 두자. 이 구조가 뒤에서 자동 프록시 생성기가 포인트컷 하나로 두 판단을 모두 하게 되는 이유와 연결된다.

    패키지로 거르는 조건을 빼면 어떻게 될까. 후처리기는 설정 클래스를 포함해 컨테이너의 모든 빈을 받는다. 스프링 부트 애플리케이션이라면 자동 구성이 등록한 수많은 빈도 이 후처리기를 지나간다. 그 빈들을 전부 프록시로 감싸면 쓸모없는 프록시가 생길 뿐 아니라, final 클래스처럼 CGLIB가 상속할 수 없는 클래스를 만나면 프록시 생성 자체가 실패한다. 그래서 후처리기는 반드시 "내가 처리할 빈"을 스스로 골라야 한다. 이 예제에서는 패키지 이름이 그 역할을 했다.

    빈 후처리기 — 정리

    직접 만든 후처리기로 얻은 것과 남은 것을 정리해 보자. 얻은 것은 두 가지다. 첫째, 프록시를 만드는 설정 코드가 빈 개수와 상관없이 후처리기 하나로 줄었다. @Bean 메서드마다 "실제 객체 생성 → 프록시 생성"을 반복할 필요가 없다. 둘째, 컴포넌트 스캔으로 등록되는 빈에도 프록시를 적용할 수 있게 되었다. 컨테이너가 직접 만든 객체도 후처리기를 지나가기 때문이다. 그리고 그 결과 실제 객체는 컨테이너에 빈으로 등록되지 않고 프록시만 등록된다. 실제 객체는 프록시 안의 타깃으로만 존재한다.

    남은 것도 있다. 후처리기의 "패키지 이름이 이것으로 시작하면"이라는 조건은 사실상 포인트컷이 하는 일, 즉 적용 대상을 고르는 일이다. 그런데 어드바이저 안에는 이미 포인트컷이 있다. 대상을 고르는 기준이 후처리기의 하드코딩된 조건과 어드바이저의 포인트컷 두 곳에 나뉘어 있는 셈이다. 어드바이저가 여러 개가 되면 문제가 커진다. 어드바이저마다 적용 대상이 다를 텐데, 후처리기가 그 모든 대상의 합집합을 직접 알고 있어야 한다.

    해법은 자연스럽다. 후처리기가 대상 선정 조건을 따로 갖지 말고, 컨테이너에 등록된 어드바이저들의 포인트컷에 물어보면 된다. "이 빈의 메서드 중 하나라도 어떤 어드바이저의 포인트컷에 맞으면 프록시로 만든다." 그러면 개발자는 어드바이저 빈만 등록하면 되고, 후처리기는 범용 장치가 된다. 스프링이 바로 이 후처리기를 제공한다.

    스프링이 제공하는 빈 후처리기1 — 자동 프록시 생성기의 등록

    스프링 부트에서 spring-boot-starter-aop를 의존성에 추가하는 것이 출발점이다. Maven Central에 공개된 3.5.x 버전의 POM을 보면 이 스타터는 spring-aop와 aspectjweaver를 함께 끌어온다. 클래스패스에 AspectJ 위버가 생기면 스프링 부트의 AopAutoConfiguration이 동작한다. Spring Boot 3.5.16 소스에서 이 자동 구성은 다음 구조다.

    @EnableAspectJAutoProxy는 @Import(AspectJAutoProxyRegistrar.class)를 달고 있고, 이 등록기는 AopConfigUtils.registerAspectJAnnotationAutoProxyCreatorIfNecessary를 호출한다. 그 결과 org.springframework.aop.config.internalAutoProxyCreator라는 이름으로 AnnotationAwareAspectJAutoProxyCreator의 빈 정의가 등록된다. 등록 시 역할은 인프라(ROLE_INFRASTRUCTURE), order 속성은 Ordered.HIGHEST_PRECEDENCE로 지정된다. 이 모든 일이 앞에서 본 refresh의 invokeBeanFactoryPostProcessors 단계, 즉 설정 클래스를 해석하는 시점에 일어나고, 다음 단계인 registerBeanPostProcessors에서 실제 객체가 만들어져 후처리기 목록에 들어간다.

    이 빈 이름이 고정되어 있다는 점이 중요하다. 자동 프록시 생성기를 등록하려는 곳은 여럿이다. @EnableTransactionManagement와 @EnableCaching이 쓰는 AutoProxyRegistrar는 AopConfigUtils.registerAutoProxyCreatorIfNecessary로 InfrastructureAdvisorAutoProxyCreator를 등록하려 한다. AopConfigUtils는 같은 이름의 정의가 이미 있으면 새로 만들지 않고 우선순위 목록을 비교해 더 높은 쪽의 클래스로 정의를 승격시킨다. 우선순위는 InfrastructureAdvisorAutoProxyCreator → AspectJAwareAdvisorAutoProxyCreator → AnnotationAwareAspectJAutoProxyCreator 순으로 높아진다. 결국 컨테이너에는 자동 프록시 생성기가 하나만 있고, 트랜잭션 어드바이저든 직접 등록한 어드바이저든 모두 그 하나가 처리한다. 한 빈에 프록시가 하나만 만들어지는 구조의 출발점이 여기다.

    자동 프록시 생성기 안에서 일어나는 일

    자동 프록시 생성기의 핵심은 AbstractAutoProxyCreator.postProcessAfterInitialization이 호출하는 wrapIfNecessary다. 6.2.19와 7.0.10 소스를 대조하며 따라가면 한 빈이 이 메서드를 지날 때 다음 순서로 판단이 이루어진다.

    3단계가 앞 실행 결과의 traceAdvisor (not proxied)를 설명한다. 어드바이저 자체가 프록시가 되면 프록시를 만드는 재료가 다시 프록시가 되는 꼴이니 제외한다. 자동 프록시 생성기의 상위 클래스인 ProxyProcessorSupport가 AopInfrastructureBean을 구현하므로 생성기 자신도 같은 규칙으로 빠진다. 컨테이너 내부 빈 다섯 개는 이유가 조금 다르다. 이들은 BeanFactoryPostProcessor나 BeanPostProcessor이거나 그 단계에서 쓰이는 빈이어서 자동 프록시 생성기가 목록에 들어가기 전에 이미 만들어졌다. 예를 들어 internalEventListenerFactory는 EventListenerMethodProcessor가 postProcessBeanFactory에서 getBeansOfType(EventListenerFactory.class, ...)로 꺼내기 때문에 빈 팩토리 후처리 단계에서 생성된다.

    4단계의 어드바이저 조회는 BeanFactoryAdvisorRetrievalHelper가 맡는다. 처음 조회할 때 Advisor 타입 빈의 이름 목록을 구해 cachedAdvisorBeanNames에 캐시하고, 이후에는 그 이름으로 getBean을 호출해 객체를 얻는다. 이름 목록에 있는 어드바이저가 지금 생성 중이면 건너뛴다. 어드바이저가 처음 필요해지는 시점, 즉 일반 빈 중 첫 번째 빈이 생성기를 지날 때 어드바이저 빈들이 만들어지는 것이다. 어드바이저도 일반 빈이므로 생성 과정에서 자기 의존성을 끌고 온다. 어드바이저가 무거운 의존성을 가지면 그 의존성들도 이 시점에 만들어진다는 점을 기억해 두자.

    5단계의 판정은 AopUtils.canApply(Pointcut, Class, boolean)에 있다. 이 메서드의 동작을 정확히 알아야 "왜 이 빈이 프록시가 됐지?"라는 질문에 답할 수 있다.

    1. 포인트컷의 ClassFilter로 클래스를 먼저 검사한다. 맞지 않으면 즉시 false.
    2. MethodMatcher가 MethodMatcher.TRUE이면 메서드를 볼 필요 없이 true.
    3. 그렇지 않으면 검사할 클래스 집합을 만든다. 원래 사용자 클래스(ClassUtils.getUserClass로 CGLIB 하위 클래스를 벗겨 낸 것)와 그 클래스가 구현한 모든 인터페이스다.
    4. 각 클래스에 대해 ReflectionUtils.getAllDeclaredMethods로 상위 클래스의 메서드까지 모두 꺼내, 메서드 매처에 하나씩 물어본다. 하나라도 맞으면 true.

    마지막 규칙이 결정적이다. 프록시 생성 여부는 "메서드 하나라도 맞는가"로 정해진다. LoanController에는 apply로 시작하는 메서드가 없으니 auditAdvisor는 걸러지고 traceAdvisor만 남았다. LoanService에는 apply가 있으므로 두 어드바이저가 모두 남았다. ping()이 제외되도록 표현식을 썼지만 같은 클래스의 apply()가 맞으므로 LoanService는 프록시가 된다. 설정 클래스 autoProxyMain.Config는 demo 패키지에 있어 traceAdvisor의 표현식에 맞지 않고, traceAdvisor()나 auditAdvisor() 같은 메서드 이름도 apply*에 맞지 않으니 어느 어드바이저도 남지 않아 원본으로 남았다.

    6단계의 ExposeInvocationInterceptor는 AspectJAwareAdvisorAutoProxyCreator.extendAdvisors가 넣는다. 적용 가능한 어드바이저 중에 AspectJ 어드바이스이거나 포인트컷이 AspectJExpressionPointcut인 것이 하나라도 있으면 목록 맨 앞에 추가한다(AspectJProxyUtils.makeAdvisorChainAspectJCapableIfNecessary). 이 인터셉터는 현재 진행 중인 MethodInvocation을 ThreadLocal에 넣어 두는 역할을 한다. AspectJ 방식의 어드바이스는 조인 포인트 정보를 이 스레드 로컬에서 꺼내 쓰기 때문에, 체인의 가장 바깥에서 먼저 실행되어야 한다. 01회에서 다룬 ThreadLocal이 스프링 AOP의 안쪽에서 이렇게 쓰이고 있다. 앞 예제의 traceAdvisor가 AspectJExpressionPointcut을 쓰므로 세 빈 모두에 이 인터셉터가 붙었다.

    7단계의 createProxy는 05회에서 직접 썼던 ProxyFactory를 그대로 쓴다. 생성기 자신이 ProxyConfig의 하위 클래스이므로 proxyFactory.copyFrom(this)로 proxyTargetClass 같은 설정을 복사하고, 어드바이저를 추가하고, 원본 빈을 SingletonTargetSource로 감싸 타깃으로 지정한 뒤 프록시를 얻는다. 결과는 advisedBeans에 TRUE로, 프록시 클래스는 proxyTypes에 기록된다. 자동 프록시 생성기는 결국 "어떤 빈에 어떤 어드바이저를 넣어 ProxyFactory를 돌릴지"를 자동으로 정하는 장치일 뿐, 프록시를 만드는 기술은 05회의 것과 같다.

    빈 하나가 자동 프록시 생성기를 지날 때 인프라 여부 → 후보 어드바이저 → 포인트컷 검사 → 프록시 생성으로 이어지는 분기. 위에서 아래로 흐르는 순서도. 맨 위 둥근 상자 "빈 도착". 다음 마름모 "인프라 빈인가?" — 오른쪽 "예" 화살표가 "원본 반환" 상자로 간다. "아니오"는 아래 사각형 "Advisor 빈 모두 조회"로 간다. 그 아래 사각형 "포인트컷으로 검사"가 있고 옆에 작은 메모 "클래스 필터 → 메서드 하나라도 일치?". 다음 마름모 "남은 어드바이저가 있는가?" — "아니오"는 오른쪽 "원본 반환"으로, "예"는 아래로 사각형 "순서대로 정렬"을 거쳐 마지막 굵은 테두리 상자 "ProxyFactory로 프록시 1개 생성"에 닿는다. 마지막 상자에서 오른쪽으로 화살표 "프록시를 빈으로 등록". 단색 선, 결정 마름모는 연노랑, 최종 상자는 청록색. 프록시 생성 여부는 어드바이저의 포인트컷이 정한다. 메서드 하나만 맞아도 빈 전체가 프록시가 된다.

    하나의 프록시, 여러 Advisor 적용

    앞 실행 결과에서 loanService에는 어드바이저가 두 개(인프라 인터셉터까지 세 개) 들어 있었고, 프록시 클래스는 LoanService$$SpringCGLIB$$0 하나였다. 어드바이저마다 프록시를 하나씩 만들어 겹겹이 감싸지 않는다. wrapIfNecessary가 적용 가능한 어드바이저를 모두 모은 뒤 ProxyFactory를 한 번만 돌리기 때문이다. 05회에서 ProxyFactory에 어드바이저를 여러 개 추가하면 프록시 하나가 여러 어드바이저를 가진다고 했던 바로 그 구조다.

    이것을 직접 만든 후처리기 방식과 비교하면 차이가 분명하다. 부가 기능마다 별도의 후처리기를 만들어 각자 ProxyFactory로 감싸면, 두 번째 후처리기는 첫 번째 후처리기가 반환한 프록시를 입력으로 받아 그 프록시를 다시 감싼다. 프록시가 프록시를 감싸는 양파 구조가 되고, 메서드 호출 한 번이 프록시 디스패치를 두 번 거친다. 자동 프록시 생성기는 컨테이너에 하나뿐이고 모든 어드바이저를 한 자리에서 고르므로 이런 중첩이 생기지 않는다. 앞에서 본 생성기 승격 규칙 덕분에 @Transactional을 처리하는 트랜잭션 어드바이저와 직접 만든 어드바이저도 같은 생성기가 처리하므로 역시 프록시 하나에 모인다.

    여러 어드바이저가 한 프록시에 들어가면 순서가 문제가 된다. Ordered 인터페이스의 getOrder()나 @Order 값이 작을수록 앞에 오고, 순서를 지정하지 않은 것은 가장 낮은 우선순위로 취급되어 뒤로 간다. 확인을 위해 같은 패키지에 적용되는 어드바이저 세 개를 일부러 순서를 섞어 등록했다.

    순환 참조와 getEarlyBeanReference — 객체를 바꾸는 후처리기의 숨은 비용

    후처리기가 객체를 다른 객체로 바꿀 수 있다는 능력에는 대가가 있다. 순환 참조(circular reference)를 만나면 "이미 다른 빈에 넘겨준 참조"와 "최종 등록될 객체"가 달라질 수 있기 때문이다. 컨테이너가 순환 참조를 푸는 방법부터 보자. doCreateBean은 객체를 생성한 직후, 의존관계를 주입하기 전에 addSingletonFactory(beanName, () -> getEarlyBeanReference(beanName, mbd, bean))를 호출한다. "아직 주입도 초기화도 안 된 이 객체를 누가 급히 달라고 하면 이 람다로 꺼내 주라"는 통로를 열어 두는 것이다. A를 만드는 중에 B가 필요하고, B를 만드는 중에 다시 A가 필요해지면, B는 이 통로로 미완성 A의 참조를 받아 완성된다.

    문제는 A가 그 뒤 초기화를 마치고 after 후처리 단계에서 프록시로 바뀌는 경우다. B는 이미 원본 A를 들고 있는데 컨테이너에는 A의 프록시가 등록된다. B를 통해 A를 호출하면 부가 기능이 적용되지 않는다. 스프링은 이 상황을 그냥 넘기지 않는다. doCreateBean의 끝에서 "조기 참조가 꺼내졌는가", "최종 객체가 원본과 다른가", "조기 참조를 받아 간 빈이 있는가"를 확인하고, 셋 다 해당하면 BeanCurrentlyInCreationException을 던진다(allowRawInjectionDespiteWrapping을 켜지 않은 기본 설정에서). 직접 확인해 보자. 서로를 필드로 주입받는 두 빈을 만들고, 앞에서 만든 TracingPostProcessor가 둘 다 감싸게 했다.

    package com.example.cycle;

@Component @Lazy
public class Payment {
    @Autowired Refund refund;   // 순환 참조: Payment -> Refund -> Payment
    public void pay() {}
}

@Component @Lazy
public class Refund {
    @Autowired Payment payment;
    public void refund() {}
    public Payment payment() { return payment; }
}

// 직접 만든 후처리기로 감싸는 설정
@Configuration
@ComponentScan("com.example.cycle")
static class HandMadeConfig {
    @Bean
    static TracingPostProcessor tracingPostProcessor() {
        return new TracingPostProcessor("com.example.cycle",
                new DefaultPointcutAdvisor(new TraceAdvice("[trace]")));
    }
}

// 자동 프록시 생성기로 감싸는 설정

    직접 만든 후처리기의 경우를 추적해 보자. getBean(Payment.class) → Payment 생성, 조기 참조 통로 등록 → refund 필드 주입을 위해 Refund 생성 → Refund의 payment 필드 주입 시 Payment가 생성 중이므로 통로로 조기 참조를 꺼냄. 이때 getEarlyBeanReference는 SmartInstantiationAwareBeanPostProcessor들에게만 물어보는데, TracingPostProcessor는 그 인터페이스를 구현하지 않았으니 원본 Payment가 그대로 넘어간다. Refund는 완성되어 프록시가 된다(첫 줄). 이어서 Payment가 초기화를 마치고 프록시가 된다(둘째 줄). 마지막 검사에서 "원본 payment가 refund에 주입되었는데 최종 객체는 감싸졌다"가 성립해 예외가 났다.

    자동 프록시 생성기는 이 문제를 해결하도록 만들어져 있다. AbstractAutoProxyCreator는 SmartInstantiationAwareBeanPostProcessor를 구현하고, getEarlyBeanReference에서 빈을 earlyBeanReferences 맵에 기록한 뒤 그 자리에서 wrapIfNecessary를 호출해 프록시를 돌려준다. 그래서 Refund는 처음부터 Payment의 프록시를 주입받는다. 나중에 Payment가 after 후처리 단계에 오면 postProcessAfterInitialization은 earlyBeanReferences에서 이 빈을 꺼내 보고 이미 감쌌던 빈임을 알아 원본을 그대로 반환한다. 원본이 반환되었으니 doCreateBean의 검사에서 "최종 객체가 원본과 같다"가 되고, 이때 컨테이너는 최종 객체로 조기 참조, 즉 이미 만들어 둔 프록시를 채택한다. 결과적으로 컨테이너에 등록된 객체와 Refund가 가진 객체가 같은 프록시가 된다(same object? = true). 앞 절 흐름도의 1단계 "조기 참조 확인"이 바로 이 장치다.

    실험에서 두 빈에 @Lazy를 붙이고 getBean을 직접 호출한 이유가 있다. 6.2.19의 DefaultListableBeanFactory.preInstantiateSingleton은 시작 시점의 사전 생성 중에 BeanCurrentlyInCreationException이 나면 이를 잡아 "currently initialized by other thread - skipping it in mainline thread"라는 INFO 로그만 남기고 넘어가는 catch 블록을 갖고 있다. 그래서 사전 생성 경로에서는 이 규칙이 실행 결과만으로 잘 드러나지 않는다. 예외가 호출자에게 그대로 전달되도록 지연 생성으로 두고 직접 조회했다.

    실무에서 이 문제를 만날 가능성은 스프링 부트에서 낮아졌다. Spring Boot 3.5.16 소스의 ApplicationProperties에서 allowCircularReferences 필드의 기본값은 false이고, SpringApplication은 이 값을 빈 팩토리의 setAllowCircularReferences에 넘긴다. 즉 스프링 부트 애플리케이션은 기본적으로 순환 참조 자체를 허용하지 않으며, spring.main.allow-circular-references=true로 켜야 위의 조기 참조 경로가 열린다. 반면 스프링 프레임워크의 AbstractAutowireCapableBeanFactory 자체의 기본값은 true여서, 위 실험처럼 부트 없이 쓰면 순환 참조가 허용된다. 직접 후처리기를 만들어 객체를 바꿔치기한다면, 순환 참조가 허용된 환경에서는 getEarlyBeanReference도 함께 구현해야 한다는 점을 기억하자. 그래서 실무에서는 프록시용 후처리기를 직접 만들기보다 자동 프록시 생성기에 어드바이저를 맡기는 편이 안전하다.

    흔한 오해와 함정

    "후처리기는 내가 신경 쓰는 빈만 지나간다"

    아니다. 후처리기가 등록된 뒤에 만들어지는 컨테이너의 모든 빈이 지나간다. 예제 코드2에서 설정 클래스가 before와 after를 지나간 것이 그 증거다. 스프링 부트 애플리케이션에서는 자동 구성이 등록한 수많은 빈이 같이 지나간다. 조건 없이 모든 빈을 감싸는 후처리기는 쓸모없는 프록시를 만들거나 final 클래스에서 실패한다. 후처리기 안에는 반드시 대상 선정 조건이 있어야 하고, 그 조건을 어드바이저의 포인트컷에 위임한 것이 자동 프록시 생성기다.

    "후처리기에서 null을 반환하면 그 빈은 등록되지 않는다"

    아니다. 6.2.19의 applyBeanPostProcessorsBeforeInitialization과 applyBeanPostProcessorsAfterInitialization은 후처리기가 null을 반환하면 그때까지의 결과를 반환하고 나머지 후처리기를 건너뛴다. 빈은 직전 객체로 등록되고, 목록에서 뒤에 있던 후처리기는 그 빈을 보지 못한다. 대상이 아닌 빈은 null이 아니라 받은 객체를 그대로 반환해야 한다.

    "후처리기를 @Bean으로 등록하는 방법은 다른 빈과 같다"

    인스턴스 메서드로 선언하면 설정 클래스가 후처리기 등록 단계에서 앞당겨 만들어지고, 후처리기의 의존 대상도 함께 앞당겨진다. 이 빈들은 아직 등록되지 않은 후처리기를 지나가지 못해 자동 프록시 대상에서 빠진다. 앞의 실험에서 리포지토리만 프록시가 되지 않은 것처럼, 이 문제는 예외 없이 경고 로그 한 줄로만 드러난다. 후처리기 @Bean 메서드는 static으로, 가능하면 의존성 없이 선언한다.

    "프록시가 됐으니 모든 메서드에 어드바이스가 적용된다"

    프록시 생성은 "메서드 하나라도 맞는가"로 정해지고, 어드바이스 적용은 호출된 메서드마다 다시 판정된다. LoanService가 프록시인데 ping()에 추적이 붙지 않은 것이 그 예다. 반대로 어드바이스가 적용되지 않는 메서드도 프록시를 거쳐 호출되므로 체인 계산(첫 호출 뒤에는 캐시 조회)과 프록시 디스패치 비용은 든다.

    "어드바이저마다 프록시가 하나씩 생긴다"

    자동 프록시 생성기는 컨테이너에 하나뿐이고(internalAutoProxyCreator라는 고정 이름과 승격 규칙), 한 빈에 적용될 어드바이저를 모두 모아 프록시를 하나 만든다. 어드바이저의 개수는 프록시 안 체인의 길이를 바꿀 뿐이다. 프록시 위에 프록시가 쌓이는 것은 서로 다른 후처리기가 각자 객체를 감쌀 때 생긴다.

    "프록시가 등록됐으니 클래스 안에서 자기 메서드를 불러도 어드바이스가 적용된다"

    프록시는 외부에서 들어오는 호출만 가로챈다. 타깃 객체 안에서 this.otherMethod()로 부르는 호출은 프록시를 거치지 않는다. 이 내부 호출 문제와, JDK 프록시와 CGLIB 프록시의 타입 차이 때문에 생기는 주입·캐스팅 문제는 10회에서 따로 다룬다.

    정리 — 다음 회차와의 연결

    이 회차의 흐름을 한 줄로 이으면 이렇다. 컨테이너는 빈을 만든 뒤 등록하기 전에 후처리기에게 객체를 넘기고, 후처리기가 돌려준 객체를 빈으로 등록한다. 이 훅에 프록시 생성을 걸면 설정 코드 반복 없이, 컴포넌트 스캔된 빈까지 프록시로 바꿀 수 있다. 스프링은 이 후처리기를 범용화해 자동 프록시 생성기로 제공하며, 생성기는 컨테이너의 어드바이저 빈을 모아 포인트컷으로 프록시 생성 여부를 정하고, 프록시 안에서는 같은 포인트컷으로 호출마다 어드바이스 적용 여부를 정한다.

    남은 것은 어드바이저를 만드는 방식이다. 지금은 AspectJExpressionPointcut과 MethodInterceptor를 DefaultPointcutAdvisor로 묶어 손으로 빈 등록을 했다. AnnotationAwareAspectJAutoProxyCreator라는 이름의 "AnnotationAware"가 가리키는 기능, 즉 @Aspect 클래스의 @Around 같은 메서드를 찾아 어드바이저로 변환해 주는 기능이 07회의 주제다. 이 생성기의 findCandidateAdvisors가 상위 클래스의 결과에 aspectJAdvisorsBuilder.buildAspectJAdvisors()의 결과를 더하는 부분이 그 입구다. 포인트컷 표현식의 문법은 09회, 실무에서 프록시가 일으키는 문제들은 10회로 이어진다.
    빈 후처리기(BeanPostProcessor)
    컨테이너가 빈 객체를 만든 뒤 등록하기 전에 객체를 넘겨받아 조작하거나 다른 객체로 바꿔 반환할 수 있는 확장 지점. 반환된 객체가 그 이름의 빈이 된다.
    before / after 초기화
    postProcessBeforeInitialization은 초기화 콜백 전, postProcessAfterInitialization은 후에 호출된다. 프록시 생성은 완성된 객체를 다루는 after 단계에서 한다.
    후처리기 등록 순서
    registerBeanPostProcessors가 PriorityOrdered → Ordered → 나머지 순으로 등록하고 내부 후처리기를 끝으로 다시 옮긴다. 이 단계에서 앞당겨 만들어진 빈은 모든 후처리를 받지 못한다.
    static @Bean 후처리기
    후처리기 @Bean 메서드를 static으로 선언하면 설정 클래스 객체를 앞당겨 만들 필요가 없어 다른 빈이 자동 프록시 대상에서 빠지는 일을 막는다.
    자동 프록시 생성기
    internalAutoProxyCreator라는 고정 이름으로 등록되는 후처리기. 스프링 부트는 AspectJ가 클래스패스에 있으면 AnnotationAwareAspectJAutoProxyCreator를 CGLIB 기본으로 등록한다.
    wrapIfNecessary
    인프라 빈 제외 → 어드바이저 빈 수집 → 포인트컷으로 선별 → 확장·정렬 → ProxyFactory로 프록시 1개 생성의 순서로 빈 하나를 처리한다.
    포인트컷의 두 쓰임
    생성 단계에서는 "메서드 하나라도 맞는가"로 프록시 생성 여부를, 사용 단계에서는 호출된 메서드마다 어드바이스 적용 여부를 판정한다.
    하나의 프록시, 여러 어드바이저

    조기 참조(getEarlyBeanReference)
    순환 참조 중 미완성 빈을 넘길 때 호출되는 훅. 자동 프록시 생성기는 여기서 미리 프록시를 만들어 원본이 다른 빈에 새어 나가지 않게 한다.

    실무에서 "AOP가 적용되지 않는다"는 문의의 상당수는 빈 후처리기의 규칙으로 설명된다. 대상 빈이 후처리기 등록 단계에서 앞당겨 만들어졌다면 시작 로그에 "is not eligible for getting processed by all BeanPostProcessors" 경고가 남아 있을 것이다. 직접 만든 후처리기나 설정이 어떤 빈에 의존하고 있는지, 후처리기 @Bean 메서드가 static인지부터 확인한다. 경고가 없다면 포인트컷이 그 빈의 메서드에 맞는지, 그리고 호출이 프록시를 거치는지(내부 호출인지)를 확인한다. AopUtils.isAopProxy와 ((Advised) bean).getAdvisors()로 프록시 여부와 어드바이저 목록을 직접 찍어 보는 것이 가장 빠르다.

    반대로 "예상하지 못한 빈이 프록시가 되었다"는 문제는 포인트컷이 너무 넓을 때 생긴다. 이름 패턴 포인트컷은 클래스를 가리지 않으므로 라이브러리나 자동 구성의 빈까지 프록시로 만들 수 있고, 그 빈이 final 클래스이거나 타입으로 주입받는 곳이 있으면 시작 단계에서 실패할 수 있다. 포인트컷은 패키지나 타입으로 범위를 좁히는 것을 기본으로 삼는다.

    후처리기를 직접 만들지 판단할 때는 목적을 본다. 객체를 바꾸지 않고 검사하거나 표시만 하는 후처리기(예: 특정 애노테이션이 붙은 빈을 목록에 모으기)는 직접 만들어도 부담이 적다. 객체를 프록시로 바꾸는 일이라면 자동 프록시 생성기에 어드바이저를 맡기는 편이 낫다. 직접 만든 후처리기는 순환 참조 시 조기 참조 처리, 다른 생성기와의 중첩 프록시, 정렬 문제를 모두 스스로 감당해야 하기 때문이다.

     빈 후처리기의 postProcessAfterInitialization이 원래 객체 대신 새 객체를 반환했다. 이후 컨테이너의 동작으로 옳은 것은? 빈 정의의 선언 타입과 다르므로 컨테이너가 예외를 던진다. 반환된 객체가 그 이름의 빈으로 등록되고, 타입 조회도 그 객체의 실제 타입을 기준으로 한다. 원래 객체와 새 객체가 모두 같은 이름으로 등록되어 타입에 따라 골라 쓸 수 있다. 새 객체는 등록되지만 의존관계 주입에는 원래 객체가 쓰인다. 컨테이너는 후처리기의 반환값을 검증 없이 그 이름의 싱글톤으로 저장한다. 이미 만들어진 싱글톤의 타입 판정은 실제 객체로 하므로, 실험에서 getBean(Lamp.class)은 실패하고 getBean(SmartLamp.class)은 성공했다. 원래 객체는 등록되지 않으며, 다른 빈은 후처리가 끝난 최종 객체를 주입받는다. 후처리기를 일반(static이 아닌) @Bean 메서드로 선언하고 매개변수로 서비스 빈 S를 받게 했다. 그 결과로 가장 정확한 설명은? S는 후처리기보다 늦게 만들어지므로 아무 문제가 없다. 후처리기가 S를 주입받는 순간 S가 프록시로 바뀐다. 설정 클래스와 S가 후처리기 등록 단계에서 앞당겨 만들어져, 아직 등록되지 않은 후처리기(자동 프록시 생성기 포함)를 거치지 못할 수 있다. 스프링이 컴파일 오류로 이 선언을 막는다. 후처리기 객체를 만들려면 인스턴스 메서드를 가진 설정 클래스와 매개변수 S가 먼저 필요하다. 이들은 후처리기 목록이 다 채워지기 전에 완성되므로 일부 후처리를 받지 못하고, BeanPostProcessorChecker가 경고를 남긴다. 실험에서 리포지토리만 프록시가 되지 않았다. 컴파일 오류는 없다. 자동 프록시 생성기가 어떤 빈을 프록시로 만들지 결정하는 기준은? 어드바이저의 포인트컷에 그 빈의 클래스가 맞고, 메서드 중 하나라도 맞으면 프록시를 만든다. 모든 메서드가 포인트컷에 맞아야 프록시를 만든다. 빈에 @Aspect가 붙어 있어야 프록시를 만든다. 인터페이스를 구현한 빈만 프록시로 만든다. AopUtils.canApply는 클래스 필터를 통과한 뒤 사용자 클래스와 모든 인터페이스의 메서드를 훑어 하나라도 맞으면 true를 반환한다. 모든 메서드가 맞을 필요는 없으며, 맞지 않는 메서드는 호출 시점의 두 번째 판정에서 그 어드바이저의 어드바이스가 빠진 채 타깃으로 간다. @Aspect는 어드바이저를 만드는 방법이고, 인터페이스 유무는 프록시 기술 선택에 영향을 줄 뿐이다. 한 빈에 어드바이저 세 개의 포인트컷이 모두 맞았다. 자동 프록시 생성기가 만드는 결과는? 어드바이저마다 프록시를 하나씩 만들어 세 겹으로 감싼다. order 값이 가장 작은 어드바이저 하나만 적용한다. 세 어드바이저를 각각 다른 빈 이름으로 등록한다. 프록시 하나를 만들고 세 어드바이저를 정렬된 순서의 체인으로 넣는다. wrapIfNecessary는 적용 가능한 어드바이저를 모두 모아 정렬한 뒤 ProxyFactory를 한 번 돌린다. 프록시 안의 ReflectiveMethodInvocation이 인터셉터 목록을 순서대로 호출하므로 order가 작은 어드바이저가 바깥에서 실행된다. 프록시가 겹겹이 쌓이는 것은 서로 다른 후처리기가 각자 감쌀 때의 일이다. 순환 참조가 허용된 환경에서 자동 프록시 생성기는 순환 참조된 빈도 문제없이 프록시로 만든다. 그 이유는? 순환 참조가 감지되면 해당 빈을 프록시 대상에서 제외하기 때문이다. getEarlyBeanReference에서 조기 참조를 요청받는 즉시 프록시를 만들어 넘기고, 이후 after 단계에서는 같은 빈을 다시 감싸지 않기 때문이다. after 단계에서 만든 프록시로 다른 빈의 필드를 다시 주입하기 때문이다. 순환 참조된 빈은 항상 JDK 동적 프록시로 만들기 때문이다. AbstractAutoProxyCreator는 SmartInstantiationAwareBeanPostProcessor로서 조기 참조 단계에서 wrapIfNecessary를 호출해 프록시를 넘기고, earlyBeanReferences에 기록해 둔다. after 단계에서는 기록을 보고 원본을 그대로 반환하며, doCreateBean은 이미 만든 프록시를 최종 객체로 채택한다. 주입된 필드를 나중에 다시 바꾸는 동작은 없다.
    빈 후처리기(BeanPostProcessor)
    컨테이너가 만든 빈 객체를 초기화 전후로 넘겨받아 조작하거나 대체할 수 있는 스프링의 확장 인터페이스.
    빈 팩토리 후처리기(BeanFactoryPostProcessor)
    빈 객체가 아니라 빈 정의(설정 메타데이터)를 읽고 수정하는 확장 인터페이스. 일반 빈이 만들어지기 전에 실행된다.
    자동 프록시 생성기(auto proxy creator)
    컨테이너의 어드바이저를 찾아 포인트컷에 맞는 빈을 자동으로 프록시로 바꾸는 빈 후처리기. AbstractAutoProxyCreator의 하위 클래스들이다.
    어드바이저(Advisor)
    포인트컷 하나와 어드바이스 하나를 묶은 객체. 자동 프록시 생성기는 어드바이저 단위로 적용 여부를 판단한다.
    인프라 빈(infrastructure bean)
    Advice, Pointcut, Advisor, AopInfrastructureBean처럼 AOP를 구성하는 빈. 자동 프록시 대상에서 제외된다.
    조기 참조(early bean reference)
    순환 참조를 풀기 위해 생성 중인 빈을 주입 완료 전에 다른 빈에 넘겨주는 참조. SmartInstantiationAwareBeanPostProcessor.getEarlyBeanReference가 이 참조를 바꿀 수 있다.
    ExposeInvocationInterceptor
    현재 메서드 호출 정보(MethodInvocation)를 ThreadLocal에 노출하는 인터셉터. AspectJ 방식 어드바이저가 있으면 체인 맨 앞에 추가된다.
    순환 참조(circular reference)
