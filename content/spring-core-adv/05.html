    프록시 기술이 둘이면 코드도 둘이 된다

    04회에서 실행 중에 프록시 클래스를 만들어 내는 두 가지 기술을 보았다. JDK 동적 프록시(JDK dynamic proxy)는 인터페이스를 구현한 $Proxy 클래스를 만들고 모든 호출을 java.lang.reflect.InvocationHandler의 invoke로 보낸다. CGLIB는 대상 클래스를 상속한 하위 클래스를 만들고 호출을 net.sf.cglib.proxy.MethodInterceptor(스프링 안에서는 org.springframework.cglib.proxy.MethodInterceptor)의 intercept로 보낸다. 둘 다 "부가 기능을 한 곳에 모은다"는 목적은 같지만, 부가 기능을 담는 그릇의 타입이 다르다.

    이 차이가 실제 코드에서 어떤 곤란함을 만드는지 따져 보자. 로그 추적 같은 부가 기능을 애플리케이션 전체에 붙이고 싶다고 하자. 어떤 객체는 인터페이스를 구현하고 있고, 어떤 객체는 인터페이스 없이 구체 클래스만 있다. 그러면 같은 로그 로직을 InvocationHandler 버전과 CGLIB MethodInterceptor 버전으로 두 번 써야 하고, 객체마다 "이건 인터페이스가 있으니 JDK, 이건 없으니 CGLIB"를 사람이 판단해 생성 코드를 갈라 써야 한다. 메서드 이름에 따라 부가 기능을 거르는 조건(04회에서 핸들러 안에 패턴 검사를 넣었던 것)도 두 그릇에 각각 들어간다.

    문제를 정리하면 세 가지다. 첫째, 프록시 기술 선택을 사람이 하지 않게 하고 싶다. 둘째, 부가 기능 로직을 기술과 무관한 하나의 타입으로 쓰고 싶다. 셋째, "어떤 메서드에 적용할지"라는 판단을 부가 기능 로직과 분리해 따로 바꿀 수 있게 하고 싶다. 스프링은 첫째와 둘째를 프록시 팩토리(ProxyFactory)와 어드바이스(Advice)로, 셋째를 포인트컷(Pointcut)과 어드바이저(Advisor)로 푼다. 이 회차는 이 네 가지가 어떻게 맞물리는지, 그리고 그 아래에서 실제로 어떤 클래스가 어떤 순서로 호출되는지를 따라간다.

    이 회차의 실행 결과는 원고를 쓰면서 JDK 21.0.13(Temurin)과 Spring Framework 6.2.19(spring-aop, spring-core, spring-context 등)로 직접 돌려 얻었다. 인용한 스프링 내부 코드는 GitHub의 6.2.x 브랜치 소스에서 가져왔다. JdkDynamicAopProxy, CglibAopProxy 같은 클래스는 패키지 비공개 구현이라 버전에 따라 바뀔 수 있다. 프록시 클래스 이름의 번호($Proxy0, $Proxy8)와 해시값은 실행 환경에 따라 달라진다.

    프록시 팩토리 — 소개

    org.springframework.aop.framework.ProxyFactory는 "대상 객체와 부가 기능을 주면 알맞은 프록시를 만들어 주는" 객체다. 사용자는 대상(target)을 넘기고 부가 기능을 등록한 뒤 getProxy()를 부르기만 한다. JDK 프록시를 쓸지 CGLIB를 쓸지는 팩토리가 대상의 모양을 보고 정한다. 스프링 레퍼런스는 이 방식을 "Spring IoC에 의존하지 않고 Spring AOP를 쓸 수 있게 해 준다"고 소개한다. 컨테이너 없이 main 메서드 하나로도 돌아간다는 뜻이고, 이 회차의 예제도 대부분 그렇게 돌린다.

    둘째 문제, 부가 기능을 담는 그릇은 AOP 얼라이언스(AOP Alliance)라는 오래된 공용 인터페이스 묶음에서 가져왔다. 핵심은 org.aopalliance.intercept.MethodInterceptor 하나다. 이 인터페이스에는 메서드가 하나뿐이다.

    // spring-aop-6.2.19.jar 안의 org.aopalliance 패키지 (javap 결과를 소스 형태로 옮김)
public interface Advice { }                                   // org.aopalliance.aop — 표시용, 메서드 없음
public interface Interceptor extends Advice { }               // org.aopalliance.intercept
public interface MethodInterceptor extends Interceptor {
    Object invoke(MethodInvocation invocation) throws Throwable;
}

public interface Joinpoint {
    Object proceed() throws Throwable;     // 다음 단계로 진행
    Object getThis();                      // 대상 객체
    AccessibleObject getStaticPart();
}
public interface Invocation extends Joinpoint { Object[] getArguments(); }
public interface MethodInvocation extends Invocation { Method getMethod(); }

    읽어 보면 04회의 두 그릇보다 단순하다. InvocationHandler.invoke(proxy, method, args)나 CGLIB의 intercept(obj, method, args, methodProxy)는 "대상을 어떻게 호출할지"를 핸들러가 직접 알아야 했다. 대상 객체 참조를 필드로 들고 있다가 method.invoke(target, args)를 부르거나 methodProxy.invoke(target, args)를 불러야 했다. 반면 MethodInterceptor.invoke가 받는 MethodInvocation은 대상 호출 방법을 이미 품고 있어서, 어드바이스는 proceed()만 부르면 된다. 대상이 무엇인지, 프록시가 어느 기술로 만들어졌는지 몰라도 된다.

    이름이 같은 MethodInterceptor가 둘 있다. 어드바이스로 쓰는 것은 org.aopalliance.intercept.MethodInterceptor이고, org.springframework.cglib.proxy.MethodInterceptor는 CGLIB의 콜백 타입이다. IDE 자동 import가 엉뚱한 쪽을 고르면 addAdvice에 넘길 수 없다는 컴파일 오류가 난다. 이 회차의 예제는 모두 AOP 얼라이언스 쪽을 쓴다.

    그러면 기술마다 다른 두 그릇은 어디로 갔을까. 스프링이 대신 구현해 두었다. JDK 프록시용으로는 JdkDynamicAopProxy가 InvocationHandler를 구현하고, CGLIB용으로는 CglibAopProxy 안의 DynamicAdvisedInterceptor가 CGLIB의 MethodInterceptor를 구현한다(javap로 확인한 6.2.19의 선언: final class JdkDynamicAopProxy implements AopProxy, InvocationHandler, Serializable, class CglibAopProxy$DynamicAdvisedInterceptor implements org.springframework.cglib.proxy.MethodInterceptor, Serializable). 둘은 하는 일이 같다. 이번 호출에 적용할 어드바이스 목록을 구해서 ReflectiveMethodInvocation이라는 MethodInvocation 구현체를 만들고 proceed()를 부른다. 사용자가 쓴 어드바이스는 그 체인 안에서 실행된다.

    클래스 계층도 한 번 보아 두면 뒤에서 덜 헷갈린다. ProxyFactory는 ProxyCreatorSupport를, 그것은 AdvisedSupport를, 그것은 ProxyConfig를 상속한다. ProxyConfig에는 proxyTargetClass, optimize, opaque, exposeProxy, frozen 같은 불리언 설정이 있고(6.2.x 소스에서 모두 기본값 false), AdvisedSupport에는 대상(TargetSource), 프록시할 인터페이스 목록, 어드바이저 목록(advisors 필드, 타입은 List), 메서드별 체인 캐시가 있다. 즉 ProxyFactory는 "설정을 담는 그릇"이면서 "프록시를 만드는 공장"이다. 이 사실이 뒤에서 "프록시를 만든 뒤 설정을 바꾸면 이미 만든 프록시도 바뀐다"는 결과로 이어진다.

    프록시 팩토리 — 예제 코드 1: 인터페이스가 있는 대상

    먼저 인터페이스가 있는 대상부터 프록시로 감싸 본다. 인터페이스 Greeter와 구현체 GreeterImpl, 그리고 호출 전후에 한 줄씩 찍는 어드바이스 LogAdvice를 준비한다. self()는 자기 자신(this)을 돌려주는 메서드인데, 뒤에서 프록시가 반환값을 어떻게 다루는지 보려고 넣었다.

    package demo;

public interface Greeter {
    String greet(String name);
    Greeter self();
}
    package demo;

public class GreeterImpl implements Greeter {
    @Override
    public String greet(String name) {
        System.out.println("  target.greet(" + name + ")");
        return "hello " + name;
    }

    @Override
    public Greeter self() {
        return this;
    }
}
    package demo;

import org.aopalliance.intercept.MethodInterceptor;   // CGLIB의 MethodInterceptor가 아니다
import org.aopalliance.intercept.MethodInvocation;

public class LogAdvice implements MethodInterceptor {
    @Override
    public Object invoke(MethodInvocation invocation) throws Throwable {
        System.out.println("LogAdvice 시작: " + invocation.getMethod().getName()
                + " (" + invocation.getClass().getSimpleName() + ")");
        Object result = invocation.proceed();          // 다음 어드바이스 또는 진짜 대상으로
        System.out.println("LogAdvice 종료: " + result);
        return result;
    }
}

    LogAdvice에는 대상 객체 필드가 없다. 04회의 InvocationHandler 구현은 생성자로 대상을 받아 필드에 두었는데, 여기서는 그럴 필요가 없다. 대상은 ProxyFactory가 알고 있고, invocation.proceed()가 그 대상까지 호출을 이어 준다. 그래서 같은 LogAdvice 인스턴스 하나를 여러 프록시에 나눠 걸어도 된다. 스프링 레퍼런스는 이처럼 대상의 상태에 의존하지 않고 여러 대상이 공유하는 어드바이스를 클래스별(per-class) 어드바이스라고 부르고, 가장 흔히 쓰이는 형태라고 설명한다.

    package demo;

import java.util.Arrays;
import org.springframework.aop.framework.Advised;
import org.springframework.aop.framework.ProxyFactory;
import org.springframework.aop.support.AopUtils;

public class InterfaceProxyDemo {
    public static void main(String[] args) {
        GreeterImpl target = new GreeterImpl();
        ProxyFactory factory = new ProxyFactory(target);   // 대상의 인터페이스를 자동으로 수집
        factory.addAdvice(new LogAdvice());
        Greeter proxy = (Greeter) factory.getProxy();

        System.out.println("class      = " + proxy.getClass().getName());
        System.out.println("interfaces = " + Arrays.toString(proxy.getClass().getInterfaces()));
        System.out.println("aop=" + AopUtils.isAopProxy(proxy)
                + " jdk=" + AopUtils.isJdkDynamicProxy(proxy)
                + " cglib=" + AopUtils.isCglibProxy(proxy));

        System.out.println(proxy.greet("kim"));
        System.out.println("self()==proxy ? " + (proxy.self() == proxy));
        System.out.println("advisors = " + Arrays.toString(((Advised) proxy).getAdvisors()));
    }
}

    한 줄씩 읽어 보자. 첫 줄의 jdk.proxy1.$Proxy0는 04회에서 본 JDK 동적 프록시 클래스다. ProxyFactory 생성자가 하는 일은 6.2.x 소스에서 단 두 줄이다: setTarget(target)과 setInterfaces(ClassUtils.getAllInterfaces(target)). 대상이 구현한 인터페이스를 상위 클래스까지 훑어 전부 모으고, 그 목록이 비어 있지 않으니 JDK 프록시가 선택되었다. 선택 규칙은 다음 절에서 소스로 정확히 본다.

    둘째 줄이 흥미롭다. 프록시 클래스는 Greeter만이 아니라 SpringProxy, Advised, DecoratingProxy도 구현한다. 이 셋은 AopProxyUtils.completeProxiedInterfaces가 덧붙인다. SpringProxy는 메서드가 없는 표시용 인터페이스로, "스프링이 만든 프록시"라는 표지다. 셋째 줄의 AopUtils.isAopProxy는 바로 이 표지를 본다. 6.2.x 소스에서 isJdkDynamicProxy는 object instanceof SpringProxy이면서 Proxy.isProxyClass(object.getClass())인지를, isCglibProxy는 SpringProxy이면서 클래스 이름에 "$$"(ClassUtils.CGLIB_CLASS_SEPARATOR)가 들어 있는지를 검사한다. 그러니 직접 Proxy.newProxyInstance로 만든 프록시는 isAopProxy가 false다.

    Advised는 프록시의 설정을 들여다보고 바꾸는 인터페이스다. 마지막 줄에서 프록시를 Advised로 캐스팅해 getAdvisors()를 불렀더니 어드바이저 하나가 나왔다. 우리는 addAdvice로 어드바이스만 넣었는데 목록에는 DefaultPointcutAdvisor가 들어 있고, 포인트컷은 Pointcut.TRUE다. AdvisedSupport.addAdvice가 어드바이스를 받으면 new DefaultPointcutAdvisor(advice)로 감싸 저장하기 때문이다. 이 감싸기는 포인트컷을 다루는 절에서 다시 등장한다. 설정을 외부에 보이고 싶지 않으면 setOpaque(true)를 주는데, 그러면 completeProxiedInterfaces가 Advised를 목록에 넣지 않아 캐스팅 자체가 실패한다.

    로그 순서는 기대한 그대로다. 어드바이스가 먼저 실행되고, proceed() 안에서 대상의 greet가 실행되고, 반환값이 어드바이스로 돌아와 출력된 다음 호출자에게 간다. 어드바이스가 받은 invocation의 실제 타입이 ReflectiveMethodInvocation이라는 것도 출력에 찍혔다.

    self()의 결과는 따로 볼 만하다. GreeterImpl.self()는 this, 즉 프록시가 아닌 진짜 대상을 반환한다. 어드바이스 로그에도 demo.GreeterImpl@71bc1ae4가 찍혔다. 그런데 호출자가 받은 값은 프록시와 같다(self()==proxy ? true). JdkDynamicAopProxy.invoke의 끝부분에 이런 처리가 있다.

    // JdkDynamicAopProxy.invoke(...) 끝부분 (spring-framework 6.2.x)

    선택 규칙: DefaultAopProxyFactory

    getProxy()는 createAopProxy().getProxy()이고, createAopProxy()는 DefaultAopProxyFactory.createAopProxy(this)로 설정 객체(팩토리 자신)를 넘긴다. 결정은 이 메서드 하나에서 내려진다. 6.2.x 소스를 그대로 옮긴다.

    // org.springframework.aop.framework.DefaultAopProxyFactory (6.2.x)
public AopProxy createAopProxy(AdvisedSupport config) throws AopConfigException {
    if (config.isOptimize() || config.isProxyTargetClass() || !config.hasUserSuppliedInterfaces()) {
        Class targetClass = config.getTargetClass();
        if (targetClass == null && config.getProxiedInterfaces().length == 0) {
            throw new AopConfigException("TargetSource cannot determine target class: " +
                    "Either an interface or a target is required for proxy creation.");
        }
        if (targetClass == null || targetClass.isInterface() ||
                Proxy.isProxyClass(targetClass) || ClassUtils.isLambdaClass(targetClass)) {
            return new JdkDynamicAopProxy(config);
        }
        return new ObjenesisCglibAopProxy(config);
    }
    else {
        return new JdkDynamicAopProxy(config);
    }
}

    바깥 if는 "CGLIB를 고려할 이유가 있는가"를 묻는다. optimize나 proxyTargetClass가 켜져 있거나, 사용자가 준 인터페이스가 하나도 없으면 CGLIB 쪽으로 들어간다. 여기서 hasUserSuppliedInterfaces()는 인터페이스 목록에서 SpringProxy 계열과 어드바이저가 도입한 인터페이스를 뺀 나머지가 하나라도 있는지 본다. 안쪽 if는 CGLIB 쪽으로 들어왔더라도 상속할 수 없는 경우를 걸러 낸다. 대상 클래스 자체가 인터페이스이거나, 이미 JDK 프록시 클래스이거나, 람다가 만든 클래스이면 하위 클래스를 만들 수 없으므로 JDK 프록시로 돌아간다. 그 밖의 경우에만 ObjenesisCglibAopProxy가 만들어진다.

    생성자는 한 번만 실행되었다: Objenesis

    실행 결과의 첫 줄을 다시 보자. "Counter 생성자 실행"은 한 번만 찍혔다. 그 한 번은 new Counter()로 대상을 만들 때의 것이다. 프록시 객체도 Counter의 하위 클래스 인스턴스이니, 자바의 규칙대로라면 프록시를 만들 때 상위 클래스 생성자 Counter()가 한 번 더 실행되어야 한다(하위 클래스 생성자는 반드시 상위 클래스 생성자를 먼저 호출한다). 그런데 실행되지 않았다.

    클래스 이름 ObjenesisCglibAopProxy가 답이다. 이 클래스는 스프링 코어에 재패키징된 Objenesis(org.springframework.objenesis.SpringObjenesis)로 생성자를 실행하지 않고 인스턴스를 만든다. 6.2.x 소스의 createProxyClassAndInstance는 먼저 enhancer.createClass()로 클래스를 만들고, objenesis.newInstance(proxyClass, ...)를 시도하고, 실패할 때만 기본 생성자 호출로 물러선다. 그 다음 ((Factory) proxyInstance).setCallbacks(callbacks)로 콜백을 꽂는다. 스프링 레퍼런스도 CGLIB 프록시 인스턴스가 Objenesis로 만들어지므로 대상의 생성자가 두 번 호출되지 않으며, JVM이 생성자 우회를 허용하지 않으면 두 번 호출될 수 있다고 적고 있다. 이 덕분에 CGLIB 프록시 대상에 기본 생성자가 없어도 된다.

    대가도 있다. 생성자가 실행되지 않았으니 프록시 객체 안에 있는 Counter 몫의 필드는 초기화되지 않은 기본값 상태다. 자바에서 필드 초기화식(= new StringBuilder("init"))은 생성자 본문과 함께 생성자( 메서드)로 컴파일되므로, 생성자를 건너뛰면 초기화식도 건너뛴다. 이 사실이 proxy.history=null이라는 결과로 드러났다.

    history()는 final이라 CGLIB가 재정의하지 못했다. 그래서 proxy.history()는 어드바이스도 거치지 않고, 대상에게 위임되지도 않고, 프록시 객체 자신의 Counter.history() 코드를 그대로 실행한다. 그 코드가 읽는 this.history는 프록시 객체의 필드이고, 그 필드는 null이다. 문자열 연결이라 "history=null"로 끝났지만, history.length()처럼 필드를 역참조했다면 NullPointerException이 났을 것이다. 6.2.x의 CglibAopProxy는 이 상황을 디버그 로그로 경고한다: final 메서드는 프록시되지 않으며 "호출이 대상 인스턴스로 전달되지 않고, 프록시 인스턴스의 초기화되지 않은 필드 때문에 NPE가 날 수 있다"는 취지다. 인터페이스를 구현한 메서드가 final이면 WARN 수준으로 "인터페이스 기반 JDK 프록시를 고려하라"고 남긴다.

    일상에서 가져온 비유대리인의 빈 서랍

    CGLIB 프록시는 진짜 담당자와 똑같은 책상을 받은 대리인이다. 손님이 일반 업무를 맡기면 대리인은 앞뒤로 기록을 남기고 진짜 담당자에게 넘긴다. 그런데 "이 업무만은 반드시 책상 주인이 직접 처리한다"고 못 박힌 업무(final 메서드)는 대리인이 가로챌 수 없어 자기 책상에서 직접 처리한다. 문제는 대리인의 서랍이 비어 있다는 것이다. 진짜 담당자의 서류는 진짜 담당자의 서랍에 있다. 비유가 깨지는 지점도 있다. 현실의 대리인은 서랍이 빈 것을 알아채지만, 프록시 객체는 null 필드를 읽고도 아무 경고 없이 계속 진행한다.

    표의 둘째 줄에는 미묘한 점이 있다. 어드바이스가 적용되지 않는 메서드라도 설정이 frozen이 아니면 AOP_PROXY로 간다. 소스의 조건이 if (haveAdvice || !isFrozen)이기 때문이다. 클래스는 한 번 만들어지면 바꿀 수 없지만 설정은 나중에 바뀔 수 있으니, 지금 어드바이스가 없는 메서드도 일단 체인을 확인하는 경로에 태워 두는 것이다. frozen일 때만 어드바이스 없는 메서드를 체인 확인 없이 대상에게 바로 보내는 콜백(INVOKE_TARGET, DISPATCH_TARGET)이 쓰이고, 여기에 대상까지 고정(static)이면 어드바이스 있는 메서드에 고정 체인을 쓰는 최적화가 더해진다.

    포인트컷, 어드바이스, 어드바이저 — 소개

    지금까지의 예제는 모든 메서드에 어드바이스가 적용되었다. self()에도 로그가 찍혔고, CGLIB 프록시라면 toString()에도 찍혔을 것이다. 실제로는 "이름이 find로 시작하는 메서드에만", "특정 패키지의 클래스에만"처럼 적용 범위를 정하고 싶다. 04회에서는 이 판단을 핸들러 안에서 if로 했다. 그렇게 하면 "무엇을 할지"와 "어디에 할지"가 한 클래스에 섞인다. 같은 로그 로직을 다른 범위에 쓰고 싶으면 클래스를 복사해야 하고, 같은 범위에 다른 로직을 쓰고 싶어도 마찬가지다.

    스프링 AOP는 이 둘을 별개의 객체로 나눈다.

    • 포인트컷(Pointcut): 어디에 적용할지를 판단한다. 인터페이스는 ClassFilter getClassFilter()와 MethodMatcher getMethodMatcher() 두 메서드로 되어 있다. 클래스 필터가 대상 클래스를 거르고, 메서드 매처가 그 클래스의 메서드를 거른다. 둘 다 통과해야 적용된다.
    • 어드바이스(Advice): 무엇을 할지, 즉 부가 기능 로직이다. 지금까지 쓴 MethodInterceptor가 대표적인 어드바이스다.
    • 어드바이저(Advisor): 포인트컷 하나와 어드바이스 하나를 묶은 것이다. Advisor 인터페이스는 getAdvice()를, 하위 인터페이스 PointcutAdvisor는 getPointcut()을 더한다. 가장 흔한 구현이 DefaultPointcutAdvisor다.

    스프링 레퍼런스가 보여 주는 MethodMatcher의 전체 모양은 다음과 같다.

    public interface ClassFilter {
    boolean matches(Class clazz);
}

public interface MethodMatcher {
    boolean matches(Method m, Class targetClass);                  // 정적 판단
    boolean isRuntime();                                              // 호출마다 다시 볼 것인가
    boolean matches(Method m, Class targetClass, Object... args);  // 동적 판단
}

    매처에 matches가 둘인 데에는 이유가 있다. 2-인자 판단은 메서드와 클래스만 본다. 이 정보는 프로그램이 실행되는 동안 바뀌지 않으므로 한 번 판단한 결과를 계속 써도 된다. 3-인자 판단은 호출 때마다 달라지는 인자까지 본다. 결과를 저장해 둘 수 없으니 매번 다시 계산해야 한다. isRuntime()은 "이 포인트컷에 3-인자 판단이 필요한가"를 알리는 스위치다. 레퍼런스는 대부분의 MethodMatcher가 정적이고(isRuntime()이 false), 그때 3-인자 matches는 절대 호출되지 않는다고 설명한다.

    일상에서 가져온 비유건물 출입 관리

    어드바이스는 출입 기록을 남기는 경비원의 업무, 포인트컷은 "어느 출입구, 어느 층에 경비원을 배치할지"를 적은 배치표, 어드바이저는 "이 배치표대로 이 업무를 하라"는 근무 명령서 한 장이다. 배치표만 바꾸면 같은 업무를 다른 곳에 할 수 있고, 업무만 바꾸면 같은 곳에서 다른 일을 할 수 있다. 정적 포인트컷은 "3층 동쪽 문"처럼 장소만 보는 규칙이라 한 번 배치하면 끝이고, 동적 포인트컷은 "방문객이 가방을 들었으면"처럼 사람마다 확인해야 하는 규칙이다. 비유가 깨지는 지점은 순서다. 경비원 여러 명이 같은 문을 지키면 현실에서는 동시에 일하지만, 어드바이저는 정해진 순서대로 한 명씩 감싸며 실행된다.

    이 셋의 관계를 프록시 팩토리 쪽에서 보면 이렇다. 팩토리는 어드바이저의 목록을 가진다. addAdvice(advice)는 addAdvisor(new DefaultPointcutAdvisor(advice))의 줄임이고, 포인트컷 없이 만든 DefaultPointcutAdvisor의 포인트컷은 Pointcut.TRUE(모든 클래스, 모든 메서드)다. 앞의 실행 결과에서 pointcut [Pointcut.TRUE]가 찍힌 이유가 이것이다. 그러니 "어드바이스만 등록하는 경우"란 없다. 팩토리의 세계에서는 언제나 어드바이저가 등록된다.

    용어를 하나 더 짚어 두자. 포인트컷, 어드바이스, 어드바이저라는 이름은 AOP 일반 용어이고, 07회에서 조인 포인트(join point), 애스펙트(aspect), 위빙(weaving)과 함께 개념 전체를 다시 정리한다. 이 회차에서는 스프링 AOP API의 인터페이스로서 이들이 어떻게 동작하는지에 집중한다.

    어드바이저 하나 안에 포인트컷과 어드바이스가 들어 있고, 포인트컷은 다시 클래스 필터와 메서드 매처로 나뉜다는 포함 관계를 보여 준다. Nested-box diagram on white background. Outer large rounded rectangle labeled "어드바이저 (Advisor)".     예제 코드 1·2 — 어드바이저와 직접 만든 포인트컷

    포인트컷을 직접 구현해 보자. 대상은 save와 find 두 메서드를 가진 Store다. 이번 예제부터는 진입과 복귀를 찍는 어드바이스를 이름표만 바꿔 여러 개 만들 일이 많아서 작은 도우미를 하나 둔다.

    package demo;

public interface Store {
    void save(String value);
    String find(long id);
}
    package demo;

public class StoreImpl implements Store {
    @Override
    public void save(String value) {
        System.out.println("  target.save(" + value + ")");
    }

    @Override
    public String find(long id) {
        System.out.println("  target.find(" + id + ")");
        return "v" + id;
    }
}
    package demo;

import org.aopalliance.intercept.MethodInterceptor;

public class Tags {
    // 이름표만 다른 어드바이스를 만드는 도우미. 진입·복귀를 찍는다.
    public static MethodInterceptor tag(String name) {
        return invocation -> {
            System.out.println(name + " 진입: " + invocation.getMethod().getName());
            Object result = invocation.proceed();
            System.out.println(name + " 복귀: " + invocation.getMethod().getName());
            return result;
        };
    }
}

    MethodInterceptor는 추상 메서드가 invoke 하나뿐인 인터페이스라 람다로 구현할 수 있다. 포인트컷은 save만 통과시키고, 판단할 때마다 한 줄을 찍게 한다. 언제, 몇 번 판단하는지 보려는 것이다.

    package demo;

import java.lang.reflect.Method;
import org.springframework.aop.ClassFilter;
import org.springframework.aop.MethodMatcher;
import org.springframework.aop.Pointcut;

public class SaveOnlyPointcut implements Pointcut {
    @Override
    public ClassFilter getClassFilter() {
        return ClassFilter.TRUE;                 // 모든 클래스 통과
    }

    @Override
    public MethodMatcher getMethodMatcher() {
        return new SaveOnlyMatcher();
    }

    static class SaveOnlyMatcher implements MethodMatcher {
        @Override
        public boolean matches(Method method, Class targetClass) {
            boolean result = method.getName().equals("save");
            System.out.println("[정적 matches] " + method.getName()
                    + " on " + targetClass.getSimpleName() + " -> " + result);
            return result;
        }

        @Override
        public boolean isRuntime() {
            return false;                        // 인자를 보지 않는다
        }

        @Override
        public boolean matches(Method method, Class targetClass, Object... args) {
            throw new UnsupportedOperationException("isRuntime()이 false라 호출되지 않는다");
        }
    }
}
    package demo;

import org.springframework.aop.framework.ProxyFactory;
import org.springframework.aop.support.DefaultPointcutAdvisor;

public class PointcutDemo {
    public static void main(String[] args) {
        ProxyFactory factory = new ProxyFactory(new StoreImpl());
        factory.addAdvisor(new DefaultPointcutAdvisor(new SaveOnlyPointcut(), Tags.tag("A")));
        Store store = (Store) factory.getProxy();
        System.out.println("-- 프록시 생성 완료");
        store.save("x");
        store.save("y");
        store.find(1);
        store.find(2);

        System.out.println("-- 동적 포인트컷");
        ProxyFactory factory2 = new ProxyFactory(new StoreImpl());
        factory2.addAdvisor(new DefaultPointcutAdvisor(new BigIdPointcut(), Tags.tag("D")));
        Store store2 = (Store) factory2.getProxy();
        store2.find(7);
        store2.find(700);
    }
}

    뒤쪽의 BigIdPointcut은 잠시 뒤에 본다. 앞쪽 절반의 실행 결과는 이렇다.

    -- 프록시 생성 완료
[정적 matches] save on StoreImpl -> true
A 진입: save
  target.save(x)
A 복귀: save
A 진입: save
  target.save(y)
A 복귀: save
[정적 matches] find on StoreImpl -> false
  target.find(1)
  target.find(2)

    세 가지를 읽어 낼 수 있다. 첫째, save에만 어드바이스 A가 적용되었고 find는 대상이 바로 호출되었다. 둘째, 판단은 프록시를 만들 때가 아니라 그 메서드가 처음 호출될 때 일어났다("프록시 생성 완료"가 먼저 찍혔다). 셋째, save를 두 번, find를 두 번 불렀지만 [정적 matches]는 메서드마다 한 번씩만 찍혔다. 두 번째 호출부터는 판단 결과를 재사용했다.
