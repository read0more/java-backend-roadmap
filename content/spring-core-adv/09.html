    포인트컷이 답해야 하는 질문

    07회와 08회에서 @Aspect 클래스에 @Around 같은 어드바이스를 쓰고, 그 위에 execution(...)으로 시작하는 문자열을 붙여 "어디에 적용할지"를 정했다. 지금까지 그 문자열은 거의 execution 하나로만 썼다. 이 회차는 그 문자열 자체, 곧 포인트컷 표현식(pointcut expression)을 바닥까지 뜯어본다. 표현식의 첫 단어를 포인트컷 지시자(pointcut designator, PCD)라고 부르는데, 스프링 AOP가 지원하는 지시자는 열 개다. 각각이 무엇을 보고 고르는지가 다르고, 그 차이가 실무에서 "왜 어드바이스가 안 붙지?", "왜 기동이 실패하지?"라는 질문으로 돌아온다.

    05회에서 본 것처럼 스프링의 Pointcut 인터페이스는 두 부품으로 되어 있다. 클래스를 거르는 ClassFilter와 메서드를 거르는 MethodMatcher다. @Aspect의 표현식 문자열은 AspectJExpressionPointcut이라는 Pointcut 구현체로 바뀌는데, 이 클래스는 문자열 해석을 직접 하지 않고 AspectJ 위버(aspectjweaver 라이브러리)의 파서와 매칭 엔진을 빌려 쓴다. 그래서 표현식 문법은 AspectJ의 문법이고, 스프링은 그중 프록시 방식으로 구현할 수 있는 부분만 허용한다. 이 클래스의 Javadoc도 프록시 기반 모델에서 처리되므로 메서드 실행 포인트컷만 지원한다고 적고 있다.

    AspectJ에서 조인 포인트(join point)는 프로그램 실행 중 어드바이스를 끼워 넣을 수 있는 지점이다. 메서드 호출, 메서드 실행, 필드 읽기와 쓰기, 생성자 실행, 정적 초기화, 예외 처리 블록 진입까지 모두 조인 포인트가 된다. 스프링 AOP는 프록시가 메서드 호출을 가로채는 방식이므로 조인 포인트가 메서드 실행 하나뿐이다. 스프링 레퍼런스가 대부분의 지시자 설명에 "(the execution of methods when using Spring AOP)" 같은 단서를 붙이는 것도 이 때문이다. 이 회차의 모든 지시자는 결국 "프록시를 거쳐 실행되는 이 메서드 호출을 고를 것인가"라는 같은 질문에 서로 다른 기준으로 답한다.

    그런데 이 질문은 두 번 던져진다. 첫 번째는 빈을 만들 때다. 06회의 자동 프록시 생성기(빈 후처리기)는 빈 하나가 만들어질 때마다 "이 빈의 메서드 중 어드바이스가 붙을 수 있는 것이 하나라도 있는가"를 묻고, 있으면 프록시를 만든다. 두 번째는 메서드가 호출될 때다. 일부 지시자는 실제 인자나 실제 객체를 봐야 답할 수 있어서, 호출이 일어날 때마다 다시 묻는다. 어떤 지시자가 어느 시점에 결론을 내는지가 이 회차를 관통하는 축이다. 이 축을 잡고 나면 지시자 열 개를 외울 필요 없이 동작을 예측할 수 있다.

    이 회차의 실행 결과는 원고를 쓰면서 JDK 21.0.13(Temurin), 스프링 프레임워크 6.2.19(spring-aop, spring-context), AspectJ 위버 1.9.25.1 조합에서 직접 돌려 얻었다. 스프링 부트 없이 AnnotationConfigApplicationContext에 자동 프록시 생성기를 등록해 실험했다. 프록시 클래스 이름 끝의 번호($Proxy11, $$SpringCGLIB$$0)는 실행 환경과 순서에 따라 달라진다. 스프링 내부 클래스(ShadowMatchUtils, InterceptorAndDynamicMethodMatcher 등)는 공개 API가 아니므로 버전에 따라 이름과 구조가 바뀔 수 있다.

    포인트컷 지시자 — 전체 지도

    스프링 레퍼런스가 나열하는 지원 지시자는 execution, within, this, target, args, @target, @args, @within, @annotation 아홉 개이고, 여기에 스프링만의 확장인 bean이 더해진다. 아래 표는 각 지시자가 무엇을 보는지, 그리고 프록시를 만드는 시점(빈 생성 시)에 결론을 낼 수 있는지를 정리한 것이다. 마지막 열은 뒤에서 실험으로 확인한 결과다.

    지시자무엇을 보고 고르는가빈 생성 시 결론
    execution메서드 시그니처(접근 제어자, 반환 타입, 선언 타입, 이름, 파라미터, 예외)항상 낸다
    within메서드가 정의된 타입항상 낸다
    args호출 시점에 넘어온 인자 객체의 실제 타입못 낼 때가 많다
    this프록시 객체의 타입대상 클래스로 1차 판정, 호출 때 재확인
    target프록시 뒤에 있는 대상 객체의 타입대상 클래스로 1차 판정, 호출 때 재확인
    @within메서드가 정의된 타입에 붙은 애너테이션낸다
    @target실행 중인 객체의 클래스에 붙은 애너테이션못 낸다
    @annotation실행되는 메서드에 붙은 애너테이션낸다
    @args넘어온 인자 객체의 실제 클래스에 붙은 애너테이션못 낸다
    bean스프링 빈의 이름낸다(스프링 확장)

    AspectJ 언어에는 이보다 많은 지시자가 있다. 레퍼런스는 call, get, set, preinitialization, staticinitialization, initialization, handler, adviceexecution, withincode, cflow, cflowbelow, if, @this, @withincode를 스프링이 지원하지 않는 지시자로 꼽는다. 이유는 앞 절에서 본 조인 포인트의 한계 그대로다. call은 "호출하는 쪽 코드"에 끼어드는 지시자인데, 프록시는 호출하는 쪽 코드를 바꿀 수 없다. get과 set은 필드 접근인데, 필드 접근은 메서드 호출이 아니므로 프록시를 거치지 않는다. 프록시가 볼 수 있는 것은 "누군가 프록시의 메서드를 불렀다"는 사건뿐이다.

    지원하지 않는 지시자를 쓰면 어떻게 될까. 레퍼런스는 IllegalArgumentException이 던져진다고 적는다. 실제로 AspectJExpressionPointcut을 직접 만들어 call(* *(..))로 매칭을 시도하면 AspectJ의 UnsupportedPointcutPrimitiveException("contains unsupported pointcut primitive 'call'")이 올라온다. 그런데 같은 표현식을 @Aspect의 어드바이스에 붙여 컨테이너를 띄우면 결과가 다르다. 6.2.19에서 실험해 보니 컨테이너는 아무 예외 없이 기동했고, 어드바이스는 어디에도 적용되지 않았다. AspectJExpressionPointcut이 클래스 매칭 단계에서 파서의 거부를 잡아 DEBUG 로그("Pointcut parser rejected expression [...]")만 남기고 "매칭 없음"으로 처리하기 때문이다. 이 동작은 지원하지 않는 지시자뿐 아니라 오타에도 똑같이 적용된다. 뒤의 "흔한 함정" 절에서 다시 다룬다.

    스프링 레퍼런스의 "좋은 포인트컷 작성" 절은 지시자를 세 부류로 나눈다. 특정 종류의 조인 포인트를 고르는 종류 지정(kinded) 지시자(execution, get, set, call, handler), 관심 있는 조인 포인트 묶음의 범위를 정하는 범위 지정(scoping) 지시자(within, withincode), 문맥으로 매칭하고 값을 바인딩하는 문맥(contextual) 지시자(this, target, @annotation)다. 레퍼런스는 좋은 포인트컷이 적어도 앞의 두 부류를 포함해야 하고, 범위 지정 지시자는 매칭이 매우 빨라 처리할 필요가 없는 조인 포인트 묶음을 빠르게 걸러 낸다고 권한다. 이 권고가 왜 스프링 AOP에서 성능 이상의 의미를 갖는지는 @target 절에서 기동 실패라는 형태로 보게 된다.

    포인트컷 판정이 빈 생성 시점(프록시를 만들지 결정)과 메서드 호출 시점(이번 호출에 어드바이스를 실행할지 결정) 두 번에 나뉘어 일어나는 모습. 가로로 긴 시퀀스 다이어그램. 왼쪽 절반 위에 "빈 생성 시점" 제목, 오른쪽 절반 위에 "메서드 호출 시점" 제목. 왼쪽: "자동 프록시 생성기" 상자에서 "ClassFilter" 상자로 화살표, 다시 "MethodMatcher (정적)" 상자로 화살표, 그 결과가 "프록시 생성" 또는 "원본 그대로" 두 갈래로 나뉜다. 오른쪽: "클라이언트" 상자에서 "프록시" 상자로 호출 화살표, 프록시 안에 "어드바이스 체인" 띠가 있고 띠 안의 한 칸에 "동적 검사 (args, this, @target)"라는 라벨, 그 칸에서 "실행" 과 "건너뜀" 두 갈래 화살표가 나간 뒤 "대상 객체" 상자로 이어진다. 두 영역 사이에 세로 점선. 깔끔한 플랫 스타일, 흰 배경, 파란색과 회색 위주. 포인트컷은 빈을 만들 때 한 번, 일부 지시자는 메서드를 호출할 때마다 한 번 더 판정된다.

    예제 만들기 — 실험대 준비

    지시자마다 "매칭된다/안 된다"를 말로만 설명하면 금방 헷갈린다. 그래서 이 회차는 작은 도메인 하나를 만들고, 표현식 하나하나를 실제로 돌려서 결과를 확인한다. 도메인은 주문 서비스 하나와 애너테이션 세 개다. @Tracked는 클래스에 붙이는 표시, @Audited는 메서드에 붙이는 표시, @Sensitive는 인자로 넘어가는 객체의 클래스에 붙이는 표시다. 셋 모두 실행 중에 리플렉션으로 읽어야 하므로 보존 정책을 RUNTIME으로 둔다. 보존 정책이 CLASS(기본값)이면 클래스 파일에는 남지만 실행 중 리플렉션으로는 보이지 않아서, 애너테이션 기반 지시자가 아무것도 고르지 못한다.

    package com.example.shop;

import java.lang.annotation.*;

@Target(ElementType.TYPE) @Retention(RetentionPolicy.RUNTIME)
public @interface Tracked {}

@Target(ElementType.METHOD) @Retention(RetentionPolicy.RUNTIME)
public @interface Audited { String value() default ""; }

@Target(ElementType.TYPE) @Retention(RetentionPolicy.RUNTIME)
public @interface Sensitive {}
// 실제로는 public 애너테이션이므로 파일 세 개로 나누어 둔다.
    package com.example.shop;

public interface OrderService {
    String order(String itemId);
}

@Tracked
public class OrderServiceImpl implements OrderService {
    @Override
    @Audited("주문")
    public String order(String itemId) { return "ok:" + itemId; }

    public void cancel(Long orderId, String reason) { }   // 인터페이스에 없는 메서드
    public int count() { return 0; }                     // 파라미터 없음, 기본형 반환
    public void log(Object value) { }                    // 파라미터 타입이 Object
}
// 이것도 실제로는 파일 두 개다.

    메서드 네 개는 일부러 모양을 다르게 만들었다. order는 인터페이스에 선언되어 있고 애너테이션도 붙어 있다. cancel은 구현 클래스에만 있고 파라미터가 두 개다. count는 파라미터가 없고 int를 반환한다. log는 선언된 파라미터 타입이 Object라서, 선언 타입과 실제 인자 타입이 다를 수 있다. 이 차이들이 지시자마다 다른 결과를 만든다.

    실험 도구는 두 가지다. 첫째는 컨테이너 없이 AspectJExpressionPointcut을 직접 만들어 "이 메서드에 이 표현식이 매칭되는가"만 묻는 도구다. 스프링 AOP가 프록시를 만들지 결정할 때 쓰는 것과 같은 메서드(matches(Method, Class))를 부르므로, 빈 생성 시점의 판정을 그대로 재현한다.

    package com.example.test;

import java.lang.reflect.Method;
import org.springframework.aop.aspectj.AspectJExpressionPointcut;

public class PointcutLab {
    static void check(String expression, Class type, String name, Class... params) throws Exception {
        AspectJExpressionPointcut pc = new AspectJExpressionPointcut();
        pc.setExpression(expression);
        Method m = type.getMethod(name, params);
        System.out.printf("%-6s runtime=%-5s %s%n", pc.matches(m, type), pc.isRuntime(), expression);
    }

    public static void main(String[] args) throws Exception {
        check("execution(* com.example.shop.*.*(..))", OrderServiceImpl.class, "order", String.class);
        // ... 이하 표현식을 바꿔 가며 반복
    }
}

    둘째는 실제 컨테이너다. 어드바이스가 정말 실행되는지, 프록시가 정말 만들어지는지는 컨테이너를 띄워야 확인된다. 스프링 부트는 클래스패스에 AspectJ가 있으면 자동 구성이 AspectJ 자동 프록시를 켜 주므로 @EnableAspectJAutoProxy조차 필요 없지만, 여기서는 부트 없이 같은 일을 손으로 한다. @EnableAspectJAutoProxy가 내부에서 부르는 것과 같은 AopConfigUtils 메서드로 AnnotationAwareAspectJAutoProxyCreator를 등록하고, 필요하면 CGLIB 프록시를 강제한다.

    static AnnotationConfigApplicationContext context(boolean proxyTargetClass, Class aspect, Class... beans) {
    AnnotationConfigApplicationContext c = new AnnotationConfigApplicationContext();
    AopConfigUtils.registerAspectJAnnotationAutoProxyCreatorIfNecessary(c);
    if (proxyTargetClass) AopConfigUtils.forceAutoProxyCreatorToUseClassProxying(c);
    c.registerBean("orderService", OrderServiceImpl.class);
    for (Class b : beans) c.registerBean(b);
    c.registerBean(aspect);          // @Aspect 클래스도 빈이어야 한다
    c.refresh();
    return c;
}

    스프링 부트의 레퍼런스는 부트의 자동 구성이 기본으로 CGLIB 프록시를 쓰도록 설정하고, JDK 프록시를 쓰려면 spring.aop.proxy-target-class를 false로 두라고 적는다. 그래서 이 회차의 실험도 따로 언급하지 않으면 CGLIB 프록시(proxyTargetClass = true)로 돌렸다. JDK 프록시와 결과가 갈리는 this/target 실험에서만 둘을 나란히 돌린다.

    execution — 표현식의 여섯 부분

    execution은 메서드 실행 조인 포인트를 시그니처로 고르는 지시자다. 스프링 레퍼런스는 이 지시자를 스프링 AOP에서 주로 쓸 지시자라고 부른다. 형식은 다음과 같다.

    execution( 접근제어자패턴?  반환타입패턴  선언타입패턴?이름패턴(파라미터패턴)  예외패턴? )
           modifiers-pattern? ret-type-pattern declaring-type-pattern?name-pattern(param-pattern) throws-pattern?

  ?  가 붙은 부분은 생략할 수 있다.
  반드시 써야 하는 것: 반환 타입 패턴, 이름 패턴, 파라미터 패턴

  public  String  com.example.shop.OrderServiceImpl . order  (String)
  ──┬───  ──┬───  ───────────────┬──────────────── ─┬───  ───┬────
  접근제어자 반환 타입          선언 타입             이름    파라미터

    이 다섯 조각이 무엇과 비교되는지 감을 잡으려면 조인 포인트의 시그니처를 직접 찍어 보면 된다. 어드바이스에서 JoinPoint.getSignature()를 출력하면 order 실행의 시그니처가 다음처럼 나온다. 표현식의 각 부분은 이 문자열의 해당 칸과 비교된다고 생각하면 된다.

    sig.toString     = String com.example.shop.OrderServiceImpl.order(String)
sig.toLongString = public java.lang.String com.example.shop.OrderServiceImpl.order(java.lang.String)
jp.getKind       = method-execution

    가장 꼼꼼한 표현식은 모든 칸을 다 쓴 것이다. execution(public String com.example.shop.OrderServiceImpl.order(String))는 order에 매칭된다. 반대로 가장 느슨한 표현식은 필수 칸만 와일드카드로 채운 execution(* *(..))이다. 반환 타입 아무거나(*), 이름 아무거나(*), 파라미터 아무거나((..))이고 접근 제어자, 선언 타입, 예외는 생략했다. 이 표현식은 프록시가 가로챌 수 있는 모든 메서드에 매칭된다. 실무 표현식은 이 두 극단 사이 어딘가에서 필요한 칸만 조인다.

    와일드카드는 두 가지다. *는 "이 자리의 아무 이름 하나"이고, 이름의 일부에도 쓸 수 있다. ord*와 *der는 모두 order에 매칭됐다. ..는 쓰이는 자리에 따라 뜻이 둘이다. 패키지 자리에서는 "점으로 시작하고 끝나는 아무 문자열", 즉 0개 이상의 하위 패키지를 뜻하고, 파라미터 자리에서는 "0개 이상의 아무 파라미터"를 뜻한다. 패키지 자리의 차이는 실험에서 분명히 갈렸다.

    표현식대상 메서드결과
    execution(* com.example.shop.*.*(..))shop.OrderServiceImpl.order매칭
    execution(* com.example.*.*(..))shop.OrderServiceImpl.order불일치
    execution(* com.example..*.*(..))shop.OrderServiceImpl.order매칭
    execution(* com.example.shop.*.*(..))shop.sub.SubThing.work불일치
    execution(* com.example.shop..*.*(..))shop.sub.SubThing.work매칭

    com.example.*.*(..)를 읽어 보자. 마지막 *가 메서드 이름, 그 앞의 *가 타입 이름, 그 앞이 패키지 com.example다. 즉 "com.example 패키지에 바로 들어 있는 아무 타입의 아무 메서드"다. OrderServiceImpl은 com.example.shop에 있으므로 한 단계 아래라서 매칭되지 않는다. 점 하나(.)는 정확히 그 패키지, 점 둘(..)은 그 패키지와 모든 하위 패키지다. 실무에서 "서비스 계층 전체"를 고를 때 ..를 빠뜨려 하위 패키지의 클래스가 빠지는 실수가 흔한 이유가 이것이다.

    execution — 타입 매칭과 파라미터 매칭

    선언 타입 자리에 부모 타입을 쓰면 무슨 일이 생길까. OrderService는 인터페이스이고 OrderServiceImpl이 그것을 구현한다. 실험 결과는 메서드마다 갈렸다.

    표현식대상 메서드결과
    execution(* com.example.shop.OrderService.*(..))OrderServiceImpl.order매칭
    execution(* com.example.shop.OrderService.*(..))OrderServiceImpl.count불일치
    execution(* com.example.shop.OrderService+.*(..))OrderServiceImpl.count매칭

    AspectJ 프로그래밍 가이드의 의미론 장은 실행(execution) 조인 포인트에 타입을 지정한 경우, 그 타입에 선언된 메서드와 그 타입이 선언하거나 물려받은 메서드를 재정의(override)한 메서드에 매칭된다고 설명한다. order는 OrderService에 선언된 메서드를 재정의한 것이므로 OrderService.*에 걸린다. count는 구현 클래스에서 처음 생긴 메서드라서 OrderService라는 이름으로는 고를 수 없다. 부모 타입으로 지정하면 "부모가 아는 메서드"까지만 잡힌다고 기억하면 된다. 타입 이름 뒤에 +를 붙이면 "그 타입과 모든 하위 타입"이라는 타입 패턴이 되므로, OrderService+에는 OrderServiceImpl 자체가 포함되고 거기 선언된 count도 매칭된다.

    파라미터 패턴은 스프링 레퍼런스에 정리되어 있다. ()는 파라미터가 없는 메서드, (..)는 0개 이상의 아무 파라미터, (*)는 아무 타입 하나, (*,String)은 두 개인데 두 번째가 String인 메서드다. 실험에서 확인한 조합은 다음과 같다.

    파라미터 패턴대상 메서드결과
    (String)order(String)매칭
    ()order(String)불일치
    (*)order(String)매칭
    (..)count()매칭
    (String, ..)order(String)매칭(뒤쪽 0개)
    (*, ..) / (*, *)cancel(Long, String)둘 다 매칭
    (Long, String)cancel(Long, String)매칭
    (long, String)cancel(Long, String)불일치
    (Object)order(String)불일치

    마지막 두 줄이 중요하다. 파라미터 패턴은 선언된 파라미터 타입과 글자 그대로 비교된다. 자바 컴파일러는 Long 자리에 long 값을 넘기면 자동으로 박싱해 주지만, 포인트컷 패턴은 오토박싱을 고려하지 않는다. 또 String이 Object의 하위 타입이라고 해서 (Object) 패턴이 order(String)에 매칭되지도 않는다. 메서드 시그니처는 클래스 파일에 기록된 디스크립터((Ljava/lang/String;)Ljava/lang/String;)로 고정되어 있고, execution은 그 고정된 선언을 보는 지시자이기 때문이다. 상속 관계를 따지고 싶다면 패턴에 +를 써서 (Object+)처럼 명시해야 한다.

    반환 타입 패턴도 같은 규칙을 따른다. execution(Object *(..))는 String을 반환하는 order에 매칭되지 않았고, execution(Object+ *(..))는 매칭됐다. execution(int *(..))는 count에 매칭됐지만 execution(Integer *(..))는 매칭되지 않았다. 반환 타입이 없는 메서드는 void로 고른다. execution(void *(..))는 cancel에 매칭됐다.

    생략 가능한 두 부분도 짚어 두자. 접근 제어자 패턴은 생략하면 "아무 접근 제어자"다. execution(private * *(..))처럼 써서 private 메서드를 고르는 표현식을 만들 수는 있지만, 프록시는 private 메서드 호출을 가로챌 수 없으므로 스프링 AOP에서 그 어드바이스는 실행될 기회가 없다. 레퍼런스는 JDK 프록시에서는 인터페이스의 public 메서드 호출만, CGLIB에서는 public과 protected(필요하면 패키지 수준까지) 메서드 호출이 가로채진다고 설명한다. 예외 패턴은 메서드 선언의 throws 절과 비교된다. order는 throws 절이 없으므로 execution(* order(..) throws Exception)에는 매칭되지 않았다. 실무에서 예외 패턴을 쓰는 일은 드물다.

    이 장의 핵심

    execution은 클래스 파일에 박힌 메서드 선언을 본다. 선언 타입 자리에서만 "부모 타입이 선언한 메서드를 재정의한 것"까지 넓혀 주고, 파라미터와 반환 타입 자리에서는 상속도 박싱도 고려하지 않는다. 상속을 따지려면 +를 명시해야 한다. 선언만 보므로 빈을 만들 때 결론이 나고, 호출할 때 다시 검사할 일이 없다.

    within — 타입 하나로 범위를 정한다

    within은 타입 패턴 하나만 받는다. 메서드의 이름, 파라미터, 반환 타입은 보지 않고 "이 메서드가 어느 타입 안에 정의되어 실행되는가"만 본다. AspectJ 가이드는 실행 중인 코드가 그 타입 패턴에 매칭되는 타입에 정의된 조인 포인트를 고른다고 정의한다. 그래서 within(com.example.shop.OrderServiceImpl)은 execution(* com.example.shop.OrderServiceImpl.*(..))과 거의 같은 뜻이 되고, within(com.example.shop..*)은 shop 패키지와 그 하위 패키지의 모든 타입을 고른다.

    차이는 부모 타입을 지정했을 때 드러난다.

    표현식대상클래스 필터결과
    within(com.example.shop.OrderServiceImpl)OrderServiceImpl.order통과매칭
    within(com.example.shop.OrderService)OrderServiceImpl.order탈락불일치
    within(com.example.shop.OrderService+)OrderServiceImpl.order통과매칭

    execution(* com.example.shop.OrderService.*(..))는 order에 매칭됐는데, within(com.example.shop.OrderService)는 매칭되지 않는다. 실행 중인 order의 코드는 OrderServiceImpl 안에 정의되어 있고, within은 그 타입 이름이 패턴과 맞는지만 보기 때문이다. 인터페이스 쪽에는 실행될 코드가 없다. 하위 타입까지 포함하려면 역시 +를 붙여야 한다.

    표의 "클래스 필터" 열에 주목하자. within은 ClassFilter 단계에서 바로 결론이 난다. 실험에서 within(com.example.shop.OrderService)는 getClassFilter().matches(OrderServiceImpl.class)부터 false였다. 클래스 단위로 탈락하면 그 클래스의 메서드는 하나도 들여다볼 필요가 없다. 레퍼런스가 범위 지정 지시자를 "매우 빠르다"고 말하는 이유가 이것이다. execution(* com.example.shop.OrderService.*(..))처럼 부모 타입을 쓰는 execution은 클래스 필터를 통과시킨 뒤 메서드마다 재정의 관계를 따져야 한다.

    정리하면 within은 "어느 패키지, 어느 클래스"만 정하고 싶을 때 짧고 빠른 표현이다. 반면 메서드 단위의 조건이 필요하면 execution을 쓰고, 둘을 &&로 묶어 범위를 먼저 좁히는 방식도 자주 쓴다. 이 조합이 왜 단순한 취향 문제가 아닌지는 @target 절에서 본다.

    args — 실제로 넘어온 인자를 본다

    args는 파라미터 목록 패턴을 받는다는 점에서 execution의 파라미터 칸과 비슷해 보인다. 그러나 비교 대상이 다르다. execution의 파라미터 칸은 선언된 타입과 비교하고, args는 호출 시점에 실제로 넘어온 인자 객체의 타입과 비교한다. 레퍼런스가 이 차이를 직접 예로 든다. args(java.io.Serializable)은 실행 중 넘어온 인자가 Serializable이면 매칭되고, execution(* *(java.io.Serializable))은 시그니처에 Serializable 타입 파라미터 하나가 선언되어 있어야 매칭된다.

    표현식대상정적 판정isRuntime
    args(String)order(String)매칭true
    args(Object)order(String)매칭true
    args(java.io.Serializable)order(String)매칭true
    execution(* *(java.io.Serializable))order(String)불일치false
    args(String)log(Object)매칭(가능성)true
    args(String)count()불일치true
    args(Long, ..)cancel(Long, String)매칭true

    세 가지를 읽어 낼 수 있다. 첫째, args는 상속을 따진다. String 인자는 Object이기도 하고 Serializable이기도 하므로 args(Object)와 args(java.io.Serializable)이 모두 order(String)에 매칭된다. execution의 파라미터 칸이 상속을 따지지 않던 것과 정반대다. 둘째, 정적 판정이 "매칭"으로 나온 log(Object)는 사실 확정이 아니다. log에는 String이 넘어올 수도, Integer가 넘어올 수도 있다. 빈을 만드는 시점에는 어느 쪽인지 알 수 없으므로 "매칭될 수도 있다"는 뜻의 참이다. 셋째, 파라미터 개수가 맞지 않는 count()는 인자를 보지 않아도 결론이 나므로 정적 판정에서 바로 탈락한다.

    log(Object)의 "가능성"이 실제 호출에서 어떻게 갈리는지는 컨테이너에서 확인했다. 다음 어드바이스는 뒤의 "매개변수 전달" 절에서 다룰 바인딩 형식을 미리 쓴 것이다. 여기서는 args(arg,..)와 String arg의 조합을 "첫 번째 인자가 String일 때만"이라는 조건으로 읽으면 된다.

    @Aspect
public class ArgsStringAspect {
    @Before("execution(* com.example.shop..*.*(..)) && args(arg,..)")
    public void before(String arg) {
        System.out.println("  [args String] arg=" + arg);
    }
}

    log("text")를 부를 때는 어드바이스가 실행되고 log(42)를 부를 때는 실행되지 않았다. 같은 메서드, 같은 프록시인데 결과가 호출마다 다르다. 이 판정은 프록시를 만들 때가 아니라 호출할 때마다 일어난다. cancel(7L, "late")도 어드바이스가 실행되지 않았는데, 첫 번째 인자가 Long이어서 args(arg,..)의 arg 자리(어드바이스 파라미터 타입 String)와 맞지 않기 때문이다. cancel의 경우는 선언 타입만으로도 결론이 나므로 실제로는 빈 생성 시점에 이미 걸러진다. 이 두 판정이 스프링 내부에서 어떻게 나뉘는지가 다음 절의 주제다.

    args는 바인딩 없이 타입만 쓸 때도 위처럼 실행 시점 검사가 필요하다. 그래서 args를 단독으로 쓰면 빈 생성 시점에 "아닐 수도 있다"는 판정을 내리지 못하는 메서드가 거의 모든 클래스에 생긴다. 모든 클래스가 Object에게서 물려받은 equals(Object)가 바로 그런 메서드다. 이 사실이 @target 절의 기동 실패로 이어진다.

    한 층 아래 — 빈 생성 시점의 판정과 호출 시점의 판정

    AspectJ 매칭 엔진에는 섀도(shadow)라는 개념이 있다. 섀도는 조인 포인트가 생길 수 있는 코드상의 자리다. AspectJ 컴파일러는 바이트코드를 훑으며 메서드 호출 명령, 필드 접근 명령 같은 자리를 모두 섀도로 보지만, 스프링 AOP에서 섀도는 "어떤 클래스의 어떤 메서드 실행" 하나뿐이다. 매칭 엔진은 포인트컷을 섀도에 대어 보고 ShadowMatch라는 결과를 돌려준다. 이 결과는 세 가지 중 하나다. 항상 매칭(alwaysMatches()가 참), 절대 불일치(neverMatches()가 참), 그리고 실행해 봐야 안다(maybeMatches()는 참이지만 alwaysMatches()는 거짓. maybeMatches()는 항상 매칭일 때도 참을 돌려준다). 세 번째 경우 엔진은 실행 시점에 확인해야 할 남은 조건, 즉 잔여 검사(residue)를 함께 기록한다. "첫 번째 인자가 String의 인스턴스인가" 같은 조건이다.

    빈을 만들 때의 판정은 이 세 결과로 이루어진다. 06회에서 본 자동 프록시 생성기는 빈이 초기화된 뒤 후보 어드바이저마다 AopUtils.canApply를 부른다. 이 메서드는 먼저 ClassFilter.matches(대상 클래스)를 묻는다. AspectJExpressionPointcut은 이 질문을 AspectJ의 couldMatchJoinPointsInType으로 넘기고, within이 맞지 않는 클래스처럼 확실히 아닌 경우는 여기서 끝난다. 통과하면 대상 클래스와 그 인터페이스의 메서드를 하나씩 꺼내 MethodMatcher.matches(메서드, 대상 클래스)를 묻는다. 섀도 판정이 항상 매칭이면 참, 절대 불일치면 거짓, "실행해 봐야 안다"면 대부분 참으로 처리한다. 메서드 하나라도 참이 나오면 그 빈에는 프록시가 만들어진다. 섀도 판정은 비용이 있으므로 결과를 캐시해 둔다. 6.2.19에서는 ShadowMatchUtils라는 클래스의 static 맵에 (포인트컷, 메서드) 쌍을 키로 저장한다.

    호출할 때의 판정은 다른 길로 일어난다. 프록시는 메서드가 호출되면 그 메서드에 적용할 인터셉터 체인을 만들어 캐시해 두고 재사용한다(6.2.19의 AdvisedSupport에는 메서드를 키로 하는 methodCache 필드가 있다). 체인을 만들 때 각 어드바이저의 포인트컷에 isRuntime()을 묻는데, AspectJExpressionPointcut은 표현식 전체에 대해 AspectJ의 mayNeedDynamicTest()를 그대로 돌려준다. 참이면 인터셉터를 InterceptorAndDynamicMethodMatcher라는 포장으로 감싸 체인에 넣는다. 다음은 AspectJProxyFactory로 프록시를 만들고 getInterceptorsAndDynamicInterceptionAdvice(method, targetClass)로 메서드별 체인의 원소 타입을 출력한 결과다. 애스펙트 이름 대신 그 애스펙트의 표현식을 머리글로 적었다.

    == execution(* com.example.shop..*.*(..))
  chain(order): [ExposeInvocationInterceptor, MethodBeforeAdviceInterceptor]
  chain(count): [ExposeInvocationInterceptor, MethodBeforeAdviceInterceptor]
== execution(* com.example.shop..*.*(..)) && args(String)
  chain(order): [ExposeInvocationInterceptor, InterceptorAndDynamicMethodMatcher]
  chain(count): [ExposeInvocationInterceptor]
== @annotation(com.example.shop.Audited)
  chain(order): [ExposeInvocationInterceptor, InterceptorAndDynamicMethodMatcher]
  chain(count): [ExposeInvocationInterceptor]

    execution만 쓴 포인트컷은 어드바이스 인터셉터가 체인에 바로 들어간다. 호출할 때 다시 물을 것이 없다. args(String)이 섞이면 order의 체인에는 포장된 인터셉터가 들어가고, 파라미터가 없는 count의 체인에서는 아예 빠진다. count는 섀도 판정에서 절대 불일치가 나왔기 때문이다. 흥미로운 것은 @annotation이다. 메서드에 붙은 애너테이션은 선언만 보고 알 수 있는데도 포장이 붙었다. isRuntime()이 메서드별이 아니라 표현식 전체에 대해 답하기 때문이다(앞의 실험에서 @annotation, @within, this, target 모두 isRuntime=true였다). 다만 이 경우 캐시된 섀도 판정이 이미 "항상 매칭"이므로, 호출할 때의 검사(matchesJoinPoint)는 실제 객체나 인자와 상관없이 참으로 끝난다.

    포장된 인터셉터를 만났을 때의 처리는 ReflectiveMethodInvocation.proceed()에 있다. 바이트코드를 javap -c로 열어 보면 체인의 다음 원소가 InterceptorAndDynamicMethodMatcher인지 instanceof로 확인하고, 맞으면 matcher().matches(Method, Class, Object[])를 부른 뒤 참일 때만 interceptor().invoke(...)를 부르는 흐름이 보인다. 거짓이면 그 인터셉터를 건너뛰고 다음 원소로 넘어간다. 앞 절에서 log(42)를 부를 때 어드바이스가 실행되지 않은 것이 바로 이 건너뛰기다.

    세 인자짜리 matches는 실제 객체가 필요하다. 그런데 MethodMatcher의 시그니처에는 메서드, 클래스, 인자 배열만 있고 프록시나 대상 객체는 없다. AspectJExpressionPointcut은 이 정보를 ExposeInvocationInterceptor에서 얻는다. 위 출력에서 모든 체인의 맨 앞에 있던 그 인터셉터다. 이 인터셉터는 현재 진행 중인 MethodInvocation을 static ThreadLocal에 넣어 두고 다음 인터셉터로 진행한다. 01회에서 본 ThreadLocal이 여기서 쓰인다. 같은 스레드에서 체인을 따라 내려가는 동안이라면 어디서든 "지금 처리 중인 호출"을 꺼낼 수 있다. @Aspect 기반 어드바이저가 있으면 스프링이 이 인터셉터를 체인 맨 앞에 자동으로 추가한다.

    정리하면 지시자의 성격에 따라 판정 비용이 놓이는 곳이 다르다. execution과 within은 빈을 만들 때 모든 결론이 난다. @annotation, @within은 결론은 빈 생성 때 나지만 체인에는 동적 포장이 붙는다. args, @args, @target, this, target은 호출마다 실제 객체를 보고 다시 판정한다. 그리고 "실행해 봐야 안다"는 판정은 빈 생성 시점에 프록시를 만드는 쪽으로 기운다. 이 마지막 성질이 다음 절의 문제를 만든다.

    @target과 @within — 부모에게서 물려받은 메서드

    두 지시자 모두 클래스에 붙은 애너테이션으로 고른다. 레퍼런스의 정의는 이렇다. @target은 "실행 중인 객체의 클래스(the class of the executing object)"가 그 애너테이션을 가진 조인 포인트를 고르고, @within은 그 애너테이션을 가진 타입 안의 조인 포인트, 스프링 AOP로 말하면 "그 애너테이션을 가진 타입에 선언된 메서드의 실행"을 고른다. 한쪽은 객체를 보고 다른 쪽은 선언을 본다. 이 차이는 상속받은 메서드에서 드러난다.

    public class BaseService {
    public void parentMethod() { }
}

@Tracked
public class ChildService extends BaseService {
    public void childMethod() { }
}

@Aspect
public class AtWithinAspect {
    @Before("@within(com.example.shop.Tracked)")
    public void before(JoinPoint jp) { /* [@within] 시그니처 출력 */ }
}

@Aspect
public class AtTargetAspect {
    @Before("@target(com.example.shop.Tracked) && within(com.example.shop..*)")
    public void before(JoinPoint jp) { /* [@target] 시그니처 출력 */ }
}

    ChildService 빈을 등록하고 각 애스펙트를 따로 적용한 컨테이너에서 childMethod()와 parentMethod()를 차례로 불렀다.

    == @within
child.childMethod()
  [@within] ChildService.childMethod target=ChildService
child.parentMethod()
== @target
child.childMethod()
  [@target] ChildService.childMethod target=ChildService
child.parentMethod()
  [@target] BaseService.parentMethod target=ChildService

    childMethod는 둘 다 적용됐다. ChildService에 선언되어 있고 실행 중인 객체도 ChildService이기 때문이다. parentMethod에서 갈린다. 이 메서드의 선언 위치는 BaseService다(시그니처가 BaseService.parentMethod로 찍힌 것을 보라). BaseService에는 @Tracked가 없으므로 @within은 고르지 않는다. 반면 이 메서드를 실행하고 있는 객체는 ChildService 인스턴스이고 그 클래스에는 @Tracked가 있으므로 @target은 고른다. "애너테이션이 붙은 클래스의 객체라면 부모에게서 물려받은 메서드까지"가 필요하면 @target, "그 클래스에 직접 선언된 메서드만"이면 @within이다.

    부모 클래스에서 물려받은 메서드를 @within은 고르지 않고 @target은 고르는 이유를 클래스 계층과 실행 중 객체로 보여 준다. 위아래 두 단의 클래스 다이어그램. 위 상자 "BaseService" 안에 메서드 "parentMethod()". 아래 상자 "ChildService" 왼쪽 위 모서리에 노란 꼬리표 "@Tracked", 안에 메서드 "childMethod()". 아래 상자에서 위 상자로 속이 빈 삼각형 상속 화살표. 오른쪽에 동그란 객체 아이콘 "실행 중인 객체: ChildService 인스턴스"가 있고 아래 상자와 점선으로 연결. 왼쪽 여백에 초록 체크 표시 둘: "@within: childMethod만", 오른쪽 여백에 "@target: childMethod, parentMethod" 라벨. parentMethod 옆에는 "@within ✕ / @target ✓" 작은 표시. 플랫 스타일, 흰 배경. @within은 메서드가 선언된 타입을 보고, @target은 실행 중인 객체의 클래스를 본다.

    이제 위 코드에서 @target 쪽에만 && within(com.example.shop..*)을 붙여 둔 이유를 볼 차례다. 선언을 보는 @within은 빈 생성 시점에 결론을 낸다. 실험에서 @within(Tracked)을 @Tracked가 없는 클래스에 대어 보면 canApply가 거짓이었다. 그러나 @target은 "실행 중인 객체의 클래스"를 보는 지시자라서 AspectJ 엔진은 이를 실행 시점 검사로 다룬다. 같은 실험에서 @target(Tracked)은 애너테이션이 전혀 없는 클래스에 대해서도 canApply가 참이었고, 그 클래스의 모든 메서드에 대한 정적 판정이 참이었다. 결국 @target을 단독으로 쓰면 컨테이너의 거의 모든 빈에 프록시를 만들려고 한다.

    그것이 어떤 결과로 이어지는지 확인하려고 final 클래스 하나를 빈으로 함께 등록했다.

    package com.example.infra;

public final class FinalBean {
    public void hello() { }
}

@Aspect
public class AtTargetAloneAspect {
    @Before("@target(com.example.shop.Tracked)")   // 범위 지정 없이 단독
    public void before(JoinPoint jp) { }
}

  Could not generate CGLIB subclass of class com.example.infra.FinalBean:
  Common causes of this problem include using a final class or a non-visible class
...
Caused by: java.lang.IllegalArgumentException: Cannot subclass final class com.example.infra.FinalBean
	at org.springframework.cglib.proxy.Enhancer.generateClass(Enhancer.java:653)

    FinalBean에는 @Tracked가 없고 패키지도 다르다. 그런데도 자동 프록시 생성기는 이 빈에 프록시가 필요하다고 판단했고, 인터페이스가 없는 클래스이니 CGLIB로 하위 클래스를 만들려다 04회에서 본 CGLIB의 제약(final 클래스는 상속할 수 없다)에 걸려 기동 자체가 실패했다. args(String) 단독으로도 똑같이 실패했다. FinalBean.hello()는 파라미터가 없으니 args(String)과 무관한데, 실험해 보면 hello에 대한 판정은 거짓이고 Object에게서 물려받은 equals(Object)에 대한 판정이 참이었다. equals에 String이 넘어올 수도 있으니 "실행해 봐야 안다"이고, 이것만으로 프록시 대상이 된다. @args 단독도 FinalBean에 대해 canApply가 참이었다.

    해결은 범위 지정 지시자를 함께 쓰는 것이다. @target(com.example.shop.Tracked) && within(com.example.shop..*)은 FinalBean에 대해 canApply가 거짓이었다. &&로 묶인 표현식에서 within이 클래스 단계에서 거짓을 내면 나머지는 볼 필요도 없기 때문이다. execution(* com.example.shop..*.*(..)) && @args(com.example.shop.Sensitive)도 마찬가지로 거짓이었다. 스프링 부트 애플리케이션에는 직접 만들지 않은 빈이 수백 개 등록되는 일이 흔하고, 그중 하나라도 프록시로 만들 수 없는 빈이면 위와 같은 기동 실패가 난다. 실패하지 않더라도 쓸모없는 프록시가 잔뜩 생기고 그 모든 호출에 동적 검사가 끼어든다. 레퍼런스가 "범위 지정 지시자를 가능하면 항상 포함하라"고 권하는 것은 AspectJ 위빙의 성능 이야기이지만, 스프링 AOP에서는 이처럼 정확성의 문제이기도 하다.

    @annotation과 @args — 메서드와 인자의 애너테이션

    @annotation은 실행되는 메서드 자체에 그 애너테이션이 붙어 있으면 고른다. 실험에서 @annotation(com.example.shop.Audited)은 @Audited가 붙은 order에 매칭되고 count에는 매칭되지 않았다. 원하는 메서드에 표시를 달아 두고 그 표시로 어드바이스를 거는 방식은 대상이 명확해서 실무에서 많이 쓴다. 표현식이 패키지 구조나 메서드 이름에 의존하지 않으므로 리팩터링에도 덜 깨진다.

    주의할 점이 하나 있다. 애너테이션을 인터페이스의 메서드에만 붙이면 어떻게 될까. 인터페이스 Api의 run()에만 @Audited를 붙이고 구현 클래스의 run()에는 붙이지 않은 채 @annotation(Audited) 어드바이스를 걸어 보았다. JDK 프록시 설정과 CGLIB 설정 모두에서 프록시가 아예 만들어지지 않았다(꺼낸 빈의 클래스가 ApiImpl 그대로였다). 자바에서 메서드에 붙은 애너테이션은 재정의한 메서드로 상속되지 않는다. java.lang.annotation.Inherited 메타 애너테이션도 클래스에 붙은 애너테이션을 상위 클래스에서 물려받게 할 뿐이고, 구현한 인터페이스의 애너테이션에는 효과가 없다고 Javadoc에 적혀 있다. 매칭 엔진은 실행되는 메서드, 즉 구현 클래스의 run()을 보므로 표시를 찾지 못한다.

    @args는 넘어온 인자 객체의 실제 클래스에 그 애너테이션이 붙어 있으면 고른다. args와 @annotation을 섞은 것으로 이해하면 된다. 실행 시점의 인자를 봐야 하므로 동적 판정이다.

    @Sensitive public class CardInfo { }
public class PlainInfo { }

public class PaymentService {
    public void pay(Object payload) { }
}

@Aspect
public class AtArgsAspect {
    @Before("execution(* com.example.shop..*.*(..)) && @args(com.example.shop.Sensitive)")
    public void before(JoinPoint jp) { /* [@args] 시그니처와 인자 클래스 출력 */ }
}
    pay(CardInfo)
  [@args] PaymentService.pay arg=CardInfo
pay(PlainInfo)

    같은 pay(Object) 메서드인데 CardInfo를 넘길 때만 어드바이스가 실행됐다. 선언된 파라미터 타입은 Object이고 Object에는 @Sensitive가 없지만, @args는 선언이 아니라 넘어온 객체의 클래스를 본다. 레퍼런스의 예에서도 @args(X)는 파라미터가 하나인 메서드에서 넘어온 그 인자의 클래스를 본다. 앞 절에서 본 대로 @args도 단독으로 쓰면 모든 빈을 프록시 후보로 만들므로 execution이나 within과 함께 써야 한다.

    bean — 스프링만의 지시자

    bean은 AspectJ에 없는, 스프링 AOP가 추가한 지시자다. bean(빈 이름) 형식으로 스프링 빈의 이름(id 또는 name)으로 고르고, * 와일드카드를 쓸 수 있다. 레퍼런스는 이 지시자가 스프링 AOP에서만 지원되고 네이티브 AspectJ 위빙에서는 지원되지 않는다고 적는다. AspectJ 컴파일러(ajc)나 로드 타임 위빙은 스프링 컨테이너의 빈 이름이라는 개념을 모르기 때문이다.

    @Aspect
public class BeanNameAspect {
    @Before("bean(order*)")
    public void before(JoinPoint jp) { /* [bean(order*)] 시그니처 출력 */ }
}

    이름이 orderService인 빈에는 적용되고 paymentService에는 적용되지 않았다. AspectJ의 파서는 모르는 지시자를 받으면 거부하는데, 어떻게 bean이 통과할까. AspectJ는 외부에서 지시자를 추가할 수 있는 확장점(PointcutDesignatorHandler)을 제공하고, AspectJExpressionPointcut은 파서를 만들 때 bean이라는 이름의 핸들러(BeanPointcutDesignatorHandler)를 등록한다. 그 핸들러가 만드는 매처는 지금 프록시를 만들고 있는 빈의 이름을 ProxyCreationContext에서 꺼내 패턴과 비교한다. javap로 보면 ProxyCreationContext는 static final ThreadLocal 필드 하나를 가진 클래스다. 여기서도 ThreadLocal이 "메서드 시그니처로 넘길 수 없는 문맥"을 전달하는 통로로 쓰인다.

    그래서 bean은 자동 프록시 생성기가 빈을 처리하는 도중에만 의미가 있다. 실험에서 컨테이너 없이 AspectJExpressionPointcut에 bean(order*)를 넣고 canApply를 물었을 때는 어떤 클래스에 대해서도 거짓이었다. 빈 이름으로 고르는 방식은 간편하지만, 빈 이름은 코드의 구조가 아니라 등록 방식에서 나오는 값이다. 빈 이름을 바꾸거나 같은 패턴의 이름을 가진 빈이 새로 생기면 AOP 적용 범위가 조용히 바뀐다. 범위를 정확히 통제해야 하는 곳에서는 타입이나 애너테이션 기반 지시자가 더 안전하다.

    매개변수 전달 — 표현식에서 어드바이스로 값 넘기기

    지금까지는 지시자에 타입 이름을 썼다. 타입 자리에 이름을 쓰면 바인딩 형식이 된다. 레퍼런스의 설명대로 args(account,..)는 두 가지 일을 한다. 첫째, 첫 번째 파라미터로 넘어온 인자가 어드바이스 메서드의 account 파라미터 타입의 인스턴스인 메서드 실행만 고르도록 제한한다. 둘째, 그 실제 객체를 account 파라미터로 어드바이스에 넘긴다. 바인딩할 수 있는 지시자는 args 외에 this(프록시), target(대상 객체), @within, @target, @annotation, @args(애너테이션 객체)다.

    파라미터 이름은 어디서 오는가

    바인딩은 "표현식에 쓴 이름"과 "어드바이스 메서드의 파라미터 이름"을 맞추는 일이다. 그런데 자바 클래스 파일에는 기본적으로 메서드의 파라미터 이름이 남지 않는다. 메서드 디스크립터에는 타입만 있다. javac에 -parameters 옵션을 주면 컴파일러가 각 메서드에 MethodParameters라는 속성을 추가해 이름을 기록하고, 이것을 java.lang.reflect.Parameter API로 읽을 수 있다. 같은 어드바이스를 두 방식으로 컴파일해 javap -v로 비교하면 차이가 그대로 보인다.

      public void b(java.lang.String);
    descriptor: (Ljava/lang/String;)V
    flags: (0x0001) ACC_PUBLIC
    // ... Code 속성 생략
    MethodParameters:
      Name                           Flags
      arg
    RuntimeVisibleAnnotations:
        org.aspectj.lang.annotation.Before(
          value="execution(* com.example.shop..*.*(..)) && args(arg,..)"

    디스크립터 (Ljava/lang/String;)V에는 타입만 있고 이름은 MethodParameters 속성에만 있다. 같은 소스를 -parameters 없이 컴파일한 클래스에서는 이 속성이 나타나지 않았다. 포인트컷 표현식 문자열은 어드바이스 애너테이션의 값으로 클래스 파일에 그대로 들어 있고, 스프링은 실행 중에 리플렉션으로 이 문자열을 읽어 파싱한다.

    스프링 레퍼런스는 스프링 AOP가 파라미터 이름을 알아내는 방법을 차례로 나열한다. 어드바이스 애너테이션의 argNames 속성에 직접 적은 이름(AspectJAnnotationParameterNameDiscoverer), 코틀린 리플렉션, 표준 리플렉션의 Parameter API(-parameters 필요, 레퍼런스가 권장하는 방식), 마지막으로 포인트컷 표현식과 returning/throwing 절에서 이름을 추론하는 AspectJAdviceParameterNameDiscoverer다. 앞에서 성공한 것이 이기고, 모두 실패하면 예외가 난다. 과거에는 디버그 정보의 지역 변수 테이블을 바이트코드에서 읽어 이름을 알아내는 방법도 있었지만, 스프링 프레임워크 6.1 릴리스 노트는 LocalVariableTableParameterNameDiscoverer가 제거되었고 더 이상 바이트코드를 파싱해 파라미터 이름을 추론하지 않는다고 밝힌다. 스프링 부트 Gradle 플러그인은 자바 플러그인이 적용되면 모든 JavaCompile 작업에 -parameters를 설정한다.

    -parameters 없이 컴파일하면 어떻게 되는지도 실험했다. 바인딩 변수가 하나뿐인 어드바이스(args(arg,..)와 String arg)는 문제없이 동작했다. 추론기가 "이름 하나, 빈 자리 하나"를 짝지을 수 있기 때문이다. 그러나 this(proxy) && target(target)처럼 같은 단계에서 바인딩할 변수가 둘 이상이면 컨테이너 기동이 실패했다.

    둘 다 Object 타입인 proxy와 target 중 어느 것이 this이고 어느 것이 target인지 이름 없이는 정할 방법이 없다는 뜻이다. 해결책은 -parameters로 컴파일하거나, 어드바이스 애너테이션에 argNames = "itemId,proxy,target,tracked,audited"처럼 순서대로 이름을 적어 주는 것이다. 레퍼런스에 따르면 첫 번째 파라미터가 JoinPoint, ProceedingJoinPoint, JoinPoint.StaticPart 타입이면 argNames에서 그 이름은 생략할 수 있다.

    제네릭 타입 파라미터에도 바인딩이 동작하지만 한계가 있다. 레퍼런스는 void sampleGenericMethod(T param)을 args(param)과 MyType param으로 좁히는 것은 가능하지만, Collection 같은 제네릭 컬렉션으로는 좁힐 수 없다고 설명한다. 컬렉션의 모든 원소를 검사해야 하고 null을 어떻게 다룰지도 정할 수 없기 때문이다. 이 경우 Collection으로 받아 원소 타입을 직접 확인해야 한다.

    this와 target — 프록시를 볼 것인가, 원본을 볼 것인가

    레퍼런스는 this를 "빈 참조(스프링 AOP 프록시)가 주어진 타입의 인스턴스인" 조인 포인트로, target을 "대상 객체(프록시되는 애플리케이션 객체)가 주어진 타입의 인스턴스인" 조인 포인트로 정의한다. 그리고 AspectJ 자체에서는 실행 조인 포인트의 this와 target이 같은 객체(메서드를 실행하는 객체)를 가리키지만, 프록시 기반인 스프링 AOP는 프록시 자체(this)와 프록시 뒤의 대상 객체(target)를 구분한다고 덧붙인다. 둘 다 정확한 타입 이름만 받는다. this(com.example.shop..*)나 target(com.example.shop.Order*)처럼 와일드카드를 쓰면 "error wildcard type pattern not allowed, must use type name"이라는 파싱 오류가 났다. 상속 관계는 자동으로 따진다. 인스턴스 검사이므로 부모 타입을 써도 매칭된다.

    둘의 차이는 프록시 기술에 따라 드러난다. OrderService 인터페이스를 구현한 OrderServiceImpl을 JDK 동적 프록시와 CGLIB로 각각 프록시하고, 세 표현식을 하나씩 적용해 order("A1")을 불렀다.

    04회에서 본 프록시의 구조를 떠올리면 이유가 바로 보인다. JDK 동적 프록시가 만드는 $Proxy 클래스는 java.lang.reflect.Proxy를 상속하고 OrderService 인터페이스를 구현한 클래스다. OrderServiceImpl과는 아무 관계가 없다. 그래서 "프록시가 OrderServiceImpl의 인스턴스인가"라는 this(OrderServiceImpl)의 질문에 거짓이 나온다. CGLIB 프록시는 OrderServiceImpl을 상속한 하위 클래스이므로 참이다. target은 프록시 뒤의 원본, 즉 언제나 OrderServiceImpl 인스턴스를 보므로 프록시 기술과 상관없이 참이다. 인터페이스를 지정한 this(OrderService)는 두 프록시 모두 그 인터페이스를 구현하므로 참이다.

    this는 프록시 객체를, target은 원본 객체를 검사하며, JDK 프록시는 구현 클래스의 하위 타입이 아니라서 this(구현 클래스)가 거짓이 되는 이유. 좌우 두 칸 비교 그림. 왼쪽 칸 제목 "JDK 동적 프록시": 위에 "OrderService" 인터페이스 상자, 그 아래 왼쪽에 "$Proxy" 상자, 오른쪽에 "OrderServiceImpl" 상자. 두 상자 모두 인터페이스 상자로 점선 구현 화살표. "$Proxy"에서 "OrderServiceImpl"로 실선 화살표 "위임". "$Proxy" 아래에 "this" 꼬리표와 빨간 ✕ "this(OrderServiceImpl)", "OrderServiceImpl" 아래에 "target" 꼬리표와 초록 ✓. 오른쪽 칸 제목 "CGLIB": "OrderServiceImpl" 상자 아래에 "OrderServiceImpl$$SpringCGLIB" 상자가 실선 상속 화살표로 연결, 그 옆에 원본 "OrderServiceImpl" 객체로 "위임" 화살표. 프록시 아래 "this" 꼬리표와 초록 ✓, 원본 아래 "target" 꼬리표와 초록 ✓. 플랫 스타일, 흰 배경. this는 프록시를, target은 원본을 본다. JDK 프록시는 구현 클래스의 하위 타입이 아니다.

    한 가지 더 눈여겨볼 점이 있다. JDK 프록시 설정에서 this(OrderServiceImpl)을 적용했을 때 꺼낸 빈은 $Proxy11이었다. 프록시는 만들어졌는데 어드바이스는 한 번도 실행되지 않은 것이다. 빈을 만드는 시점에는 아직 프록시가 없으므로, 정적 판정은 대상 클래스(OrderServiceImpl)를 기준으로 하고 "가능하다"는 결론을 낸다. 실제로 this(OrderServiceImpl)은 OrderServiceImpl에 대해 canApply가 참이고, 무관한 PaymentService에 대해서는 거짓이었다. 호출 시점이 되어서야 AspectJExpressionPointcut이 ThreadLocal에서 꺼낸 진짜 프록시 객체의 클래스로 this 조건을 다시 검사하고, 거기서 거짓이 나와 어드바이스를 건너뛴다. 이 메서드의 소스 주석에도 스프링 AOP 프록시를 AspectJ의 this에, 스프링 AOP의 대상 객체를 AspectJ의 target에 묶는다고 적혀 있다.

    this와 target은 레퍼런스의 말대로 바인딩 형식으로 더 자주 쓰인다. 앞 절의 BindAllAspect 출력에서 proxy가 $Proxy11 또는 OrderServiceImpl$$SpringCGLIB$$0이고 target이 OrderServiceImpl이었던 것이 바로 이 구분이다. 타입 조건으로 쓸 때는 어느 프록시 기술이 쓰일지에 따라 결과가 달라질 수 있다는 점을 염두에 둔다. 스프링 부트는 기본이 CGLIB이지만 spring.aop.proxy-target-class=false로 바꾸면 인터페이스가 있는 빈은 JDK 프록시가 되고, 그 순간 this(구현 클래스)로 건 어드바이스는 조용히 꺼진다. 프록시 기술 차이가 타입 캐스팅과 의존관계 주입에 미치는 영향은 10회에서 이어서 다룬다.

    포인트컷 지시자(PCD)
    포인트컷 표현식의 첫 단어로, 무엇을 기준으로 조인 포인트를 고를지 정한다. 스프링 AOP는 AspectJ 지시자 아홉 개와 스프링 전용 bean을 지원하고, 조인 포인트는 메서드 실행뿐이다.
    execution
    클래스 파일에 기록된 메서드 선언과 비교한다. 선언 타입 자리는 부모 타입이 선언한 메서드의 재정의까지 넓혀 주지만, 파라미터와 반환 타입은 상속도 박싱도 고려하지 않는다.
    within
    메서드가 정의된 타입만 본다. 부모 타입을 쓰면 매칭되지 않으므로 +가 필요하며, 클래스 필터 단계에서 결론이 나서 빠르다.
    args와 @args
    호출 시점에 넘어온 인자 객체의 실제 타입(또는 그 클래스의 애너테이션)을 본다. 호출마다 다시 판정되며, 단독으로 쓰면 거의 모든 빈이 프록시 후보가 된다.
    @within과 @target
    @within은 메서드가 선언된 타입의 애너테이션을, @target은 실행 중인 객체 클래스의 애너테이션을 본다. 부모에게서 물려받은 메서드는 @target만 고른다.
    정적 판정과 동적 판정
    빈 생성 시 섀도 판정은 항상/절대/실행해 봐야 앎 중 하나다. 표현식이 동적 검사를 필요로 할 수 있으면 인터셉터가 InterceptorAndDynamicMethodMatcher로 감싸져 호출마다 다시 검사된다.
    this와 target
    this는 프록시 객체, target은 원본 객체를 검사하거나 바인딩한다. JDK 프록시는 구현 클래스의 하위 타입이 아니어서 this(구현 클래스)가 거짓이다.
    매개변수 바인딩
    타입 자리에 이름을 쓰면 값을 어드바이스로 넘기고, 어드바이스 파라미터 타입이 매칭 조건이 된다. 이름은 -parameters가 남긴 MethodParameters 속성이나 argNames에서 온다.

    실무에서 포인트컷 문제는 대개 "어드바이스가 안 붙는다"와 "기동이 안 된다" 두 형태로 나타난다. 앞의 경우 가장 먼저 의심할 것은 표현식의 오타다. 스프링 6.2.19에서 확인한 대로 잘못된 타입 이름이나 지원하지 않는 지시자는 기동을 막지 않고 DEBUG 로그만 남긴다. 그다음은 execution의 파라미터·반환 타입이 선언과 정확히 일치하는지, 애너테이션이 인터페이스에만 붙어 있지 않은지, this(구현 클래스)를 JDK 프록시 환경에서 쓰고 있지 않은지를 본다. 어드바이스 파라미터 타입을 바꾼 커밋이 적용 범위를 바꿨을 가능성도 있다.

    뒤의 경우, 즉 AOP를 추가했더니 무관한 빈에서 "Could not generate CGLIB subclass"가 난다면 args, @args, @target을 범위 지정 없이 단독으로 쓴 포인트컷을 찾는다. 이 지시자들은 빈 생성 시점에 "아니다"라고 말하지 못하므로 모든 빈을 프록시로 감싸려 한다. 해결은 within이나 execution으로 범위를 묶는 것이다. 판단이 달라지는 조건은 프로젝트에 final 클래스 빈이 있는지인데, 지금 없더라도 나중에 생길 수 있으므로 범위 지정은 처음부터 넣는 것이 맞다.

    설계 관점에서는 "무엇이 대상을 정의하는가"를 먼저 정한다. 계층 전체에 일괄 적용하는 횡단 관심사(로그, 지표)는 패키지 기반의 within/execution이 자연스럽고, 메서드마다 적용 여부와 설정이 다른 관심사(감사, 재시도, 권한)는 애너테이션 기반이 명확하다. 애너테이션 방식은 대상 코드에 표시가 남아 읽는 사람이 적용 여부를 바로 알 수 있다는 장점과, 표시를 잊으면 적용되지 않는다는 단점을 함께 가진다. 성능이 문제 될 만큼 호출이 잦은 경로라면 호출마다 동적 검사가 필요한 지시자를 피하고, 빈 생성 시점에 결론이 나는 조건으로 대상을 좁힌다.

OrderServiceImpl은 OrderService를 구현한다. 무슨 일이 일어나는가? 프록시가 만들어지지 않고 어드바이스도 실행되지 않는다. 프록시가 만들어지고 어드바이스가 매번 실행된다. 와일드카드가 없어 파싱 오류로 기동이 실패한다. 프록시는 만들어지지만, 호출할 때 프록시 객체가 OrderServiceImpl의 인스턴스가 아니므로 어드바이스는 실행되지 않는다. 빈 생성 시점에는 대상 클래스 기준으로 "가능하다"고 판정해 JDK 프록시($Proxy)를 만든다. 호출 시점에 실제 프록시 클래스로 this를 다시 검사하는데, JDK 프록시는 Proxy를 상속하고 OrderService만 구현하므로 거짓이 되어 어드바이스를 건너뛴다. this는 정확한 타입 이름을 받으므로 와일드카드가 없는 것이 정상이다. @Before("execution(* com.example..*.*(..)) && this(proxy) && target(target)")와 before(Object proxy, Object target) 어드바이스를 -parameters 없이 컴파일했다(스프링 6.2.19). 결과는? 바이트코드의 지역 변수 테이블에서 이름을 읽어 정상 동작한다. 이름을 추론할 수 없어 AmbiguousBindingException으로 기동이 실패한다. 파라미터 순서대로 this, target에 배정되어 정상 동작한다. 바인딩을 무시하고 두 파라미터에 null이 들어간다. 스프링 6.1에서 지역 변수 테이블을 읽는 방식이 제거되었다. MethodParameters 속성이 없으면 표현식에서 이름을 추론하는 방식만 남는데, 같은 타입의 바인딩 변수가 둘이면 어느 쪽이 this인지 정할 수 없어 예외가 난다. -parameters로 컴파일하거나 argNames를 지정해야 한다.
    포인트컷 지시자(pointcut designator, PCD)
    포인트컷 표현식에서 조인 포인트를 고르는 기준을 정하는 키워드. execution, within, args 등이 있다.
    조인 포인트(join point)
    어드바이스를 끼워 넣을 수 있는 프로그램 실행 지점. AspectJ에는 여러 종류가 있지만 스프링 AOP에서는 메서드 실행뿐이다.
    섀도(shadow)
    조인 포인트가 생길 수 있는 코드상의 자리. AspectJ 매칭 엔진은 섀도에 대해 항상 매칭, 절대 불일치, 실행해 봐야 앎 중 하나의 ShadowMatch를 돌려준다.
    잔여 검사(residue)
    정적 분석만으로 결론이 나지 않을 때 실행 시점에 확인하도록 남겨 둔 조건. 인자의 실제 타입이나 객체 클래스의 애너테이션 검사 같은 것이다.
    타입 패턴(type pattern)
    *, .., +를 써서 여러 타입을 한꺼번에 가리키는 표기. com.example..*는 하위 패키지까지의 모든 타입, OrderService+는 그 타입과 하위 타입이다.
    동적 메서드 매처(dynamic method matcher)
    isRuntime()이 참이어서 호출마다 인자와 함께 다시 판정되는 매처. 스프링은 이런 어드바이스를 InterceptorAndDynamicMethodMatcher로 감싸 체인에 넣는다.
    MethodParameters 속성
    javac -parameters로 컴파일할 때 클래스 파일의 메서드에 추가되는 속성으로, 파라미터 이름을 기록한다. 리플렉션의 Parameter.getName()이 이 값을 읽는다.
    ProxyCreationContext
    자동 프록시 생성기가 지금 처리 중인 빈의 이름을 ThreadLocal에 노출하는 스프링 클래스. bean 지시자가 이 값을 읽어 매칭한다.
