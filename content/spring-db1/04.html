    이 회차의 질문: 트랜잭션 코드는 어디에 있어야 하는가

    앞 회차에서 트랜잭션은 커넥션 단위로 걸린다는 것을 확인했다. 데이터베이스 서버는 커넥션 하나마다 세션을 하나 만들고, 자동 커밋을 끈 세션에서 실행한 SQL들이 커밋이나 롤백을 만날 때까지 하나의 트랜잭션으로 묶인다. 그래서 계좌이체처럼 두 번의 update를 원자적으로 처리하려면 두 SQL이 반드시 같은 커넥션으로 나가야 한다. 이 사실 하나가 이 회차 전체의 출발점이다.

    문제는 그 "같은 커넥션"을 누가 열고, 누가 들고 다니고, 누가 닫느냐다. 가장 단순한 방법은 서비스 메서드가 커넥션을 직접 열어 자동 커밋을 끄고, 그 커넥션을 리포지토리 메서드에 파라미터로 넘기는 것이다. 동작은 한다. 하지만 그렇게 하면 비즈니스 규칙만 담아야 할 서비스 코드가 java.sql 패키지로 뒤덮인다. 이 회차는 그 코드를 네 단계에 걸쳐 걷어 낸다. 트랜잭션 매니저로 기술을 추상화하고, 트랜잭션 동기화로 커넥션 파라미터를 없애고, 트랜잭션 템플릿으로 반복 코드를 없애고, 마지막으로 AOP 프록시로 서비스에서 트랜잭션 코드를 완전히 몰아낸다.

    단계마다 질문은 같다. "지금 이 순간 커넥션은 어디에 있는가." 파라미터로 넘어가는가, 스레드에 묶여 있는가, 프록시가 열었는가. 이 질문을 놓치지 않으면 @Transactional 한 줄 뒤에서 일어나는 일이 전부 보인다. 이 회차의 실행 결과는 Spring Framework 7.0.10, H2 2.4.240, JDK 21로 직접 돌려 얻은 것이다. 이 강좌의 기준 버전은 Spring Framework 6.x와 Spring Boot 3.x이므로, 규칙에 해당하는 부분(트랜잭션 템플릿의 롤백 규칙, 커넥션 획득·반환 로직, 프록시 클래스 이름 규칙, 부트 자동 구성)은 6.2.x와 Boot 3.x의 소스·문서로 따로 대조했다.

    문제점들: 서비스 계층에 새어 든 JDBC

    애플리케이션은 흔히 세 계층으로 나눈다. HTTP 요청과 응답을 다루는 프레젠테이션 계층(컨트롤러), 비즈니스 규칙을 담는 서비스 계층, 데이터베이스에 접근하는 데이터 접근 계층(리포지토리)이다. 이렇게 나누는 이유는 변경의 이유를 분리하기 위해서다. 웹 기술이 바뀌면 컨트롤러만, 데이터 접근 기술이 바뀌면 리포지토리만 고치고, 회사의 가장 중요한 자산인 비즈니스 규칙은 그대로 두고 싶다. 그러려면 서비스 계층은 특정 기술에 의존하지 않는 순수한 자바 코드에 가까울수록 좋다.

    이제 앞 회차 방식으로 계좌이체 서비스를 써 보자. 예제의 테이블은 이 권 1회차에서 만든 account(account_id, balance)를 그대로 쓴다. "EX"라는 계좌로 이체하면 일부러 예외를 던져 롤백 상황을 만든다.

    public class TransferServiceV0 {

    private final DataSource dataSource;
    private final AccountRepositoryV0 repository;
    // 생성자 ...

    public void transfer(String fromId, String toId, int amount) throws SQLException {
        Connection con = dataSource.getConnection();
        try {
            con.setAutoCommit(false);                       // 트랜잭션 시작
            int fromBalance = repository.findBalance(con, fromId);
            repository.updateBalance(con, fromId, fromBalance - amount);
            if (toId.equals("EX")) {
                throw new IllegalStateException("transfer failed");
            }
            int toBalance = repository.findBalance(con, toId);
            repository.updateBalance(con, toId, toBalance + amount);
            con.commit();                                   // 성공하면 커밋
        } catch (Exception e) {
            con.rollback();                                 // 실패하면 롤백
            throw new IllegalStateException(e);
        } finally {
            if (con != null) {
                try {
                    con.setAutoCommit(true);                // 풀에 돌려주기 전에 원래대로
                    con.close();
                } catch (Exception e) {
                    // 로그만 남긴다 ...
                }
            }
        }
    }
}

    비즈니스 규칙은 가운데 다섯 줄뿐이다. 나머지는 전부 트랜잭션과 커넥션을 위한 코드다. 이 코드가 가진 문제를 세 갈래로 나눠 보자.

    문제 1. 트랜잭션 문제

    첫째, 서비스가 JDBC 기술에 의존한다. javax.sql.DataSource, java.sql.Connection, setAutoCommit, commit, rollback이 서비스 코드에 그대로 박혀 있다. 데이터 접근 기술을 JPA로 바꾸면 트랜잭션을 시작하는 방법 자체가 달라진다. JPA에서는 EntityManager에서 EntityTransaction을 얻어 begin(), commit(), rollback()을 호출한다. 리포지토리만 바꾸면 될 줄 알았는데 서비스의 트랜잭션 코드까지 전부 고쳐야 한다. 계층을 나눈 의미가 사라진다.

    둘째, 같은 커넥션을 쓰기 위해 커넥션을 파라미터로 넘긴다. 그 결과 리포지토리에는 커넥션을 받는 메서드와 받지 않는 메서드가 두 벌씩 생기기 쉽다. 트랜잭션이 필요한 곳에서는 받는 버전을, 필요 없는 곳에서는 스스로 커넥션을 여는 버전을 써야 하기 때문이다. 또 커넥션을 받은 리포지토리 메서드는 그 커넥션을 절대 닫으면 안 된다. 닫는 순간 서비스가 아직 진행 중인 트랜잭션이 끊긴다. "누가 닫는가"라는 규칙이 코드에 드러나지 않고 개발자의 기억에만 남는다.

    셋째, try, catch, finally로 이루어진 같은 모양의 코드가 트랜잭션이 필요한 모든 서비스 메서드에 반복된다. 이체, 입금, 출금, 해지 메서드마다 똑같은 스무 줄이 붙는다.

    문제 2. 예외 누수

    리포지토리가 던지는 SQLException은 체크 예외(checked exception)다. 서비스가 이것을 처리하지 못하면 throws SQLException을 선언해야 하고, 그러면 서비스의 메서드 시그니처에 JDBC 전용 예외가 새어 나온다. JPA로 바꾸면 JPA의 예외가 나오므로 이 선언도 바뀌어야 한다. 이 문제는 이 권의 5회차(자바 예외 이해)와 6회차(예외 처리, 반복)에서 다룬다. 이 회차의 코드에도 throws SQLException이 계속 남아 있을 텐데, 일부러 남겨 둔 것이다.

    문제 3. JDBC 반복

    리포지토리 쪽에도 반복이 있다. 커넥션을 얻고, PreparedStatement를 만들고, 파라미터를 바인딩하고, 실행하고, 결과를 읽고, 역순으로 닫는 코드가 메서드마다 되풀이된다. 이것도 6회차에서 JdbcTemplate으로 정리한다. 이 회차는 셋 중 첫 번째, 트랜잭션 문제에 집중한다.

    프레젠테이션·서비스·데이터 접근 세 계층 가운데 서비스 계층에 JDBC 관련 코드가 침범한 모습을 보여 준다. 가로로 긴 세 개의 층을 위에서 아래로 쌓은 다이어그램. 맨 위 층 "프레젠테이션 계층", 가운데 층 "서비스 계층", 맨 아래 층 "데이터 접근 계층". 가운데 서비스 계층 안에 연두색 상자 "비즈니스 로직"이 있고, 그 주변을 빨간 테두리 칩 세 개가 둘러싼다: "Connection", "setAutoCommit / commit / rollback", "throws SQLException". 맨 아래 층에서 빨간 화살표 세 개가 위로 올라와 그 칩들을 가리킨다. 오른쪽 여백에 작은 메모 "JDBC → JPA로 바꾸면 서비스도 수정". 평면 기술 도해 스타일, 흰 배경, 녹색과 회색 계열, 침범한 부분만 적갈색. 비즈니스 로직보다 트랜잭션과 커넥션 코드가 더 많은 서비스 계층

    트랜잭션 추상화: PlatformTransactionManager

    첫 번째 문제부터 풀자. 기술마다 트랜잭션을 시작하고 끝내는 방법이 다르다면, 그 차이를 인터페이스 뒤로 숨기면 된다. 1회차에서 본 JDBC의 해법과 같은 생각이다. JDBC가 데이터베이스마다 다른 프로토콜을 Connection 인터페이스 뒤로 숨겼듯이, 스프링은 기술마다 다른 트랜잭션 API를 하나의 인터페이스 뒤로 숨긴다.

    기술시작성공실패
    JDBCcon.setAutoCommit(false)con.commit()con.rollback()
    JPAem.getTransaction().begin()tx.commit()tx.rollback()
    스프링 추상화tm.getTransaction(def)tm.commit(status)tm.rollback(status)

    스프링이 정의한 인터페이스가 org.springframework.transaction.PlatformTransactionManager다. Spring Framework 소스에서 주석을 걷어 내면 다음이 전부다.

    public interface PlatformTransactionManager extends TransactionManager {

    TransactionStatus getTransaction(@Nullable TransactionDefinition definition)
            throws TransactionException;

    void commit(TransactionStatus status) throws TransactionException;

    void rollback(TransactionStatus status) throws TransactionException;
}

    부모인 TransactionManager는 메서드가 하나도 없는 표시용 인터페이스(marker interface)이고, Spring 5.2에서 추가되었다. 리액티브 트랜잭션 매니저와 명령형 트랜잭션 매니저를 한 지붕 아래 두기 위한 것이다. 이 권에서 다루는 것은 명령형인 PlatformTransactionManager다.

    세 메서드의 모양을 눈여겨보자. getTransaction은 트랜잭션을 "시작한다"가 아니라 "얻는다"이다. 이미 진행 중인 트랜잭션이 있으면 새로 시작하지 않고 거기에 참여할 수도 있기 때문이다. 어떻게 할지는 인자로 넘기는 TransactionDefinition의 전파(propagation) 속성이 정한다. 이 정의에는 전파 외에도 격리 수준, 타임아웃, 읽기 전용 여부, 이름이 들어 있다. 기본 구현인 DefaultTransactionDefinition을 그냥 쓰면 전파는 PROPAGATION_REQUIRED, 격리 수준은 데이터베이스 기본값을 따르는 ISOLATION_DEFAULT다. 아래 실행 로그에서 이 두 값이 그대로 찍히는 것을 보게 된다. 전파의 세부 규칙은 다음 권(스프링 DB 2편)의 주제다.

    getTransaction이 돌려주는 TransactionStatus는 "지금 얻은 트랜잭션의 상태"를 담은 객체다. 새로 시작한 트랜잭션인지(isNewTransaction()), 롤백 전용으로 표시되었는지(isRollbackOnly()), 이미 완료되었는지(isCompleted())를 물을 수 있다. commit과 rollback이 이 상태 객체를 인자로 받는 이유가 여기 있다. 트랜잭션 매니저는 상태 객체 안에 실제 트랜잭션 자원(JDBC라면 커넥션을 감싼 객체)을 넣어 두었다가, 커밋할 때 그것을 꺼내 쓴다. 또 Spring Framework 소스의 AbstractPlatformTransactionManager.processCommit을 보면, 실제 커밋(doCommit)은 status.isNewTransaction()이 참일 때만 호출된다. 기존 트랜잭션에 참여만 한 쪽이 commit을 불러도 물리 커밋은 일어나지 않는다는 뜻이다. 이 규칙이 2편에서 다룰 논리 트랜잭션과 물리 트랜잭션 구분의 뿌리다.

    이제 서비스는 PlatformTransactionManager 인터페이스에만 의존하면 된다. JDBC를 쓸 때는 DataSourceTransactionManager를, JPA로 바꾸면 JpaTransactionManager를 주입한다. 서비스 코드는 그대로다. 스프링 핵심 원리에서 본 의존관계 주입(DI)과 역할·구현 분리가 트랜잭션에 적용된 것이다.

    그런데 인터페이스만으로는 두 번째 문제가 풀리지 않는다. getTransaction은 커넥션을 돌려주지 않는다. 트랜잭션 매니저가 내부에서 커넥션을 열고 자동 커밋을 껐다면, 리포지토리는 그 커넥션을 어떻게 손에 넣는가. 파라미터로 받지 않는다면 어딘가 공유된 곳에 있어야 한다. 그 "어딘가"가 트랜잭션 동기화다.

    트랜잭션 동기화: 커넥션을 스레드에 묶는다

    공유 장소의 후보부터 생각해 보자. 싱글톤 빈의 필드에 커넥션을 넣어 두면 어떨까. 웹 애플리케이션에서는 여러 요청이 동시에 같은 서비스 빈을 호출한다. 요청 A가 넣어 둔 커넥션을 요청 B가 꺼내 쓰면, B의 SQL이 A의 트랜잭션에 섞인다. 자바 중급에서 본 공유 자원 경합 그대로다. 필요한 것은 "지금 이 코드를 실행하는 흐름"에만 보이는 저장소다.

    동기 방식의 서블릿 처리에서는 요청 하나를 서블릿 컨테이너의 스레드 하나가 처음부터 끝까지 처리한다. 컨트롤러가 서비스를 부르고 서비스가 리포지토리를 부르는 동안 스레드는 바뀌지 않는다. 그렇다면 "이 실행 흐름"을 "이 스레드"로 바꿔 말할 수 있고, 스레드마다 따로 보이는 저장소가 바로 자바의 ThreadLocal이다.

    ThreadLocal은 어디에 값을 저장하는가

    ThreadLocal 객체 자체가 값을 들고 있는 것이 아니다. JDK 21의 java.lang.Thread 소스를 보면 각 Thread 객체에 ThreadLocal.ThreadLocalMap threadLocals라는 필드가 있다. ThreadLocal.get()은 Thread.currentThread()로 현재 스레드 객체를 구하고, 그 스레드의 threadLocals 맵에서 자기 자신(ThreadLocal 인스턴스)을 키로 값을 찾는다. 즉 값은 힙에 있는 각 스레드 객체가 소유한 맵 안에 있다. 같은 ThreadLocal 인스턴스 하나를 모든 스레드가 공유해도, 각 스레드는 자기 맵만 들여다보므로 서로의 값을 볼 수 없다. 맵의 엔트리는 WeakReference를 상속해 ThreadLocal 키를 약하게 참조한다는 것도 같은 소스에서 확인할 수 있다.

    스프링의 TransactionSynchronizationManager는 이 구조 위에 서 있다. 이 클래스의 Javadoc 첫 문장은 스레드마다 자원과 트랜잭션 동기화를 관리하는 중앙 위임자(central delegate)라고 스스로를 소개한다. 소스를 보면 정적 필드로 여러 개의 NamedThreadLocal(이름을 붙인 ThreadLocal 하위 클래스)을 가지고 있다.

    private static final ThreadLocal> resources =
        new NamedThreadLocal<>("Transactional resources");

private static final ThreadLocal> synchronizations =
        new NamedThreadLocal<>("Transaction synchronizations");

private static final ThreadLocal currentTransactionName =
        new NamedThreadLocal<>("Current transaction name");

private static final ThreadLocal actualTransactionActive =
        new NamedThreadLocal<>("Actual transaction active");
// ... 읽기 전용 여부, 격리 수준용 ThreadLocal도 있다

    핵심은 첫 번째 resources다. 스레드마다 Map 하나를 두고, 그 맵에 "키 → 자원"을 넣는다. JDBC 트랜잭션에서 키는 DataSource 객체이고 값은 커넥션을 감싼 ConnectionHolder다. 키가 DataSource인 이유는 한 애플리케이션이 데이터베이스를 여러 개 쓸 수 있기 때문이다. 같은 스레드라도 주문 DB와 회원 DB의 트랜잭션은 서로 다른 커넥션이어야 하고, "어느 데이터소스의 커넥션인가"로 구분한다.

    두 스레드가 같은 ThreadLocal과 같은 DataSource 키를 쓰지만 각자의 맵에 서로 다른 커넥션을 보관한다는 것을 보여 준다. 세로로 나란히 놓인 큰 상자 두 개. 왼쪽 상자 제목 "스레드 1", 오른쪽 상자 제목 "스레드 2". 각 상자 안에 작은 표 모양 "threadLocals 맵"이 있고, 표 안에 "DataSource" 칸에서 화살표가 나가 "ConnectionHolder" 상자로, 다시 화살표가 원통 모양 커넥션 아이콘으로 이어진다. 왼쪽 커넥션 라벨 "커넥션 1", 오른쪽 커넥션 라벨 "커넥션 2". 두 상자 위쪽 가운데에 둘이 함께 가리키는 하나의 둥근 상자 "TransactionSynchronizationManager"가 있고, 거기서 점선 화살표가 두 맵으로 내려간다. 맨 아래 가로 띠에 "같은 키, 스레드마다 다른 값". 평면 기술 도해 스타일, 흰 배경, 녹색과 회색 계열. 동기화 매니저는 하나지만, 커넥션은 스레드마다 따로 보관된다.

    이렇게 커넥션을 스레드에 묶어 두는 일을 스프링은 트랜잭션 동기화(transaction synchronization)라고 부른다. 역할 분담은 이렇다. 트랜잭션 매니저가 트랜잭션을 시작할 때 커넥션을 열어 동기화 매니저에 바인딩(bind)한다. 리포지토리는 동기화 매니저에서 커넥션을 꺼내 쓴다. 트랜잭션이 끝나면 트랜잭션 매니저가 바인딩을 풀고(unbind) 커넥션을 닫는다. 서비스와 리포지토리 사이에 커넥션 파라미터가 오갈 필요가 없어진다.

    일상에서 가져온 비유사물함 열쇠를 손목에 차고 다니는 수영장

    수영장 입구에서 직원(트랜잭션 매니저)이 빈 사물함 하나를 배정하고 열쇠를 손님 손목에 채워 준다. 손님이 탈의실, 샤워실, 수영장 어디를 가든(서비스, 리포지토리) 열쇠는 손목에 붙어 다니므로 매번 "제 사물함이 몇 번이죠" 하고 물을 필요가 없다. 나갈 때 직원이 열쇠를 회수한다. 손목이 스레드, 열쇠가 커넥션이다. 비유가 깨지는 지점도 있다. 손님은 친구에게 열쇠를 건네줄 수 있지만, ThreadLocal에 든 값은 다른 스레드가 꺼낼 방법이 없다. 아래에서 보듯 새 스레드를 만들면 그 스레드는 빈 손목으로 시작한다.

    트랜잭션 문제 해결 — 트랜잭션 매니저 1: 코드 바꾸기

    이제 코드를 바꾼다. 리포지토리는 커넥션을 파라미터로 받지 않는다. 대신 커넥션을 얻을 때 DataSource.getConnection()을 직접 부르지 않고 스프링의 DataSourceUtils.getConnection(dataSource)를 부른다. 닫을 때도 con.close() 대신 DataSourceUtils.releaseConnection(con, dataSource)를 부른다. 바뀌는 곳은 이 두 군데뿐이다.

    public class AccountRepository {

    private final DataSource dataSource;

    public AccountRepository(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public int findBalance(String accountId) throws SQLException {
        String sql = "select balance from account where account_id = ?";
        Connection con = null;
        PreparedStatement pstmt = null;
        ResultSet rs = null;
        try {
            con = getConnection();
            pstmt = con.prepareStatement(sql);
            pstmt.setString(1, accountId);
            rs = pstmt.executeQuery();
            if (!rs.next()) {
                throw new IllegalArgumentException("no account " + accountId);
            }
            return rs.getInt("balance");
        } finally {
            close(con, pstmt, rs);
        }
    }

    public void updateBalance(String accountId, int balance) throws SQLException {
        // ... findBalance와 같은 모양으로 update 문을 executeUpdate()로 실행한다
    }

    private Connection getConnection() throws SQLException {
        Connection con = DataSourceUtils.getConnection(dataSource);
        System.out.println("repo: " + con + " autoCommit=" + con.getAutoCommit());
        return con;
    }

    private void close(Connection con, Statement stmt, ResultSet rs) {
        JdbcUtils.closeResultSet(rs);
        JdbcUtils.closeStatement(stmt);
        DataSourceUtils.releaseConnection(con, dataSource);
    }
}

    JdbcUtils(org.springframework.jdbc.support)는 null 검사와 예외 무시를 대신해 주는 정리 도우미다. 진짜 일은 DataSourceUtils가 한다. Spring Framework 6.2.x 소스의 doGetConnection을 따라가면 다음 순서다.

    1. 동기화 매니저에서 getResource(dataSource)로 현재 스레드에 묶인 ConnectionHolder를 찾는다.
    2. 있으면 참조 횟수를 하나 올리고(requested()) 그 안의 커넥션을 돌려준다. 새 커넥션을 열지 않는다.
    3. 없으면 DataSource에서 새 커넥션을 얻는다. 이때 트랜잭션 동기화가 활성 상태라면(트랜잭션 매니저가 동기화를 켜 둔 상태) 새 커넥션도 홀더에 담아 스레드에 바인딩해 두고, 같은 트랜잭션 안의 다음 호출이 재사용하게 한다.

    doReleaseConnection은 그 반대다. 넘겨받은 커넥션이 지금 스레드에 묶인 트랜잭션 커넥션과 같은 것이면 닫지 않고 참조 횟수만 하나 내린다(released()). 소스 주석이 그대로 "트랜잭션 커넥션이므로 닫지 않는다"고 적고 있다. 묶인 커넥션이 아니면 그때 비로소 닫는다. 커넥션 풀을 쓰는 데이터소스라면 "닫는다"는 2회차에서 본 대로 풀에 반납한다는 뜻이다.

    이 두 메서드 덕분에 리포지토리는 자기가 트랜잭션 안에서 불리는지 밖에서 불리는지 몰라도 된다. 트랜잭션 안이면 트랜잭션 커넥션을 빌려 쓰고 돌려주지 않으며, 밖이면 스스로 열고 닫는다. 앞에서 지적한 "커넥션을 받는 버전과 안 받는 버전의 메서드 두 벌" 문제가 사라진다.

    서비스는 이렇게 바뀐다.

    public class TransferServiceV1 {

    private final PlatformTransactionManager transactionManager;
    private final AccountRepository repository;
    // 생성자 ...

    public void transfer(String fromId, String toId, int amount) throws SQLException {
        TransactionStatus status =
                transactionManager.getTransaction(new DefaultTransactionDefinition());
        try {
            bizLogic(fromId, toId, amount);
            transactionManager.commit(status);
        } catch (RuntimeException | SQLException e) {
            transactionManager.rollback(status);
            throw e;
        }
    }

    private void bizLogic(String fromId, String toId, int amount) throws SQLException {
        int fromBalance = repository.findBalance(fromId);
        repository.updateBalance(fromId, fromBalance - amount);
        if (toId.equals("EX")) {
            throw new IllegalStateException("transfer failed");
        }
        int toBalance = repository.findBalance(toId);
        repository.updateBalance(toId, toBalance + amount);
    }
}

    Connection도 DataSource도 서비스에서 사라졌다. 남은 의존은 스프링의 트랜잭션 추상화와, 5·6회차에서 정리할 SQLException뿐이다. 트랜잭션 매니저는 설정 쪽에서 new DataSourceTransactionManager(dataSource)로 만들어 주입한다. 트랜잭션 매니저가 생성자로 DataSource를 받는 이유는 커넥션을 직접 열어야 하고, 동기화 매니저에 바인딩할 때 그 DataSource를 키로 써야 하기 때문이다. 리포지토리가 같은 DataSource 객체를 들고 있어야 같은 키로 커넥션을 찾을 수 있다. 서로 다른 DataSource 인스턴스를 주입하면 리포지토리는 트랜잭션 커넥션을 찾지 못하고 새 커넥션을 연다.

    catch (RuntimeException | SQLException e)에서 throw e가 컴파일되는 것은 자바 7부터의 정밀한 재던지기(precise rethrow) 규칙 덕분이다. 컴파일러는 e가 두 타입 중 하나라는 것을 알고 있으므로, 메서드에 throws SQLException만 선언해도 된다. 다만 이 손으로 쓴 코드에는 빈틈이 두 개 있다. Error가 나면 롤백 없이 빠져나가고, commit 자체가 실패하면 같은 catch로 들어가 이미 완료된 트랜잭션에 rollback을 부른다. 후자는 AbstractPlatformTransactionManager가 "Transaction is already completed - do not call commit or rollback more than once per transaction" 메시지로 거부한다. 이 빈틈을 트랜잭션 템플릿이 어떻게 메우는지는 뒤에서 본다.

    트랜잭션 문제 해결 — 트랜잭션 매니저 2: 실행 흐름 추적

    코드만 봐서는 커넥션이 정말 하나만 쓰이는지 알 수 없다. 스프링의 디버그 로그를 켜고 리포지토리가 받은 커넥션을 찍어 보자. 데이터소스는 스프링의 DriverManagerDataSource를 썼다. 풀 없이 getConnection()마다 물리 커넥션을 새로 여는 데이터소스라서, 커넥션이 몇 개 열렸는지 그대로 보인다. H2 드라이버의 커넥션 객체는 toString()이 conn번호: url=... user=... 꼴로 찍힌다. 계좌 A와 B는 각각 10000원에서 시작하고, A에서 B로 2000원을 보낸다. 준비 단계(테이블 생성)와 마지막 잔액 확인에서 나온 줄, 데이터소스의 "새 커넥션 생성" 줄은 뺐고, 로그 형식은 "[로거 클래스 이름] 메시지"로 줄였다.

    로그 한 줄 한 줄 뒤의 소스

    로그의 각 줄은 DataSourceTransactionManager 소스의 특정 지점에서 찍힌다. 시작 쪽은 doBegin, 끝 쪽은 doCommit/doRollback과 doCleanupAfterCompletion이다. 순서대로 묶으면 다음과 같다.

    트랜잭션 매니저가 커넥션을 열어 동기화 매니저에 넣고, 리포지토리가 꺼내 쓰고, 끝나면 트랜잭션 매니저가 회수하는 순서를 보여 준다. 왼쪽에서 오른쪽으로 다섯 개의 세로 생명선을 가진 시퀀스 다이어그램. 생명선 이름: "서비스", "트랜잭션 매니저", "DataSource", "동기화 매니저", "리포지토리". 화살표 순서: 서비스→트랜잭션 매니저 "getTransaction", 트랜잭션 매니저→DataSource "getConnection", 트랜잭션 매니저 자기 자신에게 "setAutoCommit(false)", 트랜잭션 매니저→동기화 매니저 "bindResource", 서비스→리포지토리 "SQL 실행", 리포지토리→동기화 매니저 "커넥션 꺼내기"(점선 되돌아오는 화살표), 서비스→트랜잭션 매니저 "commit", 트랜잭션 매니저→동기화 매니저 "unbind", 트랜잭션 매니저→DataSource "close(반납)". 평면 기술 도해 스타일, 흰 배경, 녹색과 회색 계열, 라벨은 정확히 위 문구로. 커넥션을 여는 쪽과 닫는 쪽은 트랜잭션 매니저 하나다. 리포지토리는 빌려 쓰기만 한다.

    7단계의 자동 커밋 복구가 왜 필요한지 짚고 가자. 2회차에서 본 커넥션 풀에서는 close()가 물리 연결을 끊지 않고 커넥션을 풀에 되돌려 놓는다. 자동 커밋을 끈 채로 반납하면, 다음에 그 커넥션을 빌린 다른 요청은 자기가 트랜잭션을 시작한 적도 없는데 수동 커밋 상태의 커넥션을 받는다. 그 요청이 자동 커밋을 기대하고 update만 실행하고 반납하면 변경은 커밋되지 않은 채 남는다. 그래서 스프링은 3단계에서 "원래 자동 커밋이었는지"를 기억해 두었다가 7단계에서 되돌린다. 3단계 소스에는 주석이 하나 붙어 있다. 자동 커밋 전환은 일부 JDBC 드라이버에서 비용이 커서, 커넥션 풀이 이미 자동 커밋을 꺼 둔 경우에는 불필요하게 바꾸지 않으려고 먼저 getAutoCommit()을 확인한다는 내용이다.

    4단계와 7단계의 바인딩·언바인딩도 짝이 맞아야 한다. 서블릿 컨테이너는 스레드 풀의 스레드를 재사용한다. 바인딩을 풀지 않은 채 스레드가 풀로 돌아가면, 그 스레드가 다음 요청을 처리할 때 이전 요청의 커넥션 홀더가 맵에 그대로 남아 있다. TransactionSynchronizationManager.unbindResource 소스는 맵에서 키를 지운 뒤 맵이 비면 resources.remove()로 ThreadLocal 값 자체를 지운다. 반대로 같은 키에 이미 값이 있는데 bindResource를 부르면 "Already value ... bound to thread"라는 IllegalStateException을 던진다. 덮어쓰기를 허용하지 않아 실수를 일찍 드러내는 설계다.

    트랜잭션 문제 해결 — 트랜잭션 템플릿

    트랜잭션 매니저로 기술 의존과 커넥션 파라미터는 사라졌다. 남은 것은 반복이다. 트랜잭션이 필요한 모든 서비스 메서드가 "트랜잭션 얻기 → try → 로직 → 커밋 → catch → 롤백 → 다시 던지기"라는 같은 틀을 가진다. 바뀌는 것은 가운데 로직 한 줄뿐이다. 변하지 않는 틀은 한곳에 두고, 변하는 부분만 넘겨받는 방식을 템플릿 콜백 패턴(template callback pattern)이라고 한다. 틀이 템플릿이고, 넘겨받는 코드 조각이 콜백이다. 자바에서 콜백은 보통 람다로 넘긴다.

    스프링은 트랜잭션용 템플릿으로 TransactionTemplate을 제공한다. 인터페이스 TransactionOperations를 구현하며, 핵심 메서드는 둘이다.

    • execute(TransactionCallback): 콜백이 값을 돌려줄 때. 콜백의 반환값을 그대로 돌려준다.
    • executeWithoutResult(Consumer): 돌려줄 값이 없을 때. Spring 5.2에 추가된 기본 메서드로, 내부에서 execute를 호출하고 null을 돌려주는 콜백으로 감싼다.
    public class TransferServiceV2 {

    private final TransactionTemplate txTemplate;
    private final AccountRepository repository;

    public TransferServiceV2(PlatformTransactionManager transactionManager,
                             AccountRepository repository) {
        this.txTemplate = new TransactionTemplate(transactionManager);
        this.repository = repository;
    }

    public void transfer(String fromId, String toId, int amount) {
        txTemplate.executeWithoutResult(status -> {
            try {
                bizLogic(fromId, toId, amount);
            } catch (SQLException e) {
                throw new IllegalStateException(e);
            }
        });
    }

    // bizLogic은 TransferServiceV1과 같다 ...
}

    생성자에서 PlatformTransactionManager를 받아 템플릿을 만드는 모양을 보자. TransactionTemplate은 트랜잭션 매니저를 감싼 얇은 도우미이고, TransactionDefinition을 상속한 클래스이기도 해서(정확히는 DefaultTransactionDefinition의 하위 클래스) 템플릿 객체에 전파·격리 수준·타임아웃 같은 설정을 직접 걸 수 있다. 그래서 템플릿 자신이 getTransaction(this)의 인자가 된다.

    템플릿 안에서 일어나는 일

    Spring Framework 6.2.x의 TransactionTemplate.execute 소스를 그대로 따라가면 흐름은 이렇다. 콜백을 더 선호하는 특수한 트랜잭션 매니저(CallbackPreferringPlatformTransactionManager)가 아니라면, 먼저 transactionManager.getTransaction(this)로 트랜잭션을 얻는다. 이어서 콜백의 doInTransaction(status)를 호출한다. 여기서 RuntimeException이나 Error가 나오면 롤백하고 그 예외를 그대로 다시 던진다. 그 밖의 Throwable이 나오면 역시 롤백하되, UndeclaredThrowableException으로 감싸서 던진다. 아무 예외도 없으면 try 블록 바깥에서 commit(status)를 호출하고 콜백의 결과를 돌려준다.

    앞에서 손으로 쓴 TransferServiceV1의 빈틈 두 개가 여기서 메워진다. Error도 롤백 대상에 들어 있고, commit이 try 바깥에 있으므로 커밋이 실패해도 완료된 트랜잭션에 롤백을 다시 부르는 일이 없다. 반복되는 틀을 라이브러리 한곳에 모으면 이런 경계 조건을 한 번만 제대로 처리하면 된다는 이점이 있다.

    체크 예외는 왜 람다 안에서 감싸야 하는가

    TransferServiceV2의 람다 안에는 try-catch가 하나 있다. bizLogic이 던지는 SQLException을 IllegalStateException으로 감싸는 코드다. 이것을 지우면 컴파일 오류가 난다. 람다가 구현하는 Consumer.accept나 TransactionCallback.doInTransaction은 throws 절에 체크 예외를 선언하지 않았기 때문이다. JLS 11.2의 예외 검사 규칙에 따라 람다 본문은 그 함수형 인터페이스 메서드가 선언한 체크 예외만 던질 수 있다.

    그렇다면 템플릿 소스의 catch (Throwable ex) 분기는 언제 실행되는가. 체크 예외 검사는 컴파일러가 하는 일이고 JVM은 관여하지 않는다. 바이트코드의 athrow 명령은 어떤 Throwable이든 던지며, 메서드의 throws 선언을 실행 시점에 확인하지 않는다. 그래서 다른 JVM 언어로 작성한 콜백이나, 제네릭 타입 소거를 이용해 컴파일러를 우회하는 코드에서는 체크 예외가 실제로 새어 나올 수 있다. 다음 코드로 확인해 보자.

    @SuppressWarnings("unchecked")
static  void sneakyThrow(Throwable e) throws E {
    throw (E) e;      // E는 소거되어 Throwable이 되므로 실행 시점 검사가 없다
}

// ...
try {
    txTemplate.executeWithoutResult(
            status -> Sneaky.sneakyThrow(new SQLException("boom")));
} catch (Exception e) {
    System.out.println(e.getClass().getName() + " / cause=" + e.getCause());
}

    컴파일러는 E를 RuntimeException으로 보고 통과시켰지만, 바이트코드에는 캐스트 검사조차 없이 aload_0, athrow 두 명령만 남았다. 실제로 던져진 것은 SQLException이고, 템플릿은 그것을 catch (Throwable ex)로 받아 롤백한 뒤 UndeclaredThrowableException으로 감쌌다. 템플릿이 "선언되지 않은 체크 예외"를 따로 처리하는 이유가 이것이다.

    트랜잭션 템플릿으로 반복은 사라졌지만, 서비스에는 여전히 txTemplate.executeWithoutResult(...)라는 트랜잭션 처리 코드가 남아 있다. 비즈니스 로직이 람다 안에 갇혀 들여쓰기 한 단계를 더 먹고, 체크 예외를 감싸는 코드도 붙는다. 서비스가 "트랜잭션을 어떻게 시작하는지"는 몰라도 되지만, "여기서 트랜잭션을 시작해야 한다"는 사실은 여전히 직접 말하고 있다. 이것까지 서비스 밖으로 빼내는 것이 다음 단계다.

    트랜잭션 문제 해결 — 트랜잭션 AOP 이해

    서비스에서 트랜잭션 코드를 완전히 없애려면, 서비스가 호출되기 직전과 직후에 누군가 대신 트랜잭션을 시작하고 끝내 주어야 한다. 스프링 핵심 원리에서 본 프록시(proxy)가 그 역할을 한다. 클라이언트는 서비스를 호출한다고 생각하지만 실제로 받은 객체는 서비스와 같은 타입의 대리 객체다. 대리 객체가 트랜잭션을 시작하고, 진짜 서비스 객체(target)를 호출하고, 결과에 따라 커밋이나 롤백을 한다.

    개념을 보이기 위해 프록시를 손으로 써 보면 다음과 같다. 스프링이 실제로 만드는 클래스는 이 코드와 다르며, 아래에서 실제 모습을 확인한다.

    // 개념 설명용으로 손으로 쓴 프록시. 스프링이 생성하는 실제 클래스와는 다르다.
public class TransferServiceTxProxy extends TransferService {

    private final TransferService target;
    private final PlatformTransactionManager transactionManager;

    public TransferServiceTxProxy(TransferService target, PlatformTransactionManager tm) {
        super(null);
        this.target = target;
        this.transactionManager = tm;
    }

    @Override
    public void transfer(String fromId, String toId, int amount) throws SQLException {
        TransactionStatus status =
                transactionManager.getTransaction(new DefaultTransactionDefinition());
        try {
            target.transfer(fromId, toId, amount);      // 진짜 서비스 호출
        } catch (RuntimeException | Error e) {
            transactionManager.rollback(status);        // 런타임 예외, 에러 → 롤백
            throw e;
        } catch (SQLException e) {
            transactionManager.commit(status);          // 체크 예외 → 기본 규칙은 커밋
            throw e;
        }
        transactionManager.commit(status);
    }
}

    이 프록시가 있으면 서비스는 비즈니스 로직만 가진다. 트랜잭션은 프록시가, 커넥션 전달은 동기화 매니저가 맡는다. 프록시와 리포지토리 사이에 커넥션을 전달하는 통로가 동기화 매니저라는 점이 중요하다. 프록시가 시작한 트랜잭션의 커넥션을 리포지토리가 찾을 수 있는 것은 둘이 같은 스레드에서 실행되기 때문이다. 트랜잭션 동기화가 없었다면 AOP로 트랜잭션을 분리하는 것 자체가 불가능했다.

    체크 예외 분기를 눈여겨보자. Spring Framework 레퍼런스의 @Transactional 설명은 기본 설정에서 RuntimeException이나 Error는 롤백을 일으키고, 체크 예외는 롤백을 일으키지 않는다고 적고 있다. 소스에서는 DefaultTransactionAttribute.rollbackOn이 ex instanceof RuntimeException || ex instanceof Error를 돌려주는 한 줄로 구현되어 있다. 프록시는 예외가 롤백 대상이 아니면 커밋한 뒤 예외를 그대로 다시 던진다. 왜 이런 규칙이 기본값인지, 그리고 그것이 SQLException을 던지는 이 회차의 코드에 어떤 함정을 만드는지는 아래 실험과 5·6회차에서 이어진다.

    스프링이 제공하는 것: @Transactional과 세 부품

    트랜잭션 프록시를 클래스마다 손으로 쓸 수는 없다. 스프링은 @Transactional 애노테이션이 붙은 빈을 찾아 프록시를 자동으로 만들어 준다. 스프링 AOP의 용어로 말하면 세 부품이 필요하다. 어디에 적용할지 고르는 포인트컷(pointcut), 무엇을 할지 담은 어드바이스(advice), 그리고 둘을 묶은 어드바이저(advisor)다. @EnableTransactionManagement를 붙이면 ProxyTransactionManagementConfiguration이라는 설정 클래스(와 그 부모 클래스 AbstractTransactionManagementConfiguration)가 이 부품들을 빈으로 등록한다.

    부품클래스하는 일
    어드바이저BeanFactoryTransactionAttributeSourceAdvisor아래 둘을 묶어 하나의 적용 단위로 만든다
    포인트컷TransactionAttributeSourcePointcut메서드에 트랜잭션 속성이 있는지 묻는다. 속성은 AnnotationTransactionAttributeSource가 @Transactional을 읽어 만든다
    어드바이스TransactionInterceptor메서드 호출을 가로채 트랜잭션 매니저로 시작·커밋·롤백한다

    부품만으로는 프록시가 생기지 않는다. 누군가 빈이 만들어질 때마다 "이 빈에 적용할 어드바이저가 있는가"를 묻고, 있으면 원래 객체 대신 프록시를 컨테이너에 등록해야 한다. 그 일을 하는 것이 자동 프록시 생성기(auto proxy creator)라는 빈 후처리기(BeanPostProcessor)다. @EnableTransactionManagement가 프록시 모드일 때 가져오는 AutoProxyRegistrar가 이것을 등록하며, 트랜잭션만 켠 경우 InfrastructureAdvisorAutoProxyCreator가 등록된다. AspectJ 스타일 AOP도 켜져 있으면 AopConfigUtils의 우선순위 목록에 따라 더 기능이 많은 생성기 하나로 올려서 쓴다. 생성기는 컨테이너 안에 하나만 있다.

    프록시를 만드는 방식은 두 가지다. 대상 클래스가 구현한 인터페이스로 만드는 JDK 동적 프록시와, 대상 클래스를 상속해 하위 클래스를 바이트코드로 만드는 CGLIB 프록시다. Spring AOP의 DefaultAopProxyFactory는 proxyTargetClass가 참이거나 대상에 쓸 만한 인터페이스가 없으면 CGLIB을, 그렇지 않으면 JDK 동적 프록시를 고른다. 순수 스프링에서 @EnableTransactionManagement의 proxyTargetClass 기본값은 false다(레퍼런스 문서의 설정 표). 이 회차의 TransferService처럼 인터페이스 없는 클래스라면 어차피 CGLIB이 쓰인다. 스프링 부트의 기본값은 다르다. 그것은 부트 자동 구성 절에서 본다.

    트랜잭션 문제 해결 — 트랜잭션 AOP 적용

    서비스에서 트랜잭션 코드를 모두 지우고 메서드에 @Transactional만 붙인다. 리포지토리는 그대로 DataSourceUtils를 쓴다.

    public class TransferService {

    private final AccountRepository repository;

    public TransferService(AccountRepository repository) {
        this.repository = repository;
    }

    @Transactional
    public void transfer(String fromId, String toId, int amount) throws SQLException {
        bizLogic(fromId, toId, amount);
    }

    // bizLogic은 TransferServiceV1과 같다 ...
}

    애노테이션은 클래스에 붙여도 된다. 클래스에 붙이면 그 클래스의 메서드 전체에 적용되고, 메서드에 붙인 설정이 클래스 설정보다 우선한다. 이제 서비스에는 트랜잭션 매니저 필드조차 없다. 대신 스프링 컨테이너가 반드시 있어야 한다. 프록시를 만들고, 트랜잭션 인터셉터에 트랜잭션 매니저를 넣어 주는 것이 컨테이너이기 때문이다. 그래서 테스트도 스프링 컨테이너를 띄워서 해야 한다. 스프링 부트 테스트로 쓰면 다음과 같다.

    트랜잭션 매니저를 빈으로 등록하는 것이 핵심이다. TransactionInterceptor는 실행 시점에 컨테이너에서 트랜잭션 매니저 빈을 찾아 쓴다. 트랜잭션 매니저 빈이 없으면 프록시는 만들어져도 트랜잭션을 시작할 수 없다. 서비스 빈에는 @Transactional이 있으니 프록시가 되고, 리포지토리 빈에는 없으니 원래 객체 그대로 등록된다. 두 번째 단언이 그것을 확인한다.

CGLIB이 상속으로 만든 프록시라는 뜻이다. 이 이름 규칙은 Spring 6.2.x 소스의 SpringNamingPolicy에서도 같다. 대상 클래스 이름 뒤에 $$SpringCGLIB$$를 붙이고 0부터 시작하는 번호를 붙인다.     상속 프록시인데 TransferService의 생성자가 AccountRepository를 요구한다면 프록시는 생성자에 무엇을 넘겼을까. 답은 "생성자를 호출하지 않았다"이다. Spring AOP의 기본 CGLIB 프록시 구현인 ObjenesisCglibAopProxy는 Javadoc 그대로 클래스의 생성자를 호출하지 않고 프록시 인스턴스를 만든다(Objenesis 라이브러리 사용). 그래서 프록시 객체의 상속받은 필드 repository는 비어 있다. 프록시는 그 필드를 쓰지 않는다. 호출이 들어오면 내부에 보관한 진짜 대상 객체에 위임할 뿐이다. 위에서 손으로 쓴 프록시의 super(null)은 이 사정을 흉내 낸 것이다.

    트랜잭션 문제 해결 — 트랜잭션 AOP 정리

    지금까지의 조각을 하나의 흐름으로 이어 보자. 요청 하나가 들어와 @Transactional 메서드를 거쳐 나갈 때까지다.

    선언적 트랜잭션과 프로그래밍 방식 트랜잭션

    구분방법장점단점
    선언적 트랜잭션 관리(declarative)@Transactional 하나로 선언, 프록시가 처리서비스가 트랜잭션 코드를 모름. 간결함스프링 컨테이너와 프록시가 있어야 동작. 프록시의 한계를 그대로 물려받음
    프로그래밍 방식 트랜잭션 관리(programmatic)트랜잭션 매니저나 TransactionTemplate을 코드에서 직접 호출경계를 코드로 정확히 표현. 컨테이너 없이도 쓸 수 있음서비스에 트랜잭션 코드가 섞임

    실무의 기본은 선언적 방식이다. 그러나 둘은 대립 관계가 아니라 같은 바닥 위의 두 입구다. 이 회차의 실행 로그가 보여 주듯, @Transactional이든 TransactionTemplate이든 손으로 쓴 getTransaction이든 결국 똑같이 DataSourceTransactionManager의 doBegin과 doCommit에 도착한다. 트랜잭션 범위를 메서드보다 잘게 나눠야 하거나, 컨테이너 밖의 코드에서 트랜잭션이 필요하면 템플릿을 쓴다.

    프록시이기 때문에 생기는 함정

    선언적 방식의 단점 칸에 적은 "프록시의 한계"를 구체적으로 보자. 가장 흔한 것은 내부 호출(self-invocation)이다. 같은 서비스 안에서 @Transactional이 없는 메서드가 @Transactional 메서드를 부르면 어떻게 될까.

            + TransactionSynchronizationManager.isActualTransactionActive());
    transfer("A", "B", 0);                          // 같은 객체의 @Transactional 메서드
}

      at bank.TransferService$$SpringCGLIB$$0.outer

    트랜잭션이 없다. 호출 스택이 이유를 보여 준다. 프록시의 outer에는 걸린 어드바이스가 없으므로 곧바로 진짜 객체의 outer로 넘어갔다. 진짜 객체 안에서 transfer(...)는 this.transfer(...)이고, 앞에서 본 대로 대상 메서드 안의 this는 프록시가 아니라 진짜 객체다. 프록시를 거치지 않았으니 TransactionInterceptor가 끼어들 기회가 없다. 실제로 이 호출에서 리포지토리는 호출마다 새 자동 커밋 커넥션을 열었다. Spring Framework 레퍼런스도 프록시 모드에서는 프록시를 통해 들어온 외부 호출만 가로채며, 내부 호출은 @Transactional이 붙어 있어도 실제 트랜잭션으로 이어지지 않는다고 적고 있다. 해결 방법은 다음 권에서 다룬다.

    메서드 가시성도 프록시 방식과 엮여 있다. 레퍼런스 문서에 따르면 @Transactional은 보통 public 메서드에 쓰지만, Spring 6.0부터는 클래스 기반 프록시(CGLIB)에서 protected와 패키지 가시성 메서드도 기본으로 트랜잭션이 적용된다. 인터페이스 기반 프록시에서는 여전히 인터페이스에 정의된 public 메서드여야 한다. private 메서드는 하위 클래스가 오버라이드할 수 없으므로 어느 쪽 프록시로도 가로챌 수 없다. 마지막으로, 앞에서 본 스레드 경계도 그대로 적용된다. @Transactional 메서드 안에서 새 스레드로 넘긴 작업은 그 트랜잭션에 참여하지 않는다.

    이 장의 핵심

    @Transactional은 세 겹의 장치가 맞물려 동작한다. 바깥에서는 프록시가 호출을 가로채 트랜잭션 매니저를 부르고, 가운데에서는 트랜잭션 매니저가 기술별 트랜잭션 API를 하나의 인터페이스로 감추며, 안쪽에서는 동기화 매니저가 커넥션을 현재 스레드의 ThreadLocal에 묶어 리포지토리에 전달한다. 프록시를 거치지 않은 호출, 다른 스레드에서의 호출, 같은 데이터소스를 쓰지 않는 리포지토리는 이 셋 중 하나가 끊긴 경우다.

    스프링 부트의 자동 리소스 등록

    앞의 테스트 설정에서는 DataSource와 트랜잭션 매니저를 직접 빈으로 등록했다. 스프링 부트를 쓰면 대부분 그럴 필요가 없다. 부트는 클래스패스와 설정값을 보고 이 자원들을 자동으로 등록한다. 무엇이 어떤 조건에서 등록되는지 알아야, 직접 등록과 자동 등록이 섞였을 때 어느 쪽이 쓰이는지 판단할 수 있다.

    데이터소스

    Spring Boot 3.5 레퍼런스의 "SQL Databases" 장에 따르면 데이터소스 설정은 spring.datasource.* 외부 설정으로 제어한다.

    spring.datasource.url=jdbc:h2:tcp://localhost/~/bankdb
spring.datasource.username=sa
spring.datasource.password=

    커넥션 풀 구현은 정해진 순서로 고른다. HikariCP가 있으면 항상 HikariCP를 쓰고, 없으면 Tomcat 풀링 데이터소스, 그다음 Commons DBCP2, 마지막으로 Oracle UCP 순이다. spring-boot-starter-jdbc나 spring-boot-starter-data-jpa를 쓰면 HikariCP 의존성이 자동으로 들어오므로 보통 결과는 HikariDataSource다. spring.datasource.url을 지정하지 않으면 부트는 클래스패스에 있는 임베디드 데이터베이스(H2, HSQL, Derby)로 데이터소스를 자동 구성하려 한다. 그리고 같은 문서는 개발자가 직접 DataSource 빈을 정의하면 이 자동 구성이 일어나지 않는다고 밝힌다. 앞의 테스트 설정이 정확히 그 경우였다. 직접 등록한 DriverManagerDataSource가 쓰이고 HikariCP는 만들어지지 않는다.

    트랜잭션 매니저

    트랜잭션 매니저는 DataSourceTransactionManagerAutoConfiguration이 등록한다. Spring Boot 3.0.x와 3.5.x 소스를 모두 확인했는데 구조가 같다. 조건은 세 가지다. 클래스패스에 JdbcTemplate, TransactionManager 클래스가 있어야 하고(3.5.x 소스는 여기에 DataSource도 명시한다), DataSource 빈 후보가 하나여야 하며, TransactionManager 타입의 빈이 아직 없어야 한다(@ConditionalOnMissingBean(TransactionManager.class)). 빈 메서드 이름이 transactionManager이므로 빈 이름도 transactionManager다.

    등록되는 객체의 타입을 눈여겨보자. 소스는 spring.dao.exceptiontranslation.enabled 속성이 참(기본값)이면 JdbcTransactionManager를, 거짓이면 DataSourceTransactionManager를 만든다. 즉 Boot 3.x의 기본 트랜잭션 매니저는 JdbcTransactionManager다. 이것은 DataSourceTransactionManager의 하위 클래스로, 커밋·롤백 단계에서 난 SQLException을 스프링의 데이터 접근 예외로 바꿔 준다는 점만 다르다. 실무에서 바로 부딪히는 차이가 하나 있다. 트랜잭션 매니저의 로거는 LogFactory.getLog(getClass())로 만들어진다(AbstractPlatformTransactionManager 소스). 그래서 부트 애플리케이션에서 이 회차의 디버그 로그를 보려고 logging.level.org.springframework.jdbc.datasource.DataSourceTransactionManager=debug를 설정하면 아무것도 나오지 않는다. 실제 로거 이름은 org.springframework.jdbc.support.JdbcTransactionManager이기 때문이다. 이 이름을 쓰거나 상위 패키지 org.springframework.jdbc의 레벨을 올려야 한다.

    JPA를 쓰면 이야기가 달라진다. JPA 자동 구성(JpaBaseConfiguration)이 같은 @ConditionalOnMissingBean(TransactionManager.class) 조건으로 JpaTransactionManager를 등록한다. JDBC용 자동 구성은 순서상 가장 나중에 평가되도록(@AutoConfigureOrder(Ordered.LOWEST_PRECEDENCE)) 되어 있어, 이미 트랜잭션 매니저가 있으면 물러난다. JpaTransactionManager는 JPA 트랜잭션뿐 아니라 같은 데이터소스를 쓰는 JDBC 접근에도 같은 커넥션을 제공할 수 있으므로, JPA와 JdbcTemplate을 함께 쓰는 프로젝트에서도 트랜잭션 매니저는 하나로 충분하다. 그 세부는 JPA 권들에서 다룬다.

    TransactionTemplate과 프록시 방식

    TransactionAutoConfiguration은 두 가지를 더 해 준다. 첫째, 트랜잭션 매니저 후보가 하나이고 TransactionOperations 빈이 없으면 TransactionTemplate 빈을 등록한다. 그래서 부트에서는 템플릿을 생성자에서 new로 만들지 않고 주입받아 써도 된다. 둘째, 트랜잭션 매니저 빈이 있으면 @EnableTransactionManagement를 대신 켠다. 이때 spring.aop.proxy-target-class 속성이 없거나 true면 @EnableTransactionManagement(proxyTargetClass = true)가, false로 지정했을 때만 proxyTargetClass = false가 적용된다. 순수 스프링의 기본값(false, 인터페이스가 있으면 JDK 동적 프록시)과 달리, 부트에서는 서비스가 인터페이스를 구현하고 있어도 기본으로 CGLIB 클래스 프록시가 만들어진다는 뜻이다. 구체 클래스 타입으로 주입받는 코드가 부트에서 문제없이 동작하는 이유가 이것이다.

    자원부트가 등록하는 것 (Boot 3.x)물러나는 조건
    데이터소스HikariCP가 있으면 HikariDataSource, 설정은 spring.datasource.*직접 DataSource 빈을 정의
    트랜잭션 매니저JDBC만 쓰면 JdbcTransactionManager, JPA를 쓰면 JpaTransactionManager직접 TransactionManager 빈을 정의
    트랜잭션 템플릿TransactionTemplateTransactionOperations 빈이 이미 있거나 트랜잭션 매니저 후보가 여럿
    트랜잭션 AOP@EnableTransactionManagement(proxyTargetClass = true)트랜잭션 관리 설정을 직접 켬, 또는 spring.aop.proxy-target-class=false면 JDK 프록시 쪽 설정

    결과적으로 부트 애플리케이션의 리포지토리와 서비스는 이렇게까지 줄어든다. 리포지토리는 생성자로 DataSource를 주입받고, 서비스는 리포지토리만 주입받아 메서드에 @Transactional을 붙인다. 데이터소스, 트랜잭션 매니저, 프록시 설정은 한 줄도 쓰지 않는다. 그 대신 이 회차에서 따라간 모든 단계는 여전히 그 뒤에서 그대로 실행된다.

    정리: 네 단계에서 커넥션은 어디에 있었나

    단계커넥션을 여는 곳리포지토리가 받는 방법서비스에 남은 기술 코드
    JDBC 직접(V0)서비스메서드 파라미터DataSource, Connection, 커밋·롤백, SQLException
    트랜잭션 매니저(V1)트랜잭션 매니저동기화 매니저(ThreadLocal)트랜잭션 매니저 호출, try-catch, SQLException
    트랜잭션 템플릿(V2)트랜잭션 매니저동기화 매니저템플릿 호출과 람다, 체크 예외 감싸기
    @Transactional(V3)프록시가 부른 트랜잭션 매니저동기화 매니저@Transactional, SQLException

    표의 마지막 열에서 끝까지 남은 것이 SQLException이다. 서비스는 트랜잭션 기술로부터는 독립했지만 예외로는 여전히 JDBC에 묶여 있고, 그 탓에 체크 예외가 커밋으로 이어지는 함정까지 생겼다. 다음 5회차는 자바의 체크 예외와 언체크 예외를 바닥부터 다시 보고, 6회차는 스프링의 예외 추상화와 JdbcTemplate으로 이 마지막 의존과 리포지토리의 반복을 걷어 낸다. 트랜잭션 전파, 내부 호출 해결, 여러 트랜잭션 매니저의 선택 같은 주제는 스프링 DB 2편으로 이어진다.
    PlatformTransactionManager
    getTransaction, commit, rollback 세 메서드로 기술마다 다른 트랜잭션 API를 감춘 스프링의 인터페이스. JDBC는 DataSourceTransactionManager(부트 3.x 기본은 하위 클래스 JdbcTransactionManager), JPA는 JpaTransactionManager가 구현한다.
    TransactionStatus
    getTransaction이 돌려주는 현재 트랜잭션의 상태. 새 트랜잭션인지, 롤백 전용인지, 완료되었는지를 담고, 실제 물리 커밋은 새 트랜잭션일 때만 일어난다.
    트랜잭션 동기화
    트랜잭션 매니저가 연 커넥션을 TransactionSynchronizationManager의 ThreadLocal 맵에 DataSource를 키로 묶어 두고, 같은 스레드의 리포지토리가 꺼내 쓰게 하는 장치. 커넥션 파라미터 전달을 없앤다.
    DataSourceUtils
    getConnection은 스레드에 묶인 트랜잭션 커넥션이 있으면 그것을, 없으면 새 커넥션을 돌려준다. releaseConnection은 트랜잭션 커넥션이면 닫지 않고, 아니면 닫는다.
    트랜잭션 정리 단계
    커밋·롤백 뒤 트랜잭션 매니저는 바인딩을 풀고 자동 커밋과 격리 수준을 원래대로 돌린 다음 커넥션을 닫는다. 풀에 오염된 커넥션이 돌아가지 않게 하기 위해서다.
    TransactionTemplate
    트랜잭션 시작·커밋·롤백 틀을 담은 템플릿. 런타임 예외와 에러는 롤백 후 다시 던지고, 선언되지 않은 체크 예외는 롤백 후 UndeclaredThrowableException으로 감싸며, 커밋은 try 바깥에서 한다.
    @Transactional 프록시
    자동 프록시 생성기가 @Transactional 빈을 프록시로 바꿔 등록하고, 프록시 안의 TransactionInterceptor가 트랜잭션 매니저를 호출한다. 기본 규칙은 런타임 예외·에러면 롤백, 체크 예외면 커밋이다.
    스프링 부트 자동 등록
    부트는 HikariDataSource, 트랜잭션 매니저, TransactionTemplate을 등록하고 CGLIB 프록시 방식으로 트랜잭션 AOP를 켠다. 같은 타입의 빈을 직접 등록하면 해당 자동 구성은 물러난다.

    운영 중인 서비스에서 "예외 로그는 찍혔는데 데이터는 반쯤 바뀌어 있다"는 장애가 나면, 이 회차의 세 겹 장치 중 어디가 끊겼는지부터 확인한다. 예외가 체크 예외였다면 기본 롤백 규칙 때문에 커밋되었을 수 있다. 호출 스택에 TransactionInterceptor가 없다면 프록시를 거치지 않은 내부 호출이다. 트랜잭션 메서드 안에서 비동기 작업이나 병렬 스트림으로 리포지토리를 불렀다면 그 부분은 처음부터 다른 스레드의 자동 커밋 커넥션으로 실행되었다. 세 경우 모두 트랜잭션 매니저의 디버그 로그를 켜면 "어느 커넥션으로, 어떤 이름의 트랜잭션이, 커밋되었는지 롤백되었는지"가 한 줄씩 남으므로 원인을 좁히기 쉽다. 부트에서는 로거 이름이 JdbcTransactionManager나 JpaTransactionManager라는 점을 잊지 않는다.

    커넥션 풀 고갈 장애도 이 회차의 지식으로 읽을 수 있다. @Transactional 메서드는 시작부터 끝까지 커넥션 하나를 붙잡는다. 메서드 안에서 외부 API 호출처럼 오래 걸리는 작업을 하면, 그 시간 동안 커넥션은 아무 SQL도 실행하지 않으면서 풀에 돌아가지 못한다. 트랜잭션 범위를 정하는 것은 곧 커넥션 점유 시간을 정하는 일이다. 메서드 전체가 아니라 일부만 트랜잭션으로 묶어야 한다면 TransactionTemplate으로 경계를 코드에 직접 그리는 것이 맞는 선택일 수 있다.

    설정 판단도 달라진다. 데이터베이스를 둘 이상 쓰게 되면 DataSource 후보가 여럿이 되어 부트의 트랜잭션 매니저 자동 구성이 적용되지 않는다. 그때는 데이터소스마다 트랜잭션 매니저를 직접 등록하고, @Transactional에 어느 트랜잭션 매니저를 쓸지 지정해야 한다. 또 동기화 매니저의 키가 DataSource 객체라는 점을 기억하면, 리포지토리와 트랜잭션 매니저가 서로 다른 데이터소스 인스턴스를 주입받는 설정 실수가 왜 "트랜잭션이 안 걸리는" 증상으로 나타나는지 바로 설명할 수 있다.
  • TransferServiceV1을 그대로 두고, 리포지토리의 getConnection()만 DataSourceUtils.getConnection(dataSource)에서 dataSource.getConnection()으로 바꿨다. A에서 "EX"로 2000원을 이체하면 최종 잔액은 어떻게 되는가? 리포지토리가 받는 커넥션과 자동 커밋 상태를 단계별로 적어 보라.
  • @Transactional 메서드 안에서 CompletableFuture.runAsync(...)로 repository.updateBalance("B", 0)을 실행하고, 메서드 끝에서 런타임 예외를 던졌다. B의 잔액은 어떻게 되는가? 동기화 매니저의 구조로 설명하라.
  • 스프링 부트 애플리케이션에서 디버그 로그를 보려고 logging.level.org.springframework.jdbc.datasource.DataSourceTransactionManager=debug를 넣었는데 트랜잭션 로그가 하나도 나오지 않는다. JPA는 쓰지 않는다. 원인을 설명하고 고쳐라.
  • 다음 두 메서드가 같은 서비스 빈에 있다. 외부에서 a()를 호출했을 때와 b()를 호출했을 때, 각각 트랜잭션이 있는지, 예외 후 데이터가 롤백되는지 예측하라. a()는 @Transactional이 없고 b()를 호출한다. b()는 @Transactional이 있고 update 후 IllegalStateException을 던진다.
  • 테스트 설정에 DataSource 빈을 두 개(dataSourceA, dataSourceB) 등록하고 트랜잭션 매니저는 등록하지 않았다. 스프링 부트는 트랜잭션 매니저를 자동 등록하는가? 자동 구성 조건을 근거로 답하라.

    1. A=8000, B=10000으로 2000원이 사라진다. 트랜잭션 매니저는 conn1을 열어 자동 커밋을 끄고 스레드에 묶지만, 리포지토리는 동기화 매니저를 보지 않고 데이터소스에서 직접 새 커넥션을 연다. A 조회와 A 수정은 각각 새로 연 자동 커밋 커넥션으로 실행되고, 수정은 그 즉시 확정된다. 이후 예외로 트랜잭션 매니저가 conn1을 롤백하지만 conn1에서는 아무 SQL도 실행되지 않았으므로 되돌릴 것이 없다. 또 리포지토리는 닫을 때 여전히 DataSourceUtils.releaseConnection을 쓰므로, 자기가 연 커넥션이 스레드에 묶인 트랜잭션 커넥션과 다르다고 판단해 닫는다. 결론적으로 트랜잭션 매니저와 리포지토리가 같은 통로(동기화 매니저)를 써야만 트랜잭션이 성립한다.

    2. B는 0으로 바뀐 채 남는다(비동기 작업이 실행되었다면). runAsync는 다른 스레드(기본은 공용 ForkJoinPool)에서 작업을 실행한다. 그 스레드의 threadLocals 맵에는 바깥 트랜잭션의 커넥션 홀더가 없으므로 DataSourceUtils가 새 자동 커밋 커넥션을 열고, update는 즉시 커밋된다. 바깥 메서드의 런타임 예외로 롤백되는 것은 바깥 스레드의 커넥션뿐이다. 실행 순서는 스레드 스케줄링에 따라 달라지므로, 비동기 작업이 롤백 전에 끝났는지조차 실행마다 다를 수 있다.

    3. 부트 3.x의 JDBC 트랜잭션 매니저 자동 구성은 기본으로 JdbcTransactionManager를 만든다. 트랜잭션 매니저의 로거는 getClass()로 만들어지므로 로거 이름은 org.springframework.jdbc.support.JdbcTransactionManager다. 설정한 로거 이름과 다르니 로그가 나오지 않는다. logging.level.org.springframework.jdbc.support.JdbcTransactionManager=debug로 바꾸거나, 범위를 넓혀 org.springframework.jdbc에 debug를 준다.

    4. 외부에서 a()를 부르면 프록시의 a()에는 어드바이스가 없어 바로 진짜 객체의 a()가 실행되고, 그 안의 b() 호출은 this.b()라 프록시를 거치지 않는다. 트랜잭션이 없으므로 update는 자동 커밋으로 확정되고, 예외가 나도 롤백되지 않는다. 외부에서 b()를 직접 부르면 프록시가 트랜잭션을 시작하고, IllegalStateException은 런타임 예외이므로 롤백된다. 같은 메서드라도 "프록시를 거쳐 들어왔는가"가 결과를 가른다.

    5. 등록하지 않는다. DataSourceTransactionManagerAutoConfiguration의 트랜잭션 매니저 설정은 @ConditionalOnSingleCandidate(DataSource.class) 조건을 가진다. DataSource 후보가 둘이고 그중 어느 것도 주(primary) 후보로 지정되지 않았다면 단일 후보 조건을 만족하지 못한다. 트랜잭션 매니저가 없으니 TransactionAutoConfiguration의 @EnableTransactionManagement 설정(트랜잭션 매니저 빈이 있어야 적용)과 TransactionTemplate 등록도 따라서 적용되지 않는다. 데이터소스마다 트랜잭션 매니저를 직접 등록해야 한다.

     트랜잭션 매니저가 트랜잭션을 시작한 뒤, 리포지토리가 파라미터 없이도 같은 커넥션을 얻을 수 있는 이유로 가장 정확한 것은? 트랜잭션 매니저가 커넥션 풀의 크기를 1로 줄여 같은 커넥션만 나오게 하기 때문이다. 트랜잭션 매니저가 커넥션 홀더를 현재 스레드의 ThreadLocal 맵에 DataSource를 키로 묶어 두고, 리포지토리가 DataSourceUtils로 같은 키를 조회하기 때문이다. 데이터베이스 서버가 같은 애플리케이션에서 온 요청을 하나의 세션으로 합쳐 주기 때문이다. 스프링 컨테이너가 커넥션을 싱글톤 빈으로 등록해 모든 리포지토리에 주입하기 때문이다. doBegin이 bindResource(dataSource, connectionHolder)를 호출하고, DataSourceUtils.doGetConnection이 getResource(dataSource)로 그 홀더를 찾는다. 풀 크기를 바꾸는 일은 없고, DB 서버는 커넥션마다 세션을 따로 만든다. 커넥션을 싱글톤 빈으로 공유하면 동시 요청의 SQL이 한 트랜잭션에 섞인다. @Transactional(속성 기본값) 메서드가 데이터를 수정한 뒤 java.lang.Exception(체크 예외)을 던졌다. 결과는? 롤백되고 예외가 다시 던져진다. 롤백되고 예외는 UndeclaredThrowableException으로 감싸져 던져진다. 커밋되고 예외가 그대로 다시 던져진다. 커밋되고 예외는 삼켜져 호출자에게 전달되지 않는다. 기본 롤백 규칙(DefaultTransactionAttribute.rollbackOn)은 RuntimeException과 Error만 롤백 대상으로 본다. 체크 예외는 커밋한 뒤 원래 예외를 그대로 던진다. 실험에서도 "Initiating transaction commit" 로그 뒤에 예외가 잡혔다. UndeclaredThrowableException으로 감싸는 것은 TransactionTemplate이 선언되지 않은 체크 예외를 만났을 때의 동작이다. DataSourceTransactionManager가 트랜잭션을 끝낸 뒤 커넥션의 자동 커밋을 true로 되돌리는 가장 중요한 이유는? 커넥션 풀에 반납된 커넥션을 다음에 빌리는 쪽이 원래 상태(자동 커밋)를 기대하기 때문이다. 자동 커밋을 켜야 커밋이 실제로 디스크에 기록되기 때문이다. JDBC 명세상 자동 커밋이 꺼진 커넥션은 close할 수 없기 때문이다. 다음 트랜잭션에서 setAutoCommit(false)를 다시 호출하지 않아도 되게 하기 위해서다. 풀의 close는 물리 연결을 끊지 않고 반납한다. 수동 커밋 상태로 반납되면 트랜잭션을 시작하지 않은 다른 요청의 변경이 커밋되지 않은 채 남을 수 있다. 그래서 doBegin에서 원래 자동 커밋이었는지 기억했다가 doCleanupAfterCompletion에서 되돌린다. 커밋의 지속성은 commit 호출로 정해지며, 마지막 보기는 오히려 반대 방향의 이야기다. 서비스 빈 안에서 @Transactional이 없는 메서드 outer()가 같은 클래스의 @Transactional 메서드 inner()를 호출한다. 외부에서 outer()를 호출하면 inner()에 트랜잭션이 적용되지 않는 이유는? @Transactional은 public 메서드에만 적용되는데 inner()가 public이 아니기 때문이다. CGLIB 프록시는 같은 클래스의 메서드를 하나만 가로챌 수 있기 때문이다. 트랜잭션 동기화 매니저가 한 스레드에서 트랜잭션을 한 번만 시작하도록 막기 때문이다. outer() 안의 inner() 호출은 프록시가 아닌 진짜 객체의 this로 일어나 TransactionInterceptor를 거치지 않기 때문이다. 프록시는 외부에서 들어온 호출만 가로챈다. 프록시의 outer()는 어드바이스 없이 진짜 객체로 위임되고, 진짜 객체 안의 this.inner()는 프록시를 다시 거치지 않는다. 실험의 호출 스택에도 TransactionInterceptor가 없었다. 문제의 inner()는 public일 수도 있으므로 가시성은 원인이 아니며, Spring 6.0부터는 클래스 기반 프록시에서 protected·패키지 가시성 메서드도 적용 대상이다.
    트랜잭션 추상화(transaction abstraction)
    JDBC, JPA, JTA처럼 기술마다 다른 트랜잭션 시작·종료 방법을 PlatformTransactionManager라는 하나의 인터페이스 뒤로 감춘 스프링의 설계.
    트랜잭션 동기화(transaction synchronization)
    트랜잭션 자원(커넥션 등)을 현재 스레드에 묶어 같은 트랜잭션 안의 코드가 공유하게 하는 장치. TransactionSynchronizationManager가 ThreadLocal로 구현한다.
    ThreadLocal
    스레드마다 독립된 값을 갖는 변수. 값은 각 Thread 객체의 threadLocals 맵에 ThreadLocal 인스턴스를 키로 저장된다.
    ConnectionHolder
    JDBC 커넥션을 감싸 트랜잭션 활성 여부와 참조 횟수 같은 상태를 함께 들고 있는 스프링의 자원 홀더. 동기화 매니저에 DataSource를 키로 바인딩된다.
    템플릿 콜백 패턴(template callback pattern)
    변하지 않는 처리 틀(템플릿) 안에 변하는 코드 조각(콜백)을 넘겨 실행하는 방식. TransactionTemplate, JdbcTemplate이 이 패턴을 쓴다.
    선언적 트랜잭션 관리(declarative transaction management)
    @Transactional처럼 트랜잭션 경계를 선언만 하고 실제 처리는 프록시에 맡기는 방식. 코드로 직접 경계를 그리는 프로그래밍 방식과 대비된다.
    CGLIB 프록시(CGLIB proxy)
    대상 클래스를 상속한 하위 클래스를 실행 중에 바이트코드로 만들어 메서드를 가로채는 프록시. Spring 6.x에서는 클래스 이름에 $$SpringCGLIB$$와 번호가 붙는다.
    자동 프록시 생성기(auto proxy creator)
    빈이 만들어질 때마다 적용할 어드바이저가 있는지 확인하고, 있으면 원래 객체 대신 프록시를 컨테이너에 등록하는 빈 후처리기.
    내부 호출(self-invocation)
    대상 객체의 메서드가 같은 객체의 다른 메서드를 this로 호출하는 것. 프록시를 거치지 않으므로 그 메서드의 @Transactional이 적용되지 않는다.
