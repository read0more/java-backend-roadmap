    이 회차의 질문: 예외는 계층의 경계를 어떻게 넘는가

    앞의 회차들에서 JDBC로 데이터베이스와 대화하고, 커넥션 풀로 커넥션을 재사용하고, 트랜잭션을 스프링의 추상화로 옮겼다. 트랜잭션 매니저와 트랜잭션 동기화 덕분에 서비스 코드에서 Connection을 직접 꺼내고 닫는 코드는 사라질 수 있다. 그런데 한 가지 흔적이 남는다. 리포지토리가 JDBC를 쓰는 한 그 메서드는 throws SQLException을 선언하고, 그 메서드를 부르는 서비스도 같은 선언을 달아야 컴파일된다. 비즈니스 규칙만 담겨야 할 서비스의 메서드 선언에 "나는 JDBC를 쓰는 리포지토리에 기대고 있다"는 사실이 새겨지는 것이다.

    이 회차는 스프링을 잠시 내려놓고 자바 예외 자체를 다시 본다. 왜 컴파일러는 SQLException을 처리하라고 강제하는가. 그 강제가 계층 구조를 가진 애플리케이션에서는 어떤 비용으로 돌아오는가. 그 비용을 피하려고 예외를 다른 예외로 바꿀 때, 무엇을 반드시 함께 넘겨야 하는가. 그리고 예외 객체 하나를 만들 때 JVM은 실제로 무엇을 기록하는가. 이 네 가지가 이 회차의 질문이다.

    자바 중급 1편에서 예외의 기초는 이미 다뤘다. athrow 명령과 예외 테이블로 스택이 풀리는 과정, finally가 컴파일되는 모양, try-with-resources와 억제된(suppressed) 예외가 그것이다. 이 회차는 그 위에서 설계의 관점을 더한다. 어떤 실패를 어떤 종류의 예외로 표현할지, 예외가 리포지토리에서 서비스, 컨트롤러로 올라가는 동안 각 계층이 무엇을 알아야 하고 무엇을 몰라도 되는지가 중심이다. 이 판단은 다음 회차에서 스프링이 SQLException을 자신의 예외 계층으로 바꿔 주는 이유를 이해하는 바탕이 된다.

    예제는 주문을 저장하는 리포지토리와 결제 승인을 요청하는 클라이언트, 그 둘을 부르는 서비스와 컨트롤러로 구성한다. 모든 예제는 OpenJDK 21(Temurin 21.0.13)에서 컴파일하고 실행했으며, 본문에 실은 컴파일 오류 문구와 실행 결과는 그 실행에서 그대로 옮겼다.

    예외 계층: Throwable 아래의 두 갈래와 SQLException의 자리

    자바에서 던질 수 있는 것은 java.lang.Throwable과 그 하위 타입의 객체뿐이다. throw 문의 피연산자는 Throwable에 대입할 수 있는 타입이어야 하고, catch 절의 매개변수 타입도 마찬가지다. Throwable 바로 아래에는 두 갈래가 있다. 하나는 Error로, OutOfMemoryError나 StackOverflowError처럼 가상 머신이나 실행 환경 수준의 심각한 문제를 나타낸다. Error의 Javadoc은 이것이 합리적인 애플리케이션이 잡으려 해서는 안 되는 문제라고 적는다. 힙이 바닥난 상황에서 애플리케이션 코드가 할 수 있는 복구는 거의 없고, 섣불리 잡아서 계속 실행하면 일관성이 깨진 상태로 요청을 처리하게 된다.

    다른 갈래는 Exception이다. 애플리케이션이 다룰 수 있는 실패는 모두 여기에 속한다. 그리고 Exception의 하위에 RuntimeException이라는 특별한 가지가 있다. Java Language Specification(JLS) §11.1.1은 언체크 예외 클래스(unchecked exception classes)를 "런타임 예외 클래스와 에러 클래스"로 정의하고, 체크 예외 클래스(checked exception classes)를 그 나머지 전부, 즉 Throwable과 그 하위 클래스 중 RuntimeException 계열과 Error 계열을 뺀 모든 것으로 정의한다. 정리하면 체크냐 언체크냐는 클래스에 붙은 표시가 아니라 상속 계층에서의 위치로 정해진다.

                             Throwable                (체크)
                 ┌───────────┴───────────┐
               Error                  Exception   (체크)
          (언체크)                 ┌───────┴──────────────┐
     OutOfMemoryError      RuntimeException        SQLException  (체크)
     StackOverflowError       (언체크)              IOException   (체크)
                       ┌─────────┼─────────┐          └ ConnectException 등
         IllegalArgument  IllegalState  NullPointer
          Exception        Exception    Exception

    이 그림에서 두 가지를 기억해 두자. 첫째, Throwable 자체와 Exception 자체는 체크 예외다. 둘째, RuntimeException은 Exception의 자식이다. 그래서 catch (Exception e)는 체크 예외만 잡는 것이 아니라 NullPointerException 같은 프로그래밍 오류까지 모두 잡는다. catch (Throwable t)는 여기에 Error까지 더한다. 넓은 타입으로 잡는 코드가 위험한 이유는 대부분 이 포함 관계에서 나온다.

    Throwable을 뿌리로 Error, Exception, RuntimeException, SQLException이 어디에 있고 어느 영역이 체크 예외인지 색으로 구분해 보여 준다. 흰 배경의 트리 형태 클래스 계층도. 맨 위 중앙에 "Throwable" 상자. 아래로 두 갈래: 왼쪽 "Error", 오른쪽 "Exception". "Error" 아래에 "OutOfMemoryError", "StackOverflowError" 두 상자. "Exception" 아래로 두 갈래: 왼쪽 "RuntimeException", 오른쪽 "SQLException". "RuntimeException" 아래에 "IllegalStateException" 상자 하나. Error 가지 전체와 RuntimeException 가지 전체를 연한 파란 영역으로 묶고 라벨 "언체크 예외"를 붙인다. Throwable, Exception, SQLException 상자는 연한 주황 영역으로 묶고 라벨 "체크 예외"를 붙인다. 화살표는 자식에서 부모로 향하는 상속 화살표. 깔끔한 다이어그램 스타일, 그림자 없음. 체크 여부는 상속 계층의 위치로 정해진다. RuntimeException과 Error의 가지만 언체크다.

    SQLException은 어디에 있고, 무엇을 담고 있는가

    이 권의 주인공인 java.sql.SQLException은 JDK 1.1부터 있던 클래스로, Exception을 직접 상속한다. 따라서 체크 예외다. JDBC 드라이버가 데이터베이스에서 받은 오류는 거의 모두 이 타입이나 그 하위 타입으로 애플리케이션에 전달된다. SQLException은 메시지와 원인 외에 데이터베이스 오류를 식별하는 정보를 두 가지 더 담는다. 하나는 getSQLState()가 돌려주는 SQLState로, 다섯 글자 문자열이며 앞 두 글자가 오류의 분류(class)를 나타낸다. 다른 하나는 getErrorCode()가 돌려주는 벤더 오류 코드로, 데이터베이스 제품마다 다른 정수다. 같은 "기본 키 중복"이라도 데이터베이스마다 오류 코드가 다르다는 사실이 다음 회차에서 스프링이 오류 코드 변환기를 두는 이유가 된다.

    Java 6(JDBC 4.0)부터는 SQLException 아래에 오류의 성격을 나타내는 하위 계층이 생겼다. JDK 21 소스의 Javadoc이 정의하는 의미를 표로 옮기면 다음과 같다.

    클래스Javadoc이 정의하는 상황대표 하위 클래스
    SQLTransientException애플리케이션의 개입 없이 같은 작업을 다시 시도하면 성공할 수도 있는 상황SQLTimeoutException, SQLTransactionRollbackException, SQLTransientConnectionException
    SQLNonTransientException원인을 고치지 않는 한 같은 작업을 다시 시도해도 실패하는 상황SQLIntegrityConstraintViolationException, SQLSyntaxErrorException, SQLDataException, SQLNonTransientConnectionException
    SQLRecoverableException애플리케이션이 복구 단계를 거친 뒤 트랜잭션 전체를 다시 시도하면 성공할 수도 있는 상황. 최소한 현재 커넥션을 닫고 새 커넥션을 얻어야 한다(JDK에 정의된 하위 클래스 없음)

    예를 들어 SQLIntegrityConstraintViolationException의 Javadoc은 이 예외가 SQLState의 분류 값이 23이거나 벤더가 정한 조건일 때 던져지며, 기본 키·외래 키·유니크 키 같은 무결성 제약 조건 위반을 뜻한다고 적는다. 어떤 상황에서 어떤 하위 클래스를 던질지는 결국 드라이버 구현에 달려 있으므로, Javadoc도 구체적 조건은 드라이버 문서를 보라고 한다. 또 하나 눈여겨볼 점은 SQLException이 Iterable을 구현하고 getNextException()을 가진다는 것이다. 원인(cause) 사슬과는 별도로 SQLException끼리 잇는 "다음 예외" 사슬이 따로 있는 것이다. SQLException의 Javadoc은 이 사슬을 추가 오류 정보를 제공하는 데 쓸 수 있다고 설명한다.

    이 하위 계층은 "다시 시도하면 될 수도 있는가"라는 유용한 정보를 타입으로 표현한다. 그런데 이들은 모두 SQLException의 자식이므로 모두 체크 예외다. SQL 문법 오류처럼 실행 중에 고칠 방법이 전혀 없는 실패도, 컴파일러는 호출하는 쪽이 잡거나 선언하라고 똑같이 요구한다. 이 회차 후반의 문제는 바로 여기서 출발한다.

    예외 기본 규칙: 잡거나 던지거나, 그리고 부모 타입의 의미

    예외를 다루는 규칙은 두 개로 요약된다. 첫째, 예외가 발생한 메서드는 그 예외를 잡아서 처리하거나, 처리하지 못하면 호출한 쪽으로 던져야 한다. 던진 예외는 호출 스택을 한 프레임씩 거슬러 올라가며 처리할 곳을 찾는다. 둘째, 어떤 타입으로 예외를 잡거나 던지면 그 타입의 하위 타입도 함께 잡거나 던진 것이 된다. catch (SQLException e)는 SQLIntegrityConstraintViolationException도 잡고, throws Exception은 모든 체크 예외를 던질 수 있다는 선언이 된다.

    두 번째 규칙에서 컴파일러가 강제하는 제약이 몇 가지 파생된다. 하위 타입을 잡는 catch가 상위 타입을 잡는 catch 뒤에 오면 그 절에는 영원히 도달할 수 없으므로 컴파일 오류다. 또 try 블록 안에서 던져질 수 없는 체크 예외를 catch하면 그것도 컴파일 오류다. 다음 코드를 컴파일해 보자.

    import java.sql.SQLException;

class B {
    void order() {
        try { throw new SQLException("x"); }
        catch (Exception e) {}
        catch (SQLException e) {}      // 상위 타입 뒤의 하위 타입
    }
    void never() {
        try { int a = 1; }
        catch (SQLException e) {}      // 던져질 수 없는 체크 예외
    }
}

    두 번째 오류는 체크 예외에만 해당한다. try 블록이 체크 예외를 던질 수 있는지는 컴파일러가 메서드 선언의 throws만 보고 판단할 수 있지만, 언체크 예외는 어떤 코드에서든 나올 수 있기 때문이다. 같은 이유로 catch (Exception e)나 catch (RuntimeException e)는 try 블록이 비어 있어도 오류가 아니다. Exception은 언체크 예외인 RuntimeException을 포함하므로 "던져질 수 없다"고 단정할 수 없다.

    끝까지 아무도 잡지 않으면

    예외가 호출 스택의 바닥, 즉 스레드의 첫 메서드까지 올라가도 잡히지 않으면 그 스레드는 끝난다. JDK 21에서 JVM은 이때 스레드의 미처리 예외 처리기(uncaught exception handler)를 부르고, 따로 지정하지 않았다면 ThreadGroup.uncaughtException이 표준 오류에 Exception in thread "스레드 이름"을 찍은 뒤 printStackTrace를 호출한다. 실제로 ThreadGroup 소스에는 그 문자열을 출력하는 코드가 그대로 있다. 중요한 점은 끝나는 것이 그 스레드 하나라는 것이다.

    public class Uncaught {
    public static void main(String[] args) throws Exception {
        Thread t = new Thread(() -> { throw new IllegalStateException("작업 스레드 실패"); }, "worker-1");
        t.start();
        t.join();
        System.out.println("main은 계속 실행된다");
    }
}

    체크 예외 기본 이해: 컴파일러가 장부를 맞춘다

    체크 예외는 컴파일러가 처리 여부를 확인하는 예외다. JLS §11.2는 메서드나 생성자의 실행 결과로 나올 수 있는 체크 예외에 대해, 그 throws 절이 해당 예외 클래스나 그 상위 클래스를 언급해야 한다고 규정하고, 이 컴파일 시점 검사의 목적을 제대로 처리되지 않는 예외를 줄이는 데 둔다. 비유하면 컴파일러는 메서드마다 "이 메서드에서 나갈 수 있는 체크 예외" 장부를 만들고, 호출하는 쪽의 장부가 그것을 모두 받아 내는지(잡거나 다시 적거나) 대조한다.

    재고에서 물건을 꺼내는 작은 예제로 규칙을 확인해 보자. 재고가 모자라는 상황을 Exception을 상속한 체크 예외로 표현했다.

    public class CheckedBasic {

    static class StockShortageException extends Exception {
        StockShortageException(String message) { super(message); }
    }

    static class Inventory {
        void take(String item, int qty) throws StockShortageException {
            throw new StockShortageException(item + " 재고 부족, 요청 " + qty);
        }
    }

    static class Picker {
        private final Inventory inventory = new Inventory();

        void pickOrSkip(String item) {              // 잡아서 처리한다
            try {
                inventory.take(item, 3);
            } catch (StockShortageException e) {
                System.out.println("건너뜀: " + e.getMessage());
            }
        }

        void pickOrFail(String item) throws StockShortageException {  // 밖으로 던진다
            inventory.take(item, 3);
        }
    }

    public static void main(String[] args) {
        Picker picker = new Picker();
        picker.pickOrSkip("연필");
        try {
            picker.pickOrFail("지우개");
        } catch (StockShortageException e) {
            System.out.println("호출자에게 도착: " + e.getMessage());
        }
    }
}

    한 줄씩 따라가 보자. main이 pickOrSkip("연필")을 부르면 take가 예외 객체를 만들어 던진다. 예외는 take의 프레임을 벗어나 pickOrSkip의 try 블록에 도착하고, 타입이 맞는 catch가 있으므로 거기서 처리된다. pickOrSkip은 정상적으로 반환하고 main은 그 사실을 모른다. 다음으로 pickOrFail("지우개")에서는 같은 예외가 pickOrFail을 그대로 통과한다. pickOrFail은 잡지 않았지만 throws로 선언했으므로 컴파일러의 장부는 맞는다. 예외는 main의 catch에서 잡힌다.

    이제 장부가 맞지 않는 경우를 보자. pickOrFail에서 throws StockShortageException을 지우면, 또는 throws SQLException을 선언한 메서드를 아무 처리 없이 부르면 javac는 다음 오류를 낸다.

    "잡거나(caught) 선언하라(declared to be thrown)"는 문구가 규칙 그 자체다. 이 오류 덕분에 개발자는 실패할 수 있는 호출을 놓치지 않는다. 체크 예외의 장점은 정확히 이것이다. 메서드 선언만 보고 어떤 실패가 올 수 있는지 알 수 있고, 처리를 빠뜨리면 실행하기 전에 컴파일러가 알려 준다.

    throws는 클래스 파일에 기록된다

    컴파일러는 다른 클래스의 메서드가 어떤 체크 예외를 던지는지 어떻게 알까. 소스가 없고 클래스 파일만 있어도 검사가 동작해야 한다. 답은 클래스 파일의 Exceptions 속성이다. Java Virtual Machine Specification(JVMS) §4.7.5가 정의하는 이 속성에 throws 절이 그대로 기록된다. javap -v로 확인해 보자.

    재정의는 장부를 넓힐 수 없다

    체크 예외 규칙은 상속과 만나면 더 강한 제약이 된다. 인터페이스 메서드를 구현하거나 상위 클래스 메서드를 재정의하는 메서드는 원래 메서드가 선언하지 않은 체크 예외를 새로 던질 수 없다(JLS §8.4.8.3). 호출하는 쪽은 인터페이스 타입만 보고 장부를 맞췄는데, 구현체가 장부에 없는 체크 예외를 던지면 약속이 깨지기 때문이다.

    이 규칙은 설계에 직접 영향을 준다. JDBC 구현체가 SQLException을 그대로 던지게 하려면 인터페이스가 먼저 void save(String s) throws SQLException으로 선언해야 한다. 그 순간 기술에 중립적이어야 할 인터페이스가 java.sql 패키지에 묶인다. 반대로 하위 메서드가 장부를 좁히는 것, 즉 상위가 선언한 예외의 일부만 던지거나 아예 던지지 않는 것은 허용된다.

    체크 예외의 단점도 여기서 보인다. 실무에서는 처리할 수 없는 예외가 많다. 그런 예외도 컴파일러는 모두 잡거나 선언하라고 하므로, 실제로는 아무것도 하지 않는 throws 선언이 호출 경로의 모든 메서드에 반복된다. 이 반복이 계층을 넘으면 어떤 문제가 되는지는 조금 뒤 "체크 예외 활용"에서 구체적으로 본다.

    언체크 예외 기본 이해: 선언은 선택, 책임은 그대로

    언체크 예외는 컴파일러가 처리 여부를 확인하지 않는 예외다. JLS §11.2는 언체크 예외 클래스가 컴파일 시점 검사에서 면제된다고 적는다. 그 외의 동작은 체크 예외와 똑같다. 잡으면 처리되고, 잡지 않으면 호출 스택을 거슬러 올라간다. 차이는 오직 잡지도 선언하지도 않았을 때 컴파일러가 아무 말도 하지 않는다는 데 있다. 앞의 예제에서 상위 타입만 RuntimeException으로 바꿔 보자.

        StockShortageException(String message) { super(message); }

    언체크 예외도 throws에 적을 수 있다. 앞의 javap 출력에서 보았듯 적으면 클래스 파일에 기록되고, IDE와 문서 도구가 그것을 보여 준다. 다만 컴파일러는 그 선언을 근거로 호출하는 쪽을 검사하지 않는다. 그래서 언체크 예외를 주로 쓰는 코드에서는 중요한 예외를 메서드 선언이나 Javadoc의 @throws 태그로 문서화하는 습관이 체크 예외의 장부 역할을 대신한다.

    언체크 예외의 장점은 처리할 수 없는 예외를 중간 계층이 신경 쓰지 않아도 된다는 것이다. 예외를 처리할 수 있는 곳에서만 잡고, 나머지 계층의 코드와 선언은 예외와 무관하게 유지된다. 단점은 그 대가다. 개발자가 처리해야 할 예외를 놓쳐도 컴파일러가 알려 주지 않는다. 놓친 예외는 실행 중에, 대개 운영 환경에서 처음 드러난다.

    체크 예외 활용: 언제 쓰고, 어디서 문제가 되는가

    두 종류의 예외를 언제 쓸지에 대해 이 강좌는 다음 기준을 따른다. 기본은 언체크 예외를 쓴다. 체크 예외는 호출하는 쪽이 그 실패를 반드시 의식하고 처리해야 하는, 비즈니스 흐름의 일부인 실패에만 쓴다. 예를 들어 계좌 이체에서 잔고가 부족한 경우, 호출하는 쪽은 사용자에게 안내하거나 다른 결제 수단을 제안하는 식으로 이 실패를 정상적인 흐름의 한 갈래로 다뤄야 한다. 이런 실패는 놓치면 곤란하므로 컴파일러의 도움을 받을 가치가 있다. 반면 데이터베이스 서버가 응답하지 않는 상황이나 SQL 문법이 틀린 상황은 서비스 로직이 그 자리에서 할 수 있는 일이 없다. 이 기준이 왜 합리적인지는 체크 예외를 계층 구조에서 써 보면 드러난다.

    주문 저장과 결제 승인을 하는 애플리케이션을 생각해 보자. 리포지토리는 JDBC를 쓰므로 SQLException을, 결제 클라이언트는 소켓으로 외부 시스템에 연결하므로 java.net.ConnectException(IOException의 하위 클래스로 체크 예외다)을 던진다. 둘 다 서비스 계층에서는 복구할 방법이 없는 실패다.

    import java.net.ConnectException;
import java.sql.SQLException;

class OrderRepository {
    void save(String orderId) throws SQLException { /* ... */ }
}
class PaymentClient {
    void approve(String orderId) throws ConnectException { /* ... */ }
}
class OrderService {
    private final OrderRepository repository = new OrderRepository();
    private final PaymentClient paymentClient = new PaymentClient();

    void place(String orderId) throws SQLException, ConnectException {
        repository.save(orderId);
        paymentClient.approve(orderId);
    }
}
class OrderController {
    private final OrderService service = new OrderService();

    String order(String orderId) throws SQLException, ConnectException {
        service.place(orderId);
        return "ok";
    }
}

    이 코드는 컴파일된다. 그리고 바로 그 점이 문제다. 컴파일러의 요구를 만족시키는 가장 쉬운 방법이 선언을 위로 복사하는 것이기 때문에, 서비스와 컨트롤러의 메서드 선언에 두 예외가 그대로 올라왔다. 여기에는 두 가지 문제가 겹쳐 있다.

    문제 1: 복구할 수 없는 예외를 모두가 짊어진다

    OrderService.place가 SQLException을 잡는다고 해 보자. 무엇을 할 수 있을까. 데이터베이스가 내려갔다면 서비스는 데이터베이스를 살릴 수 없다. SQL 문법이 틀렸다면 코드를 고쳐 다시 배포해야 한다. 컨트롤러도 마찬가지다. 결국 이런 예외는 계층을 따라 끝까지 올라가 공통 처리 지점에서 로그로 남고 사용자에게 "잠시 후 다시 시도해 달라"는 오류 응답으로 바뀐다. 그 과정에서 중간 계층이 한 일은 throws 선언을 복사한 것뿐이다. 호출 경로에 메서드가 열 개 있으면 열 개의 선언이 같은 정보를 반복한다.

    문제 2: 기술 의존이 위로 번진다

    더 근본적인 문제는 의존 관계다. OrderService와 OrderController의 파일 맨 위에 import java.sql.SQLException;이 생겼다. 서비스와 컨트롤러가 JDBC라는 특정 데이터 접근 기술에 컴파일 시점에 의존하게 된 것이다. 이제 리포지토리를 JPA로 바꾼다고 해 보자. JPA는 JDBC와 다른 예외를 쓴다. Jakarta Persistence의 PersistenceException은 RuntimeException을 상속하므로, 바꾼 뒤에는 SQLException 선언이 더 이상 맞지 않는다. 리포지토리 하나를 바꿨을 뿐인데 그 리포지토리에 기대는 모든 서비스와 컨트롤러의 선언과 import를 고쳐야 한다. 스프링 핵심 원리 기본편에서 본 개방-폐쇄 원칙(OCP)과 의존관계 역전 원칙(DIP)이 지키려던 것, 즉 구현 기술을 바꿔도 클라이언트 코드는 바뀌지 않아야 한다는 약속이 예외 선언 한 줄 때문에 깨진다.

    인터페이스를 도입해도 해결되지 않는다. 앞에서 본 재정의 규칙 때문에, JDBC 구현체가 SQLException을 던지려면 인터페이스 메서드가 throws SQLException을 선언해야 한다. 그러면 인터페이스 자체가 java.sql에 묶이고, 그 인터페이스는 더 이상 "기술에 중립적인 저장소 계약"이 아니다. 체크 예외는 메서드의 반환 타입만큼이나 강하게 계약의 일부가 된다는 점을 기억해 두자.

       OrderController ── throws SQLException, ConnectException ──┐
         │ (import java.sql.*, java.net.*)                     │ 기술 의존이
   OrderService    ── throws SQLException, ConnectException ──┤ 위로 번진다
         │                                                     │
   OrderRepository ── throws SQLException     (JDBC)          │
   PaymentClient   ── throws ConnectException (소켓)  ─────────┘

    throws Exception이라는 탈출구와 그 대가

    선언이 길어지는 것이 번거로워 throws Exception 하나로 모든 체크 예외를 뭉뚱그리는 코드를 종종 본다. 두 번째 기본 규칙에 따라 이 선언은 모든 체크 예외를 포함하므로 컴파일은 된다. 하지만 이것은 체크 예외라는 장치를 끄는 것과 같다. 이 메서드를 부르는 쪽은 어떤 체크 예외가 오는지 알 수 없고, 정말로 놓치면 안 되는 비즈니스 체크 예외가 새로 생겨도 컴파일러는 이미 Exception으로 장부가 맞았다고 판단해 아무것도 알려 주지 않는다. 짝을 이루는 catch (Exception e)는 더 위험하다. 앞의 계층 그림에서 보았듯 이것은 NullPointerException 같은 프로그래밍 오류와 뒤에서 볼 InterruptedException까지 함께 잡는다.

    람다 안에서는 체크 예외를 던질 수 없다

    체크 예외가 불편해지는 곳이 하나 더 있다. 람다와 스트림이다. 람다와 함수형 인터페이스는 자바 고급 3편에서 자세히 다루므로, 여기서는 람다 본문이 함수형 인터페이스의 추상 메서드를 구현한 것이라는 점만 알면 된다. Stream.map이 받는 java.util.function.Function의 apply 메서드는 throws 절이 없다. 람다 본문은 이 메서드의 구현이므로, 재정의 규칙과 같은 이치로 장부에 없는 체크 예외를 밖으로 던질 수 없다(JLS §11.2.3은 람다 본문이 대상 함수 타입의 throws 절에 없는 체크 예외를 던질 수 있으면 컴파일 오류로 규정한다).

List all(List ids) {

}

    all 메서드에 throws SQLException을 붙여도 소용없다. 예외가 나가야 하는 곳은 all이 아니라 람다가 구현하는 apply이기 때문이다. 결국 람다 안에서 잡아 언체크 예외로 바꿔 던지는 수밖에 없다. JDK도 같은 선택을 했다. Java 8에서 스트림 API와 함께 java.io.UncheckedIOException이 추가되었고, BufferedReader.lines()의 Javadoc은 내부에서 IOException이 나면 그것을 UncheckedIOException으로 감싸 스트림 연산에서 던진다고 적는다. 체크 예외를 언체크 예외로 감싸는 것은 우회 기법이 아니라 표준 라이브러리도 쓰는 정식 방법이다.

    언체크 예외 활용: 경계에서 바꾸고, 원인은 품고 간다

    해법은 기술이 드러나는 경계에서 체크 예외를 잡아 언체크 예외로 바꾸는 것이다. 이렇게 예외를 다른 예외로 바꾸는 것을 예외 전환(exception translation)이라 하고, 원래 예외를 새 예외의 원인으로 넣는 것을 예외 포함 또는 예외 연결(exception chaining)이라 한다. 앞의 예제를 바꿔 보자.

    import java.net.ConnectException;
import java.sql.SQLException;

class RepositoryException extends RuntimeException {
    RepositoryException(String message, Throwable cause) { super(message, cause); }
}
class PaymentGatewayException extends RuntimeException {
    PaymentGatewayException(String message, Throwable cause) { super(message, cause); }
}

class OrderRepository {
    void save(String orderId) {
        try {
            insert(orderId);
        } catch (SQLException e) {
            throw new RepositoryException("주문 저장 실패: " + orderId, e);
        }
    }
    private void insert(String orderId) throws SQLException { /* JDBC 코드 ... */ }
}
class PaymentClient {
    void approve(String orderId) {
        try {
            send(orderId);
        } catch (ConnectException e) {
            throw new PaymentGatewayException("결제 승인 요청 실패: " + orderId, e);
        }
    }
    private void send(String orderId) throws ConnectException { /* 소켓 코드 ... */ }
}
class OrderService {
    private final OrderRepository repository = new OrderRepository();
    private final PaymentClient paymentClient = new PaymentClient();

    void place(String orderId) {
        repository.save(orderId);
        paymentClient.approve(orderId);
    }
}
class OrderController {
    private final OrderService service = new OrderService();

    String order(String orderId) {
        service.place(orderId);
        return "ok";
    }
}

    달라진 점을 따라가 보자. SQLException이라는 이름은 이제 OrderRepository 안에만 있다. insert가 던진 체크 예외는 같은 클래스의 save에서 잡혀 RepositoryException으로 바뀌고, 이 예외는 언체크이므로 OrderService.place와 OrderController.order는 아무것도 선언하지 않는다. 두 클래스의 import에서 java.sql과 java.net이 사라졌다. 리포지토리를 다른 기술로 바꿔도, 그 구현이 실패를 RepositoryException(또는 같은 의미의 언체크 예외)으로 알리는 한 서비스와 컨트롤러는 바뀌지 않는다.

    그렇다고 예외가 사라진 것은 아니다. 실패하면 RepositoryException이 서비스와 컨트롤러를 그대로 통과해 올라가고, 웹 애플리케이션이라면 스프링 MVC의 @ExceptionHandler나 @ControllerAdvice 같은 공통 처리 지점, 또는 서블릿 컨테이너의 오류 처리에서 한꺼번에 처리된다. 예외를 처리하는 코드가 여러 계층에 흩어지지 않고 한 곳에 모인다는 것이 이 구조의 또 다른 장점이다. 반대로 복구할 수 있는 특정 실패만 골라 잡고 싶다면, 그 실패를 나타내는 언체크 예외의 하위 타입을 만들고 필요한 계층에서 그 타입만 잡으면 된다. 예를 들어 키 중복이라면 새 키로 다시 시도할 수 있다. 데이터베이스마다 다른 오류 코드를 보고 그런 타입을 고르는 일은 다음 회차의 주제다.

    왼쪽은 체크 예외가 모든 계층의 선언에 번진 구조, 오른쪽은 리포지토리와 클라이언트 경계에서 원인을 품은 언체크 예외로 바뀌어 위 계층이 기술을 모르는 구조를 나란히 비교한다. 좌우 두 패널로 나뉜 비교 다이어그램. 각 패널에 위에서 아래로 "컨트롤러", "서비스", "리포지토리" 세 상자가 세로로 쌓여 있다. 왼쪽 패널 제목 "체크 예외를 그대로 던질 때": 세 상자 모두 옆에 빨간 꼬리표 "throws SQLException"이 붙어 있고, 아래에서 위로 빨간 화살표가 세 상자를 관통한다. 오른쪽 패널 제목 "경계에서 전환할 때": "리포지토리" 상자 안에서 작은 빨간 상자 "SQLException"이 큰 파란 상자 "RepositoryException"에 안겨 있는 모양(원인으로 포함됨을 표현), 그 위의 "서비스", "컨트롤러" 상자에는 꼬리표가 없고 파란 점선 화살표가 위로 통과해 맨 위의 "공통 예외 처리" 상자에 도착한다. 평면 벡터 스타일, 흰 배경. 기술 예외는 기술이 드러나는 경계에서 잡고, 원인을 품은 언체크 예외로 바꿔 올려 보낸다.

    언체크 예외를 쓸 때 지켜야 할 것

    언체크 예외는 컴파일러가 확인해 주지 않으므로, 그 공백을 사람이 메워야 한다. 첫째, 중요한 예외는 문서화한다. 메서드 선언에 throws RepositoryException을 적어도 되고, Javadoc에 @throws로 어떤 상황에서 던지는지 적어도 된다. 둘째, 예외를 바꿀 때 반드시 원인을 넘긴다. 위 코드에서 new RepositoryException("...", e)의 두 번째 인수가 그것이다. 이것을 빠뜨리면 무엇을 잃는지는 바로 다음 절에서 실행 결과로 확인한다. 셋째, 바꾼 예외의 메시지에는 원래 예외에 없는, 이 계층만 아는 맥락(여기서는 주문 번호)을 넣는다.

    이 방향은 개인적인 취향이 아니라 자바 생태계의 흐름이기도 하다. 스프링의 데이터 접근 예외의 뿌리인 org.springframework.dao.DataAccessException은 NestedRuntimeException을 거쳐 RuntimeException을 상속한다. 이 클래스의 Javadoc은 런타임 예외이므로 오류를 치명적인 것으로 볼 때(보통의 경우) 사용자 코드가 이 예외를 잡을 필요가 없다고 설명한다. Jakarta Persistence의 PersistenceException도 RuntimeException을 상속하고, JDK도 앞에서 본 것처럼 UncheckedIOException을 추가했다.

    예외의 종류는 트랜잭션 결과에도 영향을 준다. 스프링 레퍼런스에 따르면 선언적 트랜잭션은 기본 설정에서 RuntimeException과 그 하위 타입, 그리고 Error가 던져질 때 롤백하고, 체크 예외가 던져지면 롤백하지 않는다. 비즈니스 실패를 체크 예외로 표현하면 기본적으로 커밋된다는 뜻이다. 이 규칙과 그 설계 의도는 스프링 DB 2편에서 다시 본다.

    예외 포함과 스택 트레이스: 원인을 잃지 않는 법

    예외를 바꿀 때 원인을 넘기는 장치는 Throwable에 처음부터 들어 있다. Throwable의 공개 생성자는 네 개다. 인수 없음, 메시지, 메시지와 원인, 원인. 원인을 받는 생성자는 받은 예외를 cause 필드에 저장하고, getCause()로 꺼낼 수 있다. Throwable의 Javadoc은 원인이 다시 원인을 가질 수 있어 예외들이 사슬을 이루므로 이 장치를 연쇄 예외(chained exception) 기능이라 부른다고 설명한다. 직접 만드는 예외 클래스에는 최소한 메시지와 원인을 받는 생성자를 두어 이 사슬에 참여할 수 있게 해야 한다.

    원인을 넘긴 예외가 어떻게 출력되는지 실행해 보자. 실제 드라이버 대신, SQLState와 벤더 오류 코드를 직접 채운 SQLException을 만들어 던진다. SQLState 23000은 앞에서 본 분류 값 23, 즉 무결성 제약 위반에 해당한다. 행 번호가 출력과 맞도록 파일 전체를 싣는다.

    import java.sql.SQLException;

public class OrderApp {

    static class RepositoryException extends RuntimeException {
        RepositoryException(String message, Throwable cause) { super(message, cause); }
    }

    static class OrderRepository {
        void save(String orderId) {
            try {
                insert(orderId);
            } catch (SQLException e) {
                throw new RepositoryException("주문 저장 실패: " + orderId, e);
            }
        }
        private void insert(String orderId) throws SQLException {
            throw new SQLException("Duplicate entry '" + orderId + "'", "23000", 1062);
        }
    }

    static class OrderService {
        private final OrderRepository repository = new OrderRepository();
        void place(String orderId) {
            repository.save(orderId);
        }
    }

    public static void main(String[] args) {
        OrderService service = new OrderService();
        try {
            service.place("A-100");
        } catch (RepositoryException e) {
            e.printStackTrace();
            SQLException root = (SQLException) e.getCause();
            System.out.println("SQLState=" + root.getSQLState() + ", errorCode=" + root.getErrorCode());
        }
    }
}

    출력을 위에서부터 읽어 보자. 첫 줄은 바깥 예외의 toString(), 즉 클래스 이름과 메시지다. 그 아래 at으로 시작하는 세 줄은 바깥 예외가 만들어진 지점의 호출 스택으로, 맨 위가 가장 최근 프레임이다. 14행은 new RepositoryException(...)이 있는 줄이다. 다음의 Caused by:부터가 원인 예외다. 원인 예외는 18행 insert에서 만들어졌고, 그때 스택은 insert(18행) → save(12행) → place(25행) → main(32행)이었다.

    그런데 출력에는 원인의 프레임이 두 개만 있고 ... 2 more가 붙었다. Throwable.printStackTrace의 Javadoc은 이 줄이, 이 예외의 나머지 스택 트레이스가 자신을 감싼(enclosing) 예외의 스택 트레이스 맨 아래에서부터 표시된 개수만큼의 프레임과 같다는 뜻이라고 설명한다. 실제로 원인의 스택 아래쪽 두 프레임 place(25행)와 main(32행)은 바깥 예외의 아래쪽 두 프레임과 같다. save는 두 예외 모두에 있지만 행 번호가 12와 14로 다르므로 같은 프레임으로 치지 않는다. 그래서 공통인 두 줄을 생략하고 "2 more"라고 적은 것이다. 사슬이 길어도 같은 규칙이 반복된다. 각 원인은 바로 바깥 예외와 비교해 공통 꼬리를 생략한다.

    마지막 줄은 원인을 넘겼기 때문에 얻는 것을 보여 준다. 컨트롤러나 공통 예외 처리기는 getCause()로 원래의 SQLException에 접근해 SQLState와 벤더 오류 코드를 읽을 수 있다. 어떤 SQL이, 어느 줄에서, 어떤 데이터베이스 오류로 실패했는지가 모두 보존된다.

    왼쪽의 호출 스택 네 프레임과 오른쪽의 스택 트레이스 출력 두 부분을 선으로 이어, 생략된 "... 2 more"가 바깥 예외와 공통인 아래쪽 두 프레임이라는 것을 보여 준다. 왼쪽에 세로로 쌓인 스택 프레임 네 개, 위에서부터 "insert:18", "save:12", "place:25", "main:32". 오른쪽에 두 개의 텍스트 블록. 위 블록 제목 "RepositoryException", 줄은 "save:14", "place:25", "main:32". 아래 블록 제목 "Caused by: SQLException", 줄은 "insert:18", "save:12", 그리고 회색 글씨 "... 2 more". 왼쪽의 "insert:18"과 "save:12"에서 아래 블록의 같은 줄로 실선 화살표. 왼쪽의 "place:25"와 "main:32"는 회색 점선 테두리로 묶고, 그 묶음에서 위 블록의 "place:25", "main:32"로 점선 화살표, 그리고 아래 블록의 "... 2 more"로도 점선 화살표를 잇는다. 점선 묶음 옆 라벨 "공통 꼬리". 깔끔한 기술 문서 스타일, 흰 배경. 원인 예외의 프레임 중 바깥 예외와 공통인 아래쪽 꼬리는 "... n more"로 줄여 출력된다.

    원인을 넘기지 않으면 무엇을 잃는가

    이제 흔한 실수를 재현해 보자. 예외를 바꾸면서 원인을 넘기지 않는 코드다.

    import java.sql.SQLException;

public class Lost {
    static void insert() throws SQLException {
        throw new SQLException("Duplicate entry 'A-100'", "23000", 1062);
    }
    static void save() {
        try {
            insert();
        } catch (SQLException e) {
            throw new RuntimeException("주문 저장 실패");   // 원인을 넘기지 않았다
        }
    }
    public static void main(String[] args) {
        save();
    }
}
    Exception in thread "main" java.lang.RuntimeException: 주문 저장 실패
	at Lost.save(Lost.java:11)
	at Lost.main(Lost.java:15)

    Caused by:가 없다. 운영 환경의 로그에 이것만 남았다면 우리가 아는 것은 "11행에서 저장에 실패했다"뿐이다. 어떤 SQL이 실패했는지, 데이터베이스가 무슨 오류를 돌려줬는지, 연결 실패인지 제약 위반인지 알 방법이 없다. 원래 예외의 정보는 catch 블록이 끝나는 순간 참조를 잃고 가비지 컬렉션 대상이 되었다. 메시지만 옮기는 new RuntimeException(e.getMessage())도 크게 다르지 않다. 메시지 문자열은 남지만 원래 예외의 타입, SQLState와 오류 코드, 그리고 실패가 시작된 지점의 스택은 모두 사라진다. 예외를 바꿀 때는 생성자의 마지막 인수로 원래 예외를 넘기는 것을 습관으로 만들어야 한다.

    initCause와 원인의 "미설정" 상태

    원인을 받는 생성자가 없는 예외 클래스도 있다. 그럴 때는 initCause(Throwable)로 원인을 나중에 설정할 수 있다. 다만 이 메서드는 한 번만 쓸 수 있다. JDK 21 소스에서 Throwable의 cause 필드는 처음에 자기 자신(this)으로 초기화되어 있고, 이것이 "아직 설정되지 않음"을 뜻한다. getCause()는 이 경우 null을 돌려준다. initCause는 필드가 아직 this일 때만 값을 바꾸고, 이미 설정된 경우(생성자로 원인을 넘긴 경우를 포함해, 그 원인이 null이었더라도)에는 IllegalStateException을 던진다. 자기 자신을 원인으로 넣으려 하면 IllegalArgumentException이다.

    RuntimeException e = new RuntimeException("wrapper", null);   // 원인을 null로 "설정"했다
e.initCause(new Exception("root"));
// java.lang.IllegalStateException: Can't overwrite cause with java.lang.Exception: root

RuntimeException e3 = new RuntimeException("w3");
e3.initCause(e3);
// java.lang.IllegalArgumentException: Self-causation not permitted

    예외를 출력하고 기록하는 방법

    System.out.println(e)는 e.toString()만 출력하므로 클래스 이름과 메시지 한 줄뿐이다. 스택 트레이스와 원인 사슬은 printStackTrace()가 출력하는데, 이 메서드는 기본적으로 표준 오류(System.err)에 쓴다. 실제 애플리케이션에서는 둘 다 쓰지 않고 로깅 라이브러리를 쓴다. 스프링 애플리케이션에서 흔히 쓰는 로깅 API인 SLF4J에서는 예외 객체를 로그 메서드의 마지막 인수로 넘기면 된다. SLF4J FAQ는 마지막 인수가 예외이면 남는 인수가 아니라 예외로 해석한다고 설명하며, 이 동작은 1.6.0부터다. 따라서 log.warn("주문 저장 실패 orderId={}", orderId, e)처럼 쓰면 메시지 뒤에 원인 사슬을 포함한 스택 트레이스가 함께 기록된다. 반대로 log.warn("실패: " + e)처럼 문자열로 이어 붙이면 toString()만 남는다.

    한 층 아래: 스택 트레이스는 언제, 어떻게 만들어지는가

    Throwable의 Javadoc은 throwable이 자신이 만들어진 시점의 스레드 실행 스택 스냅숏을 담는다고 적는다. 던진 시점이 아니라 만든 시점이다. JDK 21 소스를 보면 이유가 보인다. 네 개의 공개 생성자는 모두 첫 줄에서 fillInStackTrace()를 부르고, 이 메서드는 다시 native 메서드 fillInStackTrace(int)를 부른다. 여기서 JVM이 현재 스레드의 스택 프레임을 걸어 내려가며 각 프레임이 어떤 메서드의 어느 바이트코드 위치인지를 내부 형식으로 기록하고, 그 결과를 Throwable의 transient 필드 backtrace와 depth에 넣는다.

    우리가 보는 StackTraceElement 배열은 이때 만들어지지 않는다. getStackTrace()나 printStackTrace()가 처음 불릴 때 getOurStackTrace()가 backtrace를 바탕으로 StackTraceElement.of(backtrace, depth)를 호출해 클래스 이름, 메서드 이름, 파일 이름, 행 번호를 가진 객체 배열로 바꾸고, 그 결과를 stackTrace 필드에 저장해 둔다. 즉 비용이 두 단계로 나뉜다. 예외를 만들 때마다 스택 깊이에 비례하는 걷기와 기록이 일어나고, 스택 트레이스를 실제로 읽을 때에만 사람이 읽을 수 있는 형태로의 변환이 일어난다.

    이 사실에서 몇 가지 결과가 나온다. 첫째, 예외 객체를 미리 만들어 두었다가(예를 들어 static final 필드에) 나중에 던지면, 스택 트레이스는 던진 곳이 아니라 만든 곳, 즉 클래스 초기화 시점의 스택을 가리킨다. 디버깅할 때 엉뚱한 위치를 보게 되는 원인이 된다. 둘째, 예외를 정상적인 흐름 제어에 쓰면, 예를 들어 반복문의 종료 조건을 예외로 처리하면, 반복할 때마다 스택을 걷는 비용을 치른다. 예외는 이름 그대로 예외적인 상황에 쓰는 것이 맞다.

    셋째, 기록되는 깊이에는 상한이 있다. HotSpot에는 MaxJavaStackTraceDepth 옵션이 있고, java -XX:+PrintFlagsFinal -version으로 확인한 JDK 21.0.13의 기본값은 1024다. 무한 재귀로 StackOverflowError를 일으켜 보면 실제 재귀 깊이는 1024보다 훨씬 깊어도 getStackTrace().length는 1024였고, -XX:MaxJavaStackTraceDepth=50으로 실행하면 50이었다. 깊은 재귀 오류의 트레이스에서 맨 처음 호출 지점이 보이지 않는 것은 이 때문이다.

    넷째, 스택 트레이스를 아예 기록하지 않는 예외도 만들 수 있다. Java 7에 추가된 보호(protected) 생성자 Throwable(String message, Throwable cause, boolean enableSuppression, boolean writableStackTrace)에서 writableStackTrace를 false로 넘기면 fillInStackTrace()를 부르지 않고, 이후 getStackTrace()는 길이 0인 배열을 돌려준다. Javadoc은 이런 예외가 적절한 경우로, 메모리가 부족할 때 가상 머신이 예외 객체를 재사용하는 상황과 두 하위 시스템 사이의 흐름 제어처럼 같은 예외 객체를 반복해서 잡고 다시 던지는 상황을 든다. 일반적인 애플리케이션 예외에는 쓰지 않는다. 스택 트레이스가 없는 예외는 디버깅할 때 아무것도 알려 주지 않기 때문이다.

    운영 로그에서 스택 트레이스가 사라지는 현상

    마지막으로, 스택 트레이스가 개발자의 의도와 무관하게 사라지는 경우가 있다. 다음 코드는 0으로 나누기를 20만 번 반복하면서, 스택 트레이스가 비어 있는 예외가 처음 나타나는 순간을 찾는다.

    public class FastThrow {
    static int divide(int a, int b) { return a / b; }

    public static void main(String[] args) {
        for (int i = 1; i <= 200_000; i++) {
            try {
                divide(i, 0);
            } catch (ArithmeticException e) {
                if (e.getStackTrace().length == 0) {
                    System.out.println(i + "번째 예외: 메시지=" + e.getMessage() + ", 스택 트레이스 길이=0");
                    return;
                }
            }
        }
        System.out.println("끝까지 스택 트레이스가 채워졌다");
    }
}
    1174번째 예외: 메시지=null, 스택 트레이스 길이=0
1192번째 예외: 메시지=null, 스택 트레이스 길이=0
1194번째 예외: 메시지=null, 스택 트레이스 길이=0

    처음 천여 번은 정상적인 ArithmeticException("/ by zero" 메시지와 스택 트레이스가 있는)이 나오다가, 어느 순간부터 메시지도 스택 트레이스도 없는 예외가 나온다. 정확히 몇 번째인지는 JIT 컴파일 시점에 달려 있어 실행마다 다르다. 이것은 HotSpot의 OmitStackTraceInFastThrow 옵션 때문이며, 앞의 PrintFlagsFinal 출력에서 기본값은 true였다. 같은 프로그램을 -XX:-OmitStackTraceInFastThrow로 실행하거나, JIT 컴파일 없이 인터프리터로만 실행하는 -Xint로 실행하면 끝까지 스택 트레이스가 채워졌다. 빈 스택 트레이스 예외들이 같은 객체인지 확인하는 실험도 해 보았는데, 처음 나타난 빈 예외 이후에 나온 빈 예외 15만여 개가 모두 그 첫 객체와 ==로 같았다(그 사이에 스택 트레이스가 채워진 예외도 4만여 개 섞여 나왔다). HotSpot의 JIT 컴파일러가 자주 발생하는 암묵적 예외(이 실험에서는 정수 나눗셈의 ArithmeticException)를 컴파일된 코드에서 미리 만들어 둔 하나의 객체로 대신 던진 것이다. 이것은 JVM 명세가 아니라 HotSpot 구현의 동작이다.

    실무에서 이 현상은 이렇게 나타난다. 같은 NullPointerException이 반복해서 나던 서버의 로그를 보니 최근 로그에는 스택 트레이스 없이 예외 이름만 찍혀 있다. 이럴 때는 로그를 거슬러 올라가 그 예외가 처음 나기 시작한 시점의 기록을 찾으면 정상적인 스택 트레이스가 있다. 또는 원인을 찾는 동안 -XX:-OmitStackTraceInFastThrow로 서버를 띄울 수 있다. 어느 쪽이든, "스택 트레이스가 없다"는 것이 "예외가 이상한 곳에서 났다"는 뜻이 아니라는 것을 알면 엉뚱한 곳을 뒤지는 시간을 줄일 수 있다.

    예외 객체를 만드는 순간 JVM이 스레드 스택을 걸어 backtrace를 기록하고, 스택 트레이스를 처음 읽을 때 StackTraceElement 배열이 만들어진다는 두 단계를 시간 순서로 보여 준다. 가로 시간축을 가진 시퀀스 다이어그램. 왼쪽 세로 막대 "스레드 스택"에는 프레임 상자 세 개가 위에서부터 "insert", "save", "main"으로 쌓여 있다. 가운데 세로 막대 "Throwable 객체"에는 두 칸 "backtrace"와 "stackTrace"가 있다. 오른쪽 세로 막대 "호출자". 첫 번째 화살표: "insert" 프레임에서 "Throwable 객체"로 "new + fillInStackTrace()" 라벨, 스택의 세 프레임에서 "backtrace" 칸으로 얇은 점선들이 모인다. 두 번째 화살표: "Throwable 객체"에서 "호출자"로 "throw (스택 풀기)". 세 번째 화살표: "호출자"에서 "Throwable 객체"로 "getStackTrace() 첫 호출", 이때 "backtrace" 칸에서 "stackTrace" 칸으로 굵은 화살표와 라벨 "StackTraceElement[] 생성". 차분한 색, 흰 배경, 평면 스타일. 스택은 예외를 만들 때 기록되고, 사람이 읽는 형태의 배열은 처음 읽을 때 만들어진다(OpenJDK 21 기준).

    흔한 오해와 함정

    "체크 예외가 더 안전하다"

    컴파일러가 확인해 주니 체크 예외가 더 안전하다는 생각은 절반만 맞다. 확인이 의미 있는 것은 호출하는 쪽이 실제로 할 일이 있는 실패에 한해서다. 할 일이 없는 실패에 체크 예외를 쓰면 개발자는 컴파일러를 달래기 위해 무언가를 써야 하고, 그 무언가는 대개 throws Exception이나 빈 catch 블록이다. 둘 다 체크 예외가 주려던 안전을 오히려 없앤다. 빈 catch는 실패를 성공처럼 보이게 만들어, 문제를 몇 계층 떨어진 곳에서 엉뚱한 증상으로 드러나게 한다. 예외를 정말로 무시해야 하는 드문 경우라면 왜 무시하는지 주석과 로그를 남긴다.

    catch (Exception e)가 삼키는 인터럽트

    넓은 타입으로 잡을 때 생기는 미묘한 문제가 있다. 자바 고급 1편에서 다룰 스레드 인터럽트다. Thread.sleep 같은 차단 메서드는 인터럽트를 받으면 InterruptedException을 던지는데, Thread.sleep의 Javadoc에 따르면 이 예외가 던져질 때 현재 스레드의 인터럽트 상태는 지워진다.

    public class Interrupt {
    static void work() throws Exception {
        Thread.sleep(10_000);
    }
    public static void main(String[] args) throws Exception {
        Thread worker = new Thread(() -> {
            try {
                work();
            } catch (Exception e) {
                System.out.println("잡음: " + e);
            }
            System.out.println("인터럽트 상태: " + Thread.currentThread().isInterrupted());
        });
        worker.start();
        worker.interrupt();
        worker.join();
    }
}
    잡음: java.lang.InterruptedException: sleep interrupted
인터럽트 상태: false

    작업 스레드는 "그만하라"는 요청을 받았지만, catch (Exception e)가 InterruptedException을 일반 실패처럼 잡아 로그 한 줄로 끝냈고, 인터럽트 상태도 지워졌다. 이 스레드를 멈추려던 쪽은 요청이 전달됐는지 알 수 없다. 스레드 풀을 종료할 때 작업이 끝나지 않는 문제가 이런 코드에서 나온다. InterruptedException을 잡았는데 다시 던질 수 없다면 Thread.currentThread().interrupt()로 인터럽트 상태를 되살려 두어야 한다.

    "로그를 남기고 다시 던지면 안전하다"

    계층마다 예외를 잡아 로그를 남기고 다시 던지면, 같은 실패가 로그에 계층 수만큼 반복해서 찍힌다. 장애 상황에서 로그를 읽는 사람은 이것이 한 번의 실패인지 여러 번의 실패인지부터 가려야 한다. 원칙은 단순하다. 예외는 처리하는 곳에서 한 번만 기록한다. 처리하지 않고 전환만 한다면 기록하지 말고 원인을 넘긴다. 공통 예외 처리 지점이 있다면 기록은 대부분 거기서 한 번 이루어진다.

    "원인 메시지만 옮기면 충분하다", "finally는 무엇이든 안전하게 정리한다"

    메시지만 옮기는 전환이 타입, SQLState, 스택을 잃는다는 것은 앞에서 실행으로 확인했다. 그리고 자바 중급 1편에서 본 것처럼 finally 블록 안의 return이나 새로 던진 예외는 try에서 나던 예외를 덮어 버린다. 정리 코드에서 실패가 날 수 있다면 try-with-resources를 써서 정리 중 실패가 억제된(suppressed) 예외로 원래 예외에 붙게 해야 한다. 원인 사슬과 억제된 예외 목록은 둘 다 "실패에 대한 정보를 버리지 않기 위한" 장치라는 점에서 같은 뿌리를 가진다.

    정리: 예외를 다루는 다섯 가지 기준

    이 회차에서 다룬 내용을 실무에서 쓸 수 있는 기준으로 묶어 보자.

    1. 기본은 언체크 예외다. 처리할 수 없는 실패(데이터베이스·네트워크 장애, 코드 결함)는 RuntimeException 계열로 표현해 중간 계층이 몰라도 되게 한다.
    2. 체크 예외는 의도적으로 쓴다. 호출하는 쪽이 반드시 의식하고 처리해야 하는 비즈니스 실패에만 쓴다. 이때 컴파일러의 확인은 비용이 아니라 이득이다.
    3. 기술 예외는 경계에서 바꾼다. SQLException, IOException 같은 기술 예외는 그 기술을 쓰는 클래스 안에서 잡아 의미를 담은 언체크 예외로 바꾸고, 위 계층의 선언과 import에 기술이 새어 나가지 않게 한다.
    4. 바꿀 때는 원인을 넘긴다. 새 예외 생성자의 마지막 인수로 원래 예외를 넘긴다. 메시지에는 이 계층이 아는 맥락을 더한다.
    5. 기록은 처리하는 곳에서 한 번, 예외 객체째로 한다. 로그 메서드의 마지막 인수로 예외를 넘겨 원인 사슬 전체를 남긴다. 넓은 타입으로 잡아 삼키지 않는다.
    이 장의 핵심

    체크 예외는 컴파일러가 장부를 맞추게 하는 장치이고, 그 장부는 throws 절로 메서드 계약의 일부가 된다. 처리할 수 없는 기술 예외를 이 장부에 올리면 기술 의존이 모든 계층의 계약으로 번진다. 그래서 기술 예외는 경계에서 원인을 품은 언체크 예외로 바꾸고, 공통 지점에서 한 번 처리한다. 원인을 넘기는 한 정보는 하나도 잃지 않는다.

    다른 주제와의 연결

    다음 회차에서는 이 회차의 해법을 스프링이 어떻게 일반화하는지 본다. 리포지토리마다 RepositoryException 같은 예외를 직접 만들고 데이터베이스마다 다른 오류 코드를 해석하는 대신, 스프링은 DataAccessException을 뿌리로 하는 기술 중립적 예외 계층과 SQL 오류 코드를 그 계층으로 바꾸는 변환기를 제공하고, JdbcTemplate으로 JDBC의 반복 코드와 예외 전환을 한꺼번에 처리한다.

    예외의 종류는 트랜잭션에도 이어진다. 앞에서 본 스프링의 기본 롤백 규칙(언체크 예외와 Error는 롤백, 체크 예외는 커밋)과 그 규칙을 바꾸는 방법은 스프링 DB 2편에서 다룬다. 공통 예외 처리 지점인 @ExceptionHandler와 서블릿 오류 페이지는 스프링 MVC 2편에서 다뤘고, InterruptedException과 인터럽트 상태의 의미는 자바 고급 1편의 스레드 제어에서 자세히 다룬다. 스택 트레이스가 만들어지는 비용은 JPA나 스프링처럼 프록시와 리플렉션으로 호출 스택이 깊어지는 프레임워크에서 예외 로그가 길어지는 이유와도 연결된다.
    체크 예외와 언체크 예외
    JLS §11.1.1 기준으로 RuntimeException 계열과 Error 계열이 언체크이고 나머지 Throwable 하위 타입은 모두 체크다. 차이는 컴파일러가 잡거나 선언했는지 확인하느냐뿐이다.
    예외 기본 규칙
    예외는 잡아서 처리하거나 호출한 쪽으로 던져야 하고, 어떤 타입으로 잡거나 던지면 그 하위 타입도 포함된다. 끝까지 잡히지 않으면 그 스레드가 끝난다.
    throws와 Exceptions 속성
    throws 절은 클래스 파일의 Exceptions 속성에 기록되어 컴파일러가 호출하는 쪽을 검사할 때 쓰인다. 재정의 메서드는 상위 메서드에 없는 체크 예외를 추가할 수 없다.
    SQLException
    Exception을 직접 상속한 체크 예외로, SQLState와 벤더 오류 코드를 담는다. Java 6부터 일시적·비일시적·복구 가능 하위 계층이 있지만 모두 체크 예외다.
    체크 예외의 두 문제
    복구할 수 없는 예외의 throws 선언이 호출 경로 전체에 반복되고, 서비스와 컨트롤러가 java.sql 같은 특정 기술에 컴파일 시점에 의존하게 된다.
    예외 전환과 예외 포함
    기술이 드러나는 경계에서 체크 예외를 잡아 의미를 담은 언체크 예외로 바꾸고, 원래 예외를 원인으로 넘겨 타입·SQLState·스택을 보존한다.
    Caused by와 ... n more
    printStackTrace는 원인 사슬을 Caused by로 이어 출력하고, 바깥 예외와 공통인 아래쪽 프레임을 ... n more로 줄인다.
    스택 트레이스의 생성 시점
    Throwable 생성자가 fillInStackTrace로 만든 시점의 스택을 기록하고, StackTraceElement 배열은 처음 읽을 때 만들어진다(OpenJDK 21). HotSpot은 자주 나는 암묵적 예외의 스택 트레이스를 생략할 수 있다.

    실무에서 예외 설계가 드러나는 순간은 대개 장애 대응이다. 새벽에 오류 알림을 받고 로그를 열었을 때 RuntimeException: 주문 저장 실패 한 줄만 있다면, 원인을 넘기지 않은 전환 한 곳 때문에 데이터베이스 로그와 애플리케이션 로그를 시간으로 맞춰 보는 긴 추리가 시작된다. 반대로 Caused by: 아래에 SQLState와 드라이버의 메시지가 남아 있다면 몇 분 안에 제약 위반인지 연결 실패인지 가를 수 있다. 예외 전환 코드를 리뷰할 때 생성자의 마지막 인수를 확인하는 것만으로도 이런 차이를 만든다.

    체크 예외를 쓸지 판단할 때의 기준은 "호출하는 쪽이 이 실패를 받아서 할 수 있는 일이 있는가"다. 같은 실패라도 계층에 따라 답이 다르다. 결제 승인 실패는 결제 클라이언트 입장에서는 네트워크 문제지만, 주문 서비스 입장에서는 "다른 결제 수단을 안내한다"는 비즈니스 흐름일 수 있다. 이때 기술 예외는 클라이언트 경계에서 언체크로 바꾸고, 서비스가 의식해야 하는 실패는 별도의 타입으로 표현하는 식으로 계층별로 다시 판단한다. 다만 스프링의 선언적 트랜잭션은 체크 예외에 대해 기본적으로 커밋한다는 점을 함께 고려해야 한다. 비즈니스 실패를 체크 예외로 표현했다면 그 실패에서 데이터를 남길지 되돌릴지를 명시적으로 결정해야 한다.

    공통 라이브러리나 사내 프레임워크를 설계할 때는 공개 메서드의 throws 절이 곧 하위 호환성의 일부라는 점을 기억하자. 공개 API에 체크 예외를 새로 추가하면 그 메서드를 부르는 모든 코드가 컴파일되지 않는다. 언체크 예외의 하위 타입을 추가하는 것은 기존 호출 코드를 깨지 않는다. 운영 중인 JVM에서 반복되는 예외의 스택 트레이스가 사라지는 현상(OmitStackTraceInFastThrow)도 알아 두면, 스택 없는 로그를 보고 엉뚱한 곳을 의심하지 않게 된다.

HotSpot의 OmitStackTraceInFastThrow(기본값 true) 때문이다. 같은 위치에서 암묵적 예외가 자주 나면 JIT 컴파일된 코드가 미리 만들어 둔 스택 트레이스 없는 예외 객체를 대신 던질 수 있다. 오전에는 아직 컴파일되지 않았거나 발생 횟수가 적어 정상 예외가 나왔고, 오후에는 생략된 예외가 나온 것이다. 찾는 방법은 첫째, 로그를 거슬러 올라가 같은 예외가 처음 나기 시작한 시점의 기록에서 스택 트레이스를 읽는 것이고, 둘째, -XX:-OmitStackTraceInFastThrow로 JVM을 다시 띄워 다음 발생 때 전체 스택 트레이스를 받는 것이다.

    5번. 스레드 풀 종료는 작업 스레드에 인터럽트를 보낸다. queue.take()는 인터럽트를 받으면 InterruptedException을 던지면서 인터럽트 상태를 지우는데, catch (Exception e)가 이것을 일반 실패처럼 잡아 로그만 남기고 반복문의 다음 회차로 돌아간다. 인터럽트 상태도 지워졌으므로 스레드는 종료 요청을 영영 알지 못하고 다시 take()에서 기다린다. InterruptedException을 먼저 따로 잡아 인터럽트 상태를 되살리고(Thread.currentThread().interrupt()) 반복문을 빠져나오게 고친다. 예를 들어 catch (InterruptedException e) { Thread.currentThread().interrupt(); return; } catch (Exception e) { log.error("작업 실패", e); }처럼 쓴다.

    체크 예외(checked exception)
    컴파일러가 잡거나 throws로 선언했는지 확인하는 예외. RuntimeException 계열과 Error 계열을 제외한 모든 Throwable 하위 타입이다.
    언체크 예외(unchecked exception)
    컴파일 시점 검사에서 면제되는 예외. RuntimeException 계열과 Error 계열이다.
    예외 전환(exception translation)
    한 계층에서 받은 예외를 그 계층의 의미에 맞는 다른 예외로 바꿔 던지는 것. 기술 예외를 경계에서 언체크 예외로 바꿀 때 쓴다.
    연쇄 예외(chained exception)
    예외가 다른 예외를 원인(cause)으로 품어 사슬을 이루는 Throwable의 기능. getCause로 원인을 따라갈 수 있다.
    스택 트레이스(stack trace)
    예외 객체가 만들어진 시점의 호출 스택 기록. StackTraceElement 배열로 꺼낼 수 있고 printStackTrace가 출력한다.
    Exceptions 속성(Exceptions attribute)
    메서드의 throws 절을 기록하는 클래스 파일 속성(JVMS §4.7.5). 컴파일러가 호출하는 쪽을 검사할 때 읽는다.
    SQLState
    SQLException이 담는 다섯 글자 오류 코드. 앞 두 글자가 오류 분류이며, 23은 무결성 제약 위반이다.
    미처리 예외 처리기(uncaught exception handler)
    스레드에서 잡히지 않은 예외로 스레드가 끝날 때 호출되는 처리기. 기본 동작은 Exception in thread와 스택 트레이스를 표준 오류에 출력하는 것이다.
