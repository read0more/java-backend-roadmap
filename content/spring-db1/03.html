    이 회차의 질문: 두 번의 쓰기 중 하나만 성공하면

    계좌 A에서 B로 3,000원을 보내는 일을 생각해 보자. 데이터베이스 입장에서 이체는 두 번의 쓰기다. A의 잔액에서 3,000을 빼는 UPDATE, 그리고 B의 잔액에 3,000을 더하는 UPDATE. 앞의 회차에서 만든 JDBC 코드로 이 두 문장을 차례로 보내면 대부분은 잘 동작한다. 문제는 첫 번째 문장이 성공하고 두 번째 문장이 실패하는 경우다. 입금 계좌 번호가 잘못되었을 수도 있고, 두 문장 사이에서 애플리케이션 서버가 죽을 수도 있고, 네트워크가 끊길 수도 있다. 그러면 A에서는 돈이 빠졌는데 B에는 들어오지 않은, 어느 쪽에서 보아도 틀린 상태가 데이터베이스에 남는다.

    이 문제는 코드를 더 꼼꼼히 쓴다고 사라지지 않는다. 두 번째 문장이 실패했을 때 첫 번째 문장을 되돌리는 UPDATE를 하나 더 보내는 방법을 떠올릴 수 있지만, 그 되돌리는 문장도 실패할 수 있고, 되돌리기 전에 서버가 죽으면 되돌릴 기회조차 없다. 게다가 되돌리기 전까지 다른 사용자가 중간 상태(A만 줄어든 상태)를 읽어 갈 수 있다. 결국 필요한 것은 "이 문장들은 전부 반영되거나 하나도 반영되지 않는다"는 보장을 데이터베이스 쪽에서 해 주는 것이다. 그 보장이 트랜잭션(transaction)이다.

    이 회차는 세 가지 층을 차례로 내려간다. 먼저 트랜잭션이 무엇을 보장하는지(ACID와 격리 수준)를 정리한다. 다음으로 그 보장이 실제로 어디에 붙어 있는지, 즉 커넥션과 DB 세션의 관계를 본다. 트랜잭션은 추상적인 개념이 아니라 서버 안의 세션 하나가 들고 있는 상태이고, 이 사실이 이 권 나머지 전체를 끌고 간다. 마지막으로 두 세션이 같은 데이터를 건드릴 때 데이터베이스가 쓰는 락을 보고, 자바 서비스 코드에 트랜잭션을 직접 적용해 본다. 직접 적용한 코드가 어떤 문제를 남기는지가 다음 회차 「스프링과 문제 해결 — 트랜잭션」의 출발점이다.

    실험은 앞 회차들과 같은 환경에서 한다. Java 21(Temurin 21.0.13), H2 2.4.240, 커넥션 풀로 HikariCP를 쓴다. 이 회차에 나오는 자바 실행 결과는 모두 H2 메모리 데이터베이스에 커넥션 두 개를 열어 직접 실행해 얻은 것이다. MySQL에 대한 서술은 MySQL 8.0 Reference Manual로 확인한 범위만 적고, 그때는 "MySQL InnoDB 기준"이라고 밝힌다. 본문의 MySQL SQL 예제와 오류 문구는 MySQL 8.4.13과 8.0.46 서버에 세션 두세 개를 열어 직접 실행해 확인했고, 그 결과를 실은 곳에는 버전을 적었다. H2와 InnoDB는 같은 개념을 다르게 구현한 부분이 있어서, 둘이 다른 곳은 따로 짚는다.

    트랜잭션 개념: 작업 단위, 커밋, 롤백

    트랜잭션은 데이터베이스가 하나의 단위로 다루는 작업 묶음이다. 트랜잭션 안에서 실행한 변경은 커밋(commit)을 해야 확정되고, 롤백(rollback)을 하면 트랜잭션 시작 이전 상태로 되돌아간다. 이체라면 출금 UPDATE와 입금 UPDATE를 한 트랜잭션에 넣고, 둘 다 성공하면 커밋, 하나라도 실패하면 롤백한다. 롤백은 애플리케이션이 반대 방향의 SQL을 새로 보내는 것이 아니다. 데이터베이스가 자기가 기록해 둔 변경 이전 정보를 써서 되돌린다. 그래서 애플리케이션이 되돌리는 코드를 직접 짤 필요가 없고, 애플리케이션이 죽어 커밋 명령이 오지 않은 트랜잭션도 데이터베이스가 정리할 수 있다.

    트랜잭션이 보장하는 성질은 흔히 ACID라는 네 글자로 정리한다. 각 글자가 무엇을 약속하는지, 그리고 MySQL InnoDB가 그 약속을 어떤 장치로 지키는지 함께 보면 개념이 구체적으로 잡힌다. MySQL 매뉴얼의 "InnoDB and the ACID Model" 절은 각 성질에 관련된 기능을 나열하는데, 아래 표는 그 목록과 InnoDB 로그 문서를 바탕으로 정리한 것이다.

    성질약속하는 것InnoDB에서 관련된 장치
    원자성(Atomicity)트랜잭션 안의 작업은 전부 반영되거나 전부 반영되지 않는다autocommit 설정, COMMIT, ROLLBACK 문. 되돌릴 정보는 언두 로그(undo log)에 남는다
    일관성(Consistency)트랜잭션 전후로 데이터베이스가 정의된 규칙(제약 조건 등)을 만족한다제약 조건 검사, 크래시 복구와 이중 쓰기 버퍼(doublewrite buffer)로 손상된 상태를 남기지 않음
    격리성(Isolation)동시에 실행되는 트랜잭션이 서로의 중간 상태에 간섭받지 않는다(정도는 격리 수준이 정함)격리 수준과 SET TRANSACTION, 락, 다중 버전(MVCC)
    지속성(Durability)커밋이 성공했다면 그 결과는 장애가 나도 사라지지 않는다리두 로그(redo log)와 innodb_flush_log_at_trx_commit, 이중 쓰기 버퍼, 저장 장치와 운영체제의 fsync()

    원자성과 지속성을 뒷받침하는 두 로그는 방향이 반대다. 언두 로그는 "바꾸기 전 값"을 기록한다. MySQL 매뉴얼은 언두 로그 레코드를 트랜잭션이 클러스터드 인덱스 레코드에 가한 최근 변경을 되돌리는 방법에 대한 정보라고 설명하고, 다른 트랜잭션이 일관된 읽기를 할 때 바뀌기 전 데이터를 이 언두 로그에서 가져온다고 적는다. 롤백할 때도, 다른 세션에 옛 버전을 보여 줄 때도 언두 로그가 쓰인다. 리두 로그는 반대로 "바꾼 내용"을 기록한다. 매뉴얼의 정의로는 크래시 복구 때 미완료 트랜잭션이 쓴 데이터를 바로잡는 디스크 기반 자료 구조이고, 데이터 파일에 다 반영되지 못한 변경은 서버가 다시 뜰 때 연결을 받기 전에 자동으로 재생된다.

    지속성에서 중요한 것은 "언제 디스크에 내리는가"다. innodb_flush_log_at_trx_commit의 기본값은 1이고, 매뉴얼은 이 값이 완전한 ACID 준수에 필요하며 커밋할 때마다 로그를 쓰고 디스크로 플러시한다고 설명한다. 0이면 로그를 초당 한 번 쓰고 플러시하며, 2면 커밋마다 쓰되 플러시는 초당 한 번 한다. 0이나 2에서는 플러시되지 않은 트랜잭션이 크래시 때 사라질 수 있다. 즉 "커밋 성공"이라는 응답이 지속성을 의미하려면 그 응답 전에 로그가 디스크에 내려가 있어야 하고, 기본 설정은 그렇게 동작한다. 커밋이 공짜가 아닌 이유도 여기에 있다. 커밋마다 디스크 플러시가 일어나므로, 문장마다 커밋하는 것과 여러 문장을 묶어 한 번 커밋하는 것은 디스크 입장에서 일의 양이 다르다.

    일관성은 네 글자 중 성격이 다르다. 나머지 셋은 데이터베이스가 기계적으로 지켜 주는 성질인데, 일관성의 상당 부분은 "무엇이 올바른 상태인가"를 정의하는 쪽, 즉 스키마 설계자와 애플리케이션의 몫이다. 데이터베이스는 기본 키, 외래 키, NOT NULL, CHECK 같은 제약 조건을 위반하는 변경을 거부해 줄 뿐이다. "이체 전후 두 계좌의 잔액 합은 같아야 한다"는 규칙은 데이터베이스가 모르는 규칙이다. 이 규칙은 애플리케이션이 출금과 입금을 한 트랜잭션에 넣었을 때 비로소 원자성 덕분에 지켜진다.

    일상에서 가져온 비유장바구니와 결제 버튼

    온라인 쇼핑몰에서 물건을 장바구니에 담는 동안은 아무것도 확정되지 않는다. 담고 빼기를 몇 번 해도 상점의 재고와 내 카드에는 변화가 없고, 결제 버튼을 누르는 순간 담긴 것 전부가 한 번에 주문된다. 결제를 포기하고 창을 닫으면 장바구니 내용은 없던 일이 된다. 트랜잭션 안의 변경이 장바구니, 커밋이 결제 버튼, 롤백이 창 닫기에 해당한다. 다만 비유가 깨지는 지점이 있다. 실제 트랜잭션은 커밋 전에도 변경 대상 행에 락을 걸어 다른 트랜잭션의 쓰기를 막는다. 장바구니에 담는 순간 그 상품을 다른 사람이 못 사게 막는 쇼핑몰은 드물지만, 데이터베이스는 바로 그렇게 동작한다.

    격리 수준: 동시에 실행될 때 무엇을 보게 할 것인가

    ACID의 격리성을 글자 그대로 지키려면 트랜잭션을 한 번에 하나씩 순서대로 실행하면 된다. 하지만 그러면 동시에 들어오는 요청을 처리할 수 없다. 그래서 SQL 표준은 격리의 정도를 네 단계로 나누고, 단계가 낮을수록 동시 처리량을 얻는 대신 특정 이상 현상을 허용한다. JDBC의 Connection 인터페이스는 이 네 단계를 상수로 정의하고, Javadoc에 각 단계에서 일어날 수 있는 현상을 적어 두었다.

    • 더티 리드(dirty read): 다른 트랜잭션이 아직 커밋하지 않은 변경을 읽는 것. 그 트랜잭션이 롤백하면 존재한 적 없는 값을 읽은 셈이 된다.
    • 반복 불가능한 읽기(non-repeatable read): 한 트랜잭션이 같은 행을 두 번 읽는 사이에 다른 트랜잭션이 그 행을 바꾸고 커밋해서, 두 번째 읽기에서 다른 값이 나오는 것.
    • 팬텀 읽기(phantom read): 같은 WHERE 조건으로 두 번 조회하는 사이에 다른 트랜잭션이 조건에 맞는 행을 삽입해서, 두 번째 조회에 없던 행이 나타나는 것.

    이 표는 JDBC Javadoc이 각 상수에 붙인 설명을 옮긴 것이고, "발생 가능"은 그 수준이 해당 현상을 막을 의무가 없다는 뜻이지 반드시 일어난다는 뜻이 아니다. 실제 데이터베이스는 표준이 허용하는 것보다 강하게 막기도 한다. MySQL InnoDB의 기본 격리 수준은 REPEATABLE READ다. InnoDB 매뉴얼에 따르면 REPEATABLE READ에서 같은 트랜잭션 안의 일관된 읽기(consistent read)는 그 트랜잭션의 첫 읽기 때 만든 스냅샷을 계속 읽고, READ COMMITTED에서는 일관된 읽기마다 새 스냅샷을 만든다. 같은 행을 두 번 읽어도 같은 값이 나오는 이유는 행에 락을 걸어서가 아니라, 처음 만든 시점의 버전을 언두 로그로 재구성해 보여 주기 때문이다. 이렇게 행의 여러 버전을 유지하며 읽는 방식을 다중 버전 동시성 제어(MVCC, multi-version concurrency control)라고 부른다.

    한편 이번 실험에 쓰는 H2 2.4.240은 기본 격리 수준이 READ COMMITTED다. 뒤에 나오는 실험에서 getTransactionIsolation()이 2를 돌려주고, H2의 INFORMATION_SCHEMA.SESSIONS 표의 ISOLATION_LEVEL 열에도 READ COMMITTED가 찍힌 것으로 확인했다. 같은 코드를 MySQL에 연결하면 기본 격리 수준이 다르므로 일부 실험에서 보이는 값이 달라질 수 있다. 그런 곳은 그때마다 짚는다. 격리 수준은 세션 단위로 바꿀 수 있다. MySQL에서는 SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED로, JDBC에서는 connection.setTransactionIsolation(Connection.TRANSACTION_READ_COMMITTED)로 바꾼다. Javadoc은 트랜잭션 도중에 이 메서드를 호출했을 때의 결과는 구현에 따라 다르다고 적고 있으므로, 트랜잭션을 시작하기 전에 정해 두어야 한다.

    격리 수준 이야기가 "세션 단위로 바꾼다"로 끝난다는 점을 기억해 두자. 격리 수준, 자동 커밋 여부, 진행 중인 트랜잭션, 보유한 락은 모두 데이터베이스 서버 안의 세션 하나에 붙어 있는 상태다. 다음 절은 그 세션이 무엇인지 본다.

    데이터베이스 연결 구조와 DB 세션

    1회차에서 커넥션 하나를 얻을 때 TCP 연결이 맺어지고, 인증을 거쳐 데이터베이스 서버 안에 그 연결을 담당하는 세션이 만들어진다는 것을 보았다. 2회차에서는 그 비용 때문에 커넥션을 미리 만들어 두는 커넥션 풀을 다루었다. 이 회차에서 새로 붙일 사실은 하나다. 트랜잭션은 세션 안에서 시작되고 끝난다. 클라이언트가 커넥션으로 보낸 SQL은 그 커넥션에 대응하는 세션이 실행하고, 트랜잭션을 시작하는 것도, 커밋하는 것도, 롤백하는 것도 그 세션이다.

    MySQL 매뉴얼은 연결 관리 방식을 이렇게 설명한다. 연결 관리자 스레드가 클라이언트 연결마다 그 연결 전용 스레드를 붙여 인증과 요청 처리를 맡기고, 새 스레드를 만들기 전에 스레드 캐시에서 재사용할 스레드가 있는지 먼저 확인한다. 그리고 이 모델에서는 현재 연결된 클라이언트 수만큼 스레드가 있다고 적는다(MySQL Enterprise Edition의 스레드 풀 플러그인은 다른 모델을 쓴다). 즉 MySQL 커뮤니티 서버 기준으로 애플리케이션의 커넥션 풀이 커넥션 10개를 들고 있으면, 서버 쪽에도 세션 10개와 그 세션을 처리하는 스레드 10개가 있다. 각 세션은 서로 독립된 상태를 가진다. 세션 1이 자동 커밋을 끄고 트랜잭션을 진행 중이어도 세션 2는 자동 커밋 상태로 전혀 다른 일을 할 수 있다.

 -------------------------------------------         -----------------------------------------
 요청 스레드 T1 --빌림--> 커넥션 #1 ===== TCP =====> 세션 #1 (전용 서버 스레드)

 * 트랜잭션, 자동 커밋 여부, 격리 수준, 락은 모두 "세션"의 상태다.
 * 커넥션 #1로 보낸 SQL과 커넥션 #2로 보낸 SQL은 절대 같은 트랜잭션에 들어가지 않는다.
    애플리케이션의 커넥션 하나가 DB 서버의 세션 하나에 일대일로 대응하고, 트랜잭션과 락이 세션 안에 들어 있다는 것을 보여 준다. 왼쪽에 "애플리케이션 서버" 라벨이 붙은 큰 상자, 오른쪽에 "데이터베이스 서버" 라벨이 붙은 큰 상자를 둔다. 왼쪽 상자 안에 "요청 스레드 1", "요청 스레드 2" 아이콘이 위아래로 있고, 그 옆에 "커넥션 풀" 라벨이 붙은 둥근 상자 안에 커넥션을 뜻하는 플러그 모양 세 개가 있다. 각 플러그에서 오른쪽으로 굵은 선 세 개가 뻗어 오른쪽 상자 안의 세 칸에 닿고, 선 위에 "TCP 연결" 라벨을 한 번만 붙인다. 오른쪽 세 칸에는 각각 "세션 1", "세션 2", "세션 3" 라벨이 있다. "세션 1" 칸 안에만 작은 상자 두 개를 넣어 "트랜잭션 진행 중", "행 락 보유"라고 적는다. "세션 2" 칸 안에는 "자동 커밋"이라고 적는다. 요청 스레드 1에서 첫 번째 플러그로 점선 화살표를 그린다. 평면적인 기술 다이어그램 스타일, 흰 배경, 파랑과 회색 위주. 커넥션 하나는 DB 세션 하나다. 트랜잭션과 락은 세션에 붙어 있으므로, 같은 트랜잭션에 넣으려면 같은 커넥션으로 SQL을 보내야 한다.

    이 구조에서 바로 나오는 결론이 있다. 출금과 입금을 한 트랜잭션으로 묶으려면 두 SQL을 같은 커넥션으로 보내야 한다. 출금 메서드가 풀에서 커넥션을 하나 빌려 쓰고 반납하고, 입금 메서드가 다시 커넥션을 빌린다면, 두 번째로 빌린 커넥션이 우연히 같은 물리 커넥션일 수는 있어도 첫 번째 커넥션의 트랜잭션은 이미 커밋되었거나 정리된 뒤다. 앞 회차들에서 만든 저장소 코드는 메서드마다 커넥션을 얻고 닫았다. 그 코드 그대로는 트랜잭션을 걸 수 없다. 이 회차 후반부의 "트랜잭션 적용"은 결국 "같은 커넥션을 어떻게 여러 메서드가 함께 쓰게 할 것인가"의 문제다.

    세션은 눈으로 확인할 수 있다. MySQL에서는 SELECT CONNECTION_ID()로 현재 세션의 번호를, SHOW PROCESSLIST로 서버에 붙은 세션 목록을 볼 수 있다. H2에서는 SESSION_ID() 함수와 INFORMATION_SCHEMA.SESSIONS 표가 같은 역할을 한다. 아래 실험은 같은 JVM 안에서 같은 이름의 H2 메모리 데이터베이스에 커넥션 두 개를 연다. H2의 jdbc:h2:mem:이름 URL은 같은 JVM 안에서 그 이름으로 하나의 데이터베이스를 공유하고, DB_CLOSE_DELAY=-1은 마지막 커넥션이 닫혀도 데이터베이스를 지우지 않게 한다. 커넥션 두 개는 서로 다른 두 세션이고, 이 회차에서는 이 둘을 각각 세션1(s1), 세션2(s2)라고 부르며 동시에 접근하는 두 사용자를 흉내 낸다.

    import java.sql.*;
import java.util.concurrent.*;

public class Exp {
    static final String URL = "jdbc:h2:mem:bank;DB_CLOSE_DELAY=-1";

    static int balance(Connection c, String id) throws SQLException {
        try (PreparedStatement ps = c.prepareStatement("select balance from account where id = ?")) {
            ps.setString(1, id);
            try (ResultSet rs = ps.executeQuery()) { rs.next(); return rs.getInt(1); }
        }
    }
    static void exec(Connection c, String sql) throws SQLException {
        try (Statement st = c.createStatement()) { st.execute(sql); }
    }
    static Object one(Connection c, String sql) throws SQLException {
        try (Statement st = c.createStatement(); ResultSet rs = st.executeQuery(sql)) { rs.next(); return rs.getObject(1); }
    }

    public static void main(String[] args) throws Exception {
        try (Connection c = DriverManager.getConnection(URL, "sa", "")) {
            exec(c, "create table account(id varchar(10) primary key, balance int not null)");
            exec(c, "insert into account values ('A', 10000), ('B', 10000)");
        }
        Connection s1 = DriverManager.getConnection(URL, "sa", "");
        Connection s2 = DriverManager.getConnection(URL, "sa", "");
        System.out.println("== A: sessions");
        System.out.println("s1 session=" + one(s1, "select session_id()") + " autoCommit=" + s1.getAutoCommit() + " iso=" + s1.getTransactionIsolation());
        System.out.println("s2 session=" + one(s2, "select session_id()") + " autoCommit=" + s2.getAutoCommit() + " iso=" + s2.getTransactionIsolation());
        // ... 이어지는 실험은 아래 절에서 차례로 본다
    }
}
    == A: sessions
s1 session=4 autoCommit=true iso=2
s2 session=5 autoCommit=true iso=2

    세션 번호는 서버가 붙이는 식별자이므로 구체적인 숫자는 환경과 실행 순서에 따라 달라질 수 있다. 중요한 것은 두 커넥션이 서로 다른 번호를 받았다는 것, 그리고 둘 다 새로 만든 직후에 autoCommit=true라는 것이다. 마지막 값 2는 Connection.TRANSACTION_READ_COMMITTED의 값으로, 앞에서 말한 H2의 기본 격리 수준이다. 이제 이 두 세션으로 트랜잭션을 관찰한다.

    자동 커밋과 수동 커밋

    트랜잭션을 명시적으로 시작하지 않고 SQL을 보내면 어떻게 될까. MySQL 매뉴얼은 MySQL이 기본적으로 자동 커밋(autocommit) 모드로 실행되며, 트랜잭션 안에 있지 않을 때 각 문장은 START TRANSACTION과 COMMIT으로 감싼 것처럼 원자적이라고 설명한다. 그래서 자동 커밋 모드에서 실행한 UPDATE는 끝나는 즉시 확정되고 ROLLBACK으로 되돌릴 수 없다. 다만 문장 하나가 실행 도중 오류를 내면 그 문장 자체는 롤백된다. 문장 단위의 원자성은 언제나 보장되고, 자동 커밋은 그 "문장 하나"를 곧 "트랜잭션 하나"로 만드는 모드다.

    JDBC도 같은 기본값을 택했다. Connection Javadoc의 첫머리는 커넥션이 기본적으로 자동 커밋 모드이며 각 문장을 실행한 뒤 자동으로 커밋한다고 적고, 자동 커밋을 끄면 commit을 명시적으로 호출해야 변경이 저장된다고 덧붙인다. 앞 실험에서 새 커넥션 두 개가 모두 autoCommit=true였던 이유다. Javadoc은 자동 커밋에서 "문장이 끝나는 시점"도 정의한다. INSERT·UPDATE·DELETE 같은 DML과 DDL은 실행이 끝나는 즉시, SELECT는 그 결과 집합(ResultSet)을 닫을 때 끝난 것으로 본다.

    여러 문장을 묶으려면 자동 커밋을 꺼야 한다. MySQL에서는 두 가지 방법이 있다.

    -- 방법 1: 한 묶음에 대해서만 자동 커밋을 끈다
START TRANSACTION;          -- BEGIN, BEGIN WORK 도 같은 뜻
UPDATE account SET balance = balance - 3000 WHERE id = 'A';
UPDATE account SET balance = balance + 3000 WHERE id = 'B';
COMMIT;                     -- 이후 자동 커밋 모드로 돌아간다

-- 방법 2: 세션의 기본 모드를 수동 커밋으로 바꾼다
SET autocommit = 0;
UPDATE account SET balance = balance - 3000 WHERE id = 'A';
UPDATE account SET balance = balance + 3000 WHERE id = 'B';
COMMIT;                     -- 다음 문장부터는 다시 새 트랜잭션 안이다

    MySQL 매뉴얼에 따르면 START TRANSACTION을 쓰면 COMMIT이나 ROLLBACK으로 트랜잭션을 끝낼 때까지 자동 커밋이 꺼져 있다가, 끝나면 이전 상태로 돌아간다. BEGIN과 BEGIN WORK는 그 별칭이지만, 매뉴얼은 표준 SQL 구문인 START TRANSACTION을 권장한다. 반면 SET autocommit = 0은 그 세션의 기본 모드 자체를 바꾸므로, 커밋한 뒤에도 수동 커밋 상태가 유지된다. 커밋하거나 롤백하지 않는 한 변경은 확정되지 않는다.

    트랜잭션을 끝내는 숨은 방법들: 암묵적 커밋

    트랜잭션은 COMMIT과 ROLLBACK으로만 끝나는 것이 아니다. MySQL 매뉴얼의 "Statements That Cause an Implicit Commit" 절은 실행 전에 현재 세션의 트랜잭션을 COMMIT한 것처럼 끝내 버리는 문장들을 나열한다. 대표적인 것이 CREATE TABLE, ALTER TABLE, DROP TABLE, TRUNCATE TABLE 같은 DDL이다. 트랜잭션 제어 문장도 그렇다. 트랜잭션 도중 START TRANSACTION이나 BEGIN을 다시 실행하면 진행 중이던 트랜잭션이 커밋되고, 자동 커밋이 꺼진 상태에서 SET autocommit = 1을 실행해도(이미 1이 아니라면) 커밋된다. 매뉴얼은 트랜잭션이 중첩될 수 없는 이유가 바로 이 암묵적 커밋 때문이라고 설명한다. MySQL 8.4.13과 8.0.46에서 두 경우를 실행해 보면, 커밋 없이 SET autocommit = 1을 실행한 직후에도, 트랜잭션 도중 START TRANSACTION을 다시 실행한 직후에도 다른 세션이 바뀐 값을 바로 읽었고, 그 뒤의 ROLLBACK은 이미 커밋된 변경을 되돌리지 못했다.

    JDBC에도 같은 규칙이 있다. setAutoCommit Javadoc의 주석은 트랜잭션 도중에 이 메서드가 호출되어 자동 커밋 모드가 바뀌면 그 트랜잭션이 커밋된다고 적는다. 모드가 바뀌지 않으면 아무 일도 하지 않는다. "롤백하려고 했는데 자동 커밋을 다시 켜는 바람에 커밋되어 버렸다"는 사고는 이 규칙에서 나온다. 실험으로 확인해 보자. 세션1에서 자동 커밋을 끈 채로 B를 7,777로 바꾸고, 커밋 대신 setAutoCommit(true)를 호출한 뒤 세션2에서 읽는다. 아래 코드는 실험 프로그램에서는 락 실험들이 끝난 뒤, 세션1이 이미 setAutoCommit(false) 상태이고 진행 중인 트랜잭션이 없을 때 실행된다. 설명 순서상 여기에 먼저 싣는다.

    System.out.println("== F: autocommit toggle commits");
exec(s1, "update account set balance = 7777 where id = 'B'");   // s1은 이미 수동 커밋 모드
s1.setAutoCommit(true);                                          // commit()을 부르지 않았다
System.out.println("after setAutoCommit(true) s2 sees B=" + balance(s2, "B"));
try { s1.commit(); System.out.println("commit in autocommit: no exception"); }
catch (SQLException e) { System.out.println("commit in autocommit: " + e.getMessage()); }
    == F: autocommit toggle commits
after setAutoCommit(true) s2 sees B=7777
commit in autocommit: no exception

    세션2가 7,777을 읽었으므로 setAutoCommit(true)가 커밋을 일으킨 것이 확인된다. 두 번째 줄은 다른 이야기를 한다. Javadoc은 commit()과 rollback()이 자동 커밋 모드의 커넥션에서 호출되면 SQLException을 던진다고 명시하지만, H2 2.4.240은 예외 없이 넘어갔다. 표준 문서가 정한 동작과 드라이버의 실제 동작이 다를 수 있다는 좋은 예다. 이 차이에 기대는 코드, 예를 들어 "자동 커밋이든 아니든 일단 rollback()을 부른다"는 코드는 드라이버를 바꾸는 순간 예외를 만날 수 있다. 커밋과 롤백은 자동 커밋을 끈 커넥션에서만 호출한다고 정해 두는 것이 안전하다.

    이 절의 핵심

    자동 커밋은 "문장 하나 = 트랜잭션 하나"인 모드이고, 새 커넥션은 MySQL과 JDBC 모두 이 모드로 시작한다. 여러 문장을 묶으려면 세션의 자동 커밋을 끄고(setAutoCommit(false)), 같은 커넥션으로 문장을 보낸 다음 commit()이나 rollback()으로 끝낸다. DDL, 트랜잭션 재시작, 자동 커밋 다시 켜기는 진행 중인 트랜잭션을 조용히 커밋한다.

    트랜잭션 실습: 커밋 전의 데이터는 누구에게 보이는가

    이제 두 세션으로 커밋 전후의 차이를 본다. 세션1이 자동 커밋을 끄고 A의 잔액을 9,000으로 바꾼다. 아직 커밋하지 않은 상태에서 세션1 자신과 세션2가 각각 A를 읽고, 그다음 세션1이 커밋한 뒤 세션2가 다시 읽는다.

    s1.setAutoCommit(false);                                          // 세션1: 수동 커밋 모드
exec(s1, "update account set balance = 9000 where id = 'A'");    // 아직 커밋 전
System.out.println("s1 sees A=" + balance(s1, "A"));
System.out.println("s2 sees A=" + balance(s2, "A"));
s1.commit();
System.out.println("after commit s2 sees A=" + balance(s2, "A"));
    s1 sees A=9000
s2 sees A=10000
after commit s2 sees A=9000

    세 줄을 차례로 읽어 보자. 첫 줄에서 세션1은 자기가 바꾼 값 9,000을 본다. 트랜잭션은 자기 자신의 커밋 전 변경은 볼 수 있다. 둘째 줄에서 세션2는 여전히 10,000을 본다. 세션2의 격리 수준은 READ COMMITTED이므로 커밋되지 않은 변경, 즉 더티 데이터를 읽지 않는다. 이때 세션2의 SELECT는 기다리지도 않았다는 점이 중요하다. 세션1이 A 행을 바꾸는 중이지만 세션2는 바로 응답을 받았다. 커밋된 마지막 버전을 읽었기 때문이다. 셋째 줄에서 세션1이 커밋하자 세션2도 9,000을 본다.

    같은 실험을 MySQL InnoDB에서 하면 세션2의 격리 수준이 기본값 REPEATABLE READ라는 점이 결과에 영향을 줄 수 있다. 세션2가 자동 커밋 모드라면 SELECT 하나가 곧 트랜잭션 하나이므로 매번 새 스냅샷으로 읽고, 결과는 H2와 같다. 그런데 세션2도 자동 커밋을 끄고 세션1이 커밋하기 전에 이미 한 번 A를 읽었다면, 세션1이 커밋한 뒤에 다시 읽어도 InnoDB는 첫 읽기 때 만든 스냅샷을 보여 주므로 10,000이 나온다. 매뉴얼의 표현대로 현재 트랜잭션을 커밋한 뒤 새로 조회하면 더 새로운 스냅샷을 얻는다. "커밋했는데 다른 세션에서 안 보인다"는 질문의 상당수가 이 경우다.

    이 흐름을 MySQL 콘솔 두 개로 재현하면 다음과 같다. 두 터미널에서 각각 접속해 왼쪽 번호 순서대로 실행하는 장면을 하나의 목록으로 적었다. 주석의 값은 MySQL 8.4.13과 8.0.46에서 이 순서대로 실행해 얻은 것이고, 두 버전의 결과가 같았다.

    -- (1) 세션1
SET autocommit = 0;
UPDATE account SET balance = 9000 WHERE id = 'A';

-- (2) 세션2 (자동 커밋 모드)
SELECT balance FROM account WHERE id = 'A';   -- 10000: 커밋 전 변경은 보이지 않는다

-- (3) 세션1
COMMIT;

-- (4) 세션2
SELECT balance FROM account WHERE id = 'A';   -- 9000: 새 문장 = 새 트랜잭션 = 새 스냅샷

    롤백도 확인해 두자. (3)에서 COMMIT 대신 ROLLBACK을 실행하면, 세션1의 변경은 언두 로그를 써서 되돌려지고 (4)에서 세션2는 여전히 10,000을 본다. 세션1 자신도 롤백 이후에는 10,000을 본다. 트랜잭션 안에서 아무리 많은 행을 바꿨어도 롤백 한 번이면 모두 되돌아간다. 데이터베이스가 시작 이전 상태를 기억하고 있기 때문에 가능한 일이다.

    계좌이체로 보는 원자성: 자동 커밋과 트랜잭션의 차이

    이제 이 회차의 첫 질문으로 돌아간다. 입금 계좌가 존재하지 않는 이체를 두 방식으로 실행해 보자. 출금은 성공하고 입금은 대상 행이 없어 0행이 바뀐다. SQL 자체는 오류가 아니므로, 애플리케이션이 "바뀐 행 수가 1이 아니면 실패"라고 판단해야 한다.

    -- 자동 커밋 모드(기본값)에서 이체
UPDATE account SET balance = balance - 3000 WHERE id = 'A';   -- 1 row affected, 즉시 확정
UPDATE account SET balance = balance + 3000 WHERE id = 'X';   -- 0 rows affected
-- 애플리케이션이 실패를 감지해도 첫 문장은 이미 커밋되었다 → A만 3000 줄어든 상태

-- 트랜잭션 안에서 이체
START TRANSACTION;
UPDATE account SET balance = balance - 3000 WHERE id = 'A';   -- 1 row affected, 미확정
UPDATE account SET balance = balance + 3000 WHERE id = 'X';   -- 0 rows affected
ROLLBACK;                                                      -- 출금까지 함께 취소된다

    자동 커밋 모드에서는 첫 문장이 끝나는 순간 커밋되므로, 두 번째 문장에서 실패를 알아도 되돌릴 수단이 없다. 트랜잭션 안에서는 두 번째 문장의 결과를 본 뒤에 커밋할지 롤백할지 결정할 수 있다. 원자성은 결국 "결정을 미룰 수 있는 능력"이다. 모든 단계가 성공했는지 확인한 뒤에 한 번에 확정한다.

    이 예제에는 하나 더 볼 점이 있다. 출금 SQL을 balance = balance - 3000처럼 현재 값을 기준으로 계산하도록 썼다. 애플리케이션이 잔액을 먼저 읽어 와서 자바 코드로 뺀 결과를 balance = 7000처럼 써 넣는 방식과는 동시성 측면에서 성질이 다르다. 그 차이는 락을 다룬 뒤 "갱신 손실" 절에서 실험으로 확인한다. 트랜잭션이 원자성을 주어도, 동시에 실행되는 다른 트랜잭션과의 관계는 격리 수준과 락이 정한다.

    DB 락 개념: 같은 행을 두 세션이 바꾸려 할 때

    지금까지는 한 세션만 쓰기를 했다. 이번에는 세션1이 A의 잔액을 8,000으로 바꾸고 아직 커밋하지 않은 상태에서, 세션2가 같은 A의 잔액을 500으로 바꾸려 한다고 하자. 데이터베이스가 세션2의 변경을 그냥 허용하면 무슨 일이 생길까. 세션1이 나중에 롤백하면 A는 세션1이 바꾸기 전 값으로 돌아가야 하는데, 그 사이에 세션2가 덮어쓴 500은 어떻게 처리해야 하는가. 세션1의 롤백이 세션2의 변경까지 지워 버리면 세션2의 커밋은 거짓말이 되고, 세션2의 값을 남기면 세션1의 롤백이 불완전해진다. 어느 쪽이든 원자성이 깨진다.

    그래서 데이터베이스는 커밋되지 않은 변경이 있는 행을 다른 트랜잭션이 바꾸지 못하게 막는다. 이 장치가 락(lock)이다. 세션1이 A 행을 바꾸는 순간 그 행에 대한 배타적 락을 얻고, 세션2는 같은 행을 바꾸려면 같은 락을 얻어야 하므로 기다린다. 세션1이 커밋하거나 롤백해서 트랜잭션이 끝나면 락이 풀리고, 기다리던 세션2가 락을 얻어 자기 변경을 진행한다. 락은 문장이 끝날 때가 아니라 트랜잭션이 끝날 때 풀린다는 점이 핵심이다. 자동 커밋 모드에서는 문장 하나가 곧 트랜잭션이므로 락도 그 문장 동안만 잡혀 있다가 바로 풀리지만, 수동 커밋 모드에서는 커밋할 때까지 계속 잡혀 있다.

    락에는 두 가지 모드가 있다. 공유 락(shared lock, S)은 "읽고 있으니 바꾸지 마라"는 뜻이고, 배타 락(exclusive lock, X)은 "바꾸고 있으니 아무도 건드리지 마라"는 뜻이다. 공유 락끼리는 함께 걸릴 수 있지만, 배타 락은 다른 어떤 락과도 함께 걸릴 수 없다.

    이미 걸린 락 \ 새로 요청한 락공유 락(S)배타 락(X)
    공유 락(S)함께 걸림대기
    배타 락(X)대기대기

    MySQL InnoDB에서 UPDATE와 DELETE, 그리고 뒤에서 볼 SELECT ... FOR UPDATE는 배타 락을, SELECT ... FOR SHARE는 공유 락을 건다. InnoDB의 행 락에는 주의할 성질이 하나 있다. 락은 "행"이라는 추상적인 대상이 아니라 인덱스 레코드에 걸린다. 매뉴얼은 잠금 읽기, UPDATE, DELETE가 SQL을 처리하면서 스캔한 모든 인덱스 레코드에 대개 레코드 락을 걸며, WHERE 조건에서 걸러질 행인지와 상관없이 그렇다고 설명한다. InnoDB는 정확한 WHERE 조건을 기억하는 것이 아니라 어떤 인덱스 범위를 스캔했는지만 안다. 그래서 적절한 인덱스가 없어 테이블 전체를 스캔해야 하는 문장은 테이블의 모든 행을 잠그고, 다른 사용자의 삽입까지 막는다(기본 격리 수준 REPEATABLE READ 기준. 매뉴얼에 따르면 READ COMMITTED에서는 UPDATE·DELETE가 WHERE 조건을 평가한 뒤 조건에 맞지 않는 행의 레코드 락을 푼다).

    반대로 기본 키처럼 유일한 인덱스로 유일한 행을 찾는 경우에는 그 인덱스 레코드 하나만 잠근다. 매뉴얼은 UPDATE ... WHERE ...가 탐색 중 만나는 모든 레코드에 배타적 넥스트 키 락(next-key lock)을 걸지만, 유일 인덱스로 유일한 행을 찾는 문장에는 인덱스 레코드 락만 필요하다고 적는다. 넥스트 키 락은 레코드와 그 앞의 간격(gap)을 함께 잠가 그 사이로 새 행이 삽입되는 것을 막는 락이다. REPEATABLE READ에서 범위 조건으로 잠금 읽기를 하면 이런 간격 락이 쓰이고, READ COMMITTED에서는 외래 키 검사와 중복 키 검사 때를 제외하면 간격 락을 쓰지 않는다. 이 회차의 예제는 모두 기본 키로 한 행을 찾으므로 레코드 하나만 잠긴다고 보면 된다. 인덱스와 간격 락의 자세한 동작은 데이터베이스 기본편의 저장 엔진 이야기와 이어지는 주제다.

    기다림의 끝: 락 대기 시간 초과와 교착 상태

    락을 기다리는 세션이 영원히 기다리지는 않는다. InnoDB에서 그 한도는 시스템 변수 innodb_lock_wait_timeout이 정하고, 기본값은 50초다. 매뉴얼에 따르면 다른 InnoDB 트랜잭션이 잠근 행에 접근하려는 트랜잭션은 쓰기 접근을 최대 이 시간만큼 기다린 뒤 다음 오류를 낸다.

    ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction

    여기서 많이 오해하는 지점이 있다. 시간 초과가 나면 무엇이 롤백되는가. InnoDB의 오류 처리 문서는 락 대기 시간 초과가 현재 문장, 즉 락을 기다리다 시간 초과를 만난 그 문장만 롤백한다고 설명한다. 트랜잭션 전체를 롤백하게 하려면 서버를 --innodb-rollback-on-timeout 옵션으로 띄워야 한다. 기본 설정에서는 시간 초과 뒤에도 트랜잭션이 열려 있고, 그 트랜잭션이 앞서 바꾼 행과 잡고 있는 락도 그대로 남는다. 따라서 애플리케이션이 오류를 받은 뒤 명시적으로 rollback()을 호출해야 트랜잭션이 정리된다. 예외를 잡아서 로그만 찍고 커넥션을 계속 쓰면 앞선 변경이 반쯤 남은 트랜잭션 위에서 다음 작업을 하게 된다. MySQL 8.4.13과 8.0.46에서 세션의 innodb_lock_wait_timeout을 2초로 줄여 확인해 보았다. 트랜잭션 안에서 B를 바꾼 뒤 다른 세션이 잠근 A를 바꾸려다 오류 1205를 받았는데, 그 뒤에도 같은 세션에서 B는 바뀐 값으로 보였고 information_schema.innodb_trx에는 그 트랜잭션이 trx_state=RUNNING, trx_rows_modified=1로 남아 있었다. 명시적으로 ROLLBACK을 실행한 뒤에야 B가 원래 값으로 돌아왔다.

    교착 상태(deadlock)는 다르게 처리된다. 트랜잭션 1이 A를 잠그고 B를 기다리는데 트랜잭션 2가 B를 잠그고 A를 기다리면, 둘 다 영원히 기다리게 된다. InnoDB는 교착 상태 탐지가 켜져 있을 때(기본값) 이를 자동으로 탐지하고, 교착을 풀기 위해 트랜잭션 하나 이상을 롤백한다. 매뉴얼은 InnoDB가 작은 트랜잭션을 골라 롤백하려 하며, 크기는 삽입·수정·삭제한 행 수로 정한다고 적는다. 오류 처리 문서에 따르면 이때는 문장이 아니라 트랜잭션 전체가 롤백되므로, 애플리케이션은 트랜잭션 전체를 처음부터 다시 시도해야 한다. 이체에서 교착 상태가 생기는 전형적인 장면은 A에서 B로, B에서 A로 보내는 두 이체가 동시에 실행되는 경우다. H2에서 이 상황을 재현해 보면 두 번째 세션이 상대의 락을 요청하는 즉시 다음 오류를 받는다.

    s2 40001 40001 Deadlock detected. The current transaction was rolled back. Details: "ACCOUNT"; SQL statement:
s1 ok

    같은 장면을 MySQL에서 SQL 두 세션으로 재현했다. 세션1이 A를, 세션2가 B를 출금한 뒤 세션1이 B에 입금하려고 기다리는 동안 세션2가 A에 입금하려 하자, 세션2가 곧바로 다음 오류를 받았다. 오류 직후 information_schema.innodb_trx에서 세션2의 트랜잭션은 사라져 있었고, 세션2가 먼저 실행한 B 출금도 남지 않았다.

    ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

    H2와 MySQL 모두 세션2의 트랜잭션이 롤백되어 락이 풀리자, B를 기다리던 세션1은 그대로 진행해 성공했다. 교착 상태를 줄이는 가장 단순한 방법은 모든 트랜잭션이 같은 순서로 락을 잡게 하는 것이다. 이체라면 출금 계좌와 입금 계좌 중 식별자가 작은 쪽을 먼저 갱신하도록 순서를 고정하면, 두 이체가 서로의 락을 엇갈려 기다리는 순환이 생기지 않는다.

    DB 락 실습 1: 변경과 변경이 부딪힐 때

    이제 실험으로 확인하자. 세션2의 락 대기 한도를 2초로 줄여 두고(H2의 SET LOCK_TIMEOUT은 밀리초 단위다), 세션1이 커밋하지 않은 A 행을 세션2가 바꾸려 한다. 이 실험은 앞 절 "트랜잭션 실습"의 코드에 이어서 실행되므로 실험 직전 A는 9,000이다.

    System.out.println("== B: lock wait timeout");
exec(s2, "SET LOCK_TIMEOUT 2000");                               // 세션2: 락을 최대 2초 기다린다
exec(s1, "update account set balance = 8000 where id = 'A'");   // 세션1: A 행 락 획득, 커밋 안 함
long t0 = System.nanoTime();
try {
    exec(s2, "update account set balance = 500 where id = 'A'"); // 세션2: 같은 행 → 대기
    System.out.println("s2 update done?");
} catch (SQLException e) {
    System.out.println("s2 failed after ~" + Math.round((System.nanoTime() - t0) / 1e9) + "s");
    System.out.println("  message=" + e.getMessage());
    System.out.println("  SQLState=" + e.getSQLState() + " errorCode=" + e.getErrorCode() + " class=" + e.getClass().getName());
}
System.out.println("s2 can still read A=" + balance(s2, "A"));
s1.rollback();

    세션2의 UPDATE는 약 2초 동안 멈춰 있다가 시간 초과 예외로 끝났다(경과 시간은 반올림한 값이고 실행마다 조금씩 다르다). 오류는 H2 고유의 오류 코드 50200과 SQLState HYT00으로 왔다. MySQL 8.4.13과 8.0.46에서 같은 상황을 SQL로 만들면 앞에서 본 오류 1205가 온다. 같은 "락 대기 시간 초과"라도 데이터베이스마다 오류 코드가 다르다는 점은 5회차와 6회차에서 예외를 다룰 때 다시 문제가 된다. 스프링이 이런 벤더별 코드를 공통 예외로 바꿔 주는 이유가 여기에 있다.

    H2의 메시지에는 "lock table"이라고 쓰여 있지만, 테이블 전체가 잠긴 것은 아니다. 별도 실험에서 세션1이 A 행을 잠근 상태로 세션2가 B 행을 바꾸자 바로 성공했다. 잠긴 것은 A 행뿐이다. 세션2가 A를 읽는 것도 막히지 않았다. 세션2는 커밋된 마지막 값 9,000을 즉시 읽었다. 쓰기 락은 다른 쓰기를 막을 뿐, 다중 버전을 쓰는 일반 SELECT는 막지 않는다. 마지막으로 세션1이 롤백하자 A는 8,000으로 바뀌기 전 값인 9,000에 머물렀다.

    이번에는 대기 한도를 넉넉히 두고, 세션2가 기다리는 동안 세션1이 커밋하는 경우를 보자. 세션2의 UPDATE는 별도 스레드에서 실행한다. 같은 스레드에서 실행하면 세션2가 대기하는 동안 세션1의 커밋을 호출할 수 없기 때문이다.

    System.out.println("== C: wait then proceed");
ExecutorService ex = Executors.newSingleThreadExecutor();
exec(s2, "SET LOCK_TIMEOUT 10000");
exec(s1, "update account set balance = 8000 where id = 'A'");   // 세션1: 락 보유
Future f = ex.submit(() -> { exec(s2, "update account set balance = balance - 500 where id = 'A'"); return null; });
Thread.sleep(500);
System.out.println("s2 finished before s1 commit? " + f.isDone());
s1.commit();                                                      // 락 해제 → 세션2 진행
f.get();
System.out.println("final A=" + balance(s1, "A"));

final A=7500

    0.5초가 지나도 세션2는 끝나지 않았다. 락을 기다리고 있었기 때문이다. 세션1이 커밋하자 세션2가 락을 얻어 실행을 마쳤고, 최종 값은 7,500이다. 세션2의 문장이 balance - 500이었으므로, 세션2는 기다리기 시작할 때의 9,000이 아니라 세션1이 커밋한 8,000을 기준으로 계산했다. 락을 얻은 뒤의 쓰기는 최신 커밋 값을 대상으로 한다. MySQL InnoDB도 같다. 매뉴얼은 REPEATABLE READ에서도 스냅샷은 SELECT 문에 적용되는 것이고 DML 문에 반드시 적용되는 것은 아니며, 다른 트랜잭션이 막 커밋한 행을 UPDATE나 DELETE가 건드릴 수 있다고 설명한다.

    세션1이 행 락을 잡은 동안 세션2의 UPDATE가 멈춰 있다가, 세션1의 커밋으로 락이 풀리는 순간 진행되는 시간 순서를 보여 준다. 세로 생명선 세 개를 왼쪽부터 "세션1", "DB의 A 행", "세션2" 라벨로 그린다. 위에서 아래로 시간이 흐른다. 세션1에서 가운데로 화살표 "UPDATE A (락 획득)"를 긋고, 가운데 생명선 옆에 이 지점부터 아래로 길쭉한 주황색 막대를 붙여 "배타 락 보유" 라벨을 단다. 세션2에서 가운데로 화살표 "UPDATE A"를 긋고, 세션2 생명선에 회색 점선 구간과 "대기" 라벨을 붙인다. 세션1에서 가운데로 화살표 "COMMIT"을 그으면 주황색 막대가 끝나고, 바로 이어서 가운데에서 세션2로 "락 획득, 실행"이라는 화살표가 나간다. 오른쪽 여백에 작은 메모 상자로 "기다림이 50초를 넘으면 오류 1205"를 적는다. 깔끔한 UML 시퀀스 다이어그램 스타일, 흰 배경. 세션2의 UPDATE는 세션1의 트랜잭션이 끝날 때까지 기다린다. 락은 문장이 아니라 트랜잭션이 끝날 때 풀린다.

    누가 누구를 기다리는지 보기

    운영 중인 데이터베이스에서 요청이 멈췄을 때 가장 먼저 확인할 것은 "누가 누구를 막고 있는가"다. H2에서는 INFORMATION_SCHEMA.SESSIONS 표가 이를 보여 준다. 세션1이 A 행을 잠근 상태에서 세션2의 UPDATE를 별도 스레드로 실행해 대기하게 만들고, 세 번째 커넥션으로 이 표를 조회했다.

    // 세션1(s1): 수동 커밋, A 행 갱신 후 커밋하지 않음
// 세션2(s2): 별도 스레드에서 같은 행 갱신 → 대기 중
Future f = ex.submit(() -> { exec(s2, "update account set balance = 1 where id = 'A'"); return null; });
Thread.sleep(500);
try (Statement st = mon.createStatement(); ResultSet rs = st.executeQuery(
        "select * from information_schema.sessions order by session_id")) {
    // ... 모든 열을 출력
}
    SESSION_ID | EXECUTING_STATEMENT                                            | CONTAINS_UNCOMMITTED | SESSION_STATE | BLOCKER_ID
4          | null                                                           | true                 | SLEEP         | null
5          | update account set balance = 1 where id = 'A'                  | false                | BLOCKED       | 4
6          | select * from information_schema.sessions order by session_id | false                | RUNNING       | null

    세션 4는 지금 실행 중인 문장이 없지만(SLEEP) 커밋하지 않은 변경을 갖고 있다(CONTAINS_UNCOMMITTED=true). 세션 5는 UPDATE를 실행하다 막혀 있고(BLOCKED), 막고 있는 세션이 4라고 알려 준다. 실무에서 자주 보는 장면이 바로 이것이다. 막고 있는 쪽은 아무것도 실행하지 않고 놀고 있는 세션이다. 애플리케이션이 트랜잭션을 열어 행을 바꾼 뒤 커밋하지 않은 채 다른 일(외부 API 호출, 사용자 입력 대기, 혹은 단순한 버그)을 하고 있으면, 서버 입장에서는 한가한 세션이 락을 쥐고 있는 것처럼 보인다.

    MySQL 8.0에서는 Performance Schema의 data_locks 표가 보유 중이거나 요청 중인 데이터 락을 보여 주고, data_lock_waits 표가 어떤 락 요청이 어떤 보유 락에 막혀 있는지를 보여 준다. data_locks의 LOCK_TYPE은 InnoDB에서 행 락이면 RECORD, 테이블 락이면 TABLE이고, LOCK_MODE에는 S, X, IS, IX 같은 값과 간격 락을 뜻하는 ,GAP, 간격 없이 레코드만 잠근 락을 뜻하는 ,REC_NOT_GAP 같은 접미사가 붙을 수 있으며, LOCK_STATUS는 보유 중이면 GRANTED, 기다리는 중이면 WAITING이다. LOCK_DATA에는 행 락이 기본 키 인덱스에 걸린 경우 잠긴 레코드의 기본 키 값이 나온다(보조 인덱스에 걸린 락이면 보조 인덱스 값 뒤에 기본 키 값이 붙는다). 행에 배타 락을 거는 트랜잭션은 테이블에도 IX 같은 의도 락(intention lock)을 함께 걸기 때문에, 한 행만 바꿔도 TABLE 행과 RECORD 행이 함께 보인다.

    -- MySQL 8.0: 현재 잡혀 있거나 기다리는 락
SELECT ENGINE_TRANSACTION_ID, OBJECT_NAME, INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_STATUS, LOCK_DATA
FROM performance_schema.data_locks;

-- 어떤 요청이 어떤 락에 막혀 있는가
SELECT * FROM performance_schema.data_lock_waits;

    앞의 H2 실험과 비슷한 장면을 MySQL에서 만들고 첫 번째 쿼리를 실행했다. 세션1이 A를, 세션2가 B를 바꾼 채 커밋하지 않았고, 세션2가 이어서 A를 바꾸려다 기다리는 중이다. 같은 서버를 다른 작업도 쓰고 있어서 이 실험의 테이블에 걸린 락만 골라 ENGINE_TRANSACTION_ID 순으로 정렬했고, 값이 실행마다 달라지는 ENGINE_TRANSACTION_ID 열은 출력에서 뺐다.

    위 두 줄이 세션1, 아래 세 줄이 세션2의 락이다. 두 세션 모두 테이블에 IX 의도 락을 걸었고, 기본 키로 한 행을 찾았으므로 행 락은 간격 없이 레코드만 잠그는 X,REC_NOT_GAP이다. 세션2의 마지막 줄은 이미 세션1이 보유한 A 레코드의 락을 요청해 WAITING 상태로 기다리는 중이다.

    DB 락 실습 2: 조회할 때 락을 거는 이유

    일반 SELECT는 락을 걸지 않는다. InnoDB 매뉴얼은 SELECT ... FROM이 일관된 읽기로서 데이터베이스의 스냅샷을 읽고, 격리 수준이 SERIALIZABLE이 아니라면 아무 락도 걸지 않는다고 설명한다. 앞의 실험에서 세션2가 잠긴 A를 기다리지 않고 읽은 것도 이 때문이다. 그렇다면 조회할 때 락을 걸어야 하는 경우는 언제일까. 읽은 값을 근거로 쓰기를 할 때다.

    잔액을 읽어서 자바 코드로 계산한 뒤 그 결과를 써 넣는 코드를 생각해 보자. 두 세션이 동시에 A에서 1,000을 출금한다. 두 세션 모두 10,000을 읽고, 각자 9,000을 계산해 써 넣는다. 두 번 출금했는데 잔액은 1,000만 줄었다. 한쪽의 변경이 다른 쪽에 덮여 사라졌으므로 이를 갱신 손실(lost update)이라고 부른다. 락이 있는데도 이런 일이 생기는 이유는, 두 세션의 UPDATE가 차례로 실행되기는 했지만(쓰기 락 덕분에) 그 UPDATE에 들어간 값이 이미 낡은 읽기에서 나왔기 때문이다. 락은 쓰기와 쓰기의 동시 실행을 막았을 뿐, 읽기와 쓰기 사이에 끼어든 변경은 막지 못했다. 실험으로 재현해 보자. 실험 코드라서 SQL을 문자열로 이어 붙였지만, 실제 코드에서는 1회차에서 본 것처럼 파라미터 바인딩을 써야 한다.

    System.out.println("== E1: lost update (read then write)");
s2.setAutoCommit(false);                       // 두 세션 모두 수동 커밋, A=10000에서 시작
int r1 = balance(s1, "A");                     // 세션1 읽기
int r2 = balance(s2, "A");                     // 세션2 읽기 (같은 값)
exec(s1, "update account set balance = " + (r1 - 1000) + " where id = 'A'"); s1.commit();
exec(s2, "update account set balance = " + (r2 - 1000) + " where id = 'A'"); s2.commit();
System.out.println("read r1=" + r1 + " r2=" + r2 + " final A=" + balance(s1, "A"));
    == E1: lost update (read then write)
read r1=10000 r2=10000 final A=9000

    두 번 출금했는데 최종 잔액은 9,000이다. 이 결과는 MySQL InnoDB의 기본 격리 수준 REPEATABLE READ에서도 같다. REPEATABLE READ는 "같은 트랜잭션 안에서 다시 읽으면 같은 값"을 보장할 뿐, 내가 읽은 뒤에 남이 바꾸지 못하게 막아 주지는 않는다. 오히려 세션2는 자기 스냅샷 때문에 세션1의 커밋 이후에도 계속 10,000을 볼 수 있다. 그리고 세션2의 UPDATE는 계산된 상수 9,000을 그대로 써 넣으므로 세션1의 출금을 지운다. MySQL 8.4.13과 8.0.46에서 같은 순서를 SQL로 재현했다(읽은 값을 사용자 변수에 담아 두었다가 UPDATE에 썼다). 세션2는 세션1이 커밋한 뒤 다시 읽어도 10,000을 보았고, 최종 잔액은 9,000이었다.

    해결책은 읽는 순간부터 그 행에 배타 락을 거는 것이다. 이것이 SELECT ... FOR UPDATE다. 매뉴얼은 FOR UPDATE가 탐색 중 만나는 인덱스 레코드에 대해 그 행들에 UPDATE를 실행한 것과 같은 락을 걸고, 다른 트랜잭션이 그 행을 갱신하거나 FOR SHARE로 읽는 것을 막는다고 설명한다. 그리고 이렇게 건 락은 트랜잭션이 커밋되거나 롤백될 때 풀린다. 같은 출금을 FOR UPDATE로 다시 실행해 보자.

    System.out.println("== E2: with for update");
exec(s1, "update account set balance = 10000 where id = 'A'"); s1.commit();   // 다시 10000에서 시작
exec(s2, "SET LOCK_TIMEOUT 10000");
int q1 = (Integer) one(s1, "select balance from account where id='A' for update");  // 세션1: 읽으며 락
Future g = ex.submit(() -> {
    int q2 = (Integer) one(s2, "select balance from account where id='A' for update"); // 세션2: 여기서 대기
    exec(s2, "update account set balance = " + (q2 - 1000) + " where id = 'A'");
    s2.commit();
    return q2;
});
Thread.sleep(500);
System.out.println("s2 done before s1 commit? " + g.isDone());
exec(s1, "update account set balance = " + (q1 - 1000) + " where id = 'A'"); s1.commit();
System.out.println("q1=" + q1 + " q2=" + g.get() + " final A=" + balance(s1, "A"));
    == E2: with for update
s2 done before s1 commit? false
q1=10000 q2=9000 final A=8000

    세션2의 SELECT ... FOR UPDATE는 세션1이 커밋할 때까지 결과를 돌려주지 않았다. 세션1이 9,000을 쓰고 커밋한 다음에야 세션2가 락을 얻었고, 그때 읽은 값은 9,000이었다. 그래서 최종 잔액은 8,000으로 정확하다. 읽기 자체가 줄을 서게 만든 것이다. 같은 순서를 MySQL 8.4.13과 8.0.46에서 FOR UPDATE로 재현해도 세션2가 읽은 값은 9,000, 최종 잔액은 8,000이었다. MySQL에서도 잠금 읽기는 스냅샷이 아니라 최신 값을 읽는다. 매뉴얼은 FOR SHARE에 대해, 읽은 행 중 커밋되지 않은 다른 트랜잭션의 변경이 있으면 그 트랜잭션이 끝날 때까지 기다렸다가 최신 값을 쓴다고 설명한다. 같은 매뉴얼은 REPEATABLE READ 트랜잭션 하나 안에서 잠금 읽기와 일반 읽기를 섞으면 서로 일관되지 않은 테이블 상태를 볼 수 있으니 섞지 말라고 권한다. 일반 SELECT는 스냅샷을, 잠금 읽기는 최신 값을 보기 때문이다.

    잠금 읽기가 일반 읽기를 막지는 않는다는 것도 확인해 두자. 세션1이 FOR UPDATE로 A를 잠근 상태에서 세션2가 일반 SELECT와 UPDATE를 차례로 실행했다. 이 코드는 실험 프로그램에서는 E1보다 먼저, 세션2가 아직 자동 커밋 모드일 때 실행된다.

    System.out.println("== D: select for update");
exec(s1, "update account set balance = 10000 where id = 'A'"); s1.commit();
exec(s2, "SET LOCK_TIMEOUT 2000");
System.out.println("s1 for update A=" + one(s1, "select balance from account where id='A' for update"));
System.out.println("s2 plain select A=" + balance(s2, "A"));     // 막히지 않는다
try {
    exec(s2, "update account set balance = 1 where id = 'A'");   // 막힌다
} catch (SQLException e) {
    System.out.println("s2 update blocked -> " + e.getErrorCode());
}
s1.commit();
    == D: select for update
s1 for update A=10000
s2 plain select A=10000
s2 update blocked -> 50200

    매뉴얼의 표현으로 일관된 읽기는 읽기 뷰에 있는 레코드에 걸린 락을 무시한다. 옛 버전은 잠글 수 없고 언두 로그를 적용해 메모리에서 재구성하는 것이기 때문이다. 즉 FOR UPDATE는 "다른 쓰기와 다른 잠금 읽기"만 막는다. 일반 SELECT로 값을 읽어 판단하는 코드가 하나라도 섞여 있으면 그 코드는 보호받지 못한다. 동시성 제어는 같은 데이터를 다루는 모든 경로가 같은 규칙을 따를 때만 동작한다.

    위쪽은 두 세션이 같은 값을 읽어 갱신 손실이 나는 타임라인, 아래쪽은 FOR UPDATE로 두 번째 읽기가 기다려 올바른 결과가 나오는 타임라인을 나란히 보여 준다. 위아래 두 개의 가로 타임라인 패널. 위 패널 제목 "일반 SELECT", 아래 패널 제목 "SELECT ... FOR UPDATE". 각 패널에는 위쪽 줄 "세션1", 아래쪽 줄 "세션2" 두 레인이 있고 시간은 왼쪽에서 오른쪽으로 흐른다. 위 패널: 세션1 레인에 "읽기 10000" 상자, 세션2 레인에 거의 같은 위치에 "읽기 10000" 상자, 이어서 세션1에 "9000 쓰기·커밋", 세션2에 "9000 쓰기·커밋" 상자. 패널 오른쪽 끝에 빨간색 결과 상자 "최종 9000"을 둔다. 아래 패널: 세션1 레인에 "읽기 10000 + 락", "9000 쓰기·커밋" 상자. 세션2 레인에는 회색 빗금 구간 "대기"가 세션1의 커밋 지점까지 이어지고, 그 뒤에 "읽기 9000 + 락", "8000 쓰기·커밋" 상자. 패널 오른쪽 끝에 초록색 결과 상자 "최종 8000". 평면적인 인포그래픽 스타일, 흰 배경. 일반 조회로 읽은 값을 근거로 쓰면 한쪽의 출금이 사라진다. FOR UPDATE는 두 번째 읽기를 첫 트랜잭션이 끝날 때까지 기다리게 한다.

    잠금 읽기의 변형과 대안

    MySQL 8.0의 잠금 읽기에는 몇 가지 변형이 있다. FOR SHARE는 읽은 행에 공유 락을 걸어 다른 세션이 읽을 수는 있지만 바꾸지는 못하게 한다. 부모 행이 존재하는 것을 확인한 뒤 자식 행을 삽입할 때처럼 "내가 확인한 사실이 커밋 전까지 바뀌지 않아야" 하는 경우에 맞다. 반면 읽은 값을 바꿀 생각이라면 FOR SHARE는 좋지 않다. 매뉴얼은 카운터 예제에서 두 사용자가 동시에 공유 락으로 카운터를 읽으면 적어도 한쪽은 카운터를 갱신하려 할 때 교착 상태에 빠진다고 지적한다. 둘 다 공유 락을 가진 상태에서 둘 다 배타 락으로 올리려 하면 서로를 기다리게 되기 때문이다. 그래서 읽고 증가시키는 작업에는 FOR UPDATE를 쓰라고 권한다.

    NOWAIT와 SKIP LOCKED는 기다리지 않는 잠금 읽기다. NOWAIT은 요청한 행이 잠겨 있으면 기다리지 않고 바로 오류를 낸다. SKIP LOCKED는 잠긴 행을 결과에서 빼고 바로 돌려준다. MySQL 8.4.13과 8.0.46에서 세션1이 FOR UPDATE로 A를 잠근 상태로 두고, 세션2에서 두 옵션을 차례로 실행했다.

    mysql> SELECT balance FROM account WHERE id = 'A' FOR UPDATE NOWAIT;
ERROR 3572 (HY000): Statement aborted because lock(s) could not be acquired immediately and NOWAIT is set.

mysql> SELECT id, balance FROM account FOR UPDATE SKIP LOCKED;
+----+---------+
| id | balance |
+----+---------+
| B  |   10000 |
+----+---------+

    NOWAIT은 기다리지 않고 오류 3572로 끝났다(이때 SHOW WARNINGS에는 저장 엔진이 보낸 Got error 203 - 'Do not wait for lock' from storage engine도 함께 남는다). SKIP LOCKED는 잠긴 A를 빼고 B 한 행만 돌려주었다. 매뉴얼은 이 결과가 데이터의 일관된 모습이 아니므로 일반적인 트랜잭션 작업에는 맞지 않고, 여러 세션이 큐처럼 쓰는 테이블에서 경합을 피하는 용도로 쓸 수 있다고 설명한다. 두 옵션 모두 행 락에만 적용된다. 마지막으로 매뉴얼은 잠금 읽기가 자동 커밋을 끈 상태(START TRANSACTION이나 autocommit=0)에서만 가능하다고 적는다. 자동 커밋 모드에서 FOR UPDATE를 쓰면 문장이 끝나는 순간 트랜잭션도 끝나므로 락이 아무것도 지켜 주지 못한다.

    갱신 손실을 막는 방법이 잠금 읽기만 있는 것은 아니다. 계산을 데이터베이스 안으로 옮기면 읽기와 쓰기 사이의 틈 자체가 사라진다. 앞의 이체 예제처럼 balance = balance - ?로 쓰면, 이 계산은 행 락을 얻은 뒤 최신 커밋 값을 대상으로 실행되므로(실험 C에서 7,500이 나온 이유) 두 출금이 모두 반영된다. 잔액이 모자라면 안 되는 조건도 WHERE id = ? AND balance >= ?처럼 같은 문장에 넣고, 바뀐 행 수가 0이면 실패로 처리할 수 있다. 다만 이 방법은 판단 로직이 SQL 한 문장에 담길 만큼 단순할 때만 쓸 수 있다. 판단이 여러 테이블을 읽고 복잡한 계산을 거쳐야 한다면 잠금 읽기로 필요한 행을 먼저 잠그는 편이 낫다. 행에 버전 번호를 두고 갱신할 때 버전이 그대로인지 확인하는 낙관적 방식도 있는데, 이는 JPA를 다루는 권에서 다시 만난다.

    트랜잭션 적용 1: 트랜잭션은 어디서 시작해야 하는가

    이제 자바 애플리케이션 코드에 트랜잭션을 적용한다. 먼저 정할 것은 트랜잭션의 경계, 즉 어디서 시작하고 어디서 끝낼지다. 데이터 접근 코드(저장소, DAO)의 메서드 하나는 SQL 하나에 대응하는 작은 단위다. "출금"과 "입금"은 각각 데이터 접근이지만, 둘을 묶어야 의미가 생기는 단위는 "이체"라는 비즈니스 로직이다. 그래서 트랜잭션은 비즈니스 로직이 있는 서비스 계층에서 시작하고 끝내야 한다. 서비스 메서드가 시작될 때 트랜잭션을 열고, 서비스 메서드가 정상 종료되면 커밋, 예외로 끝나면 롤백한다.

    그런데 앞 절에서 확인했듯 트랜잭션은 커넥션 하나에 붙어 있다. 서비스가 트랜잭션을 시작하려면 서비스가 커넥션을 얻어 setAutoCommit(false)를 호출해야 하고, 그 트랜잭션 안에서 실행될 모든 데이터 접근 메서드는 바로 그 커넥션을 써야 한다. 데이터 접근 메서드가 스스로 dataSource.getConnection()을 호출하면 다른 커넥션, 다른 세션이 되어 트랜잭션 밖에서 실행된다. 가장 직접적인 해결책은 커넥션을 메서드의 파라미터로 넘기는 것이다. 아래 데이터 접근 코드는 커넥션을 받아서 쓰기만 하고 닫지 않는다. 커넥션의 수명은 그것을 연 서비스가 책임진다.

    static class AccountDao {
    void withdraw(Connection con, String id, int amount) throws SQLException {
        String sql = "update account set balance = balance - ? where id = ? and balance >= ?";
        try (PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setInt(1, amount);
            ps.setString(2, id);
            ps.setInt(3, amount);
            if (ps.executeUpdate() != 1) {
                throw new IllegalStateException("출금 실패: 계좌가 없거나 잔액 부족 id=" + id);
            }
        }   // PreparedStatement만 닫는다. 커넥션은 닫지 않는다
    }
    void deposit(Connection con, String id, int amount) throws SQLException {
        String sql = "update account set balance = balance + ? where id = ?";
        try (PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setInt(1, amount);
            ps.setString(2, id);
            if (ps.executeUpdate() != 1) {
                throw new IllegalStateException("입금 실패: 계좌 없음 id=" + id);
            }
        }
    }
    int balance(Connection con, String id) throws SQLException {
        try (PreparedStatement ps = con.prepareStatement("select balance from account where id = ?")) {
            ps.setString(1, id);
            try (ResultSet rs = ps.executeQuery()) {
                if (!rs.next()) throw new IllegalStateException("계좌 없음 id=" + id);
                return rs.getInt(1);
            }
        }
    }
}

    출금 SQL은 잔액 조건을 WHERE에 넣은 조건부 갱신이다. 잔액이 부족하거나 계좌가 없으면 바뀐 행 수가 0이 되고, 메서드는 예외를 던진다. 입금 SQL도 바뀐 행 수가 1이 아니면 예외를 던진다. executeUpdate()의 반환값이 바뀐 행 수라는 것은 1회차에서 보았다. SQL은 오류 없이 끝났어도 비즈니스 관점에서는 실패일 수 있고, 그 판단은 애플리케이션이 해야 한다는 점이 이 코드의 요점이다.

    서비스는 트랜잭션 없이 이체하는 메서드와 트랜잭션으로 이체하는 메서드 두 개를 두어 비교한다. 데이터소스는 2회차에서 본 HikariCP다.

    static class TransferService {
    private final DataSource dataSource;
    private final AccountDao dao = new AccountDao();
    TransferService(DataSource dataSource) { this.dataSource = dataSource; }

    // 트랜잭션 없이: 문장마다 자동 커밋
    void transferNoTx(String fromId, String toId, int amount) throws SQLException {
        try (Connection con = dataSource.getConnection()) {
            dao.withdraw(con, fromId, amount);
            dao.deposit(con, toId, amount);
        }
    }

    // 하나의 커넥션 = 하나의 세션에서 수동 커밋
    void transfer(String fromId, String toId, int amount) throws SQLException {
        Connection con = dataSource.getConnection();
        try {
            con.setAutoCommit(false);            // 트랜잭션 시작
            dao.withdraw(con, fromId, amount);
            dao.deposit(con, toId, amount);
            con.commit();                        // 둘 다 성공했을 때만 반영
        } catch (SQLException | RuntimeException e) {
            con.rollback();                      // 하나라도 실패하면 전부 취소
            throw e;
        } finally {
            release(con);
        }
    }

    private void release(Connection con) {
        try {
            con.setAutoCommit(true);             // 풀에 돌려주기 전에 기본값으로
            con.close();                         // 풀 커넥션이면 실제로는 반납
        } catch (SQLException e) {
            System.out.println("커넥션 정리 실패: " + e.getMessage());
        }
    }
}

    catch (SQLException | RuntimeException e)는 다중 catch다. 잡은 예외를 그대로 다시 던지는데, 메서드 선언의 throws SQLException만으로 컴파일되는 이유는 두 타입 중 검사 예외가 SQLException뿐이기 때문이다. 이 코드를 실행하는 main은 계좌 A와 B를 각각 10,000원으로 만든 뒤 네 가지 상황을 차례로 실행한다. 존재하지 않는 계좌 X로 트랜잭션 없이 이체, 같은 이체를 트랜잭션으로, A에서 B로 정상 이체, 그리고 다음 절에서 볼 "커밋도 롤백도 하지 않고 닫기"다.

    public static void main(String[] args) throws Exception {
    HikariConfig cfg = new HikariConfig();
    cfg.setJdbcUrl("jdbc:h2:mem:bank;DB_CLOSE_DELAY=-1");
    cfg.setUsername("sa");
    cfg.setMaximumPoolSize(2);
    try (HikariDataSource ds = new HikariDataSource(cfg)) {
        try (Connection c = ds.getConnection(); Statement st = c.createStatement()) {
            st.execute("create table account(id varchar(10) primary key, balance int not null)");
            st.execute("insert into account values ('A', 10000), ('B', 10000)");
        }
        TransferService service = new TransferService(ds);
        AccountDao dao = new AccountDao();

        try { service.transferNoTx("A", "X", 3000); }
        catch (IllegalStateException e) { System.out.println("[자동 커밋] " + e.getMessage()); }
        print(ds, dao);

        try { service.transfer("A", "X", 3000); }
        catch (IllegalStateException e) { System.out.println("[트랜잭션] " + e.getMessage()); }
        print(ds, dao);

        service.transfer("A", "B", 2000);
        print(ds, dao);

        // 커밋도 롤백도 하지 않고 close 하면?
        try (Connection c = ds.getConnection()) {
            c.setAutoCommit(false);
            dao.withdraw(c, "A", 1000);
        }
        try (Connection c = ds.getConnection()) {
            System.out.println("반납 후 다시 빌린 커넥션 autoCommit=" + c.getAutoCommit());
        }
        print(ds, dao);
    }
}

static void print(DataSource ds, AccountDao dao) throws SQLException {
    try (Connection c = ds.getConnection()) {
        System.out.println("  A=" + dao.balance(c, "A") + ", B=" + dao.balance(c, "B"));
    }
}

  A=7000, B=10000
[트랜잭션] 입금 실패: 계좌 없음 id=X

    한 줄씩 추적해 보자. 첫 번째 이체는 자동 커밋 모드의 커넥션으로 실행되었다. 출금 UPDATE가 끝나는 순간 A=7,000이 커밋되었고, 입금이 실패해 예외가 났지만 이미 확정된 출금은 그대로 남았다. 같은 커넥션 하나를 썼는데도 트랜잭션이 되지 못한 것은 자동 커밋 때문이다. 같은 커넥션은 필요조건이지 충분조건이 아니다. 두 번째 이체는 트랜잭션 안에서 실행되었다. 출금으로 A가 4,000이 되었지만 커밋되지 않았고, 입금이 실패하자 rollback()이 출금까지 되돌려 A는 7,000을 유지했다. 세 번째 정상 이체는 둘 다 성공해 커밋되었으므로 A=5,000, B=12,000이다. 두 계좌의 합은 첫 번째 사고로 잃은 3,000을 빼면 항상 같다.

    서비스가 커넥션을 얻어 트랜잭션을 시작하고, 같은 커넥션을 출금과 입금 메서드에 넘긴 뒤 커밋 또는 롤백하고 반납하는 흐름을 보여 준다. 왼쪽에서 오른쪽으로 흐르는 흐름도. 맨 왼쪽에 "커넥션 풀" 원통 아이콘. 그 오른쪽에 큰 상자 "이체 서비스"가 있고, 그 안에 위에서 아래로 단계 상자 다섯 개 "커넥션 획득", "자동 커밋 끄기", "출금 호출", "입금 호출", "커밋 또는 롤백"이 화살표로 이어진다. "출금 호출"과 "입금 호출"에서 각각 오른쪽의 "저장소" 상자로 화살표가 나가고, 두 화살표에는 같은 색의 작은 플러그 아이콘과 "같은 커넥션" 라벨을 한 번만 붙인다. "저장소" 상자에서 오른쪽 끝의 "DB 세션" 상자로 SQL 화살표가 간다. 마지막 단계에서 왼쪽의 "커넥션 풀"로 돌아가는 곡선 화살표에 "반납" 라벨. 평면 다이어그램 스타일, 흰 배경, 파랑과 초록 위주. 트랜잭션은 서비스 계층에서 시작하고 끝나며, 그 사이의 모든 데이터 접근은 서비스가 얻은 같은 커넥션을 써야 한다.

    트랜잭션 적용 2: 커넥션 반납과 이 구조가 남기는 문제

    이제 release 메서드를 보자. 커넥션을 닫기 전에 setAutoCommit(true)를 호출했다. 커넥션 풀에서 close()는 물리 커넥션을 끊는 것이 아니라 풀에 반납하는 것이고, 반납된 커넥션은 그 세션 상태 그대로 다음 요청에 빌려 간다. 수동 커밋 모드인 채로 반납되면, 다음에 그 커넥션을 빌린 코드는 자동 커밋을 기대하고 INSERT를 보냈는데 커밋되지 않는 상황을 만날 수 있다. 그 코드는 커밋을 호출하지 않으므로 변경은 확정되지 않은 채 남고, 그 사이 잡힌 락은 계속 다른 요청을 막는다. 그래서 자기가 바꾼 세션 상태는 반납 전에 되돌려 놓는 것이 원칙이다. 이 코드에서 setAutoCommit(true)는 이미 커밋이나 롤백이 끝난 뒤에 호출되므로, 진행 중인 트랜잭션이 없어 아무것도 커밋하지 않는다.

    그렇다면 마지막 실험처럼 자동 커밋을 끄고 출금한 뒤 커밋도 롤백도 하지 않고 닫으면 어떻게 될까. JDBC Javadoc은 활성 트랜잭션이 있는 상태에서 close를 호출했을 때의 결과는 구현에 따라 다르다고 적고, 닫기 전에 명시적으로 커밋하거나 롤백할 것을 강하게 권한다. 표준이 정하지 않았으므로 실제 동작은 커넥션을 감싼 쪽이 정한다. 실행 결과를 보면 다시 빌린 커넥션은 autoCommit=true였고, 출금한 1,000은 반영되지 않아 A는 5,000 그대로였다. HikariCP가 정리해 준 것이다.

    HikariCP 소스에서 애플리케이션이 받는 커넥션은 실제 드라이버 커넥션을 감싼 프록시(ProxyConnection)이고, 그 close()는 대략 다음 일을 한다. HikariCP 5.1.0 태그의 소스와 이번 실험에 쓴 7.0.2 소스에서 이 부분은 같았다.

    // HikariCP ProxyConnection.close() 의 핵심 부분 (발췌)
if (isCommitStateDirty && !isAutoCommit) {
   delegate.rollback();       // 커밋되지 않은 변경이 있으면 롤백
   // ... 디버그 로그
}
if (dirtyBits != 0) {
   poolEntry.resetConnectionState(this, dirtyBits);   // autoCommit, 격리 수준, readOnly 등을 풀 설정값으로 복구
}
delegate.clearWarnings();
// ... finally 에서 풀에 반납(recycle)

    프록시는 자동 커밋이 꺼진 상태에서 문장이 실행되면 "커밋 상태가 더럽다"는 표시를 해 두고, commit()이나 rollback()이 호출되면 표시를 지운다. 반납 시점에 표시가 남아 있으면 롤백한다. 또 애플리케이션이 setAutoCommit, setTransactionIsolation, setReadOnly 등으로 바꾼 상태를 비트로 기록해 두었다가, 반납할 때 풀 설정의 기본값과 다르면 되돌린다. 그래서 HikariCP를 쓰면 release의 setAutoCommit(true)가 없어도 다음 사용자가 수동 커밋 커넥션을 받지는 않는다. 그래도 직접 되돌리는 코드를 두는 이유는, 이것이 특정 풀의 구현에 기댄 동작이기 때문이다. 풀 없이 DriverManager로 얻은 커넥션은 close()가 물리 연결을 끊으므로 상태가 이어지지 않지만, 활성 트랜잭션의 처리는 드라이버와 데이터베이스에 달려 있다. 이번 실험에서 H2 커넥션을 풀 없이 열어 커밋하지 않은 변경을 둔 채 닫았을 때는 변경이 반영되지 않았다.

    System.out.println("== G: close with open tx (raw H2)");
s1.setAutoCommit(false);
exec(s1, "update account set balance = 1 where id = 'B'");   // 커밋하지 않고
s1.close();                                                   // 닫는다
s2.commit();
System.out.println("after close s2 sees B=" + balance(s2, "B"));
    == G: close with open tx (raw H2)
after close s2 sees B=7777

    B는 앞의 자동 커밋 실험에서 커밋된 7,777 그대로다. 어떤 구현이 이렇게 롤백해 준다고 해서 그것에 기대는 코드를 쓰면 안 된다. 커밋도 롤백도 하지 않은 경로가 코드에 있다는 것은 그 자체로 버그이고, 그 경로가 실행되는 동안 행 락과 커넥션이 묶여 있다는 뜻이기 때문이다.

    롤백 중에 나는 예외

    위의 transfer 코드에는 작은 함정이 하나 있다. catch 블록의 con.rollback() 자체가 SQLException을 던질 수 있다. 예를 들어 네트워크가 끊겨 입금이 실패했다면 롤백 명령도 보낼 수 없다. 그러면 롤백의 예외가 원래 예외를 대신해 밖으로 나가고, 진짜 원인(입금 실패)은 사라진다. 원래 예외를 보존하려면 롤백 예외를 잡아 원래 예외에 억제된 예외로 붙이면 된다.

    } catch (SQLException | RuntimeException e) {
    try {
        con.rollback();
    } catch (SQLException rollbackEx) {
        e.addSuppressed(rollbackEx);   // 원래 예외를 살리고 롤백 실패는 덧붙인다
    }
    throw e;
}

    롤백 명령을 보내지 못했다고 해서 데이터가 위험해지는 것은 아니다. 연결이 끊기면 서버 쪽 세션도 정리되고, 커밋되지 않은 트랜잭션은 확정되지 않는다. 원자성은 "커밋 명령이 도착했는가"로 판정되기 때문이다. 문제가 되는 것은 데이터가 아니라 예외 정보다. 장애를 분석하는 사람이 "롤백 실패"만 보고 "입금 실패"를 보지 못하면 원인을 찾는 데 시간이 걸린다.

    이 구조가 남기는 문제

    트랜잭션은 걸렸다. 그런데 코드를 다시 보면 불편한 점이 여럿 보인다. 이 불편함을 정확히 짚어 두는 것이 다음 회차를 이해하는 열쇠다.

    1. 서비스 계층이 JDBC 기술에 묶였다. 이체 서비스는 비즈니스 로직을 담는 곳인데 java.sql.Connection, DataSource, SQLException을 직접 다룬다. 데이터 접근 기술을 JDBC에서 JPA로 바꾸면 JPA는 트랜잭션을 다루는 방식이 다르므로(커넥션 대신 엔티티 매니저의 트랜잭션을 쓴다) 비즈니스 로직은 그대로인데 서비스 코드를 고쳐야 한다.
    2. 커넥션을 계속 넘겨야 한다. 트랜잭션 안에서 호출되는 모든 데이터 접근 메서드는 커넥션 파라미터를 받아야 한다. 트랜잭션이 필요 없는 곳에서 쓰는 버전(스스로 커넥션을 얻는 메서드)과 트랜잭션용 버전을 따로 둬야 하는 경우도 생긴다. 서비스가 다른 서비스를 호출하면 커넥션이 그 서비스로도 넘어가야 한다.
    3. 같은 틀이 반복된다. 커넥션 획득, 자동 커밋 끄기, 커밋, 롤백, 반납으로 이루어진 try-catch-finally가 트랜잭션이 필요한 모든 서비스 메서드에 똑같이 들어간다. 비즈니스 로직은 그 사이의 두 줄뿐이다.
    4. 예외가 기술을 드러낸다. SQLException은 검사 예외이고 JDBC 전용이다. 서비스가 이 예외를 처리하거나 선언해야 하므로, 서비스 인터페이스에 JDBC가 새어 나온다. 오류 코드도 앞서 본 것처럼 데이터베이스마다 다르다.

    다음 회차는 앞의 세 문제를 스프링이 어떻게 푸는지 따라간다. 트랜잭션을 시작하고 끝내는 일을 추상화한 PlatformTransactionManager, 커넥션을 파라미터 대신 현재 스레드에 보관해 같은 스레드의 데이터 접근 코드가 같은 커넥션을 찾아 쓰게 하는 트랜잭션 동기화(ThreadLocal 기반), 반복되는 틀을 없애는 트랜잭션 템플릿, 그리고 @Transactional과 AOP 프록시가 그것이다. 마지막 문제인 예외는 5회차와 6회차에서 자바 예외의 원리와 스프링의 예외 추상화로 다룬다. 이 모든 해결책이 결국 같은 사실 위에 서 있다는 점을 기억하자. 트랜잭션을 유지하려면 같은 커넥션을 써야 한다.

    정리: 트랜잭션은 세션의 상태다

    이 회차의 내용을 한 줄로 줄이면 "트랜잭션은 데이터베이스 세션 하나가 들고 있는 상태"다. 자동 커밋 여부, 격리 수준, 아직 커밋하지 않은 변경, 그 변경을 지키는 행 락이 모두 세션 안에 있고, 애플리케이션에서 세션을 가리키는 손잡이가 커넥션이다. 그래서 트랜잭션을 시작하려면 커넥션의 자동 커밋을 끄고, 묶을 SQL을 모두 그 커넥션으로 보내고, 그 커넥션으로 커밋이나 롤백을 해야 한다.

    동시성 쪽에서 기억할 것은 세 가지다. 첫째, 쓰기는 행 락을 잡고 그 락은 트랜잭션이 끝날 때까지 유지된다. 트랜잭션이 길어지면 락도 길어지고, 그 행을 바꾸려는 다른 요청이 모두 줄을 선다. 둘째, 일반 SELECT는 락을 걸지도 기다리지도 않고 스냅샷을 읽는다. 읽은 값을 근거로 쓰기를 한다면 SELECT ... FOR UPDATE로 읽거나, 계산을 UPDATE 문 안으로 옮겨야 갱신 손실을 막을 수 있다. 셋째, 락 대기 시간 초과와 교착 상태는 롤백 범위가 다르다. InnoDB 기본 설정에서 시간 초과는 문장만, 교착 상태는 트랜잭션 전체를 롤백한다.

    애플리케이션 쪽에서 기억할 것은 트랜잭션의 경계가 서비스 계층에 있다는 것, 그리고 직접 구현하면 JDBC 의존, 커넥션 전달, 반복 코드라는 비용을 치른다는 것이다. 커넥션을 반납하기 전에 세션 상태를 되돌리는 일, 커밋도 롤백도 하지 않는 경로를 남기지 않는 일, 롤백 중의 예외가 원래 예외를 가리지 않게 하는 일도 모두 그 비용에 포함된다. 다음 회차에서 스프링이 이 비용을 어떻게 덜어 주는지 보면, 그 추상화 하나하나가 이 회차의 어떤 문제를 겨냥한 것인지 바로 알아볼 수 있을 것이다.
    트랜잭션
    데이터베이스가 하나의 단위로 다루는 작업 묶음. 커밋하면 전부 확정되고, 롤백하면 시작 이전 상태로 돌아간다.
    ACID
    원자성·일관성·격리성·지속성. InnoDB는 언두 로그로 되돌리기와 옛 버전 읽기를, 리두 로그와 커밋 시 플러시(기본값 innodb_flush_log_at_trx_commit=1)로 지속성을 지킨다.
    커넥션과 DB 세션
    커넥션 하나는 서버의 세션 하나에 대응하고, 트랜잭션·자동 커밋 여부·격리 수준·락은 세션의 상태다. 같은 트랜잭션에 넣으려면 같은 커넥션으로 SQL을 보내야 한다.
    자동 커밋
    문장 하나를 트랜잭션 하나로 실행하는 모드. MySQL과 JDBC 모두 기본값이다. setAutoCommit(false)로 끄고, 트랜잭션 중 다시 켜면 그 트랜잭션이 커밋된다.
    격리 수준
    READ UNCOMMITTED부터 SERIALIZABLE까지 네 단계로, 더티 리드·반복 불가능한 읽기·팬텀 읽기 중 무엇을 허용하는지 정한다. InnoDB 기본은 REPEATABLE READ, H2 2.4.240 기본은 READ COMMITTED였다.
    행 락
    UPDATE·DELETE·잠금 읽기는 인덱스 레코드에 락을 걸고, 락은 트랜잭션이 끝날 때 풀린다. REPEATABLE READ에서 인덱스가 없어 전체를 스캔하면 모든 행이 잠긴다.
    락 대기 시간 초과와 교착 상태
    InnoDB에서 대기 한도는 기본 50초이고, 초과하면 오류 1205와 함께 그 문장만 롤백된다. 교착 상태는 탐지 즉시 한 트랜잭션 전체를 롤백한다.
    잠금 읽기와 갱신 손실
    일반 SELECT는 스냅샷을 읽고 락을 걸지 않는다. 읽은 값으로 쓰기를 하면 갱신 손실이 생길 수 있으므로 SELECT ... FOR UPDATE로 읽거나 계산을 UPDATE 문 안에 넣는다.
    서비스 계층의 트랜잭션
    트랜잭션 경계는 비즈니스 로직 단위인 서비스에 있다. 직접 구현하면 커넥션 전달, JDBC 의존, 반복되는 try-catch-finally가 남고, 다음 회차에서 스프링이 이를 해결한다.

    실무에서 트랜잭션 관련 장애의 상당수는 "트랜잭션이 너무 길다"로 요약된다. 트랜잭션을 연 채로 외부 결제 API를 호출하거나 파일을 업로드하면, 그 시간 내내 커넥션 하나가 풀에서 빠져 있고 그 트랜잭션이 바꾼 행의 락도 유지된다. 외부 호출이 느려지는 순간 같은 행을 바꾸려는 요청들이 줄을 서고, 그 요청들도 커넥션을 하나씩 붙잡고 기다리므로 풀이 바닥난다. 그러면 그 행과 상관없는 요청까지 커넥션을 얻지 못해 멈춘다. 데이터베이스에서는 data_locks나 세션 목록에 아무것도 실행하지 않는 세션이 락을 쥐고 있는 모습으로 나타난다. 그래서 트랜잭션에는 데이터베이스 작업만 넣고, 느린 외부 작업은 트랜잭션 밖으로 빼는 것이 기본 설계 원칙이 된다.

    락 대기 시간의 기본값 50초는 웹 요청 관점에서는 매우 길다. 사용자의 HTTP 요청이나 앞단 프록시의 시간 초과가 그보다 짧으면, 사용자는 이미 오류 화면을 보았는데 서버에서는 요청 스레드가 여전히 락을 기다리는 상황이 생긴다. 한편 시간 초과가 나도 기본 설정에서는 문장만 롤백되고 트랜잭션은 열려 있으므로, 예외를 받은 코드가 롤백 없이 커넥션을 계속 쓰면 반쯤 진행된 트랜잭션 위에서 일이 이어진다. 시간 초과를 어떻게 설정할지, 오류를 받으면 트랜잭션 전체를 롤백하고 재시도할지는 서비스 특성에 따라 정해야 하는 판단이다.

    갱신 손실을 막는 방법을 고를 때도 조건에 따라 판단이 달라진다. 판단이 "잔액이 금액 이상인가"처럼 SQL 한 문장으로 표현된다면 조건부 UPDATE가 가장 짧고 락 보유 시간도 짧다. 여러 행을 읽고 복잡한 규칙을 적용해야 한다면 SELECT ... FOR UPDATE로 필요한 행을 먼저 잠그되, 잠그는 순서를 일정하게 정해 교착 상태를 줄인다. 경합이 드물고 충돌 시 재시도가 허용된다면 버전 열을 비교하는 낙관적 방식이 락을 오래 쥐지 않는다. 어느 방법이든 같은 데이터를 바꾸는 모든 코드 경로가 같은 규칙을 따라야 의미가 있다.
  • MySQL InnoDB, 기본 격리 수준 REPEATABLE READ에서 A의 잔액이 10,000이다. 세션2가 START TRANSACTION 후 A를 조회한다. 그다음 세션1이 자동 커밋 모드로 UPDATE account SET balance = 9000 WHERE id = 'A'를 실행한다. 이어서 세션2가 (1) A를 다시 조회하고, (2) UPDATE account SET balance = balance - 100 WHERE id = 'A'를 실행한 뒤, (3) A를 또 조회한다. 세 번의 결과를 예측하고 이유를 설명하라.
  • 어떤 개발자가 서비스 메서드에서 Connection con = dataSource.getConnection(); con.setAutoCommit(false);로 트랜잭션을 시작한 뒤, 저장소의 withdraw(id, amount)와 deposit(id, amount)를 호출하고 실패하면 con.rollback()을 호출했다. 저장소 메서드는 각자 dataSource.getConnection()으로 커넥션을 얻어 SQL을 실행하고 닫는다. 입금이 실패했을 때 출금이 되돌려지지 않는 이유를 커넥션과 세션의 관점에서 설명하라.
  • 기본 격리 수준 REPEATABLE READ인 InnoDB에서, 테이블 member(id PK, name, point)의 name 열에 인덱스가 없다. 트랜잭션 T1이 UPDATE member SET point = point + 10 WHERE name = 'kim'을 실행하고 커밋하지 않았다. 트랜잭션 T2가 UPDATE member SET point = 0 WHERE id = 5를 실행한다(id 5의 name은 'lee'). T2는 기다리게 되는가? 매뉴얼의 락 규칙으로 설명하고, 해결 방법을 제시하라.
  • 커넥션 풀이 반납 시 상태를 초기화하지 않는다고 가정하자. 서비스 A는 setAutoCommit(false)로 작업을 하고 커밋한 뒤 자동 커밋을 되돌리지 않고 close()했다. 그 커넥션을 빌려 간 서비스 B는 자동 커밋을 가정하고 INSERT 하나를 실행한 뒤 커넥션을 반납했다. 무슨 일이 생기는지, 그 영향이 언제 어떻게 드러나는지 설명하라.
  • 이체 A→B와 B→A가 동시에 실행되어 교착 상태가 생기는 과정을 두 세션의 시간 순서로 그려라. 각 이체가 출금 후 입금 순서로 UPDATE를 실행한다고 가정한다. 그리고 코드 구조를 바꾸지 않고 순서만 바꿔 교착 상태를 피하는 방법을 제시하라.
    •

    1번. (1)은 10,000이다. REPEATABLE READ에서 같은 트랜잭션의 일관된 읽기는 첫 읽기 때 만든 스냅샷을 계속 읽으므로, 세션1의 커밋은 보이지 않는다. (2)의 UPDATE는 스냅샷이 아니라 최신 커밋 값 9,000을 대상으로 실행된다. 매뉴얼은 스냅샷이 SELECT 문에 적용되는 것이고 DML 문에 반드시 적용되는 것은 아니라고 설명한다. 따라서 A는 8,900이 된다. (3)은 8,900이다. 매뉴얼에 따르면 트랜잭션이 다른 트랜잭션이 커밋한 행을 갱신하면 그 변경은 현재 트랜잭션에 보이게 된다. 같은 트랜잭션 안에서 10,000을 본 직후 8,900을 보게 되는 이 장면이, 매뉴얼이 잠금 읽기·갱신과 일반 읽기를 한 트랜잭션에 섞지 말라고 권하는 이유다. MySQL 8.4.13과 8.0.46에서 이 순서대로 실행했을 때도 세 번의 결과는 10,000, (갱신 후) 8,900, 8,900이었다.

    2번. 트랜잭션은 커넥션, 즉 DB 세션에 붙어 있다. 서비스가 자동 커밋을 끈 것은 서비스가 얻은 커넥션의 세션뿐이다. 저장소 메서드가 각자 얻은 커넥션은 다른 세션이고 자동 커밋 모드이므로, 출금 UPDATE는 실행이 끝나는 즉시 그 세션에서 커밋된다. 서비스의 con.rollback()은 아무 SQL도 실행하지 않은 자기 세션을 롤백할 뿐이다. 풀에서 같은 물리 커넥션을 우연히 다시 받더라도 출금은 이미 커밋된 뒤다. 해결하려면 서비스가 얻은 커넥션을 저장소 메서드에 넘겨 같은 세션에서 실행해야 한다.

    3번. 기다린다. InnoDB는 UPDATE를 처리하며 스캔한 모든 인덱스 레코드에 락을 걸고, WHERE 조건에 맞지 않는 행인지와 상관이 없다. name에 인덱스가 없으므로 T1은 클러스터드 인덱스 전체를 스캔하고, 매뉴얼의 설명대로 테이블의 모든 행이 잠긴다. id 5의 레코드도 T1의 락에 걸려 있으므로 T2는 T1이 끝날 때까지 기다린다. 해결 방법은 name에 인덱스를 만들어 T1이 'kim'에 해당하는 인덱스 범위만 스캔하게 하는 것이다. 트랜잭션을 짧게 유지하는 것도 대기 시간을 줄인다. MySQL 8.4.13과 8.0.46에서 id 1~6인 여섯 행(그중 'kim' 두 행)으로 재현해 보니, 인덱스가 없을 때 T1은 data_locks에 기본 키 1~6과 supremum pseudo-record까지 일곱 개의 X 락을 잡았고, T2는 id 5의 락을 기다리다 대기 한도(세션에서 2초로 줄였다)를 넘겨 오류 1205를 받았다. name에 인덱스를 만든 뒤 같은 순서로 실행하자 T2는 기다리지 않고 바로 끝났다.

    4번. 서비스 B가 받은 커넥션은 수동 커밋 모드다. B의 INSERT는 실행되지만 커밋되지 않고, B는 커밋을 부르지 않은 채 반납한다. 그 세션에는 커밋되지 않은 변경과 그 변경의 락이 남는다. 이후 그 커넥션을 빌린 누군가가 우연히 커밋하면 B의 데이터가 그때 함께 커밋되고, 롤백하거나 커넥션이 정리되면 B의 데이터는 사라진다. B는 성공 응답을 이미 보냈으므로, 사용자는 저장되었다고 믿는데 데이터가 없거나 엉뚱한 시점에 나타나는 증상으로 드러난다. 그 사이 남은 락 때문에 같은 행을 바꾸려는 요청이 대기하는 현상도 함께 나타날 수 있다. 원인이 A에 있는데 증상은 B와 그 뒤의 요청에서 나타나므로 추적이 어렵다.

    5번. T1(A→B)이 A를 출금하며 A 행의 배타 락을 얻고, 거의 동시에 T2(B→A)가 B를 출금하며 B 행의 배타 락을 얻는다. 이어서 T1이 B에 입금하려고 B의 락을 요청하지만 T2가 쥐고 있어 기다리고, T2가 A에 입금하려고 A의 락을 요청하지만 T1이 쥐고 있어 기다린다. 서로가 서로를 기다리는 순환이므로 교착 상태다. InnoDB는 이를 탐지해 한쪽 트랜잭션 전체를 롤백한다. 피하는 방법은 락을 잡는 순서를 모든 트랜잭션에서 같게 만드는 것이다. 예를 들어 두 계좌 중 식별자가 작은 쪽의 UPDATE를 항상 먼저 실행하면(B→A 이체라면 A에 입금을 먼저, B 출금을 나중에), 두 이체 모두 A의 락을 먼저 요청하므로 한쪽은 A에서 기다리게 될 뿐 순환이 생기지 않는다.

     출금과 입금을 같은 트랜잭션으로 묶으려 할 때 반드시 필요한 조건은? 두 SQL이 같은 스레드에서 실행되는 것 두 SQL이 자동 커밋이 꺼진 같은 커넥션으로 실행되는 것 두 SQL이 같은 커넥션 풀에서 얻은 커넥션으로 실행되는 것 격리 수준을 SERIALIZABLE로 올리는 것 트랜잭션은 DB 세션의 상태이고 커넥션 하나가 세션 하나다. 같은 풀에서 얻었더라도 다른 커넥션이면 다른 세션이다. 같은 스레드인지 여부는 데이터베이스가 알지 못한다(스프링이 스레드를 이용해 같은 커넥션을 찾아 주는 것은 다음 회차의 이야기다). 격리 수준은 다른 트랜잭션과의 관계를 정할 뿐 문장을 묶어 주지 않는다. 또 같은 커넥션이라도 자동 커밋 모드면 문장마다 커밋된다. MySQL InnoDB 기본 설정에서 트랜잭션 안의 UPDATE가 행 락을 기다리다 innodb_lock_wait_timeout을 넘겨 오류 1205를 받았다. 이 시점의 상태로 옳은 것은? 트랜잭션 전체가 롤백되었고 락도 모두 풀렸다 아무것도 롤백되지 않았고, 문장은 락을 얻는 즉시 자동으로 다시 실행된다 시간 초과된 문장만 롤백되었고, 트랜잭션은 열려 있어 앞서 바꾼 행과 락이 남아 있다 세션이 강제로 종료되었다 InnoDB 오류 처리 문서에 따르면 락 대기 시간 초과는 현재 문장만 롤백한다. 트랜잭션 전체를 롤백하려면 --innodb-rollback-on-timeout으로 서버를 띄워야 한다. 그래서 애플리케이션은 오류를 받으면 명시적으로 롤백할지 결정해야 한다. 트랜잭션 전체 롤백은 교착 상태일 때의 동작이다. InnoDB에서 세션1이 SELECT ... FOR UPDATE로 A 행을 읽고 커밋하지 않았다. 세션2가 일반 SELECT로 A 행을 조회하면? 기다리지 않고 바로 스냅샷의 값을 읽는다 세션1이 커밋할 때까지 기다린다 즉시 락 오류가 난다 세션1이 아직 커밋하지 않은 값을 읽는다 일반 SELECT는 일관된 읽기로, 스냅샷을 읽고 락을 걸지 않으며 읽기 뷰에 있는 레코드에 걸린 락을 무시한다. 옛 버전은 언두 로그로 재구성하므로 락과 무관하다. FOR UPDATE가 막는 것은 다른 트랜잭션의 갱신, FOR SHARE, 그리고 일부 격리 수준에서의 읽기다. 커밋되지 않은 값을 읽는 것은 READ UNCOMMITTED의 더티 리드다. 자동 커밋을 끄고 UPDATE를 실행한 뒤, commit()이나 rollback()을 호출하지 않고 connection.setAutoCommit(true)를 호출했다. JDBC 명세상 결과는? 진행 중인 트랜잭션이 롤백된다 아무 일도 일어나지 않고, 변경은 다음 commit() 호출까지 대기한다 SQLException이 발생한다 진행 중인 트랜잭션이 커밋된다 Connection.setAutoCommit의 Javadoc은 트랜잭션 도중 이 메서드가 호출되어 자동 커밋 모드가 바뀌면 트랜잭션이 커밋된다고 적는다. MySQL에서도 SET autocommit = 1은 값이 1이 아니었다면 암묵적 커밋을 일으킨다. 이 회차의 H2 실험에서도 다른 세션이 바로 변경된 값을 읽었다. 두 세션이 같은 계좌에서 동시에 1,000원씩 출금한다. 갱신 손실을 막지 못하는 방법은? SELECT ... FOR UPDATE로 잔액을 읽고 계산한 값을 UPDATE한다 REPEATABLE READ에서 일반 SELECT로 잔액을 읽고 계산한 값을 UPDATE한다 UPDATE 문 안에서 balance - 1000으로 계산하고, 잔액이 충분한지는 같은 문장의 WHERE 조건으로 확인한다 행에 버전 열을 두고, 읽을 때의 버전과 같을 때만 갱신하며 바뀐 행 수가 0이면 재시도한다 REPEATABLE READ는 같은 트랜잭션에서 다시 읽을 때 같은 값을 보여 줄 뿐, 내가 읽은 뒤 다른 트랜잭션이 바꾸는 것을 막지 않는다. 두 세션이 같은 값을 읽고 각자 계산한 상수를 쓰면 한쪽 출금이 사라진다. FOR UPDATE는 두 번째 읽기를 기다리게 하고, SQL 안의 계산은 락을 얻은 뒤 최신 값으로 실행되며, 버전 비교는 충돌을 감지해 재시도하게 한다.
    트랜잭션(transaction)
    데이터베이스가 하나의 단위로 다루는 작업 묶음. 커밋으로 확정하고 롤백으로 취소한다.
    자동 커밋(autocommit)
    각 SQL 문장을 하나의 트랜잭션으로 실행하고 끝나는 즉시 커밋하는 모드. MySQL과 JDBC 커넥션의 기본값이다.
    DB 세션(database session)
    클라이언트 연결 하나에 대응해 서버가 유지하는 상태. 트랜잭션, 자동 커밋 여부, 격리 수준, 보유한 락이 여기에 속한다.
    언두 로그(undo log)
    트랜잭션이 바꾸기 전의 정보를 담은 InnoDB 로그. 롤백과, 다른 트랜잭션에 옛 버전을 보여 주는 일관된 읽기에 쓰인다.
    리두 로그(redo log)
    변경 내용을 기록하는 InnoDB의 디스크 기반 로그. 크래시 후 데이터 파일에 반영되지 못한 변경을 재생해 지속성을 지킨다.
    일관된 읽기(consistent read)
    다중 버전을 이용해 특정 시점의 스냅샷을 보여 주는 InnoDB의 일반 SELECT. 락을 걸지 않고 다른 트랜잭션의 락도 기다리지 않는다.
    잠금 읽기(locking read)
    SELECT ... FOR UPDATE나 FOR SHARE처럼 읽으면서 행에 락을 거는 조회. 최신 값을 읽고, 락은 트랜잭션이 끝날 때 풀린다.
    갱신 손실(lost update)
    두 트랜잭션이 같은 값을 읽고 각자 계산한 결과를 쓰면서 한쪽의 변경이 다른 쪽에 덮여 사라지는 현상.
    교착 상태(deadlock)
    두 트랜잭션 이상이 서로가 가진 락을 기다려 어느 쪽도 진행하지 못하는 상태. InnoDB는 탐지해 한 트랜잭션 전체를 롤백한다.
