    이 회차의 질문: 해시 인덱스만으로 집합이 되는가

    셋(Set)은 두 가지 성질로 정의되는 자료 구조다. 같은 원소를 두 번 담지 않고, 원소 사이의 순서를 약속하지 않는다. 그래서 셋의 핵심 연산은 "몇 번째에 무엇이 있는가"가 아니라 "이 값이 이미 들어 있는가"다. 원소를 넣는 add조차 먼저 이 질문에 답해야 한다. 이미 있으면 넣지 않아야 하기 때문이다.

    리스트로 셋을 흉내 내면 이 질문 하나에 원소 전체를 훑어야 한다. 원소가 n개면 add 한 번이 O(n)이고, n개를 차례로 넣는 데 드는 비교 횟수는 n의 제곱에 비례한다. 06회에서 본 해시 인덱스는 이 탐색 범위를 줄이는 방법이었다. 값을 배열 크기로 나눈 나머지를 인덱스로 쓰면 값이 있어야 할 칸을 계산으로 바로 찾을 수 있고, 서로 다른 값이 같은 칸으로 몰리는 해시 충돌(hash collision)은 한 칸에 여러 값을 담는 버킷(bucket)으로 받아 낸다.

    이번 회차에서는 그 생각을 실제 셋으로 조립한다. 조립하다 보면 세 가지 질문에 차례로 부딪힌다.

    • 정수는 나머지 연산으로 인덱스를 만들 수 있다. 그러면 문자열이나 직접 만든 객체처럼 숫자가 아닌 것은 어떻게 배열 인덱스가 되는가.
    • 셋은 "같은 값"을 걸러 내야 한다. 그 "같다"는 판단은 누가, 어떤 기준으로 하는가.
    • 인덱스를 정하는 계산과 같음을 정하는 판단이 서로 어긋나면 셋 안에서 무슨 일이 벌어지는가.

    첫 질문의 답이 hashCode(), 둘째 질문의 답이 equals(), 셋째 질문의 답이 이 회차의 본론이다. 구현은 네 단계로 키운다. 정수만 담는 셋, 모든 객체를 담는 셋, 직접 만든 객체를 담았을 때의 문제, 마지막으로 제네릭과 인터페이스를 입힌 셋이다. 클래스 이름과 예제는 모두 이 글에서 새로 만든 것이다.

    1단계: 정수만 담는 해시 셋

    가장 단순한 형태부터 만든다. 버킷 배열을 하나 두고, 버킷마다 연결 리스트를 하나씩 넣는다. 값이 들어오면 배열 길이로 나눈 나머지를 인덱스로 삼아 그 버킷 하나만 들여다본다.

    import java.util.Arrays;
import java.util.LinkedList;

public class IntHashSet {
    private static final int DEFAULT_CAPACITY = 10;

    private final LinkedList[] buckets;
    private int size;

    public IntHashSet() {
        this(DEFAULT_CAPACITY);
    }

    @SuppressWarnings("unchecked")
    public IntHashSet(int capacity) {
        buckets = new LinkedList[capacity];
        for (int i = 0; i < capacity; i++) {
            buckets[i] = new LinkedList<>();
        }
    }

    public boolean add(int value) {
        LinkedList bucket = buckets[indexOf(value)];
        if (bucket.contains(value)) {
            return false;               // 이미 있으면 넣지 않는다
        }
        bucket.add(value);
        size++;
        return true;
    }

    public boolean contains(int value) {
        return buckets[indexOf(value)].contains(value);
    }

    public boolean remove(int value) {
        boolean removed = buckets[indexOf(value)].remove(Integer.valueOf(value));
        if (removed) {
            size--;
        }
        return removed;
    }

    public int size() {
        return size;
    }

    private int indexOf(int value) {
        return value % buckets.length;
    }

    @Override
    public String toString() {
        return Arrays.toString(buckets) + " size=" + size;
    }
}

    세 연산의 뼈대가 똑같다는 점을 먼저 본다. indexOf(value)로 버킷 하나를 고르고, 그 버킷 안에서만 일을 한다. 나머지 아홉 개 버킷은 쳐다보지 않는다. add가 contains와 다른 점은 "없으면 넣는다"가 붙는 것뿐이고, 셋의 "중복 없음"은 바로 이 한 줄(if (bucket.contains(value)) return false;)에서 나온다. 생성자의 new LinkedList[capacity]와 @SuppressWarnings가 눈에 걸리겠지만 그 이유는 4단계에서 따로 다룬다.

    public class IntHashSetMain {
    public static void main(String[] args) {
        IntHashSet set = new IntHashSet();
        set.add(1);
        set.add(2);
        set.add(14);
        set.add(99);
        System.out.println(set.add(9));
        System.out.println(set.add(99));
        System.out.println(set);

        System.out.println(set.contains(9));
        System.out.println(set.contains(19));
        System.out.println(set.remove(99));
        System.out.println(set);
    }
}

    9번 버킷을 따라가 보자. add(99)는 99 % 10 = 9를 계산해 9번 버킷으로 간다. 버킷이 비어 있으니 비교할 것이 없고 바로 넣는다. add(9)도 9 % 10 = 9라서 같은 버킷으로 간다. 이번에는 버킷에 99가 있으므로 9와 99를 한 번 비교하고, 다르니 뒤에 붙인다. 버킷은 [99, 9]가 되고 true가 반환된다. 두 번째 add(99)는 같은 버킷에서 첫 원소와 비교하자마자 같다는 것을 알고 false를 돌려준다. 이때 1, 2, 14가 든 다른 버킷은 전혀 건드리지 않았다.

    contains(19)가 false인 과정도 같다. 19 % 10 = 9이므로 9번 버킷의 99, 9 두 개와만 비교하고 끝난다. 원소가 다섯 개인데 비교는 두 번이다. 셋 전체의 크기가 아니라 버킷 하나의 길이가 비용을 정한다. 값이 버킷에 고르게 퍼져 있다면 버킷 하나의 평균 길이는 (원소 수 ÷ 버킷 수)이고, 이 값이 작게 유지되는 한 연산 비용은 원소 수와 무관하다.

    배열 칸에 들어 있는 것은 리스트가 아니라 리스트 객체를 가리키는 참조다. 리스트 안의 노드도 값이 아니라 Integer 객체의 참조를 들고 있다. 제네릭의 타입 인자에는 기본형이 올 수 없으므로 add(int)로 받은 값은 bucket.add(value)에서 Integer로 박싱된다. contains(9) 한 번은 나머지 연산 한 번, 배열 칸 읽기 한 번, 그 뒤 리스트 노드를 따라가며 Integer.equals로 비교하는 순서로 진행된다.

    버킷 배열 10칸과 각 칸에 매달린 연결 리스트, 그리고 99와 9가 같은 9번 버킷으로 들어가는 계산을 한 장에 보여 준다. 가로형 16:9의 깔끔한 기술 다이어그램. 왼쪽에 세로로 긴 배열 상자 10칸을 그리고 위에 라벨 "buckets (길이 10)"을 붙인다. 각 칸 왼쪽에 인덱스 숫자 0부터 9를 적는다. 1번 칸에서 오른쪽으로 화살표가 나가 둥근 사각형 "1"을 가리키고, 2번 칸은 "2", 4번 칸은 "14"를 가리킨다. 9번 칸에서 나간 화살표는 둥근 사각형 "99"를 가리키고, "99"에서 다시 화살표가 나가 "9"를 가리킨다. 나머지 칸 옆에는 옅은 회색의 작은 빈 상자를 그리고 라벨 "빈 리스트"를 한 번만 붙인다. 오른쪽 위에 말풍선 두 개 "99 % 10 = 9", "9 % 10 = 9"를 그려 둘 다 9번 칸을 가리키게 한다. 맨 아래에 강조 문구 "같은 인덱스 → 같은 버킷 → 버킷 안에서만 비교"를 넣는다. 흰 배경, 파랑과 주황 두 가지 색만 사용, 장식 없이 평면적인 선 그림. 값은 나머지 연산으로 버킷 하나를 고르고, 비교는 그 버킷 안에서만 일어난다.

    이 구현에 숨어 있는 세 가지 함정

    첫째는 remove의 Integer.valueOf(value)다. 이것을 빼고 bucket.remove(value)라고 쓰면 전혀 다른 메서드가 호출된다. LinkedList에는 remove(int index)와 remove(Object o)가 둘 다 있고, 인자가 int면 컴파일러는 박싱이 필요 없는 remove(int index)를 먼저 고른다. 버킷 [99, 9]에서 remove(99)를 부르면 99번째 원소를 지우려다 IndexOutOfBoundsException: Index: 99, Size: 2가 난다. 값이 우연히 유효한 인덱스 범위에 들면 예외도 없이 엉뚱한 원소가 지워지므로 더 나쁘다. "값으로 지운다"는 의도를 Integer 객체를 넘겨 분명히 해야 한다.

    둘째는 음수다. set.add(-3)을 실행하면 ArrayIndexOutOfBoundsException: Index -3 out of bounds for length 10이 난다. 자바의 %는 나머지의 부호가 나누어지는 수(피제수)를 따르기 때문에 -3 % 10은 7이 아니라 -3이다. JLS §15.17.3은 정수 나머지 연산이 (a/b)*b+(a%b) == a를 만족하도록 정의되고, 그 결과는 피제수가 음수일 때만 음수가 될 수 있다고 적는다. 이 문제는 문자열 해시 코드를 다룰 때 다시 만나고, 거기서 고친다.

    셋째는 버킷 수가 고정이라는 점이다. 버킷이 10개인 채로 원소가 1,000개가 되면 버킷 하나에 평균 100개가 들어가고, 연산은 다시 리스트 탐색에 가까워진다. 원소가 늘 때 버킷 배열을 키워 다시 배치하는 방법은 자바가 제공하는 셋 구현을 다루는 08회의 몫으로 남겨 둔다.

    문자열을 숫자로 바꾸기: 문자열 해시 코드

    정수는 그 자체로 나머지 연산을 할 수 있었다. "AB" 같은 문자열을 버킷에 넣으려면 먼저 문자열을 정수로 바꾸는 계산이 필요하다. 이렇게 임의의 데이터에서 계산해 낸 정수를 해시 코드(hash code), 그 계산을 해시 함수(hash function)라고 부른다. 해시 코드를 배열 길이에 맞게 줄인 것이 해시 인덱스다. 두 단계를 구분해 두면 뒤의 이야기가 쉬워진다. 객체가 책임지는 것은 해시 코드까지이고, 인덱스로 줄이는 일은 셋이 한다.

    출발점은 문자가 이미 숫자라는 사실이다. 자바의 char는 UTF-16 코드 유닛을 나타내는 16비트 부호 없는 정수다(JLS §4.2). 'A'는 65, 'B'는 66, 'a'는 97, '가'는 44032다. 그러니 가장 먼저 떠오르는 방법은 글자 값을 전부 더하는 것이다.

    public class StringHashDemo {
    static int sumHash(String s) {
        int h = 0;
        for (int i = 0; i < s.length(); i++) {
            h += s.charAt(i);
        }
        return h;
    }

    static int polyHash(String s) {
        int h = 0;
        for (int i = 0; i < s.length(); i++) {
            h = 31 * h + s.charAt(i);
        }
        return h;
    }

    public static void main(String[] args) {
        System.out.println((int) 'A' + " " + (int) 'B' + " " + (int) 'a' + " " + (int) '가');
        System.out.println(sumHash("AB") + " " + sumHash("BA"));
        System.out.println(polyHash("AB") + " " + polyHash("BA"));
        System.out.println("AB".hashCode() + " " + "BA".hashCode());
        System.out.println("Aa".hashCode() + " " + "BB".hashCode());
        System.out.println(polyHash("hello") + " " + polyHash("hello "));
        System.out.println("collection".hashCode());
    }
}

    더하기만 하면 순서가 사라진다

    sumHash는 "AB"와 "BA"에 똑같이 131을 준다. 덧셈은 순서를 바꿔도 결과가 같으므로 글자의 위치 정보가 통째로 사라진다. 같은 글자로 이루어진 문자열은 모두 한 버킷에 몰린다. 값의 범위도 좁다. 영문 소문자 10글자짜리 문자열의 합은 많아야 1,220('z'가 122)이어서, 버킷을 아무리 늘려도 앞쪽 일부만 쓰게 된다. 해시 함수가 지켜야 할 조건은 "같은 입력에 같은 결과"뿐이지만, 쓸모 있는 해시 함수는 서로 다른 입력을 되도록 서로 다른 값으로 넓게 흩어 놓아야 한다.

    자릿값을 주면 순서가 살아난다

    십진수 12와 21이 다른 수인 까닭은 자리마다 10의 거듭제곱이 곱해지기 때문이다. 같은 방법을 문자열에 쓴다. 글자 값을 자릿수로 보고, 자리마다 31의 거듭제곱을 곱한다. "AB"는 65×31 + 66 = 2081, "BA"는 66×31 + 65 = 2111이 된다. String.hashCode()의 API 문서는 이 계산을 식으로 못 박아 둔다. 길이가 n인 문자열 s의 해시 코드는 int 연산으로 계산한 s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1]이고, 빈 문자열의 해시 코드는 0이다.

    polyHash의 반복문 h = 31 * h + c는 이 식을 앞 글자부터 한 번의 순회로 계산하는 방법이다. 글자를 하나 받을 때마다 지금까지의 값을 한 자리 올리고(×31) 새 글자를 일의 자리에 더한다. 출력 셋째 줄과 넷째 줄이 같다는 것은 직접 만든 계산이 String.hashCode()와 같은 값을 낸다는 뜻이다.

    글자 값을 단순히 더하면 AB와 BA가 같아지지만, 자리마다 31을 곱하면 달라진다는 것을 나란히 보여 준다. 가로형 16:9, 좌우 두 칸으로 나눈 비교 다이어그램. 왼쪽 칸 제목은 "더하기만: 순서가 사라진다". 그 아래 두 줄로 "AB → 65 + 66 = 131", "BA → 66 + 65 = 131"을 적고 두 결과 131을 빨간 등호로 묶어 "충돌"이라고 표시한다. 오른쪽 칸 제목은 "자릿값 31: 순서가 남는다". 그 아래 두 줄로 "AB → 65 × 31 + 66 = 2081", "BA → 66 × 31 + 65 = 2111"을 적고 두 결과를 초록색 부등호로 구분한다. 각 문자열의 글자는 네모 타일로 그리고 타일 아래에 숫자 65, 66을 작게 적는다. 맨 아래 가운데에 공식 라벨 "h = 31 × h + 글자"를 넣는다. 흰 배경, 평면적인 선 그림, 글자는 굵은 고딕. 자리마다 31을 곱하면 같은 글자로 이루어진 문자열도 서로 다른 해시 코드를 얻는다.

    오버플로는 버그가 아니라 계산의 일부다

    "hello"를 한 글자씩 따라가면 h는 104, 3325, 103183, 3198781, 99162322로 커진다. 여기에 공백 한 글자를 더 붙이면 31 × 99162322 + 32 = 3,074,032,014가 되어야 하는데, int의 최댓값 2,147,483,647을 넘는다. 실제로 나온 값은 -1,220,935,282다. 수학적인 값에서 2의 32제곱(4,294,967,296)을 뺀 값과 같다.

    이것은 예외 상황이 아니다. JLS §15.17.1은 정수 곱셈이 넘치면 결과가 수학적 곱의 하위 비트가 되고 부호가 달라질 수 있으며, 곱셈 연산자는 실행 중 예외를 던지지 않는다고 정한다. 32비트 밖으로 넘친 상위 비트는 버려지고, 남은 32비트의 최상위 비트가 1이면 2의 보수 표현에서 음수로 읽힌다. 해시 코드에 필요한 것은 크기의 의미가 아니라 "같은 문자열이면 언제나 같은 값"이라는 결정성이고, 넘친 비트를 버리는 계산도 입력이 같으면 결과가 같다. 그래서 길이가 조금만 되는 문자열의 해시 코드는 흔히 음수다. "collection"의 해시 코드는 -1741312354다.

    왜 홀수를 곱하는가

    int 연산은 사실상 2의 32제곱으로 나눈 나머지 위에서 이루어진다. 이 세계에서 짝수를 곱하면 정보가 빠져나간다. 곱하는 수가 2라고 해 보자. 글자를 하나 처리할 때마다 지금까지의 값이 왼쪽으로 한 비트씩 밀린다. 글자가 32개 더 들어오면 처음 글자가 남긴 비트는 전부 32비트 바깥으로 밀려나 사라지고, 그 뒤로는 앞 글자가 무엇이었든 결과가 같아진다.

    홀수를 곱할 때는 이런 일이 없다. 홀수를 곱하는 연산은 32비트 정수 전체를 서로 겹치지 않게 다른 값으로 옮기는 일대일 대응이어서, 서로 다른 두 값에 31을 곱하면 넘침이 있어도 결과가 서로 다르다. 앞 글자의 흔적이 뒤섞일 뿐 지워지지는 않는다. 31에는 계산상의 성질도 하나 있다. 31 = 32 - 1이므로 31 * h는 (h << 5) - h와 언제나 같은 값이다.

    충돌은 없앨 수 없다

    출력 다섯째 줄을 보면 "Aa"와 "BB"의 해시 코드가 둘 다 2112다. 65×31 + 97 = 2112이고 66×31 + 66 = 2112다. 첫 글자가 1 커지면 31이 늘고, 둘째 글자가 31 작아지면 31이 줄어 상쇄된다. 이런 쌍을 이어 붙인 "AaAa", "AaBB", "BBAa", "BBBB"도 모두 같은 해시 코드(2031744)를 가진다.

    이것은 31이라는 숫자의 결함이 아니다. int가 나타낼 수 있는 값은 2의 32제곱 가지뿐인데 문자열의 가짓수에는 끝이 없다. 어떤 해시 함수를 쓰든 서로 다른 문자열 둘이 같은 해시 코드를 받는 경우가 반드시 생긴다. 따라서 해시 코드가 같다는 것은 같은 값이라는 증거가 될 수 없다. 해시 코드는 후보를 좁히는 데까지만 쓰고, 정말 같은지는 내용을 직접 비교해야 한다. 이 역할 분담이 뒤에서 equals와 hashCode의 관계로 이어진다.

    음수 해시 코드를 인덱스로 바꾸기

"polygenelubricants"가 그렇다. 이 문자열 하나 때문에 Math.abs(h) % 10은 -8이 되고, 평소에는 멀쩡하던 코드가 특정 입력에서만 ArrayIndexOutOfBoundsException을 낸다.

    Math.floorMod(h, n)는 결과의 부호가 나누는 수를 따르므로, n이 양수면 결과는 언제나 0 이상 n 미만이다. 최솟값을 넣어도 2가 나온다. Math.abs를 쓴 결과(4)와 floorMod의 결과(6)가 다르다는 점은 문제가 되지 않는다. 넣을 때와 찾을 때 같은 계산을 쓰기만 하면 된다. 참고로 OpenJDK 21의 HashMap은 배열 길이 n을 2의 거듭제곱으로 유지하고 (n - 1) & hash로 인덱스를 구한다. 비트 AND의 결과는 음수가 될 수 없고 나눗셈도 필요 없다.

    자바의 hashCode(): 모든 객체가 가진 해시 함수

    문자열에 해시 함수가 필요했듯, 셋에 넣으려는 모든 타입에 "나를 정수로 바꾸는 방법"이 필요하다. 자바는 이 메서드를 최상위 클래스 Object에 두었다. public int hashCode()다. 모든 클래스가 Object를 상속하므로 어떤 객체에든 hashCode()를 부를 수 있고, 클래스마다 자기 내용에 맞게 재정의한다. API 문서는 이 메서드가 HashMap 같은 해시 테이블을 위해 존재한다고 밝히고, 지켜야 할 일반 규약 세 가지를 적는다.

    1. 일관성. 한 번의 프로그램 실행 안에서, equals 비교에 쓰이는 정보가 바뀌지 않았다면 같은 객체의 hashCode는 몇 번을 불러도 같은 정수여야 한다. 실행과 실행 사이에서는 값이 달라도 된다.
    2. equals가 같으면 hashCode도 같다. 두 객체가 equals로 같다면 두 객체의 hashCode는 반드시 같은 정수여야 한다.
    3. 역은 요구하지 않는다. equals로 다른 두 객체가 서로 다른 hashCode를 가질 필요는 없다. 다만 다른 객체에 다른 값을 주면 해시 테이블의 성능이 좋아질 수 있다.

    둘째와 셋째를 합치면 방향이 하나뿐인 화살표가 된다. "같은 객체 → 같은 해시 코드"는 의무이고, "같은 해시 코드 → 같은 객체"는 성립하지 않아도 된다. 앞에서 본 "Aa"와 "BB"가 셋째 항목의 실례다. 첫째 항목의 "실행 사이에서는 달라도 된다"도 기억해 둔다. 해시 코드를 파일이나 DB에 저장해 두고 다음 실행에서 비교하는 코드는 이 규약에 기대어서는 안 된다.

    일상에서 가져온 비유우편번호와 주소

    우편물은 먼저 우편번호로 분류함을 정하고, 그 분류함 안에서 주소를 읽어 받는 집을 가린다. 같은 집이면 우편번호가 반드시 같아야 한다. 그렇지 않으면 우편물이 엉뚱한 분류함으로 가서 영영 찾지 못한다. 반대로 우편번호가 같다고 같은 집은 아니다. hashCode가 우편번호, equals가 주소 대조다. 비유가 맞지 않는 곳도 있다. 우편번호는 기관이 정해 주고 오래 유지되지만, 해시 코드는 객체가 자기 내용으로 직접 계산하고 프로그램을 다시 실행하면 달라질 수 있다.

Objects.hashCode(null)은 0이다. null에는 메서드를 부를 수 없으므로 null의 해시 코드를 0으로 치는 관례를 메서드로 만든 것이다.

    String에는 한 가지 장치가 더 있다. 문자열은 불변이라 해시 코드가 변할 일이 없으므로, OpenJDK 21의 String은 처음 계산한 값을 hash 필드에 저장해 두고 다음부터는 그 값을 돌려준다. 계산 결과가 마침 0인 경우를 "아직 계산하지 않음"과 구분하기 위한 hashIsZero 필드도 따로 둔다. 같은 문자열을 해시 셋에서 여러 번 찾아도 긴 문자열 전체를 매번 다시 훑지 않는 이유다.

    한 층 아래: Object의 기본 hashCode는 어디에서 오는가

    클래스가 hashCode()를 재정의하지 않으면 Object의 구현이 쓰인다. 소스에서 이 메서드는 public native int hashCode();로, 자바 코드가 아니라 JVM이 값을 만들어 준다. API 문서가 이 기본 구현에 대해 말하는 것은 한 문장뿐이다. 합리적으로 가능한 한 서로 다른 객체에 서로 다른 정수를 돌려준다는 것이다. 내용이 같은지는 전혀 보지 않고 "어느 객체인가"만으로 정해지는 값이어서 이것을 identity hash code라고 부른다.

    public class IdentityHashDemo {
    public static void main(String[] args) {
        Object o1 = new Object();
        Object o2 = new Object();
        System.out.println(o1.hashCode() + " " + o2.hashCode());
        System.out.println(o1.hashCode() == System.identityHashCode(o1));
        System.out.println(o1 + " / " + Integer.toHexString(o1.hashCode()));

        int before = o1.hashCode();
        System.gc();
        System.out.println(before == o1.hashCode());

        String s = new String("AB");
        System.out.println(s.hashCode() + " " + System.identityHashCode(s));
    }
}

    첫 줄의 두 숫자와 마지막 줄의 둘째 숫자는 환경에 따라 달라진다. 변하지 않는 것은 관계다. 둘째 줄은 재정의하지 않은 hashCode()가 System.identityHashCode()와 같은 값이라는 것, 셋째 줄은 Object.toString()이 출력하는 @ 뒤의 16진수가 해시 코드를 16진수로 적은 것이라는 점을 보여 준다(Object.toString()의 구현이 getClass().getName() + "@" + Integer.toHexString(hashCode())다). 넷째 줄은 GC를 요청한 뒤에도 값이 같다는 것, 다섯째 줄은 String처럼 hashCode를 재정의한 클래스에서도 System.identityHashCode()로 기본 값을 따로 얻을 수 있다는 것을 보여 준다.

    메모리 주소가 아니다

    "hashCode의 기본값은 객체의 메모리 주소"라는 설명이 널리 퍼져 있지만, Java 21의 API 문서에는 주소라는 말이 없고 HotSpot의 기본 동작도 그렇지 않다. OpenJDK 21 HotSpot에서 identity hash를 만드는 코드(synchronizer.cpp의 get_next_hash)는 hashCode라는 실험용 VM 옵션 값에 따라 방식을 고르는데, 기본값은 5이고 이 경우 스레드마다 가진 상태로 xor-shift 방식의 의사 난수를 만들어 쓴다. 주소를 그대로 쓰는 방식은 옵션 값 4로만 선택할 수 있는 대안이다. 기본값은 다음 명령으로 확인할 수 있다.

    java -XX:+UnlockExperimentalVMOptions -XX:+PrintFlagsFinal -version | grep hashCode
# intx hashCode = 5   {experimental} {default}

    주소를 쓰지 않는 까닭은 규약의 첫째 항목에서 나온다. HotSpot의 가비지 컬렉터는 살아 있는 객체를 다른 위치로 옮긴다. 주소가 곧 해시 코드라면 GC가 지나갈 때마다 해시 코드가 바뀌고, 해시 셋에 넣어 둔 객체는 옮겨진 뒤 엉뚱한 버킷에서 찾게 된다. 한 실행 안에서 값이 변하지 않아야 한다는 규약을 지키려면 값이 객체의 위치와 무관해야 한다.

    그래서 HotSpot은 identity hash를 한 번 만들어 객체에 적어 둔다. 모든 객체의 앞머리에는 마크 워드(mark word)라는 헤더가 있고, 64비트 HotSpot(OpenJDK 21)에서는 그 가운데 31비트가 해시 자리다. 객체가 처음 만들어질 때 이 자리는 비어 있다(0이 "아직 없음"을 뜻한다). hashCode()가 처음 불릴 때 값을 생성해 CAS로 헤더에 써 넣고, 그 뒤 호출은 헤더에서 읽기만 한다. GC가 객체를 옮길 때는 헤더도 함께 옮겨지므로 값이 유지된다. 잠금이 무거운 모니터로 팽창한 객체는 모니터가 보관하는 헤더 사본에 값이 들어가지만 원리는 같다.

    new Object() 직후               hashCode() 첫 호출 뒤            GC가 객체를 옮긴 뒤
┌──────────────────────┐        ┌──────────────────────┐        ┌──────────────────────┐
│ mark word            │        │ mark word            │        │ mark word            │
│   hash 자리 = 0 (없음)│  ───▶  │   hash 자리 = 생성값  │  ───▶  │   hash 자리 = 같은 값 │
│ 클래스 포인터          │        │ 클래스 포인터          │        │ 클래스 포인터          │
└──────────────────────┘        └──────────────────────┘        └──────────────────────┘
  주소 X                           주소 X                           주소 Y (바뀜)
    기본 hashCode가 주소가 아니라 헤더에 저장된 값이라는 점, 그래서 객체가 옮겨져도 변하지 않는다는 점을 세 장면으로 보여 준다. 가로형 16:9, 왼쪽에서 오른쪽으로 이어지는 세 장면. 각 장면에는 위아래 두 칸으로 나뉜 객체 상자가 있다. 위 칸 라벨은 "마크 워드", 아래 칸 라벨은 "필드". 첫 장면 제목 "객체 생성 직후": 마크 워드 칸 안에 작은 슬롯을 그리고 "hash: 비어 있음"이라고 적는다. 둘째 장면 제목 "hashCode() 첫 호출": 주사위 아이콘에서 슬롯으로 화살표를 그리고 슬롯에 "hash: 2a139a55"를 적는다. 셋째 장면 제목 "GC가 객체를 이동": 객체 상자가 힙 영역의 다른 위치로 옮겨진 모습을 점선 화살표로 표현하고 슬롯에는 여전히 "hash: 2a139a55"를 적는다. 각 장면 아래에 주소 라벨을 붙인다: 첫째와 둘째는 "주소 X", 셋째는 "주소 Y". 맨 아래에 강조 문구 "주소는 바뀌어도 해시 코드는 그대로"를 넣는다. 흰 배경, 차분한 파랑과 회색, 평면적인 선 그림. 기본 해시 코드는 처음 요청될 때 만들어져 객체 헤더에 저장된다. 객체의 위치와는 무관하다.

    이 절에서 가져갈 결론은 하나다. new로 만든 두 객체는 필드 값이 완전히 같아도 기본 hashCode가 서로 다르다. 내용이 아니라 객체마다 따로 만들어 붙인 값이기 때문이다. 이 사실이 뒤에서 직접 만든 객체를 셋에 넣을 때 문제를 일으킨다.

    2단계: 모든 객체를 담는 해시 셋

    이제 정수 전용 셋을 일반화할 수 있다. 바꿀 곳은 두 군데다. 원소 타입을 Object로 넓히고, 인덱스를 값 자체가 아니라 value.hashCode()에서 구한다. 음수 해시 코드에 대비해 나머지 연산도 Math.floorMod로 바꾼다.
