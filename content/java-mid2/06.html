    리스트와 세트 — 약속이 다르면 구현의 자유도 다르다

    앞의 세 회차에서 다룬 자료 구조는 모두 리스트였다. 배열 리스트든 연결 리스트든 리스트는 같은 계약을 지킨다. 요소에 순서가 있고, 같은 값을 여러 번 넣을 수 있으며, 정수 인덱스로 위치를 지정해 꺼낼 수 있다. Java SE 21 API 문서는 List를 "An ordered collection, where the user has precise control over where in the list each element is inserted"라고 정의한다.

    세트(Set)는 계약이 다르다. Set 문서의 첫 문장은 "A collection that contains no duplicate elements"이고, 이 인터페이스가 수학의 집합을 본뜬 것이라고 밝힌다. 수학의 집합 {1, 2, 5}에는 "첫 번째 원소"라는 개념이 없고, 1을 두 번 적어도 같은 집합이다. 세트도 그렇다. 같은 값은 한 번만 들어가고, 인덱스로 요소를 꺼내는 연산이 없으며, 인터페이스 차원에서는 요소의 순서를 약속하지 않는다.

    쓰임새도 여기서 갈린다. 가입하려는 아이디가 이미 쓰이고 있는지, 이 주소를 이미 방문했는지, 방금 뽑은 번호가 앞에서 뽑은 번호와 겹치는지 묻는 일은 모두 "값이 들어 있는가"를 묻는 일이다. 그래서 세트의 성능은 값의 존재 여부를 확인하는 contains가 좌우한다. 넣는 연산도 예외가 아니다. 중복을 막으려면 넣기 전에 이미 있는지 확인해야 하므로 add 안에는 언제나 contains가 숨어 있다.

    계약이 약하다는 것은 구현이 자유롭다는 뜻이기도 하다. 리스트는 "넣은 순서대로 i번째"를 약속했기 때문에 요소가 놓일 자리를 구현이 마음대로 고를 수 없다. 세트는 자리를 약속하지 않았으므로 구현이 요소를 찾기 좋은 자리에 둘 수 있다. 이 회차는 이 한 문장을 끝까지 밀고 가는 과정이다. 먼저 자리를 고르지 않는 세트를 만들어 왜 느린지 확인하고, 값이 스스로 자기 자리를 정하게 만든 다음, 그 방법이 치러야 하는 대가를 하나씩 해결한다.

    순서를 약속하지 않는다는 것은 순서가 있으면 안 된다는 뜻이 아니다. 넣은 순서나 정렬 순서를 지키는 세트 구현도 있고, 이 권의 08회에서 다룬다. 이 회차는 순서를 포기했을 때 무엇을 얻는지에 집중한다.

    배열로 만든 첫 번째 세트 — 넣을 때마다 전수 조사

    가장 단순한 세트부터 만든다. 문제를 작게 유지하려고 요소는 int로 한정한다. 배열에 값을 차례로 채우되, 넣기 전에 같은 값이 있는지 확인하는 것이 전부다.

    import java.util.Arrays;

public class ArrayIntSet {
    private int[] elements = new int[10];
    private int size;

    public boolean add(int value) {
        if (contains(value)) {
            return false;
        }
        if (size == elements.length) {
            elements = Arrays.copyOf(elements, size * 2);
        }
        elements[size++] = value;
        return true;
    }

    public boolean contains(int value) {
        for (int i = 0; i < size; i++) {
            if (elements[i] == value) {
                return true;
            }
        }
        return false;
    }

    public int size() {
        return size;
    }

    @Override
    public String toString() {
        return Arrays.toString(Arrays.copyOf(elements, size));
    }
}
    public class ArrayIntSetMain {
    public static void main(String[] args) {
        ArrayIntSet set = new ArrayIntSet();
        System.out.println(set.add(1));
        System.out.println(set.add(2));
        System.out.println(set.add(5));
        System.out.println(set.add(8));
        System.out.println(set.add(5));
        System.out.println(set + ", size=" + set.size());
        System.out.println(set.contains(8));
        System.out.println(set.contains(99));
    }
}

    두 번째 add(5)를 따라가 보자. contains(5)가 elements[0]의 1, elements[1]의 2와 차례로 비교하고 elements[2]에서 5를 찾아 true를 돌려준다. add는 아무것도 넣지 않고 false를 반환한다. 세트의 계약은 지켜졌다. 문제는 그 계약을 지키는 데 든 비용이다.

    새로운 값을 넣는 경우가 더 나쁘다. 없는 값을 찾는 탐색은 끝까지 가야 "없다"고 말할 수 있으므로 언제나 최악의 경우다. 요소가 k개 들어 있는 세트에 새 값을 넣으면 정확히 k번 비교한 뒤에야 배열 끝에 값을 쓴다. 빈 세트에서 시작해 서로 다른 값 n개를 넣으면 비교 횟수는 0 + 1 + 2 + … + (n-1) = n(n-1)/2다. 비교 연산에 카운터를 달아 실제로 세어 보면 이 식 그대로 나온다.

    값의 개수가 10배가 되면 비교 횟수는 100배가 된다. add 한 번이 O(n)이고, n개를 채우는 전체 비용이 O(n²)이기 때문이다. 03회에서 배열 리스트의 add는 배열이 가득 찰 때의 복사까지 포함해도 분할 상환 O(1)이었다. 같은 배열에 "중복 없음"이라는 약속 하나를 더했을 뿐인데 넣는 비용이 O(n)으로 올라간 것이다. 배열을 두 배로 늘리는 복사는 여기서도 분할 상환 O(1)이므로 원인이 아니다. 원인은 오직 매번 실행되는 탐색이다.

    연결 리스트로 바꿔도 달라지지 않는다. 연결 리스트 역시 값으로 찾으려면 첫 노드부터 차례로 비교해야 한다. 결국 세트를 빠르게 만든다는 것은 "값으로 찾기"를 빠르게 만든다는 것과 같은 말이다.

    느린 이유 — 값과 위치 사이에 아무 관계가 없다

    방금 만든 세트의 배열 [1, 2, 5, 8]에서 8은 왜 인덱스 3에 있는가. 네 번째로 넣었기 때문이다. 8이라는 값 자체는 위치를 정하는 데 아무 역할도 하지 않았다. 5를 나중에 넣었다면 8은 인덱스 2에 있었을 것이다. 위치를 결정한 것은 값이 아니라 넣은 이력이다.

    그래서 "8이 들어 있는가"라는 질문을 받았을 때 후보를 좁힐 단서가 없다. 8이 있다면 어느 칸에 있을지 값만 보고는 알 수 없으니 모든 칸을 확인하는 수밖에 없다. 반대 방향의 질문인 "인덱스 3에 무엇이 있는가"는 사정이 전혀 다르다. 배열은 시작 위치에 인덱스만큼의 거리를 더해 그 칸으로 바로 가므로 요소가 몇 개든 한 번에 끝난다.

    인덱스 → 값 :  elements[3] 은?   ──(위치 계산 1번)──▶  8

값 → 인덱스 :  8 은 어디에?     ──▶ [0]=1 ✗ ──▶ [1]=2 ✗ ──▶ [2]=5 ✗ ──▶ [3]=8 ✓
                                     (요소가 n개면 최대 n번)

    배열은 인덱스에서 값으로 가는 방향으로만 빠르다. 그렇다면 발상을 바꿀 수 있다. 값에서 인덱스를 계산할 수 있게 만들면 "값으로 찾기"가 "계산한 인덱스로 찾기"로 바뀌고, 배열이 잘하는 방향의 연산이 된다. 값을 넣을 때 그 값으로 계산한 자리에 넣고, 찾을 때 같은 계산을 해서 그 자리만 본다. 해시 알고리즘은 이 생각에서 출발한다.

    일상에서 가져온 비유도착한 순서대로 쌓은 우편물과 호수별 우편함

    공동 현관에 우편물을 도착한 순서대로 쌓아 두면 302호 우편물이 왔는지 알려면 더미를 다 넘겨 봐야 한다. 호수가 적힌 우편함이 있으면 302번 함만 열면 된다. 우편물의 주소가 곧 놓일 자리를 정해 주기 때문이다. 비유가 깨지는 지점은 우편함의 개수다. 건물의 호수는 몇백 개로 정해져 있지만 프로그램이 다루는 값의 범위는 훨씬 넓어서, 값마다 함을 하나씩 만들어 둘 수 없다. 뒤에서 다루는 문제가 바로 이것이다.

    값을 인덱스로 쓴다 — 직접 주소 지정

    가장 단순한 계산은 계산을 하지 않는 것이다. 값 자체를 인덱스로 쓴다. 1은 1번 칸에, 8은 8번 칸에 넣는다.

    import java.util.Arrays;

public class DirectIndexMain {
    public static void main(String[] args) {
        Integer[] table = new Integer[10];
        table[1] = 1;
        table[2] = 2;
        table[5] = 5;
        table[8] = 8;
        System.out.println(Arrays.toString(table));

        int search = 8;
        System.out.println(table[search] != null);
        search = 7;
        System.out.println(table[search] != null);
    }
}

    배열의 타입을 int[]가 아니라 Integer[]로 둔 데는 이유가 있다. int[]의 빈칸은 0으로 채워지므로 "비어 있음"과 "0이 들어 있음"을 구분할 수 없다. 참조 배열은 빈칸이 null이라서 구분이 된다. 값의 존재 여부만 필요하다면 boolean[]로도 충분하지만, 조금 뒤에 한 칸이 여러 값의 후보 자리가 되면 칸에 실제 값을 넣어 두어야 하므로 미리 값을 담는 형태로 시작한다.

    8이 있는지 확인하는 코드는 table[8] 한 줄이다. 반복문이 없다. 요소가 4개든 4만 개든 배열 접근 한 번이므로 O(1)이다. 넣는 것도 table[value] = value 한 줄이고, 중복 검사는 따로 할 필요조차 없다. 같은 값을 두 번 넣으면 같은 칸에 같은 값을 두 번 쓸 뿐이다. 지우는 것은 table[value] = null이다. 세트의 세 연산이 모두 O(1)이 되었다.

    배열 접근이 요소 개수와 무관한 이유는 03회에서 본 그대로다. 배열의 칸은 크기가 같고 연속해 있으므로 i번째 칸의 위치는 배열의 시작 위치에서 곱셈과 덧셈 한 번으로 구해진다. 자바는 여기에 범위 검사를 더한다. JLS §10.4는 모든 배열 접근이 실행 시점에 검사되며 인덱스가 0보다 작거나 길이 이상이면 ArrayIndexOutOfBoundsException을 던진다고 정한다. 범위 검사도 비교 두 번이면 끝나는 일이라 O(1)이라는 결론은 바뀌지 않는다.

    이렇게 값을 그대로 주소로 쓰는 방식을 직접 주소 지정(direct addressing)이라고 부르고, 이렇게 쓰는 배열을 직접 주소 테이블(direct-address table)이라고 한다. 탐색 문제가 사라진 것처럼 보인다. 그런데 이 코드에는 숨은 전제가 하나 있다. 값이 0에서 9 사이라는 것이다.

    같은 값 8을 찾을 때, 넣은 순서대로 채운 배열은 여러 칸을 차례로 비교하고 값을 인덱스로 쓴 배열은 한 칸만 보는 차이를 한눈에 보여 준다. 깔끔한 교육용 평면 다이어그램, 흰 배경, 위아래 2단 구성. 위쪽 단 왼쪽에 제목 라벨 "넣은 순서대로 저장". 가로로 붙은 네모 칸 4개에 숫자 1, 2, 5, 8이 차례로 들어 있고 칸 아래에 작은 인덱스 0, 1, 2, 3. 왼쪽에서 오른쪽으로 칸마다 하나씩 화살표 4개가 차례로 닿으며 앞의 세 화살표에는 회색 X 표시, 마지막 화살표에는 초록 체크 표시. 오른쪽에 라벨 "비교 4번". 아래쪽 단 왼쪽에 제목 라벨 "값을 인덱스로 저장". 가로로 붙은 네모 칸 10개, 칸 아래 인덱스 0부터 9, 그중 1번, 2번, 5번, 8번 칸에만 각각 숫자 1, 2, 5, 8이 들어 있고 나머지는 옅은 회색 빈칸. 위에서 8번 칸으로 곧장 내려오는 굵은 화살표 하나와 라벨 "table[8]". 오른쪽에 라벨 "접근 1번". 색은 파랑과 회색 위주, 강조는 초록. 넣은 순서가 위치를 정하면 값으로 찾을 때 차례로 비교해야 하고, 값이 위치를 정하면 한 칸만 보면 된다.

    대가 — 칸 수가 값의 범위를 따라간다

    세트에 99를 넣고 싶다면 table[99]가 존재해야 하므로 배열 길이가 최소 100이어야 한다. 1,000,000을 넣고 싶다면 길이가 1,000,001이어야 한다. 넣은 값이 1, 2, 5, 8, 99, 1000000 여섯 개뿐이어도 그렇다. 직접 주소 테이블에 필요한 칸 수는 값의 개수가 아니라 값이 가질 수 있는 범위가 정한다.

    세트가 int 전체를 받는다면 범위는 232, 즉 4,294,967,296가지다. 칸 하나의 크기를 알아야 메모리를 계산할 수 있다. 이 원고를 쓰며 사용한 OpenJDK 21 HotSpot(압축 참조가 켜진 기본 설정)에서 클래스 히스토그램으로 재 보면 Integer[1000000] 배열은 4,000,016바이트다. 배열 헤더 16바이트에 참조 한 칸당 4바이트씩이다. 이 단가로 232칸을 잡으면 참조만 16GiB이고, 값이 들어간 칸마다 16바이트짜리 Integer 객체가 추가로 필요하다. 값 여섯 개를 넣으려고 16GiB를 잡는 셈이다.

    사실 이 배열은 만들 수조차 없다. JLS §10.4에 따라 배열은 int 값으로만 인덱싱되고, long 인덱스는 컴파일 오류다. 음수 인덱스는 허용되지 않으니 배열 하나가 가질 수 있는 칸은 많아야 231-1개이고 음수 값은 인덱스로 쓸 수 없다. 한계 근처도 순탄하지 않다. OpenJDK 21 HotSpot에서 다음 한 줄은 힙을 16GB로 늘려 실행해도 같은 오류로 끝난다.

    Integer[] table = new Integer[Integer.MAX_VALUE];
// java.lang.OutOfMemoryError: Requested array size exceeds VM limit

    칸의 단가를 극단까지 줄여도 문제의 성격은 그대로다. 값의 존재 여부만 기록하기로 하고 칸 하나를 1비트로 줄이면 232비트, 512MiB가 된다. 16GiB보다는 훨씬 작지만 여전히 값의 개수와 무관하게 범위만큼 쓴다. 범위가 long이 되면 264칸이 필요하고, 문자열처럼 길이에 제한이 없는 값이면 범위 자체가 끝이 없다.

    공간만 낭비되는 것도 아니다. 자바에서 배열을 만들면 모든 칸이 기본값으로 초기화되므로, 테이블을 만드는 일 자체가 범위에 비례하는 시간이 든다. 세트의 모든 요소를 순회하는 일도 범위만큼의 칸을 훑어야 한다. 값이 여섯 개인데 순회에 40억 칸을 보는 구조는 받아들이기 어렵다.

    정리하면 직접 주소 지정은 시간을 O(1)로 만드는 대신 공간을 값의 범위만큼 쓴다. 범위가 작고 값이 빽빽하게 들어차는 경우에는 이것이 가장 좋은 방법이다. 0부터 999까지의 번호가 쓰였는지 기록하는 일이라면 길이 1,000의 배열이 어떤 자료 구조보다 빠르고 작다. 표준 라이브러리에도 이런 구조가 있다. java.util.BitSet은 음이 아닌 정수로 인덱싱되는 비트 벡터이고, EnumSet은 문서에서 내부 표현이 비트 벡터라고 밝힌다. 문제는 범위가 넓고 값이 드문드문 있을 때다. 우리가 원하는 것은 "값에서 위치를 계산한다"는 성질은 유지하면서 칸 수는 값의 개수 정도로 묶어 두는 방법이다.

    범위를 접는다 — 나머지 연산과 해시 인덱스

    칸을 10개만 쓰기로 정했다고 하자. 필요한 것은 어떤 int 값이든 0에서 9 사이의 숫자로 바꿔 주는 계산이다. 초등학교에서 배운 나머지가 정확히 그 일을 한다. 음이 아닌 정수를 10으로 나눈 나머지는 언제나 0에서 9 사이다.

    자바의 %가 무엇을 계산하는지는 JLS §15.17.3이 정한다. 정수 피연산자에 대해 (a/b)*b+(a%b)가 a와 같아지는 값이 나머지다. 14는 1×10+4이므로 14 % 10은 4이고, 99는 9×10+9이므로 99 % 10은 9다. 100칸이 필요했던 값 99가 10칸짜리 배열의 마지막 칸에 들어간다. 넓은 범위의 수직선을 10칸 길이로 잘라 차곡차곡 겹쳐 접은 것과 같다.

    import java.util.Arrays;

public class ModIndexMain {
    static final int CAPACITY = 10;

    static int hashIndex(int value) {
        return value % CAPACITY;
    }

    public static void main(String[] args) {
        Integer[] table = new Integer[CAPACITY];
        int[] values = {1, 2, 5, 8, 14, 99};
        for (int value : values) {
            int index = hashIndex(value);
            table[index] = value;
            System.out.println(value + " -> " + index);
        }
        System.out.println(Arrays.toString(table));

        System.out.println(contains(table, 14));
        System.out.println(contains(table, 4));
        System.out.println(contains(table, 3));
    }

    static boolean contains(Integer[] table, int value) {
        Integer stored = table[hashIndex(value)];
        return stored != null && stored == value;
    }
}

    조회 세 번을 차례로 추적한다. contains(table, 14)는 14 % 10 = 4를 계산해 4번 칸을 본다. 거기에 14가 있고 찾는 값과 같으므로 true다. contains(table, 3)은 3번 칸이 null이므로 false다. 눈여겨볼 것은 가운데의 contains(table, 4)다. 4 % 10도 4이므로 같은 4번 칸을 본다. 칸은 비어 있지 않다. 하지만 들어 있는 값은 14이고 찾는 값은 4이므로 답은 false다.

    직접 주소 지정에서는 칸이 비어 있지 않다는 사실이 곧 값이 있다는 뜻이었다. 범위를 접고 나면 그렇지 않다. 4번 칸은 4, 14, 24, 34, … 가 모두 자기 자리라고 주장하는 칸이다. 칸에 무엇인가 있다는 것만으로는 부족하고, 들어 있는 값이 찾는 값과 같은지 반드시 비교해야 한다. 테이블에 boolean이 아니라 값 자체를 넣어 둔 이유가 이것이다. stored == value에서 Integer와 int를 비교하면 Integer가 언박싱되어 값끼리 비교된다는 점도 확인해 둔다.

    용어를 정리한다. 임의의 값을 정해진 범위의 숫자로 바꾸는 함수를 해시 함수(hash function)라고 하고, 그 결과를 배열 인덱스로 쓸 때 해시 인덱스(hash index)라고 부른다. 해시 인덱스로 자리를 정하는 배열이 해시 테이블(hash table)이다. 이 회차의 해시 함수는 "칸 수로 나눈 나머지"다. 해시 함수가 갖춰야 할 조건은 지금까지의 과정에 이미 들어 있다.

    • 결정적이어야 한다. 같은 값은 언제 계산해도 같은 인덱스가 나와야 한다. 넣을 때와 찾을 때 계산 결과가 다르면 넣어 둔 값을 찾을 수 없다.
    • 결과가 배열 범위 안이어야 한다. 0 이상이고 칸 수보다 작아야 한다. 바로 뒤에서 이 조건이 깨지는 경우를 본다.
    • 계산이 싸야 한다. 탐색을 없애려고 넣은 계산이 탐색보다 비싸면 의미가 없다.
    • 값을 칸에 고르게 퍼뜨려야 한다. 여러 값이 한 칸에 몰리면 어떤 일이 생기는지는 충돌을 다룰 때 본다.
    자바의 해시 자료 구조는 이 계산을 두 단계로 나눈다. 객체를 int로 바꾸는 단계(hashCode())와 그 int를 배열 인덱스로 줄이는 단계다. 이 회차는 요소가 처음부터 int라서 둘째 단계만 다룬다. 문자열이나 직접 만든 객체를 int로 바꾸는 첫째 단계는 07회의 몫이다.
    긴 수직선 위의 값들이 10으로 나눈 나머지에 따라 10칸짜리 배열의 칸으로 모이는 모습, 그리고 서로 다른 값이 같은 칸을 가리킬 수 있음을 보여 준다. 깔끔한 교육용 평면 다이어그램, 흰 배경. 위쪽에 왼쪽에서 오른쪽으로 긴 수직선이 있고 0, 10, 20, 90, 100 위치에 눈금. 수직선 위에 점 여섯 개가 찍혀 있고 각각 숫자 1, 2, 5, 8, 14, 99 라벨. 수직선 위 제목 라벨 "값의 범위". 가운데에 둥근 상자 하나, 안에 문구 "값 % 10". 아래쪽에 가로로 붙은 네모 칸 10개, 칸 아래 인덱스 0부터 9, 제목 라벨 "칸 10개짜리 배열". 수직선의 각 점에서 가운데 상자를 거쳐 아래 배열 칸으로 화살표: 1은 1번 칸, 2는 2번 칸, 5는 5번 칸, 8은 8번 칸, 14는 4번 칸, 99는 9번 칸. 14와 99에서 나오는 화살표는 주황색으로 강조. 배열 4번 칸 안에 14, 9번 칸 안에 99, 나머지 해당 칸에도 각 숫자 표시. 4번 칸 옆에 작은 말풍선 라벨 "4, 14, 24 ... 의 자리". 색은 파랑, 회색, 주황 강조. 나머지 연산은 넓은 범위를 칸 수만큼의 구간으로 접는다. 한 칸은 여러 값의 공통 자리가 된다.

    나머지 연산의 경계 — 음수, 그리고 비트 마스크

    앞에서 "음이 아닌 정수를 10으로 나눈 나머지는 0에서 9 사이"라고 조건을 달았다. int의 절반은 음수이므로 이 조건을 그냥 넘어갈 수 없다. JLS §15.17.3은 항등식 (a/b)*b+(a%b) == a에서 따라 나오는 결과로, 나머지가 음수가 될 수 있는 것은 나누어지는 수가 음수일 때뿐이라고 적는다. 자바의 정수 나눗셈은 0 쪽으로 버리므로 -7 / 10은 0이고, 항등식을 맞추려면 -7 % 10은 -7이어야 한다.

    Integer[] table = new Integer[10];
table[-7 % 10] = -7;
// java.lang.ArrayIndexOutOfBoundsException: Index -7 out of bounds for length 10

    해시 인덱스가 배열 범위를 벗어났다. 음수를 받을 수 있는 해시 테이블은 인덱스를 0 이상으로 만드는 처리가 꼭 필요하고, 흔히 쓰는 방법이 네 가지 있다. 그중 하나는 함정이다.

    • Math.floorMod(value, capacity) — 결과의 부호가 나누는 수를 따른다. 구현은 %로 구한 나머지가 0이 아니고 두 수의 부호가 다르면 나누는 수를 한 번 더해 주는 것이 전부다. Math.floorMod(-7, 10)은 3이다.
    • Math.abs(value) % capacity — 함정이다. Math.abs의 문서는 인자가 Integer.MIN_VALUE이면 결과가 그 값 그대로, 즉 음수라고 명시한다. int로 표현할 수 있는 가장 큰 양수가 2,147,483,647이라 2,147,483,648을 담을 수 없기 때문이다. Math.abs(Integer.MIN_VALUE) % 10은 -8이다.
    • (value & 0x7FFFFFFF) % capacity — 부호 비트를 0으로 지워 음이 아닌 수로 만든 다음 나머지를 구한다. OpenJDK 21의 java.util.Hashtable이 (hash & 0x7FFFFFFF) % tab.length로 이 방법을 쓴다.
    • value & (capacity - 1) — 칸 수가 2의 거듭제곱일 때만 쓸 수 있다. OpenJDK 21의 java.util.HashMap이 버킷 인덱스를 (n - 1) & hash로 구해 이 방법을 쓴다.

    마지막 방법이 왜 성립하는지 보자. 칸 수가 16이면 capacity - 1은 15, 이진수로 1111이다. 이 값과 AND를 하면 아래 4비트만 남고 나머지는 0이 된다. 아래 4비트가 나타낼 수 있는 수는 0에서 15이므로 결과는 언제나 배열 범위 안이다. 음수도 예외가 아니다. -7은 2의 보수 표현으로 11111111111111111111111111111001이고 아래 4비트 1001은 9다. Math.floorMod(-7, 16)도 9다. 2의 보수에서 아래 k비트를 남기는 일과 2k로 나눈 음이 아닌 나머지를 구하는 일은 같은 계산이다.

    표에서 -7의 행을 보면 방법마다 인덱스가 3, 1, 9로 다르다. 틀린 것이 아니다. 해시 인덱스에 정답이 있는 것이 아니라, 한 테이블 안에서 넣을 때와 찾을 때 같은 함수를 쓴다는 일관성만 지켜지면 된다. 반대로 음수 인덱스는 어떤 테이블에서도 쓸 수 없으므로 %만 쓴 첫 번째 열은 음수 값이 들어오는 순간 예외로 끝난다.

    Math.abs 함정이 위험한 이유는 드러나는 조건이 좁기 때문이다. 약 43억 개의 int 값 가운데 단 하나에서만 문제가 생긴다. 게다가 칸 수가 16처럼 2의 거듭제곱이면 Integer.MIN_VALUE % 16이 0이라서 예외조차 나지 않는다. 테스트는 모두 통과하고, 어느 날 특정 입력과 특정 칸 수가 만났을 때만 터진다. 경계값을 손으로 계산해 보지 않으면 찾기 어려운 종류의 버그다.

    비트 마스크 방식에는 다른 종류의 약점이 있다. 아래쪽 비트만 인덱스에 반영되므로, 위쪽 비트만 다른 값들은 전부 같은 칸으로 간다. 칸 수가 16일 때 16의 배수는 아래 4비트가 모두 0이라 전부 0번 칸이다. OpenJDK의 HashMap 소스는 주석에서 이 문제를 직접 언급하고, 인덱스를 구하기 전에 해시 값의 위쪽 16비트를 아래쪽에 XOR해 섞는다. 그 세부는 09회에서 다룬다.

    나누는 수가 0이면 어떻게 되는지도 확인해 둔다. JLS는 정수 나머지 연산에서 나누는 수가 0이면 ArithmeticException을 던진다고 정한다. 칸 수가 0인 해시 테이블은 만들 수 없다는 뜻이다. 이 회차의 나머지 코드는 음수에도 안전한 Math.floorMod를 쓴다.

    해시 충돌 — 피할 수 없는 이유와 생각보다 잦은 이유

    지금까지의 예제는 값을 조심스럽게 골랐다. 1, 2, 5, 8, 14, 99는 10으로 나눈 나머지가 모두 다르다. 여기에 9를 하나 더 넣어 본다.

    import java.util.Arrays;

public class CollisionMain {
    public static void main(String[] args) {
        Integer[] table = new Integer[10];
        table[99 % 10] = 99;
        table[9 % 10] = 9;
        System.out.println(Arrays.toString(table));

        Integer stored = table[99 % 10];
        System.out.println(stored != null && stored == 99);
    }
}

    99와 9는 둘 다 9번 칸이 자기 자리다. 나중에 들어온 9가 99를 덮어썼고, 분명히 넣었던 99는 사라졌다. 예외도 경고도 없다. 서로 다른 값이 같은 해시 인덱스를 갖는 이 상황을 해시 충돌(hash collision)이라고 한다. 충돌을 처리하지 않는 해시 테이블은 데이터를 조용히 잃어버리므로 쓸 수 없다.

    충돌은 왜 피할 수 없는가

    더 좋은 해시 함수를 고르면 충돌을 없앨 수 있을까. 없앨 수 없다. 비둘기 11마리를 비둘기집 10칸에 넣으면 어느 칸에는 반드시 두 마리 이상이 들어간다. 이것을 비둘기집 원리(pigeonhole principle)라고 한다. int 값은 약 43억 가지이고 칸은 10개다. 어떤 함수를 쓰든 한 칸은 평균 4억 개가 넘는 서로 다른 값의 공통 자리가 된다. 범위를 접어 칸 수를 줄이기로 한 순간 충돌은 선택이 아니라 구조의 일부가 된다. 충돌을 완전히 없애는 유일한 방법은 칸 수를 값의 범위만큼 늘리는 것인데, 그것은 방금 버리고 온 직접 주소 지정이다.

    충돌은 얼마나 자주 생기는가

    칸이 10개이고 값이 4개뿐이라면 충돌이 드물 것 같지만 계산해 보면 그렇지 않다. 값이 칸에 고르게 무작위로 떨어진다고 가정하자. 첫 값은 어느 칸이든 괜찮다. 둘째 값이 첫 값을 피할 확률은 9/10, 셋째 값이 앞의 둘을 피할 확률은 8/10, 넷째는 7/10이다. 네 값이 모두 다른 칸에 들어갈 확률은 0.9 × 0.8 × 0.7 = 0.504이고, 한 번이라도 충돌할 확률은 49.6%다.

    칸 10개에 넣은 값의 개수23457

    칸의 40%만 채워도 충돌 확률이 절반이다. 칸을 늘려도 성질은 같다. 칸이 365개일 때 값 23개면 충돌 확률이 50.73%로 절반을 넘는다. 23명이 모이면 생일이 같은 쌍이 있을 확률이 절반을 넘는다는 생일 문제(birthday problem)와 같은 계산이다. 같은 식으로 계산하면 칸을 232개로 잡아도 값 약 7만 7천 개에서 절반을 넘는다. 충돌 확률은 "값의 개수 ÷ 칸 수"가 아니라 값들이 만들 수 있는 쌍의 수에 좌우되기 때문에 직관보다 훨씬 빨리 커진다.

    결론은 분명하다. 충돌은 운이 나쁠 때 생기는 예외 상황이 아니라 해시 테이블이 늘 겪는 정상 상황이다. 해시 테이블의 설계는 "충돌을 어떻게 없앨까"가 아니라 "충돌이 생겨도 올바르게, 그리고 여전히 빠르게 동작하려면 어떻게 할까"에서 시작한다.

    충돌을 다루는 방법은 크게 두 갈래다. 하나는 한 칸에 값을 여러 개 담을 수 있게 하는 분리 연결법(separate chaining)이다. 다른 하나는 자리가 차 있으면 정해진 규칙에 따라 다른 빈칸을 찾아가는 개방 주소법(open addressing)이다. JDK에는 두 방식이 모두 있다. HashMap과 Hashtable은 분리 연결법을 쓰고, IdentityHashMap은 문서에서 스스로를 선형 탐사(linear-probe) 해시 테이블이라고 설명한다. 이 회차는 구조가 단순하고 HashMap의 바탕이기도 한 분리 연결법을 구현한다.

    충돌을 받아들이는 구조 — 버킷과 체이닝

    발상은 단순하다. 배열의 한 칸에 값을 하나만 넣을 수 있어서 덮어쓰기가 생겼으니, 한 칸에 여러 값을 담을 수 있게 한다. 배열의 각 칸이 값이 아니라 작은 리스트를 가리키게 하고, 해시 인덱스가 같은 값들은 그 리스트에 함께 넣는다. 이렇게 여러 값을 담는 칸 하나를 버킷(bucket)이라고 부른다. 같은 버킷에 든 값들이 사슬처럼 이어진다고 해서 이 방식을 체이닝(chaining)이라고도 한다.

    세 연산은 모두 같은 두 단계로 이루어진다. 첫 단계에서 해시 인덱스를 계산해 버킷 하나를 고른다. 둘째 단계에서 그 버킷 안의 값들과 차례로 비교한다. 9가 들어 있는지 확인하는 과정을 따라가 보자.

    없는 값을 찾을 때도 같다. contains(19)는 9번 버킷으로 가서 99, 9와 차례로 비교하고 버킷 끝에 도달해 false를 반환한다. 비교는 두 번이다. contains(3)은 3번 버킷이 비어 있으므로 비교를 한 번도 하지 않고 false다. 세트에 값이 일곱 개 들어 있지만 어떤 조회도 일곱 번 비교하지 않는다.

    여기서 해시 인덱스와 비교가 맡은 역할을 분명히 구분해 둘 필요가 있다. 해시 인덱스는 답을 내지 않는다. 해시 인덱스가 하는 일은 후보를 전체 n개에서 버킷 하나에 든 몇 개로 줄이는 것이다. 답은 버킷 안에서 값이 같은지 비교해서 낸다. "어느 버킷인가"를 정하는 계산과 "버킷 안에서 같은 값인가"를 정하는 비교, 이 두 가지가 맞물려야 해시 자료 구조가 동작한다. 자바 객체에서 앞의 것을 맡는 메서드가 hashCode()이고 뒤의 것을 맡는 메서드가 equals()다. 두 메서드를 왜 함께 재정의해야 하는지는 07회에서 다루는데, 그 이유의 뿌리가 이 두 단계 구조다.

    이 장의 핵심

    해시 테이블은 값으로부터 자리를 계산해 탐색 범위를 버킷 하나로 줄이고, 버킷 안에서는 값을 직접 비교해 답을 낸다. 충돌은 없앨 수 없으므로 받아들이되, 버킷 하나에 든 값의 수가 작게 유지되는 동안에만 O(1)이 성립한다.

    배열의 각 칸이 리스트를 가리키고, 해시 인덱스가 같은 99와 9가 한 버킷에 사슬로 이어져 있으며, 조회가 버킷 하나만 훑는다는 것을 보여 준다. 깔끔한 교육용 평면 다이어그램, 흰 배경. 왼쪽에 세로로 쌓인 네모 칸 10개, 위에서 아래로 인덱스 0부터 9, 상단 제목 라벨 "버킷 배열". 각 칸에서 오른쪽으로 화살표가 나간다. 1번 칸 화살표 끝에 둥근 상자 "1", 2번 칸에 "2", 4번 칸에 "14", 5번 칸에 "5", 8번 칸에 "8". 0번, 3번, 6번, 7번 칸의 화살표 끝에는 점선 테두리의 빈 상자. 9번 칸에서 나간 화살표 끝에 둥근 상자 "99", 거기서 다시 화살표로 이어진 둥근 상자 "9", 이 두 상자는 주황색으로 강조하고 위에 라벨 "해시 충돌: 같은 버킷". 왼쪽 위 바깥에 작은 상자 "contains(9)"에서 "9 % 10 = 9" 라벨이 붙은 굵은 화살표가 9번 칸을 가리킨다. 9번 버킷을 따라 번호 1, 2가 붙은 작은 돋보기 아이콘 두 개와 라벨 "버킷 안에서만 비교". 색은 파랑과 회색 위주, 강조는 주황. 해시 인덱스가 버킷을 고르고, 버킷 안에서는 값을 하나씩 비교한다. 충돌한 99와 9는 같은 버킷에 함께 들어 있다.

    버킷 배열 구현 — 제네릭 배열과 remove의 함정까지

    버킷으로는 04회에서 원리를 살펴본 연결 리스트를 쓴다. 표준 라이브러리의 LinkedList를 버킷으로 삼아 세트를 완성한다.

    import java.util.Arrays;
import java.util.LinkedList;

public class ChainedIntSet {
    private final LinkedList[] buckets;
    private int size;

    @SuppressWarnings("unchecked")
    public ChainedIntSet(int capacity) {
        buckets = new LinkedList[capacity];
        for (int i = 0; i < capacity; i++) {
            buckets[i] = new LinkedList<>();
        }
    }

    private int hashIndex(int value) {
        return Math.floorMod(value, buckets.length);
    }

    public boolean add(int value) {
        LinkedList bucket = buckets[hashIndex(value)];
        if (bucket.contains(value)) {
            return false;
        }
        bucket.add(value);
        size++;
        return true;
    }

    public boolean contains(int value) {
        return buckets[hashIndex(value)].contains(value);
    }

    public boolean remove(int value) {
        LinkedList bucket = buckets[hashIndex(value)];
        boolean removed = bucket.remove(Integer.valueOf(value));
        if (removed) {
            size--;
        }
        return removed;
    }

    public int size() {
        return size;
    }

    @Override
    public String toString() {
        return Arrays.toString(buckets);
    }
}
    public class ChainedIntSetMain {
    public static void main(String[] args) {
        ChainedIntSet set = new ChainedIntSet(10);
        int[] values = {1, 2, 5, 8, 14, 99, 9};
        for (int value : values) {
            set.add(value);
        }
        System.out.println(set.add(99));
        System.out.println(set);
        System.out.println("size=" + set.size());

        System.out.println(set.contains(9));
        System.out.println(set.contains(19));
        System.out.println(set.contains(3));

        System.out.println(set.remove(99));
        System.out.println(set.remove(99));
        System.out.println(set);
        System.out.println("size=" + set.size());
    }
}

    99와 9가 9번 버킷에 함께 들어 있고, 이번에는 아무것도 사라지지 않았다. 이미 있는 99를 다시 넣으면 9번 버킷 안에서 99를 찾아 false를 반환한다. add의 중복 검사가 전체 요소가 아니라 버킷 하나만 훑는다는 점이 배열 세트와의 결정적인 차이다. 코드는 짧지만 짚어 둘 곳이 네 군데 있다.

    제네릭 타입의 배열은 왜 직접 만들 수 없는가

    생성자에서 new LinkedList[capacity]라고 쓰지 않고 new LinkedList[capacity]라고 쓴 뒤 경고를 눌렀다. 앞의 것은 컴파일되지 않기 때문이다.

    error: generic array creation
    LinkedList[] buckets = new LinkedList[10];
                                    ^

    JLS §15.10.1은 배열 생성식의 요소 타입이 실체화 가능 타입(reifiable type)이어야 한다고 정하고, §10.5가 이유를 설명한다. 참조 타입 배열은 실행 시점에 자신의 요소 타입을 알고 있어서, 칸에 값을 넣을 때마다 그 타입에 맞는지 검사하고 맞지 않으면 ArrayStoreException을 던진다. 그런데 02회에서 본 타입 소거 때문에 LinkedList와 LinkedList은 실행 시점에 둘 다 그냥 LinkedList다. JVM이 둘을 구분할 수 없으니 이 검사를 할 수 없고, 그래서 언어가 그런 배열의 생성 자체를 금지한다.

    원시 타입(raw type)으로 만든 배열을 대입하는 것은 허용되지만 컴파일러는 비검사 경고(unchecked warning)를 낸다. 검사가 빠진 자리로 잘못된 객체가 들어갈 수 있다는 뜻이고, 실제로 그렇게 만들 수 있다.

    @SuppressWarnings("unchecked")
LinkedList[] buckets = new LinkedList[2];
Object[] objects = buckets;                // 배열은 공변이라 대입된다
LinkedList strings = new LinkedList<>();
strings.add("hello");
objects[0] = strings;                      // ArrayStoreException이 나지 않는다
Integer first = buckets[0].get(0);         // 여기서 ClassCastException

    문자열 리스트가 정수 리스트 배열에 들어갔는데 넣는 순간에는 아무 일도 없고, 한참 뒤 값을 꺼내는 줄에서 "class java.lang.String cannot be cast to class java.lang.Integer"로 시작하는 예외가 난다. 우리 클래스에서 경고를 눌러도 되는 근거는 이 배열이 private final 필드에 갇혀 밖으로 나가지 않고, 생성자가 넣는 것이 정수 리스트뿐이라는 사실을 코드로 확인할 수 있기 때문이다. OpenJDK의 HashMap도 내부 배열을 같은 방식으로 만들고 같은 애너테이션으로 경고를 누른다.

    버킷 안의 비교는 equals다

    bucket.contains(value)에 넘긴 것은 int지만 LinkedList.contains의 매개변수는 Object이므로 Integer로 박싱되어 넘어간다. LinkedList의 소스를 보면 contains는 indexOf를 부르고, indexOf는 첫 노드부터 next를 따라가며 o.equals(x.item)으로 비교한다. 참조가 같은지 보는 ==이 아니라 값이 같은지 보는 equals다. 버킷 안에서의 "같다"가 동등성을 뜻한다는 점은 요소가 직접 만든 객체로 바뀔 때 중요해진다.

    remove(int)와 remove(Object)

    remove에서 Integer.valueOf(value)로 굳이 박싱한 것은 꾸밈이 아니다. LinkedList에는 인덱스로 지우는 remove(int index)와 값으로 지우는 remove(Object o)가 둘 다 있다. JLS §15.12.2에 따르면 오버로드 해석의 첫 단계는 박싱과 언박싱을 허용하지 않은 채 적용 가능한 메서드를 찾고, 거기서 찾으면 다음 단계로 가지 않는다. 인자가 int이면 첫 단계에서 remove(int index)가 선택된다.

    LinkedList bucket = new LinkedList<>();
bucket.add(9);
bucket.add(99);
int value = 99;
bucket.remove(value);
// java.lang.IndexOutOfBoundsException: Index: 99, Size: 2

LinkedList other = new LinkedList<>();
other.add(1);
other.add(0);
other.add(7);
other.remove(1);               // 값 1이 아니라 인덱스 1의 요소 0을 지운다
System.out.println(other);     // [1, 7]

    첫 번째 경우는 예외라도 나니 다행이다. 두 번째 경우가 더 위험하다. 값 1을 지우려 했는데 인덱스 1에 있던 0이 지워지고, 프로그램은 아무 일 없이 계속 실행된다. 정수를 담는 리스트에서 값을 지울 때는 인자의 타입이 int인지 Integer인지에 따라 전혀 다른 메서드가 불린다는 것을 기억해 둔다.

    출력 순서가 말해 주는 것

    실행 결과의 [[], [1], [2], [], [14], [5], [], [], [8], [99, 9]]를 다시 보자. 넣은 순서는 1, 2, 5, 8, 14, 99, 9였는데 버킷 순서대로 읽으면 1, 2, 14, 5, 8, 99, 9다. 넣은 순서도 아니고 크기 순서도 아니다. 세트를 순회한다는 것은 버킷 배열을 0번부터 훑는 것이고, 값이 어느 버킷에 있는지는 해시 인덱스가 정하기 때문이다. "세트는 순서를 약속하지 않는다"는 말의 물리적인 이유가 여기에 있다.

    이 성질은 착시를 만들기도 한다. 버킷 10개짜리 세트에 5, 3, 1, 4, 2를 차례로 넣고 출력하면 [[], [1], [2], [3], [4], [5], [], [], [], []]가 나온다. 정렬해 준 것처럼 보이지만 작은 정수는 값이 곧 해시 인덱스라서 생긴 우연이다. 여기에 11과 -7을 더 넣으면 [[], [1, 11], [2], [3, -7], [4], [5], [], [], [], []]가 되어 정렬처럼 보이던 것이 깨진다. java.util.HashSet의 문서도 순회 순서를 보장하지 않으며 시간이 지나도 같은 순서가 유지된다는 보장조차 없다고 적는다. 시간이 지나면 순서가 바뀔 수 있는 이유는 조금 뒤 재해싱에서 드러난다.

    비용 분석 — 평균 O(1)의 조건과 최악 O(n)

    체이닝 세트에서 연산 하나의 비용은 두 부분의 합이다. 해시 인덱스를 계산해 버킷을 고르는 비용은 요소 수와 무관한 O(1)이다. 버킷 안을 훑는 비용은 그 버킷에 든 값의 수에 비례한다. 따라서 성능은 전적으로 버킷 하나에 값이 몇 개 들어 있는가에 달려 있다.

    값이 n개, 버킷이 m개라고 하자. 값이 버킷에 고르게 퍼져 있다면 버킷 하나에는 평균 n/m개가 들어 있다. 이 비율을 적재율(load factor)이라고 한다. 없는 값을 찾거나 새 값을 넣을 때는 버킷을 끝까지 훑어야 하므로 평균 n/m번 비교한다. 있는 값을 찾을 때는 버킷 중간쯤에서 만나게 되므로, 길이가 L인 버킷이라면 평균 (L+1)/2번 비교한다. 어느 쪽이든 적재율에 비례한다.

    여기서 두 가지 결론이 나온다. 버킷 수 m을 값의 수 n에 맞춰 늘려 적재율을 일정한 상수 이하로 묶어 두면, 버킷 길이의 평균도 상수이므로 연산은 평균 O(1)이다. 반대로 m을 고정해 두면 적재율이 n에 비례해 커지므로 연산은 O(n)이다. 버킷이 10개면 배열 세트보다 10배 빠를 뿐 증가율은 같다.

    버킷을 언제 늘릴 것인가 — 적재율과 재해싱

    ChainedIntSet은 버킷 수가 생성할 때 고정된다. 버킷 10개로 만든 세트에 값을 만 개 넣으면 버킷마다 평균 천 개가 들어간다. 03회의 배열 리스트가 가득 차면 배열을 키웠듯이, 해시 테이블도 값이 늘면 버킷 배열을 키워야 한다. 기준은 가득 찼는가가 아니라 적재율이다. 값의 수가 "버킷 수 × 기준 적재율"을 넘으면 버킷 배열을 두 배로 늘린다.

    배열 리스트와 다른 점이 하나 있다. 배열 리스트는 옛 배열의 내용을 새 배열의 같은 인덱스로 복사하면 끝났다. 해시 테이블은 그럴 수 없다. 해시 인덱스가 버킷 수로 나눈 나머지이므로, 버킷 수가 바뀌면 같은 값의 인덱스도 바뀐다. 14는 버킷이 10개일 때 4번이었지만 20개가 되면 14번이다. 옛 배열을 그대로 복사하면 14는 4번 버킷에 남아 있는데 조회는 14번 버킷을 보게 되어, 들어 있는 값을 없다고 답하게 된다. 그래서 모든 값의 인덱스를 새 버킷 수로 다시 계산해 다시 넣어야 한다. 이 작업을 재해싱(rehashing)이라고 한다.

    import java.util.Arrays;
import java.util.LinkedList;

public class GrowingIntSet {
    private static final double LOAD_FACTOR = 0.75;

    private LinkedList[] buckets;
    private int size;

    public GrowingIntSet(int capacity) {
        buckets = newBuckets(capacity);
    }

    @SuppressWarnings("unchecked")
    private static LinkedList[] newBuckets(int capacity) {
        LinkedList[] created = new LinkedList[capacity];
        for (int i = 0; i < capacity; i++) {
            created[i] = new LinkedList<>();
        }
        return created;
    }

    private static int hashIndex(int value, int capacity) {
        return Math.floorMod(value, capacity);
    }

    public boolean add(int value) {
        LinkedList bucket = buckets[hashIndex(value, buckets.length)];
        if (bucket.contains(value)) {
            return false;
        }
        if (size + 1 > buckets.length * LOAD_FACTOR) {
            resize(buckets.length * 2);
            bucket = buckets[hashIndex(value, buckets.length)];
        }
        bucket.add(value);
        size++;
        return true;
    }

    private void resize(int newCapacity) {
        LinkedList[] old = buckets;
        buckets = newBuckets(newCapacity);
        for (LinkedList bucket : old) {
            for (int value : bucket) {
                buckets[hashIndex(value, newCapacity)].add(value);
            }
        }
    }

    public boolean contains(int value) {
        return buckets[hashIndex(value, buckets.length)].contains(value);
    }

    public int capacity() {
        return buckets.length;
    }

    @Override
    public String toString() {
        return Arrays.toString(buckets);
    }
}
    public class GrowingMain {
    public static void main(String[] args) {
        GrowingIntSet set = new GrowingIntSet(10);
        int[] values = {1, 2, 5, 8, 14, 99, 9};
        for (int value : values) {
            set.add(value);
        }
        System.out.println(set.capacity() + " " + set);
        set.add(21);
        System.out.println(set.capacity() + " " + set);
        System.out.println(set.contains(99) + " " + set.contains(19));
    }
}

    버킷 10개에 기준 적재율 0.75이면 한계는 7.5다. 값 일곱 개까지는 그대로 들어간다. 여덟 번째 값 21을 넣으려는 순간 8이 7.5를 넘으므로 버킷이 20개로 늘어난다. resize가 옛 버킷을 0번부터 훑으며 값을 하나씩 새 인덱스에 넣는다. 14는 4번에서 14번으로, 99는 9번에서 19번으로 옮겨 가고 9는 9번에 남는다. 한 버킷에서 충돌하던 99와 9가 서로 다른 버킷으로 갈라졌다. 그런 다음 21이 21 % 20 = 1번 버킷에 들어간다. 확장한 뒤 bucket 변수를 다시 구하는 줄이 빠지면 21이 버려진 옛 버킷에 들어가므로 주의한다.

    확장 전후의 출력을 비교하면 순회 순서도 달라졌다. 앞에서는 14가 5보다 먼저 나왔는데 이제는 5가 먼저다. 요소를 넣기만 했는데 기존 요소들의 순회 순서가 바뀐 것이다. HashSet의 문서가 순서가 시간이 지나도 유지된다고 보장하지 않는다고 적은 것이 이 현상을 가리킨다.

    재해싱은 값 전체를 다시 넣는 O(n) 작업이다. 그래도 add의 분할 상환 비용은 O(1)로 유지된다. 논리는 03회의 배열 확장과 같다. 버킷 수를 두 배씩 늘리면 재해싱이 일어나는 시점의 값 개수도 대략 두 배씩 커지고, 그때까지의 재해싱 작업량을 모두 더해도 마지막 재해싱 작업량의 두 배를 넘지 않는다. 값 n개를 넣는 동안 재해싱에 쓴 일의 총량이 n에 비례하므로, 한 번의 add에 나눠 얹으면 상수다.

    기준 적재율은 왜 0.75인가

    기준 적재율은 시간과 공간 사이의 저울이다. 낮게 잡으면 버킷이 넉넉해 충돌이 줄지만 빈 버킷이 늘어 메모리를 더 쓴다. 높게 잡으면 메모리는 아끼지만 버킷이 길어져 비교가 늘어난다. HashMap의 문서는 기본 초기 용량이 16, 기본 적재율이 0.75이고 "the default load factor (.75) offers a good tradeoff between time and space costs"라고 적는다. 항목 수가 적재율과 현재 용량의 곱을 넘으면 버킷 수를 약 두 배로 늘려 재해싱한다는 것도 같은 문서에 있다.

    이 설정에서 버킷이 실제로 얼마나 길어지는지에 대한 수치가 OpenJDK 21의 HashMap.java 구현 주석에 있다. 해시 코드가 무작위로 퍼진다는 이상적인 조건에서, 버킷에 든 노드의 수는 평균이 약 0.5인 푸아송 분포를 따른다는 내용이다. 버킷 수를 두 배로 늘린 직후의 적재율은 0.375이고 다음 확장 직전이 0.75이니, 0.5는 그 사이의 값이다. 주석이 제시하는 길이별 버킷의 비율은 다음과 같다.

    버킷 수가 바뀌면 같은 값의 해시 인덱스가 달라져 모든 값을 다시 배치해야 하고, 한 버킷에 있던 99와 9가 갈라진다는 것을 보여 준다. 깔끔한 교육용 평면 다이어그램, 흰 배경, 좌우 2단 구성. 왼쪽 단 제목 라벨 "확장 전: 버킷 10개". 세로로 쌓인 칸 10개, 인덱스 0부터 9. 1번 칸 옆에 둥근 상자 "1", 2번에 "2", 4번에 "14", 5번에 "5", 8번에 "8", 9번에 둥근 상자 "99"와 "9"가 사슬로 연결. 오른쪽 단 제목 라벨 "확장 후: 버킷 20개". 세로로 쌓인 칸 20개, 인덱스 0부터 19. 1번 칸 옆에 "1"과 "21"이 사슬로 연결, 2번에 "2", 5번에 "5", 8번에 "8", 9번에 "9", 14번에 "14", 19번에 "99". 왼쪽 4번 버킷의 "14"에서 오른쪽 14번 버킷으로 가는 주황색 곡선 화살표와 라벨 "14 % 20 = 14". 왼쪽 9번 버킷의 "99"에서 오른쪽 19번 버킷으로 가는 주황색 곡선 화살표와 라벨 "99 % 20 = 19". 왼쪽 9번 버킷의 "9"에서 오른쪽 9번 버킷으로 가는 회색 화살표. 가운데 위에 라벨 "모든 값의 인덱스를 다시 계산". 색은 파랑과 회색 위주, 이동은 주황 강조. 해시 인덱스는 버킷 수의 함수다. 버킷 수가 바뀌면 모든 값의 자리를 다시 계산해야 한다.

    같은 값을 int[]에 담는 배열 세트는 값 하나에 4바이트를 쓴다. 체이닝 세트는 값 하나에 40바이트를 쓰고, 여기에 버킷 몫이 더해진다. 해시 테이블은 메모리를 열 배 넘게 써서 탐색 시간을 줄이는 구조다. 직접 주소 지정이 범위만큼의 공간을 요구했던 것과 비교하면 훨씬 나은 거래지만, 공짜가 된 것은 아니다.

    빈 버킷의 비용도 눈에 띈다. 우리 구현은 생성자에서 버킷마다 LinkedList 객체를 만들어 두므로, 값이 하나도 없는 버킷도 참조 4바이트와 리스트 객체 32바이트를 차지한다. 앞의 푸아송 표에서 버킷의 약 61%가 비어 있었던 것을 떠올리면 낭비가 크다. OpenJDK의 HashMap은 이 부분을 다르게 설계했다. 버킷마다 리스트 객체를 따로 두지 않고 테이블의 칸이 첫 노드를 직접 가리키며, 빈 버킷은 그냥 null이다. 테이블 배열 자체도 필드 주석에 적힌 대로 처음 쓸 때 만들어진다.

    시간 쪽의 상수는 참조를 따라가는 횟수다. contains(9)가 첫 번째 비교를 하기까지 버킷 배열, 리스트 객체, 노드, Integer 객체를 차례로 거친다. 네 객체는 힙의 서로 다른 곳에 있을 수 있다. 04회에서 본 것처럼 연속한 배열을 훑는 것과 흩어진 객체를 참조로 건너다니는 것은 CPU 캐시를 쓰는 방식이 다르다. 그래서 요소가 몇 개뿐일 때는 "O(n)인 배열 훑기"와 "O(1)인 해시 조회"의 실제 차이가 표기에서 받는 인상만큼 크지 않을 수 있다. 해시의 이점은 요소 수가 커질수록, 즉 배열 훑기의 n이 상수를 압도할수록 분명해진다.

    흔한 오해, 그리고 다음으로 이어지는 것

    "해시 자료 구조는 항상 O(1)이다." 평균이 O(1)이고, 그 평균에는 값이 고르게 퍼진다는 조건과 적재율이 관리된다는 조건이 붙는다. 조건이 깨지면 O(n)까지 내려간다. 앞의 실험에서 1000의 배수를 버킷 1,000개에 넣은 경우가 그랬다.

    "좋은 해시 함수를 쓰면 충돌이 없다." 칸 수가 값의 범위보다 작은 한 충돌하는 값의 쌍은 반드시 존재한다. 좋은 해시 함수의 목표는 충돌을 없애는 것이 아니라 값을 버킷에 고르게 퍼뜨려 버킷 하나의 길이를 짧게 유지하는 것이다.

    "해시 인덱스가 같으면 같은 값이다." 14와 4는 버킷 10개에서 인덱스가 같지만 다른 값이다. 인덱스가 같다는 것은 같은 버킷을 봐야 한다는 뜻일 뿐이고, 같은 값인지는 비교해야 안다. 반대 방향은 성립해야 한다. 같은 값은 반드시 같은 인덱스가 나와야 한다. 그렇지 않으면 넣은 값을 다른 버킷에서 찾다가 놓친다. 이 비대칭이 07회에서 "equals가 같다고 하는 두 객체는 hashCode도 같아야 한다"는 규약으로 다시 나온다.

    "세트는 값을 정렬해 준다" 또는 "넣은 순서를 지켜 준다." 작은 정수에서 정렬처럼 보이는 것은 값과 버킷 번호가 우연히 일치해서다. 해시 기반 세트의 순회 순서는 버킷 배치가 정하고, 재해싱이 일어나면 바뀐다.

    "버킷은 많을수록 좋다." 버킷 배열은 값이 없어도 메모리를 차지하고, 전체를 순회하는 시간은 값의 수가 아니라 버킷 수에도 비례한다. HashMap의 문서가 순회 성능이 중요하면 초기 용량을 너무 크게 잡지 말라고 경고하는 이유다. 버킷을 무한히 늘린 극단이 앞에서 버린 직접 주소 지정이라는 것을 기억하면 된다.

    이 회차에서 만든 것은 int만 담는 세트였다. 남은 질문은 세 가지이고 각각 뒤의 회차가 받는다. 문자열이나 직접 만든 객체는 어떻게 정수로 바꾸는가, 그리고 그 객체의 "같다"는 누가 정하는가는 07회가 다룬다. 자바가 제공하는 세트 구현들은 순서와 정렬을 어떻게 다루는가는 08회의 몫이다. 값에 다른 값을 짝지어 저장하는 맵, 그리고 HashMap의 실제 내부 구조는 09회에서 본다.

    해시가 포기한 것이 무엇인지도 정리해 둔다. 해시 테이블에는 값의 크기 순서가 남아 있지 않다. 그래서 "5 이상 20 이하인 값"을 찾는 범위 질문에는 버킷 전체를 훑는 것 말고 방법이 없다. 이 한계는 자바 밖에서도 똑같이 나타난다. MySQL 매뉴얼은 해시 인덱스가 =와 <=> 같은 동등 비교에만 쓰이고, 범위를 찾는 비교 연산자나 ORDER BY의 속도를 높이는 데는 쓸 수 없다고 설명한다. 같은 값인지 묻는 질문에는 해시가, 순서와 범위를 묻는 질문에는 정렬된 구조가 답한다는 구분은 컬렉션에서도 데이터베이스 인덱스에서도 그대로 통한다.
    세트(Set)
    중복을 허용하지 않고 인덱스 연산이 없는 컬렉션이다. 핵심 연산은 값의 존재 여부를 묻는 contains이고, 중복 검사 때문에 add 안에도 탐색이 들어 있다.
    배열 기반 세트의 비용
    요소의 위치가 값과 무관하므로 값으로 찾으려면 전부 비교해야 한다. add와 contains가 O(n)이고 서로 다른 값 n개를 넣는 데 n(n-1)/2번 비교한다.
    직접 주소 지정
    값을 그대로 배열 인덱스로 쓰면 모든 연산이 O(1)이 되지만, 칸 수가 값의 개수가 아니라 값의 범위만큼 필요하다.
    해시 인덱스
    값을 칸 수로 나눈 나머지처럼, 넓은 범위의 값을 배열 범위 안의 인덱스로 바꾼 것이다. 같은 값은 항상 같은 인덱스가 나와야 한다.
    나머지 연산의 경계
    자바의 %는 나누어지는 수가 음수면 결과도 음수일 수 있다. Math.floorMod, 부호 비트 제거, 2의 거듭제곱 칸 수와 비트 마스크로 해결하고 Math.abs는 Integer.MIN_VALUE에서 실패한다.
    해시 충돌
    서로 다른 값이 같은 해시 인덱스를 갖는 것이다. 칸 수가 범위보다 작으면 반드시 존재하고, 칸 10개에 값 4개만 넣어도 발생 확률이 49.6%다.
    버킷과 체이닝
    배열의 각 칸이 여러 값을 담는 버킷이 된다. 해시 인덱스로 버킷을 고르고, 버킷 안에서는 동등성 비교로 값을 찾는다.
    적재율과 재해싱
    값의 수를 버킷 수로 나눈 적재율이 평균 버킷 길이를 정한다. 적재율이 기준을 넘으면 버킷을 늘리고 모든 값의 인덱스를 다시 계산해 옮긴다.
    평균 O(1), 최악 O(n)
    값이 고르게 퍼지고 적재율이 상수로 묶일 때만 평균 O(1)이다. 모든 값이 한 버킷에 몰리면 연결 리스트 하나와 같아진다.

    실무에서 해시 기반 컬렉션이 느리다는 보고를 받으면 가장 먼저 의심할 것은 분포다. 이 회차의 실험에서 버킷이 1,000개나 있어도 값이 한 버킷에 몰리자 비교 횟수가 배열 세트와 같아졌다. 실제 코드에서는 해시 값을 상수나 몇 가지 값으로만 돌려주는 구현, 입력의 규칙성이 버킷 수와 맞물리는 경우가 같은 결과를 낸다. 평균 O(1)은 자료 구조가 혼자 보장하는 성질이 아니라 해시 함수와 함께 만드는 성질이라는 점을 기억하면 원인을 찾는 순서가 정해진다.

    크기를 미리 아는 경우에는 초기 용량을 판단할 수 있다. 재해싱은 모든 값을 다시 배치하는 작업이므로, 수십만 개를 넣을 것을 알면서 기본 용량에서 시작하면 확장을 여러 번 거친다. HashMap의 문서는 초기 용량이 최대 항목 수를 적재율로 나눈 값보다 크면 재해싱이 일어나지 않는다고 적는다. 반대로 용량을 지나치게 크게 잡으면 빈 버킷이 메모리를 차지하고 순회가 느려진다. 예상 개수라는 근거가 있을 때만 조정하고, 없으면 기본값을 쓰는 것이 합리적이다.

    해시가 맞지 않는 상황도 구분해야 한다. 값의 범위가 작고 빽빽하면 직접 주소 지정이 더 빠르고 작다. 0부터 수천까지의 번호가 쓰였는지 기록하는 일에 해시 세트를 쓸 이유가 없고, 열거형 값의 집합에 EnumSet이 있는 것도 같은 판단의 결과다. 순서나 범위가 필요한 질문, 예를 들어 "이 값 이상인 것 중 가장 작은 것"에는 해시가 답할 수 없으므로 정렬된 구조를 골라야 한다. 요소가 수백만 개인 정수 집합이라면 요소당 수십 바이트라는 해시 테이블의 메모리 단가가 설계를 좌우할 수 있다.

    마지막으로, 해시 기반 컬렉션의 순회 순서에 의존하는 코드는 언젠가 깨진다. 테스트 데이터가 작은 정수일 때는 정렬된 것처럼 보이고, 요소가 늘어 재해싱이 일어나거나 값의 종류가 바뀌면 순서가 달라진다. 순서가 요구 사항이라면 순서를 계약으로 보장하는 컬렉션을 써야 한다.

    1번. 요소가 k개 있을 때 새 값을 넣으면 끝까지 훑어야 하므로 k번 비교한다. 0 + 1 + … + 1,999 = 2,000 × 1,999 ÷ 2 = 1,999,000번이다. 이미 있는 값을 다시 넣으면 contains가 그 값을 만나는 순간 멈춘다. 맨 처음 넣었던 값이면 1번, 맨 마지막에 넣었던 값이면 2,000번이다. 없는 값의 탐색은 항상 최악이고 있는 값의 탐색은 위치에 따라 달라진다는 점이 드러난다.

    2번. Math.floorMod(value, 8)로 계산한다. 3은 3, 11은 3, -5는 3(-5에 8을 더한 값), 16은 0, 8은 0, 19는 3, 0은 0이다. 출력은 [[16, 8, 0], [], [], [3, 11, -5, 19], [], [], [], []]이다. 일곱 값이 버킷 두 개에만 몰렸다. contains(27)은 27 % 8 = 3이므로 3번 버킷의 네 값과 모두 비교한 뒤 false를 반환한다. 비교는 4번이다. 값이 일곱 개인데 없는 값 하나를 찾는 데 4번을 비교했으니, 분포가 나쁘면 해시의 이점이 줄어든다는 것을 보여 주는 예다.

    3번. 값은 Integer.MIN_VALUE다. Math.abs(Integer.MIN_VALUE)는 양수로 표현할 수 없어 Integer.MIN_VALUE 그대로 음수가 나오고, 10으로 나눈 나머지는 -8이다. 배열 접근에서 ArrayIndexOutOfBoundsException: Index -8 out of bounds for length 10이 발생한다. 버킷이 16개이면 Integer.MIN_VALUE % 16이 0이므로 예외 없이 0번 버킷이 선택된다. 버그는 그대로 있는데 칸 수에 따라 증상이 숨는다. 2의 거듭제곱 크기로만 테스트하면 발견되지 않는다.

    4번. (가) 배열이 16 + 4 × 1,000,000 = 4,000,016바이트이고, 값이 모두 128 이상이라 캐시되지 않으므로 Integer 객체 1,000개가 16,000바이트다. 합계 4,016,016바이트다. (나) 버킷 배열이 16 + 4 × 2,048 = 8,208바이트, 리스트 객체가 32 × 2,048 = 65,536바이트, 노드와 Integer가 40 × 1,000 = 40,000바이트다. 합계 113,744바이트다. 직접 주소 테이블은 값의 범위에 비례해 약 4MB를 쓰고, 해시 테이블은 값의 개수와 버킷 수에 비례해 그 35분의 1 정도를 쓴다. 범위가 더 넓어질수록 차이는 커진다.

    5번. 1 % 20 = 1, 11 % 20 = 11, 21 % 20 = 1, 31 % 20 = 11이다. 1과 21은 1번에 남고 11과 31은 11번으로 간다. 일반화하면, m으로 나눈 나머지가 i인 값을 2m으로 나눈 나머지는 i이거나 i + m이다. 즉 i번 버킷은 i번과 i + m번 두 버킷으로 갈라질 뿐 다른 곳으로 흩어지지 않는다. 옛 배열을 인덱스 그대로 복사하면 11이 여전히 1번 버킷에 남는데, contains(11)은 11 % 20 = 11번 버킷을 보므로 들어 있는 값을 없다고 답한다. 같은 이유로 11을 다시 넣으면 중복 검사를 통과해 값이 두 번 들어간다.

     배열에 넣은 순서대로 저장하는 세트에 서로 다른 값 n개를 넣는 전체 비용이 O(n²)이 되는 직접적인 원인은 무엇인가? 배열이 가득 찰 때마다 두 배 크기의 배열로 복사하기 때문이다. 넣을 때마다 중복 확인을 위해 기존 요소와 차례로 비교해야 하고, 값만으로는 후보를 좁힐 수 없기 때문이다. 배열 접근마다 인덱스 범위 검사를 하기 때문이다. 세트는 순서를 유지하기 위해 요소를 한 칸씩 밀어야 하기 때문이다. 요소의 위치가 넣은 이력으로 정해져 값과 무관하므로, 새 값이 이미 있는지 알려면 전부 비교해야 한다. k개가 든 상태에서 k번씩 비교하니 합이 n(n-1)/2다. 배열 확장 복사는 분할 상환 O(1)이라 원인이 아니고, 범위 검사는 접근 한 번의 상수 비용이다. 이 세트는 끝에만 추가하므로 요소를 밀지도 않는다. 칸이 10개이고 인덱스를 value % 10으로 구하며 칸마다 값을 하나만 저장하는 테이블에 14가 들어 있다. contains(4)를 올바르게 판단하는 방법은 무엇인가? 4번 칸이 null이 아니면 true를 반환한다. 4번 칸이 차 있으므로 나머지 아홉 칸도 모두 확인한다. 4번 칸에 들어 있는 값이 4와 같은지 비교해 그 결과를 반환한다. 14와 4는 해시 인덱스가 같으므로 같은 값으로 보고 true를 반환한다. 범위를 접으면 4번 칸은 4, 14, 24처럼 나머지가 4인 모든 값의 공통 자리가 된다. 칸이 차 있다는 것은 후보가 있다는 뜻일 뿐이므로 들어 있는 값과 직접 비교해야 한다. 해시 인덱스는 볼 칸을 정해 주므로 다른 칸을 볼 필요는 없고, 인덱스가 같다고 값이 같은 것도 아니다. 해시 충돌에 대한 설명으로 옳은 것은? 칸 수가 값이 가질 수 있는 범위보다 작으면 어떤 해시 함수를 쓰더라도 같은 인덱스로 가는 서로 다른 값이 존재한다. 칸 수를 저장할 값 개수의 두 배로 잡으면 충돌은 일어나지 않는다. 충돌은 음수 값을 나머지 연산에 넣을 때만 발생한다. 충돌이 발생하면 자료 구조는 예외를 던져 호출자에게 알려야 한다. 비둘기집 원리에 따라 더 많은 종류의 값을 더 적은 칸으로 보내는 함수는 반드시 겹치는 값을 가진다. 칸을 값 개수의 두 배 넘게 잡아도, 칸 10개에 값 4개일 때 충돌 확률이 49.6%였듯이 충돌은 흔하다. 충돌은 양수끼리도 생기며(99와 9), 정상 상황이므로 버킷에 함께 담아 처리한다. 버킷이 16개이고 인덱스를 value & 15로 구하는 체이닝 세트에 0, 16, 32, …처럼 16의 배수 1,000개를 넣었다. 들어 있지 않은 16의 배수 하나를 contains로 찾을 때 값 비교는 몇 번 일어나는가? 0번. 해당 버킷이 비어 있다. 1번. 해시 조회는 항상 비교 한 번이다. 약 62번. 1,000개가 16개 버킷에 나뉘어 들어간다. 1,000번. 모든 값이 0번 버킷에 들어 있다. 16의 배수는 아래 4비트가 모두 0이므로 value & 15가 항상 0이다. 1,000개가 전부 0번 버킷에 들어가고, 찾는 값도 0번 버킷으로 가서 끝까지 비교한다. 버킷이 16개 있어도 값이 고르게 퍼지지 않으면 연결 리스트 하나를 훑는 것과 같다. 평균 O(1)은 값이 고르게 분산된다는 조건에서만 성립한다. 버킷 배열을 두 배로 늘릴 때, 옛 배열의 버킷들을 새 배열의 같은 인덱스로 그대로 옮기면 안 되는 이유는 무엇인가? 자바에서는 배열의 참조 요소를 다른 배열로 복사할 수 없기 때문이다. 해시 인덱스가 버킷 수에 따라 달라지므로, 옮긴 뒤의 조회가 값이 들어 있는 버킷과 다른 버킷을 보게 되기 때문이다. 새 배열의 칸이 null로 초기화되어 있어 대입할 수 없기 때문이다. 버킷을 옮기는 동안 값이 정렬 순서를 잃기 때문이다. 해시 인덱스는 값만의 함수가 아니라 값과 버킷 수의 함수다. 14는 버킷 10개에서 4번이지만 20개에서는 14번이다. 그대로 복사하면 14는 4번에 남는데 조회는 14번을 보므로 있는 값을 없다고 답한다. 그래서 모든 값의 인덱스를 새 버킷 수로 다시 계산하는 재해싱이 필요하다. 참조 복사는 가능하고, 해시 테이블에는 애초에 정렬 순서가 없다.
    세트(Set)
    중복 요소를 담지 않는 컬렉션. 자바의 Set 인터페이스는 수학의 집합을 본뜬 것으로, 인덱스로 요소에 접근하는 연산이 없다.
    직접 주소 지정(direct addressing)
    값 자체를 배열 인덱스로 써서 저장하고 찾는 방식. 연산은 O(1)이지만 값의 범위만큼 칸이 필요하다.
    해시 함수(hash function)
    임의의 값을 정해진 범위의 정수로 바꾸는 함수. 같은 입력에는 항상 같은 결과를 내야 한다.
    해시 인덱스(hash index)
    해시 함수의 결과를 배열 범위 안으로 줄여 버킷의 위치로 쓰는 값. 이 회차에서는 값을 버킷 수로 나눈 나머지다.
    해시 테이블(hash table)
    해시 인덱스로 요소의 자리를 정하는 배열 기반 자료 구조.
    해시 충돌(hash collision)
    서로 다른 값이 같은 해시 인덱스를 갖는 상황. 칸 수가 값의 범위보다 작으면 피할 수 없다.
    버킷(bucket)
    해시 테이블 배열의 한 칸. 체이닝 방식에서는 해시 인덱스가 같은 값 여러 개를 함께 담는다.
    분리 연결법(separate chaining)
    충돌한 값들을 같은 버킷 안의 리스트에 이어 저장하는 충돌 처리 방식. 체이닝이라고도 한다.
    개방 주소법(open addressing)
    자리가 차 있으면 정해진 규칙에 따라 테이블 안의 다른 빈칸을 찾아 저장하는 충돌 처리 방식. 선형 탐사가 그 한 가지다.
    적재율(load factor)
    저장된 값의 수를 버킷 수로 나눈 비율. 자바의 HashMap에서는 버킷을 늘리기 전에 허용하는 한계 비율을 가리키는 설정값의 이름이기도 하다.
