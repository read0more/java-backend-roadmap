    이 회차의 질문: 배열이 있는데 왜 리스트를 만드는가

    앞의 두 회차에서 제네릭을 다뤘다. 타입을 매개변수로 받는 클래스를 만들면 코드 한 벌로 여러 타입을 안전하게 다룰 수 있고, 그 타입 정보는 컴파일이 끝나면 소거된다는 것까지 확인했다. 이번 회차부터 이 권의 나머지는 컬렉션 프레임워크(Collections Framework)를 다룬다. 컬렉션 프레임워크는 여러 값을 담아 두는 자료 구조(data structure)들을 표준 라이브러리로 제공하는 것이고, 그 가운데 가장 많이 쓰이는 것이 배열 리스트, 곧 java.util.ArrayList다.

    자바에는 이미 여러 값을 담는 수단이 언어 차원에 들어 있다. 배열(array)이다. 배열은 빠르고 단순하지만 두 가지가 불편하다. 한 번 만들면 길이를 바꿀 수 없고, 중간에 값을 끼워 넣거나 빼려면 나머지 값을 손으로 밀고 당겨야 한다. 배열 리스트는 이 두 가지 불편을 클래스 안으로 감춘 것이다. 속에는 여전히 배열이 들어 있다.

    그래서 배열 리스트를 이해하는 순서는 정해져 있다. 먼저 배열이 왜 빠른지를 메모리 수준에서 본다. 그다음 "빠르다"를 정확히 말하는 도구인 빅오 표기법을 세운다. 그 도구로 배열에 값을 추가하는 비용을 따져 본 뒤, 배열 리스트를 네 단계에 걸쳐 직접 만든다. 고정 용량에서 시작해 동적 확장을 넣고, 중간 삽입과 삭제를 넣고, 마지막으로 제네릭을 적용한다.

    직접 만드는 이유는 OpenJDK의 ArrayList 소스가 같은 뼈대로 되어 있기 때문이다. Object[] 필드 하나, int size 필드 하나, 꽉 차면 더 큰 배열로 옮기는 메서드 하나. 손으로 만든 것과 JDK 소스를 나란히 놓고 보면, 문서에 적힌 "분할 상환 상수 시간" 같은 말이 무엇을 보장하고 무엇을 보장하지 않는지 읽을 수 있게 된다.

    배열과 인덱스: 메모리에서 일어나는 일

    자바 언어 명세(JLS) 10장은 배열을 이렇게 규정한다. 배열은 객체이고, 실행 중에 만들어지며, 구성 요소(component)라고 부르는 이름 없는 변수들을 담는다. 구성 요소는 모두 같은 타입이고 0부터 시작하는 정수 인덱스로 가리킨다. 그리고 §10.2에 이 회차 전체를 좌우하는 문장이 있다. "Once an array object is created, its length never changes." 배열 객체는 만들어진 뒤 길이가 바뀌지 않는다.

    길이가 고정되고 칸의 타입이 모두 같다는 두 조건 덕분에, 구현은 배열을 같은 크기의 칸이 빈틈없이 이어진 메모리 한 덩어리로 만들 수 있다. 그러면 i번째 칸의 위치는 찾는 것이 아니라 계산하는 것이 된다.

    i번째 칸의 위치 = 배열 객체의 시작 위치 + 첫 칸까지의 거리 + i × 칸 하나의 크기

    곱셈 한 번과 덧셈 두 번이다. 배열에 칸이 5개 있든 500만 개 있든 이 계산의 양은 같다. 배열의 원소 접근이 빠르다는 말의 실체는 이것이다. 다른 칸을 거쳐 가지 않는다.

    이 식이 실제로 성립하는지 확인해 보자. JDK에는 객체 내부의 바이트 위치를 직접 다루는 내부 API sun.misc.Unsafe가 있다. 애플리케이션 코드에서 쓰라고 만든 것이 아니고 컴파일할 때 경고도 나오지만, 구조를 눈으로 확인하는 용도로는 쓸 만하다. arrayBaseOffset은 배열 객체의 시작에서 첫 칸까지의 거리를, arrayIndexScale은 칸 하나의 크기를 바이트로 돌려준다.

    import java.lang.reflect.Field;
import sun.misc.Unsafe;

public class ArrayLayout {
    public static void main(String[] args) throws Exception {
        Field f = Unsafe.class.getDeclaredField("theUnsafe");
        f.setAccessible(true);
        Unsafe unsafe = (Unsafe) f.get(null);

        long base = unsafe.arrayBaseOffset(int[].class);
        long scale = unsafe.arrayIndexScale(int[].class);
        System.out.println("base=" + base + ", scale=" + scale);

        int[] arr = {10, 20, 30, 40, 50};
        for (int i = 0; i < arr.length; i++) {
            long offset = base + i * scale;
            System.out.println("arr[" + i + "] offset=" + offset
                    + " value=" + unsafe.getInt(arr, offset));
        }
        System.out.println("long[] scale=" + unsafe.arrayIndexScale(long[].class));
        System.out.println("Object[] scale=" + unsafe.arrayIndexScale(Object[].class));
    }
}

arr[3]의 위치 = 16 + 3 × 4 = 28
    16이나 4 같은 숫자는 명세가 아니라 구현의 선택이다. JVM 명세(JVMS) §2.7은 "The Java Virtual Machine does not mandate any particular internal structure for objects"라고 적어, 객체의 내부 배치를 구현에 맡긴다. 명세가 보장하는 것은 배열의 동작(인덱스로 읽고 쓴다, 길이는 고정이다, 범위를 검사한다)이고, "연속한 칸과 주소 계산"은 그 동작을 가장 값싸게 구현하는 방법이다.

    참조형 배열의 칸에는 객체가 아니라 참조가 들어 있다

    출력의 마지막 줄을 보자. Object[]의 칸 크기가 4바이트다. 객체 하나가 4바이트에 들어갈 리 없으니, 칸에 들어 있는 것은 객체가 아니라 객체를 가리키는 참조(reference)다. 자바 기본편에서 본 "참조형 변수는 참조값을 담는다"는 규칙이 배열의 칸에도 그대로 적용된다. String[]에 문자열 세 개를 넣으면 힙에는 배열 객체 하나와 String 객체 세 개가 따로 있고, 배열의 칸은 그 세 객체의 위치만 적어 둔다.

    4바이트라는 크기도 구현의 선택이다. 64비트 HotSpot은 힙이 아주 크지 않으면 참조를 4바이트로 줄여 저장하는 압축 참조(compressed oops)를 기본으로 켠다. 같은 프로그램을 java -XX:-UseCompressedOops ArrayLayout으로 실행하면 마지막 줄이 Object[] scale=8로 바뀐다. 어느 쪽이든 원리는 같다. 칸의 크기가 모두 같으므로 주소 계산식이 성립한다.

    이 구분은 뒤에서 중요해진다. 배열 리스트가 배열을 통째로 새 배열로 복사할 때 옮겨지는 것은 참조뿐이고, 원소 객체 자체는 제자리에 있다.

    바이트코드로 본 배열 접근

    arr[i]라는 식은 클래스 파일에서 명령 하나가 된다. int 배열을 읽는 메서드와 참조 배열을 읽는 메서드를 javap -c로 열면 다음과 같다.

    iaload는 피연산자 스택에서 배열 참조와 인덱스를 꺼내고 그 칸의 int 값을 올려놓는다. aaload는 같은 일을 참조 배열에 대해 한다. 두 명령에는 반복이나 분기가 없다. JVMS 6장은 이 명령들의 실행 시점 예외도 정해 둔다. 배열 참조가 null이면 NullPointerException, 인덱스가 배열의 범위를 벗어나면 ArrayIndexOutOfBoundsException이다. JLS §10.4의 표현으로는 "All array accesses are checked at run time", 모든 배열 접근은 실행 시점에 검사된다.

    범위를 검사하려면 길이를 알아야 한다. 그래서 길이는 배열 객체 안에 저장되어 있고, arr.length는 그 값을 읽는 arraylength 명령 하나로 번역된다. 필드 접근처럼 생겼지만(JLS §10.7은 length를 public final 필드로 규정한다) 바이트코드에서는 전용 명령이다.

    다섯 단계 가운데 원소의 개수에 따라 일이 늘어나는 단계는 없다. 이것이 "배열의 인덱스 접근은 상수 시간"이라는 말의 근거다. 범위를 벗어난 접근이 어떻게 드러나는지도 한 번 보아 두자. 길이 5인 배열에서 arr[5]를 읽으면 다음 예외가 난다.

    Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 5 out of bounds for length 5

    인덱스를 모르면 사정이 달라진다

    빠른 것은 "몇 번째 칸"을 알 때뿐이다. "값이 40인 칸이 어디인가"를 물으면 주소 계산식은 쓸모가 없다. 칸의 위치는 값과 아무 관계가 없기 때문이다. 방법은 0번 칸부터 하나씩 읽어 비교하는 것밖에 없고, 찾는 값이 맨 끝에 있거나 아예 없으면 모든 칸을 읽어야 한다. 이것을 선형 탐색(linear search)이라고 한다.

    일상에서 가져온 비유좌석 번호와 사람 이름

    극장에서 "H열 12번"이라는 좌석 번호를 받으면 다른 자리를 살피지 않고 곧장 걸어간다. 좌석이 100개든 1만 개든 걸리는 시간이 거의 같다. 반대로 "김 아무개 씨가 어디 앉았는지 찾아 달라"는 부탁을 받으면 앞줄부터 얼굴을 확인해야 하고, 좌석이 많을수록 오래 걸린다. 배열의 인덱스는 좌석 번호이고, 값으로 찾는 일은 얼굴을 확인하며 도는 일이다. 비유가 맞지 않는 지점도 있다. 극장에서는 먼 좌석까지 걷는 거리가 늘어나지만, 메모리에서는 어느 칸이든 주소 계산의 양이 같다.

    배열이 같은 크기의 칸이 이어진 한 덩어리이고, 인덱스에서 칸의 위치가 계산식 하나로 나온다는 점과 참조 배열의 칸이 객체가 아니라 참조를 담는다는 점을 보여 준다. 흰 배경의 메모리 구조 다이어그램. 화면을 위아래 두 단으로 나눈다. 위 단에는 가로로 길게 이어진 띠 하나가 있다. 띠의 맨 왼쪽은 회색 칸으로 "헤더와 길이"라고 적고, 그 오른쪽으로 같은 너비의 파란 칸 다섯 개가 붙어 있으며 안에 차례로 10, 20, 30, 40, 50이 적혀 있다. 파란 칸 아래에는 작은 글씨로 인덱스 [0], [1], [2], [3], [4]. 띠 위쪽에는 바이트 위치를 나타내는 눈금 16, 20, 24, 28, 32가 파란 칸의 왼쪽 경계마다 적혀 있다. 네 번째 파란 칸(값 40)은 주황색 테두리로 강조하고, 그 위로 말풍선 "16 + 3 × 4 = 28". 띠 왼쪽 바깥에 라벨 "int 배열". 아래 단에도 같은 모양의 띠가 있는데 파란 칸은 세 개이고 안에는 숫자 대신 검은 점이 하나씩 있다. 각 점에서 아래로 화살표가 나가 띠와 떨어진 곳에 흩어져 있는 둥근 상자 세 개를 가리킨다. 둥근 상자에는 "String 객체"라고 적는다. 아래 띠 왼쪽 바깥에 라벨 "참조 배열". 아래 단 오른쪽에 작은 글씨 "칸에는 참조만 들어 있다". 차분한 파랑과 회색, 강조는 주황. 평면적인 기술 도해 스타일. 배열은 같은 크기의 칸이 이어진 한 덩어리여서 인덱스에서 위치가 바로 계산된다. 참조 배열의 칸에는 객체가 아니라 객체의 위치가 들어 있다.

    빅오 표기법: 입력이 커질 때 일이 얼마나 늘어나는가

    방금 "상수 시간"이라는 말을 썼다. 이런 말을 정확하게 하려면 약속이 필요하다. 실행 시간을 초 단위로 재면 기계와 JVM 상태에 따라 값이 달라져서 알고리즘 자체의 성질을 말하기 어렵다. 그래서 시간 대신 입력의 크기 n이 커질 때 기본 연산의 횟수가 어떤 모양으로 늘어나는가를 본다. 이것을 적는 표기가 빅오(Big-O) 표기법이다.

    세 가지 메서드로 시작하자. 첫 원소를 돌려주는 것, 값을 찾는 것, 중복이 있는지 검사하는 것이다. 비교 횟수를 세도록 카운터를 넣었다.

    public class BigODemo {
    static long comparisons = 0;

    static int first(int[] arr) {
        return arr[0];
    }

    static int indexOf(int[] arr, int target) {
        for (int i = 0; i < arr.length; i++) {
            comparisons++;
            if (arr[i] == target) {
                return i;
            }
        }
        return -1;
    }

    static boolean hasDuplicate(int[] arr) {
        for (int i = 0; i < arr.length; i++) {
            for (int j = i + 1; j < arr.length; j++) {
                comparisons++;
                if (arr[i] == arr[j]) {
                    return true;
                }
            }
        }
        return false;
    }

    public static void main(String[] args) {
        int[] arr = new int[1024];
        for (int i = 0; i < arr.length; i++) {
            arr[i] = i;                 // 모두 다른 값
        }
        System.out.println("first: " + first(arr));

        comparisons = 0;
        indexOf(arr, -1);               // 없는 값을 찾는다: 최악의 경우
        System.out.println("indexOf: " + comparisons);

        comparisons = 0;
        hasDuplicate(arr);              // 중복이 없다: 최악의 경우
        System.out.println("hasDuplicate: " + comparisons);
    }
}
    first: 0

hasDuplicate: 523776

    first는 n이 얼마든 칸 하나만 읽는다. indexOf는 최악의 경우 n번 비교한다. hasDuplicate는 서로 다른 두 칸의 쌍을 모두 비교하므로 n(n−1)/2번이다. n이 1,024일 때 1,024 × 1,023 ÷ 2 = 523,776으로 출력과 일치한다.

    정의와 두 가지 규칙

    빅오의 정의는 다음과 같다. 연산 횟수를 n의 함수 f(n)으로 적었을 때, 어떤 양의 상수 c와 어떤 시작점 n₀가 있어서 n₀ 이상의 모든 n에 대해 f(n) ≤ c · g(n)이 성립하면 f(n)은 O(g(n))이라고 한다. 풀어 말하면 "n이 충분히 커지면 f는 g의 상수 배를 넘지 못한다"는 뜻이다. 빅오는 증가 속도의 상한을 말한다.

    흔히 외우는 두 규칙은 이 정의에서 바로 나온다. 첫째, 상수 배수는 버린다. 연산 횟수가 3n + 5라면 n이 5 이상일 때 3n + 5 ≤ 4n이므로 c = 4, n₀ = 5로 정의를 만족한다. 따라서 O(n)이다. 둘째, 차수가 낮은 항은 버린다. n(n−1)/2 = n²/2 − n/2는 언제나 n² 이하이므로 O(n²)이다. 정의에 상수 c가 들어 있기 때문에 계수가 3이든 1/2이든 같은 분류에 들어가는 것이다.

    이 정의로 위의 세 메서드를 분류하면 first는 O(1), indexOf는 O(n), hasDuplicate는 O(n²)이다. O(1)은 "한 번"이라는 뜻이 아니라 "n과 무관한 상수 번"이라는 뜻이다. 배열 원소를 읽을 때의 null 검사, 범위 검사, 주소 계산, 읽기를 모두 세어도 n이 커진다고 늘어나지 않으므로 O(1)이다.

    최선, 평균, 최악

    같은 알고리즘도 입력에 따라 연산 횟수가 달라진다. 선형 탐색은 찾는 값이 0번 칸에 있으면 1번, 맨 끝에 있거나 없으면 n번 비교한다. 찾는 값이 각 칸에 같은 확률로 있다고 가정하면 평균은 (n + 1)/2번이다. 평균도 최악도 n에 비례하므로 둘 다 O(n)이다.

    특별한 언급이 없으면 빅오는 보통 최악의 경우를 말한다. 최악의 경우는 가정 없이 성립하는 보장이기 때문이다. 평균을 말하려면 입력이 어떻게 분포하는지에 대한 가정이 필요하고, 그 가정이 실제와 다르면 평균도 틀린다. 뒤에서 볼 "분할 상환"은 최악도 평균도 아닌 세 번째 관점이다.

    빅오가 말해 주지 않는 것

    빅오는 버리는 것이 많은 표기다. 무엇을 버렸는지 알고 써야 한다.

    • 상수 배수. 둘 다 O(n)인 두 방법이 실제로는 열 배 차이가 날 수 있다. 연산 한 번의 비용이 다르기 때문이다. 빅오는 그 차이를 구분하지 않는다.
    • 작은 n에서의 순서. 정의에 "n₀ 이상에서"라는 조건이 있다. n이 작을 때는 O(n²)인 방법이 O(n log n)인 방법보다 빠를 수 있다.
    • 연산의 실제 비용. "메모리 읽기 한 번"을 모두 같은 비용으로 세지만, 실제로는 읽으려는 위치가 CPU 캐시에 올라와 있는지에 따라 차이가 크다. 연속한 칸을 차례로 읽는 배열과 여기저기 흩어진 노드를 따라가는 연결 리스트가 같은 O(n) 순회에서도 속도가 다른 이유이고, 다음 회차에서 다룬다.

    또 하나, 빅오는 상한이므로 선형 탐색을 O(n²)이라고 불러도 정의상 거짓은 아니다. 다만 쓸모가 없다. 관례적으로는 성립하는 상한 가운데 가장 낮은 것을 적는다.

    배열에 데이터 추가하기: 위치에 따라 달라지는 비용

    배열의 길이는 바뀌지 않으므로, 엄밀히 말하면 배열에 "추가"라는 연산은 없다. 추가처럼 쓰려면 넉넉한 길이로 만들어 두고 앞에서부터 채우면서, 지금 몇 칸이 차 있는지를 따로 세어야 한다. 그 상태에서 새 값을 어디에 넣느냐에 따라 할 일이 달라진다.

    • 맨 뒤에 추가. 차 있는 칸 바로 다음 칸에 대입하면 끝난다. 다른 칸을 건드리지 않는다.
    • 맨 앞에 추가. 0번 칸을 비워야 하므로 기존 값을 모두 한 칸씩 오른쪽으로 옮긴다. n개가 들어 있으면 n번 옮긴다.
    • 중간에 추가. 넣을 위치부터 뒤쪽에 있는 값만 한 칸씩 옮긴다. 위치가 index라면 n − index번이다.
    import java.util.Arrays;

public class ArrayInsertDemo {
    public static void main(String[] args) {
        int[] arr = new int[5];
        arr[0] = 1;
        arr[1] = 2;
        System.out.println(Arrays.toString(arr));

        insert(arr, 2, 0, 3);   // 2개 들어 있는 상태에서 맨 앞(인덱스 0)에 3
        insert(arr, 3, 2, 4);   // 3개 들어 있는 상태에서 중간(인덱스 2)에 4
        insert(arr, 4, 4, 5);   // 4개 들어 있는 상태에서 맨 뒤(인덱스 4)에 5
    }

    // count: 지금 들어 있는 원소 수, index: 넣을 위치
    static void insert(int[] arr, int count, int index, int value) {
        int moves = 0;
        for (int i = count; i > index; i--) {
            arr[i] = arr[i - 1];
            moves++;
        }
        arr[index] = value;
        System.out.println(Arrays.toString(arr) + " index=" + index + ", moves=" + moves);
    }
}

    반복문의 방향에 주의하자. 오른쪽 끝에서 시작해 왼쪽으로 오면서 arr[i] = arr[i - 1]을 한다. 맨 앞에 3을 넣는 첫 호출을 추적하면 이렇다.

    넣을 위치를 찾는 일 자체는 인덱스 계산이므로 O(1)이다. 비용은 전부 "밀기"에서 나온다. 삭제도 대칭이다. 중간의 값을 빼면 그 뒤의 값을 한 칸씩 왼쪽으로 당겨야 빈틈이 생기지 않는다.

    여기까지 오면 배열을 그대로 쓰기 불편한 이유가 둘로 정리된다. 첫째, 길이가 고정이다. 다섯 칸이 다 차면 여섯 번째 값을 넣을 방법이 없고, 그렇다고 처음부터 크게 잡으면 쓰지 않는 칸이 메모리를 차지한다. 둘째, 개수를 세고 값을 미는 코드를 배열을 쓰는 곳마다 반복해서 적어야 한다. 배열 리스트는 이 두 가지를 클래스 하나에 넣어 감춘다.

    넣는 위치에 따라 기존 값을 옮기는 양이 0에서 n까지 달라진다는 것과, 옮기는 순서가 오른쪽 끝부터라는 것을 보여 준다. 흰 배경의 세로 3단 비교 다이어그램. 각 단에는 여섯 칸짜리 가로 배열이 하나씩 그려져 있고 앞의 네 칸에는 A, B, C, D가 들어 있으며 뒤의 두 칸은 비어 있다. 첫째 단 왼쪽 라벨 "맨 뒤에 추가". 다섯째 칸으로 위에서 초록색 블록 "X"가 내려오는 화살표가 있고 다른 칸은 그대로다. 오른쪽에 "이동 0칸". 둘째 단 왼쪽 라벨 "맨 앞에 추가". A, B, C, D 네 칸 각각에서 오른쪽 이웃 칸으로 가는 짧은 주황색 곡선 화살표가 네 개 있고, 화살표에는 오른쪽 것부터 1, 2, 3, 4라는 순서 번호가 붙어 있다. 첫째 칸으로 위에서 초록색 블록 "X"가 내려온다. 오른쪽에 "이동 4칸". 셋째 단 왼쪽 라벨 "중간에 추가". C, D 두 칸에서만 오른쪽 이웃 칸으로 가는 주황색 곡선 화살표가 있고 순서 번호 1, 2가 붙어 있다. 셋째 칸으로 위에서 초록색 블록 "X"가 내려온다. 오른쪽에 "이동 2칸". 그림 맨 아래에 작은 글씨 "오른쪽 끝부터 옮긴다". 차분한 파랑과 회색, 이동은 주황, 새 값은 초록. 평면적인 기술 도해 스타일. 맨 뒤에 넣으면 아무것도 옮기지 않고, 앞쪽에 넣을수록 옮길 칸이 늘어난다. 덮어쓰지 않으려면 오른쪽 끝의 값부터 옮긴다.

    직접 구현 1단계: 용량과 크기를 나눈다

    첫 단계는 배열과 개수 세는 변수를 한 클래스에 넣는 것이다. 아직 길이는 늘어나지 않는다. 어떤 타입이든 담을 수 있도록 칸의 타입은 Object로 한다.

    import java.util.Arrays;

public class FixedList {
    private static final int INITIAL_CAPACITY = 4;

    private Object[] elements;
    private int size = 0;

    public FixedList() {
        elements = new Object[INITIAL_CAPACITY];
    }

    public int size() {
        return size;
    }

    public void add(Object e) {
        elements[size] = e;
        size++;
    }

    public Object get(int index) {
        return elements[index];
    }

    public Object set(int index, Object e) {
        Object old = elements[index];
        elements[index] = e;
        return old;
    }

    public int indexOf(Object o) {
        for (int i = 0; i < size; i++) {
            if (o.equals(elements[i])) {
                return i;
            }
        }
        return -1;
    }

    @Override
    public String toString() {
        return Arrays.toString(Arrays.copyOf(elements, size))
                + " size=" + size + ", capacity=" + elements.length;
    }
}

    이 클래스에는 숫자가 두 개 있고, 둘을 구분하는 것이 배열 리스트 전체의 핵심이다.

    • 용량(capacity): 내부 배열의 길이 elements.length. 담을 수 있는 칸의 수다.
    • 크기(size): 실제로 담긴 원소의 수. 사용자가 보는 리스트의 길이다.

    두 숫자 사이에는 항상 지켜야 하는 조건, 곧 불변식(invariant)이 있다. 0 ≤ size ≤ capacity이고, 인덱스 0부터 size − 1까지가 유효한 원소이며, size부터 capacity − 1까지의 칸은 쓰지 않는 칸이다. 이후의 모든 메서드는 이 조건을 깨지 않도록 작성된다. add의 두 줄을 보면 size가 두 가지 역할을 겸한다는 것을 알 수 있다. 원소의 개수이면서 동시에 다음에 쓸 칸의 인덱스다.

    원소 세 개를 넣은 직후의 메모리는 다음과 같다. 객체가 다섯 개 있다. 리스트 객체, 배열 객체, 문자열 객체 세 개다.

    get과 set은 배열의 인덱스 접근을 그대로 넘겨주므로 O(1)이다. indexOf는 선형 탐색이므로 O(n)이다. 비교에 ==가 아니라 equals를 쓰는 이유는 찾으려는 것이 "같은 객체"가 아니라 "같은 값"이기 때문이다. 반복 범위가 elements.length가 아니라 size인 점도 중요하다. 쓰지 않는 칸의 null까지 비교할 이유가 없다.

    출력에서 두 가지 문제가 드러난다. 하나는 get(3) = null이다. 원소가 세 개뿐인 리스트에 인덱스 3을 물었는데 예외가 나지 않고 null이 나왔다. 배열의 범위 검사는 용량 4를 기준으로 하므로 인덱스 3은 통과한다. JVM이 해 주는 검사는 "배열의 범위"이지 "리스트의 범위"가 아니다. 리스트는 size를 기준으로 한 검사를 스스로 해야 한다.

    다른 하나는 마지막 줄이다. 다섯 번째 원소를 넣자 elements[4]에 대입하려다 배열의 범위 검사에 걸렸다. 스택 트레이스의 첫 줄이 FixedList.add인 것에서 알 수 있듯이 내부 배열의 사정이 예외로 새어 나온 것이다. 이 두 문제를 차례로 고친다.

    직접 구현 2단계: 꽉 차면 더 큰 배열로 옮긴다

    배열의 길이는 바꿀 수 없으므로 "늘린다"는 것은 실제로는 세 동작이다. 더 큰 배열을 새로 만들고, 기존 원소를 새 배열로 복사하고, 필드가 새 배열을 가리키게 바꾼다. 이렇게 필요할 때 내부 배열을 교체해 가며 커지는 구조를 동적 배열(dynamic array)이라고 한다. add에 검사 한 줄과 메서드 하나를 더한다. 이 단계부터 클래스 이름을 GrowList로 바꾼다. 전체 코드는 다음 단계에서 한 번에 싣고, 여기서는 달라진 부분만 본다.

    public void add(Object e) {
    if (size == elements.length) {
        grow();
    }
    elements[size] = e;
    size++;
}

private void grow() {
    int oldCapacity = elements.length;
    int newCapacity = oldCapacity * 2;
    elements = Arrays.copyOf(elements, newCapacity);
}

    Arrays.copyOf(original, newLength)가 앞의 두 동작을 한다. OpenJDK 21의 소스를 보면 Object[]에 대해서는 new Object[newLength]로 새 배열을 만들고 System.arraycopy로 원래 배열과 새 길이 가운데 짧은 쪽만큼을 복사한 뒤 새 배열을 돌려준다. 새 배열에서 복사되지 않은 뒤쪽 칸은 참조형의 기본값인 null로 채워져 있다. 돌려받은 참조를 elements에 대입하는 것이 세 번째 동작이다.

    원소 a부터 i까지 아홉 개를 넣으면서 매번 상태를 출력하면 용량이 바뀌는 지점이 보인다.

    public class GrowListMain {
    public static void main(String[] args) {
        GrowList list = new GrowList();
        for (char c = 'a'; c <= 'i'; c++) {
            list.add(String.valueOf(c));
            System.out.println(list);
        }
    }
}

    세 가지를 짚어 두자. 첫째, 복사되는 것은 참조다. 문자열 객체 "a"부터 "d"는 복사되지 않고 제자리에 있으며, 잠깐 동안 두 배열이 같은 객체들을 가리킨다. 원소 객체가 아무리 커도 확장 비용은 참조 n개를 옮기는 비용이다. 둘째, 옛 배열은 어디서도 참조하지 않게 되므로 가비지 컬렉터가 회수할 대상이 된다. 확장이 일어날 때마다 배열 객체 하나가 쓰레기가 된다. 셋째, (2)의 순간에는 옛 배열과 새 배열이 함께 살아 있다. 용량 c에서 2c로 갈 때 칸 3c개 분량의 메모리가 동시에 필요하다. 원소가 수천만 개인 리스트에서는 이 순간의 메모리 요구가 문제가 될 수 있다.

    일상에서 가져온 비유책장이 꽉 차서 더 큰 책장을 들인다

    칸이 네 개인 책장이 꽉 찼다. 책장에 칸을 덧붙일 수는 없으니 여덟 칸짜리 책장을 새로 들이고, 책을 순서대로 옮겨 꽂고, 옛 책장을 내놓는다. 옮기는 동안에는 방에 책장이 두 개 있어야 한다. 비유가 맞지 않는 지점은 "책을 옮긴다"는 부분이다. 실제로 옮겨지는 것은 책이 아니라 책이 어디 있는지 적은 쪽지(참조)이고, 책(객체)은 힙의 원래 자리에 그대로 있다.

    확장이 새 배열 생성, 참조 복사, 필드 교체의 세 동작이며 원소 객체는 복사되지 않고 옛 배열만 버려진다는 것을 보여 준다. 흰 배경의 메모리 구조 다이어그램. 왼쪽에 둥근 모서리 상자 "리스트 객체"가 있고 안에 두 줄 "elements", "size = 4". 가운데 위쪽에 네 칸짜리 가로 배열이 있고 라벨 "옛 배열 (용량 4)". 가운데 아래쪽에 여덟 칸짜리 가로 배열이 있고 라벨 "새 배열 (용량 8)". 두 배열의 앞 네 칸에는 검은 점이 하나씩 있다. 화면 오른쪽에는 둥근 상자 네 개가 세로로 놓여 있고 각각 "a", "b", "c", "d"라고 적혀 있다. 옛 배열의 네 점과 새 배열의 앞 네 점에서 각각 대응하는 오른쪽 둥근 상자로 가는 가는 화살표가 있어, 상자마다 화살표 두 개가 모인다. 새 배열의 뒤 네 칸은 비어 있고 옅은 회색이다. 옛 배열에서 새 배열로 내려가는 굵은 주황색 화살표에 라벨 "참조만 복사". 리스트 객체의 elements에서 옛 배열로 가는 화살표는 회색 점선에 가위표가 있고, elements에서 새 배열로 가는 화살표는 굵은 파란 실선에 라벨 "필드 교체". 옛 배열 옆에 휴지통 아이콘과 라벨 "GC 대상". 차분한 파랑과 회색, 강조는 주황. 평면적인 기술 도해 스타일. 확장은 새 배열을 만들고 참조를 복사한 뒤 필드를 바꾸는 일이다. 원소 객체는 옮겨지지 않고, 옛 배열만 가비지가 된다.

    분할 상환 분석: 왜 한 칸씩이 아니라 배수로 늘리는가

    확장이 들어가면서 add의 비용이 일정하지 않게 되었다. 대부분의 호출은 대입 한 번으로 끝나지만, 꽉 찬 순간의 호출은 원소 n개를 복사한다. 최악의 경우만 보면 add는 O(n)이다. 그렇다면 원소 n개를 넣는 데 O(n²)이 걸리는가. 그리고 새 용량을 왜 하필 두 배로 했는가. 필요한 만큼만 한 칸씩 늘리면 메모리 낭비가 없지 않은가.

    세어 보면 답이 나온다. 다음 프로그램은 실제 배열을 만들지 않고, 초기 용량 4에서 시작해 원소 n개를 넣는 동안 확장이 몇 번 일어나고 원소 복사가 모두 몇 번 일어나는지만 센다. 증가 정책 네 가지를 비교한다.

    import java.util.function.IntUnaryOperator;

public class GrowthCount {
    public static void main(String[] args) {
        for (int n : new int[]{100, 10_000, 1_000_000}) {
            count("x2  ", n, c -> c * 2);
            count("x1.5", n, c -> c + (c >> 1));
            count("+1  ", n, c -> c + 1);
            count("+10 ", n, c -> c + 10);
        }
    }

    static void count(String policy, int n, IntUnaryOperator next) {
        int capacity = 4;
        long copies = 0;
        int grows = 0;
        for (int size = 0; size < n; size++) {
            if (size == capacity) {      // 꽉 찼다: 기존 원소 size개를 새 배열로 복사
                copies += size;
                capacity = next.applyAsInt(capacity);
                grows++;
            }
        }
        System.out.println(policy + " n=" + n + " grows=" + grows
                + " copies=" + copies + " capacity=" + capacity);
    }
}

    두 배 정책의 총 복사 횟수는 2n을 넘지 않는다

    왜 그런지는 등비수열의 합으로 설명된다. 초기 용량을 c라고 하면 확장은 크기가 c, 2c, 4c, 8c, …일 때 일어나고, 그때마다 그 크기만큼 복사한다. n개를 넣는 동안의 복사 총합은 c + 2c + 4c + … 이고 마지막 항은 n보다 작다. 이 합은 마지막 항의 두 배보다 작다(1 + 2 + 4 + 8 = 15가 16보다 작은 것과 같은 이치다). 따라서 복사 총합은 2n보다 작다. 위 출력에서도 100개에 124번, 10,000개에 16,380번, 1,000,000개에 1,048,572번으로 모두 2n 아래다.

    원소 n개를 넣는 총비용은 대입 n번에 복사 2n번 미만을 더한 3n 미만이다. 이것을 n으로 나누면 add 한 번에 3 미만, 곧 상수다. 이렇게 연산 하나하나가 아니라 연속된 연산 전체의 비용을 구해 연산 횟수로 나눈 값을 분할 상환(amortized) 비용이라고 하고, 동적 배열의 끝 추가는 "분할 상환 O(1)"이라고 말한다.

    이 계산을 저금에 빗대어 보면 기억하기 쉽다. add를 호출할 때마다 3원을 낸다고 하자. 1원은 그 자리에서 대입에 쓰고 2원은 저금한다. 용량이 c에서 2c로 늘어난 직후 리스트에는 원소가 c개 있다. 다음 확장까지 c번 더 추가할 수 있고 그동안 2c원이 모인다. 다음 확장에서 복사할 원소가 정확히 2c개이므로 모아 둔 돈으로 비용이 치러진다. 비싼 연산의 비용을 그 앞의 싼 연산들이 나누어 낸 셈이다.

    고정 폭 정책은 왜 제곱이 되는가

    한 번에 k칸씩 늘리면 확장이 약 n/k번 일어나고, 각 확장에서 복사하는 양은 k, 2k, 3k, …로 늘어난다. 등차수열의 합이므로 총합은 약 n²/(2k)다. k = 1이면 n²/2, k = 10이면 n²/20이고 위 출력의 값과 맞는다. k를 키우면 상수가 줄어들 뿐 n²이라는 모양은 그대로다. 확장 횟수가 n에 비례하는 한 제곱을 벗어날 수 없다. 배수로 늘려야 확장 횟수가 log n으로 줄고, 그래야 총합이 n에 비례한다.

    분할 상환은 평균이 아니다

    "평균적으로 O(1)"과 "분할 상환 O(1)"은 다른 말이다. 평균은 입력의 분포를 가정하고 기댓값을 구한다. 분할 상환에는 확률 가정이 없다. 어떤 순서로 호출하든 n번의 add 전체가 3n 안에 끝난다는 것이 증명된 보장이다.

    반대로 분할 상환이 말해 주지 않는 것도 분명하다. 개별 호출의 최악은 여전히 O(n)이다. 백만 번째 근처의 add 한 번이 백만 개를 복사할 수 있다. 전체 처리량을 따지는 일에서는 문제가 없지만, 호출 하나하나의 응답 시간이 고르게 나와야 하는 곳에서는 이 한 번이 눈에 띈다. 넣을 개수를 미리 안다면 처음부터 그 용량으로 만들어 확장을 없애는 것이 대응책이다.

    실제 ArrayList의 증가 정책

    배수는 2가 아니어도 된다. 1보다 큰 배수이면 총 복사 횟수가 n에 비례한다. 정확히 1.5배씩 늘린다면 복사 총합은 3n보다 작다(공비가 1.5인 등비수열의 합은 마지막 항의 세 배보다 작다). 위 출력의 x1.5 줄은 정수로 내림하는 1.5배 정책인데, 백만 개에 약 210만 번으로 역시 n에 비례한다. 두 배보다 복사는 많지만 확장 직후에 비어 있는 칸이 적다. 배수가 클수록 복사가 줄고 낭비되는 칸이 늘어나는, 시간과 공간의 교환이다.

    java.util.ArrayList의 API 문서는 정책을 일부러 정하지 않는다. 문서의 문장은 "The details of the growth policy are not specified beyond the fact that adding an element has constant amortized time cost"이다. 약속한 것은 분할 상환 상수 시간뿐이고 구체적인 배수는 구현의 자유다. OpenJDK 21의 구현은 다음과 같다.

    int newCapacity = ArraysSupport.newLength(oldCapacity,
        minCapacity - oldCapacity, /* minimum growth */
        oldCapacity >> 1           /* preferred growth */);
return elementData = Arrays.copyOf(elementData, newCapacity);

    선호하는 증가분이 oldCapacity >> 1, 곧 현재 용량의 절반이다. 새 용량은 현재 용량의 1.5배가 된다. 정수 연산이므로 소수점 아래는 버려진다. 확장의 나머지 절반은 우리가 만든 것과 같은 Arrays.copyOf다. 또 하나 읽을 것은 이 코드가 실행되지 않는 경우다. 인자 없는 생성자로 만든 리스트는 길이 0인 공유 배열을 가리킨 채 시작하고, 첫 원소가 들어올 때 grow의 다른 가지에서 비로소 용량 10짜리 배열을 만든다(DEFAULT_CAPACITY = 10). API 문서는 이 생성자를 "Constructs an empty list with an initial capacity of ten"이라고 설명하지만, 이 구현에서 실제 할당은 첫 add까지 미뤄진다. 만들어 놓고 쓰지 않는 리스트가 배열을 차지하지 않게 하려는 것이다.

    리플렉션으로 내부 배열의 길이를 읽어 확인할 수 있다. JDK 내부 필드에 접근하므로 실행할 때 --add-opens java.base/java.util=ALL-UNNAMED 옵션이 필요하다.

    import java.lang.reflect.Field;
import java.util.ArrayList;

public class RealCapacity {
    public static void main(String[] args) throws Exception {
        Field f = ArrayList.class.getDeclaredField("elementData");
        f.setAccessible(true);

        ArrayList list = new ArrayList<>();
        int last = ((Object[]) f.get(list)).length;
        System.out.println("size=0 capacity=" + last);
        for (int i = 1; i <= 120; i++) {
            list.add(i);
            int capacity = ((Object[]) f.get(list)).length;
            if (capacity != last) {
                System.out.println("size=" + list.size() + " capacity " + last + " -> " + capacity);
                last = capacity;
            }
        }
    }
}

ArraysSupport.newLength는 선호 증가분과 최소 증가분 가운데 큰 쪽을 더한다. 그래서 용량 1에서 시작한 리스트(new ArrayList<>(1))는 절반이 0이어도 멈추지 않고 1 → 2 → 3 → 4 → 6 → 9 → 13으로 커진다. 같은 메서드에는 상한도 있다. 선호하는 길이가 Integer.MAX_VALUE - 8을 넘으면 그 값으로 제한하고(꼭 필요한 길이가 그보다 크면 필요한 길이를 쓴다), 필요한 길이가 int 범위를 넘으면 OutOfMemoryError를 던진다. 배열의 인덱스가 int이므로(JLS §10.4) 배열 리스트가 담을 수 있는 원소 수에는 약 21억 개라는 천장이 있다.

    이 장의 핵심

    동적 배열의 끝 추가가 빠른 것은 확장이 없어서가 아니라 확장이 드물어지도록 용량을 배수로 늘리기 때문이다. 배수로 늘리면 n개를 넣는 동안의 복사 총합이 n에 비례하고, 고정 폭으로 늘리면 n²에 비례한다. API 문서가 약속하는 것은 이 "분할 상환 상수 시간"까지이고, 1.5배나 초기 용량 10 같은 숫자는 구현의 선택이다.

    대부분의 add는 비용 1이고 확장이 일어나는 호출만 높이 솟지만, 솟는 간격이 두 배씩 벌어져 누적 비용이 직선 아래에 머문다는 것을 보여 준다. 흰 배경의 막대 그래프. 가로축 라벨 "add 호출 순서 (1번째 ~ 17번째)", 세로축 라벨 "그 호출의 비용". 가로축에 1부터 17까지 눈금이 있고 각 눈금 위에 막대가 하나씩 있다. 대부분의 막대는 높이 1의 낮은 파란 막대다. 5번째, 9번째, 17번째 막대만 주황색으로 높이 솟아 있으며 높이는 각각 5, 9, 17이고 막대 위에 "복사 4 + 대입 1", "복사 8 + 대입 1", "복사 16 + 대입 1"이라고 적혀 있다. 솟은 막대 사이의 간격이 4, 8로 점점 벌어지는 것을 아래쪽 양방향 화살표로 표시하고 "간격이 두 배씩 벌어진다"라고 적는다. 그래프 위에 겹쳐서 초록색 점선 직선이 왼쪽 아래에서 오른쪽 위로 올라가고 라벨 "호출당 3씩 낸 저금". 그 아래를 따라가는 회색 계단 모양 선에 라벨 "실제 누적 비용". 계단 선은 언제나 초록 점선 아래에 있다. 차분한 파랑과 회색, 확장은 주황, 상한선은 초록. 평면적인 기술 도해 스타일. 확장이 일어나는 호출은 비싸지만 그 간격이 두 배씩 벌어진다. 누적 비용은 호출당 3이라는 직선을 넘지 않는다.

    직접 구현 3단계: 중간 삽입과 삭제, 그리고 범위 검사

    이제 원하는 위치에 넣는 add(index, e)와 원하는 위치의 원소를 빼는 remove(index)를 더한다. 1단계에서 미뤄 둔 범위 검사도 함께 넣는다. 이 단계의 전체 코드다.

    import java.util.Arrays;
import java.util.Objects;

public class GrowList {
    private static final int INITIAL_CAPACITY = 4;

    private Object[] elements;
    private int size = 0;

    public GrowList() {
        elements = new Object[INITIAL_CAPACITY];
    }

    public int size() {
        return size;
    }

    public void add(Object e) {
        if (size == elements.length) {
            grow();
        }
        elements[size] = e;
        size++;
    }

    public void add(int index, Object e) {
        Objects.checkIndex(index, size + 1);
        if (size == elements.length) {
            grow();
        }
        for (int i = size; i > index; i--) {
            elements[i] = elements[i - 1];
        }
        elements[index] = e;
        size++;
    }

    public Object remove(int index) {
        Objects.checkIndex(index, size);
        Object old = elements[index];
        for (int i = index; i < size - 1; i++) {
            elements[i] = elements[i + 1];
        }
        size--;
        elements[size] = null;
        return old;
    }

    public Object get(int index) {
        Objects.checkIndex(index, size);
        return elements[index];
    }

    public Object set(int index, Object e) {
        Objects.checkIndex(index, size);
        Object old = elements[index];
        elements[index] = e;
        return old;
    }

    public int indexOf(Object o) {
        for (int i = 0; i < size; i++) {
            if (Objects.equals(o, elements[i])) {
                return i;
            }
        }
        return -1;
    }

    private void grow() {
        int oldCapacity = elements.length;
        int newCapacity = oldCapacity * 2;
        elements = Arrays.copyOf(elements, newCapacity);
    }

    @Override
    public String toString() {
        return Arrays.toString(Arrays.copyOf(elements, size))
                + " size=" + size + ", capacity=" + elements.length;
    }
}

    Objects.checkIndex(index, length)는 index가 0 이상 length 미만이 아니면 IndexOutOfBoundsException을 던지는 표준 메서드다. get, set, remove는 이미 있는 원소를 가리켜야 하므로 length 자리에 size를 넘긴다. add(index, e)는 맨 뒤 바로 다음 위치, 곧 인덱스 size에도 넣을 수 있어야 하므로 size + 1을 넘긴다. 이제 범위의 기준이 배열의 길이가 아니라 리스트의 크기가 되었다. indexOf도 Objects.equals로 바꿔 null을 찾아도 예외가 나지 않게 했다.

    삭제를 한 줄씩 따라가기

    삭제는 삽입의 반대 방향이다. 지울 칸 뒤의 원소를 왼쪽 것부터 차례로 한 칸씩 당긴다. remove(0)을 추적하면 이렇다.

    호출 전               [X, a, Y, b, c, Z, null, null]    size=6
old = elements[0]     old = X
i=0 ~ i=4             [a, Y, b, c, Z, Z, null, null]    한 칸씩 왼쪽으로
size--                size=5  (인덱스 5의 Z는 쓰지 않는 칸에 남은 참조)
elements[5] = null    [a, Y, b, c, Z, null, null, null]

    마지막 줄 elements[size] = null은 없어도 리스트의 동작은 달라지지 않는다. size가 5이므로 인덱스 5는 범위 검사에서 걸러지고 toString에도 나오지 않는다. 그런데도 이 줄이 필요한 이유는 가비지 컬렉션 때문이다. 가비지 컬렉터는 어디선가 참조를 따라 도달할 수 있는 객체를 살아 있다고 본다. 배열의 쓰지 않는 칸에 참조가 남아 있으면 그 객체는 리스트 → 배열 → 칸을 따라 여전히 도달 가능하다. 프로그램은 그 객체를 다시 쓸 일이 없는데 메모리는 회수되지 않는다.

    위 추적에서는 남은 참조가 리스트에 아직 들어 있는 Z를 가리키므로 당장 해가 없어 보인다. 하지만 마지막 원소를 지우는 remove(3)의 경우를 보면 다르다. 반복문은 한 번도 돌지 않고 size만 3으로 줄어든다. null을 넣지 않으면 인덱스 3의 칸이 리스트에서 빠진 Z를 계속 붙들고 있게 된다. OpenJDK 21의 ArrayList도 삭제의 마지막 문장이 es[size = newSize] = null;이다.

    출력의 마지막 세 줄도 읽어 두자. 삭제를 세 번 했지만 용량은 8에서 줄지 않았다. 이 구현에는 배열을 줄이는 코드가 없다. 그리고 예외 메시지 두 개의 length가 다르다. get(3)은 size 3을 기준으로 검사했고, add(5, "Q")는 size + 1인 4를 기준으로 검사했다.

    System.arraycopy로 한 번에 옮기기

    밀고 당기는 반복문은 같은 배열 안에서 구간 하나를 한 칸 옆으로 복사하는 일이다. 표준 라이브러리에 이 일을 하는 메서드가 있다. System.arraycopy(src, srcPos, dest, destPos, length)다. 원본과 대상이 같은 배열이고 구간이 겹쳐도 된다. API 문서는 이 경우 원본 구간을 임시 배열에 먼저 복사한 뒤 대상 위치에 복사한 것처럼 동작한다고 정해 두었다. 그래서 호출하는 쪽은 "오른쪽부터 옮길지 왼쪽부터 옮길지"를 신경 쓰지 않아도 된다.

    // 삽입: index부터 (size - index)개를 한 칸 오른쪽으로
System.arraycopy(elements, index, elements, index + 1, size - index);

// 삭제: index + 1부터 (size - index - 1)개를 한 칸 왼쪽으로
System.arraycopy(elements, index + 1, elements, index, size - index - 1);

    옮기는 원소의 수는 반복문과 같으므로 빅오는 달라지지 않는다. 달라질 수 있는 것은 상수다. OpenJDK 21 소스에서 System.arraycopy는 native 메서드이고 @IntrinsicCandidate로 표시되어 있다. 자바로 쓴 반복문을 그대로 실행하는 대신 JVM이 구간 복사 전용 구현으로 처리할 수 있다는 뜻이다. OpenJDK의 ArrayList도 삽입과 삭제에 System.arraycopy를 쓴다. 다음 단계의 코드에서는 이것으로 바꾼다.

    연산별 비용

    연산하는 일비용
    get(index), set(index, e)범위 검사 뒤 배열 칸 하나 접근O(1)
    add(e)끝 칸에 대입, 가끔 확장분할 상환 O(1), 개별 최악 O(n)
    add(index, e)뒤쪽 size − index개를 민다O(n), 맨 뒤이면 끝 추가와 같다
    remove(index)뒤쪽 size − index − 1개를 당긴다O(n), 맨 뒤이면 O(1)
    indexOf(o)앞에서부터 equals 비교O(n)

    이 표에서 조심할 조합이 있다. 맨 앞에 넣기를 n번 반복하면 옮기는 횟수가 0 + 1 + 2 + … + (n − 1) = n(n − 1)/2가 되어 O(n²)이다. 1,000번이면 499,500번을 옮긴다. 한 번의 O(n)은 대수롭지 않아 보여도 반복문 안에 들어가면 제곱이 된다.

    import java.util.Arrays;
import java.util.Objects;

public class TypedList {
    private static final int INITIAL_CAPACITY = 4;

    private Object[] elements;
    private int size = 0;

    public TypedList() {
        elements = new Object[INITIAL_CAPACITY];
    }

    public int size() {
        return size;
    }

    public void add(E e) {
        if (size == elements.length) {
            grow();
        }
        elements[size] = e;
        size++;
    }

    public void add(int index, E e) {
        Objects.checkIndex(index, size + 1);
        if (size == elements.length) {
            grow();
        }
        System.arraycopy(elements, index, elements, index + 1, size - index);
        elements[index] = e;
        size++;
    }

    public E remove(int index) {
        E old = get(index);
        System.arraycopy(elements, index + 1, elements, index, size - index - 1);
        size--;
        elements[size] = null;
        return old;
    }

    @SuppressWarnings("unchecked")
    public E get(int index) {
        Objects.checkIndex(index, size);
        return (E) elements[index];
    }

    public E set(int index, E e) {
        E old = get(index);
        elements[index] = e;
        return old;
    }

    public int indexOf(Object o) {
        for (int i = 0; i < size; i++) {
            if (Objects.equals(o, elements[i])) {
                return i;
            }
        }
        return -1;
    }

    private void grow() {
        elements = Arrays.copyOf(elements, elements.length * 2);
    }

    @Override
    public String toString() {
        return Arrays.toString(Arrays.copyOf(elements, size))
                + " size=" + size + ", capacity=" + elements.length;
    }

    필드를 E[] 타입으로 선언하는 2번 줄은 문제가 없다. 오류는 배열을 만드는 5번 줄에서 난다. JLS §15.10.1은 배열 생성식의 원소 타입이 실체화 가능 타입(reifiable type)이 아니면 컴파일 오류라고 규정한다. 실체화 가능 타입은 JLS §4.7의 용어로, 컴파일 과정에서 타입 정보 일부가 소거되기 때문에 실행 시점에 온전히 남아 있는 타입만을 가리킨다. 제네릭이 아닌 클래스, 로 타입, 기본형 등이 여기에 들어가고 타입 변수 E는 들어가지 않는다.

    배열을 만들 때 왜 실행 시점의 타입이 필요한가. 이유는 두 층에 있다.

    첫째, 배열 생성 명령 자체가 구성 요소의 클래스를 요구한다. new Object[n]을 컴파일해 javap -c로 보면 anewarray #2 // class java/lang/Object라는 명령이 나온다. anewarray는 어떤 클래스의 배열을 만들지를 상수 풀의 클래스 참조로 받는다. 앞 회차에서 확인했듯이 E는 소거되어 메서드의 디스크립터와 명령에는 Object로만 남는다. TypedList과 TypedList가 같은 클래스 하나를 공유하므로, 생성자 안의 new E[n]이 어느 쪽 배열을 만들어야 하는지 그 코드로서는 알 길이 없다.

    둘째, 배열은 자기 구성 요소의 타입을 기억하고 있다가 값을 저장할 때마다 검사한다. 자바의 배열은 공변이어서 String[]은 Object[] 타입의 변수에 대입할 수 있다. 그 대신 JLS §10.5에 따라 참조 배열의 칸에 값을 넣을 때마다 실행 시점 검사가 일어난다.

    Object[]로 만들고 꺼낼 때 캐스트한다

    이 캐스트가 안전하다는 것은 누가 보증하는가

    컴파일러는 보증하지 못한다. 그래서 경고를 낸 것이다. 보증은 클래스를 만든 사람이 논증으로 해야 한다. 논증은 짧다. elements는 private이고 배열의 참조를 밖으로 내보내는 메서드가 없다. 배열에 값을 써넣는 곳은 add(E), add(int, E), set(int, E)와 null을 넣는 remove뿐이다. 앞의 세 메서드는 매개변수 타입이 E여서 컴파일러가 호출 지점마다 타입을 검사한다. 따라서 배열에 들어 있는 null이 아닌 값은 모두 E이고, 꺼낼 때의 캐스트는 실패할 수 없다.

    @SuppressWarnings("unchecked")는 "이 논증을 했다"는 표시다. 그러므로 붙이는 범위는 논증이 미치는 가장 좁은 곳이어야 한다. 클래스 전체에 붙이면 나중에 추가된 다른 비검사 연산의 경고까지 함께 사라진다. 그리고 이 논증에는 전제가 하나 있다. 사용하는 쪽이 로 타입으로 컴파일러의 검사를 우회하지 않는다는 것이다. 앞 회차에서 본 힙 오염(heap pollution)이 그 전제가 깨진 경우다.

    배열을 E[]로 캐스트해 두는 방식과 그 함정

    캐스트를 꺼낼 때마다 하는 대신 배열을 만들 때 한 번만 하는 방법도 있다. (E[]) new Object[n]으로 만들어 E[] 타입 필드에 넣는 것이다. 클래스 안에서는 E[]가 Object[]로 소거되므로 잘 동작한다. 문제는 그 배열이 E[]라는 타입을 달고 클래스 밖으로 나갈 때 생긴다.

    private E[] items;

    @SuppressWarnings("unchecked")

    배열 리스트의 성능과 한계

    배열 리스트의 강점은 모두 배열에서 온다. 인덱스로 읽고 쓰는 것이 O(1)이고, 끝에 추가하는 것이 분할 상환 O(1)이다. 그리고 참조들이 메모리에 연속해 있다. CPU는 메모리를 한 칸씩이 아니라 이웃한 구간 단위로 캐시에 가져오므로, 배열을 앞에서부터 차례로 읽으면 다음에 읽을 칸이 이미 캐시에 올라와 있을 가능성이 높다. 빅오에는 나타나지 않지만 실제 순회 속도에 영향을 주는 성질이고, 다음 회차에서 연결 리스트와 비교하며 다룬다. 다만 연속해 있는 것은 참조이고, 참조가 가리키는 객체들이 힙에서 서로 가까이 있다는 보장은 없다.

    약점도 모두 배열에서 온다.

    • 앞쪽 삽입과 삭제가 O(n)이다. 맨 앞에 넣거나 맨 앞에서 빼는 일을 반복하는 용도에는 맞지 않는다.
    • 쓰지 않는 칸이 있다. 두 배 정책이라면 확장 직후에 용량의 절반 가까이가 비어 있다. 1.5배 정책은 확장 직후의 빈 칸을 용량의 3분의 1 가까이로 줄이는 대신 확장을 더 자주 한다.
    • 확장하는 순간이 비싸다. 원소 전체의 참조를 복사하고, 그동안 옛 배열과 새 배열이 함께 메모리를 차지한다.
    • 줄어들지 않는다. 원소를 지워도 내부 배열은 그대로다. 한때 컸던 리스트는 비워도 큰 배열을 쥐고 있다.

    기본형을 담을 때의 사정도 알아 두자. ArrayList의 칸에는 int 값이 아니라 Integer 객체에 대한 참조가 들어 있다. 위의 javap 출력에서 numbers.add(1)이 Integer.valueOf를 거치고 numbers.get(i)가 checkcast Integer와 intValue를 거치는 것을 볼 수 있다. 값이 칸에 직접 들어 있는 int[]와 달리, 칸에서 참조를 읽고 그 참조가 가리키는 Integer 객체에서 값을 읽는 한 단계가 더 있다.

    앞쪽 삽입이 느리다는 약점을 정면으로 겨냥한 구조가 연결 리스트다. 다음 회차에서는 같은 인터페이스를 노드와 참조로 구현해 보고, 무엇을 얻고 무엇을 내주는지 같은 방법으로 따진다.

    흔한 오해

    "ArrayList의 add는 언제나 O(1)이다"

    API 문서의 표현은 "amortized constant time"이다. n번을 합쳐서 O(n)이라는 뜻이고, 한 번의 호출이 원소 전체를 복사할 수 있다는 사실은 그대로다. 그리고 이 말은 끝에 추가하는 add(e)에 대한 것이다. 위치를 지정하는 add(index, e)는 O(n)이다.

    "ArrayList는 용량을 두 배로 늘린다"

    명세가 정한 배수는 없다. OpenJDK 21의 구현은 약 1.5배다. 다른 구현이나 다른 버전이 다른 숫자를 써도 문서의 약속을 어기는 것이 아니다. 특정 배수에 기대어 메모리 사용량을 계산한 코드는 구현 세부에 의존하고 있는 것이다.

    "new ArrayList<>(100)으로 만들면 원소가 100개 있다"

    생성자의 인자는 용량이지 크기가 아니다. 이렇게 만든 직후의 size()는 0이고 get(0)은 IndexOutOfBoundsException: Index 0 out of bounds for length 0을 던진다. 배열 new String[100]이 곧바로 인덱스 0부터 99까지 쓸 수 있는 것과 다르다. 용량과 크기를 구분하면 헷갈릴 이유가 없다.

    "원소를 지우면 메모리가 줄어든다"

    지워진 원소 객체는 다른 곳에서 참조하지 않는다면 회수될 수 있다. 그러나 리스트의 내부 배열은 줄어들지 않는다. 용량까지 줄이려면 trimToSize()를 호출하거나 필요한 원소만 담은 새 리스트를 만들어야 한다.

    "O(1)은 O(n)보다 항상 빠르다"

    빅오는 n이 커질 때의 증가 모양이지 걸리는 시간이 아니다. 원소가 몇 개뿐인 리스트에서 중간 삽입의 O(n)은 참조 몇 개를 옮기는 일이다. ArrayList의 API 문서도 선형 시간 연산들에 대해 "The constant factor is low compared to that for the LinkedList implementation"이라고 적고 있다. 분류가 같아도 상수가 다르고, 분류가 달라도 n이 작으면 순서가 뒤집힐 수 있다.

    다른 주제와의 연결

    "배열 하나와 개수 하나, 모자라면 더 큰 배열로 옮긴다"는 구조는 ArrayList에만 있는 것이 아니다. 중급 1편에서 문자열을 이어 붙일 때 쓴 StringBuilder도 같은 구조다. OpenJDK 21의 AbstractStringBuilder는 내부 배열이 모자라면 ArrayList와 같은 ArraysSupport.newLength로 새 길이를 정하는데, 선호하는 새 용량이 현재 용량의 두 배에 2를 더한 값이다. 반복문 안에서 append를 수없이 호출해도 전체 비용이 길이에 비례하는 이유가 이 회차의 분할 상환 분석이다.

    이 권의 뒤쪽에서 다룰 해시 기반 컬렉션에서도 같은 생각이 다시 나온다. HashMap은 내부 배열이 일정 비율 이상 차면 두 배 길이의 배열로 옮겨 간다. 거기서는 옮길 때 원소의 위치를 다시 계산해야 한다는 점이 더해진다. 6회부터 9회에 걸쳐 본다.

    동시성과도 닿아 있다. add의 두 줄 elements[size] = e; size++;는 한 번에 일어나는 연산이 아니다. 두 스레드가 같은 size를 읽으면 같은 칸에 써서 한쪽의 원소가 사라진다. ArrayList의 API 문서가 "this implementation is not synchronized"라고 굵게 적어 둔 까닭이고, 여러 스레드가 함께 쓰는 리스트의 문제는 자바 고급편의 주제다.

    마지막으로, 이 회차에서 익힌 분석 방법 자체가 이후 회차의 도구다. 자료 구조를 만나면 "메모리에 어떤 모양으로 놓이는가"를 그리고, 연산마다 "무엇을 몇 번 하는가"를 세고, 그것을 빅오로 적는다. 연결 리스트, 해시 테이블, 트리를 모두 같은 순서로 살펴본다.
    배열의 인덱스 접근
    배열은 같은 크기의 칸이 이어진 한 덩어리여서 칸의 위치가 "시작 + 인덱스 × 칸 크기"로 계산된다. 원소 수와 무관하므로 O(1)이고, 모든 접근은 실행 시점에 범위가 검사된다.
    빅오 표기법
    입력 크기 n이 커질 때 연산 횟수의 증가 모양을 상한으로 적는 표기다. 상수 배수와 낮은 차수의 항을 버리므로 실제 시간이나 작은 n에서의 우열은 말해 주지 않는다.
    배열에 값 넣기의 비용
    맨 뒤는 대입 한 번으로 O(1), 맨 앞이나 중간은 뒤쪽 원소를 한 칸씩 밀어야 해서 O(n)이다. 덮어쓰지 않으려면 오른쪽 끝부터 옮긴다.
    용량과 크기
    용량은 내부 배열의 길이, 크기는 실제로 담긴 원소의 수다. 리스트의 범위 검사는 배열 길이가 아니라 크기를 기준으로 스스로 해야 한다.
    동적 배열의 확장
    배열은 늘릴 수 없으므로 더 큰 배열을 만들고 참조를 복사한 뒤 필드를 바꾼다. 원소 객체는 복사되지 않고 옛 배열은 가비지가 된다.
    분할 상환 O(1)
    용량을 배수로 늘리면 n개를 추가하는 동안의 복사 총합이 n에 비례하므로 한 번당 비용이 상수가 된다. 고정 폭으로 늘리면 총합이 n²에 비례한다. 개별 호출의 최악은 여전히 O(n)이다.
    삭제 뒤의 null 대입
    크기만 줄이고 칸의 참조를 남겨 두면 리스트에서 빠진 객체가 계속 도달 가능해 회수되지 않는다. 쓰지 않게 된 칸은 null로 지운다.
    제네릭 배열과 비검사 캐스트
    타입 변수는 실체화 가능 타입이 아니어서 new E[n]은 컴파일되지 않는다. Object[]로 만들고 꺼낼 때 (E)로 캐스트하며, 그 안전성은 "E만 넣는다"는 클래스의 불변식이 보증한다.
    ArrayList의 명세와 구현
    API 문서는 끝 추가의 분할 상환 상수 시간만 약속하고 증가 정책은 정하지 않는다. OpenJDK 21은 기본 용량 10을 첫 추가 때 할당하고 약 1.5배씩 늘린다.

    실무에서 다시 판단하면, 이 회차의 지식이 가장 자주 쓰이는 곳은 "리스트에 몇 개가 들어갈지 아는가"라는 질문이다. 조회 결과를 변환해 담는 것처럼 개수를 미리 아는 경우에는 그 개수를 초기 용량으로 주면 중간 확장과 그때마다 버려지는 배열이 없어진다. 개수를 모른다면 기본값으로 충분하다. 분할 상환 분석이 보여 주듯 확장의 총비용은 원소 수에 비례할 뿐이다. 어림짐작으로 큰 용량을 주는 것은 오히려 쓰지 않는 칸을 늘린다.

    성능 문제로 이어지는 것은 대개 확장이 아니라 반복문 안의 O(n) 연산이다. 리스트의 맨 앞에서 하나씩 꺼내 처리하는 코드, 조건에 맞는 원소를 인덱스로 하나씩 지우는 코드, 반복문 안에서 indexOf나 contains로 중복을 확인하는 코드는 모두 전체로는 O(n²)이다. 데이터가 수백 건일 때는 드러나지 않다가 수십만 건이 되면 갑자기 느려진다. 이럴 때는 연산을 바꾸거나 구조를 바꾼다. 남길 원소만 새 리스트에 담으면 O(n)이고, 앞에서 꺼내는 용도라면 9회에서 다룰 큐 구현이 맞고, 포함 여부를 자주 묻는다면 7회의 해시 기반 집합이 맞다.

    메모리 쪽에서는 두 가지를 기억해 둔다. 아주 큰 리스트가 확장되는 순간에는 옛 배열과 새 배열이 함께 필요하므로, 힙 여유가 빠듯한 상황에서 리스트 하나의 확장이 메모리 부족의 계기가 될 수 있다. 그리고 오래 살아남는 리스트가 한때 커졌다가 대부분 비워졌다면 내부 배열은 큰 채로 남아 있다. 캐시나 버퍼처럼 수명이 긴 객체가 리스트를 쥐고 있을 때는 비운 뒤 용량까지 줄일지 따져 볼 만하다.

    판단이 달라지는 조건도 있다. 호출 하나하나의 지연이 고르게 나와야 하는 경로에서는 분할 상환 보장만으로 부족하고, 미리 용량을 확보해 확장 자체를 없애야 한다. 반대로 원소가 몇 개 되지 않는 리스트라면 이 모든 고려가 의미 없다. 빅오로 가려낸 후보를 실제 데이터 크기에서 측정해 확인하는 것이 마지막 단계다.

A, B를 넣으면 배열은 [A, B, null, null], size=2다. remove(1)에서 반복문은 돌지 않고 size만 1이 된다. null 대입이 없으므로 배열은 여전히 [A, B, null, null]이다. 리스트의 관점에서 B는 없는 원소지만, 리스트 객체 → elements 배열 → 인덱스 1의 칸을 따라 B에 도달할 수 있으므로 B는 가비지 컬렉션의 대상이 아니다. 이 상태에서 add(C)를 호출하면 elements[1] = C가 실행되어 B를 가리키던 참조가 덮어써지고, 다른 곳에서 B를 참조하지 않는다면 그제야 B가 회수 대상이 된다. 곧 이 버그는 "언젠가 덮어써질 때까지" 객체를 붙들고 있는 형태로 나타나며, 크게 자랐다가 줄어든 뒤 다시 자라지 않는 리스트에서는 붙들린 객체가 리스트의 수명 내내 남는다.

     길이가 100만인 int 배열에서 arr[999_999]를 읽는 일과 arr[0]을 읽는 일의 연산량이 같은 이유로 가장 정확한 것은? JIT 컴파일러가 자주 읽는 칸의 값을 따로 캐시해 두기 때문이다. 배열이 내부적으로 인덱스를 키로 하는 해시 테이블로 구현되어 있기 때문이다. 칸의 크기가 모두 같고 연속해 있어서, 시작 위치에 인덱스 × 칸 크기를 더하면 칸의 위치가 바로 계산되기 때문이다. JVM이 배열을 만들 때 모든 칸의 주소를 별도의 표에 기록해 두고 그 표를 조회하기 때문이다. 배열은 같은 크기의 칸이 이어진 한 덩어리이므로 칸의 위치는 찾는 것이 아니라 계산하는 것이다. 계산의 양은 인덱스의 크기나 원소 수와 무관하다. 캐시나 별도의 주소 표, 해시 테이블은 필요하지 않고, 배열 접근 명령(iaload 등)이 하는 일은 null 검사, 범위 검사, 칸 읽기뿐이다. 동적 배열의 확장 정책을 "꽉 차면 1,000칸을 늘린다"로 정했다. 원소 n개를 끝에 차례로 추가할 때 원소 복사의 총횟수에 대한 설명으로 옳은 것은? 1,000은 충분히 큰 수이므로 총횟수가 n에 비례하고, 끝 추가는 분할 상환 O(1)이다. 확장 횟수가 약 n/1,000번으로 여전히 n에 비례하고 확장마다 복사량이 늘어나므로, 총횟수는 n²에 비례한다. 확장할 때마다 후보가 절반으로 줄어들므로 총횟수는 n log n에 비례한다. 한 번에 넉넉히 늘리므로 n이 얼마든 확장은 한 번만 일어난다. 고정 폭 k로 늘리면 확장이 약 n/k번 일어나고 각 확장의 복사량은 k, 2k, 3k, …로 커져 총합이 약 n²/(2k)가 된다. k를 키우면 상수가 줄 뿐 제곱이라는 모양은 그대로다. 분할 상환 O(1)이 되려면 확장 횟수가 log n 수준으로 줄어야 하고, 그러려면 용량을 배수로 늘려야 한다. 본문의 TypedList에서 get 메서드 안의 (E) elements[index]에 대한 설명으로 옳은 것은? get 메서드의 바이트코드 안에서 checkcast String이 실행되어 원소의 타입을 검사한다. 컴파일러가 E를 String으로 치환한 get 메서드를 타입 인자마다 따로 만든다. 비검사 캐스트는 실행 중 언제든 실패할 수 있으므로 이 구현은 타입 안전하지 않다. E가 Object로 소거되어 get 안에는 캐스트 명령이 없고, 검사는 호출한 쪽에 컴파일러가 넣은 checkcast String에서 일어난다. javap로 보면 get은 aaload 뒤에 바로 areturn이고, 호출 지점에 checkcast가 있다. 클래스는 타입 인자와 무관하게 하나뿐이므로 타입 인자별 메서드는 만들어지지 않는다. 비검사 캐스트는 컴파일러가 안전성을 확인해 주지 못한다는 뜻이지 안전하지 않다는 뜻이 아니다. 이 클래스에서는 배열에 E만 들어간다는 불변식이 안전성을 보증한다. remove(index)에서 size를 줄인 뒤 elements[size] = null을 실행하는 이유는? 배열 칸에 남은 참조 때문에, 리스트에서 뺀 객체가 계속 도달 가능한 상태로 남아 회수되지 못하는 것을 막기 위해서다. null을 넣지 않으면 다음 add에서 그 칸에 대입할 때 ArrayStoreException이 발생하기 때문이다. indexOf가 배열의 모든 칸을 검색하므로, 지워진 원소가 검색되는 것을 막기 위해서다. null을 넣어야 JVM이 배열의 길이를 줄여 메모리를 돌려주기 때문이다. size 밖의 칸은 범위 검사와 indexOf의 반복 범위에서 이미 제외되므로 리스트의 동작에는 영향이 없다. 문제는 가비지 컬렉션이다. 칸에 참조가 남아 있으면 그 객체는 리스트를 통해 도달 가능하므로 회수되지 않는다. Object[]의 칸에는 어떤 참조든 대입할 수 있어 ArrayStoreException과는 무관하고, 배열의 길이는 만들어진 뒤 바뀌지 않는다. 다음 가운데 Java SE 21 API 문서가 ArrayList에 대해 약속하는 것은? 용량이 모자라면 현재 용량의 1.5배로 늘어난다. 인자 없는 생성자를 호출하는 즉시 길이 10인 내부 배열이 할당된다. add는 분할 상환 상수 시간에 동작한다. 곧 원소 n개를 추가하는 데 O(n) 시간이 든다. remove로 원소를 지우면 내부 배열의 용량도 그만큼 줄어든다. 문서는 "The add operation runs in amortized constant time, that is, adding n elements requires O(n) time"이라고 하고, 증가 정책의 세부는 이 사실 말고는 정하지 않는다고 밝힌다. 1.5배와 첫 추가 때까지 할당을 미루는 것은 OpenJDK 21 구현의 선택이다. 삭제는 용량을 줄이지 않으며, 줄이려면 trimToSize()를 호출해야 한다.
    배열 리스트(array list)
    내부에 배열을 두고 크기를 따로 세며, 모자라면 더 큰 배열로 옮겨 가는 방식으로 길이가 변하는 목록을 구현한 자료 구조.
    용량(capacity)
    배열 리스트 내부 배열의 길이. 확장 없이 담을 수 있는 원소의 수다.
    크기(size)
    배열 리스트에 실제로 담긴 원소의 수. 유효한 인덱스의 범위는 0부터 size − 1까지다.
    빅오 표기법(Big-O notation)
    입력 크기 n이 충분히 클 때 연산 횟수가 어떤 함수의 상수 배를 넘지 않는다는 것을 O(g(n))으로 적는 표기.
    선형 탐색(linear search)
    앞에서부터 하나씩 비교해 값을 찾는 방법. 최악의 경우 모든 원소를 비교하므로 O(n)이다.
    동적 배열(dynamic array)
    꽉 차면 더 큰 배열을 새로 만들어 원소를 옮기는 방식으로 커지는 배열 기반 구조.
    분할 상환 분석(amortized analysis)
    연산 하나의 최악이 아니라 연속된 연산 전체의 비용을 구해 연산 횟수로 나누어 평가하는 방법. 입력 분포에 대한 가정이 없다.
    실체화 가능 타입(reifiable type)
    실행 시점에 타입 정보가 온전히 남아 있는 타입(JLS §4.7). 타입 변수는 여기에 속하지 않아 배열 생성식의 원소 타입으로 쓸 수 없다.
    비검사 캐스트(unchecked cast)
    소거 때문에 실행 시점에 온전히 검사할 수 없는 캐스트. 컴파일러가 경고를 내며, 안전성은 프로그래머가 논증해야 한다.
    압축 참조(compressed oops)
    64비트 HotSpot이 힙의 객체 참조를 더 작은 크기로 저장하는 구현 기법. 이 문서의 실험에서 참조 배열의 칸이 4바이트로 나온 이유다.
