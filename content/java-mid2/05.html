    이 회차의 질문: 구현이 둘이면 쓰는 코드도 둘이어야 하는가

    앞의 두 회차는 리스트(list)라는 자료 구조를 두 가지 방식으로 세웠다. 하나는 배열 위에 원소를 차례로 놓는 방식이고, 다른 하나는 노드(node)를 참조로 이어 붙이는 방식이다. 두 방식은 바깥에서 보면 같은 약속을 지킨다. 원소에 순서가 있고, 0부터 시작하는 인덱스로 원소를 가리킬 수 있고, 같은 값을 여러 번 넣을 수 있다. 다른 것은 안쪽의 저장 방식과, 그 저장 방식 때문에 연산마다 달라지는 비용이다.

    약속이 같고 비용만 다르다면 자연스럽게 두 가지 질문이 생긴다. 첫째, 리스트를 쓰는 쪽 코드는 어느 구현을 쓰는지 몰라도 되지 않는가. 몰라도 된다면 나중에 구현을 바꿀 때 쓰는 쪽 코드를 고치지 않아도 된다. 둘째, 그렇다면 언제 어느 구현을 골라야 하는가. 이것은 감으로 답할 문제가 아니라 연산 횟수를 세어서 답할 문제다.

    이 회차의 앞쪽 절반은 첫째 질문을 다룬다. 인터페이스를 도입하고, 의존관계를 주입하고, 그 결과를 클래스 파일과 힙에서 확인한다. "의존한다"는 말은 추상적으로 들리지만 자바에서는 눈으로 볼 수 있는 대상이다. 컴파일된 클래스 파일을 javap로 열면 그 클래스가 이름을 알고 있는 다른 클래스가 전부 적혀 있다. 뒤쪽 절반은 둘째 질문을 다룬다. 직접 만든 두 리스트의 비용을 세고, 자바가 제공하는 java.util.List와 그 두 구현 ArrayList, LinkedList의 내부를 OpenJDK 21 소스 기준으로 읽은 다음 같은 방법으로 비용을 센다.

    예제로는 쇼핑몰의 "최근 본 상품" 목록을 쓴다. 상품을 볼 때마다 그 이름이 목록의 맨 앞에 들어가고, 화면에는 가장 최근 것부터 보여 준다. 맨 앞에 넣는 연산이 반복된다는 점이 뒤에서 구현을 고르는 근거가 된다.

    출발점: 구현 클래스의 이름이 박힌 코드

    배열 기반 리스트 클래스 ArraySimpleList가 이미 있다고 하자(전체 코드는 다음 절에 있다). 최근 본 상품 목록을 가장 단순하게 쓰면 이렇게 된다.

    public class RecentViews {
    private final ArraySimpleList items = new ArraySimpleList<>();

    public void view(String product) {
        items.add(0, product);   // 가장 최근에 본 상품이 맨 앞
    }

    public String latest() {
        return items.get(0);
    }

    public int count() {
        return items.size();
    }
}

    동작에는 문제가 없다. 문제는 이 클래스가 ArraySimpleList라는 이름을 얼마나 깊이 알고 있는가이다. 소스에서는 필드 선언 한 줄에 두 번 나올 뿐이지만, 컴파일된 클래스 파일을 열어 보면 더 많이 나온다.

    #7, #9 같은 번호는 클래스 파일의 상수 풀(constant pool) 항목 번호다. 상수 풀은 클래스 파일마다 하나씩 있는 표로, 이 클래스가 사용하는 다른 클래스·필드·메서드의 이름이 문자열로 적혀 있다. 이렇게 이름으로 적어 둔 참조를 기호 참조(symbolic reference)라고 한다. JVM은 실행 중에 이 이름을 실제 클래스와 메서드로 바꿔 연결하는데, 그 과정이 해석(resolution)이다.

    출력을 보면 ArraySimpleList라는 이름이 네 가지 역할로 나온다. 객체를 만드는 new의 대상, 생성자 의 소유 클래스, 필드 items의 타입(LArraySimpleList;), 그리고 add·get·size를 호출할 때 메서드를 찾을 클래스다. 메서드 디스크립터가 (ILjava/lang/Object;)V인 것은 2회에서 본 타입 소거 때문이다. 타입 매개변수 E는 클래스 파일에서 Object가 되고, latest()에는 컴파일러가 넣은 checkcast String이 붙는다.

    이 상태에서 "맨 앞 삽입이 많으니 연결 리스트로 바꾸자"는 결정이 나면 무슨 일이 생기는가. 소스에서 타입 이름을 고치고 다시 컴파일해야 하며, 그 결과 RecentViews.class의 상수 풀과 명령이 바뀐다. 목록을 다루는 논리는 한 글자도 달라지지 않았는데 클래스가 바뀐 것이다. 게다가 한 프로그램 안에서 어떤 목록은 배열 리스트로, 어떤 목록은 연결 리스트로 쓰고 싶다면 RecentViews를 두 벌 만들어야 한다. 1회에서 본 "타입마다 같은 코드를 다시 쓰는" 문제가 구현 선택이라는 다른 축에서 되풀이된다.

    리스트 추상화 1: 인터페이스 도입

    두 리스트가 지키는 약속만 따로 떼어 인터페이스로 적는다. 인터페이스는 "무엇을 할 수 있는가"의 목록이고, 어떻게 하는지는 적지 않는다.

    public interface SimpleList {
    int size();
    void add(E e);               // 맨 뒤에 추가
    void add(int index, E e);    // index 위치에 끼워 넣기
    E get(int index);
    E set(int index, E e);
    E remove(int index);
    int indexOf(Object o);
}

    배열 기반 구현은 다음과 같다. 이 회차만으로 읽을 수 있도록 최소한의 형태로 다시 적었고, 인덱스 범위 검사는 넣지 않았다.

    import java.util.Arrays;

public class ArraySimpleList implements SimpleList {
    private Object[] elements = new Object[10];
    private int size;

    @Override
    public int size() {
        return size;
    }

    @Override
    public void add(E e) {
        add(size, e);
    }

    @Override
    public void add(int index, E e) {
        if (size == elements.length) {
            elements = Arrays.copyOf(elements, size * 2);   // 꽉 차면 2배 배열로 옮긴다
        }
        for (int i = size; i > index; i--) {
            elements[i] = elements[i - 1];                  // index부터 뒤쪽을 한 칸씩 민다
        }
        elements[index] = e;
        size++;
    }

    @Override
    @SuppressWarnings("unchecked")
    public E get(int index) {
        return (E) elements[index];
    }

    @Override
    public E set(int index, E e) {
        E old = get(index);
        elements[index] = e;
        return old;
    }

    @Override
    public E remove(int index) {
        E old = get(index);
        for (int i = index; i < size - 1; i++) {
            elements[i] = elements[i + 1];                  // 뒤쪽을 한 칸씩 당긴다
        }
        elements[--size] = null;
        return old;
    }

    @Override
    public int indexOf(Object o) {
        for (int i = 0; i < size; i++) {
            if (o.equals(elements[i])) {
                return i;
            }
        }
        return -1;
    }
}

    연결 리스트 구현은 첫 노드만 기억하는 단일 연결 리스트(singly linked list)다. node(index)는 첫 노드에서 출발해 next를 index번 따라간다.

    public class LinkedSimpleList implements SimpleList {
    private static class Node {
        E item;
        Node next;

        Node(E item) {
            this.item = item;
        }
    }

    private Node first;
    private int size;

    private Node node(int index) {
        Node x = first;
        for (int i = 0; i < index; i++) {
            x = x.next;                      // 노드 하나를 건너간다
        }
        return x;
    }

    @Override
    public int size() {
        return size;
    }

    @Override
    public void add(E e) {
        add(size, e);
    }

    @Override
    public void add(int index, E e) {
        Node created = new Node<>(e);
        if (index == 0) {
            created.next = first;
            first = created;
        } else {
            Node prev = node(index - 1);  // 끼워 넣을 자리의 앞 노드를 찾는다
            created.next = prev.next;
            prev.next = created;
        }
        size++;
    }

    @Override
    public E get(int index) {
        return node(index).item;
    }

    @Override
    public E set(int index, E e) {
        Node x = node(index);
        E old = x.item;
        x.item = e;
        return old;
    }

    @Override
    public E remove(int index) {
        Node removed;
        if (index == 0) {
            removed = first;
            first = removed.next;
        } else {
            Node prev = node(index - 1);
            removed = prev.next;
            prev.next = removed.next;
        }
        size--;
        return removed.item;
    }

    @Override
    public int indexOf(Object o) {
        int i = 0;
        for (Node x = first; x != null; x = x.next) {
            if (o.equals(x.item)) {
                return i;
            }
            i++;
        }
        return -1;
    }
}

    인터페이스는 클래스 파일에서 무엇인가

    인터페이스도 컴파일하면 SimpleList.class라는 클래스 파일이 된다. javap -v SimpleList의 머리 부분에는 flags: (0x0601) ACC_PUBLIC, ACC_INTERFACE, ACC_ABSTRACT가 찍히고, 메서드 일곱 개는 모두 ACC_PUBLIC, ACC_ABSTRACT로 표시되며 실행할 코드(Code 속성)가 없다. 반대로 ArraySimpleList.class에는 interfaces: 1이라는 항목이 생기고 그 한 칸이 SimpleList를 가리킨다. "구현한다(implements)"는 관계는 구현 클래스의 클래스 파일에 기록되고, JVM은 클래스를 로딩할 때 이 기록을 읽는다.

    두 가지가 달라졌다. 필드의 타입이 LSimpleList;가 되었고, 메서드 호출 명령이 invokevirtual에서 invokeinterface로 바뀌었다. 상수 풀의 항목 종류도 Methodref에서 InterfaceMethodref로 바뀌어 "SimpleList라는 인터페이스의 add"를 가리킨다. view, latest, count의 본문에서는 구현 클래스의 이름이 완전히 사라졌다. 컴파일러는 변수의 선언 타입만 보고 메서드가 있는지 검사하고, 그 선언 타입을 기호 참조에 적기 때문이다.

    invokeinterface 뒤의 숫자 3은 이 명령에만 있는 count 피연산자다. size() 호출에서는 1, get(int)에서는 2, add(int, E)에서는 3으로, 수신 객체까지 포함해 스택에서 꺼낼 인자 칸 수를 센 값이다. JVM 명세(JVMS §6.5)는 이 정보가 메서드 디스크립터에서도 얻을 수 있는 것이고 중복해서 적는 것은 역사적인 이유라고 밝힌다.

    그런데 생성자는 달라지지 않았다. new #7 // class ArraySimpleList와 그 생성자 호출이 그대로 남아 있다. 상수 풀에서 클래스 항목만 뽑아 보면 java/lang/Object, ArraySimpleList, RecentViews, SimpleList, java/lang/String 다섯 개다. 인터페이스를 도입해서 얻은 것은 "메서드를 호출하는 코드가 구현을 모른다"까지다. 객체를 만드는 코드는 여전히 구현 클래스의 이름을 알아야 하고, 그 코드가 RecentViews 안에 있는 한 이 클래스는 ArraySimpleList에 묶여 있다.

    자바에서 객체를 만드는 식(클래스 인스턴스 생성식)은 익명 클래스를 선언하는 경우가 아니면 new 뒤에 추상이 아닌 클래스의 이름만 올 수 있다(JLS §15.9.1). 인터페이스는 인스턴스를 만들 수 없으므로, 프로그램 어딘가에는 반드시 구현 클래스의 이름을 적는 코드가 있어야 한다. 추상화의 문제는 그 이름을 "없애는" 것이 아니라 "어디에 둘 것인가"를 정하는 것이다.

    리스트 추상화 2: 의존관계 주입

    남은 한 줄, new ArraySimpleList<>()를 RecentViews 밖으로 내보낸다. RecentViews는 리스트를 직접 만들지 않고 생성자의 매개변수로 건네받는다.

    public class RecentViews {
    private final SimpleList items;

    public RecentViews(SimpleList items) {
        this.items = items;
    }

    public void view(String product) {
        items.add(0, product);
    }

    public String latest() {
        return items.get(0);
    }

    public int count() {
        return items.size();
    }
}

    어떤 구현을 쓸지는 이 클래스를 사용하는 쪽이 정한다. 아래 Main은 실행 인자에 따라 구현을 고른 뒤 RecentViews에 넘긴다.

    public class Main {
    public static void main(String[] args) {
        SimpleList list;
        if (args.length > 0 && args[0].equals("linked")) {
            list = new LinkedSimpleList<>();
        } else {
            list = new ArraySimpleList<>();
        }

        RecentViews views = new RecentViews(list);
        views.view("키보드");
        views.view("마우스");
        views.view("모니터");

        System.out.println(views.latest() + " / " + views.count()
                + " / " + list.getClass().getSimpleName());
    }
}

    세 번의 view 호출은 매번 인덱스 0에 넣으므로 마지막에 넣은 "모니터"가 맨 앞에 있다. 결과의 앞 두 값은 어느 구현을 쓰든 같고, 마지막 값만 실제로 만들어진 객체의 클래스를 보여 준다. 실행할 때마다 프로그램을 다시 컴파일하지 않았다는 점에 주목하자. 같은 클래스 파일들이 실행 인자 하나에 따라 다른 객체 구성으로 동작했다.

    이렇게 객체가 자신이 사용할 다른 객체를 스스로 만들지 않고 외부에서 건네받는 것을 의존관계 주입(dependency injection, DI)이라고 한다. 생성자로 받으면 생성자 주입(constructor injection)이다. 생성자 주입에는 부수적인 이점이 있다. 필드를 final로 둘 수 있어서 객체가 만들어진 뒤에는 구현이 바뀌지 않고, 리스트 없이 만들어진 반쪽짜리 RecentViews가 존재할 수 없다.

    리스트 추상화 3: 컴파일 타임 의존관계와 런타임 의존관계

    지금까지 "의존한다", "안다"는 말을 여러 번 썼다. 이 말에는 서로 다른 두 가지 뜻이 섞여 있고, 둘을 나누는 것이 이 절의 목적이다.

    • 컴파일 타임 의존관계(compile-time dependency): 소스 코드에 적힌 타입 사이의 관계다. 클래스 A의 코드에 클래스 B의 이름이 나오면 A는 B에 의존한다. 프로그램을 실행하지 않고 소스나 클래스 파일만 읽어도 알 수 있으므로 정적(static) 의존관계라고도 한다.
    • 런타임 의존관계(runtime dependency): 프로그램이 실행되는 동안 힙에 만들어진 인스턴스 사이의 참조 관계다. 어떤 객체의 필드가 어떤 객체를 가리키고 있는가이다. 실행해 봐야 정해지고, 같은 프로그램이라도 실행마다 달라질 수 있다.

    컴파일 타임 의존관계는 앞에서 이미 눈으로 확인했다. 클래스 파일의 상수 풀에 적힌 클래스 이름이 곧 그 클래스의 컴파일 타임 의존 대상이다. 이 관계가 실제로 "컴파일에 필요하다"는 뜻인지 실험해 보자. 폴더 하나에 SimpleList.class만 넣어 두고, 그 폴더를 클래스패스로 주어 RecentViews.java를 컴파일한다.

    클래스 사이의 화살표(코드에 적힌 관계)와 인스턴스 사이의 화살표(힙에서의 참조)가 서로 다른 그림이라는 점, RecentViews 클래스에서는 인터페이스로만 화살표가 나간다는 점을 보여 준다. 흰 배경의 좌우 2단 비교 다이어그램. 왼쪽 패널 머리 라벨 "컴파일 타임 의존관계". 왼쪽 패널 가운데에 둥근 모서리 상자 "RecentViews"가 있고, 오른쪽으로 실선 화살표가 나가 점선 테두리 상자 "SimpleList (인터페이스)"를 가리킨다. 인터페이스 상자 아래에 실선 테두리 상자 두 개 "ArraySimpleList", "LinkedSimpleList"가 나란히 놓이고, 각각 위쪽 인터페이스 상자로 속이 빈 삼각형 머리의 점선 화살표(구현 관계)가 올라간다. RecentViews 상자에서 두 구현 상자로 가는 화살표는 없다. 오른쪽 패널 머리 라벨 "런타임 의존관계". 오른쪽 패널 왼쪽에 상자 "RecentViews 인스턴스"가 있고 안에 칸 하나 "items". items 칸에서 굵은 실선 화살표가 나가 상자 "LinkedSimpleList 인스턴스"를 가리킨다. 그 상자에서 다시 화살표가 나가 작은 원 세 개가 화살표로 이어진 사슬을 가리키고 사슬 아래에 라벨 "노드". 오른쪽 패널 아래쪽에 흐린 회색 상자 "ArraySimpleList 인스턴스"가 있고 items 칸에서 그쪽으로 가는 흐린 점선 화살표에 라벨 "다른 실행에서는 이쪽". 두 패널 사이에 세로 점선. 차분한 파랑과 회색을 쓰고 인터페이스 상자만 주황색 테두리로 강조한다. 평면적인 기술 도해 스타일. 클래스 수준에서 RecentViews는 인터페이스만 안다. 어느 구현의 인스턴스를 가리킬지는 실행 중에 객체를 연결할 때 정해진다.

    한 층 아래: invokeinterface는 실행 시점에 무엇을 하는가

    클래스 파일에는 SimpleList.add라는 이름만 적혀 있는데, 실행하면 LinkedSimpleList.add의 코드가 돈다. 이 연결은 누가 언제 하는가. JVM 명세의 invokeinterface 항목(JVMS §6.5)은 두 단계를 구분한다.

    핵심은 셋째 단계가 변수의 선언 타입이 아니라 객체의 클래스를 기준으로 한다는 점이다. 객체는 자신이 어느 클래스의 인스턴스인지에 대한 정보를 가지고 있고, JVM은 호출할 때마다 그 정보에서 출발해 메서드를 고른다. 선택 규칙 자체는 invokevirtual과 같다. 명세는 두 명령 모두에 "C를 수신 객체의 클래스라 하고, C와 해석된 메서드에 대해 메서드를 선택한다"는 같은 문장을 쓴다.

    둘째 단계에서 수신 객체의 클래스가 그 인터페이스를 구현하는지 확인하는 검사는 invokeinterface에만 있다. 정상적으로 함께 컴파일한 코드에서는 만날 일이 거의 없는 오류지만, 명세에 이 검사가 있다는 사실은 의미가 있다. "이 객체가 이 인터페이스를 구현하는가"는 호출하는 순간 실제 객체를 보고 답하는 실행 시점의 질문이라는 것이다.

    HotSpot의 vtable과 itable

    명세는 메서드를 "찾는다"고만 하고 어떻게 빨리 찾을지는 구현에 맡긴다. 호출할 때마다 클래스 계층을 이름으로 뒤지면 느리므로, OpenJDK의 HotSpot은 클래스마다 표를 미리 만들어 둔다. HotSpot 소스의 klassVtable.hpp는 두 가지 표를 설명한다. 하나는 클래스에 붙어 있는 가변 길이의 가상 메서드 표인 vtable이다. 다른 하나는 인터페이스 메서드 표인 itable로, "구현한 인터페이스와, 그 인터페이스의 메서드 항목들이 시작하는 위치"를 짝지은 목록이 앞에 있고 그 뒤에 메서드 항목들이 이어진다.

    표가 두 종류인 까닭은 상속 구조의 차이에서 나온다. 클래스는 부모가 하나뿐이다. 같은 디렉터리의 klassVtable.cpp를 보면 HotSpot은 자식 클래스 vtable의 앞부분에 부모의 vtable을 그대로 복사하고, 재정의한 메서드는 그 복사본의 같은 칸에 바꿔 넣고, 새로 생긴 메서드만 끝에 덧붙인다. 그래서 같은 메서드가 모든 하위 클래스에서 같은 칸 번호에 놓인다. 그래서 invokevirtual은 "수신 객체 클래스의 vtable에서 몇 번 칸"으로 바로 갈 수 있다. 인터페이스는 사정이 다르다. 서로 아무 관계가 없는 클래스들이 같은 인터페이스를 구현할 수 있고 한 클래스가 여러 인터페이스를 구현할 수도 있어서, 인터페이스 메서드에 모든 구현 클래스에 공통인 칸 번호를 줄 수 없다. 그래서 수신 객체 클래스의 itable에서 먼저 해당 인터페이스의 구획을 찾고, 그 구획 안에서 메서드 칸으로 가는 한 단계가 더 필요하다. 이것은 HotSpot의 구현 방식이고 명세가 요구하는 것은 아니다.

    인터페이스를 거치면 느려지는가

    단계가 하나 더 있다는 설명을 들으면 "인터페이스 타입으로 선언하면 성능이 떨어진다"는 결론으로 건너뛰기 쉽다. 실제로는 HotSpot의 JIT 컴파일러가 자주 실행되는 호출 지점을 다시 번역하면서 이 탐색을 없애는 경우가 많다. 아래는 SimpleList를 받아 size()와 get(i)를 반복 호출하는 메서드를 충분히 여러 번 실행하고, 진단 옵션 -XX:+UnlockDiagnosticVMOptions -XX:+PrintInlining으로 JIT 컴파일러의 인라인 기록을 본 것이다. 바이트코드에서 위치 6과 17은 각각 invokeinterface SimpleList.size와 invokeinterface SimpleList.get이었다.

    @ 6   ArraySimpleList::size (5 bytes)   accessor
 \-> TypeProfile (360294/360294 counts) = ArraySimpleList
@ 17   ArraySimpleList::get (7 bytes)   inline (hot)

    인터페이스 메서드를 호출하던 자리에 SimpleList가 아니라 ArraySimpleList의 메서드가 적혀 있고, get에는 inline (hot)이 붙어 있다. TypeProfile 줄은 JVM이 실행하면서 기록해 둔 수신 객체의 클래스가 전부 ArraySimpleList였다는 뜻이다. JIT 컴파일러는 이 관측을 근거로 메서드 본문을 호출 지점에 직접 펼쳐 넣었다. 이 실험에서는 인터페이스 호출이 표를 뒤지는 호출로 남지 않았다.

    이 최적화는 HotSpot의 구현 세부이고, 한 호출 지점에 여러 구현의 객체가 섞여 들어오면 결과가 달라진다. 그래도 설계 판단의 방향은 분명하다. 인터페이스 호출 한 번의 비용은 표를 한 단계 더 거치는 정도인 반면, 다음 절부터 볼 자료 구조 선택의 차이는 연산 횟수가 0번이냐 12억 번이냐의 차이다. 추상화를 포기해서 아낄 수 있는 비용보다, 추상화 덕분에 구현을 쉽게 바꿔 얻을 수 있는 이득이 훨씬 크다.

    직접 구현한 리스트의 성능 비교

    인터페이스를 도입한 덕을 가장 먼저 보는 곳은 측정 코드다. 측정하는 메서드가 SimpleList만 알면 되므로, 구현마다 측정 코드를 따로 쓸 필요가 없다.

    public class FrontAddTimer {
    static long measure(SimpleList list, int n) {
        long start = System.nanoTime();
        for (int i = 0; i < n; i++) {
            list.add(0, i);
        }
        return (System.nanoTime() - start) / 1_000_000;
    }

    public static void main(String[] args) {
        int n = 50_000;
        System.out.println("배열 리스트: " + measure(new ArraySimpleList<>(), n) + "ms");
        System.out.println("연결 리스트: " + measure(new LinkedSimpleList<>(), n) + "ms");
    }
}

    출력되는 시간은 실행마다, 기계마다 다르므로 숫자를 적지 않는다. Temurin 21에서 여러 번 돌렸을 때 배열 리스트 쪽이 매번 훨씬 오래 걸렸다. 그런데 시간은 원인이 아니라 결과다. JIT 컴파일, 가비지 컬렉션, 다른 프로세스의 영향이 섞여 있어서 시간만 보고는 왜 그런지 알 수 없다. 원인을 보려면 실행마다 달라지지 않는 양, 곧 연산 횟수를 세어야 한다.

    두 구현에서 비용의 대부분을 차지하는 동작은 하나씩이다. 배열 리스트에서는 원소를 한 칸 옮기는 대입(elements[i] = elements[i - 1])이고, 연결 리스트에서는 다음 노드로 건너가는 대입(x = x.next)이다. 두 문장 옆에 카운터를 하나씩 넣고, 배열 확장 때 Arrays.copyOf가 옮기는 원소 수는 따로 세어 실행한 결과가 다음 표다. 이 값은 몇 번을 실행해도 같다.

    숫자가 나오는 과정

    맨 앞 추가. 원소가 s개 든 배열 리스트의 인덱스 0에 넣으려면 기존 원소 s개를 전부 한 칸씩 뒤로 밀어야 한다. s가 0에서 49,999까지 커지는 동안 민 횟수를 더하면 0 + 1 + … + 49,999 = 49,999 × 50,000 ÷ 2 = 1,249,975,000이다. 연결 리스트는 index == 0 분기로 들어가 새 노드의 next에 기존 첫 노드를 넣고 first를 새 노드로 바꾼다. 리스트가 아무리 길어도 대입 두 번이다.

    가운데 추가. 배열 리스트는 자리를 바로 찾지만 그 뒤쪽 절반을 밀어야 하고, 연결 리스트는 연결 자체는 대입 두 번이지만 그 자리의 앞 노드까지 걸어가야 한다. 어느 쪽이든 한 번에 대략 s ÷ 2번이고, 50,000번을 합치면 약 6억 2,500만 번으로 거의 같다. "연결 리스트는 중간 삽입이 빠르다"는 말이 왜 절반만 맞는지 이 줄이 보여 준다. 빠른 것은 연결하는 동작이고, 연결할 자리를 찾는 동작은 느리다.

    맨 뒤 추가. 배열 리스트는 밀 원소가 없다. 대신 배열이 꽉 찰 때마다 2배 크기의 새 배열로 전체를 옮기는데, 용량이 10에서 시작해 13번 2배가 되는 동안 옮긴 원소는 10 + 20 + … + 40,960 = 81,910개다. 50,000번의 추가에 81,910번의 복사이므로 추가 한 번에 평균 2번이 안 된다. 3회에서 다룬 분할 상환(amortized) 분석이 말하는 바가 이 숫자다. 반면 첫 노드만 기억하는 단일 연결 리스트는 맨 뒤에 붙이려면 매번 처음부터 끝까지 걸어가야 해서, 합계가 (n − 1)(n − 2) ÷ 2 = 1,249,925,001번이 된다.

    인덱스 조회. 배열은 인덱스에서 주소를 계산해 한 번에 간다. 연결 리스트는 인덱스만큼 노드를 건넌다. 표의 마지막 세 줄이 그 차이다.

    연산배열 리스트단일 연결 리스트(첫 노드만 기억)
    맨 앞 추가·삭제O(n): 전부 민다O(1)
    가운데 추가·삭제O(n): 찾기 O(1) + 밀기 O(n)O(n): 찾기 O(n) + 연결 O(1)
    맨 뒤 추가O(1) (분할 상환)O(n): 끝까지 걸어간다
    인덱스 조회O(1)O(n)
    값 검색(indexOf)O(n)O(n)

    Temurin 21에서 잰 시간의 순서도 횟수와 같은 방향이었다. 맨 앞 추가는 배열 리스트가, 맨 뒤 추가는 연결 리스트가 훨씬 오래 걸렸고, 가운데 추가는 둘 다 오래 걸렸다. n이 50,000일 때 n에 비례하는 일과 n²에 비례하는 일의 차이는 5만 배쯤 된다. 빅오 표기가 상수를 버리고 증가율만 남기는 이유가 여기 있다. 이 정도 차이 앞에서는 한 번의 동작이 조금 빠르고 느린 것이 순서를 뒤집지 못한다.

    일상에서 가져온 비유극장 좌석과 보물찾기 쪽지

    배열 리스트는 번호가 붙은 극장 좌석이다. 37번 좌석은 번호만 알면 바로 걸어갈 수 있다. 대신 맨 앞자리에 한 사람을 끼워 넣으려면 그 줄의 모든 사람이 한 칸씩 옮겨 앉아야 한다. 연결 리스트는 "다음 쪽지는 어디에 있다"고 적힌 보물찾기 쪽지다. 맨 앞에 쪽지를 하나 더 두는 일은 새 쪽지에 원래 첫 쪽지의 위치를 적기만 하면 끝나지만, 37번째 쪽지를 보려면 첫 쪽지부터 서른일곱 장을 차례로 찾아다녀야 한다. 비유가 깨지는 지점도 있다. 극장에서는 사람이 스스로 움직이지만 배열에서는 리스트 코드가 원소를 하나씩 옮겨 줘야 하고, 극장 좌석 수는 고정이지만 배열 리스트는 꽉 차면 더 큰 극장으로 전원이 이사한다.

    같은 "맨 앞에 추가"가 배열에서는 모든 원소의 이동이고 연결 리스트에서는 참조 두 개의 변경이라는 점을 나란히 보여 준다. 흰 배경의 상하 2단 비교 다이어그램. 위쪽 단 왼쪽에 라벨 "배열 리스트: 맨 앞에 추가". 가로로 이어 붙인 정사각형 칸 여섯 개가 있고 칸 아래에 인덱스 0부터 5가 적혀 있다. 앞의 네 칸에는 "A", "B", "C", "D"가 들어 있고 뒤 두 칸은 비어 있다. 각 원소 위에 오른쪽 옆 칸으로 향하는 짧은 곡선 화살표가 네 개 그려져 있고 화살표 묶음 위에 주황색 라벨 "원소 4개를 모두 한 칸씩 민다". 맨 왼쪽 0번 칸 위로 새 원소 "N"이 내려오는 화살표. 위쪽 단 오른쪽 끝에 큰 글씨 "O(n)". 아래쪽 단 왼쪽에 라벨 "연결 리스트: 맨 앞에 추가". 둥근 상자 네 개 "A", "B", "C", "D"가 오른쪽 방향 화살표로 이어져 있고 마지막 화살표 끝에 "null". 맨 왼쪽 위에 작은 상자 "first"가 있다. 새 둥근 상자 "N"이 A의 왼쪽에 놓이고, N에서 A로 가는 굵은 파란 화살표에 라벨 "N.next = 기존 첫 노드", first 상자에서 N으로 가는 굵은 파란 화살표에 라벨 "first = N". first에서 A로 가던 원래 화살표는 흐린 점선으로 표시한다. 아래쪽 단 오른쪽 끝에 큰 글씨 "O(1)". 차분한 파랑과 회색, 이동 화살표만 주황색. 평면적인 기술 도해 스타일. 맨 앞 삽입에서 배열 리스트는 원소 수만큼 이동하고, 연결 리스트는 길이와 관계없이 참조 두 개만 바꾼다.

    ArrayList의 상태는 Object[] elementData와 int size 두 필드다. ArraySimpleList와 뼈대가 같다. 다른 점은 세부에 있고, 그 세부가 성능을 가른다.

    • 배열을 늦게 만든다. Javadoc은 인자 없는 생성자를 "초기 용량 10인 빈 리스트를 만든다"고 설명한다. 그런데 리플렉션으로 내부 배열을 들여다보면 생성 직후의 길이는 0이고, 첫 원소를 추가하는 순간 길이 10인 배열이 만들어진다. 만들기만 하고 쓰지 않는 리스트가 10칸을 차지하지 않게 하려는 구현이다.
    • 1.5배씩 늘린다. 꽉 차면 새 용량을 "기존 용량 + 기존 용량의 절반(oldCapacity >> 1)"으로 잡는다. 실제로 원소를 하나씩 추가하며 배열 길이를 찍어 보면 10, 15, 22, 33, 49, 73, 109, 163, …으로 늘어난다. Javadoc은 확장 정책의 세부를 정하지 않고 "원소 추가의 분할 상환 비용이 상수"라는 것만 약속하므로, 1.5배라는 값은 명세가 아니라 구현이다.
    • System.arraycopy로 민다. add(int index, E e)와 remove(int index)는 반복문으로 한 칸씩 옮기지 않고, 옮길 구간 전체를 System.arraycopy 한 번으로 옮긴다. 이 메서드는 native로 선언되어 있고 @IntrinsicCandidate가 붙어 있다. 이 애너테이션은 HotSpot이 해당 메서드를 손으로 작성한 어셈블리나 컴파일러 내부 코드로 대체할 수 있다는 표시다.
    • 범위를 검사한다. get, set, remove는 인덱스가 0 이상 size 미만인지 먼저 확인하고, 아니면 IndexOutOfBoundsException을 던진다. 내부 배열의 길이가 아니라 size가 기준이라는 점이 중요하다. 배열에는 아직 쓰지 않은 빈칸이 있기 때문이다.
    • null을 원소로 허용한다. indexOf(null)은 equals를 부르지 않고 ==로 null인 칸을 찾는다. 앞에서 만든 ArraySimpleList.indexOf(null)은 원소가 하나라도 들어 있으면 o.equals(...)에서 NullPointerException이 난다.

    분할 상환이 실제로 얼마나 싼지도 세어 볼 수 있다. 빈 ArrayList에 원소 1,000,000개를 하나씩 추가하면 내부 배열은 첫 추가 때 길이 10으로 만들어진 뒤 더 큰 배열로 29번 교체되고, 마지막 길이는 1,215,487이며, 교체 때 옮긴 원소는 모두 2,430,972개다. 추가 한 번에 평균 2.4개를 복사한 셈이다. 넣을 개수를 미리 안다면 new ArrayList<>(1_000_000)처럼 초기 용량을 주어 이 복사와 남는 21만여 칸을 모두 없앨 수 있다.

    LinkedList의 내부 (OpenJDK 21 기준)

    LinkedList의 Javadoc 첫 문장은 이 클래스가 List와 Deque 인터페이스의 이중 연결 리스트(doubly-linked list) 구현이라고 밝힌다. 노드는 item, next, prev 세 필드를 가지고, 리스트는 first와 last 두 참조와 size를 가진다. 직접 만든 LinkedSimpleList와 두 가지가 다르다. 노드가 앞 노드도 가리킨다는 것, 그리고 리스트가 마지막 노드를 기억한다는 것이다.

     first                                          last
   │                                              │
   ▼                                              ▼
 ┌─────┐ next ┌─────┐ next ┌─────┐ next ┌─────┐
 │  A  │─────▶│  B  │─────▶│  C  │─────▶│  D  │─────▶ null
 │     │◀─────│     │◀─────│     │◀─────│     │
 └─────┘ prev └─────┘ prev └─────┘ prev └─────┘
 인덱스 0       1            2            3

 get(1): 1 < 4/2 이므로 first에서 next로 1번
 get(2): 2 >= 4/2 이므로 last에서 prev로 4 - 1 - 2 = 1번

    이 두 차이가 직접 만든 연결 리스트의 약점 두 개를 지운다. 첫째, add(E e)는 last에서 바로 새 노드를 이어 붙이므로 맨 뒤 추가가 O(1)이다. 둘째, 인덱스로 노드를 찾을 때 인덱스가 size의 절반보다 작으면 first에서 next를 따라가고, 그렇지 않으면 last에서 prev를 따라 거꾸로 간다. Javadoc도 인덱스를 쓰는 연산은 지정한 인덱스에 더 가까운 쪽 끝에서 리스트를 순회한다고 적는다. 노드 이동 횟수를 식으로 쓰면 인덱스가 절반보다 작을 때는 index번, 아니면 size - 1 - index번이다. 최악은 한가운데이고 그때도 n ÷ 2번을 넘지 않는다.

    Deque를 함께 구현한다는 것은 이 클래스가 양 끝에서 넣고 빼는 자료 구조로도 쓰인다는 뜻이다. 큐와 덱은 9회에서 다룬다.

    자바 리스트의 성능 비교

    같은 실험을 자바의 두 리스트에 적용한다. JDK 클래스에는 카운터를 넣을 수 없으므로, 위에서 읽은 소스의 규칙으로 횟수를 계산했다. ArrayList는 인덱스 뒤쪽의 원소 수(size - index)만큼을 System.arraycopy로 옮기고, LinkedList는 가까운 끝에서부터 노드를 건넌다.

    횟수가 같은데 시간이 다른 경우

    시간을 재면 표에서 예상하지 못한 결과가 하나 나온다. Temurin 21에서 여러 번 실행했을 때의 순서는 이랬다. 맨 앞 추가는 LinkedList가 훨씬 짧았다. 맨 뒤 추가는 둘 다 다른 실험에 비해 매우 짧았다. 인덱스 조회 반복은 ArrayList가 훨씬 짧았다. 여기까지는 횟수와 같은 방향이다. 그런데 가운데 추가는 두 리스트의 횟수가 6억 2,500만 번으로 거의 같은데도 ArrayList가 훨씬 짧았다. 또 맨 앞 추가에서 ArrayList는 직접 만든 ArraySimpleList와 옮긴 원소 수가 똑같은데도 훨씬 짧게 끝났다.

    횟수가 같으면 한 번의 값이 다른 것이다. 빅오 표기는 "한 번"의 비용을 상수로 보고 지워 버리지만, 그 상수가 구조에 따라 크게 다르다. 이유는 두 가지다.

    첫째는 옮기는 방식이다. 배열의 원소들은 메모리에 빈틈없이 이어져 있어서, 원소 1,000개를 한 칸씩 미는 일은 "연속한 메모리 구간 하나를 옆으로 복사하는 일"이다. System.arraycopy는 이 일을 원소 하나하나에 대한 자바 반복문이 아니라 구간 단위의 복사로 처리한다. 직접 만든 ArraySimpleList가 같은 원소 수를 옮기고도 더 오래 걸린 것은 반복문으로 하나씩 대입했기 때문이다.

    둘째는 메모리 지역성(locality)이다. CPU는 메모리에서 값을 읽을 때 그 주변의 값들을 함께 캐시에 가져온다. 배열은 이웃한 원소가 이웃한 주소에 있으므로 한 번 가져온 캐시 구간에서 여러 원소를 처리한다. 연결 리스트의 노드는 하나하나가 힙에 따로 할당된 객체이고, 다음 노드의 주소는 지금 노드를 읽어야 알 수 있다. 노드를 건널 때마다 어디에 있을지 모르는 주소를 새로 읽어야 하므로 캐시의 도움을 받기 어렵다. 같은 "한 번"이라도 배열의 한 번과 노드의 한 번은 무게가 다르다.

    원소 하나가 차지하는 메모리

    메모리 사용량도 구조에서 바로 나온다. 원소 1,000,000개를 넣은 두 리스트를 만들어 두고 jcmd GC.class_histogram으로 힙에 있는 객체를 클래스별로 세어 보았다. 측정 환경은 Temurin 21의 64비트 HotSpot이고, 참조를 4바이트로 줄여 저장하는 압축 참조(-XX:+UseCompressedOops)가 켜진 기본 설정이다.

     num     #instances         #bytes  class name (module)
   1:       1000000       24000000  java.util.LinkedList$Node (java.base@21.0.13)

    노드 1,000,000개가 24,000,000바이트, 곧 노드 하나에 24바이트다. 객체 헤더와 참조 세 개(item, next, prev)가 들어 있는 크기다. 같은 방법으로 길이 1,000,000인 Object[]를 재면 4,000,016바이트로, 배열 헤더 16바이트를 빼면 한 칸에 4바이트다. 원소 객체 자체의 크기는 두 리스트에서 같으므로, 리스트 구조가 원소 하나를 붙들고 있는 데 드는 비용은 이 환경에서 ArrayList가 칸당 4바이트, LinkedList가 노드당 24바이트다. ArrayList에 쓰지 않는 빈칸이 있다는 점을 감안해도(1.5배 확장 직후라면 전체의 3분의 1), 차이는 여전히 크다. 그리고 노드는 개수만큼의 객체이므로 가비지 컬렉터가 추적해야 할 객체 수도 그만큼 늘어난다.

    ArrayList는 참조가 연속으로 놓인 배열 하나이고 LinkedList는 흩어진 노드 객체들이 참조로 이어진 구조라는 점, 노드 하나에 참조가 세 개 들어 있다는 점을 보여 준다. 흰 배경의 좌우 2단 메모리 구조 다이어그램. 왼쪽 패널 머리 라벨 "ArrayList". 위쪽에 이름 없는 작은 상자가 있고 안에 칸 하나 "elementData". elementData 칸에서 화살표가 내려가 가로로 길게 이어 붙인 작은 칸 여덟 개짜리 띠를 가리킨다. 띠 위에 라벨 "Object[] (연속한 메모리)". 앞의 다섯 칸은 파란색으로 채워져 있고 뒤 세 칸은 비어 있으며 빈칸 아래에 작은 글씨 "남는 칸". 오른쪽 패널 머리 라벨 "LinkedList". 위쪽에 이름 없는 작은 상자가 있고 안에 칸 두 개 "first", "last". 패널 안 여기저기 불규칙한 위치에 둥근 모서리 상자 다섯 개가 흩어져 있고 각 상자는 세 칸으로 나뉘어 "prev", "item", "next"라고 적혀 있다. 상자들은 next 칸에서 다음 상자로 가는 실선 화살표와 prev 칸에서 이전 상자로 가는 점선 화살표로 구불구불하게 이어진다. first 칸에서 첫 상자로, last 칸에서 마지막 상자로 화살표. 흩어진 상자들 옆에 라벨 "노드마다 따로 할당된 객체". 차분한 파랑과 회색을 쓰고 화살표는 짙은 남색. 평면적인 기술 도해 스타일. ArrayList의 원소 참조는 한 배열 안에 연속으로 놓이고, LinkedList의 원소 참조는 흩어진 노드 객체 안에 하나씩 들어 있다.

    인덱스 반복문의 함정과 RandomAccess

    인터페이스는 "무엇을 할 수 있는가"를 약속하지만 "얼마나 걸리는가"는 약속하지 않는다. List.get(int)는 두 구현 모두에서 올바른 값을 돌려주지만 비용은 O(1)과 O(n)으로 다르다. 이 차이가 가장 아프게 드러나는 코드가 인덱스로 도는 반복문이다.

    static long sumByIndex(List list) {
    long sum = 0;
    for (int i = 0; i < list.size(); i++) {
        sum += list.get(i);
    }
    return sum;
}

static long sumByIterator(List list) {
    long sum = 0;
    for (int value : list) {
        sum += value;
    }
    return sum;
}

    0부터 49,999까지 든 리스트를 넘기면 두 메서드 모두 1,249,975,000을 돌려준다. 결과는 같지만 하는 일은 다르다. LinkedList에 sumByIndex를 쓰면 get(i)가 매번 가까운 끝에서 다시 출발하므로, 앞 표의 마지막 줄대로 노드를 624,975,000번 건넌다. 원소는 5만 개인데 6억 번을 움직인다. sumByIterator의 향상된 for 문은 반복자(Iterator)를 쓰고, LinkedList의 반복자는 지금 서 있는 노드를 기억하고 있다가 한 칸만 전진한다. 전체가 5만 번으로 끝난다. Temurin 21에서 잰 시간도 그대로였다. LinkedList에서 인덱스 반복문은 훨씬 오래 걸렸고, 향상된 for 문은 ArrayList와 비슷했다.

    List의 Javadoc에는 이 경고가 직접 적혀 있다. 위치 접근 연산은 일부 구현(예로 LinkedList)에서 인덱스 값에 비례하는 시간이 걸릴 수 있으므로, 호출하는 쪽이 구현을 모른다면 인덱스로 도는 것보다 원소를 순회하는 편이 대체로 낫다는 내용이다. 반복자의 동작 원리는 10회에서 다룬다.

    구현을 모르는 채로 알고리즘을 골라야 하는 라이브러리 코드를 위해 자바는 RandomAccess라는 표지 인터페이스(marker interface)를 둔다. 메서드가 하나도 없고, "이 리스트는 인덱스 접근이 빠르다(대체로 상수 시간)"는 사실만 타입으로 표시한다. ArrayList는 이 인터페이스를 구현하고 LinkedList는 구현하지 않는다. Collections.binarySearch의 소스를 보면 list instanceof RandomAccess를 검사해서, 참이면 인덱스로 접근하는 이진 탐색을, 아니면(그리고 리스트가 일정 크기 이상이면) 반복자로 이동하는 이진 탐색을 고른다. 추상화 뒤에 숨긴 성능 특성을 필요한 곳에서만 다시 꺼내 보는 장치다.

    무엇을 고를 것인가, 그리고 흔한 오해

    표와 측정에서 나오는 결론은 단순하다. 대부분의 상황에서 기본 선택은 ArrayList다. 맨 뒤 추가와 인덱스 조회가 O(1)이고, 순회가 캐시에 유리하고, 원소당 메모리가 적다. O(n)인 가운데 삽입조차 실제 시간은 LinkedList보다 짧았다. ArrayList의 Javadoc도 상수 인자가 LinkedList 구현에 비해 낮다고 적는다.

    LinkedList가 이기는 것은 맨 앞에서의 추가와 삭제가 반복되고, 리스트가 충분히 길고, 인덱스 조회가 드문 경우다. 이 회차의 "최근 본 상품" 예제가 그런 모양이다. 다만 목록을 최근 20개로 제한한다면 n이 20을 넘지 않으므로 어느 구현이든 차이가 드러나지 않는다. 빅오는 n이 커질 때의 이야기이고, n이 작게 묶여 있으면 구현 선택은 중요한 문제가 아니다. 선택이 확실하지 않을 때 할 일은 추측이 아니라 측정이며, 앞에서 한 것처럼 의존관계를 주입해 두면 측정을 위해 구현을 바꾸는 데 한 줄이면 된다.

    오해 1: 연결 리스트는 삽입과 삭제가 빠르다

    빠른 것은 "이미 손에 쥔 노드의 앞뒤에 연결하는 동작"이다. 인덱스로 위치를 지정하면 그 노드까지 걸어가는 O(n)이 먼저 든다. 그래서 양 끝이 아닌 곳에서는 배열 리스트와 같은 O(n)이고, 실제 시간은 더 길었다.

    오해 2: 인터페이스 타입으로 선언하면 구현에 의존하지 않는다

    List list = new ArrayList<>()라고 쓴 클래스의 상수 풀에는 java/util/ArrayList가 그대로 있다. 의존을 끊는 것은 선언 타입이 아니라 new를 어디에 두느냐다. 물론 메서드 안의 지역 변수라면 이 정도로 충분하다. 구현을 바꿀 일이 생겨도 고칠 곳이 그 한 줄이기 때문이다. 주입까지 가야 하는 것은 그 선택이 클래스 바깥의 사정에 따라 달라지는 경우다.

    오해 3: 빅오가 같으면 성능도 같다

    빅오는 입력이 커질 때 연산 횟수가 늘어나는 모양만 말한다. 가운데 삽입에서 두 리스트는 같은 O(n)이고 횟수까지 거의 같았지만 시간은 크게 달랐다. 빅오로 후보를 거르고, 남은 후보는 한 번의 연산이 메모리에서 실제로 무엇을 하는지로 비교해야 한다.

    오해 4: 컴파일할 때 있던 클래스는 실행할 때도 모두 로딩된다

    클래스 파일에 이름이 적혀 있다는 것과 그 클래스가 로딩된다는 것은 다르다. 앞의 실험에서 쓰이지 않은 구현은 클래스 파일이 없어도 프로그램이 정상 종료했다. 반대로 말하면, 클래스 파일이 빠진 채 배포된 프로그램은 그 클래스를 처음 쓰는 순간에야 NoClassDefFoundError로 실패한다. 컴파일이 통과했다는 사실은 실행 환경에 필요한 클래스가 다 있다는 보증이 아니다.

    오해 5: 리스트는 무엇이든 찾을 수 있으니 검색에도 쓰면 된다

    indexOf와 contains는 두 구현 모두 앞에서부터 하나씩 equals로 비교하는 O(n)이다. 원소가 많은 리스트에 대해 반복문 안에서 contains를 부르면 전체가 O(n²)이 된다. 리스트는 순서와 위치를 다루는 자료 구조이지 "이 값이 있는가"에 빠르게 답하는 자료 구조가 아니다. 그 질문에 답하는 구조가 다음 회차의 해시다.

    다른 주제와의 연결

    이 회차의 앞 절반은 리스트 이야기처럼 보이지만 실은 객체를 조립하는 방법에 관한 이야기다. Main이 한 일, 곧 구현 객체를 만들고 그것을 필요로 하는 객체의 생성자에 넘기는 일은 프로그램이 커지면 수백 개의 클래스에 대해 반복된다. 로드맵 뒤쪽의 스프링 권에서 다루는 스프링 컨테이너는 이 조립을 대신 해 주는 도구다. 거기서 "스프링이 의존관계를 주입해 준다"는 말을 만나면, 이 회차에서 본 생성자 호출과 필드 대입이 실제로 일어나는 일의 전부라는 점을 떠올리면 된다. 테스트에서도 같은 구조가 쓰인다. 실제 구현 대신 시험용 구현을 주입하면 대상 클래스를 고치지 않고 격리해서 검증할 수 있다.

    컴파일 타임 의존관계를 인터페이스로 좁혀 두는 습관은 자바 표준 라이브러리를 쓰는 방식에도 그대로 이어진다. 필드와 매개변수, 반환 타입은 List로 선언하고 구현 클래스의 이름은 객체를 만드는 한 곳에만 둔다. 이 권의 나머지 회차에서 만날 Set과 Map도 같은 구조다. 인터페이스가 약속을 정하고, 해시 기반 구현과 트리 기반 구현이 서로 다른 비용으로 그 약속을 지킨다.

    뒤 절반에서 연습한 방법, 곧 시간을 재기 전에 연산 횟수를 세고 한 번의 연산이 메모리에서 하는 일을 따져 보는 방법은 자료 구조마다 되풀이된다. 다음 회차는 리스트가 풀지 못한 문제에서 출발한다. 값이 들어 있는지 찾는 데 드는 O(n)을 어떻게 O(1)에 가깝게 줄이는가이다.
    추상화와 인터페이스
    두 리스트가 공통으로 지키는 약속을 인터페이스로 분리하면, 메서드를 호출하는 코드는 invokeinterface와 인터페이스 이름만 담게 되어 구현을 모르게 된다.
    new가 남기는 의존
    필드를 인터페이스 타입으로 선언해도 그 클래스 안에서 new 구현클래스()를 하면 상수 풀에 구현 클래스의 이름이 남는다. 의존을 끊으려면 객체를 만드는 코드를 밖으로 옮겨야 한다.
    의존관계 주입
    사용할 객체를 스스로 만들지 않고 생성자 등으로 건네받는 것이다. 구현 선택이 조립하는 코드로 옮겨 가고, 사용하는 클래스는 구현이 바뀌어도 수정과 재컴파일이 필요 없다.
    컴파일 타임 의존관계와 런타임 의존관계
    앞의 것은 클래스 파일의 기호 참조에 적힌 타입 사이의 관계이고, 뒤의 것은 실행 중 힙에서 인스턴스가 인스턴스를 가리키는 참조다. 주입은 앞의 것을 인터페이스에 고정하고 뒤의 것을 실행 시점에 정한다.
    메서드 선택
    invokeinterface와 invokevirtual은 변수의 선언 타입이 아니라 수신 객체의 클래스를 기준으로 실행할 메서드를 고른다. HotSpot은 이를 위해 vtable과 itable을 두고, JIT 컴파일러는 관측한 타입을 근거로 호출을 인라인하기도 한다.
    배열 리스트의 비용
    인덱스 조회와 맨 뒤 추가는 O(1), 앞쪽에 넣거나 지우면 뒤의 원소를 모두 옮기는 O(n)이다. ArrayList는 1.5배씩 확장하고 System.arraycopy로 구간을 옮긴다.
    연결 리스트의 비용
    연결 자체는 O(1)이지만 인덱스로 노드를 찾는 데 O(n)이 든다. LinkedList는 이중 연결과 last 참조로 양 끝 연산을 O(1)로 만들고, 가까운 끝에서 탐색한다.
    빅오 밖의 차이
    연산 횟수가 같아도 연속한 메모리를 구간으로 복사하는 것과 흩어진 노드를 참조로 건너는 것은 비용이 다르다. 측정 환경에서 원소당 구조 비용도 배열 한 칸 4바이트 대 노드 24바이트였다.
    인덱스 반복문과 RandomAccess
    LinkedList에서 get(i) 반복은 O(n²)이 된다. 구현을 모를 때는 순회를 쓰고, 라이브러리는 RandomAccess 표지 인터페이스로 인덱스 접근이 빠른 리스트를 구분한다.

    실무에서 리스트 구현을 고르는 일은 대개 고민거리가 아니다. 필드와 매개변수는 List로 선언하고 ArrayList로 만든다. 개수를 미리 알면 초기 용량을 준다. 판단이 필요해지는 것은 성능 문제가 실제로 관측되었을 때이고, 그때 찾아야 할 것은 "어떤 자료 구조가 좋은가"가 아니라 "어느 코드가 n에 비례하는 일을 n번 하고 있는가"다. 긴 리스트의 맨 앞에 반복해서 넣는 코드, LinkedList를 인덱스로 도는 코드, 반복문 안에서 contains나 indexOf를 부르는 코드가 전형적인 모양이다. 셋 다 데이터가 적은 개발 환경에서는 보이지 않다가 운영 데이터가 쌓이면 드러난다.

    맨 앞 삽입이 병목이라고 해서 곧바로 LinkedList로 바꾸는 것이 답은 아니다. 같은 리스트를 다른 곳에서 인덱스로 읽고 있다면 병목이 옮겨 갈 뿐이다. 뒤에 추가하고 읽을 때 거꾸로 읽는 식으로 연산의 방향을 바꾸거나, 양 끝 연산에 맞춘 다른 자료 구조를 쓰는 편이 나은 경우가 많다. 어느 쪽이든 리스트를 쓰는 코드가 구현 클래스의 이름을 모르게 해 두었다면 바꿔 보고 재는 데 드는 비용이 작다.

    의존관계 주입도 모든 곳에 적용할 기법은 아니다. 메서드 안에서 잠깐 쓰는 지역 리스트까지 주입받을 이유는 없다. 인터페이스와 주입이 값을 하는 곳은 선택이 바깥 사정에 따라 달라지는 지점이다. 저장소가 메모리인지 데이터베이스인지, 외부 시스템을 실제로 호출할지 흉내 낼지, 정책이 고객마다 다른지 같은 것들이다. 판단 기준은 "이 new를 나중에 다른 것으로 바꿀 가능성이 있는가, 그리고 바꿀 때 이 클래스를 건드리고 싶은가"다.

    배포 문제를 볼 때도 이 회차의 구분이 쓰인다. 컴파일은 되는데 실행 중 특정 기능에서만 NoClassDefFoundError가 난다면, 컴파일할 때의 클래스패스와 실행할 때의 클래스패스가 다르고 그 차이가 해당 코드 경로를 처음 지날 때에야 드러난 것이다. 기호 참조가 사용 시점에 해석된다는 사실을 알면 "왜 시작할 때는 멀쩡했는가"를 설명할 수 있다.

    3번. 출력은 [0, 9, 2, 4] 3 false다. 처음 리스트는 [0, 1, 2, 3, 4]다. list.remove(1)의 인자는 int이므로 remove(int index)가 선택되어 인덱스 1의 원소 1이 지워지고 [0, 2, 3, 4]가 된다. list.remove(Integer.valueOf(3))의 인자는 Integer 참조이므로 remove(Object o)가 선택되어 값이 3인 원소가 지워지고 [0, 2, 4]가 된다. 컴파일러는 오버로드된 메서드를 고를 때 먼저 박싱·언박싱 없이 맞는 메서드를 찾기 때문에, int 인자는 Object로 박싱되기 전에 remove(int)에 걸린다. 이어서 add(1, 9)로 [0, 9, 2, 4]가 되고, 4의 위치는 3이며, 1은 이미 지워졌으므로 contains(1)은 false다. List에서 "값 1을 지우려고" remove(1)을 쓰면 인덱스 1이 지워진다는 점이 이 문제의 요점이다.

    4번. 배열은 1번째, 11번째, 16번째, 23번째 추가 때 새로 만들어진다. 생성 직후에는 길이 0인 배열을 가리키고 있다가 첫 추가에서 길이 10이 된다(복사할 원소 없음). 10개가 찬 뒤 11번째에 15로 늘면서 10개를, 16번째에 22로 늘면서 15개를, 23번째에 33으로 늘면서 22개를 복사한다. 복사 총수는 10 + 15 + 22 = 47개이고 마지막 배열 길이는 33이다. new ArrayList<>(23)이면 처음부터 길이 23인 배열을 만들므로 23개를 넣는 동안 교체도 복사도 없고 남는 칸도 없다.

    5번. LinkedList.get(i)는 인덱스가 절반보다 작으면 i번, 아니면 n − 1 − i번 노드를 건넌다. n이 100,000일 때 앞쪽 절반의 합은 0 + 1 + … + 49,999 = 1,249,975,000이고 뒤쪽 절반도 대칭으로 같으므로 전체는 2,499,950,000번이다. 원소 수에 대해 n² ÷ 4로 늘어나므로 데이터가 2배가 되면 일은 4배가 된다. 고치는 방법 첫째는 순회 방식을 바꾸는 것이다. for (String item : list)처럼 향상된 for 문을 쓰면 반복자가 현재 노드를 기억하므로 전체가 n번으로 끝난다. 둘째는 자료 구조를 바꾸는 것이다. 이 리스트가 뒤에 추가하고 차례로 읽는 용도라면 ArrayList로 충분하고 인덱스 조회도 O(1)이 된다. 리스트를 List 타입으로 선언하고 주입받게 해 두었다면 둘째 방법은 조립하는 코드 한 줄을 고치는 일이다. 두 방법을 함께 적용해도 좋다. 구현을 모르는 코드라면 인덱스 반복보다 순회를 쓰는 것이 안전하다.

     필드를 private final SimpleList items = new ArraySimpleList<>();로 선언한 클래스를 컴파일했다. 이 클래스 파일에 대한 설명으로 옳은 것은? 필드 타입이 인터페이스이므로 상수 풀에 ArraySimpleList라는 이름은 남지 않는다. items.add(...)는 invokeinterface로 번역되지만, 생성자의 new와 생성자 호출 때문에 상수 풀에 ArraySimpleList가 남는다. items.add(...)는 실제 객체가 ArraySimpleList이므로 invokevirtual ArraySimpleList.add로 번역된다. ArraySimpleList.class가 없어도 이 클래스는 컴파일된다. 컴파일러는 변수의 선언 타입으로 호출 명령과 기호 참조를 만든다. 선언 타입이 인터페이스이므로 호출은 invokeinterface SimpleList.add가 된다. 그러나 new ArraySimpleList<>()는 구현 클래스의 이름을 직접 쓰므로 new 명령과 생성자 호출이 그 이름을 상수 풀에 남긴다. 컴파일러는 실행 시점의 객체를 알 수 없으므로 세 번째 보기는 틀리고, new의 대상을 찾지 못하면 cannot find symbol 오류가 나므로 네 번째 보기도 틀리다. 이 회차의 Main은 실행 인자에 따라 ArraySimpleList 또는 LinkedSimpleList를 만든다. 컴파일 후 LinkedSimpleList의 클래스 파일을 지우고 인자 없이 java Main을 실행했더니 정상 종료했다. 가장 정확한 설명은? Main.class에는 실제로 실행될 클래스의 이름만 기록되기 때문이다. JVM이 시작할 때 없는 클래스를 자동으로 무시하도록 정해져 있기 때문이다. Main.class의 상수 풀에는 LinkedSimpleList라는 기호 참조가 있지만, 그 참조를 쓰는 명령이 실행되지 않아 해석과 로딩이 일어나지 않았기 때문이다. LinkedSimpleList가 SimpleList를 구현하므로 인터페이스의 클래스 파일만 있으면 충분하기 때문이다. 컴파일 타임 의존관계는 클래스 파일에 그대로 남는다. 두 구현의 이름이 모두 Main.class의 상수 풀에 있다. JVM 명세는 기호 참조를 사용할 때 해석하는 방식을 허용하고, 이 실험에서 HotSpot은 new LinkedSimpleList가 실행될 때에야 클래스를 찾았다. 그래서 그 분기를 지나지 않는 실행은 문제없이 끝나고, java Main linked는 NoClassDefFoundError로 실패한다. 인터페이스의 클래스 파일이 구현 클래스를 대신할 수는 없다. items.add(0, product)가 invokeinterface SimpleList.add로 컴파일되어 있다. 실행 시점에 어느 클래스의 add 코드가 실행될지를 정하는 기준은? 스택에서 꺼낸 수신 객체가 실제로 속한 클래스 필드 items의 선언 타입 클래스패스에서 SimpleList를 구현한 클래스 가운데 먼저 발견되는 것 호출하는 클래스의 상수 풀에 적힌 구현 클래스 이름 JVM 명세는 수신 객체의 클래스를 C라 하고 C에 대해 메서드를 선택한다고 정한다. 선언 타입은 컴파일러가 검사하고 기호 참조를 만드는 데 쓰일 뿐 실행 시점의 선택 기준이 아니다. 주입 방식의 클래스 파일에는 구현 클래스의 이름이 아예 없으므로 네 번째 보기는 성립할 수 없고, 클래스패스 순서는 메서드 선택과 관계가 없다. 원소 50,000개 규모에서 ArrayList와 LinkedList의 가운데 삽입은 둘 다 O(n)이고 계산한 연산 횟수도 거의 같았지만, 실제 시간은 ArrayList가 훨씬 짧았다. 이 차이를 가장 잘 설명하는 것은? ArrayList는 가운데 삽입이 분할 상환 O(1)이기 때문이다. LinkedList는 삽입할 때마다 전체 노드를 새 메모리로 복사하기 때문이다. ArrayList는 인터페이스를 거치지 않고 직접 호출되기 때문이다. ArrayList는 연속한 메모리 구간을 한 번에 복사하고, LinkedList는 흩어진 노드를 참조로 하나씩 따라가야 해서 한 번의 연산 비용이 다르기 때문이다. 빅오가 지우는 상수가 구조에 따라 다르다. 배열의 원소 이동은 이웃한 주소 사이의 구간 복사이고 System.arraycopy가 이를 처리한다. 연결 리스트는 다음 노드의 주소를 현재 노드를 읽어야 알 수 있고 노드가 힙 곳곳에 있어 캐시의 도움을 받기 어렵다. 분할 상환 O(1)은 맨 뒤 추가의 성질이고, LinkedList는 삽입 때 전체를 복사하지 않으며, 두 클래스 모두 List 타입으로 호출할 수 있다.
    추상화(abstraction)
    여러 구현에 공통인 약속만 남기고 구현 방법을 가리는 것. 자바에서는 주로 인터페이스로 표현한다.
    의존관계 주입(dependency injection, DI)
    객체가 사용할 다른 객체를 직접 생성하지 않고 생성자나 메서드를 통해 외부에서 건네받는 방식.
    컴파일 타임 의존관계(compile-time dependency)
    소스 코드와 클래스 파일에 적힌 타입 사이의 관계. 실행하지 않아도 알 수 있고, 바꾸려면 다시 컴파일해야 한다.
    런타임 의존관계(runtime dependency)
    실행 중 힙에 있는 인스턴스가 다른 인스턴스를 참조하는 관계. 객체를 만들어 연결할 때 정해진다.
    기호 참조(symbolic reference)
    클래스 파일의 상수 풀에 이름으로 적힌 클래스·필드·메서드에 대한 참조. JVM이 실행 중 실제 대상으로 해석한다.
    invokeinterface
    인터페이스에 선언된 메서드를 호출하는 JVM 명령. 수신 객체의 클래스를 기준으로 실행할 메서드를 선택한다.
    개방-폐쇄 원칙(open-closed principle, OCP)
    기능을 추가할 때 기존 코드를 고치지 않고 새 코드를 더하는 것으로 해결할 수 있어야 한다는 설계 원칙.
    이중 연결 리스트(doubly linked list)
    각 노드가 다음 노드와 이전 노드를 모두 가리키는 연결 리스트. java.util.LinkedList의 구조다.
    메모리 지역성(locality)
    가까운 주소의 데이터를 이어서 사용하는 성질. 연속한 배열은 CPU 캐시를 잘 활용하고, 흩어진 노드는 그러지 못한다.
    RandomAccess
    인덱스 접근이 빠른(대체로 상수 시간) List 구현임을 표시하는 표지 인터페이스. ArrayList는 구현하고 LinkedList는 구현하지 않는다.
