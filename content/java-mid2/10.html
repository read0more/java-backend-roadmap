    이 회차의 질문: 구조가 다른데 꺼내는 코드는 같을 수 있는가

    이 권에서 지금까지 만든 자료 구조를 떠올려 보자. 3회의 배열 리스트는 칸이 이어진 배열 하나였고, 4회의 연결 리스트는 참조로 이어진 노드의 사슬이었다. 6회부터 8회까지는 해시 값으로 버킷을 고르는 구조와 값의 크기로 좌우를 가르는 트리를 다뤘고, 9회에서는 키로 값을 찾는 맵과 끝으로만 드나드는 스택·큐를 봤다. 속 모양이 전부 다르다.

    속 모양이 다르면 "들어 있는 것을 전부 하나씩 꺼내 본다"는 단순한 일도 방법이 달라진다. 배열은 인덱스를 0부터 올리면 되고, 연결 리스트는 첫 노드에서 next를 따라가야 한다. 해시 구조는 버킷 배열을 처음부터 훑으면서 버킷마다 매달린 노드를 따라가야 하고, 트리는 왼쪽 서브트리, 자기 자신, 오른쪽 서브트리 순으로 내려갔다 올라와야 한다. 쓰는 쪽이 이 방법을 구조마다 알아야 한다면, 5회에서 인터페이스로 구현을 감춘 일은 절반만 된 셈이다.

    이 회차의 첫 번째 주제가 이 문제의 답이다. 자바는 "다음 원소가 있는가"와 "다음 원소를 달라"는 두 질문만으로 어떤 자료 구조든 훑을 수 있게 하는 약속을 정해 두었다. Iterable과 Iterator다. 향상된 for문은 이 약속 위에서 컴파일러가 대신 써 주는 코드이고, 순회 도중에 컬렉션을 고치면 터지는 ConcurrentModificationException도 이 약속을 구현한 코드에서 나온다.

    두 번째 주제는 정렬이다. 정렬 알고리즘이 원소에게 묻는 것은 하나뿐이다. 둘 중 누가 앞인가. 정수라면 CPU가 답하지만 객체라면 누군가 답을 정해 줘야 한다. 그 답을 원소 자신이 갖고 있게 하는 것이 Comparable이고, 바깥에서 따로 건네는 것이 Comparator다. 이 둘의 규약이 깨지면 무슨 일이 생기는지, 자바가 실제로 돌리는 정렬 알고리즘이 무엇을 보장하는지까지 내려간다.

    마지막으로 Collections와 Arrays의 도구 메서드와 수정할 수 없는 컬렉션을 살핀 다음, 이 권에서 다룬 컬렉션 프레임워크 전체를 한 장의 지도로 묶는다. 본문의 실행 결과, 오류 문구, 바이트코드, JDK 소스 인용은 모두 OpenJDK 21(Temurin 21.0.13)에서 직접 확인한 것이다.

    순회 1 — Iterable과 Iterator를 직접 만든다

    순회(iteration, traversal)는 자료 구조에 들어 있는 원소를 빠짐없이 한 번씩 방문하는 일이다. 방문하는 쪽에서 보면 필요한 것은 두 가지 동작뿐이다. 아직 방문하지 않은 원소가 남았는지 묻는 것, 그리고 다음 원소를 하나 받는 것. 자바는 이 두 동작을 java.util.Iterator 인터페이스로 정해 두었고, "이 객체는 그런 반복자를 내줄 수 있다"는 사실을 java.lang.Iterable 인터페이스로 표시한다.

    package java.lang;

public interface Iterable {
    Iterator iterator();          // 반복자를 하나 만들어 돌려준다
    // default 메서드 forEach, spliterator 생략
}

package java.util;

public interface Iterator {
    boolean hasNext();               // 남은 원소가 있는가
    E next();                        // 다음 원소를 돌려주고 한 칸 나아간다
    // default 메서드 remove, forEachRemaining 생략
}

    이름이 비슷해서 헷갈리기 쉬우니 역할을 먼저 못 박아 두자. Iterable은 "순회할 수 있는 것", 곧 자료 구조 쪽이다. Iterator는 "순회하는 것", 곧 지금 어디까지 왔는지를 기억하며 한 칸씩 나아가는 객체다. 한국어로는 보통 반복자라고 부른다. 자료 구조는 반복자를 만들어 내주기만 하고, 실제로 걸어가는 일은 반복자가 한다.

    속 모양이 다른 두 자료 구조에 이 약속을 구현해 보자. 하나는 배열을 감싼 것이고, 하나는 4회에서 본 단일 연결 구조다.

    import java.util.Iterator;
import java.util.NoSuchElementException;

class ArrayBox implements Iterable {
    private final String[] items;

    ArrayBox(String... items) {
        this.items = items;
    }

    @Override
    public Iterator iterator() {
        return new BoxIterator();          // 부를 때마다 새 반복자
    }

    private class BoxIterator implements Iterator {
        private int cursor = 0;            // 다음에 돌려줄 칸의 인덱스

        @Override
        public boolean hasNext() {
            return cursor < items.length;
        }

        @Override
        public String next() {
            if (!hasNext()) {
                throw new NoSuchElementException();
            }
            return items[cursor++];
        }
    }
}
    import java.util.Iterator;
import java.util.NoSuchElementException;

class Chain implements Iterable {
    private static class Node {
        final String item;
        final Node next;

        Node(String item, Node next) {
            this.item = item;
            this.next = next;
        }
    }

    private Node first;

    void addFirst(String item) {
        first = new Node(item, first);
    }

    @Override
    public Iterator iterator() {
        return new Iterator() {
            private Node cursor = first;   // 다음에 돌려줄 노드

            @Override
            public boolean hasNext() {
                return cursor != null;
            }

            @Override
            public String next() {
                if (cursor == null) {
                    throw new NoSuchElementException();
                }
                String item = cursor.item;
                cursor = cursor.next;
                return item;
            }
        };
    }
}

    두 반복자의 차이는 "위치"를 무엇으로 기억하느냐다. ArrayBox의 반복자는 정수 인덱스를, Chain의 반복자는 노드 참조를 들고 있다. hasNext()의 조건도 다르다. 하나는 인덱스가 길이보다 작은지를, 하나는 참조가 null이 아닌지를 본다. 그런데 바깥에서 부르는 메서드의 이름과 의미는 똑같다. 쓰는 쪽 코드를 보자.

    import java.util.Iterator;

public class IterMain {
    static void printAll(Iterable source) {
        Iterator it = source.iterator();
        while (it.hasNext()) {
            String s = it.next();
            System.out.print(s + " ");
        }
        System.out.println();
    }

    public static void main(String[] args) {
        ArrayBox box = new ArrayBox("A", "B", "C");

        Chain chain = new Chain();
        chain.addFirst("C");
        chain.addFirst("B");
        chain.addFirst("A");

        printAll(box);
        printAll(chain);
    }
}
    A B C
A B C

    printAll은 매개변수의 타입을 Iterable으로만 알고 있다. 넘어온 것이 배열인지 노드 사슬인지 모르고, 알 필요도 없다. 5회에서 리스트를 인터페이스 뒤로 감췄던 것과 같은 구조인데, 감춘 대상이 "저장 방식"에서 "훑는 방식"으로 바뀌었을 뿐이다.

    왜 인터페이스가 둘인가: 위치를 기억하는 상태

    자료 구조가 hasNext()와 next()를 직접 갖고 있으면 안 되는가 하는 의문이 든다. 답은 반복자에 상태가 있기 때문이다. "지금 어디까지 왔는가"라는 값은 순회 한 번마다 따로 있어야 한다. 그 값을 자료 구조 안에 필드 하나로 두면, 같은 자료 구조를 동시에 두 군데서 훑는 순간 서로의 위치를 망가뜨린다. 그래서 위치는 별도의 객체에 담고, 자료 구조는 그런 객체를 필요할 때마다 새로 만들어 준다.

    Iterator it1 = box.iterator();
Iterator it2 = box.iterator();

System.out.println(it1 == it2);               // false: 서로 다른 객체
System.out.println(it1.next() + it1.next());  // AB: it1만 두 칸 나아갔다
System.out.println(it2.next());               // A : it2는 처음 위치 그대로다

    이때의 힙을 그려 보면 다음과 같다. 반복자 객체 둘이 같은 ArrayBox를 가리키면서 저마다 cursor를 갖고 있다.

      it1                      it2
   │                        │
   ▼                        ▼
┌ BoxIterator ─┐      ┌ BoxIterator ─┐
│ cursor = 2   │      │ cursor = 1   │
│ this$0 ──┐   │      │ this$0 ──┐   │
└──────────┼───┘      └──────────┼───┘
           └───────┬─────────────┘
                   ▼
            ┌ ArrayBox ─┐        ┌ String[3] ───────────────┐
            │ items ────┼───────▶│ [0]→"A" [1]→"B" [2]→"C"  │
            └───────────┘        └──────────────────────────┘

    그림의 this$0은 소스에 없는 필드다. BoxIterator는 static이 붙지 않은 내부 클래스이므로, 중급 1편의 중첩 클래스 회차에서 본 대로 컴파일러가 바깥 인스턴스를 가리키는 숨은 필드를 넣는다. items[cursor++]라고만 썼지만 실제로는 this$0.items를 읽는 것이다. 클래스 파일을 열어 보면 그대로 나온다.

    class ArrayBox$BoxIterator implements java.util.Iterator {
  private int cursor;
  final ArrayBox this$0;
  private ArrayBox$BoxIterator(ArrayBox);
  public boolean hasNext();
  public java.lang.String next();
  public java.lang.Object next();
}

    next()가 둘인 것도 눈에 띈다. 반환 타입이 Object인 쪽은 2회에서 다룬 브리지 메서드다. Iterator의 next()는 타입 소거 뒤에 Object를 돌려주는 메서드가 되므로, 컴파일러가 그 시그니처로 들어온 호출을 String next()로 넘겨주는 메서드를 하나 더 만든 것이다. 이 사실은 조금 뒤 향상된 for문의 바이트코드를 읽을 때 다시 쓰인다.

    반복자의 규칙

    Iterator의 Javadoc이 정한 규칙은 짧다. hasNext()는 next()가 예외 없이 원소를 돌려줄 수 있으면 true다. next()는 다음 원소를 돌려주고, 더 돌려줄 원소가 없으면 NoSuchElementException을 던진다. 여기서 구현자가 지켜야 할 것이 두 가지 나온다. hasNext()는 몇 번을 불러도 위치를 옮기지 않아야 하고, next()는 끝을 넘었을 때 null이나 엉뚱한 값을 돌려주지 말고 예외를 던져야 한다. 위의 두 구현이 next() 첫머리에서 검사하는 이유다.

    반복자는 한 방향으로만 가고, 다 쓰면 끝이다. 처음으로 되돌리는 메서드가 없다. 다시 훑고 싶으면 iterator()를 한 번 더 불러 새 반복자를 받는다. 반복자를 값싸게 만들고 버리는 객체로 설계한 것이다.

    일상에서 가져온 비유책과 책갈피

    책 한 권을 두 사람이 번갈아 읽는다면 책갈피를 각자 하나씩 꽂는다. 책이 Iterable이고 책갈피가 Iterator다. 책은 내용을 갖고 있고, 책갈피는 "어디까지 읽었는가"만 갖고 있다. 책갈피가 책 속에 인쇄되어 있다면 한 번에 한 사람만 읽을 수 있을 것이다. 비유가 깨지는 지점도 있다. 종이 책갈피는 책의 쪽수가 바뀌어도 알아채지 못하지만, 자바 컬렉션의 반복자는 자기가 만들어진 뒤에 컬렉션이 바뀌었는지를 검사한다. 이 검사는 뒤의 fail-fast 절에서 다룬다.

    자료 구조(Iterable)는 원소를 갖고, 반복자(Iterator)는 위치만 갖는다는 것과 반복자를 여러 개 만들어도 서로 간섭하지 않는다는 것을 보여 준다. 흰 배경의 메모리 구조 다이어그램. 화면 아래쪽 가운데에 가로로 긴 세 칸짜리 배열이 있고 칸 안에 차례로 "A", "B", "C"가 적혀 있다. 배열 왼쪽에 둥근 모서리 상자가 있고 제목 "ArrayBox", 안에 한 줄 "items". items에서 배열로 가는 파란 화살표. 이 묶음 전체를 옅은 파란 점선 테두리로 감싸고 라벨 "Iterable (원소를 가진 쪽)". 화면 위쪽에는 작은 둥근 상자 두 개가 좌우로 떨어져 있다. 왼쪽 상자의 제목은 "반복자 1", 안에 "cursor = 2". 오른쪽 상자의 제목은 "반복자 2", 안에 "cursor = 1". 두 상자를 옅은 주황 점선 테두리로 감싸고 라벨 "Iterator (위치만 가진 쪽)". 왼쪽 상자에서 아래 배열의 세 번째 칸 "C" 위로 내려오는 주황색 화살표, 오른쪽 상자에서 두 번째 칸 "B" 위로 내려오는 주황색 화살표. 각 화살표 끝에 작은 글씨 "다음에 줄 칸". ArrayBox 상자에서 두 반복자 상자로 올라가는 회색 점선 화살표 두 개에 라벨 "iterator() 호출마다 새로 생성". 차분한 파랑과 회색, 강조는 주황. 평면적인 기술 도해 스타일. 원소는 자료 구조가 갖고, 위치는 반복자가 갖는다. 반복자는 부를 때마다 새로 만들어지므로 여러 순회가 서로를 방해하지 않는다.

    순회 2 — 향상된 for문은 컴파일러가 풀어 쓴다

    while (it.hasNext())로 시작하는 세 줄은 순회할 때마다 똑같이 반복된다. 자바 5에서 들어온 향상된 for문(enhanced for statement), 흔히 for-each라고 부르는 문법은 이 세 줄을 컴파일러가 대신 쓰게 한 것이다. JLS §14.14.2는 이 문법의 의미를 "다음과 같은 기본 for문으로 번역한 것과 같다"는 식으로 정의한다. 규칙은 두 갈래다.

    먼저 조건이 있다. 콜론 오른쪽 식의 타입은 배열이거나 Iterable의 하위 타입이어야 하고, 아니면 컴파일 오류다. 식이 Iterable이면 다음 모양으로 번역된다. #i는 컴파일러가 만든, 소스의 다른 이름과 겹치지 않는 변수다.

    for (I #i = Expression.iterator(); #i.hasNext(); ) {
    T Identifier = (TargetType) #i.next();
    Statement
}

    식이 배열이면 반복자가 등장하지 않는다. 배열 참조를 임시 변수에 한 번 담고, 정수 인덱스로 훑는다.

    S[] #a = Expression;
for (int #i = 0; #i < #a.length; #i++) {
    T Identifier = #a[#i];
    Statement
}

    명세의 말을 컴파일러가 실제로 그렇게 하는지 확인해 보자. 배열을 도는 메서드와 리스트를 도는 메서드를 나란히 놓고 바이트코드를 본다.

    import java.util.List;

public class ForEachMain {
    static int sumArray(int[] arr) {
        int sum = 0;
        for (int v : arr) {
            sum += v;
        }
        return sum;
    }

    번역 규칙에서 따라 나오는 것들

    향상된 for문의 동작에 대한 질문은 대부분 번역문을 보면 답이 나온다. 하나씩 확인해 보자.

    직접 만든 클래스도 for-each의 대상이 된다. 컴파일러가 확인하는 것은 식의 타입이 Iterable인가 하나뿐이다. java.util의 컬렉션일 필요가 없다. 더 나아가 원소를 저장하고 있을 필요조차 없다. 다음 클래스는 숫자를 하나도 담아 두지 않고, 요청받을 때마다 다음 숫자를 계산해서 내준다.

    import java.util.Iterator;
import java.util.NoSuchElementException;

public class Range implements Iterable {
    private final int from;
    private final int to;                  // to는 포함하지 않는다

    Range(int from, int to) {
        this.from = from;
        this.to = to;
    }

    @Override
    public Iterator iterator() {
        return new Iterator<>() {
            private int next = from;

            @Override
            public boolean hasNext() {
                return next < to;
            }

            @Override
            public Integer next() {
                if (next >= to) {
                    throw new NoSuchElementException();
                }
                return next++;
            }
        };
    }

    public static void main(String[] args) {
        int sum = 0;
        for (int n : new Range(1, 5)) {
            sum += n;
            System.out.print(n + " ");
        }
        System.out.println("합 = " + sum);
    }
}

    Iterable이 약속하는 것은 "원소를 차례로 내줄 수 있다"이지 "원소를 갖고 있다"가 아니라는 점을 이 예제가 보여 준다. 파일의 줄, 네트워크에서 오는 메시지, 계산으로 만들어지는 수열도 같은 약속으로 다룰 수 있다.

    콜론 오른쪽 식은 한 번만 평가된다. 번역문에서 Expression은 for문의 초기화 자리에 한 번 나온다. for (String s : loadNames())라고 써도 loadNames()는 한 번만 호출된다.

    식이 null이면 NullPointerException이다. null.iterator()나 null에 대한 arraylength를 실행하게 되기 때문이다. 원소가 0개인 컬렉션은 hasNext()가 처음부터 false라서 본문이 한 번도 실행되지 않을 뿐 문제가 없다. "없음"을 null이 아니라 빈 컬렉션으로 표현하라는 조언의 근거가 여기에 있다.

    반복 변수는 복사본이다. 번역문의 T Identifier = #a[#i]는 칸의 값을 지역 변수에 복사한다. 그 변수에 다른 값을 대입해도 배열의 칸은 바뀌지 않는다. int[] arr = {1, 2, 3}을 돌면서 v = v * 10을 해도 배열은 [1, 2, 3] 그대로다. 참조 타입이라면 복사되는 것이 참조이므로, 변수가 가리키는 객체의 필드를 바꾸는 것은 원래 객체에 반영된다. 기본편에서 다룬 "자바는 언제나 값을 복사한다"는 규칙의 한 사례다.

    Map은 for-each의 대상이 아니다. Map은 Iterable을 확장하지 않는다. 맵을 콜론 오른쪽에 그대로 놓으면 컴파일러가 이렇게 답한다.

    반복자가 성능을 바꾸는 경우

    반복자는 편의 문법이기만 한 것이 아니다. 연결 리스트에서는 시간 복잡도를 바꾼다. LinkedList의 Javadoc은 인덱스로 접근하는 연산이 리스트의 처음이나 끝 가운데 가까운 쪽에서부터 걸어간다고 적고 있다. 그래서 for (int i = 0; i < list.size(); i++) list.get(i)는 매번 사슬을 다시 걸어가고, 전체로는 노드를 건너는 횟수가 대략 n²/4번이 된다. O(n²)이다. 반복자는 "지금 서 있는 노드"를 필드로 기억하므로 next() 한 번이 참조 하나를 따라가는 O(1)이고, 전체가 O(n)이다.

    배열 리스트에서는 인덱스 반복과 반복자 반복이 모두 O(n)이다. 반복자 쪽에는 반복자 객체 하나를 만드는 일과 호출마다의 검사가 더 있지만, 어느 쪽이 더 빠른지를 가를 만큼의 차이인지는 측정해 봐야 아는 영역이다. 판단 기준은 이렇게 잡으면 된다. 인덱스가 따로 필요하지 않다면 for-each를 쓴다. 그러면 구현체가 LinkedList로 바뀌어도, HashSet으로 바뀌어도 순회 코드는 그 구조에 맞는 방법으로 돌아간다.

    순회 3 — 자바가 제공하는 Iterable과 Iterator

    컬렉션 프레임워크의 뿌리 인터페이스인 Collection는 Iterable를 확장한다. List, Set, Queue, Deque가 모두 Collection의 하위 인터페이스이므로, 이 권에서 다룬 구현체는 맵을 빼면 전부 iterator()를 갖고 있고 for-each의 대상이 된다. 다음 메서드 하나로 여섯 가지 구조의 합을 구할 수 있다.

    import java.util.*;

public class SumMain {
    static int sum(Iterable source) {
        int total = 0;
        for (int n : source) {
            total += n;
        }
        return total;
    }

    public static void main(String[] args) {
        List data = List.of(1, 2, 3, 4);

        System.out.println(sum(new ArrayList<>(data)));    // 배열
        System.out.println(sum(new LinkedList<>(data)));   // 이중 연결 노드
        System.out.println(sum(new HashSet<>(data)));      // 해시 테이블
        System.out.println(sum(new TreeSet<>(data)));      // 레드-블랙 트리
        System.out.println(sum(new ArrayDeque<>(data)));   // 원형 배열
        System.out.println(sum(new Range(1, 5)));          // 저장소 없음
    }
}

    Iterator와 Iterable의 나머지 메서드

    Iterator에는 추상 메서드 둘 말고 default 메서드가 둘 있다. remove()는 방금 next()가 돌려준 원소를 밑에 있는 컬렉션에서 지운다. 지원하지 않아도 되는 선택적 연산이라서 기본 구현은 UnsupportedOperationException을 던진다. 앞에서 만든 Range의 반복자에 remove()를 부르면 이 예외가 난다. forEachRemaining(action)은 남은 원소 전부에 대해 주어진 동작을 실행한다.

    Iterable에도 default 메서드 forEach(action)이 있다. 소스를 보면 특별한 것이 없다. for (T t : this) action.accept(t);가 전부다. 향상된 for문을 메서드 호출 모양으로 감싼 것이고, 동작을 인자로 넘기는 방식은 중급 1편에서 잠깐 본 람다와 함께 쓰인다.

    리스트에는 Iterator를 확장한 ListIterator도 있다. hasPrevious()와 previous()로 뒤로 갈 수 있고, set()으로 방금 본 원소를 바꾸거나 add()로 현재 위치에 끼워 넣을 수 있다. 연결 리스트의 "위치를 알고 있으면 삽입이 O(1)"이라는 장점을 실제로 쓰려면 이 반복자를 통해야 한다. 인덱스로 add(i, e)를 부르면 그 위치까지 걸어가는 비용을 다시 치르기 때문이다.

    자료 구조의 내부를 드러내지 않고 원소를 차례로 방문하게 하는 이 구조에는 반복자 패턴(Iterator pattern)이라는 이름이 붙어 있다. 자바는 이 패턴을 인터페이스 두 개와 문법 하나(향상된 for문)로 언어 수준에 들여놓았다.

    ArrayList의 Javadoc은 이 선택을 이렇게 설명한다. 반복자가 만들어진 뒤에 반복자 자신의 remove나 add가 아닌 방법으로 리스트가 구조적으로 수정되면 반복자는 ConcurrentModificationException을 던진다. 그럼으로써 언제 터질지 모르는 임의의 동작을 감수하는 대신 빠르고 깨끗하게 실패한다. 이 성질을 fail-fast라고 부른다. 잘못된 상태로 계속 가느니 잘못을 발견한 자리에서 멈추는 것이다.

    검사는 최선을 다할 뿐, 보장이 아니다

    같은 프로그램에서 지우는 원소만 "B"에서 "C"로 바꿔 보자. 끝에서 두 번째 원소다.

    List list = new ArrayList<>(List.of("A", "B", "C", "D"));
for (String s : list) {
    System.out.println("방문: " + s);
    if (s.equals("C")) {
        list.remove(s);
    }
}
System.out.println(list);
    방문: A
방문: B
방문: C
[A, B, D]

    예외가 나지 않는다. 그리고 "D"는 방문되지 않았다. 추적해 보면 이유가 보인다. "C"를 돌려준 직후 cursor는 3이다. 삭제로 size가 4에서 3이 된다. 다음 hasNext()는 cursor != size, 곧 3 ≠ 3을 계산해 false를 돌려주고, 반복은 next()를 부르지 않은 채 끝난다. 검사는 next() 안에 있으므로 실행될 기회가 없었다.

    이것은 구현의 결함이 아니라 문서에 적힌 한계다. Javadoc은 fail-fast 동작을 보장할 수 없다고, 반복자는 최선을 다해(best-effort) 예외를 던질 뿐이라고 밝힌다. 그리고 이렇게 맺는다. 이 예외에 프로그램의 정확성을 기대는 것은 잘못이며, fail-fast 동작은 버그를 찾는 용도로만 써야 한다. 예외가 안 났다고 코드가 옳은 것이 아니다. 위 코드는 조용히 틀렸다.

    덧붙여 hasNext()가 cursor < size가 아니라 cursor != size인 데에도 쓸모가 있다. 마지막 원소를 방문하다가 그 원소를 지우면 cursor가 size보다 1 커진다. 부등호였다면 반복이 조용히 끝났겠지만, !=이므로 true가 되어 next()가 불리고 검사에 걸린다.

    무엇이 구조적 수정인가

    ArrayList의 Javadoc은 구조적 수정을 원소를 하나 이상 더하거나 지우는 연산, 또는 내부 배열의 크기를 명시적으로 바꾸는 연산이라고 정의하고, 원소의 값을 바꾸기만 하는 것은 구조적 수정이 아니라고 덧붙인다. 그래서 순회 중에 list.set(i, 값)으로 칸의 내용을 바꾸는 것은 예외를 일으키지 않는다. 칸의 수와 위치가 그대로라서 반복자의 cursor가 여전히 옳기 때문이다.

    HashMap도 같은 방식으로 modCount를 센다. 이미 있는 키에 put으로 값을 덮어쓰는 것은 노드가 늘지 않으므로 구조적 수정이 아니고, 새 키를 넣는 것은 구조적 수정이다. keySet()을 돌면서 map.put(k, map.get(k) * 10)을 하면 정상적으로 끝나지만 map.put(k + k, 0)을 하면 ConcurrentModificationException이 난다. 반대로 원소 수가 그대로여도 구조적 수정으로 세는 경우가 있다. ArrayList.sort는 끝에서 modCount++를 실행한다. 순회 중에 그 리스트를 정렬하면 다음 next()에서 예외가 난다.

    순회하면서 지우는 올바른 방법

    반복자에게 삭제를 맡기면 된다. Iterator.remove()는 방금 돌려준 원소를 지우면서 반복자 자신의 상태를 함께 고친다. ArrayList.Itr.remove()의 핵심은 네 줄이다. ArrayList.this.remove(lastRet)로 지우고, cursor = lastRet으로 당겨진 만큼 커서를 되돌리고, lastRet = -1로 "방금 돌려준 원소"를 비우고, expectedModCount = modCount로 기대값을 새로 맞춘다. 커서 보정과 기대값 갱신, 두 가지가 바깥에서 지울 때 빠져 있던 것이다.

    List list = new ArrayList<>(List.of("A", "B", "C", "D"));

Iterator it = list.iterator();
while (it.hasNext()) {
    String s = it.next();
    if (s.equals("B") || s.equals("C")) {
        it.remove();                 // 반복자를 통해 지운다
    }
}
System.out.println(list);            // [A, D]

List list2 = new ArrayList<>(List.of("A", "B", "C", "D"));
list2.removeIf(s -> s.equals("B") || s.equals("C"));
System.out.println(list2);           // [A, D]

    lastRet = -1 때문에 next() 한 번에 remove()는 한 번만 부를 수 있다. 연달아 두 번 부르면 IllegalStateException이 난다. 두 번째 방법인 removeIf는 자바 8에서 Collection에 추가된 메서드로, 조건을 넘기면 컬렉션이 스스로 훑으며 지운다. ArrayList는 이 메서드를 따로 구현해 두었다. 지울 원소에 먼저 표시만 해 두고, 남길 원소를 앞으로 모으는 이동을 한 번에 한다. 반복자의 remove()는 지울 때마다 뒤쪽 원소 전체를 한 칸씩 당기므로 지울 것이 많으면 O(n²)까지 가지만, removeIf는 O(n)이다.

    마지막으로 이름에 대해 짚어 둔다. 예외 이름의 Concurrent 때문에 스레드 문제로 오해하기 쉽지만, 지금까지의 예제에는 스레드가 하나뿐이었다. ConcurrentModificationException의 Javadoc도 이 예외가 언제나 다른 스레드의 수정을 뜻하는 것은 아니라고 명시한다. 여기서 "동시"는 "순회가 진행되는 동안"이라는 뜻이다. 거꾸로, modCount는 평범한 int 필드일 뿐 스레드 사이의 동기화 수단이 아니다. 여러 스레드가 한 컬렉션을 건드리는 상황은 이 검사로 막을 수 없고, 그 문제는 고급 1편에서 동시성 컬렉션과 함께 다룬다.

    삭제 직후 배열이 당겨져 커서가 가리키는 칸의 내용이 달라지고, 다음 next()에서 두 카운터의 불일치가 발견된다는 것을 세 장면으로 보여 준다. 흰 배경의 가로 3단계 다이어그램. 세 장면이 왼쪽에서 오른쪽으로 화살표로 이어진다. 각 장면에는 위쪽에 가로 배열이 있고 아래쪽에 작은 상자 두 개가 있다. 장면 1의 제목 "B를 방문한 직후". 배열은 네 칸 "A", "B", "C", "D"이고, 세 번째 칸 "C" 위에 주황색 삼각형 표시와 라벨 "cursor = 2". 아래 상자 두 개에는 각각 "modCount = m", "expectedModCount = m"이라고 적고 둘 사이에 초록색 등호. 장면 2의 제목 "리스트에서 B를 삭제". 배열은 세 칸 "A", "C", "D"와 옅은 회색 빈 칸 하나이고, "C"와 "D" 위에 왼쪽으로 한 칸 이동을 나타내는 짧은 곡선 화살표. 주황색 삼각형은 여전히 세 번째 칸 위에 있는데 그 칸의 내용은 이제 "D". 아래 상자는 "modCount = m+1"(빨간 글씨), "expectedModCount = m". 장면 3의 제목 "다음 next() 호출". 배열은 장면 2와 같고, 아래 두 상자 사이에 빨간색 부등호(≠)와 번개 모양 아이콘, 그 아래 라벨 "ConcurrentModificationException". 장면 3 오른쪽 구석에 작은 회색 글씨 "검사가 없었다면 C를 건너뛴다". 차분한 파랑과 회색, 커서는 주황, 불일치는 빨강. 평면적인 기술 도해 스타일. 바깥에서 지우면 배열은 당겨지는데 반복자의 커서는 그대로다. 반복자는 다음 next()에서 수정 횟수가 달라진 것을 보고 멈춘다.

    정렬 1 — 순서는 원소가 정한다: Comparable

    정렬(sort)은 원소를 정해진 순서대로 늘어놓는 일이다. 여기서 다루는 정렬 알고리즘은 모두 비교 기반이다. 알고리즘은 원소의 내용을 모른다. 하는 일은 두 원소를 골라 "누가 앞인가"를 묻고, 답에 따라 자리를 옮기는 것의 반복이다. 원소가 int라면 JVM에 두 정수를 비교하는 명령이 있으니 물을 것도 없다. 그런데 원소가 객체라면 변수에 들어 있는 것은 참조이고, 참조끼리는 같은지 다른지만 가릴 수 있을 뿐 크고 작음이 없다. 회원 객체 둘 가운데 누가 앞인지는 그 클래스를 만든 사람이 정해 줘야 한다.

    그 답을 클래스 자신이 갖고 있게 하는 인터페이스가 java.lang.Comparable다. 메서드는 int compareTo(T o) 하나다. 자기 자신(this)이 인자 o보다 앞이면 음수, 순서가 같으면 0, 뒤면 양수를 돌려준다. Javadoc은 이렇게 정해진 순서를 그 클래스의 자연 순서(natural ordering)라고 부른다. Integer, String 같은 클래스는 이미 이 인터페이스를 구현하고 있다.

    import java.util.Arrays;

public class NaturalOrderMain {
    public static void main(String[] args) {
        Integer[] nums = {30, 10, 20};
        Arrays.sort(nums);
        System.out.println(Arrays.toString(nums));

        String[] words = {"banana", "Apple", "cherry", "apple", "Banana"};
        Arrays.sort(words);
        System.out.println(Arrays.toString(words));

        String[] mixed = {"다", "가", "나", "a", "Z", "1"};

        System.out.println(Arrays.toString(mixed));

        System.out.println("b".compareTo("a"));
        System.out.println("a".compareTo("a"));
        System.out.println("apple".compareTo("Banana"));
    }
}

    마지막 줄의 31에서 하나 더 배운다. compareTo의 반환값에서 의미가 있는 것은 부호뿐이다. -1, 0, 1만 나온다고 가정하고 == 1이나 == -1로 비교하는 코드는 틀린 코드다. < 0, == 0, > 0으로 써야 한다.

    compareTo가 지켜야 하는 규약

    compareTo는 아무 정수나 돌려주면 되는 메서드가 아니다. Javadoc은 구현자가 반드시 지켜야 할 조건 세 가지를 적고 있다. sgn은 부호(음수면 -1, 0이면 0, 양수면 1)를 뜻한다.

    • 대칭성: 모든 x, y에 대해 sgn(x.compareTo(y)) == -sgn(y.compareTo(x)). x가 y보다 앞이면 y는 x보다 뒤여야 한다. x와 자기 자신을 넣어 보면 x.compareTo(x)는 0일 수밖에 없다는 것도 나온다.
    • 추이성: x.compareTo(y) > 0이고 y.compareTo(z) > 0이면 x.compareTo(z) > 0. x가 y보다 뒤이고 y가 z보다 뒤이면 x는 z보다 뒤다.
    • 동순위의 일관성: x.compareTo(y) == 0이면 모든 z에 대해 sgn(x.compareTo(z)) == sgn(y.compareTo(z)). 순서가 같은 둘은 다른 어떤 원소와 견줘도 같은 결과를 내야 한다.

    이 세 조건이 필요한 이유는 정렬 알고리즘이 모든 쌍을 비교하지 않기 때문이다. 원소가 n개면 쌍은 n(n−1)/2개인데, 좋은 정렬은 그보다 훨씬 적은 횟수만 묻는다. a가 b보다 앞이고 b가 c보다 앞이라는 답을 얻었으면 a와 c는 묻지 않고 a를 앞에 둔다. 묻지 않은 쌍의 답을 이미 얻은 답에서 추론하는 것이다. 추론이 맞으려면 비교가 위의 조건을 만족해야 한다. 조건이 깨지면 알고리즘은 틀린 추론 위에서 계속 진행하고, 그 결과는 정렬 2의 함정에서 직접 보게 된다.

    네 번째로, 필수는 아니지만 강하게 권장되는 것이 있다. x.compareTo(y) == 0인 것과 x.equals(y)가 참인 것이 일치해야 한다는 것이다. Javadoc은 이것을 equals와 일관된(consistent with equals) 순서라고 부른다. 이 권장을 어기면 무슨 일이 생기는지는 뒤의 "정렬 컬렉션은 equals를 묻지 않는다"에서 확인한다.

    정렬 2 — 순서를 바깥에서 건넨다: Comparator

    자연 순서는 클래스에 하나만 줄 수 있다. Runner를 나이순으로 정했다면 이름순으로 보고 싶을 때 쓸 수가 없다. 고칠 수 없는 클래스도 있다. String의 자연 순서가 마음에 들지 않아도 String을 고칠 수는 없다. 그리고 "어떤 순서로 보여 줄 것인가"는 대개 원소의 본질이 아니라 화면이나 기능의 사정이다. 순서를 원소 바깥의 객체로 떼어 낼 필요가 여기서 나온다.

    java.util.Comparator가 그 객체의 타입이다. 추상 메서드는 int compare(T o1, T o2) 하나이고, 반환값의 의미는 compareTo와 같다. 첫 인자가 앞이면 음수, 같으면 0, 뒤면 양수다. 지켜야 하는 규약 세 가지도 같다. 차이는 비교의 주체가 원소가 아니라 제삼자라는 점이다. 그래서 인자가 둘이다. 한국어로는 비교자라고 부른다.

    import java.util.Comparator;

class ByName implements Comparator {
    @Override
    public int compare(Runner a, Runner b) {
        return a.name.compareTo(b.name);     // String의 자연 순서에 맡긴다
    }
}
    import java.util.ArrayList;
import java.util.Arrays;
import java.util.Comparator;
import java.util.List;

public class ComparatorMain {
    public static void main(String[] args) {
        Runner[] runners = {
            new Runner("다온", 31), new Runner("가람", 27),
            new Runner("나래", 31), new Runner("라희", 27), new Runner("마루", 24)
        };

        Arrays.sort(runners, new ByName());
        System.out.println(Arrays.toString(runners));

        Arrays.sort(runners, new ByName().reversed());
        System.out.println(Arrays.toString(runners));

        List list = new ArrayList<>(List.of(runners));
        list.sort(Comparator.comparing((Runner r) -> r.age).reversed()
                .thenComparing(r -> r.name));
        System.out.println(list);

        list.sort(null);                     // null이면 자연 순서(compareTo)
        System.out.println(list);
    }
}

[마루(24), 라희(27), 다온(31), 나래(31), 가람(27)]

    비교자를 넘기면 정렬은 원소의 compareTo를 부르지 않고 비교자의 compare만 부른다. 원소가 Comparable이든 아니든 상관없다. 첫 줄은 이름순, 둘째 줄은 그 역순이다. reversed()는 Comparator의 default 메서드로, 원래 비교자를 감싸 인자의 자리를 바꿔 부르는 새 비교자를 돌려준다. OpenJDK 21 소스에서 그 비교자의 compare(t1, t2)는 cmp.compare(t2, t1) 한 줄이다. 결과에 -1을 곱하는 것이 아니라 인자를 뒤집는다.

    셋째 줄은 비교자를 조립한 것이다. Comparator.comparing은 원소에서 비교 기준이 될 값을 뽑는 함수를 받아, 뽑은 값끼리 compareTo로 견주는 비교자를 만든다. thenComparing은 앞의 비교가 0을 돌려줄 때만 다음 기준을 묻는 비교자를 만든다. 소스로는 int res = compare(c1, c2); return (res != 0) ? res : other.compare(c1, c2);다. 그래서 "나이 내림차순, 나이가 같으면 이름 오름차순"이 된다. 인자로 넘긴 r -> r.age는 중급 1편 8회에서 본 람다이고, 클래스를 따로 선언하지 않고 비교 기준만 적은 것이다. Comparator는 추상 메서드가 하나뿐인 함수형 인터페이스라서 람다를 받을 수 있다.

    비교자를 받는 자리는 정렬 메서드만이 아니다. 순서가 필요한 곳이면 어디든 받는다. Arrays.sort(배열, 비교자), List.sort(비교자), Collections.sort(리스트, 비교자), Collections.max(컬렉션, 비교자), 그리고 TreeSet, TreeMap, PriorityQueue의 생성자가 그렇다. 정렬 컬렉션에 비교자를 넘기면 그 컬렉션은 원소의 자연 순서 대신 비교자의 순서로 자리를 잡는다.

    Comparable과 Comparator

    Comparable은 원소가 "나는 이렇게 줄을 선다"고 스스로 밝히는 것이고, Comparator는 바깥에서 "이번에는 이 기준으로 줄을 세운다"고 정하는 것이다. 클래스에 누가 봐도 당연한 순서가 하나 있으면(수의 크기, 날짜의 선후) Comparable로 두고, 그 밖의 순서는 필요한 자리에서 Comparator로 건넨다. 둘 다 있으면 비교자가 우선한다.

    함정 1: 뺄셈으로 만든 비교

    정수 필드를 비교할 때 a - b를 돌려주는 코드를 흔히 본다. a가 작으면 음수, 같으면 0, 크면 양수이니 맞는 것처럼 보인다. 다음을 실행해 보자.

    import java.util.Arrays;
import java.util.Comparator;

public class SubtractMain {
    public static void main(String[] args) {
        Comparator bySubtract = new Comparator<>() {
            @Override
            public int compare(Integer a, Integer b) {
                return a - b;                 // 흔히 쓰는 지름길
            }
        };

        System.out.println(bySubtract.compare(-2_000_000_000, 2_000_000_000));
        System.out.println(Integer.compare(-2_000_000_000, 2_000_000_000));

        Integer[] xs = {2_000_000_000, -2_000_000_000, 0};
        Arrays.sort(xs, bySubtract);
        System.out.println(Arrays.toString(xs));
    }
}

    −20억에서 20억을 빼면 −40억인데, int가 담을 수 있는 가장 작은 값은 −2,147,483,648이다. 입문편에서 본 오버플로가 일어나 결과는 −4,000,000,000 + 2³² = 294,967,296, 양수가 된다. 비교자가 "−20억이 20억보다 뒤"라고 답한 것이다. 그 결과 정렬을 마친 배열이 정렬되어 있지 않다. 예외도 없다.

    이 비교자는 규약을 어긴다. −20억은 0보다 앞이고(−20억 − 0은 음수) 0은 20억보다 앞인데(0 − 20억은 음수) −20억은 20억보다 뒤라고 하니 추이성이 깨진다. 나이처럼 범위가 좁은 값에서는 드러나지 않다가, 금액이나 ID처럼 큰 값이 섞일 때 터진다. Integer.compare(x, y)를 쓰면 된다. 소스는 (x < y) ? -1 : ((x == y) ? 0 : 1)로, 빼지 않고 견준다. Long.compare, Double.compare도 같은 용도다.

    함정 2: 0을 돌려주지 않는 비교

    두 번째 함정은 "같다"를 빼먹는 것이다. 크면 1, 아니면 -1을 돌려주는 비교자를 만들어 같은 값이 여럿 든 배열을 정렬해 보자.

    import java.util.Arrays;
import java.util.Comparator;

public class NoZeroMain {
    public static void main(String[] args) {
        Comparator noZero = new Comparator<>() {
            @Override
            public int compare(Integer a, Integer b) {
                return a > b ? 1 : -1;        // 같을 때도 -1을 돌려준다
            }
        };

        for (int n : new int[]{31, 32, 100}) {
            Integer[] arr = new Integer[n];
            for (int i = 0; i < n; i++) {
                arr[i] = i % 3;               // 0, 1, 2, 0, 1, 2, ...
            }
            try {
                Arrays.sort(arr, noZero);
                System.out.println(n + "개: 예외 없음");
            } catch (IllegalArgumentException e) {
                System.out.println(n + "개: " + e.getMessage());
            }
        }
    }
}
    31개: 예외 없음
32개: Comparison method violates its general contract!
100개: Comparison method violates its general contract!

    이 비교자에서 compare(1, 1)은 -1이다. 인자를 바꿔도 -1이다. "x가 y보다 앞이면 y는 x보다 뒤"라는 대칭성이 깨졌다. 그런데 원소가 31개일 때는 아무 일도 없고 32개부터 예외가 난다. 이 경계는 정렬 3에서 볼 구현 상수에서 나온다. OpenJDK의 정렬은 원소가 32개 미만이면 병합 없이 삽입 정렬만으로 끝내고, 32개 이상이면 구간을 나눠 정렬한 뒤 병합한다. 예외는 병합하는 코드에 있다. 정렬된 두 구간을 합치다가 규약이 지켜졌다면 있을 수 없는 상태를 만나면 던진다.

    이 예외도 최선을 다한 검출일 뿐이다. List.sort의 Javadoc은 이 IllegalArgumentException에 "(optional)"이라는 꼬리표를 달아 두었다. 구현이 위반을 발견하면 던질 수 있다는 뜻이지, 위반하면 반드시 던진다는 뜻이 아니다. 앞의 뺄셈 비교자는 규약을 어겼는데도 조용히 틀린 결과를 냈다. 그리고 테스트 데이터 10건에서는 통과하던 코드가 운영 데이터 수천 건에서 처음 터지는 일이 이 구조에서 나온다. 비교자를 쓸 때는 "같으면 0"을 포함해 규약 세 가지를 눈으로 확인하는 수밖에 없다.

    정렬 3 — 한 층 아래: 안정 정렬과 TimSort

    정렬 1의 실행 결과에서 나이가 같은 원소들이 원래 순서를 유지했다. 이 성질을 안정성(stability)이라고 하고, 그런 정렬을 안정 정렬(stable sort)이라고 한다. 비교 결과가 0인 원소들끼리는 정렬 전의 상대 순서가 정렬 후에도 그대로라는 뜻이다. Arrays.sort(Object[]), List.sort, Collections.sort의 Javadoc에는 모두 같은 문장이 있다. "This sort is guaranteed to be stable: equal elements will not be reordered as a result of the sort." 구현의 우연이 아니라 API의 보장이다.

    안정성이 실제로 쓸모 있는 장면은 기준이 둘 이상일 때다. 먼저 이름순으로 정렬하고, 그 결과를 나이순으로 다시 정렬해 보자.

    import java.util.ArrayList;
import java.util.List;

public class StableMain {
    public static void main(String[] args) {
        List list = new ArrayList<>(List.of(
            new Runner("다온", 31), new Runner("가람", 27),
            new Runner("나래", 31), new Runner("라희", 27), new Runner("마루", 24)));

        list.sort(new ByName());
        System.out.println("이름순: " + list);

        list.sort(null);
        System.out.println("나이순: " + list);
    }
}
    이름순: [가람(27), 나래(31), 다온(31), 라희(27), 마루(24)]
나이순: [마루(24), 가람(27), 라희(27), 나래(31), 다온(31)]

    두 번째 정렬은 나이만 봤는데, 나이가 같은 원소들이 이름순으로 늘어서 있다. 첫 번째 정렬이 만든 이름 순서를 두 번째 정렬이 동순위 안에서 깨뜨리지 않았기 때문이다. 표의 열 제목을 차례로 눌러 정렬하는 화면이 기대대로 동작하는 것도 이 성질 덕분이다. 덜 중요한 기준부터 먼저 정렬하고 가장 중요한 기준을 마지막에 정렬한다는 순서만 기억하면 된다. 안정하지 않은 정렬이라면 두 번째 정렬 뒤에 27세 두 명의 순서가 어떻게 될지 알 수 없다.

    나이가 같은 카드들의 상대 순서가 안정 정렬에서는 유지되고 불안정 정렬에서는 뒤바뀔 수 있다는 것을 보여 준다. 흰 배경의 비교 다이어그램. 맨 위 가운데에 "입력"이라는 라벨과 함께 카드 다섯 장이 가로로 놓여 있다. 카드마다 큰 숫자와 작은 이름이 적혀 있다. 왼쪽부터 "27 가람", "31 나래", "31 다온", "27 라희", "24 마루". 숫자 27인 카드 두 장은 파란색, 31인 카드 두 장은 초록색, 24인 카드는 회색이다. 입력에서 아래 왼쪽과 아래 오른쪽으로 화살표가 갈라진다. 아래 왼쪽 묶음의 제목은 "안정 정렬". 카드가 "24 마루", "27 가람", "27 라희", "31 나래", "31 다온" 순서로 놓여 있고, 파란 카드 두 장 아래에 "가람 → 라희 순서 유지", 초록 카드 두 장 아래에 "나래 → 다온 순서 유지"라는 작은 글씨와 체크 표시. 아래 오른쪽 묶음의 제목은 "불안정 정렬 (가능한 결과의 하나)". 카드가 "24 마루", "27 라희", "27 가람", "31 다온", "31 나래" 순서로 놓여 있고, 파란 카드 두 장과 초록 카드 두 장 위에 각각 서로 교차하는 주황색 화살표. 맨 아래에 작은 글씨 "숫자만 보면 둘 다 정렬된 결과다". 차분한 파랑·초록·회색, 강조는 주황. 평면적인 기술 도해 스타일. 비교 기준만 보면 두 결과 모두 정렬되어 있다. 안정 정렬은 여기에 더해 동순위 원소의 원래 순서를 지킨다.

    호출은 어디로 흘러가는가

    정렬 메서드가 여럿이지만 끝은 한 곳이다. OpenJDK 21 소스를 따라가면 다음과 같다.

    Collections.sort(list)        → list.sort(null)
Collections.sort(list, c)     → list.sort(c)

ArrayList.sort(c)             → Arrays.sort(elementData, 0, size, c)   내부 배열을 그 자리에서 정렬
                                 그리고 modCount++
List.sort(c)의 기본 구현       → Object[] a = this.toArray();          배열로 복사
(LinkedList가 쓰는 것)           Arrays.sort(a, c);                     배열을 정렬
                                 ListIterator로 돌며 set(...)           결과를 다시 써넣는다

Arrays.sort(a, c)   c != null → TimSort.sort(...)             compare를 부른다
Arrays.sort(a)      c == null → ComparableTimSort.sort(...)   compareTo를 부른다
Arrays.sort(int[])            → DualPivotQuicksort.sort(...)  기본형 전용

    여기서 세 가지를 읽을 수 있다. 첫째, 리스트의 정렬은 결국 배열의 정렬이다. ArrayList는 자기 내부 배열을 그대로 넘기고, LinkedList는 따로 구현이 없어 인터페이스의 기본 구현을 쓴다. 노드의 연결을 바꿔 가며 정렬하지 않는다. 원소를 배열로 복사해 정렬한 뒤, 반복자로 처음부터 돌면서 각 노드의 값을 바꿔 넣는다. 둘째, 정렬은 새 리스트를 만들지 않고 그 자리에서(in place) 원본을 바꾼다. 셋째, 객체 배열과 기본형 배열은 서로 다른 알고리즘을 쓴다.

    세 번째 점의 이유는 안정성이다. Arrays.sort(int[])의 Javadoc은 구현이 이중 피벗 퀵 정렬(Dual-Pivot Quicksort)이라고 밝힌다. 퀵 정렬 계열은 일반적으로 안정하지 않다. 그런데 기본형에서는 그것이 문제가 되지 않는다. 값이 같은 두 int는 구별할 방법이 없으므로 순서가 바뀌어도 관찰할 수 없다. 객체는 다르다. 비교 결과가 0이어도 서로 다른 객체이고 다른 필드를 갖고 있으므로 순서가 바뀐 것이 보인다. 그래서 객체 쪽은 안정성을 보장하는 병합 정렬 계열을 쓴다.

    TimSort가 하는 일

    Arrays.sort(Object[])의 Javadoc은 구현을 "안정적이고 적응적인 반복형 병합 정렬"이라고 소개하고, 팀 피터스(Tim Peters)가 파이썬의 리스트 정렬을 위해 만든 TimSort에서 가져왔다고 밝힌다. 적응적(adaptive)이라는 말은 입력이 이미 얼마나 정렬되어 있느냐에 따라 일의 양이 달라진다는 뜻이다. 실제 데이터는 완전히 뒤섞여 있기보다 군데군데 정렬된 구간을 갖고 있는 경우가 많다는 관찰에서 출발한 알고리즘이다. TimSort.java를 따라 큰 줄기를 보자.

    런을 찾는 규칙을 작은 배열로 따라가 보자. 규칙만 보려는 것이므로 길이 제한은 잠시 잊는다.

    입력:   1  2  5  9  8  6  3  4  7  7

런 1:  [1  2  5  9]              1 ≤ 2 ≤ 5 ≤ 9, 다음의 8이 9보다 작으므로 여기서 끊는다
런 2:              [8  6  3]     8 > 6 > 3, 다음의 4가 3보다 크므로 여기서 끊는다 → 뒤집어 [3 6 8]
런 3:                       [4  7  7]   4 ≤ 7 ≤ 7

뒤집은 뒤: [1 2 5 9] [3 6 8] [4 7 7]   → 이웃한 런끼리 병합

    내림차순의 조건이 "크거나 같다"가 아니라 "크다"인 데에 안정성이 걸려 있다. 소스의 주석이 이유를 적어 두었다. 내림차순 구간을 뒤집어도 안정성이 깨지지 않으려면 엄격한 내림차순이어야 한다는 것이다. 같은 값이 섞인 구간을 뒤집으면 동순위 원소의 순서가 거꾸로 되기 때문이다. 오름차순 쪽에서는 같은 값이 이어져도 그대로 두면 되므로 등호를 허용한다. 런 3이 7 7을 품을 수 있는 이유다.

    병합은 정렬된 두 런을 앞에서부터 견줘 작은 쪽을 먼저 내려놓는 일이다. 두 원소의 비교 결과가 0이면 왼쪽 런의 것을 먼저 내려놓는다. 왼쪽 런은 원래 배열에서 앞에 있던 구간이므로 이렇게 하면 동순위의 순서가 유지된다. 병합에는 두 런 가운데 짧은 쪽을 옮겨 둘 임시 배열이 필요하다. Javadoc은 이 임시 공간이 거의 정렬된 입력에서는 작은 상수이고, 무작위 입력에서는 최대 n/2개의 참조라고 적는다. 병합 중에 한쪽 런의 원소가 연달아 선택되면(MIN_GALLOP, 7번) 한 칸씩 견주는 대신 보폭을 늘려 가며 건너뛰는 갤러핑(galloping) 방식으로 바뀐다. 한쪽이 통째로 앞서는 구간을 빨리 지나가기 위한 것이다.

    정렬이 옮기는 것은 참조다. Runner 객체는 힙의 제자리에 있고, 배열의 칸에 든 참조만 자리를 바꾼다. 원소 객체가 아무리 커도 정렬 중에 복사되는 것은 칸 하나 크기의 참조뿐이다.

    입력에 이미 들어 있는 정렬된 구간(런)을 찾아 재활용하고, 내림차순 구간은 뒤집으며, 런끼리 병합해 전체를 완성한다는 흐름을 세 줄로 보여 준다. 흰 배경의 세로 3단 다이어그램. 각 단에는 숫자 칸 열 개가 가로로 놓여 있다. 1단의 왼쪽 라벨은 "1. 런 찾기". 칸의 숫자는 왼쪽부터 1, 2, 5, 9, 8, 6, 3, 4, 7, 7. 앞의 네 칸을 파란 테두리로 묶고 위에 "오름차순 런", 다음 세 칸(8, 6, 3)을 주황 테두리로 묶고 위에 "엄격한 내림차순 런", 마지막 세 칸(4, 7, 7)을 초록 테두리로 묶고 위에 "오름차순 런". 2단의 왼쪽 라벨은 "2. 내림차순 런 뒤집기". 칸의 숫자는 1, 2, 5, 9, 3, 6, 8, 4, 7, 7. 가운데 세 칸(3, 6, 8) 위에 좌우로 뒤집는 것을 나타내는 주황색 양방향 곡선 화살표. 세 묶음의 테두리 색은 1단과 같다. 3단의 왼쪽 라벨은 "3. 런끼리 병합". 칸의 숫자는 1, 2, 3, 4, 5, 6, 7, 7, 8, 9이고 전체를 하나의 회색 테두리로 묶는다. 2단의 세 묶음에서 3단으로 모이는 가는 화살표 세 개. 3단의 두 7 칸 아래에 작은 글씨 "같은 값은 원래 순서 그대로". 차분한 파랑·초록·회색, 강조는 주황. 평면적인 기술 도해 스타일. TimSort는 입력에 이미 있는 정렬된 구간을 찾아 그대로 쓰고, 그 구간들을 병합해 전체를 완성한다. 입력이 정렬되어 있을수록 할 일이 줄어든다.

    적응적이라는 말을 숫자로 확인하기

    비교자 안에서 호출 횟수를 세면 정렬이 비교를 몇 번 했는지 알 수 있다. 원소 1,000개를 세 가지 상태로 준비해 정렬해 보자.

    import java.util.Arrays;
import java.util.Collections;
import java.util.Random;

public class CountMain {
    static int countComparisons(Integer[] arr) {
        int[] count = {0};
        Arrays.sort(arr, (x, y) -> {
            count[0]++;
            return Integer.compare(x, y);
        });
        return count[0];
    }

    static Integer[] ascending(int n) {
        Integer[] arr = new Integer[n];
        for (int i = 0; i < n; i++) {
            arr[i] = i;
        }
        return arr;
    }

    public static void main(String[] args) {
        Integer[] sorted = ascending(1000);

        Integer[] reversed = ascending(1000);
        Collections.reverse(Arrays.asList(reversed));      // 배열을 감싼 리스트를 뒤집는다

        Integer[] shuffled = ascending(1000);
        Collections.shuffle(Arrays.asList(shuffled), new Random(42));

        System.out.println("정렬된 입력: " + countComparisons(sorted));
        System.out.println("역순 입력: " + countComparisons(reversed));
        System.out.println("섞인 입력: " + countComparisons(shuffled));
    }
}
    정렬된 입력: 999
역순 입력: 999
섞인 입력: 8688

    이미 정렬된 입력은 비교 999번으로 끝난다. 런을 찾으면서 이웃한 원소를 한 번씩 견줬더니 배열 전체가 런 하나였고, 병합할 것이 없었다. 역순 입력도 999번이다. 전체가 엄격한 내림차순 런 하나라서 찾은 뒤 뒤집기만 하면 된다. Javadoc의 "거의 정렬된 입력이면 대략 n번의 비교"라는 설명과 맞는다.

    섞인 입력의 8,688이라는 값은 이 JDK 버전과 시드 42에서 나온 것이고, 섞는 방법이 달라지면 값도 달라진다. 크기를 가늠할 기준은 있다. 원소 n개를 늘어놓는 방법은 n!가지이고, 비교 한 번은 그 가짓수를 많아야 절반으로 줄인다. 그러므로 어떤 비교 기반 정렬도 최악의 경우 log₂(n!)번보다 적은 비교로는 끝낼 수 없다. n = 1000이면 이 값은 약 8,529다. 섞인 입력에서 TimSort가 쓴 비교 횟수는 이 한계에서 멀지 않다. 정렬된 입력에서는 그 한계의 8분의 1도 쓰지 않았다. 입력의 순서가 이미 갖고 있는 정보를 버리지 않고 쓴 결과다.

    정렬 컬렉션은 equals를 묻지 않는다

    8회와 9회에서 본 TreeSet과 TreeMap은 원소를 넣을 때마다 트리를 타고 내려가며 자리를 찾는다. 내려가는 방향을 정하는 것이 비교다. 비교 결과가 음수면 왼쪽, 양수면 오른쪽으로 가고, 0이면 "이미 있는 원소"로 판단하고 멈춘다. 이 과정 어디에도 equals나 hashCode는 등장하지 않는다. 정렬 컬렉션에서 "같다"의 기준은 비교 결과가 0인가이다.

    import java.math.BigDecimal;
import java.util.Comparator;
import java.util.HashSet;
import java.util.Set;

public class SortedSetMain {

        Comparator byLength = Comparator.comparing(s -> s.length());

        Set names = new TreeSet<>(byLength);
        names.add("kiwi");
        names.add("plum");
        names.add("fig");
        names.add("pear");

        BigDecimal q = new BigDecimal("1.00");
        System.out.println(p.equals(q) + " " + p.compareTo(q));

        Set hashSet = new HashSet<>();
        hashSet.add(p);
        hashSet.add(q);
        Set treeSet = new TreeSet<>();
        treeSet.add(p);
        treeSet.add(q);
        System.out.println(hashSet.size() + " " + treeSet.size());
    }

    길이로만 비교하는 비교자를 준 TreeSet에는 네 개를 넣었는데 두 개만 남았다. "plum"과 "pear"는 "kiwi"와 길이가 같아 비교 결과가 0이었고, 집합은 이미 있는 원소라고 판단해 넣지 않았다. 넣은 적도 없는 "lime"을 갖고 있다고 답하는 것도 같은 이유다. 집합은 문서대로 동작했다. 기대와 달랐던 것은 우리가 준 "같다"의 정의다.

    아래 두 줄은 표준 라이브러리 안에 있는 사례다. BigDecimal의 equals는 값과 소수 자릿수가 모두 같아야 참이고, compareTo는 수로서의 크기만 본다. 그래서 1.0과 1.00은 equals로는 다르고 compareTo로는 같다. HashSet은 hashCode와 equals로 판단하므로 둘을 다른 원소로 보고, TreeSet은 compareTo로 판단하므로 같은 원소로 본다. Comparable의 Javadoc이 equals와 일관되지 않은 자연 순서의 예로 직접 드는 클래스가 BigDecimal이다.

    컬렉션이 원소의 어떤 메서드에 의지하는지를 한 표로 모으면 이 권의 6회부터 이어진 이야기가 정리된다.

    컬렉션 또는 연산원소에게 묻는 것"같다"의 기준
    ArrayList·LinkedList의 contains, indexOf, remove(Object)equalsequals가 참
    HashSet, HashMap, LinkedHashSet, LinkedHashMaphashCode로 버킷을 고르고 equals로 확인해시가 같고 equals가 참
    TreeSet, TreeMapcompareTo 또는 생성자에 준 비교자의 compare비교 결과가 0
    Arrays.sort, List.sort, Collections.maxcompareTo 또는 넘겨준 비교자의 compare(순서만 정한다. 0이면 원래 순서 유지)

    여기서 실무 규칙이 나온다. 정렬만 할 때는 비교자가 필드 일부만 봐도 괜찮다. 동순위가 생길 뿐이고, 안정 정렬이 원래 순서를 지켜 준다. 그러나 그 비교자를 TreeSet이나 TreeMap에 주면 동순위가 곧 중복이 되어 원소가 사라진다. 정렬 컬렉션에 쓸 비교자는 서로 다른 원소에 대해 0을 돌려주지 않도록, thenComparing으로 식별자 같은 유일한 값을 마지막 기준에 덧붙여 둔다. 그리고 Comparable을 구현하지 않은 클래스를 비교자 없이 TreeSet에 넣으면 첫 번째 add에서 곧바로 ClassCastException이 난다. 배열 정렬에서 본 것과 같은 캐스트 실패다.

    컬렉션 유틸 — Collections, Arrays, 수정할 수 없는 컬렉션

    정렬이 ArrayList만의 일이 아니라 Arrays.sort 한 곳으로 모이는 것을 앞에서 봤다. 저장 방식과 상관없이 할 수 있는 일은 구현체마다 따로 만들 이유가 없다. 원소를 차례로 받을 수 있고 둘을 견줄 수 있으면 최댓값을 찾을 수 있고, 인덱스로 읽고 쓸 수 있으면 뒤집거나 섞을 수 있다. 자바는 이런 알고리즘을 java.util.Collections와 java.util.Arrays 두 클래스의 static 메서드로 모아 두었다. 인스턴스를 만들지 않고 쓰는 도구 상자다. 이름 끝에 s가 붙은 Collections는 클래스이고 s가 없는 Collection은 인터페이스라는 점만 헷갈리지 않으면 된다.

    import java.util.*;

public class UtilMain {

    첫 세 줄은 최댓값과 최솟값이다. 셋째 줄에서 역순 비교자를 주고 max를 불렀더니 10이 나왔다. max가 찾는 것은 "가장 큰 수"가 아니라 "주어진 순서에서 가장 뒤에 오는 원소"이기 때문이다. 역순에서는 10이 맨 뒤다. 소스를 보면 이 회차의 두 주제가 그대로 합쳐져 있다.

    public static > T max(Collection coll) {
    Iterator i = coll.iterator();
    T candidate = i.next();

    while (i.hasNext()) {
        T next = i.next();
        if (next.compareTo(candidate) > 0)
            candidate = next;
    }
    return candidate;
}

    반복자를 얻어 첫 원소를 후보로 잡고, 나머지를 하나씩 받아 후보와 견준다. 원소가 n개면 비교는 n−1번이다. 인덱스를 쓰지 않으므로 리스트든 집합이든 큐든 Collection이면 받는다. 빈 컬렉션을 넘기면 첫 i.next()에서 NoSuchElementException이 난다. 반복자의 규칙이 "돌려줄 원소가 없으면 예외"였기 때문에 비어 있는지 따로 검사하는 코드가 없어도 된다.

    선언부에는 이 권 앞부분에서 배운 제네릭 장치가 셋 들어 있다. 매개변수의 Collection는 원소를 꺼내 읽기만 하므로 상한 와일드카드다. Comparable는 정렬 1에서 본 그대로다. 남은 것은 T extends Object & Comparable의 Object &인데, 타입 검사만 놓고 보면 있으나 없으나 같다. 이것이 바꾸는 것은 클래스 파일이다. 2회에서 다룬 타입 소거 규칙(JLS §4.6)에 따르면 타입 변수는 가장 왼쪽 제한으로 소거된다. 맨 왼쪽에 Object를 두었으므로 반환 타입은 Object로 소거되고, javap -s가 보여 주는 이 메서드의 서술자는 (Ljava/util/Collection;)Ljava/lang/Object;다. Object &가 없었다면 반환 타입 자리는 Ljava/lang/Comparable;이 된다. 제네릭이 들어오기 전의 max는 Object를 돌려주는 메서드였고, 그 시절에 컴파일된 클래스 파일은 그 서술자로 메서드를 찾는다. 단어 하나가 서술자를 예전 그대로 붙들어 두는 것이다.

    reverse와 swap은 새 리스트를 만들지 않고 넘겨받은 리스트의 칸을 바꾼다. Collections.sort(list)는 앞에서 본 대로 list.sort(null)을 부르는 한 줄이다. shuffle은 원소를 무작위로 섞는다. 예제처럼 시드를 정한 Random을 넘기면 같은 JDK에서는 실행할 때마다 같은 순서가 나오고, 인자 없이 부르면 실행마다 달라진다. 테스트에서 "무작위이지만 재현되는 입력"이 필요할 때 시드를 넘긴다. frequency는 컬렉션을 for-each로 돌며 equals가 참인 원소를 센다. 리스트의 contains와 같은 기준이다.

    이진 탐색이 믿는 것

    binarySearch는 정렬된 리스트에서 원소의 인덱스를 찾는다. 가운데 원소와 견줘 찾는 값이 더 뒤면 왼쪽 절반을, 더 앞이면 오른쪽 절반을 버리는 일을 되풀이하므로 비교 횟수가 O(log n)이다. 인덱스로 접근하는 쪽의 본문은 다음과 같다.

    int low = 0;
int high = list.size()-1;

    else if (cmp > 0)

    정렬된 [10, 20, 30, 40, 50]에서 35를 찾는 과정을 따라가 보자. 처음에 low = 0, high = 4이고 mid = 2다. 30은 35보다 앞이므로 low = 3이 된다. 다음 mid는 3이고, 40은 35보다 뒤이므로 high = 2가 된다. low가 high를 넘었으니 반복이 끝나고 -(3 + 1), 곧 −4를 돌려준다. 못 찾았을 때의 반환값은 "그 값을 넣는다면 들어갈 인덱스"를 음수로 접은 것이다. 3을 그냥 −3으로 돌려주지 않고 1을 더 빼는 이유는 삽입 위치가 0일 때 때문이다. −0은 0이라서 "0번 칸에서 찾았다"와 구별할 수 없다.

    mid를 구하는 식이 (low + high) / 2가 아니라 >>> 1인 것도 이유가 있다. 리스트가 아주 크면 low + high가 int 범위를 넘어 음수가 될 수 있다. 부호 없는 오른쪽 시프트는 그 비트들을 부호 없는 수로 보고 반으로 나누므로 올바른 가운데 인덱스가 나온다. 뺄셈 비교자와 같은 종류의 오버플로를 피한 것이다.

    예제의 넷째 줄은 정렬하기 전에 10을 찾은 결과다. 리스트 [40, 10, 30, 20, 50]에 10이 분명히 들어 있는데 −1이 나왔다. 추적하면 이렇다. mid = 2의 30이 10보다 뒤이므로 high = 1, 다음 mid = 0의 40도 10보다 뒤이므로 high = -1, 반복이 끝나고 -(0 + 1)이다. 알고리즘은 "30이 10보다 뒤이니 30의 오른쪽에는 10이 없다"고 추론해 절반을 버렸다. 그 추론은 리스트가 정렬되어 있을 때만 옳다. Javadoc은 정렬되어 있지 않으면 결과가 정의되지 않는다고 적는다. 예외로 알려 주지 않는다. 정렬 알고리즘이 비교 규약을 믿고 일부 쌍만 비교하는 것과 같은 구조다. 빠른 알고리즘은 입력에 대한 전제를 믿기 때문에 빠르고, 전제가 깨지면 조용히 틀린다.

    이 메서드는 리스트의 종류도 가린다. 소스의 첫 줄이 if (list instanceof RandomAccess || list.size() < BINARYSEARCH_THRESHOLD)이고 상수의 값은 5000이다. RandomAccess는 5회에서 본, 메서드가 하나도 없는 표시용 인터페이스다. ArrayList는 이것을 구현하고 LinkedList는 구현하지 않는다. 표시가 없는 큰 리스트에는 get(mid)를 쓰지 않고 반복자를 앞뒤로 움직여 가운데로 가는 방식을 쓴다. Javadoc의 표현으로 이때의 비용은 노드 건너기 O(n)번, 원소 비교 O(log n)번이다. 연결 리스트에서는 이진 탐색을 해도 걷는 비용이 남는다는 것, 그리고 순회 방식이 시간 복잡도를 정한다는 것을 라이브러리 코드가 스스로 알고 대응하는 것이다.

    Arrays.asList — 배열 위에 씌운 리스트

    Arrays는 배열을 위한 도구 상자다. 배열 타입에는 메서드를 덧붙일 수 없고, toString()과 equals()도 Object에서 물려받은 그대로다. 그래서 내용을 문자열로 만드는 Arrays.toString, 내용을 비교하는 Arrays.equals, 정렬하는 Arrays.sort, 정렬된 배열에서 찾는 Arrays.binarySearch가 바깥에 따로 있다. 이 가운데 컬렉션으로 건너가는 다리가 Arrays.asList다.

    import java.util.Arrays;
import java.util.List;

public class ViewMain {
    public static void main(String[] args) {
        String[] arr = {"x", "y", "z"};
        List asList = Arrays.asList(arr);

        asList.set(0, "X");                 // 리스트에 쓰면
        System.out.println(arr[0]);         // 배열이 바뀌어 있다
        arr[1] = "Y";                       // 배열에 쓰면
        System.out.println(asList);         // 리스트에서도 보인다
        System.out.println(asList.getClass().getName());

        try {
            asList.add("w");
        } catch (UnsupportedOperationException e) {
            System.out.println("add 실패: " + e);
        }

        int[] prim = {1, 2, 3};
        System.out.println(Arrays.asList(prim).size());
    }
}

    리스트에 쓴 것이 배열에 보이고 배열에 쓴 것이 리스트에 보인다. asList가 돌려준 객체는 원소를 복사해 갖고 있지 않다. 넘겨받은 배열의 참조를 필드 하나에 들고, get(i)는 그 배열의 i번 칸을 읽고 set(i, v)는 그 칸에 쓴다. 이렇게 자기 저장소 없이 다른 것의 내용을 다른 모양으로 보여 주는 객체를 뷰(view)라고 한다. 9회에서 본 keySet()이 맵의 뷰였던 것과 같다. 정렬 3의 비교 횟수 예제에서 Collections.reverse(Arrays.asList(reversed)) 한 줄로 배열 자체를 뒤집을 수 있었던 것도 이 때문이다.

    클래스 이름이 java.util.Arrays$ArrayList인 것에 주의하자. 우리가 아는 java.util.ArrayList가 아니라 Arrays 안에 중첩된 다른 클래스다. 이 클래스는 배열을 감쌀 뿐이고 배열의 길이는 바꿀 수 없으므로, 리스트의 크기도 바꿀 수 없다. add를 따로 구현하지 않았고, 상위 클래스 AbstractList의 add(int, E)는 본문이 throw new UnsupportedOperationException(); 한 줄이다. 값을 바꿀 수는 있지만 넣거나 뺄 수는 없는, 크기가 고정된 리스트다.

    마지막 줄의 1은 자주 걸리는 함정이다. asList의 선언은 static List asList(T... a)이고, 1회에서 본 대로 타입 인자는 참조 타입이어야 한다. int[]를 넘기면 T가 int일 수 없으므로 컴파일러는 T를 int[]로 추론한다. 결과는 배열 하나를 원소로 가진 List다. Integer[]를 넘겨야 원소 셋짜리 리스트가 된다.

    수정할 수 없는 컬렉션: 팩토리, 뷰, 사본

    자바 9에서 List.of, Set.of, Map.of가 들어왔다. 이 메서드들이 돌려주는 컬렉션은 수정할 수 없다(unmodifiable). 넣기, 빼기, 바꾸기, 정렬처럼 내용을 바꾸는 메서드를 부르면 언제나 UnsupportedOperationException이 난다. "수정할 수 없음"을 만드는 방법은 Collections.unmodifiableList와 List.copyOf(자바 10)까지 셋인데, 메모리에서 벌어지는 일이 서로 다르다.

    import java.util.ArrayList;
import java.util.Collections;
import java.util.List;

public class CopyMain {
    public static void main(String[] args) {
        List fixed = List.of("A", "B", "C");
        try {
            fixed.add("D");
        } catch (UnsupportedOperationException e) {
            System.out.println("add 실패: " + e);
        }
        System.out.println(List.of("A", "B").getClass().getName());
        System.out.println(fixed.getClass().getName());

        List source = new ArrayList<>(List.of("A", "B"));
        List view = Collections.unmodifiableList(source);   // 뷰
        List copy = List.copyOf(source);                    // 사본

        source.add("C");                    // 원본을 바꾸면
        System.out.println(view);           // 뷰에는 보인다
        System.out.println(copy);           // 사본에는 보이지 않는다
        System.out.println(List.copyOf(copy) == copy);
    }
}

    둘째, 셋째 줄이 팩토리가 만든 리스트의 속을 보여 준다. 원소가 둘인 리스트의 실제 클래스는 List12이고 셋인 리스트는 ListN이다. OpenJDK 21의 List12는 배열 없이 필드 e0, e1에 원소의 참조를 직접 담고, ListN은 원소 수에 딱 맞는 배열 하나를 갖는다. 바뀔 일이 없으니 3회에서 본 여유 용량도, 순회 중 수정을 감시하는 modCount도 필요 없다. Set.of가 만드는 SetN도 같은 발상이다. 6회와 7회의 해시 테이블처럼 버킷마다 노드를 매다는 대신, 원소 수의 두 배 길이인 배열 하나에 원소의 참조를 직접 넣는다. 해시 값을 배열 길이로 나눈 나머지 칸에서 시작해, 그 칸이 차 있으면 빈칸이 나올 때까지 다음 칸으로 간다. 원소마다 노드 객체를 만들지 않아도 되고, 삭제와 리사이즈가 없으니 이 단순한 방식으로 충분하다.

    이 팩토리들은 입력에도 엄격하다. null을 원소로 주면 NullPointerException이 나고, Set.of("a", "a")처럼 중복을 주면 IllegalArgumentException: duplicate element: a가 난다. 조용히 하나를 버리지 않고, 집합을 만들겠다면서 같은 것을 두 번 적은 것을 실수로 보고 멈춘다. 그리고 Set.of로 만든 집합의 순회 순서는 실행할 때마다 달라질 수 있다. Set.of("a", "b", "c", "d", "e")를 출력하는 프로그램을 두 번 돌렸더니 한 번은 [e, d, c, b, a], 한 번은 [d, e, a, b, c]가 나왔다. 구현이 JVM이 뜰 때 정해지는 값으로 순회의 시작 칸과 방향을 고르기 때문이다. Javadoc도 이 순서가 정해져 있지 않고 바뀔 수 있다고 적는다. 해시 구조의 순회 순서에 기댄 코드는 이 집합 앞에서 금방 드러난다.

    넷째와 다섯째 줄이 뷰와 사본의 차이다. Collections.unmodifiableList(source)는 원본을 가리키는 참조 하나를 가진 래퍼(wrapper) 객체를 만든다. 읽는 메서드는 원본에 그대로 넘기고, 쓰는 메서드는 예외를 던진다. 원소를 복사하지 않으므로 만드는 비용이 O(1)이지만, 원본을 쥔 쪽이 원본을 바꾸면 뷰를 통해 그대로 보인다. "이 참조로는 못 바꾼다"는 것이지 "바뀌지 않는다"가 아니다. List.copyOf(source)는 그 시점의 원소를 새 저장소로 옮겨 담는다. O(n)이 들지만 그 뒤로는 원본과 무관하다. 마지막 줄의 true는 덤이다. OpenJDK 21에서 이미 수정할 수 없는 리스트를 copyOf에 넘기면 복사하지 않고 그 객체를 그대로 돌려준다. 바뀔 수 없는 것은 공유해도 안전하다는, 중급 1편의 불변 객체에서 본 논리다.

    이 차이는 객체의 경계에서 중요해진다. 생성자가 받은 리스트를 필드에 그대로 저장하면, 호출한 쪽이 나중에 그 리스트를 바꿔 객체의 내부 상태를 흔들 수 있다. 받을 때 List.copyOf로 끊어 두면 그럴 수 없다. 반대로 내부 리스트를 밖으로 내줄 때 Collections.unmodifiableList로 감싼 뷰를 주면 복사 비용 없이 바깥의 수정을 막는다. 다만 어느 쪽이든 막는 것은 컬렉션의 칸까지다. 칸이 가리키는 원소 객체가 가변이면 그 객체의 필드는 여전히 바뀔 수 있다. List의 Javadoc도 원소가 가변이면 리스트의 내용이 바뀐 것처럼 보일 수 있다고 적는다.

    수정 금지가 실행 시점에야 드러난다는 점도 짚어 둔다. List.of가 돌려주는 값의 타입은 그냥 List이고, 그 인터페이스에는 add가 있다. 그래서 fixed.add("D")는 컴파일된다. 자바의 컬렉션 인터페이스는 읽기 전용 타입을 따로 두지 않고, 수정 메서드를 선택적 연산(optional operation)으로 표시해 구현체가 UnsupportedOperationException으로 거부할 수 있게 했다. 타입만으로는 수정할 수 있는지 알 수 없으므로, 남에게서 받은 컬렉션을 고쳐야 한다면 new ArrayList<>(받은_리스트)로 내 사본을 만들어 고치는 것이 안전하다.

    Collections에는 빈 컬렉션과 래퍼를 만드는 메서드가 더 있다. Collections.emptyList()는 원소가 없는 수정 불가 리스트를 돌려주는데, 부를 때마다 같은 객체다(== 비교가 true다). 결과가 없을 때 null 대신 빈 컬렉션을 돌려줘도 객체가 새로 만들어지지 않는다. Collections.synchronizedList는 메서드마다 synchronized (mutex) { ... }로 원본 호출을 감싼 래퍼를 만든다. 메서드 하나하나는 한 번에 한 스레드만 실행하지만, 순회는 여러 번의 호출로 이뤄지므로 Javadoc은 순회할 때 사용자가 직접 그 리스트에 대해 동기화해야 한다고 요구한다. 그 이유는 고급 1편의 몫이다.

Map                             "키로 값을 찾는다"  (Collection이 아니다)
  ├─ HashMap                         해시 테이블
  │    └─ LinkedHashMap              해시 테이블 + 넣은 순서를 잇는 연결
  └─ SortedMap ─ NavigableMap
       └─ TreeMap                    레드-블랙 트리

    그림에서 읽을 것은 세 가지다. 첫째, 뿌리가 둘이다. 원소 하나하나를 담는 Collection 계열과 키-값 쌍을 담는 Map이 따로 서 있고, Iterable인 것은 Collection 쪽뿐이다. 맵은 keySet(), values(), entrySet()이라는 뷰를 통해 Collection의 세계로 건너온다. 둘째, 인터페이스는 "무엇을 할 수 있는가"를, 구현체는 "어떻게 저장하는가"를 맡는다. 같은 인터페이스 아래의 구현체는 약속이 같으므로 바꿔 끼울 수 있고, 바꾸면 달라지는 것은 비용과 순회 순서다. 셋째, 구현체의 이름이 곧 설명이다. ArrayList는 배열로 만든 리스트, HashSet은 해시로 만든 집합, TreeMap은 트리로 만든 맵, LinkedHashMap은 연결을 더한 해시 맵, ArrayDeque는 배열로 만든 덱이다.

    자바 21에서는 이 그림에 SequencedCollection, SequencedSet, SequencedMap이 더해졌다. "순회 순서가 정해져 있다"는 성질을 타입으로 드러낸 인터페이스다. List, Deque, LinkedHashSet, SortedSet이 SequencedCollection 아래에 놓이고, LinkedHashMap과 SortedMap이 SequencedMap 아래에 놓인다. 앞 회차들에서 언급한 getFirst(), getLast(), reversed()가 여기서 온다. 위 그림에서는 줄기를 단순하게 보이려고 뺐다.

    구현체마다 속 구조가 정하는 성질을 표로 모으면 다음과 같다. 비용은 각 클래스의 Javadoc과 앞 회차에서 본 구조에서 나온 것이고, null 열은 직접 넣어 본 결과다.

    구현체내부 구조순회 순서주요 연산의 비용원소(키)에게 요구하는 것null

    LinkedList이중 연결 노드인덱스 순양 끝 추가·삭제 O(1), get(i) O(n), contains O(n)equals(찾을 때)허용
    HashSet / HashMap버킷 배열 + 노드(긴 버킷은 트리)정해져 있지 않다추가·조회·삭제 평균 O(1)(해시가 고르게 퍼질 때)hashCode, equals허용(원소 하나 / 키 하나)
    LinkedHashSet / LinkedHashMap해시 테이블 + 노드를 잇는 이중 연결넣은 순서(맵은 접근 순서로도 설정 가능)평균 O(1)hashCode, equals허용

    null 열에도 원리가 있다. 자연 순서를 쓰는 TreeSet은 null을 받지 않는다. null에게는 compareTo를 물을 수 없고, 비교할 수 없는 것은 정렬 구조에 자리가 없다. ArrayDeque와 PriorityQueue가 null을 거부하는 이유는 다르다. Queue와 Deque의 Javadoc이 밝히듯 poll()이나 peek() 같은 메서드가 "비어 있다"는 뜻으로 null을 돌려주기 때문이다. 원소로 null을 허용하면 꺼낸 null이 원소인지 신호인지 가릴 수 없다.

    구현체를 고를 때는 성능표부터 보지 않는다. 요구 조건을 차례로 물으면 후보가 좁혀진다.

    특별한 요구가 없을 때의 기본값은 ArrayList, HashSet, HashMap, ArrayDeque다. 앞의 셋은 배열 위에서 인덱스나 해시로 위치를 계산해 바로 가는 구조이고, ArrayDeque는 Javadoc 스스로 스택으로 쓸 때는 Stack보다, 큐로 쓸 때는 LinkedList보다 빠를 가능성이 높다고 적고 있다. 그리고 변수와 매개변수의 타입은 List, Set, Map 같은 인터페이스로 선언한다. 구현체의 이름은 new 하는 한 곳에만 나오게 해 두면, 요구가 바뀌었을 때 고칠 곳도 그 한 곳이다.

    이 권 전체의 핵심

    컬렉션의 성질은 외워야 할 표가 아니라 속 구조에서 따라 나오는 결과다. 배열은 위치를 계산해 바로 가지만 중간에 끼워 넣으려면 밀어야 한다. 노드는 끼워 넣기는 쉽지만 찾아가려면 걸어야 한다. 해시는 값에서 위치를 계산하므로 빠르지만 순서를 잃고 equals·hashCode의 약속에 기댄다. 트리는 비교로 자리를 찾으므로 순서를 유지하지만 비교의 규약에 기댄다. 그 위에 제네릭이 타입을, 인터페이스가 구현을, 반복자가 순회 방식을 감춘다.

    Collection 계열과 Map 계열이라는 두 뿌리, 그 아래 인터페이스, 그리고 구현체마다 내부 구조가 무엇인지를 작은 아이콘으로 구별해 보여 준다. 흰 배경의 구조도. 화면을 좌우 두 영역으로 나눈다. 왼쪽 영역(전체 폭의 약 3분의 2)의 맨 위에 둥근 상자 "Iterable", 그 아래에 화살표로 이어진 상자 "Collection". Collection 아래로 세 갈래가 내려간다. 첫째 갈래의 상자는 "List"이고 그 아래에 구현체 카드 두 장 "ArrayList", "LinkedList". 둘째 갈래의 상자는 "Set"이고 그 아래에 카드 세 장 "HashSet", "LinkedHashSet", "TreeSet". 셋째 갈래의 상자는 "Queue · Deque"이고 그 아래에 카드 두 장 "ArrayDeque", "PriorityQueue". 오른쪽 영역의 맨 위에는 따로 떨어진 둥근 상자 "Map"이 있고 그 아래에 카드 세 장 "HashMap", "LinkedHashMap", "TreeMap". Map 상자에서 왼쪽의 Collection 상자로 가는 회색 점선 화살표가 하나 있고 라벨은 "keySet · values · entrySet". 인터페이스 상자는 옅은 파란색, 구현체 카드는 흰색에 회색 테두리. 각 구현체 카드의 오른쪽 아래 구석에 내부 구조를 나타내는 작은 아이콘을 그린다: ArrayList와 ArrayDeque에는 가로로 이어진 네모 칸들, LinkedList에는 화살표로 이어진 동그라미들, HashSet과 HashMap에는 세로 칸 배열에서 옆으로 매달린 작은 동그라미들, LinkedHashSet과 LinkedHashMap에는 같은 그림에 동그라미들을 잇는 주황색 선, TreeSet과 TreeMap에는 작은 이진 트리, PriorityQueue에는 삼각형 모양의 힙. 화면 맨 아래에 범례 한 줄: 네모 칸 아이콘 옆에 "배열", 이어진 동그라미 옆에 "연결 노드", 매달린 동그라미 옆에 "해시 테이블", 이진 트리 옆에 "레드-블랙 트리". 차분한 파랑과 회색, 강조는 주황. 평면적인 기술 도해 스타일. 인터페이스는 무엇을 할 수 있는지를, 구현체는 어떻게 저장하는지를 정한다. 구현체의 성질은 카드 구석의 내부 구조에서 나온다.
