    리스트와 셋이 답하지 못하는 질문

    프로그램이 데이터에 던지는 질문 가운데 가장 흔한 것은 "이것에 딸린 저것은 무엇인가"다. 상품 코드에 딸린 재고 수량, 회원 아이디에 딸린 회원 정보, 단어에 딸린 등장 횟수가 모두 이 꼴이다. 지금까지 배운 두 자료 구조는 이 질문에 잘 맞지 않는다.

    리스트는 "몇 번째 요소인가"에만 빠르게 답한다. 03회에서 본 대로 배열 리스트의 인덱스 조회가 O(1)인 것은 인덱스가 0부터 빈틈없이 이어지는 정수여서 위치를 계산할 수 있기 때문이다. 찾는 기준이 "apple" 같은 문자열이면 계산할 위치가 없다. 코드와 수량을 묶은 객체를 리스트에 넣어 두고 처음부터 하나씩 비교하는 수밖에 없고, 이 탐색은 O(n)이다.

    셋은 06~08회에서 해시를 이용해 "이 값이 들어 있는가"를 평균 O(1)에 답하도록 만들었다. 하지만 셋이 돌려주는 답은 있다와 없다 둘뿐이다. 코드만으로 동등성을 판단하는 객체를 셋에 넣으면 포함 여부는 알 수 있어도, 그 안에 저장된 객체를 꺼내 수량을 읽는 연산은 Set 인터페이스에 없다.

    필요한 것은 셋의 빠른 탐색에 "찾은 자리에 딸려 있는 것을 돌려준다"는 기능 하나를 더한 구조다. 찾는 기준을 키(key), 딸린 데이터를 값(value)이라 하고, 키 하나와 값 하나를 묶은 쌍을 엔트리(entry)라 한다. 이 대응 관계 전체를 관리하는 자료 구조가 맵(Map)이다. 수학에서 한 집합의 원소를 다른 집합의 원소에 대응시키는 일을 사상(mapping)이라 부르는 데서 온 이름이고, 다른 언어에서는 딕셔너리(dictionary)나 연관 배열(associative array)이라고도 부른다.

    이 회차의 뒤쪽 절반은 성격이 다른 질문을 다룬다. "무엇이 들어 있는가"가 아니라 "다음에 무엇을 꺼낼 것인가"다. 꺼내는 순서를 규칙으로 못 박은 자료 구조가 스택(stack)과 큐(queue)이고, 둘을 하나로 합친 것이 덱(deque)이다. 한 회차에 묶여 있지만 Map과는 원리가 다르므로 따로 바닥부터 본다.

    일상에서 가져온 비유표제어와 뜻풀이

    국어사전은 표제어를 주면 뜻풀이를 돌려준다. 같은 표제어가 두 번 실리지 않고, 서로 다른 표제어가 같은 뜻풀이를 가질 수는 있다. Map의 키와 값이 정확히 이 관계다. 비유가 깨지는 지점은 찾는 방법이다. 종이 사전은 표제어가 가나다순으로 정렬되어 있어서 찾을 수 있지만, 가장 많이 쓰는 HashMap은 키를 정렬하지 않고 해시 값으로 위치를 계산한다. 종이 사전에 가까운 것은 키를 정렬해 두는 TreeMap이다.

    Map 소개 1 — 키와 값, 그리고 반환값이 알려 주는 것

    java.util.Map은 타입 매개변수가 둘인 인터페이스다. Map에서 K는 키의 타입, V는 값의 타입이다. Java SE 21 API 문서는 Map을 "키를 값에 대응시키는 객체"라고 정의하고, 중복된 키를 가질 수 없으며 키 하나는 많아야 값 하나에 대응한다고 적는다. 기본 연산부터 실행해 보자.

    import java.util.HashMap;
import java.util.Map;

public class MapBasicsMain {
    public static void main(String[] args) {
        Map stock = new HashMap<>();
        System.out.println(stock.put("apple", 10));     // null
        System.out.println(stock.put("pear", 5));       // null
        System.out.println(stock.put("apple", 7));      // 10
        System.out.println(stock.get("apple"));         // 7
        System.out.println(stock.get("plum"));          // null
        System.out.println(stock.containsKey("plum"));  // false
        System.out.println(stock.size());               // 2
        System.out.println(stock);                      // {apple=7, pear=5}

        stock.put("plum", null);
        System.out.println(stock.get("plum"));          // null
        System.out.println(stock.containsKey("plum"));  // true
        System.out.println(stock.remove("plum"));       // null
        System.out.println(stock.containsKey("plum"));  // false
    }
}

    주석에 적은 값이 OpenJDK 21에서 실행한 실제 출력이다. 여기서 읽어 낼 것이 세 가지 있다.

    첫째, put은 값을 돌려준다. 그 키에 이전에 대응되어 있던 값이다. 처음 넣는 키라면 이전 값이 없으므로 null이 나오고, "apple"을 두 번째로 넣을 때는 밀려난 값 10이 나온다. 같은 키로 다시 넣으면 엔트리가 하나 더 생기는 것이 아니라 값이 교체되므로 size()는 2에 머문다. 리스트의 add와 달리 Map의 put은 "추가 또는 교체"다.

    둘째, get이 돌려주는 null에는 두 가지 뜻이 섞여 있다. "plum"이라는 키가 아예 없을 때도 null이고, 키는 있는데 값으로 null을 넣어 두었을 때도 null이다. 둘을 가르는 것은 containsKey다. put과 remove의 반환값도 같은 모호함을 갖는다. API 문서는 put의 반환값 설명에 null이 "이전에 null이 대응되어 있었다"는 뜻일 수도 있다고 따로 적어 두었다. 이 모호함을 피하는 가장 간단한 방법은 값으로 null을 넣지 않는 것이다.

    셋째, 출력 순서다. {apple=7, pear=5}는 넣은 순서와 같아 보이지만 우연이다. HashMap의 API 문서는 순서를 보장하지 않으며 시간이 지나도 순서가 유지된다는 보장조차 없다고 적는다. 왜 그런지는 내부 구조를 본 뒤에 분명해진다.

    Map은 Collection이 아니다

    리스트와 셋은 모두 Collection의 하위 타입이었다. Map은 그렇지 않다. Map는 Collection도 Iterable도 상속하지 않는 독립된 인터페이스다. Collection는 요소 하나를 다루는 계약(add(E), contains(Object))인데 Map의 단위는 키와 값의 쌍이어서 그 계약에 들어맞지 않기 때문이다. 그래서 Map을 향상된 for문에 직접 넣을 수 없다. 순회하려면 다음 절에서 볼 뷰를 거친다.

    바이트코드로 본 put과 get

    제네릭 타입 인자는 컴파일 뒤에 지워진다는 것을 02회에서 보았다. Map도 예외가 아니다. 아래 메서드를 컴파일하고 javap -c로 열어 보면 타입 소거가 남긴 흔적이 그대로 보인다.

    이 바이트코드에서 함정 두 개가 바로 나온다. 하나는 언박싱이다. 없는 키를 int v = m.get("missing");처럼 기본형으로 받으면 get이 돌려준 null에 intValue()를 호출하게 되어 NullPointerException이 난다. JDK 21의 예외 메시지는 Cannot invoke "java.lang.Integer.intValue()" because the return value of "java.util.Map.get(Object)" is null이다. 다른 하나는 get의 매개변수 타입이다. get은 소스 수준에서도 K가 아니라 Object를 받는다. 그래서 Map에 put(1L, "kim")을 해 두고 get(1)을 호출해도 컴파일 오류가 나지 않는다. 인자 1은 Integer로 박싱되고, Integer와 Long은 값이 같아도 equals가 false이므로 결과는 null이다. 키의 타입이 맞는지는 컴파일러가 아니라 작성자가 챙겨야 한다.

    Map을 바라보는 세 개의 창 — keySet, values, entrySet

    Map이 Collection이 아니므로 그 내용을 컬렉션처럼 다루려면 통로가 필요하다. API 문서는 이를 세 가지 컬렉션 뷰(collection view)라고 부른다. 키만 모아 보는 keySet(), 값만 모아 보는 values(), 키와 값의 쌍을 모아 보는 entrySet()이다. 반환 타입이 서로 다른 데에는 이유가 있다. 키는 중복이 없으므로 Set이고, 값은 중복될 수 있고 순서 개념도 없으므로 가장 느슨한 Collection이며, 엔트리는 키가 유일하니 쌍도 유일해서 Set>다.

    Map stock = new HashMap<>();
stock.put("apple", 7);
stock.put("pear", 5);
stock.put("fig", 3);

Set keys = stock.keySet();
Collection values = stock.values();
Set> entries = stock.entrySet();
System.out.println(keys + " " + values + " " + entries);
System.out.println(keys.getClass().getName());

keys.remove("pear");                       // 뷰에서 지운다
System.out.println(stock);
for (Map.Entry entry : entries) {
    entry.setValue(entry.getValue() * 2);  // 엔트리를 통해 값을 바꾼다
}
System.out.println(stock);
stock.put("kiwi", 1);                      // 원본에 넣는다
System.out.println(keys + " " + values);

    둘째 줄이 핵심이다. keySet()이 돌려준 객체의 클래스는 HashSet이 아니라 HashMap$KeySet, 곧 HashMap 안에 정의된 내부 클래스다. 이 객체는 키를 복사해 담고 있지 않다. 자기를 만든 맵을 가리키는 참조만 갖고 있다가, 누군가 순회를 요청하면 그때 맵의 테이블을 훑어 키를 하나씩 내준다. 그래서 뷰를 만드는 비용은 맵의 크기와 무관하고, 뷰와 원본은 언제나 같은 내용을 보여 준다.

    나머지 출력이 이것을 확인해 준다. 뷰에서 "pear"를 지웠더니 원본 맵에서 엔트리가 사라졌다. 엔트리의 setValue로 값을 바꿨더니 원본의 값이 바뀌었다. 뷰를 얻은 뒤에 원본에 "kiwi"를 넣었는데, 다시 얻지 않은 keys와 values에 그 내용이 나타난다. 반대로 keys.add("melon")은 UnsupportedOperationException을 던진다. 키만 주고 값을 주지 않으면 엔트리를 만들 수 없기 때문이다.

    HashMap에서 entrySet()이 내주는 Map.Entry 객체는 따로 만든 포장이 아니다. 뒤에서 볼 테이블의 노드 클래스가 Map.Entry를 구현하고 있어서, 순회는 내부 노드를 그대로 건네준다. setValue가 원본을 바꾸는 이유가 이것이다. 노드의 값 필드에 직접 대입하는 것이다.

    순회 방법을 고를 때 이 구조가 기준이 된다. 키와 값이 모두 필요한데 keySet()으로 키를 돌면서 매번 map.get(key)를 부르면, 순회가 이미 그 노드 위에 서 있는데도 키마다 해시를 계산하고 버킷을 찾는 탐색을 한 번씩 더 하게 된다. entrySet()을 돌면 노드에서 키와 값을 바로 읽는다. 순회 도중에 맵의 구조를 바꾸면 어떤 일이 생기는지, 향상된 for문이 실제로 무엇으로 번역되는지는 10회에서 다룬다.

    Map 소개 2 — 없으면 넣고, 있으면 고친다

    Map을 쓰는 코드의 상당수는 "키가 없으면 이렇게, 있으면 저렇게"라는 분기다. 이 분기를 get과 put만으로 쓰면 코드가 길어지고 탐색도 두 번 하게 된다. Map 인터페이스는 이런 조합을 한 번의 호출로 끝내는 메서드를 갖고 있다. 먼저 가장 단순한 둘을 보자.

    Map m = new HashMap<>();
System.out.println(m.putIfAbsent("a", 1));  // null  (없었으므로 넣었다)
System.out.println(m.putIfAbsent("a", 2));  // 1     (있었으므로 넣지 않았다)
System.out.println(m);                      // {a=1}
System.out.println(m.getOrDefault("z", 0)); // 0
System.out.println(m.containsKey("z"));     // false (getOrDefault는 넣지 않는다)

    putIfAbsent는 키가 없을 때만 넣고, 원래 있던 값(없었다면 null)을 돌려준다. 반환값이 null인지로 "내가 넣었는가"를 알 수 있다. getOrDefault는 키가 없을 때 null 대신 지정한 값을 돌려줄 뿐 맵을 바꾸지 않는다. 마지막 줄이 그것을 보여 준다.

    이제 단어 수 세기를 세 가지 방법으로 써 보자. 문장을 공백으로 잘라 단어마다 등장 횟수를 센다.

    String[] words = "to be or not to be".split(" ");

Map byGetPut = new HashMap<>();
for (String word : words) {
    Integer count = byGetPut.get(word);
    if (count == null) {
        byGetPut.put(word, 1);
    } else {
        byGetPut.put(word, count + 1);
    }
}

Map byDefault = new HashMap<>();
for (String word : words) {
    byDefault.put(word, byDefault.getOrDefault(word, 0) + 1);
}

Map byMerge = new HashMap<>();
for (String word : words) {
    byMerge.merge(word, 1, Integer::sum);
}

System.out.println(byGetPut);
System.out.println(byDefault);
System.out.println(byMerge);
    {not=1, be=2, or=1, to=2}
{not=1, be=2, or=1, to=2}
{not=1, or=1, be=2, to=2}

    merge(key, value, function)은 키가 없으면 value를 그대로 넣고, 있으면 기존 값과 value를 function에 넘겨 나온 결과로 교체한다. Integer::sum은 두 정수를 더하는 함수이므로 "없으면 1, 있으면 1을 더한 값"이 된다. 앞의 두 방법은 단어마다 get(또는 getOrDefault)과 put으로 탐색을 두 번 하지만 HashMap.merge는 버킷을 한 번만 찾아가 그 자리에서 값을 고친다.

    세 맵의 내용은 같은데 셋째 줄의 출력 순서가 다르다. be와 or의 자리가 바뀌었다. 오타가 아니다. 같은 키를 같은 순서로 넣었는데도 어떤 메서드로 넣었느냐에 따라 HashMap의 순회 순서가 달라진 것이다. 두 단어는 같은 버킷에 들어가는데, OpenJDK 21의 put은 새 노드를 버킷 체인의 꼬리에 붙이고 merge는 머리에 끼운다. "HashMap은 순서를 보장하지 않는다"는 문장이 실제로 무엇을 뜻하는지 보여 주는 사례다. 뒤에서 이 버킷을 직접 그려 본다.

    값이 컬렉션인 Map, 예를 들어 첫 글자별로 단어를 모으는 Map>에는 computeIfAbsent가 맞는다. 키가 없으면 함수를 실행해 만든 값을 넣고, 있으면 아무것도 하지 않으며, 어느 쪽이든 현재 대응된 값을 돌려준다.

    Map> byInitial = new HashMap<>();
for (String word : words) {
    byInitial.computeIfAbsent(word.charAt(0), key -> new ArrayList<>()).add(word);
}
System.out.println(byInitial);   // {b=[be, be], t=[to, to], n=[not], o=[or]}

    putIfAbsent(key, new ArrayList<>())로 써도 결과는 같지만 차이가 있다. putIfAbsent는 인자를 먼저 평가하므로 키가 이미 있어도 빈 리스트를 매번 만들었다가 버린다. computeIfAbsent는 키가 없을 때만 함수를 호출한다. 그리고 putIfAbsent는 새로 넣었을 때 null을 돌려주므로 위처럼 바로 .add를 이어 붙일 수 없다.

    이 메서드들이 "한 번의 호출"이라는 것은 코드가 짧고 탐색이 줄어든다는 뜻이지, 여러 스레드가 동시에 호출해도 안전하다는 뜻이 아니다. HashMap은 API 문서가 밝히듯 동기화되어 있지 않다. 여러 스레드가 함께 쓰는 맵은 동시성을 다루는 뒤의 권에서 본다.

    Map 구현체 — HashMap, LinkedHashMap, TreeMap

    Map은 인터페이스이고 실제 일을 하는 클래스는 따로 있다. 일반적인 용도로 쓰는 구현체는 셋이다. 같은 키 다섯 개를 같은 순서로 넣고 출력만 비교해 보자.

    String[] names = {"delta", "alpha", "charlie", "bravo", "echo"};
Map hash = new HashMap<>();
Map linked = new LinkedHashMap<>();
Map tree = new TreeMap<>();
for (int i = 0; i < names.length; i++) {
    hash.put(names[i], i);
    linked.put(names[i], i);
    tree.put(names[i], i);
}
System.out.println("HashMap       " + hash);
System.out.println("LinkedHashMap " + linked);
System.out.println("TreeMap       " + tree);

LinkedHashMap {delta=0, alpha=1, charlie=2, bravo=3, echo=4}
TreeMap       {alpha=1, bravo=3, charlie=2, delta=0, echo=4}

    Set은 값을 쓰지 않는 Map이다

    세 구현체의 이름이 HashSet, LinkedHashSet, TreeSet과 나란한 것은 우연이 아니다. OpenJDK 21의 HashSet 소스에서 뼈대만 남기면 이렇다.

    public class HashSet /* ... */ {
    transient HashMap map;
    static final Object PRESENT = new Object();

    public HashSet() {
        map = new HashMap<>();
    }

    public boolean add(E e) {
        return map.put(e, PRESENT) == null;
    }
    // ...
}

    HashSet은 자기만의 해시 테이블을 갖고 있지 않다. 필드로 HashMap 하나를 들고, 요소를 그 맵의 키로 넣는다. 값 자리에는 모든 엔트리가 공유하는 더미 객체 PRESENT 하나를 넣는다. add가 boolean을 돌려줄 수 있는 것도 put의 반환값 덕분이다. 이전 값이 null이면 처음 들어온 요소이고, PRESENT가 돌아오면 이미 있던 요소다. 같은 방식으로 LinkedHashSet은 LinkedHashMap을, TreeSet은 TreeMap을 안에 둔다.

    06~08회에서 셋을 직접 만들며 익힌 해시 인덱스, 버킷, equals와 hashCode의 규약은 그러므로 전부 Map의 이야기이기도 하다. 반대로 지금부터 볼 HashMap의 내부는 HashSet의 내부 그 자체다. 셋의 요소 하나가 맵 엔트리 하나를 차지하므로, 위 표의 엔트리 크기는 셋에도 그대로 적용된다.

    한 층 아래 — HashMap의 put을 따라간다

    HashMap의 중심에는 필드 하나가 있다. Node[] table, 노드 참조의 배열이다. 배열의 칸 하나를 버킷(bucket)이라 부르고, 배열의 길이를 용량(capacity)이라 부른다. 노드는 필드 넷으로 이루어진다.

    static class Node implements Map.Entry {
    final int hash;     // 키의 해시(섞은 값). 한 번 계산해서 저장해 둔다
    final K key;
    V value;
    Node next;     // 같은 버킷의 다음 노드
    // ...
}

    04회에서 만든 단일 연결 리스트의 노드에 hash와 key가 붙은 모양이다. HotSpot의 객체 헤더 12바이트에 int 하나와 참조 셋(각 4바이트)을 더하면 28바이트이고, 8바이트 단위로 맞추면 32바이트다. 앞의 표에서 측정한 값과 같다.

    put(key, value)가 호출되면 OpenJDK 21의 HashMap은 다음 순서로 일한다.

    해시를 섞는 이유

    인덱스를 구하는 식이 나머지 연산 %가 아니라 (n - 1) & hash인 것은 테이블의 길이 n이 항상 2의 거듭제곱이기 때문이다. n이 16이면 n - 1은 이진수로 1111이고, 이것과 AND를 하면 해시의 하위 4비트만 남는다. 0부터 15까지의 값이 나오므로 16으로 나눈 나머지와 같은 결과이면서, 나눗셈보다 싼 비트 연산 하나로 끝난다. 음수 해시가 음수 나머지를 만드는 문제도 생기지 않는다.

    이 방식의 약점은 해시의 하위 비트만 쓴다는 것이다. 길이가 16인 테이블에서는 32비트 해시 가운데 28비트가 버려진다. 상위 비트에서만 차이가 나는 키들은 전부 같은 버킷으로 몰린다. 그래서 HashMap은 hashCode()를 그대로 쓰지 않고 한 번 섞는다.

    static final int hash(Object key) {
    int h;
    return (key == null) ? 0 : (h = key.hashCode()) ^ (h >>> 16);
}

    h >>> 16은 상위 16비트를 하위 16비트 자리로 내린 값이다. 이것을 원래 값과 XOR하면 상위 비트의 차이가 하위 비트에 묻어난다. Integer 키 0x10000, 0x20000, 0x30000으로 확인해 보자. Integer의 hashCode()는 값 자신이므로 세 키의 하위 4비트는 모두 0이고, 섞지 않으면 셋 다 0번 버킷이다. 섞으면 0x10001, 0x20002, 0x30003이 되어 1번, 2번, 3번 버킷으로 흩어진다.

    앞의 단어 수 세기 예제의 키도 계산해 보자. String의 hashCode()는 API 문서에 식이 정해져 있어서 어느 JVM에서나 같은 값이 나온다.

    키hashCode()섞은 해시길이 16에서의 인덱스

    "be"313931393
    "or"355535553
    "not"1092671092662

    두 글자 단어는 해시가 65536보다 작아서 상위 16비트가 0이고 섞어도 값이 그대로다. "not"은 상위 16비트가 1이어서 최하위 비트가 뒤집혔고, 그 덕분에 3번이 아니라 2번 버킷으로 갔다. 섞지 않았다면 be, or, not 세 단어가 한 버킷에 몰렸을 것이다. put으로 채운 맵의 테이블은 이런 모습이다.

순회: 0번 칸부터 차례로, 칸 안에서는 체인 순서로  →  not, be, or, to

    출력이 {not=1, be=2, or=1, to=2}였던 이유가 여기 있다. 순회는 테이블을 0번 칸부터 훑으며 각 칸의 체인을 따라간다. 넣은 순서는 어디에도 기록되어 있지 않다. merge로 채운 맵에서 or가 be보다 먼저 나온 것도 이 그림으로 설명된다. 3번 칸에 be가 먼저 들어간 뒤 or가 올 때, put은 체인 꼬리에 붙여 be → or가 되고 merge는 머리에 끼워 or → be가 된다.

    키 하나가 hashCode, 섞기, 인덱스 계산을 거쳐 테이블의 한 칸에 도착하고, 그 칸의 노드 체인 끝에 붙는 경로를 한 장에 보여 준다. 깔끔한 기술 다이어그램, 흰 배경, 왼쪽에서 오른쪽으로 흐르는 구도. 맨 왼쪽에 둥근 상자 하나, 라벨 "키 or". 여기서 오른쪽으로 화살표가 나가 작은 상자 세 개를 차례로 지난다. 첫 상자 라벨 "hashCode() = 3555", 둘째 상자 라벨 "상위 16비트를 XOR", 셋째 상자 라벨 "(16 - 1) & 해시 = 3". 셋째 상자에서 나온 화살표가 오른쪽의 세로로 긴 배열로 들어간다. 배열은 칸 16개가 세로로 쌓인 모양이고 위에 라벨 "table (길이 16)". 칸 옆에 인덱스 숫자 0부터 15까지를 작게 적는다. 화살표는 인덱스 3인 칸을 가리키며 그 칸을 강조색으로 칠한다. 3번 칸에서 오른쪽으로 화살표가 나가 가로로 놓인 노드 상자 두 개로 이어진다. 첫 노드에는 "be = 2", 둘째 노드에는 "or = 1"이라고 적고, 둘째 노드는 점선 테두리로 방금 추가되었음을 표시한다. 두 노드는 "next" 라벨이 붙은 화살표로 연결되고 둘째 노드의 끝은 "null"로 끝난다. 2번 칸에서는 노드 "not = 1" 하나로, 11번 칸에서는 노드 "to = 2" 하나로 화살표가 나간다. 나머지 칸은 비어 있다. 그림 아래에 작은 글씨로 "버킷 = 배열의 칸 하나". 장식 없이 선과 상자만 사용한다. 키 "or"가 3번 버킷에 도착해 이미 있던 "be" 뒤에 붙는다. 테이블 어디에도 넣은 순서는 기록되지 않는다.

    체인을 훑을 때 비교하는 순서

    버킷 안에서 같은 키를 찾는 조건은 소스에 이렇게 쓰여 있다.

    if (e.hash == hash &&
    ((k = e.key) == key || (key != null && key.equals(k))))

    세 단계다. 먼저 노드에 저장해 둔 해시와 찾는 키의 해시를 int끼리 비교한다. 다르면 equals를 부를 필요조차 없다. 같은 버킷에 있다는 것은 하위 몇 비트가 같다는 뜻일 뿐이므로 전체 해시는 다른 경우가 많고, 이 비교가 대부분의 불일치를 걸러 낸다. 해시가 같으면 참조가 같은지 ==로 본다. 같은 객체라면 equals도 참이어야 하므로 호출을 아낄 수 있다. 그래도 아니면 마지막으로 equals를 호출한다.

    여기서 07회의 규약이 왜 필요했는지가 다시 드러난다. equals가 참인 두 객체의 hashCode가 다르면 둘은 대개 다른 버킷으로 가고, 운 좋게 같은 버킷에 가도 첫 단계의 해시 비교에서 탈락한다. equals는 호출되지도 않는다. 앞에서 본 Map에 get(1)을 한 경우는 반대다. Integer 1과 Long 1은 hashCode가 둘 다 1이어서 같은 버킷, 같은 해시로 첫 단계를 통과하지만 마지막 equals에서 타입이 달라 거짓이 된다.

    키가 바뀌면 길을 잃는다

    노드는 키의 해시를 final int hash에 저장해 둔다. 리사이즈할 때 hashCode()를 다시 부르지 않아도 되고 비교도 빨라지는 장점이 있지만, 한 가지 전제가 깔려 있다. 맵에 들어 있는 동안 키의 해시가 변하지 않는다는 것이다. 이 전제를 깨 보자.

    static class Point {
    int x, y;                      // final이 아니다
    Point(int x, int y) { this.x = x; this.y = y; }

    @Override public boolean equals(Object o) {
        return o instanceof Point p && x == p.x && y == p.y;
    }
    @Override public int hashCode() { return 31 * x + y; }
    @Override public String toString() { return "(" + x + "," + y + ")"; }
}

public static void main(String[] args) {
    Map where = new HashMap<>();
    Point p = new Point(1, 2);
    where.put(p, "home");
    System.out.println(where.get(p));                 // home

    p.x = 100;                                        // 맵 안에 있는 키를 바꾼다
    System.out.println(where.get(p));                 // null
    System.out.println(where.get(new Point(1, 2)));   // null
    System.out.println(where.size() + " " + where);   // 1 {(100,2)=home}
    System.out.println(where.remove(p));              // null
    System.out.println(where.size());                 // 1
}

    엔트리는 맵 안에 분명히 있다. 크기가 1이고 출력에도 보인다. 그런데 어떤 키로도 꺼낼 수 없고 지울 수도 없다. 숫자로 추적하면 이유가 보인다. 넣을 때의 해시는 31 × 1 + 2 = 33이고 인덱스는 33의 하위 4비트인 1이다. 노드는 1번 버킷에 hash=33으로 저장되었다. p.x를 100으로 바꾼 뒤 get(p)를 하면 해시가 31 × 100 + 2 = 3102, 인덱스가 14다. 14번 버킷은 비어 있으므로 null이다. 원래 값과 같은 new Point(1, 2)로 찾으면 해시 33으로 1번 버킷에 제대로 도착하고 저장된 해시와도 일치하지만, 마지막 equals에서 노드의 키가 이제 (100, 2)이므로 거짓이 된다.

    두 경로가 모두 막힌 엔트리는 맵이 살아 있는 한 회수되지 않고 남는다. Map의 API 문서는 변경 가능한 객체를 키로 쓸 때 각별히 주의하라고 경고하고, 키로 들어 있는 동안 equals 비교에 영향을 주는 방식으로 객체가 바뀌면 맵의 동작은 정해져 있지 않다고 적는다. 키로는 String, Integer 같은 불변 객체나 필드가 모두 final인 클래스, 레코드, 열거형을 쓴다.

    한 층 아래 — 리사이즈와 트리화

    버킷 수가 고정되어 있으면 엔트리가 늘수록 체인이 길어지고, 체인을 훑는 시간이 늘어 상수 시간이라는 전제가 무너진다. 06회에서 본 그대로다. HashMap은 엔트리 수가 임계값(threshold)을 넘으면 테이블을 늘린다. 임계값은 용량에 적재율(load factor)을 곱한 값이고, 적재율의 기본값은 0.75다. API 문서는 엔트리 수가 이 곱을 넘으면 내부 구조를 다시 만들어 버킷 수를 대략 두 배로 한다고 적는다.

    직접 확인해 보자. table은 외부에서 볼 수 없는 필드이므로 리플렉션으로 꺼낸다. 아래 도우미 클래스는 테이블 배열을 돌려주는 메서드와, 한 버킷의 체인을 문자열로 만드는 메서드를 갖는다.

    import java.lang.reflect.Field;
import java.util.HashMap;

public class Peek {
    static Object[] table(HashMap map) throws Exception {
        Field f = HashMap.class.getDeclaredField("table");
        f.setAccessible(true);
        return (Object[]) f.get(map);
    }

    static String chain(HashMap map, int index) throws Exception {
        Field next = Class.forName("java.util.HashMap$Node").getDeclaredField("next");
        next.setAccessible(true);
        StringBuilder sb = new StringBuilder("[" + index + "] ");
        for (Object node = table(map)[index]; node != null; node = next.get(node)) {
            sb.append(node).append(" -> ");
        }
        return sb.append("null").toString();
    }
}
    public class GrowthMain {
    public static void main(String[] args) throws Exception {
        HashMap map = new HashMap<>();
        System.out.println("생성 직후: table = " + Peek.table(map));
        for (int i = 1; i <= 13; i++) {
            map.put(i, "v" + i);
            if (i == 1 || i == 12 || i == 13) {
                System.out.println("size " + i + ": table.length = " + Peek.table(map).length);
            }
        }
        HashMap sized = new HashMap<>(100);
        sized.put(1, "v1");
        System.out.println("new HashMap<>(100): table.length = " + Peek.table(sized).length);
    }
}
    생성 직후: table = null
size 1: table.length = 16
size 12: table.length = 16
size 13: table.length = 32
new HashMap<>(100): table.length = 128
    JDK 21은 java.util 패키지의 비공개 필드를 리플렉션으로 여는 것을 기본으로 막는다. --add-opens 옵션 없이 실행하면 setAccessible(true)에서 InaccessibleObjectException이 난다. 이 옵션은 내부를 관찰하는 실험에만 쓴다. 비공개 필드의 이름과 구조는 JDK 버전마다 달라질 수 있다.

    출력 한 줄마다 사실 하나가 들어 있다. 생성 직후에는 테이블이 없다. new HashMap<>()은 배열을 만들지 않고, 첫 put에서 길이 16짜리 배열을 만든다. 아무것도 넣지 않는 빈 맵은 배열 메모리를 쓰지 않는다. 엔트리가 12개일 때까지 길이는 16이고, 13번째를 넣는 순간 32가 된다. 임계값이 16 × 0.75 = 12이고 조건이 "엔트리 수가 임계값을 넘으면"이기 때문이다.

    마지막 줄은 초기 용량을 직접 줄 때의 함정을 보여 준다. 100을 주었는데 테이블 길이는 128이다. 용량은 반드시 2의 거듭제곱이어야 하므로 주어진 값 이상인 가장 작은 2의 거듭제곱으로 올린다. 그리고 이 맵의 임계값은 128 × 0.75 = 96이다. 100개를 담으려고 new HashMap<>(100)이라고 썼는데 97번째 put에서 리사이즈가 일어난다. 생성자의 인자는 "담을 엔트리 수"가 아니라 "버킷 수"다. 엔트리 100개를 리사이즈 없이 담으려면 담을 개수를 적재율로 나눈 100 ÷ 0.75, 곧 134 이상을 주면 된다. Java 19부터는 이 계산을 대신해 주는 정적 메서드 HashMap.newHashMap(100)이 있고, 실행해 보면 테이블 길이가 256으로 잡힌다.

    두 배로 늘릴 때 노드는 어디로 가는가

    리사이즈는 새 배열을 만들고 모든 노드를 새 위치로 옮기는 일이다. 길이가 16에서 32로 바뀌면 인덱스 식이 hash & 15에서 hash & 31로 바뀐다. 달라지는 것은 비트 하나, 값이 16인 자리의 비트를 새로 본다는 점뿐이다. 그 비트가 0인 노드는 인덱스가 그대로이고, 1인 노드는 원래 인덱스에 16을 더한 곳으로 간다. 다른 가능성은 없다.

    키    해시(이진수)   hash & 15       hash & 31       hash & 16
 5     000101        0101 =  5       00101 =  5       0   →  제자리 [5]
21     010101        0101 =  5       10101 = 21      16   →  [5 + 16]
37     100101        0101 =  5       00101 =  5       0   →  제자리 [5]
53     110101        0101 =  5       10101 = 21      16   →  [5 + 16]

    OpenJDK 21의 resize()는 이 성질을 그대로 쓴다. 옛 테이블의 버킷 하나를 훑으면서 (e.hash & oldCap) == 0인 노드는 "낮은 쪽" 체인에, 아닌 노드는 "높은 쪽" 체인에 차례로 이어 붙인 다음, 낮은 쪽 체인을 새 테이블의 같은 인덱스에, 높은 쪽 체인을 인덱스 + oldCap에 건다. 실행으로 확인하자.

    public class SplitMain {
    public static void main(String[] args) throws Exception {
        HashMap map = new HashMap<>();
        for (int key : new int[]{5, 21, 37, 53}) {
            map.put(key, "v" + key);
        }
        System.out.println("length " + Peek.table(map).length);
        System.out.println(Peek.chain(map, 5));

        for (int key = 6; key <= 14; key++) {   // 9개를 더 넣어 13개가 되면 리사이즈
            map.put(key, "v" + key);
        }
        System.out.println("length " + Peek.table(map).length);
        System.out.println(Peek.chain(map, 5));
        System.out.println(Peek.chain(map, 21));
    }
}
    length 16
[5] 5=v5 -> 21=v21 -> 37=v37 -> 53=v53 -> null
length 32
[5] 5=v5 -> 37=v37 -> null
[21] 21=v21 -> 53=v53 -> null

    네 노드가 한 줄로 서 있던 체인이 두 줄로 갈라졌고, 각 줄 안에서 원래의 앞뒤 순서는 유지되었다. 이 방식에는 세 가지 이점이 있다. 노드에 저장된 hash 필드만 읽으므로 키의 hashCode()를 다시 호출하지 않는다. 새 노드 객체를 만들지 않고 기존 노드의 next 참조만 고쳐 쓴다. 그리고 버킷 하나의 노드는 정해진 두 곳으로만 가므로 버킷 단위로 독립해서 처리할 수 있다.

    길이 16 테이블의 5번 버킷에 있던 노드 네 개가, 길이 32 테이블에서 해시의 비트 하나에 따라 5번과 21번으로 나뉘는 것을 보여 준다. 깔끔한 기술 다이어그램, 흰 배경, 위아래 두 단으로 나눈 구도. 위쪽 단 왼쪽에 라벨 "리사이즈 전: 길이 16". 가로로 긴 배열을 그리되 칸 16개 가운데 인덱스 5인 칸만 강조색으로 칠하고 아래에 숫자 "5"를 적는다. 5번 칸에서 아래로 화살표가 나와 가로로 나란한 노드 상자 네 개로 이어진다. 노드 상자에는 왼쪽부터 "5", "21", "37", "53"이라고 적고 서로 화살표로 연결한다. "5"와 "37" 상자는 파란색, "21"과 "53" 상자는 주황색으로 칠한다. 아래쪽 단 왼쪽에 라벨 "리사이즈 후: 길이 32". 위보다 두 배 긴 가로 배열을 그리고 인덱스 5인 칸과 인덱스 21인 칸만 강조하며 아래에 숫자 "5"와 "21"을 적는다. 5번 칸에서 파란 노드 "5"와 "37"이 차례로 이어지고, 21번 칸에서 주황 노드 "21"과 "53"이 차례로 이어진다. 위 단의 노드들에서 아래 단의 같은 색 노드로 얇은 점선 화살표를 그린다. 오른쪽 여백에 범례 두 줄: 파란 사각형 옆에 "hash & 16 = 0 → 제자리", 주황 사각형 옆에 "hash & 16 ≠ 0 → 5 + 16". 장식 없이 선과 상자만 사용한다. 길이가 두 배가 되면 새로 보는 비트 하나가 노드의 행선지를 정한다. 제자리에 남거나, 옛 길이만큼 떨어진 칸으로 간다.

    그래도 리사이즈는 모든 노드를 한 번씩 방문하므로 엔트리 수에 비례하는 O(n) 작업이다. put이 평균적으로 상수 시간이라고 말할 수 있는 근거는 03회에서 배열 리스트의 확장을 분석할 때와 같다. 용량을 두 배씩 늘리면 리사이즈가 일어나는 간격도 두 배씩 벌어지므로, 리사이즈 비용을 그 사이의 모든 put에 나눠 얹으면 호출 하나당 상수가 된다. 다만 어느 한 번의 put은 다른 호출보다 훨씬 오래 걸릴 수 있다. 담을 양을 미리 안다면 알맞은 용량으로 시작해 이 비용을 없앨 수 있다.

    반대 방향의 동작은 없다. OpenJDK 21의 HashMap은 remove나 clear로 엔트리가 줄어도 테이블을 줄이지 않는다. clear()의 소스는 모든 칸에 null을 대입할 뿐이다. 그리고 HashMap의 순회는 테이블의 모든 칸을 훑어야 하므로 걸리는 시간이 엔트리 수만이 아니라 용량에도 비례한다. 한때 엔트리 수백만 개를 담았다가 비운 맵을 계속 재사용하며 순회하면, 엔트리가 몇 개뿐이어도 빈 칸 수백만 개를 매번 지나간다.

    버킷 하나가 너무 길어지면 — 트리화

    리사이즈는 엔트리가 전체적으로 많아졌을 때의 대책이다. 엔트리 수는 적은데 특정 버킷에만 몰리는 경우에는 도움이 되지 않을 수 있다. hashCode()가 같은 키들은 테이블을 아무리 늘려도 같은 버킷에 남기 때문이다. 이 경우를 위해 OpenJDK의 HashMap은 긴 체인을 레드-블랙 트리로 바꾼다. 이 동작을 정하는 상수가 소스에 셋 있다.

    상수값뜻
    TREEIFY_THRESHOLD8체인에 노드가 8개 있는 버킷에 하나가 더 붙으면 트리화를 시도한다
    MIN_TREEIFY_CAPACITY64테이블 길이가 이보다 작으면 트리로 바꾸지 않고 리사이즈를 한다
    UNTREEIFY_THRESHOLD6리사이즈로 트리가 갈라졌을 때 한쪽이 6개 이하이면 다시 체인으로 되돌린다

    모든 키가 같은 해시 코드를 돌려주는 최악의 클래스를 만들어 관찰해 보자.

    public class TreeifyMain {
    record SameHash(int id) {
        @Override
        public int hashCode() {
            return 42;              // 모든 키가 같은 해시 코드를 돌려준다
        }
    }

    public static void main(String[] args) throws Exception {
        HashMap map = new HashMap<>();
        for (int i = 1; i <= 12; i++) {
            map.put(new SameHash(i), i);
            Object[] table = Peek.table(map);
            Object bin = table[42 & (table.length - 1)];
            System.out.println(i + "개: length=" + table.length
                    + ", 버킷의 첫 노드=" + bin.getClass().getSimpleName());
        }
    }
}
    1개: length=16, 버킷의 첫 노드=Node
   (2개부터 7개까지 같은 내용)
8개: length=16, 버킷의 첫 노드=Node
9개: length=32, 버킷의 첫 노드=Node
10개: length=64, 버킷의 첫 노드=Node
11개: length=64, 버킷의 첫 노드=TreeNode
12개: length=64, 버킷의 첫 노드=TreeNode

    엔트리가 9개뿐인데 테이블이 32로 늘었다. 임계값 12를 넘지 않았는데도 리사이즈가 일어난 것이다. 9번째 노드가 체인에 붙으면서 트리화가 시도되었지만 테이블 길이 16이 64보다 작아서, 트리로 바꾸는 대신 테이블을 늘려 체인이 갈라지기를 기대한 것이다. 이 예제에서는 모든 키의 해시가 같아 갈라지지 않는다. 10번째에서 다시 64로 늘고, 더 미룰 수 없게 된 11번째에서 버킷의 노드가 TreeNode로 바뀐다. 긴 체인의 원인이 "테이블이 작아서"일 때는 리사이즈로 풀고, "해시 자체가 같아서"일 때만 트리로 간다는 순서가 드러난다.

    트리로 바뀐 버킷 안에서 노드는 먼저 해시 값으로 정렬되고, 해시가 같으면 키가 Comparable을 구현한 경우 compareTo로 순서를 정한다. API 문서도 키가 Comparable이면 충돌한 키 사이의 순서를 정하는 데 비교를 쓸 수 있다고 적는다. 이렇게 되면 한 버킷에 n개가 몰려도 탐색이 O(n)이 아니라 O(log n)에 끝난다. 위의 SameHash처럼 해시도 같고 비교도 할 수 없는 키는 트리 안에서 방향을 정할 근거가 없어서 탐색이 양쪽 가지를 모두 뒤져야 할 수 있다.

    기준이 8인 이유는 소스의 구현 주석에 나와 있다. 해시가 무작위로 퍼진다고 가정하면 한 버킷의 노드 수는 포아송 분포를 따르고, 기본 적재율에서 한 버킷에 8개가 모일 확률은 0.00000006이라고 계산해 두었다. 정상적인 hashCode에서는 사실상 일어나지 않는 일이다. 그러므로 트리화는 평소의 성능을 위한 장치가 아니라, 분포가 나쁜 hashCode나 일부러 충돌하도록 고른 키가 들어왔을 때 성능이 급격히 무너지지 않게 하는 안전망이다. 주석은 이를 우연한 또는 악의적인 사용에서도 성능이 완만하게 떨어지도록 한다고 표현한다.

    안전망에는 값이 붙는다. 같은 측정 방법으로 재면 TreeNode 하나는 56바이트로, 32바이트인 일반 노드의 두 배에 가깝다. 부모, 왼쪽, 오른쪽, 이전 노드를 가리키는 참조와 색을 나타내는 필드가 더 붙기 때문이다. 그래서 필요할 때만 쓰고 필요가 없어지면 되돌린다. 리사이즈로 트리가 둘로 갈라졌을 때는 UNTREEIFY_THRESHOLD가 기준이 되고, 삭제로 줄어들 때는 개수가 아니라 트리의 모양으로 판단한다. 소스 주석은 이 판단이 노드 2개에서 6개 사이의 어딘가에서 일어난다고 적는다.

    한 층 아래 — LinkedHashMap의 연결과 TreeMap의 트리

    LinkedHashMap: 해시 테이블 위에 실을 한 가닥 더 꿴다

    LinkedHashMap은 HashMap을 상속한다. 테이블, 해시 섞기, 버킷 탐색, 리사이즈는 모두 물려받은 그대로다. 바뀐 것은 노드다. LinkedHashMap.Entry는 HashMap.Node를 상속하고 before와 after라는 참조 둘을 더 갖는다. 28바이트에 참조 둘(8바이트)이 붙어 36바이트, 정렬하면 40바이트다. 맵 자체는 첫 엔트리와 마지막 엔트리를 가리키는 head와 tail을 갖는다.

    같은 엔트리 다섯 개를 두 종류의 참조가 따로 엮는다

 (1) 해시 테이블의 버킷 체인 — next               (2) 삽입 순서 리스트 — before / after

  table ─▶ 버킷 순서로:                             head                                   tail
           bravo, alpha, delta, echo, charlie         │                                      │
                                                      ▼                                      ▼
  get("bravo")는 (1)만 쓴다                          delta ⇄ alpha ⇄ charlie ⇄ bravo ⇄ echo
  순회는 (2)만 쓴다

    엔트리 객체는 하나씩인데 그것을 엮는 실이 두 가닥이다. get은 HashMap과 똑같이 테이블에서 버킷을 찾아 next를 따라간다. 순회는 테이블을 보지 않고 head에서 시작해 after를 따라간다. 넣을 때는 버킷에 노드를 건 다음 리스트의 꼬리에 잇고, 지울 때는 양쪽에서 모두 떼어 낸다. 04회에서 본 이중 연결 리스트의 삽입·삭제가 여기서 그대로 쓰인다.

    순회가 리스트를 따르므로 두 가지 성질이 나온다. 순서가 삽입 순서로 고정되고, 순회 시간이 용량과 무관하게 엔트리 수에만 비례한다. API 문서는 이 점을 HashMap과의 차이로 명시한다. 이미 있는 키에 put으로 값을 다시 넣어도 순서는 바뀌지 않는다. 앞의 예제에서 linked.put("delta", 99)를 한 뒤 출력하면 {delta=99, alpha=1, charlie=2, bravo=3, echo=4}로 delta가 여전히 맨 앞이다.

    생성자의 세 번째 인자로 true를 주면 리스트의 순서가 삽입 순서가 아니라 접근 순서(access order)가 된다. get이나 put으로 건드린 엔트리가 리스트의 꼬리로 옮겨 가므로, 머리에는 항상 가장 오랫동안 쓰이지 않은 엔트리가 놓인다. 여기에 엔트리를 넣은 직후 호출되는 removeEldestEntry를 재정의하면, 가장 오래 쓰이지 않은 것부터 버리는 LRU(least recently used) 캐시가 된다.

    class LruCache extends LinkedHashMap {
    private final int limit;

    LruCache(int limit) {
        super(16, 0.75f, true);        // 세 번째 인자 true: 접근 순서
        this.limit = limit;
    }

    @Override
    protected boolean removeEldestEntry(Map.Entry eldest) {
        return size() > limit;         // true를 돌려주면 머리 엔트리가 제거된다
    }
}

// 사용
LruCache cache = new LruCache<>(3);
cache.put("a", 1);
cache.put("b", 2);
cache.put("c", 3);
System.out.println(cache);   // {a=1, b=2, c=3}
cache.get("a");              // a를 사용했다 → 꼬리로 이동
System.out.println(cache);   // {b=2, c=3, a=1}
cache.put("d", 4);           // 4개가 되었으므로 머리(b)를 버린다
System.out.println(cache);   // {c=3, a=1, d=4}

    접근 순서 모드에서는 조회가 더 이상 읽기 전용 연산이 아니라는 점을 기억해 두어야 한다. get이 리스트의 참조 여러 개를 고쳐 쓴다. API 문서는 접근 순서 맵에서는 get으로 조회하는 것만으로도 구조 변경(structural modification)이라고 굵은 글씨로 적어 두었다. Java 21부터 LinkedHashMap은 SequencedMap 인터페이스를 구현해서 firstEntry(), lastEntry(), reversed()로 양 끝과 역순 뷰를 바로 얻을 수 있다.

    TreeMap: 해시가 없는 맵

    TreeMap에는 테이블도 해시도 없다. 필드는 트리의 뿌리를 가리키는 root와 비교에 쓸 comparator, 크기 정도다. 엔트리는 이렇게 생겼다.

    static final class Entry implements Map.Entry {
    K key;
    V value;
    Entry left;
    Entry right;
    Entry parent;
    boolean color = BLACK;
    // ...
}

    헤더 12바이트에 참조 다섯(20바이트)과 boolean 하나를 더해 33바이트, 정렬하면 40바이트다. put은 뿌리에서 출발해 넣으려는 키와 현재 노드의 키를 비교한다. 결과가 음수면 왼쪽 자식으로, 양수면 오른쪽 자식으로 내려가고, 0이면 그 노드의 값을 교체하고 끝낸다. 더 내려갈 자식이 없으면 그 자리에 새 엔트리를 단다. get도 같은 길을 따라 내려간다. 이 과정 어디에서도 키의 hashCode()나 equals()는 호출되지 않는다.

    이진 탐색 트리는 키가 들어오는 순서에 따라 한쪽으로 길게 늘어질 수 있다. 1부터 7까지를 차례로 넣으면 오른쪽 자식만 이어진 줄이 되어 연결 리스트와 다를 바 없다. TreeMap은 레드-블랙 트리(red-black tree)여서 이런 일이 생기지 않는다. 노드마다 빨강 또는 검정이라는 색을 두고, 뿌리는 검정이고, 빨간 노드의 자식은 빨강일 수 없고, 어느 노드에서든 그 아래 잎까지 내려가는 모든 경로에 검은 노드의 수가 같다는 규칙을 지킨다. 이 규칙들 때문에 가장 긴 경로가 가장 짧은 경로의 두 배를 넘을 수 없고, 노드가 n개일 때 높이는 2 × log₂(n + 1) 이하로 묶인다. 삽입이나 삭제로 규칙이 깨지면 색을 바꾸고 회전(rotation)으로 부모와 자식의 자리를 바꿔 복구하는데, 회전은 참조 몇 개를 고쳐 쓰는 상수 시간 작업이다. 아래는 리플렉션으로 확인한 실제 트리의 모양이다.

    delta, alpha, charlie, bravo, echo 순서로 넣은 TreeMap        1, 2, 3, 4, 5, 6, 7 순서로 넣은 TreeMap

             charlie(검정)                                           2(검정)
            /             \                                         /       \
     alpha(검정)        delta(검정)                            1(검정)      4(빨강)
          \                  \                                             /       \
       bravo(빨강)         echo(빨강)                                 3(검정)      6(검정)
                                                                                  /       \
 중위 순회: alpha, bravo, charlie, delta, echo                             5(빨강)      7(빨강)

    왼쪽 트리에서 처음 넣은 delta는 뿌리가 아니다. 세 번째 키를 넣을 때 회전이 일어나 charlie가 뿌리로 올라왔다. 오른쪽 트리는 오름차순으로 넣었는데도 높이가 4에 그친다. 왼쪽 자식, 자신, 오른쪽 자식 순서로 방문하는 중위 순회(in-order traversal)를 하면 키가 정렬된 순서로 나온다. TreeMap의 출력이 정렬되어 있는 이유다. API 문서는 containsKey, get, put, remove의 비용이 log(n)으로 보장된다고 적는다. HashMap의 "해시가 고르게 퍼진다면"이라는 조건이 붙지 않은 보장이다.

    정렬되어 있다는 성질은 해시로는 답할 수 없는 질문을 가능하게 한다. "이 키와 같거나 그보다 작은 것 중 가장 큰 키"나 "이 범위에 속하는 키 전부" 같은 질문이다.

    TreeMap grade = new TreeMap<>();
grade.put(90, "A");
grade.put(80, "B");
grade.put(70, "C");
grade.put(0, "F");
System.out.println(grade);                             // {0=F, 70=C, 80=B, 90=A}
System.out.println(grade.firstKey() + " " + grade.lastKey());   // 0 90
System.out.println(grade.floorKey(85));                // 80  (85 이하 중 최대)
System.out.println(grade.floorEntry(85).getValue());   // B
System.out.println(grade.ceilingKey(85));              // 90  (85 이상 중 최소)
System.out.println(grade.higherKey(90));               // null (90 초과 없음)
System.out.println(grade.headMap(80));                 // {0=F, 70=C}   (80 미만)
System.out.println(grade.tailMap(80));                 // {80=B, 90=A}  (80 이상)
System.out.println(grade.descendingMap());             // {90=A, 80=B, 70=C, 0=F}

    점수 85가 어느 등급인지를 floorEntry(85) 한 번으로 구했다. 뿌리에서 내려가며 후보를 좁히는 탐색이므로 이것도 log(n)이다. HashMap으로 같은 일을 하려면 모든 키를 꺼내 훑어야 한다. headMap과 tailMap이 돌려주는 것은 복사본이 아니라 원본의 일부 구간을 보는 뷰여서, 원본에 grade.put(85, "B+")를 하면 먼저 얻어 둔 tailMap(80)에도 85가 나타난다.

    해시를 쓰지 않는다는 사실에서 TreeMap만의 규칙 세 가지가 나온다.

    • 키는 비교할 수 있어야 한다. Comparator를 주지 않으면 키를 Comparable로 캐스팅해 compareTo를 부른다. Comparable을 구현하지 않은 클래스의 객체를 넣으면 첫 put에서 ClassCastException이 난다. 컴파일러는 이것을 막아 주지 않는다.
    • 자연 순서에서는 null 키를 쓸 수 없다. null에는 compareTo를 호출할 수 없으므로 put(null, 1)과 get(null)은 NullPointerException을 던진다. HashMap이 null 키를 해시 0으로 취급해 0번 버킷에 넣는 것과 대조된다. 값으로는 null을 넣을 수 있다.
    • "같은 키"의 기준이 equals가 아니라 비교 결과 0이다. new TreeMap<>(String.CASE_INSENSITIVE_ORDER)에 put("Java", 1)과 put("JAVA", 2)를 차례로 하면 결과는 {Java=2}, 크기 1이다. 두 문자열은 equals로는 다르지만 비교 결과가 0이어서 같은 키로 취급되고, 처음 들어간 키 객체는 그대로 둔 채 값만 교체된다.

    세 번째 규칙에 대해 API 문서는 정렬 맵의 순서가 equals와 일관되어야 Map 인터페이스의 계약을 올바르게 구현한다고 적고, 일관되지 않아도 동작은 잘 정의되어 있지만 Map의 일반 계약은 지키지 못하게 된다고 덧붙인다. Comparable과 Comparator를 어떻게 구현하는지, 일관성이 정확히 무엇인지는 10회에서 다룬다.

    스택 자료 구조

    여기서부터는 질문이 바뀐다. 스택(stack)은 가장 나중에 넣은 것을 가장 먼저 꺼내는 자료 구조다. 이 규칙을 후입선출(LIFO, last in first out)이라 한다. 연산은 셋이면 된다. 맨 위에 넣는 push, 맨 위에서 꺼내는 pop, 꺼내지 않고 맨 위를 보기만 하는 peek이다. 넣고 꺼내는 곳이 한쪽 끝 하나뿐이라는 점이 전부다.

    스택은 이미 매일 쓰고 있다. JVM 명세 2.5.2절은 모든 스레드가 스레드와 함께 만들어지는 자기만의 JVM 스택을 가지며 그 스택에 프레임을 저장한다고 정한다. 2.6절에 따르면 프레임은 메서드가 호출될 때마다 새로 만들어지고 그 호출이 끝나면(정상 종료든 예외든) 없어진다. main이 a를 부르고 a가 b를 부르면 프레임이 main, a, b 순으로 쌓이고, 가장 나중에 호출된 b가 가장 먼저 끝나 사라진다. 메서드 호출의 순서가 본질적으로 후입선출이기 때문에 스택이라는 구조가 쓰인다. 예외가 났을 때 보는 스택 트레이스는 그 순간의 프레임들을 위에서부터 읽은 목록이다.

    프레임 안에도 스택이 하나 더 있다. 피연산자 스택(operand stack)이다. 앞에서 본 바이트코드를 다시 보면 aload_0, ldc, iconst_1은 값을 하나씩 push하는 명령이고, invokeinterface Map.put은 쌓여 있던 맵 참조, 키, 값 셋을 pop한 뒤 반환값 하나를 push하며, 그다음의 pop은 이름 그대로 그 반환값을 버린다. JVM의 명령어는 처음부터 스택을 조작하는 방식으로 설계되어 있다.

    일상에서 가져온 비유접시 더미와 계산대 줄

    식당 주방의 접시 더미는 스택이다. 씻은 접시를 맨 위에 올리고, 쓸 때도 맨 위에서 집는다. 맨 아래 접시는 위의 것이 다 나가야 쓰인다. 계산대 앞의 줄은 큐다. 먼저 선 사람이 먼저 계산하고, 새로 온 사람은 맨 뒤에 선다. 비유가 깨지는 지점은 접시 더미는 급하면 중간 것을 빼낼 수도 있다는 것이다. 자료 구조로서의 스택과 큐는 끝이 아닌 곳을 건드리는 연산을 아예 제공하지 않음으로써 규칙을 강제한다. 자바의 Stack 클래스가 비판받는 이유가 바로 이 강제가 뚫려 있기 때문이다.

    java.util.Stack — 있지만 쓰지 않는 클래스

    자바에는 이름이 Stack인 클래스가 있다. 동작은 기대한 대로다.

    Stack stack = new Stack<>();
stack.push(1);
stack.push(2);
stack.push(3);
System.out.println(stack);          // [1, 2, 3]
System.out.println(stack.peek());   // 3
System.out.println(stack.pop());    // 3
System.out.println(stack);          // [1, 2]

stack.add(0, 99);                   // 바닥에 끼워 넣기: 컴파일도 실행도 된다
System.out.println(stack);          // [99, 1, 2]
System.out.println(stack.get(0));   // 99

    마지막 세 줄이 문제를 보여 준다. 스택인데 바닥에 요소를 끼워 넣을 수 있고 아무 위치나 읽을 수 있다. 클래스 선언이 public class Stack extends Vector이기 때문이다. Vector는 ArrayList와 같은 배열 기반 리스트이고 List를 구현한다. Stack은 그것을 상속했으므로 add(index, e), get(index), remove(index)를 전부 물려받았다. 배열 끝에 넣고 빼는 코드를 재사용하려고 상속을 택한 결과, "한쪽 끝으로만 드나든다"는 스택의 불변식을 타입이 지켜 주지 못하게 되었다. 구현을 빌리려는 목적이라면 상속이 아니라 필드로 갖는 구성을 써야 한다는 원칙의 대표적인 반례다.

    둘째 문제는 동기화다. Vector의 메서드는 synchronized로 선언되어 있다. Stack의 pop과 peek도 synchronized이고, push는 Vector의 동기화된 addElement를 호출한다. 스레드가 하나뿐인 코드에서도 호출마다 락을 잡았다 놓는 절차를 거친다. 그렇다고 여러 스레드에서 쓰기에 충분한 것도 아니다. if (!stack.empty()) stack.pop();처럼 호출 두 번으로 이루어진 동작은 각 호출이 동기화되어 있어도 그 사이에 다른 스레드가 끼어들 수 있다.

    Stack의 API 문서는 스스로 대안을 안내한다. 더 완전하고 일관된 후입선출 연산은 Deque 인터페이스와 그 구현체가 제공하며 이 클래스보다 그것을 우선해서 써야 한다는 것이다. Deque는 조금 뒤에 본다.

    스택을 직접 쓸 일은 생각보다 많다. 괄호의 짝 검사, 실행 취소, 깊이 우선 탐색이 대표적이고, 재귀 호출을 반복문으로 바꿀 때도 쓴다. 재귀는 JVM 스택을 암묵적인 스택으로 쓰는 것인데, JVM 스택의 크기에는 한도가 있어서 호출이 그 한도보다 깊어지면 JVM 명세가 정한 대로 StackOverflowError가 난다. 같은 일을 힙에 있는 스택 객체에 직접 쌓으면서 반복문으로 처리하면 깊이의 한도가 힙 크기로 바뀐다. 기본 설정으로 실행한 이 글의 실험 환경에서 깊이 1,000만의 재귀는 StackOverflowError로 끝났고, ArrayDeque에 1,000만 개를 push하는 반복문은 정상 종료했다.

    큐 자료 구조

    큐(queue)는 가장 먼저 넣은 것을 가장 먼저 꺼내는 자료 구조다. 선입선출(FIFO, first in first out)이라 한다. 스택과 달리 끝이 둘이다. 한쪽 끝(꼬리)으로 넣고 반대쪽 끝(머리)에서 꺼낸다. 도착한 순서대로 처리해야 하는 모든 곳에 큐가 있다. 인쇄 대기열, 처리 순서를 기다리는 요청, 너비 우선 탐색이 그렇다.

    자바에서 Queue는 클래스가 아니라 Collection을 확장한 인터페이스다. 특징은 넣기, 꺼내기, 보기 세 연산이 각각 두 벌씩 있다는 점이다. API 문서의 표를 옮기면 다음과 같다.

    연산실패하면 예외를 던진다실패하면 특수한 값을 돌려준다
    넣기add(e)offer(e) → false
    꺼내기remove()poll() → null
    보기element()peek() → null
    Queue queue = new ArrayDeque<>();
queue.offer("a");
queue.offer("b");
queue.offer("c");
System.out.println(queue);          // [a, b, c]
System.out.println(queue.peek());   // a
System.out.println(queue.poll());   // a
System.out.println(queue);          // [b, c]

queue.clear();

System.out.println(queue.peek());   // null
queue.remove();                     // NoSuchElementException

    두 벌이 있는 이유는 "실패"의 뜻이 상황마다 다르기 때문이다. 꺼내는 쪽에서 실패는 큐가 비었다는 것이다. 작업이 올 때까지 기다리며 반복해서 꺼내는 코드에서 빈 큐는 정상 상황이므로 poll()이 맞고, 반드시 무언가 있어야 하는 지점에서 빈 큐는 버그이므로 remove()가 맞다. 넣는 쪽에서 실패는 큐가 가득 찼다는 것이다. API 문서는 offer가 용량이 제한된 큐를 위해 설계된 형태이고 대부분의 구현에서는 넣기가 실패하지 않는다고 설명한다. 이 회차에서 쓰는 ArrayDeque와 LinkedList는 용량 제한이 없어서 add와 offer의 결과가 같다. 용량이 정해진 큐는 동시성을 다루는 뒤의 권에서 스레드 사이에 작업을 넘기는 통로로 다시 나온다.

    poll()이 null로 "비었다"를 알린다는 약속 때문에 큐에는 null을 넣으면 안 된다. ArrayDeque는 offer(null)에 NullPointerException을 던져 이것을 강제한다. LinkedList는 막지 않는다. LinkedList로 만든 큐에 offer(null)을 한 번 하고 poll()을 두 번 부르면 둘 다 null이 나온다. 첫 번째는 넣어 둔 요소이고 두 번째는 빈 큐라는 신호인데 호출한 쪽에서는 구별할 수 없다. Map의 get이 돌려주는 null과 같은 종류의 모호함이다.

    "큐는 선입선출"이라는 말에는 예외가 있다. API 문서는 큐가 보통은 요소를 선입선출로 정렬하지만 반드시 그런 것은 아니라고 적고 우선순위 큐를 예로 든다. PriorityQueue에 5, 1, 3을 넣고 poll()을 세 번 하면 1, 3, 5가 나온다. Queue 인터페이스가 약속하는 것은 "머리에서 꺼낸다"는 것이고, 무엇이 머리에 오는지는 구현체가 정한다.

    이제 구현을 생각해 보자. 연결 리스트로 큐를 만드는 것은 쉽다. 머리와 꼬리의 참조를 갖고 있으면 꼬리에 붙이는 일도 머리를 떼는 일도 참조 몇 개의 대입으로 끝난다. 배열로 만들면 곤란한 점이 있다. 배열의 끝에 넣는 것은 싸지만, 앞에서 꺼내고 나면 0번 칸이 비고, 03회에서 본 대로 뒤의 요소를 모두 한 칸씩 당겨야 한다. ArrayList의 remove(0)이 O(n)인 이유다. 꺼낼 때마다 n개를 옮기는 큐는 쓸 수 없다. 이 문제를 푸는 방법이 다음 절의 원형 배열이다.

    Deque 자료 구조 — 양쪽이 열린 원형 배열

    덱(deque)은 double ended queue를 줄인 말로, 양쪽 끝 모두에서 넣고 꺼낼 수 있는 자료 구조다. API 문서에 따르면 보통 "덱(deck)"으로 읽는다. 자바의 Deque 인터페이스는 Queue를 확장하고, 큐의 세 연산 두 벌을 앞(first)과 뒤(last) 양쪽에 대해 모두 갖는다.

    연산앞, 예외앞, 특수값뒤, 예외뒤, 특수값
    넣기addFirst(e)offerFirst(e)addLast(e)offerLast(e)
    꺼내기removeFirst()pollFirst()removeLast()pollLast()
    보기getFirst()peekFirst()getLast()peekLast()
    Deque deque = new ArrayDeque<>();
deque.offerLast("b");
deque.offerLast("c");
deque.offerFirst("a");
System.out.println(deque);                                    // [a, b, c]
System.out.println(deque.peekFirst() + " " + deque.peekLast()); // a c
System.out.println(deque.pollFirst() + " " + deque.pollLast()); // a c
System.out.println(deque);                                    // [b]

    구현체는 둘이다. 05회에서 리스트로 만난 LinkedList는 List이면서 Deque이기도 하다. 이중 연결 리스트는 양 끝의 노드를 직접 가리키고 있으므로 양쪽 연산이 모두 O(1)이다. 다른 하나가 ArrayDeque다. 배열로 큐를 만들 때의 문제, 곧 앞에서 꺼내면 뒤를 당겨야 한다는 문제를 원형 배열(circular array)로 푼 클래스다.

    ArrayDeque의 내부 — 고리로 쓰는 배열

    발상은 단순하다. 앞에서 꺼냈을 때 요소를 당기지 말고 "첫 요소가 있는 위치"를 한 칸 뒤로 옮기면 된다. 그러면 배열 앞쪽에 빈칸이 생기는데, 뒤쪽이 다 찼을 때 그 빈칸으로 돌아와 이어 쓰면 버리는 공간도 없다. 배열의 마지막 칸 다음이 0번 칸이라고 약속하는 것이다. OpenJDK 21의 ArrayDeque는 필드 셋으로 이것을 구현한다. 요소를 담는 Object[] elements, 첫 요소의 인덱스 head, 다음에 뒤로 넣을 자리의 인덱스 tail이다. 리플렉션으로 이 셋을 찍어 보자.

    static String dump(ArrayDeque deque) throws Exception {
    Field elements = ArrayDeque.class.getDeclaredField("elements");
    Field head = ArrayDeque.class.getDeclaredField("head");
    Field tail = ArrayDeque.class.getDeclaredField("tail");
    elements.setAccessible(true);
    head.setAccessible(true);
    tail.setAccessible(true);
    return Arrays.toString((Object[]) elements.get(deque))
            + " head=" + head.getInt(deque) + " tail=" + tail.getInt(deque);
}

public static void main(String[] args) throws Exception {
    ArrayDeque deque = new ArrayDeque<>(7);   // 내부 배열의 길이는 8
    deque.addLast("a");
    deque.addLast("b");
    deque.addLast("c");
    System.out.println(dump(deque));     // (1)
    deque.addFirst("z");
    deque.addFirst("y");
    System.out.println(dump(deque));     // (2)
    System.out.println(deque);           // (3)
    deque.pollFirst();
    deque.pollLast();
    System.out.println(dump(deque));     // (4)
    for (String s : new String[]{"c", "d", "e", "f"}) {
        deque.addLast(s);
    }
    System.out.println(dump(deque));     // (5)
    deque.addLast("g");
    System.out.println(dump(deque));     // (6)
}
    [a, b, c, null, null, null, null, null] head=0 tail=3
[a, b, c, null, null, null, y, z] head=6 tail=3
[y, z, a, b, c]

[a, b, c, d, e, f, g, null, null, null, null, null, null, null, null, null, null, z] head=17 tail=7

    한 줄씩 읽어 보자. (1) addLast는 elements[tail]에 요소를 쓰고 tail을 1 늘린다. 세 번 하고 나면 0~2번 칸이 차고 tail은 3이다. (2) addFirst("z")는 head를 1 줄인 자리에 쓴다. head가 0이었으므로 1을 줄이면 배열 밖인데, 이때 배열의 마지막 인덱스 7로 넘어간다. "y"는 그 앞인 6번에 들어간다. 배열에는 a, b, c가 먼저 보이지만 덱의 논리적인 순서는 (3)에서 보듯 y, z, a, b, c다. head에서 출발해 오른쪽으로 가다가 배열 끝에서 0번으로 넘어가 tail 직전까지 읽은 것이다.

    (4) pollFirst는 elements[head]를 읽고 그 칸을 null로 지운 뒤 head를 1 늘린다. pollLast는 tail을 1 줄이고 그 칸을 읽은 뒤 지운다. 여기까지의 어떤 연산도 다른 요소를 옮기지 않았다. 인덱스 하나를 1 늘리거나 줄이고 칸 하나를 읽거나 쓴 것이 전부다. 앞에 넣기, 앞에서 꺼내기, 뒤에 넣기, 뒤에서 꺼내기 네 가지가 모두 O(1)인 이유다.

    (2)의 상태를 고리로 펴 보면

   인덱스:   0    1    2    3    4    5    6    7
           ┌────┬────┬────┬────┬────┬────┬────┬────┐
 elements  │ a  │ b  │ c  │    │    │    │ y  │ z  │
           └────┴────┴────┴────┴────┴────┴────┴────┘
                            ▲              ▲
                          tail=3         head=6
                     (다음에 뒤로 넣을 자리)  (첫 요소)

   논리적 순서:  [6]y → [7]z → (끝에서 처음으로) → [0]a → [1]b → [2]c
   addFirst  : head를 왼쪽으로 한 칸(0 다음은 7)
   addLast   : tail을 오른쪽으로 한 칸(7 다음은 0)
    길이 8인 배열을 고리 모양으로 그려, head에서 tail 직전까지가 덱의 내용이고 양쪽 끝의 추가가 서로 반대 방향으로 인덱스를 움직인다는 것을 보여 준다. 깔끔한 기술 다이어그램, 흰 배경. 화면 왼쪽 절반에 도넛 모양의 고리를 그리고 이를 같은 크기의 칸 8개로 나눈다. 각 칸 바깥쪽에 인덱스 숫자 0부터 7까지를 시계 방향으로 적는다(0이 맨 위). 칸 6, 7, 0, 1, 2에는 차례로 글자 y, z, a, b, c를 적고 연한 파란색으로 칠한다. 칸 3, 4, 5는 비워 두고 흰색으로 둔다. 칸 6을 바깥에서 가리키는 굵은 화살표에 라벨 "head = 6 (첫 요소)". 칸 3을 바깥에서 가리키는 굵은 화살표에 라벨 "tail = 3 (다음에 넣을 자리)". 고리 안쪽에 시계 방향 곡선 화살표와 라벨 "addLast: tail이 이동", 반시계 방향 곡선 화살표와 라벨 "addFirst: head가 이동". 화면 오른쪽 절반에는 같은 내용을 일자 배열로 그린다. 칸 8개가 가로로 놓이고 위에 인덱스 0~7, 칸 안에는 왼쪽부터 a, b, c, 빈칸, 빈칸, 빈칸, y, z. 일자 배열 아래에 작은 글씨로 "논리적 순서: y z a b c". 일자 배열의 7번 칸 오른쪽 끝에서 0번 칸 왼쪽 끝으로 돌아가는 점선 화살표를 배열 위로 그리고 라벨 "끝 다음은 처음". 장식 없이 선과 도형만 사용한다. 배열의 끝과 처음을 이어 붙인 고리. 요소는 움직이지 않고 head와 tail 두 인덱스만 움직인다.

    (5)에서 요소가 7개가 되었고 빈칸은 6번 하나다. (6)에서 여덟 번째 요소 "g"를 넣자 배열이 18칸으로 늘었다. addLast는 요소를 쓴 뒤 tail을 늘렸을 때 그 값이 head와 같아지면, 곧 빈칸이 하나도 남지 않게 되면 배열을 키운다. OpenJDK 21의 소스는 현재 길이가 64보다 작으면 길이에 2를 더한 만큼(약 두 배), 64 이상이면 절반만큼 더 늘린다. 8에 10을 더해 18이 된 것이다. 늘린 뒤의 배열을 보면 "z"가 7번에서 17번으로 옮겨져 있다. 고리가 배열 끝을 넘어 이어져 있던 상태에서 그냥 길이만 늘리면 7번과 0번 사이에 빈칸이 끼어 순서가 끊어지므로, head부터 옛 배열 끝까지의 조각을 새 배열의 끝으로 밀어 고리를 다시 잇는다.

    빈칸을 항상 하나 이상 남겨 두는 데에는 이유가 있다. head와 tail이 같다는 조건을 "비어 있다"는 뜻으로만 쓰기 위해서다. 가득 찬 상태도 두 인덱스가 같아지도록 두면 빈 덱과 가득 찬 덱을 구별할 수 없다. 그래서 인자 없는 생성자는 요소 16개를 담을 수 있도록 17칸짜리 배열을 만든다. 요소를 계속 넣으며 배열 길이를 관찰하면 17, 36, 74, 111, 166 순으로 커진다. 확장할 때마다 전체를 복사하지만 그 간격이 계속 벌어지므로 배열 리스트와 같은 논리로 넣기 한 번의 평균 비용은 상수다. API 문서도 ArrayDeque의 대부분의 연산이 분할 상환 상수 시간에 실행된다고 적는다.

    큐로 오래 쓰면 고리의 진가가 드러난다. 뒤로 넣고 앞에서 꺼내기를 반복하면 head와 tail이 서로를 쫓으며 고리를 계속 돈다. 길이 4인 배열로 시작한 덱에 두 개 넣고 두 개 꺼내기를 열 번 반복해 요소 스무 개를 통과시켜도 배열은 4칸 그대로다. 한 번에 들어 있는 양이 용량을 넘지 않는 한, 지나간 총량이 아무리 많아도 확장이 일어나지 않는다.

    ArrayDeque가 null을 받지 않는 것도 이 구조에서 나온다. 빈칸은 null로 표시하고, pollFirst는 elements[head]가 null이면 덱이 비었다고 판단한다. null을 요소로 허용하면 이 판단이 성립하지 않는다.

    같은 일을 하는 LinkedList와 구조를 비교하면 차이가 분명하다. ArrayDeque는 요소 하나에 배열 칸 하나(압축 참조에서 4바이트)를 쓰고, 넣을 때 새 객체를 만들지 않는다. LinkedList는 요소마다 노드 객체를 하나씩 만든다. 같은 방법으로 측정하면 LinkedList의 노드 하나는 24바이트이고, 넣을 때마다 할당하고 꺼낼 때마다 가비지가 된다. 04회에서 본 대로 노드는 힙 여기저기에 흩어져 캐시 지역성도 나쁘다. API 문서는 ArrayDeque가 스택으로 쓰일 때는 Stack보다, 큐로 쓰일 때는 LinkedList보다 빠를 가능성이 높다고 적는다. ArrayDeque가 포기한 것도 있다. List가 아니므로 인덱스로 요소를 읽는 get(i)가 없고, 가운데 요소를 지우는 remove(Object)는 선형 시간이다. 양쪽 끝만 쓰겠다는 용도에 맞춘 구조다.

    Deque와 Stack, Queue

    양쪽 끝을 모두 다룰 수 있으면 스택과 큐는 그 특수한 경우가 된다. 한쪽 끝으로만 넣고 꺼내면 스택이고, 한쪽으로 넣고 반대쪽에서 꺼내면 큐다. Deque 인터페이스는 이 두 용법을 위한 이름을 따로 갖고 있다. API 문서의 비교표와 메서드 설명에 따른 대응 관계는 다음과 같다. 스택의 peek()만은 Java SE 21 문서의 비교표에 getFirst()로 적혀 있는데, peek() 메서드 자체의 설명은 peekFirst()와 같다고 하고 실제로도 빈 덱에서 예외 없이 null을 돌려주므로 아래 표는 메서드 설명을 따랐다.

    용법메서드같은 일을 하는 Deque 메서드건드리는 끝
    스택push(e)addFirst(e)앞
    pop()removeFirst()앞
    peek()peekFirst()앞
    큐offer(e)offerLast(e)뒤
    poll()pollFirst()앞
    peek()peekFirst()앞
    Deque stack = new ArrayDeque<>();
stack.push(1);
stack.push(2);
stack.push(3);
System.out.println(stack);          // [3, 2, 1]
System.out.println(stack.peek());   // 3
System.out.println(stack.pop());    // 3
System.out.println(stack);          // [2, 1]

Queue queue = new ArrayDeque<>();
queue.offer("a");
queue.offer("b");
queue.offer("c");
System.out.println(queue.poll());   // a
System.out.println(queue);          // [b, c]

    표에서 눈여겨볼 것은 꺼내는 쪽이 스택과 큐 모두 "앞"이라는 점이다. 차이는 넣는 쪽에 있다. push는 앞에 넣고 offer는 뒤에 넣는다. 그래서 pop()과 poll()은 같은 끝에서 꺼내는 형제이고, 다른 점은 비어 있을 때 예외를 던지느냐(pop, NoSuchElementException) null을 돌려주느냐(poll)뿐이다.

    스택으로 쓴 덱의 출력이 [3, 2, 1]인 것도 여기서 나온다. push가 앞에 넣으므로 덱의 첫 요소가 스택의 꼭대기이고, 순회는 꼭대기에서 바닥 쪽으로 진행한다. java.util.Stack은 반대였다. 배열의 끝이 꼭대기여서 같은 요소가 [1, 2, 3]으로 출력되고 순회도 바닥부터 한다. 기존 코드의 Stack을 ArrayDeque로 바꿀 때 push, pop, peek만 쓰는 부분은 그대로 동작하지만, 스택을 순회하거나 리스트로 복사하는 부분은 순서가 뒤집힌다. 빈 스택에서 pop()이 던지는 예외도 EmptyStackException에서 NoSuchElementException으로 바뀐다.

    변수의 선언 타입은 의도를 드러내는 수단이다. 위에서 큐는 Queue으로 받았다. 객체는 ArrayDeque이지만 이 변수로는 큐의 연산만 호출할 수 있어서, 실수로 앞에 끼워 넣는 코드가 컴파일되지 않는다. 스택은 사정이 다르다. 자바에는 스택 전용 인터페이스가 없어서 Deque로 받을 수밖에 없고, 이 타입에는 addLast도 pollLast도 열려 있다. 그래도 Stack보다는 낫다. 가운데를 건드리는 add(index, e)와 get(index)가 없고 불필요한 동기화도 없다. 변수 이름을 stack으로 짓고 push, pop, peek만 쓰는 규율로 보완한다.

    꺼내는 끝 하나가 탐색 순서를 바꾼다

    스택과 큐의 차이가 얼마나 작은지, 그리고 그 작은 차이가 결과를 얼마나 바꾸는지를 보여 주는 예제다. 아래 트리를 뿌리 A에서 시작해 모두 방문한다. "아직 방문하지 않은 노드"를 덱에 넣어 두고 하나씩 꺼내 처리하는데, 꺼내는 끝만 인자로 바꾼다.

              A
        /   \
       B     C
      / \   / \
     D   E F   G
    public class WalkMain {
    static final Map> CHILDREN = Map.of(
            "A", List.of("B", "C"),
            "B", List.of("D", "E"),
            "C", List.of("F", "G"));

    static List walk(boolean takeFromFront) {
        Deque pending = new ArrayDeque<>();
        List visited = new ArrayList<>();
        pending.addLast("A");
        while (!pending.isEmpty()) {
            String node = takeFromFront ? pending.pollFirst() : pending.pollLast();
            visited.add(node);
            for (String child : CHILDREN.getOrDefault(node, List.of())) {
                pending.addLast(child);
            }
        }
        return visited;
    }

    public static void main(String[] args) {
        System.out.println("앞에서 꺼냄(큐):   " + walk(true));
        System.out.println("뒤에서 꺼냄(스택): " + walk(false));
    }
}
    앞에서 꺼냄(큐):   [A, B, C, D, E, F, G]
뒤에서 꺼냄(스택): [A, C, G, F, B, E, D]

    넣는 쪽은 항상 뒤다. 앞에서 꺼내면 먼저 들어간 것이 먼저 나오는 큐가 된다. 덱의 내용은 [A] → [B, C] → [C, D, E] → [D, E, F, G]로 변하고, 뿌리에서 가까운 층부터 차례로 방문하는 너비 우선 탐색(BFS)이 된다. 뒤에서 꺼내면 방금 넣은 것이 먼저 나오는 스택이 된다. 덱은 [A] → [B, C] → [B, F, G] → [B, F] → [B] → [D, E]로 변하고, 한 가지를 끝까지 내려간 뒤에야 옆 가지로 넘어가는 깊이 우선 탐색(DFS)이 된다. 반복문도, 방문 처리도, 자식을 넣는 코드도 같다. 바뀐 것은 pollFirst와 pollLast 한 단어다. 맵 CHILDREN에 키가 없는 잎 노드에는 getOrDefault가 빈 리스트를 돌려주어 분기 없이 처리된다.

    세 자료 구조를 같은 모양의 가로 통으로 그려, 드나드는 끝이 어디인지만 다르다는 것을 한눈에 보여 준다. 깔끔한 기술 다이어그램, 흰 배경, 가로로 긴 통 세 개를 위에서 아래로 나란히 배치한다. 각 통 안에는 정사각형 칸 세 개가 가로로 들어 있고 왼쪽부터 숫자 3, 2, 1이 적혀 있다(맨 위 통), a, b, c(가운데 통), a, b, c(맨 아래 통). 맨 위 통의 왼쪽에 굵은 글씨 "스택 (LIFO)". 이 통은 왼쪽 끝만 열려 있고 오른쪽 끝은 벽으로 막혀 있다. 왼쪽 끝에 통 안으로 들어가는 화살표와 라벨 "push", 통 밖으로 나오는 화살표와 라벨 "pop". 가운데 통의 왼쪽에 굵은 글씨 "큐 (FIFO)". 이 통은 양쪽이 열려 있다. 오른쪽 끝에 통 안으로 들어가는 화살표와 라벨 "offer", 왼쪽 끝에 통 밖으로 나오는 화살표와 라벨 "poll". 맨 아래 통의 왼쪽에 굵은 글씨 "덱 (Deque)". 양쪽이 열려 있고, 왼쪽 끝에 양방향 화살표와 라벨 "offerFirst / pollFirst", 오른쪽 끝에 양방향 화살표와 라벨 "offerLast / pollLast". 세 통의 왼쪽 끝 위에 작은 글씨 "앞(first)", 오른쪽 끝 위에 작은 글씨 "뒤(last)". 들어가는 화살표는 파란색, 나오는 화살표는 주황색으로 통일한다. 장식 없이 선과 상자만 사용한다. 스택은 한쪽 끝만, 큐는 넣는 끝과 꺼내는 끝을 따로, 덱은 양쪽 끝을 모두 쓴다. 스택과 큐는 덱의 연산 일부만 쓰는 용법이다.

    흔한 오해 일곱 가지

    • "HashMap은 넣은 순서대로 나온다." 키가 몇 개 안 되는 예제에서 우연히 그렇게 보일 뿐이다. 순회 순서는 버킷 번호와 체인 안의 위치로 정해지고, 리사이즈가 일어나면 바뀌며, 같은 키를 put으로 넣었는지 merge로 넣었는지에 따라서도 달라진다. 순서가 필요하면 LinkedHashMap이나 TreeMap을 쓴다.
    • "get이 null이면 그 키는 없다." 값으로 null이 들어 있어도 null이다. 존재 여부는 containsKey로 확인하고, 가능하면 값에 null을 넣지 않는다.
    • "new HashMap<>(100)은 100개까지 리사이즈가 없다." 인자는 버킷 수이고 128로 올림된다. 임계값은 그 0.75배인 96이다. 담을 개수를 기준으로 하려면 HashMap.newHashMap(100)을 쓴다.
    • "버킷에 8개가 넘으면 항상 트리가 된다." 테이블 길이가 64보다 작으면 트리로 바꾸지 않고 리사이즈를 한다. 그리고 정상적인 hashCode에서는 한 버킷에 8개가 모이는 일 자체가 거의 없다.
    • "TreeMap도 equals와 hashCode로 키를 구분한다." TreeMap은 두 메서드를 호출하지 않는다. 비교 결과가 0이면 같은 키다. 키 클래스의 equals를 아무리 잘 구현해도 비교 로직이 다르게 말하면 TreeMap은 비교 쪽을 따른다.
    • "스택이 필요하면 Stack 클래스를 쓴다." Stack은 Vector를 상속해 리스트의 연산이 모두 열려 있고 메서드가 동기화되어 있다. API 문서가 직접 Deque를 쓰라고 안내한다.
    • "큐는 넣고 빼기가 잦으니 LinkedList가 제격이다." 양 끝의 연산은 ArrayDeque도 O(1)이고, 요소마다 노드를 할당하지 않으며 메모리가 연속되어 있다. 큐와 스택의 기본 선택은 ArrayDeque다. LinkedList가 필요한 경우는 null 요소를 담아야 하거나 같은 객체를 List로도 써야 할 때 정도다.

    다른 곳에서 다시 만나는 Map과 큐

    Map은 자바 프로그램에서 가장 널리 쓰이는 구조에 속한다. 이름으로 객체를 찾고, 식별자로 데이터를 찾고, 설정 키로 값을 찾는 일은 형태가 달라도 모두 키로 값을 찾는 조회다. HTTP 메시지의 헤더, JSON 객체, 요청 파라미터처럼 이름과 값의 쌍으로 이루어진 데이터를 자바에서 다룰 때도 Map이 자연스럽게 등장한다. 그때마다 이 회차에서 본 질문이 다시 유효하다. 키로 쓰는 객체가 불변인가, equals와 hashCode가 함께 재정의되어 있는가, 순서가 필요한가.

    캐시는 Map의 대표적인 응용이다. 계산 결과나 조회 결과를 키와 함께 넣어 두고 다음에 같은 키가 오면 꺼내 쓴다. 이때 접근 순서 LinkedHashMap에서 본 "가장 오래 쓰이지 않은 것을 버린다"는 정책이 기본 어휘가 된다. 데이터베이스가 디스크 페이지를 메모리에 올려 두는 방식을 뒤의 권에서 볼 때도 같은 생각이 나온다.

    이 회차의 모든 클래스에는 공통된 한계가 있다. HashMap, LinkedHashMap, TreeMap, ArrayDeque의 API 문서는 모두 이 구현이 동기화되어 있지 않다고 밝힌다. 리사이즈가 진행 중인 테이블을 다른 스레드가 읽거나, 두 스레드가 같은 버킷 체인의 꼬리에 동시에 노드를 다는 상황을 떠올려 보면 이유를 짐작할 수 있다. 여러 스레드가 공유하는 맵과, 스레드 사이에서 작업을 주고받는 큐는 동시성을 다루는 뒤의 권에서 별도의 클래스로 배운다. 그 클래스들의 동작을 이해하는 바탕이 여기서 본 테이블, 버킷, 고리 모양 배열이다.

    다음 10회는 컬렉션 프레임워크의 마지막 회차다. 이 회차에서 "뷰를 순회한다"거나 "비교 결과가 0이면 같은 키"라고 넘어간 부분, 곧 Iterator가 순회를 어떻게 추상화하는지와 Comparable, Comparator로 순서를 정의하는 방법을 정면으로 다룬다.

    이 장의 핵심

    Map은 키로 값을 찾는 구조이고, 구현체의 차이는 키를 어떻게 찾아가느냐의 차이다. HashMap은 해시로 배열의 칸을 계산해 한 번에 가고, TreeMap은 비교하며 트리를 내려가고, LinkedHashMap은 해시 테이블에 순서를 기억하는 연결을 더한다. 스택과 큐는 꺼내는 순서를 규칙으로 고정한 구조이고, 둘 다 양쪽 끝이 열린 덱의 일부만 쓰는 용법이다. ArrayDeque는 배열을 고리처럼 써서 양쪽 끝의 연산을 요소 이동 없이 끝낸다.
    Map과 엔트리
    키 하나를 값 하나에 대응시키는 구조다. 키는 중복될 수 없고, 같은 키로 다시 put하면 엔트리가 늘지 않고 값이 교체되며 이전 값이 반환된다. get이 돌려주는 null은 "키가 없다"와 "값이 null이다"를 구별해 주지 않는다.
    컬렉션 뷰
    keySet, values, entrySet은 복사본이 아니라 원본 맵을 들여다보는 창이다. 뷰에서 지우거나 엔트리의 setValue로 고치면 원본이 바뀌고, 원본의 변화는 이미 얻어 둔 뷰에 그대로 보인다.
    HashMap의 버킷 선택
    hashCode()의 상위 16비트를 하위 16비트에 XOR해 섞고 (길이 - 1) & 해시로 칸을 고른다. 칸 안에서는 저장된 해시, ==, equals 순으로 비교한다. 순회는 칸 번호 순서로 진행하므로 넣은 순서와 무관하다.
    리사이즈
    엔트리 수가 용량 × 적재율(기본 0.75)을 넘으면 테이블을 두 배로 늘린다. 노드는 새로 보게 되는 비트 하나에 따라 제자리에 남거나 옛 길이만큼 떨어진 칸으로 간다. 엔트리가 줄어도 테이블은 줄지 않는다.
    트리화
    OpenJDK 21에서 테이블 길이가 64 이상이고 노드가 8개인 체인에 하나가 더 붙으면 그 버킷을 레드-블랙 트리로 바꾼다. 평소의 성능을 위한 장치가 아니라 해시가 한곳에 몰리는 최악의 경우를 위한 안전망이다.
    LinkedHashMap
    HashMap의 노드에 before, after 참조를 더해 모든 엔트리를 이중 연결 리스트로 엮는다. 조회는 테이블로, 순회는 리스트로 한다. 그래서 삽입 순서(선택하면 접근 순서)가 유지되고 순회 시간이 용량과 무관하다.
    TreeMap
    해시 없이 비교만으로 레드-블랙 트리를 내려간다. 키가 정렬되어 있어 floorKey, headMap 같은 크기 관계 질의가 가능하고 주요 연산이 log(n)으로 보장된다. 같은 키의 기준은 equals가 아니라 비교 결과 0이다.
    스택, 큐, 덱
    스택은 넣은 끝에서 꺼내고(LIFO) 큐는 반대쪽 끝에서 꺼낸다(FIFO). 덱은 양쪽 끝을 모두 쓰므로 둘을 포함한다. Vector를 상속해 리스트 연산이 열려 있고 동기화 비용이 붙는 Stack 대신 Deque를 쓴다.
    ArrayDeque의 원형 배열
    배열의 끝과 처음이 이어져 있다고 보고 head와 tail 두 인덱스만 움직인다. 양쪽 끝의 추가와 제거가 요소 이동 없이 끝나고, 빈칸이 하나도 남지 않게 될 때만 배열을 키운다.

    실무에서 Map 구현체를 고르는 판단은 대부분 "순서가 밖으로 새어 나가는가"에서 갈린다. 조회만 하는 맵이라면 HashMap이면 된다. 그런데 맵을 순회한 결과가 응답 본문, 로그, 파일, 테스트의 기대값으로 나가는 순간 순서는 계약의 일부가 된다. HashMap의 순회 순서에 기대는 코드는 키가 몇 개 안 될 때는 멀쩡하다가, 키가 늘어 리사이즈가 일어나거나 넣는 메서드를 put에서 merge로 바꾸는 것만으로 결과가 달라진다. 이런 문제는 재현이 어렵고 원인을 찾기까지 오래 걸린다. 순서가 눈에 보이는 곳으로 나간다면 처음부터 LinkedHashMap을 쓰고, "이 값 이하 중 가장 큰 키" 같은 질문이 반복된다면 TreeMap을 쓴다. 정렬된 결과가 마지막에 한 번만 필요하다면 HashMap에 모은 뒤 끝에서 정렬하는 쪽이 낫다.

    메모리 문제로 힙 덤프를 열었을 때 HashMap$Node가 상위에 있는 경우는 드물지 않다. 원인은 대개 둘 중 하나다. 하나는 버리는 규칙이 없는 캐시다. 넣기만 하고 지우지 않는 맵은 이름이 캐시일 뿐 누수다. 엔트리 하나가 노드만 32바이트(OpenJDK 21, 압축 참조 기준)이고 여기에 키 객체와 값 객체가 따로 붙는다는 것을 알고 있으면 엔트리 수에서 메모리 사용량을 어림할 수 있고, 상한이 필요하다는 판단도 숫자로 할 수 있다. 다른 하나는 키의 문제다. equals와 hashCode를 재정의하지 않은 클래스나 넣은 뒤에 필드가 바뀌는 객체를 키로 쓰면, 같은 데이터라고 생각한 키가 매번 새 엔트리를 만들거나 다시는 찾을 수 없는 엔트리로 남는다. 키 클래스를 볼 때 "불변인가, 두 메서드가 같은 필드로 재정의되어 있는가"를 먼저 확인하는 습관이 이런 장애를 설계 단계에서 막는다.

    스택과 큐는 ArrayDeque를 기본으로 두고, 판단이 필요한 곳은 다른 데 있다. 첫째는 재귀다. 깊이가 입력 데이터에 따라 정해지는 탐색(깊게 중첩된 문서, 길게 이어진 참조 관계)을 재귀로 쓰면 평소에는 문제없다가 특정 입력에서만 StackOverflowError로 죽는다. 깊이를 통제할 수 없는 입력이라면 힙에 둔 덱을 스택으로 쓰는 반복문으로 바꾸는 편이 안전하다. 둘째는 큐의 용량이다. 이 회차의 큐는 용량 제한이 없어서 offer가 실패하지 않는다. 넣는 쪽이 꺼내는 쪽보다 빠른 상태가 지속되면 큐는 조용히 자라다가 메모리가 바닥난 뒤에야 문제가 드러난다. 큐를 작업 대기열로 쓸 때는 "가득 차면 어떻게 할 것인가"를 정해야 하고, offer가 false를 돌려주는 형태로 설계된 이유가 여기에 있다.

    마지막으로 이 회차의 구현체는 모두 스레드 하나가 쓰는 것을 전제로 한다. 요청마다 새로 만들어 쓰고 버리는 지역 변수라면 걱정할 것이 없다. 반면 여러 요청이 함께 쓰는 필드에 HashMap이나 ArrayDeque를 두었다면 그 자체가 결함이다. 접근 순서 LinkedHashMap은 get조차 구조를 바꾸므로 "읽기만 하니까 괜찮다"는 추론도 통하지 않는다. 공유되는 맵과 큐에 어떤 클래스를 써야 하는지는 동시성을 다루는 권에서 배운다.

HashMap이 키의 변경을 감지해 그 엔트리를 삭제했기 때문이다. 노드는 넣을 당시의 해시로 정해진 버킷에 걸려 있는데, 조회는 바뀐 해시로 버킷을 계산하고 저장된 해시와도 비교하므로 그 노드에 닿지 못하기 때문이다. 노드는 넣을 때 계산한 해시를 final 필드에 저장하고 그 해시로 정한 버킷에 걸린다. 키가 바뀐 뒤의 조회는 새 해시로 다른 버킷을 찾아가고, 우연히 같은 버킷이더라도 저장된 해시와 달라 첫 비교에서 탈락한다. equals는 호출되기도 전이다. 맵은 키 객체의 참조를 저장할 뿐 복사하지 않으며, 변경을 감지하는 장치도 없다. 그래서 엔트리는 크기에 포함된 채 꺼낼 수도 지울 수도 없게 남는다. new TreeMap(String.CASE_INSENSITIVE_ORDER)에 put("Java", 1), put("JAVA", 2)를 차례로 호출했더니 맵이 {Java=2}가 되었다. 이유로 옳은 것은? 두 문자열의 hashCode()가 같아 같은 버킷에 들어갔기 때문이다. TreeMap이 키를 저장할 때 대소문자를 통일해 바꿔 넣기 때문이다. TreeMap은 비교 결과가 0인 키를 같은 키로 보고 값만 교체하며, 이 판단에 equals와 hashCode를 쓰지 않기 때문이다. put은 이미 있는 키에 대해서는 새 값을 무시하기 때문이다. TreeMap에는 버킷도 해시도 없다. 뿌리에서부터 비교하며 내려가다가 결과가 0인 엔트리를 만나면 그 엔트리의 값을 교체하고 끝낸다. 주어진 비교자는 대소문자를 무시하므로 두 문자열의 비교 결과가 0이다. 키 객체는 처음 들어간 "Java"가 그대로 남아 있으므로 키를 바꿔 저장한다는 설명은 틀렸고, 값이 2로 바뀌었으므로 새 값을 무시한다는 설명도 틀렸다. 내부 배열의 길이가 8이고 head = 6, tail = 3인 ArrayDeque가 있다. 들어 있는 요소의 수와, 여기에 addFirst(x)를 호출했을 때 일어나는 일로 옳은 것은? (OpenJDK 21 기준) 요소는 5개다. head가 5가 되고 5번 칸에 x를 쓴다. 다른 요소는 움직이지 않고 배열도 그대로다. 요소는 3개다. head가 7이 되고 7번 칸에 x를 쓴다. 요소는 5개다. 3번 칸에 x를 쓰고 tail이 4가 된다. 요소는 5개다. 논리적으로 맨 앞에 넣어야 하므로 기존 요소 5개를 한 칸씩 뒤로 민 다음 쓴다. 요소는 head에서 시작해 배열 끝을 돌아 tail 직전까지이므로 6, 7, 0, 1, 2번 칸의 5개다. addFirst는 head를 한 칸 앞으로(6에서 5로) 옮기고 그 칸에 쓴다. 쓴 뒤에도 head(5)와 tail(3)이 다르므로 빈칸이 남아 있고 확장은 없다. 3번 칸에 쓰고 tail을 늘리는 것은 addLast의 동작이다. 요소를 미는 일은 원형 배열에서 일어나지 않으며, 그것이 이 구조를 쓰는 이유다. 정수 1, 2, 3을 차례로 push한 뒤 향상된 for문으로 순회한다. Deque s = new ArrayDeque<>()와 Stack s = new Stack<>()에서 순회 순서가 어떻게 되고, 그 차이는 어디서 오는가? 둘 다 3, 2, 1이다. 스택은 후입선출이므로 순회도 항상 꼭대기부터다. ArrayDeque는 3, 2, 1이고 Stack은 1, 2, 3이다. 덱의 push는 앞쪽 끝에 넣고 순회는 앞에서 시작하지만, Stack은 Vector의 배열 끝에 넣고 순회는 0번 인덱스에서 시작한다. ArrayDeque는 1, 2, 3이고 Stack은 3, 2, 1이다. ArrayDeque는 배열 기반이라 넣은 순서대로 저장된다. ArrayDeque의 순서는 해시 값에 따라 정해져 예측할 수 없고 Stack은 1, 2, 3이다. Deque.push(e)는 addFirst(e)와 같아서 나중에 넣은 것이 덱의 첫 요소가 되고, 순회는 첫 요소부터 진행하므로 3, 2, 1이다. Stack은 Vector를 상속한 리스트여서 push가 배열의 끝에 요소를 붙이고 순회는 리스트의 순서인 1, 2, 3으로 진행한다. pop이 돌려주는 순서는 둘 다 3, 2, 1로 같으므로, 클래스를 바꿀 때 달라지는 것은 순회·출력·복사처럼 "꺼내지 않고 훑는" 코드다. ArrayDeque는 해시를 쓰지 않는다.
    엔트리(entry)
    키 하나와 값 하나를 묶은 쌍. 자바에서는 Map.Entry 타입으로 나타내고, HashMap에서는 테이블의 노드 객체가 곧 엔트리다.
    컬렉션 뷰(collection view)
    맵의 내용을 키의 셋, 값의 컬렉션, 엔트리의 셋으로 보여 주는 객체. 요소를 복사해 갖지 않고 원본 맵을 참조하므로 원본과 항상 같은 내용을 보인다.
    임계값(threshold)
    용량에 적재율을 곱한 값. HashMap의 엔트리 수가 이 값을 넘으면 테이블을 두 배로 늘린다. 기본 설정에서 용량 16의 임계값은 12다.
    트리화(treeification)
    OpenJDK의 HashMap이 지나치게 길어진 버킷의 노드 체인을 레드-블랙 트리로 바꾸는 일. 해시 충돌이 몰렸을 때 탐색 비용이 선형으로 늘어나는 것을 막는다.
    접근 순서(access order)
    LinkedHashMap이 엔트리를 가장 오래전에 접근한 것부터 가장 최근에 접근한 것 순으로 유지하는 방식. 생성자의 세 번째 인자로 선택하며 LRU 캐시의 바탕이 된다.
    후입선출(LIFO, last in first out)
    가장 나중에 넣은 것이 가장 먼저 나오는 규칙. 스택의 정의이고 메서드 호출과 반환의 순서가 이 규칙을 따른다.
    선입선출(FIFO, first in first out)
    가장 먼저 넣은 것이 가장 먼저 나오는 규칙. 일반적인 큐의 순서다. 우선순위 큐처럼 이 순서를 따르지 않는 큐도 있다.
    덱(deque, double ended queue)
    양쪽 끝 모두에서 넣고 꺼낼 수 있는 자료 구조. 한쪽 끝만 쓰면 스택, 넣는 끝과 꺼내는 끝을 나누면 큐가 된다.
    원형 배열(circular array)
    마지막 칸 다음이 0번 칸이라고 약속하고 쓰는 배열. 시작 위치와 끝 위치를 인덱스로 관리해, 앞쪽에서 요소를 꺼내도 나머지를 당기지 않는다.
