    타입 변수에 대해 컴파일러가 아는 것

    앞 회차에서 제네릭 타입을 만들었다. 클래스 이름 뒤에 를 붙여 타입 매개변수(type parameter)를 선언하고, 쓰는 쪽에서 ArrayList처럼 타입 인자(type argument)를 넣는다. 그러면 컴파일러가 넣는 값의 타입을 검사하고, 꺼내는 자리에 필요한 캐스트를 대신 넣어 준다. 여기까지는 제네릭 타입을 바깥에서 쓰는 사람의 이야기였다.

    이 회차는 방향을 바꿔 제네릭 타입을 안에서 만드는 사람의 자리에 선다. 클래스 본문에서 T 타입의 변수를 손에 쥐었을 때 그것으로 무엇을 할 수 있는가. T가 무엇이 될지는 쓰는 사람이 정하므로, 본문을 컴파일하는 시점의 컴파일러는 T에 대해 아는 것이 거의 없다. 아는 것이 없으면 허용할 수 있는 연산도 없다. 제네릭을 조금만 깊이 쓰려고 하면 곧바로 이 벽에 부딪힌다.

    이 회차에서 다루는 네 가지는 모두 이 벽과 관련이 있다. 타입 매개변수 제한은 컴파일러에게 T에 대한 지식을 더 주는 방법이다. 제네릭 메서드는 타입 매개변수를 클래스가 아니라 메서드 하나에 붙여 호출할 때마다 타입 인자를 정하게 한다. 와일드카드는 반대로 "타입 인자가 무엇인지 모른다"는 사실을 타입으로 적는 방법이다. 마지막으로 타입 소거는 컴파일러가 이 모든 검사를 끝낸 뒤 클래스 파일에 무엇을 남기고 무엇을 지우는지에 대한 규칙이다.

    용어를 먼저 맞춰 둔다. 이 회차에서는 다음 다섯 단어를 구분해서 쓴다.

    용어예뜻
    제네릭 타입(generic type)class Holder타입 매개변수를 선언한 클래스나 인터페이스
    타입 변수(type variable)T선언 안에서 타입 자리에 쓰는 이름. 타입 매개변수로 선언된다
    타입 인자(type argument)Rect사용하는 쪽에서 타입 변수 자리에 넣는 타입
    매개변수화 타입(parameterized type)Holder제네릭 타입에 타입 인자를 넣어 만든 타입

    예제는 처음부터 끝까지 도형 세 개를 쓴다. 넓이를 계산할 수 있는 추상 클래스 Shape와, 그 하위 클래스인 사각형 Rect, 삼각형 Tri다. 실행 결과가 정수로 떨어지도록 넓이는 int로 계산한다. Rect에만 width() 메서드가 하나 더 있다는 점을 기억해 두자. 반환된 객체가 정말 Rect 타입으로 다뤄지는지 확인할 때 쓴다.

    abstract class Shape {
    abstract int area();
    String name() { return getClass().getSimpleName(); }
}

class Rect extends Shape {
    private final int w, h;
    Rect(int w, int h) { this.w = w; this.h = h; }
    int area() { return w * h; }
    int width() { return w; }          // Rect에만 있는 메서드
}

class Tri extends Shape {
    private final int base, height;
    Tri(int base, int height) { this.base = base; this.height = height; }
    int area() { return base * height / 2; }
}

    출발점: 타입마다 만든 클래스와 다형성 시도

    만들려는 것은 도형 하나를 담아 두는 보관함이다. 요구 사항은 세 가지다. 도형을 넣을 수 있고(put), 담긴 도형의 넓이를 알려 주고(areaOf), 다른 도형을 받아 담긴 도형과 비교한 뒤 넓이가 더 큰 쪽을 돌려준다(larger). 뒤의 두 메서드가 중요하다. areaOf는 담긴 객체의 메서드를 호출해야 하고, larger는 담긴 것과 같은 타입의 객체를 돌려줘야 한다.

    타입마다 클래스를 만든다

    가장 단순한 방법은 사각형용 보관함과 삼각형용 보관함을 따로 만드는 것이다.

    class RectHolder {
    private Rect item;
    void put(Rect item) { this.item = item; }
    int areaOf() { return item.area(); }
    Rect larger(Rect other) { return item.area() >= other.area() ? item : other; }
}
// TriHolder는 위 코드에서 Rect를 Tri로 바꾼 것과 같다.

    이 방식은 타입에 관해서는 흠이 없다. RectHolder에 삼각형을 넣으려 하면 컴파일 오류가 나고, larger가 돌려준 값은 캐스트 없이 Rect 변수에 담긴다. 문제는 두 클래스의 본문이 타입 이름만 빼고 글자 하나까지 같다는 것이다. 도형이 열 종류가 되면 같은 코드를 열 번 복사해야 하고, 비교 규칙을 바꾸려면 열 군데를 고쳐야 한다.

    다형성으로 하나로 합친다

    두 타입에는 공통 상위 타입 Shape가 있고, 보관함이 쓰는 메서드 area()는 Shape에 선언되어 있다. 그러면 Rect 자리에 Shape를 적은 클래스 하나로 충분해 보인다.

    class ShapeHolder {
    private Shape item;
    void put(Shape item) { this.item = item; }
    int areaOf() { return item.area(); }
    Shape larger(Shape other) { return item.area() >= other.area() ? item : other; }
}

    코드는 한 벌로 줄었다. 대신 타입에 관한 약속 두 가지가 사라졌다. 사각형 전용으로 쓰려던 보관함을 다음과 같이 사용해 보자.

    ShapeHolder rectHolder = new ShapeHolder();
rectHolder.put(new Rect(4, 5));
rectHolder.put(new Tri(6, 4));                      // ① 사각형 보관함에 삼각형이 들어간다
Rect r = rectHolder.larger(new Rect(2, 3));         // ② 컴파일 오류

    ①은 아무 경고 없이 컴파일된다. put의 매개변수 타입이 Shape이고 Tri는 Shape이기 때문이다. 변수 이름을 rectHolder라고 지은 것은 사람끼리의 약속일 뿐 컴파일러는 알지 못한다. ②는 반대 방향의 문제다. larger의 반환 타입이 Shape이므로 컴파일러는 incompatible types: Shape cannot be converted to Rect라는 오류를 낸다. 호출하는 사람은 사각형이 돌아올 것이라고 믿지만 그 믿음을 타입으로 적을 방법이 없다.

    ②를 통과하려면 다운캐스트를 직접 적어야 한다. 그리고 그 캐스트는 ① 때문에 실패한다.

    Rect r = (Rect) rectHolder.larger(new Rect(2, 3));  // 컴파일은 된다
System.out.println(r.width());
    Exception in thread "main" java.lang.ClassCastException: class Tri cannot be cast to class Rect (Tri and Rect are in unnamed module of loader 'app')

    한 줄씩 따라가 보자. 두 번째 put이 item을 넓이 12인 삼각형으로 바꿔 놓았다. larger는 12와 인자의 넓이 6을 비교해 item, 곧 삼각형을 돌려준다. 캐스트 연산은 실행 시점에 객체의 실제 클래스를 확인하므로 Tri를 Rect로 바꾸려는 순간 예외가 난다. 잘못은 삼각형을 넣은 줄에서 일어났는데, 프로그램은 꺼내는 줄에서 죽는다.

    방식코드 재사용잘못된 타입을 넣을 때꺼낸 값의 타입

    원하는 것은 첫 줄의 타입 안전성과 둘째 줄의 재사용을 함께 얻는 것이다. 앞 회차에서 배운 대로라면 답은 제네릭이다.

    제네릭을 도입했는데 컴파일되지 않는다

    Shape 자리를 타입 매개변수 T로 바꾼다.

    class Holder {
    private T item;
    void put(T item) { this.item = item; }
    int areaOf() { return item.area(); }
    T larger(T other) { return item.area() >= other.area() ? item : other; }
}

    오류 문구의 마지막 줄이 원인을 말해 준다. 컴파일러는 T를 T extends Object로 보고 있다. JLS 4.4는 타입 매개변수로 선언된 모든 타입 변수에 경계(bound)가 있고, 경계를 적지 않으면 Object로 간주한다고 정한다. 그리고 타입 변수의 멤버는 그 경계 타입의 멤버다. 따라서 경계가 Object인 T 타입의 변수로 호출할 수 있는 메서드는 toString(), equals(), hashCode(), getClass()처럼 Object에 선언된 것뿐이다. area()는 거기에 없다.

    컴파일러가 이렇게 엄격한 데에는 이유가 있다. Holder의 본문은 타입 인자가 정해지기 전에, 선언된 자리에서 한 번만 검사된다. 그 검사는 앞으로 누가 어떤 타입 인자를 넣더라도 성립해야 한다. Holder라면 item.area()가 말이 되지만 Holder이나 Holder에서는 말이 되지 않는다. 그리고 지금의 선언은 그런 사용을 막지 않는다.

    Holder h = new Holder<>();   // 경계 없는 Holder라면 허용된다
h.put(10);                            // "도형 보관함"에 정수가 들어간다

    그래서 이 실패에는 두 얼굴이 있다. 클래스 안에서는 T의 메서드를 부를 수 없고, 클래스 밖에서는 도형이 아닌 타입을 타입 인자로 넣을 수 있다. 둘은 같은 원인에서 나온다. 선언이 T에 대해 아무것도 약속하지 않았기 때문에, 컴파일러는 안쪽에서는 아무것도 믿을 수 없고 바깥쪽에서는 아무것도 막을 수 없다.

    경계 없는 T가 쓸모없다는 뜻은 아니다. 담아 두었다가 돌려주기만 하는 컨테이너는 원소의 메서드를 부를 일이 없으므로 Object의 멤버만으로 충분하다. ArrayList가 그런 경우다. 경계가 필요해지는 것은 제네릭 코드가 원소에게 일을 시켜야 할 때다.

    타입 매개변수 제한: 상한 경계

    부족한 것은 "T는 도형이다"라는 약속 하나다. 타입 매개변수 선언에 extends를 붙여 그 약속을 적는다. 이것을 상한 경계(upper bound)라고 하고, 경계가 붙은 타입 매개변수를 한정된 타입 매개변수(bounded type parameter)라고 한다.

    class Holder {
    private T item;
    void put(T item) { this.item = item; }
    int areaOf() { return item.area(); }
    T larger(T other) { return item.area() >= other.area() ? item : other; }
}

    본문은 한 글자도 바뀌지 않았고 선언부의 extends Shape만 추가되었다. 이제 컴파일된다. 사용하는 코드와 결과는 다음과 같다.

    public class Main {
    public static void main(String[] args) {
        Holder rectHolder = new Holder<>();
        rectHolder.put(new Rect(4, 5));
        System.out.println(rectHolder.areaOf());
        Rect r = rectHolder.larger(new Rect(2, 3));   // 캐스트 없이 Rect
        System.out.println(r.width());

        Holder triHolder = new Holder<>();
        triHolder.put(new Tri(6, 4));
        Tri t = triHolder.larger(new Tri(10, 4));
        System.out.println(t.name() + " " + t.area());
    }
}

    첫 줄은 4×5 사각형의 넓이다. 둘째 줄에서 larger는 넓이 20과 6을 비교해 담겨 있던 사각형을 돌려주고, 그 반환값에 곧바로 width()를 호출할 수 있다. 셋째 줄에서는 담긴 삼각형(넓이 12)보다 인자로 준 삼각형(넓이 20)이 크므로 인자가 돌아온다.

    경계 하나가 세 가지를 바꿨다.

    1. 클래스 안쪽. T의 경계가 Shape가 되었으므로 T 타입 변수의 멤버는 Shape의 멤버다. item.area()와 item.name()을 호출할 수 있다. Rect에만 있는 width()는 여전히 호출할 수 없다. T가 Tri일 수도 있기 때문이다.
    2. 클래스 바깥쪽. 타입 인자는 경계의 하위 타입이어야 한다. Holder, Holder, 그리고 경계 자신인 Holder는 되고 Holder는 안 된다.
    3. 타입 인자별 검사는 그대로. Holder의 put은 Rect만 받고 larger는 Rect를 돌려준다. 다형성 버전이 잃었던 두 약속이 돌아왔다.
    Holder h1 = new Holder<>();   // 오류 ①
Holder h2 = new Holder<>();
h2.put(new Tri(6, 4));                 // 오류 ②
    error: type argument Integer is not within bounds of type-variable T
error: incompatible types: Tri cannot be converted to Rect

    문법에서 두 가지를 짚어 둔다. 첫째, 경계에 쓰는 키워드는 경계가 클래스든 인터페이스든 extends다. T extends Comparable처럼 인터페이스를 경계로 둘 때도 implements라고 쓰지 않는다. 여기서 extends는 "하위 타입이다"라는 뜻으로 읽으면 된다. 둘째, 경계는 여러 개를 &로 이어 적을 수 있다. T extends Shape & Comparable는 "도형이면서 자기 자신과 비교할 수 있는 타입"이다. JLS 4.4는 클래스 타입이나 타입 변수는 첫 자리에만 올 수 있다고 정한다. 그러니 클래스가 있으면 맨 앞에 적고 인터페이스를 뒤에 잇는다. 경계가 여러 개일 때 T의 멤버는 그 타입들을 모두 합친 교차 타입(intersection type)의 멤버다.

    일상에서 가져온 비유지원 자격을 적은 채용 공고

    경계 없는 T는 "누구나 지원 가능"이라고 적힌 공고와 같다. 누가 올지 모르니 맡길 수 있는 일은 누구나 할 수 있는 일뿐이다. "운전면허 소지자"라고 자격을 적으면 지원자는 줄어들지만, 뽑힌 사람에게 운전을 맡길 수 있다. 경계는 받아들이는 타입을 좁히는 대가로 그 타입에게 시킬 수 있는 일을 넓힌다. 비유가 맞지 않는 지점도 있다. 공고의 자격 심사는 지원할 때마다 하지만, 제네릭 클래스의 본문 검사는 선언 시점에 한 번만 하고 타입 인자가 경계 안에 있는지만 사용할 때마다 확인한다.

    경계는 클래스 파일에 어떻게 남는가

    class Holder {
  private T item;
    descriptor: LShape;

  void put(T);
    descriptor: (LShape;)V

  int areaOf();
    descriptor: ()I
    Code:
       0: aload_0
       1: getfield      #7                  // Field item:LShape;
       4: invokevirtual #13                 // Method Shape.area:()I
       7: ireturn

  T larger(T);
    descriptor: (LShape;)LShape;
}

    descriptor는 JVM이 필드와 메서드의 타입을 식별하는 데 쓰는 문자열이다. 필드 item의 디스크립터는 LShape;, 곧 Shape 타입의 참조다. areaOf의 본문은 Shape.area를 invokevirtual로 호출한다. 경계가 없던 버전을 같은 방법으로 열면 같은 자리에 Ljava/lang/Object;가 적혀 있다. 컴파일러가 타입 변수를 그 경계로 바꿔서 클래스 파일을 만든다는 뜻이다. 이것이 뒤에서 다룰 타입 소거의 한 조각이다.

    사용하는 쪽의 바이트코드도 본다. Rect r = rectHolder.larger(new Rect(2, 3)); 한 줄은 다음 명령으로 번역된다.

          41: invokevirtual #35                 // Method Holder.larger:(LShape;)LShape;
      44: checkcast     #10                 // class Rect
      47: astore_2

    larger가 돌려주는 값의 타입은 클래스 파일 수준에서는 Shape다. 그것을 Rect 변수에 넣기 위해 컴파일러가 checkcast Rect를 끼워 넣었다. 다형성 버전에서 사람이 손으로 적던 (Rect)와 같은 명령이다. 차이는 누가 적었느냐와 실패할 수 있느냐에 있다. 손으로 적은 캐스트는 누군가 삼각형을 넣어 두었으면 실패한다. 컴파일러가 넣은 캐스트는, 컴파일러가 이 보관함에 Rect만 들어가도록 모든 put 호출을 검사해 두었기 때문에 실패하지 않는다. 이 보장이 깨지는 예외적인 길은 뒤에서 로 타입과 힙 오염을 다룰 때 본다.

    소스 (컴파일러가 검사하는 것)             클래스 파일 (JVM이 실행하는 것)
───────────────────────────────────      ───────────────────────────────────────────
class Holder {          class Holder {
    private T item;                          Shape item;                 // LShape;
    void put(T item)                         void  put(Shape)            // (LShape;)V
    T larger(T other)                        Shape larger(Shape)         // (LShape;)LShape;
}                                        }

Holder h = new Holder<>();         new Holder
h.put(new Rect(4, 5));                   invokevirtual Holder.put:(LShape;)V
Rect r = h.larger(new Rect(2, 3));       invokevirtual Holder.larger:(LShape;)LShape;
                                         checkcast Rect               ← 컴파일러가 삽입
    소스에서는 T로 적힌 자리가 클래스 파일에서는 경계 타입 Shape로 바뀌고, 사용 지점에는 컴파일러가 checkcast를 넣는다는 대응을 좌우로 나란히 보여 준다. 흰 배경의 깔끔한 기술 다이어그램. 화면을 좌우 두 칸으로 나눈다. 왼쪽 칸 제목 "소스: 컴파일러가 검사", 오른쪽 칸 제목 "클래스 파일: JVM이 실행". 왼쪽 칸 위쪽에 둥근 상자 하나가 있고 안에 세 줄: "class Holder<T extends Shape>", "T item", "T larger(T other)". 오른쪽 칸 위쪽에 같은 크기의 둥근 상자가 있고 안에 세 줄: "class Holder", "Shape item", "Shape larger(Shape)". 왼쪽 상자의 글자 T 세 개를 주황색으로 칠하고, 각 T에서 오른쪽 상자의 대응하는 Shape로 가는 얇은 주황 화살표를 그린다. 화살표 묶음 위에 라벨 "타입 변수를 경계로 바꾼다". 왼쪽 칸 아래쪽에 코드 한 줄 상자 "Rect r = h.larger(new Rect(2, 3));". 오른쪽 칸 아래쪽에 세로로 쌓인 작은 상자 두 개: "invokevirtual Holder.larger" 와 "checkcast Rect". "checkcast Rect" 상자만 파란색 테두리로 강조하고 옆에 말풍선 "컴파일러가 삽입". 왼쪽 아래 코드 상자에서 오른쪽 아래 두 상자로 회색 화살표. 색은 주황과 파랑 두 가지만 쓰고 선은 얇게. 타입 변수는 클래스 파일에서 경계 타입으로 바뀌고, 정확한 타입이 필요한 사용 지점에는 캐스트가 들어간다.

    제네릭 메서드

    지금까지는 타입 매개변수를 클래스에 선언했다. 타입 매개변수는 메서드 하나에만 선언할 수도 있다. JLS 8.4.4는 타입 변수를 하나 이상 선언한 메서드를 제네릭 메서드(generic method)라고 정의한다. 타입 매개변수 목록은 반환 타입 앞에 적는다.

    class ShapeUtil {
    static  T first(T a, T b) { return a; }

    static  T larger(T a, T b) {
        return a.area() >= b.area() ? a : b;
    }
}

    static T first(T a, T b)를 왼쪽부터 읽으면 이렇다. 는 "이 메서드는 타입 매개변수 T를 선언한다"는 뜻이고, 그 뒤의 T는 반환 타입이며, 괄호 안의 두 T는 매개변수 타입이다. 선언과 사용이 같은 글자라서 처음에는 헷갈리지만, 꺾쇠 안에 있는 것만 선언이다. larger처럼 제네릭 메서드의 타입 매개변수에도 경계를 둘 수 있고, 효과는 클래스에서와 같다.

    제네릭 타입과 제네릭 메서드는 타입 인자가 정해지는 시점이 다르다. 제네릭 타입의 타입 인자는 Holder라고 타입을 적는 순간 정해지고, 그 변수로 하는 모든 호출에 똑같이 적용된다. 제네릭 메서드의 타입 인자는 호출할 때마다 따로 정해진다. 같은 larger를 한 번은 T = Rect로, 다음 줄에서는 T = Tri로 호출할 수 있다.

    명시적 타입 인자와 타입 추론

    호출할 때 타입 인자를 직접 적으려면 메서드 이름 바로 앞에 꺾쇠를 둔다. 대부분은 적지 않아도 된다. JLS 8.4.4의 표현대로 타입 인자는 추론될 수 있는 경우가 많기 때문이다. 컴파일러가 인자의 타입과 결과를 받는 쪽의 타입을 보고 타입 인자를 정하는 것을 타입 추론(type inference)이라고 하며, 규칙은 JLS 18장에 있다.

    Rect r1 = ShapeUtil.larger(new Rect(1, 1), new Rect(2, 3));  // 명시
Rect r2 = ShapeUtil.larger(new Rect(4, 5), new Rect(2, 3));        // 추론: T = Rect
Shape s = ShapeUtil.larger(new Rect(4, 5), new Tri(10, 10));       // 추론: T = Shape
System.out.println(r1.width() + " " + r2.width() + " " + s.name());
    2 4 Tri

    세 번째 호출이 추론의 동작을 잘 보여 준다. 인자가 Rect와 Tri이므로 T는 둘 모두의 상위 타입이어야 한다. 선언된 경계 때문에 T는 Shape의 하위 타입이어야 하고, 결과를 Shape 변수에 넣으므로 그 점에서도 Shape의 하위 타입이어야 한다. 이 조건을 모두 만족하는 타입은 Shape다. 넓이 20과 50을 비교해 삼각형이 돌아오므로 Tri가 출력된다.

    같은 호출의 결과를 Rect 변수에 받으려 하면 조건이 서로 충돌한다. 컴파일러는 모은 제약을 그대로 보여 준다.

    Rect bad = ShapeUtil.larger(new Rect(4, 5), new Tri(10, 10));
    error: incompatible types: inference variable T has incompatible bounds
        Rect bad = ShapeUtil.larger(new Rect(4, 5), new Tri(10, 10));
                                   ^
    upper bounds: Rect,Shape
    lower bounds: Tri,Rect
  where T is a type-variable:
    T extends Shape declared in method larger(T,T)

    읽는 법은 이렇다. lower bounds는 "T는 적어도 이 타입들의 상위 타입이어야 한다"는 제약으로, 인자 Tri와 Rect에서 나왔다. upper bounds는 "T는 이 타입들의 하위 타입이어야 한다"는 제약으로, 대입 대상 Rect와 선언된 경계 Shape에서 나왔다. Tri의 상위 타입이면서 Rect의 하위 타입인 타입은 없으므로 추론이 실패한다. 도형이 아닌 것을 넘기는 ShapeUtil.larger(1, 2)도 같은 형식으로 거절된다. 이때는 상한이 Shape, 하한이 Integer라고 나온다.

    "두 인자의 타입이 다르면 first(T a, T b)를 호출할 수 없다"고 생각하기 쉽지만 그렇지 않다. ShapeUtil.first(1, "a")는 컴파일된다. 컴파일러가 Integer와 String의 공통 상위 타입을 찾아 T로 삼기 때문이다. 두 인자가 같은 타입이기를 강제하고 싶다면 타입 매개변수만으로는 부족하고, 결과를 받는 쪽의 타입이나 경계로 제약을 더해야 한다.

    static 메서드는 클래스의 타입 매개변수를 쓸 수 없다

    제네릭 클래스 안에 static 메서드를 두고 클래스의 T를 쓰려 하면 컴파일되지 않는다.

    class Cell {
    private T value;
    static T shared;                       // 오류
    static T make() { return null; }       // 오류
    static  U pass(U u) { return u; }   // 된다: 메서드가 자기 타입 매개변수를 선언
}
    error: non-static type variable T cannot be referenced from a static context

    이유는 타입 인자가 어디에 붙는지를 생각하면 나온다. 클래스의 T는 Cell 타입의 변수, Cell 타입의 변수처럼 매개변수화 타입마다 다르게 정해진다. 반면 static 멤버는 인스턴스와 무관하게 클래스에 하나만 있다. JLS 8.1.2는 한 제네릭 클래스에서 나온 모든 매개변수화 타입이 실행 시점에 같은 클래스 하나를 공유한다고 적는다. Cell.make()라고 호출하는 자리에는 T를 정해 줄 타입 인자가 없다. 그래서 static 메서드가 타입 매개변수를 쓰려면 스스로 선언한 제네릭 메서드여야 한다.

    인스턴스 메서드는 둘 다 쓸 수 있다. 클래스의 타입 매개변수도 보이고, 자기만의 타입 매개변수도 추가로 선언할 수 있다. JDK의 Collection에 있는 T[] toArray(T[] a)가 그 예다. E는 컬렉션이 만들어질 때 정해진 원소 타입이고, T는 toArray를 호출할 때마다 넘긴 배열에 따라 정해진다.

    한 가지 함정이 있다. 메서드가 선언한 타입 매개변수의 이름이 클래스의 것과 같으면, 메서드 안에서는 메서드의 것이 클래스의 것을 가린다.

    class Cell {
    private T value;
     void assign(T t) { value = t; }   // 이 T는 클래스의 T가 아니다
}
    error: incompatible types: T#1 cannot be converted to T#2
  where T#1,T#2 are type-variables:
    T#1 extends Object declared in method assign(T#1)
    T#2 extends Object declared in class Cell

    컴파일러가 이름 뒤에 #1, #2를 붙여 두 T가 서로 다른 타입 변수임을 알려 준다. 이런 혼동을 피하려면 메서드의 타입 매개변수에는 클래스의 것과 다른 글자를 쓴다.

    호출 지점의 바이트코드

    제네릭 메서드도 클래스 파일에서는 경계로 바뀐다. first의 디스크립터는 (Ljava/lang/Object;Ljava/lang/Object;)Ljava/lang/Object;이고 larger는 (LShape;LShape;)LShape;다. 호출하는 쪽은 다음과 같다.

    // Rect r1 = ShapeUtil.larger(new Rect(1, 1), new Rect(2, 3));
      18: invokestatic  #12                 // Method ShapeUtil.larger:(LShape;LShape;)LShape;
      21: checkcast     #7                  // class Rect

// Rect r2 = ShapeUtil.larger(new Rect(4, 5), new Rect(2, 3));
      43: invokestatic  #12                 // Method ShapeUtil.larger:(LShape;LShape;)LShape;
      46: checkcast     #7                  // class Rect

    두 호출의 명령이 같다. 소스에 적은 는 바이트코드 어디에도 남지 않는다. "타입 인자"라는 이름 때문에 메서드에 무언가가 전달된다고 생각하기 쉽지만, 타입 인자는 실행 시점에 넘어가는 값이 아니다. 컴파일러가 타입 검사를 하고 checkcast를 넣을 타입을 정하는 데만 쓰이고 사라진다. 결과를 Shape 변수에 받는 세 번째 호출에는 checkcast도 없다. 반환값의 클래스 파일상 타입이 이미 Shape이기 때문이다.

    제네릭 메서드 활용: 경계와 비교

    제네릭 메서드가 가장 흔히 쓰이는 곳은 "인자의 타입과 반환 타입 사이의 관계"를 적어야 하는 유틸리티다. 두 값 가운데 큰 쪽을 돌려주는 메서드를 보자. 크기를 비교하려면 원소가 compareTo를 가져야 하므로 경계가 필요하다.

    static > T max(T a, T b) {
    return a.compareTo(b) >= 0 ? a : b;
}

    경계 T extends Comparable 안에 T 자신이 다시 나온다. 이것은 순환 오류가 아니라 "T는 T끼리 비교할 수 있는 타입"이라는 조건이다. String은 Comparable을 구현하고 Integer는 Comparable를 구현하므로 둘 다 이 경계를 만족한다.

    String m = ShapeUtil.max("apple", "banana");   // T = String
Integer i = ShapeUtil.max(3, 7);               // T = Integer
System.out.println(m + " " + i);
    banana 7

    이 선언이 막아 주는 것을 확인해 보자. ShapeUtil.max(1, "a")는 컴파일되지 않는다. 앞의 first(1, "a")와 달리 이번에는 경계가 있어서, Integer와 String을 함께 담으면서 자기 자신과 비교 가능한 T를 찾을 수 없기 때문이다. 타입 매개변수의 경계가 타입 추론의 제약으로 작동해 의미 없는 비교를 컴파일 시점에 걸러 낸 것이다.

    두 번째 호출의 바이트코드에는 Integer.valueOf가 두 번 나온다. 타입 인자는 참조 타입이어야 하므로(JLS 4.5.1) 기본형 3과 7은 호출 전에 Integer 객체로 박싱된다. Holder처럼 기본형을 타입 인자로 직접 쓰면 unexpected type, required: reference, found: int라는 오류가 난다. 클래스 파일에서 T 자리가 Object나 경계 타입의 참조로 바뀐다는 것을 떠올리면, 참조가 아닌 값이 그 자리에 들어갈 수 없다는 것도 자연스럽다.

    제네릭 타입으로 할 것인가, 제네릭 메서드로 할 것인가

    둘 가운데 무엇을 고를지는 타입 매개변수가 무엇에 묶여야 하는지로 정한다. Holder의 T는 필드 item의 타입이다. 객체가 살아 있는 동안 put과 larger가 같은 T를 써야 하므로 타입 매개변수가 객체의 상태에 묶여 있다. 이런 경우는 제네릭 타입이다. 반면 max는 상태가 없고, 한 번의 호출 안에서 두 인자와 반환값의 타입이 같다는 것만 표현하면 된다. 이런 경우는 제네릭 메서드다.

    둘을 섞을 수도 있다. 제네릭 클래스의 인스턴스 메서드가 클래스의 T와 관계없는 타입을 한 번의 호출에서만 필요로 한다면 그 메서드에만 타입 매개변수를 추가한다. 타입 매개변수의 범위는 가능한 한 좁게 잡는 편이 읽기 쉽다. 클래스 전체에 를 선언해 놓고 메서드 하나에서만 V를 쓰면, 그 클래스를 쓰는 모든 곳에서 의미 없는 세 번째 타입 인자를 적어야 한다.

    제네릭 타입은 무공변이다

    이제 방향을 바꿔 제네릭 타입을 매개변수로 받는 메서드를 쓴다. 도형 리스트를 받아 넓이의 합을 구하는 메서드다.

    static int totalArea(List shapes) {
    int sum = 0;
    for (Shape s : shapes) sum += s.area();
    return sum;
}

List rects = new ArrayList<>();
rects.add(new Rect(4, 5));
totalArea(rects);        // 컴파일 오류
    error: incompatible types: List cannot be converted to List

    Rect는 Shape의 하위 타입인데 List는 List의 하위 타입이 아니다. 처음 보면 불합리하게 느껴지지만 이유가 있다. 이 변환이 허용된다고 가정하고 한 줄씩 따라가 보자.

    List rects = new ArrayList<>();
List shapes = rects;        // 허용된다고 가정한다
shapes.add(new Tri(6, 4));         // List에 Tri를 넣는 것은 정당하다
Rect r = rects.get(0);             // Rect 리스트에서 Tri가 나온다

    둘째 줄 이후 rects와 shapes는 힙의 같은 리스트 객체를 가리킨다. 셋째 줄은 List의 규칙으로는 아무 문제가 없다. 그런데 그 결과 List라고 선언한 리스트 안에 삼각형이 들어간다. 넷째 줄에서 컴파일러가 믿고 넣은 캐스트가 실패한다. 다형성 버전의 보관함에서 본 것과 같은 사고다. 읽기만 한다면 List를 List로 다뤄도 안전하지만, List에는 쓰는 메서드가 있으므로 컴파일러는 변환 자체를 막는다.

    이 성질에는 이름이 있다. 타입 A가 B의 하위 타입일 때 G도 G의 하위 타입이면 G는 공변(covariant)이다. 방향이 뒤집혀 G가 G의 하위 타입이면 반공변(contravariant)이고, 어느 쪽도 아니면 무공변(invariant)이다. 자바의 제네릭 타입은 타입 인자가 구체적인 타입일 때 무공변이다. JLS 4.10.2가 정한 List의 상위 타입 목록에는 Collection와 로 타입 List는 있지만 List는 없다.

    배열은 다른 선택을 했다

    자바의 배열은 공변이다. String[]은 Object[]의 하위 타입이다. 그러면 방금 본 사고가 배열에서는 실제로 일어날 수 있어야 한다.

    Object[] objs = new String[1];     // 배열은 공변이라 허용된다
objs[0] = 1;                       // 컴파일된다
    Exception in thread "main" java.lang.ArrayStoreException: java.lang.Integer

    컴파일은 되고 실행 중에 ArrayStoreException이 난다. JLS 10.5는 참조 타입 배열의 원소에 값을 대입할 때마다 그 값이 배열의 원소 타입에 대입 가능한지 실행 시점에 검사한다고 정한다. 이 검사가 가능한 것은 배열 객체가 자신의 원소 타입을 실행 시점에 알고 있기 때문이다. new String[1]로 만든 객체는 변수의 타입이 Object[]여도 스스로 String[]임을 안다.

    두 설계를 나란히 놓으면 이렇다. 배열은 공변을 허용하고 그 대가로 저장할 때마다 실행 시점 검사를 한다. 제네릭은 실행 시점 검사를 할 수 없어서 컴파일 시점에 변환을 막는다. 제네릭이 실행 시점 검사를 할 수 없는 이유는 ArrayList로 만든 객체가 자기 원소 타입이 Rect라는 사실을 갖고 있지 않기 때문이다. 이 사실은 타입 소거에서 확인한다. 그 전에, 무공변 때문에 생긴 불편을 푸는 도구부터 본다.

    와일드카드 1: 상한 와일드카드와 캡처

    totalArea가 받고 싶은 것을 정확히 적으면 "Shape의 리스트"가 아니라 "Shape이거나 그 하위 타입인 어떤 타입의 리스트"다. 이것을 적는 방법은 두 가지다. 첫째는 앞에서 배운 제네릭 메서드다.

    static  int totalArea(List shapes) {
    int sum = 0;
    for (T s : shapes) sum += s.area();
    return sum;
}

    호출할 때마다 T가 Rect, Tri, Shape로 추론되므로 세 종류의 리스트를 모두 받는다. 그런데 이 선언에서 T가 하는 일을 보면 굳이 이름을 붙일 이유가 없다. T는 매개변수 타입에 한 번 나올 뿐 다른 매개변수나 반환 타입과 묶이지 않는다. 본문에서도 Shape의 메서드만 쓴다. "무엇이든 좋으니 Shape의 하위 타입"이라는 뜻만 전하면 되는 자리다.

    둘째 방법은 이름을 붙이지 않고 그 뜻만 적는 것이다. 타입 인자 자리에 물음표를 쓴다.

    static int totalArea(List shapes) {
    int sum = 0;
    for (Shape s : shapes) sum += s.area();
    return sum;
}

List rects = new ArrayList<>(List.of(new Rect(4, 5), new Rect(2, 3)));
List tris = new ArrayList<>(List.of(new Tri(6, 4)));
List mixed = List.of(new Rect(1, 1), new Tri(2, 2));
System.out.println(totalArea(rects) + " " + totalArea(tris) + " " + totalArea(mixed));
    26 12 3

    ?를 와일드카드(wildcard)라고 한다. ? extends Shape는 "Shape의 하위 타입인 어떤 타입. 구체적으로 무엇인지는 모른다"로 읽고, 상한 와일드카드(upper bounded wildcard)라고 부른다. 세 호출이 모두 컴파일되고, 넓이의 합은 20+6, 12, 1+2다.

    와일드카드는 타입 매개변수가 아니라 타입 인자라는 점을 분명히 해 두자. 타입 매개변수 T는 선언하는 쪽이 만드는 이름이고, 와일드카드는 사용하는 쪽이 List<...>의 꺾쇠 안에 적는 것이다. 그래서 class Box { }는 expected라는 문법 오류가 된다. 객체를 만드는 식에도 쓸 수 없다. new ArrayList()는 unexpected type, required: class or interface without bounds라는 오류를 낸다. 와일드카드는 "모르는 타입"을 뜻하므로, 이미 만들어진 객체를 가리키는 변수·매개변수·필드의 타입에 쓰는 표기다.

    읽을 수 있는 것과 쓸 수 없는 것

    List 타입의 변수로 무엇을 할 수 있는지 네 줄로 확인한다.

    static void probe(List shapes) {
    Shape s = shapes.get(0);        // ① 된다
    Rect r = shapes.get(0);         // ② 오류
    shapes.add(new Rect(1, 1));     // ③ 오류
    shapes.add(null);               // ④ 된다
}
    error: incompatible types: CAP#1 cannot be converted to Rect
        Rect r = shapes.get(0);
                           ^
error: incompatible types: Rect cannot be converted to CAP#1
        shapes.add(new Rect(1, 1));
                   ^
  where CAP#1 is a fresh type-variable:
    CAP#1 extends Shape from capture of ? extends Shape

    오류 문구에 CAP#1이라는 낯선 이름이 나온다. 컴파일러는 와일드카드가 든 타입의 식을 검사할 때 ? 자리에 이름 없는 새 타입 변수를 하나 만들어 넣는다. JLS 5.1.10은 이것을 캡처 변환(capture conversion)이라고 부른다. List는 검사하는 동안 List로 다뤄지고, CAP#1은 "상한이 Shape인, 정체를 모르는 타입 하나"다. 문구의 fresh type-variable이 이 새 타입 변수이고, CAP#1 extends Shape가 그 상한이다.

    네 줄을 List의 눈으로 다시 읽어 보자. get의 반환 타입은 CAP#1이다. CAP#1이 무엇이든 Shape의 하위 타입이므로 ①은 된다. Rect의 하위 타입이라는 보장은 없으므로 ②는 안 된다. add의 매개변수 타입도 CAP#1이다. Rect가 CAP#1의 하위 타입인지는 알 수 없다. CAP#1의 정체가 Tri일 수도 있기 때문이다. 그래서 ③은 거절된다. ④의 null은 어떤 참조 타입의 변수에도 넣을 수 있는 값이라서 통과한다.

    ③을 막는 이유는 앞 장의 반례와 같다. 이 메서드에 List를 넘긴 호출자가 있다면 ③은 삼각형 리스트에 사각형을 넣는 코드가 된다. 메서드 본문은 한 번만 검사되므로 가능한 모든 인자에 대해 안전한 연산만 허용된다. 그 대가로 얻은 것이 List와 List를 모두 받는 유연함이다. List는 원소 타입의 값을 넣지 않겠다고 약속하고 공변을 얻은 타입이라고 볼 수 있다.

    ? extends를 "읽기 전용 리스트"로 외우면 절반만 맞다. 막히는 것은 매개변수 타입이 캡처된 타입 변수인 메서드에 값을 넘기는 일이다. shapes.remove(0)이나 shapes.clear()는 원소 타입의 값을 받지 않으므로 그대로 컴파일된다. 리스트를 변경하지 못하게 하려는 목적이라면 와일드카드가 아니라 List.copyOf 같은 불변 리스트를 써야 한다.

    비한정 와일드카드

    ?만 쓰면 비한정 와일드카드(unbounded wildcard)다. JLS 4.5.1은 ? extends Object가 ?와 같다고 적는다. 따라서 규칙은 상한 와일드카드와 같고 상한만 Object다. List에서 꺼낸 값은 Object로만 받을 수 있고, null 말고는 넣을 수 없다. 원소가 무엇이든 상관없는 코드에 맞는다. size()처럼 원소 타입과 무관한 메서드나, toString()처럼 Object에 있는 메서드만 쓰는 경우다.

    static void printAll(List list) {
    for (Object o : list) System.out.print(o + " ");
    System.out.println();
}

printAll(List.of(1, "a", 2.5));     // 1 a 2.5
