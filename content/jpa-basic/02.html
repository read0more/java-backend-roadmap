    이 회차의 질문: persist를 불렀는데 왜 INSERT가 보이지 않는가

    JPA로 처음 코드를 짜 보면 이상한 장면을 여러 번 만난다. em.persist(member)를 호출한 줄에서 디버거를 멈추고 SQL 로그를 보면 INSERT가 없다. 그런데 바로 다음 줄에서 em.find()로 같은 키를 찾으면 객체가 나오고, SELECT도 나가지 않는다. 조회한 엔티티의 setter만 호출했는데 커밋하자 UPDATE가 나간다. 반대로 값을 분명히 바꿨는데 UPDATE가 나가지 않는 경우도 있다. 삭제를 먼저 호출하고 저장을 나중에 호출했는데 로그에는 INSERT가 DELETE보다 먼저 찍혀 유일 제약 위반이 난다.

    이 장면들은 모두 하나의 구조물에서 나온다. 엔티티 매니저 뒤에는 영속성 컨텍스트(persistence context)라는, 애플리케이션 메모리 안의 작업 공간이 있다. JPA의 저장·조회·수정·삭제 메서드는 데이터베이스를 직접 건드리지 않고 먼저 이 작업 공간을 건드린다. 데이터베이스와 맞추는 일은 플러시(flush)라는 별도의 순간에 몰아서 한다. 이 회차는 그 작업 공간이 메모리에서 어떤 자료구조로 생겼는지, 각 메서드가 그 자료구조에 무엇을 하는지, 플러시 순간에 그 자료구조가 어떤 순서로 SQL이 되는지를 따라간다.

    설명만으로 끝내지 않기 위해 실제로 실행한 결과를 근거로 쓴다. 실험 환경은 Java 21(Temurin 21.0.13), Hibernate ORM 6.6.53.Final, Jakarta Persistence API 3.1, H2 2.3.232 메모리 데이터베이스이고, Persistence.createEntityManagerFactory()로 JPA 표준 방식으로 부트스트랩했다. hibernate.show_sql=true로 Hibernate가 JDBC에 넘기는 SQL을 표준 출력에 찍었다. 실행 결과에 나오는 SQL 문자열의 별칭(m1_0)이나 열 순서는 이 버전의 Hibernate가 만든 것이며 버전에 따라 달라질 수 있다. 앞 회차에서 persistence.xml과 엔티티 매니저 팩토리를 만드는 방법을 다뤘으므로 여기서는 설정을 반복하지 않는다.

    실험에 쓰는 엔티티는 하나다. 기본 키를 애플리케이션이 직접 넣도록 했다. 키 생성 전략을 쓰면 시퀀스 호출 같은 SQL이 로그에 섞여서 이번 회차의 관찰 대상이 흐려지기 때문이다. 키 생성 전략이 쓰기 지연에 주는 영향은 이 회차 중간에 따로 본다.

    package hellojpa;

import jakarta.persistence.Entity;
import jakarta.persistence.Id;

@Entity
public class Member {
    @Id
    private Long id;
    private String name;
    private int age;

    protected Member() {}           // JPA가 리플렉션으로 쓰는 기본 생성자

    public Member(Long id, String name, int age) {
        this.id = id;
        this.name = name;
        this.age = age;
    }

    public Long getId() { return id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public int getAge() { return age; }
}

    엔티티 매니저 팩토리, 엔티티 매니저, 영속성 컨텍스트

    JPA 애플리케이션에는 수명이 다른 세 객체가 있다. 엔티티 매니저 팩토리(EntityManagerFactory)는 영속성 유닛 하나당 하나를 만든다. 만들 때 매핑 메타데이터를 읽고, 엔티티마다 SQL과 값 접근 방법을 준비하고, 커넥션 풀 같은 자원을 연다. 그래서 애플리케이션이 시작할 때 한 번 만들어 끝날 때까지 공유한다. 엔티티 매니저(EntityManager)는 작업 단위 하나를 처리할 때마다 만들고 닫는다. 웹 애플리케이션이라면 요청 하나, 또는 트랜잭션 하나가 작업 단위다.

    실험에서 두 객체의 실제 클래스를 찍어 보면 Hibernate가 JPA 인터페이스를 자기 고유 타입으로 구현했다는 것이 보인다.

    emf class = org.hibernate.internal.SessionFactoryImpl
em class = org.hibernate.internal.SessionImpl

    Hibernate의 고유 API에서 엔티티 매니저 팩토리는 SessionFactory, 엔티티 매니저는 Session이다. JPA가 표준이 되기 전부터 있던 이름이고, Hibernate 6에서는 Session이 EntityManager를 상속하므로 하나의 객체가 두 API를 모두 제공한다. 이 회차에서 Hibernate 내부를 들여다볼 때 SessionImplementor로 언랩(unwrap)하는 이유가 이것이다.

    영속성 컨텍스트는 객체라기보다 개념이다. Jakarta Persistence 3.1 명세 3.1절은 엔티티 매니저가 영속성 컨텍스트와 연결되어 있다고 하고, 영속성 컨텍스트를 "엔티티 인스턴스의 집합으로, 어떤 영속 엔티티 식별자에 대해서도 유일한 엔티티 인스턴스가 하나 있는 것"으로 정의한다. 핵심은 뒤쪽이다. 같은 테이블의 같은 기본 키, 즉 같은 데이터베이스 행에 대응하는 자바 객체가 한 영속성 컨텍스트 안에 두 개 생기지 않는다. 이 한 줄의 정의에서 1차 캐시와 동일성 보장이 나온다.

    엔티티 매니저와 영속성 컨텍스트가 늘 일대일인 것은 아니다. 명세 3.3절은 영속성 컨텍스트의 수명을 두 가지로 나눈다. 컨테이너가 관리하는 엔티티 매니저는 기본적으로 트랜잭션 범위(transaction-scoped) 영속성 컨텍스트를 쓴다. 트랜잭션이 시작되면 영속성 컨텍스트가 생기고 트랜잭션이 끝나면 사라진다. 애플리케이션이 emf.createEntityManager()로 직접 만든 엔티티 매니저는 확장(extended) 영속성 컨텍스트를 쓴다. 엔티티 매니저를 닫을 때까지 영속성 컨텍스트가 살아 있으므로 트랜잭션 여러 개에 걸칠 수 있다. 실제로 그런지 실험했다.

    EntityManager em = emf.createEntityManager();
em.getTransaction().begin();
em.persist(new Member(1L, "A", 20));
em.getTransaction().commit();
System.out.println("=== after commit, new tx, same em");

em.getTransaction().begin();
Member m = em.find(Member.class, 1L);
System.out.println("found without select? name=" + m.getName() + " contains=" + em.contains(m));
m.setName("B");
em.getTransaction().commit();
System.out.println("=== after 2nd commit");
em.close();

    첫 트랜잭션이 커밋된 뒤 두 번째 트랜잭션에서 find를 했는데 SELECT가 없다. 첫 트랜잭션에서 저장한 객체가 영속성 컨텍스트에 그대로 남아 있었기 때문이다. 그 객체를 바꾸자 두 번째 커밋에서 UPDATE도 나갔다. 직접 만든 엔티티 매니저에서는 커밋이 영속성 컨텍스트를 비우지 않는다는 뜻이다. 스프링이 주입하는 엔티티 매니저는 이와 달리 트랜잭션마다 영속성 컨텍스트를 새로 묶는 방식이고, 스프링 부트의 OSIV(open-session-in-view) 설정이 이 범위를 HTTP 요청 전체로 넓히는 문제는 「JPA 활용 2」에서 다룬다. 이 회차의 실험은 모두 직접 만든 엔티티 매니저 위에서 하므로, 영속성 컨텍스트를 비우고 싶을 때는 em.close()나 em.clear()를 명시적으로 부른다.

    엔티티 매니저를 스레드 사이에 공유하면 안 되는 이유도 이 구조에서 나온다. 영속성 컨텍스트는 내부에 해시 맵과 대기열을 품은 평범한 자바 객체이고 동기화 장치가 없다. Hibernate 소개 문서는 영속성 컨텍스트를 여러 스레드나 동시에 진행되는 트랜잭션 사이에서 절대 공유하면 안 된다고 강조한다. 두 요청 스레드가 같은 엔티티 매니저를 쓰면 한 스레드가 바꾼 엔티티를 다른 스레드의 커밋이 데이터베이스에 반영해 버리는 일이 생긴다. 반면 엔티티 매니저 팩토리는 애플리케이션 전체가 공유하라고 만든 객체다.

    엔티티의 네 가지 상태

    엔티티 객체는 자바 힙에 있는 평범한 객체다. 같은 클래스의 객체라도 영속성 컨텍스트와 어떤 관계에 있느냐에 따라 JPA가 다르게 취급한다. 명세 3.2절은 그 관계를 네 상태로 정의한다.

    상태명세의 정의(요지)영속성 컨텍스트와의 관계em.contains(e)
    비영속(new, transient)영속 식별자가 없고 영속성 컨텍스트와 연결되지 않은 인스턴스컨텍스트가 모른다false
    영속(managed)영속 식별자가 있고 영속성 컨텍스트와 연결된 인스턴스맵에 등록되어 있고 변경 감지 대상이다true
    준영속(detached)영속 식별자는 있지만 영속성 컨텍스트와 더는 연결되지 않은 인스턴스한때 관리되었으나 지금은 모른다false
    삭제(removed)영속성 컨텍스트와 연결되어 있고 커밋 때 데이터베이스에서 지워질 인스턴스삭제 예약 상태로 남아 있다false

    상태를 바꾸는 연산은 다음과 같다. new로 만든 객체는 비영속이다. persist를 호출하면 영속이 된다. find나 JPQL로 데이터베이스에서 읽어 온 객체는 처음부터 영속이다. 영속 객체에 remove를 호출하면 삭제 상태가 된다. 영속 객체에 detach를 호출하거나 clear, close로 컨텍스트를 비우면 준영속이 된다. 준영속 객체를 merge에 넘기면 그 객체 자신이 아니라 같은 식별자의 다른 영속 객체가 돌아온다. 마지막 연산은 이 회차 후반에서 실행 결과로 확인한다.

                         persist()
   ┌──────────┐  ─────────────────▶  ┌──────────┐   remove()   ┌──────────┐
   │  비영속   │                      │   영속    │ ───────────▶ │   삭제    │
   │  (new)   │                      │ (managed) │ ◀─────────── │ (removed)│
   └──────────┘                      └──────────┘   persist()  └──────────┘
                                       ▲     │                      │
               find() / JPQL 조회 ──────┘     │ detach() clear()     │ flush/commit
               (DB에서 읽으면 바로 영속)         │ close() 롤백         ▼
                                             ▼                  DB 행 삭제
                                       ┌──────────┐
                                       │  준영속   │ ── merge() ──▶ (다른 영속 인스턴스를 반환)
                                       │(detached)│
                                       └──────────┘

    명세가 삭제 상태에서 다시 persist를 호출하면 영속으로 돌아온다고 정한 것도 그림에 넣었다. 실무에서는 거의 쓰지 않지만 삭제 상태가 "아직 영속성 컨텍스트 안에 있는 상태"라는 것을 잘 보여 준다. 삭제는 즉시 사라지는 것이 아니라 예약이다.

    상태 이름에 속지 않는 것이 중요하다. 상태는 객체에 붙은 필드가 아니다. Member 객체의 바이트 어디에도 "나는 영속이다"라는 표시는 없다. 상태는 오직 영속성 컨텍스트 쪽 자료구조에 그 객체가 어떻게 등록되어 있느냐로 정해진다. 그래서 같은 객체가 어떤 엔티티 매니저에서는 영속이고 다른 엔티티 매니저에서는 아무것도 아닐 수 있다. 다음 절에서 그 자료구조를 직접 열어 본다.

    네 상태와 상태를 바꾸는 연산을 한눈에 보여 준다. 삭제가 즉시 삭제가 아니라 예약이라는 점, merge가 다른 인스턴스를 돌려준다는 점이 드러나야 한다. 흰 배경의 깔끔한 상태 전이도. 둥근 사각형 상자 네 개를 배치한다. 왼쪽에 "비영속", 가운데에 "영속"(가장 크게, 진한 파란 테두리), 오른쪽에 "삭제", 가운데 상자 아래에 "준영속". 화살표: "비영속"에서 "영속"으로 "persist()", "영속"에서 "삭제"로 "remove()", "영속"에서 "준영속"으로 "detach · clear · close · 롤백", "준영속"에서 오른쪽 바깥의 작은 점선 상자 "새 영속 인스턴스"로 "merge()". 화면 위쪽 바깥에서 "영속"으로 들어오는 화살표에 "find() · JPQL 조회" 라벨. "삭제" 상자 아래에 원통형 데이터베이스 아이콘과 "플러시 때 DELETE" 라벨. 단순한 플랫 디자인, 파란색과 회색 톤. 엔티티 상태는 객체의 필드가 아니라 영속성 컨텍스트가 그 객체를 어떻게 등록하고 있는지로 정해진다.

    Hibernate 6.6에서 영속성 컨텍스트의 실체는 org.hibernate.engine.internal.StatefulPersistenceContext 클래스다. 세션 하나가 이 객체 하나를 가진다. javap -p로 필드를 찍어 보면 이번 회차의 주제가 그대로 드러난다(일부만 옮긴다).

    private org.hibernate.engine.internal.EntityEntryContext entityEntryContext;
private java.util.HashMap entitiesByKey;
private java.util.HashMap entitySnapshotsByKey;
private java.util.HashMap> collectionsByKey;
private boolean flushing;
private boolean defaultReadOnly;

    entitiesByKey는 EntityKey를 키로 하는 해시 맵이다. EntityKey는 엔티티 종류(엔티티 퍼시스터)와 식별자 값의 쌍이다. 이것이 흔히 1차 캐시라고 부르는 것의 실체다. entityEntryContext는 엔티티 객체 하나마다 EntityEntry라는 관리 정보를 붙여 둔다. 엔트리에는 상태(MANAGED, DELETED 등)와 로딩 시점의 속성 값 배열(loaded state)이 들어 있다. 이 배열이 변경 감지에 쓰이는 스냅샷이다. 이 클래스는 내부 구현이므로 이름과 필드는 버전마다 바뀔 수 있지만, 식별자로 찾는 맵과 객체별 스냅샷이라는 두 축은 영속성 컨텍스트의 정의에서 나오는 것이라 구현이 달라도 형태가 같다.

    실행 중에 직접 확인해 보자. SessionImplementor와 EntityEntry는 Hibernate의 SPI 타입이라 애플리케이션 코드에서 쓸 일은 없지만, 관찰용으로는 쓸모가 있다.

    import org.hibernate.engine.spi.EntityEntry;
import org.hibernate.engine.spi.SessionImplementor;
import java.util.Arrays;

em.getTransaction().begin();

System.out.println("=== find #2");

System.out.println("entity count = " + s.getPersistenceContext().getNumberOfManagedEntities());

    로그가 한 줄씩 말해 준다. 첫 번째 find에서 SELECT가 한 번 나갔다. 두 번째 find는 SQL 없이 끝났고, 돌려준 객체가 첫 번째와 같은 인스턴스다. 영속성 컨텍스트에 관리되는 엔티티는 하나이고, 그 키는 hellojpa.Member#1이다. 엔트리의 상태는 MANAGED, 로딩된 상태 배열은 [20, A]로 식별자를 뺀 속성 값이 들어 있다. 배열의 순서는 필드 선언 순서(id, name, age)가 아니라 이름순(age, name)이고, 이 실험에서 Hibernate가 만든 INSERT 문의 열 순서 (age,name,id)도 같은 순서를 따른다. 속성 하나가 배열의 칸 하나에 대응하고, 이 칸 번호가 뒤에서 볼 변경 감지의 비교 단위다.

      EntityManager (SessionImpl)
   └─ StatefulPersistenceContext
       ├─ entitiesByKey : HashMap
       │     EntityKey[Member#1] ──────────────▶ Member@(힙 객체)  { id=1, name="A", age=20 }

       │                               id = 1, ... }
       └─ (세션이 가진) ActionQueue
             insertions = [ ]   updates = [ ]   deletions = [ ]   ◀── 플러시 때 채워지고 실행된다

    그림에서 엔티티 객체와 스냅샷은 별개의 메모리다. 엔티티 객체의 name 필드는 애플리케이션이 setter로 바꿀 수 있지만, loadedState 배열은 Hibernate만 만지고 애플리케이션 코드에는 노출되지 않는다. 그래서 둘을 비교하면 무엇이 바뀌었는지 알 수 있다. 맨 아래의 ActionQueue는 영속성 컨텍스트가 아니라 세션이 가진 별도의 대기열인데, 쓰기 지연을 설명할 때 다시 나온다.

    1차 캐시와 동일성 보장

    em.find(Member.class, 1L)이 내부에서 하는 일을 순서대로 적으면 이렇다.

    이 두 번째 단계가 흔히 1차 캐시(first-level cache)라고 부르는 동작이다. 다만 이것을 "성능을 위한 캐시"로 이해하면 절반만 이해한 것이다. 영속성 컨텍스트는 엔티티 매니저 하나의 것이고 작업 단위가 끝나면 사라진다. 여러 요청이 공유하지 않으므로 히트율로 이득을 보는 캐시가 아니다. 실험 로그에도 HHH000026: Second-level cache disabled가 찍혔는데, 여러 세션이 공유하는 캐시는 2차 캐시라는 별개의 선택 기능이다. 1차 캐시의 진짜 역할은 명세의 정의, 즉 같은 행에 대응하는 객체를 하나로 유지하는 데 있다.

    같은 행에 대응하는 객체가 하나라는 성질을 동일성 보장(identity guarantee)이라고 한다. 이 성질 덕분에 자바 코드는 ==로 같은 엔티티인지 비교할 수 있고, 한쪽에서 바꾼 값이 다른 쪽에서 즉시 보인다. 예를 들어 서비스 메서드 A가 회원 1을 찾아 이름을 바꾸고, 같은 트랜잭션 안에서 메서드 B가 회원 1을 다시 찾으면 B는 바뀐 이름을 본다. 둘이 같은 객체이기 때문이다. Hibernate 소개 문서는 영속성 컨텍스트의 이점으로 이 별칭 문제 회피(avoiding data aliasing), 자동 변경 감지, 같은 엔티티의 반복 조회 생략, 투명한 배치 처리를 든다.

    동일성 보장에는 덜 알려진 결과가 있다. 한 영속성 컨텍스트 안에서는 한 번 읽은 엔티티의 상태가 데이터베이스의 최신 값으로 덮어써지지 않는다. 그 사이에 다른 트랜잭션이 행을 바꾸고 커밋해도 마찬가지다. 실험으로 확인했다. 엔티티 매니저 em1이 회원 1을 읽은 뒤, 다른 엔티티 매니저 em2가 같은 행의 이름을 바꾸고 커밋한다. 그 다음 em1이 같은 행을 세 가지 방법으로 다시 읽는다.

    EntityManager em1 = emf.createEntityManager();
em1.getTransaction().begin();
Member m = em1.find(Member.class, 1L);
System.out.println("em1 first read name=" + m.getName());

EntityManager em2 = emf.createEntityManager();
em2.getTransaction().begin();
em2.find(Member.class, 1L).setName("CHANGED");
em2.getTransaction().commit();
em2.close();
System.out.println("=== em2 committed");

Member again = em1.find(Member.class, 1L);
System.out.println("em1 find again name=" + again.getName());
Member q = em1.createQuery("select m from Member m where m.id = 1", Member.class).getSingleResult();
System.out.println("em1 jpql name=" + q.getName() + ", same=" + (q == m));
Object raw = em1.createNativeQuery("select name from Member where id = 1").getSingleResult();
System.out.println("em1 native raw=" + raw);
em1.refresh(m);
System.out.println("after refresh name=" + m.getName());

    세 결과가 서로 다르다. find는 SQL 없이 영속성 컨텍스트의 객체를 돌려주므로 옛 이름 A가 나온다. JPQL은 SQL을 실제로 실행했고, 데이터베이스는 바뀐 행을 돌려줬을 것이다. 그런데 결과 객체의 이름은 여전히 A이고 처음 객체와 같은 인스턴스다. Hibernate가 결과 행에서 식별자를 읽고 EntityKey를 만들어 보니 이미 컨텍스트에 있는 엔티티였으므로, 행의 나머지 값으로 새 객체를 만들지도, 기존 객체를 덮어쓰지도 않고 기존 객체를 돌려준 것이다. 엔티티가 아니라 값 하나를 읽는 네이티브 쿼리는 영속성 컨텍스트를 거치지 않으므로 CHANGED가 그대로 보인다. 엔티티를 최신 값으로 바꾸고 싶다면 refresh를 명시적으로 호출해야 한다.

    이 동작을 데이터베이스의 격리 수준과 비교하면 이해가 쉽다. 이 실험의 H2는 em1의 트랜잭션 안에서도 다른 트랜잭션이 커밋한 값을 읽는 격리 수준으로 동작했다. 네이티브 쿼리가 em1의 트랜잭션 도중에 CHANGED를 읽은 것이 그 증거다. 그런데 엔티티 단위로 보면 em1은 처음 읽은 값을 끝까지 본다. 영속성 컨텍스트가 애플리케이션 계층에서 반복 가능한 읽기(repeatable read)를 흉내 내는 셈이다. 이것은 장점이자 함정이다. 같은 작업 단위 안에서 엔티티가 흔들리지 않는다는 장점이 있지만, 오래 사는 영속성 컨텍스트는 오래된 값을 들고 있게 된다. 동시에 같은 행을 고치는 경우의 충돌은 이 성질만으로 막을 수 없고, 낙관적 락(@Version)이나 비관적 락이 필요하다. 락은 「스프링 데이터 JPA」의 힌트와 락에서 다시 나온다.

    일상에서 가져온 비유회의실 화이트보드의 복사본

    회의 시작 때 공용 게시판(데이터베이스)에서 필요한 숫자를 화이트보드(영속성 컨텍스트)에 옮겨 적는다고 하자. 회의 중에는 모두 화이트보드만 보고, 같은 숫자를 두 번 옮겨 적지 않는다. 회의 중에 누가 게시판을 바꿔도 화이트보드는 그대로다. 회의가 끝나면 화이트보드에서 바뀐 숫자만 게시판에 반영한다. 비유가 깨지는 곳도 있다. 화이트보드에는 "회의 시작 때 무엇이었는지"가 따로 적혀 있지 않지만, 영속성 컨텍스트는 원래 값의 복사본(스냅샷)을 따로 들고 있어서 무엇이 바뀌었는지를 기계적으로 비교할 수 있다.

    트랜잭션을 지원하는 쓰기 지연

    이제 처음의 질문으로 돌아가자. persist를 불렀는데 INSERT가 바로 나가지 않는 이유다. 명세 3.2.2절은 새 엔티티에 persist를 호출하면 그 엔티티가 영속 상태가 되고, 데이터베이스에는 "트랜잭션 커밋 때 또는 그 전에, 또는 플러시의 결과로" 들어간다고 정한다. 언제 INSERT를 보낼지를 구현에 맡긴 것이다. Hibernate는 가능한 한 늦게 보낸다. 이것을 트랜잭션을 지원하는 쓰기 지연(transactional write-behind)이라고 부른다.

    EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();
tx.begin();
Member m = new Member(1L, "A", 20);
System.out.println("contains before persist = " + em.contains(m));
System.out.println("=== before persist");
em.persist(m);
System.out.println("=== after persist");
System.out.println("contains after persist = " + em.contains(m));
Member found = em.find(Member.class, 1L);
System.out.println("found == m : " + (found == m));
em.persist(new Member(3L, "C", 30));
System.out.println("=== before commit");
tx.commit();
System.out.println("=== after commit");
em.close();

=== before persist
=== after persist

Hibernate: insert into Member (age,name,id) values (?,?,?)

    persist 전후 사이에 SQL이 없다. persist 직후 contains는 true다. 데이터베이스에는 아직 행이 없는데 객체는 이미 영속 상태다. 그래서 곧바로 find를 하면 SELECT 없이 같은 객체가 나온다. 영속성 컨텍스트만 보고 답했기 때문이다. 두 INSERT는 커밋 직전에 한꺼번에 나갔다.

    그러면 그 사이에 INSERT는 어디서 기다리고 있었을까. Hibernate 세션은 ActionQueue라는 대기열을 가지고 있고, 실행할 SQL 작업을 "액션" 객체로 만들어 여기에 쌓는다. 관찰용 코드로 대기열의 길이를 직접 찍어 보면 어떤 연산이 언제 액션을 만드는지가 보인다. 회원 1과 3이 미리 저장되어 있는 상태에서 실행했다.

    ActionQueue q = em.unwrap(SessionImplementor.class).getActionQueue();
Member a = em.find(Member.class, 1L);
Member c = em.find(Member.class, 3L);
em.persist(new Member(2L, "B", 25));
System.out.println("after persist : " + counts(q));
em.remove(c);
System.out.println("after remove  : " + counts(q));
a.setName("A2");
System.out.println("after setName : " + counts(q));
System.out.println("=== flush");
em.flush();
System.out.println("after flush   : " + counts(q));
// counts(q)는 q.numberOfInsertions(), numberOfUpdates(), numberOfDeletions()를 문자열로 묶는다

    세 연산의 성격이 다르다는 것이 숫자로 드러난다. persist는 호출 즉시 삽입 액션을 하나 대기열에 넣는다. remove도 호출 즉시 삭제 액션을 넣는다. 그런데 setter 호출 뒤에는 수정 액션이 0개다. 수정은 호출 시점에 기록되지 않는다. Hibernate는 setter가 불렸다는 사실을 알 방법이 없기 때문이다. 수정 액션은 플러시가 시작될 때 변경 감지가 만들어 넣고, 플러시가 끝나면 세 종류의 액션이 모두 실행되어 대기열이 비워진다. 다음 절에서 이 수정 액션이 어디서 오는지 본다.

    쓰기를 미루면 무엇이 좋은가. 첫째, 커밋 직전에 SQL이 한꺼번에 모이므로 같은 테이블에 대한 같은 모양의 SQL을 JDBC 배치(addBatch/executeBatch)로 묶어 보낼 기회가 생긴다. Hibernate에서는 hibernate.jdbc.batch_size로 배치 크기를 정한다. Hibernate 소개 문서는 배치가 한 트랜잭션에서 같은 테이블에 많은 INSERT·UPDATE·DELETE를 실행할 때 도움이 된다고 설명한다. 둘째, 데이터베이스 잠금을 잡는 시간이 짧아진다. MySQL InnoDB 기준으로 UPDATE와 DELETE가 실제로 수정·삭제한 행에 잡은 잠금은 트랜잭션이 끝날 때까지 유지된다. 트랜잭션 초반에 UPDATE를 보내 놓고 오래 걸리는 계산을 하면 그동안 다른 트랜잭션이 그 행을 기다린다. 쓰기를 커밋 직전까지 미루면 잠금을 잡는 구간이 커밋 직전의 짧은 시간으로 줄어든다. 셋째, 한 작업 단위 안에서 같은 행을 여러 번 바꿔도 플러시 때의 최종 상태만 보내면 된다.

    그렇다고 미루는 것이 공짜는 아니다. 트랜잭션은 어차피 커밋 전까지 원자적이므로, 쓰기를 미뤄도 결과가 달라지지 않는다는 것이 쓰기 지연의 전제다. 이 전제가 깨지는 지점이 두 가지 있다. 하나는 데이터베이스가 만들어 주는 값이 필요할 때이고, 다른 하나는 데이터베이스에 직접 묻는 쿼리가 끼어들 때다. 뒤의 것은 플러시 절에서 다루고, 앞의 것을 먼저 보자.

    IDENTITY 전략은 쓰기 지연을 깬다

    영속성 컨텍스트의 맵은 EntityKey, 즉 식별자를 키로 쓴다. 따라서 엔티티를 영속 상태로 만들려면 그 순간 식별자 값이 있어야 한다. 기본 키를 데이터베이스의 자동 증가 열(GenerationType.IDENTITY)로 만들면, 식별자는 INSERT를 실행해야 비로소 생긴다. Hibernate 사용자 가이드는 IDENTITY 열에서는 식별자 값을 알기 전에 행이 물리적으로 삽입되어야 하고, 그래서 IDENTITY 생성을 쓰는 엔티티의 INSERT는 배치로 묶을 수 없다고 설명한다. 실험 결과도 같다.

    @Entity
public class Item {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;
    private String title;
    // 생성자, getter 생략
}

// ...
em.getTransaction().begin();
Item it = new Item("book");
System.out.println("=== before persist id=" + it.getId());
em.persist(it);
System.out.println("=== after persist id=" + it.getId());
em.getTransaction().commit();
System.out.println("=== after commit");
    === before persist id=null
Hibernate: insert into Item (title,id) values (?,default)
=== after persist id=1
=== after commit

    INSERT가 persist 호출 안에서 나갔고, 호출이 끝났을 때 식별자가 채워져 있다. 커밋 때는 보낼 것이 없다. 반면 시퀀스를 쓰는 기본 전략(@GeneratedValue만 붙인 경우, H2에서 Hibernate 6.6은 Seq_SEQ라는 시퀀스를 만들어 썼다)에서는 persist 때 시퀀스에서 값만 얻고 INSERT는 미룬다.

    === seq persist
Hibernate: select next value for Seq_SEQ
=== after persist id=1
Hibernate: insert into Seq (v,id) values (?,?)

    마지막 INSERT는 커밋 시점에 나간 것이다. 식별자는 시퀀스 호출로 먼저 얻고, 행 삽입은 미룬 것이다. 시퀀스를 매번 호출하는 비용을 줄이는 allocationSize와 각 전략의 세부는 다음 회차(엔티티 매핑)의 몫이다. 여기서 기억할 것은 "식별자가 정해져야 영속 상태가 될 수 있다"는 영속성 컨텍스트의 구조적 요구가 키 생성 전략의 선택에 그대로 영향을 준다는 점이다.

    변경 감지: setter를 가로채지 않는다

    JPA에는 em.update() 같은 메서드가 없다. 영속 엔티티의 필드를 바꾸기만 하면 커밋 때 UPDATE가 나간다. 이것을 변경 감지(dirty checking)라고 한다. 처음 보면 엔티티 객체가 setter 호출을 어딘가에 알리는 것처럼 보이지만, 우리 Member 클래스의 setter는 필드 하나를 바꾸는 평범한 코드이고 Hibernate가 그 바이트코드를 고치지도 않았다. 앞에서 본 것처럼 setter 직후 대기열에는 수정 액션이 없었다. 변경 감지는 비교로 이뤄진다.

    em.getTransaction().begin();
Member a = em.find(Member.class, 1L);
a.setName("AA");
EntityEntry entry = em.unwrap(SessionImplementor.class).getPersistenceContext().getEntry(a);
System.out.println("after set: name=" + a.getName() + ", loadedState = " + Arrays.toString(entry.getLoadedState()));
System.out.println("=== before commit");
em.getTransaction().commit();
System.out.println("=== after commit");
    Hibernate: select m1_0.id,m1_0.age,m1_0.name from Member m1_0 where m1_0.id=?
after set: name=AA, loadedState = [20, A]
=== before commit
Hibernate: update Member set age=?,name=? where id=?
=== after commit

    setter를 호출한 뒤에도 스냅샷은 [20, A] 그대로다. 엔티티 객체의 이름은 AA이고 스냅샷의 이름은 A다. 커밋이 플러시를 부르면, Hibernate의 플러시 이벤트 리스너(DefaultFlushEntityEventListener)가 영속성 컨텍스트에 있는 엔티티마다 현재 필드 값을 꺼내 배열을 만들고, 그 배열과 엔트리의 loadedState를 엔티티 퍼시스터의 findDirty에 넘긴다. Hibernate 6.6 바이트코드를 javap -c로 보면 이 리스너의 변경 감지 경로에서 EntityEntry.getLoadedState()와 EntityPersister.findDirty(...)를 호출하는 것이 보인다. findDirty는 속성마다 타입에 맞는 비교를 해서 달라진 속성의 칸 번호 배열을 돌려준다. 하나라도 달라졌으면 수정 액션을 만들어 대기열에 넣고, 그 액션이 UPDATE가 된다. UPDATE가 끝나면 스냅샷을 새 값으로 갈아 끼워, 다음 플러시 때는 그 값과 비교한다.

    비교로 동작한다는 사실에서 두 가지 결과가 나온다. 첫째, 값을 바꿨다가 되돌리면 UPDATE가 나가지 않는다. 변경 "이력"이 아니라 플러시 시점의 "결과"만 보기 때문이다.

    em.getTransaction().begin();
Member a = em.find(Member.class, 1L);    // name = "AA"
a.setName("ZZ");
a.setName("AA");
System.out.println("=== before commit");
em.getTransaction().commit();
System.out.println("=== after commit");
    Hibernate: select m1_0.id,m1_0.age,m1_0.name from Member m1_0 where m1_0.id=?
=== before commit
=== after commit

    둘째, UPDATE 문에는 바뀐 열만이 아니라 모든 열이 들어간다. 위 실험에서 이름만 바꿨는데 update Member set age=?,name=? where id=?가 나갔다. Hibernate는 기본적으로 엔티티마다 모든 열을 갱신하는 UPDATE 문 하나를 쓴다. 어떤 속성이 바뀌든 SQL 문자열이 같으므로, 같은 PreparedStatement 문자열을 재사용하고 같은 문장끼리 배치로 묶기 좋다. 바뀐 열만 넣고 싶으면 Hibernate 고유 애너테이션 @DynamicUpdate를 엔티티에 붙인다. 그 대신 바뀐 열 조합마다 SQL 문자열이 달라진다. 열이 아주 많은 테이블이나, 서로 다른 열을 동시에 고치는 트랜잭션이 많은 경우에 고려할 선택이다.

    비교 방식에는 비용도 있다. 영속 엔티티 하나마다 객체 본체와 별도로 스냅샷 배열, 엔트리, 맵의 키 객체가 메모리를 차지한다. 그리고 플러시 때마다 영속성 컨텍스트의 모든 엔티티를 비교한다. Hibernate 소개 문서는 플러시 때 세션이 영속성 컨텍스트의 모든 엔티티를 변경 감지해야 해서 플러시가 다소 비싼 작업이라고 하고, 그 비용을 줄이는 방법으로 엔티티를 읽기 전용으로 로딩하는 것을 든다. 만 개의 엔티티를 읽어 놓고 그중 하나만 바꿔도 플러시는 만 개를 비교한다. 뒤의 "메모리와 성능" 절에서 이 비용을 다시 계산한다.

    변경 감지를 바이트코드 수준에서 하는 방법도 있다. Hibernate의 바이트코드 향상(bytecode enhancement)을 켜면 엔티티 클래스의 바이트코드를 고쳐 필드 쓰기를 추적하게 할 수 있다. 이 회차의 실험은 향상을 쓰지 않은 기본 설정이며, 이 설정에서는 이 절에서 본 스냅샷 비교로 동작한다.
    영속성 컨텍스트 안에서 엔티티 객체와 스냅샷이 별개의 메모리로 존재하고, 플러시 때 둘을 비교한 결과가 대기열의 액션이 되어 데이터베이스로 나가는 흐름을 보여 준다. 가로로 긴 구조도. 왼쪽 큰 둥근 사각형에 "영속성 컨텍스트" 제목. 그 안에 위아래로 두 개의 표. 위쪽 표 제목 "1차 캐시", 두 열 "@Id"와 "엔티티", 한 행에 "Member#1"과 작은 객체 아이콘 "name=AA". 아래쪽 표 제목 "스냅샷", 한 행에 "Member#1"과 "[20, A]". 두 표 사이에 저울 아이콘과 라벨 "플러시 때 비교". 저울에서 오른쪽으로 화살표가 나가 세로 막대 모양의 큐에 닿는다. 큐 제목 "쓰기 지연 SQL 저장소", 안에 위에서 아래로 "INSERT", "UPDATE", "DELETE" 세 칸. 큐에서 오른쪽 원통형 데이터베이스 아이콘으로 굵은 화살표, 라벨 "flush". 데이터베이스 아이콘 아래 라벨 "DB". 깔끔한 플랫 디자인, 파란색·회색·주황색 강조. 엔티티 객체와 스냅샷은 서로 다른 메모리다. 변경 감지는 둘을 비교한 결과로 수정 액션을 만든다.

    엔티티 삭제와 플러시의 실행 순서

    remove는 엔티티를 삭제 상태로 바꾸고 삭제 액션을 대기열에 넣는다. 명세 3.2.3절은 삭제된 엔티티가 커밋 때 또는 그 전에, 또는 플러시의 결과로 데이터베이스에서 지워진다고 정한다. 삭제 상태의 엔티티는 영속성 컨텍스트 안에 남아 있지만 contains는 false를 돌려주고, Hibernate 6.6에서 같은 키로 find하면 SQL 없이 null이 나온다. 삭제 예약을 취소하고 싶으면 그 객체에 다시 persist를 호출하면 된다. 실험에서 그렇게 하자 contains가 다시 true가 되었고 커밋 때 DELETE가 나가지 않았다.

    대기열의 액션은 들어온 순서대로 실행되지 않는다. 회원 3 삭제, 회원 1 수정, 회원 2 저장 순으로 호출해 보았다.

    em.getTransaction().begin();
Member c = em.find(Member.class, 3L);
Member a = em.find(Member.class, 1L);
System.out.println("=== remove(3), then modify(1), then persist(2)");
em.remove(c);
System.out.println("contains removed = " + em.contains(c));
a.setName("A2");
em.persist(new Member(2L, "B", 25));
System.out.println("=== before commit");
em.getTransaction().commit();
System.out.println("=== after commit");
    Hibernate: select m1_0.id,m1_0.age,m1_0.name from Member m1_0 where m1_0.id=?
Hibernate: select m1_0.id,m1_0.age,m1_0.name from Member m1_0 where m1_0.id=?
=== remove(3), then modify(1), then persist(2)
contains removed = false
=== before commit
Hibernate: insert into Member (age,name,id) values (?,?,?)
Hibernate: update Member set age=?,name=? where id=?
Hibernate: delete from Member where id=?
=== after commit

    호출 순서는 삭제, 수정, 저장이었지만 SQL은 INSERT, UPDATE, DELETE 순으로 나갔다. 순서는 ActionQueue 안에 고정되어 있다. Hibernate 6.6.53의 ActionQueue$OrderedActions 열거형을 javap로 찍으면 상수가 이 순서로 선언되어 있고, 플러시는 이 순서대로 각 목록을 실행한다.

    OrphanCollectionRemoveAction
OrphanRemovalAction
EntityInsertAction
EntityUpdateAction
QueuedOperationCollectionAction
CollectionRemoveAction
CollectionUpdateAction
CollectionRecreateAction
EntityDeleteAction

    고아 객체 제거를 빼면 엔티티 INSERT가 먼저, UPDATE가 다음, 컬렉션 처리가 그 다음, 엔티티 DELETE가 마지막이다. 이 순서에서는 새 행을 가리키도록 외래 키를 바꾸는 UPDATE가 그 새 행의 INSERT 뒤에 실행되고, 지울 행을 가리키던 참조를 끊는 UPDATE와 컬렉션 처리는 DELETE보다 먼저 실행된다. 그런데 이 고정 순서가 거꾸로 문제를 만들기도 한다. 이메일에 유일 제약이 있는 계정을 지우고, 같은 이메일로 새 계정을 같은 트랜잭션에서 만들면 어떻게 될까.

    @Entity
public class Account {
    @Id
    private Long id;
    @Column(unique = true)
    private String email;
    // 생성자 생략
}

// ...  (id=1, email=a@x.com 계정이 이미 있다)
em.getTransaction().begin();
Account old = em.find(Account.class, 1L);
em.remove(old);
em.persist(new Account(2L, "a@x.com"));
em.getTransaction().commit();
    Hibernate: select a1_0.id,a1_0.email from Account a1_0 where a1_0.id=?
Hibernate: insert into Account (email,id) values (?,?)
(커밋 실패: jakarta.persistence.RollbackException
 원인: Unique index or primary key violation: "PUBLIC.CONSTRAINT_INDEX_E ON PUBLIC.ACCOUNT(EMAIL NULLS FIRST) VALUES ( /* 1 */ 'a@x.com' )")

    코드의 의도는 "지우고 넣기"인데 SQL은 "넣고 지우기"가 되어, 옛 행이 아직 남아 있는 상태에서 INSERT가 유일 인덱스에 부딪혔다. 해결책은 순서를 SQL 수준에서 강제하는 것이다. remove 직후 em.flush()를 부르면 그 시점까지의 대기열(DELETE)이 먼저 실행되고, 이후의 INSERT는 다음 플러시에서 나간다. 같은 실험에서 flush를 끼워 넣자 delete 다음에 insert가 나가고 커밋이 성공했다. 물론 행을 지웠다 다시 만드는 대신 기존 엔티티의 값을 바꾸는 설계가 가능하다면 그쪽이 더 단순하다.

    플러시: 영속성 컨텍스트를 데이터베이스에 맞추는 순간

    지금까지 여러 번 나온 플러시를 정리하자. 플러시는 영속성 컨텍스트의 변경 내용을 데이터베이스에 반영하는 일이다. 구체적으로는 앞의 흐름도대로 변경 감지를 해서 수정 액션을 만들고, 대기열의 액션을 순서대로 JDBC로 보낸다. 명세 3.2.4절은 영속성 컨텍스트가 트랜잭션 커밋 때 데이터베이스와 동기화된다고 하고, 트랜잭션이 진행 중일 때 구현이 다른 시점에 동기화할 수도 있으며, flush 메서드로 동기화를 강제할 수 있다고 정한다. 여기서 두 가지를 분명히 해 두자.

    • 플러시는 커밋이 아니다. 플러시는 SQL을 데이터베이스로 보낼 뿐이고 트랜잭션은 계속된다. 보낸 SQL은 데이터베이스 트랜잭션 안에서 실행되었으므로, 이후 롤백하면 모두 취소된다.
    • 플러시는 영속성 컨텍스트를 비우지 않는다. 플러시 뒤에도 엔티티는 영속 상태로 남고 1차 캐시도 그대로다. 대기열만 비워지고 스냅샷이 새 값으로 바뀐다.

    첫 번째 사실은 실험으로 확인했다. 회원 1의 이름을 ROLLBACK으로 바꾸고 em.flush()를 호출하자 UPDATE가 나갔다. 이어서 롤백한 뒤 새 엔티티 매니저로 읽자 데이터베이스의 이름은 바꾸기 전 값 그대로였다.

    Hibernate: select m1_0.id,m1_0.age,m1_0.name from Member m1_0 where m1_0.id=?
Hibernate: update Member set age=?,name=? where id=?
=== rollback after flush
contains after rollback = false, name=ROLLBACK
Hibernate: select m1_0.id,m1_0.age,m1_0.name from Member m1_0 where m1_0.id=?
db name = MERGED

    마지막 줄의 MERGED는 이 실험 직전 단계(merge 실험)에서 저장한 이름이다. UPDATE가 실행되었지만 롤백으로 사라졌다. 롤백 뒤 contains가 false인 것도 눈여겨보자. 명세 3.3.3절은 트랜잭션 롤백이 그때까지 관리되던 엔티티와 삭제 예약된 엔티티를 모두 준영속으로 만든다고 정한다. 자바 객체의 이름은 여전히 ROLLBACK이다. 롤백은 데이터베이스를 되돌릴 뿐 힙에 있는 자바 객체의 필드를 되돌리지 않는다. 롤백 뒤에 그 객체를 다시 쓰면 데이터베이스와 다른 값을 들고 있게 된다.

    플러시가 일어나는 세 시점

    Hibernate 소개 문서는 기본 설정에서 플러시가 일어나는 때를 셋으로 든다. 현재 트랜잭션이 커밋될 때, 대기 중인 변경이 결과에 영향을 줄 쿼리를 실행하기 전, 그리고 프로그램이 flush()를 직접 호출할 때다. 커밋과 직접 호출은 이미 보았으니 쿼리 실행 전 플러시를 실험해 보자. 이 시점에 테이블에는 회원 1, 2가 있다. 회원 4를 persist한 뒤, 관련 없는 엔티티 Item을 JPQL로 조회하고, 이어서 Member를 JPQL로 센다. 그 다음 회원 5를 persist하고 네이티브 SQL로 Item 테이블을 센다.

    em.getTransaction().begin();
em.persist(new Member(4L, "D", 40));
System.out.println("=== jpql on Item");
em.createQuery("select i from Item i", Item.class).getResultList();
System.out.println("=== jpql on Member");
long n = em.createQuery("select count(m) from Member m", Long.class).getSingleResult();
System.out.println("count = " + n);
em.persist(new Member(5L, "E", 50));
System.out.println("=== native query");
em.createNativeQuery("select count(*) from Item").getSingleResult();
System.out.println("=== rollback");
em.getTransaction().rollback();
    === jpql on Item
Hibernate: select i1_0.id,i1_0.title from Item i1_0
=== jpql on Member
Hibernate: insert into Member (age,name,id) values (?,?,?)
Hibernate: select count(m1_0.id) from Member m1_0
count = 3
=== native query
Hibernate: insert into Member (age,name,id) values (?,?,?)
Hibernate: select count(*) from Item
=== rollback

    세 쿼리의 동작이 모두 다르다. Item을 읽는 JPQL 앞에서는 플러시가 없었다. 대기 중인 변경은 Member 테이블의 INSERT뿐이고, Item을 읽는 쿼리의 결과에는 영향을 줄 수 없기 때문이다. Member를 세는 JPQL 앞에서는 INSERT가 먼저 나갔고, 그래서 count가 데이터베이스의 두 명에 방금 저장한 한 명을 더한 3이 되었다. 플러시가 없었다면 2가 나와 애플리케이션이 방금 저장한 회원을 세지 못했을 것이다.

    JPQL 앞의 이 판단은 명세에 근거가 있다. 명세 3.10.8절은 플러시 모드가 AUTO일 때 구현이 "쿼리 결과에 영향을 줄 수 있는" 엔티티 변경이 쿼리 처리에 보이도록 보장할 책임을 진다고 정하고, 그 방법으로 해당 엔티티를 플러시하거나 다른 수단을 쓸 수 있다고 한다. Hibernate는 JPQL을 SQL로 번역하면서 그 쿼리가 건드리는 테이블 목록(query space)을 알고 있으므로, 대기 중인 액션의 테이블과 겹칠 때만 플러시한다. 명세가 요구하는 것은 "영향을 줄 수 있는 변경이 보이는 것"이지 "모든 쿼리 앞에서 플러시하는 것"이 아니다.

    네이티브 SQL은 사정이 다르다. Hibernate는 SQL 문자열을 해석하지 않으므로 그 쿼리가 어느 테이블을 읽는지 모른다. 실험에서는 Item 테이블만 읽는 네이티브 쿼리 앞에서도 Member의 INSERT가 나갔다. Hibernate 소개 문서는 기본적으로 네이티브 쿼리 실행 전에 세션을 플러시하지 않는다고 설명하는데, 이 실험 결과와 다른 이유는 부트스트랩 방식에 있다. Hibernate 6.6.53의 NativeQueryImpl.shouldFlush() 바이트코드를 보면, 트랜잭션 진행 여부와 플러시 모드(ALWAYS, AUTO)를 확인하고 SessionFactoryOptions.isJpaBootstrap()을 조건에 넣는다. 이 실험처럼 JPA 표준 방식으로 만든 엔티티 매니저 팩토리에서는 AUTO 모드의 네이티브 쿼리 앞에서 플러시가 일어났고, Hibernate 고유 방식으로 부트스트랩한 세션은 이와 다르게 동작할 수 있다. 네이티브 쿼리를 쓸 때 어떤 동작에 기대고 싶다면, 앞에서 em.flush()를 직접 부르거나 Hibernate의 addSynchronizedEntityClass()로 쿼리가 어떤 엔티티에 의존하는지 알려 주는 것이 버전과 설정에 덜 흔들린다.

    플러시 모드

    JPA의 FlushModeType에는 두 값이 있다. AUTO가 기본값이고, 방금 본 대로 커밋 때와 결과에 영향을 받는 쿼리 전에 플러시한다. COMMIT은 명세 3.10.8절에 따르면 영속성 컨텍스트의 변경이 쿼리에 미치는 영향이 "명시되지 않는다(unspecified)". 커밋 때는 플러시하지만 쿼리 전에 플러시할지는 구현 마음이라는 뜻이다. Hibernate 6.6에서 확인했다. 테이블에 회원 두 명이 있는 상태다.

    EntityManager em = emf.createEntityManager();
em.setFlushMode(FlushModeType.COMMIT);
em.getTransaction().begin();
em.persist(new Member(6L, "F", 60));
System.out.println("=== jpql on Member (COMMIT mode)");
long n = em.createQuery("select count(m) from Member m", Long.class).getSingleResult();
System.out.println("count = " + n);
System.out.println("=== explicit flush");
em.flush();
System.out.println("=== jpql again");
n = em.createQuery("select count(m) from Member m", Long.class).getSingleResult();
System.out.println("count = " + n);
em.getTransaction().rollback();
    === jpql on Member (COMMIT mode)
Hibernate: select count(m1_0.id) from Member m1_0
count = 2
=== explicit flush
Hibernate: insert into Member (age,name,id) values (?,?,?)
=== jpql again
Hibernate: select count(m1_0.id) from Member m1_0
count = 3

    COMMIT 모드에서는 같은 트랜잭션에서 방금 저장한 회원이 쿼리 결과에 빠졌다. 영속성 컨텍스트와 데이터베이스가 서로 다른 답을 하는 상태를 일부러 허용하는 모드다. 쓰기와 조회가 섞이지 않는다는 것이 확실한 구간에서, 쿼리마다 대기 중인 액션과 테이블을 비교하는 비용과 이른 플러시를 피하고 싶을 때 쓴다. Hibernate 고유의 FlushMode는 여기에 두 값을 더한다. 소개 문서의 표에 따르면 MANUAL은 자동 플러시를 전혀 하지 않고, ALWAYS는 커밋 전과 모든 쿼리 실행 전에 플러시한다. 소개 문서는 COMMIT 모드에서 쿼리가 오래된 데이터를 돌려줄 수 있다고 경고한다.

    트랜잭션 없이 플러시하면

    명세 3.10.8절은 활성 트랜잭션이 없으면 구현이 데이터베이스로 플러시하면 안 된다고 정한다. 쓰기 지연의 이름이 "트랜잭션을 지원하는" 쓰기 지연인 이유다. 직접 만든 엔티티 매니저에서 트랜잭션 없이 실험했다.

    EntityManager em = emf.createEntityManager();
em.persist(new Member(7L, "G", 70));
System.out.println("persist without tx ok, contains=" + em.contains(em.find(Member.class, 7L)));
em.flush();
    persist without tx ok, contains=true
EXCEPTION jakarta.persistence.TransactionRequiredException: no transaction is in progress

    확장 영속성 컨텍스트에서는 트랜잭션 밖에서도 persist가 성공하고 엔티티가 영속 상태가 된다. 그러나 그것을 데이터베이스로 보내려는 flush는 TransactionRequiredException으로 실패한다. 영속성 컨텍스트의 변경은 트랜잭션 경계 안에서만 데이터베이스에 도달할 수 있다. 이 구조 덕분에 "SQL은 이미 나갔는데 커밋할 트랜잭션이 없는" 어중간한 상태가 생기지 않는다.

    애플리케이션의 commit 호출이 플러시(변경 감지, 액션 실행)를 거쳐 JDBC SQL이 되고, 그 뒤에 데이터베이스 커밋이 일어나는 순서를 보여 준다. 세로 생명선 네 개가 있는 시퀀스 다이어그램. 왼쪽부터 "애플리케이션", "엔티티 매니저", "영속성 컨텍스트", "DB". 첫 화살표: 애플리케이션에서 엔티티 매니저로 "commit()". 엔티티 매니저에서 영속성 컨텍스트로 "flush" 화살표. 영속성 컨텍스트 생명선 옆에 자기 자신으로 돌아오는 화살표 "스냅샷 비교". 영속성 컨텍스트에서 DB로 세 개의 화살표가 위에서 아래로 "INSERT", "UPDATE", "DELETE". 마지막으로 엔티티 매니저에서 DB로 굵은 화살표 "DB 커밋". 화살표는 위에서 아래로 시간 순서. 흰 배경, 단정한 선, 파란색 강조. 커밋은 먼저 플러시를 부르고, 플러시가 SQL을 다 보낸 뒤에 데이터베이스 커밋이 일어난다.

    준영속 상태

    준영속(detached) 엔티티는 식별자를 가지고 있고 데이터베이스에 대응하는 행도 있지만, 더 이상 영속성 컨텍스트가 관리하지 않는 엔티티다. 명세 3.2.7절은 준영속 엔티티가 생기는 경로를 여섯 가지로 든다.

    1. 트랜잭션 범위 영속성 컨텍스트를 쓸 때 트랜잭션이 커밋된 경우
    2. 트랜잭션이 롤백된 경우
    3. 엔티티를 영속성 컨텍스트에서 분리(detach)한 경우
    4. 영속성 컨텍스트를 비운(clear) 경우
    5. 엔티티 매니저를 닫은(close) 경우
    6. 엔티티를 직렬화하거나 값으로 전달한 경우(다른 계층이나 원격 인터페이스로 넘길 때)

    앞의 다섯은 영속성 컨텍스트 쪽에서 등록을 지우는 것이고, 마지막은 객체의 복사본이 만들어지는 것이다. 어느 쪽이든 결과는 같다. 그 객체를 가리키는 등록 정보(맵의 항목, 엔트리, 스냅샷)가 영속성 컨텍스트에 없다. 등록 정보가 없으니 플러시 때 비교 대상 목록에 들지 않고, 그래서 아무리 필드를 바꿔도 UPDATE가 나가지 않는다.

    // DB에는 id=1, name="A" 회원이 있다
em.getTransaction().begin();
Member a = em.find(Member.class, 1L);
em.detach(a);
System.out.println("contains after detach = " + em.contains(a));
a.setName("DETACHED");
System.out.println("=== find after detach");
Member a2 = em.find(Member.class, 1L);
System.out.println("a == a2 : " + (a == a2) + ", a2.name=" + a2.getName());
em.clear();
System.out.println("=== find after clear");
Member a3 = em.find(Member.class, 1L);
System.out.println("a2 == a3 : " + (a2 == a3));
System.out.println("=== before commit");
em.getTransaction().commit();
System.out.println("=== after commit");
em.close();
System.out.println("a3.name after close = " + a3.getName());

contains after detach = false
=== find after detach
Hibernate: select m1_0.id,m1_0.age,m1_0.name from Member m1_0 where m1_0.id=?
a == a2 : false, a2.name=A
=== find after clear
Hibernate: select m1_0.id,m1_0.age,m1_0.name from Member m1_0 where m1_0.id=?

    한 줄씩 읽어 보자. detach 뒤 contains가 false다. 준영속 객체의 이름을 DETACHED로 바꿨지만 커밋 때 UPDATE가 없다. detach 뒤 같은 키로 find하자 SELECT가 다시 나갔고, 새 객체 a2가 만들어졌다. 이제 힙에는 같은 행에 대응하는 객체가 둘(a와 a2) 있다. 영속성 컨텍스트의 "하나만 있다"는 보장은 그 컨텍스트가 관리하는 객체에만 적용된다는 것이 여기서 드러난다. clear 뒤에도 마찬가지로 SELECT가 다시 나갔고 a3는 a2와 다른 객체다. 엔티티 매니저를 닫은 뒤에도 a3의 이름은 읽을 수 있다. 필드에 이미 채워진 값을 읽는 것은 평범한 자바 객체의 필드 읽기일 뿐이기 때문이다.

    명세 3.2.6절에 따르면 detach는 엔티티를 영속성 컨텍스트에서 제거하고, 그 엔티티에 대해 아직 플러시되지 않은 변경(삭제 예약 포함)은 데이터베이스에 동기화되지 않는다. 그래서 명세는 엔티티에 변경이 있다면 이식성 있는 동작을 보장하기 위해 detach보다 flush를 먼저 호출해야 한다(must)고 정한다. clear도 같다. 컨텍스트 전체를 비우므로 아직 플러시하지 않은 변경은 모두 사라진다.

    준영속 상태에서 잃는 것

    기능영속준영속이유
    1차 캐시 조회SQL 없이 같은 객체SELECT 후 다른 객체맵에 등록 정보가 없다
    동일성 보장같은 행이면 같은 객체보장 없음보장은 컨텍스트 안의 객체에만 적용된다
    변경 감지플러시 때 UPDATE아무 일도 없다스냅샷이 없어 비교 대상이 아니다
    지연 로딩필요할 때 SELECT초기화되지 않은 연관은 읽을 수 없다로딩을 맡을 세션이 없다(7회차에서 자세히)
    이미 채워진 필드 읽기가능가능힙의 평범한 객체 필드다

    merge: 준영속 객체를 다시 붙이는 것이 아니다

    준영속 객체의 변경을 데이터베이스에 반영하는 표준 방법은 merge다. 이름 때문에 준영속 객체를 영속성 컨텍스트에 다시 붙이는 연산으로 오해하기 쉽지만, 명세 3.2.7.1절의 정의는 다르다. 준영속 객체 X의 상태를 같은 식별자의 기존 영속 인스턴스 X'에 복사하거나, 그런 인스턴스가 없으면 새 영속 인스턴스 X'를 만들어 복사하고, X'를 돌려준다. X 자신은 여전히 준영속이다. 앞의 실험에서 준영속이 된 객체 a를 새 엔티티 매니저에 넘겼다.

    EntityManager em2 = emf.createEntityManager();
em2.getTransaction().begin();
a.setName("MERGED");              // a는 앞에서 준영속이 된 객체
System.out.println("=== merge");
Member merged = em2.merge(a);
System.out.println("merged == a : " + (merged == a) + ", contains(a)=" + em2.contains(a) + ", contains(merged)=" + em2.contains(merged));
System.out.println("=== before commit");
em2.getTransaction().commit();
System.out.println("=== after commit");
    === merge

=== before commit
Hibernate: update Member set age=?,name=? where id=?
=== after commit

    merge 안에서 SELECT가 나갔다. em2의 영속성 컨텍스트가 비어 있었으므로 기존 행을 읽어 영속 인스턴스를 만들어야 했기 때문이다. 그 인스턴스에 a의 필드 값이 복사되었고, 커밋 때 스냅샷(데이터베이스의 값)과 비교되어 UPDATE가 나갔다. 돌려받은 merged는 a와 다른 객체이고, 이후 코드는 a가 아니라 merged를 써야 한다. a를 계속 고쳐도 더는 반영되지 않는다. 또 merge는 준영속 객체의 모든 필드를 복사하므로, 화면에서 일부 필드만 채워 온 객체를 넘기면 채우지 않은 필드가 null로 덮어써진다. 「JPA 활용 1」에서 다룬 변경 감지와 병합의 차이, 즉 영속 엔티티를 조회해 필요한 필드만 바꾸는 방식이 더 안전한 이유가 이 동작에서 나온다.

    준영속 객체를 persist에 넘기면

    명세 3.2.2절은 준영속 객체를 persist에 넘기면 호출 시점에 EntityExistsException이 날 수도 있고, 플러시나 커밋 때 EntityExistsException이나 다른 PersistenceException이 날 수도 있다고 정한다. 언제 실패할지를 구현에 맡긴 것이다. 식별자를 애플리케이션이 직접 넣는 이 회차의 Member로 실험하면 Hibernate 6.6은 호출 시점에 그 객체가 준영속인지 판단하지 못했다.

    persist returned, contains(a)=true
Hibernate: insert into Member (age,name,id) values (?,?,?)
EXCEPTION jakarta.persistence.RollbackException
  root: org.h2.jdbc.JdbcSQLIntegrityConstraintViolationException

    persist는 조용히 성공했고, 커밋 때 INSERT가 기본 키 중복으로 실패했다. 버전 필드도 없고 생성 전략도 없는 엔티티에서, 식별자 값만 보고는 "새 객체에 키를 넣은 것"과 "데이터베이스에서 읽었던 객체"를 구별할 정보가 없기 때문이다. 데이터베이스에 묻지 않는 한 알 수 없는 것을 Hibernate는 묻지 않았고, 그 대가가 커밋 시점의 제약 위반으로 돌아왔다. 준영속 객체의 반영은 merge로, 새 객체의 저장은 persist로 나눠 쓰는 것이 원칙이다.

    메모리와 성능의 관점에서 다시 보기

    영속성 컨텍스트는 자바 힙 위의 자료구조이므로 GC와 메모리의 규칙을 그대로 따른다. Hibernate 소개 문서는 영속성 컨텍스트가 자기 엔티티 모두에 대한 강한 참조(hard reference)를 쥐고 있어 가비지 컬렉션을 막는다고 지적하고, 작업 단위가 끝나면 세션을 버리라고 권한다. 엔티티 하나가 영속 상태일 때 힙에는 엔티티 객체 본체, 스냅샷 배열과 그 안의 값들, EntityEntry, EntityKey, 해시 맵의 노드가 함께 살아 있다. 이 객체들은 모두 영속성 컨텍스트에서 도달 가능하므로, 애플리케이션 코드가 엔티티 참조를 놓아도 GC 대상이 되지 않는다.

    배치 작업에서 이것이 문제가 된다. 십만 건의 행을 하나씩 읽어 고치는 작업을 엔티티 매니저 하나로 처리한다고 해 보자. 루프가 돌수록 영속성 컨텍스트에 엔티티가 쌓인다. 메모리가 계속 늘어나는 것도 문제지만, 플러시 비용도 함께 커진다. 자동 플러시가 일어날 때마다 그때까지 쌓인 모든 엔티티를 비교하기 때문이다. 흔한 해법은 일정 건수마다 flush()와 clear()를 함께 부르는 것이다. 순서가 중요하다. flush()만 하면 SQL은 나가지만 엔티티가 컨텍스트에 남아 메모리가 줄지 않는다. clear()만 하면 아직 보내지 않은 변경이 사라진다. flush()로 변경을 데이터베이스에 보낸 뒤 clear()로 등록 정보를 지워야 엔티티들이 GC 대상이 된다. 이때 트랜잭션은 계속되므로 데이터베이스 쪽의 롤백 단위는 그대로다.

    em.getTransaction().begin();
for (long i = 1; i <= 100_000; i++) {
    em.persist(new Member(i, "m" + i, 0));
    if (i % 1_000 == 0) {      // 1,000건마다
        em.flush();            // 대기열의 INSERT를 보낸다
        em.clear();            // 등록 정보를 지워 엔티티를 GC 대상으로 만든다
    }
}
em.getTransaction().commit();

    읽기만 하는 작업에도 같은 원리가 적용된다. 화면에 목록을 보여 주려고 엔티티 수천 개를 읽으면, 그 엔티티들은 고칠 일이 없는데도 스냅샷을 만들고 플러시 때 비교 대상이 된다. 앞에서 본 대로 Hibernate 소개 문서는 읽기 전용 로딩을 그 비용을 줄이는 방법으로 든다. 아예 엔티티가 아닌 DTO로 필요한 열만 조회하면 영속성 컨텍스트를 거치지 않는다. JPQL의 DTO 조회는 9회차에서 다룬다.

    반대 방향의 함정도 있다. JPQL의 벌크 UPDATE·DELETE나 네이티브 SQL로 데이터베이스를 직접 고치면 영속성 컨텍스트는 그 사실을 모른다. 앞의 em1 실험처럼, 이미 읽어 둔 엔티티는 옛 값을 계속 들고 있다. 벌크 연산 뒤에 영속성 컨텍스트를 어떻게 다뤄야 하는지는 10회차의 주제다.

    흔한 오해와 함정

    "persist를 하면 데이터베이스에 저장된다"

    persist는 영속성 컨텍스트에 등록하고 삽입 액션을 예약할 뿐이다. 데이터베이스 저장은 플러시 때 일어나고, 그 저장이 확정되는 것은 커밋 때다. 예외는 IDENTITY 전략처럼 식별자를 얻기 위해 INSERT가 먼저 필요한 경우다. 그래서 같은 코드라도 키 생성 전략에 따라 persist 호출 줄에서 제약 위반 예외가 나기도 하고 커밋 줄에서 나기도 한다. 예외가 어디서 나느냐로 원인 위치를 짐작하면 틀리기 쉽다.

    "플러시하면 영속성 컨텍스트가 비워진다"

    이름이 "물을 내리다"라는 뜻이라 생기는 오해다. 비워지는 것은 SQL 대기열이지 영속성 컨텍스트가 아니다. 플러시 뒤에도 1차 캐시와 동일성 보장은 그대로이고, 엔티티는 계속 영속 상태다. 컨텍스트를 비우는 것은 clear()다.

    "setter를 호출해야 UPDATE가 나간다"

    Hibernate는 기본 설정에서 setter 호출을 보지 않는다. 필드 접근 방식(이 회차처럼 @Id를 필드에 붙인 경우)에서는 setter를 거치지 않고 필드 값을 직접 읽어 스냅샷과 비교한다. setter가 아닌 다른 메서드로 필드를 바꿔도 UPDATE가 나가고, setter를 호출했어도 값이 결국 같으면 UPDATE가 나가지 않는다.

    "1차 캐시가 있으니 같은 쿼리를 두 번 하면 두 번째는 SQL이 없다"

    식별자로 찾는 find만 1차 캐시를 먼저 본다. 쿼리 캐시를 켜지 않은 기본 설정에서 JPQL은 항상 SQL을 실행한다. 다만 결과 행의 식별자가 이미 컨텍스트에 있으면 그 행의 값을 버리고 기존 객체를 돌려준다. 그래서 JPQL을 두 번 해도 SQL은 두 번 나가고, 결과 객체는 같으며, 데이터베이스가 그 사이에 바뀌었어도 엔티티 값은 바뀌지 않는다.

    "준영속 객체도 식별자가 있으니 고치면 반영된다"

    식별자가 있다는 것과 관리되고 있다는 것은 다르다. 반영 여부는 객체가 아니라 영속성 컨텍스트의 등록 정보가 결정한다. 웹 계층으로 넘어간 엔티티, 이전 요청에서 세션에 넣어 둔 엔티티, 직렬화되어 돌아온 엔티티는 모두 준영속이다.

    정리: 다른 회차와의 연결

    영속성 컨텍스트는 엔티티 매니저 안에 있는, 식별자를 키로 하는 엔티티 맵과 엔티티별 스냅샷, 그리고 세션의 쓰기 대기열이 함께 움직이는 구조다. 맵에서 1차 캐시와 동일성 보장이 나오고, 스냅샷에서 변경 감지가 나오고, 대기열에서 쓰기 지연과 고정된 SQL 순서가 나온다. 플러시는 스냅샷 비교로 대기열을 완성해 데이터베이스로 보내는 순간이고, 커밋·결과에 영향을 받는 쿼리·직접 호출 때 일어난다. 준영속은 이 세 장치 모두에서 빠진 상태다.

    이 구조는 이후 회차 곳곳에서 다시 나온다. 다음 회차의 기본 키 생성 전략은 "식별자가 있어야 영속 상태가 된다"는 요구와 쓰기 지연 사이의 절충이다. 연관관계 매핑(4~6회차)에서 연관관계의 주인만 외래 키를 바꾸는 이유는 플러시 때 어떤 쪽의 변경을 SQL로 만드느냐의 문제다. 프록시와 지연 로딩(7회차)은 영속성 컨텍스트가 살아 있어야 동작하므로 준영속 상태와 직접 부딪히고, 같은 회차의 고아 객체 제거는 이 회차에서 본 OrphanRemovalAction으로 대기열에 들어간다. JPQL(9~10회차)에서는 쿼리 전 자동 플러시와 벌크 연산의 우회가 다시 나온다.

    이 장의 핵심

    JPA의 메서드는 데이터베이스가 아니라 영속성 컨텍스트를 바꾼다. 영속성 컨텍스트는 식별자로 찾는 맵(1차 캐시·동일성), 로딩 시점의 복사본(변경 감지), 쓰기 대기열(쓰기 지연)로 이뤄져 있고, 플러시가 이 셋을 SQL로 바꾼다. 어떤 변경이 언제 데이터베이스에 도달하는지 알고 싶으면 "이 객체가 지금 어느 컨텍스트에 등록되어 있는가, 다음 플러시는 언제인가"를 물으면 된다.
    영속성 컨텍스트
    엔티티 매니저와 연결된, 식별자마다 유일한 엔티티 인스턴스를 관리하는 메모리 속 작업 공간이다. Hibernate 6.6에서는 StatefulPersistenceContext가 EntityKey를 키로 하는 맵과 엔티티별 EntityEntry로 구현한다.
    엔티티 생명주기
    비영속, 영속, 준영속, 삭제의 네 상태가 있다. 상태는 객체의 필드가 아니라 영속성 컨텍스트의 등록 정보로 정해진다.
    1차 캐시와 동일성 보장
    find는 먼저 컨텍스트의 맵을 보고, 있으면 SQL 없이 같은 객체를 돌려준다. 쿼리 결과에 이미 관리 중인 엔티티가 있으면 행 값으로 덮어쓰지 않고 기존 객체를 돌려준다.
    쓰기 지연
    persist와 remove는 호출 즉시 삽입·삭제 액션을 세션의 ActionQueue에 넣고, 실제 SQL은 플러시 때 보낸다. IDENTITY 전략은 식별자를 얻기 위해 persist 때 INSERT를 실행한다.
    변경 감지
    플러시 때 엔티티의 현재 필드 값과 로딩 시점의 스냅샷(loadedState)을 비교해 달라졌으면 UPDATE 액션을 만든다. 값을 바꿨다 되돌리면 UPDATE가 없고, 기본 UPDATE는 모든 열을 포함한다.
    플러시
    영속성 컨텍스트의 변경을 SQL로 데이터베이스에 보내는 일이다. 커밋이 아니며 컨텍스트를 비우지 않는다. 커밋 때, 결과에 영향을 받는 쿼리 전, flush() 호출 때 일어나고, 트랜잭션 없이는 할 수 없다.
    플러시 순서
    Hibernate 6.6은 호출 순서와 상관없이 INSERT, UPDATE, 컬렉션 처리, DELETE 순으로 실행한다. 같은 유일 키를 지우고 다시 넣으려면 중간에 flush가 필요하다.
    준영속과 merge
    detach, clear, close, 롤백, 트랜잭션 범위 컨텍스트의 커밋, 직렬화로 생기며 변경 감지·지연 로딩·동일성 보장을 잃는다. merge는 준영속 객체를 붙이지 않고 상태를 복사한 다른 영속 인스턴스를 돌려준다.

    운영에서 영속성 컨텍스트 지식이 가장 자주 쓰이는 곳은 "로그와 코드가 맞지 않는" 장애를 읽을 때다. 예외 스택이 서비스 코드의 save 줄이 아니라 트랜잭션 프록시의 커밋 지점을 가리키면, 원인은 그 트랜잭션 안에서 예약된 어떤 쓰기 액션이 플러시 때 실패한 것이다. 이때는 그 트랜잭션에서 영속 상태였던 엔티티 전부가 후보다. 반대로 IDENTITY 전략을 쓰는 엔티티는 save 줄에서 바로 실패하므로, 같은 제약 위반이라도 엔티티의 키 전략에 따라 스택 위치가 달라진다는 것을 알고 있어야 원인을 빨리 찾는다.

    "삭제 후 같은 키로 다시 생성"이 들어간 기능은 플러시 순서 때문에 유일 제약에서 실패할 수 있다. 중간에 flush를 넣는 것으로 고칠 수 있지만, 판단은 설계 쪽에서 먼저 한다. 지웠다 다시 만드는 것이 업무적으로 같은 대상의 갱신이라면 기존 엔티티의 값을 바꾸는 쪽이 SQL도 적고 순서 문제도 없다. 반대로 정말로 다른 대상이라면 flush로 순서를 명시하고, 그 이유를 주석으로 남겨 다음 사람이 지우지 않게 한다.

    대량 처리에서는 영속성 컨텍스트의 크기가 메모리와 처리 시간을 함께 결정한다. 처리 건수에 비례해 느려지는 배치 작업을 만나면 GC 로그와 함께 영속성 컨텍스트에 쌓이는 엔티티 수를 의심한다. flush와 clear를 묶음 단위로 넣고, 읽기만 하는 구간은 읽기 전용 로딩이나 DTO 조회로 바꾸는 것이 기본 처방이다. 다만 clear 뒤에는 그전에 받아 둔 엔티티 참조가 모두 준영속이 되므로, 루프 밖에서 들고 있던 엔티티를 clear 뒤에 고치는 코드가 없는지 함께 확인해야 한다.

    네이티브 SQL이나 벌크 연산을 섞는 코드에서는 "누가 무엇을 알고 있는가"를 따진다. 영속성 컨텍스트는 자신을 거치지 않은 변경을 모르고, 데이터베이스는 아직 플러시되지 않은 변경을 모른다. 이 회차의 실험처럼 네이티브 쿼리 전 플러시 여부는 부트스트랩 방식과 버전에 따라 달라질 수 있으므로, 결과가 그 동작에 의존한다면 flush를 명시하고 쿼리 뒤에는 필요한 엔티티를 refresh하거나 컨텍스트를 비우는 쪽이 안전하다.
  • 다음 코드를 실행하면 SQL 로그가 어떤 순서로 찍히는지 예측하라. Member는 이 회차의 엔티티이고 테이블은 비어 있으며 플러시 모드는 AUTO다. tx.begin(); Member m = new Member(10L, "X", 1); em.persist(m); m.setName("Y"); em.createQuery("select m from Member m", Member.class).getResultList(); m.setName("Z"); m.setName("Y"); tx.commit();

  • 회원 탈퇴 후 같은 이메일로 즉시 재가입하는 기능을 "기존 Account remove → 같은 email의 새 Account persist"로 한 트랜잭션에서 구현했더니 커밋 때 유일 제약 위반이 났다. SQL이 실제로 어떤 순서로 나갔는지 쓰고, 원인과 두 가지 해결 방법을 설명하라.
  • 엔티티 매니저 하나로 십만 건을 저장하는 배치가 진행될수록 느려지고 결국 OutOfMemoryError로 끝났다. 힙에서 무엇이 쌓였는지 영속성 컨텍스트의 자료구조로 설명하고, flush만 넣었을 때와 clear만 넣었을 때 각각 어떤 문제가 남는지 말하라.
  • 컨트롤러가 이전 요청에서 HTTP 세션에 넣어 둔 Member 객체를 꺼내 이름을 바꾸고, 트랜잭션이 걸린 서비스 메서드에 넘겼다. 서비스 메서드는 아무 메서드도 호출하지 않고 끝났는데 UPDATE가 나가지 않았다. 이유를 설명하고, merge를 쓰는 방법과 조회 후 변경하는 방법의 차이를 비교하라.

    1번. 로그는 INSERT, UPDATE, SELECT 순으로 세 줄이고 커밋 때는 아무것도 찍히지 않는다. Hibernate 6.6.53에서 실제로 실행해 확인한 결과다. persist는 삽입 액션을 예약하고, 그 액션은 persist 시점의 값(name=X)을 가진다. JPQL이 Member 테이블을 읽으므로 AUTO 모드에서 쿼리 전에 플러시가 일어난다. 플러시는 먼저 변경 감지를 하는데, 이 엔티티의 스냅샷은 persist 시점의 X이고 현재 값은 Y이므로 수정 액션이 추가된다. 실행 순서는 삽입 다음 수정이므로 INSERT 뒤에 UPDATE가 나가고, 그 다음 SELECT가 실행된다. 플러시가 끝나면 스냅샷이 Y로 바뀐다. 이후 Z로 바꿨다가 다시 Y로 바꿨으므로 커밋의 플러시에서 현재 값과 스냅샷이 같아 UPDATE가 없다. 조회 결과의 객체는 m과 같은 인스턴스다.

    2번. 차례로 false, true, false, true, false다. 새 객체는 컨텍스트에 등록되지 않았으므로 false, persist 뒤에는 영속이므로 true다. flush로 INSERT를 보낸 뒤 remove하면 삭제 상태가 되고 contains는 false를 돌려준다. 삭제 상태의 객체에 persist를 다시 호출하면 명세대로 영속으로 돌아와 true다. detach하면 등록 정보가 지워져 false다. detach는 아직 플러시되지 않은 변경을 버리므로 커밋 때 SQL은 나가지 않고, 데이터베이스에는 flush 때 들어간 행이 그대로 남는다(실행으로 확인).

    3번. 호출은 remove가 먼저였지만 SQL은 INSERT가 먼저, DELETE가 나중이다. Hibernate의 ActionQueue는 엔티티 삽입을 엔티티 삭제보다 먼저 실행하도록 순서가 고정되어 있다. 그래서 옛 행이 아직 있는 상태에서 같은 이메일의 INSERT가 유일 인덱스에 부딪힌다. 첫째 해결책은 remove 직후 em.flush()를 호출해 DELETE를 먼저 보내는 것이다. 둘째는 업무상 같은 대상이라면 행을 지우고 다시 만들지 않고 기존 엔티티의 상태를 바꾸는 것이다. 이 경우 UPDATE 하나로 끝나 순서 문제가 생기지 않는다.

    4번. 저장한 Member 객체마다 영속성 컨텍스트의 맵 항목(EntityKey와 홀더), EntityEntry, 스냅샷 배열이 함께 생기고, 컨텍스트가 이 모두를 강하게 참조하므로 GC가 회수하지 못한다. 자동 플러시가 일어날 때마다 쌓인 엔티티 전부를 비교하므로 처리 시간도 늘어난다. flush만 넣으면 SQL은 나가지만 등록 정보가 남아 메모리가 줄지 않고 비교 대상도 그대로 쌓인다. clear만 넣으면 아직 플러시되지 않은 INSERT 액션까지 버려져 데이터가 저장되지 않는다. 일정 건수마다 flush 후 clear를 해야 한다.

    5번. HTTP 세션에서 꺼낸 객체는 이전 요청의 영속성 컨텍스트가 끝나면서 준영속이 되었다. 지금 트랜잭션의 영속성 컨텍스트에는 그 객체의 등록 정보와 스냅샷이 없으므로 플러시 때 비교 대상에 들지 않는다. merge를 쓰면 같은 식별자의 영속 인스턴스를 조회하거나 만들고 준영속 객체의 모든 필드를 복사한다. 반환된 다른 객체를 써야 하고, 화면에서 채우지 않은 필드가 null로 덮어써질 위험이 있다. 조회 후 변경은 서비스에서 식별자로 find한 영속 엔티티에 바꿀 필드만 설정하는 방식으로, 변경 감지가 그 필드만큼만 반영하므로 의도가 분명하다.

     플러시 모드 AUTO에서 Member를 persist한 직후, Member와 관계없는 Item 엔티티만 읽는 JPQL을 실행했다. Hibernate 6.6에서 일어나는 일로 옳은 것은? JPA 명세가 AUTO 모드에서 모든 쿼리 전에 플러시하라고 요구하므로 Member의 INSERT가 먼저 나간다. 쿼리가 읽는 테이블과 대기 중인 액션의 테이블이 겹치지 않아 플러시 없이 Item의 SELECT만 나간다. persist는 즉시 INSERT를 실행하므로 플러시와 상관없이 INSERT가 이미 나가 있다. 트랜잭션이 커밋되기 전에는 어떤 쿼리도 실행할 수 없으므로 예외가 난다. 명세 3.10.8절은 쿼리 결과에 영향을 줄 수 있는 변경이 보이도록 보장하라고 요구할 뿐 모든 쿼리 전 플러시를 요구하지 않는다. Hibernate는 JPQL이 건드리는 테이블을 알고 있어서 겹칠 때만 플러시하며, 실험에서도 Item 조회 앞에는 INSERT가 없었다. persist가 즉시 INSERT를 실행하는 것은 IDENTITY 같은 예외적인 경우이고, 트랜잭션 중 쿼리 실행은 당연히 가능하다. 영속 엔티티의 name을 "A"에서 "B"로 바꿨다가 커밋 전에 다시 "A"로 바꿨다. 커밋 때 UPDATE가 나가지 않는 이유로 가장 정확한 것은? setter가 두 번 호출되면 Hibernate가 두 호출을 상쇄하도록 기록해 두기 때문이다. 같은 트랜잭션에서 같은 필드를 두 번 바꾸면 JPA가 변경을 무시하기 때문이다. 플러시 때 현재 값과 로딩 시점의 스냅샷을 비교하는데 두 값이 같기 때문이다. UPDATE는 flush()를 직접 호출해야만 나가기 때문이다. Hibernate는 기본 설정에서 setter 호출을 기록하지 않는다. ActionQueue를 찍어 보면 setter 뒤에도 수정 액션이 0개였다. 변경 감지는 플러시 시점의 필드 값과 loadedState 스냅샷을 비교하는 일이므로 최종 값이 원래 값과 같으면 바뀐 속성이 없다. 커밋도 플러시를 부르므로 직접 flush를 호출할 필요는 없다. 트랜잭션 안에서 엔티티를 수정하고 em.flush()를 호출한 뒤 트랜잭션을 롤백했다. 옳은 설명은? UPDATE는 데이터베이스로 전송되었지만 롤백으로 취소되고, 그 엔티티는 준영속이 되며 자바 객체의 필드는 수정된 값 그대로다. flush가 커밋을 겸하므로 롤백해도 수정된 값이 데이터베이스에 남는다. flush가 영속성 컨텍스트를 비웠으므로 롤백 전에 이미 엔티티는 준영속이었다. 롤백하면 Hibernate가 스냅샷을 이용해 자바 객체의 필드를 원래 값으로 되돌린다. 플러시는 SQL을 보낼 뿐 커밋하지 않고 컨텍스트도 비우지 않는다. 명세 3.3.3절에 따라 롤백은 관리 중이던 엔티티를 준영속으로 만들고, 실험에서도 contains는 false, 객체의 이름은 롤백 직전 값(ROLLBACK)이었다. 데이터베이스는 원래 값으로 돌아갔지만 힙의 객체 필드는 되돌려지지 않는다. 준영속 객체 a를 em.merge(a)에 넘겨 결과를 merged로 받았다. 옳은 것은? a가 영속성 컨텍스트에 다시 등록되므로 merged == a는 true다. merge는 SQL을 실행하지 않고 a를 그대로 영속 상태로 바꾼다. merge 이후에는 a를 고쳐도 merged를 고쳐도 모두 다음 플러시에 반영된다. a의 상태가 같은 식별자의 영속 인스턴스에 복사되고, 그 인스턴스가 merged로 반환되며 a는 계속 준영속이다. 명세 3.2.7.1절은 merge를 준영속 객체의 상태를 기존 또는 새 영속 인스턴스에 복사하는 연산으로 정의한다. 실험에서 merged == a는 false, contains(a)는 false, contains(merged)는 true였고, 컨텍스트가 비어 있어 영속 인스턴스를 만들기 위한 SELECT가 나갔다. a는 여전히 관리되지 않으므로 a의 변경은 반영되지 않는다. 기본 키를 GenerationType.IDENTITY로 생성하는 엔티티를 persist하면 호출 안에서 INSERT가 바로 나간다. 그 근본 이유는? IDENTITY 전략에서는 JPA가 쓰기 지연 기능을 꺼야 한다고 명세가 정했기 때문이다. 영속성 컨텍스트가 엔티티를 식별자로 관리하는데, IDENTITY 열의 값은 행을 삽입해야 비로소 얻을 수 있기 때문이다. IDENTITY 전략은 트랜잭션 밖에서 실행되기 때문이다. INSERT를 미루면 다른 트랜잭션이 같은 식별자를 먼저 가져가기 때문이다. 영속 상태가 되려면 EntityKey(엔티티 종류와 식별자)가 있어야 한다. IDENTITY는 데이터베이스가 INSERT 실행 중에 값을 만들어 주므로 Hibernate는 persist 때 INSERT를 실행해 식별자를 얻는다. Hibernate 사용자 가이드도 행이 먼저 물리적으로 삽입되어야 식별자를 알 수 있어 IDENTITY 엔티티의 INSERT는 배치로 묶을 수 없다고 설명한다. 명세는 INSERT 시점을 커밋 이전 어느 때로 열어 둘 뿐 특정 전략에 대해 정하지 않는다.
    영속성 컨텍스트(persistence context)
    엔티티 매니저와 연결되어, 영속 식별자마다 유일한 엔티티 인스턴스를 관리하는 작업 공간이다. 엔티티의 상태와 변경 감지, 쓰기 지연의 기반이 된다.
    1차 캐시(first-level cache)
    영속성 컨텍스트 안에서 식별자로 엔티티를 찾는 맵이다. 엔티티 매니저 하나에 속하며, 여러 세션이 공유하는 2차 캐시와는 별개다.
    스냅샷(loaded state)
    엔티티를 로딩하거나 플러시한 시점의 속성 값을 복사해 둔 배열이다. Hibernate에서는 EntityEntry가 가지고 있고 변경 감지의 비교 기준이 된다.
    쓰기 지연(transactional write-behind)
    persist·remove 등으로 생긴 쓰기 작업을 즉시 실행하지 않고 모아 두었다가 플러시 때 실행하는 방식이다.
    변경 감지(dirty checking)
    플러시 때 영속 엔티티의 현재 값과 스냅샷을 비교해 달라진 엔티티의 UPDATE를 만드는 동작이다.
    플러시(flush)
    영속성 컨텍스트의 변경을 SQL로 데이터베이스에 보내는 일이다. 트랜잭션을 커밋하지 않고 컨텍스트를 비우지도 않는다.
    ActionQueue
    Hibernate 세션이 실행할 삽입·수정·삭제·컬렉션 작업을 액션 객체로 모아 두는 대기열이다. 종류별 실행 순서가 고정되어 있다.
    FlushModeType
    JPA의 플러시 시점 설정이다. AUTO는 커밋과 결과에 영향을 받는 쿼리 전에 플러시하고, COMMIT은 쿼리에 대한 변경의 영향을 명시하지 않는다.
