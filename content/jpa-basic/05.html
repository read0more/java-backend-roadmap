    이 회차의 질문: 연결 하나를 고르는 데 왜 세 가지 축이 필요한가

    앞 회차에서 연관관계 매핑의 핵심 규칙을 세웠다. 객체는 참조로 연결되고 테이블은 외래 키(foreign key)로 연결된다. 양방향 관계에서는 두 개의 참조가 하나의 외래 키를 두고 다투므로, 둘 중 하나를 연관관계의 주인(owner)으로 정하고 주인만 외래 키를 고친다. 주인이 아닌 쪽은 mappedBy로 주인을 가리키고 읽기만 한다. 이 회차는 그 규칙을 네 가지 다중성(multiplicity)에 하나씩 적용해 본다.

    JPA가 제공하는 연관관계 애너테이션은 @ManyToOne, @OneToMany, @OneToOne, @ManyToMany 네 개다. 이름만 보면 네 가지 서로 다른 장치가 있는 것 같지만, 실제로 매핑을 결정할 때는 세 가지 질문에 차례로 답해야 한다. 첫째, 다중성: 한쪽 하나에 반대쪽이 몇 개까지 연결되는가. 둘째, 방향: 객체 그래프에서 어느 쪽에서 어느 쪽으로 탐색할 수 있어야 하는가. 셋째, 주인: 양방향이라면 어느 필드가 외래 키를 관리하는가. 같은 "부서와 직원" 관계라도 세 질문의 답에 따라 서로 다른 매핑과 서로 다른 SQL이 나온다.

    이 회차의 방법은 단순하다. 매핑을 하나 쓸 때마다 Hibernate가 실제로 만들어 내는 DDL과 SQL을 직접 실행해 확인한다. 실험은 Hibernate ORM 6.6.53.Final과 H2 2.3.232 인메모리 데이터베이스에서 hibernate.hbm2ddl.auto=create, hibernate.show_sql=true로 돌렸다. 식별자는 모두 @GeneratedValue 기본값을 썼는데, 이 조합에서 Hibernate 6.6은 엔티티마다 시퀀스를 만들고 INSERT를 플러시 시점까지 모아 둔다. 출력에서 시퀀스를 만들고 조회하는 줄은 지면을 아끼려고 생략했다. 실험 결과를 보면 네 가지 애너테이션이 테이블 쪽에서는 생각보다 적은 수의 형태로 모인다는 것이 드러난다.

    테이블은 다중성을 무엇으로 표현하는가

    객체 쪽의 매핑을 보기 전에 테이블이 다중성을 표현하는 수단부터 정리하자. 관계형 데이터베이스의 한 행, 한 컬럼에는 값이 하나만 들어간다. 그래서 "부서 하나에 직원 여럿"을 부서 행에 담을 방법이 없다. 부서 행에 직원 ID 목록을 넣는 컬럼을 만들 수는 없으니, 거꾸로 직원 행마다 자기가 속한 부서의 ID를 하나씩 적는다. 이것이 외래 키가 항상 "다(N)" 쪽 테이블에 놓이는 이유다. 다중성이 N:1이든 1:N이든, 객체에서 어느 쪽이 참조를 들고 있든, 테이블에서 외래 키 컬럼은 N 쪽에 있다.

    일대일은 외래 키에 유일 제약(unique constraint)을 더한 것이다. 직원 테이블에 주차 자리 ID를 적되 같은 주차 자리 ID가 두 번 나타나지 못하게 하면, 주차 자리 하나에 직원이 최대 한 명만 연결된다. 외래 키를 반대편 테이블에 둬도 같은 효과를 낼 수 있으므로 일대일에서는 외래 키의 위치를 설계자가 고른다. 다대다는 두 테이블만으로는 표현할 수 없다. 학생 행에 강좌 ID를 하나만 적을 수 있고 강좌 행에도 학생 ID를 하나만 적을 수 있기 때문이다. 그래서 외래 키 두 개만 가진 세 번째 테이블, 연결 테이블(join table)을 두고 다대다를 일대다 두 개로 쪼갠다.

    다중성          테이블에서의 표현
----------      ------------------------------------------------------------
N:1 / 1:N       [department]  1 ──< N  [employee: department_id FK]

1:1             [employee: parking_spot_id FK + UNIQUE]  ──  [parking_spot]
                또는 [employee]  ──  [parking_spot: employee_id FK + UNIQUE]

N:M             [student] 1 ──< N [student_course: student_id FK, course_id FK] N >── 1 [course]

    규칙이 하나 보인다. 대상이 하나인 연관관계(@ManyToOne, @OneToOne)는 기본이 즉시 로딩(EAGER)이고, 대상이 컬렉션인 연관관계(@OneToMany, @ManyToMany)는 기본이 지연 로딩(LAZY)이다. 기본값이 왜 문제가 되는지, 실무에서 왜 모두 LAZY로 바꾸는지는 07회 「프록시와 연관관계 관리」의 몫이다. 이 회차에서는 기본값이 SQL 모양을 어떻게 바꾸는지만 관찰한다.

MySQL 레퍼런스 매뉴얼은 외래 키 검사를 테이블 스캔 없이 빠르게 하려고 외래 키 컬럼과 참조되는 키에 인덱스를 요구하며, 참조하는 쪽 테이블에 그런 인덱스가 없으면 자동으로 만든다고 적고 있다(InnoDB 기준). 참조되는 쪽은 대개 기본 키라서 이미 클러스터드 인덱스(clustered index)가 있다. 결국 외래 키를 하나 만들면 양쪽 모두 인덱스를 갖게 되고, "직원으로 부서 찾기"와 "부서로 직원 찾기"가 둘 다 인덱스를 탄다. 일대일의 유일 제약은 유일 인덱스(unique index)로 구현되므로 같은 값을 두 번 넣으려는 INSERT는 인덱스 단계에서 거부된다. 다중성은 애너테이션이 아니라 이 제약과 인덱스가 데이터베이스 안에서 지킨다는 점을 기억해 두자.

    네 가지 다중성이 테이블에서는 외래 키, 외래 키+유일 제약, 연결 테이블 세 가지 형태로 표현된다는 것을 한눈에 보여 준다. 세 개의 가로 띠로 나뉜 깔끔한 데이터베이스 다이어그램. 각 띠 왼쪽에 다중성 라벨이 있다. 첫 번째 띠 라벨 "N:1 / 1:N": 왼쪽에 "department" 테이블 상자, 오른쪽에 "employee" 테이블 상자, employee 상자 안에 강조색으로 "department_id FK" 컬럼, 선 끝에 까마귀발 기호가 employee 쪽에 붙어 있다. 두 번째 띠 라벨 "1:1": "employee" 상자 안에 "parking_spot_id FK + UNIQUE" 컬럼이 강조되어 있고 "parking_spot" 상자와 단선으로 연결된다. 세 번째 띠 라벨 "N:M": "student" 상자와 "course" 상자 사이에 작은 "student_course" 연결 테이블 상자가 있고 그 안에 "student_id FK", "course_id FK" 두 컬럼이 있으며 양쪽으로 까마귀발 선이 이어진다. 흰 배경, 플랫 스타일, 외래 키 컬럼만 주황색으로 강조. 다중성은 네 가지지만 테이블의 표현은 외래 키, 외래 키와 유일 제약, 연결 테이블 세 가지다.

    다대일 [N:1]: 테이블과 가장 닮은 매핑

    다대일은 객체의 참조 방향과 테이블의 외래 키 위치가 일치하는 유일한 기본 형태다. 직원(N)이 부서(1)를 참조하고, 외래 키도 직원 테이블에 있다. 객체가 가진 참조 필드 하나가 행의 외래 키 컬럼 하나에 그대로 대응한다. 그래서 가장 먼저 익히고, 가장 많이 쓰며, 다른 매핑을 판단할 때 기준점이 된다.

    @Entity
public class Department {
    @Id @GeneratedValue
    private Long id;
    private String name;
    // 생성자, 접근자 ...
}

@Entity
public class Employee {
    @Id @GeneratedValue
    private Long id;
    private String name;

    @ManyToOne                    // @JoinColumn 생략
    private Department department;
    // 생성자, 접근자 ...
}

    @JoinColumn을 생략했는데도 외래 키 컬럼 이름이 정해지는 이유는 명세의 기본값 규칙에 있다. Jakarta Persistence 명세 11.1.25절은 조인 컬럼 이름의 기본값을 "참조하는 쪽의 연관관계 필드 이름 + 밑줄 + 참조되는 기본 키 컬럼 이름"으로 정한다. 필드 이름이 department이고 부서의 기본 키 컬럼이 id이므로 department_id가 된다. 실행해 보면 그대로 나온다.

    create table Department (id bigint not null, name varchar(255), primary key (id))
create table Employee (department_id bigint, id bigint not null, name varchar(255), primary key (id))
alter table if exists Employee add constraint FK14tijxqry9ml17nk86sqfp561 foreign key (department_id) references Department

    세 번째 줄이 외래 키 제약이다. 제약 이름은 Hibernate가 테이블과 컬럼 이름으로 만들어 붙인 것이라 사람이 읽기는 어렵지만, 같은 매핑이면 같은 이름이 나온다. 이제 부서와 직원을 하나씩 저장하고 영속성 컨텍스트를 비운 뒤 직원을 다시 조회해 보자.

    한 줄씩 추적해 보자. persist(d)와 persist(e)는 시퀀스에서 식별자만 받아 두고 INSERT를 쓰기 지연 저장소에 쌓는다. flush()에서 두 INSERT가 persist를 호출한 순서대로 나간다. 부서가 먼저 들어가므로 직원 INSERT의 department_id가 가리킬 행이 이미 존재하고, 외래 키 제약을 위반하지 않는다. 직원 INSERT의 컬럼 목록에 department_id가 들어 있다는 점이 중요하다. 외래 키가 직원 엔티티 자신의 상태이기 때문에 직원 한 행을 넣는 SQL 한 번에 연관관계까지 저장된다.

    em.clear() 뒤의 find는 1차 캐시가 비어 있으므로 데이터베이스에 간다. 이때 SELECT가 부서 테이블과 조인되어 있다. @ManyToOne의 기본 fetch가 EAGER이므로 Hibernate는 직원을 읽는 김에 부서까지 한 번에 가져온다. 조인 종류가 left join인 것도 이유가 있다. @ManyToOne의 optional 기본값은 true, 즉 부서가 없는 직원(외래 키가 NULL인 행)이 있을 수 있다. 내부 조인을 쓰면 그런 직원은 결과에서 사라지므로 외부 조인이 안전한 선택이다.

    그렇다면 반대로 모든 직원이 반드시 부서를 가진다고 선언하면 어떻게 될까. @ManyToOne(optional = false)로 바꿔 같은 코드를 실행하면 두 군데가 달라진다.

    create table Employee (department_id bigint not null, id bigint not null, name varchar(255), primary key (id))
select e1_0.id,e1_0.department_id,d1_0.id,d1_0.name,e1_0.name from Employee e1_0 join Department d1_0 on d1_0.id=e1_0.department_id where e1_0.id=?

    DDL에서 외래 키 컬럼에 not null이 붙었고, 조회 SQL의 조인이 내부 조인(join)으로 바뀌었다. 연관 대상이 반드시 있다는 정보가 스키마 제약과 쿼리 최적화 양쪽에 쓰인 것이다. 실제로 필수인 관계라면 optional = false를 적어 두는 편이 스키마로 보나 쿼리로 보나 의도를 정확히 전달한다. 단, 이 선언은 데이터베이스에 NULL이 하나라도 있으면 거짓이 된다. 기존 데이터에 외래 키가 비어 있는 행이 있는 테이블에 함부로 붙이면, 내부 조인 때문에 그 행들이 조회에서 조용히 빠진다.

    다대일 양방향: 주인은 외래 키 옆에 있다

    부서에서 소속 직원 목록을 탐색해야 한다면 반대 방향 참조를 추가한다. 테이블은 하나도 바뀌지 않는다. 외래 키는 여전히 직원 테이블의 department_id 하나뿐이다.

    @Entity
public class Department {
    @Id @GeneratedValue
    private Long id;
    private String name;

    @OneToMany(mappedBy = "department")      // 주인은 Employee.department
    private List employees = new ArrayList<>();
    // ...
}

    Jakarta Persistence 명세 2.10절은 양방향 관계의 주인을 정하는 규칙을 다중성별로 적어 두었다. 일대다·다대일 양방향에서는 "다" 쪽이 반드시 주인이어야 하며, 그래서 @ManyToOne에는 mappedBy 요소가 아예 없다. 주인을 고를 여지가 없다는 뜻이다. 외래 키가 직원 테이블에 있으니 직원 쪽 필드가 그 외래 키를 관리하는 것이 자연스럽고, 명세는 이것을 선택이 아닌 규칙으로 못 박았다. 부서의 employees 컬렉션은 데이터베이스 입장에서 아무것도 쓰지 않는 읽기 전용 거울이다.

    메모리에서 무슨 일이 일어나는지 그림으로 그려 보자. 힙(heap)에는 부서 객체가 하나 있고, 그 객체의 employees 필드는 ArrayList를 가리키며, 리스트의 내부 배열은 직원 객체들을 가리킨다. 각 직원 객체의 department 필드는 다시 부서 객체를 가리킨다. 참조는 양쪽에 모두 있지만 테이블에는 직원 행마다 department_id 칸 하나만 있다.

    자바 힙                                          데이터베이스
+----------------------+                          employee
| Department@a1        |                          +----+----------+---------------+
|  id = 1              |                          | id | name     | department_id |
|  employees ----------+--> ArrayList             +----+----------+---------------+
+----------------------+     [0] --> Employee@b7  |  1 | 한서준   |       1       |
         ^                   [1] --> Employee@c2  |  2 | 윤하은   |       1       |
         |                                         +----+----------+---------------+
         +---- Employee@b7.department                 (주인: Employee.department 만 반영)
         +---- Employee@c2.department

    Hibernate가 플러시 때 보는 것은 주인 필드뿐이다. 부서의 리스트에만 직원을 넣고 직원의 department를 비워 두면 그 직원의 department_id는 NULL로 저장된다. 반대로 직원의 department만 채우고 리스트에 넣지 않으면 데이터베이스는 올바르게 저장되지만, 같은 트랜잭션 안에서 부서의 리스트를 들여다보는 코드는 그 직원을 보지 못한다. 명세도 같은 절에서 양방향 관계의 양쪽을 런타임에 일관되게 유지할 책임은 애플리케이션에 있다고 밝힌다. 그래서 앞 회차에서 다룬 연관관계 편의 메서드가 필요하다. 소속을 바꾸는 경우까지 생각하면 기존 부서의 리스트에서 빼는 처리도 함께 넣는다.

    // Employee 안의 연관관계 편의 메서드
public void changeDepartment(Department newDepartment) {
    if (this.department != null) {
        this.department.getEmployees().remove(this);   // 옛 부서의 거울에서 제거
    }
    this.department = newDepartment;                     // 주인 필드: 외래 키에 반영된다
    newDepartment.getEmployees().add(this);              // 새 부서의 거울에 추가
}

    양방향은 테이블을 하나도 바꾸지 않으면서 코드에 일관성 유지라는 의무를 추가한다. 엔티티를 문자열로 바꾸거나 JSON으로 직렬화할 때 양쪽 참조를 따라가다 무한히 순환하는 문제도 양방향에서만 생긴다. 그래서 다대일 단방향으로 시작하고, 부서에서 직원 목록으로 탐색해야 하는 요구가 실제로 생겼을 때 반대 방향을 추가하는 순서가 무난하다. 반대 방향을 나중에 추가해도 DDL은 그대로이므로 스키마 변경이 필요 없다.

    일대다 [1:N] 단방향: 외래 키가 반대편 테이블에 있을 때

    이번에는 방향을 뒤집어 부서만 직원 목록을 알고, 직원은 부서를 모르는 모델을 생각해 보자. 객체 설계로는 그럴듯하다. 부서가 직원들을 "가지고" 있다는 표현은 직관적이고, 직원 클래스는 부서 클래스에 의존하지 않으니 결합도 낮아 보인다. 문제는 테이블이다. 외래 키는 여전히 직원 테이블에 있어야 한다. 객체의 참조는 부서에 있는데 그 참조를 저장할 칸은 직원 행에 있다. 엔티티가 관리하는 외래 키가 자기 테이블이 아닌 다른 테이블에 있는 구조, 이것이 일대다 단방향의 본질이다.

    @Entity
public class Department {
    @Id @GeneratedValue
    private Long id;
    private String name;

    @OneToMany
    @JoinColumn(name = "department_id")   // 이 컬럼은 Employee 테이블에 생긴다
    private List employees = new ArrayList<>();
    // ...
}

@Entity
public class Employee {
    @Id @GeneratedValue
    private Long id;
    private String name;               // Department를 가리키는 필드가 없다
    // ...
}

    명세 11.1.25절은 @JoinColumn의 name이 가리키는 컬럼이 어느 테이블에 있는지를 문맥별로 정해 두었다. @OneToOne이나 @ManyToOne이면 소스 엔티티의 테이블에 있고, 외래 키 매핑 전략을 쓰는 단방향 @OneToMany이면 대상 엔티티의 테이블에 있다. 같은 애너테이션이 놓인 자리에 따라 컬럼이 생기는 테이블이 달라지는 셈이다. 실제로 이 매핑의 DDL은 다대일 때와 완전히 같다. 직원 테이블에 department_id가 생기고, 부서 테이블에는 아무 컬럼도 추가되지 않는다. 차이는 저장할 때 드러난다.

    em.getTransaction().begin();
Employee e = new Employee("한서준");
em.persist(e);
Department d = new Department("개발팀");
d.getEmployees().add(e);
em.persist(d);
em.getTransaction().commit();
    insert into Employee (name,id) values (?,?)
insert into Department (name,id) values (?,?)
update Employee set department_id=? where id=?

    SQL이 세 번 나갔다. 다대일이었다면 INSERT 두 번으로 끝났을 일이다. 첫 줄을 자세히 보면 직원 INSERT의 컬럼 목록에 department_id가 아예 없다. 직원 엔티티의 상태는 id와 name뿐이고, department_id는 직원 엔티티가 아니라 부서 엔티티의 컬렉션이 관리하는 값이기 때문이다. 엔티티 INSERT는 그 엔티티 자신의 상태만 쓴다. 그래서 외래 키는 컬렉션을 처리하는 단계에서 별도의 UPDATE로 채워진다. 직원이 열 명이면 INSERT 열 번 뒤에 UPDATE가 열 번 더 나간다.

    컬렉션에서 원소를 뺄 때도 같은 구조가 보인다. 부서 하나에 직원 두 명을 저장한 뒤, 새 트랜잭션에서 부서를 조회하고 리스트의 첫 직원을 제거하면 다음 SQL이 나간다.

    select d1_0.id,d1_0.name from Department d1_0 where d1_0.id=?
select e1_0.department_id,e1_0.id,e1_0.name from Employee e1_0 where e1_0.department_id=?
update Employee set department_id=null where department_id=? and id=?

    리스트에서 뺀 것은 "이 부서에 속한다"는 사실이지 직원 자체가 아니므로, Hibernate는 직원 행을 지우지 않고 외래 키만 NULL로 되돌린다. 일대다 단방향은 결국 세 가지 비용을 낸다. 첫째, 원소마다 UPDATE가 추가로 나간다. 둘째, 직원 엔티티 코드만 읽어서는 직원 테이블이 어디서 바뀌는지 알 수 없다. 부서를 저장했는데 직원 테이블에 UPDATE가 찍히는 로그를 보고 원인을 찾으려면 부서 클래스까지 뒤져야 한다. 셋째, 위 실행처럼 INSERT 시점에 외래 키가 비어 있다가 나중에 채워지므로, 외래 키 컬럼은 적어도 그 짧은 순간 NULL을 허용해야 한다. 이 셋째 비용이 왜 생기는지 알려면 플러시가 SQL을 어떤 순서로 내보내는지 봐야 한다.

    왜 INSERT 다음에 UPDATE인가: 플러시가 SQL을 내보내는 순서

    02회에서 본 쓰기 지연 저장소는 사실 하나의 큐가 아니라 종류별로 나뉜 여러 목록이다. Hibernate 6.6 소스의 org.hibernate.engine.spi.ActionQueue는 플러시 때 실행할 작업을 종류별 목록에 나눠 담고, OrderedActions라는 열거형에 적힌 순서대로 목록을 하나씩 비운다. 그 순서는 다음과 같다.

    이 큐를 실행시키는 AbstractFlushingEventListener.performExecutions 메서드의 주석은 이 순서의 목적을 "외래 키 제약을 위반하지 않도록" SQL을 특별한 순서로 실행한다고 설명한다. 모든 엔티티 행을 먼저 넣고, 행들 사이의 연결(컬렉션)은 그다음에 맺고, 삭제는 연결을 끊은 뒤 마지막에 한다. 이 순서라면 컬렉션이 외래 키를 채우는 시점에는 참조할 부서 행과 갱신할 직원 행이 모두 이미 존재한다.

    앞 실험을 이 순서에 대입해 보자. persist(e)와 persist(d)는 EntityInsertAction 두 개를 쌓는다. 커밋 직전 플러시에서 Hibernate는 새로 영속화된 부서의 employees 컬렉션을 발견하고 CollectionRecreateAction을 만든다. 실행은 엔티티 INSERT 목록을 먼저 비우므로 직원, 부서 순으로 INSERT가 나가고, 그다음 컬렉션 목록을 비우면서 "이 컬렉션의 원소들은 이 부서 소속이다"를 직원 테이블의 UPDATE로 기록한다. 원소를 제거한 실험은 기존 컬렉션이 바뀐 경우라 CollectionUpdateAction이 그 원소의 외래 키를 NULL로 되돌렸다. 다대일에서는 외래 키가 직원 엔티티의 상태라서 EntityInsertAction 한 번에 끝났다는 것과 비교하면, 일대다 단방향의 추가 UPDATE는 우연이 아니라 "엔티티 먼저, 연결은 나중"이라는 설계의 직접적인 결과다.

    그렇다면 외래 키 컬럼을 @JoinColumn(name = "department_id", nullable = false)로 막아 버리면 어떻게 될까. 같은 매핑으로 호출 순서만 다르게 해서 두 번 실행해 보았다.

    // 실험 A: 직원을 먼저 persist하고 나중에 부서 컬렉션에 넣는다
Employee e = new Employee("한서준");
em.persist(e);
Department d = new Department("개발팀");
d.getEmployees().add(e);
em.persist(d);

// 실험 B: 컬렉션에 먼저 넣고, 부서를 먼저 persist한다
Employee e = new Employee("한서준");
Department d = new Department("개발팀");
d.getEmployees().add(e);
em.persist(d);
em.persist(e);
    -- 실험 A
insert into Employee (department_id,name,id) values (?,?,?)
org.hibernate.exception.ConstraintViolationException: could not execute statement [NULL not allowed for column "DEPARTMENT_ID"; ...]

-- 실험 B
insert into Department (name,id) values (?,?)
insert into Employee (department_id,name,id) values (?,?,?)
update Employee set department_id=? where id=?

    두 실험 모두 직원 INSERT의 컬럼 목록에 department_id가 들어갔다. 조인 컬럼이 NOT NULL이면 Hibernate 6.6은 대상 엔티티의 INSERT에도 그 컬럼을 넣는다. 그러나 값이 제대로 채워지는지는 호출 순서에 달려 있었다. 실험 A에서는 NULL이 들어가 H2가 제약 위반으로 거부했고, 실험 B에서는 값이 채워졌지만 UPDATE는 여전히 한 번 더 나갔다. 매핑만 보고는 결과를 예측할 수 없고, 코드를 고친 사람이 persist 순서를 바꾸는 순간 동작이 달라진다. 외래 키 위치와 관리 주체가 어긋난 매핑은 이렇게 경계 조건에서 약하다.

    엔티티 INSERT가 먼저 모두 실행되고, 컬렉션 처리 단계에서 반대편 테이블에 UPDATE가 나가는 순서를 보여 준다. 세로 생명선 세 개가 있는 시퀀스 다이어그램. 왼쪽 생명선 라벨 "애플리케이션", 가운데 "ActionQueue (플러시)", 오른쪽 "데이터베이스". 애플리케이션에서 가운데로 화살표 두 개 "persist(직원)", "persist(부서)". 가운데 생명선 옆에 세로로 쌓인 칸 두 개가 있고 위 칸 라벨 "1. 엔티티 INSERT", 아래 칸 라벨 "2. 컬렉션 처리". 위 칸에서 데이터베이스로 화살표 두 개 "INSERT employee (department_id 없음)", "INSERT department". 아래 칸에서 데이터베이스로 주황색 화살표 하나 "UPDATE employee SET department_id". 데이터베이스 생명선 옆에 작은 테이블 그림이 있고 department_id 칸이 처음엔 빈칸, UPDATE 뒤에 "1"로 채워진 모습. 흰 배경, 단순한 선. 일대다 단방향에서는 엔티티 INSERT가 끝난 뒤 컬렉션 단계가 반대편 테이블의 외래 키를 UPDATE로 채운다.

    조인 컬럼을 빼먹으면 생기는 것, 그리고 일대다 양방향

    일대다 단방향에서 @JoinColumn을 생략하면 어떻게 될까. 다대일에서는 생략해도 기본 이름의 외래 키 컬럼이 생겼지만, 일대다는 다르다. 명세 2.11.5.1절은 단방향 @OneToMany의 기본 매핑을 연결 테이블로 정한다. 이름은 소유 엔티티 이름이 먼저 오는 A_B 형태이고, A 쪽 외래 키 컬럼은 "엔티티 A의 이름 + 밑줄 + A의 기본 키 컬럼", B 쪽 외래 키 컬럼은 "A의 연관관계 필드 이름 + 밑줄 + B의 기본 키 컬럼"이며, B 쪽 컬럼에는 유일 제약이 걸린다. 실행 결과도 명세 그대로다.

    create table Department_Employee (Department_id bigint not null, employees_id bigint not null unique)
insert into Employee (name,id) values (?,?)
insert into Department (name,id) values (?,?)
insert into Department_Employee (Department_id,employees_id) values (?,?)

    employees_id의 unique가 이 연결 테이블을 다대다가 아닌 일대다로 만든다. 한 직원이 연결 테이블에 두 번 나타날 수 없으니 직원은 최대 한 부서에만 속한다. 동작은 맞지만 테이블이 하나 늘었고, 부서의 직원을 읽을 때마다 연결 테이블을 거치는 조인이 추가된다. 의도하지 않은 연결 테이블이 운영 스키마에 생겨 있다면 대개 이 기본값 때문이다. 일대다 단방향을 쓰겠다면 @JoinColumn은 사실상 필수다.

    일대다 양방향은 어떨까. 부서의 컬렉션을 주인으로 삼고 직원의 department를 읽기 전용 거울로 두고 싶다는 발상이다. 그런데 앞에서 본 대로 명세는 일대다·다대일 양방향에서 "다" 쪽이 주인이어야 한다고 정했고 @ManyToOne에는 mappedBy가 없다. 즉 명세가 제공하는 형태가 아니다. 대신 같은 컬럼을 두 번 매핑하고 한쪽의 쓰기를 막는 우회로를 쓸 수 있다.

    @Entity
public class Employee {
    // ...
    @ManyToOne
    @JoinColumn(name = "department_id", insertable = false, updatable = false)  // 읽기 전용
    private Department department;
}
// Department 쪽은 앞의 일대다 단방향 매핑(@OneToMany + @JoinColumn) 그대로
    insert into Department (name,id) values (?,?)
insert into Employee (name,id) values (?,?)
update Employee set department_id=? where id=?
select e1_0.id,d1_0.id,d1_0.name,e1_0.name from Employee e1_0 left join Department d1_0 on d1_0.id=e1_0.department_id where e1_0.id=?

    저장은 일대다 단방향과 똑같이 INSERT 뒤 UPDATE이고, 조회할 때는 읽기 전용 @ManyToOne이 외래 키를 읽어 부서를 채운다. insertable = false, updatable = false를 빼면 어떻게 될까. Hibernate 6.6에서 시험해 보니 오류 없이 동작했지만 SQL이 달라졌다.

    insert into Department (name,id) values (?,?)
insert into Employee (department_id,name,id) values (?,?,?)
update Employee set department_id=? where id=?

    일대일 [1:1]: 외래 키를 어느 쪽에 둘 것인가

    일대일은 다중성이 대칭이라 외래 키를 양쪽 어디에 둬도 된다. 직원과 주차 자리를 예로 들자. 직원 한 명은 주차 자리를 최대 하나 배정받고, 주차 자리 하나는 최대 한 명에게 배정된다. 이 관계를 테이블로 옮기는 방법은 세 가지다. 직원 테이블에 parking_spot_id를 두는 방법(주 테이블에 외래 키), 주차 자리 테이블에 employee_id를 두는 방법(대상 테이블에 외래 키), 그리고 주차 자리의 기본 키를 직원의 기본 키와 같게 만드는 방법(기본 키 공유)이다. 여기서 "주 테이블"은 업무에서 더 자주 조회하는 쪽, 보통 관계를 소유한다고 느끼는 쪽을 가리킨다.

    먼저 주 테이블에 외래 키를 두는 단방향 매핑을 보자. 형태는 다대일과 거의 같고 애너테이션만 다르다.

    @JoinColumn에 unique = true를 쓰지 않았는데도 parking_spot_id에 unique가 붙었다. Hibernate 6.6은 @OneToOne의 외래 키 컬럼에 유일 제약을 스스로 추가한다. 명세 2.11.1절도 양방향 일대일의 기본 매핑에서 외래 키 컬럼에 유일 제약이 있다고 적는다. 이 제약 덕분에 같은 주차 자리를 두 직원에게 배정하려는 두 번째 INSERT는 데이터베이스가 거부한다. 일대일이 다대일과 같은 모양의 SQL을 쓰면서도 다중성이 1로 지켜지는 이유는 애너테이션이 아니라 이 유일 인덱스에 있다. MySQL 매뉴얼에 따르면 UNIQUE 인덱스는 NULL을 허용하는 컬럼에 NULL이 여러 개 들어가는 것을 허용하므로, 주차 자리가 없는 직원 여러 명이 함께 NULL을 가질 수 있다. 유일 제약이 NULL을 다루는 방식은 제품마다 다를 수 있으니 다른 데이터베이스라면 그 문서를 확인한다.

    양방향으로 만들려면 주차 자리 쪽에 @OneToOne(mappedBy = "parkingSpot")을 추가한다. 명세 2.10절은 일대일 양방향에서 "외래 키를 가진 쪽"이 주인이라고 정한다. 다대일처럼 다중성이 주인을 정해 주지 않으므로 외래 키의 위치가 곧 주인을 결정한다. 그렇다면 외래 키를 대상 테이블(parking_spot.employee_id)에 두고, 직원에서만 주차 자리를 탐색하는 단방향은 가능할까. 명세 11.1.25절에 따르면 외래 키 매핑 전략에서 @OneToOne의 조인 컬럼은 소스 엔티티의 테이블에 놓인다. 직원 엔티티에 붙인 @OneToOne으로는 주차 자리 테이블의 컬럼을 관리할 표준 수단이 없다. 이 구조가 필요하면 주차 자리 엔티티에 @OneToOne을 두어 주인으로 삼고, 직원 쪽은 mappedBy로 반대편을 매핑하는 양방향으로 만든다.

    선택지장점단점
    주 테이블(employee)에 외래 키직원 한 행만 읽어도 주차 자리 유무와 ID를 안다. 객체 참조 방향과 외래 키 방향이 같아 단방향으로 충분하다.주차 자리가 없는 직원은 외래 키가 NULL이다. 나중에 "직원 한 명이 여러 자리"로 바뀌면 외래 키를 반대편 테이블로 옮기는 스키마 변경이 필요하다.
    대상 테이블(parking_spot)에 외래 키"직원 한 명이 여러 자리"로 바뀌어도 유일 제약만 지우면 일대다 구조가 된다.직원에서 탐색하려면 양방향이 필요하고, 직원 쪽(mappedBy)은 지연 로딩이 되지 않는다(다음 절).
    기본 키 공유(@MapsId)외래 키 컬럼이 따로 없고 주차 자리의 기본 키가 곧 직원 ID다. 직원 ID만 알면 주차 자리를 바로 찾는다.주차 자리가 독립된 식별자를 가질 수 없다. 배정이 바뀌면(다른 직원에게 넘기면) 행을 지우고 다시 만들어야 한다.

    표의 마지막 줄은 일대일이 "같은 생명주기"를 뜻할 때 잘 맞는다. 회원과 회원 상세 정보처럼 한쪽이 다른 쪽 없이 존재할 수 없고 짝이 바뀌지 않는 관계라면 기본 키 공유가 깔끔하다. 직원과 주차 자리처럼 배정이 바뀔 수 있는 관계에는 맞지 않는다. 이 선택지는 뒤의 설계 연습에서 실제 DDL로 확인한다.

    일대일의 함정: mappedBy 쪽은 지연 로딩이 되지 않는다

    직원이 외래 키를 가진 양방향 일대일에서 주차 자리 쪽을 지연 로딩으로 선언해 보자.

    @Entity
public class ParkingSpot {
    @Id @GeneratedValue
    private Long id;
    private String name;

    @OneToOne(mappedBy = "parkingSpot", fetch = FetchType.LAZY)
    private Employee employee;
    // ...
}

    직원 한 명과 주차 자리 하나를 저장하고, 새 트랜잭션에서 주차 자리만 find로 조회했다. employee 필드는 LAZY이므로 주차 자리 테이블만 읽고 끝나기를 기대한다.

    두 번째 SELECT가 바로 나갔고, employee 필드에 들어 있는 것은 프록시가 아니라 진짜 Employee 객체였다. LAZY 지정이 무시된 것이다. 원인은 프록시라는 구현 방식에 있다. 지연 로딩은 필드에 "나중에 채워질 대리 객체"를 넣어 두는 방식인데, 필드에 넣을 수 있는 값은 둘 중 하나다. 연관 대상이 없으면 null, 있으면 프록시. 어느 쪽을 넣을지는 엔티티를 로딩하는 바로 그 순간 정해야 한다. 프록시를 넣었다가 나중에 "사실 없었다"고 null로 바꿀 방법이 없기 때문이다.

    주인 쪽은 자기 행에 외래 키가 있으므로 그 값이 NULL인지만 보면 된다. NULL이 아니면 그 ID로 프록시를 만들어 넣고, 실제 조회는 프록시를 처음 사용할 때로 미룬다. 반면 mappedBy 쪽 행에는 상대를 가리키는 칸이 없다. 주차 자리 7번에 배정된 직원이 있는지는 직원 테이블을 parking_spot_id = 7로 찾아봐야만 알 수 있다. 어차피 조회해야 한다면 Hibernate는 그 자리에서 찾은 직원으로 필드를 채운다. Hibernate ORM 6.6 사용자 가이드도 부모 쪽 연관관계를 지연으로 표시해도 연관 대상이 null인지 알 수 없어서 그 요청을 따를 수 없다고 설명하고, 이것이 N+1 문제로 이어질 수 있다고 경고한다.

    N+1이 실제로 어떤 모습인지 확인해 보자. 직원이 배정된 주차 자리 세 개를 저장하고 JPQL select p from ParkingSpot p로 목록을 조회하니, 주차 자리 SELECT 한 번 뒤에 where e1_0.parking_spot_id=? 조건의 직원 SELECT가 세 번 따라 나갔다. 주차 자리가 100개라면 직원 이름을 화면에 하나도 표시하지 않아도 SELECT가 최대 101번이다. 같은 목록을 left join fetch p.employee를 붙인 JPQL로 조회하면 외부 조인 SELECT 한 번으로 끝났다. 페치 조인은 뒤의 JPQL 회차에서 자세히 다룬다. 해결 방법은 세 가지다. 외래 키를 자주 조회하는 쪽 테이블로 옮겨 그쪽을 주인으로 만들거나, 같은 가이드가 권하는 대로 @MapsId로 기본 키를 공유하는 단방향으로 바꾸거나, Hibernate의 바이트코드 향상(bytecode enhancement)을 켜서 필드 접근 자체를 가로채게 하는 것이다. 바이트코드 향상은 빌드 도구 플러그인 같은 별도 설정이 필요하므로 매핑 설계로 먼저 해결하는 편이 단순하다.

    대조를 위해 같은 상태에서 직원을 find로 조회한 결과도 보자. 직원 쪽 @OneToOne은 기본값 EAGER라서 주차 자리와 외부 조인한 SELECT 한 번이 나갔고, 주차 자리의 employee를 채우기 위한 추가 조회는 없었다. 이미 조인 결과에 그 주차 자리를 가리키는 직원(지금 읽은 바로 그 직원)이 있으므로 Hibernate가 같은 객체로 연결한 것이다. 실제로 조회한 직원 e에 대해 e.getParkingSpot().getEmployee() == e를 확인하면 true였다. 같은 관계라도 어느 쪽에서 출발하느냐에 따라 SQL 수가 달라진다는 점이 일대일 설계의 핵심 판단 재료다.

    외래 키를 가진 쪽은 자기 행만 보고 null과 프록시를 결정할 수 있지만, mappedBy 쪽은 상대 테이블을 조회해야만 결정할 수 있다는 차이를 좌우로 비교한다. 좌우 두 칸으로 나뉜 비교 그림. 왼쪽 제목 "주인 쪽 (외래 키 보유)": 테이블 행 하나 "employee: id=1, parking_spot_id=7"이 있고, parking_spot_id 칸에서 아래로 갈림길 화살표 두 개, 하나는 "NULL → null", 다른 하나는 "7 → 프록시"로 이어진다. 아래에 초록 체크와 라벨 "추가 조회 없음". 오른쪽 제목 "mappedBy 쪽": 테이블 행 하나 "parking_spot: id=7"만 있고 직원을 가리키는 칸이 없음을 점선 빈칸 "?"로 표시. 그 행에서 오른쪽의 "employee 테이블" 원통 아이콘으로 주황색 화살표 "SELECT ... WHERE parking_spot_id=7". 아래에 주황 경고 표시와 라벨 "즉시 조회". 흰 배경, 플랫 스타일. 프록시를 넣을지 null을 넣을지 정하려면 외래 키 값이 필요하다. mappedBy 쪽 행에는 그 값이 없다.

    다대다 [N:M]: 두 테이블로는 표현할 수 없는 관계

    학생과 강좌를 생각해 보자. 학생 한 명은 여러 강좌를 듣고, 강좌 하나에는 여러 학생이 있다. 앞에서 본 대로 테이블 두 개만으로는 이 관계를 담을 수 없으므로 연결 테이블이 필요하다. 객체는 사정이 다르다. 학생 객체가 강좌 컬렉션을 갖고 강좌 객체가 학생 컬렉션을 가지면 다대다가 그대로 표현된다. @ManyToMany는 이 차이를 메우려고 객체 쪽에는 컬렉션 두 개(또는 하나)만 보여 주고, 테이블 쪽에는 연결 테이블을 숨겨서 관리한다.

    private List courses = new ArrayList<>();
    // ...

    연결 테이블 이름은 소유 엔티티 이름이 먼저 오는 Student_Course, 컬럼은 Student_id와 courses_id다. 일대다 연결 테이블 기본값과 같은 규칙이다. 그리고 이번에는 두 컬럼을 묶은 기본 키가 생겼고, 원소 하나를 지울 때 정확히 그 행 하나만 DELETE했다.

    차이는 컬렉션의 의미에서 온다. Hibernate 6.6 사용자 가이드에 따르면 @OrderColumn이 없는 List는 기본 설정에서 bag, 즉 순서가 없고 중복을 허용하는 컬렉션으로 해석된다(hibernate.mapping.default_list_semantics 설정으로 바꿀 수 있다). bag에는 같은 강좌가 두 번 들어 있을 수 있으므로 연결 테이블에도 (student_id, course_id)가 같은 행이 둘 이상 있을 수 있다. 그러면 "이 원소에 해당하는 행"을 하나로 특정할 방법이 없다. 같은 쌍의 행 두 개 중 하나만 지우는 SQL은 표준적으로 쓸 수 없으니, Hibernate는 전부 지우고 현재 상태를 다시 넣는다. 가이드도 부모 쪽이 각각의 자식을 유일하게 식별할 수 없어서 연결 행을 모두 지우고 다시 넣는다고 설명한다. Set은 중복이 없으므로 (학생, 강좌) 쌍이 곧 행의 식별자가 되고, Hibernate는 그 쌍을 기본 키로 선언하고 그 키로 정확히 한 행만 지운다. 컬렉션 인터페이스 하나를 고르는 일이 연결 테이블의 기본 키와 DML 개수를 바꾼다.

    Set은 원소의 equals와 hashCode로 중복을 판단한다. 엔티티를 Set에 담는다면 두 메서드를 어떻게 정의했는지가 동작에 영향을 준다. 식별자가 영속화 시점에 정해지는 엔티티의 hashCode를 식별자로 계산하면, 저장 전후로 해시값이 바뀌어 HashSet에서 원소를 찾지 못하는 문제가 생길 수 있다.

    연결 테이블을 엔티티로 끌어올리기

    @ManyToMany가 숨겨 주는 연결 테이블에는 외래 키 두 개만 들어간다. 그런데 실제 요구사항에서 다대다 관계는 거의 항상 그 관계 자체에 대한 정보를 가진다. 수강 관계라면 신청 일시, 성적, 수강 상태가 붙는다. 이 값들은 학생의 속성도 강좌의 속성도 아니고 "이 학생이 이 강좌를 듣는다"는 사실의 속성이다. @ManyToMany로는 연결 테이블에 이런 컬럼을 매핑할 방법이 없다. 또 연결 테이블은 엔티티가 아니므로 JPQL에서 조회 대상으로 직접 쓸 수 없고, 어떤 SQL이 그 테이블에 나가는지 엔티티 코드에서 보이지 않는다.

    해결책은 연결 테이블을 엔티티로 승격하는 것이다. 다대다를 일대다와 다대일 두 개로 풀어서, 연결 엔티티가 양쪽에 대해 @ManyToOne을 갖게 한다. 그러면 외래 키 두 개를 모두 연결 엔티티가 주인으로 관리하고, 추가 컬럼은 평범한 필드가 된다.

    여기서 연결 엔티티의 기본 키를 무엇으로 할지 정해야 한다. 선택지는 두 가지다. 위 코드처럼 의미 없는 대리 키(surrogate key)를 따로 두고 (학생, 강좌) 쌍에는 유일 제약만 거는 방법, 그리고 (학생, 강좌) 쌍 자체를 복합 기본 키로 쓰는 방법이다. 복합 키를 쓰려면 식별자 클래스가 필요하다. 명세 2.4절은 기본 키 클래스가 public이고 public 기본 생성자를 가져야 하며, 직렬화 가능(Serializable)해야 하고, equals와 hashCode를 정의해야 한다고 정한다. 연관관계 필드를 식별자로 쓰는 것은 명세 2.4.1절의 파생 식별자(derived identity)에 해당한다.

    public class EnrollmentId implements Serializable {
    private Long student;    // Enrollment.student 와 같은 이름, Student 식별자의 타입
    private Long course;

    public EnrollmentId() {}
    public EnrollmentId(Long student, Long course) { this.student = student; this.course = course; }

    @Override public boolean equals(Object o) {
        return o instanceof EnrollmentId other
                && Objects.equals(student, other.student) && Objects.equals(course, other.course);
    }
    @Override public int hashCode() { return Objects.hash(student, course); }
}

    복합 키는 같은 쌍의 중복을 기본 키 수준에서 막는다. 실험에서 같은 학생과 강좌로 두 번째 엔티티를 persist하자 영속성 컨텍스트가 같은 식별자를 발견해 EntityExistsException을 던졌다. 그런데 이 장점은 요구사항이 바뀌면 그대로 약점이 된다. 같은 학생이 같은 강좌를 다음 학기에 다시 듣는 재수강이 허용된다면, (학생, 강좌)는 더 이상 수강 한 건을 식별하지 못한다. 기본 키를 (학생, 강좌, 학기)로 늘리면 식별자 클래스와 그것을 참조하는 모든 코드, 그리고 이 테이블을 외래 키로 참조하는 다른 테이블까지 바뀐다. 대리 키를 썼다면 유일 제약 하나를 고치는 것으로 끝난다. 비즈니스 의미가 있는 값은 바뀔 수 있으므로 식별자에서 떼어 두는 편이 변경에 강하다는 판단이다.

    한 층 아래, MySQL InnoDB에서 두 설계의 인덱스를 비교해 보자. InnoDB는 기본 키로 행을 정렬해 저장하는 클러스터드 인덱스를 쓴다. 대리 키를 쓰면 행은 id 순서로 저장되고, 유일 제약 (student_id, course_id)가 보조 인덱스로 생긴다. 이 인덱스는 student_id가 맨 앞이므로 "학생의 수강 목록" 조회와 student_id 외래 키 검사에 함께 쓰이고, course_id 외래 키에는 앞에서 본 규칙대로 MySQL이 인덱스를 자동으로 만든다. 복합 키를 쓰면 기본 키 자체가 클러스터드 인덱스가 되므로 컬럼 순서가 중요하다. 위 실험에서 Hibernate 6.6이 만든 기본 키는 (course_id, student_id) 순서였다. 이대로라면 같은 강좌의 수강생들이 물리적으로 모여 저장되고, 학생 쪽 조회는 student_id 외래 키를 위해 생기는 보조 인덱스에 기대게 된다. 자동 생성된 DDL의 컬럼 순서가 의도와 다를 수 있다는 것도 운영 스키마를 직접 관리해야 하는 이유 중 하나다.

    @ManyToMany의 숨은 연결 테이블이 Enrollment 엔티티로 바뀌면서 다대다가 다대일 두 개로 분해되고, 관계 자체의 속성이 들어갈 자리가 생기는 것을 보여 준다. 위아래 두 단으로 나뉜 전후 비교 다이어그램. 위 단 제목 "전: @ManyToMany": 왼쪽 "Student" 상자와 오른쪽 "Course" 상자가 양쪽 화살표로 직접 연결되어 있고, 그 사이 아래쪽에 회색 점선 상자 "student_course (숨은 테이블)"가 있으며 안에 "student_id", "course_id" 두 칸만 있다. 아래 단 제목 "후: 연결 엔티티": "Student" 상자, 가운데 실선 상자 "Enrollment", "Course" 상자가 나란히 있고, Enrollment에서 양쪽으로 화살표 "@ManyToOne"이 하나씩 뻗는다. Enrollment 상자 안에 "id (대리 키)", "student_id", "course_id", "enrolledAt", "grade" 칸이 있고 마지막 두 칸은 초록색으로 강조된다. 위 단에서 아래 단으로 큰 아래 화살표 라벨 "승격". 흰 배경, 플랫 스타일. 연결 테이블을 엔티티로 만들면 다대다가 다대일 두 개로 풀리고, 관계의 속성이 필드가 된다.

    설계 연습: 도서 대출 도메인을 네 가지 다중성으로 옮기기

    지금까지의 판단 기준을 한 도메인에 모두 적용해 보자. 작은 도서관의 대출 시스템을 요구사항 문장에서 출발해 엔티티와 테이블로 옮긴다. 요구사항은 다음과 같다.

    1. 이용자(patron)는 도서를 여러 번 대출할 수 있고, 같은 도서를 반납한 뒤 다시 빌릴 수도 있다. 대출마다 대출일, 반납 예정일, 실제 반납일을 기록한다.
    2. 이용자 한 명에게 회원증은 최대 한 장 발급된다. 회원증은 이용자 없이는 존재하지 않고, 다른 이용자에게 넘어가지 않는다.
    3. 도서는 여러 분류에 속할 수 있고, 분류 하나에는 여러 도서가 있다. 어떤 도서를 어떤 분류에 언제 지정했는지 기록한다.
    4. 분류는 계층 구조다. 분류 하나는 상위 분류를 최대 하나 가지고, 하위 분류를 여러 개 가질 수 있다.

    문장마다 다중성과 외래 키 위치를 정해 표로 만든다. 이 단계에서 이미 엔티티 수와 테이블 수가 결정된다.

    결과를 판단과 대조해 보자. 대출 두 건이 같은 (patron_id, book_id)로 문제없이 들어갔다. 요구사항 1의 "다시 빌릴 수 있다"를 대리 키 설계가 받아 준 것이다. 만약 대출을 @ManyToMany로 매핑했다면 날짜를 담을 곳이 없었을 것이고, (이용자, 도서) 복합 키를 썼다면 두 번째 대출이 거부되었을 것이다. 모든 INSERT가 외래 키 컬럼을 직접 포함하고 UPDATE가 한 번도 나가지 않았다는 점도 보자. 모든 외래 키를 다대일의 주인 쪽이 관리하도록 설계했기 때문이다.

    LibraryCard 테이블에는 별도의 외래 키 컬럼 없이 patron_id가 기본 키이자 외래 키로 쓰였다. 요구사항 2의 "넘어가지 않는다"와 "이용자 없이 존재하지 않는다"가 기본 키 공유와 잘 맞는다. 이용자 쪽에서 회원증으로 가는 참조를 일부러 두지 않았는데, 그 참조를 mappedBy로 추가하면 앞 절의 지연 로딩 문제가 이용자 조회마다 따라붙기 때문이다. 이용자의 회원증이 필요하면 이용자 ID로 em.find(LibraryCard.class, patronId)를 하면 된다. 기본 키가 같으니 조회 비용은 기본 키 조회 한 번이다.

    요구사항 4의 자기 참조도 특별한 장치가 필요 없다. 다대일의 대상이 우연히 같은 엔티티일 뿐이고, 외래 키 parent_id는 같은 테이블의 기본 키를 참조한다. 최상위 분류는 parent_id가 NULL이어야 하므로 이쪽에는 optional = false를 쓰지 않았다. 반면 Loan과 BookCategory의 외래 키는 반드시 있어야 하므로 optional = false를 적어 DDL에 not null이 붙게 했다. 같은 @ManyToOne이라도 요구사항 문장이 NULL을 허용하는지에 따라 선언이 달라진다.

    흔한 오해와 함정

    "일대다 단방향이 더 객체지향적이니 더 좋은 설계다"

    부서가 직원을 소유한다는 모델은 객체로는 자연스럽다. 그러나 외래 키는 직원 테이블에 있고, 그 사실은 객체 모델이 바꿀 수 없다. 관리 주체와 저장 위치가 어긋나면 원소마다 UPDATE가 추가되고, NOT NULL 제약과 호출 순서가 얽혀 앞 실험처럼 같은 매핑이 성공하기도 실패하기도 한다. 직원이 부서를 몰라야 할 강한 이유가 없다면 다대일 단방향(필요하면 양방향)이 테이블의 사실에 맞는 모델이다.

    "fetch = LAZY라고 쓰면 지연 로딩된다"

    LAZY는 명세상 공급자에게 주는 힌트이고, 실제로 지연할 수 있는지는 구현 방식이 정한다. 일대일의 mappedBy 쪽처럼 null과 프록시를 구분할 정보가 행에 없으면 Hibernate는 바이트코드 향상 없이 지연할 방법이 없다. 매핑에 LAZY를 썼다는 사실보다 실행 로그에 SELECT가 몇 번 나가는지를 믿어야 한다.

    "@ManyToMany는 편하니까 쓰고, 컬럼이 필요해지면 그때 바꾸면 된다"

    나중에 바꾸는 비용은 생각보다 크다. 연결 테이블에 기본 키가 없던 List 매핑이었다면 데이터 이전 전에 중복 행부터 정리해야 하고, 엔티티로 승격하면 컬렉션을 쓰던 모든 코드가 연결 엔티티를 거치도록 바뀐다. 관계 자체의 속성이 하나라도 예상된다면 처음부터 연결 엔티티로 시작하는 편이 싸다. 정말 속성이 없는 순수한 집합 관계라면 @ManyToMany를 쓰더라도 Set을 써서 연결 테이블에 기본 키가 생기고 DELETE가 한 행만 건드리게 하자.

    "mappedBy 쪽 컬렉션에 넣었으니 저장된다"

    mappedBy 쪽은 거울이다. 다대일 양방향에서 부서의 리스트에만 직원을 넣으면 외래 키는 NULL로 남는다. 반대로 주인 쪽만 고치면 데이터베이스는 맞지만 같은 트랜잭션의 객체 그래프가 어긋난다. 이것은 일대일과 다대다 양방향에도 똑같이 적용된다. 주인을 기준으로 값을 넣고, 편의 메서드로 거울을 함께 맞춘다.

    "일대일이니까 유일 제약은 애너테이션이 알아서 지켜 준다"

    Hibernate 6.6이 스키마를 생성할 때 유일 제약을 붙여 준 것은 사실이다. 그러나 운영 데이터베이스의 스키마는 대개 자동 생성이 아니라 마이그레이션 스크립트로 관리한다. 그 스크립트에 UNIQUE를 빠뜨리면 데이터베이스는 같은 주차 자리를 두 직원에게 배정하는 INSERT를 받아들인다. Hibernate 사용자 가이드에 따르면 양방향 일대일에서 그런 데이터를 다시 읽을 때 Hibernate가 한 행이 넘게 나왔다는 예외를 던진다. 다중성은 데이터베이스 제약이 지킨다는 원칙을 마이그레이션에서도 지켜야 한다.

    다른 회차와의 연결

    이 회차는 연관관계의 모양을 정했다. 그 모양 위에서 일어나는 일은 이후 회차가 하나씩 다룬다. 06회 「고급 매핑」은 상속 관계를 테이블로 옮기는 전략을 다루는데, 조인 전략은 부모 테이블과 자식 테이블을 기본 키 공유로 연결한다는 점에서 이 회차의 @MapsId와 같은 생각을 공유한다. 07회 「프록시와 연관관계 관리」는 이 회차에서 원리만 본 프록시와 지연 로딩, 그리고 cascade와 고아 객체 제거를 다룬다.

    09회와 10회의 JPQL에서는 이 회차에서 정한 연관관계 필드가 조인의 경로가 된다. 다대일은 경로 표현식 한 번으로 따라갈 수 있고, 컬렉션 연관관계는 명시적 조인이 필요하며, 페치 조인은 이 회차에서 본 EAGER 기본값과 mappedBy 일대일의 추가 조회 문제를 쿼리 단위로 해결하는 수단이 된다. 연결 엔티티로 승격한 Loan이나 Enrollment는 JPQL의 조회 대상이 될 수 있다는 점에서도 @ManyToMany의 숨은 테이블과 다르다.

    이 장의 핵심

    네 가지 연관관계 애너테이션은 테이블에서 외래 키, 외래 키와 유일 제약, 연결 테이블 세 가지 형태로 귀결된다. 외래 키를 가진 테이블의 엔티티가 그 외래 키를 관리할 때 SQL이 가장 적고 동작이 예측 가능하다. 일대다 단방향은 엔티티 INSERT 뒤 컬렉션 단계의 UPDATE를, 일대일의 mappedBy 쪽은 지연 로딩 불가를, List로 매핑한 다대다는 전체 삭제 후 재삽입을 비용으로 낸다. 관계 자체에 속성이 생기면 연결 테이블을 엔티티로 승격하고, 변할 수 있는 비즈니스 값은 식별자에서 떼어 둔다.
    외래 키의 위치
    한 컬럼에는 값이 하나만 들어가므로 외래 키는 항상 N 쪽 테이블에 있다. 일대일은 외래 키에 유일 제약을 더하고, 다대다는 외래 키 두 개를 가진 연결 테이블로 표현한다.
    다대일(@ManyToOne)
    객체 참조와 외래 키가 같은 엔티티에 있는 가장 기본적인 매핑이다. 양방향이면 명세상 반드시 다대일 쪽이 주인이며, optional = false를 주면 NOT NULL 제약과 내부 조인으로 바뀐다.
    일대다 단방향
    컬렉션을 가진 엔티티가 반대편 테이블의 외래 키를 관리한다. 엔티티 INSERT 뒤 컬렉션 단계에서 원소마다 UPDATE가 추가로 나가며, @JoinColumn을 생략하면 연결 테이블이 생긴다.
    플러시 실행 순서
    Hibernate 6.6의 ActionQueue는 엔티티 INSERT, 엔티티 UPDATE, 컬렉션 작업, 엔티티 DELETE 순서로 SQL을 실행해 외래 키 제약 위반을 피한다. 일대다 단방향의 UPDATE가 INSERT 뒤에 오는 이유다.
    일대일(@OneToOne)
    외래 키를 주 테이블, 대상 테이블 중 어디에 둘지 고르거나 @MapsId로 기본 키를 공유한다. 양방향에서는 외래 키를 가진 쪽이 주인이다.
    mappedBy 일대일의 즉시 조회
    외래 키가 없는 쪽은 null과 프록시 중 무엇을 넣을지 알려면 상대 테이블을 조회해야 하므로, LAZY로 선언해도 바이트코드 향상 없이는 즉시 조회된다.
    다대다와 컬렉션 타입
    @OrderColumn이 없는 List는 bag으로 해석되어 연결 테이블에 기본 키가 없고, 원소 하나를 지울 때 전체 삭제 후 재삽입한다. Set은 쌍을 기본 키로 삼아 한 행만 지운다.
    연결 엔티티와 대리 키
    관계에 속성이 생기면 연결 테이블을 엔티티로 승격해 다대일 두 개로 푼다. 같은 쌍이 반복될 수 있거나 식별 조건이 바뀔 수 있다면 복합 키 대신 대리 키와 유일 제약을 쓴다.

    연관관계 매핑의 판단은 대부분 "외래 키를 누가 관리하는가"로 정리된다. 운영 중에 저장 로그에서 예상하지 못한 UPDATE가 엔티티 수만큼 찍힌다면 먼저 일대다 단방향 매핑을 의심한다. 대량 등록 배치에서 이 UPDATE는 INSERT 수와 같은 만큼 SQL을 늘리고, 외래 키 컬럼에 NOT NULL을 걸지 못하게 만든다. 다대일 양방향으로 바꾸면 테이블은 그대로 둔 채 SQL만 줄어드므로, 스키마 변경 없이 적용할 수 있는 개선이다.

    일대일은 "어느 쪽에서 더 자주 조회하는가"와 "나중에 다중성이 바뀔 가능성이 있는가"로 외래 키 위치를 정한다. 목록 화면이 대상 쪽 엔티티를 많이 조회하는데 그쪽이 mappedBy라면 행 수만큼 추가 SELECT가 나간다. 이 문제는 대개 성능 테스트나 운영 로그에서야 드러나므로, 설계 단계에서 외래 키를 조회가 많은 쪽으로 옮기거나 @MapsId로 기본 키를 공유하는 쪽으로 결정해 두는 편이 낫다. 반대로 "한 명에게 하나"라는 규칙이 바뀔 가능성이 크다면 대상 테이블에 외래 키를 두어 유일 제약만 풀면 일대다가 되게 하는 판단도 정당하다.

    다대다는 요구사항을 다시 읽는 계기로 삼는다. 관계에 날짜, 상태, 수량 같은 말이 하나라도 붙어 있다면 그것은 관계가 아니라 독립된 사건이며, 연결 엔티티가 맞다. 이때 복합 키를 고를지 대리 키를 고를지는 "같은 쌍이 두 번 나타날 수 있는가", "식별 조건이 바뀔 수 있는가", "이 테이블을 다른 테이블이 외래 키로 참조하는가"로 판단한다. 셋 중 하나라도 그렇다면 대리 키와 유일 제약이 변경에 강하다. 자동 생성 DDL은 컬럼 순서와 제약을 의도와 다르게 만들 수 있으므로, 운영 스키마는 마이그레이션 스크립트로 직접 관리하고 Hibernate의 생성 결과는 검토 자료로만 쓴다.
  • 부서(Department)에 @OneToMany @JoinColumn(name = "department_id")로 직원 리스트를 매핑하고 직원(Employee)에는 부서 참조가 없다. 새 부서 하나와 새 직원 세 명을 persist하고 리스트에 직원 셋을 넣은 뒤 커밋할 때 나가는 SQL의 종류와 개수를 순서대로 적어라. 식별자는 시퀀스 전략이고 시퀀스 조회는 세지 않는다.
  • 직원이 @OneToOne @JoinColumn(name = "parking_spot_id")로 주차 자리를 참조하고, 주차 자리는 @OneToOne(mappedBy = "parkingSpot", fetch = FetchType.LAZY)로 직원을 참조한다. JPQL로 주차 자리 20개를 조회하는 코드가 SELECT를 최대 몇 번 실행할 수 있는지 답하고, 외래 키 위치를 바꾸지 않고 이 문제를 피할 수 있는 매핑 변경을 하나 제시하라.
  • 학생의 강좌 목록을 @ManyToMany List(정렬 컬럼 없음)로 매핑했다. 강좌가 10개인 학생에게서 강좌 하나를 제거하고 커밋할 때 연결 테이블에 나가는 SQL을 적고, Set로 바꿨을 때와 비교하라. 두 경우의 연결 테이블 DDL에서 달라지는 점도 적어라.
  • 온라인 쇼핑몰에서 "회원은 상품을 찜할 수 있고, 찜한 일시를 보여 준다. 찜을 해제한 뒤 다시 찜할 수 있다"는 요구사항이 있다. 이 관계를 매핑할 엔티티와 테이블을 설계하고, 기본 키로 (회원, 상품) 복합 키와 대리 키 중 무엇을 고를지 근거와 함께 답하라.
    •

    1. INSERT 네 번(직원 세 명과 부서 한 건, persist 호출 순서대로) 뒤에 UPDATE 세 번(update Employee set department_id=? where id=?)이 나간다. 직원 INSERT에는 department_id가 포함되지 않는다. 외래 키가 직원 엔티티의 상태가 아니라 부서 컬렉션의 상태이기 때문이다. Hibernate의 ActionQueue는 엔티티 INSERT를 모두 실행한 뒤 컬렉션 작업(새 컬렉션이므로 CollectionRecreateAction)을 실행하고, 그 단계에서 원소마다 외래 키를 UPDATE로 채운다. 다대일 양방향으로 바꾸면 INSERT 네 번으로 끝난다.

    2. 주차 자리 조회 SELECT 1번에, 직원이 배정된 자리마다 직원을 찾는 SELECT가 따라 나가 최대 21번이다. mappedBy 쪽은 자기 행에 외래 키가 없어 null과 프록시 중 무엇을 넣을지 정하려면 직원 테이블을 조회해야 하므로 LAZY가 지켜지지 않는다. 외래 키 위치를 바꾸지 않는 대안으로는, 주차 자리에서 직원으로 가는 참조를 없애 단방향으로 만들고 필요할 때 JPQL로 직원을 조회하는 방법이 있다. Hibernate의 바이트코드 향상을 켜는 방법도 있지만 빌드 설정이 추가된다. 화면에서 직원이 항상 필요하다면 select p from ParkingSpot p left join fetch p.employee처럼 JPQL 페치 조인으로 한 번에 가져오는 것도 방법이다. Hibernate 6.6에서 이 쿼리는 외부 조인 SELECT 한 번으로 끝났다.

    3. List(bag)일 때는 delete from 연결테이블 where student_id=? 한 번 뒤에 남은 9개를 다시 INSERT해 SQL이 10번 나간다. bag은 중복을 허용하므로 연결 행을 (학생, 강좌) 쌍으로 하나만 특정할 수 없어 전체를 지우고 다시 넣는다. Set이면 delete ... where student_id=? and course_id=? 한 번이다. DDL은 List일 때 연결 테이블에 기본 키가 없고, Set일 때 두 외래 키 컬럼을 묶은 기본 키가 생긴다.

    4. 찜(Wish 같은 이름) 엔티티를 두고 회원과 상품에 대해 각각 @ManyToOne을 두며, 찜한 일시 필드를 추가한다. "찜한 일시"라는 관계의 속성이 있으므로 @ManyToMany로는 매핑할 수 없다. 기본 키는 해제 방식에 따라 달라진다. 해제할 때 행을 삭제한다면 같은 쌍이 동시에 둘 존재하지 않으므로 복합 키도 가능하다. 하지만 해제 이력을 남기려고 행을 지우지 않고 상태만 바꾼다면 같은 쌍이 여러 번 나타나므로 복합 키는 쓸 수 없다. 요구사항이 바뀔 여지를 생각하면 대리 키를 두고, 행을 삭제하는 설계라면 (회원, 상품)에 유일 제약을 거는 쪽이 변경에 강하다.

     직원이 @ManyToOne으로 부서를 참조하고, 부서는 @OneToMany(mappedBy = "department")로 직원 리스트를 가진다. 새 직원을 만들어 부서의 리스트에만 add하고 직원의 department 필드는 설정하지 않은 채 persist·커밋했다. 데이터베이스의 결과는? 직원 행의 department_id에 부서 ID가 저장된다. 리스트에 넣었으므로 Hibernate가 반대편을 자동으로 채운다. 직원 행은 저장되지만 department_id는 NULL이다. 외래 키는 주인인 Employee.department만 보고 정해진다. Hibernate가 매핑 불일치를 감지해 커밋 시 예외를 던진다. 직원 INSERT 뒤에 컬렉션 단계의 UPDATE로 department_id가 채워진다. 양방향에서 mappedBy 쪽 컬렉션은 데이터베이스에 아무것도 쓰지 않는 거울이다. 외래 키는 주인 필드 값으로만 결정되므로 NULL이 저장된다. 컬렉션 단계의 UPDATE는 일대다 단방향(컬렉션이 주인)일 때의 동작이고, Hibernate는 이 불일치를 오류로 검사하지 않는다. 일대다 단방향 매핑(@OneToMany @JoinColumn)으로 부서와 직원을 저장하면 INSERT 뒤에 UPDATE가 나간다. 그 이유로 가장 정확한 것은? 직원 테이블에 외래 키 제약이 없어서 Hibernate가 안전하게 두 번에 나눠 쓴다. 시퀀스 전략이라 직원 INSERT 시점에 부서 ID를 아직 모르기 때문이다. 외래 키 값이 직원 엔티티가 아니라 부서 컬렉션의 상태이고, 플러시가 엔티티 INSERT를 모두 끝낸 뒤 컬렉션 작업을 실행하기 때문이다. JPA 명세가 일대다 관계는 반드시 UPDATE로 저장하라고 정했기 때문이다. 시퀀스 전략에서는 persist 시점에 이미 ID가 할당되므로 "ID를 몰라서"는 이유가 아니다. 엔티티 INSERT는 엔티티 자신의 상태만 쓰는데 department_id는 부서 컬렉션이 관리하는 값이고, Hibernate의 ActionQueue는 엔티티 INSERT 뒤에 컬렉션 작업을 실행하므로 외래 키는 UPDATE로 채워진다. 명세는 SQL 형태를 규정하지 않는다. 직원 테이블에 parking_spot_id 외래 키가 있는 양방향 일대일에서, ParkingSpot.employee에 fetch = FetchType.LAZY를 지정했는데도 주차 자리를 조회하면 직원 SELECT가 바로 나간다. 그 이유는? 주차 자리 행에는 직원을 가리키는 컬럼이 없어서, 필드에 null을 넣을지 프록시를 넣을지 정하려면 직원 테이블을 조회해야 하기 때문이다. @OneToOne의 명세 기본값이 EAGER라서 LAZY 지정이 무시되기 때문이다. 주차 자리 엔티티가 final 클래스라 프록시를 만들 수 없기 때문이다. 유일 제약을 검사하려고 Hibernate가 항상 상대 테이블을 읽기 때문이다. 프록시 기반 지연 로딩은 로딩 시점에 null과 프록시 중 하나를 골라야 한다. 외래 키를 가진 쪽은 자기 행의 값으로 판단할 수 있지만 mappedBy 쪽은 상대 테이블을 조회해야만 알 수 있고, Hibernate는 그렇게 조회한 결과로 필드를 바로 채운다. 명세 기본값은 명시한 LAZY로 덮였고, final 여부나 유일 제약 검사는 이 동작의 원인이 아니다. 재수강이 허용되는 수강 신청을 연결 엔티티 Enrollment로 설계한다. 기본 키 선택으로 가장 적절한 것은? (student_id, course_id) 복합 키. 같은 쌍의 중복을 기본 키가 막아 주므로 가장 안전하다. 기본 키 없이 @ManyToMany List로 매핑한다. 중복을 허용하므로 재수강을 표현할 수 있다. (student_id, course_id) 복합 키에 grade 컬럼을 추가해 구분한다. 대리 키를 두고, 필요하면 (student_id, course_id, 학기) 같은 조합에 유일 제약을 건다. 재수강이 허용되면 같은 (학생, 강좌) 쌍이 여러 번 나타나므로 그 쌍을 기본 키로 쓸 수 없다. 성적은 식별 조건이 아니라 속성이다. @ManyToMany는 신청 일시나 성적 같은 관계의 속성을 담을 수 없고, List(bag)는 원소 하나를 지울 때 전체 삭제 후 재삽입을 한다. 대리 키를 두면 식별 조건이 바뀌어도 유일 제약만 고치면 된다.
    다중성(multiplicity)
    한쪽 엔티티 하나에 반대쪽 엔티티가 몇 개까지 연결될 수 있는지를 나타내는 성질. 다대일, 일대다, 일대일, 다대다로 나뉜다.
    연관관계의 주인(owning side)
    양방향 관계에서 외래 키를 관리하는 쪽. 명세상 일대다·다대일은 다 쪽, 일대일은 외래 키를 가진 쪽이 주인이고, 다대다는 어느 쪽이든 될 수 있다.
    연결 테이블(join table)
    두 테이블을 잇는 외래 키들을 담는 별도의 테이블. 다대다 관계를 표현하거나 일대다 단방향의 기본 매핑으로 쓰인다.
    유일 제약(unique constraint)
    컬럼 값이 테이블 안에서 중복되지 않도록 하는 제약. 외래 키에 걸면 일대일 다중성을 데이터베이스가 지키게 된다. MySQL에서는 유일 인덱스로 구현된다.
    ActionQueue
    Hibernate가 플러시 때 실행할 INSERT, UPDATE, 컬렉션 작업, DELETE를 종류별로 모아 정해진 순서로 실행하는 내부 구조. 외래 키 제약 위반을 피하는 순서로 설계되어 있다.
    bag
    순서를 유지하지 않고 중복을 허용하는 컬렉션 의미. Hibernate는 기본 설정에서 @OrderColumn이 없는 List를 bag으로 해석한다.
    대리 키(surrogate key)
    업무 의미가 없는 값으로 만든 기본 키. 업무 조건이 바뀌어도 식별자가 영향을 받지 않는다.
    파생 식별자(derived identity)
    연관관계로 참조하는 엔티티의 식별자를 자기 식별자(또는 그 일부)로 쓰는 방식. @MapsId나 @Id를 붙인 @ManyToOne·@OneToOne으로 표현한다.
    바이트코드 향상(bytecode enhancement)
    Hibernate가 엔티티 클래스의 바이트코드를 변경해 필드 접근을 가로채게 하는 기능. 프록시로는 불가능한 일대일 mappedBy 쪽의 지연 로딩 등에 쓰인다.
