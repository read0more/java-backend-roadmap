    이 회차의 질문: 클래스 하나가 테이블 하나가 되려면

    앞 회차에서 영속성 컨텍스트가 엔티티를 1차 캐시에 보관하고, 쓰기 지연 저장소에 SQL을 모았다가 플러시 시점에 데이터베이스로 보낸다는 것을 보았다. 그런데 그 SQL은 어디에서 왔을까. 클래스 이름이 테이블 이름이 되고 필드 이름이 컬럼 이름이 되며, 어떤 필드가 기본 키인지, 기본 키 값은 누가 언제 만드는지를 누군가 알려 주어야 Hibernate가 insert into ... values (?, ?) 같은 문장을 만들 수 있다. 그 "누군가"가 이 회차의 주제인 매핑 정보(mapping metadata)다. 자바 코드에서는 애너테이션의 모습으로 나타나지만, 실제로는 객체 세계와 테이블 세계를 잇는 번역표다.

    번역표가 잘못되면 어떤 일이 생기는지 세 장면으로 보자. 첫째, 열거형을 순서 번호로 저장해 두었다가 상수 하나를 중간에 끼워 넣었더니, 이미 저장된 행들의 의미가 조용히 바뀐다. 예외도 로그도 없다. 둘째, 기본 키를 데이터베이스가 만들게 했더니 persist()를 호출하는 순간 INSERT가 실행되어, 앞 회차에서 배운 쓰기 지연이 그 엔티티에는 통하지 않는다. 셋째, 개발할 때 편했던 스키마 자동 갱신을 운영 데이터베이스에도 켜 두었더니, 필드를 지운 뒤에도 NOT NULL 컬럼이 테이블에 남아 그 테이블의 모든 INSERT가 실패한다. 세 장면 모두 애너테이션 한 줄에서 시작한다. 이 회차는 그 한 줄이 아래에서 무엇을 바꾸는지 따라간다.

    JPA의 매핑 애너테이션은 네 묶음으로 나눌 수 있다. 객체와 테이블을 잇는 @Entity, @Table. 필드와 컬럼을 잇는 @Column, @Enumerated, @Lob, @Transient. 기본 키를 정하는 @Id, @GeneratedValue. 그리고 객체 참조를 외래 키로 옮기는 연관관계 애너테이션. 이 회차는 앞의 세 묶음과 스키마 자동 생성을 다룬다. 연관관계는 04회와 05회, 상속 매핑과 @MappedSuperclass는 06회, 임베디드 타입은 08회의 몫이다.

    이 회차의 실험은 모두 Hibernate ORM 6.6.53.Final, H2 2.3.232, JDK 21(Temurin 21.0.13)에서 직접 실행했다. MySQL용 DDL은 Hibernate의 MySQLDialect에 MySQL 8.0을 대상으로 지정해 생성한 스크립트를 그대로 옮겼다. 스프링 부트 없이 Hibernate만 띄웠기 때문에, 따로 밝히지 않으면 테이블·컬럼 이름이 클래스·필드 이름 그대로 나온다. 스프링 부트가 이름을 어떻게 바꾸는지는 이름 전략을 다룰 때 따로 설명하고, 그 전략을 켠 실험에는 그렇다고 적는다. Hibernate 버전이나 데이터베이스에 따라 출력이 달라질 수 있는 부분은 그때마다 범위를 밝힌다.

    매핑 정보는 언제 읽히는가: 부트 시점의 메타모델

    애너테이션은 스스로 아무 일도 하지 않는다. @Entity는 보존 정책(retention)이 RUNTIME인 애너테이션이어서, 컴파일러가 클래스 파일에 기록해 두고 JVM이 클래스를 로딩한 뒤에도 리플렉션으로 읽을 수 있다. 읽는 쪽은 JPA 구현체다. Hibernate는 EntityManagerFactory(Hibernate 쪽 이름으로는 SessionFactory)를 만드는 동안 등록된 엔티티 클래스들의 애너테이션을 읽어, 엔티티 이름·테이블·컬럼·자바 타입과 SQL 타입의 대응·식별자 생성 방식을 담은 내부 모델을 만든다. 이것을 메타모델(metamodel)이라고 부른다. 이후의 모든 동작, 즉 SQL 생성, 1차 캐시의 키 구성, 조회 결과를 객체로 바꾸는 일은 이 메타모델을 참조한다.

    이 순서를 알면 실패가 언제 드러나는지 예측할 수 있다. 애너테이션 해석과 스키마 검증 단계에서 걸리는 오류(@Id가 없는 엔티티, 스키마 불일치 등)는 애플리케이션이 시작하다가 실패한다. 반면 실행해 봐야 알 수 있는 오류는 해당 코드가 처음 실행될 때 드러난다. 아래에서 볼 "기본 생성자 없음"이 좋은 예다. Hibernate는 부트 시점에 그 사실을 알아채고 INFO 로그 한 줄만 남긴 뒤 계속 진행하고, 실제 예외는 그 엔티티를 처음 조회하는 순간에 터진다.

    메타모델이 미리 만들어진다는 사실은 생성되는 SQL의 모양에서도 보인다. 이 회차 뒤쪽 실험에서 MeetingRoom 엔티티를 저장할 때 Hibernate가 보낸 문장은 insert into meeting_room (capacity,code,created_at,floor,guide,name,status,id) values (?,?,?,?,?,?,?,default)였다. floor와 guide는 값이 null이었는데도 컬럼 목록에 들어 있다. 기본 설정의 Hibernate는 엔티티 인스턴스의 현재 값이 아니라 매핑 정보만 보고 INSERT 문의 모양을 정하기 때문이다. 값이 있는 컬럼만 넣고 싶다면 Hibernate 전용 애너테이션 @DynamicInsert를 쓰는 방법이 있지만, 문장 모양이 매번 달라지므로 대개는 기본 동작을 그대로 쓴다.

    애너테이션이 붙은 자바 클래스가 부트 시점에 메타모델로 해석되고, 방언을 거쳐 DDL과 INSERT 문으로 나뉘어 나가는 흐름을 보여 준다. 왼쪽에 자바 클래스 카드 하나를 그린다. 카드 제목은 "MeetingRoom.java"이고 안에 "@Entity", "@Id", "@Column" 세 줄이 보인다. 카드에서 오른쪽으로 화살표가 나가 가운데의 큰 상자 "메타모델"로 들어간다. 화살표 위 라벨은 "부트 시점 리플렉션". 가운데 상자 아래에 작은 상자 "방언(Dialect)"이 붙어 있다. 가운데 상자에서 오른쪽으로 화살표 두 개가 갈라진다. 위쪽 화살표는 "DDL (create table)" 문서 아이콘으로, 아래쪽 화살표는 "INSERT / SELECT" 문서 아이콘으로 간다. 맨 오른쪽에 데이터베이스 원통 "MySQL"이 있고 두 문서에서 화살표가 들어간다. 평면적인 기술 다이어그램 스타일, 흰 배경, 파랑과 회색 위주. 애너테이션은 부트 시점에 한 번 해석되어 메타모델이 되고, 이후의 DDL과 SQL은 모두 이 메타모델에서 나온다.

    @Entity: JPA가 다룰 수 있는 클래스의 조건

    @Entity가 붙은 클래스를 엔티티라고 하고, JPA는 이 클래스만 영속성 컨텍스트에서 관리한다. Jakarta Persistence 3.1 명세 2.1절은 엔티티 클래스에 몇 가지 조건을 건다. 인자 없는 생성자(no-arg constructor)가 있어야 하고 그 생성자는 public 또는 protected여야 한다. 최상위 클래스(top-level class)여야 한다. 그리고 명세의 표현으로 "The entity class must not be final."이며, 메서드와 영속 대상 인스턴스 변수도 final이면 안 된다. 열거형이나 인터페이스는 엔티티가 될 수 없다. 이 조건들은 외우는 규칙이 아니라, 구현체가 객체를 다루는 방식에서 나온 요구 사항이다. 하나씩 이유를 보자.

    기본 생성자: 조회 결과로 객체를 만들 때 필요하다

    인자 있는 생성자만 가진 엔티티를 만들어 실제로 돌려 보면 이 조건이 어디에서 필요한지 정확히 드러난다.

    @Entity
public class Coupon {
    @Id
    private Long id;
    private String code;

    public Coupon(Long id, String code) {   // 인자 있는 생성자만 있다
        this.id = id;
        this.code = code;
    }
}

    세 가지를 관찰할 수 있다. 첫째, Hibernate는 부트 시점에 기본 생성자가 없다는 것을 이미 알았지만 INFO 로그만 남기고 기동을 계속했다. 둘째, 저장은 성공했다. persist()에 넘긴 객체는 애플리케이션이 이미 만든 것이므로, Hibernate는 그 필드 값을 읽어 INSERT의 파라미터에 채우기만 하면 된다. 셋째, 조회는 SELECT까지 실행된 뒤에 실패했다. 데이터베이스에서 받은 행으로 엔티티를 만들려면 먼저 빈 객체를 하나 만들고, 그다음 ResultSet의 각 컬럼 값을 필드에 채워야 한다. Hibernate는 생성자의 인자로 무엇을 넘겨야 하는지 모르므로, 인자 없는 생성자로 빈 객체를 만드는 방법을 쓴다. 그 생성자가 없으니 이 단계에서 멈춘 것이다.

    그렇다면 왜 public이 아니라 protected를 권하는가. 기본 생성자는 JPA를 위한 장치이지 애플리케이션 코드가 쓰라고 연 문이 아니다. 아무 값도 채워지지 않은 엔티티를 애플리케이션이 마음대로 만들 수 있으면, 필수 값이 빠진 객체가 시스템을 돌아다니게 된다. protected는 같은 패키지와 하위 클래스에만 접근을 허용하므로, 일반 코드에서의 new Coupon()은 막으면서 JPA 구현체와 프록시 하위 클래스는 쓸 수 있게 한다. Hibernate 사용자 가이드는 런타임 프록시를 생성하려면 생성자가 최소한 패키지 가시성(package visibility)이어야 한다고 적는다. 명세가 허용하는 범위(public, protected)와 Hibernate가 실제로 요구하는 범위가 다르다는 점도 기억해 두자. 이식성을 생각하면 명세의 범위인 protected를 쓰는 편이 안전하다.

    final 금지: 프록시는 하위 클래스다

    final 금지의 이유는 07회에서 다룰 지연 로딩(lazy loading) 프록시에 있다. Hibernate는 연관된 엔티티를 실제로 조회하지 않고 대역 객체를 먼저 돌려줄 수 있는데, 이 대역 객체는 실행 중에 바이트코드로 만든 엔티티의 하위 클래스다. 하위 클래스는 메서드를 오버라이드해서, 메서드가 처음 호출되는 순간 데이터베이스를 조회하도록 끼어든다. Java 언어 명세상 final 클래스는 하위 클래스를 가질 수 없고(JLS §8.1.1.2), final 메서드는 오버라이드할 수 없다. 클래스가 final이면 프록시를 아예 만들 수 없고, 메서드가 final이면 그 메서드 호출을 프록시가 가로채지 못해 초기화되지 않은 프록시의 빈 필드를 그대로 읽게 된다. Hibernate 사용자 가이드도 final 클래스를 저장할 수는 있지만 지연 로딩용 프록시를 쓸 수 없다고 설명한다. 영속 대상 필드에 final을 붙이면 안 되는 이유는 앞의 기본 생성자 이야기와 같다. 빈 객체를 먼저 만들고 나중에 값을 채우는 구조에서, 생성자에서만 값을 넣을 수 있는 final 필드는 맞지 않는다.

    접근 방식: 필드냐 프로퍼티냐

    Hibernate가 엔티티의 값을 읽고 쓸 때 필드를 직접 다루는지, getter·setter를 거치는지를 접근 방식(access type)이라고 한다. 명세 2.3.1절에 따르면 기본 접근 방식은 매핑 애너테이션이 어디에 붙어 있는지로 정해진다. 인스턴스 변수에 붙어 있으면 필드 접근(field access)이고, 이때 구현체는 인스턴스 변수에 직접 접근한다. getter에 붙어 있으면 프로퍼티 접근(property access)이고, 구현체는 getter와 setter를 호출한다. 실무에서는 대개 @Id를 필드에 붙이므로 필드 접근이 된다. 필드 접근에서는 setter가 없어도 Hibernate가 값을 채울 수 있다. 그래서 엔티티에 setter를 열지 않고 의미 있는 메서드로만 상태를 바꾸는 설계가 가능하다. 반대로 프로퍼티 접근에서 getter에 계산 로직을 넣으면 Hibernate가 그 계산 결과를 저장하게 되므로 의도치 않은 값이 저장될 수 있다. 한 엔티티 안에서 두 방식을 섞어야 하면 @Access로 명시한다.

    엔티티 이름

    @Entity의 name 속성은 엔티티 이름이다. 기본값은 패키지를 뺀 클래스 이름이고, 이 이름은 JPQL에서 엔티티를 가리킬 때 쓴다(select c from Coupon c). 테이블 이름이 아니라는 점에 주의한다. 테이블 이름은 @Table이 정하고, 지정하지 않으면 엔티티 이름에서 출발한다. 서로 다른 패키지에 같은 이름의 클래스가 있고 둘 다 엔티티라면 JPQL에서 쓰는 엔티티 이름이 겹치므로, 하나에 다른 엔티티 이름을 붙여 구분해야 한다.

    @Table과 이름이 정해지는 두 단계

    @Table은 엔티티가 매핑될 테이블을 지정한다. Jakarta Persistence 3.1 기준으로 속성은 name(테이블 이름), catalog, schema, uniqueConstraints(유니크 제약), indexes(인덱스)이다. 뒤의 두 속성은 스키마 자동 생성에서만 쓰이며 아래에서 자세히 본다. @Table을 생략하면 테이블 이름은 엔티티 이름을 바탕으로 정해진다.

    "바탕으로"라고 쓴 데는 이유가 있다. Hibernate는 이름을 두 단계로 정한다. 먼저 암묵적 이름 전략(implicit naming strategy)이 애너테이션에 이름이 없을 때 쓸 논리 이름(logical name)을 정한다. 필드 createdAt의 논리 컬럼 이름은 createdAt이다. 다음으로 물리 이름 전략(physical naming strategy)이 논리 이름을 실제 데이터베이스에 쓸 물리 이름(physical name)으로 바꾼다. 순수 Hibernate의 기본 물리 전략은 아무것도 바꾸지 않는다. 이 회차의 실험에서 이름 전략을 따로 지정하지 않았을 때 Hibernate가 insert into meeting_room (capacity,code,createdAt,...)처럼 필드 이름을 그대로 컬럼 이름으로 쓴 것이 그 결과다.

    스프링 부트는 다르다. 스프링 부트 문서에 따르면 부트는 물리 이름 전략으로 Hibernate의 CamelCaseToUnderscoresNamingStrategy를 기본 설정하고, 이 전략은 점을 밑줄로, 카멜 케이스를 밑줄로 바꾸며 테이블 이름을 소문자로 만든다. 문서의 예로는 TelephoneNumber 엔티티가 telephone_number 테이블에 매핑된다. 같은 엔티티를 이 전략을 켜고 띄우면 컬럼이 created_at이 된다. 하나 더 알아 둘 점은, 물리 이름 전략이 애너테이션으로 직접 지정한 이름에도 적용된다는 것이다. @Column(name = "orderedAt")이라고 써도 이 전략 아래에서는 ordered_at 컬럼이 만들어졌다. 물리 전략은 "이름이 어디서 왔는지"를 따지지 않고 마지막에 모든 이름을 한 번 더 변환하는 단계이기 때문이다. 기존 스키마의 카멜 케이스 컬럼에 맞춰야 한다면 애너테이션이 아니라 물리 전략을 바꿔야 한다.

    테이블 이름에서 자주 만나는 함정은 예약어다. 주문을 뜻하는 엔티티를 Order라는 이름 그대로 두면 테이블 이름도 Order가 되는데, ORDER는 SQL의 예약어다. H2에서 실험해 보면 Hibernate가 보낸 drop table if exists Order cascade와 create table Order (...)가 모두 구문 오류로 실패했다. 더 위험한 점은, 이 실패가 경고(WARN) 로그로만 남고 애플리케이션 기동은 정상적으로 끝났다는 것이다(Hibernate 6.6 기본 설정, 종료 코드 0). 테이블이 없는 채로 서비스가 뜨고, 첫 INSERT에서야 오류가 난다. @Table(name = "orders")처럼 예약어가 아닌 이름을 주는 것이 가장 단순한 해결이다.

    데이터베이스 스키마 자동 생성

    메타모델에는 테이블을 만드는 데 필요한 정보가 이미 다 들어 있다. 테이블 이름, 컬럼 이름과 타입, 기본 키, 제약까지. 그래서 JPA 구현체는 애플리케이션이 시작할 때 이 정보로 DDL을 만들어 실행할 수 있다. Hibernate에서는 hibernate.hbm2ddl.auto 속성이 이 기능을 제어한다. Hibernate 6.6의 org.hibernate.tool.schema.Action에 정의된 주요 값과 의미는 다음과 같다.

    값시작할 때종료할 때쓰임
    none아무것도 하지 않는다-운영. 스키마는 별도 도구로 관리
    create-onlyCREATE만 실행(기존 객체를 지우지 않음)-빈 데이터베이스에 처음 만들 때
    dropDROP만 실행-정리용
    createDROP 후 CREATE-로컬 개발, 초기 데이터 실험
    create-dropDROP 후 CREATEDROP테스트. 끝나면 흔적을 남기지 않는다
    validate매핑과 실제 스키마를 비교해 다르면 기동 실패-운영·스테이징의 안전장치
    update부족한 테이블·컬럼 등을 추가하는 DDL 실행-개인 개발 환경 정도

    JPA 표준에도 같은 역할의 속성이 있다. jakarta.persistence.schema-generation.database.action이고, 값은 none, create, drop-and-create, drop이다. 표준 속성에는 Hibernate의 update와 validate에 해당하는 값이 없다. 스프링 부트에서는 spring.jpa.hibernate.ddl-auto로 설정하는데, 부트의 설정 메타데이터는 이 속성을 hibernate.hbm2ddl.auto의 지름길(shortcut)이라고 설명한다. 기본값이 환경에 따라 다르다는 점이 중요하다. 스프링 부트 문서에 따르면 JDBC URL과 커넥션 타입을 보고 hsqldb, h2, derby 같은 내장 데이터베이스로 판단되고 Flyway나 Liquibase 같은 스키마 관리 도구가 감지되지 않으면 기본값은 create-drop이고, 그 밖의 모든 경우에는 none이다. 그래서 H2로 개발하다가 MySQL로 바꾸면 테이블이 갑자기 만들어지지 않는다. 설정을 바꾼 적이 없는데 동작이 달라지는 이유가 이것이다.

    create, update, validate가 실제로 보내는 문장

    세 모드의 차이를 같은 테이블로 확인해 보자. 처음에는 id, name, price(int) 세 필드를 가진 Product 엔티티로 띄운다. 그다음 price를 지우고 name에 @Column(length = 100)을 주고 Integer stock을 추가한 두 번째 버전으로 다시 띄운다. 마지막으로 price를 String으로 바꾼 세 번째 버전을 validate로 띄운다.

    #### v1 / hbm2ddl.auto=create
Hibernate: drop table if exists product cascade
Hibernate: create table product (price integer not null, id bigint not null, name varchar(255), primary key (id))
#### v2 / hbm2ddl.auto=update
Hibernate: alter table if exists product alter column name set data type varchar(100)
Hibernate: alter table if exists product add column stock integer
#### v3 / hbm2ddl.auto=validate
org.hibernate.tool.schema.spi.SchemaManagementException: Schema-validation: wrong column type encountered in column [price] in table [product]; found [integer (Types#INTEGER)], but expecting [varchar(255) (Types#VARCHAR)]

    create는 기존 테이블을 지우고 새로 만든다. 데이터도 함께 사라진다. update는 새 필드에 해당하는 stock 컬럼을 추가했고, 이 버전과 H2 조합에서는 name의 길이 변경도 반영했다. 그러나 엔티티에서 사라진 price 컬럼은 지우지 않았다. update는 "매핑에 있는데 데이터베이스에 없는 것"을 추가하는 쪽으로 설계되어 있고, 매핑에서 사라진 것을 지우지는 않는다. 데이터를 잃지 않으려는 보수적인 선택이지만, 이 선택이 바로 함정이 된다. validate는 아무것도 바꾸지 않고 비교만 하다가, 컬럼 타입이 다르자 기동 자체를 실패시켰다.

    update의 함정을 끝까지 따라가 보자. 두 번째 버전의 엔티티로 행 하나를 저장하면 어떻게 될까. 테이블에는 여전히 price integer not null 컬럼이 있다. 엔티티는 이 컬럼을 모르므로 INSERT 문에 넣지 않는다. 데이터베이스는 값이 없는 NOT NULL 컬럼을 받아들이지 않는다.

    [PRICE, ID, NAME, STOCK]
ConstraintViolationException <- org.h2.jdbc.JdbcSQLIntegrityConstraintViolationException: NULL not allowed for column "PRICE"

    첫 줄은 update 후 테이블의 컬럼 목록이다. 지운 필드의 컬럼이 그대로 남아 있고, 그 때문에 이 테이블의 모든 INSERT가 실패한다. 개발자의 의도는 "price를 없앤다"였지만 데이터베이스는 그 의도를 모른다. 운영 환경에서 update를 쓰지 않는 이유가 여기에 있다. 스키마 변경은 되돌릴 수 없는 일이 많고(컬럼 삭제, 타입 축소), 큰 테이블에서는 ALTER TABLE 자체가 오래 걸리거나 잠금을 잡을 수 있다. 이런 변경은 사람이 검토한 SQL로, 언제 어떤 순서로 적용됐는지 기록되는 방식으로 해야 한다. Flyway나 Liquibase 같은 마이그레이션 도구가 그 일을 한다. 정리하면 개인 개발 환경에서는 create나 update로 빠르게 반복하고, 여럿이 쓰는 개발 서버와 스테이징, 운영에서는 none이나 validate를 쓰며 스키마는 마이그레이션 도구로 관리하는 것이 일반적인 구분이다.

    위 출력의 <- 왼쪽은 Hibernate가 던진 예외, 오른쪽은 그 근본 원인인 JDBC 드라이버의 예외로, 실험 코드가 둘을 이어 출력한 것이다. 자동 생성 DDL은 시작점으로 쓰기에는 좋다. 엔티티를 만든 뒤 create로 한 번 띄워 생성된 DDL을 복사하고, 그것을 다듬어 첫 마이그레이션 스크립트로 삼는 방식이 흔하다.

    DDL 생성 기능과 런타임 검사는 다른 이야기다

    매핑 애너테이션 중에는 스키마를 만들 때 쓰이는 정보가 있다. @Column의 nullable, length, unique, precision, scale, columnDefinition, @Table의 uniqueConstraints와 indexes가 그렇다. 이 정보는 CREATE TABLE 문에 NOT NULL, varchar의 길이, UNIQUE 제약, 인덱스로 반영된다. 흔히 "이 속성들은 DDL 생성에만 쓰이고 실행 로직에는 영향을 주지 않는다"고 정리하는데, 절반만 맞다. 실제로 확인해 보자.

    회의실 엔티티의 name에 @Column(nullable = false, length = 50), code에 @Column(nullable = false, length = 10)을 주었다. 그리고 이름이 null인 회의실과, 코드가 19자인 회의실을 저장해 보았다.

    ## name = null, check_nullability 기본값
org.hibernate.PropertyValueException: not-null property references a null or transient value: rs.MeetingRoom.name
## name = null, hibernate.check_nullability=false
Hibernate: insert into meeting_room (capacity,code,createdAt,floor,guide,name,status,id) values (?,?,?,?,?,?,?,default)
org.hibernate.exception.ConstraintViolationException: could not execute statement [NULL not allowed for column "NAME"; ...
## code = "A-303-TOO-LONG-CODE"
org.hibernate.exception.DataException
  root: org.h2.jdbc.JdbcSQLDataException: Value too long for column "CODE CHARACTER VARYING(10)": "'A-303-TOO-LONG-CODE' (19)"

    첫 번째 경우에는 SQL이 한 줄도 나가지 않았다. Hibernate가 INSERT를 만들기 전에 nullable = false인 속성이 null인 것을 보고 직접 예외를 던졌다. 이 검사는 hibernate.check_nullability 설정이 켜져 있을 때 일어난다. Hibernate 6.6 Javadoc에 따르면 이 설정은 Bean Validation이 클래스패스에 있고 애너테이션을 쓰는 경우 기본적으로 꺼지고, 그 밖의 경우에는 켜진다. 이 실험의 클래스패스에는 Bean Validation이 없었으므로 켜진 상태였다. 두 번째 경우처럼 설정을 끄면 INSERT가 데이터베이스까지 가고, 데이터베이스의 NOT NULL 제약이 거부한다. 세 번째 경우인 길이 초과는 Hibernate가 검사하지 않았다. 문장이 데이터베이스로 갔고 데이터베이스가 거부했다.

    정리하면 length, unique, precision, 인덱스는 DDL을 만들 때만 쓰이고 실행 시점에 Hibernate가 검사하지 않는다. nullable은 DDL에도 쓰이고, 설정에 따라 실행 시점 검사에도 쓰인다. 어느 쪽이든 최종 방어선은 데이터베이스의 제약이다. 자동 생성을 끄고 마이그레이션 도구로 스키마를 관리하면, 애너테이션의 length = 10과 실제 컬럼의 varchar(20)이 어긋나도 아무도 알려 주지 않는다. 애너테이션에 제약을 적어 두는 것은 여전히 가치가 있다. 엔티티만 읽어도 테이블의 제약을 알 수 있는 문서 역할을 하고, validate 모드가 일부 불일치(타입 등)를 잡아 준다.

    유니크 제약에 이름을 붙이는 이유

    @Column(unique = true)는 가장 간단한 유니크 제약 선언이지만, 제약 이름을 정할 수 없다. 같은 엔티티의 email 필드에 unique = true를 주고 MySQL용 DDL을 만들면 다음과 같다.

    alter table meeting_room
   add constraint uk_room_code unique (code);

alter table meeting_room
   add constraint UKq73kh2hy7yoyp4he852aud5aa unique (email);

    위의 것은 @Table(uniqueConstraints = @UniqueConstraint(name = "uk_room_code", columnNames = "code"))로 이름을 준 제약이고, 아래가 unique = true가 만든 제약이다. 아래 이름은 Hibernate가 테이블과 컬럼 정보로 만든 문자열이다. 운영 중 중복 키 오류가 나면 MySQL은 오류 메시지에 제약(키) 이름을 담아 준다. 그때 uk_room_code는 무엇이 겹쳤는지 바로 말해 주지만, 해시처럼 생긴 이름은 스키마를 뒤져야 알 수 있다. 여러 컬럼을 묶은 복합 유니크 제약도 @Table 쪽에서만 선언할 수 있다. 그래서 제약에는 @Table로 이름을 붙이는 편이 낫다.

    필드와 컬럼 매핑: 자바 타입이 SQL 타입이 되는 규칙

    이제 필드 하나하나가 컬럼이 되는 규칙을 보자. 기준으로 삼을 엔티티는 회의실이다. 이 회차 끝의 실전 예제에서도 그대로 쓴다.

    @Entity
@Table(name = "meeting_room",
       uniqueConstraints = @UniqueConstraint(name = "uk_meeting_room_code", columnNames = "code"))
public class MeetingRoom {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(nullable = false, length = 10)
    private String code;                 // 예: "A-301"

    @Column(nullable = false, length = 50)
    private String name;

    private int capacity;                // 기본형: null을 담을 수 없다

    private Integer floor;               // 래퍼형: null 허용

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private RoomStatus status;           // enum RoomStatus { OPEN, CLOSED }

    @Lob
    private String guide;                // 이용 안내문(긴 텍스트)

    private LocalDateTime createdAt;

    @Transient
    private int todayReservationCount;   // 화면 표시용, 저장하지 않는다

    protected MeetingRoom() {}           // JPA용

    public MeetingRoom(String code, String name, int capacity) {
        this.code = code;
        this.name = name;
        this.capacity = capacity;
        this.status = RoomStatus.OPEN;
        this.createdAt = LocalDateTime.now();
    }

    public Long getId() { return id; }
}

    스프링 부트와 같은 물리 이름 전략(CamelCaseToUnderscoresNamingStrategy)을 켜고 MySQLDialect로 생성한 DDL은 다음과 같다.

    create table meeting_room (
    capacity integer not null,
    floor integer,
    created_at datetime(6),
    id bigint not null auto_increment,
    code varchar(10) not null,
    name varchar(50) not null,
    guide longtext,
    status enum ('CLOSED','OPEN') not null,
    primary key (id)
) engine=InnoDB;

alter table meeting_room
   add constraint uk_meeting_room_code unique (code);

    한 줄씩 읽어 보자. int capacity는 아무 설정도 하지 않았는데 not null이 붙었다. 자바의 기본형 int는 null을 담을 수 없으므로, Hibernate는 이 컬럼에 null이 들어가면 안 된다고 판단한다. 같은 정수라도 래퍼형 Integer floor는 null을 허용한다. @Transient를 붙인 todayReservationCount는 테이블에 없다. @Lob을 붙인 String은 MySQL에서 longtext가 되었다. 열거형 필드는 MySQL의 enum 타입이 되었는데, 이 부분은 아래에서 따로 다룬다. 컬럼 순서가 필드 선언 순서와 다르다는 점도 눈에 띈다. Hibernate 6.6에는 DDL의 컬럼 순서를 정하는 전략 설정(hibernate.column_ordering_strategy)이 따로 있고, 이 출력은 그 기본 전략이 정한 순서다. 컬럼 순서가 중요하다면 자동 생성에 기대지 말고 DDL을 직접 작성해야 한다.

    기본형과 래퍼형의 차이는 조회에서도 드러난다

    기본형 필드가 문제를 일으키는 것은 DDL보다 조회 쪽이다. 기존 데이터베이스에 엔티티를 맞추다 보면, 테이블의 컬럼은 null을 허용하는데 엔티티 필드는 int로 선언하는 일이 생긴다. 그런 컬럼에 NULL이 저장된 행을 조회하면 어떻게 될까.

    @Entity
public class Player {
    @Id
    private Long id;
    private int score;       // 기본형
    protected Player() {}
}
// 컬럼을 null 허용으로 바꾸고, score가 NULL인 행을 SQL로 직접 넣은 뒤 조회
em.find(Player.class, 1L);
    Hibernate: select p1_0.id,p1_0.score from Player p1_0 where p1_0.id=?
org.hibernate.PropertyAccessException: Null value was assigned to a property [class example.Player.score] of primitive type: 'example.Player.score' (setter)

    ResultSet에서 읽은 NULL을 int 필드에 넣을 방법이 없으므로 Hibernate가 예외를 던진다. 그 행 하나 때문에 조회 전체가 실패한다. 반대 방향의 함정도 있다. 0이 정상 값일 수 있는 필드(점수, 수량)를 int로 두면 "값이 없음"과 "0"을 구분할 수 없다. 컬럼이 null을 허용한다면 엔티티도 래퍼형으로, 컬럼이 NOT NULL이면 기본형이나 nullable = false를 단 래퍼형으로 맞추는 것이 원칙이다.

    ORDINAL이 기본값이라는 함정

    @Enumerated의 기본값은 EnumType.ORDINAL이다. 애너테이션을 생략해도 마찬가지다. ORDINAL은 열거 상수의 선언 순서 번호, 즉 Enum.ordinal()의 값을 저장한다. 예약 상태를 enum ReservationStatus { REQUESTED, CONFIRMED, CANCELED }로 선언했다면 저장되는 값은 0, 1, 2다. 운영 중에 "대기" 상태가 필요해져서 REQUESTED 다음에 WAITING을 끼워 넣었다고 하자.

    STRING을 고르면 MySQL에서는 한 가지를 더 알아야 한다. Hibernate 6.6의 MySQLDialect는 위 DDL처럼 STRING 열거형을 MySQL의 네이티브 enum 타입으로 만들었고, @Column(length = 20)은 반영되지 않았다. 이 경우 허용되는 값의 목록이 컬럼 정의에 들어가므로, 자바에 상수를 추가하면 데이터베이스에도 ALTER TABLE로 목록을 고쳐야 한다. 고치지 않은 채 새 상수를 저장하면, 엄격 SQL 모드(MySQL 8.0의 기본 sql_mode에 들어 있는 STRICT_TRANS_TABLES)에서는 데이터베이스가 목록에 없는 값이라며 거부한다. varchar 컬럼을 원한다면 Hibernate 전용 애너테이션 @JdbcTypeCode(SqlTypes.VARCHAR)를 함께 붙인다. 같은 필드에 이것을 추가하자 DDL이 status varchar(20) not null로 바뀌었다. 저장 값을 상수 이름이 아닌 별도 코드("R", "C" 등)로 두고 싶다면 JPA 표준의 AttributeConverter와 @Convert로 변환 규칙을 직접 정의할 수도 있다.

    날짜와 시간

    java.time의 LocalDate, LocalDateTime 같은 타입은 추가 애너테이션 없이 매핑된다. JPA 2.2부터 표준이 이 타입들을 지원한다. 위 실험에서 LocalDate는 date, LocalDateTime은 datetime(6)이 되었다. 괄호 안의 6은 소수점 아래 초 자릿수로, 마이크로초까지 저장한다는 뜻이다. LocalDateTime은 시간대 정보가 없는 "벽시계 시각"이라는 점을 기억하자. 서버마다 시간대 설정이 다르면 같은 순간이 다른 값으로 저장된다.

    java.util.Date와 java.util.Calendar를 쓰던 시절에는 @Temporal(TemporalType.DATE)처럼 날짜만인지, 시각만인지, 둘 다인지를 지정해야 했다. java.util.Date 하나로는 그 구분이 타입에 드러나지 않았기 때문이다. java.time은 타입 자체가 그 구분을 담고 있으므로 @Temporal이 필요 없다. Jakarta Persistence 3.2 API에서는 @Temporal과 TemporalType에 @Deprecated가 붙어 있다(3.2.0 jar를 리플렉션으로 확인). 새 코드에서는 java.time 타입을 쓰면 된다.

    @Lob과 @Transient

    @Lob은 큰 데이터를 담는 컬럼에 매핑한다. 필드가 문자 계열(String, char[])이면 CLOB 계열, 그 밖(byte[] 등)이면 BLOB 계열이다. MySQLDialect에서는 각각 longtext, longblob이 되었다. 별도 속성이 없으므로 어떤 계열인지는 필드 타입이 정한다. 긴 본문을 String으로 두고 @Lob을 빠뜨리면 varchar(255)가 만들어져, 길이 초과 오류를 운영에서 처음 만나게 된다.

    @Transient는 그 필드를 매핑에서 뺀다. 테이블에 컬럼이 생기지 않고, 저장하지도 조회하지도 않는다. 계산 결과를 잠시 들고 있거나 화면용 값을 붙여 두는 필드에 쓴다. 자바 언어의 transient 수식어가 붙은 필드도 JPA에서는 영속 대상이 아니다. 다만 그 수식어는 자바 직렬화에서도 필드를 제외하므로, 직렬화와 영속성의 의도가 다르다면 애너테이션 쪽을 쓰는 것이 의도를 분명히 한다.

    기본 키 매핑: 무엇을 키로 삼는가

    기본 키(primary key)는 null이 아니어야 하고, 유일해야 하며, 변하지 않아야 한다. 앞의 두 조건은 데이터베이스가 강제하지만, 세 번째 조건은 아무도 강제하지 않는다. 그런데 JPA에는 세 번째 조건이 특히 중요하다. 영속성 컨텍스트는 엔티티를 "엔티티 타입 + 식별자 값"을 키로 1차 캐시에 보관하고, 다른 엔티티는 외래 키로 이 값을 참조한다. 식별자가 바뀌면 캐시의 키도, 다른 테이블의 외래 키도 함께 바뀌어야 한다.

    기본 키 후보는 두 종류다. 자연 키(natural key)는 업무에 원래 있는 값이다. 사번, 이메일, 회의실 코드 같은 것이다. 대리 키(surrogate key)는 업무와 무관하게 행을 구분하려고 만든 값이다. 자동 증가 번호나 시퀀스 값이 그렇다. 자연 키는 처음에는 영원히 변하지 않을 것처럼 보이지만, 업무 규칙은 바뀐다. 이메일은 사용자가 바꾸고, 사번 체계는 조직 개편으로 바뀌며, 회의실 코드는 층 배치가 바뀌면 다시 매겨진다. 법이나 정책 때문에 그 값을 아예 저장할 수 없게 되기도 한다. 그 값을 기본 키로 썼다면 그것을 참조하는 모든 테이블의 외래 키를 함께 고쳐야 한다. 그래서 일반적인 선택은 Long 타입의 대리 키를 기본 키로 두고, 자연 키에는 유니크 제약을 거는 것이다. 위 회의실 엔티티가 그렇게 되어 있다. 정수형 중에 Long을 고르는 것은 범위 때문이다. int의 최댓값은 2,147,483,647인데, 로그나 이력처럼 빠르게 쌓이는 테이블은 이 범위를 넘을 수 있고, 기본 키 타입을 나중에 바꾸는 일은 그것을 참조하는 모든 외래 키를 함께 바꾸는 일이다.

    MySQL InnoDB에서 기본 키는 저장 순서다

    기본 키 선택은 저장 엔진 수준에서도 의미가 있다. MySQL 8.0 문서에 따르면 InnoDB 테이블에는 행 데이터를 저장하는 클러스터드 인덱스(clustered index)가 있고, 기본 키를 정의하면 그것이 클러스터드 인덱스가 된다. 즉 행은 기본 키 순서로 정렬된 B+Tree의 리프 페이지에 저장된다. 또 보조 인덱스의 각 레코드에는 그 행의 기본 키 컬럼이 들어 있어서, 문서는 기본 키가 길면 보조 인덱스가 더 많은 공간을 쓰므로 짧은 기본 키가 유리하다고 적는다. 8바이트 bigint 기본 키는 모든 보조 인덱스 레코드에 8바이트씩을 더하고, 16바이트 UUID 기본 키는 16바이트씩을 더한다.

    삽입 순서도 중요하다. 같은 문서의 인덱스 물리 구조 절은 InnoDB가 클러스터드 인덱스에 새 레코드를 넣을 때 페이지의 1/16을 비워 두려 하며, 레코드가 순차적으로 삽입되면 인덱스 페이지가 약 15/16만큼 차고, 무작위 순서로 삽입되면 1/2에서 15/16 사이로 찬다고 설명한다. 단조 증가하는 Long 키는 항상 B+Tree의 오른쪽 끝에 붙으므로 페이지가 꽉 찬 상태로 쌓인다. 무작위 값인 UUID 버전 4 키는 트리의 아무 위치에나 끼어들어, 이미 찬 페이지를 나누게 만들고 페이지의 평균 사용률을 떨어뜨린다. 같은 데이터가 더 많은 페이지를 차지하면 버퍼 풀에 올려야 할 페이지도 많아진다. 기본 키 생성 전략을 고르는 일은 결국 이 B+Tree에 어떤 순서로 값을 넣을지를 고르는 일이기도 하다.

    단조 증가 키는 B+Tree 오른쪽 끝 리프에만 붙고, 무작위 키는 여러 리프에 흩어져 들어가며 페이지 분할을 일으킨다는 차이를 보여 준다. 화면을 좌우 두 칸으로 나눈다. 두 칸 모두 위에 루트 노드 하나, 아래에 리프 페이지 사각형 다섯 개가 가로로 늘어선 B+Tree를 그린다. 왼쪽 칸 제목은 "순차 키 (1, 2, 3 ...)"이다. 새 레코드를 뜻하는 초록색 작은 사각형 세 개가 모두 맨 오른쪽 리프로 들어가는 화살표를 그리고, 나머지 리프는 거의 꽉 찬 진한 색으로 칠한다. 리프 아래 라벨은 "페이지 약 15/16 채움". 오른쪽 칸 제목은 "무작위 키 (UUID v4)"이다. 초록색 새 레코드 세 개가 서로 다른 리프 세 곳으로 흩어져 들어가고, 그중 한 리프가 두 개로 갈라지는 모습과 라벨 "페이지 분할"을 붙인다. 리프들은 절반쯤만 채워진 색으로 칠하고 아래 라벨은 "1/2 ~ 15/16 채움". 평면 기술 다이어그램, 흰 배경. InnoDB는 행을 기본 키 순서의 B+Tree에 저장한다. 키를 만드는 방식이 곧 삽입 위치를 정한다.

    기본 키 값을 정하는 방법은 두 가지다. 애플리케이션이 직접 넣는 직접 할당은 @Id만 붙이고 persist() 전에 값을 채운다. 앞의 Coupon 예제가 그랬다. 자동 생성은 @GeneratedValue를 함께 붙이고 strategy로 방법을 고른다. 선택지는 IDENTITY, SEQUENCE, TABLE, AUTO, 그리고 Jakarta Persistence 3.1에서 추가된 UUID다. 기본값은 AUTO다. 차례로 보자.

    IDENTITY: 키를 받으려면 INSERT가 먼저다

    IDENTITY는 기본 키 생성을 데이터베이스에 맡긴다. MySQL의 AUTO_INCREMENT가 대표적이고, 위 DDL에서 id bigint not null auto_increment가 그 결과다. 이 전략의 특징은 값이 정해지는 시점이다. 데이터베이스는 행이 INSERT될 때 값을 만든다. 즉 INSERT를 실행하기 전에는 아무도 그 값을 모른다. 이 사실이 JPA의 동작을 어떻게 바꾸는지 실행으로 확인해 보자.

    EntityManager em = emf.createEntityManager();
EntityTransaction tx = em.getTransaction();
tx.begin();

MeetingRoom room = new MeetingRoom("A-301", "301호 회의실", 8);
System.out.println("persist 전 id = " + room.getId());
em.persist(room);
System.out.println("persist 후 id = " + room.getId());

System.out.println("커밋 직전");
tx.commit();
em.close();
    persist 전 id = null
Hibernate: insert into meeting_room (capacity,code,created_at,floor,guide,name,status,id) values (?,?,?,?,?,?,?,default)
persist 후 id = 1
커밋 직전

    INSERT가 커밋 시점이 아니라 persist() 안에서 실행되었다. 앞 회차에서 본 쓰기 지연과 다르다. 이유는 영속성 컨텍스트의 구조에 있다. persist()가 끝나면 엔티티는 영속 상태가 되어 1차 캐시에 들어가야 하고, 1차 캐시의 키는 식별자다. 그런데 IDENTITY 전략에서는 식별자를 알려면 INSERT를 실행해야 한다. 그래서 Hibernate는 영속 상태로 만들기 위해 INSERT를 앞당겨 실행하고, 데이터베이스가 만든 키를 받아 엔티티의 id 필드에 채운다. 위 출력에서 persist 후 id = 1이 바로 그 값이다.

    JDBC 수준에서는 무슨 일이 일어날까. H2의 JDBC 호출 추적을 켜고 같은 일을 하면, Hibernate가 conn0.prepareStatement("insert into IdentityItem (name,id) values (?,default)", 1)을 호출한 뒤 executeUpdate()를 부르는 것이 보인다. 두 번째 인자 1은 java.sql.Statement.RETURN_GENERATED_KEYS 상수의 값이다(javap로 확인). 드라이버에게 "이 문장을 실행한 뒤 데이터베이스가 만든 키를 돌려 달라"고 요청하는 것이고, Hibernate는 실행 뒤 getGeneratedKeys()로 그 값을 읽는다. 이 호출이 엔티티 매니저가 이미 쓰고 있던 커넥션(conn0)에서, 자동 커밋이 꺼진 상태로 일어났다는 점도 기억해 두자.

    이 동작에서 두 가지 결과가 나온다. 첫째, 이 엔티티에 대해서는 쓰기 지연의 이점이 사라진다. 저장할 때마다 데이터베이스 왕복이 한 번씩 생긴다. 둘째, JDBC 배치(batch)를 쓸 수 없다. JDBC 배치는 같은 모양의 문장을 여러 개 모아 addBatch()로 쌓았다가 executeBatch()로 한 번에 보내는 기능인데, IDENTITY는 문장 하나를 실행할 때마다 키를 돌려받아야 하므로 모을 수가 없다. Hibernate 6.6 사용자 가이드도 IDENTITY 생성을 쓰는 엔티티는 INSERT 문을 배치로 묶을 수 없다고 명시한다. hibernate.jdbc.batch_size=10을 켜고 IDENTITY 엔티티와 SEQUENCE 엔티티를 세 개씩 저장한 JDBC 추적은 그 차이를 그대로 보여 준다.

    #### identity x3
PreparedStatement prep0 = conn0.prepareStatement("insert into IdentityItem (name,id) values (?,default)", 1);
prep0.executeUpdate();
PreparedStatement prep1 = conn0.prepareStatement("insert into IdentityItem (name,id) values (?,default)", 1);
prep1.executeUpdate();
PreparedStatement prep2 = conn0.prepareStatement("insert into IdentityItem (name,id) values (?,default)", 1);
prep2.executeUpdate();
#### seq x3

PreparedStatement prep4 = conn0.prepareStatement("select next value for seq_item_seq");

prep5.addBatch();
prep5.addBatch();
prep5.executeBatch();
    흔한 오해 하나를 바로잡자. IDENTITY에서 persist 시점에 INSERT가 "실행"되는 것이지 "커밋"되는 것은 아니다. INSERT는 같은 트랜잭션 안에서 실행되므로, 이후 롤백하면 그 행도 사라진다. 다만 MySQL에서 그때 받은 AUTO_INCREMENT 값은 되돌아가지 않는다.

    그 마지막 문장은 MySQL 8.0 문서가 명시하는 동작이다. 문서는 모든 잠금 모드에서 자동 증가 값을 생성한 트랜잭션이 롤백되면 그 값은 "잃어버린" 값이 되고 재사용되지 않으므로, AUTO_INCREMENT 컬럼의 값에 빈틈이 생길 수 있다고 적는다. 같은 문서에 따르면 MySQL 8.0의 기본 innodb_autoinc_lock_mode는 2(interleaved)이고, 8.0 이전의 기본값은 1(consecutive)이었다. 모드 2에서는 여러 INSERT 문이 동시에 값을 받아 갈 수 있어서, 한 문장이 여러 행을 넣을 때 그 행들이 받은 값이 연속이 아닐 수 있다. 또 MySQL 8.0부터는 현재 최댓값이 바뀔 때마다 리두 로그에 기록되고 체크포인트마다 데이터 딕셔너리에 저장되어, 서버를 재시작해도 자동 증가 카운터가 유지된다. 결론은 같다. 자동 증가 값은 유일성은 보장하지만 연속성은 보장하지 않는다. 기본 키 값으로 "몇 번째 주문인지"를 세려고 하면 안 된다.

    SEQUENCE와 allocationSize: 번호를 묶음으로 가져온다

    시퀀스(sequence)는 유일한 번호를 차례로 만들어 주는 데이터베이스 객체다. 테이블과 독립되어 있어서, INSERT 없이도 "다음 번호"를 받을 수 있다. 이것이 IDENTITY와의 결정적 차이다. 식별자를 INSERT 전에 알 수 있으므로 persist()는 번호만 받아 엔티티를 영속 상태로 만들고, INSERT는 쓰기 지연 저장소에 넣어 두었다가 플러시 때 보낼 수 있다. 오라클, PostgreSQL, H2 등이 시퀀스를 지원하고, MySQL에는 시퀀스 객체가 없다(MySQL에서 Hibernate가 어떻게 하는지는 다음 절에서 본다).

    @Entity
@SequenceGenerator(name = "access_log_seq_gen", sequenceName = "access_log_seq", allocationSize = 50)
public class AccessLog {
    @Id
    @GeneratedValue(strategy = GenerationType.SEQUENCE, generator = "access_log_seq_gen")
    private Long id;
    private String path;

    protected AccessLog() {}
    public AccessLog(String path) { this.path = path; }
    public Long getId() { return id; }
}

    @SequenceGenerator는 생성기에 이름(name)을 붙이고, 어떤 데이터베이스 시퀀스를 쓸지(sequenceName)와 시작 값(initialValue), 한 번에 확보할 개수(allocationSize)를 정한다. Jakarta Persistence API의 기본값은 initialValue = 1, allocationSize = 50이다. @GeneratedValue의 generator가 이 이름을 가리킨다. Hibernate가 만든 DDL은 create sequence access_log_seq start with 1 increment by 50이었다. 시퀀스의 증가 폭이 1이 아니라 50이라는 점에 주목하자. 이제 한 트랜잭션에서 53개를 저장해 보자.

    tx.begin();
for (int i = 1; i <= 53; i++) {
    AccessLog log = new AccessLog("/rooms/" + i);
    em.persist(log);
    if (i <= 3 || i >= 50) System.out.println(i + "번째 persist → id = " + log.getId());
}
System.out.println("커밋 직전");
tx.commit();

... (같은 INSERT가 커밋 시점에 모두 53번)

    53개를 저장하는 동안 시퀀스는 세 번만 호출되었고, INSERT는 모두 커밋 시점으로 미뤄졌다. 실행 뒤 H2의 information_schema.sequences에서 이 시퀀스가 다음에 돌려줄 값을 조회하면 151이었다. 세 번의 호출이 각각 1, 51, 101을 돌려주었다는 뜻이다. Hibernate 6.6.53이 이 값들을 어떻게 썼는지 정리하면 다음과 같다.

    데이터베이스 시퀀스 (increment by 50)          Hibernate 생성기(메모리)
---------------------------------------      -------------------------------------
1번째 호출 → 1   (다음 값 51)                   1을 그대로 사용 (시작 값과 같으므로)
2번째 호출 → 51  (다음 값 101)                  상한 51 확보 → 2, 3, ..., 51 을 차례로 배분
3번째 호출 → 101 (다음 값 151)                  상한 101 확보 → 52, 53, ..., 101 을 배분
4번째 호출 → 151                               상한 151 확보 → 102 ~ 151 ...

시퀀스 호출 1번 = 번호 50개 확보 (첫 호출만 예외)
배분 중에는 데이터베이스와 통신하지 않는다 (메모리에서 1씩 증가)

    핵심은 시퀀스가 돌려준 값을 "이번 묶음의 상한"으로 해석한다는 것이다. 시퀀스가 51을 돌려주었다면 데이터베이스의 증가 폭이 50이므로 다음 호출자는 101을 받게 되고, 그 사이의 번호는 이 생성기만 쓸 수 있다. 그래서 묶음 하나를 다 쓸 때까지는 메모리에서 번호를 하나씩 올리기만 하면 된다. 이 계산은 데이터베이스 시퀀스의 증가 폭과 allocationSize가 같다는 전제 위에서만 성립한다. 시퀀스를 손으로 만들면서 증가 폭을 1로 두고 매핑에는 기본값 50을 남겨 두는 실수를 하지 않도록, 두 값을 반드시 맞춰야 한다.

    persist가 여러 번 호출되는 동안 데이터베이스 시퀀스 호출은 묶음마다 한 번뿐이고, 나머지 번호는 메모리에서 배분된다는 것을 보여 준다. 세로 생명선 세 개를 가로로 배치한 시퀀스 다이어그램. 왼쪽 생명선 "애플리케이션", 가운데 "Hibernate 생성기", 오른쪽 "DB 시퀀스". 애플리케이션에서 생성기로 "persist" 화살표가 위에서 아래로 여러 번 반복된다. 첫 번째와 두 번째 persist 때만 생성기에서 DB 시퀀스로 "next value" 화살표가 가고, 각각 "1", "51"이라는 반환 화살표가 돌아온다. 두 번째 반환 옆에 괄호 "2 ~ 51 확보"를 단다. 그 아래로 persist 화살표가 여러 개 이어지지만 DB 쪽 화살표는 없고, 생성기 생명선 옆에 "메모리에서 1씩 증가"라는 메모를 붙인다. 아래쪽에 다시 "next value" 화살표와 반환 "101", 메모 "52 ~ 101 확보". 맨 아래 애플리케이션에서 DB 쪽으로 굵은 화살표 "커밋 시 INSERT 일괄 전송". 평면 기술 다이어그램, 흰 배경. 시퀀스는 묶음마다 한 번만 호출되고, INSERT는 커밋 시점까지 미뤄진다.

    묶음 할당이 만드는 번호의 모양

    메모리에 확보한 번호는 애플리케이션이 종료되면 사라진다. AccessLog를 세 개 저장하고 EntityManagerFactory를 닫은 뒤, 같은 데이터베이스로 다시 띄워 세 개를 더 저장하면 번호는 1 2 3 다음에 52 53 54가 되었다. 첫 실행이 확보한 2~51 중 4~51을 쓰지 못한 채 끝났고, 재시작한 생성기는 시퀀스에서 101을 받아 52~101 묶음을 쓰기 시작했기 때문이다. 배포할 때마다 이런 빈틈이 생긴다.

    서버가 여러 대일 때도 같은 원리가 적용된다. 각 서버의 생성기는 시퀀스에서 서로 다른 묶음을 받으므로 번호가 겹치지는 않는다. 데이터베이스가 시퀀스 호출을 원자적으로 처리하기 때문이다. 대신 번호의 크기 순서와 저장 시각의 순서가 어긋난다. 서버 A가 1~51 묶음을, 서버 B가 52~101 묶음을 쓰는 중이라면, B가 먼저 저장한 52번 행보다 A가 나중에 저장한 3번 행이 더 작은 번호를 갖는다. 기본 키 값의 크기로 시간 순서를 판단하는 코드는 이 환경에서 틀린 답을 낸다. 시간 순서가 필요하면 시각 컬럼을 따로 두어야 한다.

    allocationSize를 1로 두면 이런 빈틈과 순서 어긋남이 줄어들지만, 엔티티 하나를 저장할 때마다 시퀀스를 한 번씩 호출하게 된다. 반대로 너무 크게 잡으면 재시작 때마다 버려지는 번호가 늘어난다. 기본값 50은 이 두 비용 사이의 무난한 지점이고, 번호의 빈틈이 업무적으로 문제가 되는 경우는 드물다. 문제가 된다면 그것은 기본 키에 업무 의미를 실은 설계를 다시 보라는 신호다.

    TABLE, AUTO, UUID

    TABLE: 시퀀스를 흉내 내는 테이블

    TABLE 전략은 키 생성 전용 테이블을 만들어 시퀀스처럼 쓴다. 모든 데이터베이스에서 동작한다는 것이 장점이다. Hibernate 6.6은 기본으로 hibernate_sequences 테이블(sequence_name, next_val 컬럼)을 만들고 ('default', 0) 행을 넣었다. 번호를 받을 때의 SQL과 커넥션 사용은 JDBC 추적으로 보면 다음과 같다.

    Connection conn1 = DriverManager.getConnection("jdbc:h2:mem:t;...", "", "");
conn1.setAutoCommit(false);
PreparedStatement prep0 = conn1.prepareStatement("select tbl.next_val from hibernate_sequences tbl where tbl.sequence_name=? for update");
ResultSet rs5 = prep0.executeQuery();
PreparedStatement prep1 = conn1.prepareStatement("update hibernate_sequences set next_val=?  where next_val=? and sequence_name=?");
prep1.executeUpdate();
conn1.commit();
#### commit
PreparedStatement prep2 = conn0.prepareStatement("insert into TableItem (name,id) values (?,?)");

    Hibernate는 엔티티 매니저가 쓰던 커넥션(conn0)이 아니라 커넥션을 하나 더 얻어(conn1) 그 안에서 키 행을 select ... for update로 잠그고, 값을 올리고, 바로 커밋했다. 업무 트랜잭션이 길어져도 키 행의 잠금이 그동안 유지되지 않게 하려는 구조다. 그래도 비용은 남는다. 번호를 받을 때마다 행 잠금을 거는 갱신이 일어나고, 모든 서버가 같은 행을 두고 경쟁하며, 그 순간에는 커넥션을 두 개 쓴다. 시퀀스나 IDENTITY를 쓸 수 있는 데이터베이스라면 굳이 고를 이유가 적다. @TableGenerator의 allocationSize 기본값도 50이어서, 묶음 할당으로 잠금 횟수를 줄인다.

    AUTO: 방언이 고른다, 그런데 생각과 다를 수 있다

    @GeneratedValue만 쓰고 전략을 생략하면 AUTO다. 명세는 AUTO일 때 구현체가 적절한 전략을 고르게 한다. Hibernate 6.6 사용자 가이드에 따르면 식별자가 UUID 타입이면 UUID 생성기를, 숫자 타입이면 SequenceStyleGenerator를 쓰는데, 이 생성기는 데이터베이스가 시퀀스를 지원하면 시퀀스를 쓰고 그렇지 않으면 테이블로 대신한다. 시퀀스 이름은 엔티티가 매핑된 테이블 이름에 _SEQ를 붙인 것이다. H2에서 AutoItem 엔티티를 띄우자 create sequence AutoItem_SEQ start with 1 increment by 50이 만들어졌다.

    MySQL에서는 어떨까. AUTO가 AUTO_INCREMENT를 쓸 것이라고 기대하기 쉽지만, Hibernate 6.6의 MySQLDialect가 만든 DDL은 달랐다.

    create table AutoItem (
    id bigint not null,
    name varchar(255),
    primary key (id)
) engine=InnoDB;

create table AutoItem_SEQ (
    next_val bigint
) engine=InnoDB;

    id에 auto_increment가 없고, 대신 시퀀스를 흉내 내는 AutoItem_SEQ 테이블이 생겼다. 번호를 받을 때마다 이 테이블의 행을 잠그고 갱신한다. 사실상 앞의 TABLE 전략과 같은 비용이다. MySQL에서 AUTO_INCREMENT를 원한다면 GenerationType.IDENTITY를 명시해야 한다.

    이 기본 동작은 Hibernate 6.0에서 바뀌었다. Hibernate 6.0 마이그레이션 가이드는 6.0부터 하나의 hibernate_sequence 대신 엔티티 계층마다 시퀀스를 만들고, 그 이름은 <엔티티 이름>_seq 형태이며, 이런 암묵적 시퀀스도 @SequenceGenerator의 기본값을 따라 할당 크기가 50이라고 설명한다. 예전 방식이 필요하면 hibernate.id.db_structure_naming_strategy를 legacy나 single로 설정한다. 실제로 legacy로 바꾸자 H2에서 create sequence hibernate_sequence start with 1 increment by 1이 만들어졌다. Hibernate 5 시절에 만든 스키마를 6으로 올리면서 AUTO를 그대로 두면, 존재하지 않는 시퀀스를 찾다가 실패할 수 있는 이유다. AUTO는 "알아서"라는 이름과 달리 방언과 Hibernate 버전에 따라 결과가 달라지므로, 전략은 명시하는 편이 낫다.

    UUID

    Jakarta Persistence 3.1은 GenerationType.UUID를 추가했다. 식별자 필드를 java.util.UUID로 선언하고 이 전략을 쓰면 구현체가 UUID를 만든다. Hibernate 6.6.53에서 생성된 값의 version()은 4, 즉 무작위 기반 UUID였다. 애플리케이션 메모리에서 바로 만들어지므로 데이터베이스 왕복이 없고, 실험에서도 INSERT는 커밋 시점에 나갔다. MySQLDialect에서는 binary(16) 컬럼이 되었다. 장점은 데이터베이스 없이도 전역적으로 유일한 값을 만들 수 있다는 것이고, 단점은 앞에서 본 것처럼 16바이트로 길고 무작위 위치에 삽입된다는 것이다.

    지금까지 본 매핑 규칙을 작은 요구사항에 적용해 보자. 사내 회의실 예약 시스템이다.

    • 사원은 사번으로 구분하며 사번은 중복될 수 없다. 이름은 반드시 있어야 하고 이메일은 없을 수도 있다.
    • 회의실은 "A-301" 같은 코드로 구분하며 코드는 중복될 수 없다. 이름, 수용 인원, 층, 운영 상태(운영 중, 폐쇄), 이용 안내문을 가진다.
    • 사원은 회의실을 시작 시각과 종료 시각을 정해 예약한다. 예약에는 목적을 적을 수 있고, 상태는 요청됨, 확정됨, 취소됨 중 하나다.
    • "특정 회의실의 특정 시간대 예약"을 자주 조회한다.

    요구사항의 명사에서 엔티티 후보를 고르면 사원(Employee), 회의실(MeetingRoom), 예약(Reservation) 세 개다. 운영 상태와 예약 상태는 정해진 값 중 하나이므로 열거형으로 두고, 앞의 이유로 STRING으로 저장한다. 사번과 회의실 코드는 업무에서 쓰는 자연 키이지만 바뀔 수 있으므로 기본 키로 삼지 않고, Long 대리 키를 두고 유니크 제약을 건다. 데이터베이스는 MySQL이라고 가정하고 IDENTITY 전략을 쓴다. 마지막 요구사항은 회의실과 시작 시각을 묶은 인덱스로 받친다. 회의실은 앞 절의 MeetingRoom을 그대로 쓰고, 나머지 두 엔티티는 다음과 같다.

    @Entity
@Table(uniqueConstraints = @UniqueConstraint(name = "uk_employee_no", columnNames = "employee_no"))
public class Employee {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "employee_no", nullable = false, length = 20)
    private String employeeNo;

    @Column(nullable = false, length = 30)
    private String name;

    @Column(length = 100)
    private String email;

    protected Employee() {}
    public Employee(String employeeNo, String name) {
        this.employeeNo = employeeNo;
        this.name = name;
    }
    public Long getId() { return id; }
}

@Entity
@Table(indexes = @Index(name = "idx_reservation_room_start", columnList = "room_id, start_at"))
public class Reservation {
    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "room_id", nullable = false)
    private Long roomId;          // 회의실의 id 값

    @Column(name = "employee_id", nullable = false)
    private Long employeeId;      // 사원의 id 값

    @Column(nullable = false)
    private LocalDateTime startAt;

    @Column(nullable = false)
    private LocalDateTime endAt;

    @Column(length = 200)
    private String purpose;

    @Enumerated(EnumType.STRING)
    @Column(nullable = false, length = 20)
    private ReservationStatus status;   // REQUESTED, CONFIRMED, CANCELED

    protected Reservation() {}
    public Reservation(Long roomId, Long employeeId, LocalDateTime startAt,
                       LocalDateTime endAt, String purpose) {
        this.roomId = roomId;
        this.employeeId = employeeId;
        this.startAt = startAt;
        this.endAt = endAt;
        this.purpose = purpose;
        this.status = ReservationStatus.REQUESTED;
    }

    public Long getRoomId() { return roomId; }
}

    요구사항이 하나씩 스키마로 옮겨졌다. 사번과 회의실 코드에는 이름 붙은 유니크 제약이, 자주 쓰는 조회 조건에는 복합 인덱스가 생겼다. 상태 열거형은 STRING이어서 상수 순서를 바꿔도 안전하다(다만 MySQL enum 타입이 되었으므로 상수를 추가할 때는 ALTER TABLE이 필요하다는 점을 기억하자). 운영에 쓰려면 이 DDL을 출발점으로 마이그레이션 스크립트를 만들고, 애플리케이션은 validate나 none으로 띄우면 된다.

    그런데 이 설계에는 눈에 띄는 어색함이 있다. Reservation은 회의실과 사원을 객체가 아니라 Long roomId, Long employeeId라는 숫자로 들고 있다. 테이블의 외래 키 컬럼을 그대로 필드로 옮긴 것이다. 예약한 회의실의 이름을 알고 싶으면 이렇게 써야 한다.

    Reservation reservation = em.find(Reservation.class, reservationId);
MeetingRoom room = em.find(MeetingRoom.class, reservation.getRoomId());   // 식별자로 한 번 더 찾는다
// reservation.getRoom().getName() 처럼 객체 그래프를 따라갈 수 없다

    객체 지향에서는 참조를 따라가면 연관된 객체에 닿아야 하는데, 이 모델에서는 식별자를 들고 다시 찾아야 한다. 생성된 DDL에도 외래 키 제약이 없다. room_id에 존재하지 않는 회의실 번호가 들어가도 데이터베이스는 막지 않는다. 이것이 1회에서 본 패러다임 불일치의 한 모습이다. 테이블은 외래 키로 연결을 표현하고, 객체는 참조로 연결을 표현한다. 지금의 매핑은 테이블 쪽 방식을 객체에 그대로 가져온 것이다. 필드를 MeetingRoom room으로 바꾸고 그것을 room_id 외래 키에 매핑하는 방법이 04회 연관관계 매핑 기초의 주제다.

    이 지식이 다시 쓰이는 곳

    이 회차의 내용은 뒤에서 여러 번 다시 나온다. 07회의 프록시는 엔티티의 하위 클래스이므로, 이 회차에서 본 "final 금지"와 "protected 이상의 기본 생성자"가 그 전제 조건이다. 04회와 05회에서 연관관계를 매핑하면 @Column 대신 @JoinColumn이 외래 키 컬럼 이름을 정하고, 같은 컬럼을 두 필드가 매핑할 때 insertable·updatable이 다시 등장한다. 06회의 상속 매핑 전략은 엔티티 하나가 테이블 여러 개에 걸치거나 테이블 하나에 여러 엔티티가 들어가는 경우로, 이 회차의 "엔티티 하나 = 테이블 하나"를 확장한다. 08회의 임베디드 타입은 필드 여러 개를 값 객체 하나로 묶어 같은 테이블의 컬럼에 매핑한다.

    기본 키 생성 전략은 성능 문제로 다시 돌아온다. 대량 저장 작업에서 JDBC 배치를 켰는데도 INSERT가 한 건씩 나간다면, 가장 먼저 확인할 것이 IDENTITY 전략이다. 스프링 데이터 JPA나 대량 처리 도구를 쓸 때도 아래에서 일어나는 일은 이 회차에서 본 persist()와 시퀀스 호출, 쓰기 지연과 같다. 또 이 회차에서 InnoDB의 클러스터드 인덱스와 페이지 사용률을 본 것처럼, 매핑의 선택은 결국 데이터베이스 엔진의 자료 구조에 어떤 모양으로 데이터가 쌓이는지를 정한다. 애너테이션 한 줄을 고를 때 그 아래 B+Tree와 JDBC 호출까지 떠올릴 수 있으면 이 회차의 목표는 이룬 것이다.

    이 장의 핵심

    매핑 애너테이션은 부트 시점에 한 번 해석되어 메타모델이 되고, DDL과 모든 SQL이 거기에서 나온다. 엔티티의 조건(기본 생성자, final 금지)은 Hibernate가 빈 객체를 만들어 값을 채우고 하위 클래스로 프록시를 만드는 방식에서 나온다. DDL용 속성 대부분은 실행 시점에 검사되지 않으며 최종 방어선은 데이터베이스 제약이다. 열거형은 STRING으로 저장한다. 기본 키는 바뀌지 않는 Long 대리 키가 기본이고, IDENTITY는 식별자를 얻으려고 persist 시점에 INSERT를 실행하므로 쓰기 지연과 JDBC 배치를 잃으며, SEQUENCE는 allocationSize만큼 번호를 묶어 받아 왕복을 줄이는 대신 번호에 빈틈과 순서 어긋남을 남긴다.
    매핑 메타데이터와 메타모델
    @Entity, @Column 같은 애너테이션은 EntityManagerFactory를 만들 때 한 번 해석되어 메타모델이 된다. DDL, INSERT·SELECT 문, 1차 캐시의 키 구성이 모두 이 메타모델을 참조한다.
    엔티티 클래스의 조건
    public 또는 protected 기본 생성자, 최상위 클래스, final이 아닌 클래스·메서드·영속 필드. 조회 결과로 빈 객체를 만들어 값을 채우는 방식과 하위 클래스 프록시 때문이다.
    이름 전략
    암묵적 전략이 논리 이름을 정하고 물리 전략이 실제 이름으로 바꾼다. 스프링 부트는 CamelCaseToUnderscoresNamingStrategy를 기본 설정해 createdAt을 created_at으로 만들며, 명시한 이름에도 적용된다.
    스키마 자동 생성
    hibernate.hbm2ddl.auto(부트에서는 spring.jpa.hibernate.ddl-auto)로 제어한다. update는 사라진 필드의 컬럼을 지우지 않는다. 운영에서는 none 또는 validate와 마이그레이션 도구를 쓴다.
    DDL 속성과 런타임 검사
    length, unique, 인덱스는 DDL에만 쓰인다. nullable=false는 hibernate.check_nullability가 켜져 있으면 Hibernate가 SQL 전에 검사한다. 최종 방어선은 데이터베이스 제약이다.
    @Enumerated
    기본값 ORDINAL은 선언 순서 번호를 저장하므로 상수 순서가 바뀌면 기존 데이터의 의미가 조용히 바뀐다. STRING을 쓴다. Hibernate 6.6 MySQLDialect는 STRING을 MySQL enum 타입으로 만든다.
    IDENTITY
    데이터베이스가 INSERT 때 키를 만든다. 식별자 없이는 영속 상태로 만들 수 없으므로 persist 시점에 INSERT를 실행하고 RETURN_GENERATED_KEYS로 키를 받는다. JDBC 배치를 쓸 수 없다.
    SEQUENCE와 allocationSize
    시퀀스 호출 한 번으로 allocationSize(기본 50)개 번호를 확보해 메모리에서 배분한다. DB 시퀀스의 증가 폭과 같아야 하며, 재시작과 다중 서버 환경에서 번호의 빈틈과 순서 어긋남이 생긴다.
    AUTO
    Hibernate 6은 숫자 식별자에 엔티티별 _SEQ 시퀀스(증가 폭 50)를 쓰고, 시퀀스가 없는 MySQL에서는 테이블로 대신한다. AUTO_INCREMENT를 원하면 IDENTITY를 명시한다.

    운영 장애로 가장 자주 이어지는 매핑 실수는 스키마 자동 생성과 열거형이다. 부트의 ddl-auto 기본값이 내장 데이터베이스일 때만 create-drop이라는 사실을 모르면, 로컬에서 잘 되던 애플리케이션이 운영 MySQL에서 테이블 없이 뜨거나, 반대로 누군가 운영 설정에 update를 넣어 둔 채 배포되는 일이 생긴다. 판단 기준은 단순하다. 스키마는 사람이 검토한 마이그레이션 스크립트로만 바꾸고, 애플리케이션은 validate로 띄워 매핑과 스키마가 어긋나면 기동 단계에서 실패하게 만든다. 이때 validate가 모든 불일치를 잡아 주지는 않는다. Hibernate 6.6 실험에서 varchar(255) 컬럼에 @Column(length = 30, unique = true)를 단 엔티티도 validate를 그대로 통과했다. 그러므로 엔티티의 제약 선언과 마이그레이션 스크립트를 함께 리뷰하는 습관이 필요하다.

    기본 키 전략은 데이터베이스와 쓰기 패턴에 따라 판단이 달라진다. MySQL에서 화면 단위로 몇 건씩 저장하는 일반적인 서비스라면 IDENTITY가 단순하고 충분하다. persist 시점 INSERT는 건당 왕복 한 번이고, 어차피 커밋 전에 나갈 문장이다. 그러나 배치 작업으로 수십만 건을 저장해야 한다면 IDENTITY는 JDBC 배치를 막는 병목이 된다. 그때는 시퀀스를 지원하는 데이터베이스라면 SEQUENCE로, MySQL이라면 JPA를 우회해 JDBC 배치 INSERT를 직접 쓰는 방법 등을 검토한다. 반대로 MySQL에서 AUTO를 그대로 두면 그 엔티티를 저장하는 모든 서버가 키 테이블의 한 행을 잠그며 경쟁하게 되므로(묶음 할당으로 빈도는 줄어도 구조는 같다), 어떤 경우든 전략은 명시한다.

    UUID 기본 키는 여러 시스템이 데이터베이스 없이 식별자를 만들어야 할 때 매력적이지만, InnoDB에서는 클러스터드 인덱스의 무작위 삽입과 긴 키 길이라는 비용을 낸다. 외부에 노출할 식별자가 추측 불가능해야 한다는 요구가 이유라면, 내부 기본 키는 Long으로 두고 UUID는 유니크 제약을 건 별도 컬럼으로 두는 절충도 가능하다. 어떤 선택이든 "이 값이 B+Tree의 어디에 들어가는가"와 "이 값을 얻으려고 언제 데이터베이스에 다녀오는가"라는 두 질문으로 따져 보면 판단이 흔들리지 않는다.
  • 예약 상태를 enum ReservationStatus { REQUESTED, CONFIRMED, CANCELED }로 선언하고 @Enumerated를 생략한 채 운영해 왔다. 새 요구사항으로 REQUESTED와 CONFIRMED 사이에 WAITING을 추가하고 배포했다. 배포 전에 저장된 예약 1,000건 중 확정 600건, 취소 300건, 요청 100건이 있었다면, 배포 후 애플리케이션이 읽는 상태별 건수는 어떻게 되는가? 이 문제를 데이터 변경 없이 막으려면 처음에 무엇을 했어야 하는가?
  • H2(시퀀스 지원)에 처음 만든 데이터베이스에서, allocationSize = 50인 SEQUENCE 전략 엔티티를 쓰는 서버 A가 먼저 떠서 엔티티 2개를 저장한다. 그다음 서버 B가 떠서 2개를 저장하고, 이어서 서버 A가 1개를 더 저장한다. Hibernate 6.6 기준으로 각 엔티티가 받는 식별자를 저장 순서대로 적고, 시퀀스는 모두 몇 번 호출되는지 답하라.
  • 회의실 엔티티의 code에 @Column(nullable = false, length = 10)을 주고, 19자짜리 코드를 가진 회의실을 저장한다. 식별자 전략이 IDENTITY일 때와 SEQUENCE일 때, 예외는 각각 persist()와 commit() 중 어디에서 발생하는가? 이유를 설명하라.
  • 레거시 테이블의 score 컬럼은 NULL을 허용하고 실제로 NULL인 행이 있다. 엔티티는 private int score;로 선언했다. 저장, 조회 중 어느 시점에 어떤 문제가 생기는지 설명하고 엔티티를 어떻게 고쳐야 하는지 답하라.
  • 운영 데이터베이스에 ddl-auto=update가 켜진 채로, 엔티티에서 int price 필드를 지우고 Integer stock 필드를 추가해 배포했다. 배포 직후 Hibernate가 실행하는 DDL과, 그 뒤 첫 INSERT에서 일어나는 일을 예측하라.

    1. ORDINAL은 선언 순서 번호를 저장하므로 데이터베이스에는 요청 0이 100건, 확정 1이 600건, 취소 2가 300건 있다. WAITING이 끼어든 뒤에는 0=REQUESTED, 1=WAITING, 2=CONFIRMED, 3=CANCELED이므로 애플리케이션은 요청 100건, 대기 600건, 확정 300건, 취소 0건으로 읽는다. 취소된 예약이 확정으로 보이는 것이 가장 위험하다. 예외가 나지 않으므로 발견이 늦다. 처음부터 @Enumerated(EnumType.STRING)으로 상수 이름을 저장했다면 상수 추가나 순서 변경은 기존 데이터의 의미를 바꾸지 않는다. 이미 ORDINAL로 운영 중이라면 새 상수는 반드시 맨 뒤에 추가해야 하고, 장기적으로는 데이터를 이름으로 옮기는 마이그레이션을 계획한다.

    2. 서버 A의 첫 저장에서 시퀀스가 1을 돌려주고(1번째 호출), 이것이 시작 값이므로 식별자 1을 쓴다. A의 두 번째 저장에서 51을 받아(2번째 호출) 2~51을 확보하고 2를 쓴다. 서버 B는 첫 저장에서 101을 받는다(3번째 호출). 시작 값이 아니므로 101을 상한으로 보고 52~101을 확보해 52를 쓰고, 두 번째 저장에서 53을 쓴다. A의 세 번째 저장은 확보해 둔 묶음에서 3을 쓴다. 따라서 저장 순서대로 1, 2, 52, 53, 3이고 시퀀스 호출은 3번이다. 번호는 겹치지 않지만, 마지막에 저장된 행이 가장 작은 번호(3)를 받았으므로 식별자 크기로 시간 순서를 판단하면 틀린다. 이 계산은 본문의 재시작 실험(1 2 3 다음에 52 53 54)과 같은 원리다.

    3. 길이 제한은 Hibernate가 실행 시점에 검사하지 않고 데이터베이스가 INSERT를 거부할 때 드러난다. 따라서 예외는 INSERT가 실행되는 시점에 난다. IDENTITY는 식별자를 얻기 위해 persist() 안에서 INSERT를 실행하므로 persist()에서 예외가 난다. 본문 실험에서도 persist 다음 줄의 출력이 찍히지 않았다. SEQUENCE는 persist()에서 시퀀스 값만 받고 INSERT를 쓰기 지연 저장소에 넣어 두므로, 플러시가 일어나는 commit()에서 예외가 난다. 같은 잘못된 데이터라도 전략에 따라 예외 위치가 달라지므로, 예외 처리 코드를 persist 호출에만 걸어 두면 SEQUENCE에서는 잡지 못한다.

    4. 저장은 문제가 없다. int 필드는 항상 값(기본 0)이 있으므로 INSERT에 0이 들어간다. 이것도 "값 없음"을 0으로 바꿔 저장한다는 점에서 데이터가 왜곡될 수 있다. 조회에서는 NULL인 행을 읽는 순간 Hibernate가 NULL을 기본형 필드에 넣을 수 없어 PropertyAccessException(Null value was assigned to a property ... of primitive type)을 던지고 조회 전체가 실패한다. 컬럼이 NULL을 허용하므로 필드를 Integer score로 바꾸는 것이 맞다.

    5. update는 매핑에 있는데 데이터베이스에 없는 것을 추가하므로 alter table ... add column stock integer를 실행한다. 매핑에서 사라진 price 컬럼은 지우지 않는다. 원래 int price는 기본형이어서 price integer not null로 만들어져 있었다. 새 엔티티는 price를 모르므로 INSERT 문에 넣지 않고, 데이터베이스는 NOT NULL 컬럼에 값이 없다며 거부한다. 본문 실험처럼 그 테이블의 모든 INSERT가 ConstraintViolationException으로 실패한다. 마이그레이션 스크립트로 price 컬럼을 삭제하거나 기본값을 주는 변경을 함께 배포했어야 한다.

     IDENTITY 전략을 쓰는 엔티티에 persist()를 호출하면 커밋 전인데도 INSERT가 실행된다. 가장 근본적인 이유는? IDENTITY 전략은 자동 커밋 모드에서만 동작하기 때문이다 영속 상태가 되려면 1차 캐시의 키인 식별자가 필요한데, 그 값은 데이터베이스가 INSERT를 실행할 때 만들어지기 때문이다 Hibernate가 IDENTITY 엔티티에 대해서는 쓰기 지연 저장소를 만들지 않도록 명세가 정하기 때문이다 JDBC 배치가 꺼져 있으면 모든 INSERT는 persist 시점에 실행되기 때문이다 영속성 컨텍스트는 엔티티를 식별자로 관리하므로 persist가 끝나면 식별자가 있어야 한다. IDENTITY는 INSERT를 해야 키가 생기므로 Hibernate가 INSERT를 앞당긴다. 실험에서 INSERT는 자동 커밋이 꺼진 같은 커넥션에서 실행되었고 커밋은 따로 일어났으므로 자동 커밋 보기는 틀리다. 명세가 쓰기 지연 저장소를 두고 그렇게 정한 것도 아니며, SEQUENCE 엔티티는 배치를 끈 상태에서도 커밋 시점에 INSERT가 나갔으므로 배치 보기도 틀리다. 처음 만든 데이터베이스에서 allocationSize=50인 SEQUENCE 엔티티를 한 트랜잭션에서 3개 저장했다(Hibernate 6.6.53). 데이터베이스 시퀀스는 몇 번 호출되는가? 0번. 첫 번호는 initialValue로 메모리에서 정한다 1번. 한 번 호출로 50개를 확보한다 2번. 첫 호출은 시작 값 1을 돌려주어 그 번호만 쓰고, 두 번째 호출의 51을 상한으로 2~51을 확보한다 3번. 엔티티마다 한 번씩 호출한다 본문 실험에서 1번째 persist 전과 2번째 persist 전에 각각 select next value가 실행되었고, 3번째는 메모리에서 배분되었다. 실행 후 시퀀스의 다음 값이 이 패턴과 일치했다. 엔티티마다 호출하는 것은 allocationSize=1일 때의 모습이다. Bean Validation이 없는 클래스패스에서 Hibernate 6.6으로 다음 매핑을 쓴다. @Column(nullable = false, length = 10) private String code; 옳은 설명은? 두 속성 모두 DDL 생성에만 쓰이므로, 자동 생성을 끄면 아무 효과가 없다 두 속성 모두 Hibernate가 SQL을 보내기 전에 검사한다 length는 Hibernate가 검사하고, nullable은 데이터베이스만 검사한다 nullable=false는 hibernate.check_nullability가 켜져 있으면 SQL 전에 Hibernate가 검사하지만, length는 검사하지 않아 데이터베이스가 거부할 때 드러난다 실험에서 name이 null인 경우 SQL 없이 PropertyValueException이 났고, 19자 코드는 INSERT가 데이터베이스까지 간 뒤 DataException이 났다. check_nullability는 Bean Validation이 있으면 기본적으로 꺼지므로 환경에 따라 달라진다. "DDL에만 쓰인다"는 보기는 nullable의 실행 시점 검사를 놓쳤고, 나머지 두 보기는 length를 Hibernate가 검사한다고 잘못 설명한다. 스프링 부트 3.x 애플리케이션이 MySQL에 연결되고, Flyway·Liquibase는 쓰지 않으며, spring.jpa.hibernate.ddl-auto를 설정하지 않았다. 기동 시 Hibernate의 스키마 도구는 무엇을 하는가? 아무것도 하지 않는다(none) 테이블을 지우고 다시 만든 뒤 종료 시 지운다(create-drop) 부족한 컬럼만 추가한다(update) 매핑과 스키마를 비교만 한다(validate) 부트는 JDBC URL과 커넥션 타입으로 hsqldb, h2, derby 같은 내장 데이터베이스인지 판단하고, 내장 데이터베이스이면서 스키마 관리 도구가 없을 때만 create-drop을 기본값으로 쓴다. 그 밖의 모든 경우의 기본값은 none이다. 그래서 H2에서 MySQL로 바꾸면 테이블이 자동으로 생기지 않는다. JPA 명세가 엔티티 클래스를 final로 선언하지 못하게 하는 이유와 가장 직접 관련된 것은? final 클래스는 리플렉션으로 필드에 값을 쓸 수 없기 때문이다 final 클래스는 기본 생성자를 가질 수 없기 때문이다 지연 로딩 프록시가 엔티티의 하위 클래스로 만들어지는데, final 클래스는 하위 클래스를 가질 수 없기 때문이다 final 클래스의 인스턴스는 1차 캐시에 보관할 수 없기 때문이다 프록시는 실행 중에 생성되는 엔티티의 하위 클래스로, 메서드를 오버라이드해 처음 호출될 때 초기화한다. JLS상 final 클래스는 하위 클래스를 가질 수 없고 final 메서드는 오버라이드할 수 없다. Hibernate 사용자 가이드도 final 클래스는 저장은 되지만 지연 로딩 프록시를 쓸 수 없다고 설명한다. 나머지 보기는 사실이 아니다.
    매핑 메타데이터(mapping metadata)
    객체와 테이블의 대응을 기술한 정보. JPA에서는 주로 애너테이션으로 표현하며, 구현체가 부트 시점에 읽어 메타모델을 만든다.
    방언(Dialect)
    Hibernate가 데이터베이스마다 다른 SQL 문법과 타입을 처리하려고 쓰는 부품. 같은 매핑이라도 방언에 따라 생성되는 DDL과 SQL이 다르다.
    물리 이름 전략(physical naming strategy)
    논리 이름을 실제 데이터베이스 식별자로 바꾸는 마지막 단계. 스프링 부트는 CamelCaseToUnderscoresNamingStrategy를 기본으로 쓴다.
    스키마 생성(schema generation)
    매핑 정보로 DDL을 만들어 실행하는 기능. Hibernate에서는 hibernate.hbm2ddl.auto, JPA 표준에서는 jakarta.persistence.schema-generation.database.action으로 제어한다.
    자연 키(natural key)
    사번, 이메일처럼 업무에 원래 존재하는 값으로 만든 키. 업무 규칙이 바뀌면 값이 바뀔 수 있다.
    대리 키(surrogate key)
    업무와 무관하게 행을 구분하려고 만든 키. 자동 증가 값이나 시퀀스 값이 대표적이다.
    클러스터드 인덱스(clustered index)
    InnoDB에서 행 데이터 자체를 기본 키 순서로 저장하는 B+Tree 인덱스. 보조 인덱스 레코드는 기본 키 값을 함께 담는다.
    시퀀스(sequence)
    테이블과 독립적으로 유일한 번호를 차례로 만드는 데이터베이스 객체. INSERT 없이 다음 값을 받을 수 있다. MySQL에는 없다.
    allocationSize
    @SequenceGenerator·@TableGenerator에서 한 번의 호출로 확보할 번호 개수. 기본값 50이며 데이터베이스 시퀀스의 증가 폭과 같아야 한다.
    RETURN_GENERATED_KEYS
    JDBC Statement의 상수(값 1). 문장을 실행할 때 데이터베이스가 생성한 키를 getGeneratedKeys()로 돌려 달라고 요청한다.
