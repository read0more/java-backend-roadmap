    이 회차의 질문: 주소 세 칸과 Address 하나는 무엇이 다른가

    회원 엔티티를 처음 만들면 필드가 테이블 컬럼을 그대로 따라가기 쉽다. 이름, 도시, 도로명, 우편번호, 근무 시작일, 근무 종료일이 한 클래스에 나란히 놓인다. 테이블 입장에서는 아무 문제가 없다. 이 값들은 모두 회원 한 명에 딸린 속성이고, 관계형 테이블에서 한 행의 속성은 그 행의 컬럼으로 두는 것이 자연스럽다. 문제는 객체 쪽에서 생긴다.

    @Entity
public class Member {
    @Id @GeneratedValue
    private Long id;
    private String name;

    // 근무 기간
    private LocalDate startDate;
    private LocalDate endDate;

    // 집 주소
    private String city;
    private String street;
    private String zipcode;
    // ...
}

    이 클래스를 읽는 사람은 city, street, zipcode가 한 묶음이라는 사실을 이름과 주석으로 추측해야 한다. "오늘이 근무 기간 안인가"를 판단하는 코드는 startDate와 endDate를 꺼내 비교하는 형태로 서비스 곳곳에 흩어진다. 배송지나 도서관 지점처럼 주소가 필요한 다른 엔티티가 생기면 필드 세 개와 검증 규칙을 또 복사해야 한다. 회사 주소를 하나 더 두려면 workCity, workStreet, workZipcode가 추가되고, 엔티티는 점점 의미 없는 필드의 나열이 된다.

    객체 지향 언어에서 이 문제의 답은 익숙하다. 함께 다니는 값을 클래스 하나로 묶고, 그 값에 대한 규칙을 그 클래스의 메서드로 옮긴다. Address와 Period를 만들고 회원은 그 둘을 필드로 갖는다. 그런데 JPA에서는 이것이 간단하지 않다. Address를 엔티티로 만들면 테이블이 하나 더 생기고, 식별자와 외래 키와 조인이 따라온다. 주소는 회원 행에 그대로 두고 싶은데 객체만 잘게 나누고 싶다. 이 요구에 대한 JPA의 답이 값 타입(value type)이다.

    이 회차는 값 타입을 다섯 갈래로 정리한다. 먼저 엔티티와 값을 가르는 기준을 세우고, 가장 단순한 기본값 타입이 왜 안전한지 JVM 수준에서 확인한다. 다음으로 임베디드 타입을 만들고, 그것이 자바의 참조 타입이라서 생기는 공유 문제와 그 해결책인 불변 객체를 본다. 이어서 값을 비교하는 방법과 하이버네이트가 값을 비교하는 방법을 나눠 보고, 마지막으로 값을 여러 개 담는 값 타입 컬렉션이 테이블에서 어떻게 다뤄지는지 SQL로 추적한다.

    이 회차의 실험은 앞 회차들과 같은 환경에서 했다. 스프링 부트 없이 하이버네이트 6.6.53.Final과 H2 2.3.232 메모리 데이터베이스를 JDK 21에서 직접 실행했고, hibernate.hbm2ddl.auto=create로 테이블을 만들게 한 뒤 hibernate.show_sql=true로 SQL을 출력했다. 스프링 부트의 물리 이름 전략을 쓰지 않았으므로 컬럼 이름은 필드 이름을 그대로 따른다(startDate). 스프링 부트 3.x 기본 설정이라면 03회에서 본 대로 start_date처럼 바뀐다. 실험 코드를 짧게 하려고 엔티티 필드를 같은 패키지에서 직접 읽고 쓴 곳이 있다.

    엔티티 타입과 값 타입: 식별자와 생명주기

    JPA가 다루는 데이터 타입은 크게 엔티티 타입(entity type)과 값 타입으로 나뉜다. 둘을 가르는 기준은 두 가지다. 첫째는 식별자다. 엔티티는 @Id로 지정한 식별자를 가지고, 영속성 컨텍스트는 그 식별자로 엔티티를 추적한다. 회원의 이름과 나이와 주소가 모두 바뀌어도 식별자가 같으면 같은 회원이다. 값 타입에는 식별자가 없다. 나이 20은 그냥 20이고, 나이가 21이 되었다는 것은 "20이라는 값이 21로 바뀌었다"가 아니라 회원이 가진 값이 다른 값으로 교체되었다는 뜻이다.

    둘째는 생명주기다. 엔티티는 스스로의 생명주기를 가진다. persist()로 영속 상태가 되고 remove()로 삭제되며, 다른 엔티티가 그것을 참조하든 말든 독립적으로 존재한다. 값 타입은 자기 생명주기가 없다. 회원 엔티티를 삭제하면 그 회원의 이름, 나이, 주소도 함께 사라진다. 하이버네이트 사용자 가이드도 값 타입을 "자기 생명주기를 정의하지 않고, 생명주기를 정하는 엔티티에 소유된다"는 취지로 설명한다(Hibernate ORM 6.6 User Guide §3.1.1).

    분류예식별자저장 위치생명주기
    엔티티 타입Member, Team있다(@Id)자기 테이블의 행독립적
    기본값 타입int, Integer, String, LocalDate없다소유 엔티티 테이블의 컬럼 하나소유 엔티티에 의존
    임베디드 타입Address, Period없다소유 엔티티 테이블의 컬럼 여러 개소유 엔티티에 의존
    값 타입 컬렉션Set, List
    		없다별도의 컬렉션 테이블소유 엔티티에 의존

    여기서 하나를 분명히 해 두자. JPA가 말하는 값 타입은 자바 언어의 기본형(primitive type)과 다른 개념이다. 자바에서 int는 기본형이고 Integer, String, Address는 모두 참조형(reference type)이다. JPA의 분류는 메모리 표현이 아니라 영속성의 의미를 기준으로 한다. Address는 자바에서는 힙에 있는 객체이고 변수에는 그 참조가 담기지만, JPA에서는 식별자 없이 회원에 딸린 값이다. 이 회차에서 다룰 함정은 대부분 이 어긋남에서 나온다. 의미는 값인데 구현은 참조라서, 값처럼 다루지 않으면 참조의 성질이 그대로 드러난다.

    그래서 값 타입에는 두 가지 요구가 따른다. 하나는 공유되지 않아야 한다는 것이다. 회원 A의 주소를 바꿨는데 회원 B의 주소가 따라 바뀌면 안 된다. 다른 하나는 값으로 비교되어야 한다는 것이다. 같은 도시, 같은 도로명, 같은 우편번호를 가진 주소 두 개는 서로 다른 객체여도 같은 주소로 취급되어야 한다. 이 회차의 나머지는 이 두 요구를 자바와 JPA가 각각 어떻게 만족시키는지, 또는 만족시키지 못하는지에 대한 이야기다.

    엔티티는 자기 테이블과 식별자를 갖고, 기본값·임베디드 값은 엔티티 행의 컬럼으로, 값 타입 컬렉션은 별도 테이블로 저장된다는 대응 관계를 한눈에 보여 준다. 왼쪽에 자바 객체 영역, 오른쪽에 데이터베이스 테이블 영역을 둔 2단 구성. 왼쪽 위에 "Member 엔티티" 상자가 있고 그 안에 "id", "name", "homeAddress", "favoriteFoods" 네 칸이 세로로 있다. "homeAddress" 칸에서 작은 상자 "Address (city, street, zipcode)"로 화살표가 나가고, "favoriteFoods" 칸에서 작은 상자 "Set: 치킨, 피자"로 화살표가 나간다. 오른쪽에는 넓은 표 "Member 테이블"이 있고 컬럼 머리글은 "id", "name", "city", "street", "zipcode"다. "name" 칸에서 "name" 컬럼으로, "Address" 상자에서 "city", "street", "zipcode" 세 컬럼으로 점선 화살표가 이어진다. 그 아래에 작은 표 "favorite_food 테이블"(컬럼 "member_id", "food_name")이 있고 "Set" 상자에서 이 표로 점선 화살표가 간다. "favorite_food 테이블"의 "member_id"에서 "Member 테이블"의 "id"로 실선 화살표에 "외래 키" 라벨. 왼쪽 위 "Member 엔티티" 상자 옆에 작은 열쇠 아이콘과 "식별자 있음", Address 상자 옆에 "식별자 없음" 라벨. 엔티티만 식별자를 갖는다. 기본값과 임베디드 값은 엔티티 행의 컬럼이 되고, 값 타입 컬렉션은 엔티티 식별자를 외래 키로 갖는 별도 테이블이 된다.

    기본값 타입: 복사되거나, 공유되어도 바뀌지 않거나

    기본값 타입은 자바 기본형(int, double, boolean 등), 그 래퍼 클래스(Integer, Long 등), String, 그리고 LocalDate 같은 날짜 타입처럼 컬럼 하나에 매핑되는 값이다. 엔티티의 필드 대부분이 여기에 속한다. 회원의 name은 member 테이블의 name 컬럼 하나가 되고, 회원 행이 삭제되면 함께 사라진다. 별도의 SQL도, 별도의 식별자도 없다.

    기본값 타입은 앞에서 말한 "공유되지 않아야 한다"는 요구를 저절로 만족한다. 그 이유가 기본형과 래퍼 클래스에서 서로 다르다는 점이 흥미롭다. 작은 프로그램으로 확인해 보자.

    public class ValueDemo {
    public static void main(String[] args) {
        int a = 10;
        int b = a;
        a = 20;
        System.out.println("a=" + a + ", b=" + b);

        Integer x = 10;
        Integer y = x;
        System.out.println("x == y : " + (x == y));
        x = 20;
        System.out.println("x=" + x + ", y=" + y);
    }
}
    a=20, b=10
x == y : true
x=20, y=10

    결과만 보면 둘 다 "b와 y는 바뀌지 않았다"로 똑같다. 그런데 javap -c로 바이트코드를 열어 보면 일어난 일이 다르다. 아래는 JDK 21의 javac가 만든 main의 앞부분이다.

    기본형 쪽에서 b = a는 iload_1과 istore_2다. 지역 변수 배열의 1번 칸에 있던 32비트 정수를 피연산자 스택에 올렸다가 2번 칸에 내려놓는다. 값 자체가 복사되므로 이후 1번 칸에 20을 써도 2번 칸은 영향을 받지 않는다. JVM 명세가 지역 변수(JVMS §2.6.1)를 프레임마다 따로 두고 int 값을 칸 하나에 직접 담도록 정해 두었기 때문에, 기본형은 애초에 공유될 방법이 없다.

    래퍼 쪽은 다르다. Integer x = 10은 오토박싱이라 컴파일러가 Integer.valueOf(10) 호출을 넣었고, 그 결과인 참조를 3번 칸에 저장했다. y = x는 aload_3과 astore 4로, 참조를 복사한다. 이제 두 변수는 힙에 있는 같은 Integer 객체를 가리킨다. if_acmpne가 두 참조를 비교한 결과가 x == y : true다. 공유가 실제로 일어난 것이다. 그런데도 y가 안전한 이유는 그다음 줄에 있다. x = 20은 기존 객체의 내용을 20으로 고치는 것이 아니라 Integer.valueOf(20)이 돌려준 다른 참조를 3번 칸에 새로 쓰는 일이다. 10을 담은 객체는 그대로이고 y는 여전히 그것을 가리킨다.

    Integer 객체의 내용을 바꾸는 방법이 아예 없다는 점이 핵심이다. JDK 소스에서 Integer가 값을 담는 필드는 private final int value이고, 이 필드를 바꾸는 공개 메서드는 없다. String도 같다. String의 Javadoc은 "문자열은 상수이며 만들어진 뒤에는 값을 바꿀 수 없다"고 밝힌다. 이렇게 상태를 바꿀 수 없는 객체를 불변 객체(immutable object)라 한다. 래퍼와 문자열은 공유되지만, 공유된 쪽에서 아무도 내용을 바꿀 수 없으니 공유가 문제가 되지 않는다. 정리하면 기본형은 복사라서 안전하고, 래퍼와 String은 불변이라서 안전하다. 뒤에서 임베디드 타입을 안전하게 만드는 방법도 이 두 번째 길을 따른다.

    일상에서 가져온 비유복사한 메모와 코팅한 게시물

    기본형은 메모를 복사해 나눠 주는 것과 같다. 내가 내 복사본에 낙서해도 상대의 복사본은 그대로다. 불변 객체는 게시판에 붙인 코팅된 게시물과 같다. 여러 사람이 같은 게시물을 보지만 아무도 그 위에 쓸 수 없으니, 내용을 바꾸고 싶으면 새 게시물을 만들어 내 자리에 붙여야 한다. 비유가 깨지는 지점도 있다. 코팅은 물리적으로 벗겨낼 수 있지만, 자바의 final 필드와 세터 없는 설계는 리플렉션 같은 특수한 수단을 쓰지 않는 한 일반 코드로는 우회할 수 없다.

    임베디드 타입: 테이블은 그대로, 객체만 잘게 나눈다

    임베디드 타입(embedded type)은 개발자가 직접 정의하는 값 타입이다. 여러 기본값을 묶어 의미 있는 이름을 붙인 클래스이고, Jakarta Persistence 명세는 이것을 임베더블 클래스(embeddable class)라고 부른다. 명세는 임베더블 클래스의 인스턴스가 엔티티와 달리 자기 고유의 영속 식별자를 갖지 않으며, 소유 엔티티의 일부로만 존재한다고 정의한다(Jakarta Persistence 3.1 §2.6). 회원의 주소와 근무 기간을 임베디드 타입으로 바꿔 보자.

    @Embeddable
public class Address {
    private String city;
    private String street;
    private String zipcode;

    protected Address() {}                 // JPA가 쓰는 기본 생성자

    public Address(String city, String street, String zipcode) {
        this.city = city;
        this.street = street;
        this.zipcode = zipcode;
    }

    public String getCity() { return city; }
    public String getStreet() { return street; }
    public String getZipcode() { return zipcode; }

    public Address withCity(String newCity) {
        return new Address(newCity, street, zipcode);
    }

    @Override
    public boolean equals(Object o) {
        if (this == o) return true;
        if (!(o instanceof Address that)) return false;
        return Objects.equals(city, that.city)
            && Objects.equals(street, that.street)
            && Objects.equals(zipcode, that.zipcode);
    }

    @Override
    public int hashCode() {
        return Objects.hash(city, street, zipcode);
    }

    @Override
    public String toString() { return city + " " + street + " (" + zipcode + ")"; }
}

@Embeddable
public class Period {
    private LocalDate startDate;
    private LocalDate endDate;

    protected Period() {}

    public Period(LocalDate startDate, LocalDate endDate) {
        this.startDate = startDate;
        this.endDate = endDate;
    }

    public boolean contains(LocalDate day) {
        return !day.isBefore(startDate) && !day.isAfter(endDate);
    }
}

@Entity
public class Member {
    @Id @GeneratedValue
    Long id;

    String name;

    @Embedded
    Period workPeriod;

    @Embedded
    Address homeAddress;
    // ...
}

    @Embeddable은 값 타입을 정의하는 클래스에, @Embedded는 그것을 사용하는 필드에 붙인다. Address의 withCity, equals, hashCode는 뒤의 절에서 쓰려고 미리 넣었다. 지금은 매핑만 보자. 이 엔티티로 하이버네이트가 만든 테이블은 다음과 같다(뒤에서 쓸 회사 주소 컬럼과 컬렉션 테이블은 빼고 보였다).

    city varchar(255), name varchar(255), street varchar(255),
    zipcode varchar(255), ..., primary key (id))

    테이블은 처음의 평평한 엔티티와 똑같다. Address 테이블도, address_id 외래 키도 없다. 임베디드 타입의 필드가 소유 엔티티의 테이블에 컬럼으로 펼쳐져 들어갔을 뿐이다. 컬럼 순서는 필드 선언 순서와 다르게 나왔지만 이 회차의 관심사는 아니다. 저장과 조회 SQL도 확인해 보자.

    무엇이 좋아졌는가

    첫째, 응집도가 올라갔다. "근무 기간 안인가"라는 규칙이 Period.contains() 한 곳에 있다. 서비스 코드는 member.getWorkPeriod().contains(today)라고 쓰면 되고, 날짜 비교의 경계 조건(시작일과 종료일을 포함하는가)을 매번 다시 생각할 필요가 없다. 둘째, 재사용이 가능하다. 배송 엔티티든 도서관 지점 엔티티든 주소가 필요한 곳은 Address 필드 하나를 두면 된다. Jakarta Persistence 3.2의 @Embeddable Javadoc 표현대로, 하나의 임베더블 타입은 여러 엔티티의 여러 필드 타입으로 쓰일 수 있다. 셋째, 엔티티가 읽기 쉬워진다. 회원은 이제 이름, 근무 기간, 집 주소를 가진 객체로 읽힌다. 이 모든 이점을 얻는 동안 테이블은 하나도 바뀌지 않았다. 객체 모델이 테이블보다 잘게 나뉘는 것, 이것이 임베디드 타입이 패러다임 불일치를 다루는 방식이다.

    임베디드 타입이 지켜야 할 조건

    명세는 임베더블 클래스가 엔티티 클래스의 요구 조건을 따르되 @Entity가 아니라는 점만 다르다고 정한다(Jakarta Persistence 3.1 §2.6). 그래서 인자 없는 생성자가 있어야 하고(공개 또는 protected), 클래스가 final이면 안 된다. 실제로 하이버네이트가 이 생성자를 어떻게 쓰는지 확인하려고 두 생성자에 출력문을 넣어 실험해 보니, 조회할 때 출력된 것은 인자 없는 생성자뿐이었다. 하이버네이트 6.6은 일반 클래스 임베더블을 인자 없는 생성자로 만든 뒤 필드에 값을 채운다. 이 사실은 뒤에서 다시 중요해진다. 인자 있는 생성자에 넣은 검증 로직은 데이터베이스에서 읽은 값에는 실행되지 않는다는 뜻이기 때문이다.

    @Embeddable이 붙은 클래스라면 필드의 @Embedded는 생략해도 된다. 명세의 기본 매핑 규칙은 필드 타입이 @Embeddable이 붙은 클래스이면 @Embedded를 붙인 것과 똑같이 매핑한다고 정한다(Jakarta Persistence 3.1 §2.9). 실험에서도 @Embedded를 뺀 필드가 city, street, zipcode 컬럼으로 똑같이 매핑되었다. 그래도 두 곳에 모두 붙여 두면 엔티티만 읽는 사람도 이 필드가 컬럼 여러 개로 펼쳐진다는 것을 바로 알 수 있다.

    임베디드 타입은 다른 임베디드 타입을 품을 수 있고, 엔티티에 대한 연관관계도 가질 수 있다. 예컨대 Address 안에 @Embedded Zipcode를 두거나, 주소가 지역 엔티티를 @ManyToOne으로 참조하게 만들 수 있다(명세 §2.6). 이때도 테이블은 소유 엔티티 하나이고, 연관관계는 그 테이블의 외래 키 컬럼이 된다. 다만 임베디드 타입을 식별자(@EmbeddedId)나 맵의 키로 쓸 때는 엔티티 연관관계를 넣을 수 없고, 값 타입 컬렉션의 원소로 쓰이는 임베디드 타입은 그 안에 또 다른 값 타입 컬렉션을 가질 수 없다(명세 §2.6, §2.7).

    임베디드 값이 null이면

    임베디드 필드가 null이면 매핑된 컬럼이 모두 null로 저장된다. 반대 방향이 함정이다. 실험에서 회원 하나는 homeAddress를 null로, 다른 하나는 모든 필드가 null인 new Address(null, null, null)로 저장한 뒤 새 영속성 컨텍스트에서 읽었다.

    n1.home=null
n2.home=null

    둘 다 null로 돌아왔다. 데이터베이스에는 두 행 모두 city, street, zipcode가 null로 들어 있고, 그 상태에서 "주소 객체가 없었다"와 "모든 칸이 빈 주소 객체가 있었다"를 구분할 정보가 없다. 하이버네이트는 컬럼이 모두 null이면 임베디드 값을 null로 복원한다. 저장할 때 빈 Address를 넣은 코드가 다시 읽은 뒤 member.getHomeAddress().getCity()를 호출하면 NullPointerException이 난다. "빈 주소"라는 상태가 도메인에서 의미가 있다면 그것을 컬럼 하나로 따로 표현하거나, 임베디드 필드가 null일 수 있다는 전제로 코드를 써야 한다.

    같은 임베디드 타입을 두 번 쓰면: @AttributeOverride

    회원에게 집 주소와 회사 주소를 모두 두고 싶다. Address 필드를 하나 더 추가하면 될 것 같지만, 그대로 두면 하이버네이트는 부트스트랩 단계에서 실패한다.

    @Entity
public class Bad {
    @Id @GeneratedValue Long id;
    @Embedded Address homeAddress;
    @Embedded Address workAddress;
}

    두 필드가 모두 Address의 기본 컬럼 이름인 city, street, zipcode를 쓰려 하니 한 테이블에 같은 이름의 컬럼이 두 번 매핑된다. 오류 메시지가 제안하는 insertable=false, updatable=false는 한 컬럼을 두 필드가 일부러 공유할 때 쓰는 방법이라 지금 상황과 맞지 않다. 여기서 원하는 것은 컬럼을 따로 두는 것이고, 그 도구가 @AttributeOverride다.

    @Embedded
@AttributeOverrides({
    @AttributeOverride(name = "city",    column = @Column(name = "work_city")),
    @AttributeOverride(name = "street",  column = @Column(name = "work_street")),
    @AttributeOverride(name = "zipcode", column = @Column(name = "work_zipcode"))
})
Address workAddress;
    create table Member (endDate date, startDate date, id bigint not null,
    city varchar(255), name varchar(255), street varchar(255),
    work_city varchar(255), work_street varchar(255), work_zipcode varchar(255),
    zipcode varchar(255), primary key (id))

    name 속성에는 임베디드 클래스 안의 필드 이름을, column에는 이 엔티티에서 쓸 컬럼 정의를 준다. 자바 8부터 애너테이션 반복이 가능하므로 @AttributeOverrides 없이 @AttributeOverride를 여러 번 붙여도 된다. 하이버네이트 사용자 가이드도 같은 임베더블을 한 엔티티에서 여러 번 쓸 때 명세가 컬럼 이름을 명시하도록 요구한다고 적고 있다(§3.3.2).

    하이버네이트에는 이 반복을 줄이는 고유 기능도 있다. 암묵적 이름 전략을 hibernate.implicit_naming_strategy=component-path로 바꾸면 컬럼 이름을 필드 경로 전체로 만든다. 같은 Bad 엔티티를 이 설정으로 돌려 보니 homeAddress_city, workAddress_city처럼 충돌 없는 이름이 생겼다. 다만 사용자 가이드는 이것이 하이버네이트 전용이며 이식성을 위해서는 @AttributeOverride로 명시하는 편을 권한다(§3.3.10). 또 이 설정은 엔티티 전체의 이름 규칙을 바꾸므로, 이미 운영 중인 스키마에 적용할 때는 다른 컬럼 이름까지 바뀌지 않는지 확인해야 한다.

    공유 참조의 부작용: 한 번 바꿨는데 UPDATE가 두 번 나간다

    이제 이 회차의 핵심 함정으로 가자. 기본값 타입이 안전했던 이유는 복사되거나 불변이기 때문이었다. 임베디드 타입은 개발자가 만든 클래스이고, 세터를 넣으면 가변 객체가 된다. 그리고 자바에서 객체를 대입하면 값이 아니라 참조가 복사된다. 앞의 Integer y = x에서 본 aload와 astore가 Address에도 똑같이 일어난다. 세터가 있는 Address로 실험해 보자.

    @Embeddable

    private String city;
    private String street;
    protected Address() {}
    public Address(String city, String street) { this.city = city; this.street = street; }
    public String getCity() { return city; }
    public void setCity(String city) { this.city = city; }
}

    두 회원의 homeAddress는 힙에 있는 Address 객체 하나를 가리킨다. kim.homeAddress.setCity("부산")은 그 객체 하나를 고쳤고, lee.homeAddress로 읽어도 같은 객체이니 바뀐 값이 보인다. 커밋 직전의 플러시에서 하이버네이트는 02회에서 본 대로 영속 엔티티마다 현재 상태를 스냅샷과 비교한다. kim을 볼 때도, lee를 볼 때도 현재 city는 "부산"이고 스냅샷은 "서울"이므로 두 엔티티 모두 변경된 것으로 판정되어 update가 두 번 나간다. 하이버네이트는 잘못한 것이 없다. 두 엔티티의 상태가 실제로 바뀌었으니 정확히 반영했을 뿐이다.

    이 실험에서 부수적으로 확인되는 사실이 하나 있다. setCity()로 객체 내부를 고친 변경이 감지되었다는 것은 스냅샷이 같은 Address 인스턴스를 가리키고 있지 않았다는 뜻이다. 스냅샷이 그 인스턴스를 그대로 들고 있었다면 현재 값과 스냅샷이 언제나 같은 객체라서 차이를 찾을 수 없었을 것이다. 하이버네이트는 스냅샷에 임베디드 값의 복사본을 따로 보관한다. 그래서 객체 내부를 고치는 변경도, 객체를 통째로 바꾸는 변경도 모두 감지된다.

    마지막 두 줄도 중요하다. 다시 읽은 두 회원의 주소는 same instance=false, 서로 다른 객체다. 데이터베이스에는 "공유"라는 개념이 없다. 두 행에 같은 값이 각각 복사되어 들어 있을 뿐이다. 공유는 오직 한 영속성 컨텍스트가 살아 있는 동안 힙에서만 존재하고, 그 부작용만 플러시를 통해 데이터베이스에 새겨진다. 그래서 이 버그는 테스트에서 엔티티를 새로 조회해 검증하는 방식으로는 원인을 찾기 어렵다. 데이터베이스에 남은 것은 결과뿐이고, 원인인 참조 공유는 트랜잭션이 끝나면서 사라졌다.

    명세는 이 상황을 분명히 금한다. 임베디드 객체는 소유 엔티티에 엄격하게 속하며 영속 엔티티 사이에 공유할 수 없다고 정의하고, 공유를 시도했을 때의 동작은 정의되지 않았다고 적는다(Jakarta Persistence 3.1 §2.6). 이번 실험의 결과는 하이버네이트 6.6에서 관찰한 동작일 뿐, 다른 구현체나 다른 버전이 같은 결과를 낸다는 보장은 없다. 공유하지 않는 것이 유일하게 안전한 선택이다.

    두 엔티티가 같은 Address 객체를 참조하고, 한쪽에서 setCity를 호출하면 플러시 때 두 엔티티 모두 스냅샷과 달라져 UPDATE가 두 번 나간다는 흐름을 보여 준다. 왼쪽 절반은 "힙" 영역. 위쪽에 "Member kim", 아래쪽에 "Member lee" 상자가 있고, 각 상자 안의 "homeAddress" 칸에서 화살표 두 개가 가운데의 하나뿐인 "Address" 상자로 모인다. "Address" 상자 안에는 "city: 서울"에 취소선이 그어지고 옆에 "부산"이 적혀 있다. kim 쪽 화살표 옆에 작은 연필 아이콘과 "setCity(\"부산\")" 라벨. 오른쪽 절반은 "영속성 컨텍스트" 영역으로, "스냅샷 kim: 서울", "스냅샷 lee: 서울" 두 개의 작은 카드가 있다. 각 카드에서 오른쪽 끝의 데이터베이스 원통 아이콘으로 화살표가 하나씩, 모두 두 개 나가고 각각 "UPDATE where id=1", "UPDATE where id=2" 라벨이 붙는다. 아래쪽에 경고색 띠로 "한 번 바꿨는데 두 행이 바뀐다" 문구. 두 회원이 같은 Address 인스턴스를 가리키면, 한쪽에서 바꾼 값이 다른 쪽의 변경으로도 감지되어 UPDATE가 두 번 나간다.

    불변 객체로 막는다

    참조 공유를 컴파일러가 막아 줄 방법은 없다. 자바 21에는 객체를 대입할 때 내용을 복사하도록 만드는 언어 기능이 없으므로 lee.homeAddress = kim.homeAddress는 언제나 참조 복사다. 대입할 때마다 new Address(...)로 복사본을 만드는 방어적 복사(defensive copy)를 할 수는 있지만, 누군가 한 번 잊으면 그만이고 그것을 잡아낼 장치가 없다. 그래서 방향을 바꾼다. 공유를 막는 대신, 공유되어도 문제가 없게 만든다. 기본값 타입에서 Integer와 String이 택한 방법, 곧 불변 객체다.

    임베디드 타입을 불변으로 만드는 방법은 간단하다. 필드를 private으로 두고, 값을 바꾸는 메서드를 하나도 두지 않는다. 값은 생성자로만 정한다. 값을 바꾸고 싶으면 새 객체를 만들어 엔티티의 필드를 교체한다. 앞에서 보인 Address의 withCity()가 그 방법이다. 기존 객체를 고치지 않고 도시만 다른 새 Address를 돌려준다.

    // 객체를 고치지 않고, 새 값으로 갈아 끼운다
kim.homeAddress = kim.homeAddress.withCity("인천");
    Hibernate: update Member set city=?,street=?,zipcode=?,name=?,work_city=?,work_street=?,work_zipcode=?,endDate=?,startDate=? where id=?

    이제 앞의 공유 시나리오를 다시 생각해 보자. 두 회원이 같은 Address 인스턴스를 가리키고 있어도, 그 인스턴스를 고칠 방법이 없다. kim의 주소를 바꾸려면 kim.homeAddress에 새 객체를 넣어야 하고, 그러면 kim만 다른 객체를 가리키게 된다. lee가 가리키는 객체는 그대로이므로 플러시 때 lee의 스냅샷과 현재 값이 같고, update는 kim에 대해서만 나간다. 공유된 상태 자체는 남아 있지만 더 이상 부작용을 만들지 못한다. Integer y = x; x = 20;에서 y가 안전했던 것과 정확히 같은 구조다. 위 출력에서 update 문이 바뀌지 않은 컬럼까지 모두 포함한 것은 하이버네이트가 기본적으로 모든 컬럼을 갱신하는 update를 쓰기 때문이고, 값 타입과는 관계없다.

    왜 final 필드를 쓰지 않는가

    불변 클래스라면 필드를 final로 선언하는 것이 자바의 관례다. 그런데 클래스 형태의 임베더블에서는 그렇게 하지 않는다. Jakarta Persistence 3.2의 @Embeddable Javadoc은 임베더블 타입이 final 메서드나 final 영속 인스턴스 변수를 가져서는 안 된다고 정한다. 앞에서 확인한 대로 하이버네이트는 일반 클래스 임베더블을 인자 없는 생성자로 만든 뒤 필드에 값을 넣는다. 그러니 클래스 임베더블의 불변성은 언어가 강제하는 것이 아니라 "값을 바꾸는 메서드를 두지 않는다"는 설계 약속이다. 클래스 안의 코드가 필드를 고치는 것까지 컴파일러가 막아 주지는 않는다.

    레코드를 임베더블로

    언어 수준의 불변성을 원한다면 레코드(record)가 있다. 레코드는 구성 요소마다 private final 필드를 갖고 세터가 없으며, equals와 hashCode도 자동으로 만들어진다. Jakarta Persistence 3.2의 @Embeddable Javadoc은 임베더블 타입으로 레코드를 명시적으로 허용하고, 레코드에는 인자 없는 생성자 요구를 적용하지 않는다. 이 회차의 실험 환경(하이버네이트 6.6.53, jakarta.persistence-api 3.1.0)에서도 레코드 임베더블이 동작했다.

    @Embeddable
public record LoanPeriod(LocalDate loanedOn, LocalDate dueOn) {
    public LoanPeriod {
        if (dueOn.isBefore(loanedOn)) throw new IllegalArgumentException("반납일이 대출일보다 앞선다");
    }
    public LoanPeriod extend(int days) { return new LoanPeriod(loanedOn, dueOn.plusDays(days)); }
}

@Entity
public class Loan {
    @Id @GeneratedValue Long id;
    @Embedded LoanPeriod period;
}
    Hibernate: create table Loan (dueOn date, loanedOn date, id bigint not null, primary key (id))
Hibernate: select l1_0.id,l1_0.loanedOn,l1_0.dueOn from Loan l1_0 where l1_0.id=?
period=LoanPeriod[loanedOn=2026-11-01, dueOn=2026-11-15]
Hibernate: update Loan set loanedOn=?,dueOn=? where id=?

    레코드에는 인자 없는 생성자가 없고 필드가 final이므로, 하이버네이트는 레코드를 만들 때 정규 생성자(canonical constructor)를 호출해야 한다. 압축 생성자에 출력문을 넣고 실험해 보니 실제로 조회할 때도 정규 생성자가 호출되었다. 이것은 클래스 임베더블과의 중요한 차이다. 레코드의 압축 생성자에 둔 검증은 데이터베이스에서 읽은 값에도 적용된다. 반대로 말하면, 규칙을 어긴 행이 다른 경로로 테이블에 이미 들어가 있다면 그 행을 읽는 순간 생성자가 예외를 던져 조회가 실패한다. 클래스 임베더블의 인자 있는 생성자에 둔 검증은 조회 때 실행되지 않으므로 이런 일이 없지만, 그만큼 잘못된 값이 조용히 객체로 들어온다. 어느 쪽이 나은지는 데이터의 출처를 얼마나 믿을 수 있느냐에 달렸다.

    이 장의 핵심

    임베디드 타입은 의미는 값이지만 구현은 자바 참조형이다. 참조는 대입만으로 공유되고, 가변 객체를 공유하면 한 엔티티의 변경이 다른 엔티티의 변경으로 감지되어 데이터베이스에 그대로 반영된다. 공유를 막을 수는 없으니, 세터를 없애거나 레코드를 써서 공유되어도 해가 없는 불변 객체로 만든다. 값을 바꿀 때는 객체를 고치지 않고 새 값으로 교체한다.

    값 타입의 비교: 동일성과 동등성

    값 타입의 두 번째 요구는 값으로 비교되어야 한다는 것이었다. 자바에는 비교가 두 가지 있다. 동일성(identity) 비교는 ==로, 두 참조가 같은 객체를 가리키는지 본다. 앞의 바이트코드에서 x == y가 if_acmpne라는 참조 비교 명령으로 컴파일된 것을 보았다. 객체의 내용은 전혀 보지 않는다. 동등성(equivalence) 비교는 equals()로, 두 객체가 같은 값을 나타내는지 본다. 무엇이 "같은 값"인지는 클래스가 정한다.

    문제는 equals()의 기본 구현이다. java.lang.Object의 Javadoc은 기본 equals()가 두 참조가 같은 객체를 가리킬 때만, 즉 x == y가 참일 때만 참을 돌려준다고 밝힌다. 클래스가 equals()를 재정의하지 않으면 동등성 비교도 결국 동일성 비교다. 같은 도시, 같은 도로명, 같은 우편번호로 new Address(...)를 두 번 하면 두 객체는 ==로도, 기본 equals()로도 다르다. 값 타입에게 이것은 틀린 답이다. 그래서 값 타입은 모든 필드를 비교하도록 equals()를 재정의해야 하고, 그와 함께 hashCode()도 재정의해야 한다. Object.hashCode()의 계약은 equals()로 같은 두 객체가 같은 해시 코드를 돌려줘야 한다고 정한다. HashSet과 HashMap은 먼저 해시 코드로 버킷을 찾고 그 안에서 equals()로 원소를 찾으므로, 둘 중 하나만 재정의하면 해시 기반 컬렉션에서 같은 값을 찾지 못한다.

    앞의 Address가 구현한 equals()를 다시 보자. 먼저 this == o로 같은 객체인지 빠르게 확인하고, instanceof 패턴 매칭(자바 16부터)으로 타입을 확인하면서 변수 that을 얻는다. 필드 비교에는 Objects.equals()를 썼다. 임베디드 값의 컬럼은 null일 수 있으므로 city.equals(that.city)처럼 쓰면 city가 null일 때 NullPointerException이 난다. hashCode()는 같은 필드 목록으로 Objects.hash()를 호출해 계약을 맞췄다. 비교에 쓰는 필드 목록이 두 메서드에서 같아야 한다는 것이 요점이다.

    필드 접근과 게터 접근 중 무엇으로 비교할지도 엔티티와 사정이 다르다. 07회에서 다루는 지연 로딩 프록시는 엔티티를 대신하는 객체라서, 엔티티의 equals()에서 다른 객체의 필드를 직접 읽으면 프록시의 빈 필드를 읽게 되는 문제가 있다. 임베디드 값은 앞의 조회 SQL에서 본 것처럼 소유 엔티티를 읽을 때 같은 행에서 함께 만들어지므로, 값 객체끼리의 비교에서는 필드를 직접 읽어도 된다.

    레코드는 이 일을 대신해 준다. 레코드의 암묵적인 equals()는 같은 레코드 클래스의 인스턴스이고 모든 구성 요소가 같을 때 참이 되도록 정해져 있다(JLS §8.10.3). 바이트코드를 열어 보면 구현 방식이 독특하다.

    record Point(int x, int y) {}

Point p1 = new Point(1, 2);
Point p2 = new Point(1, 2);
System.out.println("p1 == p2 : " + (p1 == p2));
System.out.println("p1.equals(p2) : " + p1.equals(p2));
    p1 == p2 : false
p1.equals(p2) : true
    public final boolean equals(java.lang.Object);
  Code:

     2: invokedynamic #24,  0   // InvokeDynamic #0:equals:(LValueDemo$Point;Ljava/lang/Object;)Z

    javac는 필드를 하나씩 비교하는 코드를 직접 만들지 않고 invokedynamic 한 줄을 넣었다. 이 호출 지점은 처음 실행될 때 부트스트랩 메서드인 java.lang.runtime.ObjectMethods.bootstrap에 연결되어, 구성 요소 목록을 받아 비교 로직을 런타임에 만든다. javap -v로 보면 부트스트랩 메서드 표에 이 메서드가 있고, 인자로 레코드 클래스 ValueDemo$Point, 구성 요소 이름을 이은 문자열 x;y, 그리고 필드 x와 y를 읽는 메서드 핸들(REF_getField) 두 개가 들어 있다. 클래스 파일에는 "구성 요소를 모두 비교한다"는 의도만 기록되고, 구체적인 구현은 JDK가 정한다.

    래퍼 타입도 equals()로 비교해야 한다. 앞의 예에서 x == y가 참이었던 것은 y = x로 참조를 복사했기 때문이지, 값이 같아서가 아니다. JLS §5.1.7은 -128에서 127 사이의 정수를 내는 상수 표현식을 박싱할 때 같은 참조가 나온다는 것만 보장하고, 그 밖의 값은 보장하지 않는다. 실행 중에 박싱되는 값은 Integer.valueOf와 Long.valueOf의 Javadoc이 정한 대로 -128에서 127 사이만 항상 캐시된 객체가 나온다. 엔티티의 식별자를 Long으로 두고 member.getId() == otherId처럼 비교하는 코드가 작은 숫자로 테스트할 때는 통과하다가 식별자가 커지면 틀리는 이유가 여기에 있다.

    하이버네이트는 값을 어떻게 비교하는가

    값 타입의 equals()를 재정의했다면, 하이버네이트는 그것을 언제 쓰고 언제 쓰지 않을까. 실험으로 세 경우를 나눠 보자.

    1. 임베디드 필드의 변경 감지는 equals를 부르지 않는다

    영속 상태의 회원에게 지금과 똑같은 값을 가진 새 Address를 넣고 플러시했다. equals()를 재정의한 Address로 해도, 재정의하지 않은 가변 Address로 해도 결과는 같았다.

    equals()가 거짓을 돌려주는 다른 인스턴스로 교체했는데도 update가 나가지 않았다. 하이버네이트는 임베디드 필드가 바뀌었는지 판단할 때 객체의 equals()가 아니라 그 안의 속성 값을 하나씩 비교한다. 참조가 바뀌어도 컬럼에 들어갈 값이 같으면 변경이 아니다. 데이터베이스 관점에서는 정확한 판단이다. 이 결과는 임베디드 필드의 변경 감지가 사용자의 equals() 구현에 의존하지 않는다는 뜻이기도 하다.

    2. 컬렉션 조작은 자바의 equals를 쓴다

    자바 컬렉션의 contains(), remove(Object), indexOf()는 Javadoc에 정해진 대로 equals()로 원소를 찾는다. 뒤에서 볼 값 타입 컬렉션 실험에서 addressHistory.remove(new Address("부산", "해운대로 3", "48094"))가 removed=true를 돌려준 것은 Address가 equals()를 재정의했기 때문이다. 재정의하지 않았다면 새로 만든 객체는 리스트 안의 어떤 원소와도 같지 않으므로 false가 나오고, 아무것도 지워지지 않고, SQL도 나가지 않는다. 버그가 조용히 넘어가는 형태다.

    3. 집합 컬렉션의 변경 추적은 equals와 hashCode에 의존한다

    세 번째 경우가 가장 덜 알려져 있다. 하이버네이트가 Set으로 매핑한 값 타입 컬렉션의 변경을 어떻게 찾는지 하이버네이트 6.6.53의 org.hibernate.collection.spi.PersistentSet을 javap -c로 열어 보면 구조가 드러난다. getSnapshot()은 현재 원소마다 원소 타입의 deepCopy()로 복사본을 만들어 HashMap에 넣는다. 플러시 때 getDeletes()는 스냅샷의 각 원소에 대해 현재 집합이 그것을 contains()하지 않으면 삭제 대상으로 고르고, needsInserting()은 현재 원소로 스냅샷 맵을 get()해 없으면 삽입 대상으로 고른다. contains()와 get()은 모두 hashCode()와 equals()로 동작한다.

    그렇다면 equals()와 hashCode()가 없는 임베디드 타입을 Set에 담으면 어떻게 될까. 스냅샷의 원소는 복사본이라 현재 원소와 다른 객체이고, 기본 equals()는 참조 비교이므로 스냅샷의 어떤 원소도 현재 집합에서 찾아지지 않는다. 모든 원소가 삭제 대상이자 삽입 대상이 된다. 실험해 보자. 이름 하나만 가진 Tag 임베더블을 equals() 없이 만들고, 원소 세 개를 저장한 뒤 다시 읽어 원소 하나를 지웠다.

    하이버네이트가 집합의 스냅샷을 복사본으로 만들고 contains로 현재 집합과 대조하기 때문에, equals가 없으면 모든 원소가 지워졌다가 다시 들어간다는 것을 위아래 두 줄로 비교한다. 위아래 두 단으로 나뉜 비교 그림. 각 단의 왼쪽에 "스냅샷(복사본)" 상자 세 개 "a", "b", "c", 오른쪽에 "현재 집합" 상자 두 개 "b", "c"가 있다. 위 단 제목은 "equals 재정의함". 왼쪽 "b"와 오른쪽 "b", 왼쪽 "c"와 오른쪽 "c"가 초록 실선으로 이어지고 "같음" 라벨이 붙는다. 왼쪽 "a"에만 빨간 X와 "DELETE 1행" 라벨. 아래 단 제목은 "equals 없음". 왼쪽 세 상자와 오른쪽 두 상자 사이의 선이 모두 끊긴 회색 점선이고 가운데에 "참조가 달라 찾지 못함" 라벨. 왼쪽 세 상자 모두에 빨간 X와 "DELETE 3행", 오른쪽 두 상자 모두에 초록 플러스와 "INSERT 2행" 라벨. 아래 단 오른쪽 끝에 순환 화살표 아이콘과 "플러시마다 반복" 문구. 스냅샷은 원소의 복사본이다. equals와 hashCode가 없으면 복사본과 현재 원소가 서로를 찾지 못해, 하이버네이트는 모든 원소가 바뀐 것으로 판단한다.

    값 타입 컬렉션: @ElementCollection과 컬렉션 테이블

    지금까지의 값 타입은 엔티티 하나에 값 하나였다. 회원이 좋아하는 음식 여러 개, 과거에 살았던 주소 여러 개처럼 값 여러 개를 담고 싶으면 어떻게 할까. 관계형 테이블의 컬럼에는 값이 하나만 들어간다. "치킨, 피자"를 문자열 하나로 이어 붙여 컬럼 하나에 넣을 수는 있지만, 그러면 데이터베이스는 그 안의 원소를 알지 못해 원소 단위로 검색하거나 제약을 걸 수 없다. 원소마다 행 하나를 갖는 별도 테이블을 만들고, 그 테이블에 소유 엔티티의 식별자를 외래 키로 두는 것이 관계형 모델의 방식이다. 구조로 보면 일대다다. 다만 "다" 쪽 행에 자기 식별자가 없다.

    JPA에서는 이것을 값 타입 컬렉션이라 하고 @ElementCollection으로 매핑한다. 명세는 이런 컬렉션이 컬렉션 테이블(collection table)로 매핑된다고 정하고(Jakarta Persistence 3.1 §2.7), 테이블 이름과 외래 키 컬럼은 @CollectionTable로 지정한다.

    @Entity
public class Member {
    // ... (id, name, workPeriod, homeAddress, workAddress)

    @ElementCollection
    @CollectionTable(name = "favorite_food", joinColumns = @JoinColumn(name = "member_id"))

    Set favoriteFoods = new HashSet<>();

    @ElementCollection
    @CollectionTable(name = "address_history", joinColumns = @JoinColumn(name = "member_id"))

     addressHistory = new ArrayList<>();
}

    기본값 컬렉션 Set은 원소 컬럼 하나짜리 테이블이 되고, 컬럼 이름은 @Column으로 정했다. 임베디드 컬렉션 List

    는 Address의 필드가 컬렉션 테이블의 컬럼으로 펼쳐졌다. 두 테이블 모두 member_id가 Member를 가리키는 외래 키다. 그리고 눈여겨볼 것이 있다. 두 테이블 모두 기본 키가 없다. 이 사실이 다음 절의 모든 동작을 결정한다.

    @CollectionTable을 생략하면 명세의 기본 규칙이 적용된다. 테이블 이름은 "엔티티 이름 + 밑줄 + 컬렉션 속성 이름", 외래 키 컬럼 이름은 "엔티티 이름 + 밑줄 + 참조하는 기본 키 컬럼 이름"이다(@CollectionTable Javadoc). 실험에서 Patron 엔티티에 @ElementCollection Set nicknames만 두었더니 Patron_nicknames (Patron_id bigint not null, nicknames varchar(255)) 테이블이 생겼다. 기본값 컬렉션의 원소 컬럼 이름은 속성 이름을 따랐다.

    집합: 값으로 행을 지목한다

    Set은 중복을 허용하지 않으므로 "소유자 식별자 + 원소 값"이 행 하나를 유일하게 가리킨다. 그래서 원소 하나를 지우면 그 값으로 행 하나를 삭제하고, 원소 하나를 추가하면 행 하나를 넣는다. 음식 집합에서 "치킨"을 지우고 "족발"을 넣었을 때 나간 SQL은 delete from favorite_food where member_id=? and food_name=?와 insert into favorite_food (member_id,food_name) values (?,?) 두 줄뿐이었다. 원소 컬럼을 @Column(nullable = false)로 매핑하면 하이버네이트는 DDL에 primary key (patron_id, tag)처럼 소유자 식별자와 원소를 묶은 기본 키까지 만들어, 데이터베이스 수준에서도 중복을 막는다.

    임베디드 타입의 집합에서는 조건이 하나 더 붙는다. 표에서 같은 Set

    가 컬럼이 nullable일 때는 전체를 다시 썼고, 모든 컬럼을 nullable = false로 바꾸자 한 행만 지웠다. 하이버네이트 6.6.53의 AbstractPersistentCollection.needsRecreate()를 javap로 보면 이유가 보인다. 원소 타입이 복합 타입(CompositeType)이고 hasNullProperty()가 참이면 컬렉션 전체를 다시 만들도록 되어 있다. hasNullProperty는 임베디드 타입의 속성 중 하나라도 매핑상 nullable이면 참이 된다. 이 조건은 SQL의 NULL 비교 규칙과 맞물린다. SQL에서 city = NULL은 참이 되지 않으므로, null이 들어 있을 수 있는 컬럼은 where 절의 등호로 행을 지목하는 데 쓸 수 없다.

    백: 지목할 방법이 없으니 다시 쓴다

    List에 @OrderColumn이 없으면 하이버네이트는 그것을 백(bag)으로 다룬다. 중복을 허용하고 순서를 저장하지 않는 컬렉션이다(Hibernate ORM 6.6 User Guide §3.9.5). 같은 주소가 두 번 들어 있을 수 있으니 값으로도 행을 지목할 수 없고, 순서도 저장하지 않으니 위치로도 지목할 수 없다. 실험에서 이전 주소 둘 중 하나를 지웠을 때의 SQL이 그 결과다.

PersistentBag.needsRecreate()의 바이트코드는 이 컬렉션이 일대다 연관관계가 아니면 항상 참을 돌려준다. 값 타입의 백은 원소를 하나만 바꿔도 언제나 전체를 다시 쓴다는 뜻이다. 이전 주소가 1,000개인 회원에서 하나를 지우면 delete 한 번이 1,000행을 지우고 insert가 999번 나간다. 원소 하나를 추가할 때는 어떤지, 컬렉션 참조를 통째로 바꾸면 어떤지는 직접 실험해 확인해 보기를 권한다. 원칙은 같다. 행을 지목할 수 없으면 다시 쓴다.

    순서 컬럼: 위치로 지목하지만 당겨지면 갱신한다

    @OrderColumn(name = "seq")을 붙이면 리스트의 위치가 seq 컬럼에 저장되고, 하이버네이트는 (seq, 소유자 id)를 기본 키로 만든다. 이제 위치로 행을 지목할 수 있다. 원소 A, B, C를 저장한 뒤 맨 앞의 A를 지웠다.

    식별자가 없는 컬렉션 테이블에서 행을 지목하는 방법(값, 전체 재작성, 위치)이 매핑에 따라 달라진다는 것을 세 칸으로 비교한다. 가로로 세 칸이 나란히 있는 비교 그림. 각 칸 위에 제목, 가운데에 작은 테이블 그림, 아래에 SQL 요약이 있다. 첫째 칸 제목 "Set: 값으로 지목". 테이블 행 "치킨", "피자" 중 "치킨" 행에만 빨간 X. 아래 라벨 "DELETE 1행". 둘째 칸 제목 "Bag: 지목 불가". 테이블 행 "부산", "대전" 모두 빨간 X가 그어지고 오른쪽에 초록 플러스로 "대전" 행이 다시 그려진다. 아래 라벨 "전체 DELETE 후 다시 INSERT". 셋째 칸 제목 "@OrderColumn: 위치로 지목". 테이블에 "seq 0: A", "seq 1: B", "seq 2: C" 세 행이 있고, "seq 2" 행에 빨간 X, "seq 0"과 "seq 1" 행의 값이 화살표로 각각 "B", "C"로 바뀐다. 아래 라벨 "DELETE 1행 + UPDATE 2행". 세 칸 모두 테이블 위에 작은 회색 글씨로 "식별자 없음". 컬렉션 테이블에는 식별자가 없다. 집합은 값으로, 순서 컬럼이 있는 리스트는 위치로 행을 지목하고, 백은 지목할 방법이 없어 전체를 다시 쓴다.

    대안: 식별자가 필요하면 엔티티로 승격한다

    값 타입 컬렉션의 한계는 모두 한 가지에서 나온다. 행에 식별자가 없다. 그래서 행 하나를 가리키기 어렵고, 다른 곳에서 특정 원소를 참조할 수도 없고, 원소별로 이력을 추적할 수도 없다. 원소가 많아지거나 자주 바뀌는 상황에서 이 한계가 드러나면, 원소를 엔티티로 승격하는 것이 정석이다. 주소 자체는 여전히 값으로 두고, 그 값을 감싸는 작은 엔티티를 만든다.

    @Embeddable
public class Period {
    private LocalDate startDate;
    private LocalDate endDate;

    protected Period() {}

    public Period(LocalDate startDate, LocalDate endDate) {
        if (endDate.isBefore(startDate)) {
            throw new IllegalArgumentException("종료일이 시작일보다 앞선다");
        }
        this.startDate = startDate;
        this.endDate = endDate;
    }

    public boolean contains(LocalDate day) {
        return !day.isBefore(startDate) && !day.isAfter(endDate);
    }

    public Period extendTo(LocalDate newEnd) {
        return new Period(startDate, newEnd);
    }

    // equals, hashCode: startDate, endDate 두 필드로 (Address와 같은 방식)
}

@Entity
public class Patron {
    @Id @GeneratedValue
    private Long id;

    private String name;

    @Embedded
    private Address address;            // 앞에서 만든 불변 Address

    @Embedded
    @AttributeOverrides({
        @AttributeOverride(name = "startDate", column = @Column(name = "member_since")),
        @AttributeOverride(name = "endDate",   column = @Column(name = "member_until"))
    })
    private Period membership;

    protected Patron() {}

    public Patron(String name, Address address, Period membership) {
        this.name = name;
        this.address = address;
        this.membership = membership;
    }

    public boolean canBorrowOn(LocalDate day) {
        return membership != null && membership.contains(day);
    }

    public void moveTo(Address newAddress) { this.address = newAddress; }
    public void renewUntil(LocalDate newEnd) { this.membership = membership.extendTo(newEnd); }
}

    정리: 다른 회차와의 연결

    이 회차의 내용은 두 기준으로 요약된다. 식별자가 없고 생명주기를 엔티티에 맡기는 것은 값이다. 값은 공유되어서는 안 되고 값으로 비교되어야 한다. 기본값 타입은 자바가 이 둘을 저절로 지켜 주지만, 임베디드 타입은 개발자가 불변 객체와 equals()·hashCode()로 직접 지켜야 한다. 지키지 않았을 때의 결과는 예외가 아니라 조용히 잘못 나가는 SQL이라서 더 위험하다.

    이 내용은 앞뒤 회차와 이어진다. 07회의 영속성 전이와 고아 객체 제거는 값 타입 컬렉션이 기본으로 가진 생명주기를 엔티티 관계에 명시적으로 부여하는 기능이다. 09회의 JPQL에서는 m.homeAddress.city처럼 임베디드 값을 경로 표현식으로 조건에 쓰게 되는데, 임베디드 타입은 엔티티가 아니므로 그 자체를 from 절의 조회 대상으로 쓸 수는 없다는 차이가 있다. 10회의 페치 조인은 이 회차에서 본 컬렉션 초기화 SQL이 엔티티 수만큼 반복되는 문제를 다룬다. 이 강좌 뒤쪽의 스프링 데이터 JPA와 Querydsl에서도 임베디드 타입은 그대로 쓰이고, 조회 조건에서 address.city 같은 경로로 다뤄진다.

    엔티티 타입과 값 타입
    엔티티는 식별자로 추적되고 독립된 생명주기를 가진다. 값 타입은 식별자가 없고 소유 엔티티와 생명주기를 함께한다. JPA의 값 타입은 자바의 기본형과 다른 개념이며, 참조형으로 구현된 값 타입에서 함정이 생긴다.
    기본값 타입
    기본형은 지역 변수 칸 사이에서 값이 복사되어 공유될 수 없고, 래퍼와 String은 참조가 공유되지만 불변이라 안전하다. 래퍼에 대입하면 기존 객체가 바뀌지 않고 새 참조가 저장된다.
    임베디드 타입
    @Embeddable 클래스의 필드가 소유 엔티티 테이블의 컬럼으로 펼쳐진다. 테이블은 그대로 두고 객체만 의미 단위로 나누며, 인자 없는 생성자가 필요하고 클래스는 final이면 안 된다. 컬럼이 모두 null이면 null로 복원된다.
    @AttributeOverride
    같은 임베디드 타입을 한 엔티티에서 두 번 쓰면 기본 컬럼 이름이 충돌해 부트스트랩이 실패하므로, 필드별로 컬럼 이름을 재정의한다.
    공유 참조의 부작용과 불변 객체
    가변 임베디드 객체를 두 엔티티가 공유하면 한쪽의 변경이 양쪽의 변경으로 감지되어 UPDATE가 두 번 나간다. 세터를 없애거나 레코드를 써서 불변으로 만들고, 값을 바꿀 때는 새 객체로 교체한다.
    동일성과 동등성
    ==는 참조를 비교하고 equals는 값을 비교한다. Object의 기본 equals는 참조 비교이므로 값 타입은 모든 필드로 equals와 hashCode를 함께 재정의해야 한다. 레코드는 이를 자동으로 제공한다.
    하이버네이트의 값 비교
    임베디드 필드의 변경 감지는 속성 값을 하나씩 비교해 equals에 의존하지 않는다. 반면 Set 값 타입 컬렉션은 복사본 스냅샷과 현재 원소를 equals·hashCode로 대조하므로, 이 둘이 없으면 플러시마다 전체를 지우고 다시 넣는다.
    값 타입 컬렉션
    @ElementCollection과 @CollectionTable로 소유자 식별자를 외래 키로 갖는 별도 테이블에 저장한다. 기본은 지연 로딩이고, 소유자와 함께 저장·삭제된다. 행에 식별자가 없어 Set은 값으로, @OrderColumn 리스트는 위치로 행을 지목하고, 백은 전체를 다시 쓴다.
    엔티티로 승격
    원소를 따로 가리키거나 추적해야 하고 자주 바뀐다면, 값을 감싸는 엔티티를 만들고 일대다 관계에 cascade ALL과 orphanRemoval을 준다. 그러면 원소 하나의 변경이 식별자로 지목된 행 하나의 SQL이 된다.

    실무에서 값 타입 문제는 대개 "데이터가 이상하게 바뀌었다"는 장애 보고로 시작한다. 한 회원의 주소를 고쳤더니 같은 날 가입한 다른 회원의 주소도 바뀌었다는 식이다. 이때 SQL 로그에 같은 트랜잭션 안에서 서로 다른 식별자에 대한 update가 나란히 찍혀 있다면, 가장 먼저 의심할 곳은 가변 임베디드 객체의 참조 공유다. 엔티티를 만들 때 다른 엔티티의 주소 객체를 그대로 넘겨받는 팩토리 메서드나 복사 생성자가 흔한 원인이다. 근본적인 해결은 해당 임베디드 타입에서 세터를 없애는 것이고, 그러면 컴파일 오류가 공유 후 수정하던 코드를 모두 찾아 준다.

    성능 쪽 증상은 "변경한 것이 거의 없는데 쓰기 SQL이 많다"로 나타난다. SQL 로그에서 컬렉션 테이블에 대해 소유자 식별자 하나로 delete한 뒤 insert가 줄지어 나간다면 값 타입 백이고, 아무것도 바꾸지 않은 트랜잭션에서 같은 패턴이 반복된다면 equals()와 hashCode() 없는 임베디드 타입의 집합이다. 앞의 경우는 Set과 nullable = false로 바꾸거나 엔티티로 승격하고, 뒤의 경우는 두 메서드를 재정의하면 된다. 원소 수가 적을 때는 차이가 보이지 않다가 데이터가 쌓이면서 문제가 되므로, 매핑을 정할 때 원소 수가 얼마나 늘어날 수 있는지를 함께 따져야 한다.

    판단이 달라지는 조건도 있다. 주소처럼 보이는 데이터라도 "배송지 목록에서 기본 배송지를 고른다", "특정 배송지로 보낸 주문을 찾는다"처럼 원소 하나를 가리켜야 하는 요구가 있다면 처음부터 엔티티가 맞다. 반대로 레거시 테이블에 이미 기본 키 없는 자식 테이블이 있고 원소가 몇 개 되지 않는다면 값 타입 컬렉션으로 매핑하는 것이 가장 간단하다. 레코드 임베더블은 불변성과 equals()를 공짜로 주지만, 조회 때 생성자 검증이 실행되므로 규칙을 어긴 기존 데이터가 있는 테이블에 적용할 때는 먼저 데이터를 점검해야 한다.
  • 세터가 있는 Address로 회원 a, b를 만들고, a.homeAddress = new Address("서울", "테헤란로 1")을 넣은 뒤 b.homeAddress = a.homeAddress로 같은 객체를 넣어 둘 다 persist()한 뒤 flush()했다. 이어서 b.homeAddress = new Address("대구", "동성로 5")로 교체하고, 그다음 a.homeAddress.setCity("광주")를 호출한 뒤 커밋했다. 커밋 때 나가는 update는 몇 번이며, 최종적으로 두 회원의 도시는 무엇인가? 힙 그림을 그려 설명하라.
  • equals()와 hashCode()를 재정의하지 않은 임베디드 타입 Phone을 @ElementCollection List phones(순서 컬럼 없음)로 매핑했다. 원소 3개가 저장된 회원을 조회해 phones.remove(new Phone("010-1111-2222"))를 호출하고 커밋하면 어떤 SQL이 나가는가? equals()를 재정의한 경우와 비교하라.
  • 회원에 @ElementCollection Set
    deliveryAddresses가 있고, Address는 equals()·hashCode()를 재정의했지만 컬럼에 nullable = false를 주지 않았다. 배송지가 50개인 회원에서 하나를 지우면 어떤 SQL이 몇 번 나가는가? 한 행만 지우게 하려면 무엇을 바꾸면 되는가?
  • 모든 컬럼이 null인 new Address(null, null, null)을 회원에 넣어 저장한 뒤, 같은 트랜잭션 안에서 em.find()로 다시 꺼내 getHomeAddress().getCity()를 호출하는 경우와, em.flush()와 em.clear()를 차례로 호출한 뒤 em.find()로 꺼내 같은 호출을 하는 경우의 결과를 각각 예측하라.
    •

    1. update는 두 번 나가고, 최종 결과는 a가 광주, b가 대구다. 처음에는 두 회원의 homeAddress가 같은 객체 X를 가리킨다. b.homeAddress에 새 객체 Y를 넣는 순간 b는 Y를, a는 여전히 X를 가리킨다. 이후 a.homeAddress.setCity("광주")는 X만 고친다. 플러시 때 a는 스냅샷(서울)과 현재(광주)가 달라 update가 나가고, b는 스냅샷(서울, 테헤란로 1)과 현재(대구, 동성로 5)가 달라 역시 update가 나간다. 본문의 공유 실험과 update 횟수는 같지만 의미는 다르다. 여기서는 두 회원 모두 각자 값이 바뀐 것이고, a의 변경이 b에 번지지 않았다. b의 참조를 교체하는 순간 공유가 끊겼기 때문이다. "a의 변경 때문에 두 번"이라고 답했다면 교체 이후의 힙 그림을 다시 그려 보자.

    2. equals()가 없으면 remove(new Phone(...))는 리스트의 어떤 원소와도 같지 않아 false를 돌려주고 리스트는 그대로다. 다만 remove()가 원소를 비교하려면 컬렉션이 초기화되어야 하므로 컬렉션을 읽는 select는 한 번 나간다. 쓰기 SQL은 없다. equals()를 재정의했다면 원소 하나가 지워지고, 이 컬렉션은 백이므로 플러시 때 delete ... where member_id=? 한 번으로 세 행을 모두 지운 뒤 남은 두 원소를 insert 두 번으로 다시 넣는다.

    3. Address의 속성이 nullable이므로 하이버네이트 6.6에서는 needsRecreate()가 참이 되어 컬렉션 전체를 다시 쓴다. 회원의 배송지를 모두 지우는 delete 한 번(50행 삭제)과 남은 49개를 넣는 insert 49번이 나간다. 이 컬렉션의 @AttributeOverride로 city, street, zipcode 컬럼을 모두 nullable = false로 매핑하면, 하이버네이트가 (소유자 id, city, street, zipcode)를 기본 키로 만들고 모든 컬럼 값을 조건으로 한 delete 한 번만 보낸다. 원소를 따로 가리킬 일이 있다면 엔티티로 승격하는 것도 방법이다.

    4. 같은 트랜잭션 안에서 em.find()는 1차 캐시에 있는 바로 그 회원 인스턴스를 돌려주므로, homeAddress에는 처음 넣은 빈 Address 객체가 그대로 있고 getCity()는 null을 돌려준다. em.flush()로 insert가 나간 뒤 em.clear()로 1차 캐시를 비웠으므로, em.find()는 데이터베이스에서 행을 새로 읽는다. 그런데 세 컬럼이 모두 null이므로 하이버네이트는 homeAddress를 null로 복원한다. 따라서 getHomeAddress().getCity()는 NullPointerException을 던진다. 같은 코드가 영속성 컨텍스트의 상태에 따라 다르게 동작하는 예다.

     두 회원이 세터가 있는 같은 Address 인스턴스를 참조하는 상태에서 한 회원의 주소 도시만 setCity로 바꾸고 커밋했다. UPDATE가 두 번 나가는 가장 직접적인 이유는? 하이버네이트가 같은 임베디드 타입을 쓰는 엔티티를 모두 갱신하기 때문이다. Address에 equals가 재정의되어 있어 두 엔티티가 같은 값으로 판정되었기 때문이다. 두 엔티티가 힙의 같은 객체를 가리켜, 플러시 때 각 엔티티의 현재 값이 자기 스냅샷과 다르게 보이기 때문이다. 임베디드 타입은 별도 테이블에 저장되어 그 테이블과 회원 테이블이 함께 갱신되기 때문이다. 변경 감지는 엔티티마다 현재 값과 스냅샷을 비교한다. 두 엔티티가 같은 객체를 참조하므로 한 번의 setCity가 두 엔티티 모두의 현재 값을 바꾼다. 하이버네이트가 같은 타입을 쓰는 엔티티를 일괄 갱신하는 규칙은 없고, 임베디드 값은 소유 엔티티 테이블의 컬럼이지 별도 테이블이 아니다. 임베디드 필드의 변경 감지는 equals가 아니라 속성 값을 비교한다. equals와 hashCode를 재정의하지 않은 임베디드 타입을 @ElementCollection Set으로 매핑했다. 아무것도 바꾸지 않고 플러시하면 하이버네이트 6.6에서 어떤 일이 일어나는가? 아무 SQL도 나가지 않는다. 변경이 없으니 스냅샷과 현재가 같다. 원소마다 delete와 insert가 나간다. 스냅샷은 원소의 복사본이라, 참조 비교로는 현재 원소와 짝을 찾지 못한다. 컬렉션을 다시 읽는 select만 나간다. 부트스트랩 단계에서 equals가 없다는 예외가 나서 실행되지 않는다. PersistentSet은 스냅샷을 원소의 deepCopy로 만들고, 플러시 때 contains와 get으로 현재 원소와 대조한다. 기본 equals와 hashCode는 참조 기반이므로 복사본과 원본이 서로를 찾지 못해 모든 원소가 삭제 대상이자 삽입 대상이 되고, 이 일이 플러시마다 반복된다. 하이버네이트는 equals가 없다고 부트스트랩을 막지 않는다. @OrderColumn 없이 List로 매핑한 임베디드 값 타입 컬렉션(백)에서 원소 하나를 지우면, 다른 매핑과 달리 전체를 지우고 다시 넣는다. 그 근본 원인으로 가장 알맞은 것은? List는 지연 로딩을 지원하지 않기 때문이다. 임베디드 타입은 equals를 쓸 수 없기 때문이다. 컬렉션 테이블에 외래 키 제약 조건이 없기 때문이다. 행에 식별자가 없고, 백은 중복을 허용하고 순서도 저장하지 않아 값으로도 위치로도 특정 행을 지목할 수 없기 때문이다. 컬렉션 테이블에는 기본 키가 없다. Set은 중복이 없어 값으로, @OrderColumn 리스트는 위치로 행을 지목할 수 있지만 백은 둘 다 불가능하다. 하이버네이트 6.6의 PersistentBag.needsRecreate는 일대다가 아니면 항상 참을 돌려준다. 실험에서 백도 지연 로딩되었고, 외래 키 제약도 만들어졌으며, 임베디드 타입의 equals는 정상적으로 쓰였다. Integer x = 10; Integer y = x; x = 20; 을 실행한 뒤 y가 여전히 10인 이유를 바이트코드 관점에서 가장 정확하게 설명한 것은? y = x는 참조를 복사했지만, x = 20은 Integer.valueOf(20)이 돌려준 다른 참조를 x에 저장할 뿐 10을 담은 객체를 고치지 않기 때문이다. y = x에서 Integer 객체가 새로 복제되어 y가 별도의 객체를 갖기 때문이다. Integer는 기본형이라 지역 변수 칸에 값이 직접 저장되기 때문이다. -128~127 범위의 Integer는 캐시되어 값이 바뀌지 않기 때문이다. y = x는 aload와 astore로 참조를 복사하며, 실제로 x == y는 참이었다. x = 20은 Integer.valueOf(20)의 결과를 astore로 저장하는 새 대입이다. Integer는 private final int value를 가진 불변 객체라 기존 객체의 값을 바꿀 방법이 없다. Integer는 참조형이고, 캐시는 같은 참조를 돌려줄지에 관한 규칙이지 불변성의 근거가 아니다.
    값 타입(value type)
    식별자가 없고 생명주기를 소유 엔티티에 의존하는 데이터 타입. JPA에서는 기본값 타입, 임베디드 타입, 값 타입 컬렉션으로 나뉜다.
    임베더블 클래스(embeddable class)
    @Embeddable을 붙인, 소유 엔티티의 일부로만 존재하는 클래스. 필드가 소유 엔티티 테이블의 컬럼으로 매핑된다.
    불변 객체(immutable object)
    만들어진 뒤 상태를 바꿀 수 없는 객체. 참조가 공유되어도 부작용이 생기지 않으며, 값을 바꾸려면 새 객체를 만들어 교체한다.
    동일성(identity)
    두 참조가 같은 객체를 가리키는지의 비교. 자바에서는 == 연산자이며 바이트코드에서는 if_acmpeq/if_acmpne 같은 참조 비교 명령이 된다.
    동등성(equivalence)
    두 객체가 같은 값을 나타내는지의 비교. equals 메서드로 정의하며, 재정의하지 않으면 Object의 기본 구현인 참조 비교가 된다.
    컬렉션 테이블(collection table)
    값 타입 컬렉션의 원소를 원소마다 한 행씩 저장하는 테이블. 소유 엔티티의 식별자를 외래 키로 가지며 원소 자체의 식별자는 없다.
    백(bag)
    중복을 허용하고 순서를 저장하지 않는 컬렉션 의미. 하이버네이트는 @OrderColumn 없는 List나 Collection을 백으로 다룬다.
    순서 컬럼(order column)
    @OrderColumn으로 지정해 리스트 원소의 위치를 저장하는 컬럼. 소유자 식별자와 함께 컬렉션 테이블의 기본 키가 된다.
