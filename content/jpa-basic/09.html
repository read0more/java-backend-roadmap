    식별자로 찾을 수 없는 것을 찾는 문제

    지금까지 엔티티를 꺼내는 방법은 사실상 em.find(Employee.class, id) 하나였다. 식별자를 알면 영속성 컨텍스트의 1차 캐시를 먼저 보고, 없으면 기본 키로 한 행을 읽는다. 연관관계가 있으면 객체 그래프를 따라 employee.getDepartment()처럼 옆 객체로 건너갈 수도 있다. 그런데 실제 애플리케이션이 던지는 질문은 대개 식별자로 시작하지 않는다. "나이가 30보다 많은 사원", "부서별 인원 수", "가장 최근에 가입한 회원 20명" 같은 질문에는 조건, 집계, 정렬, 개수 제한이 들어간다.

    이런 질문을 객체 그래프 탐색만으로 풀려면 모든 엔티티를 메모리에 올린 뒤 자바 코드로 걸러야 한다. 사원이 몇 명일 때는 상관없지만 수백만 행이 되면 불가능하다. 결국 필터링과 집계는 데이터가 있는 곳, 즉 데이터베이스에서 해야 하고, 그러려면 SQL이 필요하다. 문제는 SQL이 테이블과 컬럼을 대상으로 한다는 점이다. 애플리케이션은 엔티티 클래스와 필드로 생각하는데 쿼리를 쓸 때만 테이블 이름, 컬럼 이름, 조인 컬럼을 떠올려야 한다면 1회에서 본 패러다임 불일치가 쿼리 작성 단계에서 다시 생긴다.

    JPQL(Jakarta Persistence Query Language)은 이 틈을 메우려고 만든 언어다. 문법은 SQL을 닮았지만 FROM 절에 오는 것은 테이블이 아니라 엔티티 이름이고, 점(.)으로 이어지는 것은 컬럼이 아니라 엔티티의 속성과 연관관계다. 명세는 이것을 추상 스키마(abstract schema)라고 부른다. 엔티티와 그 속성, 관계로 이루어진 논리적 모델 위에서 쿼리를 쓰면, 영속성 공급자가 매핑 정보를 보고 실제 테이블에 대한 SQL로 번역한다. 그래서 JPQL은 특정 데이터베이스의 SQL 방언에 묶이지 않는다.

    JPA 진영에서 쿼리를 만드는 방법은 JPQL만 있는 것이 아니다. 자바 코드로 쿼리를 조립하는 Criteria API, 같은 일을 더 읽기 쉽게 하는 오픈소스 라이브러리 Querydsl, 데이터베이스 고유 문법을 그대로 쓰는 네이티브 SQL, 그리고 JPA를 거치지 않고 JDBC나 스프링 JdbcTemplate, MyBatis를 직접 쓰는 방법이 있다. Criteria와 Querydsl은 결국 JPQL과 같은 의미의 쿼리를 만들어 내는 도구이므로, JPQL을 이해하면 나머지는 표현 방법의 차이다. 하이버네이트 6.6의 클래스 선언을 javap로 보면 Criteria의 JpaCriteriaQuery 구현체가 바로 SqmSelectStatement, 즉 JPQL 문자열을 파싱해서 만드는 것과 같은 트리 노드다. 문자열로 시작하든 자바 메서드 호출로 시작하든 같은 중간 표현으로 합류한다는 뜻이다.

    JPA를 거치지 않는 JDBC 직접 접근은 영속성 컨텍스트를 모른다. 아직 플러시되지 않은 변경이 있으면 JDBC로 읽은 결과에는 그 변경이 보이지 않으므로, 이런 코드 앞에서는 em.flush()를 직접 불러야 한다. 반대로 JPQL과 네이티브 쿼리는 아래에서 보듯 실행 전에 공급자가 플러시를 책임진다.

    이번 회차의 실험은 스프링 부트 없이 Hibernate ORM 6.6.53.Final, H2 2.3.232, JDK 21에서 persistence.xml로 부트스트랩해 돌렸다. 하이버네이트 6.6이 의존하는 API는 Jakarta Persistence 3.1이다. 명세를 인용할 때는 3.1을 기준으로 하되, 3.2에서 바뀐 부분은 따로 밝힌다. 실험에 쓴 도메인은 다음과 같다. 사원 Employee가 부서 Department를 다대일 지연 로딩으로 참조하고, 집 주소를 임베디드 타입 Address로 갖는다.

    package lab;

@Entity
public class Employee {
    @Id @GeneratedValue Long id;
    String name;
    int age;
    Integer bonus;                                  // 모두 null로 저장했다
    @Enumerated(EnumType.STRING) Grade grade;       // enum Grade { JUNIOR, SENIOR }
    @Embedded Address homeAddress;                  // city, street
    @ManyToOne(fetch = FetchType.LAZY) Department department;
    // 생성자, getter ...
}

@Entity
public class Department {
    @Id @GeneratedValue Long id;
    String name;
    @OneToMany(mappedBy = "department") List employees = new ArrayList<>();
    // ...
}

    데이터는 부서 세 개(dev, ops, hr)와 사원 네 명이다. kim(25세, JUNIOR, dev, seoul), lee(35세, SENIOR, dev, busan), park(45세, SENIOR, ops, seoul), 그리고 부서가 없는 사원 한 명이다. 마지막 사원은 조인 실험을 위해 이름을 일부러 부서 이름과 같은 ops로 지었다(30세, JUNIOR, daegu). hr 부서에는 사원이 없다. 이 데이터 모양이 뒤의 거의 모든 실행 결과를 결정하므로 기억해 두자.

    JPQL 한 줄이 SQL이 되기까지

    가장 단순한 쿼리부터 보자. em.createQuery("select e from Employee e where e.name = :name", Employee.class)에 파라미터를 바인딩하고 getResultList()를 부르면 다음 SQL이 나간다.

    select e1_0.id,e1_0.age,e1_0.bonus,e1_0.department_id,e1_0.grade,e1_0.city,e1_0.street,e1_0.name
from Employee e1_0 where e1_0.name=?

    JPQL에서 select e라고 쓴 한 단어가 SQL에서는 엔티티에 매핑된 모든 컬럼으로 펼쳐졌다. 임베디드 타입 homeAddress는 city, street 두 컬럼으로, 다대일 연관관계 department는 외래 키 컬럼 department_id 하나로 바뀌었다. 별칭 e는 e1_0이 되었는데, 하이버네이트 6가 SQL 별칭을 스스로 다시 짓기 때문이다. 이 변환이 어떤 단계를 거치는지 하이버네이트 6.6의 클래스 이름으로 따라가 보면 다음과 같다.

JPQL은 파싱과 의미 분석을 거쳐 SQM 트리가 되고, 실행 때 방언에 맞는 SQL로 렌더링된다. 결과 행은 영속성 컨텍스트의 동일성 검사를 거쳐 엔티티가 된다.

    이 흐름에서 두 가지를 기억해 두면 뒤의 내용이 쉬워진다. 첫째, JPQL의 오류 중 상당수는 SQL이 나가기 전, createQuery를 호출하는 순간에 드러난다. 엔티티 이름을 소문자로 from employee라고 쓰면 IllegalArgumentException이 나고 원인은 UnknownEntityException: Could not resolve root entity 'employee'다. 속성을 e.Name으로 쓰면 UnknownPathException: Could not resolve attribute 'Name' of 'lab.Employee'가 난다. 데이터베이스에 가 보기도 전에 메타모델과 대조해서 걸러 내는 것이다. 둘째, 해석 캐시의 키는 쿼리 문자열 그 자체다. 하이버네이트 6.6의 QueryInterpretationCacheStandardImpl은 쿼리 문자열과 기대 결과 타입을 키로 하는 크기 제한 맵(BoundedConcurrentHashMap)을 두고, 그 최대 크기는 hibernate.query.plan_cache_max_size로 정하며 기본값 상수 QueryEngine.DEFAULT_QUERY_PLAN_MAX_COUNT는 2048이다. 문자열이 조금이라도 다르면 다른 쿼리로 취급된다는 사실은 파라미터 바인딩에서 다시 중요해진다.

    쿼리 실행 전에 일어나는 플러시

    JPQL은 데이터베이스에 SQL을 보내는 쿼리이므로, 영속성 컨텍스트에만 있고 아직 데이터베이스에 반영되지 않은 변경을 볼 수 없다. 3.1 명세의 3.10.8절(Queries and Flush Mode)은 이 문제를 공급자에게 맡긴다. 트랜잭션 안에서 플러시 모드가 기본값인 AUTO이면, 공급자는 쿼리 결과에 영향을 줄 수 있는 영속성 컨텍스트의 모든 변경이 쿼리 처리에 보이도록 보장해야 한다. 방법은 플러시일 수도 있고 다른 수단일 수도 있다고 적혀 있다. 실험에서 새 사원을 persist한 직후 select count(e) from Employee e를 실행하자 INSERT가 먼저 나가고 COUNT가 5를 돌려주었다.

    insert into Employee (age,bonus,department_id,grade,city,street,name,id) values (?,?,?,?,?,?,?,?)
select count(e1_0.id) from Employee e1_0

    플러시 모드를 COMMIT으로 바꾸면 명세는 그 효과를 정하지 않는다(unspecified). 이 동작의 내부, 즉 쓰기 지연 SQL 저장소와 플러시 시점은 2회에서 다뤘으므로 여기서는 "JPQL 앞에서는 기본적으로 플러시가 일어난다"는 결론만 가져간다.

    기본 문법: SQL을 닮았지만 대상이 다르다

    JPQL의 SELECT 문은 select ... from ... [where ...] [group by ...] [having ...] [order by ...] 순서로 SQL과 같다. UPDATE와 DELETE도 있지만, 여러 행을 한 번에 바꾸는 벌크 연산은 영속성 컨텍스트를 우회한다는 별도의 문제가 있어 10회에서 다룬다. SQL과 다른 점은 FROM 절에 엔티티 이름이 오고, 엔티티마다 식별 변수(identification variable), 흔히 별칭이라고 부르는 이름을 붙여 그 이름으로 속성에 접근한다는 것이다.

    엔티티 이름은 클래스 이름이 아니라 @Entity(name = ...)로 정한 이름이고, 지정하지 않으면 패키지를 뺀 클래스 이름이 기본값이다. 테이블 이름과는 관계가 없다. @Table(name = "emp")로 테이블 이름을 바꿔도 JPQL에서는 계속 Employee라고 쓴다. 다른 패키지에 같은 이름의 엔티티 클래스가 둘 있으면 기본 엔티티 이름이 겹치므로, 명세가 요구하는 대로 영속성 유닛 안에서 엔티티 이름이 유일하도록 하나에 이름을 따로 붙여야 한다.

    대소문자 규칙: 명세와 하이버네이트가 다른 곳

    대소문자는 생각보다 미묘하다. 명세는 SELECT, FROM 같은 예약어가 대소문자를 구분하지 않는다고 정하고, 식별 변수도 대소문자를 구분하지 않는다고 적는다(4.4.2절). 반면 하이버네이트 6.6의 HQL 가이드는 키워드와 함수 이름만 대소문자를 무시하고, 식별 변수와 자바 클래스 이름, 속성 이름은 대소문자를 구분한다고 밝힌다. 실제로 select E.name from Employee e를 실행해 보니 SemanticException: Could not interpret path expression 'E.name'이 났다. 엔티티 이름과 속성 이름은 자바의 클래스와 필드에서 온 것이라 어느 쪽 기준으로도 정확히 써야 하고, 식별 변수는 명세상 무시되더라도 하이버네이트에서는 구분된다. 실무에서는 키워드는 아무렇게나 써도 되지만 나머지는 선언한 그대로 쓴다고 기억하면 된다. SELECT E.name FROM Employee E WHERE E.age > 40처럼 별칭을 선언과 같은 대문자로 쓴 쿼리는 문제없이 실행되었다.

    별칭과 SELECT 절

    Jakarta Persistence 3.1의 문법(BNF)에서 SELECT 문은 select_clause from_clause로 시작하므로 SELECT 절과 식별 변수가 필수다. as 키워드는 생략할 수 있다. 3.2 명세는 SELECT 절을 선택 사항으로 바꾸고, 식별 변수를 생략하면 암묵적 식별 변수 this를 쓴 것으로 해석한다고 정했다. 하이버네이트는 그보다 먼저 이것을 HQL 확장으로 허용했다. 하이버네이트 6.6에서 from Employee where age > 40을 Employee.class와 함께 실행하면 select e from Employee e where e.age > 40과 같은 SQL이 나간다. 이식성을 생각하는 코드라면 별칭과 SELECT 절을 모두 쓰는 편이 안전하다.

    집계 함수와 결과 타입

    집계 함수는 SQL과 같은 COUNT, SUM, AVG, MAX, MIN이다. 눈여겨볼 것은 결과의 자바 타입이다. 명세 4.8.5절은 COUNT가 Long, AVG가 Double, MAX와 MIN은 적용한 필드의 타입, SUM은 정수형 필드에 Long, 부동소수점 필드에 Double을 돌려준다고 정한다. NULL 값은 DISTINCT 여부와 상관없이 집계 전에 제외된다. 실험 결과도 그대로였다.

    select count(e), sum(e.age), avg(e.age), max(e.age), min(e.name) from Employee e

select count(e1_0.id),sum(e1_0.age),avg(cast(e1_0.age as float(53))),max(e1_0.age),min(e1_0.name) from Employee e1_0

[4, 135, 33.75, 45, kim]   타입: Long, Long, Double, Integer, String

    세 가지를 읽어 낼 수 있다. count(e)처럼 엔티티를 세면 SQL에서는 기본 키 컬럼을 센다. int 필드의 합은 Integer가 아니라 Long이어서 결과를 Integer로 캐스팅하면 ClassCastException이 난다. 그리고 AVG는 정수 나눗셈으로 소수점이 잘리지 않도록 하이버네이트가 컬럼을 부동소수점으로 캐스팅해서 보낸다. 135를 4로 나눈 33.75가 그대로 나온 이유다. GROUP BY와 HAVING, ORDER BY도 SQL과 같은 의미다. select e.department.name, count(e) from Employee e group by e.department.name having count(e) >= 1 order by count(e) desc는 [dev, 2], [ops, 1] 두 행을 돌려준다. 부서가 없는 사원 ops는 결과에서 빠졌는데, 그 이유는 뒤의 묵시적 조인에서 설명한다.

    쿼리 API: TypedQuery와 결과 꺼내기

    쿼리 객체는 두 종류다. 결과 타입을 알 수 있을 때는 createQuery(String, Class)로 TypedQuery를 받는다. 결과가 List로 나오므로 캐스팅이 필요 없다. 반환 타입이 명확하지 않을 때, 예를 들어 이름과 나이를 함께 조회할 때는 createQuery(String)로 Query를 받고, 결과는 원소가 Object인 raw 리스트로 나온다. 타입 인자가 실제 SELECT 결과와 맞지 않으면 실행 전에 예외가 난다.

    TypedQuery q1 = em.createQuery(
        "select e from Employee e where e.name = :name", Employee.class);
q1.setParameter("name", "kim");
List list = q1.getResultList();          // 결과 1건

Query q2 = em.createQuery("select e.name, e.age from Employee e");
List rows = q2.getResultList();                      // 원소는 Object[]: [kim, 25] ...

    결과를 꺼내는 메서드는 둘이다. getResultList()는 결과가 없으면 빈 리스트를 돌려준다. null이 아니므로 호출하는 쪽에서 null 검사를 할 필요가 없다. getSingleResult()는 정확히 한 건을 기대한다. 결과가 없으면 NoResultException, 두 건 이상이면 NonUniqueResultException을 던진다. 실험에서는 각각 다음 메시지가 나왔다.

    jakarta.persistence.NoResultException: No result found for query [select e from Employee e where e.name = 'nobody']
jakarta.persistence.NonUniqueResultException: Query did not return a unique result: 4 results were returned

    결과가 없다는 이유로 예외를 던지는 설계는 논란이 있다. 다만 명세는 이 두 예외가 활성 트랜잭션을 롤백 전용으로 표시하지 않는다고 분명히 적어 두었다. PersistenceException은 원칙적으로 트랜잭션을 롤백 대상으로 표시하는데, 명세는 이 둘과 LockTimeoutException, QueryTimeoutException을 그 예외로 둔다. 그래서 잡아서 처리하고 트랜잭션을 계속 진행할 수 있다. 3.2 명세는 결과가 없으면 null을 돌려주는 getSingleResultOrNull()을 추가했다. 3.1을 구현한 하이버네이트 6.6 환경에서는 표준 메서드로 이것을 쓸 수 없으므로, 스프링 데이터 JPA처럼 한 단계 위에서 Optional이나 null로 감싸 주는 계층을 두는 경우가 많다.

    또 하나, getSingleResult()는 SQL에 LIMIT을 붙이지 않는다. 위 두 번째 예외에서 실행된 SQL은 조건 없는 select ... from Employee e1_0이었다. 네 행을 모두 읽어 온 뒤에야 "한 건이 아니다"를 판단한 것이다. 한 건만 필요하다면 setMaxResults(1)을 함께 쓰는 것이 데이터베이스에 정확한 의도를 전달하는 방법이다.

    쿼리 객체의 설정 메서드는 자기 자신을 돌려주므로 메서드 체인으로 이어 쓸 수 있다. em.createQuery(...).setParameter(...).setFirstResult(...).setMaxResults(...).getResultList() 같은 형태가 흔하다.

    파라미터 바인딩은 문법이 아니라 안전과 재사용의 문제

    JPQL의 입력 파라미터는 두 가지다. 이름 기반은 :name처럼 콜론 뒤에 이름을 쓰고 setParameter("name", value)로 값을 넣는다. 위치 기반은 ?1처럼 물음표 뒤에 1부터 시작하는 번호를 쓰고 setParameter(1, value)로 넣는다. 명세는 한 쿼리 안에서 두 방식을 섞지 못하게 한다. 위치 기반은 쿼리를 고칠 때 번호가 밀리기 쉬워서 이름 기반이 보통 더 낫다. 하이버네이트 HQL 가이드는 번호 없이 ?만 쓰는 JDBC 스타일 파라미터를 폐기 예정(deprecated)으로 분류한다.

    바인딩을 써야 하는 첫째 이유는 SQL 인젝션이다. 사용자 입력을 문자열로 이어 붙인 쿼리를 실험해 보았다. 입력값은 x' or '1'='1이다.

    String input = "x' or '1'='1";
// 나쁜 예: 입력을 쿼리 문자열에 이어 붙인다
em.createQuery("select e.name from Employee e where e.name = '" + input + "'").getResultList();
// 좋은 예: 파라미터로 바인딩한다
em.createQuery("select e.name from Employee e where e.name = :n").setParameter("n", input).getResultList();
    select e1_0.name from Employee e1_0 where e1_0.name='x' or '1'='1'    → 전체 사원(이 실험 데이터에서는 4명)
select e1_0.name from Employee e1_0 where e1_0.name=?                  → 0건

    첫 번째 쿼리에서 입력에 들어 있던 작은따옴표가 문자열 리터럴을 닫아 버렸고, 뒤에 붙은 or '1'='1'이 조건식의 일부가 되었다. JPQL 파서 입장에서는 정상적인 쿼리이므로 막을 방법이 없다. 하이버네이트 6.6은 JPQL에 직접 쓴 리터럴을 SQL에도 리터럴로 옮겨 쓰기 때문에 공격이 그대로 데이터베이스까지 간다. 두 번째 쿼리에서 입력은 SQL 문장의 구조와 분리된 값으로만 전달되므로, 그 안에 무엇이 들어 있든 "이름이 정확히 이 문자열인 사원"을 찾는 조건이 될 뿐이다. 하이버네이트 가이드도 사용자 입력을 쿼리 조각과 이어 붙이는 것은 매우 위험하다고 경고한다.

    값이 SQL 구조와 분리되는 방식은 드라이버에 따라 다르다. MySQL Connector/J의 useServerPrepStmts 속성은 기본값이 false다. 이 기본 설정에서 드라이버는 서버 측 준비문(server-side prepared statement)을 쓰지 않고 클라이언트에서 준비문을 흉내 낸다. 값을 이스케이프해서 SQL 텍스트에 끼워 넣은 최종 문장을 보내는 방식이다. 이 경우 인젝션 방어는 드라이버의 이스케이프 처리가 맡는다. 속성을 켜면 SQL 구조를 서버에 먼저 준비시키고 값은 따로 전송한다. 어느 쪽이든 애플리케이션 코드가 할 일은 같다. 값을 문자열 연결로 넣지 않고 setParameter로 넘기는 것이다.

    둘째 이유는 재사용이다. 앞에서 본 해석 캐시의 키는 쿼리 문자열이었다. 이름을 이어 붙인 쿼리는 사용자마다 문자열이 달라서 매번 파싱과 의미 분석을 새로 하고, 캐시에는 한 번 쓰고 버릴 항목이 쌓여 정말 재사용되어야 할 해석을 밀어낸다. 바인딩한 쿼리는 문자열이 하나뿐이라 한 번 해석한 결과를 계속 쓴다. 데이터베이스 쪽에서도 SQL 텍스트가 같아야 문장 단위로 재사용할 여지가 생긴다. 안전과 성능이 같은 방향을 가리키는 드문 경우다.

    명세는 입력 파라미터를 WHERE·HAVING 절과 UPDATE의 SET 절에서만 쓸 수 있다고 정한다. 값이 null인 파라미터와 비교하면 결과는 참도 거짓도 아닌 unknown이 되어 행이 걸러진다. where e.bonus = :b에 null을 넣는다고 is null 검사가 되지 않는다.

    프로젝션: 무엇을 꺼내느냐가 관리 상태를 정한다

    SELECT 절에 무엇을 둘지 정하는 것을 프로젝션(projection)이라고 한다. JPQL의 프로젝션 대상은 세 가지다. 엔티티, 임베디드 타입, 그리고 숫자·문자열 같은 기본 데이터 타입인 스칼라다. 어떤 것을 꺼내느냐에 따라 결과 객체가 영속성 컨텍스트에서 관리되는지가 갈리고, 이것이 이후 동작을 좌우한다.

    엔티티 프로젝션과 결과의 동일성

    select e from Employee e처럼 엔티티를 꺼내면 결과 엔티티는 모두 영속 상태다. 값을 바꾸면 변경 감지로 UPDATE가 나간다. 여기서 쿼리 결과가 영속성 컨텍스트와 어떻게 합쳐지는지 정확히 알아야 한다. JPQL은 1차 캐시를 먼저 보지 않는다. 항상 SQL을 실행한다. 그런 다음 결과 행마다 식별자를 꺼내 영속성 컨텍스트에 같은 식별자의 엔티티가 이미 있는지 확인하고, 있으면 방금 읽은 행의 값을 버리고 기존 인스턴스를 돌려준다. 실험으로 확인해 보자.

    Employee k = em.createQuery("select e from Employee e where e.name = 'kim'", Employee.class)
        .getSingleResult();                                         // age 25로 로딩
em.createNativeQuery("update Employee set age = 99 where name = 'kim'").executeUpdate();

Employee k2 = em.createQuery("select e from Employee e where e.name = 'kim'", Employee.class)
        .getSingleResult();
Object age = em.createQuery("select e.age from Employee e where e.name = 'kim'").getSingleResult();
System.out.println("same=" + (k == k2) + " entityAge=" + k2.age + " scalarAge=" + age);
    same=true entityAge=25 scalarAge=99

    두 번째 엔티티 쿼리는 분명히 SQL을 실행했고 데이터베이스는 99를 돌려주었다. 그런데 결과 엔티티는 첫 번째와 같은 인스턴스였고 나이는 여전히 25였다. 영속성 컨텍스트가 같은 식별자에 대해 한 인스턴스만 유지한다는 동일성 보장(2회)이 쿼리 결과에도 적용되기 때문이다. 이미 관리 중인 객체를 데이터베이스 값으로 덮어쓰면 아직 플러시하지 않은 변경이 조용히 사라질 수 있으므로, 하이버네이트는 기존 객체를 지키는 쪽을 택한다. 반면 스칼라로 꺼낸 e.age는 영속성 컨텍스트를 거치지 않는 그냥 값이라 99가 보였다. 같은 트랜잭션 안에서 같은 행을 보는데 엔티티와 스칼라가 서로 다른 값을 말하는 상황이 생긴 것이다. 네이티브 SQL이나 벌크 연산으로 데이터를 바꾼 뒤에는 em.clear()나 em.refresh()로 영속성 컨텍스트를 맞춰야 하는 이유가 여기 있다.

    JPQL이 DB에서 age 99인 행을 받아 오지만, 영속성 컨텍스트에 같은 id의 엔티티(age 25)가 이미 있어서 새 값을 버리고 기존 인스턴스를 돌려주는 과정. Sequence-style diagram, flat technical style, white background.     프록시도 같은 규칙을 따른다. em.find로 사원 kim을 읽으면 department 필드에는 초기화되지 않은 프록시(Department$HibernateProxy)가 들어간다. 그 상태에서 select d from Department d를 실행하자 결과로 나온 dev 부서는 바로 그 프록시 인스턴스였고(d == proxy가 true), 쿼리가 읽은 값으로 프록시가 초기화되었다(Hibernate.isInitialized가 true). 같은 식별자에 대해 영속성 컨텍스트가 이미 내준 참조를 바꾸지 않는 것이다. 프록시의 구조는 7회에서 다뤘다.

    연관 엔티티 프로젝션은 조인을 만든다

    select e.department from Employee e처럼 사원을 통해 부서를 꺼낼 수도 있다. 이렇게 경로를 따라가면 SQL에는 조인이 생긴다.

    select d1_0.id,d1_0.name from Employee e1_0 join Department d1_0 on d1_0.id=e1_0.department_id

    JPQL에는 JOIN이라는 단어가 없는데 SQL에는 내부 조인이 들어갔다. 이것을 묵시적 조인(implicit join)이라고 한다. select d from Employee e join e.department d처럼 명시적으로 쓴 쿼리와 똑같은 SQL이 나온다. 결과는 같아도 쿼리를 읽는 사람은 앞의 형태에서 조인을 놓치기 쉽다. SQL 튜닝에서 조인은 가장 먼저 확인하는 대상이므로, 조인이 일어나는 곳에서는 명시적으로 JOIN을 쓰는 편이 좋다. 경로 표현식의 종류와 각각이 어떤 조인을 만드는지는 10회에서 자세히 정리한다.

    임베디드 타입 프로젝션

    select e.homeAddress from Employee e는 city, street 두 컬럼을 읽어 Address 객체를 만든다. 그러나 select a from Address a는 실패한다. 하이버네이트 6.6의 메시지는 UnknownEntityException: Could not resolve entity class 'lab.Address'였다. 임베디드 타입은 엔티티가 아니므로 FROM 절에 올 수 없고, 반드시 그것을 소유한 엔티티에서 시작해야 한다. 8회에서 본 대로 임베디드 타입은 식별자가 없는 값이므로, 이렇게 꺼낸 Address는 영속성 컨텍스트가 관리하지 않는다.

    스칼라 프로젝션과 여러 값 조회

    select distinct e.homeAddress.city from Employee e처럼 기본 타입 값을 꺼내면 SQL도 select distinct e1_0.city from Employee e1_0가 되고, 결과는 busan, daegu, seoul 세 문자열이다. DISTINCT는 SQL의 DISTINCT로 그대로 옮겨져 데이터베이스가 중복을 제거한다.

    여러 값을 함께 꺼낼 때는 결과를 받는 방법이 세 가지다. 첫째, Query로 받아 원소를 Object[]로 캐스팅한다. 둘째, createQuery(jpql, Object[].class)로 TypedQuery를 받는다. 실험에서는 두 방식 모두 [kim, 25]처럼 원소 타입이 String, Integer인 배열을 돌려주었다. 원시 타입 int 필드도 결과에서는 래퍼 타입이 된다는 점이 명세에 적혀 있다. 셋째, NEW 생성자 표현식으로 DTO를 바로 만든다.

    public class EmpDto {
    private final String name;
    private final int age;
    public EmpDto(String name, int age) { this.name = name; this.age = age; }
    // ...
}

List dtos = em.createQuery(
        "select new lab.EmpDto(e.name, e.age) from Employee e where e.age > 30", EmpDto.class)
        .getResultList();   // [EmpDto[lee,35], EmpDto[park,45]]

    SQL은 select e1_0.name,e1_0.age from Employee e1_0 where e1_0.age>30이다. 하이버네이트는 행마다 생성자를 호출해 객체를 만든다. 명세(4.8.2절)는 생성자 이름이 패키지를 포함한 전체 이름(fully qualified name)이어야 하고, 대상 클래스는 엔티티일 필요도 매핑될 필요도 없다고 정한다. 만든 DTO는 엔티티가 아니므로 영속성 컨텍스트와 무관하다. 생성자의 인자 순서와 타입이 SELECT 목록과 맞아야 하는데, new lab.EmpDto(e.age, e.name)처럼 순서를 바꾸면 하이버네이트 6.6은 SemanticException: Missing constructor for type 'EmpDto'를 던진다. 이 검사도 SQL을 보내기 전 의미 분석 단계에서 일어난다.

    패키지 이름을 빼면 어떻게 될까. 하이버네이트 6.6에서 select new EmpDto(...)를 결과 타입 없이 createQuery(String)로 만들면 Could not resolve class 'EmpDto' named for instantiation으로 실패했다. 그런데 EmpDto.class를 결과 타입으로 넘기자 같은 쿼리가 성공했다. 넘겨받은 결과 클래스의 단순 이름과 일치하면 그 클래스로 해석한 것이다. 명세가 보장하는 동작이 아니므로 전체 이름을 쓰는 것이 원칙이다. 패키지 이름이 길어 쿼리가 지저분해지는 문제는 Querydsl 같은 도구가 자바 코드로 DTO를 지정하게 해서 해결한다.

    프로젝션의 핵심

    엔티티로 꺼내면 영속성 컨텍스트가 관리하고, 이미 관리 중인 엔티티가 있으면 그 인스턴스가 돌아온다. 임베디드 타입, 스칼라, DTO로 꺼내면 관리 대상이 아닌 값이 돌아온다. 데이터를 수정할 계획이면 엔티티로, 화면에 보여 주기만 할 거라면 필요한 컬럼만 DTO로 꺼내는 것이 기본 판단 기준이다.

    페이징 API: 메서드 두 개가 방언마다 다른 SQL이 된다

    목록 화면은 거의 언제나 페이지 단위로 데이터를 보여 준다. 그런데 페이징 SQL은 데이터베이스마다 문법이 제각각이다. MySQL은 LIMIT, 표준 SQL은 OFFSET ... FETCH, 오래된 오라클은 ROWNUM을 감싼 중첩 쿼리를 쓴다. JPA는 이 차이를 메서드 두 개로 추상화했다. setFirstResult(int startPosition)는 몇 번째 결과부터 가져올지(0부터 센다), setMaxResults(int maxResult)는 최대 몇 건을 가져올지 정한다.

    List page = em.createQuery(
        "select e from Employee e order by e.age desc", Employee.class)
        .setFirstResult(1)
        .setMaxResults(2)
        .getResultList();   // 나이 내림차순 park, lee, ops, kim 중 두 번째부터 2건 → lee, ops

    같은 JPQL을 방언만 바꿔 SQL로 렌더링해 보았다. MySQL, 오라클, SQL Server는 실제 서버 없이 하이버네이트의 메타데이터 접근을 끄고 방언과 버전을 지정해 SQL만 확인했다. 그렇게 얻은 MySQL용 SQL은 따로 MySQL 8.4.13과 8.0.46에 같은 데이터를 넣고 limit 1,2로 값을 채워 실행했는데, 두 버전 모두 lee, ops를 돌려주었다.

    방언 (Hibernate 6.6)렌더링된 페이징 SQL
    H2 2.3order by e1_0.age desc offset ? rows fetch first ? rows only
    MySQLDialect 8.0order by e1_0.age desc limit ?,?
    OracleDialect 19order by e1_0.age desc offset ? rows fetch first ? rows only

    애플리케이션 코드는 그대로인데 SQL이 데이터베이스 문법에 맞게 바뀐다. 이 일을 하는 것이 앞의 흐름에서 본 방언별 SQL AST 번역기다. 오라클 방언에 버전 11을 지정하자 하이버네이트 6.6은 HHH000511 경고로 지원하는 최소 버전이 19라고 알리고 오래된 버전은 커뮤니티 방언 프로젝트를 보라고 안내했다. 렌더링된 SQL은 19와 같은 OFFSET ... FETCH였다. 하이버네이트 버전과 데이터베이스 버전의 조합이 페이징 SQL을 결정한다는 뜻이다. 또 하나 눈여겨볼 것은 시작 위치와 개수가 SQL 리터럴이 아니라 ? 파라미터로 들어간다는 점이다. 1페이지든 100페이지든 SQL 텍스트가 같으므로 문장 재사용에 유리하다.

    정렬 없는 페이징은 페이징이 아니다

    SQL은 ORDER BY가 없으면 결과 순서를 보장하지 않는다. 순서가 정해지지 않은 결과에서 "두 번째부터 두 건"은 의미가 없다. 실행 계획이 바뀌거나 데이터가 바뀌면 다른 행이 나올 수 있고, 페이지를 넘길 때 같은 행이 두 번 나오거나 어떤 행이 한 번도 나오지 않을 수 있다. ORDER BY가 있어도 정렬 키가 유일하지 않으면 같은 문제가 남는다. 위 예에서 나이가 같은 사원이 여럿이면 그들 사이의 순서는 정해지지 않는다. 그래서 페이징 쿼리의 정렬 조건 끝에는 order by e.age desc, e.id desc처럼 유일한 컬럼을 붙여 순서를 완전히 고정한다.

    OFFSET이 커질수록 느려지는 이유

    setFirstResult(10000).setMaxResults(10)은 정렬 순서상 10,001번째부터 10건을 달라는 뜻이다. B+Tree 인덱스는 키 값으로 위치를 찾아 내려가는 구조이지 "n번째 항목"으로 바로 건너뛰는 구조가 아니다. 그래서 정렬 순서대로 인덱스를 읽을 수 있는 경우에도 데이터베이스는 앞의 10,000건을 차례로 지나간 뒤에야 원하는 10건에 도달한다. 정렬에 인덱스를 쓸 수 없으면 조건에 맞는 행 전체를 정렬해야 하므로 더 비싸다. 페이지 번호가 뒤로 갈수록 응답이 느려지는 목록 화면은 대개 이 구조 때문이다.

    대안은 직전 페이지의 마지막 키를 기억해 두고 그 다음부터 읽는 방식이다. 키셋 페이징(keyset pagination) 또는 시크(seek) 방식이라고 부른다. where e.id < :lastId order by e.id desc에 setMaxResults(10)을 주면, 데이터베이스는 인덱스에서 lastId 위치를 키 값으로 바로 찾아간 뒤 10건만 읽는다. 대신 "37페이지로 바로 이동" 같은 임의 접근은 할 수 없다. 화면 요구 사항(페이지 번호 vs 더 보기 버튼)에 따라 둘 중 하나를 고른다.

    두 방식이 인덱스를 얼마나 읽는지는 MySQL의 세션 카운터로 셀 수 있다. id가 기본 키인 사원 테이블에 10만 행(id 1~100000)을 넣고, 같은 10건(id 90000~89991)을 두 방식으로 가져온 뒤 SHOW SESSION STATUS의 Handler_read_* 값을 보았다.

→ Handler_read_last 1, Handler_read_key 1, Handler_read_prev 10009
  EXPLAIN: type=index, key=PRIMARY, Extra=Backward index scan

flush status;
select id, name from Employee where id < 90001 order by id desc limit 10;
→ Handler_read_key 1, Handler_read_prev 9
  EXPLAIN: type=range, key=PRIMARY, Extra=Using where; Backward index scan

    OFFSET 방식은 인덱스의 끝으로 가서 뒤쪽으로 10,009번 더 읽었다. 첫 행을 읽고 나서 10,000건을 지나가며 버리고 10건을 돌려준 것이다. 키셋 방식은 id < 90001 위치를 키로 한 번 찾고 9번 더 읽어 끝났다. 돌려준 행은 같아도 읽은 인덱스 항목 수는 1,000배 넘게 차이가 난다. 이 차이는 OFFSET 값에 비례해서 커진다.

    같은 인덱스 위에서 OFFSET 방식은 앞부분을 모두 지나가고, 키셋 방식은 마지막 키 위치로 바로 내려가 필요한 만큼만 읽는다는 대비. Two-row comparison diagram, flat technical style, white background.     컬렉션을 페치 조인한 쿼리에 페이징을 걸면, 명세는 그 효과를 정의되지 않음(undefined)으로 둔다. 하이버네이트가 이때 어떻게 동작하는지는 페치 조인과 함께 10회에서 본다. 또 페이지 번호를 보여 주려면 전체 건수를 세는 COUNT 쿼리가 따로 필요하다.

    조인: 테이블이 아니라 연관관계를 따라간다

    JPQL의 조인은 SQL의 조인과 의미가 같지만 쓰는 방법이 다르다. SQL에서는 조인할 테이블과 조인 조건을 직접 쓴다. JPQL에서는 join e.department d처럼 엔티티의 연관관계 필드를 경로로 쓰고, 조인 조건은 쓰지 않는다. 조건은 매핑 정보, 즉 @ManyToOne이 가리키는 외래 키에서 나온다.

    select e.name, d.name from Employee e join e.department d where d.name = 'dev'

select e1_0.name,d1_0.name from Employee e1_0 join Department d1_0 on d1_0.id=e1_0.department_id where d1_0.name='dev'
→ [kim, dev], [lee, dev]

    join은 inner join의 줄임이다. 내부 조인은 양쪽에 짝이 있는 행만 남기므로 부서가 없는 사원 ops는 결과에 없다. 짝이 없는 왼쪽 행도 남기고 싶으면 외부 조인을 쓴다.

    select e.name, d.name from Employee e left join e.department d

select e1_0.name,d1_0.name from Employee e1_0 left join Department d1_0 on d1_0.id=e1_0.department_id
→ [kim, dev], [lee, dev], [park, ops], [ops, null]

    세 번째는 세타 조인(theta join)이다. 연관관계가 없는 두 엔티티를 FROM 절에 나란히 쓰고 WHERE 절에서 조건으로 묶는다. select count(e) from Employee e, Department d where e.name = d.name은 SQL에서도 from Employee e1_0,Department d1_0 where e1_0.name=d1_0.name로 나가고, 이름이 부서 이름과 같은 사원은 ops 한 명이므로 결과는 1이다. 논리적으로는 두 테이블의 모든 조합(카티션 곱)을 만든 뒤 조건으로 거르는 것이므로 내부 조인의 의미만 가진다. 짝이 없는 행을 남기는 외부 조인은 이 문법으로 표현할 수 없다.

    ON 절: 조인 대상 거르기

    JPA 2.1부터 조인에 ON 조건을 붙일 수 있다(3.1 문법의 join_condition ::= ON conditional_expression). 내부 조인에서는 ON에 쓰든 WHERE에 쓰든 결과가 같지만, 외부 조인에서는 완전히 다르다. 실험 데이터로 비교해 보자.

    select e.name, d.name from Employee e left join e.department d on d.name = 'ops'

select e1_0.name,d1_0.name from Employee e1_0 left join Department d1_0 on d1_0.id=e1_0.department_id and d1_0.name='ops'
→ [kim, null], [lee, null], [park, ops], [ops, null]
    select e.name, d.name from Employee e left join e.department d where d.name = 'ops'

select e1_0.name,d1_0.name from Employee e1_0 left join Department d1_0 on d1_0.id=e1_0.department_id where d1_0.name='ops'
→ [park, ops]

    JPQL에 쓴 ON 조건은 SQL의 ON 절에 외래 키 조건과 AND로 합쳐졌다. 외부 조인은 왼쪽 행을 하나도 버리지 않고, 오른쪽에 짝이 없거나 ON 조건을 만족하는 짝이 없으면 오른쪽 컬럼을 NULL로 채운다. 그래서 사원 네 명이 모두 남고 ops 부서인 park만 부서 이름이 채워졌다. WHERE 조건은 조인이 끝난 결과에 적용된다. kim과 lee의 부서 이름은 dev라서, ops 사원의 부서 이름은 NULL이라서 조건을 통과하지 못한다. 그 결과 외부 조인이 사실상 내부 조인이 되었다. "모든 사원을 보여 주되 ops 부서 정보만 붙여라"와 "ops 부서 사원만 보여 줘라"는 다른 질문이고, 조건의 위치가 그 차이를 표현한다.

    같은 왼쪽 외부 조인에서 조건을 ON에 두면 왼쪽 행 네 개가 모두 남고 오른쪽만 비워지며, WHERE에 두면 조인 후 걸러져 한 행만 남는다는 비교. Side-by-side comparison of two small result tables, flat technical style, white background. Right table titled "WHERE d.name = 'ops'" shows the same four rows but three of them are struck through with a red line and only "park | ops" remains highlighted. Above both tables a shared caption box "LEFT JOIN e.department d". No other text. ON 조건은 조인할 짝을 고르는 단계에 적용되어 왼쪽 행을 모두 남기고, WHERE 조건은 조인이 끝난 뒤 행 자체를 걸러 낸다.

    연관관계 없는 엔티티의 외부 조인

    ON 절의 두 번째 용도는 연관관계가 매핑되지 않은 엔티티와의 조인이다. 세타 조인은 내부 조인만 되므로, 관계없는 엔티티를 외부 조인하려면 left join Department d on e.name = d.name처럼 경로 대신 엔티티 이름을 쓰고 ON으로 조건을 준다. 하이버네이트 6.6은 이것을 left join Department d1_0 on e1_0.name=d1_0.name로 번역했고, 결과는 [kim, null], [lee, null], [park, null], [ops, ops]였다. 명세 쪽에서 보면 3.1의 조인 문법은 연관관계 경로를 따르는 조인만 정의한다. 엔티티 이름으로 조인하는 range_join은 3.2 문법에 들어왔다. 하이버네이트는 3.2 이전부터 이 문법을 확장으로 지원했으므로 하이버네이트 6.6에서는 쓸 수 있지만, 3.1만 구현한 다른 공급자에서는 동작을 보장받지 못한다.

    묵시적 조인은 내부 조인이다

    앞에서 e.department.name으로 그룹을 묶었을 때 부서 없는 사원이 결과에서 사라졌다. 경로 표현식이 연관 엔티티를 거쳐 가면 하이버네이트는 내부 조인을 만들기 때문이다. WHERE 절에서도 마찬가지다. where e.department.name <> 'xx'는 join Department d1_0 on d1_0.id=e1_0.department_id where d1_0.name<>'xx'가 되어 부서 없는 사원을 조용히 뺀다. 가장 헷갈리는 경우는 NULL을 처리하려고 쓴 함수 안에 경로가 들어갈 때다.

    select coalesce(e.bonus, 0), coalesce(e.department.name, 'none') from Employee e

select coalesce(e1_0.bonus,0),coalesce(d1_0.name,'none') from Employee e1_0 join Department d1_0 on d1_0.id=e1_0.department_id
→ [0, dev], [0, dev], [0, ops]          (3건: 부서 없는 사원이 빠졌다)

    작성자는 부서가 없으면 'none'을 보여 주려고 COALESCE를 썼지만, 경로 때문에 생긴 내부 조인이 그 행을 먼저 없앴다. 'none'이 나올 기회가 없다. 의도대로 하려면 select e.name, coalesce(d.name, 'none') from Employee e left join e.department d처럼 외부 조인을 명시한다. 하이버네이트 6.6은 이것을 left join Department d1_0 on d1_0.id=e1_0.department_id로 번역하므로 실험 데이터에서는 네 행이 나오고, 부서 없는 사원의 두 번째 값은 'none'이 된다.

    예외가 하나 있다. e.department.id처럼 연관 엔티티의 식별자만 쓰면 조인이 생기지 않는다. 실험에서 where e.department.id = :id는 where e1_0.department_id=?로 번역되었다. 외래 키 값이 이미 사원 테이블에 있으므로 부서 테이블을 볼 필요가 없는 것이다. 연관 엔티티와 그 컬렉션을 한 번에 로딩하는 페치 조인(fetch join)은 지연 로딩과 N+1 문제를 다루는 핵심 도구인데, 이것은 10회의 주제다.

    서브 쿼리: 쿼리 안의 쿼리

    서브 쿼리는 다른 쿼리의 조건이나 값으로 쓰이는 쿼리다. JPQL 서브 쿼리의 문법은 SQL과 같고, 바깥 쿼리와 다른 별칭을 새로 선언해서 쓴다. 3.1 명세(4.6.16절)는 서브 쿼리를 WHERE와 HAVING 절에서만 쓸 수 있게 하고, 각주에서 FROM 절 서브 쿼리 지원은 이후 버전에서 검토하겠다고 적는다. 3.2 명세의 각주도 같은 문장을 유지한다.

    서브 쿼리는 바깥 쿼리를 참조하는지에 따라 둘로 나뉜다. 바깥 쿼리를 참조하지 않는 비상관 서브 쿼리(uncorrelated subquery)는 바깥 행과 무관하게 항상 같은 결과다. 바깥 쿼리의 별칭을 참조하는 상관 서브 쿼리(correlated subquery)는 의미상 바깥 행마다 다시 평가된다.

    select e.name from Employee e where e.age > (select avg(e2.age) from Employee e2)

select e1_0.name from Employee e1_0 where e1_0.age>(select avg(cast(e2_0.age as float(53))) from Employee e2_0)
→ lee, park          (평균 33.75)

    서브 쿼리 안에서 e2라는 새 별칭을 쓴 것에 주의하자. 서브 쿼리에서 바깥 별칭 e를 그대로 썼다면 "이 사원 자신의 평균"이 되어 전혀 다른 질문이 된다. 다음은 서브 쿼리와 함께 쓰는 연산자들이다.

    연산자의미실험 JPQL과 결과
    [NOT] EXISTS서브 쿼리 결과가 한 행이라도 있으면 참select d.name from Department d where exists (select 1 from Employee e where e.department = d and e.grade = lab.Grade.SENIOR) → dev, ops
    ALL서브 쿼리의 모든 값에 대해 비교가 참where e.age >= all (select e2.age from Employee e2) → park
    ANY, SOME서브 쿼리의 값 중 하나라도 비교가 참(둘은 같은 의미)where e.department = any (select d from Department d where d.name = 'dev') → kim, lee
    [NOT] IN서브 쿼리 결과 중 하나와 같으면 참where d.id in (select e.department.id from Employee e where e.age > 40) → ops

    EXISTS 예제의 SQL은 where exists(select 1 from Employee e1_0 where e1_0.department_id=d1_0.id and e1_0.grade='SENIOR')였다. JPQL에서 e.department = d라고 엔티티끼리 비교한 것이 SQL에서는 외래 키와 기본 키의 비교로 바뀌었다. 엔티티를 비교하면 식별자를 비교한다는 이 규칙은 10회의 "엔티티 직접 사용"에서 다시 다룬다. ANY 예제도 e1_0.department_id=any(select d2_0.id from Department d2_0 where d2_0.name='dev')로, 서브 쿼리가 엔티티를 고르면 SQL에서는 그 식별자를 고르도록 바뀐다.

    데이터베이스는 서브 쿼리를 그대로 실행하지 않을 수 있다

    상관 서브 쿼리를 "바깥 행마다 다시 실행된다"고만 이해하면 성능을 잘못 예측한다. 그것은 의미를 설명하는 방식이고, 실제 실행 방법은 옵티마이저가 고른다. MySQL 8.0 매뉴얼에 따르면 옵티마이저는 IN, = ANY, EXISTS 서브 쿼리를 세미 조인(semijoin)으로 변환해 조인처럼 실행할 수 있다. EXISTS의 변환은 8.0.16부터, NOT IN과 NOT EXISTS를 안티 조인(antijoin)으로 바꾸는 변환은 8.0.17부터다. 실행 전략으로는 테이블 풀아웃(table pullout), 중복 제거(Duplicate Weedout), FirstMatch, LooseScan, 구체화(Materialization)가 있고 비용 기반으로 고른다. 다만 서브 쿼리가 WHERE나 ON 절의 최상위(AND로 연결된 항)에 있어야 하고, UNION, HAVING, 집계 함수, LIMIT이 없어야 하는 등의 조건이 붙는다. 같은 의미의 JPQL이라도 서브 쿼리 모양에 따라 실행 계획이 달라질 수 있다는 뜻이다. 실제로 무엇이 선택되었는지는 하이버네이트가 만든 SQL을 꺼내 EXPLAIN으로 확인해야 한다.

    NOT IN과 NULL

    서브 쿼리에서 가장 위험한 함정은 NOT IN과 NULL의 조합이다. 부서 dev, hr과 사원 kim(dev), ops(부서 없음)만 있는 데이터에서 "사원이 없는 부서"를 두 가지로 찾아보았다.

    select d.name from Department d where d.id not in (select e.department.id from Employee e)
→ 0건

select d.name from Department d where not exists (select 1 from Employee e where e.department = d)
→ hr

    사람이 기대하는 답은 hr인데 NOT IN은 아무것도 돌려주지 않았다. 서브 쿼리 결과가 (dev의 id, NULL)이기 때문이다. x NOT IN (a, NULL)은 x <> a AND x <> NULL과 같고, NULL과의 비교는 참도 거짓도 아닌 unknown이다. 앞항이 참이어도 전체가 unknown이 되어 WHERE를 통과하지 못한다. NOT EXISTS는 "짝이 되는 행이 존재하는가"만 보므로 NULL에 영향을 받지 않는다. 서브 쿼리가 NULL을 낼 수 있는 컬럼을 고른다면 NOT IN 대신 NOT EXISTS를 쓰거나 서브 쿼리에 is not null 조건을 붙인다. MySQL 매뉴얼이 안티 조인 변환에 대해 비교 대상이 NULL을 허용하면 대부분 적용할 수 없다고 적은 것도 같은 이유다. 같은 데이터와 같은 두 SQL을 MySQL 8.4.13과 8.0.46에서 실행해도 NOT IN은 빈 결과, NOT EXISTS는 hr이었다. 3값 논리는 데이터베이스가 바뀌어도 그대로다.

    하이버네이트의 확장: SELECT 절과 FROM 절의 서브 쿼리

    명세는 WHERE와 HAVING만 허용하지만, 하이버네이트 6.6은 SELECT 절과 FROM 절의 서브 쿼리도 지원한다. SELECT 절 서브 쿼리 select d.name, (select count(e) from Employee e where e.department = d) from Department d는 그대로 SQL의 스칼라 서브 쿼리가 되어 [dev, 2], [ops, 1], [hr, 0]을 돌려주었다. FROM 절 서브 쿼리는 HQL 가이드가 파생 루트(derived root)라고 부르는 기능이다.

    select x.dname, x.cnt
from (select d.name as dname, count(e) as cnt from Department d left join d.employees e group by d.name) x
order by x.cnt desc

select x1_0.dname,x1_0.cnt from (select d1_0.name,count(e1_0.id) from Department d1_0
  left join Employee e1_0 on d1_0.id=e1_0.department_id group by d1_0.name) x1_0(dname,cnt) order by x1_0.cnt desc
→ [dev, 2], [ops, 1], [hr, 0]

    FROM 절 서브 쿼리가 없던 시절에는 이런 질의를 쿼리 두 번으로 나누거나, 조인으로 풀거나, 네이티브 SQL로 내려가야 했다. 하이버네이트 6로 오면서 상당 부분을 JPQL(HQL) 안에서 해결할 수 있게 되었다. 대신 이 쿼리는 다른 JPA 구현체로 옮기면 동작한다는 보장이 없다. 이식성과 표현력 중 무엇이 중요한지 판단해서 쓴다.

    JPQL 타입 표현과 기타식

    JPQL에 직접 쓰는 값, 즉 리터럴의 표기는 자바와 SQL을 섞은 모양이다. 한 번에 확인해 보았다.

    select 'She''s', 10L, 10D, 10F, TRUE, e.name from Employee e where e.grade = lab.Grade.JUNIOR

select 'She''s',10,10,10,true,e1_0.name from Employee e1_0 where e1_0.grade='JUNIOR'
→ [She's, 10, 10.0, 10.0, true, kim]  타입: String, Long, Double, Float, Boolean, String
  [She's, 10, 10.0, 10.0, true, ops]
    • 문자열은 SQL처럼 작은따옴표로 감싸고, 안에 작은따옴표를 넣으려면 두 번 쓴다('She''s').
    • 숫자는 자바 리터럴 규칙을 따라 L, D, F 접미사로 타입을 지정한다. 3.2 명세는 접미사가 없는 정수 리터럴을 자바 int로, 소수점 리터럴을 double로 해석한다고 적는다(3.1에는 자바 규칙에 따른 접미사를 쓸 수 있다는 문장만 있다). 흥미로운 것은 SQL에서는 세 값이 모두 10으로 같다는 점이다. 타입 정보는 SQL로 가지 않고 SQM에 남아 있다가, 결과를 읽을 때 하이버네이트가 Long, Double, Float로 바꾼다.
    • 불리언은 TRUE, FALSE다. 대소문자를 가리지 않는다.
    • enum은 명세상 패키지를 포함한 전체 이름(lab.Grade.JUNIOR)을 써야 한다. @Enumerated(EnumType.STRING)으로 매핑했으므로 SQL에는 문자열 'JUNIOR'로 렌더링되었다. 하이버네이트 6.6은 비교 대상의 타입으로 enum 클래스를 추론할 수 있으면 e.grade = SENIOR처럼 상수 이름만 써도 받아 준다(HQL 가이드 2.1.7절). 실험에서도 where e1_0.grade='SENIOR'로 번역되었다. 표준을 지키면서 긴 이름을 피하려면 :grade 파라미터로 enum 값을 바인딩한다.
    • 엔티티 타입은 상속 매핑에서 쓴다. 단일 테이블 전략(6회)으로 매핑한 Asset과 그 자식 Laptop, Monitor가 있을 때 select a.serial from Asset a where type(a) = Laptop은 where a1_0.DTYPE='Laptop'이 되었다. 엔티티 타입 리터럴은 따옴표 없는 엔티티 이름이고, SQL에서는 구분 컬럼(discriminator) 값 비교가 된다.

    나머지 식은 SQL과 같다. 논리 연산 AND, OR, NOT, 비교 연산 =, >, >=, <, <=, <>, 그리고 BETWEEN, LIKE, IS [NOT] NULL, [NOT] IN, [NOT] EXISTS가 있다. where e.age between 30 and 40 and e.name like 'l%' and e.bonus is null은 lee 한 명을 돌려준다(BETWEEN은 양 끝을 포함한다). JPQL에만 있는 것으로는 컬렉션을 다루는 IS [NOT] EMPTY와 [NOT] MEMBER OF가 있다. 이들은 SQL에 그대로 대응하는 문법이 없어서 하이버네이트가 서브 쿼리로 번역한다. 실험에서 where d.employees is empty는 where not exists(select 1 from Employee e1_0 where d1_0.id=e1_0.department_id)가 되어 사원 없는 부서 hr을 돌려주었고, :e member of d.employees는 같은 모양의 EXISTS에 e1_0.id=? 조건이 붙었다.

    모든 비교에는 SQL의 3값 논리가 그대로 적용된다는 점을 잊지 말자. JPQL이 SQL로 번역되어 데이터베이스에서 평가되므로, NULL과 비교한 결과는 자바처럼 false가 아니라 unknown이다. 문자열 비교에서 대소문자나 후행 공백을 어떻게 다루는지도 데이터베이스와 컬럼의 콜레이션(collation)이 정한다. JPQL은 문법을 추상화할 뿐 데이터베이스의 비교 의미까지 바꾸지는 않는다.

    조건식: CASE, COALESCE, NULLIF

    조건에 따라 다른 값을 내야 할 때는 CASE 식을 쓴다. 두 형태가 있다. 기본 CASE(searched case)는 when마다 조건식을 쓰고, 단순 CASE(simple case)는 하나의 값을 여러 후보와 정확히 비교한다.

    select case when e.age <= 30 then 'young'
            when e.age <= 40 then 'middle'
            else 'senior' end
from Employee e

select case when e1_0.age<=30 then 'young' when e1_0.age<=40 then 'middle' else 'senior' end from Employee e1_0
→ young(kim 25), middle(lee 35), senior(park 45), young(ops 30)
    select case e.grade when lab.Grade.JUNIOR then 'J' else 'S' end from Employee e

select case e1_0.grade when 'JUNIOR' then 'J' else 'S' end from Employee e1_0
→ J, S, S, J

    WHEN 절은 위에서부터 차례로 평가되어 처음 참이 되는 분기의 값이 결과가 된다. ops(30세)가 young이 된 것은 첫 조건 e.age <= 30에서 이미 참이기 때문이다. ELSE가 없고 어떤 조건도 맞지 않으면 결과는 NULL이다. CASE는 SQL CASE로 그대로 옮겨져 데이터베이스에서 계산되므로, 결과를 자바로 가져와 if 문으로 바꾸는 것보다 전송량이 적고 정렬이나 그룹핑의 기준으로도 쓸 수 있다. 명세는 모든 데이터베이스가 CASE 식을 지원하지는 않으므로 이식성 문제가 있을 수 있다는 각주를 달아 두었다.

    CASE의 특수한 형태로 함수 두 개가 있다. COALESCE(a, b, ...)는 인자를 차례로 보며 처음 NULL이 아닌 값을 돌려준다. 모든 사원의 bonus가 NULL인 실험 데이터에서 coalesce(e.bonus, 0)은 모두 0이었다. NULLIF(a, b)는 두 값이 같으면 NULL, 다르면 첫 번째 값을 돌려준다. nullif(e.name, 'ops')는 kim, lee, park, NULL을 돌려주었다. NULLIF는 특정 값을 NULL로 취급하고 싶을 때 쓴다. 대표적인 예가 a / nullif(b, 0)으로, 분모가 0이면 0으로 나누는 오류 대신 NULL이 된다.

    일상에서 가져온 비유COALESCE는 연락처 우선순위표

    휴대폰, 회사 전화, 이메일 순으로 연락처를 적어 두고 비어 있지 않은 첫 번째로 연락하는 것과 같다. 모두 비어 있으면 연락할 방법이 없다(NULL). 비유가 깨지는 지점은 이 우선순위표가 사람마다 따로 적힌 것이 아니라 행마다 데이터베이스가 계산한다는 점이고, 묵시적 내부 조인처럼 행 자체가 먼저 사라지면 우선순위표를 볼 기회도 없다는 점이다.

    JPQL 함수: 표준 함수와 방언의 번역

    3.1 명세가 정의한 표준 함수는 다음과 같다. 문자열 함수는 CONCAT, SUBSTRING, TRIM, LOWER, UPPER, LENGTH, LOCATE, 수학 함수는 ABS, CEILING, EXP, FLOOR, LN, MOD, POWER, ROUND, SIGN, SQRT, 컬렉션 관련 함수는 SIZE와 INDEX다. 날짜·시간은 CURRENT_DATE, CURRENT_TIME, CURRENT_TIMESTAMP와 LOCAL DATE, LOCAL TIME, LOCAL DATETIME, EXTRACT가 있다. 3.2는 여기에 LEFT, RIGHT, REPLACE, CAST, 문자열 연결 연산자 ||, 엔티티의 식별자와 버전을 꺼내는 ID, VERSION 함수를 더했다. 하이버네이트는 3.1 환경인 6.6에서도 ||를 이미 받아 준다.

    select concat(e.name, '-', e.homeAddress.city), e.name || '!', substring(e.name, 2, 2),
       trim(' x '), lower('AB'), upper(e.name), length(e.name), locate('e', e.name)
from Employee e

select (e1_0.name||'-'||e1_0.city),(e1_0.name||'!'),substring(e1_0.name,2,2),trim(BOTH from ' x '),
       lower('AB'),upper(e1_0.name),character_length(e1_0.name),locate('e',e1_0.name) from Employee e1_0
→ kim: [kim-seoul, kim!, im, x, ab, KIM, 3, 0]
  lee: [lee-busan, lee!, ee, x, ab, LEE, 3, 2]

    결과에서 JPQL 함수의 규칙 몇 가지를 읽을 수 있다. SUBSTRING의 시작 위치는 1부터 센다. substring('kim', 2, 2)가 im이다. LOCATE도 1부터 세고 찾지 못하면 0을 돌려준다. 'kim'에는 e가 없어 0, 'lee'에서는 두 번째 글자라 2다. LENGTH는 글자 수다. 그리고 SQL을 보면 JPQL의 함수 이름과 SQL의 함수 이름이 꼭 같지 않다. H2 방언은 CONCAT을 || 연산으로, LENGTH를 character_length로, TRIM을 trim(BOTH from ...)로 렌더링했다. 같은 JPQL을 방언만 바꿔 보면 차이가 더 분명하다.

    JPQLMySQL 8.0Oracle 19SQL Server 16
    mod(e.age, 2)mod(e1_0.age,2)mod(e1_0.age,2)(e1_0.age%2)
    length(e.name)character_length(e1_0.name)length(e1_0.name)len(e1_0.name)
    locate('e', e.name)locate('e',e1_0.name)instr(e1_0.name,'e')charindex('e',e1_0.name)

    MySQL 열의 세 식을 MySQL 8.4.13과 8.0.46에서 그대로 실행하자 lee 행은 1, 3, 2, kim 행은 1, 3, 0으로 위 H2 결과와 같았다. 오라클의 instr는 찾을 문자열과 대상 문자열의 인자 순서가 LOCATE와 반대인데, 방언이 순서까지 바꿔서 렌더링했다. 이것이 JPQL 표준 함수를 쓰는 이유다. 함수 이름과 인자 순서의 차이를 방언이 흡수하므로 데이터베이스를 바꿔도 쿼리를 고칠 필요가 없다. 반대로 말하면, 표준 함수가 데이터베이스에서 어떤 SQL 함수로 실행되는지는 방언이 정하므로, 성능이나 인덱스 사용 여부를 볼 때는 반드시 렌더링된 SQL을 확인해야 한다.

    SIZE와 INDEX

    SIZE는 컬렉션의 크기를 돌려준다. select d.name, size(d.employees) from Department d는 select d1_0.name,(select count(*) from Employee e1_0 where d1_0.id=e1_0.department_id) from Department d1_0로 번역되어 [dev, 2], [ops, 1], [hr, 0]을 돌려주었다. 컬렉션을 메모리에 올려 세는 것이 아니라 상관 서브 쿼리로 데이터베이스에서 센다. 편리하지만 바깥 행마다 COUNT가 붙는 모양이므로 바깥 행이 많을 때는 조인과 GROUP BY로 바꾼 쿼리와 실행 계획을 비교해 볼 만하다. INDEX는 @OrderColumn으로 순서를 저장한 리스트에서 원소의 위치를 돌려준다. 순서 컬럼이 없는 컬렉션에는 쓸 수 없다.

    데이터베이스 함수와 사용자 정의 함수

    표준 함수가 데이터베이스의 모든 함수를 감쌀 수는 없다. 명세(4.6.17.3절)는 그 밖의 함수를 부르는 문법으로 FUNCTION(function_name, args...)을 정의한다. 함수 이름은 문자열이고, 인자는 그 함수에 맞아야 한다. 실험에서 H2 내장 함수 DIFFERENCE를 select function('difference', e.name, 'kin') from Employee e로 부르자 SQL은 select difference(e1_0.name,'kin') from Employee e1_0가 되었다.

    하이버네이트 6.6은 여기서 한 걸음 더 나간다. 등록되지 않은 함수 이름을 difference(e.name, 'kin')처럼 직접 써도 같은 SQL로 그대로 넘겼다. 편리해 보이지만 대가가 있다. 존재하지 않는 함수 no_such_fn(e.name)도 createQuery는 통과했고, 실행 시점에 H2가 Function "NO_SUCH_FN" not found를 내며 SQLGrammarException이 되었다. 엔티티 이름이나 속성 이름의 오타는 SQL을 보내기 전에 잡히지만, 함수 이름의 오타는 데이터베이스까지 가야 드러난다. 하이버네이트가 반환 타입을 모르므로 결과 타입 추론도 약해진다.

    자주 쓰는 데이터베이스 함수라면 등록하는 편이 낫다. 하이버네이트 6.6의 HQL 가이드는 두 가지 방법을 소개한다. FunctionContributor를 구현해 사용자 정의 함수를 등록하는 방법과, 방언을 상속해 initializeFunctionRegistry()를 재정의하는 방법이다. 등록하면 함수 이름과 반환 타입을 하이버네이트가 알게 되어 의미 분석 단계에서 검사하고, 데이터베이스별로 다른 SQL을 렌더링하게 할 수도 있다. 같은 가이드는 function() 문법을 가장 쉬운 방법이지만 최선은 아니라고 평가한다.

    정리: 흔한 오해와 이후 회차와의 연결

    이번 회차의 실험에서 드러난 오해를 모아 보자. 첫째, "JPQL도 find처럼 1차 캐시를 먼저 본다"는 틀렸다. JPQL은 항상 SQL을 실행하고, 결과 행을 영속성 컨텍스트와 대조해 이미 있는 인스턴스를 돌려준다. 그래서 SQL 실행은 줄지 않고, 데이터베이스 값이 바뀌어도 이미 관리 중인 엔티티에는 반영되지 않는다. 둘째, "getSingleResult()는 한 건만 가져온다"도 틀렸다. SQL에 개수 제한이 붙지 않으며 결과가 여러 건이면 예외를 던질 뿐이다. 셋째, "경로 표현식은 알아서 적절히 조인된다"는 반만 맞다. 연관 엔티티를 거치는 묵시적 조인은 내부 조인이라 NULL 관계를 가진 행을 지운다. 넷째, "JPQL로 쓰면 어느 데이터베이스에서나 똑같이 동작한다"는 표준 범위 안에서만 맞다. FROM 절 서브 쿼리, enum 상수 단순 이름, 등록되지 않은 함수 호출 같은 하이버네이트 확장은 다른 공급자에서 보장되지 않는다. 표준 문법이라도 NULL 비교와 콜레이션은 데이터베이스의 의미를 따른다.

    이 회차의 문법은 이후 거의 모든 데이터 접근 기술의 바탕이 된다. 스프링 데이터 JPA의 @Query는 JPQL 문자열을 그대로 받고, 메서드 이름으로 만드는 쿼리도 결국 JPQL 수준의 쿼리를 만든다. Querydsl은 자바 코드로 JPQL을 조립하는 도구다. 다음 10회에서는 이 회차에서 미룬 것들을 다룬다. 경로 표현식의 세 종류와 묵시적 조인 규칙, 지연 로딩의 N+1 문제를 푸는 페치 조인과 그 한계(컬렉션 페치 조인과 페이징), 상속 구조에서의 다형성 쿼리, 엔티티를 직접 비교하면 식별자 비교가 되는 규칙, 이름 붙인 쿼리(Named 쿼리), 영속성 컨텍스트를 우회하는 벌크 연산이다.
    JPQL
    테이블이 아니라 엔티티와 그 속성·연관관계를 대상으로 쓰는 객체지향 쿼리 언어. 공급자가 매핑 정보와 방언을 이용해 데이터베이스별 SQL로 번역한다.
    번역 파이프라인
    하이버네이트 6.6에서 JPQL은 HqlParser와 SemanticQueryBuilder를 거쳐 SQM 트리가 되고, 실행 때 SQL AST를 거쳐 방언별 SQL로 렌더링된다. 해석 결과는 쿼리 문자열과 결과 타입을 키로 캐시된다.
    쿼리 결과와 영속성 컨텍스트
    JPQL은 항상 SQL을 실행하지만, 결과 행의 식별자가 이미 관리 중이면 새로 읽은 값을 버리고 기존 인스턴스(프록시 포함)를 돌려준다. 실행 전에는 AUTO 플러시 모드에 따라 변경이 반영된다.
    TypedQuery와 결과 메서드
    결과 타입을 알면 TypedQuery, 아니면 Query를 쓴다. getResultList는 결과가 없으면 빈 리스트, getSingleResult는 0건이면 NoResultException, 2건 이상이면 NonUniqueResultException이며 둘 다 트랜잭션을 롤백 대상으로 표시하지 않는다.
    파라미터 바인딩
    이름 기반(:name)과 위치 기반(?1)이 있고 섞어 쓸 수 없다. 문자열 연결은 SQL 인젝션을 허용하고 해석 캐시를 오염시키므로 사용자 입력은 반드시 바인딩한다.
    프로젝션
    엔티티 프로젝션 결과는 관리되고, 임베디드·스칼라·DTO 프로젝션 결과는 관리되지 않는다. NEW 생성자 표현식은 명세상 전체 클래스 이름과 순서·타입이 맞는 생성자가 필요하다.
    페이징
    setFirstResult와 setMaxResults가 방언에 따라 LIMIT이나 OFFSET FETCH로 바뀐다. 결과 순서를 고정하는 유일한 정렬이 필요하고, OFFSET이 클수록 앞의 행을 지나가는 비용이 커진다.
    조인과 ON 절
    JPQL 조인은 연관관계 경로를 따른다. 외부 조인에서 ON 조건은 조인 대상만 거르고 WHERE 조건은 결과 행을 거른다. 연관 엔티티를 거치는 묵시적 조인은 내부 조인이다.
    서브 쿼리와 조건식
    명세상 서브 쿼리는 WHERE·HAVING에만 쓰며 EXISTS, ALL, ANY, IN과 함께 쓴다. NOT IN은 서브 쿼리 결과에 NULL이 있으면 아무 행도 돌려주지 않는다. CASE, COALESCE, NULLIF는 데이터베이스에서 계산된다.

    실무에서 JPQL과 관련된 장애는 문법 오류보다 의미 차이에서 더 자주 나온다. 대표적인 것이 묵시적 내부 조인이다. 화면에는 "전체 사원 목록"이라고 되어 있는데 정렬 조건이나 COALESCE 안에 e.department.name을 쓴 탓에 부서가 없는 사원이 목록에서 빠지는 일이 생긴다. 테스트 데이터에 연관관계가 비어 있는 행이 없으면 발견되지도 않는다. 쿼리를 리뷰할 때는 경로 표현식이 연관 엔티티를 지나가는지 보고, 지나간다면 그 관계가 NULL일 수 있는지를 확인하는 습관이 필요하다. NULL일 수 있다면 명시적 LEFT JOIN으로 바꾼다.

    두 번째로 자주 보는 문제는 영속성 컨텍스트와 데이터베이스의 불일치다. 네이티브 SQL, JDBC, 다른 애플리케이션, 벌크 연산이 데이터를 바꾼 뒤 같은 영속성 컨텍스트에서 JPQL로 엔티티를 다시 조회하면 SQL은 실행되지만 결과는 예전 값이다. 로그에 SELECT가 찍혀 있으니 최신 값을 읽었다고 착각하기 쉽다. 이런 흐름에서는 조회 전에 clear()나 refresh()를 두거나, 트랜잭션을 나눠 영속성 컨텍스트의 수명을 짧게 가져간다. 반대로 같은 트랜잭션 안에서 엔티티 상태를 일관되게 유지해 주는 이 성질 덕분에, 애플리케이션 수준에서 반복 가능한 읽기에 가까운 동작을 얻는다는 장점도 있다.

    성능 면에서는 렌더링된 SQL을 확인하는 것이 출발점이다. 페이징이 OFFSET으로 나가는지, 표준 함수가 인덱스를 쓸 수 없는 함수 호출로 감싸졌는지, SIZE가 행마다 서브 쿼리를 만드는지는 JPQL만 보고는 알 수 없다. 깊은 페이지를 자주 읽는 화면이면 키셋 페이징을, 집계 화면이면 DTO 프로젝션으로 필요한 컬럼만 읽는 쿼리를 검토한다. 이식성이 중요한 라이브러리 코드라면 하이버네이트 확장 문법(FROM 절 서브 쿼리, enum 단순 이름, 미등록 함수 호출)을 피하고, 하이버네이트만 쓰는 애플리케이션이라면 이 확장으로 네이티브 SQL을 줄이는 쪽이 유지 보수에 유리할 수 있다. 판단의 기준은 그 쿼리가 얼마나 오래, 어떤 환경에서 쓰일지다.
  • 영속성 컨텍스트가 비어 있는 상태에서 Employee a = em.find(Employee.class, 1L)로 이름이 kim인 사원을 읽고 a.name = "KIM"으로 바꾼 뒤, 플러시 모드 AUTO에서 select e from Employee e where e.name = 'KIM'을 실행한다. 실행되는 SQL의 순서와 결과 리스트의 내용, 결과 원소와 a의 동일성(==)을 예측하라.
  • select e.name, coalesce(e.department.name, '미배정') from Employee e order by e.name이 부서 없는 사원을 보여 주지 않는다는 버그 보고가 들어왔다. 원인을 SQL 수준에서 설명하고 고친 JPQL을 써라.
  • 부서 dev, ops, hr과 사원 kim(dev), lee(dev), park(ops), ops(부서 없음)가 있다. select d.name, e.name from Department d left join d.employees e on e.age > 30과 같은 조건을 WHERE로 옮긴 쿼리의 결과를 각각 표로 그려라. 나이는 kim 25, lee 35, park 45, ops 30이다.
  • 사용자가 입력한 정렬 컬럼 이름을 받아 "select e from Employee e order by e." + sortField로 쿼리를 만드는 코드가 있다. 이 코드의 두 가지 문제(보안과 캐시)를 설명하고, 파라미터 바인딩으로 해결할 수 없는 이유와 대안을 제시하라.
    •

    1번. AUTO 플러시 모드이므로 JPQL 실행 전에 플러시가 일어나 update Employee set ... name=? ... where id=?가 먼저 나가고, 이어서 select ... from Employee e1_0 where e1_0.name='KIM'이 나간다. 데이터베이스에는 이미 KIM이 반영되었으므로 SELECT는 그 행을 찾는다. 결과 행의 식별자 1은 영속성 컨텍스트에 이미 있으므로 하이버네이트는 그 인스턴스를 돌려준다. 결과 리스트에는 원소 하나가 있고 그 원소는 a와 같은 인스턴스다(==가 true). 만약 플러시가 일어나지 않았다면 데이터베이스에는 여전히 kim이 있어 결과가 빈 리스트였을 것이다. 명세가 AUTO에서 쿼리 결과에 영향을 줄 변경을 보이게 하라고 요구하는 이유가 이것이다.

    2번. e.department.name은 연관 엔티티를 지나가는 경로이므로 하이버네이트는 join Department d1_0 on d1_0.id=e1_0.department_id라는 내부 조인을 만든다. 부서가 없는 사원은 외래 키가 NULL이라 조인 짝이 없어 행 자체가 사라지고, COALESCE는 그 행을 볼 기회가 없다. 고친 쿼리는 select e.name, coalesce(d.name, '미배정') from Employee e left join e.department d order by e.name이다. 외부 조인이 사원 행을 모두 남기고, 짝이 없는 행의 d.name이 NULL이 되어 COALESCE가 '미배정'으로 바꾼다.

    3번. ON 버전은 부서 행을 모두 남기고, 나이가 30보다 많은 사원만 짝으로 붙인다. 결과는 (dev, lee), (ops, park), (hr, null)이다. dev의 kim은 25세라 짝이 되지 못했지만 dev 행은 lee와 짝을 이뤄 남는다. 사원 ops는 부서가 없으므로 어떤 부서와도 짝이 되지 않는다. WHERE 버전은 먼저 외부 조인으로 (dev, kim), (dev, lee), (ops, park), (hr, null)을 만든 뒤 e.age > 30을 적용한다. kim은 25라서, hr 행은 e.age가 NULL이라 unknown이 되어 탈락하고 (dev, lee), (ops, park)만 남는다. 차이는 사원이 없는 hr 부서가 남느냐이며, "모든 부서를 보여 주되 조건에 맞는 사원만 붙인다"는 요구에는 ON 버전이 맞다.

    4번. 보안 측면에서 sortField에 name, (select ...) 같은 문자열이 들어오면 쿼리의 구조가 바뀐다. 캐시 측면에서는 입력마다 쿼리 문자열이 달라져 해석 캐시에 새 항목이 생기고, 의도하지 않은 입력이 많으면 쓸모없는 항목이 유효한 항목을 밀어낸다. 그런데 파라미터는 값의 자리에만 올 수 있다. 명세는 입력 파라미터를 WHERE·HAVING 절과 UPDATE의 SET 절에서만 쓸 수 있다고 정하고, 속성 이름이나 정렬 방향 같은 쿼리 구조는 바인딩할 수 없다. 대안은 허용된 정렬 필드 목록(예: name, age)을 코드에 두고 입력을 그 목록과 대조해 선택하는 것, 또는 Criteria API나 Querydsl로 정렬 조건을 코드에서 조립하는 것이다. 어느 쪽이든 쿼리 문자열의 종류가 몇 가지로 제한되므로 캐시 문제도 함께 해결된다.

     같은 영속성 컨텍스트에서 사원 kim(나이 25)을 JPQL로 조회한 뒤, 네이티브 SQL로 나이를 99로 바꾸고 같은 JPQL을 다시 실행했다. 두 번째 결과에 대해 옳은 것은? JPQL은 1차 캐시를 먼저 보므로 SQL이 실행되지 않고 나이 25인 기존 인스턴스가 돌아온다. SQL이 실행되고 새 인스턴스가 만들어져 나이 99가 보인다. SQL이 실행되지만 결과 행의 식별자가 이미 관리 중이므로 기존 인스턴스가 돌아오고 나이는 25로 보인다. SQL이 실행되고 기존 인스턴스의 나이가 99로 갱신되어 돌아온다. JPQL은 식별자 조회가 아니므로 항상 SQL을 실행한다. 하이버네이트는 결과 행의 식별자로 영속성 컨텍스트를 확인하고, 이미 관리 중인 엔티티가 있으면 새로 읽은 값을 버리고 그 인스턴스를 돌려준다. 실험에서 same=true, entityAge=25였다. 1번은 SQL이 실행되지 않는다는 점이 틀렸고, 2번은 동일성 보장을 깨며, 4번은 플러시되지 않은 변경을 덮어쓸 위험 때문에 하이버네이트가 하지 않는 동작이다. select e.name, d.name from Employee e left join e.department d on d.name = 'ops'와, 같은 조건을 WHERE로 옮긴 쿼리의 차이로 옳은 것은? (사원 4명 중 ops 부서 소속은 1명) 두 쿼리는 SQL로 번역되면 같아지므로 결과도 같다. ON 버전은 사원 4명이 모두 나오고 ops 소속만 부서 이름이 채워지며, WHERE 버전은 ops 소속 1명만 나온다. ON 버전은 ops 소속 1명만 나오고, WHERE 버전은 4명이 모두 나온다. JPQL은 외부 조인에 ON 조건을 허용하지 않으므로 ON 버전은 예외가 난다. ON 조건은 SQL의 ON 절에 외래 키 조건과 AND로 합쳐져 조인할 짝만 거른다. 외부 조인은 왼쪽 행을 버리지 않으므로 4행이 남는다. WHERE 조건은 조인이 끝난 결과에 적용되어 d.name이 NULL이거나 dev인 행을 지운다. ON 절은 JPA 2.1부터 허용되었다. 부서가 없는 사원이 있을 때 select d.name from Department d where d.id not in (select e.department.id from Employee e)가 빈 결과를 돌려주는 이유는? JPQL은 서브 쿼리에서 연관 엔티티의 식별자를 꺼낼 수 없어서 조건이 무시된다. 하이버네이트가 NOT IN을 IN으로 잘못 번역한다. 서브 쿼리에 상관관계가 없어 데이터베이스가 결과를 캐시하기 때문이다. 서브 쿼리 결과에 NULL이 섞여 있어 모든 비교가 unknown이 되기 때문이다. x NOT IN (a, NULL)은 x <> a AND x <> NULL이고, NULL과의 비교는 unknown이라 전체가 참이 될 수 없다. 실험에서 SQL은 d1_0.id not in (select e1_0.department_id from Employee e1_0)로 정확히 번역되었고 결과는 0건이었다. NOT EXISTS로 바꾸면 사원 없는 부서 hr이 나온다. 같은 JPQL에 setFirstResult(20).setMaxResults(10)을 걸었을 때 하이버네이트 6.6이 만든 SQL에 대한 설명으로 옳은 것은? MySQL 방언에서는 limit ?,?, 오라클 19와 SQL Server 방언에서는 offset ? rows fetch first ? rows only로 렌더링되고, 숫자는 파라미터로 바인딩된다. 모든 방언에서 결과를 전부 읽은 뒤 자바 메모리에서 20건을 건너뛴다. 숫자가 SQL 리터럴로 들어가므로 페이지마다 다른 SQL 문장이 만들어진다. ORDER BY가 없어도 기본 키 순서가 보장되므로 페이지가 겹치지 않는다. 페이징 SQL은 방언별 SQL AST 번역기가 렌더링하며 실험에서 표의 형태가 나왔다. 시작 위치와 개수는 ?로 바인딩되므로 SQL 텍스트는 페이지와 무관하게 같다. 메모리 페이징은 컬렉션 페치 조인 같은 특수한 경우의 이야기이고, ORDER BY 없는 결과의 순서는 SQL이 보장하지 않는다.
    JPQL (Jakarta Persistence Query Language)
    엔티티 객체와 그 속성, 연관관계를 대상으로 하는 쿼리 언어. 명세의 4장이 문법과 의미를 정의하며 공급자가 SQL로 번역한다.
    SQM (Semantic Query Model)
    하이버네이트 6가 HQL·JPQL 문자열과 Criteria 쿼리를 공통으로 표현하는 의미 트리. 메타모델 검사를 마친 상태이며 실행 때 SQL AST로 바뀐다.
    방언 (Dialect)
    데이터베이스별 SQL 문법 차이를 담은 하이버네이트 구성 요소. 페이징 구문, 함수 이름과 인자 순서 등을 데이터베이스에 맞게 렌더링한다.
    식별 변수 (identification variable)
    FROM 절에서 엔티티나 조인 대상에 붙이는 이름. 명세는 대소문자를 구분하지 않는다고 하지만 하이버네이트 6.6은 구분한다.
    프로젝션 (projection)
    SELECT 절에서 조회할 대상을 고르는 것. 엔티티, 임베디드 타입, 스칼라 값, 생성자 표현식(DTO)이 대상이 될 수 있다.
    묵시적 조인 (implicit join)
    JOIN 키워드 없이 경로 표현식이 연관 엔티티를 지나갈 때 생기는 조인. 하이버네이트는 내부 조인으로 번역한다.
    상관 서브 쿼리 (correlated subquery)
    바깥 쿼리의 별칭을 참조하는 서브 쿼리. 의미상 바깥 행마다 평가되지만 옵티마이저가 세미 조인 등으로 변환해 실행할 수 있다.
    키셋 페이징 (keyset pagination)
    직전 페이지의 마지막 정렬 키를 조건으로 다음 행을 읽는 페이징 방식. OFFSET처럼 앞 행을 지나갈 필요가 없지만 임의 페이지로 바로 이동할 수 없다.
