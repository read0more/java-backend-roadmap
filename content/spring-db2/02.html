    이 회차의 질문: 두 번 돌리면 깨지는 테스트

    앞 회차에서 JdbcTemplate으로 저장·조회 코드를 만들었다면, 다음으로 할 일은 그 코드가 맞게 동작하는지 테스트로 확인하는 것이다. 그런데 데이터베이스에 닿는 테스트는 순수한 자바 객체를 다루는 테스트와 성격이 다르다. 자바 객체는 테스트 메서드가 끝나면 참조가 사라지고 가비지 컬렉터가 거둬 간다. 다음 테스트는 깨끗한 힙에서 다시 시작한다. 반면 데이터베이스에 INSERT한 행은 커밋되는 순간 JVM 바깥의 디스크에 남는다. 테스트 프로세스가 끝나도, 다음 날 다시 실행해도 그대로 있다.

    이 차이가 만드는 증상은 아주 구체적이다. 도서 두 권을 저장하고 전체 조회 결과가 두 건인지 확인하는 테스트를 생각해 보자. 처음 실행하면 통과한다. 그런데 같은 테스트를 한 번 더 실행하면 조회 결과가 네 건이 되어 실패한다. 첫 실행이 남긴 두 건이 그대로 있기 때문이다. 코드는 한 글자도 바뀌지 않았는데 결과가 달라졌다. 테스트가 검증하려는 대상(코드) 말고 다른 것(데이터베이스의 현재 상태)에 결과가 좌우되고 있다는 뜻이다.

    좋은 테스트의 조건으로 흔히 두 가지를 꼽는다. 하나는 반복 가능성(repeatability)이다. 같은 코드에 대해 몇 번을 돌려도 같은 결과가 나와야 한다. 다른 하나는 격리(isolation), 또는 독립성이다. 한 테스트의 결과가 다른 테스트가 실행됐는지, 어떤 순서로 실행됐는지에 영향을 받지 않아야 한다. 데이터베이스는 두 조건을 모두 위협한다. 데이터베이스는 테스트 바깥에 있는 공유된 가변 상태(shared mutable state)이기 때문이다. 자바 중급편에서 여러 스레드가 같은 필드를 고칠 때 생기던 문제를 떠올리면, 여러 테스트가 같은 테이블을 고칠 때 생기는 문제도 구조가 같다.

    이 회차는 이 공유 상태를 다루는 방법을 차례로 쌓아 올린다. 먼저 테스트가 어떻게 데이터베이스에 연결되는지(스프링 부트 테스트가 무엇을 띄우는지)를 본다. 다음으로 개발용 DB와 테스트용 DB를 분리하고, 그래도 남는 문제를 트랜잭션 롤백으로 푼다. 롤백을 손으로 짜 보고 나서 스프링의 @Transactional이 테스트에서 어떻게 같은 일을 대신하는지 내부를 열어 본다. 마지막으로 데이터베이스 자체를 테스트 프로세스 안에 띄우는 임베디드 모드와, 스프링 부트가 이것을 자동으로 구성하는 조건을 소스 수준에서 확인한다.

    이 회차의 실행 결과는 모두 직접 돌려서 얻은 것이다. 환경은 Java 21(Temurin 21.0.13), H2 2.4.240, 그리고 이 컴퓨터에 받아 둔 Spring Framework 7.0.10이다. 이 강좌의 기준 버전은 Spring Framework 6.x / Spring Boot 3.x이므로, 실험에서 확인한 규칙은 Spring Framework 6.2 참조 문서와 Spring Boot 3.5.0 소스로 다시 맞춰 보았다. 두 버전에서 차이가 나는 부분은 그 자리에서 밝힌다.

    테스트가 데이터베이스에 닿기까지: @SpringBootTest가 띄우는 것

    스프링 부트 프로젝트에서 데이터베이스를 쓰는 테스트는 보통 @SpringBootTest로 시작한다. 이 애너테이션이 하는 일을 정확히 알아야 테스트가 어느 데이터베이스에 붙는지 설명할 수 있다. 스프링 부트 문서에 따르면 @SpringBootTest는 테스트 클래스가 있는 패키지에서 시작해 위쪽 패키지로 올라가며 @SpringBootApplication이나 @SpringBootConfiguration이 붙은 클래스를 찾는다. 찾은 클래스가 곧 애플리케이션의 메인 설정이므로, 테스트는 애플리케이션을 실제로 실행할 때와 거의 같은 스프링 컨테이너를 만든다. 컴포넌트 스캔, 자동 구성, 그리고 application.properties의 설정이 모두 그대로 적용된다.

    그 결과 테스트 안에서 주입받는 DataSource는 애플리케이션이 쓰는 것과 같은 설정으로 만들어진다. 개발 중에 로컬 H2 서버나 MySQL에 붙도록 spring.datasource.url을 적어 두었다면, 테스트도 바로 그 데이터베이스에 붙는다. 테스트가 저장한 행은 개발하면서 화면으로 넣어 둔 데이터와 같은 테이블에 섞인다. 앞 절의 "두 번째 실행에서 깨지는 테스트"는 이렇게 만들어진다. 개발용 데이터가 있으면 첫 실행부터 깨질 수도 있다.

    @SpringBootTest
class BookRepositoryTest {

    @Autowired
    BookRepository bookRepository;

    @Test
    void findAll() {
        bookRepository.save(new Book("네트워크 입문", 20000));
        bookRepository.save(new Book("운영체제 입문", 25000));

        List result = bookRepository.findAll();

        assertThat(result).hasSize(2);   // 테이블에 이미 행이 있으면 실패한다
    }
}

    테스트 쪽에서 JUnit과 스프링이 만나는 지점도 짚어 두자. @SpringBootTest에는 JUnit Jupiter 확장인 SpringExtension이 메타 애너테이션으로 붙어 있다. JUnit은 테스트 생명주기의 정해진 지점마다 확장의 콜백을 부르고, SpringExtension은 그 콜백을 받아 스프링 테스트 프레임워크의 중심 객체인 TestContextManager에 넘긴다. Spring Framework 7.0.10 소스를 보면 beforeEach 콜백은 TestContextManager.beforeTestMethod로, beforeTestExecution은 beforeTestExecution으로, afterEach는 afterTestMethod로 그대로 위임된다. TestContextManager는 다시 등록된 TestExecutionListener들을 순서대로 부른다. 의존관계 주입, 컨텍스트 정리, 트랜잭션, SQL 스크립트 실행이 모두 이 리스너들의 일이다. 뒤에서 테스트용 트랜잭션을 열어 볼 때 이 구조가 그대로 다시 나온다.

    두 번째 단계의 컨텍스트 캐시(context cache)는 데이터베이스 테스트를 이해하는 데 중요하다. Spring Framework 문서에 따르면 테스트 프레임워크는 애플리케이션 컨텍스트를 static 변수에 보관하고, 설정 클래스·활성 프로필·테스트용 프로퍼티·컨텍스트 커스터마이저 같은 구성 요소의 조합을 키로 쓴다. 키가 같은 테스트 클래스들은 컨텍스트 하나를 함께 쓴다. 캐시의 기본 최대 크기는 32이고, 가득 차면 가장 오래 쓰이지 않은 컨텍스트부터 닫는다(LRU). 크기는 JVM 시스템 프로퍼티 spring.test.context.cache.maxSize로 바꿀 수 있다. 컨텍스트를 공유한다는 것은 그 안의 DataSource, 즉 커넥션 풀과 그 너머의 데이터베이스도 공유한다는 뜻이다. 테스트 클래스 A가 커밋한 데이터를 같은 컨텍스트를 쓰는 테스트 클래스 B가 그대로 본다.

    컨텍스트 캐시는 같은 JVM 프로세스 안에서만 의미가 있다. 문서는 빌드 도구가 테스트 클래스마다 새 프로세스를 띄우도록 설정하면 캐시가 사실상 꺼진다고 설명한다. 반대로 말하면, 보통의 설정에서는 테스트 스위트 전체가 한 프로세스에서 컨텍스트와 데이터베이스를 나눠 쓴다.

    순서 문제도 있다. JUnit 사용자 가이드는 테스트 클래스와 메서드의 기본 실행 순서를 "결정적이지만 의도적으로 드러나지 않는(deterministic but intentionally nonobvious)" 알고리즘으로 정한다고 밝힌다. 소스에 적은 순서도, 이름순도 아니라는 뜻이다. 한 테스트가 남긴 데이터 덕분에 다른 테스트가 통과하고 있다면, 순서가 바뀌는 순간(테스트를 하나 추가하거나, 하나만 골라 돌리거나) 결과가 달라진다. 순서를 @TestMethodOrder로 고정하는 것은 증상을 덮을 뿐이다. 근본적인 해결은 각 테스트가 시작할 때 데이터베이스가 항상 같은 상태라는 것을 보장하는 데 있다.

    데이터베이스 분리: 개발용과 테스트용을 나눈다

    첫 번째 조치는 가장 단순하다. 테스트가 개발용 데이터베이스를 건드리지 않게 테스트 전용 데이터베이스를 따로 둔다. 개발자가 화면을 눌러 보며 넣은 데이터와 테스트가 넣고 지우는 데이터가 섞이지 않게 하는 것이다. 스프링 부트에서는 설정 파일 하나로 이것을 할 수 있다.

    # src/main/resources/application.properties  (애플리케이션 실행용)
spring.datasource.url=jdbc:h2:tcp://localhost/~/bookshop
spring.datasource.username=sa

# src/test/resources/application.properties  (테스트 실행용)
spring.datasource.url=jdbc:h2:tcp://localhost/~/bookshop-test
spring.datasource.username=sa

    이 설정이 동작하는 원리는 클래스패스에 있다. 스프링 부트는 기본 설정 위치인 classpath:/에서 application.properties를 찾을 때, 패턴이 아닌 단일 위치이므로 클래스 로더에게 그 이름의 리소스를 하나만 요청한다(Spring Boot 4.1.2 소스의 StandardConfigDataLocationResolver에서 확인했다). 클래스 로더는 클래스패스 항목을 앞에서부터 뒤져 처음 찾은 것을 돌려준다. Gradle Java 플러그인 문서에 따르면 소스 세트의 실행 클래스패스 기본값은 그 소스 세트 자신의 출력($output, 테스트라면 컴파일된 테스트 클래스와 src/test/resources)이 먼저 오고 그 뒤에 testRuntimeClasspath 같은 구성이 붙는다. 테스트 소스 세트에는 플러그인이 메인 소스 세트의 출력을 끼워 넣는데, Gradle 소스의 JavaPlugin을 보면 순서가 테스트 출력, 메인 출력, testRuntimeClasspath다. 메인 코드의 출력은 테스트 출력보다 뒤에 있다. 그래서 테스트를 실행하면 src/test/resources/application.properties가 먼저 발견되고, 메인 쪽 파일은 읽히지 않는다.

    여기서 흔한 오해가 하나 생긴다. 테스트 쪽 파일이 메인 쪽 파일을 "덮어쓴다"고 생각하면, 테스트 파일에 적지 않은 설정은 메인 파일에서 가져올 것이라고 기대하게 된다. 실제로는 그렇지 않다. 같은 이름, 같은 위치의 파일이 두 개 있으면 하나만 읽히므로 병합되지 않는다. 메인 파일에 적어 둔 로깅 레벨이나 JPA 설정이 테스트에서 사라졌다면 이 때문이다. 테스트 파일에는 테스트에 필요한 설정을 빠짐없이 적어야 한다. 일부만 바꾸고 싶다면 프로필(@ActiveProfiles와 application-test.properties)이나 @TestPropertySource처럼 기존 설정 위에 값을 얹는 방식을 쓴다. 다만 이 둘은 컨텍스트 캐시 키에 들어가므로, 테스트 클래스마다 다르게 쓰면 컨텍스트가 그만큼 늘어난다.

    테스트 DB를 분리하면 개발 데이터는 보호된다. 그러나 이 회차 첫머리의 문제, 즉 두 번째 실행에서 깨지는 테스트는 그대로다. 테스트 DB 안에서도 첫 실행이 남긴 데이터가 두 번째 실행에 남아 있기 때문이다. 분리는 누구와 상태를 공유하는지를 줄였을 뿐, 상태가 테스트 사이에 남는 문제는 풀지 못했다. 다음 단계는 각 테스트가 끝난 뒤 자기가 만든 데이터를 없애는 것이다.

    지우는 방법들과 그 약점

    가장 먼저 떠오르는 방법은 테스트가 끝날 때 DELETE FROM book을 실행하는 것이다. @AfterEach 메서드에 넣으면 테스트마다 실행된다. 이 방법은 동작하지만 약점이 세 가지 있다. 첫째, 테스트 도중 예외가 나거나 디버깅하다 프로세스를 강제로 끝내면 정리 코드가 실행되지 않아 데이터가 남는다. 다음 실행은 그 찌꺼기 위에서 시작한다. 둘째, 테이블이 늘어날수록 지울 목록을 관리해야 하고, 외래 키가 있으면 지우는 순서까지 맞춰야 한다. 셋째, 테스트가 지워야 할 데이터와 원래 있던 기준 데이터(코드 테이블처럼 미리 넣어 둔 데이터)를 구분하기 어렵다.

    DELETE 대신 TRUNCATE TABLE을 쓰면 빠르지만 다른 문제가 생긴다. MySQL 문서는 TRUNCATE TABLE을 CREATE TABLE, ALTER TABLE, DROP TABLE과 함께 암묵적 커밋(implicit commit)을 일으키는 문장으로 분류한다. 이 문장들은 실행되기 전에 현재 세션에서 진행 중인 트랜잭션을 마치 COMMIT을 한 것처럼 끝내 버린다. 다음 절에서 볼 롤백 방식과 섞어 쓰면, 롤백하려던 트랜잭션이 정리 문장 때문에 이미 커밋되어 있는 일이 생긴다. 정리를 앞에 두는 방식(테스트 시작 전에 지우기)은 찌꺼기 문제를 줄이지만, 마지막 테스트가 남긴 데이터가 다음 실행 전까지 남고, 지울 목록 관리 문제는 그대로다.

    이 약점들을 한꺼번에 피하는 방법이 있다. 데이터베이스가 원래 가지고 있는 "없던 일로 되돌리기" 기능, 즉 트랜잭션 롤백을 쓰는 것이다.

    데이터 롤백: 테스트를 트랜잭션으로 감싸기

    스프링 DB 1편에서 본 것처럼 트랜잭션은 커밋하기 전까지 그 안의 변경을 확정하지 않는다. 테스트 메서드를 시작할 때 트랜잭션을 열고, 테스트가 끝나면 커밋 대신 롤백하면 테스트가 무엇을 넣고 고쳤든 데이터베이스는 테스트 전 상태로 돌아간다. 정리할 테이블 목록을 관리할 필요가 없고, 테스트가 중간에 실패해도 롤백은 똑같이 일어난다. 테스트 프로세스가 아예 죽어 버린 경우도 마찬가지다. MySQL 문서는 자동 커밋을 끈 세션이 마지막 트랜잭션을 커밋하지 않고 끝나면 MySQL이 그 트랜잭션을 롤백한다고 설명한다. 커밋되지 않은 변경은 찌꺼기로 남지 않는다.

    스프링의 트랜잭션 추상화를 쓰면 이것을 테스트 코드에 직접 짤 수 있다. PlatformTransactionManager를 주입받아 @BeforeEach에서 트랜잭션을 시작하고 @AfterEach에서 롤백한다.

    @SpringBootTest
class BookRepositoryTest {

    @Autowired
    BookRepository bookRepository;

    @Autowired
    PlatformTransactionManager transactionManager;

    TransactionStatus status;

    @BeforeEach
    void beginTransaction() {
        status = transactionManager.getTransaction(new DefaultTransactionDefinition());
    }

    @AfterEach
    void rollbackTransaction() {
        transactionManager.rollback(status);
    }

    @Test
    void findAll() {
        bookRepository.save(new Book("네트워크 입문", 20000));
        bookRepository.save(new Book("운영체제 입문", 25000));

        assertThat(bookRepository.findAll()).hasSize(2);
    }
}

    이 코드를 보고 이상하다고 느껴야 정상이다. 트랜잭션을 시작한 것은 테스트 클래스이고, INSERT를 실행한 것은 리포지토리다. 리포지토리 코드 어디에도 "테스트가 연 트랜잭션에 참여하라"는 말이 없다. 그런데도 리포지토리가 실행한 SQL이 테스트의 트랜잭션 안에서 실행되고 함께 롤백된다. 어떻게 그럴 수 있을까.

    한 층 아래: 스레드에 묶인 커넥션

    답은 스프링 DB 1편에서 다룬 트랜잭션 동기화(transaction synchronization)에 있다. 짧게 상기하자. 트랜잭션은 결국 커넥션 하나, 즉 데이터베이스 세션 하나에 붙은 상태다. 같은 트랜잭션에 참여하려면 같은 커넥션을 써야 한다. DataSourceTransactionManager는 getTransaction이 불리면 커넥션을 하나 얻어 자동 커밋을 끄고, 그 커넥션을 TransactionSynchronizationManager에 등록한다. 이 등록소는 내부적으로 ThreadLocal이므로, 커넥션은 지금 실행 중인 스레드에 묶인다. JdbcTemplate은 커넥션이 필요할 때 DataSource에서 바로 꺼내지 않고 DataSourceUtils.getConnection을 거치는데, 이 메서드가 먼저 현재 스레드에 묶인 커넥션이 있는지 확인하고 있으면 그것을 돌려준다.

    JUnit은 한 테스트 메서드의 @BeforeEach, 테스트 본문, @AfterEach를 같은 스레드에서 차례로 실행한다. 그래서 @BeforeEach가 스레드에 묶어 둔 커넥션을 테스트 본문이 부른 리포지토리의 JdbcTemplate이 찾아 쓰고, @AfterEach의 rollback은 그 커넥션에 대해 롤백을 보낸 뒤 스레드에서 떼어 낸다. 리포지토리 코드가 트랜잭션을 모르는 채로 참여할 수 있는 것은, 트랜잭션 정보가 메서드 인자가 아니라 스레드라는 실행 맥락에 실려 다니기 때문이다.

    테스트 스레드 (main)                                  ThreadLocal 등록소
──────────────────────────────────────────────────    ─────────────────────
@BeforeEach  transactionManager.getTransaction()  ──▶  DataSource → conn#7
               └ 풀에서 conn#7, setAutoCommit(false)        (이 스레드 전용)

테스트 본문  bookRepository.save(...)
               └ JdbcTemplate → DataSourceUtils.getConnection()
                    └ 등록소에 conn#7 있음 → conn#7로 INSERT   (커밋 안 됨)
             bookRepository.findAll()
               └ 같은 conn#7로 SELECT → 자기 INSERT가 보인다

@AfterEach   transactionManager.rollback(status)
               └ conn#7.rollback() → 등록 해제 → 풀에 반납
                                                 ▼
                                      데이터베이스: 테스트 전 상태
    테스트 메서드의 @BeforeEach, 본문, @AfterEach가 같은 스레드에서 같은 커넥션을 공유하고, 그 커넥션의 롤백으로 데이터베이스가 원래 상태로 돌아가는 구조를 보여 준다. 왼쪽에 세로로 긴 레인 하나를 그리고 위에 "테스트 스레드"라고 라벨을 붙인다. 레인 안에 위에서 아래로 세 개의 상자 "@BeforeEach", "테스트 본문", "@AfterEach"를 놓는다. 가운데에 금고 모양 상자 "ThreadLocal 등록소"를 두고 그 안에 원통 아이콘 "커넥션 #7"을 넣는다. "@BeforeEach"에서 등록소로 화살표를 긋고 "트랜잭션 시작"이라 적는다. "테스트 본문" 상자 안에 작은 상자 "리포지토리 → JdbcTemplate"를 넣고, 거기서 등록소의 "커넥션 #7"로 점선 화살표 "같은 커넥션 사용"을 긋는다. 오른쪽 끝에 데이터베이스 원통 "테스트 DB"를 두고 "커넥션 #7"에서 연결선을 긋는다. "@AfterEach"에서 데이터베이스로 굵은 빨간 화살표 "롤백"을 긋고, 데이터베이스 옆에 "테스트 전 상태"라는 말풍선을 단다. 배경은 흰색, 선은 얇고 깔끔한 기술 도식 스타일. 트랜잭션 정보는 스레드에 실려 다닌다. 같은 스레드에서 실행되는 리포지토리는 테스트가 연 트랜잭션에 자동으로 참여한다.

    데이터베이스는 롤백 때 무엇을 하는가

    롤백을 데이터베이스 쪽에서 보면, 커밋되지 않은 변경을 되돌리는 작업이다. MySQL InnoDB 기준으로 말하면, InnoDB는 행을 바꿀 때 바꾸기 전의 정보를 롤백 세그먼트의 언두 로그(undo log)에 남긴다. MySQL 문서는 InnoDB가 이 정보를 써서 트랜잭션 롤백에 필요한 되돌리기 작업을 하고, 같은 정보로 일관된 읽기를 위한 이전 버전의 행을 만든다고 설명한다. 언두 로그는 삽입용과 갱신용으로 나뉘는데, 삽입 언두 로그는 롤백에만 필요하므로 커밋되면 바로 버릴 수 있다. 테스트가 주로 하는 일이 행 삽입이라는 점을 생각하면, 테스트 롤백은 데이터베이스가 평소에 준비해 두는 정보를 그대로 쓰는 작업이다.

    격리 수준도 이 방식을 돕는다. 커밋되지 않은 변경은 READ UNCOMMITTED가 아닌 한 다른 세션에 보이지 않는다. 테스트가 트랜잭션 안에서 넣은 행은 테스트 자신의 커넥션에서만 보이고, 같은 데이터베이스를 쓰는 다른 커넥션에는 보이지 않다가 롤백과 함께 사라진다. 그래서 테스트 본문의 findAll()은 자기가 넣은 두 건을 보지만, 테스트가 끝난 뒤에는 누구도 그 두 건을 본 적이 없는 상태가 된다.

    롤백으로 되돌릴 수 없는 것

    롤백은 강력하지만 전부를 되돌리지는 않는다. 이 경계를 모르면 "롤백하는데도 테스트가 서로 영향을 준다"는 이상한 현상을 만나게 된다. 직접 확인해 보자. 아래는 순수 JDBC로 H2 메모리 데이터베이스에 테이블을 만들고, 트랜잭션 안에서 행을 넣었다가 롤백한 뒤 다시 넣어 보는 코드다.

    String url = "jdbc:h2:mem:b;DB_CLOSE_DELAY=-1";
try (Connection c = DriverManager.getConnection(url, "sa", "")) {
    c.createStatement().execute(
        "create table book(id bigint generated by default as identity primary key, title varchar(20))");
}
try (Connection c = DriverManager.getConnection(url, "sa", "")) {
    c.setAutoCommit(false);
    c.createStatement().execute("insert into book(title) values ('A')");
    // select max(id) → 1
    c.rollback();
    // select count(*) → 0

    c.createStatement().execute("insert into book(title) values ('B')");
    c.commit();
    // select id from book → ?

    c.createStatement().execute("insert into book(title) values ('C')");
    c.createStatement().execute("create table other(id int)");
    c.rollback();
    // select count(*) → ?
}
    [4] id in tx=1
[4] after rollback count=0
[4] next id=2
[5] after DDL+rollback count=2

    출력 앞의 번호는 실험 프로그램 전체의 구획 번호다(나머지 구획은 임베디드 모드를 다룰 때 본다). 결과를 한 줄씩 읽어 보자. 트랜잭션 안에서 넣은 'A'는 식별자 1을 받았고, 롤백 뒤 행 수는 0이다. 여기까지는 기대대로다. 그런데 다음에 넣은 'B'의 식별자는 1이 아니라 2다. 행은 되돌아갔지만 식별자 생성기가 내준 값은 되돌아가지 않았다. MySQL InnoDB도 같다. MySQL 문서는 AUTO_INCREMENT 처리에서 모든 잠금 모드(0, 1, 2)에서 자동 증가 값을 만든 트랜잭션이 롤백되면 그 값은 "잃어버린" 값이 되어 다시 쓰이지 않는다고 설명한다. 식별자 생성기는 여러 트랜잭션이 동시에 값을 받아 가는 공유 자원이라, 한 트랜잭션의 롤백에 맞춰 되감으면 다른 트랜잭션이 이미 받은 값과 충돌할 수 있기 때문이다. 따라서 테스트에서 "방금 저장한 행의 id는 1이다" 같은 단정은 롤백을 써도 반복 가능하지 않다. 저장 메서드가 돌려준 객체의 id로 다시 조회하는 식으로 써야 한다.

    마지막 줄은 더 놀랍다. 'C'를 넣고 CREATE TABLE을 실행한 뒤 롤백했는데 행 수가 2다. 'B'와 'C'가 모두 남았다. H2 2.4.240에서 DDL 문장이 그때까지 진행 중이던 트랜잭션을 커밋했기 때문이다. 앞에서 본 MySQL의 암묵적 커밋 규칙과 같은 결과다. 테스트 안에서 테이블을 만들거나 TRUNCATE로 비우는 순간, 그 앞의 변경은 롤백 대상에서 빠져나간다. MySQL 문서는 CREATE TEMPORARY TABLE은 암묵적 커밋을 일으키지 않지만 롤백으로 되돌릴 수도 없다고 덧붙인다.

    나머지 경계는 실험이 없어도 구조에서 바로 나온다. 롤백은 그 커넥션에서 일어난 데이터베이스 변경만 되돌린다. 테스트 중에 파일을 쓰거나, 메시지 브로커에 메시지를 보내거나, 외부 HTTP API를 호출했다면 그것은 데이터베이스 트랜잭션 바깥의 일이다. 또 같은 데이터베이스라도 다른 커넥션으로 실행된 작업은 이 트랜잭션과 무관하게 커밋된다. 다른 커넥션이 쓰이는 대표적인 경우가 다른 스레드다. 이것은 뒤에서 실행 결과로 확인한다.

    테스트용 @Transactional: 롤백을 프레임워크에 맡기기

    앞 절의 @BeforeEach·@AfterEach 코드는 테스트 클래스마다 똑같이 반복된다. 스프링 테스트 프레임워크는 이 반복을 애너테이션 하나로 줄여 준다. 테스트 클래스나 테스트 메서드에 @Transactional을 붙이면 된다. Spring Framework 6.2 참조 문서가 정리한 규칙은 다음과 같다.

    • 테스트 메서드에 @Transactional을 붙이면 그 테스트는 트랜잭션 안에서 실행되고, 끝나면 기본으로 롤백된다. 이것을 문서는 테스트 관리 트랜잭션(test-managed transaction)이라고 부른다.
    • 클래스에 붙이면 그 클래스 계층의 모든 테스트 메서드가 각각 자기 트랜잭션에서 실행된다. 클래스에도 메서드에도 붙어 있지 않은 테스트 메서드는 트랜잭션 없이 실행된다.
    • @BeforeEach, @AfterEach 같은 메서드 수준 생명주기 메서드는 테스트 관리 트랜잭션 안에서 실행된다. @BeforeAll, @AfterAll 같은 클래스 수준 생명주기 메서드는 트랜잭션 밖에서 실행된다.
    • 롤백 대신 커밋하려면 @Commit(또는 @Rollback(false))을 붙인다. 클래스에 @Commit을 붙이고 특정 메서드에만 @Rollback을 붙여 덮어쓸 수도 있다.
    • 테스트의 @Transactional에서 전파 속성은 NOT_SUPPORTED와 NEVER만 지원되며, 이 둘을 지정한 테스트는 트랜잭션 없이 실행된다. 클래스 전체에 트랜잭션을 걸어 두고 특정 테스트만 빼고 싶을 때 쓴다.
    • 테스트 컨텍스트에 PlatformTransactionManager 빈이 있어야 한다. 스프링 부트에서는 JDBC나 JPA 스타터가 자동으로 등록하므로 따로 할 일은 없다.

    세 번째 규칙이 실용적으로 중요하다. 테스트마다 필요한 기준 데이터를 @BeforeEach에서 넣으면 그 데이터도 테스트 관리 트랜잭션 안에서 들어가므로 테스트가 끝나면 함께 롤백된다. 반대로 @BeforeAll에서 넣은 데이터는 트랜잭션 밖에서 들어가 커밋되므로, 직접 지우지 않으면 남는다.

    누가 트랜잭션을 여는가: TransactionalTestExecutionListener

    여기서 질문을 하나 던져 보자. 서비스 클래스에 붙인 @Transactional은 스프링이 그 빈을 프록시로 감싸서 처리한다(이 프록시의 구조와 함정은 7회에서 자세히 다룬다). 그렇다면 테스트 클래스에 붙인 @Transactional도 프록시가 처리할까? 그렇지 않다. 테스트 인스턴스는 JUnit이 만든 평범한 객체다. 스프링은 그 객체에 의존관계를 주입할 뿐 컨테이너의 빈으로 등록하거나 프록시로 감싸지 않는다. 테스트의 @Transactional을 읽고 트랜잭션을 여닫는 것은 TransactionalTestExecutionListener라는 리스너다.

    Spring Framework 7.0.10 소스에서 이 리스너의 beforeTestMethod를 따라가면 다음 순서로 일한다. 먼저 테스트 메서드와 테스트 클래스에서 트랜잭션 속성을 읽는다. 애플리케이션의 @Transactional을 해석하는 것과 같은 종류의 속성 해석기(AnnotationTransactionAttributeSource)를 쓴다. 속성이 없으면 아무것도 하지 않는다. 전파 속성이 NOT_SUPPORTED나 NEVER이면 역시 그냥 돌아간다. 그 밖의 경우에는 트랜잭션 매니저를 찾고, @Commit·@Rollback을 보고 롤백 여부를 정해 TransactionContext를 만든 뒤, @BeforeTransaction 메서드들을 실행하고, transactionManager.getTransaction(...)으로 트랜잭션을 시작한다. 테스트가 끝나면 afterTestMethod가 TransactionContext.endTransaction을 불러, 롤백 플래그가 켜져 있으면 transactionManager.rollback, 꺼져 있으면 commit을 호출한다. 앞 절에서 손으로 짠 getTransaction·rollback과 하는 일이 같다.

    리스너의 실행 순서도 소스에 상수로 정해져 있다. Spring Framework 7.0.10 기준으로 의존관계 주입 리스너가 2000, 컨텍스트 정리(@DirtiesContext) 리스너가 3000, 트랜잭션 리스너가 4000, @Sql 스크립트 리스너가 5000이다. beforeTestMethod 같은 before 계열 콜백에서는 값이 작은 것이 먼저 실행되고, afterTestMethod 같은 after 계열 콜백에서는 TestContextManager가 역순으로 부른다. 그래서 트랜잭션이 시작될 때에는 이미 테스트 인스턴스에 빈이 주입되어 있고, @Sql로 지정한 스크립트는 트랜잭션이 열린 뒤에 실행된다.

    JUnit의 생명주기와 겹쳐 보면 @BeforeEach가 트랜잭션 안에서 실행되는 이유도 보인다. JUnit은 테스트 메서드마다 먼저 확장의 beforeEach 콜백을 부르고 나서 사용자의 @BeforeEach 메서드를 실행한다. SpringExtension.beforeEach가 곧 TestContextManager.beforeTestMethod이므로, 트랜잭션은 사용자의 @BeforeEach보다 먼저 열린다. 끝날 때는 반대로 사용자의 @AfterEach가 먼저 실행되고, 그다음 확장의 afterEach 콜백에서 롤백된다.

    JUnit 생명주기 위에서 TransactionalTestExecutionListener가 트랜잭션을 언제 시작하고 언제 롤백하는지, @BeforeEach와 @AfterEach가 그 안에 들어가는 것을 보여 준다. 세 개의 세로 생명선을 가진 시퀀스 다이어그램. 왼쪽부터 "JUnit", "TestContextManager", "트랜잭션 리스너". 위에서 아래로 시간이 흐른다. JUnit에서 TestContextManager로 화살표 "beforeTestMethod", 이어서 TestContextManager에서 트랜잭션 리스너로 화살표, 리스너 옆에 초록색 블록 "트랜잭션 시작"을 둔다. 그 아래 JUnit 생명선 옆에 세 개의 작은 상자를 차례로 놓는다: "@BeforeEach", "@Test", "@AfterEach". 이 세 상자를 연한 초록 배경의 큰 직사각형으로 함께 감싸고 "트랜잭션 안"이라 라벨을 붙인다. 아래쪽에서 JUnit에서 TestContextManager로 화살표 "afterTestMethod", 리스너 옆에 빨간 블록 "롤백"을 둔다. 맨 아래 작은 주석 "@Commit이면 커밋". 흰 배경, 기술 문서용 단정한 선. @BeforeEach부터 @AfterEach까지가 하나의 테스트 관리 트랜잭션 안에 들어가고, 끝나면 기본으로 롤백된다.

    테스트 관리 트랜잭션은 스레드에 묶인 보통의 스프링 트랜잭션이므로, 테스트가 부른 서비스에 @Transactional이 붙어 있어도 문제없이 합쳐진다. 서비스의 프록시가 트랜잭션 매니저에 트랜잭션을 요청하면, 기본 전파 속성(REQUIRED)에서는 현재 스레드에 이미 트랜잭션이 있으므로 새로 만들지 않고 거기에 참여한다. 서비스가 끝나도 실제 커밋은 일어나지 않고, 바깥의 테스트 트랜잭션이 끝날 때 한꺼번에 롤백된다. 이렇게 하나의 물리 트랜잭션 안에 여러 논리 트랜잭션이 겹치는 구조는 8회의 주제다.

    직접 확인: JUnit 없이 테스트 프레임워크를 돌려 보기

    지금까지의 설명이 맞는지 실행으로 확인해 보자. SpringExtension이 하는 일은 결국 TestContextManager의 메서드를 정해진 순서로 부르는 것이므로, JUnit 없이 그 메서드들을 직접 불러도 같은 일이 일어난다. 이렇게 하면 프레임워크가 숨겨 둔 순서가 코드에 그대로 드러난다. 의존성은 spring-core, spring-beans, spring-context, spring-aop, spring-expression, spring-jdbc, spring-tx, spring-test(모두 7.0.10)와 H2 2.4.240, 그리고 이들이 요구하는 commons-logging, micrometer-observation, jspecify다.

        return new EmbeddedDatabaseBuilder().setType(EmbeddedDatabaseType.H2)
            .generateUniqueName(true).addScript("schema.sql").build();
    }
    @Bean PlatformTransactionManager transactionManager(DataSource ds) {
        return new DataSourceTransactionManager(ds);
    }
    @Bean JdbcTemplate jdbcTemplate(DataSource ds) { return new JdbcTemplate(ds); }
}

@ContextConfiguration(classes = Config.class)
@Transactional
public class BookTest {
    @Autowired JdbcTemplate jdbc;

    int session() { return jdbc.queryForObject("select session_id()", Integer.class); }
    int count() { return jdbc.queryForObject("select count(*) from book", Integer.class); }

    public void save() {
        jdbc.update("insert into book(title) values ('A')");
        System.out.println("  in test: active=" + TransactionSynchronizationManager.isActualTransactionActive()
            + " count=" + count() + " session=" + session() + " session again=" + session());
    }
    @Commit
    public void saveCommit() {
        jdbc.update("insert into book(title) values ('B')");
        System.out.println("  in test: count=" + count());
    }
    public void saveInOtherThread() throws Exception {
        jdbc.update("insert into book(title) values ('C')");
        System.out.println("  main thread session=" + session());
        Thread t = new Thread(() -> {
            System.out.println("  other thread active=" + TransactionSynchronizationManager.isActualTransactionActive()
                + " session=" + session());
            jdbc.update("insert into book(title) values ('D')");
        });
        t.start(); t.join();
    }
    public void programmatic() {
        jdbc.update("insert into book(title) values ('E')");
        TestTransaction.flagForCommit();
        TestTransaction.end();
        System.out.println("  after end: active=" + TestTransaction.isActive());
        TestTransaction.start();
        jdbc.update("insert into book(title) values ('F')");
    }
}

public class Main {
    public static void main(String[] args) throws Exception {
        TestContextManager tcm = new TestContextManager(BookTest.class);
        JdbcTemplate outside = null;
        for (String name : new String[]{"save", "saveCommit", "saveInOtherThread", "programmatic"}) {
            BookTest t = new BookTest();
            tcm.prepareTestInstance(t);                 // 의존관계 주입
            Method m = BookTest.class.getMethod(name);
            System.out.println("== " + name);
            tcm.beforeTestMethod(t, m);                 // SpringExtension.beforeEach 가 하는 일
            tcm.beforeTestExecution(t, m);
            m.invoke(t);                                // @Test 본문
            tcm.afterTestExecution(t, m, null);
            tcm.afterTestMethod(t, m, null);            // SpringExtension.afterEach 가 하는 일
            if (outside == null) outside = tcm.getTestContext().getApplicationContext().getBean(JdbcTemplate.class);
            System.out.println("  after test: rows=" + outside.queryForList("select title from book order by id", String.class));
        }
    }
}

JdbcTemplate은 풀(여기서는 EmbeddedDatabaseBuilder가 만든 단순한 DataSource)에서 새 커넥션을 얻고, 그 커넥션은 자동 커밋 모드이므로 'D'는 문장이 끝나는 순간 커밋되었다. 테스트 관리 트랜잭션의 롤백은 이 커넥션에 닿지 않는다.

    programmatic. TestTransaction은 테스트 관리 트랜잭션을 코드로 다루는 정적 메서드 모음이다.     이 장의 핵심

    테스트의 @Transactional은 마법 같은 격리 장치가 아니라, 테스트 스레드에 커넥션 하나를 묶고 끝날 때 그 커넥션에 롤백을 보내는 장치다. 그 커넥션을 거친 변경만 되돌아간다. 다른 스레드, 다른 커넥션, 데이터베이스 밖의 부수 효과, 그리고 암묵적 커밋을 일으키는 문장은 이 장치의 범위 밖에 있다.

    테스트 트랜잭션의 함정

    테스트에 @Transactional을 붙이는 것은 편리하지만, 테스트가 실제 운영과 다른 조건에서 실행되게 만드는 면도 있다. 함정은 대부분 "롤백 범위 밖의 일"과 "운영에서는 일어나는데 테스트에서는 일어나지 않는 일" 두 종류로 나뉜다.

    다른 스레드에서 실행되는 코드

    앞의 실험이 보여 준 대로, 테스트 스레드가 아닌 곳에서 실행되는 데이터베이스 작업은 테스트 관리 트랜잭션에 참여하지 않는다. 비동기로 실행되는 코드, 별도 스레드 풀에 맡긴 작업이 모두 여기에 해당한다. Spring Framework 문서는 이것을 테스트 프레임워크 쪽에서도 경고한다. 스프링은 테스트 메서드를 부르기 전에 트랜잭션 상태를 현재 스레드에 묶는데, 선점형 타임아웃을 지원하려고 테스트 메서드를 새 스레드에서 실행하는 기능(JUnit Jupiter의 assertTimeoutPreemptively(...), JUnit 4의 @Test(timeout = ...), TestNG의 @Test(timeOut = ...))을 쓰면 그 안의 작업은 테스트 관리 트랜잭션 밖에서 실행된다.

    스프링 부트 문서는 같은 원리가 서버를 띄우는 테스트에서도 적용된다고 설명한다. @SpringBootTest의 웹 환경을 RANDOM_PORT나 DEFINED_PORT로 하면 실제 서블릿 환경이 뜨고, HTTP 클라이언트(테스트)와 서버는 서로 다른 스레드, 따라서 서로 다른 트랜잭션에서 실행된다. 테스트에 @Transactional이 붙어 있어도 서버에서 시작된 트랜잭션은 롤백되지 않는다. 기본값(MOCK)에서는 서버를 띄우지 않으므로 이 문제가 없다. 스프링 MVC 1편에서 본 것처럼 서블릿 컨테이너는 요청을 자기 스레드 풀의 워커 스레드에서 처리한다는 것을 떠올리면 당연한 결과다.

    독립된 트랜잭션을 여는 애플리케이션 코드

    Spring Framework 문서는 애플리케이션 코드의 트랜잭션이 REQUIRED나 SUPPORTS가 아닌 전파 속성을 쓸 때 주의하라고 말한다. 예를 들어 REQUIRES_NEW로 선언된 메서드는 테스트 트랜잭션에 참여하지 않고 자기 트랜잭션을 따로 열어 커밋한다. 그 결과 테스트가 끝나고 롤백되어도 그 메서드가 쓴 데이터는 남는다. 감사 로그처럼 "본 작업이 실패해도 남겨야 하는 기록"을 이렇게 설계하는 경우가 많은데, 그런 테스트는 롤백만 믿으면 데이터가 쌓인다. 전파 속성의 동작은 8회와 9회에서 다룬다.

    커밋 때에야 일어나는 일이 일어나지 않는다

    롤백되는 테스트는 커밋을 한 번도 하지 않는다. 그러면 커밋 시점에 일어나는 일은 테스트에서 검증되지 않는다. 스프링의 TransactionSynchronization.afterCommit 콜백처럼 "커밋이 성공한 뒤에 실행하라"고 등록한 작업은 롤백으로 끝나는 테스트에서 실행되지 않는다. JPA에서는 더 미묘한 문제가 있다. Spring Framework 문서는 JPA나 하이버네이트를 쓸 때 영속성 컨텍스트의 변경을 데이터베이스로 내보내는 플러시가 일어나지 않으면, 테스트는 통과하는데 같은 코드가 운영에서는 예외를 던지는 거짓 양성(false positive)이 생길 수 있다고 경고한다. 제약 조건 위반 같은 오류는 SQL이 실제로 데이터베이스에 도달해야 드러나는데, 롤백으로 끝나는 테스트에서는 그 SQL이 끝내 나가지 않을 수 있다. 문서가 제시하는 대처는 테스트 안에서 명시적으로 플러시하는 것이다. 영속성 컨텍스트와 플러시는 4회에서 다룬다.

    모든 것이 한 트랜잭션 안에서 일어난다

    운영에서는 사용자의 요청 하나가 보통 서비스 메서드 하나의 트랜잭션에서 처리되고, 다음 요청은 새 트랜잭션에서 처리된다. 테스트 관리 트랜잭션 안에서는 저장과 조회, 검증이 모두 같은 트랜잭션, 같은 커넥션에서 일어난다. 그래서 "저장 트랜잭션이 커밋되고 나서 다른 트랜잭션에서 조회하면 어떻게 보이는가"라는 질문은 이 테스트로 답할 수 없다. 격리 수준에 따른 가시성, 락 대기 같은 동시성 문제도 마찬가지다. 이런 성질을 확인하려면 테스트에서 트랜잭션을 빼고(@Transactional(propagation = Propagation.NOT_SUPPORTED) 또는 애너테이션 없이) 데이터 정리를 직접 하거나, TestTransaction으로 트랜잭션 경계를 나눠야 한다.

    임베디드 모드 DB: 데이터베이스를 테스트 프로세스 안으로

    지금까지의 방법은 모두 "어딘가에 떠 있는 데이터베이스 서버"를 전제로 했다. 테스트를 돌리려면 그 서버가 먼저 실행 중이어야 하고, 테스트용 스키마도 미리 만들어 두어야 한다. 새로 합류한 개발자의 컴퓨터나 빌드 서버에서 테스트가 바로 돌지 않는 이유가 대개 여기에 있다. 데이터베이스를 아예 테스트 프로세스 안에 띄우면 이 전제가 사라진다.

    H2 문서는 세 가지 연결 모드(connection mode)를 구분한다. 임베디드 모드(embedded mode)에서는 데이터베이스가 애플리케이션과 같은 JVM 안에서 열린다. 문서는 이것을 가장 빠르고 쉬운 연결 모드라고 설명한다. 서버 모드(server mode)에서는 별도의 H2 서버에 TCP/IP로 원격 접속하며, 모든 데이터가 네트워크를 거쳐야 하므로 더 느리다. 혼합 모드(mixed mode)는 둘을 합친 것으로, 처음 연결한 애플리케이션이 데이터베이스를 로컬로 열면서 다른 애플리케이션을 위해 서버도 함께 띄운다.

    임베디드 모드가 빠른 이유를 한 층 아래에서 보자. 서버 모드에서 executeQuery를 부르면 JDBC 드라이버가 SQL을 바이트로 직렬화해 소켓에 쓰고, 커널의 TCP 스택과(로컬이라도) 루프백 인터페이스를 거쳐 서버 프로세스가 읽고, 결과를 다시 같은 경로로 돌려보낸다. 임베디드 모드에서는 드라이버가 같은 JVM에 로드된 H2 엔진 클래스의 메서드를 직접 호출한다. 프로세스 경계도, 소켓도, 직렬화된 프로토콜도 없다. 대신 데이터베이스의 수명이 그 JVM 프로세스에 묶이고, 다른 프로세스(예를 들어 데이터를 들여다보려는 별도의 SQL 클라이언트)는 그 데이터베이스에 접근할 수 없다.

    서버 모드에서는 테스트 JVM과 H2 서버 프로세스가 TCP로 연결되고, 임베디드 모드에서는 H2 엔진이 테스트 JVM 안에 들어 있다는 차이를 보여 준다. 화면을 좌우 두 칸으로 나눈다. 왼쪽 칸 제목 "서버 모드". 왼쪽 칸에 큰 사각형 "테스트 JVM"과 그 안의 작은 상자 "JDBC 드라이버"를 두고, 오른쪽에 떨어진 별도의 사각형 "H2 서버 프로세스"와 그 안의 원통 "데이터"를 둔다. 두 사각형 사이를 양방향 화살표로 잇고 "TCP 소켓"이라 라벨을 붙인다. 오른쪽 칸 제목 "임베디드 모드". 큰 사각형 "테스트 JVM" 하나만 두고 그 안에 "JDBC 드라이버" 상자와 "H2 엔진" 상자, 원통 "메모리 데이터"를 나란히 넣는다. "JDBC 드라이버"에서 "H2 엔진"으로 짧은 화살표 "메서드 호출". 오른쪽 칸 아래에 작은 주석 "JVM이 끝나면 함께 사라짐". 흰 배경, 깔끔한 기술 도식. 임베디드 모드에서는 네트워크 왕복 없이 같은 JVM 안의 엔진을 직접 호출한다. 대신 데이터베이스의 수명이 프로세스에 묶인다.

    메모리 데이터베이스의 URL과 수명

    임베디드 모드는 파일에 저장할 수도 있지만(jdbc:h2:~/test 같은 URL), 테스트에서는 보통 데이터를 디스크에 쓰지 않는 메모리 데이터베이스를 쓴다. H2 문서가 정리한 URL 규칙은 다음과 같다.

    URL의미
    jdbc:h2:mem:이름 없는 비공개(private) 메모리 DB. 같은 JVM에서 이 URL로 커넥션을 두 번 열면 서로 다른 DB 두 개가 생긴다.
    jdbc:h2:mem:testdb이름 있는 메모리 DB. 같은 JVM, 같은 클래스 로더 환경 안에서는 같은 이름으로 같은 DB에 접근한다.
    ;DB_CLOSE_DELAY=-1마지막 커넥션이 닫혀도 DB를 닫지 않는다. 기본 동작은 마지막 커넥션이 닫히면 DB도 닫히고, 메모리 DB라면 내용이 사라진다. 문서는 이 옵션이 메모리 누수가 될 수 있으니 필요 없어지면 SHUTDOWN을 실행하라고 덧붙인다.
    ;DB_CLOSE_ON_EXIT=FALSE기본으로 H2는 닫히지 않은 DB를 JVM이 정상 종료할 때 셧다운 훅으로 닫는다. 이 옵션은 그 훅을 끈다. 처음 연결하는 커넥션만 설정할 수 있다.

    규칙을 실행으로 확인해 보자. 앞에서 롤백 실험을 했던 프로그램의 앞부분이다.

    // [1] 이름 있는 메모리 DB, DB_CLOSE_DELAY 없음
try (Connection c = DriverManager.getConnection("jdbc:h2:mem:a", "sa", "")) {
    c.createStatement().execute("create table book(id bigint generated by default as identity primary key, title varchar(20))");
    c.createStatement().execute("insert into book(title) values ('x')");
    System.out.println("[1] in first conn count=" + count(c));
}
try (Connection c = DriverManager.getConnection("jdbc:h2:mem:a", "sa", "")) {
    System.out.println("[1] reopen count=" + count(c));
} catch (SQLException e) { System.out.println("[1] reopen error: " + e.getMessage().split("\n")[0]); }

// [2] 이름 없는 메모리 DB에 커넥션 두 개
try (Connection c1 = DriverManager.getConnection("jdbc:h2:mem:", "sa", "");
     Connection c2 = DriverManager.getConnection("jdbc:h2:mem:", "sa", "")) {
    c1.createStatement().execute("create table book(id bigint primary key)");
    try { count(c2); System.out.println("[2] c2 sees table"); }
    catch (SQLException e) { System.out.println("[2] c2 error: " + e.getMessage().split("\n")[0]); }
}

// [3] DB_CLOSE_DELAY=-1
String url = "jdbc:h2:mem:b;DB_CLOSE_DELAY=-1";
try (Connection c = DriverManager.getConnection(url, "sa", "")) {
    c.createStatement().execute("create table book(id bigint generated by default as identity primary key, title varchar(20))");
}
try (Connection c = DriverManager.getConnection(url, "sa", "")) {
    System.out.println("[3] reopen count=" + count(c));
    // ... [4], [5] 는 앞의 롤백 실험
}
    [1] in first conn count=1
[1] reopen error: Table "BOOK" not found (this database is empty); SQL statement:
[2] c2 error: Table "BOOK" not found (this database is empty); SQL statement:
[3] reopen count=0

    [1]에서는 첫 커넥션 안에서 행 한 건이 보였지만, 커넥션을 닫고 같은 URL로 다시 열자 테이블 자체가 없다. 마지막 커넥션이 닫히는 순간 DB가 닫히고 메모리의 내용이 사라졌기 때문이다. 오류 메시지의 "this database is empty"가 그 상황을 그대로 말해 준다. [2]에서는 두 커넥션이 동시에 열려 있는데도 c1이 만든 테이블을 c2가 보지 못한다. 이름 없는 URL은 커넥션마다 비공개 DB를 만든다. [3]에서는 DB_CLOSE_DELAY=-1 덕분에 커넥션을 닫았다 열어도 테이블이 남아 있다(행 수 0은 행을 넣지 않았기 때문이다).

    이 결과는 커넥션 풀과 함께 쓸 때 특히 중요하다. 커넥션 풀은 커넥션을 미리 열어 두었다가 빌려주므로, 풀이 열려 있는 동안에는 보통 커넥션이 남아 있다. 그러나 커넥션 풀을 쓰지 않는 단순한 DataSource는 요청마다 커넥션을 새로 열고 닫으므로, 테스트 사이에 열린 커넥션이 하나도 없는 순간이 쉽게 생긴다(앞 실험의 EmbeddedDatabaseBuilder가 만든 DataSource가 그런 종류다). 그 순간 테스트 데이터베이스가 통째로 사라지면 원인을 찾기 어렵다. 스프링과 스프링 부트가 만드는 임베디드 H2의 URL에는 이 일을 막는 DB_CLOSE_DELAY=-1이 붙어 있다. Spring Framework 7.0.10 소스의 H2EmbeddedDatabaseConfigurer는 jdbc:h2:mem:%s;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=false 형식으로 URL을 만들고, 앞의 실험 로그에 찍힌 URL이 바로 그 형식이다. EmbeddedDatabaseBuilder의 기본 DB 이름은 testdb이고, generateUniqueName(true)를 주면 실험에서처럼 UUID가 이름이 된다.

    스키마는 매번 새로 만든다

    메모리 데이터베이스는 프로세스가 시작될 때마다 비어 있다. 이것은 장점이자 의무다. 이전 실행의 찌꺼기가 원천적으로 없다는 점에서 장점이고, 테이블을 매번 만들어야 한다는 점에서 의무다. 그래서 임베디드 DB를 쓸 때는 스키마를 만드는 SQL 스크립트가 짝으로 따라온다. 앞 실험의 addScript("schema.sql")이 그 역할을 했다. 스크립트는 같은 데이터베이스 엔진의 SQL 문법으로 써야 한다. 위 스크립트의 generated by default as identity는 H2가 받아들이는 식별 열 문법이고, MySQL이라면 AUTO_INCREMENT를 쓴다.

    이 지점에서 임베디드 DB의 근본적인 한계가 드러난다. 테스트가 H2에서 돌고 운영이 MySQL에서 돈다면, 테스트는 운영과 다른 데이터베이스 엔진을 검증하고 있다. H2 문서는 MySQL 등 특정 데이터베이스의 동작을 흉내 내는 호환 모드(MODE=MySQL)를 제공하지만, 다루는 것은 차이의 일부뿐이라고 밝힌다. 문서가 예로 드는 차이 하나만 봐도, MySQL은 기본으로 문자열 비교에서 대소문자를 구분하지 않지만 H2는 구분한다. 락의 범위, 격리 수준의 세부 구현, 실행 계획처럼 엔진 내부에 속하는 성질은 흉내 낼 수 있는 종류의 것이 아니다.

    스프링 부트와 임베디드 모드: URL을 지우면 일어나는 일

    스프링 부트는 임베디드 DB를 쓰기 위해 해야 할 일을 거의 0으로 줄인다. 스프링 부트 문서에 따르면 부트는 H2, HSQL, Derby 임베디드 데이터베이스를 자동 구성할 수 있고, 연결 URL을 줄 필요가 없으며 원하는 임베디드 DB의 의존성만 넣으면 된다. 이때 spring-jdbc가 클래스패스에 있어야 한다(JDBC나 JPA 스타터가 가져온다). 반대로 말해, 테스트용 설정 파일에서 spring.datasource.url을 지우기만 하면 H2가 클래스패스에 있는 프로젝트는 임베디드 메모리 DB로 테스트하게 된다.

    # src/test/resources/application.properties
# spring.datasource.url 을 적지 않는다 → 부트가 임베디드 H2 를 구성한다
logging.level.org.springframework.jdbc=debug
    -- src/test/resources/schema.sql
create table book (
    id    bigint generated by default as identity,
    title varchar(100) not null,
    price integer,
    primary key (id)
);

    "URL이 없으면 임베디드 DB"라는 한 문장 뒤에는 조건 판단이 몇 단계 숨어 있다. Spring Boot 3.5.0 소스의 DataSourceAutoConfiguration을 보면 임베디드 구성 조건(EmbeddedDatabaseCondition)은 다음 순서로 검사하고, 처음 걸리는 곳에서 멈춘다.

    세 번째 단계에서 H2용 URL 템플릿은 EmbeddedDatabaseConnection에 jdbc:h2:mem:%s;DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE로 정의되어 있다. 따라서 H2와 JDBC 스타터를 쓰는 보통의 부트 프로젝트에서 URL을 지우면, 결과는 "jdbc:h2:mem:(UUID);DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE에 연결하는 HikariCP 풀"이다. 앞 절에서 본 두 옵션이 여기서 의미를 갖는다. DB_CLOSE_DELAY=-1은 풀이 커넥션을 모두 닫는 순간에도 DB가 사라지지 않게 하고, DB_CLOSE_ON_EXIT=FALSE는 H2의 셧다운 훅 대신 스프링이 DB를 닫는 시점을 정하게 한다. 스프링 부트 문서도 임베디드 DB의 URL을 직접 설정하는 경우에는 자동 셧다운을 꺼야 하며, H2라면 DB_CLOSE_ON_EXIT=FALSE를 쓰라고 안내한다. 그래야 부트가 DB에 대한 접근이 더는 필요 없을 때 닫을 수 있다는 것이다. 여러 임베디드 DB가 클래스패스에 있을 때는 spring.datasource.embedded-database-connection으로 고르고, 이 값을 none으로 하면 임베디드 자동 구성이 꺼진다.

    네 번째 단계의 이름 규칙은 테스트와 직접 맞물린다. generate-unique-name의 기본값은 Spring Boot 3.5.0 소스에서 true이고, UUID는 DataSourceProperties 객체마다 한 번 만들어진다. DataSourceProperties는 애플리케이션 컨텍스트마다 하나씩 생기므로, 컨텍스트마다 별도의 메모리 DB가 생긴다. 이것을 앞에서 본 컨텍스트 캐시와 합치면 테스트 스위트 안에서 데이터베이스가 어떻게 나뉘는지가 정확히 나온다. 설정이 같아 컨텍스트를 공유하는 테스트 클래스들은 메모리 DB 하나를 함께 쓰고, @MockitoBean이나 @ActiveProfiles 같은 차이 때문에 컨텍스트가 따로 만들어지는 테스트 클래스는 자기만의 빈 DB를 받는다. 스프링 부트 3.5 문서에는 "테스트 스위트 전체가 같은 DB를 재사용하는 것을 피하려면 이 값을 true로 하라"는 안내가 남아 있는데, 3.5.0 소스에서는 이미 그것이 기본값이다.

    컨텍스트마다 DB가 따로 생긴다고 해서 롤백이 필요 없어지는 것은 아니다. 같은 컨텍스트를 쓰는 테스트 클래스와 테스트 메서드는 여전히 하나의 메모리 DB를 공유한다. 임베디드 DB는 "실행할 때마다 빈 DB에서 시작한다"는 문제를 풀고, 롤백은 "한 실행 안에서 테스트끼리 영향을 주지 않는다"는 문제를 푼다. 둘은 서로를 대신하지 않는다.

    schema.sql은 언제 실행되는가

    테이블은 누가 만들까. 스프링 부트는 기본으로 optional:classpath*:schema.sql에서 스키마 스크립트를, optional:classpath*:data.sql에서 데이터 스크립트를 읽어 실행한다. spring.sql.init.platform을 설정하면 schema-${platform}.sql, data-${platform}.sql도 함께 처리한다. 스프링 부트 문서에 따르면 이 스크립트 기반 초기화는 기본으로 임베디드 인메모리 데이터베이스를 쓸 때만 수행된다. 항상 실행하려면 spring.sql.init.mode=always, 끄려면 never로 설정한다. 이 기본값 덕분에 src/test/resources/schema.sql을 두면 임베디드 DB로 도는 테스트에서는 테이블이 자동으로 만들어지고, 같은 파일이 실제 MySQL에 붙는 실행에서는 의도치 않게 실행되지 않는다. 스크립트에서 오류가 나면 기본으로 애플리케이션(테스트 컨텍스트) 시작이 실패한다.

    JPA를 함께 쓸 때는 순서도 알아 둘 필요가 있다. 문서에 따르면 스크립트 기반 초기화는 기본으로 JPA의 EntityManagerFactory 빈이 만들어지기 전에 실행된다. 하이버네이트가 만든 스키마 위에 스크립트를 실행하고 싶다면 spring.jpa.defer-datasource-initialization=true로 순서를 미룬다. 문서는 여러 초기화 기술을 섞어 쓰는 것을 권하지 않으며, Flyway나 Liquibase 같은 마이그레이션 도구를 쓴다면 그것만으로 스키마를 만들라고 권한다.

    테스트 슬라이스는 이 모든 것을 기본으로 한다

    스프링 부트의 데이터 접근 테스트 슬라이스는 지금까지 손으로 조립한 것을 기본값으로 묶어 둔 것이다. 스프링 부트 문서에 따르면 @JdbcTest는 기본으로 인메모리 임베디드 데이터베이스와 JdbcTemplate을 구성하고, 테스트는 트랜잭션 안에서 실행되어 테스트마다 롤백된다. @DataJpaTest도 임베디드 DB가 클래스패스에 있으면 그것을 구성하고, 기본으로 트랜잭션 안에서 실행해 롤백한다. 트랜잭션을 원하지 않으면 @Transactional(propagation = Propagation.NOT_SUPPORTED)를 붙이고, 임베디드 DB 대신 설정된 실제 데이터베이스로 테스트하려면 @AutoConfigureTestDatabase(replace = Replace.NONE)을 붙인다. 슬라이스 테스트는 애플리케이션 전체가 아니라 데이터 접근에 필요한 빈만 올리므로 컨텍스트가 가볍다. 대신 슬라이스마다 컨텍스트 캐시 키가 달라지므로 @SpringBootTest와 섞어 쓰면 컨텍스트 수가 늘어난다.

    정리: 어떤 데이터베이스로, 어떻게 격리할 것인가

    이 회차에서 쌓은 방법들은 서로 다른 층의 문제를 푼다. 하나씩 겹쳐 보면 다음과 같다.

    방법푸는 문제남는 문제
    테스트용 DB 분리개발 데이터와 테스트 데이터가 섞이는 것테스트끼리, 실행끼리 데이터가 남는다
    정리 SQL(DELETE)테스트가 남긴 데이터실패·중단 시 정리 누락, 지울 목록 관리, TRUNCATE의 암묵적 커밋
    트랜잭션 롤백(@Transactional)같은 커넥션을 거친 모든 변경식별자 값, DDL, 다른 스레드·다른 트랜잭션, 커밋 시점 동작 미검증
    임베디드 메모리 DB서버 준비, 이전 실행의 찌꺼기운영과 다른 엔진, 한 컨텍스트 안의 공유 상태

    실무에서 흔히 쓰는 조합은 "임베디드 DB 또는 전용 테스트 DB + 테스트마다 롤백"이다. 이 조합에서 각 테스트는 매번 같은 상태에서 시작한다. 다만 롤백의 범위 밖에 있는 일(다른 스레드, 서버 모드 테스트, REQUIRES_NEW, 커밋 후 동작)을 테스트해야 할 때는 롤백을 끄고, 테스트 앞에서 필요한 상태를 직접 만드는 방식으로 돌아가야 한다. 어떤 엔진으로 테스트할지는 무엇을 검증하느냐에 달려 있다. 자바 코드의 흐름과 매핑을 확인하는 테스트라면 H2로 충분한 경우가 많다. 반면 특정 SQL 문법, 락과 격리 수준, 실행 계획처럼 엔진의 성질에 기대는 코드라면 운영과 같은 엔진에서 확인해야 검증이 의미를 갖는다.

    이 회차에서 만든 테스트 환경은 이 권의 나머지 회차가 계속 쓴다. 3회의 MyBatis와 4~6회의 JPA, 스프링 데이터 JPA, Querydsl은 같은 리포지토리 테스트를 서로 다른 기술로 통과시키는 과정이고, 그 테스트가 매번 같은 상태에서 시작하는 것은 이 회차의 롤백과 임베디드 DB 덕분이다. 7회에서는 서비스에 붙인 @Transactional이 프록시를 통해 어떻게 적용되는지, 8~9회에서는 테스트 트랜잭션 안에서 서비스 트랜잭션이 합쳐지던 구조(물리 트랜잭션과 논리 트랜잭션, REQUIRES_NEW)를 본격적으로 다룬다.
    공유 상태로서의 데이터베이스
    커밋된 행은 테스트가 끝나도 JVM 밖에 남는다. 그래서 DB를 쓰는 테스트는 반복 가능성과 독립성을 잃기 쉽고, 실행 순서(JUnit 기본 순서는 결정적이지만 드러나지 않는다)에 따라 결과가 바뀔 수 있다.
    테스트 설정 파일의 우선순위
    테스트 실행 시 src/test/resources가 클래스패스 앞에 오고, 부트는 classpath:application.properties를 하나만 읽는다. 테스트 파일은 메인 파일을 병합하지 않고 가린다.
    컨텍스트 캐시
    설정이 같은 테스트 클래스는 static 캐시에 보관된 애플리케이션 컨텍스트 하나를 공유한다(기본 최대 32개, LRU). 컨텍스트를 공유하면 DataSource와 그 너머의 DB도 공유한다.
    테스트 관리 트랜잭션
    테스트의 @Transactional을 TransactionalTestExecutionListener가 해석해, 테스트 전에 트랜잭션을 열고 끝나면 기본으로 롤백한다. @BeforeEach·@AfterEach는 안에, @BeforeAll·@AfterAll은 밖에 있다.
    스레드에 묶인 커넥션
    트랜잭션 매니저가 커넥션을 ThreadLocal 등록소에 묶고, JdbcTemplate은 DataSourceUtils로 그 커넥션을 찾아 쓴다. 그래서 같은 스레드의 리포지토리는 테스트 트랜잭션에 참여하고, 다른 스레드는 참여하지 않는다.
    롤백의 경계
    식별자 생성기가 내준 값, DDL·TRUNCATE의 암묵적 커밋, 다른 커넥션의 작업, REQUIRES_NEW 트랜잭션, 데이터베이스 밖의 부수 효과는 롤백으로 되돌아가지 않는다.
    H2 메모리 DB의 수명
    jdbc:h2:mem:은 커넥션마다 비공개 DB, 이름을 붙이면 같은 JVM·클래스 로더 안에서 공유된다. 마지막 커넥션이 닫히면 사라지며, DB_CLOSE_DELAY=-1이 이를 막는다.
    부트의 임베디드 자동 구성
    spring.datasource.url이 없고 H2가 있으면, 풀 구성이 jdbc:h2:mem:(UUID);DB_CLOSE_DELAY=-1;DB_CLOSE_ON_EXIT=FALSE로 연결한다. 컨텍스트마다 별도 DB가 생기고, schema.sql은 기본으로 임베디드 DB에서만 실행된다.

    실무에서 "테스트가 로컬에서는 통과하는데 CI에서 가끔 실패한다"는 증상의 상당수는 공유 상태에서 나온다. 원인을 좁힐 때는 이 회차의 경계 목록을 순서대로 대 보면 된다. 실패한 테스트가 기대한 데이터를 누가 남겼는가. @Commit이나 @BeforeAll에서 넣은 데이터인가, REQUIRES_NEW나 비동기 코드가 커밋한 데이터인가, 아니면 서버를 띄우는 테스트가 다른 스레드에서 커밋한 데이터인가. 테스트를 하나만 돌리면 통과하고 전체를 돌리면 실패한다면, 같은 컨텍스트를 공유하는 다른 테스트 클래스가 범인일 가능성이 높다. 식별자 값을 하드코딩한 단정은 롤백을 쓰는 환경에서도 실행 순서에 따라 깨진다.

    테스트에 @Transactional을 붙일지는 검증하려는 대상에 따라 판단이 달라진다. 리포지토리의 SQL과 매핑을 확인하는 테스트라면 롤백 방식이 가장 값싸고 안정적이다. 반면 서비스의 트랜잭션 경계 자체, 커밋 후에 실행되는 이벤트, 두 트랜잭션 사이의 가시성과 락을 검증하는 테스트라면 테스트 트랜잭션이 오히려 검증 대상을 가린다. 이런 테스트는 트랜잭션 없이 실행하고 데이터 준비와 정리를 명시적으로 하는 편이 정확하다. JPA를 쓰는 경우에는 롤백 테스트에서 플러시를 명시하지 않으면 운영에서만 드러나는 오류를 놓칠 수 있다.

    임베디드 H2와 운영 DB 사이의 간극도 의식적으로 관리해야 한다. 모든 테스트를 H2에서 돌리면 빠르고 설치가 필요 없지만, 운영 DB 고유의 문법이나 동작에 기대는 코드는 검증되지 않는다. 어떤 테스트를 어느 엔진에서 돌릴지 정해 두고, 엔진의 성질(대소문자 비교, 락, 격리 수준, 실행 계획)에 기대는 코드는 운영과 같은 엔진에서 확인하는 것이 안전하다. 그때도 이 회차의 원칙, 즉 테스트 전용 데이터베이스와 테스트마다 같은 시작 상태는 그대로 적용된다.
  • 클래스에 @Transactional이 붙은 테스트 클래스에 테스트 메서드 세 개가 있다. a는 행 1개를 넣고, b는 @Commit이 붙어 있고 행 1개를 넣으며, c는 전체 행 수가 0인지 단정한다. 테이블은 처음에 비어 있고 세 테스트가 같은 컨텍스트를 쓴다. 실행 순서가 a→b→c일 때와 c→a→b일 때 c의 결과를 각각 예측하고, 이 테스트 묶음의 문제를 설명하라.
  • MySQL을 테스트 DB로 쓰는 @Transactional 테스트 클래스가 있다. @BeforeEach에서 TRUNCATE TABLE book을 실행한 뒤 기준 도서 2권을 넣고, 테스트는 1권을 더 넣어 행 수가 3인지 확인한다. 테스트는 통과한다. 테스트가 끝난 뒤 book 테이블에는 무엇이 남는가? 테스트 전에 book에 있던 데이터는 어떻게 되는가?
  • 테스트 본문에서 assertTimeoutPreemptively(Duration.ofSeconds(1), () -> bookRepository.save(book))로 저장했다. 테스트 클래스에는 @Transactional이 붙어 있다. 테스트가 끝난 뒤 이 도서가 남는 이유를 스레드와 커넥션 그림으로 설명하라.
  • 테스트용 application.properties에서 spring.datasource.url 줄을 지우고 src/test/resources/schema.sql을 두었다. 프로젝트는 spring-boot-starter-jdbc와 H2를 의존성으로 가진다. (1) 테스트에서 주입받는 DataSource의 구현과 URL 형식, (2) schema.sql이 실행되는 이유, (3) 설정이 다른 두 테스트 클래스가 서로의 데이터를 보는지 여부를 답하라.

Spring Framework 문서도 이 경우를 명시적으로 경고한다. 그림에는 테스트 스레드(커넥션 A, 롤백)와 타임아웃 스레드(커넥션 B, 자동 커밋) 두 레인을 그리면 된다.

    반복 가능성(repeatability)
    같은 코드에 대해 테스트를 몇 번 실행해도 같은 결과가 나오는 성질. 데이터베이스에 남는 상태가 가장 흔한 위협이다.
    컨텍스트 캐시(context cache)
    스프링 테스트 프레임워크가 설정 조합을 키로 애플리케이션 컨텍스트를 static 변수에 보관해 재사용하는 구조. 기본 최대 32개, LRU로 제거한다.
    TestExecutionListener
    TestContextManager가 테스트 생명주기의 각 지점에서 순서대로 부르는 확장점. 의존관계 주입, 트랜잭션, @Sql 실행 등이 리스너로 구현되어 있다.
    테스트 관리 트랜잭션(test-managed transaction)
    TransactionalTestExecutionListener가 테스트 메서드 전후로 여닫는 트랜잭션. 기본으로 롤백되며 @Commit, @Rollback, TestTransaction으로 바꿀 수 있다.
    트랜잭션 동기화(transaction synchronization)
    트랜잭션 매니저가 커넥션을 현재 스레드의 ThreadLocal에 묶어, 같은 스레드의 데이터 접근 코드가 같은 커넥션을 쓰게 하는 구조.
    암묵적 커밋(implicit commit)
    MySQL에서 DDL, TRUNCATE 같은 문장이 실행 전에 진행 중인 트랜잭션을 COMMIT한 것처럼 끝내는 동작. 롤백 기반 테스트의 범위를 깨뜨린다.
    임베디드 모드(embedded mode)
    데이터베이스 엔진이 애플리케이션과 같은 JVM 안에서 실행되는 연결 방식. 네트워크 왕복이 없고, 수명이 프로세스에 묶인다.
    인메모리 데이터베이스(in-memory database)
    데이터를 디스크에 쓰지 않고 프로세스 메모리에만 두는 데이터베이스. H2에서는 마지막 커넥션이 닫히면 내용이 사라지며 DB_CLOSE_DELAY=-1로 이를 막는다.
