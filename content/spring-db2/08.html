    트랜잭션 안에서 트랜잭션을 또 시작하면

    07회에서 @Transactional이 붙은 메서드를 호출하면 프록시가 트랜잭션 매니저의 getTransaction()을 부르고, 메서드가 끝나면 commit()이나 rollback()을 부른다는 것을 보았다. 그때의 그림에서는 메서드 하나에 트랜잭션 하나가 대응했다. 하지만 실제 애플리케이션에서는 트랜잭션이 걸린 메서드가 트랜잭션이 걸린 다른 메서드를 부르는 일이 흔하다. 주문을 저장하는 서비스 메서드가 재고를 줄이는 서비스 메서드를 호출하는데, 재고 메서드는 단독으로 호출될 때도 트랜잭션이 필요해서 역시 @Transactional이 붙어 있는 식이다.

    이때 호출은 프록시를 두 번 통과하므로 getTransaction()도 두 번 불린다. 그러면 곧바로 여러 질문이 생긴다. 데이터베이스 커넥션을 두 개 쓰는가? 안쪽 메서드가 끝나며 commit()이 불리면 그 순간 안쪽에서 한 변경이 데이터베이스에 확정되는가? 안쪽이 롤백하면 바깥쪽에서 한 변경은 어떻게 되는가? 바깥이 롤백하면 이미 "커밋"한 안쪽 변경은 살아남는가? 이 질문들에 대한 답을 정해 두는 규칙이 트랜잭션 전파(transaction propagation)다.

    먼저 데이터베이스 쪽에서 무엇이 가능한지부터 확인하자. JDBC의 Connection 하나에는 한 시점에 트랜잭션이 하나만 진행된다. setAutoCommit(false) 이후 실행한 SQL은 commit()이나 rollback()이 불릴 때까지 모두 같은 트랜잭션에 속하고, 그 안에서 "트랜잭션을 하나 더 시작한다"는 JDBC API는 없다. 비슷한 것으로 세이브포인트(savepoint)가 있지만, 이것은 같은 트랜잭션 안에 되돌아갈 지점을 표시하는 것이지 독립된 트랜잭션이 아니다. 그러므로 "트랜잭션 안의 트랜잭션"은 데이터베이스가 제공하는 기능이 아니라 스프링이 그 위에 얹은 개념적인 층이다. 이 회차의 내용은 결국 그 층이 실제 커넥션과 SQL 호출로 어떻게 번역되는지를 보는 일이다.

    스프링은 이 번역 방식을 전파 옵션으로 고르게 한다. @Transactional의 propagation 속성 기본값은 Propagation.REQUIRED이고, TransactionDefinition 인터페이스에는 PROPAGATION_REQUIRED(0)부터 PROPAGATION_NESTED(6)까지 일곱 개의 상수가 정의되어 있다. 이 회차는 기본값인 REQUIRED를 중심으로 원리를 세운 다음, REQUIRES_NEW와 나머지 옵션으로 넓혀 간다. 서비스와 리포지토리 계층에 실제로 적용해 장애를 복구하는 패턴은 다음 09회의 몫이다.

    실험 준비: 프록시 없이 트랜잭션 매니저를 직접 부른다

    전파를 이해하는 가장 확실한 방법은 프록시를 걷어 내고 트랜잭션 매니저를 직접 호출해 보는 것이다. @Transactional이 결국 하는 일은 getTransaction(), commit(), rollback()을 적절한 순서로 부르는 것이므로, 이 세 메서드를 손으로 부르면 프록시가 만들어 내는 상황을 그대로 재현할 수 있다. 게다가 손으로 부르면 "안쪽 트랜잭션을 커밋했다" 같은 순간에 멈춰서 상태를 출력해 볼 수 있다.

    이 회차의 실험은 Spring Framework 7.0.10(spring-tx, spring-jdbc), HikariCP 7.0.2, H2 2.4.240, JDK 21(Temurin 21.0.13)로 실행했다. 이 강좌의 기준 버전은 Spring Framework 6.x이므로 6.2.x 브랜치의 AbstractPlatformTransactionManager와 DataSourceTransactionManager 소스를 따로 열어 대조했고, 이 회차에서 인용하는 로그 문구, 예외 메시지, 기본값(nestedTransactionAllowed, validateExistingTransaction, globalRollbackOnParticipationFailure)은 두 버전이 같았다. 버전에 따라 다른 부분은 NESTED를 다룰 때 따로 밝힌다.

import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;
import org.springframework.jdbc.datasource.DataSourceUtils;

import org.springframework.transaction.support.DefaultTransactionDefinition;

public class PropagationLab {
    static HikariDataSource ds;
    static DataSourceTransactionManager tm;
    static JdbcTemplate jdbc;

    public static void main(String[] args) {
        ds = new HikariDataSource();
        ds.setJdbcUrl("jdbc:h2:mem:propagation;DB_CLOSE_DELAY=-1");
        ds.setUsername("sa");
        ds.setMaximumPoolSize(10);
        ds.setConnectionTimeout(1000);          // 커넥션을 기다리는 최대 시간(ms)
        tm = new DataSourceTransactionManager(ds);
        jdbc = new JdbcTemplate(ds);
        jdbc.execute("create table item(id bigint auto_increment primary key, name varchar(50))");

        // 아래 시나리오 메서드 가운데 하나를 호출한다
        ds.close();
    }

    static DefaultTransactionDefinition def(int propagation) {
        DefaultTransactionDefinition d = new DefaultTransactionDefinition();
        d.setPropagationBehavior(propagation);
        return d;
    }
    static void insert(String name) { jdbc.update("insert into item(name) values (?)", name); }
    static int count() { return jdbc.queryForObject("select count(*) from item", Integer.class); }
    static void log(String s) { System.out.println(">>> " + s); }
}

    로그에 찍히는 문구 대부분은 사실 DataSourceTransactionManager가 아니라 그 부모 클래스인 AbstractPlatformTransactionManager의 코드에서 나온다. 그런데도 로거 이름이 DataSourceTransactionManager로 찍히는 이유는, 부모 클래스가 로거를 LogFactory.getLog(getClass())로 만들기 때문이다. getClass()는 실행 중인 객체의 실제 클래스를 돌려주므로 로거 이름은 구체 클래스가 된다. JPA를 쓰는 프로젝트라면 같은 문구가 org.springframework.orm.jpa.JpaTransactionManager 로거로 나온다. 로그 설정에서 엉뚱한 패키지를 열어 놓고 "로그가 안 나온다"고 헤매는 일이 많으니 기억해 둘 만하다.

    실험에서 쓰는 API는 세 가지뿐이다. tm.getTransaction(definition)은 트랜잭션을 시작하거나 기존 트랜잭션에 참여하고, 그 결과를 TransactionStatus로 돌려준다. tm.commit(status)와 tm.rollback(status)는 그 상태 객체를 받아 트랜잭션을 끝낸다. TransactionStatus에는 isNewTransaction()(이 상태가 물리 트랜잭션을 새로 시작했는가), isRollbackOnly()(롤백 전용으로 표시되었는가), setRollbackOnly(), isCompleted(), hasSavepoint() 같은 메서드가 있다. 이 다섯 개의 의미를 정확히 아는 것이 이 회차의 절반이다.

    아래 로그에서는 지면을 위해 커넥션 문자열 끝의 : url=jdbc:h2:mem:propagation user=SA 부분을 지웠다. HikariProxyConnection@ 뒤의 숫자는 객체의 식별 해시코드라서 실행 환경마다 다를 수 있다.

    커밋, 롤백, 그리고 트랜잭션을 두 번 쓰기

    전파를 보기 전에 트랜잭션이 하나뿐인 경우의 로그를 기준선으로 잡아 두자. 트랜잭션 하나를 커밋하고, 이어서 다른 트랜잭션 하나를 롤백한다. 두 트랜잭션은 순서대로 실행되므로 서로 겹치지 않는다. 각 트랜잭션 안에서는 DataSourceUtils.getConnection(ds)로 "지금 이 스레드가 쓰는 커넥션"이 무엇인지 찍어 본다. 이 메서드는 JdbcTemplate이 내부에서 커넥션을 얻을 때 쓰는 바로 그 메서드다.

    static void twoTransactions() {
    TransactionStatus tx1 = tm.getTransaction(new DefaultTransactionDefinition());
    log("tx1 conn=" + DataSourceUtils.getConnection(ds));
    tm.commit(tx1);

    TransactionStatus tx2 = tm.getTransaction(new DefaultTransactionDefinition());
    log("tx2 conn=" + DataSourceUtils.getConnection(ds));
    tm.rollback(tx2);
}

    한 트랜잭션의 일생이 일곱 줄 남짓에 다 들어 있다. Creating new transaction은 기존 트랜잭션이 없어서 새로 시작한다는 뜻이고, 뒤의 PROPAGATION_REQUIRED,ISOLATION_DEFAULT는 넘겨준 TransactionDefinition의 내용이다. 이름이 [null]인 것은 정의에 이름을 붙이지 않았기 때문인데, @Transactional을 쓰면 여기에 패키지를 포함한 클래스명.메서드명 형태의 이름(ClassUtils.getQualifiedMethodName()의 결과)이 들어간다. Acquired Connection은 데이터소스, 즉 커넥션 풀에서 커넥션을 하나 빌렸다는 뜻이다. Switching ... to manual commit은 그 커넥션의 getAutoCommit()이 true였기 때문에 setAutoCommit(false)를 불렀다는 뜻이다. 이 순간부터 이 커넥션으로 실행하는 SQL은 하나의 데이터베이스 트랜잭션으로 묶인다.

    끝날 때는 Initiating transaction commit 다음에 Committing JDBC transaction on Connection이 나오는데, 뒤쪽 줄이 실제로 Connection.commit()을 부르는 지점이다. 마지막 Releasing JDBC Connection ... after transaction은 오토커밋을 원래대로 돌려 놓고(시작할 때 바꿨다면) 커넥션을 풀에 반납했다는 뜻이다. 롤백도 같은 모양이고 가운데 두 줄만 Initiating transaction rollback, Rolling back JDBC transaction으로 바뀐다. 앞으로 볼 모든 로그는 이 기준선과 비교해 "어느 줄이 빠졌는가, 어느 줄이 새로 생겼는가"로 읽으면 된다.

    두 트랜잭션의 커넥션을 비교하면 흥미로운 점이 보인다. 둘 다 conn0을 쓰고 있지만 감싸고 있는 HikariProxyConnection 객체는 다르다(@164332069와 @2003147568). conn0은 HikariCP가 데이터베이스와 실제로 연결해 둔 물리 커넥션의 이름이고, HikariProxyConnection은 풀이 커넥션을 빌려줄 때마다 새로 만들어 씌우는 래퍼 객체다. 애플리케이션이 이 래퍼의 close()를 부르면 물리 커넥션은 닫히지 않고 풀로 돌아간다. 그래서 첫 번째 트랜잭션이 반납한 conn0을 두 번째 트랜잭션이 새 래퍼에 담아 다시 빌려 간 것이다.

    여기서 커넥션과 트랜잭션을 분리해서 생각하는 습관을 들이자. 두 트랜잭션은 같은 물리 커넥션을 썼지만 완전히 별개의 트랜잭션이다. 첫 번째는 커밋으로 끝났고, 두 번째는 커밋된 것을 볼 수 있는 상태에서 새로 시작해 롤백으로 끝났다. 커넥션은 데이터베이스 세션으로 가는 통로이고, 트랜잭션은 그 통로 위에서 처리되는 작업 단위다. 만약 두 스레드가 동시에 트랜잭션을 시작했다면 풀은 아직 반납되지 않은 conn0 대신 다른 물리 커넥션을 내주었을 것이다. 즉 "같은 커넥션을 썼다"는 사실은 트랜잭션이 이어진다는 증거가 아니라 단지 풀이 커넥션을 재사용했다는 증거다.

    전파의 기본: 물리 트랜잭션과 논리 트랜잭션

    이제 트랜잭션을 겹쳐 보자. 바깥에서 트랜잭션을 시작한 상태로, 그것을 끝내기 전에 안쪽에서 getTransaction()을 한 번 더 부른다. 이 상황을 설명하려면 두 종류의 트랜잭션을 구분해야 한다.

    • 물리 트랜잭션(physical transaction): 데이터베이스에 실제로 존재하는 트랜잭션이다. 커넥션 하나에서 setAutoCommit(false)로 시작되어 commit()이나 rollback()으로 끝난다. 앞 절의 기준선 로그가 물리 트랜잭션 하나의 일생이었다.
    • 논리 트랜잭션(logical transaction): 스프링의 트랜잭션 매니저 관점에서 getTransaction()부터 그 상태 객체에 대한 commit()/rollback()까지의 범위다. @Transactional 메서드 하나의 실행 구간이 논리 트랜잭션 하나에 해당한다. 논리 트랜잭션마다 TransactionStatus 객체가 하나씩 생긴다.

    스프링 레퍼런스 문서는 REQUIRED를 이렇게 설명한다. REQUIRED가 적용된 메서드마다 논리 트랜잭션 범위가 만들어지고, 각 범위는 롤백 전용 여부를 따로 정할 수 있지만, 표준 REQUIRED 동작에서는 이 범위들이 모두 같은 물리 트랜잭션에 대응된다. 그래서 안쪽 범위에서 설정한 롤백 전용 표시는 바깥 트랜잭션이 실제로 커밋될 수 있는지에 영향을 준다. 여기서 바로 두 가지 원칙이 나온다.

    이 장의 핵심

    여러 논리 트랜잭션이 하나의 물리 트랜잭션을 공유할 때, 모든 논리 트랜잭션이 커밋해야 물리 트랜잭션이 커밋된다. 그리고 논리 트랜잭션 하나라도 롤백하면 물리 트랜잭션은 롤백된다. 이를 실제로 집행하는 장치는 단순하다. 물리 트랜잭션을 처음 시작한 논리 트랜잭션(isNewTransaction()이 true인 것)만 실제 커밋·롤백을 실행하고, 나머지는 커밋 요청을 무시하고 롤백 요청은 "롤백 전용" 표시로 바꿔 남긴다.

    두 논리 트랜잭션이 하나의 물리 트랜잭션을 공유하고, 실제 커밋·롤백은 외부 논리 트랜잭션만 실행한다는 것을 보여 준다. 가로로 긴 타임라인 그림. 맨 아래에 굵은 파란 막대 하나가 왼쪽에서 오른쪽으로 길게 뻗어 있고 라벨은 "물리 트랜잭션 (conn0)". 막대 왼쪽 끝에 "setAutoCommit(false)", 오른쪽 끝에 "commit / rollback" 라벨. 그 위에 주황색 막대가 거의 같은 길이로 있고 라벨은 "외부 논리 트랜잭션", 옆에 작은 배지 "신규 트랜잭션". 주황 막대 위, 가운데 부분에만 짧은 초록 막대가 있고 라벨은 "내부 논리 트랜잭션", 옆에 작은 배지 "참여". 주황 막대의 양 끝에서 파란 막대 양 끝으로 굵은 화살표가 내려가고, 초록 막대 양 끝에서는 점선 화살표가 내려가다 중간에서 끊겨 있으며 그 옆에 "실제 DB 호출 없음" 라벨. 흰 배경, 평면적인 다이어그램 스타일. 내부 논리 트랜잭션은 물리 트랜잭션에 참여만 한다. 실제 commit/rollback은 처음 시작한 외부 논리 트랜잭션만 호출한다.
    일상에서 가져온 비유단체 예약과 총무

    팀 회식을 식당에 단체로 예약한다고 하자. 예약 전화를 처음 건 총무만 식당에 "확정"이나 "취소"를 통보할 수 있다. 중간에 합류한 팀원은 예약을 새로 하지 않고 총무의 예약에 이름만 올린다. 팀원이 "좋아요"라고 하면 아무 일도 일어나지 않고(확정은 총무가 한다), 팀원이 "이 예약은 취소해야 해요"라고 하면 예약 장부에 취소 메모를 붙인다. 마지막에 총무가 확정하려고 장부를 펼쳤다가 메모를 보면, 예약을 취소하고 "확정하려 했지만 취소됐다"고 알린다. 이 비유가 깨지는 지점도 있다. 실제 회식은 일부만 빠질 수 있지만 물리 트랜잭션은 전부 커밋되거나 전부 롤백될 뿐이다. 그리고 REQUIRED에서는 한번 붙은 취소 메모를 팀원이 다시 뗄 방법이 없다.

    한 층 아래: "이미 트랜잭션이 있다"는 어떻게 판단하는가

    두 번째 getTransaction()이 "기존 트랜잭션이 있다"고 판단하려면 첫 번째 호출이 무언가를 어딘가에 남겨 두어야 한다. 그 장소가 TransactionSynchronizationManager다. 이 클래스는 여러 개의 ThreadLocal을 정적 필드로 가지고 있는데, 그중 핵심은 resources라는 이름의 ThreadLocal>다. 키는 리소스 팩토리(JDBC라면 DataSource 객체)이고, 값은 그 리소스로 얻은 커넥션을 담은 ConnectionHolder다. 같은 클래스에 현재 트랜잭션 이름, 읽기 전용 여부, 격리 수준, "실제 트랜잭션이 활성인가"를 담는 ThreadLocal도 따로 있다.

    AbstractPlatformTransactionManager.getTransaction()은 final 메서드이고, 구체적인 일은 하위 클래스가 구현하는 템플릿 메서드에 맡긴다. 템플릿 메서드 패턴(template method pattern)이다. DataSourceTransactionManager의 구현을 따라가면 판단 과정이 그대로 보인다.

    이 구조에서 몇 가지 결론이 바로 나온다. 첫째, 트랜잭션은 스레드에 묶인다. 같은 트랜잭션 안에서 새 스레드를 만들어 리포지토리를 호출하면, 그 스레드의 맵은 비어 있으므로 기존 트랜잭션을 보지 못한다. 둘째, 트랜잭션은 데이터소스별로 묶인다. 맵의 키가 DataSource 객체이므로 데이터소스가 둘이면 각각 따로 홀더가 생기고, 한쪽 트랜잭션 매니저는 다른 쪽 트랜잭션을 "기존 트랜잭션"으로 인식하지 않는다. 셋째, 커넥션을 쥐고 있는 주체는 TransactionStatus가 아니라 스레드 로컬에 묶인 홀더다. 상태 객체는 그 홀더를 가리키는 트랜잭션 객체를 들고 있을 뿐이다. 이 셋째 사실이 뒤에서 rollback-only 표시가 어디에 저장되는지를 이해하는 열쇠가 된다.

    그리고 JdbcTemplate 같은 데이터 접근 코드가 트랜잭션 매니저와 같은 커넥션을 쓰는 이유도 여기에 있다. JdbcTemplate은 DataSourceUtils.getConnection(dataSource)로 커넥션을 얻는데, 이 메서드는 먼저 같은 맵에서 그 데이터소스의 홀더를 찾고, 있으면 거기 든 커넥션을 돌려준다. 트랜잭션 매니저가 맵에 넣어 둔 커넥션을 데이터 접근 코드가 같은 키로 꺼내 쓰는 구조라서, 둘은 서로의 존재를 직접 알지 못하면서도 같은 물리 트랜잭션 안에서 일한다. 02회에서 테스트의 트랜잭션 롤백이 리포지토리의 SQL까지 되돌릴 수 있었던 것도 같은 원리다.

    이 템플릿 메서드 목록, 즉 doGetTransaction, isExistingTransaction, doBegin, doSuspend, doResume, doCommit, doRollback, doSetRollbackOnly, doCleanupAfterCompletion을 JpaTransactionManager나 JtaTransactionManager도 각자의 방식으로 구현한다. 전파 규칙 자체는 공통 부모인 AbstractPlatformTransactionManager에 한 번만 구현되어 있으므로, JDBC로 이해한 전파 동작은 JPA에서도 그대로 성립한다. 다만 보류(suspend)나 세이브포인트처럼 하위 클래스의 능력에 기대는 부분은 매니저마다 지원 범위가 다르다.

    전파 예제: 외부도 커밋, 내부도 커밋

    이제 두 트랜잭션을 겹친다. 외부 트랜잭션을 시작해 한 행을 넣고, 외부를 끝내기 전에 내부 트랜잭션을 시작해 또 한 행을 넣는다. 그리고 내부, 외부 순서로 커밋한다. 이 순서는 @Transactional 메서드가 다른 @Transactional 메서드를 호출할 때 프록시가 만드는 순서와 같다. 안쪽 메서드가 먼저 끝나므로 안쪽의 commit()이 먼저 불린다.

    static void innerCommitOuterCommit() {
    TransactionStatus outer = tm.getTransaction(new DefaultTransactionDefinition());
    log("outer.isNewTransaction()=" + outer.isNewTransaction() + " conn=" + DataSourceUtils.getConnection(ds));
    insert("outer");

    log("inner.isNewTransaction()=" + inner.isNewTransaction() + " conn=" + DataSourceUtils.getConnection(ds));
    insert("inner");

    log("inner commit");
    tm.commit(inner);
    log("outer commit");
    tm.commit(outer);
    log("count=" + count());
}

    가장 중요한 관찰은 >>> inner commit 다음에 트랜잭션 매니저 로그가 한 줄도 없다는 점이다. 내부 상태 객체의 isNewTransaction()은 false였다. AbstractPlatformTransactionManager.processCommit()은 세이브포인트가 있으면 세이브포인트를 해제하고, 신규 트랜잭션이면 doCommit()을 부르며, 둘 다 아니면 (뒤에서 볼 rollback-only 검사 외에는) 아무것도 하지 않는다. 그래서 내부 커밋은 상태 객체를 "완료"로 표시하고 정리 작업만 한 채 돌아온다. 실제 Connection.commit()은 외부 커밋에서 단 한 번 일어났고, 그 결과 두 행이 함께 확정되어 count=2가 나왔다.

    6외부 commit()conn0 홀더 해제con.commit(), 두 INSERT 확정, 오토커밋 복원 후 반납

    결과는 앞 절의 표를 이해했다면 예상할 수 있다. 내부 커밋은 데이터베이스에 아무 일도 하지 않았으므로 두 INSERT는 외부 롤백 시점까지 미확정 상태로 남아 있었다. 외부 상태 객체는 isNewTransaction()이 true이므로 processRollback()은 doRollback()을 불러 con.rollback()을 실행하고, 데이터베이스는 이 트랜잭션이 만든 변경을 전부 되돌린다. 그래서 count=0이다. "내부에서 넣은 행"과 "외부에서 넣은 행"이라는 구분은 스프링 쪽의 이야기일 뿐, 데이터베이스는 같은 트랜잭션이 넣은 두 행으로만 안다.

    데이터베이스 엔진 쪽에서 보면 이것은 아주 평범한 롤백이다. MySQL InnoDB를 예로 들면, 트랜잭션이 행을 바꿀 때마다 엔진은 그 변경을 되돌리는 방법을 언두 로그(undo log) 레코드로 남겨 두고, 롤백하면 이 기록을 이용해 변경을 취소한다. 엔진은 그 변경이 자바의 어느 메서드에서 왔는지 알 방법도, 알 필요도 없다. 스프링의 "중첩된 트랜잭션"이 데이터베이스 입장에서는 그냥 SQL 여러 개가 실행된 트랜잭션 하나라는 사실을 다시 확인할 수 있다.

    이 시나리오는 원칙 하나를 보여 준다. 내부 논리 트랜잭션의 커밋은 "내 쪽 작업은 문제없다"는 의사 표시일 뿐, 결과를 확정할 권한이 없다. 확정 권한은 물리 트랜잭션을 연 외부에만 있다. 그래서 외부가 롤백을 결정하면 내부의 의사와 관계없이 모든 변경이 사라진다. 이것은 결함이 아니라 원자성(atomicity)을 지키기 위한 설계다. 주문 저장과 재고 차감처럼 함께 성공하거나 함께 실패해야 하는 작업을 하나의 트랜잭션으로 묶으려고 REQUIRED를 기본값으로 둔 것이다.

    내부 롤백: rollback-only 마크와 UnexpectedRollbackException

    마지막 조합인 "내부 롤백, 외부 커밋"이 가장 까다롭다. 내부는 물리 트랜잭션을 소유하지 않으므로 con.rollback()을 부를 권한이 없다. 그렇다고 롤백 요청을 무시하면 "하나라도 롤백하면 전체가 롤백된다"는 원칙이 깨진다. 스프링은 이 문제를 표시로 해결한다. 내부는 지금 롤백하는 대신 "이 물리 트랜잭션은 롤백만 가능하다"는 표시를 남기고, 외부가 커밋하려 할 때 그 표시를 확인한다.

    static void innerRollbackOuterCommit() {

    내부 롤백에서 나온 두 줄부터 보자. processRollback()은 상태 객체를 세 갈래로 나눈다. 세이브포인트가 있으면 세이브포인트로 롤백하고, 신규 트랜잭션이면 doRollback()을 부르며, 그 외(기존 트랜잭션에 참여한 경우)에는 isLocalRollbackOnly()이거나 isGlobalRollbackOnParticipationFailure()가 참일 때 doSetRollbackOnly()를 부른다. globalRollbackOnParticipationFailure의 기본값은 true이므로 첫 줄 Participating transaction failed - marking existing transaction as rollback-only가 찍혔다. 두 번째 줄은 DataSourceTransactionManager.doSetRollbackOnly()가 남긴 것으로, 표시가 커넥션 쪽에 붙는다는 것을 문구에서부터 드러낸다.

    실제로 표시가 저장되는 곳은 ConnectionHolder다. doSetRollbackOnly()는 트랜잭션 객체의 setRollbackOnly()를 부르고, 그것은 다시 getConnectionHolder().setRollbackOnly()를 부른다. ConnectionHolder의 부모 클래스 ResourceHolderSupport에 있는 rollbackOnly 필드가 true가 되는 것이다. 앞에서 커넥션을 쥔 주체는 상태 객체가 아니라 스레드 로컬에 묶인 홀더라고 했다. 외부와 내부의 상태 객체는 서로 다른 객체지만 같은 홀더를 가리키므로, 내부가 홀더에 붙인 표시를 외부도 그대로 본다. 출력에서 outer.isRollbackOnly()=true가 나온 이유다.

    여기서 TransactionStatus의 롤백 전용 판단이 두 갈래라는 것을 짚어야 한다. AbstractTransactionStatus.isRollbackOnly()는 isLocalRollbackOnly() || isGlobalRollbackOnly()를 돌려준다. 로컬(local) 표시는 상태 객체 자신의 필드로, 그 상태 객체에 setRollbackOnly()를 직접 부를 때 켜진다. 전역(global) 표시는 상태 객체가 가리키는 트랜잭션 객체가 판단하는데, JDBC에서는 결국 홀더의 rollbackOnly 필드다. 외부 상태 객체의 로컬 표시는 꺼져 있지만 전역 표시가 켜져 있으므로 isRollbackOnly()는 true다.

    이제 외부 커밋이다. commit()의 앞부분은 다음과 같다(Spring Framework 소스에서 발췌).

    DefaultTransactionStatus defStatus = (DefaultTransactionStatus) status;
if (defStatus.isLocalRollbackOnly()) {
    // "Transactional code has requested rollback"
    processRollback(defStatus, false);
    return;
}

if (!shouldCommitOnGlobalRollbackOnly() && defStatus.isGlobalRollbackOnly()) {
    // "Global transaction is marked as rollback-only but transactional code requested commit"
    processRollback(defStatus, true);
    return;
}

processCommit(defStatus);

    shouldCommitOnGlobalRollbackOnly()는 기본 구현이 false를 돌려주고 DataSourceTransactionManager는 이를 재정의하지 않는다. 외부 상태 객체의 전역 표시가 켜져 있으므로 두 번째 if로 들어가고, 로그에 Global transaction is marked as rollback-only but transactional code requested commit이 찍힌다. 호출자는 커밋을 요청했지만 매니저는 processRollback(defStatus, true)를 부른다. 두 번째 인자 true가 "예상치 못한 롤백(unexpected)"이라는 뜻이다. 외부 상태 객체는 신규 트랜잭션이므로 실제로 con.rollback()이 실행되고, 커넥션이 반납된 뒤 마지막에 UnexpectedRollbackException이 던져진다. 예외 메시지는 Transaction rolled back because it has been marked as rollback-only다.

    내부 롤백이 공유된 ConnectionHolder에 표시를 남기고, 외부 커밋이 그 표시를 보고 실제 롤백 후 예외를 던지는 순서를 보여 준다. 세로 생명선 네 개가 있는 시퀀스 다이어그램. 왼쪽부터 "외부 로직", "내부 로직", "트랜잭션 매니저", "ConnectionHolder (conn0)". 1) "내부 로직"에서 "트랜잭션 매니저"로 화살표 "rollback(inner)". 2) "트랜잭션 매니저"에서 "ConnectionHolder (conn0)"로 화살표 "rollbackOnly = true", 홀더 옆에 빨간 깃발 아이콘. 3) "외부 로직"에서 "트랜잭션 매니저"로 화살표 "commit(outer)". 4) "트랜잭션 매니저"에서 홀더로 점선 화살표 "표시 확인". 5) "트랜잭션 매니저"에서 홀더로 화살표 "con.rollback()". 6) "트랜잭션 매니저"에서 "외부 로직"으로 빨간 화살표 "UnexpectedRollbackException". 흰 배경, 단순한 선과 상자, 한국어 라벨은 정확히 위 문구. rollback-only 표시는 내부 상태 객체가 아니라 두 논리 트랜잭션이 공유하는 ConnectionHolder에 붙는다.

    왜 조용히 롤백하고 끝내지 않고 예외를 던질까? 스프링 레퍼런스 문서의 설명은 이렇다. 안쪽 범위가 롤백 전용 표시를 했을 때, 바깥은 스스로 롤백을 결정한 적이 없으므로 그 롤백은 바깥 입장에서 예상하지 못한 일이다. 그래서 이 시점에 UnexpectedRollbackException을 던지며, 이는 트랜잭션을 호출한 쪽이 실제로는 커밋되지 않았는데 커밋되었다고 잘못 믿는 일이 없게 하려는 의도된 동작이다. 만약 예외 없이 commit()이 정상 반환된다면, 외부 로직은 "주문이 완료되었다"는 응답을 보내거나 후속 작업을 진행할 것이다. 데이터는 없는데 성공 응답이 나가는, 가장 찾기 어려운 종류의 버그가 된다.

    예외의 시점도 정확히 이해해 두자. 로그를 보면 Releasing JDBC Connection이 예외보다 먼저 찍혔다. 즉 UnexpectedRollbackException을 받았을 때는 롤백이 이미 끝났고 커넥션도 풀로 돌아간 상태다. 이 예외는 "롤백에 실패했다"는 뜻이 아니라 "네가 요청한 커밋 대신 롤백이 일어났다"는 통지다. 출력의 outer.isCompleted()=true도 같은 이야기를 한다. 외부 상태 객체는 완료되었으므로 이 예외를 잡은 뒤 tm.rollback(outer)를 다시 부르면 안 된다. 완료된 상태 객체로 commit()이나 rollback()을 다시 부르면 IllegalTransactionStateException이 "Transaction is already completed - do not call commit or rollback more than once per transaction"라는 메시지와 함께 던져진다.

    로컬 rollback-only: setRollbackOnly()를 직접 부르는 경우

    롤백 전용 표시를 켜는 또 다른 길은 상태 객체에 setRollbackOnly()를 직접 부르는 것이다. 예외를 던지지 않고 "이 트랜잭션은 롤백해야 한다"고만 알리고 싶을 때 쓴다. 내부 상태 객체에 이 메서드를 부르고 내부를 커밋하면 어떻게 될까?

    static void innerSetRollbackOnly() {
    TransactionStatus outer = tm.getTransaction(new DefaultTransactionDefinition());
    TransactionStatus inner = tm.getTransaction(new DefaultTransactionDefinition());
    inner.setRollbackOnly();
    log("inner commit after setRollbackOnly");
    tm.commit(inner);
    log("outer.isRollbackOnly()=" + outer.isRollbackOnly());
    try {
        tm.commit(outer);
    } catch (Exception e) {
        log("caught " + e.getClass().getSimpleName() + ": " + e.getMessage());

    표시를 남기지 않게 할 수는 없나

    AbstractPlatformTransactionManager에는 setGlobalRollbackOnParticipationFailure(false)라는 설정이 있다. 이것을 끄면 참여 중인 트랜잭션이 rollback()을 요청해도 표시를 붙이지 않고 Participating transaction failed - letting transaction originator decide on rollback을 찍은 뒤 결정을 외부에 맡긴다. 하지만 이 설정의 Javadoc은 두 가지를 경고한다. 하나는 이 방식이 데이터 접근 실패 뒤에도 모든 참여 리소스가 커밋을 향해 계속 진행할 수 있을 때만 성립하며, Hibernate 세션이나 JDBC의 INSERT/UPDATE/DELETE 연속 실행은 일반적으로 그렇지 않다는 것이다. 다른 하나는 이 설정이 상태 객체에 setRollbackOnly()를 명시적으로 부른 경우에는 적용되지 않는다는 것이다. Javadoc은 하위 트랜잭션의 실패를 처리하는 권장 방법으로 이 설정 대신 NESTED, 즉 세이브포인트를 제시한다. 실무에서 이 플래그를 끄는 경우는 드물고, 끄더라도 그 의미를 정확히 이해한 경우여야 한다.

    REQUIRES_NEW: 기존 트랜잭션을 보류하고 새 물리 트랜잭션을 연다

    내부의 실패가 외부까지 끌고 가지 않게 하고 싶을 때가 있다. 예를 들어 처리 실패 이력을 남기는 작업은 본 작업이 롤백되더라도 남아야 하고, 반대로 이력 저장이 실패했다고 본 작업까지 롤백되면 곤란하다. 이럴 때 쓰는 것이 PROPAGATION_REQUIRES_NEW다. 레퍼런스 문서는 이 옵션이 영향을 받는 각 트랜잭션 범위마다 항상 독립된 물리 트랜잭션을 쓰며 외부 범위의 기존 트랜잭션에 절대 참여하지 않는다고 설명한다.

    보류(suspend)는 실제로 무엇을 하는가

    "보류"라는 말은 거창하지만, 소스를 보면 스레드 로컬 맵에서 홀더를 빼서 다른 곳에 들고 있는 것이 전부다. handleExistingTransaction()이 REQUIRES_NEW를 만나면 suspend(transaction)를 부른다. 이 메서드는 먼저 현재 스레드에 등록된 트랜잭션 동기화(synchronization) 콜백들을 떼어 내고, doSuspend()를 부른 뒤, 현재 트랜잭션의 이름, 읽기 전용 여부, 격리 수준, 실제 활성 여부를 스레드 로컬에서 읽어 비운다. DataSourceTransactionManager.doSuspend()는 트랜잭션 객체의 홀더 참조를 null로 바꾸고 TransactionSynchronizationManager.unbindResource(dataSource)로 맵에서 conn0 홀더를 꺼내 돌려준다. 이렇게 모은 것이 SuspendedResourcesHolder 객체로 묶여 새 상태 객체 안에 저장된다.

    맵이 비었으니 이어지는 doBegin()은 앞에서 본 신규 트랜잭션 시작과 똑같이 풀에서 새 커넥션을 빌리고 새 홀더를 맵에 넣는다. 이 사이에 실행되는 JdbcTemplate 코드는 맵에서 conn1 홀더를 찾으므로 자연스럽게 새 트랜잭션에서 실행된다. 내부가 끝나면 cleanupAfterCompletion()이 신규 트랜잭션의 정리(conn1 홀더를 맵에서 빼고 오토커밋 복원, 반납)를 한 뒤, 상태 객체에 보류된 리소스가 있으면 resume()을 부른다. resume()은 doResume()을 불러 bindResource(dataSource, 보류했던 홀더)로 conn0 홀더를 다시 맵에 넣고, 보류했던 이름·읽기 전용·격리 수준·동기화 콜백도 되돌린다. 보류 중이던 conn0의 데이터베이스 트랜잭션은 그 시간 동안 아무것도 하지 않았을 뿐 계속 열려 있었다.

    REQUIRES_NEW에서 내부가 커밋하는 경우도 따져 보자. 이때 내부는 신규 트랜잭션이므로 conn1에서 실제 con.commit()이 일어난다. 그 뒤 외부가 롤백하더라도 이미 커밋된 내부 변경은 되돌릴 수 없다. 데이터베이스 입장에서 두 트랜잭션은 서로 관계가 없기 때문이다. 이 성질이 이력 저장 같은 용도에서는 원하는 바지만, 함께 성공하거나 함께 실패해야 하는 작업에 REQUIRES_NEW를 쓰면 원자성이 깨진다. 내부 커밋이 외부보다 먼저 일어나므로, 외부가 나중에 실패하면 "내부만 반영된" 상태가 남는다.

    대가 1: 커넥션 풀 고갈

    REQUIRES_NEW는 외부 커넥션을 반납하지 않은 채 커넥션을 하나 더 빌린다. 레퍼런스 문서는 이것이 커넥션 풀 고갈로 이어질 수 있고, 여러 스레드가 외부 트랜잭션을 쥔 채 내부 트랜잭션용 커넥션을 기다리는데 풀이 더 내줄 커넥션이 없으면 교착 상태(deadlock)에 빠질 수 있다고 경고한다. 그리고 커넥션 풀 크기가 동시 스레드 수보다 최소 1 이상 크지 않으면 REQUIRES_NEW를 쓰지 말라고 권한다. 풀 크기를 1로 줄이면 이 상황을 스레드 하나로도 재현할 수 있다.

    // main에서 ds.setMaximumPoolSize(1)로 바꾸고 실행
static void poolExhaustion() {
    TransactionStatus outer = tm.getTransaction(new DefaultTransactionDefinition());
    try {
        tm.getTransaction(def(TransactionDefinition.PROPAGATION_REQUIRES_NEW));
    } catch (Exception e) {
        log(e.getClass().getName() + ": " + e.getMessage());
        log("cause: " + e.getCause().getClass().getName() + ": " + e.getCause().getMessage());
    }
    log("still outer actualActive=" + TransactionSynchronizationManager.isActualTransactionActive());
    tm.rollback(outer);
}

    풀에 커넥션이 하나뿐이고 그것을 외부가 쥐고 있으므로, 내부의 getConnection()은 connectionTimeout으로 설정한 1초 동안 기다리다 실패했다. HikariCP 문서에 따르면 풀이 maximumPoolSize에 도달했고 유휴 커넥션이 없으면 getConnection()은 최대 connectionTimeout 밀리초 동안 블록된 뒤 타임아웃된다. doBegin()은 이 예외를 CannotCreateTransactionException으로 감싸 던지고, handleExistingTransaction()은 시작 실패 시 resumeAfterBeginException()으로 보류했던 외부 트랜잭션을 되돌려 놓는다. 그래서 마지막 줄에서 외부 트랜잭션이 여전히 활성이다.

    스레드 하나일 때는 타임아웃 뒤 예외로 끝나지만, 운영 환경에서는 더 나쁘게 번진다. HikariCP의 maximumPoolSize 기본값은 10이다. 요청 10개가 동시에 들어와 각자 외부 트랜잭션으로 커넥션 10개를 모두 잡고, 각자 REQUIRES_NEW 구간에 들어가 11번째 커넥션을 기다린다고 하자. 아무도 커넥션을 반납하지 않으므로 모든 요청이 타임아웃까지 멈추고, 그 사이 들어온 다른 요청들도 커넥션을 얻지 못한다. 평소에는 멀쩡하다가 트래픽이 몰릴 때만 전체가 멈추는 장애의 전형적인 모양이다. REQUIRES_NEW를 쓰는 경로가 있다면 "한 요청이 동시에 최대 몇 개의 커넥션을 쥐는가"를 세어 풀 크기를 정해야 한다.

    대가 2: 같은 행을 건드리면 스스로를 기다린다

    두 물리 트랜잭션은 데이터베이스 입장에서 서로 남남이므로 잠금(lock)도 서로를 막는다. 외부 트랜잭션이 어떤 행을 UPDATE해 행 잠금을 쥐고 있는 상태에서, REQUIRES_NEW 내부 트랜잭션이 같은 행을 UPDATE하려 하면 내부는 외부의 잠금이 풀리기를 기다린다. 그런데 외부 트랜잭션은 같은 스레드가 내부를 끝내야 다음으로 진행할 수 있으므로 영원히 잠금을 풀지 않는다. 데이터베이스 안에서 보면 기다리는 쪽은 내부 트랜잭션 하나뿐이고, 외부는 잠금을 기다리는 것이 아니라 애플리케이션 스레드 안에서 멈춰 있을 뿐이라서 잠금 대기 그래프에 순환이 생기지 않는다. 그래서 InnoDB의 교착 상태 감지에 걸리지 않고, 잠금 대기 시간 제한에 걸릴 때까지 기다리다 실패한다. REQUIRES_NEW로 분리한 작업은 외부가 이미 건드린 행을 다시 건드리지 않도록 설계해야 한다.

    다양한 전파 옵션

    지금까지 본 REQUIRED와 REQUIRES_NEW 외에 다섯 가지 옵션이 더 있다. 모든 옵션은 "현재 스레드에 기존 트랜잭션이 있는가"라는 하나의 질문에 대한 반응으로 정리할 수 있다. 다음 표는 AbstractPlatformTransactionManager의 getTransaction()과 handleExistingTransaction() 분기를 그대로 옮긴 것이다.

    옵션기존 트랜잭션 없음기존 트랜잭션 있음

"기존 트랜잭션 있음" 열에서 참여하는 것은 REQUIRED, SUPPORTS, MANDATORY 셋이고, 소스의 마지막 분기에 "regular participation in existing transaction"이라는 주석과 함께 묶여 있다.

    MANDATORY와 NEVER: 전제 조건을 검사한다

    두 옵션은 트랜잭션을 만들지 않고 전제 조건만 검사한다. MANDATORY는 "반드시 호출자의 트랜잭션 안에서 실행되어야 한다"는 계약이다. 단독으로 호출되면 데이터 일관성이 깨질 수 있는 메서드에 붙여, 누군가 트랜잭션 없이 호출하는 실수를 실행 시점에 바로 드러낸다. NEVER는 그 반대로, 트랜잭션 안에서 호출되면 안 되는 메서드(예를 들어 오래 걸리는 외부 호출)를 보호한다. 실행해 보면 메시지가 다음과 같다.

    >>> MANDATORY: IllegalTransactionStateException: No existing transaction found for transaction marked with propagation 'mandatory'
>>> NEVER: IllegalTransactionStateException: Existing transaction found for transaction marked with propagation 'never'

    SUPPORTS와 NOT_SUPPORTED: 트랜잭션 없이 실행한다는 것

    "트랜잭션 없이 실행한다"는 말의 실제 의미는 커넥션이 오토커밋 모드로 SQL을 실행한다는 것이다. SQL 하나하나가 실행되는 즉시 각자 커밋된다. 다음 실험은 SUPPORTS를 단독으로, NOT_SUPPORTED를 REQUIRED 안에서 써 본다.

    static void supportsAndNotSupported() {
    TransactionStatus sup = tm.getTransaction(def(TransactionDefinition.PROPAGATION_SUPPORTS));
    log("SUPPORTS alone: isNewTransaction=" + sup.isNewTransaction()
            + " actualActive=" + TransactionSynchronizationManager.isActualTransactionActive()
            + " syncActive=" + TransactionSynchronizationManager.isSynchronizationActive());
    insert("supports");
    tm.commit(sup);

    TransactionStatus outer = tm.getTransaction(new DefaultTransactionDefinition());
    TransactionStatus ns = tm.getTransaction(def(TransactionDefinition.PROPAGATION_NOT_SUPPORTED));
    log("NOT_SUPPORTED inside: actualActive=" + TransactionSynchronizationManager.isActualTransactionActive());
    insert("not_supported");
    tm.commit(ns);
    log("after NOT_SUPPORTED: actualActive=" + TransactionSynchronizationManager.isActualTransactionActive());
    tm.rollback(outer);
    log("rows=" + jdbc.queryForList("select name from item", String.class));
}

    SUPPORTS 단독 실행에서는 트랜잭션 매니저 로그가 하나도 없다. 커넥션을 빌리지도, 오토커밋을 끄지도 않았기 때문이다. 상태 객체는 트랜잭션 객체 없이(null로) 만들어지므로 isNewTransaction()은 false다. 이 메서드는 hasTransaction() && newTransaction을 돌려주기 때문이다. 흥미로운 것은 syncActive=true다. 트랜잭션 매니저의 동기화 설정 기본값이 SYNCHRONIZATION_ALWAYS라서, 실제 트랜잭션이 없어도 이 범위에 대한 트랜잭션 동기화는 켜진다. Propagation.SUPPORTS의 Javadoc도 이 점을 짚는다. 동기화를 쓰는 트랜잭션 매니저에서 SUPPORTS는 트랜잭션이 전혀 없는 것과 조금 다르며, 동기화가 적용되는 범위를 정의하므로 그 범위 동안 같은 리소스(JDBC 커넥션, Hibernate 세션 등)가 공유된다. 그래도 커넥션은 오토커밋 상태이므로 insert("supports")는 실행 즉시 커밋되었다.

    NOT_SUPPORTED는 Suspending current transaction으로 외부 트랜잭션을 보류한다. REQUIRES_NEW의 로그와 달리 뒤에 "creating new transaction"이 붙지 않고, 커넥션도 새로 빌렸다는 로그가 없다. 보류된 동안 actualActive=false이고, 이때 실행된 insert("not_supported")는 JdbcTemplate이 풀에서 따로 얻은 다른 커넥션(외부가 conn0을 쥐고 있으므로)에서 오토커밋으로 실행되었다. 그래서 외부 트랜잭션이 롤백되었는데도 not_supported 행이 남았다. 외부는 아무 행도 넣지 않았으므로 롤백할 것이 없었고, 최종 결과는 두 행이다. NOT_SUPPORTED 구간의 작업은 외부 트랜잭션의 원자성 바깥에 있다는 것을 꼭 기억하자. 또한 이 구간에서도 외부 커넥션은 반납되지 않고 보류된 채 남으므로, 커넥션을 하나 더 쓴다는 점은 REQUIRES_NEW와 같다.

    NESTED: 하나의 물리 트랜잭션 안의 세이브포인트

    NESTED는 기존 트랜잭션이 있을 때 새 커넥션을 빌리지 않고, 같은 커넥션에 JDBC 세이브포인트를 만든다. 레퍼런스 문서의 표현으로는 여러 세이브포인트를 가진 하나의 물리 트랜잭션을 쓰며, 내부 범위가 자기 범위만 롤백해도 외부는 일부 작업이 롤백된 상태로 물리 트랜잭션을 계속 진행할 수 있다. 그리고 보통 JDBC 세이브포인트에 대응하므로 JDBC 리소스 트랜잭션에서만 동작한다.

    static void nestedInnerRollback() {
    TransactionStatus outer = tm.getTransaction(new DefaultTransactionDefinition());
    insert("outer");

    TransactionStatus inner = tm.getTransaction(def(TransactionDefinition.PROPAGATION_NESTED));

    내부 getTransaction()은 Creating nested transaction을 찍고, 커넥션을 새로 빌리지 않았다. 상태 객체는 isNewTransaction()=false, hasSavepoint()=true다. 이때 ConnectionHolder.createSavepoint()는 카운터를 하나 올려 "SAVEPOINT_" + 카운터 이름으로 Connection.setSavepoint(String)을 부른다. 내부 롤백에서는 processRollback()의 첫 분기, 즉 세이브포인트 분기를 타서 Rolling back transaction to savepoint를 찍고 Connection.rollback(Savepoint)을 부른다. 이어서 홀더의 rollback-only 표시를 초기화(resetRollbackOnly())한다. 그래서 외부의 isRollbackOnly()는 false이고, 외부 커밋은 정상적으로 진행되어 outer 행만 남았다. REQUIRES_NEW 실험과 결과는 같지만, 커넥션은 conn0 하나뿐이었다.

    결과가 같다고 의미까지 같지는 않다. NESTED 내부가 커밋하면 processCommit()의 세이브포인트 분기에서 Releasing transaction savepoint를 찍고 세이브포인트를 해제할 뿐, 실제 커밋은 일어나지 않는다. 내부 변경은 외부가 커밋할 때 함께 확정되고, 외부가 롤백하면 함께 사라진다. 정리하면 NESTED에서는 내부가 외부 없이 단독으로 확정될 수 없고 외부의 결정을 따르지만, 내부의 실패는 자기 범위 안에서 되돌릴 수 있다. REQUIRES_NEW는 내부가 외부와 무관하게 확정되거나 롤백된다. 이력처럼 "외부가 실패해도 남아야 하는" 작업에는 NESTED가 맞지 않는다.

    세이브포인트가 데이터베이스에서 무엇을 하는지도 알아 두자. MySQL 레퍼런스 매뉴얼에 따르면 InnoDB는 SAVEPOINT, ROLLBACK TO SAVEPOINT, RELEASE SAVEPOINT 문을 지원한다. ROLLBACK TO SAVEPOINT는 트랜잭션을 끝내지 않고, 세이브포인트 이후 이 트랜잭션이 행에 가한 변경을 되돌린다. 다만 매뉴얼은 InnoDB가 세이브포인트 이후 메모리에 저장된 행 잠금은 풀지 않는다고 명시한다(새로 INSERT한 행의 잠금은 행에 저장된 트랜잭션 ID로 표현되므로 언두 과정에서 풀린다). 즉 NESTED 내부를 롤백해도 그 안에서 UPDATE한 행의 잠금은 외부 트랜잭션이 끝날 때까지 남아 있을 수 있다. 그리고 COMMIT이나 세이브포인트를 지정하지 않은 ROLLBACK을 실행하면 현재 트랜잭션의 모든 세이브포인트가 삭제된다.

    NESTED는 트랜잭션 매니저가 지원해야 쓸 수 있다. AbstractPlatformTransactionManager의 nestedTransactionAllowed 기본값은 false이고, 허용되지 않은 매니저에서 NESTED를 기존 트랜잭션 안에서 요청하면 NestedTransactionNotSupportedException이 던져진다. DataSourceTransactionManager는 생성자에서 이 값을 true로 바꾸므로 바로 쓸 수 있다. JpaTransactionManager는 버전에 따라 다르다. 6.2.x에서는 기본값이 true이지만 Javadoc이 "중첩 트랜잭션은 JDBC 커넥션에만 적용되고 JPA EntityManager와 캐시된 엔티티 객체에는 적용되지 않으므로 오히려 false여야 한다"고 적고 있고, 7.0부터는 기본값이 false로 바뀌었다. JPA 자체는 중첩 트랜잭션을 지원하지 않으므로, 세이브포인트로 되돌려도 영속성 컨텍스트에 올라간 엔티티 상태는 되돌아가지 않는다. JPA 환경에서 NESTED를 실패 격리 수단으로 기대하면 안 되는 이유다.

    격리 수준, 읽기 전용, 타임아웃은 새 트랜잭션에서만 적용된다

    TransactionDefinition에는 전파 외에도 격리 수준, 읽기 전용, 타임아웃이 들어 있다. 그런데 이 설정들은 물리 트랜잭션을 시작할 때, 즉 doBegin()에서 커넥션에 적용된다. doBegin()은 격리 수준과 읽기 전용을 DataSourceUtils.prepareConnectionForTransaction()으로 커넥션에 설정하고, 타임아웃을 홀더에 기록한다. 참여하는 트랜잭션은 doBegin()을 거치지 않으므로 이 설정이 적용될 기회가 없다. 레퍼런스 문서도 참여하는 트랜잭션은 기본적으로 외부 범위의 특성을 따르며, 자신의 격리 수준, 타임아웃, 읽기 전용 플래그를 조용히 무시한다고 설명한다.

    이 조용한 무시가 싫다면 트랜잭션 매니저의 validateExistingTransaction을 true로 켠다(기본값 false). 그러면 참여하려는 정의가 기본값이 아닌 격리 수준을 지정했는데 현재 트랜잭션의 격리 수준과 다르거나, 외부는 읽기 전용인데 내부가 읽기·쓰기를 요구하면 예외를 던진다. 위 출력에서 메시지 끝이 (unknown)인 것은 외부가 ISOLATION_DEFAULT로 시작해서 스레드 로컬에 격리 수준이 기록되지 않았기 때문이다. 외부가 기본값이면 내부가 어떤 격리 수준을 지정하든 "다르다"로 판정된다.

    @Transactional로 옮기면 같은 일이 일어난다

    지금까지의 실험은 트랜잭션 매니저를 손으로 불렀지만, @Transactional을 쓰면 프록시가 같은 호출을 대신한다. 07회에서 본 TransactionInterceptor는 메서드 호출 전에 애너테이션 속성으로 만든 정의를 넘겨 getTransaction()을 부르고, 메서드가 정상 반환하면 commit(), 롤백 규칙에 해당하는 예외가 나오면 rollback()을 부른다. 따라서 아래 코드에서 placeOrder()가 decrease()를 호출하면, 외부 논리 트랜잭션 안에서 내부 논리 트랜잭션이 시작되는 앞의 실험과 같은 상황이 된다.

    @Service
public class OrderService {
    private final StockService stockService;
    // ... 생성자 생략

    @Transactional
    public void placeOrder(long productId, int quantity) {
        // ... 주문 저장
        stockService.decrease(productId, quantity);   // 프록시를 거쳐 호출된다
    }
}

@Service
public class StockService {
    @Transactional   // propagation 기본값 REQUIRED → 외부 트랜잭션에 참여
    public void decrease(long productId, int quantity) {
        // ... 재고 차감, 재고가 부족하면 RuntimeException
    }
}

    decrease()가 런타임 예외를 던지면 그 프록시가 rollback()을 부르고, 참여 중인 트랜잭션이므로 홀더에 rollback-only 표시가 붙는다. 예외가 placeOrder()를 그대로 빠져나가면 외부 프록시도 rollback()을 불러 전체가 롤백된다. 문제는 placeOrder()가 그 예외를 try-catch로 잡고 정상 반환할 때다. 외부 프록시는 commit()을 부르고, 앞의 실험처럼 UnexpectedRollbackException이 나온다. 예외를 잡았으니 복구했다고 생각했는데 전체가 롤백되는, 실무에서 자주 만나는 상황이다. 이것을 REQUIRES_NEW로 풀어내는 방법과 그때의 함정은 09회에서 다룬다.

    그리고 전파는 프록시를 거칠 때만 일어난다는 점도 07회의 내부 호출 문제와 연결해 기억하자. 같은 클래스 안에서 this.decrease()처럼 호출하면 프록시를 거치지 않으므로 내부 메서드의 @Transactional은 아예 읽히지 않는다. 이때 propagation = REQUIRES_NEW를 붙여 두었어도 새 트랜잭션은 시작되지 않고, 내부 코드는 그냥 외부 트랜잭션 안에서 실행된다. 전파 옵션은 트랜잭션 매니저에 전달되는 인자이고, 그 인자를 전달하는 것은 프록시다.

    흔한 오해와 함정

    "내부 트랜잭션이 커밋되었으니 DB에 반영되었다." REQUIRED로 참여한 내부의 commit()은 데이터베이스에 아무 호출도 하지 않는다. 로그에 아무것도 찍히지 않는 것이 증거다. 이 오해는 "커밋"이라는 같은 단어가 논리 트랜잭션과 물리 트랜잭션 양쪽에 쓰이기 때문에 생긴다. 내부 메서드가 끝난 직후 다른 시스템에 "저장 완료" 메시지를 보내는 코드는 그 시점에 데이터가 확정되지 않았다는 사실을 무시한다. 커밋 이후에 해야 할 일은 트랜잭션 동기화의 afterCommit 콜백 같은 장치로 외부 트랜잭션의 실제 커밋 뒤에 실행해야 한다.

    "REQUIRED에서 내부 롤백은 내부 작업만 되돌린다." 내부는 되돌릴 권한이 없고, 표시를 남길 뿐이다. 그 표시는 공유 홀더에 붙으므로 결국 전체가 롤백된다. 부분 롤백이 필요하면 NESTED(JDBC 한정)나 REQUIRES_NEW를 검토해야 하며, 둘은 의미가 다르다.

    "UnexpectedRollbackException은 롤백이 실패했다는 뜻이다." 반대다. 롤백은 이미 성공적으로 끝났고 커넥션도 반납되었다. 이 예외는 호출자가 커밋을 요청했지만 실제로는 롤백되었다는 사실을 알리는 통지다. 따라서 이 예외를 잡아서 다시 롤백을 시도하거나 재시도를 무작정 반복할 것이 아니라, 왜 내부가 롤백을 요청했는지(어느 내부 메서드가 예외를 던졌고 누가 그것을 삼켰는지)를 찾아야 한다.

    "REQUIRES_NEW를 쓰면 안전하게 분리된다." 데이터 측면에서는 분리되지만 자원 측면에서는 더 많이 묶인다. 외부 커넥션을 쥔 채 커넥션을 하나 더 쓰므로 풀 크기 계산이 달라지고, 외부가 잠근 행을 내부가 건드리면 스스로를 기다린다. 또 내부가 먼저 커밋되므로, 외부가 나중에 실패하면 내부 결과만 남는다는 점을 업무 규칙이 허용하는지 확인해야 한다.

    "내부 메서드에 readOnly를 붙였으니 읽기 전용이다." 참여하는 트랜잭션에서는 무시된다. 읽기 전용 최적화나 격리 수준이 꼭 필요하다면 그 설정은 트랜잭션을 시작하는 바깥쪽 메서드에 붙여야 하고, 어긋난 선언을 잡고 싶다면 validateExistingTransaction을 켠다.

    "다른 스레드에서 실행해도 같은 트랜잭션이다." 트랜잭션은 스레드 로컬 맵에 묶여 있으므로, 새 스레드에서는 기존 트랜잭션이 보이지 않는다. 그 스레드에서 @Transactional 메서드를 부르면 REQUIRED라도 별개의 물리 트랜잭션이 시작되고, 원래 스레드의 롤백과 무관하게 커밋된다.

    정리: 로그 문구로 전파를 읽는다

    이 회차의 내용은 트랜잭션 매니저 로그의 몇 가지 문구로 압축할 수 있다. Creating new transaction과 Acquired Connection이 보이면 새 물리 트랜잭션이 시작된 것이다. Participating in existing transaction이 보이면 논리 트랜잭션 하나가 기존 물리 트랜잭션에 올라탄 것이고, 그 논리 트랜잭션의 커밋은 아무 로그도 남기지 않는다. 그 논리 트랜잭션의 롤백은 marking existing transaction as rollback-only로 나타나며, 이 문구를 본 뒤에 외부의 Global transaction is marked as rollback-only but transactional code requested commit이 나오면 곧 UnexpectedRollbackException이 따라온다. Suspending current transaction은 커넥션을 하나 더 쓰기 시작했다는 신호이고, Resuming suspended transaction은 원래 커넥션으로 돌아왔다는 신호다. Creating nested transaction과 Rolling back transaction to savepoint는 같은 커넥션 위의 세이브포인트다.

    원리로 정리하면 세 문장이다. 물리 트랜잭션은 커넥션 하나 위의 데이터베이스 트랜잭션이고, 스프링은 그것을 스레드 로컬 맵에 데이터소스 키로 묶어 둔다. 논리 트랜잭션은 그 위에 겹친 스프링의 범위이며, 물리 트랜잭션을 처음 연 논리 트랜잭션만 실제 커밋·롤백을 실행한다. 나머지 논리 트랜잭션의 롤백은 공유 홀더의 rollback-only 표시로 바뀌어 최종 결정에 반영된다. 다음 09회에서는 이 원리를 서비스·리포지토리 계층에 실제로 적용해, 일부 작업이 실패해도 나머지를 커밋하고 싶을 때 어떤 선택지가 있고 각각 어디서 깨지는지를 살펴본다.
    트랜잭션 전파
    이미 진행 중인 트랜잭션이 있을 때 새 트랜잭션 요청을 어떻게 처리할지 정하는 규칙이다. @Transactional의 기본값은 REQUIRED이며, 전파 규칙은 AbstractPlatformTransactionManager에 한 번 구현되어 모든 트랜잭션 매니저가 공유한다.
    물리 트랜잭션과 논리 트랜잭션
    물리 트랜잭션은 커넥션 위의 실제 DB 트랜잭션이고, 논리 트랜잭션은 getTransaction()부터 commit()/rollback()까지의 스프링 범위다. REQUIRED에서는 여러 논리 트랜잭션이 하나의 물리 트랜잭션을 공유한다.
    신규 트랜잭션(isNewTransaction)
    물리 트랜잭션을 처음 시작한 논리 트랜잭션만 true이며, 이것만 실제 con.commit()/con.rollback()을 실행한다. 참여한 논리 트랜잭션의 커밋은 아무 DB 호출도 하지 않는다.
    스레드 로컬 리소스 바인딩
    TransactionSynchronizationManager가 스레드별 맵에 데이터소스를 키로 ConnectionHolder를 넣어 두고, 트랜잭션 매니저와 JdbcTemplate이 같은 키로 꺼내 쓴다. 홀더가 있고 활성 상태이면 "기존 트랜잭션이 있다"고 판단한다.
    rollback-only 표시
    참여한 논리 트랜잭션이 롤백을 요청하면 공유 ConnectionHolder에 표시가 붙는다. 외부가 커밋을 요청하면 이 표시를 보고 실제로는 롤백한 뒤 UnexpectedRollbackException을 던진다.
    REQUIRES_NEW
    기존 홀더를 맵에서 빼서 보류하고 새 커넥션으로 독립된 물리 트랜잭션을 연다. 내부 결과가 외부와 무관하게 확정되지만, 요청 하나가 커넥션을 두 개 쥐므로 풀 고갈과 자기 잠금 대기의 위험이 있다.
    NESTED
    같은 커넥션에 JDBC 세이브포인트를 만들어 내부 실패만 되돌린다. 내부 커밋은 세이브포인트 해제일 뿐이라 외부 결정을 따르며, JPA의 영속성 컨텍스트 상태는 되돌리지 못한다.
    새 트랜잭션에서만 적용되는 속성
    격리 수준, 읽기 전용, 타임아웃은 doBegin()에서 커넥션에 적용되므로 참여하는 트랜잭션에서는 조용히 무시된다. validateExistingTransaction을 켜면 어긋난 선언이 예외가 된다.

    운영 중에 UnexpectedRollbackException이 로그에 찍혔다면, 그것은 데이터가 이미 롤백되었다는 확정 신호이고 원인은 그보다 앞에 있다. 같은 요청의 로그에서 Participating transaction failed - marking existing transaction as rollback-only를 찾고, 그 직전에 어느 메서드가 예외를 던졌으며 그 예외를 누가 catch로 삼켰는지를 거슬러 올라가야 한다. 대부분은 "부가 작업이 실패해도 본 작업은 커밋하고 싶어서" 예외를 잡았는데 부가 작업이 REQUIRED로 같은 물리 트랜잭션에 참여하고 있던 경우다. 이때 선택지는 부가 작업을 REQUIRES_NEW로 분리하거나, 트랜잭션 밖으로 빼거나, 실패를 예외가 아닌 반환값으로 다루도록 설계를 바꾸는 것이고, 어느 쪽이 맞는지는 부가 작업이 본 작업과 함께 롤백되어야 하는지에 달려 있다.

    REQUIRES_NEW를 도입할 때는 기능보다 자원을 먼저 계산한다. 그 경로를 지나는 요청 하나가 동시에 몇 개의 커넥션을 쥐는지 세고, 최대 동시 요청 수와 곱해 커넥션 풀 크기와 비교한다. 스프링 문서가 권하는 "동시 스레드 수보다 최소 1 큰 풀"은 REQUIRES_NEW가 한 단계일 때의 하한이고, REQUIRES_NEW 안에서 또 REQUIRES_NEW를 부르면 요구량은 더 커진다. 부하 테스트에서 커넥션 획득 타임아웃이 갑자기 몰려 나온다면, 쿼리가 느린 것이 아니라 커넥션을 쥔 채 커넥션을 기다리는 구조인지부터 의심해 볼 만하다.

    NESTED는 JDBC만 쓰는 코드에서 "배치 중 일부 행이 실패해도 나머지는 커밋"하는 요구를 커넥션 하나로 처리할 수 있는 유용한 도구다. 하지만 JPA를 쓰는 서비스에서는 세이브포인트로 DB를 되돌려도 영속성 컨텍스트에 남은 엔티티 상태가 DB와 어긋날 수 있고, Spring Framework 7.0부터는 JpaTransactionManager에서 기본으로 허용되지도 않는다. 또한 MySQL InnoDB에서는 세이브포인트로 롤백해도 그 사이 잡은 행 잠금이 남을 수 있으므로, 잠금 경합이 심한 테이블에서는 기대만큼 동시성이 좋아지지 않는다. 어떤 전파 옵션이든 결정 전에 DEBUG 로그로 실제 커넥션 사용과 커밋 지점을 한 번 확인하는 습관이 가장 싸고 확실한 검증이다.
  • 외부 트랜잭션(REQUIRED)을 시작하고, 내부 트랜잭션 A(REQUIRED)를 시작해 커밋한 뒤, 내부 트랜잭션 B(REQUIRED)를 시작해 롤백하고, 마지막으로 외부를 커밋한다. 트랜잭션 매니저가 남기는 로그 문구를 순서대로 적고, 외부 커밋 호출의 결과(정상 반환인지 예외인지, 어떤 예외인지)를 예측하라.
  • 위 1번에서 내부 트랜잭션 B만 REQUIRES_NEW로 바꾸면 결과가 어떻게 달라지는가? B가 쓰는 커넥션, B 롤백 시점의 DB 동작, 외부 커밋 결과를 각각 설명하라.
  • 커넥션 풀 크기가 5이고, 모든 요청이 REQUIRED 외부 트랜잭션 안에서 REQUIRES_NEW 메서드를 한 번 호출한다. 동시에 5개의 요청이 외부 트랜잭션을 시작한 직후 무슨 일이 일어나는지, 스레드 로컬 맵과 커넥션 풀의 상태를 그림으로 그려 설명하라. 풀 크기를 얼마로 늘려야 이 상황을 피할 수 있는가?
  • 외부 트랜잭션은 기본 설정(REQUIRED, 읽기·쓰기)으로 시작했고, 내부 메서드에 @Transactional(readOnly = true, propagation = Propagation.REQUIRED)가 붙어 있다. 내부 메서드 안에서 INSERT를 실행하면 실패하는가? 이유를 doBegin()과 참여 경로의 차이로 설명하라. 같은 설정에서 propagation만 REQUIRES_NEW로 바꾸면 어떻게 되는가?
  • JDBC만 쓰는 코드에서 외부 트랜잭션 안에 NESTED 내부 트랜잭션을 만들고, 내부에서 INSERT한 뒤 내부를 커밋하고, 외부를 롤백했다. 최종적으로 내부의 INSERT는 남는가? 같은 시나리오를 REQUIRES_NEW로 바꾸면 어떻게 되는가?
    •

    1번. 외부 시작에서 Creating new transaction, Acquired Connection, Switching ... to manual commit이 찍힌다. 내부 A 시작에서 Participating in existing transaction이 찍히고, A 커밋에서는 아무것도 찍히지 않는다. 내부 B 시작에서 다시 Participating in existing transaction, B 롤백에서 Participating transaction failed - marking existing transaction as rollback-only와 Setting JDBC transaction [...] rollback-only가 찍힌다. 외부 커밋에서는 Global transaction is marked as rollback-only but transactional code requested commit, Initiating transaction rollback, Rolling back JDBC transaction, Releasing JDBC Connection이 찍히고 UnexpectedRollbackException이 던져진다. A가 먼저 커밋했다는 사실은 아무 영향이 없다. A의 커밋은 DB 호출이 아니었고, B가 공유 홀더에 붙인 표시는 A의 커밋 이후에 붙었지만 외부 커밋 시점에 검사되기 때문이다.

    2번. B는 REQUIRES_NEW이므로 외부의 conn0 홀더를 보류하고 새 커넥션(실험 환경이라면 conn1)을 빌린다. B 롤백은 신규 트랜잭션의 롤백이므로 conn1에서 실제 con.rollback()이 실행되고, conn1이 반납된 뒤 conn0 홀더가 다시 바인딩된다. conn0의 홀더에는 표시가 붙지 않았으므로 외부 커밋은 정상적으로 conn0에서 con.commit()을 실행하고 예외 없이 반환한다. 외부와 A가 넣은 데이터는 커밋되고, B가 넣은 데이터만 사라진다.

    3번. 다섯 스레드가 각자 외부 트랜잭션으로 커넥션 다섯 개를 모두 빌려 각 스레드의 맵에 바인딩한다. 이어 각 스레드가 REQUIRES_NEW에서 자기 홀더를 보류하지만, 보류는 맵에서 빼서 들고 있는 것일 뿐 반납이 아니므로 풀의 활성 커넥션은 여전히 5개, 유휴는 0개다. 다섯 스레드가 모두 getConnection()에서 대기하고, 아무도 반납하지 않으므로 connectionTimeout이 지날 때까지 전부 멈춘 뒤 CannotCreateTransactionException(원인은 커넥션 획득 타임아웃)으로 실패한다. 동시 요청이 최대 5개라면 각 요청이 동시에 2개를 쥐므로 풀이 10 이상이면 이 경로만으로는 고갈되지 않는다. 문서의 "동시 스레드 수보다 최소 1 크게"는 모든 스레드가 외부 커넥션을 쥔 상태에서도 최소 한 스레드는 내부 커넥션을 얻어 진행하고 반납할 수 있게 하는 하한이다. 그 경우 스레드들이 차례로 진행되므로 교착은 피하지만 대기는 생긴다.

    4번. 실패하지 않는다. 읽기 전용 설정은 doBegin()에서 커넥션에 적용되는데, REQUIRED로 참여하는 내부 트랜잭션은 doBegin()을 거치지 않는다. 커넥션은 외부가 시작할 때의 읽기·쓰기 상태 그대로이고, 스레드의 현재 트랜잭션 읽기 전용 여부도 false로 남는다. 이 선언 불일치를 잡으려면 validateExistingTransaction을 켜야 하는데, 이 검사는 내부가 읽기 전용인 경우가 아니라 외부가 읽기 전용이고 내부가 읽기·쓰기를 요구하는 경우를 잡는다는 점에 주의한다. propagation을 REQUIRES_NEW로 바꾸면 새 커넥션에 대해 doBegin()이 실행되어 읽기 전용이 적용된다. 이때 INSERT가 실제로 거부되는지는 JDBC 드라이버와 DB가 읽기 전용 커넥션을 어떻게 처리하는지에 따라 다르다.

    5번. NESTED에서는 남지 않는다. 내부 커밋은 세이브포인트 해제(Releasing transaction savepoint)일 뿐 실제 커밋이 아니고, 내부 INSERT는 외부와 같은 물리 트랜잭션에 속해 있으므로 외부 롤백(con.rollback())과 함께 사라진다. REQUIRES_NEW로 바꾸면 내부는 별도 커넥션의 신규 트랜잭션이므로 내부 커밋 시점에 실제 con.commit()이 실행되어 확정되고, 이후 외부가 롤백해도 남는다. "실패를 격리"한다는 점은 비슷해 보여도, 내부 결과가 외부 결정을 따르는지 여부에서 두 옵션은 정반대다.

     외부 트랜잭션(REQUIRED) 안에서 내부 트랜잭션(REQUIRED)을 시작하고 내부를 커밋했다. 이 순간 데이터베이스에서 일어나는 일은? 내부에서 실행한 SQL만 부분 커밋된다 아무 일도 일어나지 않는다. 실제 커밋은 외부가 커밋할 때 한 번 일어난다 세이브포인트가 해제된다 내부와 외부의 SQL이 모두 커밋되고 외부 커밋은 아무 일도 하지 않는다 내부 상태 객체는 isNewTransaction()이 false이고 세이브포인트도 없으므로 processCommit()은 DB 호출을 하지 않는다. 실험 로그에서도 내부 커밋 시점에 아무 로그가 찍히지 않았다. 부분 커밋은 JDBC 트랜잭션에 존재하지 않고, 세이브포인트 해제는 NESTED의 동작이며, 물리 트랜잭션을 연 외부만 con.commit()을 부른다. REQUIRED로 참여한 내부 트랜잭션이 롤백한 뒤, 외부 TransactionStatus의 isRollbackOnly()가 true를 돌려주는 이유로 가장 정확한 것은? 내부 상태 객체가 외부 상태 객체의 필드를 직접 바꾸기 때문이다 내부 롤백이 실제로 con.rollback()을 호출해서 외부 트랜잭션이 끝났기 때문이다 표시가 두 논리 트랜잭션이 공유하는 ConnectionHolder에 붙고, 외부 상태 객체의 전역 rollback-only 판단이 그 홀더를 보기 때문이다 트랜잭션 매니저가 싱글톤이어서 매니저의 필드에 표시를 저장하기 때문이다 doSetRollbackOnly()는 트랜잭션 객체를 거쳐 ConnectionHolder.setRollbackOnly()를 부른다. 외부와 내부의 상태 객체는 다르지만 같은 홀더를 가리키며, isRollbackOnly()는 로컬 표시 또는 전역 표시(홀더의 표시)를 본다. 내부는 신규 트랜잭션이 아니어서 실제 롤백을 하지 않고, 매니저는 상태를 필드에 저장하지 않으므로 여러 스레드가 동시에 써도 섞이지 않는다. 커넥션 풀 크기가 1인 환경에서, 외부 트랜잭션(REQUIRED) 안에서 REQUIRES_NEW 트랜잭션을 시작하면 어떻게 되는가? REQUIRES_NEW가 외부 커넥션을 재사용해 정상 진행된다 외부 트랜잭션이 자동으로 커밋되고 커넥션이 반납된 뒤 내부가 시작된다 REQUIRES_NEW가 자동으로 REQUIRED로 바뀌어 참여한다 외부 커넥션이 보류만 되고 반납되지 않으므로 새 커넥션 획득이 타임아웃까지 대기하다 실패한다 보류는 홀더를 스레드 로컬 맵에서 빼서 들고 있는 것이고 커넥션을 풀에 돌려주지 않는다. 실험에서 CannotCreateTransactionException과 그 원인인 HikariCP의 커넥션 획득 타임아웃이 확인되었다. 스프링은 전파 옵션을 자동으로 바꾸거나 외부를 몰래 커밋하지 않으며, REQUIRES_NEW는 정의상 기존 트랜잭션에 참여하지 않는다. JDBC(DataSourceTransactionManager) 환경에서 NESTED와 REQUIRES_NEW를 비교한 설명 중 옳은 것은? NESTED는 커넥션 하나로 세이브포인트를 쓰고 내부 결과가 외부 결정을 따르며, REQUIRES_NEW는 커넥션을 하나 더 써서 내부 결과가 외부와 독립적으로 확정된다 둘 다 별도 커넥션을 쓰지만 NESTED는 커밋 순서만 다르다 NESTED 내부를 커밋하면 즉시 DB에 확정되므로 외부가 롤백해도 남는다 REQUIRES_NEW 내부가 롤백하면 외부 트랜잭션에 rollback-only 표시가 붙는다 실험에서 NESTED는 conn0 하나로 Creating nested transaction과 Rolling back transaction to savepoint를 남겼고, REQUIRES_NEW는 conn1을 새로 빌렸다. NESTED 내부 커밋은 세이브포인트 해제일 뿐이므로 외부 롤백에 함께 사라진다. REQUIRES_NEW 내부 롤백은 conn1에서 실제로 실행되고 외부 conn0 홀더에는 표시가 붙지 않는다. 외부 트랜잭션이 기본 설정으로 시작된 상태에서 @Transactional(isolation = Isolation.SERIALIZABLE)인 내부 메서드(REQUIRED)를 호출했다. 트랜잭션 매니저 설정은 기본값이다. 내부 메서드의 SQL은 어떤 격리 수준으로 실행되는가? SERIALIZABLE. 내부가 시작될 때 커넥션의 격리 수준이 바뀐다 SERIALIZABLE. 다만 내부가 끝나면 원래대로 돌아간다 외부 트랜잭션의 격리 수준 그대로다. 참여하는 트랜잭션의 격리 수준 선언은 조용히 무시된다 격리 수준이 충돌하므로 IllegalTransactionStateException이 발생한다 격리 수준은 doBegin()에서 커넥션에 적용되는데 참여 경로는 doBegin()을 거치지 않는다. 레퍼런스 문서도 참여 트랜잭션이 자신의 격리 수준·타임아웃·읽기 전용을 조용히 무시한다고 설명한다. 예외는 validateExistingTransaction을 true로 켰을 때만 발생하며 기본값은 false다.
    트랜잭션 전파(transaction propagation)
    기존 트랜잭션이 있을 때 새 트랜잭션 요청을 참여, 보류 후 새로 시작, 세이브포인트, 예외 중 어떻게 처리할지 정하는 규칙이다.
    물리 트랜잭션(physical transaction)
    하나의 커넥션에서 오토커밋을 끄고 시작해 commit()이나 rollback()으로 끝나는 실제 데이터베이스 트랜잭션이다.
    논리 트랜잭션(logical transaction)
    스프링 트랜잭션 매니저 관점에서 getTransaction()부터 그 상태 객체의 커밋·롤백까지의 범위로, TransactionStatus 하나에 대응한다.
    참여(participation)
    새 물리 트랜잭션을 시작하지 않고 스레드에 이미 바인딩된 물리 트랜잭션을 그대로 쓰는 것이다. 로그에는 "Participating in existing transaction"으로 나타난다.
    rollback-only
    트랜잭션이 커밋될 수 없고 롤백만 가능하다는 표시다. 상태 객체 자신의 로컬 표시와 공유 리소스 홀더에 붙는 전역 표시가 있다.
    UnexpectedRollbackException
    커밋을 요청했지만 rollback-only 표시 때문에 실제로는 롤백되었음을 알리는 예외다. 예외 시점에 롤백은 이미 끝나 있다.
    트랜잭션 보류(suspend)와 재개(resume)
    현재 스레드에 바인딩된 리소스 홀더와 동기화 정보를 떼어 보관했다가, 내부 트랜잭션이 끝난 뒤 다시 바인딩하는 동작이다. 커넥션은 반납되지 않는다.
    세이브포인트(savepoint)
    하나의 트랜잭션 안에 표시한 되돌림 지점이다. JDBC의 Connection.setSavepoint()와 rollback(Savepoint)으로 다루며 NESTED 전파의 기반이다.
    ConnectionHolder
    스프링이 JDBC 커넥션과 트랜잭션 활성 여부, rollback-only 표시, 타임아웃 등을 함께 담아 스레드 로컬 맵에 바인딩하는 객체다.
