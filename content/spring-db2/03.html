    SQL은 남기고 반복만 걷어 내기: SQL 매퍼라는 선택

    01회에서 JdbcTemplate으로 커넥션 획득, PreparedStatement 생성, 자원 반납 같은 JDBC의 반복을 걷어 냈다. 그런데 JdbcTemplate을 써도 두 가지가 그대로 남는다. 하나는 SQL이 자바 문자열 안에 산다는 점이다. 여러 줄짜리 SQL을 +로 이어 붙이거나 텍스트 블록에 넣어야 하고, SQL만 따로 떼어 읽거나 DBA에게 보여 주기가 불편하다. 다른 하나는 동적 쿼리다. 검색 조건이 있을 때만 where를 붙이고, 두 번째 조건부터는 and를 붙이는 코드를 매번 if문과 플래그 변수로 짜야 한다. 이 코드는 짧은 예제에서도 실수가 잦다.

    MyBatis는 이 두 문제를 겨냥한 SQL 매퍼(SQL mapper)다. 공식 문서는 MyBatis를 커스텀 SQL, 저장 프로시저, 고급 매핑을 지원하는 영속성 프레임워크라고 소개하며, JDBC 코드와 파라미터 설정, 결과 조회 코드를 거의 모두 없애 준다고 설명한다. 핵심은 "SQL은 개발자가 직접 쓴다"는 전제다. 개발자는 SQL을 XML 파일(또는 애너테이션)에 적고, MyBatis는 그 SQL에 자바 객체의 값을 바인딩해 실행한 뒤 결과 행을 자바 객체로 옮겨 담는다. SQL의 내용에는 관여하지 않는다.

    이 점이 04회에서 다룰 JPA 같은 ORM(Object-Relational Mapping)과의 근본적인 차이다. ORM은 객체와 테이블의 매핑 정보를 바탕으로 SQL을 생성하고, 영속성 컨텍스트가 객체의 상태 변화를 추적해 언제 어떤 SQL을 보낼지 스스로 결정한다. SQL 매퍼는 SQL을 생성하지 않고, 객체 상태를 추적하지도 않는다. 같은 행을 두 번 조회하면 MyBatis는 (뒤에서 볼 로컬 캐시를 제외하면) 매번 새 객체를 만들고, 조회한 객체의 필드를 바꿔도 아무 SQL도 나가지 않는다. 그래서 MyBatis에서는 "지금 어떤 SQL이 나가는가"를 항상 XML을 보고 정확히 알 수 있는 대신, 같은 테이블에 대한 비슷한 SQL을 여러 번 써야 하는 반복은 개발자 몫으로 남는다.

    이 회차의 예제는 서점의 도서 재고를 다룬다. 도메인 객체 Book은 식별자, 제목, 가격, 재고 수량을 가지고, 테이블 book은 같은 정보를 stock_quantity처럼 언더스코어 표기의 컬럼으로 저장한다. 자바 필드 이름과 컬럼 이름의 표기법이 일부러 다르게 되어 있는데, 이 차이를 MyBatis가 어떻게 메우는지가 뒤에서 결과 매핑을 설명할 때 중요해진다.

    create table book (
    id             bigint generated by default as identity,
    title          varchar(50),
    price          integer,
    stock_quantity integer,
    primary key (id)
);
    위 DDL은 H2 문법이다. MySQL에서는 id bigint auto_increment처럼 쓴다. 키를 DB가 만들어 준다는 점은 같고, 이 차이가 뒤에서 볼 생성 키 회수(useGeneratedKeys)와 연결된다.
    package com.example.bookstore.domain;

public class Book {

    private Long id;
    private String title;
    private Integer price;
    private Integer stockQuantity;

    public Book() {                      // MyBatis가 결과 행으로 객체를 만들 때 쓰는 기본 생성자
    }

    public Book(String title, Integer price, Integer stockQuantity) {
        this.title = title;
        this.price = price;
        this.stockQuantity = stockQuantity;
    }

    // getter, setter ...
}

    검색 조건과 수정 값은 별도의 객체로 둔다. BookSearchCond는 제목 일부(title)와 최대 가격(maxPrice)을, BookUpdateForm은 바꿀 제목·가격·재고 수량을 담는 단순한 클래스다(필드, 생성자, getter, setter만 있다). 저장소는 앞 회차들과 같은 방식으로 BookRepository 인터페이스를 두고, 이번 회차에서는 그 구현을 MyBatis로 만든다.

    MyBatis 설정: 스타터가 컨테이너에 올리는 것

    스프링 부트에서 MyBatis를 쓰는 가장 짧은 길은 MyBatis 팀이 직접 관리하는 mybatis-spring-boot-starter다. 이 스타터는 MyBatis 본체(org.mybatis:mybatis), 스프링 연동 모듈(mybatis-spring), 자동 구성 모듈(mybatis-spring-boot-autoconfigure)을 함께 끌어온다. 공식 호환표에 따르면 스타터 3.0 계열은 MyBatis-Spring 3.0과 짝을 이루어 Spring Boot 3.2~3.5에서, 스타터 4.0 계열은 MyBatis-Spring 4.0과 짝을 이루어 Spring Boot 4.0 이상에서 쓰며, 둘 다 Java 17 이상을 요구한다. 스프링 부트가 버전을 관리해 주는 라이브러리가 아니므로 버전을 직접 적어야 한다.

    dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-jdbc'
    implementation 'org.mybatis.spring.boot:mybatis-spring-boot-starter:3.0.5'  // Spring Boot 3.x 기준
    runtimeOnly 'com.h2database:h2'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

    그다음은 application.properties다. 아래 세 줄이 이번 회차에서 쓰는 설정의 전부다.

    mybatis.type-aliases-package=com.example.bookstore.domain
mybatis.configuration.map-underscore-to-camel-case=true
logging.level.com.example.bookstore.repository.mybatis=trace
    • mybatis.type-aliases-package: 이 패키지의 클래스를 타입 별칭(type alias)으로 등록한다. MyBatis 문서에 따르면 패키지로 등록한 클래스는 패키지를 뺀 단순 이름의 첫 글자를 소문자로 바꾼 이름(Book → book)이 별칭이 된다. 별칭을 등록하고 조회하는 TypeAliasRegistry는 키를 toLowerCase(Locale.ENGLISH)로 정규화하므로, XML에 resultType="Book"이라고 써도 book 별칭이 찾아진다. 별칭이 없으면 resultType="com.example.bookstore.domain.Book"처럼 전체 이름을 써야 한다. 여러 패키지는 쉼표나 세미콜론으로 구분한다.
    • mybatis.configuration.map-underscore-to-camel-case: MyBatis 핵심 설정 객체 Configuration의 mapUnderscoreToCamelCase를 켠다. 공식 설정표의 기본값은 false다. 켜면 stock_quantity 같은 컬럼이 stockQuantity 프로퍼티에 자동으로 매핑된다. mybatis.configuration.*는 Configuration의 프로퍼티를 그대로 노출하는 통로이며, 공식 문서는 이 방식이 별도 XML 설정 파일(mybatis.config-location)과 동시에 쓰일 수 없다고 밝힌다.
    • logging.level...: MyBatis는 매퍼의 네임스페이스(보통 매퍼 인터페이스의 전체 이름)를 로거 이름으로 쓴다. 공식 로깅 문서에 따르면 SQL 문장은 DEBUG 레벨에, 결과 행은 TRACE 레벨에 기록된다. 그래서 이 패키지를 DEBUG로 두면 실행되는 SQL과 바인딩 값이, TRACE로 두면 조회된 행까지 보인다. MyBatis는 SLF4J를 가장 먼저 찾으므로 스프링 부트의 기본 로깅(SLF4J + Logback) 위에서 그대로 동작한다.

    02회에서 본 것처럼 테스트는 src/test/resources/application.properties를 따로 읽으므로, 테스트에서도 같은 MyBatis 설정이 필요하면 그 파일에도 같은 줄을 넣어야 한다. 특히 map-underscore-to-camel-case를 빠뜨리면 테스트에서만 stockQuantity가 null로 조회되는, 원인을 찾기 어려운 실패가 생긴다.

    의존성과 설정만으로 무엇이 생기는지는 자동 구성 클래스 MybatisAutoConfiguration을 보면 정확히 알 수 있다. 이 클래스는 클래스패스에 SqlSessionFactory와 SqlSessionFactoryBean이 있고 DataSource 빈이 하나로 정해질 때만 동작하며(@ConditionalOnClass, @ConditionalOnSingleCandidate), 다음 네 가지를 한다.

    여기서 "MyBatis 전용 커넥션 풀은 없다"는 점을 기억해 두자. MyBatis는 스프링 DB 1편에서 다룬 DataSource(기본은 HikariCP)에서 커넥션을 빌려 쓰고, 트랜잭션도 스프링의 트랜잭션 매니저가 연 커넥션 위에서 수행한다. MyBatis를 붙였다고 해서 커넥션이나 트랜잭션을 관리하는 주체가 바뀌지 않는다는 이 사실이, 뒤에서 SqlSession과 트랜잭션의 관계를 이해하는 출발점이 된다.

    적용 1 — 매퍼 인터페이스와 XML 한 쌍

    MyBatis에서 저장소 코드의 중심은 매퍼 인터페이스(mapper interface)다. 메서드 시그니처만 선언하고 구현 클래스는 만들지 않는다. @Mapper는 앞에서 본 자동 스캔이 이 인터페이스를 찾도록 붙이는 표식이다.

    package com.example.bookstore.repository.mybatis;

import com.example.bookstore.domain.Book;
import com.example.bookstore.repository.BookSearchCond;
import com.example.bookstore.repository.BookUpdateForm;
import org.apache.ibatis.annotations.Mapper;
import org.apache.ibatis.annotations.Param;

import java.util.List;
import java.util.Optional;

@Mapper
public interface BookMapper {

    void save(Book book);

    void update(@Param("id") Long id, @Param("form") BookUpdateForm form);

    Optional findById(Long id);

    List findAll(BookSearchCond cond);
}

    SQL은 XML 파일에 둔다. 파일 위치는 src/main/resources/com/example/bookstore/repository/mybatis/BookMapper.xml, 즉 인터페이스의 패키지 경로와 똑같은 디렉터리에 인터페이스와 같은 이름으로 만든다. 이 규칙이 왜 필요한지는 기동 과정을 추적할 때 소스 코드로 확인한다.

    



    
        insert into book (title, price, stock_quantity)
        values (#{title}, #{price}, #{stockQuantity})
    

    
        update book
        set title          = #{form.title},
            price          = #{form.price},
            stock_quantity = #{form.stockQuantity}
        where id = #{id}

    요소를 하나씩 읽어 보자.

    • namespace: 매퍼 인터페이스의 전체 이름과 정확히 같아야 한다. MyBatis는 네임스페이스 + "." + id를 SQL 문장의 ID로 쓰고, 매퍼 메서드를 호출하면 인터페이스 전체 이름 + "." + 메서드 이름으로 문장을 찾는다. 둘이 만나는 지점이 바로 이 문자열이다.
    • id: 메서드 이름과 같아야 한다. 메서드 오버로딩이 통하지 않는 이유가 여기서 나온다. 문장 ID에 파라미터 타입이 들어가지 않으므로, 이름이 같은 메서드 두 개는 같은 문장을 가리킨다.
    • #{title}: 파라미터 객체에서 값을 꺼내 PreparedStatement의 파라미터로 바인딩하라는 표시다. 공식 문서의 표현으로는 "PreparedStatement 파라미터를 만들라"는 뜻이다. SQL 문자열에는 ?가 들어가고 값은 따로 전달된다.
    • useGeneratedKeys="true" keyProperty="id": DB가 만든 키(identity, auto_increment)를 읽어 파라미터 객체의 id 프로퍼티에 넣으라는 뜻이다. 두 속성의 기본값은 각각 false와 미설정이다.
    • resultType="Book": 결과 행 하나를 Book 객체 하나로 만든다. List<Book>을 반환하는 메서드라도 resultType에는 컬렉션이 아니라 원소 타입을 적는다.
    • &lt;=: XML 텍스트 안에서 <는 태그의 시작으로 해석되므로 그대로 쓸 수 없다. 엔티티 &lt;로 적으면 XML 파서가 <로 되돌려 MyBatis에 넘긴다. 반면 >는 XML 텍스트에서 그대로 써도 된다.

    update 메서드는 파라미터가 두 개라서 @Param("id"), @Param("form")으로 이름을 붙였다. 그래서 XML에서 #{id}와 #{form.title}처럼 "이름.프로퍼티" 경로로 값을 꺼낸다. 반면 findAll(BookSearchCond cond)처럼 파라미터가 하나뿐이고 @Param이 없으면 그 객체 자체가 파라미터 객체가 되어, XML에서 #{cond.title}이 아니라 #{title}, test="maxPrice != null"처럼 프로퍼티 이름을 바로 쓴다. findById(Long id)처럼 파라미터가 Long 같은 단순 타입 하나뿐이면 그 값 자체가 바인딩되므로 #{id} 안의 이름은 사실상 무엇이든 상관없다. 이 규칙들은 외워야 할 예외 목록이 아니라 파라미터 이름 해석기 하나의 동작에서 모두 나온다. 뒤에서 그 소스와 함께 다시 본다.

    findById의 반환 타입이 Optional<Book>인 것도 눈여겨보자. MyBatis 3.5 계열의 매퍼 메서드는 Optional을 반환할 수 있다(MapperMethod가 반환 타입이 Optional이면 결과를 감싼다). 결과가 없으면 빈 Optional이, 한 건이면 그 객체를 감싼 Optional이 반환된다. 단건 조회의 결과가 두 건 이상이면 공식 문서의 설명대로 selectOne 계열은 예외를 던진다. "한 건이어야 한다"는 기대를 프레임워크가 검사해 주는 셈이다.

    XML을 src/main/java 아래 인터페이스 옆에 두면 안 된다. Gradle과 Maven의 기본 규칙에서 src/main/java의 .xml은 클래스패스로 복사되지 않는다. 같은 패키지 "경로"는 src/main/resources 아래에 만든다.

    XML 위치를 인터페이스와 다르게 두고 싶다면 mybatis.mapper-locations로 위치를 직접 알려 준다. 예를 들어 mybatis.mapper-locations=classpath:mapper/**/*.xml이라고 쓰면 resources/mapper 아래의 XML을 모두 읽는다. 이 경우 연결 고리는 경로가 아니라 오직 namespace 문자열이다.

    적용 2 — 저장소에 연결하고 실행하기

    매퍼를 그대로 서비스에 주입해도 되지만, 01회부터 이어 온 구조를 지키려면 BookRepository 구현체가 매퍼에 위임하게 만든다. 이렇게 하면 서비스는 저장소 인터페이스만 알고, 구현 기술을 JdbcTemplate에서 MyBatis로, 다시 JPA로 바꿀 때 서비스 코드가 바뀌지 않는다.

    package com.example.bookstore.repository.mybatis;

import com.example.bookstore.domain.Book;
import com.example.bookstore.repository.BookRepository;
import com.example.bookstore.repository.BookSearchCond;

    설정 클래스는 BookMapper 타입의 빈을 주입받는다. 우리는 BookMapper의 구현 클래스를 만든 적이 없는데도 주입이 성공한다. 즉 컨테이너 안에는 BookMapper를 구현한 어떤 객체가 이미 빈으로 등록되어 있다. 이 객체의 정체가 다음 절의 주제다. 먼저 동작부터 확인하자.

    클래스에 붙은 @Transactional은 02회에서 다룬 대로 각 테스트를 트랜잭션 안에서 실행하고 끝나면 롤백해, 테스트끼리 데이터가 섞이지 않게 한다. 첫 테스트를 한 줄씩 따라가 보자. save는 insert를 실행한 뒤 DB가 만든 키를 saved 객체의 id에 넣는다. 그래서 반환값을 따로 받지 않아도 saved.getId()가 null이 아니다. findById는 같은 행을 조회해 새 Book 객체를 만든다. 마지막 단언 isNotSameAs(saved)가 통과하는 것이 SQL 매퍼의 성격을 보여 준다. 방금 저장한 객체를 기억해 두었다가 돌려주는 장치가 없으므로 조회 결과는 항상 결과 행에서 새로 만든 객체다. 04회의 JPA에서는 같은 트랜잭션 안에서 같은 식별자로 조회하면 영속성 컨텍스트가 같은 인스턴스를 돌려준다는 점과 비교해 두자.

    두 번째 테스트는 title이 null이고 maxPrice가 26000인 조건으로 조회한다. <where> 안의 첫 <if>는 거짓이라 빠지고 두 번째만 남아 WHERE price <= ?가 붙은 SQL이 실행된다. 이 SQL이 어떻게 조립되는지는 동적 쿼리 절에서 한 글자 단위로 추적한다. 로그 레벨을 DEBUG 이상으로 두었다면 콘솔에서 ==> Preparing:으로 시작하는 줄에 ?가 들어간 SQL이, 그 아래 줄에 30000(Integer)처럼 "값(타입 이름)" 형식으로 바인딩 값이 찍힌다. 이 로그를 남기는 ConnectionLogger 역시 JDBC Connection을 감싼 JDK 동적 프록시인데, 이 "인터페이스를 감싼 프록시"라는 구조가 MyBatis 전체를 관통한다.

    적용 3 — 분석: 구현체 없는 인터페이스의 정체

    주입된 bookMapper의 클래스를 출력해 보면 jdk.proxy2.$Proxy60 같은 이름이 나온다(숫자는 실행 환경과 앞서 만들어진 프록시 수에 따라 달라진다). 이름이 말해 주듯 이 객체는 JDK 동적 프록시(dynamic proxy)다. JDK 동적 프록시는 java.lang.reflect.Proxy가 실행 중에 바이트코드를 생성해 만든 클래스의 인스턴스로, 지정한 인터페이스를 구현하며, 모든 메서드 호출을 하나의 InvocationHandler.invoke(proxy, method, args)로 모은다. 스프링 핵심 원리 기본편과 스프링 MVC를 거치며 프록시가 등장하는 장면을 여러 번 보았는데, MyBatis는 이 구조를 "인터페이스 메서드 → SQL 문장" 연결에 쓴다.

    원리를 확인하는 가장 좋은 방법은 같은 구조를 작게 직접 만들어 보는 것이다. 아래 코드는 MyBatis의 MapperProxy가 하는 일 중 핵심 골격만 흉내 낸 것으로, 외부 라이브러리 없이 JDK만으로 컴파일·실행된다.

    package demo;

import java.util.List;

public interface BookMapper {
    int updatePrice(Long id, Integer price);
    List findTitles(String title, Integer maxPrice);
    int deleteAll();                       // 등록된 SQL이 없는 메서드
    default int countAll() {               // 디폴트 메서드
        return findTitles(null, null).size();
    }
}
    package demo;

import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Parameter;
import java.lang.reflect.Proxy;
import java.util.ArrayList;
import java.util.Arrays;
import java.util.List;
import java.util.Map;

public class MiniMapperProxy implements InvocationHandler {

    private final Class mapperInterface;
    private final Map statements;   // 문장 ID -> SQL

    MiniMapperProxy(Class mapperInterface, Map statements) {
        this.mapperInterface = mapperInterface;
        this.statements = statements;
    }

    @Override
    public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
        if (method.getDeclaringClass() == Object.class) {
            return method.invoke(this, args);                        // toString, equals, hashCode
        }
        if (method.isDefault()) {
            return InvocationHandler.invokeDefault(proxy, method, args); // 디폴트 메서드 본문 실행
        }
        String statementId = mapperInterface.getName() + "." + method.getName();
        String sql = statements.get(statementId);
        if (sql == null) {
            throw new IllegalStateException("Invalid bound statement (not found): " + statementId);
        }
        List names = new ArrayList<>();
        for (Parameter p : method.getParameters()) {
            names.add(p.getName());
        }
        System.out.println("statementId = " + statementId);
        System.out.println("  sql   = " + sql);
        System.out.println("  names = " + names + ", args = " + Arrays.toString(args));
        return method.getReturnType() == int.class ? 1 : List.of("A", "B");
    }

    public static void main(String[] a) {
        Map statements = Map.of(
                "demo.BookMapper.updatePrice", "update book set price = #{price} where id = #{id}",
                "demo.BookMapper.findTitles", "select title from book");

        BookMapper mapper = (BookMapper) Proxy.newProxyInstance(
                BookMapper.class.getClassLoader(),
                new Class[]{BookMapper.class},
                new MiniMapperProxy(BookMapper.class, statements));

        System.out.println(mapper.getClass().getName());
        System.out.println(mapper.updatePrice(1L, 15000));
        System.out.println(mapper.countAll());
        try {
            mapper.deleteAll();
        } catch (IllegalStateException e) {
            System.out.println(e.getMessage());
        }
    }
}

OpenJDK 21에서는 위처럼 jdk.proxy1 패키지에 만들어졌다. updatePrice(1L, 15000) 호출은 핸들러의 invoke로 들어와 demo.BookMapper.updatePrice라는 문장 ID로 SQL을 찾았다. 반환값 1은 핸들러가 돌려준 Integer가 int로 바뀐 것이다. countAll()은 디폴트 메서드라서 InvocationHandler.invokeDefault로 인터페이스에 적힌 본문을 실행했고, 그 본문이 다시 프록시의 findTitles를 호출해 두 번째 문장 출력이 나온 뒤 리스트 크기 2가 출력됐다. 마지막으로 SQL이 등록되지 않은 deleteAll()은 문장을 찾지 못해 예외가 났다. 이 메시지 문구는 MyBatis의 MapperMethod가 실제로 던지는 BindingException의 문구를 그대로 따온 것이다.

    네 번째와 여덟 번째 줄의 파라미터 이름이 [arg0, arg1]인 점도 중요하다. 같은 코드를 javac -parameters로 컴파일하면 출력만 이렇게 바뀐다.

      names = [id, price], args = [1, 15000]
  names = [title, maxPrice], args = [null, null]

    자바 컴파일러는 기본적으로 메서드 파라미터의 이름을 클래스 파일에 남기지 않는다. -parameters 옵션을 주면 클래스 파일에 MethodParameters 속성이 기록되어, 실행 중에 java.lang.reflect.Parameter.getName()이 소스의 이름을 돌려준다. 이름 정보가 없으면 arg0, arg1 같은 합성 이름이 나온다. 이 차이가 MyBatis에서 @Param이 필요한 경우와 필요 없는 경우를 가른다. 파라미터 이름 해석 절에서 이어서 다룬다.

    일상에서 가져온 비유내선 번호만 있는 안내 데스크

    매퍼 인터페이스는 회사 안내판에 적힌 내선 번호 목록과 같다. 어느 번호로 전화를 걸어도 실제로는 한 명의 교환원(InvocationHandler)이 받고, 교환원은 걸려 온 번호(문장 ID)로 업무 매뉴얼(XML의 SQL)을 펼쳐 처리한다. 번호마다 담당 직원(구현 클래스)이 따로 있는 것이 아니다. 다만 이 비유는 교환원이 매번 매뉴얼을 처음부터 찾는 것처럼 보이게 만드는데, 실제 MyBatis는 메서드별 처리기를 캐시에 담아 두고 SQL 문장 정보도 기동 시점에 이미 해석해 둔다는 점에서 다르다.

    미니 프록시로 골격을 봤으니, 이제 실제 MyBatis와 MyBatis-Spring의 소스(Apache License 2.0)를 따라 두 시점을 추적한다. 하나는 애플리케이션이 뜰 때 인터페이스가 빈이 되기까지의 기동 시점이고, 다른 하나는 bookMapper.findAll(cond) 한 번이 JDBC 호출이 되기까지의 호출 시점이다.

    기동 시점: 인터페이스가 빈이 되기까지

    매퍼 스캐너(ClassPathMapperScanner)는 스프링의 컴포넌트 스캐너를 확장한 것인데, 후보 판정 규칙을 뒤집어 놓았다. 일반 컴포넌트 스캔은 인터페이스를 빈 후보에서 제외하지만, 매퍼 스캐너는 "독립된 인터페이스"만 후보로 받는다(MyBatis-Spring 3.0.6과 4.1.0부터는 애너테이션 타입을 제외하는 조건이 더해졌다). 후보를 찾으면 빈 정의(bean definition)를 고친다. 빈 클래스를 인터페이스에서 MapperFactoryBean으로 바꾸고, 원래 인터페이스(BookMapper.class)를 생성자 인자로 넘기며, SqlSessionFactory나 SqlSessionTemplate을 명시하지 않았으면 타입 기반 자동 주입 모드로 설정한다. 즉 컨테이너에 등록되는 것은 인터페이스가 아니라 "그 인터페이스의 구현 객체를 만들어 줄 팩토리 빈"이다.

    MapperFactoryBean은 스프링의 FactoryBean이다. 스프링 핵심 원리 기본편에서 본 것처럼, 컨테이너는 FactoryBean 자체가 아니라 그 getObject()가 반환하는 객체를 빈으로 노출한다. MapperFactoryBean의 getObjectType()은 매퍼 인터페이스를, isSingleton()은 true를 반환하므로, 우리가 BookMapper 타입으로 주입받는 것은 싱글톤 하나다. 초기화 단계에서 호출되는 checkDaoConfig()는 MyBatis Configuration에 이 매퍼가 아직 없으면 configuration.addMapper(BookMapper.class)를 호출한다.

    addMapper가 부르는 MapperAnnotationBuilder.parse()는 가장 먼저 loadXmlResource()를 실행한다. 이 메서드의 핵심은 다음 한 줄이다.

    String xmlResource = type.getName().replace('.', '/') + ".xml";

    인터페이스 이름 com.example.bookstore.repository.mybatis.BookMapper의 점을 슬래시로 바꾸고 .xml을 붙여 클래스패스에서 리소스를 찾는다. 앞에서 "XML을 인터페이스와 같은 패키지 경로에 두라"고 한 규칙의 정체가 이것이다. 리소스가 있으면 XMLMapperBuilder가 파싱하고, 없으면 조용히 넘어간다(소스 주석의 표현으로 "리소스는 필수가 아니다"). 파싱 결과 XML의 <select>, <insert> 같은 요소 하나하나가 MappedStatement 객체가 되어 Configuration에 네임스페이스.id를 키로 등록된다. MappedStatement에는 SQL의 원천(SqlSource), 문장 종류, 결과 매핑, 키 생성기, 캐시 사용 여부 같은 실행에 필요한 정보가 모두 들어 있다. 그 뒤 인터페이스 메서드에 붙은 @Select 같은 애너테이션도 같은 방식으로 MappedStatement가 된다.

    마지막으로 컨테이너가 getObject()를 호출하면 getSqlSession().getMapper(BookMapper.class)가 실행된다. 여기서 getSqlSession()이 돌려주는 것은 진짜 세션이 아니라 SqlSessionTemplate이다. SqlSessionTemplate.getMapper는 Configuration을 거쳐 MapperProxyFactory.newInstance에 도달하고, 이 메서드가 Proxy.newProxyInstance(mapperInterface.getClassLoader(), new Class[] { mapperInterface }, mapperProxy)로 프록시를 만든다. 미니 프록시에서 직접 호출한 바로 그 API다. 만들어진 MapperProxy는 필드로 SqlSessionTemplate을 쥐고 있다.

    호출 시점: 메서드 한 번이 JDBC 호출이 되기까지

    이제 트랜잭션 안에서 bookMapper.findAll(cond)를 호출했을 때 일어나는 일을 순서대로 따라가자.

    1. 프록시 진입. 프록시 클래스의 findAll은 앞의 바이트코드와 똑같이 MapperProxy.invoke를 부른다. MapperProxy는 선언 클래스가 Object인 메서드(toString 등)면 자기 자신에게 실행시키고, 그 밖의 메서드는 methodCache에서 이 Method에 대응하는 처리기를 꺼낸다(없으면 만들어 넣는 computeIfAbsent 방식이다). 디폴트 메서드면 MethodHandle로 인터페이스의 본문을 실행하는 처리기가, 그 밖의 메서드면 MapperMethod를 감싼 처리기가 만들어진다. 처음 호출될 때만 MapperMethod가 만들어지고, 이후 호출은 캐시에서 바로 꺼낸다.
    2. 문장 해석(첫 호출 때 한 번). MapperMethod를 만들 때 mapperInterface.getName() + "." + methodName으로 문장 ID를 만들어 Configuration에 있는지 확인한다. 없으면 상위 인터페이스까지 찾아보고, 그래도 없으면 Invalid bound statement (not found)를 던진다. 함께 반환 타입을 분석해 이 메서드가 여러 건(List), 한 건, Optional, 커서 중 무엇을 반환하는지 정하고, 파라미터 이름 해석기(ParamNameResolver)를 준비한다.
    3. 명령 분기. MapperMethod.execute는 문장 종류(INSERT, UPDATE, DELETE, SELECT, FLUSH)에 따라 갈라진다. findAll은 SELECT이고 여러 건을 반환하므로 인자 배열을 파라미터 객체로 바꾼 뒤 sqlSession.selectList(문장ID, 파라미터)를 호출한다. 이때의 sqlSession이 SqlSessionTemplate이다. INSERT, UPDATE, DELETE는 영향받은 행 수를 메서드의 반환 타입(void, int, long, boolean)에 맞춰 바꿔 준다. boolean이면 행 수가 0보다 클 때 true다.
    4. 두 번째 프록시. SqlSessionTemplate은 생성자에서 SqlSession 인터페이스에 대한 JDK 동적 프록시(sqlSessionProxy)를 하나 더 만들어 둔다. selectList는 이 프록시에 위임되고, 핸들러 SqlSessionInterceptor.invoke가 실행된다. 이 핸들러가 "지금 쓸 진짜 세션"을 고르고, 호출을 실행하고, 필요하면 커밋하고, 예외를 번역하고, 세션을 정리한다. 자세한 동작은 트랜잭션 절에서 본다.
    5. 진짜 세션. 고른 세션(DefaultSqlSession)의 selectList는 Configuration에서 문장 ID로 MappedStatement를 꺼내 실행기(Executor)에 넘긴다.
    6. 실행기. 설정 cacheEnabled의 기본값이 true라서 실행기는 2차 캐시를 담당하는 CachingExecutor로 한 겹 감싸여 있지만, 매퍼 XML에 <cache/>를 선언하지 않았으므로 그대로 안쪽 실행기에 넘어간다. 안쪽 실행기는 기본 실행기 종류(SIMPLE)인 SimpleExecutor다. 실행기는 MappedStatement에 파라미터를 주고 BoundSql, 즉 "?가 들어간 최종 SQL 문자열 + 각 ?에 넣을 값의 목록"을 얻는다. 동적 SQL은 바로 이때 조립된다. 그다음 문장 ID, SQL, 파라미터 값 등으로 캐시 키를 만들어 세션 단위의 로컬 캐시를 먼저 확인하고, 없으면 DB로 간다.
    7. JDBC. SimpleExecutor는 MyBatis 트랜잭션 객체에서 커넥션을 얻는다. 스프링 환경에서 이 객체는 SpringManagedTransaction이고, 내부에서 DataSourceUtils.getConnection(dataSource)를 호출해 스프링 트랜잭션 매니저가 스레드에 묶어 둔 커넥션을 가져온다. 이어서 PreparedStatementHandler가 connection.prepareStatement(sql)을 호출하고, ParameterHandler가 각 ?에 TypeHandler로 값을 넣고(Integer면 setInt), 쿼리를 실행한 뒤 ResultSetHandler가 결과 행을 Book 객체로 바꾼다. 실행이 끝나면 SIMPLE 실행기는 Statement를 닫는다.
    8. 되돌아오기. 결과 리스트가 거꾸로 올라온다. SqlSessionInterceptor는 이 세션이 트랜잭션에 묶여 있으므로 커밋하지 않고, 세션을 닫는 대신 참조 횟수만 줄인다. MapperMethod는 선언된 반환 타입이 배열이나 다른 컬렉션이면 변환해 돌려준다.

    이 경로를 보면 MyBatis의 역할 분담이 선명해진다. 프록시 계층(MapperProxy, MapperMethod)은 "자바 메서드 호출을 문장 ID와 파라미터로 바꾸는" 일만 한다. 세션 계층(SqlSessionTemplate)은 "어느 세션, 어느 커넥션 위에서 실행할지"를 스프링 트랜잭션과 맞춘다. 실행 계층(Executor와 세 개의 핸들러)은 SQL 조립, 캐시, JDBC 호출, 결과 변환을 한다. SQL을 XML에 쓰든 애너테이션에 쓰든, 저장소에서 매퍼를 쓰든 SqlSessionTemplate.selectList("...BookMapper.findAll", cond)를 직접 부르든, 아래 두 계층은 똑같이 동작한다. 서비스 메서드에 @Transactional을 붙이면 이 경로 앞에 스프링 AOP 프록시가 하나 더 서는데, 그 프록시의 동작과 내부 호출 문제는 07회에서 다룬다.

    파라미터 이름은 어디서 오는가: @Param, -parameters, param1

    XML에서 #{id}라고 쓰면 MyBatis는 "파라미터 객체"에서 id라는 이름으로 값을 찾는다. 그렇다면 자바 메서드의 인자 배열(Object[] args)은 어떻게 이름을 가진 파라미터 객체가 될까. 이 변환을 하는 것이 ParamNameResolver다. 소스를 따라가면 규칙은 다음과 같다.

    1. 메서드를 분석할 때 각 파라미터의 이름을 정한다. RowBounds, ResultHandler 타입의 특수 파라미터는 건너뛴다. @Param이 있으면 그 값이 이름이다. 없고 설정 useActualParamName이 켜져 있으면(공식 설정표의 기본값은 true, 3.4.1부터) java.lang.reflect.Parameter.getName()의 결과가 이름이다. 그것도 아니면 "0", "1" 같은 위치 번호가 이름이 된다.
    2. 호출될 때 인자 배열을 파라미터 객체로 바꾼다. 인자가 없으면 null이다. @Param이 없는 인자가 하나뿐이면 그 객체 자체가 파라미터 객체가 된다(단, 컬렉션이나 배열이면 collection, list, array 같은 이름을 붙인 맵으로 감싼다). 그 밖의 경우에는 ParamMap을 만들어 정해 둔 이름마다 값을 넣고, 추가로 param1, param2처럼 1부터 시작하는 위치 이름도 넣는다.

    이 두 규칙으로 앞 절의 예제가 모두 설명된다. findAll(BookSearchCond cond)는 인자가 하나뿐이라 BookSearchCond 객체 자체가 파라미터 객체이고, #{title}은 그 객체의 title 프로퍼티를 읽는다. update(@Param("id") Long id, @Param("form") BookUpdateForm form)은 {id=…, form=…, param1=…, param2=…} 맵이 되어 #{id}와 #{form.title}이 통한다. findById(Long id)는 인자 하나짜리 단순 값이라 Long 자체가 파라미터 객체가 되고, MyBatis는 Long처럼 TypeHandler가 있는 타입이면 이름과 무관하게 그 값을 바인딩한다.

    이제 update에서 @Param을 지웠다고 해 보자. 앞의 미니 프록시 실험에서 본 것처럼 결과는 컴파일 옵션에 달려 있다. -parameters로 컴파일됐으면 실제 이름 id, form이 쓰여 그대로 동작한다. 그 옵션 없이 컴파일됐으면 Parameter.getName()이 arg0, arg1을 돌려주므로 맵의 키는 arg0, arg1, param1, param2가 되고, #{id}를 찾는 순간 "파라미터 id를 찾을 수 없고, 사용 가능한 이름은 이것들"이라는 BindingException이 난다. 스프링 부트 Gradle 플러그인은 문서에 명시된 대로 모든 JavaCompile 작업에 -parameters를 추가하므로 Gradle로 빌드하면 보통 문제가 없다. 하지만 같은 소스를 다른 경로로 컴파일하면 이 옵션이 빠질 수 있고, 그러면 같은 코드가 어떤 환경에서만 실패한다. 파라미터가 둘 이상이면 @Param을 붙이는 습관이 빌드 설정에 기대지 않는 가장 확실한 방법이다.

    @Param을 붙이면 인자가 하나뿐이어도 맵으로 감싸진다. findAll(@Param("cond") BookSearchCond cond)로 바꾸면 XML에서도 #{cond.title}, test="cond.maxPrice != null"로 바꿔야 한다. 이 규칙도 "애너테이션이 있으면 ParamMap"이라는 같은 분기에서 나온다.

    #{}와 ${}: 바인딩과 문자열 치환

    MyBatis XML에는 값을 넣는 표기가 두 가지 있다. #{}는 앞에서 본 대로 PreparedStatement의 파라미터, 즉 ?가 된다. ${}는 공식 문서가 "문자열 치환(string substitution)"이라고 부르는 것으로, MyBatis가 값을 수정하거나 이스케이프하지 않고 SQL 문자열에 그대로 끼워 넣는다. 공식 문서는 사용자 입력을 이런 식으로 문장에 넣는 것이 안전하지 않으며 SQL 인젝션 공격으로 이어질 수 있다고 경고한다. 두 방식의 차이를 MyBatis 없이 JDBC만으로 재현해 보면 차이가 어디서 생기는지 분명해진다.

    import java.sql.*;

public class BindVsConcat {
    public static void main(String[] args) throws Exception {
        try (Connection con = DriverManager.getConnection("jdbc:h2:mem:test")) {
            try (Statement s = con.createStatement()) {
                s.execute("create table book (id bigint generated by default as identity primary key,"
                        + " title varchar(50), price int)");
                s.execute("insert into book (title, price) values ('JVM', 30000), ('SQL', 25000)");
            }
            String input = "x' or '1'='1";

            // 1) ${title} 방식: 값을 SQL 문자열에 그대로 이어 붙인다
            String concat = "select count(*) from book where title = '" + input + "'";
            System.out.println(concat);
            try (Statement s = con.createStatement(); ResultSet rs = s.executeQuery(concat)) {
                rs.next();
                System.out.println("concat count = " + rs.getInt(1));
            }

            // 2) #{title} 방식: SQL에는 ? 만 두고 값은 따로 보낸다
            try (PreparedStatement ps = con.prepareStatement("select count(*) from book where title = ?")) {
                ps.setString(1, input);
                try (ResultSet rs = ps.executeQuery()) {
                    rs.next();
                    System.out.println("bind count   = " + rs.getInt(1));
                }
            }

            // 3) useGeneratedKeys="true" 가 내부에서 쓰는 JDBC 호출
            try (PreparedStatement ps = con.prepareStatement(
                    "insert into book (title, price) values (?, ?)", Statement.RETURN_GENERATED_KEYS)) {
                ps.setString(1, "TCP");
                ps.setInt(2, 28000);
                System.out.println("updated      = " + ps.executeUpdate());
                try (ResultSet keys = ps.getGeneratedKeys()) {
                    keys.next();
                    System.out.println("generated id = " + keys.getLong(1));
                }
            }

            // 4) 결과 집합의 컬럼 라벨
            try (Statement s = con.createStatement();
                 ResultSet rs = s.executeQuery("select id, title, price as unit_price from book where id = 1")) {
                ResultSetMetaData md = rs.getMetaData();
                StringBuilder sb = new StringBuilder("labels       =");
                for (int i = 1; i <= md.getColumnCount(); i++) sb.append(' ').append(md.getColumnLabel(i));
                System.out.println(sb);
            }

            // 5) ORDER BY 자리에 ? 를 쓰면
            try (PreparedStatement ps = con.prepareStatement("select title from book order by ? desc")) {
                ps.setString(1, "price");
                ps.executeQuery();
            } catch (SQLException e) {
                System.out.println("order by ?   -> " + e.getClass().getSimpleName() + ", SQLState " + e.getSQLState());
            }
        }
    }
}

    1번은 ${}가 하는 일이다. 입력값에 들어 있던 작은따옴표가 SQL의 문자열 리터럴을 닫아 버리고, 뒤따르는 or '1'='1'이 SQL 문법의 일부가 된다. DB의 파서 입장에서 이 문장은 "제목이 x이거나 1=1인 행"이므로 모든 행(2건)이 세어진다. 2번은 #{}가 하는 일이다. SQL 텍스트는 title = ?로 고정되어 있고, 입력값 전체는 따옴표까지 포함해 하나의 값으로 전달된다. 제목이 정확히 x' or '1'='1인 책은 없으므로 0건이다. 핵심은 "어디까지가 SQL 문법이고 어디부터가 데이터인가"의 경계를 누가 정하느냐다. 문자열 치환에서는 입력값이 그 경계를 옮길 수 있고, 바인딩에서는 경계가 SQL을 준비하는 시점에 이미 고정된다.

    한 층 더 내려가 보면 "따로 보낸다"의 구체적인 방식은 드라이버와 DB에 따라 다르다. 예를 들어 MySQL Connector/J의 useServerPrepStmts 속성은 기본값이 false다. 이 경우 드라이버는 서버 측 준비 문장(server-side prepared statement)을 쓰지 않고 클라이언트에서 준비 문장을 흉내 내는데, 바인딩한 값을 드라이버가 문자열 리터럴 규칙에 맞게 이스케이프해 SQL에 넣어 보낸다. 그래도 안전한 이유는 값을 리터럴로 만드는 책임이 개발자의 문자열 연결이 아니라 드라이버에 있기 때문이다. 반대로 ${}는 드라이버가 개입하기 전에 MyBatis가 문자열을 완성해 버리므로 드라이버가 할 수 있는 일이 없다. MyBatis 내부에서도 ${}가 들어간 텍스트는 TextSqlNode로 분류되어 문장 전체를 "동적"으로 만들고, 호출할 때마다 #{}를 ?로 바꾸는 단계보다 먼저 값의 문자열이 끼워진다.

    그렇다면 ${}는 왜 있을까. 5번 실험이 답이다. ?는 값이 들어갈 자리를 표시할 뿐, 테이블 이름이나 컬럼 이름 같은 식별자 자리에는 쓸 수 없다. H2 2.4.240에서 order by ?에 "price"를 바인딩하면 데이터 변환 오류(SQLState 22018)가 난다. H2가 정렬 자리의 파라미터를 컬럼 번호로 해석하려다 문자열 "price"를 숫자로 바꾸지 못한 것이다. DB에 따라 오류 대신 상수로 정렬해 아무 효과가 없을 수도 있지만, 어느 쪽이든 "사용자가 고른 컬럼으로 정렬"은 되지 않는다. 정렬 컬럼, 동적 테이블 이름처럼 SQL 구조 자체를 바꿔야 할 때 ${}가 필요하다.

    이때 지켜야 할 원칙은 "${}에 들어가는 값은 사용자 입력이 아니라 코드가 정한 상수여야 한다"는 것이다. 입력을 검사하는 것보다 입력을 상수로 바꾸는 편이 안전하다.

    // 매퍼
List findAllOrderBy(@Param("column") String column);

// 저장소
public List findAllSorted(String sort) {
    String column = switch (sort) {
        case "title" -> "title";
        case "price" -> "price";
        default -> throw new IllegalArgumentException("정렬할 수 없는 컬럼: " + sort);
    };
    return bookMapper.findAllOrderBy(column);
}

    switch의 결과는 사용자가 보낸 문자열 객체가 아니라 코드에 적힌 리터럴이다. 따라서 sort에 무엇이 들어와도 SQL에 들어갈 수 있는 값은 title과 price 둘뿐이다. LIKE 검색에서 like '%${title}%'처럼 쓰는 것은 흔한 실수다. 이것은 사용자 입력을 그대로 치환하는 1번 실험과 똑같다. like concat('%', #{title}, '%')처럼 와일드카드는 SQL 쪽에서 붙이고 값은 바인딩하거나, 뒤에서 볼 <bind>로 패턴 문자열을 만들어 #{}로 넘긴다.

    ResultSet에서 객체로: 자동 매핑과 생성 키

    조회 결과가 Book이 되는 과정을 보자. resultType="Book"인 문장의 결과를 처리할 때 ResultSetHandler는 행마다 먼저 Book의 인스턴스를 만든다(기본 생성자를 리플렉션으로 호출한다). 다음으로 결과 집합의 컬럼 라벨마다 대응하는 프로퍼티를 찾아 값을 넣는데, 이것이 자동 매핑(auto-mapping)이다. 공식 문서의 표현대로 MyBatis는 컬럼 이름과 같은 이름의 프로퍼티를 대소문자를 무시하고 찾는다. 위 실험 4번에서 H2가 컬럼 라벨을 ID TITLE UNIT_PRICE처럼 대문자로 돌려준 것을 보았는데, 대소문자를 무시하므로 ID는 id에, TITLE은 title에 문제없이 들어간다.

    문제는 STOCK_QUANTITY다. 대소문자를 무시해도 stockQuantity와는 언더스코어 하나가 다르다. mapUnderscoreToCamelCase를 켜면 프로퍼티를 찾는 MetaClass.findProperty(name, useCamelCaseMapping)가 먼저 name.replace("_", "")로 언더스코어를 지운다. STOCK_QUANTITY는 STOCKQUANTITY가 되고, 이것을 대소문자 무시로 찾으면 stockQuantity와 일치한다. 즉 "카멜 표기 변환"이라는 이름과 달리 실제 동작은 "언더스코어 제거 + 대소문자 무시 비교"다. 이 설정이 꺼져 있으면 어떻게 될까. 공식 설정표에서 autoMappingUnknownColumnBehavior의 기본값은 NONE(아무것도 하지 않음)이므로, 매핑할 곳을 못 찾은 컬럼은 조용히 버려지고 stockQuantity는 null로 남는다. 예외가 나지 않는다는 점이 이 실수를 찾기 어렵게 만든다. 개발 중에는 이 설정을 WARNING(경고 로그)이나 FAILING(SqlSessionException)으로 바꿔 두면 이런 누락을 바로 발견할 수 있다.

    컬럼 별칭으로 해결하는 방법도 있다. select stock_quantity as stockQuantity라고 쓰면 라벨 자체가 프로퍼티 이름과 대소문자만 다르므로 설정 없이도 매핑된다. 컬럼과 프로퍼티의 이름 규칙이 아예 다르거나 매핑을 명시적으로 드러내고 싶으면 <resultMap>을 쓴다. 이것은 기타 기능 절에서 본다. 매핑 대상 프로퍼티의 타입에 맞는 TypeHandler가 값을 꺼내는데, 예를 들어 Integer 프로퍼티는 rs.getInt로 읽은 뒤 wasNull()을 확인해 SQL NULL이면 0이 아니라 null을 넣는다. 도메인 필드를 int가 아니라 Integer로 둔 이유가 여기 있다. 기본형 필드는 NULL을 표현할 수 없다.

    생성 키 회수는 반대 방향, 즉 DB에서 만든 값을 파라미터 객체에 넣는 일이다. useGeneratedKeys="true"가 붙은 문장은 키 생성기로 Jdbc3KeyGenerator를 쓰도록 설정되고, PreparedStatementHandler는 이 경우 connection.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)로 문장을 만든다(keyColumn을 지정했으면 컬럼 이름 배열을 넘기는 오버로드를 쓴다). 실행 후에는 keyGenerator.processAfter가 getGeneratedKeys()로 받은 결과 집합에서 키를 읽어 keyProperty로 지정한 프로퍼티에 넣는다. 위 실험 3번이 바로 이 JDBC 호출이며, H2가 새로 만든 id 3을 돌려주었다. MyBatisBookRepository.save가 반환값 없이 book을 그대로 돌려주는데도 id가 채워져 있는 이유다. 공식 Java API 문서는 일부 DB(예: Oracle, PostgreSQL)에서는 keyColumn이 필요하다고 밝히고 있다.

    SqlSession과 스프링 트랜잭션: 세션은 누가 열고 닫는가

    MyBatis를 스프링 없이 쓰면 개발자가 SqlSessionFactory.openSession()으로 세션을 열고, 작업 후 commit()과 close()를 직접 부른다. 공식 문서는 SqlSession에 대해 "각 스레드는 자기 SqlSession 인스턴스를 가져야 하며, SqlSession은 공유하면 안 되고 스레드 안전하지 않다"고 못 박는다. 세션은 커넥션 하나, 실행기 하나, 로컬 캐시 하나를 품은 상태 덩어리이기 때문이다. 그런데 매퍼 빈은 싱글톤이고 여러 요청 스레드가 동시에 호출한다. 스레드 안전하지 않은 세션을 쓰는 싱글톤이 어떻게 안전할 수 있을까.

    답은 매퍼 프록시가 쥔 것이 진짜 세션이 아니라 SqlSessionTemplate이라는 데 있다. 공식 문서는 SqlSessionTemplate이 스레드 안전하고 여러 매퍼가 공유할 수 있으며, 세션의 열기·커밋·롤백·닫기를 대신 관리하고, 현재 스프링 트랜잭션에 연결된 세션을 쓰도록 보장한다고 설명한다. 템플릿 자체는 상태를 갖지 않고, 호출이 올 때마다 앞에서 본 SqlSessionInterceptor가 "지금 이 스레드에 맞는 진짜 세션"을 찾아 쓴다. 그 결정을 하는 SqlSessionUtils.getSqlSession의 동작은 다음과 같다.

    1. TransactionSynchronizationManager.getResource(sqlSessionFactory)로 현재 스레드에 묶인 SqlSessionHolder를 찾는다. 스프링 DB 1편에서 본 것처럼 이 관리자는 스레드 로컬(ThreadLocal) 기반의 저장소이고, 여기서는 SqlSessionFactory가 키다.
    2. 트랜잭션과 동기화된 홀더가 있으면 그 안의 세션을 재사용하고 참조 횟수를 올린다. 이때 요청한 실행기 종류가 홀더의 것과 다르면 "기존 트랜잭션이 있는 동안 실행기 종류를 바꿀 수 없다"는 TransientDataAccessResourceException을 던진다.
    3. 없으면 sessionFactory.openSession(executorType)으로 새 세션을 연다. 트랜잭션 동기화가 활성화되어 있으면(즉 스프링 트랜잭션 안이면) 새 세션을 홀더에 담아 스레드에 묶고, 트랜잭션이 끝날 때 세션을 정리할 동기화 콜백(SqlSessionSynchronization)을 등록한다. 동기화가 활성화되어 있지 않으면 묶지 않고 그냥 돌려준다.

    호출이 끝나면 SqlSessionInterceptor는 세션이 트랜잭션에 묶인 것인지 확인한다. 묶인 세션이면 커밋하지 않고, 세션을 닫는 대신 홀더의 참조 횟수만 줄인다. 실제 커밋과 정리는 트랜잭션이 끝날 때 등록해 둔 동기화 콜백과 트랜잭션 매니저가 한다. 묶이지 않은 세션이면 그 자리에서 sqlSession.commit(true)를 부르고 세션을 닫는다. 소스 주석은 변경이 없는 세션도 강제로 커밋하는 이유를 일부 DB가 닫기 전에 커밋이나 롤백을 요구하기 때문이라고 적고 있다.

    커넥션은 어떨까. 세션이 쓰는 MyBatis 트랜잭션 객체는 SpringManagedTransaction이고, 처음 커넥션이 필요할 때 DataSourceUtils.getConnection(dataSource)를 부른다. 스프링 트랜잭션 안이라면 트랜잭션 매니저가 시작할 때 setAutoCommit(false)로 바꿔 스레드에 묶어 둔 바로 그 커넥션이 나온다. 이 경우 SpringManagedTransaction은 그 커넥션을 "트랜잭션에 묶인 커넥션"으로 표시하고, 자신의 commit(), rollback()은 아무 일도 하지 않는다. 진짜 커밋은 스프링 트랜잭션 매니저의 몫이다. 공식 문서가 트랜잭션 매니저와 SqlSessionFactoryBean이 같은 DataSource를 써야 한다고 강조하는 이유도 여기서 나온다. 다른 DataSource를 쓰면 DataSourceUtils가 트랜잭션 커넥션을 찾지 못해 MyBatis는 별도의 커넥션에서 실행되고, 스프링의 롤백이 MyBatis의 변경을 되돌리지 못한다.

    공식 문서는 두 가지 규칙을 덧붙인다. 첫째, 스프링 트랜잭션 밖에서 호출한 매퍼 메서드는 JDBC 커넥션의 자동 커밋 설정과 상관없이 호출마다 커밋된다. 그래서 서비스 메서드에 @Transactional을 빠뜨리면 "재고 차감"과 "주문 저장" 사이에서 예외가 나도 앞의 변경이 이미 커밋되어 있다. 둘째, 스프링이 관리하는 세션에 대해 commit(), rollback(), close()를 직접 부를 수 없다. 실제로 SqlSessionTemplate의 이 메서드들은 "Manual commit is not allowed over a Spring managed SqlSession" 같은 메시지로 UnsupportedOperationException을 던지도록 구현되어 있다. 트랜잭션 경계는 스프링이 정하고 MyBatis는 그 안에서만 움직인다는 설계가 코드로 강제되는 것이다.

    로컬 캐시: 같은 트랜잭션에서 같은 조회를 두 번 하면

    세션이 트랜잭션 동안 재사용된다는 사실에는 눈에 잘 띄지 않는 결과가 하나 따른다. MyBatis의 실행기(BaseExecutor)는 세션마다 로컬 캐시(local cache)를 가진다. 공식 설정표의 localCacheScope 기본값은 SESSION으로, 세션 동안 실행한 조회 결과가 모두 캐시된다. 캐시 키는 문장 ID, 페이징 범위(offset, limit), 최종 SQL, 각 파라미터 값, 환경 ID로 만들어진다. 조회할 때 같은 키의 결과가 캐시에 있으면 DB에 가지 않고 그 결과를 돌려준다.

    @Transactional
public void readTwice(Long id) {
    Book a = bookMapper.findById(id).orElseThrow();
    Book b = bookMapper.findById(id).orElseThrow();
    System.out.println(a == b);
}

    이 메서드가 트랜잭션 안에서 실행되면 두 호출은 같은 세션 S1을 쓴다. 두 번째 호출은 문장 ID, SQL, 파라미터 값이 모두 같으므로 캐시 키가 같고, 실행기는 첫 번째 조회 때 저장한 바로 그 리스트를 돌려준다. 단건 조회는 그 리스트의 첫 원소를 꺼내므로 a == b는 true이고, SQL 로그에도 조회가 한 번만 찍힌다. 같은 코드에서 @Transactional을 빼면 호출마다 새 세션이 열리므로 캐시가 공유되지 않고, SQL이 두 번 나가며 a == b는 false다. 02회에서 본 것처럼 테스트 클래스에 @Transactional을 붙이면 테스트 메서드 전체가 하나의 세션 안에서 돌아간다는 점도 함께 기억하자.

    이 캐시가 문제를 일으키는 경우는 세 가지다. 첫째, 두 조회 사이에 다른 트랜잭션이 그 행을 바꾸고 커밋했다면 두 번째 조회는 DB를 보지 않으므로 바뀐 값을 보지 못한다. MySQL InnoDB의 기본 격리 수준인 REPEATABLE READ에서는 일관된 읽기 스냅숏 때문에 어차피 같은 값을 보지만, READ COMMITTED로 운영하는 시스템이라면 DB가 보여 줄 수 있었던 최신 값을 MyBatis 캐시가 가린 셈이다. 둘째, 캐시에서 돌려준 객체는 캐시에 저장된 객체 그 자체이므로, 첫 번째 결과의 필드를 바꾸면 두 번째 조회 결과도 바뀌어 보인다. 셋째, 이 동작은 트랜잭션이 있느냐에 따라 달라지므로 같은 코드가 호출 위치에 따라 다르게 동작한다.

    캐시가 무효화되는 시점도 소스에 분명하게 나와 있다. 실행기의 update()(INSERT, UPDATE, DELETE 모두 이 경로다)는 실행 전에 로컬 캐시를 비우고, 커밋과 롤백도 캐시를 비운다. SELECT 문장의 flushCache 기본값은 false이므로 조회는 캐시를 비우지 않는다. 같은 세션에서 직접 데이터를 바꾸면 이후 조회는 DB로 가지만, 다른 트랜잭션의 변경은 감지할 방법이 없다. 세션 동안 결과를 재사용하는 것이 싫다면 mybatis.configuration.local-cache-scope=statement로 범위를 문장 단위로 줄인다. 그러면 조회가 끝날 때마다 캐시가 비워져 문장 사이에 결과가 재사용되지 않는다. 특정 조회만 매번 DB에서 읽게 하려면 그 <select>에 flushCache="true"를 붙인다.

    기능 정리 1 — 동적 쿼리

    MyBatis를 고르는 가장 큰 이유인 동적 SQL을 보자. 공식 문서는 동적 SQL 요소로 if, choose(when, otherwise), trim(where, set), foreach, bind를 제공하고, 조건식에는 OGNL 기반 표현식을 쓴다고 설명한다. 요소별 사용법보다 먼저 이 요소들이 언제, 어떻게 SQL이 되는지를 이해하면 나머지는 쉽게 따라온다.

    XML이 SqlNode 트리가 되고, 호출마다 SQL이 된다

    기동 시점에 XMLScriptBuilder는 <select>의 내용을 SqlNode 트리로 바꾼다. 평범한 텍스트는 StaticTextSqlNode가 되고, ${}가 들어간 텍스트는 TextSqlNode가 되며, if, where, foreach 같은 요소는 각각의 노드가 된다(when은 if와 같은 처리기를 쓴다). 트리 안에 요소 노드나 ${}가 하나라도 있으면 문장은 "동적"으로 표시되어 DynamicSqlSource가 되고, 그렇지 않으면 RawSqlSource가 된다. RawSqlSource는 기동 시점에 #{}를 ?로 바꾸는 파싱을 한 번만 해 둔다. DynamicSqlSource는 호출될 때마다 새 DynamicContext를 만들고, 트리의 루트부터 apply를 호출해 조건에 맞는 조각만 문자열 버퍼에 붙인 다음, 완성된 문자열에서 #{}를 ?로 바꾸고 파라미터 매핑 목록을 만들어 BoundSql을 돌려준다.

    findAll 문장의 SqlNode 트리                     cond = { title: null, maxPrice: 26000 }

MixedSqlNode
 ├ StaticTextSqlNode  "select id, title, price, stock_quantity from book"   → 그대로 붙임
 └ WhereSqlNode  (prefix "WHERE", prefixOverrides "AND ", "OR ", ...)
    └ MixedSqlNode
       ├ IfSqlNode test="title != null and title != ''"                    → 거짓: 붙이지 않음

       └ IfSqlNode test="maxPrice != null"                                  → 참

WhereSqlNode 내부 버퍼: "and price <= #{maxPrice}"
  1) 앞뒤 공백 제거, 대문자 사본 "AND PRICE <= #{MAXPRICE}" 로 비교
  2) "AND " 로 시작 → 원본에서 공백을 뺀 길이(3글자 "and") 삭제 → " price <= #{maxPrice}"
  3) 내용이 비어 있지 않음 → 앞에 "WHERE" + " " 삽입 → "WHERE  price <= #{maxPrice}" (공백 두 칸은 SQL 의미에 영향 없음)

최종 문자열에서 #{} 치환 → "select ... from book WHERE price <= ?"   파라미터: [maxPrice=26000]

    <where>의 정체는 접두사가 WHERE이고 제거 대상 접두사 목록이 "AND ", "OR ", "AND\n", "OR\n", "AND\r", "OR\r", "AND\t", "OR\t"인 TrimSqlNode다. TrimSqlNode는 자식이 만든 문자열의 앞뒤 공백을 지우고, 대문자로 바꾼 사본으로 제거 대상과 비교한 뒤, 일치한 제거 대상에서 앞뒤 공백을 뺀 길이("AND "면 세 글자)만큼 원본의 앞을 지운다. 그리고 남은 내용이 비어 있지 않을 때만 접두사를 붙인다. 따라서 조건이 하나도 맞지 않으면 WHERE 자체가 붙지 않는다. 소문자 and로 써도 제거되는 것은 대문자 사본으로 비교하기 때문이고, 로그에서 WHERE만 대문자로 보이는 것은 접두사 문자열이 대문자이기 때문이다.

    제거 대상이 "AND"가 아니라 "AND "처럼 공백을 포함하는 데도 이유가 있다. 조건 조각이 order_count > 0처럼 OR로 시작하는 컬럼 이름으로 시작해도, 대문자 사본 ORDER_COUNT는 "OR "로 시작하지 않으므로 잘려 나가지 않는다. 공식 문서도 <trim prefix="WHERE" prefixOverrides="AND |OR ">가 <where>와 같다고 설명하면서 이 공백이 중요하다고 강조한다. 직접 <trim>을 쓸 때 prefixOverrides="AND|OR"처럼 공백을 빼면 이 보호 장치가 사라진다. 여러 값은 |로 구분한다.

    조건식(test)은 OGNL로 평가된다. 파라미터 객체의 프로퍼티 이름을 바로 쓸 수 있고, 논리 연산은 and, or로 쓴다. XML 속성 안에서 &&를 쓰려면 &amp;&amp;로 이스케이프해야 하므로 and가 훨씬 읽기 쉽다. title != null and title != ''처럼 null과 빈 문자열을 함께 거르는 것은 검색 폼에서 빈 입력이 빈 문자열로 들어오는 경우를 막기 위한 흔한 패턴이다.

    애너테이션으로 SQL 쓰기

    짧은 SQL은 XML 대신 매퍼 메서드에 애너테이션으로 붙일 수 있다.

    @Mapper
public interface BookQueryMapper {

    @Select("select id, title, price, stock_quantity from book where id = #{id}")
    Optional findById(Long id);

    @Insert("insert into book (title, price, stock_quantity) values (#{title}, #{price}, #{stockQuantity})")
    @Options(useGeneratedKeys = true, keyProperty = "id")
    void save(Book book);

    @Update({""})
    void updateSelective(@Param("id") Long id, @Param("form") BookUpdateForm form);
}

    애너테이션 문장도 기동 시점에 MapperAnnotationBuilder가 읽어 XML과 똑같은 MappedStatement로 등록하므로, 실행 경로는 앞에서 추적한 것과 완전히 같다. 같은 문장 ID가 XML과 애너테이션 양쪽에 있으면 같은 키로 두 번 등록하려다 설정 단계에서 실패하므로, 메서드 하나의 SQL은 한 곳에만 둔다. 문자열 배열은 공백으로 이어 붙여진다. 동적 SQL이 필요하면 위처럼 <script>로 감싸 XML 요소를 쓸 수 있지만, 자바 문자열 안의 XML은 금방 읽기 어려워진다. 공식 Java API 문서도 자바 애너테이션은 표현력과 유연성이 제한되어 있어 가장 강력한 매핑은 애너테이션으로 만들 수 없다고 밝히며, 조인 결과 매핑은 애너테이션 API로 지원하지 않는다고 적고 있다. 또 @Options를 붙이는 순간 그 문장은 @Options의 모든 기본값을 따르게 된다는 경고도 있다. 단순 CRUD는 애너테이션, 동적 조건이나 복잡한 매핑은 XML로 나누는 것이 무난하다.

    ${alias}.id, ${alias}.title, ${alias}.price, ${alias}.stock_quantity

    resultMap: 매핑을 명시하기

    자동 매핑으로 부족할 때는 <resultMap>으로 컬럼과 프로퍼티의 대응을 직접 적는다. 공식 문서는 한 문장에 resultType과 resultMap 중 하나만 쓰라고 규정한다.

    <id>는 결과 객체의 식별자를 표시하는데, 조인 결과를 객체 그래프로 묶을 때(한 권의 책에 여러 리뷰가 달린 경우 등) 같은 식별자의 행을 하나의 객체로 합치는 기준이 된다. 연관 객체는 <association>, 컬렉션은 <collection>으로 매핑한다. 이때 조인 한 번으로 가져와 매핑하는 방식과, 연관 객체마다 별도의 select를 실행하는 "중첩 조회(nested select)" 방식이 있다. 공식 문서는 후자가 목록 조회에서 레코드 수만큼 추가 조회를 일으키는 "N+1 조회 문제(N+1 Selects Problem)"를 낳는다고 직접 경고한다. 이 문제는 04회 이후 JPA에서도 다시 만나는데, SQL을 직접 쓰는 MyBatis에서는 적어도 그 SQL이 XML에 보인다는 차이가 있다.

    XML 특수 문자와 CDATA

    MyBatis XML도 XML이므로 텍스트에 <와 &를 그대로 쓸 수 없다. 앞에서처럼 &lt;, &amp;로 쓰거나, 비교 연산자가 많은 구간을 <![CDATA[ ... ]]>로 감싼다. CDATA 구간은 XML 파서가 문자 데이터로 취급하는 영역이라 그 안에서는 이스케이프가 필요 없다. 그 대신 CDATA 안에 쓴 <if>, <where>도 요소가 아니라 그냥 글자가 되므로 동적 SQL로 동작하지 않는다. 그래서 CDATA는 동적 요소 바깥의 정적인 조건에만 좁게 쓴다.

    실행기 종류와 2차 캐시

    공식 설정표의 defaultExecutorType은 세 가지다. 기본값 SIMPLE은 특별한 일을 하지 않고 문장마다 새 PreparedStatement를 만든다. REUSE는 준비 문장을 재사용하고, BATCH는 문장 재사용에 더해 갱신 문장을 모아 일괄 실행한다. 스프링 부트에서는 mybatis.executor-type으로 바꾸거나, BATCH용 SqlSessionTemplate을 따로 만들어 쓴다. 다만 MyBatis-Spring 문서가 경고하듯 이미 다른 실행기 종류로 진행 중인 트랜잭션 안에서 BATCH 세션을 요청할 수 없다. 앞에서 본 getSqlSession의 "실행기 종류를 바꿀 수 없다" 예외가 그것이다. 문서는 이런 호출을 별도 트랜잭션(REQUIRES_NEW 등)이나 트랜잭션 밖에서 하라고 권하는데, 전파 옵션은 08회의 주제다.

    공식 문서에 따르면 기본으로는 세션 동안만 유지되는 로컬 캐시만 켜져 있고, 매퍼 XML에 <cache/> 한 줄을 추가하면 네임스페이스 단위의 2차 캐시가 켜진다. 기본 동작은 그 파일의 SELECT 결과를 캐시하고, 같은 파일의 INSERT·UPDATE·DELETE가 캐시를 비우며, LRU로 최대 1024개의 참조를 유지하는 것이다. 이 캐시는 SqlSessionFactory, 즉 한 JVM 안에 있다. 서버를 여러 대 띄우면 각 서버가 자기 캐시를 갖고, 다른 서버에서 일어난 변경이나 다른 네임스페이스의 SQL이 같은 테이블을 바꾼 경우는 이 캐시가 알지 못한다. 2차 캐시는 이런 조건을 모두 따져 본 뒤에만 켜는 기능이다.

    정리: MyBatis가 하는 일과 하지 않는 일

    이 회차에서 추적한 내용을 계층별로 다시 묶어 보자. 기동 시점에 매퍼 스캐너는 @Mapper 인터페이스를 MapperFactoryBean으로 등록하고, MapperFactoryBean은 인터페이스 이름에서 XML 경로를 계산해 SQL을 MappedStatement로 등록한 뒤, Proxy.newProxyInstance로 만든 JDK 동적 프록시를 빈으로 내놓는다. 호출 시점에 프록시는 메서드를 문장 ID와 파라미터 객체로 바꾸고, SqlSessionTemplate은 스레드에 묶인 트랜잭션 세션을 찾거나 새로 열며, 실행기는 SQL을 조립하고 로컬 캐시를 확인한 뒤, 스프링 트랜잭션이 잡아 둔 커넥션으로 JDBC를 호출한다. 오류는 스프링의 DataAccessException으로 번역되어 올라온다.

    MyBatis가 하지 않는 일도 분명하다. SQL을 만들지 않고, 객체 상태를 추적하지 않으며, 커넥션 풀과 트랜잭션 경계를 소유하지 않는다. 그래서 "어떤 SQL이 언제 나가는가"가 항상 투명하고, 복잡한 통계 쿼리나 DB 고유 기능을 쓰는 SQL을 그대로 옮겨 쓰기 좋다. 대신 테이블에 컬럼 하나가 추가되면 그 테이블을 다루는 모든 SQL을 손으로 고쳐야 하고, 단순한 CRUD도 매번 SQL로 써야 한다. 04회와 05회에서 볼 JPA와 스프링 데이터 JPA는 정확히 이 반복을 없애는 대신 SQL 생성의 주도권을 프레임워크에 넘긴다. 06회에서는 이런 기술들을 한 프로젝트에서 어떻게 조합할지를 다룬다.

    이 장의 핵심

    매퍼 빈은 SqlSessionTemplate을 쥔 JDK 동적 프록시이고, 메서드 이름은 인터페이스 이름 + "." + 메서드 이름이라는 문장 ID로 바뀌어 XML의 SQL을 찾는다. 진짜 SqlSession은 스레드 안전하지 않으므로 트랜잭션마다 스레드에 묶여 재사용되고, 그 결과 커넥션·커밋·로컬 캐시의 범위가 모두 스프링 트랜잭션의 범위를 따른다. #{}는 값의 자리를 고정하는 바인딩이고 ${}는 SQL 구조를 바꾸는 치환이므로, 치환에는 코드가 정한 상수만 넣는다.
    SQL 매퍼
    개발자가 쓴 SQL에 객체의 값을 바인딩해 실행하고 결과 행을 객체로 옮기는 기술. SQL을 생성하거나 객체 상태를 추적하지 않는다는 점에서 ORM과 다르다.
    매퍼 인터페이스와 문장 ID
    XML의 namespace는 인터페이스의 전체 이름과 같아야 하고, 메서드 호출은 "인터페이스 이름.메서드 이름"이라는 문장 ID로 MappedStatement를 찾는다. 그래서 오버로딩이 통하지 않는다.
    매퍼 프록시
    @Mapper 인터페이스는 MapperFactoryBean으로 등록되고, 그 getObject()가 Proxy.newProxyInstance로 만든 JDK 동적 프록시가 빈이 된다. 모든 호출은 MapperProxy.invoke로 모인다.
    XML 위치 규칙
    인터페이스 이름의 점을 슬래시로 바꾼 경로의 .xml이 자동으로 로드된다. 로드되지 않아도 기동은 성공하고 첫 호출에서 Invalid bound statement (not found)가 난다.
    파라미터 이름 해석
    @Param 값, -parameters로 남긴 실제 이름, 위치 번호 순으로 이름이 정해진다. @Param 없는 인자 하나는 객체 자체가, 그 밖에는 이름과 param1, param2가 담긴 맵이 파라미터 객체가 된다.
    #{}와 ${}
    #{}는 PreparedStatement의 ?로 바인딩되어 SQL 구조를 바꿀 수 없고, ${}는 이스케이프 없이 문자열을 끼워 넣어 SQL 구조를 바꾼다. 정렬 컬럼처럼 식별자를 바꿀 때만 ${}를 쓰고 값은 코드의 상수로 제한한다.
    SqlSessionTemplate
    스레드 안전한 SqlSession 구현. 호출마다 현재 스레드의 스프링 트랜잭션에 묶인 세션을 쓰거나 새로 열고, 트랜잭션 밖이면 즉시 커밋하고 닫으며, MyBatis 예외를 DataAccessException으로 번역한다.
    로컬 캐시
    세션마다 있는 조회 결과 캐시로 기본 범위는 SESSION이다. 트랜잭션 안에서는 같은 조회가 DB를 거치지 않고 같은 객체를 돌려줄 수 있고, 갱신·커밋·롤백 때 비워진다.
    동적 SQL
    XML이 기동 시점에 SqlNode 트리가 되고 호출마다 조건에 맞는 조각만 이어 붙여 BoundSql을 만든다. where와 set은 앞뒤의 AND/OR나 쉼표를 다듬는 trim의 특수형이다.

    운영 중에 "로컬에서는 되는데 서버에서만 Invalid bound statement (not found)가 난다"는 장애는 대부분 빌드 산출물에 XML이 빠진 경우다. 애플리케이션이 정상 기동하므로 배포 직후 헬스 체크로는 잡히지 않고, 그 매퍼를 처음 호출하는 요청에서야 드러난다. 기동 과정을 알고 있으면 원인을 SQL이 아니라 클래스패스에서 찾게 되고, JAR 안에 com/example/.../BookMapper.xml이 들어 있는지부터 확인하게 된다. 같은 이유로 매퍼 문장 전체를 한 번씩 실행하는 통합 테스트는 설정 오류를 배포 전에 잡는 가장 값싼 장치다.

    ${}는 코드 리뷰에서 반드시 짚어야 하는 표기다. 정렬, 동적 컬럼, 테이블 이름 분기처럼 정당한 쓰임새가 있지만, 그 값이 어디서 왔는지 끝까지 추적해 "코드가 정한 상수"인지 확인해야 한다. 화면의 정렬 파라미터를 그대로 order by ${sort}에 넘기는 코드는 SQL 인젝션 경로다. 입력을 검사하는 것보다 허용 목록으로 대응시키는 방식이 안전한 것은, 검사는 빠뜨린 경우가 생길 수 있지만 대응은 목록 밖의 값을 원천적으로 만들 수 없기 때문이다.

    트랜잭션 경계는 MyBatis 코드의 정확성을 좌우한다. 여러 매퍼 호출을 묶어야 하는 서비스 메서드에서 @Transactional을 빠뜨리면, MyBatis-Spring 문서대로 매퍼 호출마다 커밋되어 중간 실패가 데이터 불일치로 남는다. 반대로 긴 트랜잭션 안에서 같은 조회를 반복하는 배치나 폴링 코드는 로컬 캐시 때문에 DB의 새 값을 보지 못할 수 있다. 이런 코드라면 local-cache-scope=statement나 문장별 flushCache="true"를 고려하고, 실행기 종류를 바꾸는 배치 처리는 별도 트랜잭션으로 분리한다. 트랜잭션 전파와 롤백 규칙은 07~09회에서 이 그림 위에 쌓인다.

    1번. 공통 앞부분은 select id, title, price, stock_quantity from book이다. (a) title="JV"이면 첫 if만 참이다. <where>의 버퍼는 and title like concat('%', #{title}, '%')이고, 대문자 사본이 "AND "로 시작하므로 공백을 뺀 길이만큼 앞 세 글자(and)를 지운 뒤 WHERE 를 붙인다. 최종 SQL은 ... from book WHERE title like concat('%', ?, '%'), 바인딩 값은 "JV" 하나다.     2번. 인자가 둘이므로 어느 경우든 ParamMap이 만들어지고 param1, param2가 들어간다. (a) 스프링 부트 Gradle 플러그인은 -parameters를 추가하므로 Parameter.getName()이 id, form을 돌려주고, 기본값 useActualParamName=true에 따라 키는 id, form, param1, param2다. XML이 그대로 동작한다. (b) 이름 정보가 없으므로 getName()이 arg0, arg1을 돌려주고, 키는 arg0, arg1, param1, param2가 된다. #{id}를 평가하는 순간 id라는 키가 없어 사용 가능한 이름을 나열하는 BindingException이 난다. 본문의 미니 프록시 실험에서 [arg0, arg1]과 [id, price]가 갈린 것과 같은 원리다. 빌드 경로에 따라 결과가 달라지므로 @Param을 붙이는 것이 안전하다.

    4번. (1) XML이 산출물에 없다. src/main/java에 두었거나 리소스 경로가 패키지와 다르면 loadXmlResource()가 계산한 com/example/report/ReportMapper.xml을 찾지 못하고 조용히 넘어간다. JAR 안의 경로를 확인한다. (2) XML은 있지만 namespace가 인터페이스 전체 이름과 다르다. 그러면 등록된 문장 ID가 메서드가 찾는 ID와 달라진다. XML의 namespace 문자열을 확인한다. (3) id가 메서드 이름과 다르다(monthly와 monthlyReport 등). 위 세 가지 모두 기동 시점에는 오류가 아니고, MapperMethod가 처음 만들어지는 첫 호출에서야 드러난다. mapper-locations를 쓰는 프로젝트라면 그 패턴이 실제 XML 위치와 맞는지도 확인한다. 디버그 로그나 테스트에서 Configuration.getMappedStatementNames()로 등록된 문장 ID를 나열해 보는 것도 직접적인 확인 방법이다.

DB 커넥션 풀의 최대 크기가 부족한지 매퍼 XML이 클래스패스에 올바른 경로로 들어가 있고 namespace와 id가 인터페이스 이름·메서드 이름과 일치하는지 서비스 메서드에 @Transactional이 붙어 있는지 WHERE 절의 SQL 문법이 DB에 맞는지 이 예외는 MapperMethod가 "인터페이스 이름.메서드 이름"으로 MappedStatement를 찾지 못했을 때 던진다. XML이 로드되지 않아도 기동은 성공하고 첫 호출에서야 문장을 찾기 때문에 이런 증상이 나온다. 커넥션 풀이나 트랜잭션은 문장을 찾은 뒤의 일이고, SQL 문법 오류는 실행 단계에서 SQLException(번역 후 BadSqlGrammarException 등)으로 나타난다. MyBatis의 SqlSession은 스레드 안전하지 않은데, 싱글톤 매퍼 빈을 여러 요청 스레드가 동시에 호출해도 안전한 이유는? 매퍼 빈이 요청마다 새로 생성되는 프로토타입 빈이기 때문이다. MapperProxy가 모든 호출을 synchronized로 직렬화하기 때문이다. 매퍼 프록시가 쥔 것은 SqlSessionTemplate이고, 템플릿이 호출마다 현재 스레드에 묶인 세션을 찾거나 새로 열어 쓰기 때문이다. DefaultSqlSession이 내부적으로 커넥션 풀을 써서 스레드마다 커넥션을 나눠 주기 때문이다. MapperFactoryBean.isSingleton()은 true이므로 매퍼 빈은 싱글톤이다. 안전성은 잠금이 아니라 위임 구조에서 나온다. SqlSessionTemplate 자체는 상태가 없고, SqlSessionInterceptor가 TransactionSynchronizationManager(스레드 로컬)에서 현재 스레드의 세션을 찾거나, 트랜잭션 밖이면 호출마다 새 세션을 열고 닫는다. DefaultSqlSession은 커넥션 풀을 관리하지 않으며, 그 자체는 공식 문서대로 공유하면 안 되는 객체다. 사용자가 고른 컬럼으로 정렬하려고 order by #{sort}라고 썼더니 정렬이 되지 않거나 오류가 났다. 올바른 진단과 해결은? #{}는 값의 자리인 ?가 되어 컬럼 이름 같은 식별자를 대신할 수 없다. ${}를 쓰되, 넣는 값은 허용 목록으로 대응시킨 코드의 상수로 제한한다. #{}가 값을 따옴표로 감싸기 때문이므로 ${}로 바꾸고 사용자 입력을 그대로 넘기면 된다. ORDER BY에는 바인딩이 지원되지 않으므로 resultMap으로 정렬 순서를 지정해야 한다. mapUnderscoreToCamelCase를 켜면 정렬 컬럼 이름이 자동으로 변환되어 해결된다. PreparedStatement의 파라미터는 값만 대신할 수 있다. 본문의 H2 실험에서 order by ?에 "price"를 바인딩하자 데이터 변환 오류가 났다. 식별자를 바꾸려면 ${}가 필요하지만 ${}는 이스케이프 없이 끼워 넣으므로 사용자 입력을 그대로 넘기면 SQL 인젝션 경로가 된다. resultMap은 결과 매핑 설정이고, mapUnderscoreToCamelCase는 결과 컬럼을 프로퍼티에 매핑할 때만 쓰인다. @Transactional 메서드 안에서 다른 문장을 사이에 두지 않고 bookMapper.findById(1L)를 연속으로 두 번 호출했다. 기본 설정에서 맞는 설명은? 호출마다 새 SqlSession이 열리므로 SQL이 두 번 실행되고 서로 다른 객체가 반환된다. MyBatis는 영속성 컨텍스트로 엔티티를 관리하므로 첫 조회 결과를 변경 감지 대상으로 등록한다. 2차 캐시가 기본으로 켜져 있어 다른 트랜잭션의 조회 결과까지 공유된다. 같은 SqlSession이 재사용되고 로컬 캐시(기본 범위 SESSION)에 같은 캐시 키가 있으므로 두 번째는 DB에 가지 않고 같은 객체를 돌려준다. 트랜잭션 안에서는 SqlSessionUtils가 세션을 스레드에 묶어 재사용하고, BaseExecutor의 로컬 캐시는 문장 ID·SQL·파라미터 값이 같은 조회에 저장된 리스트를 그대로 돌려준다. 그래서 a == b가 true다. 트랜잭션 밖이라면 호출마다 세션이 새로 열려 첫 번째 보기처럼 동작한다. MyBatis에는 변경 감지가 없고, 2차 캐시는 매퍼 XML에 <cache/>를 선언해야 켜진다. <set> 안의 세 <if>가 모두 거짓인 상태로 updateSelective를 호출했다. 어떤 일이 일어나는가? MyBatis가 내용 없는 UPDATE를 감지하고 호출을 건너뛴다. set 요소가 빈 내용에는 SET을 붙이지 않으므로 update book where id = ?가 만들어지고 DB에서 문법 오류가 난다. 모든 컬럼이 NULL로 갱신된다. set 요소가 마지막 쉼표를 지우는 과정에서 where 절까지 지워 전체 행이 갱신된다. set은 TrimSqlNode의 특수형으로, 자식 내용의 앞뒤 공백을 지운 뒤 비어 있지 않을 때만 SET 접두사를 붙이고 끝의 쉼표를 지운다. 내용이 비면 아무것도 붙지 않아 SET 없는 UPDATE가 되고, H2 2.4.240에서 이 문장은 SQLState 42001 문법 오류를 낸다. MyBatis는 SQL의 의미를 검사하지 않으므로 호출을 건너뛰지 않으며, where 절은 set 요소 바깥에 있어 영향을 받지 않는다.
    SQL 매퍼(SQL mapper)
    개발자가 작성한 SQL에 파라미터를 바인딩해 실행하고 결과를 객체로 매핑해 주는 데이터 접근 기술. MyBatis가 대표적이다.
    매퍼 인터페이스(mapper interface)
    SQL 문장에 대응하는 메서드만 선언한 자바 인터페이스. 구현은 MyBatis가 JDK 동적 프록시로 제공한다.
    MappedStatement
    XML 요소나 애너테이션 하나를 해석한 결과. SQL 원천, 문장 종류, 결과 매핑, 키 생성기 등을 담고 "네임스페이스.id"를 키로 Configuration에 등록된다.
    SqlSession
    MyBatis에서 문장을 실행하는 단위 객체. 실행기와 커넥션, 로컬 캐시를 품고 있으며 스레드 안전하지 않다.
    SqlSessionTemplate
    MyBatis-Spring이 제공하는 스레드 안전한 SqlSession 구현. 스프링 트랜잭션에 묶인 세션을 찾아 위임하고 예외를 스프링 예외로 번역한다.
    JDK 동적 프록시(dynamic proxy)
    java.lang.reflect.Proxy가 실행 중에 생성하는 인터페이스 구현 클래스. 모든 메서드 호출을 InvocationHandler.invoke 하나로 전달한다.
    문자열 치환(string substitution)
    ${} 표기. 값을 이스케이프하지 않고 SQL 문자열에 그대로 끼워 넣는 MyBatis의 기능으로, 식별자를 바꿀 때만 제한적으로 쓴다.
    로컬 캐시(local cache)
    SqlSession마다 있는 조회 결과 캐시. 기본 범위는 SESSION이며 갱신 문장, 커밋, 롤백 때 비워진다.
    OGNL(Object-Graph Navigation Language)
    MyBatis 동적 SQL의 test, bind 속성에서 쓰는 표현식 언어. 파라미터 객체의 프로퍼티를 이름으로 탐색하고 비교·논리 연산을 할 수 있다.
