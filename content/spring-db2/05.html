    이 회차의 질문: 리포지토리 코드는 왜 다 비슷하게 생겼나

    이 권은 01회부터 도서(Book) 예제와 BookRepository 인터페이스를 고정해 두고, 그 뒤의 데이터 접근 기술만 바꿔 끼워 왔다. 01회의 JdbcTemplate, 03회의 MyBatis, 04회의 JPA가 모두 같은 인터페이스를 구현했고, 서비스는 어떤 구현이 들어왔는지 모른다. 이 회차는 같은 자리에 스프링 데이터 JPA(Spring Data JPA)를 끼운다. 그 전에 JPA로 직접 짠 리포지토리를 다시 보면서 무엇이 반복되는지부터 확인하자.

    아래는 EntityManager로 직접 작성한 전형적인 리포지토리다. 엔티티를 저장하고, 식별자로 찾고, 전부 찾고, 세고, 지운다. 04회에서 본 대로 persist는 엔티티를 영속성 컨텍스트에 넣고, find는 1차 캐시를 먼저 본 뒤 없으면 SELECT를 보내며, JPQL 조회는 영속성 컨텍스트를 거치지 않고 바로 SQL로 번역된다.

    @Repository
@Transactional
public class JpaBookRepositoryV0 {

    private final EntityManager em;

    public JpaBookRepositoryV0(EntityManager em) {
        this.em = em;
    }

    public Book save(Book book) {
        em.persist(book);
        return book;
    }

    public Optional findById(Long id) {
        return Optional.ofNullable(em.find(Book.class, id));
    }

    public List findAll() {
        return em.createQuery("select b from Book b", Book.class).getResultList();
    }

    public long count() {
        return em.createQuery("select count(b) from Book b", Long.class).getSingleResult();
    }

    public void delete(Book book) {
        em.remove(book);
    }

    public List findByTitle(String title) {
        return em.createQuery("select b from Book b where b.title = :title", Book.class)
                .setParameter("title", title)
                .getResultList();
    }
}

    이제 출판사(Publisher) 엔티티의 리포지토리를 만든다고 해 보자. 위 코드를 복사해서 Book을 Publisher로, 식별자 타입 Long을 String으로 바꾸면 처음 다섯 메서드는 끝난다. 회원, 주문, 배송 엔티티도 마찬가지다. 엔티티가 서른 개면 거의 같은 코드가 서른 벌 생긴다. 다른 것은 엔티티 타입과 식별자 타입 두 가지뿐이다. 이 두 가지는 제네릭(generic) 타입 매개변수로 뽑아낼 수 있다.

    제네릭 리포지토리로 한 번 줄여 보기

    public abstract class GenericJpaRepository {

    protected final EntityManager em;
    private final Class type;

    protected GenericJpaRepository(EntityManager em, Class type) {
        this.em = em;
        this.type = type;
    }

    public T save(T entity) {
        em.persist(entity);
        return entity;
    }

    public Optional findById(ID id) {
        return Optional.ofNullable(em.find(type, id));
    }

    public List findAll() {
        // 엔티티 이름의 기본값은 클래스의 단순 이름이다
        return em.createQuery("select e from " + type.getSimpleName() + " e", type).getResultList();
    }
    // count, delete ...
}

public class JpaBookRepositoryV0b extends GenericJpaRepository {

    public JpaBookRepositoryV0b(EntityManager em) {
        super(em, Book.class);
    }

    public List findByTitle(String title) {
        return em.createQuery("select b from Book b where b.title = :title", Book.class)
                .setParameter("title", title)
                .getResultList();
    }
}

    생성자에서 Book.class를 다시 넘기는 이유는 자바 제네릭이 소거(erasure) 방식이기 때문이다. 자바 중급 2편에서 본 대로, 컴파일이 끝나면 T는 바이트코드에서 Object로 지워지므로 실행 중에 T가 무엇이었는지 물어볼 수 없다. 그래서 em.find(type, id)에 넘길 Class 객체를 따로 받아 둔다. 이 한 줄은 뒤에서 스프링 데이터가 리포지토리 인터페이스의 제네릭 선언을 리플렉션으로 읽어 도메인 타입을 알아내는 장면과 연결된다. 클래스나 인터페이스 선언부에 적은 extends JpaRepository은 소거되지 않고 클래스 파일의 Signature 속성에 남기 때문에 읽을 수 있다.

    제네릭으로 CRUD 반복은 줄었지만 세 가지가 남는다. 첫째, 엔티티마다 하위 클래스가 여전히 하나씩 필요하다. 둘째, 조건 조회 메서드는 JPQL 문자열을 쓰고, 파라미터를 바인딩하고, 결과 타입을 지정하는 같은 모양의 코드를 매번 반복한다. "제목이 같다", "가격이 이하다", "재고가 이상이다"는 모두 "속성 X에 연산 Y를 값 Z로 적용한다"는 하나의 틀인데, 제네릭은 메서드마다 다른 이 조건까지 일반화하지 못한다. 셋째, 페이징과 정렬, 존재 여부 확인, 개수 세기 같은 부가 기능을 엔티티마다 손으로 구현해야 한다.

    두 번째 문제를 풀려면 조건 자체를 데이터로 표현해야 한다. 스프링 데이터는 그 데이터를 메서드 이름에서 읽는다. findByTitle이라는 이름에는 "제목이 인수와 같은 것을 찾는다"는 정보가 이미 다 들어 있다. 개발자가 메서드를 선언만 하면, 실행 시점에 이름을 해석해 쿼리를 만들고, 공통 CRUD는 미리 만들어 둔 구현체 하나가 처리하고, 둘을 하나의 객체처럼 보이게 이어 붙인다. 이 회차의 나머지는 이 세 문장이 실제로 어떻게 구현되어 있는지를 따라가는 일이다.

    이 장의 핵심

    스프링 데이터 JPA는 리포지토리의 일을 둘로 나눈다. 모든 엔티티에 똑같은 CRUD는 공통 구현체 SimpleJpaRepository 하나가 처리하고, 엔티티마다 다른 조회 조건은 개발자가 인터페이스에 메서드 선언으로만 적는다. 둘을 하나의 객체로 이어 붙이는 것은 애플리케이션이 시작할 때 만들어지는 JDK 동적 프록시다. 스프링 데이터 JPA는 JPA 구현체가 아니라 그 위에서 EntityManager를 대신 호출하는 층이므로, 04회의 JPA 규칙은 하나도 바뀌지 않는다.

    스프링 데이터라는 우산, 스프링 데이터 JPA의 자리

    스프링 데이터(Spring Data)는 라이브러리 하나가 아니라 프로젝트 묶음이다. 바닥에 있는 Spring Data Commons가 저장소 종류와 상관없는 추상화를 제공한다. 리포지토리 인터페이스 계층(Repository, CrudRepository 등), 페이징과 정렬 타입(Pageable, Sort, Page), 메서드 이름 파서(PartTree), 리포지토리 프록시를 조립하는 팩토리(RepositoryFactorySupport)가 여기에 있다. 그 위에 저장소별 모듈이 올라간다. Spring Data JPA, Spring Data JDBC, Spring Data MongoDB, Spring Data Redis, Spring Data R2DBC가 모두 같은 Commons 위에 서 있다. 그래서 MongoDB 리포지토리를 써 본 사람은 JPA 리포지토리의 메서드 이름 규칙을 거의 그대로 알아본다.

    이 회차에서 만날 클래스도 두 층에 나뉘어 있다. 메서드 이름을 파싱하는 PartTree, 프록시를 조립하는 RepositoryFactorySupport, 쿼리 메서드 호출을 가로채는 QueryExecutorMethodInterceptor는 Commons에 있다. JPA에 특화된 SimpleJpaRepository, JpaRepositoryFactory, JpaRepository는 Spring Data JPA 모듈에 있다. 스프링 부트의 spring-boot-starter-data-jpa는 Hibernate, Spring Data JPA, Spring ORM을 함께 가져온다(Spring Boot 3.5 참조 문서).

    층을 위에서 아래로 그려 보면 스프링 데이터 JPA가 어디에 끼어 있는지 분명해진다. 영속성 컨텍스트, 1차 캐시, 쓰기 지연, 변경 감지(dirty checking), SQL 생성은 여전히 Hibernate의 일이다. 스프링 데이터 JPA는 그 위에서 "어떤 EntityManager 메서드를 어떤 JPQL로 부를지"를 대신 정해 준다.

      BookService
      │  BookDataRepository 타입으로 주입받는다 (인터페이스, 구현 클래스 없음)
      ▼
  ┌──────────────────────────────────────────────┐
  │ 리포지토리 프록시 (JDK 동적 프록시)              │  ← Spring Data Commons가 시작 시점에 생성
  │   쿼리 메서드 ──▶ RepositoryQuery (이름 파싱 / @Query)│
  │   CRUD 메서드 ──▶ SimpleJpaRepository           │  ← Spring Data JPA
  └──────────────────────────────────────────────┘
      │  persist / merge / find / createQuery ...
      ▼
  공유 EntityManager 프록시                          ← spring-orm (현재 트랜잭션의 EntityManager로 연결)
      │
      ▼
  Hibernate: 영속성 컨텍스트, 변경 감지, SQL 생성    ← JPA 구현체
      │
      ▼
  JDBC 커넥션 ──▶ 데이터베이스
    서비스에서 데이터베이스까지 호출이 내려가는 층을 보여 주고, 스프링 데이터 JPA가 JPA 구현체 위의 얇은 층이라는 것을 드러낸다. 세로로 쌓인 다섯 개의 가로 상자. 맨 위 "서비스", 그 아래 "리포지토리 프록시"(상자 안에 작은 두 갈래 화살표: 왼쪽 "쿼리 메서드 → RepositoryQuery", 오른쪽 "CRUD 메서드 → SimpleJpaRepository"), 그 아래 "공유 EntityManager", 그 아래 "Hibernate (영속성 컨텍스트)", 맨 아래 원통 모양 "데이터베이스". 위에서 아래로 굵은 화살표가 이어진다. 오른쪽에 세로 괄호 세 개로 층의 소속을 표시: 리포지토리 프록시 옆에 "스프링 데이터 JPA", 공유 EntityManager 옆에 "spring-orm", Hibernate 옆에 "JPA 구현체". 평면적인 기술 도해 스타일, 흰 배경, 파랑과 회색 계열. 스프링 데이터 JPA는 EntityManager를 대신 호출하는 층이다. 영속성 컨텍스트와 SQL 생성은 여전히 JPA 구현체가 맡는다.

    인터페이스 계층

    개발자가 상속하는 인터페이스들의 관계는 다음과 같다. Spring Data JPA 3.5.x 소스에서 JpaRepository의 선언은 extends ListCrudRepository, ListPagingAndSortingRepository, QueryByExampleExecutor다.

    Repository                         메서드 없음. "이 인터페이스는 리포지토리다"라는 표시
 ├─ CrudRepository                 save, saveAll, findById, existsById, findAll,
 │   │                                    findAllById, count, deleteById, delete, deleteAll ...
 │   └─ ListCrudRepository         같은 메서드를 Iterable 대신 List로 돌려준다
 └─ PagingAndSortingRepository     findAll(Sort), findAll(Pageable)
     └─ ListPagingAndSortingRepository

JpaRepository  = ListCrudRepository + ListPagingAndSortingRepository + QueryByExampleExecutor
                        + flush, saveAndFlush, saveAllAndFlush,
                          deleteAllInBatch, deleteAllByIdInBatch, getReferenceById ...

    오래된 자료를 볼 때 주의할 점이 하나 있다. Spring Data Commons 2.7.x 소스에서 PagingAndSortingRepository는 CrudRepository를 확장했지만, 3.5.x 소스에서는 Repository만 확장한다. 그래서 3.x에서 PagingAndSortingRepository만 상속한 인터페이스에는 save가 없다. 3.5.x의 Javadoc도 이 인터페이스를 "CrudRepository 같은 것과 조합해 쓰는" 것으로 설명한다. JpaRepository를 상속하면 두 계통을 모두 받으므로 이 차이를 느낄 일이 없다.

    JpaRepository와 PagingAndSortingRepository에는 @NoRepositoryBean이 붙어 있다. 스프링 데이터는 Repository를 확장한 인터페이스를 찾아 프록시를 만드는데, 이 애너테이션이 붙은 인터페이스는 그 대상에서 뺀다. 도메인 타입이 정해지지 않은 중간 인터페이스에 프록시를 만들 수는 없기 때문이다. 팀에서 여러 리포지토리가 공유할 상위 인터페이스를 직접 만든다면 거기에도 @NoRepositoryBean을 붙여야 한다.

    스프링 데이터 JPA가 주는 기능을 한 표로 정리하면 다음과 같다. 이 회차는 위의 다섯 줄을 깊게 다루고, 예제 기반 조회와 사용자 정의 구현 조각은 이름과 자리만 소개한다. 사용자 정의 구현 조각은 메서드 이름이나 @Query로 표현하기 어려운 조회를 직접 구현해 리포지토리 프록시에 붙이는 방법이고, 06회에서 Querydsl을 붙일 때 다시 등장할 수 있는 자리다.

    공통 인터페이스: 상속만 하면 생기는 메서드들

    JpaRepository을 상속한 순간 수십 개의 메서드가 생긴다. 이 메서드들의 본체는 모두 SimpleJpaRepository 한 클래스에 있다. 같은 클래스가 Book에도 Publisher에도 쓰이고, 엔티티 타입은 생성자에서 받는 엔티티 정보(JpaEntityInformation) 객체로 구분한다. 앞에서 만든 제네릭 리포지토리가 Class를 생성자로 받던 것과 같은 발상이다. 아래 표는 Spring Data JPA 3.5.x의 SimpleJpaRepository 소스를 읽고 정리한 것이다. 클래스에는 @Repository와 @Transactional(readOnly = true)가 붙어 있고, 쓰기 메서드에만 메서드 수준 @Transactional이 다시 붙어 있다.

    getReferenceById(ID)em.getReference, 초기화되지 않은 프록시를 반환할 수 있음클래스 수준 읽기 전용
    findAll, count, existsById조회 쿼리, 카운트 쿼리클래스 수준 읽기 전용
    deleteById(ID)findById(id).ifPresent(this::delete). 없으면 아무 일도 하지 않음@Transactional
    delete(T)새 엔티티면 무시, 관리 상태면 remove, 아니면 식별자로 다시 찾아 있을 때만 remove@Transactional

    표에서 몇 줄은 더 들여다볼 가치가 있다. 먼저 findById와 getReferenceById의 차이다. findById는 em.find를 부르므로 영속성 컨텍스트에 없으면 바로 SELECT를 보내고, 행이 없으면 빈 Optional을 돌려준다. getReferenceById는 em.getReference를 부른다. Jakarta Persistence 명세는 이 메서드가 상태를 지연해서 가져오는 인스턴스를 돌려줄 수 있고, 행이 없으면 상태에 처음 접근할 때 EntityNotFoundException을 던진다고 정한다(구현이 getReference 호출 시점에 던지는 것도 허용한다). Hibernate는 이때 프록시를 돌려주므로 SELECT가 나가지 않는다. 연관관계를 걸 때 외래 키 값만 필요하다면 이 차이가 쿼리 한 번의 차이가 된다. 이 메서드는 Spring Data JPA 2.7에서 생겼고, 같은 일을 하던 getById와 getOne은 @Deprecated가 붙어 getReferenceById로 위임만 한다.

    Book book = new Book("JPA 입문", 30000, 10);
book.setPublisher(publisherDataRepository.getReferenceById("P01"));   // 출판사 SELECT 없이 외래 키만 채운다
bookDataRepository.save(book);

    (이 예제에서 Book에 publisher 연관이 있다고 가정했다. 01회의 Book에는 없는 필드이고, 연관관계 매핑 자체는 이 권의 범위 밖이다.) 주의할 점은 프록시를 초기화하려면 열린 영속성 컨텍스트가 필요하다는 것이다. 참조를 얻은 영속성 컨텍스트가 이미 닫힌 뒤에 그 필드를 읽으면 Hibernate는 초기화할 세션이 없다는 LazyInitializationException을 던진다.

    다음은 삭제다. deleteById는 SQL DELETE 한 문장이 아니다. 먼저 findById로 엔티티를 읽고(SELECT), 있으면 delete를 거쳐 em.remove를 부른다. DELETE는 플러시 때 나간다. 번거로워 보이지만 이유가 있다. remove를 거쳐야 JPA가 @PreRemove 같은 생명주기 콜백을 호출하고, CascadeType.REMOVE나 고아 객체 제거를 적용하고, 영속성 컨텍스트의 상태도 맞춘다. 3.5.x 소스에서 대상이 없을 때는 예외 없이 조용히 끝난다. 반대로 deleteAllInBatch()는 JPQL delete 문 하나를 바로 실행한다. 빠르지만 콜백과 영속성 전이를 모두 건너뛰고, 이미 읽어 둔 엔티티는 영속성 컨텍스트에 그대로 남는다. 아래 @Modifying에서 볼 벌크 연산의 함정이 똑같이 적용된다.

    페이징과 정렬

    페이징은 세 타입으로 표현한다. Pageable은 "몇 번째 페이지를 몇 건씩, 어떤 순서로"라는 요청이고, 보통 PageRequest.of(page, size, sort)로 만든다. 페이지 번호는 0부터 센다. 결과 타입은 무엇을 반환형으로 선언하느냐에 따라 달라지고, 그에 따라 나가는 쿼리 수도 달라진다.

page.getContent();        // 이번 페이지의 엔티티 20건 이하
page.getTotalElements();  // 전체 건수: 카운트 쿼리의 결과
page.getTotalPages();
page.hasNext();

    쿼리 메서드: 메서드 이름을 파싱해 쿼리를 만든다

    쿼리 메서드(query method)는 인터페이스에 선언한 메서드 이름을 스프링 데이터가 해석해 쿼리로 바꾸는 기능이다. Spring Data 참조 문서는 이름을 주어(subject)와 술어(predicate) 두 부분으로 나눈다고 설명한다. 앞부분(find…By, exists…By 등)이 무엇을 할지를 정하고, 첫 번째 By가 구분자 역할을 하며, 그 뒤가 조건이다. 한 이름을 분해해 보자.

    findTop3ByStockGreaterThanOrderByUnitPriceDescTitleAsc

  find              주어: 조회
  Top3              주어 안의 제한: 최대 3건
  By                구분자 (첫 번째 By부터 술어)
  StockGreaterThan  술어: stock > ?1          ← 메서드의 첫 번째 인수가 ?1
  OrderBy           정렬 시작
  UnitPriceDesc     unitPrice 내림차순
  TitleAsc          그다음 title 오름차순

    주어 자리에 올 수 있는 키워드는 Spring Data JPA 3.5 문서의 부록에 정리되어 있다. 조회는 find…By, read…By, get…By, query…By, search…By, stream…By 중 무엇을 써도 같다. exists…By는 존재 여부를, count…By는 개수를, delete…By와 remove…By는 삭제를 뜻한다. find와 By 사이의 나머지 글자는 First·Top·Distinct 같은 키워드가 아니면 설명용으로 무시된다. 그래서 findBooksByTitle도 findByTitle과 같은 쿼리가 된다. Top이나 First 뒤의 숫자를 생략하면 1건으로 본다.

    파서가 이름을 어떻게 읽는지 직접 보기

    이름을 해석하는 클래스는 Spring Data Commons의 PartTree다. 데이터베이스도 JPA도 필요 없이, 이름과 도메인 클래스만 주면 해석 결과를 돌려준다. 아래 코드로 몇 가지 이름을 파싱해 보았다. 실행 환경은 JDK 21.0.13(Temurin)과 로컬에 있던 Spring Data Commons 4.0.7 jar다. 이 강좌의 기준인 3.x와 버전이 다르므로, 결과의 해석은 Spring Data JPA 3.5 참조 문서의 규칙과 대조했고 서로 어긋나는 곳은 없었다. 단, 속성을 찾지 못했을 때 나는 PropertyReferenceException은 3.5.x에서 org.springframework.data.mapping 패키지에 있고 4.0에서 org.springframework.data.core로 옮겨졌다. 메시지 형식 문자열은 3.5.x 소스에서도 같다.

    import org.springframework.data.repository.query.parser.Part;
import org.springframework.data.repository.query.parser.PartTree;

public class PartTreeDemo {

    // 파싱에 필요한 것은 필드 이름과 타입뿐이다
    static class Publisher { String code; String name; }
    static class Book { Long id; String title; Integer unitPrice; Integer stock; Publisher publisher; }

    public static void main(String[] args) {
        String[] names = {
            "findByTitleContainingAndUnitPriceLessThanEqual",
            "findDistinctByPublisherNameOrTitle",
            "findTop3ByStockGreaterThanOrderByUnitPriceDescTitleAsc",
            "countByUnitPriceGreaterThan",
            "existsByTitle",
            "deleteByStock",
            "findByTitel",
        };
        for (String name : names) {
            try {
                PartTree tree = new PartTree(name, Book.class);
                System.out.println(name);
                System.out.println("  count=" + tree.isCountProjection() + " exists=" + tree.isExistsProjection()
                        + " delete=" + tree.isDelete() + " distinct=" + tree.isDistinct()
                        + " max=" + tree.getMaxResults() + " sort=" + tree.getSort());
                int or = 0;
                for (PartTree.OrPart orPart : tree) {
                    for (Part part : orPart) {
                        System.out.println("  or[" + or + "] " + part.getProperty().toDotPath() + " " + part.getType());
                    }
                    or++;
                }
            } catch (RuntimeException e) {
                System.out.println(name + " -> " + e.getClass().getSimpleName() + ": " + e.getMessage());
            }
        }
    }
}

    결과를 한 줄씩 읽어 보자. 첫 번째 이름은 Or가 없으므로 or[0] 한 묶음 안에 조건 두 개가 들어 있다. 같은 묶음 안의 조건은 AND로 이어진다. 각 조건 뒤의 (1)은 그 조건이 소비하는 인수 개수다. 그래서 이 메서드는 인수를 두 개 받아야 하고, 첫 번째가 title에, 두 번째가 unitPrice에 순서대로 바인딩된다. 이름 기반 쿼리의 파라미터 바인딩은 위치 기반이라는 뜻이다. 인수 순서를 바꿔 선언하면 컴파일은 되지만 타입이 맞지 않아 실행 중에 바인딩이 실패한다.

    두 번째 이름에서는 두 가지를 볼 수 있다. Or를 만나자 묶음이 or[0]과 or[1]로 나뉘었다. PartTree의 구조 자체가 "AND 묶음들의 OR"이므로, A And B Or C는 언제나 (A and B) or C로 읽힌다. 괄호로 우선순위를 바꿀 방법은 없다. 또 PublisherName이 publisher.name이라는 경로로 해석되었다. Book에 publisherName이라는 필드가 없으므로 파서가 연관된 객체의 속성으로 내려간 것이다.

    이 경로 해석 규칙은 참조 문서의 "속성 표현식(property expressions)" 절에 정확히 적혀 있다. 먼저 술어 부분 전체(PublisherName)를 첫 글자만 소문자로 바꿔 속성으로 찾는다. 없으면 낙타 표기(camel case)의 경계에서 오른쪽부터 잘라 머리와 꼬리로 나누고(Publisher + Name), 머리가 속성이면 그 타입 안에서 꼬리를 다시 찾는다. 첫 분할이 맞지 않으면 분할 지점을 왼쪽으로 옮겨 계속한다. 이 규칙은 모호할 수 있다. Book에 publisherName 필드와 publisher.name이 둘 다 있으면 통째로 맞는 쪽이 먼저 선택된다. 의도를 분명히 하려면 findByPublisher_Name처럼 밑줄로 경로를 직접 끊는다. 문서가 밑줄을 예약 문자로 다루며 필드 이름에는 낙타 표기를 권하는 이유다.

    세 번째 이름은 Top3가 max=3으로, OrderBy 이하가 Sort 객체로 바뀌었다. 정렬은 쿼리의 조건이 아니라 별도 정보로 분리되어 나중에 ORDER BY 절이 된다. 네 번째부터 여섯 번째는 주어만 다르다. 술어 해석은 같고 count, exists, delete 플래그만 바뀐다. JPA 모듈은 이 플래그를 보고 select 대신 count 쿼리를 만들거나, 결과를 읽은 뒤 삭제하는 실행 방식을 고른다.

    마지막 줄이 이 기능의 가장 중요한 성질이다. 오타가 난 속성 이름은 메서드를 호출할 때가 아니라 PartTree를 만드는 순간에 예외가 된다. 그리고 뒤에서 보겠지만 스프링 데이터는 기본 설정에서 애플리케이션이 시작할 때 모든 쿼리 메서드의 PartTree를 미리 만든다. 그래서 findByTitel을 선언한 애플리케이션은 아예 뜨지 않는다. 문자열 JPQL을 직접 쓰던 때라면 해당 메서드를 처음 호출하는 순간에야 발견했을 오류다. 제안 문구(Did you mean 'title')까지 붙여 주는 것도 이 시점에 도메인 클래스의 속성 목록을 이미 알고 있기 때문이다.

    JPA 모듈이 해석 결과로 하는 일

    Commons의 PartTree는 저장소를 모른다. 해석 결과를 실제 쿼리로 바꾸는 것은 저장소별 모듈의 몫이다. Spring Data JPA 3.5 참조 문서는 이 해석 결과로 JPA 기준 API(Criteria API)를 사용해 쿼리를 만든다고 설명하고, 결과는 본질적으로 select u from User u where u.emailAddress = ?1 and u.lastname = ?2 같은 JPQL에 해당한다고 예를 든다. 우리 예제의 첫 번째 메서드라면 select b from Book b where b.title like ?1 and b.unitPrice <= ?2에 해당하는 쿼리가 된다. 이때 Containing의 인수는 앞뒤에 %가 붙은 패턴으로 바뀌어 바인딩된다.

    여기서 놓치기 쉬운 처리가 하나 있다. 문서에 따르면 Containing, StartingWith, EndingWith 계열의 인수는 소독(sanitize)된다. 사용자가 검색어에 %나 _를 넣으면 LIKE의 와일드카드가 아니라 글자 그대로 일치하도록 이스케이프된다. 검색창에 % 하나만 넣으면 모든 행이 걸리는 흔한 버그를 쿼리 메서드는 기본으로 막아 준다. 반대로 @Query에 직접 쓴 LIKE에는 이 처리가 자동으로 붙지 않는다.

    반환 타입은 메서드 선언에서 정한다. List이면 전부, Optional이나 Book이면 한 건이다. 한 건을 기대하는 메서드에 결과가 둘 이상이면 JPA의 NonUniqueResultException이 생기고, 스프링이 이를 IncorrectResultSizeDataAccessException으로 바꿔 던진다(이 변환 표는 뒤의 예외 변환에서 다시 본다). Page, Slice를 반환형으로 하고 마지막 인수로 Pageable을 받으면 이름 기반 쿼리에도 페이징이 붙는다. Stream을 돌려받을 수도 있는데, 문서는 이 스트림이 저장소 자원을 감싸고 있으므로 다 쓰면 반드시 닫으라고(try-with-resources) 적는다.

    이름 기반 쿼리의 한계

    조건이 둘을 넘어가면 이름이 읽기 어려워진다. findByTitleContainingAndUnitPriceLessThanEqualAndStockGreaterThanOrderByUnitPriceDesc는 정확하지만 읽는 사람을 지치게 한다. 더 근본적인 한계는 조건이 실행 시점에 바뀌는 경우다. 검색 화면에서 제목과 최대 가격이 각각 입력될 수도 비어 있을 수도 있다면, 조건 조합마다 메서드가 하나씩 필요하다. 선택 조건이 두 개면 네 개, 세 개면 여덟 개다. 이름은 컴파일 시점에 고정되어 있으므로 "값이 있을 때만 조건을 붙인다"를 표현할 수 없다. 이 한계는 뒤의 적용 예제에서 실제로 부딪혀 보고, 06회의 Querydsl이 이것을 푸는 도구다.

    @Query와 파라미터 이름: 바이트코드에 이름이 남는가

    이름으로 표현하기 어려운 쿼리는 @Query로 JPQL을 직접 적는다. 메서드 이름은 이제 쿼리의 내용과 상관없으므로 의미가 잘 드러나게 지으면 된다.

    public interface BookDataRepository extends JpaRepository {

    @Query("select b from Book b where b.title like concat('%', :keyword, '%') and b.unitPrice <= :maxPrice")
    List search(@Param("keyword") String keyword, @Param("maxPrice") Integer maxPrice);
}

    @Query의 JPQL도 시작 시점에 검사된다. Spring Data JPA 3.5.x의 SimpleJpaQuery 생성자는 엔티티 매니저 팩토리에서 검증용 EntityManager를 따로 하나 만들어 createQuery(queryString)를 호출해 보고, 실패하면 "Query '%s' validation failed for method %s" 형식의 메시지로 IllegalArgumentException을 던진다. 반환형이 Page라면 카운트 쿼리도 같은 방식으로 검증한다. JPQL 문법 오류나 없는 엔티티 이름은 쿼리 메서드의 속성 오타처럼 애플리케이션 시작을 막는다. 문자열로 쓴 쿼리가 실행 전에 검사되는 이유는 JPA 구현체가 createQuery 단계에서 JPQL을 파싱하고 메타모델과 대조하기 때문이다.

    이름 있는 파라미터와 -parameters 플래그

    위 예제의 @Param("keyword")는 JPQL의 :keyword와 메서드 인수를 연결한다. 이 애너테이션을 빼면 어떻게 될까. 참조 문서는 스프링이 -parameters 컴파일러 플래그로 남긴 파라미터 이름을 읽을 수 있으므로, 이 플래그로 컴파일했다면 @Param을 생략할 수 있다고 적는다. 이 문장의 뜻을 이해하려면 자바 파라미터 이름이 클래스 파일의 어디에 남는지 봐야 한다.

    자바 소스의 파라미터 이름은 기본적으로 클래스 파일에 남지 않는다. JVM은 메서드를 이름과 서술자(descriptor)로 식별하고, 서술자 (II)Ljava/util/List;에는 타입만 있다. 이름이 남는 경로는 두 가지다. 하나는 -g로 컴파일하면 생기는 디버그 정보인 지역 변수 표(LocalVariableTable)인데, 이 표는 메서드 본체를 담는 Code 속성 안에 들어간다. 다른 하나는 -parameters로 컴파일하면 생기는 MethodParameters 속성이다. 리포지토리 인터페이스의 메서드는 추상 메서드라서 Code 속성이 없다. 따라서 -g를 줘도 이름이 남을 자리가 없다. 직접 확인해 보자.

    import java.util.List;

public interface PriceQuery {
    List findInRange(int min, int max);
}
    == javac -g
  public abstract java.util.List findInRange(int, int);
    descriptor: (II)Ljava/util/List;
    flags: (0x0401) ACC_PUBLIC, ACC_ABSTRACT
    Signature: #8                           // (II)Ljava/util/List;

== javac -parameters
  public abstract java.util.List findInRange(int, int);
    descriptor: (II)Ljava/util/List;
    flags: (0x0401) ACC_PUBLIC, ACC_ABSTRACT
    MethodParameters:
      Name                           Flags
      min
      max
    Signature: #11                          // (II)Ljava/util/List;

    -g로 컴파일한 쪽에는 Code 속성도 지역 변수 표도 없고, 상수 풀에도 min, max라는 문자열이 아예 없다. -parameters로 컴파일한 쪽에만 MethodParameters 속성이 생겼다. 리플렉션으로 읽어도 결과가 갈린다. Method.getParameters()로 이름을 출력하는 작은 프로그램을 두 클래스 파일에 각각 돌리면 다음과 같다.

    == -g
arg0 isNamePresent=false
arg1 isNamePresent=false
== -parameters
min isNamePresent=true
max isNamePresent=true

    이름이 없으면 리플렉션은 arg0, arg1이라는 합성 이름을 돌려주고 isNamePresent()가 false다. 스프링 데이터가 :keyword를 어느 인수에 묶어야 할지 알 방법이 없다. 클래스(구체 메서드)라면 예전에는 지역 변수 표를 파싱해 이름을 얻는 길이 있었지만, Spring Framework 6.1 릴리스 노트는 그 일을 하던 LocalVariableTableParameterNameDiscoverer가 6.1에서 제거되었고 더 이상 바이트코드를 파싱해 이름을 추론하지 않으니 -parameters로 컴파일하라고 안내한다. 스프링 부트의 Gradle 플러그인은 자바 플러그인이 적용되면 모든 JavaCompile 작업에 -parameters를 설정한다(Spring Boot Gradle Plugin 3.5 문서). 부트 프로젝트에서 @Param 없이도 동작하는 것은 이 설정 덕분이고, 빌드를 직접 구성하는 프로젝트에서는 같은 코드가 실패할 수 있다. 어느 환경에서든 같은 의미가 되게 하려면 @Param을 붙이는 쪽이 안전하다.

    네이티브 쿼리, 수정 쿼리, 조회 전략

    @Query(value = "...", nativeQuery = true)로 SQL을 직접 쓸 수도 있다. 데이터베이스 고유 문법이나 힌트가 필요할 때 쓰지만, JPQL의 검증과 데이터베이스 독립성을 잃는다. 참조 문서는 네이티브 쿼리에 페이징을 붙일 때 단순한 쿼리는 스프링 데이터가 카운트 쿼리로 다시 쓸 수 있지만, 복잡한 쿼리는 JSqlParser가 클래스패스에 있거나 countQuery를 직접 선언해야 한다고 적는다. 3.5 문서는 @Query(nativeQuery = true)를 묶은 @NativeQuery 애너테이션도 소개한다.

    UPDATE나 DELETE를 @Query로 쓰려면 @Modifying을 함께 붙인다. 이 표시가 있어야 스프링 데이터가 getResultList 대신 executeUpdate를 호출한다.

    @Transactional
@Modifying(clearAutomatically = true)
@Query("update Book b set b.unitPrice = b.unitPrice + :delta where b.stock = 0")
int raisePriceOfSoldOut(@Param("delta") int delta);

    이런 벌크 연산은 영속성 컨텍스트를 거치지 않고 데이터베이스에 바로 실행된다. 같은 트랜잭션에서 미리 읽어 둔 Book 엔티티가 있다면 1차 캐시의 그 객체는 옛 가격을 그대로 들고 있다. 그 뒤 findById를 부르면 1차 캐시에서 옛 객체가 나온다. 참조 문서는 수정 쿼리 실행 후 EntityManager에 낡은 엔티티가 남을 수 있지만, 자동으로 비우면 아직 플러시하지 않은 변경까지 버려지므로 기본으로는 비우지 않는다고 설명한다. 비우기를 원하면 clearAutomatically = true를 준다. 메서드에 @Transactional을 붙인 이유는 뒤의 트랜잭션 절에서 설명한다. 선언한 쿼리 메서드에는 기본 트랜잭션이 없다.

    마지막으로 스프링 데이터가 메서드마다 어떤 쿼리를 쓸지 고르는 규칙이 조회 전략(query lookup strategy)이다. CREATE는 언제나 이름에서 쿼리를 만들고, USE_DECLARED_QUERY는 선언된 쿼리만 찾으며 없으면 예외를 던진다. 기본값 CREATE_IF_NOT_FOUND는 선언된 쿼리를 먼저 찾고 없을 때 이름에서 만든다. 선언된 쿼리 중에서는 메서드에 붙은 @Query가 @NamedQuery나 orm.xml의 이름 있는 쿼리보다 우선한다. 이름 있는 쿼리는 Book.findByTitle처럼 "도메인 클래스의 단순 이름 + 점 + 메서드 이름"으로 찾는다. 이름이 우연히 이 규칙에 맞는 이름 있는 쿼리가 있으면 메서드 이름 해석보다 그것이 먼저 쓰인다는 뜻이기도 하다.

    한 층 아래 1: 구현 클래스 없이 빈이 생기는 과정

    지금까지 쓴 BookDataRepository는 인터페이스다. 구현 클래스를 쓴 적이 없는데 서비스에 주입된다. 스프링 핵심 원리 기본편에서 본 컨테이너는 빈 정의(bean definition)를 보고 객체를 만드는데, 인터페이스는 new할 수 없다. 이 틈을 메우는 것이 FactoryBean이다. 컨테이너는 빈 정의의 클래스가 FactoryBean을 구현하면 그 객체 자체가 아니라 그 객체의 getObject()가 돌려준 것을 빈으로 등록한다. 스프링 데이터는 리포지토리 인터페이스 하나마다 JpaRepositoryFactoryBean 빈 정의를 하나씩 등록한다.

    세 번째와 여섯 번째 단계는 Spring Data Commons 3.5.x의 RepositoryFactoryBeanSupport에서 다음과 같이 보인다. 핵심 줄만 옮기고 나머지는 생략했다.

    // RepositoryFactoryBeanSupport (Spring Data Commons 3.5.x) 발췌
public void afterPropertiesSet() {
    this.factory = createRepositoryFactory();
    // ... 쿼리 조회 전략, 이름 있는 쿼리, 후처리기 등 설정 ...
    this.repository = Lazy.of(() -> this.factory.getRepository(repositoryInterface, repositoryFragmentsToUse));
    // ...
    if (!lazyInit) {
        this.repository.get();
    }
}

public T getObject() {
    return this.repository.get();
}

    네 번째 단계의 getRepository()는 RepositoryFactorySupport에 있다. 3.5.x 소스에서 프록시를 조립하는 부분을 순서대로 요약하면 다음과 같다. 조건이 맞을 때만 붙는 어드바이스는 주석으로 표시했다.

    // RepositoryFactorySupport.getRepository(...) 요약 (Spring Data Commons 3.5.x)
ProxyFactory result = new ProxyFactory();
result.setTarget(target);                       // JPA 모듈에서는 SimpleJpaRepository 인스턴스
result.setInterfaces(repositoryInterface, Repository.class, TransactionalProxy.class);

// (조건부) MethodInvocationValidator, ExposeMetadataInterceptor + ExposeInvocationInterceptor

postProcessors.forEach(processor -> processor.postProcess(result, information));
                                                // CRUD 메타데이터, 예외 변환, 트랜잭션 어드바이스가 여기서 붙는다

// (조건부) DefaultMethodInvokingMethodInterceptor   인터페이스에 default 메서드가 있을 때

result.addAdvice(new QueryExecutorMethodInterceptor(information, getProjectionFactory(), queryLookupStrategy, /* ... */));
result.addAdvice(new ImplementationMethodExecutionInterceptor(information, compositionToUse, methodInvocationListeners));

T repository = (T) result.getProxy(classLoader);

    스프링 AOP의 ProxyFactory가 그대로 쓰인다. 대상(target)과 구현할 인터페이스와 어드바이스(advice) 목록을 주면, 인터페이스가 있으므로 JDK 동적 프록시를 만든다. 어드바이스는 추가한 순서대로 바깥에서 안쪽으로 감싼다. 후처리기 등록 순서도 정해져 있다. JPA 모듈의 JpaRepositoryFactory 생성자가 CRUD 메타데이터 후처리기를 먼저 등록하고, 그다음 TransactionalRepositoryFactoryBeanSupport.createRepositoryFactory()가 예외 변환 후처리기(PersistenceExceptionTranslationRepositoryProxyPostProcessor)와 트랜잭션 후처리기(TransactionalRepositoryProxyPostProcessor)를 이 순서로 등록한다. 그래서 예외 변환 인터셉터가 트랜잭션 인터셉터보다 바깥에 있다.

    다섯 번째 단계가 앞에서 본 "오타 난 쿼리 메서드는 애플리케이션을 띄우지 못한다"의 근거다. QueryExecutorMethodInterceptor의 생성자는 조회 전략으로 메서드마다 resolveQuery를 호출해 결과를 맵에 넣는다. 이 생성자는 프록시를 조립할 때 실행되고, 프록시는 기본 설정에서 빈 초기화 중에 만들어진다. 따라서 PropertyReferenceException이나 JPQL 검증 실패는 빈 생성 실패로 이어지고, 컨테이너는 시작을 중단한다. 스프링 부트는 spring.data.jpa.repositories.bootstrap-mode로 default, deferred, lazy 세 가지 시작 방식을 제공한다. 지연 방식은 시작 시간을 줄이는 대신, 이런 오류를 발견하는 시점도 뒤로 미룬다는 점을 함께 고려해야 한다.

    컨테이너 시작 중에 스캔, 팩토리 빈 등록, 팩토리 생성, 프록시 조립, 쿼리 준비가 순서대로 일어나는 것을 보여 준다. 왼쪽에서 오른쪽으로 다섯 개의 세로 생명선: "스프링 컨테이너", "JpaRepositoryFactoryBean", "JpaRepositoryFactory", "ProxyFactory", "QueryExecutorMethodInterceptor". 위에서 아래로 화살표: 컨테이너 → 팩토리 빈 "afterPropertiesSet()", 팩토리 빈 → 팩토리 "생성 + 후처리기 등록", 팩토리 빈 → 팩토리 "getRepository()", 팩토리 → ProxyFactory "대상: SimpleJpaRepository", 팩토리 → QueryExecutorMethodInterceptor "쿼리 메서드 전부 해석", QueryExecutorMethodInterceptor 옆에 작은 상자 "Map", ProxyFactory → 컨테이너로 돌아오는 점선 화살표 "JDK 동적 프록시". 맨 아래 빨간 작은 메모: "이름 오타는 여기서 시작 실패". 흰 배경, 깔끔한 UML 시퀀스 스타일. 쿼리 메서드는 호출될 때가 아니라 프록시가 조립될 때 해석된다. 그래서 잘못된 이름은 애플리케이션 시작을 막는다.

    핵심은 두 갈래다. 쿼리 메서드면 QueryExecutorMethodInterceptor가 맵에서 미리 만들어 둔 RepositoryQuery를 꺼내 실행하고 체인을 끝낸다. 3.5.x 소스에서 판정은 queries.containsKey(method) 한 줄이다. 맵에 없으면 invocation.proceed()로 다음 인터셉터에 넘기고, 마지막 ImplementationMethodExecutionInterceptor가 구현 조각(SimpleJpaRepository나 사용자 정의 구현)의 메서드를 호출한다. 이 인터셉터는 리플렉션 호출에서 생기는 InvocationTargetException을 벗겨 원래 예외를 다시 던진다.

    같은 구조를 30줄로 만들어 보기

    이 구조가 정말 이것뿐인지 확인하려면 직접 만들어 보는 것이 가장 확실하다. 아래 코드는 스프링의 ProxyFactory만 써서 "공통 구현체 + 이름 해석 쿼리 + 프록시"를 흉내 낸다. 저장소는 메모리 맵이고, 이름 해석은 findBy 뒤의 속성 하나만 지원한다. Spring Framework 7.0.9의 spring-aop jar와 JDK 21.0.13으로 실행했다. 여기서 쓴 ProxyFactory API는 6.x와 같다.

    import org.aopalliance.intercept.MethodInterceptor;
import org.springframework.aop.framework.ProxyFactory;

import java.lang.reflect.Method;
import java.lang.reflect.RecordComponent;
import java.util.*;
import java.util.function.Function;

public class MiniData {

    record Book(Long id, String title, Integer unitPrice) {}

    // 공통 인터페이스 (CrudRepository 역할)
    interface CrudRepo {
        T save(T entity);
        Optional findById(ID id);
        List findAll();
    }

    // 사용자가 선언만 하는 인터페이스
    interface BookRepo extends CrudRepo {
        List findByTitle(String title);
        List findByUnitPrice(int unitPrice);
    }

    // 공통 구현체 (SimpleJpaRepository 역할)
    static class SimpleRepo implements CrudRepo {
        private final Map store = new LinkedHashMap<>();
        public Book save(Book b) { store.put(b.id(), b); return b; }
        public Optional findById(Long id) { return Optional.ofNullable(store.get(id)); }
        public List findAll() { return new ArrayList<>(store.values()); }
    }

    public static void main(String[] args) {
        SimpleRepo target = new SimpleRepo();

        // 1) 시작 시점: 구현체에 없는 메서드를 이름으로 해석해 '쿼리'를 미리 만든다
        Map> queries = new HashMap<>();
        for (Method m : BookRepo.class.getDeclaredMethods()) {
            String name = m.getName().substring("findBy".length());
            String property = Character.toLowerCase(name.charAt(0)) + name.substring(1);
            RecordComponent rc = Arrays.stream(Book.class.getRecordComponents())
                    .filter(c -> c.getName().equals(property))
                    .findFirst()
                    .orElseThrow(() -> new IllegalStateException(
                            "No property '" + property + "' found for type 'Book'"));
            queries.put(m, a -> target.findAll().stream()
                    .filter(b -> Objects.equals(read(rc, b), a[0]))
                    .toList());
            System.out.println("준비: " + m.getName() + " -> where " + property + " = ?");
        }

        // 2) 프록시 조립: 대상 + 인터페이스 + 어드바이스
        ProxyFactory pf = new ProxyFactory();
        pf.setTarget(target);
        pf.setInterfaces(BookRepo.class);
        pf.addAdvice((MethodInterceptor) inv -> {
            Function q = queries.get(inv.getMethod());
            if (q != null) {
                return q.apply(inv.getArguments());   // 쿼리 메서드
            }
            return inv.proceed();                     // 공통 메서드는 구현체로
        });
        BookRepo repo = (BookRepo) pf.getProxy();

        // 3) 사용
        repo.save(new Book(1L, "JPA", 30000));
        repo.save(new Book(2L, "Spring", 30000));
        repo.save(new Book(3L, "JPA", 45000));
        System.out.println("프록시 클래스 = " + repo.getClass().getName());
        System.out.println("SimpleRepo인가 = " + (repo instanceof SimpleRepo));
        System.out.println("findById(2) = " + repo.findById(2L).orElseThrow().title());
        System.out.println("findByTitle(JPA) = " + repo.findByTitle("JPA").stream().map(Book::id).toList());
        System.out.println("findByUnitPrice(30000) = " + repo.findByUnitPrice(30000).stream().map(Book::id).toList());
    }

    static Object read(RecordComponent rc, Book b) {
        try {
            return rc.getAccessor().invoke(b);
        } catch (ReflectiveOperationException e) {
            throw new IllegalStateException(e);
        }
    }
}

    첫 두 줄의 순서는 getDeclaredMethods()가 돌려주는 순서를 따르는데, Class의 Javadoc은 이 순서를 보장하지 않으므로 실행 환경에 따라 바뀔 수 있다. 나머지는 결정적이다. save와 findById는 맵에 없으므로 proceed()를 거쳐 SimpleRepo로 갔다. findByTitle과 findByUnitPrice는 맵에서 함수가 나와 구현체를 거치지 않고 끝났다. 그리고 프록시는 SimpleRepo의 인스턴스가 아니다. 인터페이스 기반 프록시는 대상 클래스를 상속하지 않고 인터페이스만 구현하기 때문이다. 스프링 데이터의 리포지토리 빈을 SimpleJpaRepository 타입으로 받으려 하면 주입에 실패하는 이유가 같다.

    맵의 키가 Method 객체라는 점도 실제 구현과 같다. 프록시가 인터셉터에 넘기는 Method는 인터페이스에 선언된 메서드이고, Method.equals는 선언 클래스, 이름, 파라미터 타입, 반환 타입이 같으면 같다고 판정한다. 그래서 시작 시점에 getDeclaredMethods()로 얻은 객체와 호출 시점에 넘어온 객체가 다른 인스턴스여도 맵 조회가 성공한다.

    한 층 아래 3: save()는 persist인가 merge인가

    JPA에는 저장(persist)과 병합(merge)이 따로 있는데, 스프링 데이터의 공통 인터페이스에는 save 하나뿐이다. 둘 중 무엇을 부를지는 SimpleJpaRepository가 엔티티를 보고 정한다. Spring Data JPA 3.5.x의 save는 요약하면 다음과 같다.

    // SimpleJpaRepository.save (Spring Data JPA 3.5.x) 요약
@Transactional
public  S save(S entity) {
    // null 검사 생략
    if (entityInformation.isNew(entity)) {
        entityManager.persist(entity);
        return entity;                      // 인수 그 객체가 관리 상태가 된다
    } else {
        return entityManager.merge(entity); // merge가 돌려준 관리 객체를 반환
    }
}

    모든 것은 isNew 판정에 달려 있다. 참조 문서와 3.5.x 소스를 합치면 규칙은 다음 순서다. 첫째, 엔티티가 Persistable을 구현하면 그 엔티티의 isNew()에 판정을 맡긴다. 둘째, 기본형이 아닌 버전 속성(@Version)이 있으면 그 값이 null일 때 새 엔티티다. 문서는 JPA가 0을 첫 번째 버전 값으로 쓰므로 기본형 버전 속성으로는 새 엔티티 여부를 판단할 수 없다고 적는다. 셋째, 그 밖에는 식별자를 본다. Spring Data Commons 3.5.x의 AbstractEntityInformation.isNew는 식별자 타입이 기본형이 아니면 id == null일 때 새 것으로, 기본형 숫자면 값이 0일 때 새 것으로 보고, 숫자가 아닌 기본형이면 "Unsupported primitive id type %s" 메시지로 IllegalArgumentException을 던진다.

    엔티티의 식별자·버전save(새로 만든 객체)의 판정일어나는 일 (Hibernate 기준)
    @Id @GeneratedValue Long id (아직 null)새 엔티티 → persistIDENTITY 전략이면 식별자를 얻기 위해 persist 시점에 INSERT. 반환값은 인수와 같은 객체
    @Id String code를 직접 할당, 버전 없음식별자가 null이 아님 → merge영속성 컨텍스트에 없으므로 SELECT로 존재를 확인, 없으면 새 관리 객체에 상태를 복사, 플러시 때 INSERT. 반환값은 인수와 다른 객체
    직접 할당한 식별자 + @Version Long version (null)버전이 null → persistSELECT 없이 플러시 때 INSERT
    Persistable 구현isNew()의 결과엔티티가 스스로 정한 대로

    두 번째 줄이 실무에서 자주 문제가 된다. 출판사 코드처럼 업무상 의미 있는 값을 식별자로 직접 넣는 엔티티를 생각해 보자. 식별자가 처음부터 채워져 있으므로 isNew는 false이고, save는 merge로 간다. 명세상 merge는 새 엔티티 X를 받으면 새 관리 인스턴스 X'을 만들어 X의 상태를 복사하고 X'을 돌려준다. 그런데 Hibernate는 X가 처음 보는 엔티티인지, 이미 테이블에 있는 행의 준영속 사본인지 식별자만으로는 알 수 없으므로 먼저 데이터베이스를 조회한다. 결과적으로 INSERT 한 번이면 될 저장에 SELECT가 하나씩 더 붙는다. 출판사 만 건을 넣으면 SELECT도 만 번이다.

    Publisher p = new Publisher("P01", "예제출판");
Publisher saved = publisherDataRepository.save(p);   // merge 경로

System.out.println(saved == p);   // false: merge가 새로 만든 관리 객체가 돌아왔다
p.setName("이름 변경");            // p는 관리 대상이 아니다. 이 변경은 어디에도 반영되지 않는다

    반환값을 무시하고 원래 객체를 계속 쓰면 위처럼 변경이 사라진다. persist 경로에서는 반환값이 인수와 같아서 이 차이가 드러나지 않으므로, 습관적으로 반환값을 버리던 코드가 식별자 전략을 바꾸는 순간 조용히 틀린다. save의 반환값을 이후의 기준 객체로 삼는 습관이 안전하다.

    추가 SELECT를 없애는 방법은 표의 세 번째와 네 번째 줄이다. 낙관적 락(optimistic lock)을 어차피 쓸 생각이라면 래퍼 타입 @Version을 두는 것이 가장 간단하다. 그렇지 않다면 참조 문서가 소개하는 패턴처럼 Persistable을 구현하고, 영속화되거나 조회된 뒤에 "새 것 아님"으로 표시를 바꾼다.

    @MappedSuperclass
public abstract class AssignedIdEntity implements Persistable {

    @Transient                       // 테이블 칼럼이 아니다
    private boolean newEntity = true;

    @Override
    public boolean isNew() {
        return newEntity;
    }

    @PostPersist                     // persist 직후
    @PostLoad                        // 데이터베이스에서 읽어 만든 직후
    void markNotNew() {
        this.newEntity = false;
    }
}

@Entity
public class Publisher extends AssignedIdEntity {

    @Id
    private String code;
    private String name;

    protected Publisher() {
    }

    public Publisher(String code, String name) {
        this.code = code;
        this.name = name;
    }

    @Override
    public String getId() {
        return code;
    }

    public void setName(String name) {
        this.name = name;
    }
}

    새로 만든 Publisher는 newEntity가 true이므로 persist로 가고, 조회해 온 객체는 @PostLoad가 false로 바꿔 두므로 merge로 간다. 이 플래그는 @Transient라 데이터베이스에 저장되지 않고, 객체가 메모리에 사는 동안만 의미가 있다.

    수정에는 save가 필요 없다

    반대 방향의 오해도 있다. "조회한 엔티티를 고쳤으면 save를 불러야 반영된다"는 생각이다. 04회에서 본 변경 감지가 그대로 동작하므로, 트랜잭션 안에서 조회한 관리 상태의 엔티티는 필드를 바꾸기만 하면 커밋 직전 플러시 때 UPDATE가 만들어진다. 이 경우 save를 불러도 해롭지는 않다. 관리 상태 엔티티는 isNew가 false라 merge로 가는데, 명세상 관리 상태 엔티티에 대한 merge는 무시된다. 문제는 트랜잭션 밖에서 고친 준영속 객체를 save로 넘길 때다. 이때 merge는 그 객체의 모든 필드를 관리 객체에 덮어쓴다. 화면에서 일부 필드만 채워 만든 객체를 넘기면 비어 있던 필드가 null로 덮인다. 수정은 "트랜잭션 안에서 조회하고, 바꿀 필드만 바꾼다"가 기본이다.

    한 층 아래 4: 트랜잭션 기본값과 예외 변환

    리포지토리 프록시에는 처음부터 트랜잭션 인터셉터와 예외 변환 인터셉터가 들어 있다. 둘 다 개발자가 따로 설정하지 않아도 동작하므로, 무엇이 기본값인지 알아 두지 않으면 예상과 다른 동작을 만난다.

    CRUD 메서드: 읽기는 읽기 전용, 쓰기는 기본 트랜잭션

    참조 문서는 CrudRepository에서 물려받은 메서드가 SimpleJpaRepository의 트랜잭션 설정을 따르고, 읽기 연산은 readOnly가 true이며 나머지는 평범한 @Transactional이라고 설명한다. 소스에서 본 클래스 수준 @Transactional(readOnly = true)와 쓰기 메서드의 @Transactional이 그것이다. 읽기 전용 표시의 효과에 대해 문서는 이렇게 설명한다. 읽기 전용은 조작 쿼리를 막는 검사가 아니라 JDBC 드라이버에 전달되는 최적화 힌트이고, Hibernate와 함께 쓰면 플러시 모드가 MANUAL로 설정되어 변경 감지를 건너뛴다. Spring Framework 6.2.x의 HibernateJpaDialect.beginTransaction에서도 읽기 전용 트랜잭션을 시작할 때 세션의 플러시 모드를 FlushMode.MANUAL로 바꾸는 코드를 확인할 수 있다.

    서비스가 이미 트랜잭션을 열어 둔 상태에서 리포지토리를 호출하면 이야기가 달라진다. 기본 전파 방식에서 리포지토리 메서드의 트랜잭션은 새로 시작하지 않고 바깥 트랜잭션에 참여한다. 이때 findById의 readOnly = true가 바깥의 읽기·쓰기 트랜잭션을 읽기 전용으로 바꾸지 않는다. 그래서 서비스의 @Transactional 안에서 findById로 꺼낸 엔티티를 고치면 변경 감지가 정상적으로 UPDATE를 만든다. 참여와 전파의 정확한 규칙은 08회에서 다룬다.

    CRUD 메서드의 트랜잭션 설정을 바꾸고 싶다면 리포지토리 인터페이스에 그 메서드를 다시 선언하고 애너테이션을 붙인다. 문서의 예처럼 findAll()을 다시 선언하고 @Transactional(timeout = 10)을 붙이면 그 메서드는 10초 제한으로, 읽기 전용 표시 없이 실행된다.

    선언한 쿼리 메서드: 기본 트랜잭션이 없다

    쉽게 놓치는 것이 이쪽이다. 참조 문서는 선언한 쿼리 메서드(default 메서드 포함)에는 기본으로 어떤 트랜잭션 설정도 적용되지 않는다고 분명히 적는다. 트랜잭션이 필요하면 리포지토리 인터페이스나 메서드에 @Transactional을 붙이라고 한다. 이것이 두 가지 결과를 낳는다.

    첫째, 서비스 트랜잭션 밖에서 findByTitleContaining을 부르면 트랜잭션 없이 실행된다. 스프링의 공유 EntityManager 프록시는 현재 트랜잭션에 묶인 EntityManager가 없으면 호출마다 새로 하나를 만든다. Query를 돌려주는 호출이면 그 쿼리의 getResultList 같은 종료 메서드가 끝날 때 닫는다. 따라서 돌려받은 엔티티는 받는 순간 이미 준영속 상태이고, 지연 로딩 연관을 건드리면 초기화할 세션이 없다. 단, 웹 요청 안에서는 사정이 다를 수 있다. 스프링 부트는 웹 애플리케이션에서 기본으로 OpenEntityManagerInViewInterceptor를 등록해 요청 동안 EntityManager 하나를 열어 두므로(Spring Boot 3.5 참조 문서, spring.jpa.open-in-view), 그 경우 공유 EntityManager는 새로 만들지 않고 요청에 묶인 것을 쓴다. 이 설정의 장단점은 이 권의 범위를 넘는 주제이고, 이 회차에서는 "트랜잭션 밖의 동작은 이 설정에 따라 달라진다"는 것만 기억하자.

    둘째, 이름 기반 삭제 메서드는 트랜잭션 밖에서 실패한다. 참조 문서에 따르면 deleteByStock(0) 같은 파생 삭제 쿼리는 DELETE 문 하나가 아니라, 조회 쿼리를 실행한 뒤 결과를 하나씩 remove한다. JPA 구현체가 @PreRemove 콜백을 부를 수 있게 하려는 것이다. 그런데 Spring Framework 6.2.x의 SharedEntityManagerCreator는 joinTransaction, flush, persist, merge, remove, refresh를 트랜잭션이 필요한 메서드로 분류하고, 실제 트랜잭션이 없으면 "No EntityManager with actual transaction available for current thread - cannot reliably process 'remove' call" 메시지로 TransactionRequiredException을 던진다. 리포지토리 프록시의 예외 변환 인터셉터는 이 예외를 InvalidDataAccessApiUsageException으로 바꿔 올려 보낸다. deleteById는 같은 상황에서 잘 동작하는 것과 대비된다. deleteById는 SimpleJpaRepository에 @Transactional이 붙어 있기 때문이다.

    public interface BookDataRepository extends JpaRepository {

    @Transactional            // 없으면 서비스 트랜잭션 밖에서 호출할 때 remove 단계에서 실패한다
    long deleteByStock(Integer stock);
}

    여기서 07회의 주제 하나가 미리 보인다. SimpleJpaRepository.deleteById는 내부에서 findById(id).ifPresent(this::delete)로 같은 객체의 delete를 호출한다. 이것은 프록시를 거치지 않는 내부 호출이므로 delete에 붙은 @Transactional은 이 경로에서 해석되지 않는다. 그래도 문제가 없는 이유는 바깥 메서드 deleteById에 이미 @Transactional이 있어 트랜잭션이 열려 있기 때문이다. 트랜잭션 AOP의 내부 호출 문제는 07회에서 원리부터 다룬다.

    예외 변환: 리포지토리가 DataAccessException을 던지는 이유

    스프링 DB 1편에서 스프링이 데이터 접근 예외를 DataAccessException 계층으로 추상화한다는 것을, 04회에서 @Repository가 붙은 빈에 예외 변환 AOP를 적용한다는 것을 보았다. 스프링 데이터 리포지토리에는 인터페이스에 @Repository를 붙이지 않아도 이 변환이 걸려 있다. 앞에서 본 예외 변환 후처리기가 프록시에 PersistenceExceptionTranslationInterceptor를 직접 붙이기 때문이다. 이 인터셉터는 컨테이너의 PersistenceExceptionTranslator 빈들에게 변환을 맡기고, JPA 환경에서는 엔티티 매니저 팩토리 빈이 그 역할을 하며 실제 변환은 JpaDialect가 한다.

    Hibernate를 쓰면 HibernateJpaDialect가 변환한다. Spring Framework 6.2.x 소스에서 순서는 이렇다. 예외가 Hibernate 예외면 Hibernate 전용 규칙으로 바꾸고, Hibernate 예외를 원인으로 가진 PersistenceException이면 그 원인을 바꾸고, 둘 다 아니면 EntityManagerFactoryUtils.convertJpaAccessExceptionIfPossible의 표준 JPA 규칙으로 넘긴다. Hibernate 전용 규칙에서 제약 조건 위반(org.hibernate.exception.ConstraintViolationException)은 DataIntegrityViolationException이 되고, 메시지에 SQL과 제약 조건 이름이 붙는다. 표준 JPA 규칙에서 자주 만나는 것은 다음과 같다.

    JPA 예외스프링 예외

    NonUniqueResultExceptionIncorrectResultSizeDataAccessException

    표의 마지막 규칙도 기억해 둘 만하다. 위 어느 것에도 해당하지 않는 예외는 변환하지 않고 그대로 통과시킨다. 소스의 주석은 그런 예외가 사용자 코드에서 왔을 가능성이 높기 때문이라고 설명한다. 그래서 서비스는 리포지토리 구현이 JdbcTemplate이든 MyBatis든 스프링 데이터 JPA든 같은 DataAccessException 계층만 보고 복구 여부를 판단할 수 있다. 이 권의 첫 회차부터 지켜 온 "인터페이스 뒤에서 기술을 바꿔 끼운다"는 약속이 예외 쪽에서도 지켜지는 것이다.

    적용 1: 스프링 데이터 JPA 리포지토리 선언하기

    이제 이 권의 도서 예제에 적용해 보자. 엔티티 매핑은 04회에서 만든 것을 그대로 쓴다. 이 회차에서 중요한 것은 식별자가 @GeneratedValue로 생성되는 래퍼 타입 Long이라는 점이다. 앞의 표대로 새로 만든 Book의 save는 persist 경로로 간다.

    @Entity
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;
    private Integer unitPrice;
    private Integer stock;

    protected Book() {                       // JPA가 리플렉션으로 객체를 만들 때 쓰는 기본 생성자
    }

    public Book(String title, Integer unitPrice, Integer stock) {
        this.title = title;
        this.unitPrice = unitPrice;
        this.stock = stock;
    }
    // getter, setter ...
}

    스프링 데이터 리포지토리 인터페이스를 선언한다. 01회부터 써 온 애플리케이션의 인터페이스 이름이 BookRepository이므로, 스프링 데이터 쪽 인터페이스는 BookDataRepository로 구분한다. 검색 조건 BookSearch(titleKeyword, maxPrice)의 두 조건이 각각 있을 수도 없을 수도 있으므로, 조합마다 메서드를 하나씩 둔다. 같은 일을 @Query로 하는 메서드도 비교를 위해 함께 둔다.

    package bookshop.repository.datajpa;

public interface BookDataRepository extends JpaRepository {

    List findByTitleContaining(String titleKeyword);

    List findByUnitPriceLessThanEqual(Integer maxPrice);

    List findByTitleContainingAndUnitPriceLessThanEqual(String titleKeyword, Integer maxPrice);

    @Query("select b from Book b where b.title like concat('%', :keyword, '%') and b.unitPrice <= :maxPrice")
    List search(@Param("keyword") String keyword, @Param("maxPrice") Integer maxPrice);
}

    세 쿼리 메서드와 search는 결과가 거의 같지만 같지는 않다. 검색어에 %나 _가 들어 있으면 쿼리 메서드는 이를 이스케이프해 글자 그대로 찾고, @Query의 concat은 와일드카드로 해석한다. 쿼리 메서드 쪽이 사용자 입력에 더 안전하다. 반대로 @Query는 이름이 짧고 쿼리가 눈에 보인다는 장점이 있다.

    스프링 부트를 쓴다면 이 인터페이스를 자동 구성 패키지 아래에 두는 것 말고 설정할 것이 없다. 애플리케이션이 시작하면 앞에서 본 과정을 거쳐 BookDataRepository 타입의 프록시 빈이 생긴다. 이제 이 리포지토리로 BookSearch를 처리하는 코드를 써 보면 문제가 바로 보인다.

    public List findAll(BookSearch search) {
    String keyword = search.titleKeyword();
    Integer maxPrice = search.maxPrice();
    boolean hasKeyword = StringUtils.hasText(keyword);
    boolean hasMaxPrice = maxPrice != null;

    if (hasKeyword && hasMaxPrice) {
        return repository.findByTitleContainingAndUnitPriceLessThanEqual(keyword, maxPrice);
    } else if (hasKeyword) {
        return repository.findByTitleContaining(keyword);
    } else if (hasMaxPrice) {
        return repository.findByUnitPriceLessThanEqual(maxPrice);
    } else {
        return repository.findAll();
    }
}

    조건이 두 개라 분기가 네 개다. 검색 조건에 "최소 재고"가 하나 더 붙으면 분기와 쿼리 메서드가 각각 여덟 개가 되고, 조건이 하나 늘 때마다 두 배가 된다. 메서드 이름은 컴파일할 때 정해지는 상수이므로 "값이 있을 때만 이 조건을 붙인다"를 이름 하나로 표현할 길이 없다. 이 회차의 첫 질문으로 돌아가 보면, 스프링 데이터 JPA는 "엔티티마다 반복되는 CRUD"와 "고정된 조회 조건"은 완전히 없애 주지만 "실행 시점에 조합되는 조건"은 풀지 못한다. 이것이 06회에서 Querydsl을 함께 쓰는 이유다.

    적용 2: 기존 리포지토리 인터페이스 뒤에 어댑터로 두기

    스프링 데이터 리포지토리를 서비스에 바로 주입하는 방법도 있다. 하지만 이 권은 서비스가 BookRepository 인터페이스에만 의존하도록 만들어 왔고, 메모리 구현과 JdbcTemplate, MyBatis, JPA 구현이 모두 그 인터페이스를 구현했다. 이 구조를 지키려면 BookDataRepository를 감싸 BookRepository를 구현하는 어댑터(adapter)를 하나 둔다. 스프링 MVC 1편에서 본 어댑터 패턴 그대로, 서로 다른 두 인터페이스 사이를 잇는 클래스다.

    package bookshop.repository.datajpa;

@Transactional
public class DataJpaBookRepository implements BookRepository {

    private final BookDataRepository repository;

    public DataJpaBookRepository(BookDataRepository repository) {
        this.repository = repository;
    }

    @Override
    public Book save(Book book) {
        return repository.save(book);
    }

    @Override
    public void update(Long id, BookUpdate update) {
        Book found = repository.findById(id).orElseThrow();
        found.setTitle(update.title());
        found.setUnitPrice(update.unitPrice());
        found.setStock(update.stock());
        // save를 부르지 않는다: 커밋 직전 플러시에서 변경 감지가 UPDATE를 만든다
    }

    @Override
    public Optional findById(Long id) {
        return repository.findById(id);
    }

    @Override
    public List findAll(BookSearch search) {
        // 적용 1의 분기 코드 ...
    }
}

@Configuration
public class DataJpaConfig {

    @Bean
    public BookRepository bookRepository(BookDataRepository bookDataRepository) {
        return new DataJpaBookRepository(bookDataRepository);
    }
}

    update를 한 줄씩 따라가 보자. 어댑터 클래스에 붙은 @Transactional 때문에 update가 시작될 때 트랜잭션이 열린다. 서비스가 이미 트랜잭션을 열었다면 거기에 참여한다. repository.findById(id)는 리포지토리 프록시를 거치는데, 그 트랜잭션 인터셉터는 이미 열린 트랜잭션에 참여할 뿐 새로 시작하지 않는다. 그래서 돌려받은 found는 현재 영속성 컨텍스트의 관리 상태 엔티티다. 세 개의 setter는 메모리의 필드만 바꾼다. update가 끝나 트랜잭션이 커밋되기 직전에 Hibernate가 플러시하면서 1차 캐시에 보관해 둔 최초 상태(스냅샷)와 현재 필드를 비교하고, 달라진 엔티티에 대해 UPDATE를 만든다. 리포지토리 메서드를 하나도 더 부르지 않았는데 데이터베이스가 바뀐다.

    이 구조에서 의존 관계를 컴파일 시점과 실행 시점으로 나눠 보면 다음과 같다.

                         DataJpaBookRepository ───▶ BookDataRepository (스프링 데이터 인터페이스)

설정 (DataJpaConfig): BookRepository 빈 = new DataJpaBookRepository(BookDataRepository 프록시)

    서비스는 바뀐 것이 없다. 바뀐 것은 어떤 구현을 BookRepository 빈으로 등록할지 정하는 설정 클래스 하나다. 스프링 핵심 원리 기본편의 표현을 빌리면, 서비스는 추상화에 의존하고(DIP) 구현을 바꿔도 서비스 코드는 고치지 않는다(OCP). 02회에서 만든 리포지토리 테스트가 인터페이스를 대상으로 작성되어 있다면, 설정만 바꿔 같은 테스트로 새 구현이 계약을 지키는지 확인할 수 있다.

    대가도 분명하다. 클래스가 하나 늘고, 메서드마다 위임 코드가 생긴다. 서비스가 BookDataRepository를 직접 쓰면 이 계층이 사라지는 대신, 서비스가 스프링 데이터의 API(JpaRepository의 메서드, Page, 메서드 이름 규칙)를 알게 된다. 어느 쪽이 옳다고 정해진 것은 아니다. 데이터 접근 기술을 바꿀 가능성, 저장소를 메모리 구현으로 바꿔 끼워 테스트할 필요, 같은 인터페이스를 여러 구현이 공유하는지 같은 조건에 따라 판단이 달라진다. 이 권처럼 여러 기술을 같은 인터페이스 뒤에서 비교하는 상황에서는 어댑터가 자연스럽고, 기술을 스프링 데이터 JPA로 확정한 프로젝트에서는 직접 의존하는 쪽이 코드가 짧다.

    서비스는 애플리케이션 인터페이스만 알고, 어댑터가 스프링 데이터 인터페이스를 감싸며, 그 구현은 실행 중에 만들어진 프록시라는 것을 보여 준다. UML 클래스 다이어그램. 왼쪽 위 "BookService" 상자에서 오른쪽 인터페이스 상자 "BookRepository"로 실선 화살표. 그 아래 "DataJpaBookRepository" 상자에서 "BookRepository"로 속이 빈 삼각형 점선 화살표(구현). "DataJpaBookRepository"에서 오른쪽 인터페이스 상자 "BookDataRepository"로 실선 화살표. "BookDataRepository" 아래 점선 테두리 상자 "프록시 (실행 중 생성)"에서 위로 구현 화살표, 프록시에서 오른쪽 "SimpleJpaRepository"로 화살표. 맨 아래 가로 띠에 "DataJpaConfig: 어떤 구현을 쓸지 결정". 인터페이스 상자는 연한 파랑, 클래스는 흰색, 프록시는 점선 회색. 서비스가 아는 것은 BookRepository뿐이다. 스프링 데이터는 어댑터 뒤에 숨는다.

    흔한 오해와 함정

    "스프링 데이터 JPA를 쓰면 JPA를 몰라도 된다"

    스프링 데이터 JPA가 없애 주는 것은 EntityManager를 부르는 반복 코드다. 그 아래의 영속성 컨텍스트, 변경 감지, 플러시 시점, 지연 로딩, 준영속 상태는 그대로다. save가 merge로 가는 조건, 벌크 연산 뒤의 낡은 1차 캐시, 트랜잭션 밖에서 돌려받은 준영속 엔티티는 모두 JPA를 알아야 설명된다. 오히려 코드가 짧아진 만큼 그 아래에서 일어나는 일이 눈에 덜 보이므로 JPA 지식이 더 필요하다.

    "save의 반환값은 버려도 된다"

    persist 경로에서만 맞는 말이다. merge 경로의 반환값은 인수와 다른 객체이고, 이후의 변경은 반환된 객체에 해야 의미가 있다. 식별자를 직접 할당하는 엔티티, 준영속 객체를 넘기는 코드에서 이 차이가 버그가 된다.

    "deleteById는 DELETE 한 번이다"

    3.5.x 소스에서 deleteById는 findById 후 remove다. 조회가 먼저 나가고, 대상이 없으면 조용히 끝난다. 대량 삭제에 쓰면 행마다 SELECT가 붙는다. deleteAllInBatch나 @Modifying 벌크 삭제는 쿼리 하나로 끝나지만 생명주기 콜백과 영속성 전이를 건너뛰고 영속성 컨텍스트를 갱신하지 않는다. 무엇을 포기하는지 알고 골라야 한다.

    "리포지토리의 모든 메서드에 트랜잭션이 걸려 있다"

    공통 CRUD 메서드에만 걸려 있다. 개발자가 선언한 쿼리 메서드에는 기본 트랜잭션이 없다. 조회라면 결과가 준영속으로 돌아오는 정도로 끝나지만, 파생 삭제 쿼리와 @Modifying 쿼리는 트랜잭션 없이 실패한다. 서비스 계층에서 트랜잭션을 열고 그 안에서 호출하는 것이 기본이고, 리포지토리 단독으로 호출될 수 있는 수정 메서드에는 @Transactional을 붙인다.

    "주입받은 리포지토리는 SimpleJpaRepository 객체다"

    주입받는 것은 JDK 동적 프록시다. SimpleJpaRepository로 형변환하면 ClassCastException이 난다. 프록시의 클래스 이름과 패키지는 명세상 정해져 있지 않다. 디버거에서 리포지토리 변수를 열면 $Proxy로 시작하는 이름이 보이는 것이 정상이다.

    "이름만 잘 지으면 어떤 조회든 표현된다"

    이름 기반 쿼리는 컴파일 시점에 고정된 조건만 표현한다. AND와 OR의 우선순위를 괄호로 바꿀 수 없고, 선택적 조건은 조합마다 메서드가 필요하다. 조건이 둘을 넘거나 실행 중에 바뀌면 @Query, 사용자 정의 구현 조각, 06회의 Querydsl로 넘어갈 때다.

    정리: 무엇을 얻었고 무엇이 남았나

    이 회차는 "왜 리포지토리 코드는 다 비슷한가"에서 출발했다. 반복되는 CRUD는 엔티티 타입과 식별자 타입만 다르므로 공통 구현체 하나로 처리할 수 있고, 스프링 데이터 JPA에서 그 구현체가 SimpleJpaRepository다. 엔티티마다 다른 조회 조건은 메서드 이름으로 선언하면 PartTree가 해석하고, 이름으로 부족하면 @Query로 직접 쓴다. 둘을 하나의 객체로 보이게 하는 것은 ProxyFactory로 조립한 JDK 동적 프록시이고, 그 안에서 QueryExecutorMethodInterceptor가 쿼리 메서드와 나머지를 가른다.

    이 구조에서 실무에 바로 쓰이는 사실은 다섯 가지다. 쿼리 메서드와 JPQL은 시작 시점에 검사되므로 오타는 배포 전에 드러난다. 이름 있는 파라미터는 -parameters나 @Param 없이는 연결되지 않는다. save는 isNew에 따라 persist와 merge로 갈리고, 직접 할당한 식별자는 추가 SELECT와 다른 반환 객체를 낳는다. 공통 CRUD에만 트랜잭션이 기본으로 걸리고, 선언한 쿼리 메서드에는 없다. 리포지토리 예외는 프록시의 예외 변환 덕분에 DataAccessException 계층으로 올라온다.

    남은 것은 두 가지다. 실행 시점에 조합되는 동적 조건은 이름으로 풀리지 않았다. 06회는 Querydsl로 이 문제를 풀고, 지금까지 본 여러 기술을 실무에서 어떻게 섞어 쓸지를 다룬다. 그리고 이 회차 곳곳에서 만난 트랜잭션, 즉 리포지토리 프록시의 트랜잭션 인터셉터, 읽기 전용 표시, 바깥 트랜잭션에 참여하는 동작, 내부 호출은 07회부터 트랜잭션 AOP와 전파의 원리로 다시 정리한다.
    스프링 데이터 JPA
    JPA 구현체 위에서 EntityManager 호출을 대신해 주는 층. 영속성 컨텍스트, 변경 감지, SQL 생성은 여전히 Hibernate 같은 구현체가 맡는다.
    JpaRepository와 SimpleJpaRepository
    JpaRepository를 상속하면 공통 CRUD·페이징 메서드가 생기고, 그 본체는 모든 엔티티가 공유하는 SimpleJpaRepository 한 클래스에 있다.
    쿼리 메서드와 PartTree
    메서드 이름을 주어와 술어로 나눠 조건·정렬·개수 제한을 해석한다. 술어는 "AND 묶음들의 OR" 구조이고, 인수는 위치 순서로 바인딩된다.
    시작 시점 검증
    쿼리 메서드는 프록시 조립 때 QueryExecutorMethodInterceptor가 전부 해석하고, @Query의 JPQL도 그때 검증된다. 잘못된 이름이나 JPQL은 애플리케이션 시작을 막는다.
    리포지토리 프록시
    JpaRepositoryFactoryBean이 ProxyFactory로 조립한 JDK 동적 프록시. 쿼리 메서드는 쿼리 실행 인터셉터에서 끝나고, 나머지는 구현체로 위임된다.
    -parameters와 @Param
    추상 메서드에는 Code 속성이 없어 디버그 정보로 파라미터 이름을 남길 수 없다. -parameters가 만드는 MethodParameters 속성이나 @Param이 있어야 이름 있는 파라미터가 연결된다.
    isNew와 save
    Persistable, 래퍼 타입 버전 속성, 식별자 순으로 새 엔티티를 판정해 persist 또는 merge를 부른다. 직접 할당한 식별자는 merge 경로로 간다.
    트랜잭션 기본값
    공통 CRUD는 읽기 전용 또는 기본 트랜잭션이 걸려 있고, 선언한 쿼리 메서드에는 트랜잭션이 없다. 파생 삭제와 수정 쿼리는 트랜잭션 안에서 호출해야 한다.
    어댑터 구조
    스프링 데이터 리포지토리를 애플리케이션의 리포지토리 인터페이스 구현 안에 감추면, 서비스 코드를 고치지 않고 설정만으로 기술을 바꿀 수 있다.

    스프링 데이터 JPA로 바꾼 뒤 "저장이 갑자기 느려졌다"는 문제를 만나면 가장 먼저 엔티티의 식별자 전략을 본다. 외부 시스템의 코드나 UUID처럼 애플리케이션이 식별자를 직접 채우는 엔티티는 save가 merge로 가고, Hibernate는 행마다 SELECT로 존재를 확인한다. SQL 로그에서 INSERT마다 같은 키의 SELECT가 앞서 나간다면 이 경우다. 낙관적 락이 필요하면 래퍼 타입 @Version을, 그렇지 않으면 Persistable을 구현해 판정을 엔티티가 하도록 바꾼다. 생성 전략을 쓰는 엔티티라면 이 문제는 생기지 않으므로 판단은 식별자 설계와 함께 내려야 한다.

    운영 중에 InvalidDataAccessApiUsageException과 함께 "No EntityManager with actual transaction available" 메시지를 보면, 트랜잭션 없이 호출된 파생 삭제 쿼리나 @Modifying 쿼리를 의심한다. 배치 작업이나 이벤트 리스너처럼 서비스 계층의 트랜잭션을 거치지 않는 경로에서 리포지토리를 직접 부를 때 잘 생긴다. 고치는 방법은 호출 경로에 트랜잭션 경계를 두는 것이고, 리포지토리 인터페이스의 해당 메서드에 @Transactional을 붙이는 것은 그 메서드가 단독으로 호출될 수 있을 때의 보험이다.

    리포지토리를 서비스에 직접 노출할지, 어댑터 뒤에 둘지는 바꿀 가능성이 있는 것이 무엇인가로 판단한다. 데이터 접근 기술이 확정되었고 페이징 같은 스프링 데이터 타입을 서비스가 그대로 써도 괜찮다면 직접 의존이 단순하다. 여러 저장 기술을 섞거나, 저장소를 메모리 구현으로 바꿔 끼워 테스트하거나, 도메인 계층이 프레임워크 타입을 모르게 하고 싶다면 어댑터의 비용을 치를 가치가 있다. 어느 쪽이든 검색 조건이 실행 중에 조합되기 시작하면 메서드 이름 방식은 한계에 닿으므로, 그 시점에 동적 쿼리 도구를 들일지도 함께 결정한다.
  • 본문의 MiniData에서 BookRepo에 List findByAuthor(String author);를 추가하고 실행하면 무엇이 출력되는가? 예외가 난다면 어느 줄에서, repo.save(...) 호출 전인지 후인지 답하고, 실제 스프링 데이터에서 같은 일이 언제 일어나는지 연결해 설명하라.
  • 다음 세 이름을 PartTree가 어떻게 해석할지 본문의 실행 결과 형식으로 적어라. (가) findFirstByOrderByUnitPriceAsc (나) findByTitleOrStockGreaterThanAndUnitPriceLessThan (다) countDistinctByTitle. (나)는 SQL의 WHERE 절로 바꾸면 괄호가 어디에 들어가는지도 쓴다.
  • 식별자를 직접 할당하는 Publisher(버전 없음, Persistable 미구현)에 대해 트랜잭션 하나 안에서 Publisher p = new Publisher("P01", "가"); Publisher s = repo.save(p); s.setName("나"); p.setName("다");를 실행했다. 테이블에 처음부터 P01이 없었다고 할 때, 영속성 컨텍스트에 어떤 객체가 관리되는지 그림으로 그리고, 커밋 후 테이블의 이름 칼럼 값과 실행되는 SQL의 종류·순서를 적어라.
  • 웹 요청 밖의 코드(예: 애플리케이션 시작 직후 한 번 실행되는 초기화 코드)에서 서비스를 거치지 않고 Book b = bookDataRepository.findById(1L).orElseThrow(); b.setStock(0); bookDataRepository.deleteByStock(0);를 실행했다(deleteByStock에는 @Transactional이 없고, 바깥에 열린 트랜잭션도 없다). 각 줄에서 트랜잭션이 어떻게 열리고 닫히는지, setStock(0)이 데이터베이스에 반영되는지, 마지막 줄에서 무슨 일이 일어나는지 설명하라.

(나) Or에서 먼저 나뉘므로 or[0] title SIMPLE_PROPERTY, or[1] stock GREATER_THAN과 or[1] unitPrice LESS_THAN이다. WHERE 절은 title = ?1 or (stock > ?2 and unitPrice < ?3)이다. AND가 OR보다 먼저 묶이는 것은 PartTree가 "AND 묶음들의 OR"로 만들어져 있기 때문이고, (title = ? or stock > ?) and unitPrice < ?를 원했다면 이름으로는 표현할 수 없다. (다) count=true, distinct=true, or[0] title SIMPLE_PROPERTY다. 주어 안의 Distinct는 키워드로 인식된다.

    3번. p는 식별자가 채워져 있고 버전이 없으므로 isNew가 false, save는 merge로 간다. Hibernate는 P01을 영속성 컨텍스트에서 찾지 못해 SELECT를 보내고, 행이 없으므로 새 관리 인스턴스 s를 만들어 p의 상태("가")를 복사한다. 영속성 컨텍스트가 관리하는 것은 s 하나이고, p는 끝까지 비영속이다. s.setName("나")는 관리 객체를 바꾸므로 반영되고, p.setName("다")는 어디에도 반영되지 않는다. 커밋 직전 플러시에서 s가 INSERT된다. INSERT가 "가"로 나간 뒤 UPDATE로 "나"가 되는지, 처음부터 "나"로 INSERT되는지는 구현의 플러시 처리에 달린 세부이지만 최종 값은 "나"다. SQL 종류는 SELECT 다음에 INSERT(그리고 경우에 따라 UPDATE) 순서다.

    4번. 첫 줄의 findById는 SimpleJpaRepository의 클래스 수준 @Transactional(readOnly = true) 때문에 읽기 전용 트랜잭션을 열고 조회한 뒤 커밋하며 닫는다. 영속성 컨텍스트도 함께 닫히므로 b는 준영속이다. 둘째 줄 setStock(0)은 준영속 객체의 필드만 바꾸므로 데이터베이스에 반영되지 않는다. 변경 감지는 관리 상태 엔티티에만 적용된다. 셋째 줄 deleteByStock(0)은 선언한 쿼리 메서드라 트랜잭션이 없다. 조회 쿼리는 공유 EntityManager가 임시로 만든 EntityManager로 실행되고, 이어서 결과를 하나씩 remove하려는 순간 트랜잭션이 필요한 메서드이므로 TransactionRequiredException이 나고, 리포지토리 프록시가 이를 InvalidDataAccessApiUsageException으로 바꿔 던진다. 데이터베이스에서 재고가 0인 행이 없었다면 remove를 부를 일이 없으므로 예외 없이 0을 돌려줄 수 있다는 점도 덧붙인다. 해결은 이 세 줄을 @Transactional 서비스 메서드 안으로 옮기는 것이다.

     스프링 부트 애플리케이션에 List findByTitel(String title)을 선언한 리포지토리가 있다(Book의 필드는 title). 기본 설정에서 이 오류는 언제 드러나는가? 이 메서드를 처음 호출할 때 PropertyReferenceException이 난다 애플리케이션이 시작하면서 리포지토리 프록시를 조립할 때 예외가 나서 시작이 중단된다 컴파일할 때 javac가 존재하지 않는 속성이라고 오류를 낸다 오류가 나지 않고 항상 빈 목록을 돌려준다 메서드 이름은 자바 언어 입장에서 그냥 식별자이므로 javac는 아무것도 검사하지 않는다. 스프링 데이터는 프록시를 조립할 때 QueryExecutorMethodInterceptor 생성자에서 모든 쿼리 메서드를 미리 RepositoryQuery로 바꾸고, 이 과정의 PartTree 해석에서 PropertyReferenceException이 난다. 기본 시작 방식에서는 프록시가 빈 초기화 중에 만들어지므로 첫 호출까지 기다리지 않는다. 지연 시작 방식을 설정한 경우에만 발견 시점이 뒤로 밀린다. 식별자를 @Id String code로 직접 할당하고 버전 속성이 없는 엔티티를 새로 만들어 save했다. Hibernate 기준으로 일어나는 일을 가장 정확하게 설명한 것은? persist가 호출되어 SELECT 없이 INSERT되고, 반환값은 인수와 같은 객체다 식별자가 이미 있으므로 UPDATE가 실행되고, 행이 없으면 아무 일도 일어나지 않는다 isNew가 true라서 persist로 가지만, 플러시 때 기본 키 중복 검사를 위해 SELECT가 추가된다 isNew가 false라서 merge로 가고, 존재 확인 SELECT 뒤 새 관리 객체에 상태를 복사해 INSERT하며, 반환값은 인수와 다른 객체다 식별자 타입이 래퍼(참조) 타입이고 값이 null이 아니므로 AbstractEntityInformation.isNew는 false다. 그래서 SimpleJpaRepository.save는 merge를 부른다. 명세상 새 엔티티의 merge는 새 관리 인스턴스를 만들어 상태를 복사하고 그것을 돌려주며, Hibernate는 대상이 새 것인지 알아내려고 먼저 조회한다. UPDATE만 나간다는 2번은 merge의 의미와 다르고, 1번과 3번은 판정 자체를 잘못 짚었다. 스프링 부트를 쓰지 않고 빌드를 직접 구성한 프로젝트에서 @Query("... where b.unitPrice <= :maxPrice")를 단 인터페이스 메서드에 @Param을 빼고 -g로만 컴파일했더니 파라미터를 연결하지 못했다. 가장 근본적인 이유는? 추상 메서드에는 Code 속성이 없어 지역 변수 표에 이름이 남을 자리가 없고, 이름은 -parameters가 만드는 MethodParameters 속성에만 남기 때문이다 -g는 줄 번호만 남기고 지역 변수 이름은 어떤 경우에도 남기지 않기 때문이다 JPQL의 이름 있는 파라미터는 인터페이스 메서드에서 원래 지원되지 않기 때문이다 스프링 데이터는 이름 있는 파라미터를 위치 파라미터로 바꿔 실행하므로 이름이 무시되기 때문이다 지역 변수 표(LocalVariableTable)는 메서드 본체를 담는 Code 속성 안에 들어가는데, 인터페이스의 추상 메서드에는 본체가 없다. 본문의 javap 비교에서 -g로 컴파일한 인터페이스에는 min, max 문자열이 아예 없었다. 게다가 Spring Framework 6.1부터는 지역 변수 표를 파싱하는 기능도 제거되었다. -g가 지역 변수 이름을 남긴다는 점에서 2번은 틀렸고, 이름 있는 파라미터는 @Param이나 -parameters로 잘 지원되므로 3번과 4번도 틀렸다. 서비스 트랜잭션 밖에서 bookDataRepository.deleteById(1L)은 정상 동작하는데, 같은 위치에서 bookDataRepository.deleteByTitle("JPA")(어노테이션 없음)는 InvalidDataAccessApiUsageException으로 실패했다. 차이를 만든 것은? deleteByTitle은 이름 해석에 실패해 시작 시점에 무효화된 메서드이기 때문이다 deleteById는 JPQL delete 문 하나로 실행되어 트랜잭션이 필요 없기 때문이다 deleteById는 SimpleJpaRepository에 @Transactional이 붙어 있지만, 선언한 쿼리 메서드에는 기본 트랜잭션이 없어 remove 호출이 트랜잭션 필수 검사에 걸리기 때문이다 예외 변환 인터셉터가 쿼리 메서드에만 적용되어 정상적인 예외까지 바꿔 버리기 때문이다 파생 삭제 쿼리는 조회 후 결과를 하나씩 remove한다. 선언한 쿼리 메서드에는 트랜잭션이 걸리지 않으므로, 공유 EntityManager가 트랜잭션 없는 remove를 거부하며 TransactionRequiredException을 던지고, 프록시의 예외 변환이 이를 InvalidDataAccessApiUsageException으로 바꾼다. deleteById도 조회 후 remove이므로 2번은 틀렸고, 트랜잭션이 있어서 성공한 것이다. 예외 변환은 모든 메서드에 적용되므로 4번도 틀렸다.
    스프링 데이터(Spring Data)
    저장소 종류와 무관한 리포지토리 추상화를 제공하는 Spring Data Commons와, 그 위의 저장소별 모듈(JPA, JDBC, MongoDB 등)로 이루어진 프로젝트 묶음.
    쿼리 메서드(query method)
    리포지토리 인터페이스에 선언한 메서드 중 이름 해석이나 @Query로 쿼리가 정해지는 메서드. 구현은 실행 시점에 RepositoryQuery로 만들어진다.
    PartTree
    Spring Data Commons의 메서드 이름 파서. 이름을 주어와 술어로 나누고, 술어를 OR로 구분한 AND 조건 묶음과 정렬, 개수 제한으로 해석한다.
    속성 표현식(property expression)
    쿼리 메서드 이름에서 PublisherName처럼 연관 객체의 속성까지 내려가는 경로 표현. 낙타 표기 경계에서 오른쪽부터 잘라 찾으며, 밑줄로 경계를 직접 지정할 수 있다.
    FactoryBean
    스프링 컨테이너가 그 객체 자체가 아니라 getObject()의 결과를 빈으로 등록하는 특별한 빈. 스프링 데이터는 리포지토리마다 JpaRepositoryFactoryBean을 등록한다.
    JDK 동적 프록시(JDK dynamic proxy)
    java.lang.reflect.Proxy가 실행 중에 생성하는 클래스. 지정한 인터페이스를 구현하고, 모든 메서드 호출을 호출 처리기(InvocationHandler)의 invoke로 넘긴다.
    MethodParameters 속성
    -parameters로 컴파일할 때 클래스 파일의 메서드에 추가되는 속성으로, 파라미터 이름과 플래그를 담는다. 리플렉션의 Parameter.getName()이 이 정보를 읽는다.
    Persistable
    엔티티가 직접 getId()와 isNew()를 제공하게 하는 Spring Data 인터페이스. 구현하면 save의 새 엔티티 판정을 엔티티가 맡는다.
    어댑터(adapter)
    한 인터페이스를 다른 인터페이스로 바꿔 주는 클래스. 여기서는 애플리케이션의 BookRepository를 구현하며 스프링 데이터 리포지토리에 위임한다.
