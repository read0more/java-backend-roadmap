    이 회차의 질문: 객체를 저장하는데 왜 SQL을 매번 손으로 쓰는가

    이 권은 같은 저장소 인터페이스를 여러 데이터 접근 기술로 구현해 보며 차이를 비교하고 있다. 01회의 JdbcTemplate은 커넥션 획득과 자원 정리, 예외 변환을 템플릿이 맡고 개발자는 SQL과 결과 매핑만 썼다. 03회의 MyBatis는 SQL을 XML로 옮기고 동적 SQL을 태그로 조립하게 해 주었다. 두 기술은 겉모습이 달라도 공통점이 하나 있다. SQL은 개발자가 쓴다. 도구는 그 SQL에 파라미터를 넣고 결과 행을 객체로 옮겨 줄 뿐이다. 그래서 이런 기술을 SQL 매퍼(SQL mapper)라고 부른다.

    이 회차의 JPA는 이 책임을 뒤집는다. 개발자는 "이 클래스는 저 테이블에, 이 필드는 저 컬럼에 대응한다"는 매핑만 선언하고, 저장·조회·수정·삭제에 필요한 SQL은 구현체가 만든다. 이런 방식을 객체-관계 매핑(Object-Relational Mapping, ORM)이라고 한다. 그런데 SQL을 대신 만들어 주는 것만으로는 ORM을 다 설명하지 못한다. JPA 코드에는 update() 메서드가 없는데도 필드 값을 바꾸면 UPDATE가 나가고, 같은 행을 두 번 조회해도 SELECT는 한 번만 나간다. 이런 동작은 SQL 생성기가 아니라 객체를 기억하는 저장소가 있어야 가능하다.

    이 회차는 그 저장소, 곧 영속성 컨텍스트(persistence context)를 중심에 두고 진행한다. 먼저 SQL 중심 개발이 어떤 문제를 낳는지, 객체와 테이블이 왜 서로 맞지 않는지를 본다. 다음으로 JPA가 표준과 구현으로 어떻게 나뉘는지, 영속성 컨텍스트가 무엇을 기억하는지를 실행 가능한 모형으로 확인한다. 그 뒤 스프링 부트에서 JPA를 설정하고, 엔티티와 리포지토리를 만들어 한 번의 호출에서 어떤 SQL이 언제 나가는지 추적한다. 마지막으로 JPA 예외가 스프링의 데이터 접근 예외로 바뀌는 경로를 프록시 수준에서 따라간다.

    이 회차의 예제는 도서(Book) 하나로 진행한다. 실험 코드는 JDK 21에서 직접 컴파일해 실행한 것이고, 스프링과 Hibernate의 내부 동작은 Spring Framework 6.1, Spring Boot 3.3, Hibernate 6.4 문서와 소스를 기준으로 확인했다.

    SQL 중심 개발의 문제점 1: 객체를 SQL로 옮겨 적는 일

    JDBC든 JdbcTemplate이든 MyBatis든, SQL 매퍼로 저장소를 만들면 테이블마다 같은 일을 반복한다. 객체의 필드를 꺼내 INSERT의 파라미터로 넣고, SELECT 결과의 컬럼을 하나씩 읽어 객체의 필드에 넣고, UPDATE의 SET 절에 바뀔 수 있는 필드를 늘어놓는다. 도서, 회원, 주문 테이블이 있으면 이 일을 세 번 한다. 이 코드는 비즈니스 규칙을 하나도 담고 있지 않다. 객체 모양의 데이터를 행 모양으로, 행 모양의 데이터를 다시 객체 모양으로 옮겨 적을 뿐이다.

    반복보다 더 곤란한 것은 변경이 퍼지는 방식이다. 도서에 출판사 이름 필드 publisher를 추가한다고 해 보자. 자바 클래스에 필드 하나를 넣는 것으로 끝나지 않는다. INSERT의 컬럼 목록과 값 목록, SELECT의 컬럼 목록, 결과를 객체로 옮기는 매핑 코드, UPDATE의 SET 절을 모두 고쳐야 한다. 이 중 하나를 빠뜨려도 컴파일러는 아무 말을 하지 않는다. SQL은 자바 컴파일러에게 그저 문자열이기 때문이다. SELECT에서 컬럼을 빠뜨리면 조회한 객체의 publisher는 조용히 null이 되고, 이 버그는 화면에 빈칸이 보일 때에야 드러난다.

    // SQL 매퍼 방식: 필드 하나를 추가하면 문자열 네 곳을 손으로 고쳐야 한다
String insert = "insert into book (title, price, stock_quantity, publisher) values (?, ?, ?, ?)";
String select = "select id, title, price, stock_quantity, publisher from book where id = ?";
String update = "update book set title = ?, price = ?, stock_quantity = ?, publisher = ? where id = ?";
// 그리고 ResultSet에서 publisher를 읽어 객체에 넣는 매핑 코드도 고쳐야 한다

    여기서 한 걸음 더 나가면 엔티티를 믿을 수 없는 문제가 생긴다. 서비스 코드가 리포지토리에서 도서를 받아 book.getPublisher()를 부른다고 하자. 이 값이 null이면 두 가지 가능성이 있다. 데이터베이스에 정말 값이 없거나, 리포지토리의 SELECT가 그 컬럼을 읽지 않았거나다. 둘 중 무엇인지 알려면 서비스 개발자가 리포지토리 안의 SQL을 열어 봐야 한다. 연관된 객체라면 더 심하다. book.getAuthor()가 채워져 있는지는 그 조회가 저자 테이블과 조인했는지에 달려 있다.

    계층을 나누는 이유는 아래 계층의 세부를 몰라도 위 계층을 작성할 수 있게 하기 위해서다. 그런데 객체에 무엇이 채워져 있는지가 SQL에 달려 있으면, 서비스 계층은 리포지토리의 SQL을 알아야만 안전하게 객체를 쓸 수 있다. 인터페이스로 계층을 나눠 놓아도 실제로는 SQL이라는 세부에 묶여 있는 셈이다. SQL 중심 개발에서 "진정한 의미의 계층 분할이 어렵다"는 말은 이 상황을 가리킨다.

    SQL 중심 개발의 문제점 2: 객체와 테이블의 패러다임 불일치

    반복과 엔티티 신뢰 문제의 뿌리는 더 깊은 곳에 있다. 객체 지향 언어와 관계형 데이터베이스는 데이터를 표현하는 사고방식, 곧 패러다임이 다르다. 객체는 상태와 행위를 캡슐화하고, 상속으로 공통점을 묶고, 참조로 다른 객체를 가리키며, 참조를 따라가는 그래프를 이룬다. 관계형 데이터베이스는 데이터를 집합(테이블)의 행으로 표현하고, 외래 키 값으로 다른 행을 가리키며, 조인으로 행들을 엮는다. 이 차이를 객체-관계 패러다임 불일치(object-relational impedance mismatch)라고 부른다. 네 가지로 나눠 보자.

    상속

    도서와 음반이 모두 상품이라는 공통 부모를 가진다고 하자. 자바에서는 Item을 상속한 Book과 Album을 만들면 된다. 테이블에는 상속이 없다. 가장 비슷한 모델은 공통 컬럼을 담은 item 테이블과 고유 컬럼을 담은 book, album 테이블을 같은 키로 잇는 것이다. 그러면 도서 하나를 저장할 때 INSERT를 두 번(item, book) 해야 하고, 조회할 때는 두 테이블을 조인한 뒤 결과를 하나의 Book 객체로 조립해야 한다. 자바 컬렉션에 넣었다면 list.add(book) 한 줄로 끝났을 일이다.

    연관관계

    객체는 참조로 관계를 표현한다. book.getPublisher()로 출판사 객체에 간다. 참조에는 방향이 있어서, 도서는 출판사를 알지만 출판사는 자기 도서 목록을 따로 들고 있지 않으면 도서를 모른다. 테이블은 외래 키로 관계를 표현한다. book.publisher_id 컬럼 하나만 있으면 도서에서 출판사로도, 출판사에서 도서로도 조인할 수 있다. 방향이 없다. 그래서 SQL 매퍼로 개발하다 보면 객체에 Publisher publisher 대신 Long publisherId를 넣는 일이 흔해진다. 테이블에 맞춘 모델링이다. 반대로 참조를 그대로 두면 저장할 때 book.getPublisher().getId()를 꺼내 외래 키 값으로 바꾸고, 조회할 때 두 테이블을 조인해 두 객체를 만든 뒤 참조로 이어 줘야 한다.

    객체 그래프 탐색

    객체는 참조를 따라 자유롭게 이동할 수 있어야 한다. order.getMember().getTeam().getName()처럼. 그러나 SQL 매퍼에서는 처음 실행한 SQL이 탐색 범위를 정한다. 주문과 회원만 조인해 가져왔다면 getTeam()은 null을 돌려준다. 앞 절의 엔티티 신뢰 문제가 여기서 다시 나타난다. 그렇다고 연관된 모든 객체를 처음부터 다 조인해 메모리에 올리는 것도 답이 아니다. 주문 하나를 보는데 회원, 팀, 배송, 상품 전부를 읽는 것은 낭비다. 필요할 때 그때그때 읽어 오는 방법이 필요하다.

    비교

    자바에서 같은 객체인지 묻는 방법은 두 가지다. 참조가 같은지 보는 동일성(identity, ==)과 내용이 같은지 보는 동등성(equality, equals())이다. 데이터베이스에서는 기본 키가 같으면 같은 행이다. SQL 매퍼로 만든 리포지토리에서 같은 기본 키로 두 번 조회하면 어떻게 될까. 조회할 때마다 결과 행으로 새 객체를 만들기 때문에 두 객체는 내용이 같아도 참조가 다르다.

    Book a = jdbcRepository.findById(1L).orElseThrow();
Book b = jdbcRepository.findById(1L).orElseThrow();
System.out.println(a == b);       // false: 조회할 때마다 new Book(...)

List list = new ArrayList<>();
list.add(a);
System.out.println(list.get(0) == list.get(0));   // true: 컬렉션은 같은 참조를 돌려준다

    같은 행을 가리키는 객체가 메모리에 여러 개 있으면, 한쪽을 고쳐도 다른 쪽에는 반영되지 않는다. 어느 객체가 최신 상태인지 개발자가 기억해야 한다. 자바 컬렉션처럼 "같은 키로 꺼내면 같은 객체"를 보장하려면 누군가 이미 만든 객체를 키별로 기억하고 있어야 한다.

    왼쪽의 객체 그래프(상속과 참조)와 오른쪽의 테이블(분리된 테이블과 외래 키)이 서로 어떻게 대응하는지, 그 사이에서 개발자가 손으로 하던 변환을 ORM이 맡는다는 것을 보여 준다. 좌우 2분할 도해. 왼쪽 패널 제목 "객체". 위에 둥근 상자 "Item", 그 아래로 속이 빈 삼각형 화살표로 연결된 두 상자 "Book"과 "Album"(상속). "Book" 상자에서 오른쪽 아래 상자 "Publisher"로 실선 화살표, 화살표 라벨 "참조". 오른쪽 패널 제목 "테이블". 세 개의 표 모양 상자 "item", "book", "publisher". "book"과 "item" 사이에 "같은 키" 라벨의 점선, "book"의 칸 "publisher_id"에서 "publisher" 표로 가는 화살표 라벨 "외래 키". 두 패널 사이 가운데에 세로로 긴 회색 띠 "ORM"이 있고, 띠 양쪽으로 굵은 양방향 화살표가 지나간다. 띠 아래 작은 글씨 "변환을 대신한다". 평면 기술 도해, 흰 배경, 파랑과 회색 위주. 객체의 상속과 참조는 테이블의 분리된 테이블과 외래 키로 옮겨져야 한다. 이 변환을 개발자 대신 해 주는 것이 ORM이다.

    ORM과 JPA: 표준 명세와 구현체

    ORM은 이 불일치를 개발자 대신 해결해 주는 기술이다. 개발자는 객체를 객체답게 설계하고, 데이터베이스는 데이터베이스답게 설계한다. 둘 사이의 대응 관계는 매핑 정보로 선언한다. ORM은 그 매핑 정보를 보고 SQL을 만들고, JDBC로 실행하고, 결과를 객체로 조립하며, 같은 행은 같은 객체로 돌려준다. 애플리케이션 코드는 컬렉션에 넣고 꺼내듯 객체를 다룬다.

    JPA는 자바 진영의 ORM 표준 명세다. 지금 이름은 Jakarta Persistence이고, 명세 문서와 함께 jakarta.persistence 패키지의 인터페이스와 애너테이션으로 이루어져 있다. 명세는 "이 메서드를 부르면 이렇게 동작해야 한다"는 규칙이고, 실제로 SQL을 만들고 실행하는 코드는 구현체(provider)가 제공한다. 스프링 부트의 spring-boot-starter-data-jpa는 구현체로 Hibernate를 가져온다. JDBC가 표준 인터페이스이고 드라이버가 구현이었던 관계(스프링 DB 1편 01회)와 같은 구조다.

    패키지 이름은 버전에 따라 다르다. 오래된 자료에는 javax.persistence가 나오는데, Jakarta EE 9와 함께 나온 Jakarta Persistence 3.0부터 패키지가 jakarta.persistence로 바뀌었다. 이 강좌의 기준인 Spring Boot 3.x는 jakarta.* 네임스페이스를 쓴다. Hibernate 공식 릴리스 페이지의 호환성 표를 보면 Hibernate 6.6은 Jakarta Persistence 3.1을, Hibernate 7.x는 3.2를 구현한다. 이 회차의 코드는 두 버전에서 똑같이 동작하는 범위만 쓴다.

    JPA가 JDBC를 대체한다고 오해하기 쉽지만, JPA는 JDBC 위에 있다. 구현체는 결국 Connection을 얻어 PreparedStatement를 만들고 실행한다. 스프링 DB 1편에서 다룬 커넥션 풀, 트랜잭션, 자동 커밋, 격리 수준은 JPA를 써도 그대로 아래에서 동작한다. 바뀌는 것은 SQL을 누가 만드느냐와, 그 사이에 객체를 기억하는 층이 하나 더 생긴다는 점이다.

    영속성 컨텍스트: JPA가 객체를 기억하는 곳

    Jakarta Persistence 3.1 명세 3.1절은 영속성 컨텍스트를 엔티티 인스턴스의 집합으로 정의하고, 그 안에서는 어떤 영속 엔티티 식별자에 대해서도 유일한 엔티티 인스턴스가 있다고 말한다. 같은 기본 키를 가진 Book 객체는 하나의 영속성 컨텍스트 안에 하나만 존재한다는 뜻이다. Hibernate 6.4 입문 가이드(5.1절)는 같은 것을 두고 영속성 컨텍스트가 일종의 캐시이며 "1차 캐시(first-level cache)"라고도 부른다고 설명한다. 컨텍스트는 식별자에서 인스턴스로 가는 유일한 대응표를 갖는다.

    애플리케이션은 EntityManager를 통해 영속성 컨텍스트에 접근한다. 명세 3.2절은 엔티티 인스턴스의 상태를 넷으로 나눈다.

    영속성 컨텍스트에 있는 변경 내용을 데이터베이스에 SQL로 보내는 일을 플러시(flush)라고 한다. 명세 3.2.2절은 새 엔티티에 persist()를 적용하면 그 엔티티가 관리 상태가 되고 "트랜잭션 커밋 시점이나 그 전, 또는 플러시의 결과로" 데이터베이스에 들어간다고 말한다. 3.2.4절은 영속 엔티티의 상태가 트랜잭션 커밋 때 데이터베이스와 동기화된다고 말한다. 즉 persist()나 값 변경이 곧바로 SQL이 된다고 보장하지 않는다. 언제 보낼지는 구현체가 정하되, 커밋할 때까지는 반드시 보낸다.

    플러시가 일어나는 시점은 세 가지다. 첫째, 트랜잭션을 커밋할 때. 둘째, 쿼리를 실행하기 전. 명세 3.10.8절은 트랜잭션 안에서 플러시 모드가 FlushModeType.AUTO(기본값)인 쿼리를 실행하면, 구현체가 쿼리 결과에 영향을 줄 수 있는 영속성 컨텍스트의 모든 변경을 쿼리 처리에서 보이게 할 책임이 있다고 정한다. Hibernate 입문 가이드 5.8절도 기본 설정에서 트랜잭션 커밋 때, 그리고 메모리에 있는 변경 상태가 결과에 영향을 줄 쿼리를 실행하기 전에 플러시한다고 설명한다. 셋째, 개발자가 em.flush()를 직접 부를 때. 플러시는 영속성 컨텍스트를 비우는 일이 아니다. 변경을 SQL로 보낼 뿐 객체는 그대로 관리 상태로 남는다.

    영속성 컨텍스트가 주는 기능은 이 "식별자별 대응표"와 "플러시"에서 모두 나온다.

    • 1차 캐시와 동일성 보장: find()는 먼저 대응표를 본다. 이미 있으면 SQL 없이 그 객체를 돌려준다. 그래서 같은 컨텍스트 안에서 같은 식별자로 두 번 조회하면 ==가 true다. 앞 절의 비교 불일치가 여기서 풀린다.
    • 쓰기 지연(transactional write-behind): 변경을 모았다가 플러시 때 보낸다. Hibernate 입문 가이드 5.4절은 persist()와 remove()가 데이터베이스에 즉시 효과를 내지 않고 SQL을 나중에 실행하도록 예약한다고 설명한다. 모아 두었기 때문에 같은 종류의 문장을 JDBC 배치로 묶어 보낼 기회도 생긴다. 단, 뒤에서 볼 IDENTITY 전략의 INSERT는 예외다.
    • 변경 감지(dirty checking): 관리 상태의 객체가 컨텍스트에 들어올 때의 상태를 복사해 둔다. 이것을 스냅샷이라고 부르자. 플러시 때 지금 상태와 스냅샷을 비교해 다른 객체에 대해 UPDATE를 만든다. 그래서 update() 메서드가 필요 없다. Hibernate 입문 가이드는 엔티티를 수정한 뒤 명시적인 작업을 할 필요가 없고, 수정은 플러시 때 자동으로 감지된다고 설명한다.
    • 지연 로딩(lazy loading): 연관된 객체를 실제로 사용할 때 읽어 오도록 미뤄 둘 수 있다. 앞 절의 객체 그래프 탐색 불일치에 대한 답이다. 연관관계 매핑은 이 회차의 범위를 넘으므로, 여기서는 "가짜 객체(프록시)를 먼저 넣어 두고 처음 접근할 때 SELECT한다"는 원리만 기억해 두자. 이 원리가 엔티티 클래스에 제약을 거는데, 엔티티 매핑에서 다시 본다.

    변경 감지가 "스냅샷과 비교"라는 것은 Hibernate의 기본 방식이다. Hibernate 6.4 사용자 가이드의 바이트코드 향상(bytecode enhancement) 장은 Hibernate가 원래 차이 비교(diff) 방식의 변경 계산만 지원했다고 설명한다. 플러시 때 컨텍스트의 엔티티를 하나씩 돌며 현재 상태를 마지막으로 알려진 데이터베이스 상태의 복사본과 비교한다. 바이트코드 향상으로 "인라인 변경 추적"을 켜면 엔티티 클래스 자체에 어떤 속성이 바뀌었는지 기록하는 코드가 들어가고, 플러시 때 비교 대신 엔티티에게 무엇이 바뀌었는지 묻는다. 특별히 설정하지 않은 스프링 부트 애플리케이션은 비교 방식으로 동작한다고 보면 된다.

    EntityManager 안의 영속성 컨텍스트가 식별자별 엔티티와 그 스냅샷을 나란히 보관하고, 플러시 때 둘을 비교해 UPDATE를 만들어 데이터베이스로 보내는 흐름을 보여 준다. 가로로 긴 구조도. 왼쪽에 작은 상자 "애플리케이션", 오른쪽 끝에 원통 "데이터베이스". 가운데에 큰 둥근 사각형 "EntityManager", 그 안에 더 큰 영역 "영속성 컨텍스트". 영속성 컨텍스트 안에 3열 표: 열 제목 "@Id", "엔티티", "스냅샷". 첫 행 "1" / 파란 상자 "Book(price=27000)" / 회색 상자 "price=30000". 둘째 행 "2" / 파란 상자 "Book" / 회색 상자 "같음". 표 아래에 세로로 쌓인 작은 상자 묶음 "쓰기 지연 SQL". 애플리케이션에서 영속성 컨텍스트로 화살표 두 개, 라벨 "find(1)"과 "price 변경". 첫 행의 파란 상자와 회색 상자 사이에 빨간 양방향 화살표 라벨 "플러시 때 비교". 비교 화살표에서 "쓰기 지연 SQL"로 화살표 라벨 "UPDATE 생성". "쓰기 지연 SQL"에서 데이터베이스로 굵은 화살표 라벨 "flush". 평면 기술 도해, 흰 배경, 파랑·회색·빨강 강조. 영속성 컨텍스트는 식별자별로 엔티티와 스냅샷을 함께 보관한다. 플러시 때 둘을 비교해 바뀐 엔티티에 대해서만 UPDATE를 만든다.

    모형으로 따라가 보는 영속성 컨텍스트

    규칙을 문장으로만 외우면 "언제 어떤 SQL이 나가는가"를 예측하기 어렵다. 그래서 영속성 컨텍스트의 핵심 규칙 네 가지만 흉내 낸 모형을 직접 만들어 돌려 보자. 식별자별 대응표, 스냅샷 비교, 쿼리 전 자동 플러시, IDENTITY 방식의 즉시 INSERT다. 데이터베이스는 TreeMap으로 흉내 내고, SQL은 실행하는 대신 출력한다. 이 코드는 Hibernate가 아니다. 실제 Hibernate는 엔티티마다 상태 정보를 담은 항목을 두고, 실행할 SQL을 액션 큐에 모으고, JDBC로 진짜 SQL을 보낸다. 모형은 그 골격만 보여 준다.

    import java.util.*;

public class MiniJpa {

    static class Book {
        Long id;
        String title;
        int price;
        protected Book() {}                          // 조회 결과로 객체를 만들 때 쓴다
        Book(String title, int price) { this.title = title; this.price = price; }
        Object[] state() { return new Object[]{title, price}; }
        void load(Object[] s) { title = (String) s[0]; price = (Integer) s[1]; }
    }

    // 데이터베이스 흉내: id -> {title, price}
    static class FakeDb {
        final Map rows = new TreeMap<>();
        long seq = 0;
        long insert(Object[] s) {
            long id = ++seq;
            rows.put(id, s.clone());
            System.out.println("  SQL> insert into book (title, price) values ('" + s[0] + "', " + s[1] + ")  -- id=" + id);
            return id;
        }
        Object[] select(long id) {
            System.out.println("  SQL> select ... from book where id=" + id);
            Object[] r = rows.get(id);
            return r == null ? null : r.clone();
        }
        void update(long id, Object[] s) {
            System.out.println("  SQL> update book set title='" + s[0] + "', price=" + s[1] + " where id=" + id);
            rows.put(id, s.clone());
        }
        Map selectWherePriceGt(int p) {
            System.out.println("  SQL> select ... from book where price>" + p);
            Map result = new TreeMap<>();
            rows.forEach((id, r) -> { if ((Integer) r[1] > p) result.put(id, r.clone()); });
            return result;
        }
    }

    static class MiniEntityManager {
        final FakeDb db;
        final Map identityMap = new LinkedHashMap<>();   // 1차 캐시
        final Map snapshots = new HashMap<>();       // 들어올 때의 상태

        MiniEntityManager(FakeDb db) { this.db = db; }

        void persist(Book b) {                 // IDENTITY: 행을 넣어야 id를 안다
            b.id = db.insert(b.state());
            manage(b, b.state());
        }

        Book find(long id) {
            Book cached = identityMap.get(id);
            if (cached != null) {
                System.out.println("  (1차 캐시 적중: id=" + id + ", SQL 없음)");
                return cached;
            }
            Object[] row = db.select(id);
            return row == null ? null : hydrate(id, row);
        }

        List findByPriceGreaterThan(int price) {
            flush();                           // AUTO: 질의 전에 변경을 먼저 내보낸다
            List result = new ArrayList<>();
            db.selectWherePriceGt(price).forEach((id, row) -> {
                Book existing = identityMap.get(id);
                result.add(existing != null ? existing : hydrate(id, row));  // 이미 있으면 그 객체
            });
            return result;
        }

        void flush() {
            for (Book b : identityMap.values()) {
                Object[] now = b.state();
                if (!Arrays.equals(now, snapshots.get(b.id))) {
                    db.update(b.id, now);
                    snapshots.put(b.id, now);
                }
            }
        }

        private Book hydrate(long id, Object[] row) {
            Book b = new Book();               // 기본 생성자로 빈 객체를 만들고
            b.id = id;
            b.load(row);                       // 행의 값을 채운다
            manage(b, row);
            return b;
        }

        private void manage(Book b, Object[] state) {
            identityMap.put(b.id, b);
            snapshots.put(b.id, state.clone());
        }
    }

    public static void main(String[] args) {
        FakeDb db = new FakeDb();
        MiniEntityManager em = new MiniEntityManager(db);

        System.out.println("[1] persist");
        Book book = new Book("JPA", 30000);
        em.persist(book);
        System.out.println("  book.id=" + book.id);

        System.out.println("[2] find(1)");
        Book found = em.find(1);
        System.out.println("  found == book ? " + (found == book));

        System.out.println("[3] book.price = 27000 (메서드 호출 없음)");
        book.price = 27000;

        System.out.println("[4] price > 28000 조회");
        List list = em.findByPriceGreaterThan(28000);
        System.out.println("  결과 " + list.size() + "건");

        System.out.println("[5] book.title = \"JPA 입문\" 후 커밋");
        book.title = "JPA 입문";
        em.flush();
        System.out.println("  커밋 완료");

        System.out.println("[6] 새 영속성 컨텍스트에서 find(1) 두 번");
        MiniEntityManager em2 = new MiniEntityManager(db);
        Book x = em2.find(1);
        Book y = em2.find(1);
        System.out.println("  x == y ? " + (x == y) + ", x == book ? " + (x == book) + ", x.title=" + x.title + ", x.price=" + x.price);

    한 단계씩 추적해 보자. [1]에서 persist()는 곧바로 INSERT를 보낸다. 모형의 식별자가 데이터베이스 시퀀스(seq)에서 나오기 때문에, 행을 넣기 전에는 book.id를 알 수 없다. 대응표의 키가 식별자이므로 식별자 없이는 객체를 관리 상태로 넣을 수도 없다. INSERT가 끝나고 나서야 identityMap에 1 → book이, snapshots에 1 → {"JPA", 30000}이 들어간다. 이 구조가 실제 IDENTITY 전략이 즉시 INSERT하는 이유와 같다. 뒤의 리포지토리 분석에서 Hibernate 문서로 다시 확인한다.

    [2]에서 find(1)은 대응표에서 바로 객체를 찾는다. SQL이 나가지 않고, 돌려받은 객체는 [1]에서 만든 바로 그 객체다. found == book이 true인 것은 내용이 같아서가 아니라 참조가 같아서다. [3]에서는 필드 값만 바꾸고 아무 메서드도 부르지 않는다. 이 시점에 SQL은 없다. 데이터베이스의 행은 여전히 가격 30000이고, 메모리의 객체만 27000이다. 둘이 어긋난 상태다.

    [4]가 이 회차에서 가장 중요한 장면이다. 조회 쿼리를 실행하기 전에 flush()가 먼저 돈다. 스냅샷 {"JPA", 30000}과 현재 상태 {"JPA", 27000}이 다르므로 UPDATE가 나가고, 그 다음에 SELECT가 나간다. 만약 플러시 없이 SELECT를 바로 보냈다면 어떻게 될까. 데이터베이스의 행은 아직 30000이므로 "가격이 28000보다 큰 도서"로 이 행이 뽑힌다. 그런데 결과를 객체로 바꿀 때 대응표에 이미 있는 객체를 돌려주므로, 애플리케이션은 가격이 27000인 객체를 "28000보다 비싼 도서" 목록으로 받는다. 조건과 결과가 모순된다. 명세가 AUTO 플러시를 요구하는 이유가 이것이다.

    [5]의 flush()는 커밋에 해당한다. 제목이 바뀌었으므로 UPDATE가 하나 나간다. [4]에서 이미 가격 변경을 보내고 스냅샷을 갱신했기 때문에 가격 변경이 두 번 나가지는 않는다. 모형의 UPDATE는 바뀐 컬럼만이 아니라 두 컬럼을 모두 SET에 넣는데, 이 점도 Hibernate의 기본 동작과 닮았다. 뒤에서 다시 본다.

    [6]에서는 영속성 컨텍스트를 새로 만든다. 첫 find(1)은 대응표가 비어 있으므로 SELECT를 보내고, 기본 생성자로 빈 객체를 만든 뒤 행의 값을 채운다(hydrate). 두 번째 find(1)은 대응표에서 꺼낸다. x == y는 true지만 x == book은 false다. 동일성 보장은 하나의 영속성 컨텍스트 안에서만 성립한다. 스프링에서 영속성 컨텍스트는 보통 트랜잭션 하나와 수명이 같으므로, 서로 다른 트랜잭션에서 조회한 객체는 같은 행이라도 다른 객체다.

    이 장의 핵심

    JPA가 하는 일 대부분은 "식별자별로 객체를 하나씩 기억하고, 들어올 때의 상태를 함께 기억한다"는 한 가지 구조에서 나온다. 1차 캐시와 동일성 보장은 대응표에서, 변경 감지는 스냅샷 비교에서, 쓰기 지연은 플러시 시점에 모아 보내는 데서 나온다. 언제 SQL이 나가는지 헷갈리면 "지금 대응표와 스냅샷은 어떤 상태인가, 지금 플러시가 일어나는가"를 물으면 된다.

    JPA 설정: 스타터 하나가 등록하는 것들

    runtimeOnly 'com.h2database:h2'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

JDBC 스타터가 들어 있으므로 HikariCP 커넥션 풀과 spring-jdbc(JdbcTemplate)도 함께 온다. JPA가 JDBC 위에 있다는 앞 절의 그림이 의존성 목록에서도 드러난다. Spring Data JPA는 05회의 주제지만, 이 스타터에 들어 있다는 사실이 이 회차의 EntityManager 주입 방식에 영향을 준다. 뒤에서 다시 본다.

    다음은 설정 파일이다. 스키마는 직접 작성한 SQL로 관리하고, Hibernate가 실행하는 SQL과 바인딩 값을 로그로 본다.

spring.datasource.username=sa

# 스키마는 직접 관리한다. Hibernate가 테이블을 만들거나 지우지 않게 한다
spring.jpa.hibernate.ddl-auto=none

# Hibernate가 실행하는 SQL을 로거로 남긴다
logging.level.org.hibernate.SQL=DEBUG
# 바인딩된 파라미터 값까지 남긴다 (Hibernate 6의 로거 이름)
logging.level.org.hibernate.orm.jdbc.bind=TRACE

    설정 하나하나에 이유가 있다. Spring Boot 3.3 속성 부록은 spring.jpa.hibernate.ddl-auto를 Hibernate의 hibernate.hbm2ddl.auto로 가는 지름길이라고 설명하고, 기본값을 "임베디드 데이터베이스를 쓰고 스키마 관리 도구가 감지되지 않으면 create-drop, 그 밖에는 none"이라고 적는다. 임베디드 H2로 테스트하는 순간 Hibernate가 엔티티를 보고 테이블을 만들었다가 지우게 된다는 뜻이다. 테이블을 SQL 스크립트로 직접 관리하는 프로젝트라면 이 값을 명시적으로 none으로 두는 편이 의도가 분명하다.

    SQL을 보는 방법은 두 가지다. spring.jpa.show-sql=true는 속성 부록의 설명대로 SQL 문장 로깅을 켜는데, 이 값은 Hibernate의 hibernate.show_sql 설정으로 이어져 로거가 아닌 표준 출력(System.out)에 SQL을 찍는다. 로그 레벨이나 출력 위치를 로깅 설정으로 제어할 수 없다는 뜻이다. 그래서 보통은 org.hibernate.SQL 로거를 DEBUG로 켜는 방법을 쓴다. 바인딩 값은 별도 로거에 나온다. Hibernate 5까지는 org.hibernate.type.descriptor.sql이었고, Hibernate 6부터는 org.hibernate.orm.jdbc.bind다. 오래된 블로그의 설정을 그대로 가져오면 바인딩 값이 안 보이는 이유가 이 이름 변경이다. 바인딩 값에는 비밀번호나 개인정보가 섞일 수 있으므로 운영 환경에서는 켜지 않는다.

    JPA 적용 1: 엔티티 매핑

    이제 도서 엔티티를 만든다. 매핑 정보는 애너테이션으로 클래스에 직접 붙인다.

    package example.bookstore.domain;

import jakarta.persistence.Column;
import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Book {

    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    @Column(name = "book_title", length = 100)
    private String title;

    private Integer price;
    private Integer stockQuantity;

    protected Book() {
    }

    public Book(String title, Integer price, Integer stockQuantity) {
        this.title = title;
        this.price = price;
        this.stockQuantity = stockQuantity;
    }

    public void change(String title, Integer price, Integer stockQuantity) {
        this.title = title;
        this.price = price;
        this.stockQuantity = stockQuantity;
    }

    public Long getId() { return id; }
    public String getTitle() { return title; }
    public Integer getPrice() { return price; }
    public Integer getStockQuantity() { return stockQuantity; }
}
    -- H2 기준. MySQL이라면 id bigint not null auto_increment
create table book (
    id             bigint generated by default as identity,
    book_title     varchar(100),
    price          integer,
    stock_quantity integer,
    primary key (id)
);

    @Entity는 이 클래스가 JPA가 관리하는 엔티티라는 표시다. 엔티티 스캔이 이 애너테이션을 찾아 매핑 정보를 만든다. @Id는 기본 키에 대응하는 필드, 곧 영속성 컨텍스트 대응표의 키다. @GeneratedValue는 키 값을 누가 만드는지 정한다. 이 애너테이션의 strategy 기본값은 AUTO다(로컬 API JAR의 애너테이션 기본값을 javap -v로 확인했다). 여기서는 IDENTITY를 골랐다. 데이터베이스의 identity 또는 auto_increment 컬럼이 값을 만든다는 뜻이다. H2의 generated by default as identity, MySQL의 auto_increment가 이에 해당한다.

    @Column은 필드와 컬럼의 대응을 바꿀 때 쓴다. 필드 이름은 title이지만 컬럼 이름은 book_title이라고 알려 준다. length(기본값 255)는 문자열 컬럼의 길이인데, 이 값은 Hibernate가 스키마를 생성할 때 DDL에 쓰인다. 값을 저장할 때 길이를 검사하는 기능이 아니다. 스키마를 직접 관리한다면 DDL의 varchar(100)과 맞춰 두는 문서 역할에 가깝다.

    price와 stockQuantity에는 아무 애너테이션도 없다. JPA는 엔티티의 필드를 기본으로 모두 영속 대상으로 본다. 그런데 필드 이름은 stockQuantity이고 컬럼 이름은 stock_quantity다. 이 변환은 스프링 부트가 해 준다. Spring Boot 3.3 how-to 문서에 따르면 스프링 부트는 Hibernate의 물리 이름 전략(physical naming strategy)으로 CamelCaseToUnderscoresNamingStrategy를 설정한다. 점은 밑줄로, 낙타 표기(camel case)는 밑줄 구분으로 바꾸고, 테이블 이름은 소문자로 만든다. 문서의 예로 TelephoneNumber 엔티티는 telephone_number 테이블에 매핑된다. 스프링 없이 Hibernate만 쓰면 이 전략이 적용되지 않으므로 필드 이름이 그대로 컬럼 이름이 된다. 같은 엔티티가 환경에 따라 다른 컬럼을 찾는 일이 생기는 이유다.

    필드에 매핑 애너테이션을 붙이느냐 게터에 붙이느냐도 의미가 있다. 명세는 엔티티 계층에 하나의 접근 방식이 적용되고, 기본 접근 방식은 매핑 애너테이션의 위치로 정해진다고 말한다. @Id가 필드에 있으므로 이 엔티티는 필드 접근(field access)을 쓴다. 구현체는 리플렉션으로 필드를 직접 읽고 쓴다. 그래서 세터가 없어도 조회 결과를 채울 수 있고, 게터는 애플리케이션을 위해 있을 뿐이다. 위 엔티티가 세터 대신 의미 있는 이름의 change() 메서드를 둔 것도 이 덕분이다.

    기본 생성자와 final 금지: 명세의 규칙과 그 이유

    엔티티에는 protected Book() {}이라는, 애플리케이션 코드에서는 쓰지 않는 생성자가 있다. Jakarta Persistence 3.1 명세 2.1절은 엔티티 클래스가 인자 없는 생성자를 가져야 하고 그 생성자는 public이나 protected여야 한다고 정한다. 같은 절은 엔티티 클래스가 final이면 안 되고, 메서드나 영속 인스턴스 변수도 final이면 안 된다고 말한다. Hibernate 6.4 입문 가이드도 엔티티 클래스는 final이 아니어야 하고 private이 아닌 인자 없는 생성자가 있어야 한다고 적는다.

    기본 생성자가 필요한 이유는 모형의 hydrate()에서 이미 봤다. 조회 결과로 객체를 만들 때 구현체는 어떤 생성자에 어떤 인자를 넣어야 할지 모른다. 그래서 빈 객체를 만든 뒤 필드에 값을 채운다. 그런데 리플렉션은 접근 제한을 풀 수 있다. 실제로 확인해 보자. 다른 패키지의 private 생성자를 리플렉션으로 호출하는 코드다.

    // a/Book.java
package a;
public class Book {
    private Long id;
    private String title;
    private Book() {}
    public Book(String title) { this.title = title; }
}

// Reflect.java (기본 패키지)
import java.lang.reflect.Constructor;
public class Reflect {
    public static void main(String[] args) throws Exception {
        Constructor c = a.Book.class.getDeclaredConstructor();
        try { c.newInstance(); } catch (IllegalAccessException e) { System.out.println("1: " + e.getClass().getSimpleName()); }
        c.setAccessible(true);
        a.Book b = c.newInstance();
        System.out.println("2: created " + (b != null));
    }
}

2: created true

    JPA 적용 1: 리포지토리 개발

    저장소 인터페이스와 검색 조건, 수정 내용을 담는 타입은 다음과 같다. 이 인터페이스는 기술에 독립적이다. JdbcTemplate으로도, MyBatis로도, JPA로도 구현할 수 있다.

    public record BookSearch(String keyword, Integer maxPrice) {}

public record BookChange(String title, Integer price, Integer stockQuantity) {}

public interface BookRepository {
    Book save(Book book);
    void update(Long bookId, BookChange change);
    Optional findById(Long id);
    List findAll(BookSearch search);

    JPA 구현은 다음과 같다.

    package example.bookstore.repository.jpa;

import example.bookstore.domain.Book;
import example.bookstore.repository.BookChange;
import example.bookstore.repository.BookRepository;
import example.bookstore.repository.BookSearch;
import jakarta.persistence.EntityManager;
import jakarta.persistence.TypedQuery;
import org.springframework.stereotype.Repository;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.util.StringUtils;

import java.util.ArrayList;
import java.util.List;
import java.util.Optional;

@Repository
@Transactional
public class JpaBookRepository implements BookRepository {

    private final EntityManager em;

    public JpaBookRepository(EntityManager em) {
        this.em = em;
    }

    @Override
    public Book save(Book book) {
        em.persist(book);
        return book;
    }

    @Override
    public void update(Long bookId, BookChange change) {
        Book book = em.find(Book.class, bookId);   // 없으면 null: 예제에서는 처리 생략
        book.change(change.title(), change.price(), change.stockQuantity());
    }

    @Override
    public Optional findById(Long id) {
        Book book = em.find(Book.class, id);
        return Optional.ofNullable(book);
    }

    @Override
    public List findAll(BookSearch search) {
        String keyword = search.keyword();
        Integer maxPrice = search.maxPrice();

        List conditions = new ArrayList<>();
        if (StringUtils.hasText(keyword)) {
            conditions.add("b.title like concat('%', :keyword, '%')");
        }
        if (maxPrice != null) {
            conditions.add("b.price <= :maxPrice");
        }

        String jpql = "select b from Book b";
        if (!conditions.isEmpty()) {
            jpql += " where " + String.join(" and ", conditions);
        }

        TypedQuery query = em.createQuery(jpql, Book.class);
        if (StringUtils.hasText(keyword)) {
            query.setParameter("keyword", keyword);
        }
        if (maxPrice != null) {
            query.setParameter("maxPrice", maxPrice);
        }
        return query.getResultList();
    }
}

    코드에 SQL이 없다. save()는 persist() 한 줄이고, findById()는 find() 한 줄이다. find()는 엔티티가 없으면 null을 돌려주므로 Optional.ofNullable로 감쌌다. 가장 눈에 띄는 것은 update()다. 엔티티를 찾아 값을 바꿀 뿐, 저장하라는 호출이 없다. 이 코드가 동작하는 이유는 바로 다음 절에서 추적한다.

    findAll()에 처음으로 쿼리 문자열이 나온다. 이것은 SQL이 아니라 JPQL(Jakarta Persistence Query Language)이다. Book은 테이블 이름이 아니라 엔티티 이름이고, b.title은 컬럼 book_title이 아니라 엔티티의 필드 title이다. JPQL은 엔티티 객체를 대상으로 질의하고, 구현체가 매핑 정보로 이를 테이블과 컬럼을 쓰는 SQL로 번역한다. :keyword와 :maxPrice는 이름 있는 파라미터이고, 결국 JDBC의 ? 바인딩이 되므로 SQL 인젝션에 안전하다.

    검색 조건에 따라 JPQL 문자열을 이어 붙이는 부분은 SQL 매퍼의 동적 SQL과 같은 고민을 그대로 갖고 있다. 조건이 늘면 문자열 조립과 파라미터 바인딩이 두 군데로 갈라져 서로 맞춰야 하고, 오타는 실행해야 드러난다. JPA 자체는 이 문제를 깔끔하게 풀지 못한다. 문자열 대신 자바 코드로 쿼리를 조립하는 Querydsl이 06회의 주제다.

    클래스에 붙은 @Transactional도 눈여겨보자. 보통 트랜잭션 경계는 서비스 계층이 정한다. 여기서는 리포지토리를 직접 호출하는 테스트에서도 변경이 반영되도록 리포지토리에 붙였다. JPA에서 데이터를 바꾸는 작업은 트랜잭션 안에서 해야 한다. 트랜잭션 없이 persist()를 부르면 어떻게 되는지는 공유 EntityManager를 다루는 절에서 소스로 확인한다. 테스트에서 이 트랜잭션을 롤백해 데이터를 격리하는 방법은 02회에서 다뤘다.

    JPA 적용 2: 리포지토리 분석, 한 번의 호출에서 일어나는 일

    이제 각 메서드를 호출했을 때 스프링, Hibernate, JDBC가 어떤 순서로 무엇을 하는지 따라가 보자. 먼저 save()다.

    3단계를 Hibernate 문서로 확인하자. Hibernate 6.4 사용자 가이드의 식별자 장은 IDENTITY 컬럼에 대해 "식별자 값을 알기 전에 엔티티 행이 물리적으로 삽입되어야 한다"고 설명하고, 그 결과 IDENTITY 생성을 쓰는 엔티티는 INSERT 문을 배치로 묶을 수 없다고 경고한다. 배치 처리 장에도 identity 식별자 생성기를 쓰면 Hibernate가 JDBC 수준의 INSERT 배치를 투명하게 끈다는 문장이 있다. 모형에서 본 그대로다. 영속성 컨텍스트는 식별자를 키로 객체를 관리하는데, IDENTITY에서는 데이터베이스가 행을 넣는 순간에야 식별자가 생긴다. 그래서 쓰기 지연의 원칙을 깨고 persist() 시점에 INSERT를 보낸다. 생성된 키 값은 드라이버와 데이터베이스가 지원하는 방법(JDBC의 getGeneratedKeys() 등)으로 받아 온다.

    이 사실은 실무 판단으로 이어진다. 도서 10만 건을 한 트랜잭션에서 persist()하면 IDENTITY에서는 INSERT 10만 번이 하나씩 데이터베이스를 왕복한다. hibernate.jdbc.batch_size를 설정해도 INSERT는 묶이지 않는다. 데이터베이스가 시퀀스를 지원하면 SEQUENCE 전략으로 키 값을 미리 받아 두고 INSERT를 플러시 때 모아 보낼 수 있다. Hibernate 사용자 가이드가 시퀀스를 지원하지 않는 데이터베이스에서만 IDENTITY를 쓰라고 권하는 이유다. 반대로 IDENTITY의 즉시 INSERT는 "persist() 직후 바로 ID를 쓸 수 있다"는 편리함이기도 하다. save()가 돌려준 객체의 getId()가 커밋 전에도 값을 갖는 것이 그 결과다.

    다음은 update()다. 스프링이 트랜잭션과 EntityManager를 준비하는 부분은 같으니, 영속성 컨텍스트 안에서 일어나는 일에 집중하자.

    update(1L, new BookChange("JPA 입문", 27000, 8))

    find()는 대응표에 id 1이 없으므로 SELECT를 보내고, 결과로 엔티티를 만들면서 스냅샷을 함께 저장한다. change()는 순수한 자바 메서드 호출이다. 필드 세 개를 바꿀 뿐 Hibernate는 이 호출을 알지 못한다. 메서드가 반환되면 트랜잭션 프록시가 커밋을 요청하고, Hibernate는 커밋 전에 플러시하면서 엔티티와 스냅샷을 비교한다. 다르므로 UPDATE를 만들어 보낸다. 그다음 JDBC 커밋이 실행된다. "값만 바꿨는데 저장된다"는 현상의 정체는 커밋 직전의 비교다.

    UPDATE 문의 모양도 알아 두자. Hibernate의 @DynamicUpdate Javadoc은 이 애너테이션을 붙이면 UPDATE 문이 동적으로 만들어지고 실제로 바뀌는 컬럼만 포함한다고 설명하며, 실행 중에 SQL을 만드는 비용이 따른다고 덧붙인다. 붙이지 않은 기본 상태에서는 미리 만들어 둔 고정된 UPDATE 문을 쓰고, 그 문장은 엔티티의 컬럼을 모두 SET에 넣는다. 가격 하나만 바꿔도 제목과 재고까지 같은 값으로 다시 쓴다는 뜻이다. 문장이 하나로 고정되어 있으면 JDBC 문장 캐시와 배치에 유리하다. 컬럼이 아주 많은 테이블에서 일부만 자주 바뀐다면 @DynamicUpdate를 검토할 수 있다.

    findById()는 em.find()로 대응표를 먼저 본다. 이 리포지토리는 메서드마다 트랜잭션이 새로 시작되고 끝나므로 영속성 컨텍스트도 메서드마다 새로 만들어진다. 따라서 리포지토리를 직접 호출하면 1차 캐시가 적중할 기회는 거의 없다. 서비스 계층에 트랜잭션을 두고 그 안에서 같은 엔티티를 여러 번 조회할 때 1차 캐시가 의미를 갖는다. 1차 캐시는 애플리케이션 전체가 공유하는 캐시가 아니라 트랜잭션 하나짜리 작업 공간이다.

    findAll()의 JPQL은 다르게 동작한다. find()는 식별자 하나로 대응표를 찾을 수 있지만, "제목에 키워드가 들어간 도서"는 대응표만 보고 답할 수 없다. 그래서 JPQL 조회는 항상 SQL로 번역되어 데이터베이스에 간다. 그 전에 AUTO 플러시 규칙이 적용된다. 같은 트랜잭션에서 앞서 바꾼 엔티티가 있고 그 변경이 쿼리 결과에 영향을 줄 수 있으면 UPDATE가 먼저 나간다. 결과 행을 객체로 만들 때 대응표에 이미 같은 식별자의 객체가 있으면 새로 만들지 않고 그 객체를 돌려준다. 모형의 [4]에서 본 그대로다. JPQL은 1차 캐시를 건너뛰고 데이터베이스에 가지만, 돌려받는 객체의 동일성은 여전히 영속성 컨텍스트가 보장한다.

    JPQL이 실제로 어떤 SQL로 바뀌었는지는 org.hibernate.SQL 로그로 확인한다. 별칭이나 컬럼 순서 같은 생성 SQL의 세부 형식은 Hibernate 버전에 따라 다르므로, 로그를 볼 때는 문장의 종류와 순서, WHERE 조건에 집중하자.
    한 번의 save 호출에서 트랜잭션 프록시가 EntityManager를 만들어 스레드에 묶고, 리포지토리의 공유 프록시가 그것을 찾아 위임하며, 커밋 때 플러시와 JDBC 커밋이 일어나는 순서를 보여 준다. 세로 생명선 6개의 시퀀스 다이어그램. 왼쪽부터 "호출자", "트랜잭션 프록시", "JpaTransactionManager", "리포지토리", "공유 EntityManager 프록시", "실제 EntityManager". 오른쪽 끝에 원통 "DB". 화살표 순서: 호출자 → 트랜잭션 프록시 "save()". 트랜잭션 프록시 → JpaTransactionManager "begin". JpaTransactionManager → 실제 EntityManager 점선 "생성 후 스레드에 묶음". 트랜잭션 프록시 → 리포지토리 "save()". 리포지토리 → 공유 EntityManager 프록시 "persist()". 공유 EntityManager 프록시 → 실제 EntityManager "스레드에서 찾아 위임". 실제 EntityManager → DB "INSERT". 트랜잭션 프록시 → JpaTransactionManager "commit". 실제 EntityManager → DB "flush 후 COMMIT". 시간 흐름은 위에서 아래. 평면 UML 스타일, 흰 배경, 파란 화살표, 라벨은 화살표 위에. 리포지토리가 쥐고 있는 것은 공유 프록시이고, 실제 영속성 컨텍스트는 트랜잭션이 시작될 때 만들어져 스레드에 묶인다.

    한 층 아래: 싱글톤에 주입된 EntityManager의 정체

    앞의 흐름에는 의문이 하나 있다. JpaBookRepository는 싱글톤 빈이고, 생성자에서 받은 EntityManager 하나를 필드에 보관한다. 여러 요청 스레드가 동시에 이 리포지토리를 쓴다. 그런데 Spring Framework 레퍼런스는 EntityManagerFactory 인스턴스는 스레드 안전하지만 EntityManager 인스턴스는 그렇지 않다고 분명히 말한다. 영속성 컨텍스트의 대응표는 평범한 맵이고 동기화되어 있지 않다. 스레드 둘이 같은 영속성 컨텍스트를 쓰면 대응표와 스냅샷이 엉킨다. 그러면 필드에 든 이 객체는 무엇일까.

    답은 같은 레퍼런스에 있다. 주입되는 것은 "공유 EntityManager"로, 실제 트랜잭션용 EntityManager를 대신하는 공유되고 스레드 안전한 프록시이며, 모든 호출을 현재 트랜잭션의 EntityManager로 위임한다. 이 프록시를 만드는 클래스가 SharedEntityManagerCreator다. Spring Framework 6.1 소스에서 프록시의 invoke()는 먼저 EntityManagerFactoryUtils.doGetTransactionalEntityManager()로 현재 스레드에 묶인 EntityManager를 찾는다. 스프링 DB 1편 04회에서 본 트랜잭션 동기화 저장소(TransactionSynchronizationManager)가 커넥션 대신 EntityManager를 들고 있는 셈이다. 스레드마다 다른 EntityManager가 묶여 있으므로, 같은 프록시를 여러 스레드가 써도 각자 자기 영속성 컨텍스트로 간다.

    스레드에 묶인 EntityManager가 없을 때, 곧 트랜잭션 밖에서 호출했을 때의 동작이 중요하다. 소스는 joinTransaction, flush, persist, merge, remove, refresh를 "트랜잭션이 필요한 메서드" 집합으로 정해 두고, 이 메서드들은 대상이 없으면 곧바로 TransactionRequiredException을 던진다. 메시지는 다음과 같이 조립된다.

    No EntityManager with actual transaction available for current thread - cannot reliably process 'persist' call

    나머지 메서드, 예를 들어 find()나 createQuery()는 예외를 던지지 않는다. 그 호출만을 위한 임시 EntityManager를 새로 만들어 실행하고 닫는다. 결과가 Query이면 쿼리가 실행될 때까지 EntityManager를 열어 두었다가 닫는다. 여기에 함정이 있다. 트랜잭션 없이 update()와 같은 코드를 실행하면, find()는 임시 영속성 컨텍스트에서 엔티티를 읽어 오고 그 컨텍스트는 바로 닫힌다. 돌려받은 엔티티는 이미 준영속 상태다. 이어서 change()로 값을 바꿔도 비교할 스냅샷도, 플러시할 컨텍스트도 없다. 예외도 SQL도 없이 변경이 사라진다. persist()는 크게 실패하는데 변경 감지는 조용히 실패하는 이유가 이 비대칭이다.

    마지막으로 생성자 주입이 어떻게 가능한지 보자. 전통적인 방법은 필드에 @PersistenceContext를 붙이는 것이다. 이 애너테이션은 스프링 컨테이너가 처리해 공유 EntityManager 프록시를 넣어 준다. 그런데 위 코드는 @PersistenceContext 없이 생성자로 받았다. 이것을 가능하게 하는 것은 Spring Data JPA다. Spring Data JPA 3.3의 EntityManagerBeanDefinitionRegistrarPostProcessor는 Javadoc에서 모든 EntityManagerFactory 빈 정의마다 SharedEntityManagerCreator 빈을 등록하며, 목적이 EntityManager를 생성자 인자로 자동 주입할 수 있게 하는 것이라고 밝힌다. 소스를 보면 jpaSharedEM_AWC_ 뒤에 팩토리 빈 이름을 붙인 이름으로, SharedEntityManagerCreator.createSharedEntityManager를 팩토리 메서드로 쓰는 빈 정의를 만든다. 결국 두 방법 모두 같은 종류의 공유 프록시를 받는다. 스타터에 Spring Data JPA가 들어 있다는 앞 절의 사실이 여기서 쓰인다.

    JPA 적용 3: 예외 변환

    JPA의 예외는 런타임 예외이므로 시그니처 문제는 없다고 했다. 남은 문제는 타입이다. 서비스가 "해당 조건의 결과가 없음"을 처리하려고 jakarta.persistence.NoResultException을 잡으면 서비스는 JPA에 의존한다. 같은 상황에서 JdbcTemplate 구현은 스프링의 EmptyResultDataAccessException을 던진다. 저장소 구현을 바꾸면 서비스의 catch 절도 바꿔야 한다. 스프링 DB 1편 06회에서 세운 원칙, 곧 데이터 접근 예외는 기술에 독립적인 DataAccessException 계층으로 통일한다는 원칙이 JPA에서도 지켜지려면 누군가 변환해야 한다.

    JdbcTemplate은 템플릿 안에서 SQLException을 직접 잡아 변환했다. JPA 리포지토리는 EntityManager를 직접 부르므로 그런 템플릿이 없다. 스프링은 대신 프록시로 해결한다. 리포지토리 클래스에 @Repository를 붙이면 그 빈 앞에 예외 변환 프록시가 서고, 리포지토리 메서드 밖으로 나가는 런타임 예외를 가로채 변환한다. 경로를 하나씩 따라가 보자.

    1. 후처리기 등록: Spring Boot의 PersistenceExceptionTranslationAutoConfiguration이 PersistenceExceptionTranslationPostProcessor를 빈으로 등록한다. 조건은 spring.dao.exceptiontranslation.enabled가 false가 아닐 것(속성 부록의 기본값 true)이다. 이때 spring.aop.proxy-target-class 값을 읽어 프록시 방식을 정하는데, 속성이 없으면 true로 보아 클래스 기반(CGLIB) 프록시를 만든다.
    2. 어드바이저 부착: 이 후처리기의 Javadoc은 스프링의 @Repository가 붙은 빈에 영속성 예외 변환을 자동으로 적용하며, 그 방법으로 PersistenceExceptionTranslationAdvisor를 노출된 프록시에 추가한다고 설명한다. 대상 애너테이션의 기본값이 Repository.class로 정해져 있다.
    3. 변환기 수집: 어드바이저 안의 PersistenceExceptionTranslationInterceptor는 빈 팩토리에서 PersistenceExceptionTranslator를 구현한 빈을 모두 찾아 순서대로 ChainedPersistenceExceptionTranslator에 넣는다. JPA 환경에서 대표적인 변환기는 EntityManagerFactory를 만든 LocalContainerEntityManagerFactoryBean이다. 그 부모 AbstractEntityManagerFactoryBean의 선언부에 PersistenceExceptionTranslator가 들어 있다.
    4. 방언에 위임: AbstractEntityManagerFactoryBean.translateExceptionIfPossible()은 JpaDialect가 있으면 그것에, 없으면 EntityManagerFactoryUtils.convertJpaAccessExceptionIfPossible()에 맡긴다. Hibernate를 쓰면 방언은 HibernateJpaDialect다.
    5. Hibernate 예외 먼저: HibernateJpaDialect는 예외가 HibernateException이거나, 원인이 HibernateException인 PersistenceException이면 Hibernate 전용 변환으로 보낸다. 그 밖에는 JPA 표준 예외 변환으로 넘긴다.

    두 변환 메서드가 실제로 무엇을 무엇으로 바꾸는지는 Spring Framework 6.1 소스에서 확인할 수 있다. 자주 만나는 것만 추리면 다음과 같다.

    표에서 두 가지를 눈여겨보자. 첫째, IllegalArgumentException과 IllegalStateException도 변환 대상이다. 소스의 주석은 JPA 명세상 구현체가 PersistenceException 외에 이 두 예외도 던질 수 있기 때문이라고 설명한다. 예를 들어 em.find(Book.class, null)처럼 잘못된 인자를 넘기면 구현체가 IllegalArgumentException을 던지고, 프록시를 지나며 InvalidDataAccessApiUsageException이 된다. 둘째, 어디에도 해당하지 않는 예외는 null을 돌려받아 변환하지 않는다. 소스의 주석은 이런 예외가 구현체가 아니라 사용자 코드에서 생긴 것이므로 변환하지 않는다고 설명한다.

    인터셉터에는 규칙이 하나 더 있다. Spring Framework 6.1의 PersistenceExceptionTranslationInterceptor.invoke()는 메서드를 실행하다 RuntimeException이 나면, 그 예외 타입이 메서드의 throws 절에 선언되어 있는지 먼저 본다. 선언되어 있으면 변환하지 않고 그대로 던진다(alwaysTranslate를 켜지 않은 기본 상태). 메서드 작성자가 "이 예외를 그대로 받겠다"고 시그니처로 약속했다면 그 약속을 존중하는 것이다. 그렇지 않으면 수집한 변환기 체인에 맡기고, 변환 결과가 없으면 원래 예외를 던진다.

    이 규칙을 JDK의 동적 프록시만으로 흉내 내 확인해 보자. JPA와 스프링의 예외 클래스를 흉내 낸 작은 클래스를 만들고, 같은 예외를 던지는 메서드 두 개 중 하나만 throws에 예외를 선언했다. 스프링 부트는 기본으로 CGLIB 프록시를 쓰지만, "메서드 호출을 가로채 예외를 바꾼다"는 원리는 같다.

    import java.lang.reflect.*;

public class TranslateDemo {
    // JPA 쪽 예외를 흉내 낸다
    static class PersistenceException extends RuntimeException {
        PersistenceException(String m) { super(m); }
    }
    static class NoResultException extends PersistenceException {
        NoResultException(String m) { super(m); }
    }
    // 스프링 쪽 예외를 흉내 낸다
    static class DataAccessException extends RuntimeException {
        DataAccessException(String m, Throwable cause) { super(m, cause); }
    }
    static class EmptyResultDataAccessException extends DataAccessException {
        EmptyResultDataAccessException(String m, Throwable cause) { super(m, cause); }
    }

    interface BookRepository {
        String findTitle(long id);
        String findTitleRaw(long id) throws NoResultException;
    }

    static class JpaBookRepository implements BookRepository {
        public String findTitle(long id) { throw new NoResultException("no row: id=" + id); }
        public String findTitleRaw(long id) throws NoResultException { throw new NoResultException("no row: id=" + id); }
    }

    static DataAccessException translate(RuntimeException ex) {
        if (ex instanceof NoResultException) return new EmptyResultDataAccessException(ex.getMessage(), ex);
        if (ex instanceof PersistenceException) return new DataAccessException(ex.getMessage(), ex);
        return null;                                 // 모르는 예외는 바꾸지 않는다
    }

    static boolean declares(Method m, Class exType) {
        for (Class declared : m.getExceptionTypes()) {
            if (declared.isAssignableFrom(exType)) return true;
        }
        return false;
    }

    public static void main(String[] args) {
        BookRepository target = new JpaBookRepository();
        BookRepository proxy = (BookRepository) Proxy.newProxyInstance(
                BookRepository.class.getClassLoader(),
                new Class[]{BookRepository.class},
                (p, method, a) -> {
                    try {
                        return method.invoke(target, a);
                    } catch (InvocationTargetException ite) {
                        Throwable ex = ite.getTargetException();
                        if (ex instanceof RuntimeException re && !declares(method, re.getClass())) {
                            DataAccessException dae = translate(re);
                            if (dae != null) throw dae;
                        }
                        throw ex;
                    }
                });

        try {
            proxy.findTitle(1);
        } catch (RuntimeException e) {
            System.out.println("findTitle    -> " + e.getClass().getSimpleName()
                    + " (cause: " + e.getCause().getClass().getSimpleName() + ")");
        }
        try {
            proxy.findTitleRaw(1);
        } catch (RuntimeException e) {
            System.out.println("findTitleRaw -> " + e.getClass().getSimpleName()
                    + " (cause: " + e.getCause() + ")");
        }
    }
}
    findTitle    -> EmptyResultDataAccessException (cause: NoResultException)
findTitleRaw -> NoResultException (cause: null)

    첫 호출은 선언되지 않은 NoResultException이 프록시에서 EmptyResultDataAccessException으로 바뀌었고, 원래 예외는 원인(cause)으로 남았다. 스프링의 변환 결과도 원인을 보존하므로 로그에서 구현체가 던진 원래 예외와 SQL 정보를 따라갈 수 있다. 두 번째 호출은 throws NoResultException이 선언되어 있어 그대로 통과했다. 리플렉션으로 호출한 메서드가 던진 예외는 InvocationTargetException에 싸여 오므로, getTargetException()으로 꺼낸 뒤 판단한다는 점도 실제 프록시와 같다.

    이 경로 밖에서 생기는 예외도 있다. 커밋 시점의 플러시가 대표적이다. update()에서 변경한 값이 유일 제약을 어기면, 그 위반은 리포지토리 메서드 안이 아니라 메서드가 반환된 뒤 커밋 직전 플러시의 UPDATE에서 드러난다. 이때는 JpaTransactionManager가 변환을 맡는다. Spring Framework 6.1의 doCommit()은 커밋 중 RollbackException이 나면 그 원인을 JpaDialect로 변환해 던지고, 변환되지 않으면 TransactionSystemException을 던진다. 그 밖의 RuntimeException은 플러시 실패로 보고 DataAccessUtils.translateIfNecessary()로 변환한다. 서비스는 어느 쪽이든 DataAccessException 계층으로 받게 된다.

    예외는 트랜잭션에도 흔적을 남긴다. Jakarta Persistence 3.1 명세 3.11절은 PersistenceException의 인스턴스가 던져지면, 활성 트랜잭션이 있고 영속성 컨텍스트가 그 트랜잭션에 참여한 경우 현재 트랜잭션을 롤백 전용으로 표시한다고 정한다. 예외는 넷이다. NoResultException, NonUniqueResultException, QueryTimeoutException, LockTimeoutException은 트랜잭션을 롤백 표시하지 않는다. 그러니 저장 중 생긴 JPA 예외를 서비스에서 잡아 "복구"해도, 그 트랜잭션은 이미 커밋할 수 없는 상태일 수 있다. 롤백 전용 표시가 스프링 트랜잭션 전파와 만나 UnexpectedRollbackException으로 이어지는 과정은 07~09회에서 자세히 다룬다.

    리포지토리 메서드에서 던져진 예외가 CGLIB 프록시의 인터셉터에서 throws 선언 검사, 변환기 체인, HibernateJpaDialect, EntityManagerFactoryUtils를 거쳐 변환되거나 그대로 나가는 분기를 보여 준다. 왼쪽에서 오른쪽으로 흐르는 순서도. 시작 상자 "리포지토리 메서드에서 RuntimeException". 화살표가 마름모 "throws에 선언됨?"으로 간다. "예" 화살표는 위쪽 회색 상자 "그대로 던짐"으로. "아니오" 화살표는 파란 상자 "ChainedPersistenceExceptionTranslator"로, 다시 파란 상자 "LocalContainerEntityManagerFactoryBean"으로, 다시 마름모 "Hibernate 예외?"로. "예" 화살표는 상자 "HibernateJpaDialect 변환"으로, "아니오" 화살표는 상자 "EntityManagerFactoryUtils 변환"으로. 두 상자에서 나온 화살표가 마름모 "결과 있음?"으로 모인다. "예"는 초록 상자 "DataAccessException 하위 예외", "아니오"는 회색 상자 "원래 예외". 전체를 감싸는 점선 테두리에 라벨 "@Repository 프록시". 평면 순서도 스타일, 흰 배경. 예외 변환은 @Repository 빈 앞의 프록시에서 일어난다. throws에 선언된 예외와, 변환기가 모르는 예외는 그대로 나간다.

    흔한 오해와 함정

    "JPA를 쓰면 SQL을 몰라도 된다." JPA는 SQL을 대신 쓰지만, 어떤 SQL이 몇 번 나가는지는 여전히 개발자의 책임이다. 이 회차에서만도 IDENTITY의 즉시 INSERT, 모든 컬럼을 쓰는 기본 UPDATE, JPQL 전의 자동 플러시처럼 SQL을 알아야 판단할 수 있는 동작이 여럿 나왔다. 생성된 SQL을 로그로 읽을 수 없으면 성능 문제를 찾을 수 없다. JPA를 잘 쓰는 사람은 SQL을 잘 아는 사람이다.

    "persist()를 부르면 INSERT가 나간다" 또는 "persist()는 INSERT를 미룬다." 둘 다 반만 맞다. 명세는 커밋 시점이나 그 전, 또는 플러시 때 들어간다고만 정한다. 쓰기 지연이 원칙이지만 IDENTITY 전략에서는 식별자를 얻으려고 즉시 INSERT한다. 키 생성 전략을 바꾸면 같은 코드의 SQL 순서가 달라진다. "이 시점에 행이 이미 들어갔는가"가 중요한 코드라면 전략을 함께 확인해야 한다.

    "세터를 부르면 UPDATE가 나간다." 세터는 평범한 자바 메서드다. UPDATE는 플러시 때 스냅샷과 비교해서 나간다. 그래서 값을 여러 번 바꿔도 플러시 전에는 UPDATE가 한 번이고, 원래 값으로 되돌리면 스냅샷과 같아져 UPDATE가 나가지 않는다. 반대로 준영속 객체의 값을 바꾸면 아무 일도 일어나지 않는다. 공유 EntityManager를 트랜잭션 없이 쓸 때 find()가 돌려주는 객체가 바로 그 준영속 객체다.

    "영속성 컨텍스트는 애플리케이션 캐시다." 1차 캐시는 트랜잭션 하나의 작업 공간이다. 트랜잭션이 끝나면 사라지고, 다른 요청과 공유되지 않는다. 요청 A가 읽은 도서를 요청 B가 SQL 없이 꺼내 쓰는 일은 없다. 여러 트랜잭션에 걸친 캐시는 Hibernate의 2차 캐시라는 별도 기능이고, 이 회차의 범위가 아니다.

    "JPQL로 조회해도 1차 캐시에 있으면 SQL이 안 나간다." 식별자 하나로 찾는 find()만 대응표로 답할 수 있다. JPQL은 조건으로 행을 고르는 질의이므로 항상 데이터베이스에 간다. 다만 돌아온 행 중 대응표에 이미 있는 식별자는 기존 객체로 바뀌므로, 같은 트랜잭션에서 미리 바꿔 둔 값이 데이터베이스 값으로 덮이지 않는다. 그 대신 AUTO 플러시가 먼저 일어나 변경이 데이터베이스에 반영된다.

    "예외 변환은 JPA가 해 준다." 변환은 스프링의 프록시가 한다. 리포지토리에 @Repository가 없으면 후처리기가 그 빈을 대상으로 보지 않으므로 서비스는 JPA 예외를 그대로 받는다. @Component를 붙여도 빈으로 등록되기는 하지만 변환은 없다. 또 리포지토리 안에서 this.findById()처럼 자기 메서드를 부르면 프록시를 거치지 않는다. 변환은 프록시 경계를 넘을 때 한 번 일어난다.

    "내가 던진 예외는 그대로 나간다." 대부분은 그렇다. 변환기가 모르는 예외는 null을 받아 원래대로 나간다. 그러나 IllegalArgumentException과 IllegalStateException은 예외다. @Repository 빈 안에서 직접 throw new IllegalArgumentException("가격은 0 이상")을 해도, 변환기는 그것이 구현체에서 왔는지 사용자 코드에서 왔는지 구분하지 못하므로 InvalidDataAccessApiUsageException으로 바꾼다. 서비스에서 IllegalArgumentException을 잡으려던 코드가 동작하지 않는 이유가 이것이다. 리포지토리에서 검증 실패를 알리려면 이 두 예외 대신 의미가 분명한 다른 예외를 쓰거나, 검증을 서비스나 도메인으로 옮기는 편이 낫다.

    "엔티티의 기본 생성자는 public이어야 한다" 또는 "private이어도 된다." 명세는 public 또는 protected를 요구한다. 리플렉션만 생각하면 private도 호출할 수 있지만, 프록시가 하위 클래스로 만들어지려면 부모 생성자를 부를 수 있어야 한다. 같은 이유로 엔티티 클래스와 그 메서드에 final을 붙이지 않는다. 코틀린처럼 클래스가 기본으로 final인 언어에서 엔티티를 쓸 때 추가 설정이 필요한 것도 이 규칙 때문이다.

    정리: SQL 매퍼에서 ORM으로 옮겨 오며 바뀐 것

    이 회차의 출발점은 SQL 중심 개발의 두 문제였다. 객체를 SQL로 옮겨 적는 반복과 그 때문에 엔티티를 믿을 수 없는 문제, 그리고 그 뿌리에 있는 객체와 테이블의 패러다임 불일치다. JPA는 매핑 정보로 SQL을 만들어 반복을 없애고, 영속성 컨텍스트라는 식별자별 대응표로 비교 불일치를 풀며, 프록시를 통한 지연 로딩으로 객체 그래프 탐색 문제에 답한다.

    그 대가로 새로운 규칙을 알아야 한다. SQL이 나가는 시점은 코드의 줄이 아니라 플러시가 정한다. IDENTITY 전략은 그 원칙의 예외로 persist() 때 INSERT한다. 변경 감지는 관리 상태의 엔티티에만, 트랜잭션 안에서만 동작한다. 싱글톤에 주입된 EntityManager는 스레드에 묶인 실제 영속성 컨텍스트로 가는 공유 프록시이고, 트랜잭션이 없으면 변경 메서드는 예외를 던지고 조회는 임시 컨텍스트에서 실행된다. 예외는 @Repository 프록시와 트랜잭션 매니저가 DataAccessException 계층으로 바꾼다.

    다음 회차들과의 연결도 정리해 두자. 05회의 스프링 데이터 JPA는 이 회차의 JpaBookRepository 같은 구현 클래스를 인터페이스 선언만으로 만들어 준다. 그 아래에서는 이 회차의 EntityManager, 영속성 컨텍스트, 예외 변환이 그대로 동작한다. 06회의 Querydsl은 findAll()의 문자열 JPQL 조립을 자바 코드로 바꾼다. 07~09회의 트랜잭션 회차에서는 이 회차에서 본 트랜잭션 프록시, 커밋 시점의 플러시, JPA 예외가 남기는 롤백 전용 표시가 전파 규칙과 만나 어떤 결과를 내는지 다룬다.
    패러다임 불일치
    객체는 상속·참조·그래프로, 테이블은 분리된 테이블·외래 키·조인으로 데이터를 표현한다. 상속, 연관관계, 객체 그래프 탐색, 비교의 네 가지에서 둘이 맞지 않고, SQL 매퍼에서는 그 변환을 개발자가 손으로 한다.
    JPA와 Hibernate
    JPA(Jakarta Persistence)는 jakarta.persistence 패키지의 API와 규칙을 정한 표준 명세이고, Hibernate는 그 구현체다. JPA는 JDBC를 대체하지 않고 그 위에서 SQL을 만들어 실행한다.
    영속성 컨텍스트
    식별자별로 엔티티 인스턴스를 하나씩 보관하는 작업 공간이다. 1차 캐시와 동일성 보장은 이 대응표에서 나오며, 스프링에서는 보통 트랜잭션 하나와 수명이 같다.
    플러시와 변경 감지
    플러시는 영속성 컨텍스트의 변경을 SQL로 보내는 일로, 커밋 때와 AUTO 모드의 쿼리 실행 전, flush() 호출 때 일어난다. Hibernate는 기본으로 플러시 때 엔티티를 스냅샷과 비교해 UPDATE를 만든다.
    IDENTITY 전략
    데이터베이스가 행을 넣어야 식별자가 생기므로 Hibernate는 persist() 시점에 INSERT를 실행한다. 이 엔티티의 INSERT는 JDBC 배치로 묶이지 않는다.
    엔티티 클래스 규칙
    public 또는 protected 기본 생성자가 있어야 하고, 클래스·메서드·영속 필드가 final이면 안 된다. 조회 결과로 빈 객체를 만들고, 하위 클래스 프록시를 만들기 위해서다.
    공유 EntityManager
    싱글톤에 주입되는 EntityManager는 SharedEntityManagerCreator가 만든 스레드 안전한 프록시로, 호출마다 현재 스레드의 트랜잭션에 묶인 실제 EntityManager로 위임한다. 트랜잭션이 없으면 persist 같은 변경 메서드는 TransactionRequiredException을 던진다.
    JPA 예외 변환
    @Repository 빈 앞의 프록시가 메서드 밖으로 나가는 런타임 예외를 HibernateJpaDialect와 EntityManagerFactoryUtils로 DataAccessException 하위 예외로 바꾼다. throws에 선언된 예외와 변환기가 모르는 예외는 그대로 나간다.

    대량 등록 작업이 예상보다 훨씬 느리다는 보고가 들어오면 먼저 키 생성 전략을 본다. IDENTITY라면 hibernate.jdbc.batch_size를 설정해도 INSERT는 한 건씩 데이터베이스를 왕복한다. 데이터베이스가 시퀀스를 지원하면 SEQUENCE로 바꾸는 것이 근본적인 해결이고, MySQL처럼 시퀀스가 없으면 대량 등록 경로만 JdbcTemplate의 배치 업데이트로 따로 만드는 방법이 현실적이다. 같은 트랜잭션에서 JdbcTemplate과 JPA를 섞어 쓸 수 있다는 사실(JpaTransactionManager가 같은 커넥션을 노출한다)이 이 선택을 가능하게 한다. 다만 JdbcTemplate으로 바꾼 행은 영속성 컨텍스트가 모르므로, 같은 트랜잭션에서 그 행을 엔티티로 이미 들고 있다면 오래된 값을 보게 된다는 점을 함께 판단해야 한다.

    "수정 API가 200을 돌려주는데 값이 안 바뀐다"는 장애는 대개 트랜잭션 경계 문제다. 변경 감지는 관리 상태의 엔티티에서만, 커밋 전 플러시에서만 동작한다. 트랜잭션 없이 공유 EntityManager로 조회한 엔티티는 이미 준영속이고, 값을 바꿔도 예외조차 나지 않는다. 같은 클래스 안에서 @Transactional 메서드를 내부 호출해 프록시를 건너뛴 경우도 증상이 같다(이 문제는 07회에서 다룬다). 이런 보고를 받으면 SQL 로그에서 UPDATE가 있었는지, 그 메서드가 정말 트랜잭션 안에서 실행됐는지부터 확인한다.

    예외 처리 설계에서는 서비스가 무엇을 잡을지 결정할 때 변환 규칙을 기준으로 삼는다. 서비스는 jakarta.persistence나 org.hibernate 예외가 아니라 DataAccessException 계층을 잡아야 저장소 기술을 바꿔도 코드가 버틴다. 이 원칙은 리포지토리에 @Repository가 있고, 메서드 throws에 JPA 예외를 선언하지 않았을 때만 성립한다. 또 유일 제약 위반처럼 커밋 때 드러나는 예외는 리포지토리 호출 줄이 아니라 트랜잭션이 끝나는 지점에서 던져진다. 중복 가입을 잡아 다른 이름을 제안하는 식의 복구 로직을 짜려면, 리포지토리 호출 직후 flush()로 제약 위반을 그 자리에서 드러내거나, 복구 단위를 별도 트랜잭션으로 나누는 설계가 필요하다. 그리고 JPA 예외가 이미 트랜잭션을 롤백 전용으로 표시했을 수 있다는 점을 잊지 않는다.

  • @Transactional이 없는 서비스 메서드에서 JpaBookRepository와 같은 코드를 쓰되 리포지토리에도 @Transactional을 붙이지 않았다. save()를 부르면 무슨 일이 생기고, 예외가 서비스에 도착할 때의 타입은 무엇인가? 같은 조건에서 update()를 부르면 무슨 일이 생기는가?

    1번. (1)에서 IDENTITY이므로 INSERT가 즉시 나간다(가격 10000). (2)는 SQL이 없다. (3)은 대응표에 같은 id가 있으므로 SQL 없이 같은 객체를 돌려준다. (4)는 JPQL이고 AUTO 플러시 대상이므로, 먼저 플러시가 일어나 스냅샷(10000)과 현재 값(12000)이 다르다는 것이 감지되어 UPDATE가 나가고, 이어서 SELECT가 나간다. 이 SELECT의 결과 행은 대응표의 기존 객체로 바뀐다. (5)는 값이 그대로이므로 아무 일도 없다. (6)의 커밋 전 플러시에서는 (4)의 플러시가 스냅샷을 12000으로 갱신해 두었으므로 현재 값과 같아 UPDATE가 없고, COMMIT만 나간다. 순서는 INSERT → UPDATE → SELECT → COMMIT이다.

    2번. (2) 직후: 대응표 {id → 그 객체(가격 12000)}, 스냅샷 {id → 가격 10000}. 엔티티와 스냅샷이 어긋나 있지만 아직 데이터베이스는 10000이다. (4) 직후: 대응표는 같은 객체 하나(가격 12000), 스냅샷은 플러시로 갱신되어 가격 12000. SELECT 결과로 새 객체가 생기지 않았다는 점이 핵심이다. 대응표에 같은 식별자가 있으므로 기존 객체를 결과 목록에 넣는다.

    3번. save()의 em.persist()는 공유 프록시를 거치는데, 스레드에 묶인 EntityManager가 없으므로 SharedEntityManagerCreator가 "No EntityManager with actual transaction available for current thread - cannot reliably process 'persist' call" 메시지로 TransactionRequiredException을 던진다. 이 예외는 리포지토리 메서드 밖으로 나가며 @Repository 프록시를 지나고, EntityManagerFactoryUtils의 규칙에 따라 InvalidDataAccessApiUsageException으로 바뀌어 서비스에 도착한다. update()는 예외가 나지 않는다. find()는 트랜잭션이 필요한 메서드가 아니므로 임시 EntityManager에서 실행되고 그 컨텍스트는 바로 닫힌다. 돌려받은 엔티티는 준영속이므로 change()로 값을 바꿔도 비교할 스냅샷도 플러시도 없어, 변경이 조용히 사라진다.

    4번. 예외가 리포지토리 메서드 밖으로 나가면 PersistenceExceptionTranslationInterceptor가 받는다. 메서드 throws에 선언되지 않았으므로 변환기 체인으로 가고, LocalContainerEntityManagerFactoryBean → HibernateJpaDialect(Hibernate 예외가 아니므로 통과) → EntityManagerFactoryUtils.convertJpaAccessExceptionIfPossible()에 도착한다. 이 메서드는 JPA 명세상 구현체도 던질 수 있는 IllegalStateException을 InvalidDataAccessApiUsageException으로 바꾼다. 그래서 서비스에는 다른 타입이 도착한다. 해결책은 (가) 리포지토리에서 이 두 예외 대신 의미가 분명한 별도 예외(예: 직접 만든 OutOfStockException)를 던지거나, (나) 재고 검증 같은 규칙을 리포지토리가 아니라 도메인이나 서비스로 옮기는 것이다. 메서드에 throws IllegalStateException을 선언해 변환을 피하는 방법도 있지만, 저장소 인터페이스에 그런 선언을 퍼뜨리는 것은 의도가 흐려지므로 권하지 않는다.

    5번. 컴파일 실험에서 다른 패키지의 하위 클래스가 private 생성자를 super()로 부르려 하면 "Book() has private access in Book" 오류가 났고, final 클래스를 상속하면 "cannot inherit from final" 오류가 났다. 실행 중에 바이트코드로 하위 클래스를 만드는 프록시도 같은 언어·JVM 규칙을 따르므로, final 클래스는 상속 자체가 불가능하고 private 생성자는 하위 클래스 생성자에서 호출할 수 없다. 리플렉션의 setAccessible(true)로 빈 객체를 만드는 것은 가능하지만, 지연 로딩용 프록시는 만들 수 없다.

     IDENTITY 전략을 쓰는 엔티티를 트랜잭션 안에서 em.persist()한 직후, 커밋하기 전에 일어나는 일로 옳은 것은? INSERT는 쓰기 지연 저장소에만 쌓이고 커밋 때 다른 INSERT와 함께 배치로 나간다. INSERT가 곧바로 실행되고, 데이터베이스가 만든 키 값이 엔티티의 id 필드에 들어간다. id가 없으므로 엔티티는 영속성 컨텍스트에 들어가지 못하고 커밋 때 관리 상태가 된다. INSERT와 COMMIT이 함께 실행되어 다른 트랜잭션에서도 그 행이 보인다. IDENTITY에서는 행을 넣어야 식별자가 생기고, 영속성 컨텍스트는 식별자를 키로 엔티티를 관리하므로 Hibernate는 persist() 시점에 INSERT를 실행한다. 이 때문에 INSERT 배치가 꺼진다(첫 보기 오답). INSERT 후 엔티티는 바로 관리 상태가 된다(셋째 보기 오답). INSERT는 실행됐지만 커밋은 아직이므로, 격리 수준에 따라 다른 트랜잭션에서는 보이지 않는다(넷째 보기 오답). 한 트랜잭션 안에서 em.find()로 읽은 도서의 가격을 바꾼 뒤, 같은 테이블을 조회하는 JPQL을 기본 플러시 모드(AUTO)로 실행했다. 데이터베이스로 나가는 SQL의 순서로 옳은 것은? SELECT(find) → SELECT(JPQL) → 커밋 때 UPDATE SELECT(find) → SELECT(JPQL)만 나가고, JPQL 결과로 가격이 데이터베이스 값으로 되돌아간다. SELECT(find) → UPDATE → SELECT(JPQL) JPQL은 1차 캐시에서 처리되므로 SELECT(find) 한 번만 나간다. 명세는 AUTO 모드에서 트랜잭션 안의 쿼리를 실행할 때, 결과에 영향을 줄 수 있는 영속성 컨텍스트의 변경이 쿼리 처리에서 보이도록 구현체가 책임지게 한다. 그래서 JPQL 전에 플러시가 일어나 UPDATE가 먼저 나간다. JPQL은 대응표만으로 답할 수 없으므로 항상 데이터베이스에 가고(넷째 보기 오답), 결과 행은 대응표의 기존 객체로 바뀌므로 메모리의 값이 덮이지 않는다(둘째 보기 오답). @Repository가 붙은 JPA 리포지토리에 String findTitle(Long id) throws NoResultException 메서드가 있고, 안에서 getSingleResult()가 NoResultException을 던졌다. 호출한 서비스가 받는 예외는? jakarta.persistence.NoResultException 그대로 EmptyResultDataAccessException JpaSystemException UndeclaredThrowableException PersistenceExceptionTranslationInterceptor는 런타임 예외의 타입이 메서드의 throws 절에 선언되어 있으면 변환하지 않고 그대로 던진다. throws 선언이 없었다면 EntityManagerFactoryUtils가 NoResultException을 EmptyResultDataAccessException으로 바꿨을 것이다. JpaSystemException은 목록에 없는 그 밖의 PersistenceException에 쓰이고, 선언된 런타임 예외이므로 UndeclaredThrowableException으로 감쌀 이유도 없다. 싱글톤 리포지토리가 생성자로 받은 EntityManager 하나를 필드에 두고, 여러 요청 스레드가 동시에 이 리포지토리를 사용한다. 이것이 안전한 이유로 옳은 것은? EntityManager 구현이 내부적으로 모든 메서드를 synchronized로 막아 둔다. 스프링이 요청마다 리포지토리 빈을 새로 만들어 주입한다. 영속성 컨텍스트가 스레드별로 나뉜 ConcurrentHashMap이기 때문이다. 주입된 것은 공유 프록시이고, 호출마다 현재 스레드의 트랜잭션에 묶인 실제 EntityManager를 찾아 위임한다. Spring Framework 레퍼런스는 EntityManager 인스턴스가 스레드 안전하지 않다고 말한다. 주입되는 것은 SharedEntityManagerCreator가 만든 공유 프록시로, 호출마다 트랜잭션 동기화 저장소에서 현재 스레드의 EntityManager를 찾아 위임한다. 리포지토리는 싱글톤 그대로이고(둘째 보기 오답), 실제 EntityManager가 동기화되어 있어서가 아니다(첫째, 셋째 보기 오답). JPA 명세가 엔티티 클래스를 final로 선언하지 못하게 하고, 기본 생성자를 public 또는 protected로 요구하는 것과 가장 직접 관련된 구현 기법은? 리플렉션으로 private 필드에 값을 넣는 필드 접근 엔티티 클래스를 상속한 하위 클래스로 만드는 지연 로딩 프록시 스냅샷과 현재 상태를 비교하는 변경 감지 JPQL을 SQL로 번역하는 쿼리 해석기 프록시가 엔티티의 하위 클래스이려면 클래스가 final이 아니어야 하고, 하위 클래스 생성자가 부모의 기본 생성자를 호출할 수 있어야 하며, 메서드를 재정의할 수 있어야 한다. 실험에서 private 생성자와 final 클래스는 하위 클래스 컴파일 단계에서 거부됐다. 필드 접근은 setAccessible로 private 필드도 다룰 수 있으므로 이 제약의 이유가 아니고, 변경 감지와 JPQL 번역은 상속과 무관하다.
    ORM(Object-Relational Mapping)
    객체와 관계형 데이터베이스 테이블의 대응을 선언해 두면, 그 정보로 SQL을 만들고 결과를 객체로 조립해 주는 기술.
    Jakarta Persistence(JPA)
    자바의 ORM 표준 명세. jakarta.persistence 패키지의 인터페이스·애너테이션과 그 동작 규칙을 정하며, Hibernate 같은 구현체가 실제 동작을 제공한다.
    엔티티(entity)
    @Entity가 붙어 JPA가 관리하는 클래스의 인스턴스. 식별자(@Id)로 테이블의 행 하나에 대응한다.
    영속성 컨텍스트(persistence context)
    식별자마다 유일한 엔티티 인스턴스를 보관하는 집합. EntityManager로 접근하며 1차 캐시, 변경 감지, 쓰기 지연의 근거가 된다.
    플러시(flush)
    영속성 컨텍스트에 쌓인 변경을 SQL로 데이터베이스에 보내는 일. 커밋 때, AUTO 모드의 쿼리 실행 전, flush() 호출 때 일어나며 컨텍스트를 비우지는 않는다.
    변경 감지(dirty checking)
    관리 상태 엔티티의 현재 상태를 들어올 때의 스냅샷과 비교해 바뀐 엔티티에 대해 UPDATE를 만드는 기능.
    준영속(detached)
    식별자는 있지만 현재 영속성 컨텍스트에 속하지 않은 엔티티 상태. 값을 바꿔도 데이터베이스에 반영되지 않는다.
    JPQL(Jakarta Persistence Query Language)
    테이블과 컬럼이 아니라 엔티티와 필드를 대상으로 쓰는 질의 언어. 구현체가 매핑 정보를 이용해 SQL로 번역한다.
    공유 EntityManager(shared EntityManager)
    스프링이 주입하는 스레드 안전한 EntityManager 프록시. 호출마다 현재 트랜잭션에 묶인 실제 EntityManager로 위임한다.
    PersistenceExceptionTranslationPostProcessor
    @Repository 빈에 예외 변환 어드바이저를 붙이는 빈 후처리기. 등록된 PersistenceExceptionTranslator들로 런타임 예외를 DataAccessException 하위 예외로 바꾼다.
