    이 회차의 질문: 주문은 남기고 감사 기록만 버릴 수 있는가

    주문을 저장하면서 같은 요청 안에서 감사 기록(audit log)도 한 줄 남겨야 하는 서비스를 생각해 보자. 감사 기록은 "누가 언제 무엇을 했는가"를 남기는 부가 데이터다. 업무 규칙은 이렇게 정해져 있다. 주문과 감사 기록이 모두 성공하면 둘 다 남는다. 주문이 실패하면 둘 다 남지 않는다. 그런데 감사 기록만 실패했다면, 그것 때문에 고객의 주문까지 무르지는 않는다. 주문은 커밋하고 감사 기록만 버린다. 겉으로는 단순한 요구지만, 이 요구를 정확히 구현하려면 트랜잭션 경계를 어디에 둘지, 내부 트랜잭션이 실패했을 때 바깥 트랜잭션이 어떤 상태가 되는지, 예외를 잡으면 무엇이 바뀌고 무엇이 바뀌지 않는지를 모두 알아야 한다.

    07회에서 @Transactional이 AOP 프록시로 동작하고, 런타임 예외는 롤백·체크 예외는 커밋이라는 규칙을 보았다. 08회에서는 트랜잭션 매니저가 이미 진행 중인 트랜잭션을 발견했을 때 전파 옵션에 따라 참여하거나 새로 시작한다는 것, 그리고 하나의 물리 트랜잭션(physical transaction) 위에 여러 논리 트랜잭션(logical transaction)이 겹칠 수 있다는 것을 다뤘다. 이 회차는 그 규칙들을 하나의 요구사항에 적용한다. 경계를 리포지토리에 둘 때, 서비스로 올릴 때, 둘 다 둘 때, 예외를 그대로 던질 때와 잡을 때, 그리고 감사 기록만 REQUIRES_NEW로 분리할 때를 차례로 실행하고, 각 경우에 트랜잭션 매니저가 남기는 로그와 데이터베이스에 남은 행을 대조한다.

    설명만으로 끝내지 않기 위해 모든 경우를 실제로 실행했다. 실험 환경은 JDK 21, Spring Framework 7.0.10(spring-tx, spring-jdbc, spring-context, spring-aop), H2 2.4.240 인메모리 데이터베이스, HikariCP 7.0.2다. 이 강좌의 기준 버전은 Spring Framework 6.x이므로, 본문에 인용하는 AbstractPlatformTransactionManager의 로그 문구와 기본값은 GitHub의 6.2.x 브랜치 소스와도 대조해 같다는 것을 확인했다. 트랜잭션 매니저는 JPA 대신 DataSourceTransactionManager를 썼다. 전파 규칙은 추상 클래스 AbstractPlatformTransactionManager에 있고 JPA용 JpaTransactionManager도 같은 클래스를 상속하므로 흐름은 같다. JPA에서만 달라지는 지점은 해당 단락에서 따로 짚는다.

    실험 장치: 두 저장소, 하나의 서비스, 그리고 관찰 도구

    테이블은 두 개다. 감사 기록의 message 컬럼을 일부러 20자로 좁혀 두었다. 20자를 넘는 메시지를 넣으면 데이터베이스가 INSERT를 거부한다. 실패를 코드로 흉내 내는 대신 데이터베이스가 실제로 던지는 오류를 쓰기 위해서다. 이 오류는 JdbcTemplate의 예외 변환을 거쳐 런타임 예외인 DataIntegrityViolationException으로 올라온다(예외 변환은 스프링 DB 1편에서 다뤘다). 런타임 예외이므로 @Transactional의 기본 규칙에 따라 롤백 대상이다.

    저장소 두 개와 서비스 하나를 만든다. 실험 코드는 한 파일 Demo.java 안에 정적 중첩 클래스로 모아 두었기 때문에, 뒤에 나오는 로그의 트랜잭션 이름이 demo.Demo$OrderRepository.save처럼 바깥 클래스 이름을 포함한다. 스프링은 @Transactional이 붙은 메서드의 트랜잭션 이름으로 "클래스의 전체 이름 + 점 + 메서드 이름"을 쓴다.

    public static class OrderRepository {
    private final JdbcTemplate jdbc;
    public OrderRepository(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    @Transactional
    public void save(String item) {
        where("OrderRepository.save");
        jdbc.update("insert into orders(item) values (?)", item);
    }
}

public static class AuditLogRepository {
    private final JdbcTemplate jdbc;
    public AuditLogRepository(JdbcTemplate jdbc) { this.jdbc = jdbc; }

    @Transactional
    public void save(String message) {
        where("AuditLogRepository.save");
        jdbc.update("insert into audit_log(message) values (?)", message);
    }

    @Transactional(propagation = Propagation.REQUIRES_NEW)
    public void saveInNewTx(String message) {
        where("AuditLogRepository.saveInNewTx");
        jdbc.update("insert into audit_log(message) values (?)", message);
    }
}
    public static class OrderService {
    private final OrderRepository orders;
    private final AuditLogRepository audits;
    public OrderService(OrderRepository o, AuditLogRepository a) { orders = o; audits = a; }

    public void placeNoTx(String item, String msg) {             // 경우 1, 2

        orders.save(item);
        audits.save(msg);

    설정은 스프링 부트 없이 손으로 했다. 부트를 쓰면 같은 역할의 빈들이 자동 구성으로 만들어지지만, 여기서는 무엇이 등록되는지 눈에 보이게 하려고 직접 적었다. 풀 크기는 시스템 프로퍼티로 바꿀 수 있게 하고, 커넥션을 얻으려고 기다리는 최대 시간은 HikariCP가 허용하는 최솟값(250ms) 근처인 500ms로 줄였다. H2의 LOCK_TIMEOUT=1000은 행 락을 1초까지만 기다리게 하는 설정으로, 뒤의 락 실험에서 쓴다.

    관찰 도구는 두 가지다. 첫째는 스프링의 디버그 로그다. DataSourceTransactionManager의 로거를 DEBUG로 열면 트랜잭션을 새로 만드는지, 기존 트랜잭션에 참여하는지, 보류하는지, 언제 커밋·롤백하는지가 한 줄씩 찍힌다. 둘째는 where()라는 작은 도우미다. 이 메서드는 지금 실행 중인 코드가 트랜잭션 안에 있는지, 스레드에 묶인 트랜잭션의 이름이 무엇인지, 그리고 어떤 물리 커넥션을 쓰고 있는지를 출력한다.

    static final Map labels = new IdentityHashMap<>();
static DataSource DS;

static void where(String at) {
    try {
        Connection con = DataSourceUtils.getConnection(DS);   // 스레드에 묶인 커넥션이 있으면 그것을 돌려준다
        Object physical = con.unwrap(org.h2.jdbc.JdbcConnection.class);
        String label = labels.computeIfAbsent(physical, k -> "conn-" + (labels.size() + 1));
        System.out.println("  [" + at + "] txActive=" + TransactionSynchronizationManager.isActualTransactionActive()
            + ", txName=" + TransactionSynchronizationManager.getCurrentTransactionName()
            + ", connection=" + label + ", autoCommit=" + con.getAutoCommit());
        DataSourceUtils.releaseConnection(con, DS);
    } catch (Exception e) { throw new RuntimeException(e); }
}

    HikariCP가 돌려주는 커넥션은 HikariProxyConnection이라는 프록시라서, 같은 물리 커넥션이라도 빌릴 때마다 프록시 객체가 새로 만들어진다. 그래서 프록시가 아니라 unwrap으로 꺼낸 H2 드라이버의 실제 연결 객체를 기준으로 라벨(conn-1, conn-2)을 붙였다. 로그 속의 conn0, conn1은 H2 드라이버가 물리 연결에 붙인 이름이고, 내 라벨 conn-1, conn-2와 각각 대응한다. 아래 로그에서는 로거 이름과 실행마다 달라지는 프록시 해시값을 줄였고, TransactionInterceptor가 TRACE 수준으로 남기는 줄은 뺐다.

    한 줄씩 따라가 보자. 서비스 메서드 안에서 where()를 호출했을 때 txActive=false, autoCommit=true다. 트랜잭션이 없으므로 DataSourceUtils.getConnection은 풀에서 커넥션을 빌려 왔다가 곧바로 반납했다. 다음으로 orders.save를 호출하면 프록시의 TransactionInterceptor가 트랜잭션 매니저의 getTransaction을 부른다. 스레드에 묶인 트랜잭션이 없으므로 "Creating new transaction" 로그와 함께 새 물리 트랜잭션이 시작된다. 매니저는 풀에서 커넥션을 얻고(Acquired Connection) 자동 커밋을 끈 뒤(Switching ... to manual commit) 그 커넥션을 스레드에 묶는다. 메서드가 정상 반환되면 커밋하고 커넥션을 풀에 돌려준다.

    감사 기록 저장도 같은 순서로 새 물리 트랜잭션을 연다. INSERT가 실패해 런타임 예외가 프록시 밖으로 나가려 하면, 인터셉터는 롤백 규칙을 확인하고 매니저의 rollback을 호출한다. 이 트랜잭션은 자신이 시작한 새 트랜잭션이므로 "Initiating transaction rollback"이 찍히고 실제 JDBC 롤백이 실행된다. 그러나 주문 INSERT는 이미 앞의 트랜잭션에서 커밋되었다. 결과는 orders=[B], audit_log=[], 주문만 있고 감사 기록은 없다. 이번 요구사항으로 보면 우연히 원하는 결과지만, 반대 순서였다면, 즉 감사 기록이 먼저 커밋되고 주문이 실패했다면 존재하지 않는 주문에 대한 감사 기록이 남는다. 두 작업의 원자성(atomicity)이 처음부터 보장되지 않는 구조다.

    로그에서 눈여겨볼 점이 하나 더 있다. 두 트랜잭션 모두 wrapping conn0, 내 라벨로도 conn-1이다. 같은 물리 커넥션을 썼다. HikariCP는 반납된 커넥션을 다시 빌려주므로, 단일 스레드에서 순서대로 실행하면 같은 커넥션이 재사용되는 경우가 흔하다. 그런데도 트랜잭션은 둘이다. 첫 트랜잭션은 commit()으로 끝났고 커넥션은 자동 커밋 모드로 되돌려져 풀에 반납되었다. 두 번째 트랜잭션은 그 커넥션을 새로 빌려 다시 자동 커밋을 끄고 시작했다. 데이터베이스 입장에서 트랜잭션의 경계는 "같은 커넥션"이 아니라 "자동 커밋을 끈 시점부터 commit 또는 rollback까지"다. 같은 커넥션을 썼다는 사실이 같은 트랜잭션이라는 뜻은 아니다. 반대로 다음 경우들에서 보겠지만, 같은 트랜잭션에 참여하려면 반드시 같은 커넥션을 써야 한다.

    단일 트랜잭션: 경계를 서비스로 올리면 무엇이 같은 커넥션을 보장하는가

    원자성을 되찾는 가장 직접적인 방법은 트랜잭션 경계를 서비스로 올리는 것이다. 저장소 메서드에서 @Transactional을 떼고 서비스 메서드에만 붙인다. 그러면 서비스 프록시가 트랜잭션을 시작하고, 그 안에서 호출되는 두 저장소 메서드는 프록시의 트랜잭션 처리를 거치지 않는다. 두 INSERT는 하나의 물리 트랜잭션에서 실행되고, 둘 중 하나라도 런타임 예외로 실패하면 예외가 서비스 프록시까지 올라가 전체가 롤백된다.

    여기서 물어야 할 질문은 이것이다. 저장소의 JdbcTemplate은 트랜잭션 매니저를 전혀 모르는데, 어떻게 서비스가 시작한 트랜잭션의 커넥션을 쓰는가? 답은 스프링 DB 1편에서 본 트랜잭션 동기화다. 트랜잭션 매니저는 트랜잭션을 시작하면서 커넥션을 감싼 ConnectionHolder를 TransactionSynchronizationManager에 등록한다. 이 클래스는 내부에 ThreadLocal로 된 자원 맵을 갖고 있고, 키는 DataSource 객체, 값은 ConnectionHolder다. JdbcTemplate은 SQL을 실행할 때 DataSourceUtils.getConnection(dataSource)를 부르는데, 이 메서드는 먼저 현재 스레드의 자원 맵에서 그 DataSource를 키로 홀더를 찾는다. 있으면 그 커넥션을 쓰고, 없으면 풀에서 새로 빌린다.

    스레드 T (요청 하나를 처리하는 동안)
 ┌─────────────────────────────────────────────────────────┐
 │ ThreadLocal: TransactionSynchronizationManager.resources │
 │   key = HikariDataSource@...                              │
 │   val = ConnectionHolder ── conn0 (autoCommit=false)      │

 │ ThreadLocal: currentTransactionName = "...OrderService.place" │

    그러니까 "같은 트랜잭션"을 만드는 실체는 애너테이션이 아니라 스레드에 묶인 하나의 커넥션 홀더다. 같은 스레드에서, 같은 DataSource를 키로, 같은 홀더를 찾아가면 같은 트랜잭션이다. JPA도 원리는 같다. JpaTransactionManager는 EntityManagerFactory를 키로 EntityManagerHolder를 묶고, 리포지토리에 주입된 공유 EntityManager 프록시는 호출될 때마다 현재 스레드에 묶인 EntityManager를 찾아 위임한다. 그래서 두 리포지토리는 같은 영속성 컨텍스트를 공유한다.

    이 구조의 약점은 재사용이다. 저장소에서 @Transactional을 뗐으므로, 다른 서비스가 트랜잭션 없이 orders.save를 직접 호출하면 그 INSERT는 자동 커밋 모드로 실행된다. 저장소 단독으로도 트랜잭션이 필요하고, 서비스 안에서 쓰일 때는 서비스의 트랜잭션에 합류해야 한다. 이 두 요구를 동시에 만족시키는 장치가 전파(propagation)이고, 기본값 REQUIRED가 바로 그 일을 한다.

    위아래 두 개의 타임라인으로, 위는 저장소마다 물리 트랜잭션이 따로 열리고 닫히는 모습, 아래는 서비스가 연 하나의 물리 트랜잭션 안에 두 INSERT가 들어가는 모습을 보여 준다. 흰 배경의 깔끔한 기술 다이어그램. 가로로 긴 타임라인 두 개를 위아래로 배치한다. 위쪽 타임라인 제목은 "저장소마다 트랜잭션". 그 위에 파란 막대 하나("주문 트랜잭션: 커밋")와 그 오른쪽에 떨어져 있는 빨간 막대 하나("감사 트랜잭션: 롤백")를 그리고, 두 막대 아래에 같은 회색 원통 아이콘 "conn0"을 각각 붙인다. 위쪽 끝에는 결과 상자 "orders=[B], audit_log=[]". 아래쪽 타임라인 제목은 "서비스 하나의 트랜잭션". 하나의 긴 초록 막대("서비스 트랜잭션") 안에 작은 두 칸 "주문 INSERT", "감사 INSERT"가 들어 있고, 막대 끝에 "커밋 또는 롤백 한 번"이라는 라벨이 붙는다. 두 타임라인 사이에 굵은 글씨로 "같은 커넥션 ≠ 같은 트랜잭션" 문구를 둔다. 라벨은 모두 한국어로 정확히 위 문구를 쓴다. 위: 같은 물리 커넥션을 연달아 썼어도 트랜잭션은 둘이다. 아래: 경계를 서비스로 올리면 두 INSERT가 한 물리 트랜잭션에 묶인다.

    이제 서비스와 두 저장소 모두에 @Transactional(기본 전파 REQUIRED)을 붙인다. 서비스의 place를 짧은 메시지로 호출한 결과다.

AbstractPlatformTransactionManager.getTransaction의 첫 단계는 doGetTransaction()으로 현재 스레드의 자원 맵을 들여다보는 것이다. DataSourceTransactionManager의 isExistingTransaction은 "커넥션 홀더가 있고 그 홀더의 트랜잭션이 활성 상태인가"를 검사한다. 서비스가 이미 홀더를 묶어 두었으므로 참이고, 그러면 handleExistingTransaction으로 넘어간다. 이 메서드는 NEVER, NOT_SUPPORTED, REQUIRES_NEW, NESTED를 차례로 걸러 내고, 어디에도 해당하지 않는 REQUIRED, SUPPORTS, MANDATORY는 마지막에 "기존 트랜잭션에 참여"로 처리한다. 참여는 커넥션을 새로 얻지 않는다. 같은 트랜잭션 객체를 담은 새 TransactionStatus를 만들되, 그 상태의 newTransaction 값을 false로 둘 뿐이다.

    where()의 출력도 같은 이야기를 한다. 저장소 안에서 본 트랜잭션 이름은 저장소 메서드 이름이 아니라 demo.Demo$OrderService.place다. 트랜잭션 이름, 읽기 전용 여부, 격리 수준 같은 스레드 단위 정보는 새 동기화를 시작하는 쪽, 즉 물리 트랜잭션을 연 쪽만 설정한다. 참여하는 쪽은 그 정보를 그대로 물려받는다. 커넥션 라벨도 세 곳 모두 conn-1이다.

    커밋은 어떻게 일어나는가. 저장소 메서드가 정상 반환되면 저장소 프록시의 인터셉터도 매니저의 commit(status)를 부른다. 그런데 로그에는 저장소 단계에서 커밋 로그가 없다. processCommit은 상태 객체를 보고 세 갈래로 나뉜다. 세이브포인트가 있으면 세이브포인트를 해제하고, isNewTransaction()이 참이면 실제로 doCommit을 호출하며, 둘 다 아니면 아무것도 하지 않는다. 참여한 논리 트랜잭션의 커밋은 세 번째 갈래, 즉 아무 일도 하지 않는 커밋이다. 마지막으로 서비스 프록시가 commit을 부를 때 비로소 newTransaction=true인 상태가 들어오고 "Initiating transaction commit"과 실제 JDBC 커밋이 실행된다.

    논리 트랜잭션getTransaction 결과newTransactioncommit 호출 시 하는 일

    OrderRepository.save기존 트랜잭션 참여false없음
    AuditLogRepository.save기존 트랜잭션 참여false없음

    이 표가 08회에서 말한 원칙, "물리 트랜잭션을 처음 시작한 논리 트랜잭션만 실제 커밋·롤백을 수행한다"를 코드 수준에서 보여 준다. 그리고 이 표의 마지막 열에서 한 칸이 비어 있지 않은 경우가 있다. 커밋이 아니라 롤백일 때다.

    else {
    // Participating in larger transaction
    if (status.hasTransaction()) {
        if (status.isLocalRollbackOnly() || isGlobalRollbackOnParticipationFailure()) {
            doSetRollbackOnly(status);
        }
        // else: "letting transaction originator decide on rollback"

    // Unexpected rollback only matters here if we're asked to fail early
    if (!isFailEarlyOnGlobalRollbackOnly()) {
        unexpectedRollback = false;
    }

    참여자는 물리 트랜잭션을 롤백할 권한이 없다. 대신 globalRollbackOnParticipationFailure가 참이면(기본값이 true다) doSetRollbackOnly를 호출한다. DataSourceTransactionManager에서 이 메서드는 트랜잭션 객체의 setRollbackOnly()를 부르고, 그 구현은 단 한 줄 getConnectionHolder().setRollbackOnly()다. 즉 rollback-only 표시는 예외 객체나 논리 트랜잭션의 상태 객체에 남는 것이 아니라, 스레드에 묶인 공유 자원인 커넥션 홀더에 남는다. 로그의 "Setting JDBC transaction [...] rollback-only"가 그 순간이다. 그 뒤 인터셉터는 원래 예외를 다시 던진다.

    예외는 서비스 메서드를 그대로 통과해 서비스 프록시의 인터셉터에 도착한다. 이번에는 상태 객체가 newTransaction=true이므로 processRollback의 "Initiating transaction rollback" 갈래로 들어가 실제 JDBC 롤백을 실행한다. 주문 INSERT도 함께 사라져 orders=[], audit_log=[]이 된다. 이 경우에는 rollback-only 표시가 결과를 바꾸지 않았다. 어차피 바깥도 예외로 끝났으니 롤백할 참이었다. 표시가 결과를 바꾸는 것은 바깥이 예외를 잡았을 때다.

    JPA라면 JpaTransactionManager.doSetRollbackOnly가 "Setting JPA transaction on EntityManager [...] rollback-only" 로그를 남기고, 트랜잭션 객체의 setRollbackOnly()가 EntityManager.getTransaction().setRollbackOnly()를 호출한다. JDBC 커넥션 홀더가 함께 묶여 있으면 그 홀더에도 표시한다. 바깥에서 커밋 전에 확인할 때는 EntityTransaction.getRollbackOnly()를 읽는다(6.2.x 소스 기준).

    경우 5: 복구 REQUIRED — 예외를 잡았는데 왜 전부 롤백되는가

    요구사항으로 돌아가자. 감사 기록이 실패해도 주문은 커밋해야 한다. 가장 먼저 떠오르는 방법은 서비스에서 감사 기록 저장을 try-catch로 감싸 예외를 삼키는 것이다. 예외가 서비스 밖으로 나가지 않으니 서비스 프록시는 정상 반환을 보고 커밋할 것이라고 기대하게 된다. placeRecover가 그 코드다. 실행 결과는 기대와 다르다.

    서비스의 catch는 분명히 실행되었다("catch: DataIntegrityViolationException"). 그런데 그보다 한 줄 앞에 이미 "Setting JDBC transaction [...] rollback-only"가 찍혀 있다. 예외가 서비스의 catch에 도착하기 전에 저장소 프록시를 먼저 통과했고, 그 프록시가 커넥션 홀더에 표시를 남긴 것이다. catch가 막을 수 있는 것은 예외의 전파뿐이다. 이미 공유 자원에 남은 표시는 지우지 못한다.

    서비스 메서드가 정상 반환하면 서비스 프록시의 인터셉터는 commitTransactionAfterReturning에서 매니저의 commit(status)를 호출한다. AbstractPlatformTransactionManager.commit은 실제 커밋 전에 두 가지를 확인한다. 첫째는 이 상태 객체 자체에 걸린 지역 rollback-only(isLocalRollbackOnly)이고, 둘째가 트랜잭션 객체를 통해 커넥션 홀더에 걸린 전역 rollback-only(isGlobalRollbackOnly)다. 둘째 조건에 걸리면 "Global transaction is marked as rollback-only but transactional code requested commit" 로그를 남기고 processRollback(defStatus, true)를 호출한다. 두 번째 인자 true가 "예상하지 못한 롤백"이라는 뜻이다. 이 상태는 새 트랜잭션이므로 실제 롤백이 실행되고, 정리가 끝난 뒤 unexpectedRollback이 참이므로 UnexpectedRollbackException("Transaction rolled back because it has been marked as rollback-only")을 던진다. 이 예외는 서비스 프록시 밖, 즉 서비스를 호출한 쪽으로 나간다.

    왜 조용히 롤백만 하지 않고 굳이 예외를 던지는가. 스프링 레퍼런스의 트랜잭션 전파 문서는 이를 의도된 동작이라고 설명한다. 바깥 호출자는 커밋을 요청했고 정상 반환을 기대한다. 그런데 내부의 어떤 범위가 몰래 rollback-only를 걸어 실제로는 롤백되었다면, 호출자는 커밋되었다고 잘못 믿게 된다. 문서의 표현으로는 호출자가 "커밋이 수행되었다고 오해하지 않게" 하려고 UnexpectedRollbackException을 던진다. 만약 이 예외가 없다면 경우 5의 서비스는 정상 반환하고, 화면에는 "주문 완료"가 뜨지만 데이터베이스에는 주문이 없다. 롤백 자체보다 그 사실을 아무도 모르는 상태가 훨씬 위험하다.

    서비스 프록시, 감사 저장소 프록시, 트랜잭션 매니저, 커넥션 홀더 네 참여자 사이에서 표시가 남고, catch로 예외가 사라진 뒤에도 표시 때문에 커밋이 롤백으로 바뀌는 흐름. 흰 배경의 UML 시퀀스 다이어그램. 왼쪽부터 세로 생명선 네 개: "서비스 프록시", "감사 저장소 프록시", "트랜잭션 매니저", "커넥션 홀더". 1번 화살표: 감사 저장소 프록시 안에서 빨간 번개 아이콘과 "INSERT 실패". 2번 화살표: 감사 저장소 프록시 → 트랜잭션 매니저 "rollback(참여)". 3번 화살표: 트랜잭션 매니저 → 커넥션 홀더 "rollback-only 표시"이고, 커넥션 홀더 생명선 위에 빨간 깃발 아이콘을 꽂는다. 4번 점선 화살표: 감사 저장소 프록시 → 서비스 프록시 "예외 전파". 서비스 프록시 생명선에 초록 방패 아이콘과 "catch". 5번 화살표: 서비스 프록시 → 트랜잭션 매니저 "commit 요청". 6번 화살표: 트랜잭션 매니저 → 커넥션 홀더 쪽으로 돋보기 아이콘 "표시 확인". 7번 화살표: 트랜잭션 매니저 → 서비스 프록시 바깥 왼쪽 끝 "UnexpectedRollbackException". 빨간 깃발이 끝까지 남아 있는 것이 눈에 띄게 그린다. catch는 예외의 전파를 멈출 뿐, 커넥션 홀더에 꽂힌 rollback-only 표시는 커밋 시점까지 남아 롤백과 예외로 이어진다.

    rollback-only를 둘러싼 두 개의 스위치와 그 함정

    AbstractPlatformTransactionManager에는 이 동작을 바꾸는 스위치가 두 개 있다. 소스에서 확인한 기본값은 다음과 같다.

    속성기본값참일 때거짓일 때
    globalRollbackOnParticipationFailuretrue참여자가 롤백되면 전체를 rollback-only로 표시한다표시하지 않고 원래 트랜잭션을 연 쪽에 판단을 맡긴다
    failEarlyOnGlobalRollbackOnlyfalse표시를 처음 발견한 안쪽 경계에서부터 UnexpectedRollbackException을 던진다가장 바깥 경계에서만 예외를 던진다

    첫 번째 스위치를 끄면 경우 5의 주문이 커밋될 것처럼 보인다. 실제로 참여자의 롤백이 "Participating transaction failed - letting transaction originator decide on rollback" 로그만 남기고 표시를 하지 않게 된다. 그러나 이 속성의 Javadoc은 분명한 조건을 단다. 데이터 접근 실패 뒤에도 참여한 모든 자원이 커밋을 향해 계속 진행할 수 있어야만 의미가 있는데, Hibernate 세션은 일반적으로 그렇지 않고, JDBC의 INSERT·UPDATE·DELETE 연속도 마찬가지라는 것이다. 예외가 난 뒤의 영속성 컨텍스트는 일관성이 깨졌을 수 있다. 또 이 스위치는 매니저 전체에 적용되므로 감사 기록 한 곳을 위해 모든 서비스의 안전장치를 끄는 셈이 된다. 같은 Javadoc은 하위 트랜잭션 실패를 다루는 권장 해법으로 세이브포인트 기반의 NESTED를 든다.

    Javadoc은 하나를 더 밝힌다. 이 스위치는 인터셉터가 롤백 규칙에 따라 rollback()을 호출하는 경우에만 적용된다. 코드에서 TransactionStatus.setRollbackOnly()를 직접 호출하면 상태 객체에 지역 rollback-only가 걸리고, 참여자의 commit은 이를 보고 processRollback으로 돌아간다. 앞에서 옮긴 조건식 status.isLocalRollbackOnly() || isGlobalRollbackOnParticipationFailure()의 앞쪽이 그 경우라서, 스위치와 상관없이 전역 표시가 걸린다.

    두 번째 스위치 failEarlyOnGlobalRollbackOnly는 예외가 나는 위치만 바꾼다. 기본값 false에서는 안쪽 경계에서 표시를 발견해도 넘어가고 가장 바깥 경계에서만 예외를 던진다. Javadoc은 그 이유로, 예를 들어 단위 테스트에서 연산 하나가 실패해 트랜잭션이 결코 커밋되지 않을 상황에서도 테스트를 계속 진행할 수 있게 하려는 것이라고 설명한다. 참으로 켜면 표시된 트랜잭션에 참여한 안쪽 경계가 커밋을 시도하는 순간에 바로 예외가 난다. 어느 쪽이든 결과적으로 주문이 커밋되지는 않는다.

    이 장의 핵심

    REQUIRED로 참여한 범위의 실패는 예외가 아니라 커넥션 홀더(또는 EntityTransaction)의 rollback-only 표시로 바깥에 전달된다. 예외는 잡을 수 있어도 표시는 지울 수 없다. 그러므로 "실패해도 바깥은 커밋"이 필요한 작업은 바깥과 같은 물리 트랜잭션에 참여시키면 안 된다. 물리 트랜잭션을 분리하거나(REQUIRES_NEW), 세이브포인트로 부분만 되돌리거나(NESTED), 트랜잭션 경계 자체를 나눠야 한다.

    경우 6: 복구 REQUIRES_NEW — 물리 트랜잭션을 떼어 낸다

    감사 기록 저장을 Propagation.REQUIRES_NEW로 선언한 saveInNewTx로 바꾸고, 서비스는 경우 5와 똑같이 예외를 잡는다.

    보류(suspend)가 무엇을 하는지 소스로 보자. handleExistingTransaction의 REQUIRES_NEW 갈래는 suspend(transaction)을 호출한 뒤 startTransaction으로 새 트랜잭션을 연다. suspend는 먼저 활성화된 트랜잭션 동기화 콜백들을 보류하고, 하위 클래스의 doSuspend를 부른 다음, 스레드에 저장된 트랜잭션 이름·읽기 전용 여부·격리 수준·활성 여부를 꺼내 지운다. 이것들을 모두 SuspendedResourcesHolder 객체에 담아 새 트랜잭션의 상태 객체에 매달아 둔다. DataSourceTransactionManager.doSuspend는 세 줄이다.

    protected Object doSuspend(Object transaction) {
    DataSourceTransactionObject txObject = (DataSourceTransactionObject) transaction;
    txObject.setConnectionHolder(null);
    return TransactionSynchronizationManager.unbindResource(obtainDataSource());
}

    바깥 커넥션 홀더를 스레드의 자원 맵에서 떼어 내 반환한다. 이제 자원 맵에는 그 DataSource에 대한 항목이 없으므로, 이어지는 doBegin은 풀에서 새 커넥션을 얻어 새 홀더를 묶는다. 안쪽 메서드의 JdbcTemplate이 DataSourceUtils.getConnection으로 찾는 것은 이 새 홀더다. 바깥 커넥션은 사라진 것이 아니다. 여전히 풀에서 빌린 상태로, 트랜잭션도 열린 채로 SuspendedResourcesHolder 안에서 기다린다.

    안쪽 트랜잭션은 자기 상태 객체가 newTransaction=true이므로 롤백을 직접 실행할 권한이 있다. 롤백 대상 홀더는 conn1의 홀더이고, rollback-only 표시는 어디에도 남지 않는다. 롤백이 끝나면 cleanupAfterCompletion이 conn1을 풀에 반납하고, 상태 객체에 매달린 보류 자원이 있으므로 "Resuming suspended transaction after completion of inner transaction" 로그와 함께 resume을 호출한다. resume은 doResume으로 바깥 홀더를 다시 자원 맵에 묶고, 트랜잭션 이름과 동기화 콜백도 되돌린다. 이 모든 일이 안쪽 프록시 안에서 끝난 뒤에 원래 예외가 서비스로 던져진다. 서비스의 catch가 실행될 때 스레드의 상태는 안쪽 트랜잭션이 시작되기 직전과 같다.

    시간 →

    이 그림의 맨 아래 줄이 다음 단락의 주제다. REQUIRES_NEW가 실행되는 동안 한 스레드가 커넥션을 두 개 쥐고 있다.

    한 스레드의 자원 맵 칸에 conn0 홀더가 있다가 보관함으로 옮겨지고, conn1 홀더가 들어왔다가 나가고, 다시 conn0 홀더가 돌아오는 다섯 단계. 흰 배경의 가로 5단 상태 그림. 각 단계마다 위에 "스레드 자원 맵"이라는 사각형 칸이 있고, 아래에 "보관함(SuspendedResourcesHolder)"이라는 서랍 아이콘이 있다. 1단계 "서비스 트랜잭션 시작": 자원 맵 칸에 파란 카드 "conn0 홀더". 2단계 "suspend": 파란 카드가 아래 서랍으로 내려가는 곡선 화살표, 자원 맵 칸은 비어 있다. 3단계 "새 트랜잭션": 자원 맵 칸에 주황 카드 "conn1 홀더", 서랍 안에는 파란 카드. 4단계 "안쪽 롤백": 주황 카드가 오른쪽 위의 풀 아이콘 "커넥션 풀"로 돌아가는 화살표. 5단계 "resume": 파란 카드가 서랍에서 자원 맵 칸으로 올라오는 화살표. 각 단계 아래에 작은 숫자 배지로 빌린 커넥션 수 "1", "1", "2", "1", "1"을 표시한다. REQUIRES_NEW는 바깥 홀더를 떼어 보관하고 새 커넥션으로 독립된 트랜잭션을 연다. 그동안 스레드는 커넥션 두 개를 점유한다.

    REQUIRES_NEW의 비용 1: 한 요청이 커넥션 두 개를 동시에 쥔다

    스프링 레퍼런스의 전파 문서는 REQUIRES_NEW에 대해 경고를 단다. 바깥 트랜잭션에 묶인 자원은 그대로 묶여 있는 상태에서 안쪽 트랜잭션이 새 데이터베이스 커넥션 같은 자기 자원을 얻는다. 그래서 여러 스레드가 바깥 트랜잭션을 연 채 안쪽 트랜잭션용 커넥션을 기다리면 풀이 고갈되고 교착 상태(deadlock)에 이를 수 있다. 문서는 커넥션 풀 크기가 동시 스레드 수보다 적어도 1 이상 크지 않다면 REQUIRES_NEW를 쓰지 말라고 권한다.

    바깥 트랜잭션이 하나뿐인 커넥션을 쥔 채 보류되었고, 안쪽 doBegin이 풀에 커넥션을 요청했지만 내줄 것이 없다. HikariCP는 설정한 connectionTimeout(여기서는 500ms) 동안 기다린 뒤 SQLTransientConnectionException을 던졌다. 메시지 괄호 안의 total=1, active=1, idle=0이 상황을 그대로 보여 준다. 기다린 시간 511ms는 실행마다 조금씩 다르다. 스프링은 이를 CannotCreateTransactionException으로 감싸고, 시작에 실패한 안쪽 트랜잭션을 위해 바깥 자원을 다시 묶어 놓은 뒤 예외를 던진다. 소스에서 REQUIRES_NEW 갈래의 startTransaction 호출이 try로 감싸여 있고, 실패하면 resumeAfterBeginException을 호출하는 부분이 그 일을 한다.

    이 실행에는 함정이 하나 더 숨어 있다. 결과는 orders=[F], audit_log=[]로 정상 경우 6과 똑같다. 서비스의 catch (RuntimeException e)가 감사 기록의 데이터 오류뿐 아니라 커넥션 고갈이라는 인프라 장애까지 삼켜 버렸기 때문이다. 감사 기록 하나를 포기하는 것은 업무 규칙이 허용한 일이지만, 풀이 바닥났다는 신호를 조용히 흘려보내는 것은 아니다. 복구용 catch는 잡을 예외를 좁히거나 적어도 로그를 남겨야 하는 이유다.

    스레드가 여럿이면 문제는 더 커진다. HikariCP의 기본값은 maximumPoolSize 10, connectionTimeout 30000ms(30초)다. 요청 스레드 10개가 동시에 이 서비스에 들어와 각자 바깥 트랜잭션용 커넥션을 하나씩 가져가면 풀의 10개가 모두 바깥 트랜잭션에 묶인다. 이제 10개 스레드 모두 안쪽 트랜잭션용 커넥션을 기다리지만, 어떤 스레드도 바깥 트랜잭션을 끝내지 못하므로 커넥션은 반납되지 않는다. 고전적인 자원 교착의 모양이다. HikariCP에는 대기 시간 상한이 있으므로 영원히 멈추지는 않고 30초 뒤 모두 실패하지만, 그 30초 동안 이 풀을 쓰는 다른 요청도 모두 막힌다. 풀 크기가 넉넉하면 동시에 이런 상태에 도달하지 않을 뿐, 한 요청이 커넥션을 두 개씩 쓴다는 사실은 그대로이므로 풀 크기 계산에 반영해야 한다.

    풀의 커넥션이 모두 바깥 트랜잭션에 잡혀 있고, 각 스레드가 두 번째 커넥션을 기다리며 서로를 막는 모습. 흰 배경의 개념도. 가운데에 둥근 사각형 "커넥션 풀 (최대 10)"이 있고, 그 안의 커넥션 슬롯 10개가 모두 파란색으로 채워져 "사용 중" 상태다. 풀 주변에 스레드 아이콘 10개가 원형으로 배치되어 있고, 각 스레드에서 풀의 파란 슬롯 하나로 실선 화살표 "바깥 트랜잭션 보유"가 이어진다. 동시에 각 스레드에서 풀 입구로 빨간 점선 화살표 "안쪽 트랜잭션용 커넥션 대기"가 향한다. 풀 입구 옆에 모래시계 아이콘과 "connectionTimeout 30초"라는 라벨. 아래쪽에 상자 하나 "필요한 커넥션 = 스레드 수 × 2"를 둔다. 모든 커넥션이 바깥 트랜잭션에 묶이면, 안쪽 트랜잭션용 두 번째 커넥션은 누구에게도 돌아가지 않는다.

    REQUIRES_NEW의 비용 2: 같은 행을 건드리면 자기 자신을 기다린다

    REQUIRES_NEW의 두 트랜잭션은 같은 스레드, 같은 요청에서 실행되지만 데이터베이스가 보기에는 서로 다른 두 세션의 두 트랜잭션이다. 이것이 락과 가시성에서 문제를 만든다. 바깥 트랜잭션이 어떤 행을 UPDATE해 행 락(row lock)을 잡은 상태에서, 안쪽 REQUIRES_NEW 트랜잭션이 같은 행을 UPDATE하면 어떻게 될까. 안쪽 트랜잭션은 다른 트랜잭션이 가진 락이 풀리기를 기다린다. 그런데 그 락을 가진 바깥 트랜잭션은 안쪽 메서드가 반환되어야 진행할 수 있다. 같은 스레드 안에서 스스로를 기다리는 상황이다. 데이터베이스는 두 세션이 같은 애플리케이션 스레드에서 왔다는 것을 알지 못하므로 이를 교착 상태로 감지할 수도 없다. 결국 락 대기 시간 제한이 끝날 때까지 기다린다.

    실험 7번 경우가 이것이다. 바깥 서비스 트랜잭션이 OrderRepository를 통해 주문 행 하나를 UPDATE하고, 이어서 감사 저장소의 REQUIRES_NEW 메서드가 같은 행을 UPDATE한다.

    JPA에서 REQUIRES_NEW가 바꾸는 것: 영속성 컨텍스트도 둘이 된다

    JPA를 쓰면 커넥션 말고 하나가 더 둘로 나뉜다. JpaTransactionManager.doSuspend는 EntityManagerFactory를 키로 묶인 EntityManagerHolder를 스레드에서 떼어 내고, DataSource에 대한 ConnectionHolder가 함께 묶여 있었다면 그것도 떼어 낸다. 이어지는 doBegin은 트랜잭션 객체에 EntityManagerHolder가 없으므로 새 EntityManager를 만든다(디버그 로그 "Opened new EntityManager [...] for JPA transaction"). 안쪽 트랜잭션은 자기만의 영속성 컨텍스트를 갖는다. 6.2.x 소스에서 확인한 흐름이다.

    이것이 뜻하는 바는 세 가지다. 첫째, 바깥에서 조회해 영속 상태인 엔티티를 안쪽 메서드에 넘겨도, 안쪽의 영속성 컨텍스트 입장에서는 관리하지 않는 객체다. 안쪽에서 그 객체의 필드를 바꿔도 안쪽 커밋 때 변경 감지(dirty checking)의 대상이 되지 않는다. 둘째, 바깥 영속성 컨텍스트에 쌓인 아직 플러시되지 않은 변경은 데이터베이스에도 없으므로 안쪽에서 JPQL로 조회해도 보이지 않는다. 셋째, 쓰기 지연 때문에 실패 지점이 달라진다. REQUIRED로 참여한 안쪽 메서드에서 persist한 엔티티의 INSERT가 바깥의 커밋 직전 플러시까지 미뤄질 수 있고, 그러면 데이터 오류는 서비스의 try 블록 안이 아니라 서비스 프록시의 커밋 시점에 드러난다. 경우 5처럼 catch로 감싸 놓아도 잡히지 않는다. 반대로 REQUIRES_NEW의 안쪽 트랜잭션은 안쪽 프록시가 반환되기 전에 스스로 커밋하므로, 플러시에서 나는 오류도 안쪽 프록시를 빠져나와 서비스의 catch에 도착한다. 식별자 생성 전략이 IDENTITY여서 persist 시점에 INSERT가 바로 나가는 경우라면 오류가 persist 호출에서 바로 드러난다는 차이도 기억해 두자.

    또 다른 길 1: NESTED — 같은 커넥션 안의 세이브포인트

    커넥션을 하나 더 쓰지 않고 감사 기록만 되돌리는 방법이 NESTED다. 스프링 레퍼런스는 NESTED가 롤백할 수 있는 세이브포인트(savepoint) 여러 개를 가진 하나의 물리 트랜잭션을 쓰며, 보통 JDBC 세이브포인트에 대응되므로 JDBC 자원 트랜잭션에서만 동작한다고 설명한다. DataSourceTransactionManager는 이를 지원한다. 감사 저장소에 @Transactional(propagation = Propagation.NESTED)를 붙인 saveNested를 만들고, 경우 5·6과 같은 모양으로 서비스에서 예외를 잡았다(실험의 8번 경우).

"주문이 실패해도 실패 시도 자체는 감사 기록으로 남겨야 한다"는 요구라면 NESTED로는 안 되고, 독립 커밋이 필요한 REQUIRES_NEW나 경계 분리가 맞다. 또 레퍼런스가 말하듯 NESTED는 JDBC 세이브포인트에 기대므로, JPA처럼 영속성 컨텍스트가 메모리에 상태를 들고 있는 기술에서는 데이터베이스만 세이브포인트로 되돌아가고 메모리의 엔티티 상태는 되돌아가지 않는다는 점을 따로 고려해야 한다. 이 회차의 실험은 DataSourceTransactionManager에서만 NESTED를 확인했다.

    또 다른 길 2: 트랜잭션 경계를 나눈다

    전파 옵션을 바꾸는 대신 구조를 바꾸는 방법도 있다. 주문 저장과 감사 기록 저장을 각각 별도의 트랜잭션 메서드로 두고, 트랜잭션이 없는 바깥 객체가 둘을 차례로 호출하는 것이다.

    public class OrderFacade {                      // 트랜잭션 없음
    private final OrderTxService orderTxService;
    private final AuditTxService auditTxService;
    // 생성자 생략 ...

    public void place(String item, String msg) {
        orderTxService.place(item);             // @Transactional: 여기서 커밋까지 끝난다
        try {
            auditTxService.record(msg);         // @Transactional: 별도 트랜잭션
        } catch (DataAccessException e) {
            // 감사 기록 실패를 로그로 남기고 계속 ...
        }
    }
}

    경우 1·2와 같은 모양이지만, 이번에는 그것이 의도된 설계다. 두 트랜잭션은 순서대로 실행되므로 한 스레드가 커넥션을 동시에 두 개 쥐는 순간이 없다. 주문 트랜잭션은 감사 기록이 시작되기 전에 이미 커밋되고 락도 풀렸으므로 자기 자신을 기다리는 문제도 생기지 않는다. 감사 기록은 커밋된 주문을 볼 수도 있다. 대가는 원자성을 일부러 포기했다는 점이다. 주문 커밋 직후 프로세스가 죽으면 감사 기록 없는 주문이 남는다. 이 요구사항에서는 그것이 허용된 결과이지만, 허용되지 않는 데이터에 같은 구조를 쓰면 안 된다. catch는 앞에서 본 이유대로 DataAccessException처럼 좁게 잡았다.

    "주문이 커밋된 뒤에만 감사 기록을 남긴다"를 트랜잭션 동기화 콜백으로 구현할 때도 전파를 알아야 한다. TransactionSynchronization.afterCommit의 Javadoc은 이 시점에 트랜잭션은 이미 커밋되었지만 트랜잭션 자원은 아직 활성 상태로 접근 가능할 수 있고, 그래서 여기서 실행되는 데이터 접근 코드는 별도 트랜잭션을 명시하지 않는 한 원래 트랜잭션에 "참여"하며 그 뒤에는 커밋이 더 없다고 경고한다. 그리고 이 콜백에서 호출하는 트랜잭션 작업에는 REQUIRES_NEW를 쓰라고 권한다. 커밋 후 콜백에서 REQUIRED 메서드로 감사 기록을 저장하면, 이미 커밋을 마친 트랜잭션에 참여해 INSERT가 커밋되지 않을 수 있다는 뜻이다.

    흔한 오해 다섯 가지

    "예외를 잡으면 커밋된다." 바깥 트랜잭션을 연 메서드 안에서 직접 던진 예외를 잡았다면 맞다. 그 예외는 어떤 트랜잭션 프록시도 통과하지 않았기 때문이다. 그러나 @Transactional이 붙은 다른 빈의 메서드에서 던져진 예외는 그 빈의 프록시를 먼저 통과하면서 rollback-only 표시를 남긴다. 경우 5가 그 결과다. 잡는 위치보다 예외가 지나온 경로가 중요하다.

    "REQUIRES_NEW는 바깥과 완전히 독립이다." 커밋과 롤백은 독립이다. 그러나 같은 스레드에서 동기적으로 실행되므로 안쪽이 끝날 때까지 바깥은 멈춰 있고, 바깥이 쥔 커넥션과 락도 그대로다. 안쪽이 오래 걸리면 바깥 트랜잭션도 그만큼 길어진다. 또 안쪽에서 던진 런타임 예외를 바깥에서 잡지 않으면, 그 예외가 바깥 프록시에 도착해 바깥도 롤백된다. 안쪽이 독립적으로 롤백되었다는 사실이 예외의 전파를 막아 주지는 않는다.

    "같은 클래스 안의 다른 메서드에 REQUIRES_NEW를 붙이면 새 트랜잭션이 열린다." 07회에서 본 내부 호출 문제가 전파에도 그대로 적용된다. this.saveInNewTx(...)는 프록시를 거치지 않으므로 전파 설정이 읽히지도 않는다. 실제로 REQUIRES_NEW 메서드를 서비스 클래스 안에 두고 this로 호출해 보니 "Suspending" 로그 없이 바깥 트랜잭션 이름과 같은 커넥션(conn-1)이 그대로 찍혔다. 이 실험에서 감사 기록 메서드를 별도 빈(AuditLogRepository)에 둔 이유가 그것이다.

    "같은 커넥션이면 같은 트랜잭션, 다른 커넥션이면 다른 트랜잭션이다." 뒤쪽은 JDBC 로컬 트랜잭션에서는 맞지만, 앞쪽은 경우 2가 반례다. 풀이 같은 물리 커넥션을 돌려줘도 커밋으로 경계가 나뉘면 다른 트랜잭션이다.

    "UnexpectedRollbackException은 안쪽에서 난 예외다." 이 예외는 바깥 프록시의 commit 처리 중에, 바깥 호출자에게 던져진다. 스택 트레이스의 출발점은 바깥 트랜잭션의 커밋이고, 진짜 원인인 안쪽 예외는 이미 누군가가 잡아 삼킨 뒤다. 이 예외를 만나면 "어디서 rollback-only가 걸렸는가"를 찾아야 하고, 그 단서는 디버그 로그의 "Participating transaction failed - marking existing transaction as rollback-only" 줄에 있다.

REQUIRES_NEW는 커넥션 두 개와 락 대기 위험을, NESTED는 JDBC 세이브포인트 지원과 "바깥이 롤백되면 같이 사라짐"이라는 의미를, 경계 분리는 원자성 포기를 대가로 치른다. 어떤 비용을 받아들일지는 감사 기록이 업무에서 어떤 의미인지에 달려 있다.

    이 회차로 스프링 DB 2편이 끝난다. 01회부터 06회까지 SQL 매퍼와 ORM이 같은 저장소 기능을 어떻게 다르게 구현하는지 보았고, 07회부터 이 회차까지 그 모든 기술 아래에서 공통으로 작동하는 트랜잭션 추상화를 따라갔다. 기술은 달라도 "스레드에 묶인 자원 하나를 여러 논리 범위가 공유한다"는 구조는 같았다. 그 구조를 알고 있으면, 새 데이터 접근 기술을 만나도 커밋과 롤백이 어디서 결정되는지 스스로 추적할 수 있다.
    리포지토리별 트랜잭션
    서비스에 트랜잭션이 없고 저장소마다 @Transactional이 있으면 호출마다 물리 트랜잭션이 따로 열리고 닫힌다. 풀이 같은 물리 커넥션을 돌려줘도 커밋으로 경계가 나뉘므로 원자성이 없다.
    전파 커밋
    REQUIRED로 참여한 논리 트랜잭션의 상태는 newTransaction=false이고, 이 상태로 commit을 호출하면 아무 일도 하지 않는다. 실제 JDBC 커밋은 물리 트랜잭션을 시작한 가장 바깥 범위에서 한 번만 일어난다.
    전파 롤백과 rollback-only
    참여자가 예외로 끝나면 processRollback은 실제 롤백 대신 doSetRollbackOnly로 커넥션 홀더(JPA는 EntityTransaction)에 rollback-only를 표시한다. 기본값 globalRollbackOnParticipationFailure=true 때문이다.
    UnexpectedRollbackException
    바깥이 예외를 잡고 커밋을 요청해도 commit은 전역 rollback-only를 확인해 롤백하고, 호출자가 커밋되었다고 오해하지 않도록 이 예외를 던진다.
    REQUIRES_NEW의 보류와 재개
    suspend는 바깥 커넥션 홀더와 트랜잭션 이름 같은 스레드 상태를 떼어 SuspendedResourcesHolder에 보관하고, 새 커넥션으로 독립된 트랜잭션을 연다. 안쪽이 끝나면 resume으로 되돌린다.
    REQUIRES_NEW의 비용
    한 스레드가 커넥션 두 개를 동시에 쥐므로 풀이 동시 스레드 수보다 크지 않으면 고갈과 교착이 생길 수 있고, 바깥이 잡은 행 락을 안쪽이 기다리면 락 대기 시간 초과까지 멈춘다.
    NESTED
    같은 커넥션에 JDBC 세이브포인트를 만들어 안쪽 실패를 세이브포인트까지만 되돌린다. rollback-only를 남기지 않지만, 안쪽 작업은 바깥과 함께 커밋되고 함께 롤백된다.
    트랜잭션 경계 분리
    트랜잭션 없는 바깥 객체가 두 트랜잭션 메서드를 순서대로 호출하면 커넥션을 동시에 두 개 쓰지 않고 락 충돌도 없지만, 두 작업의 원자성은 의도적으로 포기한다.

    운영 중에 UnexpectedRollbackException이 로그에 찍혔다면, 그 스택 트레이스만 봐서는 원인을 찾을 수 없다. 예외는 바깥 트랜잭션의 커밋 지점에서 나고, 진짜 원인은 어딘가의 catch가 이미 삼켰다. 실무에서 가장 빠른 길은 org.springframework.transaction과 사용하는 트랜잭션 매니저의 로거를 잠시 DEBUG로 열고 "Participating transaction failed - marking existing transaction as rollback-only" 줄 바로 앞에서 어떤 트랜잭션 이름의 어떤 예외가 지나갔는지 찾는 것이다. 그다음 판단은 둘 중 하나다. 그 실패가 정말로 전체를 되돌려야 하는 실패라면 catch를 없애 예외가 정직하게 올라가게 하고, 실패해도 바깥을 살려야 하는 작업이라면 그 작업을 바깥 물리 트랜잭션에서 떼어 낸다.

    REQUIRES_NEW를 도입하는 결정은 커넥션 풀 설정과 함께 내려야 한다. 요청 스레드 수(예를 들어 서블릿 컨테이너의 최대 스레드 수)와 커넥션 풀 크기를 나란히 놓고, REQUIRES_NEW를 거치는 요청이 동시에 몇 개까지 들어올 수 있는지 따져 본다. 스프링 문서의 권고는 풀 크기가 동시 스레드 수보다 적어도 1 커야 한다는 것이다. 이 조건을 맞추기 어렵다면 REQUIRES_NEW 대신 경계 분리나, 데이터의 성격이 허용할 경우 NESTED가 더 나은 선택일 수 있다. 장애가 "평소에는 멀쩡하다가 트래픽이 몰릴 때만 30초씩 멈춘다"는 모양으로 나타난다면 풀 대기 타임아웃과 REQUIRES_NEW의 조합을 의심해 볼 만하다.

    판단이 달라지는 조건도 기억하자. 감사 기록이 법적 요구라 "주문 시도 자체"를 반드시 남겨야 한다면, 바깥이 롤백되어도 남아야 하므로 NESTED는 탈락하고 REQUIRES_NEW나 경계 분리 중에서 골라야 한다. 감사 기록이 주문 행을 외래 키로 참조하거나 같은 행을 갱신해야 한다면 REQUIRES_NEW는 가시성과 락 대기 문제에 부딪히므로, 주문을 먼저 커밋하는 경계 분리가 자연스럽다. JPA를 쓴다면 쓰기 지연 때문에 오류가 나는 시점이 메서드 호출이 아니라 플러시일 수 있다는 점까지 넣어서 catch의 위치를 정해야 한다.

    1번: 안쪽 REQUIRES_NEW 트랜잭션은 여전히 conn1에서 독립적으로 롤백되고, "Resuming suspended transaction" 뒤에 예외가 서비스 메서드로 전달된다. 이번에는 잡는 코드가 없으므로 예외는 서비스 프록시의 인터셉터에 도착하고, 런타임 예외이므로 바깥 트랜잭션도 롤백된다("Initiating transaction rollback" → conn0 롤백). 호출자는 DataIntegrityViolationException을 그대로 받고 두 테이블 모두 비어 있다. 안쪽이 독립적으로 롤백되었다고 해서 예외의 전파가 멈추지는 않는다는 점이 핵심이다. 이때 바깥 롤백은 rollback-only 표시가 아니라 롤백 규칙 때문이므로 UnexpectedRollbackException은 나지 않는다.

    2번: 호출자가 받는 예외와 데이터는 바뀌지 않는다. 감사 저장소의 참여 트랜잭션이 롤백될 때 processRollback은 rollback-only를 표시하고, failEarlyOnGlobalRollbackOnly가 참이면 unexpectedRollback을 거짓으로 되돌리는 코드를 건너뛴다. 하지만 이 호출의 두 번째 인자 unexpected가 처음부터 false였으므로 여기서 UnexpectedRollbackException이 나지는 않고, 원래 예외가 서비스로 전달된다. 서비스가 이를 잡고 커밋을 요청하면 commit이 전역 표시를 보고 processRollback(status, true)를 호출하므로, 경우 5와 똑같이 바깥에서 UnexpectedRollbackException이 나고 데이터는 남지 않는다. 이 스위치가 차이를 만드는 것은 이미 표시된 트랜잭션에 참여한 다른 안쪽 범위가 정상 반환해 commit을 호출하는 경우다. 그때 commit은 전역 표시를 보고 그 참여자의 상태로 processRollback(status, true)를 부르는데, 참여자 분기에서 스위치가 참이면 unexpectedRollback을 지우지 않으므로 그 안쪽 경계에서 예외가 더 일찍 난다.

    3번: 남는 데이터만 보면 경우 6과 같지만, 이유는 전혀 다르다. this.recordAudit(msg)는 프록시가 아니라 대상 객체의 메서드를 직접 부르므로 TransactionInterceptor가 개입하지 않고, REQUIRES_NEW 설정은 읽히지도 않는다. 실제로 이렇게 바꿔 실행하면 "Suspending" 로그가 나오지 않고, recordAudit 안의 where() 출력은 바깥 트랜잭션 이름 placeSelfCall과 conn-1을 보여 준다. 감사 INSERT가 바깥 트랜잭션의 커넥션에서 실행된 것이다. 실패한 예외는 어떤 트랜잭션 프록시도 거치지 않고 바로 catch에 도착하므로 rollback-only 표시도 남지 않는다. 그래서 바깥은 정상 커밋되고, 실패한 INSERT는 행을 남기지 않아 결과가 orders=[I], audit_log=[] 꼴로 나온다(H2 2.4.240에서 실패한 문장 뒤에도 트랜잭션을 커밋할 수 있음을 확인했다). 그러나 이것은 우연이다. 짧은 메시지로 실행하면 감사 INSERT는 바깥과 같은 트랜잭션에서 성공하므로, 바깥이 나중에 롤백되면 감사 기록도 함께 사라진다. 독립 트랜잭션이라는 설계 의도는 사라지고 REQUIRED처럼 동작하는 코드다. 참고로 이 코드를 옮길 때 orders 필드(프록시)를 통해 저장소 내부의 JdbcTemplate 필드에 직접 접근하게 만들면, 실험에서는 CGLIB 프록시 객체의 필드가 초기화되지 않아 NullPointerException이 났다. 서비스에 JdbcTemplate을 따로 주입해야 한다.

    4번: 최악의 경우 처음 들어온 10개 요청이 바깥 트랜잭션용으로 커넥션 10개를 모두 가져가고, 나머지 10개 요청은 바깥 트랜잭션용 커넥션조차 얻지 못해 기다린다. 커넥션을 가진 10개 스레드는 각자 saveInNewTx에서 두 번째 커넥션을 기다리지만 반납되는 커넥션이 없으므로 30초 뒤 모두 CannotCreateTransactionException을 받는다. 서비스가 catch (RuntimeException e)로 이 예외를 삼키므로 바깥 트랜잭션은 정상 커밋되고, 감사 기록 없는 주문 10건이 남는다. 바깥 커넥션을 기다리던 나머지 요청들도 같은 30초 제한을 받으므로, 커넥션이 반납되기 전에 시간이 다 되면 서비스 프록시가 트랜잭션을 시작하지 못해 CannotCreateTransactionException으로 실패한다. 이 예외는 서비스 메서드 안의 catch보다 바깥에서 나므로 호출자에게 그대로 전달된다. 제때 커넥션을 얻은 요청은 다시 같은 상황에 빠질 수 있다. 복구용 catch를 데이터 오류처럼 의도한 예외로 좁히고, 풀 크기를 동시 스레드 수보다 크게 하거나 구조를 바꿔야 한다.

     REQUIRED로 참여한 저장소 메서드가 런타임 예외를 던졌고 서비스가 이를 잡아 정상 반환했다. 서비스의 커밋이 롤백으로 바뀌는 직접적인 이유는 무엇인가? 서비스 프록시가 메서드 안에서 발생한 모든 예외를 기억해 두었다가 커밋 시점에 롤백하기 때문이다 데이터베이스가 실패한 INSERT 문장을 이유로 트랜잭션 전체를 자동으로 롤백했기 때문이다 저장소 프록시가 참여 트랜잭션을 롤백하려 할 때 실제 롤백 대신 공유 커넥션 홀더에 rollback-only를 표시했고, 커밋이 이 표시를 확인했기 때문이다 예외를 잡는 순간 스프링이 트랜잭션을 즉시 롤백하고 커넥션을 반납하기 때문이다 참여자의 rollback은 newTransaction=false이므로 doSetRollbackOnly로 커넥션 홀더에 표시만 남긴다. 바깥의 commit은 isGlobalRollbackOnly를 확인해 롤백하고 UnexpectedRollbackException을 던진다. 서비스 프록시는 메서드 안에서 잡힌 예외를 따로 기록하지 않는다. 롤백을 결정한 것도 데이터베이스가 아니라 스프링이다. 경우 5의 로그에서 "Global transaction is marked as rollback-only but transactional code requested commit" 다음에야 "Initiating transaction rollback"이 나온다. catch 시점에는 롤백도 커넥션 반납도 일어나지 않는다. REQUIRES_NEW로 선언된 메서드가 호출될 때 DataSourceTransactionManager가 하는 일로 옳은 것은? 바깥 트랜잭션을 먼저 커밋하고 같은 커넥션으로 새 트랜잭션을 시작한다 바깥 커넥션 홀더를 스레드 자원 맵에서 떼어 보관하고, 풀에서 새 커넥션을 얻어 독립된 트랜잭션을 시작한다 바깥 커넥션에 세이브포인트를 만들고 그 지점부터 새 논리 트랜잭션을 시작한다 새 스레드를 만들어 그 스레드에서 안쪽 메서드를 실행한다 doSuspend는 unbindResource로 바깥 홀더를 떼어 반환하고, doBegin은 홀더가 없으므로 새 커넥션을 얻는다. 바깥 트랜잭션은 커밋되지 않은 채 보관된다. 세이브포인트를 만드는 것은 NESTED이고, 실행은 같은 스레드에서 동기적으로 이루어진다. 바깥 트랜잭션이 주문 행 하나를 UPDATE한 직후, 같은 요청에서 REQUIRES_NEW 메서드가 같은 행을 UPDATE한다. MySQL InnoDB 기본 설정에서 예상되는 결과는? 같은 스레드에서 실행되므로 안쪽 트랜잭션이 바깥의 락을 공유해 바로 성공한다 InnoDB가 교착 상태를 즉시 감지해 둘 중 하나를 롤백한다 안쪽 UPDATE가 바깥의 변경을 덮어쓰고, 바깥 커밋 시 충돌 예외가 난다 안쪽 트랜잭션이 바깥이 잡은 행 락을 기다리다 innodb_lock_wait_timeout(기본 50초) 뒤 오류 1205로 실패한다 데이터베이스에게 두 트랜잭션은 서로 다른 세션이다. 바깥은 안쪽이 반환되어야 진행하므로 락을 풀 수 없고, 대기 그래프에서 바깥 트랜잭션은 락을 기다리는 쪽이 아니므로 데이터베이스가 볼 수 있는 순환이 없다. 결국 락 대기 시간 제한까지 기다린다. 이 회차의 H2 실험에서도 LOCK_TIMEOUT 뒤 시간 초과 오류가 났다. 감사 기록 실패만 되돌리고 주문은 커밋하되, 커넥션을 하나만 쓰고 싶다. 다만 주문이 롤백되면 감사 기록도 함께 사라져도 된다. 가장 알맞은 선택은? 감사 기록 저장을 NESTED로 선언하고 서비스에서 예외를 잡는다(JDBC 세이브포인트 지원 필요) 감사 기록 저장을 REQUIRED로 두고 서비스에서 예외를 잡는다 감사 기록 저장을 REQUIRES_NEW로 선언하고 풀 크기를 1로 설정한다 트랜잭션 매니저의 failEarlyOnGlobalRollbackOnly를 true로 바꾼다 NESTED는 같은 커넥션에 세이브포인트를 만들고 실패 시 세이브포인트까지만 되돌리며 rollback-only를 남기지 않는다. 안쪽 작업이 바깥과 함께 커밋·롤백된다는 성질도 조건에 맞는다. REQUIRED는 경우 5처럼 UnexpectedRollbackException이 나고, REQUIRES_NEW는 커넥션 두 개가 필요해 풀 크기 1에서는 시작조차 못 한다. failEarlyOnGlobalRollbackOnly는 예외가 나는 위치만 바꾼다.
    물리 트랜잭션(physical transaction)
    데이터베이스 커넥션 위에서 실제로 시작되고 커밋·롤백되는 트랜잭션. JDBC에서는 자동 커밋을 끈 시점부터 commit() 또는 rollback()까지다.
    논리 트랜잭션(logical transaction)
    @Transactional 경계마다 만들어지는 트랜잭션 범위. REQUIRED에서는 여러 논리 트랜잭션이 하나의 물리 트랜잭션에 대응된다.
    rollback-only
    트랜잭션이 커밋될 수 없고 롤백만 가능하다는 표시. 스프링에서는 참여 트랜잭션 실패 시 커넥션 홀더나 JPA의 EntityTransaction에 걸리고, 커밋 시점에 확인된다.
    UnexpectedRollbackException
    커밋을 요청했지만 rollback-only 표시 때문에 실제로는 롤백되었음을 호출자에게 알리는 스프링의 런타임 예외.
    보류와 재개(suspend/resume)
    REQUIRES_NEW나 NOT_SUPPORTED에서 현재 트랜잭션의 스레드 바인딩 자원과 동기화를 떼어 보관했다가, 안쪽 범위가 끝나면 되돌려 놓는 동작.
    세이브포인트(savepoint)
    트랜잭션 중간에 표시해 두는 지점. 그 지점까지만 부분 롤백할 수 있으며, 스프링의 NESTED 전파가 JDBC 세이브포인트를 쓴다.
    트랜잭션 동기화(transaction synchronization)
    TransactionSynchronizationManager가 ThreadLocal로 커넥션 홀더 같은 자원과 트랜잭션 정보를 스레드에 묶어, 같은 스레드의 데이터 접근 코드가 같은 트랜잭션 자원을 쓰게 하는 장치.
    락 대기 시간 초과(lock wait timeout)
    다른 트랜잭션이 가진 행 락을 기다리는 최대 시간. MySQL InnoDB에서는 innodb_lock_wait_timeout(기본 50초)이고, 초과하면 오류 1205가 난다.
