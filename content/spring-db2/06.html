    이 회차의 질문: 문자열 쿼리는 언제 틀렸다고 알려 주는가

    이 권은 같은 저장소 기능을 여러 기술로 다시 구현해 왔다. 01회의 JdbcTemplate은 SQL 문자열을, 03회의 MyBatis는 XML에 적은 SQL을, 04회의 JPA는 JPQL 문자열을 썼다. 05회의 스프링 데이터 JPA는 메서드 이름에서 쿼리를 만들어 주었지만, 조건이 몇 개만 늘어도 이름이 감당할 수 없게 길어지고, 어떤 조건을 넣을지가 실행 시점에 정해지는 쿼리는 메서드 이름 하나로 표현할 수 없었다. 기술은 달라도 공통점이 하나 있다. 쿼리는 결국 문자열로 표현되고, 그 문자열의 문법과 의미를 확인하는 것은 자바 컴파일러가 아니다.

    자바 컴파일러에게 "select b from Book b where b.titel like :kw"는 그냥 String 상수다. 엔티티 필드 이름이 title인데 titel로 잘못 적어도, 숫자 필드를 문자열과 비교해도 컴파일은 성공한다. 이 문자열을 처음으로 해석하는 것은 실행 중에 EntityManager.createQuery()가 호출될 때의 JPA 구현체다. Hibernate 6.0부터는 HQL과 Criteria 쿼리를 SQM(Semantic Query Model)이라는 전용 트리 구조로 모델링하는데, 문자열 JPQL은 이 단계에서 파싱되고 엔티티 메타데이터와 대조된다. 오타는 바로 이때, 즉 그 코드 경로가 실제로 실행되는 순간에야 예외로 드러난다.

    그 코드 경로가 사용자가 검색 조건을 특정하게 조합했을 때만 실행되는 분기라면 문제가 커진다. 테스트가 그 조합을 밟지 않으면 오류는 운영 환경에서 처음 발견된다. 이 회차는 이 문제를 Querydsl이 어떻게 컴파일 시점으로 끌어오는지, 그리고 그 대가로 무엇을 지불하는지를 다룬다. 후반부에서는 지금까지 비교한 기술들을 실제 애플리케이션에서 어떻게 조합할지, 구조의 순수함과 실용성 사이의 트레이드오프를 따진다.

    예제 도메인은 이 회차에서 새로 정한다. 도서(Book) 엔티티 하나에 제목(title), 가격(price), 재고(stock)가 있고, 검색 조건은 "제목에 포함된 키워드"와 "최대 가격" 두 가지다. 두 조건 모두 비어 있을 수 있다. 조건이 둘뿐인데도 조합은 네 가지가 되고, 이것이 동적 쿼리 문제를 보여 주기에 충분하다.

    package shop;

import jakarta.persistence.*;

@Entity
public class Book {
    @Id @GeneratedValue
    private Long id;
    private String title;
    private int price;
    private Integer stock;

    protected Book() {}                       // JPA가 리플렉션으로 쓰는 기본 생성자

    public Book(String title, int price, Integer stock) {
        this.title = title; this.price = price; this.stock = stock;
    }

    public void changePrice(int newPrice) { this.price = newPrice; }

    public Long getId() { return id; }
    public String getTitle() { return title; }
    public int getPrice() { return price; }
    public Integer getStock() { return stock; }
}
    public record BookSearch(String titleKeyword, Integer maxPrice) {}   // 둘 다 null일 수 있다

    기존 방식의 문제 1: 문자열 조립과 파라미터 바인딩이 따로 논다

    JPQL 문자열로 동적 쿼리를 만들면 두 가지 일을 따로 해야 한다. 조건에 따라 문자열에 절을 붙이는 일과, 붙인 절에 들어 있는 파라미터에 값을 바인딩하는 일이다. 같은 조건 판단(keyword != null)이 두 군데에 나타나고, 둘이 어긋나면 실행 시점에 실패한다. 먼저 가장 흔한 실수부터 직접 실행해 보자.

    String kw = null; Integer max = 30000;
String jpql = "select b from Book b";
if (kw != null)  jpql += " where b.title like :kw";
if (max != null) jpql += " and b.price <= :max";
System.out.println(jpql);
    select b from Book b and b.price <= :max

    두 번째 조건은 "앞에 where가 이미 붙어 있다"고 가정했는데, 첫 번째 조건이 비어 있으면 그 가정이 깨진다. 결과 문자열에는 where 없이 and가 나온다. 컴파일러는 아무 경고도 하지 않고, 이 문자열은 createQuery()에서 구문 오류로 실패한다. 네 가지 조합 중 하나에서만 터지는 버그다. 이를 피하려면 "지금까지 조건을 붙였는가"를 기억하는 플래그를 두거나, where 1=1처럼 항상 참인 조건을 먼저 넣고 뒤에 and를 붙이는 요령을 쓴다. 어느 쪽이든 쿼리의 의미가 아니라 문자열의 모양을 관리하는 코드가 늘어난다.

    파라미터 바인딩도 같은 분기를 반복해야 한다. if (kw != null) query.setParameter("kw", "%" + kw + "%")를 문자열 조립과 똑같은 조건으로 다시 써야 하고, 조립 쪽에서 조건을 바꾸고 바인딩 쪽을 깜빡하면 "쿼리에 없는 파라미터에 값을 넣는" 실패나 "쿼리에 있는 파라미터에 값이 없는" 실패가 실행 시점에 난다. 문자열과 바인딩이 같은 사실(어떤 조건이 들어가는가)을 두 번 표현하기 때문에 생기는 문제다. 설계 원칙으로 말하면, 하나의 결정이 두 곳에 흩어져 있어 둘을 함께 바꿔야 하는 구조다.

    필드 이름 변경도 같은 종류의 문제다. IDE의 이름 변경 리팩터링은 자바 식별자를 추적해 바꾸지만, 문자열 안의 b.title은 식별자가 아니라 문자 나열이다. 엔티티 필드를 title에서 name으로 바꾸면 컴파일은 그대로 성공하고, 그 JPQL이 실행되는 순간 실패한다. 스프링 데이터 JPA의 메서드 이름 쿼리도 필드 이름에 묶여 있지만, 자바 컴파일러가 아니라 스프링 데이터가 리포지토리를 초기화할 때 해석한다는 점에서 역시 컴파일 시점의 보호는 아니다.

    기존 방식의 문제 2: JPA Criteria는 타입을 묻지만 검사하지는 않는다

    JPA 표준에도 문자열 대신 자바 객체로 쿼리를 만드는 방법이 있다. Criteria API다. CriteriaBuilder로 조건 객체를 만들고 목록에 담아 where에 넘기면, 문자열 조립의 where/and 문제는 사라진다. 그런데 속성 이름을 문자열로 지정하는 형태로 쓰면, 타입 안전성은 기대만큼 확보되지 않는다. 아래 코드를 jakarta.persistence-api 3.2.0 jar에 대고 직접 컴파일해 보았다. 두 군데에 일부러 실수를 넣었다.

    CriteriaBuilder cb = em.getCriteriaBuilder();
CriteriaQuery cq = cb.createQuery(Book.class);
Root b = cq.from(Book.class);
List conds = new ArrayList<>();
if (keyword != null)  conds.add(cb.like(b.get("titel"), "%" + keyword + "%"));  // 오타
if (maxPrice != null) conds.add(cb.le(b.get("title"), maxPrice));              // 문자열 필드를 숫자와 비교
cq.select(b).where(conds.toArray(new Predicate[0]));
return em.createQuery(cq).getResultList();

    이 코드는 아무 오류 없이 컴파일된다. 이유는 Path 인터페이스의 시그니처에 있다. javap로 보면 public abstract Path get(String)이다. 반환 타입의 Y는 인자 문자열과 아무 관계가 없는 제네릭 메서드의 타입 변수이고, 컴파일러는 호출 위치의 기대 타입으로부터 Y를 추론한다. cb.like(...)의 첫 인자 자리가 Expression을 기대하면 Y는 String이 되고, cb.le(Expression, Number)의 자리에서는 Number 계열로 추론된다. 컴파일러는 "titel이라는 속성이 실제로 있는가", "title이 정말 숫자인가"를 알 방법이 없다. 결국 확인은 실행 시점의 JPA 구현체 몫이다.

    JPA 명세는 이 공백을 메우기 위해 정적 메타모델(static metamodel)을 정의한다. 애너테이션 프로세서가 엔티티마다 Book_ 같은 클래스를 만들고, b.get(Book_.title)처럼 문자열 대신 메타모델 속성을 넘기면 컴파일러가 타입을 검사할 수 있다. 다만 Criteria API는 조건 하나를 만드는 데에도 빌더 호출과 제네릭이 겹겹이 쌓여, 완성된 코드를 보고 어떤 쿼리인지 읽어 내기 어렵다. 타입 안전성과 가독성을 동시에 얻는 다른 방법이 필요하고, 그 자리를 채운 것이 Querydsl이다. 흥미롭게도 Querydsl도 정적 메타모델과 같은 원리, 즉 "애너테이션 프로세서로 엔티티의 구조를 자바 코드로 미리 만들어 둔다"를 쓴다. 차이는 그렇게 만든 클래스 위에 어떤 API를 올리느냐에 있다.

    Querydsl의 해결: 쿼리를 자바 객체의 트리로 만든다

    Querydsl은 쿼리를 문자열이 아니라 자바 객체의 조합으로 표현하는 라이브러리다. 이름의 DSL은 도메인 특화 언어(Domain Specific Language)의 약자로, 쿼리라는 한 가지 일에 맞춘 작은 언어를 자바 메서드 호출로 흉내 낸다는 뜻이다. 앞의 동적 검색을 Querydsl로 쓰면 이렇게 된다.

    List result = query
        .select(book)
        .from(book)
        .where(titleContains(cond.titleKeyword()), priceAtMost(cond.maxPrice()))
        .orderBy(book.price.asc())
        .fetch();

    읽는 순서가 JPQL과 거의 같아서 무슨 쿼리인지 바로 보인다. 그러면서도 book.price는 문자열이 아니라 컴파일러가 아는 필드다. 이것이 가능한 구조는 세 층으로 나눠 볼 수 있다.

    • Q타입(query type): 엔티티 Book마다 생성되는 QBook 클래스. 엔티티의 각 필드에 대응하는 경로(path) 객체를 필드로 갖는다. book.price는 QBook의 NumberPath 필드다.
    • 표현식 모델(expression model): book.price.loe(30000) 같은 호출은 즉시 무언가를 실행하지 않고 "연산자 LOE, 피연산자는 경로 book.price와 상수 30000"이라는 노드 객체를 만든다. 쿼리 전체가 이런 노드들의 트리다. 이 층은 querydsl-core 모듈에 있고 특정 저장소 기술과 무관하다.
    • 직렬화기(serializer)와 쿼리 실행: querydsl-jpa 모듈의 JPQLSerializer가 트리를 JPQL 문자열로 바꾸고, JPAQuery가 그 문자열과 파라미터 값을 EntityManager에 넘긴다. 같은 표현식 모델을 SQL로 직렬화하는 querydsl-sql 모듈도 있다. Spring Boot 3.5의 의존성 관리 목록에는 querydsl-jpa, querydsl-sql, querydsl-mongodb 등 여러 모듈이 버전 5.1.0으로 올라 있다.

    여기서 중요한 사실은 Querydsl을 쓴다고 JPQL이 사라지지 않는다는 점이다. Querydsl JPA는 JPQL 빌더다. 최종적으로 Hibernate가 받는 것은 여전히 JPQL 문자열이고, Hibernate는 그것을 이전과 똑같이 파싱한다. 달라진 것은 그 문자열을 사람이 아니라 타입 검사를 통과한 객체 트리가 기계적으로 만든다는 점이다. 오타와 타입 불일치는 트리를 만드는 자바 코드 단계에서 컴파일러가 걸러 내고, 직렬화기는 공백과 where/and 배치를 규칙대로 처리한다. 사람이 문자열 모양을 관리할 일이 없어진다.

    일상에서 가져온 비유손으로 쓴 주문서와 주문 키오스크

    손으로 쓴 주문서는 아무 글자나 적을 수 있어서, 메뉴에 없는 음식 이름을 써도 종이는 받아 준다. 틀린 것은 주방에 도착해서야 드러난다. 키오스크는 메뉴판에 있는 버튼만 누를 수 있으니 없는 메뉴를 주문하는 일 자체가 불가능하고, 주방에는 정해진 형식의 주문서가 출력된다. Q타입이 메뉴판이고, 직렬화기가 주문서 출력기다. 비유가 깨지는 지점도 있다. 키오스크 메뉴판은 가게가 바뀌면 즉시 갱신되지만, Q타입은 엔티티를 바꾼 뒤 다시 컴파일해야 갱신된다. 메뉴판이 낡으면 키오스크도 낡은 주문을 받는다.

    Q타입은 어디서 오는가: javac의 애너테이션 처리 라운드

    Q타입은 사람이 쓰지 않는다. 컴파일 중에 애너테이션 프로세서(annotation processor)가 만든다. 애너테이션 프로세서는 javac에 꽂아 쓰는 플러그인으로, 자바 표준 API인 javax.annotation.processing 패키지(JSR 269, Pluggable Annotation Processing API)로 작성된다. javac는 소스를 파싱한 뒤 어떤 애너테이션이 쓰였는지 모아서 그 애너테이션을 처리하겠다고 선언한 프로세서를 호출한다. 프로세서는 소스의 구조(클래스, 필드, 타입)를 읽고, Filer 인터페이스로 새 파일을 만들 수 있다. 중요한 제약이 하나 있다. 표준 API는 새 파일을 만드는 기능만 제공하고, 이미 있는 소스나 클래스를 고치는 기능은 없다. 그래서 Querydsl은 Book을 바꾸는 대신 옆에 QBook이라는 새 클래스를 만든다.

    새로 만든 소스도 컴파일해야 하므로 javac는 처리를 라운드(round) 단위로 반복한다. 한 라운드에서 생성된 파일은 다음 라운드의 입력이 되고, 더 이상 새 파일이 생기지 않으면 마지막 라운드를 돌고 끝난다. querydsl-apt 5.1.0의 jakarta 분류자(classifier) jar를 프로세서로 지정하고 -XprintRounds 옵션으로 이 과정을 직접 출력해 보았다(JDK 21.0.13, Temurin).

    javac -cp "$CP" -processor com.querydsl.apt.jpa.JPAAnnotationProcessor \
      -XprintRounds -s gen -d out src/shop/Book.java
    Round 1:
	input files: {shop.Book}
	annotations: [jakarta.persistence.Entity, jakarta.persistence.Id, jakarta.persistence.GeneratedValue]
	last round: false
Round 2:
	input files: {shop.QBook}
	annotations: [javax.annotation.processing.Generated]
	last round: false
Round 3:
	input files: {}
	annotations: []
	last round: true

    라운드 1의 입력은 우리가 쓴 Book이고, 거기서 발견된 애너테이션은 @Entity, @Id, @GeneratedValue다. JPAAnnotationProcessor는 @Entity가 붙은 타입을 찾아 QBook.java를 -s로 지정한 디렉터리에 쓴다. 라운드 2의 입력은 방금 생성된 QBook이고, 거기에는 @Generated 애너테이션 하나가 붙어 있다. 라운드 2에서는 새 파일이 생기지 않았으므로 라운드 3이 마지막 라운드가 된다. 최종적으로 out 디렉터리에는 Book.class와 QBook.class가 함께 생긴다. 생성된 소스는 이렇다.

    package shop;

import static com.querydsl.core.types.PathMetadataFactory.*;
import com.querydsl.core.types.dsl.*;
import com.querydsl.core.types.PathMetadata;
import javax.annotation.processing.Generated;
import com.querydsl.core.types.Path;

@Generated("com.querydsl.codegen.DefaultEntitySerializer")
public class QBook extends EntityPathBase {

    private static final long serialVersionUID = 2144499457L;

    public static final QBook book = new QBook("book");

    public final NumberPath id = createNumber("id", Long.class);
    public final NumberPath price = createNumber("price", Integer.class);
    public final NumberPath stock = createNumber("stock", Integer.class);
    public final StringPath title = createString("title");

    public QBook(String variable) {
        super(Book.class, forVariable(variable));
    }
    // ... Path, PathMetadata를 받는 생성자 두 개 생략
}

    몇 가지를 읽어 낼 수 있다. 첫째, 엔티티의 int price도 Integer stock도 모두 NumberPath가 되었다. 기본형은 제네릭 타입 인자가 될 수 없으므로 래퍼 타입으로 올라간다. 둘째, String 필드는 StringPath가 되어 like, contains, startsWith 같은 문자열 전용 연산을 갖고, NumberPath는 loe, goe, between 같은 비교 연산을 갖는다. 필드의 자바 타입이 쓸 수 있는 연산의 집합을 결정하는 것이다. 셋째, public static final QBook book이라는 기본 인스턴스가 있다. JPQL의 별칭(alias) book에 해당하는 객체로, 정적 필드 초기화 식은 컴파일되면 클래스 초기화 메서드()에 들어가므로, QBook 클래스가 처음 초기화될 때 한 번 만들어진다. 같은 엔티티를 한 쿼리에서 두 번 써야 할 때(자기 자신과의 조인 등)는 new QBook("other")처럼 별칭이 다른 인스턴스를 직접 만든다.

    넷째, 생성된 코드의 @Generated는 javax.annotation.processing.Generated다. 이 애너테이션은 JDK 9부터 java.compiler 모듈에 포함된 표준 애너테이션이라 별도 의존성이 필요 없다. 실제로 jakarta.annotation-api jar를 프로세서 경로에서 빼고 다시 컴파일해도 QBook.java는 똑같이 생성되었다(JDK 21 기준). 반면 jakarta.persistence-api를 프로세서 경로에서 빼면 결과가 달라진다. 이것은 다음 절에서 본다.

    마지막으로, -processor 옵션 없이도 프로세서는 실행된다. querydsl-apt jar 안에는 META-INF/services/javax.annotation.processing.Processor 파일이 있고 그 내용이 com.querydsl.apt.jpa.JPAAnnotationProcessor 한 줄이다. javac는 프로세서 경로의 jar에서 이 서비스 파일을 찾아 ServiceLoader 방식으로 프로세서를 발견한다. 빌드 도구 설정에서 프로세서 클래스 이름을 적지 않아도 되는 이유가 이것이다.

    Book.java가 라운드 1에서 프로세서를 거쳐 QBook.java를 만들고, 라운드 2에서 QBook.java가 컴파일 입력이 되며, 라운드 3에서 끝나 두 클래스 파일이 나오는 흐름. 가로로 긴 순서도. 왼쪽에 "Book.java" 문서 아이콘. 그 오른쪽에 큰 상자 "javac" 안에 세로로 세 칸 "라운드 1", "라운드 2", "라운드 3"이 쌓여 있다. "라운드 1" 칸 옆에 톱니바퀴 모양 "JPAAnnotationProcessor"가 붙어 있고, 거기서 화살표가 나가 문서 아이콘 "QBook.java (생성)"으로 향한다. "QBook.java (생성)"에서 다시 화살표가 "라운드 2" 칸으로 들어간다. "라운드 3" 칸에는 "새 파일 없음 → 종료"라고 적혀 있다. javac 상자 오른쪽으로 화살표가 나가 두 개의 파일 아이콘 "Book.class", "QBook.class"를 가리킨다. 프로세서 아이콘 위에 작은 상자 "META-INF/services로 발견"이 점선으로 연결되어 있다. 배경은 흰색, 선은 짙은 회색, 생성된 파일은 연한 파란색으로 강조. Q타입은 컴파일 중에 생성되고 같은 javac 실행 안에서 다음 라운드에 컴파일된다.

    Querydsl 설정: 두 개의 클래스패스와 jakarta 분류자

    Gradle에서 Querydsl을 설정할 때 핵심은 "컴파일 클래스패스"와 "애너테이션 프로세서 경로"가 서로 다른 설정이라는 점이다. Gradle 문서는 annotationProcessor 구성을 "프로젝트 소스를 컴파일하는 동안 사용되는 애너테이션 프로세서"로 설명하고, 애너테이션 프로세서는 프로세서 경로에 따로 선언해야 한다고 적는다. 애플리케이션 코드가 쓰는 라이브러리(implementation)와 컴파일러 플러그인이 실행될 때 필요한 라이브러리(annotationProcessor)는 서로를 보지 못한다. Spring Boot 3.x 프로젝트의 설정은 다음과 같은 모양이 된다.

    dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-data-jpa'

    // 실행 시점에 쓰는 Querydsl JPA (jakarta.* 패키지용 분류자)
    implementation 'com.querydsl:querydsl-jpa:5.1.0:jakarta'

    // 컴파일 중에 Q타입을 만드는 프로세서와, 프로세서가 실행될 때 필요한 API
    annotationProcessor 'com.querydsl:querydsl-apt:5.1.0:jakarta'
    annotationProcessor 'jakarta.persistence:jakarta.persistence-api'
}

    버전 뒤의 :jakarta는 Maven의 분류자다. 같은 좌표(그룹, 아티팩트, 버전)에 jar가 여러 개 있을 때 그중 하나를 고르는 꼬리표다. Querydsl 5.0.0 릴리스 노트는 새 Jakarta EE 릴리스의 jakarta.* 패키지를 jakarta 분류자로 지원한다고 적고 있다. 분류자 없는 기본 jar는 옛 javax.persistence 패키지를 기준으로 하므로, jakarta.persistence를 쓰는 Spring Boot 3.x(Hibernate 6.x)에서는 런타임 라이브러리와 프로세서 양쪽 모두 jakarta 분류자를 붙여야 한다. 한쪽만 붙이면 패키지가 어긋난다. 분류자 없는 querydsl-apt의 프로세서는 javax.persistence.Entity를 찾고, 분류자 없는 querydsl-jpa는 javax.persistence.EntityManager를 받는다. 버전 번호는 Spring Boot의 의존성 관리에 들어 있으므로(Boot 3.5 기준 5.1.0) 생략할 수도 있지만, 분류자를 붙인 좌표는 버전과 함께 적는 것이 명확하다.

    두 번째 annotationProcessor 줄이 왜 필요한지는 실험으로 확인할 수 있다. 컴파일 클래스패스(-cp)에는 jakarta.persistence-api를 두고, 프로세서 경로(-processorpath)에서만 그것을 빼고 컴파일했다.

    소스 코드 Book.java가 @Entity를 쓰는 것은 컴파일 클래스패스로 해결된다. 하지만 프로세서 자신은 별도의 클래스 로더에서 실행되는 자바 프로그램이고, 그 코드 안에서 jakarta.persistence.Entity 클래스 객체를 직접 참조한다. 프로세서를 로드한 클래스 로더가 그 클래스를 찾지 못하면 JVM은 해당 심볼을 해석(resolve)하는 순간 NoClassDefFoundError를 던진다. 자바 기본편에서 본 클래스 로딩 규칙이 빌드 설정 한 줄의 이유가 된다. Gradle의 annotationProcessor 구성이 바로 이 -processorpath에 해당한다.

    생성된 소스가 놓이는 위치도 알아 두어야 한다. Gradle의 CompileOptions.generatedSourceOutputDirectory 기본값은 ${project.layout.buildDirectory}/generated/sources/annotationProcessor/${sourceDirectorySet.name}/${sourceSet.name}이다. main 소스 세트의 자바 소스라면 build/generated/sources/annotationProcessor/java/main이 된다. 여기서 세 가지 실무 규칙이 나온다.

    • Q타입은 커밋하지 않는다. 빌드 산출물이고 build 아래에 생기므로 보통 이미 버전 관리에서 제외되어 있다. 생성 위치를 소스 디렉터리 안으로 바꿨다면 그 디렉터리를 무시 목록에 넣어야 한다. 커밋된 Q타입은 엔티티와 어긋난 채로 남을 수 있다.
    • 엔티티를 바꾸면 다시 컴파일해야 Q타입이 바뀐다. 필드를 지웠는데 옛 Q타입이 남아 있으면, 그 Q타입 필드를 쓰는 쿼리는 컴파일되지만 실행 시점의 JPQL에는 존재하지 않는 속성이 들어간다. 이상한 컴파일 결과가 보이면 빌드 디렉터리를 지우고(clean) 다시 빌드하는 것이 첫 번째 확인이다.
    • IDE가 직접 빌드할 때는 생성 위치가 다를 수 있다. IDE가 Gradle에 빌드를 맡기는지, 자체 컴파일러로 빌드하는지에 따라 생성 디렉터리가 달라지고, 두 위치에 같은 클래스가 생기면 중복 클래스 오류가 난다. 빌드 주체를 하나로 정해 두는 편이 단순하다.
    Querydsl의 원본 저장소(querydsl/querydsl)는 2024년 1월의 5.1.0이 마지막 릴리스다. 이후 OpenFeign 조직이 그룹 ID를 바꾼 포크(io.github.openfeign.querydsl)를 유지하고 있으며, 그 README는 원본 프로젝트의 활동이 멈췄다는 것을 포크 이유로 든다. 이 회차의 예제와 바이트코드 분석은 원본 5.1.0(jakarta 분류자) 기준이다.

    표현식 트리: book.price.loe(30000)는 메모리에 무엇을 만드는가

    이제 Q타입 위에서 조건식을 만들 때 실제로 어떤 객체가 생기는지 보자. 다음 코드는 조건 하나를 만들고 그 내부를 들여다본다. Querydsl의 조건식은 Operation 인터페이스를 구현하므로 연산자와 피연산자 목록을 꺼낼 수 있다.

    BooleanExpression e = book.price.loe(30000);
Operation op = (Operation) e;
System.out.println("operator=" + op.getOperator() + " args=" + op.getArgs()
    + " argTypes=" + op.getArg(0).getClass().getSimpleName()
    + "," + op.getArg(1).getClass().getSimpleName());
System.out.println("path=" + book.price + " parent=" + book.price.getMetadata().getParent());
    operator=LOE args=[book.price, 30000] argTypes=PathImpl,ConstantImpl
path=book.price parent=book

    loe는 "less than or equal"의 줄임이다. 호출 결과는 비교를 수행한 결과(true/false)가 아니라, 연산자 LOE와 두 피연산자를 담은 노드다. 첫 번째 피연산자는 경로 노드(PathImpl)로, 자신의 이름 price와 부모 경로 book에 대한 메타데이터를 갖는다. 두 번째 피연산자는 상수 노드(ConstantImpl)로, 자바 값 30000을 감싼다. 이 시점에 데이터베이스와는 아무 통신도 없다. 쿼리는 아직 존재하지 않고, 쿼리를 묘사하는 객체 그래프만 힙에 생긴 상태다.

    힙(heap)에 만들어진 조건식 객체 그래프

  BooleanOperation  (operator = Ops.LOE)
     ├─ arg[0] ──▶ PathImpl  "price"
     │                └─ metadata.parent ──▶ QBook "book"  (static final, 클래스 초기화 때 1회 생성)
     └─ arg[1] ──▶ ConstantImpl  30000 (Integer)

  title.like("%자바%") and price.loe(30000) 를 where에 넘기면:

  BooleanOperation (Ops.AND)
     ├─ BooleanOperation (Ops.LIKE)  [PathImpl "title", ConstantImpl "%자바%"]
     └─ BooleanOperation (Ops.LOE)   [PathImpl "price", ConstantImpl 30000]

    이 구조가 주는 성질이 두 가지 있다. 첫째, 같은 QBook.book 인스턴스를 수많은 스레드가 동시에 써도 안전하다. loe는 book.price를 변경하지 않고 그것을 가리키는 새 노드를 만들 뿐이며, Q타입의 필드는 모두 final이다. 그래서 정적 import한 book 하나를 애플리케이션 전체가 공유한다. 둘째, 조건식은 평범한 자바 값이므로 메서드의 반환값이 될 수 있고, 변수에 담겼다가 나중에 조합될 수 있다. 문자열 조각과 달리 각 조각이 자기 의미(연산자와 피연산자)를 갖고 있으므로, 조합할 때 공백이나 and 위치를 걱정할 필요가 없다. 동적 쿼리가 쉬워지는 근본 이유가 이것이다.

    타입 검사가 어디서 일어나는지도 이 구조로 설명된다. NumberPath의 loe는 제네릭 메서드 > loe(A right) 형태로 선언되어 있어서, 문자열을 넘기면 타입 변수의 경계를 만족하지 못한다. Criteria API의 get(String)과 달리 경로 객체의 타입이 엔티티 필드의 실제 타입에서 왔기 때문에 컴파일러가 대조할 근거가 있다. 앞의 Criteria 예제와 같은 두 실수를 Querydsl로 써서 컴파일하면 이렇게 실패한다.

    오타는 "심볼을 찾을 수 없다"로, 타입 불일치는 "추론 변수의 경계가 맞지 않는다"로 바뀌었다. 실행 시점 예외가 컴파일 오류로 옮겨 온 것이다. 다만 이 보호에는 경계가 있다. 컴파일러는 Q타입이 엔티티와 일치한다고 믿을 뿐이므로, Q타입이 낡았다면 보호도 낡는다. 또 NumberExpression에는 숫자를 문자열로 바꿔 비교하는 like(String)도 있어서, 실험에서 book.price.like("%1%")는 오류 없이 컴파일되었다. 타입 검사는 "그 타입에 정의된 연산인가"를 묻는 것이지 "의미상 합리적인 쿼리인가"를 묻는 것이 아니다.

    트리가 JPQL이 되고, JPQL이 SQL이 되기까지

    조건식 트리를 담은 쿼리 객체는 fetch() 같은 실행 메서드가 호출될 때 비로소 문자열이 된다. 이 경로는 querydsl-jpa 5.1.0의 바이트코드로 확인할 수 있다. AbstractJPAQuery.createQuery(QueryModifiers, boolean)를 javap로 열면 호출 순서가 그대로 보인다: 자기 자신을 serialize해서 JPQLSerializer를 얻고, 그 toString()으로 JPQL 문자열을 꺼내고, EntityManager.createQuery(String)에 넘긴 뒤, 직렬화기가 모아 둔 상수 목록(getConstants())을 JPAUtil.setConstants로 파라미터에 바인딩하고, 이어서 setMaxResults와 setFirstResult로 페이징 범위를 지정한다(그 뒤에는 지정된 경우에 한해 락 모드와 플러시 모드, 힌트를 설정한다).

    직렬화 결과를 직접 보자. EntityManager 없이 만든 JPAQuery에도 메타데이터는 쌓이므로, JPQLSerializer에 직접 넘기면 문자열과 상수 목록을 확인할 수 있다.

    JPAQuery q = new JPAQuery().select(book).from(book)
        .where(book.title.like("%자바%"), book.price.loe(30000))
        .orderBy(book.price.desc());
q.offset(10).limit(5);

JPQLSerializer s = new JPQLSerializer(JPQLTemplates.DEFAULT);
s.serialize(q.getMetadata(), false, null);
System.out.println(s + " | " + s.getConstants());

JPQLSerializer c = new JPQLSerializer(JPQLTemplates.DEFAULT);
c.serialize(q.getMetadata(), true, null);          // 두 번째 인자 true: 카운트 쿼리
System.out.println(c);
    select book from Book book where book.title like ?1 escape '!' and book.price <= ?2 order by book.price desc | [%자바%, 30000]
select count(book) from Book book where book.title like ?1 escape '!' and book.price <= ?2

    세 가지를 확인할 수 있다. 첫째, Q타입의 변수 이름 book이 그대로 JPQL의 별칭이 되었다. new QBook("b")로 만든 인스턴스를 쓰면 별칭이 b가 된다. 둘째, 값 30000과 %자바%는 JPQL 문자열에 들어가지 않고 ?1, ?2로 대체되었으며 값은 상수 목록에 따로 있다. 사용자 입력이 쿼리 문법의 일부로 해석될 여지가 없다는 뜻이다. 문자열을 이어 붙이는 방식에서 실수로 값을 문자열에 직접 넣으면 생기는 인젝션(injection) 위험이 구조적으로 사라진다. 셋째, offset(10).limit(5)는 JPQL 문자열 어디에도 없다. JPQL에는 LIMIT 문법이 없기 때문에, 페이징은 문자열이 아니라 JPA Query의 메서드로 전달되고 SQL에 반영하는 일은 Hibernate의 방언이 맡는다.

    직렬화 규칙은 템플릿(templates) 객체가 정한다. JPAQueryFactory(EntityManager) 생성자는 바이트코드상 템플릿 필드를 null로 두고, 쿼리를 만들 때마다 new JPAQuery(EntityManager)를 호출한다. 그 생성자는 JPAProvider.getTemplates(em)으로 템플릿을 고르는데, JPAProvider의 상수 풀에는 org.hibernate.Session, org.eclipse.persistence.jpa.JpaEntityManager, org.apache.openjpa.persistence.OpenJPAEntityManager 같은 구현체 클래스 이름이 들어 있고, 정적 초기화 블록이 이 이름들을 템플릿과 짝지어 등록한다. EclipseLink와 OpenJPA에는 EclipseLinkTemplates, OpenJPATemplates가 짝지어지고, Hibernate에는 org.hibernate.Session 패키지의 구현 버전을 읽어 주 버전이 5 이상이면 Hibernate5Templates(HQLTemplates의 하위 클래스)를, 그보다 낮으면 HQLTemplates를 짝짓는다. 따라서 Hibernate 6에서는 Hibernate5Templates가 쓰인다. 즉 EntityManager의 실제 구현체를 보고 그 구현체의 방언에 맞는 템플릿을 고른다. 위의 단순한 쿼리는 JPQLTemplates.DEFAULT, HQLTemplates.DEFAULT, Hibernate5Templates.DEFAULT로 직렬화한 결과가 글자 하나 다르지 않았다. 템플릿 차이는 함수나 특수 연산처럼 구현체마다 문법이 다른 부분에서 드러난다.

    카운트 쿼리 직렬화도 눈여겨볼 만하다. 같은 메타데이터에서 select count(book)만 바꾼 문자열이 나오고 order by는 빠졌다. 이 단순한 변환은 조건이 where에만 있을 때는 잘 맞는다. 그러나 group by가 여러 개이거나 having이 있는 쿼리의 전체 행 수는 "원래 쿼리를 서브쿼리로 감싸서 센다"로만 정확히 구할 수 있는데, Querydsl 5.1.0 Javadoc은 JPQL이 서브쿼리를 프로젝션의 대상으로 삼는 것을 허용하지 않는다고 설명한다. 그래서 Querydsl 5에서 fetchCount()와 fetchResults()는 deprecated 표시가 되었고(javap에서 Deprecated: true 확인), 그런 쿼리에서는 전체 결과를 가져와 크기를 재는 방식으로 대체된다고 Javadoc에 적혀 있다. 클래스 파일에는 "Fetchable#fetchCount() was computed in memory!"라는 경고 문자열도 들어 있다. 행 수가 필요하면 select(book.count())로 카운트 쿼리를 직접 따로 작성하는 것이 권장되는 방식이다.

    자바 객체 트리 → JPQLSerializer → JPQL 문자열과 상수 목록 → EntityManager → Hibernate SQM → SQL로 이어지는 단계와, 컴파일러가 검사하는 구간과 실행 시점에 검사되는 구간의 경계. 왼쪽에서 오른쪽으로 다섯 단계가 이어진 파이프라인. 첫 상자 "표현식 트리" 안에 작은 트리 그림: 꼭대기 "AND", 아래 두 노드 "LIKE", "LOE", 각 노드 아래 "book.title", "%자바%", "book.price", "30000". 두 번째 상자 "JPQLSerializer". 세 번째 상자는 위아래 둘로 나뉘어 위 "JPQL: ... where book.title like ?1 and book.price <= ?2", 아래 "상수: [%자바%, 30000]". 네 번째 상자 "EntityManager → Hibernate SQM". 다섯 번째 상자 "SQL + 바인딩 → DB". 첫 상자 아래에 초록색 괄호 "컴파일러가 검사"가 첫 상자만 덮고, 세 번째부터 다섯 번째 상자 아래에 주황색 괄호 "실행 시점에 해석"이 덮는다. 화살표는 굵은 회색. 배경 흰색. Querydsl은 문자열을 만드는 쪽을 컴파일러의 보호 아래로 옮길 뿐, 이후 단계는 문자열 JPQL과 같다.

    like와 contains: 같은 like 절, 다른 파라미터 값

    위 출력의 escape '!'는 Querydsl의 기본 템플릿이 붙이는 이스케이프 문자 지정이다. LIKE 패턴에서 %는 "임의 길이의 문자열", _는 "임의의 한 문자"라는 와일드카드인데, 이 문자 자체를 찾고 싶을 때는 이스케이프 문자를 앞에 붙여 와일드카드가 아님을 표시한다. 이 지정이 실제로 쓰이는지는 like와 contains를 비교하면 드러난다. 같은 사용자 입력 "50%"로 실험했다.

    book.title.like("%50%")          // 호출자가 패턴을 직접 만든다
book.title.contains("50%")       // 호출자는 찾을 문자열만 준다
book.title.containsIgnoreCase("Java")
    select book from Book book where book.title like ?1 escape '!' | [%50%]
select book from Book book where book.title like ?1 escape '!' | [%50!%%]
select book from Book book where lower(book.title) like ?1 escape '!' | [%java%]

    세 경우 모두 JPQL에는 like ?1가 나오지만 바인딩 값이 다르다. like는 넘긴 문자열을 패턴으로 그대로 쓴다. 그래서 "50%"를 찾으려던 의도와 달리 "50으로 시작하는 무엇이든을 포함하는" 제목이 모두 걸린다. contains는 입력을 리터럴로 취급해서, 입력 속의 % 앞에 이스케이프 문자 !를 붙이고(50!%) 앞뒤에 와일드카드 %를 더한다. containsIgnoreCase는 양쪽을 lower()로 맞추고 입력도 소문자로 바꿔 바인딩한다. 사용자 입력으로 "포함" 검색을 할 때는 like("%" + kw + "%")보다 contains(kw)가 의도에 맞다. 바인딩이 인젝션은 막아 주지만, 와일드카드 해석까지 막아 주지는 않는다는 점이 이 차이의 핵심이다.

    성능 측면에서 하나 덧붙이면, %로 시작하는 LIKE 패턴은 B+Tree 인덱스의 정렬 순서를 이용한 범위 탐색을 할 수 없다. 인덱스는 값의 앞부분부터 정렬되어 있으므로 "앞부분이 무엇이든 상관없다"는 조건으로는 시작 위치를 정할 수 없기 때문이다. contains는 편리하지만 큰 테이블에서는 이 성질을 알고 써야 하고, 앞부분이 정해진 검색이라면 startsWith가 만드는 값% 형태의 패턴이 인덱스 범위 탐색의 여지를 남긴다. 데이터베이스 기본편에서 본 인덱스 구조가 Querydsl 메서드 선택에도 그대로 이어진다.

    동적 쿼리: where는 null 조건을 건너뛴다

    Querydsl의 동적 쿼리는 한 가지 규칙에 기대고 있다. where에 넘긴 조건 중 null은 무시된다. 바이트코드로 확인하면 QueryMixin.where(Predicate...)는 배열을 돌며 각 조건을 QueryMetadata.addWhere에 넘기고, DefaultQueryMetadata.addWhere의 첫 명령은 인자가 null이면 그대로 반환(ifnonnull 분기 후 return)하는 것이다. 이 규칙 덕분에 "조건이 없으면 null을 반환하는 메서드"를 만들어 where에 나란히 넘기면 동적 쿼리가 완성된다.

    static BooleanExpression titleContains(String kw) {
    return (kw == null || kw.isBlank()) ? null : book.title.contains(kw);
}

static BooleanExpression priceAtMost(Integer max) {
    return max == null ? null : book.price.loe(max);
}

static void show(String label, String kw, Integer max) {
    JPAQuery q = new JPAQuery()
            .select(book).from(book)
            .where(titleContains(kw), priceAtMost(max));
    System.out.println("[" + label + "] " + q.toString().replace('\n', ' '));
}

show("둘 다", "자바", 30000);
show("키워드만", "자바", null);
show("조건 없음", null, null);
    [둘 다] select book from Book book where book.title like ?1 escape '!' and book.price <= ?2
[키워드만] select book from Book book where book.title like ?1 escape '!'
[조건 없음] select book from Book book

    네 가지 조합 모두에서 올바른 JPQL이 나온다. 조건이 하나도 없으면 where 절 자체가 생기지 않는다. 문자열 방식에서 플래그나 where 1=1로 관리하던 일을 직렬화기가 대신한다. 그리고 조건과 그 값이 한 객체에 들어 있으므로, 문자열 조립과 파라미터 바인딩을 두 번 분기할 필요도 없다. 앞에서 지적한 "하나의 결정이 두 곳에 흩어진" 구조가 해소된 것이다. 각 조건 메서드는 이름을 가진 재사용 단위가 되어, 다른 쿼리에서도 priceAtMost(max)를 그대로 쓸 수 있다.

    조건을 누적하는 다른 방법으로 BooleanBuilder가 있다. 빈 빌더를 만들고 조건이 있을 때마다 and()로 붙여 where에 넘긴다. 실험해 보면 BooleanBuilder의 and()도 null 인자를 무시한다. bb.and(titleContains("스프링")); bb.and(priceAtMost(null));을 실행한 결과 빌더의 값은 제목 조건 하나였고 hasValue()는 true였다. 빌더는 조건을 한곳에 모아 보기 좋지만, 빌더 자체가 변경 가능한 객체라서 조건 조립 로직이 메서드 하나 안에 길게 늘어나기 쉽다. 반면 BooleanExpression을 반환하는 작은 메서드들은 각각 이름이 붙어 있어 쿼리 본문이 선언처럼 읽힌다.

    null 무시 규칙이 적용되지 않는 곳

    null을 무시해 주는 것은 where와 빌더의 동작이지, 모든 메서드의 동작이 아니다. 세 가지 함정이 있다.

    • 비교 연산에 null 값을 넘기는 경우. book.title.eq((String) null)은 IllegalArgumentException을 던지며, 메시지는 "eq(null) is not allowed. Use isNull() instead"였다. SQL에서 = NULL은 참이 되지 않으므로 의도를 명확히 하라는 것이다. book.price.loe((Integer) null)은 더 불친절해서, 상수 노드를 만들다가 NullPointerException("Cannot invoke "Object.getClass()" because "constant" is null")이 났다. 조건 메서드 안에서 값이 null인지 먼저 확인하고 조건 자체를 null로 돌려주는 이유가 이것이다.
    • null인 조건에 대해 and()를 호출하는 경우. titleContains(kw).and(priceAtMost(max))처럼 조건을 연결해 하나로 만들면, kw가 비어 titleContains가 null을 반환했을 때 null에 대해 메서드를 호출하게 되어 NullPointerException이 난다. 인자 쪽이 null인 것은 괜찮지만, 호출 대상이 null인 것은 자바 언어 차원에서 막을 수 없다. 조건 여러 개를 조합할 때는 where의 가변 인자에 나란히 넘기거나 BooleanBuilder를 쓴다.
    • 모든 조건이 null인 경우. 앞의 실행 결과처럼 where 절이 통째로 사라지고 전체 행을 조회한다. 검색 화면에서는 의도한 동작일 수 있지만, 삭제나 대량 수정 쿼리에서 같은 패턴을 쓰면 위험하다. 조건이 필수인 쿼리는 조건이 없을 때 쿼리를 실행하지 않도록 따로 검사해야 한다.

    Querydsl 적용: 리포지토리와 JPAQueryFactory

    이제 실제 스프링 애플리케이션의 저장소 클래스로 옮겨 보자. 저장, 수정, 단건 조회는 04회에서 본 대로 EntityManager를 직접 쓰고, 동적 검색만 Querydsl로 작성한다. 쿼리를 만드는 시작점은 JPAQueryFactory다.

    @Repository
@Transactional
public class QuerydslBookRepository implements BookRepository {

    private final EntityManager em;
    private final JPAQueryFactory query;

    public QuerydslBookRepository(EntityManager em) {
        this.em = em;
        this.query = new JPAQueryFactory(em);
    }

    @Override
    public Book save(Book book) {
        em.persist(book);
        return book;
    }

    @Override
    public void changePrice(Long id, int newPrice) {
        Book found = em.find(Book.class, id);
        found.changePrice(newPrice);      // 변경 감지: 커밋 직전 플러시에서 UPDATE
    }

    @Override
    public Optional findById(Long id) {
        return Optional.ofNullable(em.find(Book.class, id));
    }

    @Override
    public List search(BookSearch cond) {
        return query
                .selectFrom(book)
                .where(titleContains(cond.titleKeyword()), priceAtMost(cond.maxPrice()))
                .orderBy(book.price.asc())
                .fetch();
    }

    private BooleanExpression titleContains(String kw) {
        return StringUtils.hasText(kw) ? book.title.contains(kw) : null;
    }

    private BooleanExpression priceAtMost(Integer max) {
        return max != null ? book.price.loe(max) : null;
    }
}

    이 클래스에서 짚어야 할 원리는 세 가지다. 첫째, 생성자로 받은 EntityManager는 진짜 EntityManager가 아니라 프록시다. 스프링 레퍼런스는 이렇게 주입되는 EntityManager를 "실제 트랜잭션용 EntityManager에 대한 공유되고 스레드 안전한 프록시"라고 설명한다. 호출이 들어오면 현재 트랜잭션에 묶인 EntityManager에게 위임하고, 트랜잭션이 없으면 작업마다 새 EntityManager를 만든다. 그래서 싱글톤 빈에 하나를 저장해 두고 여러 요청 스레드가 동시에 써도 각자 자기 트랜잭션의 영속성 컨텍스트를 쓰게 된다. 이 프록시를 생성자 주입으로 받을 수 있는 것은 스프링 데이터 JPA 3.x가 EntityManagerBeanDefinitionRegistrarPostProcessor로 공유 EntityManager 빈을 등록해 주기 때문이다(스프링 데이터 4.0에서는 이 클래스가 deprecated 되었고 스프링 프레임워크의 AbstractEntityManagerFactoryBean이 공유 EntityManager를 제공하는 방식으로 옮겨 갔다). 스프링 레퍼런스는 그런 등록이 없는 순수 스프링 설정에서는 @PersistenceContext 방식의 공유 EntityManager를 @Autowired로 받을 수 없으니 SharedEntityManagerBean이나 SharedEntityManagerCreator 기반의 @Bean 메서드로 빈을 직접 정의하라고 안내한다.

    둘째, JPAQueryFactory는 공유해도 되지만 JPAQuery는 공유하면 안 된다. 바이트코드를 보면 JPAQueryFactory는 생성자에서 EntityManager를 공급자(Supplier) 람다로 감싸 필드에 저장할 뿐이고, selectFrom이나 query()가 호출될 때마다 new JPAQuery로 새 쿼리 객체를 만든다. 반면 JPAQuery는 where가 호출될 때마다 내부 메타데이터에 조건을 추가하는 변경 가능한 객체다. 쿼리 객체를 필드에 두고 재사용하면 이전 요청의 조건이 남거나, 두 스레드의 조건이 섞인다. "팩토리는 공유하고 쿼리는 매번 만든다"가 규칙이다. JPAQueryFactory를 별도의 설정 클래스에서 빈으로 등록해 여러 저장소가 주입받게 하는 방식도 같은 이유로 안전하다.

    셋째, @Repository는 이 클래스에서도 예외 변환을 위해 필요하다. Querydsl JPA는 내부에서 EntityManager를 호출할 뿐이므로, 실패하면 JPA 표준 예외(PersistenceException 계열)가 그대로 올라온다. 04회에서 본 것처럼 스프링은 @Repository가 붙은 빈에 예외 변환 AOP를 적용해 이를 DataAccessException 계층으로 바꾼다. Querydsl을 쓴다고 이 경로가 달라지지 않는다. 서비스 계층이 기술 중립적인 예외만 보게 하려면 Querydsl 저장소에도 @Repository를 붙여야 한다.

    활용 방안 1: 스프링 데이터 JPA를 어댑터 뒤에 둘 때의 대가

    여기서부터는 지금까지 비교한 기술을 실제 애플리케이션에 어떤 구조로 배치할지의 문제다. 이 권은 서비스가 BookRepository 같은 인터페이스에만 의존하고, 그 구현체를 JdbcTemplate, MyBatis, JPA로 바꿔 끼우는 구조를 유지해 왔다. 스프링 핵심 원리 기본편에서 본 의존관계 주입(DI)과 개방-폐쇄 원칙(OCP)을 그대로 적용한 결과다. 구현 기술이 바뀌어도 서비스 코드는 한 줄도 바뀌지 않는다.

    스프링 데이터 JPA를 이 구조에 넣으려고 하면 문제가 생긴다. 스프링 데이터 JPA의 리포지토리는 JpaRepository를 상속한 인터페이스이고, 그 구현체는 스프링 데이터가 실행 시점에 프록시로 만든다(05회). 이 인터페이스는 서비스가 의존하는 BookRepository와 모양이 다르다. 메서드 이름이 다르고, 동적 검색처럼 스프링 데이터의 메서드 이름 규칙으로 표현할 수 없는 기능도 있다. 서비스 코드를 바꾸지 않으려면 둘 사이에 어댑터(adapter)를 둔다.

    public interface SpringDataBookRepository extends JpaRepository {
    List findByTitleContainingAndPriceLessThanEqual(String keyword, int maxPrice);
    List findByTitleContaining(String keyword);
    List findByPriceLessThanEqual(int maxPrice);
}

@Repository
@Transactional
public class SpringDataBookRepositoryAdapter implements BookRepository {   // 서비스가 아는 인터페이스

    private final SpringDataBookRepository repository;                     // 스프링 데이터가 만든 프록시

    public SpringDataBookRepositoryAdapter(SpringDataBookRepository repository) {
        this.repository = repository;
    }

    @Override
    public Book save(Book book) { return repository.save(book); }

    @Override
    public void changePrice(Long id, int newPrice) {
        repository.findById(id).orElseThrow().changePrice(newPrice);
    }

    @Override
    public Optional findById(Long id) { return repository.findById(id); }

    @Override
    public List search(BookSearch cond) {
        String kw = cond.titleKeyword();
        Integer max = cond.maxPrice();
        if (StringUtils.hasText(kw) && max != null) return repository.findByTitleContainingAndPriceLessThanEqual(kw, max);
        if (StringUtils.hasText(kw))                return repository.findByTitleContaining(kw);
        if (max != null)                            return repository.findByPriceLessThanEqual(max);
        return repository.findAll();
    }
}

    구조만 보면 깔끔하다. 서비스는 여전히 BookRepository만 알고, 스프링 데이터 JPA는 어댑터 뒤에 숨어 있다. 그러나 비용도 분명하다. 어댑터 클래스가 하나 늘었고, 메서드 대부분은 이름만 바꿔 전달하는 코드다. 더 큰 비용은 search에서 드러난다. 스프링 데이터의 메서드 이름 쿼리는 조건의 조합을 표현하지 못하므로, 조건이 둘이면 네 갈래, 셋이면 여덟 갈래로 분기와 메서드가 늘어난다. 조건 수에 대해 지수적으로 늘어나는 구조다. 그리고 어댑터 뒤에 숨긴 탓에 서비스는 스프링 데이터가 제공하는 페이징(Pageable), 정렬, 수십 개의 기본 메서드를 직접 쓸 수 없다. 쓰려면 BookRepository에 같은 기능을 다시 선언하고 어댑터에 위임 코드를 또 써야 한다.

    이것이 트레이드오프의 정체다. DI와 OCP를 지키는 추상화는 "구현 기술을 바꿀 가능성"에 대한 보험이고, 보험료는 클래스 수와 위임 코드, 그리고 하부 기술의 기능을 쓰지 못하는 제약으로 지불한다. 보험이 값어치를 하는지는 그 가능성이 실제로 얼마나 높은지에 달려 있다. 저장소 기술을 JPA에서 다른 기술로 통째로 바꾸는 일은 드물고, 바꾼다고 해도 트랜잭션 경계, 지연 로딩, 영속성 컨텍스트에 기댄 서비스 코드의 가정까지 함께 바뀌므로 인터페이스 하나로 막아지지 않는 경우가 많다. 반대로 외부 시스템 연동처럼 구현이 실제로 여럿이거나 자주 바뀌는 곳에서는 같은 추상화가 비용 이상의 값을 한다.

    활용 방안 2: 실용적인 구조 — 단순 CRUD와 복잡한 조회를 나눈다

    추상화의 비용이 이득보다 크다고 판단했다면, 서비스가 스프링 데이터 JPA 리포지토리를 직접 의존하게 하는 구조를 택할 수 있다. 이때 복잡한 동적 조회는 Querydsl로 작성한 별도의 조회 전용 저장소로 뺀다. 저장소가 두 갈래로 나뉜다.

    public interface BookRepository extends JpaRepository {
    // 기본 CRUD와 페이징은 JpaRepository가 제공한다
}

@Repository
public class BookQueryRepository {

    private final JPAQueryFactory query;

    public BookQueryRepository(EntityManager em) {
        this.query = new JPAQueryFactory(em);
    }

    public List search(BookSearch cond) {
        return query.selectFrom(book)
                .where(titleContains(cond.titleKeyword()), priceAtMost(cond.maxPrice()))
                .fetch();
    }
    // titleContains, priceAtMost는 앞과 같다
}

@Service
@Transactional
public class BookService {

    private final BookRepository bookRepository;            // 단순 CRUD
    private final BookQueryRepository bookQueryRepository;  // 화면·조건에 맞춘 조회

    public BookService(BookRepository bookRepository, BookQueryRepository bookQueryRepository) {
        this.bookRepository = bookRepository;
        this.bookQueryRepository = bookQueryRepository;
    }

    public Book register(String title, int price, int stock) {
        return bookRepository.save(new Book(title, price, stock));
    }

    public void changePrice(Long id, int newPrice) {
        bookRepository.findById(id).orElseThrow().changePrice(newPrice);
    }

    @Transactional(readOnly = true)
    public List search(BookSearch cond) {
        return bookQueryRepository.search(cond);
    }
}

    어댑터가 사라졌고, 서비스는 스프링 데이터의 모든 기능을 그대로 쓴다. 조회 전용 저장소에는 엔티티 단위의 저장·삭제가 없으므로, "엔티티의 생명주기를 다루는 쪽"과 "화면이나 보고서 요구에 맞춰 바뀌는 조회를 다루는 쪽"이 자연스럽게 분리된다. 조회 요구는 엔티티 생명주기보다 훨씬 자주 바뀌므로, 변경 이유가 다른 코드를 다른 클래스에 두는 것은 단일 책임 원칙(SRP)의 관점에서도 합리적이다. 대가는 서비스가 JPA와 스프링 데이터라는 구체 기술을 직접 안다는 점이다. 저장 기술을 바꾸면 서비스도 바뀐다. 이 구조는 그 가능성을 낮게 보고 개발 속도와 단순함을 택한 결정이다.

    스프링 데이터는 이 두 갈래를 하나의 인터페이스로 합치는 방법도 제공한다. 사용자 정의 구현 조각(fragment)이다. 조각 인터페이스를 만들고, 그 이름 뒤에 Impl을 붙인 클래스로 구현하면, 스프링 데이터가 리포지토리를 찾은 패키지 아래를 스캔해 그 클래스를 자동으로 발견하고 리포지토리 프록시에 합성한다. 스프링 데이터 문서는 조각 구현 클래스 이름에서 가장 중요한 부분이 Impl 접미사라고 강조하고, 사용자 정의 구현이 기본 구현보다 우선한다고 적고 있다.

    public interface BookRepositoryCustom {
    List search(BookSearch cond);
}

class BookRepositoryCustomImpl implements BookRepositoryCustom {   // 이름 = 조각 인터페이스 이름 + "Impl"
    private final JPAQueryFactory query;
    BookRepositoryCustomImpl(EntityManager em) { this.query = new JPAQueryFactory(em); }

    @Override
    public List search(BookSearch cond) { /* Querydsl 쿼리 */ return List.of(); }
}

public interface BookRepository extends JpaRepository, BookRepositoryCustom {}

    서비스는 BookRepository 하나만 주입받고 save와 search를 모두 호출할 수 있다. 프록시가 메서드 호출을 받아 search는 사용자 정의 조각으로, save는 기본 구현(SimpleJpaRepository)으로 보낸다. 대신 이름 규칙에 기대는 자동 발견이 하나 더 생기고, 화면 전용 조회가 엔티티 리포지토리에 섞여 들어가 인터페이스가 점점 커질 수 있다. 조회 로직이 특정 화면이나 API에 강하게 묶여 있다면 별도 클래스로 두는 편이 경계를 더 분명하게 한다.

    구조서비스가 아는 것기술 교체 시 서비스 변경추가 코드잘 맞는 상황
    인터페이스 + 어댑터자체 BookRepository만없음어댑터와 위임 메서드, 조건 조합 분기구현이 실제로 여럿이거나 교체 가능성이 높을 때
    스프링 데이터 + 조회 전용 클래스JpaRepository와 조회 클래스있음조회 클래스 하나JPA를 계속 쓸 것이 확실하고 조회 요구가 자주 바뀔 때
    스프링 데이터 + 사용자 정의 조각합성된 리포지토리 하나있음조각 인터페이스와 Impl 클래스엔티티 중심의 조회 몇 개를 한 리포지토리에 모으고 싶을 때

    어느 하나가 정답은 아니다. 중요한 것은 추상화를 "원칙이니까" 넣는 것이 아니라, 그 추상화가 막아 주는 변경이 무엇이고 그 변경이 일어날 가능성이 얼마인지를 따져서 넣는 것이다. 처음에는 단순한 구조로 시작하고, 구현이 실제로 둘 이상이 되는 시점에 인터페이스를 도입하는 것도 가능한 선택이다. 인터페이스 추출은 IDE가 기계적으로 해 주는 리팩터링이지만, 쓰이지 않는 추상화를 걷어 내는 일은 생각보다 어렵다.

    왼쪽은 서비스 → 인터페이스 ← 어댑터 → 스프링 데이터 리포지토리의 4단 구조, 오른쪽은 서비스가 스프링 데이터 리포지토리와 조회 전용 저장소를 직접 의존하는 2갈래 구조. 좌우 두 패널로 나뉜 다이어그램. 왼쪽 패널 제목 "어댑터 구조": 위에서 아래로 상자 "BookService" → (실선 화살표) "BookRepository (인터페이스)" ← (점선 구현 화살표) "어댑터" → (실선 화살표) "SpringDataBookRepository" → "스프링 데이터 프록시". 왼쪽 패널 하단에 작은 태그 "교체 비용 낮음 · 코드 많음". 오른쪽 패널 제목 "실용적인 구조": 맨 위 "BookService"에서 두 갈래 화살표가 아래로 내려가 왼쪽 "BookRepository (JpaRepository)", 오른쪽 "BookQueryRepository (Querydsl)"에 닿는다. 두 상자 아래 공통으로 "EntityManager" 상자. 오른쪽 패널 하단 태그 "코드 적음 · 서비스가 기술을 앎". 배경 흰색, 상자는 연한 회색, 서비스 상자는 연한 초록. 추상화 한 층은 기술 교체 비용을 낮추는 대신 클래스와 위임 코드로 값을 치른다.

    활용 방안 3: 여러 데이터 접근 기술을 한 트랜잭션에서 섞기

    JPA, 스프링 데이터 JPA, Querydsl의 조합은 대부분의 조회와 저장을 감당한다. 그래도 데이터베이스 고유 기능을 쓰는 복잡한 통계 SQL이나, 수많은 행을 한 번에 다루는 작업처럼 JPQL로 표현하기 어렵거나 영속성 컨텍스트를 거치는 것이 손해인 일이 남는다. 이런 곳에는 JdbcTemplate이나 MyBatis로 SQL을 직접 쓰는 것이 자연스럽다. 기술을 섞는 것 자체는 어렵지 않다. 어려운 것은 섞었을 때 트랜잭션과 커넥션이 하나로 유지되는가, 그리고 두 기술이 같은 데이터를 같은 시점의 상태로 보는가다.

    트랜잭션 매니저와 커넥션 공유

    트랜잭션 매니저부터 보자. Spring Boot의 JPA 자동 구성 클래스 JpaBaseConfiguration은 @ConditionalOnMissingBean(TransactionManager.class) 조건으로 PlatformTransactionManager 빈을 등록하는데, Boot 4.0.8의 바이트코드를 열어 보면 그 메서드는 JpaTransactionManager를 생성한다(Boot 3.5 API 문서에서도 같은 조건의 transactionManager 메서드를 확인했다). 즉 JPA를 쓰는 Boot 애플리케이션에서 @Transactional이 쓰는 트랜잭션 매니저는 기본적으로 JpaTransactionManager 하나다. JdbcTemplate만 쓰는 애플리케이션이었다면 DataSourceTransactionManager(또는 그 하위 클래스)가 등록되었을 자리다.

    JpaTransactionManager의 Javadoc은 이 매니저가 트랜잭션 안에서 같은 DataSource에 대한 직접 접근, 즉 일반 JDBC 코드도 지원한다고 명시한다. 그 조건은 애플리케이션 코드가 DataSourceTransactionManager와 같은 커넥션 조회 방식(DataSourceUtils.getConnection(DataSource) 또는 TransactionAwareDataSourceProxy)을 따르는 것과, 벤더별 JpaDialect가 설정되어 있는 것이다. JdbcTemplate은 내부에서 DataSourceUtils.getConnection을 쓰므로 첫 조건을 만족하고, Hibernate를 쓰면 HibernateJpaDialect가 둘째 조건을 채운다.

    동작 원리는 spring-orm 7.0.9의 바이트코드에서 확인할 수 있다. JpaTransactionManager.afterPropertiesSet()은 EntityManagerFactory가 EntityManagerFactoryInfo를 구현하면 거기서 DataSource와 JpaDialect를 꺼내 자기 설정으로 삼는다. 그리고 트랜잭션을 시작하는 doBegin은 EntityManager를 만들고 트랜잭션을 시작한 뒤, JpaDialect.getJdbcConnection(em, ...)으로 그 EntityManager가 쓰는 JDBC 커넥션의 핸들을 얻어 ConnectionHolder로 감싸고, TransactionSynchronizationManager.bindResource(dataSource, holder)로 현재 스레드에 바인딩한다. 스프링 DB 1편에서 본 트랜잭션 동기화 저장소 그대로다. 이후 같은 스레드에서 JdbcTemplate이 DataSourceUtils.getConnection(dataSource)를 호출하면 바인딩된 홀더를 찾아 Hibernate가 쓰고 있는 바로 그 커넥션을 돌려받는다. 같은 커넥션이므로 같은 데이터베이스 트랜잭션이고, 커밋과 롤백도 함께 된다.

    요청 스레드 T1, @Transactional 메서드 진입

 JpaTransactionManager.doBegin
   ├─ EntityManager em 생성, em.getTransaction().begin()   → JDBC 커넥션 C1 (autocommit=false)
   ├─ 스레드 로컬: EntityManagerFactory ──▶ EntityManagerHolder(em)
   └─ 스레드 로컬: DataSource           ──▶ ConnectionHolder(C1 핸들)   ← JpaDialect가 꺼낸 커넥션

 bookQueryRepository.search(...)   공유 EM 프록시 → em → C1
 jdbcTemplate.query(...)           DataSourceUtils.getConnection(ds) → C1
 커밋                               em의 트랜잭션 커밋 → C1.commit()  (JPA 변경과 JDBC 변경이 함께)

    같은 커넥션이어도 같은 상태를 보는 것은 아니다: 플러시

    커넥션을 공유한다고 문제가 모두 풀리지는 않는다. JPA는 쓰기 지연(write-behind)을 한다. 변경 감지로 생기는 UPDATE는 엔티티 필드를 바꾸는 순간이 아니라 플러시(flush) 때 데이터베이스로 보내진다(04회). JPA 명세는 이 지연이 쿼리 결과를 틀리게 만들지 않도록 규칙을 두었다. FlushModeType Javadoc에 따르면, 트랜잭션 안에서 쿼리를 실행할 때 플러시 모드가 AUTO(기본값)이면 영속성 제공자는 쿼리 결과에 영향을 줄 수 있는 영속성 컨텍스트의 변경이 그 쿼리에서 보이도록 보장해야 하고, 그 방법으로 해당 엔티티를 플러시할 수 있다. 핵심은 이 규칙의 주어가 영속성 제공자를 통해 실행되는 쿼리라는 점이다.

    JdbcTemplate의 SQL은 Hibernate를 전혀 거치지 않는다. 같은 커넥션에서 실행되지만 Hibernate는 그 SQL이 실행된다는 사실조차 모른다. 따라서 자동 플러시가 일어날 계기가 없다. 다음 메서드를 한 줄씩 추적해 보자. book 테이블에 가격이 15000인 도서가 있다고 하자.

    @Transactional
public void repriceAndCompare(Long id) {
    Book b = em.find(Book.class, id);           // ① SELECT 실행, 영속성 컨텍스트에 15000으로 적재
    b.changePrice(12000);                       // ② 엔티티 필드만 변경, SQL 없음

    Integer viaJdbc = jdbcTemplate.queryForObject(
            "select price from book where id = ?", Integer.class, id);       // ③

    List viaQuerydsl = query.selectFrom(book)
            .where(book.price.loe(12000)).fetch();                           // ④

    em.flush();                                                              // ⑤
    Integer afterFlush = jdbcTemplate.queryForObject(
            "select price from book where id = ?", Integer.class, id);       // ⑥
}
    1. ①에서 em.find는 영속성 컨텍스트에 엔티티가 없으므로 SELECT를 실행하고, 엔티티와 함께 스냅샷(가격 15000)을 저장한다.
    2. ②는 자바 객체의 필드를 바꿀 뿐이다. 데이터베이스의 행은 여전히 15000이다.
    3. ③의 JdbcTemplate은 같은 커넥션 C1로 SELECT를 보낸다. Hibernate가 개입하지 않으므로 UPDATE는 아직 나가지 않았고, 결과는 15000이다. 같은 트랜잭션 안인데 방금 바꾼 값이 보이지 않는다.
    4. ④의 Querydsl 쿼리는 EntityManager.createQuery를 거쳐 Hibernate가 실행한다. 플러시 모드가 AUTO이고 이 쿼리가 Book 엔티티를 대상으로 하므로, 명세 규칙에 따라 대기 중인 변경이 이 쿼리에 보여야 한다. Hibernate는 쿼리 전에 해당 변경을 플러시하고, 결과에는 가격이 12000이 된 이 도서가 포함된다.
    5. ⑤에서 명시적으로 플러시한다. ④에서 이미 UPDATE가 나갔다면 더 보낼 변경이 없고, ④가 없었다면 여기서 UPDATE가 나간다.
    6. ⑥의 JdbcTemplate은 이제 12000을 읽는다. 커밋 전이지만 같은 커넥션, 같은 트랜잭션이므로 자기 트랜잭션의 미커밋 변경을 본다.

    정리하면, JPA로 변경한 뒤 같은 트랜잭션에서 JdbcTemplate이나 MyBatis로 그 데이터를 읽거나 그 데이터에 의존하는 SQL을 실행하려면, 그 전에 em.flush()를 호출해 변경을 데이터베이스로 내보내야 한다. 반대 방향도 주의해야 한다. JdbcTemplate으로 행을 직접 수정하면 영속성 컨텍스트에 이미 올라와 있는 엔티티는 그 사실을 모른다. 이후 em.find는 1차 캐시의 옛 객체를 돌려준다. 이럴 때는 해당 엔티티를 em.refresh로 다시 읽거나, SQL 작업을 영속성 컨텍스트를 쓰기 전에 배치하거나, em.clear()로 컨텍스트를 비워야 한다. 두 기술을 섞는 코드에서는 "지금 이 시점에 데이터베이스의 행과 영속성 컨텍스트의 객체가 같은 상태인가"를 의식적으로 확인해야 한다.

    IDENTITY 키 생성 전략에서는 persist 시점에 식별자를 얻기 위해 INSERT가 바로 실행된다(04회). 그래서 "새로 저장한 행은 JdbcTemplate에서 보이는데 수정한 값은 안 보인다"는 혼란스러운 상황이 생길 수 있다. INSERT가 즉시 나간 것은 키 생성 전략의 부수 효과일 뿐, 쓰기 지연이 사라진 것이 아니다.
    서비스, 영속성 컨텍스트, JdbcTemplate, 커넥션 C1, DB 행 사이에서 changePrice 후 JDBC 조회는 옛 값, flush 후 JDBC 조회는 새 값을 보는 순서. 시퀀스 다이어그램. 위쪽에 다섯 개의 생명선 상자: "서비스", "영속성 컨텍스트", "JdbcTemplate", "커넥션 C1", "DB 행". 1번 메시지: 서비스→영속성 컨텍스트 "changePrice(12000)", 영속성 컨텍스트 옆에 노란 메모 "변경 대기". 2번 메시지: 서비스→JdbcTemplate "select price", JdbcTemplate→커넥션 C1→DB 행, 돌아오는 화살표 라벨 "15000 (옛 값)"을 빨간색으로. 3번 메시지: 서비스→영속성 컨텍스트 "flush()", 영속성 컨텍스트→커넥션 C1→DB 행 "UPDATE price=12000". 4번 메시지: 서비스→JdbcTemplate "select price", 돌아오는 화살표 라벨 "12000 (새 값)"을 초록색으로. 커넥션 C1 생명선 위에 작은 라벨 "JPA와 JDBC가 공유". 배경 흰색. 같은 커넥션을 써도 플러시 전의 변경은 JDBC 쪽에서 보이지 않는다.

    정리: 기술을 고르는 기준과 이 회차가 남기는 것

    이 권에서 비교한 기술들은 서로를 대체하는 관계라기보다 층을 이룬다. 엔티티의 저장과 수정은 JPA의 영속성 컨텍스트와 변경 감지가, 단순 조회와 페이징은 스프링 데이터 JPA가, 조건이 바뀌는 동적 조회는 Querydsl이 맡는다. JPQL로 표현하기 어려운 SQL이나 영속성 컨텍스트를 거치지 않는 편이 나은 대량 작업은 JdbcTemplate이나 MyBatis가 맡는다. 같은 DataSource와 JpaTransactionManager 아래에서는 이들이 한 트랜잭션에 참여할 수 있지만, 플러시 시점과 1차 캐시의 상태는 사람이 관리해야 한다.

    Querydsl에 대해서는 이렇게 요약할 수 있다. Querydsl은 쿼리를 실행하는 새로운 엔진이 아니라, 컴파일러가 검사할 수 있는 자바 객체로 JPQL을 만드는 도구다. 애너테이션 프로세서가 엔티티 구조를 Q타입으로 복사해 두고, 표현식 노드의 트리를 직렬화기가 위치 파라미터를 가진 JPQL로 바꾼다. 그 덕분에 오타와 타입 불일치가 컴파일 오류가 되고, 동적 조건은 null을 반환하는 작은 메서드의 조합이 된다. 한편 그 보호는 Q타입이 최신일 때만 유효하고, 최종 JPQL의 해석과 SQL 생성은 여전히 실행 시점의 Hibernate가 한다.

    다음 회차부터는 이 권의 후반부인 스프링 트랜잭션으로 넘어간다. 07회는 이 회차에서 당연하게 쓴 @Transactional이 프록시로 어떻게 적용되는지와 내부 호출 문제, 예외에 따른 커밋·롤백 규칙을 다루고, 08회와 09회는 트랜잭션 전파를 다룬다. 이 회차에서 본 "여러 저장소가 한 트랜잭션에 참여한다"는 구조가 전파 옵션에서 다시 문제가 된다.
    문자열 쿼리의 한계
    JPQL과 SQL 문자열은 컴파일러에게 그냥 상수라서 오타와 타입 불일치가 실행 시점에 드러나고, 동적 쿼리에서는 문자열 조립과 파라미터 바인딩이 같은 분기를 두 번 반복한다.
    Criteria의 문자열 속성
    Path.get(String)은 반환 타입을 호출 위치에서 추론하는 제네릭 메서드라서, 없는 속성 이름이나 틀린 타입 비교도 컴파일된다.
    Q타입 생성
    querydsl-apt의 JPAAnnotationProcessor가 javac 애너테이션 처리 라운드에서 @Entity마다 Q타입 소스를 만들고, 같은 컴파일의 다음 라운드에서 컴파일된다.
    설정의 핵심
    런타임용 querydsl-jpa와 프로세서용 querydsl-apt 모두 jakarta 분류자를 붙이고, 프로세서 경로에는 jakarta.persistence-api를 둔다. 빠지면 프로세서가 NoClassDefFoundError로 실패한다.
    표현식 트리와 직렬화
    book.price.loe(30000)는 연산자와 경로·상수 노드로 된 객체를 만들 뿐이고, 실행 시 JPQLSerializer가 이를 위치 파라미터를 가진 JPQL로 바꿔 EntityManager에 넘긴다.
    동적 쿼리 규칙
    where와 BooleanBuilder.and()는 null 조건을 무시하므로 조건 메서드가 null을 반환하면 되지만, eq(null)이나 null 조건에 대한 and() 호출은 예외가 난다.
    팩토리와 쿼리 객체
    JPAQueryFactory는 공유 EntityManager 프록시를 감싸 빈으로 공유해도 되지만, JPAQuery는 조건이 쌓이는 변경 가능한 객체라서 매번 새로 만든다.
    구조의 트레이드오프
    어댑터로 스프링 데이터 JPA를 숨기면 서비스가 기술에서 독립하지만 위임 코드와 기능 제약이 생기고, 직접 의존하면 단순해지는 대신 기술 교체 시 서비스가 바뀐다.
    기술 혼용과 플러시
    JpaTransactionManager는 JDBC 커넥션을 스레드에 바인딩해 JdbcTemplate과 공유하지만, JDBC로 실행한 SQL은 자동 플러시를 일으키지 않으므로 JPA 변경 뒤에는 em.flush()가 필요하다.

    운영 중인 서비스에서 "특정 검색 조합에서만 500 오류가 난다"는 보고가 들어오면, 문자열로 조립한 동적 JPQL이 가장 먼저 의심할 대상이다. 조합 수가 늘어날수록 테스트가 모든 분기를 밟기 어렵고, 오류는 그 분기가 실행될 때에만 드러난다. Querydsl로 바꾸면 문자열 모양의 오류는 사라지지만, 그 대신 Q타입과 엔티티가 어긋나는 빌드 문제가 생길 수 있다. CI에서 항상 깨끗한 빌드(clean build)를 돌리는 것이 그 위험을 줄인다. 또 Querydsl 원본 프로젝트의 릴리스가 5.1.0에서 멈춰 있다는 사실은 의존성 선택에서 고려해야 할 위험이다. 포크로 옮길지, 그대로 쓸지는 사용하는 Hibernate 버전과의 호환성을 직접 확인하고 판단할 문제다.

    저장소 구조는 팀과 시스템의 수명에 따라 판단이 달라진다. 저장 기술이 실제로 둘 이상이거나(예: 같은 기능을 관계형 DB와 외부 API로 각각 구현), 테스트에서 저장소를 가짜 구현으로 갈아 끼워야 한다면 인터페이스와 어댑터의 비용은 충분히 값을 한다. 반대로 JPA를 계속 쓸 것이 분명한 일반적인 업무 시스템에서 모든 리포지토리에 어댑터를 두면, 코드량은 늘고 스프링 데이터의 기능은 쓰지 못하는 상태가 된다. 추상화는 변경 가능성이 확인되었을 때 도입해도 늦지 않다.

    JPA와 JdbcTemplate을 섞는 코드에서 생기는 장애는 대개 조용하다. 예외가 나지 않고 "가끔 옛 값이 보인다"나 "보고서 숫자가 방금 수정한 값을 반영하지 않는다" 같은 데이터 불일치로 나타난다. 이런 보고를 받으면 같은 트랜잭션 안에서 JPA 변경과 JDBC 조회의 순서, 그리고 그 사이에 플러시가 있는지를 먼저 확인한다. 반대로 JDBC로 대량 수정을 한 뒤 JPA로 같은 엔티티를 다시 다루는 코드라면 1차 캐시에 낡은 객체가 남아 있지 않은지를 본다. 트랜잭션 매니저를 직접 여러 개 등록했다면, @Transactional이 어느 매니저를 쓰는지와 두 기술이 정말 같은 커넥션을 쓰는지도 확인 대상이다.
  • 제목 키워드, 최소 가격, 최대 가격, 재고 있음 여부의 네 가지 선택 조건으로 도서를 검색한다. 문자열 JPQL 조립 방식이라면 조건 조합이 몇 가지이고, where/and 처리와 파라미터 바인딩에서 각각 어떤 분기가 필요한지 적어 보라. 같은 검색을 Querydsl의 조건 메서드로 쓰면 메서드가 몇 개 필요한가?
  • Book 엔티티의 title 필드 이름을 name으로 바꾸고, 빌드 디렉터리를 지우지 않은 채 IDE의 증분 컴파일만 했더니 book.title.contains(kw)를 쓰는 쿼리가 컴파일은 되는데 실행 시점에 실패했다. 어떤 상황에서 이런 일이 가능한지, 그리고 실패는 어느 단계(직렬화, createQuery, SQL 실행)에서 날지 설명하라.
  • 다음 코드는 키워드가 비어 있을 때 예외가 난다. 어떤 예외가 왜 나는지 설명하고, 두 가지 방법으로 고쳐라. query.selectFrom(book).where(titleContains(kw).and(priceAtMost(max))).fetch();
  • @Service의 한 @Transactional 메서드에서 스프링 데이터 JPA로 주문 엔티티의 상태를 "취소"로 바꾼 뒤, MyBatis 매퍼로 "취소되지 않은 주문의 합계"를 SQL로 계산했더니 방금 취소한 주문이 합계에 포함되었다. 두 기술이 같은 커넥션을 쓰는지, 그리고 왜 이런 결과가 나왔는지를 트랜잭션 동기화와 플러시 관점에서 설명하고 고치는 방법을 제시하라.

    1번. 네 조건이 각각 있거나 없으므로 2의 4제곱, 16가지 조합이다. 문자열 방식에서는 조건마다 "앞에 where가 이미 붙었는가"를 판단하는 분기(또는 where 1=1 같은 요령)가 필요하고, 같은 네 조건을 바인딩 쪽에서 다시 한 번 분기해야 하므로 판단이 최소 8곳에 흩어진다. Querydsl에서는 조건마다 null 또는 조건식을 반환하는 메서드 네 개(titleContains, priceAtLeast, priceAtMost, inStock)를 만들어 where에 나란히 넘기면 된다. 직렬화기가 where/and를 배치하고, 값은 조건식 안에 들어 있어 바인딩 분기가 사라진다. 조합 수가 16이어도 작성할 코드는 조건 수에 비례한다.

    2번. 이전 빌드에서 생성된 QBook이 그대로 남아 있으면 title 필드도 남아 있으므로 컴파일러는 book.title을 유효한 필드로 본다. Q타입은 엔티티를 컴파일할 때 애너테이션 프로세서가 다시 만들어야 갱신되는데, 증분 컴파일이 프로세서를 다시 실행하지 않았거나 생성 위치가 둘로 갈라져 옛 파일이 클래스패스에 남은 경우다. 직렬화 단계는 경로 이름을 문자열로 옮겨 적을 뿐 엔티티를 검사하지 않으므로 book.title like ?1을 정상적으로 만든다. 실패는 EntityManager.createQuery에서 Hibernate가 JPQL을 해석하며 Book에 title 속성이 없음을 발견할 때 난다. SQL 실행까지 가지 않는다. 깨끗한 빌드로 Q타입을 다시 생성하면 그때 book.title이 컴파일 오류가 된다.

    3번. kw가 비어 있으면 titleContains(kw)가 null을 반환하고, null에 대해 .and(...)를 호출하므로 NullPointerException이 난다. where가 null을 무시하는 것은 인자로 받은 null이지, 호출 대상이 null인 경우가 아니다. 고치는 방법 하나는 where(titleContains(kw), priceAtMost(max))처럼 가변 인자로 나란히 넘기는 것이다. 다른 하나는 BooleanBuilder를 만들어 builder.and(titleContains(kw)); builder.and(priceAtMost(max));로 누적한 뒤 where에 넘기는 것이다. 빌더의 and()는 null 인자를 무시한다.

    4번. Boot가 등록한 JpaTransactionManager는 트랜잭션 시작 시 JpaDialect로 EntityManager의 JDBC 커넥션을 꺼내 DataSource를 키로 스레드에 바인딩한다. MyBatis-Spring도 SpringManagedTransaction.openConnection()에서 DataSourceUtils.getConnection(dataSource)로 커넥션을 얻으므로, 같은 DataSource를 쓰는 한 같은 커넥션, 같은 트랜잭션을 쓴다. 그런데 상태 변경은 변경 감지로 처리되어 플러시 전까지 UPDATE가 나가지 않고, MyBatis의 SQL은 Hibernate를 거치지 않아 자동 플러시를 일으키지 않는다. 그래서 데이터베이스 행은 아직 "취소 전" 상태이고 합계에 포함된다. 상태를 바꾼 직후, MyBatis 호출 전에 EntityManager.flush()(스프링 데이터라면 saveAndFlush나 flush())를 호출하면 같은 트랜잭션 안에서 UPDATE가 먼저 실행되어 합계에서 빠진다. 커밋 전이어도 같은 트랜잭션은 자기 변경을 본다.

     JPA Criteria에서 cb.le(root.get("title"), 1000)처럼 문자열 필드를 숫자와 비교하는 코드가 컴파일되는 이유로 가장 정확한 것은? javac가 JPA 애너테이션을 읽어 title의 타입을 자동으로 숫자로 변환하기 때문 Path.get(String)이 반환 타입 Y를 인자 문자열과 무관하게 호출 위치의 기대 타입에서 추론하는 제네릭 메서드이기 때문 Criteria API는 내부적으로 문자열 JPQL을 만들어 쓰기 때문에 컴파일러가 관여하지 않기 때문 title 필드가 private이라서 컴파일러가 타입을 볼 수 없기 때문 get의 시그니처는 Path get(String)이다. Y는 속성 이름 문자열과 연결되어 있지 않으므로 컴파일러는 le의 매개변수 타입(Expression)에 맞춰 Y를 추론하고 통과시킨다. javac는 JPA 애너테이션의 의미를 모르고, 접근 제어자는 이 추론과 관계가 없다. 정적 메타모델(Book_.title)을 쓰면 이 공백이 메워진다. Gradle 설정에서 implementation에는 jakarta.persistence-api가 있지만 annotationProcessor에는 querydsl-apt만 있고 jakarta.persistence-api가 없다. 컴파일하면 어떻게 되는가? 엔티티 소스 컴파일도 실패한다. @Entity를 찾을 수 없기 때문이다 정상적으로 Q타입이 생성된다. 프로세서는 컴파일 클래스패스를 함께 보기 때문이다 프로세서가 실행되다가 jakarta/persistence/Entity에 대한 NoClassDefFoundError로 실패한다 Q타입은 생성되지만 @Generated 애너테이션이 빠진다 소스의 @Entity는 컴파일 클래스패스로 해석되지만, 프로세서 코드는 프로세서 경로의 클래스 로더에서 실행되며 jakarta.persistence.Entity를 직접 참조한다. 실험에서 JPAAnnotationProcessor.createConfiguration이 NoClassDefFoundError를 던졌다. 두 경로는 서로를 보지 않는다. @Generated는 JDK의 javax.annotation.processing.Generated라 이 문제와 무관하다. 다음 중 Querydsl JPA 5.1.0에서 예외 없이 올바른 쿼리를 만드는 것은? (kw와 max는 모두 null이다) query.selectFrom(book).where(titleContains(kw), priceAtMost(max)).fetch() (두 메서드는 값이 null이면 null을 반환) query.selectFrom(book).where(book.title.eq(kw)).fetch() query.selectFrom(book).where(titleContains(kw).and(priceAtMost(max))).fetch() query.selectFrom(book).where(book.price.loe(max)).fetch() where는 null 조건을 무시하므로 첫 번째 보기는 where 절 없는 전체 조회가 된다. 두 번째 보기의 eq(null)은 "Use isNull() instead"라는 IllegalArgumentException을, 네 번째 보기의 loe(null)은 상수 노드를 만들다 NullPointerException을 던진다. 세 번째 보기는 null인 조건에 대해 and()를 호출하므로 NullPointerException이다. 한 @Transactional 메서드에서 JPA 엔티티의 필드를 바꾼 직후 JdbcTemplate으로 그 행을 조회했더니 옛 값이 나왔다. 원인으로 가장 정확한 것은? JpaTransactionManager가 JdbcTemplate에 별도의 커넥션을 주어 다른 트랜잭션이 되었기 때문 격리 수준 때문에 커밋되지 않은 변경은 같은 트랜잭션에서도 보이지 않기 때문 JdbcTemplate이 결과를 캐시하기 때문 변경 감지의 UPDATE는 플러시 때 나가는데, JdbcTemplate의 SQL은 Hibernate를 거치지 않아 자동 플러시를 일으키지 않기 때문 JpaTransactionManager는 EntityManager의 커넥션을 DataSource 키로 스레드에 바인딩하므로 JdbcTemplate은 같은 커넥션을 쓴다. 같은 트랜잭션은 자기의 미커밋 변경을 본다. 문제는 변경이 아직 데이터베이스로 가지 않았다는 것이다. JPA 명세의 AUTO 플러시 보장은 영속성 제공자를 통해 실행되는 쿼리에 대한 것이라 JDBC 직접 호출에는 적용되지 않는다. JdbcTemplate에는 결과 캐시가 없다. JPAQueryFactory를 싱글톤 빈으로 등록해 여러 스레드가 공유하는 것이 안전한 이유와, 같은 이유로 공유하면 안 되는 것의 조합으로 맞는 것은? JPAQueryFactory가 내부에서 synchronized를 쓰기 때문에 안전하고, Q타입 인스턴스는 공유하면 안 된다 JPAQueryFactory는 공유 EntityManager 프록시를 붙잡고 호출마다 새 JPAQuery를 만들 뿐이라 안전하고, 조건이 쌓이는 JPAQuery 객체는 공유하면 안 된다 EntityManager 자체가 스레드 안전하기 때문에 안전하고, JPAQueryFactory를 여러 개 만들면 안 된다 Querydsl 쿼리는 모두 불변이라 무엇이든 공유해도 된다 바이트코드상 JPAQueryFactory는 EntityManager를 공급자로 감싸 보관하고 query()마다 new JPAQuery를 만든다. 주입된 EntityManager는 현재 트랜잭션의 실제 EntityManager로 위임하는 스레드 안전한 프록시다. 실제 EntityManager 인스턴스는 스레드 안전하지 않다. JPAQuery는 where마다 메타데이터에 조건을 추가하는 변경 가능한 객체이므로 공유하면 조건이 섞인다. Q타입 인스턴스는 final 필드로 된 경로 객체라 공유해도 된다.
    Querydsl
    쿼리를 자바 객체의 조합으로 표현하고, 그 표현식 트리를 JPQL이나 SQL 문자열로 직렬화해 실행하는 타입 안전한 쿼리 빌더 라이브러리.
    Q타입(query type)
    애너테이션 프로세서가 엔티티마다 생성하는 QBook 같은 클래스. 엔티티 필드마다 타입에 맞는 경로 객체(StringPath, NumberPath 등)를 가진다.
    애너테이션 프로세서(annotation processor)
    javac 컴파일 중에 실행되는 플러그인. JSR 269 API로 작성되며, 소스 구조를 읽고 새 파일을 생성할 수 있지만 기존 소스를 고칠 수는 없다.
    처리 라운드(processing round)
    javac가 애너테이션 처리를 반복하는 단위. 한 라운드에서 생성된 소스는 다음 라운드의 입력이 되고, 새 파일이 없으면 마지막 라운드로 끝난다.
    분류자(classifier)
    Maven 좌표에서 같은 그룹·아티팩트·버전 아래 여러 jar 중 하나를 고르는 꼬리표. Querydsl은 jakarta 분류자로 jakarta.* 패키지용 jar를 제공한다.
    표현식 트리(expression tree)
    연산자 노드와 경로·상수 노드로 이루어진 쿼리의 객체 표현. 생성 시점에는 아무것도 실행하지 않고, 직렬화될 때 쿼리 문자열이 된다.
    정적 메타모델(static metamodel)
    JPA 명세가 정의한, 엔티티 속성을 타입 정보와 함께 담은 생성 클래스(Book_). Criteria API에서 문자열 속성 이름 대신 쓸 수 있다.
    사용자 정의 구현 조각(custom fragment)
    스프링 데이터 리포지토리에 직접 구현한 메서드를 합성하는 방식. 조각 인터페이스 이름에 Impl을 붙인 구현 클래스를 자동으로 찾아 기본 구현보다 우선해 쓴다.
    쓰기 지연(write-behind)
    영속성 컨텍스트가 엔티티 변경을 바로 SQL로 보내지 않고 모아 두었다가 플러시 때 데이터베이스로 보내는 방식.
