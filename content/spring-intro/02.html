    이 회차의 질문: 서버는 브라우저에 무엇을 돌려주는가

    01회에서 프로젝트를 빌드해 실행하면 내장 톰캣이 포트 하나를 열고 요청을 기다린다는 데까지 왔다. 이제 물어야 할 것은 그 다음이다. 요청이 하나 들어왔을 때 서버는 무엇을 돌려주는가. 스프링으로 웹 개발을 시작하면 이 질문의 답으로 정적 컨텐츠, MVC와 템플릿 엔진, API라는 세 가지 방식을 만나게 된다.

    세 방식은 따로 외워야 할 세 가지 기술처럼 보이지만, 네트워크 선 위에서는 서로 구분되지 않는다. 어느 방식이든 서버가 보내는 것은 HTTP 응답 하나이고, HTTP 응답은 상태 코드, 헤더 몇 줄, 본문 바이트로 이루어진다. 브라우저는 서버 안에서 파일을 읽었는지, 템플릿을 채웠는지, 객체를 변환했는지 알지 못한다. 받은 바이트와 그 바이트의 종류를 알려 주는 헤더만 본다.

    그렇다면 세 방식의 차이는 한 가지 물음으로 줄어든다. 응답 본문의 바이트를 누가, 무엇으로부터 만드는가. 정적 컨텐츠(static content)는 미리 만들어 둔 파일을 그대로 보낸다. MVC와 템플릿 엔진(template engine)은 요청마다 서버가 데이터를 템플릿에 채워 HTML을 만들어 보낸다. API는 화면을 만들지 않고 데이터만 정해진 형식(대개 JSON)으로 보낸다.

    이 회차는 먼저 HTTP 응답을 바이트 수준에서 확인하고, JDK만으로 세 방식을 직접 만들어 본다. 그 다음 스프링 안으로 들어가 요청 하나가 톰캣의 스레드에 실려 DispatcherServlet에 도착하고, 거기서 세 갈래로 나뉘어 응답이 되는 과정을 차례로 추적한다. 애너테이션을 어디에 붙이는지보다, 그 애너테이션을 읽는 쪽이 무슨 일을 하는지가 이 회차의 관심사다.

    이 회차의 설명은 Spring Framework 6.2 레퍼런스·Javadoc·소스와 Spring Boot 3.5 레퍼런스를 근거로 한다. 스프링의 요청·응답 예시는 이 컴퓨터에 있던 Spring Boot 4.1.2(Spring Framework 7.0.10, 톰캣 11.0.27)로 직접 실행해 curl로 받은 것에서 Date 헤더를 덜어 낸 것이고, 결과는 6.2 소스의 알고리즘으로 설명되는 것과 일치했다. 버전에 따라 달라지는 것으로 확인한 부분은 그 자리에서 밝힌다. 타임리프는 직접 실행하지 못해, 렌더링 결과는 타임리프 문서의 규칙에 따라 적었다.

    HTTP 응답 하나를 뜯어 본다

    HTTP는 요청과 응답을 주고받는 프로토콜이다. RFC 9110은 HTTP를 상태를 유지하지 않는(stateless) 요청/응답 프로토콜이라고 설명하고(3.4절), 메시지 하나가 메시지를 설명하고 전달하기 위한 제어 데이터(control data), 헤더 필드(header fields), 내용(content) 등으로 이루어진다고 정의한다(6절). HTTP/1.1에서는 이것이 사람이 읽을 수 있는 텍스트 몇 줄과 그 뒤에 붙는 바이트 덩어리로 표현된다.

    아래는 다음 절에서 만들 서버에 curl -v로 요청을 보냈을 때 실제로 오간 메시지다. 위가 요청, 아래가 응답이다.

    GET /api/greeting?name=jiho HTTP/1.1
Host: localhost:8081
User-Agent: curl/8.7.1
Accept: */*

    HTTP/1.1 200 OK
Date: Sun, 15 Nov 2026 09:49:07 GMT
Content-type: application/json
Content-length: 43

{"name":"jiho","message":"반갑습니다"}

    요청의 첫 줄에는 메서드(GET), 요청 대상(/api/greeting?name=jiho), 프로토콜 버전이 있다. 물음표 뒤의 name=jiho는 쿼리 스트링(query string)이고, 클라이언트가 서버에 값을 넘기는 가장 단순한 통로다. 그 아래 줄들은 헤더이고, 빈 줄 하나가 헤더의 끝을 알린다. GET 요청은 보통 본문이 없으므로 여기서 끝난다.

    응답의 첫 줄에는 상태 코드(200)가 있다. 헤더가 이어지고, 빈 줄 뒤에 본문이 온다. 서버가 하는 일은 이 세 부분을 채우는 것이 전부다. 이 회차에서 만나는 스프링의 모든 구성 요소는 결국 "상태 코드를 무엇으로 할까, 헤더에 무엇을 적을까, 본문에 어떤 바이트를 쓸까"를 나누어 맡는다.

    Content-Type: 바이트를 어떻게 읽을지 알려 주는 헤더

    본문은 바이트의 나열일 뿐이라서, 그것이 HTML인지 JSON인지 이미지인지는 본문만 보아서는 확정할 수 없다. 이를 알려 주는 것이 Content-Type 헤더다. RFC 9110 8.3절은 이 헤더가 표현의 미디어 타입(media type)을 나타낸다고 정의한다. 미디어 타입은 text/html, application/json처럼 "타입/서브타입" 꼴로 쓰고, 뒤에 ;charset=UTF-8 같은 매개변수를 붙일 수 있다.

    브라우저는 이 헤더를 보고 바이트를 다루는 방법을 정한다. text/html이면 HTML로 해석해 화면을 그리고, application/json이면 화면으로 그리지 않고 데이터로 취급한다. 같은 바이트라도 헤더가 다르면 다르게 다뤄진다. 헤더가 아예 없으면 받는 쪽이 application/octet-stream(정체를 모르는 바이트)으로 가정하거나 데이터를 들여다보고 추측해도 된다고 같은 절이 적고 있다. 추측에 맡기지 않으려면 서버가 정확히 적어 줘야 한다.

    Content-length: 43은 본문의 길이인데, 글자 수가 아니라 바이트 수다. 위 JSON에서 ASCII 문자는 28개이고 한글은 "반갑습니다" 다섯 글자다. UTF-8에서 한글 한 글자는 3바이트이므로 28 + 5×3 = 43이 된다. 문자열을 응답으로 보내려면 반드시 어떤 문자 인코딩으로 바이트로 바꿔야 하고, charset 매개변수는 그 인코딩이 무엇이었는지 받는 쪽에 알려 준다.

    Accept: 클라이언트가 원하는 형식

    요청에도 형식과 관련된 헤더가 있다. Accept는 사용자 에이전트가 응답으로 받고 싶은 미디어 타입의 선호를 서버에 알리는 데 쓰인다(RFC 9110 12.5.1절). curl이 보낸 */*는 모든 미디어 타입을 뜻하므로 "무엇이든 괜찮다"는 말이다. 브라우저가 주소창에서 보내는 요청은 text/html을 앞세운 목록을 보낸다. 이 헤더는 뒤에서 스프링이 응답 형식을 고를 때 실제 입력으로 쓰인다.

    택배 상자와 송장본문은 내용물, 헤더는 송장

    HTTP 응답을 택배 상자로 보면 본문은 내용물이고 헤더는 상자에 붙은 송장이다. 받는 사람은 송장의 품목란(Content-Type)을 보고 상자를 냉장고에 넣을지 책장에 꽂을지 정한다. 이 비유는 한 군데서 깨진다. 택배는 열어 보면 내용물이 무엇인지 알 수 있지만, 바이트는 열어 봐도 여러 방식으로 해석될 수 있다. 그래서 HTTP에서는 송장이 내용물의 정체를 사실상 결정한다.

    프레임워크 없이 세 방식을 만들어 본다

    스프링을 보기 전에, 세 방식이 정말로 "본문을 만드는 방법"만 다른지 JDK만으로 확인해 보자. JDK에는 간단한 HTTP 서버 API(com.sun.net.httpserver)가 들어 있다. 경로마다 HttpHandler를 등록하면, 요청이 올 때 그 핸들러의 handle 메서드가 요청·응답을 담은 HttpExchange 객체와 함께 호출된다. 아래 프로그램은 앞 권까지 배운 문법만 쓴다.

    {{name}} 님, 반갑습니다
    import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpHandler;
import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.net.InetSocketAddress;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

public class ThreeWays {

    public static void main(String[] args) throws IOException {
        HttpServer server = HttpServer.create(new InetSocketAddress(8081), 0);
        server.createContext("/guide.html", new StaticHandler());
        server.createContext("/greeting", new TemplateHandler());
        server.createContext("/api/greeting", new ApiHandler());
        server.start();
    }

    // 1) 정적 컨텐츠: 파일의 바이트를 그대로 보낸다
    static class StaticHandler implements HttpHandler {
        @Override
        public void handle(HttpExchange ex) throws IOException {
            byte[] body = Files.readAllBytes(Path.of("site/guide.html"));
            send(ex, "text/html;charset=UTF-8", body);
        }
    }

    // 2) 템플릿: 파일을 읽어 빈칸을 채운 뒤 보낸다
    static class TemplateHandler implements HttpHandler {
        @Override
        public void handle(HttpExchange ex) throws IOException {
            String name = queryValue(ex, "name");
            String template = Files.readString(Path.of("site/greeting.tpl"));
            String html = template.replace("{{name}}", name);
            send(ex, "text/html;charset=UTF-8", html.getBytes(StandardCharsets.UTF_8));
        }
    }

    // 3) API: 화면 없이 데이터만 보낸다
    static class ApiHandler implements HttpHandler {
        @Override
        public void handle(HttpExchange ex) throws IOException {
            String name = queryValue(ex, "name");
            String json = "{\"name\":\"" + name + "\",\"message\":\"반갑습니다\"}";
            send(ex, "application/json", json.getBytes(StandardCharsets.UTF_8));
        }
    }

    static void send(HttpExchange ex, String contentType, byte[] body) throws IOException {
        ex.getResponseHeaders().set("Content-Type", contentType);
        ex.sendResponseHeaders(200, body.length);   // 상태 코드와 본문 길이(바이트)
        ex.getResponseBody().write(body);           // 본문 바이트
        ex.close();
    }

    // "name=jiho" 같은 쿼리 스트링에서 값을 꺼낸다(예제용으로 단순화했다)
    static String queryValue(HttpExchange ex, String key) {
        String query = ex.getRequestURI().getQuery();
        if (query != null) {
            for (String pair : query.split("&")) {
                String[] kv = pair.split("=", 2);
                if (kv.length == 2 && kv[0].equals(key)) {
                    return kv[1];
                }
            }
        }
        return "손님";
    }
}

    세 핸들러의 마지막 줄은 모두 send다. send는 Content-Type 헤더를 적고, 상태 코드 200과 본문 길이를 보내고, 본문 바이트를 쓴다. 세 핸들러가 다른 점은 send에 넘길 바이트 배열을 어디서 얻느냐뿐이다. 첫째는 파일을 읽은 그대로, 둘째는 파일을 읽어 {{name}} 자리를 요청에서 꺼낸 값으로 바꾼 문자열, 셋째는 코드로 조립한 JSON 문자열이다. JDK 21에서 실행하고 curl로 세 경로를 차례로 요청한 결과는 다음과 같다(Date 헤더는 실행 시각이라 생략했다).

Content-length: 94

    이 70줄에 없는 것들

    이 프로그램은 세 방식의 본질을 보여 주지만 실제 서비스에 쓸 수는 없다. 무엇이 빠져 있는지 짚어 보면 스프링이 맡는 일이 그대로 드러난다.

    • 경로와 코드를 잇는 표를 손으로 만든다. 경로가 늘 때마다 createContext를 한 줄씩 추가해야 하고, 정적 파일도 파일마다 등록해야 한다. GET과 POST도 구분하지 않는다.
    • 요청 값을 손으로 꺼낸다. 쿼리 스트링을 직접 쪼개고, 값이 없을 때의 처리도 직접 한다. 숫자가 필요하면 변환도, 변환 실패 처리도 직접 해야 한다.
    • 출력을 안전하게 만들지 않는다. /greeting?name=%3Cb%3Ejiho%3C%2Fb%3E처럼 name에 태그를 넣어 요청하면 응답 HTML에 jiho가 태그 그대로 들어간다. 요청한 사람이 페이지의 구조를 바꿀 수 있다는 뜻이다. API 쪽도 name에 큰따옴표가 들어오면 {"name":"a"b", ...}처럼 깨진 JSON이 나간다. 둘 다 실제로 실행해 확인한 결과다.
    • 형식 협상이 없다. 클라이언트가 Accept에 무엇을 적어 보내든 무시한다.
    • 캐시, 오류 응답, 동시 요청 처리에 대한 고려가 없다.

    스프링 MVC는 이 빈자리를 구성 요소 하나씩으로 채운다. 아래 표는 방금 만든 프로그램의 각 부분이 스프링에서 무엇에 대응하는지를 미리 보여 준다. 이름들은 뒤에서 하나씩 설명하므로 지금은 지도로만 보아 둔다.

    직접 만든 서버의 부분스프링 부트 웹 애플리케이션에서 맡는 것
    HttpServer: 소켓을 열고 HTTP를 해석내장 톰캣
    createContext(경로, 핸들러): 경로와 코드를 잇는 표DispatcherServlet과 HandlerMapping
    queryValue: 요청에서 값을 꺼내기HandlerAdapter의 인자 해석(@RequestParam 등)
    StaticHandler: 파일을 그대로 보내기ResourceHttpRequestHandler
    TemplateHandler의 replace: 템플릿 채우기ViewResolver와 템플릿 엔진(타임리프)
    ApiHandler의 문자열 조립: 데이터를 바이트로HttpMessageConverter(Jackson)

    요청이 스프링에 닿기까지: 톰캣의 스레드와 DispatcherServlet

    스프링 부트 웹 애플리케이션에서 소켓을 열고 HTTP를 읽는 일은 스프링이 아니라 내장 톰캣이 한다. Spring Boot 레퍼런스에 따르면 내장 서버는 기본으로 8080 포트에서 HTTP 요청을 기다린다. 톰캣은 연결을 받아들이고, 들어온 바이트를 HTTP 요청으로 해석해 자바 객체(HttpServletRequest)로 만들고, 응답을 쓸 객체(HttpServletResponse)를 준비한다. 앞 절의 HttpExchange 하나가 하던 역할을 요청 객체와 응답 객체 둘로 나눈 셈이다.

    톰캣이 이 두 객체를 넘겨주는 상대가 서블릿(servlet)이다. 서블릿은 Jakarta Servlet 규격이 정한 "요청 객체와 응답 객체를 받아 처리하는 자바 객체"이고, 톰캣은 요청 경로에 맞는 서블릿을 골라 호출한다. 스프링 MVC는 서블릿을 여러 개 만들지 않는다. DispatcherServlet이라는 서블릿 하나를 두고, 스프링 부트는 이것을 기본 경로 /에 등록해 모든 요청이 이 서블릿으로 들어오게 한다. 입구를 하나로 모으고 그 안에서 실제 처리 담당을 찾아 넘기는 이 구조를 프론트 컨트롤러(front controller) 패턴이라고 한다.

    요청을 실어 나르는 것은 스레드(thread)다. 스레드는 한 프로세스 안에서 코드를 따로따로 실행해 나가는 흐름이고, 스레드마다 자기만의 호출 스택을 가진다. 톰캣은 요청을 처리할 작업 스레드(worker thread)를 풀(pool)로 관리하며, 스프링 부트의 기본 설정에서 그 최대 개수는 200이다(server.tomcat.threads.max). 요청 하나가 오면 풀에서 꺼낸 스레드 하나가 그 요청을 맡는다. 그 스레드가 DispatcherServlet의 메서드를 호출하고, 그 안에서 컨트롤러의 메서드를 호출하고, 응답을 쓰는 데까지 메서드 호출이 한 스택 위에 차례로 쌓였다가 풀린다. 처리가 끝나면 스레드는 풀로 돌아가 다음 요청을 기다린다.

    DispatcherServlet은 직접 일하지 않는다

    DispatcherServlet은 요청 처리의 순서만 쥐고 있고 실제 일은 역할별로 나뉜 객체들에게 맡긴다. 스프링 레퍼런스는 이 객체들을 특별한 빈 타입(special bean types)이라고 부른다. 이 회차에 필요한 것은 네 가지다.

    타입맡는 일이 회차에서 만나는 구현
    HandlerMapping요청을 처리할 핸들러(handler)를 찾는다. 핸들러는 "이 요청을 처리할 코드"를 가리키는 말이다.RequestMappingHandlerMapping(애너테이션 컨트롤러), 정적 리소스용 매핑
    HandlerAdapter찾은 핸들러를 실제로 호출한다. 핸들러의 종류마다 호출 방법이 달라서 그 차이를 감춘다.RequestMappingHandlerAdapter, HttpRequestHandlerAdapter
    ViewResolver핸들러가 돌려준 문자열 뷰 이름을 실제 View 객체로 바꾼다.ThymeleafViewResolver
    HandlerExceptionResolver처리 중 발생한 예외를 응답(상태 코드, 오류 화면 등)으로 바꾼다.DefaultHandlerExceptionResolver

    레퍼런스가 설명하는 처리 순서 가운데 이 회차와 관련된 부분은 세 단계다. 먼저 알맞은 핸들러를 찾는다. 다음으로 그 핸들러와 묶인 실행 체인을 실행해 렌더링에 쓸 모델을 준비한다. 마지막으로 모델이 반환되면 뷰를 렌더링한다. 여기에 예외 조항이 하나 붙어 있다. 애너테이션 컨트롤러는 뷰를 반환하는 대신 HandlerAdapter 안에서 응답을 직접 써 버릴 수 있다. 앞의 흐름이 MVC 방식이고, 이 예외 조항이 API 방식이다.

    핸들러 매핑에는 순서가 있다

    HandlerMapping은 하나가 아니라 여러 개가 등록되고, DispatcherServlet은 순서(order) 값이 작은 것부터 차례로 물어 처음으로 핸들러를 돌려준 매핑을 따른다. 스프링 MVC의 기본 구성(WebMvcConfigurationSupport)이 등록하는 매핑과 순서 값은 Javadoc에 적혀 있다.

    순서 값핸들러 매핑찾는 것
    -1RouterFunctionMapping함수형 라우터(이 회차에서는 쓰지 않는다)
    0RequestMappingHandlerMapping@GetMapping 같은 애너테이션이 붙은 컨트롤러 메서드
    1, 2뷰 컨트롤러 매핑, BeanNameUrlHandlerMapping경로를 뷰 이름이나 빈 이름에 직접 연결한 것
    Integer.MAX_VALUE - 1정적 리소스 매핑정적 파일
    Integer.MAX_VALUE기본 서블릿 매핑서블릿 컨테이너의 기본 서블릿으로 넘기기

    이 표에서 기억할 것은 컨트롤러 매핑이 0이고 정적 리소스 매핑이 거의 맨 끝이라는 점이다. 요청이 오면 스프링은 먼저 컨트롤러에서 찾고, 없을 때 비로소 정적 파일을 찾는다. 세 방식은 이 지점부터 갈라진다.

    브라우저 / curl
   │  TCP 연결 위로 HTTP 요청 바이트
   ▼
내장 톰캣 ── 요청을 해석해 HttpServletRequest / HttpServletResponse 생성
   │         작업 스레드 하나가 이 요청을 끝까지 맡는다
   ▼
DispatcherServlet  (모든 요청의 입구)
   │  HandlerMapping들에게 순서대로 묻는다: "이 요청을 처리할 핸들러가 있는가"
   │
   ├─ 컨트롤러 메서드가 매핑되어 있다 ─▶ RequestMappingHandlerAdapter가 메서드를 호출
   │      ├─ 반환값이 뷰 이름        ─▶ ViewResolver ─▶ 템플릿 엔진이 HTML 생성   [MVC]
   │      └─ @ResponseBody 반환값   ─▶ HttpMessageConverter가 본문에 직접 기록   [API]
   │
   └─ 매핑된 컨트롤러가 없다 ─▶ 정적 리소스 매핑(/**) ─▶ ResourceHttpRequestHandler
                                  └─ 클래스패스의 파일 바이트를 그대로 기록       [정적 컨텐츠]
    모든 요청이 톰캣과 DispatcherServlet이라는 같은 입구를 지나고, 그 아래에서 세 갈래로 나뉘어 각기 다른 구성 요소가 응답 본문을 만든다는 것을 한 장에 보여 준다. 깔끔한 기술 구조 다이어그램. 왼쪽에 노트북 아이콘과 라벨 "브라우저". 거기서 오른쪽으로 화살표가 나가 "내장 톰캣"이라고 적힌 큰 상자로 들어간다. 톰캣 상자 안에는 작은 사람 모양 아이콘 여러 개가 줄지어 있고 라벨 "작업 스레드 풀". 톰캣 상자 오른쪽에 "DispatcherServlet"이라고 적힌 마름모 모양 분기점. 분기점에서 오른쪽으로 세 갈래 화살표가 위·가운데·아래로 뻗는다. 위쪽 갈래 끝에는 파일 아이콘과 라벨 "정적 컨텐츠: 파일 그대로". 가운데 갈래는 "컨트롤러" 상자를 지나 "템플릿 엔진" 상자로 이어지고 끝에 라벨 "MVC: HTML 생성". 아래쪽 갈래는 같은 "컨트롤러" 상자에서 갈라져 "HttpMessageConverter" 상자로 이어지고 끝에 라벨 "API: JSON". 세 갈래의 끝은 모두 오른쪽 가장자리의 긴 세로 막대 "HTTP 응답 본문"으로 모인다. 흰 배경, 파랑·초록·주황 세 가지 색으로 세 경로를 구분, 평면 벡터 스타일, 그림자 없음. 입구는 하나이고 본문을 만드는 담당이 셋이다. 컨트롤러가 매핑되어 있지 않을 때만 정적 리소스 경로로 내려간다.

    정적 컨텐츠: 파일을 그대로 내보내는 경로

    정적 컨텐츠는 서버가 내용에 손대지 않고 그대로 내보내는 파일이다. HTML, CSS, 자바스크립트, 이미지가 여기에 속한다. Spring Boot 레퍼런스는 기본 동작을 이렇게 설명한다. 스프링 부트는 클래스패스의 /static(또는 /public, /resources, /META-INF/resources) 디렉터리에서 정적 컨텐츠를 제공하고, 이때 스프링 MVC의 ResourceHttpRequestHandler를 사용하며, 리소스는 기본으로 /** 패턴에 매핑된다. 패턴은 spring.mvc.static-path-pattern으로, 위치는 spring.web.resources.static-locations로 바꿀 수 있다.

    여기서 "클래스패스의 /static"이라는 말을 정확히 읽어야 한다. 소스에서는 src/main/resources/static/guide.html에 파일을 두지만, 실행 중인 애플리케이션은 src 디렉터리를 보지 않는다. 빌드가 src/main/resources 아래의 파일을 컴파일된 클래스와 같은 출력 위치로 복사하고, 실행 가능한 JAR를 만들면 그 내용이 BOOT-INF/classes 아래에 들어간다. 그래서 이 파일은 JAR 안에서 BOOT-INF/classes/static/guide.html이 되고, 애플리케이션은 클래스를 찾을 때와 같은 방법으로, 즉 클래스 로더를 통해 static/guide.html이라는 이름의 리소스를 찾는다. 정적 파일이 JAR 파일 하나에 함께 담겨 배포될 수 있는 이유가 이것이다.

    앞 절의 파일과 같은 내용을 src/main/resources/static/guide.html에 두고 GET /guide.html을 보냈을 때 일어나는 일을 순서대로 따라가 보자.

    HTTP/1.1 200
Last-Modified: Sun, 15 Nov 2026 10:04:23 GMT
Accept-Ranges: bytes
Content-Type: text/html
Content-Length: 94



    이용 안내: 평일 9시부터 18시까지

    본문은 파일과 한 바이트도 다르지 않고, Content-Length는 파일 크기와 같다. Content-Type은 누가 지정한 것이 아니라 .html이라는 확장자에서 나왔다. ResourceHttpRequestHandler의 Javadoc에 따르면 미디어 타입은 리소스의 파일 이름과 확장자를 기준으로 서블릿 컨텍스트의 MIME 타입 표, 핸들러에 등록된 표, 스프링의 MediaTypeFactory를 차례로 찾아 정한다. Last-Modified 값은 그 파일이 마지막으로 수정된 시각이므로 환경마다 다르다.

    이 경로에는 요청의 값을 읽는 단계가 없다. /guide.html?name=jiho처럼 쿼리 스트링을 붙여 요청해도 응답은 위와 완전히 같았다. 정적 컨텐츠가 "정적"인 까닭은 서버 쪽에 그 파일의 내용을 요청에 따라 바꿀 코드가 한 줄도 끼어들지 않기 때문이다.

    같은 경로에 컨트롤러가 있으면 컨트롤러가 이긴다

    핸들러 매핑의 순서에서 바로 나오는 결과가 있다. static/guide.html 파일이 있는 상태에서 /guide.html 경로를 처리하는 컨트롤러 메서드를 추가하면, 순서 0인 컨트롤러 매핑이 먼저 핸들러를 돌려주므로 파일은 더 이상 응답되지 않는다. 실제로 그렇게 구성해 요청하니 파일 내용이 아니라 컨트롤러의 반환값이 응답으로 왔다. 정적 파일이 갑자기 보이지 않는다면 같은 경로를 잡고 있는 컨트롤러가 있는지부터 확인하면 된다.

    반대로 컨트롤러도 없고 파일도 없으면 어떻게 되는가. 정적 리소스 매핑은 패턴이 /**라서 일단 요청을 받지만, ResourceHttpRequestHandler가 설정된 위치 어디에서도 리소스를 찾지 못하면 NoResourceFoundException을 던진다. DefaultHandlerExceptionResolver의 Javadoc 표는 이 예외를 상태 코드 404에 대응시킨다. 없는 주소로 들어갔을 때 보는 404는 대개 이 경로에서 만들어진다.

    조건부 요청과 304

    응답에 Last-Modified가 붙는 데에는 목적이 있다. 브라우저는 받은 파일과 그 수정 시각을 캐시에 넣어 두었다가, 같은 주소를 다시 요청할 때 If-Modified-Since 헤더에 그 시각을 실어 보낸다. RFC 9110 13.1.3절은 이 헤더가 GET이나 HEAD 요청을 대상의 수정 시각에 대한 조건부 요청으로 만든다고 정의한다. "이 시각 이후에 바뀌었을 때만 내용을 달라"는 뜻이다.

    GET /guide.html HTTP/1.1
Host: localhost:8080
If-Modified-Since: Sun, 15 Nov 2026 10:04:23 GMT

HTTP/1.1 304
Last-Modified: Sun, 15 Nov 2026 10:04:23 GMT

    파일이 그 뒤로 바뀌지 않았으므로 서버는 상태 코드 304(Not Modified)만 보내고 본문을 보내지 않는다. 브라우저는 캐시에 있던 사본을 쓴다. ResourceHttpRequestHandler의 Javadoc도 이 핸들러가 Last-Modified를 평가해 적절한 경우 304를 돌려준다고 적고 있다. 앞에서 만든 StaticHandler는 매번 파일 전체를 다시 보냈다. 같은 "파일을 그대로 보낸다"라도 변하지 않은 파일을 다시 보내지 않는 일까지가 정적 컨텐츠 처리에 들어 있다.

    웰컴 페이지와 templates 디렉터리

    정적 위치에 index.html을 두면 / 요청의 응답이 된다. Spring Boot 레퍼런스에 따르면 스프링 부트는 설정된 정적 컨텐츠 위치에서 먼저 index.html을 찾고, 없으면 index라는 이름의 템플릿을 찾아 웰컴 페이지(welcome page)로 쓴다. 이 기능도 핸들러 매핑 하나로 구현되어 있고 그 순서 값은 2다(Spring Boot 3.5의 WelcomePageHandlerMapping). 따라서 /를 처리하는 컨트롤러 메서드를 만들면 순서 0인 컨트롤러가 이기고 index.html은 응답되지 않는다.

    한 가지 구분해 둘 것이 있다. src/main/resources 아래에는 static 말고 templates 디렉터리도 있는데, templates는 정적 위치 목록에 들어 있지 않다. 거기에 둔 HTML 파일은 주소창에 파일 이름을 쳐서는 열리지 않는다. 그 파일들은 다음 절에서 볼 템플릿 엔진의 입력이고, 컨트롤러가 뷰 이름으로 지목했을 때만 읽힌다.

    MVC와 템플릿 엔진: 역할을 셋으로 나눈다

    정적 파일은 요청에 따라 달라질 수 없다. 이름을 넣어 인사하는 페이지를 만들려면 서버가 요청마다 HTML을 새로 만들어야 한다. 앞에서 만든 TemplateHandler가 바로 그 일을 했다. 그런데 그 메서드 하나에는 요청에서 값을 꺼내는 일, 어떤 내용을 보여 줄지 정하는 일, HTML 문자열을 만드는 일이 모두 섞여 있었다. 화면이 수십 개로 늘면 문구 하나를 고치려 해도 자바 코드를 열어야 하고, 처리 로직을 고치다 HTML을 망가뜨리기 쉽다.

    MVC는 이 일을 세 역할로 나누는 설계다. 컨트롤러(Controller)는 요청을 받아 값을 확인하고, 필요한 처리를 시키고, 화면에 보일 데이터를 정하고, 어떤 화면을 쓸지 고른다. 모델(Model)은 컨트롤러가 화면에 넘기는 데이터를 이름과 값의 쌍으로 담는 보관함이다. 뷰(View)는 모델을 받아 HTML을 만들어 응답에 쓴다. 컨트롤러는 HTML을 모르고, 뷰는 데이터가 어디서 왔는지 모른다. 둘 사이의 약속은 모델에 담긴 이름뿐이다.

    package com.example.web;

import org.springframework.stereotype.Controller;
import org.springframework.ui.Model;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;

@Controller
public class GreetingController {

    @GetMapping("/greeting")
    public String greeting(@RequestParam("name") String name, Model model) {
        model.addAttribute("name", name);
        return "greeting";
    }
}

    컨트롤러 메서드의 인자는 누가 채우는가

    greeting(String name, Model model)은 평범한 자바 메서드다. 자바에서 메서드를 호출하려면 호출하는 쪽이 인자를 모두 준비해야 한다. 그런데 컨트롤러 메서드는 개발자마다 매개변수의 개수와 타입이 제각각이다. RequestMappingHandlerAdapter는 처음 보는 메서드에 무엇을 넘겨야 할지를 어떻게 아는가.

    답은 리플렉션(reflection)이다. 리플렉션은 실행 중에 클래스가 가진 메서드, 매개변수의 타입, 붙어 있는 애너테이션을 조회하고, 그렇게 찾은 메서드를 호출할 수 있게 하는 자바의 기능이다. 어댑터는 호출할 메서드의 매개변수를 하나씩 살펴보고, 매개변수마다 "이 타입과 이 애너테이션이면 내가 값을 만들 수 있다"고 나서는 인자 해석기(HandlerMethodArgumentResolver)에게 값을 만들게 한다. 그렇게 모은 값들로 인자 배열을 만들어 메서드를 호출한다.

    @RequestParam("name") String name에서는 요청 파라미터 name의 값을 읽어 온다. @RequestParam의 Javadoc에 따르면 스프링 MVC에서 요청 파라미터는 쿼리 파라미터, 폼 데이터, 멀티파트 요청의 파트를 가리킨다. 서블릿 API가 쿼리 파라미터와 폼 데이터를 "파라미터"라는 하나의 맵으로 합쳐 주기 때문이다. 그래서 값이 URL의 쿼리 스트링으로 왔든 HTML 폼의 본문으로 왔든 컨트롤러 코드는 달라지지 않는다. 두 번째 매개변수 Model model에는 이 요청만을 위한 빈 모델 객체가 들어온다. 컨트롤러가 거기에 넣은 값이 나중에 뷰로 전달된다.

    값이 없거나 타입이 맞지 않을 때

    HTTP로 들어오는 값은 모두 문자열이다. 매개변수 타입이 int라면 어댑터가 문자열 "12"를 숫자 12로 변환해 넘긴다. "abc"처럼 변환할 수 없는 값이 오면 메서드를 호출하기 전에 예외가 발생하고, 응답은 400(Bad Request)이 된다. 실제로 int 매개변수에 abc를 보내니 400이 왔고, 서버 로그에는 String을 int로 변환하지 못했다는 MethodArgumentTypeMismatchException이 기록되었다.

    값이 아예 없을 때도 마찬가지다. @RequestParam의 required 속성은 기본값이 true이고, Javadoc은 파라미터가 요청에 없으면 예외가 발생한다고 적고 있다. GET /greeting처럼 name 없이 요청하면 응답은 400이고 로그에는 다음 줄이 남는다.

    Resolved [org.springframework.web.bind.MissingServletRequestParameterException: Required request parameter 'name' for method parameter type String is not present]

    이 400은 컨트롤러 메서드가 만든 응답이 아니다. 인자를 준비하는 단계에서 예외가 났으므로 메서드는 호출되지도 않았다. 예외는 HandlerExceptionResolver로 넘어가고, DefaultHandlerExceptionResolver가 이 예외 타입을 400에 대응시킨다. 값이 없어도 되는 파라미터라면 required = false로 두어 null을 받거나, defaultValue를 지정한다. Javadoc에 따르면 defaultValue를 주면 required는 암묵적으로 false가 된다. 앞에서 직접 만든 서버가 값이 없을 때 "손님"을 돌려준 것은 defaultValue = "손님"을 손으로 구현한 것이었다.

    매개변수 이름은 클래스 파일에 기본으로 남지 않는다

    위 코드는 @RequestParam("name")처럼 파라미터 이름을 직접 적었다. 이름을 생략하고 @RequestParam String name이라고만 써도 스프링은 매개변수의 이름 name을 요청 파라미터 이름으로 쓴다. 이때 스프링은 실행 중에 메서드 매개변수의 이름을 알아내야 하는데, 여기에 함정이 하나 있다. 리플렉션으로 매개변수 이름을 조회하는 작은 프로그램으로 확인해 보자.

    import java.lang.reflect.Method;
import java.lang.reflect.Parameter;

public class ParamNames {

    public String greet(String name, int count) {
        return name + count;
    }

    public static void main(String[] args) throws Exception {
        Method method = ParamNames.class.getMethod("greet", String.class, int.class);
        for (Parameter p : method.getParameters()) {
            System.out.println(p.getType().getSimpleName() + " " + p.getName()
                    + " (isNamePresent=" + p.isNamePresent() + ")");
        }
    }
}

int arg1 (isNamePresent=false)

$ javac -parameters ParamNames.java && java ParamNames

    옵션 없이 컴파일하면 리플렉션이 돌려주는 이름은 arg0, arg1이다. 소스에 적은 name, count가 사라졌다. 이유는 바이트코드를 보면 알 수 있다. javap -v로 본 greet 메서드의 본문은 다음과 같다.

      public java.lang.String greet(java.lang.String, int);
    descriptor: (Ljava/lang/String;I)Ljava/lang/String;
    Code:

         0: aload_1

         7: areturn

    JVM은 매개변수를 이름으로 다루지 않는다. aload_1은 "지역 변수 1번 칸의 참조를 올려라", iload_2는 "2번 칸의 int를 올려라"라는 뜻이다(0번 칸은 this다). 실행에는 번호만 있으면 되므로 컴파일러는 기본적으로 이름을 클래스 파일에 기록하지 않는다. 이름을 남기는 방법은 두 가지이고, 둘은 서로 다른 곳에 기록된다.

    컴파일 옵션클래스 파일에 남는 것Parameter.getName()
    없음매개변수 이름 없음arg0, arg1
    -g디버그 정보인 LocalVariableTable에 this, name, countarg0, arg1
    -parametersMethodParameters 속성에 name, countname, count

    세 경우 모두 JDK 21에서 직접 컴파일해 확인한 결과다. -g로 남긴 디버그 정보는 디버거가 변수 이름을 보여 주는 데 쓰이고, 자바의 리플렉션 API는 이것을 읽지 않는다. 리플렉션이 읽는 것은 -parameters가 만드는 MethodParameters 속성뿐이다.

    스프링은 예전에 클래스 파일의 디버그 정보를 직접 해석해 이름을 알아내는 방법도 함께 썼다. Spring Framework 6.1 릴리스 노트는 그 구현(LocalVariableTableParameterNameDiscoverer)이 6.1에서 제거되었고, 이제 바이트코드를 해석해 매개변수 이름을 추론하지 않는다고 밝힌다. 따라서 6.1 이후에는 -parameters 없이 컴파일된 클래스에서 이름을 생략한 @RequestParam을 쓰면 이름을 알 길이 없다. 그렇게 구성해 요청을 보내니 응답은 500이었고 로그에 다음 예외가 남았다.

    java.lang.IllegalArgumentException: Name for argument of type [java.lang.String] not specified, and parameter name information not available via reflection. Ensure that the compiler uses the '-parameters' flag.

    스프링 부트의 Gradle 플러그인 문서는 자바 플러그인이 적용된 프로젝트의 모든 JavaCompile 작업에 -parameters 인자를 쓰도록 설정한다고 적고 있다. 그래서 Gradle로 빌드하고 실행하는 한 이 문제를 만나지 않는다. 문제가 생기는 것은 Gradle을 거치지 않고 IDE의 자체 컴파일러로 빌드하도록 설정했는데 그쪽에 이 옵션이 꺼져 있는 경우다. 같은 소스가 실행 방법에 따라 되기도 하고 안 되기도 한다면 원인은 소스가 아니라 클래스 파일에 무엇이 남았느냐에 있다. @RequestParam("name")처럼 이름을 직접 적은 코드는 클래스 파일의 내용에 기대지 않으므로 어느 쪽으로 컴파일해도 동작한다.

    뷰 이름이 HTML이 되기까지: ViewResolver와 템플릿 엔진

    컨트롤러가 반환한 "greeting"은 파일 이름이 아니라 논리적인 뷰 이름이다. 스프링 레퍼런스는 String 반환값을 "ViewResolver 구현으로 해석될 뷰 이름"이라고 설명한다. 뷰 이름을 실제 템플릿 파일과 잇는 규칙은 ViewResolver 쪽에 있다. 스프링 부트는 타임리프 라이브러리가 클래스패스에 있으면 타임리프용 뷰 리졸버와 템플릿 리졸버를 자동으로 구성하고, 그 기본 설정은 접두사 classpath:/templates/, 접미사 .html이다. 뷰 이름 앞뒤에 이 둘을 붙인 classpath:/templates/greeting.html이 템플릿의 위치가 된다.

    이 간접 단계 덕분에 컨트롤러는 화면 기술을 모른다. 템플릿의 위치나 확장자가 바뀌어도, 템플릿 엔진이 다른 것으로 바뀌어도 컨트롤러의 return "greeting"은 그대로다. 대신 치르는 값이 있다. 뷰 이름은 그냥 문자열이므로 컴파일러는 그 이름의 템플릿이 실제로 있는지 검사하지 못한다. 이름의 오타는 요청이 들어와 뷰를 찾는 순간에야 드러난다.

    템플릿 엔진이 하는 일

    템플릿 엔진은 틀(템플릿)과 데이터(모델)를 받아 결과 문서를 만들어 내는 프로그램이다. 앞에서 replace("{{name}}", name) 한 줄로 흉내 낸 일을 제대로 하는 것이다. 타임리프는 템플릿을 읽어 th:로 시작하는 속성을 찾아 처리한다. 타임리프 튜토리얼에 따르면 th:text는 값 표현식을 평가해 그 결과를 해당 태그의 본문으로 넣는다. 원래 태그 안에 있던 내용은 결과로 대체된다.

    예제 템플릿의 표현식은 ${name} + ' 님, 반갑습니다'다. ${...}는 변수 표현식이고, 여기서 name은 컨트롤러가 모델에 넣은 속성의 이름이다. 튜토리얼은 이 표현식이 OGNL 표현식이며 스프링 MVC와 통합된 애플리케이션에서는 OGNL 대신 스프링의 표현 언어(SpringEL)가 쓰인다고 설명한다. 모델의 name이 jiho이므로 표현식의 결과는 jiho 님, 반갑습니다이고, 이것이 p 태그 안의 "손님 님, 반갑습니다"를 대체한다.

    그러면 템플릿에 처음부터 적혀 있던 "손님 님, 반갑습니다"는 왜 있는가. 템플릿 파일을 서버 없이 브라우저로 직접 열면 브라우저는 자기가 모르는 th:text 속성을 무시하고 태그 안의 글자를 그대로 보여 준다. 서버를 거치면 결과물로, 거치지 않으면 견본으로 보이는 것이다. 타임리프는 이것을 내추럴 템플릿(natural templating)이라고 부른다. 템플릿이 그 자체로 올바른 HTML 문서이기 때문에 가능한 일이다.

    이스케이프: 값을 문서에 넣을 때의 안전장치

    직접 만든 서버에서 name에 태그를 넣었을 때 응답 HTML의 구조가 바뀌던 문제를 기억하자. 타임리프의 th:text는 기본 동작으로 값을 이스케이프(escape)한다. HTML에서 특별한 뜻을 가진 문자를 그 문자를 "글자로서" 나타내는 표기로 바꾼다는 뜻이다. 튜토리얼의 설명대로라면 name에 jiho가 들어왔을 때 출력은 다음과 같다.

    &lt;b&gt;jiho&lt;/b&gt; 님, 반갑습니다

    브라우저는 &lt;를 태그의 시작이 아니라 화면에 보일 "작다" 기호로 해석한다. 그래서 화면에는 굵은 글씨가 아니라 입력한 글자가 그대로 보인다. 사용자가 넣은 값이 문서의 구조가 아니라 내용으로만 들어가는 것이다. 이스케이프하지 않은 채로 넣고 싶을 때 쓰는 속성(th:utext)이 따로 있다는 사실이, 이스케이프가 기본값이라는 것을 거꾸로 보여 준다. 입력값이 마크업으로 해석되면 다른 사용자의 브라우저에서 실행될 스크립트를 끼워 넣는 공격(XSS, cross-site scripting)의 통로가 되므로, 이 기본값은 템플릿 엔진이 단순 문자열 치환과 구별되는 중요한 지점이다.

    이 모든 일은 서버에서 끝난다

    템플릿 처리는 응답을 보내기 전에 서버 안에서 끝난다. 브라우저가 받는 것은 완성된 HTML이고, 브라우저에서 페이지 소스를 열어 보면 th:text도 ${name}도 없다. 이렇게 서버가 화면을 완성해 보내는 방식을 서버 사이드 렌더링(server-side rendering)이라고 한다. 요청마다 서버가 HTML을 만들어야 하므로 그만큼 서버의 일이 늘어난다. 스프링 부트의 타임리프 설정에는 템플릿 캐시가 기본으로 켜져 있어(spring.thymeleaf.cache의 기본값이 true) 이미 읽은 템플릿을 다시 쓴다. 개발 중에 템플릿을 고쳤는데 화면이 그대로라면 이 캐시를 먼저 떠올리면 된다.

    API: @ResponseBody와 HttpMessageConverter

    응답을 받는 쪽이 사람이 아니라 프로그램일 때가 있다. 모바일 앱, 브라우저 안에서 실행되는 자바스크립트, 다른 서버가 그렇다. 이들에게 필요한 것은 꾸며진 화면이 아니라 데이터다. 화면은 받는 쪽이 알아서 그린다. 이때 서버가 할 일은 자바 객체로 가지고 있는 데이터를 약속된 형식의 바이트로 바꿔 본문에 싣는 것이다. 같은 컨트롤러에 메서드 두 개를 더하고 데이터를 담을 클래스를 하나 만든다.

        @GetMapping("/api/greeting-text")
    @ResponseBody
    public String greetingText(@RequestParam("name") String name) {
        return name + " 님, 반갑습니다";
    }

    @GetMapping("/api/greeting")
    @ResponseBody
    public Greeting greetingJson(@RequestParam("name") String name) {
        return new Greeting(name, "반갑습니다");
    }
    package com.example.web;

public class Greeting {

    private final String name;
    private final String message;

    public Greeting(String name, String message) {
        this.name = name;
        this.message = message;
    }

    public String getName() {
        return name;
    }

    public String getMessage() {
        return message;
    }
}

    요청이 들어와 메서드가 호출되기까지는 MVC 방식과 한 단계도 다르지 않다. 같은 핸들러 매핑이 메서드를 찾고, 같은 어댑터가 같은 방법으로 인자를 채워 호출한다. 달라지는 것은 반환값을 받은 다음이다. 스프링 레퍼런스는 @ResponseBody를 메서드에 붙이면 반환값이 HttpMessageConverter를 통해 응답 본문으로 직렬화된다고 설명한다. 어댑터 안에서 반환값 처리를 맡은 객체(RequestResponseBodyMethodProcessor)가 본문을 직접 써 버리고, DispatcherServlet에는 렌더링할 뷰가 없다고 알린다. ViewResolver도 템플릿도 이 경로에는 등장하지 않는다.

    $ curl -i "http://localhost:8080/api/greeting-text?name=jiho"
HTTP/1.1 200
Content-Type: text/plain;charset=UTF-8
Content-Length: 25

jiho 님, 반갑습니다

$ curl -i "http://localhost:8080/api/greeting?name=jiho"
HTTP/1.1 200
Content-Type: application/json

{"name":"jiho","message":"반갑습니다"}

    첫 번째 응답은 반환한 문자열이 그대로 본문이 되었다. 두 번째 응답은 반환한 객체가 JSON이 되었다. 컨트롤러 코드는 둘 다 값을 반환했을 뿐인데 본문의 형식과 Content-Type이 다르다. 이 차이를 만든 것이 HttpMessageConverter의 선택 과정이다. 두 번째 응답에서는 본문 길이를 나타내는 헤더를 생략했는데, 버전에 따라 Content-Length 대신 다른 방식으로 길이를 알리기도 해서다.

    변환기는 여러 개이고 순서가 있다

    HttpMessageConverter는 "이 타입의 객체를 이 미디어 타입으로 쓸 수 있는가"를 답하는 메서드(canWrite)와 실제로 쓰는 메서드(write)를 가진 인터페이스다. 읽는 쪽 메서드도 있어서 요청 본문을 객체로 바꾸는 데에도 쓰인다. 스프링 MVC는 변환기를 여러 개 목록으로 가지고 있다. Spring Framework 6.2의 기본 구성 코드(WebMvcConfigurationSupport.addDefaultHttpMessageConverters)는 바이트 배열용, 문자열용(StringHttpMessageConverter), 리소스용 변환기를 먼저 넣고, 그 뒤에 클래스패스에 Jackson 라이브러리가 있는지 검사해 있으면 JSON 변환기(MappingJackson2HttpMessageConverter)를 넣는다.

    여기서 두 가지를 읽을 수 있다. 첫째, 문자열 변환기가 JSON 변환기보다 앞에 있다. 둘째, JSON 변환기는 라이브러리가 있을 때만 등록된다. 스프링 부트의 웹 스타터는 Jackson을 함께 가져오므로 따로 한 일이 없어도 객체가 JSON으로 나간다. 01회에서 본 의존성 목록이 실행 시점의 동작을 바꾸는 한 예다. Spring Boot 레퍼런스는 여기에 한 줄을 더한다. 문자열은 기본으로 UTF-8로 인코딩된다. 스프링 프레임워크의 StringHttpMessageConverter는 기본 생성자로 만들면 문자 집합이 ISO-8859-1이지만, 스프링 부트가 이 변환기를 UTF-8로 만들어 등록한다. 한글이 깨지지 않고 나간 것은 이 설정 덕분이다.

    어떤 변환기가 선택되는가

    선택 과정은 Spring Framework 6.2의 AbstractMessageConverterMethodProcessor.writeWithMessageConverters에 구현되어 있다. 핵심만 추리면 다섯 단계다.

    1. 클라이언트가 받을 수 있는 타입을 구한다. 요청의 Accept 헤더를 읽는다. 헤더가 없으면 무엇이든 받는 것으로 본다.
    2. 서버가 만들 수 있는 타입을 구한다. 변환기 목록을 돌며 반환값의 타입을 쓸 수 있다고 답한 변환기들이 지원하는 미디어 타입을 모은다.
    3. 둘을 맞춰 본다. 받을 수 있는 타입과 만들 수 있는 타입 가운데 서로 호환되는 것을 추린다. 하나도 없으면 HttpMediaTypeNotAcceptableException이 발생하고 응답은 406(Not Acceptable)이 된다.
    4. 하나를 고른다. 추린 후보를 더 구체적인 것이 앞에 오도록 정렬하고, *가 섞이지 않은 첫 번째 구체적인 타입을 응답의 미디어 타입으로 선택한다.
    5. 쓸 변환기를 찾는다. 변환기 목록을 앞에서부터 돌며 "이 반환 타입을, 선택된 미디어 타입으로" 쓸 수 있다고 답하는 첫 변환기에게 쓰기를 맡긴다.

        │                                      │
        ▼                                      ▼

                 Jackson JSON → 쓸 수 있다 ──▶ 객체를 JSON 바이트로 바꿔 본문에 기록
    반환 타입에서 나온 "만들 수 있는 타입"과 Accept 헤더에서 나온 "받을 수 있는 타입"이 만나 미디어 타입 하나가 정해지고, 그 다음 변환기 목록을 앞에서부터 훑어 첫 번째로 쓸 수 있는 변환기가 본문을 쓴다는 것을 보여 준다. 세로 방향 순서도. 맨 위에 두 개의 시작 상자가 좌우로 나란히 있다. 왼쪽 상자 라벨 "반환값의 타입", 오른쪽 상자 라벨 "Accept 헤더". 왼쪽 상자 아래에 "만들 수 있는 타입" 상자, 오른쪽 상자 아래에 "받을 수 있는 타입" 상자. 두 상자에서 나온 화살표가 가운데 아래의 마름모 "호환되는 후보가 있는가"로 모인다. 마름모에서 오른쪽으로 나가는 화살표에 "없음" 라벨이 붙고 끝에 빨간 상자 "406 응답". 마름모에서 아래로 나가는 화살표에 "있음" 라벨이 붙고 "미디어 타입 하나 선택" 상자로 이어진다. 그 아래에 세로로 쌓인 세 칸짜리 목록 그림이 있고 칸마다 위에서부터 "바이트 배열 변환기", "문자열 변환기", "JSON 변환기"라고 적혀 있다. 목록 왼쪽에 위에서 아래로 향하는 화살표와 라벨 "앞에서부터 확인". 세 번째 칸만 초록색으로 강조되고 거기서 오른쪽으로 화살표가 나가 "응답 본문" 상자에 닿는다. 흰 배경, 평면 벡터 스타일, 파란색 기본에 초록과 빨강 강조. 미디어 타입을 먼저 정하고, 그 다음에 변환기를 찾는다. 변환기 목록의 순서가 결과에 영향을 준다.

    이 다섯 단계에 여러 입력을 넣어 실제로 요청해 본 결과가 아래 표다. 첫 줄과 넷째 줄이 앞의 실행 결과에 해당한다.

    반환 타입요청의 Accept응답 Content-Type본문을 쓴 변환기본문
    String*/* (curl 기본) 또는 없음text/plain;charset=UTF-8문자열 변환기jiho 님, 반갑습니다
    Stringtext/html,…,*/*;q=0.8 (브라우저 주소창)text/html;charset=UTF-8문자열 변환기위와 같다
    Stringapplication/jsonapplication/json문자열 변환기위와 같다(따옴표 없음)
    Greeting*/*application/jsonJSON 변환기{"name":"jiho",…}
    Greetingtext/plain(없음)(없음)406, 본문 없음

    표의 각 줄은 다섯 단계로 설명된다. StringHttpMessageConverter의 Javadoc에 따르면 이 변환기는 기본으로 모든 미디어 타입(*/*)을 지원하고 text/plain으로 쓴다. 그래서 반환 타입이 String이고 클라이언트가 무엇이든 받겠다고 하면 text/plain이 선택된다. 브라우저처럼 text/html을 앞세우면 문자열 변환기가 모든 타입을 지원하므로 text/html이 선택되고, 같은 문자열이 text/html이라는 이름표를 달고 나간다.

    셋째 줄은 자주 놀라는 지점이다. 클라이언트가 JSON을 달라고 했고 응답의 Content-Type도 application/json인데, 본문은 따옴표도 없는 맨 문자열이다. 올바른 JSON 문자열이라면 큰따옴표로 감싸여 있어야 한다. 5단계에서 변환기 목록을 앞에서부터 확인할 때, 모든 미디어 타입을 지원하는 문자열 변환기가 JSON 변환기보다 먼저 "String을 application/json으로 쓸 수 있다"고 답하기 때문이다. 문자열 변환기는 받은 문자열을 그대로 바이트로 바꿀 뿐 JSON 문법을 모른다. @ResponseBody에서 String을 반환한다는 것은 "이 문자열이 이미 완성된 본문이다"라고 말하는 것과 같다.

    넷째 줄에서 Greeting을 쓸 수 있다고 답하는 변환기는 JSON 변환기뿐이므로 만들 수 있는 타입은 application/json 계열이고, 그것이 선택된다. 다섯째 줄은 클라이언트가 text/plain만 받겠다고 했는데 서버는 Greeting을 text/plain으로 만들 방법이 없으므로 3단계에서 후보가 없어 406이 된다. 서버가 가진 데이터가 잘못된 것이 아니라 양쪽이 합의할 형식이 없다는 뜻의 상태 코드다. 이렇게 클라이언트의 선호와 서버의 능력을 맞춰 응답 형식을 정하는 일을 컨텐츠 협상(content negotiation)이라고 한다.

    객체가 JSON이 되는 과정: Jackson은 게터를 본다

    JSON 변환기는 받은 객체를 Jackson 라이브러리의 ObjectMapper에 넘긴다. Jackson은 Greeting이라는 클래스를 처음 본다. 그런데도 name과 message라는 키를 가진 JSON을 만들어 냈다. 여기에도 리플렉션이 쓰인다. Jackson은 클래스가 가진 메서드와 필드를 조회해, 밖으로 내보낼 값의 목록인 프로퍼티(property)를 정한다.

    무엇을 프로퍼티로 보는지는 Jackson 2.x의 MapperFeature Javadoc에 적혀 있다. 기본으로 켜져 있는 규칙에 따르면, 이름이 get으로 시작하고 인자가 없는 public 메서드는 게터로 인식된다. 이름이 is로 시작하고 boolean을 반환하는 인자 없는 public 메서드도 게터로 인식된다. 필드는 public인 것만 프로퍼티로 인식된다. Greeting의 필드는 둘 다 private이므로 JSON의 출처가 아니다. JSON에 나온 name과 message는 필드가 아니라 getName()과 getMessage()에서 왔고, 키 이름도 게터 이름에서 get을 떼고 첫 글자를 소문자로 바꿔 만든 것이다.

    필드 이름과 게터 이름을 일부러 어긋나게 만들면 이 규칙이 눈에 보인다.

    public class Item {

    private String msg = "hi";      // 게터와 이름이 다른 필드

    public String getMessage() {    // 키 "message"
        return msg;
    }

    public int getTotal() {         // 대응하는 필드가 없는 게터: 키 "total"
        return 3;
    }

    public boolean isOpen() {       // is 게터: 키 "open"
        return true;
    }
}

    이 객체를 @ResponseBody 메서드에서 반환하면 JSON의 키는 message, total, open 세 개이고 msg라는 키는 없다. Spring Boot 4.1.2(Jackson 3)에서 실행한 결과는 {"message":"hi","open":true,"total":3}이었다. 키가 나오는 순서에는 기대지 않는 편이 좋다. Jackson 2.x의 Javadoc은 알파벳순 정렬 옵션(SORT_PROPERTIES_ALPHABETICALLY)이 기본으로 꺼져 있고, 그때의 순서는 정해져 있지 않으며 선언 순서일 수도 있지만 보장되지 않는다고 밝힌다.

    게터도 public 필드도 없는 클래스는 내보낼 프로퍼티가 하나도 없다. Jackson 2.x에서는 이런 타입을 직렬화하려 하면 예외로 처리하는 설정(SerializationFeature.FAIL_ON_EMPTY_BEANS)이 기본으로 켜져 있고, Spring Framework 6.2의 JSON 변환기는 쓰기 전에 ObjectMapper에게 그 타입을 직렬화할 수 있는지부터 묻는다. 같은 클래스를 Jackson 3를 쓰는 Spring Boot 4.1.2에서 반환하니 빈 객체 {}가 나갔다. 버전에 따라 결과는 다르지만 어느 쪽이든 private 필드의 값은 나가지 않는다. "필드를 추가했는데 JSON에 보이지 않는다"는 문제는 대개 게터가 없어서 생긴다.

    Jackson이 해 주는 일이 하나 더 있다. 직접 만든 서버는 name에 큰따옴표가 들어오면 깨진 JSON을 내보냈다. 스프링 쪽에 같은 값을 보내면(/api/greeting?name=a%22b) 본문은 {"name":"a\"b","message":"반갑습니다"}가 된다. 값 안의 큰따옴표 앞에 역슬래시가 붙어, 문자열이 거기서 끝나지 않는다는 것을 JSON 문법으로 표현한다. 템플릿 엔진이 HTML의 특수 문자를 이스케이프하는 것과 같은 종류의 일이다. 값을 어떤 형식의 문서에 넣을 때는 그 형식의 문법에 맞게 바꿔 넣어야 하고, 이것을 손으로 하지 않게 해 주는 것이 변환기와 템플릿 엔진이다.

    @RestController

    API만 제공하는 컨트롤러에서는 모든 메서드에 @ResponseBody를 붙이게 된다. 스프링 레퍼런스는 @ResponseBody를 클래스에 붙이면 모든 컨트롤러 메서드에 상속되며, @RestController가 바로 그 효과를 내는 것으로 @Controller와 @ResponseBody를 붙인 메타 애너테이션일 뿐이라고 설명한다. 따라서 @RestController 안에서 return "greeting"을 하면 greeting 템플릿이 렌더링되지 않는다. 실제로 요청해 보면 본문이 greeting이라는 여덟 글자인 text/plain 응답이 온다.

    컨트롤러는 하나, 스레드는 여럿

    지금까지 요청 하나의 흐름만 따라갔다. 실제 서버에는 요청이 동시에 여러 개 들어온다. 앞에서 톰캣이 요청마다 작업 스레드 하나를 배정한다고 했다. 그렇다면 컨트롤러 객체는 요청마다 하나씩 만들어지는가. 컨트롤러에 메서드를 하나 더해 확인해 보자. System.identityHashCode는 객체마다 정해지는 식별용 해시 값을 돌려주므로, 같은 객체라면 같은 값이 나온다.

        @GetMapping("/api/where")
    @ResponseBody
    public String where() {
        return Thread.currentThread().getName() + " / " + System.identityHashCode(this);
    }

    스레드 이름의 번호와 해시 값은 실행할 때마다 달라진다. 변하지 않는 것은 패턴이다. 요청을 처리한 스레드는 요청마다 다를 수 있고, 컨트롤러의 해시 값은 한 번 실행하는 동안 늘 같다. 스프링은 애플리케이션이 시작될 때 컨트롤러 객체를 하나만 만들어 두고(이 객체를 누가 어떻게 만드는지는 04회에서 다룬다), 모든 요청 스레드가 그 한 객체의 메서드를 호출한다.

    자바 기본편에서 본 메모리 구조를 여기에 겹쳐 보면 무엇이 공유되고 무엇이 공유되지 않는지가 정해진다. 메서드의 매개변수와 지역 변수는 그 메서드를 호출한 스레드의 스택에 있다. 스택은 스레드마다 따로 있으므로 두 요청이 동시에 greeting을 실행해도 각자의 name과 model은 섞이지 않는다. 반면 객체의 필드는 힙에 있고, 힙의 객체는 그 참조를 가진 모든 스레드가 함께 본다.

      스레드 exec-1 의 스택            스레드 exec-3 의 스택

 │   name  ─▶ "jiho"   │        │   name  ─▶ "mina"   │       스택: 스레드마다 따로

    매개변수와 지역 변수는 스레드별 스택에 따로 있고, 컨트롤러 객체와 그 필드는 힙에 하나뿐이라 모든 요청이 공유한다는 것을 보여 준다. 메모리 구조도. 화면 위쪽에 좌우로 두 개의 세로 스택 상자. 왼쪽 상자 제목 "스레드 1의 스택", 오른쪽 상자 제목 "스레드 2의 스택". 각 스택 상자 안에는 칸 세 개가 위아래로 쌓여 있다. 왼쪽 스택의 칸: "name = jiho", "model", "this". 오른쪽 스택의 칸: "name = mina", "model", "this". 화면 아래쪽에 가로로 긴 큰 상자, 제목 "힙 (모든 스레드가 공유)". 힙 상자 가운데에 진한 색 직사각형 하나, 라벨 "컨트롤러 객체 1개". 힙 상자 왼쪽과 오른쪽 끝에 옅은 색 작은 직사각형 두 개, 각각 라벨 "모델 A", "모델 B". 왼쪽 스택의 "this" 칸과 오른쪽 스택의 "this" 칸에서 나온 화살표 두 개가 모두 가운데 "컨트롤러 객체 1개"를 가리킨다. 왼쪽 "model" 칸의 화살표는 "모델 A"를, 오른쪽 "model" 칸의 화살표는 "모델 B"를 가리킨다. 스택은 파란색, 힙은 주황색 계열, 흰 배경, 평면 벡터 스타일. 두 스레드의 this는 같은 객체를 가리킨다. 요청마다 달라야 하는 값은 스택 쪽(매개변수, 지역 변수)이나 요청마다 새로 만들어지는 객체에 두어야 한다.

    이 구조에서 바로 나오는 금지 사항이 있다. 컨트롤러의 필드에 요청마다 달라지는 값을 두면 안 된다. 다음 컨트롤러는 혼자 테스트하면 잘 동작한다.

    package com.example.web;

import org.springframework.stereotype.Controller;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RequestParam;
import org.springframework.web.bind.annotation.ResponseBody;

@Controller
public class VisitController {

    private String lastName;   // 모든 요청이 함께 쓰는 칸
    private int visits;        // 모든 요청이 함께 쓰는 칸

    @GetMapping("/visit")
    @ResponseBody
    public String visit(@RequestParam("name") String name) {
        lastName = name;                                              // (1)
        visits++;                                                     // (2)
        return lastName + " 님은 " + visits + "번째 방문자입니다";      // (3)
    }
}

    jiho의 요청을 처리하는 스레드가 (1)을 실행한 직후, mina의 요청을 처리하는 다른 스레드가 (1)을 실행했다고 하자. 필드 lastName은 하나뿐이므로 이제 "mina"다. 첫 번째 스레드가 이어서 (3)을 실행하면 jiho에게 "mina 님은 …"이라는 응답이 나간다. (2)도 안전하지 않다. visits++는 필드 값을 읽고, 1을 더하고, 결과를 다시 쓰는 세 동작으로 이루어진다. 두 스레드가 같은 값을 읽은 뒤 각자 1을 더해 쓰면 방문은 두 번인데 숫자는 한 번만 오른다.

    이런 결과는 두 요청의 실행이 겹칠 때만 나타난다. 개발자가 혼자 한 번씩 요청해 볼 때는 보이지 않다가 사용자가 늘어난 뒤에야 가끔 나타나고, 다시 만들어 내기도 어렵다. 그래서 규칙으로 막는다. 요청에서 온 값과 그것으로 계산한 값은 매개변수와 지역 변수에만 둔다. 뷰에 넘길 값은 요청마다 새로 만들어지는 모델에 담는다. 컨트롤러의 필드에는 애플리케이션이 시작된 뒤로 바뀌지 않는 것만 둔다. 여러 스레드가 값 하나를 안전하게 함께 고치는 방법은 로드맵 뒤쪽의 멀티스레드 주제에서 따로 다룬다.

    세 방식을 나란히 놓고, 흔한 오해를 고친다

    요청에 따라 달라지는가달라지지 않는다달라진다달라진다
    Content-Type이 정해지는 근거파일 확장자뷰의 설정(text/html과 인코딩)반환 타입과 Accept의 협상

    세 방식을 구분하는 기준이 "URL의 모양"이나 "파일 확장자"가 아니라는 점을 다시 확인해 두자. /guide.html이라는 주소를 컨트롤러가 처리할 수도 있고, 확장자 없는 주소가 HTML을 돌려줄 수도 있다. 방식을 가르는 것은 요청이 DispatcherServlet 아래에서 어느 구성 요소에 도착해 본문이 만들어졌느냐다. 이 관점에서 자주 보는 오해를 정리한다.

    • "정적 파일 요청은 스프링을 거치지 않는다." 스프링 부트의 기본 구성에서는 정적 파일 요청도 DispatcherServlet으로 들어와 핸들러 매핑의 순서를 거친다. 그래서 같은 경로의 컨트롤러가 파일을 가리고, 없는 파일에 대한 404도 스프링이 만든다.
    • "templates 아래의 HTML도 주소로 열 수 있다." templates는 정적 위치가 아니다. 템플릿은 컨트롤러가 뷰 이름으로 지목할 때만 읽힌다.
    • "@ResponseBody로 문자열을 반환하면 JSON이 된다." 문자열 변환기가 그 문자열을 그대로 본문으로 쓴다. Content-Type이 application/json으로 협상되더라도 본문에 따옴표가 붙지 않는다.
    • "@RestController에서도 뷰 이름을 반환하면 화면이 나온다." 반환한 문자열이 본문이 된다. 화면이 필요한 메서드는 @ResponseBody가 적용되지 않는 컨트롤러에 있어야 한다.
    • "JSON의 키는 필드 이름이다." 기본 규칙에서 키는 public 게터의 이름에서 나온다. private 필드는 게터가 없으면 나가지 않는다.
    • "템플릿은 브라우저에서 채워진다." 템플릿 엔진은 서버에서 실행되고 브라우저는 완성된 HTML만 받는다.
    • "컨트롤러는 요청마다 새로 만들어진다." 객체는 하나이고 스레드가 여럿이다.

    상태 코드로 멈춘 지점을 읽는다

    요청 처리를 단계로 이해하면 오류 응답의 상태 코드가 "어느 단계에서 멈췄는가"를 알려 주는 표지가 된다. 이 회차에서 실제로 만난 것들을 단계에 맞춰 놓으면 다음과 같다.

    상태 코드멈춘 단계이 회차에서 본 원인
    404핸들러 찾기, 리소스 찾기매핑된 컨트롤러도 없고 정적 위치에 파일도 없다
    400인자 준비필수 요청 파라미터가 없다, 문자열을 매개변수 타입으로 변환하지 못했다
    406미디어 타입 선택클라이언트의 Accept와 서버가 만들 수 있는 타입이 맞지 않는다
    500처리되지 않은 예외-parameters 없이 컴파일된 클래스에서 이름을 생략한 @RequestParam

    400과 406은 컨트롤러 메서드가 호출되기 전이거나 반환된 뒤에 프레임워크가 만든 응답이다. 컨트롤러 메서드 안에 로그를 넣어 봐도 원인이 보이지 않는 이유가 여기에 있다. 응답의 상태 코드와 서버 로그의 예외 이름을 함께 보면, 고쳐야 할 곳이 요청을 보내는 쪽인지, 매핑인지, 메서드의 시그니처인지, 반환 타입인지를 좁힐 수 있다.

    이 장의 핵심

    정적 컨텐츠, MVC, API는 서로 다른 세 기술이 아니라 HTTP 응답 본문을 만드는 세 가지 담당이다. 모든 요청은 톰캣의 작업 스레드에 실려 DispatcherServlet으로 들어오고, 핸들러 매핑의 순서에 따라 컨트롤러 또는 정적 리소스 핸들러에 도착한다. 컨트롤러의 반환값은 @ResponseBody가 없으면 뷰 이름이 되어 템플릿 엔진으로 가고, 있으면 HttpMessageConverter가 바로 본문으로 쓴다. 그 사이의 인자 준비, 뷰 찾기, 형식 협상, 이스케이프는 프레임워크가 리플렉션과 순서 있는 목록으로 처리한다.

    다음으로 이어지는 것

    이 회차에서 반복해서 나온 구조가 하나 있다. HandlerMapping, HandlerAdapter, ViewResolver, HttpMessageConverter는 모두 "역할을 정한 인터페이스 하나에 구현이 여러 개 있고, 순서대로 물어 처음으로 할 수 있다고 답한 구현에게 맡긴다"는 같은 모양을 하고 있다. 스프링은 기능을 더할 때 기존 코드를 고치는 대신 이 목록에 구현을 하나 더 끼워 넣는다. 클래스패스에 Jackson이 있으면 JSON 변환기가, 타임리프가 있으면 타임리프 뷰 리졸버가 목록에 들어온 것이 그 예다. 자바 기본편의 다형성이 프레임워크 규모로 쓰인 모습이고, 앞으로 스프링의 다른 부분을 볼 때도 같은 눈으로 읽을 수 있다.

    또 하나는 리플렉션이다. 컨트롤러 메서드의 인자를 채울 때, 반환값의 처리 방법을 정할 때, 객체를 JSON으로 바꿀 때 프레임워크와 라이브러리는 우리가 쓴 클래스를 실행 중에 조회했다. 애너테이션은 그 조회에서 읽히는 표식이고, 스스로는 아무 동작도 하지 않는다. @GetMapping이나 @ResponseBody가 "동작한다"고 느껴지는 것은 그것을 읽어 행동을 바꾸는 코드가 프레임워크 안에 있기 때문이다.

    03회에서는 이 회차의 MVC 경로 위에 실제 기능을 올린다. 컨트롤러가 요청을 받아 처리를 맡기고 결과를 모델에 담아 화면으로 보내는 흐름을 예제로 만든다. 04회는 이 회차에서 미뤄 둔 질문, 즉 컨트롤러 객체를 누가 만들고 왜 하나인지를 스프링 컨테이너와 빈으로 설명한다. HTTP 자체의 규칙(메서드, 상태 코드, 캐시)과 서블릿, DispatcherServlet의 더 깊은 내부는 로드맵 뒤쪽에서 각각 한 권 분량으로 다시 만난다. 지금은 요청 하나가 들어와 응답이 되기까지 어떤 구성 요소를 어떤 순서로 지나는지를 손으로 그릴 수 있으면 된다.
    HTTP 응답의 세 부분
    상태 코드, 헤더, 본문 바이트. 정적 컨텐츠·MVC·API는 본문 바이트를 만드는 담당이 다를 뿐이고, 네트워크 위에서는 같은 모양의 응답이다.
    Content-Type과 Accept
    Content-Type은 본문 바이트의 미디어 타입을 알려 주고, Accept는 클라이언트가 받고 싶은 미디어 타입의 선호를 알린다. 스프링은 Accept와 반환 타입을 맞춰 응답 형식을 정한다.
    DispatcherServlet과 핸들러 매핑 순서
    모든 요청이 들어오는 서블릿 하나. 순서 값이 작은 HandlerMapping부터 물으며, 컨트롤러 매핑(0)이 정적 리소스 매핑(Integer.MAX_VALUE - 1)보다 먼저다.
    정적 컨텐츠
    클래스패스의 /static 등에 둔 파일을 ResourceHttpRequestHandler가 그대로 내보낸다. Content-Type은 확장자에서 정해지고, 조건부 요청에는 본문 없는 304로 답한다.
    MVC와 템플릿 엔진
    컨트롤러는 모델에 데이터를 담고 뷰 이름을 반환한다. ViewResolver가 뷰 이름을 템플릿으로 잇고, 템플릿 엔진이 서버에서 HTML을 만들며 값을 기본으로 이스케이프한다.
    인자 해석과 -parameters
    HandlerAdapter가 리플렉션으로 매개변수를 살펴 값을 채운다. 매개변수 이름은 -parameters로 컴파일해야 리플렉션으로 읽을 수 있고, Spring Framework 6.1부터는 다른 방법으로 추론하지 않는다.
    @ResponseBody와 HttpMessageConverter
    반환값을 뷰 없이 본문으로 쓴다. 미디어 타입을 먼저 정한 뒤 변환기 목록을 앞에서부터 확인하며, String은 문자열 변환기가, 그 밖의 객체는 JSON 변환기가 쓴다.
    Jackson의 프로퍼티 탐색
    기본 규칙에서 JSON의 키는 public 게터(get, is)와 public 필드에서 나온다. private 필드는 게터가 없으면 나가지 않는다.
    하나의 컨트롤러, 여러 스레드
    컨트롤러 객체는 하나이고 요청마다 다른 작업 스레드가 그 메서드를 호출한다. 요청별 값은 스택(매개변수·지역 변수)과 요청마다 만들어지는 모델에 두고, 필드에 두지 않는다.

    세 방식 가운데 무엇을 쓸지는 취향이 아니라 두 가지 물음으로 정해진다. 받는 쪽이 사람의 브라우저인가 프로그램인가, 그리고 내용이 요청마다 달라지는가. 실제 애플리케이션 하나에는 대개 세 방식이 섞여 있다. 화면과 데이터를 한 팀이 함께 배포하는 관리 화면이라면 서버가 HTML을 완성해 보내는 쪽이 구성 요소가 적어 단순하다. 같은 데이터를 모바일 앱과 웹 화면이 함께 써야 한다면 데이터만 내보내는 API가 맞다. 정적 파일은 스프링 부트가 잘 내보내 주지만, 이 회차에서 본 대로 그 요청 하나하나도 톰캣의 작업 스레드를 차지한다. 그래서 요청량이 많은 서비스에서는 정적 파일을 애플리케이션 앞단의 웹 서버나 별도 저장소가 맡게 하고 애플리케이션 서버의 스레드는 동적 요청에 쓰게 하는 구성을 검토하게 된다.

    장애를 볼 때는 "작업 스레드는 유한하고, 요청 하나가 스레드 하나를 처리가 끝날 때까지 붙잡는다"는 사실이 출발점이다. 컨트롤러가 호출한 작업이 오래 걸리면 그 스레드는 그동안 다른 요청을 받지 못한다. 느린 요청이 풀을 다 차지하면 가벼운 요청까지 함께 느려진다. 일부 기능이 느려졌는데 서버 전체가 응답하지 않는 것처럼 보인다면 스레드 풀이 바닥났는지를 의심해 볼 수 있다. 또 "가끔 다른 사용자의 값이 보인다"는 종류의 신고는 재현이 어렵지만 원인의 후보는 좁다. 여러 요청이 공유하는 객체, 곧 컨트롤러나 그것이 쓰는 객체의 필드에 요청별 값이 저장되고 있는지부터 찾는다.

    API에서는 반환한 객체의 게터 이름이 곧 외부와의 약속이 된다는 점을 기억해야 한다. 내부에서 쓰던 클래스를 그대로 반환하면 편하지만, 게터 이름 하나를 바꾸는 리팩터링이 클라이언트를 깨뜨리고, 게터를 추가하면 의도하지 않은 값이 밖으로 나간다. 외부에 보여 줄 모양을 따로 정한 클래스를 두는 판단은 이 사실에서 나온다. 문자열을 직접 반환하는 API는 그 문자열이 그대로 본문이 된다는 것을 알고 써야 하고, JSON을 문자열로 손수 조립해 반환하는 일은 이 회차 앞부분의 깨진 JSON과 같은 문제를 다시 불러온다.

    마지막으로, 같은 소스가 실행 방법에 따라 다르게 동작할 때는 소스가 아니라 산출물을 본다. -parameters의 사례가 보여 주듯 프레임워크는 소스가 아니라 클래스 파일과 클래스패스를 읽는다. 팀원의 IDE에서만 실패하거나 배포한 JAR에서만 정적 파일이 보이지 않는다면, 빌드 도구가 만든 것과 다른 경로로 만들어진 클래스 파일, JAR 안에서의 실제 파일 위치를 확인하는 것이 빠르다. 파라미터 이름을 애너테이션에 직접 적는 습관은 이런 환경 차이에 기대지 않게 해 주는 값싼 방어다.
  • src/main/resources/static/style.css 파일이 있고, 이 경로를 처리하는 컨트롤러는 없다. GET /style.css 요청이 응답이 되기까지 거치는 구성 요소를 순서대로 적고, 응답의 Content-Type이 무엇을 근거로 정해지는지 설명하라. 그 다음, 누군가 @GetMapping("/style.css")와 @ResponseBody를 붙여 문자열 "body {}"를 반환하는 컨트롤러 메서드를 추가했다면 curl로 같은 요청을 보냈을 때 응답의 본문과 Content-Type이 어떻게 달라지는지 예측하라.
  • 다음 세 요청 각각에 대해 상태 코드, Content-Type, 본문을 예측하고, 요청 처리의 어느 단계에서 그 결과가 정해졌는지 적어라. (a) @ResponseBody가 붙고 String "ok"를 반환하는 메서드에 curl 기본 설정으로 요청. (b) 본문의 Greeting을 반환하는 메서드에 Accept: text/plain 헤더를 붙여 요청. (c) 매개변수가 @RequestParam("n") int n인 메서드에 ?n=3.7로 요청.

    @Controller
public class EchoController {

    @ResponseBody

        String upper = text.toUpperCase();
        return upper + "!";

    @GetMapping("/echo-b")
    @ResponseBody

  • 메서드 public void move(int x, int y)를 가진 클래스를 (가) 옵션 없이, (나) -g로, (다) -parameters로 컴파일했다. 각각에서 리플렉션의 getParameters()[1].getName()이 돌려주는 값을 적어라. 이어서, @RequestParam int x처럼 이름을 생략한 컨트롤러가 Gradle로 실행하면 동작하는데 IDE의 자체 빌드로 실행하면 500 오류가 나는 상황의 원인을 설명하고 해결 방법 두 가지를 제시하라.
    •

    1. 톰캣이 요청을 받아 작업 스레드 하나가 DispatcherServlet을 호출한다. DispatcherServlet은 순서 0인 RequestMappingHandlerMapping부터 묻지만 매핑된 컨트롤러가 없고, 거의 마지막 순서인 정적 리소스 매핑(패턴 /**)이 ResourceHttpRequestHandler를 돌려준다. HttpRequestHandlerAdapter가 이 핸들러를 호출하고, 핸들러는 설정된 위치에서 classpath:/static/style.css를 찾아 바이트를 그대로 쓴다. Content-Type은 누가 지정한 것이 아니라 파일 이름의 확장자 .css로부터 정해진다. 컨트롤러 메서드를 추가하면 순서 0인 컨트롤러 매핑이 먼저 핸들러를 돌려주므로 파일은 더 이상 읽히지 않는다. 반환값이 String이고 curl의 Accept는 */*이므로 문자열 변환기가 쓰고, 응답은 Content-Type: text/plain;charset=UTF-8에 본문 body {}가 된다. 주소도 확장자도 그대로인데 응답을 만든 담당이 바뀌어 Content-Type까지 달라진다는 점이 핵심이다.

    2. (a) 200, text/plain;charset=UTF-8, 본문 ok. 반환값 처리 단계에서 정해진다. Accept가 */*이고 문자열 변환기가 기본으로 text/plain으로 쓰기 때문이다. (b) 406. 미디어 타입 선택 단계에서 정해진다. Greeting을 쓸 수 있는 변환기는 JSON 변환기뿐이라 서버가 만들 수 있는 타입은 application/json 계열인데 클라이언트는 text/plain만 받겠다고 했으므로 호환되는 후보가 없다. 컨트롤러 메서드는 이미 정상적으로 실행되어 객체를 반환한 뒤라는 점에 주의한다. (c) 400. 인자 준비 단계에서 정해진다. 문자열 "3.7"을 int로 변환할 수 없어 예외가 발생하고, 컨트롤러 메서드는 호출되지 않는다. 실제로 요청하면 로그에 MethodArgumentTypeMismatchException이 남는다.

JSON에 무엇이 나가는지는 필드 목록이 아니라 public 게터 목록을 보고 판단해야 한다.

     static/guide.html 파일이 있는 프로젝트에 @GetMapping("/guide.html")과 @ResponseBody가 붙어 "ctrl"을 반환하는 컨트롤러 메서드를 추가했다. GET /guide.html의 응답과 그 이유로 옳은 것은? 파일의 내용이 응답된다. 확장자가 .html인 요청은 정적 리소스 핸들러가 먼저 처리하기 때문이다. ctrl이 응답된다. 컨트롤러를 찾는 핸들러 매핑의 순서가 정적 리소스 매핑보다 앞서기 때문이다. 애플리케이션이 시작되지 않는다. 같은 경로에 핸들러가 둘이면 모호하다는 오류가 나기 때문이다. 요청마다 달라진다. 어느 작업 스레드가 요청을 맡느냐에 따라 핸들러가 정해지기 때문이다. DispatcherServlet은 핸들러 매핑을 순서 값이 작은 것부터 묻고 처음으로 핸들러를 돌려준 매핑을 따른다. 컨트롤러 매핑은 0, 정적 리소스 매핑은 Integer.MAX_VALUE - 1이므로 컨트롤러가 이긴다. 확장자는 매핑 순서에 영향을 주지 않는다. 컨트롤러와 정적 파일은 서로 다른 매핑에 속하므로 모호성 오류의 대상이 아니고, 스레드는 핸들러 선택과 관계가 없다. @ResponseBody가 붙은 메서드가 String "ok"를 반환한다. 클라이언트가 Accept: application/json으로 요청했을 때의 응답으로 옳은 것은? Content-Type: application/json, 본문은 큰따옴표로 감싼 "ok". JSON 변환기가 문자열을 JSON 문자열로 바꾸기 때문이다. 406 응답. 문자열은 text/plain으로만 쓸 수 있기 때문이다. Content-Type: application/json, 본문은 따옴표 없는 ok. 변환기 목록에서 앞에 있는 문자열 변환기가 모든 미디어 타입을 지원한다고 답하기 때문이다. Content-Type: text/plain, 본문은 ok. 반환 타입이 String이면 Accept 헤더를 읽지 않기 때문이다. 미디어 타입은 Accept와 서버가 만들 수 있는 타입을 맞춰 application/json으로 정해진다. 그 다음 변환기 목록을 앞에서부터 확인하는데, 문자열 변환기는 기본으로 모든 미디어 타입을 지원하므로 JSON 변환기보다 먼저 선택되어 문자열을 그대로 쓴다. 그래서 헤더는 JSON인데 본문에는 따옴표가 없다. 문자열 변환기가 모든 타입을 지원하므로 406이 되지 않고, Accept는 반환 타입과 무관하게 항상 읽힌다. @RequestParam("name") String name을 매개변수로 가진 컨트롤러 메서드에 name 없이 요청했더니 400이 왔다. 메서드 첫 줄에 넣어 둔 로그는 찍히지 않았다. 이유로 옳은 것은? 인자를 준비하는 단계에서 필수 파라미터가 없다는 예외가 발생해 메서드가 호출되지 않았고, 예외 리졸버가 그 예외를 400으로 바꿨기 때문이다. 메서드는 name에 null이 들어온 채로 호출되었지만, 첫 줄에 도달하기 전에 JVM이 null 인자를 거부했기 때문이다. 톰캣이 쿼리 스트링이 없는 요청을 잘못된 HTTP 요청으로 보고 스프링에 넘기지 않았기 때문이다. 핸들러 매핑이 파라미터가 없는 요청에는 이 메서드를 매핑하지 않기 때문이다. required의 기본값은 true이고, 어댑터가 인자를 준비하다가 값이 없으면 MissingServletRequestParameterException이 발생한다. 메서드 호출 전이므로 로그는 찍히지 않는다. DefaultHandlerExceptionResolver가 이 예외를 400에 대응시킨다. JVM은 참조 타입 매개변수에 null이 오는 것을 막지 않는다. 쿼리 스트링이 없는 요청은 올바른 HTTP 요청이다. 매핑 단계에서 실패했다면 400이 아니라 404가 되었을 것이다. 컨트롤러의 필드에 요청에서 받은 값을 저장해 두고 같은 메서드 안에서 다시 읽어 응답을 만들었다. 혼자 테스트할 때는 문제가 없었는데 사용자가 늘자 가끔 다른 사람의 값이 응답에 섞였다. 원인을 가장 정확하게 설명한 것은? 톰캣이 작업 스레드를 재사용하면서 이전 요청의 지역 변수를 지우지 않기 때문이다. 요청마다 컨트롤러 객체가 새로 만들어지는데 필드의 초기화가 늦어지기 때문이다. 템플릿 캐시가 켜져 있어 이전 요청의 렌더링 결과가 재사용되기 때문이다. 컨트롤러 객체는 하나이고 필드는 힙에 한 칸뿐이어서, 동시에 실행되는 여러 요청 스레드가 같은 칸을 읽고 쓰기 때문이다. 매개변수와 지역 변수는 스레드마다 따로 있는 스택에 있어 섞이지 않는다. 필드는 힙의 객체에 속하고, 컨트롤러 객체가 하나이므로 모든 요청 스레드가 같은 필드를 공유한다. 두 요청의 실행이 겹칠 때만 드러나므로 혼자 테스트할 때는 보이지 않는다. 지역 변수는 메서드가 끝나면 스택 프레임과 함께 사라지며, 컨트롤러는 요청마다 새로 만들어지지 않는다. 템플릿 캐시는 템플릿 자체를 재사용할 뿐 렌더링 결과를 재사용하지 않는다. src/main/resources/templates/greeting.html만 만들고 컨트롤러는 만들지 않았다. 브라우저에서 /greeting.html을 요청하면 어떻게 되는가? 템플릿이 모델 없이 렌더링되어, 태그 안에 미리 적어 둔 견본 문구가 보인다. 404가 된다. templates는 정적 위치가 아니어서 정적 리소스 핸들러가 파일을 찾지 못하고, 템플릿은 컨트롤러가 뷰 이름으로 지목할 때만 읽히기 때문이다. 파일이 정적 컨텐츠로 그대로 응답되어, th:text 속성이 들어 있는 원본 HTML이 보인다. 406이 된다. 템플릿 엔진이 처리하지 않은 HTML은 브라우저의 Accept와 맞지 않기 때문이다. 컨트롤러 매핑이 없으므로 요청은 정적 리소스 매핑으로 내려가지만, 기본 정적 위치는 클래스패스의 /static, /public, /resources, /META-INF/resources이고 templates는 여기에 없다. 리소스를 찾지 못해 404가 된다. 템플릿 엔진은 컨트롤러가 뷰 이름을 반환해 ViewResolver가 뷰를 찾을 때만 동작한다. 견본 문구가 보이는 것은 파일을 서버 없이 브라우저로 직접 열었을 때의 일이다. 406은 형식 협상이 실패했을 때의 상태 코드이고 이 상황과 관계가 없다.
    정적 컨텐츠(static content)
    서버가 내용을 바꾸지 않고 파일 그대로 내보내는 리소스. HTML, CSS, 자바스크립트, 이미지 파일이 대표적이다.
    미디어 타입(media type)
    text/html, application/json처럼 본문 바이트의 형식을 나타내는 이름. Content-Type과 Accept 헤더에 쓰인다.
    서블릿(servlet)
    Jakarta Servlet 규격이 정한, 요청 객체와 응답 객체를 받아 처리하는 자바 객체. 톰캣 같은 서블릿 컨테이너가 호출한다.
    프론트 컨트롤러(front controller)
    모든 요청을 하나의 입구에서 받아 실제 처리 담당에게 넘기는 구조. 스프링 MVC에서는 DispatcherServlet이 이 역할을 한다.
    핸들러 매핑(HandlerMapping)
    요청을 처리할 핸들러를 찾아 주는 구성 요소. 여러 개가 순서대로 등록되고 처음으로 핸들러를 돌려준 것이 쓰인다.
    뷰 리졸버(ViewResolver)
    컨트롤러가 반환한 문자열 뷰 이름을 실제 View 객체로 바꾸는 구성 요소.
    템플릿 엔진(template engine)
    템플릿과 데이터를 받아 결과 문서를 만들어 내는 프로그램. 이 회차에서는 타임리프가 서버에서 HTML을 만든다.
    HTTP 메시지 컨버터(HttpMessageConverter)
    자바 객체와 HTTP 본문 바이트 사이의 변환을 맡는 인터페이스. 문자열용, JSON용 등 여러 구현이 순서 있는 목록으로 등록된다.
    컨텐츠 협상(content negotiation)
    클라이언트가 받고 싶은 형식(Accept)과 서버가 만들 수 있는 형식을 맞춰 응답의 미디어 타입을 정하는 일.
    리플렉션(reflection)
    실행 중에 클래스의 메서드, 매개변수, 애너테이션 정보를 조회하고 메서드를 호출할 수 있게 하는 자바의 기능.
