    측정 코드 한 줄이 번지는 과정

    운영 중인 주문 서비스가 가끔 느리다는 보고가 들어왔다고 하자. 어느 메서드에서 시간이 새는지 알 수 없으니, 우선 서비스 계층의 메서드마다 실행 시간을 찍어 보기로 한다. 가장 먼저 떠오르는 방법은 메서드 본문 첫 줄에서 시각을 기록하고, 메서드를 빠져나가는 자리에서 다시 시각을 읽어 차이를 출력하는 것이다. 이 회차의 예제는 주문(OrderService)과 재고(StockRepository) 두 클래스로 이루어진 작은 프로그램이다.

    package shop;

public class OrderService {

    private final StockRepository stockRepository;

    public OrderService(StockRepository stockRepository) {
        this.stockRepository = stockRepository;
    }

    public String place(String item) {
        long start = System.nanoTime();
        try {
            if (stockRepository.remaining(item) <= 0) {
                return "품절: " + item;
            }
            return "주문 접수: " + item;
        } finally {
            long elapsedMs = (System.nanoTime() - start) / 1_000_000;
            System.out.println("place " + elapsedMs + "ms");
        }
    }

    public boolean inStock(String item) {
        long start = System.nanoTime();
        try {
            return stockRepository.remaining(item) > 0;
        } finally {
            long elapsedMs = (System.nanoTime() - start) / 1_000_000;
            System.out.println("inStock " + elapsedMs + "ms");
        }
    }
}

    측정 코드를 try/finally로 감싼 데는 이유가 있다. place에는 return이 두 군데 있고, 재고 조회가 예외를 던질 수도 있다. 어느 경로로 빠져나가든 종료 시각을 찍으려면 finally밖에 방법이 없다. 시각을 읽는 데 System.nanoTime()을 쓴 것도 같은 맥락이다. 이 메서드는 벽시계 시각이 아니라 임의의 기준점에서 흐른 나노초를 돌려주므로, 두 값의 차이로 경과 시간을 구하는 용도로만 쓴다.

    동작은 한다. 그런데 원래 네 줄이던 place의 본문이 열 줄이 됐고, 한 줄이던 inStock은 일곱 줄이 됐다. 메서드마다 여섯 줄씩 붙은 셈이다. 서비스 메서드가 300개인 애플리케이션이라면 같은 모양의 여섯 줄을 300번 붙여야 한다. 이 상태에서 생기는 문제를 하나씩 적어 보면 다음과 같다.

    • 읽기가 어려워진다. place가 하는 일은 "재고를 확인하고 주문을 접수한다"인데, 그 두 줄을 찾으려면 측정 코드를 눈으로 걷어 내야 한다.
    • 같은 코드가 메서드 수만큼 복제된다. 복제된 코드는 모두 같은 방향으로 함께 바뀌어야 하는데, 그것을 강제하는 장치가 없다.
    • 변경 지점이 메서드 수와 같다. 단위를 밀리초에서 마이크로초로 바꾸거나 System.out을 로거로 바꾸려면 300곳을 고쳐야 한다.
    • 빠뜨려도 알 수 없다. 새로 만든 메서드에 측정 코드를 넣지 않아도 컴파일러는 아무 말도 하지 않는다. 메서드 이름 문자열 "place"를 복사하다가 틀려도 마찬가지다.
    • 걷어 내기도 같은 비용이 든다. 원인을 찾은 뒤 측정을 끄고 싶으면 300곳을 다시 고친다.

    이 문제의 뿌리는 성격이 다른 두 가지 일이 한 메서드에 섞여 있다는 데 있다. 주문을 접수하는 일처럼 그 클래스가 존재하는 이유가 되는 로직을 핵심 관심사(core concern)라 하고, 시간 측정처럼 여러 클래스에 똑같은 모양으로 걸쳐 나타나는 로직을 횡단 관심사(cross-cutting concern) 또는 공통 관심사라 한다. 로깅, 트랜잭션 경계 설정, 권한 검사가 같은 부류다. 스프링 레퍼런스도 여러 클래스를 가로지르는 관심사의 대표적인 예로 트랜잭션 관리를 든다.

             +-----------+    +-----------+      +-----------+

             | 주문 로직 |    | 재고 로직 |      | 결제 로직 |
 트랜잭션  ==|===========|====|===========|======|===========|==▶
             +-----------+    +-----------+      +-----------+

    객체 지향에서 코드를 나누는 단위는 클래스다. 클래스는 "주문", "재고", "결제"처럼 무엇을 책임지는가에 따라 나뉜다. 시간 측정은 그 분류와 상관없이 모든 클래스의 모든 메서드에 걸쳐 있어서, 어느 한 클래스에 넣을 수가 없다. 상속으로 공통 부모에 올려도 "각 메서드의 앞뒤에서 실행한다"는 부분은 여전히 각 메서드가 직접 호출해야 한다. 그래서 이런 로직을 따로 떼어 한곳에서 정의하고, 어디에 적용할지도 그곳에서 선언하는 방법이 필요해진다. 그 방법에 붙은 이름이 관점 지향 프로그래밍(Aspect-Oriented Programming, AOP)이다.

    클래스는 세로 기둥으로, 시간 측정과 트랜잭션 같은 공통 로직은 그 기둥들을 가로지르는 띠로 그려 횡단이라는 말의 뜻을 보여 준다. 흰 배경의 평면 개념도. 세로로 긴 둥근 사각형 기둥 세 개를 나란히 배치하고 각각 위쪽에 "주문 서비스", "재고 저장소", "결제 서비스"라는 라벨을 붙인다. 기둥 안쪽에는 연한 회색으로 "핵심 로직"이라고 적는다. 세 기둥을 왼쪽에서 오른쪽으로 관통하는 가로 띠 두 줄을 그린다. 위쪽 띠는 주황색이고 왼쪽 끝에 "시간 측정", 아래쪽 띠는 파란색이고 왼쪽 끝에 "트랜잭션"이라고 적는다. 띠가 기둥과 겹치는 부분은 색을 진하게 해서 섞여 있음을 표현한다. 그림 아래에 작은 글씨로 "세로: 핵심 관심사", "가로: 횡단 관심사"라는 범례를 둔다. 장식이나 인물은 넣지 않는다. 클래스는 책임에 따라 세로로 나뉘지만, 시간 측정 같은 로직은 그 경계를 가로질러 모든 클래스에 걸친다.

    메서드로 뽑아도 남는 것

    중복이 보이면 메서드로 추출하는 것이 기본기다. 측정 로직을 한곳에 모으고, 측정할 본문은 "나중에 실행할 코드 조각"으로 넘겨 보자. 아래에서 () -> { ... }는 그런 코드 조각을 객체로 만드는 람다 문법인데, 여기서는 익명 클래스를 짧게 쓴 것으로만 읽어도 충분하다.

    package shop;

import java.util.function.Supplier;

public final class Stopwatch {

    private Stopwatch() {
    }

    public static  T measure(String name, Supplier body) {
        long start = System.nanoTime();
        try {
            return body.get();
        } finally {
            long elapsedMs = (System.nanoTime() - start) / 1_000_000;
            System.out.println(name + " " + elapsedMs + "ms");
        }
    }
}
    public String place(String item) {
    return Stopwatch.measure("place", () -> {
        if (stockRepository.remaining(item) <= 0) {
            return "품절: " + item;
        }
        return "주문 접수: " + item;
    });
}

public boolean inStock(String item) {
    return Stopwatch.measure("inStock", () -> stockRepository.remaining(item) > 0);
}

    여섯 줄이 한두 줄로 줄었고, 측정 방식을 바꿀 때 고칠 곳도 Stopwatch 하나가 됐다. 그러나 앞에서 적은 문제 가운데 절반은 그대로다. 모든 메서드가 여전히 Stopwatch를 알고 직접 호출한다. 새 메서드에서 빠뜨려도 알 수 없고, 측정을 끄려면 300곳을 다시 고쳐야 한다. 게다가 Supplier의 get()은 체크 예외를 던질 수 없고 반환값이 반드시 있어야 하므로, 반환값이 없는 메서드나 체크 예외를 던지는 메서드를 위한 헬퍼를 따로 만들어야 한다.

    정리하면 "무엇을 할 것인가"(측정 로직)는 한곳에 모였지만 "어디에 적용할 것인가"는 여전히 각 메서드 안에 흩어져 있다. 두 번째까지 한곳으로 모으려면, 측정되는 쪽 코드가 자신이 측정된다는 사실을 몰라야 한다. 곧 OrderService의 소스를 한 글자도 건드리지 않고 place 호출의 앞뒤에 다른 코드를 실행시켜야 한다.

    그것이 가능한 자리를 찾으려면 메서드 호출이 실제로 어떻게 일어나는지를 떠올려야 한다. 호출하는 쪽의 바이트코드는 수신 객체의 참조와 인자를 피연산자 스택에 쌓고 invokevirtual(인터페이스 타입이면 invokeinterface) 명령을 실행한다. JVM은 그 참조가 가리키는 객체의 실제 클래스에서 실행할 메서드를 찾아 새 스택 프레임을 만든다. 이 과정에서 끼어들 수 있는 자리는 세 군데다.

    1. 호출하는 쪽 코드를 바꾼다. 호출 명령 앞뒤에 측정 코드를 넣는다.
    2. 호출되는 쪽 코드를 바꾼다. 메서드 본문의 앞뒤에 측정 코드를 넣는다. 처음에 손으로 한 일이 이것이다.
    3. 호출자가 들고 있는 참조가 가리키는 객체를 바꾼다. 원래 객체 대신, 같은 타입으로 보이지만 앞뒤에서 측정을 하고 원래 객체에게 일을 넘기는 다른 객체를 준다.

    1번과 2번을 사람이 아니라 도구가 컴파일된 바이트코드에 대해 수행하는 방식도 있다. AspectJ가 그 방식이며 이 회차의 끝에서 스프링 AOP와 비교한다. 스프링 AOP가 택한 것은 3번이다. 소스도 바이트코드도 그대로 두고, 객체를 하나 더 만들어 호출 경로 중간에 세운다. 그 객체를 프록시(proxy)라고 부른다.

    호출자와 대상 사이에 객체 하나를 끼운다

    3번 방법을 먼저 손으로 구현해 보자. 주문 기능을 인터페이스로 뽑고, 실제 로직을 가진 구현체와 측정만 담당하는 구현체를 따로 만든다. 측정 담당은 실제 구현체의 참조를 필드로 들고 있다가 호출을 그대로 넘긴다.

    package shop;

public interface OrderService {
    String place(String item);
    boolean inStock(String item);
}
    package shop;

public class SimpleOrderService implements OrderService {

    private final StockRepository stockRepository;

    public SimpleOrderService(StockRepository stockRepository) {
        this.stockRepository = stockRepository;
    }

    @Override
    public String place(String item) {
        if (stockRepository.remaining(item) <= 0) {
            return "품절: " + item;
        }
        return "주문 접수: " + item;
    }

    @Override
    public boolean inStock(String item) {
        return stockRepository.remaining(item) > 0;
    }
}
    package shop;

public class TimedOrderService implements OrderService {

    private final OrderService target;

    public TimedOrderService(OrderService target) {
        this.target = target;
    }

    @Override
    public String place(String item) {
        long start = System.nanoTime();
        try {
            return target.place(item);
        } finally {
            long elapsedMs = (System.nanoTime() - start) / 1_000_000;
            System.out.println("place " + elapsedMs + "ms");
        }
    }

    @Override
    public boolean inStock(String item) {
        long start = System.nanoTime();
        try {
            return target.inStock(item);
        } finally {
            long elapsedMs = (System.nanoTime() - start) / 1_000_000;
            System.out.println("inStock " + elapsedMs + "ms");
        }
    }
}
    package shop;

public class Main {
    public static void main(String[] args) {
        OrderService target = new SimpleOrderService(new StockRepository());
        OrderService orderService = new TimedOrderService(target);
        System.out.println(orderService.place("키보드"));
    }
}

    경과 시간 숫자는 실행할 때마다 다르다. 눈여겨볼 것은 SimpleOrderService에 측정 코드가 한 줄도 없다는 점과, main에서 orderService.place("키보드")를 호출하는 문장이 측정이 있든 없든 똑같다는 점이다. 달라진 것은 객체를 조립하는 한 줄뿐이다. 힙의 모습을 그려 보면 호출이 지나가는 경로가 드러난다.

    main의 스택 프레임                힙
+----------------+
| orderService ──┼──▶ TimedOrderService 인스턴스   (프록시)
+----------------+       target ──▶ SimpleOrderService 인스턴스   (대상)
                                      stockRepository ──▶ StockRepository 인스턴스

orderService.place("키보드")
  ① invokeinterface OrderService.place   → 실제 클래스가 TimedOrderService이므로 그 place가 실행된다
  ② 시작 시각 기록
  ③ target.place(item)                   → SimpleOrderService.place가 실행된다
  ④ 반환값을 받은 뒤 finally에서 경과 시간 출력
  ⑤ 반환값을 main에게 그대로 돌려준다

    변수 orderService의 선언 타입은 인터페이스 OrderService다. 컴파일러는 이 타입만 보고 호출 명령을 만들고, 어떤 클래스의 place가 실행될지는 실행 시점에 참조가 가리키는 객체의 실제 클래스로 결정된다. 자바 기본편에서 다형성으로 배운 규칙 그대로다. 프록시는 이 규칙 위에 서 있다. 호출자가 구체 클래스가 아니라 상위 타입으로 대상을 알고 있기만 하면, 그 자리에 같은 타입의 다른 객체를 넣어도 호출자 코드는 바뀌지 않는다.

    일상에서 가져온 비유대표 번호를 받는 접수 창구

    회사의 대표 번호로 전화를 걸면 접수 창구가 먼저 받는다. 창구는 통화 시작 시각을 적고, 담당자에게 연결하고, 통화가 끝나면 종료 시각을 적는다. 전화를 건 사람은 대표 번호만 알 뿐 중간에 누가 기록을 남기는지 모르고, 담당자도 자신의 통화가 기록된다는 사실을 몰라도 된다. 다만 이 비유는 한 가지에서 깨진다. 담당자가 사무실 안에서 옆자리 동료에게 직접 건너가 묻는 일은 창구를 거치지 않으므로 기록되지 않는다. 프록시도 똑같은 한계를 갖는데, 뒤에서 "내부 호출" 문제로 다시 만난다.

    손으로 만든 프록시는 방향은 맞지만 비용 문제를 해결하지 못했다. TimedOrderService 안에는 측정 코드가 메서드 수만큼 다시 복제돼 있다. StockRepository에도 측정을 붙이려면 프록시 클래스를 하나 더 써야 하고, 인터페이스에 메서드가 추가될 때마다 프록시도 고쳐야 한다. 대상 클래스 수에 메서드 수를 곱한 만큼의 코드를 사람이 쓰는 셈이다. 그런데 프록시 클래스의 모든 메서드는 "측정을 시작한다, 대상의 같은 메서드를 부른다, 측정을 끝낸다"라는 같은 틀을 따른다. 틀이 같다면 클래스를 사람이 아니라 프로그램이 만들어 낼 수 있다.

    한 가지 전제도 짚어 두자. 이 방식은 호출자가 대상을 스스로 new로 만들지 않고 밖에서 건네받을 때만 통한다. main이 조립을 맡았기 때문에 TimedOrderService를 끼울 수 있었다. 04회에서 다룬 의존관계 주입이 바로 그 조건을 만든다. 객체의 생성과 연결을 컨테이너가 쥐고 있으므로, 컨테이너는 원래 객체 대신 프록시를 건넬 기회를 갖는다.

    JDK 동적 프록시 — 실행 중에 만들어지는 클래스

    JDK에는 인터페이스를 구현하는 프록시 클래스를 실행 중에 만들어 주는 기능이 들어 있다. java.lang.reflect.Proxy.newProxyInstance에 인터페이스 목록과 InvocationHandler 하나를 넘기면, 그 인터페이스들을 구현한 새 클래스를 만들고 인스턴스까지 돌려준다. 프록시의 어떤 메서드가 호출되든 실행은 핸들러의 invoke 한 곳으로 모인다.

    package shop;

import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Method;
import java.lang.reflect.Proxy;

public class DynamicProxyDemo {

    public interface OrderService {
        String place(String item);
        int count();
    }

    static class SimpleOrderService implements OrderService {
        private int placed;

        @Override
        public String place(String item) {
            placed++;
            return "주문 접수: " + item;
        }

        @Override
        public int count() {
            return placed;
        }
    }

    static class TraceHandler implements InvocationHandler {
        private final Object target;

        TraceHandler(Object target) {
            this.target = target;
        }

        @Override
        public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
            System.out.println("[시작] " + method.getName());
            try {
                return method.invoke(target, args);
            } finally {
                System.out.println("[종료] " + method.getName());
            }
        }
    }

    public static void main(String[] args) {
        OrderService target = new SimpleOrderService();
        OrderService proxy = (OrderService) Proxy.newProxyInstance(
                OrderService.class.getClassLoader(),
                new Class[] {OrderService.class},
                new TraceHandler(target));

        System.out.println(proxy.place("키보드"));
        System.out.println(proxy.count());
        System.out.println(proxy.getClass().getName());
        System.out.println(proxy.getClass().getSuperclass().getName());
        System.out.println(proxy instanceof OrderService);
        System.out.println(proxy instanceof SimpleOrderService);
    }
}

    TraceHandler에는 place나 count라는 이름이 한 번도 나오지 않는데도 두 메서드 모두 앞뒤에 로그가 찍혔다. 손으로 만든 프록시에서 메서드마다 복제하던 틀이 invoke 하나로 줄어든 것이다. 인터페이스에 메서드가 100개 있어도, 다른 인터페이스에 적용해도 이 핸들러는 고칠 필요가 없다.

    일곱 번째 줄의 jdk.proxy1.$Proxy0이 실행 중에 만들어진 클래스의 이름이다. 소스 파일에도 컴파일 결과물에도 없던 클래스다. Proxy의 API 문서는 프록시 클래스의 이름을 명세하지 않으며 $Proxy로 시작하는 이름 공간을 프록시 클래스용으로 남겨 둔다고만 적는다. 따라서 이 이름은 OpenJDK 21이 이번 실행에서 붙인 것일 뿐이고, 코드가 이 이름에 의존하면 안 된다.

    newProxyInstance의 세 인자는 각각 이유가 있다. 첫째 인자인 클래스 로더는 새로 만든 클래스를 어느 로더에 정의할지를 정한다. JVM에서 클래스는 이름만으로 구별되지 않고 그것을 정의한 클래스 로더와 함께 구별되므로, 프록시 클래스가 인터페이스를 볼 수 있는 로더에 정의돼야 한다. 둘째 인자는 프록시가 구현할 인터페이스 목록이고, 셋째 인자가 모든 호출을 넘겨받을 핸들러다.

    API 문서가 보장하는 프록시 클래스의 성질은 네 가지다. final이고 추상 클래스가 아니며, java.lang.reflect.Proxy를 상속하고, 만들 때 지정한 인터페이스들을 정확히 그 순서대로 구현한다. 실행 결과의 마지막 세 줄이 이 성질을 보여 준다. 상위 클래스는 Proxy이고, proxy instanceof OrderService는 참이지만 proxy instanceof SimpleOrderService는 거짓이다. 프록시는 대상 클래스의 자식이 아니라, 같은 인터페이스를 구현한 형제다.

    여기서 JDK 동적 프록시의 근본적인 제약이 나온다. 자바의 클래스는 부모 클래스를 하나만 가질 수 있는데, 프록시 클래스는 이미 Proxy를 상속하고 있다. 그러므로 SimpleOrderService 같은 구체 클래스를 추가로 상속할 방법이 없고, 대상과 타입을 맞출 수단은 인터페이스뿐이다. "JDK 동적 프록시는 인터페이스가 있어야 쓸 수 있다"는 말은 편의상의 규칙이 아니라 단일 상속에서 나오는 귀결이다.

    핸들러 안의 method.invoke(target, args)는 리플렉션(reflection) 호출이다. Method 객체는 "어느 클래스의 어떤 이름과 매개변수를 가진 메서드"라는 정보를 담은 객체이고, invoke는 그 메서드를 주어진 객체에 대해 실행한다. 인자는 Object[]로, 반환값은 Object로 오가므로 기본형은 박싱된다. count()가 돌려준 int 1은 Integer로 포장돼 핸들러를 거쳐 나오고, 프록시 메서드가 그것을 다시 int로 풀어 호출자에게 준다. 리플렉션 자체는 로드맵 뒤쪽의 자바 고급 2편에서 본격적으로 다룬다.

API 문서는 java.lang.Object에 선언된 이 세 메서드의 호출도 인터페이스 메서드와 같은 방식으로 핸들러에 전달된다고 명시한다. 그래서 위 예제에 System.out.println(proxy)를 한 줄 넣으면 [시작] toString과 [종료] toString이 먼저 찍힌다. 프록시를 로그에 찍거나 HashMap의 키로 쓰는 것만으로도 핸들러가 실행된다는 뜻이다.

    예외가 프록시를 통과할 때

    예외 테이블 세 줄은 프록시가 예외를 어떻게 다루는지를 말해 준다. 핸들러가 던진 것이 Error나 RuntimeException이면 그대로 다시 던지고, 그 밖의 Throwable이면 UndeclaredThrowableException으로 감싼다. 인터페이스의 place는 체크 예외를 선언하지 않았으므로, 선언되지 않은 체크 예외가 호출자에게 그대로 새어 나가지 못하게 막는 것이다. API 문서에 적힌 규칙과 같다.

    이 규칙은 위 TraceHandler에 숨어 있는 결함을 드러낸다. 대상 메서드가 IllegalArgumentException을 던지면 method.invoke는 그것을 체크 예외인 InvocationTargetException으로 감싸서 던진다. 핸들러가 이것을 그대로 내보내면 프록시는 다시 UndeclaredThrowableException으로 감싼다. 실제로 실행해 보면 호출자가 받는 예외는 java.lang.reflect.UndeclaredThrowableException이고 그 원인이 InvocationTargetException이다. 프록시를 끼웠더니 호출자의 catch (IllegalArgumentException e)가 더는 동작하지 않게 된 것이다. 핸들러에서 포장을 풀어 주어야 원래 예외가 전달된다.

    @Override
public Object invoke(Object proxy, Method method, Object[] args) throws Throwable {
    System.out.println("[시작] " + method.getName());
    try {
        return method.invoke(target, args);
    } catch (InvocationTargetException e) {
        throw e.getCause();   // 대상이 던진 원래 예외를 꺼내 다시 던진다
    } finally {
        System.out.println("[종료] " + method.getName());
    }
}

    프록시가 "있어도 없는 것처럼" 보이려면 반환값뿐 아니라 예외도 원래대로 전달해야 한다. 스프링의 프록시는 이 처리를 내부에서 해 주므로, 스프링이 만든 JDK 동적 프록시를 거쳐도 대상이 던진 IllegalArgumentException이 그대로 올라온다. 직접 프록시를 만들 일이 생기면 가장 먼저 틀리는 지점이 여기다.

    호출 한 번의 비용도 구조에서 읽을 수 있다. 프록시를 거치면 인자 배열 할당, 기본형 박싱, 리플렉션 호출, 추가 스택 프레임이 더해진다. 실제로 얼마나 느려지는지는 JIT 컴파일러의 최적화와 대상 메서드가 하는 일에 따라 달라지므로 일반적인 수치로 말할 수 없다. 기억할 것은 "공짜는 아니지만, DB 조회나 네트워크 호출이 들어 있는 메서드에서는 보통 그 비용이 본문에 묻힌다"는 방향성이다.

    AOP의 용어 — 방금 만든 것에 이름 붙이기

    AOP에는 낯선 용어가 많지만, 대부분은 앞의 예제에 이미 등장한 것들에 붙은 이름이다. 스프링 레퍼런스의 정의를 요약하고, 동적 프록시 예제의 무엇에 해당하는지 나란히 놓아 보자.

    AOP 프록시애스펙트의 계약을 구현하려고 프레임워크가 만든 객체. 스프링에서는 JDK 동적 프록시 또는 CGLIB 프록시$Proxy0 인스턴스
    위빙(weaving)애스펙트를 다른 타입이나 객체와 연결해 어드바이스가 적용된 객체를 만드는 일Proxy.newProxyInstance 호출

    가장 중요한 구분은 포인트컷과 어드바이스다. 앞 절에서 "무엇을 할 것인가"와 "어디에 적용할 것인가"를 나눠 생각했는데, 앞의 것이 어드바이스이고 뒤의 것이 포인트컷이다. 애스펙트는 이 둘을 한 클래스에 묶은 모듈이다. AOP가 푸는 문제는 결국 이 두 가지를 핵심 로직 밖의 한곳에 적을 수 있게 하는 것이다.

    어드바이스는 조인 포인트의 어느 시점에 실행되느냐에 따라 종류가 나뉜다. 레퍼런스는 다섯 가지를 든다. 메서드 실행 전에 도는 before, 정상 반환 뒤에 도는 after returning, 예외로 빠져나갈 때 도는 after throwing, 어떻게 빠져나가든 도는 after(finally), 그리고 메서드 실행 전체를 감싸는 around다. around는 대상 메서드를 실행할지 말지, 무엇을 반환할지까지 스스로 결정할 수 있어서 가장 강력하다. 시간 측정은 실행 전에 읽은 시각을 실행 후에 다시 써야 하므로 앞뒤를 한 메서드 안에서 다루는 around가 자연스럽다. 레퍼런스는 요구를 충족하는 것 가운데 가장 약한 종류의 어드바이스를 쓰라고 권한다. 권한이 큰 만큼 실수할 여지도 크기 때문이다.

    위빙은 시점에 따라 세 가지로 나뉜다. 컴파일할 때(AspectJ 컴파일러), 클래스를 로딩할 때, 그리고 실행 중이다. 레퍼런스는 스프링 AOP가 다른 순수 자바 AOP 프레임워크처럼 실행 중에 위빙을 수행한다고 적는다. 여기서 "실행 중 위빙"의 실체는 바이트코드를 고치는 것이 아니라 프록시 객체를 만들어 대상 앞에 세우는 것이다. 이 선택이 스프링 AOP의 능력과 한계를 모두 결정한다. 조인 포인트가 "항상 메서드 실행"인 것도 프록시가 가로챌 수 있는 것이 메서드 호출뿐이기 때문이다.

    AOP 적용 — 애스펙트 한 개로 모든 메서드를 감싼다

    스프링에서는 프록시 클래스도 핸들러도 직접 만들지 않는다. 개발자가 할 일은 애스펙트 클래스 하나를 쓰고 빈으로 등록하는 것이 전부다. 스프링 부트 3.x 프로젝트라면 먼저 AOP 스타터를 의존성에 추가한다. 부트 문서의 스타터 목록은 이것을 "Spring AOP와 AspectJ로 관점 지향 프로그래밍을 하기 위한 스타터"라고 소개한다.

    dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-aop'
}

    스프링 부트 레퍼런스에 따르면 AspectJ가 클래스패스에 있을 때 부트의 자동 설정이 AspectJ 자동 프록시 기능을 켜 주므로 @EnableAspectJAutoProxy를 따로 붙일 필요가 없다. 부트 없이 스프링 프레임워크만 쓴다면 설정 클래스에 @EnableAspectJAutoProxy를 붙이고, org.aspectj:aspectjweaver 1.9 이상을 클래스패스에 올려야 한다.

    스프링 AOP가 프록시 방식이라면서 왜 AspectJ 라이브러리가 필요한지 의아할 수 있다. 이유는 두 가지다. 곧 쓸 @Aspect와 @Around 애너테이션이 org.aspectj.lang.annotation 패키지에 들어 있고, 포인트컷을 적는 표현식 언어가 AspectJ의 것이기 때문이다. 스프링은 AspectJ의 표기법을 빌려 쓸 뿐, 어드바이스를 적용하는 일은 자신이 만든 프록시로 실행 중에 한다. 이제 처음의 예제로 돌아가자. 측정 코드가 없는 원래의 두 클래스에 스프링 애너테이션만 붙인다.

    package shop;

import org.springframework.stereotype.Repository;

@Repository
public class StockRepository {

    public int remaining(String item) {
        return 3;
    }
}
    package shop;

import org.springframework.stereotype.Service;

@Service
public class OrderService {

    private final StockRepository stockRepository;

    public OrderService(StockRepository stockRepository) {
        this.stockRepository = stockRepository;

    public String place(String item) {
        if (!inStock(item)) {
            return "품절: " + item;
        }
        return "주문 접수: " + item;
    }

    public boolean inStock(String item) {
        return stockRepository.remaining(item) > 0;
    }
}

    이번에는 OrderService가 인터페이스 없는 구체 클래스이고, place가 같은 클래스의 inStock을 호출한다는 점을 기억해 두자. 둘 다 뒤에서 중요한 관찰 거리가 된다. 시간 측정은 다음 클래스 하나에 모두 들어간다.

    package shop;

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;
import org.springframework.stereotype.Component;

@Aspect
@Component
public class ElapsedTimeAspect {

    @Around("execution(* shop..*(..))")
    public Object measure(ProceedingJoinPoint joinPoint) throws Throwable {
        long start = System.nanoTime();
        System.out.println("START " + joinPoint.getSignature().toShortString());
        try {
            return joinPoint.proceed();
        } finally {
            long elapsedMs = (System.nanoTime() - start) / 1_000_000;
            System.out.println("END   " + joinPoint.getSignature().toShortString() + " " + elapsedMs + "ms");
        }
    }
}

    부트 애플리케이션에서는 이 클래스를 추가하는 것으로 끝난다. 여기서는 컨테이너가 하는 일을 눈으로 확인하려고 부트 없이 컨테이너만 띄워 실행했다. 아래 설정의 proxyTargetClass = true는 스프링 부트의 기본 동작과 같은 조건을 만들기 위한 것이며, 그 의미는 CGLIB 절에서 설명한다. 이 회차의 실행 결과는 JDK 21과 Spring Framework 7.0.10에서 직접 돌려 얻었다. 규칙으로 인용한 내용은 6.2 레퍼런스에 실린 것만 썼고, 클래스 이름이나 로그 문구처럼 버전에 따라 달라질 수 있는 부분은 그때마다 밝힌다.

import org.springframework.context.annotation.ComponentScan;

import org.springframework.context.annotation.EnableAspectJAutoProxy;

@Configuration

    애스펙트 코드를 한 줄씩

    @Aspect는 이 클래스가 애스펙트임을 표시한다. 그러나 레퍼런스가 분명히 적어 두었듯 @Aspect만으로는 컴포넌트 스캔의 대상이 되지 않는다. 그래서 @Component를 함께 붙였다. 컴포넌트 스캔 대신 설정 클래스의 @Bean 메서드로 등록해도 되며, 어느 쪽이든 애스펙트는 컨테이너가 관리하는 평범한 빈이다.

    @Around의 문자열이 포인트컷이고 메서드 본문이 어드바이스다. 레퍼런스의 규칙에 따르면 around 어드바이스 메서드는 반환 타입을 Object로 선언해야 하고, 첫 번째 매개변수는 ProceedingJoinPoint여야 한다. ProceedingJoinPoint는 지금 가로챈 조인 포인트를 나타내는 객체다. getSignature()로 어떤 메서드인지 알 수 있고, proceed()를 호출하면 대상 메서드(다른 어드바이스가 더 있으면 다음 어드바이스)로 실행이 넘어간다.

    proceed()는 대상 메서드의 반환값을 Object로 돌려준다. inStock처럼 boolean을 반환하는 메서드라면 Boolean으로 박싱돼 온다. 이 값을 그대로 return해야 호출자가 결과를 받는다. 동적 프록시 예제의 return method.invoke(target, args)와 정확히 같은 자리다. 메서드 선언에 throws Throwable이 붙은 것은 proceed()가 대상 메서드가 던지는 무엇이든 그대로 던질 수 있기 때문이다. 예외를 잡지 않고 finally만 쓰면, 대상이 던진 예외는 종료 로그를 남긴 뒤 호출자에게 그대로 전달된다.

    around 어드바이스의 권한이 얼마나 큰지는 proceed()의 규칙에서 드러난다. 레퍼런스는 어드바이스 본문에서 proceed()를 한 번, 여러 번, 또는 한 번도 호출하지 않는 것이 모두 합법이라고 적는다. 호출하지 않으면 대상 메서드는 실행되지 않고 어드바이스의 반환값이 호출자에게 간다. 캐시가 그런 식으로 동작하고, 여러 번 호출하면 재시도가 된다. 반대로 실수로 proceed()의 결과를 반환하지 않거나 어드바이스의 반환 타입을 void로 선언하면 호출자는 항상 null을 받는다. 직접 실험해 보면 String을 반환하는 메서드의 호출자는 null을 받고, boolean을 반환하는 메서드에서는 프록시가 null을 기본형으로 풀 수 없어 AopInvocationException(Null return value from advice does not match primitive return type)이 발생한다.

    마지막으로 start가 필드가 아니라 지역 변수라는 점이 중요하다. 애스펙트는 싱글톤 빈이므로 인스턴스가 하나뿐이고, 요청을 처리하는 모든 스레드가 그 하나를 함께 쓴다. start를 필드에 저장하면 두 스레드가 동시에 서로 다른 메서드를 측정할 때 값을 덮어쓴다. 지역 변수는 호출마다 새로 생기는 스택 프레임에 들어가므로 스레드끼리 공유되지 않는다. 어드바이스가 호출 하나에 대한 상태를 가져야 한다면 지역 변수에 둔다.

    포인트컷 표현식 읽는 법

    포인트컷 execution(* shop..*(..))은 "어떤 메서드 실행에 이 어드바이스를 적용할 것인가"를 적은 식이다. execution은 메서드 실행 조인 포인트를 매칭하는 지시자이고, 레퍼런스는 이것을 스프링 AOP에서 주로 쓰는 지시자라고 설명한다. 괄호 안의 형식은 다음과 같이 정해져 있다.

    execution(modifiers-pattern?
          ret-type-pattern
          declaring-type-pattern?name-pattern(param-pattern)
          throws-pattern?)

    물음표가 붙은 부분은 생략할 수 있다. 반드시 있어야 하는 것은 반환 타입 패턴, 이름 패턴, 매개변수 패턴 세 가지다. 이 형식에 맞춰 예제의 식을 조각내면 다음과 같이 읽힌다.

    조각자리뜻
    *반환 타입 패턴반환 타입이 무엇이든
    shop..선언 타입 패턴shop 패키지와 그 하위 패키지에 선언된 타입
    * (괄호 바로 앞)이름 패턴메서드 이름이 무엇이든
    (..)매개변수 패턴매개변수가 0개 이상, 타입 무관

    패키지 부분의 점 개수가 범위를 가른다. 점 두 개(..)는 하위 패키지까지 포함하고, 점 하나는 바로 그 패키지만 뜻한다. shop.Top과 하위 패키지의 shop.sub.Deep에 각각 hi() 메서드를 두고 세 가지 식을 적용해 보면 차이가 분명하다.

    표현식shop.Top.hi()shop.sub.Deep.hi()
    execution(* shop..*(..))적용됨적용됨
    execution(* shop..*.*(..))적용됨적용됨
    execution(* shop.*.*(..))적용됨적용 안 됨

    둘째 줄은 레퍼런스가 "service 패키지 또는 그 하위 패키지에 정의된 모든 메서드"의 예로 드는 형태로, 타입 패턴 shop..*와 이름 패턴 *를 점으로 이어 적은 것이다. 매개변수 패턴도 몇 가지를 알아 두면 대부분의 식을 읽을 수 있다. ()는 매개변수가 없는 메서드, (..)는 개수와 타입에 상관없는 모든 메서드, (*)는 타입에 상관없이 매개변수가 정확히 하나인 메서드, (*,String)은 매개변수가 둘이고 두 번째가 String인 메서드와 매칭된다. 이름 패턴에도 set*처럼 일부에만 와일드카드를 쓸 수 있다.

    execution 외에도 지시자가 여럿 있다. 특정 타입 안으로 범위를 좁히는 within, 대상 객체의 타입으로 고르는 target, 인자 타입으로 고르는 args, 메서드에 붙은 애너테이션으로 고르는 @annotation, 그리고 빈 이름으로 고르는 스프링 전용 지시자 bean이 있다. 이들은 &&, ||, !로 조합할 수 있다. 지시자 하나하나의 세부는 로드맵 뒤쪽의 스프링 핵심 원리 고급편에서 다루므로, 여기서는 "포인트컷은 조합 가능한 술어"라는 점만 가져가면 된다.

    포인트컷이 평가되는 시점은 두 번이라는 점도 알아 두자. 첫 번째는 빈을 만들 때다. 컨테이너는 "이 빈의 클래스에 포인트컷과 매칭되는 메서드가 하나라도 있는가"를 따져 프록시를 만들지 말지 정한다. 매칭되는 메서드가 전혀 없는 빈은 프록시 없이 원래 객체가 그대로 등록된다. 두 번째는 프록시의 메서드가 호출될 때다. 이때는 "지금 호출된 이 메서드에 어떤 어드바이스들을 적용할 것인가"가 결정된다. 프록시가 씌워진 빈이라도 매칭되지 않는 메서드는 어드바이스 없이 대상으로 바로 넘어간다.

    가로챌 수 있는 메서드의 범위는 프록시 종류에 따라 다르다. 레퍼런스에 따르면 JDK 프록시에서는 인터페이스의 public 메서드 호출만, CGLIB에서는 public과 protected 메서드 호출(필요하면 패키지 가시성 메서드까지)이 가로채진다. 다만 레퍼런스는 프록시를 통한 상호작용은 언제나 public 시그니처로 설계하라고 덧붙인다.

    컨테이너는 언제 빈을 프록시로 바꾸는가

    실행 결과에서 컨테이너가 돌려준 객체의 클래스는 OrderService$$SpringCGLIB$$0이었다. 우리는 OrderService에 @Service를 붙였을 뿐인데, 누가 언제 그것을 다른 클래스의 객체로 바꿔 놓았을까. 답은 04회에서 본 빈 생성 과정에 들어 있는 확장 지점, 빈 후처리기(BeanPostProcessor)다.

    빈 후처리기는 컨테이너가 빈 인스턴스를 만들 때마다 콜백을 받는 객체다. 레퍼런스의 설명으로는 초기화 메서드가 호출되기 전과 초기화 콜백이 끝난 뒤, 두 번 콜백을 받는다. 그리고 후처리기는 받은 빈 인스턴스에 무엇이든 할 수 있는데, 대표적인 일이 "빈을 프록시로 감싸는 것"이다. 레퍼런스는 스프링 AOP의 기반 클래스 일부가 프록시 감싸기를 제공하려고 빈 후처리기로 구현돼 있다고 명시한다. 후처리기가 원래 객체 대신 다른 객체를 반환하면, 컨테이너는 반환된 그 객체를 빈으로 등록한다.

    AOP를 담당하는 후처리기의 이름은 AnnotationAwareAspectJAutoProxyCreator다. @EnableAspectJAutoProxy(부트에서는 자동 설정)가 하는 일이 바로 이 후처리기를 컨테이너에 등록하는 것이다. 예제의 컨테이너에서 BeanPostProcessor 타입의 빈을 조회해 보면 org.springframework.aop.config.internalAutoProxyCreator라는 이름으로 이 클래스가 등록돼 있는 것을 확인할 수 있다. 이 클래스의 조상인 AbstractAutoProxyCreator의 API 문서는 자신을 "자격이 있는 빈을 AOP 프록시로 감싸는 BeanPostProcessor 구현"이라고 소개하고, postProcessAfterInitialization 메서드에 대해서는 프록시 대상으로 판별된 빈이면 설정된 인터셉터들로 프록시를 만든다고 설명한다.

    이 순서를 실험으로 확인할 수 있다. OrderService의 생성자에 System.out.println("생성자 실행: " + getClass().getName())을 넣고 컨테이너를 띄우면 생성자 실행: shop.OrderService가 정확히 한 번 찍힌다. 생성자가 실행된 객체는 프록시가 아니라 원래 클래스의 인스턴스이고, 프록시는 그 뒤에 따로 만들어진다는 뜻이다. 또 앞의 실행 결과에서 OrderService가 재고를 조회할 때 START StockRepository.remaining(..)이 찍혔다는 사실은, OrderService의 생성자에 주입된 것이 StockRepository 원본이 아니라 이미 프록시였음을 말해 준다. 컨테이너가 띄워진 뒤의 힙은 다음과 같은 모습이다.

    애스펙트 자신은 프록시가 되지 않았다. 포인트컷 shop..의 범위 안에 ElapsedTimeAspect도 들어 있지만, 레퍼런스에 따르면 스프링 AOP에서 애스펙트는 다른 애스펙트의 어드바이스 대상이 될 수 없고 @Aspect가 붙은 클래스는 자동 프록시 대상에서 제외된다. 같은 이유로 빈 후처리기 자신과 후처리기가 직접 참조하는 빈도 자동 프록시의 대상이 되지 못한다. 후처리기가 준비되기 전에 만들어지는 객체에는 후처리기를 적용할 수 없기 때문이다.

    컨테이너가 대상 객체를 만든 뒤 빈 후처리기를 거치면서 프록시가 만들어지고, 빈 저장소에는 프록시가 등록된다는 흐름을 보여 준다. 흰 배경의 왼쪽에서 오른쪽으로 흐르는 순서도. 왼쪽에 둥근 사각형 "① 생성자 실행"과 그 아래 작은 파란 상자 "OrderService 객체"를 그린다. 가운데에 깔때기 모양의 큰 도형을 두고 "② 빈 후처리기 (자동 프록시 생성기)"라고 적는다. 파란 상자에서 깔때기로 화살표가 들어간다. 깔때기 위쪽에 마름모 "포인트컷과 매칭되는 메서드가 있는가?"를 연결한다. 깔때기 오른쪽으로 화살표가 나와 주황색 상자 "프록시 객체"에 닿고, 주황색 상자 안에서 점선 화살표가 작은 파란 상자 "대상 객체"를 가리킨다. 가장 오른쪽에 원통 모양의 "③ 싱글톤 빈 저장소"를 그리고, 저장소 안의 라벨 "orderService"에서 주황색 프록시 상자로 화살표를 긋는다. 저장소 아래에 "주입과 조회는 프록시를 받는다"라는 문구를 둔다. 평면 벡터 스타일, 색은 파랑·주황·회색만 사용한다. 대상 객체는 그대로 만들어지지만, 빈 저장소에 이름으로 등록되는 것은 그것을 감싼 프록시다.

    CGLIB 프록시의 정체 — 상속으로 만든 서브클래스

    JDK 동적 프록시는 인터페이스가 있어야 한다. 그런데 예제의 OrderService에는 인터페이스가 없다. 이 경우 스프링은 CGLIB이라는 바이트코드 생성 라이브러리로 프록시를 만든다. 레퍼런스의 표현으로 CGLIB 프록시는 "대상 타입의 실행 중 생성된 서브클래스"이며, CGLIB은 spring-core 안에 재포장돼 들어 있어서 따로 의존성을 추가할 필요가 없다. 타입을 맞추는 방법이 "같은 인터페이스 구현"에서 "대상 클래스 상속"으로 바뀐 것이다. 실행 결과에서 getSuperclass()가 shop.OrderService였고 instanceof OrderService가 참이었던 것이 그 증거다.

    상속이기 때문에 생기는 제약

    서브클래스를 만들어 메서드를 재정의하는 방식이므로, 자바에서 상속과 재정의가 막힌 곳에서는 CGLIB 프록시도 막힌다. 레퍼런스가 드는 제약은 다음과 같다.

    • final 클래스는 상속할 수 없으므로 프록시를 만들 수 없다. 실험해 보면 컨테이너가 뜨다가 AopConfigException: Could not generate CGLIB subclass of class ...으로 실패하고, 그 원인으로 Cannot subclass final class가 붙어 나온다.
    • final 메서드는 재정의할 수 없으므로 어드바이스가 적용되지 않는다.
    • private 메서드도 재정의할 수 없으므로 어드바이스가 적용되지 않는다.

    위 javap 출력에는 생성자 OrderService$$SpringCGLIB$$0(StockRepository)도 보인다. 자식 클래스의 생성자는 부모 생성자를 호출해야 하므로, 이 생성자로 프록시를 만들면 OrderService의 생성자가 대상 객체를 만들 때 한 번, 프록시 객체를 만들 때 또 한 번 실행될 것이다. 그러나 앞의 실험에서 생성자 로그는 한 번만 찍혔다. 레퍼런스가 그 이유를 설명한다. 스프링은 CGLIB 프록시 인스턴스를 Objenesis라는 라이브러리로 만들며, 이 방식은 생성자를 거치지 않고 인스턴스를 만든다.

    생성자를 건너뛰었다는 사실에서 중요한 귀결이 나온다. 프록시도 OrderService의 자식이므로 프록시 객체 안에도 stockRepository 필드를 위한 자리가 있다. 그러나 그 필드에 값을 넣어 줄 생성자가 실행된 적이 없으므로, 프록시 객체의 필드는 기본값인 null로 남아 있다. 값이 채워진 쪽은 대상 객체뿐이다.

Spring Framework 7.0.10은 이런 클래스를 프록시로 만들 때 "Public final method ... cannot get proxied via CGLIB"라는 경고 로그를 남겼다. 프록시가 씌워지는 빈에서는 메서드에 final을 붙이지 않고, 빈의 필드를 밖에서 직접 읽지 않는 것이 안전하다.

    JDK 동적 프록시와 CGLIB 가운데 어느 쪽이 쓰이는가

    스프링 프레임워크의 기본 규칙은 레퍼런스에 이렇게 적혀 있다. 대상 객체가 인터페이스를 하나라도 구현하면 JDK 동적 프록시를 쓰고, 인터페이스가 없으면 CGLIB 프록시를 만든다. 그리고 proxyTargetClass 옵션을 켜면 인터페이스가 있어도 CGLIB을 쓰도록 강제할 수 있다. 스프링 부트는 이 기본값이 다르다. 부트 레퍼런스는 자동 설정이 스프링 AOP가 CGLIB 프록시를 쓰도록 구성하며, JDK 프록시를 쓰려면 spring.aop.proxy-target-class를 false로 설정하라고 안내한다. 앞의 설정에서 proxyTargetClass = true를 준 것이 이 조건을 재현한 것이다.

    두 방식의 차이가 실제로 문제를 일으키는 곳은 타입이다. 인터페이스 PaymentGateway와 그 구현 클래스 CardPaymentGateway를 빈으로 등록하고, 이번에는 옵션 없이 @EnableAspectJAutoProxy만 붙여 JDK 동적 프록시가 쓰이게 한 뒤 다음 코드를 실행했다.

    PaymentGateway gateway = context.getBean(PaymentGateway.class);
System.out.println(gateway.getClass().getName());            // jdk.proxy2.$Proxy16 (번호는 환경마다 다르다)
System.out.println(gateway instanceof CardPaymentGateway);   // false
context.getBean(CardPaymentGateway.class);
// NoSuchBeanDefinitionException: No qualifying bean of type 'pay.CardPaymentGateway' available

    JDK 동적 프록시는 PaymentGateway를 구현한 형제일 뿐 CardPaymentGateway의 자식이 아니다. 따라서 구현 클래스 타입으로는 빈을 찾을 수 없고, 구현 클래스 타입의 필드에 주입할 수도 없다. CGLIB 프록시는 구현 클래스의 자식이므로 인터페이스 타입으로도 구현 클래스 타입으로도 주입된다. 두 방식을 정리하면 다음과 같다.

    구분JDK 동적 프록시CGLIB 프록시
    대상과 타입을 맞추는 방법같은 인터페이스를 구현대상 클래스를 상속
    전제 조건대상이 인터페이스를 구현해야 한다대상 클래스가 final이 아니어야 한다
    가로채지 못하는 메서드인터페이스에 없는 메서드final, private 메서드
    구현 클래스 타입으로 주입불가능가능
    프록시 클래스를 만드는 주체JDK(java.lang.reflect.Proxy)spring-core에 포함된 CGLIB
    기본으로 선택되는 경우스프링 프레임워크만 쓸 때, 대상에 인터페이스가 있으면인터페이스가 없을 때, 그리고 스프링 부트의 기본 설정

    호출 한 번이 지나는 길 — 인터셉터 체인

    프록시의 place가 인터셉터에게 호출을 넘긴다는 것까지는 바이트코드로 확인했다. 그 뒤에 어드바이스와 대상 메서드가 어떤 순서로 실행되는지는 호출 스택이 가장 정확하게 보여 준다. StockRepository.remaining 안에서 new Throwable().getStackTrace()로 스택을 찍고, main에서 orderService.inStock(...)을 호출한 결과다. 가장 안쪽 호출이 맨 위에 있으므로 아래에서 위로 읽는다.

    프록시 메서드와 대상 메서드 사이에 프레임 16개가 끼어 있다. 프레임 이름은 스프링 버전에 따라 조금씩 다를 수 있지만 구조는 세 단계로 읽힌다. 먼저 프록시 메서드가 DynamicAdvisedInterceptor.intercept를 호출한다. 이것이 생성된 클래스의 CGLIB$CALLBACK_0 필드에 들어 있던 인터셉터다. 이 인터셉터는 지금 호출된 메서드에 적용할 어드바이스 목록을 꺼내고, 프록시와 대상, 메서드, 인자, 어드바이스 목록을 한데 묶은 "호출 객체"를 만들어 proceed()를 부른다.

    두 번째 단계가 ReflectiveMethodInvocation.proceed다. 스택에 이 프레임이 세 번 나온다는 점에 주목하자. 레퍼런스는 스프링을 포함한 많은 AOP 프레임워크가 어드바이스를 인터셉터로 모델링하고 조인 포인트 주위에 인터셉터의 사슬을 유지한다고 설명한다. proceed()는 그 사슬을 한 칸씩 전진시키는 메서드다. API 문서의 설명도 "사슬의 다음 인터셉터로 진행한다"이다. 구조를 의사 코드로 적으면 다음과 같다.

    proceed():
    아직 실행하지 않은 인터셉터가 남아 있지 않으면
        대상 메서드를 리플렉션으로 호출하고 그 결과를 반환한다     ← 조인 포인트 실행
    그렇지 않으면
        다음 인터셉터를 꺼내 interceptor.invoke(이 호출 객체)를 부르고 그 결과를 반환한다
        (인터셉터는 자기 일을 하다가 호출 객체의 proceed()를 다시 부른다)

    인터셉터가 proceed()를 부르고, proceed()가 다음 인터셉터를 부르는 재귀가 어드바이스의 중첩 구조를 만든다. 예제의 사슬에는 인터셉터가 두 개 있다. 첫 번째 ExposeInvocationInterceptor는 스프링이 넣은 내부 인터셉터로, API 문서에 따르면 현재의 호출 객체를 스레드 로컬에 노출하는 역할을 하며 보통 사슬의 맨 앞에 놓인다. 두 번째 AspectJAroundAdvice가 우리가 쓴 @Around 메서드를 인터셉터 모양으로 감싼 어댑터다. 이 어댑터가 리플렉션으로 ElapsedTimeAspect.measure를 호출하는 것이 스택의 가운데 부분이다.

    세 번째 단계는 어드바이스 안에서 일어난다. measure가 joinPoint.proceed()를 호출하면 MethodInvocationProceedingJoinPoint.proceed를 거쳐 다시 ReflectiveMethodInvocation.proceed로 들어간다. 이번에는 남은 인터셉터가 없으므로 invokeJoinpoint가 Method.invoke로 대상 객체의 remaining을 실행한다. 동적 프록시 예제에서 우리가 직접 쓴 method.invoke(target, args)가 스프링 안에서는 바로 이 자리에 있다. 반환은 정확히 역순으로 일어난다. 대상 메서드가 값을 반환하면 measure의 finally가 END 로그를 찍고, 값은 프레임을 하나씩 거슬러 올라가 호출자에게 도착한다.

    호출자 ──▶ 프록시.inStock()
             └▶ 인터셉터.intercept()  : 이 메서드에 적용할 어드바이스 사슬을 꺼낸다
                  └▶ proceed()  ──▶ ElapsedTimeAspect.measure()
                                       ├ START 출력
                                       ├ joinPoint.proceed() ──▶ proceed()   (남은 어드바이스 없음)
                                       │                           └▶ 대상.inStock() 본문 실행
                                       │                        ◀── 반환값 true
                                       └ finally: END 출력
호출자 ◀── true                        (처음부터 끝까지 같은 스레드, 같은 호출 스택)

    이 스택에서 가져갈 사실이 두 가지 있다. 하나는 프록시를 거친 호출도 평범한 중첩 메서드 호출이라는 점이다. 스레드가 바뀌지 않고, 호출자의 스택 위에 프레임이 더 쌓일 뿐이다. 그래서 대상 메서드에서 예외가 나면 그 예외는 어드바이스의 finally와 catch를 차례로 지나 호출자에게 올라가고, 스레드에 묶어 둔 정보는 어드바이스와 대상 메서드가 함께 볼 수 있다. 다른 하나는 장애 상황에서 보게 될 스택 트레이스의 모양이다. 서비스 메서드 사이에 $$SpringCGLIB$$과 ReflectiveMethodInvocation.proceed가 반복해서 끼어 있으면, 그 지점에 프록시가 있고 어드바이스가 실행됐다는 뜻이다.

    애스펙트가 여러 개면 사슬이 길어질 뿐 원리는 같다. 실행 순서에 대해 레퍼런스는 서로 다른 애스펙트의 어드바이스가 같은 조인 포인트에 적용될 때 따로 지정하지 않으면 순서가 정해져 있지 않다고 밝힌다. 순서가 필요하면 애스펙트에 @Order를 붙이거나 Ordered 인터페이스를 구현한다. 값이 작을수록 우선순위가 높고, 우선순위가 높은 어드바이스가 들어갈 때는 먼저, 나올 때는 나중에 실행된다. 바깥쪽 괄호가 되는 셈이다.

    호출자, 프록시, 어드바이스, 대상 객체 네 참여자 사이에서 호출이 들어가고 반환이 역순으로 나오는 과정을 보여 준다. 흰 배경의 UML 시퀀스 다이어그램. 위쪽에 참여자 상자 네 개를 왼쪽부터 "호출자", "프록시", "어드바이스", "대상 객체" 순으로 배치하고 각각 아래로 점선 생명선을 내린다. 실선 화살표 ① "inStock()"이 호출자에서 프록시로, ② "proceed()"가 프록시에서 어드바이스로 간다. 어드바이스 생명선 위에 작은 메모 "START 기록"을 붙인다. ③ "joinPoint.proceed()"가 어드바이스에서 대상 객체로 간다. 대상 객체 생명선에 활성 막대를 그리고 "본문 실행"이라고 적는다. 점선 반환 화살표 ④ "반환값"이 대상 객체에서 어드바이스로, 어드바이스 생명선에 메모 "END 기록"을 붙인 뒤 ⑤ 점선 화살표가 어드바이스에서 프록시로, ⑥ 점선 화살표가 프록시에서 호출자로 돌아간다. 다이어그램 아래에 "모든 단계가 한 스레드의 호출 스택에서 일어난다"라는 문구를 둔다. 색은 파랑과 주황, 회색만 쓴다. 호출은 프록시와 어드바이스를 거쳐 대상에 도착하고, 반환값과 예외는 같은 길을 거꾸로 지나 호출자에게 돌아온다.

    프록시 방식이 만드는 함정

    스프링 AOP의 동작 원리는 "빈 저장소에 대상 대신 프록시를 등록하고, 프록시를 통해 들어오는 호출을 가로챈다"로 요약된다. 이 문장을 뒤집으면 한계가 된다. 프록시를 통하지 않는 호출은 가로채지 못한다. 실무에서 "AOP가 안 먹는다"는 문제의 대부분이 이 한 문장에서 나온다.

    내부 호출은 프록시를 거치지 않는다

    처음 실행 결과로 돌아가자. orderService.place("키보드")를 호출했을 때 place는 안에서 inStock을 불렀지만 START OrderService.inStock(..)은 찍히지 않았다. 호출 경로를 따라가 보면 이유가 보인다.

    ① 밖에서 들어오는 호출
   Main ──▶ [OrderService 프록시].place() ──▶ 어드바이스 ──▶ 대상 객체의 place() 본문

② 대상 객체의 place() 본문 안에서
   inStock(item)        ← 자바에서 이것은 this.inStock(item)이다
   this = 대상 객체     ← 프록시가 아니다
   ──▶ 대상 객체의 inStock() 본문이 바로 실행된다      (프록시도 어드바이스도 지나지 않는다)

    메서드 본문에서 수신 객체를 생략한 호출 inStock(item)은 this.inStock(item)과 같다. 그리고 place 본문이 실행되는 시점의 this는 프록시가 아니라 대상 객체다. 어드바이스 사슬의 끝에서 스프링이 Method.invoke에 넘긴 수신 객체가 대상 객체였기 때문이다. 대상 객체는 자기 앞에 프록시가 서 있다는 사실을 모르므로, 자신의 메서드를 직접 호출한다. 레퍼런스는 이 현상을 자기 호출(self-invocation)이라 부르며, 명시적이든 암묵적이든 this 참조를 통한 호출은 어드바이스를 우회한다고 적는다.

    여기서 한 가지 오해를 바로잡자. CGLIB 프록시는 OrderService의 서브클래스이고 inStock을 재정의했으니, 가상 메서드 호출 규칙에 따라 this.inStock()이 프록시의 재정의된 메서드로 갈 것이라고 생각하기 쉽다. this가 프록시 객체였다면 그 말이 맞다. 그러나 스프링의 프록시는 자기 자신 위에서 부모의 본문을 실행하지 않고, 따로 존재하는 대상 객체에게 호출을 넘긴다. 힙에 객체가 둘이고, 본문이 실행되는 객체의 실제 클래스는 프록시 클래스가 아닌 shop.OrderService다. 그래서 동적 디스패치가 고르는 것도 원래의 inStock이다.

    레퍼런스가 제시하는 해결책은 세 가지이고, 권하는 순서가 있다. 첫째는 자기 호출이 일어나지 않도록 코드를 고치는 것이다. 예를 들어 inStock을 별도의 빈으로 옮기면 place는 주입받은 그 빈의 프록시를 통해 호출하게 된다. 둘째는 자기 자신의 프록시를 주입받아 this 대신 그 참조로 호출하는 것이다. 셋째는 AopContext.currentProxy()로 현재 프록시를 얻는 것인데, 레퍼런스는 코드가 스프링 AOP에 묶인다는 이유로 이 방법을 강하게 말린다. AspectJ의 컴파일 시점·로드 시점 위빙은 어드바이스를 프록시가 아니라 바이트코드에 직접 넣으므로 이 문제가 없다는 점도 레퍼런스에 함께 적혀 있다.

    외부 호출은 프록시를 지나지만, 대상 객체 안에서 this로 부르는 호출은 프록시 바깥으로 나가지 않는다는 것을 두 경로로 대비한다. 흰 배경의 구조도. 가운데에 큰 주황색 둥근 사각형을 그리고 위쪽 테두리에 "프록시"라고 적는다. 그 안에 조금 작은 파란색 둥근 사각형을 넣고 "대상 객체"라고 적는다. 파란 사각형 안에 작은 상자 두 개 "place()"와 "inStock()"을 위아래로 배치한다. 왼쪽 바깥에 사람 모양 없이 상자 "호출자"를 두고, 호출자에서 출발한 굵은 초록 화살표가 주황색 테두리를 통과하며(통과 지점에 작은 원과 "어드바이스 실행" 라벨) "place()" 상자에 닿는다. "place()" 상자에서 "inStock()" 상자로 가는 빨간 화살표는 파란 사각형 안에서만 움직이며 주황색 테두리를 지나지 않는다. 빨간 화살표 옆에 "this.inStock()"이라고 적고, 그 아래에 "어드바이스 실행 안 됨"이라는 빨간 라벨을 붙인다. 평면 벡터 스타일. 어드바이스는 프록시의 경계를 지나는 호출에만 적용된다. 대상 객체가 자기 메서드를 부르는 호출은 그 경계를 넘지 않는다.

    컨테이너가 만들지 않은 객체와 재정의할 수 없는 메서드

    같은 원리에서 나오는 경우를 더 모아 보자. 레퍼런스는 스프링 AOP가 지원하는 조인 포인트를 "스프링 빈의 메서드 실행"으로 한정한다. 코드에서 new OrderService(repository)로 직접 만든 객체는 컨테이너를 거치지 않았으므로 빈 후처리기가 프록시로 감쌀 기회가 없었고, 어드바이스도 적용되지 않는다. static 메서드는 객체 참조를 통하지 않고 호출되므로 프록시가 끼어들 자리가 처음부터 없다. final과 private 메서드는 앞 절에서 본 대로 재정의가 불가능해 가로챌 수 없다. 필드를 읽고 쓰는 것도 메서드 호출이 아니므로 가로챌 수 없다. 레퍼런스는 필드 가로채기가 구현돼 있지 않다고 밝히고, 그것이 필요하면 AspectJ를 고려하라고 안내한다.

    타입을 비교하는 코드도 프록시의 영향을 받는다. 빈의 getClass()는 프록시 클래스를 돌려주므로 bean.getClass() == OrderService.class는 거짓이다. 타입 검사는 instanceof로 하고, 원래 클래스가 꼭 필요하면 스프링의 AopUtils.getTargetClass(bean)을 쓴다. 예제의 빈에 대해 이 메서드는 shop.OrderService를 돌려준다.

    포인트컷이 설정 클래스까지 덮을 때

    포인트컷을 패키지 전체로 넓게 잡으면 의도하지 않은 빈까지 프록시가 된다. 그중 애플리케이션 시작을 막는 경우가 하나 있다. 애스펙트를 @Component가 아니라 설정 클래스의 @Bean 메서드로 등록하고, 그 설정 클래스가 포인트컷의 범위 안에 있을 때다.

    package shop2;

import org.aspectj.lang.ProceedingJoinPoint;
import org.aspectj.lang.annotation.Around;
import org.aspectj.lang.annotation.Aspect;

@Aspect
public class TraceAspect {

    @Around("execution(* shop2..*(..))")
    public Object trace(ProceedingJoinPoint joinPoint) throws Throwable {
        System.out.println("START " + joinPoint.getSignature().toShortString());
        try {
            return joinPoint.proceed();
        } finally {
            System.out.println("END   " + joinPoint.getSignature().toShortString());
        }
    }
}
    package shop2;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.annotation.EnableAspectJAutoProxy;

@Configuration
@ComponentScan
@EnableAspectJAutoProxy(proxyTargetClass = true)
public class Shop2Config {

    @Bean
    public TraceAspect traceAspect() {
        return new TraceAspect();
    }
}

  Failed to instantiate [shop2.TraceAspect]: Factory method 'traceAspect' threw exception with message:
  Error creating bean with name 'traceAspect': Requested bean is currently in creation:
  Is there an unresolvable circular reference or an asynchronous initialization dependency?
Caused by: BeanCurrentlyInCreationException

    메시지를 그대로 읽으면 원인이 나온다. Shop2Config도 shop2 패키지의 빈이고, traceAspect()는 그 클래스의 메서드이므로 포인트컷과 매칭된다. 컨테이너가 애스펙트 빈을 만들려고 팩터리 메서드 traceAspect()를 호출하면, 그 호출 자체가 어드바이스 적용 대상이다. 어드바이스를 실행하려면 애스펙트 빈이 필요한데, 그 빈은 바로 지금 만들어지는 중이다. 자기 자신을 만드는 호출에 자기 자신이 필요한 순환이 생긴 것이다.

    해결 방법은 순환의 고리 가운데 하나를 끊는 것이다. 포인트컷에서 설정 클래스를 제외하도록 execution(* shop2..*(..)) && !target(shop2.Shop2Config)로 바꾸면 컨테이너가 정상적으로 뜬다. 애스펙트를 @Component로 등록해도 된다. 그 경우 애스펙트는 생성자로 만들어지고, 생성자 실행은 스프링 AOP의 조인 포인트가 아니기 때문이다. 근본적으로는 포인트컷을 "패키지 전체"가 아니라 측정하려는 계층으로 좁히는 편이 낫다.

    스프링 AOP와 AspectJ, 그리고 이후의 연결

    앞에서 호출에 끼어들 수 있는 자리가 세 군데라고 했다. 스프링 AOP는 "참조가 가리키는 객체를 바꾸는" 길을 택했고, AspectJ는 "코드를 바꾸는" 길을 택했다. 두 방식의 차이는 대부분 이 선택에서 따라 나온다.

    구분스프링 AOPAspectJ
    위빙 시점실행 중컴파일 시점 또는 클래스 로드 시점
    수단프록시 객체를 만들어 빈을 대신한다대상 클래스의 바이트코드에 어드바이스를 넣는다
    조인 포인트스프링 빈의 메서드 실행메서드 실행 외에 필드 접근 등도 가능
    내부 호출어드바이스가 적용되지 않는다적용된다
    빌드·실행 환경순수 자바. 별도의 컴파일 과정이 필요 없다AspectJ 컴파일러 또는 위버가 필요하다

    레퍼런스는 스프링 AOP의 목표가 가장 완전한 AOP 구현을 제공하는 데 있지 않다고 밝힌다. 도메인 객체처럼 아주 잘게 쪼개진 객체에 어드바이스를 거는 일은 스프링 AOP로는 쉽거나 효율적으로 할 수 없고, 그런 경우에는 AspectJ가 가장 좋은 선택이라고도 적는다. 스프링 AOP가 겨냥하는 대상은 컨테이너가 관리하는 서비스·리포지토리 수준의 빈이고, 그 범위에서는 프록시만으로 충분하다는 판단이 깔려 있다. 특별한 컴파일러 없이 평범한 자바 빌드로 돌아간다는 점이 그 대가로 얻는 것이다.

    이 회차에서 본 구조는 시간 측정에만 쓰이지 않는다. 스프링 레퍼런스는 선언적 트랜잭션 지원이 AOP 프록시를 통해 이루어지며, 트랜잭션 메타데이터와 AOP가 결합해 TransactionInterceptor를 사용하는 AOP 프록시가 만들어진다고 설명한다. @Transactional이 붙은 빈을 주입받아 getClass()를 찍으면 프록시 클래스가 나오는 이유이고, 같은 클래스 안에서 @Transactional 메서드를 내부 호출하면 트랜잭션이 시작되지 않는 이유다. 인터셉터 사슬에서 ElapsedTimeAspect가 있던 자리에 트랜잭션을 시작하고 커밋하거나 롤백하는 인터셉터가 들어간다고 생각하면 된다.

    로드맵 뒤쪽의 스프링 핵심 원리 고급편은 이 회차에서 한 번씩 훑은 주제인 프록시 패턴, 동적 프록시, 빈 후처리기, 포인트컷을 각각 한 회차씩 들여 다시 쌓아 올린다. 지금 단계에서 가져갈 것은 세부 API가 아니라 하나의 그림이다. 컨테이너는 객체의 생성과 연결을 쥐고 있고, 그 권한으로 대상 앞에 프록시를 세우며, 프록시는 메서드 호출을 데이터로 바꿔 인터셉터 사슬에 흘려보낸다. 스프링의 "애너테이션 하나 붙였더니 동작이 달라지는" 기능을 만나면, 그 빈이 프록시인지와 지금의 호출이 프록시를 지나는지를 먼저 확인하면 된다.

    이 장의 핵심

    횡단 관심사를 핵심 로직에서 떼어 내려면 "무엇을 할지"(어드바이스)와 "어디에 적용할지"(포인트컷)를 대상 코드 밖에 적을 수 있어야 한다. 스프링 AOP는 이를 위해 대상 코드를 고치지 않고, 빈 후처리기에서 대상을 감싼 프록시를 만들어 빈으로 등록한다. 프록시는 JDK 동적 프록시(인터페이스 구현)이든 CGLIB(클래스 상속)이든 메서드 호출을 Method와 인자 배열로 포장해 인터셉터 사슬에 넘기는 일만 한다. 따라서 어드바이스는 프록시를 지나는 호출에만 적용되고, 내부 호출·final 메서드·컨테이너 밖에서 만든 객체에는 적용되지 않는다.
    횡단 관심사
    시간 측정, 로깅, 트랜잭션처럼 여러 클래스의 메서드에 같은 모양으로 걸쳐 나타나는 로직. 핵심 로직에 섞이면 중복되고, 변경 지점이 메서드 수만큼 늘며, 빠뜨려도 알 수 없다.
    프록시
    대상과 같은 타입으로 보이면서 호출을 먼저 받아 부가 작업을 하고 대상에게 위임하는 객체. 호출자가 상위 타입으로 대상을 알고, 객체를 밖에서 건네받을 때 끼워 넣을 수 있다.
    JDK 동적 프록시
    실행 중에 인터페이스를 구현하는 클래스를 만들어 모든 호출을 InvocationHandler.invoke 한 곳으로 보낸다. 프록시 클래스가 이미 Proxy를 상속하므로 구체 클래스는 상속할 수 없고 인터페이스가 필요하다.
    CGLIB 프록시
    대상 클래스를 상속한 서브클래스를 실행 중에 만든다. final 클래스·final 메서드·private 메서드에는 적용할 수 없고, 스프링 부트의 기본 프록시 방식이다.
    애스펙트, 포인트컷, 어드바이스
    어드바이스는 조인 포인트에서 실행할 동작, 포인트컷은 조인 포인트를 고르는 술어, 애스펙트는 둘을 묶은 모듈이다. 스프링 AOP의 조인 포인트는 항상 메서드 실행이다.
    자동 프록시 생성기
    빈 후처리기로 구현된 AOP 기반 클래스. 빈의 초기화가 끝난 뒤 매칭되는 어드바이스가 있으면 프록시를 만들어 반환하고, 컨테이너는 그 프록시를 빈으로 등록한다.
    인터셉터 사슬
    프록시가 넘긴 호출은 어드바이스들을 차례로 지나 대상 메서드에 도착한다. proceed()가 사슬을 한 칸씩 전진시키며, 모든 과정이 호출자의 스레드와 호출 스택에서 일어난다.
    내부 호출 문제
    대상 객체 안에서 this로 부르는 호출은 프록시를 지나지 않으므로 어드바이스가 적용되지 않는다. 메서드를 다른 빈으로 분리하는 것이 권장되는 해결책이다.

    실무에서 다시 판단하면, AOP는 "코드를 줄이는 기술"이기 전에 "보이지 않는 동작을 추가하는 기술"이다. 서비스 메서드의 소스만 읽어서는 그 호출에 트랜잭션이 걸리는지, 재시도가 붙는지, 시간이 기록되는지 알 수 없다. 그래서 애스펙트로 뺄지 말지는 그 로직이 정말 횡단 관심사인지로 판단한다. 트랜잭션 경계, 호출 추적, 권한 검사처럼 업무 규칙과 무관하고 모든 대상에 같은 방식으로 적용되는 것은 애스펙트가 맞다. 반대로 "주문 금액이 일정액을 넘으면 승인을 받는다" 같은 업무 규칙을 애스펙트에 숨기면, 코드를 읽는 사람이 그 규칙을 찾지 못한다.

    장애를 조사할 때는 "지금 이 호출이 프록시를 지나는가"를 가장 먼저 확인한다. @Transactional을 붙였는데 롤백이 안 된다, 캐시가 적용되지 않는다, 로그가 빠진다는 보고의 상당수는 내부 호출이거나, 빈이 아닌 객체를 직접 생성했거나, 메서드가 private이나 final인 경우다. 주입받은 객체의 getClass()를 찍어 프록시인지 확인하고, 스택 트레이스에서 프록시 클래스와 proceed 프레임이 문제의 메서드 바로 앞에 있는지 보면 대부분 몇 분 안에 원인이 좁혀진다. 내부 호출이 원인이라면 우회 기법을 쓰기 전에 클래스의 책임이 너무 큰 것은 아닌지부터 본다. 한 클래스 안에서 트랜잭션 경계가 다른 메서드끼리 호출한다는 것은 대개 두 개의 역할이 한 클래스에 들어 있다는 신호다.

    포인트컷의 범위는 좁게 시작하는 편이 안전하다. 패키지 전체를 덮는 식은 예제로는 편하지만, 실제 애플리케이션에서는 설정 클래스나 의도하지 않은 빈까지 프록시로 만들고, 모든 호출에 프레임과 리플렉션 호출을 더한다. 조건이 달라지는 지점도 있다. 호출 빈도가 매우 높고 본문이 짧은 메서드에 어드바이스를 걸면 프록시 비용이 본문보다 커질 수 있으므로, 그런 곳은 측정 대상에서 빼거나 다른 수단을 쓴다. 그리고 프록시가 닿지 못하는 곳(도메인 객체, 필드 접근, 내부 호출)까지 가로채야 하는 요구라면 스프링 AOP를 억지로 늘리기보다 AspectJ 위빙이 맞는 도구인지 검토한다.
  • 다음 빈과 애스펙트가 CGLIB 프록시 방식으로 등록돼 있다. 애스펙트는 execution(* report..*(..))에 대해 대상 메서드 실행 전에 START 메서드이름, 실행 후에 END 메서드이름을 출력한다. ReportService에는 summary()가 return header() + body();, header()가 return "H";, final 메서드 body()가 return "B";로 정의돼 있다. 컨테이너에서 꺼낸 빈에 대해 summary(), header(), body()를 차례로 호출해 각 반환값을 출력할 때, 콘솔에 찍히는 줄을 순서대로 적어라.
  • JDK 동적 프록시의 핸들러가 return method.invoke(target, args); 한 줄로만 되어 있다. 인터페이스 메서드 String pay(int amount)는 체크 예외를 선언하지 않았고, 대상 구현은 음수 금액에 IllegalArgumentException을 던진다. 프록시에 pay(-1)을 호출하면 호출자는 어떤 타입의 예외를 받는가. 그 이유를 프록시 클래스의 예외 테이블과 연결해 설명하고, 핸들러를 어떻게 고쳐야 하는지 적어라.
  • 본문의 OrderService, StockRepository, ElapsedTimeAspect로 컨테이너를 띄운 직후의 힙을 그려라. OrderService 타입으로 볼 수 있는 객체가 몇 개인지, 각 객체의 stockRepository 필드 값이 무엇인지, 빈 이름 orderService가 어느 객체를 가리키는지 표시하라.
  • 어떤 개발자가 around 어드바이스를 public void around(ProceedingJoinPoint joinPoint) throws Throwable { joinPoint.proceed(); }로 작성했다. 이 어드바이스가 String name()과 boolean ok()에 적용될 때 호출자에게 각각 어떤 일이 일어나는지 예측하고, 왜 두 결과가 다른지 설명하라.
  • 애스펙트를 설정 클래스의 @Bean 메서드로 등록했더니 애플리케이션이 BeanCurrentlyInCreationException으로 뜨지 않는다. 포인트컷은 설정 클래스가 속한 패키지 전체를 덮고 있다. 순환이 생기는 과정을 단계별로 설명하고, 해결 방법을 두 가지 제시하라.
    •

    1번. 출력은 START summary, END summary, HB, START header, END header, H, B 순서다. summary()는 프록시를 통해 호출되므로 어드바이스가 적용된다. 그 안에서 부르는 header()와 body()는 대상 객체의 this를 통한 내부 호출이라 프록시를 지나지 않고, 그래서 summary의 START와 END 사이에 다른 로그가 없다. 밖에서 직접 호출한 header()는 프록시를 지나므로 로그가 찍힌다. body()는 final이라 프록시 클래스가 재정의하지 못했으므로 밖에서 호출해도 어드바이스 없이 본문이 실행된다. 이 메서드는 필드를 읽지 않으므로 프록시 객체 위에서 실행돼도 "B"가 정상적으로 나온다.

    2번. 호출자는 java.lang.reflect.UndeclaredThrowableException을 받고, 그 원인(cause)은 InvocationTargetException이다. Method.invoke는 대상 메서드가 던진 예외를 체크 예외인 InvocationTargetException으로 감싸 던진다. 핸들러가 이를 그대로 내보내면, 프록시 메서드의 예외 테이블에서 Error와 RuntimeException에 해당하지 않으므로 세 번째 줄(Throwable)에 걸려 UndeclaredThrowableException으로 다시 감싸진다. 핸들러에서 catch (InvocationTargetException e) { throw e.getCause(); }로 포장을 풀면 원래의 IllegalArgumentException이 RuntimeException이므로 프록시를 그대로 통과한다.

    3번. OrderService 타입으로 볼 수 있는 객체는 둘이다. 하나는 생성자가 실행된 원래의 OrderService 인스턴스(대상)이고, 이 객체의 stockRepository는 StockRepository의 프록시를 가리킨다. 다른 하나는 OrderService$$SpringCGLIB$$0 인스턴스(프록시)이고, 생성자를 거치지 않고 만들어졌으므로 상속받은 stockRepository 필드는 null이다. 빈 이름 orderService는 프록시를 가리키고, 프록시는 대상을 참조한다. StockRepository도 같은 구조로 대상과 프록시 두 객체가 있으며, ElapsedTimeAspect는 프록시 없이 인스턴스 하나만 있다.

    4번. name()의 호출자는 null을 받는다. 어드바이스의 반환 타입이 void이면 proceed()의 결과가 버려지고 항상 null이 호출자에게 반환된다고 레퍼런스가 설명한다. 대상 메서드 자체는 실행된다. ok()의 호출자는 AopInvocationException을 받는다. 반환 타입이 기본형 boolean이어서 프록시가 어드바이스의 반환값을 기본형으로 풀어야 하는데, null은 풀 수 없기 때문이다. 참조 타입은 null을 담을 수 있어 조용히 잘못된 값이 전달되고, 기본형은 담을 수 없어 예외로 드러난다. 조용히 틀리는 앞의 경우가 더 찾기 어렵다. 어드바이스는 반환 타입을 Object로 선언하고 proceed()의 결과를 반환해야 한다.

    5번. 설정 클래스도 포인트컷 범위 안의 빈이므로 프록시가 된다. 컨테이너가 애스펙트 빈을 만들려고 설정 클래스의 팩터리 메서드를 호출하면, 그 메서드 실행이 포인트컷과 매칭되어 어드바이스를 실행해야 한다. 어드바이스를 실행하려면 애스펙트 빈이 필요하므로 컨테이너에 그 빈을 요청하는데, 그 빈은 지금 생성 중이므로 BeanCurrentlyInCreationException이 발생한다. 해결책 하나는 포인트컷에 && !target(설정 클래스)를 더해 설정 클래스를 제외하거나 포인트컷 범위를 서비스 계층 등으로 좁히는 것이다. 다른 하나는 애스펙트를 @Component로 등록하는 것이다. 이 경우 애스펙트는 생성자로 만들어지고 생성자 실행은 스프링 AOP의 조인 포인트가 아니므로 순환이 생기지 않는다.

     스프링 빈 OrderService의 place()가 같은 클래스의 inStock()을 호출할 때, inStock()에 걸린 어드바이스가 실행되지 않는 이유로 가장 정확한 것은? 포인트컷은 한 번의 요청에서 메서드 하나에만 매칭되도록 설계되어 있기 때문이다. place() 본문이 실행되는 객체는 프록시가 아닌 대상 객체이고, this를 통한 호출은 프록시를 지나지 않기 때문이다. CGLIB이 생성한 서브클래스는 대상 클래스의 메서드 가운데 하나만 재정의하기 때문이다. 어드바이스는 스레드마다 한 번만 실행되도록 스레드 로컬로 제한되기 때문이다. 프록시는 호출을 따로 존재하는 대상 객체에게 넘긴다. 대상 객체 안에서 inStock(item)은 this.inStock(item)이고 this는 대상 객체이므로, 호출이 프록시의 재정의된 메서드로 가지 않는다. 포인트컷은 호출마다 독립적으로 평가되며(0번), CGLIB은 재정의 가능한 메서드를 모두 재정의한다(2번). 어드바이스 실행 횟수를 스레드 단위로 제한하는 장치는 없다(3번). JDK 동적 프록시가 인터페이스 없이 구체 클래스만으로는 프록시를 만들 수 없는 근본 이유는? 리플렉션의 Method.invoke가 인터페이스에 선언된 메서드만 호출할 수 있기 때문이다. 구체 클래스는 프록시 클래스와 다른 클래스 로더에 정의되기 때문이다. 생성되는 프록시 클래스가 이미 java.lang.reflect.Proxy를 상속하고 있고, 자바의 클래스는 부모 클래스를 하나만 가질 수 있기 때문이다. 구체 클래스의 메서드는 기본적으로 final로 취급되어 재정의할 수 없기 때문이다. 프록시가 대상과 같은 타입으로 보이려면 대상의 타입을 구현하거나 상속해야 한다. JDK가 만드는 프록시 클래스는 Proxy를 상속하도록 정해져 있어 다른 클래스를 추가로 상속할 수 없으므로, 타입을 맞출 수단이 인터페이스뿐이다. Method.invoke는 클래스의 메서드도 호출할 수 있고(0번), 클래스 로더는 인자로 지정할 수 있으며(1번), 자바의 메서드는 final을 붙이지 않는 한 재정의할 수 있다(3번). 컨테이너에서 꺼낸 빈의 클래스 이름이 OrderService$$SpringCGLIB$$0이었다. 이 상황에 대한 설명으로 옳은 것은? 힙에는 대상 객체와 프록시 객체가 따로 있고, 프록시 객체가 상속받은 인스턴스 필드는 생성자가 실행되지 않아 기본값으로 남아 있다. 대상 객체는 만들어지지 않고, 프록시 객체가 OrderService의 생성자를 실행해 필드를 직접 보관한다. 프록시 객체를 만들 때 OrderService의 생성자가 한 번 더 실행되므로 생성자는 항상 두 번 호출된다. 프록시 클래스는 OrderService와 같은 인터페이스를 구현한 형제 클래스이므로 OrderService 타입 변수에 대입할 수 없다. 스프링은 대상 객체를 먼저 정상적으로 만든 뒤, 그것을 가리키는 CGLIB 프록시 인스턴스를 Objenesis로 생성자 실행 없이 만든다. 그래서 생성자는 한 번만 실행되고(2번이 틀린 이유), 프록시의 상속 필드는 초기화되지 않는다. 대상 객체는 사라지지 않으며 실제 로직은 대상에서 실행된다(1번). CGLIB 프록시는 대상 클래스의 서브클래스이므로 OrderService 타입으로 다룰 수 있다. 3번은 JDK 동적 프록시에 대한 설명이다. @Around 어드바이스 본문에서 ProceedingJoinPoint의 proceed()를 한 번도 호출하지 않고 문자열 "cached"를 반환했다. String을 반환하는 대상 메서드를 프록시로 호출하면 어떻게 되는가? proceed() 호출이 없으므로 컴파일 오류가 발생한다. 스프링이 어드바이스가 끝난 뒤 대상 메서드를 자동으로 실행하고 그 반환값을 호출자에게 준다. 컨테이너 시작 시점에 포인트컷 검증 오류로 애플리케이션이 뜨지 않는다. 대상 메서드는 실행되지 않고, 호출자는 "cached"를 받는다. around 어드바이스는 조인 포인트로 진행할지를 스스로 결정한다. 레퍼런스는 proceed()를 한 번, 여러 번, 또는 전혀 호출하지 않는 것이 모두 합법이라고 밝힌다. 호출하지 않으면 사슬이 거기서 멈추므로 대상 메서드는 실행되지 않고 어드바이스의 반환값이 그대로 호출자에게 간다. proceed() 호출 여부는 컴파일러나 컨테이너가 검사하지 않는다. 스프링 AOP의 위빙 방식에 대한 설명으로 옳은 것은? 컴파일 시점에 대상 클래스의 바이트코드에 어드바이스 코드를 삽입한다. 실행 중에 대상 객체를 감싸는 프록시 객체를 만들고, 빈 후처리기가 그 프록시를 빈으로 등록하게 한다. 클래스 로더가 대상 클래스를 읽을 때 메서드 본문을 수정해 다시 정의한다. JIT 컴파일러가 대상 메서드를 컴파일할 때 어드바이스를 인라인으로 삽입한다. 레퍼런스는 스프링 AOP가 실행 중에 위빙을 수행한다고 적으며, 그 실체는 JDK 동적 프록시 또는 CGLIB 프록시다. 대상 클래스의 바이트코드는 바뀌지 않는다. 0번과 2번은 AspectJ의 컴파일 시점 위빙과 로드 시점 위빙에 해당한다. JIT 컴파일러는 AOP 위빙에 관여하지 않는다.
    횡단 관심사(cross-cutting concern)
    여러 클래스에 걸쳐 같은 모양으로 반복되는 로직. 시간 측정, 로깅, 트랜잭션 관리가 대표적이다.
    프록시(proxy)
    대상 객체와 같은 타입으로 보이면서 호출을 대신 받아 부가 동작을 수행하고 대상에게 위임하는 객체.
    JDK 동적 프록시(JDK dynamic proxy)
    java.lang.reflect.Proxy가 실행 중에 만드는, 지정한 인터페이스들을 구현한 프록시 클래스와 그 인스턴스.
    InvocationHandler
    JDK 동적 프록시의 모든 메서드 호출을 넘겨받는 인터페이스. invoke(proxy, method, args) 하나로 호출을 처리한다.
    CGLIB
    실행 중에 클래스를 생성하는 바이트코드 라이브러리. 스프링은 대상 클래스의 서브클래스를 만들어 프록시로 쓰며, spring-core에 재포장돼 있다.
    애스펙트(aspect)
    횡단 관심사를 모듈로 묶은 것. 스프링에서는 @Aspect가 붙은 클래스로, 포인트컷과 어드바이스를 담는다.
    조인 포인트(join point)
    프로그램 실행 중 어드바이스가 끼어들 수 있는 지점. 스프링 AOP에서는 항상 메서드 실행이다.
    포인트컷(pointcut)
    어드바이스를 적용할 조인 포인트를 골라내는 술어. 스프링은 기본으로 AspectJ 포인트컷 표현식을 쓴다.
    어드바이스(advice)
    조인 포인트에서 실행되는 동작. before, after returning, after throwing, after, around 다섯 종류가 있다.
    빈 후처리기(BeanPostProcessor)
    컨테이너가 빈을 만들 때 초기화 전후에 콜백을 받는 확장 지점. 받은 빈 대신 프록시를 반환할 수 있어 자동 프록시 생성의 기반이 된다.
