    화면 두 개짜리 기능에도 층이 필요한 이유

    01회에서 프로젝트를 만들어 내장 톰캣 위에 띄웠고, 02회에서 요청 하나가 정적 파일, 템플릿 렌더링, 객체 직렬화라는 세 갈래로 응답되는 것을 보았다. 거기까지의 컨트롤러는 받은 값을 거의 그대로 돌려주었다. 실제 서비스는 받은 값을 검사하고, 어딘가에 저장하고, 나중에 다시 꺼내 보여 준다. 이 회차는 그 최소 형태인 회원 등록과 회원 목록 조회를 처음부터 끝까지 만든다.

    기능만 놓고 보면 클래스 하나로 끝낼 수 있다. 컨트롤러 안에 맵을 하나 두고, 등록 요청이 오면 맵에 넣고, 목록 요청이 오면 맵을 꺼내 화면에 뿌리면 된다. 동작은 한다. 곤란해지는 것은 그 다음이다. 저장소를 데이터베이스로 바꾸려면 HTTP를 다루는 코드를 함께 열어야 하고, "같은 이름은 등록할 수 없다"는 규칙이 맞게 구현됐는지 확인하려면 매번 서버를 띄우고 브라우저로 눌러 봐야 한다.

    그래서 이 회차의 코드는 일부러 네 조각으로 나뉜다. 하지만 지면의 대부분은 코드가 아니라 그 아래에서 일어나는 일에 쓴다. 클래스 사이의 의존이 바이트코드에 어떻게 남는지, JUnit이 테스트 메서드를 어떤 순서와 어떤 객체로 실행하는지, 톰캣의 요청 스레드 수백 개가 리포지토리 객체 하나에 동시에 닿으면 무엇이 깨지는지, 브라우저의 폼 제출이 어떤 바이트로 날아와 어떤 메서드 호출로 바뀌는지를 차례로 본다.

    이 회차에 실린 테스트 실행 결과, 바이트코드, HTTP 응답, 부하 실험 수치는 원고를 쓰면서 JDK 21.0.13에서 직접 돌려 얻은 것이다. 서버 실험은 Spring Boot 4.1.2(스프링 프레임워크 7.0, 내장 톰캣 11), 테스트는 JUnit Jupiter 6.0.3으로 실행했다. 본문이 근거로 삼는 규칙(핸들러 매핑의 순서 값, 바인딩 규칙, 리다이렉트 상태 코드, 스레드 풀 기본값, 테스트 인스턴스 수명 주기)은 이 강좌의 기준 버전인 스프링 프레임워크 6.2, 스프링 부트 3.5, JUnit 5의 문서와 소스에서 같은 내용을 따로 확인했다.

    비즈니스 요구사항 정리 — 요구사항에서 구조로

    만들 것을 먼저 글로 적는다. 요구사항이 짧을수록 한 줄 한 줄이 설계에 미치는 영향이 잘 보인다.

    • 데이터: 회원은 식별자(ID)와 이름을 가진다.
    • 기능: 회원을 등록한다. 등록된 회원 전체를 조회한다.
    • 규칙: 이미 등록된 이름으로는 다시 등록할 수 없다.
    • 제약: 데이터를 어디에 저장할지는 아직 정해지지 않았다. 관계형 데이터베이스가 될 수도 있고 다른 저장소가 될 수도 있다.

    마지막 줄이 구조를 결정한다. 저장소가 정해질 때까지 개발을 멈출 수는 없으므로, 지금은 메모리에 저장하는 구현으로 시작하되 나중에 다른 구현으로 갈아 끼울 수 있어야 한다. "갈아 끼운다"가 가능하려면 저장소를 쓰는 쪽 코드에 구체적인 저장 방식의 이름이 나오지 않아야 한다. 자바 기본편에서 배운 인터페이스와 다형성이 바로 이 목적의 도구다.

    나머지 줄도 각자 자리를 요구한다. "등록한다, 조회한다"는 사용자가 브라우저에서 하는 행동이므로 URL과 화면을 아는 코드가 필요하다. "같은 이름은 안 된다"는 URL과도 저장 방식과도 무관한 업무 규칙이므로 둘 중 어느 쪽에도 넣지 않는 편이 낫다. 이렇게 책임을 나누면 흔히 쓰이는 네 조각이 나온다.

    일상에서 가져온 비유홀, 주방, 창고

    식당에서 홀 직원은 손님의 말을 주문서로 옮기고 음식을 내어 간다. 주방은 주문서를 보고 "품절된 메뉴는 받지 않는다" 같은 규칙에 따라 조리한다. 창고 담당은 재료를 넣고 꺼낸다. 창고가 냉장고에서 냉동 창고로 바뀌어도 홀 직원의 일은 달라지지 않는다. 비유가 깨지는 지점은 사람 수다. 식당은 바쁘면 직원을 늘리지만, 스프링 애플리케이션에서는 컨트롤러·서비스·리포지토리 객체가 보통 하나씩이고, 늘어나는 것은 그 객체의 메서드를 동시에 실행하는 스레드다. 이 차이가 뒤에서 다룰 동시성 문제의 출발점이다.

    네 계층의 상자와 의존 화살표를 그려, 서비스에서 메모리 구현으로 가는 화살표가 없다는 점을 한눈에 보여 준다. 깔끔한 기술 구조도. 왼쪽에서 오른쪽이 아니라 위에서 아래로 쌓인 상자 세 개: 맨 위 "컨트롤러 (웹 계층)", 가운데 "서비스 (업무 규칙)", 아래 "리포지토리 인터페이스". 위 상자에서 아래 상자로 실선 화살표가 내려가고 화살표 옆에 "의존" 라벨. 리포지토리 인터페이스 상자의 오른쪽에 상자 두 개를 세로로 배치: "메모리 구현" (진한 색)과 "DB 구현 (나중에)" (점선 테두리, 흐린 색). 두 구현 상자에서 인터페이스 상자로 향하는 속이 빈 삼각형 머리의 점선 화살표, 라벨 "구현". 서비스 상자에서 구현 상자로 가는 화살표는 없어야 하며, 그 빈 공간에 작은 회색 글씨 "서로 모른다". 그림 맨 아래 가로로 긴 상자 "도메인 객체: 회원"이 있고 위의 세 상자에서 가는 얇은 화살표가 모인다. 맨 위 컨트롤러 상자 위에는 브라우저 아이콘과 "HTTP 요청" 라벨의 화살표. 흰 배경, 파란색과 회색 계열, 평면 벡터 스타일, 한국어 라벨은 따옴표 안 문구 그대로. 의존 화살표는 인터페이스에서 멈춘다. 서비스의 클래스 파일에는 구현 클래스의 이름이 남지 않는다.

    회원 도메인과 리포지토리 만들기

    가장 안쪽의 도메인 객체부터 만든다. 요구사항이 말한 데이터는 식별자와 이름 둘뿐이다.

    package com.example.members.domain;

public class Member {

    private Long id;             // 저장소가 부여한다. 저장 전에는 null
    private final String name;

    public Member(String name) {
        this.name = name;
    }

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getName() { return name; }
}

    id의 타입이 기본형 long이 아니라 래퍼 클래스 Long인 데에는 이유가 있다. 이름은 사용자가 입력하지만 식별자는 시스템이 정한다. 따라서 객체가 만들어진 직후부터 저장되기 전까지는 "아직 식별자가 없다"는 상태가 실제로 존재하고, long으로는 이 상태를 표현할 수 없다. long 필드의 기본값 0은 "없음"과 "0번"을 구분하지 못한다. 식별자를 누가 언제 부여하는지는 저장소마다 다르다. 메모리 구현에서는 리포지토리가 직접 번호를 세고, 05회에서 보게 될 DB 구현에서는 데이터베이스가 부여한 값을 받아 온다.

    다음은 저장소의 계약이다. 구현이 무엇이든 서비스가 요구할 연산만 적는다.

    package com.example.members.repository;

import com.example.members.domain.Member;
import java.util.List;
import java.util.Optional;

public interface MemberRepository {
    Member save(Member member);
    Optional findById(Long id);
    Optional findByName(String name);
    List findAll();
}

    찾는 메서드 둘의 반환 타입이 Member가 아니라 Optional다. 식별자나 이름으로 찾았을 때 해당하는 회원이 없는 것은 오류가 아니라 정상적인 결과다. 이 결과를 null로 돌려주면 호출하는 쪽이 검사를 잊는 순간 NullPointerException이 난다. Optional은 값이 있을 수도 없을 수도 있다는 사실을 반환 타입에 적어 컴파일러와 읽는 사람 모두에게 알린다. Java SE 21 API 문서는 Optional이 주로 "결과 없음"을 나타낼 필요가 분명하고 null을 쓰면 오류가 나기 쉬운 메서드의 반환 타입으로 쓰도록 만든 것이라고 적는다. 조회 메서드가 바로 그 자리다.

    이제 메모리에 저장하는 첫 구현을 만든다. 이 버전에는 일부러 남겨 둔 문제가 두 가지 있고, 이 회차의 뒷부분이 그 둘을 차례로 드러낸다.

    package com.example.members.repository;

import com.example.members.domain.Member;
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;
import java.util.Optional;

public class InMemoryMemberRepository implements MemberRepository {

    private static final Map store = new HashMap<>();
    private static long sequence = 0L;

    @Override
    public Member save(Member member) {
        member.setId(++sequence);
        store.put(member.getId(), member);
        return member;
    }

    @Override
    public Optional findById(Long id) {
        return Optional.ofNullable(store.get(id));
    }

    @Override
    public Optional findByName(String name) {
        for (Member member : store.values()) {
            if (member.getName().equals(name)) {
                return Optional.of(member);
            }
        }
        return Optional.empty();
    }

    @Override
    public List findAll() {
        return new ArrayList<>(store.values());
    }

    public void clear() {
        store.clear();
    }
}

    메서드를 하나씩 따라가 보자. save는 sequence를 1 올린 값을 회원의 식별자로 넣는다. setId의 매개변수가 Long이므로 컴파일러는 long 값을 Long.valueOf로 감싸는 코드를 끼워 넣는다(오토박싱). 그 다음 식별자를 키로, 회원 객체의 참조를 값으로 맵에 넣는다. 맵에 들어가는 것은 회원의 복사본이 아니라 참조다. 호출한 쪽이 들고 있는 객체와 맵이 가리키는 객체는 같은 객체다.

    findById와 findByName은 겉모습이 비슷하지만 비용이 다르다. findById는 자바 중급 2편에서 본 해시 테이블의 조회다. 키의 해시로 버킷 위치를 계산해 바로 찾아가므로 회원이 몇 명이든 평균적으로 일정한 시간에 끝난다. findByName은 이름으로 위치를 계산할 방법이 없으므로 모든 값을 처음부터 훑는다. 회원 수에 비례하는 시간이 든다. 데이터베이스에서 인덱스가 걸린 컬럼으로 찾는 것과 인덱스 없는 컬럼으로 찾는 것의 차이가 정확히 이것이고, 그 이야기는 데이터베이스를 다루는 권에서 실행 계획과 함께 다시 나온다.

    findById의 Optional.ofNullable은 맵이 null을 돌려줄 수 있기 때문에 쓴다. Map.get은 키가 없으면 null을 반환하고, Optional.of(null)은 NullPointerException을 던진다. findAll이 store.values()를 그대로 돌려주지 않고 새 ArrayList에 담는 것도 이유가 있다. values()가 돌려주는 컬렉션은 맵과 이어진 뷰(view)여서, 그대로 내보내면 호출한 쪽이 그 컬렉션에서 요소를 지울 때 저장소의 데이터가 함께 지워진다.

    회원 둘을 저장한 뒤의 메모리는 다음과 같다. 두 필드가 static이라는 점이 그림의 핵심이다. 자바 언어 명세(JLS §8.3.1.1)는 정적 필드가 그 클래스의 인스턴스가 몇 개 만들어지든(0개여도) 정확히 하나만 존재한다고 정한다.

    InMemoryMemberRepository 클래스 (정적 필드는 클래스에 하나씩)
  sequence = 2
  store ──────────▶ HashMap
                      ├─ 키 1 ──▶ Member { id = 1, name = "spring1" }
                      └─ 키 2 ──▶ Member { id = 2, name = "spring2" }

new InMemoryMemberRepository()   ← 인스턴스 필드가 없다.
new InMemoryMemberRepository()   ← 몇 개를 만들어도 위의 맵은 하나다.

    static을 붙인 의도는 "이 프로세스에 회원 저장소는 하나"라는 것이다. 리포지토리 객체를 여러 군데에서 new로 만들어도 같은 데이터를 보게 하려는 선택이고, 지금은 그럴듯해 보인다. 이 선택의 대가는 바로 다음 절에서 드러난다.

    회원 리포지토리 테스트 케이스 작성

    방금 만든 리포지토리가 맞게 동작하는지 어떻게 확인할까. main 메서드를 만들어 저장하고 찾아서 출력해 볼 수 있고, 컨트롤러까지 만든 뒤 브라우저로 눌러 볼 수도 있다. 두 방법 모두 준비가 길고, 결과를 사람이 눈으로 판정해야 하고, 코드를 고칠 때마다 처음부터 반복해야 한다. 테스트 코드는 "코드를 실행하고 결과를 판정하는 일"을 코드로 적어 둔 것이다. 한 번 적어 두면 몇 번이든 한꺼번에 돌릴 수 있고, 판정은 기계가 한다.

    스프링 부트 프로젝트에 기본으로 들어 있는 spring-boot-starter-test는 JUnit 5와 AssertJ를 포함한다. JUnit은 테스트를 찾아 실행하고 성공과 실패를 집계하는 틀이고, AssertJ는 "이 값이 저 값과 같아야 한다"를 읽기 좋게 적는 단정(assertion) 라이브러리다. 테스트 클래스는 src/test/java 아래, 테스트 대상과 같은 패키지에 둔다.

    package com.example.members.repository;

import static org.assertj.core.api.Assertions.assertThat;

import com.example.members.domain.Member;
import java.util.List;
import org.junit.jupiter.api.Test;

class InMemoryMemberRepositoryTest {

    InMemoryMemberRepository repository = new InMemoryMemberRepository();

    @Test
    void save() {
        Member member = new Member("spring");

        repository.save(member);

        Member found = repository.findById(member.getId()).get();
        assertThat(found).isSameAs(member);
    }

    @Test
    void findByName() {
        Member first = new Member("spring1");
        Member second = new Member("spring2");
        repository.save(first);
        repository.save(second);

        Member found = repository.findByName("spring1").get();

        assertThat(found).isSameAs(first);
    }

    @Test
    void findAll() {
        repository.save(new Member("spring1"));
        repository.save(new Member("spring2"));

        List result = repository.findAll();

        assertThat(result).hasSize(2);
    }
}

    assertThat(found).isSameAs(member)는 두 참조가 같은 객체를 가리키는지(==) 검사한다. 조건이 맞으면 아무 일도 일어나지 않고, 틀리면 AssertionError를 던진다. Optional.get()은 값이 없으면 NoSuchElementException을 던지므로 운영 코드에서는 조심해서 써야 하지만, 테스트에서는 값이 없을 때 예외로 실패하는 것이 원하는 동작이므로 그대로 써도 된다.

    main이 없는데 누가 실행하는가

    테스트 클래스에는 main이 없고 public도 붙어 있지 않다. 실행의 주인은 JUnit이다. IDE나 빌드 도구가 JUnit을 띄우면, JUnit은 클래스를 살펴 @Test가 붙은 메서드를 리플렉션으로 찾아내고 하나씩 호출한다. 이때 지켜지는 규칙 하나가 이 절 전체의 열쇠다. JUnit 5 사용자 가이드는 테스트 메서드를 실행하기 전에 매번 테스트 클래스의 새 인스턴스를 만든다고 밝히고, 이 메서드 단위(per-method) 수명 주기가 기본 동작이라고 적는다.

    메서드마다 새 인스턴스를 만드는 이유는 격리다. 한 테스트가 테스트 클래스의 필드에 남긴 값이 다음 테스트에 보이지 않게 하려는 것이다. 실행 순서에 대해서도 가이드는 분명히 말한다. 기본 순서는 결정적이지만 의도적으로 뻔하지 않게 만든 알고리즘으로 정해진다. 소스에 적은 순서대로 실행된다는 보장이 없으니, 테스트끼리 순서에 기대지 말라는 뜻이다.

    하나씩 돌리면 통과하고, 함께 돌리면 실패한다

    세 테스트를 하나씩 실행하면 모두 통과한다. 클래스 전체를 한 번에 실행하면 결과가 달라진다. 이 원고를 쓰며 돌린 실행에서는 findAll, findByName, save 순서로 실행되었고 두 번째가 실패했다.

    findAll() -> SUCCESSFUL
findByName() -> FAILED
save() -> SUCCESSFUL

java.lang.AssertionError:
Expecting actual:
  com.example.members.domain.Member@52e7a6b2
and:
  com.example.members.domain.Member@29a5f4e7
to refer to the same object
    at ...InMemoryMemberRepositoryTest.findByName(InMemoryMemberRepositoryTest.java:32)

    "spring1"이라는 이름으로 찾았더니 방금 저장한 객체가 아닌 다른 객체가 나왔다는 메시지다. 각 테스트가 시작하고 끝날 때 저장소의 상태를 적어 보면 원인이 보인다.

    순서테스트시작할 때 store이 테스트가 저장한 것끝난 뒤 sequence
    1findAll비어 있음1번 spring1, 2번 spring22
    2findByName1번, 2번이 남아 있음3번 spring1, 4번 spring24
    3save1~4번이 남아 있음5번 spring5

    두 번째 테스트의 first는 3번 회원이다. 그런데 저장소에는 첫 번째 테스트가 남긴 1번 회원도 이름이 "spring1"이다. findByName은 맵의 값을 훑다가 처음 만난 "spring1"을 돌려주는데, OpenJDK의 HashMap은 버킷 순서로 순회하고 1, 2, 3, 4처럼 작은 Long 키는 값이 곧 버킷 번호가 되므로 1번이 먼저 나온다. 1번과 3번은 이름만 같은 서로 다른 객체이니 isSameAs가 실패한다. 순서가 달랐다면 findAll이 "2건이어야 하는데 4건"이라며 실패했을 것이다. 어느 쪽이 실패할지가 실행 순서에 달려 있다는 사실 자체가 문제다.

    이상한 점이 하나 있다. JUnit은 테스트마다 새 인스턴스를 만든다고 했고, 필드 초기화 식도 매번 다시 실행되어 리포지토리 객체도 새로 만들어졌다. 그런데 왜 데이터가 남아 있는가. 새로 만들어진 것은 리포지토리 객체이고, 데이터는 객체가 아니라 클래스에 붙은 정적 필드에 들어 있기 때문이다.

    테스트 인스턴스 #1 ── repository 객체 #1 ─┐
테스트 인스턴스 #2 ── repository 객체 #2 ─┼──▶ static store (하나) : 1번, 2번, 3번, 4번, 5번 …
테스트 인스턴스 #3 ── repository 객체 #3 ─┘     static sequence (하나) : 5

JUnit이 새로 만들어 주는 것: 왼쪽 두 열
JUnit이 손대지 않는 것: 오른쪽 (JVM이 끝날 때까지 유지)

    JUnit의 격리는 테스트 인스턴스의 필드까지만 닿는다. 정적 필드, 파일, 데이터베이스처럼 테스트 인스턴스 바깥에 있는 상태는 테스트를 작성하는 사람이 직접 원래대로 돌려놓아야 한다. 그 일을 하는 자리가 @AfterEach다.

    import org.junit.jupiter.api.AfterEach;

class InMemoryMemberRepositoryTest {

    InMemoryMemberRepository repository = new InMemoryMemberRepository();

    @AfterEach
    void tearDown() {
        repository.clear();
    }

    // 테스트 메서드는 그대로 ...
}

    @AfterEach가 붙은 메서드는 각 테스트 메서드가 끝날 때마다, 성공이든 실패든 호출된다. 이제 모든 테스트가 빈 저장소에서 시작하므로 어떤 순서로 실행해도 세 테스트가 통과한다. 여기서 원칙 하나를 얻는다. 테스트는 다른 테스트가 실행되었는지, 어떤 순서로 실행되었는지와 무관하게 같은 결과를 내야 한다. 그렇지 않은 테스트는 실패했을 때 코드가 틀렸는지 순서가 달라졌는지부터 의심하게 만들어 신뢰를 잃는다.

    sequence는 지우지 않았으므로 식별자는 테스트를 넘어 계속 증가한다. 위 테스트가 식별자의 구체적인 값(1번인지 3번인지)을 단정하지 않고 member.getId()로 받아 쓰는 이유다. 테스트가 "몇 번이 부여된다"가 아니라 "부여된 번호로 다시 찾을 수 있다"를 검증하면 이런 세부에 흔들리지 않는다.

    단정문에 isEqualTo가 아니라 isSameAs를 쓴 것도 짚어 둔다. Member는 equals를 재정의하지 않았으므로 isEqualTo를 써도 결국 Object.equals, 곧 참조 비교가 된다. 메모리 리포지토리는 저장한 객체의 참조를 그대로 돌려주기 때문에 이 테스트가 통과한다. 저장소가 데이터베이스로 바뀌면 조회 결과는 행(row)을 읽어 새로 만든 객체이므로 같은 테스트가 실패할 수 있다. 메모리 구현으로 통과한 테스트가 실제 저장소에서의 동작까지 보증하지는 않는다는 점을 기억해 두자.

    테스트 인스턴스와 리포지토리 객체는 테스트마다 새로 생기지만 static 맵은 하나뿐이어서 데이터가 쌓인다는 것을 보여 준다. 가로로 긴 기술 다이어그램. 왼쪽에 세로로 세 줄이 있고 각 줄은 작은 상자 두 개가 화살표로 이어진다: 첫 줄 "테스트 인스턴스 1" → "리포지토리 객체 1", 둘째 줄 "테스트 인스턴스 2" → "리포지토리 객체 2", 셋째 줄 "테스트 인스턴스 3" → "리포지토리 객체 3". 세 줄의 왼쪽에는 위에서 아래로 향하는 시간 화살표와 라벨 "테스트 실행 순서". 세 리포지토리 객체 상자에서 나온 화살표 세 개가 오른쪽의 큰 원통 모양 저장소 하나로 모인다. 원통의 라벨은 "static 저장소 (클래스에 하나)". 원통 안에는 작은 카드가 다섯 장 쌓여 있고 위의 두 장은 연한 색으로 "테스트 1이 남긴 데이터", 가운데 두 장은 "테스트 2가 남긴 데이터", 맨 아래 한 장은 "테스트 3". 왼쪽 세 줄을 감싸는 점선 테두리에 라벨 "JUnit이 매번 새로 만든다", 오른쪽 원통 아래에 라벨 "JUnit이 지워 주지 않는다". 흰 배경, 파란색과 주황색 강조, 평면 벡터 스타일, 한국어 라벨은 따옴표 안 문구 그대로. 테스트 격리는 테스트 인스턴스의 필드까지만 자동이다. 그 바깥의 상태는 직접 정리해야 한다.

    회원 서비스 개발

    서비스는 요구사항의 "규칙" 줄이 사는 곳이다. 첫 초안은 다음과 같다.

    package com.example.members.service;

import com.example.members.domain.Member;
import com.example.members.repository.InMemoryMemberRepository;
import com.example.members.repository.MemberRepository;
import java.util.List;
import java.util.Optional;

public class MemberService {

    private final MemberRepository memberRepository = new InMemoryMemberRepository();   // 초안. 다음 절에서 고친다

    public Long register(Member member) {
        rejectDuplicateName(member.getName());
        memberRepository.save(member);
        return member.getId();
    }

    private void rejectDuplicateName(String name) {
        if (memberRepository.findByName(name).isPresent()) {
            throw new IllegalStateException("이미 등록된 이름입니다: " + name);
        }
    }

    public List listMembers() {
        return memberRepository.findAll();
    }

    public Optional findMember(Long id) {
        return memberRepository.findById(id);
    }
}

    register는 두 단계다. 같은 이름의 회원이 이미 있는지 리포지토리에 묻고, 없으면 저장한다. 있으면 저장하지 않고 예외를 던진다. findByName이 Optional을 돌려주므로 null 검사 대신 isPresent()로 "값이 있는가"를 묻는다. 규칙 검사를 rejectDuplicateName이라는 메서드로 뽑아 둔 덕분에 register의 본문은 요구사항 문장을 그대로 옮긴 것처럼 읽힌다.

    예외로 IllegalStateException을 고른 것은 이 상황이 "지금 상태에서는 이 호출을 받아들일 수 없다"에 해당하기 때문이다. 자바 중급 1편에서 본 대로 이것은 언체크 예외여서 메서드 시그니처에 throws를 적을 필요가 없고, 호출한 쪽이 잡지 않으면 호출 스택을 따라 위로 전파된다. 이 예외가 웹 계층까지 올라가면 무슨 일이 생기는지는 등록 화면을 만들 때 확인한다.

    메서드 이름에도 계층의 성격이 드러난다. 리포지토리의 메서드는 save, findByName처럼 데이터를 넣고 꺼내는 말로 되어 있고, 서비스의 메서드는 register, listMembers처럼 업무를 설명하는 말로 되어 있다. 서비스는 요구사항 문서와 나란히 놓고 읽는 코드다. 기획자가 "회원 등록 규칙이 바뀌었다"고 말하면 register를 열면 된다.

    규칙이 왜 컨트롤러나 리포지토리가 아니라 서비스에 있어야 하는지도 따져 보자. 컨트롤러에 두면 나중에 같은 기능을 JSON API로도 제공할 때 규칙을 한 번 더 적어야 한다. 리포지토리에 두면 저장소 구현을 바꿀 때마다 규칙을 새 구현에 옮겨 적어야 하고, 옮기다 빠뜨릴 수 있다. 서비스에 두면 HTTP가 바뀌어도 저장소가 바뀌어도 규칙은 한 군데에 그대로 있다.

    회원 서비스 테스트

    서비스 테스트는 "어떤 상황에서, 무엇을 했더니, 어떻게 되어야 한다"의 세 토막으로 적으면 읽기 쉽다. 흔히 given, when, then이라고 부른다. 테스트가 길어져도 준비와 실행과 검증이 어디서 갈리는지 바로 보인다.

    @Test
void register() {
    // given
    Member member = new Member("spring");

    // when
    Long id = service.register(member);

    // then
    Member found = service.findMember(id).get();
    assertThat(found.getName()).isEqualTo("spring");
}

    정상 흐름만큼 중요한 것이 규칙이 실제로 막아 주는지다. 같은 이름으로 두 번 등록하면 두 번째에서 예외가 나야 한다.

    @Test
void registerRejectsDuplicateName() {
    // given
    service.register(new Member("spring"));

    // when
    IllegalStateException e = assertThrows(IllegalStateException.class,
            () -> service.register(new Member("spring")));

    // then
    assertThat(e.getMessage()).isEqualTo("이미 등록된 이름입니다: spring");
    assertThat(service.listMembers()).hasSize(1);
}

    assertThrows의 두 번째 인자 () -> service.register(...)는 람다(lambda)다. 람다는 자바 고급 3편에서 자세히 다루고, 지금은 "나중에 실행할 코드 조각을 객체로 만들어 넘기는 문법"이라고만 이해하면 된다. 이렇게 넘겨야 하는 이유가 있다. 테스트 메서드에서 service.register(...)를 그냥 호출하면 예외는 그 줄에서 곧바로 테스트 메서드 밖으로 빠져나가고, 예외가 맞게 났는지 검사할 기회 없이 테스트가 실패로 끝난다. 예외를 검사하려면 누군가 그 호출을 try로 감싸 주어야 한다. 그래서 호출의 결과가 아니라 호출하는 코드 자체를 넘긴다. 코드 조각을 넘기면 assertThrows가 자기 안의 try 블록에서 그 조각을 실행하고, 기대한 타입의 예외가 나오는지 확인한 뒤, 잡은 예외 객체를 반환한다. 풀어 쓰면 다음과 같은 일이다.

    try {
    service.register(new Member("spring"));
    fail("예외가 발생해야 한다");            // 여기까지 왔다면 예외가 안 난 것이므로 실패
} catch (IllegalStateException e) {
    assertThat(e.getMessage()).isEqualTo("이미 등록된 이름입니다: spring");
}

    검증의 마지막 줄 hasSize(1)도 의미가 있다. 예외가 났다는 것만으로는 부족하고, 두 번째 회원이 저장되지 않았다는 것까지 확인해야 규칙이 지켜진 것이다. 예외를 던지기 전에 저장부터 해 버리는 버그는 예외만 검사하는 테스트를 그대로 통과한다.

    테스트가 드러낸 설계 문제

    그런데 이 테스트의 service는 어떻게 준비하고, 테스트 사이에 저장소는 어떻게 비울까. 서비스 초안은 리포지토리를 자기 안에서 new로 만들고 private 필드에 숨겼다. 테스트가 그 리포지토리에 닿을 길이 없다. 떠올릴 수 있는 방법은 테스트에서도 new InMemoryMemberRepository()를 하나 더 만들어 clear()를 호출하는 것이다.

    MemberServiceTest ──▶ repository 객체 A ──┐
                                          ├──▶ static store (하나)
MemberService    ──▶ repository 객체 B ──┘

테스트가 비우는 것은 A, 서비스가 쓰는 것은 B.
둘이 같은 데이터를 보는 이유는 오직 store가 static이기 때문이다.

    동작은 한다. 하지만 테스트와 서비스가 서로 다른 객체를 쓰면서 정적 필드라는 뒷문으로만 이어져 있다. 누군가 static을 지우는 순간 테스트는 엉뚱한 맵을 비우게 되고, 테스트들은 다시 서로의 데이터를 밟는다. 그 변화는 컴파일 오류로 드러나지도 않는다. 근본 원인은 서비스가 자기가 쓸 리포지토리를 스스로 골라 만든다는 데 있다. 앞에서 그린 의존 그림과도 어긋난다. new InMemoryMemberRepository()라는 한 줄 때문에 서비스의 클래스 파일에 구현 클래스의 이름이 들어가 버렸다.

    해법은 서비스가 리포지토리를 만들지 않고 밖에서 받는 것이다.

    public class MemberService {

    private final MemberRepository memberRepository;

    public MemberService(MemberRepository memberRepository) {
        this.memberRepository = memberRepository;
    }

    // register, listMembers, findMember는 그대로 ...
}

    이제 서비스는 MemberRepository라는 인터페이스만 안다. 어떤 구현이 들어올지는 서비스를 만드는 쪽이 정한다. 이렇게 객체가 필요로 하는 다른 객체를 밖에서 넣어 주는 것을 의존관계 주입(dependency injection, DI)이라고 한다. 테스트는 다음처럼 바뀐다.

    package com.example.members.service;

import static org.assertj.core.api.Assertions.assertThat;
import static org.junit.jupiter.api.Assertions.assertThrows;

import com.example.members.domain.Member;
import com.example.members.repository.InMemoryMemberRepository;
import org.junit.jupiter.api.BeforeEach;
import org.junit.jupiter.api.Test;

class MemberServiceTest {

    InMemoryMemberRepository repository;
    MemberService service;

    @BeforeEach
    void setUp() {
        repository = new InMemoryMemberRepository();
        service = new MemberService(repository);
    }

    // register, registerRejectsDuplicateName은 위와 같다 ...
}

    @BeforeEach는 각 테스트 메서드 직전에 호출된다. 테스트마다 리포지토리를 새로 만들고 그것을 서비스에 넣어 주므로, 테스트와 서비스가 같은 리포지토리 객체를 쓴다는 사실이 코드에 그대로 적혀 있다. 그리고 여기서 한 걸음 더 갈 수 있다. "저장소는 하나"라는 것을 이제 객체를 하나만 만들어 필요한 곳에 넘기는 것으로 보장할 수 있으므로 static이 필요 없다. 리포지토리의 두 필드에서 static을 떼면 리포지토리 객체마다 자기 맵을 갖게 되고, 테스트마다 새 객체를 만드는 것만으로 빈 저장소에서 시작한다. clear()도 @AfterEach도 필요 없어진다. 리포지토리 테스트는 처음 적었던 모습 그대로, 필드 초기화 식만으로 격리된다.

    정리하면 상태가 어디에 사는지가 격리의 범위를 정한다. 지역 변수는 메서드 호출 하나, 인스턴스 필드는 객체 하나, 정적 필드는 JVM 전체가 범위다. 범위가 넓은 상태일수록 그것을 건드리는 코드끼리 보이지 않게 얽힌다. 운영 환경에서는 누가 리포지토리를 하나 만들어 서비스에 넣어 주는가 하는 질문이 남는데, 그 일을 하는 것이 스프링 컨테이너이고 04회의 주제다.

    한 층 아래 — 요청마다 스레드, 객체는 하나

    테스트는 한 스레드에서 차례로 실행되었다. 서버는 그렇지 않다. 01회에서 본 내장 톰캣은 요청을 처리하는 워커 스레드를 풀(pool)에 여러 개 두고, 요청이 들어올 때마다 그중 하나에 일을 맡긴다. 스프링 부트 3.5에서 이 풀의 최대 크기인 server.tomcat.threads.max의 기본값은 200이다. 스레드의 이름은 http-nio-8080-exec-1처럼 붙는다. 실험 서버의 컨트롤러에서 현재 스레드 이름을 출력해 보니 연달아 보낸 세 요청이 각각 exec-4, exec-6, exec-10에서 처리되었다.

    반면 컨트롤러, 서비스, 리포지토리 객체는 하나씩이다. 스프링 컨테이너는 기본적으로 이런 객체를 하나만 만들어 계속 재사용한다(이유와 방법은 04회). 따라서 스레드 200개가 동시에 요청을 처리하면 200개의 스레드가 같은 리포지토리 객체의 save를 동시에 실행할 수 있다.

     스레드 exec-4 의 스택           스레드 exec-6 의 스택            힙 (모든 스레드가 공유)
 ┌──────────────────────┐      ┌──────────────────────┐
 │ save(member)         │      │ save(member)         │       리포지토리 객체 (하나)
 │   member ─────────┐  │      │   member ─────────┐  │         ├─ sequence
 ├──────────────────────┤      ├──────────────────────┤         └─ store ──▶ HashMap
 │ register(member)     │      │ register(member)     │                        ├─ 1 ──▶ Member
 ├──────────────────────┤      ├──────────────────────┤                        ├─ 2 ──▶ Member

        │                              │
        └── 각자의 Member 객체 ─────────┴──▶ (힙에 있지만 아직 한 스레드만 안다)

    자바 기본편에서 본 대로 지역 변수와 매개변수는 스레드마다 따로 있는 스택에 놓인다. 한 스레드의 member 변수를 다른 스레드가 볼 방법은 없다. 문제는 힙에 있고 여러 스레드가 함께 닿을 수 있는 것, 곧 리포지토리 객체의 필드다. sequence와 store가 여기에 해당한다. static이든 인스턴스 필드든 객체가 하나뿐이면 사정은 같다.

    ++sequence는 한 동작이 아니다

    소스에서는 ++sequence가 연산자 하나지만, 컴파일된 save의 앞부분을 javap -c로 보면 여러 명령으로 나뉘어 있다.

     0: aload_1
 1: getstatic     #7     // Field sequence:J        현재 값을 읽어 스택에 올린다
 4: lconst_1                                        상수 1을 올린다
 5: ladd                                            더한다
 6: dup2                                            결과를 복사해 둔다(식의 값으로 쓰기 위해)
 7: putstatic     #7     // Field sequence:J        결과를 필드에 쓴다
10: invokestatic  #13    // Method java/lang/Long.valueOf:(J)Ljava/lang/Long;

    읽기(getstatic), 더하기(ladd), 쓰기(putstatic)가 따로다. 필드를 인스턴스 필드로 바꾸면 명령 이름만 getfield와 putfield로 바뀌고 구조는 같다. 운영체제는 이 명령들 사이 어디에서든 스레드를 멈추고 다른 스레드를 실행할 수 있고, 코어가 여러 개면 두 스레드가 말 그대로 동시에 실행된다. sequence가 41일 때 두 스레드가 다음 순서로 끼어들면 이렇게 된다.

    시각스레드 A스레드 Bsequence
    1읽는다 → 4141
    2읽는다 → 4141
    3더한다 → 42, 쓴다42
    4더한다 → 42, 쓴다42
    5store.put(42, 회원 A)42
    6store.put(42, 회원 B)42

    두 회원이 같은 식별자 42를 받았고, 맵은 키 하나에 값 하나만 가지므로 회원 A는 회원 B에 덮여 사라진다. 두 사용자 모두 등록에 성공했다는 응답을 받았는데 목록에는 한 명만 있다. 예외도 로그도 없다. 이런 현상을 갱신 손실(lost update)이라고 한다.

    HashMap 쪽도 안전하지 않다. Java SE 21 API 문서는 HashMap이 동기화되어 있지 않으며, 여러 스레드가 동시에 접근하고 그중 하나라도 맵의 구조를 바꾼다면 반드시 외부에서 동기화해야 한다고 굵은 글씨로 적어 두었다. 자바 중급 2편에서 본 대로 put은 버킷의 체인에 노드를 달고 size를 올리고 필요하면 배열을 키워 노드를 옮긴다. 이 여러 단계가 두 스레드에서 겹치면 한쪽이 단 노드를 다른 쪽이 덮어쓰거나, 노드 수와 size가 어긋난다.

    실제로 얼마나 깨지는가

    말로만 하지 않고 돌려 보았다. 먼저 순수 자바 실험이다. HashMap과 long으로 만든 리포지토리 객체 하나에 스레드 8개가 각각 10,000번씩, 모두 80,000번 save를 호출하게 하고 끝난 뒤 sequence와 store.size()를 출력했다. 수치는 실행할 때마다 다르다.

    실행기대값sequencestore.size()
    1회차80,00047,42045,572
    2회차80,00038,77834,561
    3회차80,00042,22646,606

    절반 가까운 증가가 사라졌다. 3회차에서는 size()가 부여된 식별자의 개수보다 크게 나왔는데, HashMap 안의 size 필드도 같은 방식으로 깨지기 때문이다. 다음은 실제 서버다. 같은 리포지토리를 쓰는 서버에 스레드 16개가 서로 다른 이름으로 500번씩, 모두 8,000건의 등록 요청을 보냈다. 한 번은 6,113건이 정상 응답을, 1,887건이 500 응답을 받았고, 다시 띄워 반복했을 때는 6,026건과 1,974건이었다. 500 응답의 원인은 findByName이 맵을 순회하는 도중 다른 스레드가 맵을 바꿔 발생한 ConcurrentModificationException이었다.

    더 나쁜 것은 그 뒤다. 부하가 끝난 뒤 목록 조회를 한 번 보냈더니 500이 돌아왔고, 몇 번을 다시 보내도 같았다. findAll이 돌려준 리스트에 null이 섞여 있어서 NullPointerException이 났다. new ArrayList<>(store.values())는 맵의 size만큼 배열을 잡고 실제 노드를 따라가며 채우는데, 깨진 맵은 size가 실제 노드 수보다 커서 뒤쪽 칸이 빈 채로 남은 것이다. 동시성 버그로 한 번 망가진 자료 구조는 요청이 끝나도 망가진 채로 남고, 서버를 다시 띄울 때까지 이후의 모든 요청에 영향을 준다.

    최종 리포지토리

    고치는 방법은 공유되는 두 필드를 여러 스레드가 함께 써도 되는 타입으로 바꾸는 것이다. 앞 절에서 정한 대로 static도 뗀다.

    package com.example.members.repository;

import com.example.members.domain.Member;
import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.Optional;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

public class InMemoryMemberRepository implements MemberRepository {

    private final Map store = new ConcurrentHashMap<>();
    private final AtomicLong sequence = new AtomicLong();

    @Override
    public Member save(Member member) {
        member.setId(sequence.incrementAndGet());
        store.put(member.getId(), member);
        return member;
    }

    // findById, findByName, findAll은 앞과 같다 ...
}

    AtomicLong.incrementAndGet()은 API 문서의 표현대로 현재 값을 원자적으로(atomically) 증가시킨다. 읽기, 더하기, 쓰기 사이에 다른 스레드가 끼어들어 같은 값을 받아 가는 일이 없다는 뜻이다. ConcurrentHashMap은 여러 스레드의 동시 조회와 갱신을 견디도록 만든 해시 테이블이고, API 문서에 따르면 그 반복자는 순회 도중 다른 스레드가 맵을 바꿔도 ConcurrentModificationException을 던지지 않는다. 두 클래스가 락과 CAS(compare-and-swap)로 이것을 어떻게 해내는지는 자바 고급 1편의 주제다.

    바꾼 뒤 같은 부하를 다시 걸었다. 8,000건이 모두 정상 응답을 받았고, 목록에는 8,000명이 서로 다른 식별자 8,000개로 들어 있었다. 다만 여기서 얻은 것은 "save 한 번"과 "findByName 한 번"이 각각 안전하다는 것까지다. 서비스의 register는 그 둘을 이어서 호출한다. 각각 안전한 연산 두 개를 이어 붙인 것이 안전한지는 별개의 문제이고, 이 회차의 끝에서 다시 다룬다.

    스택은 스레드마다 따로, 힙의 리포지토리와 맵은 하나라는 구조와 두 스레드가 같은 번호를 받아 가는 충돌 지점을 보여 준다. 메모리 구조 다이어그램. 왼쪽에 세로로 긴 스택 기둥 세 개가 나란히 있고 각각 위에 라벨 "워커 스레드 1", "워커 스레드 2", "워커 스레드 3". 각 기둥 안에는 아래에서 위로 쌓인 프레임 세 칸: "컨트롤러 메서드", "서비스 register", "리포지토리 save". 세 기둥 전체를 묶는 괄호 아래 라벨 "스택: 스레드마다 따로". 오른쪽에는 둥근 모서리의 큰 영역, 라벨 "힙: 모든 스레드가 공유". 그 안에 상자 하나 "리포지토리 객체 (하나)"가 있고 상자 안에 두 칸 "번호 카운터"와 "회원 맵". "회원 맵" 칸에서 오른쪽으로 작은 회원 카드 세 장으로 가는 화살표. 세 스택의 맨 위 프레임에서 리포지토리 객체 상자로 화살표 세 개가 모이고, 그중 두 화살표가 "번호 카운터" 칸에서 부딪히는 지점에 빨간 번개 표시와 라벨 "같은 번호를 읽는다". 흰 배경, 스택은 파란색, 힙은 연한 회색, 충돌 표시는 빨간색, 평면 벡터 스타일, 한국어 라벨은 따옴표 안 문구 그대로. 지역 변수는 스레드마다 따로 있지만, 하나뿐인 리포지토리 객체의 필드는 모든 요청 스레드가 함께 읽고 쓴다.

    브라우저가 GET /를 보내면 톰캣의 워커 스레드가 요청을 읽어 스프링 MVC의 입구인 DispatcherServlet에 넘긴다. DispatcherServlet은 이 요청을 처리할 핸들러를 찾아 호출하고, 메서드가 돌려준 문자열 "home"을 뷰 이름으로 받는다. 그 뒤는 02회에서 본 흐름이다. 뷰 리졸버가 뷰 이름을 템플릿 파일로 바꾸는데, 스프링 부트 3.5의 Thymeleaf 자동 설정은 접두사 classpath:/templates/와 접미사 .html을 기본값으로 쓰므로 templates/home.html이 선택되어 렌더링된다.

    index.html과 컨트롤러가 둘 다 있으면

    정적 리소스 위치에 index.html을 두면 스프링 부트는 그것을 첫 화면(welcome page)으로 쓴다. 스프링 부트 레퍼런스는 먼저 정적 컨텐츠 위치에서 index.html을 찾고, 없으면 index 템플릿을 찾는다고 설명한다. 그렇다면 static/index.html도 있고 @GetMapping("/")도 있을 때 / 요청은 어디로 가는가. 답은 "컨트롤러"이고, 이유는 DispatcherServlet이 핸들러를 찾는 방식에 있다.

    DispatcherServlet은 요청을 처리할 대상을 직접 찾지 않고 핸들러 매핑(HandlerMapping)이라는 객체들에게 묻는다. 핸들러 매핑은 여러 개가 등록되어 있고 각자 순서 값(order)을 갖는다. DispatcherServlet의 소스를 보면 핸들러 매핑들을 순서 값으로 정렬해 두고, 요청이 오면 앞에서부터 차례로 물어 처음으로 핸들러를 내놓은 매핑의 답을 쓴다. 뒤에 있는 매핑은 물어보지도 않는다.

    순서 값핸들러 매핑맡는 요청

    2WelcomePageHandlerMapping (스프링 부트)/ 요청을 index.html 또는 index 템플릿으로
    Integer.MAX_VALUE - 1정적 리소스용 핸들러 매핑/static 등에 놓인 파일

    표의 값은 스프링 프레임워크 6.2의 WebMvcConfigurationSupport와 스프링 부트 3.5의 WelcomePageHandlerMapping 소스에 적힌 것이다(관련 없는 매핑은 생략했다). 순서 값이 작을수록 먼저 묻는다. 컨트롤러 매핑이 0이고 첫 화면 매핑이 2이므로 @GetMapping("/")가 있으면 그쪽이 먼저 답한다. 실험으로도 확인했다. 둘 다 둔 상태에서 /를 요청하면 컨트롤러의 응답이 왔고, 같은 상태에서 /index.html을 직접 요청하면 정적 파일이 그대로 왔다. 그 경로에 매핑된 컨트롤러 메서드가 없으니 맨 뒤의 정적 리소스 매핑까지 내려간 것이다. 컨트롤러를 빼고 다시 띄우면 / 요청에 index.html이 돌아왔다.

    "파일을 넣었는데 왜 안 나오지", "컨트롤러를 만들었는데 왜 다른 화면이 나오지" 같은 문제는 대부분 이 표에서 풀린다. 같은 URL을 처리할 수 있는 후보가 여럿이면 순서 값이 작은 매핑이 이긴다.

    등록은 요청 두 번으로 이루어진다. 입력할 폼을 달라는 요청과, 채운 폼을 제출하는 요청이다. 두 요청은 URL이 같고 HTTP 메서드만 다르다. 컨트롤러와, 폼의 입력값을 담을 객체는 다음과 같다. 목록 조회 메서드까지 한 번에 적어 두고, 조회는 다음 절에서 설명한다.

    package com.example.members.web;

회원 등록

    form 태그의 속성 둘과 input의 속성 하나가 다음 요청의 모양을 정한다. action은 제출할 URL, method는 HTTP 메서드, input의 name은 전송될 데이터의 키다. 화면에 보이는 "이름"이라는 글자나 id 속성은 서버로 가지 않는다. 서버에 도착하는 것은 name 속성의 값과 사용자가 입력한 값의 쌍뿐이다.

    브라우저가 만드는 요청 메시지

    사용자가 "spring"을 입력하고 버튼을 누르면 브라우저는 폼의 내용으로 HTTP 요청을 만든다. MDN의 설명대로 method가 post이면 폼 데이터는 요청 본문에 실리고, 본문의 형식을 정하는 enctype의 기본값은 application/x-www-form-urlencoded다. 그 결과는 다음과 같은 메시지다(다른 헤더는 생략).

    POST /members/new HTTP/1.1
Host: localhost:8080
Content-Type: application/x-www-form-urlencoded
Content-Length: 11

name=spring

    본문은 키=값을 &로 이어 붙인 한 줄의 텍스트다. name=spring은 11바이트이고 Content-Length가 그 길이를 알려 준다. URL 뒤에 붙는 쿼리 스트링 ?name=spring과 형식이 같고, 실리는 자리만 URL에서 본문으로 옮겨졌다. 이 형식에서 쓸 수 없는 문자는 퍼센트 인코딩으로 바뀐다. 이름에 "김"을 넣어 보내면 본문은 name=%EA%B9%80이 된다. "김"을 UTF-8로 쓰면 EA, B9, 80의 세 바이트이고, 바이트마다 %와 16진수 두 자리로 적은 것이다. 서버는 이를 거꾸로 풀어 다시 문자열로 만든다.

    폼을 보여 주는 요청과 제출하는 요청의 URL이 같은 것은 우연이 아니다. URL은 "새 회원 등록"이라는 대상을 가리키고, 그 대상에 무엇을 할지는 메서드가 말한다. HTTP 명세(RFC 9110)는 GET을 안전한(safe) 메서드, 곧 본질적으로 읽기 전용인 메서드로 정의한다. POST는 안전하지도 않고, 같은 요청을 여러 번 보내도 한 번 보낸 것과 효과가 같다는 멱등(idempotent) 성질도 보장되지 않는다. @GetMapping과 @PostMapping은 같은 URL의 요청을 메서드에 따라 다른 자바 메서드로 나누어 보내는 장치다. 이 구분은 조금 뒤 리다이렉트를 설명할 때 다시 쓰인다.

    요청 파라미터가 객체가 되는 과정

    register(MemberForm form)을 보면 이상한 점이 있다. 컨트롤러 어디에도 new MemberForm()이 없고 setName을 부르는 코드도 없는데, 메서드가 실행될 때 form.getName()은 "spring"을 돌려준다. 메서드를 호출하기 전에 스프링 MVC가 인자를 준비하기 때문이다.

    2번과 4번의 근거는 스프링 프레임워크 레퍼런스에 있다. 레퍼런스는 @ModelAttribute의 사용이 선택 사항이며, 단순 값 타입이 아니고 다른 방식으로 해석되지 않는 매개변수는 암묵적으로 @ModelAttribute로 취급된다고 적는다. 데이터 바인딩에 대해서는 사용자 입력을 생성자의 인자로 넣는 생성자 바인딩과, 입력의 키를 대상 객체의 프로퍼티에 맞춰 세터로 넣는 프로퍼티 바인딩의 두 방식을 설명한다. MemberForm은 기본 생성자만 있으므로 프로퍼티 바인딩으로 채워진다.

    세터가 연결 고리라는 것은 실험으로 쉽게 확인된다. MemberForm에서 setName만 지운 클래스를 매개변수로 받게 하고 같은 요청을 보내면, 오류는 나지 않고 getName()이 null을 돌려준다. 필드 이름이 name인 것은 아무 역할을 하지 못한다. 프레임워크는 private 필드가 아니라 setName이라는 메서드 이름에서 name이라는 프로퍼티를 읽어 낸다. 게터와 세터의 이름 규칙이 관례를 넘어 프레임워크와의 약속으로 쓰이는 대표적인 자리다.

    바인딩의 재료인 "요청 파라미터"가 무엇인지도 정확히 해 두자. 서블릿 API 문서는 HTTP 서블릿에서 파라미터가 쿼리 스트링 또는 전송된 폼 데이터에 담긴다고 설명한다. 서버 입장에서는 URL 뒤의 ?name=spring과 본문의 name=spring이 같은 창구로 들어온다. 실제로 본문을 비우고 POST /members/new?name=fromquery를 보내도 form.getName()은 "fromquery"였다.

    왜 도메인 객체가 아니라 폼 객체인가

    MemberForm은 name 하나뿐이라 Member를 그대로 받으면 클래스 하나를 줄일 수 있을 것처럼 보인다. 그렇게 바꿔 실험해 보았다. 핸들러의 매개변수를 Member로 바꾸고 본문에 name=spring&id=999를 실어 보냈더니, 컨트롤러가 받은 객체는 이름이 "spring"이고 식별자가 999였다. 이름은 생성자 바인딩으로, 식별자는 setId를 통한 프로퍼티 바인딩으로 들어간 것이다(생성자 매개변수의 이름이 클래스 파일에 남도록 javac -parameters로 컴파일한 경우다).

    화면의 폼에는 식별자를 입력하는 칸이 없다. 하지만 서버는 요청이 그 폼에서 왔는지 알지 못한다. HTTP 요청은 누구나 원하는 내용으로 만들어 보낼 수 있고, 바인딩은 들어온 파라미터 이름에 맞는 세터가 있으면 호출한다. 이 예제에서는 리포지토리가 식별자를 다시 덮어쓰므로 피해가 없지만, 수정 기능처럼 식별자를 믿고 동작하는 코드였다면 남의 데이터를 바꾸는 통로가 된다. 스프링 프레임워크 레퍼런스가 보안상의 이유로 웹 바인딩 전용으로 만든 객체를 쓰거나 생성자 바인딩만 적용하라고 권하는 까닭이다.

    폼 객체를 따로 두는 이유는 하나 더 있다. 화면이 받는 입력의 모양과 도메인 객체의 모양은 처음에만 비슷하고 곧 달라진다. 비밀번호 확인 칸처럼 화면에만 있는 값이 생기고, 가입 일시처럼 도메인에만 있는 값이 생긴다. 폼 객체는 "브라우저가 보낼 수 있는 값의 목록"이고 도메인 객체는 "업무가 다루는 데이터"다. 컨트롤러의 new Member(form.getName()) 한 줄이 둘 사이의 경계다.

    응답은 화면이 아니라 302다

    등록을 마친 register는 뷰 이름 대신 "redirect:/"를 돌려준다. 스프링 MVC 레퍼런스에 따르면 뷰 이름의 redirect: 접두사는 리다이렉트가 필요하다는 지시로 인식되고, 접두사 뒤의 나머지가 리다이렉트할 URL이 되며, 결과는 컨트롤러가 RedirectView를 반환한 것과 같다. RedirectView의 Javadoc은 기본 설정에서 HttpServletResponse.sendRedirect에 위임하며 상태 코드 302를 보낸다고 적는다. 그래서 POST에 대한 응답에는 HTML이 없다.

    HTTP/1.1 302
Location: http://localhost:8080/
Content-Length: 0

    302는 "찾는 것이 지금은 다른 URI에 있다"는 뜻이고, Location 헤더가 그 URI를 알려 준다. 브라우저는 이 응답을 화면에 그리지 않고 곧바로 Location으로 새 요청을 보낸다. Location 값이 /가 아니라 전체 URL로 나온 것은 스프링 부트의 server.tomcat.use-relative-redirects 기본값이 false이기 때문이다. 사용자가 버튼을 한 번 눌렀을 때 오간 메시지를 모두 그리면 다음과 같다.

    브라우저                                              서버
   │  ① GET /members/new                               │
   │ ────────────────────────────────────────────────▶ │  registrationForm()
   │ ◀──────────────────────────────────────────────── │  200 + 폼 HTML
   │                                                   │
   │  ② POST /members/new      본문: name=spring       │
   │ ────────────────────────────────────────────────▶ │  register(form) → 서비스 → 리포지토리
   │ ◀──────────────────────────────────────────────── │  302   Location: http://localhost:8080/
   │                                                   │
   │  ③ GET /          (브라우저가 스스로 보낸다)        │
   │ ────────────────────────────────────────────────▶ │  home()
   │ ◀──────────────────────────────────────────────── │  200 + 홈 HTML
   │
   └ 이 상태에서 새로 고침 = 마지막 요청 ③ 을 다시 보낸다

    굳이 한 번 더 왕복하는 이유는 브라우저의 새로 고침이 하는 일 때문이다. 새로 고침은 화면을 다시 그리는 기능이 아니라 마지막으로 보낸 요청을 다시 보내는 기능이다. 만약 register가 리다이렉트 없이 곧바로 화면을 그렸다면 브라우저의 마지막 요청은 ②의 POST다. 사용자가 새로 고침을 누르면 같은 본문의 POST가 다시 나가고 등록이 한 번 더 시도된다. 이 예제에서는 중복 이름 검사에 걸려 오류 화면이 뜨고, 그런 검사가 없는 주문이나 결제였다면 같은 주문이 두 번 들어간다. 앞에서 본 대로 POST는 안전하지도 멱등하지도 않은 메서드이기 때문에 생기는 일이다.

    POST를 처리한 뒤 리다이렉트로 응답하면 브라우저의 마지막 요청은 ③의 GET이 된다. 몇 번을 새로 고쳐도 홈 화면을 다시 읽을 뿐이다. 이 순서를 POST, Redirect, GET의 머리글자를 따 PRG 패턴이라고 부른다. RFC 9110은 303(See Other)을 설명하면서 이 코드가 주로 POST의 결과를 다른 리소스로 리다이렉트하는 데 쓰인다고 적고, 302에 대해서는 역사적인 이유로 사용자 에이전트가 다음 요청의 메서드를 POST에서 GET으로 바꿀 수 있다고 적는다. RedirectView의 Javadoc도 많은 HTTP 1.1 클라이언트가 302를 303과 똑같이 다룬다고 설명한다. 스프링의 기본 리다이렉트가 302인데도 브라우저가 ③을 GET으로 보내는 배경이다.

    폼 제출 뒤 서버가 화면 대신 302를 돌려주고 브라우저가 스스로 GET을 보내는 흐름, 그리고 새로 고침이 마지막 GET만 반복한다는 점을 보여 준다. 시퀀스 다이어그램. 왼쪽 세로 생명선 "브라우저", 오른쪽 세로 생명선 "서버". 위에서 아래로 화살표 여섯 개. 첫째: 브라우저에서 서버로 실선 화살표 "POST /members/new (name=spring)". 서버 생명선 옆에 작은 상자 "회원 저장". 둘째: 서버에서 브라우저로 점선 화살표 "302 + Location: /", 이 화살표는 주황색으로 강조. 셋째: 브라우저에서 서버로 실선 화살표 "GET /", 옆에 작은 글씨 "브라우저가 스스로 보낸다". 넷째: 서버에서 브라우저로 점선 화살표 "200 + 홈 화면". 그 아래 브라우저 생명선 옆에 둥근 화살표 아이콘과 라벨 "새로 고침", 여기서 서버로 가는 실선 화살표 "GET / 만 다시 간다" (초록색), 서버에서 돌아오는 점선 화살표. 다이어그램 오른쪽 아래 구석에 작은 회색 상자: "리다이렉트가 없다면 새로 고침이 POST를 다시 보낸다" 문구와 빨간 경고 아이콘. 흰 배경, 평면 벡터 스타일, 한국어 라벨은 따옴표 안 문구 그대로. PRG 패턴: 상태를 바꾸는 POST에는 화면이 아니라 리다이렉트로 응답해, 브라우저의 마지막 요청을 안전한 GET으로 만든다.

    @GetMapping("/members")

    검사와 저장 사이의 틈

    리포지토리를 ConcurrentHashMap과 AtomicLong으로 바꿔 식별자가 겹치거나 맵이 깨지는 문제는 없앴다. 그런데 "같은 이름은 등록할 수 없다"는 규칙은 지켜지고 있을까. register는 이름이 있는지 검사하고, 없으면 저장한다. 두 스레드가 같은 이름으로 거의 동시에 들어오면 다음 순서가 가능하다.

    시간 ──────────────────────────────────────────────────────────────▶

스레드 A:  findByName("kim") → 없음                 save(kim) → 7번
스레드 B:           findByName("kim") → 없음                    save(kim) → 8번

결과: 이름이 "kim"인 회원이 둘. 두 요청 모두 302(성공)를 받았다.

    두 스레드 모두 상대가 저장하기 전에 검사를 마쳤으므로 둘 다 "없음"을 본다. 각 호출은 스레드 안전하지만, 검사와 저장 사이에 다른 스레드가 끼어들 수 있는 틈이 있다. 이런 구조를 검사 후 행동(check-then-act)이라고 하고, 실행 순서에 따라 결과의 옳고 그름이 갈리는 상황을 경쟁 조건(race condition)이라고 한다.

    이것도 돌려 보았다. 최종 리포지토리를 쓰는 서버에 이름 하나당 16개의 요청을 동시에 보내는 일을 이름 200개에 대해 반복했다. 규칙이 지켜졌다면 이름마다 한 명씩만 저장되어야 한다. 한 번의 실행에서 200개 가운데 36개의 이름이 두 번 이상 저장되었고, 가장 많이 겹친 이름은 다섯 번 저장되었다. 수치는 실행마다 다르지만 0이 아니라는 점이 중요하다. 순차적으로 실행되는 테스트는 이 문제를 잡지 못한다. 앞에서 만든 중복 이름 테스트는 지금도 통과한다.

    틈을 없애려면 검사와 저장이 하나의 원자적인 단위가 되어야 한다. 방법은 크게 둘이다. 하나는 애플리케이션에서 락으로 register 전체를 한 번에 한 스레드만 실행하게 하는 것이다. 서버가 한 대일 때만 유효하고, 모든 등록이 줄을 서게 된다. 다른 하나는 저장소가 규칙을 직접 지키게 하는 것이다. 관계형 데이터베이스의 유일 제약(unique constraint)은 같은 값이 두 번 들어오면 두 번째 저장을 데이터베이스가 거부한다. 서버가 몇 대든, 어떤 경로로 데이터가 들어오든 성립한다.

    그래서 실무의 답은 보통 둘을 함께 쓰는 것이다. 서비스의 사전 검사는 대부분의 경우에 사용자에게 친절한 메시지를 빨리 돌려주기 위해 두고, 최종 보증은 저장소의 제약에 맡긴다. 메모리 리포지토리는 그런 제약을 제공하지 않으므로 이 예제의 규칙은 동시 요청 앞에서 완전하지 않다. 예제의 결함이라기보다, 저장소를 실제 데이터베이스로 바꿔야 하는 이유 가운데 하나다.

    흔한 오해 다섯 가지

    1. "JUnit이 테스트마다 새 인스턴스를 만드니 테스트는 저절로 격리된다." 격리되는 것은 테스트 클래스의 인스턴스 필드뿐이다. 정적 필드, 파일, 데이터베이스, 여러 테스트가 함께 쓰는 객체에 남은 상태는 그대로 다음 테스트로 넘어간다. 그런 상태를 쓰는 테스트는 직접 초기화하거나 정리해야 한다.
    2. "컨트롤러는 요청마다 새로 만들어진다." 요청마다 새로 만들어지는 것은 MemberForm 같은 인자와 Model이고, 컨트롤러·서비스·리포지토리 객체는 하나다. 그러므로 이 객체들의 필드에 요청별 데이터(방금 등록한 이름, 현재 사용자)를 담으면 다른 요청의 스레드가 그 값을 읽거나 덮어쓴다. 요청별 데이터는 지역 변수와 매개변수로만 흘려보낸다.
    3. "ConcurrentHashMap으로 바꿨으니 스레드 안전하다." 안전해진 것은 맵의 메서드 호출 하나하나다. 검사한 뒤 저장하는 것처럼 호출 여러 개가 모여야 의미가 있는 로직은 여전히 틈이 있다. 스레드 안전성은 자료 구조의 속성이기 전에 "무엇이 한 단위로 실행되어야 하는가"라는 로직의 속성이다.
    4. "폼에 없는 값은 서버에 들어올 수 없다." 화면의 폼은 요청을 편하게 만들어 주는 도구일 뿐이다. 서버가 받는 것은 HTTP 메시지이고, 누구든 원하는 파라미터를 넣어 보낼 수 있다. 바인딩 대상 객체에 세터가 열려 있으면 그 값은 들어온다.
    5. "등록이 끝났으면 그 자리에서 결과 화면을 보여 주면 된다." 그렇게 하면 브라우저의 마지막 요청이 POST로 남아 새로 고침이 등록을 반복한다. 상태를 바꾸는 요청에는 리다이렉트로 응답해 마지막 요청을 GET으로 만든다. 다만 리다이렉트는 새로 고침만 막아 줄 뿐, 버튼을 빠르게 두 번 누르는 것 같은 동시 중복 요청은 막지 못한다. 그것은 앞 절의 문제다.

    다른 곳에서 다시 만나는 것

    이 회차에서 손으로 한 일 대부분은 이 권의 남은 회차에서 스프링이 대신 한다. 테스트의 @BeforeEach에서 리포지토리를 만들어 서비스에 넣던 조립은 04회에서 스프링 컨테이너의 일이 된다. 05회에서는 InMemoryMemberRepository 자리에 JDBC, JdbcTemplate, JPA, 스프링 데이터 JPA로 만든 구현을 차례로 끼우는데, 그동안 MemberService와 컨트롤러는 한 글자도 바뀌지 않는다. 의존 화살표를 인터페이스에서 멈추게 한 설계의 값을 그때 돌려받는다. 06회에서는 서비스와 리포지토리의 모든 메서드에 공통 기능을 덧붙이는 AOP를 다룬다.

    로드맵의 뒤쪽 권들과도 이어진다. GET과 POST의 성질, 302와 303, PRG는 HTTP 웹 기본 지식 권에서 명세 수준으로 다시 본다. DispatcherServlet이 핸들러 매핑과 어댑터, 뷰 리졸버를 거치는 전체 구조는 스프링 MVC 1편에서 직접 만들어 보며 이해하고, 입력값 검증과 예외 처리는 스프링 MVC 2편에서 다룬다. ++sequence가 왜 깨지고 AtomicLong이 어떻게 그것을 막는지는 자바 고급 1편의 멀티스레드와 동시성에서, 유일 제약과 트랜잭션은 데이터베이스와 스프링 DB 권에서 바닥까지 내려간다.

    이 장의 핵심

    회원 관리 예제의 코드는 짧지만, 그 안의 결정마다 한 층 아래의 사실이 받치고 있다. 계층을 나누는 것은 클래스 파일에 어떤 이름이 남는지를 정하는 일이고, 테스트의 격리는 상태가 지역 변수·인스턴스 필드·정적 필드 가운데 어디에 사는지로 결정된다. 서버에서는 객체가 하나이고 스레드가 여럿이므로, 필드에 놓인 가변 상태는 모든 요청이 함께 읽고 쓴다. 웹 계층에서는 브라우저의 폼이 키=값 텍스트로 날아와 세터 호출로 객체가 되고, 객체는 게터 호출로 HTML이 되어 돌아가며, 상태를 바꾼 요청에는 화면 대신 302로 응답해 새로 고침을 안전하게 만든다.
    계층과 의존 방향
    컨트롤러는 서비스를, 서비스는 리포지토리 인터페이스를 알고 그 반대는 모른다. 서비스의 클래스 파일에는 구현 클래스의 이름이 남지 않으므로 저장소 구현을 바꿔도 서비스는 그대로다.
    Optional 반환
    "찾았는데 없음"이 정상 결과인 조회 메서드는 Optional을 반환해 값이 없을 수 있다는 사실을 타입에 적는다.
    JUnit의 테스트 인스턴스 수명 주기
    기본 설정에서 JUnit은 테스트 메서드마다 테스트 클래스의 새 인스턴스를 만든다. 격리되는 것은 그 인스턴스의 필드까지이고, 정적 필드 같은 바깥의 상태는 @AfterEach나 @BeforeEach에서 직접 정리한다.
    의존관계 주입
    서비스가 리포지토리를 스스로 만들지 않고 생성자로 받으면, 테스트와 운영 코드가 어떤 구현을 넣을지 밖에서 정할 수 있고 "하나의 저장소"를 정적 필드 없이 보장할 수 있다.
    요청 스레드와 공유 객체
    톰캣은 요청마다 워커 스레드를 배정하고, 컨트롤러·서비스·리포지토리 객체는 하나다. 지역 변수는 스레드마다 따로지만 이 객체들의 필드는 모든 스레드가 공유한다.
    갱신 손실과 깨진 자료 구조
    ++sequence는 읽기·더하기·쓰기의 세 단계라 동시에 실행되면 같은 번호가 두 번 나온다. 동기화되지 않은 HashMap은 동시 수정으로 깨지면 그 뒤의 요청까지 실패하게 만든다.
    폼 전송과 데이터 바인딩
    POST 폼은 본문에 name=spring 형식으로 실려 오고, 스프링 MVC는 폼 객체를 만들어 파라미터 이름과 같은 프로퍼티의 세터를 호출한다. 바인딩은 값의 존재나 올바름을 보장하지 않는다.
    PRG 패턴
    상태를 바꾸는 POST에는 302와 Location으로 응답해 브라우저가 GET을 새로 보내게 한다. 새로 고침은 마지막 요청을 반복하므로, 마지막 요청이 GET이어야 안전하다.
    검사 후 행동의 틈
    중복 검사와 저장이 하나의 원자적 단위가 아니면 동시 요청에서 규칙이 깨진다. 최종 보증은 저장소의 유일 제약처럼 검사와 저장을 한 번에 하는 장치가 맡는다.

    실무에서 다시 판단하면, 메모리 리포지토리는 버리는 코드가 아니라 쓰임새가 분명한 도구다. 서비스의 규칙을 빠르게 검증하는 테스트에서는 데이터베이스 없이 바로 도는 가짜 저장소가 유용하다. 다만 이 회차에서 본 대로 메모리 구현은 실제 저장소와 다르게 행동하는 지점이 있다. 조회한 객체가 저장한 객체와 같은 객체이고, 유일 제약이 없고, 순서가 우연히 맞는다. 그래서 "서비스의 규칙"은 메모리 구현으로 검증하더라도 "저장소 구현이 맞는가"와 "제약이 실제로 걸려 있는가"는 실제 데이터베이스를 상대로 검증해야 한다. 어느 테스트가 무엇을 보증하는지를 구분하는 것이 판단의 핵심이다.

    하나뿐인 객체의 필드는 코드 리뷰에서 가장 먼저 볼 곳이다. 컨트롤러나 서비스에 final이 아닌 필드가 있거나, final이어도 HashMap이나 ArrayList처럼 내용이 바뀌는 객체를 가리킨다면 "이 필드를 두 요청이 동시에 건드리면 어떻게 되는가"를 물어야 한다. 이런 버그는 개발자의 PC에서 혼자 눌러 볼 때는 나타나지 않고, 요청이 겹치는 운영 환경에서만 드물게 나타나며, 이 회차의 실험처럼 한 번 깨진 상태가 재시작 전까지 남기도 한다. 판단 기준은 단순하다. 요청마다 다른 값은 지역 변수와 매개변수에 두고, 필드에는 바뀌지 않는 협력 객체만 둔다. 공유해야 하는 가변 상태가 정말 필요하면 그 상태를 바꾸는 연산의 단위가 무엇인지부터 정한다.

    중복 방지 같은 규칙을 어디에 둘지도 조건에 따라 답이 달라진다. 서버가 한 대이고 요청이 드물다면 서비스의 검사만으로도 문제가 드러나지 않은 채 오래 갈 수 있다. 서버를 여러 대로 늘리는 순간 애플리케이션 안의 락은 의미를 잃고, 데이터베이스의 유일 제약만이 모든 경로를 막는다. 그때는 제약 위반으로 발생하는 예외를 사용자가 이해할 메시지로 바꾸는 처리가 함께 필요하다. PRG도 같은 눈으로 보면 된다. 리다이렉트는 새로 고침으로 인한 재전송을 막지만 사용자가 버튼을 두 번 누르는 것은 막지 못하므로, 주문이나 결제처럼 중복이 곧 손해인 기능은 서버 쪽에 중복을 식별하고 거부하는 장치를 따로 둔다.
  • 정적 필드 버전의 InMemoryMemberRepository(본문의 첫 구현)를 쓰고 @AfterEach는 없는 테스트 클래스에 테스트가 둘 있다. X는 repository.save(new Member("kim"))을 한 뒤 assertThat(repository.findAll()).hasSize(1)을 단정한다. Y는 아무것도 저장하지 않고 assertThat(repository.findByName("kim")).isEmpty()를 단정한다. X→Y 순서와 Y→X 순서 각각에서 어느 테스트가 통과하고 실패하는지 예측하고, 리포지토리의 필드에서 static을 떼면 결과가 어떻게 달라지는지 설명하라.
  • HashMap과 long sequence를 쓰는 리포지토리에서 sequence가 10이고 저장된 회원이 10명이다. 세 스레드가 각각 다른 회원으로 save를 호출했는데, 세 스레드 모두 sequence를 읽는 명령까지 실행한 뒤에야 나머지 명령들이 실행되었다. 세 호출이 끝난 뒤 sequence의 값과 맵에 들어 있는 회원 수를 구하고, 세 회원 객체의 id 필드가 각각 얼마인지 적어라(맵 자체는 깨지지 않았다고 가정한다).
  • 등록 폼에 name="email"인 입력 칸을 하나 더 넣고, 이름에 lee, 이메일에 lee@example.com을 입력해 제출했다. 브라우저가 보내는 요청의 시작 줄, Content-Type, Content-Length, 본문을 적어라. 그리고 MemberForm을 고치지 않았다면 컨트롤러의 form에 이메일이 어떻게 되는지 설명하라.
  • 동료가 홈 화면에 "방금 등록한 회원: OOO"를 보여 주려고 MemberController에 private String lastRegisteredName; 필드를 추가했다. register에서 이 필드에 이름을 넣고, 홈 화면을 그릴 때 이 필드를 모델에 담는다. 혼자 테스트할 때는 잘 동작했다. 사용자 두 명이 거의 동시에 등록할 때 어떤 화면이 나올 수 있는지 요청 순서를 들어 설명하고, 원인을 한 문장으로 적어라.
  • register 메서드의 마지막 줄을 return "redirect:/";에서 return "home";으로 바꿨다. "spring"을 등록한 직후 화면은 똑같이 홈으로 보인다. 이 상태에서 사용자가 새로 고침을 누르면 브라우저가 어떤 요청을 보내고 서버에서 무슨 일이 일어나는지, 본문의 코드를 기준으로 설명하라.
    •

    1. X→Y 순서에서는 X가 통과하고 Y가 실패한다. X가 저장한 "kim"이 정적 맵에 남아 있어 Y의 findByName("kim")이 값을 찾기 때문이다. Y→X 순서에서는 둘 다 통과한다. Y가 실행될 때 맵이 비어 있고, Y는 아무것도 남기지 않으므로 X도 빈 맵에서 시작한다. 같은 코드가 순서에 따라 통과하기도 실패하기도 한다는 것이 문제의 요점이다. static을 떼면 맵이 리포지토리 객체마다 따로 생긴다. JUnit이 테스트 메서드마다 테스트 인스턴스를 새로 만들면서 필드 초기화 식의 new InMemoryMemberRepository()도 다시 실행하므로, 두 테스트는 서로 다른 맵을 쓰고 어떤 순서로든 둘 다 통과한다.

    2. 세 스레드 모두 10을 읽었으므로 각자 11을 계산해 필드에 쓴다. 최종 sequence는 13이 아니라 11이다. 세 회원 객체의 id는 모두 11이다. 세 스레드가 차례로 store.put(11, 회원)을 실행하면 같은 키에 대한 값이 계속 덮어써져 마지막에 실행된 한 명만 남는다. 맵의 회원 수는 10명에서 한 명 늘어난 11명이고, 두 명은 어디에도 저장되지 않았다. 세 호출 모두 예외 없이 정상적으로 반환했다는 점이 이 문제를 발견하기 어렵게 만든다.

    3. 시작 줄은 POST /members/new HTTP/1.1, Content-Type은 application/x-www-form-urlencoded다. 본문은 name=lee&email=lee%40example.com이다. 두 쌍이 &로 이어지고, @는 이 형식에서 그대로 쓸 수 없는 문자여서 %40으로 퍼센트 인코딩된다. 본문 길이는 name=lee 8바이트, & 1바이트, email=lee%40example.com 23바이트를 더해 Content-Length: 32다. MemberForm에는 email 프로퍼티(곧 setEmail)가 없으므로 그 파라미터는 바인딩할 곳이 없어 무시된다. 오류는 나지 않고, form.getName()만 "lee"가 된다.

    4. 컨트롤러 객체는 하나이고 두 사용자의 요청은 서로 다른 워커 스레드가 처리한다. 사용자 A의 POST가 필드에 "a"를 쓰고 302를 응답한다. A의 브라우저가 홈으로 GET을 보내기 전에 사용자 B의 POST가 같은 필드에 "b"를 쓴다. 이어서 도착한 A의 GET은 필드에서 "b"를 읽어 A의 화면에 "방금 등록한 회원: b"를 그린다. A는 자기가 등록하지 않은 사람의 이름을 본다. 원인은 요청마다 달라야 하는 데이터를 모든 요청 스레드가 공유하는 객체의 필드에 두었기 때문이다. 혼자 테스트할 때는 요청이 겹치지 않아 드러나지 않았다.

    5. 리다이렉트가 없으므로 브라우저가 마지막으로 보낸 요청은 POST /members/new(본문 name=spring)이다. 새로 고침은 이 요청을 다시 보낸다(대부분의 브라우저는 양식을 다시 제출할지 묻는 확인 창을 먼저 띄운다). 서버에서는 register가 다시 실행되고, 서비스의 중복 검사가 이미 저장된 "spring"을 찾아 IllegalStateException을 던진다. 컨트롤러가 이 예외를 잡지 않으므로 사용자는 500 오류 화면을 본다. 중복 검사가 없는 기능이었다면 같은 데이터가 한 번 더 저장되었을 것이다. redirect:/였다면 마지막 요청이 GET /이어서 새로 고침은 홈 화면을 다시 읽기만 한다.

     JUnit은 기본 설정에서 테스트 메서드마다 테스트 클래스의 인스턴스를 새로 만든다. 그런데도 본문의 첫 리포지토리 구현에서 앞 테스트가 저장한 회원이 다음 테스트에 보인 이유는 무엇인가? JUnit이 성능을 위해 리포지토리 객체를 캐시해 두고 재사용하기 때문이다. 데이터가 리포지토리 객체가 아니라 클래스에 하나만 존재하는 정적 필드에 들어 있어서, 리포지토리 객체를 새로 만들어도 같은 맵을 보기 때문이다. 테스트 메서드들이 여러 스레드에서 동시에 실행되어 서로의 데이터를 덮어썼기 때문이다. HashMap이 JVM이 끝날 때 내용을 파일에 저장했다가 다음 테스트에서 다시 읽기 때문이다. 테스트 인스턴스와 그 필드 초기화 식으로 만든 리포지토리 객체는 테스트마다 새것이지만, store와 sequence는 static이라 클래스에 하나뿐이다. JUnit의 격리는 테스트 인스턴스의 필드까지만 닿는다. JUnit은 테스트 대상 객체를 캐시하지 않고, 기본 설정에서 테스트를 동시에 실행하지도 않으며, HashMap은 메모리에만 존재한다. static/index.html과 @GetMapping("/")가 붙은 컨트롤러 메서드가 함께 있을 때 GET / 요청이 컨트롤러로 가는 이유로 맞는 것은? 정적 파일은 서버가 시작될 때 한 번만 읽히고 그 뒤에는 무시되기 때문이다. 톰캣이 자바 클래스를 HTML 파일보다 먼저 로딩하기 때문이다. DispatcherServlet이 핸들러 매핑을 순서 값이 작은 것부터 차례로 물어 처음 답한 것을 쓰는데, 컨트롤러 메서드를 찾는 매핑의 순서 값(0)이 첫 화면 매핑(2)보다 작기 때문이다. @GetMapping이 붙은 메서드가 있으면 스프링 부트가 정적 리소스 기능 전체를 끈다. DispatcherServlet은 정렬된 핸들러 매핑에 차례로 묻고 처음 핸들러를 내놓은 매핑을 쓴다. RequestMappingHandlerMapping은 0, 스프링 부트의 WelcomePageHandlerMapping은 2, 정적 리소스 매핑은 그보다 훨씬 뒤다. 정적 리소스 기능이 꺼지는 것이 아니어서 /index.html을 직접 요청하면 파일이 그대로 응답된다. 폼 객체 MemberForm에서 setName 메서드만 지우고 name=spring을 POST로 보냈다. 컨트롤러에서 form.getName()의 결과와 그 이유로 맞는 것은? null이다. 프로퍼티 바인딩은 필드가 아니라 세터를 통해 값을 넣으므로, 세터가 없으면 넣을 곳이 없어 그 파라미터는 조용히 무시된다. "spring"이다. 스프링이 리플렉션으로 private 필드 name에 직접 값을 넣기 때문이다. 요청이 400 오류로 거부된다. 바인딩할 수 없는 파라미터가 하나라도 있으면 스프링이 요청을 받지 않기 때문이다. 빈 문자열 ""이다. 바인딩에 실패한 문자열 필드는 빈 문자열로 초기화되기 때문이다. 데이터 바인딩의 프로퍼티 바인딩은 요청 파라미터의 이름을 자바빈 프로퍼티에 맞춰 세터를 호출하는 방식이다. 세터가 없으면 name이라는 프로퍼티가 쓰기 가능한 것으로 보이지 않아 값이 들어가지 않고, 오류도 나지 않는다. 필드는 초기값 null 그대로다. 본문의 실험에서 확인한 결과이기도 하다. 회원 등록을 처리한 POST 핸들러가 화면을 직접 그리지 않고 redirect:/를 반환하는 가장 중요한 이유는? POST 요청에는 HTML 본문을 응답으로 보낼 수 없도록 HTTP 명세가 금지하기 때문이다. 리다이렉트를 하면 서버가 요청을 두 번 처리해 데이터가 더 안전하게 저장되기 때문이다. 302 응답을 받으면 브라우저가 폼 데이터를 캐시에 저장해 다음 등록이 빨라지기 때문이다. 브라우저의 새로 고침은 마지막 요청을 다시 보내므로, 마지막 요청을 안전한 GET으로 바꿔 두어 등록이 반복되지 않게 하려는 것이다. POST는 안전하지도 멱등하지도 않아 다시 보내면 부수 효과가 반복된다. 302와 Location으로 응답하면 브라우저가 GET을 새로 보내고, 그 뒤의 새로 고침은 그 GET만 반복한다. HTTP는 POST에 HTML로 응답하는 것을 금지하지 않으며, 리다이렉트는 저장의 안전성이나 캐시와 무관하다. 리포지토리를 ConcurrentHashMap과 AtomicLong으로 바꾼 뒤에도, 같은 이름으로 동시에 들어온 등록 요청 둘이 모두 성공해 이름이 중복 저장될 수 있다. 원인으로 맞는 것은? ConcurrentHashMap의 put이 가끔 값을 잃어버리기 때문이다. AtomicLong이 두 스레드에 같은 번호를 줄 수 있기 때문이다. 이름이 있는지 검사하는 호출과 저장하는 호출이 각각은 안전하지만 둘이 하나의 원자적 단위가 아니어서, 두 스레드가 모두 "없음"을 확인한 뒤 차례로 저장할 수 있기 때문이다. 톰캣이 같은 요청을 두 스레드에 복제해 실행하기 때문이다. 검사 후 행동 구조에서는 검사와 행동 사이에 다른 스레드가 끼어들 수 있다. 개별 연산의 스레드 안전성은 연산 여러 개로 이루어진 로직의 원자성을 보장하지 않는다. ConcurrentHashMap과 AtomicLong은 문서대로 동작했고, 본문의 실험에서도 식별자는 한 번도 겹치지 않았다. 해결하려면 락으로 두 연산을 묶거나 저장소의 유일 제약에 맡겨야 한다.
    도메인 객체(domain object)
    회원, 주문처럼 업무가 다루는 대상을 표현한 객체. 웹이나 저장 기술에 대한 지식을 갖지 않는다.
    리포지토리(repository)
    도메인 객체를 저장하고 조회하는 책임을 가진 객체. 인터페이스로 계약을 정해 두면 저장 기술이 바뀌어도 사용하는 쪽 코드가 유지된다.
    서비스 계층(service layer)
    업무 규칙을 실행하는 계층. 리포지토리를 조합해 "중복 이름은 등록할 수 없다" 같은 규칙을 구현한다.
    의존관계 주입(dependency injection)
    객체가 필요로 하는 다른 객체를 스스로 만들지 않고 생성자 등을 통해 밖에서 받는 방식.
    단정(assertion)
    테스트에서 "이 값은 이래야 한다"를 코드로 적은 것. 조건이 틀리면 AssertionError를 던져 테스트를 실패시킨다.
    테스트 격리(test isolation)
    각 테스트가 다른 테스트의 실행 여부나 순서와 무관하게 같은 결과를 내는 성질.
    갱신 손실(lost update)
    두 스레드가 같은 값을 읽고 각자 계산한 결과를 써서, 한쪽의 변경이 다른 쪽에 덮여 사라지는 현상.
    경쟁 조건(race condition)
    여러 스레드의 실행 순서에 따라 결과의 옳고 그름이 달라지는 상황. 검사 후 행동(check-then-act)이 대표적인 형태다.
    데이터 바인딩(data binding)
    요청 파라미터 같은 사용자 입력을 이름에 맞춰 객체의 생성자 인자나 프로퍼티에 넣는 일.
    PRG 패턴(Post/Redirect/Get)
    POST 요청을 처리한 뒤 리다이렉트로 응답해 브라우저가 GET으로 결과 화면을 다시 요청하게 하는 방식.
