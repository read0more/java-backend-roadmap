    이 회차의 질문: 힙에 있던 데이터를 프로세스 밖에 두려면

    저장소를 자바 컬렉션으로 구현하면 데이터는 JVM 힙에 있는 객체다. 빠르고 설정할 것도 없지만 수명이 프로세스와 같다. 서버를 내리면 힙이 통째로 사라지고, 다시 띄우면 빈 컬렉션에서 시작한다. 서버를 두 대로 늘리면 두 프로세스가 서로 다른 힙을 가지므로 한쪽에 저장한 데이터를 다른 쪽이 모른다. 데이터를 프로세스보다 오래, 여러 프로세스가 함께 쓰게 하려면 데이터를 프로세스 밖에 두어야 한다.

    그 "밖"이 데이터베이스(database)다. 관계형 데이터베이스 관리 시스템(RDBMS)은 대개 별도의 프로세스로 떠 있고, 데이터를 디스크의 파일에 기록하며, SQL이라는 언어로 요청을 받는다. 자바 애플리케이션 입장에서 DB에 저장한다는 것은 메서드를 호출하는 일이 아니다. 다른 프로세스에 연결을 맺고, 문자열로 된 SQL을 보내고, 돌아온 바이트를 해석해 자바 객체로 되돌리는 일이다.

    이 회차는 그 일을 하는 네 가지 방법을 아래에서 위로 올라가며 본다. 순수 JDBC, 스프링 JdbcTemplate, JPA, 스프링 데이터 JPA다. 넷은 경쟁하는 기술이라기보다 층을 이룬다. 맨 아래에 JDBC가 있고, 나머지는 모두 JDBC 위에서 특정한 종류의 반복을 대신 처리한다. 중간에 스프링 통합 테스트를 다루는데, DB가 끼면 테스트가 왜 달라지는지가 커넥션과 트랜잭션의 성질에서 바로 나오기 때문이다.

                서비스 코드 (저장소 인터페이스에만 의존한다)
   ┌────────────────┬─────────────────┬──────────────────────┐

   │                │                 │ (프록시가 구현을 대신)   │

    그림에서 읽어야 할 것은 두 가지다. 첫째, 어느 길로 가든 마지막에는 JDBC의 Connection과 PreparedStatement를 지난다. JPA를 써도 DB로 가는 것은 SQL 문자열이고 그것을 보내는 것은 JDBC 드라이버다. 둘째, JdbcTemplate과 JPA는 위아래가 아니라 옆에 나란히 있다. JPA가 JdbcTemplate을 거쳐 가는 것이 아니다. 둘 다 JDBC를 직접 쓰는 서로 다른 방식의 도구다.

    예제는 이 회차를 위해 새로 만든 작은 도메인을 쓴다. 제목(title) 하나를 가진 도서(Book)를 book 테이블에 넣고 꺼낸다. 예제가 작아야 그 아래에서 일어나는 일이 잘 보인다. 실행 결과는 JDK 21, H2 2.4.240, spring-jdbc 7.0.10, HikariCP 7.0.2에서 직접 돌려 얻은 것이다. 이 회차가 쓰는 API(JdbcTemplate, DataSourceUtils, TransactionTemplate 등)는 스프링 프레임워크 6.x에도 같은 이름과 시그니처로 있다.

    순수 JDBC, JdbcTemplate, JPA와 스프링 데이터 JPA가 모두 같은 JDBC API와 드라이버를 거쳐 DB에 닿는다는 것, JdbcTemplate과 JPA가 위아래가 아니라 나란히 있다는 것을 보여 준다. 흰 배경의 계층 구조 다이어그램. 맨 위에 가로로 긴 회색 상자 "서비스 코드". 그 아래 단에 같은 높이로 세 기둥이 나란히 서 있다. 왼쪽 기둥은 한 칸짜리 파란 상자 "순수 JDBC 저장소". 가운데 기둥은 한 칸짜리 파란 상자 "JdbcTemplate 저장소". 오른쪽 기둥은 두 칸이 위아래로 쌓여 있는데 위 칸은 연한 초록 상자 "스프링 데이터 JPA", 아래 칸은 초록 상자 "JPA (Hibernate)". 회색 상자에서 세 기둥 각각으로 내려가는 얇은 화살표 세 개. 세 기둥 아래에는 전체 폭을 차지하는 주황색 가로 띠 "JDBC API"가 있고, 띠 안에 작은 글씨로 "Connection · PreparedStatement · ResultSet". 세 기둥 각각에서 주황 띠로 내려가는 굵은 화살표 세 개. 주황 띠 아래에 좁은 회색 띠 "JDBC 드라이버". 그 아래로 세로 화살표 하나가 내려가며 옆에 라벨 "SQL 문자열". 맨 아래에는 원통 모양의 DB 아이콘과 라벨 "DB 엔진", 그 옆에 문서 아이콘과 라벨 "데이터 파일". 평면적인 기술 도해 스타일, 차분한 파랑·초록·회색에 JDBC 띠만 주황으로 강조. 어느 기술을 고르든 마지막에는 JDBC API와 드라이버를 거쳐 SQL 문자열이 DB로 간다. 위쪽 층은 그 과정의 반복을 대신 처리할 뿐이다.

    H2 데이터베이스: 설치한다는 것의 실제 의미

    H2는 자바로 작성된 관계형 데이터베이스다. 실체는 jar 파일 하나이고, 그 안에 DB 엔진과 JDBC 드라이버, 그리고 브라우저로 쓰는 관리 도구인 H2 콘솔이 함께 들어 있다. 그래서 H2를 설치한다는 말은 운영체제에 서비스를 등록하는 일이 아니라, jar를 내려받아 JVM으로 실행하는 일이다. 학습과 테스트에 H2를 자주 쓰는 이유가 여기 있다. 띄우고 내리는 비용이 자바 프로그램 하나를 실행하는 것과 같다.

    H2를 이해하는 열쇠는 JDBC URL이다. 같은 엔진이 URL에 따라 전혀 다른 방식으로 동작한다. H2 문서의 "Database URL Overview"가 정리한 형식 가운데 이 회차에 필요한 것은 넷이다.

    방식URL 예엔진이 도는 곳데이터가 있는 곳
    임베디드(embedded)jdbc:h2:~/shop애플리케이션과 같은 JVM사용자 홈의 shop.mv.db 파일
    서버(server)jdbc:h2:tcp://localhost/~/shop별도의 H2 서버 프로세스서버 쪽 홈의 shop.mv.db 파일
    인메모리, 이름 있음jdbc:h2:mem:shop애플리케이션과 같은 JVM그 JVM의 메모리
    인메모리, 이름 없음jdbc:h2:mem:애플리케이션과 같은 JVM그 커넥션 하나만 보는 메모리

    임베디드 모드에서는 DB 엔진이 라이브러리처럼 애플리케이션의 JVM 안에서 돈다. 네트워크를 거치지 않으므로 H2 문서는 이것을 가장 빠르고 쉬운 연결 방식이라고 설명한다. 서버 모드에서는 엔진이 다른 프로세스에 있고 애플리케이션은 TCP로 접속한다. H2 문서는 서버 모드가 임베디드보다 느린 이유를 모든 데이터가 TCP/IP로 오가기 때문이라고 적는다. URL의 ~/는 사용자 홈 디렉터리를 가리킨다.

    파일 하나와 잠금

    임베디드 URL로 처음 접속하면 H2는 DB 파일을 만든다. 임시 디렉터리에 shop이라는 이름으로 접속해 테이블을 만든 뒤 디렉터리를 보면 shop.mv.db 파일 하나가 있다. H2 문서에 따르면 이 파일에 트랜잭션 로그, 인덱스, 모든 테이블의 데이터가 들어간다. "DB에 저장한다"의 물리적 실체가 이 파일이다.

    이제 한 프로세스가 임베디드 모드로 이 파일을 연 상태에서 다른 프로세스가 같은 URL로 접속을 시도하면 어떻게 되는지 실행해 보았다. 두 번째 프로세스는 접속하지 못하고 예외를 받는다.

    JdbcSQLNonTransientConnectionException errorCode=90020
Database may be already in use: ".../shop.mv.db". Possible solutions: close all other connection(s); use the server mode [90020-240]

    파일을 연 프로세스가 잠금을 쥐고 있어서다. 두 엔진이 같은 파일을 동시에 고치면 파일이 깨지므로 당연한 보호다. 여기서 실습 환경의 구성이 결정된다. 애플리케이션이 DB를 쓰는 동안 H2 콘솔로 같은 데이터를 들여다보고 싶다면, 두 프로그램이 파일을 직접 여는 것이 아니라 파일을 여는 프로세스를 하나로 정하고 둘 다 그 프로세스에 접속해야 한다. 오류 메시지가 제안하는 "use the server mode"가 그 뜻이다.

 ┌──────────────┐                          ┌──────────────┐  TCP   ┌───────────┐

    서버 모드, 콘솔, 그리고 처음 한 번의 파일 생성

    H2 콘솔은 그 자체가 웹 서버를 내장한 클라이언트/서버 애플리케이션이다. 콘솔을 띄우면 웹 서버가 뜨고, 브라우저로 http://localhost:8082에 접속해 로그인 화면에 드라이버 클래스와 JDBC URL, 사용자 이름을 넣는다. 콘솔도 결국 JDBC로 DB에 접속하는 프로그램이라는 뜻이다. H2의 org.h2.tools.Server 도구는 웹 서버의 기본 포트를 8082, TCP 서버의 기본 포트를 9092로 둔다. URL에서 포트를 생략한 jdbc:h2:tcp://localhost/~/shop은 9092번으로 간다.

    서버 모드에는 한 가지 걸림돌이 있다. TCP로 접속해서는 없는 DB를 새로 만들 수 없다. H2 문서는 TCP 연결이나 웹 인터페이스를 통한 원격 DB 생성이 기본으로 허용되지 않는다고 밝히고, 임베디드 URL이나 로컬 콘솔, Shell 도구로 로컬에서 만들 것을 권한다. TCP 서버를 띄우고 존재하는 DB와 없는 DB에 차례로 접속해 본 결과가 이를 그대로 보여 준다.

    TCP shop: 연결 성공, book 행 수 = 1
TCP nothing: errorCode=90149
  Database ".../nothing" not found, either pre-create it or allow remote database creation (not recommended in secure environments) [90149-240]

    그래서 순서가 생긴다. 처음 한 번은 임베디드 URL(jdbc:h2:~/shop)로 접속해 파일을 만들고, 그 연결을 끊은 뒤부터는 TCP URL(jdbc:h2:tcp://localhost/~/shop)로 접속한다. 네트워크 너머의 누군가가 서버에 임의의 DB 파일을 만들게 두지 않으려는 보안상의 기본값이고, -ifNotExists 옵션으로 풀 수 있지만 문서는 권하지 않는다.

    인메모리 방식은 파일을 만들지 않는다. H2 문서에 따르면 기본적으로 마지막 커넥션이 닫히면 DB도 닫히고, 인메모리 DB라면 그때 내용이 사라진다. 커넥션을 여닫을 때마다 테이블이 없어지는 것을 막으려면 URL에 ;DB_CLOSE_DELAY=-1을 붙여 JVM이 살아 있는 동안 유지하게 한다. 이 회차의 실행 예제가 이 옵션을 쓰는 이유다.

    테이블은 다음 SQL로 만든다. generated by default as identity는 행을 넣을 때 id를 주지 않으면 DB가 값을 만들어 채운다는 뜻이다. 키 값을 애플리케이션이 아니라 DB가 정한다는 이 사실이 뒤에서 JDBC의 생성 키 조회와 JPA의 IDENTITY 전략으로 이어진다.

    create table book (
    id    bigint generated by default as identity primary key,
    title varchar(255)
);

    스프링 부트 애플리케이션이 이 DB를 쓰게 하려면 접속 정보를 설정에 적는다. 스프링 부트 문서에 따르면 spring.datasource.url을 주지 않으면 부트는 임베디드 DB의 자동 구성을 시도하고, 드라이버 클래스는 대부분 URL에서 추론하므로 따로 적지 않아도 된다.

    spring.datasource.url=jdbc:h2:tcp://localhost/~/shop
spring.datasource.username=sa
    H2는 띄우기 쉬워서 학습과 테스트에 알맞다. 다만 DB 엔진마다 SQL 방언과 잠금·격리 동작이 다르다. H2에서 통과한 SQL과 테스트가 운영에서 쓰는 DB에서도 같게 동작한다는 보장은 없다.

    JDBC: 인터페이스는 JDK에, 구현은 드라이버에

    DB 제품마다 클라이언트와 서버가 주고받는 통신 규약이 다르다. 애플리케이션이 그 규약을 직접 다루면 DB를 바꿀 때 코드를 전부 다시 써야 한다. JDBC(Java Database Connectivity)는 이 문제를 인터페이스로 푼다. JDK의 java.sql, javax.sql 패키지에는 Connection, PreparedStatement, ResultSet, DataSource 같은 인터페이스가 있고, 실제로 바이트를 주고받는 구현은 DB 벤더가 드라이버(driver)라는 jar로 제공한다. 자바 기본편에서 본 다형성이 라이브러리 수준에서 쓰인 것이다.

    가장 작은 JDBC 프로그램을 실행해 그 구조를 눈으로 확인하자. 각 객체의 실제 클래스 이름을 찍어 본다.

    import java.sql.*;

public class JdbcFirst {
    public static void main(String[] args) throws SQLException {
        DriverManager.drivers()
                .forEach(d -> System.out.println("드라이버: " + d.getClass().getName()));

    소스 코드에는 org.h2라는 글자가 URL 문자열 말고는 한 번도 나오지 않는다. 그런데 실행 중에 만들어진 객체는 전부 org.h2.jdbc 패키지의 클래스다. 코드는 java.sql의 인터페이스 타입으로만 객체를 다루고, 실제 인스턴스는 드라이버가 만든다. DB를 MySQL로 바꾸면 URL과 클래스패스의 jar가 바뀌고 이 클래스 이름들이 그 드라이버의 것으로 바뀔 뿐, 호출하는 메서드는 그대로다(SQL 방언의 차이는 별개의 문제다).

    드라이버를 등록하는 코드가 없는데 첫 줄에 org.h2.Driver가 찍힌 이유도 짚어 두자. DriverManager의 Javadoc에 따르면 이 클래스는 초기화될 때 서비스 제공자 로딩 메커니즘으로 java.sql.Driver의 구현을 찾아 적재한다. H2 jar를 열어 보면 META-INF/services/java.sql.Driver라는 파일이 있고 내용은 org.h2.Driver 한 줄이다. 클래스패스에 jar를 올려 두는 것만으로 드라이버가 발견되는 이유다. 그다음 getConnection은 등록된 드라이버들 가운데 주어진 URL을 처리할 수 있는 것을 고른다. jdbc:h2:로 시작하는 URL은 H2 드라이버가 받는다.

    한 번의 조회에서 일어나는 일

    Connection의 Javadoc은 이 객체를 "특정 데이터베이스와의 연결(세션)"이라고 정의하고, SQL 문은 커넥션의 문맥 안에서 실행되고 결과도 그 안에서 돌아온다고 적는다. 커넥션은 단순한 통로가 아니라 DB 쪽에 상태를 가진 세션이다. 로그인한 사용자, 진행 중인 트랜잭션, 열려 있는 커서가 모두 이 세션에 속한다. 이 점이 이 회차의 절반을 지배한다.

    출력의 셋째 줄 autoCommit: true도 눈여겨보자. Javadoc에 따르면 새 커넥션은 기본적으로 자동 커밋(auto-commit) 모드이고, 이 모드에서는 문장 하나하나가 실행되자마자 개별 트랜잭션으로 커밋된다. 지금은 사실만 기억해 두고 뒤에서 실험한다.

    마지막으로 커넥션을 얻는 두 가지 통로를 구분하자. 위 예제는 DriverManager를 썼지만 Javadoc은 DataSource를 쓰는 것이 데이터 소스에 연결하는 더 바람직한 수단이라고 적는다. DataSource는 getConnection() 메서드 하나로 "커넥션을 얻는 방법"을 추상화한 인터페이스다. 스프링 문서는 이것을 일반화된 커넥션 팩토리라고 부르며, 컨테이너나 프레임워크가 커넥션 풀링과 트랜잭션 관리를 애플리케이션 코드로부터 감출 수 있게 해 준다고 설명한다. 매번 새로 만들어 주든 풀에서 꺼내 주든 호출하는 쪽 코드는 같다.

    순수 JDBC로 저장소를 만들면 드러나는 것

    이제 JDBC만으로 저장소를 만든다. 도메인 클래스와 저장소 인터페이스는 다음과 같다. 서비스 계층은 이 인터페이스만 알고, 뒤에서 구현을 네 번 바꿔 끼운다.

    import java.sql.*;
import java.util.ArrayList;
import java.util.List;
import java.util.Optional;
import javax.sql.DataSource;

public class JdbcBookRepository implements BookRepository {
    private final DataSource dataSource;

    public JdbcBookRepository(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    @Override
    public Book save(Book book) {
        String sql = "insert into book(title) values(?)";
        try (Connection con = dataSource.getConnection();
             PreparedStatement ps = con.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {
            ps.setString(1, book.getTitle());
            ps.executeUpdate();
            try (ResultSet keys = ps.getGeneratedKeys()) {
                if (!keys.next()) {
                    throw new IllegalStateException("생성된 키를 받지 못했다");
                }
                book.setId(keys.getLong(1));
            }
            return book;
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }

    @Override
    public Optional findById(Long id) {
        String sql = "select id, title from book where id = ?";
        try (Connection con = dataSource.getConnection();
             PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setLong(1, id);
            try (ResultSet rs = ps.executeQuery()) {
                if (!rs.next()) {
                    return Optional.empty();
                }
                Book book = new Book(rs.getString("title"));
                book.setId(rs.getLong("id"));
                return Optional.of(book);
            }
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }

    @Override
    public List findAll() {
        String sql = "select id, title from book order by id";
        try (Connection con = dataSource.getConnection();
             PreparedStatement ps = con.prepareStatement(sql);
             ResultSet rs = ps.executeQuery()) {
            List books = new ArrayList<>();
            while (rs.next()) {
                Book book = new Book(rs.getString("title"));
                book.setId(rs.getLong("id"));
                books.add(book);
            }
            return books;
        } catch (SQLException e) {
            throw new IllegalStateException(e);
        }
    }
}

    동작은 한다. 그런데 코드를 다시 읽으면 메서드마다 정말로 다른 부분은 세 가지뿐이다. SQL 문자열, 파라미터를 채우는 줄, 결과 행을 Book으로 옮기는 줄이다. 나머지는 세 메서드가 글자까지 거의 같다. 이 관찰이 뒤에 나올 모든 기술의 출발점이므로 반복되는 부분이 각각 무엇을 위한 것인지 하나씩 본다.

    자원 반납

    Connection, PreparedStatement, ResultSet은 모두 JVM 밖의 자원을 붙잡고 있다. 가비지 컬렉터는 힙의 객체를 치울 뿐 DB 서버의 세션을 닫아 주지 않으므로 코드가 직접 닫아야 한다. 예제는 try-with-resources를 썼다. 이 구문은 블록을 어떻게 빠져나가든(정상 종료든 예외든) 자원을 초기화한 순서의 반대로 닫는다. 이 구문 없이 finally로 직접 닫으면 닫는 도중의 예외까지 처리해야 해서 메서드마다 열 줄 넘는 정리 코드가 붙는다.

    체크 예외

    JDBC의 거의 모든 메서드는 SQLException을 던지고, 이것은 체크 예외(checked exception)다. 잡지 않으면 컴파일되지 않으므로 저장소는 잡아서 다른 예외로 감싸거나 throws로 올려 보내야 한다. 올려 보내면 서비스와 컨트롤러의 메서드 시그니처에 java.sql 패키지의 타입이 번져, 저장 기술을 바꿀 때 위쪽 계층까지 고쳐야 한다. 예제처럼 IllegalStateException으로 감싸면 번지지는 않지만, 키 중복인지 문법 오류인지 접속 장애인지가 한 가지 타입에 뭉개진다. 원인을 구분하려면 벤더마다 다른 오류 코드를 직접 읽어야 한다.

    DB가 만든 키

    save는 id를 모르는 채로 INSERT를 보낸다. 값은 DB가 정하기 때문이다. 그래서 Statement.RETURN_GENERATED_KEYS를 지정하고 실행 뒤에 getGeneratedKeys()로 DB가 만든 키를 되받아 객체에 채운다. 순서가 중요하다. 키는 INSERT가 실제로 실행된 다음에야 알 수 있다.

    값을 문장에 붙이지 않는다

    SQL에 값을 넣는 방법은 두 가지다. 문자열을 이어 붙여 완성된 SQL을 만들 수도 있고, 자리를 ?로 비워 두고 값을 따로 넘길 수도 있다. 둘의 차이를 실행으로 확인한다. 책 세 권이 있는 테이블에서 사용자가 제목 대신 작은따옴표가 섞인 문자열을 입력했다고 하자.

    String input = "없는 책' or '1'='1";

System.out.println("DB에 간 문장: " + glued);

    문자열을 이어 붙인 쪽에서는 입력에 들어 있던 작은따옴표가 문자열 리터럴을 닫아 버렸고, 그 뒤의 or '1'='1'이 SQL 문법의 일부가 되었다. 조건이 항상 참이 되어 세 행이 모두 잡힌다. 이것이 SQL 인젝션(SQL injection)이다. PreparedStatement에서는 SQL 문장의 구조가 ?를 포함한 채로 먼저 정해지고 값은 그 자리에 데이터로 들어간다. 입력 전체가 제목과 비교할 문자열 하나로 취급되므로 일치하는 행이 없다. PreparedStatement를 쓰는 첫째 이유는 성능이 아니라 문장과 값의 분리다.

    여기까지의 정리

    순수 JDBC 코드에서 개발자가 매번 결정하는 것은 SQL, 파라미터, 행을 객체로 옮기는 방법 세 가지다. 커넥션을 얻고 문장을 만들고 예외를 처리하고 자원을 닫는 나머지는 어느 메서드에서나 같다. 뒤에 나올 기술들은 이 "같은 부분"을 누가 어디까지 가져가느냐로 구분된다.

    커넥션은 비싸다: 커넥션 풀과 close()의 두 가지 뜻

    앞의 저장소는 메서드를 부를 때마다 dataSource.getConnection()으로 커넥션을 얻고 끝나면 닫는다. 커넥션을 새로 만드는 일은 가볍지 않다. 서버 모드라면 TCP 연결을 맺고, 사용자를 인증하고, DB 쪽에 세션을 준비해야 한다. SQL 한 줄을 실행하려고 매번 이 과정을 되풀이하면 정작 일보다 준비에 시간을 더 쓴다. 웹 서버는 요청을 스레드마다 나눠 동시에 처리하므로 이 낭비가 요청 수만큼 곱해진다.

    커넥션 풀(connection pool)은 만들어 둔 커넥션을 닫지 않고 모아 두었다가 빌려주는 구조다. 앞에서 본 것처럼 DataSource는 커넥션을 얻는 방법을 감추는 인터페이스이므로, 풀도 DataSource의 한 구현으로 제공된다. 스프링 부트 문서에 따르면 부트는 HikariCP가 있으면 항상 그것을 고르고, spring-boot-starter-jdbc나 spring-boot-starter-data-jpa 스타터를 쓰면 HikariCP 의존성이 함께 들어온다. 저장소 코드는 주입받은 DataSource가 풀인지 아닌지 모른다.

    풀을 쓰면 close()의 뜻이 달라진다. 크기가 2인 풀을 만들어 확인해 보자.

    import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;
import java.sql.Connection;
import java.sql.SQLException;

public class PoolDemo {
    public static void main(String[] args) throws SQLException {
        HikariConfig config = new HikariConfig();
        config.setJdbcUrl("jdbc:h2:mem:pool");
        config.setUsername("sa");
        config.setMaximumPoolSize(2);
        config.setConnectionTimeout(250);              // 빌릴 때 최대 250ms만 기다린다

        try (HikariDataSource ds = new HikariDataSource(config)) {
            Connection first = ds.getConnection();
            Connection physical1 = first.unwrap(org.h2.jdbc.JdbcConnection.class);
            System.out.println("받은 객체: " + first.getClass().getName());
            first.close();                              // 끊는 것이 아니라 풀에 반납
            System.out.println("close() 뒤 물리 커넥션이 닫혔는가: " + physical1.isClosed());

            Connection second = ds.getConnection();
            Connection physical2 = second.unwrap(org.h2.jdbc.JdbcConnection.class);
            System.out.println("다시 빌린 것이 같은 물리 커넥션인가: " + (physical1 == physical2));

            Connection third = ds.getConnection();      // 풀의 두 번째 커넥션
            try {
                ds.getConnection();                     // 세 번째 요청: 남은 것이 없다
            } catch (SQLException e) {
                System.out.println(e.getClass().getName());
                System.out.println(e.getMessage());
            }
            second.close();
            third.close();
        }
    }
}

    풀이 내준 것은 H2의 커넥션이 아니라 그것을 감싼 HikariProxyConnection이다. 이 객체의 close()는 DB와의 연결을 끊지 않는다. 안쪽의 물리 커넥션은 열린 채로 풀에 돌아가고, 다음에 빌리면 같은 물리 커넥션이 다시 나온다. 저장소 코드가 "매번 열고 닫는" 모양을 유지해도 실제로는 빌리고 돌려줄 뿐이라는 뜻이다. 여기서도 인터페이스 뒤의 구현이 바뀌었을 뿐 호출하는 코드는 한 글자도 바뀌지 않았다.

    마지막 두 줄은 풀이 바닥났을 때의 모습이다. 커넥션 두 개를 모두 빌려 간 상태(active=2, idle=0)에서 세 번째 요청은 설정한 시간만큼 기다리다가 예외로 끝났다. HikariCP 문서에 따르면 maximumPoolSize의 기본값은 10이고, 풀이 이 크기에 이르렀는데 쉬는 커넥션이 없으면 getConnection()은 connectionTimeout(기본 30000밀리초)까지 블로킹된 뒤 SQLException을 던진다.

    이 동작에서 순수 JDBC 코드의 가장 위험한 실수가 무엇인지 나온다. 커넥션을 닫지 않는 경로가 하나라도 있으면(예외가 났을 때 close()를 건너뛰는 코드가 전형이다) 그 경로를 지날 때마다 풀에서 커넥션이 하나씩 영영 빠진다. 열 번 지나면 기본 크기의 풀이 비고, 그 뒤 모든 요청은 30초씩 기다리다 실패한다. DB는 멀쩡한데 애플리케이션이 멈춘 것처럼 보이는 장애다. 자원 반납 코드를 사람이 메서드마다 쓰게 두지 않으려는 것이 뒤에 나올 JdbcTemplate의 첫째 동기다.

    트랜잭션은 커넥션에 산다: 자동 커밋과 스레드에 묶인 커넥션

    트랜잭션(transaction)은 여러 SQL을 하나의 작업 단위로 묶어 전부 반영하거나 전부 취소하는 기능이다. 스프링에서 트랜잭션이 어떻게 동작하는지 이해하려면 먼저 JDBC 수준에서 트랜잭션이 어디에 있는지 봐야 한다. 같은 인메모리 DB에 커넥션 두 개(a, b)를 열고, a에서만 자동 커밋을 끈 뒤 변경을 가한다.

    import java.sql.*;

public class AutoCommitDemo {
    static final String URL = "jdbc:h2:mem:tx;DB_CLOSE_DELAY=-1";

    public static void main(String[] args) throws SQLException {
        try (Connection a = DriverManager.getConnection(URL, "sa", "");
             Connection b = DriverManager.getConnection(URL, "sa", "")) {
            try (Statement st = a.createStatement()) {
                st.execute("create table book (id bigint generated by default as identity primary key, title varchar(255))");
            }

            a.setAutoCommit(false);                       // 여기서부터 a의 트랜잭션
            System.out.println("삽입, 생성된 id = " + insert(a, "JDBC"));
            System.out.println("커밋 전: a=" + count(a) + "행, b=" + count(b) + "행");

            a.rollback();
            System.out.println("롤백 후: a=" + count(a) + "행, b=" + count(b) + "행");

            System.out.println("삽입, 생성된 id = " + insert(a, "JDBC"));
            a.commit();
            System.out.println("커밋 후: a=" + count(a) + "행, b=" + count(b) + "행");
        }
    }

    static long insert(Connection con, String title) throws SQLException {
        try (PreparedStatement ps = con.prepareStatement(
                "insert into book(title) values(?)", Statement.RETURN_GENERATED_KEYS)) {
            ps.setString(1, title);
            ps.executeUpdate();
            try (ResultSet keys = ps.getGeneratedKeys()) {
                keys.next();
                return keys.getLong(1);
            }
        }
    }

    static int count(Connection con) throws SQLException {
        try (Statement st = con.createStatement();
             ResultSet rs = st.executeQuery("select count(*) from book")) {
            rs.next();
            return rs.getInt(1);
        }
    }
}

삽입, 생성된 id = 2

    한 줄씩 읽자. setAutoCommit(false)를 부르면 그 커넥션의 문장들은 commit()이나 rollback()이 불릴 때까지 한 트랜잭션으로 묶인다. 둘째 줄에서 a는 자기가 넣은 행을 보지만 b는 보지 못한다. 커밋되지 않은 변경은 그 변경을 만든 커넥션의 것이다. 셋째 줄에서 롤백하자 a에서도 행이 사라졌다. 다섯째 줄에서 커밋한 뒤에야 b가 그 행을 본다.

    넷째 줄도 지나치면 안 된다. 롤백으로 첫 행은 없던 일이 되었는데 다음에 받은 id는 1이 아니라 2다. 이 실행에서 DB는 행의 변경은 되돌렸지만 한 번 발급한 식별자 번호는 되돌리지 않았다. 뒤에서 테스트를 다룰 때 이 사실이 다시 나온다.

    이 실험의 결론은 한 문장이다. 트랜잭션은 커넥션(세션)에 속한다. JDBC에는 "트랜잭션 객체"가 따로 없다. 커밋과 롤백은 Connection의 메서드이고, 어떤 SQL이 같은 트랜잭션에 속하는지는 같은 커넥션으로 실행되었는지로 정해진다.

    그러면 문제가 생긴다. 서비스 메서드 하나가 저장소 메서드를 두 번 부르고, 두 변경이 함께 성공하거나 함께 취소되어야 한다고 하자. 앞에서 만든 JdbcBookRepository는 메서드마다 dataSource.getConnection()을 부른다. 풀은 그때마다 쉬고 있는 커넥션 가운데 하나를 내주므로 두 호출이 같은 커넥션을 쓴다는 보장이 없고, 설령 같더라도 메서드가 끝날 때마다 자동 커밋으로 이미 반영되어 있다. 두 번째 호출이 실패해도 첫 번째 변경은 남는다.

    두 호출이 같은 커넥션을 쓰게 하는 가장 단순한 방법은 서비스가 커넥션을 얻어 저장소 메서드의 파라미터로 넘기는 것이다. 동작은 하지만 서비스 코드가 JDBC에 묶이고 모든 저장소 메서드의 시그니처에 커넥션이 끼어든다. 스프링은 다른 방법을 쓴다. 스프링 문서에 따르면 DataSourceTransactionManager는 DataSource에서 얻은 JDBC Connection을 현재 실행 중인 스레드에 묶어 둔다. 데이터 접근 코드는 커넥션을 파라미터로 받는 대신 "지금 이 스레드에 묶인 커넥션"을 조회한다. 그 조회 창구가 DataSourceUtils.getConnection(DataSource)다.

    스레드에 묶는다는 것은 ThreadLocal에 넣어 둔다는 뜻이다. ThreadLocal은 스레드마다 따로 값을 갖는 변수다. 웹 요청 하나는 하나의 스레드가 컨트롤러에서 서비스, 저장소까지 차례로 호출하며 처리하므로, 스레드에 붙여 둔 값은 파라미터로 넘기지 않아도 호출 사슬의 어디에서나 꺼낼 수 있다. 다음 실험으로 확인한다.

    import java.sql.Connection;
import org.h2.jdbcx.JdbcDataSource;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.datasource.DataSourceTransactionManager;
import org.springframework.jdbc.datasource.DataSourceUtils;
import org.springframework.transaction.support.TransactionSynchronizationManager;
import org.springframework.transaction.support.TransactionTemplate;

public class SyncDemo {
    public static void main(String[] args) throws Exception {
        JdbcDataSource ds = new JdbcDataSource();          // 풀 없이 매번 새 커넥션을 만드는 DataSource
        ds.setURL("jdbc:h2:mem:sync;DB_CLOSE_DELAY=-1");
        ds.setUser("sa");
        JdbcTemplate jdbc = new JdbcTemplate(ds);
        jdbc.execute("create table book (id bigint primary key, title varchar(255))");

        System.out.println("[트랜잭션 밖]");
        Connection c1 = DataSourceUtils.getConnection(ds);
        Connection c2 = DataSourceUtils.getConnection(ds);
        System.out.println("  같은 커넥션인가: " + (c1 == c2));
        System.out.println("  스레드에 묶인 커넥션이 있는가: " + TransactionSynchronizationManager.hasResource(ds));
        DataSourceUtils.releaseConnection(c1, ds);
        DataSourceUtils.releaseConnection(c2, ds);
        System.out.println("  release 뒤 닫혔는가: " + c1.isClosed() + ", " + c2.isClosed());

        TransactionTemplate tx = new TransactionTemplate(new DataSourceTransactionManager(ds));
        System.out.println("[트랜잭션 안]");
        try {
            tx.executeWithoutResult(status -> {
                Connection a = DataSourceUtils.getConnection(ds);
                Connection b = DataSourceUtils.getConnection(ds);
                System.out.println("  같은 커넥션인가: " + (a == b));
                System.out.println("  스레드에 묶인 커넥션이 있는가: " + TransactionSynchronizationManager.hasResource(ds));
                DataSourceUtils.releaseConnection(a, ds);
                DataSourceUtils.releaseConnection(b, ds);
                System.out.println("  release 뒤 닫혔는가: " + isClosed(a));

                jdbc.update("insert into book values (1, 'JDBC')");
                jdbc.update("insert into book values (2, 'JPA')");
                System.out.println("  이 스레드가 센 행 수: " + count(jdbc));

                Thread other = new Thread(() -> System.out.println(
                        "  다른 스레드: 묶인 커넥션 " + TransactionSynchronizationManager.hasResource(ds)
                                + ", 센 행 수 " + count(jdbc)));
                other.start();
                join(other);

                throw new IllegalStateException("일부러 낸 예외");
            });
        } catch (IllegalStateException e) {
            System.out.println("  예외: " + e.getMessage());
        }
        System.out.println("[트랜잭션이 끝난 뒤] 행 수: " + count(jdbc));
    }

    static Integer count(JdbcTemplate jdbc) {
        return jdbc.queryForObject("select count(*) from book", Integer.class);
    }

    static boolean isClosed(Connection con) {
        try { return con.isClosed(); } catch (java.sql.SQLException e) { throw new IllegalStateException(e); }
    }

    static void join(Thread t) {
        try { t.join(); } catch (InterruptedException e) { throw new IllegalStateException(e); }
    }
}

    트랜잭션 밖에서는 DataSourceUtils.getConnection이 부를 때마다 새 커넥션을 내주고, releaseConnection은 그것을 실제로 닫는다. 평범한 getConnection()과 close()와 다를 바 없다. 트랜잭션 안에서는 달라진다. 두 번 불러도 같은 객체가 나오고, releaseConnection을 불러도 닫히지 않는다. 트랜잭션 매니저가 시작할 때 커넥션 하나를 얻어 자동 커밋을 끄고 스레드에 묶어 두었고, 트랜잭션이 끝날 때 자기가 커밋이나 롤백을 한 뒤 닫을 것이기 때문이다. 같은 실험에서 트랜잭션 안의 커넥션에 getAutoCommit()을 물으면 false가 나온다.

    JdbcTemplate으로 넣은 두 행은 같은 스레드에서는 보이고, 예외로 트랜잭션이 롤백되자 함께 사라졌다. JdbcTemplate에 커넥션을 넘긴 적이 없는데도 같은 트랜잭션에 들어간 것이다. 스프링 문서는 JdbcTemplate 같은 프레임워크 클래스가 모두 이 방식(DataSourceUtils를 통한 조회)을 내부에서 쓴다고 적는다. 반면 트랜잭션 도중에 새로 띄운 스레드에는 묶인 커넥션이 없다. 그 스레드의 조회는 별도의 커넥션으로 실행되었고, 커밋되지 않은 두 행을 보지 못해 0을 셌다.

    static Book saveAware(DataSource dataSource, Book book) {
    String sql = "insert into book(title) values(?)";
    Connection con = DataSourceUtils.getConnection(dataSource);      // 스레드에 묶인 커넥션이 있으면 그것을 받는다
    try (PreparedStatement ps = con.prepareStatement(sql, Statement.RETURN_GENERATED_KEYS)) {
        ps.setString(1, book.getTitle());
        ps.executeUpdate();
        try (ResultSet keys = ps.getGeneratedKeys()) {
            keys.next();
            book.setId(keys.getLong(1));
        }
        return book;
    } catch (SQLException e) {
        throw new IllegalStateException(e);
    } finally {
        DataSourceUtils.releaseConnection(con, dataSource);          // 트랜잭션 중이면 닫지 않는다
    }
}

    직접 얻은 커넥션으로 넣은 행은 롤백되지 않고 남았다. 그 커넥션은 트랜잭션 매니저가 모르는 별개의 세션이었고 자동 커밋으로 이미 반영되었기 때문이다. 고친 메서드에서 커넥션을 try-with-resources에 넣지 않고 finally에서 releaseConnection으로 돌려주는 점도 봐 두자. 스레드에 묶인 커넥션을 저장소가 close()로 닫아 버리면 진행 중인 트랜잭션의 커넥션이 중간에 사라진다. 스프링의 트랜잭션에 참여하려면 얻을 때도 돌려줄 때도 스프링의 창구를 거쳐야 한다.

    이 장치 위에 선언적 트랜잭션이 올라간다. 클래스나 메서드에 @Transactional을 붙이면 스프링은 그 빈을 프록시로 감싸고, 프록시가 메서드 호출 앞에서 트랜잭션을 시작하고 뒤에서 커밋하거나 롤백한다. 스프링 문서는 이 지원이 AOP 프록시로 이루어지며 프록시가 TransactionInterceptor와 트랜잭션 매니저를 써서 메서드 호출 둘레에서 트랜잭션을 운전한다고 설명한다. 기본 설정에서 롤백을 일으키는 것은 RuntimeException과 Error이고, 체크 예외는 롤백을 일으키지 않는다. 프록시가 어떻게 만들어지고 끼어드는지는 다음 회차의 주제다.

    트랜잭션 매니저가 풀에서 빌린 커넥션을 스레드의 보관함에 넣어 두고, 같은 스레드에서 실행되는 저장소 호출들이 그 커넥션을 꺼내 쓰며, 다른 스레드는 그것을 보지 못한다는 것을 보여 준다. 흰 배경의 구조 다이어그램. 왼쪽에 세로로 긴 둥근 사각형 두 개가 나란히 있다. 첫째 사각형의 위쪽 라벨은 "요청 스레드 A", 둘째는 "요청 스레드 B". 스레드 A 안에는 위에서 아래로 세 개의 작은 상자가 세로 화살표로 이어져 있다: "서비스 메서드", "저장소 save", "저장소 findAll". 스레드 A 사각형의 오른쪽 위 모서리에 사물함 모양의 작은 상자가 붙어 있고 라벨은 "스레드 보관함". 보관함 안에 주황색 플러그 아이콘 하나. "저장소 save"와 "저장소 findAll" 상자에서 각각 보관함의 주황 플러그로 가는 점선 화살표 두 개, 화살표 옆에 "같은 커넥션". 스레드 B 안에는 상자 하나 "다른 요청"이 있고, 스레드 B의 보관함은 비어 있으며 라벨 "비어 있음". 화면 오른쪽에는 가로로 긴 상자 "커넥션 풀"이 있고 안에 플러그 아이콘 세 개가 있다. 그중 하나는 주황색으로 칠해져 있고 스레드 A의 보관함과 굵은 주황 선으로 연결되어 있으며 선 위에 "트랜잭션 동안 대여". 나머지 두 플러그는 회색. 풀 오른쪽에 원통 모양 DB 아이콘이 있고 플러그 세 개에서 원통으로 가는 얇은 선. 화면 아래 가운데에 작은 글씨 "커밋·롤백은 이 커넥션에서 한 번". 평면적인 기술 도해 스타일, 차분한 파랑과 회색에 묶인 커넥션만 주황으로 강조. 트랜잭션이 시작되면 커넥션 하나가 스레드에 묶이고, 그 스레드에서 실행되는 데이터 접근 코드는 모두 그 커넥션을 쓴다. 그래서 커밋이나 롤백 한 번으로 전부가 함께 처리된다.

    구현을 갈아 끼우는 자리: 인터페이스와 설정 한 곳

    저장 기술을 넷이나 바꿔 가며 볼 수 있는 것은 서비스가 구현 클래스가 아니라 BookRepository 인터페이스에만 의존하기 때문이다. 어떤 구현을 쓸지는 객체를 조립하는 한 곳에서만 정한다. 앞 회차에서 다룬 스프링 빈 등록과 의존관계 주입이 여기서 값을 한다.

    public class BookService {
    private final BookRepository bookRepository;

    public BookService(BookRepository bookRepository) {
        this.bookRepository = bookRepository;
    }

    public Long register(Book book) {
        bookRepository.save(book);
        return book.getId();
    }
}
    import javax.sql.DataSource;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class AppConfig {
    private final DataSource dataSource;

    public AppConfig(DataSource dataSource) {

    생성자의 DataSource는 스프링 부트가 설정 파일의 접속 정보로 만들어 등록해 둔 빈이다. 구현을 바꿀 때 고치는 것은 bookRepository()의 한 줄이고 BookService는 다시 컴파일할 필요도 없다. 기능을 확장할 때 기존 코드를 고치지 않아도 되게 설계하라는 원칙을 개방-폐쇄 원칙(OCP, Open-Closed Principle)이라고 부르는데, 인터페이스에 의존하고 조립을 바깥에서 하는 구조가 그것을 가능하게 한다.

    다만 이 교체가 언제나 투명한 것은 아니다. 인터페이스의 시그니처가 같아도 구현마다 지켜 주는 약속이 다를 수 있다. 방금 본 것처럼 커넥션을 직접 얻는 구현은 스프링 트랜잭션에 참여하지 않는다. 뒤에서 볼 JPA 구현은 조회한 객체의 필드를 바꾸기만 해도 DB에 반영되지만 JDBC 구현에서는 아무 일도 일어나지 않는다. 구현을 바꾼 뒤에 실제 DB까지 연결해서 확인하는 테스트가 필요한 이유다.

    스프링 통합 테스트: 컨테이너와 DB까지 함께 띄우기

    자바 객체를 new로 만들어 메서드를 호출하고 결과를 확인하는 테스트는 빠르고 원인을 좁히기 쉽다. 이런 테스트를 단위 테스트(unit test)라고 한다. 그런데 DB 접근 코드는 단위 테스트만으로는 확인할 수 없는 것이 많다. SQL 문법이 맞는지, 열 이름이 테이블과 일치하는지, 설정 파일의 접속 정보로 커넥션이 얻어지는지, 스프링이 빈을 실제로 조립할 수 있는지는 실제 컨테이너와 실제 DB가 있어야 드러난다. 여러 부품을 실제로 연결해 놓고 검증하는 테스트를 통합 테스트(integration test)라고 한다.

    import static org.assertj.core.api.Assertions.assertThat;

import org.junit.jupiter.api.Test;
import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.boot.test.context.SpringBootTest;
import org.springframework.transaction.annotation.Transactional;

@SpringBootTest
@Transactional
class BookServiceIntegrationTest {

    @Autowired BookService bookService;
    @Autowired BookRepository bookRepository;

    @Test
    void 등록한_도서를_다시_찾는다() {
        Long id = bookService.register(new Book("JDBC"));

        Book found = bookRepository.findById(id).orElseThrow();

        assertThat(found.getTitle()).isEqualTo("JDBC");
    }
}

    @SpringBootTest가 하는 일

    스프링 부트 문서에 따르면 @SpringBootTest는 테스트에 쓸 ApplicationContext를 SpringApplication을 통해 만든다. 애플리케이션을 실제로 띄울 때와 같은 경로로 컨테이너를 구성한다는 뜻이다. 설정 클래스를 따로 지정하지 않으면 테스트 클래스가 속한 패키지에서 위로 올라가며 @SpringBootApplication이나 @SpringBootConfiguration이 붙은 클래스를 찾는다. 그렇게 만들어진 컨테이너에서 빈을 꺼내 테스트 클래스의 @Autowired 필드에 넣어 준다. 테스트는 운영 코드와 같은 빈 조립, 같은 DataSource 설정을 거친 객체를 대상으로 실행된다.

    컨테이너를 만드는 일은 클래스 스캔, 빈 생성, 커넥션 풀 초기화를 포함하므로 단위 테스트보다 오래 걸린다. 부트 문서는 스프링 테스트 프레임워크가 애플리케이션 컨텍스트를 테스트 사이에 캐시하므로, 설정이 같은 테스트들은 컨텍스트 로딩을 한 번만 겪는다고 밝힌다. 그래도 DB까지의 왕복이 있으므로 단위 테스트만큼 빠를 수는 없다. 로직은 단위 테스트로 촘촘히 검증하고, 통합 테스트는 연결 지점이 맞물리는지를 확인하는 데 쓰는 편이 전체 테스트 시간을 지키는 길이다.

    테스트의 @Transactional은 왜 롤백하는가

    메모리 저장소를 쓰는 테스트는 실행이 끝나면 데이터가 사라진다. DB는 프로세스 밖의 상태이므로 그렇지 않다. 테스트가 넣은 행은 다음 테스트 메서드에도, 내일 다시 돌리는 테스트에도 남아 있다. 제목이 중복되면 실패하는 로직을 테스트한다면 두 번째 실행에서 지난번에 넣은 행 때문에 엉뚱하게 실패한다. 테스트는 몇 번을 어떤 순서로 돌려도 결과가 같아야 하므로, 테스트가 DB에 남긴 흔적을 매번 지워야 한다.

    테스트 클래스에 붙인 @Transactional이 이 일을 한다. 스프링 문서에 따르면 테스트 메서드에 이 애너테이션을 붙이면 테스트가 트랜잭션 안에서 실행되고, 그 트랜잭션은 기본적으로 테스트가 끝난 뒤 자동으로 롤백된다. 스프링은 이것을 테스트가 관리하는 트랜잭션(test-managed transaction)이라고 부른다. 운영 코드의 @Transactional이 정상 종료 시 커밋하는 것과 방향이 반대다. 커밋하게 하고 싶으면 @Commit이나 @Rollback으로 바꿀 수 있다.

    어떻게 테스트의 롤백이 서비스와 저장소가 한 일까지 지울 수 있는지는 앞 절에서 이미 답이 나왔다.

    서비스에 @Transactional이 붙어 있어도 결과는 같다. 서비스의 프록시가 트랜잭션을 시작하려는 시점에 이미 스레드에 진행 중인 트랜잭션이 있으므로 새로 만들지 않고 거기에 참여한다. 서비스 메서드가 정상 종료해도 커밋은 일어나지 않고, 테스트가 끝날 때의 롤백에 함께 쓸려 간다.

    롤백 테스트가 지켜 주지 않는 것

    이 방식은 편리하지만 원리를 모르면 속기 쉬운 경계가 넷 있다. 모두 "트랜잭션은 스레드에 묶인 커넥션 하나"라는 사실에서 나온다.

    • 다른 스레드에서 실행된 코드는 롤백되지 않는다. 스프링 문서는 테스트 지원이 트랜잭션 상태를 ThreadLocal로 현재 스레드에 묶으므로, 테스트 프레임워크가 선점형 타임아웃을 위해 테스트 메서드를 새 스레드에서 실행하면 그 안의 작업은 테스트 트랜잭션에 속하지 않고 그대로 커밋된다고 경고한다. 부트 문서도 @SpringBootTest를 RANDOM_PORT나 DEFINED_PORT로 실행하면 HTTP 클라이언트와 서버가 다른 스레드, 다른 트랜잭션에서 돌기 때문에 서버 쪽에서 시작된 트랜잭션은 롤백되지 않는다고 적는다.
    • 스프링의 창구를 거치지 않은 커넥션도 롤백되지 않는다. 앞 절에서 dataSource.getConnection()을 직접 부른 저장소의 행이 남았던 것과 같은 이유다.
    • 식별자 번호는 되돌아가지 않을 수 있다. 앞의 실험에서 롤백 뒤에 받은 id는 2였다. 테스트에서 "방금 저장한 도서의 id는 1이다"처럼 생성된 키의 값을 단정하면 두 번째 실행부터 실패한다. 저장이 돌려준 id로 다시 조회하는 식으로 써야 한다.
    • 실행되지 않은 SQL은 검증되지 않는다. 뒤에서 볼 JPA는 SQL 실행을 미룬다. 스프링 문서는 영속성 컨텍스트의 상태를 바꾸는 코드를 테스트할 때 테스트 안에서 플러시하지 않으면 거짓 양성(false positive)이 생길 수 있다고 경고한다. 테스트는 통과했는데 같은 코드가 운영에서는 예외를 던지는 상황이다.

    마지막으로 운영과 트랜잭션의 범위가 다르다는 점도 기억해 둔다. 운영에서는 서비스 메서드가 끝날 때 커밋이 일어나고 그 뒤의 코드는 트랜잭션 밖에서 돈다. 테스트에서는 테스트 메서드 전체가 한 트랜잭션이다. 커밋 시점에야 드러나는 문제나 트랜잭션이 끝난 뒤에야 드러나는 문제는 롤백 테스트에서 보이지 않을 수 있다.

    스프링 JdbcTemplate: 반복을 템플릿으로 접기

    순수 JDBC 저장소에서 메서드마다 달라지는 것은 SQL, 파라미터, 행을 객체로 옮기는 방법 세 가지였다. 달라지지 않는 흐름을 한 곳에 고정해 두고 달라지는 부분만 바깥에서 받아 끼우는 설계를 템플릿 콜백(template callback) 패턴이라고 한다. JdbcTemplate이 그 템플릿이다. 스프링 문서는 이 클래스가 SQL 질의와 갱신을 실행하고, ResultSet을 순회하며, JDBC 예외를 잡아 org.springframework.dao 패키지의 예외 계층으로 변환한다고 정리한다.

    import java.util.List;
import java.util.Map;
import java.util.Optional;
import javax.sql.DataSource;
import org.springframework.jdbc.core.JdbcTemplate;
import org.springframework.jdbc.core.RowMapper;
import org.springframework.jdbc.core.simple.SimpleJdbcInsert;

public class JdbcTemplateBookRepository implements BookRepository {
    private final JdbcTemplate jdbcTemplate;
    private final SimpleJdbcInsert insert;

    private final RowMapper bookMapper = (rs, rowNum) -> {
        Book book = new Book(rs.getString("title"));
        book.setId(rs.getLong("id"));
        return book;
    };

    public JdbcTemplateBookRepository(DataSource dataSource) {
        this.jdbcTemplate = new JdbcTemplate(dataSource);
        this.insert = new SimpleJdbcInsert(dataSource)
                .withTableName("book")
                .usingGeneratedKeyColumns("id");
    }

    @Override
    public Book save(Book book) {
        Number key = insert.executeAndReturnKey(Map.of("title", book.getTitle()));
        book.setId(key.longValue());
        return book;
    }

    @Override
    public Optional findById(Long id) {
        List result = jdbcTemplate.query(
                "select id, title from book where id = ?", bookMapper, id);
        return result.stream().findFirst();
    }

    @Override
    public List findAll() {
        return jdbcTemplate.query("select id, title from book order by id", bookMapper);
    }
}

    순수 JDBC 구현과 나란히 놓고 보면 사라진 것이 분명하다. Connection, PreparedStatement, ResultSet을 얻고 닫는 코드가 없고, try와 catch가 없고, while (rs.next()) 반복문이 없다. 남은 것은 SQL 문자열, ?에 들어갈 인자(id), 그리고 RowMapper다. 정확히 "메서드마다 달라지는 세 가지"만 남았다.

    RowMapper는 결과의 한 행을 객체 하나로 바꾸는 함수다. 람다의 첫 번째 인자 rs는 이미 해당 행에 위치한 ResultSet이므로 람다 안에서 next()를 부르지 않는다. 커서를 움직이고 반환값을 리스트에 모으는 일은 템플릿이 한다. findById와 findAll이 같은 bookMapper를 함께 쓰는 것도 볼 만하다. 순수 JDBC에서 두 번 적었던 매핑 코드가 한 곳으로 모였다.

    save에 쓴 SimpleJdbcInsert는 INSERT 문까지 대신 만들어 준다. 테이블 이름과 DB가 키를 만들어 주는 열을 알려 주면, JDBC 드라이버로 조회한 테이블 메타데이터와 넘겨받은 맵의 키를 맞춰 INSERT 문을 구성하고 생성된 키를 돌려준다. 순수 JDBC에서 RETURN_GENERATED_KEYS와 getGeneratedKeys()로 했던 일이 그 안에 들어 있다.

    title 열에 유일 제약(unique)을 걸어 테이블을 만든 뒤, 같은 제목을 두 번 저장하고 이어서 열 이름을 틀리게 쓴 질의를 실행해 보았다. 던져진 예외의 타입과 그 원인(cause)을 찍었다.

}

    세 가지가 달라졌다. 첫째, 예외가 언체크 예외다. 저장소도 서비스도 throws SQLException을 적을 필요가 없다. 둘째, 예외의 타입이 원인을 말해 준다. 키 중복은 DuplicateKeyException, 잘못된 SQL은 BadSqlGrammarException이다. 서비스가 "이미 있는 제목"이라는 상황만 골라 처리하고 싶다면 그 타입만 잡으면 된다. 셋째, 이 타입들은 스프링의 것이므로 서비스 코드가 H2나 JDBC의 클래스에 의존하지 않는다. 원래의 드라이버 예외는 getCause()에 그대로 보존되어 있어 정보가 사라지지도 않는다.

    이 변환을 맡는 것이 SQLExceptionTranslator다. 스프링 문서에 따르면 6.0부터 기본 번역기는 SQLExceptionSubclassTranslator로, JDBC 4의 SQLException 하위 클래스를 보고 분류하며 그것으로 판단하지 못하면 SQLState 값을 본다. 출력의 원인 타입이 그 분류의 근거다. H2 드라이버가 던진 두 예외는 각각 JDBC 표준 예외인 java.sql.SQLIntegrityConstraintViolationException과 java.sql.SQLSyntaxErrorException의 하위 클래스다. 드라이버가 오류의 종류를 표준 타입으로 알려 주고, 스프링이 그것을 기술에 묶이지 않은 자기 예외 계층으로 옮겨 적는 구조다. 함께 찍힌 SQLState는 오류의 종류를 나타내는 다섯 글자 코드다.

    JdbcTemplate은 한 번 구성되면 스레드 안전하다고 문서가 명시한다. DataSource에 대한 참조만 들고 있을 뿐 호출 사이에 이어지는 대화 상태가 없기 때문이다. 그래서 인스턴스 하나를 싱글톤 빈들이 공유해도 된다. 스프링 부트는 JdbcTemplate과 NamedParameterJdbcTemplate을 자동 구성해 두므로 생성자에서 직접 만들지 않고 주입받아 쓸 수도 있다.

    JdbcTemplate이 가져가지 않은 것도 분명히 해 두자. SQL은 여전히 개발자가 문자열로 쓴다. 열이 하나 추가되면 INSERT, SELECT, RowMapper를 모두 손으로 고쳐야 한다. 객체와 테이블 사이의 번역은 그대로 사람의 일이다. 이 남은 부분을 겨냥한 것이 JPA다.

    JPA: SQL을 쓰는 주체를 바꾸기

    JdbcTemplate까지 와도 저장소에는 같은 종류의 SQL이 계속 쌓인다. 테이블마다 INSERT, id로 찾는 SELECT, 전체 SELECT, UPDATE, DELETE를 쓰고, 열이 바뀌면 그 문장들과 매핑 코드를 함께 고친다. 이 SQL들은 테이블의 구조와 객체의 구조만 알면 기계적으로 만들 수 있는 것들이다. 그렇다면 그 두 구조의 대응 관계를 한 번 선언해 두고 SQL은 도구가 만들게 하면 된다. 이것이 객체 관계 매핑(ORM, Object-Relational Mapping)의 생각이다.

    JPA는 자바 진영의 ORM 표준이다. 정식 이름은 Jakarta Persistence이고, 실체는 인터페이스와 애너테이션, 그리고 그것들이 어떻게 동작해야 하는지를 적은 명세다. JDBC가 인터페이스이고 드라이버가 구현이었던 것과 같은 구도로, JPA 명세를 구현한 제품이 따로 있다. 스프링 부트 문서에 따르면 spring-boot-starter-data-jpa는 Hibernate, 스프링 데이터 JPA, 스프링 ORM을 핵심 의존성으로 가져온다. 스프링 부트 3.x에서 JPA의 타입들은 jakarta.persistence 패키지에 있다.

    매핑을 선언한다

    import jakarta.persistence.Entity;
import jakarta.persistence.GeneratedValue;
import jakarta.persistence.GenerationType;
import jakarta.persistence.Id;

@Entity
public class Book {
    @Id
    @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long id;

    private String title;

    protected Book() {}                      // JPA 구현체가 쓰는 기본 생성자

    public Book(String title) { this.title = title; }

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
}

    @Entity는 이 클래스의 인스턴스 하나가 테이블의 행 하나에 대응한다는 선언이다. 이런 클래스를 엔티티(entity)라고 부른다. @Id는 기본 키에 대응하는 필드를 가리키고, @GeneratedValue(strategy = GenerationType.IDENTITY)는 그 값을 DB의 identity 열이 만든다는 뜻이다. 앞에서 테이블을 generated by default as identity로 만든 것과 짝이 맞는다. 테이블 이름과 열 이름은 따로 지정하지 않았으므로 클래스 이름과 필드 이름에서 정해진다.

    인자 없는 생성자를 추가한 데에는 이유가 있다. 조회 결과로 엔티티를 만들 때 구현체는 먼저 빈 객체를 만들고 필드를 채운다. Hibernate 문서는 엔티티 클래스가 private이 아닌 인자 없는 생성자를 가져야 한다고 적는다. 애플리케이션 코드가 제목 없는 도서를 만들지 못하도록 접근 제한자는 protected로 두었다.

    저장소에서 SQL이 사라진다

    import jakarta.persistence.EntityManager;
import java.util.List;
import java.util.Optional;

public class JpaBookRepository implements BookRepository {
    private final EntityManager em;

    public JpaBookRepository(EntityManager em) {
        this.em = em;
    }

    @Override
    public Book save(Book book) {
        em.persist(book);
        return book;
    }

    @Override
    public Optional findById(Long id) {
        return Optional.ofNullable(em.find(Book.class, id));
    }

    @Override
    public List findAll() {
        return em.createQuery("select b from Book b order by b.id", Book.class)
                .getResultList();
    }
}

    INSERT 문도, RowMapper도, 생성된 키를 되받는 코드도 없다. em.persist(book)이 반환되었을 때 book.getId()에는 DB가 만든 값이 들어 있다. findAll에 있는 문자열은 SQL처럼 보이지만 SQL이 아니다. from Book b의 Book은 테이블 이름이 아니라 엔티티 클래스 이름이고, b.id는 열이 아니라 필드다. 이 질의 언어를 JPQL(Jakarta Persistence Query Language)이라고 하며, 구현체가 매핑 정보를 이용해 해당 DB의 SQL로 번역한다.

    이 코드를 이해하려면 EntityManager가 무엇을 들고 있는지 알아야 한다. JDBC의 Connection처럼 SQL을 보내는 통로라고 생각하면 동작을 예측할 수 없다.

    영속성 컨텍스트: 엔티티를 담아 두는 작업 공간

    EntityManager는 영속성 컨텍스트(persistence context)라는 메모리 공간을 관리한다. Hibernate 문서는 영속성 컨텍스트를 일종의 캐시라고 설명하고(그래서 1차 캐시(first-level cache)라고도 부른다), 이 컨텍스트가 엔티티의 식별자에서 엔티티 인스턴스로 가는 유일한 대응을 유지한다고 적는다. 한 컨텍스트 안에서 같은 식별자를 가진 행은 자바 객체 하나로만 존재한다는 뜻이다. 문서는 또 영속성 컨텍스트의 수명이 보통 트랜잭션의 수명과 같고, 여러 스레드나 동시에 진행되는 트랜잭션 사이에 공유해서는 안 된다고 밝힌다.

    엔티티 객체는 이 컨텍스트와의 관계에 따라 세 가지 상태 가운데 하나에 있다.

    상태뜻예
    비영속(transient)영속성 컨텍스트와 관계를 맺은 적이 없다new Book("JDBC")로 막 만든 객체
    영속(persistent, managed)지금 영속성 컨텍스트가 관리하고 있다persist한 객체, find나 JPQL로 조회한 객체
    준영속(detached)전에 관리되었지만 지금 이 컨텍스트에는 속하지 않는다트랜잭션이 끝난 뒤에도 코드가 들고 있는 객체

    핵심은 영속 상태다. 컨텍스트가 관리하는 객체에 대해서는 JPA 구현체가 객체의 상태와 DB의 행을 맞춰 줄 책임을 진다. 그 맞추는 작업을 플러시(flush)라고 한다. Hibernate 문서에 따르면 플러시는 기본적으로 세 시점에 일어난다. 트랜잭션이 커밋될 때, 메모리에 있는 변경이 결과에 영향을 줄 질의를 실행하기 직전, 그리고 프로그램이 flush()를 직접 부를 때다. 문서는 또 세션의 메서드들이 대개 SQL을 그 자리에서 동기적으로 실행하지 않는다고 밝힌다. persist()의 정의도 "비영속 객체를 영속 상태로 만들고, 나중에 실행할 SQL INSERT를 예약한다"이다.

    변경을 반영하는 방식도 여기서 나온다. Hibernate 문서의 표현으로는 영속 상태의 엔티티를 고쳤을 때 그 변경을 전파하라고 요청하는 명시적 동작이 필요 없고, 변경은 세션이 플러시될 때 자동으로 감지된다. 이것을 변경 감지(dirty checking)라고 한다. JPA에 update 메서드가 없는 이유다.

    한 줄씩 추적하기

    이 규칙들을 서비스 메서드 하나에 적용해 본다. 메서드에는 @Transactional이 붙어 있고 em은 주입받은 EntityManager다.

    List all = em.createQuery("select b from Book b", Book.class)

}                                                              // (6)

    (1)비어 있다. book은 비영속이고 id는 null이다없음
    (2)book이 영속 상태가 되고 id가 채워진다INSERT (IDENTITY 전략이어서 이 시점에 실행)
    (3)그 id의 엔티티가 이미 있으므로 같은 인스턴스를 돌려준다. same == book없음
    (4)메모리의 객체만 바뀐다없음
    (5)질의 전에 플러시: 제목이 바뀐 것을 감지한다UPDATE, 이어서 SELECT
    (6)커밋 전 플러시: 더 반영할 변경이 없다DB 커밋

    (2)에는 설명이 필요하다. persist는 원래 INSERT를 예약만 한다. 그런데 엔티티를 영속성 컨텍스트에 등록하려면 식별자가 있어야 하고, IDENTITY 전략에서는 식별자를 DB가 INSERT를 실행하면서 만든다. Hibernate User Guide는 IDENTITY 열을 쓰면 식별자 값을 알기 전에 엔티티의 행이 물리적으로 먼저 삽입되어야 한다고 적고, 그 결과 이 전략을 쓰는 엔티티의 INSERT는 JDBC 배치로 묶을 수 없다고 덧붙인다. 순수 JDBC에서 "키는 INSERT가 실행된 다음에야 알 수 있다"고 한 사실이 JPA의 동작 시점을 결정한 것이다.

    (3)에서 SQL이 나가지 않는 것은 EntityManager.find가 엔티티가 영속성 컨텍스트에 있으면 거기서 돌려주도록 정의되어 있기 때문이다. (5)에서 SELECT보다 UPDATE가 먼저 나가는 것은 그러지 않으면 질의 결과가 메모리의 상태와 어긋나기 때문이다. 제목을 고친 것은 (4)인데 UPDATE가 실행되는 것은 (5)다. JPA에서는 SQL이 실행되는 시점이 그 SQL을 일으킨 코드의 위치와 다를 수 있다. DB 제약 위반 같은 오류도 원인이 된 줄이 아니라 플러시가 일어나는 줄에서 터진다. 앞에서 본 테스트의 거짓 양성이 여기서 생긴다. 플러시 없이 롤백되는 테스트에서는 UPDATE가 DB에 가 보지도 않고 끝날 수 있다.

    트랜잭션이 없으면 쓸 수 없다

    영속성 컨텍스트의 수명이 트랜잭션과 같다는 것은 JPA로 데이터를 바꾸는 코드가 반드시 트랜잭션 안에서 실행되어야 한다는 뜻이기도 하다. 스프링이 주입해 주는 EntityManager로 트랜잭션 없이 persist를 부르면 TransactionRequiredException이 나고, 메시지는 "No EntityManager with actual transaction available for current thread"로 시작한다. 그래서 JPA를 쓰는 서비스 계층에는 @Transactional이 붙는다.

    그 메시지의 "current thread"라는 말이 단서다. 스프링 문서에 따르면 EntityManagerFactory는 스레드 안전하지만 EntityManager는 그렇지 않다. 그런데 저장소는 싱글톤 빈이고 여러 요청 스레드가 동시에 쓴다. 싱글톤이 스레드 안전하지 않은 객체를 필드로 들고 있어도 되는 이유는, 주입된 것이 진짜 EntityManager가 아니라 공유 EntityManager 프록시이기 때문이다. 문서는 이 프록시가 모든 호출을 현재 트랜잭션의 EntityManager에 위임한다고 설명한다. 커넥션을 스레드에 묶어 두었던 것과 같은 방식으로, 트랜잭션마다 만들어진 실제 EntityManager가 스레드에 묶여 있고 프록시가 호출 때마다 그것을 찾아 넘겨준다.

    맨 아래는 여전히 JDBC다. Hibernate는 SQL을 만든 뒤 같은 DataSource에서 얻은 커넥션으로 실행한다. 커넥션 풀도, 드라이버도, DB가 받는 SQL 문자열이라는 형식도 앞 절들과 같다. 스프링 문서는 JpaTransactionManager가 같은 DataSource에 접근하는 JDBC 코드에도 JPA 트랜잭션을 노출할 수 있다고 적는다. 한 트랜잭션 안에서 JPA와 JdbcTemplate을 함께 쓸 수 있다는 뜻이다. 다만 그때는 플러시되지 않은 변경이 아직 DB에 없다는 점을 스스로 챙겨야 한다.

    Hibernate가 실제로 어떤 SQL을 보내는지는 설정으로 볼 수 있다. 스프링 부트의 spring.jpa.show-sql=true는 실행되는 SQL을 출력하게 한다. spring.jpa.hibernate.ddl-auto는 엔티티 매핑으로부터 테이블을 자동으로 만들지를 정한다. 부트 3.5 문서에 따르면 이 값은 임베디드 DB를 쓰고 스키마 관리 도구가 없을 때 create-drop이, 그 밖에는 none이 기본이다. 직접 만든 테이블을 그대로 쓰려면 none으로 명시해 두는 편이 헷갈리지 않는다.

    spring.jpa.show-sql=true
spring.jpa.hibernate.ddl-auto=none
    persist와 find가 DB가 아니라 영속성 컨텍스트를 상대한다는 것, 엔티티의 필드 변경은 메모리에서만 일어나고 플러시 시점에 한꺼번에 SQL이 된다는 것을 보여 준다. 흰 배경의 가로 흐름 다이어그램. 화면 위쪽에 왼쪽에서 오른쪽으로 긴 화살표 띠가 있고 왼쪽 끝에 "트랜잭션 시작", 오른쪽 끝에 "커밋"이라는 라벨. 띠 아래 가운데에 큰 둥근 사각형이 있고 제목은 "영속성 컨텍스트". 그 안에 표처럼 두 칸이 나란히 있다: 왼쪽 칸에 "id 1", 오른쪽 칸에 책 모양 아이콘과 "Book 객체". 큰 사각형의 왼쪽 바깥에 코드 조각처럼 보이는 작은 상자 세 개가 세로로 놓여 있다: 위부터 "persist", "find", "setTitle". "persist" 상자에서 영속성 컨텍스트 안의 Book 객체로 가는 파란 화살표. "find" 상자와 Book 객체 사이에는 양방향 파란 화살표가 있고 옆에 작은 글씨 "SQL 없음". "setTitle" 상자에서 Book 객체로 가는 점선 화살표가 있고 옆에 "메모리만 변경". 큰 사각형 아래쪽에서 굵은 주황 화살표가 아래로 내려가며 라벨 "플러시". 화살표 끝에는 원통 모양 DB 아이콘이 있고 그 옆에 주황 글씨로 "INSERT · UPDATE". 평면적인 기술 도해 스타일, 차분한 파랑과 회색, 플러시 화살표만 주황으로 강조. JPA 코드는 DB가 아니라 영속성 컨텍스트를 상대한다. 엔티티에 가한 변경은 플러시 시점에 감지되어 SQL로 나간다.

    스프링 데이터 JPA: 구현 클래스가 없는 리포지토리

    JPA 저장소를 몇 개 만들어 보면 또 반복이 보인다. 엔티티 타입만 다를 뿐 save는 persist를 부르고, findById는 find를 부르고, findAll은 조건 없는 JPQL을 실행한다. 특정 필드로 찾는 메서드도 필드 이름만 바뀐 JPQL이다. 스프링 데이터 JPA는 이 저장소 구현 자체를 없앤다. 개발자는 인터페이스만 쓴다.

    import java.util.Optional;
import org.springframework.data.jpa.repository.JpaRepository;

public interface SpringDataBookRepository
        extends JpaRepository, BookRepository {

    Optional findByTitle(String title);
}

    이것이 전부다. 구현 클래스는 어디에도 없다. JpaRepository의 두 타입 인자는 엔티티 타입과 식별자 타입이다. save, findById, findAll은 JpaRepository가 물려받은 인터페이스들에 이미 선언되어 있고 시그니처가 BookRepository의 것과 맞으므로, 이 인터페이스는 BookRepository이기도 하다. 서비스는 고칠 것이 없다. 직접 등록하던 bookRepository() 빈 메서드는 지운다. 스프링 부트 문서에 따르면 자동 구성을 쓰면 자동 구성 패키지에서 리포지토리 인터페이스를 찾아 주므로, 스프링 데이터가 만든 빈이 BookRepository 타입으로 서비스에 주입된다.

    인터페이스에는 실행할 코드가 없다. 그런데 주입된 객체의 메서드를 부르면 동작한다. 누가 구현했는가.

    인터페이스만으로 동작하는 원리: 프록시

    자바에는 실행 중에 "주어진 인터페이스를 구현하는 객체"를 만들어 내는 표준 수단이 있다. JDK 동적 프록시(java.lang.reflect.Proxy)다. 이렇게 만든 객체의 메서드를 호출하면 본문이 실행되는 대신, 어떤 메서드가 어떤 인자로 호출되었는지가 InvocationHandler 하나로 전달된다. 핸들러는 메서드의 이름을 읽을 수 있으므로 이름에 따라 다른 일을 할 수 있다. 이 원리만으로 "메서드 이름에서 질의를 만드는 리포지토리"의 장난감을 만들어 보자. 스프링 데이터의 실제 구현이 아니라 원리를 보기 위한 짧은 코드다.

    import java.lang.reflect.InvocationHandler;
import java.lang.reflect.Proxy;
import java.sql.*;
import java.util.ArrayList;
import java.util.List;

public class MiniRepositoryDemo {
    interface BookFinder {                       // 구현 클래스는 어디에도 없다
        List findByTitle(String title);
        List findByAuthor(String author);
    }

    public static void main(String[] args) throws Exception {
        try (Connection con = DriverManager.getConnection("jdbc:h2:mem:mini", "sa", "")) {
            try (Statement st = con.createStatement()) {
                st.execute("create table book (id bigint primary key, title varchar(255), author varchar(255))");
                st.execute("insert into book values (1, 'JDBC', 'kim'), (2, 'JPA', 'kim'), (3, 'HTTP', 'lee')");
            }

            InvocationHandler handler = (proxy, method, methodArgs) -> {
                String name = method.getName();                          // 예: "findByAuthor"
                if (!name.startsWith("findBy")) {
                    throw new UnsupportedOperationException(name);
                }
                String column = name.substring("findBy".length()).toLowerCase();
                String sql = "select title from book where " + column + " = ? order by id";
                System.out.println(name + " -> " + sql);
                try (PreparedStatement ps = con.prepareStatement(sql)) {
                    ps.setObject(1, methodArgs[0]);
                    try (ResultSet rs = ps.executeQuery()) {
                        List titles = new ArrayList<>();
                        while (rs.next()) {
                            titles.add(rs.getString(1));
                        }
                        return titles;
                    }
                }
            };

            BookFinder finder = (BookFinder) Proxy.newProxyInstance(
                    BookFinder.class.getClassLoader(),
                    new Class[]{BookFinder.class},
                    handler);

            System.out.println("프록시 클래스인가: " + Proxy.isProxyClass(finder.getClass()));
            System.out.println(finder.findByAuthor("kim"));
            System.out.println(finder.findByTitle("HTTP"));
        }
    }
}
    프록시 클래스인가: true
findByAuthor -> select title from book where author = ? order by id
[JDBC, JPA]
findByTitle -> select title from book where title = ? order by id
[HTTP]

    BookFinder를 구현한 클래스를 소스에 쓰지 않았는데 finder.findByAuthor("kim")이 동작했다. 호출은 핸들러로 들어갔고, 핸들러는 메서드 이름 findByAuthor에서 findBy를 떼어 낸 나머지를 열 이름으로 삼아 SQL을 조립했다. 값은 ?로 바인딩했다. 열 이름을 문자열로 이어 붙였지만 그 출처가 사용자 입력이 아니라 소스 코드의 메서드 이름이므로 앞에서 본 인젝션과는 사정이 다르다.

    스프링 데이터 JPA가 하는 일의 뼈대가 이것이다. RepositoryFactorySupport의 Javadoc은 이 팩토리가 설정된 리포지토리 인터페이스를 구현하는 프록시를 만들고, 호출을 질의 실행 인터셉터에 넘기는 어드바이스를 적용한다고 설명한다. 장난감과 다른 점은 셋이다. 첫째, save나 findById처럼 미리 정해진 메서드는 이름을 해석하지 않고 준비된 구현 객체로 넘긴다. 그 기본 구현이 SimpleJpaRepository이고 안에서 EntityManager를 쓴다. 둘째, 이름에서 만드는 것이 SQL이 아니라 JPQL이다. 셋째, 이름을 호출 때마다 해석하는 것이 아니라 리포지토리를 초기화할 때 분석해 둔다.

     서비스 ──▶ 프록시 (SpringDataBookRepository를 구현, 실행 중에 생성)
              │
              ├─ save / findById / findAll ...  ──▶ SimpleJpaRepository ──▶ EntityManager
              │
              └─ findByTitle (이름에서 만든 질의) ──▶ JPQL 실행        ──▶ EntityManager
                                                                         │
                                                              Hibernate ─▶ JDBC ─▶ DB

    메서드 이름이 질의가 되는 규칙

    스프링 데이터 JPA 문서는 findByEmailAddressAndLastname이라는 메서드가 select u from User u where u.emailAddress = ?1 and u.lastname = ?2라는 JPQL로 번역된다는 예를 든다. 같은 규칙으로 위의 findByTitle(String title)은 select b from Book b where b.title = ?1이 된다. findBy 뒤의 부분을 엔티티의 속성 이름과 키워드로 쪼개어 조건을 만든다. 문서의 키워드 표에서 몇 줄을 옮기면 다음과 같다.

    키워드메서드 이름 예만들어지는 JPQL 조건
    AndfindByLastnameAndFirstname… where x.lastname = ?1 and x.firstname = ?2
    OrfindByLastnameOrFirstname… where x.lastname = ?1 or x.firstname = ?2
    BetweenfindByStartDateBetween… where x.startDate between ?1 and ?2
    LessThanfindByAgeLessThan… where x.age < ?1
    OrderByfindByAgeOrderByLastnameDesc… where x.age = ?1 order by x.lastname desc

    이름이 곧 질의이므로 이름을 틀리면 질의가 틀린다. 다행히 그 오류는 일찍 드러난다. 스프링 데이터 JPA 문서에 따르면 리포지토리 빈은 기본적으로 즉시 초기화되고, 기동 중에 이미 검증과 메타데이터 분석을 위해 EntityManager와 상호작용한다. 메서드 이름이 가리키는 속성이 엔티티에 없으면 그 메서드를 처음 호출할 때가 아니라 애플리케이션이 뜨는 도중에 실패한다. 문자열로 쓴 SQL의 오타가 실행해 봐야 드러나던 것과 대비된다.

    물려받는 것들

     Repository                      표식(marker) 인터페이스
   ├─ CrudRepository             save, findById, findAll, count, delete ...
   │    └─ ListCrudRepository    같은 메서드, 반환 타입이 Iterable 대신 List
   └─ PagingAndSortingRepository 페이징과 정렬을 받는 findAll
        └─ ListPagingAndSortingRepository

 JpaRepository  =  ListCrudRepository + ListPagingAndSortingRepository + QueryByExampleExecutor
                          + flush, saveAndFlush 등 JPA에 특화된 메서드

    계층의 위쪽 인터페이스들(Repository, CrudRepository 등)은 스프링 데이터 공통 모듈에 있고 JPA가 아닌 저장 기술에서도 똑같이 쓰인다. JpaRepository는 그 위에 JPA에만 의미가 있는 메서드를 더한 것이다. 위 그림은 스프링 데이터 JPA 3.x 이후의 구조다.

    물려받은 save의 동작은 이름에서 짐작하는 것보다 조금 복잡하다. 문서에 따르면 save는 엔티티가 아직 저장된 적이 없으면 entityManager.persist를, 그렇지 않으면 entityManager.merge를 부른다. 새 엔티티인지는 기본적으로 식별자 속성을 보고 판단하며(버전 속성이 없을 때), 식별자가 null이면 새것으로 본다. Book은 id가 Long이고 DB가 값을 만들므로 막 생성한 객체는 id가 null이고, save는 persist로 이어진다.

    트랜잭션도 물려받는다. 문서에 따르면 CrudRepository에서 온 메서드들은 SimpleJpaRepository의 트랜잭션 설정을 따르는데, 읽기 메서드에는 readOnly가 true로 설정되어 있고 나머지에는 @Transactional이 붙어 있다. 그래서 서비스에 트랜잭션이 없어도 save 한 번은 자기 트랜잭션 안에서 실행된다. 서비스에 이미 트랜잭션이 있으면 리포지토리는 거기에 참여하고, 문서의 표현대로 바깥 트랜잭션의 설정이 실제로 쓰이는 설정이 된다. 여러 리포지토리 호출을 하나로 묶는 경계는 여전히 서비스에 둔다.

    스프링 데이터 JPA가 가져가지 않는 것도 짚어 둔다. 메서드 이름으로 표현할 수 있는 것은 조건을 나열하는 정도의 질의다. 이름이 지나치게 길어지거나 조건이 실행 중에 달라지는 질의는 JPQL을 직접 쓰거나 다른 도구를 붙여야 하고, 그 내용은 로드맵 뒤쪽의 JPA와 Querydsl 권에서 다룬다. 그리고 이 기술은 JPA를 감싼 것이지 대신하는 것이 아니다. 프록시 뒤에는 EntityManager가 있고, 영속성 컨텍스트와 플러시와 변경 감지는 앞 절에서 본 그대로 동작한다.

    개발자가 쓴 것은 인터페이스뿐이고, 실행 중에 만들어진 프록시가 호출을 받아 미리 정해진 메서드는 SimpleJpaRepository로, 이름으로 선언한 메서드는 이름에서 만든 JPQL 실행으로 보낸다는 것을 보여 준다. 흰 배경의 구조 다이어그램. 왼쪽에 사람 아이콘과 그 옆의 문서 모양 상자 하나. 문서 상자의 라벨은 "인터페이스 선언"이고 안에 작은 글씨 두 줄 "save" 와 "findByTitle". 문서 상자에서 오른쪽으로 점선 화살표가 나가 가운데의 큰 육각형을 가리키며 화살표 위에 "실행 중에 생성". 가운데 육각형의 라벨은 "프록시". 육각형 왼쪽 위에서 들어오는 실선 화살표가 있고 출발점에는 작은 상자 "서비스". 육각형에서 오른쪽으로 두 갈래 화살표가 갈라진다. 위쪽 갈래의 끝에는 파란 상자 "SimpleJpaRepository"가 있고 화살표 위에 "save · findById". 아래쪽 갈래의 끝에는 초록 상자 "이름에서 만든 JPQL"이 있고 화살표 위에 "findByTitle". 두 상자에서 다시 오른쪽으로 화살표가 모여 세로로 긴 회색 상자 "EntityManager"로 들어간다. 그 오른쪽에 원통 모양 DB 아이콘이 있고 EntityManager에서 DB로 가는 화살표 위에 "SQL". 평면적인 기술 도해 스타일, 차분한 파랑·초록·회색, 프록시 육각형만 주황 테두리로 강조. 리포지토리 인터페이스의 구현은 실행 중에 만들어지는 프록시다. 프록시 뒤에는 EntityManager를 쓰는 기본 구현과 메서드 이름에서 만든 질의가 있다.

    기술개발자가 쓰는 것대신 해 주는 것여전히 알아야 하는 것
    순수 JDBCSQL, 바인딩, 매핑, 자원 반납, 예외 처리 전부DB별 통신 규약을 드라이버가 감춘다커넥션 누수, 자동 커밋, 트랜잭션은 커넥션 단위
    JdbcTemplateSQL, 인자, RowMapper커넥션 조회와 반납, 순회, 예외 변환, 트랜잭션 참여SQL과 테이블 구조, 열이 바뀌면 손으로 고칠 곳
    JPA매핑 선언, EntityManager 호출, JPQL기본 SQL 생성, 행과 객체의 변환, 변경 감지영속성 컨텍스트, 플러시 시점, 실제로 나가는 SQL
    스프링 데이터 JPA인터페이스와 메서드 이름저장소 구현, 이름에서 JPQL 생성, 기본 트랜잭션JPA의 모든 것, save의 persist/merge 판단

    표의 마지막 열이 아래로 갈수록 줄어들지 않는다는 점을 보자. 위층은 아래층을 없애지 않는다. 반복해서 쓰던 코드를 대신 써 줄 뿐이고, 그 코드가 하던 일은 그대로 일어난다. 스프링 데이터 JPA의 findAll() 한 줄 뒤에서도 풀에서 커넥션을 빌리고, PreparedStatement를 만들고, ResultSet을 순회하고, 커넥션을 돌려준다. 그래서 문제가 생기면 진단은 언제나 아래층의 말로 한다. 어떤 SQL이 몇 번 나갔는가, 커넥션을 누가 쥐고 있는가, 어느 트랜잭션에 속했는가.

    자주 하는 오해

    • "JPA를 쓰면 SQL을 몰라도 된다." SQL은 사라지지 않고 작성하는 주체가 바뀌었을 뿐이다. DB가 실행하는 것은 여전히 SQL이고, 느린 질의의 원인을 찾으려면 생성된 SQL을 읽어야 한다.
    • "JPA를 쓰면 JdbcTemplate은 쓸 일이 없다." 둘은 위아래가 아니라 나란히 있고, 같은 DataSource와 같은 트랜잭션을 함께 쓸 수 있다. 엔티티 단위로 다루기 어려운 질의는 SQL을 직접 쓰는 편이 나을 때가 있다.
    • "close()는 DB와의 연결을 끊는다." 풀에서 빌린 커넥션의 close()는 반납이다. 반대로 반납을 빠뜨리면 연결이 남는 것이 아니라 풀이 마른다.
    • "@Transactional만 붙이면 그 안의 DB 작업은 모두 한 트랜잭션이다." 스레드에 묶인 커넥션을 쓰는 코드만 그렇다. 직접 얻은 커넥션과 새로 띄운 스레드는 밖에 있다.
    • "롤백 테스트가 통과하면 운영에서도 같게 동작한다." 테스트 트랜잭션은 운영의 트랜잭션보다 넓고, 플러시되지 않은 SQL은 실행조차 되지 않았을 수 있다.
    이 회차의 핵심

    DB 접근 기술의 층은 아래에서 위로 갈수록 개발자가 쓰는 코드가 줄지만, 실행되는 일은 줄지 않는다. 모든 층의 바닥에는 커넥션 하나와 그 위에서 열리고 닫히는 트랜잭션이 있다. 스프링은 그 커넥션을 스레드에 묶어 두어 서비스, 저장소, 테스트가 같은 트랜잭션을 공유하게 하고, 프록시를 써서 그 시작과 끝을 코드 밖으로 빼낸다.

    이 회차에서 프록시가 세 번 나왔다. @Transactional이 붙은 서비스를 감싸 트랜잭션을 여닫는 프록시, 싱글톤 저장소에 주입되어 호출을 현재 트랜잭션의 EntityManager로 넘기는 프록시, 인터페이스뿐인 리포지토리를 구현하는 프록시다. 셋 모두 호출하는 쪽 코드를 바꾸지 않고 호출의 앞뒤나 가는 곳을 바꾼다. 다음 회차는 이 기법을 일반화한 AOP를 다룬다. 여러 메서드에 공통으로 필요한 처리를 핵심 로직에서 떼어 내는 방법과, 스프링이 프록시로 그것을 끼워 넣는 과정을 본다.
    JDBC와 드라이버
    JDK는 Connection, PreparedStatement, ResultSet 같은 인터페이스만 정하고, DB와 실제로 바이트를 주고받는 구현은 벤더의 드라이버가 제공한다. 어떤 데이터 접근 기술을 쓰든 마지막에는 이 인터페이스를 거쳐 SQL 문자열이 DB로 간다.
    H2의 연결 방식
    같은 엔진이 URL에 따라 애플리케이션 JVM 안(임베디드, 인메모리)이나 별도 프로세스(서버 모드)에서 돈다. 임베디드로 연 파일은 다른 프로세스가 열 수 없으므로 애플리케이션과 콘솔이 함께 보려면 서버 모드로 접속한다.
    커넥션 풀
    커넥션을 만들어 두고 빌려주는 DataSource 구현이다. 풀에서 받은 커넥션의 close()는 반납이고, 반납을 빠뜨리면 풀이 비어 이후 요청이 대기하다 실패한다.
    트랜잭션과 커넥션
    트랜잭션은 커넥션에 속한다. 자동 커밋을 끈 커넥션에서 실행한 문장들이 commit()이나 rollback()까지 한 단위가 되고, 커밋 전의 변경은 다른 커넥션에 보이지 않는다.
    스레드에 묶인 커넥션
    스프링의 트랜잭션 매니저는 트랜잭션 동안 커넥션 하나를 현재 스레드에 묶어 둔다. DataSourceUtils를 거치는 코드(JdbcTemplate 포함)는 그 커넥션을 쓰고, 직접 얻은 커넥션이나 다른 스레드는 트랜잭션 밖에 있다.
    통합 테스트와 롤백
    @SpringBootTest는 실제 컨테이너를 띄우고, 테스트의 @Transactional은 테스트 스레드에 묶인 트랜잭션을 끝에서 롤백한다. 다른 스레드의 작업, 발급된 식별자 번호, 플러시되지 않은 SQL은 이 보호의 바깥이다.
    JdbcTemplate
    커넥션 조회와 반납, 결과 순회, 예외 변환을 고정된 흐름으로 가져가고 SQL, 인자, RowMapper만 받는다. SQLException은 원인별 타입을 가진 언체크 예외 DataAccessException으로 바뀐다.
    JPA와 영속성 컨텍스트
    엔티티 매핑을 선언하면 구현체가 SQL을 만든다. 영속성 컨텍스트는 트랜잭션 동안 식별자별로 엔티티 인스턴스 하나를 유지하고, 변경은 플러시 시점에 감지되어 SQL로 나간다.
    스프링 데이터 JPA
    리포지토리 인터페이스를 구현하는 프록시를 실행 중에 만든다. 기본 메서드는 SimpleJpaRepository로, 이름으로 선언한 메서드는 이름에서 만든 JPQL로 처리하며 그 뒤에는 EntityManager가 있다.

    실무에서 다시 판단하면, 이 회차의 지식이 가장 직접 쓰이는 곳은 장애 진단이다. "DB는 정상인데 애플리케이션이 응답하지 않는다"는 증상이 나오면 먼저 커넥션 풀을 의심한다. 풀에서 커넥션을 얻지 못했다는 예외가 로그에 있다면 원인은 둘 중 하나다. 커넥션이 반납되지 않고 새고 있거나, 반납은 되지만 너무 오래 쥐고 있다. 후자는 코드가 멀쩡해 보여서 찾기 어렵다. 트랜잭션이 시작되면 커넥션 하나가 그 스레드에 묶여 트랜잭션이 끝날 때까지 풀로 돌아가지 않는다. 트랜잭션 안에서 외부 시스템을 호출하거나 오래 걸리는 계산을 하면 그 시간 내내 커넥션 하나가 아무 SQL도 실행하지 않은 채 잡혀 있다. 트랜잭션의 범위를 정할 때는 "무엇을 함께 롤백해야 하는가"와 함께 "커넥션을 얼마나 오래 쥐는가"를 같이 본다.

    기술 선택은 하나를 고르는 문제가 아니라 조합의 문제다. 엔티티를 저장하고 식별자로 찾아 고치는 일이 대부분인 애플리케이션에서는 JPA와 스프링 데이터 JPA가 코드와 실수를 함께 줄인다. 반면 여러 테이블을 집계하는 통계성 질의나 대량의 행을 한 번에 넣고 고치는 작업은 엔티티 단위로 생각하는 도구와 잘 맞지 않고, SQL을 직접 쓰는 JdbcTemplate이 더 분명할 수 있다. 두 도구는 같은 DataSource와 같은 트랜잭션을 함께 쓸 수 있으므로 한 프로젝트에 같이 두는 것이 이상한 구성이 아니다. 판단 기준은 익숙함이 아니라, 그 작업에서 SQL을 누가 쓰는 편이 정확한가다. 어느 쪽이든 실행되는 SQL을 읽을 수 있어야 한다는 조건은 달라지지 않는다.

    테스트 전략에서는 편리함과 신뢰도를 저울질한다. H2와 롤백 테스트는 빠르고 설정이 거의 없어 개발 중의 피드백에 좋다. 그러나 H2는 운영 DB와 다른 엔진이고, 롤백 테스트는 운영과 다른 트랜잭션 범위에서 돈다. 방언에 의존하는 SQL, 잠금과 격리 수준에 따라 달라지는 동작, 커밋 시점에야 드러나는 제약 위반은 이 조합으로 걸러지지 않는다. 그런 부분이 중요한 코드라면 운영과 같은 종류의 DB를 띄워 실제로 커밋하는 테스트를 일부라도 두는 쪽으로 판단이 바뀐다. JPA를 쓰는 테스트에서는 검증 전에 플러시를 해서 SQL이 실제로 실행되게 하는 습관이 거짓 양성을 막는다.

HikariCP의 maximumPoolSize 기본값은 10이므로 열 번 호출하면 풀의 커넥션 열 개가 모두 빌려 간 상태로 남는다. 열한 번째 호출은 getConnection()에서 connectionTimeout의 기본값인 30초 동안 블로킹된 뒤 커넥션을 얻지 못했다는 SQLException으로 끝난다. 이때부터는 이 메서드뿐 아니라 같은 풀을 쓰는 모든 코드가 같은 일을 겪는다. 고치는 방법 하나는 세 자원을 try-with-resources로 선언해 어떤 경로로 빠져나가든 닫히게 하는 것이다. 다른 하나는 jdbcTemplate.queryForObject("select count(*) from book", Integer.class)처럼 자원 반납을 템플릿에 맡기는 것이다. 물론 오타도 고쳐야 하지만, 오타 하나가 서비스 전체의 장애로 번지는 구조를 없애는 것이 더 중요하다.

    2. ①은 2, 1, ②는 1, 1이다. b는 자동 커밋 모드이므로 "B"를 넣는 즉시 커밋된다. a는 자동 커밋을 껐으므로 "A"는 커밋되지 않은 채 a의 트랜잭션에만 있다. ①에서 a는 자기가 넣은 "A"와 이미 커밋된 "B"를 모두 보아 2를 세고, b는 커밋된 "B"만 보아 1을 센다. H2의 기본 격리 수준은 커밋된 데이터를 읽는 READ COMMITTED여서 a의 트랜잭션이 진행 중이어도 다른 커넥션이 커밋한 행이 보인다. ②에서 a.rollback()은 a의 트랜잭션에 속한 "A"만 취소한다. "B"는 다른 커넥션의 다른 트랜잭션에서 이미 커밋되었으므로 영향을 받지 않는다. 두 커넥션 모두 1을 센다. 트랜잭션의 단위가 커넥션이라는 사실을 그대로 보여 주는 결과다.

    3. 테스트의 @Transactional은 테스트 메서드 실행 전에 트랜잭션을 시작하면서 커넥션 하나를 테스트 스레드에 묶고, 끝나면 그 커넥션에서 롤백한다. 그런데 저장소는 dataSource.getConnection()을 직접 불렀으므로 스레드에 묶인 커넥션이 아니라 풀에서 새로 빌린 다른 커넥션을 받았다. 그 커넥션은 자동 커밋 모드이므로 INSERT는 실행되자마자 커밋되었다. 테스트 끝의 롤백은 아무 변경도 없는 다른 커넥션에서 일어났으니 지울 것이 없었다. 테스트 본문의 조회도 저장소를 통하면 또 다른 커넥션으로 실행되지만 이미 커밋된 행이므로 보였고, 그래서 테스트는 통과했다. 고치려면 저장소가 DataSourceUtils.getConnection(dataSource)로 커넥션을 얻고 DataSourceUtils.releaseConnection(con, dataSource)로 돌려주게 한다. 커넥션을 try-with-resources에 넣어 직접 close()하면 트랜잭션에 묶인 커넥션을 중간에 닫게 되므로 안 된다. 더 간단한 방법은 저장소를 JdbcTemplate으로 바꾸는 것이다. 템플릿이 이 조회와 반납을 내부에서 한다.

    4. (1)에서 SELECT가 한 번 나간다. 영속성 컨텍스트가 비어 있으므로 DB에서 읽어 와 엔티티를 만들고 컨텍스트에 등록한다. (2)에서는 SQL이 나가지 않는다. 식별자 7의 엔티티가 이미 컨텍스트에 있으므로 그 인스턴스를 그대로 돌려준다. (3)은 메모리의 객체만 바꾸므로 SQL이 없다. (4)는 new를 출력한다. a와 b가 같은 객체를 가리키기 때문에 a로 바꾼 제목이 b로 읽힌다. (5)는 true다. 한 영속성 컨텍스트 안에서 식별자 하나에는 인스턴스 하나만 대응한다. (6)에서 메서드가 정상 종료하면 프록시가 커밋을 시도하고, 커밋 전에 플러시가 일어나 제목이 바뀐 것을 감지해 UPDATE를 한 번 실행한 뒤 DB 트랜잭션을 커밋한다. 정리하면 SELECT 한 번, UPDATE 한 번이고 UPDATE가 나가는 시점은 제목을 바꾼 (3)이 아니라 메서드가 끝나는 (6)이다.

    5. JPQL은 select b from Book b where b.title = ?1 or b.id < ?2다. findBy 뒤를 속성과 키워드로 나누면 Title, Or, Id, LessThan이 되고, 키워드가 붙지 않은 속성은 같음 비교가 된다. 파라미터는 선언된 순서대로 ?1, ?2에 들어간다. findByTitel처럼 엔티티에 없는 속성을 가리키는 이름은 리포지토리가 초기화될 때 걸린다. 스프링 데이터 JPA의 리포지토리 빈은 기본적으로 기동 중에 초기화되면서 메서드 이름을 분석해 엔티티의 메타데이터와 맞춰 보기 때문이다. 애플리케이션이 뜨다가 실패하므로 그 코드가 실행되는 경로를 테스트가 지나가지 않아도 오류를 알게 된다. 문자열로 쓴 SQL의 오타는 그 문장이 실제로 DB에 보내질 때에야 예외(BadSqlGrammarException)로 드러나므로, 해당 메서드를 실행하는 테스트가 없으면 운영에서 처음 만날 수 있다.

     스프링 부트 애플리케이션이 jdbc:h2:~/shop으로 DB를 열어 둔 상태에서, 별도로 실행한 H2 콘솔에 같은 URL을 넣어 접속하려 하자 "Database may be already in use" 오류가 났다. 원인과 해결을 바르게 짝지은 것은? 콘솔이 쓰는 8082 포트를 애플리케이션이 먼저 차지했기 때문이다. 콘솔의 포트를 바꾼다. 임베디드 모드에서는 엔진이 각 프로세스 안에서 돌며 파일을 직접 여는데, 먼저 연 프로세스가 파일을 잠갔기 때문이다. H2 서버를 띄우고 양쪽 모두 jdbc:h2:tcp://localhost/~/shop으로 접속한다. H2는 한 번에 커넥션을 하나만 허용하기 때문이다. 애플리케이션의 커넥션 풀 크기를 1로 줄인다. 원격 DB 생성이 금지되어 있기 때문이다. 서버를 -ifNotExists 옵션으로 띄운다. 임베디드 URL은 DB 엔진이 접속한 프로세스 안에서 돌면서 shop.mv.db 파일을 직접 연다는 뜻이다. 한 프로세스가 연 파일을 다른 프로세스의 엔진이 동시에 열 수 없도록 잠금이 걸리고, 오류 메시지가 제안하는 해결도 서버 모드다. 파일은 서버 프로세스만 열고 애플리케이션과 콘솔은 TCP로 그 서버에 접속한다. 8082는 콘솔의 웹 서버 포트로 이 오류와 무관하고, H2가 커넥션을 하나만 허용하는 것도 아니다(한 프로세스 안에서는 여러 커넥션을 열 수 있다). 원격 생성 금지는 TCP로 없는 DB에 접속할 때의 다른 오류(90149)다. 서비스 메서드에 @Transactional이 붙어 있고, 그 안에서 저장소 A(JdbcTemplate 사용)와 저장소 B(dataSource.getConnection()을 직접 호출하고 닫음)를 차례로 호출해 각각 한 행을 넣은 뒤 RuntimeException이 발생했다. DB에 남는 것은? 두 행 모두 롤백되어 아무것도 남지 않는다. 같은 메서드 안에서 실행되었기 때문이다. 두 행 모두 남는다. JDBC의 기본이 자동 커밋이기 때문이다. B가 넣은 행만 남는다. A는 스레드에 묶인 커넥션을 썼고, B는 트랜잭션과 무관한 별도의 커넥션에서 자동 커밋으로 반영했기 때문이다. A가 넣은 행만 남는다. JdbcTemplate은 호출마다 스스로 커밋하기 때문이다. 트랜잭션은 커넥션에 속하고, 스프링은 트랜잭션 동안 커넥션 하나를 현재 스레드에 묶어 둔다. JdbcTemplate은 DataSourceUtils로 그 커넥션을 조회해 쓰므로 A의 INSERT는 트랜잭션에 속하고 롤백된다. B는 풀에서 다른 커넥션을 새로 빌렸고 그 커넥션은 자동 커밋 모드이므로 INSERT가 즉시 반영되어 롤백의 대상이 아니다. "같은 메서드 안"이라는 코드상의 위치는 트랜잭션의 범위를 정하지 않는다. 어떤 커넥션으로 실행되었는지가 정한다. JdbcTemplate이 SQLException을 그대로 던지지 않고 DataAccessException 계열로 바꿔 던지는 설계에서 얻는 것으로 가장 적절한 것은? 서비스 계층이 java.sql이나 특정 DB의 타입에 의존하지 않으면서도, 키 중복이나 문법 오류 같은 원인을 예외 타입으로 구분해 처리할 수 있다. 예외가 언체크 예외가 되므로 트랜잭션이 롤백되지 않아 데이터가 보존된다. 변환 과정에서 원래의 SQLException이 버려지므로 로그에 DB 정보가 노출되지 않는다. 예외 변환 덕분에 SQL 문법 오류가 컴파일 시점에 발견된다. SQLException은 체크 예외이고 원인을 벤더별 코드로만 알려 준다. 스프링은 이것을 원인별 하위 타입(DuplicateKeyException, BadSqlGrammarException 등)을 가진 언체크 예외 계층으로 옮긴다. 위쪽 계층은 throws SQLException을 달 필요가 없고, 관심 있는 상황만 타입으로 골라 잡을 수 있다. 스프링의 기본 규칙에서 롤백을 일으키는 것이 바로 RuntimeException이므로 둘째 보기는 반대다. 원래 예외는 getCause()에 보존된다. SQL은 문자열이므로 오류는 여전히 실행 시점에 드러난다. JPA에서 트랜잭션 안에서 em.find로 조회한 엔티티의 필드를 세터로 바꾸기만 하고 다른 호출 없이 메서드가 정상 종료했다. 이때 일어나는 일을 바르게 설명한 것은? 세터가 호출되는 즉시 UPDATE가 DB로 전송된다. em.persist나 별도의 갱신 메서드를 부르지 않았으므로 DB에는 반영되지 않는다. 변경은 영속성 컨텍스트에만 남고, 다음 트랜잭션에서 같은 엔티티를 조회할 때 DB에 반영된다. 커밋 직전의 플러시에서 영속 상태 엔티티의 변경이 감지되어 UPDATE가 실행되고, 이어서 DB 트랜잭션이 커밋된다. 조회한 엔티티는 영속 상태이고, 영속 상태 엔티티의 변경은 플러시 때 자동으로 감지되어 SQL로 나간다. 플러시는 트랜잭션 커밋 때 일어나므로 메서드가 끝나는 시점에 UPDATE가 실행된다. 세터는 평범한 자바 메서드여서 그 자체로는 SQL을 보내지 않는다. JPA에는 갱신을 요청하는 별도의 호출이 필요 없다. 영속성 컨텍스트의 수명은 보통 트랜잭션과 같으므로 변경이 다음 트랜잭션으로 넘어가 반영되는 일도 없다. interface SpringDataBookRepository extends JpaRepository에 Optional findByTitle(String title)만 선언하고 구현 클래스를 만들지 않았는데, 주입받아 호출하면 동작한다. 이유로 옳은 것은? 컴파일할 때 애너테이션 프로세서가 구현 클래스의 소스 코드를 생성해 함께 컴파일하기 때문이다. 스프링 데이터가 실행 중에 이 인터페이스를 구현하는 프록시를 만들어 빈으로 등록하고, 프록시가 호출을 받아 기본 메서드는 SimpleJpaRepository로, findByTitle은 메서드 이름에서 만든 JPQL의 실행으로 넘기기 때문이다. 인터페이스의 추상 메서드는 호출되면 JVM이 메서드 이름과 같은 이름의 SQL 함수를 DB에서 찾아 실행하기 때문이다. JpaRepository의 메서드가 모두 디폴트 메서드로 구현되어 있고, findByTitle도 디폴트 메서드로 자동 상속되기 때문이다. 구현은 소스나 컴파일 결과물에 없고 실행 중에 만들어진다. 스프링 데이터의 리포지토리 팩토리가 인터페이스를 구현하는 프록시를 만들고, 프록시는 호출된 메서드에 따라 준비된 기본 구현(SimpleJpaRepository)이나 이름에서 유도한 질의로 일을 넘긴다. 그 뒤에는 EntityManager가 있다. 본문의 장난감 예제가 같은 원리(JDK 동적 프록시와 메서드 이름 해석)를 보여 준다. JVM에는 메서드 이름으로 SQL을 찾아 주는 기능이 없고, JpaRepository의 메서드는 추상 메서드다.
    JDBC 드라이버(JDBC driver)
    java.sql의 인터페이스를 특정 DB에 맞게 구현한 라이브러리. DB 고유의 통신 규약으로 SQL을 보내고 결과를 받는다.
    DataSource
    커넥션을 얻는 방법을 추상화한 표준 인터페이스. 매번 새로 만드는 구현도, 풀에서 빌려주는 구현도 같은 getConnection()으로 쓴다.
    커넥션 풀(connection pool)
    DB 커넥션을 미리 만들어 두고 빌려주었다가 돌려받는 구조. 스프링 부트는 HikariCP를 우선 선택한다.
    자동 커밋(auto-commit)
    문장 하나가 실행될 때마다 개별 트랜잭션으로 커밋되는 커넥션의 기본 모드. 끄면 commit()이나 rollback()까지의 문장들이 한 트랜잭션이 된다.
    테스트 관리 트랜잭션(test-managed transaction)
    스프링 테스트 지원이 테스트 메서드 둘레에서 시작하고 끝내는 트랜잭션. 기본적으로 테스트가 끝나면 롤백된다.
    DataAccessException
    스프링이 정의한 데이터 접근 예외 계층의 최상위 타입. 언체크 예외이며 저장 기술에 묶이지 않는다.
    객체 관계 매핑(ORM, Object-Relational Mapping)
    객체와 테이블의 대응 관계를 선언해 두고, 객체를 다루는 코드로부터 SQL을 도구가 생성하게 하는 기법.
    영속성 컨텍스트(persistence context)
    EntityManager가 관리하는 엔티티의 작업 공간. 식별자마다 인스턴스 하나를 유지하며 보통 트랜잭션과 수명이 같다.
    플러시(flush)
    영속성 컨텍스트에 쌓인 변경을 SQL로 DB에 보내 둘의 상태를 맞추는 동작. 커밋 전, 영향을 받는 질의 실행 전, 직접 호출할 때 일어난다.
    JPQL(Jakarta Persistence Query Language)
    테이블과 열이 아니라 엔티티와 그 속성을 대상으로 쓰는 질의 언어. JPA 구현체가 DB의 SQL로 번역한다.
