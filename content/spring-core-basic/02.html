    이 회차의 질문: 원칙은 코드 어디에 나타나는가

    01회는 좋은 객체 지향 설계가 무엇인지를 정리했다. 역할과 구현을 나누고, 확장에는 열려 있되 변경에는 닫혀 있으며, 구체가 아니라 추상에 의존하라는 원칙들이다. 말로 들으면 반박할 곳이 없다. 어려움은 실제 코드를 앞에 두었을 때 시작된다. 인터페이스를 만들고 구현 클래스를 나눴는데도, 구현을 하나 바꾸려니 그것을 쓰는 클래스의 소스를 열어야 한다. 이 회차는 그 지점까지 직접 걸어가 어디가 왜 막혔는지 확인하고, 구조를 바꿔 푼다.

    방법은 단순하다. 회원이 상품을 주문하면 등급에 따라 할인해 주는 작은 프로그램을 스프링 없이 자바만으로 만든다. 그리고 할인 정책을 바꿔야 하는 상황을 만들어 그 변경이 코드의 어디까지 번지는지 본다. 다음으로 객체를 만들고 연결하는 일만 맡는 클래스를 따로 두어 문제를 풀고, 마지막에 그 클래스가 하던 일을 스프링 컨테이너에 넘긴다. 스프링의 클래스가 import 문에 등장하는 것은 마지막 절뿐이다. 컨테이너가 푸는 문제가 무엇인지 알려면 컨테이너 없이 그 문제를 먼저 겪어 봐야 한다.

    이 회차는 소스 코드만 보지 않는다. "주문 서비스가 정액 할인 클래스에 의존한다"는 문장은 비유가 아니라 클래스 파일에 기록된 사실이다. javap로 바이트코드를 읽고, JDK에 들어 있는 jdeps로 클래스 파일의 의존 목록을 뽑고, 클래스 로딩 로그와 호출 스택을 찍어 가며 설계 원칙이 지켜졌는지 어겨졌는지를 확인한다. 원칙을 암기 대상이 아니라 관찰할 수 있는 성질로 다루려는 것이다.

    본문의 실행 결과, 컴파일 오류, 바이트코드, 스택 트레이스는 모두 JDK 21(Temurin 21.0.13)에서 직접 실행해 얻었다. 테스트는 JUnit Jupiter 6.0.3으로, 마지막 절의 스프링 예제는 Spring Framework 7.0.10의 spring-context를 클래스패스에 올려 실행했다. 이 강좌의 기준 버전은 Spring Boot 3.x와 Spring Framework 6.x인데, 이 회차가 쓰는 API(@Configuration, @Bean, AnnotationConfigApplicationContext, JUnit의 @Test와 assertEquals)는 두 세대에서 쓰는 법이 같다. 예외 문구와 스프링 내부 클래스의 줄 번호는 버전에 따라 다를 수 있다.

    이 회차의 예제는 대응 강의의 수업 제목에 나오는 주제(회원, 주문, 할인 정책, AppConfig)를 따라 이 강좌가 새로 만든 것이다. 클래스 이름, 금액, 요구사항의 세부는 강의의 예제와 같지 않다.

    프로젝트 생성과 비즈니스 요구사항: 정해지지 않은 것을 설계에 담는다

    프로젝트는 스프링 입문에서 만들어 본 것과 같은 스프링 부트 Gradle 프로젝트면 된다. 다만 이번에는 웹 의존성을 넣지 않는다. 이 회차의 프로그램은 HTTP 요청을 받지 않고, main 메서드가 끝나면 JVM도 끝난다. 필요한 것은 기본 스타터와 테스트 스타터 둘뿐이다.

    dependencies {
    implementation 'org.springframework.boot:spring-boot-starter'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

    스타터는 그 자체로 코드를 담은 라이브러리가 아니라 다른 모듈을 끌어오는 의존성 묶음이다. Spring Boot 4.1.2의 POM에서 확인한 바로는 spring-boot-starter가 spring-boot-autoconfigure를 통해 spring-boot를 끌어오고, spring-boot가 spring-core와 spring-context에 의존한다. 이 회차의 마지막 절이 쓰는 컨테이너는 spring-context에 들어 있다. spring-boot-starter-test는 junit-jupiter와 assertj-core 등을 끌어온다. 그러니 마지막 절 전까지 우리가 쓰는 코드는 스프링이 클래스패스에 있든 없든 똑같이 동작한다. 스프링 부트의 자동 설정도, 내장 톰캣도 이 회차에는 등장하지 않는다.

    패키지는 업무 단위로 나눈다. shop.member에 회원, shop.discount에 할인, shop.order에 주문을 두고, 실행용 main 클래스는 최상위 shop에 둔다. 패키지를 나눠 두면 뒤에서 클래스 사이의 의존을 뽑아 볼 때 어느 업무가 어느 업무를 아는지가 이름만으로 드러난다.

    요구사항

    기획에서 받은 요구사항은 다음과 같다고 하자.

    • 회원: 회원은 가입할 수 있고 아이디로 조회할 수 있다. 등급은 일반(BASIC)과 골드(GOLD) 두 가지다. 회원 데이터를 어디에 저장할지는 정해지지 않았다. 자체 데이터베이스를 둘 수도 있고 외부 회원 시스템과 연동할 수도 있다.
    • 주문과 할인: 회원은 상품을 주문할 수 있다. 주문에는 회원 등급에 따른 할인이 붙는다. 지금 안은 골드 회원에게 주문 한 건마다 2,000원을 깎아 주는 정액 할인이다. 다만 할인 정책은 금액도 방식도 서비스 개시 직전까지 바뀔 수 있다.

    정해지지 않은 것이 두 가지다. 회원을 어디에 저장하는가, 할인을 어떻게 계산하는가. 이럴 때 고를 수 있는 길은 셋이다. 정해질 때까지 기다리거나, 하나를 찍어서 만들고 바뀌면 고치거나, 정해지지 않은 부분이 나머지 코드에 닿지 않도록 경계를 긋고 개발을 시작하는 것이다. 세 번째 길의 도구가 인터페이스다. "회원을 저장하고 찾는다", "할인 금액을 계산한다"는 역할(role)만 인터페이스로 정해 두고, 그 역할을 실제로 해내는 구현(implementation)은 지금 쓸 수 있는 가장 간단한 것으로 채운다.

    역할(인터페이스)지금 쓰는 구현나중에 올 수 있는 구현미정인 이유
    회원 저장소 MemberRepository메모리의 맵에 저장DB 저장, 외부 시스템 연동저장 위치가 정해지지 않음
    할인 정책 DiscountPolicy골드 회원 2,000원 정액정률 할인, 할인 없음 등기획이 계속 바뀜

    여기서 세워 둘 기준이 하나 있다. 이 설계가 성공했는지는 인터페이스를 만들었느냐가 아니라, 구현을 바꿀 때 무엇이 바뀌지 않느냐로 판정한다. 할인 정책을 정액에서 정률로 바꾸는 날, 주문을 처리하는 코드가 한 글자도 바뀌지 않는다면 성공이다. 이 기준을 들고 끝까지 간다.

    회원 도메인 설계와 개발: 그림 세 장과 코드

    설계를 그림으로 옮길 때는 서로 다른 것을 보여 주는 그림 세 장을 구분해야 한다. 첫째는 도메인 협력 관계다. 어떤 역할들이 있고 누가 누구에게 일을 부탁하는지를 그린다. 코드를 모르는 기획자와도 함께 볼 수 있는 그림이다.

    클라이언트 ──▶ 회원 서비스 ──▶ 회원 저장소
               (가입, 조회)      (저장, 조회)
                                   ├─ 메모리 회원 저장소   ◀ 지금 쓰는 구현
                                   ├─ DB 회원 저장소       ◀ 후보
                                   └─ 외부 시스템 연동     ◀ 후보

    둘째는 클래스 다이어그램이다. 협력 관계를 자바의 타입으로 구체화한 것으로, 어떤 인터페이스와 클래스가 있고 누가 누구를 구현하며 누가 누구의 이름을 코드에 적는지를 보여 준다. 소스 코드만 읽으면 그릴 수 있고 프로그램을 실행하지 않아도 정해져 있으므로 정적(static)인 그림이다.

    MemberService     (인터페이스) ◁─── 구현 ─── MemberServiceImpl
MemberRepository  (인터페이스) ◁─── 구현 ─── MemoryMemberRepository

MemberServiceImpl ───▶ MemberRepository          필드 타입으로 쓴다

    셋째는 객체 다이어그램이다. 프로그램이 실행되는 어느 순간 힙에 실제로 어떤 객체가 있고 어떤 참조로 이어져 있는지를 그린다. 클래스 다이어그램에는 "회원 서비스는 회원 저장소 역할을 쓴다"까지만 나오고, 그 자리에 메모리 저장소가 들어갈지 DB 저장소가 들어갈지는 나오지 않는다. 그것은 실행해 봐야 정해지는 동적(dynamic)인 사실이다.

    main의 지역 변수              힙
memberService ──────▶ MemberServiceImpl 객체
                         └ memberRepository ──▶ MemoryMemberRepository 객체

    이 구분은 뒤에서 의존관계 주입을 정의할 때 그대로 쓰인다. 지금은 클래스 다이어그램과 객체 다이어그램이 같은 것이 아니라는 점만 붙들어 두자. 좋은 설계에서는 클래스 다이어그램을 건드리지 않고 객체 다이어그램만 바꿀 수 있다.

    이제 코드다. 클래스마다 파일을 따로 두어야 하지만 지면을 아끼려고 한 블록에 모았다. 모두 shop.member 패키지에 있다.

    public enum Tier { BASIC, GOLD }

public class Member {
    private final long id;
    private final String name;
    private final Tier tier;

    public Member(long id, String name, Tier tier) {
        this.id = id;
        this.name = name;
        this.tier = tier;
    }

    public long getId() { return id; }
    public String getName() { return name; }
    public Tier getTier() { return tier; }
}

public interface MemberRepository {
    void save(Member member);
    Member findById(long id);      // 없으면 null
}

public class MemoryMemberRepository implements MemberRepository {
    private static final Map store = new HashMap<>();

    @Override
    public void save(Member member) { store.put(member.getId(), member); }

    @Override
    public Member findById(long id) { return store.get(id); }
}

public interface MemberService {
    void join(Member member);
    Member findMember(long id);
}

public class MemberServiceImpl implements MemberService {
    private final MemberRepository memberRepository = new MemoryMemberRepository();

    @Override
    public void join(Member member) { memberRepository.save(member); }

    @Override
    public Member findMember(long id) { return memberRepository.findById(id); }
}

    몇 군데를 짚는다. Member는 필드가 전부 final이라 만들어진 뒤에 값이 바뀌지 않는다. 저장소는 이 객체의 복사본이 아니라 참조를 맵에 넣으므로, 저장한 객체와 나중에 꺼낸 객체는 같은 객체다. MemoryMemberRepository의 맵에는 static이 붙어 있다. 맵이 저장소 객체마다 하나씩이 아니라 클래스에 하나만 있다는 뜻이다. 왜 그렇게 했는지는 주문 도메인에서 드러나는데, 결론부터 말하면 설계의 빈틈을 임시로 가리는 장치이고 뒤에서 걷어 낸다. 또 HashMap은 여러 스레드가 동시에 쓰면 안전하지 않다. 이 회차의 프로그램은 main 스레드 하나로만 돌기 때문에 문제가 되지 않을 뿐이다.

    마지막으로 MemberServiceImpl의 첫 줄을 기억해 두자. 필드의 타입은 인터페이스 MemberRepository인데, 등호 오른쪽에서 new MemoryMemberRepository()로 구현 클래스를 직접 만든다. 지금은 자연스러워 보이는 이 한 줄이 이 회차 전체의 주제다.

    회원 도메인 실행과 테스트: 눈으로 확인하는 것과 기계가 확인하는 것

    만든 것이 동작하는지 확인하는 가장 빠른 방법은 main 메서드를 하나 만들어 돌려 보는 것이다.

    package shop;

public class MemberApp {
    public static void main(String[] args) {
        MemberService memberService = new MemberServiceImpl();
        memberService.join(new Member(1L, "kim", Tier.GOLD));

        Member found = memberService.findMember(1L);
        System.out.println("찾은 회원 = " + found.getName() + ", 등급 = " + found.getTier());
    }
}
    찾은 회원 = kim, 등급 = GOLD

    동작은 한다. 그런데 이 방법에는 한계가 있다. 결과가 맞는지를 사람이 콘솔을 읽고 판단해야 한다. 확인할 것이 열 가지로 늘면 출력 열 줄을 매번 눈으로 대조해야 하고, 코드가 바뀔 때마다 그 일을 반복해야 한다. 판단을 코드로 적어 두면 기계가 대신 대조한다. 그것이 테스트 프레임워크가 하는 일이다.

    package shop.member;

import static org.junit.jupiter.api.Assertions.assertEquals;
import static org.junit.jupiter.api.Assertions.assertSame;

import org.junit.jupiter.api.Test;

class MemberServiceTest {
    private final MemberService memberService = new MemberServiceImpl();

    @Test
    void 가입한_회원을_아이디로_찾는다() {
        // given: 이런 상황에서
        Member member = new Member(1L, "kim", Tier.GOLD);

        // when: 이것을 하면
        memberService.join(member);
        Member found = memberService.findMember(1L);

        // then: 이렇게 되어야 한다
        assertSame(member, found);
        assertEquals("kim", found.getName());
    }
}

    이 클래스에는 main이 없다. 우리가 가입한_회원을_아이디로_찾는다()를 호출하는 코드도 어디에도 없다. IDE의 실행 버튼이나 Gradle의 test 작업이 JUnit을 시작하면, JUnit이 클래스패스에서 @Test가 붙은 메서드를 찾아내고, 테스트 클래스의 객체를 만들고, 리플렉션으로 그 메서드를 호출한다. 우리가 프레임워크를 부르는 것이 아니라 프레임워크가 우리 코드를 부른다. 이 호출 방향은 뒤에서 제어의 역전을 다룰 때 다시 꺼낸다.

    assertSame은 두 참조가 같은 객체를 가리키는지(==)를, assertEquals는 기대한 값과 실제 값이 같은지를 검사한다. 조건이 맞으면 아무 일 없이 다음 줄로 넘어가고, 어긋나면 예외를 던진다. JUnit은 테스트 메서드가 예외 없이 끝나면 성공으로, 예외가 빠져나오면 실패로 기록한다. 그래서 테스트의 성패는 사람의 눈이 아니라 프로세스의 결과로 남고, 빌드 도구는 실패한 테스트가 하나라도 있으면 빌드를 실패시킬 수 있다.

    JUnit Jupiter는 기본적으로 테스트 메서드 하나를 실행할 때마다 테스트 클래스의 객체를 새로 만든다. 한 테스트가 필드에 남긴 값이 다음 테스트에 새지 않게 하려는 것이다. 그런데 이 격리는 객체의 필드까지만 미친다. MemoryMemberRepository의 맵은 static이므로 테스트 객체와 서비스 객체가 몇 번을 새로 만들어져도 같은 JVM 안에서는 하나다. 한 테스트가 저장한 회원이 다른 테스트에서도 보이고, 테스트가 어떤 순서로 실행되느냐에 따라 결과가 달라질 여지가 생긴다. static 맵이 임시 장치라고 한 이유 가운데 하나가 이것이다.

    주문과 할인 도메인: 설계, 개발, 실행

    주문 쪽의 협력은 회원보다 한 단계 길다. 주문 서비스는 요청을 받으면 회원 저장소에서 회원을 찾고, 그 회원과 상품 가격을 할인 정책에 넘겨 할인 금액을 받고, 그 결과를 담은 주문 객체를 돌려준다.

    이 그림에서 주문 서비스가 상대하는 것은 둘 다 역할이다. 회원 저장소가 메모리든 DB든, 할인 정책이 정액이든 정률이든 네 단계의 순서와 내용은 같다. 저장소 구현 둘과 할인 구현 둘이면 조합이 넷인데, 넷 모두에서 주문 서비스의 코드는 하나여야 한다. 설계의 의도는 그렇다. 코드로 옮긴다.

    // shop.discount 패키지
public interface DiscountPolicy {
    /** @return 깎아 줄 금액(원). 할인 대상이 아니면 0 */
    int discount(Member member, int price);
}

public class FlatDiscountPolicy implements DiscountPolicy {
    private static final int AMOUNT = 2000;

    @Override
    public int discount(Member member, int price) {
        return member.getTier() == Tier.GOLD ? AMOUNT : 0;
    }
}

// shop.order 패키지
public class Order {
    private final long memberId;
    private final String itemName;
    private final int itemPrice;
    private final int discountAmount;

    public Order(long memberId, String itemName, int itemPrice, int discountAmount) {
        this.memberId = memberId;
        this.itemName = itemName;
        this.itemPrice = itemPrice;
        this.discountAmount = discountAmount;
    }

    public int getDiscountAmount() { return discountAmount; }
    public int payAmount() { return itemPrice - discountAmount; }

    @Override
    public String toString() {
        return "Order{memberId=" + memberId + ", itemName='" + itemName + "', itemPrice=" + itemPrice
                + ", discountAmount=" + discountAmount + ", payAmount=" + payAmount() + "}";
    }
}

public interface OrderService {
    Order createOrder(long memberId, String itemName, int itemPrice);
}

    주문 서비스의 구현은 뒤에서 줄 단위로 들여다볼 것이므로 import 문까지 파일 전체를 싣는다.

    package shop.order;

import shop.discount.DiscountPolicy;
import shop.discount.FlatDiscountPolicy;
import shop.member.Member;
import shop.member.MemberRepository;
import shop.member.MemoryMemberRepository;

public class OrderServiceImpl implements OrderService {
    private final MemberRepository memberRepository = new MemoryMemberRepository();
    private final DiscountPolicy discountPolicy = new FlatDiscountPolicy();

    @Override
    public Order createOrder(long memberId, String itemName, int itemPrice) {
        Member member = memberRepository.findById(memberId);
        if (member == null) {
            throw new IllegalArgumentException("없는 회원: " + memberId);

        int discountAmount = discountPolicy.discount(member, itemPrice);
        return new Order(memberId, itemName, itemPrice, discountAmount);

}

    createOrder의 본문은 앞의 네 단계를 그대로 옮긴 것이다. 할인 금액을 어떻게 구하는지는 이 클래스에 한 줄도 없다. 등급을 비교하는 코드도, 2,000이라는 숫자도 FlatDiscountPolicy 안에만 있다. 할인 금액을 5,000원으로 올리라는 요청이 와도 주문 서비스는 열 필요가 없다. 여기까지는 역할을 나눈 효과가 난다. 실행해 보자.

    한 층 아래: 의존은 클래스 파일에 적혀 있다

    "A가 B에 의존한다"는 말은 B가 바뀌거나 없어지면 A가 영향을 받는다는 뜻이다. 자바에서 이 말은 꽤 구체적인 사실로 바꿔 쓸 수 있다. A의 소스가 B의 이름을 쓰면, 컴파일러는 A의 클래스 파일 안 상수 풀(constant pool)에 B의 이름을 기록한다. 그 기록이 의존이다. OrderServiceImpl의 클래스 파일을 javap -c -p로 열어 생성자를 보자.

JVM 명세는 invokeinterface를 실행할 때 스택에 놓인 객체의 실행 시점 타입을 기준으로 메서드를 선택한다고 정한다(JVMS §5.4.6). 필드에 FlatDiscountPolicy 객체가 들어 있으면 그 클래스의 discount가, 다른 구현의 객체가 들어 있으면 그 구현의 discount가 실행된다. 이 호출 지점은 구현이 무엇이든 다시 컴파일할 필요가 없다. 다형성이 "역할과 구현의 분리"를 가능하게 하는 바닥이 여기다.

    정리하면 한 클래스 파일 안에 할인에 대한 참조가 두 종류 들어 있다. 호출할 때 쓰는 인터페이스 이름과, 객체를 만들 때 쓰는 구현 클래스 이름이다. 앞의 것은 설계가 의도한 의존이고 뒤의 것은 의도하지 않은 의존이다. JDK의 jdeps는 클래스 파일을 분석해 그 클래스가 의존하는 클래스의 목록을 보여 주는 도구다. 결과에서 java.base에 속한 줄과, 의존 대상이 들어 있는 위치를 적은 마지막 열은 빼고 옮긴다.

   shop.order.OrderServiceImpl   -> shop.member.MemoryMemberRepository

    한 클래스 파일 안에 '호출용 인터페이스 이름'과 '생성용 구현 클래스 이름'이 함께 기록되어 있고, 문제가 되는 것은 뒤쪽임을 보여 준다. 깔끔한 기술 도해. 왼쪽에 큰 문서 모양 상자 하나, 제목 라벨 "OrderServiceImpl.class". 상자 안에 위아래로 두 구역. 위 구역 라벨 "상수 풀"에는 작은 칸 세 개가 세로로 있고 각각 "DiscountPolicy", "FlatDiscountPolicy", "MemberRepository"라고 적는다. 아래 구역 라벨 "바이트코드"에는 두 줄의 코드 조각 "new FlatDiscountPolicy"와 "invokeinterface discount". 오른쪽에는 작은 문서 모양 상자 두 개를 위아래로 배치: 위는 "DiscountPolicy.class" (인터페이스, 점선 테두리), 아래는 "FlatDiscountPolicy.class" (실선 테두리). "invokeinterface discount"에서 "DiscountPolicy.class"로 가는 파란 화살표에 라벨 "호출: 역할만 안다". "new FlatDiscountPolicy"에서 "FlatDiscountPolicy.class"로 가는 빨간 굵은 화살표에 라벨 "생성: 구현을 안다". 빨간 화살표 옆에 작은 경고 표시. 흰 배경, 평면 벡터 스타일, 한국어 라벨은 따옴표 안 문구 그대로. 같은 클래스 파일에 역할의 이름과 구현의 이름이 함께 적혀 있다. 호출은 인터페이스만 알아도 되지만, 객체를 만드는 명령은 구현 클래스의 이름을 요구한다.

    새로운 할인 정책 개발: 클래스 하나를 더하는 일과 정수 산술의 경계

    예상한 대로 기획이 바뀌었다. 정액 2,000원 대신 주문 금액의 10%를 깎아 주기로 했다. 비싼 상품을 사는 골드 회원에게 혜택이 더 가게 하려는 것이다. 새 정책을 만드는 일 자체는 쉽다. DiscountPolicy를 구현하는 클래스를 하나 더 쓰면 되고, 기존 파일은 하나도 열지 않는다. 설계 원칙으로 말하면 "확장에 열려 있다"는 절반은 인터페이스만으로 이미 얻었다.

    package shop.discount;

import shop.member.Member;
import shop.member.Tier;

public class PercentDiscountPolicy implements DiscountPolicy {
    private static final int PERCENT = 10;

    @Override
    public int discount(Member member, int price) {
        return member.getTier() == Tier.GOLD ? price * PERCENT / 100 : 0;
    }
}

    새 클래스는 주문 서비스에 꽂기 전에 혼자 검사할 수 있다. 정책 객체를 직접 만들어 회원과 가격을 넣어 보면 되기 때문이다. 테스트를 쓸 때는 잘 되는 경우 하나로 끝내지 말고 경계를 함께 적는다. 할인 대상이 아닌 회원, 그리고 10%가 원 단위로 떨어지지 않는 가격이다.

    세 테스트 모두 통과한다. 세 번째 테스트는 한 줄짜리 계산식 안에 숨어 있는 규칙을 드러낸다. 12,559원의 10%는 1,255.9원인데 결과는 1,255다. 자바의 정수 나눗셈은 몫을 0에 가까운 쪽으로 잘라 낸다. 반올림이 아니다. 고객에게 유리하게 올림할지 버릴지는 업무 규칙이므로, 테스트로 적어 두어야 누가 계산식을 고쳤을 때 규칙이 바뀐 것을 알아챌 수 있다.

    연산 순서도 결과를 바꾼다. price * PERCENT / 100은 곱한 다음 나누고, price / 100 * PERCENT는 나눈 다음 곱한다. 수학에서는 같은 식이지만 정수 산술에서는 나눗셈이 먼저 오면 그 자리에서 소수부가 사라진다.

    곱셈을 먼저 하는 쪽이 정확하지만 대가가 있다. 곱한 중간값이 int의 최댓값 2,147,483,647을 넘으면 자바는 예외를 던지지 않고 넘친 상위 비트를 버린 값을 돌려준다. 가격이 3억 원이면 price * 10은 30억이어야 하는데 실제로는 -1,294,967,296이 되고, 할인 금액은 -12,949,672원이 된다. 음수 할인은 가격을 올려 받는다는 뜻이다. 이 정책의 계산식이 안전한 범위는 가격 214,748,364원까지다. 그 이상을 다뤄야 한다면 (long) price * PERCENT / 100처럼 곱하기 전에 long으로 넓히거나, 넘칠 때 ArithmeticException을 던지는 Math.multiplyExact를 쓴다.

    정액 정책에도 경계가 있다. 1,500원짜리 상품에 2,000원을 깎으면 payAmount()는 -500이 된다. 할인 금액이 가격을 넘지 않게 하는 규칙을 어디에 둘지는 설계 결정이다. 그 규칙을 DiscountPolicy의 계약, 곧 "돌려주는 값은 0 이상 가격 이하"로 정해 두면 주문 서비스는 어떤 구현이 오든 그 범위를 믿고 쓸 수 있다. 이 계약은 뒤에서 구현을 바꿔 끼울 때 다시 중요해진다.

    첫째, 확장하려고 클라이언트를 변경했다

    개방-폐쇄 원칙(OCP)은 기능을 확장할 때 기존 코드를 변경하지 않아야 한다고 말한다. 새 정책 클래스를 추가한 것은 확장이다. 그런데 그것을 적용하려고 정책을 쓰는 쪽, 곧 클라이언트인 OrderServiceImpl을 변경했다. 소스가 바뀌었으니 다시 컴파일되고, 클래스 파일의 상수 풀에 적힌 이름이 FlatDiscountPolicy에서 PercentDiscountPolicy로 바뀐다. 주문 흐름에는 손대지 않았는데도 주문 서비스는 "변경된 클래스"가 되어 다시 검토하고 다시 검사하고 다시 배포해야 한다.

    그 비용이 얼마나 실제적인지는 테스트가 보여 준다. 앞에서 쓴 OrderServiceTest를 돌리면 하나가 실패한다.

    둘째, 추상과 구체에 함께 의존하고 있었다

    의존관계 역전 원칙(DIP)은 구체가 아니라 추상에 의존하라고 말한다. OrderServiceImpl의 필드 타입은 인터페이스이니 지킨 것처럼 보였다. 하지만 앞 절의 jdeps 출력이 말해 주듯 이 클래스는 DiscountPolicy와 FlatDiscountPolicy를 둘 다 알고 있었다. 의도한 그림과 실제 그림이 달랐던 것이다.

    셋째, 만드는 곳이 여러 곳이면 고칠 곳도 여러 곳이다

    지금은 할인 정책을 쓰는 클래스가 하나라서 두 줄로 끝났다. 정책을 쓰는 클래스가 다섯이고 각자 new FlatDiscountPolicy()를 갖고 있다면 다섯 파일을 고쳐야 한다. 하나를 빠뜨려도 컴파일러는 알려 주지 않는다. 빠뜨린 클래스는 옛 정책으로 문제없이 컴파일되고, 한 서비스 안에서 화면에 따라 할인 금액이 다르게 계산되는 버그가 조용히 배포된다. "어떤 구현을 쓸 것인가"라는 하나의 결정이 코드 여러 곳에 복제되어 있기 때문이다.

    관심사의 분리: 쓰는 코드와 만드는 코드를 가른다

    처음의 OrderServiceImpl은 두 가지 일을 하고 있었다. 하나는 주문을 처리하는 일이다. 회원을 찾고, 할인을 받고, 주문을 만든다. 다른 하나는 그 일에 쓸 협력 객체를 고르고 만드는 일이다. 저장소는 메모리 구현으로, 할인은 정액 구현으로 하겠다는 결정이 필드 선언 두 줄에 들어 있었다. 앞의 것은 "주문은 어떻게 처리되는가"라는 관심사이고 뒤의 것은 "이 애플리케이션은 어떤 부품으로 구성되는가"라는 관심사다. 바뀌는 이유도, 바뀌는 시점도, 결정하는 사람도 다르다.

    주방에서 가져온 비유요리사와 구매 담당

    요리사는 조리법에 따라 "식용유"를 쓴다. 어느 납품업체의 식용유를 들일지는 구매 담당이 정해서 주방에 가져다 놓는다. 요리사가 납품업체와 직접 계약까지 한다면, 업체가 바뀔 때마다 요리사의 일이 바뀌고 조리에 쓸 시간이 줄어든다. 일을 나누면 업체를 바꿔도 조리법은 그대로다. 다만 이 비유는 한 군데서 깨진다. 실제 요리사는 기름의 품질이 달라지면 조리법을 조정하지만, 코드의 클라이언트는 인터페이스가 약속한 것만 믿고 구현이 무엇인지 끝까지 모른다. 그래서 구현들이 약속을 똑같이 지키는지가 코드에서는 더 엄격한 조건이 된다.

    코드로 옮기면 이렇다. 먼저 서비스들은 협력 객체를 만들지 않고 생성자의 인자로 받는다.

    AppConfig 리팩터링: 역할이 보이는 구성, 그리고 "하나"의 문제

    방금 만든 AppConfig는 동작하지만 읽기에 좋지 않다. new MemoryMemberRepository()가 두 번 나온다. 저장소 구현을 바꾸려면 두 곳을 고쳐야 하니, 앞에서 본 "결정의 복제"가 구성 코드 안에서 되풀이된 셈이다. 그리고 이 애플리케이션에 어떤 역할들이 있는지가 한눈에 보이지 않는다. 역할마다 메서드를 하나씩 두고, 메서드의 반환 타입을 인터페이스로 적으면 둘 다 풀린다.

    public class AppConfig {
    public MemberService memberService() {
        return new MemberServiceImpl(memberRepository());
    }

    public OrderService orderService() {
        return new OrderServiceImpl(memberRepository(), discountPolicy());
    }

    public MemberRepository memberRepository() {
        return new MemoryMemberRepository();
    }

    public DiscountPolicy discountPolicy() {
        return new FlatDiscountPolicy();
    }
}

    이제 AppConfig는 설계도처럼 읽힌다. 메서드 이름과 반환 타입이 역할이고, return 뒤의 new가 그 역할에 지금 배정된 구현이다. 회원 서비스는 회원 저장소를 쓰고, 주문 서비스는 회원 저장소와 할인 정책을 쓴다는 연결 관계가 메서드 호출로 드러난다. 구현을 바꾸는 지점은 역할마다 정확히 한 곳이다.

    static을 걷어 내면

    객체를 만드는 곳이 한 군데로 모였으니, 저장소의 맵에 붙여 둔 static을 걷어 낼 차례다. 맵을 인스턴스 필드로 바꾸고, 실험을 위해 저장소의 생성자에 출력 한 줄을 넣는다.

    public class MemoryMemberRepository implements MemberRepository {
    private final Map store = new HashMap<>();

    public MemoryMemberRepository() {
        System.out.println("MemoryMemberRepository 생성");

    // ... save, findById는 그대로
}

    저장소가 두 번 만들어졌고, 주문 도메인에서 본 그 오류가 다시 났다. 소스를 보면 memberRepository()라는 같은 메서드를 두 번 불렀으니 같은 저장소가 올 것처럼 읽힌다. 그러나 자바에서 메서드 호출은 본문을 처음부터 다시 실행하는 것이고, 본문에 new가 있으면 부를 때마다 새 객체가 힙에 생긴다. memberService()가 부른 memberRepository()와 orderService()가 부른 memberRepository()는 서로 다른 객체를 돌려준다.

    appConfig.memberService()  ──▶ MemberServiceImpl ── memberRepository ──▶ MemoryMemberRepository #1 { 1 = kim }
appConfig.orderService()   ──▶ OrderServiceImpl  ─┬ memberRepository ──▶ MemoryMemberRepository #2 { }
                                                  └ discountPolicy   ──▶ FlatDiscountPolicy

    public class AppConfig {

    public MemberService memberService() {
        return new MemberServiceImpl(memberRepository());
    }

    public OrderService orderService() {
        return new OrderServiceImpl(memberRepository(), discountPolicy());
    }

    public MemberRepository memberRepository() {
        return memberRepository;
    }

    public DiscountPolicy discountPolicy() {
        return new FlatDiscountPolicy();
    }

    저장소가 한 번만 만들어졌고 주문이 성공한다. static 맵과 견주어 보면 무엇이 나아졌는지 분명하다. static은 "이 클래스의 객체는 몇 개를 만들든 전부 데이터를 공유한다"는 결정을 저장소 클래스 안에 박아 넣는다. 테스트마다 빈 저장소를 새로 쓰고 싶어도 그럴 수 없다. 지금 구조에서는 저장소 클래스는 평범한 클래스이고, 몇 개를 만들어 누구와 공유할지는 조립하는 쪽이 정한다. 애플리케이션에서는 AppConfig가 하나를 만들어 나눠 주고, 테스트에서는 테스트마다 new로 깨끗한 저장소를 만든다.

    그런데 이 해법은 손이 많이 간다. 지금은 공유해야 할 객체가 저장소 하나지만, 역할이 스무 개로 늘면 필드도 스무 개로 늘고, 새 역할을 추가할 때마다 "이것은 하나만 있어야 하는가"를 사람이 기억해서 처리해야 한다. 같은 AppConfig에서 memberService()를 두 번 부르면 서비스 객체는 여전히 둘이 만들어진다는 점도 그대로다. 만든 객체를 이름표를 붙여 보관해 두고, 같은 것을 달라고 하면 보관해 둔 것을 내주는 장부가 있으면 이 일을 일반화할 수 있다. 스프링 컨테이너가 바로 그 장부를 갖고 있고, 이 회차의 마지막 절에서 그 효과를 먼저 확인한 뒤 04회에서 내부를 연다.

    메서드 호출마다 new가 실행되면 객체가 둘이 되고, 구성 클래스가 한 개를 들고 있으면 두 서비스가 같은 저장소를 가리킨다는 것을 좌우로 대비한다. 좌우 두 패널로 나눈 메모리 도해. 왼쪽 패널 제목 "호출할 때마다 new". 위쪽에 둥근 상자 두 개 "MemberServiceImpl"과 "OrderServiceImpl", 아래쪽에 원통 모양 저장소 두 개 "저장소 #1"과 "저장소 #2". "MemberServiceImpl"에서 "저장소 #1"로, "OrderServiceImpl"에서 "저장소 #2"로 화살표. "저장소 #1" 안에는 작은 카드 "1 = kim", "저장소 #2" 안은 비어 있고 옆에 빨간 글씨 "없는 회원". 오른쪽 패널 제목 "AppConfig가 하나를 보관". 맨 위에 상자 "AppConfig", 그 아래 원통 하나 "저장소", AppConfig에서 저장소로 화살표와 라벨 "필드". 양옆에 "MemberServiceImpl"과 "OrderServiceImpl" 상자가 있고 둘 다 같은 "저장소"를 가리키는 화살표. 저장소 안에 카드 "1 = kim". 오른쪽 패널의 화살표는 초록색. 흰 배경, 평면 벡터, 한국어 라벨은 따옴표 안 문구 그대로. 메서드를 부를 때마다 new가 실행되면 저장소가 둘이 된다. 구성 클래스가 하나를 보관해 나눠 주어야 두 서비스가 같은 데이터를 본다.

    이 구조를 두 영역으로 나누어 부를 수 있다. 업무 로직을 수행하는 사용 영역과, 객체를 만들고 연결하는 구성 영역이다.

    사용 영역 (구현 이름을 모른다)                 구성 영역 (구현 이름을 안다)
---------------------------------            ---------------------------------

OrderServiceImpl  ──▶ DiscountPolicy          AppConfig ──▶ MemoryMemberRepository

    OCP가 말하는 "변경에 닫혀 있다"는 코드를 아예 고치지 않는다는 뜻이 아니다. 누군가는 새 구현을 쓰겠다고 적어야 하므로 구성 영역은 바뀐다. 닫혀 있어야 하는 것은 사용 영역이다. 변경을 구성 영역 한 곳으로 몰아넣고 사용 영역을 그 변경에서 격리하는 것, 그것이 이 구조가 한 일이다.

    사용 영역의 클래스는 인터페이스만 알고, 구성 영역의 AppConfig만 구현을 알며, 정책 교체 시 바뀌는 선이 구성 영역 안의 하나뿐임을 보여 준다. 가로로 두 구역을 나눈 구조도. 왼쪽 넓은 구역은 연한 파란 배경에 제목 "사용 영역", 오른쪽 좁은 구역은 연한 주황 배경에 제목 "구성 영역". 사용 영역 안: 위에 상자 "OrderServiceImpl", 그 아래 점선 테두리 상자 두 개 "MemberRepository"와 "DiscountPolicy" (인터페이스 표시). OrderServiceImpl에서 두 인터페이스로 실선 화살표. 인터페이스 "DiscountPolicy" 아래에 구현 상자 두 개 "FlatDiscountPolicy" (회색, 흐리게)와 "PercentDiscountPolicy" (진하게), 각각 인터페이스로 향하는 빈 삼각형 화살표. 구성 영역 안: 상자 "AppConfig" 하나. AppConfig에서 "OrderServiceImpl"로 가는 화살표에 라벨 "생성", AppConfig에서 "PercentDiscountPolicy"로 가는 굵은 주황 화살표에 라벨 "생성 후 주입", AppConfig에서 "FlatDiscountPolicy"로 가던 화살표는 점선과 가위표로 끊어 표시하고 라벨 "교체". 그림 아래 한 줄 설명 "정책을 바꿔도 사용 영역은 그대로". 흰 바탕, 평면 벡터, 한국어 라벨은 따옴표 안 문구 그대로. 구현을 아는 것은 구성 영역의 AppConfig뿐이다. 정책을 교체하면 구성 영역의 선 하나가 바뀌고 사용 영역은 그대로 남는다.

    전체 흐름 정리

    좋은 객체 지향 설계 원칙의 적용: 무엇을 지키게 되었는가

    01회에서 정리한 다섯 원칙을 이 예제의 처음과 끝에 대어 본다. 이 과정에서 직접 문제가 되고 해결된 것은 SRP, DIP, OCP 셋이고, 나머지 둘은 이 구조가 성립하기 위한 조건으로 작용했다.

    단일 책임 원칙(SRP). 한 클래스는 변경되는 이유가 하나여야 한다. 처음의 OrderServiceImpl은 변경 이유가 둘이었다. 주문 흐름이 바뀔 때, 그리고 어떤 구현을 쓸지가 바뀔 때다. 관심사를 분리한 뒤에는 주문 흐름이 바뀌면 OrderServiceImpl이, 구현 선택이 바뀌면 AppConfig가 바뀐다. 변경 이유 하나에 클래스 하나가 대응한다.

    의존관계 역전 원칙(DIP). 처음에는 OrderServiceImpl이 추상(DiscountPolicy)과 구체(FlatDiscountPolicy)에 함께 의존했다. 구체를 지우자 실행할 수 없게 되었고, 바깥에서 구현 객체를 만들어 넣어 주는 것으로 풀었다. 결과적으로 주문 서비스도 정책 구현들도 모두 DiscountPolicy라는 추상을 향한다. 구현을 향하는 화살표는 구성 영역에만 있다.

    개방-폐쇄 원칙(OCP). 다형성만으로는 새 구현을 추가하는 것까지만 되었고, 그것을 적용하려면 클라이언트를 고쳐야 했다. 구성 영역을 분리하자 새 구현의 적용이 AppConfig의 변경으로 끝났다. 사용 영역은 변경에 닫혀 있으면서 새 정책으로 확장되었다. OCP는 다형성과 "구현을 바깥에서 넣어 주는 구조"가 함께 있어야 성립한다.

    리스코프 치환 원칙(LSP). 구현을 바꿔 끼워도 프로그램이 올바르게 동작하려면, 모든 구현이 인터페이스의 계약을 지켜야 한다. 컴파일러가 확인해 주는 것은 메서드의 이름과 타입뿐이다. 어떤 정책 구현이 음수를 돌려주거나 일반 회원에게 예외를 던진다면, 타입은 맞아서 꽂을 수는 있지만 주문 서비스는 잘못된 결제 금액을 만들어 낸다. 앞에서 "돌려주는 값은 0 이상 가격 이하"를 계약으로 정해 두자고 한 이유다. 교체 가능한 구조는 계약을 지키는 구현들 위에서만 안전하다.

    인터페이스 분리 원칙(ISP). 주문 서비스가 회원에 대해 필요로 하는 것은 아이디로 찾는 기능뿐이고, MemberRepository는 저장과 조회 두 메서드만 가진 작은 인터페이스다. 인터페이스가 작으면 새 구현을 쓰기 쉽고, 테스트에서 가짜를 만들기도 쉽다. DiscountPolicy가 메서드 하나여서 람다 한 줄로 스텁을 만들 수 있었던 것이 그 효과다.

    제어의 역전(IoC)

    처음 코드에서 OrderServiceImpl은 자기가 쓸 객체를 스스로 골라 만들었다. 무엇을 언제 만들지에 대한 결정, 곧 제어가 그 클래스 안에 있었다. 지금은 OrderServiceImpl이 어떤 구현을 받게 될지, 언제 만들어질지, 자기 자신이 몇 개 만들어질지조차 모른다. 그 결정은 전부 AppConfig에 있고, 주문 서비스는 주어진 것으로 자기 로직만 실행한다. 프로그램의 흐름을 구현 객체가 아니라 바깥이 쥐고 있는 것을 제어의 역전(Inversion of Control, IoC)이라고 한다.

    호출 스택으로 보면 방향이 드러난다. OrderServiceImpl의 생성자에 스택을 출력하는 줄(Thread.dumpStack())을 잠시 넣고 실행한 결과다.

    의존관계 주입(DI)

    의존관계는 두 층으로 나누어 봐야 한다. 정적인 클래스 의존관계는 소스의 import 문과 클래스 파일의 상수 풀에 적힌 것이다. 실행하지 않고도 알 수 있고, 앞에서 jdeps로 뽑아 본 것이 이것이다. OrderServiceImpl은 DiscountPolicy에 의존한다는 것까지는 여기서 알 수 있다. 동적인 객체 의존관계는 실행 중에 힙에서 어떤 객체가 어떤 객체의 참조를 갖고 있는가다. 주문 서비스 객체의 discountPolicy 필드가 실제로 정률 정책 객체를 가리키는지는 실행해 봐야 정해진다. 처음에 구분해 둔 클래스 다이어그램과 객체 다이어그램이 각각 이 두 층에 해당한다.

    의존관계 주입(Dependency Injection, DI)은 실행 시점에 바깥에서 실제 구현 객체를 만들어 클라이언트에 전달함으로써, 클라이언트와 구현 객체 사이의 동적 의존관계를 맺어 주는 것이다. 핵심은 정적 의존관계를 건드리지 않고 동적 의존관계만 바꿀 수 있다는 데 있다. 정책을 정률로 바꿨을 때 OrderServiceImpl.class가 한 바이트도 변하지 않았던 것이 그 증거다. 클래스 다이어그램은 그대로이고 객체 다이어그램만 달라졌다.

    스프링 레퍼런스도 같은 방식으로 정의한다. 객체는 자신이 함께 일할 대상을 생성자 인자, 팩토리 메서드의 인자, 또는 프로퍼티로만 드러내고, 컨테이너가 그 객체를 만들 때 의존 대상을 넣어 준다. 객체가 의존 대상을 직접 생성하거나 찾아오는 방식과 방향이 반대라서 제어의 역전이라는 이름이 붙었고, DI는 IoC의 특수한 형태라는 설명이다. 용어의 내력도 이 관계를 보여 준다. 마틴 파울러는 2004년 1월의 글에서 당시 이런 컨테이너들을 뭉뚱그려 부르던 IoC라는 말을 두고 "Inversion of Control is too generic a term"이라고 지적하며, 그 가운데 의존 대상을 넣어 주는 패턴에 Dependency Injection이라는 이름을 붙였다. 프레임워크가 내 코드를 호출하는 것은 전부 제어의 역전이므로, IoC는 넓은 말이고 DI는 그 가운데 객체의 의존관계에 관한 한 가지다.

    주입하는 통로는 하나가 아니다. 이 회차에서 쓴 것은 생성자를 통한 주입이고, 객체를 만든 뒤 세터 메서드로 넣어 주는 방식도 있다. 스프링이 지원하는 주입 방법들과 그 가운데 생성자 주입을 고르는 이유는 06회에서 다룬다.

    DI 컨테이너

    AppConfig처럼 객체를 만들고, 보관하고, 의존관계를 연결해 주는 것을 IoC 컨테이너 또는 DI 컨테이너라고 부른다. 조립한다는 뜻에서 어셈블러(assembler), 만들어 낸다는 뜻에서 오브젝트 팩토리(object factory)라고도 한다. 우리가 손으로 쓴 AppConfig는 이 애플리케이션 전용의 작은 DI 컨테이너다. 스프링은 어떤 애플리케이션에도 쓸 수 있는 범용 DI 컨테이너를 제공한다.

    제어의 역전을 화살표 방향의 뒤바뀜으로 보여 준다. 왼쪽은 서비스가 구현을 향해 new 화살표를 쏘고, 오른쪽은 바깥의 조립자가 서비스와 구현을 모두 만들고 서비스에 구현을 건넨다. 좌우 두 패널의 비교 다이어그램. 왼쪽 패널 제목 "직접 생성". 가운데 상자 "OrderServiceImpl", 그 오른쪽 아래 상자 "FlatDiscountPolicy". OrderServiceImpl에서 FlatDiscountPolicy로 가는 빨간 화살표에 라벨 "new". OrderServiceImpl 위에 말풍선 "무엇을 쓸지 내가 정한다". 오른쪽 패널 제목 "제어의 역전". 맨 위에 상자 "AppConfig", 그 아래 왼쪽에 "OrderServiceImpl", 오른쪽에 "PercentDiscountPolicy". AppConfig에서 두 상자로 각각 내려가는 초록 화살표에 라벨 "new". PercentDiscountPolicy에서 OrderServiceImpl의 생성자 쪽으로 향하는 점선 화살표에 라벨 "생성자로 주입". OrderServiceImpl 위에 말풍선 "받은 것으로 일만 한다". 두 패널 사이에 큰 화살표와 라벨 "결정권이 바깥으로". 흰 배경, 평면 벡터, 한국어 라벨은 따옴표 안 문구 그대로. 왼쪽에서는 서비스가 쓸 구현을 스스로 정하고 만든다. 오른쪽에서는 그 결정이 바깥의 구성 클래스로 옮겨 가고, 서비스는 받은 객체로 일만 한다.

    스프링으로 전환하기: 손으로 쓴 컨테이너를 범용 컨테이너로

    이제 AppConfig가 하던 일을 스프링 컨테이너에 넘긴다. 바꿀 파일은 둘이다. 구성 클래스에 애노테이션을 붙이고, main에서 AppConfig를 직접 부르던 것을 컨테이너에게 묻는 것으로 바꾼다. 사용 영역의 클래스는 건드리지 않는다.

    package shop;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
// ... shop 패키지의 import는 생략

@Configuration
public class AppConfig {
    @Bean
    public MemberService memberService() {
        return new MemberServiceImpl(memberRepository());
    }

    @Bean
    public OrderService orderService() {
        return new OrderServiceImpl(memberRepository(), discountPolicy());
    }

    @Bean
    public MemberRepository memberRepository() {
        return new MemoryMemberRepository();
    }

    @Bean
    public DiscountPolicy discountPolicy() {
        return new PercentDiscountPolicy();
    }
}

    @Configuration은 이 클래스의 주된 목적이 빈 정의를 제공하는 것임을 나타내고, @Bean은 그 메서드가 컨테이너가 관리할 객체를 만들어 돌려준다는 표시다. 눈여겨볼 곳은 memberRepository()다. 저장소를 하나만 두려고 넣었던 필드를 지우고, 버그가 났던 모양 그대로 본문에서 new를 한다. 일부러 그렇게 했다. 결과가 어떻게 되는지 보자.

    package shop;

import org.springframework.context.ApplicationContext;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
// ... shop 패키지의 import는 생략

public class OrderApp {
    public static void main(String[] args) {
        ApplicationContext ac = new AnnotationConfigApplicationContext(AppConfig.class);
        System.out.println("컨테이너 생성 완료");

        MemberService memberService = ac.getBean("memberService", MemberService.class);
        OrderService orderService = ac.getBean("orderService", OrderService.class);

        memberService.join(new Member(1L, "kim", Tier.GOLD));
        Order order = orderService.createOrder(1L, "키보드", 30000);

        System.out.println(order);
        System.out.println(orderService == ac.getBean(OrderService.class));
    }
}

    첫째 줄과 둘째 줄의 순서. 저장소 생성 로그가 "컨테이너 생성 완료"보다 먼저 나왔다. ApplicationContext가 스프링 컨테이너이고, AnnotationConfigApplicationContext는 애노테이션이 붙은 자바 클래스를 구성 정보로 받는 구현이다. 생성자에 AppConfig.class를 넘기면 컨테이너는 그 클래스와 그 안의 @Bean 메서드 넷을 빈 정의로 등록하고, 이어서 메서드들을 호출해 객체를 만들어 보관한다. 이렇게 컨테이너가 만들고 관리하는 객체를 스프링 빈(bean)이라고 한다. 우리가 getBean을 부르기 전에, 컨테이너의 생성자가 끝나기 전에 객체들은 이미 다 만들어져 있다.

    저장소 생성 로그가 한 번뿐이다. memberService()와 orderService()가 각각 memberRepository()를 부르고 그 본문에는 new가 있는데, 저장소는 하나만 만들어졌고 주문도 성공했다. 순수 자바였다면 두 번 만들어져 "없는 회원" 오류가 났을 코드다. 스프링의 빈 생성 로그를 DEBUG 수준으로 켜 보면 순서가 보인다. 스프링이 내부용으로 등록하는 빈 넷의 줄은 뺐다.

    memberService를 만드는 도중에 memberRepository가 만들어졌다. memberService()의 본문이 memberRepository()를 부른 시점이다. 그다음 orderService를 만들 때도 본문이 memberRepository()를 부르지만, 이번에는 생성 로그가 없고 곧바로 discountPolicy로 넘어간다. 이미 만들어 보관해 둔 저장소가 돌아온 것이다. 앞에서 필드 하나로 흉내 냈던 "만든 것을 보관해 두었다가 같은 것을 내주는 장부"를 컨테이너가 모든 빈에 대해 갖고 있다. 평범한 자바 메서드 호출이 어떻게 보관된 객체를 돌려줄 수 있는지는 @Configuration 클래스에 대한 스프링의 특별한 처리 때문이고, 그 원리는 04회의 주제다.

    셋째 줄. 주문 결과는 순수 자바 버전과 같다. getBean("memberService", MemberService.class)의 첫 인자는 빈의 이름이다. 스프링 레퍼런스가 밝히듯 @Bean 메서드로 등록한 빈의 이름은 기본적으로 메서드 이름과 같다. 없는 이름을 대면 NoSuchBeanDefinitionException: No bean named 'orderSvc' available처럼 예외가 난다. 둘째 인자는 돌려받을 타입이다.

    넷째 줄의 true. 이름으로 꺼낸 주문 서비스와 타입으로 다시 꺼낸 주문 서비스가 같은 객체다. getBean은 객체를 새로 만드는 메서드가 아니라 보관소에서 꺼내는 메서드다. 순수 자바 AppConfig에서 orderService()를 두 번 부르면 서로 다른 객체 둘이 나왔던 것과 대비된다.

    바뀐 것과 바뀌지 않은 것

    스프링을 도입했는데도 OrderServiceImpl.class는 도입 전과 바이트 단위로 같다. jdeps로 보면 org.springframework로 시작하는 클래스를 참조하는 것은 AppConfig와 OrderApp뿐이고, 회원·주문·할인 패키지의 클래스는 스프링의 존재를 모른다. 사용 영역과 구성 영역을 갈라 둔 덕에 컨테이너의 교체가 구성 영역 안의 일로 끝났다. 생성자로 협력 객체를 받는 클래스는 스프링 없이도 new로 조립해 쓸 수 있고, 앞에서 쓴 테스트들은 컨테이너를 띄우지 않고 그대로 통과한다.

    솔직히 말하면 지금 단계에서는 스프링을 쓴 쪽이 코드가 더 길다. 순수 자바 AppConfig로도 충분해 보인다. 컨테이너를 쓰는 이득은 이제부터 하나씩 나타난다. 빈을 이름과 타입으로 조회하고 구성 정보를 다루는 방식은 03회에서, 객체를 하나만 유지하는 방식과 그것이 여러 스레드가 함께 쓰는 서버에서 갖는 의미는 04회에서, 구성 클래스에 일일이 적지 않고 클래스를 찾아 등록하는 컴포넌트 스캔은 05회에서, 생성자 인자를 타입으로 찾아 채워 주는 자동 주입은 06회에서, 객체의 초기화와 종료 시점에 끼어드는 콜백은 07회에서, 싱글톤이 아닌 생존 범위는 08회에서 다룬다.

    흔한 오해 다섯 가지

    • "인터페이스 타입으로 선언했으니 DIP를 지켰다." 필드 타입이 인터페이스여도 같은 클래스 안에서 new 구현()을 하면 그 클래스 파일의 상수 풀에 구현 클래스의 이름이 들어간다. 판정 기준은 선언 타입이 아니라, 그 소스의 import 문과 본문 어디에도 구현 클래스 이름이 없는가다.
    • "의존관계 주입은 스프링의 기능이다." 이 회차의 대부분에서 스프링 없이 생성자 인자만으로 주입을 했다. DI는 객체를 조립하는 방식이고, 스프링은 그 조립을 대신 해 주는 도구다. 스프링 애노테이션이 하나도 없는 클래스도 주입받을 수 있다.
    • "OCP를 지키면 코드를 한 줄도 안 고친다." 새 구현을 쓰겠다는 결정은 어딘가에 적혀야 한다. 구성 영역은 바뀐다. 원칙이 지키려는 것은 변경이 사용 영역으로 번지지 않는 것이다.
    • "AppConfig가 구현 클래스를 전부 아니까 AppConfig가 DIP 위반이다." 실행하려면 누군가는 구현의 이름을 알아야 한다. 그 지식을 업무 로직에서 떼어 한 곳에 모으는 것이 목적이고, AppConfig는 그 일만 하는 클래스다. 구성 영역이 구현을 아는 것은 설계의 결함이 아니라 설계의 결과다.
    • "IoC와 DI는 같은 말이다." 프레임워크가 내 코드를 호출하는 구조는 모두 제어의 역전이다. JUnit이 테스트 메서드를 부르는 것도, 서블릿 컨테이너가 서블릿을 부르는 것도 그렇다. DI는 그 가운데 "객체가 쓸 의존 대상을 바깥에서 넣어 준다"는 한 가지 형태다.

    이 지식이 다시 쓰이는 곳

    이 회차에서 손으로 한 일은 이 권의 나머지 회차에서 스프링이 대신 한다. 그때마다 "순수 자바 AppConfig에서는 이것을 어떻게 했는가"를 떠올리면 스프링의 기능이 무엇을 자동화한 것인지 알 수 있다. 저장소를 하나로 유지하려고 둔 필드는 컨테이너의 싱글톤 보관소가 되고, 역할마다 쓴 메서드는 빈 정의가 되며, 생성자에 인자를 넘기던 코드는 자동 주입이 된다. 같은 타입의 구현이 둘 이상 빈으로 등록되어 있을 때 컨테이너가 어느 것을 넣을지 정하는 규칙도, AppConfig에서 우리가 new PercentDiscountPolicy()라고 한 줄로 정했던 그 결정을 다른 방식으로 표현하는 것이다.

    데이터베이스를 붙일 때도 같은 구조가 쓰인다. 회원 저장소를 메모리 구현에서 JDBC나 JPA를 쓰는 구현으로 바꾸는 일은 이 회차의 할인 정책 교체와 모양이 같다. MemberRepository를 구현하는 새 클래스를 더하고, 구성 정보에서 그 역할에 배정된 구현을 바꾼다. 서비스 계층의 클래스 파일은 그대로다. 저장소가 실제 데이터베이스가 되면 테스트가 느려지고 준비가 번거로워지는데, 그때 서비스의 로직만 빠르게 검사하려고 메모리 구현이나 스텁을 넣는 것도 이 회차에서 한 것과 같은 일이다.

    객체를 컨테이너가 만든다는 사실은 프록시와 AOP의 전제이기도 하다. 클라이언트가 인터페이스만 알고 구현 객체를 바깥에서 받는다면, 바깥은 원래 구현 대신 그것을 감싼 다른 객체를 넣어 줄 수 있다. 감싼 객체가 같은 인터페이스를 구현하고 계약을 지키는 한 클라이언트는 차이를 모른다. 트랜잭션을 시작하고 끝내는 코드, 실행 시간을 재는 코드가 업무 로직에 한 줄도 없이 끼어들 수 있는 것이 이 구조 덕분이다. 그리고 바이트코드에서 본 invokeinterface의 실행 시점 메서드 선택이 그 모든 것을 떠받친다.

    이 장의 핵심

    인터페이스를 쓰는 것만으로는 구현에서 자유로워지지 않는다. 객체를 만드는 new가 구현 클래스의 이름을 클래스 파일에 새겨 넣기 때문이다. 쓰는 코드에서 만드는 코드를 떼어 내 구성 영역으로 옮기면, 사용 영역은 인터페이스만 알게 되고(DIP) 구현 교체가 구성 영역의 변경으로 끝난다(OCP). 바깥에서 구현 객체를 만들어 넣어 주는 것이 의존관계 주입이고, 그 일을 맡은 존재가 DI 컨테이너이며, 스프링 컨테이너는 손으로 쓴 구성 클래스가 하던 생성·보관·연결을 범용으로 대신한다.
    역할과 구현의 분리
    요구사항에서 정해지지 않았거나 바뀔 부분을 인터페이스(역할) 뒤에 두고 지금 가능한 구현으로 채운다. 성공의 기준은 구현을 바꿀 때 클라이언트 코드가 바뀌지 않는 것이다.
    정적 의존관계와 동적 의존관계
    정적 의존관계는 소스의 import 문과 클래스 파일의 상수 풀에 적힌 클래스 사이의 관계이고, 동적 의존관계는 실행 중 힙에서 객체가 객체를 참조하는 관계다. 앞의 것은 클래스 다이어그램, 뒤의 것은 객체 다이어그램으로 그린다.
    클래스 파일에 기록되는 의존
    new 구현()은 구현 클래스의 이름을 상수 풀에 남기고, 인터페이스 메서드 호출은 invokeinterface로 인터페이스 이름만 남긴다. jdeps로 그 목록을 뽑아 볼 수 있고, 기록된 클래스가 없으면 컴파일도 실행도 되지 않는다.
    DIP 위반이 OCP 위반으로 이어지는 이유
    클라이언트가 구현 클래스를 직접 만들면 추상과 구체에 함께 의존하게 된다. 구현을 교체하려면 그 new가 있는 클라이언트의 소스를 고쳐야 하므로, 확장이 곧 기존 코드의 변경이 된다.
    관심사의 분리와 구성 영역
    업무 로직을 실행하는 사용 영역과 객체를 만들고 연결하는 구성 영역을 가른다. 구현 클래스의 이름은 구성 영역(AppConfig)에만 있고, 구현 교체는 그곳의 변경으로 끝난다.
    생성자 주입
    협력 객체를 생성자의 인자로 받아 final 필드에 저장한다. 협력 객체 없이는 객체를 만들 수 없고, 테스트에서는 스텁을 넣어 그 클래스만 검사할 수 있다.
    "하나"의 문제
    본문에 new가 있는 메서드는 부를 때마다 새 객체를 만든다. 공유해야 할 객체는 조립하는 쪽이 한 번만 만들어 보관해야 하며, 순수 자바에서는 필드로, 스프링에서는 컨테이너의 보관소로 해결한다.
    IoC와 DI
    제어의 역전은 객체의 생성과 실행 흐름에 대한 결정이 그 객체 바깥에 있는 구조다. 의존관계 주입은 그 가운데 실행 시점에 바깥에서 구현 객체를 만들어 넣어 주어 동적 의존관계를 맺는 방식이다.
    스프링 컨테이너로의 전환
    @Configuration 클래스의 @Bean 메서드가 빈 정의가 되고, ApplicationContext가 생성될 때 그 메서드들을 호출해 객체를 만들어 보관한다. 사용 영역의 클래스 파일은 전환 전과 같다.

    모든 클래스에 인터페이스를 붙여야 하는 것은 아니다. 역할과 구현을 나누면 파일이 늘고, 코드를 읽을 때 한 단계를 더 건너야 한다. 이 비용을 치를 만한 곳은 이 회차의 요구사항처럼 바뀔 것이 예상되는 지점이다. 외부 시스템과 닿는 곳, 저장 기술이 정해지지 않은 곳, 기획이 자주 바뀌는 정책, 테스트에서 실제 구현을 쓰기 어려운 곳이 그렇다. 반대로 구현이 하나뿐이고 바뀔 조짐이 없다면 구체 클래스를 생성자로 받는 것으로 시작해도 된다. 생성자 주입 구조만 지켜 두면 나중에 인터페이스를 뽑아내는 변경은 그 클래스와 구성 코드에 한정된다. 포기하면 안 되는 것은 인터페이스가 아니라 "쓰는 코드가 협력 객체를 스스로 만들지 않는다"는 구조다.

    기존 코드에서 이 회차의 문제를 찾을 때는 new만 보면 놓친다. 업무 클래스 안에서 XxxFactory.getInstance() 같은 정적 메서드로 협력 객체를 얻어 오는 코드, 상태를 가진 static 필드에 직접 접근하는 코드도 구현 클래스의 이름을 클라이언트에 새긴다는 점에서 같은 문제다. 증상도 같다. 그 클래스만 떼어 테스트할 수 없고, 구현을 바꾸려면 호출하는 쪽을 전부 찾아 고쳐야 한다. 이 회차에서 쓴 static 맵이 그 축소판이다. 변경 가능한 static 상태는 프로세스 전체가 공유하는 전역 변수이므로 테스트 사이에 데이터가 새고, 서버처럼 여러 스레드가 도는 환경에서는 동시 접근 문제까지 더해진다.

    구성 정보를 바꾸는 방식의 교체는 배포 시점의 결정에 맞는다. 정책이 실행 중에 바뀌어야 한다면 사정이 다르다. 이벤트 기간에만 정률로 깎는다거나 회원 등급에 따라 다른 계산식을 쓴다는 요구는 "어떤 부품으로 구성하는가"가 아니라 업무 규칙이다. 이런 규칙을 구성 코드의 분기문에 넣으면 구성 영역이 업무 로직을 품게 된다. 날짜나 조건을 보고 알맞은 정책에 위임하는 DiscountPolicy 구현을 하나 더 만드는 편이 낫다. 그 구현도 계약을 지키는 한 주문 서비스는 여전히 바뀌지 않는다.

    금액 계산은 한 줄이어도 가볍게 넘기지 않는다. 정수 나눗셈이 소수부를 버린다는 것, 연산 순서가 결과를 바꾼다는 것, int 곱셈이 넘쳐도 예외가 나지 않는다는 것은 모두 조용한 오류다. 운영에서 "가끔 1원이 안 맞는다"거나 "고액 주문에서만 금액이 이상하다"는 형태로 드러나고 재현이 어렵다. 올림·버림 규칙을 정책의 계약으로 정하고, 경계값을 테스트로 고정하고, 다룰 금액의 최대 범위에 맞는 타입을 고르는 일은 정책 클래스를 만들 때 함께 해야 한다.

DiscountPolicy를 구현하고 discount가 항상 0을 돌려주는 클래스(예: NoDiscountPolicy)를 shop.discount 패키지에 새로 만들고, AppConfig.discountPolicy()의 return 문을 그 클래스로 바꾼다. 고치는 기존 파일은 AppConfig.java 하나다. 컴파일 결과를 비교하면 NoDiscountPolicy.class가 새로 생기고 AppConfig.class의 내용이 달라진다. OrderServiceImpl.class를 비롯한 나머지는 바이트 단위로 같다. 0은 "0 이상 가격 이하"를 만족하므로 계약을 지킨다. 다만 가격이 음수로 들어오는 경우까지 따지면 0이 가격보다 커지는데, 그것은 정책이 아니라 주문 서비스가 입력을 받는 단계에서 걸러야 할 문제다. 한 가지 더 생각할 점이 있다. 이벤트가 끝나면 다시 구성을 고쳐 배포해야 한다. 기간이 코드로 정해져 있다면 날짜를 보고 두 정책 가운데 하나에 위임하는 구현을 만드는 편이 배포 횟수를 줄인다.

    5. 주문은 정상적으로 만들어진다. orderService()는 본문에서 policy()를 자바 메서드로 직접 호출하므로 빈 이름과 관계없이 정책 객체를 받는다. 추가한 줄에서는 NoSuchBeanDefinitionException: No bean named 'discountPolicy' available이 난다. @Bean 메서드로 등록된 빈의 이름은 따로 지정하지 않으면 메서드 이름이므로, 메서드 이름을 바꾸는 순간 빈 이름도 policy로 바뀌었다. ac.getBean("policy", DiscountPolicy.class)로 꺼내면 된다. 이 문제에서 얻을 교훈은 이름으로 빈을 꺼내는 코드가 문자열에 의존한다는 점이다. 메서드 이름을 바꾸는 리팩터링을 컴파일러가 따라가 주지 못하고, 실행해야 오류가 드러난다. 이름을 유지해야 한다면 @Bean("discountPolicy")처럼 이름을 직접 지정할 수 있다.

     처음 구조의 OrderServiceImpl은 필드를 private final DiscountPolicy discountPolicy = new FlatDiscountPolicy();로 선언했다. 필드 타입이 인터페이스인데도 DIP를 어겼다고 하는 근거로 가장 정확한 것은? 인터페이스 타입의 필드에는 final을 붙일 수 없는데 붙였기 때문이다. discount 메서드를 호출할 때 JVM이 FlatDiscountPolicy의 메서드를 실행하기 때문이다. new FlatDiscountPolicy() 때문에 이 클래스의 소스와 클래스 파일에 구현 클래스의 이름이 기록되어, 그 클래스 없이는 컴파일도 실행도 되지 않기 때문이다. 인터페이스에 구현 클래스가 둘 이상 있기 때문이다. DIP는 구체에 의존하지 말라는 원칙이고, 의존 여부는 선언 타입이 아니라 그 클래스가 어떤 이름을 알고 있는가로 판정한다. 본문의 javap 출력에서 new #16 // class shop/discount/FlatDiscountPolicy가 그 기록이고, jdeps 목록에 구현 클래스가 나타났으며, 클래스 파일을 지우자 생성자에서 NoClassDefFoundError가 났다. 실행 시점에 구현의 메서드가 선택되는 것은 다형성의 정상 동작이지 위반이 아니다. final과 구현의 개수는 관계가 없다. 구성 영역을 분리한 뒤 할인 정책을 정액에서 정률로 바꿨더니 OrderServiceImpl.class가 바이트 단위로 같았는데도 주문에는 정률 할인이 적용되었다. 이것이 가능한 이유는? 컴파일러가 OrderServiceImpl 안에 두 정책의 코드를 모두 넣어 두고 실행할 때 골라 쓰기 때문이다. 호출 지점에는 인터페이스 메서드의 이름만 적혀 있고, 실제로 실행할 메서드는 필드가 가리키는 객체의 실행 시점 타입을 기준으로 선택되기 때문이다. JVM이 시작할 때 클래스패스의 모든 DiscountPolicy 구현을 로딩해 가장 최근에 컴파일된 것을 고르기 때문이다. AppConfig가 실행 중에 OrderServiceImpl의 바이트코드를 고쳐 쓰기 때문이다. 주문 서비스의 바이트코드에서 할인 호출은 invokeinterface DiscountPolicy.discount다. 어느 구현을 실행할지는 그 순간 필드에 들어 있는 객체가 정하고, 그 객체는 AppConfig가 만들어 생성자로 넣어 준 것이다. 그래서 정적 의존관계(클래스 파일)는 그대로 두고 동적 의존관계(객체 참조)만 바꿀 수 있다. 본문의 로딩 로그에서 쓰지 않는 구현은 로딩조차 되지 않았으므로 구현을 전부 로딩해 고른다는 설명은 틀리다. 컴파일러나 구성 클래스가 주문 서비스의 코드를 건드리는 일도 없다. 순수 자바 AppConfig에서 memberRepository()의 본문이 return new MemoryMemberRepository();이고 저장소의 맵은 인스턴스 필드다. memberService()로 얻은 서비스로 회원을 가입시킨 뒤 orderService()로 얻은 서비스로 주문하면 "없는 회원" 오류가 난다. 원인으로 옳은 것은? HashMap이 스레드에 안전하지 않아서 저장한 값이 사라졌기 때문이다. AppConfig 객체를 하나만 만들었기 때문이다. 생성자 주입은 객체를 복사해서 넣어 주므로 두 서비스가 서로 다른 복사본을 받았기 때문이다. 메서드를 부를 때마다 본문의 new가 다시 실행되어 두 서비스가 서로 다른 저장소 객체를 받았고, 각 저장소가 자기 맵을 따로 갖기 때문이다. 자바의 메서드 호출은 본문을 다시 실행하는 것이므로 memberRepository()를 두 번 부르면 저장소 객체가 둘 생긴다. 본문 실험에서 생성 로그가 두 번 찍힌 것이 그 증거다. 회원은 첫 번째 저장소의 맵에 들어갔고 주문 서비스는 비어 있는 두 번째 저장소를 조회했다. 생성자 주입은 객체를 복사하지 않고 참조를 넘긴다. 이 프로그램은 스레드가 하나뿐이어서 HashMap의 스레드 안전성은 원인이 아니다. 해결은 조립하는 쪽이 저장소를 한 번만 만들어 같은 참조를 나눠 주는 것이다. 스프링 버전에서 OrderServiceImpl의 생성자에 호출 스택을 찍었더니 맨 아래가 OrderApp.main, 그 위가 AnnotationConfigApplicationContext의 생성자와 refresh, 중간에 Method.invoke, 그 위가 AppConfig.orderService였다. 이 스택이 보여 주는 것으로 옳은 것은? 우리 코드가 orderService()를 직접 호출하지 않았고, 컨테이너가 초기화 과정에서 리플렉션으로 그 메서드를 호출해 객체를 만들었다. 호출의 주도권이 프레임워크에 있다. main이 getBean을 호출한 순간에 비로소 주문 서비스가 만들어졌다. OrderServiceImpl이 스프링의 클래스를 상속하고 있어서 스프링이 생성자를 호출할 수 있었다. AppConfig의 메서드가 static이라서 객체 없이 호출되었다. 스택은 아래에서 위로 호출 순서를 보여 준다. main은 컨테이너의 생성자만 불렀고, 그 안의 refresh가 싱글톤 빈을 미리 만드는 단계에서 Method.invoke로 orderService()를 호출했다. 이것이 제어의 역전이다. 스택에 getBean을 부르는 main의 줄이 없고 생성 로그가 "컨테이너 생성 완료"보다 먼저 나왔으므로 조회 시점에 만들어진 것이 아니다. OrderServiceImpl은 스프링의 어떤 클래스도 참조하지 않는 평범한 클래스이고, @Bean 메서드는 인스턴스 메서드다. 골드 회원에게 10%를 깎아 주는 정책에서 할인 금액을 price * 10 / 100으로 계산한다(price는 int). 이 식에 대한 설명으로 옳은 것은? 결과는 항상 소수 첫째 자리에서 반올림된 값이다. price / 100 * 10으로 순서를 바꿔도 모든 가격에서 결과가 같다. 나눗셈에서 소수부가 버려지고, price * 10이 int 범위를 넘으면 예외 없이 엉뚱한 값이 되어 음수 할인까지 나올 수 있다. 곱셈 결과가 int 범위를 넘으면 JVM이 ArithmeticException을 던져 알려 준다. 자바의 정수 나눗셈은 몫을 0 쪽으로 잘라 내므로 12,559원의 10%는 1,255가 된다. 나눗셈을 먼저 하면 그 자리에서 소수부가 사라져 1,250이 되므로 순서에 따라 결과가 다르다. int 곱셈은 넘쳐도 예외를 던지지 않고 상위 비트가 잘린 값을 내놓는다. 본문에서 3억 원에 대해 할인 금액이 음수로 계산된 것이 그 예다. 넘침을 예외로 받고 싶다면 Math.multiplyExact를 쓰거나 곱하기 전에 long으로 넓혀야 한다.
    역할과 구현(role / implementation)
    역할은 클라이언트가 기대하는 기능의 약속으로 인터페이스로 표현하고, 구현은 그 약속을 실제로 수행하는 클래스다. 클라이언트가 역할만 알면 구현을 바꿔 끼울 수 있다.
    정적 의존관계(static dependency)
    소스 코드와 클래스 파일만 보고 알 수 있는 클래스 사이의 의존. 한 클래스가 다른 클래스의 이름을 쓰면 생긴다.
    동적 의존관계(dynamic dependency)
    실행 중에 객체가 다른 객체의 참조를 가짐으로써 생기는 의존. 어떤 구현 객체가 연결되었는지는 실행해야 정해진다.
    상수 풀(constant pool)
    클래스 파일 안에서 그 클래스가 쓰는 클래스 이름, 메서드 이름, 문자열 같은 상수를 모아 둔 표. 바이트코드 명령은 이 표의 번호로 대상을 가리킨다.
    심벌릭 참조(symbolic reference)
    상수 풀에 이름으로 적혀 있는 클래스·필드·메서드에 대한 참조. JVM이 실행 중에 이것을 실제 대상으로 바꾸는 과정을 해석(resolution)이라고 한다.
    관심사의 분리(separation of concerns)
    바뀌는 이유가 다른 일들을 서로 다른 곳에 두는 것. 이 회차에서는 업무 로직의 실행과 객체의 생성·연결을 갈랐다.
    생성자 주입(constructor injection)
    객체가 필요로 하는 협력 객체를 생성자의 인자로 받는 방식. 객체가 만들어지는 순간 의존관계가 완성된다.
    제어의 역전(Inversion of Control)
    객체를 언제 만들고 무엇과 연결하고 언제 호출할지를 그 객체가 아니라 바깥(구성 코드나 프레임워크)이 결정하는 구조.
    의존관계 주입(Dependency Injection)
    실행 시점에 바깥에서 구현 객체를 만들어 클라이언트에 전달해 동적 의존관계를 맺어 주는 방식. 제어의 역전의 한 형태다.
    DI 컨테이너(DI container)
    객체를 생성하고 보관하며 의존관계를 연결해 주는 것. IoC 컨테이너라고도 하며, 스프링에서는 ApplicationContext가 이 역할을 한다.
