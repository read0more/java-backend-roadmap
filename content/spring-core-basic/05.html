    이 회차의 질문: 설정 클래스에 적지 않은 빈은 어디에서 오는가

    앞 회차까지는 설정 클래스에 @Bean 메서드를 하나씩 적어 빈을 등록했다. 메서드 이름이 빈 이름이 되고, 메서드 본문에서 다른 @Bean 메서드를 부르는 것이 곧 의존관계의 표현이었다. 이 방식은 어떤 객체가 어떤 객체를 쓰는지가 한 파일에 모여 있다는 장점이 있다. 대신 클래스가 늘어나는 만큼 설정 클래스도 같이 길어진다.

    곤란한 점은 길이보다 두 군데를 맞춰야 한다는 데 있다. 서비스 클래스를 하나 새로 만들면 설정 클래스에도 메서드를 하나 추가해야 한다. 한쪽만 고치고 다른 쪽을 빠뜨려도 컴파일은 된다. 빠뜨린 사실은 컨테이너가 그 타입의 빈을 찾다가 실패하는 실행 시점에야 드러난다. 빈이 수백 개인 애플리케이션에서 이 일을 사람이 계속 맞추는 것은 실수가 생기기 쉬운 구조다.

    컴포넌트 스캔(component scan)은 이 중복을 없앤다. 클래스에 "이것은 빈이다"라는 표시를 붙여 두면, 컨테이너가 시작할 때 정해진 패키지 아래를 뒤져 표시가 붙은 클래스를 찾아 스스로 등록한다. 설정 클래스에 한 줄씩 적던 목록이 사라지고, 등록 여부는 클래스 자신이 들고 다닌다. 그런데 목록이 사라지면 새 질문이 생긴다. 컨테이너는 어디를 뒤지는가. 표시를 무엇으로 읽는가. 표시가 붙은 클래스 가운데 일부만 넣거나 빼려면 어떻게 하는가. 이름이 겹치면 누가 이기는가.

    이 회차는 그 네 질문을 순서대로 다룬다. 스프링 입문 권에서 컴포넌트 스캔을 한 번 써 보았으므로 사용법은 짧게 상기하고, 지면은 그 아래에 쓴다. 패키지 이름이 파일 목록으로 바뀌는 과정, 클래스 파일 안에서 애노테이션이 놓인 자리, 스캐너가 후보를 두 번 걸러 빈 정의로 만드는 규칙, 그리고 같은 이름을 두고 벌어지는 충돌의 판정이다. 스캔으로 등록된 빈에 의존관계를 채우는 방법의 여러 갈래는 6회의 몫이므로 여기서는 생성자 하나만 쓴다.

    확인 방법을 밝혀 둔다. 스프링 없이 만든 실험 코드의 출력은 JDK 21(Temurin 21.0.13)에서 직접 실행해 얻었다. 스프링 내부 동작은 Spring Framework 6.2.x와 Spring Boot 3.5.x의 소스, 그리고 해당 클래스의 Javadoc에서 확인했고, 스프링 예제의 출력은 그 소스의 흐름으로 결정되는 것만 적었다. 내부 클래스 이름과 예외 문구는 버전에 따라 달라질 수 있다.

    컴포넌트 스캔과 자동 주입을 시작한다

    좌석을 예약하는 작은 프로그램을 예로 든다. 좌석 저장소 인터페이스와 메모리 구현, 그 저장소를 쓰는 서비스가 있다. 패키지는 seat와 그 아래 seat.store 둘이다. 먼저 설정 클래스다. 본문이 비어 있다.

    package seat;

import org.springframework.context.annotation.ComponentScan;
import org.springframework.context.annotation.Configuration;

@Configuration
@ComponentScan
public class SeatConfig {
}

    다음은 빈이 될 클래스들이다. 저장소 구현에는 @Repository를, 서비스에는 @Service를 붙였다. 인터페이스에는 아무것도 붙이지 않았다.

    package seat.store;

public interface SeatStore {
    boolean reserve(String seat);
}
    package seat.store;

import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import org.springframework.stereotype.Repository;

@Repository
public class MemorySeatStore implements SeatStore {
    private final Set taken = ConcurrentHashMap.newKeySet();

    @Override
    public boolean reserve(String seat) {
        return taken.add(seat);      // 처음 넣으면 true, 이미 있으면 false
    }
}
    package seat;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Service;
import seat.store.SeatStore;

@Service
public class SeatService {
    private final SeatStore seatStore;

    @Autowired
    public SeatService(SeatStore seatStore) {
        this.seatStore = seatStore;
    }

    public boolean reserve(String seat) {
        return seatStore.reserve(seat);
    }
}

    실행 코드는 등록된 빈 정의 가운데 애플리케이션이 등록한 것만 골라 이름순으로 찍고, 서비스를 꺼내 같은 좌석을 두 번 예약한다.

    package seat;

import java.util.Arrays;
import org.springframework.beans.factory.config.BeanDefinition;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class SeatMain {
    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(SeatConfig.class)) {
            Arrays.stream(ctx.getBeanDefinitionNames())
                    .filter(name -> ctx.getBeanDefinition(name).getRole() == BeanDefinition.ROLE_APPLICATION)
                    .sorted()
                    .forEach(name -> System.out.println(
                            name + " : " + ctx.getBeanDefinition(name).getClass().getSimpleName()));

            SeatService service = ctx.getBean(SeatService.class);
            System.out.println(service.reserve("A-12"));
            System.out.println(service.reserve("A-12"));
        }
    }
}

    출력의 앞 세 줄이 이 회차 전체의 요약이다. 컨테이너에 직접 넘긴 것은 SeatConfig 하나인데 빈 정의는 셋이다. seatConfig는 생성자 인자로 넘겨서 등록된 것이고, 그 정의의 종류는 AnnotatedGenericBeanDefinition이다. 나머지 둘은 누구도 이름을 적어 준 적이 없는데 등록되었고, 정의의 종류가 ScannedGenericBeanDefinition이다. 이름 그대로 스캔으로 찾아낸 정의라는 뜻이다. SeatStore 인터페이스와 SeatMain은 같은 패키지 아래에 있지만 목록에 없다.

    빈 이름은 클래스 이름의 첫 글자를 소문자로 바꾼 것이다. MemorySeatStore는 memorySeatStore가 되고 SeatService는 seatService가 되었다. 이 규칙에는 예외가 하나 있는데 뒤에서 정확히 본다. 마지막 두 줄은 같은 좌석을 두 번 예약한 결과다. 첫 호출은 true, 두 번째는 false이므로 서비스가 받은 저장소가 실제로 동작하는 MemorySeatStore 객체라는 것을 알 수 있다.

    자동 주입이 함께 필요한 이유

    @Bean 메서드로 등록할 때는 new SeatService(seatStore())처럼 메서드 본문이 "무엇을 무엇에 넣는가"를 말해 주었다. 스캔으로 등록한 빈 정의에는 그런 본문이 없다. 정의가 가진 것은 클래스 이름 seat.SeatService와 스코프 같은 몇 가지 속성뿐이다. 이 클래스의 생성자는 SeatStore를 하나 요구하는데, 그 인자를 어디서 가져올지 적어 둔 곳이 어디에도 없다.

    그래서 연결 정보도 클래스 안으로 들어가야 한다. 생성자에 붙인 @Autowired가 그 표시다. 컨테이너는 SeatService 객체를 만들 차례가 되면 이 생성자의 매개변수 타입을 보고, 자기가 가진 빈 가운데 SeatStore 타입에 대입할 수 있는 것을 찾는다. 여기서는 memorySeatStore 하나가 맞으므로 그 객체를 먼저 만들고 생성자 인자로 넘긴다. 이름이 아니라 타입으로 찾는다는 점이 핵심이다.

    스프링 레퍼런스는 대상 빈이 생성자를 하나만 정의하면 그 생성자의 @Autowired는 필요하지 않다고 적는다. 생성자가 여럿이고 기본 생성자가 없으면 어느 것을 쓸지 알려 주기 위해 적어도 하나에 붙여야 한다. 위 예제는 생성자가 하나라서 지워도 결과가 같지만, 표시가 무엇을 뜻하는지 보이도록 남겨 두었다. 같은 타입의 빈이 둘 이상이거나 하나도 없을 때의 규칙, 필드와 세터에 주입하는 방법은 6회에서 다룬다.

    이 장의 핵심

    컴포넌트 스캔은 "어떤 클래스를 빈으로 등록할 것인가"를 설정 클래스에서 각 클래스로 옮기고, 자동 주입은 "그 빈에 무엇을 넣을 것인가"를 설정 클래스에서 각 클래스의 생성자로 옮긴다. 둘은 따로 떨어진 기능이지만 스캔을 쓰는 순간 연결을 적을 자리가 사라지므로 늘 함께 쓰인다.

    스캔은 컨테이너가 시작하는 과정의 어디에서 일어나는가

    @ComponentScan은 애노테이션이다. 애노테이션은 클래스 파일에 적힌 정보일 뿐이고 스스로 실행되지 않는다. 누군가 이 정보를 읽고 패키지를 뒤져야 한다. 그 일이 언제 누구의 손에서 일어나는지를 알면, 뒤에 나오는 충돌의 판정 순서가 자연스럽게 설명된다.

    출발점은 new AnnotationConfigApplicationContext(SeatConfig.class)다. 이 생성자의 본문은 세 줄이다. 먼저 인자 없는 생성자를 불러 AnnotatedBeanDefinitionReader와 ClassPathBeanDefinitionScanner를 만든다. 다음으로 register(SeatConfig.class)로 설정 클래스 하나를 빈 정의로 등록한다. 마지막으로 refresh()를 부른다. 리더가 만들어질 때 컨테이너가 스스로 쓰는 처리기 몇 개도 빈 정의로 함께 등록된다. 그 가운데 둘이 이 회차와 관계가 있다. 설정 클래스를 해석하는 ConfigurationClassPostProcessor와 @Autowired를 처리하는 AutowiredAnnotationBeanPostProcessor다. 앞의 실행 코드에서 역할이 ROLE_APPLICATION인 정의만 고른 것은 이 내부 처리기들을 출력에서 빼기 위해서였다.

    refresh()가 시작되는 시점에 컨테이너가 아는 애플리케이션 빈 정의는 seatConfig 하나뿐이다. refresh()는 빈 객체를 만들기 전에 먼저 빈 팩토리 후처리기(bean factory post-processor)들을 실행한다. 이 후처리기는 "빈 정의 목록을 고칠 기회"를 받는 객체다. ConfigurationClassPostProcessor가 이 단계의 앞쪽에서 움직인다. 이 클래스의 Javadoc은 설정 클래스의 @Bean 메서드에 대응하는 빈 정의가 다른 후처리기보다 먼저 등록되어 있어야 하므로 우선순위를 가진다고 설명한다.

    이 후처리기는 이미 등록된 정의를 훑어 설정 클래스 후보를 고르고, 각 후보의 애노테이션을 정해진 순서로 처리한다. 6.2.x 소스에서 그 순서는 중첩 클래스, @PropertySource, @ComponentScan, @Import, @ImportResource, @Bean 메서드, 인터페이스의 디폴트 메서드, 상위 클래스다. @ComponentScan을 만나면 그 자리에서 곧바로 스캔을 실행한다. 소스의 주석도 설정 클래스에 @ComponentScan이 붙어 있으면 스캔을 즉시 수행한다고 적고 있다. 반면 @Bean 메서드는 이 단계에서 "이런 메서드가 있다"고 기록만 해 두고, 모든 설정 클래스의 해석이 끝난 뒤에 한꺼번에 빈 정의로 등록한다.

    이 흐름에서 세 가지를 기억해 두자. 첫째, 스캔은 빈 정의를 등록하는 일이지 객체를 만드는 일이 아니다. 스캔이 끝난 시점에 SeatService나 MemorySeatStore의 인스턴스는 하나도 없다. 객체는 모든 정의가 모인 뒤 마지막 단계에서 만들어진다. 그래서 스캔이 클래스를 발견하는 순서와 무관하게, 컨테이너는 SeatService를 만들 때 필요한 SeatStore 타입의 정의를 이미 알고 있다.

    둘째, 스캔으로 찾은 클래스는 다시 설정 클래스 후보로 검사된다. 6.2.x의 ConfigurationClassUtils는 @Component, @ComponentScan, @Import, @ImportResource 가운데 하나가 붙어 있거나 @Bean 메서드를 가진 클래스를 후보로 본다. 따라서 스캔 범위 안에 다른 @Configuration 클래스가 있으면 그 클래스도 빈으로 등록되고, 그 안의 @Bean 메서드와 @ComponentScan까지 이어서 처리된다. 설정 클래스 하나에서 출발한 해석이 패키지 전체로 번져 나가는 구조다.

    셋째, 같은 설정 클래스 안에서는 스캔으로 찾은 정의가 @Bean 메서드의 정의보다 먼저 등록된다. 이 순서는 이름이 겹칠 때 누가 "기존 정의"이고 누가 "새 정의"인지를 정하므로, 수동 등록과 자동 등록의 충돌을 다루는 절에서 다시 쓰인다.

    컨텍스트가 처음에 만들어 둔 ClassPathBeanDefinitionScanner는 ctx.scan("seat")처럼 코드로 스캔을 요청할 때 쓰인다. @ComponentScan을 처리할 때는 ComponentScanAnnotationParser가 애노테이션의 속성값으로 스캐너를 따로 하나 더 만든다. 두 경로 모두 실제 스캔은 같은 클래스의 doScan이 한다.

    한 층 아래 1: 패키지 이름이 파일 목록이 되기까지

    스캐너가 받는 입력은 "seat" 같은 문자열 하나다. JVM에는 "이 패키지에 속한 클래스를 전부 알려 달라"는 기능이 없다. 클래스 로더는 이름을 주면 그 클래스를 찾아 주는 방향으로만 동작하고, 아직 로딩하지 않은 클래스의 목록을 내놓지 않는다. 그래서 스캐너는 패키지를 자원 경로로 바꿔 파일을 찾는 길을 택한다.

    6.2.x의 ClassPathScanningCandidateComponentProvider는 기준 패키지 이름의 점을 슬래시로 바꾼 뒤 앞에 classpath*:를, 뒤에 /**/*.class를 붙인다. seat는 classpath*:seat/**/*.class가 된다. 뒤쪽의 **/*.class는 @ComponentScan의 resourcePattern 속성 기본값이고, 하위 디렉터리를 깊이에 상관없이 포함한다는 뜻이다. 이 패턴을 실제 파일 목록으로 바꾸는 일은 PathMatchingResourcePatternResolver가 맡는다.

    이 클래스의 Javadoc에 따르면 classpath*: 접두어는 내부에서 ClassLoader.getResources() 호출로 처리된다. 와일드카드가 섞인 패턴이면 와일드카드가 나오기 전 마지막 경로 조각까지, 여기서는 seat/까지를 클래스 로더에 물어 그 디렉터리를 가진 클래스패스 위치를 모두 얻는다. 그다음은 얻은 URL의 종류에 따라 갈린다. 파일 시스템의 디렉터리이면 그 아래를 걸어 내려가며 패턴에 맞는 파일을 고르고, jar 안의 경로이면 jar 파일의 엔트리 목록을 훑어 고른다.

    이 과정을 스프링 없이 흉내 내 보자. 실험용 패키지 scanlab.app에 클래스 몇 개를 두고, 그 패키지 아래의 클래스 파일을 모두 찾아 각 파일에 붙은 애노테이션을 찍는 프로그램이다. 애노테이션을 읽는 ClassFileAnnotations.read는 다음 절에서 만든다. 지금은 파일을 찾는 부분에 집중한다.

    package scanlab;

// import 생략: java.io, java.net, java.nio.file, java.util, java.util.jar, java.util.stream

public class MiniScanner {

    public static void main(String[] args) throws Exception {
        String basePath = "scanlab.app".replace('.', '/');          // scanlab/app
        ClassLoader loader = MiniScanner.class.getClassLoader();

        Map classFiles = new TreeMap<>();            // 자원 경로 -> 파일 내용
        Enumeration roots = loader.getResources(basePath);
        while (roots.hasMoreElements()) {
            URL root = roots.nextElement();
            System.out.println("루트 프로토콜: " + root.getProtocol());
            if (root.getProtocol().equals("file")) {
                Path dir = Path.of(root.toURI());
                try (Stream walk = Files.walk(dir)) {
                    for (Path p : walk.filter(f -> f.toString().endsWith(".class")).toList()) {
                        String rel = dir.relativize(p).toString().replace('\\', '/');
                        classFiles.put(basePath + "/" + rel, Files.readAllBytes(p));
                    }
                }
            } else if (root.getProtocol().equals("jar")) {
                JarFile jar = ((JarURLConnection) root.openConnection()).getJarFile();
                for (JarEntry e : jar.stream().toList()) {
                    if (e.getName().startsWith(basePath + "/") && e.getName().endsWith(".class")) {
                        try (InputStream in = jar.getInputStream(e)) {
                            classFiles.put(e.getName(), in.readAllBytes());
                        }
                    }
                }
            }
        }

        System.out.println("1단계: 파일만 읽는다");
        for (Map.Entry e : classFiles.entrySet()) {
            List annotations = ClassFileAnnotations.read(e.getValue());
            System.out.println("  " + e.getKey() + " -> " + annotations);
        }

        System.out.println("2단계: 후보 하나를 실제로 쓴다");
        Class type = Class.forName("scanlab.app.MemorySeatStore");
        Object bean = type.getDeclaredConstructor().newInstance();
        System.out.println("  만든 객체의 클래스: " + bean.getClass().getName());
    }
}

    실험용 클래스는 다섯 개다. MemorySeatStore와 하위 패키지의 web.SeatController에는 직접 만든 @Component를, SeatService에는 직접 만든 @Service를 붙였다. SeatStore 인터페이스와 유틸리티 클래스 SeatCodec에는 아무것도 없다. 인터페이스를 뺀 네 클래스에는 static { System.out.println(" [클래스 초기화] ..."); } 블록을 넣어 초기화되는 순간이 보이게 했다. 컴파일 결과를 out 디렉터리에 두고 실행한 결과다.

    같은 클래스들을 jar cf app.jar -C out .으로 묶어 java -cp app.jar scanlab.MiniScanner로 실행하면 첫 줄만 루트 프로토콜: jar로 바뀌고 나머지 출력은 같다. 클래스 로더가 돌려준 URL이 디렉터리가 아니라 jar 안의 경로를 가리키므로 파일 시스템을 걸어 내려갈 수 없고, jar의 엔트리 목록에서 경로가 scanlab/app/로 시작하는 것을 골라야 한다. PathMatchingResourcePatternResolver가 두 갈래의 코드를 따로 갖고 있는 이유가 이것이다.

    디렉터리 엔트리가 없는 jar와 기본 패키지

    실험을 하나 더 했다. 같은 클래스 파일을 zip -r -D로 묶어 디렉터리 엔트리 없이 파일 엔트리만 든 jar를 만들고 그것으로 실행했다. 결과는 달라진다. 루트 프로토콜 줄이 아예 나오지 않고 1단계 목록이 비어 있다. getResources("scanlab/app")이 아무것도 돌려주지 않은 것이다. 그런데 2단계의 Class.forName은 그대로 성공한다.

    클래스를 이름으로 로딩하는 일은 scanlab/app/MemorySeatStore.class라는 파일 엔트리만 있으면 된다. 반면 패키지를 자원으로 찾는 일은 scanlab/app/이라는 디렉터리 엔트리가 jar 안에 있어야 성립한다. 스프링 레퍼런스의 클래스패스 스캐닝 절에도 같은 주의가 적혀 있다. 클래스패스 패키지의 스캔에는 대응하는 디렉터리 엔트리가 클래스패스에 있어야 한다는 내용이다. "클래스는 잘 로딩되는데 스캔만 안 된다"는 증상이 있다면 jar를 만든 방식을 의심해 볼 근거가 된다.

    패턴의 앞머리가 비면 어떻게 되는지도 이 구조에서 설명된다. package 선언이 없는 클래스는 기본 패키지(default package)에 속한다. 그런 클래스에 @ComponentScan을 붙이면 기준 패키지가 빈 문자열이 되어, 탐색이 클래스패스의 모든 위치의 뿌리에서 시작한다. 스프링 부트 레퍼런스는 기본 패키지의 사용을 피하라고 하면서 그 이유로 모든 jar의 모든 클래스를 읽게 된다는 점을 든다. 기준 패키지를 com이나 org 한 단어로 잡는 것도 정도만 다를 뿐 같은 종류의 문제를 만든다. 스캐너가 읽어야 하는 양은 기준 패키지 아래에 있는 클래스 파일의 수만큼 늘어나고, 그 파일이 내 것인지 라이브러리의 것인지는 가리지 않기 때문이다.

    한 층 아래 2: 클래스를 로딩하지 않고 애노테이션을 읽는다

    앞 절의 실험에서 가장 중요한 줄은 scanlab/app/SeatService.class -> [Lscanlab/Service;]다. 클래스를 로딩하지 않았는데 그 클래스에 무슨 애노테이션이 붙었는지 알아냈다. 이것이 가능한 까닭은 애노테이션이 클래스 파일 안에 정해진 형식으로 적혀 있고, 그 형식이 JVM 명세에 공개되어 있기 때문이다.

    실험용 애노테이션 셋의 선언부터 보자. 스프링의 것이 아니라 같은 모양으로 직접 만든 것이다.

    package scanlab;

@Target(ElementType.TYPE)

    보존 정책이 정하는 것

    자바 언어 명세 9.6.4.2절은 @Retention의 값에 따라 컴파일러가 해야 할 일을 정한다. SOURCE이면 그 애노테이션이 클래스 파일에 나타나지 않게 해야 한다. CLASS나 RUNTIME이면 클래스 파일에 기록해야 한다. RUNTIME이면 여기에 더해 리플렉션 라이브러리가 실행 중에 그 애노테이션을 내주어야 한다. @Retention을 붙이지 않으면 CLASS로 취급한다.

    CLASS (기본값)기록된다보이지 않는다쓸 수 없다. 스프링의 메타데이터 리더가 런타임에 보이는 애노테이션만 읽는다

    @Memo가 사라진 것은 SOURCE였기 때문이다. 표의 마지막 열은 스프링 쪽 사정이다. 6.2.x의 메타데이터 읽기 코드는 애노테이션을 만났을 때 그것이 런타임에 보이는 종류가 아니면 곧바로 건너뛴다. 따라서 필터에 쓸 표시용 애노테이션을 직접 만들 때 @Retention(RetentionPolicy.RUNTIME)을 빠뜨리면, 컴파일은 되고 클래스 파일에도 흔적이 남지만 스캔에서는 없는 것으로 취급된다. 스프링의 @Component와 그것을 품은 스테레오타입 애노테이션은 모두 RUNTIME이다.

    클래스 파일을 직접 읽는 80줄

    package scanlab;

import java.io.ByteArrayInputStream;
import java.io.DataInputStream;
import java.io.IOException;
import java.util.ArrayList;
import java.util.List;

/** 클래스를 로딩하지 않고, 클래스 파일의 바이트에서 클래스에 붙은 런타임 애노테이션을 읽는다. */
public class ClassFileAnnotations {

    public static List read(byte[] classFile) throws IOException {
        DataInputStream in = new DataInputStream(new ByteArrayInputStream(classFile));
        if (in.readInt() != 0xCAFEBABE) throw new IOException("클래스 파일이 아니다");
        in.skipBytes(4);                                       // minor_version, major_version
        int cpCount = in.readUnsignedShort();
        String[] utf8 = new String[cpCount];
        for (int i = 1; i < cpCount; i++) {                    // 상수 풀은 1번부터 시작한다
            int tag = in.readUnsignedByte();
            switch (tag) {
                case 1 -> utf8[i] = in.readUTF();              // CONSTANT_Utf8
                case 7, 8, 16, 19, 20 -> in.skipBytes(2);
                case 15 -> in.skipBytes(3);
                case 3, 4, 9, 10, 11, 12, 17, 18 -> in.skipBytes(4);
                case 5, 6 -> { in.skipBytes(8); i++; }         // long, double은 두 칸을 차지한다
                default -> throw new IOException("알 수 없는 상수 태그 " + tag);
            }
        }
        in.skipBytes(6);                                       // access_flags, this_class, super_class
        in.skipBytes(2 * in.readUnsignedShort());              // interfaces
        for (int kind = 0; kind < 2; kind++) {                 // fields, methods는 건너뛴다
            int members = in.readUnsignedShort();
            for (int m = 0; m < members; m++) {
                in.skipBytes(6);                               // access_flags, name, descriptor
                int attrs = in.readUnsignedShort();
                for (int a = 0; a < attrs; a++) {
                    in.skipBytes(2);
                    in.skipBytes(in.readInt());
                }
            }
        }
        List found = new ArrayList<>();
        int attrs = in.readUnsignedShort();                    // 클래스 수준 속성
        for (int a = 0; a < attrs; a++) {
            String name = utf8[in.readUnsignedShort()];
            int length = in.readInt();
            if (!name.equals("RuntimeVisibleAnnotations")) {
                in.skipBytes(length);
                continue;
            }
            int count = in.readUnsignedShort();
            for (int n = 0; n < count; n++) {
                found.add(readAnnotation(in, utf8));
            }
        }
        return found;
    }

    private static String readAnnotation(DataInputStream in, String[] utf8) throws IOException {
        String type = utf8[in.readUnsignedShort()];            // 예: Lscanlab/Component;
        int pairs = in.readUnsignedShort();
        for (int p = 0; p < pairs; p++) {
            in.skipBytes(2);                                   // 속성 이름
            skipValue(in, utf8);
        }
        return type;
    }

    private static void skipValue(DataInputStream in, String[] utf8) throws IOException {
        int tag = in.readUnsignedByte();
        switch (tag) {
            case 'e' -> in.skipBytes(4);                       // enum 상수
            case '@' -> readAnnotation(in, utf8);              // 중첩 애노테이션
            case '[' -> {                                      // 배열
                int n = in.readUnsignedShort();
                for (int i = 0; i < n; i++) skipValue(in, utf8);
            }
            default -> in.skipBytes(2);                        // 기본형, String, Class
        }
    }
}

    코드의 흐름은 위 그림을 위에서 아래로 읽는 것과 같다. 상수 풀에서는 문자열 항목만 배열에 담고 나머지는 태그별로 정해진 길이만큼 건너뛴다. long과 double 상수가 번호를 두 개 차지한다는 규칙은 JVM 명세 4.4.5절에 있다. 필드와 메서드는 각자의 속성 길이를 읽어 통째로 건너뛴다. 메서드 본문의 바이트코드는 메서드의 속성 안에 들어 있으므로 이 건너뛰기 한 번으로 코드 전체를 지나친다. 마지막에 클래스 수준 속성 목록에 이르러 이름이 RuntimeVisibleAnnotations인 것만 풀어 읽는다.

    이 프로그램은 클래스를 한 번도 JVM에 올리지 않는다. 다루는 것은 처음부터 끝까지 바이트 배열과 문자열이다. 그래서 대상 클래스의 static 블록이 실행되지 않고, 대상 클래스가 참조하는 다른 클래스가 클래스패스에 있는지도 따지지 않는다.

    스프링이 쓰는 도구: ASM 기반의 메타데이터 리더

    스프링이 하는 일도 원리는 같다. 스캐너는 찾아낸 자원마다 메타데이터 리더(MetadataReader)를 얻는다. 6.2.x의 구현인 SimpleMetadataReader는 자원의 입력 스트림을 열어 ASM 라이브러리의 ClassReader에 넘긴다. ASM은 클래스 파일을 읽고 쓰는 라이브러리이고, 스프링은 이것을 자기 패키지(org.springframework.asm) 안에 넣어 들고 다닌다. 리더는 클래스 이름, 상위 클래스 이름, 구현한 인터페이스 이름, 추상 여부, 붙어 있는 애노테이션과 그 속성값을 뽑아 메타데이터 객체로 만든다.

    리더가 ClassReader에 넘기는 옵션은 SKIP_DEBUG, SKIP_CODE, SKIP_FRAMES 셋이다. 디버그 정보와 메서드 본문의 바이트코드, 스택 맵 프레임은 해석하지 않는다는 뜻이다. 스캔에 필요한 것은 "이 클래스가 무엇이고 무엇이 붙어 있는가"이지 "메서드가 무슨 일을 하는가"가 아니기 때문이다. 위에서 직접 만든 파서가 필드와 메서드를 건너뛴 것과 같은 판단이다.

    클래스를 로딩하지 않는 데에는 이유가 있다. 클래스 하나를 로딩하려면 그 상위 클래스와 상위 인터페이스가 먼저 로딩되어야 한다. 앞의 로딩 로그에서 MemorySeatStore보다 SeatStore가 먼저 올라온 것이 그 예다. 스캔 범위의 모든 클래스를 이렇게 로딩하면 빈이 되지 않을 클래스와 그 조상들까지 메모리에 올라오고, 조상 가운데 하나라도 클래스패스에 없으면 로딩이 실패한다. 선택적으로만 쓰이는 라이브러리에 기대는 클래스가 범위 안에 하나라도 있으면 스캔 전체가 깨질 수 있다는 뜻이다. 파일만 읽는 방식에는 이런 연쇄가 없다.

    다만 "아무것도 로딩하지 않는다"는 말은 정확하지 않다. 6.2.x의 메타데이터 읽기 코드는 후보 클래스에 붙은 애노테이션의 타입은 클래스 로더로 로딩한다. 애노테이션의 속성 기본값과 그 애노테이션에 다시 붙은 애노테이션을 알아내려면 애노테이션 타입 자체가 필요하기 때문이다. 이때 애노테이션 클래스를 찾지 못하면 예외를 던지지 않고 그 애노테이션만 조용히 건너뛴다. 로딩되지 않는 것은 스캔 대상인 클래스 쪽이다.

    ASM은 자신이 아는 버전의 클래스 파일만 해석한다. 6.2.x의 SimpleMetadataReader는 해석에 실패하면 "ASM ClassReader failed to parse class file - probably due to a new Java class file version that is not supported yet"로 시작하는 예외를 던지고, 낮은 대상 버전으로 컴파일하거나 프레임워크를 올리라고 안내한다. 새 JDK로 컴파일한 클래스를 오래된 스프링으로 스캔할 때 나는 오류가 이것이다. 위 javap 출력의 major version: 65가 자바 21의 클래스 파일 버전이다.
    클래스 파일이 앞에서부터 차례로 놓인 구획들의 띠이고, 스캐너는 메서드 본문을 건너뛰고 맨 끝의 속성 구획에서 애노테이션 이름을 읽는다는 것을 보여 준다. 가로로 긴 띠 하나를 여섯 구획으로 나눈 구조 다이어그램. 왼쪽에서 오른쪽으로 구획 라벨은 "매직·버전", "상수 풀", "클래스 정보", "필드", "메서드", "속성" 순서이고, "메서드" 구획은 회색 빗금으로 흐리게 칠해 "건너뜀"이라는 작은 라벨을 붙인다. "필드" 구획도 같은 회색 빗금. 맨 오른쪽 "속성" 구획은 강조색으로 칠하고 그 아래로 확대 상자를 내려 상자 안에 두 줄 "SourceFile"과 "RuntimeVisibleAnnotations"를 적는다. "RuntimeVisibleAnnotations" 줄에서 곡선 화살표가 왼쪽 "상수 풀" 구획 안의 작은 칸 "Lscanlab/Service;"로 향한다. 띠 위쪽에는 왼쪽에서 오른쪽으로 가는 긴 화살표와 라벨 "앞에서부터 차례로 읽는다". 띠 왼쪽 바깥에는 돋보기를 든 단순한 사람 아이콘과 라벨 "스캐너". 오른쪽 아래 구석에는 X 표시가 된 작은 JVM 상자와 라벨 "클래스 로딩 없음". 흰 배경, 평면 벡터 스타일, 선은 가늘고 색은 세 가지 이하. 애노테이션은 클래스 파일 끝의 속성 구획에 이름으로 기록된다. 스캐너는 메서드 본문을 건너뛰고 이 구획만 읽는다.

    메타 애노테이션: @Service가 @Component로 통하는 이유

    앞 절에서 미뤄 둔 관찰로 돌아가자. SeatService.class의 속성에는 Lscanlab/Service;만 있고 Component라는 글자는 없었다. Component가 적힌 곳은 Service.class다. 애노테이션 선언도 컴파일하면 클래스 파일 하나가 되고, 그 선언에 붙은 애노테이션은 같은 속성에 같은 형식으로 기록된다.

    @Service라는 애노테이션에 붙은 애노테이션이 셋이고 그 가운데 하나가 @Component다. 이렇게 다른 애노테이션에 붙일 수 있는 애노테이션을 메타 애노테이션(meta-annotation)이라고 부른다. 그런데 자바 언어는 이 관계에 아무 뜻도 부여하지 않는다. 애노테이션 선언에는 extends를 쓸 수 없고, "A가 붙은 것은 B도 붙은 것으로 본다"는 규칙이 언어에 없다. 리플렉션으로 확인해 보자.

    package scanlab;

import java.lang.annotation.Annotation;
import java.util.HashSet;
import java.util.Set;
import scanlab.app.MemorySeatStore;
import scanlab.app.SeatService;

public class MetaDemo {

    static boolean hasMeta(Class type, Class target, Set> visited) {
        for (Annotation a : type.getAnnotations()) {
            Class at = a.annotationType();
            if (at.getName().startsWith("java.lang.annotation.")) continue;   // @Retention, @Target 등
            if (at == target) return true;
            if (visited.add(at) && hasMeta(at, target, visited)) return true;
        }
        return false;
    }

    public static void main(String[] args) {
        System.out.println(MemorySeatStore.class.isAnnotationPresent(Component.class));
        System.out.println(SeatService.class.isAnnotationPresent(Component.class));
        System.out.println(SeatService.class.isAnnotationPresent(Service.class));
        System.out.println(Service.class.isAnnotationPresent(Component.class));
        System.out.println(hasMeta(SeatService.class, Component.class, new HashSet<>()));
    }
}

    둘째 줄이 요점이다. @Service가 붙은 SeatService에 대해 자바의 리플렉션은 @Component가 없다고 답한다. 셋째와 넷째 줄은 "SeatService에는 @Service가 있다", "@Service에는 @Component가 있다"는 두 사실을 각각 확인한 것이다. 이 둘을 이어 붙여 "그러므로 SeatService는 컴포넌트다"라고 결론을 내리는 것은 언어가 아니라 그 위에서 도는 코드의 몫이다. 직접 만든 hasMeta가 애노테이션의 애노테이션을 따라 올라가 다섯째 줄에서 true를 낸 것이 그런 해석의 가장 단순한 형태다.

    스프링도 같은 일을 한다. 기본 스캔에 쓰이는 필터는 AnnotationTypeFilter이고, 6.2.x 소스에서 이 필터의 판정은 "메타데이터에 그 애노테이션이 직접 있는가, 또는 메타 애노테이션으로 있는가"다. 메타 애노테이션을 고려할지를 정하는 값은 따로 끄지 않는 한 켜져 있다. 스프링 레퍼런스는 @Service가 @Component로 메타 애노테이션되어 있어서 @Component와 같은 방식으로 취급된다고 설명한다. 레퍼런스가 드는 또 다른 예는 @RestController다. 이것은 @Controller와 @ResponseBody를 합쳐 만든 합성 애노테이션(composed annotation)이고, @Controller에 @Component가 붙어 있으므로 역시 스캔 대상이 된다.

    이 구조는 확장 지점이기도 하다. 직접 만든 애노테이션에 @Component를 붙이면 스프링 설정을 하나도 건드리지 않고 새로운 스캔 표시를 만들 수 있다. 팀에서 "유스케이스", "어댑터" 같은 역할 이름을 애노테이션으로 만들어 쓰는 방식이 이 위에 서 있다.

    메타 애노테이션과 @Inherited는 다른 것이다. 자바 언어 명세 9.6.4.3절의 @Inherited는 클래스에 붙은 애노테이션이 그 하위 클래스로 이어지게 하는 표시다. 스프링의 @Component 선언에는 @Inherited가 없다. 그래서 @Service가 붙은 클래스를 상속한 하위 클래스는 자기에게 애노테이션이 없으면 스캔 대상이 아니다. 6.2.x의 AnnotationTypeFilter는 애노테이션 타입에 @Inherited가 있을 때만 상위 클래스까지 따져 본다.

    1차 판정: 필터와 조건

    6.2.x 소스에서 1차 판정의 본문은 짧다. 제외 필터를 차례로 돌려 하나라도 맞으면 false를 돌려준다. 그다음 포함 필터를 차례로 돌려 하나라도 맞으면 조건 검사의 결과를 돌려준다. 어느 포함 필터에도 맞지 않으면 false다. 순서가 고정되어 있으므로 제외가 포함보다 항상 먼저 판정되고, 양쪽에 다 걸리는 클래스는 탈락한다.

    기본 설정에서 포함 필터는 @Component를 찾는 AnnotationTypeFilter 하나다. 6.2.x에서는 클래스패스에 해당 애노테이션 클래스가 있으면 jakarta.annotation.ManagedBean과 jakarta.inject.Named(그리고 같은 이름의 javax.* 애노테이션)를 찾는 필터도 함께 등록된다. 제외 필터는 기본으로는 없지만, @ComponentScan을 처리하는 파서가 스캔을 선언한 클래스 자신을 빼는 필터를 하나 넣는다. SeatConfig가 스캔 결과에 없는 것은 그 때문이다. 이 클래스는 이미 직접 등록되어 있으므로 다시 찾을 필요가 없다.

    포함 필터를 통과한 뒤의 "조건 검사"는 @Conditional의 평가다. 클래스에 조건이 붙어 있고 그 조건이 지금 환경에서 성립하지 않으면, 그 클래스는 빈 정의로 등록되지 않는다. 프로필에 따라 빈을 켜고 끄는 @Profile이 이 길로 처리된다. 조건에 맞지 않는 컴포넌트는 "등록되었지만 쓰이지 않는" 것이 아니라 정의 목록에 처음부터 올라가지 않는다는 점을 기억해 두자.

    2차 판정: 독립적으로 만들 수 있는 구체 클래스

    1차를 통과한 메타데이터로 ScannedGenericBeanDefinition을 만들고 한 번 더 본다. 6.2.x의 조건은 "독립적인 클래스이고, 구체 클래스이거나 @Lookup 메서드를 가진 추상 클래스일 것"이다. 구체 클래스란 인터페이스도 추상 클래스도 아닌 것을 말한다. 독립적이라는 것은 바깥 객체 없이 단독으로 만들 수 있다는 뜻으로, 최상위 클래스와 정적 중첩 클래스가 해당한다.

    이 판정 때문에 인터페이스나 추상 클래스에 @Component를 붙여도 빈 정의가 생기지 않는다. 컨테이너가 객체를 만들 수 없는 타입이므로 정의를 등록해 봐야 생성 단계에서 실패할 뿐이기 때문이다. 바깥 클래스의 인스턴스가 있어야 만들 수 있는 내부 클래스(정적이 아닌 중첩 클래스)도 같은 이유로 걸러진다. 스캐너의 로그를 DEBUG 수준으로 올리면 통과한 자원은 "Identified candidate component class"로, 2차에서 떨어진 자원은 "Ignored because not a concrete top-level class"로 기록된다. 붙였는데도 빈이 안 생기는 클래스가 있다면 이 로그가 가장 빠른 단서다.

    일상에서 가져온 비유서류 전형과 자격 확인

    채용 담당자가 지원 서류 더미를 두 번 거른다고 생각하면 된다. 첫 번째는 서류에 찍힌 표시만 본다. 제외 명단에 있는 사람을 먼저 빼고, 지원 자격 표시가 있는 서류만 남긴다. 두 번째는 남은 서류를 보고 그 사람이 혼자서 바로 일을 시작할 수 있는지를 확인한다. 비유가 깨지는 지점도 있다. 채용에서는 결국 사람을 불러 면접을 보지만 스캐너는 이 단계가 끝날 때까지 클래스를 한 번도 불러오지 않는다. 판정의 근거는 처음부터 끝까지 서류, 곧 클래스 파일에서 읽은 메타데이터뿐이다.

    이름을 짓고 등록한다

    두 판정을 통과한 후보마다 스캐너는 정해진 순서로 일을 한다. 먼저 @Scope를 읽어 스코프를 정한다. 없으면 싱글톤이다. 다음으로 빈 이름 생성기에게 이름을 받는다. 그다음 @Lazy, @Primary, @DependsOn 같은 공통 애노테이션을 읽어 정의의 속성에 반영한다. 그리고 같은 이름의 정의가 이미 있는지 검사한 뒤 문제가 없으면 레지스트리에 등록한다.

    이름을 짓는 기본 구현은 AnnotationBeanNameGenerator다. 스테레오타입 애노테이션의 값으로 이름이 주어져 있으면, 예를 들어 @Service("booking")이면 그 값을 쓴다. 없으면 패키지를 뗀 클래스 이름을 프로퍼티 이름 규칙으로 바꾼다. 6.x에서 이 변환은 StringUtils.uncapitalizeAsProperty가 하고, 규칙은 "첫 글자를 소문자로 바꾸되, 처음 두 글자가 연달아 대문자이면 그대로 둔다"다. 이 메서드의 Javadoc이 참고로 거는 JDK의 Introspector.decapitalize가 같은 조건을 쓰므로, 그것을 JDK 21에서 실행해 결과를 확인했다.

    탐색 위치: 어디에서부터 뒤질지를 정하는 세 가지 방법

    스캔의 범위는 기준 패키지(base package)가 정한다. @ComponentScan에서 기준 패키지를 정하는 방법은 셋이다. 아래 세 줄은 하나를 고른다는 뜻으로 나란히 적은 것이다.

    @ComponentScan(basePackages = {"seat.store", "seat.web"})   // 패키지 이름을 문자열로 적는다
@ComponentScan(basePackageClasses = SeatStore.class)        // 이 클래스가 속한 패키지(seat.store)를 쓴다
@ComponentScan                                               // 이 애노테이션을 붙인 클래스의 패키지를 쓴다

    basePackages는 문자열 배열이고 value가 그 별칭이라 @ComponentScan("seat")처럼 줄여 쓸 수 있다. 문자열이므로 오타를 컴파일러가 잡아 주지 못하고, 패키지 이름을 바꾸는 리팩터링에서 함께 바뀌지 않을 수 있다. basePackageClasses는 그 약점을 메우는 방법이다. Javadoc은 이것을 타입 안전한 대안이라고 부르며, 지정한 각 클래스가 속한 패키지가 스캔된다고 적는다. 여기 적는 클래스는 위치를 가리키는 표지일 뿐이라서 그 클래스 하나만 스캔된다는 뜻이 아니다.

    둘 다 적지 않았을 때의 규칙은 Javadoc에 한 문장으로 있다. 특정 패키지를 정하지 않으면 이 애노테이션을 선언한 클래스의 패키지에서 시작해 재귀적으로 스캔한다. 6.2.x의 파서도 모은 기준 패키지가 비어 있으면 선언 클래스의 패키지 이름을 넣는다. "재귀적으로"는 하위 패키지를 모두 포함한다는 뜻이다. 상위 패키지와 옆 패키지는 포함되지 않는다.

    범위가 어긋났을 때 보이는 증상

    첫 예제에서 SeatConfig만 seat.config 패키지로 옮겼다고 해 보자. 기준 패키지가 seat.config로 바뀐다. seat.SeatService는 상위 패키지에, seat.store.MemorySeatStore는 옆 패키지에 있으므로 둘 다 범위 밖이다. 컨테이너는 오류 없이 뜬다. 스캔한 결과가 0개인 것은 오류가 아니기 때문이다. 문제는 ctx.getBean(SeatService.class)를 부르는 순간 NoSuchBeanDefinitionException으로 드러나고, 문구는 "No qualifying bean of type 'seat.SeatService' available"이다.

    이 증상을 읽는 요령은 예외가 말하는 것을 그대로 받아들이는 것이다. 그 타입의 빈 정의가 없다는 뜻이고, 원인은 대개 둘 중 하나다. 클래스에 표시를 빠뜨렸거나, 표시는 있는데 스캔 범위 밖에 있다. 뒤쪽은 코드만 봐서는 잘 보이지 않는다. 클래스에 @Service가 멀쩡히 붙어 있기 때문이다. 이럴 때는 설정 클래스의 패키지와 문제 클래스의 패키지를 나란히 적어 보면 바로 드러난다.

    반대로 범위가 너무 넓은 경우도 있다. 기준 패키지를 회사 도메인의 최상위나 그보다 위로 잡으면 같은 접두어를 쓰는 사내 라이브러리의 클래스까지 읽게 된다. 읽는 양이 늘어 시작이 느려지는 것은 덜 심각한 쪽이다. 더 곤란한 것은 라이브러리 안에 스테레오타입 애노테이션이 붙은 클래스가 있을 때 그것이 의도하지 않게 빈으로 등록되는 일이다. 그 빈이 내 빈과 이름이나 타입이 겹치면 다음 절들에서 다룰 충돌로 이어진다.

    설정 클래스를 최상위 패키지에 두는 관례

    이런 이유로 기준 패키지를 따로 적지 않고 설정 클래스의 위치로 범위를 정하는 방식이 널리 쓰인다. 설정 클래스를 프로젝트의 최상위 패키지에 두면 그 아래 전부가 범위에 들고, 프로젝트 밖은 들지 않는다. 패키지를 새로 만들어도 최상위 아래이기만 하면 설정을 고칠 일이 없다.

    스프링 부트가 이 관례를 기본으로 삼는다. 3.5.x 소스에서 @SpringBootApplication의 선언에는 @ComponentScan이 메타 애노테이션으로 붙어 있고, 기준 패키지는 지정되어 있지 않다. 따라서 @SpringBootApplication을 붙인 메인 클래스의 패키지가 스캔의 출발점이 된다. 스프링 부트 레퍼런스는 메인 애플리케이션 클래스를 다른 클래스들보다 위에 있는 루트 패키지에 두라고 권하고, 루트 패키지를 쓰면 컴포넌트 스캔이 자기 프로젝트에만 적용된다고 덧붙인다. 같은 문서에 따르면 이 위치는 JPA 엔티티를 찾는 기준으로도 쓰인다.

    범위를 바꾸고 싶을 때는 @SpringBootApplication의 scanBasePackages와 scanBasePackageClasses를 쓴다. 소스에서 이 둘은 @ComponentScan의 basePackages, basePackageClasses에 대한 별칭으로 선언되어 있다. 다만 Javadoc은 scanBasePackages가 @Entity 스캔과 스프링 데이터 리포지토리 스캔에는 영향을 주지 않는다고 밝힌다. 컴포넌트 스캔의 범위만 넓혀 놓고 엔티티나 리포지토리 인터페이스가 왜 안 잡히는지 헤매는 일이 여기서 나온다. 그 둘은 각자의 스캔 설정을 따로 갖는다.

    @ComponentScan은 반복해서 붙일 수 있는 애노테이션이고, 6.2.x의 Javadoc은 클래스에 직접 선언한 @ComponentScan이 메타 애노테이션으로 붙은 @ComponentScan보다 항상 우선하며 그것을 사실상 가린다고 적는다. @SpringBootApplication이 붙은 클래스에 @ComponentScan을 따로 또 붙이면, 부트가 넣어 둔 스캔 설정 대신 직접 붙인 것이 쓰인다는 뜻이다.

    기본 스캔 대상: 다섯 애노테이션과 각자에게 덧붙는 일

    @ComponentScan의 useDefaultFilters 속성은 기본값이 true이고, Javadoc은 이것이 @Component, @Repository, @Service, @Controller가 붙은 클래스의 자동 탐지를 켜는 값이라고 설명한다. 여기에 @Configuration을 더한 다섯이 흔히 말하는 기본 스캔 대상이다. 앞에서 본 대로 스캐너가 실제로 찾는 것은 @Component 하나이고, 나머지 넷은 선언에 @Component가 붙어 있어서 함께 걸린다.

    그렇다면 왜 이름이 다른 애노테이션을 여럿 두었는가. 스캔이 끝난 뒤에 각 애노테이션을 따로 알아보는 다른 부품들이 있기 때문이다. 스캐너는 "빈으로 등록할 것인가"만 정하고, 등록된 빈에 무엇을 더 해 줄지는 각 부품이 그 빈의 클래스에 붙은 애노테이션을 보고 정한다.

    애노테이션스캔되는 이유스캔 뒤에 덧붙는 일그 일을 하는 쪽
    @Component기본 포함 필터가 찾는 대상 자체없다해당 없음
    @Controller선언에 @Component가 있다요청을 처리하는 핸들러로 인식된다스프링 MVC의 RequestMappingHandlerMapping. 6.2.x에서는 빈의 타입에 @Controller가 있는지를 본다
    @Service선언에 @Component가 있다없다. 서비스 계층이라는 역할 표시다해당 없음
    @Repository선언에 @Component가 있다데이터 접근 예외를 스프링의 DataAccessException으로 바꿔 주는 대상이 된다PersistenceExceptionTranslationPostProcessor가 등록되어 있을 때
    @Configuration선언에 @Component가 있다설정 클래스로 해석되어 @Bean 메서드가 처리된다ConfigurationClassPostProcessor

    스프링 레퍼런스는 @Repository, @Service, @Controller를 각각 영속성 계층, 서비스 계층, 표현 계층을 위한 @Component의 특수화라고 설명한다. @Service는 지금 덧붙는 처리가 없지만 레퍼런스는 서비스 계층에 @Component와 @Service 가운데 무엇을 쓸지 고민된다면 @Service가 더 나은 선택이라고 말한다. 역할이 드러나 도구로 처리하거나 관점(aspect)을 걸기에 알맞고, 이후 릴리스에서 의미가 더해질 수 있다는 것이 그 이유다.

    이 표에서 읽어야 할 원리는 등록과 부가 기능이 분리되어 있다는 것이다. 애노테이션은 클래스에 붙어 있으므로 그 클래스가 스캔으로 등록되었든 @Bean 메서드로 등록되었든 부품들은 같은 것을 본다. 거꾸로, 포함 필터로 억지로 등록한 클래스에 @Controller가 없다면 스프링 MVC는 그것을 핸들러로 보지 않는다. "스캔 대상이다"와 "그 역할로 동작한다"는 서로 다른 부품이 내리는 서로 다른 판정이다.

    필터: 포함과 제외의 판정 순서

    기본 규칙만으로 부족할 때 쓰는 것이 필터다. includeFilters는 기본 필터에 더해서 스캔 대상으로 삼을 타입을 정하고, excludeFilters는 스캔 대상에서 뺄 타입을 정한다. Javadoc의 표현으로 포함 필터는 기본 필터에 추가로 적용된다. 기본 필터 없이 포함 필터만으로 스캔하고 싶으면 useDefaultFilters = false를 함께 적는다.

    예제를 조금 늘려 보자. 표시용 애노테이션 둘을 만든다. 둘 다 @Component를 붙이지 않았고, 보존 정책은 RUNTIME이다.

    package seat.scan;

import java.lang.annotation.*;

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
public @interface NightJob {
}

@Target(ElementType.TYPE)
@Retention(RetentionPolicy.RUNTIME)
public @interface Sandbox {
}

    그리고 클래스 셋을 더한다. SeatCleanupJob에는 @NightJob만 있다. FakePaymentService에는 @Service와 @Sandbox가 함께 있다. LegacySeatStore는 @Repository가 붙은 또 하나의 SeatStore 구현이다. 설정은 다음과 같다.

    @Configuration
@ComponentScan(
        includeFilters = @ComponentScan.Filter(NightJob.class),
        excludeFilters = {
                @ComponentScan.Filter(Sandbox.class),
                @ComponentScan.Filter(type = FilterType.ASSIGNABLE_TYPE, classes = LegacySeatStore.class)
        })
public class SeatConfig {
}

    @ComponentScan.Filter의 type은 기본값이 FilterType.ANNOTATION이라서, 타입을 적지 않고 클래스만 넘기면 그 클래스를 애노테이션으로 해석한다. 판정 결과를 클래스별로 적으면 이렇다.

    클래스붙은 것제외 필터포함 필터결과
    SeatService@Service안 걸린다기본 필터에 걸린다등록
    MemorySeatStore@Repository안 걸린다기본 필터에 걸린다등록
    SeatCleanupJob@NightJob안 걸린다NightJob 필터에 걸린다등록. 이름은 seatCleanupJob
    FakePaymentService@Service, @SandboxSandbox 필터에 걸린다보지 않는다제외
    LegacySeatStore@Repository대입 가능 타입 필터에 걸린다보지 않는다제외
    SeatStore없음안 걸린다안 걸린다제외

    세 가지를 확인하자. SeatCleanupJob은 @Component가 직접으로도 메타로도 없는데 빈이 된다. 포함 필터에 걸리는 것으로 충분하기 때문이다. FakePaymentService는 @Service가 있어 기본 필터에 걸릴 클래스지만 제외 필터가 먼저 판정되어 탈락한다. LegacySeatStore가 빠졌으므로 SeatStore 타입의 빈은 memorySeatStore 하나만 남고, SeatService의 생성자 주입은 후보가 하나라서 문제없이 풀린다.

    필터 타입 다섯 가지

    FilterType무엇을 적는가무엇과 맞춰 보는가
    ANNOTATION (기본값)classes에 애노테이션 타입그 애노테이션이 클래스에 직접 또는 메타 애노테이션으로 있는가
    ASSIGNABLE_TYPEclasses에 클래스나 인터페이스대상이 그 타입에 대입 가능한가. 곧 그 타입 자신이거나 그것을 상속·구현하는가
    ASPECTJpattern에 AspectJ 타입 패턴대상 타입이 그 패턴에 맞는가
    REGEXpattern에 정규식대상의 패키지를 포함한 전체 클래스 이름이 그 정규식에 맞는가
    CUSTOMclasses에 TypeFilter 구현 클래스구현이 직접 판정한다

    한 필터의 classes에 여러 클래스를 적으면 "그중 하나라도 맞으면"으로 해석된다. 필터가 받는 재료가 무엇인지는 CUSTOM 타입을 직접 구현해 보면 분명해진다.

    package seat.scan;

import org.springframework.core.type.classreading.MetadataReader;
import org.springframework.core.type.classreading.MetadataReaderFactory;
import org.springframework.core.type.filter.TypeFilter;

public class StubNameFilter implements TypeFilter {

    @Override
    public boolean match(MetadataReader metadataReader, MetadataReaderFactory metadataReaderFactory) {
        String className = metadataReader.getClassMetadata().getClassName();
        return className.endsWith("Stub");
    }
}

    match가 받는 것은 Class 객체가 아니라 메타데이터 리더다. 앞 절에서 본, 클래스 파일을 읽어 만든 그 메타데이터다. 필터는 로딩되지 않은 클래스에 대해 이름, 상위 타입 이름, 애노테이션을 물어 답을 낸다. 둘째 인자인 팩토리는 상위 클래스나 인터페이스 같은 다른 클래스의 메타데이터가 필요할 때 그 파일을 읽어 오는 데 쓴다. ASSIGNABLE_TYPE 같은 내장 필터도 같은 인터페이스의 구현이다. 이 필터를 @ComponentScan.Filter(type = FilterType.CUSTOM, classes = StubNameFilter.class)로 제외 필터에 걸면 이름이 Stub으로 끝나는 클래스가 스캔에서 빠진다.

    실제로 쓰이는 예는 가까이에 있다. 스프링 부트 3.5.x의 @SpringBootApplication에 붙은 @ComponentScan은 CUSTOM 타입의 제외 필터 둘, TypeExcludeFilter와 AutoConfigurationExcludeFilter를 달고 있다. 부트 애플리케이션의 컴포넌트 스캔은 처음부터 필터가 걸린 스캔인 셈이다.

    필터는 편리하지만 자주 꺼낼 도구는 아니다. 제외 필터를 쓰기 시작하면 "이 클래스에는 @Service가 붙어 있는데 빈이 아니다"라는 상황이 생기고, 그 이유는 클래스가 아니라 멀리 떨어진 설정 클래스에 적혀 있다. 컴포넌트 스캔이 없앴던 "두 군데를 맞춰야 하는 구조"가 되돌아오는 것이다. 빼고 싶은 클래스가 있다면 표시를 떼거나 패키지를 옮기는 쪽이 대개 더 단순하다.

    제외 필터가 포함 필터보다 먼저 판정되고, 포함 필터를 통과한 뒤에도 조건 검사와 구체 클래스 검사가 남아 있다는 것을 보여 준다. 위에서 아래로 내려가는 판정 순서도. 맨 위에 둥근 시작 상자 "클래스 파일 하나". 그 아래 마름모 네 개가 세로로 이어진다. 첫째 마름모 라벨 "제외 필터에 걸리는가", 오른쪽으로 나가는 화살표 라벨 "예"가 빨간 종료 상자 "탈락"으로 간다. 아래로 내려가는 화살표 라벨 "아니오". 둘째 마름모 "포함 필터에 걸리는가", 오른쪽 화살표 라벨 "아니오"가 같은 "탈락" 상자로 간다. 아래 화살표 라벨 "예". 셋째 마름모 "조건이 성립하는가", 오른쪽 "아니오"는 "탈락"으로. 넷째 마름모 "구체 클래스인가", 오른쪽 "아니오"는 "탈락"으로. 맨 아래 초록 종료 상자 "빈 정의 등록". 첫째와 둘째 마름모를 묶는 점선 테두리에 라벨 "1차 판정", 넷째 마름모 옆에 라벨 "2차 판정". 흰 배경, 평면 벡터 스타일, 빨강과 초록은 종료 상자에만 쓴다. 판정 순서는 고정되어 있다. 제외 필터가 먼저이므로 포함과 제외에 모두 걸리는 클래스는 등록되지 않는다.

    중복 등록과 충돌 1: 자동 등록끼리 이름이 겹칠 때

    빈 정의 레지스트리는 이름을 키로 하는 맵이다. 타입이 같은 빈은 여럿 있을 수 있지만 이름이 같은 정의는 하나만 있을 수 있다. 컴포넌트 스캔은 이름을 사람이 아니라 규칙이 짓기 때문에, 서로 모르는 두 클래스가 같은 이름을 받는 일이 생긴다.

    가장 흔한 경우는 패키지가 다른 두 클래스의 짧은 이름이 같을 때다. seat.SeatService가 있는데 관리자 기능을 만들면서 seat.admin.SeatService를 새로 만들고 둘 다 @Service를 붙였다고 하자. 자바에서는 패키지가 다르므로 아무 문제 없는 두 클래스다. 그러나 기본 빈 이름은 둘 다 seatService다. 스캐너가 둘째 클래스를 등록하려는 순간 예외가 난다.

    BeanDefinitionStoreException
  Failed to parse configuration class [seat.SeatConfig]
원인: ConflictingBeanDefinitionException
  Annotation-specified bean name 'seatService' for bean class [seat.admin.SeatService]
  conflicts with existing, non-compatible bean definition of same name and class [seat.SeatService]

    바깥쪽 예외는 설정 클래스의 해석이 실패했다는 사실만 말하고, 실제 원인은 안쪽 예외에 있다. 안쪽 문구는 세 가지를 알려 준다. 문제의 빈 이름, 지금 등록하려던 클래스, 그 이름으로 이미 등록되어 있던 클래스다. 두 클래스 이름의 자리는 어느 쪽이 먼저 발견되었는지에 따라 바뀔 수 있다. 스캔이 자원을 찾는 순서는 코드로 정한 것이 아니기 때문이다.

    6.2.x의 스캐너는 이름이 이미 쓰이고 있을 때 다음 순서로 판단한다.

    1. 기존 정의가 스캔으로 만들어진 것이 아니고, 오버라이딩이 허용되어 있거나 두 정의의 클래스가 같으면 새 후보를 조용히 버린다. 명시적으로 등록된 정의가 스캔 결과보다 우선한다는 뜻이다.
    2. 기존 정의와 새 후보가 같은 파일에서 나왔거나 서로 동등하면 새 후보를 버린다. 같은 클래스를 두 번 스캔한 경우다.
    3. 그 밖에는 ConflictingBeanDefinitionException을 던진다.

    둘째 규칙 덕분에 스캔 범위가 겹쳐도 문제가 없다. basePackages에 seat와 seat.store를 함께 적거나 두 설정 클래스의 스캔 범위가 겹치면 같은 클래스 파일이 두 번 발견되지만, 출처가 같은 파일이므로 둘째는 건너뛴다. 예외가 나는 것은 서로 다른 클래스가 같은 이름을 놓고 다툴 때뿐이다.

    자동 등록끼리의 충돌에서 스프링이 한쪽을 골라 주지 않고 멈추는 데에는 이유가 있다. 두 정의는 자격이 같고, 어느 쪽이 먼저 발견되는지는 파일 시스템이나 jar 안의 순서에 달려 있다. 여기서 "나중 것이 이긴다"거나 "먼저 것이 이긴다"로 조용히 넘어가면, 같은 코드가 환경에 따라 다른 객체를 쓰게 된다. 시작 단계에서 멈추는 편이 훨씬 싸다.

    해결 방법은 이름을 다르게 만드는 것이다. 한쪽에 @Service("adminSeatService")처럼 이름을 직접 적는 것이 가장 단순하다. 같은 일이 프로젝트 전체에서 반복된다면 이름 생성기를 바꿀 수 있다. 스프링 레퍼런스는 이런 충돌에 대해 패키지를 포함한 전체 클래스 이름을 기본 빈 이름으로 쓰는 FullyQualifiedAnnotationBeanNameGenerator를 @ComponentScan의 nameGenerator로 지정하는 방법을 안내한다. 다만 이름 생성기를 바꾸면 빈 이름으로 무언가를 찾는 모든 코드가 영향을 받으므로, 클래스 이름을 처음부터 겹치지 않게 짓는 쪽이 더 낫다.

    중복 등록과 충돌 2: 수동 등록과 자동 등록이 겹칠 때

    이번에는 스캔으로 등록된 빈과 @Bean 메서드로 등록한 빈의 이름이 같은 경우다. 스캔 대상인 MemorySeatStore는 그대로 두고, 설정 클래스에 같은 이름의 @Bean 메서드를 추가한다. 돌려주는 객체는 예약 시도를 출력하는 다른 구현 AuditSeatStore이고, 이 클래스에는 스테레오타입 애노테이션이 없다.

    package seat.store;

import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;

public class AuditSeatStore implements SeatStore {
    private final Set taken = ConcurrentHashMap.newKeySet();

    @Override
    public boolean reserve(String seat) {
        System.out.println("예약 시도: " + seat);
        return taken.add(seat);
    }
}
    @Configuration
@ComponentScan
public class SeatConfig {

    @Bean
    public SeatStore memorySeatStore() {
        return new AuditSeatStore();
    }
}

    이름 memorySeatStore를 두고 두 정의가 생긴다. 하나는 스캔이 MemorySeatStore 클래스에서 만든 것이고, 하나는 @Bean 메서드에서 만든 것이다. 앞에서 정리한 순서를 떠올리자. 같은 설정 클래스 안에서 스캔은 해석 도중에 즉시 실행되고 @Bean 메서드는 해석이 끝난 뒤에 등록된다. 따라서 스캔의 정의가 기존 정의이고 @Bean의 정의가 새 정의다.

    스프링 프레임워크만 쓸 때: 수동 등록이 덮어쓴다

    6.2.x에서 @Bean 메서드를 등록하는 코드는 같은 이름의 기존 정의가 스캔으로 만든 것이면 등록을 그대로 진행한다. 그러면 빈 팩토리의 등록 메서드가 기존 정의를 발견하고 오버라이딩이 허용되어 있는지를 확인한다. DefaultListableBeanFactory에서 이 허용 여부는 따로 설정하지 않으면 허용으로 취급된다. 결국 새 정의가 맵의 같은 키에 들어가 기존 정의를 대신한다. 첫 예제의 SeatMain을 그대로 실행하면 출력이 이렇게 바뀐다.

    memorySeatStore : ConfigurationClassBeanDefinition
seatConfig : AnnotatedGenericBeanDefinition
seatService : ScannedGenericBeanDefinition
예약 시도: A-12
true
예약 시도: A-12
false

    memorySeatStore의 정의 종류가 ScannedGenericBeanDefinition에서 ConfigurationClassBeanDefinition으로 바뀌었다. @Bean 메서드에서 온 정의라는 뜻이다. "예약 시도"가 찍힌 것으로 보아 SeatService가 받은 저장소는 AuditSeatStore다. MemorySeatStore는 @Repository가 붙어 있고 스캔에도 걸렸지만 객체가 만들어지지 않는다. 정의가 사라졌기 때문이다.

    이 동작에서 곤란한 점은 조용하다는 것이다. 6.2.x의 빈 팩토리는 다른 정의로 덮어쓸 때 "Overriding bean definition for bean 'memorySeatStore' with a different definition"으로 시작하는 로그를 남기는데, 오버라이딩 허용 여부를 명시적으로 설정하지 않은 기본 상태에서는 그 수준이 DEBUG다. 운영 환경의 로그 수준에서는 보이지 않는다. 누군가 일부러 덮어쓴 것이라면 괜찮지만, 이름이 우연히 겹친 것이라면 MemorySeatStore를 고쳐도 아무 변화가 없는 이유를 한참 찾게 된다.

    스프링 부트에서: 시작이 실패한다

    스프링 부트는 이 기본값을 뒤집었다. 3.5.x의 SpringApplication은 컨텍스트를 준비할 때 빈 팩토리의 오버라이딩 허용 값을 자기 설정값으로 지정하고, 그 설정의 기본값은 false다. 위 설정 클래스를 부트 애플리케이션에 넣으면 빈 팩토리가 BeanDefinitionOverrideException을 던지고, 부트의 실패 분석기가 다음 설명과 조치를 출력한다. 꺾쇠 자리에는 각 정의가 나온 자원의 설명이 들어간다.

    The bean 'memorySeatStore', defined in <새 정의의 출처>, could not be registered. A bean with that name has already been defined in <기존 정의의 출처> and overriding is disabled.

Consider renaming one of the beans or enabling overriding by setting spring.main.allow-bean-definition-overriding=true

    문구가 원인과 선택지를 모두 말해 준다. 같은 이름의 빈이 이미 정의되어 있고 덮어쓰기는 꺼져 있다. 조치는 둘 중 하나다. 이름을 바꾸거나, spring.main.allow-bean-definition-overriding=true로 덮어쓰기를 켠다. 뒤쪽을 고르면 프레임워크만 쓸 때와 같은 동작으로 돌아간다. 다만 이 경우에는 허용 여부가 명시적으로 설정된 상태이므로, 6.2.x의 빈 팩토리는 덮어쓸 때의 로그를 INFO 수준으로 남긴다.

    어느 쪽이 맞는 기본값인지는 실패의 비용으로 따져 볼 수 있다. 덮어쓰기를 허용하면 의도한 교체는 편하지만 의도하지 않은 교체가 조용히 지나간다. 금지하면 의도한 교체에 설정 한 줄이 더 들지만 의도하지 않은 겹침은 시작 단계에서 드러난다. 조용히 틀린 객체로 도는 애플리케이션과 뜨지 않는 애플리케이션 가운데 뒤쪽이 원인을 찾기 쉽다. 부트의 기본값은 그 판단을 반영한 것이다.

    클래스가 같으면 예외가 아니다

    경계 조건이 하나 있다. 6.2.x의 @Bean 등록 코드에는 스캔으로 만든 정의는 @Bean 메서드가 조용히 덮어쓸 수 있고, 6.1부터는 빈의 클래스가 같다면 일반 오버라이딩이 꺼져 있어도 그렇다는 주석이 달려 있다. 코드는 @Bean 메서드의 선언된 반환 타입 이름과 스캔된 정의의 클래스 이름을 비교해, 같으면 스캔된 정의를 레지스트리에서 먼저 지운 뒤 새 정의를 등록한다. 기존 정의가 없어진 상태이므로 덮어쓰기 검사에 걸리지 않는다.

    위 예제에서 메서드를 public MemorySeatStore memorySeatStore()로 선언하고 MemorySeatStore 객체를 돌려주게 바꾸면 이 경우에 해당한다. 스캔으로도 찾고 @Bean으로도 등록한, 같은 클래스의 같은 이름이다. 반대로 반환 타입을 인터페이스인 SeatStore로 선언하면 이름이 다르므로 해당하지 않는다. 위 예제가 부트에서 실패하는 것은 반환 타입이 SeatStore이고 스캔된 클래스가 MemorySeatStore여서다.

    순서가 반대인 경로도 결과는 같다. 정의를 코드로 먼저 등록해 둔 뒤에 스캔이 같은 이름의 후보를 만나면, 앞 절의 첫째 규칙에 따라 스캐너가 후보를 버린다. 명시적으로 등록한 정의가 남는다. 스캔이 먼저든 수동 등록이 먼저든, 프레임워크의 기본 동작에서는 사람이 직접 적은 정의가 규칙이 찾아낸 정의를 이긴다.

    스캔의 정의가 먼저 레지스트리에 들어가고 @Bean의 정의가 나중에 같은 이름으로 도착했을 때, 프레임워크 기본 설정과 스프링 부트 기본 설정에서 결과가 갈리는 것을 보여 준다. 왼쪽에서 오른쪽으로 흐르는 타임라인과 그 끝의 두 갈래 분기. 타임라인 위의 첫 지점 라벨 "1. 스캔", 그 아래 레지스트리를 뜻하는 표 모양 상자에 한 줄 "memorySeatStore → MemorySeatStore". 둘째 지점 라벨 "2. @Bean 등록", 같은 이름표를 든 새 카드 "memorySeatStore → AuditSeatStore"가 표 상자로 다가가는 화살표. 그 오른쪽에 마름모 "덮어쓰기 허용?". 마름모에서 위쪽으로 가는 갈래 라벨 "프레임워크 기본: 허용", 끝에 표 상자가 있고 안의 줄은 "memorySeatStore → AuditSeatStore", 옆에 흐린 글씨 "기존 정의 사라짐". 마름모에서 아래쪽으로 가는 갈래 라벨 "스프링 부트 기본: 금지", 끝에 빨간 경고 상자 "시작 실패". 흰 배경, 평면 벡터 스타일, 빨강은 경고 상자에만 쓴다. 같은 설정 클래스에서는 스캔이 먼저, @Bean이 나중이다. 나중에 온 정의를 받아들일지 여부가 프레임워크와 부트의 기본값에서 갈린다.

    흔한 오해 여섯 가지

    "컴포넌트 스캔은 패키지의 클래스를 전부 로딩해서 확인한다." 스캐너는 클래스 파일을 자원으로 읽어 메타데이터를 뽑는다. 후보 클래스는 로딩하지 않는다. 다만 후보에 붙은 애노테이션의 타입은 로딩한다. "아무것도 로딩하지 않는다"도, "전부 로딩한다"도 정확하지 않다.

    "스캔이 끝나면 객체가 만들어져 있다." 스캔의 산출물은 빈 정의다. 객체는 모든 빈 팩토리 후처리기가 끝난 뒤, 정의 목록을 따라 싱글톤을 만드는 단계에서 생긴다. 스캔 중에 생성자가 불리는 일은 없다.

    "@Service와 @Repository는 스캐너가 각각 따로 알아본다." 스캐너의 기본 필터가 찾는 것은 @Component다. 나머지는 선언에 @Component가 붙어 있어서 걸린다. 각 애노테이션 고유의 기능은 스캔 뒤에 다른 부품이 그 애노테이션을 보고 붙인다.

    "인터페이스에 @Component를 붙이면 구현 클래스들이 스캔된다." 인터페이스 자신은 구체 클래스가 아니라서 2차 판정에서 떨어진다. 구현 클래스는 자기 클래스 파일에 그 애노테이션이 없으므로 기본 필터에 걸리지 않는다. java.lang.annotation.Inherited의 Javadoc도 @Inherited는 상위 클래스의 애노테이션만 물려주고, 구현한 인터페이스에 붙은 애노테이션에는 효과가 없다고 적는다. 구현들을 한꺼번에 등록하고 싶다면 포함 필터의 ASSIGNABLE_TYPE에 그 인터페이스를 적는 방법이 있다.

    "제외 필터에 걸린 클래스는 빈이 될 수 없다." 필터는 그 @ComponentScan 한 번의 스캔에만 적용된다. 같은 클래스를 @Bean 메서드로 등록하거나 다른 설정 클래스의 스캔이 찾아내면 빈이 된다. "스캔에서 뺐다"와 "컨테이너에 없다"는 다른 말이다.

    "이름이 겹치면 항상 예외가 난다." 자동 등록끼리는 예외가 난다. 같은 클래스를 두 번 스캔한 것은 예외가 아니다. 수동 등록과 자동 등록이 겹치면 프레임워크의 기본 동작은 수동 쪽이 덮어쓰는 것이고, 스프링 부트의 기본 동작은 시작 실패다. 어느 환경에서 도는 코드인지에 따라 답이 다르다.

    이 지식이 다시 쓰이는 곳

    바로 다음 회차의 주제가 이 위에 선다. 스캔이 타입이 같은 빈을 둘 이상 등록해 놓으면 생성자의 매개변수 하나에 후보가 여럿이 된다. 그때 컨테이너가 무엇을 기준으로 하나를 고르고, 고르지 못하면 어떤 예외를 내는지가 6회의 내용이다. 이 회차에서 본 빈 이름 규칙이 거기서 후보를 좁히는 기준 가운데 하나로 다시 나온다.

    7회의 생명주기 콜백과 8회의 스코프도 스캔과 맞닿아 있다. 스캐너가 후보마다 가장 먼저 한 일이 @Scope를 읽어 스코프를 정하는 것이었고, @ComponentScan에는 스캔된 빈에 프록시를 만들지를 정하는 scopedProxy 속성이 있다. 이 속성이 무엇을 위한 것인지는 스코프가 다른 빈을 주입할 때의 문제를 다루는 8회에서 드러난다.

    이 권 밖에서는 스프링 부트의 구조를 읽을 때 쓰인다. @SpringBootApplication은 설정 클래스 표시, 자동 구성 활성화, 컴포넌트 스캔 셋을 묶은 합성 애노테이션이다. 메인 클래스의 패키지가 왜 중요한지, 멀티 모듈 프로젝트에서 다른 모듈의 빈이 왜 안 잡히는지, 같은 이름의 빈을 등록했을 때 왜 부트에서만 시작이 실패하는지는 모두 이 회차의 규칙으로 설명된다.

    웹과 데이터 접근 쪽에서도 같은 패턴이 반복된다. 스프링 MVC는 등록된 빈 가운데 @Controller가 붙은 것을 골라 요청 매핑을 읽는다. JPA 엔티티 탐색과 스프링 데이터의 리포지토리 인터페이스 탐색은 컴포넌트 스캔과 별개의 스캔이지만, 기준 패키지에서 출발해 클래스패스를 훑어 표시가 붙은 타입을 찾는다는 발상은 같다. "기준 위치, 표시, 필터, 이름"이라는 네 요소로 스캔을 읽는 습관은 이후의 권들에서 그대로 통한다.
    컴포넌트 스캔
    기준 패키지 아래의 클래스 파일을 읽어 표시가 붙은 클래스를 빈 정의로 등록하는 기능이다. 산출물은 객체가 아니라 빈 정의이고, 객체는 그 뒤의 싱글톤 생성 단계에서 만들어진다.
    스캔이 일어나는 시점
    refresh()의 빈 팩토리 후처리기 단계에서 ConfigurationClassPostProcessor가 설정 클래스를 해석하다가 @ComponentScan을 만나면 즉시 실행한다. 같은 설정 클래스의 @Bean 메서드는 그보다 나중에 등록된다.
    패키지에서 파일로
    기준 패키지는 classpath*:패키지경로/**/*.class 패턴으로 바뀌고, 클래스 로더가 알려 준 위치가 디렉터리이면 파일 시스템을, jar이면 엔트리 목록을 훑는다. 디렉터리 엔트리가 없는 jar나 기본 패키지에서는 이 과정이 기대와 다르게 동작한다.
    클래스 파일의 애노테이션
    보존 정책이 RUNTIME인 애노테이션은 클래스 파일 끝의 RuntimeVisibleAnnotations 속성에 타입 이름으로 기록된다. 스캐너는 ASM 기반의 메타데이터 리더로 이 정보를 읽으며 후보 클래스를 로딩하지 않는다.
    메타 애노테이션
    자바 언어에는 애노테이션의 상속이 없다. @Service가 붙은 클래스가 컴포넌트로 취급되는 것은 스프링이 애노테이션에 붙은 애노테이션을 따라가 @Component를 찾기 때문이다.
    두 번의 판정
    1차는 제외 필터, 포함 필터, 조건의 순서로 메타데이터를 본다. 2차는 독립적으로 만들 수 있는 구체 클래스인지를 본다. 둘을 모두 통과해야 빈 정의가 된다.
    기본 빈 이름
    패키지를 뗀 클래스 이름의 첫 글자를 소문자로 바꾼 것이다. 처음 두 글자가 모두 대문자이면 바꾸지 않는다. 패키지가 이름에 들어가지 않으므로 짧은 이름이 같은 두 클래스는 충돌한다.
    탐색 위치
    basePackages, basePackageClasses로 정하고, 정하지 않으면 @ComponentScan을 선언한 클래스의 패키지에서 하위로 내려간다. 설정 클래스를 프로젝트 최상위 패키지에 두는 관례가 여기서 나온다.
    이름 충돌의 판정
    자동 등록끼리는 ConflictingBeanDefinitionException이 난다. 수동 등록과 자동 등록이 겹치면 프레임워크 기본값에서는 수동 쪽이 덮어쓰고, 스프링 부트 기본값에서는 시작이 실패한다.

    실무에서 가장 먼저 내리는 판단은 무엇을 스캔에 맡기고 무엇을 직접 등록할 것인가다. 컨트롤러, 서비스, 리포지토리처럼 수가 많고 만드는 방식이 한결같은 업무 로직은 스캔에 맡기는 편이 낫다. 클래스를 만들 때마다 설정을 고칠 일이 없고, 빠뜨릴 자리가 없다. 반대로 데이터 소스, 외부 시스템 클라이언트, 공통 기술 지원 객체처럼 수가 적고 설정값과 생성 절차가 중요한 것은 @Bean으로 설정 클래스에 드러내는 쪽이 유지보수에 유리하다. 이런 빈은 문제가 생겼을 때 "어디서 어떤 값으로 만들어졌는가"를 한 파일에서 볼 수 있어야 하기 때문이다. 스캔은 그 정보를 클래스 여러 개에 흩어 놓는다.

    장애로 이어지는 유형은 대체로 범위와 이름이다. 멀티 모듈 프로젝트에서 공통 모듈의 패키지가 메인 클래스의 패키지 아래에 있지 않으면 그 모듈의 빈은 통째로 누락된다. 이때 흔히 스캔 범위를 넓히는 것으로 대응하는데, 범위를 넓힐수록 의도하지 않은 클래스가 빈으로 딸려 올 가능성도 함께 커진다. 공통 모듈이 자기 설정 클래스를 하나 제공하고 쓰는 쪽에서 그것을 가져오는 방식이 범위를 좁게 유지하는 대안이다. 그리고 컴포넌트 스캔의 범위를 바꿔도 엔티티 스캔과 리포지토리 스캔은 따라 바뀌지 않는다는 점을 함께 점검해야 한다.

    스프링 부트에서 이름 충돌로 시작이 실패했을 때 spring.main.allow-bean-definition-overriding=true는 가장 빠른 해결처럼 보이지만, 그 설정은 지금의 충돌 하나만이 아니라 앞으로 생길 모든 우연한 겹침을 조용히 통과시킨다. 문구가 알려 준 두 정의의 출처를 보고 어느 쪽이 의도한 것인지 판단해 다른 쪽의 등록을 없애거나 이름을 바꾸는 것이 원칙이다. 덮어쓰기를 켜는 것은 교체가 설계의 일부이고 그 사실이 팀에 공유되어 있을 때로 한정하는 편이 안전하다.

    스캔 범위와 시작 시간의 관계도 판단 거리다. 스캔은 기준 패키지 아래의 클래스 파일을 모두 열어 읽으므로 범위가 넓을수록 시작이 느려진다. 다만 느린 시작의 원인이 정말 스캔인지는 재 봐야 안다. 스캔은 시작 과정의 한 구간일 뿐이고 그 뒤에 수백 개의 객체를 만드는 단계가 이어진다. 추측으로 범위를 손대기 전에 어느 구간에서 시간이 드는지를 먼저 측정하고, 스캔이 원인으로 확인되었을 때 기준 패키지를 좁히는 것이 순서다.

    컴포넌트 스캔(component scan)
    기준 패키지 아래의 클래스 파일을 읽어, 표시가 붙은 클래스를 빈 정의로 자동 등록하는 스프링의 기능.
    스테레오타입 애노테이션(stereotype annotation)
    클래스의 역할을 나타내는 표시용 애노테이션. @Component와 그것을 메타 애노테이션으로 가진 @Controller, @Service, @Repository 등을 가리킨다.
    메타 애노테이션(meta-annotation)
    다른 애노테이션의 선언에 붙일 수 있는 애노테이션. 스프링은 이것을 따라가 @Service가 붙은 클래스를 @Component가 붙은 것처럼 다룬다.
    기준 패키지(base package)
    스캔이 출발하는 패키지. 그 패키지와 모든 하위 패키지가 탐색 범위가 된다.
    RuntimeVisibleAnnotations 속성
    클래스 파일에서 런타임 보존 애노테이션을 기록하는 속성. 클래스, 필드, 메서드 등에 붙을 수 있고 애노테이션의 타입과 속성값이 들어 있다.
    메타데이터 리더(MetadataReader)
    클래스 파일을 읽어 클래스 이름, 상위 타입, 애노테이션 같은 정보를 제공하는 스프링의 인터페이스. 기본 구현은 ASM의 ClassReader를 쓴다.
    타입 필터(TypeFilter)
    메타데이터 리더를 받아 그 타입이 조건에 맞는지를 판정하는 인터페이스. 포함 필터와 제외 필터가 모두 이 인터페이스의 구현이다.
    빈 이름 생성기(BeanNameGenerator)
    빈 정의에 이름을 붙이는 전략. 스캔의 기본 구현인 AnnotationBeanNameGenerator는 애노테이션에 적힌 이름을 쓰고, 없으면 짧은 클래스 이름에서 만든다.
    빈 팩토리 후처리기(BeanFactoryPostProcessor)
    빈 객체가 만들어지기 전에 빈 정의 목록을 고칠 기회를 받는 객체. ConfigurationClassPostProcessor가 그 하나이고 컴포넌트 스캔을 실행한다.
    빈 정의 오버라이딩(bean definition overriding)
    이미 등록된 이름으로 다른 빈 정의를 등록해 기존 정의를 대신하는 것. 스프링 프레임워크는 기본으로 허용하고 스프링 부트는 기본으로 금지한다.
