    객체를 몇 개 만들 것인가

    02회에서는 어떤 구현 객체를 만들어 누구에게 넘길지 결정하는 일을 설정 클래스 한 곳에 모았고, 03회에서는 그 설정을 읽어 객체를 만들고 이름으로 찾아 주는 스프링 컨테이너를 보았다. 두 회차가 다룬 질문은 "누가 객체를 만들고 연결하는가"였다. 이 회차의 질문은 그 다음이다. 그렇게 만든 객체는 몇 개인가.

    사소해 보이지만 답에 따라 프로그램의 성질이 달라진다. 요청마다 새 객체를 만들면 객체끼리 서로 영향을 주지 않는 대신, 함께 봐야 할 데이터가 공유되지 않고 만들고 버리는 비용이 요청 수에 비례해 늘어난다. 하나만 만들어 함께 쓰면 그 비용은 사라지지만 수백 개의 요청 스레드가 같은 객체의 같은 필드에 동시에 닿는다. 스프링은 기본값으로 후자를 택했고, 그 선택이 서비스 클래스를 작성하는 방식에 조건을 건다.

    이 회차는 다섯 단계로 간다. 먼저 요청마다 새로 만드는 방식이 왜 곤란한지 실행해서 확인한다. 다음으로 자바만으로 "하나"를 보장하는 싱글톤 패턴과, 그 패턴이 JVM의 클래스 초기화 규칙에 기대는 방식을 본다. 패턴의 비용을 따진 뒤에는 같은 보장을 클래스 밖으로 옮긴 스프링의 싱글톤 레지스트리를 소스 수준에서 따라간다. 이어서 객체가 하나일 때 필드에 무엇을 두면 안 되는지를 힙과 스택으로 설명하고, 마지막으로 @Configuration 클래스에서 자바 문법대로라면 일어날 수 없는 일이 왜 일어나는지를 생성된 바이트코드까지 열어 확인한다.

    이 회차의 실행 결과와 바이트코드는 원고를 쓰면서 JDK 21.0.13(Temurin)에서 직접 돌려 얻은 것이다. 스프링 실험에는 스프링 프레임워크 7.0.10을 썼고, 본문이 근거로 삼는 규칙(싱글톤 스코프의 정의, 즉시 초기화, 싱글톤 캐시의 자료구조, @Configuration의 CGLIB 처리와 제약, proxyBeanMethods)은 이 강좌의 기준 버전인 6.2의 레퍼런스 문서·Javadoc·소스에서 같은 내용을 따로 확인했다. 본문에 나오는 스프링 내부 클래스와 필드 이름은 공개 API가 아니므로 버전에 따라 달라질 수 있다.

    웹 애플리케이션과 싱글톤 — 요청마다 새로 만들면 생기는 일

    웹 애플리케이션은 혼자 쓰는 프로그램과 한 가지가 다르다. 사용자가 여럿이고, 그들이 같은 시각에 요청을 보낸다. 스프링 입문 03회에서 본 것처럼 서블릿 컨테이너는 스레드 풀을 두고 들어오는 요청마다 스레드 하나를 배정하므로, 같은 순간에 여러 스레드가 같은 서비스 코드를 실행한다. 그렇다면 각 요청이 쓸 서비스 객체를 어떻게 마련할지 정해야 한다.

    가장 단순한 답은 "필요할 때마다 만든다"이다. 스프링 없이 자바만으로 쓴 설정 클래스가 정확히 그렇게 동작한다. 도서관의 대출과 검색을 예로 작은 객체 그래프를 만들어 보자. 리포지토리 하나를 서비스 둘이 함께 쓰는 구조다.

    public interface BookRepository {
    void save(String isbn, String title);
    String findTitle(String isbn);
}

public class MemoryBookRepository implements BookRepository {
    private final Map store = new ConcurrentHashMap<>();

    public MemoryBookRepository() {
        System.out.println("  new MemoryBookRepository()");
    }

    @Override public void save(String isbn, String title) { store.put(isbn, title); }
    @Override public String findTitle(String isbn) { return store.get(isbn); }
}

public class LoanService {
    private final BookRepository bookRepository;

    public LoanService(BookRepository bookRepository) {
        this.bookRepository = bookRepository;
    }

    public BookRepository getBookRepository() { return bookRepository; }   // 실험용
}

public class SearchService {
    private final BookRepository bookRepository;

    public SearchService(BookRepository bookRepository) {
        this.bookRepository = bookRepository;
    }

    public BookRepository getBookRepository() { return bookRepository; }   // 실험용
}

public class LibraryConfig {
    public BookRepository bookRepository() {
        System.out.println("call LibraryConfig.bookRepository()");
        return new MemoryBookRepository();
    }

    public LoanService loanService() {
        System.out.println("call LibraryConfig.loanService()");
        return new LoanService(bookRepository());
    }

    public SearchService searchService() {
        System.out.println("call LibraryConfig.searchService()");
        return new SearchService(bookRepository());
    }
}

    이 설정 클래스에 세 번의 요청이 들어왔다고 하고, 요청마다 필요한 서비스를 꺼내 본다.

    public class PlainMain {
    public static void main(String[] args) {
        LibraryConfig config = new LibraryConfig();

        LoanService loan = config.loanService();          // 요청 1: 대출
        SearchService search = config.searchService();    // 요청 2: 검색
        System.out.println("same repository? "
                + (loan.getBookRepository() == search.getBookRepository()));

        LoanService loan2 = config.loanService();         // 요청 3: 대출
        System.out.println("same service? " + (loan == loan2));
    }
}

    결과는 자바 문법 그대로다. 메서드 본문에 new가 있으므로 호출할 때마다 힙에 새 객체가 생긴다. 요청 세 번에 서비스 객체 셋과 리포지토리 객체 셋, 모두 여섯 개가 만들어졌다. 두 == 비교는 참조가 같은 객체를 가리키는지 묻는 것이므로 둘 다 false다.

    요청 1 ──▶ LoanService@1   ──▶ MemoryBookRepository@1 { store: {} }
요청 2 ──▶ SearchService@1 ──▶ MemoryBookRepository@2 { store: {} }
요청 3 ──▶ LoanService@2   ──▶ MemoryBookRepository@3 { store: {} }

요청이 끝나면 각 줄의 객체는 아무도 가리키지 않게 되어 가비지 컬렉션 대상이 된다.

    첫째 문제는 정확성이다

    비용보다 먼저 봐야 할 것이 있다. 이 구조에서는 프로그램이 틀리게 동작한다. 요청 1이 MemoryBookRepository@1의 맵에 책을 저장해도 요청 2의 검색은 MemoryBookRepository@2의 빈 맵을 본다. 저장소가 메모리가 아니라 데이터베이스라면 데이터는 DB에 있으니 괜찮아 보이지만, 그때는 커넥션 풀이 같은 자리에 선다. 커넥션 풀은 만들어 둔 연결을 여러 요청이 돌려 쓰게 하려는 물건이라, 요청마다 풀을 새로 만들면 풀의 의미가 없어진다. 캐시, 설정 값을 읽어 둔 객체, 외부 API 클라이언트도 같다. 여러 요청이 같은 것을 봐야 하는 객체가 애플리케이션에는 반드시 있다.

    둘째 문제는 만들고 버리는 비용이다

    공유할 데이터가 없는 서비스 객체라도 요청마다 만들면 그만큼 힙에 쓰레기가 쌓인다. 얼마나 쌓이는지 직접 재 보았다. 서비스 하나와 리포지토리 하나로 된 작은 그래프를 요청마다 새로 만드는 경우와 한 번 만든 것을 계속 쓰는 경우를, 요청 5천만 건으로 비교한다.

    public class AllocMain {
    static class Repo {
        private final Map store = new HashMap<>();
        Repo() { store.put("isbn-1", "title"); }
        String find(String isbn) { return store.get(isbn); }
    }
    static class Service {
        private final Repo repo;
        Service(Repo repo) { this.repo = repo; }
        int handle(String isbn) { return repo.find(isbn).length(); }
    }
    static Service newGraph() { return new Service(new Repo()); }

    public static void main(String[] args) {
        boolean perRequest = args[0].equals("per-request");
        Service shared = newGraph();
        long sum = 0;
        for (int i = 0; i < 50_000_000; i++) {
            Service s = perRequest ? newGraph() : shared;   // 요청 하나에 해당
            sum += s.handle("isbn-1");
        }
        long count = 0;
        for (GarbageCollectorMXBean gc : ManagementFactory.getGarbageCollectorMXBeans()) {
            count += gc.getCollectionCount();
        }
        System.out.println(args[0] + ": sum=" + sum + ", GC 횟수=" + count);
    }
}
    per-request: sum=250000000, GC 횟수=51
shared: sum=250000000, GC 횟수=0

    같은 일을 했는데 한쪽은 가비지 컬렉션이 51번 돌았고 다른 쪽은 한 번도 돌지 않았다. 횟수는 힙 크기와 수집기 종류, JIT 컴파일러의 최적화에 따라 달라지므로 51이라는 숫자 자체에는 의미가 없다. 의미가 있는 것은 방향이다. -Xlog:gc로 로그를 켜면 Pause Young (Normal) (G1 Evacuation Pause) 153M->1M(256M) 같은 줄이 반복되는데, 153MB를 채운 객체 가운데 1MB만 살아남았다는 뜻이다. 요청마다 만든 객체는 요청이 끝나는 즉시 전부 쓰레기가 된다.

    이 결과를 과장해서 읽으면 안 된다. HotSpot은 기본 설정에서 스레드별 할당 버퍼(TLAB, -XX:+UseTLAB)를 써서 객체 할당 자체를 싸게 처리하고, 금방 죽는 객체를 치우는 일은 세대별 수집기가 가장 잘하는 일이다. 객체 두 개짜리 그래프를 요청마다 만드는 정도로 서비스가 멈추지는 않는다. 다만 실제 애플리케이션의 객체 그래프는 두 개가 아니라 수백 개의 서비스·리포지토리·설정 객체로 이루어지고, 그중에는 생성자에서 파일을 읽거나 네트워크 연결을 맺는 것도 있다. 요청 수에 비례해 늘어나는 이 비용을 낼 이유가 없다.

    이 장의 핵심

    요청마다 객체를 새로 만드는 방식은 공유해야 할 데이터를 공유하지 못해 틀리게 동작하고, 공유할 데이터가 없는 객체에 대해서도 요청 수에 비례하는 생성·수거 비용을 낸다. 그래서 서비스 객체는 하나만 만들어 모든 요청이 함께 쓰게 한다. 남는 질문은 둘이다. "하나"를 누가 어떻게 보장할 것인가, 그리고 하나뿐인 객체를 여러 스레드가 함께 써도 안전하려면 무엇을 지켜야 하는가.

    왼쪽은 요청 셋이 각자 서비스와 리포지토리를 따로 갖는 모습, 오른쪽은 요청 셋이 서비스 하나와 리포지토리 하나를 함께 가리키는 모습을 나란히 보여 준다. 깔끔한 평면 벡터 스타일의 좌우 비교 다이어그램, 흰 배경. 왼쪽 패널 제목 "요청마다 새로 생성". 왼쪽 패널에는 위에서 아래로 세 줄이 있고, 각 줄은 왼쪽의 작은 사람 아이콘(라벨 "요청 1", "요청 2", "요청 3")에서 오른쪽으로 화살표가 나가 둥근 사각형 "서비스"에 닿고, 다시 화살표가 둥근 원통 "저장소"에 닿는다. 세 줄의 서비스와 저장소는 서로 다른 색조로 그려 각각 다른 객체임을 보인다. 왼쪽 패널 아래에 회색 휴지통 아이콘과 라벨 "요청이 끝나면 전부 쓰레기". 오른쪽 패널 제목 "하나를 공유". 오른쪽 패널에는 같은 세 사람 아이콘("요청 1", "요청 2", "요청 3")에서 나온 화살표 세 개가 가운데의 둥근 사각형 "서비스" 하나로 모이고, 그 서비스에서 화살표 하나가 원통 "저장소" 하나로 간다. 오른쪽 패널 아래에 라벨 "객체 수는 요청 수와 무관". 두 패널 사이에 가는 세로 구분선. 글자는 한국어, 산세리프, 선명하게. 요청마다 객체 그래프를 만들면 저장소가 요청별로 갈라지고 요청이 끝날 때마다 전부 버려진다. 공유하면 객체 수가 요청 수와 무관해진다.

    싱글톤 패턴 — 클래스가 스스로 하나임을 보장한다

    객체를 하나만 두려면 누군가 "두 번째 new"를 막아야 한다. 싱글톤 패턴(singleton pattern)은 그 책임을 클래스 자신에게 준다. 클래스가 자기 인스턴스를 직접 하나 만들어 쥐고, 바깥에서는 생성자를 부를 수 없게 한 뒤, 쥐고 있는 인스턴스를 돌려주는 정적 메서드만 열어 둔다.

    public class Registry {
    private static final Registry INSTANCE = new Registry();   // (1) 하나를 만들어 정적 필드에 둔다

    private Registry() {                                        // (2) 밖에서는 new를 쓸 수 없다
        System.out.println("Registry 생성");
    }

    public static Registry getInstance() {                      // (3) 유일한 접근 통로
        return INSTANCE;
    }
}

public class RegistryMain {
    public static void main(String[] args) {
        System.out.println("main 시작");
        Registry a = Registry.getInstance();
        Registry b = Registry.getInstance();
        System.out.println("a == b ? " + (a == b));
    }
}
    main 시작
Registry 생성
a == b ? true

    장치는 세 개다. private 생성자는 다른 클래스의 new Registry()를 컴파일 오류로 만든다. static final 필드는 인스턴스를 클래스에 딸린 저장 공간 한 칸에 묶어 둔다. 정적 메서드 getInstance()는 그 칸의 참조를 복사해 돌려줄 뿐 새로 만들지 않는다. 그래서 몇 번을 불러도 같은 객체가 나온다.

    JVM이 한 번만 만든다는 것을 어떻게 보장하는가

    코드에는 synchronized도 락도 없다. 그런데도 여러 스레드가 동시에 getInstance()를 처음 부르는 상황에서 인스턴스가 둘 만들어지지 않는다. 근거는 언어 명세의 클래스 초기화 규칙에 있다. 먼저 컴파일된 모습을 보자.

    필드 선언에 붙어 있던 new Registry()는 컴파일러가 만든 클래스 초기화 메서드(static {}, 클래스 파일에서의 이름은 ) 안으로 옮겨졌다. 객체를 만들고(new, invokespecial) 정적 필드에 넣는(putstatic) 일은 이 메서드가 실행될 때 일어난다. 그러면 이 메서드는 언제, 몇 번 실행되는가.

    JLS §12.4.1은 클래스가 초기화되는 시점을 정해 둔다. 그 클래스의 인스턴스가 만들어질 때, 그 클래스가 선언한 정적 메서드가 호출될 때, 정적 필드에 값이 대입될 때, 상수 변수가 아닌 정적 필드가 사용될 때다. 실행 결과에서 "main 시작"이 "Registry 생성"보다 먼저 찍힌 이유가 여기에 있다. JVM이 시작할 때가 아니라 main이 Registry.getInstance()를 처음 부르는 순간에 Registry가 초기화되었다.

    같은 절의 §12.4.2는 초기화 절차를 정한다. 클래스마다 고유한 초기화 락이 있고, 초기화를 시작하려는 스레드는 먼저 이 락을 얻는다. 다른 스레드가 이미 초기화를 진행하고 있으면 락을 놓고 그 초기화가 끝났다는 통지를 받을 때까지 기다린다. 따라서 스레드 열 개가 동시에 getInstance()를 처음 불러도 static {}을 실행하는 스레드는 하나뿐이고, 나머지 아홉은 그 실행이 끝난 뒤에야 getstatic으로 넘어간다. 이 패턴에서 "한 번만"을 보장하는 것은 프로그래머가 쓴 코드가 아니라 JVM의 클래스 초기화 절차다.

    지연 초기화를 직접 구현하면 그 보장이 사라진다

    인스턴스를 처음 요청받을 때 만들겠다고 다음처럼 쓰는 경우가 많다. 클래스 초기화에 기대지 않고 null 검사로 직접 판단하는 방식이다.

    public class LazyRegistry {
    static final AtomicInteger CREATED = new AtomicInteger();   // 생성 횟수를 세는 실험용 카운터
    private static LazyRegistry instance;

    private LazyRegistry() {
        CREATED.incrementAndGet();
    }

    public static LazyRegistry getInstance() {
        if (instance == null) {              // (1) 검사
            instance = new LazyRegistry();   // (2) 생성과 대입
        }
        return instance;
    }
}

    (1)과 (2) 사이에는 아무 보호가 없다. 스레드 A가 (1)에서 null을 보고 (2)로 들어가 객체를 만드는 동안, 스레드 B도 (1)에서 아직 null인 필드를 본다. 둘 다 (2)를 실행하므로 객체가 둘 만들어지고, 나중에 대입한 쪽이 필드를 덮어쓴다. A는 자기가 만든 객체를, B는 자기가 만든 객체를 돌려받아 서로 다른 "싱글톤"을 쓰게 된다. 스레드 넷이 동시에 getInstance()를 부르는 실험을 10만 회 반복해 생성 횟수가 2 이상인 회차를 세었더니 세 번의 실행에서 각각 3,546회, 3,428회, 2,952회가 나왔다. 이 수치는 실행마다, 기계마다 다르다. 0이 아니라는 점만 확인하면 된다.

    고치는 방법은 여럿이다. getInstance()에 synchronized를 붙여 한 번에 한 스레드만 들어오게 하면 안전하지만, 인스턴스가 만들어진 뒤의 모든 호출도 락을 거친다. 검사를 락 밖에서 한 번, 락 안에서 한 번 하는 이중 검사 락(double-checked locking)은 필드를 volatile로 선언해야만 올바르다. 이 도구들의 원리는 자바 고급 1편에서 다룬다. 지금 쓸 수 있는 가장 간단한 방법은 다시 클래스 초기화에 기대는 것이다. 인스턴스를 중첩 클래스의 정적 필드에 두면, 그 중첩 클래스가 처음 쓰일 때 JVM이 한 번만 초기화해 준다.

    public class HolderRegistry {
    private HolderRegistry() { }

    private static class Holder {
        static final HolderRegistry INSTANCE = new HolderRegistry();
    }

    public static HolderRegistry getInstance() {
        return Holder.INSTANCE;      // Holder 클래스는 이 줄이 처음 실행될 때 초기화된다
    }
}

    싱글톤 패턴이 치르는 값

    싱글톤 패턴은 "하나"를 확실히 보장한다. 대신 그 보장을 클래스의 구조에 새겨 넣기 때문에, 02회에서 애써 지킨 설계 원칙 몇 가지를 내준다. 하나씩 코드로 본다.

    쓰는 쪽이 구체 클래스에 묶인다

    리포지토리를 싱글톤 패턴으로 만들었다면 서비스는 그것을 이렇게 얻는다.

    public class LoanService {
    private final BookRepository bookRepository = MemoryBookRepository.getInstance();
    // ...
}

    필드 타입은 인터페이스지만 오른쪽에 구현 클래스의 이름이 적혀 있다. 정적 메서드 호출은 바이트코드에서 invokestatic이 되고, 호출 대상인 MemoryBookRepository가 LoanService의 상수 풀에 이름으로 기록된다. 인스턴스 메서드처럼 실행 시점의 객체 타입에 따라 대상이 달라지는 일이 없다. 저장소를 다른 구현으로 바꾸려면 LoanService의 소스를 고쳐 다시 컴파일해야 한다. 구현이 아니라 추상에 의존하라는 DIP를 어겼고, 그 결과 확장할 때 기존 코드를 고쳐야 하니 OCP도 어긴다. 02회에서 설정 클래스를 따로 둔 이유가 바로 이 한 줄을 서비스에서 없애는 것이었다.

    테스트에서 바꿔 끼울 수 없고, 상태가 테스트 사이에 남는다

    서비스가 리포지토리를 스스로 가져오므로 테스트가 가짜 리포지토리를 넣어 줄 통로가 없다. 또 인스턴스가 정적 필드에 매여 있어 JVM이 살아 있는 동안 계속 남는다. 스프링 입문 03회에서 본 것처럼 JUnit은 테스트 메서드마다 테스트 클래스의 인스턴스를 새로 만들지만 정적 필드는 그대로이므로, 앞 테스트가 싱글톤에 남긴 데이터가 뒤 테스트의 결과를 바꾼다.

    private 생성자가 상속을 막는다

    자식 클래스의 생성자는 부모 생성자를 호출해야 하는데 부모의 생성자가 private뿐이면 다른 파일에서는 자식 클래스를 선언할 수 없다. 당장은 아쉬울 것이 없어 보이지만, 이 회차 뒷부분에서 보듯 스프링은 어떤 클래스의 자식 클래스를 실행 중에 만들어 기능을 덧붙이는 기법을 쓴다. 생성자를 잠가 둔 클래스에는 그 기법을 적용할 수 없다.

    "하나"의 범위가 생각보다 좁거나 깨질 수 있다

    private은 컴파일러와 JVM의 접근 검사일 뿐이어서 리플렉션으로 넘을 수 있다. 앞의 RegistryMain에 세 줄을 더해 보자(main에 throws Exception이 필요하다).

    싱글톤 컨테이너 — "하나"를 보장하는 책임을 클래스 밖으로 옮긴다

    스프링 컨테이너는 같은 목표를 다른 방법으로 이룬다. 클래스는 평범하게 둔다. 생성자는 public이고 정적 필드도 getInstance()도 없다. 대신 객체를 만드는 쪽인 컨테이너가 한 번만 만들고, 만든 것을 보관해 두었다가 같은 것을 돌려준다. 앞의 LibraryConfig에 애너테이션 두 가지만 붙여 스프링에 넘겨 보자. 메서드 본문은 한 글자도 바꾸지 않는다.

    @Configuration
public class LibraryConfig {

    @Bean
    public BookRepository bookRepository() {

        return new MemoryBookRepository();

    싱글톤 레지스트리의 실체

    "보관해 둔다"는 말의 실체는 맵 하나다. AnnotationConfigApplicationContext가 내부에 두는 빈 팩터리인 DefaultListableBeanFactory는 DefaultSingletonBeanRegistry를 상속하고, 그 클래스에 다음 필드가 있다.

    /** Cache of singleton objects: bean name to bean instance. */
private final Map singletonObjects = new ConcurrentHashMap<>(256);

    키는 빈 이름, 값은 완성된 빈 객체다. 레퍼런스 문서가 싱글톤 스코프를 설명하면서 "이 하나의 인스턴스는 싱글톤 빈들의 캐시에 저장되고, 그 이름의 빈에 대한 이후의 모든 요청과 참조는 캐시된 객체를 돌려받는다"고 한 그 캐시가 이 맵이다. 이렇게 객체를 이름으로 등록해 두고 하나만 유지해 주는 구조를 싱글톤 레지스트리(singleton registry)라고 부른다. 실험이 끝난 시점의 모습을 그리면 다음과 같다.

    DefaultListableBeanFactory (DefaultSingletonBeanRegistry를 상속)
└─ singletonObjects : ConcurrentHashMap
     "libraryConfig"   ──▶ 설정 클래스의 인스턴스
     "bookRepository"  ──▶ MemoryBookRepository ◀───────────┐ ◀─────────┐
     "loanService"     ──▶ LoanService   { bookRepository ──┘ }         │
     "searchService"   ──▶ SearchService { bookRepository ──────────────┘ }
     "environment", "messageSource", ... ──▶ 컨테이너 자신이 쓰는 객체들

    맵에 무엇이 들어 있는지는 공개 API로 확인할 수 있다. ac.getBeanFactory().getSingletonNames()를 출력하면 우리가 등록한 네 개 말고도 environment, systemProperties, messageSource, applicationEventMulticaster, 그리고 설정 클래스를 해석하는 ConfigurationClassPostProcessor(빈 이름은 org.springframework.context.annotation.internalConfigurationAnnotationProcessor) 같은 내부 부품이 함께 나온다. 이 실험에서는 모두 16개였다. 컨테이너는 자기 자신의 부품도 같은 레지스트리에 싱글톤으로 넣어 관리한다.

    getBean이 이 맵을 읽는 경로는 짧다.

    싱글톤 패턴과 견주면 책임의 위치가 옮겨졌을 뿐 장치는 같다. 패턴에서 정적 필드가 하던 "보관"을 맵이 하고, 클래스 초기화 락이 하던 "한 번만 생성"을 컨테이너의 생성 락과 putIfAbsent가 한다. 조회 쪽이 락 없이 동작할 수 있는 것은 맵이 ConcurrentHashMap이기 때문이다. 스프링 입문 03회에서 리포지토리의 저장소로 썼던 그 맵으로, 여러 스레드가 동시에 읽고 써도 내부 구조가 깨지지 않게 만들어져 있고 조회에는 락을 쓰지 않는다.

    생성 경로의 세부는 버전마다 다르다. 6.2와 7.0의 소스에서 생성용 락은 ReentrantLock 타입의 singletonLock 필드이고, 순환 참조를 풀기 위한 보조 맵(earlySingletonObjects, singletonFactories)이 함께 쓰인다. "완성된 싱글톤은 singletonObjects에 이름으로 저장되고, 조회는 먼저 이 맵을 본다"는 뼈대만 기억하면 충분하다.
    컨테이너 안의 맵(빈 이름 → 객체)과, 서로 다른 세 곳의 조회가 같은 객체 하나를 가리키게 되는 모습을 보여 준다. 깔끔한 평면 벡터 스타일의 구조도, 흰 배경. 가운데에 큰 둥근 사각형이 있고 위쪽에 라벨 "스프링 컨테이너". 그 안 왼쪽에 2열 표 모양의 상자가 있고 표 제목은 "싱글톤 레지스트리 (이름 → 객체)". 표의 행은 세 개로, 왼쪽 칸에 각각 "bookRepository", "loanService", "searchService"라고 적혀 있다. 각 행의 오른쪽 칸에서 화살표가 나가 컨테이너 안 오른쪽에 있는 객체 상자 세 개를 가리킨다. 객체 상자의 라벨은 위에서부터 "MemoryBookRepository 객체", "LoanService 객체", "SearchService 객체". "LoanService 객체"와 "SearchService 객체"에서 각각 점선 화살표가 나와 "MemoryBookRepository 객체" 하나를 가리킨다. 컨테이너 바깥 왼쪽에는 작은 말풍선 세 개가 세로로 놓여 있고 각각 "getBean ①", "getBean ②", "getBean ③"이라고 적혀 있으며, 세 말풍선에서 나온 화살표가 모두 표의 "loanService" 행으로 모인다. 그림 아래에 한 줄 라벨 "몇 번을 조회해도 같은 객체". 글자는 한국어와 영문 식별자, 산세리프, 선명하게. 컨테이너는 완성된 빈을 이름으로 맵에 넣어 두고, 같은 이름의 조회에는 언제나 그 객체를 돌려준다.

    언제 만들어지는가 — 시작할 때 전부

    실행 결과에서 객체 생성 로그가 "context ready"보다 앞에 찍혔다. 싱글톤 패턴의 정적 필드는 클래스가 처음 쓰일 때 초기화되었지만, 스프링의 ApplicationContext는 기본적으로 시작하면서 싱글톤을 모두 만든다. 컨테이너의 refresh()는 빈 정의를 다 읽고 난 뒤쪽 단계에서 preInstantiateSingletons()를 불러, 등록된 빈 정의를 차례로 돌며 추상이 아니고 싱글톤 스코프인 것마다 빈을 생성한다(지연 초기화로 표시한 빈은 건너뛴다).

    레퍼런스 문서는 이유를 이렇게 적는다. 설정이나 주변 환경의 오류가 몇 시간, 며칠 뒤가 아니라 즉시 드러나기 때문에 이 사전 생성이 대체로 바람직하다는 것이다. 의존하는 빈이 없거나 생성자에서 예외가 나는 문제를 첫 사용자 요청이 아니라 배포 직후 기동 단계에서 만나게 된다. 첫 요청이 객체 생성 비용을 떠안지 않는다는 이점도 따라온다.

    "하나"의 범위 — 컨테이너마다, 빈 정의마다

    스프링의 싱글톤은 "클래스에 하나"가 아니다. 레퍼런스 문서는 GoF의 싱글톤이 클래스 로더당 특정 클래스의 인스턴스를 하나로 고정하는 것과 달리 스프링 싱글톤의 범위는 컨테이너당, 빈당(per-container and per-bean)이라고 설명한다. 레지스트리의 키가 클래스가 아니라 빈 이름이고, 레지스트리 자체가 컨테이너마다 따로 있으니 당연한 결과다. 같은 클래스로 빈 정의를 둘 만들고 컨테이너도 둘 띄워 확인한다.

    public class ScopeMain {
    @Configuration
    static class TwoRepoConfig {
        @Bean BookRepository mainRepository() { return new MemoryBookRepository(); }
        @Bean BookRepository archiveRepository() { return new MemoryBookRepository(); }
    }

    public static void main(String[] args) {
        var ac1 = new AnnotationConfigApplicationContext(TwoRepoConfig.class);
        var ac2 = new AnnotationConfigApplicationContext(TwoRepoConfig.class);

        Object main1 = ac1.getBean("mainRepository");
        Object archive1 = ac1.getBean("archiveRepository");
        Object main2 = ac2.getBean("mainRepository");

        System.out.println("같은 컨테이너, 같은 이름:   " + (main1 == ac1.getBean("mainRepository")));
        System.out.println("같은 컨테이너, 다른 이름:   " + (main1 == archive1));
        System.out.println("다른 컨테이너, 같은 이름:   " + (main1 == main2));
        ac1.close();
        ac2.close();
    }
}

같은 컨테이너, 다른 이름:   false
다른 컨테이너, 같은 이름:   false

    MemoryBookRepository 객체는 JVM 안에 넷이다. 그래도 각각은 자기 컨테이너에서 자기 이름으로는 유일하다. 싱글톤 패턴에서 불가능했던 "같은 클래스의 객체를 용도별로 둘"이 빈 정의를 하나 더 쓰는 것으로 끝난다.

    요청을 처리할 때는 레지스트리를 거치지 않는다

    맵 조회가 요청마다 일어난다고 생각하기 쉽지만 그렇지 않다. 컨테이너는 시작할 때 LoanService를 만들면서 생성자에 리포지토리 참조를 넘겼고, 그 참조는 LoanService 객체의 final 필드에 들어갔다. 이후 요청 스레드가 서비스의 메서드를 실행하며 리포지토리를 쓸 때 일어나는 일은 필드 읽기(getfield)와 메서드 호출(invokeinterface)뿐이다. 싱글톤 레지스트리는 조립할 때 쓰는 장부이고, 조립이 끝난 뒤의 객체들은 서로를 직접 가리킨다.

    시작할 때 한 스레드가 만든 객체를 나중에 다른 스레드들이 읽어도 값이 제대로 보이는가 하는 의문이 남는다. 자바 언어 명세의 메모리 모델(Java Memory Model)은 한 스레드가 쓴 값이 다른 스레드의 읽기에 보인다고 보장되는 조건을 정해 두는데, 싱글톤 빈은 두 가지 조건에 걸린다. JLS §17.5에 따르면 생성자가 끝난 뒤에야 객체의 참조를 볼 수 있었던 스레드는 그 객체의 final 필드에 대해 올바르게 초기화된 값을 본다. 또 java.util.concurrent 패키지 문서는 한 스레드가 객체를 동시성 컬렉션에 넣기 전에 한 동작이, 다른 스레드가 그 원소를 컬렉션에서 꺼낸 뒤에 하는 동작보다 먼저 일어난 것으로 보장된다고(happens-before) 명시한다. 싱글톤 레지스트리가 바로 그런 컬렉션이다. 이 규칙들의 전체 그림은 자바 고급 1편의 몫이고, 여기서는 06회에서 다룰 생성자 주입과 final 필드가 이 가시성 보장과도 맞닿아 있다는 것만 짚어 둔다.

    싱글톤 방식의 주의점 — 객체가 하나면 필드도 하나다

    여기까지의 결론은 "서비스 객체는 하나이고 모든 요청 스레드가 그것을 함께 쓴다"이다. 이 문장에서 곧바로 따라 나오는 사실이 있다. 객체가 하나면 그 객체의 인스턴스 필드도 메모리에 한 칸씩만 있다. 어느 스레드가 그 칸에 쓴 값은 다른 모든 스레드에게 보이고, 다른 스레드가 덮어쓸 수 있다.

    거리에 따라 요금을 계산하는 서비스를 예로 든다. 계산한 요금을 필드에 넣어 두고 나중에 꺼내 가게 만든 코드다.

    public class FareService {
    private int fare;                      // 인스턴스 필드: 힙의 객체 안에 한 칸

    public void calculate(String passenger, int km) {
        this.fare = 1_500 + km * 100;      // 요청마다 달라지는 값을 필드에 쓴다
    }

    public int getFare() {
        return fare;
    }
}

    스레드 하나로 테스트하면 아무 문제가 없다. calculate("A", 5)를 부르고 getFare()를 부르면 2,000이 나온다. 요청 스레드 둘이 이 객체 하나를 함께 쓰면 달라진다. 실행 순서를 재현할 수 있도록 "A가 계산한 뒤, A가 읽기 전에 B가 계산한다"는 순서를 고정해 돌려 본다. CountDownLatch는 다른 스레드가 countDown()을 부를 때까지 await()를 부른 스레드를 세워 두는 도구이고, 여기서는 그 순서를 강제하는 용도로만 쓴다. new Thread(() -> { ... }, "request-A")는 중괄호 안의 코드 조각(람다)을 그 이름의 새 스레드에서 실행하게 한다.

    public class FareMain {
    public static void main(String[] args) throws Exception {
        FareService service = new FareService();           // 객체는 하나
        CountDownLatch aCalculated = new CountDownLatch(1);
        CountDownLatch bCalculated = new CountDownLatch(1);

        Thread a = new Thread(() -> {
            service.calculate("A", 5);                     // A의 요금은 2,000원이어야 한다
            aCalculated.countDown();
            await(bCalculated);                            // 그 사이 B가 끼어든다
            System.out.println("A가 읽은 요금 = " + service.getFare());
        }, "request-A");

        Thread b = new Thread(() -> {
            await(aCalculated);
            service.calculate("B", 40);                    // B의 요금은 5,500원
            bCalculated.countDown();
            System.out.println("B가 읽은 요금 = " + service.getFare());
        }, "request-B");

        a.start(); b.start();
        a.join(); b.join();
    }

    private static void await(CountDownLatch latch) {
        try { latch.await(); } catch (InterruptedException e) { throw new IllegalStateException(e); }
    }
}
    A가 읽은 요금 = 5500
B가 읽은 요금 = 5500

    승객 A는 5km를 탔는데 5,500원을 청구받았다. 코드 어디에도 문법 오류나 예외는 없다. 시간 순서대로 따라가면 원인이 보인다.

    순서request-A 스레드request-B 스레드힙에 있는 fare 필드
    1calculate("A", 5) → 2000을 필드에 쓴다대기2000
    2대기calculate("B", 40) → 5500을 필드에 쓴다5500
    3getFare() → 필드를 읽는다getFare() → 필드를 읽는다5500

    실험에서는 래치로 순서를 고정했지만 실제 서버에서는 이 순서가 우연히 생긴다. 두 요청의 처리 구간이 겹칠 때만 나타나고 다시 시도하면 사라지므로 테스트로는 잡히지 않다가 운영 중에 "가끔 다른 사람의 값이 보인다"는 형태로 드러난다. 금액, 사용자 식별자, 권한 같은 값에서 이런 일이 생기면 단순한 버그가 아니라 사고다.

    힙과 스택으로 보면

    왜 필드는 섞이고 지역 변수는 섞이지 않는지는 JVM의 메모리 구조가 답한다. JVMS §2.5.3은 힙이 모든 JVM 스레드가 공유하는 영역이라고 규정하고, §2.5.2는 스레드마다 자기만의 JVM 스택이 있다고 규정한다. §2.6에 따르면 메서드를 호출할 때마다 프레임이 새로 만들어지고, 한 스레드가 만든 프레임은 그 스레드에 속하며 다른 스레드가 참조할 수 없다. 지역 변수와 매개변수는 이 프레임 안의 지역 변수 배열에 놓인다.

    request-A의 스택                  힙 (모든 스레드가 공유)            request-B의 스택
┌──────────────────────┐        ┌───────────────────────┐        ┌──────────────────────┐
│ calculate 프레임     │        │ FareService 객체      │        │ calculate 프레임     │
│  this ───────────────┼───────▶│   fare : [ 한 칸 ]    │◀───────┼─ this                │
│  passenger = "A"     │        └───────────────────────┘        │  passenger = "B"     │
│  km = 5              │                                         │  km = 40             │
└──────────────────────┘                                         └──────────────────────┘

    두 스레드의 this는 같은 객체를 가리킨다. passenger와 km은 프레임마다 따로 있어서 A의 5와 B의 40이 섞일 일이 없지만, this.fare는 힙의 한 칸이다. 바이트코드에서도 차이가 드러난다. 필드에 쓰는 버전은 계산 결과를 putfield로 힙의 객체에 내보낸다.

           0: aload_0
       1: sipush        1500
       4: iload_2
       5: bipush        100

       9: putfield      #7                  // Field fare:I
      12: return

    자식 클래스가 메서드를 오버라이딩했다고 해도, 문제의 호출은 부모 클래스 LibraryConfig의 메서드 본문 안에 있다. 부모의 코드가 자식의 메서드로 들어가는 이유는 원본 loanService()의 바이트코드에 있다.

           8: new           #26                 // class lib/LoanService
      11: dup
      12: aload_0
      13: invokevirtual #28                 // Method bookRepository:()Llib/BookRepository;
      16: invokespecial #34                 // Method lib/LoanService."":(Llib/BookRepository;)V
      19: areturn

    소스의 bookRepository()는 this.bookRepository()를 줄여 쓴 것이다. 컴파일러는 this를 스택에 올리고(aload_0) invokevirtual을 낸다. 자바 기본편에서 다형성을 배울 때 본 그 명령이다. invokevirtual은 컴파일 시점의 타입이 아니라 스택에 놓인 객체의 실제 클래스에서 출발해 실행할 메서드를 고른다. 컨테이너 안에서 this는 자식 클래스의 인스턴스이므로, 부모의 코드에 적힌 invokevirtual bookRepository는 자식이 오버라이딩한 bookRepository()를 실행한다. 원본 클래스 파일을 한 바이트도 고치지 않고 동작을 바꿀 수 있는 것은 이 호출이 처음부터 실행 시점에 결정되도록 컴파일되어 있기 때문이다.

    자식 클래스 방식이어야 하는 이유도 여기서 나온다. 원본 객체를 따로 두고 그 앞에 대리 객체를 세워 호출을 넘겨주는 구조였다면, 원본 객체의 메서드 안에서 this는 원본 자신이고 자기 메서드 호출은 대리 객체를 거치지 않는다. 뒤 권에서 배울 스프링 AOP의 프록시가 그런 구조여서, 같은 객체 안의 메서드를 직접 부르면 프록시의 부가 기능이 적용되지 않는다는 제약이 있다. @Configuration의 경우는 원본 객체가 따로 없고 자식 클래스의 인스턴스가 곧 설정 객체이므로 자기 호출까지 가로챈다.

    인터셉터는 무엇을 보고 판단하는가

    오버라이딩한 메서드가 호출을 넘기는 인터셉터는 ConfigurationClassEnhancer 안의 BeanMethodInterceptor다. 하는 일의 뼈대는 분기 하나다.

    intercept(설정객체, 호출된 @Bean 메서드, 인자, 부모 호출 통로):
    beanFactory = 설정객체의 $$beanFactory 필드
    beanName    = 그 @Bean 메서드가 정의하는 빈의 이름

    if (지금 컨테이너가 바로 이 메서드를 불러 빈을 만드는 중인가?)
        return 부모 호출 통로로 원본 메서드 실행          // 여기서만 new가 일어난다
    else
        return beanFactory.getBean(beanName)              // 레지스트리에 있는 것을 돌려준다

    조건문의 판단 근거는 스레드별 기록이다. 컨테이너는 @Bean 메서드를 리플렉션으로 부르기 직전에 그 Method를 ThreadLocal 변수(SimpleInstantiationStrategy의 currentlyInvokedFactoryMethod)에 적어 두고, 호출이 끝나면 이전 값으로 되돌린다. ThreadLocal은 스레드마다 값을 따로 갖는 변수여서 "지금 이 스레드가 어느 팩터리 메서드를 실행하는 중인가"를 기록하기에 알맞다. 인터셉터는 방금 가로챈 메서드의 이름과 매개변수 타입이 그 기록과 같은지 비교한다. 같으면 컨테이너가 빈을 만들려고 부른 것이고, 다르면 다른 @Bean 메서드의 본문이나 바깥 코드가 부른 것이다.

    이 규칙으로 LibraryConfig의 시작 과정을 한 단계씩 따라가 본다. 컨테이너는 빈 정의가 등록된 순서인 libraryConfig, bookRepository, loanService, searchService 순으로 싱글톤을 만든다.

    단계누가 무엇을 호출하는가스레드에 기록된 팩터리 메서드인터셉터의 판단결과
    1컨테이너가 bookRepository 빈을 만들려고 설정 객체의 bookRepository()를 리플렉션으로 호출bookRepository기록과 같다 → 원본 실행로그 한 줄, new MemoryBookRepository(), 레지스트리에 등록
    2컨테이너가 loanService 빈을 만들려고 loanService()를 호출loanService기록과 같다 → 원본 실행로그 한 줄, 원본 본문 진입
    3원본 loanService() 본문의 this.bookRepository()loanService (그대로)기록과 다르다 → getBean("bookRepository")1단계에서 등록된 객체를 반환. 원본 bookRepository()는 실행되지 않는다
    4컨테이너가 searchService()를 호출하고, 그 본문이 this.bookRepository()를 호출searchService2, 3단계와 같다같은 리포지토리 객체가 주입된다

    실행 결과에서 call LibraryConfig.bookRepository()가 한 번만 찍힌 이유가 3단계다. 자식의 bookRepository()는 호출되었지만 인터셉터가 원본으로 내려보내지 않았으므로 원본 본문의 println과 new가 실행되지 않았다. 1단계에서 컨테이너가 리플렉션으로 호출할 때 자식의 메서드가 실행되는 것도 같은 원리다. Method.invoke의 Javadoc은 인스턴스 메서드를 호출할 때 대상 객체의 실행 시점 타입에 따른 오버라이딩이 적용된다고 적고 있다.

    선언 순서를 바꾸면 어떻게 되는지도 확인했다. loanService(), searchService(), bookRepository() 순으로 선언한 설정 클래스에서는 출력이 다음과 같다.

    call OrderConfig.loanService()
call OrderConfig.bookRepository()
  new MemoryBookRepository()
call OrderConfig.searchService()

    이번에는 loanService가 먼저 만들어진다. 원본 loanService()가 this.bookRepository()를 부르면 인터셉터는 기록(loanService)과 다르다고 보고 getBean("bookRepository")를 부른다. 레지스트리에 아직 그 빈이 없으므로 컨테이너가 그 자리에서 만들기 시작한다. 기록을 bookRepository로 바꾸고 설정 객체의 bookRepository()를 호출하면, 이번에는 기록과 같으므로 원본이 실행되어 객체가 만들어지고 등록된다. 호출이 끝나면 기록은 loanService로 되돌아가고 loanService()의 본문이 이어진다. 선언 순서와 무관하게 리포지토리는 한 번만 만들어진다. 어느 메서드가 먼저 불리든 "레지스트리에 없으면 컨테이너가 만들고, 있으면 그것을 준다"는 규칙이 같기 때문이다.

    실제 인터셉터에는 분기가 더 있다. 호출된 메서드가 FactoryBean을 만드는 경우와 스코프 프록시가 걸린 빈의 경우를 따로 처리한다. 또 getBean이 돌려준 객체가 메서드의 반환 타입과 맞지 않으면 예외를 던진다. 싱글톤이 아닌 스코프의 빈이라면 getBean이 그 스코프의 규칙대로 객체를 돌려준다. 스코프는 08회에서 다룬다.
    컨테이너의 호출은 원본 메서드로 내려가고, 원본 메서드 안의 자기 호출은 인터셉터가 레지스트리 조회로 바꾼다는 두 갈래를 한 그림에서 보여 준다. 깔끔한 평면 벡터 스타일의 시퀀스 다이어그램, 흰 배경. 위쪽에 참여자 상자 네 개가 왼쪽부터 "컨테이너", "설정 객체 (CGLIB 자식)", "LibraryConfig 원본 코드", "싱글톤 레지스트리" 순으로 놓이고 각 상자에서 아래로 생명선이 내려온다. 위에서 아래로 번호가 붙은 화살표: ① "컨테이너"에서 "설정 객체 (CGLIB 자식)"로 실선 화살표, 라벨 "loanService() 호출". ② "설정 객체 (CGLIB 자식)"에서 "LibraryConfig 원본 코드"로 실선 화살표, 라벨 "컨테이너의 호출 → 원본 실행". ③ "LibraryConfig 원본 코드"에서 "설정 객체 (CGLIB 자식)"로 되돌아가는 굵은 강조색 화살표, 라벨 "this.bookRepository()". ④ "설정 객체 (CGLIB 자식)"에서 "싱글톤 레지스트리"로 실선 화살표, 라벨 "getBean(bookRepository)". ⑤ "싱글톤 레지스트리"에서 "LibraryConfig 원본 코드"로 점선 화살표, 라벨 "이미 있는 객체 반환". ⑥ "LibraryConfig 원본 코드"에서 "컨테이너"로 점선 화살표, 라벨 "LoanService 완성". ③번 화살표 옆에 작은 메모 상자 "원본의 new는 실행되지 않는다". 글자는 한국어와 영문 식별자, 산세리프, 선명하게. 컨테이너가 부른 호출은 원본 메서드로 내려가고, 원본 본문 안에서 다른 @Bean 메서드를 부르는 호출은 레지스트리 조회로 바뀐다.

    프록시가 없으면 — 라이트 모드와 proxyBeanMethods

    자식 클래스가 이 모든 일을 한다면, 자식 클래스가 만들어지지 않을 때는 어떻게 되는가. LibraryConfig에서 @Configuration만 지우고 @Bean은 그대로 둔 LiteConfig를 만들어 같은 방식으로 컨테이너에 넘겼다.

    call LiteConfig.bookRepository()
  new MemoryBookRepository()
call LiteConfig.loanService()
call LiteConfig.bookRepository()
  new MemoryBookRepository()
call LiteConfig.searchService()
call LiteConfig.bookRepository()
  new MemoryBookRepository()

loan.repo == search.repo? false

    예외도 경고도 없이 시작된다. @Bean 메서드 셋은 여전히 빈으로 등록되고, 각 빈은 레지스트리에 하나씩 들어간다. 달라진 것은 설정 객체의 클래스가 원본 LiteConfig라는 점 하나다. 가로챌 자식이 없으니 loanService() 안의 bookRepository()는 평범한 자바 메서드 호출이 되어 새 객체를 만든다. 리포지토리가 셋 생겼고, 그중 컨테이너가 아는 것은 첫 번째뿐이다. 두 서비스 안에 들어간 나머지 둘은 레지스트리에 없는 객체다. 대출 서비스로 저장한 책이 검색 서비스에서도, getBean(BookRepository.class)로 꺼낸 리포지토리에서도 보이지 않는다. 이 회차 첫머리에서 본 문제가 스프링 안에서 조용히 되살아난 것이다.

    레퍼런스 문서는 @Configuration이 없는 클래스의 @Bean 메서드, 그리고 @Configuration(proxyBeanMethods = false)로 선언한 클래스의 @Bean 메서드가 처리되는 방식을 "라이트(lite) 모드"라고 부른다. 이 모드의 @Bean 메서드는 특별한 실행 시점 처리가 없는 일반적인 팩터리 메서드이고, 자바 코드에서 직접 부르면 가로채지지 않아 매번 새 인스턴스가 만들어진다고 적혀 있다. 자식 클래스를 만드는 기본 방식은 이와 구분해 풀(full) 모드라고 한다.

    proxyBeanMethods = false와 매개변수 주입

    proxyBeanMethods는 스프링 프레임워크 5.2에서 @Configuration에 추가된 속성이고 기본값은 true다. false로 두면 자식 클래스를 만들지 않는다. 그 대신 @Bean 메서드끼리 직접 부르지 말고, 필요한 빈을 메서드의 매개변수로 받아야 한다.

    @Configuration(proxyBeanMethods = false)
public class NoProxyConfig {

    @Bean
    public BookRepository bookRepository() {
        System.out.println("call NoProxyConfig.bookRepository()");
        return new MemoryBookRepository();
    }

    @Bean
    public LoanService loanService(BookRepository bookRepository) {       // 컨테이너가 인자를 채운다
        System.out.println("call NoProxyConfig.loanService(repo)");
        return new LoanService(bookRepository);
    }

    @Bean
    public SearchService searchService(BookRepository bookRepository) {
        System.out.println("call NoProxyConfig.searchService(repo)");
        return new SearchService(bookRepository);
    }
}

    설정 객체는 원본 클래스 그대로인데 리포지토리는 하나다. 컨테이너가 loanService(...)를 호출하기 전에 매개변수 타입에 맞는 빈을 레지스트리에서 찾아 인자로 넣어 주기 때문이다. 메서드 본문에는 다른 @Bean 메서드를 부르는 코드가 아예 없으므로 가로챌 것도 없다. 이 방식은 풀 모드에서도 똑같이 동작한다. 레퍼런스 문서는 자식 클래스를 만들지 않는 만큼 부담과 차지하는 공간이 줄어든다는 점을 이 방식의 부수 효과로 든다. 스프링 부트가 제공하는 자동 구성 클래스에 붙는 @AutoConfiguration(스프링 부트 2.7부터)도 proxyBeanMethods가 항상 false인 @Configuration이다.

    상속으로 구현했기 때문에 생기는 제약

    풀 모드의 가로채기는 오버라이딩에 기대므로, 자바에서 오버라이딩할 수 없는 것은 가로챌 수 없다. 각 경우를 실제로 돌려 확인했다.

    선언결과이유
    @Configuration public final class시작 실패: @Configuration class 'FinalConfig' may not be final. Remove the final modifier to continue.final 클래스는 상속할 수 없다
    @Bean public final ... 또는 private 메서드시작 실패: @Bean method 'bookRepository' must not be private or final; change the method's modifiers to continue.final·private 메서드는 오버라이딩할 수 없다
    생성자가 private뿐인 설정 클래스시작 실패: No visible constructors in class lib.PrivateCtorConfig자식의 생성자가 부를 부모 생성자가 없다
    @Bean public static ...시작은 된다. 그러나 다른 @Bean 메서드가 이 메서드를 직접 부르면 새 객체가 만들어진다정적 메서드는 객체가 아니라 클래스에 묶여 있어 오버라이딩 대상이 아니다
    @Configuration(proxyBeanMethods = false) public final class정상 시작자식 클래스를 만들지 않으므로 제약이 없다

    앞의 세 줄은 스프링이 시작 시점에 검사해서 알려 주므로 놓칠 일이 없다. 조심할 것은 넷째 줄이다. 정적 @Bean 메서드를 가진 설정 클래스로 실험하면 설정 객체의 클래스는 StaticConfig$$SpringCGLIB$$0으로 바뀌지만, loanService()가 정적 bookRepository()를 부를 때마다 새 리포지토리가 만들어지고 서비스가 가진 것과 컨테이너의 빈이 서로 다른 객체가 된다. 레퍼런스 문서도 정적 @Bean 메서드에 대한 호출은 @Configuration 클래스 안에서도 가로채지지 않는다고 명시한다. 싱글톤 패턴 절에서 private 생성자가 상속을 막는다고 한 것이 여기서 실제 제약으로 돌아온다.

    흔한 오해 다섯 가지

    • "스프링 빈은 JVM에 하나만 있다." 범위는 컨테이너 하나, 빈 정의 하나다. 같은 클래스로 빈 정의를 둘 쓰면 객체가 둘이고, 컨테이너를 둘 띄우면 각자 따로 갖는다. 서버 프로세스를 여러 대 띄운 서비스라면 프로세스마다 컨테이너가 있으므로 "싱글톤 빈의 필드에 둔 카운터"는 서버마다 따로 센다.
    • "싱글톤 빈은 스레드 안전하다." 컨테이너가 보장하는 것은 객체가 한 번만 만들어지고 안전하게 공개된다는 것까지다. 그 객체의 필드를 여러 스레드가 고쳐 써도 되는지는 클래스를 쓴 사람이 책임진다. 오히려 싱글톤이기 때문에 모든 필드가 공유 자원이 된다.
    • "무상태란 필드가 없다는 뜻이다." 주입받은 의존 객체나 설정 값처럼 시작할 때 정해지고 바뀌지 않는 필드는 상태로 치지 않는다. 문제 되는 것은 특정 요청에 속한 값을 요청 처리 중에 필드에 쓰는 것이다.
    • "@Bean만 붙이면 @Configuration은 있으나 없으나 같다." 빈으로 등록되는 것까지는 같다. @Bean 메서드끼리 직접 호출하는 순간 달라진다. 풀 모드에서는 같은 빈이, 라이트 모드에서는 컨테이너가 모르는 새 객체가 나온다.
    • "CGLIB 프록시가 요청마다 끼어들어 느려진다." 자식 클래스로 바뀌는 것은 설정 클래스뿐이다. 싱글톤 목록에서 본 것처럼 bookRepository 빈의 클래스는 MemoryBookRepository 그대로이고 LoanService는 그 객체를 직접 가리킨다. 인터셉터가 동작하는 때는 누군가 설정 객체의 @Bean 메서드를 부를 때, 곧 대부분 시작할 때뿐이다.

    다른 곳에서 다시 만나는 것

    이 회차의 내용은 이 권의 나머지 회차가 딛고 서는 바닥이다. 05회의 컴포넌트 스캔은 설정 클래스에 @Bean 메서드를 쓰는 대신 클래스에 붙은 애너테이션을 찾아 빈 정의를 만드는데, 그렇게 등록된 빈도 기본 스코프는 싱글톤이고 같은 레지스트리에 들어간다. 06회의 생성자 주입은 싱글톤 빈의 의존 객체를 final 필드로 고정해, 이 회차에서 말한 "시작할 때 정해지고 바뀌지 않는 필드"를 문법으로 강제한다. 07회의 생명주기 콜백은 빈이 만들어져 의존관계 주입이 끝난 뒤와 컨테이너가 닫힐 때 호출되는 메서드를 다루고, 08회는 싱글톤이 아닌 스코프와, 싱글톤 빈이 수명이 더 짧은 빈을 주입받을 때 생기는 문제를 다룬다. 08회의 해법 가운데 하나가 다시 CGLIB으로 만든 자식 클래스다.

    권 밖으로 나가도 같은 구조가 반복된다. 스프링 MVC의 컨트롤러는 싱글톤 빈이므로 요청 데이터를 컨트롤러의 필드에 두면 이 회차의 FareService와 똑같이 깨진다. 스프링 핵심 원리 고급편에서 배울 AOP와, 스프링 DB 편에서 배울 선언적 트랜잭션은 빈을 감싸는 프록시로 동작하는데, 그 프록시를 만드는 수단 가운데 하나가 이 회차에서 본 CGLIB의 자식 클래스 생성이다. 그때 "클래스나 메서드가 final이면 적용되지 않는다", "같은 객체 안의 메서드 호출에는 적용되지 않는다" 같은 제약을 만나면, 상속과 invokevirtual이라는 이 회차의 설명으로 돌아오면 된다. 락, volatile, 원자적 연산, ThreadLocal의 원리는 자바 고급 1편에서 바닥부터 다시 다룬다.
    요청마다 객체를 만드는 방식의 문제
    저장소·커넥션 풀·캐시처럼 함께 봐야 할 객체가 요청별로 갈라져 틀리게 동작하고, 공유할 것이 없는 객체도 요청 수에 비례해 만들어지고 버려진다.
    싱글톤 패턴
    private 생성자, 정적 필드, 정적 접근 메서드로 클래스가 스스로 인스턴스를 하나로 제한한다. 정적 필드 초기화 방식이 락 없이 안전한 것은 JVM이 클래스 초기화를 클래스별 초기화 락으로 한 번만 실행하기 때문이다(JLS §12.4).
    싱글톤 패턴의 비용
    쓰는 쪽이 구체 클래스에 의존해 DIP·OCP를 어기고, 테스트에서 교체하기 어렵고, 상속이 막히며, "하나"의 범위는 클래스 로더 단위이고 리플렉션으로 깨진다.
    싱글톤 레지스트리
    스프링 컨테이너는 완성된 빈을 빈 이름을 키로 하는 ConcurrentHashMap(singletonObjects)에 보관하고 같은 이름의 조회에는 그 객체를 돌려준다. 클래스는 평범하게 두고 "하나"의 보장을 컨테이너가 맡는다.
    스프링 싱글톤의 범위와 생성 시점
    컨테이너마다, 빈 정의마다 하나다. ApplicationContext는 기본적으로 시작할 때 싱글톤을 모두 만들어 설정 오류를 기동 단계에서 드러낸다.
    무상태 설계
    싱글톤 객체의 필드는 힙에 한 칸뿐이어서 모든 요청 스레드가 공유한다. 요청별 값은 스레드마다 따로 있는 스택 프레임의 지역 변수·매개변수·반환값으로 다루고, 필드에는 바뀌지 않는 의존 객체와 설정 값만 둔다.
    @Configuration과 CGLIB
    빈 객체를 만들기 전에 ConfigurationClassPostProcessor가 설정 클래스를 상속한 자식 클래스를 생성해 빈 정의의 클래스를 바꾼다. 자식은 @Bean 메서드를 오버라이딩해, 컨테이너가 부른 호출만 원본으로 보내고 나머지는 getBean으로 돌린다.
    라이트 모드
    @Configuration이 없거나 proxyBeanMethods = false이면 자식 클래스가 없어 @Bean 메서드끼리의 직접 호출이 평범한 자바 호출이 된다. 이때는 의존 빈을 메서드 매개변수로 받아야 한다.

    실무에서 "가끔 다른 사용자의 값이 보인다", "부하가 걸릴 때만 금액이 틀린다"는 제보를 받으면 가장 먼저 의심할 곳이 싱글톤 빈의 필드다. 컨트롤러·서비스·리포지토리 클래스에서 final이 아닌 인스턴스 필드를 찾고, 그 필드에 값을 쓰는 코드가 요청 처리 경로에 있는지 본다. 값을 쓰지 않더라도 스레드 안전하지 않다고 문서에 적힌 객체를 필드에 두고 여러 요청이 함께 쓰는 경우도 같은 종류의 문제다. 이런 버그는 단일 스레드 테스트를 전부 통과하므로 코드 리뷰에서 "이 필드는 누구의 값인가"를 묻는 습관으로 막는 편이 훨씬 싸다.

    상태가 정말 필요할 때는 그 상태의 범위를 먼저 정한다. 한 요청 안에서만 필요하면 매개변수와 반환값으로 넘기거나 요청마다 새 객체를 만든다. 한 서버 프로세스 안에서 모든 요청이 공유해야 하면 싱글톤 빈의 필드에 두되 스레드 안전한 자료구조를 쓴다. 서버 여러 대가 공유해야 하면 싱글톤 빈의 필드로는 해결되지 않는다. 스프링의 싱글톤은 컨테이너 단위이므로 서버가 세 대면 그 필드도 셋이다. 이 경우 상태는 데이터베이스 같은 외부 저장소로 나가야 한다. "싱글톤이니까 하나"라는 생각으로 메모리 카운터나 메모리 캐시에 정합성이 필요한 값을 두었다가 서버를 늘리면서 문제가 되는 일이 흔하다.

    @Configuration의 풀 모드와 라이트 모드는 편의와 제약의 교환이다. 풀 모드는 메서드 호출로 의존관계를 표현할 수 있어 읽기 쉽지만 시작할 때 클래스를 하나 더 생성하고, 클래스와 메서드에 final을 쓸 수 없다. proxyBeanMethods = false는 그 비용과 제약을 없애는 대신 "@Bean 메서드를 직접 부르지 않는다"는 규율을 사람에게 맡긴다. 어느 쪽을 택하든 의존 빈을 메서드 매개변수로 받는 방식은 두 모드에서 똑같이 올바르게 동작하므로, 팀의 설정 클래스를 이 방식으로 통일해 두면 모드를 바꿔도 동작이 달라지지 않는다. 설정 클래스에서 @Configuration을 실수로 빠뜨려도 오류 없이 기동된다는 점은 기억해 둘 만하다. 같은 타입의 객체가 둘 이상 만들어진 흔적(생성자 로그가 두 번 찍힌다, 저장한 데이터가 다른 빈에서 보이지 않는다)이 보이면 설정 객체의 getClass()를 찍어 보는 것이 가장 빠른 진단이다.

(나) 네 번 출력되고 두 인자는 다른 객체다. 자식 클래스가 없으므로 컨테이너의 호출 한 번, quoteService() 안의 두 번, invoiceService() 안의 한 번이 모두 원본을 실행한다. (다) 역시 네 번 출력되고 두 인자는 다른 객체다. 설정 클래스는 자식으로 바뀌지만 정적 메서드는 오버라이딩할 수 없어 가로채지지 않는다. 세 경우 모두 직접 실행해 확인한 결과다.

    4. MemoryBookRepository는 6개다. 스프링 싱글톤의 단위는 "컨테이너 하나 안의 빈 정의 하나"이고 3 × 2 = 6이다. Registry는 (세 컨테이너의 클래스가 같은 클래스 로더로 로드되었다면) 1개다. 싱글톤 패턴의 단위는 "클래스 로더 하나 안의 클래스 하나"이고 컨테이너가 몇 개인지는 관계가 없다. 정적 필드는 컨테이너가 아니라 클래스에 딸려 있기 때문이다.

    5. @Configuration class 'AppSettings' may not be final. Remove the final modifier to continue.라는 설정 오류로 시작이 실패한다. 기본(풀) 모드에서 스프링은 설정 클래스를 상속한 자식 클래스를 만들어 @Bean 메서드를 오버라이딩하는데, final 클래스는 상속할 수 없기 때문이다. final을 유지하려면 @Configuration(proxyBeanMethods = false)로 선언한다. 이때는 자식 클래스가 만들어지지 않으므로 @Bean 메서드 안에서 다른 @Bean 메서드를 직접 호출하면 안 되고, 필요한 빈을 메서드 매개변수로 받아야 한다.

     스프링의 싱글톤 스코프 빈에서 "인스턴스가 하나"라는 말의 범위로 옳은 것은? JVM 전체에서 클래스마다 하나 컨테이너 하나 안에서 빈 정의마다 하나 클래스 로더마다 클래스 하나에 하나 요청 스레드마다 하나 싱글톤 레지스트리는 컨테이너마다 따로 있고 키가 빈 이름이므로, 범위는 컨테이너당·빈 정의당이다. 같은 클래스로 빈 정의를 둘 만들면 객체도 둘이고, 컨테이너를 둘 띄우면 각자 따로 만든다. "클래스 로더마다 클래스에 하나"는 싱글톤 패턴의 범위이고, 스레드마다 하나인 것은 스택 프레임이나 ThreadLocal의 성질이다. 싱글톤 빈으로 등록된 서비스 클래스의 필드 가운데, 동시에 들어온 두 요청의 값이 섞일 수 있는 것은? private final BookRepository bookRepository; (생성자에서 주입) private final int baseFare; (생성자에서 설정 값으로 초기화) private int fare; (요청을 처리하는 메서드가 계산 결과를 대입) private static final int FARE_PER_KM = 100; 싱글톤 객체의 인스턴스 필드는 힙에 한 칸뿐이고 모든 요청 스레드가 공유한다. 요청 처리 중에 값을 쓰는 필드는 다른 스레드가 덮어쓸 수 있다. 나머지 셋은 시작할 때 정해진 뒤 읽기만 하므로 공유되어도 문제가 없다. 지역 변수였다면 스레드마다 따로 있는 스택 프레임에 놓여 섞이지 않는다. @Configuration 클래스의 loanService() 본문이 bookRepository()를 직접 호출해도 새 객체가 아니라 컨테이너의 빈이 돌아오는 이유는? 컨테이너에 등록된 설정 객체가 설정 클래스를 상속한 자식 클래스의 인스턴스이고, this.bookRepository()는 실행 시점의 클래스로 대상을 정하는 invokevirtual이어서 자식이 오버라이딩한 메서드가 실행되기 때문이다 자바 컴파일러가 @Bean 애너테이션을 보고 메서드가 한 번만 실행되도록 바이트코드를 다르게 만들기 때문이다 JVM이 인자가 같은 메서드 호출의 결과를 자동으로 캐시하기 때문이다 스프링이 시작할 때 설정 클래스의 .class 파일을 고쳐서 디스크에 다시 저장하기 때문이다 원본 클래스 파일은 그대로다. 스프링은 원본을 상속한 클래스를 실행 중에 생성해 빈 정의의 클래스를 바꾸고, 그 자식이 @Bean 메서드를 오버라이딩한다. 부모 코드 안의 자기 호출도 invokevirtual이므로 자식의 메서드로 들어가고, 인터셉터가 컨테이너의 호출이 아니라고 판단해 getBean으로 돌린다. 컴파일러와 JVM은 이런 일을 하지 않는다. @Configuration을 붙이지 않은 클래스에 @Bean 메서드들을 두고 컨테이너에 등록했다. loanService()가 본문에서 bookRepository()를 직접 호출한다면 어떤 일이 일어나는가? 시작할 때 "@Configuration이 필요하다"는 예외가 난다 @Bean 메서드가 빈으로 등록되지 않는다 풀 모드와 똑같이 컨테이너의 bookRepository 빈이 주입된다 오류 없이 시작되지만, LoanService가 가진 리포지토리는 컨테이너가 관리하는 bookRepository 빈과 다른 객체다 라이트 모드에서는 자식 클래스가 만들어지지 않으므로 @Bean 메서드끼리의 직접 호출은 평범한 자바 호출이고 매번 새 객체를 만든다. 빈 등록 자체는 정상이고 경고도 없어서 알아차리기 어렵다. 라이트 모드에서는 의존 빈을 메서드 매개변수로 받아야 한다. private static final Registry INSTANCE = new Registry();로 만든 싱글톤이 synchronized 없이도 여러 스레드에서 한 번만 생성되는 근거는? private 생성자는 JVM이 한 번만 호출되도록 제한하기 때문이다 정적 필드 초기화 코드는 클래스 초기화 때 실행되고, JVM은 클래스 초기화를 클래스별 초기화 락으로 보호해 한 스레드만 실행하게 하기 때문이다 static final 필드는 컴파일 시점에 객체가 만들어져 클래스 파일에 저장되기 때문이다 getInstance()가 정적 메서드라서 한 번에 한 스레드만 실행할 수 있기 때문이다 필드 초기화식은 컴파일러가 클래스 초기화 메서드에 넣는다. JLS §12.4.2는 클래스마다 고유한 초기화 락을 두고, 이미 다른 스레드가 초기화 중이면 끝날 때까지 기다리도록 정한다. private은 접근 검사일 뿐 호출 횟수를 제한하지 않고(리플렉션으로 다시 호출할 수 있다), 객체는 실행 중에 힙에 만들어지며, 정적 메서드는 여러 스레드가 동시에 실행할 수 있다.
    싱글톤 패턴(singleton pattern)
    클래스가 자기 인스턴스를 하나만 만들도록 스스로 제한하는 설계 패턴. private 생성자와 정적 필드, 정적 접근 메서드로 구현한다.
    클래스 초기화(class initialization)
    정적 필드의 초기화식과 static 블록을 실행하는 단계. 클래스가 처음 쓰일 때 한 번, 클래스별 초기화 락의 보호 아래 실행된다.
    싱글톤 레지스트리(singleton registry)
    객체를 이름으로 등록해 두고 이름마다 하나의 인스턴스만 유지하는 저장소. 스프링에서는 DefaultSingletonBeanRegistry가 이 역할을 한다.
    싱글톤 스코프(singleton scope)
    스프링 빈의 기본 스코프. 컨테이너 하나 안에서 빈 정의 하나에 인스턴스 하나가 만들어져 공유된다.
    사전 인스턴스화(pre-instantiation)
    ApplicationContext가 시작하는 동안 지연 초기화가 아닌 싱글톤 빈을 모두 만들어 두는 동작.
    무상태(stateless)
    특정 호출이나 특정 클라이언트에 속한 값을 객체의 필드에 남기지 않는 설계. 요청별 값은 지역 변수·매개변수·반환값으로 다룬다.
    CGLIB
    실행 중에 바이트코드를 만들어 기존 클래스의 자식 클래스를 정의하는 라이브러리. 스프링은 org.springframework.cglib 패키지로 spring-core에 포함한다.
    풀 모드와 라이트 모드(full / lite mode)
    @Bean 메서드가 처리되는 두 방식. 풀 모드는 설정 클래스의 CGLIB 자식이 @Bean 메서드 호출을 컨테이너로 돌리고, 라이트 모드는 그런 처리 없이 평범한 팩터리 메서드로 다룬다.
    빈 팩터리 후처리기(BeanFactoryPostProcessor)
    빈 정의가 모인 뒤, 빈 객체가 만들어지기 전에 빈 정의를 고칠 수 있는 확장 지점. 설정 클래스의 해석과 자식 클래스 교체가 여기서 일어난다.
    스레드 로컬(ThreadLocal)
    스레드마다 값을 따로 갖는 변수. 스프링은 지금 호출 중인 팩터리 메서드를 여기에 기록해 @Bean 메서드 호출의 출처를 구분한다.
