    만들어진 객체와 쓸 수 있는 객체 사이

    06회에서는 컨테이너가 싱글톤 빈 하나를 만드는 과정을 인스턴스 생성, 주입 지점 수집, 프로퍼티 채우기, 초기화의 네 단계로 나누었고, 마지막 단계는 이 회차로 미뤄 두었다. 이 회차는 그 넷째 단계와, 컨테이너가 닫힐 때 반대편에서 일어나는 일을 다룬다. 두 지점을 묶어 빈의 생명주기(lifecycle)라고 부르고, 그 지점에서 컨테이너가 빈의 메서드를 불러 주는 것을 생명주기 콜백(lifecycle callback)이라고 한다.

    왜 이런 장치가 필요한가. 어떤 객체는 만들어지는 것만으로는 일을 시작할 수 없다. 데이터베이스 커넥션 풀은 첫 요청이 오기 전에 연결을 미리 맺어 두어야 하고, 메시지 수신기는 소켓을 열어야 하며, 파일에 기록하는 객체는 파일을 열어야 한다. 그리고 이런 객체는 끝날 때 할 일이 있다. 연결을 끊고, 버퍼에 남은 데이터를 내보내고, 파일을 닫아야 한다. 준비와 정리를 누가, 정확히 언제 부르는가가 이 회차의 질문이다.

    04회의 도서관 예제를 이어서, 대출과 반납을 한 줄씩 파일에 남기는 대출 기록 저널을 만들어 보자. 기록할 파일의 경로는 수정자(setter)로 받고, 파일을 여는 메서드와 닫는 메서드를 따로 둔다. 먼저 생명주기 콜백 없이 써 본다.

    import java.io.BufferedWriter;
import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

public class ProblemMain {

    static class LoanJournal {
        private Path file;            // 수정자로 받는다
        private BufferedWriter out;

        public LoanJournal() {
            System.out.println("[생성자]   file = " + file);
        }

        public void setFile(Path file) {
            System.out.println("[setFile]  file = " + file);
            this.file = file;
        }

        public void openFile() throws IOException {
            out = Files.newBufferedWriter(file);
            System.out.println("[openFile] " + file + " 열림");
        }

        public void append(String line) throws IOException {
            out.write(line);
            out.newLine();
        }

        public void closeFile() throws IOException {
            out.close();
            System.out.println("[closeFile] 버퍼를 비우고 닫음");
        }
    }

    @Configuration
    static class JournalConfig {
        @Bean
        LoanJournal loanJournal() {
            LoanJournal journal = new LoanJournal();
            journal.setFile(Path.of("loan-journal.txt"));
            return journal;
        }
    }

    public static void main(String[] args) throws IOException {
        var ctx = new AnnotationConfigApplicationContext(JournalConfig.class);
        LoanJournal journal = ctx.getBean(LoanJournal.class);

        journal.openFile();                       // 누군가 불러 줘야 한다
        journal.append("B-1001 loaned to M-17");
        journal.append("B-2040 loaned to M-03");
        journal.append("B-1001 returned");

        System.out.println("파일 크기 = " + Files.size(Path.of("loan-journal.txt")) + "바이트");
    }   // closeFile()을 아무도 부르지 않고 끝난다
}
    [생성자]   file = null
[setFile]  file = loan-journal.txt
[openFile] loan-journal.txt 열림
파일 크기 = 0바이트

    프로그램은 예외 없이 끝났고 종료 코드도 0이다. 그런데 끝난 뒤에 loan-journal.txt를 열어 보면 비어 있다. 세 줄을 기록했는데 한 글자도 남지 않았다. 이 짧은 실행에 이 회차가 풀어야 할 문제 세 가지가 모두 들어 있다.

    • 생성자는 너무 이르다. 생성자가 실행될 때 file은 null이다. 파일을 여는 일을 생성자에 넣을 수 없다.
    • 준비를 부르는 책임이 사용자에게 넘어갔다. main이 openFile()을 직접 불렀다. 저널을 주입받아 쓰는 클래스가 열 개라면 누가 부를지 정해야 하고, 두 번 부르면 파일이 다시 잘린다.
    • 정리를 부르는 사람이 없다. closeFile()이 불리지 않아 기록이 사라졌다. 그리고 이 실수는 예외도 경고도 남기지 않는다.
    이 회차의 실행 결과, 예외 문구, 호출 스택, 바이트코드는 원고를 쓰면서 JDK 21.0.13(Temurin)과 스프링 프레임워크 7.0.10에서 직접 돌려 얻은 것이다. 본문이 근거로 삼는 규칙(콜백의 호출 순서, 소멸 메서드 추론, 원본 객체에서의 초기화, 소멸 순서, 셧다운 훅)은 이 강좌의 기준 버전인 6.2의 레퍼런스 문서·Javadoc·소스에서 같은 내용을 따로 확인했다. 본문에 나오는 스프링 내부 클래스와 메서드 이름은 공개 API가 아니므로 버전에 따라 달라질 수 있다.

    생성자가 너무 이른 이유: new가 하는 일

    첫 번째 문제부터 보자. 설정 클래스의 @Bean 메서드는 객체를 만들고 수정자를 부른 다음 돌려준다. 이 세 줄이 어떤 순서로 실행되는지는 바이트코드에 그대로 적혀 있다. 같은 모양의 메서드를 컴파일해 javap -c로 열어 본 결과다.

    0번의 new가 힙에 객체 자리를 잡고, 4번의 invokespecial이 생성자(<init>)를 실행한다. 생성자가 끝나고 나서야 7번에서 참조가 지역 변수에 저장되고, 그 참조를 써서 18번에서 setFile이 호출된다. 생성자의 본문은 4번 명령 안에서 처음부터 끝까지 실행되므로, 18번에서 들어올 값을 볼 방법이 없다.

    이것은 컴파일러의 선택이 아니라 언어가 정한 순서다. 자바 언어 명세 §12.5는 새 인스턴스를 만들 때 먼저 메모리를 할당하고 모든 인스턴스 변수를 기본값으로 초기화한 다음, 참조를 결과로 돌려주기 직전에 생성자를 처리한다고 적는다. 참조 타입 필드의 기본값은 null이므로 생성자가 본 file은 null이다. 객체 바깥의 코드는 생성자가 끝나야 참조를 손에 넣고, 참조가 있어야 수정자를 부르거나 필드에 값을 쓸 수 있다.

    컨테이너도 이 순서를 벗어날 수 없다. 06회에서 본 것처럼 필드 주입과 수정자 주입은 인스턴스 생성 단계가 끝난 뒤의 프로퍼티 채우기 단계에서 일어난다. 컨테이너가 리플렉션으로 생성자를 호출하든 우리가 @Bean 메서드 안에서 new를 쓰든, 생성자가 실행되는 동안에는 나중에 들어올 값이 아직 없다.

    생성자 주입이면 문제가 없는가

    06회의 결론은 생성자 주입을 기본으로 쓰자는 것이었다. 경로를 생성자 파라미터로 받으면 생성자 안에서 file이 보이므로, 그 자리에서 파일을 열 수도 있다. 그래도 준비 작업을 생성자와 나누는 데에는 이유가 있다.

    첫째, 모든 값이 생성자로 들어오지는 않는다. 선택적인 의존관계를 수정자로 받는 경우, 필드 주입을 쓰는 기존 코드, 그리고 뒤에서 볼 것처럼 컨테이너가 빈에게 알려 주는 정보(빈 이름 같은 것)는 생성자가 끝난 뒤에 들어온다. 초기화 콜백은 이 값들이 전부 들어온 뒤라는 것을 컨테이너가 보장하는, 빈 하나의 생성 과정 안의 지점이다.

    둘째, 생성자와 준비 작업은 성격이 다르다. 생성자가 하는 일은 받은 값을 필드에 넣어 객체를 일관된 상태로 만드는 것이고, 메모리 안에서 끝난다. 파일을 열거나 네트워크 연결을 맺는 일은 프로세스 바깥의 자원을 건드리고, 시간이 걸리며, 실패할 수 있다. 이 일이 생성자에 들어 있으면 단위 테스트에서 객체 하나를 new로 만드는 것만으로 파일이 생기고 연결이 맺어진다. 둘을 나누면 객체를 만드는 일과 자원을 여는 일을 따로 다룰 수 있다.

    셋째, 컨테이너의 일은 생성자가 끝난 뒤에도 남아 있다. 뒤에서 확인하겠지만 빈은 초기화가 끝난 다음에 프록시로 감싸질 수 있고, 그제서야 다른 빈에게 건네질 완성품이 된다. 생성자 안은 그 과정의 가장 앞쪽이다.

    메모리는 GC가 거두지만 파일은 아무도 닫아 주지 않는다

    세 번째 문제, 사라진 세 줄로 가 보자. BufferedWriter는 write로 받은 문자를 곧바로 파일에 보내지 않고 내부의 char 배열에 모아 둔다. JDK 21 소스 기준으로 플랫폼 스레드에서 크기를 지정하지 않고 만든 BufferedWriter의 버퍼는 8,192자다. 60바이트 남짓한 세 줄은 이 배열에만 있었고, 배열이 차거나 flush()·close()가 불려야 운영체제의 write 호출로 넘어간다.

    프로세스가 끝나면 운영체제는 그 프로세스가 열어 둔 파일 디스크립터를 회수한다. 그래서 파일이 열린 채로 남지는 않는다. 그러나 운영체제에 넘어간 적이 없는 데이터는 JVM 힙의 배열에만 있었으므로 프로세스와 함께 사라진다. closeFile()을 부르도록 한 줄만 추가하면 같은 프로그램이 60바이트짜리 파일을 남긴다. 차이는 누군가 닫았느냐 하나뿐이다.

    자바에는 가비지 컬렉터가 있는데 왜 이런 일을 사람이 챙겨야 하는가. 가비지 컬렉터가 관리하는 것은 힙 메모리다. 파일 디스크립터, 소켓, 데이터베이스 연결은 힙 바깥에 있는 자원이고, 객체가 수거될 때 이것들을 정리해 주던 장치인 종료자(finalizer)는 믿을 수 없다. 자바 언어 명세 §12.6은 종료자가 얼마나 빨리 호출될지를 언어가 정하지 않는다고 적고 있고, JDK 21의 Object.finalize에는 @Deprecated(since="9", forRemoval=true)가 붙어 있다.

    싱글톤 빈에는 한 가지 사정이 더 있다. 04회에서 본 것처럼 컨테이너는 싱글톤 객체를 자신의 맵에 넣어 들고 있다. 컨테이너가 살아 있는 한 이 객체들은 계속 도달 가능하므로 수거 대상조차 되지 않는다. 싱글톤 빈의 수명은 가비지 컬렉터가 아니라 컨테이너가 정한다.

    블록 하나 안에서 열고 닫는 자원이라면 try-with-resources가 답이다. 그러나 저널은 한 메서드 안에서 쓰고 버리는 객체가 아니라, 애플리케이션이 떠 있는 내내 여러 빈이 함께 쓰는 객체다. 이 객체의 "블록"은 컨테이너의 수명 전체다. 그렇다면 그 블록의 시작과 끝을 아는 쪽, 곧 컨테이너가 알려 줘야 한다.

    일상에서 가져온 비유가게의 개점 준비와 마감 정리

    새 직원이 출근했다고 해서 바로 손님을 받을 수 있는 것은 아니다. 유니폼과 열쇠를 받고(주입), 계산대를 켜고 시재를 세고 나서야(초기화) 문을 연다. 마감 때는 정산을 하고 계산대를 잠근 뒤(소멸 전 정리) 퇴근한다. 직원은 개점 시각과 폐점 시각을 스스로 정하지 않고, 점장이 "이제 열 준비를 하라", "이제 마감하라"고 알려 준다. 점장이 컨테이너이고 그 두 번의 알림이 콜백이다. 비유가 깨지는 지점도 있다. 가게는 정전이 나도 다음 날 직원이 와서 정리할 수 있지만, 프로세스가 강제로 죽으면 마감 정리를 할 주체 자체가 사라진다. 이 차이는 뒤에서 다시 다룬다.

    정리하면 컨테이너가 빈에게 알려 줘야 하는 시점은 둘이다. 하나는 "필요한 것을 모두 넣어 주었으니 이제 준비하라"이고, 다른 하나는 "곧 닫을 테니 정리하라"이다. 앞의 것을 초기화 콜백(initialization callback), 뒤의 것을 소멸 콜백(destruction callback)이라고 한다. 02회에서 본 제어의 역전이 "누가 객체를 만드는가"에 대한 것이었다면, 생명주기 콜백은 같은 원리를 "누가 언제 부르는가"에 적용한 것이다.

    빈 하나의 수명을 가로 타임라인으로 그리고, 생성자·주입·초기화 콜백·사용·소멸 콜백이 어느 구간에 놓이는지와 그동안 객체의 필드가 어떻게 변하는지를 보여 준다. 가로 방향 타임라인 다이어그램. 왼쪽에서 오른쪽으로 다섯 개의 둥근 사각형 단계가 화살표로 이어진다. 라벨은 차례로 "생성자", "의존관계 주입", "초기화 콜백", "사용", "소멸 콜백". "사용" 단계는 다른 단계보다 세 배쯤 길게 그려 수명의 대부분임을 나타낸다. "초기화 콜백"과 "소멸 콜백" 두 단계는 주황색으로 강조하고 나머지는 회색빛 파랑으로 칠한다. 타임라인 위쪽에는 전체를 덮는 긴 괄호를 그리고 라벨 "컨테이너의 수명"을 붙인다. 타임라인 아래쪽에는 같은 객체 상자를 세 번 그린다. 첫 상자는 "생성자" 아래에 두고 안에 두 칸 "file = null", "out = null"을 적는다. 둘째 상자는 "초기화 콜백" 아래에 두고 두 칸 모두 채워진 원으로 그리며 옆에 작은 파일 아이콘과 라벨 "파일 열림"을 붙인다. 셋째 상자는 "소멸 콜백" 아래에 두고 파일 아이콘에 체크 표시와 라벨 "버퍼 비우고 닫힘"을 붙인다. 흰 배경, 평면 벡터 스타일, 글자는 선명한 고딕체. 초기화 콜백은 주입이 끝난 직후에, 소멸 콜백은 컨테이너가 닫히기 직전에 한 번씩 불린다. 두 콜백 사이가 빈이 실제로 일하는 구간이다.

    스프링은 이 두 콜백을 받는 방법을 세 가지 제공한다. 스프링의 인터페이스를 구현하는 방법, 빈을 등록할 때 메서드 이름을 지정하는 방법, 메서드에 애노테이션을 붙이는 방법이다. 차례로 같은 저널에 적용해 보고, 그다음에 셋이 컨테이너 안에서 어떻게 다른 경로로 호출되는지를 본다.

    인터페이스 InitializingBean, DisposableBean

    첫 번째 방법은 빈 클래스가 스프링이 정한 인터페이스를 구현하는 것이다. InitializingBean에는 afterPropertiesSet() 하나가, DisposableBean에는 destroy() 하나가 선언되어 있다. 이름이 뜻을 말해 준다. 앞의 것은 "프로퍼티가 모두 설정된 뒤"에, 뒤의 것은 빈이 소멸될 때 컨테이너가 부른다.

    import org.springframework.beans.factory.DisposableBean;
import org.springframework.beans.factory.InitializingBean;
// 나머지 import는 앞의 예제와 같다

public class InterfaceMain {

    static class LoanJournal implements InitializingBean, DisposableBean {
        private Path file;
        private BufferedWriter out;

        public LoanJournal() {
            System.out.println("[생성자]   file = " + file);
        }

        public void setFile(Path file) {
            System.out.println("[setFile]  file = " + file);
            this.file = file;
        }

        @Override
        public void afterPropertiesSet() throws Exception {
            out = Files.newBufferedWriter(file);
            System.out.println("[afterPropertiesSet] " + file + " 열림");
        }

        public void append(String line) throws IOException {
            out.write(line);
            out.newLine();
        }

        @Override
        public void destroy() throws Exception {
            out.close();
            System.out.println("[destroy]  버퍼를 비우고 닫음");
        }
    }

    @Configuration
    static class JournalConfig {
        @Bean
        LoanJournal loanJournal() {
            LoanJournal journal = new LoanJournal();
            journal.setFile(Path.of("loan-journal.txt"));
            return journal;
        }
    }

    public static void main(String[] args) throws IOException {
        var ctx = new AnnotationConfigApplicationContext(JournalConfig.class);
        System.out.println("--- 컨테이너 준비 끝 ---");
        LoanJournal journal = ctx.getBean(LoanJournal.class);
        journal.append("B-1001 loaned to M-17");
        journal.append("B-2040 loaned to M-03");
        journal.append("B-1001 returned");
        Path file = Path.of("loan-journal.txt");
        System.out.println("닫기 전 파일 크기 = " + Files.size(file) + "바이트");
        ctx.close();
        System.out.println("닫은 뒤 파일 크기 = " + Files.size(file) + "바이트");
    }
}
    [생성자]   file = null
[setFile]  file = loan-journal.txt
[afterPropertiesSet] loan-journal.txt 열림
--- 컨테이너 준비 끝 ---
닫기 전 파일 크기 = 0바이트
[destroy]  버퍼를 비우고 닫음
닫은 뒤 파일 크기 = 60바이트

    한 줄씩 따라가 보자. 컨테이너가 loanJournal()을 호출하면 생성자와 수정자가 차례로 실행되고 객체가 반환된다. 컨테이너는 돌려받은 객체에 대해 초기화 단계를 수행하고, 그 안에서 afterPropertiesSet()을 부른다. 이 모든 일이 new AnnotationConfigApplicationContext(...) 한 줄 안에서 끝나므로 "컨테이너 준비 끝"이 찍힐 때 파일은 이미 열려 있다. main은 더 이상 openFile()을 부를 필요가 없다.

    ctx.close()가 호출되면 컨테이너는 자신이 만든 싱글톤들을 정리하면서 destroy()를 부른다. 그 직전에는 0바이트이던 파일이 직후에는 60바이트가 되었다. 준비와 정리를 부르는 책임이 사용하는 쪽에서 컨테이너로 옮겨 간 것이다. 다만 close() 자체는 여전히 main이 불렀다는 점을 기억해 두자. 이 호출이 없으면 어떻게 되는지는 뒤에서 따로 다룬다.

    컨테이너는 이 빈이 콜백을 원한다는 것을 어떻게 아는가

    인터페이스 방식에서는 답이 단순하다. 타입을 본다. 초기화 단계에서 컨테이너는 bean instanceof InitializingBean을 검사하고, 참이면 그 타입으로 바꿔 afterPropertiesSet()을 직접 호출한다. 리플렉션으로 메서드를 찾지 않는, 평범한 인터페이스 메서드 호출이다. 소멸 쪽도 같아서, 빈이 DisposableBean이면 소멸 대상으로 등록해 두었다가 닫을 때 destroy()를 호출한다.

    자바 기본편에서 다룬 다형성이 그대로 쓰인 것이다. 컨테이너는 LoanJournal이라는 클래스를 전혀 모르고, 그 객체가 InitializingBean이라는 역할을 구현했다는 것만 안다. 클래스 파일에 기록된 implements 절이 "나는 초기화 콜백을 받겠다"는 표시 역할을 한다.

    이 방식이 치르는 값

    단순한 만큼 제약도 분명하다. 첫째, LoanJournal이 org.springframework.beans.factory 패키지의 타입에 의존하게 된다. 파일에 줄을 쓰는 것이 전부인 클래스가 스프링 없이는 컴파일되지 않는다. 둘째, 메서드 이름을 바꿀 수 없다. 이 클래스에서 afterPropertiesSet이 뜻하는 것은 "파일을 연다"인데, 이름은 그것을 말해 주지 않는다. 셋째, 소스를 고칠 수 없는 클래스에는 적용할 수 없다. 외부 라이브러리가 제공하는 커넥션 풀에 implements InitializingBean을 덧붙일 방법은 없다.

    스프링 레퍼런스 문서도 같은 판단을 적어 두었다. InitializingBean과 DisposableBean은 코드를 불필요하게 스프링에 묶으므로 쓰지 말 것을 권하고, 대신 @PostConstruct·@PreDestroy 애노테이션이나 빈 정의에 지정하는 일반 메서드를 쓰라고 안내한다. 그렇다고 이 인터페이스들이 사라진 것은 아니다. 스프링 자신의 내부 클래스들이 널리 쓰고 있고, 뒤에서 볼 호출 순서에도 한 자리를 차지한다.

    빈 등록 초기화, 소멸 메서드

    두 번째 방법은 클래스를 건드리지 않고, 빈을 등록하는 쪽에서 "이 빈의 초기화 메서드는 이것, 소멸 메서드는 이것"이라고 이름을 알려 주는 것이다. 자바 설정에서는 @Bean의 initMethod와 destroyMethod 속성을 쓴다.

    public class BeanMethodMain {

    // 스프링을 전혀 모르는 클래스
    static class LoanJournal {
        private Path file;
        private BufferedWriter out;

        public void setFile(Path file) { this.file = file; }

        public void openFile() throws IOException {
            out = Files.newBufferedWriter(file);
            System.out.println("[openFile]  " + file + " 열림");
        }

        public void append(String line) throws IOException {
            out.write(line);
            out.newLine();
        }

        public void closeFile() throws IOException {
            out.close();
            System.out.println("[closeFile] 버퍼를 비우고 닫음");
        }
    }

    @Configuration
    static class JournalConfig {
        @Bean(initMethod = "openFile", destroyMethod = "closeFile")
        LoanJournal loanJournal() {
            LoanJournal journal = new LoanJournal();
            journal.setFile(Path.of("loan-journal.txt"));
            return journal;
        }
    }

    public static void main(String[] args) throws IOException {
        var ctx = new AnnotationConfigApplicationContext(JournalConfig.class);
        var definition = ctx.getBeanFactory().getBeanDefinition("loanJournal");
        System.out.println("initMethodName    = " + definition.getInitMethodName());
        System.out.println("destroyMethodName = " + definition.getDestroyMethodName());
        ctx.getBean(LoanJournal.class).append("B-1001 loaned to M-17");
        ctx.close();
        System.out.println("닫은 뒤 파일 크기 = " + Files.size(Path.of("loan-journal.txt")) + "바이트");
    }
}
    [openFile]  loan-journal.txt 열림
initMethodName    = openFile
destroyMethodName = closeFile
[closeFile] 버퍼를 비우고 닫음
닫은 뒤 파일 크기 = 22바이트

    LoanJournal의 import 문에서 스프링이 사라졌다. 이 클래스는 스프링이 없는 프로젝트에서도 그대로 쓸 수 있고, 메서드 이름도 하는 일을 그대로 말한다. 콜백에 대한 정보는 클래스가 아니라 설정에 있다.

    그 정보가 저장되는 곳은 03회에서 본 BeanDefinition이다. 출력의 둘째, 셋째 줄이 보여 주듯 @Bean의 두 속성은 빈 정의의 initMethodName과 destroyMethodName으로 옮겨진다. 저장된 것은 메서드가 아니라 문자열이다. 컨테이너는 초기화 단계에서 이 문자열을 꺼내 빈의 클래스에서 같은 이름의 메서드를 리플렉션으로 찾고, Method.invoke로 호출한다.

    이름이 문자열이라는 점에서 약점이 하나 나온다. 오타를 컴파일러가 잡아 주지 못한다. 다행히 컨테이너가 시작할 때 잡힌다. initMethod = "opneFile"이라고 잘못 쓰고 실행하면 다음 예외로 컨테이너 생성이 실패한다.

    BeanCreationException: Error creating bean with name 'journal' defined in MsgMain$BadInit:

    눈여겨볼 것은 소멸 메서드의 오타도 시작할 때 드러난다는 점이다. 컨테이너는 빈을 다 만든 직후에 소멸 때 부를 메서드를 미리 찾아 등록해 두기 때문이다. 종료 시점에 가서야 "그런 메서드가 없다"는 것을 알게 되는 일은 없다.

    이 방식의 가장 큰 쓸모는 소스를 고칠 수 없는 클래스에 있다. 외부 라이브러리의 클래스는 스프링 인터페이스를 구현하고 있지도, 스프링이 읽는 애노테이션을 달고 있지도 않다. 그래도 "시작할 때 start()를, 끝날 때 stop()을 불러야 한다"는 규칙은 문서에 적혀 있다. @Bean 메서드에 그 이름을 적어 주는 것으로 그 클래스를 컨테이너의 생명주기에 편입시킬 수 있다.

    @Bean의 Javadoc은 initMethod가 흔히 쓰이지는 않는다고 적고 있다. @Bean 메서드의 본문이 자바 코드이므로 객체를 돌려주기 전에 초기화 메서드를 직접 호출할 수 있기 때문이다. 반면 소멸 시점에는 우리가 끼어들 코드가 없으므로 destroyMethod는 대신할 방법이 없다.

    destroyMethod를 쓰지 않아도 close()가 불린다: 소멸 메서드 추론

    destroyMethod에는 독특한 기본값이 있다. 빈 문자열이 아니라 "(inferred)"다. 추론하라는 뜻이다. @Bean의 Javadoc에 따르면 컨테이너는 @Bean 메서드가 돌려준 객체에서 close 또는 shutdown이라는 이름의, public이고 인자가 없는 메서드를 찾아 소멸 메서드로 등록한다. 괄호가 들어간 이상한 값을 쓴 것은 실제 메서드 이름과 절대 겹치지 않게 하기 위해서다. 여러 경우를 한꺼번에 실험해 보자.

    public class InferMain {

    static class Pool {                       // 외부 라이브러리의 클래스라고 가정
        private final String name;
        Pool(String name) { this.name = name; }
        public void close()    { System.out.println(name + ".close()"); }
    }

    static class Scheduler {
        public void shutdown() { System.out.println("scheduler.shutdown()"); }
    }

    static class Both {
        public void close()    { System.out.println("both.close()"); }
        public void shutdown() { System.out.println("both.shutdown()"); }
    }

    static class Hidden {
        void close() { System.out.println("hidden.close()"); }   // public이 아니다
    }

    @Component
    static class ScannedPlain {               // @Bean이 아니라 클래스로 등록
        public void close() { System.out.println("scannedPlain.close()"); }
    }

    @Component
    static class ScannedCloseable implements AutoCloseable {
        @Override public void close() { System.out.println("scannedCloseable.close()"); }
    }

    @Configuration
    static class Config {
        @Bean Pool inferredPool()                      { return new Pool("inferredPool"); }
        @Bean(destroyMethod = "") Pool keptOpenPool()  { return new Pool("keptOpenPool"); }
        @Bean Scheduler scheduler()                    { return new Scheduler(); }
        @Bean Both both()                              { return new Both(); }
        @Bean Hidden hidden()                          { return new Hidden(); }
    }

    public static void main(String[] args) {
        var ctx = new AnnotationConfigApplicationContext(
                Config.class, ScannedPlain.class, ScannedCloseable.class);
        for (String name : new String[] {"inferredPool", "keptOpenPool", "scheduler", "hidden",
                "inferMain.ScannedPlain", "inferMain.ScannedCloseable"}) {
            System.out.printf("%-28s destroyMethodName = %s%n", name,
                    ctx.getBeanFactory().getBeanDefinition(name).getDestroyMethodName());
        }
        System.out.println("--- close ---");
        ctx.close();
    }
}

    빈등록 방법닫을 때 일어난 일이유
    inferredPool@Beanclose() 호출기본값 (inferred)가 public close()를 찾았다
    keptOpenPool@Bean(destroyMethod = "")아무 일도 없음빈 문자열로 추론을 껐다
    scheduler@Beanshutdown() 호출close가 없으면 shutdown을 찾는다
    both@Beanclose()만 호출둘 다 있으면 close가 먼저 선택된다
    hidden@Bean아무 일도 없음추론은 public 메서드만 본다
    ScannedPlain클래스 등록아무 일도 없음빈 정의의 소멸 메서드 이름이 null이라 추론하지 않는다
    ScannedCloseable클래스 등록close() 호출AutoCloseable을 구현한 빈은 등록 방법과 상관없이 닫는다

    이 기본값이 있는 이유는 실용적이다. 커넥션 풀이나 스레드 풀 같은 외부 라이브러리의 자원 객체는 대개 close나 shutdown이라는 이름의 정리 메서드를 갖고 있다. @Bean의 Javadoc이 드는 예가 바로 그것으로, Apache Commons DBCP의 BasicDataSource를 돌려주는 @Bean 메서드가 있으면 컨테이너가 그 객체의 close()를 알아채 소멸 메서드로 등록한다고 적는다. 개발자가 destroyMethod를 깜빡해도 자원이 새지 않게 하려는 장치다.

    반대 방향의 실수도 여기서 나온다. 컨테이너가 닫으면 안 되는 객체, 예를 들어 다른 모듈이 소유하고 수명을 관리하는 공유 자원을 @Bean으로 등록하면, 그 객체에 public close()가 있다는 이유만으로 컨테이너가 닫힐 때 함께 닫힌다. 이럴 때는 keptOpenPool처럼 destroyMethod = ""로 추론을 끈다. 추론은 빈 인스턴스 자체를 리플렉션으로 살펴서 이루어지므로, @Bean 메서드의 반환 타입을 인터페이스로 선언해 close를 가려도 피할 수 없다.

    애노테이션 @PostConstruct, @PreDestroy

    세 번째 방법은 메서드에 애노테이션을 붙이는 것이다. 초기화 메서드에는 @PostConstruct를, 소멸 메서드에는 @PreDestroy를 붙인다. 이름이 시점을 말한다. 생성(과 주입)이 끝난 뒤, 그리고 소멸되기 전이다.

    import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
// 나머지 import는 앞의 예제와 같다

public class AnnotationMain {

    static class LoanJournal {
        private Path file;
        private BufferedWriter out;

        public void setFile(Path file) { this.file = file; }

        @PostConstruct
        void openFile() throws IOException {
            out = Files.newBufferedWriter(file);
            System.out.println("[@PostConstruct] " + file + " 열림");
        }

        public void append(String line) throws IOException {
            out.write(line);
            out.newLine();
        }

        @PreDestroy
        void closeFile() throws IOException {
            out.close();
            System.out.println("[@PreDestroy]    버퍼를 비우고 닫음");
        }
    }

    @Configuration
    static class JournalConfig {
        @Bean
        LoanJournal loanJournal() {
            LoanJournal journal = new LoanJournal();
            journal.setFile(Path.of("loan-journal.txt"));
            return journal;
        }
    }

    public static void main(String[] args) throws IOException {
        var ctx = new AnnotationConfigApplicationContext(JournalConfig.class);
        ctx.getBean(LoanJournal.class).append("B-1001 loaned to M-17");
        ctx.close();
        System.out.println("닫은 뒤 파일 크기 = " + Files.size(Path.of("loan-journal.txt")) + "바이트");
    }
}

    설정 클래스에는 아무 속성도 적지 않았고, LoanJournal은 스프링의 타입을 하나도 import하지 않는다. 메서드 이름은 자유롭게 지었고, 두 메서드 모두 public이 아니다. 인터페이스 방식의 세 가지 제약 가운데 둘이 사라졌다.

    이 애노테이션은 스프링의 것이 아니다

    import 문을 보면 패키지가 jakarta.annotation이다. 두 애노테이션은 스프링이 아니라 자바 진영의 공통 애노테이션 규격(JSR-250, 지금의 Jakarta Annotations)이 정의한 것이다. 스프링 레퍼런스에 따르면 이 타입들은 JDK 6부터 8까지 표준 라이브러리의 javax.annotation 패키지에 들어 있었고, JDK 9에서 핵심 모듈과 분리된 뒤 JDK 11에서 제거되었다. Jakarta EE 9부터는 패키지 이름이 jakarta.annotation으로 바뀌었다. 그래서 지금은 JDK만으로는 이 애노테이션을 쓸 수 없고, jakarta.annotation-api 아티팩트가 클래스패스에 있어야 한다. 스프링 프레임워크 6과 스프링 부트 3이 jakarta.* 네임스페이스를 쓰므로 이 강좌의 기준 버전에서는 jakarta.annotation을 import한다.

    표준 규격이라는 것은 이 애노테이션을 붙인 클래스가 스프링이 아닌 다른 DI 컨테이너에서도 같은 뜻으로 읽힌다는 의미다. Jakarta Annotations의 @PostConstruct Javadoc은 이 메서드가 의존관계 주입이 끝난 뒤, 클래스가 서비스에 투입되기 전에 호출되어야 한다고 정의한다. 스프링은 그 규격을 구현한 여러 컨테이너 가운데 하나다.

    누가 이 애노테이션을 읽는가

    애노테이션은 그 자체로는 아무 일도 하지 않는다. 클래스 파일에 기록된 표시일 뿐이다. @PostConstruct와 @PreDestroy는 @Retention(RUNTIME)으로 선언되어 있어 실행 중에 리플렉션으로 읽을 수 있고, 스프링에서 그것을 읽는 객체는 CommonAnnotationBeanPostProcessor라는 빈 후처리기다. 06회에서 @Autowired를 읽는 후처리기가 컨테이너에 빈으로 등록되어 있던 것과 같은 구조다. 애노테이션 기반 컨텍스트에서 org.springframework.context.annotation.internalCommonAnnotationProcessor라는 이름으로 빈을 꺼내면 이 클래스의 인스턴스가 나온다.

    이 후처리기는 빈의 클래스를 훑어 두 애노테이션이 붙은 메서드의 목록을 만들어 캐시에 넣고, 초기화 단계에서 @PostConstruct 메서드들을, 소멸 단계에서 @PreDestroy 메서드들을 리플렉션으로 호출한다. 호출 전에 접근 제한을 풀기 때문에 private 메서드여도 동작한다. 대신 인자가 있으면 안 된다. 인자가 있는 메서드에 붙이면 컨테이너가 시작하다가 다음 원인으로 실패한다.

    java.lang.IllegalStateException: Lifecycle annotation requires a no-arg method: void MiscMain$Bad.init(java.lang.String)

    상속 관계에서는 순서가 정해져 있다. 부모 클래스와 자식 클래스가 각각 @PostConstruct 메서드를 가지면 부모의 것이 먼저 실행되고, @PreDestroy는 반대로 자식의 것이 먼저 실행된다. 생성자가 부모부터 실행되는 것과 같은 방향이고, 정리는 그 역순이다. 후처리기가 클래스 계층을 자식에서 부모 쪽으로 올라가며 초기화 메서드는 목록의 앞에, 소멸 메서드는 목록의 뒤에 붙이기 때문에 이런 순서가 나온다.

    이 방식의 한계는 인터페이스 방식과 하나를 공유한다. 애노테이션은 소스에 붙여야 하므로 고칠 수 없는 외부 라이브러리의 클래스에는 쓸 수 없다. 그런 클래스에는 앞 절의 @Bean(initMethod, destroyMethod)나 소멸 메서드 추론을 쓴다.

    세 방식이 한 빈에 함께 있을 때: 초기화 단계의 안쪽

    세 방식은 서로를 배제하지 않는다. 한 클래스가 InitializingBean을 구현하면서 @PostConstruct 메서드를 갖고, 설정에서 initMethod까지 지정할 수 있다. 일부러 이렇게 쓸 일은 드물지만, 부모 클래스는 인터페이스 방식을 쓰고 자식 클래스는 애노테이션을 쓰는 식으로 섞이는 일은 생긴다. 그때 어느 것이 먼저 불리는가. 순서를 외우는 대신 각 콜백이 누구에게 불리는지를 호출 스택으로 찍어 보자.

        @Override public void setBeanName(String n) { trace("setBeanName(" + n + ")"); }
        @PostConstruct void postConstruct()        { trace("@PostConstruct"); }
        @Override public void afterPropertiesSet() { trace("afterPropertiesSet()"); }
        void customInit()                          { trace("initMethod"); }
        @PreDestroy void preDestroy()              { trace("@PreDestroy"); }
        @Override public void destroy()            { trace("destroy()"); }
        void customDestroy()                       { trace("destroyMethod"); }
    }

    static class Config {

            return journal;
        }
    }

    public static void main(String[] args) {

    순서는 구조에서 나온다

    실행 결과의 순서가 이 그림과 그대로 겹친다. setBeanName은 ①에서, @PostConstruct는 ②에서, afterPropertiesSet()과 initMethod는 ③에서 불렸다. 그러니 "애노테이션, 인터페이스, 지정한 메서드" 순서는 따로 정한 규칙이 아니라 구현 방식의 결과다.

    @PostConstruct가 가장 먼저인 이유는 이 애노테이션을 처리하는 것이 빈 후처리기이기 때문이다. 빈 후처리기(BeanPostProcessor)는 컨테이너가 만든 빈을 초기화 전과 후에 한 번씩 건네받는 확장 지점이고, CommonAnnotationBeanPostProcessor는 그 가운데 "초기화 전" 훅 안에서 @PostConstruct 메서드를 호출한다. "초기화 전" 훅은 이름 그대로 초기화 메서드들(③)보다 앞에 있으므로, 컨테이너의 눈으로 보면 @PostConstruct는 초기화 메서드가 아니라 초기화 직전에 후처리기가 하는 일이다.

    afterPropertiesSet()이 initMethod보다 먼저인 이유는 ③의 본문에 있다. invokeInitMethods는 먼저 타입을 검사해 인터페이스 메서드를 직접 호출하고, 그다음에 빈 정의에서 메서드 이름을 꺼내 리플렉션으로 호출한다. 스택에서도 차이가 보인다. afterPropertiesSet()은 invokeInitMethods가 곧바로 불렀지만, initMethod는 invokeCustomInitMethod라는 리플렉션 호출 단계를 한 번 더 거쳤다.

    스프링 문서도 같은 순서를 적는다. 레퍼런스는 한 빈에 여러 생명주기 방식이 서로 다른 메서드 이름으로 설정되어 있으면 @PostConstruct 메서드, afterPropertiesSet(), 지정한 초기화 메서드 순으로 불린다고 하고, BeanFactory의 Javadoc은 Aware 인터페이스들에서 시작해 후처리기의 초기화 후 훅으로 끝나는 전체 목록을 "표준 순서"로 싣고 있다. 문서가 규칙을 말하고 소스가 그 규칙이 생기는 이유를 보여 준다.

    ①의 정체: 컨테이너가 빈에게 알려 주는 것들

    예제의 BeanNameAware는 앞에서 예고한 "생성자가 끝난 뒤에 들어오는 값"의 한 예다. 빈은 자신이 어떤 이름으로 등록되었는지 스스로 알 수 없으므로, 알고 싶다면 이 인터페이스를 구현해 컨테이너에게서 통지받는다. 이런 인터페이스들을 묶어 Aware 인터페이스라고 부르고, 이름·클래스 로더·빈 팩토리를 알려 주는 세 가지는 ①에서 호출된다. ApplicationContextAware처럼 애플리케이션 컨텍스트가 알려 주는 것들도 초기화 콜백보다 앞에서 전달된다. BeanFactory의 Javadoc이 적은 표준 순서에서 이들은 모두 후처리기의 초기화 전 훅보다 앞에 놓여 있고, 실제로 ApplicationContextAware를 구현한 빈의 @PostConstruct 메서드에서 통지받은 컨텍스트를 확인해 보면 이미 들어와 있다.

    그래서 초기화 콜백은 "이 빈이 받을 수 있는 것을 전부 받은 뒤"라고 말할 수 있다. 생성자 파라미터, 필드와 수정자로 주입되는 값, 컨테이너가 통지하는 값이 모두 채워진 다음에야 ②와 ③이 시작된다.

    같은 메서드를 두 방식에 걸어 두면

    한 메서드에 @PostConstruct를 붙이고, 같은 메서드 이름을 @Bean(initMethod = "...")에도 적으면 두 번 불릴 것처럼 보인다. 실제로 open()에 @PostConstruct를 붙인 클래스를 @Bean(initMethod = "open")으로 등록해 실행하면 open()은 한 번만 실행된다. 레퍼런스도 같은 메서드 이름이 둘 이상의 방식에 설정되어 있으면 그 메서드는 한 번 실행된다고 적는다.

    이것도 구조로 설명된다. 후처리기는 @PostConstruct 메서드를 찾아낼 때 그 이름을 빈 정의에 "외부에서 관리하는 초기화 메서드"로 기록해 둔다. ③의 invokeInitMethods는 이름으로 메서드를 호출하기 전에 그 기록을 확인하고, 이미 후처리기가 맡은 메서드면 건너뛴다. InitializingBean을 구현한 빈에 initMethod = "afterPropertiesSet"을 적은 경우도 같은 자리에서 걸러진다. 초기화 콜백은 빈 인스턴스 하나에 대해 메서드마다 한 번씩만 실행된다.

    세 가지 초기화 콜백이 initializeBean이라는 한 메서드의 서로 다른 단계에서 불린다는 것, 그리고 그 뒤에 프록시가 씌워진다는 것을 한 장으로 보여 준다. 세로 방향 호출 구조 다이어그램. 왼쪽에 큰 세로 사각형을 그리고 위에 라벨 "initializeBean"을 붙인다. 사각형 안에는 위에서 아래로 네 개의 가로 칸이 쌓여 있고 각 칸에 번호와 라벨을 적는다: "① Aware 통지", "② 후처리기: 초기화 전", "③ 초기화 메서드", "④ 후처리기: 초기화 후". 오른쪽에는 빈 객체를 나타내는 둥근 사각형을 그리고 라벨 "원본 빈 객체"를 붙인다. ②번 칸에서 오른쪽 객체로 주황색 화살표를 그리고 화살표 위에 "@PostConstruct"라고 적는다. ③번 칸에서는 화살표 두 개가 위아래로 나란히 객체로 향한다. 위쪽 화살표에는 "afterPropertiesSet()", 아래쪽 화살표에는 "initMethod (리플렉션)"이라고 적는다. ④번 칸에서 나온 화살표는 객체를 감싸는 점선 테두리로 이어지고, 점선 테두리에 라벨 "프록시"를 붙인다. 세 개의 콜백 화살표 옆에는 작은 원 안에 1, 2, 3 숫자를 적어 호출 순서를 표시한다. 흰 배경, 평면 벡터 스타일, 파랑과 주황 두 가지 색, 선명한 고딕체 글자. 세 방식의 호출 순서는 따로 정한 규칙이 아니라 initializeBean의 네 단계 가운데 어디에 걸려 있느냐의 결과다. 프록시는 그 모든 콜백이 끝난 뒤에 씌워진다.

    초기화 콜백은 프록시가 씌워지기 전의 원본에서 실행된다

    그림의 ④가 남았다. 빈 후처리기의 "초기화 후" 훅은 건네받은 빈을 그대로 돌려줄 수도 있고 다른 객체로 바꿔 돌려줄 수도 있다. 컨테이너는 돌려받은 객체를 싱글톤으로 등록하고 다른 빈에게 주입한다. 스프링이 빈을 프록시(proxy)로 감싸는 자리가 여기다. 프록시는 원본과 같은 타입으로 보이면서 메서드 호출을 가로채 앞뒤에 다른 일을 끼워 넣는 대리 객체다. 프록시라는 말은 04회에서 @Configuration 클래스를 다룰 때 처음 나왔는데, 여기서 말하는 것은 일반 빈을 감싸는 프록시다.

    그렇다면 초기화 콜백은 프록시가 생기기 전에 실행된다는 말이 된다. 직접 확인해 보자. JDK의 java.lang.reflect.Proxy로 인터페이스의 대리 객체를 만들어 돌려주는 빈 후처리기를 하나 등록한다.

    import java.lang.reflect.Proxy;
import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.beans.factory.config.BeanPostProcessor;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

public class ProxyMain {

    interface Journal {
        void append(String line);
    }

    static class FileJournal implements Journal {
        @PostConstruct
        void open() { System.out.println("open()   this = " + getClass().getSimpleName()); }

        @Override
        public void append(String line) { System.out.println("append() this = " + getClass().getSimpleName()); }

        @PreDestroy
        void close() { System.out.println("close()  this = " + getClass().getSimpleName()); }
    }

    static class LoggingWrapper implements BeanPostProcessor {
        @Override
        public Object postProcessBeforeInitialization(Object bean, String beanName) {
            if (bean instanceof Journal) {
                System.out.println("[후처리기] 초기화 전: " + bean.getClass().getSimpleName());
            }
            return bean;
        }

        @Override
        public Object postProcessAfterInitialization(Object bean, String beanName) {
            if (!(bean instanceof Journal target)) {
                return bean;
            }
            System.out.println("[후처리기] 초기화 후: 프록시로 감싼다");
            return Proxy.newProxyInstance(Journal.class.getClassLoader(), new Class[] {Journal.class},
                    (proxy, method, methodArgs) -> {
                        System.out.println("[프록시]   " + method.getName() + " 호출을 가로챔");
                        return method.invoke(target, methodArgs);
                    });
        }
    }

    @Configuration
    static class Config {
        @Bean static LoggingWrapper loggingWrapper() { return new LoggingWrapper(); }
        @Bean Journal journal() { return new FileJournal(); }
    }

    public static void main(String[] args) {
        var ctx = new AnnotationConfigApplicationContext(Config.class);
        Journal journal = ctx.getBean(Journal.class);
        System.out.println("getBean 결과가 FileJournal인가 = " + (journal instanceof FileJournal));
        System.out.println("프록시 클래스인가 = " + Proxy.isProxyClass(journal.getClass()));
        journal.append("B-1001 loaned to M-17");
        ctx.close();
    }
}
    [후처리기] 초기화 전: FileJournal
open()   this = FileJournal
[후처리기] 초기화 후: 프록시로 감싼다
getBean 결과가 FileJournal인가 = false
프록시 클래스인가 = true
[프록시]   append 호출을 가로챔
append() this = FileJournal
close()  this = FileJournal

    둘째 줄과 셋째 줄의 순서가 핵심이다. open()이 실행된 뒤에야 후처리기가 프록시를 만들었다. 컨테이너에서 꺼낸 journal은 FileJournal이 아니라 프록시이고, 그 프록시를 통해 부른 append는 "[프록시] 가로챔" 줄을 남긴 뒤 원본으로 넘어갔다. 반면 open() 앞에는 그런 줄이 없다. 초기화 콜백은 프록시를 거치지 않고 원본 객체의 메서드로 직접 호출되었다.

    마지막 줄도 같은 이야기를 한다. close() 앞에도 "[프록시]" 줄이 없다. 컨테이너는 초기화가 끝난 뒤 소멸 대상을 등록할 때 프록시가 아니라 원본 객체를 넘긴다. 그래서 소멸 콜백도 원본에서 직접 실행된다.

    스프링 레퍼런스는 이 동작을 보장으로 적어 둔다. 초기화 콜백은 빈이 의존관계를 모두 공급받은 직후에 호출되며, 따라서 원본 빈 참조(raw bean reference)에 대해 호출되고 AOP 인터셉터 같은 것은 아직 적용되지 않은 상태라는 것이다. 순서를 뒤집어 프록시를 먼저 만들 수 없는 이유도 여기서 보인다. 프록시는 완성된 대상 객체를 감싸는 것인데, 초기화가 끝나지 않은 객체는 아직 완성품이 아니다.

    여기서 실무적인 결론이 하나 나온다. 프록시가 메서드 호출을 가로채서 제공하는 기능은 초기화 콜백 자체에는 걸리지 않는다. 스프링의 선언적 트랜잭션이 프록시로 구현된 대표적인 기능이고, 스프링 DB 1편과 스프링 핵심 원리 고급편에서 다룬다. 지금은 "초기화 콜백 안에서는 이 객체가 아직 날것"이라는 사실만 가져가면 된다.

    초기화 콜백이 보는 세계: 준비된 것과 아직 아닌 것

    초기화 콜백이 불릴 때 무엇이 준비되어 있는지를 정확히 해 두자. "컨테이너가 다 뜬 다음"이라고 뭉뚱그려 기억하면 틀린다.

    준비된 것: 이 빈과 이 빈이 주입받은 빈

    이 빈이 주입받은 다른 빈은 이미 자신의 초기화 콜백까지 마친 상태다. 컨테이너가 의존관계를 채우려고 다른 빈을 요청하면, 그 빈의 생성 과정(생성, 주입, 초기화)이 통째로 끝난 뒤에 완성된 객체가 돌아오기 때문이다. 그래서 초기화 콜백 안에서 주입받은 빈의 메서드를 호출해도 된다. 뒤에 나올 소멸 순서 예제에서 서비스의 초기화 콜백이 저널에 한 줄을 기록하는데, 그 시점에 저널은 이미 열려 있다. 예외는 06회에서 본 순환 참조다. 필드나 수정자로 서로를 주입받는 두 빈은 한쪽이 아직 초기화되지 않은 상대의 참조를 받게 된다.

    아직 아닌 것: 컨테이너의 나머지

    이 빈과 상관없는 다른 빈들은 아직 만들어지지도 않았을 수 있다. 컨테이너는 싱글톤을 하나씩 차례로 만들고, 한 빈의 초기화 콜백은 그 빈의 차례에 실행된다. 다음 예제의 두 빈은 서로 의존하지 않는다.

    import org.springframework.beans.factory.SmartInitializingSingleton;
// 나머지 import는 앞의 예제와 같다

public class ReadyMain {

    static class Warmup implements SmartInitializingSingleton {
        Warmup() { System.out.println("warmup   생성자"); }

        @PostConstruct
        void init() { System.out.println("warmup   @PostConstruct"); }

        @Override
        public void afterSingletonsInstantiated() {
            System.out.println("warmup   afterSingletonsInstantiated()");
        }
    }

    static class Catalog {
        Catalog() { System.out.println("catalog  생성자"); }

        @PostConstruct
        void init() { System.out.println("catalog  @PostConstruct"); }
    }

    @Configuration
    static class Config {
        @Bean Warmup warmup()   { return new Warmup(); }
        @Bean Catalog catalog() { return new Catalog(); }
    }

    public static void main(String[] args) {
        var ctx = new AnnotationConfigApplicationContext(Config.class);
        System.out.println("--- 컨테이너 준비 끝 ---");
        ctx.close();
    }
}
    warmup   생성자
warmup   @PostConstruct
catalog  생성자
catalog  @PostConstruct
warmup   afterSingletonsInstantiated()
--- 컨테이너 준비 끝 ---

    warmup의 @PostConstruct가 실행될 때 catalog는 객체조차 없었다. 초기화 콜백은 "내 준비"를 하는 자리이지 "모두가 준비된 뒤에 할 일"을 하는 자리가 아니다. 뒤의 것이 필요하면 다른 지점을 써야 하는데, 다섯째 줄이 그것이다. SmartInitializingSingleton의 afterSingletonsInstantiated()는 지연 초기화가 아닌 싱글톤이 전부 만들어진 뒤에 호출된다.

    스프링 레퍼런스는 이 구분을 꽤 강한 말로 적어 둔다. @PostConstruct를 비롯한 초기화 메서드는 컨테이너의 싱글톤 생성 락 안에서 실행되고, 빈은 이 메서드에서 돌아온 뒤에야 완전히 초기화되어 다른 곳에 공개될 준비가 된 것으로 취급된다. 따라서 초기화 메서드는 설정 상태를 검증하고 주어진 설정을 바탕으로 자료 구조를 준비하는 정도에 쓰고, 그 이상의 외부 빈 접근 활동은 하지 말라는 것이다. 그렇지 않으면 초기화 교착 상태의 위험이 있다고 한다. 비용이 큰 후속 작업에는 SmartInitializingSingleton이나 컨텍스트 새로 고침 이벤트(ContextRefreshedEvent)를 쓰라고 안내한다.

    어느 스레드에서 실행되는가

    지연 초기화가 아닌 싱글톤의 초기화 콜백은 기본적으로 컨테이너를 만드는 스레드에서 실행된다. 이 회차의 예제에서는 main 스레드다(스프링 6.2부터는 @Bean(bootstrap = Bean.Bootstrap.BACKGROUND)로 특정 빈을 백그라운드 스레드에서 만들게 할 수 있는데, 이 회차의 예제는 모두 기본값을 쓴다). 기본 설정에서는 싱글톤이 하나씩 차례로 만들어지므로, 한 빈의 초기화 콜백이 오래 걸리면 그 뒤의 모든 빈과 애플리케이션 시작 전체가 그만큼 늦어진다. 초기화 콜백에서 원격 서버를 호출하고 응답을 기다리는 코드가 시작 시간을 좌우하게 되는 이유다.

    이 순서는 여러 스레드가 싱글톤을 함께 쓰는 문제와도 맞닿아 있다. 컨테이너는 빈의 생성 과정이 초기화 콜백까지 끝난 뒤에 그 객체를 04회에서 본 싱글톤 맵에 넣고, 그제서야 다른 빈에 주입하거나 조회 결과로 내준다. 그래서 순환 참조 같은 예외적인 경우가 아니라면, 이 빈을 건네받는 쪽은 누구든 초기화 콜백이 채운 필드까지 갖춘 객체를 받는다. 한 스레드가 쓴 값을 다른 스레드가 언제 볼 수 있는가라는 질문 자체는 자바 고급 1편의 주제다. 여기서는 초기화 콜백이 빈이 바깥에 공개되기 전에 끝난다는 것만 짚어 둔다.

    지연 초기화 빈과 프로토타입 빈

    초기화 콜백의 시점은 컨테이너의 시작이 아니라 그 빈이 만들어지는 때에 묶여 있다. 지연 초기화(@Lazy)로 등록한 싱글톤은 처음 요청될 때 만들어지므로 초기화 콜백도 그때 실행된다. 요청할 때마다 새 객체를 만드는 프로토타입 스코프의 빈은 만들어질 때마다 초기화 콜백이 실행된다. 소멸 쪽에서는 이 두 경우가 싱글톤과 다르게 움직이는데, 뒤의 "소멸 콜백을 믿을 수 있는 범위"에서 실행 결과로 확인한다.

    소멸의 안쪽: DisposableBeanAdapter와 소멸 순서

    이제 반대편이다. 앞의 호출 구조 그림 맨 아래에 "소멸 때 부를 것을 미리 등록"이라는 줄이 있었다. 컨테이너는 빈의 초기화가 끝나면 이 빈에 소멸 때 할 일이 있는지 검사한다. DisposableBean을 구현했는가, 빈 정의에 소멸 메서드 이름이 있거나 추론할 수 있는가, @PreDestroy 메서드처럼 후처리기가 처리할 것이 있는가를 본다. 하나라도 해당하면 그 빈을 DisposableBeanAdapter라는 객체로 감싸 "소멸 대상" 맵에 빈 이름으로 넣어 둔다. 해당하는 것이 없는 빈은 이 맵에 들어가지 않는다.

    이름의 어댑터(adapter)는 하는 일을 말해 준다. 소멸 방식은 세 가지지만 컨테이너가 닫힐 때 다루는 것은 "destroy()를 부를 수 있는 객체"의 목록 하나다. DisposableBeanAdapter는 스스로 DisposableBean을 구현하고, 자신의 destroy() 안에서 감싸고 있는 빈의 세 가지 소멸 콜백을 차례로 부른다. 앞의 실행 결과에서 소멸 쪽 세 줄이 모두 DisposableBeanAdapter.destroy를 거친 이유다.

 │
 └─ ③ 빈 정의에 지정된(또는 추론된) 소멸 메서드   ──►  destroyMethod / close() / shutdown()

    초기화와 같은 차례다. 애노테이션, 인터페이스, 이름으로 지정한 메서드 순이다. 초기화의 역순이 아니라는 점에 주의하자. 레퍼런스도 소멸 메서드가 "같은 순서로" 호출된다고 적는다. 앞에서 소멸 메서드 이름의 오타가 시작할 때 드러난 것도 이 구조 때문이다. 어댑터가 만들어질 때, 곧 빈이 초기화된 직후에 지정된 이름의 메서드를 미리 찾아 두기 때문이다.

    여러 빈 사이의 순서

    빈 하나 안의 순서는 정리되었다. 빈이 여럿일 때는 어느 빈의 소멸 콜백이 먼저 불리는가. 자원을 가진 빈들은 서로 기대고 있기 때문에 이 순서는 중요하다. 대출 서비스가 종료 직전에 저널에 마지막 한 줄을 남기려 한다고 하자. 저널이 먼저 닫히면 그 한 줄은 실패한다.

    // import는 앞의 예제와 같다
public class MultiMain {

    static class Journal {
        private boolean open;
        @PostConstruct void open()  { open = true;  System.out.println("journal  초기화"); }
        void append(String line) {
            if (!open) throw new IllegalStateException("저널이 이미 닫혔다");
            System.out.println("journal  기록: " + line);
        }
        @PreDestroy void close()    { open = false; System.out.println("journal  소멸"); }
    }

    static class LoanService {
        private final Journal journal;
        LoanService(Journal journal) { this.journal = journal; }
        @PostConstruct void start() { System.out.println("service  초기화"); journal.append("service started"); }
        @PreDestroy void stop()     { journal.append("service stopping"); System.out.println("service  소멸"); }
    }

    static class Metrics {
        @PostConstruct void start() { System.out.println("metrics  초기화"); }
        @PreDestroy void stop()     { System.out.println("metrics  소멸"); }
    }

    @Configuration
    static class Config {
        // 일부러 의존하는 쪽을 먼저 선언했다
        @Bean LoanService loanService(Journal journal) { return new LoanService(journal); }
        @Bean Journal journal()                        { return new Journal(); }
        @Bean Metrics metrics()                        { return new Metrics(); }
    }

    public static void main(String[] args) {
        var ctx = new AnnotationConfigApplicationContext(Config.class);
        var bf = ctx.getBeanFactory();
        System.out.println("journal에 의존하는 빈 = " + String.join(", ", bf.getDependentBeans("journal")));
        System.out.println("--- close ---");
        ctx.close();
    }
}

    초기화부터 보자. 설정 클래스에는 loanService가 먼저 선언되어 있지만 먼저 초기화된 것은 journal이다. 컨테이너가 loanService를 만들려면 파라미터에 넣을 Journal이 필요하고, 그것을 얻는 과정에서 journal의 생성과 초기화가 먼저 끝난다. 초기화가 끝난 차례는 journal, loanService, metrics이고, 소멸 대상 맵에도 이 차례로 들어간다. 이 맵은 넣은 순서를 기억하는 LinkedHashMap이다.

    소멸은 정확히 그 역순이다. metrics, loanService, journal. 컨테이너는 소멸 대상 맵의 이름들을 배열로 옮긴 뒤 마지막 것부터 거꾸로 돌며 소멸시킨다. 나중에 완성된 빈일수록 먼저 완성된 빈에 기대고 있을 수 있으므로, 나중 것부터 치우면 기대고 있던 상대가 아직 살아 있다. 서비스의 stop()이 저널에 "service stopping"을 남길 수 있었던 이유다. 자바의 try-with-resources가 자원을 선언의 역순으로 닫는 것과 같은 생각이다.

    컨테이너는 역순 규칙에 더해 한 가지를 따로 보장한다. 어떤 빈을 소멸시키기 전에 그 빈에 의존하는 빈들을 먼저 소멸시킨다. 컨테이너는 주입을 수행하면서 "누가 누구에게 의존하는가"를 기록해 두는데, 출력의 다섯째 줄이 그 기록이다. journal에 의존하는 빈으로 loanService가 등록되어 있다. 일반적인 경우에는 역순 규칙만으로 같은 결과가 나오지만, 이 기록이 있기 때문에 생성 순서가 꼬인 경우에도 의존하는 쪽이 먼저 정리된다.

    컨테이너가 모르는 의존관계에는 이 보장이 미치지 않는다. 주입받지 않고 메서드 안에서 컨테이너를 직접 조회해 쓰는 빈이나, 정적 필드를 통해 몰래 쓰는 객체는 기록에 남지 않는다. 그런 관계를 컨테이너에게 알려 주는 방법이 @DependsOn이다. 레퍼런스는 depends-on이 초기화 시점의 의존뿐 아니라 싱글톤 빈에 한해 소멸 시점의 의존도 지정하며, 의존한다고 선언한 빈이 먼저 소멸되므로 종료 순서를 제어하는 데에도 쓸 수 있다고 적는다.

    콜백에서 예외가 나면

    초기화 콜백과 소멸 콜백은 실패할 수 있는 일을 한다. 파일이 없거나, 포트가 이미 쓰이고 있거나, 원격 서버가 응답하지 않는다. 콜백이 예외를 던지면 컨테이너는 어떻게 하는가. 초기화와 소멸에서 처리 방식이 정반대다.

    // import는 앞의 예제와 같다
public class FailMain {

    static class Part {
        private final String name;
        private final boolean failOnInit;
        private final boolean failOnDestroy;
        Part(String name, boolean failOnInit, boolean failOnDestroy) {
            this.name = name; this.failOnInit = failOnInit; this.failOnDestroy = failOnDestroy;
            System.out.println(name + " 생성자");
        }
        @PostConstruct void init() {
            if (failOnInit) throw new IllegalStateException(name + ": 포트를 열 수 없다");
            System.out.println(name + " 초기화");
        }
        @PreDestroy void destroy() {
            if (failOnDestroy) throw new IllegalStateException(name + ": 닫다가 실패");
            System.out.println(name + " 소멸");
        }
    }

    @Configuration
    static class InitFails {
        @Bean Part first()  { return new Part("first",  false, false); }
        @Bean Part second() { return new Part("second", true,  false); }
        @Bean Part third()  { return new Part("third",  false, false); }
    }

    @Configuration
    static class DestroyFails {
        @Bean Part first()  { return new Part("first",  false, false); }
        @Bean Part second() { return new Part("second", false, true); }
        @Bean Part third()  { return new Part("third",  false, false); }
    }

    public static void main(String[] args) {
        System.out.println("=== 초기화 콜백에서 예외 ===");
        try {
            new AnnotationConfigApplicationContext(InitFails.class);
            System.out.println("컨테이너 생성 성공");
        } catch (Exception e) {
            System.out.println("컨테이너 생성 실패: " + e.getClass().getSimpleName());
            System.out.println("  " + e.getMessage());
            for (Throwable c = e.getCause(); c != null; c = c.getCause()) System.out.println("  cause: " + c);
        }

        System.out.println("=== 소멸 콜백에서 예외 ===");
        var ctx = new AnnotationConfigApplicationContext(DestroyFails.class);
        System.out.println("--- close ---");
        ctx.close();
        System.out.println("close()가 정상적으로 돌아왔다");
    }
}

    초기화의 실패는 시작 전체의 실패다

    앞쪽 절반을 보자. second의 초기화 콜백이 예외를 던지자 컨테이너는 그것을 BeanCreationException으로 감싸 던졌고, new AnnotationConfigApplicationContext(...)가 그 예외로 끝났다. third는 생성자조차 실행되지 않았다. 빈 하나가 준비에 실패하면 컨테이너 전체가 시작에 실패한다.

    이것은 바람직한 성질이다. 준비되지 않은 빈을 가진 채로 애플리케이션이 떠서 요청을 받기 시작하면, 문제는 한참 뒤에 엉뚱한 곳에서 드러난다. 시작할 때 멈추면 원인이 예외 메시지에 그대로 적혀 있다. 그래서 초기화 콜백은 설정값을 검증하기에 알맞은 자리다. 필수 설정이 비어 있으면 예외를 던져 시작을 막는다.

    눈여겨볼 줄이 하나 더 있다. 예외가 전파되기 전에 "first 소멸"이 찍혔다. 컨테이너는 시작에 실패하면 그때까지 만들어 둔 싱글톤들을 소멸시킨 뒤에 예외를 다시 던진다. 이미 열린 자원이 주인 없이 남지 않게 하려는 것이다. 반면 second 자신의 @PreDestroy는 불리지 않았다. 소멸 대상 등록은 초기화가 성공한 다음에 일어나므로, 초기화에 실패한 빈은 소멸 대상 맵에 들어간 적이 없다.

    여기서 초기화 콜백을 쓸 때의 규칙이 하나 나온다. 초기화 콜백 안에서 자원을 두 개 열다가 둘째에서 실패하면, 이미 연 첫째는 그 콜백이 스스로 닫아야 한다. 컨테이너는 실패한 빈의 소멸 콜백을 불러 주지 않기 때문이다.

    소멸의 실패는 기록만 남는다

    뒤쪽 절반은 다르다. second의 소멸 콜백이 예외를 던졌는데도 first의 소멸 콜백은 실행되었고, close()는 예외 없이 돌아왔다. 남은 것은 경고 수준의 로그 한 줄이다. 컨테이너는 소멸 콜백이 던진 예외를 잡아서 기록하고 다음 빈으로 넘어간다.

    이렇게 설계된 이유는 종료라는 상황의 성격에 있다. 한 빈의 정리가 실패했다고 거기서 멈추면 나머지 빈들이 가진 연결과 파일은 닫히지 못한다. 그리고 종료 중에 던져진 예외는 받아서 무언가를 할 주체가 없다. 그래서 최대한 많이 정리하고 실패는 기록으로 남기는 쪽을 택한 것이다.

    대신 값이 있다. 소멸 콜백의 실패는 조용하다. 버퍼를 비우다 실패해 데이터가 유실되어도 프로세스는 정상 종료 코드로 끝날 수 있다. 종료 시점의 경고 로그를 버리지 말아야 하는 이유이고, 다음 절에서 볼 것처럼 중요한 데이터의 보존을 소멸 콜백 하나에 맡기면 안 되는 이유 가운데 하나다.

    누가 close()를 부르는가: JVM 종료 절차와 셧다운 훅

    지금까지의 예제는 모두 main이 ctx.close()를 직접 불렀다. 소멸 콜백을 부르는 책임은 컨테이너로 옮겼지만, 컨테이너를 닫는 책임은 여전히 우리 코드에 남아 있었다. ConfigurableApplicationContext는 Closeable을 확장하므로 컨테이너 자체를 try-with-resources에 넣어 블록이 끝날 때 닫히게 할 수도 있다.

    try (var ctx = new AnnotationConfigApplicationContext(JournalConfig.class)) {
    ctx.getBean(LoanJournal.class).append("B-1001 loaned to M-17");
}   // 블록을 벗어나면서 ctx.close()가 호출된다

    그러나 이 방법은 프로그램이 "끝나는 줄"을 우리가 알 때만 쓸 수 있다. 서버 애플리케이션은 요청을 기다리며 계속 떠 있다가 바깥에서 종료 신호를 받고 끝난다. 코드 어딘가에서 System.exit를 부를 수도 있고, main이 예외로 끝날 수도 있다. 이런 경로에서는 누가 컨테이너를 닫는가.

    먼저 분명히 할 것이 있다. JVM은 스프링 컨테이너를 모른다. JVM이 보기에 컨테이너는 힙에 있는 객체 가운데 하나일 뿐이고, 프로세스가 끝날 때 그 객체의 close()를 불러 줄 이유가 없다. JVM이 제공하는 것은 더 일반적인 장치인 셧다운 훅(shutdown hook)이다.

    JVM의 종료 절차

    java.lang.Runtime의 Javadoc(Java 21)은 JVM이 종료 절차(shutdown sequence)를 시작하는 계기를 셋으로 적는다. 살아 있는 비데몬(non-daemon) 스레드의 수가 처음으로 0이 될 때, Runtime.exit나 System.exit가 처음 호출될 때, 그리고 인터럽트나 운영체제의 신호 같은 외부 사건이 일어날 때다. 종료 절차가 시작되면 등록되어 있던 셧다운 훅들이 시작되고, 모든 훅이 끝나면 종료 절차가 끝나며 JVM이 종료된다.

    셧다운 훅의 정체는 단순하다. 같은 Javadoc의 표현으로 "초기화되었지만 아직 시작되지 않은 스레드"다. Runtime.getRuntime().addShutdownHook(thread)로 스레드 객체를 맡겨 두면 JVM이 종료 절차를 시작하면서 그 스레드의 start()를 불러 준다. 종료할 때 실행하고 싶은 코드를 스레드의 run()에 넣어 두는 방식이다.

    스프링이 등록하는 훅

    스프링은 이 장치 위에 한 줄짜리 메서드를 얹었다. ConfigurableApplicationContext의 registerShutdownHook()이다. 이 메서드는 SpringContextShutdownHook이라는 이름의 스레드를 만들어 JVM에 셧다운 훅으로 등록하고, 그 스레드의 run()은 컨테이너를 닫는 내부 메서드를 호출한다. close()가 하는 일과 같은 일이다. 여러 종료 경로에서 소멸 콜백이 불리는지, 불린다면 어느 스레드에서 불리는지 확인해 보자.

    // import는 앞의 예제와 같다
public class HookMain {

    static class Journal {
        @PostConstruct void open() {
            System.out.println("초기화 콜백  스레드 = " + Thread.currentThread().getName());
        }
        @PreDestroy void close() {
            System.out.println("소멸 콜백    스레드 = " + Thread.currentThread().getName());
        }
    }

    @Configuration
    static class Config {
        @Bean Journal journal() { return new Journal(); }
    }

    public static void main(String[] args) throws Exception {
        String mode = args[0];
        var ctx = new AnnotationConfigApplicationContext(Config.class);
        switch (mode) {
            case "none"  -> { }                                   // 닫지 않고 main이 끝난다
            case "close" -> ctx.close();
            case "hook"  -> ctx.registerShutdownHook();           // 훅만 등록하고 main이 끝난다
            case "exit"  -> { ctx.registerShutdownHook(); System.exit(3); }
            case "throw" -> { ctx.registerShutdownHook(); throw new IllegalStateException("main에서 예외"); }
            case "halt"  -> { ctx.registerShutdownHook(); Runtime.getRuntime().halt(3); }
            case "wait"  -> {                                     // 바깥에서 신호를 보낼 때까지 기다린다
                ctx.registerShutdownHook();
                System.out.println("pid = " + ProcessHandle.current().pid());
                Thread.sleep(60_000);
            }
            default -> throw new IllegalArgumentException(mode);
        }
        System.out.println("main 끝");
    }
}

    훅 등록 후 System.exit(3)(exit)불림SpringContextShutdownHook3
    훅 등록 후 main에서 예외(throw)불림SpringContextShutdownHook1
    훅 등록 후 Runtime.halt(3)(halt)불리지 않음—3
    훅 등록 후 대기 중 kill <pid>(SIGTERM)불림SpringContextShutdownHook143
    훅 등록 후 대기 중 kill -9 <pid>(SIGKILL)불리지 않음—137

    첫 줄부터 읽어 보자. none에서는 main이 끝나 비데몬 스레드가 0이 되었고 JVM은 종료 절차를 시작했다. 그러나 등록된 훅이 없으니 컨테이너에게 알려 줄 것이 없었다. 프로세스는 종료 코드 0으로 깔끔하게 끝났고 소멸 콜백은 불리지 않았다. 이 회차 첫 예제에서 저널의 세 줄이 사라진 것과 같은 상황이다.

    hook에서는 "main 끝"이 찍힌 뒤에 소멸 콜백이 실행되었고, 실행한 스레드는 main이 아니라 훅 스레드다. main 스레드는 이미 끝났고, JVM이 종료 절차의 일부로 훅 스레드를 시작한 것이다. exit와 throw도 같은 경로를 탄다. System.exit는 종료 절차를 시작시키는 둘째 계기이고, 잡히지 않은 예외는 main 스레드를 끝내 첫째 계기에 해당한다. exit에서 "main 끝"이 찍히지 않은 것은 System.exit가 정상적으로 돌아오지 않는 메서드이기 때문이다.

    SIGTERM은 셋째 계기다. kill 명령이 기본으로 보내는 이 신호를 JVM이 받아서 종료 절차를 시작했다. JDK의 java 명령 문서는 -Xrs 옵션을 설명하면서, 윈도우가 아닌 환경에서 JVM이 SIGHUP, SIGINT, SIGTERM을 셧다운 훅 실행을 시작하는 데 쓴다고 적는다. 터미널에서 Ctrl+C를 눌러 보내는 SIGINT도 같은 경로를 탄다는 뜻이다. 표의 종료 코드 143은 128에 SIGTERM의 번호 15를 더한 값이다.

    소멸 콜백이 불리지 않은 나머지 두 줄이 중요하다. Runtime.halt는 Javadoc의 표현으로 종료 절차를 시작하지 않고 JVM을 즉시 종료한다. SIGKILL은 프로세스가 잡거나 무시할 수 없는 신호여서, 운영체제가 프로세스를 그 자리에서 없앤다. JVM은 자바 코드를 한 줄도 더 실행하지 못하므로 훅도, 소멸 콜백도 실행되지 않는다. 종료 코드 137은 128에 SIGKILL의 번호 9를 더한 값이다.

    스프링 부트와 웹 애플리케이션

    이 권의 예제처럼 컨테이너를 직접 만드는 코드에서는 close()를 부르거나 registerShutdownHook()을 불러 두는 것이 우리의 몫이다. 스프링 레퍼런스도 웹이 아닌 환경에서 컨테이너를 쓴다면 JVM에 셧다운 훅을 등록하라고 안내한다. 같은 문서는 웹 기반 ApplicationContext 구현에는 웹 애플리케이션이 내려갈 때 컨테이너를 닫는 코드가 이미 들어 있다고 적는다.

    스프링 부트를 쓰면 이 일이 자동으로 된다. 스프링 부트 레퍼런스는 SpringApplication이 종료 시 ApplicationContext가 정상적으로 닫히도록 JVM에 셧다운 훅을 등록하며, DisposableBean 인터페이스나 @PreDestroy 같은 표준 생명주기 콜백을 모두 쓸 수 있다고 적는다. 부트 애플리케이션에서 아무것도 하지 않아도 @PreDestroy가 불리는 이유다. 그렇다고 표의 마지막 줄이 달라지지는 않는다. 훅이 등록되어 있어도 SIGKILL에는 실행될 기회가 없다.

    닫히는 순서와, 그동안 멈춰 있지 않은 다른 스레드

    컨테이너가 닫힐 때 소멸 콜백이 가장 먼저 불리는 것은 아니다. 닫는 메서드는 먼저 컨텍스트가 닫힌다는 이벤트(ContextClosedEvent)를 발행하고, 자체적으로 시작과 정지를 관리하는 Lifecycle 빈들을 멈춘 다음에 싱글톤들의 소멸 콜백을 부른다. Lifecycle은 이 회차의 범위 밖이므로 "소멸 콜백 앞에 정지 단계가 하나 더 있다"는 것만 기억해 두자. 그리고 같은 컨테이너에 대해 닫는 일이 두 번 일어나지는 않는다. close()를 직접 부르면 등록해 둔 훅은 해제되고, 이미 닫힌 컨테이너에 close()를 다시 불러도 아무 일도 일어나지 않는다. 닫힌 뒤에 getBean을 부르면 "has been closed already"라는 메시지의 IllegalStateException이 난다.

    스레드 관점에서 한 가지를 더 짚어야 한다. Runtime의 Javadoc에 따르면 셧다운 훅들은 정해지지 않은 순서로 시작되고, 종료 절차가 시작될 때 살아 있던 다른 스레드들과 동시에 실행된다. 종료 절차가 시작되었다고 해서 일하던 스레드가 멈추는 것이 아니다. 훅 스레드가 저널의 소멸 콜백을 실행하는 바로 그 순간에, 아직 끝나지 않은 작업 스레드가 같은 저널의 append를 부르고 있을 수 있다.

    그래서 소멸 콜백은 "이제 아무도 나를 쓰지 않는다"고 가정하면 안 된다. 닫힌 뒤에 들어온 호출이 어떻게 되어야 하는지를 정해 두어야 하고, 닫는 동작과 쓰는 동작이 같은 필드를 건드린다면 04회에서 본 공유 상태의 문제가 그대로 생긴다. 같은 Javadoc은 셧다운 훅을 방어적으로 작성하고, 스레드에 안전하게 만들고, 빨리 끝내라고 권한다. 사용자 로그오프나 시스템 종료로 JVM이 끝날 때에는 운영체제가 제한된 시간만 줄 수 있기 때문이라고 한다.

    이 "제한된 시간"은 운영 환경에서 구체적인 숫자로 나타난다. 한 예로 도커의 docker stop 문서는 컨테이너의 주 프로세스가 SIGTERM을 받고, 유예 시간이 지나면 SIGKILL을 받는다고 적으며, 리눅스 컨테이너의 기본 유예 시간을 10초로 적고 있다. 소멸 콜백들이 그 안에 끝나지 않으면 표의 일곱째 줄로 시작한 종료가 여덟째 줄로 끝난다.

    프로세스가 끝나는 여러 경로가 JVM의 종료 절차를 거치는 쪽과 거치지 않는 쪽으로 갈리고, 종료 절차를 거치는 쪽만 셧다운 훅을 통해 소멸 콜백에 도달한다는 것을 보여 준다. 왼쪽에서 오른쪽으로 흐르는 분기 흐름도. 왼쪽 열에 여섯 개의 작은 둥근 사각형을 세로로 나열한다. 위의 네 개는 파란색으로 칠하고 라벨은 차례로 "main 종료", "System.exit", "SIGTERM", "Ctrl+C". 아래의 두 개는 빨간색으로 칠하고 라벨은 "Runtime.halt", "SIGKILL". 위의 네 상자에서 나온 화살표는 가운데의 큰 파란 사각형 하나로 모이고 그 사각형의 라벨은 "JVM 종료 절차". 이 사각형에서 오른쪽으로 화살표가 나가 "셧다운 훅 스레드"라는 상자로 이어지고, 다시 화살표가 "컨테이너 닫기"라는 상자로, 마지막으로 초록색 상자 "소멸 콜백 실행"으로 이어진다. 아래의 두 빨간 상자에서 나온 화살표는 가운데 사각형을 거치지 않고 아래쪽으로 돌아 오른쪽 끝의 회색 상자 "프로세스 즉시 종료"로 곧장 이어진다. 이 회색 상자 아래에 작은 글씨로 "소멸 콜백 없음"이라고 적는다. 흰 배경, 평면 벡터 스타일, 화살표는 굵고 단순하게, 글자는 선명한 고딕체. 소멸 콜백에 도달하는 길은 JVM의 종료 절차를 거치는 길뿐이다. halt와 SIGKILL은 그 절차를 건너뛴다.

    소멸 콜백을 믿을 수 있는 범위

    초기화 콜백과 소멸 콜백은 대칭처럼 보이지만 보장의 강도가 다르다. 초기화 콜백은 빈이 쓰이기 전에 반드시 실행된다. 실행되지 않았다면 그 빈은 만들어지지 못한 것이고 애플리케이션은 시작에 실패한다. 소멸 콜백은 그렇지 않다. 지금까지 본 것을 모으면 소멸 콜백이 불리지 않는 경우가 꽤 많다.

    • 아무도 컨테이너를 닫지 않았고 셧다운 훅도 등록되어 있지 않다.
    • 프로세스가 종료 절차 없이 끝났다. Runtime.halt, SIGKILL, JVM 자체의 비정상 종료, 전원 차단이 여기에 든다.
    • 종료 절차는 시작되었지만 주어진 시간 안에 끝나지 못해 강제로 종료되었다.
    • 그 빈의 초기화 콜백이 실패했다. 소멸 대상으로 등록된 적이 없다.
    • @Bean(destroyMethod = "")로 추론을 꺼 두었고 다른 소멸 방식도 없다.
    • 싱글톤이 아닌 빈이거나, 한 번도 만들어지지 않은 지연 초기화 빈이다.

    마지막 항목은 실행해 보면 분명해진다.

    import org.springframework.context.annotation.Lazy;
import org.springframework.context.annotation.Scope;
// 나머지 import는 앞의 예제와 같다

public class ScopeMain {

    static class Part {
        private final String name;
        Part(String name) { this.name = name; }
        @PostConstruct void init()  { System.out.println(name + " 초기화 콜백"); }
        @PreDestroy void destroy()  { System.out.println(name + " 소멸 콜백"); }
    }

    @Configuration
    static class Config {
        @Bean Part eager()                         { return new Part("eager"); }
        @Bean @Lazy Part lazyUsed()                { return new Part("lazyUsed"); }
        @Bean @Lazy Part lazyUnused()              { return new Part("lazyUnused"); }
        @Bean @Scope("prototype") Part prototype() { return new Part("prototype"); }
    }

    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(Config.class)) {
            System.out.println("--- 컨테이너 준비 끝 ---");
            ctx.getBean("lazyUsed");
            ctx.getBean("prototype");
            ctx.getBean("prototype");
            System.out.println("--- try 블록 끝 ---");
        }
        System.out.println("--- 닫힌 뒤 ---");
    }
}

--- 컨테이너 준비 끝 ---
lazyUsed 초기화 콜백
prototype 초기화 콜백
prototype 초기화 콜백
--- try 블록 끝 ---
lazyUsed 소멸 콜백
eager 소멸 콜백
--- 닫힌 뒤 ---

    lazyUnused는 한 줄도 남기지 않았다. 요청된 적이 없어 만들어지지 않았고, 없는 객체에는 초기화도 소멸도 없다. prototype은 두 번 요청되어 객체가 둘 만들어졌고 초기화 콜백도 두 번 실행되었지만, 컨테이너를 정상적으로 닫았는데도 소멸 콜백은 한 번도 불리지 않았다. 스프링 레퍼런스는 스프링이 프로토타입 빈의 생명주기 전체를 관리하지 않으며, 초기화 콜백은 스코프와 상관없이 호출되지만 프로토타입의 경우 설정된 소멸 콜백은 호출되지 않는다고 적는다. 컨테이너는 프로토타입 객체를 만들어 건넨 뒤 그 참조를 들고 있지 않으므로, 닫을 때 부를 대상을 알지 못한다. 스코프에 따라 수명을 정하는 주체가 달라지는 이야기는 08회에서 이어진다.

    소멸 콜백에 맡겨도 되는 일과 안 되는 일

    이 목록이 설계에 주는 조건은 분명하다. 소멸 콜백은 정상 종료 때 해 두면 좋은 정리를 하는 자리이지, 프로그램의 올바름이 걸린 일을 맡기는 자리가 아니다. 연결을 예의 바르게 끊고, 버퍼에 남은 것을 내보내고, 스레드 풀을 멈추는 일은 여기에 알맞다. 이 일들은 실행되지 않아도 운영체제가 소켓과 파일 디스크립터를 회수해 주고, 다음 실행이 망가지지 않는다.

    반대로 "이것이 실행되지 않으면 데이터가 틀어진다"는 일은 소멸 콜백에만 두면 안 된다. 저널의 예로 돌아가면, 대출 기록이 종료 시점의 close()에서만 파일로 내려간다면 강제 종료 한 번에 그동안의 기록이 통째로 사라진다. 잃어도 되는 양을 정하고 그 단위로 내려 써야 한다. 한 건을 기록할 때마다, 또는 일정한 간격으로 버퍼를 비우는 식이다.

    프로세스 바깥에 남긴 흔적도 같다. 임시 파일, 다른 서버에 등록해 둔 자신의 주소, 다른 프로세스와 나눠 쓰는 잠금 같은 것을 소멸 콜백에서만 지운다면, 강제 종료 뒤에는 주인 없는 흔적이 남는다. 이런 흔적에는 스스로 만료되는 시한을 두거나, 다음 시작 때 이전 실행이 남긴 것을 치우는 절차를 초기화 콜백에 두어야 한다. 앞의 가게 비유에서 미뤄 둔 차이가 이것이다. 정전으로 마감 정리를 못 한 가게는 다음 날 아침에 직원이 수습할 수 있지만, 그 수습 절차는 누군가 미리 만들어 두어야 한다.

    고르는 기준은 표에서 그대로 나온다. 직접 작성하는 클래스라면 @PostConstruct와 @PreDestroy를 쓴다. 스프링의 타입에 묶이지 않고, 콜백이라는 사실이 메서드 바로 위에 적혀 있으며, 설정 쪽에 따로 적을 것이 없다. 소스를 고칠 수 없는 외부 라이브러리의 클래스라면 @Bean의 initMethod·destroyMethod를 쓰거나 소멸 메서드 추론에 맡긴다. 인터페이스 방식은 새 코드에서 고를 이유가 적지만, 스프링 위에서 동작하는 기반 코드를 읽을 때 계속 만나게 되므로 뜻과 호출 차례는 알아 두어야 한다.

    흔한 오해

    • "@PostConstruct는 생성자 마지막 줄에 쓰는 것과 같다." 생성자가 끝난 뒤에 필드·수정자 주입과 Aware 통지가 있고, 초기화 콜백은 그다음이다. 생성자 주입만 쓰는 클래스에서도 둘은 다르다. 생성자는 컨테이너 없이 new로 만들 때도 실행되지만 초기화 콜백은 컨테이너가 부를 때만 실행된다.
    • "초기화 콜백이 불릴 때는 컨테이너가 다 준비되어 있다." 준비된 것은 이 빈과 이 빈이 주입받은 빈까지다. 나머지 싱글톤은 아직 만들어지지 않았을 수 있다.
    • "초기화 콜백 안에서도 프록시가 제공하는 기능이 동작한다." 초기화 콜백은 프록시가 씌워지기 전의 원본 객체에서 직접 호출된다.
    • "@PreDestroy는 객체가 가비지 컬렉션될 때 불린다." 소멸 콜백은 컨테이너가 닫힐 때 불리고 가비지 컬렉션과는 관계가 없다. 소멸 콜백이 끝난 객체도 참조가 남아 있는 동안은 힙에 그대로 있다.
    • "@PreDestroy는 프로그램이 끝날 때 반드시 불린다." 컨테이너가 닫혀야 불린다. 닫는 주체가 없거나 프로세스가 종료 절차 없이 끝나면 불리지 않는다.
    • "destroyMethod를 적지 않았으니 컨테이너는 이 객체를 닫지 않는다." @Bean으로 등록한 객체에 public close()나 shutdown()이 있으면 추론으로 호출된다. 닫히면 안 되는 객체라면 빈 문자열로 꺼야 한다.

    이어지는 것

    다음 08회는 빈의 수명을 정하는 규칙인 스코프를 다룬다. 이 회차의 모든 설명은 싱글톤을 전제로 했는데, 방금 본 것처럼 프로토타입 빈에서는 소멸 쪽 절반이 사라진다. 그 이유와, 웹 요청처럼 컨테이너보다 짧은 수명을 가진 스코프가 어떻게 구현되는지가 08회의 주제다.

    더 멀리 보면 이 회차의 지식은 자원을 가진 빈을 만날 때마다 다시 쓰인다. 커넥션 풀을 @Bean으로 등록하는 순간 소멸 메서드 추론이 그 풀을 닫아 줄 것인지를 판단할 수 있어야 하고, 스레드 풀을 가진 빈이라면 종료 때 남은 작업을 어떻게 할지가 소멸 콜백의 내용이 된다. 초기화 뒤에 프록시가 씌워진다는 사실은 스프링 핵심 원리 고급편에서 빈 후처리기와 프록시를 본격적으로 다룰 때의 출발점이다. 셧다운 훅과 스레드의 관계는 자바 고급 1편에서 스레드의 생명주기를 배운 뒤에 다시 읽으면 더 많은 것이 보인다.

    이 장의 핵심

    객체가 만들어지는 것과 쓸 수 있게 되는 것 사이에는 틈이 있고, 그 틈의 시작과 끝을 아는 것은 객체의 수명을 쥔 컨테이너뿐이다. 컨테이너는 주입을 마친 직후 원본 객체에 대해 초기화 콜백을 부르고, 닫힐 때 만든 순서의 역순으로 소멸 콜백을 부른다. 세 가지 방식은 같은 두 지점에 거는 서로 다른 표시일 뿐이며, 호출 순서는 initializeBean과 DisposableBeanAdapter의 구조에서 나온다. 초기화 콜백은 반드시 실행되고 실패하면 시작이 멈추지만, 소멸 콜백은 컨테이너가 닫힐 기회를 얻었을 때만 실행된다.
    생명주기 콜백
    컨테이너가 빈의 수명 가운데 정해진 지점에서 빈의 메서드를 불러 주는 것이다. 주입이 끝난 직후의 초기화 콜백과 컨테이너가 닫힐 때의 소멸 콜백 두 가지가 있다.
    생성자와 초기화를 나누는 이유
    JLS §12.5에 따라 생성자는 참조가 바깥으로 나가기 전에 실행되므로, 필드·수정자 주입과 Aware 통지로 들어올 값은 생성자 안에서 아직 없다. 외부 자원을 여는 일은 그 값들이 모두 들어온 뒤의 초기화 콜백에 둔다.
    InitializingBean · DisposableBean
    컨테이너가 instanceof로 확인하고 afterPropertiesSet()과 destroy()를 직접 호출한다. 단순하지만 클래스가 스프링 타입에 묶이고 메서드 이름을 바꿀 수 없다.
    initMethod · destroyMethod
    메서드 이름을 빈 정의에 문자열로 저장해 두고 리플렉션으로 호출한다. 소스를 고칠 수 없는 클래스에 쓸 수 있고, destroyMethod의 기본값 (inferred)는 public close()나 shutdown()을 찾아 소멸 메서드로 등록한다.
    @PostConstruct · @PreDestroy
    Jakarta Annotations가 정의한 표준 애노테이션이고 스프링에서는 빈 후처리기 CommonAnnotationBeanPostProcessor가 읽어 호출한다. 직접 작성하는 클래스에서 기본으로 쓰는 방식이다.
    한 빈 안의 호출 순서
    초기화와 소멸 모두 애노테이션, 인터페이스, 지정한 메서드 순이다. 초기화는 initializeBean의 단계 배치에서, 소멸은 DisposableBeanAdapter.destroy()의 본문에서 나오는 순서다.
    원본 객체에서의 실행
    초기화 콜백은 빈 후처리기의 "초기화 후" 훅보다 앞에서, 곧 프록시가 씌워지기 전의 원본 객체에 대해 호출된다. 소멸 콜백도 원본 객체에 대해 호출된다.
    빈 사이의 소멸 순서와 예외
    싱글톤은 초기화가 끝난 순서의 역순으로 소멸되고, 어떤 빈에 의존하는 빈이 그 빈보다 먼저 소멸된다. 초기화 콜백의 예외는 컨테이너 시작을 실패시키고, 소멸 콜백의 예외는 경고 로그만 남기고 삼켜진다.
    셧다운 훅과 그 한계
    컨테이너를 직접 닫지 않는 경로에서는 JVM의 종료 절차가 시작한 훅 스레드가 컨테이너를 닫는다. Runtime.halt나 SIGKILL처럼 종료 절차를 거치지 않는 경로에서는 소멸 콜백이 실행되지 않는다.

    실무에서 다시 판단하면, 세 방식 가운데 무엇을 쓸지는 고민할 것이 적다. 우리 코드에는 애노테이션을, 남의 클래스에는 @Bean 속성과 추론을 쓰면 된다. 판단이 필요한 것은 콜백 안에 무엇을 넣느냐다. 초기화 콜백의 실패는 시작의 실패이므로, 초기화 콜백에서 외부 시스템을 호출하면 그 시스템의 장애가 우리 애플리케이션이 뜨지 못하는 장애로 번진다. 없으면 일을 할 수 없는 자원(주 데이터베이스)이라면 그렇게 실패하는 편이 옳고, 없어도 줄어든 기능으로 버틸 수 있는 자원(통계 수집 서버)이라면 초기화 콜백에서 연결을 강제하지 않는 편이 낫다. 이 구분을 하지 않으면 부수적인 시스템 하나가 느려진 날 전체 배포가 멈춘다. 초기화 콜백이 한 스레드에서 차례로 실행되어 시작 시간에 그대로 더해진다는 점도 같은 판단의 재료다.

    종료 쪽에서는 시간이 제약이다. 본문에서 본 docker stop처럼 프로세스를 내리는 도구는 SIGTERM을 보내고 정해진 시간을 기다린 뒤 SIGKILL을 보낸다. 소멸 콜백들이 쓰는 시간의 합이 그 유예 시간을 넘으면 뒤쪽 빈들의 정리는 실행되지 못한다. 소멸은 생성의 역순이므로 가장 먼저 만들어진 기반 자원(커넥션 풀 같은 것)의 차례가 가장 늦고, 시간이 모자랄 때 정리되지 못하는 쪽도 그 자원들이다. 종료가 느리다는 보고를 받으면 어느 빈의 소멸 콜백이 오래 걸리는지부터 확인하고, 소멸 콜백에서 던져진 예외가 경고 로그로만 남는다는 점을 기억해 종료 시점의 로그를 확인 대상에 넣는다.

    설계 수준에서는 "소멸 콜백이 실행되지 않아도 시스템이 올바른가"를 묻는다. 운영 중인 프로세스는 메모리 부족이나 장비 장애로 종료 절차 없이 죽는 일이 있고, 그때 소멸 콜백에만 의지한 정리는 일어나지 않는다. 버퍼의 내용은 잃어도 되는 단위로 내려 쓰고, 바깥에 남기는 흔적에는 만료 시한이나 재시작 시의 복구 절차를 둔다. 그리고 @Bean으로 등록하는 객체가 다른 곳과 공유되는 것인지 확인한다. 소멸 메서드 추론은 편리하지만, 컨테이너가 소유하지 않은 객체를 닫아 버리는 사고도 같은 장치에서 나온다.

    static class Mailer implements InitializingBean, DisposableBean {
    Mailer()                                    { System.out.println("A"); }
    void connect()                              { System.out.println("B"); }
    @PostConstruct void verify()                { System.out.println("C"); }
    @Override public void afterPropertiesSet()  { System.out.println("D"); }
    @PreDestroy void flush()                    { System.out.println("E"); }
    @Override public void destroy()             { System.out.println("F"); }
    public void close()                         { System.out.println("G"); }
}

  • 설정 클래스에 @Bean Audit audit(), @Bean Service service(Repo repo), @Bean Repo repo()가 이 순서로 선언되어 있고, 세 클래스 모두 @PostConstruct와 @PreDestroy 메서드에서 자신의 클래스 이름을 출력한다. 컨테이너를 만들고 닫을 때 초기화 콜백과 소멸 콜백이 불리는 순서를 적고, 소멸 순서가 그렇게 되는 근거 두 가지를 말하라.
  • @PreDestroy 메서드를 가진 싱글톤 빈이 있다. 다음 각 경우에 그 메서드가 실행되는지 답하고 이유를 한 문장씩 적어라. (가) 컨테이너를 직접 만든 프로그램에서 close()도 registerShutdownHook()도 부르지 않고 main이 끝났다. (나) registerShutdownHook()을 부른 뒤 다른 스레드에서 System.exit(1)을 불렀다. (다) 스프링 부트 애플리케이션에 운영자가 kill <pid>를 실행했다. (라) 같은 애플리케이션에 kill -9 <pid>를 실행했다. (마) 같은 메서드를 가진 프로토타입 빈을 여러 번 조회해 쓴 뒤 컨테이너를 close()로 닫았다.

    1. A, C, D, B가 컨테이너를 만들 때, E, F, G가 닫을 때 출력된다. A는 @Bean 메서드 안에서 생성자가 실행될 때 나온다. 그 뒤 initializeBean이 차례로 후처리기의 초기화 전 훅(C: @PostConstruct), InitializingBean 검사(D: afterPropertiesSet()), 빈 정의에 적힌 이름의 메서드(B: connect)를 부른다. B가 소스에서는 C보다 위에 선언되어 있지만 선언 순서는 아무 영향이 없다. 닫을 때는 DisposableBeanAdapter.destroy()가 소멸 전 훅(E: @PreDestroy), DisposableBean의 destroy()(F), 지정한 소멸 메서드(G: close) 순으로 부른다. 소멸이 초기화의 역순(G, F, E)이 아니라 같은 순서라는 점이 함정이다.

    2. 근본 원인은 생성자 안에서 난 NullPointerException이고, JDK 21의 메시지는 Cannot invoke "java.time.Clock.millis()" because "this.clock" is null이다. 컨테이너는 이것을 BeanInstantiationException과 BeanCreationException으로 감싸 던진다. 필드 주입은 인스턴스 생성 단계가 끝난 뒤의 프로퍼티 채우기 단계에서 일어난다. 생성자가 실행되는 시점에 clock은 JLS §12.5가 정한 기본값 null이고, 컨테이너는 생성자가 끝나 참조를 얻기 전에는 필드에 값을 쓸 수 없다. 고치는 방법 하나는 생성자 주입으로 바꾸는 것이다. Stamp(Clock clock) { this.startedAt = clock.millis(); }로 쓰면 생성자가 호출되기 전에 인자가 준비된다. 다른 하나는 필드 주입을 유지하고 계산을 초기화 콜백으로 옮기는 것이다. startedAt에서 final을 떼고 @PostConstruct void init() { startedAt = clock.millis(); }로 쓴다. 앞의 방법이 final 필드를 유지할 수 있어 더 낫다.

    3. 초기화는 Audit, Repo, Service 순이고 소멸은 Service, Repo, Audit 순이다. 컨테이너는 선언 순서대로 audit을 먼저 만든다. 다음으로 service를 만들려면 파라미터에 넣을 Repo가 필요하므로, repo의 생성과 초기화가 먼저 끝나고 그다음에 service의 초기화가 끝난다. 소멸 순서의 근거는 둘이다. 첫째, 컨테이너는 초기화가 끝난 순서대로 소멸 대상 맵에 넣고 그 역순으로 소멸시킨다. 둘째, 주입할 때 기록해 둔 의존관계에 따라, 어떤 빈을 소멸시키기 전에 그 빈에 의존하는 빈을 먼저 소멸시킨다. 이 예에서는 두 규칙이 같은 결과를 낸다. 그래서 Service의 소멸 콜백 안에서는 Repo를 아직 쓸 수 있다.

    4. (가) 실행되지 않는다. JVM은 종료 절차를 시작하지만 등록된 훅이 없어 컨테이너를 닫을 주체가 없다. (나) 실행된다. System.exit는 어느 스레드에서 부르든 종료 절차를 시작시키고, 스프링이 등록한 훅 스레드가 컨테이너를 닫는다. (다) 실행된다. kill의 기본 신호 SIGTERM을 JVM이 받아 종료 절차를 시작하고, 스프링 부트가 등록해 둔 훅이 컨테이너를 닫는다. (라) 실행되지 않는다. SIGKILL은 프로세스가 잡을 수 없어 JVM이 종료 절차를 시작할 기회가 없다. (마) 실행되지 않는다. 컨테이너는 프로토타입 빈을 만들어 건넨 뒤 참조를 들고 있지 않으며, 프로토타입에 대해서는 소멸 콜백을 호출하지 않는다.

    5. @Bean의 destroyMethod 기본값은 (inferred)다. 컨테이너는 @Bean 메서드가 돌려준 객체에서 public이고 인자가 없는 close()를 찾아 소멸 메서드로 등록했고, 컨테이너가 닫힐 때 그것을 호출했다. 컨테이너는 그 객체가 다른 모듈과 공유된다는 것을 알 방법이 없다. @Bean(destroyMethod = "")로 추론을 끄면 해결된다. 반환 타입을 인터페이스로 바꾸는 것은 해결책이 아니다. @Bean의 Javadoc이 밝히듯 추론은 메서드의 반환 타입이 아니라 생성된 빈 인스턴스 자체를 리플렉션으로 살펴서 이루어진다. 덧붙이면, 수명을 관리하지 않을 객체를 빈으로 등록하는 것 자체가 소유 관계를 흐리게 하므로, 누가 이 객체를 닫을 책임을 지는지를 먼저 정하는 것이 근본적인 해결이다.

     수정자로 주입되는 값을 생성자 안에서 사용할 수 없는 근본적인 이유는 무엇인가? 스프링이 성능을 위해 주입을 뒤로 미루도록 최적화했기 때문이다. 생성자는 객체의 참조가 바깥에 전달되기 전에 실행되고, 바깥의 코드는 참조가 있어야 수정자를 부를 수 있기 때문이다. 리플렉션으로 호출한 생성자에서는 필드를 읽을 수 없기 때문이다. 수정자 주입은 별도의 스레드에서 비동기로 실행되기 때문이다. 자바 언어 명세 §12.5는 인스턴스 변수를 기본값으로 초기화한 뒤, 참조를 결과로 돌려주기 직전에 생성자를 처리한다고 정한다. 수정자를 부르려면 참조가 필요하므로 수정자 호출은 반드시 생성자가 끝난 뒤다. 이것은 스프링의 선택이나 최적화가 아니라 언어의 규칙이고, 리플렉션을 쓰든 new를 쓰든 같다. 주입은 컨테이너를 만드는 스레드에서 동기적으로 일어난다. 한 빈에 @PostConstruct 메서드, afterPropertiesSet(), @Bean의 initMethod가 서로 다른 메서드로 모두 있다. @PostConstruct 메서드가 가장 먼저 호출되는 이유로 가장 정확한 것은? 애노테이션이 붙은 메서드가 클래스 파일에서 가장 앞에 저장되기 때문이다. 표준 규격의 애노테이션이 스프링 고유의 방식보다 우선순위가 높도록 설정되어 있기 때문이다. @PostConstruct는 빈 후처리기의 "초기화 전" 훅에서 호출되고, 그 훅은 초기화 메서드들을 부르는 단계보다 앞에 있기 때문이다. 리플렉션 호출이 인터페이스 메서드 호출보다 먼저 실행되도록 JVM이 보장하기 때문이다. initializeBean은 Aware 통지, 후처리기의 초기화 전 훅, 초기화 메서드 호출, 후처리기의 초기화 후 훅을 이 순서로 수행한다. @PostConstruct는 CommonAnnotationBeanPostProcessor가 초기화 전 훅 안에서 호출하므로 afterPropertiesSet()과 initMethod(둘 다 초기화 메서드 호출 단계)보다 앞선다. 메서드의 선언 위치나 우선순위 설정과는 관계가 없고, JVM은 호출 방식에 따른 순서를 보장하지 않는다. 서로 의존하지 않는 싱글톤 빈 A, B, C가 이 순서로 초기화를 마친 컨테이너를 닫는 도중 B의 소멸 콜백이 예외를 던졌다. 어떻게 되는가? C의 소멸 콜백이 먼저 실행되고, B의 예외는 경고 로그로 남고, A의 소멸 콜백도 실행되며, close()는 정상적으로 돌아온다. B의 예외가 close()를 부른 쪽으로 전파되고 A의 소멸 콜백은 실행되지 않는다. 컨테이너가 닫기를 취소하고 다시 사용할 수 있는 상태로 돌아간다. A의 소멸 콜백이 먼저 실행되고 그다음 B에서 예외가 나며 C는 정리되지 않는다. 소멸은 초기화가 끝난 순서의 역순이므로 C, B, A 순이다. 컨테이너는 소멸 콜백이 던진 예외를 잡아 경고 로그로 남기고 다음 빈으로 넘어간다. 한 빈의 정리 실패 때문에 다른 빈의 자원이 닫히지 못하는 일을 막기 위해서다. 초기화 콜백의 예외가 BeanCreationException으로 전파되어 시작을 실패시키는 것과 반대다. registerShutdownHook()을 호출해 둔 애플리케이션에서 싱글톤 빈의 소멸 콜백이 실행되지 않는 경우는? main 메서드가 잡히지 않은 예외로 끝났다. 작업 스레드 하나가 System.exit(2)를 호출했다. 운영체제가 프로세스에 SIGTERM을 보냈다. 운영체제가 프로세스에 SIGKILL을 보냈다. 셧다운 훅은 JVM의 종료 절차가 시작될 때 실행된다. 비데몬 스레드가 모두 끝나는 것, System.exit 호출, SIGTERM 같은 신호의 수신은 모두 종료 절차를 시작시킨다. SIGKILL은 프로세스가 잡을 수 없는 신호여서 JVM이 자바 코드를 더 실행하지 못하고, 훅도 소멸 콜백도 실행되지 않는다. Runtime.halt도 종료 절차를 시작하지 않는다. 빈 후처리기가 어떤 빈을 프록시로 감싸 컨테이너에 등록하도록 구성되어 있다. 이 빈의 @PostConstruct 메서드에 대한 설명으로 옳은 것은? 프록시를 거쳐 호출되므로 프록시가 끼워 넣는 부가 동작이 함께 실행된다. 프록시가 만들어지기 전에 원본 객체에서 직접 호출되므로 프록시의 부가 동작이 적용되지 않는다. 프록시와 원본에서 한 번씩, 모두 두 번 호출된다. 프록시가 적용되는 빈에서는 호출되지 않는다. 프록시는 후처리기의 "초기화 후" 훅에서 만들어지고, 초기화 콜백은 그보다 앞 단계에서 실행된다. 스프링 레퍼런스도 초기화 콜백이 원본 빈 참조에 대해 호출되며 AOP 인터셉터 등이 아직 적용되지 않은 상태라고 적는다. 초기화 콜백은 빈 인스턴스 하나에 대해 메서드마다 한 번만 실행된다.
    생명주기 콜백(lifecycle callback)
    컨테이너가 빈의 수명 가운데 정해진 시점에 빈의 메서드를 호출해 주는 것. 초기화 콜백과 소멸 콜백이 있다.
    초기화 콜백(initialization callback)
    의존관계 주입과 Aware 통지가 끝난 직후, 빈이 다른 곳에 공개되기 전에 호출되는 메서드. 자원을 열고 설정을 검증하는 자리다.
    소멸 콜백(destruction callback)
    컨테이너가 닫히면서 싱글톤 빈을 정리할 때 호출되는 메서드. 버퍼를 비우고 자원을 닫는 자리다.
    빈 후처리기(BeanPostProcessor)
    컨테이너가 만든 빈을 초기화 전과 후에 건네받아 가공하거나 다른 객체로 바꿔 돌려줄 수 있는 확장 지점. @PostConstruct 처리와 프록시 적용이 여기서 이루어진다.
    CommonAnnotationBeanPostProcessor
    @PostConstruct와 @PreDestroy가 붙은 메서드를 찾아 초기화 전 훅과 소멸 전 훅에서 호출하는 빈 후처리기.
    소멸 메서드 추론(destroy method inference)
    @Bean의 destroyMethod 기본값 (inferred)에 따라, 빈 인스턴스에서 public이고 인자가 없는 close 또는 shutdown 메서드를 찾아 소멸 메서드로 등록하는 동작.
    DisposableBeanAdapter
    세 가지 소멸 방식을 가진 빈을 감싸 destroy() 하나로 호출할 수 있게 해 주는 스프링 내부 클래스. 초기화가 끝난 빈마다 필요할 때 만들어져 소멸 대상으로 등록된다.
    Aware 인터페이스
    빈 이름, 빈 팩토리, 애플리케이션 컨텍스트처럼 컨테이너만 아는 정보를 빈이 통지받기 위해 구현하는 인터페이스들. 초기화 콜백보다 먼저 호출된다.
    셧다운 훅(shutdown hook)
    JVM에 등록해 둔, 초기화되었지만 시작되지 않은 스레드. JVM이 종료 절차를 시작할 때 실행된다. 스프링은 이 훅 안에서 컨테이너를 닫는다.
    종료 절차(shutdown sequence)
    비데몬 스레드가 모두 끝나거나, System.exit가 호출되거나, 운영체제의 신호를 받았을 때 JVM이 시작하는 절차. 등록된 셧다운 훅을 실행하고 모두 끝나면 JVM이 종료된다.
