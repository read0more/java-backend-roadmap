deck: 컨테이너가 빈을 만드는 어느 단계에서 어떤 리플렉션 호출로 의존관계를 넣는지 따라가고, 생성자 주입을 고르는 이유와 같은 타입의 빈이 여럿일 때 후보를 좁히는 규칙을 실행 결과로 확인한다. minutes: 90
  • 빈 하나가 만들어지는 단계(인스턴스 생성, 주입 지점 수집, 프로퍼티 채우기, 초기화) 위에 생성자·필드·수정자·일반 메서드 주입이 일어나는 자리를 표시하고, 생성자 안에서 필드 주입 대상이 null인 이유를 설명할 수 있다.
  • 주입할 빈이 없을 때 required = false, @Nullable, Optional이 각각 어떤 결과를 내는지 실행 결과를 예측할 수 있다.
  • 생성자 주입을 고르는 이유를 final 필드의 언어 규칙, 자바 메모리 모델, 컴파일 오류, 순환 참조의 관점에서 각각 말할 수 있다.
  • 같은 타입의 빈이 여럿일 때 한정자, @Primary, 주입 지점 이름이 어떤 순서로 적용되는지 따져 주입될 빈이나 발생할 예외를 맞힐 수 있다.
  • List와 Map으로 같은 타입의 빈을 모두 주입받는 코드를 작성하고, 스프링이 타입 소거 뒤에도 원소 타입을 알아내는 근거를 클래스 파일에서 찾을 수 있다.

    설정 클래스가 사라지면 연결 정보는 어디로 가는가

    자바 코드로 빈을 직접 등록하던 설정 클래스에는 두 가지 정보가 한 줄에 함께 들어 있었다. new AlarmService(emailNotifier()) 같은 코드는 "AlarmService라는 빈이 있다"는 사실과 "그 빈은 EmailNotifier를 쓴다"는 사실을 동시에 적는다. 앞 회차의 컴포넌트 스캔은 이 가운데 앞쪽만 자동화한다. 클래스패스를 훑어 @Component가 붙은 클래스를 찾고 빈으로 등록할 뿐, 어느 빈이 어느 빈을 쓰는지는 스캔만으로 알 수 없다.

    그래서 연결 정보는 설정 클래스에서 빠져나와 각 클래스 안으로 들어간다. "나는 이 타입의 객체가 필요하다"는 선언을 클래스가 직접 하고, 컨테이너가 그 선언을 읽어 맞는 빈을 넣어 준다. 이 선언이 @Autowired이고, 이렇게 컨테이너가 선언만 보고 의존관계를 채우는 일을 의존관계 자동 주입(autowiring)이라고 한다.

    선언만으로 연결이 이루어지려면 컨테이너는 두 가지 질문에 답해야 한다. 첫째는 어디에, 언제 넣는가다. 생성자의 인자로 넣을 수도 있고 이미 만들어진 객체의 필드에 써 넣을 수도 있는데, 이 선택에 따라 객체가 겪는 상태가 달라진다. 둘째는 무엇을 넣는가다. 선언에 적힌 것은 타입뿐인데 그 타입의 빈이 하나도 없거나 둘 이상이면 컨테이너는 판단할 근거가 더 필요하다. 이 회차의 앞쪽 절반은 첫째 질문을, 뒤쪽 절반은 둘째 질문을 다룬다.

    예제는 알림 발송을 다루는 작은 프로그램이다. 알림을 보내는 수단을 Notifier 인터페이스로 추상화하고, 이메일·문자·푸시 구현을 필요할 때마다 하나씩 추가한다. 실행 결과는 JDK 21과 Spring Framework 7.0.10에서 얻었고, 본문에서 설명하는 동작은 Spring Framework 6.2의 레퍼런스 문서와 소스에서도 같은 것을 확인했다. 버전에 따라 달라지는 부분은 그 자리에서 밝힌다.

    // Notifier.java
package notice;

public interface Notifier {
    String send(String to, String text);
}

// EmailNotifier.java
package notice;

import org.springframework.stereotype.Component;

@Component
public class EmailNotifier implements Notifier {
    @Override
    public String send(String to, String text) {
        return "EMAIL -> " + to + ": " + text;
    }
}

// MessageFormatter.java
package notice;

import org.springframework.stereotype.Component;

@Component
public class MessageFormatter {
    public String format(String text) {
        return "[알림] " + text;
    }
}

// AuditLog.java
package notice;

import org.springframework.stereotype.Component;

@Component
public class AuditLog {
    public void record(String line) {
        System.out.println("audit: " + line);
    }
}

    예제의 main은 AnnotationConfigApplicationContext의 생성자에 컴포넌트 클래스를 직접 나열한다. 패키지를 스캔하게 해도 결과는 같지만, 예제마다 컨테이너에 어떤 빈이 들어 있는지가 코드 한 줄에 드러나도록 이렇게 했다. 등록 방법이 스캔이든 직접 나열이든 주입이 일어나는 방식은 달라지지 않는다.

    빈 하나가 만들어지는 순서와 주입이 끼어드는 자리

    자바에서 객체가 생기는 과정을 먼저 떠올려 보자. new를 만나면 JVM은 힙에 객체가 차지할 메모리를 잡고 모든 인스턴스 필드를 기본값으로 채운다. 참조 타입 필드라면 null이다. 그다음 생성자가 실행되고, 생성자가 끝나야 호출한 쪽이 참조를 받는다. 여기서 한 가지 물리적인 제약이 나온다. 생성자의 인자는 생성자가 호출되기 전에 이미 준비되어 있어야 한다. 반대로 필드에 값을 쓰거나 메서드를 호출하는 일은 객체가 생긴 뒤에만 할 수 있다.

    스프링 컨테이너가 싱글톤 빈 하나를 만드는 과정은 이 제약을 그대로 따른다. Spring Framework 6.2 소스의 AbstractAutowireCapableBeanFactory.doCreateBean을 보면 다음 네 단계가 순서대로 호출된다.

    이 과정에서 @Autowired를 읽고 해석하는 일을 맡은 객체는 AutowiredAnnotationBeanPostProcessor다. 이름 그대로 빈 후처리기(BeanPostProcessor)의 하나이며, 컨테이너가 빈을 만드는 과정의 정해진 지점마다 호출되어 끼어든다. 이 클래스는 세 개의 메서드로 위 단계에 참여한다. determineCandidateConstructors가 1단계에서 어떤 생성자를 쓸지 알려 주고, postProcessMergedBeanDefinition이 2단계에서 주입 지점 목록을 만들며, postProcessProperties가 3단계에서 그 목록대로 값을 넣는다.

    애노테이션 기반 애플리케이션 컨텍스트는 이 후처리기를 스스로 등록해 둔다. AnnotationConfigApplicationContext를 만든 뒤 org.springframework.context.annotation.internalAutowiredAnnotationProcessor라는 이름으로 빈을 꺼내면 이 클래스의 인스턴스가 나온다. @Autowired가 동작하는 것은 언어나 JVM의 기능이 아니라, 컨테이너 안에 등록된 이 객체 하나가 리플렉션으로 애노테이션을 읽고 값을 넣기 때문이다.

    시간 →  (컨테이너를 초기화하는 스레드 하나가 순서대로 실행한다)

 [1] 인스턴스 생성 ─────► [2] 주입 지점 수집 ─► [3] 프로퍼티 채우기 ───► [4] 초기화
     생성자 인자 해결          필드·메서드 훑기       필드에 값 쓰기            초기화 콜백
     생성자 호출               목록을 캐시에 저장     메서드 호출               (다음 회차)
     │                                                │
     └ 생성자 주입                                     └ 필드 주입 → 수정자·일반 메서드 주입

힙에 있는 AlarmService 객체의 필드
 [1] 직후   formatter = (빈)    auditLog = null    notifier = null
 [3] 직후   formatter = (빈)    auditLog = (빈)    notifier = (빈)

    이 구조에서 두 가지 귀결이 바로 나온다. 하나는 @Autowired가 컨테이너가 만든 객체에서만 동작한다는 것이다. 코드에서 new AlarmService(...)로 직접 만든 객체는 위 단계를 거치지 않으므로, 필드에 @Autowired가 붙어 있어도 아무도 값을 넣어 주지 않는다. 다른 하나는 레퍼런스 문서가 명시하는 제약으로, @Autowired를 처리하는 주체가 빈 후처리기이기 때문에 직접 만든 BeanPostProcessor나 BeanFactoryPostProcessor 안에서는 이 애노테이션을 쓸 수 없다. 후처리기 자신은 일반 빈보다 먼저 만들어져야 하기 때문이다.

    빈 하나가 만들어지는 네 단계 가운데 생성자 주입은 첫 단계에, 필드·수정자·일반 메서드 주입은 셋째 단계에 놓인다는 것과, 그 사이에 객체의 필드가 null인 구간이 있다는 것을 보여 준다. 가로 방향 타임라인 다이어그램. 왼쪽에서 오른쪽으로 네 개의 둥근 사각형 단계가 화살표로 이어진다. 각 단계의 라벨은 차례로 "1. 인스턴스 생성", "2. 주입 지점 수집", "3. 프로퍼티 채우기", "4. 초기화". 첫 단계 아래에 작은 꼬리표 "생성자 주입"을, 셋째 단계 아래에 꼬리표 세 개 "필드 주입", "수정자 주입", "일반 메서드 주입"을 위에서 아래 순서로 붙인다. 타임라인 아래쪽에는 같은 객체를 두 번 그린다. 왼쪽 객체 상자는 첫 단계 바로 아래에 두고 라벨 "생성 직후"를 붙이며, 안에 세 칸이 있고 첫 칸만 채워진 원, 나머지 두 칸은 "null"이라고 적는다. 오른쪽 객체 상자는 셋째 단계 바로 아래에 두고 라벨 "주입 완료"를 붙이며 세 칸 모두 채워진 원이다. 두 객체 상자 사이를 점선 화살표로 잇는다. 차분한 파랑과 회색 계열, 흰 배경, 평면 벡터 스타일, 글자는 선명한 고딕체. 생성자 주입은 객체가 생기는 순간에, 나머지 세 가지 주입은 객체가 생긴 뒤에 일어난다. 그 사이에는 일부 필드가 null인 구간이 있다.

    네 가지 주입 방법과 실행 순서

    스프링이 의존관계를 넣는 방법은 주입 지점의 종류에 따라 넷으로 나뉜다. 생성자 주입(constructor injection), 수정자 주입(setter injection), 필드 주입(field injection), 일반 메서드 주입이다. 네 가지를 한 클래스에 모두 넣고 각 지점에서 필드 상태를 출력해 보면 앞 절의 단계가 눈에 보인다.

    package notice;

import org.springframework.beans.factory.annotation.Autowired;
import org.springframework.stereotype.Component;

@Component
public class AlarmService {

    private final MessageFormatter formatter;   // 생성자 주입

    @Autowired
    private AuditLog auditLog;                  // 필드 주입

    private Notifier notifier;                  // 수정자 주입

    @Autowired   // 생성자가 하나뿐이면 생략할 수 있다
    public AlarmService(MessageFormatter formatter) {
        this.formatter = formatter;
        System.out.println("[생성자] formatter=" + (formatter != null)
                + ", auditLog=" + (auditLog != null)
                + ", notifier=" + (notifier != null));
    }

    @Autowired
    public void setNotifier(Notifier notifier) {
        this.notifier = notifier;
        System.out.println("[수정자] auditLog=" + (auditLog != null));
    }

    @Autowired
    public void prepare(MessageFormatter formatter, AuditLog auditLog) {
        System.out.println("[일반 메서드] 같은 빈인가: "
                + (formatter == this.formatter) + ", " + (auditLog == this.auditLog));
    }

    public String alarm(String to, String text) {
        auditLog.record(to);
        return notifier.send(to, formatter.format(text));
    }
}
    package notice;

import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class Main {
    public static void main(String[] args) {
        try (var ctx = new AnnotationConfigApplicationContext(
                AlarmService.class, EmailNotifier.class, MessageFormatter.class, AuditLog.class)) {
            AlarmService service = ctx.getBean(AlarmService.class);
            System.out.println(service.alarm("kim", "결제가 완료되었습니다"));
        }
    }
}
    [생성자] formatter=true, auditLog=false, notifier=false
[수정자] auditLog=true
[일반 메서드] 같은 빈인가: true, true
audit: kim
EMAIL -> kim: [알림] 결제가 완료되었습니다

    첫 줄부터 읽어 보자. 생성자가 실행되는 동안 formatter는 인자로 들어와 있지만 auditLog와 notifier는 아직 null이다. 객체가 막 생긴 참이고 3단계는 시작되지도 않았기 때문이다. 필드 주입이나 수정자 주입으로 받는 의존관계를 생성자 안에서 사용하면 NullPointerException이 나는 이유가 여기에 있다. 주입이 끝난 뒤에 해야 하는 초기화 작업을 생성자에 넣으면 안 되고, 그런 작업을 위한 자리가 4단계의 초기화 콜백이다.

    둘째 줄에서 수정자가 호출될 때 auditLog는 이미 채워져 있다. 필드 주입이 메서드 주입보다 먼저라는 뜻이다. AutowiredAnnotationBeanPostProcessor의 Javadoc도 필드는 빈이 생성된 직후, 설정 메서드가 호출되기 전에 주입된다고 적고 있다. 소스에서도 주입 지점 목록을 만들 때 한 클래스의 필드 항목을 메서드 항목 앞에 두고, 상위 클래스의 항목을 하위 클래스의 항목 앞에 둔다.

    셋째 줄은 일반 메서드 주입이다. 이름이 set으로 시작하지 않고 인자가 둘인 메서드에도 @Autowired를 붙일 수 있고, 컨테이너는 인자마다 맞는 빈을 찾아 한 번에 호출한다. 출력의 true, true는 여기로 들어온 빈이 생성자와 필드로 받은 것과 같은 객체임을 보여 준다. 싱글톤 빈이므로 어느 경로로 주입받든 같은 인스턴스다. 한편 수정자와 일반 메서드 사이의 순서에는 기대지 않는 편이 안전하다. 자바 리플렉션의 Class.getDeclaredMethods()는 반환하는 배열이 정렬되어 있지 않고 특정한 순서를 따르지 않는다고 명세한다. Spring Framework 6.2 소스는 이를 보완하려고 ASM으로 클래스 파일을 읽어 @Autowired 메서드를 선언 순서대로 정렬하려고 시도하지만, 레퍼런스 문서가 약속하는 동작은 아니다.

    네 방법은 컨테이너가 수행하는 리플렉션 호출이 서로 다르다. 그 차이가 각 방법의 성질을 결정한다.

    방법주입 지점컨테이너가 하는 일일어나는 단계필드를 final로
    생성자 주입생성자의 파라미터인자 배열을 만들어 생성자를 리플렉션으로 호출인스턴스 생성가능
    필드 주입@Autowired 필드접근 검사를 끄고 Field.set으로 값을 씀프로퍼티 채우기(먼저)불가
    수정자 주입@Autowired가 붙은 setterMethod.invoke로 호출프로퍼티 채우기(필드 다음)불가
    일반 메서드 주입@Autowired가 붙은 임의의 메서드Method.invoke로 호출프로퍼티 채우기(필드 다음)불가

    생성자 주입에는 생성자 선택 규칙이 따른다. 클래스에 생성자가 하나뿐이면 @Autowired가 없어도 그 생성자가 쓰인다. 이 규칙은 Spring Framework 4.3부터 적용되며, 위 예제에서 생성자의 @Autowired를 지워도 결과가 같은 이유다. 생성자가 여럿이면 컨테이너는 어느 것을 쓸지 모르므로 하나에 @Autowired를 붙여 알려 줘야 한다. 표시가 없으면 컨테이너는 인자 없는 기본 생성자를 찾고, 그것마저 없으면 빈 생성에 실패한다. 인자가 하나인 생성자와 둘인 생성자만 두고 어느 쪽에도 애노테이션을 붙이지 않은 클래스를 등록하면 다음 메시지가 나온다.

    BeanInstantiationException: Failed to instantiate [notice.TwoCtors]: No default constructor found
Caused by: java.lang.NoSuchMethodException: notice.TwoCtors.()

    수정자 주입에서 "수정자"는 자바빈 프로퍼티 규약의 setXxx 메서드를 말한다. 스프링 입장에서 수정자는 특별한 것이 아니다. Javadoc의 표현을 빌리면 빈 프로퍼티의 setter는 일반 설정 메서드의 특수한 경우일 뿐이다. 이런 메서드는 public일 필요도 없다. 필드 주입은 코드가 가장 짧지만 표에서 보듯 접근 검사를 끄는 리플렉션 호출에 전적으로 기대므로, 컨테이너 밖에서는 그 필드에 값을 넣을 정상적인 방법이 없다. 그리고 static 필드나 static 메서드는 주입 대상이 아니다. 후처리기는 그런 지점을 만나면 지원하지 않는다는 로그만 남기고 건너뛴다.

    스프링은 @Autowired 외에 jakarta.inject.Inject(클래스패스에 있을 때)도 같은 후처리기로 처리한다. jakarta.annotation.Resource는 이름을 기준으로 찾는 별도의 애노테이션이며 필드와 인자 하나짜리 setter에만 쓸 수 있다. 이 회차는 @Autowired에 집중한다.

    리플렉션으로 직접 만들어 보는 주입기

    컨테이너가 하는 일을 손으로 축소해서 만들어 보면 앞의 표가 추상적인 설명이 아니라 코드 몇 줄이라는 것을 알 수 있다. 아래는 스프링 없이 순수 자바로 작성한 80줄짜리 주입기다. 생성자 주입과 필드 주입 두 가지만 흉내 낸다.

            System.out.println("생성자 안: auditLog=" + auditLog);
        }
