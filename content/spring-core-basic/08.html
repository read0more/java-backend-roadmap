    객체는 얼마나 오래 살아야 하는가

    04회의 질문은 "객체를 몇 개 만들 것인가"였고 스프링의 기본 답은 "빈 정의마다 하나"였다. 하나를 만들어 컨테이너가 닫힐 때까지 모두가 함께 쓰므로, 그 객체의 필드에는 특정 요청에 속한 값을 둘 수 없었다. 서비스나 리포지토리처럼 일하는 방법만 담은 객체는 이 조건을 어렵지 않게 지킨다. 곤란한 것은 처음부터 상태를 담으려고 만드는 객체다.

    작성 중인 주문서는 품목 목록을 들고 있어야 한다. HTTP 요청 하나를 따라다니며 로그에 번호를 찍는 추적 객체는 그 번호를 들고 있어야 한다. 로그인한 사용자의 장바구니는 담긴 상품을 들고 있어야 한다. 셋 다 상태가 본업이고, 셋 다 누구와 공유하고 언제 버릴지가 다르다. 주문서는 주문 한 건을 받는 동안만, 추적 객체는 요청 하나가 끝날 때까지, 장바구니는 세션이 끝날 때까지 살아야 한다.

    이런 객체를 싱글톤으로 두면 04회에서 본 대로 여러 스레드의 값이 섞인다. 그렇다고 필요한 곳에서 new로 직접 만들면 두 가지를 잃는다. 하나는 컨테이너의 조립이다. 직접 만든 객체는 의존관계 주입도 초기화 콜백도 받지 못한다. 다른 하나는 전달 경로다. 컨트롤러에서 만든 추적 객체를 서비스와 리포지토리에서도 쓰려면 그 사이의 모든 메서드에 매개변수를 하나씩 더해야 한다.

    스프링은 이 문제를 빈 스코프로 푼다. 객체를 만드는 방법은 그대로 두고, 만든 객체를 어디에 얼마 동안 보관할지만 빈 정의에 따로 적게 한 것이다. 이 회차는 먼저 그 보관 규칙이 컨테이너 코드의 어느 분기인지 확인하고, 아예 보관하지 않는 스코프인 프로토타입과 그것을 싱글톤에 주입할 때 생기는 문제를 본다. 이어서 웹 요청에 묶인 스코프를 ThreadLocal 하나로 직접 만들어 본 다음, 같은 구조를 스프링의 request 스코프와 스코프 프록시 안에서 찾아낸다.

    끝까지 반복되는 생각은 하나다. 오래 사는 객체가 자기보다 짧게 사는 객체를 써야 할 때, 그 객체를 필드에 쥐고 있으면 안 된다. 쥐고 있어야 하는 것은 "지금 유효한 객체를 찾아오는 방법"이다. Provider와 프록시는 그 방법을 담는 두 가지 그릇이다.

    이 회차의 실행 결과는 원고를 쓰면서 JDK 21.0.13(Temurin), 스프링 프레임워크 7.0.10, 내장 톰캣 11.0.27에서 직접 돌려 얻은 것이다. 웹 예제는 톰캣과 DispatcherServlet을 코드로 띄워 실행했고, 컨트롤러·서비스·빈 클래스는 스프링 부트 프로젝트에 넣어도 같은 코드다. 스코프의 정의, 프로토타입의 소멸 콜백, 웹 스코프의 조건, 스코프 프록시에 관한 규칙은 이 강좌의 기준 버전인 6.2의 레퍼런스 문서와 Javadoc에서 확인했다. 본문에 나오는 스프링 내부 클래스·메서드 이름은 7.0.10 소스에서 읽었고, 그 가운데 doGetBean의 분기, RequestContextHolder, 요청 스코프의 조회 메서드, 프록시 빈 정의를 만드는 코드는 6.2.x 소스에서도 같은 구조임을 확인했다. 공개 API가 아니므로 버전에 따라 달라질 수 있다.

    빈 스코프란? — 빈 정의 하나에서 나오는 객체의 수명과 공유 범위

    03회에서 본 것처럼 컨테이너는 객체부터 들고 시작하지 않는다. 먼저 "이 클래스의 객체를 이런 방법으로 만들어라"라는 설계 정보인 빈 정의(BeanDefinition)를 모으고, 객체는 그 정의를 보고 만든다. 스코프(scope)는 빈 정의에 들어 있는 문자열 속성 하나다. 뜻은 "이 정의로 만든 객체를 어느 범위 안에서 하나로 유지할 것인가"이다.

    스프링 레퍼런스는 여섯 가지 스코프를 든다. 앞의 둘은 어떤 컨테이너에서나 쓸 수 있고, 나머지 넷은 웹 환경의 컨테이너에서만 쓸 수 있다.

    스코프 이름빈 정의 하나가 묶이는 범위같은 객체를 받는 조건
    singleton (기본값)스프링 컨테이너 하나같은 컨테이너에서 조회하면 언제나
    prototype묶이지 않는다. 객체 수에 제한이 없다없다. 조회할 때마다 새 객체
    requestHTTP 요청 하나의 생명주기같은 요청을 처리하는 동안
    sessionHTTP 세션 하나의 생명주기같은 세션에 속한 요청들에서
    application서블릿 컨텍스트(ServletContext) 하나의 생명주기같은 웹 애플리케이션 안에서
    websocket웹소켓(WebSocket) 하나의 생명주기같은 웹소켓 안에서

    지정하는 방법은 두 가지다. 컴포넌트 스캔으로 등록하는 클래스에는 @Component 옆에, 설정 클래스에서 등록하는 빈에는 @Bean 메서드에 @Scope를 붙인다. 한 클래스에 대해서는 둘 중 한 방법만 쓴다.

    // 방법 1: 컴포넌트 스캔으로 등록하는 클래스에 붙인다
@Component
@Scope("prototype")
public class OrderSheet {
}

// 방법 2: 설정 클래스의 @Bean 메서드에 붙인다 (이때 OrderSheet에는 @Component를 붙이지 않는다)
@Configuration
public class SheetConfig {
    @Bean
    @Scope("prototype")
    public OrderSheet orderSheet() {
        return new OrderSheet();
    }
}

    문자열 대신 상수를 써도 된다. ConfigurableBeanFactory.SCOPE_PROTOTYPE의 값이 "prototype"이고 WebApplicationContext.SCOPE_REQUEST의 값이 "request"다. @Scope를 붙이지 않거나 이름을 비워 두면 싱글톤이 된다. 지금까지 이 권에서 등록한 빈이 전부 싱글톤이었던 것은 스코프를 한 번도 적지 않았기 때문이다.

    컨테이너 코드에서 스코프가 갈리는 지점

    스코프가 실제로 무엇을 바꾸는지는 빈을 조회하는 코드에서 드러난다. getBean 호출은 AbstractBeanFactory.doGetBean으로 들어가고, 04회에서 본 싱글톤 캐시에 객체가 없으면 빈 정의의 스코프를 보고 세 갈래로 나뉜다. 아래는 그 부분에서 예외 처리와 순환 참조 검사를 걷어 낸 요약이다. mbd는 조회 대상의 빈 정의다.

    if (mbd.isSingleton()) {
    // 레지스트리에 있으면 그것을, 없으면 만들어서 넣고 돌려준다
    sharedInstance = getSingleton(beanName, () -> createBean(beanName, mbd, args));
}
else if (mbd.isPrototype()) {
    // 찾아보지 않고 만든다. 만든 것을 어디에도 넣지 않는다
    prototypeInstance = createBean(beanName, mbd, args);
}
else {
    // 스코프 이름으로 등록된 Scope 객체에 "찾기와 보관"을 맡긴다
    Scope scope = this.scopes.get(mbd.getScope());
    if (scope == null) {
        throw new IllegalStateException("No Scope registered for scope name '" + scopeName + "'");
    }
    scopedInstance = scope.get(beanName, () -> createBean(beanName, mbd, args));
}

    세 갈래 모두 객체를 만드는 일은 같은 createBean이 한다. 인스턴스 생성, 의존관계 주입, 07회에서 본 초기화 콜백까지가 그 안에서 일어난다. 스코프가 바꾸는 것은 만들기 전후의 일, 곧 "이미 만든 것이 있는지 어디서 찾고, 새로 만든 것을 어디에 넣는가"뿐이다.

    • 싱글톤은 getSingleton이 컨테이너 안의 맵(singletonObjects)을 찾아보고 없으면 만들어 넣는다. 컨테이너가 그 객체의 참조를 계속 들고 있다.
    • 프로토타입은 찾아보는 단계가 없다. 만들고, 만든 것을 그대로 호출한 쪽에 돌려준다.
    • 그 밖의 스코프는 이름으로 등록된 Scope 객체에 "이 이름의 객체를 달라, 없으면 이 방법으로 만들어라"라고 맡긴다. 어디서 찾고 어디에 넣을지는 그 Scope 구현이 정한다. request 스코프라면 현재 HTTP 요청이 저장소가 된다.
                                  getBean("x")
                                   │
            ┌──────────────────────┼───────────────────────────┐
     scope = singleton       scope = prototype        scope = request, session, ...
            │                      │                           │
  singletonObjects 맵에서 찾는다   찾지 않는다                 scopes 맵에서 Scope 객체를 꺼낸다
  없으면 createBean → 맵에 넣는다  createBean                  scope.get(이름, 만드는 방법)
            │                      │                           │
  컨테이너가 참조를 보관           아무도 보관하지 않음         Scope 구현이 정한 저장소에 보관
  (컨테이너 종료까지)              (받은 쪽이 전부 책임)        (요청·세션이 끝날 때까지)
    같은 createBean으로 만든 객체가 스코프에 따라 컨테이너의 맵, 아무 곳에도 없음, HTTP 요청 객체 안이라는 서로 다른 곳에 놓인다는 것을 한눈에 보여 준다. 가로로 세 칸으로 나눈 깔끔한 기술 다이어그램. 흰 배경, 얇은 선, 파랑·주황·초록 세 가지 강조색. 맨 위 가운데에 "getBean" 라벨이 붙은 둥근 상자가 있고 거기서 세 칸으로 화살표가 내려간다. 왼쪽 칸 제목 "singleton": "컨테이너"라고 적힌 큰 상자 안에 "singletonObjects"라는 표(맵)가 있고 그 표의 한 칸에서 객체 원 하나로 화살표가 간다. 객체 원은 컨테이너 상자 안쪽에 있다. 가운데 칸 제목 "prototype": 컨테이너 상자는 비어 있고, 컨테이너 바깥에 객체 원 세 개가 흩어져 있으며 각 원은 "받은 쪽" 라벨이 붙은 작은 사람 아이콘이 화살표로 가리킨다. 컨테이너에서 객체로 가는 화살표는 없다. 오른쪽 칸 제목 "request": 컨테이너 바깥에 "HTTP 요청 A", "HTTP 요청 B" 라벨의 봉투 모양 두 개가 있고 각 봉투 안에 객체 원이 하나씩 들어 있다. 컨테이너 상자에는 "Scope 객체" 라벨의 작은 상자가 있고 거기서 두 봉투로 점선 화살표가 간다. 맨 아래에 세 칸에 걸쳐 "만드는 방법은 같다 (createBean)" 라벨의 띠. 스코프는 객체를 만드는 방법이 아니라 만든 객체를 어디에 얼마 동안 두는지를 정한다.
    이 장의 핵심

    스코프는 생성 규칙이 아니라 보관 규칙이다. 싱글톤은 컨테이너가 보관하고, 프로토타입은 아무도 보관하지 않으며, 그 밖의 스코프는 Scope 구현이 정한 저장소(요청, 세션 등)에 보관한다. 소멸 콜백을 누가 언제 부르는지도 "누가 보관하고 있는가"에서 그대로 따라 나온다.

    프로토타입 스코프 — 조립해서 넘기고 잊는다

    가장 단순한 갈래부터 실행으로 확인하자. 싱글톤 빈 하나와 프로토타입 빈 하나를 등록하고, 각각 두 번씩 조회한 뒤 컨테이너를 닫는다. 두 클래스 모두 생성자, 초기화 콜백, 소멸 콜백에서 한 줄씩 출력한다. 07회에서 본 대로 @PostConstruct는 의존관계 주입이 끝난 직후에, @PreDestroy는 빈이 소멸되기 직전에 호출할 메서드를 표시한다.

    import jakarta.annotation.PostConstruct;
import jakarta.annotation.PreDestroy;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;

public class ScopeBasics {

    @Component   // 스코프를 적지 않았으므로 singleton
    static class PriceTable {
        PriceTable() { System.out.println("PriceTable 생성자"); }
        @PostConstruct void init() { System.out.println("PriceTable.init"); }
        @PreDestroy void close() { System.out.println("PriceTable.close"); }
    }

    @Component
    @Scope("prototype")
    static class OrderSheet {
        OrderSheet() { System.out.println("OrderSheet 생성자"); }
        @PostConstruct void init() { System.out.println("OrderSheet.init"); }
        @PreDestroy void close() { System.out.println("OrderSheet.close"); }
    }

    public static void main(String[] args) {
        AnnotationConfigApplicationContext ctx =
                new AnnotationConfigApplicationContext(PriceTable.class, OrderSheet.class);
        System.out.println("--- 컨테이너 준비 완료");

        PriceTable p1 = ctx.getBean(PriceTable.class);
        PriceTable p2 = ctx.getBean(PriceTable.class);
        System.out.println("p1 == p2 : " + (p1 == p2));

        System.out.println("--- 프로토타입 첫 조회");
        OrderSheet s1 = ctx.getBean(OrderSheet.class);
        System.out.println("--- 프로토타입 둘째 조회");
        OrderSheet s2 = ctx.getBean(OrderSheet.class);
        System.out.println("s1 == s2 : " + (s1 == s2));

        System.out.println("--- close 호출");
        ctx.close();
        System.out.println("--- 끝");
    }
}

PriceTable.close
--- 끝

    출력에서 네 가지를 읽을 수 있다. 첫째, "컨테이너 준비 완료" 앞에 나온 것은 PriceTable뿐이다. 04회에서 본 대로 ApplicationContext는 시작하는 동안 싱글톤 빈을 미리 만들어 두지만, 프로토타입은 누군가 달라고 하기 전에는 만들 이유가 없다. 미리 만들어 봐야 넣어 둘 곳이 없기 때문이다.

    둘째, 프로토타입은 조회할 때마다 생성자와 초기화 콜백이 다시 실행되고 s1 == s2는 false다. 앞의 분기에서 본 대로 프로토타입 갈래는 찾아보는 단계 없이 곧바로 createBean을 부른다. 셋째, 초기화 콜백은 프로토타입에서도 호출된다. 초기화는 createBean 안에서 일어나고 그 메서드는 스코프와 상관없이 공통이기 때문이다.

    넷째가 이 실험의 요점이다. 컨테이너를 닫을 때 PriceTable.close는 나오지만 OrderSheet.close는 두 객체 어느 쪽에서도 나오지 않는다. 프로토타입 빈에 붙인 @PreDestroy는 컨테이너가 호출해 주지 않는다.

    소멸 콜백이 호출되지 않는 이유

    소멸 콜백을 부르려면 컨테이너가 "닫힐 때 정리해야 할 객체 목록"을 갖고 있어야 한다. 그 목록에 올리는 코드가 createBean의 마지막 단계에 있는데, 첫 줄이 프로토타입을 걸러 낸다.

    if (!mbd.isPrototype() && requiresDestruction(bean, mbd)) {
    if (mbd.isSingleton()) {
        registerDisposableBean(beanName, ...);                 // 컨테이너의 소멸 대상 목록에 등록
    }
    else {
        scope.registerDestructionCallback(beanName, ...);      // 해당 Scope 구현에 소멸 콜백을 맡김
    }
}

    싱글톤은 컨테이너의 목록에, request나 session 같은 스코프의 빈은 그 Scope 구현에 소멸 콜백이 등록된다. 프로토타입만 어디에도 등록되지 않는다. 구현을 빠뜨린 것이 아니라 그렇게 정한 것이다. 프로토타입은 쓸 때마다 새로 만드는 객체이므로 수가 계속 늘어난다. 컨테이너가 나중에 정리해 주려고 그 참조를 전부 모아 두면, 이미 다 쓴 객체들도 컨테이너가 닫힐 때까지 가비지 컬렉션 대상이 되지 못하고 힙에 쌓인다.

    그래서 스프링은 프로토타입에 대해 생명주기의 앞 절반만 책임진다. 레퍼런스의 표현으로는 컨테이너가 프로토타입 객체를 만들고 설정하고 조립해 클라이언트에 건넨 뒤 그 인스턴스를 더 기록하지 않는다("with no further record of that prototype instance"). 프로토타입 빈이 파일이나 소켓 같은 자원을 쥐고 있다면 그것을 닫는 일은 객체를 받아 간 코드의 몫이다.

    힙에서 보면

    자바 기본편에서 본 것처럼 객체가 가비지 컬렉션 대상이 되는지는 그 객체에 닿는 참조가 남아 있는지로 정해진다. 두 스코프의 차이는 참조의 출발점에 있다.

    싱글톤 (PriceTable)
  컨테이너 ──▶ singletonObjects 맵 ──▶ PriceTable 객체
  · 컨테이너가 살아 있는 한 항상 닿는다. 조회한 쪽이 참조를 버려도 객체는 남는다.

프로토타입 (OrderSheet)
  main의 지역 변수 s1 ──▶ OrderSheet 객체 #1
  main의 지역 변수 s2 ──▶ OrderSheet 객체 #2
  · 컨테이너에서 이 객체들로 가는 참조는 없다.
  · s1, s2가 사라지면 두 객체는 닿을 수 없게 되고 수거 대상이 된다.

    이 그림을 보면 프로토타입 빈은 new로 만든 객체와 수명이 같다. 다른 점은 만드는 과정이다. 컨테이너를 거쳐 만들어지므로 생성자 매개변수에 다른 빈이 주입되고, 초기화 콜백이 호출되고, 컨테이너에 등록된 후처리기가 적용된다. 프로토타입은 "컨테이너가 조립해 주는 new"라고 보면 된다.

    따라서 선택 기준도 여기서 나온다. 다른 빈이 필요 없는 단순한 상태 객체라면 메서드 안에서 new로 만드는 편이 짧고 분명하다. 공유하면 안 되는 상태를 가지면서 동시에 컨테이너의 다른 빈을 주입받아야 하는 객체일 때 프로토타입이 맞는 선택이 된다.

    항목싱글톤프로토타입

    컨테이너의 보관singletonObjects에 보관보관하지 않음
    의존관계 주입·초기화 콜백한 번 실행만들 때마다 실행
    소멸 콜백컨테이너가 닫힐 때 호출컨테이너가 호출하지 않음
    자원 정리 책임컨테이너객체를 받아 간 코드

    프로토타입 스코프 - 싱글톤 빈과 함께 사용시 문제점

    프로토타입 빈을 getBean으로 직접 꺼내 쓰는 코드는 실제로는 드물다. 이 권이 지금까지 해 온 대로라면 필요한 객체는 생성자로 주입받는다. 주문을 받는 창구 OrderDesk가 주문서 OrderSheet를 주입받는다고 하자. 주문서는 품목 목록이라는 상태를 가지므로 프로토타입으로 선언했다. 의도는 "주문을 받을 때마다 새 주문서"다.

    import java.util.ArrayList;
import java.util.List;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;
import org.springframework.context.annotation.Scope;
import org.springframework.stereotype.Component;

public class SharedSheet {

    @Component
    @Scope("prototype")
    static class OrderSheet {
        private final List items = new ArrayList<>();
        OrderSheet() { System.out.println("  OrderSheet 생성"); }
        void add(String item) { items.add(item); }
        List items() { return items; }
    }

    @Component
    static class OrderDesk {                     // 싱글톤
        private final OrderSheet sheet;          // 생성 시점에 한 번 주입된다
        OrderDesk(OrderSheet sheet) { this.sheet = sheet; }

        List accept(String item) {
            sheet.add(item);
            return sheet.items();
        }
        OrderSheet sheet() { return sheet; }     // 실험용
    }

    @Component
    static class ReturnDesk {                    // 싱글톤
        private final OrderSheet sheet;
        ReturnDesk(OrderSheet sheet) { this.sheet = sheet; }
        OrderSheet sheet() { return sheet; }     // 실험용
    }

    public static void main(String[] args) {
        System.out.println("--- 컨테이너 생성");
        AnnotationConfigApplicationContext ctx =
                new AnnotationConfigApplicationContext(OrderSheet.class, OrderDesk.class, ReturnDesk.class);
        System.out.println("--- 준비 완료");

        OrderDesk desk = ctx.getBean(OrderDesk.class);
        System.out.println("고객 A: " + desk.accept("키보드"));
        System.out.println("고객 B: " + desk.accept("모니터"));

        OrderDesk again = ctx.getBean(OrderDesk.class);
        System.out.println("desk == again              : " + (desk == again));
        System.out.println("desk.sheet == again.sheet  : " + (desk.sheet() == again.sheet()));
        System.out.println("desk.sheet == returnDesk.sheet : "
                + (desk.sheet() == ctx.getBean(ReturnDesk.class).sheet()));
        ctx.close();
    }
}

  OrderSheet 생성
  OrderSheet 생성
--- 준비 완료
고객 A: [키보드]
고객 B: [키보드, 모니터]
desk == again              : true
desk.sheet == again.sheet  : true
desk.sheet == returnDesk.sheet : false

    고객 B의 주문서에 고객 A의 키보드가 들어 있다. 프로토타입으로 선언했는데도 주문서가 공유된 것이다. 원인은 출력의 앞부분에 이미 나와 있다. OrderSheet 생성은 컨테이너가 시작하는 동안 두 번 찍히고, 그 뒤로는 주문을 몇 번 받아도 다시 찍히지 않는다.

    "프로토타입은 조회할 때마다 새로 만든다"는 규칙은 지켜졌다. 조회가 한 번밖에 없었을 뿐이다. 06회에서 본 것처럼 의존관계 주입은 빈이 만들어질 때 일어나고, 싱글톤 빈은 한 번만 만들어진다. 레퍼런스도 같은 말을 한다. 프로토타입 빈을 싱글톤 빈에 주입하면 그 프로토타입 인스턴스는 그 싱글톤에 공급되는 유일한 인스턴스가 된다.

    출력의 마지막 줄도 같은 규칙으로 설명된다. ReturnDesk도 OrderSheet를 주입받는데, 그때 조회가 한 번 더 일어나므로 #2가 만들어진다. 그래서 두 창구의 주문서는 서로 다른 객체다. 프로토타입 객체의 수는 "사용한 횟수"가 아니라 "주입받은 지점의 수"만큼이다.

    컨테이너
  singletonObjects
    OrderDesk 빈  ──▶ OrderDesk 객체 ── sheet ──▶ OrderSheet #1  { items = [키보드, 모니터] }
    ReturnDesk 빈 ──▶ ReturnDesk 객체 ─ sheet ──▶ OrderSheet #2  { items = [] }

  · #1, #2로 가는 컨테이너의 참조는 없다. 싱글톤의 필드만이 이들을 붙잡고 있다.
  · OrderDesk가 컨테이너 종료까지 살아 있으므로 #1도 그때까지 살아 있다.
    선언은 프로토타입이지만 실제 수명과 공유 범위는 싱글톤과 같아졌다.
    프로토타입으로 선언했더라도 싱글톤의 필드에 주입되는 순간 객체가 하나로 고정되고, 여러 요청 스레드가 그 하나에 닿게 된다는 것을 보여 준다. 왼쪽에 스레드 스택 두 개, 오른쪽에 힙 영역을 그린 메모리 다이어그램. 흰 배경, 얇은 선, 파랑과 주황 강조. 왼쪽 위 스택 라벨 "요청 스레드 1", 왼쪽 아래 스택 라벨 "요청 스레드 2". 각 스택에는 "accept()" 라벨의 프레임 하나가 있다. 오른쪽 힙 영역에는 "컨테이너" 라벨의 큰 상자가 있고 그 안에 "OrderDesk (싱글톤)" 라벨의 객체 상자가 있다. OrderDesk 객체 안에는 "sheet" 라벨의 필드 칸이 있고, 그 칸에서 컨테이너 상자 바깥에 놓인 "OrderSheet #1 (프로토타입)" 라벨의 객체로 굵은 화살표가 간다. OrderSheet #1 안에는 "items: 키보드, 모니터" 라벨. 두 스택의 프레임에서 각각 OrderDesk 객체로 화살표가 가고, OrderDesk를 거쳐 같은 OrderSheet #1에 닿는다는 것이 보이게 한다. OrderSheet #1 옆에 주황색 경고 표시와 "주입은 한 번" 라벨. 컨테이너 상자에서 OrderSheet #1로 직접 가는 화살표는 없다. 프로토타입 객체가 싱글톤의 필드에 들어가면, 그 필드를 거치는 모든 스레드가 같은 객체를 쓴다.

    이 상황은 논리 오류로 끝나지 않는다. OrderDesk는 싱글톤이므로 웹 애플리케이션에서는 여러 요청 스레드가 동시에 accept를 실행한다. 그 스레드들이 모두 같은 OrderSheet 객체의 같은 ArrayList에 쓴다. 04회에서 본 "요청별 값을 필드에 둔 싱글톤"과 정확히 같은 구조가 주입을 한 단계 거쳐 다시 만들어진 것이다. 상태를 싱글톤에서 떼어 내려고 프로토타입으로 분리했는데, 주입하는 순간 다시 싱글톤에 붙어 버렸다.

    프로토타입 스코프 - 싱글톤 빈과 함께 사용시 Provider로 문제 해결

    문제를 한 문장으로 줄이면 "주입 시점에 조회가 끝나 버린다"이다. 그러면 답의 방향도 정해진다. 주문서 객체를 주입받지 말고, 주문을 받을 때마다 컨테이너에 조회를 요청하면 된다. 의존 객체를 외부에서 넣어 주는 의존관계 주입(Dependency Injection, DI)과 구별해, 필요한 객체를 사용하는 쪽이 직접 찾는 방식을 의존관계 조회(Dependency Lookup, DL)라고 부른다. 남은 질문은 싱글톤이 무엇을 통해 조회할 것인가다.

    방법 1: 컨테이너를 통째로 주입받는다

    가장 직접적인 방법은 ApplicationContext 자체를 주입받아 getBean을 부르는 것이다. 아래 세 가지 방법의 코드는 모두 앞 예제와 같은 OrderSheet를 쓴다.

    @Component
static class DeskWithContext {
    private final ApplicationContext ctx;
    DeskWithContext(ApplicationContext ctx) { this.ctx = ctx; }

    List accept(String item) {
        OrderSheet sheet = ctx.getBean(OrderSheet.class);   // 호출할 때마다 조회
        sheet.add(item);
        return sheet.items();
    }
}
      OrderSheet 생성
A: [키보드]
  OrderSheet 생성
B: [모니터]

    동작은 원하던 대로다. 그러나 치르는 값이 크다. 이 클래스에 필요한 것은 "새 주문서 하나"인데, 주입받은 것은 모든 빈을 꺼낼 수 있고 이벤트를 발행하고 환경 정보를 읽을 수 있는 컨테이너 전체다. 01회에서 다룬 원칙으로 보면 필요한 것보다 훨씬 넓은 대상에 의존하게 된 것이다. 단위 테스트에서도 주문서 하나를 건네려고 컨테이너를 띄우거나 ApplicationContext의 가짜 구현을 만들어야 한다. 레퍼런스도 이 방식을 두고 업무 코드가 스프링 프레임워크를 알고 거기에 묶이므로 바람직하지 않다고 적는다.

    방법 2: ObjectProvider — 조회 기능 하나만 주입받는다

    필요한 것은 컨테이너 전체가 아니라 "이 타입의 빈을 지금 찾아 달라"는 기능 하나다. 스프링은 그 기능만 담은 인터페이스 ObjectProvider를 제공한다. 주입 지점의 타입을 OrderSheet 대신 ObjectProvider에 타입 인자를 준 형태로 바꾸고, 사용할 때 getObject()를 부른다.

    @Component
static class DeskWithObjectProvider {
    private final ObjectProvider sheets;

    DeskWithObjectProvider(ObjectProvider sheets) {
        this.sheets = sheets;
        System.out.println("주입된 것: " + sheets.getClass().getName());
    }

    List accept(String item) {
        OrderSheet sheet = sheets.getObject();   // 이 순간 컨테이너가 OrderSheet 빈을 조회한다
        sheet.add(item);
        return sheet.items();
    }
}
    주입된 것: org.springframework.beans.factory.support.DefaultListableBeanFactory$DependencyObjectProvider
  OrderSheet 생성

B: [모니터]

    첫 줄이 이 방법의 정체를 알려 준다. 주입된 객체는 우리가 등록한 빈이 아니라 컨테이너(DefaultListableBeanFactory)의 내부 클래스 인스턴스다. 실제로 ctx.getBeanNamesForType(ObjectProvider.class)의 결과는 빈 배열이다. 컨테이너는 주입 지점의 타입이 ObjectProvider나 그 부모인 ObjectFactory이면 빈을 찾는 대신 그 자리에서 조회용 객체를 하나 만들어 넣어 준다.

    그 조회용 객체가 기억하는 것은 "어느 주입 지점이 어떤 타입을 원했는가"라는 정보다. getObject()가 호출되면 그 정보로 컨테이너의 의존관계 해석을 그때 실행한다. 06회에서 본 자동 주입의 규칙, 곧 타입으로 후보를 찾고 @Qualifier와 @Primary로 좁히는 과정이 생성 시점이 아니라 호출 시점에 일어나는 것이다. 그 끝에서 OrderSheet 빈이 조회되고, 프로토타입 갈래를 타므로 새 객체가 나온다.

    ObjectProvider는 프로토타입 전용 도구가 아니다. 하는 일은 "조회를 나중으로 미루는 것"뿐이므로, 대상이 싱글톤이면 getObject()는 매번 같은 싱글톤을 돌려준다. Javadoc도 반환값을 "공유된 것일 수도 독립된 것일 수도 있는" 인스턴스라고 설명한다. 새 객체가 나오는 이유는 Provider가 아니라 대상 빈의 스코프에 있다.

    상속 관계도 알아 두면 좋다. 부모인 ObjectFactory에는 getObject() 하나만 있다. ObjectProvider는 스프링 4.3에 추가된 확장으로, 빈이 없으면 null을 돌려주는 getIfAvailable(), 후보가 하나로 정해질 때만 돌려주는 getIfUnique(), 5.1부터는 맞는 빈 전부를 차례로 꺼내는 stream() 같은 메서드를 더했다.

    ObjectProvider는 타입 인자를 어떻게 아는가

    한 가지 의문이 남는다. 자바 중급 2편에서 본 것처럼 제네릭의 타입 인자는 컴파일 뒤에 지워진다(타입 소거). 실행 중인 ObjectProvider 객체만 보아서는 그것이 OrderSheet용인지 알 수 없다. 그런데 컨테이너는 어떻게 OrderSheet를 찾아 주는가.

    지워지는 것은 객체가 실행 중에 들고 다니는 타입 정보다. 필드, 메서드, 생성자의 선언에 적힌 제네릭 타입은 클래스 파일에 Signature라는 속성으로 남고, 리플렉션으로 읽을 수 있다. 스프링 없이 확인해 보자.

    import java.lang.reflect.Constructor;

    컨테이너는 빈을 만들기 전에 생성자의 매개변수 선언을 이렇게 읽는다. 매개변수가 ObjectProvider이고 타입 인자가 OrderSheet라는 것을 알아낸 뒤, 그 정보를 조회용 객체 안에 넣어 둔다. Provider는 실행 중에 자기 타입 인자를 알아내는 것이 아니라, 만들어질 때 선언에서 읽은 값을 건네받는 것이다.

    방법 3: jakarta.inject.Provider — 표준 인터페이스

    ObjectProvider는 스프링의 타입이다. 같은 역할의 인터페이스가 자바 진영의 의존관계 주입 표준(JSR-330)에도 있다. jakarta.inject.Provider이고, 메서드는 get() 하나뿐이다. 스프링의 일부가 아니므로 라이브러리를 따로 추가해야 한다. 원고의 실험에서는 jakarta.inject:jakarta.inject-api:2.0.1을 썼다.

    import jakarta.inject.Provider;

@Component
static class DeskWithJsr330 {
    private final Provider sheets;

    DeskWithJsr330(Provider sheets) {
        this.sheets = sheets;
        System.out.println("주입된 것: " + sheets.getClass().getName());
    }

    List accept(String item) {
        OrderSheet sheet = sheets.get();
        sheet.add(item);
        return sheet.items();
    }
}

    이번에도 주입된 것은 컨테이너가 그 자리에서 만든 내부 객체이고, 동작은 방법 2와 같다. 레퍼런스는 jakarta.inject.Provider를 스프링의 ObjectFactory를 그대로 대신할 수 있고 메서드 이름이 get()으로 더 짧을 뿐이라고 설명한다. 차이는 의존하는 대상이다. 이 클래스의 import 문에는 조회 기능에 관한 한 스프링 타입이 없으므로, JSR-330을 지원하는 다른 컨테이너에서도 같은 코드가 동작한다. 대신 의존 라이브러리가 하나 늘고, getIfAvailable 같은 부가 기능은 없다.

    그 밖의 방법: 조회 메서드 주입

    레퍼런스가 이 문제의 해법으로 소개하는 것이 하나 더 있다. 조회 메서드 주입(lookup method injection)이다. 클래스에 "새 주문서를 돌려준다"는 메서드를 추상 메서드로 선언하고 @Lookup을 붙여 두면, 컨테이너가 그 클래스의 자식 클래스를 CGLIB로 만들어 메서드 본문을 "컨테이너에서 조회해 돌려준다"로 채운다.

    @Component
static abstract class OrderDesk {
    List accept(String item) {
        OrderSheet sheet = newSheet();
        sheet.add(item);
        return sheet.items();
    }

    @Lookup
    protected abstract OrderSheet newSheet();   // 본문은 컨테이너가 만든 자식 클래스가 채운다
}

    이 빈을 조회해 클래스 이름을 출력하면 LookupFix$OrderDesk$$SpringCGLIB$$0처럼 자식 클래스의 이름이 나오고, accept를 두 번 부르면 [키보드], [모니터]가 따로 나온다(LookupFix는 실험에 쓴 바깥 클래스 이름이다). 04회에서 @Configuration 클래스가 자식 클래스로 바뀌던 것과 같은 기법이다. 자식 클래스를 만들어야 하므로 클래스와 해당 메서드가 final이면 안 되고, @Bean 메서드로 직접 만들어 돌려주는 객체에는 적용되지 않는다. 컨테이너가 객체 생성을 맡지 않으면 자식 클래스로 바꿔 끼울 기회가 없기 때문이다.

    방법싱글톤이 의존하는 대상조회가 일어나는 때치르는 값
    직접 주입OrderSheet싱글톤이 만들어질 때 한 번객체가 고정되어 공유된다(문제 상황)
    ApplicationContext 주입컨테이너 전체getBean을 부를 때마다의존 범위가 지나치게 넓고 테스트가 무겁다
    ObjectProvider조회 기능 하나(스프링 인터페이스)getObject()를 부를 때마다업무 코드에 스프링 타입이 하나 들어온다
    jakarta.inject.Provider조회 기능 하나(표준 인터페이스)get()을 부를 때마다라이브러리 추가, 부가 기능 없음
    @Lookup자기 자신의 추상 메서드그 메서드를 부를 때마다클래스가 CGLIB 자식으로 바뀌고 제약이 붙는다

    어느 방법이든 구조는 같다. 싱글톤의 필드에 들어 있는 것은 주문서가 아니라 주문서를 구하는 방법이고, 실제 조회는 사용하는 순간에 일어난다. 이 구조가 뒤에서 request 스코프를 다룰 때 그대로 다시 쓰인다.

    웹 스코프 — 저장소가 요청·세션·서블릿 컨텍스트가 된다

    프로토타입은 "보관하지 않는다"는 극단이었다. 웹 스코프는 그 사이를 채운다. 컨테이너가 닫힐 때까지는 아니지만, 정해진 범위가 끝날 때까지는 같은 객체를 유지한다. 범위의 기준이 웹의 단위들이다.

    • request: HTTP 요청 하나가 들어와 응답이 끝날 때까지. 요청마다 별도의 객체가 만들어지고, 요청 처리가 끝나면 그 객체는 버려진다.
    • session: HTTP 세션 하나가 유지되는 동안. 같은 세션에 속한 여러 요청이 같은 객체를 본다. 세션이 폐기되면 객체도 버려진다.
    • application: 서블릿 컨텍스트 하나가 유지되는 동안. 레퍼런스는 이것이 싱글톤과 비슷하지만 스프링 컨테이너 단위가 아니라 서블릿 컨텍스트 단위로 하나이고, 서블릿 컨텍스트의 속성으로 노출된다는 점이 다르다고 설명한다.
    • websocket: 웹소켓 하나의 생명주기 동안.

    프로토타입과 결정적으로 다른 점은 끝이 관리된다는 것이다. 앞에서 본 registerDisposableBeanIfNecessary의 else 갈래가 이 스코프들의 것이다. 소멸 콜백이 해당 Scope 구현에 등록되므로, 범위가 끝날 때 @PreDestroy가 호출된다. 뒤의 request 스코프 예제에서 이것을 출력으로 확인한다.

    웹 환경이 아니면 스코프 자체가 없다

    이 스코프들은 이름만 적는다고 쓸 수 있는 것이 아니다. 지금까지 써 온 AnnotationConfigApplicationContext에 @Scope("request") 빈을 등록하고 조회하면 다음 예외가 난다.

    java.lang.IllegalStateException: No Scope registered for scope name 'request'

    메시지는 앞에서 본 doGetBean의 셋째 갈래에서 나온 것이다. 컨테이너의 scopes 맵에 "request"라는 이름으로 등록된 Scope 객체가 없다. 이 맵을 채우는 것은 웹 환경용 컨테이너다. 웹용 ApplicationContext는 준비 단계에서 "request"에 RequestScope를, "session"에 SessionScope를, 서블릿 컨텍스트가 있으면 "application"에 ServletContextScope를 등록한다. 스프링 부트는 클래스패스에 스프링 MVC가 있으면 서블릿 웹 환경용 컨테이너를 만들기 때문에, 웹 스타터를 넣은 프로젝트에서는 별도 설정 없이 이 스코프들을 쓸 수 있다.

    Scope 인터페이스 — 저장소를 갈아 끼우는 자리

    셋째 갈래가 부르는 Scope는 메서드 다섯 개짜리 인터페이스다. Javadoc은 이것을 빈 인스턴스를 담아 둘 대상 스코프를 나타내는 전략 인터페이스라고 설명한다. 핵심은 두 메서드다.

    public interface Scope {
    // name으로 저장소를 찾아보고, 없으면 objectFactory로 만들어 저장한 뒤 돌려준다
    Object get(String name, ObjectFactory objectFactory);

    // 이 스코프의 객체가 소멸될 때 실행할 콜백을 등록한다
    void registerDestructionCallback(String name, Runnable callback);

    // 그 밖에 remove, resolveContextualObject, getConversationId가 있다
}

    컨테이너는 "만드는 방법"(objectFactory, 안에서 createBean을 부른다)만 건네고 저장소가 무엇인지는 모른다. HTTP 요청의 속성일 수도, 세션의 속성일 수도, 직접 만든 맵일 수도 있다. 그래서 스코프는 직접 만들어 registerScope로 등록할 수도 있다. 스프링에도 스레드마다 객체를 하나씩 두는 SimpleThreadScope가 들어 있는데, 기본으로는 등록되어 있지 않다.

    싱글톤과 프로토타입은 이 인터페이스로 구현되어 있지 않다. 앞의 분기에서 보았듯 두 스코프는 컨테이너 코드에 직접 들어 있는 갈래다. registerScope에 "singleton"이나 "prototype"이라는 이름을 주면 "Cannot replace existing scopes 'singleton' and 'prototype'"이라는 메시지와 함께 IllegalArgumentException이 난다.

    손으로 만드는 request 스코프 — 스레드에 묶인 저장소

    RequestScope의 get은 "현재 HTTP 요청"을 저장소로 쓴다고 했다. 그런데 이 메서드의 매개변수에는 요청 객체가 없다. 빈 이름과 만드는 방법뿐이다. 싱글톤인 Scope 객체 하나가 동시에 들어온 수십 개의 요청 가운데 "지금 이 호출이 속한 요청"을 어떻게 알아내는가. 스프링 코드를 보기 전에 같은 문제를 순수 자바로 풀어 보자.

    실마리는 스레드다. 스프링 입문 03회에서 본 것처럼 서블릿 컨테이너는 요청 하나를 스레드 하나에 맡긴다. 컨트롤러가 서비스를 부르고 서비스가 리포지토리를 부르는 동안 호출은 모두 그 스레드의 스택 위에 프레임으로 쌓인다. 요청 하나를 처리하는 코드는 깊이 들어가든 얕게 있든 같은 스레드에서 실행된다. 그러니 "현재 요청"을 알고 싶으면 "현재 스레드"에 물어보면 된다.

    스레드에 값을 붙여 두는 표준 도구가 ThreadLocal이다. Javadoc의 설명대로, 이 변수에 접근하는 스레드는 저마다 독립적으로 초기화된 자기만의 사본을 갖는다. 구현을 보면 이유가 분명하다. OpenJDK 21의 Thread 클래스에는 threadLocals라는 맵 필드가 있고, ThreadLocal.get()은 현재 스레드 객체를 구한 다음 그 스레드의 threadLocals 맵에서 자기 자신(ThreadLocal 객체)을 키로 값을 꺼낸다. 값이 ThreadLocal 객체 안이 아니라 각 스레드 객체 안에 들어 있으므로, 같은 ThreadLocal에 물어도 스레드가 다르면 다른 값이 나온다.

      static ThreadLocal CURRENT  (프로그램 전체에 하나. 값은 없고 "키" 역할만 한다)

  Thread "exec-1" 객체                         Thread "exec-2" 객체
  ┌───────────────────────────────┐            ┌───────────────────────────────┐
  │ threadLocals (맵)             │            │ threadLocals (맵)             │
  │   CURRENT ─▶ { "trace" ─▶ ● } │            │   CURRENT ─▶ { "trace" ─▶ ○ } │
  └───────────────────────────────┘            └───────────────────────────────┘
               ●  RealTrace(req-1)                          ○  RealTrace(req-2)

  CURRENT.get()을 exec-1이 부르면 왼쪽 맵을, exec-2가 부르면 오른쪽 맵을 본다.

    이 도구로 요청 스코프의 세 부품을 만든다. 요청이 시작될 때 빈 저장소를 스레드에 묶고 끝날 때 푸는 코드, 저장소에서 이름으로 객체를 찾되 없으면 만들어 넣는 코드, 그리고 싱글톤에 주입될 프록시다. 프록시(proxy)는 진짜 객체와 같은 인터페이스를 가지면서, 호출을 받으면 진짜 객체를 찾아 일을 넘기는 대리 객체다.

    import java.util.HashMap;
import java.util.Map;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.function.Supplier;

public class HandMadeRequestScope {

    interface Trace {
        void log(String message);
    }

    static class RealTrace implements Trace {
        private static final AtomicInteger SEQ = new AtomicInteger();
        private final String id = "req-" + SEQ.incrementAndGet();

        RealTrace() {
            System.out.println("  new RealTrace: " + id + " on " + Thread.currentThread().getName());
        }

        @Override
        public void log(String message) {
            System.out.println("[" + id + "] " + message);
        }
    }

    // 스코프: 객체를 이름으로 찾되, 저장소는 "지금 이 스레드에 묶인 요청"의 것이다.
    static class RequestScope {
        private static final ThreadLocal> CURRENT = new ThreadLocal<>();

        static void begin() { CURRENT.set(new HashMap<>()); }   // 요청 시작: 빈 저장소를 스레드에 묶는다
        static void end()   { CURRENT.remove(); }               // 요청 끝: 묶음을 푼다

        static Object get(String name, Supplier
