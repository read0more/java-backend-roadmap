    이 회차의 질문: 설정 클래스 한 장이 어떻게 객체 그래프가 되는가

    스프링 입문 권에서 컨테이너와 빈이라는 낱말을 한 번 실물에 붙여 보았다. 이 권의 01회와 02회에서는 역할과 구현을 나누고, 구현을 고르는 책임을 그것을 사용하는 코드 밖으로 빼내는 설계를 다뤘다. 그렇게 하고 나면 애플리케이션에는 "무엇을 만들어 어떻게 이을지"만 적은 설정 클래스가 하나 남는다. 이 회차는 그 설정 클래스를 스프링 컨테이너에 넘긴 다음에 일어나는 일을 다룬다.

    겉으로 보이는 코드는 두 줄이다. 컨테이너를 만들고, 빈을 꺼낸다. 이 두 줄을 외우면 예제는 돌아간다. 그런데 실무에서 마주치는 문제는 그 두 줄 사이에서 생긴다. 애플리케이션이 뜨다가 NoUniqueBeanDefinitionException으로 멈춘다. 분명히 등록했다고 생각한 빈을 컨테이너가 못 찾는다. 이런 메시지를 읽으려면 컨테이너가 무엇을 어떤 순서로 하는지, 조회 요청을 무엇과 비교하는지를 알아야 한다.

    그래서 이 회차는 API 목록을 외우는 대신 다음 질문의 답을 따라간다. 컨테이너의 생성자 안에서는 어떤 일이 어떤 순서로 일어나는가. 컨테이너는 빈을 어디에, 어떤 자료구조로 들고 있는가. 이름으로 찾는 것과 타입으로 찾는 것은 내부에서 같은 연산인가. BeanFactory와 ApplicationContext는 무엇이 다른가. 자바 코드와 XML이라는 전혀 다른 형식의 설정이 어떻게 같은 컨테이너에서 돌아가는가.

    이 회차의 실행 결과, 예외 메시지, 스택 트레이스는 원고를 쓰면서 JDK 21.0.13과 스프링 프레임워크 7.0.10(spring-context와 그 의존 라이브러리, jakarta.annotation-api 3.0.0)에서 직접 돌려 얻은 것이다. 본문이 근거로 삼는 규칙(refresh()의 단계, 빈 팩토리의 필드와 타입 조회 방식, 기능 비교표, BeanDefinition의 속성)은 이 강좌의 기준 버전인 스프링 프레임워크 6.2의 레퍼런스 문서, Javadoc, 소스에서 같은 내용을 따로 확인했다. 스택 트레이스의 줄 번호와 toString() 출력 형식처럼 버전에 따라 달라질 수 있는 곳은 본문에서 밝힌다.

    실험에 쓸 코드

    예제는 알림 발송이다. 템플릿 저장소에서 문구를 찾아 발송기로 보낸다. 역할을 나타내는 인터페이스가 둘, 구현 클래스가 셋, 두 역할을 사용하는 서비스가 하나다. 객체가 언제 만들어지는지 눈으로 보려고 생성자마다 출력을 한 줄씩 넣었다. 지면을 줄이려고 한 파일에 모았고 모두 notify 패키지에 있다.

    package notify;

interface MessageSender {
    void send(String to, String text);
}

class EmailSender implements MessageSender {
    EmailSender() { System.out.println("  [생성] EmailSender"); }
    public void send(String to, String text) { System.out.println("email -> " + to + ": " + text); }
}

class SmsSender implements MessageSender {
    SmsSender() { System.out.println("  [생성] SmsSender"); }
    public void send(String to, String text) { System.out.println("sms -> " + to + ": " + text); }
}

interface TemplateRepository {
    String find(String code);
}

class MemoryTemplateRepository implements TemplateRepository {
    MemoryTemplateRepository() { System.out.println("  [생성] MemoryTemplateRepository"); }
    public String find(String code) { return "[" + code + "] 안내"; }
}

class NotificationService {
    private final TemplateRepository templates;
    private final MessageSender sender;

    NotificationService(TemplateRepository templates, MessageSender sender) {
        System.out.println("  [생성] NotificationService");
        this.templates = templates;
        this.sender = sender;
    }

    void deliver(String to, String code) { sender.send(to, templates.find(code)); }
}

    설정 클래스는 세 객체를 만드는 메서드를 하나씩 가진다. notificationService()는 본문에서 나머지 두 메서드를 직접 불러 의존 객체를 얻는다. 메서드가 불리는 시점을 보려고 여기에도 출력을 넣었다.

    package notify;

import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class NotifyConfig {

    @Bean
    public NotificationService notificationService() {
        System.out.println(" @Bean notificationService() 호출");
        return new NotificationService(templateRepository(), messageSender());
    }

    @Bean
    public TemplateRepository templateRepository() {
        System.out.println(" @Bean templateRepository() 호출");
        return new MemoryTemplateRepository();
    }

    @Bean
    public MessageSender messageSender() {
        System.out.println(" @Bean messageSender() 호출");
        return new EmailSender();
    }
}

    스프링 컨테이너 생성: 생성자 한 줄이 하는 일

    스프링 컨테이너(Spring container)는 빈을 만들고, 설정하고, 서로 이어 주는 객체다. 레퍼런스 문서는 org.springframework.context.ApplicationContext 인터페이스가 스프링 IoC 컨테이너를 나타내며 빈의 인스턴스화, 설정, 조립을 책임진다고 적는다. 컨테이너는 무엇을 만들어야 하는지를 설정 메타데이터(configuration metadata)를 읽어서 안다. 같은 문서에 따르면 설정 메타데이터는 애노테이션이 붙은 컴포넌트 클래스, 팩토리 메서드를 가진 설정 클래스, 외부 XML 파일, Groovy 스크립트로 표현할 수 있다.

    ApplicationContext는 인터페이스이므로 new로 만들 수 없다. 자바 설정 클래스를 읽는 구현이 AnnotationConfigApplicationContext다. 생성자에 설정 클래스의 Class 객체를 넘기면 컨테이너가 만들어진다.

    package notify;

import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class CreateMain {
    public static void main(String[] args) {
        System.out.println("1. 컨테이너 생성 시작");
        AnnotationConfigApplicationContext ac = new AnnotationConfigApplicationContext(NotifyConfig.class);
        System.out.println("2. 컨테이너 생성 끝");
        NotificationService service = ac.getBean("notificationService", NotificationService.class);
        System.out.println("3. 빈 조회 끝");
        service.deliver("kim", "WELCOME");
        ac.close();
    }
}

    두 번째 사실은 호출 순서다. notificationService()가 가장 먼저 불렸고, 그 본문이 templateRepository()와 messageSender()를 부르면서 두 의존 객체가 먼저 완성됐다. NotificationService는 두 인자가 준비된 뒤 마지막에 만들어졌다. 자바에서 메서드 호출의 인자는 호출보다 먼저 평가되므로 당연한 순서다.

    세 번째 사실은 눈에 보이지 않는 쪽에 있다. templateRepository() 호출 줄은 한 번만 찍혔다. 설정 클래스에는 templateRepository라는 빈도 따로 선언되어 있으니, 컨테이너가 그 빈을 만들 차례에 메서드를 한 번 더 불렀다면 줄이 두 번 나왔어야 한다. 그렇게 되지 않았다. 빈 하나는 한 번만 만들어지고, 이미 만들어진 것은 재사용된다. 이 동작을 만드는 장치는 04회의 주제이므로 여기서는 결과만 기억해 둔다.

    생성자를 세 조각으로 나눈다

    AnnotationConfigApplicationContext(Class... componentClasses) 생성자의 본문은 세 줄이다. this(), register(componentClasses), refresh(). 첫 줄의 인자 없는 생성자는 AnnotatedBeanDefinitionReader와 ClassPathBeanDefinitionScanner를 만든다. 앞의 것은 클래스를 받아 빈 정의로 등록하는 도구이고, 뒤의 것은 패키지를 훑어 컴포넌트를 찾는 도구다(05회). 이 세 호출을 직접 나눠 부르면서 그 사이에 정의의 수와 만들어진 싱글톤의 수를 세어 보자.

    package notify;

import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class PhaseMain {
    public static void main(String[] args) {
        AnnotationConfigApplicationContext ac = new AnnotationConfigApplicationContext();
        System.out.println("기본 생성자 직후: 정의 " + ac.getBeanDefinitionCount()
                + ", 싱글톤 " + ac.getBeanFactory().getSingletonCount());
        ac.register(NotifyConfig.class);
        System.out.println("register 직후: 정의 " + ac.getBeanDefinitionCount()
                + ", 싱글톤 " + ac.getBeanFactory().getSingletonCount());
        ac.refresh();
        System.out.println("refresh 직후: 정의 " + ac.getBeanDefinitionCount()
                + ", 싱글톤 " + ac.getBeanFactory().getSingletonCount());
        ac.close();
    }
}

    refresh()가 끝나면 정의는 9개, 싱글톤은 17개가 된다. 정의 3개가 늘었으니 @Bean 메서드 셋이 발견되어 등록된 것이고, 싱글톤이 0에서 17로 늘었으니 객체가 만들어진 것이다. 정의를 더 찾아내는 일과 객체를 만드는 일이 모두 refresh() 안에서 일어난다.

    여기서 이 회차 전체에 걸쳐 쓰일 구분이 나온다. 컨테이너가 다루는 것은 두 종류다. 하나는 빈 정의(bean definition), 곧 "이런 빈을 이렇게 만들라"는 설계도다. 다른 하나는 빈 인스턴스, 곧 그 설계도로 만든 실제 객체다. 위 출력에서 보듯 둘의 개수는 따로 움직인다.

    이 장의 핵심

    스프링 컨테이너는 설정을 읽어 곧바로 객체를 만들지 않는다. 먼저 모든 설정을 빈 정의라는 한 가지 형태의 설계도로 바꿔 등록하고, 설계도가 다 모인 뒤에 그것을 보고 인스턴스를 만든다. 조회, 중복 오류, 설정 형식의 다양성은 모두 이 두 단계 구조에서 설명된다.

    refresh()를 단계로 읽는다

    refresh()는 AbstractApplicationContext에 있는 메서드이고, 자바 설정용 컨텍스트든 XML용 컨텍스트든 같은 코드를 쓴다. 소스에서 이 메서드가 부르는 메서드를 순서대로 옮기면 다음과 같다. 6.2와 7.0의 소스에서 순서가 같다.

    열두 단계를 다 외울 필요는 없다. 5번과 11번, 두 곳만 붙잡으면 된다. 5번에서 빈 정의가 모두 모이고, 11번에서 그 정의로 인스턴스가 만들어진다. 앞 절의 출력에서 정의가 6에서 9로 늘어난 곳이 5번이고, [생성] 줄이 찍힌 곳이 11번이다.

    증거: 싱글톤이 등록된 순서

    이 순서를 소스를 읽지 않고도 확인할 방법이 있다. 빈 팩토리는 싱글톤의 이름을 등록된 순서대로 기억하고, getSingletonNames()로 그 순서를 돌려준다. 컨테이너를 만든 뒤 이것을 번호와 함께 출력한다.

int i = 1;
for (String name : ac.getBeanFactory().getSingletonNames()) {
    System.out.println(i++ + " " + name);
}

    5단계: 설정 클래스가 빈 정의로 풀린다

    5단계의 주인공은 목록 5번의 빈, ConfigurationClassPostProcessor다. 이 클래스는 BeanDefinitionRegistryPostProcessor를 구현한다. 이름 그대로 빈 정의 레지스트리가 준비된 뒤, 일반 빈이 만들어지기 전에 불려서 정의를 더 등록할 수 있는 후처리기다. 우리가 정의한 어떤 빈보다도 먼저 인스턴스가 만들어지는 이유가 여기에 있다.

    이 후처리기는 레지스트리에 이미 들어 있는 정의 가운데 설정 클래스를 찾는다. 지금은 notifyConfig 하나다. 그 클래스의 메타데이터를 분석해 @Bean이 붙은 메서드마다 빈 정의를 하나씩 만들어 등록한다. 빈의 이름은 메서드 이름이다. 이때 메서드를 호출하지는 않는다. 정의에는 "notifyConfig 빈의 notificationService 메서드를 부르면 이 빈이 나온다"는 정보만 들어간다. 이 정보가 실제로 어떤 필드에 담기는지는 BeanDefinition을 다루는 절에서 출력해 본다.

    11단계: 정의 목록을 돌며 getBean을 부른다

    11단계의 끝에서 빈 팩토리의 preInstantiateSingletons()가 불린다. 이 메서드는 빈 정의의 이름 목록을 복사한 다음 앞에서부터 돌면서, 추상 정의가 아니고 싱글톤이며 지연 초기화가 아닌 빈마다 getBean(이름)을 부른다. 이름 목록은 등록된 순서를 유지하는 리스트이므로, 생성도 기본적으로 등록 순서를 따른다.

    다만 어떤 빈을 만드는 도중에 다른 빈이 필요해지면 그 빈의 생성이 사이에 끼어든다. 실험에서 루프는 notifyConfig를 만들고 이어서 notificationService를 만들려 했다. 그 팩토리 메서드가 실행되는 동안 templateRepository와 messageSender가 먼저 완성되어 싱글톤 저장소에 들어갔다. 나중에 루프가 templateRepository의 차례에 도달했을 때는 저장소에 이미 객체가 있으므로 곧바로 돌아온다.

    단계가 둘로 나뉘어 있어서 얻는 것이 두 가지 있다. 첫째, 정의가 전부 모인 뒤에 인스턴스를 만들기 때문에 설정 클래스에서 메서드를 어떤 순서로 적든 의존관계가 풀린다. 둘째, 인스턴스를 만들기 전에 정의를 읽고 고칠 틈이 생긴다. 빈 팩토리 후처리기(BeanFactoryPostProcessor)가 바로 그 틈에서 일하는 확장 지점이다.

    자바 설정에서는 객체 생성과 의존관계 연결이 한 문장에서 일어난다. new NotificationService(templateRepository(), messageSender())는 생성자를 부르면서 동시에 의존 객체를 넘긴다. XML이나 컴포넌트 스캔처럼 컨테이너가 직접 생성자를 고르는 방식에서도 생성자 주입이라면 마찬가지로, 컨테이너가 인자로 넣을 빈을 먼저 준비한 뒤 생성자를 한 번 호출한다. 생성 뒤에 따로 일어나는 주입(세터, 필드)은 06회에서 다룬다.
    설정 클래스가 먼저 빈 정의(설계도)로 바뀌어 한곳에 모이고, 그다음에 정의를 보고 인스턴스가 만들어진다는 두 단계 구조를 한눈에 보여 준다. 왼쪽에서 오른쪽으로 흐르는 깔끔한 순서도. 맨 왼쪽에 문서 모양 아이콘 하나, 라벨 "설정 클래스". 가운데에 넓은 상자, 제목 "1단계: 빈 정의 등록". 그 안에 설계도(청사진) 모양 카드 네 장이 세로로 쌓여 있고 카드마다 라벨 "notifyConfig", "notificationService", "templateRepository", "messageSender". 문서 아이콘에서 가운데 상자로 화살표, 화살표 위 라벨 "분석". 오른쪽에 또 하나의 넓은 상자, 제목 "2단계: 인스턴스 생성". 그 안에 둥근 객체 세 개가 있고, 위쪽 객체에서 아래 두 객체로 참조 화살표가 뻗어 있다. 가운데 상자에서 오른쪽 상자로 굵은 화살표, 화살표 위 라벨 "정의마다 getBean". 두 상자 아래를 가로지르는 긴 괄호 하나, 라벨 "refresh()". 색은 설계도 쪽은 파란 계열, 객체 쪽은 주황 계열로 구분. 흰 배경, 평면 벡터 스타일, 장식 없음. 정의가 다 모인 뒤에 인스턴스를 만든다. 두 단계는 모두 refresh() 안에서 일어난다.

    실패했을 때의 동작도 이 메서드에 적혀 있다. 4단계부터 12단계 사이에서 예외가 나면 refresh()는 이미 만든 싱글톤을 파괴하고, 활성 플래그를 되돌린 다음 예외를 다시 던진다. 빈이 절반만 만들어진 컨테이너가 쓸 수 있는 상태로 남는 일은 없다. 그리고 GenericApplicationContext 계열은 refresh()를 한 번만 허용한다. 두 번째로 부르면 IllegalStateException이 나고, close()한 뒤에 getBean을 불러도 "has been closed already"라는 IllegalStateException이 난다.

    스레드 관점도 짚어 둔다. refresh()는 그것을 부른 스레드에서 실행된다. 6.2의 소스는 시작과 종료를 직렬화하는 락(startupShutdownLock)을 잡은 채 열두 단계를 진행한다. 이 회차의 실험에서 모든 [생성] 줄은 main 스레드가 찍은 것이다. 6.2에는 표시한 빈을 별도 스레드에서 초기화하는 선택 기능이 추가되었지만, 따로 설정하지 않으면 호출 스레드가 차례대로 만든다.

    객체는 실제로 어떻게 만들어지는가: 호출 스택으로 본 경로

    여기서 세 가지를 읽어 낼 수 있다. 첫째, 컨테이너가 빈을 미리 만드는 일도 결국 getBean 호출이다. 우리가 부르는 getBean과 같은 메서드이고, 누가 먼저 부르느냐만 다르다. getSingleton은 저장소에 그 이름의 객체가 없으면 넘겨받은 팩토리(스택의 lambda$doGetBean$0)를 실행해 객체를 만들고 저장소에 넣는다. 다음 호출부터는 저장소에서 꺼내기만 한다.

    둘째, @Bean 메서드는 리플렉션(reflection)으로 호출된다. 리플렉션은 실행 중에 Class, Method, Constructor 같은 객체로 클래스의 구성 요소를 얻어 다루는 자바의 기능이다. 스택 가운데의 java.lang.reflect.Method.invoke가 그것이다. 빈 정의에는 팩토리 메서드의 이름이 문자열로 들어 있고, 컨테이너는 그 이름에 해당하는 Method 객체를 찾아 설정 빈 인스턴스를 대상으로 invoke한다.     셋째, invoke의 대상은 TraceConfig가 아니라 TraceConfig$$SpringCGLIB$$0이라는 클래스의 traced()다. 이 클래스가 중간에서 호출을 받아 원래 메서드로 넘긴다. 앞에서 templateRepository()가 한 번만 호출된 것과 관계가 있는 장치이고, 04회에서 다룬다.

    클래스를 직접 지정한 빈 정의라면 경로의 끝이 다르다. 팩토리 메서드가 없으므로 컨테이너가 생성자를 골라 BeanUtils.instantiateClass로 호출하고, 그 안에서 Constructor.newInstance가 불린다. 어느 쪽이든 프레임워크의 코드에 우리 클래스를 향한 new가 컴파일되어 들어 있는 것이 아니다. 실행 중에 메서드나 생성자의 메타데이터를 얻어 호출한다. 컨테이너가 처음 보는 클래스의 객체를 만들 수 있는 것은 이 때문이다.

    컨테이너는 JVM 입장에서 특별한 존재가 아니다. 힙에 있는 평범한 객체이고, 필드로 맵과 리스트를 들고 있다. 6.2와 7.0의 소스에서 필드 선언을 확인하면 구조는 다음과 같다.

    컨테이너가 힙의 평범한 객체이며, 이름으로 설계도를 찾는 맵과 이름으로 완성된 객체를 찾는 맵을 따로 가진다는 것을 보여 준다. 메모리 구조도. 왼쪽에 좁은 세로 상자, 제목 "스택", 그 안에 칸 하나, 라벨 "ac". 오른쪽에 큰 영역, 제목 "힙". 힙 안 위쪽에 상자 하나, 라벨 "ApplicationContext". 스택의 "ac" 칸에서 이 상자로 화살표. 그 상자에서 아래의 더 큰 상자로 화살표, 큰 상자의 라벨 "DefaultListableBeanFactory". 큰 상자 안에 표 모양 두 개가 나란히 있다. 왼쪽 표 제목 "빈 정의 맵", 행 세 개에 "notificationService", "templateRepository", "messageSender"가 적혀 있고 각 행 오른쪽에 작은 설계도 아이콘. 오른쪽 표 제목 "싱글톤 저장소", 같은 세 이름이 적힌 행 세 개, 각 행에서 힙의 오른쪽 아래에 있는 둥근 객체 세 개로 화살표. 맨 위 객체에서 나머지 두 객체로 점선 화살표 두 개, 라벨 "참조". 흰 배경, 평면 벡터 스타일, 설계도는 파란색, 객체는 주황색. 이름 하나에 설계도 하나와 객체 하나가 대응한다. 주입된 필드와 저장소는 같은 객체를 가리킨다.

    컨테이너에 등록된 모든 빈 조회

    컨테이너에 무엇이 들어 있는지 전부 꺼내 보자. getBeanDefinitionNames()는 등록된 빈 정의의 이름을 배열로 돌려준다. 이름마다 정의를 얻어 역할(role) 값을 찍고, 인스턴스의 클래스 이름도 함께 찍는다. 이어서 정의의 수와 싱글톤의 수를 비교하고, 정의 없이 들어 있는 싱글톤을 골라낸다.

    package notify;

import org.springframework.beans.factory.config.BeanDefinition;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class ListMain {
    public static void main(String[] args) {
        AnnotationConfigApplicationContext ac = new AnnotationConfigApplicationContext(NotifyConfig.class);
        for (String name : ac.getBeanDefinitionNames()) {
            BeanDefinition bd = ac.getBeanDefinition(name);
            Object bean = ac.getBean(name);
            System.out.println("role=" + bd.getRole() + " " + name + " -> " + bean.getClass().getSimpleName());
        }
        System.out.println("정의 수 = " + ac.getBeanDefinitionCount());
        System.out.println("싱글톤 수 = " + ac.getBeanFactory().getSingletonCount());
        for (String name : ac.getBeanFactory().getSingletonNames()) {
            if (!ac.containsBeanDefinition(name)) {
                System.out.println("정의 없는 싱글톤: " + name);
            }
        }
        ac.close();
    }
}

    역할 값과 내부 빈

    BeanDefinition에는 역할을 나타내는 정수 힌트가 있다. Javadoc의 설명을 옮기면 ROLE_APPLICATION(0)은 애플리케이션의 주요 부분으로 보통 사용자가 정의한 빈이고, ROLE_SUPPORT(1)는 더 큰 설정의 보조 부분이며, ROLE_INFRASTRUCTURE(2)는 최종 사용자와 무관하게 전적으로 뒤에서 일하는 빈이다. 내가 등록한 빈만 보고 싶으면 bd.getRole() == BeanDefinition.ROLE_APPLICATION인 것만 고르면 된다.

    역할 값이 2인 다섯 개는 리더가 만들어질 때 등록된 내부 빈이다. 기본 생성자 직후에 정의가 이미 5개였던 이유가 이것이다. 각각이 하는 일은 다음과 같다.

    빈 이름의 끝부분클래스맡은 일
    internalConfigurationAnnotationProcessorConfigurationClassPostProcessor@Configuration 클래스를 분석해 @Bean 메서드 등을 빈 정의로 등록한다
    internalAutowiredAnnotationProcessorAutowiredAnnotationBeanPostProcessor@Autowired, @Value가 붙은 곳에 의존관계와 값을 넣는다
    internalCommonAnnotationProcessorCommonAnnotationBeanPostProcessor@PostConstruct, @PreDestroy, @Resource를 처리한다

    internalEventListenerFactoryDefaultEventListenerFactory위 처리기가 리스너 객체를 만들 때 쓰는 기본 팩토리다

    이 표가 말해 주는 것은 애노테이션이 스스로 동작하지 않는다는 사실이다. 애노테이션은 클래스 파일에 기록된 메타데이터일 뿐이고, 그것을 읽어 일을 하는 코드가 따로 있어야 한다. 스프링에서는 그 코드가 빈으로 등록되어 있다. 컨테이너의 기능 상당 부분이 컨테이너 자신이 관리하는 빈으로 구현되어 있는 셈이다. 이 점은 뒤에서 BeanFactory와 ApplicationContext를 비교할 때 결정적인 차이로 다시 나온다.

    내부 빈의 수는 클래스패스에 따라 달라진다. 7.0.10의 소스를 보면 CommonAnnotationBeanPostProcessor는 jakarta.annotation.PostConstruct 클래스가 클래스패스에 있을 때만 등록되고, JPA API와 스프링의 ORM 모듈이 함께 있으면 영속성 애노테이션 처리기가 하나 더 등록된다. jakarta.annotation-api를 뺀 클래스패스에서 같은 프로그램을 돌리면 내부 빈은 4개, 정의는 8개가 나온다.

    정의 없이 들어온 싱글톤

    정의는 9개인데 싱글톤은 17개다. 차이 나는 8개가 "정의 없는 싱글톤"으로 찍힌 것들이다. 이들은 컨테이너가 refresh() 도중에 이미 만들어진 객체를 registerSingleton(이름, 객체)로 저장소에 직접 넣은 것이다. 만드는 방법을 설명할 필요가 없으니 설계도가 없다. 앞에서 본 싱글톤 등록 순서의 1~4번, 6번, 11번, 12번, 17번이 여기에 해당한다.

    그래서 조회 방법에 따라 보이는 범위가 다르다. getBeanDefinitionNames()는 설계도의 이름만 돌려주므로 environment는 나오지 않는다. 하지만 getBean("environment")는 성공한다. 이름 조회는 싱글톤 저장소를 보기 때문이다. containsBeanDefinition("environment")는 false이고 containsBean("environment")는 true다. 타입으로 조회할 때도 이 객체들은 후보에 들어간다. 뒤에서 Object 타입으로 전부 조회하면 정의의 수보다 많은 결과가 나오는 것을 볼 것이다.

    레퍼런스 문서도 이 두 가지 등록 경로를 언급한다. DefaultListableBeanFactory가 registerSingleton(..)과 registerBeanDefinition(..)을 지원하지만, 일반적인 애플리케이션은 빈 정의 메타데이터로 정의된 빈만 다룬다고 적는다. 우리가 쓰는 경로는 설계도를 등록하는 쪽이고, 완성품을 직접 넣는 쪽은 주로 프레임워크가 쓴다.

    빈 이름은 어디서 오는가

    @Bean 메서드로 등록한 빈의 이름은 기본적으로 메서드 이름이다. @Bean(name = "...")으로 바꿀 수 있다. register()로 넘긴 클래스의 이름은 단순 클래스 이름의 첫 글자를 소문자로 바꾼 것이다. NotifyConfig가 notifyConfig가 된 것이 그 결과다. 레퍼런스는 이 규칙이 java.beans.Introspector.decapitalize와 같다고 설명한다. 따라서 첫 두 글자가 모두 대문자인 이름은 바뀌지 않는다. Introspector.decapitalize("SMSSender")를 실행하면 SMSSender가 그대로 나온다.

    이름은 beanDefinitionMap과 singletonObjects의 키다. 그러므로 이름 하나는 컨테이너 안에서 빈 하나만 가리킨다. 같은 이름이 두 번 등록되려 할 때의 처리는 컴포넌트 스캔과 함께 05회에서 다룬다.

    스프링 빈 조회 - 기본: 이름으로 찾기와 타입으로 찾기

    빈을 꺼내는 기본 메서드는 getBean이고, 인자의 조합이 세 가지다. 이름만 주는 것, 이름과 타입을 함께 주는 것, 타입만 주는 것. 같은 빈을 네 가지 방법으로 꺼내 같은 객체인지 비교하고, 실패하는 조회 세 가지의 예외도 함께 본다.

    package notify;

import org.springframework.beans.BeansException;
import org.springframework.context.annotation.AnnotationConfigApplicationContext;

public class LookupMain {
    public static void main(String[] args) {
        AnnotationConfigApplicationContext ac = new AnnotationConfigApplicationContext(NotifyConfig.class);

        Object byName = ac.getBean("templateRepository");
        TemplateRepository byNameAndType = ac.getBean("templateRepository", TemplateRepository.class);
        TemplateRepository byType = ac.getBean(TemplateRepository.class);

        System.out.println(byNameAndType == byType);
        System.out.println(byType == byImplType);
        System.out.println(ac.getType("templateRepository"));

        show(() -> ac.getBean(SmsSender.class));
        show(() -> ac.getBean("templateRepository", MessageSender.class));
        ac.close();
    }

    static void show(Runnable lookup) {
        try {
            lookup.run();
        } catch (BeansException e) {
            System.out.println(e.getClass().getSimpleName() + ": " + e.getMessage());
        }
    }
}

    이름 조회: 해시 맵에서 한 번 꺼낸다

    ac.getBean("templateRepository")의 경로를 따라가 보자. AbstractApplicationContext.getBean(String)의 본문은 두 줄이다. 컨텍스트가 활성 상태인지 확인하고, getBeanFactory().getBean(name)으로 넘긴다. 빈 팩토리는 이름을 정리한 다음(별칭이면 원래 이름으로 바꾼다) 싱글톤 저장소에서 그 이름을 찾는다. 소스의 해당 줄은 this.singletonObjects.get(beanName)이고, 그 위에는 전체 싱글톤 락 없이 기존 인스턴스를 빠르게 확인한다는 주석이 달려 있다.

    singletonObjects는 ConcurrentHashMap이다. 따라서 이미 만들어진 싱글톤의 이름 조회는 해시 맵 조회 한 번이고, 빈이 몇 개 등록되어 있든 비용이 거의 같다. 락을 잡지 않으므로 여러 요청 스레드가 동시에 getBean을 불러도 서로를 기다리게 하지 않는다. 스프링 입문 권에서 리포지토리의 저장소로 썼던 바로 그 자료구조가 컨테이너의 한가운데에 있다.

    이름만 주는 getBean(String)의 반환 타입은 Object다. 호출하는 쪽이 캐스팅해야 하고, 틀리면 ClassCastException이 호출 지점에서 난다. 타입을 함께 주는 T getBean(String name, Class requiredType)은 Class 객체를 타입 정보로 받아 컨테이너가 대신 검사한다. 꺼낸 객체가 requiredType.isInstance(bean)을 통과하지 못하면 BeanNotOfRequiredTypeException을 던진다. 출력의 마지막 줄이 그 예외이고, 메시지에 기대한 타입과 실제 타입이 모두 적혀 있다. 제네릭의 타입 인자는 실행 중에 남지 않으므로(자바 중급 2편의 타입 소거) 실행 중에 검사하려면 이렇게 Class 객체를 값으로 넘겨야 한다.

    타입 조회: 정의 목록을 훑는다

    ac.getBean(TemplateRepository.class)에는 이름이 없다. 빈 팩토리는 먼저 그 타입에 맞는 빈의 이름을 구해야 한다. 이 일을 하는 doGetBeanNamesForType은 beanDefinitionNames 리스트를 처음부터 끝까지 돌면서 이름마다 "이 빈은 요청한 타입에 맞는가"를 검사한다. 그다음 정의 없이 등록된 싱글톤의 이름도 같은 방식으로 검사한다. 후보 이름이 하나면 그 이름으로 빈을 꺼내고, 하나도 없으면 NoSuchBeanDefinitionException을 던진다. 둘 이상인 경우는 뒤의 절에서 다룬다.

    이름 조회가 맵 조회 한 번이었던 것과 달리 타입 조회는 선형 탐색이다. 빈이 수백 개면 수백 번의 타입 검사가 필요하다. 그래서 빈 팩토리는 결과를 캐시한다. refresh()의 11단계에서 설정이 동결된 뒤에는, 타입별 조회 결과를 Class 객체를 키로 하는 맵(allBeanNamesByType, singletonBeanNamesByType)에 넣어 둔다. 같은 타입을 다시 조회하면 이 맵에서 이름 배열을 바로 꺼낸다. 새 싱글톤이 저장소에 추가되면, 그 객체가 속하는 타입의 캐시 항목은 지워진다.

    타입이 맞는지는 어떻게 검사할까. 이미 만들어진 싱글톤이라면 빈 팩토리는 저장소에서 인스턴스를 꺼내 요청한 타입의 인스턴스인지 확인한다. 자바의 instanceof와 같은 판정이다. 그래서 @Bean 메서드의 반환 타입을 TemplateRepository로 선언했는데도 getBean(MemoryTemplateRepository.class)가 성공했다. 기준은 선언이 아니라 만들어진 객체의 실제 클래스다. getType("templateRepository")가 인터페이스가 아니라 class notify.MemoryTemplateRepository를 돌려준 것도 같은 이유다.

    성공한다고 해서 그렇게 써도 된다는 뜻은 아니다. 구현 타입으로 조회하거나 주입받는 코드는 구현 클래스에 의존한다. 01회와 02회에서 구현을 바꿀 때 사용하는 쪽 코드가 함께 바뀌던 그 문제가 조회 코드에서 되살아난다. 조회와 주입은 역할 타입으로 한다.

    타입 예측: 아직 만들어지지 않은 빈의 타입은 어떻게 아는가

    앞 절에서 타입 검사는 인스턴스의 실제 클래스를 본다고 했다. 그러면 인스턴스가 아직 없는 빈은 어떻게 될까. 지연 초기화(lazy initialization)로 표시한 빈으로 실험한다. @Lazy가 붙은 빈은 preInstantiateSingletons()가 건너뛰므로, 컨테이너 생성이 끝난 뒤에도 인스턴스가 없다.

    // 두 파일을 이어 적었다. package와 import 문은 생략
@Configuration
public class LazyConfig {

    @Bean
    @Lazy
    public TemplateRepository templateRepository() {
        return new MemoryTemplateRepository();
    }
}

public class LazyMain {
    public static void main(String[] args) {
        AnnotationConfigApplicationContext ac = new AnnotationConfigApplicationContext(LazyConfig.class);
        System.out.println("컨테이너 생성 끝");
        System.out.println(ac.getType("templateRepository"));
        try {
            ac.getBean(MemoryTemplateRepository.class);
        } catch (NoSuchBeanDefinitionException e) {
            System.out.println(e.getMessage());
        }
        ac.getBean(TemplateRepository.class);
        System.out.println(ac.getType("templateRepository"));
        System.out.println(ac.getBean(MemoryTemplateRepository.class).getClass().getSimpleName());
        ac.close();
    }
}

    그래서 구현 타입으로 조회하면 후보가 없다. TemplateRepository는 MemoryTemplateRepository의 하위 타입이 아니므로, 예측된 타입으로는 요청을 만족시킬 수 없다. 이어서 인터페이스 타입으로 조회하면 후보가 하나 나오고, 그 순간 인스턴스가 만들어진다. 이제 저장소에 실제 객체가 있으므로 getType은 실제 클래스를 돌려주고, 구현 타입 조회도 성공한다. 첫 조회 때 비어 있던 캐시 항목은 싱글톤이 추가되면서 지워졌기 때문에 두 번째 조회는 다시 계산된 결과를 받는다.

    레퍼런스 문서는 이 동작을 직접 설명한다. @Bean 메서드를 인터페이스 반환 타입으로 선언하면 사전 타입 예측이 그 인터페이스로 제한되고, 전체 타입은 해당 싱글톤이 인스턴스화된 뒤에야 컨테이너에 알려진다고 한다. 지연 초기화가 아닌 싱글톤도 선언 순서대로 만들어지므로, 다른 컴포넌트가 선언되지 않은 타입으로 매칭을 시도하는 시점에 따라 결과가 달라질 수 있다고 덧붙인다. 그래서 여러 인터페이스를 구현하는 컴포넌트나 구현 타입으로 참조될 가능성이 있는 컴포넌트는 가능한 한 구체적인 반환 타입을 선언하는 편이 안전하다고 권한다.

    반대 방향의 실험도 해 보았다. 위 설정에서 메서드의 반환 타입만 MemoryTemplateRepository로 바꾸면, 컨테이너 생성 직후의 getType이 class notify.MemoryTemplateRepository를 돌려주고 첫 번째 구현 타입 조회가 바로 성공한다. 인터페이스 타입 조회도 같은 객체를 돌려준다. 선언 반환 타입이 구체적일수록 컨테이너가 미리 아는 것이 많아진다.

    정리하면 판단 기준은 둘이다. 그 빈을 참조하는 모든 곳이 일관되게 역할 인터페이스만 쓴다면 반환 타입을 인터페이스로 선언해도 문제가 없다. 구현 타입이나 그 빈이 구현한 다른 인터페이스로 참조하는 곳이 하나라도 있다면 반환 타입을 구체 클래스로 선언해야 시점에 따라 결과가 달라지는 일을 피할 수 있다.

    스프링 빈 조회 - 동일한 타입이 둘 이상

    역할 하나에 구현이 둘 등록되어 있으면 타입 조회는 어떻게 될까. 발송기 두 개를 모두 빈으로 등록하는 설정을 만든다. 두 메서드 모두 반환 타입은 역할 인터페이스 MessageSender다.

    // 두 파일을 이어 적었다. package와 import 문은 생략

    getBean(MessageSender.class)는 NoUniqueBeanDefinitionException으로 실패했다. 메시지를 읽으면 원인과 해결의 실마리가 다 들어 있다. 하나를 기대했는데 둘을 찾았고, 그 둘의 이름이 emailSender와 smsSender다. 예외 객체에서 getNumberOfBeansFound()와 getBeanNamesFound()로 같은 정보를 꺼낼 수도 있다.

    컨테이너가 아무거나 하나를 고르지 않고 실패하는 쪽을 택한 데에는 이유가 있다. "등록 순서로 첫 번째"를 돌려주는 규칙이었다고 해 보자. 누군가 설정 클래스에서 메서드의 순서를 바꾸거나 발송기를 하나 추가하는 순간, 오류 없이 다른 발송기가 선택된다. 이메일로 나가야 할 알림이 문자로 나가는 문제를 운영 중에 발견하게 된다. 실패는 시끄럽지만 시작 시점에 드러나고, 메시지가 후보를 알려 준다.

    이 예외의 상위 클래스는 NoSuchBeanDefinitionException이다. 그러므로 catch (NoSuchBeanDefinitionException e)는 빈이 없는 경우와 빈이 너무 많은 경우를 함께 잡는다. 두 경우를 구분해야 한다면 하위 타입을 먼저 잡아야 한다.

    조회하는 쪽에서 할 수 있는 일

    해결 방법은 무엇을 원하느냐에 따라 갈린다. 특정한 하나가 필요하면 이름을 함께 준다. getBean("smsSender", MessageSender.class)는 이름으로 저장소에서 꺼낸 뒤 타입만 확인하므로 후보가 여럿이라는 문제가 생기지 않는다. 이름은 컨테이너 안에서 유일하기 때문이다.

    전부가 필요하면 getBeansOfType을 쓴다. 빈 이름을 키로, 인스턴스를 값으로 하는 Map이 돌아온다. 이 실행에서 순서는 빈 정의가 등록된 순서와 같았다. 이름만 필요하면 getBeanNamesForType이 이름 배열을 돌려준다. 발송 채널을 설정값으로 고르거나, 모든 발송기에 같은 메시지를 보내는 식의 코드가 이 조회 위에서 만들어진다.

    빈 팩토리는 예외를 던지기 전에 몇 가지를 더 시도한다. 소스를 보면 후보가 여럿일 때 우선(primary)으로 표시된 후보를 찾고, 없으면 우선순위가 가장 높은 후보를 찾는다. 그래도 하나로 정해지지 않으면 예외다. 이 실험의 두 빈에는 그런 표시가 없으므로 곧바로 예외가 났다. 빈에 우선 표시나 한정자를 붙여 주입 대상을 정하는 방법은 의존관계 자동 주입을 다루는 06회의 몫이다.

    스프링 빈 조회 - 상속 관계

    규칙은 한 줄이다. 부모 타입으로 조회하면 자식 타입의 빈이 모두 후보가 된다. 앞 절의 실험이 이미 그 규칙을 보여 주었다. MessageSender로 조회했더니 그것을 구현한 EmailSender와 SmsSender의 빈이 둘 다 걸렸다.

    이유는 타입 검사가 instanceof 판정이기 때문이다. 자바에서 SmsSender의 인스턴스는 SmsSender이면서 MessageSender이고 Object다. 타입 계층의 어느 지점에서 물어도 "맞다"고 답한다. 컨테이너는 이름 목록을 돌며 이 질문을 빈마다 던질 뿐이다. 자바 기본편에서 배운 "부모 타입의 변수는 자식 인스턴스를 참조할 수 있다"는 규칙을, 저장소 검색에 그대로 적용한 것이다.

    표의 첫 두 줄처럼 자식 타입으로 조회하면 후보가 하나로 줄어든다. 실험의 ac.getBean(SmsSender.class) == sms가 true였다. 이름으로 꺼낸 것과 같은 객체다. 다만 앞에서 말했듯 구현 타입으로 조회하는 코드는 구현에 묶인다.

    맨 아래 줄이 흥미롭다. 모든 객체는 Object의 인스턴스이므로 Object 타입으로 조회하면 컨테이너에 든 빈이 전부 나온다. 실험에서 getBeansOfType(Object.class).size()는 16이었다. 이 컨테이너의 빈 정의는 8개다(내부 빈 5개, senderConfig, 발송기 2개). 나머지 8개는 앞에서 본 정의 없는 싱글톤이다. 타입 조회가 정의 목록에 이어 직접 등록된 싱글톤도 훑는다는 것을 숫자로 확인한 셈이다.

    "상속 관계"라고 부르지만 extends만 뜻하지 않는다. 이 예제의 관계는 전부 implements다. 클래스 상속이든 인터페이스 구현이든, 자바의 하위 타입 관계 전체가 타입 조회의 기준이다. 인터페이스를 여러 개 구현한 빈은 그 인터페이스 각각으로 조회될 수 있다.

    설계 쪽에서 보면 이 절과 앞 절은 같은 이야기의 두 면이다. 역할 인터페이스 아래에 구현이 하나뿐일 때는 타입만으로 빈이 정해진다. 구현을 추가하는 순간, 곧 확장에 열려 있다는 장점을 실제로 쓰는 순간, 타입만으로는 고를 수 없게 된다. 어느 구현을 쓸지에 대한 정보가 타입 바깥의 어딘가(이름, 우선 표시, 한정자)에 있어야 한다.

    부모 타입으로 조회하면 그 아래의 모든 빈이 후보가 되고, 자식 타입으로 조회하면 하나로 좁혀진다는 것을 타입 트리 위에 표시한다. 위에서 아래로 뻗는 트리 다이어그램. 맨 위 노드 라벨 "Object". 그 아래 노드 라벨 "MessageSender". 그 아래로 가지가 둘로 갈라져 왼쪽 노드 "EmailSender", 오른쪽 노드 "SmsSender". 맨 아래 두 노드 밑에는 각각 둥근 객체 아이콘이 하나씩 달려 있고 라벨 "emailSender", "smsSender". 트리 오른쪽에 돋보기 아이콘 세 개가 세로로 놓여 각각 다른 높이의 노드를 가리킨다. 맨 위 돋보기는 "Object" 노드를 가리키고 옆에 라벨 "모든 빈". 가운데 돋보기는 "MessageSender" 노드를 가리키고 옆에 라벨 "후보 2개". 아래 돋보기는 "SmsSender" 노드를 가리키고 옆에 라벨 "후보 1개". 각 돋보기가 가리키는 노드 아래의 영역이 옅은 색으로 칠해져 범위를 나타낸다. 흰 배경, 평면 벡터 스타일. 조회하는 타입이 트리의 위쪽일수록 후보가 늘어난다. Object로 조회하면 전부다.

    BeanFactory와 ApplicationContext

    지금까지 "컨테이너"라고 뭉뚱그려 부른 것은 사실 두 겹으로 되어 있다. 스택 트레이스에 AbstractApplicationContext와 DefaultListableBeanFactory가 함께 나온 것이 그 흔적이다. 인터페이스의 상속 구조부터 본다.

    BeanFactory는 맨 위의 인터페이스다. 이름이나 타입으로 빈을 꺼내는 메서드를 정의한다. ListableBeanFactory는 빈을 하나씩 꺼내는 것이 아니라 목록으로 열거하는 메서드를 더하고, HierarchicalBeanFactory는 부모 팩토리를 가질 수 있게 한다. ApplicationContext는 이 인터페이스들을 모두 상속하고, 빈 관리와 직접 관계없는 인터페이스 네 개를 더 상속한다.

    상속하지만 위임한다

    타입으로만 보면 ApplicationContext는 BeanFactory다. 그런데 구현을 보면 관계가 다르다. GenericApplicationContext는 DefaultListableBeanFactory를 필드로 가지고, 생성자에서 그것을 새로 만든다. 그리고 getBean을 비롯한 빈 팩토리 메서드는 그 필드에 그대로 넘긴다. 앞에서 본 getBean(String)의 두 줄짜리 본문이 그 위임이다.

    뒤의 XML 실험에는 이것을 확인하는 줄이 하나 있다. 컨텍스트에 getBean("messageSender")를 부른 결과와, 컨텍스트에서 꺼낸 빈 팩토리에 같은 호출을 한 결과를 ==로 비교하면 true가 나온다. 빈을 실제로 보관하고 만드는 것은 DefaultListableBeanFactory다. ApplicationContext는 그것을 감싸고, 시작 절차(refresh)와 부가 기능을 얹는다.

    일상에서 가져온 비유엔진과 자동차

    BeanFactory는 엔진이다. 연료를 넣고 직접 돌리면 동력은 나온다. ApplicationContext는 그 엔진을 얹은 자동차다. 시동 절차가 정해져 있고, 계기판과 전장품이 달려 있어서 운전자는 엔진을 직접 만지지 않는다. 비유가 깨지는 지점도 있다. 자동차는 엔진의 한 종류가 아니지만, ApplicationContext는 BeanFactory 인터페이스를 스스로 구현하고 있어서 엔진을 받는 자리에 그대로 넘길 수 있다.

    엔진만 쓰면 무엇이 빠지는가

    DefaultListableBeanFactory를 컨텍스트 없이 직접 만들어 써 보면 차이가 드러난다. A는 설정 클래스를 빈 정의로 등록한 경우이고, B는 XML 파일에서 정의를 읽어 넣은 경우다. XML 파일의 내용은 다음 절에 있고, 지금은 같은 세 빈이 정의되어 있다는 것만 알면 된다.

    package notify;

import org.springframework.beans.factory.support.DefaultListableBeanFactory;
import org.springframework.beans.factory.support.RootBeanDefinition;
import org.springframework.beans.factory.xml.XmlBeanDefinitionReader;
import org.springframework.core.io.ClassPathResource;

public class FactoryMain {
    public static void main(String[] args) {
        System.out.println("A. 빈 팩토리에 설정 클래스만 등록");
        DefaultListableBeanFactory a = new DefaultListableBeanFactory();
        a.registerBeanDefinition("notifyConfig", new RootBeanDefinition(NotifyConfig.class));
        System.out.println(a.getBeanDefinitionCount() + " " + a.containsBean("notificationService"));
        System.out.println(a.getBean("notifyConfig").getClass().getSimpleName());

        System.out.println("B. 빈 팩토리에 XML 정의를 읽어 넣기");
        DefaultListableBeanFactory b = new DefaultListableBeanFactory();
        int count = new XmlBeanDefinitionReader(b).loadBeanDefinitions(new ClassPathResource("notify.xml"));

    B는 생성 시점의 차이를 보여 준다. 정의 3개를 읽어 넣은 뒤에도 싱글톤은 0개다. getBean을 부른 순간에 세 객체가 만들어졌다. 빈 팩토리는 요청을 받아야 만든다. ApplicationContext가 빈을 미리 만들어 두는 것은 refresh()의 11단계에서 스스로 모든 싱글톤에 getBean을 부르기 때문이지, 빈 팩토리의 성질이 달라서가 아니다.

    미리 만드는 쪽에는 분명한 이점이 있다. 없는 빈을 참조했다든가, 같은 타입이 둘이라든가 하는 설정 오류가 첫 요청이 들어온 때가 아니라 애플리케이션이 뜨는 때에 드러난다. 레퍼런스 문서의 비교표는 두 인터페이스의 차이를 다음과 같이 정리한다.

    ApplicationContext가 더하는 기능

    ApplicationContext가 추가로 상속하는 네 인터페이스는 각각 기능 하나에 대응한다.

    인터페이스기능대표 메서드

    리스너를 등록해 두었더니 refresh()가 끝날 때 ContextRefreshedEvent가, close()할 때 ContextClosedEvent가 전달됐다. 환경 객체는 JVM의 시스템 프로퍼티를 읽어 자바 버전을 돌려주었고, classpath: 접두어가 붙은 위치 문자열로 클래스패스의 파일을 찾았다. 메시지는 등록한 것이 없어서 기본 문구가 나왔다. 이 기능들을 실제로 수행하는 객체가 앞에서 본 정의 없는 싱글톤 environment, messageSource, applicationEventMulticaster다.

    레퍼런스 문서의 권고는 분명하다. 특별한 이유가 없으면 ApplicationContext를 쓰라고 한다. 애플리케이션 코드가 BeanFactory를 직접 만들 일은 거의 없다. 그래도 둘의 관계를 알아야 하는 이유가 있다. 빈 생성이 실패했을 때 스택 트레이스에 찍히는 클래스는 대부분 빈 팩토리 쪽의 것이기 때문이다.

    ApplicationContext가 BeanFactory 인터페이스를 구현하면서도 실제 빈 관리는 내부의 DefaultListableBeanFactory에 위임하고, 그 둘레에 네 가지 부가 기능을 가진다는 것을 보여 준다. 동심 구조의 구조도. 한가운데에 진한 색의 둥근 사각형, 라벨 "DefaultListableBeanFactory", 그 안에 작은 글씨 두 줄 "빈 정의 맵", "싱글톤 저장소". 그것을 감싸는 더 큰 옅은 색의 둥근 사각형, 위쪽 테두리에 라벨 "ApplicationContext". 바깥 사각형과 안쪽 사각형 사이의 띠에 네 개의 작은 배지가 네 방향으로 놓여 있다: 위 "환경", 오른쪽 "메시지", 아래 "이벤트", 왼쪽 "리소스". 구조도 왼쪽 바깥에 사람 아이콘 하나, 거기서 바깥 사각형으로 화살표, 화살표 위 라벨 "getBean". 바깥 사각형 테두리에서 가운데 사각형으로 이어지는 두 번째 화살표, 라벨 "위임". 바깥 사각형 위쪽에 둥근 화살표 아이콘과 라벨 "refresh()". 흰 배경, 평면 벡터 스타일, 안쪽은 파란색, 바깥은 옅은 회색. 호출은 ApplicationContext가 받지만 빈을 보관하고 만드는 일은 안쪽의 빈 팩토리가 한다.

    다양한 설정 형식 지원 - 자바 코드, XML

    같은 객체 그래프를 이번에는 XML로 적는다. 자바 설정 클래스는 쓰지 않는다. 도메인 클래스는 그대로다.

    bean 요소 하나가 빈 정의 하나다. id는 빈의 이름, class는 만들 클래스의 패키지를 포함한 이름이다. constructor-arg의 ref는 생성자 인자로 넣을 다른 빈의 이름이다. 이 파일을 읽는 컨텍스트가 GenericXmlApplicationContext다. 아래 프로그램은 XML 컨텍스트를 만들어 쓰고, 이어서 자바 설정 컨텍스트도 만들어 같은 이름의 빈 정의를 나란히 출력한다. 뒷부분의 출력은 다음 절에서 읽는다.

    동작은 자바 설정 때와 같다. 컨테이너 생성이 끝나기 전에 세 객체가 만들어졌고, 서비스는 주입받은 저장소와 발송기로 일했다. 다른 점이 둘 있다. 정의의 수가 9가 아니라 3이다. XML 컨텍스트는 애노테이션 처리용 내부 빈을 자동으로 등록하지 않기 때문이다. 그리고 @Bean ... 호출 줄이 없다. 팩토리 메서드가 없으므로 컨테이너가 직접 생성자를 골라 호출했다.

    생성 순서도 읽어 보자. 파일에는 notificationService가 가장 먼저 적혀 있지만 가장 나중에 만들어졌다. 컨테이너는 정의 순서대로 notificationService를 만들려다가, 생성자 인자로 넣을 templateRepository와 messageSender가 필요하다는 것을 정의에서 읽고 그 둘을 먼저 만든 것이다. 자바 설정에서는 우리가 쓴 메서드 본문이 하던 일을, 여기서는 컨테이너가 정의에 적힌 참조를 따라가며 한다.

    문자열로 적은 클래스 이름의 대가

    XML의 class 속성은 문자열이다. 자바 컴파일러는 이 문자열을 검사하지 않는다. notify.EmailSender를 notify.EmialSender로 잘못 적은 파일로 컨텍스트를 만들면 다음 예외가 난다.

    BeanCreationException: Error creating bean with name 'notificationService' defined in class path resource [typo.xml]: Cannot resolve reference to bean 'messageSender' while setting constructor argument
 원인: CannotLoadBeanClassException: Cannot find class [notify.EmialSender] for bean with name 'messageSender' defined in class path resource [typo.xml]
 원인: ClassNotFoundException: notify.EmialSender

    원인의 사슬을 아래에서 위로 읽으면 일어난 일이 그대로 보인다. 컨테이너는 문자열을 클래스 로더에 넘겨 클래스를 찾으려 했고 실패했다(ClassNotFoundException). 그래서 messageSender 빈의 클래스를 로딩할 수 없었고, 그 빈을 생성자 인자로 받아야 하는 notificationService도 만들 수 없었다. 자바 설정이었다면 new EmialSender()는 컴파일 단계에서 걸렸을 것이다. 자바 설정이 컴파일러의 타입 검사를 받는다는 점은 XML에 비해 분명한 장점이다.

    그래도 이 오류는 애플리케이션이 뜨는 시점에 드러났다. 싱글톤을 미리 만드는 덕분이다. 그리고 메시지마다 붙어 있는 defined in class path resource [typo.xml]이라는 문구에 주목하자. 빈 정의는 자신이 어디에서 왔는지를 기억하고 있고, 예외 메시지가 그것을 알려 준다. XML의 장점도 하나 적어 둔다. 설정이 클래스 파일 밖에 있으므로, 애플리케이션을 다시 컴파일하지 않고 파일만 바꿔서 구성을 바꿀 수 있다.

    XML 첫머리의 스키마 위치는 URL 모양이지만, 스프링은 이 주소로 네트워크 요청을 보내지 않는다. spring-beans 라이브러리 안의 META-INF/spring.schemas 파일이 그 URL을 라이브러리 안에 들어 있는 XSD 파일의 경로로 연결해 주고, 스프링의 스키마 리졸버가 이 매핑을 써서 로컬 파일을 읽는다.

    형식이 달라도 컨테이너가 같은 이유

    자바 설정과 XML은 겉모습이 전혀 다른데 같은 빈 팩토리에서, 같은 refresh()로 동작했다. 중간에 형식의 차이를 흡수하는 층이 있기 때문이다. 형식마다 그것을 읽는 리더(reader)가 있고, 모든 리더는 읽은 내용을 BeanDefinition으로 바꿔 레지스트리에 등록한다. 빈 팩토리는 BeanDefinition만 본다.

    자바 설정 클래스 ──▶ AnnotatedBeanDefinitionReader ────┐

    컨텍스트 클래스들의 차이는 어떤 리더를 들고 있느냐에 있다. AnnotationConfigApplicationContext는 애노테이션 리더와 스캐너를 필드로 가진다. GenericXmlApplicationContext는 XmlBeanDefinitionReader를 필드로 가지고, 생성자에서 파일을 읽어 들인 다음 refresh()를 부른다. 둘 다 GenericApplicationContext의 하위 클래스이므로 그 뒤의 과정은 한 줄도 다르지 않다. 앞 절의 실험 B에서 본 것처럼 XML 리더는 컨텍스트 없이 빈 팩토리에 직접 붙여 쓸 수도 있다.

    레퍼런스 문서는 가장 유연한 방식으로 GenericApplicationContext에 리더를 조합해 쓰는 것을 들고, 한 컨텍스트에 여러 리더를 섞어 서로 다른 설정 원천에서 빈 정의를 읽을 수 있다고 설명한다. 같은 문서에는 XML을 읽는 ClassPathXmlApplicationContext와 Groovy 설정을 읽는 GenericGroovyApplicationContext도 나온다. 새 형식이 필요하면 리더를 하나 더 만들면 되고, 빈 팩토리는 고칠 필요가 없다.

    자바 설정, XML, 스캔 등 서로 다른 입력이 각자의 리더를 거쳐 같은 형태의 BeanDefinition이 되고, 빈 팩토리는 그것만 본다는 깔때기 구조를 보여 준다. 왼쪽에서 오른쪽으로 좁아지는 깔때기 모양의 구조도. 맨 왼쪽에 세로로 나란한 입력 아이콘 세 개: 자바 파일 아이콘(라벨 "자바 설정"), 꺾쇠 괄호가 그려진 문서 아이콘(라벨 "XML"), 폴더와 돋보기 아이콘(라벨 "컴포넌트 스캔"). 각 아이콘에서 오른쪽으로 화살표가 나가 작은 톱니바퀴 상자 세 개로 이어지고, 세 상자를 묶는 괄호 위에 라벨 "리더". 세 상자에서 나온 화살표가 한 점으로 모여 가운데의 설계도 카드 묶음으로 들어간다. 카드 묶음의 라벨 "BeanDefinition". 카드 묶음에서 오른쪽으로 굵은 화살표 하나가 나가 큰 상자로 들어간다. 큰 상자의 라벨 "빈 팩토리", 상자 안에는 둥근 객체 세 개. 화살표 위 라벨 "인스턴스 생성". 흰 배경, 평면 벡터 스타일, 입력은 회색, 설계도는 파란색, 객체는 주황색. 형식의 차이는 리더에서 끝난다. 빈 팩토리가 받는 것은 언제나 BeanDefinition이다.

    스프링 빈 설정 메타 정보 - BeanDefinition

    리더들이 공통으로 만들어 내는 결과물이 BeanDefinition이다. Javadoc은 이 인터페이스가 빈 인스턴스를 기술하며, 프로퍼티 값과 생성자 인자 값, 그리고 구현체가 제공하는 추가 정보를 가진다고 설명한다. 레퍼런스 문서는 그 내용을 네 갈래로 나눈다. 만들 빈의 클래스 이름, 컨테이너 안에서의 동작 방식(스코프, 생명주기 콜백 등), 일하는 데 필요한 다른 빈에 대한 참조, 새로 만든 객체에 넣을 그 밖의 설정값이다.

    빈을 만드는 두 가지 방식

    두 정의는 같은 빈을 서로 다른 방식으로 기술한다. XML 쪽에는 클래스 이름이 있고 생성자 인자가 2개 있다. "이 클래스의 생성자를 이 두 빈을 인자로 호출하라"는 뜻이다. 컨테이너는 클래스를 로딩하고, 인자에 맞는 생성자를 찾고, 참조된 빈을 준비해 생성자를 호출한다. 클래스를 직접 지정하는 방식이다.

    자바 설정 쪽에는 클래스 이름이 아예 없다. 대신 팩토리 빈의 이름 notifyConfig와 팩토리 메서드의 이름 notificationService가 있다. "notifyConfig 빈을 얻어 그 객체의 notificationService 메서드를 호출하면 결과가 이 빈이다"라는 뜻이다. 생성자 인자가 0개인 것도 자연스럽다. 인자를 채우는 일은 메서드 본문이 하므로 정의에 적을 것이 없다. 스택 트레이스에서 createBeanInstance 아래에 Method.invoke가 있었던 것이 이 정의를 실행한 흔적이다.

    이 차이를 알면 앞에서 본 두 현상의 근거가 보인다. 자바 설정으로 등록한 빈의 정의에는 클래스 이름이 없으므로, 인스턴스가 만들어지기 전에 컨테이너가 타입을 알 방법은 팩토리 메서드의 선언 반환 타입뿐이다. 타입 예측 실험의 결과가 여기서 나온다. 그리고 5단계에서 @Bean 메서드가 "호출되지 않고 등록만 된다"는 말은, 메서드의 이름이 정의의 필드에 문자열로 적힌다는 뜻이었다.

    몇 군데를 짚는다. scope는 두 정의 모두 빈 문자열인데 isSingleton()은 true였다. 소스에서 빈 문자열은 기본 스코프를 나타내는 상수이고, 주석은 이것이 싱글톤과 같은 상태라고 설명한다. 따로 적지 않으면 싱글톤이라는 규칙이 이 필드에 들어 있다. autowireMode는 XML이 0, 자바 설정이 3이다. @Bean 메서드에 매개변수가 있으면 컨테이너가 타입에 맞는 빈을 찾아 넣어 주는데, 그 동작을 켜는 값이 3이다.

    자바 설정 쪽의 destroyMethodNames=[(inferred)]도 눈에 띈다. 레퍼런스 문서에 따르면 자바 설정으로 정의한 빈은 공개된 close나 shutdown 메서드가 있으면 그것이 소멸 콜백으로 자동 등록된다. "추론"이라는 표시가 그 기본 동작을 가리킨다. 자세한 내용은 07회에서 다룬다.

    구현 클래스가 여럿인 이유

    BeanDefinition은 인터페이스이고, 정의가 어디에서 왔느냐에 따라 구현 클래스가 다르다. 이 회차의 실험에서 직접 확인한 것과 소스에서 확인한 것을 모으면 다음과 같다.

    정의의 출처구현 클래스
    XML의 bean 요소GenericBeanDefinition
    register()로 넘긴 클래스(설정 클래스 자신)AnnotatedGenericBeanDefinition
    @Bean 메서드ConfigurationClassBeanDefinition(RootBeanDefinition의 하위 클래스)
    컴포넌트 스캔으로 찾은 클래스ScannedGenericBeanDefinition(05회)

    구현이 달라도 빈 팩토리는 인터페이스가 정한 정보만 읽는다. 빈을 실제로 만들기 직전에는 정의를 RootBeanDefinition 형태로 병합해 쓰는데, 이때 비어 있던 기본값도 채워진다. 자바 설정 컨텍스트에서 병합된 정의를 꺼내 getScope()를 출력하면 빈 문자열이 아니라 singleton이 나온다.

    정의를 손으로 등록한다

    리더는 편의 도구일 뿐이다. 리더 없이 BeanDefinition 객체를 직접 만들어 등록해도 컨테이너는 똑같이 동작한다.

    package notify;

import org.springframework.beans.factory.support.GenericBeanDefinition;
import org.springframework.context.support.GenericApplicationContext;

public class ManualMain {
    public static void main(String[] args) {
        GenericApplicationContext ac = new GenericApplicationContext();

        GenericBeanDefinition definition = new GenericBeanDefinition();
        definition.setBeanClass(SmsSender.class);
        definition.setLazyInit(true);
        ac.registerBeanDefinition("handMade", definition);

        ac.registerBean("bySupplier", MessageSender.class, () -> new EmailSender());

        ac.refresh();
        System.out.println("refresh 끝");
        System.out.println(ac.getBean("handMade").getClass().getSimpleName());
        System.out.println(ac.getBean("bySupplier").getClass().getSimpleName());
        ac.close();
    }
}

    애노테이션도 XML도 없다. handMade는 클래스와 지연 초기화 여부만 적은 정의다. lazyInit을 참으로 두었으므로 refresh() 때는 만들어지지 않고, getBean을 부른 때에 SmsSender가 만들어졌다. 필드 하나가 생성 시점을 바꾼 것이다. bySupplier는 객체를 만드는 함수를 정의에 직접 넣는 등록 방식이다. 지연 표시가 없으므로 refresh() 안에서 만들어졌다.

    이 추상화가 주는 것은 두 가지다. 첫째, 빈 팩토리는 BeanDefinition이라는 역할에만 의존하고 그것이 어떤 형식에서 왔는지는 모른다. 01회와 02회에서 애플리케이션 코드에 적용한 원칙, 곧 구체적인 것이 아니라 추상에 의존하고 확장할 때 기존 코드를 고치지 않는다는 원칙이 스프링 자신의 설계에도 들어 있다. 둘째, 정의는 객체를 만들기 전에 존재하는 데이터이므로 읽고 고칠 수 있다. Javadoc은 이 인터페이스의 주된 의도가 BeanFactoryPostProcessor가 프로퍼티 값과 그 밖의 빈 메타데이터를 들여다보고 수정할 수 있게 하는 것이라고 적는다.

    정의가 실제로 고쳐지는 모습도 확인할 수 있다. PhaseMain처럼 단계를 나눠 실행하면서 notifyConfig 정의의 getBeanClassName()을 찍어 보면, refresh() 전에는 notify.NotifyConfig이고 refresh() 뒤에는 notify.NotifyConfig$$SpringCGLIB$$0이다. ConfigurationClassPostProcessor가 인스턴스를 만들기 전에 설계도의 클래스를 바꿔 넣은 것이다. 왜 바꾸는지는 04회에서 이어진다.

    흔한 오해 여섯 가지

    "getBean을 부를 때 객체가 만들어진다." ApplicationContext에서 지연 초기화가 아닌 싱글톤은 refresh() 안에서 이미 만들어져 있다. getBean은 저장소에서 꺼내 줄 뿐이다. 호출 시점에 만들어지는 것은 지연 초기화 빈, 순수한 BeanFactory에 등록된 빈, 그리고 싱글톤이 아닌 스코프의 빈(08회)이다.

    "getBeanDefinitionNames()가 컨테이너에 든 빈의 전부다." 이 메서드는 설계도의 이름만 돌려준다. environment나 messageSource처럼 완성된 객체로 직접 등록된 싱글톤은 여기에 없지만 이름으로도 타입으로도 조회된다. 이 회차의 실험에서는 정의가 9개일 때 싱글톤이 17개였다.

    "타입 조회는 @Bean 메서드의 반환 타입과 비교한다." 인스턴스가 이미 있으면 그 객체의 실제 클래스로 판정한다. 선언 반환 타입이 쓰이는 것은 인스턴스가 아직 없을 때의 예측이다. 같은 조회가 시점에 따라 성공하기도 실패하기도 하는 이유가 여기에 있다.

    "ApplicationContext는 BeanFactory를 상속했으니 스스로 빈을 보관한다." 인터페이스는 상속하지만 구현은 위임한다. 빈 정의의 맵과 싱글톤 저장소는 컨텍스트가 필드로 가진 DefaultListableBeanFactory 안에 있다.

    "XML 설정과 자바 설정은 서로 다른 컨테이너다." 다른 것은 설정을 읽는 리더다. 읽은 결과는 같은 인터페이스의 BeanDefinition이 되어 같은 종류의 빈 팩토리에 등록되고, 같은 refresh()로 인스턴스가 된다.

    "빈을 쓰려면 getBean으로 꺼내야 한다." 이 회차에서 getBean을 계속 쓴 것은 컨테이너를 관찰하기 위해서였다. 레퍼런스 문서는 애플리케이션 코드가 이상적으로는 getBean()을 전혀 호출하지 않아야 하고, 그래서 스프링 API에 의존하지 않아야 한다고 적는다. 필요한 객체를 컨테이너에 물어 가져오는 방식을 의존관계 조회(dependency lookup)라고 하는데, 이렇게 하면 클래스가 무엇에 의존하는지가 생성자 시그니처에서 사라지고 코드가 컨테이너에 묶인다. 애플리케이션 코드는 필요한 것을 생성자로 주입받는다.

    이 지식이 다시 쓰이는 곳

    이 권의 남은 회차는 모두 이 회차의 구조 위에서 진행된다. 04회는 싱글톤 저장소가 "하나"를 어떻게 보장하는지, 그리고 templateRepository()가 왜 한 번만 호출되었는지를 설정 클래스의 CGLIB 서브클래스로 설명한다. 05회의 컴포넌트 스캔은 이 회차에서 본 스캐너가 클래스패스를 훑어 ScannedGenericBeanDefinition을 등록하는 과정이다. 설계도가 등록된 뒤의 일은 이 회차에서 본 것과 같다.

    06회의 의존관계 자동 주입은 이 회차의 타입 조회를 컨테이너가 대신 수행하는 것이다. 주입할 빈을 타입으로 찾고, 후보가 없으면 NoSuchBeanDefinitionException, 둘 이상이면 NoUniqueBeanDefinitionException이 난다. 예외의 이름과 메시지가 이 회차에서 직접 일으켜 본 것과 같으므로, 주입 실패 메시지는 "누군가 이 타입으로 조회했는데 후보가 0개 또는 여러 개였다"로 읽으면 된다. 07회의 생명주기 콜백은 refresh()와 close() 사이에 끼어드는 지점들이고, 08회의 스코프는 BeanDefinition의 scope 필드가 싱글톤이 아닐 때의 이야기다.

    이 권 밖에서도 같은 구조를 만난다. 스프링 부트 3.5의 소스를 보면 서블릿 웹 애플리케이션용 컨텍스트인 ServletWebServerApplicationContext는 refresh()의 onRefresh 단계를 재정의해 내장 웹 서버를 만든다. 이 클래스도 GenericApplicationContext의 후손이다. 그래서 부트 애플리케이션이 뜨다가 빈 생성에 실패했을 때의 스택 트레이스에는 이 회차에서 본 refresh, finishBeanFactoryInitialization, preInstantiateSingletons, createBean의 프레임이 나온다. 그 프레임들이 무엇을 하는 중이었는지 알면, 긴 스택에서 어느 빈의 어느 단계가 문제였는지를 짚을 수 있다.
    스프링 컨테이너
    빈을 만들고 설정하고 이어 주는 객체다. ApplicationContext 인터페이스로 나타내며, JVM에서는 맵과 리스트를 필드로 가진 평범한 힙 객체다.
    두 단계 구조
    컨테이너는 먼저 모든 설정을 빈 정의로 바꿔 등록하고, 그다음 정의를 보고 인스턴스를 만든다. 두 단계 모두 refresh() 안에서 일어난다.
    미리 만들기
    refresh()의 끝에서 빈 팩토리가 정의 목록을 돌며 지연 초기화가 아닌 싱글톤마다 getBean을 부른다. 설정 오류가 시작 시점에 드러나는 이유다.
    이름 조회와 타입 조회
    이름 조회는 싱글톤 저장소(ConcurrentHashMap)에서 한 번 꺼내는 연산이고, 타입 조회는 정의 목록을 훑으며 타입을 검사하는 선형 탐색이다. 타입 조회 결과는 타입별로 캐시된다.
    타입 판정의 기준
    인스턴스가 있으면 그 객체의 실제 클래스로 instanceof 판정을 한다. 인스턴스가 없으면 정의에서 예측한 타입(자바 설정이면 팩토리 메서드의 선언 반환 타입)을 쓴다.
    둘 이상과 상속 관계
    부모 타입으로 조회하면 자식 타입의 빈이 모두 후보다. 후보가 둘 이상이면 NoUniqueBeanDefinitionException이 나고, 이름을 주거나 getBeansOfType으로 전부 받아 해결한다.
    BeanFactory와 ApplicationContext
    ApplicationContext는 BeanFactory 인터페이스를 상속하지만 실제 빈 관리는 내부의 DefaultListableBeanFactory에 위임한다. 여기에 시작 절차, 후처리기 자동 등록, 환경·메시지·이벤트·리소스 기능을 더한다.
    BeanDefinition
    빈 하나를 만드는 방법을 담은 설계도다. 클래스를 직접 지정하는 방식과 팩토리 빈·팩토리 메서드를 지정하는 방식이 있고, 스코프·지연 초기화·자동 연결 방식·출처 같은 정보를 함께 가진다.
    설정 형식의 다양성
    자바 설정, XML, 스캔은 각자의 리더가 읽어 BeanDefinition으로 바꾼다. 빈 팩토리는 정의만 보므로 형식이 늘어나도 바뀌지 않는다.

    애플리케이션이 뜨다가 멈췄을 때 가장 먼저 할 일은 예외의 종류를 이 회차의 표에 대 보는 것이다. NoSuchBeanDefinitionException이면 "누군가 그 이름이나 타입으로 조회했는데 후보가 없었다"는 뜻이다. 원인은 셋 중 하나로 좁혀진다. 정의가 아예 등록되지 않았거나, 등록은 되었지만 다른 타입으로 선언되어 예측 타입이 맞지 않았거나, 이름이 다르다. NoUniqueBeanDefinitionException이면 메시지 끝의 후보 이름 목록이 곧 답의 절반이다. 메시지에 붙은 defined in ... 문구는 그 정의가 어느 설정 클래스나 파일에서 왔는지를 알려 주므로, 의도하지 않은 설정이 함께 읽혔는지를 바로 확인할 수 있다.

    @Bean 메서드의 반환 타입을 인터페이스로 할지 구현 클래스로 할지는 취향의 문제가 아니다. 그 빈을 참조하는 모든 곳이 역할 인터페이스만 쓴다는 것이 확실하면 인터페이스로 선언해도 된다. 그 빈이 여러 인터페이스를 구현하고 있고 다른 곳에서 그 인터페이스 중 하나로 주입받는다면, 선언 타입에 없는 인터페이스는 인스턴스가 만들어지기 전까지 컨테이너에 보이지 않는다. 생성 순서에 따라 되기도 하고 안 되기도 하는 주입 오류는 재현이 어렵다. 그런 가능성이 있으면 구체 타입으로 선언하는 쪽이 안전하다.

    싱글톤을 미리 만드는 기본 동작은 시작 시간을 늘리지만 오류를 앞당긴다. 지연 초기화를 넓게 켜면 애플리케이션은 빨리 뜨는 대신, 설정 오류가 그 빈을 처음 쓰는 요청에서 드러난다. 개발 중의 빠른 재시작에는 도움이 될 수 있어도, 운영 환경에서는 잘못된 설정이 배포 직후가 아니라 특정 기능이 처음 호출될 때 발견된다는 대가를 치른다. 어느 쪽을 택하든 그 차이가 BeanDefinition의 필드 하나와 preInstantiateSingletons()의 조건 하나에서 나온다는 것을 알고 정해야 한다.

    컨텍스트를 주입받아 getBean으로 필요한 객체를 꺼내 쓰는 코드를 실무에서 가끔 만난다. 동작은 하지만, 그 클래스가 무엇에 의존하는지가 생성자에서 보이지 않고 테스트하려면 컨테이너나 그 대역이 필요해진다. 조회 API는 프레임워크와 맞닿는 경계의 코드, 테스트, 그리고 지금처럼 컨테이너의 상태를 진단하는 용도에 쓴다. 또 하나 기억할 것은 등록 시점이다. 레퍼런스 문서는 빈 메타데이터와 직접 넣는 싱글톤을 가능한 한 일찍 등록해야 하며, 팩토리가 사용되고 있는 도중에 새 빈을 등록하는 것은 공식적으로 지원하지 않는다고 적는다. 실행 중에 구성을 바꾸고 싶다는 요구가 나오면, 빈을 새로 등록하는 대신 이미 등록된 빈들 가운데 하나를 고르는 구조로 푸는 편이 맞다.

    스프링 컨테이너(Spring container)
    빈의 생성, 설정, 조립을 맡는 객체. ApplicationContext 인터페이스가 이를 나타낸다.
    빈 정의(BeanDefinition)
    빈 하나를 어떻게 만들고 어떻게 다룰지를 담은 메타데이터 객체. 클래스 또는 팩토리 메서드, 스코프, 지연 초기화 여부, 의존 참조 등을 가진다.
    BeanFactory
    이름이나 타입으로 빈을 꺼내는 메서드를 정의한 최상위 인터페이스. 대표 구현은 DefaultListableBeanFactory다.
    ApplicationContext
    BeanFactory 계열 인터페이스에 환경, 메시지, 이벤트, 리소스 기능을 더한 인터페이스. 구현은 내부 빈 팩토리에 빈 관리를 위임한다.
    refresh
    컨텍스트가 설정을 읽어 빈 정의를 등록하고, 후처리기를 준비하고, 싱글톤을 만드는 시작 절차 전체를 수행하는 메서드.
    빈 팩토리 후처리기(BeanFactoryPostProcessor)
    빈 인스턴스가 만들어지기 전에 빈 정의를 읽고 수정하거나 추가할 수 있는 확장 지점. ConfigurationClassPostProcessor가 대표적이다.
    팩토리 메서드(factory method)
    호출하면 빈이 될 객체를 돌려주는 메서드. 자바 설정의 @Bean 메서드가 빈 정의에 이 형태로 기록된다.
    지연 초기화(lazy initialization)
    컨테이너 시작 때가 아니라 처음 요청될 때 빈을 만드는 설정. 빈 정의의 lazyInit 필드로 표현된다.
    타입 예측(type prediction)
    인스턴스가 아직 없는 빈의 타입을 빈 정의의 정보만으로 미리 판단하는 일. 자바 설정에서는 팩토리 메서드의 선언 반환 타입이 기준이 된다.
    의존관계 조회(dependency lookup)
    필요한 객체를 주입받지 않고 컨테이너에 직접 물어 가져오는 방식. getBean 호출이 여기에 해당한다.
