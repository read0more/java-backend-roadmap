    이 회차의 질문: 대시보드가 원본 테이블을 매번 훑으면

    쇼핑몰 운영 화면에 "이번 달 상품별 주문 수와 매출" 표가 있다고 하자. 가장 먼저 떠오르는 구현은 주문 테이블에 GROUP BY를 거는 것이다. 개발 환경에서는 주문이 몇천 건뿐이라 이 쿼리는 눈 깜짝할 사이에 끝나고, 처음 서비스를 열었을 때도 문제가 없다. 그런데 주문이 쌓일수록 같은 쿼리가 조금씩 느려지고, 어느 날 월말 정산 기간에 여러 운영자가 동시에 화면을 새로 고치자 주문 접수 API까지 느려진다. 쿼리는 한 글자도 바뀌지 않았는데 무엇이 달라진 것일까.

    달라진 것은 쿼리가 읽어야 하는 행의 수다. 한 달 치 매출을 구하려면 그 달에 들어온 주문을 하나도 빠짐없이 읽어야 한다. 하루 주문이 10만 건인 서비스라고 가정하면 한 달 범위의 집계는 약 300만 행을 읽는다. 이 계산은 화면을 열 때마다 처음부터 다시 이루어지고, 지난달처럼 이미 끝나서 더 이상 바뀌지 않는 기간도 매번 다시 계산된다. 결과는 상품 수만큼의 행, 예를 들어 1,000행 남짓인데 그것을 얻으려고 300만 행을 훑는 셈이다.

    이 회차의 주제인 통계 테이블(summary table)은 이 불균형을 바로잡는 설계다. 원본 데이터를 미리 정해 둔 단위(예: 날짜×상품)로 집계해 별도 테이블에 저장해 두고, 조회는 그 테이블에서 한다. 위 가정에서 하루에 팔린 상품이 1,000종이라면 일별 상품 통계는 하루 1,000행, 한 달 3만 행이다. 같은 질문에 답하기 위해 읽는 행이 300만에서 3만으로 100분의 1이 된다. 계산을 조회 시점에서 집계 시점으로 옮기고, 한 번 계산한 결과를 여러 번 읽게 만드는 것이 핵심이다.

    물론 공짜는 아니다. 통계 테이블은 원본에서 파생된 데이터라서 원본과 어긋날 수 있다. 언제 집계하느냐에 따라 최신성이 떨어지고, 집계 작업이 실패하거나 두 번 돌면 숫자가 틀어지며, 평균이나 고유 회원 수처럼 단순히 더해서는 안 되는 값을 잘못 저장하면 주간·월간 통계로 올라갈 때 엉뚱한 숫자가 나온다. 이 회차는 다음 순서로 이 문제들을 하나씩 다룬다. 먼저 원본 집계가 InnoDB 안에서 왜 비싼지 확인한다. 다음으로 통계 테이블의 모양(입도, 차원, 측정값, 기본 키)을 정하고, 주간·월간 통계를 일 단위에서 효율적으로 만드는 법을 본다. 그다음 실시간성이 필요할 때의 동기 카운터와 하이브리드 설계, 집계 작업을 몇 번 돌려도 결과가 같게 만드는 멱등성, 짧은 주기로 집계하는 마이크로 배치, 마지막으로 통계 테이블 쓰기의 중심인 UPSERT의 잠금과 비용을 다룬다. 기준 환경은 MySQL 8.0 이상, InnoDB, 기본 격리 수준 REPEATABLE READ다.

    이 회차에서 계속 쓸 원본 테이블은 다음과 같다. 한 행이 주문 하나이고, 상품 하나를 여러 개 살 수 있다고 단순화했다.

    CREATE TABLE orders (
  order_id    BIGINT        NOT NULL AUTO_INCREMENT,
  member_id   BIGINT        NOT NULL,
  product_id  BIGINT        NOT NULL,
  quantity    INT           NOT NULL,
  amount      DECIMAL(15,2) NOT NULL,
  ordered_at  DATETIME      NOT NULL,   -- 서비스 기준 시간대(KST)로 저장한다고 가정
  PRIMARY KEY (order_id),
  KEY idx_orders_ordered_at (ordered_at)
);

    집계 쿼리가 InnoDB 안에서 하는 일

    통계 테이블이 왜 필요한지 제대로 이해하려면 원본에 대한 집계가 엔진 안에서 무엇을 하는지부터 봐야 한다. 다음 쿼리를 생각해 보자.

    SELECT product_id, COUNT(*) AS order_count, SUM(amount) AS amount_sum
FROM orders
WHERE ordered_at >= '2026-10-01' AND ordered_at < '2026-11-01'
GROUP BY product_id;

    범위 스캔과 클러스터형 인덱스 조회

    InnoDB 테이블의 행은 기본 키 순서로 정렬된 B+Tree, 즉 클러스터형 인덱스(clustered index)의 리프 페이지에 저장된다. idx_orders_ordered_at 같은 보조 인덱스(secondary index)의 리프에는 인덱스 열 값과 그 행의 기본 키 값만 있다. 옵티마이저가 ordered_at 범위 조건으로 보조 인덱스를 고르면, 엔진은 보조 인덱스에서 10월 1일 0시에 해당하는 위치를 찾은 뒤 리프를 따라 오른쪽으로 걸어가며 범위 안의 항목을 하나씩 읽는다. 그런데 이 쿼리는 product_id와 amount도 필요하고, 그 값은 보조 인덱스에 없다. 그래서 항목마다 기본 키 값을 들고 클러스터형 인덱스를 루트부터 다시 내려가 실제 행을 읽는다. 300만 행이면 이 왕복이 300만 번이다. 주문 ID는 시간 순서로 증가하므로 이 조회가 완전히 무작위는 아니지만, 행 하나마다 B+Tree를 한 번씩 내려가는 비용은 그대로 남는다.

    옵티마이저는 이 왕복 비용이 너무 크다고 판단하면 보조 인덱스를 버리고 클러스터형 인덱스 전체를 처음부터 끝까지 읽는 쪽을 고르기도 한다. 어느 쪽이든 결론은 같다. 범위 안의 행을 전부 읽어야 한다. 인덱스는 "어디서부터 어디까지 읽을지"를 정해 줄 수 있을 뿐, 집계에 필요한 행의 수 자체를 줄여 주지는 못한다. 합계를 구하려면 더해야 할 값을 모두 봐야 하기 때문이다.

    커버링 인덱스가 해 주는 것과 해 주지 못하는 것

    클러스터형 인덱스 왕복을 없애는 방법은 쿼리에 필요한 열을 모두 담은 인덱스, 즉 커버링 인덱스(covering index)를 만드는 것이다. (ordered_at, product_id, amount) 인덱스가 있으면 엔진은 보조 인덱스의 리프만 읽고 실제 행에는 가지 않는다. MySQL 매뉴얼은 실행 계획의 Extra 열에 나오는 Using index를 "실제 행을 읽는 추가 탐색 없이 인덱스 트리의 정보만으로 열 값을 가져온다"는 뜻으로 설명한다. 행당 비용은 크게 줄지만 읽는 항목의 수는 여전히 300만이다. 게다가 이 인덱스는 공짜가 아니다. 매뉴얼의 INSERT 최적화 절은 행 하나를 넣는 시간의 구성 요소로 "행 삽입"과 별도로 "인덱스 삽입(인덱스 수에 비례)"을 든다. 집계를 빠르게 하려고 넓은 인덱스를 붙이면 그 비용은 주문이 들어올 때마다 쓰기 쪽에서 치른다.

    GROUP BY와 임시 테이블

    범위 조건은 ordered_at에 걸려 있는데 묶는 기준은 product_id다. 인덱스에서 읽어 나오는 순서가 시간순이라, 같은 상품의 주문이 연속으로 나오지 않는다. MySQL은 이럴 때 내부 임시 테이블을 만들어 상품별 누적값을 담아 두고, 행을 읽을 때마다 해당 상품의 칸을 찾아 갱신한다. 실행 계획의 Extra에 나타나는 Using temporary가 이 작업이다. 매뉴얼의 GROUP BY 최적화 절은 GROUP BY를 처리하는 가장 일반적인 방법이 전체를 읽어 각 그룹의 행이 연속되도록 임시 테이블을 만드는 것이고, 경우에 따라 인덱스 순서를 이용해 임시 테이블을 피할 수 있다고 설명한다. 그런데 product_id를 앞에 둔 인덱스로 순서를 맞추면 이번에는 ordered_at 범위가 인덱스 앞부분이 아니어서 범위 탐색을 할 수 없다. 범위 조건과 그룹 기준이 서로 다른 열이면 둘을 동시에 인덱스 순서로 만족시키기 어렵다.

    COUNT(*)도 공짜가 아니다

    "전체 주문 수"처럼 단순한 숫자도 InnoDB에서는 매번 센다. 매뉴얼은 InnoDB가 테이블의 행 수를 내부에 따로 보관하지 않는 이유를 "동시에 실행되는 트랜잭션들이 같은 순간에 서로 다른 행 수를 볼 수 있기 때문"이라고 설명한다. MVCC 아래에서는 트랜잭션마다 보이는 행 집합이 다르니, 하나의 숫자로 저장해 둘 수가 없다. 그래서 SELECT COUNT(*)는 현재 트랜잭션에 보이는 행만 세며, 조건이 없으면 가장 작은 보조 인덱스를 훑고 보조 인덱스가 없으면 클러스터형 인덱스를 훑는다. 같은 절에서 매뉴얼은 더 빠른 개수가 필요하면 카운터 테이블을 만들어 애플리케이션이 갱신하라고 권하면서, 수천 개의 동시 트랜잭션이 같은 카운터를 갱신하는 상황에서는 잘 확장되지 않을 수 있다고 덧붙인다. 이 경고는 뒤의 실시간 통계에서 다시 만난다.

    버퍼 풀과 undo에 남는 흔적

    큰 범위를 읽는 쿼리는 그 범위의 페이지를 버퍼 풀(buffer pool)로 읽어 들인다. 버퍼 풀이 단순한 LRU였다면 보고서 쿼리 하나가 주문 처리에 필요한 뜨거운 페이지를 밀어낼 것이다. InnoDB는 이를 막기 위해 새로 읽은 페이지를 LRU 목록의 맨 앞이 아니라 꼬리에서 3/8 지점(innodb_old_blocks_pct 기본값 37)에 넣고, 처음 접근한 뒤 innodb_old_blocks_time(기본값 1000밀리초) 안에 다시 접근해도 앞쪽으로 올리지 않는다. 스캔은 한 페이지를 짧은 시간에 몇 번 읽고 다시는 보지 않으므로, 이 규칙 덕분에 스캔한 페이지는 "오래된" 구역에서 먼저 밀려난다. 하지만 이 장치는 피해를 줄일 뿐이다. 보고서가 읽는 페이지가 버퍼 풀에 없으면 디스크에서 읽어야 하고, 그 I/O 대역폭과 버퍼 풀의 오래된 구역은 다른 쿼리와 나눠 쓴다.

    더 눈에 띄지 않는 비용은 undo다. REPEATABLE READ에서 일관된 읽기(consistent read)는 트랜잭션의 첫 읽기 때 만든 스냅샷을 기준으로 한다. 집계 쿼리가 몇 분 동안 돌면 그동안 다른 트랜잭션이 바꾼 행의 예전 버전을 이 스냅샷이 필요로 할 수 있으므로, InnoDB는 해당 undo 로그를 지우지 못한다. 매뉴얼은 일관된 읽기만 하는 트랜잭션이라도 주기적으로 커밋하라고 권하면서, 그렇지 않으면 update undo 로그를 버리지 못해 롤백 세그먼트가 너무 커질 수 있다고 경고한다. 주문이 활발히 바뀌는 시간대에 긴 집계가 돌면 그 시간 동안의 변경 이력이 고스란히 쌓이는 것이다.

    이 장의 핵심

    집계의 비용은 "읽어야 하는 행 수 × 행당 비용"이고, 인덱스는 행당 비용만 줄인다. 행 수를 줄이려면 계산을 미리 해 두는 수밖에 없다. 통계 테이블은 조회마다 반복되던 계산을 한 번의 집계로 바꾸고, 이미 끝난 기간을 다시 계산하지 않게 만드는 설계다.

    같은 질문(이번 달 상품별 매출)에 답하기 위해 원본 집계는 수백만 행을, 통계 테이블은 수만 행을 읽는다는 대비를 보여 준다. 가로로 두 패널을 나란히 놓은 비교 그림. 왼쪽 패널 제목 "원본 집계", 오른쪽 패널 제목 "통계 테이블 조회". 왼쪽에는 아주 긴 세로 막대(작은 행 조각이 빽빽하게 쌓인 모양)에 라벨 "orders 한 달 치 약 300만 행"을 붙이고, 막대에서 아래로 굵은 화살표가 내려가 작은 표 "상품별 결과 1,000행"에 도착한다. 화살표 옆에 "조회할 때마다 다시 계산". 오른쪽에는 짧은 막대에 라벨 "daily_product_sales 한 달 치 약 3만 행"을 붙이고, 같은 결과 표 "상품별 결과 1,000행"으로 가는 얇은 화살표를 그린다. 오른쪽 위에 점선 상자 "하루에 한 번 미리 집계". 아래쪽 공통 캡션 영역에 "가정: 하루 주문 10만 건, 하루 판매 상품 1,000종". 차분한 파랑과 회색, 평면 스타일. 같은 결과를 얻기 위해 읽는 행 수의 차이. 수치는 본문의 가정에서 나온 것이다.

    통계 테이블 설계: 입도, 차원, 측정값

    통계 테이블을 만들 때 가장 먼저 정할 것은 입도(grain), 즉 통계 테이블의 행 하나가 무엇을 뜻하는가다. "하루 동안 상품 하나의 판매 실적"이 한 행이면 입도는 날짜×상품이다. 입도가 정해지면 나머지가 따라온다. 입도를 이루는 열들, 여기서는 날짜와 상품이 차원(dimension)이고, 그 단위로 모아 둔 숫자인 주문 수, 판매 수량, 매출 합계가 측정값(measure)이다. 입도를 정하지 않고 "필요한 숫자를 담는 테이블"로 시작하면 어떤 행은 하루치이고 어떤 행은 한 시간치인 식으로 섞여서, 합치는 순간 중복 계산이 생긴다.

    CREATE TABLE daily_product_sales (
  stat_date     DATE          NOT NULL,
  product_id    BIGINT        NOT NULL,
  order_count   INT           NOT NULL,
  quantity_sum  INT           NOT NULL,
  amount_sum    DECIMAL(15,2) NOT NULL,
  aggregated_at DATETIME      NOT NULL,   -- 이 행을 마지막으로 계산한 시각
  PRIMARY KEY (stat_date, product_id)
);

    입도가 거칠수록 통계 테이블은 작고 빠르지만 답할 수 있는 질문이 줄어든다. 월×상품 입도라면 "이번 주 매출"에는 답할 수 없다. 반대로 입도가 너무 잘면 원본과 크기가 비슷해져 통계 테이블을 만든 의미가 사라진다. 실무에서 가장 흔한 선택은 날짜(일) 단위다. 주와 월은 서로 경계가 맞지 않는다. 어떤 주는 두 달에 걸친다. 그래서 주간 통계를 월간 통계에서 만들 수도, 월간 통계를 주간 통계에서 만들 수도 없다. 둘 다 만들 수 있는 가장 거친 공통 단위가 일이다. 시간대별 그래프가 필요하면 시간 단위 테이블을 따로 둔다.

    기본 키: 자연 복합 키를 그대로 쓴다

    통계 테이블의 기본 키는 입도를 이루는 차원 열의 조합, 여기서는 (stat_date, product_id)가 자연스럽다. 이 조합이 행 하나를 정확히 식별하기 때문이다. 여기에 습관처럼 id BIGINT AUTO_INCREMENT 대리 키를 붙이고 (stat_date, product_id)에 유니크 인덱스를 따로 걸면 세 가지 손해가 생긴다.

    • UPSERT가 유니크 키 두 개를 상대한다. 뒤에서 볼 INSERT ... ON DUPLICATE KEY UPDATE는 기본 키와 유니크 키 가운데 어느 것과 충돌해도 동작한다. 매뉴얼은 유니크 인덱스가 여러 개인 테이블에서는 이 구문을 피하라고 권하고, 기본 키나 유니크 키가 둘 이상인 테이블에 대한 이 문장을 문장 기반 복제(statement-based replication)에서 안전하지 않은 문장으로 분류한다.
    • 자동 증가 값이 버려진다. 매뉴얼은 INSERT ... ON DUPLICATE KEY UPDATE를 "혼합 모드 삽입(mixed-mode insert)"의 한 종류로 설명한다. 최악의 경우 INSERT 뒤에 UPDATE가 이어지는 셈이라, 할당된 자동 증가 값이 갱신 단계에서 쓰일 수도 쓰이지 않을 수도 있고, 한 번 생성된 값은 되돌려지거나 재사용되지 않는다. 매일 같은 행을 수천 번 갱신하는 통계 테이블에서는 이렇게 버려지는 값이 계속 쌓인다.
    • 클러스터형 인덱스가 조회 순서와 어긋난다. InnoDB에서 행은 기본 키 순서로 저장되므로, (stat_date, product_id)가 기본 키면 "10월 한 달 치"는 리프 페이지가 연속된 한 구간이다. 대리 키를 기본 키로 두면 행의 물리적 순서는 삽입 순서를 따르고, 날짜 범위 조회는 유니크 인덱스를 거쳐 클러스터형 인덱스로 한 번 더 내려가야 한다.

    열 순서도 조회 패턴으로 정한다. 날짜 범위로 여러 상품을 한꺼번에 보는 대시보드가 주된 용도면 (stat_date, product_id)가 맞다. 상품 상세 화면에서 한 상품의 일별 추이를 보는 것이 주된 용도면 (product_id, stat_date)가 맞다. 둘 다 중요하면 하나를 기본 키로, 다른 하나를 보조 인덱스로 둔다. 통계 테이블은 원본보다 훨씬 작으므로 인덱스 하나를 더 두는 비용도 원본 테이블에서보다 작다.

    차원 속성을 복사할 것인가

    "카테고리별 매출"이 필요하다고 하자. 방법은 두 가지다. 하나는 조회할 때 daily_product_sales를 상품 테이블과 조인해 카테고리별로 다시 묶는 것이고, 다른 하나는 집계할 때 그 시점의 category_id를 통계 테이블에 함께 저장하는 것이다. 둘의 차이는 상품의 카테고리가 바뀔 때 드러난다. 조인 방식은 과거 매출까지 현재 카테고리로 다시 분류되고, 복사 방식은 집계 당시의 카테고리로 고정된다. 어느 쪽이 맞는지는 업무 질문이 정한다. "지금 기준 카테고리 매출 추이"인지 "그때 그 카테고리에서 얼마 팔렸나"인지다. 다만 복사 방식을 택했다면, 같은 날짜를 나중에 원본에서 다시 집계했을 때 카테고리가 바뀌어 있을 수 있다는 점까지 감안해야 한다. 원본에 주문 당시의 카테고리가 남아 있지 않다면 재집계는 과거를 재현하지 못한다. 시점별 값을 남기는 방법은 이 권의 변경 이력 회차에서 다룬 선분 이력과 같은 문제다.

    통계 테이블은 파생 데이터다

    통계 테이블의 모든 숫자는 원본에서 다시 계산할 수 있어야 한다. 이 성질이 뒤에서 볼 멱등한 재집계와 정합성 점검의 바탕이 된다. 원본을 일정 기간이 지나면 지우거나 다른 저장소로 옮기는 서비스라면, 그 기간을 넘어선 통계 행은 더 이상 파생 데이터가 아니라 유일한 기록이 된다. 그때부터는 재집계로 덮어쓰면 오히려 데이터를 잃으므로, 보존 기간 이전의 날짜를 재집계 대상에서 빼는 규칙이 필요하다. 하루 동안 아무것도 팔리지 않은 상품은 행이 생기지 않는다는 점도 기억해 두자. 그래프에 0을 찍어야 한다면 날짜 목록(달력 테이블이나 재귀 CTE로 만든 날짜열)과 외부 조인하거나 애플리케이션에서 빈칸을 채운다.

    측정값의 가산성: 무엇을 저장해야 다시 합칠 수 있는가

    통계 테이블의 숫자는 대부분 다시 묶여서 쓰인다. 일별 행을 더해 월간을 만들고, 상품별 행을 더해 카테고리별을 만든다. 그래서 측정값마다 가산성(additivity), 즉 작은 단위의 값을 더해서 큰 단위의 값을 얻을 수 있는지를 따져야 한다.

    측정값일→월로 합칠 수 있나저장 방법
    주문 수 COUNT(*)그대로 더하면 된다(가산)order_count
    매출 합계 SUM(amount)그대로 더하면 된다(가산)amount_sum
    평균 주문 금액 AVG(amount)평균끼리 평균 내면 틀린다(비가산)합계와 건수를 저장하고 읽을 때 나눈다
    최대 주문 금액 MAX(amount)최댓값들의 최댓값으로 합칠 수 있다저장 가능. 단 취소로 최댓값 주문이 빠지면 차감할 방법이 없어 재집계해야 한다
    구매 회원 수 COUNT(DISTINCT member_id)더하면 중복이 생긴다(비가산)회원×일 테이블을 두거나 기간별로 따로 집계한다
    전환율, 객단가 같은 비율비율끼리 합칠 수 없다(비가산)분자와 분모를 각각 저장한다

    평균의 평균은 평균이 아니다

    예를 들어 보자. 첫째 날에는 10만 원짜리 주문이 1건 있었고, 둘째 날에는 1만 원짜리 주문이 9건 있었다. 일별 평균 주문 금액은 10만 원과 1만 원이고, 이 둘의 평균은 5만 5천 원이다. 그러나 이틀 동안의 실제 평균은 총매출 19만 원을 총 주문 10건으로 나눈 1만 9천 원이다. 일별 평균만 저장해 두었다면 주간·월간 평균을 바르게 구할 방법이 없다. 그래서 통계 테이블에는 평균 대신 amount_sum과 order_count를 저장하고, 어떤 기간의 평균이든 SUM(amount_sum) / SUM(order_count)로 구한다. 비율도 같다. 전환율을 저장하지 말고 방문 수와 구매 수를 저장한다.

    고유 건수는 합칠 수 없다

    "이번 달 구매 회원 수"는 더 까다롭다. 어떤 회원이 1일과 2일에 모두 샀다면 일별 구매 회원 수에는 두 번 들어가 있다. 일별 숫자를 더하면 그 회원이 두 번 세어진다. 고유 건수는 "어느 회원들이었는가"라는 집합 정보가 있어야 합칠 수 있는데, 일별 숫자에는 그 정보가 없다. 대안은 두 가지다. 하나는 집합 정보를 줄인 형태로 남기는 것이다. (stat_date, member_id)를 기본 키로 하는 "일별 구매 회원" 테이블을 두면 원본 주문보다 훨씬 작으면서도 월간 고유 회원 수를 COUNT(DISTINCT member_id)로 정확히 구할 수 있다. 다른 하나는 필요한 기간 단위마다 원본에서 따로 집계해 월간 통계 테이블에 저장하는 것이다. 어느 쪽이든 "일별 구매 회원 수를 더해서 월간을 만든다"는 선택지는 없다.

    NULL과 0을 구분한다

    집계 함수는 별도 언급이 없는 한 NULL을 무시하고, 일치하는 행이 없으면 AVG()와 SUM()은 NULL을, COUNT()는 0을 돌려준다. 통계 테이블의 측정값 열을 NOT NULL로 두고 집계 시 COALESCE로 0을 넣어 두면, 읽는 쪽에서 NULL 처리 때문에 합계가 NULL이 되는 일을 피할 수 있다. 반대로 "측정하지 않았음"과 "0이었음"을 구분해야 하는 지표라면 NULL을 허용하고 그 의미를 열 주석에 적어 둔다.

    주간·월간 통계: 일 단위에서 굴려 올리기

    일별 통계가 있으면 주간·월간 통계를 원본에서 다시 계산할 필요가 없다. 이것을 롤업(roll-up)이라고 한다. 가산 측정값은 일별 행을 그대로 더하면 된다.

    -- 2026년 10월 상품별 매출: 일별 통계에서 굴려 올린다
SELECT product_id,
       SUM(order_count)                   AS order_count,
       SUM(amount_sum)                    AS amount_sum,
       SUM(amount_sum) / SUM(order_count) AS avg_order_amount
FROM daily_product_sales
WHERE stat_date >= '2026-10-01' AND stat_date < '2026-11-01'
GROUP BY product_id;

    앞의 가정에서 이 쿼리가 읽는 행은 31일×1,000종, 약 3만 1천 행이다. 기본 키가 (stat_date, product_id)이므로 이 행들은 클러스터형 인덱스에서 연속된 구간에 모여 있고, 엔진은 그 구간의 리프 페이지만 차례로 읽는다.

    기간 조건은 열을 함수로 감싸지 않고 범위로 쓴다

    같은 뜻으로 WHERE YEAR(stat_date) = 2026 AND MONTH(stat_date) = 10이라고 쓸 수도 있다. 결과는 같지만 비용은 전혀 다르다. B+Tree는 stat_date 값 자체의 순서로 정렬되어 있고, MONTH(stat_date)의 순서로 정렬되어 있지 않다. 엔진은 "MONTH()가 10인 첫 항목"의 위치를 트리에서 찾을 수 없으므로 범위 탐색을 하지 못하고, 모든 행에 함수를 적용해 걸러야 한다. 시작은 포함하고 끝은 포함하지 않는 반열린 구간(>= 시작 AND < 다음 시작)으로 쓰면 인덱스 범위 탐색이 되고, 달마다 다른 말일(30일, 31일, 28일)이나 DATETIME 열의 23시 59분 59초 이후 같은 경계 문제도 함께 사라진다.

    주의 시작일로 묶는다

    주간 통계는 경계 정의부터 정해야 한다. 주가 월요일에 시작하는가 일요일에 시작하는가, 연초와 연말에 걸친 주는 어느 해에 속하는가. MySQL의 WEEK(date, mode)는 여덟 가지 모드로 이 규칙을 고르게 한다. 모드 1과 3은 월요일 시작이고 "그해에 4일 이상 포함된 주"를 1주로 삼아 ISO 8601의 주 번호 규칙을 따르는데, 모드 3은 범위가 1~53이고 모드 1은 0~53이다. 모드를 생략하면 default_week_format 시스템 변수 값이 쓰이므로, 서버 설정이 바뀌면 같은 쿼리의 결과가 달라질 수 있다. 주간 집계에서는 모드를 반드시 명시해야 한다.

    모드를 명시해도 함정이 하나 더 있다. 다음처럼 연도와 주 번호를 따로 구해 묶는 쿼리를 보자.

    -- 잘못된 주간 집계: 연도와 ISO 주 번호를 따로 구한다
SELECT YEAR(stat_date) AS y, WEEK(stat_date, 3) AS w, SUM(amount_sum)
FROM daily_product_sales
WHERE stat_date >= '2024-01-01' AND stat_date < '2025-01-06'
GROUP BY YEAR(stat_date), WEEK(stat_date, 3);

    ISO 8601에서 2024년 12월 30일(월)부터 2025년 1월 5일(일)까지는 2025년의 1주다. 그래서 WEEK('2024-12-30', 3)은 1이다. 그런데 YEAR('2024-12-30')은 2024다. 결국 12월 30일과 31일의 매출은 그룹 (2024, 1)에 들어가는데, 이 그룹은 2024년 1월 1일(월)부터 7일까지의 ISO 1주다. 연말 이틀 치 매출이 1년 전 첫 주에 더해지고, (2025, 1) 그룹에는 1월 1일~5일만 남는다. 오류도 경고도 없이 숫자만 틀린다. 매뉴얼은 YEARWEEK()가 돌려주는 연도가 그해의 첫 주와 마지막 주에서 날짜의 연도와 다를 수 있다고 명시한다. 즉 주 번호를 쓸 때는 YEARWEEK(stat_date, 3)처럼 연도와 주를 한 함수에서 함께 구해야 한다.

    더 단순하고 오해의 여지가 없는 방법은 주 번호 대신 그 주의 시작일로 묶는 것이다. WEEKDAY()는 월요일을 0, 일요일을 6으로 돌려주므로, 날짜에서 그만큼 빼면 그 주의 월요일이 나온다.

    SELECT DATE_SUB(stat_date, INTERVAL WEEKDAY(stat_date) DAY) AS week_start,
       product_id,
       SUM(order_count) AS order_count,
       SUM(amount_sum)  AS amount_sum
FROM daily_product_sales
WHERE stat_date >= '2024-12-23' AND stat_date < '2025-01-13'
GROUP BY week_start, product_id;

    2024-12-30부터 2025-01-05까지의 모든 날짜는 week_start가 2024-12-30으로 같아 한 그룹이 된다. 결과 열이 실제 날짜이므로 사람이 읽기도 쉽고, 다른 테이블과 날짜로 조인하기도 쉽다. 이 방식으로 묶을 때는 조회 범위도 주의 시작일(월요일)에서 시작해 다음 주 시작일에서 끝나게 잡아야, 첫 주와 마지막 주가 일부 날짜만 담긴 반쪽 주가 되지 않는다.

    주간·월간 테이블을 따로 둘 때

    일별 통계에서 즉석으로 굴려 올리는 방식이 기본이지만, 별도의 주간·월간 테이블이 필요한 경우가 있다. 첫째, 고유 회원 수 같은 비가산 측정값은 일별 테이블에서 만들 수 없으므로 기간별로 따로 집계해야 한다. 둘째, 몇 년 치 추이를 자주 보는 화면이라면 일별 행조차 많다. 셋째, 월말 확정 숫자처럼 한 번 정하면 바뀌지 않아야 하는 값은 별도 테이블에 고정해 두는 편이 감사(audit)에 유리하다. 이런 상위 테이블은 원본이 아니라 일별 테이블에서 만든다. 원본 300만 행 대신 일별 3만 행을 읽으니 집계 자체가 가볍다. 일별 통계를 다시 집계해 고쳤다면 그 날짜가 속한 주와 월도 다시 굴려 올려야 한다는 의존 관계가 생긴다는 점도 함께 관리해야 한다.

    소계와 합계: WITH ROLLUP

    보고서에는 상품별 행 아래에 전체 합계 행이 붙는 경우가 많다. GROUP BY에 WITH ROLLUP을 붙이면 MySQL이 상위 집계(super-aggregate) 행을 추가로 만들어 준다. 상위 집계 행에서 묶음 기준 열은 NULL로 나오는데, 원래 값이 NULL인 그룹과 구분하려면 GROUPING() 함수를 쓴다. 매뉴얼에 따르면 GROUPING()은 선택 목록과 HAVING에서 쓸 수 있고, MySQL 8.0.12부터는 ORDER BY에서도 쓸 수 있으며, WITH ROLLUP과 ORDER BY를 함께 쓰는 제한도 8.0.12에서 풀렸다.

    SELECT IF(GROUPING(product_id) = 1, '합계', CAST(product_id AS CHAR)) AS product,
       SUM(amount_sum) AS amount_sum
FROM daily_product_sales
WHERE stat_date >= '2026-10-01' AND stat_date < '2026-11-01'
GROUP BY product_id WITH ROLLUP;
    원본 → 일별 → 주간/월간의 계층과, 주와 월은 서로 만들 수 없고 둘 다 일별에서 만든다는 점, 비가산 측정값은 일별을 거치지 않는다는 점을 보여 준다. 아래에서 위로 올라가는 3층 구조 그림. 맨 아래 넓은 띠 "orders 원본(주문 1건 = 1행)". 그 위 가운데 띠 "daily_product_sales(날짜×상품)". 맨 위에 나란히 놓인 두 상자 "주간(주 시작일×상품)"과 "월간(월×상품)". 아래 띠에서 가운데 띠로 굵은 화살표와 라벨 "하루 한 번 집계". 가운데 띠에서 위의 두 상자로 각각 화살표와 라벨 "SUM으로 롤업". 위의 두 상자 사이에 X 표시가 있는 양방향 점선 화살표와 라벨 "서로 만들 수 없음(주가 두 달에 걸침)". 그림 오른쪽에 원본에서 월간 상자로 직접 올라가는 주황색 점선 화살표와 라벨 "고유 회원 수는 원본에서 직접". 평면 스타일, 파랑 계열과 주황 강조. 일은 주와 월을 모두 만들 수 있는 가장 거친 공통 입도다. 고유 건수 같은 비가산 측정값은 이 경로를 탈 수 없다.

    실시간 통계: 동기 카운터와 핫 로우

    하루 한 번 집계하는 통계는 오늘의 숫자를 보여 주지 못한다. "오늘 지금까지의 매출"이 필요해지면 선택지는 크게 셋이다. 주문을 저장하는 트랜잭션 안에서 통계 행도 함께 갱신하는 동기 카운터, 확정된 과거는 통계 테이블에서 읽고 오늘은 원본에서 읽는 하이브리드 조회, 그리고 몇 분 간격으로 짧게 집계하는 마이크로 배치다. 먼저 가장 직관적인 동기 카운터부터 본다.

    START TRANSACTION;

INSERT INTO orders (member_id, product_id, quantity, amount, ordered_at)
VALUES (7, 10, 2, 30000.00, '2026-11-17 10:04:58');

-- 같은 트랜잭션에서 통계 행을 1건 늘린다. stat_date는 주문의 ordered_at에서 구한다
INSERT INTO daily_product_sales
  (stat_date, product_id, order_count, quantity_sum, amount_sum, aggregated_at)
VALUES ('2026-11-17', 10, 1, 2, 30000.00, NOW()) AS new
ON DUPLICATE KEY UPDATE
  order_count   = daily_product_sales.order_count  + new.order_count,
  quantity_sum  = daily_product_sales.quantity_sum + new.quantity_sum,
  amount_sum    = daily_product_sales.amount_sum   + new.amount_sum,
  aggregated_at = new.aggregated_at;

COMMIT;

    장점은 분명하다. 주문과 통계가 한 트랜잭션이므로 둘은 항상 함께 커밋되거나 함께 롤백된다. 지연도 없고 중복 계산도 없다. 주석에 적은 대로 stat_date는 반드시 주문의 시각에서 구해야 한다. 주문은 애플리케이션이 정한 ordered_at으로, 통계는 CURDATE()로 날짜를 정하면 자정 직전에 들어온 주문이 23시 59분 59초로 저장되고 통계는 다음 날짜로 올라가는 일이 생긴다. 두 문장이 서로 다른 시각에 실행되기 때문이다. 하나의 사실(이 주문의 날짜)은 한 번만 정하고 양쪽에서 같은 값을 쓴다.

    같은 행을 향한 줄서기

    문제는 잠금이다. 매뉴얼에 따르면 INSERT ... ON DUPLICATE KEY UPDATE는 중복이 발생하면 갱신할 행에 배타 잠금을 걸고, 기본 키 중복이면 배타 인덱스 레코드 잠금(exclusive index-record lock)이다. InnoDB의 행 잠금은 트랜잭션이 끝날 때까지 유지된다. 그러니 오늘 상품 10을 주문하는 모든 트랜잭션은 ('2026-11-17', 10)이라는 행 하나의 잠금을 차례로 기다린다. 인기 상품일수록 대기가 길어진다. 이렇게 여러 트랜잭션이 몰리는 행을 핫 로우(hot row)라고 부른다.

    시간 →
T1 주문(상품 10) : INSERT orders ─ UPSERT 통계[X 잠금 획득] ─ ... ─ COMMIT[해제]
T2 주문(상품 10) : INSERT orders ─ UPSERT 통계[대기............] ─[획득] ─ COMMIT
T3 주문(상품 10) : INSERT orders ─ UPSERT 통계[대기..........................] ─[획득] ─ COMMIT

주문 저장은 병렬로 진행되지만, 통계 행 갱신부터 커밋까지는 한 줄로 선다.
한 행의 처리량 상한 ≈ 1 / (UPSERT부터 COMMIT까지 잠금을 쥐고 있는 시간)

    그림에서 보듯 줄을 서는 구간은 통계 행을 갱신한 순간부터 커밋까지다. 그래서 동기 카운터를 쓴다면 통계 UPSERT를 트랜잭션의 맨 마지막, 커밋 바로 앞에 둔다. 그 뒤에 결제 승인 API 호출 같은 느린 작업이 있으면 그 시간만큼 모든 대기자가 함께 기다린다. 앞에서 본 대로 매뉴얼도 카운터 테이블을 권하는 같은 자리에서, 수천 개의 동시 트랜잭션이 같은 카운터를 갱신하면 잘 확장되지 않을 수 있다고 경고한다.

    교착 상태와 장애 전파

    장바구니 주문처럼 한 트랜잭션이 상품 여러 개의 통계 행을 갱신하면 교착 상태(deadlock)도 생긴다. T1이 상품 10, 15 순서로, T2가 상품 15, 10 순서로 갱신하면 T1은 10을 쥐고 15를, T2는 15를 쥐고 10을 기다린다. InnoDB는 교착 상태를 감지해 한쪽을 롤백한다. 그 한쪽은 통계가 아니라 주문 전체다. 매뉴얼의 교착 상태 대응 절은 같은 테이블의 여러 행을 바꿀 때 매번 일관된 순서로 하라고 권한다. 통계 행은 항상 기본 키 순서(stat_date, product_id 오름차순)로 갱신하면 트랜잭션들이 같은 순서로 줄을 서서 순환 대기가 생기지 않는다. 동기 카운터의 또 다른 비용은 장애 전파다. 통계 행의 잠금 대기가 시간 초과로 끝나면 주문이 실패한다. 부가 기능인 통계가 핵심 기능인 주문의 가용성을 끌어내리는 구조다.

    카운터를 쪼개기

    한 행에 몰리는 경합을 줄이는 방법은 행을 여러 개로 쪼개는 것이다. 기본 키에 slot 열을 추가해 (stat_date, product_id, slot)으로 만들고, 주문마다 slot = order_id % 8처럼 정해진 규칙으로 여덟 칸 가운데 하나를 갱신한다. 같은 상품의 주문이 여덟 개의 행에 흩어지므로 한 행을 기다리는 트랜잭션 수가 줄어든다. 읽을 때는 SUM()으로 슬롯을 합친다. 측정값이 가산적이어야 쓸 수 있는 방법이고, 읽는 행 수가 슬롯 수만큼 늘어나는 비용을 낸다. 슬롯을 무작위가 아니라 주문 번호에서 정하면 나중에 원본과 대조할 때 어떤 주문이 어느 슬롯에 들어갔는지 재현할 수 있다.

    하이브리드 설계: 확정 구간과 진행 구간

    동기 카운터의 잠금 비용을 피하면서 오늘의 숫자도 보여 주려면, 시간을 두 구간으로 나눈다. 이미 끝나서 더 이상 바뀌지 않는 확정 구간은 통계 테이블에서 읽고, 아직 진행 중인 진행 구간은 원본에서 그때그때 집계한다. 진행 구간은 많아야 하루치이므로 원본 집계도 감당할 만한 크기다.

    설계의 핵심은 두 구간의 경계를 무엇으로 정하느냐다. 가장 쉬운 답은 "어제까지는 통계, 오늘은 원본"이다. 그러나 이 규칙은 어제 치 집계 배치가 끝났다고 가정한다. 배치가 실패했거나 아직 돌고 있으면 어제는 통계 테이블에도 없고 원본 쪽 조건에도 걸리지 않아, 하루치 매출이 조용히 사라진다. 경계는 달력이 아니라 집계가 실제로 끝난 지점이어야 한다. 이것을 기록하는 행을 워터마크(watermark)라고 부르자.

    CREATE TABLE stat_watermark (
  stat_name    VARCHAR(50) NOT NULL,
  closed_until DATE        NOT NULL,   -- 이 날짜까지는 통계 테이블이 확정되어 있다
  updated_at   DATETIME    NOT NULL,
  PRIMARY KEY (stat_name)
);

    배치는 어떤 날짜의 통계 행을 다 쓴 뒤, 같은 트랜잭션 안에서 closed_until을 그 날짜로 올린다. 통계 행만 커밋되고 워터마크가 올라가지 않은 상태가 바깥에 보이면 그날이 통계와 원본 양쪽에서 두 번 세어지고, 반대로 워터마크만 먼저 올라가면 그날이 어느 쪽에도 없다. 한 트랜잭션으로 묶으면 다른 세션은 MVCC 덕분에 둘 다 바뀌기 전이나 둘 다 바뀐 후만 본다. 조회는 워터마크를 먼저 읽고 그 값을 두 쿼리의 경계로 쓴다.

    -- 1) SELECT closed_until FROM stat_watermark WHERE stat_name = 'daily_product_sales';
--    결과가 '2026-11-16' 이라고 하자. 이번 달(11월) 상품별 매출:
SELECT product_id,
       SUM(order_count) AS order_count,
       SUM(amount_sum)  AS amount_sum
FROM (
    SELECT product_id, order_count, amount_sum
    FROM daily_product_sales
    WHERE stat_date >= '2026-11-01' AND stat_date <= '2026-11-16'   -- 확정 구간
    UNION ALL
    SELECT product_id, COUNT(*), SUM(amount)
    FROM orders
    WHERE ordered_at >= '2026-11-17'                                 -- 진행 구간
    GROUP BY product_id
) AS t
GROUP BY product_id;

    어제 배치가 실패해 워터마크가 '2026-11-15'에 머물러 있으면, 같은 쿼리를 그 값으로 만들면 확정 구간은 15일까지, 진행 구간은 16일 0시부터가 된다. 배치가 늦어진 만큼 원본을 조금 더 읽을 뿐 숫자는 빠지지 않는다. 경계가 두 쿼리에 명시적으로 들어가므로, 조회 도중에 배치가 커밋되어 워터마크가 올라가도 이번 조회는 자신이 읽은 경계를 일관되게 쓴다.

    UNION이 아니라 UNION ALL

    두 결과를 합칠 때 UNION을 쓰면 안 된다. UNION은 중복 행을 제거한다. 통계 쪽에서 나온 (상품 10, 3건, 45,000원) 행과 원본 쪽에서 나온 (상품 10, 3건, 45,000원) 행은 서로 다른 기간의 숫자인데도 값이 같다는 이유로 하나로 합쳐져, 바깥 SUM()에는 한 번만 더해진다. 같은 상품 여러 날짜의 통계 행끼리도 마찬가지다. 값이 우연히 같은 행이 한 번만 세어진다. 이 오류는 데이터에 따라 나타났다 사라지기 때문에 테스트에서 잡히기 어렵다. 행을 합쳐서 다시 더하는 용도에는 항상 UNION ALL을 쓴다.

    진행 구간을 작게 유지하기

    진행 구간의 원본 집계는 하루가 지날수록 커진다. 앞의 가정이라면 자정 직후에는 거의 0행이지만 밤 11시에는 10만 행 가까이 읽는다. 진행 구간 쿼리는 ordered_at 범위가 앞에 오고 필요한 열을 모두 담은 커버링 인덱스(예: (ordered_at, product_id, amount))가 있으면 실제 행을 읽지 않고 보조 인덱스의 연속 구간만 읽는다. 그래도 하루치가 부담스러우면 확정 구간의 입도를 더 잘게 만든다. 시간 단위 통계를 두고 "지난 시간까지는 시간 통계, 이번 시간은 원본"으로 나누면 원본에서 읽는 양은 많아야 한 시간치다. 결국 하이브리드 설계는 "원본에서 읽는 구간의 길이"를 집계 주기로 조절하는 설계이고, 이것을 끝까지 밀고 가면 다음 절의 마이크로 배치가 된다.

    확정된 과거가 바뀔 때

    "확정 구간은 바뀌지 않는다"는 가정이 깨지는 경우도 있다. 지난주 주문이 오늘 취소되거나 환불되면 지난주 통계는 틀린 숫자가 된다. 대응은 두 가지 모델 가운데 하나를 고르는 것이다. 첫째는 발생 기준이다. 매출을 주문이 일어난 날짜에 귀속시키고, 과거 주문이 바뀌면 그 날짜의 통계를 다시 집계한다. 바뀐 주문들의 날짜 목록을 모아 해당 날짜만 재집계하면 된다. 둘째는 처리 기준이다. 취소를 취소가 일어난 날의 음수 거래로 기록해, 과거 행은 건드리지 않고 오늘 통계에 반영한다. 회계 장부가 과거 전표를 고치지 않고 반대 전표를 쓰는 방식과 같다. 두 모델 모두 타당하지만 같은 "11월 매출"이 서로 다른 숫자가 된다. 어느 모델인지 정하지 않고 화면마다 섞어 쓰면 정산팀의 숫자와 대시보드의 숫자가 영원히 맞지 않는다.

    시간축 위에서 워터마크 왼쪽은 통계 테이블, 오른쪽은 원본에서 읽고 UNION ALL로 합친다는 것과, 배치가 늦어지면 경계가 왼쪽에 머물러 원본 구간이 넓어진다는 것을 보여 준다. 가로 시간축 그림. 축 아래 날짜 눈금 "11-01", "11-15", "11-16", "11-17", 오른쪽 끝에 "지금". 11-16과 11-17 사이에 굵은 세로 점선을 긋고 라벨 "워터마크 closed_until". 점선 왼쪽 구간 전체를 파란 띠로 칠하고 라벨 "확정 구간: daily_product_sales". 점선 오른쪽에서 "지금"까지를 주황 띠로 칠하고 라벨 "진행 구간: orders 원본". 두 띠에서 아래로 화살표가 내려가 가운데 상자 "UNION ALL 후 SUM"으로 모인다. 그림 아래쪽에 작은 보조 타임라인을 하나 더 그리고, 워터마크가 11-15와 11-16 사이에 있으며 주황 띠가 이틀로 넓어진 모습, 라벨 "배치가 늦으면 원본 구간이 넓어질 뿐 빠지지 않음". 평면 스타일. 경계를 달력이 아니라 집계가 끝난 지점으로 잡으면, 배치가 늦어져도 숫자가 빠지지 않는다.

    멱등성 설계: 다시 돌려도 같은 결과

    집계 배치는 반드시 다시 실행된다. 스케줄러가 응답 시간 초과를 실패로 보고 재시도했는데 사실 첫 실행은 성공했을 수 있다. 집계 로직의 버그를 고친 뒤 지난 한 달을 다시 돌려야 할 수도 있다. 늦게 들어온 데이터를 반영하려고 같은 날짜를 또 집계하기도 하고, 서버 이중화 설정 실수로 두 대에서 같은 작업이 동시에 뜨기도 한다. 그래서 집계 작업은 멱등(idempotent)해야 한다. 같은 입력에 대해 한 번 실행하든 여러 번 실행하든 결과 상태가 같아야 한다는 뜻이다.

    더하기는 멱등하지 않다

    가장 흔한 실수는 "기존 값에 더하는" 집계를 날짜 단위 배치에 쓰는 것이다. ON DUPLICATE KEY UPDATE order_count = order_count + c 형태로 하루치를 반영하는 배치를 두 번 돌리면 그날의 숫자는 정확히 두 배가 된다. 오류도 나지 않는다. 흥미롭게도 기본 키가 (stat_date, product_id)인 테이블에 단순 INSERT ... SELECT를 두 번 실행하면 두 번째 실행은 중복 키 오류로 실패한다. 실패는 시끄럽지만 적어도 숫자를 틀리게 만들지는 않는다. 대리 키만 있고 차원 조합에 유니크 제약이 없는 테이블이었다면 같은 날짜·상품 행이 두 벌 저장되고 합계가 두 배가 되었을 것이다. 입도를 기본 키로 선언하는 것은 이런 사고를 데이터베이스가 막게 하는 장치이기도 하다.

    멱등하게 만드는 방법은 세 가지다. 어떤 기간을 통째로 다시 계산해 그 결과로 교체하거나, 계산한 값을 더하지 않고 덮어쓰거나, 더하되 같은 입력을 두 번 더하지 않도록 처리 이력을 남기는 것이다.

    방법 1: 기간 단위로 지우고 다시 넣기

    SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;  -- 이유는 아래에서

START TRANSACTION;

DELETE FROM daily_product_sales WHERE stat_date = '2026-11-16';

INSERT INTO daily_product_sales
  (stat_date, product_id, order_count, quantity_sum, amount_sum, aggregated_at)
SELECT DATE(ordered_at), product_id, COUNT(*), SUM(quantity), SUM(amount), NOW()
FROM orders
WHERE ordered_at >= '2026-11-16' AND ordered_at < '2026-11-17'
GROUP BY DATE(ordered_at), product_id;

UPDATE stat_watermark
SET closed_until = GREATEST(closed_until, '2026-11-16'), updated_at = NOW()
WHERE stat_name = 'daily_product_sales';

COMMIT;

    이 트랜잭션은 몇 번을 실행해도 결과가 같다. 매번 그날의 행을 모두 지우고 원본에서 새로 계산한 행으로 채우기 때문이다. 원본에서 그날 주문이 모두 취소되어 사라진 상품의 행도 지워진 채로 남으니, 재계산 결과와 테이블 상태가 정확히 일치한다. 워터마크 갱신에 GREATEST()를 쓴 것은 지난 날짜를 재집계할 때 워터마크가 뒤로 물러나지 않게 하려는 것이다.

    이 사이에 대시보드가 통계 테이블을 읽으면 어떻게 될까. 다른 세션의 일반 SELECT는 일관된 읽기이므로 커밋된 데이터만 본다. 이 트랜잭션이 커밋되기 전에는 지우기 전의 행을, 커밋된 뒤에는 새 행을 본다. "그날 행이 텅 빈 순간"은 바깥에서 보이지 않는다. 지우기와 넣기를 각각 자동 커밋으로 실행하면 이 보장이 사라진다는 점도 함께 기억하자.

    격리 수준을 READ COMMITTED로 바꾼 이유는 원본 테이블의 잠금이다. 매뉴얼은 INSERT INTO T SELECT ... FROM S가 격리 수준이 READ COMMITTED면 S를 일관된 읽기로(잠금 없이) 검색하고, 그렇지 않으면 S의 행에 공유 next-key 잠금을 건다고 설명한다. 기본값인 REPEATABLE READ에서 위 배치를 돌리면, 하루치 주문 행과 그 사이 간격에 공유 잠금이 걸린다. 그 행을 바꾸려는 주문 상태 변경이나 그 간격에 들어갈 주문 삽입은 배치가 커밋할 때까지 기다린다. 매뉴얼은 이렇게 잠그는 이유를 문장 기반 바이너리 로그로 복구할 때 모든 문장이 원래와 똑같이 실행되어야 하기 때문이라고 밝힌다. 같은 매뉴얼은 READ COMMITTED에서는 행 기반 바이너리 로그만 지원한다고 명시하므로, 이 설정은 행 기반 복제(MySQL 8.0의 기본) 환경을 전제로 한다.

    방법 2: 덮어쓰는 UPSERT

    지우지 않고 계산 결과로 덮어쓸 수도 있다. 이때 갱신 절은 더하기가 아니라 대입이다. 매뉴얼은 INSERT ... SELECT ... ON DUPLICATE KEY UPDATE에서 GROUP BY를 쓰는 SELECT의 열을 갱신 절에서 참조하려면 쿼리를 파생 테이블(derived table)로 감싸라고 안내한다.

    INSERT INTO daily_product_sales
  (stat_date, product_id, order_count, quantity_sum, amount_sum, aggregated_at)
SELECT * FROM (
    SELECT DATE(ordered_at) AS d, product_id AS p,
           COUNT(*) AS c, SUM(quantity) AS q, SUM(amount) AS a, NOW() AS t
    FROM orders
    WHERE ordered_at >= '2026-11-16' AND ordered_at < '2026-11-17'
    GROUP BY DATE(ordered_at), product_id
) AS dt
ON DUPLICATE KEY UPDATE
  order_count   = c,      -- 더하지 않고 대입한다: 몇 번을 실행해도 같다
  quantity_sum  = q,
  amount_sum    = a,
  aggregated_at = t;

    덮어쓰기는 "이번 계산에 나온 행"에 대해서만 멱등하다. 첫 실행 때는 상품 20의 주문이 3건 있었는데 그 뒤 모두 삭제되었다면, 두 번째 실행의 SELECT에는 상품 20이 나오지 않으므로 기존 행이 3건인 채로 남는다. 이 남은 행까지 정리하려면 실행마다 고유한 실행 번호를 열에 기록해 두고, 덮어쓰기가 끝난 뒤 그 날짜에서 실행 번호가 다른 행을 지우는 단계를 덧붙여야 한다. 하루치를 통째로 다시 만드는 작업이라면 방법 1이 더 단순하다. 덮어쓰기는 기간 전체가 아니라 일부 키만 고쳐 쓰는 작업, 예를 들어 바뀐 주문이 있는 상품만 다시 계산하는 경우에 어울린다. 덧붙여 매뉴얼은 INSERT ... SELECT ... ON DUPLICATE KEY UPDATE 문장을 문장 기반 복제에서 안전하지 않은 문장으로 분류한다. 행 기반 복제에서는 문제가 없다.

    방법 3: 처리한 이벤트를 기록하기

    동기 카운터나 이벤트 소비자처럼 건별로 더해야 하는 경우에는 교체도 덮어쓰기도 쓸 수 없다. 이때는 "이 입력을 이미 반영했는가"를 기록해 두고, 기록과 반영을 한 트랜잭션으로 묶는다.

    CREATE TABLE stat_applied_event (
  event_id   BIGINT   NOT NULL,     -- 예: 주문 완료 이벤트의 주문 번호
  applied_at DATETIME NOT NULL,
  PRIMARY KEY (event_id)
);

START TRANSACTION;
INSERT INTO stat_applied_event (event_id, applied_at) VALUES (1001, NOW());
-- 이미 반영한 이벤트면 여기서 중복 키 오류(1062)가 난다 → 롤백하고 "이미 처리됨"으로 끝낸다
INSERT INTO daily_product_sales
  (stat_date, product_id, order_count, quantity_sum, amount_sum, aggregated_at)
VALUES ('2026-11-17', 10, 1, 2, 30000.00, NOW()) AS new
ON DUPLICATE KEY UPDATE
  order_count   = daily_product_sales.order_count  + new.order_count,
  quantity_sum  = daily_product_sales.quantity_sum + new.quantity_sum,
  amount_sum    = daily_product_sales.amount_sum   + new.amount_sum,
  aggregated_at = new.aggregated_at;
COMMIT;

    같은 이벤트가 두 번 와도 두 번째는 첫 문장에서 막힌다. 두 문장이 한 트랜잭션이므로 "기록은 됐는데 반영은 안 됨"이나 "반영은 됐는데 기록은 안 됨" 상태가 생기지 않는다. 메시지 브로커가 "최소 한 번(at-least-once)" 전달만 보장하더라도, 데이터베이스 쪽에서 결과를 한 번만 반영하게 만드는 구조다. 처리 이력 테이블은 계속 커지므로, 재전달이 일어날 수 있는 기간이 지난 행은 정기적으로 지운다.

    멱등성과 동시 실행은 다른 문제다

    멱등성은 "차례로 여러 번" 실행해도 같다는 성질이지, "동시에 두 번" 실행해도 안전하다는 보장이 아니다. 같은 날짜를 두 세션이 동시에 지우고 넣으면 서로의 행 잠금을 기다리게 되고, 원본 하루치를 두 번 읽는 낭비도 생긴다. 그래서 집계 작업에는 동시 실행을 막는 장치를 함께 둔다. 작업 이름과 대상 날짜를 기본 키로 하는 실행 기록 테이블의 행을 잠그거나, MySQL의 이름 있는 잠금 함수 GET_LOCK()으로 "daily_product_sales:2026-11-16" 같은 이름을 선점하는 식이다. 실행 기록 테이블은 언제, 어떤 범위를, 몇 행으로 집계했는지를 남겨 두므로 나중에 숫자가 이상할 때 추적의 출발점도 된다.

    마이크로 배치와 늦게 커밋되는 행

    하루 한 번 배치와 실시간 동기 카운터 사이에는 마이크로 배치(micro-batch)가 있다. 1분이나 5분 같은 짧은 주기로 "지난번 이후 들어온 데이터"만 집계해 통계 테이블에 더하는 방식이다. 주문 트랜잭션은 통계 행을 건드리지 않으므로 핫 로우 경합이 없고, 통계는 주기만큼만 늦다. 한 번에 처리하는 양이 작으므로 배치 하나가 잡는 잠금과 만드는 undo도 작다. 구현은 보통 "어디까지 처리했는가"를 기록하는 커서를 두고, 매 주기마다 커서부터 지금까지를 하나의 창(window)으로 집계한다.

    CREATE TABLE stat_cursor (
  stat_name         VARCHAR(50) NOT NULL,
  last_processed_at DATETIME    NOT NULL,   -- 이 시각 이전의 주문은 반영했다
  PRIMARY KEY (stat_name)
);

START TRANSACTION;
SELECT last_processed_at FROM stat_cursor
WHERE stat_name = 'daily_product_sales' FOR UPDATE;      -- '2026-11-17 10:00:00'

INSERT INTO daily_product_sales
  (stat_date, product_id, order_count, quantity_sum, amount_sum, aggregated_at)
SELECT * FROM (
    SELECT DATE(ordered_at) AS d, product_id AS p,
           COUNT(*) AS c, SUM(quantity) AS q, SUM(amount) AS a, NOW() AS t
    FROM orders
    WHERE ordered_at >= '2026-11-17 10:00:00' AND ordered_at < '2026-11-17 10:05:00'
    GROUP BY DATE(ordered_at), product_id
) AS dt
ON DUPLICATE KEY UPDATE
  order_count   = order_count  + c,     -- 창 하나의 증분을 더한다
  quantity_sum  = quantity_sum + q,
  amount_sum    = amount_sum   + a,
  aggregated_at = t;

UPDATE stat_cursor SET last_processed_at = '2026-11-17 10:05:00'
WHERE stat_name = 'daily_product_sales';
COMMIT;

    여기서는 더하기를 쓰는데도 멱등성이 지켜진다. 증분 반영과 커서 이동이 한 트랜잭션이기 때문이다. 커밋 전에 실패하면 둘 다 롤백되어 같은 창을 다시 처리하고, 커밋 후에는 커서가 이미 다음 창을 가리킨다. 커서를 별도 트랜잭션으로 옮기면 "증분은 커밋됐는데 커서는 그대로"인 순간에 장애가 나서 같은 창이 두 번 더해진다. 방법 3의 처리 이력과 같은 원리를 창 단위로 적용한 것이다. FOR UPDATE로 커서 행을 잠그는 것은 같은 작업이 동시에 두 번 뜨는 것을 막는 역할도 한다.

    창의 경계를 넘어가는 행

    이 구조에는 놓치기 쉬운 구멍이 있다. 행의 시각(ordered_at)은 INSERT를 실행할 때, 혹은 그보다 앞서 애플리케이션이 정하지만, 다른 세션에 보이는 시점은 커밋할 때다. 그 사이의 시간이 창의 경계를 넘으면 다음과 같은 일이 일어난다. 배치 세션이 READ COMMITTED로 동작한다고 하자.

    시각       주문 트랜잭션 T1                    마이크로 배치
10:04:58   INSERT 주문 1001 (ordered_at=10:04:58)
10:04:59   (재고 차감, 포인트 적립 등 진행 중)
10:05:00                                       창 [10:00, 10:05) 집계
                                               → 1001은 아직 커밋 전이라 보이지 않음
                                               → 커서를 10:05:00으로 이동, 커밋
10:05:01   COMMIT
10:10:00                                       창 [10:05, 10:10) 집계
                                               → 1001의 ordered_at=10:04:58은 범위 밖

결과: 주문 1001은 어느 창에도 들어가지 않는다

    READ COMMITTED의 일관된 읽기는 커밋되지 않은 행을 건너뛰므로 첫 창에서 빠지고, 시각이 이미 지난 창에 속하므로 두 번째 창에서도 빠진다. 자동 증가 기본 키를 커서로 써도 같은 일이 생긴다. 번호는 INSERT 시점에 할당되지만 커밋 순서는 번호 순서와 다를 수 있다. 1001번이 할당된 뒤 1002번이 먼저 커밋되면, 배치는 1002번까지 처리하고 커서를 옮기며 1001번은 나중에 커밋되어도 영영 처리되지 않는다.

    격리 수준을 REPEATABLE READ로 두면 사정이 조금 다르다. 앞에서 본 대로 이때 INSERT ... SELECT는 원본 행에 공유 next-key 잠금을 걸며 읽는다. 잠금 읽기는 이미 인덱스에 들어와 있는 커밋 전 행을 만나면 그 트랜잭션이 끝날 때까지 기다리므로, 위 그림의 1001번은 배치가 기다렸다가 포함한다. 그 대신 배치가 읽는 동안 그 범위의 간격도 잠기므로 해당 간격에 들어갈 주문 삽입이 막히고, INSERT 문 자체가 배치의 스캔보다 늦게 실행된 행(애플리케이션이 시각을 정해 두고 한참 뒤에 저장한 행)은 여전히 놓친다. 격리 수준으로는 이 문제를 없앨 수 없다.

    구멍을 메우는 방법

    • 안전 지연을 둔다. 창의 끝을 "지금"이 아니라 "지금에서 일정 시간 전"으로 잡는다. 10:05에 [09:58, 10:03)을 처리하는 식이다. 트랜잭션이 그 지연보다 짧게 끝난다면 빠지는 행이 없다. 하지만 트랜잭션 길이에 상한이 있다는 보장은 데이터베이스가 해 주지 않으므로, 이것만으로는 확률을 낮출 뿐이다.
    • 진행 중인 날을 통째로 덮어쓴다. 증분을 더하지 않고, 매 주기마다 오늘 0시부터 지금까지를 방법 2처럼 덮어쓴다. 늦게 커밋된 행도 다음 주기에 오늘 전체를 다시 셀 때 들어간다. 멱등하고 구멍이 없지만, 주기마다 읽는 양이 하루가 지날수록 커진다. 앞에서 본 커버링 인덱스와 함께 쓰면 하루치 정도는 감당할 수 있는 경우가 많다.
    • 보정 배치를 둔다. 짧은 주기의 증분 집계는 최신성을 위해 쓰고, 하루가 끝난 뒤 넉넉한 지연을 두고 그날 전체를 방법 1로 다시 만든다. 마이크로 배치가 놓친 행은 다음 날 새벽에 바로잡히고, 워터마크는 이 보정 배치가 끝났을 때만 올린다. 하이브리드 조회의 확정 구간은 보정까지 끝난 날짜만 가리키게 된다.

    어느 방법을 고르든 핵심은 같다. 시각이나 번호를 기준으로 "여기까지 처리했다"고 선언하는 순간, 그 기준보다 앞선 값을 가진 행이 나중에 보일 수 있다는 사실을 설계에 넣어야 한다. 데이터베이스가 행에 붙이는 시각과 번호는 커밋 순서를 뜻하지 않는다.

    주문 트랜잭션의 INSERT 시각과 COMMIT 시각 사이에 배치의 창 경계가 끼면, 행이 어느 창에도 포함되지 않는다는 것을 보여 준다. 세로 생명선 두 개의 시퀀스 다이어그램. 왼쪽 생명선 "주문 트랜잭션 T1", 오른쪽 생명선 "마이크로 배치". 위에서 아래로 시간이 흐른다. 왼쪽 위에 "10:04:58 INSERT 주문 1001"이라는 점. 그 아래 오른쪽 생명선에 "10:05:00 창 [10:00, 10:05) 집계" 상자가 있고 왼쪽 점을 향한 점선 화살표에 빨간 X와 라벨 "커밋 전이라 보이지 않음". 그 아래 왼쪽에 "10:05:01 COMMIT" 점. 맨 아래 오른쪽에 "10:10:00 창 [10:05, 10:10) 집계" 상자가 있고 1001을 향한 점선 화살표에 빨간 X와 라벨 "시각이 범위 밖". 다이어그램 아래에 강조 상자 "주문 1001은 어느 창에도 들어가지 않음". 단순한 선과 상자, 흰 배경. 행의 시각은 INSERT 때 정해지지만 보이는 것은 COMMIT 이후다. 그 사이에 창의 경계가 끼면 행이 빠진다.

    UPSERT 최적화

    통계 테이블에 쓰는 거의 모든 경로, 즉 동기 카운터, 덮어쓰기 재집계, 마이크로 배치가 "없으면 넣고 있으면 고친다"는 UPSERT로 귀결된다. MySQL에서 이것을 한 문장으로 하는 방법이 INSERT ... ON DUPLICATE KEY UPDATE(이하 ODKU)다. 문장 하나가 행마다 삽입을 시도하고, 기본 키나 유니크 키가 충돌하면 그 행에 갱신 절을 적용한다. 이 절에서는 ODKU를 빠르고 안전하게 쓰는 데 필요한 사실들을 모은다.

    행 별칭과 VALUES() 함수

    갱신 절에서 "새로 넣으려던 값"을 가리키는 방법은 버전에 따라 다르다. 오래된 코드에서는 VALUES(amount_sum)처럼 VALUES() 함수를 쓴다. 매뉴얼에 따르면 MySQL 8.0.19부터 VALUES나 SET 절 뒤에 AS new처럼 행 별칭(row alias)을 붙일 수 있고, 8.0.20부터 VALUES() 함수로 새 행을 가리키는 방식은 폐기 예정(deprecated)이 되어 이후 버전에서 제거될 수 있다. 행 별칭은 테이블 이름과 같으면 안 된다(같게 쓰면 ERROR 1066 (42000): Not unique table/alias가 난다). 갱신 절에서 new.order_count는 넣으려던 값을, daily_product_sales.order_count처럼 테이블 이름으로 한정한 열은 테이블에 이미 있는 행의 값을 가리킨다. 같은 이름의 열이 별칭 쪽과 테이블 쪽에 모두 있으므로, 대입식 오른쪽에 order_count처럼 한정 없이 쓰면 MySQL 8.0.46과 8.4.13 모두 ERROR 1052 (23000): Column 'order_count' in field list is ambiguous로 문장을 거부한다. 대입식 왼쪽의 열 이름은 갱신할 테이블의 열이므로 한정하지 않아도 된다. 이 회차의 ODKU 예제가 기존 값을 테이블 이름으로 한정해 쓰는 이유다. AS new(d, p, c, q, a, t)처럼 행 별칭에 열 별칭을 함께 붙여 이름이 겹치지 않게 하면 order_count = order_count + c로 쓸 수도 있다. 옛 VALUES() 함수 형태는 8.4.13에서도 실행되지만 경고 1287('VALUES function' is deprecated and will be removed in a future release.)이 붙는다.

    영향받은 행 수 읽기

    ODKU의 영향받은 행 수(affected rows)는 행마다 다르게 센다. 매뉴얼에 따르면 새 행으로 삽입되면 1, 기존 행이 갱신되면 2, 기존 행을 현재 값과 같은 값으로 설정하면 0이다. 클라이언트가 CLIENT_FOUND_ROWS 플래그로 접속하면 마지막 경우가 0이 아니라 1이 된다. 그러니 세 행짜리 ODKU가 3을 돌려줬다고 해서 "세 행이 삽입되었다"고 읽으면 안 된다. 하나가 갱신(2)되고 하나가 삽입(1)되고 하나는 값이 같아 그대로(0)였을 수도 있다. 값이 같으면 0이 되는 것은 일반 UPDATE와 같은 원리다. 매뉴얼은 열을 이미 가진 값으로 설정하면 MySQL이 이를 알아차리고 갱신하지 않는다고 설명한다. 덮어쓰기 재집계에서 대부분의 숫자가 그대로라면, 바뀌지 않는 aggregated_at 같은 열까지 매번 새 시각으로 바꾸지 않는 편이 실제로 쓰는 행을 줄인다. 반대로 "언제 마지막으로 확인했는가"가 필요하다면 그 비용을 감수하고 갱신한다.

    ODKU가 거는 잠금과 애플리케이션 UPSERT의 교착 상태

    ODKU 대신 애플리케이션에서 UPSERT를 흉내 내는 방법이 두 가지 흔히 쓰인다. 하나는 SELECT로 행이 있는지 보고 없으면 INSERT, 있으면 UPDATE하는 것이다. 두 세션이 동시에 "없음"을 보고 둘 다 INSERT하면 하나는 중복 키 오류로 실패한다. JPA의 merge()로 통계 엔티티를 저장하는 코드도 식별자로 조회한 뒤 없으면 새로 저장하는 같은 구조라 같은 경쟁을 겪는다. 다른 하나는 일단 INSERT하고, 중복 키 오류가 나면 UPDATE하는 것이다. 이 방식에는 더 미묘한 함정이 있다. 매뉴얼에 따르면 일반 INSERT가 중복 키 오류를 만나면 중복된 인덱스 레코드에 공유 잠금을 건다. 두 세션이 같은 행에 대해 동시에 오류를 만나면 둘 다 공유 잠금을 쥔 상태에서 UPDATE를 위해 배타 잠금을 요청하고, 서로의 공유 잠금 때문에 어느 쪽도 배타 잠금을 얻지 못해 교착 상태가 된다. 매뉴얼은 세 세션이 같은 키를 INSERT하는 예로 이 상황을 직접 보여 준다.

    ODKU는 이 문제를 엔진 안에서 처리한다. 매뉴얼은 ODKU가 일반 INSERT와 달리 중복 키 오류가 났을 때 갱신할 행에 공유 잠금이 아니라 배타 잠금을 건다고 설명한다. 처음부터 배타 잠금을 잡으므로 "공유 잠금을 쥔 채 배타 잠금으로 올리려다 막히는" 단계가 없다. 같은 절에 따르면 중복된 값이 기본 키면 배타 인덱스 레코드 잠금이, 유니크 보조 키면 배타 next-key 잠금이 걸린다. next-key 잠금은 레코드와 그 앞의 간격까지 잠그므로 범위가 더 넓다. 통계 테이블의 입도를 대리 키 옆의 유니크 키가 아니라 기본 키로 선언해야 하는 또 하나의 이유다.

    여러 행을 한 문장으로, 적당한 크기로 커밋

    마이크로 배치나 이벤트 소비자가 1,000개의 키를 갱신해야 한다면, ODKU 1,000번보다 여러 VALUES 목록을 가진 문장 몇 개가 훨씬 낫다. 매뉴얼의 INSERT 최적화 절은 행 하나를 넣는 시간을 접속(3), 쿼리 전송(2), 파싱(2), 행 삽입(1×행 크기), 인덱스 삽입(1×인덱스 수), 종료(1)의 대략적인 비율로 나누고, 같은 클라이언트가 많은 행을 넣을 때는 여러 VALUES 목록을 가진 INSERT를 쓰는 것이 단일 행 INSERT를 여러 번 하는 것보다 상당히 빠르다고 적는다. 행마다 반복되던 전송과 파싱이 문장마다 한 번으로 줄기 때문이다.

    INSERT INTO daily_product_sales
  (stat_date, product_id, order_count, quantity_sum, amount_sum, aggregated_at)
VALUES
  ('2026-11-17', 10, 2, 4, 59000.00, NOW()),
  ('2026-11-17', 11, 1, 1, 12000.00, NOW()),
  ('2026-11-17', 15, 2, 2, 30000.00, NOW()) AS new
ON DUPLICATE KEY UPDATE
  order_count   = daily_product_sales.order_count  + new.order_count,
  quantity_sum  = daily_product_sales.quantity_sum + new.quantity_sum,
  amount_sum    = daily_product_sales.amount_sum   + new.amount_sum,
  aggregated_at = new.aggregated_at;

    커밋 횟수도 비용이다. innodb_flush_log_at_trx_commit의 기본값 1은 매뉴얼의 표현대로 완전한 ACID 준수에 필요한 설정이며, 트랜잭션이 커밋될 때마다 로그를 쓰고 디스크로 플러시한다. 자동 커밋 모드에서 행마다 문장을 보내면 행마다 이 플러시를 기다린다. 반대로 한 트랜잭션을 너무 크게 만들면 잠금을 오래 쥐고, undo가 커지고, 실패 시 되돌릴 양도 커진다. 문장 하나의 크기는 max_allowed_packet을 넘을 수 없다. 그래서 적당한 크기의 묶음으로 나눠 문장을 만들고 묶음마다 커밋한다. 적당한 크기는 행의 크기, 동시에 같은 행을 건드리는 트랜잭션의 수, 복제 지연 허용치에 따라 다르므로 측정으로 정한다.

    정렬해서 보낸다

    여러 행을 갱신하는 UPSERT 두 개가 동시에 실행되면, 동기 카운터에서 본 것과 같은 교착 상태가 생길 수 있다. 한 문장은 상품 10, 15 순서로, 다른 문장은 15, 10 순서로 행을 잠그는 경우다. 보내기 전에 행을 기본 키 순서로 정렬하면 모든 세션이 같은 순서로 잠금을 요청하므로 순환 대기가 생기지 않는다. 매뉴얼이 권하는 "일관된 순서"를 데이터 준비 단계에서 지키는 것이다. 그래도 교착 상태는 완전히 없앨 수 없으므로, 매뉴얼의 권고대로 교착 상태로 실패한 트랜잭션은 다시 실행할 수 있게 만든다. 앞의 방법들로 멱등하게 만들어 두었다면 재시도는 안전하다.

    먼저 줄이고 나서 쓴다

    이벤트 1,000건이 실제로는 상품 50종에 대한 것이라면, 통계 테이블에 1,000번 갱신할 이유가 없다. 메모리에서 먼저 키별로 합친 뒤 50행만 UPSERT하면 잠금 획득, undo, redo가 모두 20분의 1로 준다. 다음 자바 코드는 주문 이벤트를 (stat_date, product_id) 키로 미리 합치고, 기본 키와 같은 순서로 정렬된 상태로 배치 UPSERT를 보낸다. TreeMap을 쓴 것은 합치기와 정렬을 한 번에 하기 위해서다.

    import java.math.BigDecimal;
import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import java.time.LocalDate;
import java.util.List;
import java.util.Map;
import java.util.TreeMap;

public class SalesUpsert {

    record OrderEvent(long orderId, LocalDate date, long productId, int quantity, BigDecimal amount) {}

    // 통계 테이블의 기본 키와 같은 순서로 비교한다: (stat_date, product_id)
    record Key(LocalDate date, long productId) implements Comparable {
        public int compareTo(Key o) {
            int c = date.compareTo(o.date);
            return c != 0 ? c : Long.compare(productId, o.productId);
        }
    }

    static final class Acc {
        int orders;
        int quantity;
        BigDecimal amount = BigDecimal.ZERO;
    }

    static TreeMap preAggregate(List events) {
        TreeMap map = new TreeMap<>();
        for (OrderEvent e : events) {
            Acc a = map.computeIfAbsent(new Key(e.date(), e.productId()), k -> new Acc());
            a.orders++;
            a.quantity += e.quantity();
            a.amount = a.amount.add(e.amount());
        }
        return map;
    }

    static final String SQL = """
        INSERT INTO daily_product_sales
          (stat_date, product_id, order_count, quantity_sum, amount_sum, aggregated_at)
        VALUES (?, ?, ?, ?, ?, NOW()) AS new
        ON DUPLICATE KEY UPDATE
          order_count   = daily_product_sales.order_count  + new.order_count,
          quantity_sum  = daily_product_sales.quantity_sum + new.quantity_sum,
          amount_sum    = daily_product_sales.amount_sum   + new.amount_sum,
          aggregated_at = new.aggregated_at
        """;

    static void upsert(Connection con, Map rows) throws SQLException {
        try (PreparedStatement ps = con.prepareStatement(SQL)) {
            for (Map.Entry e : rows.entrySet()) { // TreeMap이므로 키 순서대로 나온다
                ps.setObject(1, e.getKey().date());
                ps.setLong(2, e.getKey().productId());
                ps.setInt(3, e.getValue().orders);
                ps.setInt(4, e.getValue().quantity);
                ps.setBigDecimal(5, e.getValue().amount);
                ps.addBatch();
            }
            ps.executeBatch();
        }
    }

    public static void main(String[] args) {
        LocalDate d = LocalDate.of(2026, 11, 17);
        List events = List.of(
                new OrderEvent(1, d, 15, 1, new BigDecimal("15000")),
                new OrderEvent(2, d, 10, 2, new BigDecimal("30000")),
                new OrderEvent(3, d, 15, 1, new BigDecimal("15000")),
                new OrderEvent(4, d, 11, 1, new BigDecimal("12000")),
                new OrderEvent(5, d, 10, 2, new BigDecimal("29000")));
        preAggregate(events).forEach((k, a) ->
                System.out.println(k.date() + " 상품 " + k.productId() + " -> "
                        + a.orders + "건, " + a.quantity + "개, " + a.amount + "원"));
    }
}
    2026-11-17 상품 10 -> 2건, 4개, 59000원
2026-11-17 상품 11 -> 1건, 1개, 12000원
2026-11-17 상품 15 -> 2건, 2개, 30000원

    이벤트는 상품 15, 10, 15, 11, 10 순서로 들어왔지만, TreeMap은 Key.compareTo()에 따라 상품 10, 11, 15 순서로 키를 유지한다. 상품 10의 두 주문(30,000원, 29,000원)은 한 항목으로 합쳐져 2건, 4개, 59,000원이 되었다. 다섯 건의 이벤트가 세 번의 UPSERT로 줄었고, 그 세 번은 기본 키 순서로 실행된다. 이 결과가 앞의 여러 행 ODKU 예제의 값과 같다. main은 데이터베이스 없이 합치기만 확인하며, upsert()는 MySQL 연결을 넘겨야 실행된다.

    JDBC 배치는 드라이버 설정까지 봐야 한다

    addBatch()와 executeBatch()를 썼다고 해서 여러 행이 한 문장으로 가는 것은 아니다. MySQL Connector/J는 rewriteBatchedStatements 속성이 참일 때 executeBatch()가 호출되면 INSERT와 REPLACE 준비된 문장을 여러 VALUES 목록을 가진 문장으로 다시 쓴다. 이 속성의 기본값은 false다. 기본값 그대로면 배치의 각 항목이 따로 실행된다. 이 속성을 켜고 ODKU를 쓸 때는 반환값이 달라진다는 점도 알아 두자. Connector/J 문서에 따르면 다시 쓴 ODKU 문장에 대해 서버는 배치 전체의 영향받은 행 수 하나만 돌려주므로, 드라이버는 그 합이 0이면 각 항목에 0을, 0보다 크면 각 항목에 Statement.SUCCESS_NO_INFO(값은 -2)를 돌려준다. executeBatch()의 반환 배열로 "몇 건이 새로 들어갔는가"를 세는 코드는 이 설정에서 의미를 잃는다. 실제로 서버에 어떤 SQL이 도착하는지는 서버의 general log로 확인하는 것이 가장 확실하다.

    REPLACE는 UPSERT가 아니다

    REPLACE INTO도 "있으면 바꾼다"처럼 보이지만 의미가 다르다. 매뉴얼은 REPLACE가 INSERT와 똑같이 동작하되, 기본 키나 유니크 인덱스 값이 같은 기존 행이 있으면 그 행을 지운 다음 새 행을 넣는다고 설명한다. 문장에 적지 않은 열은 INSERT처럼 기본값이 된다. 통계 행에 운영자가 따로 적어 둔 메모 열이 있었다면 REPLACE 한 번에 사라진다. 영향받은 행 수도 지운 행과 넣은 행의 합이라 충돌이 있으면 2 이상이 나온다. 잠금 면에서도 매뉴얼은 충돌이 있으면 바뀔 행에 배타 next-key 잠금을 건다고 적는다. 기존 값에 더하는 갱신은 REPLACE로는 표현할 수도 없다. 통계 테이블의 UPSERT에는 ODKU를 쓴다.

    흔한 오해와 함정

    "통계 테이블은 캐시니까 틀리면 다시 만들면 된다"

    절반만 맞다. 다시 만들 수 있으려면 원본이 남아 있어야 하고, 재집계가 멱등해야 하며, 재집계 범위가 정해져 있어야 한다. 원본 보존 기간이 지난 날짜의 통계는 더 이상 다시 만들 수 없는 기록이다. 그리고 캐시와 달리 통계 테이블의 숫자는 보고서, 정산, 의사 결정에 그대로 쓰인다. "언제든 고칠 수 있다"는 생각으로 멱등성과 워터마크를 생략하면, 틀린 숫자가 이미 다른 곳으로 퍼진 뒤에야 발견된다.

    "어제까지는 통계, 오늘은 원본"

    달력으로 경계를 정하면 배치가 실패하거나 늦은 날 하루치가 사라진다. 경계는 집계가 끝난 지점을 기록한 워터마크로 정하고, 통계 행과 워터마크는 한 트랜잭션에서 바꾼다.

    "시각이나 자동 증가 번호로 커서를 잡으면 빠짐없다"

    시각과 번호는 INSERT 때 정해지고, 행이 보이는 것은 커밋 때다. 커밋 순서는 시각이나 번호의 순서와 다를 수 있으므로, 커서보다 앞선 값을 가진 행이 나중에 나타난다. 안전 지연, 진행 중인 날 덮어쓰기, 보정 배치 가운데 하나로 이 구멍을 메운다.

    "평균과 비율을 저장해 두면 편하다"

    평균의 평균, 비율의 평균은 원래 기간의 평균이나 비율이 아니다. 합계와 건수, 분자와 분모를 저장하고 읽을 때 나눈다. 고유 건수는 아예 더할 수 없으니 별도 집계 경로를 둔다.

    시간대가 바뀌면 날짜가 바뀐다

    MySQL의 TIMESTAMP 열은 저장할 때 현재 세션의 시간대에서 UTC로, 읽을 때 UTC에서 세션 시간대로 변환되고, DATETIME은 이런 변환을 하지 않는다. 원본 시각이 TIMESTAMP인데 집계 배치의 접속 시간대가 애플리케이션과 다르면, 같은 주문의 DATE(ordered_at)이 배치에서는 하루 다르게 나올 수 있다. 통계 테이블의 stat_date가 어느 시간대의 날짜인지 정하고(예: 한국 시간), 원본이 UTC로 저장되어 있다면 "한국 시간 11월 16일"을 UTC 범위 [11월 15일 15:00, 11월 16일 15:00)으로 바꿔 조회한다. 한국 시간은 일광 절약 시간이 없어 오프셋이 고정이지만, 일광 절약 시간이 있는 지역의 날짜는 23시간이나 25시간일 수 있다는 점도 기억해 두자.

    삭제와 상태의 의미를 원본과 맞춘다

    원본에서 소프트 삭제된 주문, 취소 상태의 주문, 테스트 주문을 통계에 넣을지 뺄지는 집계 쿼리의 조건 한 줄로 정해진다. 이 조건이 실시간 원본 조회와 일별 배치에서 서로 다르면 하이브리드 조회의 두 구간이 서로 다른 정의로 계산된다. 이 권의 SOFT DELETE 회차에서 본 삭제 표시 열을 쓰는 테이블이라면, 집계 조건을 한곳(뷰나 공통 쿼리)에 두어 모든 경로가 같은 정의를 쓰게 한다.

    정리: 통계 테이블을 설계할 때 정하는 것들

    통계 테이블은 "느린 쿼리를 빠르게 하는 요령"이 아니라, 계산을 언제 할지 옮기는 설계다. 원본 집계의 비용은 읽는 행 수에 비례하고 인덱스는 행당 비용만 줄이므로, 반복되는 큰 집계는 미리 계산해 두는 수밖에 없다. 그 대가로 파생 데이터의 정합성을 직접 관리해야 한다. 설계할 때 정할 것을 순서대로 모으면 다음과 같다.

    1. 입도: 행 하나가 무엇인가. 주와 월을 모두 만들 수 있는 가장 거친 공통 단위(대개 일)에서 시작한다.
    2. 기본 키: 입도를 이루는 차원 열의 조합을 기본 키로 선언하고, 열 순서는 주된 조회 패턴으로 정한다. 대리 키와 유니크 키의 조합은 ODKU에서 손해다.
    3. 측정값: 가산적인 값만 저장한다. 평균과 비율은 분자·분모로, 고유 건수는 별도 경로로.
    4. 최신성: 하루 배치, 마이크로 배치, 동기 카운터, 하이브리드 조회 가운데 무엇을 쓸지. 동기 카운터는 핫 로우와 장애 전파를, 마이크로 배치는 늦은 커밋을, 하이브리드는 원본 구간의 크기를 따진다.
    5. 재실행: 기간 교체, 덮어쓰기, 처리 이력 가운데 하나로 멱등하게 만들고, 동시 실행은 따로 막는다. 경계를 나타내는 워터마크나 커서는 통계 행과 같은 트랜잭션에서 바꾼다.
    6. 쓰기 방식: ODKU를 기본 키 기준으로, 미리 합치고, 정렬하고, 적당한 크기로 묶어 쓴다. 격리 수준과 드라이버 설정이 잠금과 반환값을 바꾼다는 점을 확인한다.

    다음 회차에서는 슈퍼타입과 서브타입을 테이블로 옮기는 상속 관계 설계를 다룬다. 이 회차에서 본 "입도를 기본 키로 선언한다"와 "파생 데이터는 다시 만들 수 있어야 한다"는 생각은 이 권의 남은 회차에서도 계속 판단 기준이 된다.
    통계 테이블(summary table)
    원본을 정해 둔 단위로 미리 집계해 저장한 파생 테이블이다. 조회마다 반복되던 큰 집계를 한 번의 계산으로 바꾸는 대신, 원본과의 정합성을 직접 관리해야 한다.
    집계 비용의 구조
    비용은 읽는 행 수와 행당 비용의 곱이다. 커버링 인덱스는 클러스터형 인덱스 왕복을 없애 행당 비용을 줄이지만, 합계에 필요한 행 수는 줄이지 못한다.
    입도와 기본 키
    행 하나의 의미(예: 날짜×상품)를 먼저 정하고 그 조합을 기본 키로 선언한다. InnoDB에서는 이 순서대로 행이 저장되어 기간 조회가 연속 구간 읽기가 되고, 중복 집계는 키 충돌로 드러난다.
    가산성
    합계와 건수는 더해서 상위 기간을 만들 수 있지만 평균, 비율, 고유 건수는 그렇지 않다. 평균과 비율은 분자·분모로 저장하고, 고유 건수는 별도로 집계한다.
    주간·월간 롤업
    일별 통계를 기간 범위 조건으로 읽어 더한다. 주는 WEEKDAY()로 구한 주 시작일로 묶는 것이 안전하며, YEAR()와 WEEK()를 따로 구하면 연말 날짜가 엉뚱한 주로 들어간다.
    하이브리드 조회와 워터마크
    집계가 끝난 지점까지는 통계 테이블에서, 그 뒤는 원본에서 읽어 UNION ALL로 합친다. 경계는 달력이 아니라 통계 행과 같은 트랜잭션에서 갱신한 워터마크로 정한다.
    멱등성
    같은 집계를 몇 번 실행해도 결과가 같아야 한다. 기간 단위 삭제 후 삽입, 대입형 UPSERT, 처리 이력과 반영을 한 트랜잭션으로 묶는 방법이 있고, 동시 실행 방지는 별도 장치로 한다.
    늦게 커밋되는 행
    행의 시각과 자동 증가 번호는 INSERT 때 정해지고 행은 커밋 후에 보이므로, 이를 기준으로 한 커서는 행을 놓칠 수 있다. 안전 지연, 진행 중인 날 덮어쓰기, 보정 배치로 메운다.
    ON DUPLICATE KEY UPDATE
    충돌 시 갱신할 행에 처음부터 배타 잠금을 걸어 INSERT 후 UPDATE 방식의 교착 상태를 피한다. 영향받은 행 수는 삽입 1, 갱신 2, 변경 없음 0이고, 8.0.19부터 행 별칭을 쓰며 VALUES()는 8.0.20부터 폐기 예정이다.

UNION은 결과를 정렬하므로 느려질 뿐 숫자는 정확하다 값이 우연히 같은 행이 중복으로 간주되어 하나로 합쳐지므로, 바깥 SUM에서 일부 숫자가 빠진다 두 쿼리의 열 개수가 같으면 UNION과 UNION ALL은 결과가 항상 같다 UNION은 통계 테이블 쪽 행만 남기고 원본 쪽 행을 버린다 UNION은 중복 행을 제거한다. 서로 다른 날짜나 구간에서 나온 (상품, 건수, 금액) 행의 값이 우연히 같으면 하나로 합쳐져 한 번만 더해진다. 데이터에 따라 나타났다 사라지는 오류라 발견하기 어렵다. 합쳐서 다시 더하는 용도에는 UNION ALL을 써야 한다. 마이크로 배치가 ordered_at 기준 5분 창으로 증분을 더하고 커서를 옮긴다. 배치 세션은 READ COMMITTED다. 10:04:58에 INSERT되고 10:05:01에 커밋된 주문이 있고, 배치는 10:05:00에 [10:00, 10:05) 창을 처리했다. 이 주문은 어떻게 되는가? 첫 창에서 커밋을 기다렸다가 포함된다 두 번째 창 [10:05, 10:10)에서 포함된다 두 창에 모두 포함되어 두 번 세어진다 어느 창에도 포함되지 않는다 READ COMMITTED의 일관된 읽기는 커밋되지 않은 행을 건너뛰므로 첫 창에서 빠진다. 두 번째 창은 ordered_at이 10:05 이상인 행만 읽으므로 10:04:58인 이 주문은 범위 밖이다. 행의 시각은 INSERT 때 정해지지만 보이는 것은 커밋 이후라서 생기는 구멍이다. 커밋을 기다리는 것은 잠금 읽기(REPEATABLE READ의 INSERT ... SELECT)일 때의 동작이다. 통계 테이블에 대리 키 id AUTO_INCREMENT를 기본 키로 두고 (stat_date, product_id)에 유니크 인덱스를 거는 대신, (stat_date, product_id)를 기본 키로 선언하는 편이 ODKU를 쓸 때 유리한 이유로 옳은 것은? 유니크 키가 하나뿐이라 충돌 대상이 모호하지 않고, ODKU가 갱신으로 끝나도 자동 증가 값이 할당되어 버려지는 일이 없으며, 기간 조회가 클러스터형 인덱스의 연속 구간 읽기가 된다 기본 키가 복합 키면 ODKU가 잠금을 전혀 걸지 않는다 대리 키가 있으면 ODKU 문법 자체를 쓸 수 없다 복합 기본 키에서는 영향받은 행 수가 항상 1로 나와 결과를 해석하기 쉽다 매뉴얼은 유니크 인덱스가 여러 개인 테이블에서 ODKU를 피하라고 권하고, 이런 문장을 문장 기반 복제에서 안전하지 않은 문장으로 분류한다. ODKU는 중복 시 배타 잠금을 걸고, 영향받은 행 수는 1·2·0으로 달라지며, 대리 키가 있어도 문법은 쓸 수 있다. 기본 격리 수준(REPEATABLE READ)에서 INSERT INTO daily_product_sales SELECT ... FROM orders WHERE ordered_at ... GROUP BY ... 배치를 실행하는 동안 주문 API가 느려졌다. 가장 직접적인 원인은? INSERT ... SELECT는 항상 테이블 전체에 테이블 잠금을 건다 집계 결과가 버퍼 풀을 모두 밀어내 주문 테이블 페이지가 사라진다 REPEATABLE READ에서 INSERT ... SELECT는 원본 행에 공유 next-key 잠금을 걸며 읽으므로, 그 행의 변경이나 그 간격에 들어갈 삽입이 배치의 커밋을 기다린다 통계 테이블의 기본 키가 복합 키라서 삽입이 느리다 매뉴얼에 따르면 INSERT INTO T SELECT ... FROM S는 READ COMMITTED에서는 S를 잠금 없는 일관된 읽기로 검색하지만, 그 밖의 격리 수준에서는 S의 행에 공유 next-key 잠금을 건다. 행 수준 잠금이지 테이블 잠금이 아니며, 버퍼 풀은 미드포인트 삽입으로 스캔 페이지가 먼저 밀려나도록 설계되어 있다. 배치 세션만 READ COMMITTED로 실행하면(행 기반 바이너리 로그 전제) 원본에 잠금을 걸지 않는다.
    통계 테이블(summary table)
    원본 데이터를 정해 둔 단위로 미리 집계해 저장한 테이블. 원본에서 다시 계산할 수 있는 파생 데이터다.
    입도(grain)
    통계 테이블의 행 하나가 나타내는 단위. 예: 날짜×상품. 차원 열의 조합으로 표현되며 보통 기본 키가 된다.
    가산 측정값(additive measure)
    작은 단위의 값을 더해 큰 단위의 값을 얻을 수 있는 측정값. 합계와 건수가 해당하고, 평균·비율·고유 건수는 해당하지 않는다.
    롤업(roll-up)
    잘게 집계된 데이터를 더 큰 단위로 다시 묶는 것. 일별 통계에서 주간·월간 통계를 만드는 것이 예다.
    워터마크(watermark)
    집계가 어디까지 끝났는지 기록한 경계 값. 하이브리드 조회에서 통계 테이블과 원본을 나누는 기준이 된다.
    멱등성(idempotency)
    같은 작업을 한 번 실행하든 여러 번 실행하든 결과 상태가 같은 성질. 재시도와 재실행이 안전해진다.
    마이크로 배치(micro-batch)
    짧은 주기로 직전 이후의 데이터만 집계하는 배치 방식. 실시간 갱신과 하루 단위 배치의 중간이다.
    핫 로우(hot row)
    많은 트랜잭션이 동시에 갱신하려고 몰리는 행. 행 잠금이 트랜잭션 끝까지 유지되므로 갱신이 한 줄로 직렬화된다.
    UPSERT
    행이 없으면 삽입하고 있으면 갱신하는 연산. MySQL에서는 INSERT ... ON DUPLICATE KEY UPDATE로 한 문장에 표현한다.
