    이 회차의 질문: EAV 다음은 무엇인가

    앞 회차에서는 카테고리마다 속성이 다른 상품을 EAV(Entity-Attribute-Value)로 저장했다. 속성을 열이 아니라 행으로 두니 새 속성이 생겨도 스키마를 바꿀 필요가 없었다. 대신 비용이 따라왔다. 상품 하나를 화면에 보이려면 속성 개수만큼의 행을 읽어 피벗해야 했고, 여러 속성을 동시에 만족하는 상품을 찾으려면 셀프 조인이나 GROUP BY ... HAVING을 써야 했다. 값은 문자열 열 하나에 몰아넣거나 타입별 값 열로 나눠야 했고, 어느 쪽이든 데이터베이스가 "이 속성은 정수다"를 지켜 주기는 어려웠다.

    EAV가 잘 다루지 못하는 형태도 있다. 티셔츠의 사이즈 목록 S, M, L처럼 값이 여러 개인 속성, 배송지처럼 여러 필드가 한 덩어리로 움직이는 속성, 옵션 안에 다시 옵션이 있는 중첩 구조가 그렇다. EAV로 이것들을 표현하려면 값 행에 순번 열을 붙이거나 부모 값 ID를 두는 식으로 테이블을 계속 늘려야 한다. 그러면 처음에 원했던 "속성이 자주 바뀌어도 가볍게 저장한다"는 목표에서 멀어진다.

    그래서 다른 질문을 해 볼 수 있다. 자주 바뀌는 속성들을 한 행 안의 한 값으로 묶어서 저장하되, 그 값이 타입(수, 문자열, 참·거짓)과 중첩 구조와 배열을 그대로 담고, 데이터베이스가 형식을 검증하고 안쪽 값을 검색하고 인덱스까지 만들어 줄 수는 없을까. MySQL의 JSON 자료형이 이 질문에 대한 답 가운데 하나다. 같은 노트북 속성을 두 방식으로 저장하면 차이가 분명하다.

    이 회차는 다음 순서로 진행한다. 먼저 JSON이라는 형식 자체의 규칙을 RFC 8259로 정확히 세운다. 다음으로 MySQL이 JSON 문서를 받아 검증하고 정규화해 이진 형식으로 저장하는 과정을, MySQL 서버 소스의 이진 형식 정의까지 내려가 바이트 단위로 따라간다. 그다음 경로 식과 함수로 JSON을 읽고, 고치고, 찾고, 관계형으로 펼친다. 실무 사례 두 묶음을 본 뒤 인덱스(생성 열, 함수 기반 키 파트, 다중 값 인덱스)와 부분 업데이트로 성능 문제를 다루고, 마지막으로 장단점, 사용 가이드라인, 문서 데이터베이스와의 비교로 판단 기준을 정리한다. 기준 환경은 MySQL 8.0 이상, InnoDB, 기본 행 형식 DYNAMIC, 문자 집합 utf8mb4다. 버전에 따라 달라지는 기능은 도입 버전을 함께 적는다.

    JSON 열은 정규화를 대신하는 도구가 아니다. 스키마를 없애는 것이 아니라 스키마를 지키는 책임의 일부를 데이터베이스에서 애플리케이션으로 옮기는 선택이다. 이 회차 전체가 "무엇을 옮겨도 되고 무엇은 옮기면 안 되는가"를 가리는 이야기다.

    JSON 문법: RFC 8259가 정한 것과 정하지 않은 것

    JSON(JavaScript Object Notation)의 표준 문법은 IETF의 RFC 8259와 Ecma의 ECMA-404에 정의되어 있다. 이 회차에서는 RFC 8259를 기준으로 삼는다. 문법은 작다. JSON 값(value)은 객체(object), 배열(array), 수(number), 문자열(string) 넷 중 하나이거나, 리터럴 이름 true, false, null 셋 중 하나다. RFC는 리터럴 이름이 반드시 소문자여야 하고 다른 리터럴은 허용하지 않는다고 적는다. 그래서 True, NULL, undefined는 JSON이 아니다.

    구조를 만드는 문자는 여섯 개다. 객체의 시작과 끝 { }, 배열의 시작과 끝 [ ], 이름과 값을 가르는 :, 원소를 가르는 ,다. 이 구조 문자 앞뒤에는 의미 없는 공백(insignificant whitespace)을 넣을 수 있고, 공백으로 인정되는 문자는 스페이스, 수평 탭, 줄 바꿈(LF), 캐리지 리턴(CR) 네 가지뿐이다. 객체는 "이름/값 쌍 0개 이상의 순서 없는 모음(unordered collection)"으로 정의된다. 배열은 값의 순서 있는 나열이고, RFC는 배열 원소의 타입이 같을 필요가 없다고 명시한다. [1, "a", true, null, {"k": []}]도 올바른 배열이다.

    문자열은 반드시 큰따옴표로 감싼다. 작은따옴표 문자열은 JSON이 아니다. 문자열 안에서 반드시 이스케이프해야 하는 문자는 큰따옴표, 역슬래시, 그리고 제어 문자(U+0000부터 U+001F까지)다. 그래서 문자열 안에 줄 바꿈 문자를 그대로 넣을 수 없고 \n으로 써야 한다. 임의의 문자는 \u 뒤에 16진수 네 자리로 쓸 수 있고, 기본 다국어 평면(BMP) 밖의 문자는 UTF-16 대리 쌍(surrogate pair) 두 개, 즉 😀(U+1F600) 같은 12글자 시퀀스로 쓴다.

    수의 문법은 생각보다 엄격하다. 형태는 [-] 정수부 [.소수부] [e지수]이고, 정수부는 0이거나 0이 아닌 숫자로 시작해야 한다. 그래서 007(앞자리 0), +1(양의 부호), .5(정수부 없음), 1.(소수부 숫자 없음), 0x1F(16진수)는 모두 JSON 수가 아니다. RFC는 이 문법으로 표현할 수 없는 값, 예를 들어 Infinity와 NaN은 허용하지 않는다고 적는다. 주석과 마지막 원소 뒤의 쉼표(trailing comma)는 문법 규칙 어디에도 자리가 없으므로 역시 JSON이 아니다.

    표준이 정하지 않은 세 가지

    RFC 8259가 일부러 열어 둔 부분이 있다. 이 부분은 구현마다 다르게 동작하므로 설계할 때 반드시 의식해야 한다. 첫째, 이름의 중복이다. RFC는 객체 안의 이름이 "유일해야 한다(SHOULD be unique)"고만 적는다. 이름이 중복된 객체를 받은 소프트웨어의 동작은 예측할 수 없다고 하고, 많은 구현이 마지막 쌍만 보고하지만 오류를 내거나 파싱에 실패하는 구현도 있다고 설명한다. 둘째, 객체 멤버의 순서다. 객체는 순서 없는 모음이고, 파서마다 멤버 순서를 드러내는지가 다르다는 것을 RFC가 인정한다. 순서에 의존하지 않는 구현끼리만 상호 운용된다.

    셋째, 수의 범위와 정밀도다. RFC는 수의 정밀도를 제한하지 않는 대신, IEEE 754 binary64(배정밀도) 수가 널리 쓰이므로 그보다 더 큰 정밀도나 범위를 기대하지 않는 구현끼리는 상호 운용이 잘 된다고 적는다. 특히 [-(2^53)+1, (2^53)-1] 범위의 정수는 구현들이 정확히 같은 값으로 합의한다고 명시한다. 이 문장이 실무에서 의미하는 바는 분명하다. 자바스크립트의 Number는 binary64이므로 9007199254740993(2^53 + 1)을 JSON으로 받으면 가장 가까운 짝수 가수 쪽인 9007199254740992로 반올림된다. MySQL BIGINT나 자바 long으로 만든 ID가 이 범위를 넘을 수 있다면, 외부 API의 JSON에서는 ID를 문자열로 내보내는 것이 안전하다.

    마지막으로 인코딩이다. RFC는 닫힌 생태계 밖에서 주고받는 JSON 텍스트는 반드시 UTF-8로 인코딩해야 한다고 정한다. MySQL의 JSON 자료형이 문서를 utf8mb4로 다루는 것과 맞물리는 규칙이다. 이제 MySQL이 위의 "정하지 않은 세 가지"를 어떻게 정했는지 보자.

    MySQL의 JSON 자료형: 문자열이 아니라 검증된 이진 문서

    JSON을 TEXT나 VARCHAR 열에 넣어도 저장은 된다. 문제는 세 가지다. 데이터베이스가 형식을 검증하지 않으므로 깨진 문서가 들어와도 막지 못한다. 안쪽 값을 읽을 때마다 텍스트 전체를 처음부터 파싱해야 한다. 그리고 "16"과 16의 차이 같은 타입 정보가 데이터베이스 입장에서는 그저 문자다. MySQL의 JSON 자료형은 이 셋을 해결한다. MySQL 8.0 매뉴얼은 JSON 열에 저장되는 문서가 자동으로 검증되고, 유효하지 않은 문서는 오류를 낸다고 설명한다. 또 저장된 문서는 원소에 빠르게 접근할 수 있는 내부 이진 형식으로 변환되므로, 값을 읽을 때 텍스트에서 다시 파싱할 필요가 없다.

    예제로 쓸 상품 테이블을 만든다. 모든 상품이 가진 속성(카테고리, 이름, 가격)은 일반 열로 두고, 카테고리마다 다른 속성만 attrs JSON 열에 담는다.

    CREATE TABLE product (
  product_id BIGINT       NOT NULL AUTO_INCREMENT,
  category   VARCHAR(20)  NOT NULL,
  name       VARCHAR(100) NOT NULL,
  price      INT          NOT NULL,
  attrs      JSON         NOT NULL DEFAULT (JSON_OBJECT()),
  PRIMARY KEY (product_id),
  CONSTRAINT chk_product_attrs_object CHECK (JSON_TYPE(attrs) = 'OBJECT')
);

INSERT INTO product (category, name, price, attrs) VALUES
 ('CLOTHES', '기본 반팔 티셔츠', 19000,
  '{"color": "white", "size": ["S", "M", "L"], "material": "cotton"}'),
 ('LAPTOP', '울트라북 14', 1590000,
  '{"cpu": "8코어", "memory_gb": 16, "storage_gb": 512, "weight_kg": 1.2, "tags": ["경량", "학생"]}'),
 ('CAMPING', '접이식 캠핑 의자', 59000,
  '{"max_load_kg": 120, "foldable": true, "color": "khaki", "tags": ["경량", "캠핑"]}'),
 ('SHOES', '데일리 러닝화', 89000,
  '{"color": "black", "sizes_mm": [250, 260, 270], "tags": ["러닝"]}');

    두 군데를 짚어 두자. DEFAULT (JSON_OBJECT())처럼 괄호로 감싼 식 기본값은 MySQL 8.0.13부터 가능하다. 매뉴얼은 BLOB, TEXT, GEOMETRY, JSON 타입은 기본값을 식으로 써야만 지정할 수 있고, 8.0.13 이전에는 JSON 열이 NULL이 아닌 기본값을 가질 수 없었다고 적는다. CHECK (JSON_TYPE(attrs) = 'OBJECT')는 최상위 값이 객체가 아닌 문서(예: 배열 [1, 2]나 문자열 "abc")를 거부한다. JSON 자료형의 자동 검증은 "올바른 JSON인가"까지만 보장하므로, "최상위는 객체여야 한다" 같은 구조 규칙은 이렇게 따로 걸어야 한다. MySQL이 CHECK 제약을 실제로 검사하는 것은 8.0.16부터다.

    저장할 때 일어나는 일: 검증과 정규화

    INSERT된 문서를 다시 읽어 보면 입력한 모양과 다르다.

    1  {"size": ["S", "M", "L"], "color": "white", "material": "cotton"}
2  {"cpu": "8코어", "tags": ["경량", "학생"], "memory_gb": 16, "weight_kg": 1.2, "storage_gb": 512}
3  {"tags": ["경량", "캠핑"], "color": "khaki", "foldable": true, "max_load_kg": 120}
4  {"tags": ["러닝"], "color": "black", "sizes_mm": [250, 260, 270]}

    키 순서가 바뀌었다. 매뉴얼은 조회를 효율적으로 하려고 MySQL이 객체의 키를 정렬한다고 설명하면서, 이 정렬 결과는 바뀔 수 있고 릴리스 간에 일관된다는 보장이 없다고 경고한다. MySQL 8.0 소스의 키 비교기(json_dom.h의 Json_key_comparator)는 키를 먼저 바이트 길이로, 길이가 같으면 바이트 사전 순으로 오름차순 정렬하며, 주석에 "조회 속도를 위해 고른 순서"라고 적혀 있다. 그래서 3번 상품은 tags(4바이트), color(5), foldable(8), max_load_kg(11) 순으로 나오고, 2번 상품에서 길이가 9로 같은 memory_gb와 weight_kg는 m이 w보다 앞서므로 그 순서가 된다. 이 동작에서 얻을 교훈은 하나다. JSON 객체의 키 순서에 의미를 담지 않는다. 순서가 필요하면 배열을 쓴다. RFC가 객체를 순서 없는 모음으로 정의한 것과 같은 결론이다.

    공백도 정리된다. 매뉴얼에 따르면 MySQL은 원본 문서의 키, 값, 원소 사이에 있던 여분의 공백을 버리고, 출력할 때 쉼표와 콜론 뒤에 공백 하나를 두거나 넣는다. 위 출력에서 모든 쉼표·콜론 뒤에 공백이 하나씩인 이유다. 중복 키는 MySQL 8.0.3부터 마지막 키가 이긴다. 왼쪽에서 오른쪽으로 읽을 때 뒤에 같은 키가 다시 나오면 앞의 멤버를 버린다. 8.0.3 이전에는 반대로 처음 나온 키가 이겼다. RFC가 열어 둔 부분을 MySQL은 이렇게 닫았지만, 다른 언어의 JSON 라이브러리는 다르게 닫았을 수 있으므로 중복 키가 있는 문서는 애초에 만들지 않는 것이 맞다.

    수와 null의 저장

    JSON 텍스트의 수가 MySQL 안에서 어떤 타입이 되는지도 알아 둘 필요가 있다. MySQL 8.0 소스(json_dom.cc)의 파서 처리기를 보면 정수는 정수 값으로, 소수부나 지수가 있는 수는 double 값(Json_double)으로 만들어진다. 그래서 {"price": 19.99}로 들어온 19.99는 십진 소수가 아니라 이진 부동소수점으로 저장된다. 정확한 십진 연산이 필요한 금액은 JSON 안에 넣지 말고 DECIMAL 열로 두는 것이 원칙이다. 예제에서 price를 일반 열로 둔 이유이기도 하다.

    JSON의 null과 SQL의 NULL은 다른 것이다. {"discount": null}에서 attrs->'$.discount'는 JSON 타입의 값 null을 돌려주며, 이것은 SQL 관점에서 NULL이 아닌 값이다. 반면 문서에 아예 없는 경로를 읽으면 SQL NULL이 나온다. 그래서 attrs->'$.discount' IS NULL은 "키가 없다"는 뜻이고, "키는 있는데 값이 JSON null"인 경우는 걸러 내지 못한다. 이 둘을 구분할 필요가 없도록, 값이 없으면 키 자체를 빼는 쪽으로 규칙을 정해 두는 편이 단순하다.

    크기 한도

    매뉴얼은 JSON 문서를 저장하는 데 필요한 공간이 대략 LONGBLOB나 LONGTEXT와 같고, JSON 열에 저장되는 문서의 크기는 max_allowed_packet 시스템 변수 값으로 제한된다고 적는다. 서버가 메모리에서 JSON을 다룰 때는 이보다 커질 수 있지만, 저장할 때 이 한도가 적용된다. 한 문서의 저장 크기는 JSON_STORAGE_SIZE()로 확인할 수 있다. 다음 절에서 이 크기가 어디서 나오는지 바이트 단위로 계산해 본다.

    한 층 아래: JSON 이진 형식과 InnoDB 저장

    매뉴얼은 이진 형식이 "문서 앞뒤의 값을 모두 읽지 않고도 키나 배열 인덱스로 하위 객체나 중첩 값을 바로 찾을 수 있게" 구성되어 있다고만 설명한다. 구체적인 배치는 MySQL 서버 소스의 sql-common/json_binary.h 머리 주석에 문법으로 정의되어 있다. 핵심만 옮기면 다음과 같다(MySQL 8.0 소스 기준).

    doc    ::= type value                 // type은 1바이트 타입 식별자
type   ::= 0x00 작은 객체 | 0x01 큰 객체 | 0x02 작은 배열 | 0x03 큰 배열
         | 0x04 리터럴(true/false/null) | 0x05 int16 | 0x06 uint16 | 0x07 int32
         | 0x08 uint32 | 0x09 int64 | 0x0a uint64 | 0x0b double | 0x0c utf8mb4 문자열
         | 0x0f 사용자 정의 데이터(임의의 MySQL 타입)
object ::= element-count size key-entry* value-entry* key* value*
array  ::= element-count size value-entry* value*
element-count, size ::= 작은 형식이면 uint16, 큰 형식이면 uint32
key-entry   ::= key-offset key-length    // key-length는 uint16, 키는 64KB 미만
value-entry ::= type offset-or-inlined-value
                // 리터럴이나 충분히 작은 정수는 오프셋 자리에 값을 직접 넣는다(inline)
string ::= data-length utf8mb4-data      // 길이는 가변 바이트: 127까지 1바이트, 16383까지 2바이트 ...

    객체 하나는 머리(header)와 몸통으로 나뉜다. 머리에는 멤버 수, 전체 바이트 수, 키마다 (오프셋, 길이) 항목, 값마다 (타입, 오프셋 또는 값) 항목이 고정 크기로 줄지어 있다. 몸통에는 키 문자열들이 이어지고 그 뒤에 값들이 이어진다. 작은 형식은 오프셋과 개수를 2바이트로, 큰 형식은 4바이트로 쓴다. 고정 크기 항목이 배열처럼 늘어서 있으므로 i번째 항목의 위치는 계산 한 번으로 나온다. 소스의 json_binary::Value 클래스 주석은 배열 원소를 element()로 상수 시간에, 객체 멤버를 lookup()으로 O(log n) 시간에 찾는다고 적는다. 객체 조회가 O(log n)인 것은 키 항목이 정렬되어 있어 이진 탐색을 할 수 있기 때문이고, 앞 절에서 본 키 정렬이 바로 이 탐색을 위한 것이다.

    1번 상품의 문서 {"size": ["S", "M", "L"], "color": "white", "material": "cotton"}를 이 규칙대로 배치하고 바이트를 세어 보자. 문서 전체가 작으므로 작은 형식(2바이트 필드)이다.

    오프셋  내용                                          바이트
------  --------------------------------------------  ------

    합계는 75바이트다. 이 계산 방식이 맞는지는 매뉴얼의 JSON_STORAGE_SIZE() 예제로 확인할 수 있다. 매뉴얼은 [100, "sakila", [1, 3, 5], 425.05]의 크기를 45, {"a": 1000, "b": "wxyz", "c": "[1, 3, 5, 7]"}의 크기를 47로 보여 준다. 앞의 것을 같은 규칙으로 세면 타입 1 + 머리 4 + 값 항목 4×3 = 12 + "sakila" 7 + 중첩 배열 13(머리 4 + 항목 9, 작은 정수는 인라인) + double 8 = 45이고, 뒤의 것은 타입 1 + 머리 4 + 키 항목 12 + 값 항목 9 + 키 3 + "wxyz" 5 + 12글자 문자열 13 = 47이다(1000은 int16 범위라 값 항목 안에 인라인된다). 두 값이 정확히 맞는다. MySQL 8.4.13과 8.0.46에서 직접 실행해도 매뉴얼의 두 예는 45와 47, 1번 상품의 JSON_STORAGE_SIZE(attrs)는 75가 나온다.

    이 계산에서 두 가지를 읽어 낼 수 있다. 첫째, 같은 문서를 공백 없이 쓴 텍스트 {"color":"white","size":["S","M","L"],"material":"cotton"}는 58바이트인데 이진 형식은 75바이트다. 이진 형식의 목적은 공간 절약이 아니라 파싱 없이 바로 찾아가는 것이고, 그 대가로 오프셋 항목만큼 공간을 더 쓴다. 둘째, 키 이름이 행마다 저장된다. 일반 열의 이름은 데이터 사전에 한 번만 기록되지만, JSON 키 "size", "color", "material"의 17바이트(키 항목까지 치면 29바이트)는 모든 행에 반복된다. 100만 행이면 키 바이트만 1,700만 바이트, 약 16MB다. 긴 키 이름은 행 수만큼 비싸다.

    InnoDB는 이 바이트열을 어디에 두는가

    MySQL 8.0 소스에서 JSON 열을 다루는 Field_json 클래스는 Field_blob을 상속한다. 매뉴얼이 저장 공간을 LONGBLOB에 빗대는 것과 같은 맥락으로, 이진 문서는 InnoDB에 BLOB 계열 값처럼 저장된다. InnoDB 매뉴얼은 DYNAMIC 행 형식에서 긴 가변 길이 값(VARCHAR, VARBINARY, BLOB, TEXT)을 페이지 밖(off-page)에 통째로 두고 클러스터형 인덱스 레코드에는 20바이트 포인터만 남길 수 있다고 설명한다. 어느 열을 밖으로 보낼지는 페이지 크기와 행 전체 크기에 달려 있다. 행이 너무 길면 클러스터형 인덱스 레코드가 B-tree 페이지에 들어갈 때까지 가장 긴 열부터 밖으로 보낸다. 40바이트 이하인 TEXT, BLOB 값은 행 안에 둔다.

    결과적으로 75바이트짜리 작은 문서는 대개 행 안에 함께 놓이지만, 수 KB를 넘는 큰 문서는 오버플로 페이지로 나가고 행에는 포인터만 남는다. 그러면 그 JSON 값을 읽는 쿼리는 클러스터형 인덱스 페이지에 더해 오버플로 페이지까지 읽어야 한다. 목록 화면처럼 JSON이 필요 없는 쿼리에서 SELECT *를 습관처럼 쓰면 쓰지도 않을 큰 문서를 매번 버퍼 풀로 끌어올리게 된다. 큰 원문 JSON은 필요한 쿼리에서만 열 이름을 지정해 읽고, 자주 읽는 테이블과 분리된 별도 테이블에 두는 것도 고려한다.

    MySQL에서 JSON 사용하기 1: 경로 식으로 읽기

    JSON 문서 안의 위치는 경로 식(path expression)으로 가리킨다. 경로는 문서 전체를 뜻하는 $로 시작하고 그 뒤에 선택자를 잇는다. 매뉴얼이 정의한 선택자는 다음과 같다.

    경로뜻예 (1번 상품 기준)
    $문서 전체문서 그대로
    $.key객체의 멤버. 경로에서 허용되지 않는 이름이면 $."my key"처럼 큰따옴표로 감싼다$.color → "white"
    $[N]배열의 N번째 원소(0부터)$.size[0] → "S"
    $[last], $[last-1]마지막 원소, 그 앞 원소$.size[last] → "L"
    $[M to N]M번째부터 N번째까지(M은 0 이상, N은 M보다 커야 한다)$.size[1 to 2] → ["M", "L"]
    $[*]배열의 모든 원소$.size[*] → ["S", "M", "L"]
    $.*객체의 모든 멤버 값세 값을 담은 배열
    $**.key깊이와 상관없이 key로 끝나는 모든 경로. 경로가 **로 끝날 수는 없다중첩 객체 속 모든 color

    값을 꺼내는 기본 함수는 JSON_EXTRACT(doc, path)이고, col->path는 그 동의어다. col->>path는 JSON_UNQUOTE(JSON_EXTRACT(col, path))의 동의어다. 차이는 결과 타입이다. ->는 JSON 값을 돌려주므로 문자열이면 큰따옴표가 붙은 JSON 문자열 "white"가 나온다. ->>는 따옴표와 이스케이프를 벗긴 SQL 문자열 white를 돌려준다.

    SELECT name,
       attrs->'$.color'         AS color_json,
       attrs->>'$.color'        AS color_text,
       attrs->'$.size[0]'       AS first_size,
       attrs->'$.size[last]'    AS last_size,
       attrs->'$.size[1 to 2]'  AS middle,
       attrs->'$.memory_gb'     AS memory
FROM product
WHERE product_id = 1;
    name             color_json  color_text  first_size  last_size  middle      memory
기본 반팔 티셔츠  "white"     white       "S"         "L"        ["M", "L"]  NULL

    한 줄씩 보자. color_json은 JSON 문자열이라 따옴표가 보이고, color_text는 벗겨진 SQL 문자열이다. $.size[1 to 2]처럼 여러 값을 고를 수 있는 경로는 매뉴얼 규칙대로 결과를 배열로 감싸(autowrap) 돌려준다. 티셔츠 문서에는 memory_gb가 없으므로 memory는 SQL NULL이다. 경로가 아무것도 가리키지 않는 것은 오류가 아니다. 이 성질 덕분에 카테고리마다 키가 달라도 같은 쿼리를 쓸 수 있지만, 반대로 키 이름 오타($.colour)도 오류 없이 NULL로 조용히 지나간다는 점을 기억해 두자.

    문서의 모양을 묻는 함수

    SELECT JSON_TYPE(attrs->'$.memory_gb'),           -- INTEGER
       JSON_TYPE(attrs->'$.weight_kg'),           -- DOUBLE
       JSON_TYPE(attrs->'$.tags'),                -- ARRAY
       JSON_LENGTH(attrs),                        -- 5   (최상위 멤버 수)
       JSON_LENGTH(attrs, '$.tags'),              -- 2
       JSON_CONTAINS_PATH(attrs, 'one', '$.color', '$.cpu'),  -- 1 (둘 중 하나라도 있으면)
       JSON_CONTAINS_PATH(attrs, 'all', '$.color', '$.cpu')   -- 0 (color가 없다)
FROM product
WHERE product_id = 2;

    JSON_TYPE은 값의 JSON 타입 이름을 돌려준다. 노트북의 무게 1.2가 DOUBLE로 나오는 것은 앞 절에서 본 대로 소수부가 있는 수가 double로 저장되기 때문이다. JSON_KEYS(attrs)는 최상위 키 목록을 배열로 돌려주는데, 그 순서는 저장된 키 순서를 따르므로 앞에서 말한 이유로 의미를 두면 안 된다. JSON_CONTAINS_PATH는 값이 아니라 경로의 존재를 묻는다. 'one'은 하나라도, 'all'은 모두 있어야 1이다.

    JSON_VALUE: 꺼내면서 타입을 정한다

    MySQL 8.0.21에서 추가된 JSON_VALUE(doc, path [RETURNING type] [on_empty] [on_error])는 경로의 스칼라 값을 꺼내 지정한 SQL 타입으로 바꿔 준다. RETURNING에는 SIGNED, UNSIGNED, DECIMAL, DOUBLE, DATE, DATETIME, CHAR 같은 CAST()의 비배열 타입을 쓸 수 있다. RETURNING을 생략하면 결과는 VARCHAR(512)이고, 문자 집합은 utf8mb4, 콜레이션은 이진(대소문자 구분) 콜레이션이다. 경로에 값이 없으면 기본적으로 NULL(NULL ON EMPTY), 값이 객체·배열이거나 변환에 실패하면 기본적으로 NULL(NULL ON ERROR)이며, 변환 오류는 NULL로 처리되더라도 항상 경고를 남긴다. 경로의 값이 JSON null이면 SQL NULL을 돌려준다. 매뉴얼은 결과가 NULL인 경우를 빼면 JSON_VALUE(doc, path RETURNING type)이 CAST(JSON_UNQUOTE(JSON_EXTRACT(doc, path)) AS type)과 같다고 설명한다.

    -- 16GB 이상이고 1.3kg 미만인 노트북 (EAV라면 속성 행 두 개를 셀프 조인해야 했던 질의)
SELECT product_id, name
FROM product
WHERE category = 'LAPTOP'
  AND JSON_VALUE(attrs, '$.memory_gb' RETURNING UNSIGNED) >= 16
  AND JSON_VALUE(attrs, '$.weight_kg' RETURNING DECIMAL(4,2)) < 1.3;
-- 결과: 2, 울트라북 14

    비교의 함정: 문자열, 콜레이션, JSON 비교 규칙

    JSON 쿼리에서 가장 흔한 오답은 타입을 의식하지 않은 비교에서 나온다. 세 가지 함정을 차례로 보자.

    함정 1: ->>는 문자열이다. attrs->>'$.memory_gb'의 결과는 SQL 문자열 '16'이다. 이것을 '8'이라는 문자열과 비교하면 문자열 비교가 되어 첫 글자 '1'과 '8'을 먼저 비교하고, '16' > '8'은 거짓이 된다. 16GB 노트북이 "8GB보다 큰 상품" 목록에서 빠지는 것이다. 숫자 리터럴 8과 비교하면 MySQL의 일반 형 변환 규칙에 따라 문자열과 수의 비교는 부동소수점 비교가 되어 결과는 맞지만, 쿼리를 읽는 사람이 그 규칙을 떠올려야 하고 인덱스를 쓸 수도 없다. 의도를 분명히 하려면 JSON_VALUE ... RETURNING UNSIGNED나 CAST로 타입을 명시한다.

    SELECT name FROM product WHERE attrs->>'$.memory_gb' > '8';   -- 빈 결과: '16' < '8' (문자열 비교)
SELECT name FROM product WHERE attrs->>'$.memory_gb' > 8;     -- 울트라북 14 (부동소수점 비교로 변환)
SELECT name FROM product
WHERE JSON_VALUE(attrs, '$.memory_gb' RETURNING UNSIGNED) > 8;  -- 울트라북 14 (의도가 드러난다)

    함정 2: ->>의 콜레이션은 utf8mb4_bin이다. 매뉴얼의 CREATE INDEX 장은 JSON_UNQUOTE()가 LONGTEXT 타입, 그리고 하드코딩된 utf8mb4_bin 콜레이션의 문자열을 돌려준다고 설명한다. 이진 콜레이션은 대소문자를 구분하므로 attrs->>'$.color' = 'White'는 "white"를 찾지 못한다. 일반 VARCHAR 열이 기본 콜레이션 utf8mb4_0900_ai_ci로 대소문자를 무시하던 것과 다르다. 이 차이는 뒤에서 함수 기반 인덱스를 만들 때 다시 문제가 된다.

    함정 3: JSON 값끼리의 비교는 JSON 비교 규칙을 따른다. 비교 대상이 JSON 타입이면(예: ->의 결과) MySQL은 먼저 두 값의 JSON 타입을 비교하고, 타입이 다르면 우선순위만으로 결과를 정한다. 매뉴얼이 정한 우선순위는 높은 쪽부터 BLOB, BIT, OPAQUE, DATETIME, TIME, DATE, BOOLEAN, ARRAY, OBJECT, STRING, INTEGER와 DOUBLE, NULL 순이다. 타입이 같을 때만 값을 비교한다(문자열은 utf8mb4_bin 기준 사전 순이라 "A" < "a"). 또 매뉴얼은 BETWEEN, IN(), GREATEST(), LEAST()가 아직 JSON 값과의 비교를 지원하지 않으므로 네이티브 수나 문자열 타입으로 변환해서 쓰라고 안내하고, 스칼라가 아닌 값(객체, 배열)의 정렬은 지원하지 않아 경고가 난다고 적는다. 결국 WHERE와 ORDER BY에서는 JSON 값을 그대로 쓰지 말고 SQL 타입으로 바꿔서 쓴다는 습관 하나로 세 함정을 모두 피할 수 있다.

    MySQL에서 JSON 사용하기 2: 고치기, 찾기, 펼치기

    문서 일부를 고치는 함수

    문서 전체를 새 문자열로 바꿔 끼울 수도 있지만, MySQL은 경로를 지정해 일부만 고치는 함수를 제공한다. 가장 자주 쓰는 세 함수는 "경로가 이미 있을 때"와 "없을 때"의 동작만 다르다. 매뉴얼의 정의는 이렇다. JSON_SET()은 있는 값은 바꾸고 없는 값은 추가한다. JSON_INSERT()는 있는 값은 건드리지 않고 없는 값만 추가한다. JSON_REPLACE()는 있는 값만 바꾼다. 1번 상품 문서에 같은 인자를 주면 차이가 바로 보인다.

    -- 1번 상품: {"size": ["S", "M", "L"], "color": "white", "material": "cotton"}
SELECT JSON_SET(attrs,     '$.color', 'black', '$.fit', 'regular'),
       JSON_INSERT(attrs,  '$.color', 'black', '$.fit', 'regular'),
       JSON_REPLACE(attrs, '$.color', 'black', '$.fit', 'regular')
FROM product WHERE product_id = 1;
    함수있는 경로 $.color없는 경로 $.fit결과의 color / fit
    JSON_SET바꾼다추가한다"black" / "regular"
    JSON_INSERT그대로 둔다추가한다"white" / "regular"
    JSON_REPLACE바꾼다무시한다"black" / 없음

    "없는 경로에 추가한다"에는 조건이 붙는다. 매뉴얼은 존재하지 않는 경로라도 그것이 이미 있는 객체의 새 멤버이거나 이미 있는 배열의 끝을 넘는 위치일 때만 값을 추가하고, 그 밖의 경우에는 아무 효과 없이 무시한다고 정한다. 그래서 care 객체가 없는 문서에 JSON_SET(attrs, '$.care.wash', 'cold')를 실행하면 중간 객체 care가 자동으로 만들어지지 않고, 이 경로-값 쌍은 무시된다. 오류도 나지 않으므로 "저장했다고 생각했는데 저장되지 않은" 버그가 되기 쉽다. 중첩 위치에 값을 넣을 때는 JSON_SET(attrs, '$.care', JSON_OBJECT('wash', 'cold'))처럼 부모 객체째 넣는다.

    값의 타입도 주의한다. JSON_SET(attrs, '$.dims', '[30, 40]')의 세 번째 인자는 SQL 문자열이므로 문서에는 배열이 아니라 문자열 "[30, 40]"이 들어간다. 매뉴얼의 예도 같은 결과를 보여 주며, 배열을 넣으려면 CAST('[30, 40]' AS JSON)이나 JSON_ARRAY(30, 40)을 쓰라고 안내한다.

    나머지 수정 함수도 정리해 두자. JSON_REMOVE(attrs, '$.material')은 경로의 값을 지우고, 없는 경로를 지우려는 것은 오류가 아니다. 다만 경로가 $이거나 *, ** 와일드카드를 포함하면 오류다. JSON_ARRAY_APPEND(attrs, '$.size', 'XL')은 배열 끝에 원소를 붙여 ["S", "M", "L", "XL"]을 만든다. 경로가 배열이 아니라 스칼라나 객체를 가리키면 그 값을 배열로 감싼 뒤 붙이므로, JSON_ARRAY_APPEND(attrs, '$.color', 'navy')는 color를 ["white", "navy"] 배열로 바꿔 버린다. 키의 타입이 조용히 바뀌는 것이다. JSON_ARRAY_INSERT(attrs, '$.size[0]', 'XS')는 지정한 위치에 끼워 넣고 뒤의 원소를 오른쪽으로 민다. 경로-값 쌍을 여러 개 주면 앞쪽 수정이 뒤쪽 경로의 위치에 영향을 준다는 점을 매뉴얼이 예로 보여 준다.

    두 문서를 합치는 함수는 둘이다. JSON_MERGE_PATCH()는 RFC 7396(JSON Merge Patch)을 구현한다. 두 인자가 모두 객체면 키별로 재귀적으로 합치되 같은 키는 두 번째 값이 이기고, 두 번째 문서에서 값이 null인 키는 결과에서 지워진다. 두 번째 인자가 객체가 아니면 결과는 두 번째 인자 그 자체다. JSON_MERGE_PRESERVE()는 같은 키의 값을 버리지 않고 배열로 모은다. 매뉴얼의 예에서 {"a": 1, "b": 2}, {"a": 3, "c": 4}, {"a": 5, "d": 6}을 합치면 PATCH는 {"a": 5, "b": 2, "c": 4, "d": 6}, PRESERVE는 {"a": [1, 3, 5], "b": 2, "c": 4, "d": 6}이다. 예전 이름 JSON_MERGE()는 PRESERVE의 별칭으로 남아 있지만 사용 중단(deprecated) 대상이다. 설정값 덮어쓰기 같은 실무 용도에는 대부분 PATCH가 맞는다.

    문서 안을 찾는 함수

    "이 배열에 이 값이 있는가"를 묻는 함수는 세 가지이고, 뒤에서 볼 다중 값 인덱스를 쓸 수 있는 것도 이 셋이다.

    -- '경량' 태그가 있는 상품: 2, 3
SELECT product_id FROM product WHERE JSON_CONTAINS(attrs->'$.tags', '"경량"');

-- '경량'과 '캠핑'을 모두 가진 상품(AND): 3
SELECT product_id FROM product WHERE JSON_CONTAINS(attrs->'$.tags', '["경량", "캠핑"]');

-- '학생'이나 '캠핑' 중 하나라도 가진 상품(OR): 2, 3
SELECT product_id FROM product WHERE JSON_OVERLAPS(attrs->'$.tags', '["학생", "캠핑"]');

-- '캠핑'이 배열의 원소인 상품: 3
SELECT product_id FROM product WHERE '캠핑' MEMBER OF (attrs->'$.tags');

    JSON_CONTAINS(target, candidate[, path])의 두 번째 인자는 JSON 문서여야 한다. 그래서 문자열 하나를 찾을 때도 '"경량"'처럼 따옴표까지 넣은 JSON 문자열로 써야 하고, '경량'이라고 쓰면 유효한 JSON이 아니라서 오류가 난다. 포함 규칙은 매뉴얼에 이렇게 정의되어 있다. 스칼라는 비교 가능하고 같을 때만 포함된다(INTEGER와 DECIMAL끼리를 빼면 JSON_TYPE이 같아야 비교 가능하다). 후보가 배열이면 후보의 모든 원소가 대상의 어떤 원소에 포함되어야 하고, 후보가 배열이 아니면 대상 배열의 어떤 원소에 포함되면 된다. 후보가 객체면 후보의 모든 키가 대상에 있고 각 값이 포함되어야 한다. 이 규칙 때문에 JSON_CONTAINS는 "모두 포함(AND)", MySQL 8.0.17에 추가된 JSON_OVERLAPS는 "하나라도 겹침(OR)"으로 동작한다고 매뉴얼이 짝지어 설명한다.

    역시 8.0.17에 추가된 value MEMBER OF (json_array)는 값이 배열의 원소인지를 묻는다. 매뉴얼은 수와 문자열 사이의 변환을 하지 않는다는 점을 예로 강조한다. 17 MEMBER OF('[23, "abc", "17", "ab", 10]')은 0이다. 문서에 "17"(문자열)로 저장했다면 수 17로는 찾을 수 없다. JSON_OVERLAPS도 같아서 JSON_OVERLAPS('[4,5,"6",7]', '6')은 0이다. 같은 의미의 값을 문서마다 다른 타입으로 넣는 순간 검색이 깨진다는 뜻이고, 이것이 JSON에도 구조 규칙(스키마)이 필요한 이유 중 하나다.

    JSON_SEARCH(doc, 'one' | 'all', search_str)는 방향이 반대다. 값을 주면 그 값이 있는 경로를 돌려준다. 문자열 값만 찾으며, %와 _를 LIKE처럼 쓸 수 있다. 3번 상품에서 JSON_SEARCH(attrs, 'one', 'khaki')는 "$.color"를 돌려준다. 'one'일 때 여러 일치 중 어느 것을 첫 번째로 볼지는 정의되어 있지 않다고 매뉴얼이 밝히므로, 결과 경로를 특정 위치로 가정하면 안 된다. 태그가 없는 상품(1번)에서는 attrs->'$.tags'가 SQL NULL이므로 위 검색 함수들도 NULL을 돌려주고, WHERE 절에서 자연스럽게 빠진다.

    JSON_TABLE: 문서를 행으로 펼친다

    JSON 배열을 집계하거나 다른 테이블과 조인하려면 배열 원소를 행으로 바꿔야 한다. JSON_TABLE(expr, path COLUMNS (...)) AS alias는 JSON 식을 관계형 테이블로 바꾸는 테이블 함수다. 매뉴얼에 따르면 별칭은 필수이고, 같은 FROM 절의 앞 테이블 열을 참조할 수 있는 래터럴 파생 테이블(lateral derived table)로 취급된다. 열은 name FOR ORDINALITY(1부터 세는 순번), name type PATH path(값 추출), name type EXISTS PATH path(존재하면 1), NESTED PATH path COLUMNS (...)(중첩 배열 평탄화)로 정의하고, 값이 없거나 변환 오류가 나면 기본적으로 NULL을 넣는다.

    SELECT p.product_id, t.ord, t.tag
FROM product AS p,
     JSON_TABLE(p.attrs, '$.tags[*]'
       COLUMNS (ord FOR ORDINALITY,
                tag VARCHAR(20) PATH '$')) AS t
ORDER BY p.product_id, t.ord;
    product_id  ord  tag
2           1    경량
2           2    학생
3           1    경량
3           2    캠핑
4           1    러닝

    2번 상품의 $.tags[*]는 원소 두 개를 내므로 행 두 개가 되고, 태그가 없는 1번 상품은 JSON_TABLE이 행을 하나도 내지 않으므로 내부 조인 결과에서 빠진다. 이렇게 펼친 결과는 보통 테이블처럼 다룰 수 있다. GROUP BY t.tag로 묶어 COUNT(*)를 세면 경량 2, 러닝 1, 캠핑 1, 학생 1이 나온다. 다만 이 집계는 매번 모든 문서를 읽고 펼친 결과이며, 태그별 건수를 자주 봐야 한다면 6회에서 다룬 통계 테이블로 미리 집계하거나 태그를 별도 테이블로 두는 설계를 검토해야 한다.

    반대 방향, 즉 행을 JSON으로 모으는 집계 함수도 있다. JSON_ARRAYAGG(expr)는 그룹의 값들을 배열 하나로, JSON_OBJECTAGG(key, value)는 키-값 쌍들을 객체 하나로 만든다. SELECT category, JSON_ARRAYAGG(JSON_OBJECT('id', product_id, 'name', name)) FROM product GROUP BY category는 카테고리별 상품 목록을 API 응답 모양으로 바로 만든다. 단, JSON_ARRAYAGG가 만드는 배열의 원소 순서는 정의되어 있지 않으므로 순서가 필요하면 애플리케이션에서 정렬한다.

    JSON 활용 - 실무 사례 1: 상품 속성과 사용자 설정

    상품 속성: 공통 속성은 열로, 가변 속성은 JSON으로

    앞 회차의 EAV 사례를 JSON으로 옮기면 위에서 만든 product 테이블이 된다. 설계의 핵심은 나누는 선이다. 모든 상품이 가지며 목록 조회, 정렬, 조인, 집계에 쓰이는 속성(카테고리, 이름, 가격, 판매 상태, 등록일)은 일반 열로 둔다. 일반 열은 타입과 NOT NULL과 외래 키를 데이터베이스가 지키고, 인덱스와 통계를 그대로 쓸 수 있다. 카테고리마다 다르고, 주로 상세 화면에서 통째로 읽히며, 검색 조건으로는 일부만 쓰이는 속성이 attrs로 간다.

    JSON으로 옮겨도 "카테고리별로 어떤 키가 어떤 타입으로 있어야 하는가"라는 규칙은 사라지지 않는다. 이 규칙을 지키는 방법은 두 가지다. 하나는 앞 회차의 속성 정의 테이블처럼 속성 정의는 행으로, 속성 값은 JSON으로 두는 혼합형이다. 관리 화면은 속성 정의 테이블을 읽어 입력 폼을 만들고, 애플리케이션이 저장 직전에 문서를 검증한다. 다른 하나는 데이터베이스의 CHECK와 JSON_SCHEMA_VALID()로 거는 것이다. MySQL 8.0.17부터 JSON_SCHEMA_VALID(schema, doc)이 JSON Schema 명세 Draft 4를 따르는 스키마로 문서를 검증한다. CHECK 제약 안에서는 서브쿼리와 변수를 쓸 수 없으므로 스키마를 다른 테이블에서 읽어 올 수는 없고 식 안에 직접 적어야 한다. 대신 같은 행의 다른 열은 참조할 수 있으므로 카테고리별 조건을 걸 수 있다.

    ALTER TABLE product ADD CONSTRAINT chk_product_laptop_attrs CHECK (
  category <> 'LAPTOP' OR JSON_SCHEMA_VALID('{
    "type": "object",

      "cpu":        {"type": "string"},

RETURNING UNSIGNED가 변환에 실패해 NULL을 내는 문제를 입구에서 막는 것이다. 대가는 스키마가 DDL 안에 들어간다는 점이다. 노트북에 필수 속성을 하나 추가하려면 제약을 지우고 다시 만드는 ALTER TABLE이 필요하다. 속성이 매주 바뀌는 카테고리라면 애플리케이션 검증 쪽이, 몇 달에 한 번 바뀌고 여러 애플리케이션이 같은 테이블에 쓰는 환경이라면 데이터베이스 제약 쪽이 유리하다.

    사용자 설정: 부분 덮어쓰기와 기본값 병합

    회원별 알림 설정, 화면 테마, 언어 같은 설정은 JSON이 잘 맞는 전형적인 경우다. 항목이 자주 늘어나고, 항상 회원 한 명 단위로 통째로 읽히며, 설정 값으로 회원을 검색할 일은 드물다. 설정 하나를 바꿀 때마다 전체 문서를 다시 보내는 대신 JSON_MERGE_PATCH로 바뀐 부분만 보낼 수 있다.

    CREATE TABLE member_setting (
  member_id BIGINT NOT NULL,
  settings  JSON   NOT NULL,
  PRIMARY KEY (member_id)
);
INSERT INTO member_setting VALUES
  (1, '{"theme": "dark", "notify": {"email": true, "sms": true}}');

-- 문자 알림만 끄고 언어를 추가한다
UPDATE member_setting
SET settings = JSON_MERGE_PATCH(settings, '{"notify": {"sms": false}, "lang": "ko"}')
WHERE member_id = 1;
-- {"lang": "ko", "theme": "dark", "notify": {"sms": false, "email": true}}

-- 테마 설정을 지워 기본값으로 되돌린다 (null은 키 삭제)
UPDATE member_setting
SET settings = JSON_MERGE_PATCH(settings, '{"theme": null}')
WHERE member_id = 1;
-- {"lang": "ko", "notify": {"sms": false, "email": true}}

    첫 UPDATE에서 notify는 양쪽 모두 객체이므로 재귀적으로 합쳐져 email은 남고 sms만 바뀐다. 두 번째 UPDATE에서 값이 null인 theme은 RFC 7396 규칙대로 결과에서 사라진다. 출력의 키 순서는 앞에서 본 MySQL 8.0의 정렬 규칙(길이, 그다음 바이트 순)을 따른 것이다.

    저장된 설정에 없는 키는 기본값으로 채워야 한다. 기본값 문서를 첫 번째 인자로, 회원 설정을 두 번째 인자로 PATCH하면 회원이 정한 값만 기본값을 덮는다. 기본값이 {"theme": "light", "lang": "ko", "notify": {"email": true, "sms": false}}이고 회원 설정이 {"theme": "dark", "notify": {"email": true, "sms": true}}라면 결과는 {"lang": "ko", "theme": "dark", "notify": {"sms": true, "email": true}}다. 기본값을 각 행에 미리 다 써 두지 않으므로, 기본값이 바뀌면 코드 한 곳만 바꾸면 된다. 대신 "현재 기본값으로 동작 중인 회원"과 "명시적으로 같은 값을 고른 회원"이 구분된다는 점을 의도한 것인지 확인해 둔다.

    JSON 활용 - 실무 사례 2: 시점 스냅샷과 외부 연동 원문

    주문 시점의 배송지 스냅샷

    3회와 4회의 이력 설계에서 보았듯이, 주문은 "그 시점의 사실"을 보존해야 한다. 회원이 나중에 주소를 바꿔도 이미 끝난 주문의 배송지는 바뀌면 안 된다. 배송지를 회원 주소 테이블의 외래 키로만 참조하면 이 요구를 지킬 수 없으므로 주문에 값을 복사해 두는데, 수령인, 연락처, 우편번호, 주소, 상세 주소, 배송 메모 같은 필드는 언제나 한 덩어리로 쓰이고 한 덩어리로 읽힌다. 주문이 만들어진 뒤에는 바뀌지 않으므로 갱신 비용도 문제가 되지 않는다. 이런 불변 스냅샷은 JSON이 잘 맞는 자리다.

    우편번호가 빠진 문서는 3819 오류로 거부된다. 매뉴얼은 MySQL 8.0.19부터 이 직후 SHOW WARNINGS로 어떤 요구 사항(required, maximum 등)이 문서의 어느 위치에서 실패했는지 볼 수 있다고 설명한다. 위 출력에서는 required 요구 사항이 문서 최상위(#)에서 실패했다고 나온다. 우편번호를 숫자가 아니라 문자열로 정한 것은 앞자리 0을 보존하기 위해서이고, 스키마의 pattern이 형식을 지킨다. 지역별 주문 통계처럼 스냅샷 안의 값으로 집계해야 할 일이 생기면, 그 값만 생성 열로 꺼내 인덱스를 걸면 된다(다음 절).

    외부 연동 원문: 원문은 JSON으로, 규칙은 열로

    결제 대행사의 승인 응답이나 웹훅(webhook) 같은 외부 시스템의 메시지는 형식을 우리가 정하지 않는다. 필드가 예고 없이 늘어나기도 하고, 장애를 분석할 때는 받은 그대로의 원문이 필요하다. 원문을 JSON 열에 보관하되, 데이터베이스가 지켜야 할 규칙에 쓰이는 값만 생성 열로 꺼내는 설계가 깔끔하다. 아래 예의 필드 이름(eventId, status)은 설명을 위한 가상의 형식이다.

    CREATE TABLE payment_event (
  event_id    BIGINT      NOT NULL AUTO_INCREMENT,
  received_at DATETIME(6) NOT NULL,
  payload     JSON        NOT NULL,
  external_id VARCHAR(64) COLLATE utf8mb4_bin
              GENERATED ALWAYS AS (payload->>'$.eventId') STORED NOT NULL,
  status      VARCHAR(20)
              GENERATED ALWAYS AS (payload->>'$.status') VIRTUAL,
  PRIMARY KEY (event_id),
  UNIQUE KEY uk_payment_event_external (external_id),
  KEY idx_payment_event_status (status, received_at)
);

    이 테이블이 하는 일을 하나씩 보자. external_id는 원문의 eventId를 꺼낸 저장 생성 열이고 NOT NULL이므로, eventId가 없는 메시지는 INSERT 단계에서 거부된다(경로가 없으면 ->>가 NULL이 되기 때문이다). 이 열의 유니크 키는 멱등성(idempotency)을 데이터베이스가 보장하게 한다. 같은 웹훅이 재전송되면 두 번째 INSERT가 중복 키 오류로 실패하므로, 애플리케이션은 이를 "이미 처리한 이벤트"로 다루면 된다. 외부 ID는 대소문자를 구분해야 할 수 있으므로 콜레이션을 utf8mb4_bin으로 명시했다. 생략하면 테이블 기본 콜레이션(예: utf8mb4_0900_ai_ci)을 따라 대소문자만 다른 두 ID가 같은 값으로 취급된다. status는 조회 조건으로만 쓰므로 가상 생성 열로 두고, 일반 열 received_at과 묶어 복합 인덱스를 만들었다. 매뉴얼은 가상 열과 일반 열을 섞은 보조 인덱스와 가상 열을 포함한 UNIQUE 인덱스를 모두 허용한다.

    같은 원리를 참조 무결성에도 쓸 수 있다. JSON 안에 들어 있는 ID에는 외래 키를 걸 수 없지만, 그 값을 저장 생성 열로 꺼내면 외래 키를 걸 수 있다. 매뉴얼은 저장 생성 열에 정의한 외래 키가 ON UPDATE에 CASCADE, SET NULL, SET DEFAULT를, ON DELETE에 SET NULL, SET DEFAULT를 쓸 수 없다는 제약을 적고 있고, 외래 키가 가상 생성 열을 참조할 수는 없다고 밝힌다. 다만 이렇게까지 해야 하는 값이라면 처음부터 일반 열로 두는 편이 더 단순한지 먼저 따져 본다.

    다중 선택 값: JSON 배열과 연결 테이블

    상품 태그, 신발 사이즈 목록, 관심 카테고리 같은 다중 선택 값은 JSON 배열로 둘 수도, 연결 테이블(상품-태그)로 둘 수도 있다. 판단 기준은 그 값이 독립된 실체인가다. 태그에 이름 변경, 사용 중지, 설명 같은 자기 생명주기가 있고 태그별 상품 수를 자주 센다면 태그 테이블과 연결 테이블이 맞다. 외래 키가 존재하지 않는 태그를 막고, 태그 이름을 바꿀 때 행 하나만 고치면 되며, 태그별 집계는 인덱스를 탄다. 반대로 사이즈 목록처럼 값 자체가 의미의 전부이고 그 행에 딸려 있는 단순한 스칼라 목록이라면 JSON 배열과 다중 값 인덱스로 충분하다. JSON 배열로 둔 태그 이름을 바꾸려면 그 태그를 가진 모든 문서를 찾아 고쳐야 한다는 점이 둘을 가르는 가장 현실적인 비용이다.

    JSON 인덱스와 성능 최적화 1: 생성 열과 함수 기반 인덱스

    지금까지의 검색 쿼리는 모두 테이블의 모든 행을 읽어 문서마다 함수를 계산한다. 행이 수백만 개면 감당할 수 없다. 그런데 매뉴얼은 JSON 열이 다른 이진 타입 열처럼 직접 인덱싱되지 않는다고 명시한다. B+Tree 인덱스는 비교 가능한 키 값이 필요한데, 문서 전체는 그런 키가 아니기 때문이다. 대신 문서에서 스칼라 값을 꺼내는 식을 만들고 그 식에 인덱스를 건다. 방법은 세 가지다.

    생성 열: VIRTUAL과 STORED

    생성 열(generated column)은 값을 직접 넣지 않고 같은 행의 다른 열로부터 계산되는 열이다. VIRTUAL(기본값)은 값을 행에 저장하지 않고 읽을 때 계산하며, STORED는 INSERT·UPDATE 때 계산해 행에 저장한다. 매뉴얼은 InnoDB가 가상 생성 열에 보조 인덱스를 지원한다고 설명한다. 이때 생성 열 값은 인덱스 레코드 안에 실체화(materialize)된다. 즉 클러스터형 인덱스(행)에는 값이 없지만 보조 인덱스의 B+Tree에는 계산된 값이 키로 들어간다. 그래서 인덱스가 쿼리에 필요한 열을 모두 담은 커버링 인덱스라면 값을 다시 계산하지 않고 인덱스에서 꺼낸다.

    비용도 매뉴얼에 정리되어 있다. 가상 열 인덱스는 INSERT·UPDATE 때 값을 계산해 인덱스 레코드에 넣는 쓰기 비용이 있다. 그래도 클러스터형 인덱스에 값을 저장해 테이블을 키우는 STORED보다 나을 수 있다. 인덱스가 없는 가상 열은 행을 볼 때마다 다시 계산하는 읽기 비용이 있다. 인덱스가 걸린 가상 열 값은 롤백이나 퍼지 때 재계산하지 않도록 언두 로그(MVCC)에 기록되며, 그 길이는 DYNAMIC 행 형식에서 인덱스 키 한도인 3072바이트로 제한된다. 운영 관점의 차이는 더 크다. 온라인 DDL 문서에 따르면 VIRTUAL 열 추가는 분할되지 않은 테이블에서 ALGORITHM=INSTANT로 메타데이터만 바꾸는 반면, STORED 열 추가는 서버가 모든 행의 식을 계산해야 하므로 테이블을 복사해 재구성하고 그동안 동시 DML을 허용하지 않는다. 보조 인덱스 생성은 제자리(in place)로 진행되며 동시 읽기·쓰기를 허용한다.

    -- 1) 가상 생성 열 추가: 메타데이터만 바뀐다
ALTER TABLE product
  ADD COLUMN memory_gb INT UNSIGNED
      GENERATED ALWAYS AS (JSON_VALUE(attrs, '$.memory_gb' RETURNING UNSIGNED)) VIRTUAL,
  ALGORITHM = INSTANT;

-- 2) 보조 인덱스 생성: 이때 모든 행의 값을 계산해 인덱스 레코드에 넣는다
CREATE INDEX idx_product_memory_gb ON product (memory_gb);

-- 3) 생성 열 이름으로 조회한다
SELECT product_id, name FROM product WHERE memory_gb >= 16;

    memory_gb 키가 없는 상품은 JSON_VALUE가 NULL을 돌려주므로 생성 열도 NULL이 되고, 인덱스에는 NULL 키로 들어간다. 행이 충분히 많고 조건이 선택적이면 옵티마이저는 이 인덱스로 범위 스캔을 한다. 매뉴얼의 예(c->"$.id"를 꺼낸 INT 생성 열 g와 인덱스 i)에서 WHERE g > 2의 EXPLAIN은 type: range, key: i로 나온다. 위 product 테이블(4행)에서도 MySQL 8.4.13과 8.0.46 모두 WHERE memory_gb >= 16의 EXPLAIN이 type: range, key: idx_product_memory_gb였고, 생성 열 정의와 같은 식 JSON_VALUE(attrs, '$.memory_gb' RETURNING UNSIGNED) >= 16을 쓴 쿼리도 같은 계획이었다(rows 같은 추정치는 실행 환경과 통계에 따라 달라진다).

    옵티마이저가 식을 생성 열로 바꿔 주는 조건

    쿼리에 생성 열 이름 대신 원래 식을 써도 인덱스를 탈 수 있다. 매뉴얼의 "생성 열 인덱스의 옵티마이저 사용" 절은 조건을 이렇게 정한다. 대상 연산자는 =, <, <=, >, >=, BETWEEN, IN()이다(단 BETWEEN과 IN()은 JSON 값 비교에는 아직 지원되지 않는다). 쿼리의 식은 생성 열 정의와 똑같아야 하고 결과 타입도 같아야 한다. 정의가 f1 + 1이면 쿼리의 1 + f1은 인식하지 못한다. 생성 열 정의가 단순한 열 참조(AS (f1))이면 고려 대상이 아니다. 조건이 맞으면 옵티마이저가 식을 생성 열 이름으로 바꾸며, EXPLAIN 뒤의 SHOW WARNINGS에 바뀐 조건(where (t1.gc > 9))이 보인다.

    JSON에는 특별한 주의 사항이 하나 더 있다. 매뉴얼은 따옴표 붙은 문자열을 돌려주는 JSON 함수로 생성 열을 정의할 때 JSON_UNQUOTE()를 정의에 넣으라고 한다. 문자열과 함수 결과를 직접 비교할 때는 JSON 비교기가 따옴표를 처리하지만, 인덱스 조회에서는 그렇지 않기 때문이다. 정의가 JSON_UNQUOTE(JSON_EXTRACT(jdoc, '$.name'))이면 JSON_EXTRACT(jdoc, '$.name') = 'x'와 JSON_UNQUOTE(JSON_EXTRACT(jdoc, '$.name')) = 'x' 둘 다 인식되지만, JSON_UNQUOTE가 없으면 앞의 것만 인식된다. 이런 규칙을 매번 맞추기보다는 쿼리에서 생성 열 이름을 직접 쓰는 것이 가장 확실하다. 식 일치 여부를 신경 쓸 필요가 없고, 쿼리를 읽는 사람도 어떤 인덱스를 노린 조건인지 바로 안다.

    생성 열에는 또 하나의 이점이 있다. 매뉴얼에 따르면 히스토그램은 지리 타입과 JSON 열에는 만들 수 없지만, 저장·가상 생성 열에는 만들 수 있다. JSON 안의 값 분포를 옵티마이저가 알게 하려면 생성 열로 꺼내 ANALYZE TABLE product UPDATE HISTOGRAM ON memory_gb를 실행하면 된다. 인덱스를 만들지 않을 열의 조건 선택도를 추정하는 데 쓰인다.

    함수 기반 키 파트와 콜레이션 함정

    MySQL 8.0.13부터는 열을 만들지 않고 인덱스 정의에 식을 바로 쓸 수 있다. 함수 기반 키 파트(functional key part)다. 식은 괄호로 한 번 더 감싸 열 이름과 구분한다. 매뉴얼은 함수 기반 인덱스가 숨은 가상 생성 열로 구현된다고 설명하므로, 생성 열의 제약을 그대로 물려받고 테이블 열 개수 한도에도 포함된다. 기본 키에는 쓸 수 없고 외래 키에도 쓸 수 없지만 UNIQUE는 가능하다.

    JSON 문자열 값에 함수 기반 인덱스를 걸 때 매뉴얼이 직접 경고하는 함정이 있다. INDEX ((data->>'$.name'))는 만들어지지 않는다. ->>의 결과 타입이 LONGTEXT인데, MySQL은 접두사 길이 없이 LONGTEXT를 인덱싱할 수 없고, 함수 기반 키 파트에는 접두사 길이를 쓸 수 없기 때문이다. MySQL 8.4.13과 8.0.46에서 실행하면 ERROR 3757 (HY000): Cannot create a functional index on an expression that returns a BLOB or TEXT. Please consider using CAST.가 난다. 그래서 CAST(... AS CHAR(30))으로 길이를 정하면 인덱스는 만들어진다. 그런데 이번에는 쿼리 WHERE data->>'$.name' = 'James'가 이 인덱스를 쓰지 않는다. CAST()의 결과는 서버 기본 콜레이션 utf8mb4_0900_ai_ci이고 ->>의 결과는 utf8mb4_bin이어서 두 식이 같은 식이 아니기 때문이다. 매뉴얼이 제시하는 해결책은 둘이다.

    -- 해결 1: 인덱스 식에 COLLATE utf8mb4_bin을 붙인다 → ->> 쿼리가 인덱스를 쓴다 (대소문자 구분 비교)
CREATE INDEX idx_product_color
  ON product ((CAST(attrs->>'$.color' AS CHAR(30)) COLLATE utf8mb4_bin));
SELECT product_id, name FROM product WHERE attrs->>'$.color' = 'khaki';

-- 해결 2: 인덱스는 CAST만 두고, 쿼리에도 같은 CAST 식을 쓴다 (대소문자 무시 비교)
--   INDEX ((CAST(attrs->>'$.color' AS CHAR(30))))
--   WHERE CAST(attrs->>'$.color' AS CHAR(30)) = 'khaki'

-- 수 값은 JSON_VALUE로 타입을 정한 함수 기반 인덱스가 간단하다
CREATE INDEX idx_product_max_load
  ON product ((JSON_VALUE(attrs, '$.max_load_kg' RETURNING UNSIGNED)));
SELECT product_id, name FROM product
WHERE JSON_VALUE(attrs, '$.max_load_kg' RETURNING UNSIGNED) >= 100;

    두 해결책은 비교 의미가 다르다. 매뉴얼의 예에서 이름이 James와 james인 두 행이 있을 때, 해결 1은 대소문자를 구분해 한 행만 찾고, 해결 2는 대소문자를 무시해 두 행을 찾는다. 인덱스를 타게 만드는 것만 생각하다가 검색 결과의 의미가 바뀌는 일이 없도록, 어떤 비교가 업무적으로 맞는지 먼저 정한다. JSON_VALUE를 쓴 함수 기반 인덱스는 매뉴얼이 별도의 생성 열 없이 JSON 값을 인덱싱하는 방법으로 소개하는 형태이며, 역시 쿼리의 식이 인덱스 식과 똑같아야 한다.

    JSON 인덱스와 성능 최적화 2: 다중 값 인덱스와 부분 업데이트

    다중 값 인덱스: 행 하나에 인덱스 레코드 여러 개

    생성 열과 함수 기반 인덱스는 행 하나에서 키 값 하나를 꺼낸다. 하지만 "sizes_mm": [250, 260, 270]처럼 배열의 모든 원소로 행을 찾고 싶을 때는 키 하나로는 부족하다. MySQL 8.0.17부터 InnoDB가 지원하는 다중 값 인덱스(multi-valued index)가 이 문제를 푼다. 매뉴얼의 표현으로, 보통 인덱스는 데이터 레코드 하나에 인덱스 레코드 하나(1:1)지만 다중 값 인덱스는 데이터 레코드 하나에 인덱스 레코드 여러 개(N:1)를 가질 수 있다.

    ALTER TABLE product
  ADD INDEX idx_product_sizes ((CAST(attrs->'$.sizes_mm' AS UNSIGNED ARRAY)));

SELECT product_id, name FROM product WHERE 260 MEMBER OF (attrs->'$.sizes_mm');
SELECT product_id, name FROM product
WHERE JSON_CONTAINS(attrs->'$.sizes_mm', CAST('[250, 270]' AS JSON));
SELECT product_id, name FROM product
WHERE JSON_OVERLAPS(attrs->'$.sizes_mm', CAST('[245, 250]' AS JSON));
-- 세 쿼리 모두 결과: 4, 데일리 러닝화
    idx_product_sizes 의 리프 레코드 (키 → 기본 키)

   NULL → 1     (sizes_mm 경로가 없어 키 생성 결과가 NULL: NULL 항목 하나)
   NULL → 2
   NULL → 3
   250  → 4  ┐
   260  → 4  ├ 데이터 레코드 하나(4번 상품)에 인덱스 레코드 세 개
   270  → 4  ┘

    옵티마이저는 WHERE 절에 MEMBER OF(), JSON_CONTAINS(), JSON_OVERLAPS()가 있을 때 다중 값 인덱스를 쓴다. 매뉴얼의 예에서 인덱스를 만들기 전에는 세 쿼리 모두 type: ALL(전체 스캔)이었다가, 만든 뒤에는 MEMBER OF가 ref, 나머지 둘이 range로 바뀐다. 위 product 테이블에서 MySQL 8.4.13과 8.0.46으로 실행해도 같았다. 인덱스 전 MEMBER OF는 type: ALL, 인덱스 뒤에는 MEMBER OF가 ref, JSON_CONTAINS와 JSON_OVERLAPS가 range이고 세 쿼리 모두 key: idx_product_sizes다. 쿼리의 attrs->'$.sizes_mm'은 인덱스 정의의 JSON 식과 같아야 한다. NULL과 빈 배열의 처리도 매뉴얼에 정해져 있다. 키 생성 결과가 NULL이면 NULL 항목 하나가 들어가고, 빈 배열이면 인덱스 항목이 하나도 들어가지 않아 그 행은 인덱스 스캔으로 찾을 수 없다. 배열 안의 JSON null은 허용되지 않아 오류가 난다.

    제약도 많다. 매뉴얼이 나열한 것 가운데 설계에 영향을 주는 것만 추리면 다음과 같다.

    • 인덱스 하나에 다중 값 키 파트는 하나만 둘 수 있다. 일반 열과 묶은 복합 인덱스는 가능하다.
    • 같은 행의 인덱스 레코드가 인덱스 전체에 흩어지므로 범위 스캔과 인덱스만 읽는 스캔(커버링)을 지원하지 않는다. "250 이상 사이즈가 있는 상품" 같은 범위 조건에는 쓸 수 없다.
    • 순서를 지원하지 않으므로 기본 키가 될 수 없고 ASC, DESC도 쓸 수 없다. 외래 키에도 쓸 수 없다.
    • ARRAY 캐스트의 타입은 CAST()가 지원하는 타입 가운데 BINARY, JSON, YEAR를 뺀 것이다. 문자 집합과 콜레이션은 binary/binary 또는 utf8mb4/utf8mb4_0900_as_cs 조합만 지원한다.
    • 레코드당 값 개수는 언두 로그 페이지 하나에 담을 수 있는 양(65,221바이트)으로 제한되며, 매뉴얼은 정수 키 1,604개까지 들어간 시험 결과를 예로 든다.
    • 온라인 생성을 지원하지 않아 ALGORITHM=COPY로 테이블을 복사한다. 운영 중인 큰 테이블에 추가할 때는 이 점을 일정에 반영해야 한다.
    • UNIQUE로 정의할 수 있고, 이미 인덱스에 있는 값을 넣으면 중복 키 오류가 난다.
    JSON 배열 원소마다 인덱스 레코드가 하나씩 생겨 한 행을 가리키는 N:1 관계와, MEMBER OF 조회가 이 레코드를 타는 흐름을 보여 준다. Left side: a table row card labeled "4번 상품" containing JSON text "sizes_mm: [250, 260, 270]". Right side: a vertical list of index leaf entries labeled "다중 값 인덱스", showing "250 → 4", "260 → 4", "270 → 4", plus faded entries "NULL → 1", "NULL → 2", "NULL → 3". Three arrows fan out from the array in the row card to the three entries 250, 260, 270, labeled "원소마다 레코드". At top right, a query box "260 MEMBER OF (attrs->'$.sizes_mm')" with an arrow pointing to entry "260 → 4", then an arrow from that entry back to the row card labeled "기본 키로 행 읽기". A small caption badge at bottom: "N:1". Flat clean style, teal accents, white background. 배열 원소마다 인덱스 레코드가 생기므로 한 행을 여러 키로 찾을 수 있다.

    부분 업데이트: 문서 전체를 다시 쓰지 않는 조건

    큰 문서의 값 하나를 바꿀 때마다 문서 전체를 다시 쓰면 쓰기 양과 바이너리 로그가 문서 크기만큼 늘어난다. MySQL 8.0에서 옵티마이저는 조건이 맞으면 JSON 열을 부분적으로, 제자리에서(partial, in-place) 갱신한다. 매뉴얼의 조건은 다음을 모두 만족해야 한다.

    1. 갱신하는 열이 JSON으로 선언되어 있다.
    2. UPDATE 문이 JSON_SET(), JSON_REPLACE(), JSON_REMOVE() 셋 중 하나로 열을 갱신한다. SET jcol = '{"a": 10}' 같은 직접 대입은 부분 업데이트가 될 수 없다.
    3. 입력 열과 대상 열이 같다. SET jcol1 = JSON_SET(jcol2, ...)는 안 된다.
    4. 모든 변경이 기존 배열·객체 값을 새 값으로 바꾸는 것이고, 부모 객체나 배열에 새 원소를 추가하지 않는다.
    5. 바뀌는 값이 새 값보다 작지 않다. 즉 새 값이 옛 값보다 클 수 없다(이전 부분 업데이트가 남긴 빈 공간이 있으면 그만큼은 쓸 수 있다).

    앞의 이진 형식 계산을 3번 상품에 적용해 보자. {"tags": ["경량", "캠핑"], "color": "khaki", "foldable": true, "max_load_kg": 120}은 타입 1 + 머리 4 + 키 항목 16 + 값 항목 12 + 키 28 + 태그 배열 24(머리 4 + 항목 6 + 한글 두 글자 문자열 7바이트 × 2) + "khaki" 6 = 91바이트다(true와 120은 값 항목 안에 인라인된다).

    -- 주석의 값은 MySQL 8.4.13과 8.0.46에서 실행한 결과다(두 버전 같음)
UPDATE product SET attrs = JSON_SET(attrs, '$.color', 'red') WHERE product_id = 3;
SELECT JSON_STORAGE_SIZE(attrs), JSON_STORAGE_FREE(attrs) FROM product WHERE product_id = 3;
-- 91, 2   : "khaki"(6바이트) 자리에 "red"(4바이트)를 제자리에 쓰고 2바이트가 비었다

UPDATE product SET attrs = JSON_SET(attrs, '$.color', 'charcoal') WHERE product_id = 3;
-- "charcoal"(9바이트)은 원래 자리(6바이트)보다 커서 부분 업데이트 조건 5를 어긴다
-- → 문서 전체를 다시 쓴다. 다시 계산한 크기는 94, FREE는 0

    숫자를 읽는 법은 매뉴얼의 JSON_STORAGE_FREE() 설명에 있다. JSON 열 값에 대해 JSON_STORAGE_SIZE()는 부분 업데이트 이전의 크기를 그대로 보고하고, JSON_STORAGE_FREE()는 부분 업데이트로 생긴 빈 공간을 보고한다. 부분 업데이트가 아니었거나 이진 표현이 같거나 커졌다면 FREE는 0이다. 매뉴얼의 예에서도 "wxyz"를 "a"로 바꾸면 SIZE 47은 그대로이고 FREE가 3이 된다. 이 동작을 바이너리 로그에도 반영하려면 binlog_row_value_options를 PARTIAL_JSON으로 설정한다. 그러면 행 기반 복제에서 문서 전체 대신 변경분만 기록하는 간결한 형식을 쓴다.

    이 조건들은 설계에 직접 쓰인다. 자주 바뀌는 값(재고 수량, 상태 코드)을 JSON 안에 두면, 값의 길이가 늘어날 때마다, 새 키를 추가할 때마다, 애플리케이션이 문서를 통째로 대입할 때마다 전체 다시 쓰기가 일어난다. 자주 바뀌는 값은 일반 열로, 거의 바뀌지 않는 값의 묶음은 JSON으로 나누는 것이 부분 업데이트 조건과도 맞는 설계다.

    문서 단위로 쓰는 애플리케이션: 갱신 손실과 JPA 매핑

    스프링 애플리케이션에서 JSON 열은 보통 Hibernate로 매핑한다. Hibernate 6 사용자 가이드는 @JdbcTypeCode(SqlTypes.JSON)으로 명시했을 때만 JSON 타입을 쓴다고 설명한다. 직렬화·역직렬화에 쓰는 JSON 라이브러리는 자동으로 감지되며, hibernate.type.json_format_mapper 설정(jackson 또는 jsonb, 혹은 FormatMapper 구현)으로 바꿀 수 있다.

    import jakarta.persistence.*;
import org.hibernate.annotations.JdbcTypeCode;
import org.hibernate.type.SqlTypes;
import java.util.HashMap;
import java.util.Map;

@Entity
public class Product {

    @Id @GeneratedValue(strategy = GenerationType.IDENTITY)
    private Long productId;

    private String category;
    private String name;
    private int price;

    @JdbcTypeCode(SqlTypes.JSON)
    private Map attrs = new HashMap<>();

    protected Product() {
    }

    public void changeAttr(String key, Object value) {
        attrs.put(key, value);
    }
    // ...
}

    이 매핑에서 일어나는 일을 데이터베이스 쪽에서 보자. 영속성 컨텍스트는 엔티티를 읽을 때 attrs 문서 전체를 Map으로 역직렬화하고, 플러시 때 변경 감지로 값이 바뀐 것을 알아내면 UPDATE product SET attrs = ? ...로 문서 전체를 바인딩 값으로 대입한다. 앞 절의 조건 2에 따르면 직접 대입은 부분 업데이트가 될 수 없으므로, 키 하나를 바꿔도 문서 전체가 다시 쓰이고 바이너리 로그에도 전체가 기록된다.

    더 큰 문제는 동시성이다. 두 요청이 같은 상품의 서로 다른 키를 동시에 바꾼다고 하자.

    시간  트랜잭션 A (색상 변경)                    트랜잭션 B (태그 추가)
----  ----------------------------------------  ----------------------------------------
t1    SELECT → attrs = {color: khaki, tags:[경량,캠핑]}
t2                                              SELECT → attrs = {color: khaki, tags:[경량,캠핑]}
t3    메모리에서 color = red
t4    UPDATE SET attrs = {color: red, tags:[경량,캠핑]}
      COMMIT
t5                                              메모리에서 tags += 할인
t6                                              UPDATE SET attrs = {color: khaki, tags:[경량,캠핑,할인]}
                                                COMMIT
결과  attrs = {color: khaki, tags:[경량,캠핑,할인]}   ← A의 색상 변경이 사라졌다 (갱신 손실)

    B는 t2에 읽은 낡은 문서를 바탕으로 전체를 덮어썼다. 두 트랜잭션은 서로 다른 "필드"를 바꿨지만 데이터베이스 입장에서는 같은 열 하나를 통째로 바꾼 것이므로 나중에 쓴 쪽이 이긴다. 일반 열이었다면 Hibernate가 바뀐 열만 UPDATE하도록 설정할 수 있지만(동적 업데이트), JSON 열 하나 안의 필드는 그렇게 나눌 수 없다.

    해결책은 셋이다. 첫째, 낙관적 락이다. 엔티티에 @Version을 두면 B의 UPDATE는 WHERE version = ? 조건에서 영향받은 행이 0이 되어 충돌이 드러난다. 갱신을 잃는 대신 실패를 알리고 재시도하게 한다. 둘째, SQL 수준에서 부분 수정을 한다. UPDATE product SET attrs = JSON_SET(attrs, '$.color', 'red') WHERE product_id = 3 같은 문장을 네이티브 쿼리로 실행하면, InnoDB의 UPDATE는 행에 배타 락을 걸고 가장 최근에 커밋된 값을 읽어 그 위에 수정을 적용한다. B의 JSON_ARRAY_APPEND는 A의 락이 풀릴 때까지 기다린 뒤 A가 바꾼 문서에 태그를 붙이므로 두 변경이 모두 남는다. 덤으로 부분 업데이트 조건도 만족할 수 있다. 다만 이 방식은 영속성 컨텍스트를 거치지 않으므로, 같은 트랜잭션에서 이미 읽은 엔티티가 있다면 그 상태가 데이터베이스와 어긋난다는 점을 관리해야 한다. 셋째, 동시에 자주 바뀌는 값을 문서 밖의 열로 옮긴다. 갱신 경합이 있는 값은 애초에 JSON에 어울리지 않는다.

    JSON 설계의 장단점과 한계

    지금까지 본 내용을 장점과 비용으로 나눠 정리한다. 각 항목이 어느 원리에서 나오는지 함께 적었다.

    장점근거가 되는 동작
    새 속성을 DDL 없이 추가문서의 키는 데이터이므로 ALTER TABLE이 필요 없다
    한 행에서 속성 묶음을 한 번에 읽음EAV처럼 속성 개수만큼 행을 읽고 피벗하지 않는다
    타입, 중첩, 배열을 그대로 보존이진 형식이 정수, double, 문자열, 리터럴, 객체, 배열을 구분해 저장한다
    형식 검증과 빠른 내부 접근저장 시 검증, 정렬된 키로 O(log n) 조회, 재파싱 없음
    필요한 값만 골라 인덱스생성 열, 함수 기반 키 파트, 다중 값 인덱스
    외부 형식 원문 보관필드가 늘어나도 스키마 변경 없이 그대로 저장
    비용과 한계근거가 되는 동작
    참조 무결성 없음JSON 안의 ID에는 외래 키를 걸 수 없다(저장 생성 열로 꺼내야 한다)
    키별 타입·필수 여부를 DB가 모름자동 검증은 문법까지만. CHECK와 JSON_SCHEMA_VALID를 따로 걸어야 한다
    키 이름이 행마다 저장됨이진 형식에 키 문자열과 키 항목이 행마다 들어간다
    옵티마이저가 내부 값 분포를 모름JSON 열에는 히스토그램을 만들 수 없다. 생성 열로 꺼내야 통계가 생긴다
    인덱스가 식 일치에 민감함식과 결과 타입이 같아야 하고, ->>의 utf8mb4_bin 콜레이션이 어긋나기 쉽다
    비교·정렬 규칙이 SQL과 다름JSON 타입 우선순위, BETWEEN·IN() 미지원, 비스칼라 정렬 미지원
    스키마 변경이 데이터 변경으로 바뀜키 이름을 바꾸려면 모든 문서를 UPDATE해야 한다. DDL 한 줄이 대량 DML이 된다
    쓰기가 문서 단위로 커지기 쉬움부분 업데이트 조건이 까다롭고, ORM은 문서 전체를 대입한다
    큰 문서는 오프 페이지로DYNAMIC 행 형식에서 긴 값은 오버플로 페이지에 저장되고 읽을 때 추가 I/O가 든다

    표에서 가장 중요한 줄은 "스키마 변경이 데이터 변경으로 바뀜"이다. JSON은 스키마를 없애지 않는다. 문서를 읽는 코드는 여전히 "이 키는 이 타입"이라고 가정하고 있고, 그 가정이 곧 스키마다. 그 스키마가 데이터베이스 카탈로그에서 애플리케이션 코드와 문서 데이터 속으로 흩어졌을 뿐이다. 그래서 JSON 설계에서는 문서에 "v": 2 같은 형식 버전 키를 두어 옛 형식과 새 형식이 공존하는 기간을 코드가 구분할 수 있게 하는 방식도 쓰인다.

    JSON 사용 가이드라인

    속성 하나를 어디에 둘지 정할 때 아래 질문을 위에서부터 차례로 던진다. 앞쪽 질문에 "예"가 나오면 일반 열 쪽으로 기운다.

    JSON을 쓰기로 했다면 다음 규칙을 함께 지킨다.

    • 최소 구조는 데이터베이스가 지킨다. 적어도 CHECK (JSON_TYPE(col) = 'OBJECT')를 걸고, 여러 애플리케이션이 쓰는 테이블이면 JSON_SCHEMA_VALID로 필수 키와 타입을 건다.
    • 키 이름 규칙을 하나로 정한다. 키 비교는 바이트 비교라 대소문자를 구분한다. memoryGb와 memory_gb가 섞이면 같은 속성이 두 키로 나뉜다. 짧고 일관된 이름은 행마다 반복되는 저장 비용도 줄인다.
    • 값의 타입을 문서 전체에서 통일한다. 같은 키가 어떤 문서에서는 16, 어떤 문서에서는 "16"이면 MEMBER OF, JSON_CONTAINS, 다중 값 인덱스가 서로 다른 값으로 본다.
    • 금액과 정확한 소수는 JSON에 넣지 않는다. 소수부가 있는 JSON 수는 double로 저장된다. DECIMAL 열을 쓴다.
    • 검색 조건은 SQL 타입으로 바꿔 쓴다. JSON_VALUE ... RETURNING이나 생성 열을 쓰고, ->> 결과를 문자열 리터럴과 비교하거나 JSON 값에 BETWEEN을 쓰지 않는다.
    • 자주 검색되는 키는 승격시킨다. 생성 열로 꺼내 인덱스를 걸고, 그래도 핵심 속성이 되어 가면 일반 열로 옮긴다. 생성 열은 이 이동의 중간 단계로 쓰기 좋다.
    • 끝없이 자라는 배열을 만들지 않는다. 이력, 댓글, 로그처럼 계속 붙는 목록은 문서 크기, 부분 업데이트 불가(새 원소 추가), max_allowed_packet 한도에 걸린다. 별도 테이블의 행으로 둔다.
    • 큰 원문은 따로 둔다. 수 KB 이상의 원문은 자주 읽는 테이블과 분리하고, 목록 쿼리에서 SELECT *로 읽지 않는다.

    관계형 데이터베이스 vs NoSQL

    JSON 문서를 다루다 보면 "그럴 거면 처음부터 문서 데이터베이스를 쓰면 되지 않나"라는 질문이 나온다. 이 질문에 답하려면 두 모델이 어디서 출발하는지 봐야 한다. 관계형 모델은 데이터를 정규화된 테이블로 나누고, 관계는 외래 키와 조인으로 표현하며, 스키마는 쓰기 시점에 데이터베이스가 강제한다(schema-on-write). 여러 행과 여러 테이블에 걸친 트랜잭션이 기본이다. 데이터를 어떤 방식으로 읽을지 미리 몰라도, 정규화된 구조 위에서 조인으로 새로운 질문에 답할 수 있다는 것이 강점이다.

    MongoDB 같은 문서 데이터베이스는 함께 읽히는 데이터를 한 문서 안에 내장(embedding)하는 쪽에서 출발한다. MongoDB 문서를 예로 들면, MongoDB는 기본적으로 유연한 스키마 모델을 써서 한 컬렉션의 문서들이 같은 필드나 타입을 가질 필요가 없고, 필요하면 스키마 검증 규칙을 추가할 수 있다. 트랜잭션 문서는 단일 문서에 대한 연산이 원자적이며, 관련 데이터를 한 문서에 내장하면 다중 문서 트랜잭션의 필요가 줄어든다고 설명한다. 또 분산 트랜잭션은 대부분의 경우 단일 문서 쓰기보다 성능 비용이 크고, 분산 트랜잭션이 있다고 해서 효과적인 스키마 설계를 대신할 수는 없다고 적는다. 한도 문서에 따르면 BSON 문서 하나의 최대 크기는 16MiB이고, 중첩은 100단계까지다. 즉 문서 모델은 읽기 패턴에 맞춰 데이터를 미리 묶어 두는 설계이고, 그 묶음 단위가 곧 원자성의 단위다.

    관점관계형 (MySQL InnoDB)문서형 (MongoDB 문서 기준)
    설계 출발점데이터의 구조와 종속성(정규화)애플리케이션의 읽기 패턴(내장)
    스키마쓰기 시점에 DB가 강제기본은 유연한 스키마, 검증 규칙은 선택
    관계 표현외래 키와 조인내장 문서, 또는 참조와 애플리케이션 측 결합
    원자성의 기본 단위트랜잭션(여러 행·여러 테이블)단일 문서, 필요하면 다중 문서 트랜잭션
    예상 못한 새 질문조인과 집계로 대응하기 쉽다내장 구조가 맞지 않으면 재설계가 필요할 수 있다

    MySQL의 JSON 열은 이 둘 사이에 놓인다. 핵심 엔티티와 관계는 관계형으로 두고, 행마다 모양이 다른 일부 속성만 문서로 담는다. 문서 안의 값이 중요해지면 생성 열로 꺼내 인덱스와 제약을 걸고, 더 중요해지면 일반 열로 옮긴다. 반대로 데이터 대부분이 문서 단위로 읽히고, 문서 간 관계와 조인이 거의 없고, 문서 구조가 계속 바뀌는 시스템이라면 문서 데이터베이스가 더 자연스러울 수 있다. 어느 쪽이든 질문은 같다. 이 데이터는 어떤 단위로 함께 읽히고, 어떤 단위로 함께 바뀌며, 어떤 규칙을 누가 지키는가.

    이 장의 핵심

    MySQL의 JSON 열은 검증·정규화된 이진 문서로, 정렬된 키와 오프셋 항목 덕분에 파싱 없이 내부 값을 찾는다. 그러나 JSON 자체로는 외래 키, 키별 타입, 통계, 인덱스를 갖지 못하므로, 검색·무결성·동시성이 걸린 값은 생성 열이나 일반 열로 꺼내야 한다. JSON은 스키마를 없애는 도구가 아니라, 행마다 모양이 다른 데이터의 스키마를 애플리케이션과 나눠 지는 도구다. 그 경계를 정하는 기준은 언제나 "무엇을 함께 읽고, 함께 바꾸고, 누가 규칙을 지키는가"다.
    JSON 문법(RFC 8259)
    값은 객체·배열·수·문자열과 소문자 리터럴 true, false, null이다. 이름 중복, 멤버 순서, 수의 정밀도는 표준이 열어 두었고, 상호 운용되는 정수 범위는 ±(2^53 - 1)이다.
    JSON 자료형의 정규화
    MySQL은 저장 시 문서를 검증하고, 중복 키는 마지막 것을 남기며(8.0.3+), 공백을 정리하고 키를 정렬한다. 키 순서는 보장되지 않으므로 의미를 두지 않는다.
    이진 형식
    객체는 개수, 크기, 키 항목, 값 항목의 머리와 키·값 몸통으로 저장된다. 정렬된 키로 멤버를 O(log n)에 찾고, 작은 정수와 리터럴은 값 항목에 인라인된다.
    ->와 ->>
    ->는 JSON 값, ->>는 따옴표를 벗긴 utf8mb4_bin 문자열을 돌려준다. 비교에는 JSON_VALUE ... RETURNING이나 CAST로 타입을 정한다.
    수정 함수
    JSON_SET은 바꾸고 추가, JSON_INSERT는 추가만, JSON_REPLACE는 바꾸기만 한다. 없는 중간 객체는 만들지 않고, JSON_MERGE_PATCH의 null은 키를 지운다.
    생성 열 인덱스
    가상 생성 열의 값은 보조 인덱스 레코드에만 실체화된다. 옵티마이저는 같은 식·같은 타입일 때 식을 생성 열로 바꾸고, 생성 열에는 히스토그램도 만들 수 있다.
    함수 기반 키 파트
    8.0.13부터 식에 바로 인덱스를 건다. ->> 값은 CAST로 길이를 정하고, 쿼리와 콜레이션을 맞춰야 인덱스가 쓰인다.
    다중 값 인덱스
    8.0.17부터 배열 원소마다 인덱스 레코드를 만든다(N:1). MEMBER OF, JSON_CONTAINS, JSON_OVERLAPS에 쓰이며 범위·커버링 스캔은 지원하지 않는다.
    부분 업데이트
    JSON_SET·JSON_REPLACE·JSON_REMOVE로 같은 열을 고치고, 새 원소를 추가하지 않으며, 새 값이 옛 값보다 크지 않을 때만 제자리 갱신된다. 직접 대입은 항상 전체 다시 쓰기다.

    실무에서 JSON 열이 문제를 일으키는 경로는 대개 정해져 있다. 처음에는 "상세 화면에만 쓰는 속성"으로 JSON에 넣었는데, 몇 달 뒤 그 속성으로 검색하고 정렬하고 집계하는 요구가 생긴다. 이때 함수 호출을 WHERE에 그대로 쓰면 전체 스캔이 되고, ->>를 문자열과 비교해 숫자 정렬이 틀리고, 대소문자 콜레이션 때문에 검색 결과가 빠진다. 대응 순서는 정해져 있다. 그 키의 타입을 CHECK로 통일하고, 생성 열로 꺼내 인덱스와 히스토그램을 만들고, 쿼리는 생성 열 이름으로 바꾼다. 가상 열 추가는 즉시(INSTANT) 끝나고 인덱스 생성은 온라인으로 진행되므로 운영 중에도 할 수 있지만, 다중 값 인덱스는 테이블 복사가 필요하다는 점을 일정에 넣어야 한다.

    두 번째로 흔한 장애는 갱신 손실이다. 설정이나 속성을 JPA 엔티티의 Map으로 다루면 코드가 깔끔해 보이지만, 같은 행의 서로 다른 키를 바꾸는 요청이 겹치면 한쪽 변경이 조용히 사라진다. 로그에는 두 UPDATE가 모두 성공으로 남기 때문에 원인을 찾기도 어렵다. 동시 수정 가능성이 있는 JSON 열에는 처음부터 @Version을 두거나, 키 단위 변경을 JSON_SET 같은 SQL로 내려보내거나, 경합하는 값을 열로 분리한다.

    판단이 달라지는 조건도 기억해 두자. 같은 "상품 속성"이라도 카테고리가 몇 개 안 되고 속성이 거의 바뀌지 않는다면 7회의 서브타입 테이블이 타입과 제약 면에서 낫다. 속성 정의 자체를 운영자가 관리 화면에서 만들고 그 정의로 검색 필터까지 동적으로 구성해야 한다면, 속성 정의는 테이블로, 값은 JSON으로 두는 혼합형이 현실적이다. 외부 시스템 원문은 거의 항상 JSON 보관이 맞지만, 멱등성 키처럼 데이터베이스가 지켜야 할 값만큼은 생성 열과 유니크 제약으로 꺼내 두어야 한다.
  • 문서 {"name": "kim", "id": 7}를 JSON 열에 저장한 뒤 조회하면 키가 어떤 순서로 나오는가(MySQL 8.0 기준)? 또 이 문서의 JSON_STORAGE_SIZE()를 이진 형식 규칙으로 계산하라.
  • SET @j = '{"a": 1, "b": [2, 3]}'일 때 JSON_SET(@j, '$.a', 10, '$.c', '[true, false]'), JSON_INSERT(@j, '$.a', 10, '$.c', '[true, false]'), JSON_REPLACE(@j, '$.a', 10, '$.c', '[true, false]'), JSON_ARRAY_APPEND(@j, '$.a', 9)의 결과를 예측하라.
  • 테이블에 INDEX ((CAST(attrs->>'$.brand' AS CHAR(40))))를 만들었는데 WHERE attrs->>'$.brand' = 'Acme'가 인덱스를 쓰지 않는다. 원인을 설명하고, 두 가지 해결책과 각각의 검색 결과 의미 차이를 적어라.
  • JPA 엔티티의 @JdbcTypeCode(SqlTypes.JSON) Map settings를 두 요청이 동시에 수정한 뒤 한쪽 변경이 사라졌다는 장애 보고가 들어왔다. 데이터베이스에서 실제로 실행된 UPDATE를 기준으로 원인을 설명하고, 해결책 두 가지를 제시하라.
  • 숙박 예약 테이블에 다음 값을 저장하려 한다: 체크인 날짜, 객실 유형 코드(코드 테이블 참조), 투숙객 요청 사항 자유 입력, 예약 채널이 보낸 원문 응답, 부대시설 목록(검색 필터로 사용). 각 값을 일반 열, 별도 테이블, JSON 중 어디에 둘지 정하고 이유를 적어라.

    1. MySQL 8.0의 키 비교기는 길이를 먼저, 같으면 바이트 순으로 비교하므로 2바이트인 id가 4바이트인 name보다 앞선다. 조회 결과는 {"id": 7, "name": "kim"}이다. 크기는 타입 1 + 머리(개수 2 + 크기 2) 4 + 키 항목 2개 × 4 = 8 + 값 항목 2개 × 3 = 6 + 키 바이트 2 + 4 = 6 + 값(7은 int16이라 값 항목에 인라인되어 0, "kim"은 길이 1 + 3 = 4) 4 = 29바이트다. 키 순서가 입력과 달라도 문서의 의미는 같다는 점, 그리고 그 순서가 릴리스 간에 보장되지 않는다는 점까지 함께 기억한다.

    2. 매뉴얼의 예와 같다. JSON_SET은 {"a": 10, "b": [2, 3], "c": "[true, false]"}, JSON_INSERT는 a가 이미 있으므로 그대로 두고 c만 추가해 {"a": 1, "b": [2, 3], "c": "[true, false]"}, JSON_REPLACE는 없는 c를 무시해 {"a": 10, "b": [2, 3]}이다. 세 경우 모두 c의 값은 배열이 아니라 문자열이다. 세 번째 인자가 SQL 문자열이기 때문이며, 배열을 원하면 CAST(... AS JSON)을 써야 한다. JSON_ARRAY_APPEND는 경로가 스칼라를 가리키므로 그 값을 배열로 감싼 뒤 붙여 {"a": [1, 9], "b": [2, 3]}이 된다.

    3. CAST(... AS CHAR(40))의 결과는 서버 기본 콜레이션(utf8mb4_0900_ai_ci)이고, 쿼리의 ->> 결과는 utf8mb4_bin이다. 옵티마이저는 인덱스 식과 쿼리 식이 같아야 인덱스를 쓰는데, 콜레이션이 달라 같은 식으로 보지 않는다. 해결 1은 인덱스 식에 COLLATE utf8mb4_bin을 붙이는 것으로, ->> 쿼리를 그대로 쓸 수 있지만 비교가 대소문자를 구분한다(acme는 찾지 못한다). 해결 2는 쿼리를 WHERE CAST(attrs->>'$.brand' AS CHAR(40)) = 'Acme'로 바꾸는 것으로, 비교가 대소문자를 무시한다(acme, ACME도 찾는다). 어느 의미가 업무에 맞는지 먼저 정해야 한다.

    4. Hibernate는 변경 감지 후 UPDATE ... SET settings = ?로 문서 전체를 대입한다. 두 트랜잭션이 같은 문서를 읽고 각자 다른 키를 바꿨더라도, 나중에 커밋한 쪽이 자기가 읽었던 낡은 문서 전체를 쓰므로 먼저 커밋한 변경이 덮인다(갱신 손실). 해결책은 (1) 엔티티에 @Version을 두어 두 번째 UPDATE가 버전 불일치로 실패하게 하고 재시도하는 것, (2) 키 단위 변경을 UPDATE ... SET settings = JSON_SET(settings, '$.key', ?) 같은 SQL로 실행해 InnoDB가 행 락을 잡고 최신 값 위에 수정을 적용하게 하는 것이다. 경합이 잦은 키라면 일반 열로 분리하는 것도 근본적인 방법이다. 직접 대입은 부분 업데이트 조건도 만족하지 못하므로, 문서 전체가 매번 다시 쓰인다는 비용도 함께 설명할 수 있다.

    5. 체크인 날짜는 모든 예약에 있고 검색·정렬·집계에 쓰이므로 DATE 일반 열이다. 객실 유형 코드는 다른 테이블을 참조하므로 일반 열과 외래 키다(1회의 공통 코드 설계). 투숙객 요청 사항은 자유 입력 한 덩어리이므로 TEXT 열이면 충분하고, 구조화된 요청 항목이 채널마다 다르다면 JSON도 가능하다. 예약 채널 원문 응답은 형식을 우리가 정하지 않고 감사·분석용으로 그대로 보관해야 하므로 JSON이 맞으며, 채널의 예약 번호처럼 중복을 막아야 하는 값은 저장 생성 열과 유니크 키로 꺼낸다. 부대시설 목록은 시설에 이름·설명 같은 자기 생명주기가 있고 필터·집계에 쓰인다면 시설 테이블과 연결 테이블이, 단순한 코드 목록이라면 JSON 배열과 다중 값 인덱스가 후보다.

     attrs에 {"memory_gb": 16}이 있는 행이 WHERE attrs->>'$.memory_gb' > '8'에 걸리지 않는 이유는? JSON 열은 비교 연산자를 지원하지 않기 때문이다. ->>의 결과가 문자열이고 '8'도 문자열이라 사전 순 비교가 되어 '16'이 '8'보다 작기 때문이다. 16이 double로 저장되어 8과 정확히 비교되지 않기 때문이다. 경로 식에 $가 빠졌기 때문이다. ->>는 JSON_UNQUOTE(JSON_EXTRACT(...))로, 따옴표를 벗긴 SQL 문자열을 돌려준다. 문자열끼리 비교하면 첫 글자 '1'과 '8'을 먼저 비교하므로 '16'이 작다. 16은 소수부가 없어 정수로 저장되므로 보기 2는 틀리고, 비교 연산자는 문제없이 동작한다. 해결은 JSON_VALUE(attrs, '$.memory_gb' RETURNING UNSIGNED) > 8처럼 타입을 정하는 것이다. 3번 상품의 "color": "khaki"를 바꾸는 다음 UPDATE 중 부분(제자리) 업데이트가 될 수 있는 것은? SET attrs = '{"color": "red", ...문서 전체...}' SET attrs = JSON_MERGE_PATCH(attrs, '{"color": "red"}') SET attrs = JSON_SET(attrs, '$.color', 'red') SET attrs = JSON_SET(attrs, '$.color', 'red', '$.season', 'all') 부분 업데이트는 JSON_SET, JSON_REPLACE, JSON_REMOVE로 같은 열을 고치고, 새 원소를 추가하지 않으며, 새 값이 옛 값보다 크지 않을 때만 가능하다. 직접 대입(보기 0)과 JSON_MERGE_PATCH(보기 1)는 허용된 세 함수가 아니다. 보기 3은 없는 키 season을 추가하므로 조건을 어긴다. "red"(4바이트)는 "khaki"(6바이트)보다 작으므로 보기 2만 조건을 모두 만족한다. INDEX ((CAST(attrs->'$.sizes_mm' AS UNSIGNED ARRAY)))가 있을 때, 이 다중 값 인덱스를 쓸 수 있는 조건은? WHERE JSON_VALUE(attrs, '$.sizes_mm[0]' RETURNING UNSIGNED) >= 250 WHERE 260 MEMBER OF (attrs->'$.sizes_mm') WHERE attrs->>'$.sizes_mm' LIKE '%260%' ORDER BY attrs->'$.sizes_mm' 옵티마이저는 WHERE 절의 MEMBER OF(), JSON_CONTAINS(), JSON_OVERLAPS()에 다중 값 인덱스를 쓴다. 보기 0은 다른 식(첫 원소 추출)이고, 다중 값 인덱스는 범위 스캔도 지원하지 않는다. 보기 2는 문자열 패턴 검색이라 인덱스 식과 관계가 없고, 보기 3의 정렬은 다중 값 인덱스가 순서를 지원하지 않으므로 쓸 수 없다. JSON 안의 회원 ID에 참조 무결성을 걸고 싶다. MySQL 문서의 규칙에 맞는 방법은? JSON 열에 바로 FOREIGN KEY (attrs->'$.member_id')를 선언한다. 함수 기반 키 파트로 인덱스를 만들고 그 인덱스를 외래 키로 쓴다. 가상 생성 열로 꺼내고, 다른 테이블이 그 가상 열을 참조하게 한다. 저장 생성 열로 꺼내 그 열에 외래 키를 정의한다(ON UPDATE CASCADE 같은 일부 참조 동작은 쓸 수 없다). JSON 열은 직접 인덱싱되지 않고 외래 키의 대상이 될 수 없다. 함수 기반 키 파트는 외래 키 명세에 쓸 수 없고, 외래 키는 가상 생성 열을 참조할 수 없다. 매뉴얼은 저장 생성 열에 정의한 외래 키의 참조 동작 제약(ON UPDATE의 CASCADE·SET NULL·SET DEFAULT, ON DELETE의 SET NULL·SET DEFAULT 불가)을 적고 있으므로 보기 3이 맞다. 다만 이 정도로 중요한 값이면 일반 열로 두는 것이 더 단순하다. API가 {"orderId": 9007199254740993}을 JSON으로 내보냈다. 브라우저의 자바스크립트가 이를 JSON.parse로 읽었을 때 생길 수 있는 문제와 RFC 8259의 근거로 옳은 것은? 2^53 - 1을 넘는 정수는 binary64로 정확히 표현되지 않아 9007199254740992로 바뀔 수 있다. RFC는 [-(2^53)+1, (2^53)-1] 범위의 정수는 구현들이 정확히 같은 값으로 합의한다는 의미에서 상호 운용된다고 적는다. JSON 수는 32비트 정수로 제한되므로 파싱 오류가 난다. RFC가 큰 정수를 금지하므로 이 문서는 유효한 JSON이 아니다. JSON 수는 항상 문자열로 파싱되므로 문제가 없다. RFC 8259는 수의 범위를 제한하지 않으므로 문서 자체는 유효하다. 하지만 IEEE 754 binary64를 쓰는 구현은 2^53 + 1을 정확히 표현하지 못해 가장 가까운 값 2^53으로 반올림한다. RFC는 binary64 구현이 널리 쓰인다는 점을 들어 ±(2^53 - 1) 범위의 정수는 구현 간에 정확히 합의된다고 설명한다. 큰 ID는 문자열로 내보내는 것이 안전하다.
    JSON 경로 식(JSON path expression)
    $로 시작해 .key, [N], [*], ** 같은 선택자로 문서 안의 위치를 가리키는 식. 가리키는 값이 없으면 SQL NULL이 된다.
    JSON 정규화(JSON normalization)
    MySQL이 JSON을 저장할 때 중복 키를 정리하고(8.0.3부터 마지막 키 유지), 공백을 정리하고, 키를 정렬하는 처리. 키 순서는 릴리스 간에 보장되지 않는다.
    생성 열(generated column)
    같은 행의 다른 열로부터 식으로 계산되는 열. VIRTUAL은 읽을 때 계산하고, STORED는 쓸 때 계산해 행에 저장한다.
    함수 기반 키 파트(functional key part)
    MySQL 8.0.13부터 인덱스 정의에 열 대신 식을 쓰는 기능. 숨은 가상 생성 열로 구현된다.
    다중 값 인덱스(multi-valued index)
    MySQL 8.0.17부터 JSON 배열의 원소마다 인덱스 레코드를 만들어 한 행을 여러 키로 찾게 하는 보조 인덱스. CAST(... AS type ARRAY)로 정의한다.
    부분 업데이트(partial update)
    JSON 열의 일부 값을 문서 전체를 다시 쓰지 않고 제자리에서 바꾸는 갱신. 허용된 세 함수, 같은 열, 원소 추가 없음, 크기 증가 없음 조건이 필요하다.
    JSON 스키마(JSON Schema)
    JSON 문서의 구조, 타입, 필수 키를 기술하는 명세. MySQL 8.0.17부터 JSON_SCHEMA_VALID()가 Draft 4 스키마로 검증한다.
    오프 페이지 저장(off-page storage)
    InnoDB DYNAMIC 행 형식에서 긴 가변 길이 값을 오버플로 페이지에 두고 행에는 20바이트 포인터만 남기는 저장 방식.
    문서 데이터베이스(document database)
    함께 읽히는 데이터를 JSON 계열 문서 하나에 내장해 저장하는 데이터베이스. 단일 문서 연산이 원자성의 기본 단위다.
