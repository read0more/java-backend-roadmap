    이 회차의 질문: "그때는 얼마였나"에 답하려면

    앞 회차에서 우리는 행에 변경 추적 컬럼을 붙였다. created_at과 updated_at은 행이 언제 생기고 언제 마지막으로 바뀌었는지를, 변경 사유 컬럼은 왜 바뀌었는지를, created_by와 updated_by 같은 감사 컬럼은 누가 바꿨는지를 알려 준다. 그런데 이 컬럼들은 모두 마지막 변경 하나에 대한 정보다. 상품 가격이 세 번 바뀌었다면 updated_at에는 세 번째 변경 시각만 남고, 첫 번째와 두 번째 변경에 대해서는 아무것도 알 수 없다. 무엇보다 바뀌기 전의 값이 얼마였는지를 알려 주는 컬럼은 하나도 없다.

    이유는 단순하다. UPDATE는 행을 덮어쓴다. 관계형 테이블의 한 행은 "지금 이 대상에 대해 참인 사실"을 담도록 설계되어 있고, 새 사실이 들어오면 옛 사실은 그 자리에서 사라진다. InnoDB가 내부에 옛 값을 잠시 보관하기는 한다. UPDATE를 실행하면 바뀌기 전의 값이 언두 로그(undo log)에 기록되고, 이것으로 롤백을 하거나 다른 트랜잭션의 일관된 읽기(consistent read)에 옛 버전을 보여 준다. 하지만 언두 로그는 그 옛 버전을 필요로 하는 트랜잭션이 모두 끝나면 퍼지(purge)가 지운다. 언두 로그는 동시성과 복구를 위한 장치이지 이력 저장소가 아니다. 바이너리 로그(binary log)에도 행 변경 전후의 값이 남지만 이것도 보관 기간이 지나면 지워지는 파일이고, SQL로 "3월 15일의 가격"을 물을 수 있는 구조가 아니다.

    그래서 이력이 필요하면 설계로 남겨야 한다. 그런데 "이력"이라는 한 단어 안에는 성격이 다른 질문이 적어도 셋 들어 있다. 첫째, 특정 시점의 상태: "2025년 3월 15일 0시에 이 상품의 가격은 얼마였나", "그날 판매 중이던 상품 목록은 무엇이었나". 둘째, 변경 내역: "이 상품의 가격을 누가, 언제, 무엇에서 무엇으로 바꿨나". 셋째, 범위와 비용: 이력이 필요한 테이블이 하나인가 수십 개인가, 하루에 몇 건이 바뀌고 몇 년을 보관해야 하는가. 이 회차에서 볼 다섯 가지 설계는 이 세 질문에 서로 다르게 답한다. 한 방식이 모든 질문에 잘 답하는 일은 없다. 그래서 각 방식을 볼 때마다 "이 구조로는 첫째 질문에 어떤 SQL로 답하는가, 둘째 질문에는 어떤가, 그 대가로 무엇을 저장하고 무엇을 잠그는가"를 따져 보겠다.

    예제는 MySQL 8.0 InnoDB를 기준으로 하고, 온라인 쇼핑몰의 상품을 대상으로 한다. 상품에는 상품 코드(sku), 이름, 가격, 판매 상태가 있고, 상품 코드는 상품마다 유일하다. 가격은 DECIMAL(12,0)(원 단위 정수), 시각은 마이크로초까지 담는 DATETIME(6)을 쓴다. MySQL 매뉴얼에 따르면 DATETIME은 소수점 아래 최대 6자리(마이크로초)까지 저장할 수 있고, TIMESTAMP와 달리 저장할 때 시간대 변환을 하지 않는다.

    상품 하나의 가격이 10000 → 9000 → 8000으로 바뀐 같은 사건이 다섯 가지 설계에서 각각 어떤 행으로 남는지 나란히 보여 준다. 가로로 긴 흰 배경에 다섯 개의 세로 칸을 나란히 그린다. 맨 위 가운데 제목 "가격 10000 → 9000 → 8000". 첫째 칸 제목 "이전 값 컬럼": 표 한 행만 있고 칸에 "price 8000", "prev_price 9000"이 적혀 있으며 10000은 회색 취소선으로 칸 밖에 떠 있다. 둘째 칸 제목 "현재 테이블에 버전 행": 행 세 개가 쌓여 있고 맨 아래 행만 초록색 테두리에 "현재" 라벨. 셋째 칸 제목 "스냅샷 이력 테이블": 위쪽에 작은 표 "product" 한 행, 아래쪽에 표 "product_history" 세 행, 위에서 아래로 화살표. 넷째 칸 제목 "컬럼 단위 로그": 좁은 행 두 개에 "price 10000→9000", "price 9000→8000". 다섯째 칸 제목 "공통 이력 테이블": 여러 색의 행이 섞인 큰 표 하나, 그중 두 행만 강조. 칸 사이 간격은 넉넉하게, 선은 단정하게. 같은 사건도 어떤 모양으로 남기느냐에 따라 나중에 던질 수 있는 질문과 치러야 할 비용이 달라진다.

    가장 작은 이력: 이전 값을 컬럼에 보관하는 방식

    가장 단순한 방법은 바뀌는 값 옆에 바뀌기 전 값을 담을 컬럼을 하나 더 두는 것이다. 쇼핑몰 화면에서 "정가 10,000원 → 할인가 9,000원"처럼 직전 가격을 함께 보여 줘야 하는 요구가 있다면, 이 정도면 충분할 수 있다.

    CREATE TABLE product (
  product_id        BIGINT        NOT NULL AUTO_INCREMENT,
  sku               VARCHAR(30)   NOT NULL,
  name              VARCHAR(100)  NOT NULL,
  price             DECIMAL(12,0) NOT NULL,
  prev_price        DECIMAL(12,0) NULL,      -- 직전 가격. 한 번도 바뀌지 않았으면 NULL
  price_changed_at  DATETIME(6)   NULL,      -- price가 마지막으로 바뀐 시각
  PRIMARY KEY (product_id),
  UNIQUE KEY uk_product_sku (sku)
);

    가격을 바꿀 때는 지금 가격을 prev_price로 옮기고 새 가격을 넣는다. 여기서 MySQL만의 함정이 하나 있다. MySQL 8.0 매뉴얼의 UPDATE 설명에 따르면, 단일 테이블 UPDATE의 대입은 대체로 왼쪽에서 오른쪽으로 평가되고, 대입식의 오른쪽에서 갱신 대상 테이블의 컬럼을 참조하면 그 시점의 현재 값, 즉 앞선 대입이 이미 반영된 값을 쓴다. 매뉴얼은 이 동작이 표준 SQL과 다르다고 명시한다. 표준 SQL에서는 SET 절의 오른쪽 식이 모두 갱신 전 행을 기준으로 계산되므로 대입 순서가 결과에 영향을 주지 않는다.

    -- 시작 상태: product_id = 1, price = 10000, prev_price = NULL

-- (가) 올바른 순서: prev_price 대입이 먼저 실행되어 갱신 전 price(10000)를 읽는다
UPDATE product
   SET prev_price = price,
       price = 9000,
       price_changed_at = '2025-03-01 09:00:00'
 WHERE product_id = 1;
-- 결과(MySQL 8.0.46·8.4.13에서 실행): price = 9000, prev_price = 10000

-- (나) 순서를 바꾸면: price가 먼저 9000이 되고, prev_price는 갱신된 price(9000)를 읽는다
UPDATE product
   SET price = 9000,
       prev_price = price,
       price_changed_at = '2025-03-01 09:00:00'
 WHERE product_id = 1;
-- 결과(시작 상태에서 실행, MySQL 8.0.46·8.4.13): price = 9000, prev_price = 9000  ← 직전 가격이 사라졌다
-- 경고 없음, ROW_COUNT() = 1

    (나)는 문법 오류가 아니므로 아무 경고 없이 실행되고, 영향받은 행 수도 1로 정상이다. 테스트에서 직전 가격 표시를 확인하지 않으면 운영에서 "할인 전 가격이 할인가와 같게 나온다"는 문의가 들어온 다음에야 발견된다. 같은 SQL을 PostgreSQL처럼 표준 동작을 따르는 DBMS에서 옮겨 왔다면 더 찾기 어렵다. 규칙은 하나다. MySQL에서 이전 값을 다른 컬럼으로 옮기는 UPDATE는 옮기는 대입을 먼저 쓴다. 매뉴얼은 다중 테이블 UPDATE에서는 대입 순서가 보장되지 않는다고도 적고 있으므로, 조인이 들어간 UPDATE에서 이 패턴을 쓰지 않는 편이 안전하다.

    두 번째 함정은 값이 바뀌지 않는 UPDATE다. 관리 화면에서 가격 칸을 건드리지 않고 저장 버튼을 누르면 애플리케이션이 price = 9000을 다시 보낼 수 있다. (가)의 SQL은 이 경우에도 prev_price = price를 실행하므로 직전 가격 10000이 9000으로 덮인다. 그래서 이 UPDATE에는 AND price <> 9000처럼 "값이 실제로 바뀔 때만"이라는 조건을 붙이거나, 애플리케이션에서 이전 값과 새 값을 비교한 뒤에만 실행해야 한다. 이력 설계 전반에 걸쳐 반복되는 원칙이 여기서 처음 나온다. 변경 이력은 "UPDATE 문이 실행되었다"가 아니라 "값이 바뀌었다"를 기록해야 한다.

    이 방식이 답하는 질문과 답하지 못하는 질문

    가격이 10000 → 9000 → 8000으로 두 번 바뀐 뒤의 행은 price = 8000, prev_price = 9000이다. 10000이라는 값은 어디에도 없다. 이 구조가 기억하는 것은 정확히 한 단계 전뿐이다. 그러므로 "직전 가격 대비 몇 퍼센트 할인인가"에는 답하지만 "3월 15일의 가격은 얼마였나"에는 답하지 못한다. price_changed_at이 3월 20일이라면 3월 15일의 가격은 prev_price일 수도 있고 그보다 더 이전 값일 수도 있다. prev_price가 언제부터 유효했는지 모르기 때문이다. 이를 알려면 prev_price_changed_at을 또 둬야 하고, 두 단계 전이 필요하면 prev_prev_price를 둬야 한다. 컬럼으로 시간을 늘리는 설계는 여기서 무너진다.

    또 이 방식은 컬럼마다 따로 붙여야 한다. 이름의 이전 값이 필요하면 prev_name, 판매 상태의 이전 값이 필요하면 prev_status가 생긴다. 반대로 말하면 이 방식이 맞는 곳은 분명하다. 화면이나 업무 규칙이 "직전 값 하나"를 현재 값과 함께 필요로 하고, 그보다 오래된 값은 업무적으로 의미가 없는 경우다. 이전 값은 현재 행과 같은 페이지에 있으므로 조인도 추가 조회도 없이 함께 읽힌다. 데이터 웨어하우스 분야에서 쓰는 Kimball의 용어로는 이것이 SCD(Slowly Changing Dimension) Type 3에 해당한다. Kimball Group은 Type 3을 "옛 값을 보존할 새 속성을 추가하고, 새 값은 주 속성을 덮어쓰는" 방식으로 정의한다. 이력을 남기는 장치라기보다 현재 행에 비교 기준 하나를 붙이는 장치에 가깝다.

    현재 테이블로 이력 관리하기: 같은 테이블에 버전 행을 쌓는다

    값을 덮어쓰지 않으려면 바뀔 때마다 새 행을 넣으면 된다. 가장 직접적인 방법은 상품 테이블 자체를 "상품의 버전" 테이블로 바꾸는 것이다. 상품 하나는 여러 행으로 표현되고, 그중 한 행만 현재 버전이다.

    CREATE TABLE product_version (
  product_id  BIGINT        NOT NULL,   -- 같은 상품의 버전들이 공유하는 식별자
  version_no  INT           NOT NULL,   -- 1, 2, 3 ...
  sku         VARCHAR(30)   NOT NULL,
  name        VARCHAR(100)  NOT NULL,
  price       DECIMAL(12,0) NOT NULL,
  status      VARCHAR(20)   NOT NULL,
  is_current  TINYINT(1)    NOT NULL,   -- 1이면 현재 버전
  changed_at  DATETIME(6)   NOT NULL,   -- 이 버전이 만들어진 시각
  PRIMARY KEY (product_id, version_no)
);

    기본 키를 (product_id, version_no)로 둔 데는 두 가지 이유가 있다. 첫째, "한 상품 안에서 버전 번호는 겹치지 않는다"는 규칙을 기본 키가 직접 지킨다. 뒤에서 보겠지만 이 규칙이 동시 수정 사고를 막는 마지막 방어선이 된다. 둘째, InnoDB에서 테이블의 행은 기본 키 순서로 정렬된 클러스터형 인덱스(clustered index)의 리프 페이지에 저장된다. 기본 키가 product_id로 시작하면 한 상품의 버전들이 리프에서 서로 붙어 있게 되어, 한 상품의 이력이나 현재 버전을 찾을 때 기본 키 범위 하나만 읽으면 된다. 만약 기본 키를 AUTO_INCREMENT 대리 키 하나로 두면, 버전 행은 만들어진 순서로 저장되므로 한 상품의 버전들이 테이블 전체에 흩어진다.

    상품 1의 가격과 이름이 두 번 바뀐 뒤 테이블은 다음과 같다.

    product_idversion_noskunamepricestatusis_currentchanged_at
    11KB-01무선 키보드10000ON_SALE02025-01-01 09:00
    12KB-01무선 키보드9000ON_SALE02025-03-01 09:00
    13KB-01무선 키보드 프로9000ON_SALE12025-04-01 09:00

    이제 세 가지 질문에 모두 SQL로 답할 수 있다. 현재 상태는 WHERE product_id = 1 AND is_current = 1, 전체 이력은 WHERE product_id = 1 ORDER BY version_no, 특정 시점의 상태는 그 시점 이전에 만들어진 버전 중 가장 최근 것이다.

    -- 2025-03-15 0시의 상품 1
SELECT version_no, name, price
  FROM product_version
 WHERE product_id = 1
   AND changed_at <= '2025-03-15 00:00:00'
 ORDER BY version_no DESC
 LIMIT 1;
-- 결과(MySQL 8.4.13에서 실행): version_no = 2, name = '무선 키보드', price = 9000

    변경 절차는 "현재 버전을 닫고, 새 버전을 연다"는 두 단계다. 두 단계는 반드시 한 트랜잭션 안에 있어야 한다. 첫 단계만 반영되고 둘째 단계가 실패하면 현재 버전이 하나도 없는 상품이 생기고, 순서를 거꾸로 해서 둘째 단계만 반영되면 현재 버전이 둘인 상품이 생긴다.

    START TRANSACTION;

-- ① 현재 버전을 잠그면서 읽는다
SELECT version_no, sku, name, price, status
  FROM product_version
 WHERE product_id = 1 AND is_current = 1
   FOR UPDATE;
-- 결과(MySQL 8.4.13에서 실행): version_no = 3, sku = 'KB-01', name = '무선 키보드 프로', price = 9000, status = 'ON_SALE'

-- ② 현재 버전을 닫는다
UPDATE product_version
   SET is_current = 0
 WHERE product_id = 1 AND version_no = 3;

-- ③ 새 버전을 연다 (바뀐 값 + 바뀌지 않은 값 전부)
INSERT INTO product_version
  (product_id, version_no, sku, name, price, status, is_current, changed_at)
VALUES
  (1, 4, 'KB-01', '무선 키보드 프로', 8000, 'ON_SALE', 1, '2025-05-01 09:00:00');

COMMIT;

    ①의 FOR UPDATE는 장식이 아니다. InnoDB의 기본 격리 수준인 REPEATABLE READ에서 평범한 SELECT는 일관된 읽기, 즉 트랜잭션의 첫 읽기 때 만들어진 스냅샷을 읽는다. 다른 트랜잭션이 방금 커밋한 새 버전을 보지 못할 수 있다는 뜻이다. MySQL 매뉴얼은 가장 최신 상태를 보려면 READ COMMITTED를 쓰거나 잠금 읽기(locking read)를 쓰라고 안내하고, 잠금 읽기는 최신 행을 가진 트랜잭션이 끝날 때까지 기다린다고 설명한다. 이 조건 product_id = 1 AND is_current = 1은 기본 키의 앞부분 product_id로 범위를 찾는 조건이고 유일한 행 하나를 지목하는 조건이 아니다. 매뉴얼의 InnoDB 잠금 설명에 따르면 이런 검색 조건에서 SELECT ... FOR UPDATE는 훑은 인덱스 범위에 넥스트 키 락(next-key lock)이나 갭 락(gap lock)을 걸어 그 범위에 다른 세션이 끼어드는 것을 막는다. 결과적으로 같은 상품을 동시에 수정하려는 두 번째 트랜잭션은 ①에서 기다리고, 첫 번째가 커밋한 뒤에야 버전 4를 현재 버전으로 읽는다.

    여기까지 보면 꽤 깔끔한 설계다. 테이블 하나로 현재와 과거를 모두 표현하고, 특정 시점 조회도 SQL 한 문장이다. 하지만 이 테이블은 이제 "상품"이 아니라 "상품의 버전"을 담는다. 이 차이가 테이블을 쓰는 모든 곳에 비용을 퍼뜨린다. 그 비용을 두 묶음으로 나눠 보자.

    현재 테이블 방식의 단점 1: 식별자와 참조가 흔들린다

    첫 번째 묶음은 "상품 하나 = 행 하나"라는 전제가 깨지면서 생기는 문제다. 데이터베이스 설계 1편에서 본 것처럼 테이블의 한 행은 엔티티 인스턴스 하나를 나타내고, 기본 키는 그 인스턴스를 식별한다. product_version의 기본 키 (product_id, version_no)는 버전을 식별할 뿐, 상품을 식별하는 컬럼 product_id에는 유일성이 없다. 이 사실이 세 군데에서 터진다.

    모든 조회가 "현재" 조건을 짊어진다

    상품 목록, 상품 검색, 장바구니, 재고, 정산처럼 상품을 읽는 거의 모든 쿼리는 현재 상태만 필요하다. 이 쿼리들은 이제 하나도 빠짐없이 is_current = 1을 붙여야 한다. 하나라도 빠뜨리면 결과가 틀린다. 그런데 이 오류는 바로 드러나지 않는다. 막 등록된 상품은 버전이 하나뿐이어서 조건이 없어도 결과가 맞고, 수정이 쌓인 상품에서만 같은 상품이 여러 번 나온다. 개발 환경의 테스트 데이터는 대부분 수정 이력이 없으므로, 이 버그는 운영 데이터에서 처음 발견된다.

    조인과 집계에서는 더 조용하게 틀린다. 주문 상품 테이블이 product_id만 갖고 있다고 하자. 상품 1을 2개 산 주문 한 건을 product_version과 product_id로만 조인하면, 상품 1의 버전이 4개이므로 주문 상품 한 행이 네 행으로 불어난다. 이 상태에서 SUM(quantity)를 구하면 8이 나온다. 쿼리는 오류 없이 실행되고 숫자만 네 배가 된다. 이렇게 조인 결과의 행이 늘어나는 현상을 행 증식(fan-out)이라 하는데, 이 설계에서는 수정 횟수가 곧 증식 배수다. COUNT(*)로 상품 수를 세는 쿼리도 마찬가지로 버전 수를 센다.

    외래 키가 가리킬 곳이 없다

    외래 키는 참조되는 쪽의 기본 키나 유니크 키를 가리켜야 의미가 있다. 주문 상품이 "상품"을 참조하고 싶어도, product_id가 유일한 테이블이 없으므로 FOREIGN KEY (product_id) REFERENCES ...를 걸 대상이 없다. 남은 선택지는 둘이다. 하나는 (product_id, version_no)를 참조하는 것이다. 이렇게 하면 주문 상품은 "주문할 때의 그 버전"에 고정된다. 데이터베이스 설계 1편에서 본 "주문 당시 가격"을 보존하는 효과가 있으므로 이것이 오히려 맞는 경우도 있다. 하지만 장바구니처럼 "그 상품의 지금 상태"를 가리켜야 하는 참조에는 맞지 않는다. 상품이 수정될 때마다 장바구니의 참조를 새 버전으로 옮겨야 하기 때문이다. 다른 하나는 외래 키를 포기하는 것이다. 그러면 참조 무결성을 데이터베이스가 지켜 주지 않는다.

    새 상품의 product_id를 어떻게 발급할지도 문제다. 버전 테이블에는 상품 단위로 하나씩 늘어나는 값을 만들어 줄 자리가 없다. SELECT MAX(product_id) + 1로 구하면 동시에 두 상품을 등록할 때 같은 번호가 나온다. 이 두 문제를 함께 푸는 정석은 상품의 정체성만 담는 작은 테이블을 따로 두는 것이다.

    CREATE TABLE product (
  product_id  BIGINT      NOT NULL AUTO_INCREMENT,  -- 상품 식별자를 여기서 발급한다
  created_at  DATETIME(6) NOT NULL,
  PRIMARY KEY (product_id)
);

-- product_version에 외래 키 추가
ALTER TABLE product_version
  ADD CONSTRAINT fk_pv_product FOREIGN KEY (product_id) REFERENCES product (product_id);

-- 장바구니, 주문 상품 등은 product(product_id)를 참조할 수 있다

    이렇게 하면 외래 키와 식별자 문제는 풀린다. 그런데 이 구조를 잘 보면, 상품의 정체성은 product에 있고 상품의 상태는 product_version에 있다. 현재 상태를 읽으려면 여전히 product_version에서 is_current = 1을 찾아야 한다. 여기서 한 걸음만 더 가서 "현재 상태도 product에 두고, product_version에는 과거만 두면 어떨까"라고 생각하면, 그것이 뒤에서 볼 이력 테이블 방식이다. 현재 테이블 방식의 문제를 고치다 보면 자연스럽게 테이블이 둘로 갈라진다.

    현재 테이블 방식의 단점 2: 유일성, 동시성, 그리고 공간

    두 번째 묶음은 과거 행이 현재 행과 같은 테이블, 같은 인덱스, 같은 페이지에 섞여 있어서 생기는 문제다.

    유니크 제약을 그대로 걸 수 없다

    상품 코드 sku는 상품마다 유일해야 한다. 그런데 product_version에서는 같은 상품의 버전들이 같은 sku를 공유하므로 UNIQUE (sku)를 걸면 두 번째 버전부터 INSERT가 실패한다. 우리가 원하는 규칙은 "현재 버전들 사이에서 sku가 유일하다"인데, 이는 행의 일부에만 적용되는 제약이다. PostgreSQL 같은 일부 DBMS는 WHERE 절이 붙은 부분 인덱스(partial index)로 이를 표현하지만, MySQL 8.0의 CREATE INDEX 문법에는 인덱스에 행 조건을 붙이는 절이 없다.

    대신 MySQL에서는 두 가지 사실을 조합해 같은 효과를 낸다. 첫째, 매뉴얼에 따르면 UNIQUE 인덱스는 NULL을 허용하는 컬럼에서 여러 개의 NULL을 허용한다. 둘째, MySQL 8.0.13부터 인덱스 키에 컬럼 대신 식을 쓰는 함수 기반 키 부분(functional key part)을 지원하며, 이는 숨겨진 가상 생성 컬럼(hidden virtual generated column)으로 구현된다. 그러므로 "현재 버전이면 값, 아니면 NULL"인 식에 유니크 인덱스를 걸면, 과거 버전은 모두 NULL이 되어 제약에서 빠지고 현재 버전끼리만 비교된다.

    -- 현재 버전들 사이에서만 sku 유일
CREATE UNIQUE INDEX uk_pv_current_sku
  ON product_version ((CASE WHEN is_current = 1 THEN sku END));

-- 상품 하나에 현재 버전은 최대 하나
CREATE UNIQUE INDEX uk_pv_current_product
  ON product_version ((CASE WHEN is_current = 1 THEN product_id END));

    두 번째 인덱스가 특히 중요하다. "상품마다 현재 버전은 하나"라는 이 설계의 핵심 불변식을 데이터베이스가 지키게 해 주기 때문이다. 다만 이 인덱스는 "최대 하나"만 보장하고 "최소 하나"는 보장하지 못한다. 현재 버전을 닫고 새 버전을 넣지 않은 채 커밋하면 현재 버전이 없는 상품이 생기는데, 이것은 제약으로 막을 수 없고 트랜잭션 절차로 막아야 한다. 또 절차의 순서가 정해진다. MySQL은 유니크 제약을 문장 끝이나 커밋 때가 아니라 행을 바꿀 때마다 검사한다. 매뉴얼의 UPDATE 설명에는 유니크 인덱스가 있는 id에 UPDATE t SET id = id + 1을 실행하면 행을 갱신하는 순서에 따라 중복 키 오류가 날 수 있다는 예가 나온다. 따라서 새 버전을 먼저 INSERT하고 옛 버전을 나중에 닫으면, INSERT 시점에 현재 버전이 둘이 되어 오류가 난다. 위 두 인덱스를 만든 뒤 MySQL 8.0.46과 8.4.13에서 상품 1의 현재 버전을 닫지 않고 새 현재 버전을 INSERT하면 ERROR 1062 (23000): Duplicate entry 'KB-01' for key 'product_version.uk_pv_current_sku'로 실패한다(같은 sku를 쓰므로 sku 쪽 인덱스에서 먼저 걸렸다). 앞 절의 절차가 "닫고, 연다" 순서인 이유다.

    동시 수정이 현재 버전을 둘로 만든다

    앞 절의 ①에서 FOR UPDATE를 빼면 어떻게 되는지 두 트랜잭션 T1, T2로 추적해 보자. 상품 1의 현재 버전은 3이다.

    시각  T1 (가격 8000으로)                       T2 (이름 변경)
────  ─────────────────────────────────────   ─────────────────────────────────────
 t1   SELECT ... is_current = 1  → 버전 3
 t2                                            SELECT ... is_current = 1  → 버전 3
 t3   UPDATE 버전 3 SET is_current = 0
      (행 (1,3)에 배타 잠금)
 t4                                            UPDATE 버전 3 SET is_current = 0
                                               → (1,3) 잠금 대기
 t5   INSERT (1, 4, ... price 8000, 현재)
 t6   COMMIT  → 잠금 해제
 t7                                            UPDATE 진행 (이미 0인 값을 0으로)
 t8                                            INSERT (1, 4, ... 새 이름, 현재)
                                               → 기본 키 (1,4) 중복 오류

    t7에서 T2의 UPDATE는 기다렸다가 T1이 커밋한 최신 행을 대상으로 진행한다. 이미 is_current가 0이어도 WHERE 조건 product_id = 1 AND version_no = 3에는 맞으므로 문장은 성공한다. 그다음 T2는 t2에서 읽은 버전 3을 기준으로 다음 번호 4를 계산했으므로 (1, 4)를 넣으려다 기본 키 중복으로 실패한다. 오류가 났으니 애플리케이션이 재시도하거나 사용자에게 알리면 된다. 기본 키에 version_no를 넣은 덕분에 데이터가 망가지는 대신 오류가 난 것이다. MySQL 8.4.13에서 두 세션으로 이 순서를 재현하면, T2의 UPDATE는 T1이 커밋할 때까지 기다린 뒤 영향받은 행 0(이미 0인 값이라 바뀐 행이 없다)으로 끝나고, t8의 INSERT는 기본 키(PRIMARY) 중복 오류 ERROR 1062 (23000): Duplicate entry '1-4'로 실패한다. 앞 절의 현재 버전 유니크 인덱스 두 개를 함께 걸어 두어도 기본 키 중복으로 먼저 걸렸다.

    만약 기본 키가 AUTO_INCREMENT 대리 키 하나뿐이고 (product_id, version_no)에 유니크 제약도, 앞의 현재 버전 유니크 인덱스도 없었다면 t8의 INSERT는 성공한다(MySQL 8.4.13에서 같은 순서로 재현해 두 INSERT가 모두 성공하는 것을 확인했다). 상품 1에는 is_current = 1인 버전 4가 두 개 생기고, 하나는 가격만 바뀐 버전, 하나는 이름만 바뀐 버전이다. T1의 가격 변경이 T2의 버전에는 반영되지 않았으므로 어느 쪽을 현재로 보든 한 사람의 수정은 사라진다. 이것이 갱신 손실(lost update)이 이력 테이블에서 나타나는 모습이다. 정리하면 이중 방어가 필요하다. 절차로는 잠금 읽기(①의 FOR UPDATE)로 같은 상품의 수정을 줄 세우고, 제약으로는 버전 번호 유일성과 현재 버전 유일성을 걸어 절차가 뚫렸을 때 오류로 끝나게 한다.

    과거가 현재의 페이지를 차지한다

    마지막 비용은 공간과 캐시다. 상품 10만 개에 버전이 평균 20개씩 쌓였다면 테이블에는 200만 행이 있고, 그중 현재 행은 10만 개, 즉 5%다. 기본 키가 product_id로 시작하므로 상품 하나의 버전 20개는 리프 페이지에서 붙어 있고, 현재 버전은 그 사이에 끼어 있다. InnoDB는 기본 16KB 크기의 페이지 단위로 디스크를 읽고 버퍼 풀에 올린다. 그러므로 "판매 중인 상품 전체 목록"처럼 현재 행만 필요한 쿼리도 과거 행이 95%를 차지하는 페이지들을 모두 읽어야 한다. 버퍼 풀에 올라온 페이지의 대부분이 거의 읽히지 않는 과거 행으로 채워져, 같은 메모리로 캐시할 수 있는 현재 데이터의 양이 줄어든다.

    is_current로 시작하는 보조 인덱스를 만들면 현재 행을 찾는 범위는 좁힐 수 있다. 하지만 보조 인덱스에서 찾은 각 행의 나머지 컬럼을 읽으려면 클러스터형 인덱스를 다시 찾아가야 하고, 그 페이지에는 여전히 과거 행이 섞여 있다. 또 모든 보조 인덱스에 과거 행의 항목이 들어가므로 인덱스도 함께 커진다. 이력이 길어질수록 현재 데이터에 대한 모든 작업이 조금씩 느려진다. 과거와 현재를 한 테이블에 두는 설계의 근본적인 대가다.

    현재 테이블 방식의 핵심

    버전 행을 같은 테이블에 쌓으면 "행 하나 = 대상 하나"라는 전제가 깨진다. 그 결과 모든 조회에 현재 조건이 필요해지고, 외래 키와 유니크 제약은 그대로 걸 수 없으며, 동시 수정은 잠금 읽기와 제약 두 겹으로 막아야 하고, 현재 데이터만 필요한 작업도 과거 행이 섞인 페이지를 읽는다. 정체성 테이블을 분리하고 생성 컬럼 유니크 인덱스를 쓰면 상당 부분을 막을 수 있지만, 그만큼 구조는 이력 테이블 방식에 가까워진다.

    유효 기간: 버전이 "언제부터 언제까지" 참이었나

    지금까지의 product_version은 각 버전이 만들어진 시각 changed_at만 갖고 있었다. 특정 시점 조회는 "그 시점 이전에 만들어진 버전 중 가장 최근 것"이라는 정렬과 LIMIT으로 풀었다. 상품 하나를 볼 때는 이것으로 충분하지만, "3월 15일에 판매 중이던 상품 전체"처럼 여러 상품을 한꺼번에 볼 때는 상품마다 최신 버전을 골라내는 계산이 필요해진다. 그래서 버전마다 유효 시작 시각과 유효 종료 시각을 함께 저장하는 방식이 널리 쓰인다. Kimball Group은 SCD Type 2를 "바뀐 속성 값으로 새 행을 추가하는" 방식으로 정의하면서, 최소한 행 유효 시작일, 행 만료일, 현재 행 표시 세 컬럼을 추가하라고 설명한다. 지금까지 본 버전 행 방식이 바로 Type 2이고, 유효 기간이 그 완성형이다.

    CREATE TABLE product_version (
  product_id  BIGINT        NOT NULL,
  version_no  INT           NOT NULL,
  sku         VARCHAR(30)   NOT NULL,
  name        VARCHAR(100)  NOT NULL,
  price       DECIMAL(12,0) NOT NULL,
  status      VARCHAR(20)   NOT NULL,
  valid_from  DATETIME(6)   NOT NULL,                                   -- 포함
  valid_to    DATETIME(6)   NOT NULL DEFAULT '9999-12-31 23:59:59',     -- 제외
  current_product_id BIGINT
      AS (CASE WHEN valid_to = '9999-12-31 23:59:59' THEN product_id END) STORED,
  PRIMARY KEY (product_id, version_no),
  UNIQUE KEY uk_pv_current (current_product_id),
  CONSTRAINT ck_pv_period CHECK (valid_from < valid_to),
  CONSTRAINT fk_pv_product FOREIGN KEY (product_id) REFERENCES product (product_id)
);

    이 정의에는 결정이 네 가지 들어 있다. 하나씩 이유를 따져 보자.

    결정 1: 반열린 구간 [valid_from, valid_to)

    버전 2가 3월 1일 9시에 시작해 4월 1일 9시에 끝났다면, 버전 2의 valid_to와 버전 3의 valid_from은 같은 값 2025-04-01 09:00:00이다. 이 경계 시각에 상품은 버전 2인가 버전 3인가? 답은 하나여야 한다. 시작은 포함하고 끝은 제외하는 반열린 구간(half-open interval)으로 정의하면 시점 t에 유효한 버전의 조건은 valid_from <= t AND t < valid_to가 되고, 경계 시각 4월 1일 9시에는 버전 3 하나만 걸린다. 연속된 두 구간이 정확히 맞닿으므로 틈도 겹침도 없다.

    양 끝을 모두 포함하는 닫힌 구간으로 정의하면 어떻게 될까. 흔히 쓰는 t BETWEEN valid_from AND valid_to가 바로 닫힌 구간이다. MySQL의 BETWEEN은 최솟값 이상이고 최댓값 이하일 때 참이다. 그러면 경계 시각 4월 1일 9시에는 버전 2와 버전 3이 동시에 걸려 두 행이 나온다. 이를 피하려고 버전 2의 종료를 "다음 버전 시작 1초 전"인 08:59:59로 저장하면, 이번에는 08:59:59.5 같은 시각이 어느 버전에도 속하지 않는 틈이 생긴다. DATETIME(6)이 마이크로초까지 담는 이상, "1초 전"이든 "1마이크로초 전"이든 정밀도를 하나 정해 빼는 방식은 정밀도가 바뀌는 순간 깨진다. 반열린 구간은 정밀도와 무관하게 성립한다. 날짜 범위 검색에서 ordered_at >= '2025-03-01' AND ordered_at < '2025-04-01'처럼 끝을 제외하는 것과 같은 원리다.

    버전 1, 2, 3의 유효 기간이 반열린 구간으로 틈 없이 맞닿아 있고, 경계 시각을 조회하면 정확히 한 버전만 걸린다는 것을 보여 준다. 흰 배경에 왼쪽에서 오른쪽으로 가는 가로 시간축을 그린다. 축 아래에 눈금 라벨 "01-01 09:00", "03-01 09:00", "04-01 09:00", "9999-12-31". 축 위에 가로 막대 세 개를 계단처럼 배치한다: 막대 1 "버전 1 · 10000원"(01-01부터 03-01까지), 막대 2 "버전 2 · 9000원"(03-01부터 04-01까지), 막대 3 "버전 3 · 9000원 · 이름 변경"(04-01부터 오른쪽 끝까지, 끝이 흐려지며 "현재"). 각 막대의 왼쪽 끝은 채워진 동그라미, 오른쪽 끝은 속이 빈 동그라미로 그린다. 03-15 위치에 세로 점선과 라벨 "t = 03-15 → 버전 2", 04-01 09:00 위치에 빨간 세로 점선과 라벨 "경계 시각 → 버전 3 하나만". 오른쪽 아래 작은 상자에 "시작 포함, 끝 제외". 시작은 포함하고 끝은 제외하면 연속된 버전이 틈 없이 맞닿고, 어떤 시각을 물어도 정확히 한 버전이 답한다.

    결정 2: 열린 끝은 NULL이 아니라 최댓값으로

    현재 버전은 아직 끝나지 않았다. 이를 valid_to = NULL로 표현하고 싶어지지만, 그러면 시점 조회 조건이 valid_from <= t AND (valid_to IS NULL OR t < valid_to)가 된다. 조건이 길어지는 것보다 위험한 것은 빠뜨렸을 때다. 누군가 t < valid_to만 쓰면, 현재 버전에서 이 비교는 t < NULL이 되어 결과가 NULL이고, WHERE는 NULL을 거짓처럼 취급하므로 현재 버전이 결과에서 조용히 빠진다. 오류도 경고도 없다. 반면 열린 끝을 DATETIME이 표현할 수 있는 큰 값으로 두면 모든 버전에 같은 비교식 하나가 적용된다. MySQL 매뉴얼에 따르면 DATETIME의 지원 범위는 '1000-01-01 00:00:00'부터 '9999-12-31 23:59:59'까지이므로, 위 정의는 그 상한을 "아직 끝나지 않음"의 표시로 쓴다. 이 값은 실제 시각이 아니라 약속이므로, 애플리케이션 코드에 상수로 한 곳에만 정의해 두고 화면에 그대로 노출하지 않는다.

    이 선택은 인덱스와도 맞물린다. 종료 시각이 항상 값이면 valid_to로 시작하는 인덱스에서 t < valid_to는 B+Tree의 한 범위가 된다. NULL을 섞으면 "범위 하나 + NULL인 행들"이라는 두 갈래 조건이 되어 이를 위한 인덱스 접근도 그만큼 복잡해진다.

    결정 3: 현재 표시는 저장하지 않고 계산한다

    Kimball의 설명대로라면 현재 행 표시도 컬럼으로 두는데, 유효 기간이 있으면 is_current는 valid_to로부터 계산되는 값이다. 둘을 따로 저장하면 하나만 갱신하는 실수로 둘이 어긋날 수 있다. 위 정의는 current_product_id를 저장 생성 컬럼(stored generated column)으로 만들어, 열린 끝을 가진 버전이면 product_id, 아니면 NULL이 되게 했다. 사람이 직접 쓰는 컬럼이 아니므로 어긋날 수 없고, 여기에 유니크 키를 걸어 "상품마다 열린 버전은 최대 하나"를 지킨다. 앞 절의 함수 기반 인덱스와 같은 원리를 명시적인 컬럼으로 쓴 것이다.

    결정 4: 닫는 시각과 여는 시각은 한 번만 계산한다

    버전을 바꿀 때 옛 버전의 valid_to와 새 버전의 valid_from은 같은 값이어야 한다. 이것을 각 문장에서 NOW(6)로 채우면 안 된다. MySQL 매뉴얼에 따르면 NOW()는 그 문장이 실행을 시작한 시각을 돌려준다. 한 문장 안에서는 일정하지만, UPDATE 문과 INSERT 문은 서로 다른 문장이므로 실행 시작 시각이 다르다. 마이크로초 정밀도에서는 두 값이 거의 항상 다르고, 그 차이만큼 어느 버전에도 속하지 않는 틈이 생긴다. 시각을 한 번 구해 두 문장에 같은 값을 넣는다.

    START TRANSACTION;

SET @now = NOW(6);   -- 경계 시각을 한 번만 구한다

SELECT version_no FROM product_version
 WHERE product_id = 1 AND valid_to = '9999-12-31 23:59:59'
   FOR UPDATE;
-- 결과: version_no = 3

UPDATE product_version
   SET valid_to = @now
 WHERE product_id = 1 AND version_no = 3;

INSERT INTO product_version
  (product_id, version_no, sku, name, price, status, valid_from)
VALUES
  (1, 4, 'KB-01', '무선 키보드 프로', 8000, 'ON_SALE', @now);   -- valid_to는 기본값

COMMIT;

    애플리케이션에서 시각을 만들어 넘겨도 원리는 같다. 다만 애플리케이션 서버의 시계와 DB 서버의 시계가 다를 수 있으므로, 시각의 출처를 한쪽으로 정해 두는 것이 좋다. 한 테이블의 valid_from이 어떤 행은 애플리케이션 시각, 어떤 행은 DB 시각이면 순서가 뒤집힌 구간이 생길 수 있다.

    겹침과 틈은 제약으로 막을 수 없다

    정의에 넣은 CHECK (valid_from < valid_to)는 한 행 안의 규칙이다. MySQL은 8.0.16부터 CHECK 제약을 실제로 검사하지만, 매뉴얼에 나열된 규칙에 따르면 CHECK 식에는 서브쿼리를 쓸 수 없고 다른 테이블의 컬럼도 쓸 수 없다. 즉 "같은 상품의 다른 버전과 구간이 겹치면 안 된다"처럼 다른 행을 봐야 하는 규칙은 CHECK로 표현할 수 없다. 이 규칙은 앞의 절차(잠금 읽기 → 닫기 → 열기)로 지키고, 주기적으로 검증한다. MySQL 8.0의 윈도 함수 LEAD()로 각 버전의 다음 버전 시작 시각을 옆에 붙이면, 틈이나 겹침이 있는 곳이 바로 드러난다.

    SELECT product_id, version_no, valid_from, valid_to, next_from
  FROM (SELECT product_id, version_no, valid_from, valid_to,
               LEAD(valid_from) OVER (PARTITION BY product_id
                                      ORDER BY valid_from) AS next_from
          FROM product_version) v
 WHERE next_from IS NOT NULL
   AND valid_to <> next_from;   -- 작으면 틈, 크면 겹침

    시점 조회와 인덱스의 방향

    유효 기간이 생기면 "3월 15일 0시에 판매 중이던 상품 전체"가 조건 하나로 풀린다.

    SET @t = '2025-03-15 00:00:00';

SELECT product_id, name, price
  FROM product_version
 WHERE valid_from <= @t AND @t < valid_to
   AND status = 'ON_SALE';

    이 조건은 두 컬럼에 각각 부등호가 걸린 구간 조건이다. B+Tree 인덱스는 키 순서로 정렬되어 있으므로, 복합 인덱스에서 범위로 좁힐 수 있는 것은 사실상 첫 번째 범위 컬럼까지다. 인덱스 (valid_from, valid_to)를 쓰면 valid_from <= @t인 항목, 즉 @t 이전에 시작한 모든 버전을 훑으면서 valid_to를 걸러야 한다. @t가 최근일수록 이 범위는 테이블 거의 전체다. 반대로 (valid_to, valid_from)을 쓰면 @t < valid_to인 항목, 즉 @t 이후에 끝난 버전과 아직 열려 있는 버전을 훑는다. @t가 최근이면 이 범위는 현재 버전과 최근에 닫힌 버전 정도로 작다. 정리하면 "최근 시점"을 주로 묻는다면 valid_to가 앞선 인덱스가, "먼 과거"를 주로 묻는다면 valid_from이 앞선 인덱스가 훑는 양이 적다. 어떤 시점을 주로 묻는지가 인덱스 설계를 정한다. 상품 하나를 묻는 조회라면 product_id가 등호로 먼저 오므로 기본 키 (product_id, version_no)만으로도 그 상품의 버전 몇 개만 읽으면 된다.

    유효 기간은 현재 테이블 방식의 단점 중 하나인 "상품마다 최신 버전 고르기"를 없애 주지만, 앞 절의 다른 단점들, 즉 모든 조회에 현재 조건이 필요하고 과거 행이 현재 행의 페이지를 차지하는 문제는 그대로 남는다. 현재 조건이 is_current = 1에서 valid_to = '9999-12-31 23:59:59'로 바뀌었을 뿐이다. 이제 과거를 아예 다른 테이블로 옮겨 보자.

    전체 행 스냅샷 이력 테이블: 현재와 과거를 나눈다

    현재 테이블 방식의 문제는 대부분 과거 행이 현재 테이블 안에 있다는 데서 나왔다. 그렇다면 둘을 나누면 된다. 원래 테이블 product는 지금까지처럼 "상품 하나 = 행 하나"를 유지하고 UPDATE로 덮어쓴다. 그 대신 행이 바뀔 때마다 행 전체의 복사본을 별도의 이력 테이블에 한 행씩 추가한다. 이것이 전체 행 스냅샷(full-row snapshot) 이력 테이블이다.

    CREATE TABLE product (
  product_id  BIGINT        NOT NULL AUTO_INCREMENT,
  sku         VARCHAR(30)   NOT NULL,
  name        VARCHAR(100)  NOT NULL,
  price       DECIMAL(12,0) NOT NULL,
  status      VARCHAR(20)   NOT NULL,
  updated_at  DATETIME(6)   NOT NULL,
  updated_by  VARCHAR(50)   NOT NULL,
  PRIMARY KEY (product_id),
  UNIQUE KEY uk_product_sku (sku)
);

CREATE TABLE product_history (
  history_id  BIGINT        NOT NULL AUTO_INCREMENT,
  product_id  BIGINT        NOT NULL,        -- 외래 키를 걸지 않는다(뒤에서 설명)
  op          CHAR(1)       NOT NULL,        -- I: 등록, U: 수정, D: 삭제
  sku         VARCHAR(30)   NOT NULL,        -- 유니크 제약을 옮기지 않는다
  name        VARCHAR(100)  NOT NULL,
  price       DECIMAL(12,0) NOT NULL,
  status      VARCHAR(20)   NOT NULL,
  changed_at  DATETIME(6)   NOT NULL,
  changed_by  VARCHAR(50)   NOT NULL,
  PRIMARY KEY (history_id),
  KEY idx_ph_product_changed (product_id, changed_at)
);

    이제 현재 상태를 읽는 모든 쿼리는 이력이 없던 시절과 똑같다. product에는 상품마다 행이 하나뿐이므로 is_current 조건이 필요 없고, UNIQUE (sku)도 그대로 걸리며, 다른 테이블은 product(product_id)를 외래 키로 참조할 수 있다. 과거 행은 다른 테이블의 다른 B+Tree에 있으므로 현재 데이터의 페이지를 차지하지 않는다. 앞의 두 절에서 본 단점이 한꺼번에 사라진다. 이력이 필요한 쿼리만 product_history를 읽는다.

    무엇을 복사하는가: 변경 후 값인가, 변경 전 값인가

    스냅샷 이력 테이블을 만들 때 가장 먼저 정해야 하는 것은 각 이력 행이 바뀐 뒤의 상태를 담는지, 바뀌기 전의 상태를 담는지다. 두 방식은 같은 테이블 정의로도 표현되므로, 정하지 않고 시작하면 사람마다 다르게 쓰는 일이 생긴다.

    변경 후 상태(after image)를 담는 방식은 등록·수정·삭제가 일어날 때마다 그 결과 상태를 기록한다. 등록할 때도 한 행을 남기므로, 이력 테이블만 보면 상품이 태어난 순간부터 지금까지의 모든 상태가 시간순으로 들어 있다. 가장 마지막 이력 행은 현재 product 행과 내용이 같다. 같은 상태가 두 곳에 있는 셈이지만, 그 덕분에 특정 시점 조회가 이력 테이블 하나로 끝난다. "changed_at이 t 이하인 가장 마지막 행"이 곧 시점 t의 상태다.

    변경 전 상태(before image)를 담는 방식은 수정이나 삭제가 일어날 때 덮어써지기 직전의 상태를 기록한다. 이력 테이블에는 과거만 있고 현재는 product에만 있으므로 중복이 없다. 하지만 시간축이 두 테이블로 쪼개진다. 상품의 전체 타임라인을 보려면 이력 테이블과 현재 테이블을 UNION으로 이어야 하고, 각 이력 행의 시각이 무엇을 뜻하는지도 헷갈린다. 수정 시각에 기록한 "변경 전 상태"는 그 시각에 끝난 상태이므로, 그 상태가 시작된 시각은 바로 앞 이력 행이나 등록 시각에서 찾아야 한다.

    어느 쪽도 틀리지 않았지만, 시점 조회가 주된 용도라면 변경 후 상태가 다루기 쉽다. 이 회차의 예제는 변경 후 상태를 쓴다. 상품 1이 등록되고 가격과 이름이 한 번씩 바뀐 뒤의 두 테이블은 다음과 같다.

    history_idproduct_idopnamepricechanged_atchanged_by
    1011I무선 키보드100002025-01-01 09:00kim
    1871U무선 키보드90002025-03-01 09:00lee
    2401U무선 키보드 프로90002025-04-01 09:00kim

    product에는 name = '무선 키보드 프로', price = 9000, updated_at = 2025-04-01 09:00, updated_by = 'kim'인 행 하나가 있다. history_id가 101, 187, 240처럼 띄엄띄엄인 것은 이력 테이블이 모든 상품의 변경을 한곳에 쌓기 때문이다. 그 사이 번호는 다른 상품의 이력이다. 그래서 이력 테이블에서 한 상품의 이력을 읽을 때는 기본 키가 아니라 (product_id, changed_at) 보조 인덱스를 탄다.

    이력 행은 누가 넣는가

    이력 행을 넣는 쪽은 애플리케이션이거나 데이터베이스 트리거(trigger)다. 애플리케이션이 넣는다면 상품을 수정하는 서비스 메서드 안에서, 같은 트랜잭션으로 UPDATE와 INSERT를 함께 실행한다. 트리거로 넣는다면 product에 AFTER 트리거를 건다. MySQL 트리거는 FOR EACH ROW로 정의되어 영향받은 행마다 한 번씩 실행되고, UPDATE 트리거 안에서는 OLD.컬럼으로 변경 전 값을, NEW.컬럼으로 변경 후 값을 읽는다.

    CREATE TRIGGER trg_product_ai AFTER INSERT ON product
FOR EACH ROW
  INSERT INTO product_history
    (product_id, op, sku, name, price, status, changed_at, changed_by)
  VALUES
    (NEW.product_id, 'I', NEW.sku, NEW.name, NEW.price, NEW.status,
     NEW.updated_at, NEW.updated_by);

CREATE TRIGGER trg_product_au AFTER UPDATE ON product
FOR EACH ROW
  INSERT INTO product_history
    (product_id, op, sku, name, price, status, changed_at, changed_by)
  VALUES
    (NEW.product_id, 'U', NEW.sku, NEW.name, NEW.price, NEW.status,
     NEW.updated_at, NEW.updated_by);

    트리거 본문이 문장 하나이므로 BEGIN ... END와 mysql 클라이언트의 DELIMITER 변경이 필요 없다. 두 트리거 모두 changed_at과 changed_by를 NEW.updated_at, NEW.updated_by에서 가져온다는 점을 기억해 두자. 이유는 다음 절에서 본다.

    스냅샷 이력 테이블의 주의점

    스냅샷 이력 테이블은 구조가 단순한 만큼, 몇 가지 규칙을 어기면 조용히 이력이 빠지거나 틀린다. 하나씩 원인과 함께 보자.

    주의 1: 원래 변경과 같은 트랜잭션에서 기록한다

    상품 UPDATE는 커밋되었는데 이력 INSERT가 실패했다면 그 변경은 이력에서 영원히 사라진다. 반대로 이력은 남았는데 UPDATE가 롤백되었다면 일어나지 않은 변경이 이력에 남는다. 그래서 둘은 반드시 한 트랜잭션 안에 있어야 한다. 트리거를 쓰면 이것이 자동으로 보장된다. MySQL 매뉴얼에 따르면 AFTER 트리거는 BEFORE 트리거와 행 변경이 성공한 경우에만 실행되고, 트리거에서 오류가 나면 트리거를 일으킨 문장 전체가 실패하며, 트랜잭션을 지원하는 테이블에서는 그 문장의 변경이 모두 롤백된다. 애플리케이션에서 기록한다면 같은 커넥션, 같은 트랜잭션 경계 안에서 실행해야 한다. 스프링이라면 상품 수정과 이력 기록이 같은 @Transactional 메서드 호출 범위 안에 있어야 하고, 이력 기록을 커밋 이후의 이벤트 처리나 별도 스레드로 미루면 이 보장이 사라진다.

    애플리케이션의 UPDATE 한 번이 product 행 잠금, 행 변경, AFTER UPDATE 트리거의 이력 INSERT를 거쳐 한 번의 COMMIT으로 함께 확정되는 순서를 보여 준다. 흰 배경의 시퀀스 다이어그램. 왼쪽부터 세로 생명선 네 개: "애플리케이션", "product", "트리거", "product_history". 위에서 아래로 화살표: ① 애플리케이션 → product "UPDATE ... WHERE product_id = 1", ② product 생명선 옆 자물쇠 아이콘과 라벨 "행 배타 잠금", ③ product → 트리거 "AFTER UPDATE (OLD, NEW)", ④ 트리거 → product_history "INSERT 변경 후 상태", ⑤ 애플리케이션 → product "COMMIT". ②부터 ⑤까지를 감싸는 연한 파란 상자에 "한 트랜잭션" 라벨. 오른쪽 아래 작은 빨간 상자에 "④ 실패 → 문장 전체 롤백". 선은 단정하게, 글자는 크게. 트리거의 INSERT는 원래 문장의 일부로 실행되므로, 둘 중 하나만 반영되는 일은 없다.

    주의 2: 트리거는 "누가"를 모른다

    트리거 안에서 CURRENT_USER()를 부르면 MySQL에 접속한 계정이 나온다. 그런데 웹 애플리케이션은 커넥션 풀을 통해 모든 요청을 하나의 DB 계정으로 처리하므로, 이 값은 모든 이력 행에서 똑같다. 실제로 상품을 고친 관리자 "lee"는 애플리케이션만 안다. 그래서 위 트리거는 앞 회차의 감사 컬럼 updated_by를 애플리케이션이 채워 주고, 트리거는 그 값을 NEW.updated_by로 옮겨 적기만 한다. 감사 컬럼과 이력 테이블은 이렇게 짝을 이룬다. 같은 이유로 변경 사유도 현재 행에 컬럼으로 있어야 트리거가 이력에 옮길 수 있다.

    삭제는 더 까다롭다. DELETE 트리거에는 NEW가 없고 OLD만 있으므로, 삭제한 사람을 OLD.updated_by에서 가져오면 "마지막으로 수정한 사람"이 기록된다. 삭제자를 정확히 남기려면 애플리케이션이 삭제 직전에 updated_by를 갱신하거나, 삭제 이력을 애플리케이션에서 직접 쓰거나, 행을 지우는 대신 상태를 바꾸는 방식을 택해야 한다. 마지막 선택지는 다음 회차의 Soft Delete에서 이력 테이블과 함께 다시 다룬다.

    주의 3: 트리거가 일어나지 않는 변경이 있다

    MySQL 매뉴얼의 저장 프로그램 제약 사항에는 "트리거는 외래 키 동작으로는 활성화되지 않는다"는 문장이 있다. 주문 테이블이 회원을 ON DELETE CASCADE로 참조한다면, 회원을 지울 때 연쇄로 지워지는 주문 행에 대해서는 주문 테이블의 DELETE 트리거가 실행되지 않는다. 주문 테이블에 트리거로 이력을 남기고 있었다면, 이 주문들의 삭제는 이력에 남지 않는다. MySQL 8.0.46과 8.4.13에서 확인해 보면, 회원 한 명을 지워 그 회원의 주문 두 행이 연쇄로 지워졌지만 주문의 AFTER DELETE 트리거가 쓰는 이력 테이블에는 한 행도 남지 않았고, 주문을 DELETE 문으로 직접 지웠을 때만 이력이 남았다. ON UPDATE CASCADE로 바뀌는 값도 마찬가지다. 매뉴얼은 또 트리거가 SQL 문장을 통한 변경에만 반응하며 SQL을 전달하지 않는 API를 통한 변경(매뉴얼의 예는 NDB API)에는 반응하지 않는다고 적고 있다. 트리거 방식으로 이력을 남기는 테이블이라면, 그 테이블에 대한 외래 키 연쇄 동작이 있는지부터 확인해야 한다.

    트리거에는 반대 방향의 제약도 있다. 매뉴얼에 따르면 저장 함수나 트리거는 그것을 일으킨 문장이 이미 사용 중인(읽거나 쓰는) 테이블을 수정할 수 없다. 앞에서 본 product_version 방식에서 "새 버전을 INSERT하면 트리거가 같은 테이블의 이전 버전을 닫게 하자"는 설계가 불가능한 이유다. MySQL 8.0.46과 8.4.13에서 product_version에 그런 AFTER INSERT 트리거를 만들어 보면 CREATE TRIGGER 자체는 성공하지만, INSERT를 실행하는 순간 ERROR 1442 (HY000): Can't update table 'product_version' in stored function/trigger because it is already used by statement which invoked this stored function/trigger.로 실패한다. 스냅샷 이력 테이블은 트리거가 다른 테이블에 쓰므로 이 제약에 걸리지 않는다.

    주의 4: 제약을 옮겨 오지 않는다

    이력 테이블을 만들 때 원래 테이블의 DDL을 복사해 이름만 바꾸는 경우가 많다. 그러면 원래 테이블의 제약이 함께 따라온다. UNIQUE (sku)가 이력 테이블에 남아 있으면 같은 상품의 두 번째 이력부터 INSERT가 실패하고, 트리거라면 그 실패가 원래 UPDATE까지 실패시킨다. 원래 테이블에서 product_id가 기본 키였다고 이력 테이블에서도 기본 키로 두면 같은 문제가 난다. 이력 테이블의 기본 키는 이력 행 자체의 식별자여야 한다.

    외래 키도 신중해야 한다. product_history.product_id에 product를 가리키는 외래 키를 걸면, 상품을 삭제하려 할 때 이력 행이 그 상품을 참조하고 있어서 삭제가 거부된다. 이를 피하려고 ON DELETE CASCADE를 붙이면 상품을 지우는 순간 그 상품의 이력이 함께 지워진다. 삭제된 대상의 이력이야말로 나중에 가장 많이 찾게 되는 이력인데, 그것이 사라지는 것이다. 그래서 이력 테이블은 원래 테이블을 외래 키로 참조하지 않는 것이 일반적이다. 이력은 "그때 그 값이 있었다"는 기록이므로, 그 대상이 지금 존재하는지와 무관하게 남아야 한다.

    주의 5: 원래 테이블의 스키마 변경을 따라간다

    product에 brand 컬럼을 추가했는데 product_history와 트리거를 고치지 않으면, 그날부터 브랜드 변경은 이력에 남지 않는다. 오류가 나지 않으므로 아무도 모른다. 트리거나 이력 INSERT를 INSERT INTO product_history SELECT * FROM ...처럼 컬럼 목록 없이 쓰면 더 위험하다. 두 테이블의 컬럼 수가 달라지면 오류가 나고, 컬럼 수가 같은데 순서가 다르면 오류 없이 엉뚱한 컬럼에 값이 들어간다. 이력 INSERT는 항상 컬럼 이름을 나열하고, 원래 테이블의 스키마 변경 절차에 "이력 테이블과 이력 기록 코드도 함께 바꾼다"를 넣어 두어야 한다.

    주의 6: 같은 상품의 이력 순서는 잠금이 정한다

    두 관리자가 같은 상품을 거의 동시에 고치면 이력 행의 순서는 어떻게 될까. UPDATE는 기본 키로 행 하나를 찾을 때 그 레코드에 배타 잠금을 건다. 두 번째 UPDATE는 첫 번째 트랜잭션이 커밋할 때까지 기다리고, 그 뒤에 자기 변경과 트리거의 INSERT를 실행한다. 그러므로 같은 상품의 이력 행은 커밋 순서대로 들어가고, history_id도 그 순서로 커진다. 하지만 서로 다른 상품 사이에서는 그렇지 않다. AUTO_INCREMENT 값은 INSERT할 때 발급되고 커밋 순서와는 무관하므로, 전체 이력 테이블에서 history_id 순서가 곧 커밋 순서라고 가정해서는 안 된다. 또 changed_at이 같은 두 이력이 생길 수 있으므로, 한 상품의 이력을 정렬할 때는 ORDER BY changed_at, history_id처럼 동률을 깨는 컬럼을 덧붙인다.

    스냅샷 이력 테이블과 유효 기간

    변경 후 상태를 담는 스냅샷 이력 테이블에서 특정 시점의 상태를 찾는 방법은 세 가지다. 유효 기간 컬럼을 두지 않고 정렬로 찾는 방법, 유효 기간 컬럼을 두고 기록할 때 채우는 방법, 조회할 때 계산하는 방법이다.

    방법 1: 유효 기간 없이, 한 상품의 최근 이력 하나

    SELECT name, price
  FROM product_history
 WHERE product_id = 1
   AND changed_at <= '2025-03-15 00:00:00'
 ORDER BY changed_at DESC, history_id DESC
 LIMIT 1;
-- 결과: name = '무선 키보드', price = 9000 (history_id 187)

    이 쿼리는 보조 인덱스 idx_ph_product_changed (product_id, changed_at)로 처리된다. InnoDB는 보조 인덱스의 각 항목 끝에 기본 키 값을 붙여 저장하고, MySQL 매뉴얼의 인덱스 확장(index extensions) 설명에 따르면 옵티마이저는 이 덧붙은 기본 키 컬럼까지 고려해 인덱스 사용 방법을 정한다(use_index_extensions는 기본으로 켜져 있다). 그래서 이 인덱스는 사실상 (product_id, changed_at, history_id) 순서로 정렬되어 있다. 옵티마이저는 product_id = 1 구간 안에서 changed_at이 3월 15일 이하인 곳의 끝을 찾은 뒤 거꾸로 한 항목만 읽고 멈출 수 있다. 별도의 정렬 작업이 필요 없다. MySQL 8.0.46과 8.4.13에서 이 쿼리의 EXPLAIN을 보면 type은 range, key는 idx_ph_product_changed이고 Extra에는 Using index condition; Backward index scan만 나오며 Using filesort는 없다. 상품 하나의 시점 조회라면 유효 기간 컬럼 없이도 충분히 빠르다.

    문제는 여러 상품을 한꺼번에 볼 때다. "3월 15일 0시에 판매 중이던 상품 전체"를 구하려면 상품마다 그 시점 이전의 마지막 이력을 골라야 한다. MySQL 8.0의 윈도 함수로 쓰면 다음과 같다.

    SELECT product_id, name, price
  FROM (SELECT product_id, op, name, price, status,
               ROW_NUMBER() OVER (PARTITION BY product_id
                                  ORDER BY changed_at DESC, history_id DESC) AS rn
          FROM product_history
         WHERE changed_at <= '2025-03-15 00:00:00') h
 WHERE rn = 1
   AND op <> 'D'              -- 그 시점에 이미 삭제된 상품 제외
   AND status = 'ON_SALE';

    이 쿼리는 3월 15일 이전의 이력 행을 전부 읽어 상품별로 줄 세운 다음 첫 행만 남긴다. 이력이 수천만 행이면 그만큼 읽고 정렬한다. 시점 조회가 드물고 상품 단위로만 일어난다면 이것으로 충분하지만, 정산이나 리포트처럼 "그 시점의 전체 상태"를 자주 묻는다면 비용이 크다.

    방법 2: 기록할 때 유효 기간을 채운다

    이력 테이블에 valid_from과 valid_to를 두고, 새 이력을 넣을 때 그 상품의 직전 이력의 valid_to를 닫는다. 그러면 전체 상태 조회는 앞에서 본 구간 조건 하나가 된다. 트리거로 구현하면 본문이 두 문장이 되므로 BEGIN ... END와 DELIMITER가 필요하다.

    -- product_history에 changed_at 대신 valid_from, valid_to 컬럼이 있다고 하자
-- valid_from DATETIME(6) NOT NULL
-- valid_to   DATETIME(6) NOT NULL DEFAULT '9999-12-31 23:59:59'
-- (changed_at을 NOT NULL로 남겨 두면 아래 INSERT가 ERROR 1364 (HY000): Field 'changed_at'
--  doesn't have a default value로 실패하고 상품 UPDATE까지 롤백된다. MySQL 8.0.46·8.4.13에서 확인)

DELIMITER //
CREATE TRIGGER trg_product_au AFTER UPDATE ON product
FOR EACH ROW
BEGIN
  UPDATE product_history
     SET valid_to = NEW.updated_at
   WHERE product_id = NEW.product_id
     AND valid_to = '9999-12-31 23:59:59';

  INSERT INTO product_history
    (product_id, op, sku, name, price, status, valid_from, changed_by)
  VALUES
    (NEW.product_id, 'U', NEW.sku, NEW.name, NEW.price, NEW.status,
     NEW.updated_at, NEW.updated_by);
END//
DELIMITER ;

-- 시점 조회
SELECT product_id, name, price
  FROM product_history
 WHERE valid_from <= '2025-03-15 00:00:00'
   AND '2025-03-15 00:00:00' < valid_to
   AND op <> 'D' AND status = 'ON_SALE';

    트리거 안의 UPDATE가 앞 절의 "같은 테이블 수정 금지" 제약에 걸리지 않는 이유는 트리거를 일으킨 문장이 product를 갱신하는 문장이고, 트리거가 고치는 테이블은 product_history이기 때문이다. 닫는 시각과 여는 시각에는 모두 NEW.updated_at 하나를 쓰므로, 앞에서 본 "시각을 한 번만 계산한다"는 규칙도 지켜진다. 이 UPDATE가 열린 이력을 빠르게 찾으려면 (product_id, valid_to) 인덱스가 있어야 한다. 그렇지 않으면 상품의 이력 전체를 훑는다.

    대가는 쓰기 비용이다. 상품을 한 번 고칠 때마다 이력 테이블에 INSERT 하나와 UPDATE 하나가 생기고, UPDATE는 이미 기록된 이력 행을 다시 고친다. 이력 테이블이 "추가만 하는(append-only)" 테이블이 아니게 되는 것이다. 이 선택은 JPA 생태계에도 그대로 있다. Hibernate의 감사 모듈 Envers는 엔티티마다 기본 접미사 _AUD가 붙은 감사 테이블에 리비전별 스냅샷을 쌓는데, 기본 감사 전략(DefaultAuditStrategy)은 행을 추가하기만 하고, ValidityAuditStrategy를 고르면 종료 리비전 컬럼(기본 이름 REVEND)을 함께 관리한다. Hibernate 6.4의 ValidityAuditStrategy Javadoc은 새 행에는 시작 리비전만 기록하고 동시에 직전 감사 행의 종료 리비전을 현재 리비전으로 설정하며, 조회할 때는 서브쿼리 대신 시작·종료 리비전 사이를 묻는 조건을 쓴다고 설명한다. Hibernate 사용자 가이드(5.0)는 이 전략이 추가 UPDATE 때문에 기록은 조금 느려지지만 조회는 서브쿼리를 피해 빨라진다고 정리한다. 우리가 손으로 만든 방법 1과 방법 2의 차이가 정확히 이것이다.

    방법 3: 조회할 때 유효 기간을 계산한다

    이력은 추가만 하고, 유효 종료 시각은 조회할 때 LEAD()로 계산할 수도 있다. 각 이력 행의 valid_to는 "같은 상품의 다음 이력의 changed_at"이기 때문이다.

    SELECT product_id, name, price, changed_at AS valid_from,
       COALESCE(LEAD(changed_at) OVER (PARTITION BY product_id
                                       ORDER BY changed_at, history_id),
                '9999-12-31 23:59:59') AS valid_to
  FROM product_history;

    이 쿼리를 뷰로 만들어 두면 시점 조회 쿼리는 방법 2와 같은 모양이 된다. 다만 뷰 바깥의 시점 조건은 윈도 함수가 계산된 뒤에야 적용될 수 있으므로, 결국 이력 전체에 대해 윈도 함수를 계산하는 비용은 방법 1과 비슷하다. 기록은 단순하게 유지하고 조회 비용을 감수하는 선택이다. 세 방법 중 무엇을 고를지는 결국 "쓰기와 시점 조회 중 어느 쪽이 더 잦고 더 중요한가"로 정해진다.

    스냅샷 이력 테이블의 한계

    스냅샷 이력 테이블은 현재 테이블을 깨끗하게 지키면서 시점 조회에 강하다. 그 대신 다음 네 가지 한계가 있다.

    첫째, 바뀌지 않은 값까지 복사한다. 가격 하나를 바꿔도 이름, 상품 코드, 상태, 그리고 상품 설명처럼 긴 컬럼까지 모두 한 행으로 복사된다. 이력 테이블의 크기는 대략 "행 크기 × 변경 횟수"로 늘어난다. 예를 들어 이력 행 하나가 2KB이고 하루 10만 건의 변경이 일어난다고 가정하면, 하루에 2KB × 100,000 = 200,000KB, 약 200MB가 쌓이고 1년이면 약 73GB가 된다. 이 계산에는 인덱스와 페이지의 빈 공간이 빠져 있으므로 실제로는 더 크다. 수치는 가정이지만 "자주 바뀌는 작은 값 하나 때문에 큰 행 전체가 반복 복사된다"는 구조는 가정이 아니다. 상품 설명 같은 큰 값이 거의 바뀌지 않고 가격과 재고 상태만 자주 바뀐다면, 이력이 필요한 컬럼만 담는 좁은 이력 테이블을 따로 두는 편이 낫다.

    둘째, 무엇이 바뀌었는지가 행에 적혀 있지 않다. 스냅샷은 상태를 기록할 뿐 변화를 기록하지 않는다. "누가 언제 가격을 바꿨나"를 알려면 같은 상품의 연속된 두 이력을 비교해야 한다. 윈도 함수 LAG()로 직전 이력의 값을 옆에 붙이면 된다.

    SELECT product_id, changed_at, changed_by, prev_price, price
  FROM (SELECT product_id, changed_at, changed_by, price,
               LAG(price) OVER (PARTITION BY product_id
                                ORDER BY changed_at, history_id) AS prev_price
          FROM product_history
         WHERE product_id = 1) h
 WHERE NOT (prev_price <=> price);
-- 결과(MySQL 8.4.13에서 실행): (등록) prev_price NULL → 10000, 03-01 lee 10000 → 9000
--       04-01의 이름 변경 행은 price가 같으므로 나오지 않는다

    조건에 prev_price <> price 대신 NULL 안전 비교 연산자 <=>를 쓴 이유가 있다. 첫 이력에서 prev_price는 NULL인데, NULL <> 10000의 결과는 참이 아니라 NULL이어서 등록 시점의 가격이 결과에서 빠진다. <=>는 두 피연산자가 모두 NULL이면 1, 한쪽만 NULL이면 0을 돌려주므로 NULL에서 값으로 바뀐 경우도 "바뀌었다"로 잡는다. 컬럼 하나의 변화를 보는 데는 이 정도로 되지만, "이 상품의 모든 변경 내역을 컬럼별로 보여 달라"는 화면을 만들려면 컬럼마다 이런 비교를 해야 한다.

    셋째, 스키마가 변하면 과거 행의 의미가 흐려진다. 원래 테이블에 컬럼이 추가되면 이력 테이블에도 추가해야 하고, 추가 이전의 이력 행에서 그 컬럼은 NULL이나 기본값이다. 이 NULL은 "그때 값이 없었다"가 아니라 "그때는 기록하지 않았다"는 뜻인데, 둘을 구별할 방법이 행 안에 없다. 컬럼의 의미나 단위가 바뀌면(예를 들어 가격이 부가세 포함에서 별도로 바뀌면) 같은 컬럼 안에 서로 다른 의미의 값이 섞인다. 원래 테이블에서 컬럼을 지우면 이력 테이블에서는 남겨 둘지 지울지를 정해야 한다.

    넷째, 테이블마다 하나씩 생긴다. 이력이 필요한 테이블이 30개면 이력 테이블도 30개, 트리거나 기록 코드도 30벌이다. 각각의 스키마 동기화, 보관 기간, 인덱스를 따로 관리해야 한다. 이 넷째 한계와 둘째 한계를 정면으로 겨냥한 것이 다음 두 방식이다.

    컬럼 단위 변경 로그 테이블

    스냅샷이 "상태"를 기록한다면, 컬럼 단위 변경 로그는 "변화"를 기록한다. 행이 바뀔 때 실제로 값이 바뀐 컬럼마다 한 행씩, 무엇에서 무엇으로 바뀌었는지를 남긴다.

    CREATE TABLE product_change_log (
  log_id       BIGINT        NOT NULL AUTO_INCREMENT,
  product_id   BIGINT        NOT NULL,
  column_name  VARCHAR(64)   NOT NULL,
  old_value    VARCHAR(1000) NULL,
  new_value    VARCHAR(1000) NULL,
  changed_at   DATETIME(6)   NOT NULL,
  changed_by   VARCHAR(50)   NOT NULL,
  PRIMARY KEY (log_id),
  KEY idx_pcl_product (product_id, changed_at)
);

DELIMITER //
CREATE TRIGGER trg_product_au_log AFTER UPDATE ON product
FOR EACH ROW
BEGIN
  IF NOT (OLD.price <=> NEW.price) THEN
    INSERT INTO product_change_log
      (product_id, column_name, old_value, new_value, changed_at, changed_by)
    VALUES
      (NEW.product_id, 'price', OLD.price, NEW.price, NEW.updated_at, NEW.updated_by);
  END IF;
  IF NOT (OLD.name <=> NEW.name) THEN
    INSERT INTO product_change_log
      (product_id, column_name, old_value, new_value, changed_at, changed_by)
    VALUES
      (NEW.product_id, 'name', OLD.name, NEW.name, NEW.updated_at, NEW.updated_by);
  END IF;
  -- sku, status도 같은 모양으로 ...
END//
DELIMITER ;

    앞의 스냅샷 트리거 trg_product_au와 이 트리거가 함께 있어도 된다. MySQL 매뉴얼에 따르면 한 테이블에 이벤트와 시점이 같은 트리거를 여러 개 둘 수 있고, 기본적으로 만들어진 순서대로 실행되며 FOLLOWS, PRECEDES로 순서를 바꿀 수 있다. 상품 1의 가격을 10000에서 9000으로 바꾼 UPDATE는 로그에 ('price', '10000', '9000') 한 행을 남기고, 이름만 바꾼 UPDATE는 ('name', '무선 키보드', '무선 키보드 프로') 한 행을 남긴다. 가격과 이름을 한 문장에서 함께 바꾸면 두 행이 남는다. 값이 같은 UPDATE는 아무 행도 남기지 않는다. 여기서도 비교에 <=>를 쓴 것이 중요하다. OLD.price <> NEW.price로 쓰면 한쪽이 NULL일 때 결과가 NULL이고, IF는 NULL을 참으로 보지 않으므로 NULL과 값 사이의 변경을 놓친다. 이 예제의 컬럼은 모두 NOT NULL이지만, 할인율처럼 NULL을 허용하는 컬럼이 추가되는 순간 이 차이가 드러난다.

    강점: 변경 내역 화면이 SELECT 한 번이다

    "이 상품의 가격을 누가 언제 무엇에서 무엇으로 바꿨나"는 WHERE product_id = 1 AND column_name = 'price' ORDER BY changed_at으로 끝난다. 관리자 화면의 "변경 이력" 탭이 요구하는 것이 정확히 이 모양이다. 저장량도 바뀐 컬럼만큼이다. 가격 하나를 바꾸면 긴 상품 설명은 복사되지 않는다.

    약점 1: 타입이 사라진다

    가격도, 이름도, 날짜도 모두 VARCHAR 한 컬럼에 문자열로 들어간다. DECIMAL 9000은 문자열 '9000'이 된다. 이 값으로 비교하면 숫자가 아니라 문자열 순서로 비교된다. "가격이 10000원을 넘게 오른 변경"을 WHERE column_name = 'price' AND new_value > '10000'으로 찾으면, '9500'은 첫 글자 '9'가 '1'보다 크므로 '10000'보다 큰 값으로 판정되어 결과에 들어온다. 올바르게 하려면 CAST(new_value AS DECIMAL(12,0))처럼 컬럼마다 원래 타입으로 되돌려야 하는데, 그러면 인덱스를 쓸 수 없고 어떤 컬럼이 어떤 타입이었는지를 쿼리 작성자가 알고 있어야 한다. 날짜나 소수의 문자열 표현이 기록 경로마다 다르면(예를 들어 애플리케이션이 쓴 '9000.00'과 트리거가 쓴 '9000') 같은 값이 다른 문자열이 된다. 데이터베이스가 타입으로 지켜 주던 규칙을 이 테이블에서는 아무도 지키지 않는다.

    약점 2: 상태를 다시 조립해야 한다

    "3월 15일 0시의 상품 1 전체 상태"를 구하려면 컬럼마다 그 시점 이전의 마지막 new_value를 찾아야 한다. 그런데 한 번도 바뀌지 않은 컬럼은 로그에 없다. UPDATE만 기록했다면 등록 당시 값이 로그에 없기 때문이다. 이를 해결하는 깔끔한 방법은 현재 행에서 거꾸로 되감는 것이다. 시점 t의 각 컬럼 값은, t 이후에 일어난 그 컬럼의 첫 번째 변경의 old_value다. t 이후로 바뀐 적이 없으면 현재 값과 같다.

    -- 시점 t 이후 각 컬럼의 첫 변경의 old_value = 시점 t의 값
SELECT column_name, old_value AS value_at_t
  FROM (SELECT column_name, old_value,
               ROW_NUMBER() OVER (PARTITION BY column_name
                                  ORDER BY changed_at, log_id) AS rn
          FROM product_change_log
         WHERE product_id = 1
           AND changed_at > '2025-03-15 00:00:00') x
 WHERE rn = 1;
-- 결과에 없는 컬럼은 product의 현재 값을 그대로 쓴다
-- 예제 데이터(MySQL 8.4.13에서 실행): ('name', '무선 키보드') 한 행 → 3월 15일의 이름은 '무선 키보드',
--              price는 3월 15일 이후 변경이 없으므로 현재 값 9000

    결과는 컬럼별로 세로로 나오므로, 화면이나 애플리케이션에서 가로 한 행으로 다시 조립해야 한다. 상품 하나가 아니라 상품 전체의 시점 상태를 구하는 일은 이 방식에서 가장 비싸다. 컬럼 단위 로그는 시점 조회에 약하고 변경 내역 조회에 강하다. 스냅샷과 정확히 반대다.

    약점 3: 한 번의 변경이 여러 행으로 흩어진다

    가격과 상태를 함께 바꾼 하나의 변경은 로그에서 두 행이 된다. 이 둘이 같은 변경이었다는 것은 changed_at과 changed_by가 같다는 것으로 추측할 수밖에 없다. 같은 관리자가 같은 마이크로초에 두 번 변경했을 리는 거의 없지만, "거의"는 설계의 근거가 아니다. 변경 단위를 명확히 하려면 변경 한 번을 나타내는 상위 테이블을 둔다.

    CREATE TABLE change_set (
  change_id   BIGINT       NOT NULL AUTO_INCREMENT,
  changed_at  DATETIME(6)  NOT NULL,
  changed_by  VARCHAR(50)  NOT NULL,
  reason      VARCHAR(200) NULL,
  PRIMARY KEY (change_id)
);
-- product_change_log에는 changed_at, changed_by 대신 change_id를 둔다

    애플리케이션이 변경을 시작할 때 change_set에 한 행을 넣고, 그 change_id로 컬럼 로그들을 기록한다. 변경 사유도 여기에 한 번만 적으면 된다. Envers가 엔티티의 감사 행들과 별도로 리비전 정보 테이블(기본 이름 REVINFO)을 두고 감사 행들이 리비전 번호를 공유하게 하는 것도 같은 구조다. 이렇게 하면 트리거는 change_id를 알 방법이 마땅치 않으므로, 기록 주체는 대개 애플리케이션이 된다.

    컬럼 단위 로그의 구조를 다시 보면 (대상 식별자, 속성 이름, 값)이다. 이것은 8회차에서 다룰 EAV(Entity-Attribute-Value)와 같은 모양이고, 타입이 사라지고 다시 조립해야 한다는 약점도 EAV의 약점과 같다. 다만 EAV가 현재 데이터를 이 모양으로 저장하는 것과 달리, 변경 로그는 주로 사람이 읽는 기록이고 다시 조립할 일이 드물다는 점에서 약점의 무게가 훨씬 가볍다.

    공통 이력 테이블: 모든 테이블의 이력을 한곳에

    스냅샷이든 컬럼 로그든 테이블마다 만들면 이력 테이블과 기록 코드가 테이블 수만큼 늘어난다. 이를 하나로 합친 것이 공통 이력 테이블(감사 로그 테이블)이다. 어느 테이블의 어느 행인지를 컬럼으로 적고, 변경 내용은 테이블마다 모양이 다르므로 형식에 얽매이지 않는 그릇에 담는다. MySQL에서는 JSON 자료형이 그 그릇으로 쓰인다.

    CREATE TABLE audit_log (
  audit_id     BIGINT       NOT NULL AUTO_INCREMENT,
  table_name   VARCHAR(64)  NOT NULL,
  row_key      VARCHAR(100) NOT NULL,   -- 대상 행의 기본 키를 문자열로
  op           CHAR(1)      NOT NULL,   -- I, U, D
  before_data  JSON         NULL,       -- 변경 전 (등록이면 NULL)
  after_data   JSON         NULL,       -- 변경 후 (삭제면 NULL)
  changed_at   DATETIME(6)  NOT NULL,
  changed_by   VARCHAR(50)  NOT NULL,
  PRIMARY KEY (audit_id),
  KEY idx_audit_target (table_name, row_key, changed_at)
);

CREATE TRIGGER trg_product_au_audit AFTER UPDATE ON product
FOR EACH ROW
  INSERT INTO audit_log
    (table_name, row_key, op, before_data, after_data, changed_at, changed_by)
  VALUES
    ('product', CAST(NEW.product_id AS CHAR), 'U',
     JSON_OBJECT('sku', OLD.sku, 'name', OLD.name, 'price', OLD.price, 'status', OLD.status),
     JSON_OBJECT('sku', NEW.sku, 'name', NEW.name, 'price', NEW.price, 'status', NEW.status),
     NEW.updated_at, NEW.updated_by);

    변경 전후를 모두 담으면 이 테이블 하나로 스냅샷(어느 쪽 JSON이든 그 시점의 상태)과 변경 내역(두 JSON의 차이)을 모두 복원할 수 있다. 변경된 키만 담도록 줄일 수도 있다. 새 테이블에 이력이 필요해지면 이 테이블을 고칠 필요 없이 기록 코드만 추가하면 된다. 관리자 화면의 "변경 이력" 기능도 하나만 만들면 모든 테이블에 쓸 수 있다. 이것이 공통 이력 테이블의 매력이다.

    대가 1: 무엇을 가리키는지 데이터베이스가 모른다

    (table_name, row_key)는 "어느 테이블의 어느 행"을 뜻하지만 외래 키로 표현할 수 없다. 외래 키는 한 테이블만 가리킬 수 있는데, 이 컬럼 쌍은 행마다 다른 테이블을 가리키기 때문이다. 이런 구조를 다형성 연관(polymorphic association)이라고 부른다. 앞에서 본 것처럼 이력 테이블은 원래 외래 키를 걸지 않는 편이 맞으므로 이것 자체는 큰 손해가 아니다. 하지만 table_name에 오타가 들어가거나 테이블 이름이 바뀌면 그 이력은 아무것과도 연결되지 않는다. 기본 키가 여러 컬럼인 테이블은 row_key에 값을 이어 붙여야 하므로, 이어 붙이는 규칙(순서, 구분자)을 모든 기록 경로가 똑같이 지켜야 한다. 기본 키가 숫자인 테이블도 문자열로 바뀌어 저장되므로 row_key = 1처럼 숫자로 비교하면 문자열을 숫자로 변환하는 비교가 되어 인덱스를 제대로 쓰지 못한다. MySQL 8.0.46과 8.4.13에서 WHERE table_name = 'product' AND row_key = 1의 EXPLAIN을 보면 idx_audit_target의 앞 컬럼 table_name만 쓰고(key_len 258, ref는 const 하나) Warning 1739: Cannot use range access on index 'idx_audit_target' due to type or collation conversion on field 'row_key'가 나온다. row_key = '1'로 바꾸면 두 컬럼을 모두 쓴다(key_len 660, ref는 const,const). 항상 row_key = '1'로 비교해야 한다.

    대가 2: 내용으로 찾기 어렵다

    "가격이 바뀐 이력만", "상태가 SOLD_OUT으로 바뀐 이력만" 찾으려면 JSON 안의 값을 꺼내 비교해야 한다. 이 조건에는 일반 인덱스가 걸리지 않으므로 대상 범위를 (table_name, row_key, changed_at)으로 먼저 좁히지 못하면 테이블 전체를 훑게 된다. JSON 값에 인덱스를 거는 방법(생성 컬럼, 함수 기반 인덱스, 다중 값 인덱스)과 그 비용은 9회차에서 자세히 다룬다. 여기서 기억할 것은 공통 이력 테이블이 "특정 대상의 이력을 시간순으로 보기"에는 잘 맞지만 "특정 내용의 변경을 전체에서 찾기"에는 맞지 않는다는 점이다.

    대가 3: 모든 쓰기가 한 테이블로 모인다

    이력이 필요한 테이블이 30개면, 그 30개 테이블에 대한 모든 변경이 이 테이블 하나에 INSERT된다. 이 테이블의 크기와 쓰기량은 30개 테이블 변경량의 합이다. 테이블이 커지면 오래된 이력을 지우는 일 자체가 부담이 된다. 수억 행 가운데 1년이 지난 행을 DELETE로 지우면 그 행들 하나하나에 대해 언두 로그와 리두 로그가 만들어진다. 이 문제를 피하려고 changed_at 기준으로 월별 범위 파티션을 나누고 오래된 파티션을 통째로 버리는 방법을 쓰기도 한다. 이때 MySQL은 파티션 식에 쓰인 모든 컬럼이 기본 키를 포함한 모든 유니크 키에 들어 있어야 한다는 규칙이 있으므로, 기본 키를 (audit_id, changed_at)처럼 넓혀야 한다.

    보관 정책이 하나로 묶이는 것도 문제다. 주문 이력은 오래 보관해야 하고, 회원의 연락처 변경 이력은 회원이 탈퇴하면 함께 정리해야 할 수 있다. 개인 정보가 담긴 컬럼을 JSON으로 통째로 복사해 두면, 원래 테이블에서는 지웠는데 이력 테이블에는 남아 있는 상황이 생긴다. 테이블별 이력 테이블이라면 테이블마다 다른 정책을 쉽게 적용할 수 있지만, 공통 이력 테이블에서는 table_name별로 다른 정리 작업을 따로 만들어야 한다. 접근 권한도 마찬가지다. 이 테이블을 읽을 수 있는 사람은 모든 테이블의 변경 내용을 읽을 수 있다.

    어디에서 기록할 것인가, 그리고 무엇을 고를 것인가

    지금까지는 이력의 모양을 봤다. 마지막으로 이력을 어디에서 기록하는지를 정리하자. 같은 모양이라도 기록 위치에 따라 보장이 달라진다.

    기록 위치보장빈틈
    애플리케이션 코드같은 트랜잭션에서 기록 가능. 실제 사용자, 변경 사유, 업무 맥락을 안다. Envers처럼 ORM이 대신 해 주기도 한다.그 코드를 거치지 않는 변경(배치 SQL, 운영자의 직접 수정, 다른 애플리케이션)은 기록되지 않는다.
    DB 트리거SQL 문장을 통한 모든 변경을 같은 문장 안에서 잡는다. 어느 애플리케이션이 고쳤든 빠지지 않는다.실제 사용자를 모른다(감사 컬럼에 의존). 외래 키 연쇄 동작으로 일어난 변경은 잡지 못한다. 로직이 스키마 안에 숨어 있어 코드 리뷰에서 보이지 않는다.
    바이너리 로그 읽기(CDC)원래 트랜잭션에 쓰기 비용을 더하지 않는다. MySQL 8.0의 기본 설정(binlog_format=ROW, binlog_row_image=full)에서 수정 이벤트에는 모든 컬럼의 변경 전·후 이미지가 담긴다.비동기라서 커밋 직후에는 이력이 아직 없을 수 있다. 실제 사용자와 사유는 행에 기록된 것만 안다. 로그를 읽어 이력 테이블에 쓰는 별도 프로세스를 운영해야 한다.

    바이너리 로그 방식은 변경 데이터 캡처(Change Data Capture, CDC)라고 부른다. MySQL 매뉴얼에 따르면 행 기반 로깅의 행 이벤트는 수정이면 변경 전 이미지와 변경 후 이미지를 모두, 삭제면 변경 전 이미지만, 삽입이면 변경 후 이미지만 담는다. binlog_row_image를 minimal로 바꾸면 변경 전 이미지에는 행을 식별하는 데 필요한 컬럼만, 변경 후 이미지에는 SQL 문이 값을 지정했거나 AUTO_INCREMENT로 생성된 컬럼만 남으므로, CDC로 이력을 만든다면 이 설정을 바꾸지 않아야 한다. 참고로 매뉴얼은 binlog_format 변수 자체가 8.0.34부터 폐기 예정(deprecated)이라고 밝히고 있다.

    이력의 모양을 고르는 기준은 이 회차 처음에 세운 세 질문이다.

    방식특정 시점의 상태무엇이 바뀌었나저장·운영 비용잘 맞는 경우
    이전 값 컬럼불가(한 단계 전만)직전 변경 하나가장 작음화면이 직전 값 하나를 함께 보여 줘야 할 때
    현재 테이블에 버전 행쉬움(유효 기간이 있으면 조건 하나)연속 행 비교모든 현재 조회에 조건과 페이지 비용버전 자체가 업무 대상일 때(버전을 참조하는 주문, 약관 버전)
    스냅샷 이력 테이블쉬움연속 행 비교(LAG)행 전체 복사, 테이블마다 하나시점 조회·정산·복원이 주된 용도일 때
    컬럼 단위 로그어려움(되감기·재조립)쉬움바뀐 컬럼만, 타입 손실관리자 변경 내역 화면, 감사 추적
    공통 이력 테이블대상 하나는 가능가능(JSON 비교)한 테이블로 집중, 내용 검색 어려움많은 테이블에 같은 감사 기능이 필요할 때

    이 방식들은 서로 배타적이지 않다. 정산의 근거가 되는 가격은 스냅샷 이력 테이블에 유효 기간과 함께 두고, 관리자 화면용 변경 내역은 공통 이력 테이블에 남기는 식으로 질문마다 다른 그릇을 쓰는 것이 보통이다. 반대로 "혹시 모르니 모든 테이블에 모든 이력을" 남기는 것은 그 자체로 저장, 보관 정책, 개인 정보 관리라는 비용을 만든다. 이력은 누군가 그 질문을 던질 것이 확실할 때 그 질문에 맞는 모양으로 남긴다.

    Kimball의 SCD 번호를 이력 설계 용어로 빌려 쓸 때 주의할 점이 있다. Type 2(새 행 추가)와 Type 3(이전 값 속성 추가)은 이 회차의 버전 행 방식, 이전 값 컬럼 방식과 대응하지만, Kimball Group의 정의에서 Type 4는 자주 바뀌는 속성 묶음을 미니 디멘션(mini-dimension)으로 떼어 내는 기법이다. "Type 4 = 별도 이력 테이블"이라는 설명을 흔히 볼 수 있는데, 이는 Kimball의 원래 정의와 다르다.

    다음 회차에서는 삭제를 다룬다. 행을 지우는 대신 삭제 표시를 남기는 Soft Delete는 "삭제 이력을 어디에 남기는가"라는 이 회차의 질문과 바로 이어지고, 그때 유니크 제약을 어떻게 지키는지는 이 회차에서 쓴 생성 컬럼 유니크 인덱스 기법이 다시 등장한다.
    UPDATE는 덮어쓴다
    InnoDB의 언두 로그와 바이너리 로그에도 옛 값이 잠시 남지만 각각 동시성·복구와 복제를 위한 것이고 지워진다. 이력이 필요하면 테이블 설계로 남겨야 한다.
    이전 값 컬럼
    직전 값 하나만 기억한다(SCD Type 3). MySQL의 단일 테이블 UPDATE는 대입을 왼쪽에서 오른쪽으로 평가하므로 이전 값을 옮기는 대입을 먼저 써야 하고, 값이 바뀌지 않는 UPDATE는 걸러야 한다.
    현재 테이블에 버전 행
    한 테이블로 현재와 과거를 모두 표현하지만, 행 하나가 대상 하나라는 전제가 깨져 모든 조회에 현재 조건이 필요하고 외래 키·유니크 제약·버퍼 풀 효율이 나빠진다.
    현재 버전 유일성
    MySQL에는 부분 인덱스가 없으므로, 현재 버전이면 값이고 아니면 NULL인 생성 컬럼이나 함수 기반 키 부분에 유니크 인덱스를 건다. "최대 하나"만 보장하고 "최소 하나"는 절차로 지킨다.
    반열린 유효 기간
    [valid_from, valid_to)로 정의하면 연속 버전이 틈 없이 맞닿고 경계 시각에 정확히 한 행이 걸린다. 열린 끝은 NULL 대신 DATETIME 상한값으로 두고, 닫는 시각과 여는 시각은 한 번만 계산한다.
    스냅샷 이력 테이블
    현재 테이블은 그대로 두고 변경마다 행 전체를 이력 테이블에 추가한다. 같은 트랜잭션에서 기록하고, 원래 테이블의 유니크·외래 키 제약을 옮기지 않으며, 스키마 변경을 함께 따라가야 한다.
    트리거의 경계
    트리거는 같은 문장 안에서 실행되어 원자성을 보장하지만, 실제 사용자를 모르고, 외래 키 동작으로 일어난 변경에는 실행되지 않으며, 자신을 일으킨 문장이 쓰는 테이블을 수정할 수 없다.
    컬럼 단위 변경 로그
    바뀐 컬럼마다 이전 값과 새 값을 남겨 변경 내역 조회에 강하지만, 값이 문자열이 되어 타입이 사라지고 특정 시점 상태는 되감아 재조립해야 한다. 변경 단위는 상위 테이블로 묶는다.
    공통 이력 테이블
    모든 테이블의 변경을 (테이블, 행 키, JSON)으로 한곳에 모아 기능을 하나로 만들지만, 외래 키로 대상을 표현할 수 없고 내용 검색이 어려우며 쓰기량·보관 정책·접근 권한이 한 테이블에 묶인다.

    실무에서 이력 설계가 문제가 되는 순간은 대개 장애나 분쟁이다. "어제 오후 2시에 이 상품이 왜 0원에 팔렸나"를 물었을 때 updated_at과 updated_by만 있다면 마지막으로 고친 사람만 알 수 있고, 그 사이에 0원으로 바뀌었다가 되돌려진 일은 흔적이 없다. 이런 질문이 실제로 나올 테이블, 즉 돈과 재고와 권한을 다루는 테이블에는 처음부터 스냅샷 이력이나 공통 이력이 필요하다. 반대로 공지사항 본문 같은 테이블에 행 전체 스냅샷을 쌓는 것은 아무도 읽지 않는 데이터에 저장 공간과 쓰기 비용을 내는 일이다. 판단 기준은 "누가 어떤 질문을 던질 것인가"이고, 그 질문이 시점 상태인지 변경 내역인지에 따라 모양이 갈린다.

    현재 테이블에 버전 행을 쌓는 방식을 일반 업무 테이블에 쓰자는 제안이 나오면, 이 회차에서 본 비용 목록을 꺼내면 된다. 모든 조회의 현재 조건, 조인에서의 행 증식, 외래 키와 유니크 제약의 우회, 동시 수정 방어, 버퍼 풀을 차지하는 과거 행. 다만 버전 자체가 업무의 대상인 경우, 예를 들어 약관처럼 "사용자가 동의한 그 버전"을 다른 테이블이 참조해야 하는 경우에는 버전 행이 올바른 모델이다. 이때는 버전이 엔티티이고, 정체성 테이블을 분리하고 현재 버전 유일성을 생성 컬럼 유니크 인덱스로 지키면 된다.

    기록 위치는 "어떤 경로의 변경을 놓치면 안 되는가"로 정한다. 운영자가 직접 SQL로 고치는 일이 있는 조직이라면 애플리케이션 코드만으로는 이력이 빈다. 그렇다고 트리거로 옮기면 실제 사용자를 알기 위해 감사 컬럼 규칙을 모든 경로가 지켜야 하고, 외래 키 연쇄 동작이 걸린 테이블에서는 이력이 새어 나간다. 이력 테이블을 도입할 때는 그 테이블을 고치는 모든 경로(서비스 코드, 배치, 운영 SQL, 외래 키 연쇄 동작, 다른 애플리케이션)를 목록으로 만들고, 각 경로가 어떤 방식으로 이력에 잡히는지 확인하는 것이 첫 작업이다.
  • MySQL 8.0에서 product의 상품 1이 price = 10000, prev_price = NULL인 상태다. (가) UPDATE product SET price = 9000, prev_price = price WHERE product_id = 1을 실행한 뒤의 두 값, (나) 시작 상태에서 UPDATE product SET prev_price = price, price = 9000 WHERE product_id = 1을 두 번 연속 실행한 뒤의 두 값을 각각 구하고, 각 결과가 왜 그렇게 되는지 설명하라.
  • product_version에 상품 1의 버전 1 [01-01 09:00, 03-01 09:00), 버전 2 [03-01 09:00, 04-01 09:00), 버전 3 [04-01 09:00, 9999-12-31 23:59:59)이 있다. 시각 2025-03-01 09:00:00에 대해 (가) 반열린 조건 valid_from <= t AND t < valid_to, (나) t BETWEEN valid_from AND valid_to로 조회하면 각각 어떤 버전이 나오는가. 또 버전 2를 닫을 때 UPDATE와 INSERT에서 각각 NOW(6)을 불렀다면 어떤 문제가 생길 수 있는가.
  • 기본 키가 AUTO_INCREMENT 대리 키 version_id 하나뿐이고 다른 유니크 제약이 없는 product_version에서, 두 트랜잭션이 잠금 읽기 없이 같은 상품의 현재 버전 3을 읽고 각자 버전 4를 만든다. 최종 상태를 표로 그리고, 이 사고를 막는 절차적 방법과 제약 방법을 하나씩 제시하라.
  • 컬럼 단위 변경 로그에 상품 1에 대해 다음 행이 있다: (03-01, price, '10000' → '9000'), (04-01, name, '무선 키보드' → '무선 키보드 프로'), (05-01, price, '9000' → '8000'). 현재 행은 name = '무선 키보드 프로', price = 8000이다. 되감기 방법으로 2025-03-15 0시의 이름과 가격을 구하라. 또 WHERE column_name = 'price' AND old_value > '8500'의 결과 행을 구하고 그 결과가 숫자 비교와 같은지 판단하라.
  • 회원(member)을 삭제하면 주문(orders)이 ON DELETE CASCADE로 함께 지워지는 스키마에서, 주문 테이블에 AFTER DELETE 트리거로 스냅샷 이력을 남기고 있다. 회원 한 명을 삭제했을 때 주문 이력 테이블에 무엇이 남는지 설명하고, 주문 삭제 이력을 확실히 남기려면 설계를 어떻게 바꿔야 하는지 두 가지 이상 제시하라.

    1번. (가) MySQL은 단일 테이블 UPDATE의 대입을 왼쪽에서 오른쪽으로 평가하고, 대입식 오른쪽의 컬럼 참조는 앞선 대입이 반영된 현재 값을 읽는다. price = 9000이 먼저 실행되어 price가 9000이 되고, prev_price = price는 그 9000을 읽으므로 결과는 price = 9000, prev_price = 9000이다. 표준 SQL 동작이라면 prev_price는 갱신 전 값 10000이 되었을 것이다. (나) 첫 번째 실행에서 prev_price = price가 먼저 실행되어 10000을 옮기고, price는 9000이 된다. 두 번째 실행에서는 prev_price에 현재 price 9000이 옮겨지고 price는 다시 9000이 된다. 결과는 price = 9000, prev_price = 9000으로, 값이 바뀌지 않는 UPDATE가 직전 값을 지웠다. 이를 막으려면 AND price <> 9000 조건을 붙이거나 애플리케이션에서 값이 바뀔 때만 실행해야 한다.

    2번. (가) 반열린 조건에서 t = 03-01 09:00은 버전 1의 끝(제외)이고 버전 2의 시작(포함)이므로 버전 2 한 행만 나온다. (나) BETWEEN은 양 끝을 포함하므로 버전 1(valid_to가 t와 같음)과 버전 2(valid_from이 t와 같음)가 모두 나와 두 행이 된다. NOW(6) 문제: NOW()는 문장이 실행을 시작한 시각을 돌려주므로 UPDATE와 INSERT에서 값이 다를 수 있다. UPDATE의 값이 더 이르면 두 값 사이의 시각에는 어느 버전도 걸리지 않는 틈이 생긴다. 시각을 한 번 구해(SET @now = NOW(6) 또는 애플리케이션에서) 두 문장에 같은 값을 써야 한다.

    3번. 두 트랜잭션 모두 버전 3의 is_current를 0으로 바꾸고(나중에 실행된 쪽은 이미 0인 값을 다시 0으로 바꾼다), 각자 새 행을 INSERT한다(두 트랜잭션이 겹쳐 실행되면 두 번째 UPDATE는 첫 번째의 커밋을 기다린다). 대리 키는 서로 다른 값을 받으므로 둘 다 성공한다. 최종 상태는 버전 1~3이 is_current = 0, 그리고 version_no = 4, is_current = 1인 행이 두 개다. 하나는 T1의 변경만, 다른 하나는 T2의 변경만 반영하므로 어느 쪽을 현재로 보든 한 변경은 사라진다(갱신 손실). 절차적 방법: 현재 버전을 SELECT ... FOR UPDATE로 잠그며 읽어 같은 상품의 수정을 줄 세운다. 제약 방법: (product_id, version_no)에 유니크 제약을 걸거나, CASE WHEN is_current = 1 THEN product_id END에 유니크 인덱스를 걸어 두 번째 INSERT를 중복 키 오류로 만든다.

    4번. 3월 15일 0시 이후의 변경은 04-01의 name 변경과 05-01의 price 변경이다. 각 컬럼에서 t 이후 첫 변경의 old_value가 시점 t의 값이므로 이름은 '무선 키보드', 가격은 '9000'이다. 03-01 변경은 t 이전이므로 쓰지 않는다. 두 번째 쿼리: price 행의 old_value는 '10000'과 '9000'이다. 문자열 비교에서 '10000'은 첫 글자 '1'이 '8'보다 작으므로 '8500'보다 작고, '9000'은 '9'가 '8'보다 크므로 크다. 결과는 05-01 행 하나다. 숫자로 비교하면 10000과 9000 모두 8500보다 크므로 두 행이 나와야 한다. 문자열 저장 때문에 결과가 틀렸고, 올바르게 하려면 CAST(old_value AS DECIMAL(12,0)) > 8500으로 비교해야 한다(이 경우 인덱스는 쓰지 못한다).

    5번. MySQL에서 트리거는 외래 키 동작으로는 활성화되지 않으므로, 연쇄로 지워진 주문 행에 대해서는 주문 테이블의 DELETE 트리거가 실행되지 않고 주문 이력 테이블에는 아무것도 남지 않는다. 바꾸는 방법: (1) ON DELETE CASCADE를 없애고 애플리케이션이 주문을 명시적인 DELETE 문으로 먼저 지우게 하면 그 문장에 대해 트리거가 실행된다. (2) 회원 테이블의 DELETE 트리거나 애플리케이션 코드에서 그 회원의 주문 스냅샷을 이력에 먼저 기록한다. (3) 주문을 물리적으로 지우지 않고 상태를 바꾸는 방식(다음 회차의 Soft Delete)으로 바꾸면 UPDATE 트리거가 이력을 남긴다.

     MySQL 8.0에서 price = 10000, prev_price = NULL인 행에 UPDATE product SET price = 9000, prev_price = price를 실행했다. 결과는? price = 9000, prev_price = 10000 price = 9000, prev_price = 9000 price = 9000, prev_price = NULL 같은 컬럼을 참조하므로 오류가 난다 MySQL의 단일 테이블 UPDATE는 대입을 왼쪽에서 오른쪽으로 평가하고, 대입식 오른쪽의 컬럼 참조는 이미 갱신된 현재 값을 읽는다. price가 먼저 9000이 되므로 prev_price도 9000이 된다. 첫 번째 보기는 표준 SQL의 동작이고 MySQL 매뉴얼은 이 차이를 명시한다. 문법상 문제가 없으므로 오류는 나지 않는다. 버전 행에 유효 기간을 둘 때 [valid_from, valid_to) 반열린 구간을 쓰는 가장 중요한 이유는? BETWEEN을 쓸 수 있어 쿼리가 짧아진다 valid_to에 NULL을 넣을 수 있게 된다 연속된 버전이 같은 경계 값을 공유하면서도 어떤 시각을 물어도 정확히 한 버전만 걸린다 DATETIME의 정밀도를 초 단위로 낮출 수 있다 반열린 구간에서는 앞 버전의 끝과 다음 버전의 시작이 같은 값이어도 경계 시각이 뒤 버전에만 속하므로 틈도 겹침도 없다. BETWEEN은 양 끝을 포함하는 닫힌 구간이라 경계에서 두 행이 걸린다. NULL 사용 여부나 정밀도와는 관계가 없고, 오히려 반열린 구간은 정밀도와 무관하게 성립한다는 것이 장점이다. product_version에 UNIQUE INDEX ((CASE WHEN is_current = 1 THEN product_id END))를 만들었다. 이 인덱스가 보장하는 것은? 상품마다 현재 버전이 최대 하나다 상품마다 현재 버전이 정확히 하나다 과거 버전의 product_id가 모두 서로 다르다 현재 버전을 닫기 전에 새 버전을 INSERT해도 커밋 시점에만 검사하므로 안전하다 과거 버전에서 식의 값은 NULL이고, MySQL의 UNIQUE 인덱스는 여러 NULL을 허용하므로 현재 버전끼리만 비교된다. 따라서 "최대 하나"를 보장한다. 현재 버전이 하나도 없는 상태는 막지 못하므로 "정확히 하나"는 트랜잭션 절차로 지켜야 한다. MySQL은 유니크 제약을 행을 바꿀 때마다 검사하므로, 새 버전을 먼저 넣으면 그 순간 중복 키 오류가 난다. 주문 테이블에 AFTER DELETE 트리거로 이력을 남긴다. 회원을 삭제해 ON DELETE CASCADE로 주문이 함께 지워졌을 때 주문 이력은? 주문 행마다 이력이 하나씩 남는다 회원 삭제 문장 하나에 대해 이력이 하나 남는다 트리거가 오류를 내서 회원 삭제가 롤백된다 주문 테이블의 트리거가 실행되지 않아 이력이 남지 않는다 MySQL 매뉴얼은 트리거가 외래 키 동작으로는 활성화되지 않는다고 명시한다. 연쇄 삭제는 외래 키 동작이므로 주문 테이블의 DELETE 트리거는 실행되지 않고, 오류도 나지 않는다. 그래서 이 빈틈은 조용히 생긴다. 트리거로 이력을 남기는 테이블은 그 테이블에 걸린 연쇄 동작을 먼저 확인해야 한다. 상품 설명(긴 텍스트)은 거의 바뀌지 않고 가격과 재고 상태만 하루에도 여러 번 바뀐다. 관리자 화면에는 "가격을 누가 언제 무엇에서 무엇으로 바꿨나"를 보여 줘야 하고, 특정 시점 전체 상품의 상태를 묻는 요구는 없다. 가장 알맞은 설계는? 상품 테이블 전체를 버전 행 방식으로 바꾼다 가격과 상태에 대한 컬럼 단위 변경 로그를 남긴다 상품 행 전체를 스냅샷 이력 테이블에 복사한다 prev_price 컬럼을 추가한다 요구가 "변경 내역"이고 시점 상태 조회가 없으므로 변화를 직접 기록하는 컬럼 단위 로그가 맞다. 바뀐 컬럼만 남으므로 긴 설명이 반복 복사되지 않는다. 버전 행 방식은 현재 조회 전체에 비용을 퍼뜨리고, 스냅샷은 매번 긴 설명까지 복사하며 변경 내역을 보려면 연속 행을 비교해야 한다. prev_price는 직전 값 하나만 기억하고 누가 바꿨는지도 남기지 않는다.
    스냅샷 이력 테이블(full-row snapshot history table)
    원래 테이블의 행이 바뀔 때마다 행 전체의 복사본을 한 행씩 추가하는 별도 테이블. 변경 후 상태를 담을지 변경 전 상태를 담을지를 먼저 정해야 한다.
    반열린 구간(half-open interval)
    시작은 포함하고 끝은 제외하는 구간 [a, b). 연속된 구간이 같은 경계 값을 공유해도 틈과 겹침이 생기지 않는다.
    SCD(Slowly Changing Dimension)
    데이터 웨어하우스에서 천천히 바뀌는 속성을 다루는 기법의 분류. Kimball Group의 정의에서 Type 2는 새 행 추가, Type 3은 이전 값을 담을 속성 추가, Type 4는 미니 디멘션 분리다.
    트리거(trigger)
    테이블의 INSERT·UPDATE·DELETE에 반응해 실행되는 저장 프로그램. MySQL에서는 영향받은 행마다 실행되며 OLD와 NEW로 변경 전후 값을 읽는다. 외래 키 동작으로는 실행되지 않는다.
    함수 기반 키 부분(functional key part)
    MySQL 8.0.13부터 인덱스 키로 컬럼 대신 식을 쓰는 기능. 숨겨진 가상 생성 컬럼으로 구현되며, UNIQUE와 함께 써서 부분 유니크 제약을 흉내 낼 수 있다.
    NULL 안전 비교(<=>)
    두 피연산자가 모두 NULL이면 1, 한쪽만 NULL이면 0을 돌려주는 MySQL의 비교 연산자. 이력 기록에서 NULL과 값 사이의 변경을 놓치지 않으려면 이것으로 비교한다.
    변경 데이터 캡처(Change Data Capture, CDC)
    데이터베이스의 변경 로그(MySQL에서는 행 기반 바이너리 로그)를 읽어 변경 사항을 다른 곳으로 전달하는 방식. 원래 트랜잭션에 쓰기를 더하지 않지만 비동기다.
    다형성 연관(polymorphic association)
    한 컬럼 쌍(테이블 이름, 행 키)이 행마다 서로 다른 테이블을 가리키는 구조. 외래 키로 표현할 수 없어 참조 무결성을 데이터베이스가 지켜 주지 못한다.
