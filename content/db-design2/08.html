    이 회차의 질문: 상품마다 속성이 다르다

    옷, 노트북, 식품을 함께 파는 종합 쇼핑몰을 생각해 보자. 티셔츠에는 색상, 사이즈, 소재가 있다. 노트북에는 CPU, 메모리 용량, 저장 용량, 무게가 있다. 식품에는 유통기한, 원산지, 중량이 있다. 상품명, 가격, 카테고리처럼 모든 상품이 가진 속성도 있지만, 상품 상세 화면의 "상품 정보" 표에 들어가는 속성 대부분은 카테고리마다 다르다. 게다가 이 목록은 고정되어 있지 않다. 상품 기획자(MD)가 이번 주에 캠핑 의자를 들여오면 "최대 하중"과 "접이식 여부"가 새로 필요해지고, 다음 달 노트북 기획전에서는 "배터리 용량"으로 상품을 걸러 보고 싶다는 요청이 들어온다.

    관계형 데이터베이스의 테이블은 이런 요구와 맞지 않는 전제 위에 서 있다. 테이블을 만들 때 열의 이름, 타입, 제약을 정하고, 그 테이블의 모든 행은 같은 열 집합을 가진다. 열 집합은 스키마(schema)이고, 스키마는 설계 시점에 정해져 배포를 통해서만 바뀐다. 반면 값은 데이터이고, 데이터는 운영 중에 언제든 바뀐다. 상품 속성 문제의 핵심은 "어떤 속성이 있는가" 자체가 데이터처럼 운영 중에 바뀐다는 데 있다. 스키마가 바뀌는 속도(배포 주기)와 업무가 바뀌는 속도(매일)가 어긋나는 것이다.

    이 회차는 이 어긋남을 다루는 대표적인 설계인 EAV(Entity-Attribute-Value, 엔티티-속성-값) 패턴을 다룬다. 순서는 다음과 같다. 먼저 속성을 모두 열로 두는 넓은 테이블과, 속성이 생길 때마다 스키마를 바꾸는 방식이 어디서 막히는지 InnoDB와 MySQL 서버 동작으로 확인한다. 다음으로 EAV의 구조를 세우고 쇼핑몰 상품 속성으로 저장·조회·검색을 실습한다. 그다음 EAV 행이 InnoDB 페이지에 어떻게 놓이는지 바이트 단위로 따져 보고, 속성 정의 테이블과 타입별 값 열로 패턴을 개선한다. 마지막으로 옵티마이저가 EAV 쿼리를 어떻게 보는지, 애플리케이션에서 값 행을 어떻게 다시 타입 있는 객체로 되돌리는지, 장단점과 주의사항, 실무 사례를 정리한다. 기준 환경은 MySQL 8.0 이상, InnoDB, 기본 행 형식 DYNAMIC, 문자 집합 utf8mb4다.

    기존 방식의 한계 1: 모든 속성을 열로 두는 넓은 테이블

    가장 먼저 떠오르는 방법은 등장할 수 있는 모든 속성을 상품 테이블의 열로 만드는 것이다. 티셔츠 행은 의류 관련 열만 채우고 노트북 관련 열은 비워 두며, 노트북 행은 그 반대로 한다.

    CREATE TABLE product_wide (
  product_id   BIGINT       NOT NULL AUTO_INCREMENT,
  category     VARCHAR(20)  NOT NULL,
  name         VARCHAR(100) NOT NULL,
  price        INT          NOT NULL,
  -- 의류
  color        VARCHAR(30)  NULL,
  size         VARCHAR(10)  NULL,
  material     VARCHAR(50)  NULL,
  -- 노트북
  cpu          VARCHAR(30)  NULL,
  memory_gb    INT          NULL,
  storage_gb   INT          NULL,
  weight_g     INT          NULL,
  -- 식품
  expire_date  DATE         NULL,
  origin       VARCHAR(30)  NULL,
  -- ... 카테고리가 늘 때마다 열이 늘어난다
  PRIMARY KEY (product_id)
);

    행 몇 개를 넣으면 테이블은 다음과 같은 모양이 된다. 행마다 채워진 칸보다 빈 칸이 많은, 이른바 희소(sparse)한 테이블이다. 카테고리가 수십 개가 되고 카테고리마다 속성이 열 개 남짓이면 열은 수백 개가 되고, 각 행은 그중 열 개 정도만 채운다.

    NULL 칸은 공간을 얼마나 차지하는가

    넓은 테이블을 처음 보면 "빈 칸이 이렇게 많으니 공간 낭비가 심하겠다"는 생각이 든다. InnoDB에서는 사실과 다르다. MySQL 문서의 COMPACT 행 형식 설명(DYNAMIC도 이 구조를 따른다)에 따르면, 레코드 헤더의 가변 길이 부분에 NULL 열을 표시하는 비트 벡터가 있고, NULL이 될 수 있는 열이 N개면 이 벡터는 CEILING(N/8)바이트를 차지한다. 그리고 NULL인 열은 이 벡터의 비트 하나 외에는 공간을 차지하지 않는다. 즉 NULL 허용 열이 300개인 테이블이라도 행마다 NULL 비트맵은 CEILING(300/8) = 38바이트이고, NULL인 칸 자체는 0바이트다.

    그러므로 넓은 테이블의 문제는 공간이 아니다. 오히려 뒤에서 계산하겠지만 사실 하나(예: "1번 상품의 색상은 검정")를 저장하는 바이트만 따지면 넓은 테이블이 EAV보다 훨씬 작다. 넓은 테이블이 곤란한 진짜 이유는 다음 세 가지다.

    진짜 문제 1: 제약이 카테고리를 모른다

    노트북이라면 CPU가 반드시 있어야 하고, 티셔츠라면 사이즈가 반드시 있어야 한다. 그런데 cpu 열에 NOT NULL을 걸면 티셔츠를 넣을 수 없다. 열의 제약은 테이블의 모든 행에 똑같이 적용되기 때문이다. 카테고리에 따라 다른 규칙을 걸려면 MySQL 8.0.16부터 실제로 검사되는 CHECK 제약을 쓸 수 있다.

    ALTER TABLE product_wide
  ADD CONSTRAINT ck_laptop_cpu
  CHECK (category <> 'LAPTOP' OR cpu IS NOT NULL);

    위 코드는 실제로는 <> 대신 !=로 써도 같다. 이 방법은 동작하지만, 카테고리 이름이 제약 안에 상수로 박힌다. 카테고리가 하나 늘 때마다, 필수 속성 규칙이 하나 바뀔 때마다 제약을 고치는 DDL이 필요하다. 업무 규칙이 바뀌는 속도로 스키마를 바꾸어야 한다는 문제가 그대로 남는다. 또 NULL이 "이 카테고리에는 해당 없음"인지, "해당하지만 아직 입력하지 않음"인지 구별되지 않는다. 노트북 행의 weight_g가 NULL이면 무게를 모르는 것이고, 티셔츠 행의 weight_g가 NULL이면 애초에 관심 없는 속성이다. 같은 NULL이 서로 다른 뜻을 가진다.

    진짜 문제 2: 열과 행의 크기에는 한도가 있다

    열을 무한히 늘릴 수도 없다. MySQL은 테이블당 열 4096개라는 하드 한도를 두고, InnoDB 테이블은 최대 1017개 열을 가질 수 있다(가상 생성 열 포함). 이보다 먼저 부딪히는 것은 행 크기 한도다. MySQL 서버는 저장 엔진과 상관없이 한 행의 크기를 65,535바이트로 제한하는데, 이때 가변 길이 열은 실제 값이 아니라 선언한 최대 길이와 길이 바이트로 계산된다. utf8mb4의 VARCHAR(255)는 문자 하나에 최대 4바이트이므로 1,020바이트에 길이 바이트 2바이트를 더해 1,022바이트로 계산된다. 이런 열을 65개 선언하면 그 열들만으로 66,430바이트가 되어 테이블 생성이 ERROR 1118 (42000): Row size too large로 거부된다. MySQL 8.4.13과 8.0.46에서 이런 열 65개로 테이블을 만들면 실제로 이 오류가 나고, 64개(65,408바이트)면 만들어진다. 문서는 해결책으로 일부 열을 TEXT나 BLOB으로 바꾸라고 안내하는데, 이 타입들은 행 크기 계산에 9~12바이트만 더하기 때문이다.

    InnoDB에는 별도의 한도가 하나 더 있다. 한 페이지 안에 저장되는 행 데이터는 페이지 크기의 절반보다 약간 작아야 하므로, 기본 16KB 페이지에서는 8KB 조금 못 되는 크기가 상한이다. DYNAMIC 행 형식은 긴 가변 길이 값을 통째로 오버플로 페이지로 옮기고 레코드에는 20바이트 포인터만 남겨 이 한도를 피해 가지만, CHAR처럼 고정 길이로 자리를 잡는 열이 많으면 테이블 생성 단계에서 Row size too large (> 8126) 오류를 만난다. MySQL 8.4.13·8.0.46에서 latin1 CHAR(255) 열 40개로 테이블을 만들면 이 오류가 난다. 같은 개수의 utf8mb4 CHAR(255) 열로는 테이블이 만들어지는데, 문서에 따르면 InnoDB는 최대 길이가 768바이트 이상인 고정 길이 열을 가변 길이로 다루어 오버플로 페이지에 둘 수 있고, utf8mb4의 CHAR(255)는 최대 1,020바이트이기 때문이다. 인덱스 쪽에도 한도가 있다. 문서는 InnoDB 테이블의 보조 인덱스가 최대 64개라고 적지만, 실제로 걸리는 것은 기본 키까지 포함해 테이블당 인덱스 64개라는 서버 한도다. MySQL 8.4.13·8.0.46에서 기본 키를 선언한 테이블은 보조 인덱스를 63개까지 만들 수 있고(기본 키가 없으면 64개), 다중 열 인덱스의 열은 최대 16개다. 기본 키를 둔 테이블에 속성마다 검색용 인덱스를 하나씩 만들면 속성 64개째에서 막힌다.

    이 한도들을 넘기는 CREATE TABLE을 차례로 실행하면 다음 오류가 난다. 순서대로 utf8mb4 VARCHAR(255) 열 65개, latin1 CHAR(255) 열 40개, INT 열 1,018개, 기본 키에 보조 인덱스 64개, 열 17개짜리 인덱스다. 열 1,017개, 기본 키에 보조 인덱스 63개, 열 16개짜리 인덱스는 만들어진다.

    진짜 문제 3: 범용 열이라는 유혹

    열이 계속 늘어나는 것이 부담스러워지면 흔히 다음과 같은 타협이 등장한다. 의미가 정해지지 않은 열 attr1부터 attr20까지를 만들어 두고, 카테고리마다 "의류는 attr1이 색상, attr2가 사이즈", "노트북은 attr1이 CPU, attr2가 메모리" 하는 식으로 약속하는 것이다. 이 약속은 데이터베이스 어디에도 없고 애플리케이션 코드나 문서에만 있다. 모든 열은 아무 값이나 받아야 하므로 VARCHAR가 되고, attr2에 만든 인덱스에는 사이즈 문자열과 메모리 숫자가 뒤섞인다. 열 이름만 보고는 값의 의미를 알 수 없으니 SQL을 쓰는 사람마다 약속표를 찾아봐야 한다. 이 방식은 사실상 뒤에서 볼 EAV의 "속성" 정보를 열 번호에 숨겨 둔 것과 같은데, 속성의 정의를 데이터로 관리하지도 못하므로 EAV보다 나쁜 형태라고 할 수 있다.

    기존 방식의 한계 2: 속성이 생길 때마다 스키마를 바꾸는 비용

    열을 미리 다 만들어 두지 않고, 새 속성이 필요할 때마다 ALTER TABLE ... ADD COLUMN을 하면 어떨까. 또는 카테고리마다 테이블을 따로 만들어(product_clothing, product_laptop 처럼) 카테고리가 생길 때 CREATE TABLE을 하는 방법도 있다. 후자는 07회의 상속 관계 설계에서 본 서브타입 테이블과 같은 구조로, 카테고리를 가로지르는 조회가 UNION ALL이 되고 카테고리 추가가 곧 스키마와 코드 변경이 된다는 점에서 전자와 같은 비용을 진다. 여기서는 열 추가의 비용을 자세히 본다.

    INSTANT 열 추가: 데이터는 건드리지 않는다

    MySQL 8.0의 InnoDB는 열 추가를 INSTANT 알고리즘으로 처리할 수 있다. 문서에 따르면 INSTANT는 MySQL 8.0.12부터 지원되는 작업의 기본 알고리즘이고, 열 추가는 메타데이터만 바꾸는 작업으로 분류된다. 기존 행을 다시 쓰지 않으므로 테이블이 아무리 커도 변경 자체는 짧게 끝난다. 다만 조건이 붙는다. 8.0.29 이전에는 INSTANT로 맨 마지막 열로만 추가할 수 있었고, 8.0.29부터는 아무 위치에나 추가할 수 있다. ROW_FORMAT=COMPRESSED 테이블, FULLTEXT 인덱스가 있는 테이블, 임시 테이블에는 INSTANT로 열을 추가할 수 없다. 또 8.0.29부터는 INSTANT로 열을 추가하거나 삭제할 때마다 테이블에 새 행 버전(row version)이 생기는데, 허용되는 행 버전은 최대 64개다. 한도에 이르면 ALGORITHM=INSTANT를 지정한 추가·삭제는 오류로 거부되고, 테이블을 다시 만드는(rebuild) ALTER TABLE이나 OPTIMIZE TABLE을 해야 버전 수가 0으로 돌아간다. MySQL 8.4.13과 8.0.46에서 열을 INSTANT로 64번 추가하면 information_schema.innodb_tables의 total_row_versions가 64가 되고, 그다음 ALGORITHM=INSTANT를 지정한 열 추가와 열 삭제는 모두 다음 오류로 거부된다. 같은 상태에서 ALGORITHM을 적지 않은 ADD COLUMN은 오류 없이 테이블을 다시 만드는 방식으로 넘어가 실행되었고, 그 뒤 total_row_versions는 0이었다.

    ERROR 4092 (HY000): Maximum row versions reached for table m_db_design2_08/t_inst. No more columns can be added or dropped instantly. Please use COPY/INPLACE.

    MySQL 8.4.13·8.0.46에서 FULLTEXT 인덱스가 있는 테이블과 ROW_FORMAT=COMPRESSED 테이블에 ALGORITHM=INSTANT로 열을 추가하면 각각 ERROR 1846 (0A000)과 ERROR 1845 (0A000)로 거부된다.

    INSTANT를 쓸 수 없어 ALGORITHM=INPLACE로 열을 추가하면 문서가 밝히듯 테이블이 다시 만들어진다. 클러스터형 인덱스의 모든 행이 새 구조로 다시 쓰이고 보조 인덱스도 다시 만들어진다는 뜻이다. 행이 수천만 개인 상품 테이블이라면 이 작업은 오래 걸리고, 그동안 디스크 I/O와 리두 로그를 크게 쓴다. 속성이 매주 늘어나는 도메인이라면 64라는 행 버전 한도는 1년 남짓이면 닿을 수 있는 숫자다.

    짧은 변경도 잠금을 기다린다: 메타데이터 잠금

    더 자주 사고를 일으키는 것은 변경 시간이 아니라 메타데이터 잠금(metadata lock, MDL)이다. MySQL은 테이블 정의를 보호하기 위해, 테이블을 쓰는 모든 문장에 그 테이블의 메타데이터 잠금을 건다. SELECT나 INSERT 같은 일반 문장은 서로 호환되는 공유 메타데이터 잠금을 잡고, 이 잠금은 문장이 끝날 때가 아니라 트랜잭션이 끝날 때 풀린다. 온라인 DDL 문서는 DDL 실행을 세 단계로 설명한다. 초기화 단계에서는 공유 업그레이드 가능 메타데이터 잠금을 잡고, 실행 단계에서는 필요하면 준비 중에 잠깐 배타 잠금을 잡으며, 마지막 테이블 정의 커밋 단계에서는 옛 정의를 내보내고 새 정의를 확정하기 위해 반드시 배타 메타데이터 잠금으로 올린다. INSTANT 열 추가도 이 배타 잠금이 필요하다.

    문제는 배타 잠금이 앞서 공유 잠금을 쥔 트랜잭션이 모두 끝나기를 기다린다는 것, 그리고 문서의 표현대로 대기 중인 배타 잠금 요청이 그 뒤에 오는 트랜잭션을 막는다는 것이다. 시간순으로 따라가 보자.

    시각  세션 A (관리 배치)              세션 B (DDL)                         세션 C, D, E ... (주문 화면)
----  ------------------------------  -----------------------------------  ------------------------------
t0    START TRANSACTION;
t1    SELECT ... FROM product ...;
      → product 공유 MDL 보유
        (커밋하지 않고 다른 일을 함)
t2                                    ALTER TABLE product ADD COLUMN ...;
                                      → 배타 MDL 요청, A가 끝나기를 대기
t3                                                                         SELECT ... FROM product ...;
                                                                           → 공유 MDL 요청
                                                                             B의 대기 중인 배타 요청 뒤에 줄 섬
t4    (다른 일 계속 ...)              (대기)                               (대기 중인 연결이 계속 쌓임)
t5    COMMIT;                         → 배타 MDL 획득, 정의 교체, 해제     → 쌓였던 문장이 차례로 실행

    t3 이후 SHOW PROCESSLIST에는 세션 B와 C 모두 Waiting for table metadata lock 상태로 보인다. 세션 C의 SELECT는 세션 A의 공유 잠금과는 충돌하지 않지만, 먼저 줄을 선 세션 B의 배타 요청을 앞지르지 못한다. 그래서 변경 자체는 순식간에 끝나는 INSTANT 열 추가라도, 커밋하지 않은 채 열려 있는 트랜잭션이 하나 있으면 그 테이블을 쓰는 모든 요청이 멈춘다. 애플리케이션 쪽에서는 커넥션 풀의 커넥션이 하나씩 대기 상태로 묶이다가 풀이 바닥나고, 결국 상품과 관계없는 요청까지 커넥션을 얻지 못해 실패한다. 문서는 오래 실행되거나 비활성 상태인 트랜잭션이 있으면 온라인 DDL이 배타 메타데이터 잠금을 기다리다 시간 초과될 수 있다고 적고 있다.

    MySQL 8.4.13에서 이 순서를 재현해 보았다. 세션 A는 START TRANSACTION 뒤 product를 한 번 조회하고 DO SLEEP(12)로 커밋을 미루며, 2초 뒤 세션 B가 ALGORITHM=INSTANT 열 추가를, 다시 2초 뒤 두 세션이 product 조회를 실행한다. 그 2초 뒤 information_schema.processlist와 performance_schema.metadata_locks를 조회한 결과다. id와 time은 실행할 때마다 다르다.

    +-----+---------+------+---------------------------------+--------------------------------------------------------------+
| id  | command | time | state                           | info                                                         |
+-----+---------+------+---------------------------------+--------------------------------------------------------------+
| 591 | Query   |    6 | User sleep                      | DO SLEEP(12)                                                 |
| 592 | Query   |    4 | Waiting for table metadata lock | ALTER TABLE product ADD COLUMN memo VARCHAR(10), ALGORITHM=I |
| 593 | Query   |    2 | Waiting for table metadata lock | SELECT name FROM product WHERE product_id = 2                |
| 594 | Query   |    2 | Waiting for table metadata lock | SELECT COUNT(*) FROM product                                 |
+-----+---------+------+---------------------------------+--------------------------------------------------------------+
+-------------+-------------------+-------------+
| object_name | lock_type         | lock_status |
+-------------+-------------------+-------------+
| product     | SHARED_READ       | GRANTED     |
| product     | SHARED_UPGRADABLE | GRANTED     |
| product     | EXCLUSIVE         | PENDING     |
| product     | SHARED_READ       | PENDING     |
| product     | SHARED_READ       | PENDING     |
+-------------+-------------------+-------------+

    세션 A의 공유 잠금(SHARED_READ)과 세션 B의 공유 업그레이드 가능 잠금(SHARED_UPGRADABLE)은 승인되었고, B의 배타 잠금 요청과 뒤에 온 두 조회의 공유 잠금 요청은 대기(PENDING) 중이다. A가 커밋하자 열 추가와 두 조회가 모두 끝났다.

    공유 MDL을 쥔 열린 트랜잭션, 배타 MDL을 기다리는 ALTER TABLE, 그 뒤에 막힌 일반 SELECT들이 하나의 대기열을 이루는 구조를 보여 준다. 가로 시간축(왼쪽에서 오른쪽)을 가진 시퀀스 다이어그램. 위에서 아래로 세 개의 수평 레인: "세션 A: 열린 트랜잭션", "세션 B: ALTER TABLE", "세션 C·D·E: 일반 SELECT". 가운데에 세로로 긴 자물쇠 아이콘 기둥 "product 테이블 메타데이터 잠금". 세션 A 레인에는 초록 막대가 길게 이어지고 라벨 "공유 MDL 보유(커밋 전)". 세션 B 레인에는 주황 점선 막대와 라벨 "배타 MDL 대기". 세션 C·D·E 레인에는 회색 막대 여러 개가 계단식으로 쌓이고 라벨 "B 뒤에 줄 섬". 오른쪽 끝에서 세션 A 막대가 끝나는 지점에 세로 점선과 라벨 "COMMIT", 그 직후 세션 B의 짧은 빨간 막대 "정의 교체", 이어서 회색 막대들이 풀려 나가는 화살표. 평면 스타일, 파랑·주황·회색. INSTANT 열 추가도 마지막에 배타 메타데이터 잠금이 필요하다. 대기 중인 배타 요청은 그 뒤의 공유 요청까지 막는다.

    데이터베이스 밖의 비용

    스키마 변경 비용은 데이터베이스에서 끝나지 않는다. 새 열이 생기면 JPA 엔티티에 필드를 추가하고, 화면 DTO와 관리자 입력 화면, 검색 조건을 고치고, 테스트하고, 배포해야 한다. MD가 "오늘 오후에 캠핑 의자 상품을 등록해야 하니 최대 하중 칸을 만들어 달라"고 하면, 그 요청은 개발자와 DBA의 일정, 그리고 배포 창을 거쳐야 한다. 속성 하나를 늘리는 데 필요한 사람과 절차가 업무 속도를 따라가지 못하는 것이다.

    새로운 접근법

    속성의 목록이 업무 중에 계속 바뀐다면, 속성을 스키마(열)로 표현하는 한 매번 DDL과 배포가 필요하다. 발상을 바꿔 속성 자체를 데이터(행)로 표현하면 새 속성의 등장은 INSERT 한 번이 된다. 열을 늘리는 대신 행을 늘리는 것, 이것이 EAV의 출발점이다. 그 대가로 스키마가 해 주던 일(타입, 필수 여부, 허용 값 검사, 최적화에 필요한 정보)을 누가 대신할지가 이 회차 나머지의 주제다.

    EAV 패턴 소개: 속성을 열이 아니라 행으로

    EAV는 사실 하나를 세 요소로 나눠 한 행에 담는다. 엔티티(entity)는 그 사실이 누구에 관한 것인지(2번 상품), 속성(attribute)은 무엇에 관한 것인지(메모리 용량), 값(value)은 그 내용(16)이다. 넓은 테이블에서 한 행에 가로로 늘어서 있던 칸들이, EAV에서는 칸 하나당 한 행씩 세로로 늘어선다.

    넓은 테이블 (속성 = 열 이름)

 product_id | cpu | memory_gb | storage_gb | weight_g
 -----------+-----+-----------+------------+---------
          2 | i5  |        16 |        512 |     1120

                  │  언피벗(unpivot): 칸 하나를 행 하나로
                  ▼                ▲ 피벗(pivot): 행들을 다시 칸으로

EAV 테이블 (속성 = 열의 값)

 entity(product_id) | attribute    | value
 -------------------+--------------+------
                  2 | cpu          | i5
                  2 | memory_gb    | 16
                  2 | storage_gb   | 512
                  2 | weight_g     | 1120

    그림에서 가장 중요한 변화는 "memory_gb"라는 이름이 어디에 있느냐다. 넓은 테이블에서 그것은 열 이름, 즉 스키마의 일부다. 데이터베이스는 그 열의 타입이 INT라는 것, NULL을 허용하는지, 어떤 인덱스가 걸려 있는지를 알고 모든 쓰기에서 이를 검사한다. EAV에서 "memory_gb"는 attribute 열에 들어 있는 문자열 값일 뿐이다. 데이터베이스가 보기에 ('memory_gb', '16')과 ('memory_gb', '많음')은 똑같이 올바른 행이다. 스키마에 있던 정보, 곧 메타데이터가 데이터의 자리로 내려온 것이다.

    이것이 EAV의 힘이자 비용이다. 새 속성 "battery_wh"를 추가하는 일은 attribute 열에 새 문자열을 쓰는 INSERT이므로 DDL도, 메타데이터 잠금의 배타 요청도, 배포도 필요 없다. 반면 열이 하던 일은 모두 다른 곳으로 옮겨 가야 한다. 다음 표는 넓은 테이블에서 열 정의가 맡던 역할이 EAV에서 어디로 가는지를 정리한 것이다.

    열 정의가 하던 일넓은 테이블EAV에서 이 일을 맡는 곳
    속성의 존재와 이름열 이름(DDL)attribute 열의 값, 개선하면 속성 정의 테이블의 행
    값의 타입열의 데이터 타입보통 문자열 하나로 뭉뚱그려짐. 개선하면 타입별 값 열과 정의 테이블의 타입 정보
    필수 여부NOT NULL데이터베이스가 강제할 수 없음. 정의 테이블의 플래그 + 애플리케이션 검증
    허용 값 목록외래 키, ENUM, CHECK선택지 테이블과 복합 외래 키(개선 구조)
    표시 이름, 단위, 순서애플리케이션 코드정의 테이블의 열(오히려 데이터로 관리하기 쉬워짐)
    조회 시 결과의 모양열 그대로피벗 쿼리 또는 애플리케이션 조립
    옵티마이저가 쓰는 통계열마다 인덱스 통계·히스토그램모든 속성이 한 열에 섞인 통계
    속성 이름이 열 이름(스키마)에서 열의 값(데이터)으로 내려가는 변화와, 피벗/언피벗이 서로 반대 방향의 변환이라는 점을 보여 준다. 위아래 두 부분으로 나뉜 그림. 위쪽에 가로로 긴 표 하나: 머리글 칸 "product_id", "cpu", "memory_gb", "storage_gb", "weight_g"가 파란 배경이고 그 아래 한 행 "2", "i5", "16", "512", "1120". 머리글 칸 위에 중괄호와 라벨 "속성 = 스키마(열 이름)". 아래쪽에 세로로 긴 3열 표: 머리글 "product_id", "attribute", "value", 아래 4행 "2 / cpu / i5", "2 / memory_gb / 16", "2 / storage_gb / 512", "2 / weight_g / 1120". attribute 열의 값 칸 4개가 파란 배경이고 옆에 라벨 "속성 = 데이터(열의 값)". 두 표 사이 왼쪽에 아래 방향 화살표 "언피벗", 오른쪽에 위 방향 화살표 "피벗". 위 표의 파란 머리글 칸에서 아래 표의 파란 값 칸으로 가는 곡선 점선 화살표. 평면 스타일, 흰 배경. EAV는 속성 이름을 스키마에서 데이터로 옮긴다. 화면에 보여 줄 때는 다시 피벗해 가로로 펼친다.

    EAV는 키-값 저장소(key-value store)와 닮았다. 엔티티마다 "속성 이름 → 값"의 사전을 하나씩 가진다고 볼 수 있기 때문이다. 차이는 관계형 데이터베이스 안에 있다는 점이다. 엔티티는 여전히 외래 키로 묶이고, 트랜잭션으로 여러 값을 한 번에 바꿀 수 있으며, SQL로 다른 테이블과 조인할 수 있다. 이 장점을 살리고 단점을 줄이는 것이 EAV 설계의 전부라 해도 과장이 아니다.

    EAV 실습 1: 쇼핑몰 상품 속성 저장과 한 상품 조회

    가장 단순한 형태부터 만들어 보자. 모든 상품이 공통으로 가진 속성(카테고리, 이름, 가격)은 product 테이블의 열로 두고, 카테고리마다 다른 속성만 EAV 테이블 product_attribute로 보낸다. 공통 속성까지 EAV로 보내지 않는 이유는 뒤의 주의사항에서 다시 다룬다.

    CREATE TABLE product (
  product_id  BIGINT       NOT NULL AUTO_INCREMENT,
  category    VARCHAR(20)  NOT NULL,
  name        VARCHAR(100) NOT NULL,
  price       INT          NOT NULL,
  PRIMARY KEY (product_id)
);

CREATE TABLE product_attribute (
  product_id       BIGINT       NOT NULL,
  attribute_name   VARCHAR(50)  NOT NULL,
  attribute_value  VARCHAR(255) NOT NULL,
  PRIMARY KEY (product_id, attribute_name),
  KEY idx_pa_name_value (attribute_name, attribute_value),
  CONSTRAINT fk_pa_product FOREIGN KEY (product_id) REFERENCES product (product_id)
);

    기본 키 (product_id, attribute_name)은 "한 상품은 한 속성에 값을 하나만 가진다"는 규칙을 표현한다. 같은 상품에 "CPU" 행을 두 번 넣으면 기본 키 중복으로 거부된다. 보조 인덱스 (attribute_name, attribute_value)는 "색상이 검정인 상품"처럼 속성으로 상품을 찾을 때 쓴다. 데이터를 넣어 보자. 속성 이름은 화면에 보이는 한국어 이름을 그대로 쓰고, 단위는 이름의 괄호 안에 적었다. 이 선택이 나중에 어떤 문제를 만드는지도 함께 볼 것이다.

    한 상품의 속성 읽기

    상품 상세 화면은 한 상품의 속성을 모두 읽는다.

    SELECT attribute_name, attribute_value
FROM product_attribute
WHERE product_id = 2;

    조건이 기본 키의 첫 열에 대한 등호이므로 InnoDB는 클러스터형 인덱스에서 product_id = 2인 구간 하나를 읽는다. 결과는 네 행이고, 애플리케이션은 이것을 "이름 → 값" 맵으로 만들어 화면의 상품 정보 표에 순서대로 뿌린다. 단, ORDER BY가 없는 결과의 행 순서는 SQL이 보장하지 않으므로 화면 순서가 중요하면 정렬 기준이 따로 있어야 한다. 이 단순한 구조에는 "화면에 어떤 순서로 보여 줄지"를 담을 곳이 없다는 것도 뒤에서 개선할 점이다.

    피벗: 행을 다시 열로 펼치기

    노트북 목록을 표로 보여 주려면 상품 하나를 한 행으로, 속성을 열로 펼쳐야 한다. SQL에서 이 피벗은 조건부 집계(conditional aggregation)로 한다.

    SELECT p.product_id,
       p.name,
       MAX(CASE WHEN a.attribute_name = 'CPU'           THEN a.attribute_value END) AS cpu,
       MAX(CASE WHEN a.attribute_name = '메모리(GB)'    THEN a.attribute_value END) AS memory_gb,
       MAX(CASE WHEN a.attribute_name = '저장 용량(GB)' THEN a.attribute_value END) AS storage_gb
FROM product p
JOIN product_attribute a ON a.product_id = p.product_id
WHERE p.category = 'LAPTOP'
GROUP BY p.product_id, p.name
ORDER BY p.product_id;

    2번 상품 그룹이 어떻게 한 행이 되는지 추적해 보자. 조인 결과에서 2번 상품의 행은 네 개다. 각 행에 대해 세 CASE 식을 계산하면, 속성 이름이 일치하는 식만 값을 내고 나머지는 ELSE가 없으므로 NULL이 된다.

    (2, 메모리(GB), 16)NULL16NULL
    (2, 저장 용량(GB), 512)NULLNULL512

    MAX()는 NULL을 무시하므로 각 열에서 하나뿐인 NULL 아닌 값이 그대로 남는다. 기본 키가 상품마다 속성 하나에 행 하나만 허용하므로 그룹 안에서 NULL 아닌 값은 많아야 하나이고, 그래서 MAX는 사실상 "그 값 하나를 고르는" 역할만 한다. 속성이 아예 없으면 MAX는 NULL을 돌려준다. 무게 행은 어느 식에도 해당하지 않아 결과에서 사라진다. 최종 결과는 다음과 같다.

    +------------+------------------------+------+-----------+------------+
| product_id | name                   | cpu  | memory_gb | storage_gb |
+------------+------------------------+------+-----------+------------+
|          2 | 경량 노트북 14    | i5   | 16        | 512        |
|          3 | 게이밍 노트북 16 | i7   | 32        | 1024       |
|          4 | 보급형 노트북 15 | i3   | 8         | 256        |
+------------+------------------------+------+-----------+------------+

    여기서 피벗의 근본적인 제약 하나가 드러난다. 결과의 열 이름과 개수는 SQL 문장 안에 상수로 적혀 있다. SQL 문장의 결과 집합 모양은 문장을 해석하는 시점에 정해지며, JDBC의 ResultSetMetaData가 실행 전에 열 정보를 알려 줄 수 있는 것도 그 때문이다. 속성이 데이터로 바뀌었는데 결과 열은 여전히 코드에 고정되어 있으니, 새 속성을 목록 표에 넣으려면 SQL을 고쳐야 한다. 이를 피하려면 애플리케이션이 속성 목록을 먼저 읽고 CASE 식을 그 개수만큼 만들어 SQL을 생성해야 한다. 이때 속성 이름을 SQL 식별자(별칭)로 이어 붙이면 SQL 주입의 통로가 되므로, 값 비교에는 바인드 변수를 쓰고 별칭은 col1, col2처럼 코드가 정한 이름을 쓰는 것이 안전하다. 더 흔한 방법은 피벗을 아예 SQL에서 하지 않고, 세로 결과를 받아 애플리케이션에서 맵으로 조립하는 것이다.

    조건부 집계 대신 속성마다 LEFT JOIN을 하나씩 거는 방식도 있다.

    SELECT p.product_id, p.name,
       c.attribute_value AS cpu,
       m.attribute_value AS memory_gb,
       s.attribute_value AS storage_gb
FROM product p
LEFT JOIN product_attribute c ON c.product_id = p.product_id AND c.attribute_name = 'CPU'
LEFT JOIN product_attribute m ON m.product_id = p.product_id AND m.attribute_name = '메모리(GB)'
LEFT JOIN product_attribute s ON s.product_id = p.product_id AND s.attribute_name = '저장 용량(GB)'
WHERE p.category = 'LAPTOP'
ORDER BY p.product_id;

    각 LEFT JOIN은 기본 키 (product_id, attribute_name) 전체에 대한 등호 조건이므로 상품마다 많아야 한 행을 찾는 기본 키 조회가 된다. LEFT인 이유는 속성이 없는 상품도 목록에서 빠지지 않게 하기 위해서다. 결과는 위와 같지만, 펼칠 속성이 하나 늘 때마다 같은 테이블이 한 번 더 조인에 참여한다. 속성 30개를 펼치면 테이블 참조가 31개인 조인이 된다. 이 차이가 옵티마이저에게 무엇을 뜻하는지는 뒤에서 다시 본다.

    EAV 실습 2: 속성으로 상품 찾기

    속성을 저장하고 보여 주는 것보다 어려운 것은 속성으로 찾는 것이다. 조건 하나는 쉽다.

    SELECT product_id
FROM product_attribute
WHERE attribute_name = '색상' AND attribute_value = '검정';

    보조 인덱스 (attribute_name, attribute_value)의 두 열 모두에 등호가 걸리므로 인덱스에서 한 구간만 읽는다. 게다가 InnoDB의 보조 인덱스 레코드에는 기본 키 열 가운데 인덱스에 없는 열, 여기서는 product_id가 함께 들어 있다. 그래서 이 쿼리는 클러스터형 인덱스를 다시 찾아갈 필요 없이 보조 인덱스만 읽고 끝난다(커버링 인덱스).

    조건이 둘 이상이면: 셀프 조인과 관계 나눗셈

    "CPU가 i7이고 메모리가 32GB인 노트북"은 조건이 두 개다. 넓은 테이블이라면 WHERE cpu = 'i7' AND memory_gb = 32로 끝나지만, EAV에서는 두 조건이 서로 다른 행에 대한 조건이다. 한 행이 동시에 CPU 행이면서 메모리 행일 수는 없으므로, 다음처럼 쓰면 결과는 언제나 비어 있다.

    -- 잘못된 쿼리: 어떤 행도 두 조건을 동시에 만족하지 못한다
SELECT product_id FROM product_attribute
WHERE attribute_name = 'CPU' AND attribute_value = 'i7'
  AND attribute_name = '메모리(GB)' AND attribute_value = '32';

    방법은 두 가지다. 첫째는 조건마다 테이블을 한 번씩 참조하는 셀프 조인이다.

    SELECT c.product_id
FROM product_attribute c
JOIN product_attribute m
  ON m.product_id = c.product_id
 AND m.attribute_name = '메모리(GB)'
 AND m.attribute_value = '32'
WHERE c.attribute_name = 'CPU'
  AND c.attribute_value = 'i7';

    둘째는 조건 중 하나라도 맞는 행을 모은 뒤, 상품별로 몇 개의 조건을 맞췄는지 세는 방법이다. "주어진 조건 집합을 모두 만족하는 엔티티를 찾는" 이 연산을 관계 대수에서는 관계 나눗셈(relational division)이라 부른다.

    SELECT product_id
FROM product_attribute
WHERE (attribute_name = 'CPU'        AND attribute_value = 'i7')
   OR (attribute_name = '메모리(GB)' AND attribute_value = '32')
GROUP BY product_id
HAVING COUNT(*) = 2;

    추적해 보면, WHERE를 통과하는 행은 (3, CPU, i7)과 (3, 메모리(GB), 32) 두 개뿐이다. 2번과 4번 상품은 CPU도 메모리도 조건에 맞지 않아 한 행도 통과하지 못한다. 그룹은 3번 하나이고 개수가 2이므로 3번이 결과다. MySQL 8.4.13·8.0.46에서 실행하면 앞의 잘못된 쿼리는 빈 결과를, 셀프 조인과 이 쿼리는 모두 3 한 행을 돌려준다. 이 쿼리가 옳은 이유는 기본 키가 상품마다 속성 하나에 행 하나를 보장하기 때문이다. 만약 한 상품이 같은 속성에 여러 값을 가질 수 있는 구조라면(예: CPU 행이 두 개), 한 조건이 두 번 세어져 COUNT(*) = 2가 조건 하나만 맞춘 상품도 통과시킨다. 그때는 COUNT(DISTINCT attribute_name)으로 세어야 한다. EAV 쿼리의 정확성이 키 설계에 직접 기대고 있다는 좋은 예다.

    셀프 조인은 조건 수만큼 테이블 참조가 늘고, 관계 나눗셈은 테이블을 한 번만 읽는 대신 그룹핑이 필요하다. 어느 쪽이든 넓은 테이블의 AND 한 줄과 비교하면 쿼리를 쓰는 사람과 옵티마이저 모두에게 일이 늘어난다.

    숫자 범위 검색: 문자열 열에 숫자를 담으면

    이번에는 "메모리 16GB 이상"을 찾아보자. 값 열이 VARCHAR이므로 처음에는 이렇게 쓰기 쉽다.

    SELECT product_id, attribute_value
FROM product_attribute
WHERE attribute_name = '메모리(GB)' AND attribute_value >= '16';

    MySQL 문서의 비교 규칙에 따르면 두 피연산자가 모두 문자열이면 문자열로 비교한다. 문자열 비교는 앞 글자부터 하나씩 견주므로 '32'는 첫 글자 3이 1보다 커서 '16'보다 크고, '8'도 첫 글자 8이 1보다 커서 '16'보다 크다. 결과는 2번(16), 3번(32), 그리고 8GB인 4번이다. 반대로 값이 '128'이었다면 둘째 글자 2가 6보다 작아 '16'보다 작다고 판정되어 빠졌을 것이다. 정렬도 마찬가지다. 저장 용량을 ORDER BY attribute_value로 정렬하면 '1024', '256', '512' 순서가 된다. 숫자로는 가장 큰 1024가 맨 앞에 온다.

    그렇다면 상수를 숫자로 쓰면 어떨까.

    SELECT product_id, attribute_value
FROM product_attribute
WHERE attribute_name = '메모리(GB)' AND attribute_value >= 16;

    문서의 규칙상 문자열과 숫자를 비교하면, 앞의 어느 규칙에도 해당하지 않는 "그 밖의 경우"로 두 값을 배정밀도 부동소수점 수로 바꿔 비교한다. 그래서 이 쿼리는 2번과 3번만 돌려주어 결과는 맞다. 그러나 두 가지 대가가 있다. 첫째, 문서는 문자열 열을 숫자와 비교하면 그 열의 인덱스로 값을 빠르게 찾을 수 없다고 명시한다. '1', ' 1', '1a'처럼 서로 다른 많은 문자열이 같은 숫자 1로 바뀌므로, 인덱스의 정렬 순서(문자열 순서)가 숫자 순서와 맞지 않기 때문이다. 이 쿼리는 인덱스의 첫 열 attribute_name으로 메모리 행들의 구간은 찾지만, 그 안에서 값 조건은 한 행씩 변환해 검사한다. 둘째, 변환은 관대하다. 문서의 예처럼 '6x'는 6으로 바뀌어 비교된다. 무게 조건 attribute_value <= 1500을 걸면 4번 상품의 '1,650'은 앞부분 숫자만 읽혀 1이 되고, 1,650g짜리 노트북이 "1.5kg 이하" 결과에 끼어든다. 오류가 나는 것이 아니라 조용히 틀린 답이 나온다. MySQL 8.4.13·8.0.46에서 이 조건을 실행하면 4번('1,650')과 2번('1120')이 나오고, --show-warnings로 실행해도 경고 하나 남지 않는다. 같은 문자열을 SELECT '1,650' + 0처럼 식에서 바꾸면 1이 나오면서 Warning (Code 1292): Truncated incorrect DOUBLE value: '1,650' 경고가 붙는데, WHERE 절의 비교에서는 그 경고조차 없었다.

    CAST(attribute_value AS UNSIGNED) >= 16처럼 명시적으로 변환해도 사정은 같다. 열에 함수를 씌운 조건은 인덱스 구간으로 바꿀 수 없고, 숫자가 아닌 문자열은 여전히 무언가로 변환된다. 문제의 뿌리는 쿼리가 아니라 타입이 다른 값들을 한 문자열 열에 담은 저장 구조에 있다. 이것이 뒤에서 값 열을 타입별로 나누는 이유다.

    조건비교 방식결과(메모리)값 조건에 인덱스 사용
    attribute_value >= '16'문자열 비교2, 3, 4(틀림: 8GB 포함)가능하지만 순서가 틀림
    attribute_value >= 16부동소수점 변환 후 비교2, 3불가(행마다 변환)
    CAST(attribute_value AS UNSIGNED) >= 16함수 적용 후 비교2, 3불가(열에 함수)

    표의 결과는 MySQL 8.4.13과 8.0.46에서 실행해 확인한 것이다. 인덱스 사용 차이는 EXPLAIN의 key_len에 드러난다. 위가 문자열 상수, 아래가 숫자 상수인 쿼리다. 문자열 상수는 range 접근에 key_len 1224, 곧 인덱스의 두 열을 모두 구간에 쓰고, 숫자 상수는 ref 접근에 key_len 202, 곧 attribute_name(VARCHAR(50) × 4바이트 + 길이 2바이트)까지만 쓴다. CAST를 씌운 조건의 계획도 숫자 상수와 같은 ref, key_len 202였다. rows와 filtered 같은 추정치는 실행 환경과 통계에 따라 달라진다.

    한 층 아래: EAV 행이 InnoDB 페이지에 놓이는 모양

    EAV의 비용을 감으로 말하지 않으려면 행 하나가 디스크와 메모리에서 몇 바이트를 차지하는지 따져 봐야 한다. InnoDB 테이블은 기본 키 순서로 정렬된 B+Tree, 곧 클러스터형 인덱스(clustered index) 자체에 행을 저장한다. product_attribute의 기본 키는 (product_id, attribute_name)이므로 리프 페이지에는 레코드가 상품 번호 순서로, 같은 상품 안에서는 속성 이름 순서로 놓인다.

    클러스터형 인덱스 (PRIMARY KEY (product_id, attribute_name)) 의 리프 페이지들

  ┌──────────────── 리프 페이지 ────────────────┐   ┌──────────── 리프 페이지 ────────────┐
  │ (1,사이즈,L) (1,소재,면 100%) (1,색상,검정)  │ ⇄ │ (3,CPU,i7) (3,메모리(GB),32) ...     │
  │ (2,CPU,i5) (2,메모리(GB),16)                 │   │ (4,CPU,i3) (4,메모리(GB),8) ...      │
  │ (2,무게(g),1120) (2,저장 용량(GB),512)       │   │                                      │
  └──────────────────────────────────────────────┘   └──────────────────────────────────────┘
   같은 상품의 속성 행은 서로 이웃한다 → 한 상품 조회 = 짧은 구간 하나

보조 인덱스 idx_pa_name_value (attribute_name, attribute_value) + 기본 키의 나머지 열(product_id)

  (CPU,i3,4) (CPU,i5,2) (CPU,i7,3) ... (메모리(GB),16,2) (메모리(GB),32,3) (메모리(GB),8,4) ...
   같은 속성의 행은 서로 이웃한다 → 속성으로 찾기 = 짧은 구간 하나
   (값은 문자열 순서로 정렬되어 '8'이 '32' 뒤에 온다)

    그림의 속성 이름 순서는 MySQL 8.4.13·8.0.46의 기본 콜레이션 utf8mb4_0900_ai_ci에서 ORDER BY product_id, attribute_name으로 읽은 실제 순서다(1번 상품은 사이즈, 소재, 색상 순). 이 순서는 열의 콜레이션이 정한다. 중요한 것은 두 인덱스가 서로 다른 축으로 행을 모은다는 점이다. 클러스터형 인덱스는 상품 축으로 모으므로 "한 상품의 모든 속성"을 읽는 상세 화면에 맞고, 보조 인덱스는 속성 축으로 모으므로 "어떤 속성이 어떤 값인 상품"을 찾는 검색에 맞는다. 기본 키를 대리 키(value_id BIGINT AUTO_INCREMENT)로 두면 행이 삽입 순서로 놓이므로, 상품 등록 뒤 나중에 추가된 속성은 멀리 떨어진 페이지에 놓이고, "한 상품에 속성 하나"를 지키려면 UNIQUE (product_id, attribute_name) 인덱스를 따로 만들어야 한다. EAV 값 테이블에서는 자연 키 (엔티티, 속성)을 기본 키로 삼는 편이 저장 위치와 무결성 두 측면에서 모두 이득이다.

    사실 하나에 몇 바이트가 드는가

    MySQL 문서가 설명하는 COMPACT 계열 행 형식 규칙으로 "1번 상품의 색상은 검정"이라는 사실 하나의 비용을 계산해 보자. 규칙은 다음과 같다. 인덱스 레코드마다 5바이트 헤더가 있고 그 앞에 가변 길이 헤더가 올 수 있다. 가변 길이 헤더에는 NULL 비트 벡터(NULL 허용 열이 N개면 CEILING(N/8)바이트)와, NULL이 아닌 가변 길이 열마다 1~2바이트의 길이 정보가 들어간다. 길이가 2바이트가 되는 것은 값 일부가 오버플로 페이지에 있거나, 최대 길이가 255바이트를 넘으면서 실제 길이가 127바이트를 넘을 때뿐이다. 클러스터형 인덱스 레코드에는 사용자 열 외에 6바이트 트랜잭션 ID(DB_TRX_ID)와 7바이트 롤 포인터(DB_ROLL_PTR)가 더 있다. 보조 인덱스 레코드에는 이 숨은 열이 없고, 대신 인덱스에 없는 기본 키 열이 들어간다. 한글 음절은 utf8mb4에서 글자당 3바이트다.

    구성 요소클러스터형 인덱스 레코드보조 인덱스 레코드
    레코드 헤더55
    NULL 비트 벡터 (NULL 허용 열 0개)00
    가변 길이 열의 길이 정보2 (이름, 값 각 1)2 (이름, 값 각 1)
    product_id BIGINT88 (기본 키 열로 덧붙음)
    attribute_name '색상'66
    attribute_value '검정'66
    DB_TRX_ID + DB_ROLL_PTR13없음
    합계40바이트27바이트

    넓은 테이블이라면 같은 사실은 color 열의 값 6바이트와 길이 정보 1바이트, 합쳐 7바이트다(NULL 허용 열이라면 이미 있는 NULL 비트맵의 비트 하나). EAV에서는 두 인덱스를 합쳐 67바이트, 거의 열 배다. 그것도 페이지 디렉터리 슬롯이나 페이지 안의 빈 공간처럼 레코드 바깥의 비용은 빼고 센 최소치다. 속성 이름 문자열이 모든 행에 반복되는 것도 눈에 띈다. '저장 용량(GB)'은 한글 네 글자 12바이트에 공백 1바이트, (GB) 4바이트로 17바이트인데, 이 문자열이 저장 용량 값이 있는 모든 상품마다, 그것도 두 인덱스에 한 번씩 들어간다. 속성을 정수 ID로 바꾸면 이 부분이 4바이트로 줄어드는데, 이것이 다음 절에서 속성 정의 테이블을 두는 이유 중 하나다.

    쓰기 경로에서도 차이가 난다. 노트북 하나의 사양 네 개를 고치면 넓은 테이블에서는 레코드 하나가 바뀌고 언두 로그 레코드도 하나 생긴다. EAV에서는 레코드 네 개가 바뀌고, 각각에 대해 이전 값을 담은 언두 로그 레코드와 행 잠금이 생기며, 값이 인덱스에 포함되어 있으므로 보조 인덱스 레코드도 바뀐다. 행 수가 많아지면 버퍼 풀에 올려 둬야 하는 페이지도 그만큼 많아진다. 상품 100만 개에 평균 속성 20개면 EAV 테이블은 2,000만 행이다. EAV는 공간과 쓰기 비용을 내고 스키마의 유연성을 사는 거래다.

    클러스터형 인덱스는 같은 상품의 속성 행을, 보조 인덱스는 같은 속성의 행을 이웃하게 모은다는 것과, 레코드 하나에 붙는 숨은 비용을 보여 준다. 위아래 두 개의 B+Tree를 단순화한 그림. 위쪽 트리 제목 "클러스터형 인덱스 (product_id, attribute_name)": 루트 상자 하나 아래 리프 상자 세 개가 가로로 연결(양방향 화살표). 각 리프 상자 안에 작은 레코드 칸들이 있고, 같은 상품의 칸은 같은 색으로 묶임(상품 1은 연두, 상품 2는 하늘색, 상품 3은 살구색). 리프 위에 라벨 "같은 상품의 속성 = 이웃". 레코드 칸 하나를 확대한 말풍선에 "헤더 5B", "길이 2B", "product_id 8B", "이름·값", "트랜잭션 ID 6B + 롤 포인터 7B". 아래쪽 트리 제목 "보조 인덱스 (attribute_name, attribute_value)": 리프 칸들이 속성별 색(CPU는 보라, 메모리는 주황)으로 묶이고 라벨 "같은 속성 = 이웃", 각 칸 끝에 작은 태그 "+ product_id". 평면 스타일, 흰 배경. 상세 조회는 상품 축(클러스터형 인덱스), 검색은 속성 축(보조 인덱스)을 탄다. 사실 하나가 두 인덱스에 모두 레코드를 남긴다.

    EAV 패턴 개선: 속성 정의 테이블

    실습에서 만든 단순한 EAV에는 구멍이 여럿 보였다. 하나씩 짚어 보면 다음과 같다.

    • 속성 이름이 자유 문자열이다. 누군가 '메모리 (GB)'처럼 공백을 하나 더 넣거나 'RAM'이라고 쓰면 데이터베이스는 그것을 새 속성으로 받아들인다. 검색 조건 attribute_name = '메모리(GB)'는 그 상품을 찾지 못한다.
    • 값에 타입이 없다. 숫자, 날짜, 선택지가 모두 문자열로 저장되어 비교와 정렬이 틀리고, 값 조건에 인덱스를 못 쓰며, '1,650' 같은 값이 들어와도 막지 못한다.
    • 속성에 딸린 정보를 둘 곳이 없다. 단위는 이름의 괄호 안에 박혔고, 화면 표시 순서, 어느 카테고리에서 쓰는 속성인지, 필수인지, 검색 필터에 노출할지를 기록할 곳이 없다.
    • 허용 값 목록이 없다. 사이즈는 S, M, L, XL 가운데 하나여야 하지만 '라지'도 들어간다.
    • 속성 이름 문자열이 모든 값 행과 두 인덱스에 반복 저장된다.

    다섯 가지 모두 "속성"이 독립된 개념인데도 이름 문자열 하나로만 존재한다는 데서 나온다. 해법은 01회의 공통 코드에서 값 목록을 테이블로 꺼냈던 것과 같은 방향이다. 속성을 자기 테이블을 가진 엔티티로 꺼내고, 값 행은 속성을 이름이 아니라 식별자로 참조하게 한다. 그러면 넓은 테이블에서 열 정의(DDL)가 하던 일, 곧 앞의 표에서 여기저기로 흩어졌던 일이 속성 정의 테이블의 행으로 다시 모인다. 데이터베이스가 스키마로 관리하던 메타데이터를, 우리가 만든 작은 데이터 사전(data dictionary)이 데이터로 관리하게 되는 셈이다.

    CREATE TABLE attribute_definition (
  attribute_id   INT          NOT NULL AUTO_INCREMENT,
  code           VARCHAR(50)  NOT NULL,   -- 프로그램이 쓰는 바뀌지 않는 식별자: memory_gb
  display_name   VARCHAR(50)  NOT NULL,   -- 화면 문구: 메모리
  data_type      VARCHAR(10)  NOT NULL,   -- STRING, NUMBER, DATE, OPTION
  unit           VARCHAR(10)  NULL,       -- GB, g, kg
  searchable     BOOLEAN      NOT NULL DEFAULT FALSE,
  PRIMARY KEY (attribute_id),
  UNIQUE KEY uk_attr_code (code),
  UNIQUE KEY uk_attr_id_type (attribute_id, data_type),
  CONSTRAINT ck_attr_type CHECK (data_type IN ('STRING', 'NUMBER', 'DATE', 'OPTION'))
);

CREATE TABLE category_attribute (
  category       VARCHAR(20)  NOT NULL,
  attribute_id   INT          NOT NULL,
  required       BOOLEAN      NOT NULL DEFAULT FALSE,
  display_order  INT          NOT NULL,
  PRIMARY KEY (category, attribute_id),
  CONSTRAINT fk_ca_attr FOREIGN KEY (attribute_id)
      REFERENCES attribute_definition (attribute_id)
);

CREATE TABLE attribute_option (
  attribute_id   INT          NOT NULL,
  option_id      INT          NOT NULL,
  label          VARCHAR(50)  NOT NULL,
  display_order  INT          NOT NULL,
  PRIMARY KEY (attribute_id, option_id),
  CONSTRAINT fk_ao_attr FOREIGN KEY (attribute_id)
      REFERENCES attribute_definition (attribute_id)
);

CREATE TABLE product_attribute_value (
  product_id     BIGINT        NOT NULL,
  attribute_id   INT           NOT NULL,
  data_type      VARCHAR(10)   NOT NULL,   -- 정의 테이블의 타입을 복사해 둔다
  value_string   VARCHAR(255)  NULL,
  value_number   DECIMAL(18,4) NULL,
  value_date     DATE          NULL,
  option_id      INT           NULL,
  PRIMARY KEY (product_id, attribute_id),
  KEY idx_pav_string (attribute_id, value_string),
  KEY idx_pav_number (attribute_id, value_number),
  KEY idx_pav_date   (attribute_id, value_date),
  KEY idx_pav_option (attribute_id, option_id),
  CONSTRAINT fk_pav_product FOREIGN KEY (product_id)
      REFERENCES product (product_id),
  CONSTRAINT fk_pav_attr_type FOREIGN KEY (attribute_id, data_type)
      REFERENCES attribute_definition (attribute_id, data_type),
  CONSTRAINT fk_pav_option FOREIGN KEY (attribute_id, option_id)
      REFERENCES attribute_option (attribute_id, option_id),
  CONSTRAINT ck_pav_one_value CHECK (
        (data_type = 'STRING') = (value_string IS NOT NULL)
    AND (data_type = 'NUMBER') = (value_number IS NOT NULL)
    AND (data_type = 'DATE')   = (value_date   IS NOT NULL)
    AND (data_type = 'OPTION') = (option_id    IS NOT NULL))
);

    네 테이블의 역할을 차례로 보자. attribute_definition은 속성 하나에 행 하나다. code는 프로그램과 검색 조건이 쓰는 바뀌지 않는 식별자이고, display_name은 운영 중에 언제든 고칠 수 있는 화면 문구다. 01회에서 코드 값과 표시 이름을 나눈 것과 같은 이유다. data_type은 이 속성의 값이 어느 값 열에 들어가야 하는지를, unit은 이름의 괄호 안에 박혀 있던 단위를 담는다. 이제 화면에 "메모리"를 "램"으로 바꿔 보여 주고 싶으면 display_name 한 칸을 고치면 되고, 이미 저장된 값 행 수백만 개는 건드릴 필요가 없다. 값 행은 이름이 아니라 attribute_id를 들고 있기 때문이다.

    category_attribute는 카테고리와 속성의 다대다 관계다. 노트북에는 CPU·메모리·저장 용량·무게가, 의류에는 색상·사이즈·소재가 연결된다. 필수 여부와 표시 순서를 속성 정의가 아니라 이 연결 테이블에 둔 데는 이유가 있다. 그것은 속성 자체의 성질이 아니라 "이 카테고리에서 이 속성"의 성질이다. 같은 무게 속성이 노트북에서는 선택이고 택배 규격이 중요한 가구에서는 필수일 수 있다. 예제의 product에는 카테고리 테이블이 없어 category를 문자열로 두었지만, 카테고리 테이블이 있다면 이 열도 그 테이블을 참조하게 한다. attribute_option은 선택형 속성의 허용 값 목록이고, 기본 키가 (attribute_id, option_id)이므로 선택지는 자기 속성 안에서만 식별된다. 마지막으로 product_attribute_value가 값 행이다. 값 열이 타입별로 나뉘었고, 속성은 4바이트 정수로 참조한다.

    값 행이 상품, 속성 정의, 선택지를 각각 어떤 키로 참조하는지, 특히 (attribute_id, data_type)과 (attribute_id, option_id) 두 복합 외래 키를 보여 준다. 흰 배경의 ER 다이어그램. 가운데에 큰 상자 "product_attribute_value"(필드 목록: "product_id PK", "attribute_id PK", "data_type", "value_string / value_number / value_date / option_id"). 왼쪽에 상자 "product"(필드 "product_id PK", "category"). 오른쪽 위에 상자 "attribute_definition"(필드 "attribute_id PK", "code", "data_type", "unit"). 오른쪽 아래에 상자 "attribute_option"(필드 "attribute_id PK", "option_id PK", "label"). 위쪽 가운데에 상자 "category_attribute"(필드 "category PK", "attribute_id PK", "required"). 화살표: 가운데 상자에서 product로 라벨 "product_id", attribute_definition으로 굵은 파란 화살표 라벨 "(attribute_id, data_type)", attribute_option으로 굵은 주황 화살표 라벨 "(attribute_id, option_id)". category_attribute에서 attribute_definition으로 가는 가는 화살표. 가운데 상자 아래에 작은 메모 상자 "CHECK: 타입에 맞는 값 열 하나만". 평면 스타일, 까마귀 발 표기 없이 단순한 화살표. 값 행은 타입 복사본과 복합 외래 키로 속성 정의와 묶이고, 타입별 값 열 가운데 하나만 채운다는 규칙은 CHECK 제약이 지킨다.

    값 행이 타입을 복사해 들고 있는 이유

    값 행의 data_type은 정의 테이블에 이미 있는 정보를 다시 적은 것이다. 이 중복은 의도적이다. "NUMBER 속성이면 value_number만 채운다"는 규칙을 데이터베이스가 검사하게 하려면 CHECK 제약이 필요한데, MySQL 문서에 따르면 CHECK 식에는 다른 테이블의 열을 쓸 수 없고 서브쿼리도 허용되지 않는다. CHECK는 자기 행만 본다. 그래서 타입을 행 안에 가져와야 하고, 가져온 복사본이 원본과 같다는 것은 복합 외래 키 (attribute_id, data_type)이 보장한다. 정의 테이블에 (2, 'NUMBER')는 있어도 (2, 'STRING')은 없으므로, 복사본을 틀리게 적은 행은 외래 키에서 걸린다. 외래 키가 참조할 수 있도록 정의 테이블에는 UNIQUE (attribute_id, data_type)를 두었다. attribute_id만으로 이미 유일하므로 이 제약은 새 규칙을 더하지 않고 참조할 인덱스만 제공한다. 자식 쪽에는 (attribute_id, data_type)으로 시작하는 인덱스가 없으므로 MySQL이 외래 키를 만들 때 그런 인덱스를 자동으로 하나 만든다. MySQL 8.4.13·8.0.46에서 테이블을 만든 뒤 SHOW CREATE TABLE을 보면 이 인덱스가 외래 키 이름 그대로 KEY `fk_pav_attr_type` (`attribute_id`,`data_type`)로 나타난다.

    01회에서는 같은 목적에 그룹 상수를 담은 저장 생성 열을 썼다. 여기서는 생성 열을 쓸 수 없다. 생성 열의 식도 다른 테이블을 읽을 수 없는데, 속성마다 타입이 다르므로 상수 하나로 적을 수도 없기 때문이다. 그래서 애플리케이션이 정의를 보고 값을 채우고, 데이터베이스는 외래 키로 그것을 검증하는 분업이 된다.

    CHECK는 FALSE만 거부한다

    ck_pav_one_value를 (조건) = (조건)의 모양으로 쓴 데도 이유가 있다. MySQL 문서는 CHECK 조건이 각 행에 대해 TRUE 또는 UNKNOWN이어야 하며 FALSE일 때만 위반이라고 정의한다. NULL이 끼어 UNKNOWN이 되는 식은 검사를 통과한다는 뜻이다. 여기서 data_type은 NOT NULL이고 IS NOT NULL은 언제나 TRUE나 FALSE를 내므로, MySQL에서 각 비교의 양쪽은 1 또는 0이고 결과도 1 또는 0이다. 식 전체가 UNKNOWN이 될 길이 없다.

    같은 규칙을 무심코 (data_type = 'OPTION') = (option_id > 0)처럼 쓰면 구멍이 생긴다. OPTION 행인데 option_id가 NULL이면 option_id > 0이 NULL이 되고, 1 = NULL도 NULL이므로 그 줄은 UNKNOWN이다. AND로 이어진 나머지 줄이 모두 TRUE면 식 전체가 UNKNOWN이 되어, 막으려던 바로 그 행이 통과한다. 열이 NULL을 허용한다면 CHECK 식은 "NULL일 때 무엇이 되는가"를 따로 확인해야 한다.

    NULL은 외래 키에서도 비슷하게 작동한다. fk_pav_option은 (attribute_id, option_id) 복합 외래 키인데, STRING·NUMBER·DATE 행에서는 option_id가 NULL이다. MySQL 문서는 MySQL이 사실상 표준 SQL의 MATCH SIMPLE 의미를 구현한다고 설명한다. 외래 키의 열이 전부 또는 일부라도 NULL이면 부모 테이블에 맞는 행이 없어도 자식 행을 넣을 수 있다. 그래서 선택형이 아닌 행은 선택지 외래 키 검사를 자연스럽게 건너뛰고, 우리가 원하던 동작이 된다. 그러나 같은 이유로 외래 키만으로는 "OPTION 행은 반드시 선택지를 가진다"를 지킬 수 없다. 그 빈틈을 CHECK의 OPTION 줄이 메운다. 외래 키와 CHECK가 각자 NULL을 어떻게 다루는지 알아야 둘을 맞물려 쓸 수 있다.

    데이터베이스가 지킬 수 없는 규칙

    여기까지 와도 데이터베이스가 지키지 못하는 규칙이 남는다. 첫째는 필수 속성이다. "노트북에는 CPU 값이 반드시 있어야 한다"는 규칙은 어떤 행의 값이 아니라 행이 존재하는지에 대한 규칙이다. CHECK는 자기 행만 보고 서브쿼리를 쓸 수 없으므로 다른 행의 존재를 확인하지 못한다. 넓은 테이블에서 NOT NULL 한 단어로 되던 일이 EAV에서는 애플리케이션의 검증 코드가 된다. 그 코드를 거치지 않는 경로(운영자의 직접 SQL, 다른 배치)를 대비해 다음과 같은 점검 쿼리를 정기적으로 돌리는 것이 현실적인 보완이다.

    -- 필수 속성이 빠진 상품 찾기 (안티 조인)
SELECT p.product_id, ca.attribute_id
FROM product p
JOIN category_attribute ca
  ON ca.category = p.category
 AND ca.required = TRUE
LEFT JOIN product_attribute_value v
  ON v.product_id = p.product_id
 AND v.attribute_id = ca.attribute_id
WHERE v.product_id IS NULL;

    상품마다 그 카테고리의 필수 속성 행을 만들고, 값 행이 붙지 않은 조합만 남긴다. 예제 데이터로 추적하면, 1번 티셔츠는 필수인 색상(5)과 사이즈(6)가 모두 있고 2번 노트북도 필수인 1·2·3번 속성이 모두 있어 결과에 나오지 않는다. 값 행이 하나도 없는 3번 노트북은 (3, 1), (3, 2), (3, 3)으로, 선택 속성인 무게(4)만 있는 4번 노트북은 (4, 1), (4, 2), (4, 3)으로 나온다. MySQL 8.4.13·8.0.46에서 실행해도 이 여섯 행이 나온다(ORDER BY가 없어 행 순서는 두 버전이 달랐다). 이 쿼리의 LEFT JOIN은 기본 키 (product_id, attribute_id) 전체에 대한 등호라 조합마다 기본 키 조회 한 번이다. EXPLAIN에서도 v는 eq_ref, key는 PRIMARY이고 Extra에 Not exists가 붙는다. 짝이 되는 행을 하나 찾으면 그 조합은 결과에서 빠지므로 더 찾지 않는다는 뜻이다.

    둘째는 속성이 상품의 카테고리에 속하는지다. 지금 구조에서는 티셔츠에 메모리 값을 넣어도 막을 장치가 없다. 이것은 데이터베이스로 지킬 수 있지만 대가가 크다. 값 테이블에 category 열을 하나 더 복사해 두고, product에 UNIQUE (product_id, category)를 만든 뒤 (product_id, category)로 상품을, (category, attribute_id)로 category_attribute를 참조하는 외래 키 두 개를 거는 방식이다. 이렇게 하면 상품의 카테고리를 바꾸는 일이 값 행 전체와 얽힌다. 기본 참조 동작(InnoDB에서 NO ACTION은 RESTRICT와 같다)이면 값이 남아 있는 한 카테고리 변경이 즉시 거부되고, 연쇄 갱신을 걸면 새 카테고리에 없는 속성의 값 행이 두 번째 외래 키에 걸린다. 어느 쪽이든 카테고리 변경이 "값을 정리하고 옮기는" 명시적인 작업이 되므로, 그 엄격함이 업무에 맞는지를 보고 고른다.

    셋째는 속성별 값 범위다. "메모리는 1에서 512 사이"처럼 속성마다 다른 범위를 CHECK로 걸려면 속성 ID를 식 안에 상수로 박아야 한다. 범위를 정의 테이블의 열(min_value, max_value)로 두면 데이터로 관리할 수는 있지만, CHECK는 그 열을 읽을 수 없으므로 검사는 애플리케이션 몫이 된다. 넓은 테이블의 문제였던 "규칙이 바뀔 때마다 DDL"을 피하려고 EAV로 왔으니, 속성별 규칙은 데이터로 두고 애플리케이션이 검사하는 것이 이 구조의 자연스러운 귀결이다.

    속성의 타입을 바꾸려 하면

    운영 중에 CPU 속성을 자유 입력(STRING)에서 선택형(OPTION)으로 바꾸고 싶어졌다고 하자. UPDATE attribute_definition SET data_type = 'OPTION' WHERE attribute_id = 1은 거부된다. 값 행들이 (1, 'STRING')을 참조하고 있고, 참조 동작을 적지 않은 외래 키의 기본값은 InnoDB에서 부모 쪽 변경을 즉시 거부하는 NO ACTION이기 때문이다. ON UPDATE CASCADE를 걸면 되지 않을까 싶지만, MySQL 문서는 CHECK 제약에 쓰인 열에는 외래 키 참조 동작(ON UPDATE, ON DELETE)을 걸 수 없다고 명시한다. 값 행의 data_type은 ck_pav_one_value에 쓰이므로 연쇄 갱신을 지정할 수 없다. 설령 지정할 수 있었더라도 타입만 OPTION으로 바뀌고 값은 value_string에 남아 있으니 CHECK에 걸렸을 것이다. MySQL 8.4.13·8.0.46에서 위의 UPDATE와, fk_pav_attr_type을 지우고 ON UPDATE CASCADE를 붙여 다시 만드는 ALTER TABLE을 차례로 실행한 결과다.

    ERROR 1451 (23000): Cannot delete or update a parent row: a foreign key constraint fails (`m_db_design2_08`.`product_attribute_value`, CONSTRAINT `fk_pav_attr_type` FOREIGN KEY (`attribute_id`, `data_type`) REFERENCES `attribute_definition` (`attribute_id`, `data_type`))
ERROR 3823 (HY000): Column 'data_type' cannot be used in a check constraint 'ck_pav_one_value': needed in a foreign key constraint 'fk_pav_attr_type' referential action.

    이 거부는 불편이 아니라 보호다. 타입 변경은 기존 값을 새 형식으로 옮기는 데이터 마이그레이션이다. 선택지를 만들고, 각 값 행의 문자열을 선택지 ID로 바꾸고, 바꿀 수 없는 값(오타, 변형)을 사람이 정리해야 한다. 실무에서는 새 속성을 하나 만들어 값을 변환해 옮기고, 검증한 뒤 프로그램이 새 속성 코드를 보게 바꾸고, 옛 속성을 지우는 순서를 밟는다. 데이터베이스가 이 순서를 건너뛰지 못하게 막는 것이다.

    개선한 구조는 더 작은가

    속성 이름이 정수가 되었으니 공간도 줄었을 것 같지만, 행 하나만 보면 그렇지 않다. 앞의 계산과 같은 규칙으로 따지면, '저장 용량(GB)'의 17바이트는 attribute_id 4바이트로 줄었다. 대신 타입 복사본 'NUMBER' 6바이트와 길이 1바이트, NULL 허용 열 네 개를 위한 NULL 비트 벡터 1바이트(CEILING(4/8))가 붙고, 값은 DECIMAL(18,4)이 되었다. MySQL 문서의 규칙대로 DECIMAL은 정수부와 소수부를 따로 계산해 아홉 자리마다 4바이트를 쓰고 남은 자리는 1~4바이트를 쓰므로, 정수부 14자리는 4 + 3 = 7바이트, 소수부 4자리는 2바이트, 합쳐 9바이트다. 문자열 '512'의 3바이트보다 크다.

    더 큰 차이는 보조 인덱스다. 타입별 값 열마다 인덱스를 하나씩 두었고, 외래 키를 위해 자동으로 만들어진 인덱스까지 더하면 값 행 하나가 보조 인덱스 다섯 개에 레코드를 남긴다. 숫자 값 행은 idx_pav_string, idx_pav_date, idx_pav_option에서는 키가 NULL인 레코드가 된다. InnoDB 보조 인덱스는 키가 NULL인 행에도 레코드를 두기 때문이다. 결국 개선된 구조는 공간과 쓰기 비용을 더 내고, 그 대가로 타입 검사와 쓸모 있는 인덱스를 산다. 그 비용이 아깝다면 타입별로 값 테이블을 따로 두는 방법이 있다. product_attribute_number, product_attribute_string처럼 나누면 NULL 키 레코드도, 값이 하나만 채워졌는지 보는 CHECK도 필요 없다. 이때 타입 일치는 01회의 기법 그대로, 테이블마다 data_type VARCHAR(10) AS ('NUMBER') STORED 같은 상수 저장 생성 열을 두고 (attribute_id, data_type)로 정의 테이블을 참조하면 지킬 수 있다. 대신 한 상품의 속성을 모두 읽으려면 타입 수만큼 쿼리를 하거나 UNION ALL로 이어야 한다.

    개선된 구조로 다시 찾기

    이제 실습 2에서 실패했던 숫자 범위 검색을 다시 해 보자.

    -- 메모리 16GB 이상인 상품, 메모리 오름차순
SELECT v.product_id, v.value_number
FROM product_attribute_value v
WHERE v.attribute_id = 2
  AND v.value_number >= 16
ORDER BY v.value_number;

    idx_pav_number (attribute_id, value_number)의 첫 열에는 등호, 둘째 열에는 범위 조건이 걸린다. 인덱스에서 (2, 16)부터 attribute_id가 2인 마지막 레코드까지가 연속된 한 구간이므로, 옵티마이저는 이 구간 하나만 읽는다. 구간 안의 레코드는 value_number의 숫자 순서로 놓여 있다. 8, 16, 32, 128이 이 순서로 저장되므로 문자열 비교에서 128이 빠지고 8이 끼어들던 문제는 사라진다. 첫 열이 상수로 고정되어 있으니 구간을 읽는 순서가 곧 ORDER BY v.value_number의 순서이고, 별도의 정렬(filesort)이 필요 없다. 보조 인덱스 레코드에는 기본 키 열 product_id가 들어 있으므로 클러스터형 인덱스로 돌아갈 필요도 없다. 넓은 테이블에서 memory_gb 열에 인덱스를 만든 것과 거의 같은 접근이다. 차이는 인덱스 하나를 모든 숫자 속성이 나눠 쓴다는 점, 그래서 키 앞에 attribute_id가 붙는다는 점뿐이다. 위 예제 데이터로 MySQL 8.4.13에서 EXPLAIN을 보면 그대로다. idx_pav_number의 range 접근이고 key_len 14는 attribute_id 4바이트와 NULL 허용 DECIMAL(18,4) 9+1바이트, 곧 두 열을 모두 구간에 쓴다는 뜻이며, Extra에 Using filesort 없이 Using index만 있다. 결과는 2번 상품 16.0000 한 행이다.

    +----+-------------+-------+------------+-------+----------------------------------------------------------------------------+----------------+---------+------+------+----------+--------------------------+
| id | select_type | table | partitions | type  | possible_keys                                                              | key            | key_len | ref  | rows | filtered | Extra                    |
+----+-------------+-------+------------+-------+----------------------------------------------------------------------------+----------------+---------+------+------+----------+--------------------------+
|  1 | SIMPLE      | v     | NULL       | range | idx_pav_string,idx_pav_number,idx_pav_date,idx_pav_option,fk_pav_attr_type | idx_pav_number | 14      | NULL |    1 |   100.00 | Using where; Using index |

    프로그램에 숫자 ID를 박고 싶지 않다면 속성 코드로 정의 테이블을 조인한다.

    SELECT v.product_id, v.value_number
FROM attribute_definition d
JOIN product_attribute_value v
  ON v.attribute_id = d.attribute_id
WHERE d.code = 'memory_gb'
  AND v.value_number >= 16;

    d.code에는 유니크 인덱스가 있고 상수와 비교되므로, 옵티마이저는 d를 많아야 한 행인 const 테이블로 다룬다. const 테이블은 쿼리 시작 시점에 한 번 읽히고, 그 행의 열 값은 나머지 최적화에서 상수처럼 취급된다. 그래서 이 쿼리도 앞의 쿼리와 같은 idx_pav_number 구간 읽기가 될 수 있다. 다만 실제로 그 계획을 고르는지는 비용 추정에 달려 있었다. 노트북 상품 10만 개를 더해(값 행 400,306개, 메모리 값 행 100,001개 가운데 16 이상이 66,667개, 96 이상이 16,666개) MySQL 8.4.13과 8.0.46에서 EXPLAIN해 보면, 두 버전 모두 d는 uk_attr_code로 읽는 const 테이블이다. 조건을 v.value_number >= 96으로 바꾸면 v는 앞의 쿼리와 같은 idx_pav_number range 접근이 된다. 그러나 메모리 행 대부분이 걸리는 >= 16 그대로는 attribute_id만으로 idx_pav_string을 찾아 들어가고 value_number는 행마다 거르는 계획을 골랐다. 같은 데이터에서 attribute_id = 2를 직접 적은 앞의 쿼리는 >= 16에서도 idx_pav_number range를 골랐다. 위의 작은 예제 데이터에서도 두 쿼리의 계획은 같은 식으로 갈렸다. 다음은 10만 개 데이터에서 >= 16 조건의 EXPLAIN FORMAT=TREE 출력이다. 비용과 행 수 추정치는 실행 환경과 통계에 따라 달라진다.

    -> Filter: (v.value_number >= 16.0000)  (cost=8282 rows=66226)
    -> Index lookup on v using idx_pav_string (attribute_id='2')  (cost=8282 rows=198698)

    실무에서는 속성 정의를 애플리케이션 시작 시점이나 변경 시점에 메모리로 읽어 두고 코드 → ID 변환을 메모리에서 하는 경우가 많다. 정의는 적고 자주 읽히며 드물게 바뀌기 때문이다.

    조건이 둘 이상이면 여전히 셀프 조인이나 관계 나눗셈이 필요하다는 점은 바뀌지 않는다.

    -- CPU가 i7이고 메모리가 32GB 이상인 상품
SELECT c.product_id
FROM product_attribute_value c
JOIN product_attribute_value m
  ON m.product_id = c.product_id
 AND m.attribute_id = 2
 AND m.value_number >= 32
WHERE c.attribute_id = 1
  AND c.value_string = 'i7';

    이 쿼리를 실행하는 길은 둘이다. c를 먼저 읽는다면 idx_pav_string에서 (1, 'i7') 구간을 읽고, 찾은 상품마다 m을 기본 키 (product_id, 2)로 한 번씩 찾아 값이 32 이상인지 본다. m을 먼저 읽는다면 idx_pav_number에서 (2, 32) 이상 구간을 읽고, 상품마다 c를 기본 키 (product_id, 1)로 찾아 값이 'i7'인지 본다. 어느 쪽이 나은지는 각 구간에 행이 몇 개 있느냐에 달려 있다. i7 상품이 500개이고 32GB 이상 상품이 5만 개라면 앞의 순서가 기본 키 조회를 500번만 하므로 훨씬 싸다. 이 선택은 옵티마이저의 행 수 추정이 하고, 바로 그 추정이 EAV에서 약해지는 지점이다.

    앞의 10만 개 데이터는 i7 상품 500개, 32GB 이상 상품 50,000개로 만들었다. MySQL 8.4.13과 8.0.46에서 이 쿼리를 EXPLAIN하면 두 버전 모두 앞의 순서를 고른다. (1, 'i7')이 두 열 모두 상수인 구간이라 인덱스 다이브로 500행을 정확히 추정했다.

    조인할 테이블이 늘어날 때

    넓은 테이블에서 조건 다섯 개는 WHERE 절의 AND 다섯 개이고 테이블은 하나다. EAV에서 조건 다섯 개를 셀프 조인으로 풀면 테이블 참조가 다섯 개인 조인이 되고, 속성 30개를 LEFT JOIN으로 펼치면 31개짜리 조인이 된다. 옵티마이저는 조인 순서를 정해야 하는데, MySQL 문서는 조인 쿼리에서 옵티마이저가 살펴보는 실행 계획의 수가 참조하는 테이블 수에 대해 지수적으로 늘어나며, 테이블이 적을 때(대개 7~10개 미만)는 문제가 되지 않지만 그보다 큰 쿼리에서는 최적화 시간 자체가 서버 성능의 주된 병목이 될 수 있다고 설명한다. 이를 줄이는 장치가 optimizer_prune_level(행 수 추정을 근거로 일부 계획을 건너뜀, 기본으로 켜져 있다)과 optimizer_search_depth(미완성 계획을 얼마나 앞까지 내다볼지)다. MySQL 8.4.13·8.0.46 서버에서 조회한 값은 optimizer_prune_level이 1, optimizer_search_depth가 62였다. 건너뛰는 만큼 최적의 계획을 놓칠 수도 있다.

    한도도 있다. MySQL에서 한 조인이 참조할 수 있는 테이블은 최대 61개이고, 이 수에는 FROM 절의 파생 테이블이나 뷰가 바깥 쿼리에 병합되어 들어온 것도 포함된다. 속성을 열마다 LEFT JOIN으로 펼치는 방식은 속성 60개 남짓에서 이 벽에 닿는다. MySQL 8.4.13·8.0.46에서 같은 테이블을 61번 참조하는 조인은 실행되고, 62번 참조하면 ERROR 1116 (HY000): Too many tables; MySQL can only use 61 tables in a join으로 거부된다. 조건부 집계로 피벗하면 테이블 참조가 하나라서 이 문제를 피하는데, 이것이 앞의 두 피벗 방식 가운데 조건부 집계가 더 널리 쓰이는 실질적인 이유다.

    통계는 속성을 구별하지 못한다

    옵티마이저가 조인 순서와 접근 방법을 고르는 근거는 행 수 추정이다. 추정에 쓰이는 정보는 크게 두 가지다. 하나는 인덱스 다이브(index dive)다. 상수로 정해진 구간이 있으면 옵티마이저는 구간의 양 끝으로 인덱스를 직접 내려가 그 사이의 행 수를 추정하며, 문서는 이 방법이 정확한 추정을 준다고 설명한다. 앞의 셀프 조인처럼 (1, 'i7')과 (2, 32) 이상이 모두 상수 구간이면 두 구간의 크기를 각각 잴 수 있다. 다른 하나는 인덱스 통계다. InnoDB는 인덱스마다 열 접두사별로 서로 다른 값의 수를 저장한다. 영구 통계 테이블 mysql.innodb_index_stats의 n_diff_pfx01은 첫 열의 서로 다른 값 수, n_diff_pfx02는 앞 두 열 조합의 서로 다른 값 수다. 이 값은 ANALYZE TABLE 같은 작업 때 인덱스의 페이지를 표본으로 골라(기본 20페이지) 추정한다.

    MySQL 문서는 같은 키 접두사 값을 가진 행들의 집합을 값 그룹(value group)이라 부르고, 옵티마이저가 평균 값 그룹 크기를 두 곳에 쓴다고 설명한다. ref 접근 한 번에 읽어야 할 행 수를 추정할 때, 그리고 ... JOIN t ON t.key = expr 형태의 부분 조인이 몇 행을 만들지 추정할 때다. 조인 중에 앞 테이블의 값으로 뒤 테이블을 찾는 경우처럼 키 값이 미리 정해지지 않은 접근에서는 이 평균이 쓰인다는 뜻이다.

    EAV에서 이 평균이 무엇을 뜻하는지 숫자를 가정해 보자. 값 행이 2,000만 개이고 속성이 200개라면 idx_pav_number의 첫 열 attribute_id에 대한 평균 값 그룹 크기는 10만 행이다. 그런데 실제 분포는 고르지 않다. 색상처럼 거의 모든 상품에 있는 속성은 80만 행일 수 있고, 최대 하중처럼 캠핑 용품에만 있는 속성은 300행일 수 있다. 옵티마이저가 평균에 기대는 순간, 이 둘은 똑같이 "10만 행쯤"으로 보인다. 예를 들어 검색 필터에 노출하는 속성(searchable = TRUE)들을 정의 테이블에서 고른 뒤 그 속성들의 값 행을 조인하는 쿼리라면, 값 테이블을 attribute_id로 찾는 ref 접근의 추정은 어떤 속성이 골라지든 평균값이다. 넓은 테이블이었다면 색상 열과 최대 하중 열은 서로 다른 인덱스와 서로 다른 통계를 가졌을 것이다.

    히스토그램도 같은 한계를 가진다. MySQL 8.0의 히스토그램은 열 하나의 값 분포를 기록하는데, value_number 열에는 그램 단위 무게, GB 단위 메모리, kg 단위 하중이 섞여 있다. 이 열의 히스토그램은 어느 속성의 분포도 아닌, 단위가 섞인 숫자들의 분포다. 스키마의 열을 데이터의 행으로 바꾸면서, 열마다 따로 쌓이던 통계도 한 덩어리로 섞인 것이다. 결국 EAV 쿼리의 계획 품질은 상수 구간을 얼마나 많이 주느냐에 기대게 된다. 속성 ID와 값 범위를 상수로 넣은 쿼리는 인덱스 다이브로 잘 추정되고, 조인으로 속성이 정해지는 쿼리는 평균에 기댄다.

    이 절의 행 수(2,000만, 200개, 80만, 300)는 설명을 위해 가정한 숫자다. 실제 계획은 EXPLAIN과 EXPLAIN ANALYZE로 데이터마다 확인해야 한다.

    규모를 줄여 같은 현상을 확인해 보았다. 앞의 10만 개 데이터에는 "최대 하중"(9번, 단위 kg) 값 행 300개도 넣어 두었다. 값 행 400,306개 가운데 무게(4번, 단위 g)는 100,001행이다. ANALYZE TABLE 뒤 idx_pav_number의 n_diff_pfx01은 MySQL 8.4.13과 8.0.46 모두 6이었다. SELECT v.product_id FROM attribute_definition d JOIN product_attribute_value v ON v.attribute_id = d.attribute_id WHERE d.unit = 'kg'를 EXPLAIN하면 v는 idx_pav_number를 ref(ref 열은 d.attribute_id)로 읽는데, 추정 rows는 8.4.13에서 65666, 8.0.46에서 64757이었다. d.unit = 'g'로 바꿔 무게를 골라도 추정은 똑같았다. 300행짜리 속성과 10만 행짜리 속성이 같은 평균으로 보인 것이다. 반면 WHERE v.attribute_id = 9처럼 상수로 적으면 인덱스 다이브로 300행, attribute_id = 4는 182188행으로 추정해 둘을 구별했다(실제는 100,001행이므로 큰 구간의 다이브 추정은 근사값이다). 이 수치들은 실행 환경과 통계 표본에 따라 달라진다.

    애플리케이션 쪽: 값 행을 다시 타입 있는 객체로

    넓은 테이블을 JPA 엔티티로 매핑하면 Integer memoryGb 같은 필드가 생기고, 컴파일러는 이 필드에 문자열을 넣는 코드를 거부한다. 열 타입에서 필드 타입으로, 타입 정보가 데이터베이스에서 자바 코드까지 이어진다. EAV에서는 이 연결이 끊긴다. 값 행은 (속성, 값)의 목록이고, 애플리케이션이 받는 것은 보통 Map<String, Object>다. 어떤 키에 어떤 타입의 값이 있는지는 컴파일 시점이 아니라 실행 시점에 속성 정의를 보고서야 알 수 있다. 타입 검사가 컴파일러에서 런타임으로, 그리고 데이터베이스 스키마에서 정의 테이블과 검증 코드로 옮겨 간 것이다.

    아래 코드는 화면에서 들어온 입력(속성 코드 → 문자열)을 속성 정의에 따라 타입 있는 값으로 바꾸고, 바꿀 수 없는 입력을 오류로 모으는 최소한의 검증기다. JDK 21에서 그대로 컴파일하고 실행할 수 있다.

    import java.math.BigDecimal;
import java.time.LocalDate;
import java.util.*;

public class EavAssemble {
    enum DataType { STRING, NUMBER, DATE }

    record AttributeDef(int id, String code, DataType type, boolean required) {}

    // 화면에서 들어온 입력: 속성 코드 -> 사용자가 입력한 문자열
    static Map parse(List defs, Map input,
                                     List errors) {
        Map typed = new LinkedHashMap<>();
        for (AttributeDef def : defs) {
            String raw = input.get(def.code());
            if (raw == null) {
                if (def.required()) errors.add(def.code() + ": 필수 속성 누락");
                continue;
            }
            try {
                Object value = switch (def.type()) {
                    case STRING -> raw;
                    case NUMBER -> new BigDecimal(raw);
                    case DATE   -> LocalDate.parse(raw);
                };
                typed.put(def.code(), value);
            } catch (RuntimeException e) {
                errors.add(def.code() + ": " + e.getClass().getSimpleName());
            }
        }
        for (String code : input.keySet()) {
            if (defs.stream().noneMatch(d -> d.code().equals(code))) {
                errors.add(code + ": 정의되지 않은 속성");
            }
        }
        return typed;
    }

    public static void main(String[] args) {
        List laptop = List.of(
            new AttributeDef(1, "cpu", DataType.STRING, true),
            new AttributeDef(2, "memory_gb", DataType.NUMBER, true),
            new AttributeDef(4, "weight_g", DataType.NUMBER, false),
            new AttributeDef(8, "release_date", DataType.DATE, false));

        Map input = new LinkedHashMap<>();
        input.put("cpu", "i3");
        input.put("weight_g", "1,650");
        input.put("release_date", "2026-02-30");
        input.put("colour", "silver");

        List errors = new ArrayList<>();
        Map typed = parse(laptop, input, errors);
        System.out.println("typed  = " + typed);
        errors.forEach(e -> System.out.println("error  = " + e));

        Map ok = parse(laptop,
            Map.of("cpu", "i5", "memory_gb", "16"), new ArrayList<>());
        Object memory = ok.get("memory_gb");
        System.out.println("memory = " + memory + " (" + memory.getClass().getName() + ")");
        try {
            Integer gb = (Integer) memory;   // 컴파일은 된다
            System.out.println(gb);
        } catch (ClassCastException e) {
            System.out.println(e.getMessage());
        }
    }
}

error  = weight_g: NumberFormatException

    결과를 한 줄씩 보자. cpu만 통과했다. memory_gb는 입력에 없고 필수이므로 누락 오류가 된다. 이것이 앞에서 데이터베이스가 지킬 수 없다고 한 필수 규칙이다. weight_g의 "1,650"은 new BigDecimal이 쉼표를 받아들이지 않아 NumberFormatException을 던진다. 실습 2에서 MySQL은 같은 문자열을 숫자와 비교하며 앞부분만 읽어 1로 바꿨다. 문서의 예 SELECT 1 > '6x'가 0을 내는 것처럼, MySQL의 문자열 → 숫자 비교 변환은 오류 없이 관대하게 바꾼다. 자바의 파싱은 엄격하고, 이 차이 때문에 검증은 값이 저장되기 전 애플리케이션에서, 저장 시점에는 타입 있는 열과 엄격 모드가 맡아야 한다. "2026-02-30"은 존재하지 않는 날짜라 LocalDate.parse가 거부한다. 문자열 열 하나에 모든 값을 담던 구조였다면 이 값은 아무 문제 없이 저장되었을 것이다. colour는 정의에 없는 속성이다. 철자가 다른 속성 이름이 새 속성으로 둔갑하던 문제를, 여기서는 정의 테이블을 기준으로 막는다.

    마지막 두 줄은 타입 정보가 사라진 대가를 보여 준다. ok.get("memory_gb")의 정적 타입은 Object이므로 (Integer) memory라는 캐스트는 컴파일된다. 캐스트는 바이트코드의 checkcast 명령이 되고, JVM은 실행 시점에 객체의 실제 클래스가 Integer에 대입 가능한지 검사한다. 실제 객체는 BigDecimal이므로 ClassCastException이 난다. 넓은 테이블의 엔티티였다면 컴파일러가 잡았을 실수가 EAV에서는 런타임 예외가 된다. 그래서 EAV를 쓰는 코드는 속성 정의의 타입을 보고 값을 꺼내는 접근자(예: getNumber(code)가 정의 타입을 확인한 뒤 BigDecimal을 돌려주는 식)를 한곳에 모아 두는 편이 안전하다.

    JPA로 매핑할 때도 같은 구조가 이어진다. 값 행은 @ManyToOne으로 상품과 속성 정의를 참조하는 엔티티가 되고, 상품 상세 화면은 상품 하나의 값 행을 기본 키 앞 열로 한 번에 읽는다. 상품 목록 화면에서 상품마다 값 컬렉션을 지연 로딩하면 앞 권들에서 본 N+1 문제가 그대로 나타나므로, 목록에 보일 상품 ID들을 모아 WHERE product_id IN (...) 한 번으로 값 행을 읽고 메모리에서 상품별로 묶는 방식이 기본이 된다. 이 쿼리도 기본 키의 앞 열 product_id로 구간을 여러 개 읽는 것이라 클러스터형 인덱스의 "상품 축" 정렬을 그대로 활용한다.

    EAV의 장단점과 사용 시 주의사항

    지금까지 본 것을 장단점으로 정리하면 다음과 같다.

    관점얻는 것잃는 것
    속성 추가DDL과 배포 없이 INSERT로 추가. 배타 메타데이터 잠금도, 행 버전 한도도 없다.누구나 속성을 늘릴 수 있으므로 비슷한 속성이 중복 생성되기 쉽다. 관리 권한과 명명 규칙이 필요하다.
    희소성상품이 가진 속성만 행으로 존재한다. 열 개수·행 크기 한도와 무관하다.사실 하나당 바이트가 넓은 테이블보다 크고, 행 수가 엔티티 수 × 평균 속성 수로 불어난다.
    무결성정의 테이블, 선택지, 복합 외래 키, CHECK로 타입과 허용 값은 지킬 수 있다.필수 속성(행의 존재), 속성별 범위, 속성 간 규칙은 데이터베이스가 지키지 못한다.
    조회한 엔티티의 모든 속성 읽기는 기본 키 구간 하나로 빠르다.가로 모양의 결과는 피벗이 필요하고, 결과 열이 SQL에 고정된다.
    검색속성 하나의 조건은 (속성, 값) 인덱스로 구간 읽기가 된다.조건마다 셀프 조인이나 관계 나눗셈이 필요하고, 통계가 속성을 구별하지 못해 계획이 불안정해질 수 있다.
    메타데이터 관리표시 이름, 단위, 순서, 필터 노출 여부를 데이터로 관리하고 운영자가 바꿀 수 있다.스키마가 하던 일을 정의 테이블과 검증 코드가 대신하므로, 그 코드의 품질이 데이터 품질이 된다.

    EAV를 쓰기로 했다면 다음 주의사항을 지킨다.

    1. 모든 엔티티가 가진 속성과 핵심 속성은 열로 둔다. 이름, 가격, 카테고리, 재고처럼 모든 상품에 있고 업무 로직과 정렬과 조인에 쓰이는 속성을 EAV로 보내면, 가장 자주 쓰는 쿼리마다 피벗과 셀프 조인을 하게 된다. EAV는 "카테고리마다 다르고, 자주 바뀌고, 업무 로직이 의존하지 않는" 속성만을 위한 자리다.
    2. 관계를 값에 넣지 않는다. "브랜드" 속성의 값으로 브랜드 ID를 문자열에 담으면 외래 키를 걸 수 없고, 브랜드가 지워져도 값 행은 남는다. 다른 엔티티를 가리키는 속성은 그 엔티티를 참조하는 열이나 연결 테이블로 만든다. 개선된 구조의 선택지 테이블은 "속성 안의 허용 값"이라는 좁은 경우에만 쓴다.
    3. 값 테이블의 키를 엔티티와 속성의 조합으로 정한다. 한 속성에 값 하나라면 기본 키를 (엔티티, 속성)으로 두어 중복을 막고 저장 위치를 모은다. 여러 값을 허용해야 한다면(예: 지원 규격이 여러 개) 그 사실을 명시적으로 설계하고, 검색 쿼리는 COUNT(DISTINCT attribute_id)로 세어야 한다.
    4. 속성 정의의 변경을 마이그레이션으로 다룬다. 타입 변경, 선택지 삭제, 속성 삭제는 기존 값 행과 얽힌다. 외래 키가 이를 막아 줄 때 우회하지 말고, 새 속성으로 옮기는 절차를 밟는다.
    5. 필수 규칙은 검증 코드와 점검 쿼리로 이중으로 지킨다. 데이터베이스가 지킬 수 없는 규칙은 애플리케이션 한 곳에 모으고, 그 코드를 거치지 않은 데이터를 찾는 점검 쿼리를 정기적으로 돌린다.
    6. 검색 요구가 커지면 구조를 나눈다. 자주 검색하고 정렬하는 소수의 속성은 열로 승격하거나, 검색용으로 가로 모양을 미리 만들어 둔 별도 테이블을 둔다. 06회의 통계 테이블처럼 쓰기용 원본과 읽기용 구조를 나누는 발상이다.

    EAV 실무 활용 사례

    쇼핑몰 상품 스펙과 검색 필터. 이 회차의 예제 그대로다. 상품의 공통 정보는 열로, 카테고리별 스펙은 EAV로 두고, 속성 정의의 searchable 같은 플래그로 검색 필터 화면을 데이터에서 만든다. 실제 상거래 플랫폼에서도 이 구조를 볼 수 있다. Adobe Commerce 개발 문서는 Customer와 Catalog 모듈이 EAV 속성을 쓰는 주요 모델이며, EAV 속성을 쓰는 객체는 값을 보통 여러 MySQL 테이블에 나눠 저장한다고 설명한다. 같은 문서는 EAV 속성을 읽어 올 때 캐시하면 데이터베이스에 보내는 요청이 줄어 성능이 좋아진다고 하며, 2.3.4 버전부터 시스템 EAV 속성은 읽어 올 때 모두 캐시된다고 적고 있다. 정의는 메모리에 두고 값만 데이터베이스에서 읽는다는, 앞에서 본 운영 방식과 같은 방향이다.

    메타데이터 테이블. WordPress의 메타데이터 API 문서는 기본으로 wp_commentmeta, wp_postmeta, wp_usermeta 테이블이 있고, 모든 메타 테이블이 네 개의 열을 가진다고 설명한다. meta_id(BIGINT(20), 자동 증가 기본 키), 대상 객체의 ID(post_id 등, 외래 키로 정의하지 않는다고 명시), meta_key(VARCHAR(255)), meta_value(LONGTEXT)다. 그리고 한 객체가 같은 키에 값만 다른 여러 항목을 가질 수 있다고 한다. 이 회차의 기준으로 읽으면 이것은 가장 단순한 형태의 EAV다. 대리 키를 기본 키로 두었으니 같은 키의 여러 값이 허용되고(그래서 관계 나눗셈은 COUNT(DISTINCT ...)가 필요하다), 값은 타입 없는 긴 문자열이며, 대상 객체와의 참조 무결성은 데이터베이스가 지키지 않는다. 플러그인이 아무 키나 추가할 수 있어야 하는 범용 플랫폼이 유연성을 최대로 고른 결과이고, 타입과 무결성은 그 위의 코드가 책임진다.

    사용자 정의 필드. 이슈 관리 도구나 CRM처럼 고객사(테넌트)마다 자기 필드를 추가하는 제품은 EAV의 전형적인 쓰임새다. 이때 속성 정의 테이블에는 tenant_id가 붙고, 속성 코드의 유일성도 (tenant_id, code) 범위가 된다. 수천 개 테넌트가 각자 필드를 만드는 상황에서 테넌트마다 ALTER TABLE을 한다는 것은 앞에서 본 행 버전 한도, 메타데이터 잠금, 열 개수 한도 모두에 부딪히는 일이라 다른 선택지가 마땅치 않다.

    설문과 동적 폼의 응답. 운영자가 질문을 만들고 응답자가 답하는 설문에서 질문은 속성, 응답 한 건은 엔티티, 답은 값이다. 질문 정의에 타입(단답, 숫자, 날짜, 선택형)과 선택지가 있고, 응답은 값 행으로 쌓인다. 설문은 응답 한 건을 통째로 읽거나 질문 하나의 답을 집계하는 일이 대부분이고, 여러 질문의 조건을 동시에 거는 검색은 드물다. 그래서 EAV의 약점이 잘 드러나지 않는 사례다.

    설정값. 사용자별 알림 설정, 시스템 설정처럼 "키로 하나 읽고 하나 쓰는" 데이터도 EAV 모양이다. 키로만 접근하고 값으로 검색하지 않으므로 EAV의 비용이 거의 없다. 반대로 말하면, EAV가 잘 맞는 사례들의 공통점은 엔티티 단위로 읽고, 값으로 검색하는 일이 드물다는 것이다.

    고정 열, 서브타입 테이블, EAV 사이에서 고르기

    가변 속성을 만났을 때 고를 수 있는 길은 여럿이다. 07회의 상속 관계 설계에서 본 서브타입 테이블, 이 회차의 EAV, 그리고 다음 09회에서 다룰 JSON 열이다. JSON은 MySQL의 JSON 자료형과 생성 열·함수 기반 인덱스로 같은 문제를 다른 방식으로 푸는데, 자세한 비교는 09회의 몫이다. 여기서는 앞의 셋을 비교한다.

    흔한 오해와 함정

    "NULL이 많은 넓은 테이블은 공간 낭비라서, EAV로 바꾸면 공간을 아낀다." InnoDB에서 NULL 칸은 NULL 비트 벡터의 비트 하나만 차지한다. 사실 하나를 저장하는 바이트는 오히려 EAV가 몇 배 크다. 레코드 헤더, 엔티티 ID, 속성 식별자, 트랜잭션 ID와 롤 포인터가 사실마다 붙고, 보조 인덱스에도 레코드가 하나 이상 생기기 때문이다. EAV를 고르는 이유는 공간이 아니라 스키마 변경을 피하는 유연성이어야 한다.

    "값 열을 VARCHAR 하나로 두고 필요할 때 CAST하면 된다." 비교와 정렬을 쿼리마다 올바르게 고쳐 써야 하고, 열에 함수를 씌운 조건은 인덱스 구간이 되지 못하며, 문자열 → 숫자 변환은 '1,650'을 1로 바꾸는 식으로 오류 없이 틀린 값을 낸다. 문제는 쿼리가 아니라 저장 구조에 있으므로, 고칠 곳도 저장 구조다.

    "CHECK 제약을 걸었으니 규칙은 데이터베이스가 지킨다." CHECK는 FALSE만 거부하고 UNKNOWN은 통과시킨다. NULL 허용 열이 섞인 식은 NULL일 때의 결과를 따로 따져야 한다. 또 CHECK는 자기 행만 볼 수 있어서, 다른 행의 존재(필수 속성)나 다른 테이블의 값(정의 테이블의 범위)에 대한 규칙은 걸 수 없다.

    "속성 정의 테이블까지 두면 EAV의 문제는 해결된다." 정의 테이블이 해결하는 것은 이름의 일관성, 타입, 허용 값, 메타데이터 관리다. 여러 조건 검색에 셀프 조인이 필요하다는 것, 결과를 가로로 펼치려면 피벗이 필요하다는 것, 통계가 속성을 구별하지 못한다는 것은 그대로다. 개선은 EAV를 안전하게 만들 뿐 넓은 테이블처럼 만들지는 않는다.

    "EAV는 안티패턴이니 쓰면 안 된다." 속성이 운영 중에 계속 생기고 엔티티 단위로 읽는 도메인에서 EAV를 피하면, 그 대가는 끝없는 DDL과 배포, 또는 의미 없는 범용 열 attr1~attr20이다. 범용 열은 속성의 의미를 열 번호에 숨긴 EAV이면서 정의를 데이터로 관리하지도 못하니, 제대로 설계한 EAV보다 나쁘다. 문제는 EAV 자체가 아니라, 그것이 맞지 않는 곳(핵심 속성, 관계, 복잡한 검색)에 쓰는 것이다.

    정리

    이 회차는 "어떤 속성이 있는가"가 데이터처럼 바뀌는 도메인에서 출발했다. 넓은 테이블은 공간이 아니라 카테고리를 모르는 제약, 열·행 크기와 인덱스 개수의 한도, 그리고 속성이 생길 때마다 필요한 DDL과 배타 메타데이터 잠금 때문에 막혔다. EAV는 속성 이름을 스키마에서 데이터로 내려 이 문제를 피하고, 새 속성의 등장을 INSERT 한 번으로 만든다. 그 대가로 스키마가 하던 일, 곧 타입·필수·허용 값 검사와 결과의 모양, 옵티마이저 통계가 다른 곳으로 옮겨 간다.

    이 장의 핵심

    EAV는 스키마의 일을 데이터로 옮기는 설계다. 속성 정의 테이블은 옮겨 간 메타데이터를 다시 한곳에 모으고, 타입 복사본 + 복합 외래 키 + CHECK는 데이터베이스가 지킬 수 있는 규칙을 최대한 되찾는다. 그래도 필수 규칙, 여러 조건 검색, 속성별 통계는 돌아오지 않는다. 그러므로 EAV는 "카테고리마다 다르고, 운영 중에 생기고, 엔티티 단위로 읽는" 속성에만 쓰고, 핵심 속성과 관계는 열과 외래 키에 남긴다.
    EAV(Entity-Attribute-Value)
    사실 하나를 (엔티티, 속성, 값) 한 행으로 저장해, 속성을 열이 아니라 행으로 표현하는 설계다. 새 속성의 추가가 DDL이 아니라 INSERT가 되는 대신, 열 정의가 하던 타입·필수·허용 값 검사와 통계가 다른 곳으로 옮겨 간다.
    넓은 테이블의 실제 한계
    InnoDB에서 NULL 칸은 NULL 비트 벡터의 비트 하나만 차지하므로 문제는 공간이 아니다. 카테고리를 모르는 열 제약, 열 개수·행 크기·보조 인덱스 개수의 한도, 속성마다 필요한 DDL이 문제다.
    스키마 변경과 메타데이터 잠금
    INSTANT 열 추가도 마지막에 배타 메타데이터 잠금이 필요하다. 열린 트랜잭션이 공유 잠금을 쥐고 있으면 DDL이 기다리고, 대기 중인 배타 요청이 뒤따르는 일반 쿼리까지 막는다.
    피벗과 관계 나눗셈
    세로로 저장된 값은 MAX(CASE ...) 조건부 집계로 가로로 펼친다. 여러 속성 조건을 모두 만족하는 엔티티는 셀프 조인이나 GROUP BY ... HAVING COUNT(*) = n으로 찾으며, 이 셈은 (엔티티, 속성) 유일성에 기댄다.
    문자열 값 열의 함정
    값을 VARCHAR 하나에 담으면 문자열 비교로 '8' >= '16'이 참이 되고, 숫자와 비교하면 부동소수점 변환 때문에 값 조건에 인덱스를 못 쓰며 '1,650'이 1로 바뀌는 식의 조용한 오류가 난다.
    속성 정의 테이블
    속성을 코드, 표시 이름, 타입, 단위를 가진 엔티티로 꺼내고, 카테고리-속성 연결에 필수 여부와 순서를, 선택지 테이블에 허용 값을 둔다. 값 행은 속성을 정수 ID로 참조한다.
    타입 복사본 + 복합 외래 키 + CHECK
    CHECK는 다른 테이블을 읽을 수 없으므로 값 행에 타입을 복사하고, (attribute_id, data_type) 외래 키로 복사본을 검증하며, CHECK로 타입에 맞는 값 열 하나만 채우게 한다. CHECK는 UNKNOWN을 통과시키고 외래 키는 NULL이 섞이면 검사하지 않는다는 점을 함께 고려한다.
    데이터베이스가 지키지 못하는 규칙
    필수 속성(행의 존재), 속성별 값 범위, 속성 간 규칙은 애플리케이션 검증과 정기 점검 쿼리가 맡는다. 속성 타입 변경은 외래 키가 막으므로 새 속성으로 옮기는 마이그레이션으로 처리한다.
    옵티마이저와 EAV
    조건과 펼칠 속성마다 테이블 참조가 늘어 계획 탐색 비용이 커지고, 한 조인의 테이블 참조는 61개가 한도다. 인덱스 통계와 히스토그램은 모든 속성이 섞인 값이라, 상수 구간이 없는 접근은 평균 값 그룹 크기에 기대어 추정된다.

    이미 EAV로 운영되는 시스템을 맡았다면 먼저 속성 목록을 뽑아 본다. 같은 뜻의 속성이 이름만 달리해 여러 개 있지 않은지(무게, 중량, 무게(g)), 숫자여야 하는 속성의 값 가운데 숫자로 읽히지 않는 것이 얼마나 되는지를 세어 보면, 그 시스템이 정의 테이블 없이 얼마나 오래 굴러왔는지가 드러난다. 정리는 이 회차의 개선 순서를 따른다. 속성을 정의 테이블로 꺼내고, 값을 타입별 열로 변환해 옮기고, 변환할 수 없는 값은 사람이 고치게 목록으로 넘긴다. 이 작업은 한 번에 끝내기보다 검색에 쓰이는 속성부터 하는 것이 효과가 크다. 문자열 비교 때문에 틀린 검색 결과가 나가고 있었다면 그 속성이 가장 급하다.

    EAV 속성 가운데 하나가 업무 로직에 들어가기 시작하는 순간을 놓치지 않는다. 예를 들어 "무게"로 배송비를 계산하기 시작하면, 그 속성은 더 이상 표시용 스펙이 아니다. 무게가 없는 상품, 단위가 다른 값, 운영자가 실수로 바꾼 타입이 곧바로 결제 금액 오류가 된다. 이런 속성은 열로 승격해 NOT NULL과 타입 검사를 데이터베이스에 맡기는 것이 맞다. 반대로 열로 만들었지만 일부 카테고리에서만 쓰이고 계속 늘어나는 열들은 EAV로 내릴 후보다. 판단 기준은 이 회차 내내 같았다. 그 속성의 존재가 업무 중에 바뀌는가, 그 속성에 로직이 의존하는가, 그 속성으로 검색하는가.

    넓은 테이블을 유지하기로 했다면 열 추가 작업의 위험은 변경 시간이 아니라 메타데이터 잠금 대기열이라는 점을 운영 절차에 반영한다. DDL을 실행하기 전에 그 테이블을 건드린 채 오래 열려 있는 트랜잭션이 없는지 information_schema.innodb_trx와 프로세스 목록으로 확인하고, DDL 세션의 lock_wait_timeout을 짧게 두어 잠금을 오래 기다리느니 실패하고 다시 시도하게 한다. 이 절차가 매주 필요할 만큼 속성 추가가 잦다면, 그 빈도 자체가 EAV나 JSON을 검토할 신호다.

    EAV(Entity-Attribute-Value)
    엔티티, 속성, 값을 한 행에 담아 속성을 열이 아니라 행으로 표현하는 설계 패턴이다. 속성 목록이 운영 중에 바뀌는 도메인에서 스키마 변경을 피하려고 쓴다.
    희소 테이블(sparse table)
    열은 많지만 행마다 채워진 칸이 일부뿐인 테이블이다. InnoDB에서는 NULL 칸이 비트 하나만 차지하므로 공간보다 제약과 스키마 변경이 문제다.
    피벗과 언피벗(pivot, unpivot)
    세로로 늘어선 (속성, 값) 행을 속성별 열로 펼치는 변환이 피벗, 그 반대가 언피벗이다. SQL에서 피벗은 흔히 MAX(CASE ...) 조건부 집계로 하며, 결과 열은 SQL 문장에 고정된다.
    관계 나눗셈(relational division)
    주어진 조건 집합을 모두 만족하는 엔티티를 찾는 연산이다. EAV에서는 조건 중 하나라도 맞는 행을 모아 엔티티별로 맞춘 조건 수를 세는 GROUP BY ... HAVING으로 쓴다.
    속성 정의 테이블(attribute definition table)
    속성의 코드, 표시 이름, 타입, 단위 같은 메타데이터를 행으로 관리하는 테이블이다. 스키마가 하던 열 정의의 역할을 데이터로 되찾는 작은 데이터 사전이다.
    메타데이터 잠금(metadata lock)
    MySQL이 테이블 정의를 보호하려고 거는 잠금이다. 일반 문장은 공유 잠금을 트랜잭션 끝까지 쥐고, DDL은 정의를 바꿀 때 배타 잠금이 필요하며, 대기 중인 배타 요청은 뒤따르는 공유 요청을 막는다.
    MATCH SIMPLE
    복합 외래 키의 열 가운데 하나라도 NULL이면 참조 검사를 하지 않는 의미 규칙이다. MySQL은 사실상 이 의미를 구현하며, 명시적인 MATCH 절은 인식하지 않는다.
    평균 값 그룹 크기(average value group size)
    같은 키 접두사 값을 가진 행 집합(값 그룹)의 평균 크기다. MySQL은 ref 접근의 행 수와 부분 조인의 결과 행 수를 추정할 때 이 값을 쓰며, 테이블 행 수를 인덱스의 서로 다른 값 수로 나눈 것과 관련된다.
