    이 회차의 질문: 엔티티를 거치지 않으면 무엇이 달라지는가

    앞 회차에서는 주문과 주문 상품처럼 일대다 관계를 가진 엔티티를 조회해 API 응답으로 내보내는 방법을 단계별로 개선했다. 엔티티를 그대로 내보내면 API 스펙이 엔티티에 묶이고, DTO로 바꾸면 지연 로딩 때문에 쿼리가 폭증하며, 컬렉션 페치 조인으로 쿼리를 하나로 줄이면 행이 불어나 페이징을 할 수 없고, 그 한계는 default_batch_fetch_size가 만드는 IN 쿼리로 넘었다. 그 모든 단계에서 데이터베이스가 돌려준 행은 일단 엔티티가 되었다. 엔티티가 영속성 컨텍스트에 올라가고, 그다음에야 DTO로 옮겨졌다.

    이 회차는 그 중간 단계를 없앤다. JPQL의 생성자 표현식으로 처음부터 DTO를 만들어 받는 DTO 직접 조회다. 엔티티가 없으니 영속성 컨텍스트도, 지연 로딩 프록시도, 변경 감지를 위한 스냅샷도 생기지 않는다. 대신 엔티티 그래프가 해 주던 일, 즉 "주문 하나에 주문 상품 여러 개"라는 구조를 맞추는 일을 개발자가 직접 해야 한다. 생성자 표현식은 결과 한 행을 객체 하나로 바꿀 뿐, 여러 행을 묶어 컬렉션을 만들지 않기 때문이다.

    그래서 이 회차의 주제는 세 가지 조립 방식과 그 비용이다. 첫째는 루트 DTO를 조회한 뒤 루트마다 컬렉션 쿼리를 따로 보내는 방식(이 강좌에서는 V4라고 부른다), 둘째는 루트의 식별자를 모아 IN 쿼리 한 번으로 컬렉션을 가져와 메모리에서 붙이는 방식(V5), 셋째는 모든 것을 조인한 평평한(flat) 결과를 한 번에 받아 애플리케이션에서 다시 묶는 방식(V6)이다. 각 방식이 데이터베이스에 보내는 쿼리 수, 네트워크로 오가는 행 수, 페이징 가능 여부, JVM 힙에서 일어나는 일을 차례로 확인한다. 마지막으로 앞 회차와 이 회차를 합쳐 "엔티티 조회와 DTO 직접 조회 중 무엇부터 쓸 것인가"를 정리한다. 이 과정에서 생기는 영속성 컨텍스트의 수명 문제, 즉 OSIV는 다음 회차의 몫이다.

    이 회차의 실행 결과는 모두 JDK 21(Temurin 21.0.13), Hibernate ORM 6.6.53.Final, H2 2.3.232 인메모리 데이터베이스에서 직접 돌려 얻은 것이다. 스프링 부트 없이 Hibernate의 Configuration으로 세션 팩토리를 만들었고, 실행된 SQL은 Hibernate의 StatementInspector로 가로채 출력했다. 그래서 테이블과 컬럼 이름이 자바 이름 그대로(OrderLine, itemName) 나온다. 데이터베이스 엔진 쪽 설명은 MySQL 8.0 InnoDB 기준이며, 매뉴얼로 확인한 내용에 더해 인덱스와 실행 계획 부분은 MySQL 8.0.46과 8.4.13에서 직접 돌려 확인했다.

    실험 모델: 고객, 주문, 주문 줄

    예제 도메인은 이 회차를 위해 새로 만든 작은 모델이다. 고객(Customer)이 주문(Order)을 하고, 주문에는 여러 개의 주문 줄(OrderLine)이 달린다. 주문에서 고객은 다대일(ToOne), 주문에서 주문 줄은 일대다(ToMany) 관계다. 연관관계는 모두 지연 로딩으로 두었다. 이 회차에서는 엔티티를 거의 조회하지 않지만, JPQL은 엔티티와 그 연관관계를 기준으로 쓰기 때문에 매핑은 그대로 필요하다.

    @Entity
public class Customer {
    @Id @GeneratedValue Long id;
    String name;
    // 생성자 생략
}

@Entity
@Table(name = "orders")   // ORDER는 SQL 예약어라 테이블 이름을 바꾼다
public class Order {
    @Id @GeneratedValue Long id;
    @ManyToOne(fetch = FetchType.LAZY) Customer customer;
    String status;
    @OneToMany(mappedBy = "order") List lines = new ArrayList<>();
    // 생성자 생략
}

@Entity
public class OrderLine {
    @Id @GeneratedValue Long id;
    @ManyToOne(fetch = FetchType.LAZY) Order order;
    String itemName;
    int price;
    int quantity;
    // 생성자 생략
}

    조회 결과를 담을 DTO는 자바 16에서 정식 기능이 된 레코드(record)로 만든다. 레코드는 컴포넌트 순서대로 매개변수를 받는 정규 생성자(canonical constructor)와 equals, hashCode, toString을 컴파일러가 만들어 주므로, 값을 실어 나르기만 하는 DTO에 잘 맞는다. 뒤에서 보겠지만 equals와 hashCode가 자동으로 생긴다는 점이 V6에서 실제로 쓸모가 있다.

    package shop;

record OrderRow(Long orderId, String customerName, String status) {}
record LineRow(Long orderId, String itemName, int price, int quantity) {}
record FlatRow(Long orderId, String customerName, String status,
               String itemName, int price, int quantity) {}
record OrderView(OrderRow header, List lines) {}

    생성자 표현식은 무엇을 약속하는가

    Jakarta Persistence 3.1 명세 4.8절은 SELECT 절에 올 수 있는 것을 다섯 가지로 정한다. 식별 변수, 단일 값 경로 표현식(single-valued path expression), 스칼라 표현식, 집계 표현식, 그리고 생성자 표현식(constructor expression)이다. 생성자 표현식의 문법은 NEW constructor_name(constructor_item, ...)이고, 괄호 안의 각 항목은 단일 값 경로, 스칼라 식, 집계 식, 식별 변수 중 하나여야 한다. 4.8.2절은 여기에 세 가지를 덧붙인다. 지정한 클래스는 엔티티일 필요도, 매핑되어 있을 필요도 없다. 생성자 이름은 패키지까지 포함한 정규화된 이름(fully qualified name)이어야 한다. 그리고 엔티티 클래스를 생성자 이름으로 쓰면 만들어진 인스턴스는 기본 키를 조회했는지에 따라 새(new) 상태나 준영속(detached) 상태가 된다.

    마지막 규칙에는 짝이 되는 문장이 하나 더 있다. 생성자의 인자로 넘긴 단일 값 경로나 식별 변수가 엔티티를 가리키면, 그 엔티티 인스턴스는 영속(managed) 상태가 된다. 즉 select new shop.Something(o.customer, o.status)처럼 엔티티 자체를 인자로 넘기면, 바깥의 DTO는 영속성 컨텍스트와 무관하지만 안에 들어간 Customer는 영속성 컨텍스트에 등록된 진짜 엔티티다. "DTO로 조회했으니 영속성 컨텍스트와 상관없다"는 말은 인자가 전부 스칼라 값일 때만 맞다. Hibernate 6.6 사용자 가이드도 같은 취지로, select new로 만든 인스턴스는 그 클래스가 엔티티라 해도 관리되는 엔티티가 아니며 세션과 연결되지 않는다고 적는다.

    이 약속이 실제로 어떻게 지켜지는지 통계로 확인해 보자. Hibernate의 Statistics를 켜고 같은 세 건의 주문을 두 가지로 읽었다. 하나는 이 회차의 DTO 조회이고, 다른 하나는 앞 회차에서 쓴 컬렉션 페치 조인이다.

    DTO 조회 (select new ...)      entityLoadCount=0  영속성 컨텍스트의 엔티티 수=0
엔티티 페치 조인 (join fetch)   entityLoadCount=9  영속성 컨텍스트의 엔티티 수=9

    페치 조인 쪽의 9는 주문 3건과 주문 줄 6건이다. 이 9개의 엔티티는 각각 1차 캐시의 맵에 식별자를 키로 등록되고, 변경 감지를 위한 로딩 시점 상태(JPA 기본편에서 본 스냅샷)도 함께 보관된다. 트랜잭션이 끝날 때 플러시가 일어나면 Hibernate는 이 엔티티들을 순회하며 바뀐 것이 있는지 비교한다. 읽기만 하는 API라도 이 비용은 빠지지 않는다. DTO 조회 쪽은 0이다. 결과 리스트에 담긴 레코드 객체는 영속성 컨텍스트가 전혀 모르는 평범한 자바 객체이고, 그 객체가 쓰는 힙 메모리는 결과 리스트에 대한 참조가 사라지는 순간 GC 대상이 된다.

    문자열 하나가 생성자 호출이 되기까지

    생성자 표현식이 붙은 JPQL은 어떤 단계를 거쳐 레코드 객체가 될까. Hibernate 6은 HQL/JPQL 문자열을 먼저 SQM(Semantic Query Model)이라는 의미 트리로 해석한다. Hibernate 6.6 jar 안에서 new 구문에 대응하는 트리 노드는 org.hibernate.query.sqm.tree.select.SqmDynamicInstantiation 클래스다. 이 단계에서 경로 표현식 o.customer는 조인으로, c.name은 특정 테이블의 특정 열로 해석되고, 각 인자의 자바 타입도 정해진다. 그 타입 목록과 맞는 생성자가 대상 클래스에 있는지도 이 단계에서 검사한다.

    검사가 이 단계에서 일어난다는 사실은 실험으로 확인할 수 있다. 맞는 생성자가 없는 쿼리를 createQuery만 호출하고 실행하지 않았더니, createQuery가 곧바로 IllegalArgumentException을 던졌고 데이터베이스로 간 SQL은 0개였다. 쿼리 문자열의 오류가 데이터베이스까지 가지 않고 애플리케이션 안에서 잡힌다는 뜻이다. 이름 붙은 쿼리(@NamedQuery)로 등록해 두면 더 앞당길 수 있다. Hibernate 6.6 사용자 가이드에 따르면 hibernate.query.startup_check의 기본값이 true이고, 이때 이름 붙은 쿼리는 시작 시점에 검사된다. 그러면 이런 오류는 사용자의 첫 요청이 아니라 애플리케이션 기동 단계에서 드러난다.

    SQM은 다시 SQL AST를 거쳐 SQL 문자열이 된다. 이때 SELECT 목록에는 생성자 인자에 해당하는 열만 들어간다. 우리 예제의 루트 조회는 다음 SQL이 되었다.

    select o1_0.id,c1_0.name,o1_0.status
from orders o1_0
join Customer c1_0 on c1_0.id=o1_0.customer_id
order by o1_0.id

    엔티티를 조회했다면 orders의 모든 매핑 열(customer_id 포함)이 SELECT에 올라왔을 것이다. 여기서는 생성자에 넘긴 세 값만 온다. JDBC 드라이버가 결과 집합(ResultSet)을 돌려주면, Hibernate는 행마다 열 값을 꺼내 순서대로 배열에 담고 대상 생성자를 리플렉션으로 호출한다. Hibernate 6.6에서 이 조립을 맡는 결과 객체는 org.hibernate.sql.results.graph.instantiation.internal.DynamicInstantiationResultImpl이다. 결과 객체가 엔티티가 아니므로 1차 캐시 조회도, 식별자로 기존 인스턴스를 찾는 작업도, 스냅샷 복사도 없다. 한 행이 정확히 한 번의 생성자 호출이 된다.

    JPQL 한 줄이 SQL 열 목록과 결과 행을 거쳐 생성자 호출이 되고, 영속성 컨텍스트는 비어 있는 채로 남는다는 것을 보여 준다. 왼쪽에서 오른쪽으로 흐르는 가로 흐름도. 맨 왼쪽 상자에 "JPQL: select new shop.OrderRow(o.id, c.name, o.status)" 라고 적고, 화살표로 "SQM 트리" 상자, 다시 화살표로 "SQL: select id, name, status" 상자로 이어진다. 그 오른쪽에 데이터베이스 원통 아이콘 "데이터베이스"가 있고, 원통에서 나온 화살표가 표 모양의 "결과 행 3개"로 간다. 결과 행 각각에서 화살표가 하나씩 나와 오른쪽의 객체 상자 세 개 "OrderRow 객체"로 이어지며, 화살표 위에 "생성자 호출"이라고 적는다. 그림 아래쪽에 점선으로 그린 빈 상자 "영속성 컨텍스트 (비어 있음)"를 두고, 객체 상자들과 연결선이 없음을 보여 준다. 생성자 검사 단계 옆에 작은 경고 아이콘과 "생성자가 없으면 여기서 예외"라는 라벨을 단다. 평면 벡터 스타일, 흰 배경, 차분한 청록색 계열. select new는 결과 한 행을 생성자 호출 한 번으로 바꾼다. 영속성 컨텍스트에는 아무것도 올라가지 않는다.

    생성자 표현식의 함정 다섯 가지

    생성자 표현식은 문자열 안에 자바 생성자 호출을 적는 구조라서, 컴파일러가 잡아 주지 못하는 실수가 생긴다. 실험으로 확인한 다섯 가지를 차례로 보자. 오류 메시지는 Hibernate 6.6.53.Final이 실제로 낸 문구다.

    1. 패키지 이름을 빼면 클래스를 찾지 못한다

    명세가 정규화된 이름을 요구하므로, select new OrderRow(...)처럼 클래스 이름만 쓰면 Hibernate는 그 이름을 클래스로 해석하지 못한다.

    java.lang.IllegalArgumentException: org.hibernate.query.SemanticException:
  Could not resolve class 'OrderRow' named for instantiation
  [select new OrderRow(o.id, o.customer.name, o.status) from Order o]

    엔티티 이름은 클래스 이름만으로 쓰는데 DTO는 왜 안 될까. 엔티티는 메타모델에 등록되어 있어 Hibernate가 이름표를 들고 있지만, DTO 클래스는 쿼리 문자열에서 처음 등장하므로 클래스 로더에 넘길 이름 전체가 필요하기 때문이다. Hibernate는 이 제약을 풀어 주는 전용 애너테이션 @org.hibernate.annotations.Imported를 제공한다. 실험에서 이 애너테이션을 붙인 레코드를 매핑 클래스로 등록하자 select new ShortName(o.id, o.status)가 정상 실행되었다. 다만 이것은 Hibernate 전용 기능이며 명세가 보장하는 동작이 아니다.

    2. 인자는 이름이 아니라 위치로 짝지어진다

    가장 위험한 실수는 오류가 나지 않는 실수다. OrderRow(Long orderId, String customerName, String status)에 고객 이름과 상태의 순서를 바꿔 넘겨 보았다.

    select new shop.OrderRow(o.id, o.status, o.customer.name) from Order o
    OrderRow[orderId=1, customerName=ORDER, status=kim]
OrderRow[orderId=2, customerName=ORDER, status=lee]
OrderRow[orderId=3, customerName=CANCEL, status=kim]

    두 인자가 모두 String이라 타입 목록 (Long, String, String)이 생성자와 일치하므로 Hibernate는 아무 문제 없이 객체를 만든다. 생성자 표현식에는 이름 붙은 인자(named argument)가 없고, 자바 생성자도 매개변수 이름이 아니라 위치로 호출된다. 같은 타입의 인자가 여럿인 DTO에서는 필드 순서를 바꾸는 리팩터링 한 번이 조용한 데이터 오염으로 이어진다. 이런 쿼리는 결과 값까지 확인하는 테스트로만 지킬 수 있다.

    3. 타입이 맞지 않으면 생성자가 "없다"

    명세 4.8.5절은 집계 함수의 결과 타입을 정해 둔다. COUNT는 Long, AVG는 Double이고, SUM은 정수형 상태 필드에 쓰면(BigInteger 제외) Long이다. 그래서 주문별 합계를 int로 받으려는 생성자는 쓸 수 없다.

    record TotalI(Long orderId, int total) {}
// select new shop.TotalI(l.order.id, sum(l.price * l.quantity)) from OrderLine l group by l.order.id
    org.hibernate.query.SemanticException: Missing constructor for type 'TotalI' [...]

    같은 쿼리를 record TotalL(Long orderId, Long total)로 바꾸자 TotalL[orderId=1, total=50000], TotalL[orderId=2, total=14000], TotalL[orderId=3, total=50000]이 나왔다. 반대 방향은 어떨까. int 필드인 l.price를 long 매개변수로 받는 생성자는 Hibernate 6.6.53에서 정상 동작했다. 즉 이 버전의 생성자 검사는 자바의 기본형 확장 변환(widening)은 허용하고, 정보가 줄어들 수 있는 축소 변환(Long에서 int)은 허용하지 않았다. 이 허용 범위는 명세가 정한 것이 아니라 구현의 판단이므로, 타입은 처음부터 정확히 맞추는 편이 안전하다.

    4. 컬렉션은 인자가 될 수 없다

    "주문 DTO의 생성자에 주문 줄 리스트를 바로 넘기면 되지 않을까" 하는 생각이 가장 먼저 든다. 명세는 이것을 막는다. 4.8절은 SELECT 절이 단일 값 표현식만 반환해야 한다고 적고, SELECT o.lineItems FROM Order AS o를 올바르지 않은 쿼리의 예로 든다. 생성자 인자의 문법도 단일 값 경로까지만 허용한다. Hibernate 6.6에서 이것을 시도하면 다음처럼 된다.

    select new shop.OrderView(o.id, o.lines) from Order o
  → SemanticException: Missing constructor for type 'OrderView'

select o.id, o.lines from Order o   (생성자 없이 직접 조회)
  → [1, OrderLine@...] [1, OrderLine@...] [2, OrderLine@...]   (3행)

    두 번째 실험이 이유를 보여 준다. Hibernate는 SELECT 절의 컬렉션 경로를 명세보다 너그럽게 받아들이지만, 그 의미는 "컬렉션 하나"가 아니라 "컬렉션과 내부 조인해 원소 하나씩"이다. 그 실험 데이터(주문 2건, 줄 3건)에서 결과는 줄 수만큼인 3행이었다. 그러니 o.lines 자리의 인자 타입은 List가 아니라 OrderLine이고, (Long, OrderLine) 생성자가 없으니 "생성자가 없다"는 오류가 난다. 근본적으로는 SQL 결과가 행의 목록이고 생성자 표현식이 행 하나를 객체 하나로 바꾸는 장치이기 때문이다. 여러 행을 하나의 리스트로 묶는 일은 이 장치의 바깥, 곧 애플리케이션 코드에서 해야 한다. 이것이 V4, V5, V6이 존재하는 이유다.

    5. 페치 조인을 섞을 수 없고, 기본형에는 null이 들어갈 수 없다

    DTO 조회에 join fetch를 섞으면 Hibernate는 쿼리 생성 단계에서 거절한다. 페치 조인은 "조회한 엔티티의 연관 필드를 채워 달라"는 지시인데, 결과가 DTO라 채울 엔티티가 없기 때문이다.

    select new shop.OrderRow(o.id, c.name, o.status) from Order o join fetch o.customer c
  → SemanticException: Query specified join fetching, but the owner of the fetched
    association was not present in the select list [...]

    DTO 조회에서 필요한 것은 페치 조인이 아니라 일반 조인이다. 조인한 별칭에서 원하는 열을 꺼내 인자로 넘기면 된다. 또 하나는 실행 시점에야 드러나는 오류다. 주문 줄이 없는 주문까지 보려고 left join o.lines l로 바꾸면, 줄이 없는 주문의 행에서 l.price는 NULL이다. 이 값을 int price 매개변수에 넣으려 하면 생성자 호출이 실패한다.

    org.hibernate.query.sqm.sql.internal.InstantiationException: Error instantiating class 'shop.FlatRow'
  java.lang.IllegalArgumentException: java.lang.NullPointerException:
    Cannot invoke "java.lang.Number.intValue()" because the return value of
    "sun.invoke.util.ValueConversions.primitiveConversion(...)" is null

    이 오류는 쿼리 생성 단계가 아니라 결과 행을 객체로 바꾸는 단계에서 난다. 타입 목록은 맞았으니 생성자 검사는 통과했고, 실제 값이 null인 행을 만나서야 실패한 것이다. 예외 체인에 sun.invoke.util.ValueConversions가 보이는 이유는 JDK 18부터 java.lang.reflect.Constructor의 구현이 메서드 핸들 위로 옮겨졌기 때문이다(JEP 416). 리플렉션 호출이 언박싱 변환을 하다가 null을 만난 것이다. 줄 없는 주문(id 4)을 하나 추가한 데이터에서 매개변수를 Integer로 바꾸자, 그 주문의 행이 FlatBoxed[orderId=4, itemName=null, price=null]로 정상 변환되었다. 외부 조인으로 null이 올 수 있는 열은 래퍼 타입으로 받아야 한다.

    V4: 루트를 먼저, 컬렉션은 루트마다 따로

    이제 주문 목록 API를 DTO 직접 조회로 만들어 보자. 컬렉션을 생성자에 넣을 수 없으니 일을 둘로 나눈다. 먼저 행 수가 늘지 않는 관계, 즉 ToOne 관계만 조인해 루트 DTO를 조회한다. 주문 하나에 고객은 하나이므로 orders와 Customer를 조인해도 결과 행 수는 주문 수 그대로다. 그다음 루트마다 컬렉션을 조회해 붙인다.

    List roots = em.createQuery(
        "select new shop.OrderRow(o.id, c.name, o.status)" +
        " from Order o join o.customer c order by o.id", OrderRow.class)
    .getResultList();

List views = roots.stream()
    .map(r -> new OrderView(r, em.createQuery(
            "select new shop.LineRow(l.order.id, l.itemName, l.price, l.quantity)" +
            " from OrderLine l where l.order.id = :id", LineRow.class)
        .setParameter("id", r.orderId())
        .getResultList()))
    .toList();
    select o1_0.id,c1_0.name,o1_0.status from orders o1_0 join Customer c1_0 on c1_0.id=o1_0.customer_id order by o1_0.id
select ol1_0.order_id,ol1_0.itemName,ol1_0.price,ol1_0.quantity from OrderLine ol1_0 where ol1_0.order_id=?
select ol1_0.order_id,ol1_0.itemName,ol1_0.price,ol1_0.quantity from OrderLine ol1_0 where ol1_0.order_id=?
select ol1_0.order_id,ol1_0.itemName,ol1_0.price,ol1_0.quantity from OrderLine ol1_0 where ol1_0.order_id=?
    OrderView[header=OrderRow[orderId=1, customerName=kim, status=ORDER], lines=[LineRow[orderId=1, itemName=book-A, ...],LineRow[orderId=1, itemName=book-B, ...]]]
OrderView[header=OrderRow[orderId=2, customerName=lee, status=ORDER], lines=[pen, ink, note 세 줄]]
OrderView[header=OrderRow[orderId=3, customerName=kim, status=CANCEL], lines=[bag 한 줄]]

    결과는 맞지만 쿼리는 1 + 3 = 4개다. 루트가 N개면 1 + N개가 된다. 앞 회차에서 엔티티를 DTO로 바꿀 때 지연 로딩이 만들던 N+1과 같은 모양인데, 이번에는 지연 로딩이 아니라 우리가 작성한 반복문이 쿼리를 만든다는 점만 다르다. 원인이 프록시가 아니니 default_batch_fetch_size 같은 설정으로는 줄어들지 않는다. 그 설정은 Hibernate가 프록시나 지연 컬렉션을 초기화할 때 쓰는 것이고, 여기에는 초기화할 프록시가 없다.

    SQL에서 눈여겨볼 곳이 두 군데 있다. 첫째, JPQL의 l.order.id는 orders 테이블과 조인하지 않고 OrderLine의 외래 키 열 order_id를 바로 썼다. 연관 엔티티의 식별자는 외래 키 열에 이미 들어 있으므로 조인할 필요가 없다는 것을 Hibernate가 안다. 둘째, 루트 쿼리는 join이 내부 조인(inner join)이라 고객이 없는 주문은 결과에서 빠진다. ToOne 관계가 선택적(optional)이라면 left join을 써야 하고, 그때는 앞에서 본 대로 NULL을 받을 매개변수 타입을 확인해야 한다.

    V4가 늘 나쁜 것은 아니다. 주문 상세 화면처럼 루트가 하나뿐이면 V4는 루트 1번, 컬렉션 1번으로 끝나므로 다른 방식과 쿼리 수가 같고 코드는 가장 단순하다. 문제는 목록 화면이다. 한 페이지에 주문 20건을 보여 주면 쿼리가 21개다. 쿼리 하나하나는 인덱스를 타는 가벼운 쿼리라도, 그 개수에 비례해 늘어나는 비용이 있다. 그 비용이 어디서 생기는지 데이터베이스 쪽으로 내려가 보자.

    한 층 아래: 쿼리 한 번이 InnoDB에서 하는 일

    예제 테이블을 MySQL 8.0 InnoDB에 만들었다고 하고, V4의 컬렉션 쿼리 select ... from OrderLine where order_id = ? 한 번이 엔진 안에서 어떻게 처리되는지 따라가 보자. 먼저 인덱스다. OrderLine.order_id에는 외래 키 제약이 걸린다. MySQL 매뉴얼의 FOREIGN KEY 제약 절에 따르면 MySQL은 외래 키 검사가 테이블 전체 스캔 없이 빨리 끝나도록 참조하는 쪽 테이블에 외래 키 열로 시작하는 인덱스를 요구하고, 그런 인덱스가 없으면 자동으로 만든다. 그래서 order_id로 찾는 쿼리는 별도 작업 없이도 이 보조 인덱스(secondary index)를 쓸 수 있다.

    실제로 확인해 보자. Hibernate의 MySQL DDL처럼 테이블을 먼저 만들고 alter table OrderLine add constraint FK_line_order foreign key (order_id) references orders (id)로 외래 키만 추가했다. 인덱스는 따로 만들지 않았다.

    mysql> SELECT INDEX_NAME, NON_UNIQUE, SEQ_IN_INDEX, COLUMN_NAME FROM information_schema.STATISTICS
    -> WHERE TABLE_SCHEMA='m_jpa_app2_04' AND TABLE_NAME='OrderLine' ORDER BY INDEX_NAME, SEQ_IN_INDEX;
+---------------+------------+--------------+-------------+
| INDEX_NAME    | NON_UNIQUE | SEQ_IN_INDEX | COLUMN_NAME |
+---------------+------------+--------------+-------------+
| FK_line_order |          1 |            1 | order_id    |
| PRIMARY       |          0 |            1 | id          |
+---------------+------------+--------------+-------------+

    외래 키 제약과 같은 이름의 비유일(NON_UNIQUE = 1) 인덱스 FK_line_order가 order_id 위에 저절로 생겼다.

    InnoDB의 테이블 데이터는 기본 키 순서로 정렬된 B+Tree, 즉 클러스터형 인덱스(clustered index)의 리프 페이지에 행 전체로 저장된다. 보조 인덱스는 다르다. 매뉴얼은 보조 인덱스의 각 레코드가 인덱스 대상 열과 함께 그 행의 기본 키 열을 담고 있고, InnoDB가 이 기본 키 값으로 클러스터형 인덱스에서 행을 찾는다고 설명한다. 그러면 order_id = 2 쿼리의 실행은 이렇게 된다. 보조 인덱스 B+Tree의 루트에서 리프까지 내려가 order_id = 2인 첫 레코드를 찾고, 리프를 따라 같은 값이 끝날 때까지 읽는다. 레코드마다 기본 키를 꺼내 클러스터형 인덱스를 다시 루트부터 내려가 itemName, price, quantity를 읽는다. SELECT에 보조 인덱스에 없는 열이 있기 때문이다.

      보조 인덱스 (order_id, 기본 키)                  클러스터형 인덱스 (기본 키 → 행 전체)
  ┌────────────── 루트 ──────────────┐            ┌──────────── 루트 ────────────┐
  └───────┬───────────────┬──────────┘            └──────┬────────────────┬──────┘
   리프: (1,l1) (1,l2) │ (2,l3) (2,l4) (2,l5) │ (3,l6)     리프: l1[1,book-A,10000,1] l2[...] l3[2,pen,1000,5] ...
                         └──── order_id = 2 ────┘
                              │      │      │
                              └──────┴──────┴──── 기본 키 l3, l4, l5 로 클러스터형 인덱스를 다시 탐색 ──▶

    이 과정 자체는 빠르다. B+Tree의 높이는 낮고, 자주 쓰는 페이지는 버퍼 풀에 올라와 있을 것이다. 문제는 V4가 이 일을 문장 단위로 N번 반복한다는 데 있다. 쿼리마다 애플리케이션과 데이터베이스 사이의 네트워크 왕복이 한 번씩 일어나고, 서버는 문장을 받아 실행을 준비하고, 결과를 패킷으로 만들어 보낸다. JDBC 드라이버는 결과 집합을 받아 Hibernate에 넘기고, Hibernate는 다시 DTO를 만든다. 인덱스를 내려가는 일보다 이 고정 비용이 쿼리 수에 정확히 비례해 쌓인다. 게다가 그 시간 동안 트랜잭션은 커넥션 하나를 붙잡고 있다. 커넥션을 얼마나 오래 붙잡는가는 다음 회차의 OSIV에서 다시 중요해진다.

    여기서 미리 정확히 해 둘 점이 있다. 다음에 볼 IN 쿼리도 B+Tree를 내려가는 횟수 자체를 줄이지는 않는다. order_id IN (1, 2, 3)도 엔진 안에서는 세 개의 범위를 각각 찾아간다. IN이 줄이는 것은 문장 단위의 고정 비용, 곧 왕복과 문장 처리와 결과 전송의 반복이다. 무엇을 줄이고 무엇을 줄이지 못하는지 구분해 두어야 IN 목록이 커질 때 생기는 문제를 바르게 볼 수 있다.

    V5: 식별자를 모아 IN 한 번, 조립은 메모리에서

    V4의 반복문에서 쿼리를 밖으로 꺼내면 V5가 된다. 루트를 조회한 뒤 주문 id를 모두 모아, 주문 줄을 한 번에 가져온다. 가져온 주문 줄은 주문 id로 묶어 맵에 넣고, 루트를 돌면서 맵에서 자기 줄 목록을 꺼내 붙인다.

    List roots = em.createQuery(
        "select new shop.OrderRow(o.id, c.name, o.status)" +
        " from Order o join o.customer c order by o.id", OrderRow.class)
    .getResultList();

    .getResultList()

    쿼리는 루트 수와 상관없이 2개다. 결과는 V4와 한 글자도 다르지 않았다. JPQL의 in :ids에 리스트를 바인딩하면 Hibernate는 리스트 원소 수만큼 자리 표시자(?)를 펼쳐 SQL을 만든다. 원소가 3개라 in (?,?,?)가 되었다. 이 방식이 앞 회차의 default_batch_fetch_size와 무엇이 같고 무엇이 다른지 짚어 두자. 둘 다 "부모 식별자 목록으로 자식을 IN 한 번에 가져온다"는 같은 생각이다. 배치 페치는 Hibernate가 지연 컬렉션을 초기화할 때 영속성 컨텍스트에 있는 다른 미초기화 컬렉션의 소유자 id를 모아 자동으로 해 주고, V5는 엔티티가 없으니 개발자가 손으로 한다.

    루트 조회는 ToOne 조인만 하므로 행이 불어나지 않는다. 따라서 루트 쿼리에는 페이징을 그대로 걸 수 있다. 한 페이지에 주문 20건을 가져오면 IN 목록도 많아야 20개다. 페이징이 IN 목록의 크기를 자연스럽게 묶어 주는 셈이다. V5가 목록 API의 기본형으로 쓸 만한 이유가 여기 있다.

    경계 조건도 두 가지 확인했다. 첫째, 루트가 하나도 없어 빈 리스트를 바인딩하면 Hibernate 6.6은 where 1=0을 만들어 실행했다. 오류는 나지 않지만 결과가 뻔한 쿼리를 보내는 셈이므로, 루트가 비었으면 두 번째 쿼리를 생략하는 것이 깔끔하다. 둘째, hibernate.query.in_clause_parameter_padding을 켜고 같은 코드를 돌리자 SQL이 in (?,?,?,?)로 바뀌었다. 사용자 가이드는 이 설정(5.2.17부터)이 자리 표시자 수를 2의 거듭제곱(4, 8, 16, 32, 64...)으로 올리고 남는 자리에는 null을 바인딩한다고 적는다. 실행 계획을 캐시하는 데이터베이스에서 SQL 문자열의 종류를 줄여 캐시 적중률을 높이려는 장치다. 다만 H2의 JDBC 트레이스로 실제 바인딩 값을 보니, Hibernate 6.6.53은 남는 넷째 자리에 null이 아니라 마지막 값 3을 한 번 더 바인딩했다. 어느 쪽이든 결과는 같다. 같은 값이 IN 목록에 두 번 있어도 일치하는 행은 달라지지 않고, null이라면 SQL의 삼값 논리에 따라 order_id = NULL이 참이 아니라 UNKNOWN이며 WHERE는 참인 행만 남기므로 그 자리는 어떤 행과도 일치하지 않는다.

    IN 목록은 옵티마이저에게 무엇인가

    MySQL 8.0 매뉴얼의 범위 최적화(Range Optimization) 절은 col_name IN(val1, ..., valN)을 col_name = val1 OR ... OR col_name = valN과 같은 것으로 보고, 각 값을 하나짜리 범위, 곧 등치 범위(equality range)로 다룬다. 인덱스가 걸린 열이라면 이 조건은 범위 접근(range access) 방식으로 처리된다. 앞의 그림으로 말하면 보조 인덱스 위에서 order_id = 1, = 2, = 3이라는 세 구간을 차례로 찾아가는 것이다.

    예제 데이터(주문 3건, 주문 줄 6건)를 넣고 ANALYZE TABLE을 한 뒤 V4와 V5의 컬렉션 쿼리를 EXPLAIN으로 보면 접근 방식이 다르게 나온다. 등치 조건 하나인 V4 쿼리는 ref, IN 목록인 V5 쿼리는 range다.

    두 쿼리 모두 자동으로 생긴 FK_line_order를 썼다. rows는 주문 2의 줄 3개, 주문 1~3의 줄 6개와 정확히 맞는다. 값이 몇 개 안 되면 옵티마이저가 각 범위를 실제로 세어 보기 때문인데, 바로 다음 문단의 이야기다.

    흥미로운 것은 실행 계획을 고르는 단계다. 옵티마이저는 각 범위에 행이 몇 개 있는지 추정해야 비용을 계산할 수 있다. 인덱스가 유일 인덱스면 범위마다 1행으로 추정하면 끝이다. order_id 인덱스처럼 유일하지 않으면 두 가지 방법이 있다. 하나는 인덱스 다이브(index dive)로, 범위의 양 끝으로 실제로 인덱스를 내려가 그 사이 행 수를 세는 방법이다. 정확하지만 값이 많을수록 추정에 시간이 든다. 다른 하나는 인덱스 통계를 쓰는 방법으로, 덜 정확하지만 값이 많아도 빠르다. 둘 사이의 전환점이 eq_range_index_dive_limit 시스템 변수이고, MySQL 8.0의 기본값은 200이다. 등치 범위가 이 값 이상이면 옵티마이저는 다이브 대신 통계를 쓴다. 매뉴얼은 N개까지 다이브를 쓰게 하려면 이 값을 N + 1로 두라고 적는다. 즉 기본값에서는 199개까지 다이브, 200개부터 통계다.

    이 전환을 직접 보려면 데이터가 조금 더 있어야 한다. 예제 테이블에 주문을 1000건까지 늘리고, 주문 줄을 주문마다 5개 안팎씩 넣은 뒤 주문 1~10에만 200개씩 더 몰아 넣어 주문 줄이 모두 7000건이 되게 했다. 값의 분포가 고르지 않아야 다이브와 통계의 차이가 드러난다. 그리고 order_id IN (1, 2, ..., n)을 n = 199, 200, 250으로 바꿔 가며 EXPLAIN을 실행하고, 옵티마이저 트레이스(SET SESSION optimizer_trace="enabled=on")의 range_scan_alternatives에서 index_dives_for_eq_ranges와 추정 rows를 꺼냈다. 실제 행 수는 count(*)로 따로 셌다. 서버 변수는 모두 기본값(eq_range_index_dive_limit 200, range_optimizer_max_mem_size 8388608)이었다.

    추정이 바뀌자 계획도 바뀌었다. 199개일 때는 정확한 추정치 2995행이 테이블의 40% 남짓이라 옵티마이저가 인덱스 대신 전체 스캔(ALL)을 골랐다. 값 하나를 더한 200개에서는 낮아진 추정치 때문에 범위 접근(range)을 골랐다. 어느 쪽이 실제로 더 빠른지는 이 실험이 말해 주지 않는다. 다만 IN 목록의 길이가 기준값을 넘는 순간 옵티마이저가 보는 숫자가 달라지고, 그 숫자로 계획이 갈릴 수 있다는 것은 분명하다. 그래서 큰 IN 목록의 계획은 짐작하지 말고 EXPLAIN으로 확인해야 한다.

    IN 목록이 아주 길어지면 다른 한계도 있다. 범위 최적화가 쓰는 메모리는 range_optimizer_max_mem_size로 제한되며 MySQL 8.0 기본값은 8388608바이트다. 매뉴얼은 IN 목록의 리터럴 하나하나가 OR로 결합된 조건으로 계산된다고 적는다. 한도를 넘을 것 같으면 옵티마이저는 범위 접근을 포기하고 테이블 전체 스캔을 포함한 다른 방법을 고려하며, 이때 경고 3170이 남는다. 인덱스가 있는데도 전체 스캔이 일어날 수 있다는 뜻이다.

    기본값 8388608바이트를 IN 목록으로 넘기려면 값이 아주 많아야 하므로, 앞의 주문 줄 7000건 테이블에서 세션 변수만 작게 줄여(SET SESSION range_optimizer_max_mem_size = 10000) 같은 일을 재현했다. 기본값에서 range로 처리되던 250개짜리 IN 쿼리가 이렇게 바뀌었다.

    이 두 가지에서 실무 판단이 나온다. IN 목록의 길이는 페이지 크기처럼 작게 묶여 있어야 하고, 식별자 수천 개를 한 번에 넣는 일괄 처리라면 목록을 잘라 여러 번 나누어 보내야 한다. 어느 크기로 자를지는 데이터와 서버 설정에 달려 있으므로, EXPLAIN으로 실제 계획(범위 접근인지, 예상 행 수가 얼마인지)을 확인하고 정한다. 이 원리는 앞 회차의 배치 페치 크기를 정할 때도 그대로 적용된다. 배치 페치가 만드는 SQL도 결국 같은 IN 조건이기 때문이다.

    order_id IN (1,2,3)이 보조 인덱스 리프에서 세 개의 구간으로 처리되고, 각 레코드의 기본 키로 클러스터형 인덱스를 다시 찾는 구조를 보여 준다. 두 개의 나무 구조를 좌우로 배치한 자료 구조도. 왼쪽 나무의 제목은 "보조 인덱스 (order_id)", 오른쪽 나무의 제목은 "클러스터형 인덱스 (기본 키)". 왼쪽 나무의 맨 아래 리프 줄에는 작은 칸 여섯 개가 나란히 있고 칸 위에 1, 1, 2, 2, 2, 3 이라는 숫자가 적혀 있다. 이 칸들을 세 개의 색 띠로 묶어 각각 "범위 1", "범위 2", "범위 3"이라고 라벨을 붙인다. 왼쪽 나무 위쪽에 말풍선 "IN (1, 2, 3)"을 둔다. 리프의 각 칸에서 오른쪽 나무의 리프로 가는 가는 화살표를 그리고 화살표 묶음 위에 "기본 키로 다시 탐색"이라고 적는다. 오른쪽 나무 리프 칸에는 "행 전체"라는 라벨을 단다. 그림 아래쪽에 작은 표지판 두 개를 둔다: "200개 이상이면 통계로 추정", "메모리 한도 초과 시 전체 스캔 고려". 평면 벡터 스타일, 흰 배경, 파란색과 회색 계열. IN 목록의 값 하나가 보조 인덱스 위의 등치 범위 하나가 된다. 줄어드는 것은 문장 수이지 인덱스 탐색 횟수가 아니다.

    메모리에서 묶기: groupingBy 안에서 일어나는 일

    V5의 두 번째 절반은 순수한 자바 코드다. Collectors.groupingBy(LineRow::orderId)는 무엇을 만들까. 실행해 보면 맵의 실제 클래스는 java.util.HashMap이었다. OpenJDK 21 소스에서 인자 하나짜리 groupingBy(classifier)는 groupingBy(classifier, toList())를 부르고, 그것이 다시 groupingBy(classifier, HashMap::new, downstream)를 부른다. 그리고 원소마다 computeIfAbsent(key, ...)로 키에 해당하는 리스트를 찾거나 새로 만들어 원소를 넣는다. 다만 Javadoc은 반환되는 맵의 타입, 변경 가능성, 직렬화 가능성, 스레드 안전성을 보장하지 않는다고 적는다. HashMap은 구현의 선택일 뿐 약속이 아니다.

    이 맵에서 키 하나를 찾는 일은 해시 계산 한 번과 버킷 접근 한 번이다. 주문 줄 M개를 묶는 데 M번, 루트 N개가 자기 목록을 꺼내는 데 N번, 합쳐 대략 N + M번의 맵 연산으로 조립이 끝난다. 맵 없이 루트마다 주문 줄 리스트 전체를 훑어 자기 것을 고르면 N × M번 비교가 필요하다. 페이지가 작을 때는 차이가 미미하지만, 일괄 처리처럼 N과 M이 커지면 이 차이가 그대로 CPU 시간이 된다.

    V5 코드에서 결과 순서가 루트 순서를 따르는 이유도 짚어 두자. 조립은 roots 리스트를 돌면서 맵에서 꺼내는 방식이므로, 맵 안의 순서가 무엇이든 최종 결과는 루트 쿼리의 order by o.id 순서다. 반대로 맵을 직접 순회해 결과를 만들면 이야기가 달라진다. HashMap의 순회 순서는 키의 해시값이 떨어지는 버킷의 순서이기 때문이다. OpenJDK 21에서 Long.hashCode()는 (int)(value ^ (value >>> 32))이고, HashMap은 이 값에 h ^ (h >>> 16)을 적용한 뒤 (n - 1) & hash로 버킷 번호를 정한다. 작은 양수 id라면 해시값이 id 자신이고, 기본 용량 16에서 버킷 번호는 id를 16으로 나눈 나머지다.

    Stream.of(3L, 1L, 2L, 3L, 1L).collect(Collectors.groupingBy(x -> x)).keySet();   // [1, 2, 3]
Stream.of(3L, 17L, 20L, 17L).collect(Collectors.groupingBy(x -> x)).keySet();    // [17, 3, 20]
Stream.of(3L, 17L, 20L, 17L)
      .collect(Collectors.groupingBy(x -> x, LinkedHashMap::new, Collectors.toList()))
      .keySet();                                                                  // [3, 17, 20]

    첫 줄은 마치 정렬된 것처럼 보인다. id 1, 2, 3이 버킷 1, 2, 3에 들어갔을 뿐이다. 둘째 줄에서 17은 버킷 1, 3은 버킷 3, 20은 버킷 4에 들어가므로 순회 순서가 17, 3, 20이 된다. 개발 환경의 작은 id로 테스트하면 순서가 맞아 보이다가, 운영 데이터의 큰 id에서 뒤섞이는 것이 바로 이 구조 때문이다. 순서가 의미 있는 결과를 맵 순회로 만든다면 셋째 줄처럼 LinkedHashMap::new를 넘겨 삽입 순서를 유지해야 한다. LinkedHashMap은 엔트리들을 이중 연결 리스트로 한 번 더 이어 두어 삽입 순서대로 순회한다.

    V6: 모든 것을 조인한 평평한 결과 한 번

    V5의 쿼리 2개를 1개로 줄일 수 있을까. 주문, 고객, 주문 줄을 모두 조인해 한 행에 모든 값을 담으면 된다. 이런 행을 평평한(flat) 데이터라고 부른다. 계층 구조가 없는 표 한 장이라는 뜻이다.

    List rows = em.createQuery(
        "select new shop.FlatRow(o.id, c.name, o.status, l.itemName, l.price, l.quantity)" +
        " from Order o join o.customer c join o.lines l order by o.id, l.id", FlatRow.class)
    .getResultList();

FlatRow[orderId=2, customerName=lee, status=ORDER, itemName=ink, price=3000, quantity=1]

    결과는 주문 수(3)가 아니라 주문 줄 수(6)만큼의 행이다. 일대다 조인이 행을 불린 것이다. 앞 회차의 컬렉션 페치 조인과 똑같은 현상인데, 차이가 하나 있다. Hibernate 6 사용자 가이드는 join fetch로 생긴 중복 결과를 Hibernate가 엔티티를 만든 뒤 메모리에서 자동으로 제거한다고 설명한다. 그 제거는 같은 엔티티 인스턴스가 여러 번 나오는 경우의 이야기다. DTO 행은 엔티티가 아니고 행마다 값이 다르므로, 여기서는 6행이 그대로 6개의 FlatRow가 되었다. 다시 계층 구조로 묶는 일은 애플리케이션 몫이다.

    Map> grouped = rows.stream().collect(Collectors.groupingBy(

    이 코드는 행마다 OrderRow를 새로 만들어 키로 쓴다. 첫 행과 둘째 행에서 만든 두 OrderRow는 서로 다른 객체인데도 같은 그룹에 들어갔다. HashMap은 키를 hashCode()로 버킷을 고른 뒤 equals()로 같은지 판단하는데, 레코드는 모든 컴포넌트가 같으면 같은 것으로 판단하는 equals와 그에 맞는 hashCode를 자동으로 갖기 때문이다. 결과 맵을 순회해 만들기 때문에 V6에서는 LinkedHashMap::new와 SQL의 order by가 둘 다 필요하다. SQL이 주문 순서로 행을 주고, LinkedHashMap이 처음 등장한 순서를 기억한다.

    java.lang.Record의 Javadoc은 자동 구현된 equals가 모든 컴포넌트가 같을 때 참을 돌려주고, hashCode는 각 컴포넌트의 해시 코드에서 유도되지만 정확한 알고리즘은 명시하지 않으며 바뀔 수 있다고 적는다. 그러니 해시값 자체에 의존하는 코드는 쓰지 말아야 하지만, "같은 컴포넌트면 같은 키"라는 성질은 믿어도 된다. 이 성질이 없는 일반 클래스를 키로 쓰면 어떻게 될까. equals를 재정의하지 않은 클래스로 같은 6행을 묶어 보니 그룹이 3개가 아니라 6개였다. Object.equals는 참조 동일성이므로 행마다 새로 만든 키 객체가 전부 다른 키가 된 것이다. 레코드 대신 일반 클래스를 키로 쓴다면 식별자(orderId)를 기준으로 equals와 hashCode를 반드시 함께 재정의해야 한다.

    V6의 대가: 중복 전송, 메모리, 그리고 페이징

    V6은 쿼리가 하나라는 점에서 가장 매력적으로 보인다. 하지만 비용이 사라진 것이 아니라 다른 곳으로 옮겨 갔다. 우리 데이터로 데이터베이스가 보낸 값의 수를 세어 보자. V5는 루트 3행 × 3열 = 9개, 주문 줄 6행 × 4열 = 24개로 모두 33개의 값을 보냈다. V6은 6행 × 6열 = 36개다. 그중 주문 쪽 값(orderId, customerName, status)은 V5에서 9개였지만 V6에서는 18개다. 주문 하나에 줄이 M개면 주문 쪽 열은 M번 반복된다. 주문 쪽 열이 넓을수록(주소, 메모 같은 긴 문자열), 줄 수가 많을수록 V6이 보내는 바이트는 V5보다 빠르게 늘어난다.

    받는 쪽의 메모리도 생각해야 한다. MySQL Connector/J 문서는 기본 설정에서 결과 집합(ResultSet)이 통째로 받아져 메모리에 저장된다고 적는다. 행 단위로 흘려받으려면 TYPE_FORWARD_ONLY, CONCUR_READ_ONLY 문장에 fetch size를 Integer.MIN_VALUE로 주어야 하고, 그 경우 결과를 다 읽거나 닫기 전에는 같은 커넥션으로 다른 쿼리를 보낼 수 없다는 제약이 붙는다. 기본 설정의 V6이라면 N × M행 전체가 드라이버 버퍼에 들어오고, Hibernate가 그것으로 FlatRow 리스트를 만들고, 다시 묶으면서 OrderRow와 LineRow를 만든다. 결과 리스트를 다 만들 때까지 이 객체들이 함께 힙에 있다.

    가장 결정적인 한계는 페이징이다. 같은 쿼리에 setFirstResult(0).setMaxResults(4)를 걸어 보았다.

    select ... from orders o1_0 join Customer c1_0 on ... join OrderLine l1_0 on ...
order by o1_0.id,l1_0.id offset ? rows fetch first ? rows only

FlatRow[orderId=1, ..., itemName=book-A, ...]
FlatRow[orderId=1, ..., itemName=book-B, ...]
FlatRow[orderId=2, ..., itemName=pen, ...]
FlatRow[orderId=2, ..., itemName=ink, ...]

    H2 방언이라 offset ... fetch first ... 구문이 나왔고, MySQL 방언이라면 LIMIT 절이 된다. 어느 쪽이든 데이터베이스가 자르는 단위는 행이다. 첫 4행을 받았더니 주문 1은 줄 2개가 다 왔지만, 주문 2는 줄 3개 중 pen과 ink만 오고 note가 잘렸다. 이것을 묶으면 주문 2의 줄이 2개뿐인, 틀린 응답이 만들어진다. API가 원하는 것은 "주문 20건"인데 SQL은 "행 20개"만 셀 수 있다. 앞 회차에서 컬렉션 페치 조인에 페이징을 걸 수 없었던 것과 같은 이유다. 다만 그때는 Hibernate가 경고를 남기고 메모리에서 페이징했지만, DTO 플랫 조회에서는 Hibernate가 결과가 계층 구조라는 것을 모르므로 아무 경고 없이 잘린 결과가 그대로 돌아온다.

    페이징이 필요하면 결국 주문 id를 먼저 페이지 단위로 구한 뒤 그 id들로 줄을 가져와야 하는데, 그것이 V5다. 또 V6은 내부 조인이라 줄이 없는 주문은 결과에서 사라진다. left join으로 바꾸면 줄 쪽 열이 NULL인 행이 생기므로 앞에서 본 대로 래퍼 타입으로 받고, 묶을 때 NULL 행을 빈 목록으로 처리하는 코드가 더 붙는다.

    여섯 행짜리 플랫 결과에서 앞의 4행만 자르면 주문 2의 세 번째 줄이 잘려 나가는 것을 보여 준다. 세로로 긴 표 하나를 가운데 둔다. 표의 열 머리글은 "주문 id", "고객", "상품". 행은 여섯 개: "1 kim book-A", "1 kim book-B", "2 lee pen", "2 lee ink", "2 lee note", "3 kim bag". 같은 주문 id의 행은 같은 배경색으로 칠한다(주문 1은 연한 초록, 주문 2는 연한 노랑, 주문 3은 연한 파랑). 넷째 행과 다섯째 행 사이에 빨간 가위 아이콘과 빨간 점선을 가로로 긋고 "LIMIT 4"라는 라벨을 단다. 다섯째 행 "2 lee note"는 반투명하게 흐리게 처리하고 옆에 "잘림"이라고 적는다. 표 오른쪽에는 결과로 만들어진 묶음 두 개를 그린다: "주문 1: 2줄 (정상)", "주문 2: 2줄 (원래 3줄)". 두 번째 묶음에 경고 삼각형 아이콘을 붙인다. 평면 벡터 스타일, 흰 배경. 데이터베이스는 행을 세고 API는 주문을 센다. 그 차이가 플랫 결과의 페이징을 막는다.

    애플리케이션과 데이터베이스 사이를 오가는 쿼리의 수와 각 응답의 모양을 세 방식별로 비교한다. 가로로 세 칸을 나눈 비교 시퀀스 다이어그램. 각 칸의 위쪽 제목은 "V4 건별 조회", "V5 IN 한 번", "V6 플랫 한 번". 각 칸 왼쪽에 "애플리케이션" 세로선, 오른쪽에 "데이터베이스" 세로선이 있다. V4 칸에는 오른쪽으로 가는 화살표 네 개("루트 조회", "주문 1의 줄", "주문 2의 줄", "주문 3의 줄")와 각각 돌아오는 점선 화살표가 있다. V5 칸에는 화살표 두 개("루트 조회", "IN (1, 2, 3)")와 돌아오는 점선 화살표 두 개. V6 칸에는 화살표 하나("전체 조인")와 돌아오는 굵은 점선 화살표 하나, 그 옆에 작은 표 아이콘에 "6행, 주문 열 반복"이라고 적는다. 각 칸 아래에 쿼리 수를 크게 적는다: "1+N", "2", "1". V6 칸 아래에는 작은 경고 아이콘과 "페이징 불가"라는 라벨을 단다. 평면 벡터 스타일, 흰 배경. V4는 루트 수만큼 왕복하고, V5는 두 번, V6은 한 번 왕복하는 대신 중복된 행을 받는다.

    API 개발 고급 정리: 무엇부터 쓰고 언제 넘어가는가

    이제 앞 회차와 이 회차를 합쳐 조회 API를 만드는 전체 길을 정리하자. 주문 목록을 만드는 방법은 크게 두 갈래였다. 엔티티를 조회한 뒤 DTO로 변환하는 길(앞 회차의 V2, V3, V3.1)과, 처음부터 DTO로 조회하는 길(이 회차의 V4, V5, V6)이다.

    방식쿼리 수(주문 N건)주문 단위 페이징핵심 장치

    표의 첫 줄은 지연 로딩이 연쇄될 때의 대략적인 규모만 나타낸 것이고, 정확한 수는 연관관계 구조와 영속성 컨텍스트에 이미 있는 엔티티에 따라 달라진다. 이 표에서 판단 기준을 끌어내 보자. 먼저 눈에 띄는 것은 "엔티티 + ToOne 페치 조인 + 배치 페치"와 "DTO 직접 조회 V5"가 같은 아이디어라는 점이다. 둘 다 ToOne은 조인으로, ToMany는 부모 id의 IN으로 가져온다. 쿼리 수도 비슷하다. 차이는 그 IN을 누가 만드느냐다. 배치 페치는 설정 한 줄로 Hibernate가 만들고, V5는 개발자가 쿼리와 조립 코드를 직접 쓴다.

    이 차이가 순서를 정한다. 엔티티 조회 쪽은 성능을 바꿀 때 코드를 거의 바꾸지 않는다. 페치 조인을 추가하거나 배치 크기를 바꾸는 것으로 쿼리 모양이 달라지고, DTO 변환 코드는 그대로다. 반대로 DTO 직접 조회는 화면이 바뀌면 쿼리 문자열, 생성자, 조립 코드가 함께 바뀐다. 그래서 합리적인 순서는 이렇다.

    1. 엔티티 조회 후 DTO로 변환한다. 엔티티를 API로 직접 내보내지 않는다는 원칙은 어느 경우에도 유지한다.
    2. ToOne 관계는 페치 조인으로 한 번에 가져온다. 행이 불어나지 않으므로 페이징에도 영향이 없다.
    3. 컬렉션은 페이징이 필요하면 배치 페치로, 필요 없으면 컬렉션 페치 조인으로 가져온다. 앞 회차의 결론 그대로다.
    4. 그래도 부족하면 DTO 직접 조회로 넘어간다. 목록이라면 V5를 기본으로, 단건 상세라면 V4로 충분하다. V6은 페이징이 없고 측정으로 이득이 확인될 때만 쓴다.
    5. 그래도 부족하면 JPA 밖으로 나간다. 데이터베이스 고유 기능이 필요한 쿼리는 네이티브 SQL이나 스프링 DB 편에서 본 JdbcTemplate으로 직접 쓴다.

    4단계에서 DTO 직접 조회로 얻는 이득은 정확히 무엇일까. 쿼리 수는 배치 페치와 비슷하므로 크지 않다. 남는 것은 SELECT 열 수와 영속성 컨텍스트 비용이다. 열 수를 줄이는 효과는 열이 짧고 몇 개 안 될 때는 작고, 긴 TEXT 열을 빼거나 SELECT한 열이 모두 보조 인덱스 안에 있어 클러스터형 인덱스를 다시 찾지 않아도 되는 경우(커버링 인덱스)에는 커진다. 앞에서 본 InnoDB 보조 인덱스의 구조, 즉 인덱스 열과 기본 키만 담는다는 사실에서 바로 나오는 결론이다. 영속성 컨텍스트 비용은 한 번에 수많은 엔티티를 읽는 조회에서 커진다. 엔티티마다 1차 캐시 등록과 스냅샷 보관이 따르고, 플러시 때 변경 감지가 그것을 순회하기 때문이다. 반대로 한 페이지에 수십 건을 읽는 API에서 이 비용이 병목인 경우는 드물다. 그 수준에서 응답이 느리다면 인덱스, 데이터 양, 캐시처럼 다른 곳을 먼저 의심하는 편이 맞다.

    DTO 직접 조회 코드를 어디에 둘지도 판단할 거리다. 엔티티를 저장하고 찾는 리포지토리는 도메인의 생명주기를 따르고, 특정 화면이나 API를 위한 조회 쿼리는 화면의 생명주기를 따른다. 화면 전용 DTO 조회를 핵심 리포지토리에 섞으면 화면이 바뀔 때마다 핵심 리포지토리가 흔들린다. 그래서 화면 전용 조회는 별도의 조회 전용 리포지토리(이름은 프로젝트마다 다르다)로 분리해 두는 구성이 흔하다. 이것은 명세가 정한 규칙이 아니라 변경의 이유가 다른 코드를 떼어 놓는다는 설계 판단이다.

    흔한 오해 다섯 가지

    "DTO 직접 조회가 엔티티 조회보다 항상 빠르다." V4는 DTO 직접 조회지만 1 + N개의 쿼리를 보낸다. 배치 페치를 건 엔티티 조회보다 쿼리가 훨씬 많다. 빠르기를 정하는 것은 조회 대상이 엔티티냐 DTO냐가 아니라 쿼리 수, 받는 행 수, 인덱스 사용이다. DTO냐 엔티티냐는 그다음에 영속성 컨텍스트 비용과 열 수를 조금 바꿀 뿐이다.

    "쿼리는 하나로 줄일수록 좋다." V6이 반례다. 쿼리 하나는 중복된 열의 전송, 드라이버 버퍼의 메모리, 페이징 불가라는 비용과 바꾼 것이다. 왕복 수, 전송량, 메모리, 기능 제약을 함께 보아야 한다.

    "select new로 조회하면 영속성 컨텍스트와 무관하다." 인자가 모두 스칼라 값일 때만 맞다. 명세 4.8.2절에 따라 엔티티를 가리키는 경로나 식별 변수를 인자로 넘기면 그 엔티티는 영속 상태가 된다. DTO가 엔티티를 품고 있으면 그 엔티티의 지연 로딩 연관관계는 여전히 프록시이고, 트랜잭션 밖에서 건드리면 앞 회차에서 본 지연 로딩 문제가 그대로 돌아온다.

    "groupingBy는 입력 순서를 지킨다." 기본 맵은 OpenJDK 21에서 HashMap이고, Javadoc은 맵의 타입조차 보장하지 않는다. 작은 id에서 정렬된 것처럼 보이는 것은 버킷 번호가 id와 같아서일 뿐이다. 순서가 필요하면 LinkedHashMap::new를 넘기거나, V5처럼 순서를 가진 리스트를 기준으로 조립한다.

    "IN 목록은 길어도 인덱스만 있으면 된다." MySQL 8.0에서 등치 범위가 200개 이상이면 옵티마이저는 행 수 추정에 인덱스 다이브 대신 통계를 쓰고, 범위 최적화 메모리가 기본 8388608바이트를 넘을 것 같으면 범위 접근 자체를 포기하고 전체 스캔도 후보에 넣는다. IN 목록은 페이지 크기 정도로 묶어 두고, 큰 목록은 나누어 보낸다.

    이 장의 핵심

    생성자 표현식은 결과 한 행을 객체 하나로 바꾸는 장치이고, 컬렉션을 만들지 않는다. 그래서 DTO 직접 조회에서 일대다 구조는 애플리케이션이 조립해야 하며, 그 조립 방식이 쿼리 수(1 + N, 2, 1)와 전송량, 페이징 가능 여부를 결정한다. 목록 조회의 기본은 루트를 페이징하고 자식을 IN 한 번으로 가져오는 방식이다. 이 아이디어는 엔티티 조회의 배치 페치와 같으므로, 먼저 엔티티 조회와 페치 조인·배치 페치로 해결하고, 부족할 때 DTO 직접 조회로 넘어간다.
    생성자 표현식
    JPQL의 select new 패키지.클래스(...). 명세상 정규화된 이름이 필요하고, 인자는 단일 값 표현식만 올 수 있으며, 인자 위치와 타입으로 생성자를 고른다.
    DTO 조회와 영속성 컨텍스트
    생성자 표현식으로 만든 객체는 관리되지 않는다. 실험에서 DTO 조회의 엔티티 로드 수는 0, 같은 데이터의 페치 조인은 9였다. 단, 인자로 넘긴 엔티티는 영속 상태가 된다.
    V4 건별 조회
    ToOne만 조인해 루트 DTO를 조회하고 루트마다 컬렉션 쿼리를 보낸다. 쿼리는 1 + N개이며 루트가 하나인 상세 조회에 적합하다.
    V5 IN 조회
    루트 id를 모아 in :ids 한 번으로 자식을 가져와 맵으로 묶어 붙인다. 쿼리 2개, 루트 페이징 가능, 배치 페치와 같은 아이디어다.
    V6 플랫 조회
    모든 것을 조인한 한 번의 쿼리로 행을 받아 애플리케이션에서 다시 묶는다. 루트 열이 자식 수만큼 반복되고, 행 단위로 잘리므로 루트 단위 페이징이 안 된다.
    IN 목록과 옵티마이저
    MySQL은 IN의 값마다 등치 범위를 만든다. 비유일 인덱스에서는 범위가 200개(eq_range_index_dive_limit 기본값) 이상이면 다이브 대신 통계로 행 수를 추정한다.
    groupingBy와 키
    OpenJDK 21의 기본 맵은 HashMap이라 순서를 보장하지 않는다. 키는 equals/hashCode가 값 기준이어야 하며, 레코드는 ObjectMethods 부트스트랩으로 이를 자동 제공한다.
    조회 최적화의 순서
    엔티티 조회 후 DTO 변환, ToOne 페치 조인, 컬렉션은 배치 페치나 페치 조인, 그다음 DTO 직접 조회, 마지막으로 네이티브 SQL이나 JdbcTemplate.

    목록 API가 느리다는 보고를 받으면 가장 먼저 볼 것은 요청 하나가 보내는 SQL의 개수와 모양이다. 쿼리 로그에서 같은 모양의 SQL이 파라미터만 바꿔 수십 번 반복된다면 N+1이고, 그것이 지연 로딩에서 오는지(엔티티 조회) 반복문에서 오는지(DTO 조회 V4)를 구분해야 한다. 앞의 것은 배치 페치 설정으로 줄지만, 뒤의 것은 설정으로 줄지 않고 코드를 V5 모양으로 바꿔야 한다. 같은 증상에 처방이 다르다는 점이 이 회차에서 가장 실무적인 구분이다.

    DTO 직접 조회를 도입할 때는 테스트가 결과 값까지 확인하는지 점검한다. 생성자 인자의 순서 바꿈은 예외 없이 틀린 값을 만들고, 외부 조인의 NULL은 데이터가 특정 모양일 때만 실행 시점 예외를 낸다. 개발 데이터에 "줄이 없는 주문", "같은 타입 필드가 여럿인 DTO"를 일부러 넣어 두면 이런 문제를 배포 전에 잡을 수 있다. 또 결과 순서를 맵 순회로 만든 코드는 작은 id에서 우연히 맞기 쉬우므로, 큰 id나 무작위 id로 순서를 검증한다.

    판단이 달라지는 조건도 있다. 화면에 필요한 열이 엔티티의 일부이고 그 엔티티에 긴 TEXT나 BLOB 열이 있다면, DTO 조회의 열 축소 효과가 커서 일찍 DTO 조회로 넘어갈 이유가 된다. 수만 건을 한 번에 읽는 배치나 리포트라면 영속성 컨텍스트 비용과 드라이버의 전체 버퍼링이 문제가 되므로, DTO 조회에 더해 IN 목록 분할이나 스트리밍 같은 별도의 설계가 필요하다. 반대로 한 페이지에 수십 건을 보여 주는 일반적인 API라면 엔티티 조회와 배치 페치로 충분한 경우가 많고, 그때 DTO 직접 조회로 바꾸는 것은 성능 대신 유지보수 비용만 늘린다.

    1. V4는 루트 1번과 주문마다 1번씩이므로 1 + 20 = 21개의 쿼리를 보내고, 행은 루트 20행과 주문 줄 100행으로 120행이다. V5는 루트 1번과 IN 1번으로 쿼리 2개, 행은 똑같이 20 + 100 = 120행이다. V6은 쿼리 1개, 행은 주문 줄 수인 100행이지만 각 행에 주문 쪽 열이 반복되어 실려 온다. V6에 setMaxResults(20)을 걸면 데이터베이스는 행 20개를 자르고, 주문마다 정확히 5행이므로 응답에는 주문 4건만 담긴다. 이 경우에는 잘린 주문이 생기지 않지만, 줄 수가 주문마다 다르면 마지막 주문의 줄이 잘려 틀린 응답이 된다. 어느 쪽이든 "주문 20건"이라는 API의 요구는 지켜지지 않는다.

    2. 두 번째와 세 번째 인자가 모두 String이라 타입 목록 (Long, String, String)이 정규 생성자와 일치한다. 따라서 오류 없이 실행되고, name에는 이메일이, email에는 이름이 들어간다. 생성자 표현식은 인자를 이름이 아니라 위치로 넘기기 때문이다. 잡는 방법으로는 결과 값까지 비교하는 테스트(이름과 이메일이 서로 다른 픽스처로), 같은 타입이 연달아 오지 않도록 DTO를 설계하거나 이름과 이메일을 별도 값 타입으로 감싸 타입 목록이 달라지게 하는 방법, 그리고 JPQL을 쓰는 대신 엔티티를 조회해 자바 코드에서 DTO를 만드는 방법이 있다. 마지막 방법은 컴파일러가 접근자 이름을 확인해 준다.

    3. [33, 5, 40]이 나온다. 작은 양수 long에서 Long.hashCode()는 (int)(value ^ (value >>> 32))이므로 값 자신이고, HashMap의 h ^ (h >>> 16)도 16비트 안쪽 값에는 영향이 없다. 키가 3개라 기본 용량 16에서 크기 조정이 일어나지 않으므로, 버킷 번호는 15 & hash, 곧 16으로 나눈 나머지다. 40은 버킷 8, 5는 버킷 5, 33은 버킷 1이다. 순회는 버킷 번호 순서이므로 33, 5, 40이다. 입력 순서와도, 크기 순서와도 다르다는 점이 핵심이다. 같은 버킷에 키가 둘 이상 들어가면 그 안의 순서는 삽입 방식에 따라 달라지는 구현 세부다(OpenJDK 21의 computeIfAbsent는 새 노드를 버킷의 맨 앞에 넣는다).

    4. 줄이 없는 주문의 행에서는 l.itemName, l.price, l.quantity가 모두 NULL이다. 생성자 검사는 타입만 보므로 쿼리 생성 단계는 통과하지만, 결과를 변환할 때 리플렉션이 NULL을 int 매개변수로 언박싱하려다 NullPointerException이 나고, Hibernate가 그것을 InstantiationException으로 감싼다. DTO는 NULL이 올 수 있는 열을 Integer 같은 래퍼 타입으로 받도록 바꾼다. 조립 코드는 줄 쪽 값이 모두 NULL인 행을 "줄 없음"으로 해석해, 그 주문의 줄 목록에 NULL로 채워진 LineRow를 넣지 말고 빈 목록을 두도록 고친다. 예를 들어 다운스트림을 Collectors.filtering(f -> f.itemName() != null, Collectors.mapping(...))로 감싸면, 그룹 키는 첫 행을 만날 때 맵에 이미 만들어지고 걸러진 행만 목록에 들어가지 않으므로 줄 없는 주문은 빈 목록을 갖게 된다.

     select new shop.CustomerCard(o.customer, o.status) from Order o로 DTO 리스트를 받았다. CustomerCard는 엔티티가 아닌 레코드다. Jakarta Persistence 3.1 명세 기준으로 옳은 설명은? DTO 조회이므로 영속성 컨텍스트에는 아무것도 등록되지 않는다. CustomerCard 객체가 영속 상태가 되어 변경 감지 대상이 된다. CustomerCard는 관리되지 않지만, 그 안에 들어간 Customer 엔티티는 영속 상태다. 생성자 인자로 엔티티를 넘길 수 없으므로 쿼리 생성 단계에서 예외가 난다. 명세 4.8.2절은 생성자 인자로 넘긴 단일 값 경로나 식별 변수가 엔티티를 가리키면 그 엔티티 인스턴스는 영속 상태가 된다고 정한다. 바깥의 레코드는 엔티티가 아니므로 관리 대상이 아니다. 엔티티를 인자로 넘기는 것은 문법상 허용되므로 예외도 나지 않는다. "DTO 조회는 영속성 컨텍스트와 무관하다"는 말은 인자가 모두 스칼라 값일 때만 맞다. 주문 DTO에 주문 줄 리스트를 담으려고 select new shop.OrderView(o.id, o.lines) from Order o를 썼더니 Hibernate 6.6이 "Missing constructor"를 보고했다. OrderView에는 (Long, List) 생성자가 있다. 가장 정확한 원인은? Hibernate가 List 같은 제네릭 타입을 생성자 인자로 다루지 못하기 때문이다. SQL 결과는 행의 목록이고 생성자 표현식은 한 행을 한 객체로 바꾸므로, 컬렉션 경로는 리스트가 아니라 원소 하나씩(조인)으로 해석되어 인자 타입이 맞지 않기 때문이다. 컬렉션이 지연 로딩이라 프록시 타입이 List와 다르기 때문이다. 생성자 표현식은 인자를 이름으로 짝짓는데 매개변수 이름이 lines와 다르기 때문이다. 명세는 SELECT 절이 단일 값 표현식만 반환해야 한다고 정하고 컬렉션 경로를 SELECT에 두는 쿼리를 올바르지 않은 예로 든다. Hibernate 6.6은 이를 너그럽게 받아 컬렉션과 조인한 원소로 해석하므로, 인자 타입이 OrderLine이 되어 (Long, OrderLine) 생성자를 찾다가 실패한다. 근본 원인은 행 하나가 객체 하나가 되는 구조다. 인자는 이름이 아니라 위치로 짝지어지고, 지연 로딩 프록시와는 관계가 없다. V6 방식(주문·고객·주문 줄 전체 조인)에 setFirstResult(0).setMaxResults(4)를 걸었다. 주문 1에 줄 2개, 주문 2에 줄 3개가 있다. 결과에 대한 설명으로 옳은 것은? Hibernate가 결과의 계층 구조를 알아 주문 4건을 메모리에서 페이징하고 경고를 남긴다. 데이터베이스가 주문 단위로 잘라 주문 4건과 그 줄 전부를 돌려준다. DTO 조회에는 페이징을 걸 수 없으므로 예외가 난다. 데이터베이스가 행 4개를 잘라 보내므로 주문 2는 줄 3개 중 2개만 담긴 채 경고 없이 돌아온다. SQL의 LIMIT(또는 OFFSET/FETCH)는 행을 센다. 플랫 결과의 한 행은 주문 줄 하나이므로, 앞의 4행은 주문 1의 2줄과 주문 2의 2줄이다. 컬렉션 페치 조인과 달리 DTO 플랫 조회에서는 Hibernate가 결과가 계층 구조라는 것을 모르므로 메모리 페이징도 경고도 없다. 실험에서도 주문 2의 note 줄이 빠진 결과가 그대로 돌아왔다. MySQL 8.0 InnoDB에서 order_id(비유일 보조 인덱스)에 대해 WHERE order_id IN (...)에 값 250개를 넣었다. 서버 변수는 모두 기본값이다. 옳은 설명은? 등치 범위가 eq_range_index_dive_limit(기본 200) 이상이므로 옵티마이저는 인덱스 다이브 대신 인덱스 통계로 행 수를 추정한다. IN 목록이 200개를 넘으면 MySQL은 인덱스를 쓰지 않고 항상 전체 테이블 스캔을 한다. IN 목록은 범위 접근이 아니므로 값마다 별도의 SQL 문장으로 나뉘어 실행된다. 보조 인덱스에는 기본 키가 없으므로 값마다 테이블 전체에서 행을 찾는다. eq_range_index_dive_limit는 행 수 추정 방법을 다이브에서 통계로 바꾸는 기준일 뿐, 인덱스 사용 여부를 정하지 않는다. 본문의 실측(MySQL 8.0.46, 8.4.13)에서도 값 250개일 때 트레이스의 index_dives_for_eq_ranges는 false였고 접근 방식은 range였다. 인덱스를 아예 쓰지 못하고 범위 최적화 없이 전체 스캔만 남는 것은 범위 최적화 메모리(range_optimizer_max_mem_size)를 넘을 때다(추정 행 수가 많으면 비용 비교로 전체 스캔을 고를 수는 있다). IN은 하나의 문장 안에서 여러 등치 범위로 처리되며, InnoDB 보조 인덱스의 각 레코드는 기본 키를 담고 있어 그 값으로 클러스터형 인덱스를 찾는다.
    생성자 표현식(constructor expression)
    JPQL SELECT 절의 NEW 클래스(인자...). 결과 한 행마다 지정한 클래스의 생성자를 호출해 객체를 만든다.
    DTO 직접 조회(DTO projection)
    엔티티를 거치지 않고 필요한 열만 조회해 처음부터 DTO로 받는 방식. 결과는 영속성 컨텍스트에 등록되지 않는다.
    SQM(Semantic Query Model)
    Hibernate 6이 HQL/JPQL과 Criteria를 해석해 만드는 의미 트리. 여기서 경로가 조인으로, new가 동적 인스턴스화 노드로 바뀐다.
    플랫 데이터(flat data)
    일대다 관계를 모두 조인해 계층 없이 한 표로 만든 결과. 부모 쪽 열이 자식 수만큼 반복된다.
    등치 범위(equality range)
    MySQL 범위 최적화에서 col = 값 하나에 해당하는, 값 하나짜리 범위. IN 목록의 값마다 하나씩 생긴다.
    인덱스 다이브(index dive)
    옵티마이저가 범위의 양 끝으로 인덱스를 실제로 내려가 범위 안의 행 수를 추정하는 방법. 정확하지만 범위가 많으면 느리다.
    IN 절 파라미터 패딩(IN clause parameter padding)
    Hibernate의 hibernate.query.in_clause_parameter_padding. IN의 자리 표시자 수를 2의 거듭제곱으로 올리고 남는 자리를 채운다(사용자 가이드는 null을 바인딩한다고 적고, 6.6.53 실행에서는 마지막 값이 반복되었다).
    ObjectMethods 부트스트랩
    레코드의 equals, hashCode, toString이 쓰는 invokedynamic의 부트스트랩 메서드. 컴포넌트 필드 핸들을 엮어 실제 구현을 런타임에 만든다.
