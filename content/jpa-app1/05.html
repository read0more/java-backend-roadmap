    이 회차의 질문: 화면에서 돌아온 값은 엔티티인가

    앞 회차까지 회원·상품·주문 도메인을 엔티티로 만들고, 그 위에 리포지토리와 서비스를 올려 테스트로 동작을 확인했다. 이 회차는 그 위에 웹 계층을 얹는다. 브라우저가 보낸 HTTP 요청이 컨트롤러에 도착하고, 서비스가 트랜잭션을 열어 엔티티를 바꾸고, 결과를 HTML로 그려 돌려보내는 한 바퀴를 기능마다 반복한다. 기능 목록은 평범하다. 홈 화면과 공통 레이아웃, 회원 등록과 목록, 상품 등록·목록·수정, 상품 주문, 주문 목록 검색과 취소다.

    그런데 이 평범한 기능 중 하나에서 JPA를 쓰는 웹 애플리케이션이라면 반드시 한 번은 부딪히는 질문이 나온다. 상품 수정이다. 수정 화면은 데이터베이스에서 읽은 상품으로 폼을 채워 보여 주고, 사용자가 값을 고쳐 제출하면 서버가 그 값을 받는다. 이때 서버 손에 들어온 것은 HTTP 요청 본문에 실린 문자열 몇 개와, 스프링이 그 문자열로 새로 만든 객체다. 식별자(id)는 들어 있지만, 처음 화면을 그릴 때 읽었던 엔티티 인스턴스는 이미 다른 요청, 다른 트랜잭션, 다른 영속성 컨텍스트와 함께 사라졌다. 이 값을 데이터베이스에 반영하는 방법은 두 가지다. 영속 엔티티를 다시 조회해 값을 바꾸는 변경 감지(dirty checking)와, 넘겨받은 객체를 EntityManager.merge()에 그대로 넘기는 병합(merge)이다. 둘 다 결국 UPDATE 문 하나를 만들지만, 만드는 경로와 실패하는 방식이 다르다.

    이 회차는 두 방법을 말로만 비교하지 않고 실제로 돌려 본다. 실험 환경은 JDK 21, Hibernate ORM 6.6.53.Final, H2 2.3.232 인메모리 데이터베이스다. 스프링 없이 Hibernate를 직접 부트스트랩하고 hibernate.show_sql=true로 SQL 로그를 보았다. 스프링 쪽 동작은 Spring Framework 6.2.19, Spring Data JPA 3.5.13, Spring Boot 3.5.16의 클래스 파일을 javap로 열어 확인했고, 본문의 컨트롤러·서비스 예제는 Spring Framework 6.2.19 라이브러리로 컴파일되는 것을 확인했다. 본문에 붙인 SQL 로그는 이 실험에서 나온 그대로다. 실험용 엔티티의 클래스 이름이 테이블 이름이 되므로 로그에는 Item, orders 같은 이름이 보인다.

    홈 화면과 레이아웃: 요청 하나가 HTML이 되기까지

    홈 화면은 링크 몇 개가 전부인 페이지지만, 이 페이지 하나가 그려지는 경로가 이후 모든 화면의 뼈대다. 브라우저가 GET /를 보내면 톰캣의 요청 처리 스레드 하나가 이 요청을 맡아 DispatcherServlet을 호출한다. 디스패처 서블릿은 핸들러 매핑에서 @GetMapping("/")이 붙은 컨트롤러 메서드를 찾고, 핸들러 어댑터가 그 메서드를 호출한다. 메서드가 문자열 "home"을 반환하면 그것은 응답 본문이 아니라 뷰 이름(view name)이다. 뷰 리졸버가 이 이름을 실제 템플릿 위치로 바꾸고, 뷰 객체가 모델을 받아 HTML을 응답 스트림에 쓴다. 스프링 MVC 편에서 본 구조를 다시 꺼내는 이유는, 이 회차의 쟁점이 거의 모두 "이 흐름의 어느 구간에서 영속성 컨텍스트가 살아 있는가"로 모이기 때문이다.

    스프링 부트는 타임리프(Thymeleaf) 스타터가 있으면 ThymeleafViewResolver를 자동으로 등록한다. 템플릿 위치의 기본값은 spring.thymeleaf.prefix=classpath:/templates/, spring.thymeleaf.suffix=.html이다(Spring Boot 3.5.16의 설정 메타데이터로 확인). 그래서 뷰 이름 "home"은 classpath:/templates/home.html이 되고, "members/createMemberForm"은 templates/members/createMemberForm.html이 된다. 반면 CSS·자바스크립트·이미지 같은 정적 리소스는 spring.web.resources.static-locations의 기본값인 classpath:/META-INF/resources/, classpath:/resources/, classpath:/static/, classpath:/public/에서 찾는다. 템플릿은 서버가 모델을 넣어 가공한 뒤 내보내는 파일이고, 정적 리소스는 가공 없이 그대로 내보내는 파일이다. 그 차이가 디렉터리 구분으로 드러나 있다.

    상점 관리

    서버가 home.html을 렌더링하면 th:replace가 붙은 head는 통째로 header 조각으로 바뀌고, 그 안에 적어 둔 title은 사라진다. 그러나 같은 파일을 서버 없이 브라우저로 바로 열면 브라우저는 th:* 속성을 모르는 속성으로 보고 무시하므로 원래 적힌 내용이 그대로 보인다. 타임리프 템플릿이 그 자체로 올바른 HTML이어서 디자이너가 서버 없이도 열어 볼 수 있다는 성질을 내추럴 템플릿(natural template)이라고 부른다. @{/css/app.css} 같은 링크 표현식은 애플리케이션의 컨텍스트 경로를 앞에 붙여 주므로, 애플리케이션이 /shop 아래에 배포되어도 링크를 고칠 필요가 없다. 조각에 매개변수를 선언해 제목이나 링크 목록을 호출하는 쪽에서 넘기게 할 수도 있지만(th:fragment="common_header(title,links)" 형태), 레이아웃을 정교하게 만드는 일은 화면 기술의 문제이므로 이 권에서는 여기서 멈춘다.

    렌더링 단계를 한 층만 더 들여다보자. 타임리프는 스프링과 함께 쓰일 때 ${...} 안의 식을 스프링 표현식 언어(SpEL)로 평가한다. ${member.name}은 모델에서 member라는 이름의 객체를 꺼내 getName()을 호출하는 것과 같다. 즉 템플릿은 그저 게터를 호출하는 자바 코드이고, 그 게터가 엔티티의 지연 로딩 프록시를 건드리면 프록시는 초기화를 시도한다. 템플릿 렌더링을 "화면 그리기"로만 생각하면 놓치기 쉬운 사실이다.

    컨트롤러·서비스·뷰가 차례로 실행되는 동안 트랜잭션 구간은 서비스 안에만 있고, 뷰 렌더링은 트랜잭션 밖에서 일어난다는 점을 보여 준다. 가로로 긴 시퀀스 다이어그램. 왼쪽부터 세로 생명선 다섯 개: "브라우저", "DispatcherServlet", "컨트롤러", "서비스", "타임리프 뷰". 맨 오른쪽 바깥에 원통 모양 "DB". 위에서 아래로 화살표: 브라우저→DispatcherServlet "GET /orders", DispatcherServlet→컨트롤러 "orderList()", 컨트롤러→서비스 "search()", 서비스→DB "SQL", 서비스→컨트롤러 "List 반환", 컨트롤러→DispatcherServlet "뷰 이름", DispatcherServlet→타임리프 뷰 "render(model)", 타임리프 뷰→DB 점선 화살표 "지연 로딩?", DispatcherServlet→브라우저 "HTML". 서비스 생명선 위에 주황색 막대를 겹쳐 "트랜잭션"이라고 표시하고, 요청 전체를 감싸는 연한 파란 띠에 "영속성 컨텍스트 (OSIV 켜짐)"라고 적는다. 평면적인 기술 도식 스타일, 흰 배경. 트랜잭션은 서비스 메서드 안에서 끝나지만 뷰 렌더링은 그 뒤에 일어난다. 렌더링 중 지연 로딩이 가능한지는 영속성 컨텍스트의 범위에 달렸다.

    회원 등록: 폼 객체, 검증, 그리고 PRG

    회원 등록 화면은 이름 입력란 하나짜리 폼이다. 여기서 첫 번째 설계 결정이 나온다. 폼 데이터를 바인딩할 객체로 Member 엔티티를 그대로 쓸 것인가, 화면 전용 객체(폼 객체, form object)를 따로 만들 것인가. 엔티티를 그대로 쓰면 클래스가 하나 줄어든다. 그 대가를 하나씩 따져 보자.

    1. 세터가 필요해진다. 스프링의 데이터 바인더는 기본 설정에서 요청 파라미터 이름과 같은 프로퍼티를 찾아 세터로 값을 넣는다. Member에 setName()을 열어 두면 도메인의 어느 코드에서든 회원 이름을 바꿀 수 있게 되고, 엔티티 설계 단계에서 세터를 닫고 의미 있는 변경 메서드만 두려던 의도가 무너진다.
    2. 대량 할당(mass assignment)이 열린다. 바인더는 폼에 입력란이 있는지 따지지 않는다. 요청에 id=7이나 등급 같은 파라미터를 끼워 넣으면, 그 이름의 쓰기 가능한 프로퍼티가 있는 한 값이 들어간다. 화면에 없는 필드라고 안전한 것이 아니다.
    3. 검증 규칙은 화면마다 다르다. 가입 화면에서 필수인 값이 관리자 화면에서는 선택일 수 있다. 엔티티 필드에 @NotEmpty를 붙이면 그 규칙은 화면 하나의 규칙이 아니라 엔티티를 쓰는 모든 곳의 규칙이 된다.
    4. 의존 방향이 뒤집힌다. 오류 메시지, 화면 전용 필드, 입력 형식 같은 웹 계층의 사정이 도메인 모델 안으로 흘러든다. 도메인은 웹을 모르는 것이 계층 구조의 원칙이다.

    그래서 화면이 단순해 보여도 폼 객체를 따로 둔다. 폼 객체는 세터가 열려 있어도 괜찮다. 그 객체의 수명은 요청 하나이고, 할 일은 요청 파라미터를 담아 검증받는 것뿐이기 때문이다.

    public class MemberForm {
    @NotEmpty(message = "이름은 필수다")
    private String name;

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
}

@Controller
public class MemberController {
    private final MemberService memberService;

    public MemberController(MemberService memberService) {
        this.memberService = memberService;
    }

    @GetMapping("/members/new")
    public String createForm(Model model) {
        model.addAttribute("memberForm", new MemberForm());
        return "members/createMemberForm";
    }

    @PostMapping("/members/new")
    public String create(@Valid MemberForm form, BindingResult result) {
        if (result.hasErrors()) {
            return "members/createMemberForm";
        }
        memberService.join(form.getName());
        return "redirect:/";
    }
}

@Service
@Transactional(readOnly = true)
public class MemberService {
    @PersistenceContext
    private EntityManager em;

    @Transactional
    public Long join(String name) {
        Member member = new Member(name);
        em.persist(member);
        return member.getId();
    }
}

    서비스의 join()은 MemberForm을 받지 않고 이름 문자열만 받는다. 폼 객체는 웹 계층의 것이므로 서비스 계층으로 내려보내지 않는다. 받아야 할 값이 많아지면 서비스 계층 소속의 명령 객체(command DTO)를 따로 만든다. 이렇게 하면 같은 서비스를 배치 작업이나 API 컨트롤러가 호출해도 웹 폼 클래스에 묶이지 않는다.

    검증에 실패한 POST를 한 단계씩 따라가기

    사용자가 이름을 비운 채 제출했다고 하자. 요청은 POST /members/new, 본문은 name=이다.

    1. ModelAttributeMethodProcessor가 MemberForm 인스턴스를 만들고 name 파라미터를 바인딩한다. 값은 빈 문자열이다.
    2. 파라미터에 @Valid가 붙어 있으므로 바인딩 직후 Bean Validation이 실행된다. @NotEmpty는 빈 문자열을 위반으로 보고, 그 결과가 FieldError로 BindingResult에 기록된다.
    3. 바로 다음 파라미터로 BindingResult가 선언되어 있으므로 스프링은 예외를 던지지 않고 컨트롤러 메서드를 호출한다. 이 파라미터가 없으면 MethodArgumentNotValidException이 발생하고 컨트롤러 메서드는 호출되지 않는다(Spring Framework 6.2.19의 ModelAttributeMethodProcessor 바이트코드에서 이 예외를 생성하는 지점을 확인했다).
    4. 컨트롤러는 hasErrors()를 보고 같은 뷰 이름을 반환한다. 이때 모델에는 사용자가 입력한 값이 담긴 MemberForm이 "memberForm"이라는 이름으로 들어 있다. @ModelAttribute의 이름을 생략하면 타입 이름의 첫 글자를 소문자로 바꾼 이름이 모델 키가 되기 때문이다. GET 요청에서 model.addAttribute("memberForm", ...)로 넣은 이름과 같으므로 템플릿은 두 경우를 구별하지 않는다.

    th:object는 폼이 다룰 객체를 정하고, 그 안의 *{name}은 그 객체를 기준으로 한 선택 표현식(selection expression)이다. 타임리프+스프링 문서에 따르면 th:field="*{name}"은 id="name" name="name" value="..." 세 속성을 만든다. 검증에 실패해 화면이 다시 그려질 때 입력란에 사용자가 쳤던 값이 남아 있는 것은 value가 바인딩 결과에서 오기 때문이다. th:errors는 그 필드의 오류 메시지들을 출력하고, th:errorclass는 오류가 있을 때만 CSS 클래스를 덧붙인다.

    성공한 POST는 리다이렉트로 끝낸다

    검증을 통과하면 서비스에 이름만 넘기고 "redirect:/"를 반환한다. 이 접두어를 본 뷰 리졸버는 템플릿을 찾지 않고 리다이렉트 뷰를 만들며, 응답은 Location 헤더가 붙은 3xx 응답이 된다. 브라우저는 그 주소로 GET을 새로 보낸다. 사용자가 새로고침을 누르면 브라우저는 마지막 요청인 GET을 반복할 뿐 POST를 다시 보내지 않으므로 같은 회원이 두 번 가입되지 않는다. 이것이 POST/Redirect/GET(PRG) 패턴이고, HTTP 웹 기본 지식과 스프링 MVC 편에서 다룬 그대로다.

    서비스 안에서 em.persist(member)가 실행될 때 데이터베이스에서 일어나는 일도 로그로 보자. 실험에서 회원 하나와 상품 하나를 한 트랜잭션에서 저장하자 다음 로그가 나왔다. 식별자 전략은 @GeneratedValue 기본값이고, H2에서는 시퀀스가 쓰였다.

    Hibernate: select next value for Member_SEQ
Hibernate: select next value for Item_SEQ
Hibernate: insert into Member (name,id) values (?,?)
Hibernate: insert into Item (name,price,stockQuantity,id) values (?,?,?,?)

    persist() 두 번은 시퀀스 값만 가져왔고, INSERT 두 개는 커밋 시점의 플러시에서 한꺼번에 나갔다. persist()는 "지금 INSERT하라"가 아니라 "이 객체를 영속성 컨텍스트에 등록하고 식별자를 정하라"는 뜻이기 때문이다. 같은 실험의 DDL 로그에는 create sequence Item_SEQ start with 1 increment by 50이 찍혀 있었다. 시퀀스가 50씩 증가하도록 만들어 두고, Hibernate는 한 번 가져온 값으로 여러 식별자를 메모리에서 나눠 쓴다. MySQL에서 흔히 쓰는 IDENTITY 전략은 사정이 다르다. 식별자를 데이터베이스가 INSERT 시점에 정하므로, Hibernate는 식별자를 알기 위해 persist() 시점에 INSERT를 바로 실행한다. 어느 쪽이든 join()이 반환하는 member.getId()는 이미 값이 채워져 있다.

    회원 목록 조회: 엔티티를 화면에 그대로 넘겨도 되는가

    목록은 JPQL 한 줄로 끝난다. em.createQuery("select m from Member m", Member.class).getResultList(). JPQL은 테이블이 아니라 엔티티와 그 필드를 대상으로 쓰는 쿼리 언어이고, Hibernate가 매핑 정보를 보고 SQL로 번역한다. 조회 결과로 만들어진 Member 인스턴스들은 그 트랜잭션의 영속성 컨텍스트에 등록된다. 같은 식별자의 회원을 이미 영속성 컨텍스트가 갖고 있었다면 새 인스턴스를 만들지 않고 기존 인스턴스를 돌려준다. 한 영속성 컨텍스트 안에서 같은 행은 같은 자바 객체 하나로 표현된다는 이 규칙(동일성 보장)이 뒤에서 merge를 이해할 때 다시 쓰인다.

    컨트롤러가 model.addAttribute("members", memberService.findMembers())로 엔티티 목록을 그대로 넘기는 것은 서버 사이드 렌더링에서는 비교적 무해하다. 템플릿은 서버 안에서 실행되고, 어떤 필드를 출력할지 템플릿이 고르며, 출력하지 않은 필드는 응답에 실리지 않는다. 다만 두 가지는 기억해 둔다. 첫째, 템플릿이 연관 엔티티를 따라가면 그 시점에 지연 로딩 SQL이 실행될 수 있고, 그것이 성공할지는 영속성 컨텍스트가 그때 열려 있는지에 달렸다. 둘째, 같은 엔티티를 JSON API 응답으로 그대로 반환하는 것은 전혀 다른 문제다. 엔티티의 모든 필드가 직렬화되어 외부와의 계약이 되므로 엔티티 필드 하나를 바꾸면 API 스펙이 바뀌고, 양방향 연관관계는 서로를 따라가며 직렬화가 끝나지 않을 수 있으며, 지연 로딩 프록시를 만난 직렬화 라이브러리가 예외를 던질 수 있다. API 응답을 DTO로 분리하는 문제는 JPA 활용 2편의 주제다.

    상품 등록과 목록: 규칙은 엔티티가 지킨다

    상품 등록도 모양은 같다. ItemForm에 이름·가격·재고를 받아 검증하고, 서비스가 엔티티를 만들어 persist()한다. 여기서 짚을 것은 "가격과 재고는 음수일 수 없다" 같은 규칙을 어디에 두느냐다. 폼 검증에 두면 사용자에게 친절한 오류 메시지를 보여 줄 수 있다. 그러나 상품은 등록 화면으로만 만들어지지 않는다. 관리자 일괄 등록, 외부 API, 다른 서비스의 코드도 상품을 만들고 고친다. 그 모든 경로를 막는 곳은 엔티티 자신뿐이다. 그래서 같은 규칙이 두 곳에 있는 것은 중복이 아니라 역할 분담이다. 폼 검증은 입력 오류를 사용자에게 돌려주는 장치이고, 엔티티의 검사는 도메인 불변식(invariant)을 지키는 장치다.

    @Entity
public class Item {
    @Id @GeneratedValue
    private Long id;
    private String name;
    private int price;
    private int stockQuantity;

    protected Item() {}

    public Item(String name, int price, int stockQuantity) {
        change(name, price, stockQuantity);
    }

    public void change(String name, int price, int stockQuantity) {
        if (price < 0 || stockQuantity < 0) {
            throw new IllegalArgumentException("가격과 재고는 음수일 수 없다");
        }
        this.name = name;
        this.price = price;
        this.stockQuantity = stockQuantity;
    }

    public void removeStock(int quantity) {
        int rest = stockQuantity - quantity;
        if (rest < 0) {
            throw new IllegalStateException("재고 부족: 남은 수량 " + stockQuantity);
        }
        stockQuantity = rest;
    }

    public void addStock(int quantity) { stockQuantity += quantity; }

    public Long getId() { return id; }
    public String getName() { return name; }
    public int getPrice() { return price; }
    public int getStockQuantity() { return stockQuantity; }
}

    생성자와 change()가 같은 검사를 거치므로 Item 인스턴스는 어느 경로로 만들어지든 음수 가격을 가질 수 없다. 세터는 하나도 없다. protected 기본 생성자는 JPA 명세가 엔티티에 요구하는 무인자 생성자다. Hibernate는 조회 결과로 엔티티를 만들 때 이 생성자로 빈 인스턴스를 만든 뒤 필드에 값을 채운다. @Id가 필드에 붙어 있으므로 접근 방식은 필드 접근이고, 값을 채울 때 세터를 거치지 않는다. 그래서 세터가 없어도 조회는 정상 동작한다.

    상품 목록 화면은 회원 목록과 같고, 각 행에 수정 화면으로 가는 링크를 단다. th:href="@{/items/{id}/edit(id=${item.id})}"처럼 쓰면 타임리프가 경로 변수 자리에 값을 넣어 /items/1/edit 같은 주소를 만든다. 이 링크를 누르는 순간부터 이 회차의 본론이 시작된다.

    상품 수정: 폼에서 돌아온 객체는 어떤 상태인가

    수정 기능은 요청 두 개로 이루어진다. GET /items/1/edit는 상품을 조회해 폼 객체에 값을 옮겨 담고 화면을 그린다. POST /items/1/edit는 사용자가 고친 값을 받아 반영한다.

    @Controller
public class ItemController {
    private final ItemService itemService;

    public ItemController(ItemService itemService) {
        this.itemService = itemService;
    }

    @GetMapping("/items/{itemId}/edit")
    public String updateForm(@PathVariable("itemId") Long itemId, Model model) {
        Item item = itemService.findOne(itemId);
        ItemForm form = new ItemForm();
        form.setId(item.getId());
        form.setName(item.getName());
        form.setPrice(item.getPrice());
        form.setStockQuantity(item.getStockQuantity());
        model.addAttribute("form", form);
        return "items/updateItemForm";
    }

    @PostMapping("/items/{itemId}/edit")
    public String update(@PathVariable("itemId") Long itemId,
                         @ModelAttribute("form") ItemForm form) {
        itemService.updateItem(itemId, form.getName(), form.getPrice(), form.getStockQuantity());
        return "redirect:/items";
    }
}

    두 요청 사이에 무슨 일이 있었는지 시간 순서로 보자. GET 요청의 서비스 호출은 트랜잭션을 열고 Item을 조회해 영속성 컨텍스트에 올렸다가 트랜잭션을 끝냈다. 그 요청이 끝나면서 영속성 컨텍스트도 닫혔다. 사용자가 화면을 보며 값을 고치는 몇 초, 몇 분 동안 서버에는 그 상품을 기억하는 객체가 아무것도 없다. POST 요청이 오면 스프링은 요청 파라미터로 ItemForm을 새로 만든다. 이 객체에는 상품의 식별자와 새 값이 들어 있지만 JPA는 이 객체의 존재를 모른다. 이 상황을 정확히 말하려면 엔티티의 상태를 구분해야 한다.

    상태뜻이 상태가 되는 대표적인 순간
    비영속(new, transient)영속성 컨텍스트와 아무 관계가 없다. 보통 식별자가 없다.new Item(...) 직후
    영속(managed)영속성 컨텍스트가 관리한다. 변경 감지의 대상이다.persist() 이후, find()나 JPQL로 조회한 직후
    준영속(detached)식별자가 있고 한때 관리되었지만 지금은 관리되지 않는다.트랜잭션 범위 영속성 컨텍스트가 커밋으로 끝난 뒤, detach()·clear()·close() 이후
    삭제(removed)삭제가 예약되었다. 플러시 때 DELETE가 나간다.remove() 이후 커밋 전

    Jakarta Persistence 3.1 명세 3.2.7절은 엔티티가 준영속이 되는 경우로 트랜잭션 범위 영속성 컨텍스트에서의 커밋, 롤백, 명시적 분리, 영속성 컨텍스트 비우기(clear), 엔티티 매니저 닫기, 그리고 직렬화되거나 값으로 다른 계층에 전달되는 경우를 든다. 마지막 항목이 웹 애플리케이션의 상황과 닮았다. 엔티티의 값이 HTML 폼을 거쳐 브라우저에 갔다가 다시 돌아왔으니, 값으로 다른 계층에 전달된 것과 같다.

    엄밀히 말하면 ItemForm은 엔티티 클래스가 아니므로 어떤 상태도 아니다. 그러나 이 폼의 값으로 Item 인스턴스를 새로 만들고 식별자까지 채우면, 그 인스턴스는 데이터베이스의 행과 같은 식별자를 가지면서 영속성 컨텍스트에는 없는 객체가 된다. JPA 입장에서 이것은 "한때 영속이었다가 분리된 객체"와 구별되지 않는다. 그래서 실무에서는 이런 객체도 준영속 엔티티라고 부른다. 그리고 준영속 엔티티는 아무리 값을 바꿔도 데이터베이스에 반영되지 않는다. 실험으로 확인해 보자. 한 엔티티 매니저에서 상품을 조회하고 트랜잭션을 끝낸 뒤 그 엔티티 매니저를 닫고, 객체의 가격을 바꾼 다음, 새 엔티티 매니저에서 빈 트랜잭션을 커밋했다.

    EntityManager em = emf.createEntityManager();
em.getTransaction().begin();
Item i = em.find(Item.class, id);
em.getTransaction().commit();
em.close();                       // 이제 i는 준영속

    두 번째 엔티티 매니저는 i를 모르고(contains가 false), 커밋해도 UPDATE가 없다. 이후 다시 조회한 가격도 바뀌지 않았다. 준영속 엔티티의 값을 반영하려면 두 길 중 하나를 골라야 한다. 영속 엔티티를 다시 얻어 값을 옮기거나(변경 감지), JPA에게 옮겨 달라고 부탁하거나(merge).

    POST 요청의 식별자는 사용자가 마음대로 바꿀 수 있다. 폼의 숨은 필드든 URL의 경로 변수든 브라우저 개발자 도구나 직접 만든 HTTP 요청으로 다른 상품의 번호를 넣을 수 있다. 따라서 "이 사용자가 이 식별자의 상품을 수정할 권한이 있는가"는 서버가 요청마다 확인해야 한다. 위 예제는 경로 변수 itemId를 쓰고 폼의 id는 무시한다. 둘이 다를 때 어느 쪽을 믿을지 헷갈릴 여지를 없애기 위해서다.

    변경 감지: 스냅샷과 플러시가 UPDATE를 만든다

    변경 감지는 영속 엔티티에만 일어난다. 원리는 단순하다. Hibernate는 엔티티를 조회해 인스턴스를 만들 때 그 순간의 필드 값을 따로 복사해 둔다. 이 복사본을 스냅샷이라고 부르며, Hibernate 6.6에서는 영속성 컨텍스트가 엔티티마다 들고 있는 EntityEntry의 getLoadedState()가 이 배열을 돌려준다. 플러시가 일어나면 Hibernate는 영속성 컨텍스트의 관리 엔티티를 하나씩 꺼내 현재 필드 값과 스냅샷을 비교한다. 이 비교는 DefaultFlushEntityEventListener의 dirtyCheck()가 맡는다. 값이 다른 필드가 하나라도 있으면 그 엔티티의 UPDATE를 쓰기 지연 저장소(action queue)에 넣고, 플러시의 마지막에 SQL을 실행한다. 메서드 이름은 Hibernate 6.6.53의 클래스 파일에서 확인했다.

    실험으로 두 경우를 비교했다. 첫 번째는 가격을 10000에서 20000으로 바꿨고, 두 번째는 이미 20000인 가격에 다시 20000을 넣었다. 커밋 직전에 -- before commit을 찍어 SQL이 언제 나가는지 표시했다.

    em.getTransaction().begin();
Item i = em.find(Item.class, id);
i.setPrice(20000);
System.out.println("-- before commit");
em.getTransaction().commit();

    로그에서 세 가지를 읽을 수 있다. 첫째, UPDATE는 setPrice()를 호출한 순간이 아니라 커밋 때 나갔다. 둘째, 가격만 바꿨는데 UPDATE의 SET 절에는 name, price, stockQuantity가 모두 들어 있다. Hibernate의 기본 UPDATE는 매핑된 모든 컬럼을 쓰므로 엔티티마다 UPDATE 문장 모양이 하나로 고정된다. 셋째, 같은 값을 다시 넣은 두 번째 경우에는 UPDATE가 아예 없다. 변경 감지는 "세터가 호출되었는가"가 아니라 "값이 스냅샷과 다른가"를 보기 때문이다.

    바뀐 컬럼만 SET 절에 넣고 싶으면 Hibernate의 @DynamicUpdate를 엔티티에 붙인다. 이번에는 @Version 필드가 있는 실험용 엔티티 VItem에 @DynamicUpdate를 붙이고 가격만 바꿨다.

    Hibernate: update VItem set price=?,version=? where id=? and version=?

    SET 절에 price와 version만 남았다. 대신 바뀐 필드 조합마다 다른 SQL 문장이 만들어진다. 컬럼이 아주 많거나 일부 컬럼이 큰 테이블에서 고려할 선택지이고, 기본값을 바꿔야 할 이유는 대개 없다. WHERE 절의 and version=?는 뒤에서 낙관적 락을 다룰 때 다시 본다.

    변경 감지가 일어나지 않는 경우

    변경 감지는 플러시가 있어야 의미가 있다. Jakarta Persistence 명세 3.2.4절은 영속성 컨텍스트가 트랜잭션 커밋 시점에 데이터베이스와 동기화되며, 활성 트랜잭션이 없거나 영속성 컨텍스트가 현재 트랜잭션에 참여하지 않았으면 프로바이더가 데이터베이스로 플러시해서는 안 된다고 정한다. 트랜잭션 밖에서 영속 엔티티를 바꾸면 그 변경은 아직 아무 데도 반영되지 않은 채 메모리에 남는다. 이 "남는다"는 점이 OSIV 절에서 문제를 일으킨다.

    스프링의 읽기 전용 트랜잭션도 변경 감지를 꺼 버린다. Spring Framework 6.2.19의 HibernateJpaDialect.beginTransaction()은 트랜잭션 정의가 읽기 전용이면 Hibernate 세션의 플러시 모드를 FlushMode.MANUAL로 바꾸고, 엔티티 매니저가 그 트랜잭션을 위해 새로 만들어진 경우(OSIV처럼 이미 열린 엔티티 매니저를 재사용하지 않는 경우)에는 세션에 setDefaultReadOnly(true)도 호출한다(소스로 확인). 플러시 모드가 MANUAL이면 커밋 때 자동 플러시가 일어나지 않고, 기본 읽기 전용 세션에서 조회한 엔티티는 Hibernate가 변경 감지 대상에서 뺀다(Hibernate 6.6.53 실험으로 확인). 그래서 클래스에 @Transactional(readOnly = true)를 붙이고 쓰기 메서드에만 @Transactional을 다시 붙이는 관례에는 이유가 있다. 쓰기 메서드에 @Transactional을 빠뜨리면, 그 메서드는 클래스의 읽기 전용 트랜잭션으로 실행되고 엔티티를 아무리 바꿔도 UPDATE가 나가지 않는다. 예외도 나지 않으니 테스트로 잡지 않으면 오래 숨어 있는 버그가 된다.

    영속성 컨텍스트 안에 엔티티 인스턴스와 조회 시점 스냅샷이 짝으로 저장되고, 플러시 때 둘을 비교해 UPDATE가 쓰기 지연 저장소로 들어가는 흐름을 보여 준다. 왼쪽에 큰 둥근 사각형 "영속성 컨텍스트". 그 안에 표 두 줄: 각 줄은 왼쪽 상자 "엔티티 Item#1 (price=20000)"과 오른쪽 상자 "스냅샷 (price=10000)"이 나란히 놓여 있다. 두 상자 사이에 저울 아이콘과 라벨 "플러시 때 비교". 비교 결과에서 아래로 화살표가 나와 "쓰기 지연 저장소" 상자로 들어가고, 그 안에 종이 쪽지 모양 "UPDATE Item SET ..."가 있다. 그 상자에서 오른쪽 원통 "DB"로 화살표 "커밋 시 실행". 두 번째 줄의 엔티티 "Item#2 (price=500)"과 스냅샷 "(price=500)"에는 초록 체크와 라벨 "같음: SQL 없음". 평면 도식 스타일, 흰 배경, 파란색과 주황색 강조. 변경 감지는 세터 호출이 아니라 스냅샷과의 차이를 본다. 값이 같으면 UPDATE도 없다.

    병합(merge): 명세의 규칙과 Hibernate가 실제로 하는 일

    merge는 준영속 엔티티의 상태를 영속성 컨텍스트로 가져오는 연산이다. Jakarta Persistence 3.1 명세 3.2.7.1절은 merge(X)의 의미를 X의 상태에 따라 나눠 정한다.

    • X가 준영속이면, X의 상태를 같은 식별자를 가진 기존 영속 인스턴스 X'에 복사하거나, X의 새 영속 사본 X'을 만든다.
    • X가 새(비영속) 엔티티이면, 새 영속 인스턴스 X'을 만들고 X의 상태를 그쪽에 복사한다.
    • X가 삭제(removed) 상태이면 merge가 IllegalArgumentException을 던지거나 커밋이 실패한다.
    • X가 이미 영속이면 merge는 X 자체를 무시하지만, cascade=MERGE(또는 ALL)로 표시된 연관 엔티티에는 merge를 전파한다.
    • X가 cascade=MERGE로 참조하는 엔티티 Y는 재귀적으로 Y'로 병합되고, X'은 Y'를 참조하도록 설정된다.

    명세는 두 가지를 더 정한다. 지연 로딩(LAZY)으로 표시되었는데 아직 가져오지 않은 필드는 merge할 때 무시해야 한다. 그리고 @Version 필드가 있으면 프로바이더는 merge 시점이나 플러시·커밋 시점에 버전을 검사해야 하며, 버전 필드가 없으면 추가 검사는 없다. 이 규칙들에서 가장 중요한 단어는 "복사"다. merge는 넘겨받은 객체를 영속 상태로 바꾸지 않는다. 영속 인스턴스를 따로 마련해 그쪽에 값을 옮기고, 그 영속 인스턴스를 반환한다.

    실험으로 확인해 보자. 데이터베이스에 있는 상품의 식별자를 가진 객체를 new로 만들고 값을 채워 merge했다. merge 직후 반환값과 인자가 같은 객체인지, 각각을 영속성 컨텍스트가 관리하는지 출력하고, 그다음 인자 쪽 가격을 99999로 바꾼 뒤 커밋했다.

    Item detached = new Item();          // 실험용 엔티티: 세터를 모두 열어 두었다
detached.setId(id);                  // 데이터베이스에 있는 행의 식별자
detached.setName("JPA book 2nd");
detached.setPrice(25000);
detached.setStockQuantity(10);

EntityManager em = emf.createEntityManager();
em.getTransaction().begin();
Item managed = em.merge(detached);
System.out.println("same? " + (managed == detached)
        + " containsDetached=" + em.contains(detached)
        + " containsManaged=" + em.contains(managed));
detached.setPrice(99999);            // merge 이후에 인자를 고친다
System.out.println("-- before commit");
em.getTransaction().commit();
em.close();
// 새 엔티티 매니저로 다시 조회해 출력한다

    한 줄씩 추적하면 merge의 정체가 드러난다. Hibernate 6.6에서 merge 요청은 DefaultMergeEventListener가 처리한다. 이 리스너는 먼저 인자의 상태를 판정한다. 식별자가 있고 현재 영속성 컨텍스트에 그 객체가 없으므로 준영속으로 보고 entityIsDetached()로 간다. 여기서 같은 식별자의 영속 엔티티를 찾는데, 영속성 컨텍스트에 없으니 데이터베이스에서 조회한다. 로그의 첫 SELECT가 이것이다. 조회한 영속 인스턴스와 그 스냅샷이 영속성 컨텍스트에 올라가고, copyValues()가 인자의 필드 값을 영속 인스턴스에 하나하나 복사한다. 그리고 영속 인스턴스를 반환한다. 출력의 same? false는 반환값과 인자가 다른 객체라는 뜻이고, containsDetached=false는 인자가 merge 이후에도 여전히 준영속이라는 뜻이다.

    커밋 때는 지금까지 본 변경 감지가 그대로 일어난다. 영속 인스턴스의 현재 값(복사된 값)과 SELECT 시점의 스냅샷이 다르므로 UPDATE가 나간다. 결국 merge는 "식별자로 조회 → 값 복사 → 변경 감지"를 한 번에 해 주는 연산이다. 마지막 줄에서 가격이 99999가 아니라 25000인 것은 merge 이후 인자를 고친 것이 아무 효과가 없었기 때문이다. 영속성 컨텍스트가 관리하는 것은 반환된 managed이지 detached가 아니다. em.merge(item);처럼 반환값을 버리고 그 뒤에도 item을 계속 고치는 코드는 이 실험의 99999와 같은 운명을 맞는다. 같은 트랜잭션에서 그 상품을 이미 조회해 두었다면 SELECT는 생략되고, 명세가 말한 "같은 식별자를 가진 기존 영속 인스턴스"에 값이 복사된다. 한 영속성 컨텍스트에서 같은 행은 객체 하나라는 동일성 규칙 때문이다.

    merge의 인자는 영속성 컨텍스트 밖에 그대로 남고, 조회로 얻은 별도의 영속 인스턴스에 값이 복사되어 그것이 반환된다는 점을 보여 준다. 왼쪽에 회색 점선 테두리 상자 "준영속 객체 (인자)" 안에 "id=1, name=JPA book 2nd, price=25000". 가운데에 큰 둥근 사각형 "영속성 컨텍스트", 그 안에 파란 실선 상자 "영속 인스턴스 (반환값)"와 그 옆 작은 상자 "스냅샷". 오른쪽 원통 "DB". 번호 붙은 화살표: ① DB에서 영속성 컨텍스트로 "SELECT로 조회", ② 준영속 객체에서 영속 인스턴스로 굵은 화살표 "값 복사", ③ 영속 인스턴스에서 바깥으로 "반환", ④ 영속 인스턴스와 스냅샷 사이 "커밋 때 비교", ⑤ 영속성 컨텍스트에서 DB로 "UPDATE". 준영속 객체 아래에 빨간 글씨 "merge 후에도 관리되지 않음". 평면 도식 스타일, 흰 배경. merge는 인자를 영속으로 만들지 않는다. 조회한 영속 인스턴스에 값을 복사하고 그것을 돌려준다.

    상품 이름은 null이 되었고, 재고는 int 필드의 기본값인 0이 되었다. merge는 "채워진 필드만 반영하라"는 뜻이 아니라 "이 객체의 상태가 곧 새 상태"라는 뜻이기 때문이다. 실무에서는 수정 화면에 없는 등록일, 작성자, 상태 코드 같은 필드가 이렇게 지워진다. 명세가 말한 "가져오지 않은 LAZY 필드는 무시한다"는 규칙은 지연 로딩 연관관계나 지연 로딩 속성에 대한 것이지, 개발자가 채우지 않은 일반 필드를 보호해 주는 규칙이 아니다.

    그러면 폼에 모든 필드를 숨은 입력란으로 실어 보내면 해결될까? 데이터는 지워지지 않겠지만, 이번에는 모든 필드의 값을 클라이언트가 정하게 된다. 수정 권한이 없는 필드(예: 승인 상태)라도 요청을 조작하면 바꿀 수 있다. 앞에서 본 대량 할당 문제가 merge를 통해 다시 들어오는 것이다.

    둘째, 그 사이 삭제된 행을 만나면 버전에 따라 결과가 다르다

    사용자가 수정 화면을 보는 동안 다른 관리자가 그 상품을 삭제했다면 merge는 어떻게 될까. 데이터베이스에 없는 식별자 999를 가진 객체를 merge해 보았다. 이 엔티티는 식별자를 @GeneratedValue로 생성한다.

EX jakarta.persistence.OptimisticLockException: Row was updated or deleted by another transaction (or unsaved-value mapping was incorrect): [ex.Item#999]

    조회 결과가 없자 Hibernate는 OptimisticLockException을 던졌다. 이 동작은 Hibernate 6.6에서 바뀐 것이다. Hibernate 6.6 마이그레이션 가이드에 따르면, 이전 버전은 일치하는 행이 없으면 준영속 엔티티의 merge를 SQL INSERT로 처리했다. 6.6부터는 엔티티가 확실히 준영속이라고 판단할 수 있는 경우, 즉 식별자가 생성(@GeneratedValue)되거나 래퍼 타입의 @Version 필드가 있는 경우에 예외를 던진다. 둘 다 없는 엔티티는 새 객체와 삭제된 행의 준영속 객체를 구별할 수 없으므로 예전처럼 동작한다. 같은 Spring Boot 3.x 계열이라도 함께 쓰는 Hibernate 버전에 따라 "삭제된 상품을 수정했더니 새 상품이 생겼다"와 "예외가 났다"로 결과가 갈린다는 뜻이다. 변경 감지 방식이라면 이 상황은 em.find()가 null을 돌려주는 것으로 드러나고, 처리는 애플리케이션 코드가 정한다.

    셋째, 다른 사람의 수정을 조용히 덮는다

    관리자 A와 B가 같은 상품의 수정 화면을 거의 동시에 열었다. A는 가격을 고쳐 저장했고, 잠시 뒤 B는 재고만 고쳐 저장했다. B의 폼에는 A가 고치기 전의 가격이 그대로 실려 있으므로, B의 저장은 A가 바꾼 가격을 옛 값으로 되돌린다. 마지막에 저장한 사람이 이기는(last write wins) 이 현상은 merge만의 문제는 아니다. 폼의 모든 필드를 받아 change()로 옮기는 변경 감지 방식도 똑같이 덮어쓴다. 차이는 탐지 방법에서 난다.

    엔티티에 @Version을 두고 그 값을 폼에 숨은 필드로 실어 보내면, merge는 명세대로 버전을 검사한다. 실험에서 버전 0일 때 읽어 둔 객체를 다른 트랜잭션이 버전 1로 올린 뒤 merge했다.

    == merge stale
Hibernate: select v1_0.id,v1_0.name,v1_0.price,v1_0.version from VItem v1_0 where v1_0.id=?
EX jakarta.persistence.OptimisticLockException: Row was updated or deleted by another transaction (or unsaved-value mapping was incorrect): [ex.VItem#1]

    SELECT로 읽은 현재 버전(1)과 인자의 버전(0)이 다르므로 UPDATE를 시도하기도 전에 예외가 났다. 변경 감지 방식에서는 서비스가 엔티티를 새로 조회하므로 엔티티의 버전은 항상 최신이고, 그대로는 B의 요청이 낡았다는 것을 알 수 없다. 이때는 폼에서 받은 버전과 조회한 엔티티의 버전을 서비스나 엔티티 메서드가 직접 비교해 다르면 예외를 던진다. 버전 필드는 영속성 프로바이더가 관리하는 값이므로 애플리케이션이 영속 엔티티의 버전 필드에 폼의 값을 덮어쓰는 방식은 쓰지 않는다. 어느 방식이든 "화면을 연 시점의 버전"을 요청에 실어 보내야만 다른 사람의 수정을 감지할 수 있다는 점은 같다.

    덧붙여: persist와 Spring Data의 save()

    준영속 객체를 persist()에 넘기면 어떻게 될까. 실험 결과는 jakarta.persistence.EntityExistsException: detached entity passed to persist: ex.Item이었다. persist()는 새 엔티티를 위한 연산이다. 이 구분을 자동으로 해 주는 것이 Spring Data JPA의 save()다. Spring Data JPA 3.5.13의 SimpleJpaRepository.save()는 entityInformation.isNew(entity)가 참이면 persist()를, 거짓이면 merge()를 호출한다. isNew()는 래퍼 타입의 @Version 필드가 있으면 그 값이 null인지로, 없으면 식별자가 null인지(원시 타입 식별자라면 0인지)로 판단한다(두 클래스의 바이트코드로 확인). 그래서 식별자를 직접 할당하는 엔티티를 save()하면 새 엔티티인데도 merge 경로로 가서 SELECT를 먼저 실행한다. 또 같은 트랜잭션에서 조회해 고친 엔티티를 굳이 save()로 다시 넘기는 것은 필요 없는 일이다. 영속 엔티티의 merge는 명세상 무시되고, 변경은 어차피 플러시 때 반영된다. Spring Data JPA는 로드맵의 뒤쪽 권에서 자세히 다룬다.

    그래서 수정은 이렇게: 식별자와 바꿀 값만 서비스에 넘긴다

    지금까지의 관찰을 모으면 수정 기능의 모양이 정해진다. 컨트롤러는 식별자와 바꿀 값만 서비스에 넘긴다. 서비스는 트랜잭션 안에서 엔티티를 조회해 영속 상태로 만들고, 엔티티의 의미 있는 메서드로 값을 바꾼다. 저장 메서드는 호출하지 않는다. 커밋의 플러시가 변경 감지로 UPDATE를 만든다.

    @Service
@Transactional(readOnly = true)
public class ItemService {
    @PersistenceContext
    private EntityManager em;

    public Item findOne(Long itemId) {
        Item item = em.find(Item.class, itemId);
        if (item == null) {
            throw new IllegalArgumentException("상품이 없다. id=" + itemId);
        }
        return item;
    }

    @Transactional
    public void updateItem(Long itemId, String name, int price, int stockQuantity) {
        Item item = findOne(itemId);              // 영속 상태
        item.change(name, price, stockQuantity);  // 규칙 검사 + 필드 변경
    }                                             // 커밋: 플러시 → 변경 감지 → UPDATE
}

    updateItem()을 호출하면 스프링의 트랜잭션 프록시가 메서드 단위 @Transactional을 보고 쓰기 트랜잭션을 연다. 클래스의 readOnly = true보다 메서드의 설정이 우선한다. findOne()은 같은 객체 안의 호출이므로 프록시를 거치지 않고, 이미 열린 트랜잭션 안에서 실행된다. 조회된 Item은 영속 상태이고 스냅샷이 함께 저장된다. change()가 음수 검사를 통과하면 필드가 바뀌고, 메서드가 끝나 프록시가 커밋을 요청하면 플러시가 일어나 UPDATE가 나간다. 두 방식을 표로 비교하면 다음과 같다.

    항목조회 후 변경(변경 감지)merge
    바꿀 필드를 정하는 쪽서비스와 엔티티 메서드의 코드넘겨받은 객체의 모든 필드
    실행되는 SQL조회 SELECT 1회 + 커밋 때 UPDATE병합 중 SELECT 1회 + 커밋 때 UPDATE
    폼에 없는 필드그대로 유지null이나 기본값으로 덮인다
    도메인 규칙change() 같은 메서드가 검사한다필드 접근 엔티티는 값을 필드에 직접 복사하므로 메서드의 검사를 거치지 않는다
    행이 삭제되었을 때find()가 null, 처리는 코드가 정한다Hibernate 6.6: 조건에 따라 OptimisticLockException, 그 이전: INSERT
    결과 객체조회한 영속 엔티티 하나반환값은 영속, 인자는 준영속으로 남는다

    SQL 수는 같다. 성능 차이가 아니라 의미 차이다. 변경 감지 방식은 "무엇을 어떻게 바꾸는가"를 코드가 쥐고, merge는 그것을 넘겨받은 객체에 맡긴다. 그래서 웹 요청을 처리하는 수정 기능에서는 변경 감지를 기본으로 쓰고, merge는 객체 전체를 통째로 교체하는 것이 정말 의도일 때만 쓴다. 바꿀 값이 많아 파라미터가 길어지면 서비스 계층용 명령 객체(예: UpdateItemCommand)를 만들어 넘긴다. 이때도 웹 계층의 ItemForm을 그대로 넘기지는 않는다. 의존 방향이 웹 → 서비스 → 도메인으로 한쪽만 향하도록 지키기 위해서다.

    같은 행을 두 요청이 동시에 고치면

    변경 감지는 "읽고, 자바 메모리에서 계산하고, 결과를 쓴다(read-modify-write)"는 구조다. 이 구조는 동시성 앞에서 약점을 가진다. 재고가 10인 상품에 두 주문 요청이 동시에 들어왔다고 하자. 기본 격리 수준이 REPEATABLE READ인 MySQL InnoDB를 가정한다.

    시간  트랜잭션 T1 (주문 1개)                 트랜잭션 T2 (주문 1개)
 │    SELECT ... → stockQuantity=10
 │                                            SELECT ... → stockQuantity=10
 │                                            (잠금 없는 일관된 읽기: T1의 변경 전 값)
 │    removeStock(1) → 메모리에서 9
 │                                            removeStock(1) → 메모리에서 9
 │    커밋: UPDATE Item SET ..., stockQuantity=9
 │                                            커밋: UPDATE Item SET ..., stockQuantity=9
 ▼                                            (T1 커밋까지 행 잠금을 기다린 뒤 실행)
결과: 두 주문이 성공했지만 재고는 9. 기대값은 8.

    InnoDB의 평범한 SELECT는 잠금을 걸지 않는 일관된 읽기(consistent nonlocking read)이므로 두 트랜잭션 모두 10을 읽는다. Hibernate가 만드는 UPDATE는 앞의 로그에서 본 것처럼 stockQuantity=?에 자바에서 계산한 절댓값을 넣는다. 두 번째 UPDATE는 첫 번째 트랜잭션의 행 잠금이 풀리기를 기다렸다가 실행되며, 같은 9를 다시 쓴다. 한 건의 재고 차감이 사라졌다. 이것이 갱신 손실(lost update)이다. 대책은 세 갈래다.

    • 낙관적 락: @Version을 두면 Hibernate의 UPDATE에 and version=?가 붙는다. 늦게 커밋한 쪽의 UPDATE는 갱신된 행이 0건이 되고, Hibernate는 이를 낙관적 락 실패 예외로 바꾼다. 충돌이 드물 때 알맞고, 실패한 요청은 재시도하거나 사용자에게 다시 시도하라고 알린다.
    • 비관적 락: em.find(Item.class, id, LockModeType.PESSIMISTIC_WRITE)로 조회하면 MySQL에서는 SELECT ... FOR UPDATE가 나가 행 잠금을 먼저 잡는다. T2는 SELECT 단계에서 기다렸다가 T1이 커밋한 9를 읽는다. 충돌이 잦은 인기 상품에 알맞지만, 잠금 대기가 길어지면 커넥션과 요청 스레드가 함께 묶인다.
    • 조건부 원자적 UPDATE: update Item i set i.stockQuantity = i.stockQuantity - :count where i.id = :id and i.stockQuantity >= :count처럼 계산을 데이터베이스에 맡기고, 갱신 건수가 0이면 재고 부족으로 처리한다. 이런 벌크 연산은 영속성 컨텍스트를 거치지 않으므로, 같은 트랜잭션에 이미 올라와 있는 엔티티의 값은 낡은 채로 남는다는 점을 함께 관리해야 한다.
    두 트랜잭션이 같은 재고 10을 읽고 각자 9를 계산해 쓰는 바람에 차감 한 건이 사라지는 과정을 시간 축 위에 보여 준다. 세로로 흐르는 두 개의 평행한 타임라인. 왼쪽 열 제목 "트랜잭션 T1", 오른쪽 열 제목 "트랜잭션 T2". 위에서 아래로 상자들: T1 "SELECT 재고=10", T2 "SELECT 재고=10", T1 "메모리에서 9 계산", T2 "메모리에서 9 계산", T1 "UPDATE 재고=9 커밋", T2 쪽에 모래시계 아이콘과 "행 잠금 대기", T2 "UPDATE 재고=9 커밋". 가운데 아래에 데이터베이스 원통 "DB 재고=9"와 빨간 경고 표시 "기대값 8". 오른쪽 여백에 작은 초록 상자 세 개를 세로로: "@Version", "SELECT ... FOR UPDATE", "조건부 UPDATE". 평면 도식 스타일, 흰 배경. 변경 감지는 메모리에서 계산한 절댓값을 쓴다. 동시에 같은 행을 고치면 한쪽의 변경이 사라질 수 있다.

    상품 주문: 컨트롤러는 식별자만 넘긴다

    주문 화면은 회원과 상품을 고르는 선택 상자 두 개와 수량 입력란으로 이루어진다. 화면을 그리는 GET 요청은 회원 목록과 상품 목록을 모델에 담아 option 태그를 만들고, 각 옵션의 값은 엔티티의 식별자다. 제출된 요청에는 결국 숫자 세 개, memberId, itemId, count만 실려 온다.

    @Controller
public class OrderController {
    private final OrderService orderService;

    public OrderController(OrderService orderService) {
        this.orderService = orderService;
    }

    @PostMapping("/order")
    public String order(@RequestParam("memberId") Long memberId,
                        @RequestParam("itemId") Long itemId,
                        @RequestParam("count") int count) {
        orderService.order(memberId, itemId, count);
        return "redirect:/orders";
    }
}

@Service
@Transactional(readOnly = true)
public class OrderService {
    @PersistenceContext
    private EntityManager em;

    @Transactional
    public Long order(Long memberId, Long itemId, int count) {
        Member member = em.find(Member.class, memberId);
        Item item = em.find(Item.class, itemId);
        Order order = Order.create(member, OrderItem.of(item, count)); // 재고 차감 포함
        em.persist(order);                                              // OrderItem은 cascade로 함께
        return order.getId();
    }
    // ...
}

    OrderItem.of()는 상품의 removeStock()을 호출해 재고를 줄이고 주문 시점 가격을 기록한다. Order는 orderItems 컬렉션에 cascade = CascadeType.ALL을 걸어 두었으므로 주문을 persist()하면 주문 상품도 함께 저장된다. 이 도메인 구조와 연관관계 편의 메서드는 앞 회차에서 설계한 것이고, 여기서는 웹 계층과 이어지는 지점만 본다. 실행 로그는 다음과 같다.

    재고를 줄이는 UPDATE는 어디에도 명시되지 않았다. 트랜잭션 안에서 조회한 Item이 영속 상태였고, removeStock()이 그 필드를 바꿨으며, 커밋의 플러시가 변경 감지로 UPDATE를 만들었다. 로그에서 두 INSERT가 UPDATE보다 먼저 나간 것도 볼 수 있다.

    컨트롤러에서 엔티티를 찾아 넘기면 생기는 일

    다른 설계도 가능해 보인다. 컨트롤러가 memberService.findOne()과 itemService.findOne()으로 엔티티를 먼저 찾고, 서비스에는 order(member, item, count)처럼 엔티티를 넘기는 것이다. 각 조회 메서드는 자기 트랜잭션을 열고 닫으므로, 영속성 컨텍스트가 트랜잭션 범위라면 서비스에 도착한 member와 item은 준영속이다. 이 상황을 그대로 재현했다. 앞 트랜잭션에서 조회하고 닫은 회원과 상품을 새 트랜잭션의 주문 생성에 넘겼다.

stock=10 orders=1

    주문과 주문 상품은 저장되었는데 재고 UPDATE가 없다. 재고는 10 그대로이고 주문은 1건이다. 예외는 하나도 나지 않았다. removeStock(2)는 준영속 Item의 자바 필드만 8로 바꿨고, 이 객체는 영속성 컨텍스트에 없으니 변경 감지 대상이 아니었다. 주문 상품의 외래 키 item_id는 준영속 객체의 식별자만 읽으면 채울 수 있으므로 INSERT는 정상적으로 나갔다. 결과적으로 데이터가 조용히 어긋났다.

    같은 코드가 스프링 부트 기본 설정에서는 재고를 제대로 줄일 수도 있다. 뒤의 OSIV 절에서 보듯 기본 설정은 요청 내내 엔티티 매니저 하나를 유지하므로, 컨트롤러에서 조회한 엔티티가 서비스의 트랜잭션까지 영속 상태로 남기 때문이다. 같은 코드의 정합성이 설정 플래그 하나에 달려 있다는 것 자체가 위험 신호다. 서비스가 식별자를 받아 자기 트랜잭션 안에서 조회하면 이 의존이 사라진다. 조회, 검증, 변경, 지연 로딩이 모두 한 트랜잭션과 한 영속성 컨텍스트 안에서 일어나므로 설정과 무관하게 같은 결과가 나온다.

    주문 목록 검색과 취소

    동적 쿼리를 문자열로 조립할 때

    주문 목록 화면에는 회원 이름과 주문 상태로 거르는 검색 폼이 있다. 두 조건은 각각 있을 수도, 없을 수도 있으므로 쿼리의 WHERE 절이 실행 시점에 결정되는 동적 쿼리(dynamic query)가 된다. 검색 조건은 GET 요청의 쿼리 파라미터로 받는다. 검색은 상태를 바꾸지 않는 조회이고, 검색 결과 주소를 북마크하거나 공유할 수 있어야 하기 때문이다.

    public class OrderSearch {
    private String memberName;
    private OrderStatus status;     // ORDER, CANCEL
    // getter, setter ...
}

@GetMapping("/orders")
public String orderList(@ModelAttribute("orderSearch") OrderSearch orderSearch, Model model) {
    model.addAttribute("orders", orderService.search(orderSearch));
    return "order/orderList";
}

public List search(OrderSearch cond) {
    StringBuilder jpql = new StringBuilder("select o from Order o join o.member m");
    List where = new ArrayList<>();
    if (cond.getStatus() != null) {
        where.add("o.status = :status");
    }
    if (StringUtils.hasText(cond.getMemberName())) {
        where.add("m.name like :name");
    }
    if (!where.isEmpty()) {
        jpql.append(" where ").append(String.join(" and ", where));
    }
    TypedQuery query = em.createQuery(jpql.toString(), Order.class)
            .setMaxResults(1000);
    if (cond.getStatus() != null) {
        query.setParameter("status", cond.getStatus());
    }
    if (StringUtils.hasText(cond.getMemberName())) {
        query.setParameter("name", "%" + cond.getMemberName() + "%");
    }
    return query.getResultList();
}

    상태를 ORDER, 이름을 "ki"로 검색했을 때 H2 방언에서 나온 SQL은 다음과 같다.

    Hibernate: select o1_0.id,o1_0.member_id,o1_0.orderDate,o1_0.status from orders o1_0 join Member m1_0 on m1_0.id=o1_0.member_id where o1_0.status=? and m1_0.name like ? escape '' fetch first ? rows only

    몇 가지를 읽어 두자. 엔티티 이름은 Order지만 테이블 이름은 @Table(name = "orders")로 바꿔 두었다. ORDER는 SQL의 예약어(ORDER BY)이기 때문이다. JPQL의 from Order o는 Hibernate 6.6에서 문제없이 해석되었다. setMaxResults(1000)은 H2 방언에서 fetch first ? rows only가 되었고, 행 수 제한 문법은 데이터베이스마다 달라 MySQL 방언이라면 limit 구문이 된다. 이렇게 방언이 SQL의 차이를 흡수해 준다.

    가장 중요한 것은 사용자가 입력한 이름이 쿼리 문자열에 직접 들어가지 않고 :name 파라미터로 바인딩되었다는 점이다. SQL 로그의 ? 자리에는 JDBC PreparedStatement의 파라미터로 값이 따로 전달된다. 만약 "m.name like '%" + name + "%'"처럼 입력값을 이어 붙였다면 작은따옴표 하나로 쿼리의 구조를 바꿀 수 있는 JPQL 인젝션이 열린다. 동적 쿼리를 문자열로 조립할 때도 조립하는 것은 쿼리의 구조뿐이고, 값은 언제나 파라미터로 넘긴다.

    문자열 조립 방식의 약점은 분명하다. 조건이 늘수록 분기가 늘고, 공백 하나나 and 하나를 빠뜨린 오류는 실행해 봐야 드러난다. JPA 표준의 Criteria API는 쿼리를 자바 객체로 조립하게 해 주지만 코드가 장황하다. 이 문제를 깔끔하게 푸는 도구인 Querydsl은 로드맵의 뒤쪽 권에서 다룬다.

    검색 결과를 그리는 템플릿에는 ${order.member.name}이 들어간다. Order.member는 @ManyToOne(fetch = FetchType.LAZY)이므로 위 SQL은 회원 이름을 가져오지 않았고, order.getMember()는 회원 프록시를 돌려준다. 엔티티 매니저를 닫은 뒤 이 프록시의 이름을 읽으면 다음과 같다.

    EX org.hibernate.LazyInitializationException: Could not initialize proxy [shop.Member#1] - no session

    프록시를 초기화하려면 SELECT를 실행할 세션(영속성 컨텍스트)이 필요한데 이미 닫혔다는 뜻이다. 스프링 부트 기본 설정에서는 이 예외 대신 렌더링 도중 회원 SELECT가 나간다. 그 이유가 다음 절의 OSIV다. 다만 주문이 100건이고 회원이 모두 다르면 회원 SELECT도 최대 100번 나갈 수 있다. 이 N+1 문제와 페치 조인(fetch join)을 이용한 해결은 JPA 활용 2편의 주제다.

    주문 취소: 여러 엔티티의 변경을 한 번의 커밋이 모은다

    주문 취소는 상태를 바꾸는 요청이므로 POST /orders/{orderId}/cancel로 받는다. GET은 HTTP 명세상 안전한(safe) 메서드여서 링크 미리 가져오기나 크롤러가 호출해도 서버 상태가 바뀌지 않아야 한다. 취소를 GET 링크로 만들면 그 약속을 깬다.

    서비스 코드는 두 줄인데 SQL은 다섯 개다. 첫 SELECT는 주문을 읽었다. for 문이 orderItems를 처음 순회할 때 지연 로딩 컬렉션이 초기화되며 두 번째 SELECT가 나갔고, oi.cancel() 안에서 상품 프록시의 필드에 접근할 때 세 번째 SELECT가 나갔다. 모두 트랜잭션 안이므로 영속성 컨텍스트가 열려 있어 지연 로딩이 가능했다. 커밋의 플러시는 주문의 상태 변경과 상품의 재고 변경을 각각 감지해 UPDATE 두 개를 만들었다. 주문으로 2개가 차감되어 8이던 재고는 취소로 다시 10이 되었다.

    비즈니스 로직이 엔티티 안에 있고 서비스는 조회와 위임만 하는 이 구조를 도메인 모델 패턴이라고 부른다. 같은 기능을 트랜잭션 스크립트 패턴으로 쓰면 서비스가 주문 상태를 확인하고, 주문 상태 UPDATE와 상품별 재고 UPDATE를 직접 실행한다. 어느 쪽이 맞는지는 로직의 복잡도에 달렸고, 두 패턴의 비교는 앞 회차에서 다뤘다. 여기서 짚을 것은 도메인 모델 패턴이 변경 감지 위에서만 자연스럽게 성립한다는 점이다. 엔티티가 자기 필드를 바꾸기만 하면 SQL은 플러시가 책임진다.

    영속성 컨텍스트는 요청의 어디까지 사는가: OSIV

    지금까지 "트랜잭션이 끝나면 엔티티는 준영속이 된다"고 말했지만, 스프링 부트 웹 애플리케이션의 기본 설정에서는 그렇지 않다. 스프링 부트 문서에 따르면 웹 애플리케이션에서 스프링 부트는 기본으로 OpenEntityManagerInViewInterceptor를 등록해 Open EntityManager in View 패턴을 적용하며, 이는 웹 뷰에서 지연 로딩을 허용하기 위해서다. 끄려면 spring.jpa.open-in-view=false를 설정한다. Spring Boot 3.5.16의 설정 메타데이터에서 이 속성의 기본값은 true이고, 자동 구성 클래스는 이 속성을 명시하지 않은 채 기본값으로 켜지면 뷰 렌더링 중에 데이터베이스 쿼리가 실행될 수 있다는 경고 로그를 남긴다(바이트코드의 문자열로 확인).

    이 인터셉터는 요청이 컨트롤러에 도착하기 전에 엔티티 매니저를 만들어 현재 스레드에 묶고, 요청 처리가 완전히 끝난 뒤에 닫는다. 그 사이의 @Transactional 메서드들은 새 엔티티 매니저를 만들지 않고 스레드에 묶인 것을 재사용한다. 트랜잭션은 서비스 메서드마다 시작하고 끝나지만, 영속성 컨텍스트는 요청 전체에 걸쳐 하나다. 그래서 서비스에서 조회한 엔티티가 컨트롤러와 뷰에서도 영속 상태로 남고, 뷰의 지연 로딩이 성공한다.

    편리한 만큼 대가도 있다. 첫째, 데이터베이스 커넥션이다. Spring Framework 6.2.19의 HibernateJpaVendorAdapter는 리소스 로컬(JTA가 아닌) 구성에서 Hibernate 설정 hibernate.connection.handling_mode를 DELAYED_ACQUISITION_AND_HOLD로 지정한다. 커넥션을 처음 필요할 때 얻고, 세션이 닫힐 때까지 쥐고 있는다는 뜻이다. 세션이 요청 끝까지 살아 있으면 커넥션도 요청 끝까지 풀로 돌아가지 않는다. 뷰 렌더링이나 외부 API 호출이 오래 걸리는 화면이 많으면 커넥션 풀이 먼저 바닥난다.

    둘째, 트랜잭션 밖에서 바꾼 엔티티가 나중에 반영될 수 있다. 엔티티 매니저 하나에서 트랜잭션 두 개를 차례로 실행하고, 그 사이 트랜잭션 밖에서 엔티티를 바꾸는 실험을 했다. 스프링 없이 Hibernate만으로 OSIV와 같은 구조를 만든 것이다.

    EntityManager em = emf.createEntityManager();       // 요청 하나 동안 살아 있는 엔티티 매니저
em.getTransaction().begin();
Item i = em.find(Item.class, id);                    // 서비스 A의 트랜잭션
em.getTransaction().commit();
System.out.println("-- tx1 done, modify outside tx, contains=" + em.contains(i));
i.setPrice(555);                                     // 컨트롤러에서 엔티티를 고쳤다
em.getTransaction().begin();                         // 서비스 B의 트랜잭션: 아무 일도 하지 않는다
System.out.println("-- tx2 begin (no work)");
em.getTransaction().commit();
System.out.println("-- tx2 committed");
em.close();

    첫 트랜잭션이 끝난 뒤에도 contains는 true다. 엔티티 매니저가 닫히지 않았으니 엔티티는 준영속이 아니라 여전히 영속이다. 트랜잭션 밖에서 가격을 555로 바꾼 순간에는 아무 SQL도 없었다. 그런데 아무 일도 하지 않은 두 번째 트랜잭션이 커밋하자, 플러시가 영속성 컨텍스트 전체를 검사해 그 변경을 발견하고 UPDATE를 실행했다. OSIV가 켜진 애플리케이션에서 컨트롤러가 서비스에서 받은 엔티티를 화면 표시용으로 살짝 고친 뒤 다른 쓰기 서비스를 호출하면 정확히 이 일이 일어난다. 반대로 OSIV가 꺼져 있으면 같은 코드의 변경은 준영속 객체에 머물러 조용히 사라진다. 어느 쪽이든 의도와 다르다.

    두 결과를 함께 놓으면 규칙 하나가 남는다. 엔티티의 변경은 서비스 계층의 트랜잭션 안에서만 한다. 컨트롤러와 뷰는 엔티티를 읽기만 하거나, 더 엄격하게는 엔티티 대신 DTO만 받는다. 이 규칙을 지키면 OSIV를 켜든 끄든 쓰기의 의미가 바뀌지 않는다. OSIV를 끌 것인가는 지연 로딩을 서비스 안으로 끌어들이는 비용과 커넥션 점유 시간 사이의 선택이며, JPA 활용 2편에서 성능 최적화와 함께 다룬다.

    이 장의 핵심

    폼에서 돌아온 값은 영속성 컨텍스트가 모르는 객체다. 그 값을 반영하는 가장 안전한 길은 서비스가 식별자로 엔티티를 다시 조회해 영속 상태로 만들고, 의미 있는 메서드로 필요한 필드만 바꾼 뒤 커밋의 플러시에 맡기는 것이다. merge는 같은 SQL을 만들지만 넘겨받은 객체의 모든 필드를 복사하므로, 폼에 없는 필드와 낡은 값까지 그대로 데이터베이스에 쓴다.

    트랜잭션이 끝나면 엔티티는 항상 준영속이다OSIV가 켜져 있으면 요청이 끝날 때까지 영속 상태로 남는다.
    읽기 전용 트랜잭션에서도 바꾸면 반영된다스프링은 Hibernate 세션의 플러시 모드를 MANUAL로 바꾸므로 반영되지 않는다. 예외도 없다.

    이 회차로 「JPA 활용 1」의 애플리케이션이 화면까지 연결되었다. 도메인을 설계하고, 엔티티에 규칙을 넣고, 서비스가 트랜잭션 경계를 긋고, 웹 계층은 식별자와 값만 전달하는 구조다. 그 과정에서 영속성 컨텍스트, 플러시, 프록시, 지연 로딩 같은 개념을 쓰임새부터 보았다. 다음 권인 「JPA 기본편」은 이 개념들을 명세의 규칙부터 체계적으로 다시 쌓는다. 그 뒤의 「JPA 활용 2」는 이 회차에서 미뤄 둔 문제들, 즉 엔티티를 API로 노출하지 않는 법, 지연 로딩으로 생기는 N+1 문제와 페치 조인, OSIV를 끌 때의 설계를 다룬다.
    폼 객체(form object)
    요청 파라미터를 받아 검증하는 웹 계층 전용 객체다. 엔티티에 세터를 열지 않고, 대량 할당과 화면별 검증 규칙이 도메인으로 새어 들어가는 것을 막는다.
    준영속 엔티티
    식별자는 있지만 영속성 컨텍스트가 관리하지 않는 엔티티다. 폼 값으로 만든 객체도 같은 처지이며, 값을 바꿔도 데이터베이스에 반영되지 않는다.
    변경 감지
    조회 시점의 스냅샷과 플러시 시점의 필드 값을 비교해 달라진 영속 엔티티의 UPDATE를 만드는 동작이다. 값이 같으면 SQL이 없고, 기본 UPDATE는 모든 컬럼을 쓴다.
    플러시와 읽기 전용 트랜잭션
    플러시는 커밋 직전(그리고 AUTO 모드의 쿼리 전)에 일어난다. 스프링의 읽기 전용 트랜잭션은 Hibernate 플러시 모드를 MANUAL로 바꿔 변경 감지 결과가 반영되지 않는다.
    merge
    식별자로 영속 인스턴스를 조회한 뒤 인자의 모든 필드를 복사하고 그 영속 인스턴스를 반환한다. 인자는 준영속으로 남는다.
    merge의 함정
    채우지 않은 필드를 null이나 기본값으로 덮고, 낡은 값으로 다른 사람의 수정을 덮는다. 행이 삭제되었으면 Hibernate 6.6은 조건에 따라 OptimisticLockException을 던지고, 이전 버전은 INSERT했다.
    식별자만 넘기는 서비스
    컨트롤러는 식별자와 값만 넘기고 서비스가 트랜잭션 안에서 엔티티를 조회해 바꾼다. 조회·검증·변경·지연 로딩이 한 영속성 컨텍스트 안에서 일어나 설정과 무관하게 같은 결과가 나온다.
    갱신 손실
    두 트랜잭션이 같은 값을 읽고 각자 계산한 값을 쓰면 한쪽 변경이 사라진다. @Version, 비관적 락, 조건부 원자적 UPDATE로 막는다.
    OSIV
    스프링 부트는 웹 애플리케이션에서 기본으로 요청 내내 엔티티 매니저 하나를 유지한다. 뷰의 지연 로딩이 되지만 커넥션을 오래 쥐고, 트랜잭션 밖의 변경이 다음 트랜잭션에 실려 나갈 수 있다.

    실무에서 "수정했는데 저장이 안 된다"는 장애 보고는 대부분 세 가지 중 하나다. 수정 대상이 준영속 객체였거나, 쓰기 메서드에 @Transactional이 빠져 클래스의 읽기 전용 트랜잭션으로 실행되었거나, merge의 반환값을 버리고 인자를 계속 고쳤다. 셋 다 예외가 나지 않으므로 로그에서 UPDATE가 있었는지를 먼저 본다. UPDATE가 없다면 "그 순간 이 객체를 영속성 컨텍스트가 알고 있었는가, 그리고 플러시가 일어났는가"를 차례로 묻는다. 반대로 "고친 적 없는 값이 바뀌었다"는 보고라면 merge로 들어온 null 필드나, OSIV 아래에서 트랜잭션 밖의 변경이 다음 트랜잭션에 실려 나간 경우를 의심한다.

    merge를 쓸지 변경 감지를 쓸지는 취향이 아니라 "누가 새 상태를 정하는가"의 문제다. 화면에서 일부 필드만 고치는 수정 기능은 서버가 바꿀 필드를 정해야 하므로 변경 감지가 맞다. 반대로 외부 시스템에서 받은 완전한 스냅샷으로 엔티티 전체를 교체하는 동기화 작업이라면 merge가 의도에 맞을 수 있다. 그때도 Hibernate 버전에 따라 삭제된 행을 만났을 때의 결과가 다르다는 점, 버전 필드 없이 쓰면 다른 변경을 조용히 덮는다는 점을 확인하고 쓴다.

    동시 수정은 기능을 만들 때가 아니라 트래픽이 붙은 뒤에 드러난다. 재고처럼 여러 요청이 같은 행을 차감하는 값이라면 처음부터 @Version이나 조건부 UPDATE를 고려하고, 관리자 화면처럼 사람이 오래 들여다본 뒤 저장하는 폼이라면 화면을 연 시점의 버전을 요청에 실어 낡은 저장을 거절한다. 판단 기준은 충돌 빈도다. 충돌이 드물면 낙관적 락과 재시도로 충분하고, 특정 행에 충돌이 몰리면 비관적 락이나 데이터베이스가 계산하는 원자적 UPDATE가 낫다. 이때 비관적 락은 OSIV가 붙잡는 커넥션 점유 시간과 합쳐져 풀 고갈로 이어질 수 있으므로 두 설정을 함께 본다.
  • 영속 엔티티 item(가격 10000)에 대해 한 트랜잭션 안에서 item.setPrice(15000); item.setPrice(10000);을 실행하고 커밋했다. 이때 실행되는 SQL을 예측하고 이유를 설명하라.
  • 식별자 1번 상품(이름 "A", 가격 1000, 재고 5)에 대해, 이름과 가격만 입력받는 폼의 값으로 Item을 새로 만들고 식별자를 1로 채워 em.merge()했다. 커밋 후 행의 세 값은 무엇인가? 같은 요구를 변경 감지로 구현하는 서비스 메서드의 시그니처와 본문을 적어라.
  • 클래스에 @Transactional(readOnly = true)가 붙은 서비스에 public void rename(Long id, String name)을 추가하면서 메서드에는 @Transactional을 붙이지 않았다. 메서드 안에서 em.find()로 회원을 찾아 이름을 바꿨다. 어떤 일이 일어나는지, 왜 예외가 나지 않는지 설명하라.
  • 재고가 1인 상품에 두 사용자가 동시에 1개씩 주문했고, 두 주문 모두 성공했으며 재고는 0으로 기록되었다. 이 결과가 어떻게 가능한지 SELECT와 UPDATE의 순서로 설명하고, @Version을 추가했을 때 두 번째 커밋에서 일어나는 일을 적어라.

    1번. UPDATE는 나가지 않는다. 변경 감지는 세터 호출 횟수가 아니라 플러시 시점의 값과 조회 시점 스냅샷의 차이를 본다. 두 번의 대입 뒤 가격은 다시 10000이 되어 스냅샷과 같으므로, 플러시의 비교에서 바뀐 필드가 하나도 없다. 본문의 실험에서 이미 20000인 가격에 20000을 다시 넣었을 때 UPDATE가 없었던 것과 같은 이유다. 중간 값 15000은 자바 필드에만 잠시 있었을 뿐 데이터베이스는 그 존재를 모른다.

    2번. 이름과 가격은 폼의 값이 되고 재고는 0이 된다. merge는 인자의 모든 필드를 영속 인스턴스에 복사하는데, 폼에 재고가 없으니 새로 만든 객체의 int 필드는 기본값 0이었다. 본문 실험에서 이름이 null, 재고가 0이 된 것과 같은 원리다. 변경 감지로 구현하면 @Transactional public void changeNameAndPrice(Long itemId, String name, int price)에서 Item item = em.find(Item.class, itemId);로 영속 엔티티를 얻고(없으면 예외), 엔티티에 changeNameAndPrice(name, price) 같은 메서드를 두어 두 필드만 바꾼다. 재고 필드는 코드가 건드리지 않으므로 5로 남는다.

    3번. 이름은 바뀌지 않는다. 메서드에 @Transactional이 없으므로 트랜잭션 프록시는 클래스의 설정을 적용해 읽기 전용 트랜잭션을 연다. Spring Framework 6.2의 HibernateJpaDialect는 읽기 전용 트랜잭션에서 Hibernate 세션의 플러시 모드를 MANUAL로 바꾸고, 엔티티 매니저가 그 트랜잭션용으로 새로 만들어졌다면 세션을 기본 읽기 전용으로도 만든다. 커밋 때 자동 플러시가 없으므로(기본 읽기 전용 세션이었다면 조회한 엔티티도 변경 감지 대상에서 빠진다) UPDATE가 만들어지지 않는다. 어느 단계도 오류 조건이 아니므로 예외가 없고, 메서드는 정상 반환한다. 고치려면 rename()에 @Transactional을 붙인다.

    4번. 두 트랜잭션이 모두 재고 1을 읽었다. MySQL InnoDB의 기본 격리 수준 REPEATABLE READ에서 평범한 SELECT는 잠금 없는 일관된 읽기이므로 서로를 막지 않는다. 각자 removeStock(1)을 통과해 메모리에서 0을 계산하고, 커밋 때 stockQuantity=0을 쓴다. 두 번째 UPDATE는 첫 번째 트랜잭션의 행 잠금을 기다린 뒤 같은 0을 쓰므로 두 주문이 모두 성공한다. 실제로는 한 개를 두 번 판 것이다. @Version을 추가하면 두 UPDATE 모두 where id=? and version=?에 읽은 시점의 버전을 넣는다. 첫 커밋이 버전을 올렸으므로 두 번째 UPDATE의 조건에 맞는 행이 없어 갱신 건수가 0이 되고, Hibernate는 낙관적 락 예외를 던지며 두 번째 트랜잭션은 롤백된다. 그 주문은 실패로 처리하거나 다시 조회해 재시도한다.

     준영속 객체 detached(가격 25000)를 Item managed = em.merge(detached);로 병합한 직후 detached.setPrice(99999);를 실행하고 커밋했다. 데이터베이스의 가격은? 99999. merge 이후 detached가 영속 상태가 되었기 때문이다. 25000. 영속성 컨텍스트가 관리하는 것은 반환된 managed이고 detached는 여전히 준영속이다. merge 이전의 원래 가격. merge는 커밋 전까지 아무것도 복사하지 않는다. 예외가 발생한다. 준영속 객체를 merge 후에 수정하는 것은 금지되어 있다. merge는 인자를 영속으로 바꾸지 않고, 조회한 영속 인스턴스에 merge 시점의 값을 복사해 그것을 반환한다. 본문 실험에서 containsDetached=false, 최종 가격 25000이 확인되었다. 이후 인자를 고치는 것은 영속성 컨텍스트 밖 객체의 필드 대입일 뿐이라 금지된 것도 아니고 반영되지도 않는다. 복사는 merge 호출 시점에 일어나므로 원래 가격이 남는다는 보기도 틀렸다. 식별자 1번 상품(이름 "A", 가격 1000, 재고 5)에 대해 Item p = new Item(); p.setId(1L); p.setPrice(2000); em.merge(p);를 실행하고 커밋했다. 상품 이름은? LazyInitializationException이 발생한다. TransactionRequiredException이 발생한다. 트랜잭션 밖에서 엔티티를 바꿨기 때문이다. 원래 재고 + 100 - 1로 UPDATE된다. 요청 내내 같은 영속성 컨텍스트이므로 order()의 커밋 때 플러시가 컨트롤러의 변경까지 반영한다. OSIV에서는 요청 전체가 엔티티 매니저 하나를 공유한다. findOne()의 트랜잭션이 끝나도 item은 영속 상태이고, addStock(100)은 메모리의 필드만 바꾼다. order() 안의 em.find()는 같은 영속성 컨텍스트에서 같은 인스턴스를 돌려주므로 removeStock(1)은 이미 100이 더해진 값에서 뺀다. 커밋의 플러시가 그 결과를 UPDATE한다. 본문의 "엔티티 매니저 하나, 트랜잭션 둘" 실험과 같은 구조다. 엔티티 필드 대입은 트랜잭션을 요구하지 않으므로 TransactionRequiredException은 나지 않는다. 클래스에 @Transactional(readOnly = true), 메서드에는 아무것도 붙이지 않은 서비스 메서드에서 영속 엔티티의 필드를 바꿨다. Spring Framework 6.2와 Hibernate를 쓸 때 일어나는 일로 옳은 것은? UPDATE 없이 정상 종료된다. 읽기 전용 트랜잭션에서 스프링이 Hibernate 플러시 모드를 MANUAL로 바꾸기 때문이다. 커밋 때 UPDATE가 정상적으로 실행된다. readOnly는 성능 힌트일 뿐이다. 필드를 바꾸는 순간 예외가 발생한다. 컴파일 오류가 난다. Spring Framework 6.2.19의 HibernateJpaDialect.beginTransaction()은 읽기 전용 정의를 보면 세션 플러시 모드를 MANUAL로 바꾸고, 엔티티 매니저가 그 트랜잭션용으로 새로 만들어진 경우에는 세션을 기본 읽기 전용으로도 만든다. 커밋 때 자동 플러시가 없으니 UPDATE가 없다. 엔티티 필드 대입은 평범한 자바 코드라 그 순간 예외를 던질 주체가 없고, 애노테이션 조합은 컴파일러가 검사하지 않는다. "성능 힌트일 뿐"이라는 보기는 JDBC 수준만 본 설명이고, Hibernate 세션의 플러시 동작까지 바뀐다는 점을 놓쳤다. Hibernate 6.6에서 @GeneratedValue 식별자를 쓰는 엔티티의 준영속 객체를 merge했는데, 그 사이 다른 사용자가 해당 행을 삭제했다. 결과는? 새 행이 INSERT된다. 아무 일도 일어나지 않고 merge가 null을 반환한다. OptimisticLockException이 발생한다. EntityExistsException이 발생한다. Hibernate 6.6 마이그레이션 가이드에 따르면 이전 버전은 이 경우 INSERT를 실행했지만, 6.6부터는 식별자가 생성되거나 래퍼 타입 @Version이 있어 엔티티가 확실히 준영속이라고 판단할 수 있으면 OptimisticLockException을 던진다. 본문 실험(6.6.53)에서도 그대로 확인되었다. INSERT는 6.6 이전의 동작이고, EntityExistsException은 준영속 객체를 persist()에 넘겼을 때의 예외다.
    영속성 컨텍스트(persistence context)
    엔티티 인스턴스를 식별자별로 하나씩 관리하는 저장소다. 같은 행은 같은 객체로 돌려주고, 스냅샷을 들고 있다가 플러시 때 변경을 SQL로 바꾼다.
    준영속(detached)
    식별자를 가졌지만 영속성 컨텍스트가 관리하지 않는 엔티티 상태다. 트랜잭션 범위 영속성 컨텍스트가 끝나거나 detach·clear·close가 일어나면 이 상태가 된다.
    변경 감지(dirty checking)
    플러시 때 관리 엔티티의 현재 값과 조회 시점 스냅샷을 비교해 달라진 엔티티의 UPDATE를 만드는 동작이다.
    플러시(flush)
    영속성 컨텍스트의 변경을 SQL로 데이터베이스에 보내는 일이다. 커밋 직전에 일어나며, 커밋과 달리 트랜잭션을 끝내지 않는다.
    병합(merge)
    준영속이나 새 객체의 상태를 같은 식별자의 영속 인스턴스에 복사하고 그 영속 인스턴스를 반환하는 연산이다.
    낙관적 락(optimistic locking)
    버전 컬럼을 UPDATE 조건에 넣어, 읽은 뒤 다른 트랜잭션이 행을 바꿨으면 갱신 건수 0으로 충돌을 감지하는 방식이다. JPA에서는 @Version으로 쓴다.
    갱신 손실(lost update)
    두 트랜잭션이 같은 값을 읽고 각자 계산한 결과를 써서 한쪽의 변경이 사라지는 동시성 이상 현상이다.
    OSIV(Open EntityManager In View)
    요청이 시작될 때 엔티티 매니저를 열어 뷰 렌더링이 끝날 때까지 유지하는 패턴이다. 스프링 부트 웹 애플리케이션의 기본값이며 spring.jpa.open-in-view로 끈다.
    PRG(Post/Redirect/Get)
    상태를 바꾸는 POST 처리 후 리다이렉트로 응답해 브라우저가 GET으로 결과 화면을 보게 하는 패턴이다. 새로고침이 POST를 반복하지 않는다.
