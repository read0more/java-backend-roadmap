    이 회차의 질문: 스프링 MVC는 직접 만든 프런트 컨트롤러와 무엇이 같은가

    앞 회차에서는 서블릿 하나가 모든 요청을 먼저 받는 프런트 컨트롤러(front controller)를 직접 만들었다. 그 서블릿은 URL로 처리할 객체를 찾고, 그 객체의 호출 방식이 제각각이어도 부를 수 있도록 어댑터(adapter)를 사이에 두었고, 컨트롤러가 돌려준 논리 이름을 실제 화면 경로로 바꿔 렌더링했다. 이 구조를 만들면서 생긴 부품마다 스프링 MVC에는 같은 역할을 하는 부품이 있다. 이 회차는 그 대응을 확인하고, 스프링의 부품이 내부에서 실제로 무엇을 하는지 소스와 실험으로 들여다본다.

    코드 사용법만 보면 스프링 MVC는 @Controller와 @RequestMapping을 붙이는 것으로 끝난다. 그러나 운영 중에 "왜 404인가", "왜 내 컨트롤러가 호출되지 않는가", "왜 뷰를 못 찾는가"를 판단하려면 요청이 어느 객체에서 어느 객체로 넘어가는지 알아야 한다. 이 회차가 답하려는 질문은 다음과 같다.

    • DispatcherServlet은 어떤 클래스이고, 서블릿 컨테이너는 그것을 언제 어떻게 부르는가.
    • 요청 하나를 처리하는 동안 어떤 객체들이 어떤 순서로 일을 넘겨받는가.
    • URL에 맞는 처리 객체는 누가, 언제 만든 표에서 찾는가. 호출 방식이 다른 처리 객체를 어떻게 한 가지 방법으로 부르는가.
    • 컨트롤러가 돌려준 문자열 하나가 어떻게 화면이 되는가.
    • @Controller, @RequestMapping, @GetMapping, Model, @RequestParam은 위 구조의 어느 지점에 끼워지는가.

    먼저 역할의 대응부터 정리한다. 왼쪽은 프런트 컨트롤러를 직접 만들 때 필요했던 역할이고 오른쪽은 스프링 MVC에서 그 역할을 맡는 타입이다.

    모든 요청을 먼저 받는 서블릿DispatcherServletdoDispatch(request, response)
    URL로 처리 객체를 찾는 조회 표HandlerMappinggetHandler(request)
    호출 방식의 차이를 흡수하는 어댑터HandlerAdaptersupports(handler), handle(request, response, handler)

    스프링은 처리 객체를 컨트롤러라고 부르지 않고 핸들러(handler)라고 부른다. 컨트롤러는 핸들러의 한 종류일 뿐이고, 정적 파일을 내려 주는 객체나 함수형 라우터도 핸들러가 될 수 있기 때문이다. 이 구분은 뒤에서 어댑터를 볼 때 다시 중요해진다.

    이 회차의 실험은 로컬에 있는 Spring Framework 7.0.10과 spring-test의 Mock 서블릿 객체(MockHttpServletRequest 등)로 실행했다. 톰캣을 띄우지 않고 DispatcherServlet 객체를 직접 만들어 service()를 호출한 것이다. 이 강좌의 기준 버전은 Spring Framework 6.x이므로, 본문의 규칙은 6.2.x 소스와 레퍼런스 문서로 다시 확인했고 두 버전이 다른 곳은 따로 적었다.

    DispatcherServlet도 서블릿이다

    DispatcherServlet은 특별한 실행 환경이 아니라 HttpServlet을 상속한 평범한 서블릿 클래스다. 서블릿 컨테이너 입장에서는 개발자가 직접 만든 서블릿과 똑같이 객체 하나를 만들고, init()을 한 번 부르고, 요청이 올 때마다 작업 스레드에서 service()를 부른다. 상속 계층은 네 단계다.

    jakarta.servlet.http.HttpServlet     HTTP 메서드를 보고 doGet, doPost … 로 나눈다
            ▲
HttpServletBean                      init(): 서블릿 초기화 파라미터를 자기 프로퍼티에 넣고 initServletBean() 호출
            ▲
FrameworkServlet                     스프링 컨테이너(WebApplicationContext)와 연결한다
                                     doGet, doPost … 를 전부 processRequest() 하나로 모은다
            ▲
DispatcherServlet                    doService() → doDispatch(): 핸들러 조회, 실행, 뷰 렌더링

    HttpServlet은 요청을 HTTP 메서드별로 흩어 놓는데, FrameworkServlet은 그것을 다시 한 곳으로 모은다. doGet, doPost, doPut, doDelete가 모두 processRequest를 호출하도록 재정의되어 있다. HTTP 메서드에 따른 분기는 서블릿 수준이 아니라 뒤에서 볼 핸들러 매핑 수준에서 하겠다는 설계다. processRequest는 현재 요청과 로케일 정보를 스레드 로컬(RequestContextHolder, LocaleContextHolder)에 넣어 두고 doService를 부른 다음, 끝나면 스레드 로컬을 원래대로 되돌린다. DispatcherServlet.doService는 요청 속성에 스프링 컨테이너와 로케일 리졸버 같은 객체를 넣어 둔 뒤 doDispatch로 넘어간다.

    이 경로는 추측할 필요 없이 컨트롤러 안에서 스택을 찍어 보면 그대로 나온다. 아래는 뒤에서 만들 애노테이션 컨트롤러의 메서드 안에서 new Throwable().getStackTrace()를 출력한 결과에서 클래스의 단순 이름과 메서드 이름만 남긴 것이다. 아래에서 위로 읽으면 호출 순서가 된다.

    스프링 부트에서는 누가 등록하는가

    스프링 부트는 자동 구성으로 DispatcherServlet을 스프링 빈으로 만들고, dispatcherServlet이라는 이름으로 내장 서블릿 컨테이너에 등록한다. 매핑 경로는 spring.mvc.servlet.path 프로퍼티이고 기본값은 /다. 서블릿 명세에서 URL 패턴 /는 기본 서블릿(default servlet)을 뜻하며, 더 구체적인 패턴에 걸리지 않은 요청이 모두 이 서블릿으로 온다. 그래서 따로 서블릿을 등록하지 않은 부트 애플리케이션에서는 사실상 모든 요청이 DispatcherServlet 하나를 지난다.

    초기화 시점도 알아 둘 만하다. 부트의 spring.mvc.servlet.load-on-startup 기본값은 -1이다. 서블릿 명세는 이 값이 음수이면 컨테이너가 로딩 시점을 정해도 된다고 하고, 톰캣은 첫 요청이 왔을 때 서블릿의 init()을 부른다. 부트 애플리케이션을 띄운 뒤 첫 요청을 보내야 Initializing Spring DispatcherServlet 'dispatcherServlet' 로그가 찍히는 이유다. 이 회차의 실험에서도 init()을 직접 호출했을 때 같은 형식의 로그(Initializing Servlet 'dispatcher', Completed initialization in … ms)가 나왔다. 소요 시간은 실행마다 다르다.

    doDispatch: 요청 하나의 전체 경로

    스프링 MVC의 구조는 doDispatch 메서드 하나에 들어 있다. 아래는 Spring Framework 6.2.x의 DispatcherServlet.doDispatch에서 멀티파트, 비동기, Last-Modified 처리와 예외 포장을 걷어 내고 뼈대만 옮긴 것이다. 변수 이름과 호출 순서는 원본과 같다.

    // DispatcherServlet.doDispatch의 뼈대 (6.2.x 소스를 줄여 옮김)
HandlerExecutionChain mappedHandler = getHandler(processedRequest);       // ① 핸들러 조회
if (mappedHandler == null) {
    noHandlerFound(processedRequest, response);                           //    못 찾으면 404로 가는 길
    return;
}
HandlerAdapter ha = getHandlerAdapter(mappedHandler.getHandler());        // ② 어댑터 조회

if (!mappedHandler.applyPreHandle(processedRequest, response)) {          // ③ 인터셉터 preHandle
    return;
}
ModelAndView mv = ha.handle(processedRequest, response, mappedHandler.getHandler());  // ④ 핸들러 실행

applyDefaultViewName(processedRequest, mv);
mappedHandler.applyPostHandle(processedRequest, response, mv);            // ⑤ 인터셉터 postHandle

processDispatchResult(processedRequest, response, mappedHandler, mv, dispatchException);
// ⑥ 예외가 있었으면 HandlerExceptionResolver로 처리 → mv가 있으면 render() → 인터셉터 afterCompletion

    ①의 getHandler는 등록된 HandlerMapping 목록을 순서대로 돌며 mapping.getHandler(request)를 호출하고, null이 아닌 첫 결과를 돌려준다. 결과 타입은 HandlerExecutionChain인데, 핸들러 객체 하나와 그 앞뒤에서 실행할 인터셉터 목록을 묶은 것이다. ②의 getHandlerAdapter는 등록된 HandlerAdapter 목록을 순서대로 돌며 adapter.supports(handler)가 true인 첫 어댑터를 돌려준다. 하나도 없으면 "No adapter for handler"라는 ServletException을 던진다. 두 메서드 모두 본문이 반복문 하나뿐이다.

    ④에서 어댑터가 핸들러를 실행하고 ModelAndView를 돌려준다. 이 반환값이 null일 수도 있다는 점이 중요하다. 핸들러가 응답을 이미 직접 써 버렸다면 그릴 화면이 없으므로 어댑터는 null을 돌려주고, ⑥에서 렌더링을 건너뛴다. ⑥의 processDispatchResult는 mv가 있으면 render를 부른다. render는 뷰 이름이 있으면 ViewResolver 목록을 순서대로 돌며 resolveViewName을 호출해 null이 아닌 첫 View를 얻고, 그 View의 render(model, request, response)를 호출한다. View를 얻지 못하면 "Could not resolve view with name"이라는 ServletException이 난다.

    이 순서에서 DispatcherServlet이 구체 클래스를 하나도 모른다는 점을 확인해 두자. 핸들러의 타입은 Object이고, 나머지는 전부 인터페이스다. DispatcherServlet은 "찾아라, 실행해라, 이름을 뷰로 바꿔라, 그려라"를 순서대로 시킬 뿐이고, 각 일을 실제로 어떻게 하는지는 목록에 들어 있는 구현체가 정한다. 「스프링 핵심 원리 기본편」에서 본 역할과 구현의 분리가 프레임워크 내부에 그대로 적용된 모습이다.

    7.0.10 소스에서는 순서가 조금 다르다. 인터셉터 preHandle을 먼저 호출하고 그다음에 어댑터를 찾으며, GET·HEAD 요청에서 getLastModified를 묻던 코드는 없어졌다. 핸들러 조회 → 실행 → 뷰 렌더링이라는 큰 흐름은 두 버전에서 같다.
    요청 하나가 DispatcherServlet을 중심으로 다섯 협력 객체를 순서대로 거친다는 것, 그리고 핸들러를 직접 부르는 것은 어댑터라는 것을 보여 준다. 깔끔한 시퀀스 다이어그램, 흰 배경, 평면 색. 세로 생명선 여섯 개가 왼쪽부터 "DispatcherServlet", "HandlerMapping", "HandlerAdapter", "핸들러(컨트롤러)", "ViewResolver", "View" 순서로 서 있다. 맨 왼쪽 생명선은 굵은 남색 띠로 강조한다. 화살표를 위에서 아래로 순서대로 그리고 각 화살표 앞에 원 번호를 붙인다. 1번: DispatcherServlet에서 HandlerMapping으로 실선 화살표, 라벨 "1 핸들러 조회". 되돌아오는 점선 화살표에는 라벨 없이 작은 상자 아이콘. 2번: DispatcherServlet에서 HandlerAdapter로 실선 화살표, 라벨 "2 어댑터 조회". 3번: DispatcherServlet에서 HandlerAdapter로 실선 화살표, 이어서 HandlerAdapter에서 핸들러(컨트롤러)로 주황색 실선 화살표, 라벨 "3 핸들러 실행". 핸들러에서 HandlerAdapter를 거쳐 DispatcherServlet으로 돌아오는 점선 화살표, 라벨 "ModelAndView". 4번: DispatcherServlet에서 ViewResolver로 실선 화살표, 라벨 "4 뷰 이름 해석". 5번: DispatcherServlet에서 View로 실선 화살표, 라벨 "5 렌더링". View 생명선 아래에서 화면 밖 오른쪽으로 나가는 화살표, 라벨 "HTTP 응답". 장식 없이 단순한 선. DispatcherServlet은 핸들러를 직접 부르지 않는다. 핸들러를 부르는 것은 어댑터이고, DispatcherServlet은 인터페이스 네 개에만 의존한다.

    전략 객체는 어디서 오는가

    doDispatch가 쓰는 목록들(handlerMappings, handlerAdapters, viewResolvers)은 서블릿이 초기화될 때 한 번 채워진다. init() 과정에서 initStrategies가 호출되고, 이 메서드가 initHandlerMappings, initHandlerAdapters, initHandlerExceptionResolvers, initViewResolvers 등을 차례로 부른다. 채우는 규칙은 세 종류 모두 같다.

    1. 스프링 컨테이너에서 해당 타입(예: HandlerMapping)의 빈을 전부 찾는다.
    2. 찾은 빈이 있으면 Ordered·@Order의 순서 값으로 정렬해 목록으로 쓴다.
    3. 하나도 없으면 spring-webmvc jar 안의 DispatcherServlet.properties 파일에 적힌 기본 구현체들을 만들어 쓴다.

    DispatcherServlet.properties는 스프링이 jar에 넣어 둔 파일로, 첫머리 주석에 "Not meant to be customized by application developers"라고 적혀 있다. 6.2.x 기준으로 핸들러 매핑의 기본값은 BeanNameUrlHandlerMapping, RequestMappingHandlerMapping, RouterFunctionMapping 순서이고, 핸들러 어댑터는 HttpRequestHandlerAdapter, SimpleControllerHandlerAdapter, RequestMappingHandlerAdapter, HandlerFunctionAdapter 순서이며, 뷰 리졸버는 InternalResourceViewResolver 하나다. MVC 관련 설정을 아무것도 하지 않은 컨테이너로 DispatcherServlet을 초기화한 뒤 세 목록을 출력하면 파일 내용과 똑같이 나온다.

    handlerMappings:
  - BeanNameUrlHandlerMapping
  - RequestMappingHandlerMapping
  - RouterFunctionMapping
handlerAdapters:
  - HttpRequestHandlerAdapter
  - SimpleControllerHandlerAdapter
  - RequestMappingHandlerAdapter
  - HandlerFunctionAdapter
viewResolvers:
  - InternalResourceViewResolver

    3번 규칙에는 함정이 있다. 기본값은 "해당 타입의 빈이 하나도 없을 때"만 쓰인다. 예를 들어 HandlerMapping 타입의 빈을 하나 직접 등록하면 기본 매핑 세 개는 더해지는 것이 아니라 통째로 빠진다. 타입별로 따로 판단하므로, 뷰 리졸버 빈만 등록했다면 핸들러 매핑과 어댑터는 여전히 기본값이다.

    실무의 애플리케이션은 이 기본값으로 돌지 않는다. @EnableWebMvc를 붙이면 WebMvcConfigurationSupport가 핸들러 매핑과 어댑터, 예외 리졸버, 뷰 리졸버를 빈으로 등록하고, 스프링 부트의 자동 구성도 같은 클래스를 상속한 설정(DelegatingWebMvcConfiguration의 하위 클래스)을 쓴다. 이때는 1·2번 규칙에 따라 빈들이 순서 값으로 정렬된다. @EnableWebMvc만 붙인 설정으로 같은 출력을 해 보면 순서가 달라진다.

    handlerMappings:
  - RouterFunctionMapping
  - RequestMappingHandlerMapping
  - BeanNameUrlHandlerMapping
handlerAdapters:
  - RequestMappingHandlerAdapter
  - HandlerFunctionAdapter
  - HttpRequestHandlerAdapter
  - SimpleControllerHandlerAdapter
viewResolvers:
  - ViewResolverComposite

    WebMvcConfigurationSupport의 Javadoc은 RequestMappingHandlerMapping을 순서 0, BeanNameUrlHandlerMapping을 순서 2로 등록한다고 밝힌다(6.2.x와 7.0.x 모두 같다). 순서 값이 작을수록 먼저 물어보므로, 애노테이션 기반 매핑이 빈 이름 기반 매핑보다 앞선다. 기본값 파일의 순서와 반대라는 점에 주의하자. 같은 URL을 두 방식으로 모두 등록했을 때 누가 이기는지는 어느 구성으로 돌고 있느냐에 달려 있다. 부트 애플리케이션에서는 여기에 더해 정적 리소스와 웰컴 페이지(index.html)를 위한 매핑이 추가로 등록된다.

    핸들러 매핑과 핸들러 어댑터: 세 종류의 핸들러로 실험한다

    핸들러 매핑과 어댑터가 왜 목록으로 여러 개 있는지는 핸들러를 여러 종류로 만들어 보면 드러난다. 스프링 MVC가 지금도 지원하는 세 가지 방식으로 핸들러를 하나씩 만든다. 도메인은 사내 공지(notice) 게시판으로 잡았다.

    // import 생략: jakarta.servlet.http.*, org.springframework.web.servlet.*, org.springframework.mock.web.* 등
public class MvcLab {

    // (1) 인터페이스 기반 컨트롤러: 빈 이름이 곧 URL이다
    static class LegacyController implements org.springframework.web.servlet.mvc.Controller {
        @Override
        public ModelAndView handleRequest(HttpServletRequest request, HttpServletResponse response) {
            return new ModelAndView("legacy-view");
        }
    }

    // (2) 서블릿과 가장 비슷한 핸들러: 응답을 직접 쓰고 아무것도 반환하지 않는다
    static class RawHandler implements HttpRequestHandler {
        @Override
        public void handleRequest(HttpServletRequest request, HttpServletResponse response) throws IOException {
            response.getWriter().write("raw ok");
        }
    }

    // (3) 애노테이션 기반 컨트롤러: 어떤 인터페이스도 구현하지 않는다
    @Controller
    static class NoticeController {
        @RequestMapping("/notices")
        public ModelAndView list() {
            ModelAndView mv = new ModelAndView("notices");
            mv.addObject("count", 3);
            return mv;
        }
    }

    @Configuration
    static class LabConfig {
        @Bean("/legacy") LegacyController legacyController() { return new LegacyController(); }
        @Bean("/raw") RawHandler rawHandler() { return new RawHandler(); }
        @Bean NoticeController noticeController() { return new NoticeController(); }
    }
    // ... (아래에 이어진다)
}

    (1)과 (2)는 빈 이름이 /로 시작한다. (3)은 빈 이름이 평범하고, 대신 클래스에 @Controller, 메서드에 @RequestMapping이 붙어 있다. 세 클래스는 공통 상위 타입이 없고 메서드 시그니처도 제각각이다. (1)은 ModelAndView를 돌려주고, (2)는 void이며, (3)은 메서드 이름과 파라미터를 개발자가 마음대로 정한다.

    선택 과정을 눈으로 보기 위해 DispatcherServlet을 상속해 getHandler, getHandlerAdapter, resolveViewName을 재정의한다. 세 메서드는 모두 protected로 열려 있다. getHandler는 원본과 같은 반복문을 돌되 매핑마다 결과를 출력하게 했다.

        static class TracingDispatcherServlet extends DispatcherServlet {

        TracingDispatcherServlet(AnnotationConfigWebApplicationContext context) {
            super(context);
        }

        @Override
        protected HandlerExecutionChain getHandler(HttpServletRequest request) throws Exception {
            for (HandlerMapping mapping : getHandlerMappings()) {
                HandlerExecutionChain chain = mapping.getHandler(request);
                System.out.println("  매핑   " + mapping.getClass().getSimpleName() + " -> "
                        + (chain == null ? "null" : describe(chain.getHandler())));
                if (chain != null) {
                    return chain;
                }
            }
            return null;
        }

        @Override
        protected HandlerAdapter getHandlerAdapter(Object handler) throws ServletException {
            HandlerAdapter adapter = super.getHandlerAdapter(handler);
            System.out.println("  어댑터 " + adapter.getClass().getSimpleName());
            return adapter;
        }

        @Override
        protected View resolveViewName(String viewName, Map model, Locale locale,
                HttpServletRequest request) throws Exception {
            View view = super.resolveViewName(viewName, model, locale, request);
            System.out.println("  뷰     \"" + viewName + "\" -> " + view);
            return view;
        }

        static String describe(Object handler) {
            if (handler instanceof HandlerMethod hm) {
                return "HandlerMethod[" + hm.getBeanType().getSimpleName() + "#" + hm.getMethod().getName() + "]";
            }
            return handler.getClass().getSimpleName();
        }
        // ... printStrategies(): 리플렉션으로 세 목록 필드를 읽어 클래스 이름을 출력(앞 절의 출력)
    }

    static TracingDispatcherServlet start(Class... configs) throws Exception {
        AnnotationConfigWebApplicationContext context = new AnnotationConfigWebApplicationContext();
        context.register(configs);
        TracingDispatcherServlet servlet = new TracingDispatcherServlet(context);
        servlet.init(new MockServletConfig(new MockServletContext(), "dispatcher"));
        return servlet;
    }

    static void send(DispatcherServlet servlet, MockHttpServletRequest request) {
        System.out.println(request.getMethod() + " " + request.getRequestURI());
        MockHttpServletResponse response = new MockHttpServletResponse();
        try {
            servlet.service(request, response);
            System.out.println("  결과   status=" + response.getStatus()
                    + ", forward=" + response.getForwardedUrl()
                    + ", redirect=" + response.getRedirectedUrl()
                    + ", body=\"" + response.getContentAsString() + "\"");
            for (String name : Collections.list(request.getAttributeNames())) {
                if (!name.startsWith("org.springframework") && !name.startsWith("jakarta")) {
                    System.out.println("  요청 속성 " + name + "=" + request.getAttribute(name));
                }
            }
        }
        catch (Exception ex) {
            System.out.println("  예외   " + ex.getMessage());
        }
    }

    public static void main(String[] args) throws Exception {
        TracingDispatcherServlet servlet = start(LabConfig.class);
        servlet.printStrategies();
        send(servlet, new MockHttpServletRequest("GET", "/legacy"));
        send(servlet, new MockHttpServletRequest("GET", "/raw"));
        send(servlet, new MockHttpServletRequest("GET", "/notices"));
        send(servlet, new MockHttpServletRequest("GET", "/nothing"));
    }

    start는 톰캣이 하는 일을 흉내 낸다. 서블릿 객체를 만들고 init()을 한 번 부른다. send는 요청·응답 객체를 만들어 service()를 부른다. MockHttpServletResponse는 forward나 리다이렉트가 일어났을 때 그 대상 경로를 기록해 두므로, JSP 엔진 없이도 뷰가 어디로 넘기려 했는지를 볼 수 있다. 실행 결과에서 요청 네 개 부분은 다음과 같다.

    출력을 한 줄씩 읽는다

    GET /legacy. 목록의 첫 매핑인 BeanNameUrlHandlerMapping이 바로 답을 냈다. 이 매핑은 기동 시점에 컨테이너의 빈 이름(과 별칭) 가운데 /로 시작하는 것을 찾아 "URL → 빈" 표에 넣어 둔다. 요청 경로 /legacy가 표에 있으므로 LegacyController 객체를 돌려주었다. 다음으로 어댑터 목록을 돈다. 첫째 HttpRequestHandlerAdapter의 supports는 handler instanceof HttpRequestHandler라서 거짓이고, 둘째 SimpleControllerHandlerAdapter의 supports는 handler instanceof Controller라서 참이다. 이 어댑터의 handle은 한 줄, ((Controller) handler).handleRequest(request, response)를 그대로 돌려주는 것이 전부다.

    GET /raw. 같은 매핑이 RawHandler를 찾았고, 이번에는 첫 어댑터 HttpRequestHandlerAdapter가 맡았다. 이 어댑터의 handle은 handleRequest를 호출한 뒤 null을 반환한다. 그래서 출력에 "뷰" 줄이 없다. ModelAndView가 null이면 DispatcherServlet은 뷰 해석과 렌더링을 건너뛰고, 핸들러가 직접 쓴 raw ok가 응답 본문이 된다. 이 방식은 옛 유물이 아니다. 스프링 MVC가 정적 리소스를 내려 줄 때 쓰는 ResourceHttpRequestHandler가 HttpRequestHandler의 구현체이고, 그 핸들러도 이 어댑터를 통해 실행된다.

    GET /notices. BeanNameUrlHandlerMapping은 /notices라는 이름의 빈이 없으므로 null을 냈고, 둘째 RequestMappingHandlerMapping이 답을 냈다. 돌려준 핸들러의 타입에 주목하자. 컨트롤러 객체가 아니라 HandlerMethod다. HandlerMethod는 "어느 빈의 어느 메서드인가"를 담은 객체로, 빈과 java.lang.reflect.Method, 파라미터 정보를 갖고 있다. 애노테이션 방식에서 요청을 처리하는 단위는 클래스가 아니라 메서드라는 뜻이다. 어댑터 목록에서는 셋째 RequestMappingHandlerAdapter가 선택되었다. 이 어댑터의 supports는 핸들러가 HandlerMethod인지를 본다. 그 뒤에 난 "Circular view path" 예외는 뷰 리졸버 절에서 설명한다.

    GET /nothing. 세 매핑이 모두 null을 냈다. getHandler가 null을 돌려주면 doDispatch는 noHandlerFound로 가고 결과는 404다. 스프링 MVC에서 404는 "핸들러 매핑 가운데 누구도 이 요청을 맡겠다고 하지 않았다"는 뜻이다. 6.1부터는 이때 NoHandlerFoundException을 던지는 것이 기본 동작이고(throwExceptionIfNoHandlerFound의 기본값이 true가 되고 설정 자체는 폐기 예정이 되었다), 이 예외를 예외 리졸버가 404 응답으로 바꾼다.

    핸들러의 타입이 Object인 이유

    HandlerMapping.getHandler가 돌려주는 핸들러와 HandlerAdapter.handle이 받는 핸들러는 모두 Object 타입이다. 타입 안전성을 포기한 것처럼 보이지만 의도된 설계다. 만약 핸들러의 타입을 어떤 인터페이스로 고정했다면, 인터페이스를 구현하지 않는 (3) 같은 클래스는 핸들러가 될 수 없다. 스프링은 핸들러에 아무 제약도 두지 않는 대신 "이 객체를 내가 실행할 줄 안다"고 답하는 어댑터가 반드시 하나는 있어야 한다는 조건을 걸었다. 새로운 종류의 핸들러를 도입하려면 DispatcherServlet을 고치는 것이 아니라 매핑과 어댑터 구현체를 한 쌍 추가하면 된다. 함수형 엔드포인트용 RouterFunctionMapping과 HandlerFunctionAdapter가 그렇게 추가된 쌍이다.

    일상에서 가져온 비유여행용 멀티 어댑터

    나라마다 콘센트 모양이 다르지만 노트북 충전기는 하나다. 멀티 어댑터가 벽의 모양에 맞는 면을 내밀고 충전기에는 늘 같은 구멍을 보여 준다. 핸들러 어댑터도 핸들러마다 다른 호출 방식을 받아서 DispatcherServlet에는 늘 "handle을 부르면 ModelAndView가 나온다"는 한 가지 모양만 보여 준다. 다만 전기 어댑터는 모양만 바꾸지만 핸들러 어댑터는 일을 더 한다. 특히 RequestMappingHandlerAdapter는 메서드 파라미터에 넣을 값을 요청에서 만들어 내고 반환값을 해석하는 일까지 맡는다.

    핸들러 종류마다 짝이 되는 매핑과 어댑터가 다르지만 DispatcherServlet으로 돌아오는 결과는 한 가지 형태라는 것을 보여 준다. 깔끔한 구조 다이어그램, 흰 배경, 평면 색. 왼쪽 끝에 세로로 긴 남색 상자 "DispatcherServlet". 오른쪽으로 세 개의 가로 줄이 평행하게 뻗는다. 각 줄은 왼쪽부터 둥근 상자(매핑), 둥근 상자(어댑터), 각진 상자(핸들러) 순서이고 화살표로 이어진다. 첫째 줄(회색 계열): "BeanNameUrlHandlerMapping" → "SimpleControllerHandlerAdapter" → "Controller 구현체". 둘째 줄(녹색 계열): "BeanNameUrlHandlerMapping" → "HttpRequestHandlerAdapter" → "HttpRequestHandler 구현체". 셋째 줄(주황 계열, 가장 굵게): "RequestMappingHandlerMapping" → "RequestMappingHandlerAdapter" → "@RequestMapping 메서드". 각 어댑터 상자에서 DispatcherServlet으로 되돌아오는 점선 화살표를 그리고, 첫째와 셋째 줄에는 라벨 "ModelAndView", 둘째 줄에는 라벨 "null". 장식 없이 단순한 선. 핸들러의 호출 방식은 셋 다 다르지만 DispatcherServlet이 받는 것은 ModelAndView 또는 null뿐이다.

    RequestMappingHandlerMapping의 내부: 기동 시점에 만드는 조회 표

    프런트 컨트롤러를 직접 만들 때는 생성자에서 "URL → 컨트롤러 객체" 맵에 항목을 한 줄씩 넣었다. RequestMappingHandlerMapping은 같은 일을 애노테이션을 읽어서 자동으로 한다. 중요한 것은 그 시점이다. 조회 표는 요청이 올 때가 아니라 이 빈이 초기화될 때(afterPropertiesSet) 한 번 만들어진다. 과정은 다음과 같다.

    1. 컨테이너에 등록된 모든 빈 이름을 훑으며 각 빈의 타입을 얻는다.
    2. 타입이 핸들러 후보인지 isHandler로 판정한다. 6.x와 7.x에서 이 메서드는 클래스에 @Controller가 있는지만 본다.
    3. 후보 클래스의 메서드를 하나씩 살펴 @RequestMapping(또는 그것을 메타 애노테이션으로 가진 애노테이션)이 붙은 메서드를 고른다.
    4. 메서드의 매핑 정보로 RequestMappingInfo를 만든다. 클래스에도 @RequestMapping이 있으면 클래스의 정보와 메서드의 정보를 결합한다.
    5. RequestMappingInfo와 HandlerMethod(빈 이름 + Method)의 쌍을 내부 레지스트리에 등록한다.

    RequestMappingInfo는 경로 하나가 아니라 조건의 묶음이다. 경로 패턴, HTTP 메서드, 요청 파라미터, 헤더, Content-Type(consumes), Accept(produces) 조건이 들어 있고, 요청이 이 조건을 모두 만족해야 그 매핑이 선택된다. 직접 만든 구조의 키가 문자열 하나였던 것과 달리, 스프링의 키는 "경로가 같아도 GET이면 이 메서드, POST면 저 메서드"를 표현할 수 있다. 각 조건의 사용법은 다음 회차에서 다룬다.

    레지스트리(MappingRegistry)에는 맵이 여러 개 있는데 그중 둘이 핵심이다. 하나는 "매핑 정보 → 등록 항목"인 HashMap이고, 다른 하나는 "패턴 문자가 없는 고정 경로 → 매핑 정보 목록"인 pathLookup이다. 요청이 오면 먼저 요청 경로를 키로 pathLookup을 조회한다. /notices/new처럼 고정된 경로라면 해시 조회 한 번으로 후보가 좁혀지고, 그 후보들에 대해서만 HTTP 메서드 같은 나머지 조건을 검사한다. 고정 경로로 찾지 못했을 때에만 등록된 매핑 전체를 돌며 패턴을 맞춰 본다. 후보가 여럿이면 더 구체적인 매핑이 이기도록 정렬해 첫째를 고른다.

    표를 미리 만들어 두는 설계에는 실용적인 이점이 하나 더 있다. 매핑의 잘못이 요청 시점이 아니라 기동 시점에 드러난다. 같은 조건의 매핑을 두 메서드에 붙여 보자.

    핸들러 메서드는 리플렉션으로 호출된다

    앞에서 본 스택의 위쪽 절반을 다시 보자. DispatcherServlet.doDispatch가 AbstractHandlerMethodAdapter.handle을 부르고, RequestMappingHandlerAdapter.invokeHandlerMethod를 거쳐 InvocableHandlerMethod.invokeForRequest에 이른다. 이 메서드는 두 가지 일을 한다. 먼저 getMethodArgumentValues로 컨트롤러 메서드의 파라미터마다 넣을 값을 만들어 Object[] 배열에 담는다. 그다음 doInvoke에서 method.invoke(getBean(), args)를 호출한다. 스택에 찍힌 Method.invoke가 그 줄이다.

    리플렉션(reflection)은 클래스의 메서드 정보를 java.lang.reflect.Method 객체로 얻어, 소스 코드에 메서드 이름을 적지 않고도 호출하게 해 주는 자바 기능이다. 스프링은 컴파일 시점에 PracticalNoticeController.trace라는 메서드가 있는지 알 수 없으므로 이 방법 말고는 부를 길이 없다. 인터페이스 기반 컨트롤러와 견주어 보면 차이가 선명하다. SimpleControllerHandlerAdapter는 Controller 타입으로 캐스팅한 뒤 인터페이스 메서드를 평범하게 호출한다. 호출할 메서드의 이름과 시그니처가 인터페이스로 고정되어 있기 때문이다. 애노테이션 방식은 시그니처를 자유롭게 풀어 준 대가로, 어떤 메서드를 어떤 인자로 부를지를 실행 중에 계산한다. Method.invoke 바로 위에 보이는 DirectMethodHandleAccessor는 JDK 21에서 리플렉션 호출을 실제로 수행하는 JDK 내부 클래스다.

    정리하면 애노테이션 컨트롤러 호출의 비용 구조는 이렇다. 클래스를 훑고 애노테이션을 해석하는 무거운 일은 기동 시점에 한 번 한다. 요청 시점에는 맵 조회, 인자 배열 만들기, 리플렉션 호출을 한다. 파라미터 값을 만드는 부품(ArgumentResolver)과 반환값을 해석하는 부품(ReturnValueHandler)이 어떻게 생겼는지는 07회차의 주제다.

    뷰 리졸버: 논리 이름에서 View 객체로

    컨트롤러가 "notices/list" 같은 문자열을 돌려주는 이유는 직접 만든 구조에서와 같다. 컨트롤러가 /WEB-INF/views/notices/list.jsp라는 물리 경로를 알고 있으면, 뷰 파일의 위치나 템플릿 기술이 바뀔 때 모든 컨트롤러를 고쳐야 한다. 그래서 컨트롤러는 논리 이름만 말하고, 그 이름을 실제 화면으로 바꾸는 일은 한 곳에 모은다. 스프링은 이 일을 두 인터페이스로 나눴다. ViewResolver는 이름을 받아 View 객체를 돌려주고, View는 모델을 받아 응답을 만든다. 뷰 리졸버는 그리지 않고, 그리는 것은 View다.

    InternalResourceViewResolver와 "Circular view path"

    기본 뷰 리졸버인 InternalResourceViewResolver가 하는 일은 문자열 덧셈이다. 상위 클래스 UrlBasedViewResolver의 buildView에 view.setUrl(getPrefix() + viewName + getSuffix())라는 줄이 있고, 이렇게 만든 URL을 가진 InternalResourceView 객체를 돌려준다. 접두사와 접미사의 기본값은 빈 문자열이다. 그래서 앞 실험에서 뷰 이름 notices는 URL notices가 되었다.

    InternalResourceView의 렌더링은 서블릿의 RequestDispatcher.forward다. URL이 상대 경로 notices이고 현재 요청 URI가 /notices이면, 상대 경로를 풀었을 때 다시 /notices가 된다. 그대로 forward하면 요청이 DispatcherServlet으로 되돌아와 같은 컨트롤러가 다시 실행되고, 같은 뷰 이름이 나오고, 다시 forward한다. 끝나지 않는 순환이다. 스프링은 forward 직전에 대상 경로가 현재 요청 URI와 같은지 검사해서, 같으면 "Circular view path" 예외를 던진다. /legacy 요청에서 뷰 이름 legacy-view는 풀면 /legacy-view여서 이 검사에 걸리지 않았을 뿐이다.

    이 오류는 접두사·접미사 설정 없이 뷰 이름을 URL과 같게 지었을 때, 또는 템플릿 엔진 의존성을 빼먹어서 뷰 이름을 처리할 리졸버가 InternalResourceViewResolver밖에 남지 않았을 때 만나게 된다. 예외 메시지의 힌트("unspecified view, due to default view name generation")는 또 다른 경우를 가리킨다. 컨트롤러가 뷰 이름을 주지 않으면 applyDefaultViewName이 요청 경로에서 뷰 이름을 만들어 내는데, 그 이름은 당연히 요청 경로와 같아진다.

    접두사와 접미사를 주고 다시 실행한다

    뷰 리졸버를 빈으로 등록한다. 앞에서 본 규칙대로 ViewResolver 타입 빈이 생겼으므로 기본값 대신 이 빈이 쓰인다. 리다이렉트도 함께 보려고 루트 경로를 공지 목록으로 보내는 컨트롤러를 하나 더했다.

static class ViewConfig {
    @Bean

    }
}

    둘째 요청에서는 뷰 이름이 redirect:로 시작한다. UrlBasedViewResolver는 접두사·접미사를 붙이기 전에 이 접두어를 먼저 검사해서, 나머지 문자열을 URL로 하는 RedirectView를 돌려준다. RedirectView의 렌더링은 화면을 그리는 것이 아니라 Location 헤더와 함께 302 응답을 보내는 것이다. 같은 방식으로 forward: 접두어는 접두사·접미사를 붙이지 않은 InternalResourceView를 만든다. 컨트롤러는 여전히 문자열만 돌려주는데 그 문자열의 해석이 뷰 리졸버 한 곳에 모여 있다는 점이 요점이다.

    뷰 리졸버가 여럿일 때, 그리고 스프링 부트에서

    뷰 리졸버도 목록이다. DispatcherServlet은 순서대로 resolveViewName을 호출하고, 어떤 리졸버가 null을 돌려주면 "나는 모른다"는 뜻으로 보고 다음 리졸버에게 묻는다. 여기서 InternalResourceViewResolver의 특성이 문제가 된다. 이 리졸버는 해당 JSP 파일이 실제로 있는지 알 방법이 없다. 스프링 레퍼런스의 설명대로, JSP가 있는지 알아내는 유일한 방법은 RequestDispatcher로 넘겨 보는 것이기 때문이다. 그래서 이 리졸버는 어떤 이름이든 View를 만들어 돌려주고, 여러 리졸버를 함께 쓸 때는 반드시 맨 뒤에 두어야 한다. 한편 리졸버가 만든 View 객체는 뷰 이름과 로케일별로 캐시된다(AbstractCachingViewResolver). 같은 뷰 이름으로 들어온 다음 요청은 새 객체를 만들지 않고 캐시에 있는 View를 다시 쓴다.

    스프링 부트는 spring.mvc.view.prefix와 spring.mvc.view.suffix 프로퍼티를 읽어 InternalResourceViewResolver를 자동으로 등록한다. 위 ViewConfig와 같은 일을 프로퍼티 두 줄로 하는 셈이다. 같은 타입의 빈을 직접 등록하면 자동 등록은 물러난다. 부트는 이 밖에 BeanNameViewResolver(뷰 이름과 같은 이름의 View 빈을 찾는다)와 ContentNegotiatingViewResolver(스스로 뷰를 만들지 않고 다른 리졸버들에게 위임해 요청의 Accept에 맞는 뷰를 고른다)를 등록한다.

    타임리프(Thymeleaf) 스타터를 넣으면 부트가 타임리프용 뷰 리졸버를 추가로 등록한다. 기본 접두사는 classpath:/templates/, 접미사는 .html이라서 뷰 이름 notices/list는 src/main/resources/templates/notices/list.html을 가리킨다. 타임리프 뷰는 JSP처럼 다른 서블릿으로 forward하지 않고, 템플릿 엔진이 만든 결과를 응답에 쓴다. 컨트롤러 코드는 한 글자도 달라지지 않는다. 부트 레퍼런스는 내장 서블릿 컨테이너에서 JSP를 쓸 때 여러 제약이 있으니 가능하면 피하라고 권한다. 이 회차가 JSP 경로를 예로 든 것은 forward가 눈에 보여 구조를 설명하기 좋기 때문이고, 템플릿 작성은 08회차에서 다룬다.

    뷰 이름 문자열 하나가 redirect: 접두어 여부에 따라 RedirectView의 302 응답과 InternalResourceView의 forward로 갈라지는 것을 보여 준다. 깔끔한 순서도, 흰 배경, 평면 색, 왼쪽에서 오른쪽으로 흐른다. 맨 왼쪽에 둥근 상자 "컨트롤러"에서 화살표가 나오고 화살표 위에 라벨 "뷰 이름(문자열)". 화살표는 큰 상자 "ViewResolver"로 들어간다. ViewResolver 상자 안에 마름모 하나, 라벨 "redirect: 로 시작?". 마름모에서 위쪽으로 나가는 화살표에 라벨 "예", 그 끝에 주황색 상자 "RedirectView", 거기서 오른쪽으로 화살표, 끝에 라벨 "302 + Location 헤더". 마름모에서 아래쪽으로 나가는 화살표에 라벨 "아니오", 그 끝에 작은 상자 "접두사 + 뷰 이름 + 접미사", 이어서 파란색 상자 "InternalResourceView", 거기서 오른쪽으로 화살표 두 단계: 첫 단계 라벨 "모델 → 요청 속성", 둘째 단계 라벨 "forward", 끝에 문서 아이콘과 라벨 "JSP". 장식 없이 단순한 선. 뷰 리졸버는 이름을 View 객체로 바꾸기만 한다. 302를 보낼지 forward할지는 만들어진 View의 종류가 정한다.

    스프링 MVC 시작하기: @Controller와 @RequestMapping

    이제 애노테이션 기반 컨트롤러를 구조 위에 올려 본다. 공지 등록 폼, 공지 저장, 공지 목록 세 기능을 만든다. 첫 단계에서는 직접 만든 프레임워크의 모양을 그대로 따라, 기능마다 클래스를 하나씩 두고 ModelAndView를 돌려준다.

    // 여러 요청 스레드가 함께 쓰는 저장소. 스레드 안전한 컬렉션을 쓴다.
static class NoticeStore {
    private final List titles = new CopyOnWriteArrayList<>(List.of("점검 안내"));
    void add(String title) { titles.add(title); }
    List findAll() { return titles; }
}

@Controller
static class NoticeFormController {
    @RequestMapping("/notices/new")
    public ModelAndView form() {
        return new ModelAndView("notices/form");
    }
}

@Controller
static class NoticeSaveController {
    private final NoticeStore store;
    NoticeSaveController(NoticeStore store) { this.store = store; }

    @RequestMapping("/notices/save")
    public ModelAndView save(HttpServletRequest request) {
        String title = request.getParameter("title");
        store.add(title);
        ModelAndView mv = new ModelAndView("notices/saved");
        mv.addObject("title", title);
        return mv;
    }
}

@Controller
static class NoticeListController {
    private final NoticeStore store;
    NoticeListController(NoticeStore store) { this.store = store; }

    @RequestMapping("/notices")
    public ModelAndView list() {
        ModelAndView mv = new ModelAndView("notices/list");
        mv.addObject("titles", store.findAll());
        return mv;
    }
}

    @Controller는 두 가지 일을 한다. 첫째, 이 애노테이션 자체에 @Component가 붙어 있어서 컴포넌트 스캔의 대상이 되고 스프링 빈으로 등록된다. 둘째, 앞에서 본 isHandler 판정을 통과시켜 RequestMappingHandlerMapping이 이 클래스의 메서드를 훑게 만든다. 실험 코드에서는 스캔 대신 @Bean 메서드로 등록했는데, 빈이 어떤 경로로 등록되었는지는 상관없다. 매핑이 보는 것은 빈의 타입에 @Controller가 있는가뿐이다.

    둘째 역할은 버전에 따라 달랐다. Spring Framework 5.3까지는 클래스에 @RequestMapping만 있어도 핸들러 후보로 보았다. 6.0 릴리스 노트는 이 동작이 바뀌었음을 명시한다. 스프링 MVC와 WebFlux는 더 이상 클래스 수준 @RequestMapping만으로는 컨트롤러를 감지하지 않는다. @Component와 @RequestMapping("/plain")만 붙인 클래스를 빈으로 등록하고 확인해 보면 다음과 같다.

    스프링 MVC — 컨트롤러 통합

    세 클래스는 같은 저장소를 주입받고 같은 주제를 다루는데 파일이 셋으로 흩어져 있다. 직접 만든 프레임워크에서는 컨트롤러 인터페이스에 메서드가 하나뿐이라 기능 하나에 클래스 하나가 강제되었다. 스프링의 애노테이션 방식에는 그 제약이 없다. 앞에서 본 것처럼 조회 표의 값은 클래스가 아니라 HandlerMethod, 곧 메서드이기 때문이다. 한 클래스에 핸들러 메서드를 여러 개 두어도 표의 항목은 여전히 메서드당 하나다.

    @Controller
@RequestMapping("/notices")
static class MergedNoticeController {
    private final NoticeStore store;
    MergedNoticeController(NoticeStore store) { this.store = store; }

    @RequestMapping("/new")
    public ModelAndView form() {
        return new ModelAndView("notices/form");
    }

    @RequestMapping("/save")
    public ModelAndView save(HttpServletRequest request) {
        String title = request.getParameter("title");
        store.add(title);
        ModelAndView mv = new ModelAndView("notices/saved");
        mv.addObject("title", title);
        return mv;
    }

    @RequestMapping
    public ModelAndView list() {
        ModelAndView mv = new ModelAndView("notices/list");
        mv.addObject("titles", store.findAll());
        return mv;
    }
}

  { [/notices/new]} -> MergedNoticeController#form

    조회 표의 키는 첫 단계와 똑같고, 값의 클래스 이름만 달라졌다. 클래스에 붙인 @RequestMapping("/notices")와 메서드에 붙인 @RequestMapping("/new")가 결합되어 /notices/new가 되었다. 이 결합은 요청마다 일어나는 것이 아니라 기동 시점에 표를 만들 때 한 번 계산된다. 경로를 주지 않은 list의 @RequestMapping은 클래스의 경로 /notices를 그대로 물려받았다. 클래스 수준 애노테이션은 공통 조건을, 메서드 수준 애노테이션은 그 안에서의 세부 조건을 표현한다고 보면 된다.

    통합의 이점은 중복된 경로 접두사와 중복된 의존관계 주입이 한 곳으로 모인다는 것이다. 다만 한 클래스에 무엇이든 넣으라는 뜻은 아니다. 클래스 하나가 수십 개의 핸들러 메서드와 여러 저장소 의존성을 갖게 되면 응집도가 떨어진다. 같은 자원(여기서는 공지)을 다루는 요청끼리 묶는 것이 일반적인 기준이다.

    스프링 MVC — 실용적인 방식

    통합한 뒤에도 불편이 남아 있다. 모든 메서드가 ModelAndView를 직접 만들고, 파라미터를 꺼내려고 HttpServletRequest를 받고, HTTP 메서드를 가리지 않는다. 직접 만든 프레임워크에서 컨트롤러가 뷰 이름만 돌려주고 모델은 파라미터로 받도록 고쳤던 것과 같은 방향의 개선을 스프링은 이미 갖추고 있다.

    String 반환과 Model 파라미터

    DispatcherServlet과 어댑터 사이의 계약은 그대로다. HandlerAdapter.handle은 여전히 ModelAndView를 돌려준다. 달라진 것은 그 객체를 누가 만드느냐다. RequestMappingHandlerAdapter는 핸들러 메서드를 부르기 전에 요청마다 ModelAndViewContainer라는 작업용 객체를 하나 만든다. 메서드 파라미터에 Model이 있으면 이 컨테이너가 가진 모델을 인자로 넘긴다. 그러니 컨트롤러가 model.addAttribute로 넣은 값은 어댑터가 쥐고 있는 컨테이너에 쌓인다. 메서드가 문자열을 반환하면 반환값 처리기(ViewNameMethodReturnValueHandler)가 그 문자열을 컨테이너의 뷰 이름으로 넣는다. 마지막으로 어댑터가 컨테이너의 뷰 이름과 모델로 new ModelAndView(…)를 만들어 DispatcherServlet에 돌려준다.

    결국 ModelAndView를 만드는 반복 코드가 컨트롤러에서 어댑터로 옮겨 간 것이다. 컨트롤러는 여전히 ModelAndView를 직접 반환해도 되고, 두 방식은 같은 애플리케이션 안에서 섞어 쓸 수 있다. 어댑터가 반환 타입마다 다른 처리기를 고르기 때문이다.

    @RequestParam

    @RequestParam("title") String title은 request.getParameter("title")을 어댑터가 대신 호출해 그 결과를 인자로 넣어 달라는 선언이다. 쿼리 문자열의 파라미터와 HTML 폼 본문의 파라미터가 같은 방법으로 읽히는 것은 서블릿의 getParameter가 원래 그렇기 때문이다. 대신 호출해 주는 것 이상의 차이도 있다. 출력의 마지막 요청은 title 없이 보낸 POST인데 결과가 400이다. @RequestParam은 기본적으로 필수라서, 파라미터가 없으면 컨트롤러 메서드를 부르지 않고 예외를 던지고, 그 예외가 400 응답으로 바뀐다. 앞의 두 단계에서 같은 요청을 보내면 getParameter가 null을 돌려주고, 코드는 그 null을 그대로 저장한 뒤 200으로 응답했다. 검증을 직접 쓰지 않으면 조용히 잘못된 데이터가 들어가는 코드와, 선언만으로 거절되는 코드의 차이다.

    이름을 생략해 @RequestParam String title처럼 쓰는 코드를 자주 보게 된다. 이때 스프링은 파라미터의 이름을 리플렉션으로 알아내야 하는데, 자바 컴파일러는 -parameters 옵션을 주어야 메서드 파라미터 이름을 클래스 파일에 남긴다. 6.1 릴리스 노트에 따르면 그 전까지 디버그 정보에서 이름을 읽어 내던 LocalVariableTableParameterNameDiscoverer가 6.1에서 제거되었다. 옵션 없이 컴파일한 클래스에 요청을 보내면 다음 예외가 난다.

    java.lang.IllegalArgumentException: Name for argument of type [java.lang.String] not specified, and parameter name information not available via reflection. Ensure that the compiler uses the '-parameters' flag.

    스프링 부트의 Gradle 플러그인은 자바 컴파일 작업에 이 옵션을 넣어 주므로 부트 프로젝트를 Gradle로 빌드하면 문제가 드러나지 않는다. 빌드 방식이 달라져 옵션이 빠지면 같은 코드가 요청 시점에 실패한다. 이름을 애노테이션에 적어 두면 컴파일 옵션과 무관하게 동작한다.

    @GetMapping과 @PostMapping은 합성 애노테이션이다

    @GetMapping의 선언에는 @RequestMapping(method = RequestMethod.GET)이 메타 애노테이션으로 붙어 있다. 4.3에서 추가된 이 애노테이션은 @RequestMapping(value = "/new", method = RequestMethod.GET)을 줄여 쓰는 방법이다. 그런데 자바 언어에는 "애노테이션에 붙은 애노테이션까지 찾아 준다"는 기능이 없다. 메서드에 @GetMapping("/dup")을 붙이고 표준 리플렉션과 스프링의 탐색을 각각 써 보면 차이가 보인다.

    Method m = DupController.class.getDeclaredMethod("first");
System.out.println("isAnnotationPresent(RequestMapping) = " + m.isAnnotationPresent(RequestMapping.class));
RequestMapping merged = AnnotatedElementUtils.findMergedAnnotation(m, RequestMapping.class);
System.out.println("merged = path " + Arrays.toString(merged.path()) + ", method " + Arrays.toString(merged.method()));
    isAnnotationPresent(RequestMapping) = false
merged = path [/dup], method [GET]

    표준 리플렉션은 메서드에 직접 붙은 애노테이션만 알려 주므로 @RequestMapping이 없다고 답한다. 스프링은 애노테이션의 애노테이션을 따라 올라가며 찾고, @GetMapping에 적은 /dup을 @RequestMapping의 path 속성으로 옮겨 합친 결과를 만들어 준다. 조회 표를 만들 때 쓰이는 것이 이 병합된 애노테이션이다. @Controller 안에 @Component가 들어 있는 것, @SpringBootApplication 안에 여러 애노테이션이 들어 있는 것도 같은 탐색으로 동작한다.

    HTTP 메서드 조건이 생기자 출력의 GET /notices/save가 405가 되었다. 이 요청의 추적 출력에는 RequestMappingHandlerMapping 줄이 없다. 매핑이 null을 돌려준 것이 아니라 예외를 던졌기 때문이다. 이 매핑은 조건에 맞는 항목을 찾지 못하면 "경로는 맞는데 다른 조건이 안 맞는 항목"이 있는지 한 번 더 확인하고, HTTP 메서드만 다른 항목이 있으면 HttpRequestMethodNotSupportedException을 던진다. 이 예외가 405 응답이 되고, 응답에는 허용되는 메서드를 알리는 Allow 헤더가 붙는다. 경로 자체가 없으면 null을 돌려주어 404가 된다. 404와 405는 같은 지점에서 갈린다.

  HandlerExecutionChain, HandlerMethod 사본, ModelAndViewContainer, ModelAndView, 모델 맵, 인자 배열

    공유되는 쪽은 전부 "요청과 무관한 것"이다. 조회 표는 기동 뒤에 읽기만 하고, 어댑터와 뷰 리졸버는 설정값만 갖고 있다. 캐시된 View 객체도 공유되지만 문제가 없다. View.render(model, request, response)의 시그니처를 보면 요청마다 달라지는 것은 전부 인자로 들어온다. 요청별 데이터를 필드에 두지 않고 호출 인자로만 흘려보내는 것, 이것이 스프링 MVC 내부가 스레드 안전을 지키는 방식이다. 요청마다 달라지는 값은 지역 변수와 파라미터로 각 스레드의 스택 프레임에 놓이고, 그 변수가 가리키는 객체는 그 스레드만 참조한다.

    개발자가 쓰는 컨트롤러는 공유되는 쪽에 속한다. 그래서 컨트롤러의 필드에 요청별 데이터를 두면 스프링이 지켜 온 규칙을 개발자가 깨게 된다. 예를 들어 save 메서드가 this.lastTitle = title로 필드에 값을 적어 두고 몇 줄 뒤에 그 필드를 읽어 모델에 넣는다면, 그 사이에 다른 스레드가 같은 필드에 다른 제목을 덮어쓸 수 있고, 사용자는 남이 쓴 제목이 적힌 화면을 받는다. 컨트롤러의 필드에 둘 수 있는 것은 NoticeStore처럼 그 자체가 스레드 안전한 협력 객체뿐이다. 예제의 NoticeStore가 ArrayList가 아니라 CopyOnWriteArrayList를 쓴 이유도 여기에 있다. 저장소는 싱글톤이고, 여러 스레드가 동시에 add와 순회를 하기 때문이다.

    DispatcherServlet, 조회 표, 컨트롤러는 하나씩만 있고 두 요청 스레드가 함께 참조하지만, ModelAndView와 모델은 스레드마다 따로 생긴다는 것을 보여 준다. 깔끔한 메모리 구조 그림, 흰 배경, 평면 색. 화면 위쪽 절반에 넓은 연회색 영역, 왼쪽 위에 라벨 "공유 객체(싱글톤)". 그 안에 상자 네 개를 가로로 배치: "DispatcherServlet", "매핑 조회 표", "컨트롤러", "View 캐시". 화면 아래쪽 절반을 좌우로 나눠 왼쪽에 파란 테두리 영역 "요청 스레드 A", 오른쪽에 주황 테두리 영역 "요청 스레드 B". 각 스레드 영역 안에 세로로 쌓인 스택 프레임 두 칸을 그리고 그 옆에 작은 상자 두 개 "ModelAndView", "모델"을 둔다. 스레드 A의 상자들은 파란색, 스레드 B의 상자들은 주황색으로 칠해 서로 다른 객체임을 나타낸다. 두 스레드 영역에서 위쪽 공유 영역의 "컨트롤러" 상자로 각각 화살표 하나씩, 두 화살표가 같은 상자에 모인다. 화살표 옆에 라벨 "같은 객체를 동시에 실행". 스레드 A의 스택에서 자기 "ModelAndView"로, 스레드 B의 스택에서 자기 "ModelAndView"로 짧은 화살표. 장식 없이 단순한 선. 프레임워크의 부품과 컨트롤러는 하나를 함께 쓰고, 요청의 데이터는 스레드마다 따로 만든다. 컨트롤러 필드에 요청 데이터를 두면 이 경계가 무너진다.

    흔한 오해와 함정

    "컨트롤러가 요청을 받는다." 서블릿 컨테이너가 부르는 것은 DispatcherServlet 하나다. 컨트롤러는 서블릿이 아니고 컨테이너는 그 존재를 모른다. 컨트롤러 메서드는 DispatcherServlet이 고른 어댑터가 리플렉션으로 부르는 평범한 메서드다. 그래서 컨트롤러 메서드에 찍은 브레이크포인트까지 요청이 오지 않는다면, 볼 곳은 컨트롤러가 아니라 그 앞 단계(필터, 핸들러 매핑, 인터셉터)다.

    "뷰 리졸버가 화면을 그린다." 뷰 리졸버는 이름을 View 객체로 바꿀 뿐이다. "Could not resolve view"는 리졸버 단계의 실패이고, 템플릿 문법 오류나 JSP 404는 View.render 단계의 실패다. 두 실패는 원인도 고칠 곳도 다르다.

    "빈을 하나 등록하면 기본 구성에 더해진다." DispatcherServlet.properties의 기본값은 해당 타입의 빈이 하나도 없을 때만 쓰인다. 비슷한 일이 한 단계 위에서도 일어난다. 스프링 부트 애플리케이션에 @EnableWebMvc를 붙이면 부트의 MVC 자동 구성이 통째로 빠진다. 부트 레퍼런스는 부트의 MVC 설정을 유지하면서 인터셉터나 포매터를 추가하려면 @EnableWebMvc 없이 WebMvcConfigurer를 구현한 설정 클래스를 쓰라고 안내한다.

    "HTTP 메서드가 안 맞으면 404다." 경로가 없으면 404, 경로는 있는데 메서드가 다르면 405다. 클라이언트 개발자가 "404가 난다"고 할 때와 "405가 난다"고 할 때 서버에서 확인할 것이 다르다. 전자는 경로 오타나 컨트롤러 미등록(@Controller 누락, 컴포넌트 스캔 범위 밖)을, 후자는 @GetMapping과 @PostMapping의 선택을 본다.

    "핸들러 매핑의 우선순위는 정해져 있다." 순서는 구성에 따라 다르다. 실험에서 본 것처럼 기본값 파일에서는 BeanNameUrlHandlerMapping이 먼저이고 @EnableWebMvc와 부트의 구성에서는 RequestMappingHandlerMapping이 먼저다. 순서를 외우기보다 "목록을 순서대로 묻고 첫 답을 쓴다"는 규칙과, 그 목록을 확인하는 방법을 아는 편이 낫다.

    "@RequestMapping만 붙여도 컨트롤러가 된다." 5.3까지는 그랬고 6.0부터는 아니다. 클래스에 @Controller(또는 그것을 포함한 @RestController)가 있어야 조회 표에 들어간다.

    다른 주제와의 연결

    이 회차는 요청이 지나가는 길의 전체 모양을 보았고, 다음 회차들은 그 길의 각 구간을 확대한다. 06회차는 RequestMappingInfo의 조건들, 곧 경로 변수와 HTTP 메서드·파라미터·헤더·미디어 타입 조건을 다루고, 요청 데이터를 꺼내는 여러 애노테이션을 본다. 07회차는 RequestMappingHandlerAdapter의 안쪽을 연다. 이 회차에서 "어댑터가 인자를 만들고 반환값을 해석한다"고만 말한 부분이 ArgumentResolver와 ReturnValueHandler, 그리고 HTTP 메시지 컨버터로 구체화된다. @ResponseBody를 쓰면 어댑터가 응답 본문을 직접 쓰고 ModelAndView로 null을 돌려주어 뷰 렌더링이 생략되는데, 이는 이 회차의 HttpRequestHandler 실험에서 본 것과 같은 길이다.

    08회차에서는 타임리프 템플릿으로 실제 화면을 만들고, redirect: 뷰 이름이 왜 폼 처리에 필요한지를 PRG 패턴으로 설명한다. 「스프링 MVC 2편」으로 가면 doDispatch에서 스쳐 지나간 두 지점이 주제가 된다. HandlerExecutionChain에 담긴 인터셉터의 preHandle·postHandle·afterCompletion, 그리고 processDispatchResult에서 예외를 응답으로 바꾸는 HandlerExceptionResolver다. 둘 다 이 회차의 흐름도에서 자리를 찾을 수 있다.

    더 멀리 보면, 조회 표를 기동 시점에 만들어 두고 요청 시점에는 리플렉션으로 호출하는 방식은 스프링 전반에서 반복된다. 애노테이션을 읽어 메타데이터를 미리 계산해 두고, 실행 시점에는 그 메타데이터에 따라 대신 호출해 주는 구조는 트랜잭션이나 AOP의 프록시에서도 같은 모양으로 나타난다.

    이 장의 핵심

    스프링 MVC는 프런트 컨트롤러 하나(DispatcherServlet)와 세 종류의 교체 가능한 목록(핸들러 매핑, 핸들러 어댑터, 뷰 리졸버)으로 이루어져 있다. 요청은 "목록을 순서대로 묻고 첫 답을 쓴다"는 같은 규칙으로 세 번 넘겨진다. @Controller와 @RequestMapping은 기동 시점에 조회 표의 항목이 되고, 요청 시점에는 어댑터가 리플렉션으로 메서드를 부른 뒤 결과를 ModelAndView로 맞춰 준다. 프레임워크의 부품과 컨트롤러는 모든 요청이 공유하고, 요청의 데이터는 호출 인자와 지역 변수로만 흐른다.
    DispatcherServlet
    HttpServlet을 상속한 프런트 컨트롤러. doDispatch에서 핸들러 조회, 어댑터 조회, 핸들러 실행, 뷰 해석, 렌더링을 순서대로 지휘하고 구체 클래스에는 의존하지 않는다.
    HandlerMapping
    요청에 맞는 핸들러와 인터셉터 묶음(HandlerExecutionChain)을 돌려준다. 여러 개가 목록으로 등록되고, 순서대로 물어 null이 아닌 첫 답이 쓰인다. 모두 null이면 404다.
    HandlerAdapter
    supports(handler)로 자신이 실행할 수 있는 핸들러인지 답하고, handle에서 핸들러 고유의 호출 방식을 감춘 채 ModelAndView 또는 null을 돌려준다.
    전략의 출처
    서블릿 초기화 때 컨테이너에서 타입별 빈을 찾아 순서대로 정렬해 쓰고, 그 타입의 빈이 하나도 없을 때만 DispatcherServlet.properties의 기본값을 쓴다. @EnableWebMvc와 스프링 부트는 빈으로 등록하는 쪽이다.
    RequestMappingHandlerMapping
    기동 시점에 @Controller 빈의 메서드를 훑어 RequestMappingInfo → HandlerMethod 조회 표를 만든다. 중복 매핑은 기동 시점에, 메서드 불일치(405)와 경로 없음(404)은 요청 시점에 드러난다.
    ViewResolver와 View
    뷰 리졸버는 논리 이름을 View 객체로 바꾸고, View가 모델을 받아 응답을 만든다. InternalResourceView는 모델을 요청 속성에 옮긴 뒤 forward하고, RedirectView는 302를 보낸다.
    컨트롤러 통합
    조회 표의 값은 메서드 단위(HandlerMethod)이므로 한 클래스에 핸들러 메서드를 여럿 둘 수 있다. 클래스 수준과 메서드 수준 @RequestMapping은 기동 시점에 한 번 결합된다.
    실용적인 방식
    String 반환, Model·@RequestParam 파라미터, @GetMapping·@PostMapping을 쓰면 ModelAndView를 만드는 일이 어댑터로 옮겨 간다. DispatcherServlet과 어댑터 사이의 계약은 변하지 않는다.
    공유와 스레드 안전
    DispatcherServlet, 매핑, 어댑터, 뷰 리졸버, 컨트롤러는 하나를 모든 요청 스레드가 공유한다. 요청별 데이터는 인자와 지역 변수로만 다루고 컨트롤러 필드에 두지 않는다.

    실무에서 다시 판단하면, 이 회차의 지식이 가장 자주 쓰이는 곳은 "요청이 어디까지 갔는가"를 가리는 장애 분석이다. 404라면 핸들러 매핑 단계에서 끝난 것이므로 조회 표에 항목이 있는지부터 본다. org.springframework.web 로그 레벨을 TRACE로 낮춰 기동 시 등록되는 매핑을 확인하거나 액추에이터의 매핑 엔드포인트를 보는 방법이 있다. 컨트롤러 클래스가 컴포넌트 스캔 범위 밖에 있거나 @Controller가 빠져 있으면 빈이 있어도 표에는 없다. 405라면 경로는 맞았다는 뜻이고, 필수 파라미터 누락으로 난 400이라면 핸들러까지는 찾았고 어댑터가 인자를 만들다 실패한 것이다. 뷰 이름을 못 찾는 오류와 "Circular view path"는 핸들러가 정상 종료한 뒤의 일이므로 컨트롤러 로직이 아니라 뷰 리졸버 구성과 템플릿 의존성을 본다.

    설계 판단에서는 "무엇을 구성으로 바꾸고 무엇을 건드리지 않을 것인가"가 문제다. 핸들러 매핑, 어댑터, 뷰 리졸버를 직접 빈으로 등록하면 기본값이나 자동 구성이 물러나는 규칙 때문에, 하나를 바꾸려다 전체를 잃는 일이 생긴다. 스프링 부트를 쓴다면 @EnableWebMvc를 붙이기 전에 WebMvcConfigurer로 충분한지 먼저 확인하는 것이 안전하다. 반대로 레거시 애플리케이션에서 인터페이스 기반 Controller와 애노테이션 컨트롤러가 섞여 있다면, 두 방식이 서로 다른 매핑·어댑터 쌍으로 공존한다는 것을 알고 있어야 같은 URL을 양쪽에 등록했을 때 누가 응답하는지 예측할 수 있다.

    성능 관점에서 프레임워크가 요청마다 하는 일(맵 조회, 리플렉션 호출, 작은 객체 몇 개 생성)은 컨트롤러가 호출하는 데이터베이스나 외부 API의 대기 시간에 비하면 대개 문제가 되지 않는다. 그보다 중요한 것은 이 모든 과정이 요청을 받은 작업 스레드 하나에서 동기적으로 실행된다는 사실이다. 컨트롤러 메서드가 느린 호출에서 멈춰 있으면 그 스레드는 풀로 돌아가지 못하고, 01회차에서 본 스레드 풀 고갈로 이어진다. 그리고 컨트롤러는 싱글톤이다. 코드 리뷰에서 컨트롤러나 서비스에 final이 아닌 필드가 보이면, 그것이 요청별 데이터가 아닌지 확인하는 습관이 동시성 버그를 가장 싸게 막는다.
  • MVC 설정 클래스에 다음 두 빈이 함께 등록되어 있다. 빈 이름이 /reports이고 Controller 인터페이스를 구현해 뷰 이름 old/reports를 돌려주는 객체, 그리고 @Controller 클래스 안에서 @RequestMapping("/reports")가 붙어 뷰 이름 new/reports를 돌려주는 메서드다. GET /reports를 보냈을 때 (가) MVC 관련 빈을 따로 등록하지 않아 DispatcherServlet.properties의 기본 전략으로 도는 경우와 (나) @EnableWebMvc를 붙인 경우에 각각 어느 뷰 이름이 나오는지, getHandler의 동작으로 설명하라.
  • 다음 컨트롤러가 등록되었을 때 만들어지는 조회 표의 항목을 모두 적고, 여섯 요청 GET /orders, POST /orders, DELETE /orders, GET /orders/new, POST /orders/new, GET /orders/old의 결과(호출되는 메서드 또는 상태 코드)를 예측하라. 클래스에는 @Controller와 @RequestMapping("/orders")가, 메서드 list에는 @GetMapping, create에는 @PostMapping, form에는 @GetMapping("/new")가 붙어 있다.
  • 뷰 리졸버가 접두사·접미사 없는 InternalResourceViewResolver 하나뿐이다. (가) /reports에 매핑된 메서드가 뷰 이름 reports를 돌려줄 때와 (나) /reports/monthly에 매핑된 메서드가 뷰 이름 summary를 돌려줄 때 각각 무슨 일이 일어나는지 설명하라. 그리고 접두사 /WEB-INF/views/, 접미사 .jsp를 설정하면 두 경우의 forward 대상이 무엇이 되는지 적어라.
  • 다음 컨트롤러는 혼자 테스트할 때는 잘 동작하지만 사용자가 몰리면 가끔 다른 사람의 검색어가 화면에 나온다. 원인을 메모리와 스레드 관점에서 설명하고 고쳐라. 
    @Controller
public class SearchController {
    private String keyword;

    @GetMapping("/search")
    public String search(@RequestParam("q") String q, Model model) {
        this.keyword = q;
        List results = searchService.find(q);   // 수십 밀리초가 걸린다
        model.addAttribute("keyword", this.keyword);
        model.addAttribute("results", results);
        return "search/result";
    }
    // ... searchService 필드와 생성자
}

    1번. getHandler는 핸들러 매핑 목록을 앞에서부터 돌며 null이 아닌 첫 결과를 쓴다. 그러므로 답은 목록의 순서가 정한다. (가)에서는 기본값 파일의 순서대로 BeanNameUrlHandlerMapping이 첫째다. 이 매핑의 표에 /reports가 있으므로 인터페이스 기반 컨트롤러가 선택되고 뷰 이름은 old/reports다. RequestMappingHandlerMapping에는 물어보지도 않는다. (나)에서는 WebMvcConfigurationSupport가 RequestMappingHandlerMapping을 순서 0, BeanNameUrlHandlerMapping을 순서 2로 등록하므로 애노테이션 매핑이 먼저 답하고 뷰 이름은 new/reports다. 실제로 두 구성으로 실행해 보면 이 결과가 나온다. 같은 코드가 구성에 따라 다르게 동작하므로, 한 URL을 두 방식으로 등록하는 것 자체를 피해야 한다.

    2번. 클래스와 메서드의 매핑이 결합되어 항목은 셋이다. {GET [/orders]} → list, {POST [/orders]} → create, {GET [/orders/new]} → form. GET /orders는 list, POST /orders는 create, GET /orders/new는 form이 호출된다. DELETE /orders는 경로가 같은 항목이 있지만 메서드 조건이 맞는 것이 없으므로 405이고, Allow 헤더에는 GET과 POST가 들어간다. POST /orders/new도 같은 이유로 405이며 Allow는 GET이다. GET /orders/old는 경로가 맞는 항목이 아예 없으므로 매핑이 null을 돌려주고 404가 된다. 경로가 맞는지 여부가 404와 405를 가른다.

    3번. (가) 접두사와 접미사가 빈 문자열이므로 뷰의 URL은 reports다. 현재 요청 URI /reports를 기준으로 상대 경로를 풀면 /reports로 같아진다. forward하면 같은 핸들러로 되돌아와 끝없이 반복되므로 스프링이 forward 전에 "Circular view path" 예외를 던진다. (나) URL은 summary이고, /reports/monthly를 기준으로 풀면 /reports/summary다. 요청 URI와 다르므로 순환 검사는 통과하고 그 경로로 forward가 일어난다. 그 경로를 처리할 서블릿이나 핸들러가 없으면 결과는 404다. 예외 없이 엉뚱한 404가 나오므로 (가)보다 원인을 찾기 어렵다. 접두사와 접미사를 설정하면 URL은 각각 /WEB-INF/views/reports.jsp와 /WEB-INF/views/summary.jsp가 된다. 접두사가 /로 시작하는 절대 경로이므로 현재 요청 URI와 무관해진다.

    4번. SearchController는 싱글톤 빈이어서 힙에 객체가 하나뿐이고, 모든 요청 스레드가 같은 객체의 search를 실행한다. keyword 필드도 하나뿐이다. 스레드 A가 this.keyword = "java"를 실행하고 searchService.find에서 기다리는 동안 스레드 B가 this.keyword = "spring"을 실행하면, A가 돌아와 this.keyword를 읽을 때 값은 spring이다. A의 화면에는 java의 검색 결과와 spring이라는 검색어가 함께 나온다. 혼자 테스트할 때는 두 스레드가 겹치지 않아 드러나지 않는다. 반면 파라미터 q와 지역 변수 results, 그리고 어댑터가 요청마다 새로 만들어 넘기는 model은 스레드마다 따로다. 고치는 방법은 필드를 없애고 model.addAttribute("keyword", q)로 파라미터를 직접 쓰는 것이다. 필드에 volatile을 붙이거나 메서드를 synchronized로 만드는 것은 답이 아니다. 전자는 덮어쓰기를 막지 못하고, 후자는 모든 검색 요청을 한 줄로 세워 처리량을 떨어뜨린다. 요청별 데이터는 애초에 공유할 이유가 없다.

     스프링 MVC에 지금까지 없던 새로운 형태의 핸들러(특정 인터페이스를 구현하지 않고, 고유한 방식으로 호출해야 하는 객체)를 지원하려고 한다. 구조에 맞는 방법은 무엇인가? DispatcherServlet을 상속해 doDispatch 안에 새 핸들러 타입을 처리하는 분기를 추가한다. 요청을 그 핸들러로 연결하는 HandlerMapping과, 그 핸들러를 실행할 줄 아는 HandlerAdapter를 구현해 빈으로 등록한다. 새 핸들러가 ModelAndView를 반환하도록 강제하면 기존 어댑터가 자동으로 실행해 준다. ViewResolver를 새로 구현해 핸들러의 반환값을 해석하게 한다. DispatcherServlet은 핸들러를 Object로만 다루고, 누가 찾고 누가 실행할지는 등록된 매핑과 어댑터 목록에 묻는다. 새 핸들러 종류는 매핑·어댑터 한 쌍을 추가하는 것으로 지원되며, 함수형 엔드포인트의 RouterFunctionMapping과 HandlerFunctionAdapter가 그런 예다. doDispatch를 고치는 것은 이 설계가 피하려던 방법이다. 기존 어댑터는 supports에서 타입을 검사하므로 반환 타입만 맞춘다고 실행해 주지 않는다. 뷰 리졸버는 핸들러 실행이 끝난 뒤의 단계다. @PostMapping("/notices/save") 메서드만 있는 애플리케이션에 GET /notices/save를 보내면 405가, GET /notices/remove를 보내면 404가 응답된다. 두 결과가 갈리는 지점에 대한 설명으로 옳은 것은? 405는 톰캣이 서블릿을 호출하기 전에 판단하고, 404는 DispatcherServlet이 판단한다. 둘 다 핸들러 어댑터가 컨트롤러 메서드를 호출하다가 실패한 결과다. 둘 다 핸들러 매핑 단계에서 갈린다. 경로가 맞는 항목이 없으면 매핑이 null을 돌려주어 404가 되고, 경로는 맞지만 HTTP 메서드가 다른 항목이 있으면 매핑이 예외를 던져 405가 된다. 405는 뷰 리졸버가 뷰를 찾지 못해서, 404는 뷰 파일이 없어서 나는 결과다. RequestMappingHandlerMapping은 조건에 맞는 항목을 찾지 못하면 경로만 맞는 항목이 있는지 다시 확인하고, 있으면 HttpRequestMethodNotSupportedException을 던진다. 경로조차 맞는 것이 없으면 null을 돌려주고, 모든 매핑이 null이면 404다. 두 경우 모두 핸들러가 선택되지 않았으므로 어댑터와 뷰 리졸버는 관여하지 않는다. 톰캣은 /에 매핑된 DispatcherServlet으로 요청을 넘길 뿐 컨트롤러의 HTTP 메서드 조건을 알지 못한다. MVC 관련 빈을 전혀 등록하지 않고 DispatcherServlet의 기본 전략으로 잘 돌던 애플리케이션에, 특정 URL을 처리하려고 HandlerMapping 구현체 하나를 빈으로 등록했다. 그 뒤로 기존 @Controller들의 URL이 전부 404가 되었다. 원인은 무엇인가? HandlerMapping 타입의 빈이 하나라도 있으면 DispatcherServlet.properties의 기본 핸들러 매핑들이 쓰이지 않아, RequestMappingHandlerMapping이 목록에서 빠졌기 때문이다. 새 매핑이 모든 요청에 대해 예외를 던지기 때문이다. 핸들러 매핑은 애플리케이션에 하나만 존재할 수 있기 때문이다. 새 매핑을 등록하면 컴포넌트 스캔이 중단되어 컨트롤러 빈이 만들어지지 않기 때문이다. 초기화 때 DispatcherServlet은 컨테이너에서 HandlerMapping 빈을 찾고, 하나도 없을 때에만 기본값 파일의 구현체들을 만든다. 빈을 하나 등록하는 순간 목록은 그 빈 하나가 되고, 애노테이션 매핑을 맡던 RequestMappingHandlerMapping은 만들어지지 않는다. 컨트롤러 빈은 그대로 컨테이너에 있지만 조회 표를 만들 주체가 없다. 매핑은 여러 개가 공존할 수 있고, 그것이 목록으로 관리하는 이유다. 컨트롤러가 뷰 이름 notices/list를 돌려주고, 접두사 /WEB-INF/views/와 접미사 .jsp가 설정된 InternalResourceViewResolver가 등록되어 있다. 모델의 값을 요청 속성으로 옮기고 RequestDispatcher.forward를 호출하는 객체는 무엇인가? 컨트롤러. 뷰 이름을 돌려주는 시점에 스프링이 컨트롤러 안에서 forward를 수행한다. RequestMappingHandlerAdapter. 핸들러 실행과 화면 이동을 함께 맡는다. InternalResourceViewResolver. 이름을 경로로 바꾼 뒤 바로 forward한다. InternalResourceView. 뷰 리졸버가 만들어 돌려준 이 객체의 render가 호출될 때 수행한다. 뷰 리졸버의 일은 이름을 View 객체로 바꾸는 데서 끝난다. DispatcherServlet이 그 View의 render(model, request, response)를 호출하면, InternalResourceView가 모델 항목을 request.setAttribute로 옮기고 forward한다. 어댑터는 ModelAndView를 돌려주는 것까지만 하고, 컨트롤러는 문자열을 반환한 뒤 이미 끝났다. 이 분리 덕분에 같은 컨트롤러가 RedirectView나 타임리프 뷰와도 그대로 동작한다. 스프링 MVC 컨트롤러에서 동시 요청이 몰려도 다른 요청의 데이터와 섞이지 않는 것은 어느 것인가? 컨트롤러 클래스의 인스턴스 필드에 저장한 요청 파라미터 값 컨트롤러 클래스의 static 필드에 저장한 현재 사용자 이름 핸들러 메서드가 파라미터로 받은 Model에 넣은 값 컨트롤러가 필드로 가진 ArrayList에 요청마다 추가한 값 컨트롤러는 싱글톤 빈이어서 인스턴스 필드도 static 필드도 모든 요청 스레드가 공유한다. 필드에 둔 ArrayList는 공유될 뿐 아니라 스레드 안전하지도 않아 동시에 add하면 내용이 깨질 수 있다. 반면 Model은 어댑터가 요청마다 새로 만든 ModelAndViewContainer에 속한 객체이고, 그 참조는 해당 요청을 처리하는 스레드의 스택 프레임에만 있다.
    프런트 컨트롤러(front controller)
    모든 요청을 먼저 받아 공통 처리를 한 뒤 알맞은 처리 객체로 넘기는 단일 진입점. 스프링 MVC에서는 DispatcherServlet이 이 역할이다.
    핸들러(handler)
    요청을 실제로 처리하는 객체. 타입 제약이 없어 Controller 구현체, HttpRequestHandler 구현체, HandlerMethod(애노테이션 메서드) 등이 모두 핸들러가 될 수 있다.
    핸들러 매핑(HandlerMapping)
    요청을 보고 핸들러와 인터셉터 묶음을 찾아 주는 전략 인터페이스. RequestMappingHandlerMapping, BeanNameUrlHandlerMapping 등이 구현체다.
    핸들러 어댑터(HandlerAdapter)
    핸들러 종류마다 다른 호출 방식을 감추고 DispatcherServlet에 한 가지 호출 방법(handle)을 제공하는 전략 인터페이스.
    HandlerExecutionChain
    핸들러 하나와 그 앞뒤에서 실행할 인터셉터 목록을 묶은 객체. 핸들러 매핑의 반환값이다.
    HandlerMethod
    애노테이션 기반 핸들러를 나타내는 객체. 어느 빈의 어느 Method인지와 파라미터 정보를 담는다.
    RequestMappingInfo
    @RequestMapping에서 만들어지는 매핑 조건의 묶음. 경로 패턴, HTTP 메서드, 파라미터, 헤더, 미디어 타입 조건을 포함하며 조회 표의 키가 된다.
    뷰 리졸버(ViewResolver)
    논리 뷰 이름을 View 객체로 바꾸는 전략 인터페이스. 모른다는 뜻으로 null을 돌려줄 수 있고, 그러면 다음 리졸버에게 기회가 넘어간다.
    합성 애노테이션(composed annotation)
    다른 애노테이션을 메타 애노테이션으로 포함해 그 설정을 미리 채워 둔 애노테이션. @GetMapping은 @RequestMapping(method = GET)을 포함한다. 스프링의 병합 탐색이 이를 해석한다.
    리플렉션(reflection)
    실행 중에 클래스의 메서드·필드 정보를 객체로 얻어 조회하거나 호출하는 자바 기능. 애노테이션 컨트롤러의 메서드는 Method.invoke로 호출된다.
