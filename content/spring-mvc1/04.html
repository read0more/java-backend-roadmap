    이 회차의 질문: 컨트롤러가 열 개가 되면 무엇이 열 번 반복되는가

    03회에서 서블릿이 컨트롤러 역할을, JSP가 뷰 역할을 맡도록 나누는 MVC 패턴까지 왔다. 서블릿은 요청 파라미터를 읽어 비즈니스 로직을 호출하고, 결과를 요청 속성(request attribute)에 담은 다음 JSP로 forward한다. 역할은 나뉘었지만 그 구조로 기능을 하나 더 만들 때마다 같은 코드를 다시 쓰게 된다. 도서를 등록하는 컨트롤러 하나를 그 방식으로 써 보면 반복되는 부분이 보인다.

    @WebServlet(urlPatterns = "/books/save")
public class SaveBookServlet extends HttpServlet {
    private final BookRepository repository = BookRepository.getInstance();

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        request.setCharacterEncoding("UTF-8");                          // 모든 컨트롤러가 똑같이 하는 일

        String title = request.getParameter("title");
        String author = request.getParameter("author");
        Book book = repository.save(title, author);                     // 이 컨트롤러만 하는 일

        request.setAttribute("book", book);
        request.getRequestDispatcher("/WEB-INF/views/book-saved.jsp")   // 모든 컨트롤러가 똑같이 하는 일
                .forward(request, response);
    }
}

    이 클래스에서 "도서 저장"이라는 기능에 고유한 부분은 가운데 세 줄뿐이다. 나머지는 등록 폼, 목록, 상세, 수정 컨트롤러를 만들 때마다 글자 그대로 되풀이된다. 되풀이되는 것을 종류별로 나누면 다음과 같다.

    • 공통 전처리. 요청 본문의 문자 인코딩 지정, 로그, 로그인 여부 확인 같은 일을 서블릿마다 맨 앞에 적어야 한다. 한 군데라도 빠뜨리면 그 URL만 다르게 동작한다.
    • 뷰로 넘기는 절차. getRequestDispatcher(경로).forward(request, response)라는 두 호출, 그리고 경로의 앞부분 /WEB-INF/views/와 뒷부분 .jsp가 매번 나온다. 뷰 파일의 위치나 기술을 바꾸면 모든 컨트롤러를 고쳐야 한다.
    • 서블릿이라는 형식. 컨트롤러 하나가 HttpServlet을 상속하고 URL 매핑을 하나씩 선언한다. HttpServletResponse는 forward에 넘기는 것 말고는 쓰지 않는데도 받아야 한다. 요청·응답 객체의 실제 구현은 컨테이너가 만들어 넘겨주므로, 이 세 줄짜리 로직을 시험하려면 서버를 띄우거나 요청·응답을 흉내 낸 가짜 객체를 따로 만들어야 한다.

    이 셋은 원인이 같다. 요청이 들어오는 입구가 컨트롤러 수만큼 있다. 컨테이너가 URL을 보고 서블릿을 고르는 순간 요청은 이미 개별 컨트롤러 안에 들어와 있으므로, 모든 요청에 공통인 일을 적어 둘 "그 앞"이 애플리케이션 코드에는 없다. 서블릿 필터(filter)를 쓰면 서블릿 앞에 공통 코드를 끼울 수 있지만, 필터의 본래 역할은 요청이나 응답에 공통 작업을 한 뒤 컨테이너가 매핑으로 고른 대상에 요청을 넘기는 것이어서, 어느 컨트롤러를 부를지 고르고 컨트롤러가 돌려준 결과를 받아 뷰를 그리는 일은 그 역할 밖에 있다. 이 회차는 입구를 하나로 줄이는 데서 시작해, 그 입구를 다섯 번 고쳐 가며 작은 MVC 프레임워크를 만든다. 다 만들고 나면 05회에서 볼 스프링 MVC의 DispatcherServlet과 뼈대가 같다는 것을 확인하게 된다.

    이 회차의 실행 결과, 호출 스택, 바이트코드는 원고를 쓰면서 JDK 21.0.13(Temurin)과 임베디드 톰캣 11.0.27(서블릿 API 6.1)에서 직접 돌려 얻은 것이다. 스프링 부트 없이 서블릿을 코드로 등록했고, JSP 엔진은 붙이지 않았다. JSP가 있을 자리에는 *.jsp에 매핑한 확인용 서블릿을 두어, forward를 받으면 자신이 받은 경로와 요청 속성을 그대로 출력하게 했다. 본문이 근거로 삼는 규칙(매핑 순서, 경로 요소, forward의 제약, WEB-INF)은 이 강좌의 기준인 Jakarta Servlet 6.0 명세에서 확인했고, 스프링에 관한 서술은 스프링 프레임워크 7.0.10 소스에서 확인했고, DispatcherServlet의 처리 순서와 기본 어댑터 목록, InternalResourceView의 동작은 기준 버전인 6.2 소스에서도 같음을 확인했다.

    프런트 컨트롤러 패턴: 입구를 하나로 줄인다

    프런트 컨트롤러(front controller) 패턴은 모든 요청을 서블릿 하나가 먼저 받게 하는 구조다. 그 서블릿은 요청을 직접 처리하지 않는다. 공통으로 할 일을 한 다음, 요청에 맞는 컨트롤러 객체를 찾아 호출하고, 컨트롤러가 일을 마치면 응답을 마무리한다. 이 "맨 앞의 서블릿"을 프런트 컨트롤러라고 부른다.

    구조가 바뀌면 일을 나누는 층이 하나 더 생긴다. 지금까지는 "URL을 보고 실행할 코드를 고른다"는 일을 컨테이너가 혼자 했다. 프런트 컨트롤러를 두면 이 일이 두 단계로 나뉜다. 컨테이너는 넓은 범위의 URL 전체를 프런트 컨트롤러 하나에 넘기기만 하고, 그 안에서 어느 컨트롤러를 부를지는 애플리케이션이 가진 표를 보고 프런트 컨트롤러가 정한다.

    [도입 전] 컨테이너가 URL마다 다른 서블릿을 고른다

  요청 ─▶ 서블릿 컨테이너 ─┬─ /books/new-form ─▶ NewBookFormServlet  (공통 처리 + 로직 + forward)
                          ├─ /books/save     ─▶ SaveBookServlet     (공통 처리 + 로직 + forward)
                          └─ /books          ─▶ ListBooksServlet    (공통 처리 + 로직 + forward)

[도입 후] 컨테이너는 서블릿 하나만 알고, 나머지는 그 서블릿이 고른다

  요청 ─▶ 서블릿 컨테이너 ── /v1/* ─▶ 프런트 컨트롤러 (서블릿, 공통 처리)
                                        │  URL → 컨트롤러 표를 조회
                                        ├─▶ 등록 폼 컨트롤러  (서블릿이 아닌 보통 객체)
                                        ├─▶ 저장 컨트롤러
                                        └─▶ 목록 컨트롤러

    이 변화에서 얻는 것은 세 가지다. 첫째, 공통 처리를 적을 자리가 생긴다. 프런트 컨트롤러의 메서드 첫머리에 한 번 적으면 모든 요청에 적용된다. 둘째, 나머지 컨트롤러는 서블릿일 필요가 없어진다. 컨테이너가 직접 부르는 객체는 프런트 컨트롤러뿐이므로 컨트롤러는 프런트 컨트롤러가 정한 인터페이스만 구현한 보통 자바 객체가 된다. 셋째, 컨트롤러 호출의 앞과 뒤를 프런트 컨트롤러가 쥐게 된다. 컨트롤러에 무엇을 넘기고 무엇을 돌려받을지를 애플리케이션이 설계할 수 있다는 뜻이고, 이 회차의 v2부터 v5까지는 전부 이 세 번째 이점을 조금씩 더 쓰는 과정이다.

    일상에서 가져온 비유건물 1층의 안내 데스크

    방문객이 각 사무실 문을 직접 찾아가는 건물에서는 사무실마다 방문증 확인과 방명록 작성을 따로 해야 한다. 1층에 안내 데스크를 두고 모든 방문객이 거기를 거치게 하면, 확인과 기록은 데스크에서 한 번만 하고 사무실은 본래 업무만 하면 된다. 어느 사무실로 보낼지는 데스크가 가진 층별 안내표로 정한다. 안내 데스크가 프런트 컨트롤러, 안내표가 URL과 컨트롤러를 잇는 표, 사무실이 컨트롤러다. 비유가 깨지는 지점은 줄이다. 안내 직원은 한 번에 한 사람만 응대하므로 방문객이 몰리면 줄이 생기지만, 프런트 컨트롤러는 객체가 하나일 뿐 그 메서드는 요청 스레드 여러 개가 같은 순간에 각자 실행한다. 입구가 하나라는 것은 코드가 한 벌이라는 뜻이지 차례를 기다린다는 뜻이 아니다.

    왼쪽은 컨테이너가 URL마다 다른 서블릿으로 요청을 보내고 각 서블릿 안에 공통 처리가 중복된 모습, 오른쪽은 컨테이너가 프런트 컨트롤러 하나에만 요청을 보내고 그 뒤에 보통 객체인 컨트롤러들이 매달린 모습을 나란히 보여 준다. 깔끔한 평면 벡터 스타일의 좌우 비교 다이어그램, 흰 배경. 왼쪽 패널 제목 "도입 전". 왼쪽 패널의 왼쪽 끝에 세로로 긴 둥근 사각형 "서블릿 컨테이너"가 있고, 거기서 오른쪽으로 화살표 세 개가 나가 세로로 나란한 상자 세 개에 닿는다. 세 상자의 라벨은 모두 "서블릿"이며, 각 상자 안에는 위에서 아래로 띠 세 개가 있다. 위 띠와 아래 띠는 같은 회색으로 칠하고 라벨 없이 두며, 가운데 띠만 상자마다 다른 색으로 칠한다. 왼쪽 패널 아래에 회색 띠 옆에 "공통 처리가 서블릿마다 중복"이라는 주석을 단다. 오른쪽 패널 제목 "도입 후". 오른쪽 패널의 왼쪽 끝에 같은 "서블릿 컨테이너" 상자가 있고, 굵은 화살표 하나가 가운데의 큰 상자 "프런트 컨트롤러"로 간다. 프런트 컨트롤러 상자 안 위쪽에 회색 띠 하나와 라벨 "공통 처리", 아래쪽에 작은 표 아이콘과 라벨 "URL → 컨트롤러". 프런트 컨트롤러에서 오른쪽으로 가는 화살표 세 개가 색이 서로 다른 작은 상자 세 개에 닿고, 세 상자 묶음에 라벨 "컨트롤러 (보통 객체)"를 단다. 입구가 하나가 되면 공통 처리는 한 번만 쓰고, 컨트롤러는 서블릿이라는 형식에서 벗어난다.

    컨테이너는 어떤 요청을 프런트 컨트롤러에 넘기는가

    프런트 컨트롤러도 서블릿이므로, 그것이 "모든 요청"을 받게 하려면 컨테이너의 URL 매핑 규칙을 정확히 알아야 한다. Jakarta Servlet 명세는 매핑 패턴의 형태를 다섯 가지로 정해 두었고(§12.2), 요청 경로를 서블릿에 대응시키는 순서도 정해 두었다(§12.1).

    이 차이는 프런트 컨트롤러가 "URL → 컨트롤러" 표의 키로 어떤 문자열을 쓸지와 직접 이어진다. 이 회차의 예제는 읽기 쉽도록 getRequestURI()를 키로 쓴다. 표에 적힌 키가 브라우저 주소창의 경로와 같아서 따라가기 편하지만, 컨텍스트 경로가 바뀌거나 경로에 인코딩된 글자, 경로 파라미터가 섞이면 키가 어긋난다. 실제 프레임워크가 요청 경로를 다루는 코드가 단순한 문자열 비교보다 훨씬 긴 이유가 여기에 있다.

    v1 — 프런트 컨트롤러 도입

    첫 단계의 목표는 구조만 바꾸는 것이다. 컨트롤러 안의 코드는 서블릿이던 때와 거의 같게 두고, 입구만 하나로 모은다. 먼저 프런트 컨트롤러가 컨트롤러를 부를 때 쓸 약속을 인터페이스로 정한다. 서블릿의 service와 모양이 같다.

    interface ServletController {
    void handle(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException;
}

class SaveBookV1 implements ServletController {
    private final BookRepository repository = BookRepository.getInstance();

    @Override
    public void handle(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        String title = request.getParameter("title");
        String author = request.getParameter("author");
        Book book = repository.save(title, author);

        request.setAttribute("book", book);
        request.getRequestDispatcher("/WEB-INF/views/book-saved.jsp").forward(request, response);
    }
}

class ListBooksV1 implements ServletController {
    private final BookRepository repository = BookRepository.getInstance();

    @Override
    public void handle(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        request.setAttribute("books", repository.findAll());
        request.getRequestDispatcher("/WEB-INF/views/book-list.jsp").forward(request, response);
    }
}

    Book은 record Book(long id, String title, String author)이고, BookRepository는 도서를 메모리에 보관하는 저장소다. 저장소가 어떤 자료구조를 쓰는지는 뒤의 동시성 절에서 다시 본다. 컨트롤러 클래스에는 extends HttpServlet도 @WebServlet도 없다. 컨테이너는 이 클래스들의 존재를 모른다. 이들을 아는 것은 프런트 컨트롤러뿐이다.

    @WebServlet(urlPatterns = "/v1/*")
public class FrontV1 extends HttpServlet {
    private final Map controllers = new HashMap<>();

    public FrontV1() {
        controllers.put("/v1/books/new-form", new NewBookFormV1());
        controllers.put("/v1/books/save", new SaveBookV1());
        controllers.put("/v1/books", new ListBooksV1());
    }

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        request.setCharacterEncoding("UTF-8");

        ServletController controller = controllers.get(request.getRequestURI());
        if (controller == null) {
            response.sendError(HttpServletResponse.SC_NOT_FOUND);
            return;
        }
        controller.handle(request, response);
    }
}

    한 줄씩 보자. 필드 controllers가 앞에서 말한 "URL → 컨트롤러" 표다. 생성자가 컨트롤러 객체를 하나씩 만들어 표에 넣는다. 분산 환경이 아닌 기본 설정에서 컨테이너는 서블릿 선언 하나에 인스턴스를 하나만 쓰므로(명세 §2.2) FrontV1의 생성자는 한 번 실행되고, 따라서 컨트롤러 객체도 종류마다 하나씩만 만들어진다. service는 HttpServlet이 HTTP 메서드를 보고 doGet, doPost 등으로 나눠 부르기 전의 메서드다. 프런트 컨트롤러는 메서드 종류와 무관하게 모든 요청을 한곳에서 받아야 하므로 이것을 직접 재정의했다.

    service의 첫 줄이 공통 처리다. 요청 본문의 문자 인코딩을 지정하는 일은 본문에서 파라미터를 읽기 전에 해야 효과가 있다고 명세가 정해 두었는데(§3.13), 프런트 컨트롤러는 어떤 컨트롤러보다 먼저 실행되므로 이 조건을 구조적으로 만족한다. 이 실험 환경에서 이 줄을 빼고 한글 제목을 폼으로 보내면 글자가 깨졌고, 파라미터를 한 번 읽은 뒤에 호출해도 마찬가지로 깨졌다. 다음 줄은 표에서 컨트롤러를 찾는다. 없으면 404로 끝내고, 있으면 호출한다. 프런트 컨트롤러가 하는 일은 이것이 전부다.

    forward를 한 층 아래에서 본다

    forward는 서버 안에서 한 서블릿이 다른 리소스에 요청 처리를 넘기는 호출이다. 클라이언트는 이 일이 있었는지 모른다. 보낸 요청은 하나고 받은 응답도 하나다. v1의 목록 요청에서, JSP 자리의 서블릿이 실행되는 순간의 호출 스택을 찍으면 forward의 정체가 보인다. 아래가 먼저 호출된 쪽이고, 톰캣 내부 프레임은 몇 개만 남겼다.

    forward는 메서드 호출이다. 컨트롤러의 프레임 위에 컨테이너의 디스패처 프레임이 쌓이고 그 위에서 뷰가 실행된다. 네트워크도 새 스레드도 끼어들지 않는다. 뷰가 일을 마치면 스택이 거꾸로 풀리면서 forward가 반환하고, 컨트롤러가 반환하고, 프런트 컨트롤러가 반환한다. 이 구조에서 forward의 성질 대부분이 나온다.

    • 같은 스레드, 같은 요청. 뷰는 컨트롤러와 같은 스레드에서 실행되고, 컨트롤러가 setAttribute로 넣은 값을 같은 요청에서 꺼낸다. 요청 속성이 컨트롤러와 뷰 사이의 전달 통로가 될 수 있는 이유다.
    • 경로 값은 대상의 것으로 바뀐다. forward된 쪽에서 getRequestURI()를 부르면 /WEB-INF/views/book-list.jsp가 나오고 getDispatcherType()은 FORWARD다. 원래 요청 경로 /v1/books는 jakarta.servlet.forward.request_uri라는 요청 속성에 보존된다(명세 §9.4.2).
    • forward 전에 쓴 내용은 버려진다. 응답 버퍼에 아직 클라이언트로 나가지 않은 내용이 있으면 대상의 service가 호출되기 전에 지워진다(§9.4).
    • 이미 나간 응답은 되돌릴 수 없다. 응답이 커밋(commit)된 뒤, 곧 상태 줄과 헤더가 이미 클라이언트로 나간 뒤에 forward를 부르면 IllegalStateException이 난다.
    • forward가 반환하면 응답은 끝난 것이다. 명세는 forward가 예외 없이 반환하기 전에 응답 내용이 전송·커밋되고 닫혀야 한다고 정한다. 그 뒤에 쓴 내용은 클라이언트에 가지 않는다.

    뒤의 세 가지를 실제로 확인한 결과가 다음 표다. 세 경우 모두 서블릿 하나가 정해진 순서로 쓰기와 forward를 시도한다.

    서블릿이 한 일관찰한 결과
    버퍼에 문자열을 쓰고(flush 없이) forwardforward 직전 isCommitted()는 false. 응답 본문에는 뷰의 출력만 있고 먼저 쓴 문자열은 없다.
    forward한 뒤 문자열을 더 쓴다forward 직후 isCommitted()는 true. 쓰기에서 예외는 나지 않지만 응답 본문에 나타나지 않는다.
    문자열을 쓰고 flushBuffer()한 뒤 forwardIllegalStateException: Cannot forward after response has been committed. 클라이언트는 먼저 쓴 문자열만 받는다.

    마지막으로 뷰 파일을 WEB-INF 아래에 두는 이유다. 명세 §10.5는 WEB-INF 디렉터리 안의 파일을 컨테이너가 클라이언트에게 직접 제공해서는 안 되고 그런 요청에는 404로 답해야 한다고 정한다. 한편 같은 내용을 RequestDispatcher 호출로는 내보일 수 있다고 적는다. 실험에서도 /WEB-INF/views/book-list.jsp를 브라우저처럼 직접 요청하면 404가 왔고, 프런트 컨트롤러를 거쳐 forward하면 같은 경로가 정상 처리됐다. WEB-INF 밖에 둔 /x.jsp는 직접 요청해도 처리됐다. 뷰를 WEB-INF 아래에 두면 "컨트롤러를 거치지 않고는 뷰에 닿을 수 없다"는 것을 컨테이너가 보장해 준다. 모델 없이 뷰만 실행되는 경로가 사라지는 것이다.

    이 성질들은 프레임워크 설계에 조건을 건다. 뷰 렌더링은 한 요청 처리에서 가장 마지막 일이어야 하고, 렌더링 전에 응답에 무언가를 써서 내보내면 안 된다. 그리고 v1의 호출 스택이 보여 주듯, 컨트롤러가 forward를 직접 부르는 한 뷰가 다 그려질 때까지 컨트롤러는 반환하지 못한다.

    v2 — View 분리

    v1의 컨트롤러마다 마지막 줄에 있던 getRequestDispatcher(경로).forward(request, response)를 없애는 것이 두 번째 단계다. 방법은 "뷰로 넘기는 행동"을 객체로 만드는 것이다. 컨트롤러는 그 행동을 직접 하지 않고, 어떤 뷰를 그릴지를 나타내는 객체를 반환한다. 실제로 그리는 일은 프런트 컨트롤러가 한다.

    class ForwardView {
    private final String path;

    ForwardView(String path) { this.path = path; }

    void render(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        request.getRequestDispatcher(path).forward(request, response);
    }
}

interface ViewReturningController {
    ForwardView handle(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException;
}

class SaveBookV2 implements ViewReturningController {
    private final BookRepository repository = BookRepository.getInstance();

    @Override
    public ForwardView handle(HttpServletRequest request, HttpServletResponse response) {
        Book book = repository.save(request.getParameter("title"), request.getParameter("author"));
        request.setAttribute("book", book);
        return new ForwardView("/WEB-INF/views/book-saved.jsp");
    }
}

ForwardView view = controller.handle(request, response);
view.render(request, response);

    v1에서는 컨트롤러의 프레임이 뷰 아래에 깔려 있었다. v2에서는 컨트롤러가 이미 반환했고, 그 자리에 ForwardView.render가 있다. 컨트롤러가 반환하는 시점과 뷰가 그려지기 시작하는 시점 사이에 프런트 컨트롤러의 코드가 실행되는 틈이 생긴 것이다. v2는 이 틈에서 view.render를 부를 뿐이지만, 이 틈이 있어야 다음 단계들이 가능하다. 컨트롤러의 결과를 가공하거나, 뷰 이름을 실제 경로로 바꾸거나, 모델을 요청 속성으로 옮기는 일은 모두 여기에서 한다. 스프링의 DispatcherServlet에서도 핸들러 호출과 뷰 렌더링 사이에 인터셉터의 후처리가 실행되는 자리가 같은 곳에 있다.

    설계의 관점에서 정리하면, v2는 "효과를 직접 일으키는 코드"를 "무엇을 할지 기술한 값을 반환하는 코드"로 바꿨다. 값을 반환하는 코드는 호출한 쪽이 결과를 보고 다음 행동을 정할 수 있다. v2에 남은 문제는 셋이다. 컨트롤러가 여전히 서블릿의 요청·응답 객체를 받는다. 뷰 경로의 앞뒤(/WEB-INF/views/, .jsp)가 컨트롤러마다 반복된다. 모델을 요청 객체의 속성으로 직접 넣는다.

    v3 — Model 추가: 서블릿에서 독립한 컨트롤러

    세 번째 단계는 v2에 남은 세 문제를 한꺼번에 푼다. 컨트롤러가 서블릿 API를 전혀 모르게 만드는 것이 목표다. 컨트롤러가 요청 객체에서 쓰던 것은 둘뿐이었다. 파라미터를 읽는 것과 모델을 속성으로 넣는 것이다. 이 둘을 서블릿과 무관한 자료구조로 바꾸면 요청 객체를 넘길 이유가 없어진다.

    • 입력. HttpServletRequest 대신 파라미터 이름과 값을 담은 Map을 받는다. 요청 객체에서 맵을 만드는 일은 프런트 컨트롤러가 한다.
    • 출력. 뷰에 넘길 데이터(모델)와 뷰를 가리키는 이름을 하나의 객체에 담아 반환한다. 모델을 요청 속성으로 옮기는 일은 프런트 컨트롤러 쪽이 한다.
    • 뷰 이름. 컨트롤러는 /WEB-INF/views/book-saved.jsp라는 물리적 경로 대신 book-saved라는 논리 뷰 이름(logical view name)만 말한다. 이름을 실제 경로로 바꾸는 규칙은 프런트 컨트롤러 한 곳에 둔다.
    final class Rendering {
    private final String viewName;
    private final Map model = new HashMap<>();

    Rendering(String viewName) { this.viewName = viewName; }

    String viewName() { return viewName; }
    Map model() { return model; }
}

interface ParamController {
    Rendering handle(Map params);
}

class SaveBookV3 implements ParamController {
    private final BookRepository repository = BookRepository.getInstance();

    @Override
    public Rendering handle(Map params) {
        Book book = repository.save(params.get("title"), params.get("author"));
        Rendering rendering = new Rendering("book-saved");
        rendering.model().put("book", book);
        return rendering;
    }
}

class ListBooksV3 implements ParamController {

        return rendering;

}

    컨트롤러 파일에서 jakarta.servlet으로 시작하는 import가 전부 사라졌다. 예외 선언도 없다. ServletException과 IOException은 forward 때문에 붙어 있던 것이고, forward는 이제 컨트롤러의 일이 아니다. 줄어든 만큼 프런트 컨트롤러가 늘어난다.

    // FrontV3 — 생성자와 컨트롤러 조회까지는 v1과 같다
        Map params = toParamMap(request);
        Rendering rendering = controller.handle(params);

        ForwardView view = resolveView(rendering.viewName());
        view.render(rendering.model(), request, response);
    }

    private Map toParamMap(HttpServletRequest request) {
        Map params = new HashMap<>();
        request.getParameterNames().asIterator()
                .forEachRemaining(name -> params.put(name, request.getParameter(name)));
        return params;
    }

    private ForwardView resolveView(String viewName) {
        return new ForwardView("/WEB-INF/views/" + viewName + ".jsp");
    }
}

// ForwardView 에 추가한 메서드
    void render(Map model, HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        model.forEach(request::setAttribute);
        render(request, response);
    }

    세 가지 변화가 각각 무엇을 얻는지 따져 보자. 먼저 논리 뷰 이름. 뷰 파일을 다른 디렉터리로 옮기거나 JSP가 아닌 템플릿 기술로 바꾸더라도 고칠 곳은 resolveView 한 군데다. 컨트롤러는 "저장 완료 화면을 보여 달라"고만 말하고, 그 화면이 어느 파일로 구현됐는지는 모른다. 스프링이 JSP용으로 제공하는 InternalResourceViewResolver가 하는 일도 이것과 같아서, 설정된 접두어와 접미어 사이에 뷰 이름을 끼워 URL을 만든다.

    다음은 모델. 03회에서 본 대로 JSP는 요청 속성에서 값을 꺼내 화면을 만든다. 그렇다고 컨트롤러가 요청 속성을 직접 알아야 하는 것은 아니다. 컨트롤러는 보통의 맵에 값을 담고, 그 맵을 요청 속성으로 옮기는 일은 JSP로 forward하는 뷰 객체가 맡는다. 요청 속성은 "JSP라는 뷰 기술이 데이터를 받는 방식"이므로 그 지식이 뷰 객체 안에 있는 편이 맞다. 다른 뷰 기술이라면 같은 모델 맵을 다른 방식으로 넘기면 된다.

    마지막으로 서블릿 독립. 컨트롤러가 받는 것도 반환하는 것도 보통의 자바 객체이므로, 서버 없이 main 메서드에서 바로 호출해 볼 수 있다.

    톰캣도 요청 객체도 없이 컨트롤러의 입력과 출력을 전부 확인했다. v1의 컨트롤러로는 할 수 없던 일이다. v1에서는 요청·응답 객체를 흉내 낸 가짜를 만들어 넘기고, forward가 어느 경로로 호출됐는지를 가짜 쪽에서 기록해 꺼내 봐야 했다.

    이 단순화에는 한계도 있다. Map은 이름 하나에 값 하나만 담는다. 체크박스처럼 같은 이름의 파라미터가 여러 번 오면 getParameter는 첫 값만 돌려주므로 나머지는 사라진다. 헤더, 쿠키, 세션, 요청 본문의 JSON도 이 맵에는 없다. "컨트롤러에 무엇을 넘겨줄 것인가"는 생각보다 큰 문제이고, 스프링이 이 문제를 푸는 방식은 06회와 07회에서 다룬다. 여기서는 프런트 컨트롤러가 컨트롤러 호출의 앞뒤를 쥐고 있으므로 컨트롤러가 받을 것과 돌려줄 것을 마음대로 설계할 수 있다는 점만 가져가면 된다.

    프런트 컨트롤러가 가운데에서 컨트롤러와 뷰를 차례로 호출하고, 컨트롤러는 서블릿 객체를 전혀 건드리지 않는다는 점이 보여야 한다. 깔끔한 평면 벡터 스타일의 시퀀스 다이어그램, 흰 배경. 위쪽에 참여자 상자 다섯 개가 왼쪽부터 가로로 놓인다: "클라이언트", "프런트 컨트롤러", "컨트롤러", "뷰 객체", "JSP". 각 상자에서 아래로 점선 생명선이 내려온다. 위에서 아래로 번호가 붙은 화살표: 1번은 클라이언트에서 프런트 컨트롤러로 가는 실선 화살표, 라벨 "HTTP 요청". 2번은 프런트 컨트롤러에서 컨트롤러로 가는 실선 화살표, 라벨 "파라미터 맵". 3번은 컨트롤러에서 프런트 컨트롤러로 돌아오는 점선 화살표, 라벨 "뷰 이름 + 모델". 4번은 프런트 컨트롤러 생명선 위에서 자기 자신으로 돌아오는 짧은 고리 화살표, 라벨 "뷰 이름 → 경로". 5번은 프런트 컨트롤러에서 뷰 객체로 가는 실선 화살표, 라벨 "모델 전달, 렌더링". 6번은 뷰 객체에서 JSP로 가는 실선 화살표, 라벨 "요청 속성 + forward". 7번은 JSP에서 클라이언트까지 길게 돌아가는 점선 화살표, 라벨 "HTML 응답". 컨트롤러 상자와 그 생명선 둘레에만 연한 초록 배경을 깔고 "서블릿 API를 모른다"라는 주석을 단다. v3에서 서블릿의 요청·응답 객체를 만지는 것은 프런트 컨트롤러와 뷰 객체뿐이다. 컨트롤러는 맵을 받고 이름과 모델을 돌려준다.

    v4 — 단순하고 실용적인 컨트롤러

    v3의 구조는 깔끔하지만 컨트롤러를 쓰는 사람에게는 번거로운 데가 남았다. 컨트롤러마다 Rendering 객체를 만들고, 그 안의 모델을 꺼내 값을 넣고, 객체를 반환한다. 목록 컨트롤러의 세 줄 가운데 로직은 한 줄이고 나머지는 Rendering을 다루는 형식이다. 네 번째 단계는 구조를 그대로 두고 이 형식만 덜어 낸다. 모델 맵을 프런트 컨트롤러가 미리 만들어 인자로 넘기고, 컨트롤러는 거기에 값을 넣은 뒤 뷰 이름을 문자열로 반환한다.

    interface ModelController {
    String handle(Map params, Map model);
}

class SaveBookV4 implements ModelController {
    private final BookRepository repository = BookRepository.getInstance();

    @Override
    public String handle(Map params, Map model) {
        model.put("book", repository.save(params.get("title"), params.get("author")));
        return "book-saved";
    }
}

class ListBooksV4 implements ModelController {

    이 방식이 동작하는 근거는 자바의 인자 전달 규칙이다. 자바는 항상 값을 복사해 넘기고, 참조형 변수의 값은 객체를 가리키는 참조다. service의 지역 변수 model과 handle의 매개변수 model은 서로 다른 변수지만 힙에 있는 같은 HashMap 객체 하나를 가리킨다. 컨트롤러가 그 객체에 put하면 프런트 컨트롤러가 자기 변수로 같은 객체를 들여다볼 때 값이 보인다. 반대로 컨트롤러가 매개변수 자체에 새 맵을 대입하면 컨트롤러 쪽 변수만 다른 객체를 가리키게 되고, 프런트 컨트롤러가 든 원래 맵은 빈 채로 남는다. 반환값이 아니라 인자를 통해 결과를 내보내는 방식은 이런 실수의 여지가 있고 메서드 시그니처만 봐서는 무엇이 출력인지 드러나지 않는다. 그 대가로 얻는 것이 컨트롤러 코드의 간결함이다.

    단계컨트롤러의 시그니처프런트 컨트롤러가 새로 떠맡은 일컨트롤러에 남은 일
    v1void handle(request, response)컨트롤러 조회와 호출, 공통 처리파라미터 읽기, 로직, 속성 저장, forward
    v2ForwardView handle(request, response)뷰 객체의 렌더링 호출파라미터 읽기, 로직, 속성 저장, 전체 경로로 뷰 생성
    v3Rendering handle(Map)파라미터 맵 생성, 뷰 이름 해석, 모델을 요청 속성으로 옮기기로직, Rendering 생성과 모델 채우기
    v4String handle(Map, Map)모델 맵 생성로직, 모델 채우기, 뷰 이름 반환

    표를 위에서 아래로 읽으면 일이 오른쪽 칸에서 왼쪽 칸으로 옮겨 간다. 복잡함이 사라진 것은 아니다. 컨트롤러 수만큼 반복되던 코드가 프런트 컨트롤러에 한 번만 적히는 코드로 옮겨 갔다. 프레임워크를 만든다는 것은 이 이동을 되풀이하는 일이고, 그래서 프레임워크 내부는 길고 그 위에 올리는 코드는 짧다.

    v3과 v4 가운데 어느 쪽이 옳다고 할 수는 없다. v3은 입력과 출력이 시그니처에 분명하고 반환값 하나로 결과가 완결된다. v4는 쓰기 편하다. 한 프로젝트 안에서도 두 방식을, 나아가 아직 생각하지 못한 다른 방식을 함께 쓰고 싶을 수 있다. 그 요구가 v5로 이어진다. 그 전에, 다섯 단계 내내 바닥에 깔려 있던 전제 하나를 짚고 간다.

    하나뿐인 객체와 요청마다 생기는 객체

    컨테이너가 정말 한 객체에 여러 스레드를 동시에 들여보내는지 확인해 보았다. 서블릿의 service 안에서 스레드 둘이 모여야만 통과되는 장벽(CyclicBarrier(2))을 기다리게 하고, 요청 둘을 동시에 보냈다. 두 요청이 같은 순간에 service 안에 있지 않으면 어느 쪽도 끝나지 못하는 실험이다.

    servlet@480b9210 thread=http-nio-auto-1-exec-3
servlet@480b9210 thread=http-nio-auto-1-exec-2

    두 요청 모두 정상 응답을 받았고, 서블릿 객체의 식별 해시는 같고 스레드 이름은 달랐다. 명세도 같은 말을 한다. 분산 환경이 아닌 기본 설정에서 컨테이너는 서블릿 선언 하나에 인스턴스를 하나만 써야 하고(§2.2), 그 서블릿의 service 메서드로 동시 요청을 보낼 수 있다(§2.3.3.1). 프런트 컨트롤러가 그렇다면 그것이 표에 넣어 둔 컨트롤러와 어댑터, 저장소도 모두 같은 조건에 놓인다.

    컨트롤러의 필드에 요청별 값을 두면

    이 조건을 어기는 가장 흔한 방법은 요청에서 읽은 값을 컨트롤러의 인스턴스 필드에 잠깐 넣어 두는 것이다. 메서드 하나 안에서 쓰고 읽으니 문제없어 보이지만 그 필드는 힙에 하나뿐이다. 두 스레드의 실행이 어떻게 엇갈리는지를 래치로 고정해 재현했다.

    class StatefulSave implements ModelController {
    private String title;                       // 요청마다 다른 값을 인스턴스 필드에 뒀다
    Consumer gap = t -> {};             // 실험용: 두 줄 사이에 다른 스레드가 끼어들 틈

    @Override
    public String handle(Map params, Map model) {
        title = params.get("title");            // (1) 필드에 쓴다
        gap.accept(title);
        model.put("saved", title);              // (2) 필드에서 읽는다
        return "book-saved";
    }
}

public class StatefulDemo {
    public static void main(String[] args) throws InterruptedException {
        StatefulSave controller = new StatefulSave();          // 프런트 컨트롤러의 표에 든 단 하나의 인스턴스
        CountDownLatch aWrote = new CountDownLatch(1);
        CountDownLatch bDone = new CountDownLatch(1);
        controller.gap = title -> {
            if (title.equals("A")) {                           // A 요청은 (1)과 (2) 사이에서 B 요청이 끝나기를 기다린다
                aWrote.countDown();
                await(bDone);
            }
        };

        Map modelA = new HashMap<>();
        Map modelB = new HashMap<>();
        Thread a = new Thread(() -> controller.handle(Map.of("title", "A"), modelA), "request-A");
        Thread b = new Thread(() -> {
            await(aWrote);
            controller.handle(Map.of("title", "B"), modelB);
            bDone.countDown();
        }, "request-B");
        a.start(); b.start();
        a.join(); b.join();

        System.out.println("A 요청의 모델 = " + modelA);
        System.out.println("B 요청의 모델 = " + modelB);
    }
    // await(latch)는 latch.await()를 호출하고 InterruptedException을 감싸 던지는 도우미다.
}
    A 요청의 모델 = {saved=B}
B 요청의 모델 = {saved=B}
    순서스레드 request-A스레드 request-B힙의 title 필드
    1(1) title = "A"aWrote를 기다린다"A"
    2gap에서 bDone을 기다린다(1) title = "B""B"
    3기다린다(2) 필드를 읽어 자기 모델에 "B"를 넣고 끝난다"B"
    4(2) 필드를 읽어 자기 모델에 "B"를 넣는다—"B"

    A 요청을 보낸 사용자의 화면에 B 요청의 제목이 나온다. 모델 맵은 요청마다 따로였는데도 그렇다. 섞인 지점은 두 스레드가 함께 쓰는 필드 한 칸이다. 실제 서버에서는 래치가 없으니 이 엇갈림이 요청이 몰리는 순간에만 드물게 일어나고, 그래서 개발 중에는 재현되지 않는다. 고치는 방법은 title을 지역 변수로 바꾸는 것이다. 지역 변수는 스레드마다 따로인 스택 프레임에 놓이므로 엇갈릴 수가 없다. 스프링 핵심 원리 기본편에서 싱글톤 빈을 무상태(stateless)로 설계해야 한다고 한 이유가 이것이고, 프런트 컨트롤러 구조의 컨트롤러는 스프링 없이도 이미 그 조건에 놓여 있다.

    공유되는 표와 저장소는 왜 안전한가

    공유를 아예 피할 수 없는 객체도 있다. "URL → 컨트롤러" 표와 저장소다. 표는 여러 스레드가 동시에 읽는데도 보통의 HashMap이다. HashMap의 문서는 여러 스레드가 동시에 접근하면서 그중 하나라도 맵의 구조를 바꾸면 외부에서 동기화해야 한다고 적는다. 뒤집어 말하면, 아무도 구조를 바꾸지 않는 동안의 동시 읽기는 문제가 되지 않는다. 예제의 표는 생성자에서 채운 뒤 다시는 바뀌지 않는다.

    남는 질문은 "생성자에서 채운 내용이 다른 스레드에 온전히 보이는가"다. 표를 가리키는 필드가 final이라는 점이 여기서 쓰인다. 자바 언어 명세 §17.5는 생성자가 끝난 뒤에야 객체의 참조를 볼 수 있었던 스레드는 그 객체의 final 필드에서 올바르게 초기화된 값을 본다고 보장하고, 그 필드가 가리키는 객체도 적어도 final 필드가 정해진 시점만큼은 최신인 상태로 본다고 덧붙인다. 그래서 생성자 안에서 채우기를 마치고 그 뒤로 건드리지 않는 표는 추가 동기화 없이 안전하다. 이 보장은 생성자가 끝난 뒤의 수정에는 미치지 않는다. 실행 중에 컨트롤러를 등록하거나 빼는 기능이 필요하다면 ConcurrentHashMap 같은 동시성 자료구조나 락으로 바꿔야 한다.

    저장소는 성격이 다르다. 요청이 도서를 저장할 때마다 내용이 바뀌는, 공유되는 가변 상태다. 그래서 처음부터 동시 수정에 안전한 도구로 만들어 두었다.

    final class BookRepository {
    private static final BookRepository INSTANCE = new BookRepository();
    private final Map store = new ConcurrentHashMap<>();
    private final AtomicLong sequence = new AtomicLong();

    static BookRepository getInstance() { return INSTANCE; }

    Book save(String title, String author) {
        Book book = new Book(sequence.incrementAndGet(), title, author);
        store.put(book.id(), book);
        return book;
    }

    List findAll() {
        return store.values().stream().sorted(Comparator.comparingLong(Book::id)).toList();
    }
}

    번호를 long 필드에 두고 ++로 올렸다면 두 요청이 같은 번호를 받을 수 있다. ++는 읽기·더하기·쓰기 세 단계로 실행되고 그 사이에 다른 스레드가 끼어들 수 있기 때문이다. AtomicLong.incrementAndGet()은 이 세 단계를 원자적으로 수행한다. 정리하면 이 구조의 객체는 셋으로 나뉜다. 요청마다 새로 만들어 공유하지 않는 것(파라미터 맵, 모델, 뷰 객체), 공유하지만 만든 뒤로 바뀌지 않는 것(표, 컨트롤러, 어댑터), 공유하면서 바뀌는 것(저장소). 동시성 도구가 필요한 것은 셋째뿐이다.

    두 스레드의 스택 프레임이 같은 컨트롤러 객체를 함께 가리키면서도, 파라미터 맵과 모델 맵은 요청마다 다른 객체를 가리킨다는 점을 색으로 구분해 보여 준다. 깔끔한 평면 벡터 스타일의 메모리 구조도, 흰 배경. 화면 위쪽 3분의 2는 큰 둥근 사각형이고 왼쪽 위에 라벨 "힙". 힙 안 왼쪽에 파란 상자 "프런트 컨트롤러"가 있고, 거기서 화살표가 표 모양의 파란 상자 "URL → 컨트롤러 표"로 간다. 표에서 화살표 두 개가 파란 상자 "저장 컨트롤러", "목록 컨트롤러"로 가고, 두 컨트롤러에서 화살표가 파란 원통 "저장소"로 모인다. 파란 상자들을 점선으로 묶고 라벨 "하나뿐인 객체". 힙 안 오른쪽에는 주황 상자 두 개 "파라미터 맵", "모델 맵"이 한 묶음으로 있고 라벨 "요청 A의 객체", 그 아래 초록 상자 두 개가 같은 이름으로 한 묶음이며 라벨 "요청 B의 객체". 화면 아래쪽 3분의 1에는 세로로 쌓인 칸으로 이루어진 스택 그림 두 개가 좌우로 놓이고, 각각 라벨 "스레드 1의 스택", "스레드 2의 스택". 스레드 1의 스택에서 나온 주황 화살표는 주황 맵들을, 스레드 2의 스택에서 나온 초록 화살표는 초록 맵들을 가리킨다. 두 스택 모두에서 나온 회색 화살표는 같은 파란 "저장 컨트롤러" 상자 하나를 가리킨다. 컨트롤러는 모든 요청이 함께 쓰고, 파라미터 맵과 모델은 요청마다 따로 생긴다. 요청별 값은 스택과 요청별 객체에만 둔다.

    v5 — 유연한 컨트롤러 1: 어댑터 패턴

    v4까지의 프런트 컨트롤러에는 공통된 한계가 있다. 표의 타입이 컨트롤러 인터페이스 하나로 고정돼 있다. FrontV4의 필드는 Map이고 service는 controller.handle(params, model)이라는 호출 하나만 안다. v3 방식으로 써 둔 컨트롤러를 이 표에 넣으면 컴파일되지 않는다. 방식을 바꾸려면 모든 컨트롤러를 한꺼번에 고쳐야 하고, 두 방식을 섞어 쓸 수 없다.

    가장 먼저 떠오르는 해법은 표의 값 타입을 Object로 풀고 service 안에서 타입을 검사하는 것이다. ParamController면 이렇게 부르고 ModelController면 저렇게 부르는 if를 늘어놓는다. 동작은 하지만, 새 방식이 생길 때마다 프런트 컨트롤러의 service를 열어 분기를 추가해야 한다. 스프링 핵심 원리 기본편에서 본 개방-폐쇄 원칙(OCP)을 정면으로 어기는 구조다. 프런트 컨트롤러는 모든 요청이 지나가는 코드라서 자주 고칠수록 위험도 크다.

    어댑터 패턴(adapter pattern)은 이런 상황을 위한 것이다. 쓰는 쪽이 기대하는 인터페이스와 실제 객체의 인터페이스가 맞지 않을 때, 둘 사이에 변환을 맡는 객체를 끼운다. 쓰는 쪽은 변환 객체하고만 이야기하고, 변환 객체가 실제 객체의 방식에 맞춰 대신 호출한 뒤 결과를 쓰는 쪽이 기대하는 형태로 바꿔 돌려준다.

    일상에서 가져온 비유여행용 전원 어댑터

    한국에서 쓰던 충전기를 영국 콘센트에 꽂으려면 사이에 어댑터를 끼운다. 충전기도 벽의 콘센트도 고치지 않는다. 어댑터의 한쪽은 콘센트 모양에, 다른 쪽은 충전기 플러그 모양에 맞춰져 있을 뿐이다. 나라가 하나 늘면 어댑터를 하나 더 사면 된다. 프런트 컨트롤러가 콘센트, 컨트롤러가 충전기, 핸들러 어댑터가 여행용 어댑터다. 비유가 깨지는 지점은 선택이다. 여행자는 어느 어댑터를 쓸지 눈으로 보고 고르지만 프런트 컨트롤러는 그럴 수 없다. 그래서 어댑터마다 "이 객체를 내가 처리할 수 있는가"를 답하는 메서드를 두고, 프런트 컨트롤러가 차례로 물어본다.

    프런트 컨트롤러가 기대하는 것은 하나로 정한다. "요청과 응답, 그리고 처리할 객체를 주면, 뷰 이름과 모델이 담긴 Rendering을 돌려 달라." 이것이 어댑터의 인터페이스다.

    interface HandlerAdapter {
    boolean supports(Object handler);

    Rendering handle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws ServletException, IOException;
}

class ParamControllerAdapter implements HandlerAdapter {
    @Override
    public boolean supports(Object handler) {
        return handler instanceof ParamController;
    }

    @Override
    public Rendering handle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        ParamController controller = (ParamController) handler;
        return controller.handle(Requests.toParamMap(request));
    }
}

class ModelControllerAdapter implements HandlerAdapter {
    @Override
    public boolean supports(Object handler) {
        return handler instanceof ModelController;
    }

    @Override
    public Rendering handle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        ModelController controller = (ModelController) handler;
        Map model = new HashMap<>();
        String viewName = controller.handle(Requests.toParamMap(request), model);

        Rendering rendering = new Rendering(viewName);
        rendering.model().putAll(model);
        return rendering;
    }
}

class ServletControllerAdapter implements HandlerAdapter {
    @Override
    public boolean supports(Object handler) {
        return handler instanceof ServletController;
    }

    @Override
    public Rendering handle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws ServletException, IOException {
        ((ServletController) handler).handle(request, response);
        return null;   // 응답을 직접 끝냈다. 그릴 뷰가 없다.
    }
}

    Requests.toParamMap은 v3의 toParamMap을 어댑터들이 함께 쓰도록 유틸리티 클래스로 옮긴 것이다. 어댑터 셋을 나란히 놓으면 각자가 하는 일이 "모양 맞추기"뿐임이 보인다. ParamControllerAdapter는 프런트 컨트롤러가 준 요청에서 파라미터 맵을 뽑아 컨트롤러에 넘기고, 컨트롤러가 돌려준 Rendering을 그대로 전달한다. ModelControllerAdapter는 할 일이 더 많다. v4의 프런트 컨트롤러가 하던 대로 모델 맵을 만들어 넘기고, 컨트롤러가 돌려준 문자열과 채워진 모델을 Rendering 하나로 조립한다. v4 컨트롤러가 String을 반환한다는 사실은 이 어댑터 안에서 흡수되고, 프런트 컨트롤러에는 언제나 Rendering이 온다. ServletControllerAdapter는 v1 방식, 곧 응답을 직접 쓰는 컨트롤러를 위한 것이다. 그런 컨트롤러는 그릴 뷰가 없으므로 "뷰 없음"을 뜻하는 null을 돌려준다.

    이름도 바뀌었다. 매개변수가 controller가 아니라 handler이고 타입은 Object다. 어댑터만 있으면 어떤 모양의 객체든 요청을 처리하는 자리에 올 수 있으니, 그 객체를 꼭 "컨트롤러"라고 부를 이유가 없어서 더 넓은 말인 핸들러(handler)를 쓴다. 타입이 Object인 까닭은 세 인터페이스 사이에 공통 상위 타입이 없기 때문이다. 공통 인터페이스를 억지로 만들면 다시 한 가지 시그니처에 묶인다.

    v5 — 유연한 컨트롤러 2: 프런트 컨트롤러를 완성하고 실행을 추적한다

    어댑터가 준비됐으니 프런트 컨트롤러를 고친다. 표의 값 타입이 Object가 되고, 어댑터 목록이 필드로 추가되고, 컨트롤러를 직접 부르던 줄이 "어댑터를 찾아 어댑터에게 시킨다"로 바뀐다.

    @WebServlet(urlPatterns = "/v5/*")
public class FrontV5 extends HttpServlet {
    private final Map handlers = new HashMap<>();
    private final List adapters = List.of(
            new ParamControllerAdapter(), new ModelControllerAdapter(), new ServletControllerAdapter());

    public FrontV5() {
        handlers.put("/v5/old/books/save", new SaveBookV3());   // Rendering을 반환하는 방식
        handlers.put("/v5/old/books", new ListBooksV3());
        handlers.put("/v5/books/save", new SaveBookV4());       // 뷰 이름을 반환하는 방식
        handlers.put("/v5/books", new ListBooksV4());
        handlers.put("/v5/ping", new Ping());                   // 응답을 직접 쓰는 방식
        handlers.put("/v5/broken", "컨트롤러가 아닌 객체");
    }

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        request.setCharacterEncoding("UTF-8");

        Object handler = handlers.get(request.getRequestURI());          // 1. 핸들러 조회
        if (handler == null) {
            response.sendError(HttpServletResponse.SC_NOT_FOUND);
            return;
        }
        HandlerAdapter adapter = findAdapter(handler);                   // 2. 어댑터 조회
        Rendering rendering = adapter.handle(request, response, handler); // 3. 어댑터가 핸들러 호출
        if (rendering == null) {
            return;                                                      // 핸들러가 응답을 직접 끝냈다
        }
        ForwardView view = resolveView(rendering.viewName());            // 4. 뷰 이름 해석
        view.render(rendering.model(), request, response);              // 5. 렌더링
    }

    private HandlerAdapter findAdapter(Object handler) throws ServletException {
        for (HandlerAdapter adapter : adapters) {
            if (adapter.supports(handler)) {
                return adapter;
            }
        }
        throw new ServletException("처리할 어댑터가 없다: " + handler.getClass().getName());
    }

    private ForwardView resolveView(String viewName) {
        return new ForwardView("/WEB-INF/views/" + viewName + ".jsp");
    }
}

    어댑터 목록의 순서도 동작의 일부다. findAdapter는 처음으로 supports가 참인 어댑터를 쓴다. 한 클래스가 ParamController와 ModelController를 둘 다 구현하면 목록에서 앞에 있는 ParamControllerAdapter가 선택되고, ModelController로서의 메서드는 호출되지 않는다. 이런 종류의 오류를 요청이 올 때까지 미루지 않으려면, 표를 만드는 시점에 모든 핸들러에 대해 어댑터가 있는지 한 번 훑어 확인하면 된다. 검사를 컴파일 시점에서 잃었으면 시작 시점에서라도 되찾는다는 생각이고, 프레임워크들이 애플리케이션을 띄울 때 설정을 검증하는 까닭도 같다.

    프런트 컨트롤러는 어댑터만 호출하고, 모양이 서로 다른 핸들러 셋은 각자의 어댑터 뒤에 있다는 점과 번호가 붙은 처리 순서를 보여 준다. 깔끔한 평면 벡터 스타일의 순서도, 흰 배경. 왼쪽에 큰 세로 상자 "프런트 컨트롤러". 그 위쪽에 표 아이콘이 붙은 상자 "핸들러 표"가 있고 프런트 컨트롤러에서 그 표로 가는 화살표에 "1 핸들러 조회"라는 라벨. 가운데에 세로로 나란히 놓인 상자 세 개가 있고 점선으로 묶여 라벨 "어댑터 목록". 프런트 컨트롤러에서 어댑터 목록으로 가는 화살표에 "2 처리할 수 있나?"라는 라벨, 세 상자 중 가운데 하나만 진한 색으로 강조한다. 프런트 컨트롤러에서 강조된 어댑터로 가는 굵은 화살표에 "3 호출"이라는 라벨. 오른쪽에는 모양이 서로 다른 도형 세 개(원, 육각형, 사다리꼴)가 세로로 놓이고 묶음 라벨 "핸들러 (방식이 제각각)". 각 어댑터에서 같은 줄의 핸들러 도형으로 가는 화살표가 있고, 강조된 어댑터의 화살표만 굵다. 강조된 어댑터에서 프런트 컨트롤러로 돌아오는 점선 화살표에 "뷰 이름 + 모델"이라는 라벨. 프런트 컨트롤러 아래쪽에서 오른쪽 아래의 상자 "뷰"로 가는 화살표에 "4 이름 해석, 5 렌더링"이라는 라벨. 프런트 컨트롤러는 핸들러의 모양을 모른다. 모양의 차이는 어댑터가 흡수하고, 프런트 컨트롤러에는 늘 같은 형태의 결과가 돌아온다.

    정리: 다섯 단계와 DispatcherServlet

    다섯 번 고치는 동안 한 일을 한 문장씩으로 줄이면 이렇다. v1은 입구를 하나로 모았다. v2는 forward 호출을 뷰 객체로 옮겨 컨트롤러가 뷰를 "반환"하게 했다. v3은 컨트롤러에서 서블릿 API를 걷어 내고 모델과 논리 뷰 이름을 도입했다. v4는 구조를 그대로 두고 컨트롤러를 쓰기 편하게 다듬었다. v5는 어댑터를 끼워 한 프런트 컨트롤러가 여러 방식의 핸들러를 받아들이게 했다. 단계마다 해결한 문제는 달랐지만 방향은 하나였다. 반복되는 일과 바뀌기 쉬운 결정을 컨트롤러에서 꺼내 한 번만 적히는 곳으로 옮기는 것이다.

    흔한 오해와 함정

    "모든 요청이 프런트 컨트롤러 하나를 지나가니 병목이 된다." 객체가 하나라는 것과 한 번에 하나만 실행된다는 것은 다른 이야기다. 앞에서 확인한 대로 컨테이너는 같은 서블릿 객체의 service를 여러 스레드로 동시에 실행한다. 프런트 컨트롤러의 필드는 만든 뒤로 바뀌지 않으므로 락이 필요 없고, 따라서 스레드끼리 기다릴 일도 없다. 동시에 처리할 수 있는 요청 수를 정하는 것은 01회에서 본 스레드 풀의 크기이지 프런트 컨트롤러의 개수가 아니다.

    "프런트 컨트롤러는 필터로도 만들 수 있으니 같은 것이다." 둘 다 요청의 앞단에 있지만 맡은 일이 다르다. 필터는 서블릿 앞뒤에 공통 동작을 끼우는 장치이고, 요청을 누구에게 넘길지는 여전히 컨테이너의 매핑이 정한다. 프런트 컨트롤러는 자신이 핸들러를 고르고, 핸들러의 반환값을 받아 뷰를 그린다. 호출의 결과를 받아 다음 일을 정한다는 점이 구조의 핵심이다.

    "forward는 리다이렉트의 서버 버전이다." 리다이렉트는 응답을 한 번 끝내고 클라이언트가 새 요청을 보내게 하는 것이라 요청이 둘이고, 첫 요청의 요청 속성은 둘째 요청에 없다. forward는 호출 스택에서 본 대로 한 요청 안의 메서드 호출이다. 그래서 모델을 요청 속성으로 넘길 수 있고, 그래서 브라우저의 주소는 바뀌지 않는다. 이 회차의 저장 요청은 POST의 응답으로 결과 화면을 바로 그리는데, 그 화면에서 새로 고침을 하면 같은 POST가 다시 전송된다. 이 문제와 해결책인 PRG 패턴은 08회에서 다룬다.

    "논리 뷰 이름은 파일 이름에서 확장자를 뗀 것이다." 이 회차의 resolveView가 그렇게 구현됐을 뿐이다. 논리 이름은 컨트롤러와 뷰 해석 규칙 사이의 약속이고, 그것이 파일 경로가 될지 다른 무엇이 될지는 해석하는 쪽이 정한다. 컨트롤러가 이름에 경로나 확장자를 섞어 쓰기 시작하면 v3에서 얻은 분리를 스스로 되돌리는 것이다.

    "어댑터를 거치면 호출이 한 단계 늘어 느려진다." 요청 하나에 늘어나는 것은 짧은 목록의 순회와 instanceof 검사 몇 번, 인터페이스 호출 한 번이다. 같은 요청이 소켓에서 바이트를 읽고, HTTP를 파싱하고, 데이터베이스에 다녀오는 데 쓰는 일과 견줄 크기가 아니다. 어댑터의 실제 비용은 속도가 아니라 앞에서 본 타입 검사의 상실이고, 그 비용을 치르고 얻는 것이 프런트 컨트롤러를 고치지 않고 핸들러의 모양을 늘릴 수 있는 자유다.

    이 장의 핵심

    프런트 컨트롤러는 요청 처리에서 "어떤 요청에나 똑같은 부분"을 한 곳에 모은 것이다. 컨테이너가 넘긴 요청을 받아 핸들러를 찾고, 어댑터를 통해 호출하고, 돌아온 뷰 이름을 해석해 모델과 함께 렌더링한다. 이 다섯 걸음이 고정되면 핸들러는 서블릿을 몰라도 되고, 뷰 기술과 핸들러의 모양은 프런트 컨트롤러를 건드리지 않고 바꿀 수 있다. 프런트 컨트롤러와 그것이 든 객체들은 하나씩만 만들어져 모든 요청 스레드가 함께 쓰므로, 요청마다 달라지는 값은 지역 변수와 요청마다 새로 만드는 객체에만 둔다.
    프런트 컨트롤러 패턴
    모든 요청을 서블릿 하나가 먼저 받아 공통 처리를 하고, 요청에 맞는 핸들러를 찾아 호출한 뒤 응답을 마무리하는 구조다. 나머지 컨트롤러는 서블릿일 필요가 없어진다.
    서블릿 매핑의 적용 순서
    정확 매핑, 가장 긴 경로 매핑, 확장자 매핑, 기본 서블릿 순으로 시도하고 먼저 성공한 것을 쓴다. /*는 확장자 매핑보다 앞서므로 JSP로의 forward까지 가로채고, /는 맨 마지막이라 그렇지 않다.
    forward
    같은 스레드에서 같은 요청 객체로 다른 리소스를 호출하는 서버 내부 호출이다. 커밋 전에만 가능하고, 미리 쓴 버퍼 내용은 지워지며, 반환하면 응답은 닫힌 상태다.
    뷰 객체의 반환(v2)
    컨트롤러가 forward를 직접 하지 않고 뷰 객체를 돌려주면, 컨트롤러의 반환과 렌더링 사이에 프런트 컨트롤러가 개입할 자리가 생긴다.
    모델과 논리 뷰 이름(v3)
    컨트롤러는 파라미터 맵을 받고 모델과 논리 이름을 돌려준다. 이름을 실제 경로로 바꾸는 일과 모델을 요청 속성으로 옮기는 일은 프런트 컨트롤러 쪽이 맡으므로 컨트롤러는 서블릿 API를 모른다.
    모델을 인자로 받는 컨트롤러(v4)
    프런트 컨트롤러가 만든 모델 맵을 인자로 받아 채우고 뷰 이름만 반환한다. 같은 맵 객체를 두 변수가 가리키기 때문에 동작하며, 반복 코드가 프런트 컨트롤러로 한 번 더 옮겨 간다.
    하나뿐인 객체와 요청별 객체
    프런트 컨트롤러, 핸들러 표, 핸들러, 어댑터는 하나씩만 있고 모든 요청 스레드가 함께 쓴다. 요청마다 다른 값은 지역 변수와 요청마다 새로 만든 객체에만 두어야 섞이지 않는다.
    핸들러 어댑터(v5)
    프런트 컨트롤러가 기대하는 호출 방식과 핸들러의 실제 시그니처 사이를 변환하는 객체다. supports로 처리 가능 여부를 답하고 handle로 대신 호출한다. 컴파일 시점의 타입 검사를 내주고 확장의 자유를 얻는다.
    DispatcherServlet과의 대응
    핸들러 조회, 어댑터 조회, 어댑터를 통한 호출, 뷰 이름 해석, 렌더링이라는 다섯 걸음은 스프링의 HandlerMapping, HandlerAdapter, ModelAndView, ViewResolver, View가 맡은 일과 같다.

    실무에서 프런트 컨트롤러를 직접 만들 일은 거의 없다. 그래도 이 구조를 손으로 만들어 본 사람은 스프링 MVC의 오류 메시지를 다르게 읽는다. 핸들러를 찾지 못한 요청은 404로 끝나므로, 404를 만나면 먼저 첫 걸음인 핸들러 조회를 의심하고 매핑 선언과 요청 경로(컨텍스트 경로, 서블릿 경로 포함)를 맞춰 본다. "No adapter for handler"는 둘째 걸음에서, 핸들러는 찾았는데 그 모양을 호출해 줄 어댑터가 없다는 뜻이다. 뷰 이름을 해석하지 못했다는 오류는 넷째 걸음이다. InternalResourceView가 던지는 "Circular view path" 오류는 forward할 경로가 지금 처리 중인 요청 경로와 같아 자기 자신으로 되돌아오게 생겼다는 뜻으로, 이 회차에서 /* 매핑으로 본 재진입과 같은 종류의 문제를 미리 막는 검사다. 증상이 다섯 걸음 가운데 어디에서 났는지를 먼저 가르면 볼 범위가 좁아진다.

    컨트롤러를 서블릿 API에서 얼마나 떼어 놓을지는 상황에 따라 다르게 판단한다. v3과 v4처럼 떼어 놓으면 테스트가 쉽고 뷰 기술을 바꾸기 쉽다. 그러나 파일을 스트림으로 내려보내거나, 응답 헤더와 상태 코드를 세밀하게 다루거나, 응답을 조금씩 흘려보내야 하는 핸들러는 응답 객체를 직접 쥐는 편이 자연스럽다. v5에서 응답을 직접 쓰는 방식을 어댑터 하나로 함께 받아 준 것처럼, 좋은 프레임워크는 추상화된 방식을 기본으로 두되 낮은 수준으로 내려갈 길을 막지 않는다. 다만 그 길을 쓴 핸들러는 뷰 렌더링과 섞을 수 없다. 응답을 이미 내보낸 뒤에는 forward가 불가능하기 때문이다.

    코드 리뷰에서 가장 값진 습관은 컨트롤러와 서비스의 인스턴스 필드를 보는 것이다. 필드가 final이고 생성 시점에 정해진 협력 객체나 설정값이라면 문제가 없다. 요청을 처리하는 도중에 대입되는 필드가 있다면 그 값이 요청별 값인지 따진다. 이런 버그는 트래픽이 낮은 개발 환경에서는 나타나지 않고, 운영 환경에서 "가끔 다른 사람의 데이터가 보인다"는 형태로 드러나며, 발생한 뒤에는 재현이 어렵다. 그래서 테스트가 아니라 구조를 읽는 눈으로 막아야 한다.

    매핑을 정할 때는 애플리케이션이 어떤 컨텍스트 경로와 서블릿 경로 아래에 배포되는지를 함께 본다. 리버스 프록시 뒤에서 경로 접두어가 붙거나 떨어지는 구성, 여러 애플리케이션을 한 서버에 올리는 구성에서는 getRequestURI() 전체를 기준으로 한 비교가 어긋나기 쉽다. 직접 경로를 비교하는 코드(필터, 보안 설정의 경로 규칙)를 쓸 때 어느 경로 값을 기준으로 삼는지, 인코딩된 문자와 경로 파라미터는 어떻게 다뤄지는지 확인하는 것이 안전하다.
  • 한 애플리케이션(컨텍스트 경로는 빈 문자열)에 서블릿 넷이 각각 /app/*, /app/health, *.json, /에 매핑돼 있다. 요청 /app/health, /app/health/db, /app/books.json, /api/books.json, /images/logo.png 각각에 대해 어느 서블릿이 선택되는지와 그때의 getServletPath(), getPathInfo() 값을 적어라.
  • v4 방식의 컨트롤러를 다음처럼 썼다. handle의 첫 줄에서 model = new HashMap<>();로 매개변수에 새 맵을 대입하고, 다음 줄에서 model.put("book", ...)을 한 뒤 "book-saved"를 반환한다. 이 컨트롤러로 저장 요청을 보내면 뷰는 무엇을 받는가? FrontV4.service의 지역 변수와 컨트롤러의 매개변수가 각각 힙의 어느 객체를 가리키는지 그려서 설명하라.
  • FrontV1을 그대로 둔 채 애플리케이션을 컨텍스트 경로 /library로 배포했다. http://host/library/v1/books를 요청하면 어떤 응답이 오는가? 원인을 경로 요소로 설명하고, 컨텍스트 경로가 무엇이든 동작하도록 표의 키와 조회 코드를 고쳐라.
  • v1 방식의 컨트롤러가 response.getWriter().write("저장했습니다");를 실행한 다음 JSP로 forward한다. (가) 클라이언트가 받는 본문에 "저장했습니다"가 있는가? (나) 두 줄 사이에 response.flushBuffer();를 넣으면 어떻게 되는가? (다) forward가 끝난 뒤 프런트 컨트롤러가 응답에 글자를 더 쓰면 어떻게 되는가? 각각 이유를 적어라.
  • FrontV5에 본문 텍스트를 바로 반환하는 새 방식 interface TextController { String text(Map params); }을 추가하려 한다. 반환된 문자열을 응답 본문에 그대로 쓰고 뷰는 그리지 않는다. 새로 만들 클래스와 고칠 곳을 모두 나열하고, FrontV5.service를 고칠 필요가 있는지 답하라. 또 한 클래스가 ParamController와 ModelController를 둘 다 구현했다면 어느 메서드가 호출되는지도 답하라.

    1번. /app/health는 정확 매핑이 가장 먼저 시도되므로 /app/health 서블릿이 선택되고, 서블릿 경로는 /app/health, 경로 정보는 null이다. /app/health/db는 정확히 같은 매핑이 없으므로 경로 매핑 /app/*가 선택되고 서블릿 경로 /app, 경로 정보 /health/db다. /app/books.json은 확장자가 .json이지만 경로 매핑이 확장자 매핑보다 먼저 시도되므로 /app/*가 선택된다. 서블릿 경로 /app, 경로 정보 /books.json이다. /api/books.json은 정확 매핑도 경로 매핑도 없으므로 *.json이 선택되고, 확장자 매핑에서는 경로 전체가 서블릿 경로가 되어 /api/books.json, 경로 정보는 null이다. /images/logo.png는 앞의 세 규칙에 모두 걸리지 않아 기본 서블릿 /가 받는다. 이때 서블릿 경로는 /images/logo.png, 경로 정보는 null이다.

    2번. 뷰는 book 속성을 받지 못한다. 실제로 이 컨트롤러를 호출한 뒤 프런트 컨트롤러 쪽 맵을 출력하면 빈 맵 {}이다. service의 지역 변수 model은 프런트 컨트롤러가 만든 맵(맵 1)을 가리킨다. handle이 호출될 때 그 참조 값이 매개변수 model에 복사되어 둘이 맵 1을 함께 가리킨다. 컨트롤러의 첫 줄은 매개변수에 새 맵(맵 2)의 참조를 대입하므로, 이제 매개변수만 맵 2를 가리키고 service의 변수는 여전히 맵 1을 가리킨다. put은 맵 2에 일어나고, handle이 반환하면 맵 2를 가리키는 변수는 사라진다. 프런트 컨트롤러는 비어 있는 맵 1을 뷰에 넘긴다. 매개변수에 대입하는 것은 호출한 쪽의 변수를 바꾸지 못한다는 자바의 인자 전달 규칙이 원인이다.

    3번. 404가 온다. 컨텍스트 경로가 /library이므로 getRequestURI()는 /library/v1/books를 돌려주는데, 표의 키는 /v1/books라서 조회 결과가 null이다. 컨테이너의 매핑은 컨텍스트 경로를 뺀 나머지로 이뤄지므로 요청은 FrontV1까지는 도착하지만, 그 안의 표 조회가 실패한다. 경로 요소로 보면 요청 URI는 컨텍스트 경로 /library, 서블릿 경로 /v1, 경로 정보 /books의 합이다. 고치는 방법 하나는 키를 서블릿 매핑 아래의 경로로 바꾸는 것이다. 표에 "/books", "/books/save", "/books/new-form"으로 등록하고 controllers.get(request.getPathInfo())로 조회한다. 경로 정보는 컨텍스트 경로와 서블릿 경로가 빠진 값이고 디코딩과 경로 파라미터 제거도 된 값이라 더 견고하다. /v1처럼 뒤에 아무것도 없는 요청에서는 null이 오는데, HashMap.get(null)은 예외 없이 null을 돌려주므로 404로 이어진다.

    4번. (가) 없다. forward는 커밋되지 않은 버퍼 내용을 대상 호출 전에 지우므로 본문에는 JSP의 출력만 있다. (나) flushBuffer()가 버퍼 내용을 클라이언트로 내보내면서 응답이 커밋된다. 그 뒤의 forward는 IllegalStateException을 던지고, 클라이언트에는 이미 나간 "저장했습니다"까지만 전달된다. 상태 줄과 헤더가 이미 나갔으므로 되돌릴 방법이 없다. (다) 클라이언트에 전달되지 않는다. forward가 반환하기 전에 컨테이너가 응답을 전송·커밋하고 닫기 때문이다. 톰캣 11.0.27에서는 이때의 쓰기 호출이 예외 없이 무시됐다. 세 경우가 같은 결론으로 이어진다. 뷰로 forward하는 요청에서는 forward 전에도 후에도 응답 본문을 직접 쓰지 않는다.

    5번. 새로 만들 것은 TextController 인터페이스, 그것을 구현한 핸들러 클래스, 그리고 TextControllerAdapter다. 어댑터의 supports는 handler instanceof TextController를 돌려주고, handle은 핸들러를 캐스팅해 파라미터 맵을 넘겨 호출한 뒤 반환된 문자열을 response.getWriter()에 쓰고 null을 반환한다. 고칠 곳은 둘이다. adapters 목록에 새 어댑터를 더하고, 생성자에서 핸들러를 표에 등록한다. service와 findAdapter는 고치지 않는다. service는 null이 돌아오면 뷰 렌더링을 건너뛰도록 이미 돼 있다. 두 인터페이스를 모두 구현한 클래스는 목록에서 앞에 있는 ParamControllerAdapter의 supports가 먼저 참을 돌려주므로 Rendering을 반환하는 handle(Map)이 호출된다. 목록의 순서를 바꾸면 결과도 바뀐다.

     프런트 컨트롤러를 /*에 매핑하고 JSP 경로로 forward했더니 JSP가 실행되지 않고 프런트 컨트롤러가 다시 호출됐다. 원인으로 옳은 것은? forward는 클라이언트에게 새 요청을 보내게 하는데, 새 요청은 언제나 처음 호출된 서블릿으로 간다. forward 대상도 매핑 규칙을 거치는데, 경로 매핑 /*가 확장자 매핑 *.jsp보다 먼저 시도되어 모든 경로에 일치한다. WEB-INF 아래의 파일은 forward로도 접근할 수 없어서 컨테이너가 요청을 되돌려 보낸다. 프런트 컨트롤러가 싱글톤이라 한 번 호출되면 같은 요청의 나머지 처리도 모두 맡게 된다. 컨테이너는 정확 매핑, 가장 긴 경로 매핑, 확장자 매핑, 기본 서블릿 순으로 시도하고 먼저 성공한 것을 쓴다. /*는 경로 매핑이라 JSP 경로에도 먼저 일치한다. 기본 서블릿 /에 매핑하면 확장자 매핑이 먼저 걸려 JSP로 간다. forward는 클라이언트를 거치지 않는 서버 내부 호출이고, WEB-INF는 직접 요청만 막을 뿐 RequestDispatcher로는 내보일 수 있다. 싱글톤 여부는 매핑과 무관하다. v1과 v2에서 뷰가 실행되는 순간의 호출 스택을 비교했을 때 옳은 설명은? 두 경우 모두 컨트롤러의 handle 프레임이 뷰 아래에 남아 있다. v2에서는 뷰가 별도의 스레드에서 실행되므로 스택에 프런트 컨트롤러가 없다. v1에서는 컨트롤러의 프레임 위에서 뷰가 실행되고, v2에서는 컨트롤러가 이미 반환한 뒤 프런트 컨트롤러가 부른 뷰 객체의 프레임 위에서 실행된다. v1에서는 forward가 네트워크를 거치므로 스택이 끊기고, v2에서는 이어진다. v1의 컨트롤러는 forward를 직접 호출하므로 뷰가 끝날 때까지 반환하지 못한다. v2의 컨트롤러는 뷰 객체를 반환하고 끝나며, 렌더링은 프런트 컨트롤러가 호출한다. 그래서 컨트롤러의 반환과 렌더링 사이에 프런트 컨트롤러의 코드가 실행될 자리가 생긴다. 두 경우 모두 같은 스레드의 연속된 메서드 호출이고 네트워크는 끼어들지 않는다. 프런트 컨트롤러의 표에 등록된 컨트롤러가 요청 파라미터를 인스턴스 필드에 저장했다가 같은 메서드 안에서 읽어 쓴다. 요청이 몰릴 때 다른 사용자의 값이 섞여 나오는 근본 원인은? 컨트롤러 객체가 하나뿐이어서 그 필드도 힙에 하나뿐인데, 여러 요청 스레드가 같은 객체의 메서드를 동시에 실행하기 때문이다. 컨테이너가 요청마다 컨트롤러를 새로 만들면서 이전 객체의 필드 값을 복사하기 때문이다. 모델 맵을 여러 요청이 함께 쓰기 때문이다. HashMap으로 만든 핸들러 표가 스레드 안전하지 않아 다른 컨트롤러가 조회되기 때문이다. 컨트롤러는 프런트 컨트롤러의 생성자가 한 번 만든 객체이고 모든 요청 스레드가 공유한다. 인스턴스 필드는 그 객체 안에 한 칸뿐이므로 한 스레드가 쓴 값을 다른 스레드가 덮어쓸 수 있다. 지역 변수는 스레드별 스택 프레임에 있어 섞이지 않는다. 모델 맵은 요청마다 새로 만들고, 핸들러 표는 생성 후 바뀌지 않아 동시 읽기에 문제가 없다. v3에서 컨트롤러를 서버 없이 main 메서드에서 바로 호출해 검증할 수 있게 된 직접적인 이유는? 프런트 컨트롤러가 요청마다 컨트롤러를 새로 만들기 때문이다. 뷰 파일을 WEB-INF 아래에 두었기 때문이다. 컨트롤러가 싱글톤이 되었기 때문이다. 컨트롤러의 매개변수와 반환 타입에서 서블릿 API 타입이 사라져, 입력과 출력이 모두 보통의 자바 객체가 되었기 때문이다. v3의 컨트롤러는 파라미터 맵을 받고 뷰 이름과 모델을 담은 객체를 돌려준다. 컨테이너가 만들어 주는 요청·응답 객체가 필요 없으므로 맵 하나를 만들어 넘기면 호출할 수 있고, 반환값만 보면 결과가 확인된다. 컨트롤러는 v1부터 하나만 만들어 공유했고, 뷰의 위치는 컨트롤러 호출 가능 여부와 관계가 없다. v5에서 표의 값 타입을 Object로 바꾸고 어댑터를 도입했을 때 치른 대가로 가장 정확한 것은? 요청마다 어댑터 객체를 새로 만들어야 해서 메모리 사용이 요청 수에 비례해 늘어난다. 프런트 컨트롤러의 service를 핸들러 방식이 늘 때마다 고쳐야 한다. 핸들러가 올바른 타입인지를 컴파일러가 확인해 주지 못하고, 실행 시점에 instanceof와 캐스팅으로 확인하게 된다. 핸들러가 더는 서블릿 API를 쓸 수 없게 된다. Object 타입의 표에는 어떤 객체든 들어가므로 잘못 등록해도 컴파일된다. 지원 여부는 실행 중 supports의 instanceof로, 호출은 캐스팅을 거쳐 이뤄지며, 맞는 어댑터가 없으면 요청 시점에 예외가 난다. 어댑터는 한 번 만들어 공유하고, service는 고치지 않는 것이 이 구조의 목적이다. 응답을 직접 쓰는 핸들러도 어댑터 하나로 계속 지원된다.
    프런트 컨트롤러(front controller)
    모든 요청을 가장 먼저 받는 단일 진입점. 공통 처리를 하고 요청을 알맞은 핸들러에 넘긴다. 스프링 MVC에서는 DispatcherServlet이 이 역할을 한다.
    경로 매핑(path mapping)
    /로 시작해 /*로 끝나는 서블릿 URL 패턴. 그 접두 경로 아래의 모든 요청에 일치하며 확장자 매핑보다 먼저 시도된다.
    기본 서블릿(default servlet)
    / 한 글자로 매핑된 서블릿. 다른 어느 매핑에도 걸리지 않은 요청을 받는다.
    경로 정보(path info)
    요청 경로에서 컨텍스트 경로와 서블릿 경로를 뺀 나머지. 남는 것이 없으면 null이다.
    포워드(forward)
    RequestDispatcher.forward로 서버 안의 다른 리소스에 요청 처리를 넘기는 것. 같은 스레드, 같은 요청 안에서 일어나며 클라이언트는 알지 못한다.
    커밋(commit)
    응답의 상태 줄과 헤더가 클라이언트로 전송되기 시작한 상태. 커밋된 뒤에는 forward도 상태 코드 변경도 할 수 없다.
    모델(model)
    컨트롤러가 뷰에 넘기는 데이터의 묶음. 이 회차에서는 이름과 객체의 맵이며, JSP로 렌더링할 때 요청 속성으로 옮겨진다.
    논리 뷰 이름(logical view name)
    컨트롤러가 뷰를 가리킬 때 쓰는, 물리적 위치와 무관한 이름. 뷰 리졸버가 실제 뷰로 바꾼다.
    핸들러(handler)
    요청을 실제로 처리하는 객체를 가리키는 넓은 말. 어댑터가 있으면 어떤 모양의 객체든 핸들러가 될 수 있어 컨트롤러보다 넓은 이름을 쓴다.
    핸들러 어댑터(handler adapter)
    프런트 컨트롤러가 기대하는 한 가지 호출 방식과 핸들러의 실제 시그니처 사이를 변환하는 객체. 처리할 수 있는 핸들러인지 답하고 대신 호출한다.
