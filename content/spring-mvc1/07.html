    이 회차의 질문: 반환값은 어떻게 HTTP 응답이 되는가

    앞 회차에서는 요청이 컨트롤러 메서드에 도달하는 쪽, 곧 URL 매핑과 요청 데이터를 파라미터로 받는 방법을 다뤘다. 이번에는 반대쪽이다. 컨트롤러 메서드가 return한 뒤에 무슨 일이 일어나는가. HTTP 응답은 상태 줄, 헤더, 그리고 바이트로 된 본문이다. 서블릿을 직접 쓸 때는 response.setStatus(), response.setContentType(), response.getWriter().write()를 차례로 불러 이 셋을 손으로 채웠다. 스프링 MVC의 컨트롤러는 그렇게 하지 않고 문자열이나 객체를 돌려줄 뿐이다. 그 값을 누가, 어떤 규칙으로 상태 코드와 헤더와 바이트로 바꾸는지가 이 회차의 주제다.

    스프링 MVC에서 응답 본문이 만들어지는 길은 크게 셋이다. 셋은 본문의 출처가 다르고, 요청을 맡는 핸들러가 다르고, 마지막에 바이트를 쓰는 부품이 다르다.

    실험용 컨트롤러

    도메인은 택배 접수 창구로 잡았다. 메서드마다 반환 방식이 다르다. 아래 코드와 그 실행 결과를 회차 내내 다시 본다.

    // import 생략: org.springframework.web.bind.annotation.*, org.springframework.http.*, jakarta.servlet.http.* 등
public class BodyLab {

    record Parcel(String code, int weight) {}

    @Controller
    static class ParcelController {

        @GetMapping("/page")                       // (1) 뷰 이름을 반환
        String page(Model model) { model.addAttribute("count", 2); return "parcel-list"; }

        @GetMapping("/direct")                     // (2) 서블릿 응답 객체에 직접 쓴다
        void direct(HttpServletResponse response) throws IOException { response.getWriter().write("direct ok"); }

        @GetMapping("/text") @ResponseBody         // (3) 문자열을 본문으로
        String text() { return "접수 ok"; }

        @GetMapping(value = "/text-utf8", produces = "text/plain;charset=UTF-8") @ResponseBody
        String textUtf8() { return "접수 ok"; }

        @GetMapping("/parcel") @ResponseBody       // (4) 객체를 본문으로
        Parcel parcel() { return new Parcel("P-100", 3); }

        @PostMapping("/parcels")                   // (5) 상태 코드·헤더·본문을 한 값으로
        ResponseEntity create(@RequestBody Parcel parcel) {
            return ResponseEntity.status(HttpStatus.CREATED)
                    .header("Location", "/parcels/" + parcel.code())
                    .body(parcel);
        }

        @PostMapping("/raw") @ResponseBody         // (6) 본문을 문자열 그대로 받는다
        String raw(@RequestBody String body) { return "chars=" + body.length(); }
    }
    // ... 설정 클래스와 요청을 보내는 도우미는 필요한 곳에서 보인다
}

    관찰 장치는 두 가지를 달았다. 하나는 인터셉터로, preHandle에서 선택된 핸들러의 종류를 찍고 postHandle에서 어댑터가 돌려준 ModelAndView가 무엇인지 찍는다. 다른 하나는 @ControllerAdvice로 등록한 ResponseBodyAdvice·RequestBodyAdvice다. 이 두 인터페이스의 콜백은 어떤 메시지 컨버터가 선택되었는지를 인자로 받으므로, 출력의 [write], [read ] 줄에서 컨버터 이름과 미디어 타입을 볼 수 있다.

    응답 본문을 만드는 길이 세 가지이고, 각 길에서 마지막에 바이트를 쓰는 부품이 다르다는 것을 한눈에 보여 준다. 깔끔한 구조 다이어그램, 흰 배경, 평면 색. 왼쪽 끝에 세로로 긴 남색 상자 "DispatcherServlet". 그 오른쪽으로 세 개의 가로 줄이 평행하게 뻗는다. 첫째 줄(회색 계열): 상자 "ResourceHttpRequestHandler" → 문서 아이콘과 라벨 "파일 그대로" → 오른쪽 끝의 넓은 상자 "HTTP 응답 본문"으로 화살표. 둘째 줄(파란 계열): 상자 "컨트롤러 메서드" → 화살표 라벨 "뷰 이름" → 상자 "ViewResolver · View" → 화살표 라벨 "렌더링한 HTML" → "HTTP 응답 본문". 셋째 줄(주황 계열, 가장 굵게): 상자 "컨트롤러 메서드" → 화살표 라벨 "객체 반환" → 상자 "HttpMessageConverter" → 화살표 라벨 "JSON · 텍스트 바이트" → "HTTP 응답 본문". 각 줄 맨 왼쪽 위에 작은 라벨을 붙인다: "정적 리소스", "뷰 템플릿", "HTTP API". 장식 없이 단순한 선. 세 길은 DispatcherServlet에서 갈라진다. 정적 리소스는 핸들러 자체가 다르고, 뷰와 메시지 바디는 같은 컨트롤러 메서드에서 반환값을 다루는 방식이 다르다.

    정적 리소스: 파일을 그대로 내려 주는 핸들러

    정적 리소스(static resource)는 서버가 내용을 가공하지 않고 파일의 바이트를 그대로 내려 주는 응답이다. HTML, CSS, 자바스크립트, 이미지가 여기에 속한다. 스프링 부트는 클래스패스의 네 위치를 기본 정적 리소스 위치로 삼는다. 부트 3.5의 WebProperties에 적힌 순서대로 classpath:/META-INF/resources/, classpath:/resources/, classpath:/static/, classpath:/public/이다. URL 패턴의 기본값은 /**이고 spring.mvc.static-path-pattern으로 바꿀 수 있으며, 위치는 spring.web.resources.static-locations로 바꾼다. 그래서 src/main/resources/static/guide/price.html 파일은 GET /guide/price.html로 열린다. 빌드 도구가 src/main/resources 아래를 클래스패스 루트로 복사하기 때문에 경로가 그렇게 이어진다.

    이 일을 하는 객체는 ResourceHttpRequestHandler다. 이름에 드러나듯 05회에서 본 HttpRequestHandler의 구현체이고, 따라서 HttpRequestHandlerAdapter가 실행한다. 컨트롤러가 아니므로 RequestMappingHandlerAdapter도, 뷰 리졸버도 관여하지 않는다. 정적 리소스 요청과 컨트롤러 요청은 DispatcherServlet의 첫 단계인 핸들러 조회에서 이미 다른 핸들러로 갈린다.

    /**는 모든 경로에 걸리는 패턴이다. 그런데도 컨트롤러가 가려지지 않는 것은 핸들러 매핑의 순서 때문이다. 정적 리소스용 매핑을 만드는 ResourceHandlerRegistry의 기본 순서 값은 Ordered.LOWEST_PRECEDENCE - 1로, 거의 맨 끝이다. 순서 값 0인 RequestMappingHandlerMapping이 먼저 질문을 받으므로 같은 경로에 컨트롤러 메서드가 있으면 컨트롤러가 이긴다. 정적 리소스 핸들러는 다른 누구도 맡지 않은 요청을 마지막에 받는 자리에 있다.

    실험: 정적 파일 하나를 두 번 요청한다

    부트 없이 같은 구조를 만들려면 WebMvcConfigurer.addResourceHandlers로 URL 패턴과 위치를 직접 등록한다. 부트의 자동 구성이 하는 일도 결국 이 등록이다. 실험에서는 클래스패스의 static-lab 디렉터리에 64바이트짜리 guide.html을 두고 /files/**에 연결했다.

    첫 요청에서 읽을 것이 네 가지 있다. 핸들러는 컨트롤러 메서드가 아니라 ResourceHttpRequestHandler 객체다. Content-Type은 파일 확장자 .html에서 정해졌고, Content-Length는 파일 크기 그대로다. Last-Modified는 파일의 수정 시각이므로 실행 환경마다 다르다. 그리고 어댑터가 돌려준 ModelAndView가 null이다. 핸들러가 응답을 스스로 다 썼으니 그릴 뷰가 없다는 뜻이다.

    두 번째 요청은 첫 응답의 Last-Modified 값을 If-Modified-Since 헤더에 넣어 보냈다. 결과는 본문이 없는 304다. 「HTTP 웹 기본 지식」 권에서 본 조건부 요청(conditional request)이 프레임워크 안에서 구현된 자리가 여기다. 세 번째 요청은 없는 파일이어서 404가 되었다. Spring Framework 6.1부터는 핸들러가 NoResourceFoundException을 던지고 기본 예외 리졸버가 그것을 404로 바꾼다. 네 번째 요청은 ../로 등록한 위치 밖의 파일을 노린 것인데, 핸들러가 경로를 검사해 거부했다. 정적 리소스 위치는 URL로 접근할 수 있는 파일의 경계이고, 그 경계를 지키는 검사가 핸들러 안에 들어 있다.

    7.0.10 소스의 ResourceHttpRequestHandler.handleRequest를 순서대로 옮기면 다음과 같다. 마지막 단계에서 파일을 쓰는 것이 메시지 컨버터라는 점을 눈여겨보자. 메시지 컨버터는 컨트롤러 전용 부품이 아니라 "자바 객체를 HTTP 본문으로 쓰는 일"이 필요한 곳 어디서나 쓰이는 부품이다.

    정적 리소스에서 자주 하는 착각이 둘 있다. 첫째, 정적 파일은 템플릿 엔진을 거치지 않는다. static/ 아래 HTML에 템플릿 문법을 적어도 서버는 해석하지 않고 그대로 내려보낸다. 둘째, 템플릿 디렉터리(templates/)는 정적 리소스 위치가 아니다. 그 안의 파일은 URL로 직접 열리지 않고, 컨트롤러가 뷰 이름을 반환해야만 쓰인다. 부트는 여기에 웰컴 페이지 규칙을 하나 더 얹는다. 레퍼런스에 따르면 정적 위치에서 index.html을 먼저 찾고, 없으면 index 템플릿을 찾아 루트 경로의 화면으로 쓴다.

    뷰 템플릿: 문자열 반환이 뷰 이름이 되는 경로

    뷰 템플릿 방식은 서버가 요청마다 HTML을 만들어 내려 주는 응답이다. 컨트롤러는 화면에 쓸 데이터를 모델에 담고 뷰의 논리 이름을 반환한다. 05회에서 본 대로 어댑터는 이 결과를 ModelAndView로 맞춰 DispatcherServlet에 돌려주고, DispatcherServlet은 뷰 리졸버로 View를 얻어 render를 호출한다. 실험의 /page가 이 경로다.

    GET /page
    [handler] HandlerMethod page()
    [postHandle] mv=view 'parcel-list', committed=false
    status=200
    Content-Language: en
    Content-Type: text/html;charset=UTF-8

    postHandle 시점에 ModelAndView가 있고 뷰 이름이 parcel-list다. 본문은 아직 한 바이트도 쓰이지 않았다. 본문은 그 뒤 DispatcherServlet이 View.render를 호출할 때 만들어진다. Content-Language는 DispatcherServlet이 뷰를 그리기 직전에 응답의 로케일을 설정해서 붙은 헤더이고, 값은 요청의 로케일에 따라 달라진다. 실험의 뷰 리졸버는 템플릿 엔진을 흉내 낸 람다 한 개다.

    @Override
public void configureViewResolvers(ViewResolverRegistry registry) {
    // 템플릿 엔진 흉내: 뷰 이름과 모델을 받아 HTML 문자열을 응답에 쓴다
    registry.viewResolver((viewName, locale) -> (View) (model, request, response) -> {
        response.setContentType("text/html;charset=UTF-8");
        response.getWriter().write("
    " + viewName + " " + model + "
    ");
    });
}

    이 가짜 엔진과 실제 템플릿 엔진은 구조상 같은 자리에 있다. ViewResolver가 이름을 받아 View를 만들고, View가 모델을 받아 응답 스트림에 HTML을 쓴다. 스프링 부트에 타임리프 스타터를 넣으면 자동 구성이 타임리프용 뷰 리졸버를 등록한다. 부트 3.5의 ThymeleafProperties에서 spring.thymeleaf.prefix의 기본값은 classpath:/templates/, spring.thymeleaf.suffix의 기본값은 .html이다. 뷰 이름 parcel-list는 앞뒤에 이 둘이 붙어 classpath:/templates/parcel-list.html이 된다. 소스 트리에서는 src/main/resources/templates/parcel-list.html이다. 템플릿 문법과 화면 구성은 다음 회차에서 다룬다.

    문자열이 뷰 이름으로 해석되는 지점

    반환된 String을 뷰 이름으로 받아들이는 것은 ViewNameMethodReturnValueHandler라는 작은 클래스다. 이 클래스의 supportsReturnType은 반환 타입이 void이거나 CharSequence의 하위 타입이면 true를 돌려주고, handleReturnValue는 요청마다 만들어지는 ModelAndViewContainer에 setViewName으로 그 문자열을 적어 둔다. 하는 일은 그것뿐이다. 응답에는 손대지 않는다. 메서드 호출이 끝난 뒤 어댑터가 컨테이너에서 뷰 이름과 모델을 꺼내 ModelAndView를 만든다. 이 클래스가 목록의 어디에 있고 왜 @ResponseBody가 붙으면 선택되지 않는지는 뒤에서 어댑터 구조를 볼 때 확인한다.

    void를 반환하면

    반환 타입이 void인 메서드는 두 가지로 해석될 수 있다. 레퍼런스의 규칙은 이렇다. 메서드가 ServletResponse나 OutputStream 파라미터를 받거나 @ResponseStatus가 붙어 있으면 응답을 스스로 다 처리한 것으로 본다. 그런 것이 없으면 REST 컨트롤러에서는 "본문 없음", HTML 컨트롤러에서는 "기본 뷰 이름을 쓰겠다"는 뜻이 된다. 실험의 /direct는 HttpServletResponse를 받으므로 앞의 경우다. 비교를 위해 응답 객체를 받지 않는 void 메서드를 /parcels/board에 하나 더 만들어 함께 호출했다.

    GET /direct
    [handler] HandlerMethod direct()
    [postHandle] mv=null, committed=false
    status=200
    body(9 bytes): direct ok
GET /parcels/board
    [handler] HandlerMethod board()
    [postHandle] mv=view 'parcels/board', committed=false
    status=200
    Content-Language: en
    Content-Type: text/html;charset=UTF-8
    body(32 bytes): 
    parcels/board {count=9}

    /direct는 ModelAndView가 null이고 본문은 메서드가 직접 쓴 9바이트다. Content-Type 헤더가 아예 없다는 점도 보인다. 직접 쓰는 방식에서는 헤더도 직접 챙겨야 한다. /parcels/board는 뷰 이름을 반환하지 않았는데도 parcels/board라는 뷰가 그려졌다. 05회의 doDispatch 뼈대에 있던 applyDefaultViewName이 요청 경로에서 기본 뷰 이름을 만들어 넣은 것이다. URL과 템플릿 경로가 암묵적으로 묶이므로, 이 규칙에 기대기보다 뷰 이름을 명시해 반환하는 쪽이 코드를 읽는 사람에게 분명하다.

    HTTP API 응답: 메시지 바디에 직접 쓰는 세 가지 방법

    HTML 화면이 아니라 데이터를 주고받는 HTTP API에서는 뷰가 필요 없다. 반환한 값이 곧 본문이어야 한다. 스프링 MVC에서 본문을 직접 정하는 방법은 세 가지이고, 뒤로 갈수록 서블릿 API에서 멀어진다.

    1. HttpServletResponse에 직접 쓴다. 실험의 /direct다. 서블릿을 직접 쓸 때와 같다. 상태 코드, Content-Type, 문자 인코딩, 직렬화를 모두 손으로 한다.
    2. ResponseEntity를 반환한다. 상태 코드, 헤더, 본문 객체를 한 값에 담아 돌려준다. 실험의 POST /parcels다. 본문 객체는 메시지 컨버터가 바이트로 바꾼다.
    3. @ResponseBody를 붙이고 값을 반환한다. 실험의 /text, /parcel이다. 상태 코드는 기본 200이고, 바꾸려면 @ResponseStatus를 함께 쓴다.
    GET /parcel
    [handler] HandlerMethod parcel()
    [write] JacksonJsonHttpMessageConverter as application/json
    [postHandle] mv=null, committed=false
    status=200
    Content-Type: application/json
    body(27 bytes): {"code":"P-100","weight":3}
POST /parcels  Content-Type: application/json
    [handler] HandlerMethod create()
    [read ] JacksonJsonHttpMessageConverter -> Parcel
    [write] JacksonJsonHttpMessageConverter as application/json
    [postHandle] mv=null, committed=true
    status=201
    Location: /parcels/P-200
    Content-Type: application/json
    body(27 bytes): {"code":"P-200","weight":7}

    /parcel에서 컨트롤러는 Parcel 객체를 반환했을 뿐인데 응답에는 Content-Type: application/json과 27바이트의 JSON이 실렸다. [write] 줄이 그 일을 한 주체를 알려 준다. POST /parcels에서는 읽기와 쓰기 양쪽에 컨버터가 나온다. 요청 본문의 JSON을 Parcel로 바꾼 것도, ResponseEntity에 담긴 Parcel을 다시 JSON으로 바꾼 것도 같은 컨버터다. 상태 코드 201과 Location 헤더는 ResponseEntity에 담은 값이 그대로 응답으로 옮겨진 것이다. 두 경우 모두 ModelAndView는 null이다.

    @ResponseBody, @RestController, @ResponseStatus가 하는 일

    @ResponseBody는 스스로 아무 일도 하지 않는 표식이다. 일을 하는 것은 이 표식을 찾는 쪽인 RequestResponseBodyMethodProcessor다. 이 클래스의 supportsReturnType은 두 곳을 본다. 메서드에 @ResponseBody가 붙어 있는가, 또는 메서드를 가진 클래스에 @ResponseBody가 붙어 있는가. 클래스 쪽 검사는 메타 애노테이션까지 따라간다. @RestController의 소스를 열면 선언 위에 @Controller와 @ResponseBody가 나란히 붙어 있다. 그래서 @RestController 클래스의 모든 메서드는 @ResponseBody를 붙인 것과 같아진다. 새로운 기능이 아니라 두 애노테이션을 묶은 이름이다.

    @ResponseStatus는 메서드 호출 직후, 반환값을 처리하기 전에 반영된다. ServletInvocableHandlerMethod.invokeAndHandle은 컨트롤러 메서드를 부른 다음 곧바로 setResponseStatus를 호출하는데, 이 메서드는 reason 속성이 비어 있으면 response.setStatus(코드)를, 값이 있으면 response.sendError(코드, reason)을 부른다. sendError는 서블릿 컨테이너의 오류 처리로 넘어가는 호출이므로, reason을 적으면 메서드의 반환값은 버려진다. @RestController 클래스에 두 메서드를 만들어 확인했다. 하나는 @ResponseStatus(HttpStatus.ACCEPTED)를 붙이고 "queued"를 반환하고, 다른 하나는 @ResponseStatus(code = HttpStatus.GONE, reason = "desk closed")를 붙이고 "ignored"를 반환한다.

    POST /desk/pickup
    [handler] HandlerMethod pickup()
    [write] StringHttpMessageConverter as text/plain
    [postHandle] mv=null, committed=false
    status=202
    Content-Type: text/plain;charset=ISO-8859-1
    Content-Length: 6
    body(6 bytes): queued
GET /desk/old
    [handler] HandlerMethod old()
    [postHandle] mv=null, committed=true
    status=410 (desk closed)

    둘째 요청에는 [write] 줄이 없고 본문도 없다. 스프링은 이 경우 기동 시점에 "Return value of […] will be ignored since @ResponseStatus 'reason' attribute is set"이라는 경고를 남긴다. @ResponseStatus와 ResponseEntity의 차이도 여기서 정리된다. 애노테이션의 값은 컴파일 시점에 고정되므로 메서드 안의 조건에 따라 상태 코드를 바꿀 수 없다. 처리 결과에 따라 201과 200을 나눠 보내야 한다면 상태 코드를 값으로 다루는 ResponseEntity가 맞는 도구다.

    이 장의 핵심

    컨트롤러 메서드는 응답을 쓰지 않는다. 값을 돌려줄 뿐이다. 그 값을 "뷰 이름"으로 읽을지 "본문"으로 읽을지는 반환값 핸들러 목록에서 누가 먼저 손을 드느냐로 정해지고, 본문으로 읽기로 했다면 그것을 어떤 바이트로 바꿀지는 메시지 컨버터 목록에서 누가 먼저 손을 드느냐로 정해진다. 이 회차에 나오는 동작은 대부분 이 두 목록의 순서에서 설명된다.

    HttpMessageConverter: 객체와 바이트 사이의 계약

    HTTP 본문은 바이트의 나열이고, 그 바이트를 어떻게 읽어야 하는지는 Content-Type 헤더의 미디어 타입(media type)이 알려 준다. 자바 쪽에는 String, byte[], 사용자 정의 객체가 있다. 이 둘 사이를 오가는 변환을 한 가지 계약으로 묶은 것이 HttpMessageConverter 인터페이스다. Javadoc의 설명은 "HTTP 요청과 응답으로부터, 그리고 그쪽으로 변환하는 전략 인터페이스"이고, 6.2.x 기준 메서드는 여섯 개다.

    public interface HttpMessageConverter {

    boolean canRead(Class clazz, @Nullable MediaType mediaType);   // 이 타입을, 이 미디어 타입의 본문에서 읽을 수 있는가
    boolean canWrite(Class clazz, @Nullable MediaType mediaType);  // 이 타입을, 이 미디어 타입의 본문으로 쓸 수 있는가

    List getSupportedMediaTypes();                         // 지원하는 미디어 타입 목록
    default List getSupportedMediaTypes(Class clazz) { /* ... */ }   // 5.3.4부터

    T read(Class clazz, HttpInputMessage inputMessage)
            throws IOException, HttpMessageNotReadableException;
    void write(T t, @Nullable MediaType contentType, HttpOutputMessage outputMessage)
            throws IOException, HttpMessageNotWritableException;
}

    질문 메서드 canRead·canWrite는 인자가 둘이다. 자바 타입과 미디어 타입이다. 컨버터 선택은 언제나 이 두 조건을 함께 본다. "이 컨버터는 JSON 담당"이라는 식으로 한 가지 조건만 기억하면 뒤에서 볼 선택 결과를 설명할 수 없다. 실행 메서드 read·write가 받는 HttpInputMessage와 HttpOutputMessage는 헤더와 스트림을 묶은 작은 인터페이스다. 각각 getHeaders()와 getBody()를 가지며, getBody()는 InputStream 또는 OutputStream을 돌려준다. 컨버터는 서블릿 API를 모른다. 헤더와 바이트 스트림만 안다. 그래서 같은 컨버터가 서버뿐 아니라 HTTP 클라이언트(RestClient, RestTemplate)에서도 쓰인다.

    기본으로 등록되는 컨버터

    @EnableWebMvc나 부트의 자동 구성이 쓰는 WebMvcConfigurationSupport는 기본 컨버터 목록을 만들어 RequestMappingHandlerAdapter에 넣는다. 6.2.x 소스의 addDefaultHttpMessageConverters는 다섯 개를 무조건 넣고, 그 뒤는 클래스패스에 해당 라이브러리가 있을 때만 넣는다. Atom·RSS 피드(ROME), XML, 코틀린 직렬화, JSON, 그 밖의 Jackson 데이터 형식 순이다. JSON 라이브러리가 Jackson뿐인 환경에서 어댑터의 getMessageConverters()를 출력하면 여섯 개가 나온다.

    일상에서 가져온 비유창구에 붙은 통역사 명단

    접수 창구에 통역사 명단이 순서대로 붙어 있다고 하자. 서류가 들어오면 창구 직원은 명단 위에서부터 "이 종류의 서류를 이 언어로 옮길 수 있습니까"라고 묻고, 처음 손든 사람에게 맡긴다. 서류의 종류가 자바 타입이고 언어가 미디어 타입이다. 비유가 맞지 않는 곳도 있다. 통역사는 내용을 이해하지만 컨버터는 형식만 바꾼다. 그리고 가장 잘하는 사람이 아니라 가장 먼저 손든 사람이 맡기 때문에, 명단의 순서가 결과를 바꾼다.

    한 층 아래: 문자가 바이트가 되는 순간과 본문의 길이

    자바의 String은 문자의 나열이고 HTTP 본문은 바이트의 나열이다. 둘 사이에는 반드시 문자 인코딩(character encoding)이 끼어든다. 어떤 인코딩으로 바꿨는지는 Content-Type의 charset 매개변수로 상대에게 알린다. 이 결정을 내리는 것도 컨버터다. 실험의 /text와 /text-utf8은 똑같이 "접수 ok"를 반환하고, 뒤쪽에만 produces = "text/plain;charset=UTF-8"이 붙어 있다. 응답 바이트를 16진수로 함께 찍었다.

    GET /text
    [handler] HandlerMethod text()
    [write] StringHttpMessageConverter as text/plain
    [postHandle] mv=null, committed=false
    status=200
    Content-Type: text/plain;charset=ISO-8859-1
    Content-Length: 5
    body(5 bytes): ?? ok
    hex: 3f 3f 20 6f 6b
GET /text-utf8
    [handler] HandlerMethod textUtf8()
    [write] StringHttpMessageConverter as text/plain;charset=UTF-8
    [postHandle] mv=null, committed=false
    status=200
    Content-Type: text/plain;charset=UTF-8
    Content-Length: 9
    body(9 bytes): 접수 ok
    hex: ec a0 91 ec 88 98 20 6f 6b

    첫 응답의 본문은 5바이트이고 앞의 두 바이트가 3f, 곧 물음표다. StringHttpMessageConverter의 소스에는 DEFAULT_CHARSET = StandardCharsets.ISO_8859_1이라는 상수가 있다. 미디어 타입에 charset이 없으면 컨버터는 이 기본값으로 문자열을 인코딩하고, 헤더에도 그 이름을 적는다. ISO-8859-1에는 한글이 없으므로 "접"과 "수"는 인코딩 단계에서 대체 문자 ?가 된다. 이 손실은 서버에서 바이트를 만드는 순간에 일어난 것이어서 브라우저의 인코딩 설정으로는 되돌릴 수 없다. 둘째 응답은 선택된 미디어 타입에 charset=UTF-8이 들어 있었기 때문에 "접"이 ec a0 91 세 바이트로, "수"가 ec 88 98 세 바이트로 바뀌었다.

    스프링 부트 애플리케이션에서 이 문제를 겪지 않는 까닭은 부트가 컨버터를 다르게 만들기 때문이다. 부트 3.5의 HttpMessageConvertersAutoConfiguration은 server.servlet.encoding 설정의 문자 집합으로 StringHttpMessageConverter 빈을 만들고, 그 설정의 기본값은 UTF-8이다. 부트 레퍼런스도 "기본적으로 문자열은 UTF-8로 인코딩된다"고 적는다. 부트 없이 스프링 MVC를 구성했거나 컨버터 목록을 직접 갈아 끼웠다면 실험과 같은 결과가 나올 수 있다. JSON은 사정이 다르다. /parcel의 응답은 Content-Type: application/json에 charset이 없었는데, Jackson 컨버터는 문자 집합이 지정되지 않으면 UTF-8로 쓴다.

    Content-Length는 누가 정하는가

    출력을 다시 보면 /text의 응답에는 Content-Length가 있고 /parcel의 응답에는 없다. 컨버터의 공통 상위 클래스 AbstractHttpMessageConverter는 본문을 쓰기 전에 getContentLength를 불러 값이 있으면 헤더에 넣는다. StringHttpMessageConverter는 문자열을 정해진 문자 집합으로 인코딩한 바이트 수를 돌려주고, byte[] 컨버터도 배열 길이를 안다. JSON 컨버터는 길이를 미리 계산하지 않는다. 객체를 스트림에 곧바로 직렬화하기 때문에 다 써 보기 전에는 길이를 모른다.

    길이가 정해지지 않은 응답을 어떻게 내보낼지는 서블릿 컨테이너의 몫이다. 톰캣 11.0.27의 소스에서 두 지점을 확인했다. 응답을 닫는 OutputBuffer.close()는 응답이 아직 커밋되지 않았고 길이가 설정되지 않았으면 버퍼에 쌓인 바이트 수를 Content-Length로 설정한다. 헤더를 내보내는 Http11Processor.prepareResponse()는 길이가 끝내 정해지지 않은 HTTP/1.1 응답에 Transfer-Encoding: chunked를 붙인다. 정리하면, 본문이 버퍼에 다 들어 있는 채로 응답이 끝나면 톰캣이 길이를 계산해 주고, 그 전에 누군가 flush를 해서 헤더가 먼저 나가 버렸다면 청크 전송이 된다.

    이 지점에서 스프링 버전이 갈린다. 컨버터는 쓰기를 마치면 outputMessage.getBody().flush()를 호출한다. 6.2.x의 ServletServerHttpResponse.getBody()는 서블릿의 출력 스트림을 그대로 돌려주므로 이 flush가 서블릿 응답까지 내려가 응답을 커밋시킨다. 길이를 계산하지 않는 JSON 컨버터가 쓴 응답이라면 그 시점에 길이가 정해져 있지 않으니 위 규칙에 따라 청크 전송이 된다. 7.0.10의 getBody()는 기본 설정에서 flush를 아래로 전달하지 않는 래퍼 스트림을 돌려준다. 실험 출력에서 @ResponseBody 응답의 committed가 false로 남은 까닭이다. 어느 쪽이든 클라이언트가 받는 본문 바이트는 같다. 달라지는 것은 본문의 끝을 알리는 방식이다.

    쓰기: 응답을 맡을 컨버터는 어떻게 선택되는가

    반환값을 본문으로 쓰기로 한 다음의 과정은 AbstractMessageConverterMethodProcessor.writeWithMessageConverters 메서드 하나에 들어 있다. @ResponseBody와 ResponseEntity가 모두 이 메서드로 모인다. 6.2.x와 7.0.10의 소스에서 같은 순서를 확인했다.

    컨버터 목록은 두 번 쓰인다. 3단계에서는 "이 타입으로 만들 수 있는 미디어 타입이 무엇인가"를 묻는 데 쓰이고, 6단계에서는 "그래서 누가 쓸 것인가"를 정하는 데 쓰인다. 두 번 모두 목록의 앞에서부터 돈다. 실험으로 각 단계를 건드려 보자.

    첫 요청이 가장 많은 것을 알려 준다. 클라이언트가 JSON을 원한다고 했고 응답의 Content-Type도 application/json인데, 본문은 따옴표 없는 접수 ok다. 유효한 JSON이 아니다. 과정을 따라가면 이유가 나온다. 선택된 미디어 타입은 application/json이다. 6단계에서 목록을 앞에서부터 돌면 byte[] 컨버터는 타입이 맞지 않아 넘어가고, 둘째인 StringHttpMessageConverter가 "타입은 String, 미디어 타입은 무엇이든"이라는 조건으로 손을 든다. JSON 컨버터까지 차례가 가지 않는다. 문자열 컨버터는 받은 문자열을 인코딩해 쓸 뿐 JSON 문법으로 감싸지 않는다. 본문이 9바이트인 것은 이 컨버터가 JSON 계열 미디어 타입에 한해 문자 집합이 없을 때 UTF-8을 쓰도록 되어 있기 때문이다.

    둘째 요청은 4단계에서 끝났다. Parcel을 쓸 수 있다고 답한 컨버터는 JSON 컨버터뿐이어서 서버가 만들 수 있는 타입은 application/json과 application/*+json이다. 클라이언트가 받겠다는 text/plain과 겹치지 않는다. 결과는 406이고, 컨트롤러 메서드는 이미 실행된 뒤라는 점에 주의하자. [handler] 줄이 찍혀 있다. 406은 메서드가 반환한 다음 단계에서 나는 오류다. 응답에 붙은 Accept 헤더는 스프링이 서버가 지원하는 타입을 알려 주려고 넣은 것이다. 셋째 요청은 클라이언트가 HTML을 가장 원하고 JSON은 가중치 0.8로 받겠다고 한 경우다. 서버가 HTML을 만들 수 없으므로 교집합에는 JSON만 남는다.

    선택이 순서에 달려 있다는 것을 확인하기 위해 JSON 컨버터를 목록의 맨 앞에 하나 더 넣고 /text를 다시 호출했다.

Jackson은 String도 직렬화할 수 있다고 답하므로, 맨 앞에 선 JSON 컨버터가 3단계에서 application/json을 가장 먼저 내놓고 6단계에서도 가장 먼저 손을 든다. 기본 목록에서 타입 조건이 좁은 컨버터가 앞에, 넓은 컨버터가 뒤에 놓인 까닭이 이것이다. 넓은 컨버터가 앞에 서면 뒤의 좁은 컨버터에게는 차례가 오지 않는다. 클라이언트가 Accept: text/plain을 보낸 둘째 요청에서는 JSON 컨버터가 미디어 타입 조건에서 탈락해 다시 문자열 컨버터가 선택되었다. 두 조건을 함께 본다는 말의 뜻이 이것이다.

    같은 메서드, 다른 표현: 컨버터를 하나 추가한다

    컨버터를 직접 만들어 보면 계약이 손에 잡힌다. Parcel을 text/csv로 읽고 쓰는 컨버터를 만들어 목록의 맨 뒤에 추가했다. 상위 클래스 AbstractHttpMessageConverter가 미디어 타입 비교와 기본 헤더 처리를 해 주므로, 구현할 것은 타입 조건 하나와 읽기·쓰기 둘뿐이다.

    static class ParcelCsvConverter extends AbstractHttpMessageConverter {

    ParcelCsvConverter() { super(StandardCharsets.UTF_8, new MediaType("text", "csv")); }

    @Override
    protected boolean supports(Class clazz) { return clazz == Parcel.class; }

    @Override
    protected Parcel readInternal(Class clazz, HttpInputMessage in) throws IOException {
        String[] f = new String(in.getBody().readAllBytes(), StandardCharsets.UTF_8).trim().split(",");
        return new Parcel(f[0], Integer.parseInt(f[1]));
    }

    @Override
    protected void writeInternal(Parcel p, HttpOutputMessage out) throws IOException {
        out.getBody().write((p.code() + "," + p.weight() + "\n").getBytes(StandardCharsets.UTF_8));
    }
}

    컨트롤러는 그대로인데 같은 URL이 Accept 헤더에 따라 JSON으로도 CSV로도 응답한다. 같은 자원을 클라이언트가 원하는 표현(representation)으로 내려 주는 것, 이것이 「HTTP 웹 기본 지식」 권에서 본 콘텐츠 협상(content negotiation)의 서버 쪽 구현이다. Accept가 없을 때 JSON이 선택되는 것은 JSON 컨버터가 목록에서 CSV 컨버터보다 앞에 있기 때문이다. 셋째 요청은 읽기와 쓰기가 독립이라는 것을 보여 준다. 요청 본문은 Content-Type: text/csv에 따라 CSV 컨버터가 읽었고, 응답은 Accept가 없어서 JSON 컨버터가 썼다. 한 요청 안에서 들어오는 형식과 나가는 형식이 달라도 된다.

    컨버터 선택이 자바 타입과 미디어 타입 두 조건을 함께 보는 순차 탐색이며, 같은 String 반환이라도 목록 순서에 따라 다른 컨버터로 간다는 것을 보여 준다. 깔끔한 순서도, 흰 배경, 평면 색. 화면 왼쪽에 입력 상자 두 개를 세로로 놓는다: 위 상자 "반환 타입: String", 아래 상자 "Accept: application/json". 두 상자에서 나온 화살표가 하나로 합쳐져 화면 가운데의 세로 목록으로 들어간다. 세로 목록은 위에서 아래로 세 칸이며 각 칸은 둥근 사각형이다: 첫 칸 "byte[] 컨버터", 둘째 칸 "String 컨버터", 셋째 칸 "JSON 컨버터". 목록 왼쪽에 위에서 아래로 향하는 굵은 화살표와 라벨 "위에서부터 차례로 질문". 첫 칸 오른쪽에 빨간 X 표시와 라벨 "타입 불일치". 둘째 칸은 주황색으로 강조하고 오른쪽에 초록 체크 표시와 라벨 "타입 일치 · 미디어 타입 무엇이든". 셋째 칸은 흐린 회색으로 칠하고 오른쪽에 라벨 "차례가 오지 않음". 둘째 칸에서 오른쪽으로 화살표가 나가 화면 오른쪽 끝의 상자 "본문: 접수 ok (따옴표 없음)"으로 이어진다. 장식 없이 단순한 선. 컨버터는 "가장 알맞은 것"이 아니라 "조건이 맞는 첫 번째 것"이 선택된다. String 반환에 JSON을 요청해도 문자열 컨버터가 먼저 손을 든다.

    읽기: 요청 본문을 맡을 컨버터와 400·415

    앞 회차에서 @RequestBody로 요청 본문을 받는 방법을 다뤘다. 여기서는 그때 컨버터가 어떤 규칙으로 골라지는지를 쓰기와 나란히 놓고 본다. 읽기는 쓰기보다 단순하다. 협상할 것이 없기 때문이다. 본문은 이미 클라이언트가 만든 바이트이고, 그 형식은 클라이언트가 Content-Type 헤더로 선언했다. 서버가 고를 수 있는 것은 "이 형식의 바이트를 이 자바 타입으로 읽어 줄 컨버터가 있는가"뿐이다. 이 과정은 AbstractMessageConverterMethodArgumentResolver.readWithMessageConverters에 들어 있고, 6.2.x와 7.0.10의 순서가 같다.

    쓰기에서는 컨버터 목록을 두 번 돌았지만 읽기에서는 한 번만 돈다. 미디어 타입이 처음부터 하나로 정해져 있어서다. 그 대신 실패의 종류가 여럿이다. 형식을 읽을 컨버터가 없는 경우, 컨버터는 있는데 내용이 깨진 경우, 본문이 아예 없는 경우가 서로 다른 지점에서 서로 다른 예외가 된다. 다섯 가지 요청으로 하나씩 밟아 보자.

    첫 요청은 Content-Type이 JSON인데도 JSON 컨버터가 읽지 않았다. raw 메서드의 파라미터가 @RequestBody String이기 때문이다. 목록의 둘째인 문자열 컨버터가 "타입은 String, 미디어 타입은 무엇이든"이라는 조건으로 먼저 손을 들었고, 본문 27바이트를 해석하지 않은 채 문자열 27자로 넘겼다. 쓰기에서 본 것과 같은 현상의 읽기 쪽이다. Content-Type만으로 컨버터가 정해지는 것이 아니라 받는 쪽 파라미터의 자바 타입이 함께 정한다. 본문을 원문 그대로 받아 서명을 검증하거나 로그로 남겨야 할 때 이 성질을 쓴다. 문자열 컨버터가 바이트를 문자로 되돌릴 때 쓰는 문자 집합도 쓰기와 같은 규칙을 따른다. Content-Type에 charset이 있으면 그것을, 없고 JSON 계열이면 UTF-8을, 그 밖에는 컨버터의 기본 문자 집합을 쓴다.

    둘째 요청은 본문이 멀쩡한 JSON인데 415다. 클라이언트가 text/plain이라고 선언했기 때문이다. 목록을 따라가 보면 byte[]·문자열·리소스·폼 컨버터는 Parcel이라는 타입에서 탈락하고, JSON 컨버터는 타입은 받지만 미디어 타입 text/plain에서 탈락한다. 손든 컨버터가 없다. 서버는 본문의 내용을 들여다보고 형식을 짐작하지 않는다. 선언된 미디어 타입만 본다. 셋째 요청은 헤더가 없어서 application/octet-stream으로 간주되었고, 오류 문구에 그 이름이 그대로 나온다. 클라이언트가 보낸 적 없는 미디어 타입이 오류 문구에 보이면 Content-Type 헤더를 빠뜨린 것이다. 두 응답에 붙은 Accept 헤더는 이 타입을 읽을 수 있는 컨버터들의 지원 미디어 타입을 모은 것으로, 무엇을 보냈어야 하는지 알려 준다.

    넷째와 다섯째는 둘 다 400이지만 걸린 단계가 다르다. 넷째는 JSON 컨버터가 선택되어 read를 시작했고, 파서가 객체가 닫히기 전에 입력이 끝난 것을 발견했다. 컨버터는 이것을 HttpMessageNotReadableException으로 감싸 던진다. 다섯째는 컨버터가 선택되기는 했으나 본문이 0바이트여서 read가 불리지 않았고, 결과가 null인 채로 필수 검사에 걸렸다. 예외 메시지는 "Required request body is missing"으로 시작한다. @RequestBody(required = false)로 선언하면 이 경우 예외 없이 null이 파라미터로 들어온다.

    다섯 요청 모두 [handler] 줄은 찍혔다. 핸들러 조회는 성공했고 인터셉터의 preHandle도 지나갔다는 뜻이다. 그러나 실패한 네 요청에서 컨트롤러 메서드의 본문은 한 줄도 실행되지 않았다. 인자를 만들지 못했으니 호출할 수 없었던 것이다. 이 점이 앞에서 본 406과 다르다. 406은 메서드가 반환한 뒤에 나므로, 그 메서드가 저장이나 외부 호출을 했다면 그 일은 이미 일어난 상태로 클라이언트는 오류 응답을 받는다.

    예외가 상태 코드가 되는 자리는 어댑터 밖이다. 어댑터 안에서 던져진 예외는 DispatcherServlet까지 올라가고, 거기서 예외 리졸버가 처리한다. 기본으로 등록되는 DefaultHandlerExceptionResolver가 HttpMediaTypeNotSupportedException을 415로, HttpMediaTypeNotAcceptableException을 406으로, HttpMessageNotReadableException을 400으로, HttpMessageNotWritableException을 500으로 바꾼다. 예외 리졸버의 구조는 「스프링 MVC 2편」 권에서 다룬다.

    같은 415·406이 핸들러 조회 단계에서도 난다

    앞 회차에서 본 대로 @RequestMapping의 consumes와 produces는 매핑 조건이다. 이 조건이 붙은 메서드에서는 컨버터까지 가기 전에, 핸들러를 찾는 단계에서 같은 상태 코드가 난다. consumes = "application/json", produces = "application/json"을 붙인 POST /strict 메서드를 만들어 호출했다.

    POST /strict  Content-Type: text/plain
    status=415 (Content-Type 'text/plain' is not supported.)
    Accept: application/json
POST /strict  Content-Type: application/json  Accept: text/plain
    status=406 (Acceptable representations: [application/json].)
    Accept: application/json
POST /strict  Content-Type: application/json;charset=UTF-8
    [handler] HandlerMethod strict()
    [read ] JacksonJsonHttpMessageConverter -> Parcel
    [write] JacksonJsonHttpMessageConverter as application/json
    [postHandle] mv=null, committed=false
    status=200
    Content-Type: application/json
    body(27 bytes): {"code":"P-200","weight":7}

    앞의 두 요청에는 [handler] 줄이 없다. RequestMappingHandlerMapping이 경로와 HTTP 메서드는 맞지만 미디어 타입 조건이 맞지 않는 후보만 남은 것을 보고 예외를 던졌기 때문이다. 핸들러가 정해지지 않았으니 인터셉터도, 어댑터도 실행되지 않았다. 오류에 실린 지원 목록도 다르다. 컨버터 단계의 오류는 컨버터들이 지원하는 타입을 모아서 application/json, application/*+json을 보여 줬지만, 여기서는 consumes와 produces에 적은 값만 나온다. 상태 코드는 같아도 어느 단계에서 났는지를 응답과 로그에서 구분할 수 있다.

    상태나는 단계조건컨트롤러 메서드
    415핸들러 조회(매핑)consumes 조건과 요청의 Content-Type이 맞지 않는다실행 안 됨
    415인자 준비(읽기)파라미터 타입과 Content-Type의 조합을 읽을 컨버터가 없다실행 안 됨
    400인자 준비(읽기)컨버터가 본문을 해석하다 실패했다. 또는 필수 본문이 비어 있다실행 안 됨
    406핸들러 조회(매핑)produces 조건과 요청의 Accept가 맞지 않는다실행 안 됨
    406반환값 처리(쓰기)반환 타입으로 만들 수 있는 미디어 타입과 Accept가 겹치지 않는다이미 실행됨
    500반환값 처리(쓰기)반환 타입을 쓸 수 있는 컨버터가 하나도 없다(HttpMessageNotWritableException)이미 실행됨

    표의 마지막 두 줄이 말하는 것은 설계에 영향을 준다. 응답 형식이 정해져 있는 API라면 produces를 명시해 두는 편이 낫다. 받을 수 없는 형식을 요구한 요청이 메서드에 들어오기 전에 걸러지기 때문이다. RFC 9110은 406을 "클라이언트가 협상 헤더로 밝힌 조건에 맞는 표현이 없고 서버가 기본 표현을 보낼 뜻도 없을 때"의 응답으로, 415를 "요청 내용의 형식을 대상 자원이 지원하지 않을 때"의 응답으로 정의한다(§15.5.7, §15.5.16). 스프링 MVC의 두 예외는 이 정의를 그대로 구현한 것이다.

    HttpEntity로 헤더와 본문을 함께 받는다

    본문과 함께 요청 헤더도 필요하면 파라미터를 HttpEntity로 선언한다. HttpEntity처럼 타입 인자로 본문의 타입을 적으면, 그 타입으로 위와 똑같은 readWithMessageConverters가 실행되고 결과가 헤더와 함께 HttpEntity 객체에 담긴다. 하위 타입 RequestEntity로 받으면 HTTP 메서드와 URL까지 들어 있다. 반환 쪽의 ResponseEntity도 HttpEntity의 하위 타입이며 상태 코드를 더 가진다. HttpEntity을 받아 Content-Type과 본문 길이를 돌려주는 POST /echo를 호출했다.

    POST /echo  Content-Type: application/json                본문: {"code":"P-200","weight":7}
    [handler] HandlerMethod echo()
    [read ] StringHttpMessageConverter -> String
    [write] StringHttpMessageConverter as text/plain;charset=UTF-8
    [postHandle] mv=null, committed=true
    status=200
    Content-Type: text/plain;charset=UTF-8
    Content-Length: 31
    body(31 bytes): type=application/json, chars=27
POST /echo                                                본문 없음
    [handler] HandlerMethod echo()
    [write] StringHttpMessageConverter as text/plain;charset=UTF-8
    [postHandle] mv=null, committed=true
    status=200
    Content-Type: text/plain;charset=UTF-8
    Content-Length: 19
    body(19 bytes): type=null, chars=-1

    둘째 요청이 @RequestBody와의 차이를 보여 준다. 본문이 없는데 400이 아니라 메서드가 실행되었고, getBody()가 null이었다. HttpEntity 쪽에는 필수 검사가 없다. 본문의 유무를 스스로 판단해야 하는 자리에서는 이쪽이 맞고, 본문이 반드시 있어야 하는 API라면 @RequestBody의 필수 검사에 맡기는 편이 낫다. 응답의 Content-Type이 실험 메서드가 ResponseEntity에 넣은 값 그대로인 것도 보인다. 쓰기 순서의 첫 단계, "이미 정해진 Content-Type이 있으면 협상을 건너뛴다"가 적용된 결과다.

    같은 상태 코드가 서로 다른 단계에서 날 수 있고, 반환값 처리 단계의 406만 컨트롤러 메서드가 이미 실행된 뒤라는 것을 보여 준다. 깔끔한 가로 순서도, 흰 배경, 평면 색. 왼쪽에서 오른쪽으로 네 개의 둥근 사각형이 화살표로 이어진다: "① 핸들러 조회", "② 인자 준비(읽기)", "③ 컨트롤러 메서드 실행", "④ 반환값 처리(쓰기)". 셋째 상자만 진한 남색으로 칠하고 나머지는 연한 회색. 첫째 상자 아래로 빨간 점선 화살표 두 개가 내려가 빨간 꼬리표 "415 · consumes 불일치"와 "406 · produces 불일치"에 닿는다. 둘째 상자 아래로 빨간 점선 화살표 두 개가 내려가 꼬리표 "415 · 읽을 컨버터 없음"과 "400 · 본문 해석 실패"에 닿는다. 넷째 상자 아래로 빨간 점선 화살표 하나가 내려가 꼬리표 "406 · 쓸 수 있는 형식 없음"에 닿는다. 셋째 상자와 넷째 상자 사이 위쪽에 세로 점선을 긋고 그 위에 주황색 라벨 "여기부터는 메서드가 이미 실행됨". 장식 없이 단순한 선. 415와 406은 두 군데에서 날 수 있다. 응답에 실린 지원 타입 목록과 컨트롤러 메서드의 실행 여부로 단계를 구분한다.

    요청 매핑 핸들러 어댑터 구조 ①: 메서드를 호출하기까지와 인자 리졸버

    여기까지 본 것을 다시 묶어 보자. 뷰 이름을 받아 적는 클래스, @ResponseBody를 알아보는 클래스, HttpServletResponse를 넣어 주는 클래스, 메시지 컨버터 목록. 이들은 모두 한 객체 안에 들어 있다. @RequestMapping 메서드를 실행하는 핸들러 어댑터, RequestMappingHandlerAdapter다. 05회에서 핸들러 어댑터의 일은 DispatcherServlet이 핸들러의 종류를 몰라도 실행할 수 있도록 호출 방식을 맞춰 주는 것이라고 했다. 인터페이스 기반 핸들러라면 정해진 메서드 하나를 부르면 끝난다. 애노테이션 기반 컨트롤러는 사정이 다르다. 메서드마다 파라미터의 수와 타입이 다르고 반환 타입도 다르다. 어댑터가 풀어야 할 문제는 "시그니처를 미리 알 수 없는 메서드를 어떻게 호출하고, 그 결과를 어떻게 한 가지 형태로 맞추는가"다.

    답은 일을 둘로 쪼개 각각 목록에 맡기는 것이다. 파라미터 하나의 값을 만드는 일은 인자 리졸버(argument resolver) 목록에, 반환값 하나를 처리하는 일은 반환값 핸들러(return value handler) 목록에 맡긴다. 어댑터의 invokeHandlerMethod와 그것이 부르는 ServletInvocableHandlerMethod.invokeAndHandle의 뼈대를 소스에서 추리면 다음과 같다. 6.2.x와 7.0.10이 같은 구조다.

    // RequestMappingHandlerAdapter.invokeHandlerMethod → ServletInvocableHandlerMethod.invokeAndHandle
// 실제 소스의 뼈대만 남긴 의사 코드다. 비동기 처리, 검증, 예외 로깅은 뺐다.

ServletWebRequest webRequest = new ServletWebRequest(request, response);   // 요청마다 새로 만든다
ModelAndViewContainer mavContainer = new ModelAndViewContainer();          // 요청마다 새로 만든다

// 1. 파라미터마다 인자 리졸버에게 값을 만들게 한다
Object[] args = new Object[parameters.length];
for (int i = 0; i < parameters.length; i++) {
    args[i] = argumentResolvers.resolveArgument(parameters[i], mavContainer, webRequest, binderFactory);
}

// 2. 리플렉션으로 컨트롤러 메서드를 호출한다
Object returnValue = method.invoke(controllerBean, args);

// 3. @ResponseStatus 가 있으면 상태 코드를 반영한다
setResponseStatus(webRequest);

// 4. 반환값 핸들러에게 반환값을 처리하게 한다
returnValueHandlers.handleReturnValue(returnValue, returnType, mavContainer, webRequest);

// 5. 컨테이너에 모인 결과로 ModelAndView 를 만든다. "처리 완료" 표시가 있으면 null 이다
return mavContainer.isRequestHandled() ? null : new ModelAndView(mavContainer.getViewName(), mavContainer.getModel());

    가운데의 method.invoke가 컨트롤러 메서드가 실제로 실행되는 한 줄이다. 그 앞은 전부 인자를 준비하는 일이고 그 뒤는 전부 결과를 해석하는 일이다. ModelAndViewContainer는 이 과정 내내 들고 다니는 메모지 구실을 한다. 인자 리졸버가 모델을 꺼내 주는 곳도, 반환값 핸들러가 뷰 이름을 적어 두는 곳도, "응답을 이미 다 썼다"는 표시를 남기는 곳도 이 객체다.

    HandlerMethodArgumentResolver 인터페이스

    public interface HandlerMethodArgumentResolver {

    boolean supportsParameter(MethodParameter parameter);            // 이 파라미터를 내가 맡을 수 있는가

    @Nullable
    Object resolveArgument(MethodParameter parameter,                 // 맡았다면 값을 만들어 돌려준다
                           @Nullable ModelAndViewContainer mavContainer,
                           NativeWebRequest webRequest,
                           @Nullable WebDataBinderFactory binderFactory) throws Exception;
}

    Javadoc의 정의는 "주어진 요청의 맥락에서 메서드 파라미터를 인자 값으로 풀어내는 전략 인터페이스"다. 모양이 메시지 컨버터와 닮았다. 질문 메서드 하나와 실행 메서드 하나다. MethodParameter는 파라미터 하나에 대한 리플렉션 정보를 묶은 객체로, 타입, 붙어 있는 애노테이션, 제네릭 타입 인자, 이름을 꺼낼 수 있다. 리졸버는 이것만 보고 손을 들지 말지 정한다. NativeWebRequest는 서블릿 요청·응답 객체를 감싼 것이고, WebDataBinderFactory는 문자열을 목적 타입으로 바꾸거나 객체에 값을 채워 넣을 때 쓰는 바인더를 만들어 준다.

    6.2.x 소스에서는 25번이 없고, 코틀린이 클래스패스에 있을 때만 그 자리에 코루틴용 리졸버가 하나 들어간다. 나머지 종류와 순서는 같다. 선택 규칙은 컨버터와 같다. 위에서부터 supportsParameter를 묻고 처음 true를 답한 리졸버가 맡는다. 그래서 이 목록의 순서를 읽으면 그동안 규칙으로 외웠던 것들이 구조로 설명된다.

    • 같은 클래스가 두 번 나온다. 1번과 28번, 7번과 29번은 같은 클래스의 다른 객체다. 괄호 안의 값은 생성자 인자다. 앞의 것은 애노테이션이 붙은 파라미터만 받고, 뒤의 것은 애노테이션이 없어도 받는다. 앞 회차에서 본 "@RequestParam과 @ModelAttribute는 생략할 수 있다"는 규칙의 정체가 목록 맨 끝의 이 두 객체다. 28번은 BeanUtils.isSimpleProperty가 참인 타입(String, 숫자, 날짜 등)을 받고, 29번은 그 나머지를 받는다. 레퍼런스의 인자 표 마지막 줄 "Any other argument"가 이 동작을 적은 것이다.
    • 마지막 그물은 반드시 마지막이어야 한다. 29번은 단순 타입이 아니면 무엇이든 받는다. 이것이 앞에 있으면 Model도 HttpServletRequest도 "요청 파라미터로 채울 객체"로 취급된다. 조건이 좁은 것을 앞에, 넓은 것을 뒤에 두는 배치는 컨버터 목록에서 본 것과 같은 원리다.
    • HttpServletResponse를 받으면 "처리 완료"가 되는 까닭. 17번 리졸버의 resolveArgument는 응답 객체를 돌려주기 전에 mavContainer.setRequestHandled(true)를 부른다. 메서드가 void나 null을 반환하면 invokeAndHandle은 이 표시를 보고 반환값 핸들러를 부르지 않고 끝낸다. 앞의 /direct 실험에서 ModelAndView가 null이었던 과정이 이것이다. 메서드가 값을 반환하면 표시는 지워지고 반환값 처리가 정상대로 진행된다.

    탐색은 메서드마다 한 번: 리졸버 캐시

    요청마다 파라미터 하나에 서른 개 가까운 객체에게 차례로 묻는다면 낭비다. 실제로는 그렇지 않다. 목록을 감싼 HandlerMethodArgumentResolverComposite는 ConcurrentHashMap으로 된 캐시를 갖고 있다. 어떤 MethodParameter에 대해 리졸버를 한 번 찾으면 그 결과를 저장하고, 다음부터는 목록을 돌지 않고 캐시에서 꺼낸다. 컨트롤러 메서드의 시그니처는 실행 중에 바뀌지 않으므로 "이 파라미터는 누가 맡는가"의 답도 바뀌지 않는다. 이 성질 때문에 supportsParameter는 요청의 내용을 보고 답하면 안 된다. 인자로 요청 객체를 주지 않는 것도 그래서다.

    실험: 리졸버를 하나 만들어 끼운다

    접수 요청을 보낸 쪽의 정보를 Caller라는 레코드로 받고 싶다고 하자. 주소는 연결 정보에서, 에이전트 이름은 헤더에서 온다. 컨트롤러마다 HttpServletRequest를 받아 같은 코드를 되풀이하는 대신 리졸버 하나에 그 일을 모은다.

    record Caller(String ip, String agent) {}

static class CallerResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        supportsCalls.incrementAndGet();                         // 관찰용: 몇 번 질문받았는지 센다
        return parameter.getParameterType() == Caller.class;     // 타입만 보고 답한다
    }

    @Override
    public Object resolveArgument(MethodParameter parameter, ModelAndViewContainer mavContainer,
                                  NativeWebRequest webRequest, WebDataBinderFactory binderFactory) {
        HttpServletRequest request = webRequest.getNativeRequest(HttpServletRequest.class);
        return new Caller(request.getRemoteAddr(), request.getHeader("User-Agent"));
    }
}

// 설정 클래스(WebMvcConfigurer)에서 등록
@Override
public void addArgumentResolvers(List resolvers) {
    resolvers.add(new CallerResolver());
}

    반환 쪽 인터페이스도 같은 모양이다.

    public interface HandlerMethodReturnValueHandler {

    boolean supportsReturnType(MethodParameter returnType);          // 이 반환 타입을 내가 맡을 수 있는가

    void handleReturnValue(@Nullable Object returnValue,              // 맡았다면 처리한다
                           MethodParameter returnType,

    ModelAndView가 null이 되는 과정

    실험 출력의 [postHandle] mv=null이 어디서 정해지는지도 이제 소스로 말할 수 있다. RequestResponseBodyMethodProcessor.handleReturnValue와 HttpEntityMethodProcessor.handleReturnValue는 둘 다 첫 줄에서 mavContainer.setRequestHandled(true)를 부르고, 그다음에 writeWithMessageConverters로 본문을 쓴다. 메서드 호출이 끝난 뒤 어댑터의 getModelAndView는 이 표시가 켜져 있으면 null을 돌려준다. DispatcherServlet은 ModelAndView가 null이면 뷰를 찾지도 그리지도 않는다. 05회의 흐름에서 "뷰 리졸버 호출"과 "뷰 렌더링" 두 단계가 통째로 빠지는 것이다. HTTP API 응답이 뷰 템플릿 응답과 갈리는 지점은 DispatcherServlet의 분기가 아니라 어댑터가 돌려준 값 하나다.

    두 스택의 아래쪽 다섯 줄, doDispatch부터 invokeAndHandle까지는 같다. 거기서 갈라진다. 읽기 스택은 getMethodArgumentValues를 거쳐 인자 리졸버 컴포지트로 들어가고, 그 안에서 RequestResponseBodyMethodProcessor.resolveArgument가 컨버터의 read를 부른다. 쓰기 스택은 반환값 핸들러 컴포지트로 들어가고, 그 안에서 HttpEntityMethodProcessor.handleReturnValue가 컨버터의 write를 부른다. 그 사이, 두 스택 어디에도 찍히지 않은 시점에 컨트롤러의 create 메서드가 실행되었다.

    메시지 컨버터를 부르는 것은 DispatcherServlet도 어댑터 자신도 아니다. 인자 리졸버 하나와 반환값 핸들러 하나가 부른다. 정확히는 두 클래스가 양쪽 일을 다 한다. RequestResponseBodyMethodProcessor는 인자 리졸버로서 @RequestBody를, 반환값 핸들러로서 @ResponseBody를 맡는다. HttpEntityMethodProcessor는 인자 리졸버로서 HttpEntity·RequestEntity 파라미터를, 반환값 핸들러로서 HttpEntity·ResponseEntity 반환을 맡는다. 이름이 Resolver나 Handler가 아니라 Processor로 끝나는 클래스들은 이렇게 두 인터페이스를 함께 구현한 것들이다. 두 클래스 모두 AbstractMessageConverterMethodProcessor를 상속하고, 어댑터가 이들을 만들 때 자신의 컨버터 목록을 넘겨준다.

    이 그림에서 읽어야 할 것이 하나 더 있다. 요청 데이터를 읽는 모든 길이 메시지 컨버터를 지나는 것은 아니다. @RequestParam과 @ModelAttribute를 맡는 리졸버는 컨버터 목록에 닿지 않는다. 이들은 서블릿 컨테이너가 이미 파싱해 둔 요청 파라미터(쿼리 스트링과 폼 본문)를 읽고, 문자열을 목적 타입으로 바꾸는 일은 바인더와 타입 변환 체계에 맡긴다. 메시지 컨버터는 "본문 전체를 한 덩어리로 객체와 맞바꾸는" 두 프로세서만 쓴다. JSON 요청을 @ModelAttribute로 받으려 하면 필드가 비는 까닭, 폼 요청을 @RequestBody 객체로 받으려 하면 415가 나는 까닭이 여기서 나온다. 둘은 목록에서 서로 다른 리졸버가 맡고, 그 리졸버들은 서로 다른 곳에서 데이터를 읽는다.

    @RequestParam, 애노테이션 없는 단순 타입RequestParamMethodArgumentResolver요청 파라미터(쿼리 스트링, 폼 본문)쓰지 않음

    어댑터 안이 '인자 준비 → 메서드 호출 → 반환값 처리' 세 칸으로 나뉘고, 메시지 컨버터는 어댑터가 직접 부르는 것이 아니라 인자 리졸버와 반환값 핸들러 중 일부가 부른다는 것을 보여 준다. 깔끔한 구조 다이어그램, 흰 배경, 평면 색. 화면 대부분을 차지하는 큰 둥근 사각형 테두리를 그리고 왼쪽 위에 라벨 "RequestMappingHandlerAdapter". 큰 상자 안 위쪽에 세 개의 칸을 가로로 배치한다. 왼쪽 칸(파란 계열): 제목 "인자 리졸버 목록", 안에 세로로 쌓인 작은 막대 다섯 개, 그중 셋째 막대만 주황색으로 칠하고 라벨 "@RequestBody". 가운데 칸(진한 남색): 제목 "컨트롤러 메서드". 오른쪽 칸(초록 계열): 제목 "반환값 핸들러 목록", 안에 세로로 쌓인 작은 막대 다섯 개, 그중 셋째 막대만 주황색으로 칠하고 라벨 "@ResponseBody". 왼쪽 칸에서 가운데 칸으로 화살표와 라벨 "인자", 가운데 칸에서 오른쪽 칸으로 화살표와 라벨 "반환값". 큰 상자 안 아래쪽에 가로로 긴 주황색 상자 "HttpMessageConverter 목록". 왼쪽 칸의 주황 막대에서 아래 주황 상자로 내려가는 화살표와 라벨 "read", 오른쪽 칸의 주황 막대에서 아래 주황 상자로 내려가는 화살표와 라벨 "write". 큰 상자 바깥 왼쪽에 작은 상자 "DispatcherServlet"이 있고 큰 상자로 들어가는 화살표, 큰 상자 바깥 오른쪽으로 나가는 화살표에 라벨 "ModelAndView 또는 null". 장식 없이 단순한 선. 메시지 컨버터는 어댑터의 세 칸 중 첫째와 셋째 칸에 있는 특정 프로세서가 부른다. 컨트롤러 메서드는 그 사이에서 리플렉션으로 한 번 호출된다.

    공유되는 객체와 요청마다 만들어지는 객체

    이 구조를 메모리 관점에서 다시 보자. 어댑터는 스프링 컨테이너의 싱글톤 빈이고, 어댑터가 가진 리졸버 목록, 반환값 핸들러 목록, 컨버터 목록도 애플리케이션이 뜰 때 한 번 만들어진다. 이 권의 앞 회차에서 본 대로 서블릿 컨테이너는 요청마다 스레드 풀의 스레드 하나를 배정하므로, 동시에 들어온 요청들은 서로 다른 스레드에서 같은 리졸버 객체와 같은 컨버터 객체의 메서드를 실행한다. 요청마다 새로 만들어지는 것은 ServletWebRequest, ServletInvocableHandlerMethod, ModelAndViewContainer, 그리고 컨버터에게 넘기는 입력·출력 메시지 객체다. 이것들은 한 스레드의 호출 스택에서만 참조되므로 다른 요청과 섞이지 않는다.

    직접 만드는 컨버터와 리졸버도 같은 규칙 아래 놓인다. 앞의 ParcelCsvConverter와 CallerResolver에는 요청에 따라 바뀌는 필드가 없다. 읽은 본문이나 만든 객체는 모두 지역 변수에 있다가 반환된다. 만약 컨버터가 "방금 읽은 본문"을 필드에 저장해 두고 다른 메서드에서 꺼내 쓴다면, 두 요청이 겹치는 순간 한 요청의 데이터가 다른 요청의 응답에 실릴 수 있다. 실험에서 호출 횟수를 세는 데 AtomicInteger를 쓴 것도 같은 이유다. 싱글톤 서블릿에 상태를 두면 안 된다는 원칙이 스프링 MVC의 확장 부품에도 그대로 적용된다.

    확장 지점 정리: 어디에 무엇을 끼우는가

    지금까지 본 세 목록은 모두 열려 있다. 스프링 MVC는 WebMvcConfigurer 인터페이스의 콜백으로 각 목록에 손을 댈 자리를 준다. 어느 콜백이 목록의 어느 위치에 영향을 주는지가 중요하다.

    콜백(6.2.x 기준)대상 목록들어가는 위치할 수 있는 것과 없는 것
    addArgumentResolvers인자 리졸버내장 리졸버 뒤, 마지막 그물 앞새 타입·새 애노테이션 지원은 가능. 내장 리졸버가 맡는 파라미터는 가로챌 수 없다
    addReturnValueHandlers반환값 핸들러내장 핸들러 뒤, 마지막 그물 앞새 반환 타입 지원은 가능. String이나 @ResponseBody 반환은 가로챌 수 없다
    extendMessageConverters메시지 컨버터기본 목록이 만들어진 뒤 그 목록을 넘겨받는다추가, 삭제, 순서 변경 모두 가능
    configureMessageConverters메시지 컨버터빈 목록을 넘겨받는다하나라도 넣으면 기본 컨버터가 등록되지 않는다. 목록을 통째로 정할 때 쓴다

    실험에서 CSV 컨버터를 맨 뒤에, JSON 컨버터를 맨 앞에 넣는 데 쓴 것이 extendMessageConverters다. 6.2 레퍼런스는 configureMessageConverters가 기본값을 대체하고 extendMessageConverters가 구성된 목록을 마지막에 손보는 용도라고 구분한다. configureMessageConverters에 컨버터 하나만 넣고 끝내면 문자열 컨버터도 JSON 컨버터도 사라진다는 점에 주의하자. Spring Framework 7.0에서는 목록을 받는 이 두 메서드가 제거 예정으로 표시되었고, HttpMessageConverters.ServerBuilder를 받는 새 configureMessageConverters가 그 자리를 대신한다. 목록을 직접 만지는 대신 "JSON 컨버터를 이것으로 바꾼다", "사용자 정의 컨버터를 추가한다"를 빌더에 말하는 방식이다.

    스프링 부트에서는 한 단계가 더 있다. 부트 3.5 레퍼런스에 따르면 컨텍스트에 있는 HttpMessageConverter 빈은 모두 컨버터 목록에 추가되고, 부트가 제공하는 HttpMessageConverters 클래스의 빈을 선언해 컨버터를 추가하거나 바꿀 수도 있다. 부트 4.x 레퍼런스는 같은 일을 ServerHttpMessageConvertersCustomizer 빈으로 하도록 안내한다. 어떤 방법을 쓰든 결과를 확인하는 방법은 하나다. 이 회차의 실험처럼 RequestMappingHandlerAdapter 빈을 꺼내 getMessageConverters()를 출력해 보는 것이다. 순서가 결과를 정하는 구조에서는 "등록했다"가 아니라 "몇 번째에 있다"를 알아야 한다.

    본문을 읽기 직전이나 쓰기 직전에 끼어드는 자리도 있다. 실험에서 컨버터 이름을 찍는 데 쓴 RequestBodyAdvice와 ResponseBodyAdvice다. @ControllerAdvice 빈으로 등록하면 readWithMessageConverters와 writeWithMessageConverters가 컨버터를 고른 뒤 이 콜백을 부른다. 선택된 컨버터의 클래스와 미디어 타입이 인자로 넘어오고, 본문 객체를 다른 객체로 바꿔 돌려줄 수도 있다. 모든 API 응답을 공통 봉투 객체로 감싸는 식의 일을 컨트롤러를 고치지 않고 할 수 있는 자리다. 다만 이 콜백은 메시지 컨버터를 쓰는 길에서만 불린다. 뷰 템플릿 응답이나 정적 리소스 응답에는 적용되지 않는다.

    흔한 오해와 함정

    "@ResponseBody를 붙이면 JSON이 나간다"

    @ResponseBody가 정하는 것은 "반환값을 메시지 컨버터로 본문에 쓴다"까지다. 어떤 형식이 될지는 반환 타입, Accept 헤더, 컨버터 목록의 순서가 정한다. String을 반환하면 기본 목록에서는 문자열 컨버터가 받아 text/plain으로 나가고, 클라이언트가 JSON을 요구해도 따옴표 없는 문자열이 나간다. 객체를 반환할 때 JSON이 되는 것은 그 타입을 받겠다고 손드는 컨버터가 기본 목록에서는 JSON 컨버터뿐이기 때문이다. XML 컨버터가 클래스패스에 있거나 사용자 정의 컨버터를 추가했다면 같은 메서드가 다른 형식으로 응답할 수 있다.

    "컨버터는 가장 알맞은 것이 선택된다"

    점수를 매겨 최선을 고르는 단계는 없다. 미디어 타입을 하나로 좁힐 때는 구체성과 가중치로 정렬하지만, 컨버터는 목록에서 조건이 맞는 첫 번째가 선택된다. 인자 리졸버와 반환값 핸들러도 같다. 그래서 세 목록 모두에서 조건이 넓은 구현체를 앞에 넣으면 뒤의 구현체들이 조용히 가려진다. 무엇을 추가했는데 동작하지 않는다면, 그것이 호출되는지보다 그 앞에서 누가 먼저 손을 들었는지를 확인하는 것이 빠르다.

    "415는 본문이 잘못된 것이고 406은 URL이 잘못된 것이다"

    둘 다 본문의 내용이나 URL과는 관계가 없다. 415는 요청의 Content-Type 선언과 서버가 읽을 수 있는 형식이 맞지 않는 것이고, 406은 요청의 Accept 선언과 서버가 만들 수 있는 형식이 맞지 않는 것이다. 내용이 깨진 것은 400이다. 멀쩡한 JSON을 보내고 415를 받았다면 헤더를 본다. 헤더가 없으면 application/octet-stream으로 간주된다는 것도 함께 기억하자.

    "@RequestBody는 폼 데이터도 객체로 받아 준다"

    기본 컨버터 목록의 폼 컨버터는 MultiValueMap 타입만 맡는다. 사용자 정의 객체를 @RequestBody로 선언하고 application/x-www-form-urlencoded 본문을 보내면, 그 조합을 읽겠다는 컨버터가 없어 415가 난다. 폼 데이터를 객체로 받는 길은 @ModelAttribute이고, 그 길은 메시지 컨버터가 아니라 요청 파라미터와 바인더를 쓴다. 두 애노테이션은 비슷해 보이지만 목록의 다른 칸에 있는 다른 부품이다.

    "한글이 깨지면 브라우저 설정 문제다"

    응답 바이트를 보면 구분된다. 본문에 3f가 들어 있다면 서버가 한글을 표현할 수 없는 문자 집합으로 인코딩하면서 이미 정보를 잃은 것이다. 받는 쪽에서 고칠 수 없다. 바이트는 UTF-8로 맞게 나갔는데 화면이 깨진다면 Content-Type의 charset이 빠졌거나 틀려서 받는 쪽이 다른 문자 집합으로 해석한 것이다. 앞의 경우는 컨버터의 기본 문자 집합이나 produces를 고치고, 뒤의 경우는 헤더를 고친다.

    "사용자 정의 리졸버를 등록하면 내장 동작을 바꿀 수 있다"

    addArgumentResolvers로 넣은 리졸버는 내장 묶음 뒤에 들어간다. @RequestParam이 붙은 파라미터의 처리 방식을 바꾸려고 리졸버를 만들어 등록해도 질문조차 받지 못한다. 반대 방향의 함정도 있다. 등록을 빠뜨리면 오류 없이 마지막 그물로 떨어져, 서버가 채워야 할 객체가 요청 파라미터로 채워진다. 리졸버가 맡는 타입에는 전용 애노테이션을 만들어 붙이고 supportsParameter에서 애노테이션과 타입을 함께 검사해 두면, 적어도 코드를 읽는 사람이 그 파라미터가 특별한 경로로 채워진다는 것을 알 수 있다.

    다른 주제와의 연결

    HTTP 권과의 연결. 이 회차의 실험은 「HTTP 웹 기본 지식」 권에서 규칙으로 배운 것들이 서버 코드의 어느 줄에서 실행되는지를 보여 준다. 조건부 요청과 304는 ResourceHttpRequestHandler의 수정 시각 비교였다. 콘텐츠 협상은 writeWithMessageConverters가 Accept 목록과 컨버터가 만들 수 있는 목록의 교집합을 구하는 일이었다. 표현 헤더 Content-Type은 읽을 때는 컨버터를 고르는 열쇠였고 쓸 때는 컨버터가 채우는 값이었다. Content-Length와 청크 전송은 컨버터가 길이를 미리 아는지, 그리고 응답이 언제 커밋되는지에 달려 있었다.

    다음 회차. 08회에서는 세 갈래 중 뷰 템플릿 길로 실제 화면을 만든다. 컨트롤러가 문자열을 반환하고 ViewNameMethodReturnValueHandler가 그것을 뷰 이름으로 적는 과정은 그대로이고, 그 위에 템플릿 문법과 폼 처리, 리다이렉트가 올라간다. 13번 핸들러의 소스에는 뷰 이름이 리다이렉트를 뜻하는지 검사하는 줄이 있는데, 그 의미는 다음 회차의 PRG 패턴에서 드러난다.

    뒤의 권. 이 회차에서 상태 코드가 된 예외들은 모두 DispatcherServlet의 예외 리졸버가 바꾼 것이다. API의 오류 응답 본문을 원하는 형식으로 만드는 방법, 인자 리졸버를 로그인 사용자 주입 같은 일에 쓰는 방법, @RequestBody 객체를 검증하는 방법, 그리고 요청 파라미터의 문자열을 객체로 바꾸는 타입 컨버터는 「스프링 MVC 2편」 권의 주제다. 이름이 비슷한 타입 컨버터와 메시지 컨버터를 미리 구분해 두자. 타입 컨버터는 문자열 하나를 값 하나로 바꾸며 @RequestParam·@ModelAttribute 길에서 쓰이고, 메시지 컨버터는 본문 전체를 객체와 맞바꾸며 @RequestBody·@ResponseBody 길에서 쓰인다.

    서버 밖에서. HttpMessageConverter는 서블릿 API를 모르고 헤더와 스트림만 안다고 했다. 그래서 같은 컨버터가 HTTP 클라이언트에서도 쓰인다. 다른 서버를 호출하는 RestClient나 RestTemplate은 보낼 객체를 컨버터의 write로 요청 본문에 쓰고, 받은 응답 본문을 컨버터의 read로 객체로 바꾼다. 방향만 반대이고 "자바 타입과 미디어 타입 두 조건으로 목록에서 첫 번째를 고른다"는 규칙은 같다.

    이 장의 핵심

    RequestMappingHandlerAdapter는 목록 세 개를 가진 객체다. 인자 리졸버 목록이 파라미터를 채우고, 리플렉션이 메서드를 호출하고, 반환값 핸들러 목록이 결과를 뷰 이름이나 응답 본문으로 바꾼다. 메시지 컨버터 목록은 그중 본문을 통째로 다루는 두 프로세서가 쓴다. 세 목록 모두 "앞에서부터 물어 처음 손든 것이 맡는다"는 한 가지 규칙으로 움직이고, 애노테이션의 생략 규칙, @ResponseBody의 효과, 406과 415의 원인은 모두 이 규칙과 목록의 순서에서 나온다.
    응답 본문의 세 갈래
    정적 리소스는 ResourceHttpRequestHandler가 파일 바이트를 그대로, 뷰 템플릿은 ViewResolver가 찾은 View가 모델로 만든 HTML을, HTTP API는 HttpMessageConverter가 반환값을 바이트로 바꿔 쓴다. 정적 리소스는 핸들러 조회 단계에서, 뷰와 메시지 바디는 어댑터의 반환값 처리 단계에서 갈린다.
    정적 리소스 핸들러의 자리
    /** 패턴이어도 컨트롤러를 가리지 않는다. 리소스 핸들러 매핑의 순서 값이 Ordered.LOWEST_PRECEDENCE - 1로 거의 맨 끝이어서, 순서 0인 RequestMappingHandlerMapping이 맡지 않은 요청만 받는다. 조건부 요청(304), 경로 검사, 없는 파일의 404도 이 핸들러가 처리한다.
    String 반환의 두 뜻
    반환값 핸들러 목록에서 @ResponseBody를 보는 RequestResponseBodyMethodProcessor가 ViewNameMethodReturnValueHandler보다 앞에 있다. 그래서 애노테이션이 있으면 본문, 없으면 뷰 이름이 된다. @RestController는 @Controller와 @ResponseBody를 묶은 메타 애노테이션이다.
    HttpMessageConverter 계약
    canRead·canWrite가 자바 타입과 미디어 타입 두 조건을 함께 보고, read·write는 헤더와 바이트 스트림만 다룬다. 기본 목록은 타입 조건이 좁은 컨버터(byte[], String)가 앞에, 넓은 JSON 컨버터가 뒤에 있다.
    쓰기 컨버터 선택
    이미 정해진 Content-Type이 없으면 Accept와 "이 타입으로 만들 수 있는 미디어 타입"의 교집합을 구하고, 구체적인 첫 타입을 고른 뒤, 그 타입으로 canWrite가 참인 첫 컨버터를 쓴다. 교집합이 비면 406이며 이때 컨트롤러 메서드는 이미 실행된 뒤다.
    읽기 컨버터 선택과 400·415
    요청의 Content-Type(없으면 application/octet-stream)과 파라미터 타입으로 canRead가 참인 첫 컨버터를 고른다. 없으면 415, 컨버터가 해석에 실패하거나 필수 본문이 비면 400이다. 매핑의 consumes·produces 조건이 어긋나면 같은 415·406이 핸들러 조회 단계에서 먼저 난다.
    문자 집합과 본문 길이
    StringHttpMessageConverter의 기본 문자 집합은 ISO-8859-1이어서 charset 없이 한글을 쓰면 서버에서 ?(0x3f)로 손실된다. 스프링 부트는 이 컨버터를 UTF-8로 만든다. 길이를 미리 아는 컨버터는 Content-Length를 넣고, 모르는 경우는 서블릿 컨테이너가 버퍼 크기로 길이를 정하거나 청크 전송을 쓴다.
    RequestMappingHandlerAdapter의 세 목록
    인자 리졸버 목록이 파라미터 값을 만들고, 리플렉션으로 메서드를 호출하고, 반환값 핸들러 목록이 결과를 ModelAndViewContainer에 적거나 응답에 직접 쓴다. 메시지 컨버터는 RequestResponseBodyMethodProcessor와 HttpEntityMethodProcessor가 읽기·쓰기 양쪽에서 부른다. 본문을 직접 썼다는 표시가 켜지면 어댑터는 ModelAndView 대신 null을 돌려준다.
    마지막 그물과 리졸버 캐시
    애노테이션 없는 파라미터는 목록 끝의 RequestParamMethodArgumentResolver(true)와 ServletModelAttributeMethodProcessor(true)가 받는다. 사용자 정의 리졸버는 내장 묶음 뒤, 마지막 그물 앞에 들어가며, 파라미터마다 한 번 찾은 리졸버는 캐시되어 요청마다 다시 묻지 않는다.

    실무에서 다시 판단하면, 응답 형식이 정해진 API는 매핑에 produces를 적어 두는 쪽이 안전하다. 협상이 반환값 처리 단계에서 실패하면 컨트롤러 메서드는 이미 실행된 뒤라서, 저장이나 외부 호출 같은 부수 효과는 일어났는데 클라이언트는 406을 받는다. 클라이언트가 같은 요청을 다시 보내면 부수 효과가 한 번 더 일어난다. produces가 있으면 같은 요청이 핸들러 조회 단계에서 걸러져 메서드에 닿지 않는다. 반대로 같은 자원을 여러 형식으로 내려 줘야 하는 API라면 produces를 비워 두고 컨버터 목록의 협상에 맡기되, 기본 형식이 무엇이 될지는 목록의 순서가 정한다는 점을 설계에 넣어야 한다.

    메시지 컨버터를 손댈 때 판단을 가르는 것은 "추가했는가"가 아니라 "몇 번째에 있는가"다. 사용자 정의 컨버터를 목록 맨 앞에 넣으면 Accept를 보내지 않거나 */*를 보내는 클라이언트의 기본 응답 형식이 바뀐다. 기존 클라이언트가 JSON을 기대하고 있었다면 배포 직후 파싱 오류가 쏟아진다. configureMessageConverters에 하나만 넣으면 기본 컨버터가 모두 빠진다는 것도 같은 종류의 사고다. 변경 뒤에는 RequestMappingHandlerAdapter의 getMessageConverters()를 출력해 순서를 확인하는 테스트를 두자. Spring Framework 7로 올라가면 JSON 컨버터의 클래스가 Jackson 3용으로 바뀌므로, 클래스 이름으로 컨버터를 찾아 위치를 옮기는 코드는 다시 점검해야 한다.

    장애를 진단할 때는 상태 코드와 함께 "컨트롤러 메서드가 실행되었는가"를 먼저 본다. 415·400이면 메서드는 실행되지 않았고 원인은 요청 헤더나 본문이다. 406이면 매핑 단계인지 반환값 단계인지를 응답에 실린 지원 타입 목록으로 구분한다. 한글이 깨졌다는 신고에는 응답 바이트를 직접 확인한다. 3f가 보이면 서버가 이미 정보를 잃은 것이니 서버의 문자 집합을 고치고, UTF-8 바이트가 맞게 나갔다면 Content-Type의 charset을 고친다.

    인자 리졸버를 직접 만들 때는 등록이 빠졌을 때의 동작까지 생각해야 한다. 리졸버가 맡을 타입이 애노테이션 없는 일반 객체라면, 등록이 빠진 환경에서는 오류 없이 마지막 그물이 요청 파라미터로 그 객체를 채운다. 서버가 인증 정보나 연결 정보에서 채워야 하는 값을 클라이언트가 쿼리 스트링으로 정할 수 있게 되는 셈이다. 전용 애노테이션을 붙여 의도를 드러내고, 리졸버가 실제로 그 파라미터를 맡는지 확인하는 테스트를 함께 두는 것이 이 위험을 줄이는 방법이다.

    2번. (a)와 (b)는 CSV 컨버터가 text/csv;charset=UTF-8로 P-100,3을 쓴다. 쓰기 3단계에서 목록을 앞에서부터 돌며 "만들 수 있는 미디어 타입"을 모으므로 text/csv가 application/json보다 앞에 놓인다. Accept가 없거나 */*이면 모두 호환되고, text/csv와 application/json은 서로보다 구체적이라고 할 수 없어 정렬 뒤에도 순서가 유지되므로 첫 구체 타입 text/csv가 선택된다. 6단계에서도 CSV 컨버터가 먼저 손을 든다. (c)는 교집합에 application/json만 남으므로 CSV 컨버터는 미디어 타입 조건에서 탈락하고 JSON 컨버터가 {"code":"P-100","weight":3}을 쓴다. 이 결과는 실험 환경(7.0.10)에서 직접 확인했다. 폼 본문 요청은 415다. 폼 컨버터는 MultiValueMap만 맡고, CSV·JSON 컨버터는 Parcel 타입은 받지만 미디어 타입 application/x-www-form-urlencoded에서 탈락한다. 오류 응답의 Accept 헤더에는 Parcel을 읽을 수 있는 컨버터들의 지원 타입을 목록 순서대로 모은 text/csv, application/json, application/*+json이 실린다.

    3번. 서버 A는 바이트를 만드는 순간에 정보를 잃었다. 문자열 컨버터가 charset 없는 미디어 타입을 받아 기본 문자 집합 ISO-8859-1로 인코딩했고, 이 문자 집합에 없는 "접", "수"가 대체 문자 ?(0x3f)가 되었다. 받는 쪽에서 어떤 문자 집합으로 해석해도 복원할 수 없으므로 서버를 고쳐야 한다. produces에 charset=UTF-8을 적거나, 문자열 컨버터를 UTF-8로 만들어 등록한다(부트는 기본으로 그렇게 한다). 서버 B는 바이트가 UTF-8로 올바르게 나갔다. "접"이 ec a0 91, "수"가 ec 88 98이다. 문제는 헤더가 문자 집합을 알리지 않아 받는 쪽이 다른 문자 집합으로 해석한 것이다. Content-Type에 charset=UTF-8이 실리도록 응답 헤더를 고친다.

    4번. tenant.id()는 "other"다. Tenant를 맡겠다는 리졸버가 없으므로 질문은 목록 끝까지 내려가고, 단순 타입이 아닌 파라미터를 받는 마지막 그물 ServletModelAttributeMethodProcessor(true)가 손을 든다. 이 프로세서는 Tenant를 @ModelAttribute 객체로 보고 요청 파라미터 id의 값으로 레코드를 만든다. X-Tenant 헤더는 아무도 읽지 않는다. 마지막 그물이 정상적으로 값을 만들었으니 예외가 날 이유가 없다. 본문의 Caller 실험에서 같은 일이 일어났다. 줄이는 방법은 첫째, 리졸버가 맡는 파라미터에 전용 애노테이션(예: @CurrentTenant)을 붙이고 supportsParameter에서 애노테이션과 타입을 함께 검사하는 것이다. 애노테이션만 붙어 있고 리졸버가 없으면 여전히 마지막 그물로 떨어지지만, 코드를 읽는 사람에게 특별한 경로라는 사실이 드러나고 검사하기 쉬워진다. 둘째, 모듈마다 헤더와 파라미터를 다르게 준 요청을 보내 값의 출처를 확인하는 테스트를 두는 것이다.

     @RestController 클래스에 @GetMapping("/home") String home() { return "home"; }이 있고, 템플릿 디렉터리에 home.html이 있다. 기본 컨버터 목록에서 Accept 없이 요청하면 응답은 어떻게 되는가? home.html 템플릿이 렌더링된다 본문이 따옴표 없는 home이고 Content-Type은 text/plain 계열이다 본문이 JSON 문자열 "home"이다 반환값을 처리할 핸들러가 없어 예외가 난다 @RestController는 클래스에 @ResponseBody를 붙인 것과 같다. 반환값 핸들러 목록에서 @ResponseBody를 보는 RequestResponseBodyMethodProcessor가 뷰 이름 핸들러보다 앞에 있으므로 문자열은 뷰 이름이 아니라 본문이 된다. 컨버터 목록에서는 String을 받는 문자열 컨버터가 JSON 컨버터보다 앞에 있어 따옴표 없이 그대로 쓴다. 템플릿을 렌더링하려면 ModelAndView를 반환하거나 @Controller를 써야 한다. @ResponseBody Parcel을 반환하는 메서드가 반환 직전에 DB에 접수 기록을 저장한다. 매핑에 produces는 없다. 클라이언트가 Accept: text/plain으로 요청했다. 맞는 설명은? 핸들러 조회 단계에서 406이 나므로 저장은 일어나지 않는다 메서드가 실행되어 저장까지 끝난 뒤, 반환값 처리 단계에서 406이 난다 요청 본문 형식이 맞지 않아 415가 난다 문자열 컨버터가 Parcel의 toString()을 써서 200이 된다 produces가 없으므로 매핑 단계에서는 걸러지지 않는다. 협상은 반환값을 쓰는 writeWithMessageConverters에서 일어나고, Parcel을 쓸 수 있는 컨버터는 JSON 컨버터뿐이라 text/plain과 교집합이 없어 406이 된다. 그 시점에 메서드는 이미 실행되었다. 문자열 컨버터는 String 타입만 맡으므로 Parcel에 손을 들지 않는다. 415는 요청 본문을 읽을 때의 오류다. 문법상 올바른 JSON 본문을 @RequestBody Parcel을 받는 POST 메서드에 보냈는데 "Content-Type 'application/octet-stream' is not supported"와 함께 415를 받았다. 가장 가능성 높은 원인은? JSON 본문의 필드 이름이 레코드 컴포넌트와 달라서 요청에 Content-Type 헤더가 없어서 application/octet-stream으로 간주되었고, 그 미디어 타입으로 Parcel을 읽을 컨버터가 없어서 요청에 Accept 헤더가 없어서 byte[] 컨버터가 본문을 먼저 읽어 버려서 읽기 과정은 Content-Type이 없으면 application/octet-stream으로 간주한다. JSON 컨버터는 타입 조건은 맞지만 미디어 타입 조건에서 탈락하고, byte[] 컨버터는 파라미터 타입이 byte[]가 아니어서 손을 들지 않는다. 손든 컨버터가 없으므로 415다. 필드 이름 불일치는 컨버터가 선택된 뒤의 문제이고, Accept는 응답 쪽 협상에 쓰인다. 모든 @RequestParam String 값의 앞뒤 공백을 지우려고 그 파라미터를 맡는 리졸버를 만들어 addArgumentResolvers로 등록했는데 아무 효과가 없다. 이유는? 사용자 정의 리졸버는 내장 리졸버들 뒤에 들어가므로, 목록 앞쪽의 RequestParamMethodArgumentResolver가 먼저 손을 들어 사용자 정의 리졸버는 질문조차 받지 못한다 리졸버 캐시 때문에 첫 요청에서만 동작하고 그 뒤로는 무시된다 사용자 정의 리졸버는 마지막 그물 뒤에 들어가므로 아무 파라미터도 맡을 수 없다 인자 리졸버는 String 타입을 반환할 수 없다 addArgumentResolvers로 추가한 리졸버는 애노테이션 기반·타입 기반 내장 묶음 뒤, 마지막 그물 앞에 들어간다. @RequestParam이 붙은 파라미터는 목록 첫 번째인 RequestParamMethodArgumentResolver(false)가 맡는다. 캐시는 "누가 맡는가"의 답을 저장할 뿐이고 그 답은 처음부터 내장 리졸버였다. 마지막 그물보다 앞에 있으므로 애노테이션 없는 새 타입은 맡을 수 있다. Javadoc도 내장 동작을 바꾸려면 RequestMappingHandlerAdapter를 직접 설정하라고 안내한다. @ResponseBody 메서드의 요청에서 뷰 리졸버가 호출되지 않는 직접적인 이유는? DispatcherServlet이 핸들러 메서드의 @ResponseBody 애노테이션을 검사해 렌더링 단계를 건너뛴다 메시지 컨버터가 쓰기를 마치면서 응답을 커밋하므로 뷰 리졸버가 실행될 수 없다 반환값 핸들러가 ModelAndViewContainer에 처리 완료 표시를 남기고, 어댑터가 그 표시를 보고 ModelAndView 대신 null을 돌려준다 @ResponseBody 메서드는 HttpRequestHandlerAdapter가 실행하므로 뷰가 없다 RequestResponseBodyMethodProcessor.handleReturnValue는 첫 줄에서 setRequestHandled(true)를 부르고 본문을 쓴다. 어댑터는 이 표시가 켜져 있으면 null을 반환하고, DispatcherServlet은 null이면 뷰를 찾지도 그리지도 않는다. DispatcherServlet은 애노테이션을 보지 않는다. 커밋은 원인이 아니다. 7.0.10 실험에서는 @ResponseBody 응답이 postHandle 시점에 커밋되지 않았는데도 뷰가 그려지지 않았다. HttpRequestHandlerAdapter는 정적 리소스 핸들러 같은 HttpRequestHandler를 실행한다.
    메시지 컨버터(HttpMessageConverter)
    HTTP 요청·응답 본문과 자바 객체 사이를 변환하는 전략 인터페이스. 자바 타입과 미디어 타입 두 조건으로 읽기·쓰기 가능 여부를 답하고, 헤더와 바이트 스트림만 다루므로 서버와 HTTP 클라이언트에서 함께 쓰인다.
    미디어 타입(media type)
    text/plain, application/json처럼 본문의 형식을 나타내는 값. Content-Type과 Accept 헤더에 실리며, charset 같은 매개변수와 */* 같은 와일드카드를 가질 수 있다.
    콘텐츠 협상(content negotiation)
    같은 자원에 대해 클라이언트가 원하는 표현을 고르는 과정. 스프링 MVC에서는 Accept 목록과 반환 타입으로 만들 수 있는 미디어 타입 목록의 교집합에서 하나를 고르는 일로 구현된다.
    인자 리졸버(HandlerMethodArgumentResolver)
    컨트롤러 메서드의 파라미터 하나에 넣을 값을 만드는 전략 인터페이스. supportsParameter로 맡을지 답하고 resolveArgument로 값을 만든다.
    반환값 핸들러(HandlerMethodReturnValueHandler)
    컨트롤러 메서드의 반환값을 처리하는 전략 인터페이스. 뷰 이름과 모델을 ModelAndViewContainer에 적거나, 응답에 직접 쓰고 처리 완료 표시를 남긴다.
    ModelAndViewContainer
    핸들러 메서드 하나를 실행하는 동안 모델, 뷰 이름, 처리 완료 표시를 담아 두는 요청 단위 객체. 어댑터는 실행이 끝나면 이것으로 ModelAndView를 만들거나 null을 돌려준다.
    정적 리소스(static resource)
    서버가 가공하지 않고 파일의 바이트를 그대로 내려 주는 응답 대상. 스프링 MVC에서는 ResourceHttpRequestHandler가 처리한다.
    문자 집합(charset)
    문자를 바이트로 바꾸는 규칙. Content-Type의 charset 매개변수로 상대에게 알리며, 표현할 수 없는 문자는 인코딩 단계에서 대체 문자로 바뀌어 정보가 사라진다.
