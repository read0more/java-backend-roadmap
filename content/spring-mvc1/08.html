    이 회차의 질문: 화면 네 개를 만드는 동안 무엇이 움직이는가

    앞의 세 회차에서 스프링 MVC의 부품을 하나씩 보았다. 요청이 DispatcherServlet을 지나 핸들러 메서드에 닿는 경로, 요청 파라미터와 본문을 읽는 방법, 응답을 뷰나 메시지 컨버터로 내보내는 방법이다. 이 회차는 그 부품을 모아 상품을 관리하는 작은 웹 페이지를 만든다. 목록, 상세, 등록 폼, 수정 폼 네 화면이 전부이고 코드도 짧다.

    그런데 이 짧은 코드가 돌아가는 동안 아래에서는 꽤 많은 일이 일어난다. 저장소 객체 하나를 톰캣의 여러 작업 스레드가 동시에 건드리고, 브라우저가 보낸 문자열 몇 개가 리플렉션으로 자바 객체가 되고, 저장 한 번에 HTTP 요청이 두 번 오간다. 화면이 잘 뜨는 것만 확인하고 넘어가면 이 부분이 보이지 않는다. 이 회차가 답하려는 질문은 다음과 같다.

    • 정적 HTML 파일과 템플릿은 서버 안에서 각각 누가 처리하는가. 템플릿은 언제 읽히고, 언제 다시 읽히지 않는가.
    • 메모리에 둔 저장소는 왜 동시 요청에서 깨지는가. 어떤 연산 사이에 다른 스레드가 끼어드는가.
    • 폼 전송은 네트워크에 어떤 바이트로 나가고, 그 문자열은 어떤 순서로 객체의 필드에 들어가는가.
    • 저장한 뒤 새로고침을 누르면 왜 상품이 하나 더 생기는가. 리다이렉트는 이 문제를 어떻게 끊는가.
    • 리다이렉트로 요청이 둘로 갈라지면, 앞 요청의 데이터는 무엇에 실어 뒤 요청으로 넘기는가.
    이 회차의 실행 결과, HTTP 메시지, 호출 스택, 바이트코드는 원고를 쓰면서 JDK 21.0.13(Temurin), Spring Framework 7.0.10, 임베디드 톰캣 11.0.27에서 직접 돌려 얻었다. 스프링 부트와 타임리프는 붙이지 않았다. 뷰가 있을 자리에는 "어떤 템플릿 경로로 어떤 모델을 받았는지"를 텍스트로 출력하는 확인용 뷰를 두었고, HTTP 메시지는 curl 8.7.1로 주고받았다. 이 강좌의 기준은 Spring Framework 6.x이므로 규칙은 6.2 레퍼런스와 6.2.x 소스로 다시 확인했고, 버전에 따라 다른 곳은 따로 적었다. 타임리프 템플릿 예제는 실행해 보지 못했으며, 타임리프 3.1 공식 튜토리얼이 설명하는 문법 범위 안에서만 썼다.

    프로젝트 생성: 의존성 두 개가 대신 등록해 주는 것

    스프링 부트 프로젝트에 웹 스타터(spring-boot-starter-web)와 타임리프 스타터(spring-boot-starter-thymeleaf)를 넣으면 준비가 끝난다. 패키징은 Jar다. 이 두 줄을 "라이브러리를 받아 온다" 정도로만 이해하면, 나중에 파일을 엉뚱한 폴더에 두고 화면이 왜 안 뜨는지 헤매게 된다. 의존성이 클래스패스에 올라오면 부트의 자동 구성(auto-configuration)이 그것을 감지해 객체 몇 개를 스프링 빈으로 등록한다. 그 결과 프로젝트의 폴더 두 개가 서로 다른 의미를 갖게 된다.

    위치브라우저에서의 접근처리하는 객체용도
    src/main/resources/static/파일 경로가 곧 URL이 된다ResourceHttpRequestHandlerCSS, 이미지, 내용이 고정된 HTML
    src/main/resources/templates/직접 접근할 수 없다. 컨트롤러가 뷰 이름으로 지목해야 한다타임리프 뷰 리졸버가 만든 뷰요청마다 내용이 달라지는 화면

    첫 줄은 부트 레퍼런스가 밝히는 기본 동작이다. 부트는 클래스패스의 /static(또는 /public, /resources, /META-INF/resources) 디렉터리에서 정적 콘텐츠를 내려 주고, 이 일에 스프링 MVC의 ResourceHttpRequestHandler를 쓴다. 매핑 패턴의 기본값은 /**다. 그래서 static/css/app.css라는 파일은 /css/app.css라는 URL로 열린다.

    둘째 줄도 문서에 있다. 부트가 자동 구성하는 템플릿 엔진을 기본 설정으로 쓰면 템플릿은 src/main/resources/templates에서 찾는다. 타임리프의 경우 부트의 설정 클래스(ThymeleafProperties)에 기본값이 적혀 있다. 접두사 classpath:/templates/, 접미사 .html, 모드 HTML, 인코딩 UTF-8, 캐시 사용(spring.thymeleaf.cache=true)이다. 컨트롤러가 "products/list"라는 문자열을 돌려주면 접두사와 접미사가 앞뒤에 붙어 classpath:/templates/products/list.html이 된다. 05회에서 본 뷰 리졸버의 "논리 이름을 실제 위치로 바꾸기"가 여기서 일어난다.

    경로 앞의 classpath:는 운영체제의 파일 경로가 아니라 클래스 로더가 찾아 주는 리소스라는 뜻이다. 빌드하면 src/main/resources 아래의 파일은 컴파일된 클래스와 함께 Jar 안에 들어가고, 실행 중에는 클래스 로더가 Jar 안에서 그 파일을 꺼낸다. 개발 중에 IDE로 돌릴 때와 Jar 하나로 배포했을 때 같은 설정으로 동작하는 이유다. 반대로 서블릿 시절에 쓰던 src/main/webapp은 Jar 패키징에서 쓰면 안 된다. 부트 레퍼런스는 이 디렉터리가 War 패키징에서만 동작하고, Jar를 만들 때는 대부분의 빌드 도구가 조용히 무시한다고 경고한다.

    첫 화면도 자동 구성이 챙긴다. 부트는 정적 콘텐츠 위치에서 index.html을 먼저 찾고, 없으면 index라는 이름의 템플릿을 찾아 웰컴 페이지로 쓴다. 문서의 표현대로 이것은 대체 수단(fallback)이어서, 애플리케이션이 루트 경로를 직접 매핑하면 그쪽이 쓰인다.

    요구사항 분석: 화면보다 요청 표를 먼저 그린다

    만들 것은 상품 관리 화면이다. 상품은 이름, 가격, 수량을 가진다. 상품 목록을 보고, 하나를 골라 상세를 보고, 새 상품을 등록하고, 기존 상품을 수정할 수 있어야 한다. 요구사항을 들으면 화면 그림부터 떠올리기 쉽지만, 서버 입장에서 요구사항은 "어떤 요청이 들어오고 각각에 무엇으로 답하는가"의 목록이다. 화면 네 개는 요청 여섯 가지로 풀린다.

    기능메서드URL서버가 하는 일응답
    상품 목록GET/products전체 조회목록 화면(HTML)
    상품 상세GET/products/{productId}한 건 조회상세 화면(HTML)
    등록 폼GET/products/new없음빈 폼(HTML)
    등록 처리POST/products/new저장상세 화면으로 리다이렉트
    수정 폼GET/products/{productId}/edit한 건 조회값이 채워진 폼(HTML)
    수정 처리POST/products/{productId}/edit수정상세 화면으로 리다이렉트

    이 표에서 읽어 둘 것이 네 가지 있다. 첫째, 조회는 모두 GET이고 서버의 상태를 바꾸는 요청은 모두 POST다. RFC 9110은 GET을 안전한(safe) 메서드로 정의하고, 안전하다는 것을 의미상 읽기 전용이라고 설명한다(§9.2.1). 브라우저, 프록시, 검색 로봇은 이 약속을 믿고 GET을 미리 가져오거나 다시 보낸다. 상태를 바꾸는 일을 GET에 걸어 두면 내가 누르지 않은 요청이 데이터를 바꾸게 된다.

    둘째, 등록 폼과 등록 처리가 같은 URL을 쓴다. "새 상품 등록"이라는 한 가지 일에 대해 GET은 폼을 달라는 요청이고 POST는 폼을 처리해 달라는 요청이다. 06회에서 본 것처럼 스프링의 매핑 표는 URL만이 아니라 HTTP 메서드까지 조건으로 삼으므로 두 요청은 서로 다른 메서드로 간다. URL을 하나로 두면 폼의 action을 따로 관리할 필요가 줄고, 주소만 봐도 두 요청이 한 쌍임을 알 수 있다.

    셋째, POST 두 건의 응답은 화면이 아니라 리다이렉트다. 저장을 끝낸 자리에서 바로 상세 화면을 그려 줘도 될 것 같은데 왜 한 번 돌려보내는가가 이 회차 후반부의 주제다.

    넷째, /products/new는 /products/{productId} 패턴에도 맞는다. new라는 글자를 상품 ID로 읽을 수도 있기 때문이다. 두 패턴이 모두 맞으면 스프링은 더 구체적인 쪽을 고른다. 실험에서 GET /products/new는 등록 폼 메서드로 갔다. 만약 등록 폼 매핑이 없다면 이 요청은 상세 메서드로 가고, "new"를 Long으로 바꾸지 못해 400으로 끝난다. 경로를 설계할 때 고정 글자와 변수가 같은 자리에 오는지 확인해 두어야 하는 이유다.

    [상품 목록]  GET /products
   │
   ├─ "상품 등록" 링크 ──▶ [등록 폼]  GET /products/new
   │                           │ "저장" 버튼
   │                           ▼
   │                      POST /products/new ── 저장 ── 302 ──▶ [상품 상세]
   │
   └─ 상품 ID 링크 ────▶ [상품 상세]  GET /products/{productId}
                               │ "수정" 링크
                               ▼
                          [수정 폼]  GET /products/{productId}/edit
                               │ "저장" 버튼
                               ▼
                          POST /products/{productId}/edit ── 수정 ── 302 ──▶ [상품 상세]
    네 화면을 상자로 놓고 그 사이를 GET 화살표와 POST 화살표로 잇는다. POST 두 개는 화면으로 바로 가지 않고 302를 거쳐 상세 화면으로 돌아간다는 점이 눈에 띄어야 한다. 깔끔한 기술 문서용 평면 흐름도. 흰 배경. 둥근 사각형 네 개를 마름모꼴로 배치한다. 왼쪽에 "상품 목록", 위쪽 가운데에 "등록 폼", 오른쪽에 "상품 상세", 아래쪽 가운데에 "수정 폼". 파란 실선 화살표(조회)를 그린다: "상품 목록"에서 "등록 폼"으로 라벨 "GET /products/new", "상품 목록"에서 "상품 상세"로 라벨 "GET /products/{id}", "상품 상세"에서 "수정 폼"으로 라벨 "GET /products/{id}/edit". 주황 굵은 화살표(변경)를 그린다: "등록 폼"에서 나와 작은 원 "저장"을 거쳐 "상품 상세"로 들어가며 라벨 "POST /products/new → 302", "수정 폼"에서 나와 작은 원 "수정"을 거쳐 "상품 상세"로 들어가며 라벨 "POST /products/{id}/edit → 302". 오른쪽 아래 범례에 파란 선 "GET: 화면을 받는다", 주황 선 "POST: 상태를 바꾸고 리다이렉트". 색은 파랑, 주황, 회색만 쓴다. 화면은 넷이지만 요청은 여섯이다. 상태를 바꾸는 POST 두 건은 화면을 직접 그리지 않고 상세 화면으로 돌려보낸다.

    상품 도메인 개발: 힙에 하나뿐인 저장소를 여러 스레드가 쓴다

    상품을 나타내는 클래스부터 만든다. 필드 네 개와 기본 생성자, 필드마다 getter와 setter가 있는 평범한 클래스다.

    public class Product {
    private Long id;
    private String name;
    private Integer price;
    private Integer quantity;

    public Product() {}

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public Integer getPrice() { return price; }
    public void setPrice(Integer price) { this.price = price; }
    public Integer getQuantity() { return quantity; }
    public void setQuantity(Integer quantity) { this.quantity = quantity; }
}

    이 모양에는 이유가 있다. 뒤에서 볼 데이터 바인더는 기본 생성자로 객체를 만든 다음 setter를 불러 값을 넣고, 템플릿 엔진은 getter를 불러 값을 읽는다. 둘 다 "getName/setName이 있으면 name이라는 프로퍼티가 있다"는 자바빈(JavaBeans) 규약으로 객체를 다룬다. 가격과 수량을 int가 아니라 Integer로 둔 것은 "아직 입력되지 않음"을 null로 나타내기 위해서다. 이 선택이 바인딩 결과를 어떻게 바꾸는지는 등록 처리에서 실험으로 확인한다.

    첫 번째 저장소: 요청이 겹치면 깨진다

    데이터베이스는 뒤의 권에서 붙이므로 지금은 메모리에 저장한다. 맵 하나와 ID를 만들 숫자 하나면 된다. 가장 먼저 떠오르는 구현은 다음과 같다. 실험을 단순하게 하려고 값의 타입만 문자열로 바꿨다.

    static class UnsafeStore {
    private final Map store = new HashMap<>();
    private long sequence = 0L;

    long save(String name) {
        long id = ++sequence;
        store.put(id, name);
        return id;
    }
}

    혼자 요청을 보내 보면 아무 문제가 없다. 문제는 이 객체가 놓이는 자리다. 저장소를 스프링 빈으로 등록하면 컨테이너는 객체를 하나만 만들고(싱글톤), 컨트롤러도 하나만 만들어 그 저장소를 주입한다. 01회에서 본 대로 톰캣은 요청마다 스레드 풀의 작업 스레드를 하나 배정한다. 요청 두 개가 겹치면 스레드 두 개가 힙에 있는 같은 저장소 객체의 save를 동시에 실행한다. 각 스레드의 스택에는 지역 변수 id가 따로 있지만 sequence와 store는 힙에 하나뿐이다.

    고친 저장소와 그래도 남는 것

    증가 연산과 맵을 각각 동시 접근용 클래스로 바꾼다. AtomicLong.incrementAndGet()은 Javadoc 표현대로 현재 값을 원자적으로(atomically) 증가시킨다. 읽기, 더하기, 쓰기가 다른 스레드가 사이에 끼어들 수 없는 한 동작처럼 수행된다는 뜻이다. ConcurrentHashMap은 여러 스레드의 동시 읽기와 쓰기를 맵 내부에서 안전하게 처리한다. 같은 실험에서 이 조합은 세 번 모두 sequence = 400000, size = 400000이 나왔다.

    public class ProductStore {
    private final Map store = new ConcurrentHashMap<>();
    private final AtomicLong sequence = new AtomicLong();

    public Product save(Product product) {
        product.setId(sequence.incrementAndGet());
        store.put(product.getId(), product);
        return product;
    }

    public Product findById(Long id) {
        return store.get(id);
    }

    public List findAll() {
        return new ArrayList<>(store.values());
    }

    public void update(Long id, Product form) {
        Product product = store.get(id);
        product.setName(form.getName());
        product.setPrice(form.getPrice());
        product.setQuantity(form.getQuantity());
    }
}

    이것으로 "ID가 겹친다"와 "맵이 망가진다"는 막았다. 그러나 동시성 문제가 모두 사라진 것은 아니다. update를 보자. 맵에서 꺼낸 것은 상품 객체의 참조이고, 그 객체의 필드 세 개를 setter 세 번으로 바꾼다. 세 번의 쓰기는 한 덩어리가 아니다. 한 스레드가 이름만 바꾼 시점에 다른 스레드가 상세 화면을 그리려고 같은 객체를 읽으면 새 이름과 옛 가격이 섞인 상품을 보게 된다. 맵은 안전해졌지만 맵에 담긴 객체는 여전히 여러 스레드가 함께 쓰는 변경 가능한 객체다. findAll이 맵의 값 묶음을 그대로 돌려주지 않고 새 리스트에 복사하는 것도 같은 맥락이다. 호출한 쪽이 리스트를 고쳐도 저장소 내부에는 영향이 없다. 다만 리스트에 담긴 상품 객체는 여전히 저장소의 그 객체다.

    메모리 저장소의 한계는 이 밖에도 분명하다. 서버를 다시 띄우면 힙이 사라지므로 데이터도 사라지고, 서버를 두 대로 늘리면 저장소도 둘이 되어 서로 다른 목록을 보여 준다. 여러 필드의 수정을 한 덩어리로 만들고, 수정 중인 중간 상태를 다른 요청이 보지 못하게 하고, 서버가 죽어도 데이터가 남게 하는 일은 데이터베이스의 트랜잭션이 맡는다. 지금 단계에서는 "싱글톤 객체의 필드는 모든 요청 스레드가 공유한다"는 사실과, 그 필드를 고치는 연산이 한 덩어리인지 따져 보는 습관을 가져가면 된다.

    일상에서 가져온 비유번호표 기계와 공용 장부

    은행에 번호표 기계가 하나 있고 창구 직원 여럿이 공용 장부 한 권을 쓴다고 하자. 번호표 기계가 "지금 번호를 본다, 1을 더한다, 화면에 쓴다"를 따로따로 한다면 두 손님이 동시에 버튼을 눌렀을 때 같은 번호가 두 장 나온다. AtomicLong은 버튼 한 번에 이 세 동작이 끊기지 않고 끝나는 기계다. 다만 비유가 맞지 않는 곳이 있다. 은행에서는 사람이 같은 번호표를 보고 이상하다고 알아채지만, 프로그램은 아무 경고 없이 한쪽 데이터를 덮어쓰고 지나간다.

    상품 서비스 HTML: 정적 파일은 컨트롤러를 거치지 않는다

    화면은 처음부터 템플릿으로 만들지 않고 순수 HTML로 먼저 만들어 볼 수 있다. 목록, 상세, 등록 폼, 수정 폼을 각각 HTML 파일로 써서 static/html/products/ 아래에 두면, 서버를 띄운 뒤 /html/products/list.html 같은 주소로 바로 열린다. 컨트롤러를 하나도 만들지 않았는데 화면이 뜨는 이유는 앞에서 본 정적 콘텐츠 처리 때문이다.

    이 요청이 서버 안에서 지나는 길을 05회의 구조로 따라가 보자. 요청은 다른 요청과 똑같이 DispatcherServlet에 들어온다. DispatcherServlet은 핸들러 매핑들에게 차례로 이 URL을 처리할 핸들러가 있는지 묻는다. @RequestMapping 메서드 표에는 맞는 것이 없다. 순서가 가장 뒤쪽인 정적 리소스 매핑(7.0.10 소스에서 리소스 핸들러의 기본 순서 값은 Ordered.LOWEST_PRECEDENCE - 1이다)이 /** 패턴으로 이 요청을 받아 ResourceHttpRequestHandler를 돌려준다. 이 핸들러는 클래스패스의 static 아래에서 파일을 찾아 그 바이트를 응답 본문으로 내보낸다.

    여기에는 모델도, 뷰 리졸버도, 템플릿 엔진도 없다. 파일 내용이 그대로 나가므로 누가 언제 요청해도 같은 HTML이다. 상품 목록에 실제 상품을 넣으려면 서버가 요청을 받은 시점에 저장소를 조회해서 HTML을 만들어야 하는데, 정적 파일 처리 경로에는 그 일을 끼워 넣을 자리가 없다. 그래서 내용이 바뀌는 화면은 templates로 옮기고 컨트롤러를 거치게 한다.

    정적 폴더에 관해 하나 더 기억할 것이 있다. static 아래의 파일은 URL만 알면 누구나 받아 갈 수 있다. 로그인 여부를 검사하는 컨트롤러 코드도, 권한을 확인하는 로직도 이 경로에는 없기 때문이다. 화면을 미리 잡아 보려고 만든 HTML을 그대로 둔 채 배포하면 그 파일도 함께 공개된다.

    타임리프가 이 단계에서 주는 이점은 정적 HTML을 버리지 않고 템플릿으로 바꿀 수 있다는 점이다. 타임리프의 기능은 th:text 같은 속성으로 들어간다. 타임리프 튜토리얼의 설명대로 브라우저는 자신이 모르는 속성을 무시하므로, 템플릿 파일을 서버 없이 브라우저로 직접 열어도 원래 써 둔 HTML이 그대로 보인다. 같은 파일이 파일로 열면 견본 화면이고 서버를 거치면 실제 화면이 된다. 타임리프는 이런 템플릿을 내추럴 템플릿(natural template)이라고 부른다.

    속성 하나씩 읽기

    th:each="product : ${products}"는 이 속성이 붙은 tr 요소를 컬렉션의 원소 수만큼 반복해서 찍는다. 반복할 때마다 product라는 변수에 원소가 하나씩 들어간다. 자바의 향상된 for 문과 같은 모양이다. 상품이 세 개면 tr이 세 번 나오고, 하나도 없으면 한 번도 나오지 않는다.

    th:text="${product.name}"은 요소의 내용을 표현식의 값으로 바꾼다. 원래 적혀 있던 "상품 이름"이라는 글자는 견본용이고 서버를 거치면 실제 값으로 대체된다. 스프링과 함께 쓸 때 ${...} 안의 식은 스프링 표현 언어(SpEL)로 평가된다(타임리프의 스프링 통합 튜토리얼이 OGNL 대신 SpEL을 쓴다고 밝힌다).     th:text에는 눈에 잘 띄지 않는 중요한 동작이 하나 더 있다. 값을 HTML에 넣을 때 특수 문자를 이스케이프한다. 누군가 상품 이름에 굵게를 입력했다면 출력되는 HTML에는 &lt;b&gt;굵게&lt;/b&gt;가 들어가고, 브라우저 화면에는 꺾쇠가 글자 그대로 보인다. 태그로 해석되지 않는다. 사용자가 입력한 문자열을 그대로 HTML에 끼워 넣으면 입력에 섞인 스크립트 태그가 다른 사용자의 브라우저에서 실행될 수 있는데, 이스케이프가 기본값이어서 이 위험이 줄어든다. 이스케이프하지 않는 th:utext도 있지만, 신뢰할 수 없는 값에는 쓰지 않는다.

    th:href="@{/products/{id}(id=${product.id})}"는 링크 URL을 만든다. @{...}는 URL 전용 표현식이다. 경로 안의 {id} 자리에 괄호 안에서 준 값이 들어가므로 ID가 3인 상품이면 /products/3이 된다. 괄호 안에 경로에 없는 이름을 주면 쿼리 파라미터가 되고, 튜토리얼에 따르면 값의 URL 인코딩도 자동으로 이루어진다. /로 시작하는 URL에는 애플리케이션의 컨텍스트 경로가 자동으로 앞에 붙는다. 문자열을 이어 붙여 URL을 만들 때 놓치기 쉬운 두 가지를 표현식이 대신 처리해 주는 것이다.

    템플릿은 요청마다 다시 읽히지 않는다

    네 번째 단계의 캐시는 개발 중에 자주 혼란을 준다. 타임리프 튜토리얼은 템플릿 캐시가 파싱된 템플릿, 곧 템플릿 파일을 읽고 파싱한 결과를 저장한다고 설명한다. 부트의 기본값도 캐시 사용이다. 운영에서는 같은 파일을 요청마다 읽고 분해하는 비용을 없애 주지만, 개발 중에는 HTML을 고쳐도 서버를 다시 띄우기 전까지 화면이 바뀌지 않는 원인이 된다. 부트 레퍼런스는 이런 캐시가 운영에서는 이롭고 개발 중에는 방해가 된다고 설명하며, spring-boot-devtools를 넣으면 spring.thymeleaf.cache를 포함한 캐시 설정이 기본적으로 꺼진다고 밝힌다.

    캐시되는 것이 무엇인지 구분해 두자. 캐시에 남는 것은 템플릿의 구조이지 렌더링 결과가 아니다. 표현식 평가와 출력은 요청마다 그때의 모델로 다시 한다. 그래서 캐시가 켜져 있어도 상품을 등록하면 다음 요청의 목록에 바로 나타난다.

    왼쪽의 뷰 이름 문자열과 모델이 오른쪽의 HTML로 바뀌는 과정을 가로 파이프라인으로 그린다. 템플릿 파일을 읽는 길에는 캐시가 끼어 있고, 표현식 평가는 요청마다 다시 한다는 구분이 드러나야 한다. 깔끔한 기술 문서용 평면 다이어그램, 흰 배경, 왼쪽에서 오른쪽으로 흐르는 가로 파이프라인. 맨 왼쪽에 작은 상자 두 개를 세로로 놓는다. 위 상자 라벨 "뷰 이름: products/list", 아래 상자 라벨 "모델: products". 가운데에 큰 둥근 사각형 세 개를 가로로 나란히 놓는다. 첫째 라벨 "뷰 리졸버", 둘째 라벨 "템플릿 엔진", 셋째 라벨 "출력 스트림". 뷰 이름 상자에서 "뷰 리졸버"로 화살표, "뷰 리졸버"에서 "템플릿 엔진"으로 화살표, 모델 상자에서 "템플릿 엔진"으로 화살표. "템플릿 엔진" 위쪽에 문서 모양 아이콘을 그리고 라벨 "templates/products/list.html", 그 옆에 원통 모양 아이콘을 그리고 라벨 "템플릿 캐시". 문서에서 캐시로 점선 화살표를 그리고 "파싱은 처음 한 번"이라고 적는다. 캐시에서 "템플릿 엔진"으로 실선 화살표. "템플릿 엔진" 아래에 굵은 글씨로 "표현식 평가는 요청마다"라고 적는다. "템플릿 엔진"에서 "출력 스트림"으로 화살표, 맨 오른쪽에 브라우저 창 아이콘과 라벨 "HTML 응답". 색은 파랑과 회색 계열만 쓰고, 캐시 관련 요소만 연한 주황으로 구분한다. 템플릿의 구조는 한 번 파싱해 캐시에 두고, 값 채우기는 요청마다 그때의 모델로 다시 한다.

    상품 상세: 경로 변수 하나가 객체가 되기까지

    목록에서 ID 링크를 누르면 GET /products/3 같은 요청이 온다. 상세 메서드는 경로에서 ID를 꺼내 저장소를 조회하고 결과를 모델에 담는다.

    @GetMapping("/{productId}")
public String detail(@PathVariable Long productId, Model model) {
    Product product = store.findById(productId);
    if (product == null) {
        throw new ResponseStatusException(HttpStatus.NOT_FOUND);
    }
    model.addAttribute("product", product);
    return "products/detail";
}

    URL은 문자열이므로 경로에서 잘라 낸 값도 처음에는 문자열 "3"이다. 06회에서 본 인자 리졸버가 이 문자열을 매개변수 타입인 Long으로 바꿔 메서드에 넘긴다. 바꿀 수 없는 값이 오면 메서드는 호출되지 않는다. GET /products/abc를 보냈을 때 응답은 400이었고 서버 로그에는 다음이 남았다.

    Resolved [org.springframework.web.method.annotation.MethodArgumentTypeMismatchException: Method parameter 'productId': Failed to convert value of type 'java.lang.String' to required type 'java.lang.Long'; For input string: "abc"]

    형식은 맞지만 그런 상품이 없는 경우는 따로 생각해야 한다. store.findById(999L)은 null을 돌려준다. 위 코드에서 null 검사를 빼면 모델에 product = null이 들어간 채 뷰로 넘어가고(확인용 뷰는 실제로 model[product] = null을 출력했다), 템플릿이 ${product.name}을 평가하다가 실패한다. SpEL은 null에서 프로퍼티를 읽으려 하면 EL1007E: Property or field 'name' cannot be found on null 같은 메시지의 예외를 던진다. 사용자의 잘못된 주소 입력이 서버 내부 오류처럼 보이게 되는 것이다. 없는 자원을 요청한 것이므로 컨트롤러가 404로 답해야 한다. ResponseStatusException(HttpStatus.NOT_FOUND)를 던진 실험에서 응답은 HTTP/1.1 404였다.

    상세 화면의 템플릿은 값을 보여 주기만 하므로 입력 칸에 readonly를 붙이고 th:value로 값을 채운다. th:value는 value 속성을 표현식의 값으로 설정한다. 아래 링크 두 개는 수정 폼과 목록으로 간다.

    상품 등록 폼: 브라우저가 폼을 바이트로 바꾸는 규칙

    등록 폼을 내려 주는 메서드는 할 일이 없다. 조회할 데이터가 없으므로 뷰 이름만 돌려준다.

    @GetMapping("/new")
public String newForm() {
    return "products/newForm";
}

    th:action은 th:value와 같은 부류의 속성이다. 타임리프 튜토리얼의 설명대로 이런 th:* 속성은 특정 HTML 속성의 값을 정하는 일을 한다. 서버를 거치면 action이 /products/new로 바뀌고, 파일로 직접 열면 원래 적어 둔 detail.html이 남는다. 폼이 전송되는 곳은 이 폼을 받아 온 주소와 같다. 요청 표에서 본 대로 같은 URL에 GET은 폼을 주고 POST는 폼을 처리한다.

    이 HTML에서 서버와의 약속에 해당하는 것은 세 가지다. action(어디로), method(어떤 메서드로), 그리고 입력 요소의 name(어떤 이름으로)이다. id는 label과 입력 칸을 잇거나 스크립트에서 요소를 찾는 데 쓰는 브라우저 안의 식별자이고 서버로 가지 않는다. 서버가 받는 파라미터 이름은 name 속성이다. name을 productName으로 바꾸면 서버가 받는 이름도 productName이 되고, 뒤에서 볼 바인딩이 조용히 어긋난다.

    "상품 등록" 버튼을 누르면 브라우저는 입력 요소의 이름과 값을 모아 요청 본문을 만든다. MDN의 form 요소 문서에 따르면 method가 post일 때 폼 데이터는 요청 본문으로 가고, 본문의 형식을 정하는 enctype의 기본값은 application/x-www-form-urlencoded다. 상품명에 "무선 키보드", 가격에 30000, 수량에 5를 넣은 폼과 같은 내용을 curl로 보내고, 실제로 나간 바이트를 기록한 것이다.

    POST /products/new HTTP/1.1
Host: localhost:18608
User-Agent: curl/8.7.1
Accept: */*
Content-Length: 74
Content-Type: application/x-www-form-urlencoded

name=%EB%AC%B4%EC%84%A0+%ED%82%A4%EB%B3%B4%EB%93%9C&price=30000&quantity=5

    본문 한 줄을 뜯어 보자. 이름=값 쌍이 &로 이어져 있다. GET 요청의 쿼리 문자열과 같은 형식이고, 놓인 자리만 URL이 아니라 본문이다. "무"라는 글자는 UTF-8로 세 바이트(EB AC B4)이고, 각 바이트가 %EB%AC%B4처럼 퍼센트 인코딩되었다. 공백은 +가 되었다. 한글 다섯 글자가 45바이트를 차지해서 본문 전체가 74바이트이고, Content-Length가 그 값을 알려 준다.

    여기서 가져갈 사실은 두 가지다. 첫째, 네트워크로 나가는 것은 전부 문자열이다. price=30000의 30000은 숫자가 아니라 글자 다섯 개다. 입력 칸에 "삼만원"이라고 써도 브라우저는 그대로 보낸다. 서버의 Integer price에 숫자가 들어가려면 누군가 문자열을 숫자로 바꿔야 하고, 바꿀 수 없을 때의 처리도 서버의 몫이다. 둘째, 서버는 이 본문을 Content-Type을 보고 해석한다. 02회에서 본 대로 서블릿 컨테이너는 본문이 폼 형식인 POST 요청을 쿼리 문자열과 같은 방식으로 풀어 request.getParameter()로 꺼낼 수 있게 해 준다. 그래서 06회의 @RequestParam이 쿼리 문자열과 폼 본문을 구분하지 않고 받을 수 있었다.

    퍼센트 인코딩된 바이트를 어떤 문자 집합으로 되돌릴지는 서버 쪽 설정이 정한다. 이 실험에서는 톰캣 컨텍스트의 요청 문자 인코딩을 UTF-8로 지정했다. 보내는 쪽과 받는 쪽의 문자 집합이 다르면 한글 이름이 깨진 채 저장된다.

    MDN 문서는 method에 쓸 수 있는 값을 get, post, dialog로 한정한다. HTML 폼은 PUT이나 PATCH를 직접 보내지 못한다는 뜻이다. 요청 표에서 수정 처리가 POST인 이유가 여기에 있다. 자바스크립트나 다른 서버가 호출하는 HTTP API라면 메서드를 자유롭게 고를 수 있지만, 브라우저의 폼 전송만으로 동작하는 화면에서는 선택지가 GET과 POST 둘뿐이다.

    상품 등록 처리 - @ModelAttribute: 문자열이 객체가 되는 과정

    폼을 받는 메서드를 06회에서 배운 도구로 먼저 써 보자. 파라미터를 하나씩 받아 객체를 조립하고, 저장한 뒤 상세 화면에 넘길 모델에 담는다.

    @PostMapping("/new")
public String create(@RequestParam String name,
                     @RequestParam Integer price,
                     @RequestParam Integer quantity,
                     Model model) {
    Product product = new Product();
    product.setName(name);
    product.setPrice(price);
    product.setQuantity(quantity);
    store.save(product);
    model.addAttribute("product", product);
    return "products/detail";
}

    동작은 하지만 메서드의 대부분이 "파라미터를 꺼내 객체에 옮겨 담는" 코드다. 필드가 열 개로 늘면 매개변수도 열 개, setter 호출도 열 줄이 된다. 이 반복을 프레임워크에 맡기는 것이 @ModelAttribute다.

    @PostMapping("/new")
public String create(@ModelAttribute("product") Product product) {
    store.save(product);
    return "products/detail";
}

    두 메서드에 같은 폼을 보냈을 때 확인용 뷰가 받은 모델은 같았다. 객체 생성, 값 채우기, 모델에 담기가 모두 메서드 바깥에서 일어났다는 뜻이다. (뷰를 바로 돌려주는 마지막 줄에는 문제가 있다. PRG 절에서 고친다.)

    @ModelAttribute("product")의 괄호 안은 모델에 담을 때 쓰는 이름이다. 이름을 주지 않으면 타입에서 만든다. 실험에서 Product 타입은 product, PrimitiveProduct는 primitiveProduct라는 이름으로 모델에 들어갔다. 첫 글자를 소문자로 바꾸는 규칙이다. 예외가 하나 있어서 URLInfo처럼 앞의 두 글자가 모두 대문자인 클래스는 URLInfo 그대로 들어갔다. 자바빈의 프로퍼티 이름 규칙(java.beans.Introspector.decapitalize("URLInfo")의 결과가 "URLInfo"다)과 같은 결과다. 반대로 이름을 goods로 지정하면 모델 키는 goods가 되고, 템플릿이 ${product.name}을 찾고 있었다면 값을 얻지 못한다.

    애너테이션 자체도 생략할 수 있다. 6.2 레퍼런스에 따르면 단순 값 타입(BeanUtils.isSimpleProperty로 판단한다)이 아니면서 다른 인자 리졸버가 처리하지 않는 매개변수는 암묵적인 @ModelAttribute로 취급된다. String이나 Integer 같은 단순 타입을 생략하면 06회에서 본 대로 @RequestParam으로 처리된다. 매개변수에 Product product만 쓴 메서드도 실험에서 위와 같은 결과를 냈다. 다만 같은 문서는 GraalVM 네이티브 이미지로 컴파일할 때는 암묵적 방식으로는 필요한 리플렉션 정보를 미리 추론하지 못하므로 애너테이션을 명시하라고 권한다. 코드를 읽는 사람에게도 "이 객체는 요청에서 채워진다"는 표시가 남는 쪽이 낫다.

    경계 조건: 틀린 값, 빈 값, 없는 값, 남는 값

    사용자는 폼을 항상 얌전하게 채우지 않는다. 같은 메서드에 여러 가지 본문을 보내 결과를 모았다. int 줄은 가격 필드를 기본형으로 바꾼 별도 클래스로 실험한 것이다.

    둘째부터 다섯째 줄은 도메인 클래스에서 Integer를 고른 이유를 보여 준다. 래퍼 타입에서는 "입력하지 않음"이 null이라는 구별되는 값으로 남는다. 기본형 int는 null을 담을 수 없어서, 빈 값은 변환 오류가 되고 파라미터가 아예 없으면 0이 남는다. 0은 "가격이 0원"과 "가격을 보내지 않음"을 구분하지 못한다. 한편 String은 빈 칸으로 제출하면 null이 아니라 빈 문자열이 온다. 입력 칸이 폼에 있으면 비어 있어도 name=이 전송되기 때문이다. "이름은 필수"를 null 검사만으로 확인하면 빈 이름이 통과한다.

    마지막 줄이 가장 주의할 곳이다. 등록 폼에는 ID 입력 칸이 없지만, 본문에 id=777을 끼워 보내자 객체의 id가 777로 채워졌다. 로그에도 setId(777)이 찍혔다. 바인더는 폼에 어떤 칸이 있었는지 모른다. 요청에 들어 있는 이름 중 setter가 있는 것은 모두 채운다. 등록에서는 저장소가 ID를 새로 덮어쓰므로 해가 없었지만, 객체에 "관리자 여부"나 "승인 상태" 같은 필드가 있고 그 객체를 그대로 저장한다면 사용자가 폼에 없는 값을 마음대로 정할 수 있게 된다. 6.2 레퍼런스는 이 때문에 모델 객체 설계에 주의가 필요하다고 하고, 보안상 웹 바인딩 전용으로 만든 객체를 쓰거나 생성자 바인딩만 적용하라고 권한다. 프로퍼티 바인딩을 써야 한다면 허용할 필드 패턴(allowedFields)을 지정하라고 한다. 화면이 받는 값만 가진 폼 전용 클래스를 따로 두는 습관이 여기서 나온다.

    왼쪽의 요청 본문 문자열이 가운데 데이터 바인더를 지나 오른쪽 힙의 Product 객체 필드로 들어가는 모습. 문자열이 타입 변환을 거쳐 setter로 들어간다는 점과, 완성된 객체가 모델과 컨트롤러 인자 양쪽에서 참조된다는 점이 보여야 한다. 깔끔한 기술 문서용 평면 다이어그램, 흰 배경, 왼쪽에서 오른쪽으로 흐른다. 맨 왼쪽에 긴 상자를 그리고 라벨 "요청 본문", 그 안에 고정폭 글꼴로 "name=무선 키보드", "price=30000", "quantity=5" 세 줄. 가운데에 큰 둥근 사각형, 라벨 "데이터 바인더". 그 안에 작은 단계 상자 세 개를 위에서 아래로: "이름으로 setter 찾기", "문자열 → Integer 변환", "리플렉션으로 setter 호출". 오른쪽에 "힙"이라고 적힌 영역을 그리고 그 안에 객체 상자 하나, 제목 "Product", 칸 네 개: "id = null", "name = 무선 키보드", "price = 30000", "quantity = 5". 요청 본문의 세 줄에서 데이터 바인더로 화살표 세 개, 데이터 바인더에서 Product의 name, price, quantity 칸으로 화살표 세 개. 오른쪽 아래에 작은 상자 두 개 "모델: product"와 "컨트롤러 인자"를 그리고 둘 다 같은 Product 객체를 가리키는 점선 화살표를 그린다. 색은 파랑과 회색, 변환 단계만 연한 주황. 바인더는 파라미터 이름으로 setter를 찾고, 문자열을 필드 타입으로 바꾼 뒤 리플렉션으로 호출한다. 완성된 객체 하나를 모델과 컨트롤러가 함께 가리킨다.

    상품 수정: 폼 두 개가 같은 객체를 다르게 쓴다

    수정은 등록과 같은 부품으로 만들지만 요청이 두 번에 걸쳐 온다. 먼저 GET으로 현재 값이 채워진 폼을 받고, 고친 뒤 POST로 보낸다.

    @GetMapping("/{productId}/edit")
public String editForm(@PathVariable Long productId, Model model) {
    Product product = store.findById(productId);
    if (product == null) {
        throw new ResponseStatusException(HttpStatus.NOT_FOUND);
    }
    model.addAttribute("product", product);
    return "products/editForm";
}

@PostMapping("/{productId}/edit")
public String edit(@PathVariable Long productId, @ModelAttribute Product form) {
    if (store.findById(productId) == null) {
        throw new ResponseStatusException(HttpStatus.NOT_FOUND);
    }
    store.update(productId, form);
    return "redirect:/products/{productId}";
}

    수정 폼은 상세 화면과 거의 같고, 입력 칸을 고칠 수 있다는 점만 다르다. th:value가 저장소의 현재 값을 value 속성에 넣어 주므로 사용자는 바꿀 칸만 고치고 저장한다. 제출하면 고치지 않은 칸의 값도 함께 전송된다. 서버가 받는 것은 "무엇이 바뀌었는가"가 아니라 "폼에 있던 칸 전체의 현재 값"이다.

    POST 메서드의 두 매개변수는 서로 다른 곳에서 온다. productId는 URL 경로에서, form은 본문에서 채워진다. 여기서 form은 저장소에 있는 그 상품 객체가 아니다. 바인더가 이 요청을 위해 새로 만든 객체이고, 값을 실어 나르는 용도로만 쓰인다. store.update가 저장소의 진짜 객체를 찾아 값을 옮겨 적는다. 이 구조에서 확인해 둘 것이 네 가지 있다.

    어느 상품을 고칠지는 경로가 정한다. 폼에는 읽기 전용 ID 칸이 있고 그 값도 본문에 실려 온다. readonly는 브라우저 화면에서 못 고치게 할 뿐이고, 요청을 직접 만들어 보내는 쪽에는 아무 제약이 아니다. 실험에서 POST /products/1/edit의 본문에 id=555를 넣어 보냈다. 컨트롤러가 받은 form은 Product{id=555, name=유선 키보드, price=20000, quantity=9}였지만, 저장소는 경로에서 온 1번 상품을 고쳤고 그 상품의 ID는 1 그대로였다. update가 form의 ID를 읽지 않기 때문이다. 만약 form.getId()로 대상을 찾았다면 1번 수정 화면에서 555번을 고치는 요청이 통했을 것이다.

    폼에 없는 칸은 null로 덮인다. 수정 폼에서 수량 칸을 지웠다고 해 보자. 본문에 quantity가 없으므로 앞 절의 표대로 form.getQuantity()는 null이다. update는 그 null을 저장소 객체에 그대로 옮긴다. 이름과 가격만 보낸 실험에서 저장된 상품은 Product{id=1, name=X, price=1, quantity=null}이 되었다. "보내지 않은 값은 그대로 둔다"는 동작은 저절로 생기지 않는다. 화면마다 고칠 수 있는 필드가 다르면 화면마다 폼 전용 객체를 두고, 그 객체에 있는 필드만 옮겨 적어야 한다.

    없는 상품에 대한 POST도 온다. 폼을 연 뒤 다른 사람이 그 상품을 지웠을 수도 있고, 누군가 URL을 고쳐 보냈을 수도 있다. 위 코드에서 존재 검사를 뺀 채 POST /products/999/edit를 보내자 update 안에서 null에 setter를 부르다 NullPointerException이 났고 응답은 500이었다. GET에서 한 번 확인했다고 POST에서도 있다고 가정할 수 없다. 두 요청은 서로 독립된 HTTP 요청이고 그 사이에 서버의 상태는 얼마든지 바뀔 수 있다.

    두 사람이 같은 상품을 고치면 나중 것이 이긴다. A와 B가 같은 상품의 수정 폼을 받았다. A는 가격을 고쳐 저장하고, 조금 뒤 B는 수량을 고쳐 저장한다. B의 폼에는 B가 폼을 받은 시점의 옛 가격이 그대로 들어 있으므로, B의 저장은 A가 고친 가격을 옛 값으로 되돌린다. 저장소의 맵이 스레드에 안전한 것과 무관하게 생기는 문제다. 앞에서 본 ++sequence의 갱신 유실과 구조가 같다. "읽기"가 폼을 받는 GET이고 "쓰기"가 POST이며, 그 사이의 간격이 나노초가 아니라 사람이 폼을 들여다보는 몇 분이라는 점만 다르다. 이 문제는 뒤의 권에서 데이터베이스와 JPA를 다룰 때 버전 번호로 충돌을 알아채는 방법으로 다시 만난다.

    마지막 줄의 "redirect:/products/{productId}"에는 값을 넣어 준 코드가 없는데도 실험에서 Location: /products/1이 나왔다. 6.2 레퍼런스는 현재 요청의 URI 템플릿 변수가 리다이렉트 URL을 펼칠 때 자동으로 쓰이므로 모델이나 RedirectAttributes에 따로 넣을 필요가 없다고 설명한다. 이 요청의 경로 변수 productId가 그대로 다시 쓰인 것이다.

    PRG Post/Redirect/Get: 마지막 요청을 GET으로 바꿔 놓는다

    등록 처리 메서드는 저장한 뒤 상세 뷰 이름을 돌려주고 있었다. 화면은 잘 나온다. 그런데 이 화면에서 새로고침을 누르면 상품이 하나 더 생긴다. 뷰를 바로 돌려주는 메서드에 같은 POST를 두 번 보내는 것으로 이 상황을 재현했다. 첫 응답은 200과 함께 상세 화면이었고, 두 번 보낸 뒤 저장소의 상품 수는 1개에서 3개가 되어 있었다.

    원인은 새로고침의 뜻에 있다. 브라우저의 새로고침은 "지금 화면을 만들어 낸 마지막 요청을 다시 보낸다"이다. 이 화면을 만든 마지막 요청은 POST /products/new와 그 본문이다. 브라우저는 대개 양식을 다시 제출할지 묻는 확인 창을 띄우지만, 사용자가 확인을 누르면 같은 본문의 POST가 그대로 다시 나간다. 주소창에도 흔적이 남아 있다. 화면에는 상품 상세가 보이는데 주소는 /products/new다.

    서버는 두 번째 POST가 실수인지 알 수 없다. HTTP 요청은 서로 독립적이어서, 같은 본문의 POST 두 개는 "같은 이름의 상품을 두 번 등록하겠다"는 정상 요청과 구별되지 않는다. RFC 9110은 같은 요청을 여러 번 보내도 서버에 의도한 효과가 한 번 보낸 것과 같은 메서드를 멱등(idempotent)하다고 하고, 이 명세가 정의한 메서드 중 PUT, DELETE, 그리고 안전한 메서드가 멱등하다고 적는다(§9.2.2). POST는 이 목록에 없다. 다시 보내면 효과가 다시 생길 수 있는 요청이라는 뜻이고, 등록은 정확히 그런 요청이다.

    해결은 POST의 응답으로 화면을 주지 않는 것이다. 저장을 끝낸 서버는 "결과는 저 주소에 있으니 그리로 가라"고만 답한다.

    @PostMapping("/new")
public String create(@ModelAttribute Product product) {
    Product saved = store.save(product);
    return "redirect:/products/" + saved.getId();
}

    이 버전은 ID를 문자열로 이어 붙인다. 숫자뿐이라 여기서는 문제가 없지만 좋은 방법은 아니고, 다음 절에서 RedirectAttributes로 바꾼다. 다음 절의 최종 버전으로 주고받은 실제 메시지를 먼저 보자.

    HTTP/1.1 302
Location: /products/1?status=true
Content-Language: ko-KR
Content-Length: 0
Date: Mon, 16 Nov 2026 05:42:47 GMT

    본문이 없다(Content-Length: 0). 상태 코드 302와 Location 헤더가 전부다. 브라우저는 이 응답을 받으면 화면을 그리지 않고 Location의 주소로 새 요청을 보낸다. Location의 값은 /로 시작하는 상대 참조이고, 브라우저가 현재 요청의 주소를 기준으로 완전한 URL을 만든다.

    브라우저                                         서버
   │                                               │
   │ ① POST /products/new   (본문: name=...&price=...)
   │ ─────────────────────────────────────────────▶│  바인딩 → 저장(id=1)
   │                                               │
   │ ② HTTP/1.1 302   Location: /products/1?status=true
   │ ◀─────────────────────────────────────────────│  화면은 주지 않는다
   │                                               │
   │ ③ GET /products/1?status=true   (브라우저가 스스로 보낸다)
   │ ─────────────────────────────────────────────▶│  조회 → 뷰 렌더링
   │                                               │
   │ ④ HTTP/1.1 200   (상세 화면 HTML)
   │ ◀─────────────────────────────────────────────│
   │
   │ 새로고침 = 마지막 요청 다시 보내기 = ③을 다시 보낸다. 저장은 다시 일어나지 않는다.

    이제 화면을 만든 마지막 요청은 ③의 GET이다. 새로고침을 몇 번 눌러도 조회만 반복된다. 실험에서 등록 뒤 상세 주소를 두 번 더 요청했을 때 상품 수는 1개 그대로였다. 주소창도 /products/1로 바뀌어 있어서 이 주소를 복사해 다른 사람에게 보내거나 즐겨찾기에 넣을 수 있다. POST, 리다이렉트, GET 순서로 이어지는 이 흐름을 줄여 PRG라고 부른다.

    브라우저와 서버 사이에 요청·응답 두 쌍이 오가는 시퀀스. 첫 쌍(POST → 302)과 둘째 쌍(GET → 200)을 색으로 구분하고, 새로고침이 둘째 요청만 반복한다는 것을 아래쪽 되돌이 화살표로 보여 준다. 깔끔한 기술 문서용 시퀀스 다이어그램, 흰 배경. 세로 생명선 두 개: 왼쪽 위에 상자 "브라우저", 오른쪽 위에 상자 "서버". 위에서 아래로 화살표 네 개를 그린다. 첫째, 브라우저에서 서버로 주황 실선 화살표, 라벨 "POST /products/new". 서버 생명선 옆에 작은 메모 "저장". 둘째, 서버에서 브라우저로 주황 점선 화살표, 라벨 "302 Location: /products/1". 셋째, 브라우저에서 서버로 파란 실선 화살표, 라벨 "GET /products/1". 서버 생명선 옆에 작은 메모 "조회 + 렌더링". 넷째, 서버에서 브라우저로 파란 점선 화살표, 라벨 "200 상세 화면". 브라우저 생명선 왼쪽 아래에 둥근 되돌이 화살표를 그려 셋째 화살표의 출발점을 가리키게 하고 라벨 "새로고침은 GET만 다시 보낸다". 첫째와 둘째 화살표를 묶는 옅은 주황 배경 띠에 "상태를 바꾸는 요청", 셋째와 넷째를 묶는 옅은 파랑 배경 띠에 "화면을 받는 요청". 색은 주황, 파랑, 회색만 쓴다. 저장하는 요청과 화면을 받는 요청을 둘로 가른다. 브라우저에 남는 마지막 요청은 GET이다.

    302인데 왜 GET으로 바뀌는가

    ①은 POST였는데 ③은 GET이다. 누가 메서드를 바꿨는가. RFC 9110은 302(Found)를 설명하면서 역사적인 이유로 사용자 에이전트가 다음 요청의 메서드를 POST에서 GET으로 바꿀 수 있다(MAY)고 적는다(§15.4.3). 브라우저의 동작을 정의하는 WHATWG Fetch 표준은 더 단정적이다. 응답 상태가 301 또는 302이고 요청 메서드가 POST이면 메서드를 GET으로 바꾸고 본문을 비운다. 실험에서 리다이렉트를 따라가게 한 curl도 Switch from POST to GET이라는 로그를 남기고 GET /products/9?status=true를 보냈다.

    이 용도에 꼭 맞게 정의된 코드는 303(See Other)이다. RFC 9110은 303이 주로 POST 동작의 결과를 다른 자원으로 리다이렉트하는 데 쓰인다고 설명한다(§15.4.4). 반대로 307(Temporary Redirect)은 메서드를 바꾸지 않는 리다이렉트여서, PRG에 쓰면 브라우저가 새 주소로 POST를 다시 보낸다. 스프링의 RedirectView는 기본 설정(http10Compatible = true)에서 서블릿의 response.sendRedirect()를 불러 302를 보낸다. 6.2.x 소스를 보면 이 값을 false로 바꾸었을 때 따로 지정한 상태 코드가 없으면 303을 쓴다. 302와 303 가운데 어느 쪽이든 브라우저의 폼 전송에서는 결과가 같다.

    서버 안에서 일어나는 일

    "redirect:"로 시작하는 문자열은 뷰 이름이 지나는 길을 그대로 지난다. 6.2 레퍼런스에 따르면 UrlBasedViewResolver와 그 하위 클래스가 이 접두사를 리다이렉트 지시로 인식하고, 접두사를 뺀 나머지를 리다이렉트 URL로 쓴다. 결과는 컨트롤러가 RedirectView를 직접 돌려준 것과 같다. 실험의 뷰 리졸버가 이 클래스이고, 타임리프의 스프링 통합 튜토리얼도 컨트롤러가 redirect:로 시작하는 뷰 이름을 돌려주는 예제를 쓴다. RedirectView의 "렌더링"은 템플릿을 그리는 것이 아니라 URL을 완성해 상태 코드와 Location 헤더를 쓰는 것이다.

    03회에서 본 포워드(forward)와 혼동하지 말아야 한다. 포워드는 서버 안에서 다른 자원으로 처리를 넘기는 것이어서 브라우저는 그런 일이 있었는지 모른다. 요청은 여전히 하나이고 마지막 요청은 POST로 남는다. 리다이렉트는 응답이 브라우저까지 갔다가 새 요청이 되어 돌아온다. 서버 입장에서 ①과 ③은 완전히 별개의 요청이다. 실험 로그에서 ①은 http-nio-18608-exec-1 스레드가, ③은 exec-2 스레드가 처리했다(스레드 배정은 실행마다 다르다). 요청 객체도, 모델도 새로 만들어진다. ①에서 만든 모델은 ②의 응답과 함께 사라진다.

    이 방식에는 비용이 있다. 왕복이 한 번 늘어난다. RFC 9110도 POST 결과를 303으로 돌리는 방식의 이점과 함께 요청이 하나 더 드는 비용을 언급한다(§9.3.3). 그리고 PRG가 막는 것은 "응답을 받은 뒤의 새로고침"뿐이다. 응답이 오기 전에 버튼을 두 번 누르면 POST 두 개가 이미 나간 뒤이고, 뒤로 가기로 폼 화면에 돌아가 다시 제출하는 것도 막지 못한다. 중복 자체를 막으려면 서버가 같은 요청임을 알아볼 수단이 따로 있어야 한다.

    RedirectAttributes: 갈라진 두 요청 사이에 값을 건네는 두 가지 길

    리다이렉트로 요청이 둘이 되자 새 문제가 생겼다. 첫 요청에서 알게 된 것(새로 생긴 상품의 ID, "방금 저장했다"는 사실)을 둘째 요청에 전해야 한다. 서버는 요청 사이에 아무것도 기억하지 않으므로 값을 실을 수 있는 곳은 두 군데뿐이다. 브라우저가 다시 들고 올 URL에 싣거나, 서버가 세션에 맡겨 두는 것이다. RedirectAttributes는 이 두 길을 메서드 두 개로 제공한다.

    addAttribute: URL에 싣는다

    @PostMapping("/new")
public String create(@ModelAttribute Product product, RedirectAttributes redirectAttributes) {
    Product saved = store.save(product);
    redirectAttributes.addAttribute("productId", saved.getId());
    redirectAttributes.addAttribute("status", true);
    return "redirect:/products/{productId}";
}

    앞에서 본 응답의 Location: /products/1?status=true가 이 코드의 결과다. 넣은 속성 가운데 리다이렉트 URL의 {productId}와 이름이 같은 것은 경로의 그 자리에 들어갔고, 자리가 없는 status는 쿼리 파라미터로 붙었다. 값은 문자열로 바뀌어 URL에 들어간다.

    문자열 연결 대신 이것을 쓰는 이유는 인코딩이다. URL에 넣는 값이 숫자가 아니라 사용자가 입력한 문자열이라고 해 보자. 상품 이름 키보드 A&B를 검색어로 넘기는 리다이렉트를 두 방식으로 만들어 비교했다.

    방식값실제 응답
    "redirect:/products?keyword=" + name키보드 A&B302이지만 Location 헤더가 없음
    "redirect:/products?keyword=" + namekey A&B=1Location: /products?keyword=key A&B=1
    addAttribute("keyword", name)키보드 A&BLocation: /products?keyword=%ED%82%A4%EB%B3%B4%EB%93%9C+A%26B

    첫 줄에서 톰캣은 한글이 그대로 들어간 헤더 값을 유효하지 않다고 보고 헤더를 통째로 지웠다. 서버 로그에는 The HTTP response header [Location] with value [/products?keyword=키보드 A&B] has been removed from the response because it is invalid가 남았다(톰캣 11.0.27). 브라우저는 갈 곳이 없는 302를 받는다. 둘째 줄은 헤더가 나가긴 했지만 뜻이 달라졌다. 값 안의 &가 파라미터 구분자로 읽혀서, 받는 쪽은 keyword가 key A이고 B라는 파라미터가 따로 있다고 해석한다. 사용자가 입력한 문자열이 URL의 구조를 바꾼 것이다. 셋째 줄에서는 한글이 퍼센트 인코딩되고 &가 %26이 되어 값의 일부로 남았다. 타임리프의 @{...}가 링크에서 해 주던 일을 리다이렉트에서는 addAttribute가 한다.

    이제 상세 템플릿 맨 위의 th:if="${param.status}"를 설명할 수 있다. 타임리프 튜토리얼에 따르면 ${param.x}는 x라는 요청 파라미터를 돌려준다. th:if는 값이 null이면 거짓으로 평가한다. 목록에서 링크를 눌러 들어온 /products/1에는 status 파라미터가 없으므로 문구가 나오지 않고, 등록 직후 리다이렉트로 들어온 /products/1?status=true에서는 나온다. 컨트롤러의 상세 메서드는 고칠 필요가 없다. 요청 파라미터는 템플릿이 직접 읽기 때문이다.

    다만 URL에 실은 값은 URL에 남는다. ?status=true가 붙은 주소에서 새로고침을 하면 "저장되었습니다"가 다시 나오고, 이 주소를 받은 다른 사람의 화면에도 나온다. 누구든 주소 뒤에 ?status=true를 붙여 문구를 띄울 수도 있다. URL에는 "주소의 일부로 남아도 되는 값"만 실어야 한다. 상품 ID는 그런 값이고, 한 번만 보여 줄 안내 문구는 그렇지 않다.

    addFlashAttribute: 세션에 잠깐 맡긴다

    @PostMapping("/new")
public String create(@ModelAttribute Product product, RedirectAttributes redirectAttributes) {
    Product saved = store.save(product);
    redirectAttributes.addAttribute("productId", saved.getId());
    redirectAttributes.addFlashAttribute("message", "저장되었습니다");
    return "redirect:/products/{productId}";
}

    플래시 속성(flash attribute)은 URL에 나타나지 않는다. 6.2 레퍼런스의 설명으로는 리다이렉트 전에 임시로(보통 세션에) 저장되었다가 리다이렉트 뒤의 요청에서 쓸 수 있게 되고 즉시 제거된다. 이 메서드에 등록 요청을 보내고, 받은 쿠키를 들고 상세 주소를 두 번 요청한 결과다.

    레퍼런스는 이 동작을 두 가지 추상화로 설명한다. FlashMap은 플래시 속성을 담는 맵이고, FlashMapManager는 그것을 저장하고 꺼내고 관리한다. 요청마다 앞 요청이 넘겨준 "입력" FlashMap과 다음 요청에 넘길 "출력" FlashMap이 있다. RedirectAttributes에 넣은 플래시 속성은 출력 쪽으로 전달되고, 리다이렉트 뒤에는 입력 쪽의 속성이 대상 URL을 처리하는 컨트롤러의 모델에 자동으로 더해진다. 기본 구현인 SessionFlashMapManager는 세션에 SessionFlashMapManager의 클래스 이름 뒤에 .FLASH_MAPS를 붙인 이름의 속성으로 이것을 보관한다(7.0.10 소스). 플래시 기능은 항상 켜져 있지만, 쓰지 않으면 세션을 만들지 않는다고 문서는 밝힌다.

    "다음 요청"이 꼭 의도한 그 요청이라는 보장은 없다. 리다이렉트 응답과 뒤따르는 GET 사이에 같은 브라우저의 다른 요청(다른 탭, 주기적으로 서버를 호출하는 스크립트)이 먼저 도착하면 그 요청이 플래시 속성을 가져가 버릴 수 있다. 레퍼런스는 이 문제를 줄이려고 RedirectView가 FlashMap에 대상 URL의 경로와 쿼리 파라미터를 찍어 두고, 기본 FlashMapManager가 들어온 요청과 그 정보를 맞춰 본다고 설명한다. 가능성을 없애지는 못하고 크게 줄인다는 것이 문서의 표현이다. 리다이렉트가 끝내 따라오지 않은 플래시 맵은 만료 시간(7.0.10 소스의 기본값 180초)이 지나면 정리 대상이 된다.

    ①의 Location 끝에 붙은 ;jsessionid=...도 짚어 두자. RedirectView는 URL을 response.encodeRedirectURL()에 통과시킨다(6.2.x 소스). 세션이 방금 만들어진 이 시점에 서블릿 컨테이너는 브라우저가 쿠키를 돌려보낼지 아직 모르므로, 쿠키와 URL 양쪽에 세션 ID를 실은 것이다. 세션과 쿠키, 세션 ID를 URL에 싣지 않게 하는 설정은 뒤의 권에서 로그인을 다룰 때 본다.

    리다이렉트하는 메서드에서 습관대로 model.addAttribute("status", "ok")를 쓰면 어떻게 될까. 실험에서 응답은 Location: /products였고 status는 어디에도 붙지 않았다. 6.x에서는 RequestMappingHandlerAdapter의 ignoreDefaultModelOnRedirect 속성이 이 동작을 정한다. 6.2.x 소스의 Javadoc은 이 값이 6.0부터 기본으로 true이며, true이면 RedirectAttributes를 선언하지 않았더라도 리다이렉트에 기본 모델을 쓰지 않는다고 적는다. 같은 Javadoc에 따르면 이 속성은 6.0에서 폐기 예정(deprecated)이 되었다. 실험에 쓴 7.0.10 소스에는 이 속성이 없고, 기본 모델은 리다이렉트에서 항상 쓰이지 않는다. 한편 레퍼런스의 Redirect Attributes 절은 기본 모델의 기본형 속성이 쿼리 파라미터로 붙는다는 예전 기본 동작을 여전히 설명하고 있으므로, 6.x 이상에서는 소스와 실험 결과를 기준으로 삼아야 한다. 리다이렉트에 실어 보낼 값은 RedirectAttributes에 명시적으로 넣는다.

    남겨 둔 숙제도 분명하다. 가격에 글자를 넣으면 400 화면이 뜨고, 이름을 비워도 그대로 저장되며, 음수 가격을 막지 못한다. 서버를 다시 띄우면 상품이 사라진다. 누구나 아무 상품이나 고칠 수 있다. 타임리프의 폼 지원과 입력 검증, 로그인과 세션은 스프링 MVC 2편에 해당하는 다음 권에서, 데이터베이스 저장은 그 뒤의 권에서 이 화면을 출발점으로 다시 다룬다.

    이 장의 핵심

    웹 페이지 하나는 독립된 HTTP 요청 여러 개의 연속이고, 서버는 그 사이를 기억하지 않는다. 그래서 요청과 요청 사이에 있는 모든 것(힙의 저장소, URL, 세션, 사용자가 들여다보는 폼)이 설계의 대상이 된다. 상태를 바꾸는 요청은 POST로 받아 바인딩하고 저장한 뒤 리다이렉트로 끝내고, 화면은 언제 다시 보내도 안전한 GET으로 그린다. 두 요청을 잇는 값 가운데 주소로 남아도 되는 것은 URL에, 한 번 쓰고 버릴 것은 플래시 속성에 싣는다.
    정적 리소스와 템플릿
    static의 파일은 ResourceHttpRequestHandler가 바이트 그대로 내보내고 컨트롤러를 거치지 않는다. templates의 파일은 컨트롤러가 뷰 이름으로 지목해야 하고, 요청마다 모델 값이 채워진다.
    싱글톤 저장소의 공유 상태
    스프링 빈인 저장소의 필드는 모든 요청 스레드가 공유한다. ++sequence는 읽기·더하기·쓰기 세 단계여서 섞이면 갱신이 유실되고, AtomicLong과 ConcurrentHashMap은 ID 중복과 맵 손상을 막지만 맵에 담긴 객체의 여러 필드 수정을 한 덩어리로 만들어 주지는 않는다.
    타임리프 렌더링
    뷰 이름에 접두사·접미사를 붙여 템플릿을 찾고, 파싱한 구조는 캐시하며, 표현식 평가는 요청마다 한다. th:text는 값을 이스케이프하고 @{...}는 경로 변수와 쿼리 파라미터를 인코딩해 URL을 만든다.
    폼 전송
    브라우저는 입력 요소의 name과 값을 application/x-www-form-urlencoded 본문으로 보낸다. 전부 문자열이고, HTML 폼이 쓸 수 있는 HTTP 메서드는 GET과 POST뿐이다.
    @ModelAttribute 바인딩
    인자 리졸버가 객체를 만들고, 데이터 바인더가 파라미터 이름으로 setter를 찾아 타입을 변환한 뒤 리플렉션으로 호출하며, 완성된 객체를 모델에 넣는다. 이 모든 일이 컨트롤러 메서드 호출 전에 끝난다.
    바인딩의 경계 조건
    타입이 맞지 않으면 BindingResult가 없을 때 예외와 400으로 끝난다. 빈 값과 없는 파라미터는 래퍼 타입에서 null이 되고, 폼에 없던 이름도 setter가 있으면 채워진다.
    PRG(Post/Redirect/Get)
    POST 응답으로 화면 대신 302와 Location을 보내 브라우저가 GET을 새로 보내게 한다. 브라우저의 마지막 요청이 GET이 되므로 새로고침이 저장을 반복하지 않는다.
    RedirectAttributes
    addAttribute는 값을 인코딩해 리다이렉트 URL의 경로 변수나 쿼리 파라미터로 싣고, addFlashAttribute는 세션에 맡겼다가 다음 요청의 모델에 넣어 주고 지운다.

    실무에서 다시 판단하면, PRG는 중복 제출 방지의 출발점이지 전부가 아니다. PRG가 끊는 것은 응답을 받은 뒤의 새로고침 하나다. 느린 네트워크에서 버튼을 두 번 누른 경우, 뒤로 가기 후 재제출, 응답을 받지 못한 클라이언트나 중간 장비의 재시도는 여전히 같은 POST를 두 번 만든다. 결제나 주문처럼 두 번 실행되면 곤란한 요청은 서버가 "같은 요청"을 알아볼 수 있어야 한다. 폼을 내려 줄 때 한 번만 쓸 수 있는 토큰을 함께 주거나, 요청마다 클라이언트가 고유한 키를 보내게 하거나, 데이터베이스의 유일 제약으로 두 번째 저장을 실패시키는 방법이 쓰인다. 버튼을 비활성화하는 자바스크립트는 사용자 경험을 돕지만 서버를 보호하지는 못한다.

    도메인 객체를 @ModelAttribute로 직접 받는 구조는 화면이 단순할 때만 유지된다. 이 회차의 실험에서 본 두 가지, 폼에 없는 필드가 채워지는 것과 폼에 없는 필드가 null로 덮이는 것은 방향만 다른 같은 문제다. 바인더는 "이 화면이 어떤 필드를 다루는가"를 모른다. 등록 화면과 수정 화면이 받는 필드가 달라지는 순간, 또는 사용자가 고치면 안 되는 필드가 객체에 생기는 순간 화면별 폼 객체로 나누는 편이 안전하다. 변환 코드가 늘어나는 비용은 있지만, 어떤 값이 외부 입력으로 바뀔 수 있는지가 타입에 드러난다.

    플래시 속성은 세션에 기대므로 세션의 운영 조건을 그대로 물려받는다. 서버가 여러 대이고 세션이 서버 메모리에만 있다면, 리다이렉트 뒤의 GET이 다른 서버로 가는 순간 메시지는 사라진다. 세션을 공유 저장소에 두거나 같은 서버로 보내 주는 구성이 있어야 한다. 세션을 쓰지 않기로 한 서비스라면 "한 번만 보여 줄 문구" 하나를 위해 세션을 만드는 것이 맞는지부터 따져야 한다. URL 파라미터로 타협하되 새로고침에 다시 보이는 것을 받아들이거나, 화면 쪽 스크립트로 처리하는 선택도 있다.

    메모리 저장소에서 본 문제는 데이터베이스로 옮겨도 형태만 바꿔 남는다. ID 발급은 시퀀스나 자동 증가 열이 맡고, 여러 필드의 수정은 트랜잭션이 한 덩어리로 묶는다. 그러나 수정 폼을 받은 시점과 저장하는 시점 사이의 갱신 유실은 트랜잭션 하나의 범위 밖에서 일어나므로 저절로 해결되지 않는다. 어떤 화면이 "마지막 저장이 이긴다"로 충분하고 어떤 화면이 충돌을 사용자에게 알려야 하는지는 기능마다 판단해야 한다.
  • 다음 저장소를 스프링 빈으로 등록했다. 스레드 두 개가 동시에 save를 한 번씩 호출할 때 나올 수 있는 결과를 모두 나열하고, store를 ConcurrentHashMap으로만 바꾸면 그중 무엇이 남는지 설명하라. 
    private final Map store = new HashMap<>();
private long sequence = 0L;

long save(String name) {
    long id = ++sequence;
    store.put(id, name);
    return id;
}

    @PostMapping("/{productId}/edit")

    1번. 두 스레드를 A, B라 하자. 증가 연산이 섞이지 않으면 A와 B가 1과 2(또는 2와 1)를 받고 맵에 두 항목이 들어간다. getfield와 putfield 사이에 섞이면 둘 다 0을 읽고 둘 다 1을 써서 sequence는 1이 되고 두 스레드가 같은 ID 1을 받는다. 이때 같은 키로 put이 두 번 일어나 나중 것만 남는다. 여기에 더해 HashMap은 동시 구조 변경을 견디지 못하므로, ID가 서로 달랐더라도 두 put이 섞여 한 항목이 빠질 수 있다. store만 ConcurrentHashMap으로 바꾸면 마지막 문제(맵 내부 손상)는 사라지지만 ID 중복은 그대로다. sequence의 읽기-더하기-쓰기가 여전히 한 덩어리가 아니기 때문이다. 같은 ID가 나오면 맵이 아무리 안전해도 두 번째 put은 첫 번째 값을 정상적으로 덮어쓴다. 그래서 AtomicLong까지 함께 바꿔야 한다.

    2번. 호출된다. 변환에 실패하는 값이 없기 때문이다. name=은 빈 문자열이므로 name = ""(null이 아니다). price=는 Integer에서 null이 된다. quantity는 파라미터가 없어 setter가 불리지 않고 null로 남는다. id=9는 폼에 그런 칸이 없었더라도 setId가 있으므로 id = 9가 된다. color는 대응하는 프로퍼티가 없어 무시된다. 만약 price=abc였다면 typeMismatch 오류가 기록되고, 매개변수 뒤에 BindingResult가 없으므로 예외가 던져져 메서드는 호출되지 않고 400으로 끝난다.

    3번. 뷰를 바로 돌려주는 경우 서버가 받는 요청은 POST /products/new 세 번이다. 새로고침은 화면을 만든 마지막 요청을 다시 보내는 것이고 그 요청이 POST이기 때문이다. 요청마다 바인더가 새 객체를 만들고 저장소가 새 ID를 주므로 상품은 세 개가 된다. 리다이렉트로 바꾸면 POST /products/new 한 번, 이어서 브라우저가 스스로 보낸 GET /products/1 한 번, 새로고침으로 같은 GET 두 번이다. 모두 네 번의 요청이 오지만 저장은 한 번뿐이라 상품은 한 개다. 요청 수는 오히려 늘었다는 점, 곧 PRG가 왕복 한 번을 비용으로 치른다는 점도 확인할 수 있다.

    4번. 리다이렉트 응답의 Location은 /products/{id}?status=true이고 message는 URL에 없다. 첫 화면에서는 param.status가 값을 갖고(URL의 쿼리 파라미터), message도 값을 갖는다(세션에 있던 플래시 속성이 모델로 옮겨졌다). 새로고침하면 브라우저가 같은 URL로 GET을 다시 보내므로 param.status는 여전히 값을 갖는다. message는 첫 요청에서 꺼내지며 세션에서 지워졌으므로 값이 없다. URL에 실은 값은 URL이 살아 있는 한 반복되고, 플래시 속성은 한 번 소비되면 끝이라는 차이다. 한 번만 보여 줄 문구라면 status가 아니라 message 쪽 조건으로 그려야 한다.

    5번. 이 코드는 고칠 대상을 본문의 id에서 얻는다. 경로의 productId는 매핑에만 쓰이고 버려진다. 요청을 직접 만드는 사용자는 /products/1/edit로 보내면서 본문에 id=555를 넣어 555번 상품을 고칠 수 있다. 뒤에 경로를 기준으로 권한을 검사하는 코드가 붙더라도 실제로 고쳐지는 것은 본문이 가리키는 상품이어서 검사가 무력해진다. 본문에 id가 아예 없으면 form.getId()가 null이고, update 안의 ConcurrentHashMap.get(null)이 NullPointerException을 던져 리다이렉트에 이르지 못하고 500으로 끝난다. 대상은 경로 변수로 정하고 본문의 ID는 믿지 않아야 한다. 수량 칸을 뺀 폼에서는 quantity 파라미터가 오지 않아 form.getQuantity()가 null이고, update가 그 null을 저장소 객체에 덮어써 기존 수량이 지워진다. 그 화면이 다루는 필드만 가진 폼 객체를 따로 두고 해당 필드만 옮겨 적어야 한다.

     싱글톤 저장소의 long sequence를 ++sequence로 증가시킬 때, 두 요청이 같은 ID를 받을 수 있는 근본 이유는 무엇인가? long이 64비트여서 JVM이 값을 절반씩 나누어 쓰기 때문이다 증가가 힙의 값을 읽고, 스택에서 더하고, 힙에 다시 쓰는 여러 명령으로 이루어져 있어 그 사이에 다른 스레드가 같은 값을 읽을 수 있기 때문이다 톰캣이 요청마다 저장소 객체를 새로 만들어 sequence가 0에서 다시 시작하기 때문이다 HashMap이 같은 키를 허용하지 않아 ID를 다시 계산하기 때문이다 바이트코드에서 ++sequence는 getfield, ladd, putfield로 나뉜다. 두 스레드가 모두 getfield로 같은 값을 읽은 뒤 각자 1을 더해 쓰면 증가가 한 번만 반영된다. 이 회차의 실험에서 일어난 유실은 64비트 값의 분할 쓰기와는 다른 현상이다. 저장소는 싱글톤이라 요청마다 새로 만들어지지 않으며, 그래서 오히려 필드가 공유된다. HashMap은 같은 키가 오면 값을 덮어쓸 뿐 ID 계산에는 관여하지 않는다. @ModelAttribute Product product를 받는 컨트롤러 메서드에 대해 옳은 설명은? 컨트롤러 메서드가 먼저 실행되고, 메서드 안에서 product의 getter를 처음 부를 때 요청 파라미터가 읽힌다 바인더는 폼 HTML에 있던 입력 칸의 이름만 채우므로 폼에 없는 필드는 요청에 들어 있어도 무시된다 메서드가 호출되기 전에 인자 리졸버가 객체를 만들고, 데이터 바인더가 파라미터 이름에 맞는 setter를 리플렉션으로 호출해 값을 채운 뒤 모델에도 넣는다 가격에 숫자가 아닌 문자열이 오면 해당 필드만 null로 두고 항상 메서드를 정상 호출한다 호출 스택에서 본 대로 바인딩은 getMethodArgumentValues 단계, 곧 컨트롤러 메서드 호출 전에 끝난다. 서버는 폼 HTML을 알지 못하고 요청에 실려 온 이름만 본다. 그래서 폼에 없던 id=777도 setter가 있으면 채워진다. 타입 변환에 실패하면 오류가 기록되고, 매개변수 뒤에 BindingResult가 없으면 예외가 던져져 메서드는 호출되지 않는다. 등록 처리 후 뷰를 바로 렌더링하지 않고 리다이렉트로 응답하면 새로고침에 의한 중복 등록이 사라지는 이유는? 브라우저가 302 응답의 Location으로 GET을 새로 보내므로, 새로고침이 다시 보내는 마지막 요청이 POST가 아니라 GET이 되기 때문이다 302 응답을 받으면 브라우저가 POST 본문을 캐시에서 지우고 서버가 같은 본문을 거부하기 때문이다 리다이렉트는 서버 내부에서 처리되어 브라우저가 요청을 한 번만 보낸 것으로 기록하기 때문이다 스프링이 같은 세션의 두 번째 POST를 자동으로 감지해 무시하기 때문이다 새로고침은 화면을 만든 마지막 요청의 재전송이다. PRG는 그 마지막 요청을 조회용 GET으로 바꿔 놓는다. 서버가 같은 본문의 POST를 알아보고 거부하는 기능은 기본으로 없으며, 그래서 응답 전의 두 번 클릭 같은 경우는 PRG로 막지 못한다. 서버 내부에서 처리되어 브라우저가 모르는 것은 포워드이고, 포워드에서는 마지막 요청이 POST로 남아 문제가 그대로다. 리다이렉트 URL을 "redirect:/products?keyword=" + keyword처럼 문자열 연결로 만들 때의 문제와 RedirectAttributes.addAttribute("keyword", keyword)의 차이를 바르게 설명한 것은? 두 방식은 결과가 같고, addAttribute는 코드를 짧게 해 줄 뿐이다 문자열 연결은 값을 세션에 저장하고 addAttribute는 URL에 저장한다 addAttribute는 값을 URL에 넣지 않고 다음 요청의 모델에 직접 넣어 준다 문자열 연결은 값을 인코딩하지 않아 한글이나 &가 헤더를 무효로 만들거나 파라미터 구조를 바꿀 수 있고, addAttribute는 값을 인코딩해 경로 변수나 쿼리 파라미터로 넣는다 실험에서 한글이 그대로 들어간 Location 헤더는 톰캣이 제거했고, &가 든 값은 별도의 파라미터로 갈라졌다. addAttribute로 넣은 값은 퍼센트 인코딩되어 &가 %26으로 남았다. 세션에 저장했다가 다음 요청의 모델에 넣어 주는 것은 addFlashAttribute의 동작이다. addFlashAttribute("message", "저장되었습니다")로 리다이렉트한 뒤 도착한 화면을 새로고침했더니 메시지가 사라졌다. 이 동작의 원인으로 옳은 것은? 플래시 속성이 URL의 쿼리 파라미터로 전달되는데 브라우저가 새로고침 때 쿼리 문자열을 지우기 때문이다 플래시 속성은 리다이렉트 전에 세션에 저장되었다가 다음 요청에서 모델로 옮겨지면서 세션에서 제거되므로, 그다음 요청에는 남아 있지 않기 때문이다 타임리프의 템플릿 캐시가 메시지가 있는 화면을 한 번만 보관하기 때문이다 플래시 속성은 싱글톤 컨트롤러의 필드에 저장되어 다른 요청이 덮어쓰기 때문이다 플래시 속성은 URL에 나타나지 않는다. 세션에 잠깐 보관되고, 다음 요청이 시작될 때 꺼내져 모델에 더해진 뒤 지워진다. 실험에서도 첫 GET의 뷰가 그려질 때 세션의 속성 목록은 이미 비어 있었다. 템플릿 캐시는 파싱된 템플릿 구조를 보관할 뿐 렌더링 결과나 모델 값을 보관하지 않는다.
    정적 리소스(static resource)
    요청과 무관하게 내용이 고정된 파일. 스프링 부트에서는 클래스패스의 /static 등에 두면 파일 경로가 URL이 된다.
    내추럴 템플릿(natural template)
    템플릿 기능을 HTML 속성으로 넣어, 서버 없이 브라우저로 열어도 온전한 HTML로 보이는 템플릿.
    갱신 유실(lost update)
    둘 이상의 실행 흐름이 같은 값을 읽고 각자 고쳐 쓴 결과, 한쪽의 변경이 덮여 사라지는 현상.
    폼 URL 인코딩(application/x-www-form-urlencoded)
    HTML 폼의 기본 전송 형식. 이름=값 쌍을 &로 잇고, 값의 바이트를 퍼센트 인코딩한다.
    데이터 바인딩(data binding)
    요청 파라미터 같은 문자열 값을 타입 변환을 거쳐 객체의 프로퍼티에 넣는 일. 스프링에서는 DataBinder가 맡는다.
    모델 애트리뷰트(@ModelAttribute)
    요청 값으로 채운 객체를 컨트롤러 인자로 넘기고 같은 객체를 모델에도 담게 하는 애너테이션.
    멱등(idempotent)
    같은 요청을 여러 번 보내도 서버에 의도한 효과가 한 번 보낸 것과 같은 성질. RFC 9110에서 PUT, DELETE, 안전한 메서드가 이에 해당하고 POST는 아니다.
    PRG(Post/Redirect/Get)
    POST 요청을 처리한 뒤 리다이렉트로 응답해 브라우저가 GET으로 결과 화면을 받게 하는 패턴.
    리다이렉트(redirect)
    3xx 상태 코드와 Location 헤더로 클라이언트에게 다른 URL을 다시 요청하게 하는 응답. 서버 내부에서 처리를 넘기는 포워드와 달리 요청이 둘이 된다.
    플래시 속성(flash attribute)
    한 요청이 다음 요청에 넘기려고 잠시(보통 세션에) 저장하는 값. 다음 요청에서 쓰이고 바로 제거된다.
