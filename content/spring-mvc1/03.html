    이 회차의 질문: 같은 화면을 세 번 만들면 무엇이 남는가

    앞의 두 회차에서 서블릿 컨테이너가 HTTP 메시지를 요청·응답 객체로 바꿔 서블릿을 호출한다는 것, 그 호출이 스레드 풀의 스레드 위에서 일어난다는 것, 요청 객체에서 파라미터를 꺼내고 응답 객체에 글자를 쓰는 방법을 다뤘다. 재료는 다 모였다. 이번 회차는 그 재료로 화면 세 개짜리 작은 웹 애플리케이션을 만든다. 다만 한 번이 아니라 세 번 만든다.

    대응 섹션의 소재는 회원 관리다. 이 원고는 크기가 같은 다른 소재인 책 등록으로 예제를 새로 만들었다. 폼을 보여 주고, 입력을 저장하고, 목록을 조회한다는 뼈대는 소재와 무관하게 같다. 실험은 OpenJDK 21과 임베디드 톰캣 11.0.27(Servlet 6.1)에서 돌렸고, 규칙은 Spring Boot 3.x가 쓰는 톰캣 10.1의 기준인 Servlet 6.0·Pages 3.1 명세와 톰캣 10.1 문서로 확인했다.

    요구사항: 등록하고, 저장하고, 목록을 본다

    만들 것은 책을 등록하고 목록을 보는 애플리케이션이다. 책은 식별자(id), 제목(title), 쪽수(pages)를 가진다. 식별자는 사용자가 입력하지 않고 저장할 때 서버가 붙인다. 기능은 세 가지다.

    • 등록 폼: 제목과 쪽수를 입력하는 HTML 폼을 보여 준다(GET).
    • 저장: 폼이 보낸 값을 받아 책을 저장하고 결과를 보여 준다(POST).
    • 목록: 저장된 책을 모두 보여 준다(GET).

    이 셋은 웹 애플리케이션의 가장 작은 단위다. 화면을 주고, 입력을 받아 상태를 바꾸고, 바뀐 상태를 다시 화면으로 보여 준다. 쇼핑몰의 상품 등록이든 게시판의 글쓰기든 규모만 다를 뿐 같은 순환을 돈다. 데이터베이스는 아직 쓰지 않고 메모리에 저장한다. 서버를 내리면 데이터가 사라지지만, 지금 관심사는 저장 기술이 아니라 요청이 화면이 되기까지의 구조다.

    package shelf;

public class Book {
    private Long id;
    private final String title;
    private final int pages;

    public Book(String title, int pages) {
        this.title = title;
        this.pages = pages;
    }

    public Long getId() { return id; }
    public void setId(Long id) { this.id = id; }
    public String getTitle() { return title; }
    public int getPages() { return pages; }
}
    package shelf;

import java.util.ArrayList;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.atomic.AtomicLong;

public class BookRepository {
    private static final BookRepository instance = new BookRepository();

    private final Map store = new ConcurrentHashMap<>();
    private final AtomicLong sequence = new AtomicLong();

    private BookRepository() { }

    public static BookRepository getInstance() { return instance; }

    public Book save(Book book) {
        book.setId(sequence.incrementAndGet());
        store.put(book.getId(), book);
        return book;
    }

    public Book findById(Long id) { return store.get(id); }

    public List findAll() { return new ArrayList<>(store.values()); }
}

    클래스에 패키지(shelf)를 붙인 데는 이유가 있다. 뒤에서 JSP가 이 클래스들을 import하는데, 이름 없는 패키지의 클래스는 다른 패키지에서 임포트할 수 없기 때문이다. 저장소는 스프링 없이 직접 구현한 싱글톤이다. 생성자를 private으로 막고 static 필드에 하나만 만들어 둔다. 스프링 핵심 원리 권에서 본 것처럼 스프링 컨테이너를 쓰면 이 코드는 필요 없지만, 지금은 서블릿과 JSP만으로 만들기로 했으므로 손으로 한다.

    메모리 저장소가 드러내는 동시성

    저장소의 두 필드가 HashMap과 long이 아니라 ConcurrentHashMap과 AtomicLong인 이유는 01회차의 결론에서 곧바로 나온다. 서블릿 컨테이너는 서블릿 객체를 하나 만들어 두고 요청이 올 때마다 스레드 풀의 스레드로 그 객체의 메서드를 호출한다. 저장소 객체도 하나뿐이다. 두 사용자가 동시에 등록 버튼을 누르면 두 스레드가 같은 저장소의 save를 동시에 실행한다. 이때 평범한 필드가 어떻게 깨지는지 직접 보자. 아래는 일부러 안전장치를 뺀 저장소다.

    import java.util.HashMap;
import java.util.Map;

public class UnsafeStore {
    private static final Map store = new HashMap<>();
    private static long sequence = 0L;

    public static long save(String title) {
        long id = ++sequence;
        store.put(id, title);
        return id;
    }
    public static int size() { return store.size(); }
    public static long lastId() { return sequence; }
}

    왼쪽 두 열의 값은 실행마다 다르다. 스레드가 어디에서 끼어드는지가 매번 달라서다. 그래도 읽어 낼 수 있는 것이 있다. 마지막 번호가 80만에 못 미친다는 것은 같은 번호가 여러 번 발급됐다는 뜻이고, 같은 번호로 put하면 나중 것이 앞의 것을 덮어쓰므로 등록한 책 가운데 상당수가 사라졌다는 뜻이다. 또 하나 이상한 점은 위 세 번의 실행에서 size()가 마지막 번호보다 크다는 것이다(다시 돌려 보면 작게 나오는 실행도 있다). 키로 쓰인 값은 1부터 마지막 번호까지뿐이니 서로 다른 키는 많아야 그만큼인데, HashMap이 스스로 세는 개수는 그보다 많다. 맵의 내부 상태 자체가 실제 내용과 어긋난 것이다. HashMap은 동기화되지 않는 구현이어서, 여러 스레드가 동시에 접근하면서 그중 하나라도 구조를 바꾼다면 바깥에서 동기화해 주어야 한다.

    AtomicLong.incrementAndGet()은 읽기·더하기·쓰기를 다른 스레드가 끼어들 수 없는 한 동작으로 수행하고, ConcurrentHashMap은 동시 put을 견디도록 만들어졌다. 그 내부(CAS와 락)는 자바 고급 1편에서 다룬다. 여기서 기억할 것은 한 가지다. 웹 애플리케이션에서 "객체 하나를 모든 요청이 공유한다"는 말은 곧 "그 객체의 필드는 여러 스레드가 동시에 건드린다"는 말이다.

    이 요청 하나가 처리되는 과정을 한 줄씩 따라가 보자. 브라우저가 폼의 등록 버튼을 누르면 입력값이 application/x-www-form-urlencoded 형식의 본문으로 전송된다. 컨테이너는 getParameter("title")이 호출되면 이 본문을 해석해 문자열 "JVM"을 돌려준다(이 해석 규칙은 02회차의 몫이다). 파라미터는 언제나 문자열이므로 쪽수는 Integer.parseInt로 직접 숫자로 바꿔야 한다. 저장소가 번호를 붙여 저장하고 나면 응답 차례다. 콘텐츠 타입과 문자 인코딩을 먼저 정하고 getWriter()를 얻는 순서가 중요하다. Servlet API 문서는 getWriter가 호출된 뒤에는 응답의 문자 인코딩이 더는 바뀌지 않는다고 적는다. 이 인코딩에 따라 한글이 바이트로 바뀌어 응답 버퍼에 쌓이고, service가 돌아오면 컨테이너가 응답을 마무리해 보낸다.

    동적 HTML의 정체

    여기서 "동적 HTML"이라는 말의 실체가 보인다. 요청마다 달라지는 값을 사이사이에 끼워 넣어 조립한 문자열이다. 브라우저 쪽에서 보면 정적 파일과 구별할 방법이 없다. 상태 줄이 있고, Content-Type: text/html;charset=UTF-8 헤더가 있고, 본문에 HTML 글자가 있을 뿐이다. 서버가 디스크의 파일을 읽어 보냈는지 방금 문자열을 이어 붙여 만들었는지는 HTTP 메시지에 드러나지 않는다. 템플릿 엔진이든 JSP든 뒤에 나오는 모든 뷰 기술은 결국 이 문자열 조립을 더 편하고 덜 위험하게 하는 방법이다.

    무엇이 곤란한가

    동작은 한다. 하지만 이 방식으로 실제 서비스의 화면을 만든다고 생각하면 곤란한 점이 줄줄이 나온다.

    • HTML이 자바 문자열 안에 갇힌다. 저장 서블릿의 \"UTF-8\"처럼 큰따옴표마다 역슬래시를 붙이고 줄바꿈을 \n으로 적어야 한다. 폼 서블릿처럼 텍스트 블록(Java 15부터 정식 기능)을 쓰면 이 부분은 나아지지만 아래 문제들은 그대로다.
    • 반복과 조건이 문서를 조각낸다. 목록 서블릿에서 표 하나가 for 문을 사이에 두고 세 토막의 문자열로 나뉘었다. 화면이 복잡해질수록 완성된 HTML이 어떤 모양일지 코드만 보고 떠올리기 어려워진다.
    • 도구가 돕지 못한다. 컴파일러에게 이것은 그냥 문자열이다. 태그를 닫지 않아도 컴파일은 통과하고, 오류는 브라우저 화면이 깨진 뒤에야 드러난다.
    • 문구 하나를 고쳐도 자바를 다시 컴파일하고 배포해야 한다. 화면을 다루는 사람이 자바 소스를 고쳐야 한다는 뜻이기도 하다.
    • 이스케이프를 잊기 쉽다. 아래에서 따로 본다.

    package shelf;

public final class Html {
    private Html() { }

    public static String escape(String s) {
        StringBuilder sb = new StringBuilder(s.length());
        for (int i = 0; i < s.length(); i++) {
            char c = s.charAt(i);
            switch (c) {
                case '<' -> sb.append("&lt;");
                case '>' -> sb.append("&gt;");
                case '&' -> sb.append("&amp;");
                case '"' -> sb.append("&quot;");
                case '\'' -> sb.append("&#39;");
                default -> sb.append(c);
            }
        }
        return sb.toString();
    }
}

    Html.escape("")의 결과는 &lt;script&gt;alert(1)&lt;/script&gt;이고, 브라우저는 이것을 태그가 아니라 꺾쇠 글자가 들어간 텍스트로 화면에 보여 준다. 문제는 이 함수를 만드는 것이 아니라 모든 출력 지점에서 빠짐없이 부르는 것이다. 문자열을 손으로 이어 붙이는 방식에서는 한 곳만 잊어도 구멍이 된다. 뷰 기술을 고를 때 "기본 동작이 이스케이프인가"를 따지는 이유가 여기에 있다.

    JSP: 문서 안에 코드를 넣는다

    서블릿 방식의 불편은 한 문장으로 줄일 수 있다. 화면의 대부분은 고정된 HTML인데, 그 HTML을 자바 코드 안에 넣었다. 그렇다면 뒤집으면 된다. HTML 문서를 그대로 쓰고, 값이 바뀌어야 하는 자리에만 코드를 넣는다. 이렇게 고정된 문서 틀에 동적인 값을 끼워 결과 문서를 만들어 내는 도구를 템플릿 엔진(template engine)이라고 하고, 그 가운데 Jakarta EE 표준 명세로 정해져 있는 것이 JSP(Jakarta Server Pages, 예전 이름은 JavaServer Pages)다.

    JSP는 서블릿으로 번역된다

    JSP 파일을 그대로 실행하는 무언가가 있는 것이 아니다. Jakarta Server Pages 3.1 명세는 JSP 페이지가 JSP 페이지 구현 클래스(JSP page implementation class)를 정의하고, 그 클래스는 jakarta.servlet.Servlet 인터페이스를 구현한다고 적는다. JSP는 서블릿의 다른 표기법이다. 명세는 JSP 컨테이너가 페이지의 생애를 두 단계로 관리한다고 설명한다. 페이지마다 한 번 수행하는 번역 단계(translation phase)와 요청마다 수행하는 요청 단계(request phase)다. 번역은 페이지가 배포된 시점부터 그 페이지에 대한 첫 요청이 올 때까지의 사이 어느 때든 일어날 수 있다.

    톰캣에서 이 일을 맡는 부품이 Jasper다. 톰캣의 전역 설정 파일 conf/web.xml에는 *.jsp와 *.jspx로 끝나는 주소를 org.apache.jasper.servlet.JspServlet이라는 서블릿에 매핑하는 설정이 들어 있다. 즉 .jsp로 끝나는 요청을 실제로 받는 것은 JSP 파일이 아니라 이 서블릿이다. 톰캣 10.1을 기준으로 /jsp/books/save.jsp에 대한 첫 요청은 이렇게 처리된다.

    JSP는 한 번 번역·컴파일되어 서블릿 객체가 되고, 그 뒤 요청은 이미 만들어진 객체의 메서드 호출일 뿐이라는 점을 보여 준다. 왼쪽에서 오른쪽으로 흐르는 가로 순서도. 위쪽 줄에 상자 네 개를 화살표로 잇는다. 첫 상자는 문서 아이콘과 라벨 "save.jsp", 둘째 상자는 "save_jsp.java (자바 소스)", 셋째 상자는 "save_jsp.class", 넷째 상자는 톱니 아이콘과 "서블릿 인스턴스 1개". 첫째에서 둘째로 가는 화살표에 "번역", 둘째에서 셋째로 가는 화살표에 "컴파일", 셋째에서 넷째로 가는 화살표에 "적재·초기화". 이 세 화살표를 묶는 중괄호 위에 "번역 단계: 페이지당 한 번". 아래쪽 줄에는 왼쪽에 브라우저 아이콘 세 개가 세로로 있고 각각 넷째 상자를 향해 화살표를 보낸다. 화살표 묶음 옆에 "_jspService(request, response) 호출", 그 아래에 "요청 단계: 요청마다". 차분한 기술 문서 스타일, 흰 배경, 파란색과 회색 위주. 번역과 컴파일은 페이지당 한 번, _jspService 호출은 요청마다 일어난다.

    번역된 코드를 읽는다

    Jasper가 save.jsp로부터 만들어 내는 클래스의 뼈대는 다음과 같다. 톰캣 10.1의 Jasper 코드 생성기 소스를 읽고 핵심만 추린 것이다. 실제 생성 코드에는 허용할 HTTP 메서드를 검사하는 부분, 의존 파일을 추적하는 부분 같은 것이 더 들어 있다.

    package org.apache.jsp.jsp.books;

import shelf.Book;
import shelf.BookRepository;
// ...

public final class save_jsp extends org.apache.jasper.runtime.HttpJspBase /* ... */ {

    public void _jspService(final jakarta.servlet.http.HttpServletRequest request,
                            final jakarta.servlet.http.HttpServletResponse response)
            throws java.io.IOException, jakarta.servlet.ServletException {

        final jakarta.servlet.jsp.PageContext pageContext;
        jakarta.servlet.http.HttpSession session = null;
        final jakarta.servlet.ServletContext application;
        final jakarta.servlet.ServletConfig config;
        jakarta.servlet.jsp.JspWriter out = null;
        final java.lang.Object page = this;
        // ...
        try {
            response.setContentType("text/html;charset=UTF-8");
            pageContext = _jspxFactory.getPageContext(this, request, response, null, true, 8192, true);
            application = pageContext.getServletContext();
            config = pageContext.getServletConfig();
            session = pageContext.getSession();
            out = pageContext.getOut();

            // 스크립틀릿: 쓰인 그대로 복사된다
            BookRepository repository = BookRepository.getInstance();
            String title = request.getParameter("title");
            int pages = Integer.parseInt(request.getParameter("pages"));
            Book book = repository.save(new Book(title, pages));

            // 템플릿 텍스트: 문자열 리터럴을 출력하는 문장이 된다
            // ... (문서 앞부분을 출력하는 out.write 문장들)
            out.write("
    저장했습니다.
    \n");
            out.write("
      \n");
            out.write("  
    • id=");
            // 표현식: out.print(식)이 된다
            out.print(book.getId());
            out.write("
      • \n");
            out.write("  
    • title=");
            out.print(book.getTitle());
            // ...
        } catch (java.lang.Throwable t) {
            // 버퍼를 정리하고 pageContext.handlePageException(t)에 넘긴다
        } finally {
            _jspxFactory.releasePageContext(_jspx_page_context);
        }
    }
}

    첫 번째 버전에서 손으로 쓴 저장 서블릿과 비교해 보자. 파라미터를 읽고, 저장하고, out.write로 HTML 조각을 출력하고, 그 사이에 값을 출력한다. 같은 코드다. 문자열에 역슬래시를 붙이고 조각을 나누는 귀찮은 일을 사람 대신 번역기가 했을 뿐이다. 상위 클래스 HttpJspBase는 HttpServlet을 상속하고, 그 service 메서드가 하는 일은 _jspService를 호출하는 것 하나다. 명세의 HttpJspPage 인터페이스 문서는 _jspService가 JSP 페이지의 몸통에 해당하며 컨테이너가 자동으로 정의하므로 페이지 작성자가 직접 정의해서는 안 된다고 적는다.

    번역 규칙이 설명해 주는 것들

    번역된 모양을 알면 앞 절에서 이상해 보였던 것들과 JSP의 여러 성질이 한꺼번에 설명된다.

    • 선언 없이 쓰는 변수의 정체. request와 response는 _jspService의 매개변수이고, out·session·application·config·pageContext·page는 그 메서드 첫머리에 선언되는 지역 변수다. 명세는 이들을 암묵 객체(implicit object)라고 부른다. 스크립틀릿은 같은 메서드 안에 복사되므로 이 변수들이 보인다.
    • 쪼개진 중괄호가 허용되는 이유. 스크립틀릿 하나하나가 완결된 자바 문장일 필요는 없다. 전부 복사해 이어 붙인 결과가 올바른 자바이면 된다. 목록 JSP의 for (Book book : books) {와 } 사이에 놓인 템플릿 텍스트와 표현식은 번역 후 반복문 몸통 안의 out.write와 out.print가 된다.
    • 스크립틀릿의 변수는 요청마다 따로 있다. title, pages, book은 _jspService의 지역 변수다. 지역 변수는 호출마다 그 스레드의 스택 프레임에 새로 만들어지므로 동시에 들어온 다른 요청과 섞이지 않는다.
    • 선언의 변수는 모든 요청이 공유한다. <%! int count; %>처럼 선언으로 적은 것은 메서드 밖, 클래스의 멤버로 들어간다. 인스턴스는 하나이므로 이 필드는 앞에서 본 UnsafeStore.sequence와 똑같은 처지가 된다. 명세도 선언은 페이지가 초기화될 때 초기화된다고 구분해 적는다.
    • 문법 오류는 실행할 때 드러난다. JSP 안의 자바는 번역된 뒤에야 컴파일된다. 중괄호 하나를 빠뜨린 실수는 서버를 빌드할 때가 아니라 그 페이지가 번역되는 시점에 컴파일 오류로 나타난다.
    • 첫 요청이 느리다. 첫 요청은 번역과 컴파일 비용을 함께 치른다. 톰캣 문서는 JSP의 주된 최적화로 미리 컴파일해 두는 것(precompilation)을 든다.
    • 세션이 기본으로 연결된다. page 지시자의 session 속성은 기본값이 true이고, 이때 암묵 변수 session은 현재 세션 또는 새로 만든 세션을 가리킨다. 세션이 필요 없는 페이지는 <%@ page session="false" %>로 꺼야 불필요한 세션이 생기지 않는다.
    • 출력은 버퍼를 거친다. out은 JspWriter이고, 기본 설정에서 8kb 이상의 버퍼를 가지며 가득 차면 자동으로 비운다(buffer와 autoFlush 속성의 기본값).

    개발 중에 JSP를 고치면 서버를 다시 띄우지 않아도 반영되는 것도 같은 구조에서 나온다. Jasper의 development 설정은 기본값이 true이고, 이 모드에서는 페이지에 접근할 때 원본 파일이 바뀌었는지 검사해 바뀌었으면 다시 번역한다. 검사를 너무 자주 하지 않도록 마지막 검사로부터 일정 시간(modificationTestInterval, 기본 4초) 안에는 다시 검사하지 않는다. 톰캣 문서는 운영 환경에서는 development를 false로 두어 접근 때마다 하는 검사를 끄라고 권한다.

    Spring Boot에서 JSP를 쓰는 데는 제약이 있다. Spring Boot 참고 문서는 임베디드 서블릿 컨테이너와 함께 쓸 때 톰캣과 제티에서는 war 패키징이면 동작하지만 실행 가능한 jar에서는 JSP가 지원되지 않는다고 적고, 가능하면 JSP를 피하라고 권한다. 이 회차가 JSP를 다루는 목적은 JSP 사용법이 아니라 템플릿 엔진과 뷰가 무엇인지를 가장 단순한 형태로 보는 데 있다.

    JSP만으로 만들었을 때 남는 문제

    JSP 버전은 HTML을 쓰기 편해졌다. 그런데 save.jsp를 다시 보면 파일이 위아래로 갈라져 있다. 위쪽 절반은 파라미터를 읽고 저장소를 호출하는 자바 코드이고, 아래쪽 절반은 결과를 보여 주는 HTML이다. 서블릿 버전에서는 자바 안에 HTML이 섞여 있었고, 이번에는 HTML 문서 안에 업무 로직이 섞여 있다. 섞였다는 사실은 그대로다.

    예제가 작아서 지금은 견딜 만하다. 하지만 실제 저장 로직은 입력 검증, 중복 확인, 트랜잭션, 다른 시스템 호출로 수백 줄이 되고, 실제 화면도 수백 줄이다. 그것이 한 파일에 있으면 다음과 같은 일이 생긴다.

    • 화면 문구를 고치려는 사람이 업무 로직을 건드릴 수 있고, 업무 규칙을 고치려는 사람이 화면을 깨뜨릴 수 있다.
    • 같은 저장 로직을 다른 화면이나 JSON API에서도 쓰고 싶어도 JSP 안에 들어 있는 코드는 꺼내 부를 방법이 없다.
    • 업무 로직을 검증하려면 컨테이너를 띄워 페이지를 요청해야 한다. 자바 메서드를 직접 호출하는 단위 테스트를 쓸 수 없다.
    • JSP가 저장소에 직접 손을 댄다. 화면을 그리는 코드가 데이터를 바꿀 수 있는 구조에서는 "이 데이터가 어디서 바뀌는가"를 찾으려면 모든 화면 파일을 뒤져야 한다.

    정리하면 문제는 JSP라는 기술이 아니라 한 덩어리가 두 가지 일을 한다는 점이다. 요청을 처리하는 일과 결과를 표현하는 일을 나눌 차례다.

    MVC 패턴 — 개요: 바뀌는 이유가 다른 것을 나눈다

    MVC(Model-View-Controller)는 한 덩어리가 하던 일을 세 역할로 나누는 설계 패턴이다. 웹 애플리케이션에서 세 역할은 이렇게 정해진다.

    • 컨트롤러(controller): HTTP 요청을 받는다. 파라미터를 꺼내 검증하고, 업무 로직을 실행하거나 호출하고, 그 결과 가운데 화면에 필요한 것을 모델에 담는다.
    • 모델(model): 뷰에 전달할 데이터를 담는 통이다. 컨트롤러가 채우고 뷰가 읽는다.
    • 뷰(view): 모델에 담긴 데이터를 읽어 화면을 그린다. 여기서는 HTML을 만드는 일이다.

    무엇을 기준으로 나누는가. 바뀌는 이유다. 화면의 생김새는 디자인이나 문구 때문에 바뀌고, 업무 로직은 정책 때문에 바뀐다. 두 변화는 서로 다른 때에 서로 다른 사람의 요청으로 일어난다. 변경의 이유가 다른 코드를 한 파일에 두면 한쪽을 고칠 때마다 다른 쪽이 위험해진다. 아래 표는 같은 변경 요청이 들어왔을 때 어디를 고치게 되는지를 비교한 것이다.

    모델이 맡는 구실을 눈여겨봐야 한다. 뷰는 모델에 담겨 온 것만 안다. 그 데이터가 메모리의 맵에서 나왔는지 데이터베이스에서 나왔는지, 어떤 검증을 거쳤는지 모른다. 반대로 컨트롤러는 그 데이터가 표로 그려질지 카드로 그려질지 모른다. 이 "모른다"가 분리의 실체다. 서로 모르기 때문에 한쪽을 바꿔도 다른 쪽을 고칠 필요가 없다.

    컨트롤러와 업무 로직의 관계도 짚어 둔다. 컨트롤러에 업무 로직을 모두 넣으면 이번에는 컨트롤러가 너무 많은 일을 하게 된다. 그래서 보통은 업무 로직을 서비스(service)라는 별도 계층에 두고, 컨트롤러는 요청을 해석해 서비스를 호출하는 일까지만 한다. 이 회차의 예제는 업무 로직이 저장소를 한 번 부르는 것이 전부라서 컨트롤러가 저장소를 직접 호출한다.

    식당에서 가져온 비유주문을 받는 사람, 쟁반, 접시에 담는 사람

    홀 직원은 손님의 주문을 받아 알아들을 수 있는 형태로 주방에 넘기고, 완성된 음식을 쟁반에 받아 온다. 접시에 담아 내는 사람은 쟁반에 올라온 것만 보고 모양을 낸다. 그 음식이 어떤 재료와 과정으로 만들어졌는지는 몰라도 된다. 홀 직원이 컨트롤러, 쟁반이 모델, 담아 내는 사람이 뷰다. 비유가 맞지 않는 지점도 있다. 식당에서는 사람들이 각자 움직이지만, 뒤에서 보듯 웹의 뷰는 컨트롤러와 같은 스레드에서 이어서 호출되는 코드다.

    MVC 패턴 — 적용: 서블릿은 컨트롤러, JSP는 뷰, request는 모델 보관함

    이미 가진 재료로 세 역할을 구현한다. 요청을 받고 자바 코드를 실행하는 데는 서블릿이 낫고, HTML을 쓰는 데는 JSP가 낫다. 그래서 서블릿이 컨트롤러를, JSP가 뷰를 맡는다. 남은 것은 모델이다. 컨트롤러가 만든 데이터를 뷰에게 어떻게 건넬 것인가.

    요청 속성: 요청 하나 동안만 사는 보관함

    HttpServletRequest에는 이름과 객체를 짝지어 넣어 두는 기능이 있다. setAttribute(이름, 객체)로 넣고 getAttribute(이름)으로 꺼낸다. Servlet API 문서는 setAttribute를 두고 속성은 요청과 요청 사이에 초기화되며 이 메서드는 RequestDispatcher와 함께 쓰이는 일이 가장 많다고 설명한다. 컨트롤러와 뷰가 같은 요청 객체를 보게 만들 수만 있다면 이 보관함이 그대로 모델이 된다. 요청 파라미터와 헷갈리기 쉬우므로 차이를 정리해 둔다.

@WebServlet("/books/save")
public class BookSaveController extends HttpServlet {
    private final BookRepository repository = BookRepository.getInstance();

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws ServletException, IOException {
        String title = request.getParameter("title");
        int pages = Integer.parseInt(request.getParameter("pages"));

    }
}

    Jasper는 JSP 파일 이름을 자바 식별자로 바꿔 클래스 이름을 만든다. 식별자에 쓸 수 없는 문자는 밑줄과 네 자리 16진 코드로 바뀌므로, 하이픈이 든 save-result.jsp의 클래스 이름은 save_002dresult_jsp가 된다(톰캣 10.1 소스 기준). 스택 트레이스에서 이런 이름을 보면 어느 JSP인지 거꾸로 읽어 낼 수 있다.

    forward는 서버 안에서 일어난다

    컨트롤러의 마지막 두 줄이 이 구조의 핵심이다. RequestDispatcher는 Servlet API 문서의 표현으로 서버에 있는 자원(서블릿, HTML 파일, JSP 파일)을 감싼 객체이고, 컨테이너가 만들어 준다. request.getRequestDispatcher(경로)에 넘긴 경로가 /로 시작하면 웹 애플리케이션의 루트(컨텍스트 루트)를 기준으로 해석된다. 이 객체의 forward를 호출하면 그 자원이 요청을 이어받아 응답을 만든다. 문서는 이 메서드가 한 서블릿이 요청의 사전 처리를 하고 다른 자원이 응답을 생성하게 해 준다고 설명한다. 컨트롤러와 뷰의 관계 그대로다.

    말로만 읽으면 forward가 무엇인지 흐릿하다. 실험으로 확인하자. JSP도 결국 서블릿이므로 뷰 자리에 서블릿을 하나 두고 forward하면 같은 동작을 관찰할 수 있다. 컨트롤러와 뷰가 각각 자신을 실행하는 스레드 이름, 디스패처 타입, 요청 URI, 요청 객체의 클래스를 출력한다. 뷰 서블릿은 /WEB-INF/views/save-result에 매핑했다. 서블릿을 등록하고 HTTP 요청을 보내는 부분은 01회차에서 임베디드 톰캣을 띄운 방식과 같아 생략한다.

    static void trace(String who, HttpServletRequest req) {
    System.out.printf("[%s] thread=%s dispatcher=%s uri=%s class=%s%n",
            who, Thread.currentThread().getName(), req.getDispatcherType(),
            req.getRequestURI(), req.getClass().getSimpleName());
}

    본문이 title=JVM&pages=320인 POST 요청을 /books/save로 한 번 보낸 결과다. 대괄호로 시작하는 줄은 서버가, 마지막 줄은 클라이언트가 찍었다.

    == POST /books/save
[controller] thread=http-nio-auto-1-exec-1 dispatcher=REQUEST uri=/books/save class=RequestFacade
[controller] before forward: committed=false
[view] thread=http-nio-auto-1-exec-1 dispatcher=FORWARD uri=/WEB-INF/views/save-result class=ApplicationHttpRequest
[view] original uri=/books/save, param title=JVM
[controller] after forward: committed=true
status=200 body=저장됨: JVM(320쪽)

    스레드 이름은 실행 환경에 따라 달라진다. 볼 것은 값 자체가 아니라 줄 사이의 관계다. 이 출력에서 여섯 가지 사실을 읽을 수 있다.

    1. HTTP 요청은 한 번뿐이다. 클라이언트는 POST 하나를 보내고 200 응답 하나를 받았다. 중간에 서버가 클라이언트에게 무언가를 돌려보낸 적이 없다. 브라우저였다면 주소창은 /books/save 그대로다. 브라우저는 뷰의 존재를 모른다.
    2. 같은 스레드다. 컨트롤러와 뷰가 찍은 스레드 이름이 같다. forward는 스레드를 바꾸거나 새 요청을 만드는 동작이 아니라 메서드 호출이다. 컨트롤러의 service가 forward를 부르고, 그 안에서 컨테이너가 뷰의 service를 부른다. 뷰가 실행되는 동안 컨트롤러의 스택 프레임은 그 아래에 그대로 남아 있다.
    3. 디스패처 타입이 바뀐다. 컨트롤러에서는 REQUEST, 뷰에서는 FORWARD다. 컨테이너는 이 값으로 호출이 클라이언트에게서 직접 온 것인지 서버 안에서 넘겨진 것인지 구별한다. 서블릿 필터가 기본으로 적용되는 대상은 REQUEST뿐이어서(@WebFilter의 dispatcherTypes 기본값), 따로 지정하지 않은 필터는 forward된 호출에 다시 끼어들지 않는다.
    4. 경로 정보는 대상 기준으로 바뀌고, 데이터는 그대로 따라온다. 뷰에서 getRequestURI()는 /WEB-INF/views/save-result를 돌려준다. 원래 주소는 jakarta.servlet.forward.request_uri라는 이름의 요청 속성에 보관된다. 요청 객체의 클래스가 달라진 것은 톰캣이 원래 요청을 래퍼로 감싸 경로 관련 메서드의 결과를 대상에 맞게 바꿔 보여 주기 때문이다. 파라미터 title과 속성 book은 뷰에서도 똑같이 읽힌다.
    5. forward 전에 쓴 내용은 지워진다. (A)에서 쓴 글자가 응답에 없다. 그 글자는 응답 버퍼에만 있었고 아직 클라이언트로 나가지 않았다(committed=false). API 문서는 커밋되지 않은 버퍼의 출력이 forward 전에 자동으로 지워진다고 적는다.
    6. forward가 돌아오면 응답은 끝나 있다. 돌아온 직후 committed=true이고, (B)에서 쓴 글자도 응답에 없다. 명세는 forward가 돌아오기 전에 응답이 전송·커밋되고 닫혀야 한다고 정한다. 그런데 (B) 줄 자체는 실행됐다는 점에 주의하자. forward 뒤의 코드는 건너뛰어지지 않는다. 응답에 반영되지 않을 뿐이다.
    요청 처리 스레드 하나의 호출 스택 (위쪽이 나중에 호출된 것)

  ResultView.service(req', resp)        뷰가 응답 본문을 쓴다
  ... 컨테이너의 디스패치 코드 ...       버퍼 비우기, 요청 감싸기, 대상 서블릿 찾기
  RequestDispatcher.forward(req, resp)
  SaveController.service(req, resp)     forward가 끝나면 이 프레임으로 돌아온다
  ... 컨테이너의 요청 처리 코드 ...
  스레드 풀 스레드의 run()

    톰캣 11.0.27의 ApplicationDispatcher.forward 소스는 이 순서를 그대로 담고 있다. 먼저 응답이 커밋됐는지 검사해 커밋됐으면 예외를 던지고, 응답 버퍼를 비우고(resetBuffer), 요청을 래퍼로 감싸 대상을 호출한 다음, 끝나면 응답에 더는 출력되지 않게 막는다(원래의 응답 객체이면 suspended 상태로 바꾸고, 래퍼로 감싼 응답이면 출력기를 닫는다). 이미 커밋된 응답으로 forward하면 어떻게 되는지도 확인했다. 글자를 쓰고 flushBuffer()로 응답을 내보낸 뒤 forward를 호출하는 서블릿을 만들어 요청하면 다음과 같다.

    == GET /commit-then-forward
[commit-then-forward] java.lang.IllegalStateException: Cannot forward after response has been committed
status=200 body=이미 나간 글자

    응답이 커밋됐다는 것은 상태 줄과 헤더가 이미 네트워크로 나갔다는 뜻이다. 나간 바이트는 되돌릴 수 없으므로 컨테이너는 다른 자원에게 응답을 처음부터 다시 만들게 할 방법이 없다. 그래서 명세는 이 경우 IllegalStateException을 던지도록 정한다. 컨트롤러가 뷰로 넘기기 전에 응답에 무언가를 쓰거나 내보내면 안 되는 이유다.

    redirect와 무엇이 다른가

    이름이 비슷해 자주 섞이는 것이 리다이렉트(redirect)다. response.sendRedirect("/books")를 호출하는 서블릿에 요청을 보내면 실험의 클라이언트는 이런 응답을 받는다.

    == GET /redirect
status=302 Location=/books

    서버는 화면을 만들지 않고 "다른 주소로 가라"는 응답을 돌려보냈다. 브라우저는 Location 헤더의 주소로 새 요청을 보낸다. HTTP 요청이 두 번 일어나고, 두 번째 요청은 완전히 새로운 요청이므로 요청 객체도 새로 만들어진다. 첫 요청에서 넣어 둔 속성은 남지 않는다.

    모델을 뷰에 넘겨야 하는 화면 렌더링에는 forward가 맞다. 반면 지금의 저장 컨트롤러에는 forward 때문에 생기는 문제가 하나 숨어 있다. 저장 결과 화면은 브라우저에게 POST /books/save의 응답이다. 이 화면에서 새로고침을 하면 브라우저는 마지막 요청, 즉 그 POST를 다시 보내고 같은 책이 한 번 더 저장된다. 상태를 바꾸는 요청 뒤에는 redirect로 조회 화면에 보내는 것이 해법이고, 08회차에서 PRG 패턴으로 다룬다.

    forward에서는 브라우저와 서버 사이를 화살표가 한 번 왕복하고, redirect에서는 두 번 왕복한다는 것을 나란히 비교한다. 좌우로 나란히 놓인 시퀀스 다이어그램 두 개. 왼쪽 제목 "forward", 오른쪽 제목 "redirect". 각 다이어그램에는 세로 생명선 세 개가 있다: "브라우저", "컨트롤러", "뷰". 왼쪽: 브라우저에서 컨트롤러로 화살표 "POST /books/save", 컨트롤러에서 뷰로 화살표 "forward (같은 스레드, 같은 요청)", 뷰에서 브라우저로 화살표 "200 HTML". 서버 쪽 두 생명선을 묶는 점선 상자에 "서버 내부". 아래에 "요청 1번, 주소 그대로". 오른쪽: 브라우저에서 컨트롤러로 화살표 "POST /books/save", 컨트롤러에서 브라우저로 화살표 "302 Location: /books", 브라우저에서 서버로 두 번째 화살표 "GET /books (새 요청)", 서버에서 브라우저로 화살표 "200 HTML". 아래에 "요청 2번, 주소 바뀜". 차분한 기술 문서 스타일, 흰 배경. forward는 서버 안의 메서드 호출이고, redirect는 브라우저에게 다시 요청하라고 시키는 응답이다.

    WEB-INF와 상대 경로: 브라우저가 볼 수 없는 것과 보는 것

    뷰 JSP를 WEB-INF 아래에 둔 이유를 볼 차례다. JSP만 쓴 두 번째 버전에서는 JSP 파일이 웹 애플리케이션 루트 아래에 있었고, 파일 경로가 곧 주소였다. MVC 구조에서 그렇게 두면 사용자가 주소창에 뷰의 경로를 직접 입력해 컨트롤러를 건너뛸 수 있다. 그러면 모델이 채워지지 않은 채로 뷰가 실행된다. 뷰는 반드시 컨트롤러를 거쳐서만 실행되어야 한다.

    Servlet 명세에는 이 요구에 맞는 장소가 정해져 있다. 명세 10.5절은 WEB-INF 디렉터리 안의 파일을 컨테이너가 클라이언트에게 직접 서비스해서는 안 되며, 그런 요청에는 404(SC_NOT_FOUND)로 응답해야 한다고 정한다. 동시에 서블릿 코드는 ServletContext의 getResource·getResourceAsStream이나 RequestDispatcher 호출을 통해 그 내용에 접근할 수 있다고 적는다. 밖에서는 못 들어오고 안에서는 쓸 수 있는 자리다. 앞의 실험 프로그램에는 이것을 확인하는 요청도 넣어 두었다. WEB-INF/views/hello.html과 루트의 open.html이라는 정적 파일을 하나씩 두고, /static-forward에 매핑된 서블릿은 앞의 파일로 forward한다.

status=404

status=200 body=

    WEB-INF 안의 파일

    /WEB-INF/views/save-result에는 분명히 서블릿이 매핑되어 있는데도 직접 요청하면 404다. 같은 디렉터리의 정적 파일도 직접 요청하면 404이고, 서블릿이 forward해 주면 200으로 내용이 나온다. 톰캣 11.0.27의 소스(StandardContextValve)를 보면 요청 경로가 /WEB-INF/나 /META-INF/로 시작할 때 매핑된 서블릿을 호출하기 전에 404를 보내도록 되어 있다. forward는 이 관문을 지나지 않고 컨테이너 내부에서 대상을 찾으므로 통과한다. WEB-INF에는 뷰 말고도 컴파일된 클래스(classes), 라이브러리(lib), 배포 설정(web.xml)이 들어간다. 모두 주소만 알면 내려받을 수 있어서는 안 되는 것들이다.

    폼의 action에 쓴 상대 경로

    new-form.jsp의 폼은 action="save"라고만 적었다. 슬래시로 시작하지 않는 상대 경로다. 상대 경로를 실제 주소로 바꾸는 것은 서버가 아니라 브라우저이고, 기준은 브라우저가 알고 있는 현재 문서의 주소다. 여기서 forward의 성질이 다시 나온다. 이 폼 화면은 /WEB-INF/views/new-form.jsp가 만들었지만 브라우저는 그 사실을 모른다. 브라우저가 아는 주소는 자신이 요청한 /books/new다. 그래서 마지막 경로 조각 new가 save로 바뀌어 /books/save로 전송된다. RFC 3986의 참조 해석 규칙을 구현한 java.net.URI.resolve로 계산해 보면 이렇다.

    현재 문서의 주소action 값전송되는 경로

    /books/new/save/save
    /books/new/save/books/new/save

    세 번째 줄처럼 주소 끝에 슬래시 하나가 붙는 것만으로 결과가 달라진다. 상대 경로는 같은 뷰를 여러 주소 체계에서 재사용할 수 있게 해 주지만, 뷰 파일만 봐서는 어디로 전송될지 알 수 없다는 뜻이기도 하다. 기준이 되는 것은 JSP 파일의 위치가 아니라 그 화면을 내보낸 컨트롤러의 주소다.

    뷰가 모델을 읽는 법: EL과 JSTL

    뷰에서 쓴 ${book.title}은 EL(Expression Language)의 식이다. 스크립틀릿으로 쓰면 ((Book) request.getAttribute("book")).getTitle()이 될 것을 짧게 적은 것인데, 평가는 두 단계로 일어난다.

    첫 단계는 이름 book이 무엇을 가리키는지 찾는 일이다. JSP는 객체를 넣어 둘 수 있는 범위(scope)를 네 가지 정의한다. 한 페이지 안에서만 보이는 page, 요청 하나 동안 보이는 request, 같은 세션의 요청들에서 보이는 session, 애플리케이션 전체에서 보이는 application이다. Pages API 문서에 따르면 EL은 이름 하나가 주어지면 page, request, session, application 순서로 그 이름의 속성을 찾는다. 컨트롤러가 request.setAttribute("book", book)으로 넣었으므로 request 범위에서 발견된다. 어디에도 없으면 기본 설정에서는 null로 평가되고, null은 출력될 때 빈 문자열이 된다. 컨트롤러가 모델에 담는 것을 잊어도 오류 없이 그 자리만 비어 나오므로 원인을 찾기 어려울 때가 있다(Pages 3.1 명세에는 error-on-el-not-found 설정으로 이 경우 예외가 나게 하는 방법이 있다).

    둘째 단계는 .title이다. EL은 필드를 직접 읽지 않는다. 자바빈 규약에 따라 getTitle()이라는 getter 메서드를 찾아 리플렉션으로 호출한다. EL 구현만 따로 떼어 확인해 볼 수 있다. 아래 예제는 톰캣의 EL 구현(11.0.27, EL 6.0)을 직접 호출한다. ELProcessor.defineBean은 JSP의 범위 대신 이름과 객체를 직접 등록하는 방법이다.

    import jakarta.el.ELProcessor;

public class ElDemo {
    public static class Book {
        private final String title;
        private final int pages;

        public Book(String title, int pages) { this.title = title; this.pages = pages; }

        public String getTitle() {
            System.out.println("  getTitle() 호출됨");
            return title;
        }
        // pages에는 getter가 없다
    }

    public static void main(String[] args) {
        ELProcessor el = new ELProcessor();
        el.defineBean("book", new Book("JVM", 320));

        System.out.println("book.title = " + el.eval("book.title"));
        try {
            el.eval("book.pages");
        } catch (RuntimeException e) {
            System.out.println(e.getClass().getName() + ": " + e.getMessage());
        }
    }
}
      getTitle() 호출됨
book.title = JVM
jakarta.el.PropertyNotFoundException: Property [pages] not found on type [ElDemo$Book]

    book.title을 평가하는 동안 getTitle()이 호출됐다. pages는 필드가 있는데도 getter가 없으니 "그런 프로퍼티가 없다"는 예외가 난다. EL에서 프로퍼티란 필드가 아니라 getter다. 뷰에서 값이 안 나올 때 클래스에 getter가 있는지부터 확인해야 하는 이유다.

    반복과 이스케이프

    목록 뷰에서 스크립틀릿의 for 문 자리를 차지한 는 JSTL(Jakarta Standard Tag Library)의 태그다. items에 준 컬렉션을 돌면서 원소를 하나씩 var에 적은 이름으로 내놓고, 태그 몸통을 원소마다 한 번씩 출력한다. JSTL은 Pages와는 별개의 명세여서 쓰려면 구현 라이브러리가 애플리케이션의 클래스패스에 있어야 하고, 페이지 첫머리의 taglib 지시자로 어떤 태그 라이브러리를 어떤 접두사로 쓸지 선언한다. JSTL 3.0에서 core 라이브러리의 URI는 jakarta.tags.core다.

    제목을 출력하는 자리에만 을 쓴 것은 앞에서 본 구멍 때문이다. 템플릿 텍스트에 ${book.title}을 그대로 쓰면 Jasper는 식을 평가한 결과를 그대로 출력하는 코드를 만든다. 제목에 script 태그가 들어 있으면 서블릿 버전과 똑같이 브라우저에서 실행된다. 은 기본 동작으로 <, >, &, 작은따옴표, 큰따옴표를 문자 참조로 바꿔 출력한다(escapeXml 속성의 기본값이 true). 번호와 쪽수는 서버가 만든 숫자라 그대로 출력했지만, 사용자가 입력한 문자열이 나가는 자리는 반드시 이스케이프를 거쳐야 한다. 템플릿 엔진을 쓴다고 이스케이프가 저절로 되는 것은 아니며, 엔진마다 기본 동작이 다르다.

    MVC 패턴 — 한계: 입구가 여러 개다

    역할을 나눈 덕분에 뷰는 깔끔해졌다. 이제 컨트롤러 세 개를 나란히 놓고 보자. 서로 다른 일을 하는 줄보다 똑같은 줄이 더 많다.

    • forward 호출이 반복된다. getRequestDispatcher(viewPath)와 forward(request, response) 두 줄이 모든 컨트롤러의 끝에 있다. 메서드로 뽑아도 그 메서드를 부르는 줄은 여전히 컨트롤러마다 있어야 하고, 빠뜨리면 빈 응답이 나간다.
    • 뷰 경로가 반복된다. 세 경로 모두 /WEB-INF/views/로 시작해 .jsp로 끝난다. 뷰 디렉터리를 옮기거나 JSP를 다른 템플릿 엔진으로 바꾸면 모든 컨트롤러를 고쳐야 한다. 컨트롤러는 save-result 같은 이름만 말하고 실제 위치는 다른 누군가가 알아내는 편이 낫다.
    • 쓰지 않는 것을 받는다. 세 컨트롤러 어디에서도 response를 직접 쓰지 않는다. forward에 넘겨주기 위해 받을 뿐이다. request도 파라미터를 꺼내고 모델을 담는 통로로만 쓴다. 그런데도 시그니처가 HttpServletRequest와 HttpServletResponse에 묶여 있어서, 컨트롤러를 테스트하려면 이 두 인터페이스의 가짜 구현을 준비해야 한다.
    • 공통 처리를 둘 곳이 없다. 모든 요청에 로그인 여부를 확인하거나 요청을 기록하고 싶다고 하자. 공통 메서드를 만들어도 컨트롤러마다 첫 줄에서 호출해야 한다. 컨트롤러가 백 개면 백 군데이고, 한 군데라도 빠뜨리면 그곳이 구멍이다.

    네 가지는 같은 원인에서 나온다. 요청이 들어오는 입구가 컨트롤러 수만큼 있다. 컨테이너가 주소마다 서로 다른 서블릿을 곧바로 호출하므로, 모든 요청이 공통으로 지나는 우리 코드가 한 줄도 없다. 서블릿 필터를 쓰면 서블릿 앞에 공통 처리를 둘 수는 있다. 하지만 필터는 서블릿 호출의 앞뒤에 끼어드는 장치여서 컨트롤러가 무엇을 받고 무엇을 돌려주는지, 뷰를 누가 호출하는지 같은 호출 방식 자체를 바꾸지는 못한다.

    지금의 구조: 입구가 컨트롤러마다 있다

  /books/new  ──▶ BookFormController ──┐
  /books/save ──▶ BookSaveController ──┼─ 각자 뷰 경로를 만들고 각자 forward
  /books      ──▶ BookListController ──┘

바라는 구조: 입구가 하나다

  /books/new  ─┐                     ┌─▶ 폼 컨트롤러  ─┐
  /books/save ─┼─▶ 하나의 서블릿 ────┼─▶ 저장 컨트롤러 ─┼─▶ 하나의 서블릿이 뷰를 찾아 호출
  /books      ─┘   (공통 처리)       └─▶ 목록 컨트롤러 ─┘

    해법은 입구를 하나로 만드는 것이다. 서블릿 하나가 모든 요청을 받아 공통 처리를 한 뒤 주소에 맞는 컨트롤러를 호출하고, 컨트롤러가 돌려준 결과를 가지고 뷰를 찾아 실행한다. 이 구조를 프런트 컨트롤러(front controller) 패턴이라고 한다. 그렇게 되면 컨트롤러는 서블릿일 필요가 없어지고, forward도 뷰 경로 조립도 한 곳으로 모인다. 04회차에서 이 프런트 컨트롤러를 직접 만들며 단계적으로 발전시키고, 05회차에서 스프링 MVC의 DispatcherServlet이 바로 그 프런트 컨트롤러임을 확인한다.

    공통 처리와 뷰 호출이 컨트롤러마다 흩어져 있는 현재 구조와, 입구 하나로 모인 구조를 위아래로 비교한다. 위아래 두 단으로 나뉜 구조 다이어그램. 위쪽 단 제목 "입구가 여러 개". 왼쪽에 요청 화살표 세 개가 각각 상자 "폼 컨트롤러", "저장 컨트롤러", "목록 컨트롤러"로 곧바로 들어간다. 각 컨트롤러 상자 안에 작은 회색 조각 두 개가 똑같이 그려져 있고 조각의 라벨은 "뷰 경로", "forward". 세 상자 옆에 "같은 코드가 세 번". 아래쪽 단 제목 "입구가 하나". 왼쪽 요청 화살표 세 개가 모두 큰 상자 "프런트 컨트롤러"로 들어가고, 그 상자에서 화살표가 갈라져 "폼 컨트롤러", "저장 컨트롤러", "목록 컨트롤러" 세 상자로 간다. 프런트 컨트롤러 상자 안에 조각 세 개 "공통 처리", "뷰 경로", "forward"가 한 번씩만 그려져 있다. 차분한 기술 문서 스타일, 흰 배경, 중복 조각은 주황색으로 강조. 반복되던 코드는 모든 요청이 지나는 한 곳이 생기면 그곳으로 모을 수 있다.

    흔한 오해와 이 지식이 다시 쓰이는 곳

    이 회차의 내용은 이름이 비슷하거나 눈에 보이지 않는 동작이 많아 잘못 기억되기 쉽다. 자주 보이는 오해를 실험 결과와 짝지어 정리한다.

    흔한 오해실제
    JSP는 요청이 올 때마다 해석되는 스크립트다한 번 자바 소스로 번역되고 컴파일된 서블릿이다. 요청마다 일어나는 일은 _jspService 호출이다
    JSP에서 선언한 변수는 요청마다 새로 만들어진다스크립틀릿의 변수는 지역 변수라 그렇지만, 선언(<%! %>)의 변수는 필드라서 모든 요청이 공유한다
    forward하면 브라우저가 뷰의 주소로 이동한다브라우저는 forward를 알 수 없다. 요청은 한 번이고 주소는 그대로다
    forward를 호출하면 그 뒤의 코드는 실행되지 않는다실행된다. 응답이 이미 닫혀 출력이 반영되지 않을 뿐이다. 뒤에 상태를 바꾸는 코드가 있으면 그대로 수행된다
    요청 속성에 넣은 값은 클라이언트로 전송되거나 다음 요청에도 남는다서버 메모리의 요청 객체 안에만 있고, 그 요청이 끝나면 사라진다
    WEB-INF 아래의 파일은 아무도 읽을 수 없다클라이언트의 직접 요청만 막힌다. 서버 코드는 forward나 ServletContext로 접근한다
    MVC의 모델은 데이터베이스나 도메인 객체를 뜻한다여기서 모델은 컨트롤러가 뷰에 건네는 데이터의 묶음이다. 그 안에 도메인 객체가 담길 수는 있다

    손으로 해 본 setAttribute와 forward는 스프링 MVC 안에 그대로 들어 있다. 스프링에서 JSP를 뷰로 쓸 때 동작하는 InternalResourceView의 API 문서는 이 클래스가 모델 객체를 요청 속성으로 노출하고 RequestDispatcher를 사용해 지정된 자원 URL로 요청을 forward한다고 설명한다. 스프링의 컨트롤러가 모델에 값을 담고 뷰 이름을 돌려주면, 프레임워크가 이 회차의 컨트롤러 마지막 세 줄을 대신 실행하는 것이다. 뷰 기술이 JSP가 아니어도 컨트롤러가 모델을 채우고 뷰가 그것만 읽는다는 구조는 같다.

    이 장의 핵심

    서블릿은 자바 안에 HTML을 넣었고, JSP는 HTML 안에 자바를 넣었지만 번역하면 같은 서블릿이다. 둘 다 처리와 표현이 한 덩어리라는 문제가 남아, 요청을 처리하는 컨트롤러와 화면을 그리는 뷰를 나누고 요청 속성을 모델로 삼아 둘을 이었다. 둘을 잇는 forward는 네트워크를 다시 타지 않는, 같은 스레드 위의 메서드 호출이다. 그렇게 나누고 나면 컨트롤러마다 반복되는 코드가 눈에 들어오고, 그것이 모든 요청을 한곳에서 받는 프런트 컨트롤러를 요구한다.
    동적 HTML
    요청마다 달라지는 값을 끼워 넣어 서버가 조립한 문자열이다. HTTP 메시지로는 정적 파일과 구별되지 않는다.
    공유 상태와 동시성
    서블릿과 저장소는 객체가 하나이고 요청마다 다른 스레드가 호출한다. ++ 같은 연산은 읽기·더하기·쓰기로 나뉘므로 보호 없는 필드는 깨진다.
    JSP의 번역
    JSP는 한 번 자바 서블릿 소스로 번역·컴파일된다. 스크립틀릿과 템플릿 텍스트는 _jspService의 몸통이 되고, 선언은 클래스의 멤버가 된다.
    MVC 패턴
    요청을 처리하는 컨트롤러, 화면을 그리는 뷰, 둘 사이에 데이터를 전달하는 모델로 역할을 나눈다. 기준은 바뀌는 이유가 다른 코드를 분리하는 것이다.
    요청 속성
    요청 객체에 이름과 객체 참조를 넣어 두는 보관함이다. 서버 메모리에만 있고 요청 하나 동안만 유지되어 모델을 담는 데 쓰인다.
    forward
    같은 요청, 같은 스레드에서 컨테이너가 다른 자원을 호출하는 것이다. 커밋되지 않은 버퍼는 비워지고, 돌아왔을 때 응답은 닫혀 있다. 브라우저는 알지 못한다.
    redirect
    서버가 3xx 응답과 Location 헤더를 돌려보내 브라우저가 새 요청을 보내게 하는 것이다. 요청이 두 번이고 요청 속성은 이어지지 않는다.
    WEB-INF
    컨테이너가 클라이언트에게 직접 서비스하지 않는 디렉터리다. 뷰를 여기에 두면 컨트롤러의 forward를 거쳐야만 실행된다.
    MVC 패턴의 한계
    forward 호출, 뷰 경로, 쓰지 않는 매개변수, 공통 처리가 컨트롤러마다 반복된다. 입구가 여러 개라서 생기는 문제이며 프런트 컨트롤러가 해법이다.

    실무에서 새 프로젝트에 JSP와 스크립틀릿을 고를 일은 드물다. Spring Boot 문서부터 임베디드 컨테이너에서의 제약을 들어 JSP를 피하라고 권한다. 그래도 이 회차의 지식은 두 군데에서 쓰인다. 하나는 오래된 시스템을 유지보수할 때다. JSP에서 난 예외의 스택 트레이스에 _jspService와 _jsp로 끝나는 클래스 이름이 보이면 그것이 번역된 서블릿이라는 것을 알아야 하고, 톰캣이 work 디렉터리에 남겨 두는 번역된 자바 소스(Jasper의 keepgenerated 기본값은 true다)를 열어 보는 것이 가장 빠른 디버깅 길이 된다. 다른 하나는 어떤 뷰 기술을 쓰든 통하는 판단 기준이다. 사용자 입력이 출력될 때 이스케이프가 기본인지, 뷰가 모델 밖의 것에 손댈 수 있는지를 먼저 확인한다.

    forward와 redirect의 선택은 실제 장애와 직결된다. 주문이나 결제처럼 상태를 바꾸는 POST를 처리하고 결과 화면으로 forward하면 사용자의 새로고침 한 번이 중복 처리로 이어진다. 상태 변경 뒤에는 redirect하고, 조회 결과를 그릴 때는 forward한다는 구분이 기본이다. 반대로 redirect는 요청이 한 번 더 오므로 그만큼 지연과 부하가 늘고, 요청 속성으로 전달하던 데이터가 사라진다는 대가가 있다. 전달할 것이 있으면 식별자를 주소에 실어 다시 조회하는 식으로 설계가 바뀐다.

    공유 상태의 문제는 예제의 메모리 저장소에서 끝나지 않는다. 서블릿, 스프링의 싱글톤 빈, JSP의 선언 필드는 모두 "객체 하나를 모든 요청이 쓴다"는 같은 조건에 놓인다. 여기에 요청마다 다른 값(현재 사용자, 입력값, 중간 계산 결과)을 필드로 두면 부하가 낮을 때는 멀쩡하다가 동시 요청이 겹치는 순간 다른 사용자의 데이터가 섞여 보이는 사고가 난다. 이런 값은 지역 변수나 요청 속성처럼 요청 하나에 묶인 자리에 두어야 한다. 코드 리뷰에서 싱글톤 객체의 변경 가능한 필드는 그것만으로 질문할 이유가 된다.
  • 어떤 JSP에 <%! int count = 0; %> 선언이 있고, 그 아래에 스크립틀릿 <% int local = 0; count++; local++; %>와 출력 <%= count %> / <%= local %>가 있다. 서버를 띄운 뒤 이 페이지를 순서대로 세 번 요청하면 각각 무엇이 출력되는가. 동시에 많은 요청이 몰리면 어느 값에 어떤 문제가 생길 수 있는가. 번역된 클래스에서 두 변수가 놓이는 위치로 설명하라.
  • 저장 컨트롤러의 dispatcher.forward(request, response); 바로 다음 줄에 repository.save(new Book("부록", 1));과 response.getWriter().write("끝");을 추가했다. 저장 요청을 한 번 보내면 저장소에는 책이 몇 권 들어가고, 응답 본문에 "끝"이 포함되는가.
  • 브라우저가 /books/new에서 받은 폼의 action이 각각 save, /save, ./save, books/save일 때 폼은 어느 경로로 전송되는가. 이 폼을 그린 JSP 파일이 /WEB-INF/views/new-form.jsp에 있다는 사실은 결과에 영향을 주는가.
  • 컨트롤러가 request.setAttribute("book", a)를 호출했고, 같은 사용자의 세션에는 이전에 "book"이라는 이름으로 다른 객체 b가 들어 있다. 뷰의 ${book.title}은 어느 객체의 제목을 출력하는가. 모델에 넣은 적이 없는 이름을 쓴 ${author}는 기본 설정에서 무엇을 출력하는가.
  • 세 번째 버전에서 책을 저장하고 결과 화면이 뜬 상태로 브라우저의 새로고침을 두 번 눌렀다. 목록에는 같은 책이 몇 번 보이는가. forward의 어떤 성질 때문인가.
    •

    1. 차례로 1 / 1, 2 / 1, 3 / 1이 출력된다(그 사이에 JSP가 다시 번역되어 인스턴스가 바뀌지 않았다고 할 때). 선언으로 적은 count는 번역된 클래스의 필드가 된다. JSP의 서블릿 인스턴스는 하나이므로 이 필드는 요청이 끝나도 남아 다음 요청이 이어서 증가시킨다. 스크립틀릿의 local은 _jspService의 지역 변수라 호출마다 0에서 새로 시작한다. 동시 요청이 몰리면 문제가 생기는 쪽은 count다. count++는 읽기·더하기·쓰기로 나뉘므로 두 스레드가 같은 값을 읽으면 증가가 한 번 사라진다. local은 스레드마다 자기 스택 프레임에 따로 있어 안전하다.

    2. 책은 두 권 저장되고 "끝"은 응답에 없다. forward는 메서드 호출이므로 돌아온 뒤 다음 줄이 그대로 실행된다. repository.save는 응답과 무관한 자바 코드라 정상 수행되어 "부록"이 저장된다. 반면 forward가 돌아왔을 때 응답은 이미 커밋되고 닫혀 있으므로 그 뒤에 쓴 글자는 클라이언트에 전달되지 않는다. 실험의 (B) 줄과 같은 상황이다. forward 뒤에는 코드를 두지 않거나, 두더라도 바로 return해야 한다는 규칙이 여기서 나온다.

    3. 차례로 /books/save, /save, /books/save, /books/books/save다. 상대 경로는 현재 문서 주소 /books/new에서 마지막 조각 new를 떼어 낸 /books/를 기준으로 해석된다. 슬래시로 시작하면 호스트 바로 아래부터의 경로가 된다. JSP 파일의 위치는 영향을 주지 않는다. 브라우저는 forward를 알 수 없고 자신이 요청한 주소만 알기 때문이다.

    4. a의 제목이 출력된다. EL은 이름을 page, request, session, application 순서로 찾고 먼저 발견된 것을 쓴다. request 범위에 a가 있으므로 세션의 b까지 가지 않는다. 같은 이름을 여러 범위에 두면 이런 가림이 생기므로 이름을 겹치지 않게 하거나 ${sessionScope.book}처럼 범위를 명시한다. ${author}는 어느 범위에도 없어 null로 평가되고 빈 문자열이 출력된다. 예외가 나지 않으므로 오타를 눈으로 찾아야 한다.

    5. 세 번 보인다(처음 저장 한 번에, 브라우저의 재전송 확인에 동의한 새로고침 두 번). forward는 브라우저가 모르는 서버 내부 동작이라, 결과 화면은 브라우저에게 POST /books/save 요청의 응답이다. 새로고침은 마지막 요청을 다시 보내는 것이므로 같은 POST가 두 번 더 전송되고 컨트롤러는 그때마다 저장한다. 저장 뒤에 redirect로 조회 주소에 보내면 브라우저의 마지막 요청이 GET이 되어 새로고침해도 다시 저장되지 않는다.

     JSP의 스크립틀릿 안에서 선언한 변수가 동시에 들어온 다른 요청과 섞이지 않는 이유로 가장 정확한 것은? JSP 컨테이너가 요청마다 JSP의 서블릿 인스턴스를 새로 만들기 때문이다 스크립틀릿은 번역되면 _jspService 메서드의 몸통에 들어가므로 그 변수는 호출마다 스택에 따로 만들어지는 지역 변수이기 때문이다 JSP 컨테이너가 스크립틀릿 전체를 동기화 블록으로 감싸 한 번에 한 스레드만 실행하게 하기 때문이다 스크립틀릿의 변수는 요청 속성에 자동으로 저장되기 때문이다 스크립틀릿의 코드는 번역된 서블릿의 _jspService 안에 그대로 복사된다. 메서드의 지역 변수는 호출하는 스레드의 스택 프레임에 만들어지므로 요청끼리 공유되지 않는다. 인스턴스는 하나만 쓰이고(그래서 선언으로 만든 필드는 공유된다), 기본 동작에서 동기화로 직렬 실행하지도 않으며, 지역 변수가 요청 속성에 자동 저장되는 일도 없다. 컨트롤러 서블릿이 RequestDispatcher.forward로 뷰에 넘기는 동작에 대한 설명으로 옳은 것은? 서버가 302 응답을 보내고 브라우저가 뷰의 주소로 다시 요청한다 컨테이너가 스레드 풀에서 다른 스레드를 꺼내 뷰를 실행하고 컨트롤러 스레드는 즉시 반납된다 같은 스레드에서 컨테이너가 대상 자원을 호출하며, 클라이언트 입장에서는 요청 한 번에 응답 한 번이다 forward가 호출되면 그 뒤에 있는 컨트롤러의 코드는 실행되지 않는다 forward는 서버 내부의 메서드 호출이다. 실험에서 컨트롤러와 뷰가 같은 스레드 이름을 찍었고 클라이언트는 응답을 하나만 받았다. 302와 재요청은 redirect의 동작이다. forward 뒤의 코드는 실행되며, 다만 응답이 이미 닫혀 출력이 반영되지 않는다. 뷰 JSP를 /WEB-INF/views/ 아래에 두는 이유로 가장 적절한 것은? 컨테이너가 이 디렉터리의 파일을 클라이언트에게 직접 서비스하지 않으므로, 뷰가 컨트롤러의 forward를 거쳐서만 실행되게 할 수 있다 이 디렉터리의 JSP는 번역 단계 없이 바로 실행되어 더 빠르다 이 디렉터리에 있어야 EL 식이 요청 속성을 읽을 수 있다 이 디렉터리의 파일은 서버 코드에서도 접근할 수 없어 가장 안전하다 Servlet 명세는 WEB-INF 안의 파일을 클라이언트에게 직접 서비스하지 못하게 하고 그런 요청에 404를 주도록 정한다. 서버 코드는 RequestDispatcher나 ServletContext로 접근할 수 있으므로 컨트롤러를 거친 forward는 동작한다. 번역 방식이나 EL 동작은 파일 위치와 무관하다. 서블릿 버전의 목록 화면에서 제목에 넣은 script 태그가 다른 사용자의 브라우저에서 실행된 근본 원인은? 응답의 문자 인코딩을 UTF-8로 지정했기 때문이다 저장소가 ConcurrentHashMap이라 입력값을 검사하지 못했기 때문이다 POST 요청의 본문은 컨테이너가 해석하지 않기 때문이다 사용자가 입력한 문자열을 HTML에서 특별한 뜻을 가진 문자를 바꾸지 않은 채 HTML 문자열 사이에 그대로 이어 붙였기 때문이다 브라우저는 응답 본문의 글자가 개발자가 쓴 태그인지 사용자 데이터인지 구별하지 못한다. 데이터를 HTML에 넣을 때 꺾쇠 같은 문자를 문자 참조로 바꾸는 이스케이프를 하지 않으면 데이터가 태그로 해석된다. 인코딩, 저장소 구현, 본문 해석은 이 문제와 관계가 없다. 서블릿과 JSP로 만든 MVC 구조에서 forward 호출, 뷰 경로 조립, 공통 처리가 컨트롤러마다 반복되는 근본 원인은? JSP가 서블릿으로 번역되기 때문이다 요청 속성의 수명이 요청 하나로 제한되기 때문이다 컨테이너가 주소마다 서로 다른 서블릿을 곧바로 호출해서, 모든 요청이 공통으로 지나는 지점이 애플리케이션 코드에 없기 때문이다 뷰를 WEB-INF 아래에 두었기 때문이다 입구가 컨트롤러 수만큼 있으면 모든 요청에 대해 한 번만 써 두면 되는 코드를 둘 자리가 없어 각 컨트롤러가 되풀이하게 된다. 모든 요청을 먼저 받는 프런트 컨트롤러를 두면 그 지점이 생긴다. 번역 방식, 속성의 수명, 뷰의 위치는 반복의 원인이 아니다.
    템플릿 엔진(template engine)
    고정된 문서 틀과 요청마다 달라지는 데이터를 합쳐 결과 문서를 만들어 내는 도구. JSP가 그 한 예다.
    JSP(Jakarta Server Pages)
    HTML 문서 안에 동적 요소를 적는 Jakarta EE의 뷰 기술. 컨테이너가 서블릿 클래스로 번역해 실행한다.
    스크립틀릿(scriptlet)
    JSP에서 <% %> 사이에 적는 자바 문장. 번역되면 _jspService 메서드의 몸통에 그대로 들어간다.
    번역 단계(translation phase)
    JSP 컨테이너가 JSP 페이지로부터 구현 클래스를 만들어 내는 단계. 페이지당 한 번 수행된다.
    Jasper
    톰캣의 JSP 엔진. JSP를 자바 소스로 번역하고 컴파일해 서블릿으로 실행한다.
    모델(model)
    MVC에서 컨트롤러가 뷰에 전달하는 데이터의 묶음. 서블릿과 JSP 조합에서는 요청 속성이 그 구실을 한다.
    RequestDispatcher
    서버 안의 자원을 감싼 객체로, 요청을 그 자원으로 넘기거나(forward) 그 자원의 출력을 포함시키는(include) 데 쓴다.
    forward
    현재 요청의 처리를 같은 서버 안의 다른 자원에 넘기는 것. HTTP 요청은 한 번이며 클라이언트는 알 수 없다.
    EL(Expression Language)
    JSP에서 ${이름.프로퍼티} 꼴로 범위 속성과 자바빈 프로퍼티를 읽는 식 언어.
    프런트 컨트롤러(front controller)
    모든 요청을 하나의 입구에서 받아 공통 처리를 한 뒤 알맞은 컨트롤러에 넘기는 구조.
