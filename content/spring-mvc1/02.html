    이 회차의 질문: 두 객체 안에서 무슨 일이 일어나는가

    01회에서 확인한 구도는 이렇다. 서블릿 컨테이너가 TCP 연결을 받고, HTTP 메시지를 해석해 요청 객체와 응답 객체를 만들고, 작업 스레드 하나가 그 둘을 들고 서블릿의 service를 호출한다. 서블릿은 소켓을 보지 않는다. 이 회차는 서블릿이 보는 세계의 전부인 두 객체, HttpServletRequest와 HttpServletResponse를 연다.

    메서드 목록을 외우는 것이 목적이 아니다. 이름은 문서에서 찾으면 된다. 붙잡아야 할 것은 메서드 뒤에서 일어나는 일이고, 구체적으로는 다음 질문에 답할 수 있어야 한다.

    • 요청 객체가 돌려주는 값은 메시지의 어느 바이트에서 왔고, 언제 문자열로 바뀌는가.
    • 쿼리 스트링과 HTML 폼은 왜 같은 메서드로 읽히고, JSON은 왜 그렇게 읽히지 않는가.
    • 본문은 왜 한 번만 읽을 수 있는가. 서블릿이 호출된 시점에 본문은 서버에 다 도착해 있는가.
    • 응답 객체에 쓴 글자는 언제 소켓으로 나가는가. 본문을 쓰다가 상태 코드를 바꾸면 어떻게 되는가.
    • 한글은 어느 지점에서, 어떤 규칙 때문에 깨지는가.

    프로젝트의 뼈대: 스프링 부트가 톰캣을 띄우고 서블릿을 등록한다

    서블릿을 실행하려면 서블릿 컨테이너가 있어야 한다. 오래된 방식은 톰캣을 서버에 따로 설치하고, 애플리케이션을 war 파일로 묶어 톰캣의 배포 디렉터리에 넣는 것이다. 스프링 부트 프로젝트는 방향이 반대다. 톰캣이 애플리케이션 안에 라이브러리로 들어온다.

    dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
}

    이 한 줄이 끌어오는 것은 Maven Central에 올라온 POM에 적혀 있다. Spring Boot 3.5.7의 spring-boot-starter-web은 spring-boot-starter-tomcat, spring-boot-starter-json, spring-web, spring-webmvc에 의존하고, spring-boot-starter-tomcat은 다시 tomcat-embed-core 10.1.48을 포함한다. 실험에 쓴 tomcat-embed-core jar를 열어 보면 톰캣 본체와 함께 jakarta/servlet/http/HttpServlet.class 같은 서블릿 API 클래스가 들어 있다. 그래서 서블릿 API 의존성을 따로 적지 않아도 HttpServlet을 상속할 수 있고, main 메서드로 시작하는 평범한 자바 프로세스가 곧 WAS가 된다.

    톰캣을 시작하는 주체는 스프링 컨테이너다. 스프링 부트 문서의 설명으로는 임베디드 구성에서 쓰이는 ServletWebServerApplicationContext가 ServletWebServerFactory 빈 하나를 찾아 자신을 구동하고, 보통은 자동 구성된 TomcatServletWebServerFactory가 그 빈이다. 01회에서 손으로 했던 new Tomcat(), 포트 지정, start()를 스프링 컨테이너의 초기화 과정이 대신 한다.

    이제 서블릿을 등록할 차례다. 서블릿 API의 @WebServlet은 본래 컨테이너가 war를 배포하면서 클래스를 훑어 찾아내는 애노테이션이다. 임베디드 구성에는 그 배포 단계가 없다. 스프링 부트는 대신 @ServletComponentScan을 제공한다. 문서의 표현으로는 임베디드 컨테이너를 쓸 때 @WebServlet, @WebFilter, @WebListener가 붙은 클래스의 자동 등록을 켜는 애노테이션이고, 독립 실행형 컨테이너에서는 컨테이너 자체의 탐색 기능이 쓰이므로 아무 효과가 없다. 패키지를 지정하지 않으면 이 애노테이션이 붙은 클래스의 패키지부터 찾는다.

    package lab;

import org.springframework.boot.SpringApplication;
import org.springframework.boot.autoconfigure.SpringBootApplication;
import org.springframework.boot.web.servlet.ServletComponentScan;   // Boot 3.x 의 패키지

@ServletComponentScan        // lab 패키지 아래의 @WebServlet, @WebFilter, @WebListener 를 찾아 등록
@SpringBootApplication
public class LabApplication {
    public static void main(String[] args) {
        SpringApplication.run(LabApplication.class, args);
    }
}
    package lab;

import jakarta.servlet.annotation.WebServlet;
import jakarta.servlet.http.HttpServlet;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import java.io.IOException;

@WebServlet(name = "pingServlet", urlPatterns = "/ping")      // 서블릿 이름과 URL 패턴
public class PingServlet extends HttpServlet {
    public PingServlet() {
        System.out.println("[" + Thread.currentThread().getName() + "] PingServlet 생성자");
    }

    @Override
    public void init() {
        System.out.println("[" + Thread.currentThread().getName() + "] PingServlet init");
    }

    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws IOException {
        System.out.println("[" + Thread.currentThread().getName() + "] PingServlet service");
        response.getWriter().println("pong");
    }
}

    첫 서블릿: service에서 doGet까지, 그리고 URL 매핑

    HttpServlet이 메서드를 가려 준다

    HttpServlet에는 service가 둘 있다. 컨테이너가 부르는 것은 Servlet 인터페이스의 public void service(ServletRequest, ServletResponse)다. 이 메서드는 두 인자를 HTTP용 타입으로 바꿔 protected void service(HttpServletRequest, HttpServletResponse)로 넘기고, 그 메서드가 요청 메서드를 보고 doGet, doPost, doPut, doDelete 같은 메서드로 다시 넘긴다. 공통 흐름을 부모 클래스가 쥐고 달라지는 부분만 자식이 채우는 구조다. Javadoc은 하위 클래스가 doGet, doPost 같은 메서드 중 적어도 하나를 재정의해야 한다고 적고, service를 재정의할 이유는 거의 없다고 덧붙인다.

    doGet만 재정의해 GET only 한 줄을 응답하는 서블릿을 /only-get에 올리고 다른 메서드로 요청해 보았다.

    $ curl -s -o /dev/null -w "%{http_code}\n" -X POST http://localhost:18082/only-get
405

$ curl -s -i -X OPTIONS http://localhost:18082/only-get
HTTP/1.1 200
Allow: GET, HEAD, OPTIONS
Content-Length: 0

$ curl -s -I http://localhost:18082/only-get        # HEAD 요청
HTTP/1.1 200
Content-Length: 9

    재정의하지 않은 doPost의 기본 구현은 405 Method Not Allowed를 보낸다. 톰캣이 붙인 오류 페이지에는 HTTP method POST is not supported by this URL이라는 문구가 있었다. OPTIONS에는 HttpServlet이 어떤 doXxx가 재정의되었는지 조사해 Allow 헤더를 만들어 준다. HEAD는 doGet을 실행하되 본문 없이 헤더만 보낸다. Content-Length: 9는 GET only와 줄바꿈 한 글자를 합친 길이다. Servlet 6.0 Javadoc의 doOptions 설명에는 Allow 예시에 TRACE도 들어 있지만, 톰캣의 HttpServlet은 커넥터의 allowTrace 속성이 켜져 있을 때만 TRACE를 덧붙이고, Tomcat 10.1 문서에 적힌 이 속성의 기본값은 false다. Tomcat 10.1.55에서 같은 요청을 보냈을 때도 목록은 GET, HEAD, OPTIONS였다.

    이 회차의 예제 가운데 메서드를 가리지 않고 받고 싶은 서블릿은 protected service를 직접 재정의했다. 그러면 분기 로직을 통째로 건너뛰어 GET이든 POST든 같은 코드가 실행된다. 실험에는 편하지만 405 응답이나 OPTIONS 처리까지 사라지므로, Javadoc이 권하는 방식은 아니라는 점은 알아 둔다.

CoyoteAdapter가 그 결과를 서블릿 쪽 세계로 넘긴다. 이어서 엔진(Engine), 호스트(Host), 컨텍스트(Context), 래퍼(Wrapper)라는 이름이 붙은 단계가 차례로 나온다. 톰캣 문서의 정의로 엔진은 한 서비스의 요청 처리 파이프라인이고, 호스트는 네트워크 이름 하나와 톰캣의 연결이며, 컨텍스트는 웹 애플리케이션 하나다. 래퍼는 Javadoc에 서블릿 정의 하나를 나타내는 컨테이너라고 적혀 있다. 요청은 "어느 호스트인가, 어느 애플리케이션인가, 어느 서블릿인가"를 좁혀 가며 안쪽으로 들어간다.

    래퍼 다음에 ApplicationFilterChain.doFilter가 있다. 등록된 필터들이 여기서 차례로 실행되고, 체인의 끝에서 서블릿의 service가 불린다. 그 위 두 줄이 방금 설명한 HttpServlet의 두 service이고, 맨 위가 내가 쓴 doPost다. 이 모든 프레임이 스레드 하나의 스택에 쌓여 있다는 점이 중요하다. 소켓 읽기부터 내 코드까지가 한 스레드의 연속된 메서드 호출이다.

             └ service(HttpServletRequest, HttpServletResponse)
                 └ doGet / doPost / …           여기부터 개발자가 쓴 코드
    소켓에서 읽은 바이트가 서블릿 코드에 닿기까지 톰캣 안의 어떤 층을 거치는지, 그리고 그 전체가 한 스레드의 호출이라는 점을 보여 준다. 깔끔한 기술 구조 다이어그램, 흰 배경, 왼쪽에서 오른쪽으로 흐르는 가로 구도. 맨 왼쪽에 작은 소켓 아이콘과 라벨 "HTTP 요청 바이트". 그 오른쪽에 둥근 사각형 여섯 개가 가로로 나란히 놓이고 굵은 화살표 하나가 모두를 관통해 오른쪽으로 간다. 사각형의 라벨은 왼쪽부터 "커넥터", "엔진", "호스트", "컨텍스트", "래퍼", "필터 체인". 맨 오른쪽에 강조색으로 칠한 큰 사각형, 라벨 "서블릿", 그 안에 세로로 작은 상자 세 개 "service", "service(HTTP)", "doGet / doPost". 여섯 사각형과 서블릿 전체를 하나의 얇은 점선 테두리가 감싸고 테두리 위쪽에 라벨 "작업 스레드 하나의 호출 스택". 커넥터 사각형 아래에 작은 주석 "메시지 해석", 래퍼 아래에 작은 주석 "서블릿 하나". 장식 없는 단순한 선과 차분한 색. 요청은 톰캣의 여러 층을 지나지만 그 전체가 스레드 하나의 연속된 메서드 호출이다. 개발자의 코드는 그 스택의 맨 끝에 놓인다.

    URL 매핑 규칙

    래퍼, 곧 서블릿 하나를 고르는 규칙은 Servlet 6.0 명세 12장에 있다. 12.2절이 정한 패턴의 문법은 이렇다. /로 시작해 /*로 끝나면 경로 매핑, *.로 시작하면 확장자 매핑, / 한 글자뿐이면 애플리케이션의 기본 서블릿(default servlet), 빈 문자열은 컨텍스트 루트에만 맞는 매핑, 그 밖의 문자열은 정확히 일치할 때만 쓰이는 매핑이다. 12.1절은 적용 순서를 정한다. 정확히 일치하는 서블릿을 먼저 찾고, 없으면 경로를 / 단위로 한 단계씩 줄여 가며 가장 길게 맞는 경로 매핑을 찾고, 그래도 없으면 마지막 조각의 확장자로 찾고, 끝내 없으면 기본 서블릿에 넘긴다. 비교는 대소문자를 구분한다.

    같은 서블릿 클래스를 /exact, /api/*, *.do, / 네 패턴에 각각 등록하고, 어느 패턴으로 선택되었는지와 경로가 어떻게 나뉘었는지를 출력하게 했다. request.getHttpServletMapping()이 선택에 쓰인 패턴과 종류를 알려 준다.

    /exact           패턴=/exact  종류=EXACT     servletPath=/exact         pathInfo=null
/exact/          패턴=/       종류=DEFAULT   servletPath=/exact/        pathInfo=null
/api/books/3     패턴=/api/*  종류=PATH      servletPath=/api           pathInfo=/books/3
/api             패턴=/api/*  종류=PATH      servletPath=/api           pathInfo=null
/report.do       패턴=*.do    종류=EXTENSION servletPath=/report.do     pathInfo=null
/api/report.do   패턴=/api/*  종류=PATH      servletPath=/api           pathInfo=/report.do
/nothing/here    패턴=/       종류=DEFAULT   servletPath=/nothing/here  pathInfo=null

    세 줄이 눈여겨볼 만하다. /exact/는 끝의 슬래시 하나 때문에 /exact와 일치하지 않아 기본 서블릿으로 갔다. /api는 뒤에 아무것도 없어도 /api/*에 맞는다. /api/report.do는 확장자 .do를 가졌지만 경로 매핑이 확장자 매핑보다 먼저 적용되므로 /api/*가 가져갔다. 경로 매핑에서는 패턴의 고정된 부분이 getServletPath()로, 나머지가 getPathInfo()로 나뉜다는 것도 표에서 읽힌다.

    명세는 하나의 패턴이 두 서블릿에 매핑되면 배포가 실패해야 한다고도 정한다. 그리고 앞 절의 등록 목록에서 본 대로 스프링 부트는 DispatcherServlet을 기본 서블릿 자리인 /에 둔다. 더 구체적인 패턴에 걸리지 않은 모든 요청이 그리로 간다는 뜻이다. /ping처럼 정확히 일치하는 서블릿이 있으면 그쪽이 먼저다.

    오가는 HTTP 메시지를 눈으로 확인하는 방법

    HttpServletRequest는 인터페이스다: 바이트가 값이 되는 시점

    HttpServletRequest는 jakarta.servlet.http 패키지의 인터페이스다. 명세가 정한 것은 메서드의 계약이고, 구현 클래스는 컨테이너가 가져온다. 서블릿 안에서 request.getClass().getName()을 찍으면 톰캣에서는 org.apache.catalina.connector.RequestFacade가 나온다. 이 객체가 하는 일은 세 갈래다.

    • HTTP 요청 메시지 조회. 시작 줄, 헤더, 파라미터, 본문을 꺼낸다. 이 회차의 대부분이 여기에 해당한다.
    • 요청 범위의 저장소. setAttribute(name, value)와 getAttribute(name)로 요청 하나가 처리되는 동안만 유지되는 객체를 맡기고 꺼낸다. 컨트롤러가 만든 데이터를 뷰에 넘기는 용도로 03회에서 쓴다.
    • 세션 접근. getSession()은 현재 요청에 연결된 세션을 돌려주고 없으면 만든다. 여러 요청에 걸쳐 상태를 유지하는 장치이며 이 로드맵의 뒤쪽 권에서 다룬다.

    변환은 미뤄진다

    소켓에서 도착한 것은 바이트다. 메서드 이름, 경로, 헤더 값은 모두 그 바이트 배열의 어느 구간이다. 톰캣은 이 구간들을 MessageBytes라는 객체로 표현하는데, Javadoc은 이 클래스를 HTTP 메시지 안 바이트의 부분 배열을 나타내며 바이트와 문자 사이의 변환이 지연되고 캐시된다고 설명한다. 헤더가 스무 개 왔다고 해서 스무 개의 값을 모두 문자열로 만들어 두고 시작하지 않는다는 뜻이다. 요청마다 쓰이지도 않을 문자열 객체를 만들지 않으려는 설계다.

    파라미터도 같다. 쿼리 스트링을 &와 =로 쪼개 이름과 값의 표를 만드는 일은 서블릿이 getParameter 계열 메서드를 처음 부를 때 일어난다. 명세 3.1.1절이 폼 데이터를 파라미터로 만드는 조건의 하나로 "서블릿이 getParameter 계열 메서드를 처음 호출했을 것"을 든 것이 이 지연을 전제로 한다. 뒤에서 이 사실이 눈에 보이는 결과 차이를 만든다.

    요청 객체의 수명

    명세 3.14절은 요청 객체가 서블릿의 service 메서드(필터라면 doFilter) 범위 안에서만 유효하다고 정한다. 컨테이너가 객체 생성 비용을 줄이려고 요청 객체를 재활용하는 일이 흔하기 때문이며, 범위 밖에서 참조를 쥐고 있으면 결과를 예측할 수 없다고 경고한다. 일부러 그 금지된 일을 해 보았다. 요청 객체를 서블릿의 필드에 붙잡아 두고, 다음 요청에서 이전 객체에게 파라미터를 묻는다.

    @WebServlet(name = "leakServlet", urlPatterns = "/leak")
public class LeakServlet extends HttpServlet {
    private HttpServletRequest previous;        // 하면 안 되는 일: 요청 객체를 필드에 붙잡아 둔다

    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws IOException {
        response.setContentType("text/plain;charset=UTF-8");
        PrintWriter out = response.getWriter();
        out.println("이번 요청의 n = " + request.getParameter("n"));
        if (previous != null) {
            out.println("이전 요청 객체와 같은 객체인가 = " + (previous == request));
            try {
                out.println("이전 요청 객체의 n = " + previous.getParameter("n"));
            } catch (IllegalStateException e) {
                out.println("이전 요청 객체: IllegalStateException: " + e.getMessage());
            }
        }
        previous = request;
    }
}

    첫 요청이 끝나는 순간 그 요청 객체는 쓸 수 없는 껍데기가 되었다. 메시지가 말하는 그대로다. 서블릿이 받은 RequestFacade는 톰캣 내부의 요청 처리 객체를 감싼 겉 객체(facade)이고, 요청이 끝나면 속과의 연결이 끊긴다. Tomcat 10.1 설정 문서의 discardFacades 항목에 따르면 기본값 true에서 이 겉 객체는 요청이 끝날 때마다 버려지고, false로 바꾸면 겉 객체까지 재사용된다. 뒤쪽 설정에서는 낡은 참조가 예외로 걸러지지 않으므로, 명세가 경고한 예측할 수 없는 결과가 그대로 코드에 드러난다.

    일상에서 가져온 비유푸드코트의 쟁반

    요청 객체는 손님 한 명의 식사 동안만 쓰이는 쟁반과 같다. 식사가 끝나면 쟁반은 회수되어 닦인 뒤 다음 손님에게 간다. 쟁반을 들고 나갔다가 나중에 들여다보면 내 음식은 없다. 비유가 맞지 않는 곳도 있다. 톰캣의 기본 설정은 서블릿에 건네는 겉 객체를 요청마다 새로 만들고 속 객체만 재사용하므로, 낡은 참조는 남의 음식을 보는 대신 예외를 만난다.

    이 규칙은 01회의 "서블릿 객체는 하나, 스레드는 여럿"과 한 쌍이다. 서블릿의 필드는 모든 요청이 공유하므로 요청에 속한 것을 두면 안 되고, 요청 객체는 그 요청을 처리하는 동안에만 지역 변수와 메서드 인자로 흘러 다녀야 한다. 요청 객체를 다른 스레드에 넘겨 나중에 읽게 하는 코드도 같은 이유로 위험하다.

    출처메서드알아 둘 점
    시작 줄getMethod, getRequestURI, getQueryString, getProtocol시작 줄 GET /inspect?keyword=servlet&page=2 HTTP/1.1을 공백과 ?에서 자른 조각이다. getRequestURI와 getQueryString은 컨테이너가 디코딩하지 않은 원문을 준다.
    헤더 원문getHeader, getHeaders, getHeaderNames이름은 대소문자를 가리지 않는다. 같은 이름의 헤더가 여럿이면 getHeader는 첫 번째를 준다. 없는 헤더는 null이다.
    헤더를 해석한 값getServerName, getServerPort, getLocale, getCookies, getContentType, getContentLength, getCharacterEncodingHost, Accept-Language, Cookie, Content-Type, Content-Length 헤더를 용도에 맞게 가공한 것이다.
    연결(소켓)getRemoteAddr, getRemotePort, getLocalAddr, getLocalPort, getScheme, isSecure메시지가 아니라 이 요청이 타고 온 TCP 연결의 양쪽 끝과 연결 방식에서 나온다.

    몇 가지를 풀어 본다. getRequestURL은 메시지에 그대로 있던 값이 아니다. 연결 방식(http), Host 헤더, 경로를 이어 붙여 클라이언트가 요청한 URL을 다시 만든 것이고 쿼리 스트링은 빠진다. getLocale은 Accept-Language의 후보를 가중치 q가 큰 순서로 늘어놓았을 때의 첫째다. 헤더가 없으면 서버의 기본 로케일을 돌려준다. 본문이 없는 GET 요청이라 getContentType은 null, getContentLength는 길이를 모른다는 뜻의 -1이다. getCharacterEncoding의 null은 "인코딩이 지정되지 않았다"는 뜻이며 뒤에서 한글 폼이 깨지는 원인으로 다시 등장한다.

    getRemoteAddr이 0:0:0:0:0:0:0:1인 것은 curl이 localhost를 IPv6 루프백 주소로 연결했기 때문이다. 이 값은 헤더가 아니라 소켓의 상대편 주소다. Javadoc도 이 메서드가 클라이언트 또는 요청을 보낸 마지막 프록시의 주소를 돌려준다고 적는다. 01회에서 본 것처럼 WAS 앞에 웹 서버나 로드 밸런서가 있으면 여기에 찍히는 것은 사용자의 주소가 아니라 그 앞단 서버의 주소다. 같은 이유로 앞단이 HTTPS를 풀어 평문 HTTP로 넘겨주는 구성에서는, 앞단이 알려 준 원래 정보를 쓰도록 따로 설정하지 않는 한 getScheme이 http, isSecure가 false가 된다.

    요청 객체의 메서드들이 메시지의 서로 다른 부분(시작 줄, 헤더, 본문)과 메시지 밖의 연결 정보에서 값을 가져온다는 점을 한눈에 보여 준다. 깔끔한 대응 다이어그램, 흰 배경. 왼쪽 절반에 고정폭 글꼴로 적힌 HTTP 요청 메시지 상자가 있고 세 구역으로 색이 나뉜다. 위 구역(연한 파랑)에는 "GET /inspect?keyword=servlet&page=2 HTTP/1.1" 한 줄, 가운데 구역(연한 초록)에는 "Host: localhost:18082", "Accept-Language: ko-KR", "Cookie: theme=dark" 세 줄, 아래 구역(연한 주황)은 빈 줄 뒤에 "본문 바이트". 메시지 상자 아래에 따로 떨어진 회색 띠가 있고 라벨 "TCP 연결". 오른쪽 절반에는 둥근 사각형 네 개가 세로로 놓인다. 위에서부터 라벨 "getMethod · getRequestURI · getQueryString", "getHeader · getLocale · getCookies", "getInputStream · getParameter", "getRemoteAddr · getScheme". 위 구역에서 첫째 사각형으로, 가운데 구역에서 둘째 사각형으로, 아래 구역에서 셋째 사각형으로, 회색 띠에서 넷째 사각형으로 가는 화살표를 각각 같은 색으로 그린다. 왼쪽 상자 위에 제목 "요청 메시지", 오른쪽 위에 제목 "HttpServletRequest". 장식 없이 단순한 선. 요청 객체의 메서드는 값을 가져오는 자리가 다르다. 시작 줄, 헤더, 본문은 메시지 안에 있고, 상대 주소와 연결 방식은 메시지 밖의 TCP 연결에서 나온다.

    요청 데이터가 실려 오는 세 자리

    클라이언트가 서버에 데이터를 건네는 자리는 메시지 안에 세 군데가 있고, 실무의 요청은 거의 전부 이 셋 중 하나다. 어느 자리에 무엇이 실리는지를 구분하는 것이 요청 처리의 출발점이다.

    첫째와 둘째는 자리만 다르고 형식이 같다. 그래서 서블릿 API는 둘을 같은 메서드로 읽게 해 준다. 셋째는 본문의 형식을 컨테이너가 모른다. 컨테이너가 해 줄 수 있는 일은 바이트를 건네는 데까지이고, 그것이 JSON인지 XML인지 해석하는 일은 서블릿에 남는다. 이 구분이 다음 네 절의 뼈대다.

    세 가지 전달 방식을 요청 메시지 세 개로 나란히 놓고, 데이터가 실린 자리와 그것을 읽는 메서드를 대비한다. 깔끔한 비교 다이어그램, 흰 배경, 세로 칸 세 개가 가로로 나란히 놓인 구도. 각 칸 위에 제목 "GET 쿼리 파라미터", "POST HTML 폼", "HTTP 메시지 바디". 각 칸에는 고정폭 글꼴의 HTTP 요청 메시지 상자가 하나씩 있다. 첫째 상자는 시작 줄 "GET /search?keyword=a&page=2"에서 "keyword=a&page=2" 부분만 노란 형광색으로 칠하고 본문 영역은 비어 있다. 둘째 상자는 시작 줄 "POST /search", 헤더 "Content-Type: application/x-www-form-urlencoded", 본문 "keyword=a&page=2"이며 본문만 노란 형광색. 셋째 상자는 시작 줄 "POST /reservations", 헤더 "Content-Type: application/json", 본문 "{"guest":"한결","seats":2}"이며 본문만 주황 형광색. 첫째와 둘째 상자 아래에서 화살표가 하나로 합쳐져 둥근 사각형 "getParameter"를 가리킨다. 셋째 상자 아래의 화살표는 둥근 사각형 "getInputStream"을 가리키고 그 옆에 작은 주석 "해석은 서블릿의 몫". 장식 없이 단순한 선과 차분한 색. 쿼리 스트링과 폼 본문은 자리만 다른 같은 형식이라 getParameter 하나로 읽힌다. 그 밖의 본문은 바이트로 받아 서블릿이 직접 해석한다.

    GET 쿼리 파라미터

    쿼리 스트링은 URL에서 ? 뒤에 오는 부분이고, 이름=값 쌍을 &로 이어 붙인 문자열이다. 컨테이너가 이것을 파라미터 표로 바꾸는 절차는 단순하다. &에서 쪼개 쌍을 얻고, 각 쌍을 첫 =에서 쪼개 이름과 값을 얻고, 이름과 값 각각에서 +를 공백으로, %XX를 해당 바이트로 되돌린 뒤 그 바이트 열을 문자 인코딩에 따라 문자열로 만든다. 마지막 단계의 인코딩이 Tomcat 커넥터의 URIEncoding 속성이고, Tomcat 10.1 설정 문서에 적힌 기본값은 UTF-8이다.

    @WebServlet(name = "searchServlet", urlPatterns = "/search")
public class SearchServlet extends HttpServlet {
    @Override
    protected void service(HttpServletRequest request, HttpServletResponse response)
            throws IOException {
        response.setContentType("text/plain;charset=UTF-8");
        PrintWriter out = response.getWriter();
        out.println("요청 인코딩 = " + request.getCharacterEncoding());
        out.println("keyword = [" + request.getParameter("keyword") + "]");
        out.println("page    = [" + request.getParameter("page") + "]");
        out.println("flag    = [" + request.getParameter("flag") + "]");
        out.println("tag     = " + Arrays.toString(request.getParameterValues("tag")));
        out.println("이름 목록 = " + Collections.list(request.getParameterNames()));
    }
}

keyword = [servlet]
page    = [2]
flag    = [null]
tag     = [java, web]
이름 목록 = [keyword, page, tag]

    같은 이름 tag가 두 번 왔고 둘 다 보존되었다. 파라미터 표의 값은 문자열 하나가 아니라 문자열 배열이다. getParameterValues가 배열 전체를 주고, getParameter는 Javadoc의 표현대로 그 배열의 첫 번째 값을 준다. 값이 하나뿐이라고 믿을 수 있을 때만 getParameter를 쓴다. 표 전체가 필요하면 getParameterMap이 이름에서 문자열 배열로 가는 수정 불가능한 Map을 준다.

    $ curl "http://localhost:18082/search?keyword=%EC%84%9C%EB%B8%94%EB%A6%BF&page=&flag&tag=a+b&tag=a%2Bb"
요청 인코딩 = null
keyword = [서블릿]

    이 결과에는 구분해 둘 경계가 여럿 들어 있다.

    • 퍼센트 인코딩. %EC%84%9C는 바이트 세 개 EC 84 9C이고 UTF-8로 읽으면 "서"다. URL에는 한글을 그대로 실을 수 없으므로 클라이언트가 바이트로 바꿔 % 표기로 보내고, 톰캣이 URIEncoding에 따라 되돌린다. getQueryString은 되돌리기 전의 원문을, getParameter는 되돌린 값을 준다.
    • +와 %2B. 값 안의 +는 공백으로 풀렸고, 더하기 기호 자체를 보내려면 %2B로 적어야 했다.
    • 없는 것과 빈 것. 앞 실행에서 flag는 null이었다. 이름 자체가 오지 않았다는 뜻이다. 이번에는 page=도 flag도 빈 문자열이다. 이름은 왔고 값이 비었다. null 검사만 하는 코드는 빈 문자열을 통과시키고, isEmpty()를 바로 부르는 코드는 null에서 NullPointerException을 낸다.
    • 모든 값은 문자열이다. page=2의 2는 숫자가 아니라 문자 하나다. 숫자로 쓰려면 Integer.parseInt를 직접 불러야 하고, page=two가 오면 NumberFormatException이 난다. 형 변환과 그 실패 처리는 서블릿을 쓰는 사람의 일이다.

    POST HTML Form: 본문으로 자리를 옮긴 쿼리 스트링

    브라우저가 HTML 폼을 전송할 때 일어나는 일을 본다.

    입력 요소의 name이 파라미터 이름이 되고 사용자가 넣은 내용이 값이 된다. method="post"이면 그 쌍들이 메시지 본문에 실리고 Content-Type은 application/x-www-form-urlencoded가 된다. MDN의 설명으로 이 형식은 키와 값을 =로 잇고 쌍을 &로 구분하며 영숫자가 아닌 문자를 퍼센트 인코딩한다. 쿼리 스트링과 같은 문법이다. method="get"이면 같은 쌍들이 본문이 아니라 URL의 쿼리 스트링으로 간다. 브라우저 대신 curl로 같은 형식의 요청을 만들어 보냈다.

    POST /search HTTP/1.1
Host: localhost:18082
User-Agent: curl/8.7.1
Accept: */*
Content-Length: 61
Content-Type: application/x-www-form-urlencoded

keyword=%EC%84%9C%EB%B8%94%EB%A6%BF+%EC%9E%85%EB%AC%B8&page=1

    본문 61바이트가 앞 절의 쿼리 스트링과 같은 모양이다. 그래서 서버 쪽 코드를 바꿀 필요가 없다. SearchServlet은 service를 재정의했으므로 POST도 그대로 받고, getParameter는 값이 URL에서 왔는지 본문에서 왔는지 따지지 않는다. 둘이 한꺼번에 오면 어떻게 되는지부터 확인한다.

    두 출처의 값이 하나의 표로 합쳐졌고 쿼리 스트링의 값이 앞에 놓였다. 명세 3.1절이 정한 그대로다. 쿼리 스트링과 본문의 데이터는 하나의 파라미터 집합으로 합쳐지고, 쿼리 스트링의 데이터가 본문의 데이터보다 먼저 온다. 그래서 getParameter("keyword")는 fromQuery를 돌려준다.

    본문이 파라미터가 되는 조건

    컨테이너가 모든 본문을 파라미터로 해석하는 것은 아니다. 명세 3.1.1절은 네 조건이 모두 맞을 때만 폼 데이터를 파라미터 집합에 넣는다고 정한다. 요청이 HTTP 또는 HTTPS일 것, 메서드가 POST일 것, 콘텐츠 타입이 application/x-www-form-urlencoded일 것, 그리고 서블릿이 getParameter 계열 메서드를 처음 호출했을 것이다. 셋째 조건은 같은 본문에 헤더만 바꿔 보내면 드러난다.

    $ curl -H "Content-Type: text/plain" -d "keyword=book" "http://localhost:18082/search?page=9"
요청 인코딩 = null
keyword = [null]
page    = [9]
flag    = [null]
tag     = null
이름 목록 = [page]

    쿼리 스트링의 page는 읽혔지만 본문의 keyword는 파라미터가 되지 않았다. 컨테이너는 본문을 들여다보고 형식을 추측하지 않는다. Content-Type 헤더가 해석 방법을 정한다. JSON 본문이 getParameter로 읽히지 않는 이유가 이것이다.

    넷째 조건은 앞에서 말한 지연 해석이다. 명세는 조건이 맞아 폼 데이터가 파라미터가 되면 그 데이터를 더는 입력 스트림에서 직접 읽을 수 없고, 반대로 파라미터가 되지 않았다면 입력 스트림으로 읽을 수 있다고 덧붙인다. 본문은 소켓에서 한 번 흘러 들어오는 바이트이고, 먼저 읽는 쪽이 가져간다. 같은 서블릿을 두 URL에 매핑해 읽는 순서만 바꿔 보았다.

    @WebServlet(name = "formOrderServlet", urlPatterns = {"/form/param-first", "/form/stream-first"})
public class FormOrderServlet extends HttpServlet {
    @Override
    protected void doPost(HttpServletRequest request, HttpServletResponse response)
            throws IOException {
        response.setContentType("text/plain;charset=UTF-8");
        PrintWriter out = response.getWriter();
        if (request.getRequestURI().endsWith("/param-first")) {
            out.println("getParameter(keyword) = " + request.getParameter("keyword"));
            byte[] rest = request.getInputStream().readAllBytes();
            out.println("그 뒤 스트림에서 읽은 바이트 수 = " + rest.length);
        } else {
            byte[] raw = request.getInputStream().readAllBytes();
            out.println("스트림에서 읽은 본문 = " + new String(raw, StandardCharsets.UTF_8));
            out.println("그 뒤 getParameter(keyword) = " + request.getParameter("keyword"));
            out.println("그 뒤 getParameter(from)    = " + request.getParameter("from"));
        }
    }
}
    $ curl -d "keyword=book" "http://localhost:18082/form/param-first?from=query"
getParameter(keyword) = book
그 뒤 스트림에서 읽은 바이트 수 = 0

$ curl -d "keyword=book" "http://localhost:18082/form/stream-first?from=query"
스트림에서 읽은 본문 = keyword=book
그 뒤 getParameter(keyword) = null
그 뒤 getParameter(from)    = query

    getParameter를 먼저 부르면 톰캣이 그 순간 본문을 끝까지 읽어 파라미터 표를 만들고, 스트림에는 남는 것이 없다. 스트림을 먼저 읽으면 본문은 이미 지나갔고, 뒤늦은 getParameter는 쿼리 스트링에서 온 from만 찾는다. 서블릿이 호출되기 전에 톰캣이 본문을 미리 분해해 두었다면 둘째 실행에서도 keyword가 나왔을 것이다. 이 결과가 "파라미터 해석은 첫 호출 때 일어난다"의 증거다.

"서"의 UTF-8 바이트 EC 84 9C가 한 글자로 묶이지 않고 바이트마다 한 글자씩, ì와 화면에 보이지 않는 제어 문자 둘로 바뀐 것이 위 출력이다.

    고치는 방법은 요청의 인코딩을 알려 주는 것이고, 시점이 중요하다. 명세는 setCharacterEncoding을 POST 데이터가 해석되거나 입력이 읽히기 전에 불러야 하며 그 뒤의 호출은 효과가 없다고 정한다. 해석은 첫 getParameter 때 일어나므로 그보다 앞이어야 한다.

    request.setCharacterEncoding("UTF-8");              // 첫 getParameter 보다 먼저
response.setContentType("text/plain;charset=UTF-8");
PrintWriter out = response.getWriter();
out.println("요청 인코딩 = " + request.getCharacterEncoding());
out.println("keyword = [" + request.getParameter("keyword") + "]");

// keyword = [서블릿 입문]

    클라이언트가 Content-Type: application/x-www-form-urlencoded; charset=UTF-8처럼 인코딩을 밝혀 보내도 같은 결과가 나왔다. 그러나 클라이언트가 알아서 밝혀 주기를 기대할 수는 없고, 서블릿마다 첫 줄에 같은 호출을 넣는 것도 번거롭다. 모든 요청이 지나가는 필터에서 한 번 해 주면 된다. 스프링 부트 애플리케이션의 등록 목록에 있던 characterEncodingFilter가 그 일을 한다. 스프링 부트 3.5의 설정 문서에 server.servlet.encoding.charset의 기본값은 UTF-8이고, 요청에 대한 강제 적용은 force를 지정하지 않으면 켜진다고 적혀 있다. 부트 4.1.2 애플리케이션에 같은 한글 폼을 보냈을 때 getCharacterEncoding()은 UTF-8이었고 값도 깨지지 않았다. 부트 4.x에서는 이 속성들의 이름이 spring.servlet.encoding.*이다.

    폼 본문의 크기에는 한도가 있다. Tomcat 10.1 문서에 따르면 커넥터의 maxPostSize는 톰캣이 파라미터로 변환해 주는 본문의 최대 바이트 수이고 기본값은 2097152(2 MiB)다. 본문 전체에 대한 일반적인 제한이 아니라 파라미터 변환에만 적용된다. 스프링 부트에서는 server.tomcat.max-http-form-post-size(기본 2MB)로 조정한다.

    메시지 바디를 직접 읽기: 단순 텍스트

    폼이 아닌 본문은 컨테이너가 해석해 주지 않는다. 서블릿이 받는 것은 ServletInputStream, 곧 바이트의 흐름이다. 가장 단순한 경우인 평문 텍스트로 이 흐름의 성질을 본다.

    @WebServlet(name = "textBodyServlet", urlPatterns = "/body/text")
public class TextBodyServlet extends HttpServlet {
    @Override
    protected void doPost(HttpServletRequest request, HttpServletResponse response)
            throws IOException {
        ServletInputStream in = request.getInputStream();
        byte[] bytes = in.readAllBytes();                            // 본문 바이트 전부
        String text = new String(bytes, StandardCharsets.UTF_8);     // 바이트 -> 문자는 내가 정한다

        response.setContentType("text/plain;charset=UTF-8");
        PrintWriter out = response.getWriter();
        out.println("Content-Type 헤더   = " + request.getContentType());
        out.println("Content-Length 헤더 = " + request.getContentLength());
        out.println("읽은 바이트 수       = " + bytes.length);
        out.println("UTF-8로 해석        = " + text + " (문자 " + text.length() + "개)");
        out.println("ISO-8859-1로 해석   = " + new String(bytes, StandardCharsets.ISO_8859_1));
        out.println("한 번 더 read()     = " + in.read());
        try {
            request.getReader();
        } catch (IllegalStateException e) {
            out.println("getReader()         = IllegalStateException: " + e.getMessage());
        }
    }
}

    출력의 줄마다 본문에 관한 사실이 하나씩 들어 있다.

    • 길이는 바이트로 센다. 보낸 글자는 10개인데 Content-Length는 14다. 한글 두 글자가 UTF-8에서 3바이트씩, 공백과 영문 여덟 글자가 1바이트씩이다. HTTP 메시지의 본문은 바이트이고, 문자는 그것을 해석한 결과다.
    • 해석 규칙은 읽는 쪽이 정한다. 같은 14바이트를 UTF-8로 읽으면 원문이, ISO-8859-1로 읽으면 깨진 글자가 나온다. 바이트 자체에는 "나는 UTF-8이다"라는 표시가 없다. 보내는 쪽과 읽는 쪽이 같은 규칙을 써야 하고, 그 합의를 싣는 자리가 Content-Type의 charset이다. getInputStream으로 읽을 때는 그 헤더가 있든 없든 디코딩을 서블릿이 직접 한다.
    • 본문은 한 번 흘러가면 끝이다. 다 읽은 뒤의 read()는 -1이다. 스트림은 배열이 아니라 소켓에서 흘러 들어오는 데이터의 창구이고, 되감는 기능이 없다. 클라이언트가 응답을 기다리며 연결을 열어 둔 상태인데도 -1이 나온다는 점도 눈여겨본다. 연결이 닫혀서가 아니라, 컨테이너가 Content-Length가 말한 14바이트를 다 내주었기 때문이다. 메시지가 어디서 끝나는지는 컨테이너가 관리한다.
    • 바이트 창구와 문자 창구 중 하나만 쓴다. getReader()는 요청의 문자 인코딩으로 디코딩까지 해 주는 문자 스트림이다. Javadoc은 본문을 읽는 데 getInputStream()과 getReader() 중 하나만 호출할 수 있다고 정하고, 어기면 위와 같이 IllegalStateException이 난다. 같은 바이트를 두 경로가 나눠 읽으면 어느 쪽도 온전한 본문을 얻지 못하기 때문이다.

    서블릿이 호출될 때 본문은 다 와 있는가

    지금까지는 본문이 요청과 함께 한 덩어리로 도착한 것처럼 다루었다. 실제 네트워크에서는 헤더와 본문이 시간 차를 두고 올 수 있다. 헤더를 보낸 뒤 2초를 쉬고 본문 5바이트를 보내는 클라이언트를 nc로 만들고, 서블릿에는 doPost에 들어온 시각과 본문을 다 읽은 시각의 차이를 찍게 했다.

    이것을 01회의 스레드 풀과 이어 보면 의미가 분명해진다. 본문을 천천히 보내는 클라이언트는 그동안 작업 스레드 하나를 붙잡고 있다. 서블릿 코드에는 readAllBytes() 한 줄뿐이지만 그 줄은 네트워크를 기다리는 블로킹 호출이다. 큰 파일 업로드나 느린 모바일 네트워크가 서버의 스레드를 어떻게 소모하는지가 여기서 나온다.

    메시지 바디: JSON

    HTTP API가 주고받는 JSON도 서블릿의 눈에는 방금 본 텍스트 본문과 다르지 않다. 본문에 JSON 문법의 텍스트가 있고 Content-Type이 application/json일 뿐이다. 서블릿 API에는 JSON이라는 개념이 없다. 바이트를 읽어 구조를 해석하고 자바 객체로 옮기는 일은 라이브러리에 맡긴다. 스프링 부트 프로젝트에는 spring-boot-starter-json을 통해 Jackson이 들어와 있다. 예약 한 건을 나타내는 클래스와, 본문을 그 객체로 바꾸는 서블릿이다.

    public class Reservation {
    private String guest;
    private int seats;

    public String getGuest() { return guest; }
    public void setGuest(String guest) { this.guest = guest; }
    public int getSeats() { return seats; }
    public void setSeats(int seats) { this.seats = seats; }
}
    import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
// ...

@WebServlet(name = "jsonBodyServlet", urlPatterns = "/body/json")
public class JsonBodyServlet extends HttpServlet {
    private final ObjectMapper objectMapper = new ObjectMapper();   // 설정을 바꾸지 않고 읽기만 한다

    @Override
    protected void doPost(HttpServletRequest request, HttpServletResponse response)
            throws IOException {
        response.setContentType("text/plain;charset=UTF-8");
        PrintWriter out = response.getWriter();
        try {
            Reservation reservation =
                    objectMapper.readValue(request.getInputStream(), Reservation.class);
            out.println("guest = " + reservation.getGuest());
            out.println("seats = " + reservation.getSeats());
        } catch (JsonProcessingException e) {                        // 깨진 JSON, 타입 불일치 등
            response.setStatus(HttpServletResponse.SC_BAD_REQUEST);
            out.println(e.getClass().getSimpleName() + ": " + e.getOriginalMessage());
        }
    }
}

    결과에서 따져 볼 것이 넷이다.

    • 빠진 값은 예외가 아니다. {}를 보내면 객체는 만들어지고 필드는 자바의 기본값으로 남는다. seats가 0일 때 그것이 "0을 보냈다"인지 "보내지 않았다"인지 이 객체만으로는 구분할 수 없다. 입력 검증은 변환과 별개의 일이다.
    • 모르는 이름의 처리는 설정이다. Jackson 2.18.6에서 new ObjectMapper()의 기본 동작은 대상 클래스에 없는 이름이 오면 예외를 던지는 것이다. 스프링 부트 3.5 문서에 따르면 부트가 자동 구성하는 ObjectMapper는 이 기능(FAIL_ON_UNKNOWN_PROPERTIES)이 꺼져 있다. 같은 라이브러리라도 누가 만든 객체인지에 따라 결과가 다르다.
    • 잘못된 입력은 400으로 돌려보낸다. Jackson 2의 JsonProcessingException은 IOException의 하위 타입이라 잡지 않으면 doPost 밖으로 나가고, 톰캣은 500과 오류 페이지를 보낸다. 앞에서 본 스택 트레이스가 그 상황이었다. 형식이 틀린 본문은 서버의 고장이 아니라 클라이언트의 잘못이므로 잡아서 400으로 바꿨다.
    • 서블릿은 Content-Type을 확인하지 않았다. 같은 JSON을 Content-Type: text/plain으로 보내도 이 서블릿은 200으로 응답했다. 코드가 헤더를 보지 않고 스트림을 곧장 Jackson에 넘겼기 때문이다. 폼에서는 컨테이너가 Content-Type을 보고 해석 여부를 정했지만, 본문을 직접 읽는 순간부터 그 판단은 서블릿의 일이 된다.

    서블릿 필드에 둔 ObjectMapper

    objectMapper가 서블릿의 필드라는 점을 그냥 지나치면 안 된다. 서블릿 객체는 하나이고 여러 작업 스레드가 동시에 doPost를 실행하므로, 이 필드는 모든 요청이 공유한다. 요청 객체를 필드에 두면 안 된다고 한 직후에 이것은 왜 괜찮은가. Jackson의 ObjectMapper Javadoc에 답이 있다. 모든 설정이 읽기나 쓰기 호출보다 먼저 끝난다는 조건에서 매퍼 인스턴스는 스레드에 안전하다고 적혀 있다. 이 서블릿은 매퍼를 만든 뒤 설정을 건드리지 않고 변환에만 쓴다.

    싱글톤 객체의 필드에 둘 수 있는 것의 기준이 여기서 나온다. 요청마다 달라지는 데이터는 안 되고, 만들어진 뒤 상태가 바뀌지 않거나 동시 사용이 보장된 도구는 된다. 스프링의 빈이 대부분 싱글톤이면서 다른 빈을 필드로 들고 있는 것도 같은 기준 위에 있다.

    이 예제의 패키지 이름은 스프링 부트 3.x가 쓰는 Jackson 2.x의 것이다. 스프링 부트 4.1.2의 spring-boot-jackson 모듈은 tools.jackson.core:jackson-databind 3.1.7에 의존하며, Jackson 3은 패키지 이름이 tools.jackson으로 시작한다.

    HttpServletResponse: 상태 줄, 헤더, 본문을 채운다

    응답 메시지는 상태 줄, 헤더, 본문으로 이루어진다. HttpServletResponse는 이 세 부분을 채워 넣는 그릇이고, 채워진 내용을 HTTP 메시지의 바이트로 바꿔 소켓에 쓰는 일은 컨테이너가 한다. 세 부분을 모두 건드리는 서블릿으로 대응 관계를 확인한다.

    @WebServlet(name = "basicResponseServlet", urlPatterns = "/resp/basic")
public class BasicResponseServlet extends HttpServlet {
    @Override
    protected void doGet(HttpServletRequest request, HttpServletResponse response)
            throws IOException {
        response.setStatus(HttpServletResponse.SC_OK);                       // 상태 줄
        response.setHeader("Cache-Control", "no-cache, no-store, must-revalidate");
        response.setHeader("X-Trace-Id", "lab-0001");                        // 임의의 헤더
        response.setContentType("text/plain");                               // Content-Type 편의 메서드
        response.setCharacterEncoding("UTF-8");

        Cookie cookie = new Cookie("lastVisit", "servlet");                  // Set-Cookie 편의 객체
        cookie.setMaxAge(600);                                               // 초 단위
        response.addCookie(cookie);

        response.getWriter().println("응답 본문");                            // 메시지 바디
    }
}

    서블릿이 적은 것과 톰캣이 채운 것을 갈라 본다. 상태 코드 200, Cache-Control, X-Trace-Id는 적은 그대로 나갔다. setStatus를 부르지 않아도 기본 상태는 200이다. setContentType과 setCharacterEncoding은 따로 불렀지만 헤더에서는 Content-Type: text/plain;charset=UTF-8 한 줄로 합쳐졌다. Cookie 객체는 Set-Cookie 헤더 한 줄이 되었고, 실험에 쓴 Tomcat 11.0.27은 Max-Age=600과 함께 그 시각을 계산한 Expires도 붙였다. Tomcat 10.1.55에서도 두 속성이 함께 붙었고, 순서만 Max-Age, Expires로 반대였다. Content-Length: 14와 Date는 서블릿이 적지 않았다. 14는 "응답 본문"의 한글 네 글자 12바이트에 공백과 줄바꿈을 더한 값으로, 톰캣이 계산했다.

    편의 메서드라는 말의 뜻이 여기서 드러난다. setContentType, addCookie는 결국 헤더 한 줄을 만드는 일이고 setHeader로도 같은 줄을 쓸 수 있다. 형식을 틀리지 않게 대신 조립해 줄 뿐이다. setHeader는 같은 이름의 헤더가 이미 있으면 값을 덮어쓰고, addHeader는 같은 이름으로 값을 하나 더 추가한다. 리다이렉트도 같은 성격의 편의 메서드다.

    HTTP/1.1 302
Location: /inspect?from=redirect
Content-Length: 0
Date: Mon, 16 Nov 2026 00:58:38 GMT

    sendRedirect는 상태 코드를 302로 바꾸고 Location 헤더를 넣는다. Javadoc에 따르면 이때 버퍼에 있던 본문은 비워지고, 응답이 이미 커밋되었으면 IllegalStateException이 난다. 서버가 하는 일은 이 메시지를 보내는 데까지다. Location의 주소로 다시 요청하는 것은 브라우저이고, 그것은 처음 요청과 무관한 새 요청이다. Javadoc은 상대 URL을 컨테이너가 절대 URL로 바꿔 보내야 한다고 적지만 실험의 응답은 상대 경로 그대로였다. Tomcat 10.1의 컨텍스트 설정 useRelativeRedirects가 기본으로 true이기 때문이다.

    상태 코드를 바꾸는 방법은 둘이다. setStatus는 숫자만 바꾸고 본문은 서블릿이 쓰게 둔다. 앞의 JSON 서블릿이 400을 보낼 때 쓴 방식이다. sendError는 버퍼를 비우고 컨테이너의 오류 페이지를 보낸다. Javadoc은 setStatus로 오류 코드를 설정해도 컨테이너의 오류 페이지 처리가 동작하지 않는다는 점을 밝혀 둔다.

    응답 버퍼와 커밋: 헤더는 언제 서버를 떠나는가

    응답 메시지에서 상태 줄과 헤더는 본문보다 앞에 온다. 그런데 서블릿 코드는 헤더 설정과 본문 쓰기를 원하는 순서로 섞어 부른다. 본문의 첫 글자를 쓰자마자 소켓으로 내보낸다면 그 앞에 상태 줄과 헤더가 먼저 나가야 하고, 한번 나간 바이트는 되돌릴 수 없다. 그래서 컨테이너는 본문을 곧바로 보내지 않고 버퍼에 모은다. 명세 5.1절은 버퍼가 차면 컨테이너가 그 내용을 클라이언트로 내보내야 하고, 그것이 처음 보내는 데이터라면 그 순간 응답이 커밋된(committed) 것으로 본다고 정한다. Javadoc의 정의로 커밋된 응답은 상태 코드와 헤더가 이미 쓰인 응답이다.

    크기를 파라미터로 받아 그만큼의 글자를 쓰는 서블릿으로 버퍼의 경계를 찾아본다.

    int size = Integer.parseInt(request.getParameter("size"));
response.setContentType("text/plain;charset=UTF-8");
PrintWriter out = response.getWriter();
System.out.println("[big] size=" + size + ", 버퍼 크기=" + response.getBufferSize());
for (int i = 1; i <= size; i++) {
    out.write('a');                                     // 1바이트짜리 문자를 size 개 쓴다
    if (i == size / 2) {
        System.out.println("[big] 절반 썼을 때 isCommitted=" + response.isCommitted());
    }
}
System.out.println("[big] 다 썼을 때   isCommitted=" + response.isCommitted());

    100바이트짜리 응답은 서블릿이 끝날 때까지 커밋되지 않았다. 본문 전체가 버퍼 안에 있었으므로, 서블릿이 돌아온 뒤 톰캣은 본문의 길이를 정확히 알고 Content-Length: 100을 적을 수 있었다. 20000바이트짜리 응답은 다르다. 버퍼가 넘치는 순간 톰캣은 헤더를 먼저 보내야 하는데, 그 시점에는 서블릿이 앞으로 얼마나 더 쓸지 알 수 없다. Content-Length를 적을 수 없으므로 길이를 미리 알리지 않아도 되는 전송 방식, 청크 전송 인코딩(chunked transfer encoding)을 쓴다. 본문을 조각으로 나누고 조각마다 앞에 자기 길이를 적는 방식이다. 응답을 가공하지 않고 받아 a를 지우면 조각의 뼈대만 남는다.

    2000\r\n  (a 8192개)  \r\n
2000\r\n  (a 8192개)  \r\n
e20\r\n   (a 3616개)  \r\n
0\r\n\r\n

    조각의 길이는 16진수다. 2000은 8192, e20은 3616이고 셋을 더하면 20000이다. 길이 0인 조각이 본문의 끝을 알린다. 버퍼 크기와 같은 8192바이트씩 나간 것이 보인다. 크기를 바꿔 가며 확인한 경계는 8192바이트였다. 8192바이트까지는 Content-Length가 붙었고 8193바이트부터 청크 전송으로 바뀌었다. 로그에서 10000자를 쓴 시점에 아직 커밋 전인 까닭은 getWriter로 쓴 문자가 먼저 문자 버퍼에 모였다가 바이트로 인코딩되어 바이트 버퍼로 넘어가는 두 단계를 거치기 때문이다. Tomcat의 OutputBuffer에는 문자용과 바이트용 버퍼가 따로 있다. 커밋 시점은 "8192번째 바이트를 쓴 순간"처럼 딱 떨어지지 않으므로, 코드가 그 정확한 시점에 기대면 안 된다.

    서블릿의 호출                     응답 버퍼(8192바이트)            소켓

    서블릿이 쓴 본문이 버퍼에 머무는 동안과 소켓으로 나간 뒤를 커밋 시점으로 나누어, 그 전후로 가능한 일이 달라진다는 것을 보여 준다. 깔끔한 타임라인 다이어그램, 흰 배경, 왼쪽에서 오른쪽으로 시간이 흐른다. 가로로 긴 띠 세 줄이 위아래로 놓인다. 맨 위 줄의 라벨은 "서블릿 코드", 가운데 줄은 "응답 버퍼", 맨 아래 줄은 "소켓(클라이언트로)". 화면 가운데쯤에 굵은 빨간 세로 점선이 세 줄을 관통하고 그 위에 라벨 "커밋". 점선 왼쪽 구간: 맨 위 줄에 작은 상자 "setStatus · setHeader"와 "본문 쓰기", 가운데 줄에 조금씩 차오르는 버퍼 그림 세 개(4분의 1, 절반, 가득), 맨 아래 줄은 비어 있고 연한 회색 글씨 "아직 아무것도 나가지 않음". 점선 바로 위치에서 가운데 줄의 가득 찬 버퍼로부터 맨 아래 줄로 내려가는 굵은 화살표, 라벨 "상태 줄 + 헤더 + 본문 첫 조각". 점선 오른쪽 구간: 맨 위 줄에 상자 "본문 쓰기 계속", 그 옆에 금지 표시가 붙은 상자 "setHeader · setStatus 무시됨", 맨 아래 줄에 작은 조각 상자 여러 개가 이어진다. 점선 왼쪽 구간 전체 아래에 초록색 괄호와 라벨 "헤더·상태 변경 가능", 오른쪽 구간 아래에 회색 괄호와 라벨 "변경 불가". 장식 없이 단순한 선. 커밋은 상태 줄과 헤더가 소켓으로 나간 시점이다. 그 전에는 응답의 모든 것을 바꿀 수 있고, 그 뒤에는 본문을 이어 쓰는 것만 가능하다.

    커밋 뒤에 헤더를 건드리면 어떻게 되는지는 flushBuffer()로 커밋을 강제해 보면 안다.

    response.setContentType("text/plain;charset=UTF-8");
PrintWriter out = response.getWriter();
out.println("첫 줄");
response.setHeader("X-Before", "1");
System.out.println("[commit] flush 전 isCommitted=" + response.isCommitted());

response.flushBuffer();                                 // 버퍼를 강제로 내보낸다
System.out.println("[commit] flush 후 isCommitted=" + response.isCommitted());

response.setHeader("X-After", "1");                     // 이미 늦었다
response.setStatus(500);                                // 이것도 늦었다
System.out.println("[commit] setStatus(500) 후 getStatus=" + response.getStatus());
try {
    response.sendRedirect("/inspect");
} catch (IllegalStateException e) {
    System.out.println("[commit] sendRedirect: IllegalStateException: " + e.getMessage());
}
out.println("둘째 줄");

    본문을 쓴 뒤라도 커밋 전에 설정한 X-Before는 나갔다. 커밋 뒤의 X-After는 조용히 사라졌고 setStatus(500)도 무시되어 상태는 200으로 남았다. 예외도 경고도 없다는 점이 까다롭다. 명세 5.2절이 커밋 뒤에 설정한 헤더는 컨테이너가 무시한다고 정한 그대로다. sendRedirect만은 예외로 실패를 알린다. 본문 쓰기는 커밋 뒤에도 계속할 수 있어서 "둘째 줄"은 정상적으로 나갔다.

    이 규칙이 실제로 문제가 되는 것은 본문을 쓰는 도중에 실패할 때다. 글자를 size개 쓴 다음 예외를 던지는 서블릿으로 두 경우를 비교했다.

    size=100    → HTTP/1.1 500
size=30000  → HTTP/1.1 200, Transfer-Encoding: chunked
              30000바이트를 받은 뒤 연결이 끊김. curl 종료 코드 18

    100바이트를 쓴 시점에는 아직 커밋 전이라 톰캣이 상태 코드를 500으로 바꿀 수 있었다. 30000바이트를 쓴 시점에는 이미 200과 헤더가 클라이언트에 도착해 있다. 톰캣이 할 수 있는 일은 끝을 알리는 길이 0 조각을 보내지 않은 채 연결을 끊는 것뿐이고, curl은 전송이 완결되지 않았다는 오류(종료 코드 18)로 이를 알렸다. 응답을 받는 쪽이 이 신호를 확인하지 않으면 "200으로 성공한 잘린 응답"이 된다. 여기서 두 가지 습관이 나온다. 상태 코드, 헤더, 쿠키, 리다이렉트에 관한 결정은 본문을 쓰기 전에 끝낸다. 실패할 수 있는 작업, 곧 검증과 조회는 본문의 첫 글자를 쓰기 전에 마친다.

    Writer와 문자 인코딩

    getWriter()가 주는 PrintWriter는 문자를 받아 응답의 문자 인코딩으로 바이트를 만든다. 요청 본문을 읽을 때의 반대 방향이고, 같은 종류의 함정이 있다. 응답 인코딩을 아무도 정하지 않았을 때의 기본값이 ISO-8859-1이라는 점이다. 명세 5.6절과 ServletResponse의 Javadoc이 그렇게 정한다. 같은 세 글자 "가나다"를 다섯 가지 방법으로 쓰고, 응답의 Content-Type 헤더와 본문 바이트를 16진수로 확인했다.

    서블릿이 한 일(순서대로)Content-Type 헤더본문 바이트
    getWriter().print("가나다")만없음3f 3f 3f
    setContentType("text/plain") → getWritertext/plain;charset=ISO-8859-13f 3f 3f
    setContentType("text/plain") → getWriter → setCharacterEncoding("UTF-8")text/plain;charset=ISO-8859-13f 3f 3f
    setContentType("text/plain") → setCharacterEncoding("UTF-8") → getWritertext/plain;charset=UTF-8ea b0 80 eb 82 98 eb 8b a4
    setContentType("text/plain") → getOutputStream에 UTF-8 바이트를 직접 씀text/plainea b0 80 eb 82 98 eb 8b a4

    3f는 물음표다. ISO-8859-1에는 한글이 없으므로 인코더가 표현할 수 없는 글자를 물음표로 바꿨다. 요청 쪽의 깨짐과 성격이 다르다는 데 주의한다. 요청에서는 바이트는 온전한데 해석이 틀렸으므로 올바른 인코딩으로 다시 읽으면 복구된다. 여기서는 원래 글자의 정보가 바이트로 바뀌는 단계에서 사라졌다. 클라이언트가 무슨 수를 써도 "가나다"를 되찾을 수 없다.

    셋째 줄이 순서의 규칙을 보여 준다. Javadoc은 setCharacterEncoding이 getWriter가 호출된 뒤나 응답이 커밋된 뒤에는 효과가 없다고 정한다. Writer가 만들어질 때 문자를 바이트로 바꾸는 규칙이 함께 고정되기 때문이다. 요청에서 "첫 getParameter보다 먼저"였던 것이 응답에서는 "getWriter보다 먼저"다. 둘째 줄에서는 서블릿이 인코딩을 말하지 않았는데도 톰캣이 헤더에 charset=ISO-8859-1을 붙였다. getWriter 시점에 확정된 인코딩을 클라이언트에 알려, 헤더와 본문이 어긋나지 않게 한 것이다. 다섯째 줄처럼 getOutputStream으로 바이트를 직접 쓰면 컨테이너는 인코딩에 관여하지 않고 charset도 붙이지 않는다. 본문을 쓰는 데도 getWriter와 getOutputStream 가운데 하나만 쓸 수 있고, 둘 다 부르면 IllegalStateException이 난다.

    스프링 부트의 characterEncodingFilter가 응답까지 고쳐 주지는 않는다. 부트 4.1.2 애플리케이션에서 아무 설정 없이 response.getWriter().print("가나다")를 실행했을 때 본문은 ???였고 response.getCharacterEncoding()은 ISO-8859-1이었다. 문서에도 강제 적용이 기본으로 켜지는 쪽은 요청이라고만 적혀 있다. 서블릿으로 직접 응답을 쓸 때는 응답 인코딩을 스스로 정한다.

    JSON 응답

    JSON 응답은 요청에서 한 일의 역방향이다. 객체를 JSON 텍스트로 바꾸고, Content-Type을 application/json으로 알린다.

    Reservation reservation = new Reservation();
reservation.setGuest("한결");
reservation.setSeats(2);

response.setContentType("application/json");
if ("stream".equals(request.getParameter("mode"))) {
    objectMapper.writeValue(response.getOutputStream(), reservation);   // 바이트로 직접
} else {
    response.setCharacterEncoding("UTF-8");
    String json = objectMapper.writeValueAsString(reservation);         // 객체 -> JSON 문자열
    response.getWriter().write(json);
}

    Jackson은 객체의 게터를 읽어 getGuest에서 이름 guest를, getSeats에서 seats를 만들었다. 본문은 두 경로 모두 같은 28바이트다. 차이는 헤더다. Writer로 쓴 쪽에는 ;charset=UTF-8이 붙었고 스트림으로 쓴 쪽에는 붙지 않았다. JSON의 표준인 RFC 8259는 닫힌 생태계 밖에서 시스템끼리 주고받는 JSON 텍스트는 UTF-8로 인코딩해야 한다고 정하고, application/json 등록 정보에는 charset 파라미터가 정의되어 있지 않으며 붙여도 규격을 따르는 수신자에게는 아무 효과가 없다고 적는다. JSON은 처음부터 UTF-8이므로 인코딩을 따로 말할 필요가 없다는 뜻이다. Writer 경로에서 붙은 파라미터는 앞에서 본 톰캣의 동작, 곧 getWriter를 쓰면 확정된 인코딩을 헤더에 적는 동작의 결과다. 해롭지는 않지만 의미도 없다. 스트림 경로는 Jackson이 UTF-8 바이트를 직접 쓰므로 헤더가 표준이 말하는 모양 그대로 나간다.

    이 장의 핵심

    요청 객체와 응답 객체는 HTTP 메시지의 바이트를 가리는 얇은 막이다. 요청 쪽에서는 값이 필요해지는 순간에 바이트가 문자열과 파라미터로 바뀌고, 본문은 소켓에서 한 번 흘러 들어올 뿐이다. 응답 쪽에서는 쓴 내용이 버퍼에 머무는 동안에만 상태 줄과 헤더를 바꿀 수 있다. API의 사용 순서에 관한 규칙은 모두 이 두 사실에서 나온다.
    서블릿 등록과 URL 매핑
    임베디드 톰캣에서는 @ServletComponentScan이 @WebServlet 클래스를 찾아 등록한다. 요청 경로는 정확한 일치, 가장 긴 경로 매핑, 확장자 매핑, 기본 서블릿(/) 순서로 서블릿에 연결된다.
    HttpServlet의 분기
    컨테이너가 부른 service가 요청 메서드를 보고 doGet, doPost 등으로 넘긴다. 재정의하지 않은 메서드로 요청이 오면 405가 나간다.
    요청 객체의 값의 출처
    시작 줄, 헤더, 본문은 메시지 안에서, 상대 주소와 연결 방식은 TCP 연결에서 나온다. 톰캣은 바이트를 문자열로 바꾸는 일을 값이 요청될 때까지 미룬다.
    요청 객체의 수명
    요청 객체는 service 범위 안에서만 유효하다. 필드나 다른 스레드에 넘겨 두면 요청이 끝난 뒤에는 쓸 수 없고, 톰캣의 기본 설정에서는 예외가 난다.
    파라미터
    쿼리 스트링과 application/x-www-form-urlencoded 본문은 같은 형식이라 getParameter로 함께 읽힌다. 값은 문자열 배열이고 쿼리 스트링의 값이 앞에 온다. 해석은 첫 getParameter 호출 때 일어난다.
    메시지 바디
    getInputStream은 소켓에서 오는 바이트를 Content-Length만큼 한 번만 내준다. 디코딩과 JSON 해석은 서블릿의 일이고, 본문이 아직 오지 않았으면 작업 스레드가 읽기에서 기다린다.
    요청과 응답의 인코딩
    쿼리 스트링은 URIEncoding(기본 UTF-8)으로, 폼 본문은 요청 인코딩(지정이 없으면 ISO-8859-1)으로 풀린다. 응답 Writer의 기본도 ISO-8859-1이다. 요청은 첫 getParameter 전에, 응답은 getWriter 전에 인코딩을 정한다.
    응답 버퍼와 커밋
    본문은 버퍼에 모였다가 나간다. 첫 데이터가 나가는 순간 상태 줄과 헤더가 함께 나가 응답이 커밋되고, 그 뒤의 헤더·상태 변경은 무시된다.
    Content-Length와 chunked
    본문 전체가 버퍼에 들어간 채 서블릿이 끝나면 컨테이너가 길이를 계산해 Content-Length를 붙인다. 버퍼가 넘치면 길이를 모르는 채 헤더를 보내야 하므로 청크 전송 인코딩을 쓴다.

    실무에서 다시 판단하면, 이 회차의 지식이 가장 자주 쓰이는 곳은 "본문은 한 번만 읽힌다"는 제약이다. 요청 본문을 로그로 남기려는 필터가 스트림을 읽어 버리면 그 뒤의 컨트롤러는 빈 본문을 받는다. 반대로 폼 요청에서 필터가 getParameter를 먼저 부르면 뒤에서 스트림을 읽으려는 코드가 빈 스트림을 만난다. 본문을 두 번 써야 하는 요구가 생기면 읽은 바이트를 메모리에 보관해 다시 내주는 요청 래퍼를 끼워야 하고, 그 비용(요청마다 본문 크기만큼의 메모리)을 감수할지 판단해야 한다. 요청 로그를 헤더와 메타데이터로 한정하는 편이 나은 경우가 많다.

    커밋은 장애 분석에서 다시 만난다. "서버 로그에는 예외가 있는데 클라이언트는 200을 받았다"는 보고는 대개 응답이 커밋된 뒤에 실패한 경우다. 큰 목록을 스트리밍으로 내려 주는 API, 파일 다운로드, 템플릿을 렌더링하면서 지연 로딩으로 DB를 조회하는 화면이 여기에 해당한다. 대응은 버퍼를 키우는 것이 아니라 순서를 바꾸는 것이다. 실패할 수 있는 조회와 검증을 본문 쓰기 전에 끝내고, 응답은 확정된 데이터만으로 만든다. 스트리밍이 꼭 필요하면 클라이언트가 마지막 조각까지 받았는지 확인하도록 계약에 넣는다.

    요청 객체에서 꺼낸 값의 신뢰도는 배치 구조에 달려 있다. getRemoteAddr, getScheme, getServerName은 WAS가 직접 인터넷에 노출된 구성에서만 사용자의 실제 접속 정보다. 앞에 로드 밸런서나 웹 서버가 있으면 그 값은 앞단과 WAS 사이의 연결을 말해 준다. 접속 제한, 감사 로그, 리다이렉트 URL 생성처럼 이 값에 기대는 기능을 만들 때는 앞단이 원래 정보를 어떤 헤더로 넘겨주는지, WAS가 그 헤더를 믿도록 설정되어 있는지를 먼저 확인한다.

    마지막으로, 요청 객체를 요청 밖으로 들고 나가지 않는다는 규칙은 비동기 코드를 쓸 때 깨지기 쉽다. 다른 스레드에서 실행될 작업에 HttpServletRequest를 그대로 넘기면, 그 작업이 실행될 때는 원래 요청이 끝나 있을 수 있다. 필요한 값(헤더, 파라미터, 사용자 식별자)을 요청 스레드에서 미리 꺼내 불변 값으로 넘기는 것이 안전하다.

    5. 100바이트일 때는 본문이 아직 버퍼 안에 있고 응답이 커밋되지 않았으므로 컨테이너가 상태 코드를 500으로 바꿔 보낼 수 있다. 30000바이트일 때는 버퍼가 이미 넘쳐 200과 헤더, 본문의 앞부분이 청크 전송으로 나간 뒤다. 상태 줄은 되돌릴 수 없으므로 클라이언트가 본 상태 코드는 200이다. 다만 컨테이너가 끝을 알리는 길이 0 조각을 보내지 못한 채 연결을 끊으므로, 클라이언트는 본문이 완결되지 않았다는 전송 오류로 이를 알 수 있다. 상태 코드만 확인하는 클라이언트는 잘린 응답을 성공으로 처리하게 된다.

     Content-Type: application/x-www-form-urlencoded인 POST 요청을 받은 서블릿이 먼저 request.getInputStream().readAllBytes()로 본문을 읽고, 그다음 request.getParameter("keyword")를 불렀다. 본문에는 keyword=book이 있었다. 결과와 이유로 옳은 것은? book이 나온다. 컨테이너는 서블릿을 호출하기 전에 본문을 미리 해석해 파라미터 표를 만들어 두기 때문이다. null이 나온다. 폼 본문은 첫 getParameter 호출 때 입력 스트림에서 읽어 해석되는데, 그 스트림을 이미 다 읽어 버렸기 때문이다. IllegalStateException이 난다. getInputStream과 getParameter는 한 요청에서 함께 쓸 수 없기 때문이다. 빈 문자열이 나온다. 이름은 등록되지만 값을 읽을 바이트가 남아 있지 않기 때문이다. 폼 데이터가 파라미터가 되는 조건 가운데 하나가 "서블릿이 getParameter 계열 메서드를 처음 호출했을 것"이다. 해석은 그 시점에 입력 스트림을 읽어 이루어지고, 본문은 한 번만 흘러 들어오므로 먼저 스트림을 읽으면 해석할 것이 남지 않는다. 실험에서도 null이 나왔다. 미리 해석해 둔다는 설명은 이 결과와 맞지 않는다. 함께 쓸 수 없어 예외가 나는 조합은 getInputStream과 getReader다. 이름조차 읽지 못했으므로 빈 문자열이 아니라 null이다. 같은 서블릿이 어떤 요청에는 Content-Length가 붙은 응답을, 다른 요청에는 Transfer-Encoding: chunked 응답을 보냈다. 서블릿은 두 경우 모두 헤더를 직접 지정하지 않았다. 차이를 만든 것은? 클라이언트가 보낸 Accept 헤더의 값 서블릿이 getWriter를 썼는지 getOutputStream을 썼는지 서블릿이 끝날 때까지 본문 전체가 응답 버퍼 안에 들어갔는지 여부 응답 본문에 한글이 포함되었는지 여부 본문 전체가 버퍼에 든 채 서블릿이 끝나면 컨테이너는 길이를 알 수 있으므로 Content-Length를 붙인다. 버퍼가 넘치면 길이를 모르는 채 헤더를 먼저 보내야 하므로 조각마다 길이를 적는 청크 전송을 쓴다. 실험에서 경계는 버퍼 크기인 8192바이트였다. Accept 헤더, 쓰기 창구의 종류, 문자의 종류는 이 선택과 무관하다. 로드 밸런서 뒤에 있는 WAS에서 모든 요청의 request.getRemoteAddr()이 같은 사설 IP로 찍힌다. 가장 정확한 설명은? 이 메서드는 HTTP 메시지가 아니라 요청이 타고 온 TCP 연결의 상대편 주소를 돌려주는데, 그 상대편이 로드 밸런서이기 때문이다. 톰캣이 요청 객체를 재사용하면서 첫 요청의 주소가 그대로 남았기 때문이다. Host 헤더에 로드 밸런서의 주소가 들어 있기 때문이다. 사용자들이 User-Agent가 같은 브라우저를 쓰기 때문이다. getRemoteAddr의 값은 소켓에서 나온다. WAS가 맺은 TCP 연결의 반대쪽 끝은 사용자가 아니라 요청을 대신 전달한 로드 밸런서다. Javadoc도 클라이언트 또는 마지막 프록시의 주소라고 적는다. 요청 객체의 재사용은 요청 사이에 값이 섞이지 않게 정리된 뒤에 이루어지므로 원인이 아니다. Host 헤더는 getServerName과 getServerPort의 출처이고, User-Agent는 주소와 무관하다. 쿼리 스트링으로 보낸 한글은 정상인데, 같은 서블릿에 HTML 폼(POST)으로 보낸 한글만 깨진다. 스프링 부트 없이 톰캣만 쓰는 환경이다. 원인과 해결로 옳은 것은? 폼 본문은 퍼센트 인코딩을 하지 않기 때문이다. 클라이언트가 인코딩해서 보내야 한다. 응답의 문자 인코딩을 정하지 않았기 때문이다. response.setCharacterEncoding("UTF-8")을 추가한다. getParameter가 본문의 값을 읽지 못하기 때문이다. getInputStream으로 바꿔야 한다. 쿼리 스트링과 본문은 디코딩에 쓰는 인코딩이 따로 정해지는데 본문 쪽이 지정되지 않았기 때문이다. 첫 getParameter 전에 request.setCharacterEncoding("UTF-8")을 부른다. 쿼리 스트링은 커넥터의 URIEncoding(기본 UTF-8)으로, 폼 본문은 요청의 문자 인코딩으로 풀린다. Content-Type에 charset이 없으면 요청 인코딩은 지정되지 않은 상태이고 %nn 값이 ISO-8859-1로 해석되어 깨진다. 해석이 일어나는 첫 getParameter보다 먼저 인코딩을 정해야 한다. 폼 본문도 퍼센트 인코딩되어 온다. 응답 인코딩만 문제라면 쿼리 스트링의 한글도 같은 응답에서 깨져 보였을 것이다. getParameter는 폼 본문을 읽을 수 있다. 서블릿 클래스의 필드로 두어도 되는 것은? 방금 들어온 요청의 HttpServletRequest. 같은 요청의 다른 메서드에서 쓰기 편하다. 현재 요청의 파라미터에서 꺼낸 keyword 문자열. 불변 객체라 안전하다. 생성한 뒤 설정을 바꾸지 않고 변환에만 쓰는 ObjectMapper. 요청마다 값을 채워 쓰는 Reservation 객체 하나. 객체 생성을 줄일 수 있다. 서블릿 객체는 하나이고 여러 작업 스레드가 동시에 실행하므로 필드는 모든 요청이 공유한다. ObjectMapper는 설정이 읽기·쓰기 호출보다 먼저 끝났다면 스레드에 안전하다고 Javadoc이 밝히므로 공유할 수 있다. 요청 객체는 요청이 끝나면 무효가 되고 다른 스레드의 요청과 뒤섞인다. keyword 문자열은 객체 자체는 불변이어도 필드라는 변수는 요청마다 덮어써지므로 다른 요청의 값이 읽힌다. 공유 Reservation도 같은 이유로 두 요청의 값이 섞인다.
    쿼리 파라미터(query parameter)
    URL의 ? 뒤에 이름=값 쌍을 &로 이어 실어 보내는 데이터. 시작 줄에 있으므로 본문이 없는 GET 요청으로도 보낼 수 있다.
    application/x-www-form-urlencoded
    HTML 폼의 기본 전송 형식. 쿼리 스트링과 같은 문법의 텍스트를 메시지 본문에 싣는다. 서블릿 컨테이너는 이 콘텐츠 타입의 POST 본문만 파라미터로 해석한다.
    퍼센트 인코딩(percent-encoding)
    URL이나 폼 본문에 그대로 쓸 수 없는 바이트를 %와 16진수 두 자리로 적는 표기. 받는 쪽은 바이트로 되돌린 뒤 문자 인코딩에 따라 문자열로 만든다.
    메시지 바디(message body)
    HTTP 메시지에서 헤더 뒤의 빈 줄 다음에 오는 바이트. 형식은 Content-Type이, 길이는 Content-Length나 청크 전송이 알려 준다.
    기본 서블릿(default servlet)
    URL 패턴 /에 매핑된 서블릿. 다른 어떤 패턴에도 맞지 않은 요청이 도달한다. 스프링 부트는 이 자리에 DispatcherServlet을 둔다.
    파사드(facade)
    내부 객체를 감싸 정해진 메서드만 드러내는 겉 객체. 톰캣은 서블릿에 내부 요청 객체 대신 RequestFacade를 건네고 요청이 끝나면 연결을 끊는다.
    응답 버퍼(response buffer)
    서블릿이 쓴 본문을 소켓으로 보내기 전에 모아 두는 컨테이너의 메모리 영역. 실험한 톰캣에서 크기는 8192바이트였다.
    커밋(commit)
    응답의 상태 줄과 헤더가 클라이언트로 쓰인 상태. 버퍼가 차거나 flushBuffer를 부르거나 서블릿이 끝나면 일어나며, 그 뒤에는 헤더와 상태 코드를 바꿀 수 없다.
    청크 전송 인코딩(chunked transfer encoding)
    본문을 조각으로 나누고 조각마다 16진수 길이를 앞에 붙여 보내는 HTTP/1.1의 전송 방식. 전체 길이를 미리 알 수 없을 때 쓰며, 길이 0인 조각이 끝을 알린다.
    데이터 바인딩(data binding)
    JSON 같은 텍스트 구조를 자바 객체의 프로퍼티에 대응시켜 값을 채우거나, 반대로 객체를 텍스트로 쓰는 일. 이 회차에서는 Jackson의 ObjectMapper가 맡았다.
