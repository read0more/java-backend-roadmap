    이 회차의 질문: 요청 한 건은 어떻게 메서드 호출 한 번이 되는가

    05회에서 DispatcherServlet이 요청을 받아 핸들러 매핑(HandlerMapping)에게 처리할 대상을 묻고, 핸들러 어댑터(HandlerAdapter)에게 실행을 맡기는 뼈대를 보았다. 뼈대만으로는 두 가지가 설명되지 않는다. 컨트롤러 메서드가 수백 개일 때 스프링은 그중 하나를 무엇을 기준으로 고르는가. 골라낸 메서드의 매개변수에 넣을 값은 요청의 어느 부분에서, 어떤 변환을 거쳐 나오는가.

    두 질문 모두 출발점은 「HTTP 웹 기본 지식」 권에서 본 HTTP 요청 메시지의 구조다. 요청은 시작 줄, 헤더, 빈 줄, 메시지 바디로 이루어진 바이트의 나열이고, 스프링 MVC의 애너테이션은 이 가운데 어느 조각을 읽을지를 가리키는 표지다.

    POST /loans/form?from=web HTTP/1.1                      ← 시작 줄: 메서드 · 경로 · 쿼리 스트링
Host: localhost:8080                                    ← 헤더
Content-Type: application/x-www-form-urlencoded
Cookie: visit=3
                                                        ← 빈 줄
borrower=kim&days=7                                     ← 메시지 바디

  요청의 조각                    그것을 읽는 수단
  ─────────────────────────────────────────────────────────────────────
  메서드, 경로                   @RequestMapping 계열(어느 메서드를 부를지), @PathVariable
  쿼리 스트링                    @RequestParam, @ModelAttribute
  헤더                           @RequestHeader, @CookieValue
  (Content-Type, Accept)         매핑 조건 consumes, produces
  바디 - HTML 폼 형식            @RequestParam, @ModelAttribute   ← 쿼리 스트링과 같은 창구
  바디 - 그 밖의 형식            @RequestBody, HttpEntity, InputStream

    이 표에서 눈여겨볼 곳은 두 군데다. 하나는 헤더인 Content-Type과 Accept가 값을 읽는 데만이 아니라 핸들러를 고르는 데에도 쓰인다는 점이다. 다른 하나는 바디가 형식에 따라 전혀 다른 창구로 읽힌다는 점이다. HTML 폼이 보낸 바디는 쿼리 스트링과 같은 방법으로 읽히고, JSON이나 일반 텍스트 바디는 그 방법으로는 한 글자도 읽히지 않는다. 이 회차의 뒤쪽 절반은 이 경계가 왜 생겼는지, 경계를 잘못 넘으면 어떤 증상이 나오는지를 다룬다.

    순서는 다음과 같다. 프로젝트의 형태를 짧게 확인하고, 이후 모든 실험의 관찰 도구가 될 로깅을 먼저 본다. 그다음 요청 매핑이 등록되고 조회되는 과정을 따라가고, 헤더, 요청 파라미터, 메시지 바디 순으로 요청의 조각을 하나씩 읽어 본다. 응답을 만드는 쪽과 HTTP 메시지 컨버터, 인자를 만들어 주는 RequestMappingHandlerAdapter의 내부 구조는 07회의 몫이므로 여기서는 필요한 만큼만 이름을 부른다.

    이 권의 기준은 Spring Boot 3.x(Spring Framework 6.x)다. 이 회차의 실험은 JDK 21에서 Spring Boot 4.1.2(Spring Framework 7.0.10, 임베디드 Tomcat 11.0.27, Jackson 3.1.7)로 돌렸다. 본문에 적은 규칙은 Spring Framework 6.2 레퍼런스와 6.2.x 소스, Spring Boot 3.5 레퍼런스에서 같은 내용임을 확인했고, 버전에 따라 달라지는 부분은 그 자리에서 밝힌다. 실행 결과의 시각, 프로세스 ID, 스레드 번호는 실행마다 다르다.
    HTTP 요청 한 건을 네 조각으로 나누고, 각 조각에서 화살표가 나가 그 조각을 읽는 애너테이션 묶음에 닿는 그림. 바디가 형식에 따라 두 갈래로 갈리는 것이 핵심이다. 깔끔한 기술 문서용 평면 다이어그램. 왼쪽에 세로로 긴 문서 모양의 상자 하나를 그리고 위에서 아래로 네 구역으로 나눈다. 첫째 구역 라벨 "시작 줄: POST /loans/form?from=web", 둘째 구역 라벨 "헤더: Content-Type, Cookie", 셋째 구역은 얇은 빈 띠, 넷째 구역 라벨 "메시지 바디". 오른쪽에는 둥근 사각형 다섯 개를 세로로 배치한다. 위에서부터 라벨 "@RequestMapping, @PathVariable", "@RequestParam, @ModelAttribute", "@RequestHeader, @CookieValue", "consumes, produces 조건", "@RequestBody, HttpEntity". 화살표: 시작 줄의 메서드·경로 부분에서 첫째 상자로, 시작 줄의 쿼리 스트링 부분에서 둘째 상자로, 헤더 구역에서 셋째와 넷째 상자로 각각 하나씩. 메시지 바디 구역에서는 화살표가 둘로 갈라진다. 위쪽 갈래에는 작은 글씨 "폼 형식"을 붙여 둘째 상자로, 아래쪽 갈래에는 "JSON·텍스트"를 붙여 다섯째 상자로 보낸다. 갈라지는 두 화살표는 다른 화살표보다 굵게 그린다. 배경은 흰색, 색은 파랑과 회색 두 가지 계열만 쓴다. 요청의 조각마다 읽는 수단이 다르다. 바디만은 형식에 따라 두 창구로 갈린다.

    프로젝트 생성: 실행 가능한 Jar가 품고 있는 것

    스프링 부트 프로젝트를 만들 때 고르는 항목 가운데 원리와 닿아 있는 것은 패키징(Jar 또는 War)과 웹 의존성 두 가지다. 웹 스타터를 넣으면 스프링 MVC와 함께 서블릿 컨테이너, JSON 처리 라이브러리, 로깅 구현체가 딸려 온다. Spring Boot 3.5 레퍼런스는 서블릿 애플리케이션을 위해 내장 Tomcat, Jetty, Undertow를 지원하고 내장 서버가 기본으로 8080 포트에서 HTTP 요청을 기다린다고 적는다. 01회에서 직접 띄워 본 서블릿 컨테이너가 라이브러리 형태로 애플리케이션 안에 들어와 있는 셈이다.

    Jar 패키징을 고르면 main() 메서드가 스프링 컨테이너를 만들고, 그 과정에서 톰캣을 생성해 포트를 연다. 톰캣이 애플리케이션을 품는 것이 아니라 애플리케이션이 톰캣을 품는 방향이다. War는 이미 설치된 서블릿 컨테이너에 배포하거나 JSP를 쓸 때 필요하다. 레퍼런스의 JSP 제약 항목은 실행 가능한 Jar에서는 JSP가 지원되지 않는다고 명시한다. JSP를 쓰지 않는 이 회차의 예제는 Jar로 충분하다.

    Jar로 만들 때 정적 파일의 위치도 달라진다. 스프링 부트는 클래스패스의 /static(또는 /public, /resources, /META-INF/resources) 디렉터리에서 정적 콘텐츠를 제공하고, 이 위치에서 index.html을 찾으면 그것을 환영 페이지(welcome page)로 쓴다. 그래서 src/main/resources/static/index.html을 두면 / 요청에 그 파일이 응답된다. 반대로 전통적인 src/main/webapp 디렉터리는 War 패키징에서만 동작하고 Jar를 만들 때는 대부분의 빌드 도구가 조용히 무시한다고 레퍼런스가 경고한다.

    System.out.println()은 문자열을 표준 출력으로 내보낼 뿐이다. 언제, 어느 스레드가, 어느 클래스에서 남긴 것인지 알려 주지 않고, 개발할 때만 보고 싶은 출력과 운영에서도 남겨야 하는 출력을 가를 방법이 없으며, 출력 대상을 파일로 바꾸려면 코드를 고쳐야 한다. 요청 수십 건이 서로 다른 스레드에서 동시에 처리되는 서버에서는 이 세 가지가 모두 필요하다. 로깅 라이브러리는 출력 한 건에 시각, 레벨, 스레드, 출처를 붙이고, 설정만으로 어떤 것을 어디에 내보낼지 정하게 해 준다.

    SLF4J는 창구이고 Logback이 일한다

    코드에서 부르는 것은 SLF4J(Simple Logging Facade for Java)다. SLF4J FAQ는 자신을 여러 로깅 시스템을 위한 단순한 퍼사드(facade)이며, 최종 사용자가 배포 시점에 원하는 로깅 시스템을 끼워 넣을 수 있게 한다고 소개한다. 즉 SLF4J는 Logger라는 인터페이스 묶음이고, 실제로 문자열을 만들어 콘솔이나 파일에 쓰는 구현체는 따로 있다. Spring Boot 레퍼런스에 따르면 스타터를 쓸 때의 기본 구현체는 Logback이다. 「스프링 핵심 원리 기본편」에서 본 역할과 구현의 분리가 로깅에도 그대로 적용되어 있다.

    package study.mvc;

import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.web.bind.annotation.GetMapping;
import org.springframework.web.bind.annotation.RestController;

@RestController
class LogProbeController {
    private final Logger log = LoggerFactory.getLogger(getClass());

    @GetMapping("/probe/log")
    public String probe() {
        String who = "reader";
        log.trace("trace who={}", who);
        log.debug("debug who={}", who);
        log.info("info  who={}", who);
        log.warn("warn  who={}", who);
        log.error("error who={}", who);
        return "ok";
    }
}

    LoggerFactory.getLogger(getClass())가 돌려주는 객체의 실제 클래스를 출력해 보면 ch.qos.logback.classic.Logger다. 변수의 타입은 SLF4J의 인터페이스이고 객체는 Logback의 것이다. 롬복의 @Slf4j는 log라는 이름의 SLF4J 로거 필드 선언을 컴파일 시점에 대신 만들어 주는 편의 기능이다. /probe/log를 한 번 호출하면 콘솔에 세 줄이 찍힌다.

    다섯 줄을 썼는데 세 줄만 나온 이유

    레벨에는 순서가 있다. Logback 매뉴얼의 표기로는 TRACE < DEBUG < INFO < WARN < ERROR다. 그리고 출력 여부는 한 문장의 규칙으로 정해진다. 유효 레벨이 q인 로거에 레벨 p의 로그 요청이 오면 p >= q일 때만 출력된다. 매뉴얼은 이것을 기본 선택 규칙(basic selection rule)이라고 부른다.

    남은 문제는 로거의 유효 레벨(effective level)이 어떻게 정해지는가다. 로거는 이름으로 계층을 이룬다. 어떤 로거의 이름 뒤에 점을 붙인 것이 다른 로거 이름의 접두사이면 앞의 로거가 조상이다. study.mvc는 study.mvc.LogProbeController의 조상이고, 모든 로거의 꼭대기에는 루트 로거가 있다. 유효 레벨은 자기 자신에서 시작해 루트 쪽으로 올라가며 처음 만나는 "레벨이 지정된 로거"의 레벨이다.

    root                               레벨 = INFO   (스프링 부트의 기본 설정)
 └─ study                          (지정 없음)
     └─ study.mvc                  (지정 없음)
         └─ study.mvc.LogProbeController   (지정 없음) → 위로 올라가 root의 INFO를 물려받는다

log.debug(...)  : DEBUG >= INFO ?  아니다 → 버린다
log.info(...)   : INFO  >= INFO ?  그렇다 → 출력

    Logback 자체의 루트 로거 기본 레벨은 DEBUG다. 그런데 Spring Boot 레퍼런스는 기본 로그 설정에서 ERROR, WARN, INFO 레벨 메시지가 기록된다고 적는다. 부트가 Logback을 INFO 기준으로 설정해 두었다는 뜻이고, 그래서 위 실험에서 trace와 debug 두 줄이 사라졌다. 레벨은 logging.level.로거이름=레벨 형태의 설정으로 바꾼다.

    # application.properties
logging.level.root=info
logging.level.study.mvc=debug

    둘째 줄은 study.mvc 로거에 DEBUG를 지정한다. 그 아래의 study.mvc.LogProbeController는 자기 레벨이 없으므로 루트까지 올라가기 전에 study.mvc의 DEBUG를 만나고, 네 줄(debug, info, warn, error)이 출력된다. trace로 바꾸면 다섯 줄이 모두 나온다. 패키지 이름으로 로거 이름을 짓는 관례 덕분에 "내 코드는 자세히, 라이브러리는 조용히"를 설정 두 줄로 표현할 수 있다. 같은 방법으로 logging.level.org.springframework.web=debug를 주면 스프링 MVC가 스스로 남기는 디버그 로그가 열리는데, 이 회차의 뒤에서 그것을 관찰 도구로 쓴다.

    로깅 ②: 찍히지 않는 로그의 비용 — 인자 평가와 바이트코드

    로그 문장을 쓰는 방법은 두 가지가 눈에 띈다. 문자열을 +로 이어 붙이는 방법과 {} 자리 표시자를 쓰는 방법이다. 출력되는 문자열은 같다. 차이는 그 로그가 출력되지 않을 때 드러난다. toString()이 불릴 때마다 흔적을 남기는 객체로 확인해 보자.

    class Noisy {
    @Override
    public String toString() {
        System.out.println("  Noisy.toString() 호출됨");
        return "noisy";
    }
}

    log.debug("치환: {}", new Noisy());

    DEBUG 로그는 어느 쪽도 출력되지 않았다. 그런데 (A)에서는 toString()이 호출되었고 (B)에서는 호출되지 않았다. 버려질 문자열을 만들기 위해 (A)는 일을 했다는 뜻이다. 이유는 자바의 메서드 호출 규칙에 있다. JLS §15.12.4.2는 메서드를 호출할 때 인자 식을 먼저 평가한다고 정한다. log.debug("연결: " + new Noisy())에서 인자는 문자열 연결식이고, 이 식의 값을 구하려면 Noisy를 문자열로 바꿔야 한다. debug() 안에서 레벨을 검사하는 것은 그다음 일이다. 바이트코드로 보면 순서가 그대로 보인다.

    유효 레벨을 DEBUG로 낮추고 다시 실행하면 (A)와 (B) 모두에서 toString()이 한 번씩 불리고 로그 두 줄이 찍힌다. 출력할 때의 비용은 어차피 같고, 차이는 버릴 때만 난다.

    자리 표시자가 막아 주는 것은 포매팅과 toString()까지다. log.debug("결과={}", expensiveQuery())처럼 인자 자리에 메서드 호출이 있으면 그 호출은 인자 평가 단계에서 무조건 실행된다. 이런 경우에는 if (log.isDebugEnabled())로 감싸거나, SLF4J 2.x의 log.atDebug().setMessage("결과={}").addArgument(() -> expensiveQuery()).log()처럼 Supplier를 받는 형태로 평가 자체를 뒤로 미룬다.

    운영 관점에서 한 가지를 더 적어 둔다. 스프링 MVC의 디버그 로그를 켜고 폼을 전송해 보면 POST "/loans/form-omitted", parameters={masked}처럼 파라미터가 가려진 채로 찍히고, 첫 요청 때 "request parameters and headers will be masked to prevent unsafe logging of potentially sensitive data"라는 안내가 찍힌다. 프레임워크조차 요청 값을 기본으로는 로그에 남기지 않는다. 로그는 파일로, 수집 시스템으로 흘러가 오래 남으므로, 비밀번호나 토큰 같은 값은 레벨과 무관하게 로그 문장에 넣지 않는 것이 원칙이다.

    요청 매핑 ①: 애플리케이션이 뜰 때 만들어지는 등록부

    @RequestMapping("/books")는 그 자체로는 아무 일도 하지 않는다. 애너테이션은 클래스 파일에 실린 메타데이터일 뿐이고, 누군가 리플렉션으로 읽어야 의미가 생긴다. 스프링 MVC에서 그 일을 하는 객체가 05회에서 이름을 본 RequestMappingHandlerMapping이다. 이 객체는 요청이 올 때마다 애너테이션을 뒤지지 않는다. 애플리케이션이 시작할 때 한 번 전부 읽어 등록부를 만들어 두고, 요청이 오면 등록부만 조회한다.

    2단계의 판정 기준은 버전에 따라 다르다. Spring Framework 6.0 릴리스 노트는 타입 수준의 @RequestMapping만으로는 더 이상 컨트롤러로 감지하지 않는다고 적는다. 6.0부터는 @Controller(그리고 이것을 메타 애너테이션으로 가진 @RestController)가 있어야 한다. @RestController는 @Controller에 @ResponseBody를 합친 것이어서, 메서드가 돌려준 문자열이 뷰 이름으로 해석되지 않고 응답 바디에 그대로 쓰인다. 응답 쪽의 차이는 07회에서 다루고, 이 회차의 예제는 결과를 바로 눈으로 보기 위해 모두 @RestController를 쓴다.

    @GetMapping은 @RequestMapping이다

    3단계에서 스프링이 찾는 것은 @RequestMapping 하나다. 그런데 실무 코드에는 @GetMapping, @PostMapping이 더 많이 보인다. 레퍼런스는 이들이 @RequestMapping을 메타 애너테이션으로 가진 합성 애너테이션(composed annotation)이라고 설명한다. 리플렉션으로 직접 확인할 수 있다.

    Method find = BookApiController.class.getMethod("find", String.class);   // @GetMapping("/{bookId}")가 붙은 메서드

System.out.println(find.getAnnotation(RequestMapping.class));
System.out.println(Arrays.toString(GetMapping.class.getAnnotation(RequestMapping.class).method()));

RequestMapping merged = AnnotatedElementUtils.findMergedAnnotation(find, RequestMapping.class);
System.out.println(Arrays.toString(merged.path()) + " " + Arrays.toString(merged.method()));

[GET]
[/{bookId}] [GET]

    첫 줄이 null인 것은 JDK의 리플렉션이 메서드에 직접 붙은 애너테이션만 보기 때문이다. 메서드에는 @GetMapping이 붙어 있고 @RequestMapping은 붙어 있지 않다. 둘째 줄은 @GetMapping이라는 애너테이션 타입 자체에 @RequestMapping(method = GET)이 붙어 있음을 보여 준다. 셋째 줄이 스프링이 하는 일이다. AnnotatedElementUtils.findMergedAnnotation은 애너테이션에 붙은 애너테이션까지 따라 올라가고, @GetMapping에 적은 경로 /{bookId}를 @RequestMapping의 path 속성으로 옮겨 담아 하나로 합친 결과를 돌려준다. 그래서 등록부를 만드는 코드는 @RequestMapping만 알면 된다. 레퍼런스가 지적하듯 메서드를 지정하지 않은 @RequestMapping은 모든 HTTP 메서드에 매칭되므로, 대부분의 핸들러에는 메서드가 고정된 합성 애너테이션을 쓰는 편이 맞다.

    등록부 들여다보기

    등록부는 공개 API로 꺼내 볼 수 있다. 다음 컨트롤러를 등록한 뒤 getHandlerMethods()의 내용을 출력했다.

Cannot map 'dupController' method로 시작해 어느 메서드가 {GET [/dup]}에 이미 매핑되어 있는지를 알려 준다. 같은 키를 가진 항목이 둘이면 요청이 왔을 때 고를 근거가 없으므로, 요청을 받기 전에 실패하게 만든 것이다. 다만 이 검사가 잡는 것은 "키가 완전히 같은" 경우뿐이다. 그렇지 않은 모호함은 요청 시점에 드러나는데, 바로 다음 절에서 본다.

    요청 매핑 ②: 요청이 왔을 때 — 후보 추리기, 조건 검사, 최선 고르기

    요청이 들어오면 DispatcherServlet은 핸들러 매핑에게 이 요청을 처리할 핸들러를 달라고 한다. RequestMappingHandlerMapping이 하는 일은 시작 시점에 만든 등록부에서 항목 하나를 고르는 것이다. 등록부는 조회 방식이 다른 두 개의 맵으로 되어 있다.

    MappingRegistry (Spring Framework 6.2.x 소스의 필드 이름)
 ├─ pathLookup : 경로 문자열 → [RequestMappingInfo ...]      변수·와일드카드가 없는 경로만 들어간다
 │      "/books"             → [ {GET [/books]}, {POST [/books]} ]
 │      "/routes/books/new"  → [ {GET [/routes/books/new]} ]
 │
 ├─ registry   : RequestMappingInfo → 호출할 메서드           모든 항목이 들어간다
 │      {GET [/books/{bookId}]}         → BookApiController#find
 │      {GET [/routes/books/{bookId}]}  → RouteController#book
 │      ...
 │
 └─ readWriteLock : 등록할 때는 쓰기 락, 조회할 때는 읽기 락

    조회 전체는 읽기 락을 잡은 채로 이루어진다. 읽기 락은 여러 스레드가 동시에 잡을 수 있으므로 톰캣 작업 스레드들은 서로를 기다리지 않고 등록부를 읽는다. 등록부를 바꾸는 쓰기는 시작 시점에 몰려 있다. 01회에서 본 "하나뿐인 객체를 여러 스레드가 함께 쓴다"는 구조가 여기에도 있고, 읽기 위주의 공유 자료를 다루는 정석적인 방법이 쓰였다.

    리터럴 경로가 변수 경로를 이기는 두 가지 이유

    GET /routes/books/new는 /routes/books/new에도, /routes/books/{bookId}에도 들어맞는다. 응답은 new-book-form이었다. 위 순서로 따라가 보면 이 경우는 비교자까지 갈 필요도 없다. 1단계에서 pathLookup이 리터럴 경로 항목을 찾았고 2단계의 조건 검사도 통과했으므로 후보 목록이 비어 있지 않다. 3단계의 전체 훑기는 실행되지 않고, {bookId} 패턴은 비교 대상에 오르지도 않는다. 반면 GET /routes/books/B-17은 pathLookup에 그런 키가 없으므로 3단계로 넘어가 패턴 매칭으로 book 메서드에 닿는다.

    패턴이 있는 항목끼리 겹칠 때는 4단계의 비교자가 일한다. 레퍼런스가 정리한 기준은 이렇다. URI 변수 하나와 단일 와일드카드(*) 하나를 각각 1점, 이중 와일드카드(**)를 2점으로 세어 점수가 낮은 패턴이 더 구체적이다. 점수가 같으면 더 긴 패턴이, 그것도 같으면 와일드카드보다 URI 변수가 많은 패턴이 선택된다. "더 적게 열려 있는 패턴이 이긴다"로 기억하면 된다. Spring Framework 6.0부터 스프링 MVC는 경로를 미리 파싱해 두는 PathPattern 방식을 기본으로 쓰고, {name}, {name:정규식}, {*path}, ?, *, ** 같은 문법이 이 패턴 언어에 속한다.

    비교자로도 가려지지 않는 경우가 요청 시점의 모호함이다. 두 메서드에 각각 @GetMapping("/amb/{a}")와 @GetMapping("/amb/{b}")를 붙이면 애플리케이션은 정상적으로 뜬다. 패턴 문자열이 다르므로 등록부의 키가 서로 다르고, 시작 시점의 중복 검사에 걸리지 않기 때문이다. 그러나 GET /amb/1이 오면 둘 다 들어맞고 구체성도 같다. 실험에서는 IllegalStateException: Ambiguous handler methods mapped for '/amb/1'이 발생해 500이 응답되었다. 시작이 성공했다고 해서 매핑에 모순이 없다는 뜻은 아니다.

    후보가 없을 때: 404만 있는 것이 아니다

    HEAD와 OPTIONS는 누가 처리했나

    HEAD /routes/get-only는 200과 Content-Length: 8, 그리고 빈 바디로 응답되었다. HEAD를 매핑한 적이 없는데도 그렇다. 레퍼런스에 따르면 GET 매핑은 HEAD를 투명하게 지원하고, 서블릿 쪽의 응답 래퍼가 실제로 쓰지 않으면서 바이트 수만 세어 Content-Length를 채운다. OPTIONS /routes/get-only는 Allow: GET,HEAD,OPTIONS로, 메서드를 지정하지 않은 /routes/any에 대한 OPTIONS는 Allow: GET,HEAD,POST,PUT,PATCH,DELETE,OPTIONS로 응답되었다. 경로가 맞는 매핑들이 선언한 메서드 목록으로 스프링이 응답을 만든 것이다. 405의 Allow와 OPTIONS의 Allow가 같은 재료, 곧 등록부의 메서드 조건에서 나온다는 것을 알 수 있다.

    요청 하나가 등록부의 두 맵을 차례로 거치며 핸들러가 정해지거나 404·405·415·406·400으로 갈라지는 흐름. 직접 경로 조회에서 찾으면 패턴 비교를 건너뛴다는 점이 보여야 한다. 위에서 아래로 흐르는 순서도. 맨 위 둥근 상자 라벨 "요청: GET /routes/books/new". 아래 마름모 라벨 "pathLookup에 경로가 있는가". 마름모의 "예" 화살표는 사각형 "조건 검사: 메서드 · params · headers · consumes · produces"로 간다. 마름모의 "아니오" 화살표와, 조건 검사에서 나온 "남은 후보 없음" 화살표는 둘 다 사각형 "registry 전체 훑기(패턴 매칭 포함)"로 모인다. 조건 검사와 전체 훑기에서 각각 "후보 있음" 화살표가 나와 사각형 "비교자로 정렬, 가장 구체적인 것 선택"으로 모이고, 여기서 초록색 둥근 상자 "핸들러 메서드 결정"으로 간다. 정렬 상자 옆으로 빨간 작은 상자 "동률이면 예외(500)"를 점선 화살표로 붙인다. 전체 훑기에서 "후보 없음" 화살표는 사각형 "경로만 맞는 항목이 있었나"로 가고, 여기서 오른쪽으로 주황색 상자 네 개 "405", "415", "406", "400"이 나란히 달리며, 아래쪽으로 회색 상자 "null → 404"가 달린다. 직접 경로 조회에서 바로 조건 검사로 가는 화살표는 다른 것보다 굵게 그려 지름길임을 나타낸다. 배경 흰색, 글씨는 진한 회색. 요청 시점의 핸들러 선택. 리터럴 경로는 해시 조회 한 번으로 후보가 되고, 못 고른 이유에 따라 상태 코드가 갈린다.

    경로 변수와 매개변수 이름: -parameters가 필요한 이유

    /routes/books/{bookId}의 중괄호 부분이 경로 변수(path variable)다. 패턴 매칭에 성공하면 스프링은 중괄호 자리에 들어맞은 문자열을 변수 이름과 짝지어 맵으로 만들고 요청 속성(request attribute)에 넣어 둔다. @PathVariable("bookId")는 나중에 인자를 만들 때 그 맵에서 값을 꺼내라는 표지다. 실험 결과는 다음과 같다.

    이름을 생략하면 스프링은 어디서 이름을 얻는가

    shelfBook 메서드는 @PathVariable String shelfId처럼 변수 이름을 적지 않았다. 스프링은 매개변수의 이름이 shelfId라는 사실을 실행 중에 알아내야 한다. 그런데 자바 컴파일러는 기본적으로 매개변수 이름을 실행 시점에 읽을 수 있는 형태로 남기지 않는다. 직접 확인해 보자.

    import java.lang.reflect.Method;
import java.lang.reflect.Parameter;

public class Names {
    public String find(String username, int age) { return username + age; }

    public static void main(String[] args) throws Exception {
        Method m = Names.class.getMethod("find", String.class, int.class);
        for (Parameter p : m.getParameters()) {
            System.out.println(p.getType().getSimpleName() + " " + p.getName() + " isNamePresent=" + p.isNamePresent());
        }
    }
}

    바이트코드는 지역 변수를 이름이 아니라 슬롯 번호로 다룬다(aload_1, iload_2). 실행에는 이름이 필요 없으므로 기본 컴파일 결과에는 이름이 없고, 리플렉션은 arg0, arg1이라는 지어낸 이름을 돌려준다. -g는 디버거를 위해 LocalVariableTable을 남기지만 리플렉션 API는 이 표를 읽지 않는다. -parameters를 줘야 리플렉션이 읽는 MethodParameters 속성(JVMS §4.7.24)이 클래스 파일에 기록된다.

    예전의 스프링은 -g로 남은 LocalVariableTable을 바이트코드 파싱으로 직접 읽어 이름을 알아냈다. Spring Framework 6.1 릴리스 노트는 이 일을 하던 LocalVariableTableParameterNameDiscoverer가 6.1에서 제거되었고, 매개변수 이름에 의존하는 기능을 쓰려면 -parameters 플래그로 컴파일해야 한다고 적는다(6.0에서는 폐기 예정 상태로 경고 로그를 남겼다). 플래그 없이 컴파일한 컨트롤러로 실험하면 애플리케이션은 정상적으로 뜨고, 해당 핸들러가 호출되는 순간에야 500이 난다.

    java.lang.IllegalArgumentException: Name for argument of type [java.lang.String] not specified, and parameter name information not available via reflection. Ensure that the compiler uses the '-parameters' flag.

    같은 실험에서 @RequestParam String username과 애너테이션을 생략한 String username도 똑같은 예외를 냈다. 이름을 애너테이션에 직접 적은 @PathVariable("bookId") 형태는 영향을 받지 않는다. 스프링 부트의 Gradle 플러그인은 모든 JavaCompile 작업에 -parameters를 붙여 주므로 Gradle로 빌드하면 문제를 만날 일이 없다. IDE가 Gradle에 위임하지 않고 자체 컴파일러로 빌드하도록 설정되어 있으면 플래그가 빠질 수 있는데, 릴리스 노트가 IDE별 설정 방법을 따로 안내하는 것도 그 때문이다. "터미널에서는 되는데 IDE에서 실행하면 500이 난다"는 증상을 만나면 이 지점을 의심한다.

    요청 매핑 - API 예시: URL은 자원을, 메서드는 행위를

    앞에서 등록부를 들여다볼 때 쓴 BookApiController는 HTTP API에서 흔한 설계를 따른 것이다. URL은 자원(도서 목록, 도서 한 권)을 가리키고, 그 자원에 무엇을 할지는 HTTP 메서드가 말한다. 「HTTP 웹 기본 지식」 권에서 본 메서드의 의미를 그대로 쓰는 방식이다.

    요청의미등록부의 항목응답
    GET /books목록 조회{GET [/books]}list
    POST /books등록{POST [/books]}register
    GET /books/7한 건 조회{GET [/books/{bookId}]}find 7
    PATCH /books/7부분 수정{PATCH [/books/{bookId}]}update 7
    DELETE /books/7삭제{DELETE [/books/{bookId}]}remove 7
    PUT /books/7(매핑 없음)경로만 맞는 항목 셋405, Allow에 GET·PATCH·DELETE
    DELETE /books(매핑 없음)경로만 맞는 항목 둘405, Allow에 GET·POST

    이 설계가 스프링 MVC와 잘 맞는 이유는 등록부의 키 구조에 있다. HTTP 메서드가 경로와 별개의 조건 칸이므로, 같은 URL에 메서드별 핸들러를 얼마든지 나눠 붙일 수 있다. URL에 /books/7/delete처럼 동사를 넣지 않아도 된다. 마지막 두 줄도 같은 구조에서 나온다. "그 자원은 있지만 그 메서드는 지원하지 않는다"는 405의 의미와 Allow 헤더의 내용을 스프링은 등록부에서 계산해 낸다(Allow 안의 메서드 나열 순서는 실행마다 달랐다). 디버그 로그를 켜면 Mapped to study.mvc.BookApiController#find(String)처럼 매핑 결과가 한 줄로 남으므로, 의도한 메서드가 선택되었는지 바로 확인할 수 있다.

    클래스 수준의 @RequestMapping("/books")는 공통 접두 경로를 한 곳에 모으는 역할을 한다. 대부분의 속성은 클래스 수준과 메서드 수준의 값이 합쳐지지만, 레퍼런스는 consumes와 produces만은 메서드 수준 선언이 클래스 수준 선언을 확장하지 않고 덮어쓴다고 따로 밝힌다.

    한 줄씩 읽어 보자. HttpServletRequest 자리에 들어온 객체는 톰캣의 RequestFacade다. 스프링이 만든 것이 아니라 서블릿 컨테이너가 만든 요청 객체가 그대로 전달된 것이므로, 02회에서 다룬 서블릿 API가 스프링 컨트롤러 안에서도 전부 유효하다. HttpMethod는 요청 메서드를 나타내는 스프링의 타입이고, Locale은 레퍼런스의 표현으로 "가장 구체적인 LocaleResolver가 결정한" 현재 요청의 로캘이다. 이 요청에서는 Accept-Language의 첫 항목 ko-KR이 반영되었다.

    @RequestHeader에 이름 없이 MultiValueMap을 받으면 모든 헤더가 담긴다. MultiValueMap은 키 하나에 값 여러 개를 담는 맵이다. HTTP에서는 같은 이름의 헤더가 여러 번 올 수 있으므로 일반 Map으로는 값이 유실된다. X-Tag=[red, blue]가 그 예다. 같은 헤더를 String으로 받으면 red,blue처럼 쉼표로 이어 붙인 값이, List으로 받으면 원소 두 개인 리스트가 들어온다. @RequestHeader("host")가 Host 헤더를 찾은 것은 HTTP 헤더 이름이 대소문자를 구분하지 않기 때문이다.

    @CookieValue("visit")는 Cookie: visit=3; theme=dark라는 헤더 한 줄을 이름-값 쌍으로 쪼갠 결과에서 visit의 값만 꺼낸다. 쿠키는 결국 Cookie 헤더이지만, 파싱을 대신해 주는 전용 표지가 있는 것이다. 헤더와 쿠키를 모두 빼고 다시 요청하면 tagText=null, tagList=null, visit=null이 나온다. 세 매개변수에 required = false를 주었기 때문이고, @RequestHeader와 @CookieValue의 required 기본값은 true여서 이 속성을 빼면 값이 없을 때 예외가 발생한다. 이때도 locale은 여전히 ko_KR이었는데, 서블릿 API 문서는 Accept-Language 헤더가 없으면 getLocale()이 서버의 기본 로캘을 돌려준다고 적는다. 실험 장비의 기본 로캘이 한국어였다.

    이 값들을 만들어 넣는 주체는 인자 리졸버(HandlerMethodArgumentResolver)라는 객체들이다. 매개변수 하나마다 "내가 처리할 수 있다"고 답하는 리졸버가 값을 만든다. 이 구조와 목록은 07회에서 RequestMappingHandlerAdapter를 열어 볼 때 다루고, 이 회차에서는 리졸버 각각이 어떤 규칙으로 값을 만드는지에 집중한다.

Jakarta Servlet 6.0 명세 §3.1은 쿼리 스트링의 데이터와 POST 바디의 데이터가 요청 파라미터 집합으로 합쳐지며, 쿼리 스트링의 데이터가 바디의 데이터보다 앞에 놓인다고 정한다. 그래서 request.getParameter() 하나로 양쪽을 모두 읽을 수 있다. 단, 바디가 파라미터로 취급되려면 조건이 있다. §3.1.1이 나열하는 조건은 네 가지다.

    1. HTTP 또는 HTTPS 요청이다.
    2. HTTP 메서드가 POST다.
    3. 콘텐츠 타입이 application/x-www-form-urlencoded다.
    4. 서블릿이 요청 객체에 대해 getParameter 계열 메서드를 처음으로 호출했다.

    넷째 조건이 핵심이다. 파라미터는 요청이 도착하자마자 만들어지는 것이 아니라, 누군가 처음 물어볼 때 만들어진다. 명세는 이어서 조건이 충족되면 폼 데이터는 더 이상 요청 객체의 입력 스트림에서 직접 읽을 수 없고, 충족되지 않으면 입력 스트림을 통해 읽을 수 있어야 한다고 적는다. 직접 확인해 보자.

    @RestController

        String borrower = request.getParameter("borrower");

    이렇게 되는 근본 이유는 바디가 스트림이기 때문이다. 01회에서 본 것처럼 요청은 소켓에서 흘러 들어오는 바이트이고, 컨테이너는 헤더까지만 읽어 요청 객체를 만든 뒤 서블릿을 호출한다. 바디는 누군가 읽을 때 비로소 소켓(과 그 앞의 버퍼)에서 꺼내지며, 한 번 꺼낸 바이트를 컨테이너가 따로 보관해 두지 않는다. 수십 메가바이트짜리 업로드를 매번 메모리에 복사해 둘 수는 없으므로 합리적인 설계다. 그 대가로 "바디는 한 번만 읽을 수 있다"는 제약이 생기고, 파라미터 조회와 스트림 읽기는 같은 바이트를 두고 경쟁하게 된다.

    5번에서 한글이 올바르게 풀린 것도 당연한 일은 아니다. 명세 §3.13은 폼 형식 바디에 문자 집합이 지정되지 않았을 때의 기본 인코딩을 UTF-8로 정하고 있지 않다. Spring Boot 3.5의 자동 구성은 CharacterEncodingFilter를 등록해, 파라미터가 처음 읽히기 전에 요청의 문자 인코딩을 UTF-8로 지정한다(server.servlet.encoding.* 설정, 기본값 UTF-8이고 요청 쪽은 강제 적용). 파라미터 파싱이 지연된다는 사실이 여기서도 쓰인다. 필터가 인코딩을 정할 시간이 있는 것은 그때까지 아무도 파라미터를 읽지 않았기 때문이다.

    서블릿 명세가 폼 바디를 파라미터로 만들어 주는 것은 POST뿐이다. PUT·PATCH·DELETE로 폼 형식 바디를 보내는 클라이언트를 위해 스프링은 FormContentFilter를 제공한다. 이 필터는 바디를 읽어 요청 객체를 감싼 뒤 getParameter 계열 메서드로 값을 읽을 수 있게 해 준다. 스프링 부트는 이 필터를 기본으로 등록하며, 실험에서도 필터 체인에 들어 있는 것을 스택 트레이스로 확인했다.
    하나뿐인 바디 스트림을 두 소비자가 두고 경쟁하는 모습. 먼저 읽은 쪽이 바이트를 가져가고 다른 쪽은 빈손이 된다. 쿼리 스트링은 스트림 바깥에 있어 항상 읽힌다. 좌우 두 칸으로 나뉜 비교 그림. 두 칸 모두 위쪽에 같은 모양의 긴 파이프를 그리고 파이프 안에 바이트 조각을 나타내는 작은 네모들을 넣는다. 파이프 라벨은 "바디 스트림: borrower=kim&days=7". 파이프 위에는 따로 떨어진 작은 꼬리표 "쿼리 스트링: from=query"를 둔다. 왼쪽 칸 제목 "getParameter()를 먼저 호출". 파이프에서 굵은 화살표가 아래의 상자 "파라미터 맵: from, borrower, days"로 내려가고, 그 옆의 상자 "getInputStream()"에는 빈 파이프 아이콘과 라벨 "읽을 것이 없다"를 붙인다. 오른쪽 칸 제목 "getInputStream()을 먼저 호출". 파이프에서 굵은 화살표가 아래의 상자 "애플리케이션이 읽은 바이트"로 내려가고, 그 옆의 상자 "파라미터 맵: from"에는 라벨 "바디의 값은 없다"를 붙인다. 두 칸 모두 쿼리 스트링 꼬리표에서 파라미터 맵으로 가는 얇은 점선 화살표를 그려 쿼리 스트링은 항상 읽힌다는 것을 나타낸다. 색은 파랑(읽힌 쪽)과 회색(비어 있는 쪽) 두 가지. 바디는 한 번만 읽히는 스트림이다. 파라미터 조회와 입력 스트림 가운데 먼저 읽은 쪽이 바이트를 가져간다.

    @RequestParam: 문자열 하나가 인자 하나가 되는 절차

    @RequestParam은 방금 본 요청 파라미터 집합에서 값 하나를 꺼내 매개변수에 넣으라는 표지다. 레퍼런스의 표현으로는 서블릿 요청 파라미터, 곧 쿼리 파라미터나 폼 데이터를 메서드 인자에 바인딩한다. 그래서 GET 쿼리 스트링이든 POST 폼이든 핸들러 코드는 같다. 내부 절차는 다음과 같다(Spring Framework 6.2.x의 AbstractNamedValueMethodArgumentResolver와 RequestParamMethodArgumentResolver).

    // ParamController 안
@RequestMapping("/params/named")
public String named(@RequestParam("borrower") String name, @RequestParam("days") int period) {
    return name + "/" + period;
}

@RequestMapping("/params/omitted")
public String omitted(String borrower, int days) {
    return borrower + "/" + days;
}

@RequestMapping("/params/optional")
public String optional(@RequestParam String borrower,
                       @RequestParam(required = false) Integer days) {
    return "[" + borrower + "]/" + days;
}

@RequestMapping("/params/default")
public String withDefault(@RequestParam(defaultValue = "guest") String borrower,
                          @RequestParam(defaultValue = "14") int days) {
    return borrower + "/" + days;
}

@RequestMapping("/params/map")
public String map(@RequestParam Map one,
                  @RequestParam MultiValueMap all) {
    return one + " / " + all;
}

    눈여겨볼 것은 세 가지다. 첫째, required = true가 보장하는 것은 "파라미터 이름이 요청에 있다"까지다. ?borrower=처럼 값이 빈 문자열이어도 통과한다. 값이 비어 있지 않아야 한다는 요구는 검증(validation)의 몫이고 「스프링 MVC 2편」에서 다룬다. 둘째, 기본형 매개변수와 null의 충돌이다. 값이 없어도 되는 파라미터를 int로 선언하면 넣을 값이 없어서 IllegalStateException이 발생하고, 이것은 클라이언트의 잘못을 뜻하는 400이 아니라 서버 코드의 잘못을 뜻하는 500으로 응답된다. 예외 메시지가 직접 해법을 말해 준다. "Consider declaring it as object wrapper for the corresponding primitive type." 곧 Integer로 선언하거나 defaultValue를 주라는 것이다. 셋째, defaultValue를 주면 값이 없는 경우가 사라지므로 required는 의미가 없어진다.

    애너테이션을 생략한 omitted(String borrower, int days)가 동작하는 것은 스프링의 마지막 규칙 덕분이다. 레퍼런스의 인자 표 맨 끝줄은, 앞의 어떤 항목에도 해당하지 않는 인자가 단순 타입(BeanUtils#isSimpleProperty가 판정한다)이면 @RequestParam으로, 그 밖에는 @ModelAttribute로 처리한다고 정한다. 단순 타입은 기본형과 래퍼, String, Number, Enum, 날짜·시간 타입 같은 값 타입과 그 배열을 가리킨다. 생략형은 짧지만 대가가 있다. 이름을 매개변수 이름에서 얻으므로 -parameters에 의존하고, 위 표에서 본 것처럼 required가 꺼진 상태로 동작하며, 코드를 읽는 사람이 값의 출처를 한눈에 알기 어렵다.

    @ModelAttribute: 객체를 만들고 프로퍼티를 채운다

    파라미터가 두세 개일 때는 @RequestParam으로 충분하다. 열 개가 되면 매개변수 목록이 감당하기 어려워지고, 받은 값을 다시 객체에 옮겨 담는 코드가 핸들러마다 반복된다. 서블릿만으로 쓴다면 이런 모양이다.

    LoanRequest loan = new LoanRequest();
loan.setBorrower(request.getParameter("borrower"));
loan.setDays(Integer.parseInt(request.getParameter("days")));

    @ModelAttribute는 이 세 줄을 스프링이 대신 하게 한다. 무슨 일이 어떤 순서로 일어나는지 보기 위해, 생성자와 세터가 호출될 때마다 흔적을 남기는 클래스를 준비했다.

    package study.mvc;

    스프링은 먼저 기본 생성자로 빈 객체를 만들었다. 그다음 요청 파라미터의 이름마다 같은 이름의 프로퍼티(property)를 찾아 세터를 호출했다. 여기서 프로퍼티는 필드가 아니다. 자바빈 규약에서 days라는 프로퍼티는 getDays()/setDays()라는 메서드 쌍으로 정의되고, 필드 이름이 무엇인지, 필드가 있기는 한지와는 무관하다. 스프링이 private 필드에 직접 값을 써넣은 것이 아니라 공개된 세터를 호출했다는 것을 흔적이 보여 준다. setDays(7)에 문자열이 아니라 int 7이 전달된 것에서, 세터의 매개변수 타입에 맞춘 변환도 이 과정에 포함된다는 것을 알 수 있다(세터들이 호출되는 순서는 약속된 것이 아니다).

    이름의 출처가 세터의 메서드 이름이므로, 이 방식은 -parameters 플래그와 무관하게 동작한다. 메서드 이름은 언제나 클래스 파일에 있기 때문이다. 실제로 플래그 없이 컴파일한 컨트롤러에서 @RequestParam String username은 실패했지만 객체로 받는 핸들러는 정상 동작했다. 경계 조건을 몇 가지 더 보자.

    생성자로 바인딩하기

    레퍼런스는 인스턴스를 얻는 경로로 기본 생성자 외에 "주 생성자(primary constructor)"도 든다. 생성자의 인자 이름을 요청 파라미터 이름과 맞춰 값을 넣는 방식이고, 인자 이름은 바이트코드에 남은 매개변수 이름에서 얻는다. 세터가 없는 레코드로 확인했다.

    formOmitted(LoanRequest loan)처럼 @ModelAttribute도 생략할 수 있다. 앞 절에서 본 마지막 규칙의 나머지 절반이다.

    이름에 "Model"이 들어 있는 이유도 적어 둔다. @ModelAttribute로 만들어진 객체는 인자로 전달될 뿐 아니라 모델에도 자동으로 담긴다. 뷰 템플릿이 그 객체를 꺼내 화면을 그릴 수 있게 하기 위한 것이고, 08회에서 폼 화면을 만들 때 이 성질을 쓴다.

    요청 파라미터 두 개가 객체 생성과 세터 호출 두 번으로 바뀌는 순서. 필드에 직접 쓰지 않고 세터를 거친다는 점, 문자열이 세터의 타입으로 변환된다는 점이 보여야 한다. 세로 생명선 네 개가 있는 시퀀스 다이어그램. 왼쪽부터 생명선 라벨 "요청 파라미터", "스프링(데이터 바인더)", "LoanRequest 객체", "컨트롤러 메서드". 맨 위에 "요청 파라미터"에서 "스프링(데이터 바인더)"로 가는 화살표, 라벨 "borrower=kim, days=7 (모두 문자열)". 다음으로 "스프링(데이터 바인더)"에서 "LoanRequest 객체"로 가는 화살표 세 개를 차례로 그린다. 첫째 라벨 "new LoanRequest()", 둘째 라벨 "setBorrower(kim)", 셋째 라벨 "setDays(7)". 셋째 화살표 옆에는 작은 말풍선 "문자열 7 → int 7 변환"을 붙인다. LoanRequest 객체 생명선 옆에는 상태 상자를 두 번 그린다. 생성 직후 상자에는 "borrower=null, days=0", 세터 호출 뒤 상자에는 "borrower=kim, days=7". 마지막으로 "스프링(데이터 바인더)"에서 "컨트롤러 메서드"로 가는 화살표, 라벨 "form(loan) 호출". 배경 흰색, 화살표는 진한 파랑, 상태 상자는 연한 노랑. @ModelAttribute의 바인딩. 빈 객체를 만든 뒤 파라미터 이름과 같은 프로퍼티의 세터를 호출한다.

    HTTP 요청 메시지 - 단순 텍스트: 바이트 스트림을 문자열로

    지금까지의 수단은 모두 요청 파라미터를 읽었다. 바디가 폼 형식이 아니면 요청 파라미터는 만들어지지 않는다는 것을 앞의 4번 실험에서 보았다. JSON이나 일반 텍스트처럼 바디에 직접 실린 데이터는 @RequestParam으로도 @ModelAttribute로도 읽을 수 없고, 바디 스트림을 읽어야 한다. 읽는 방법을 가장 낮은 층에서 시작해 한 단계씩 올려 보자.

    @RestController
class BodyController {

    @PostMapping("/echo/servlet")
    public void servlet(HttpServletRequest request, HttpServletResponse response) throws IOException {
        byte[] raw = request.getInputStream().readAllBytes();
        String asUtf8 = new String(raw, StandardCharsets.UTF_8);
        String asLatin1 = new String(raw, StandardCharsets.ISO_8859_1);
        response.setContentType("text/plain");
        response.setCharacterEncoding("UTF-8");
        response.getWriter().write(raw.length + "바이트, UTF-8로 읽으면 " + asUtf8.length() + "글자 [" + asUtf8
                + "], ISO-8859-1로 읽으면 " + asLatin1.length() + "글자");
    }

    @PostMapping("/echo/stream")
    public void stream(InputStream in, Writer out) throws IOException {
        String text = StreamUtils.copyToString(in, StandardCharsets.UTF_8);
        out.write("stream: " + text);
    }

    @PostMapping("/echo/entity")
    public HttpEntity entity(HttpEntity request) {
        return new HttpEntity<>("entity: " + request.getBody()
                + " / Content-Type=" + request.getHeaders().getContentType());
    }

    @PostMapping("/echo/body")
    public String body(@RequestBody String text) {
        return "body: " + text;
    }

    @PostMapping("/echo/twice")
    public String twice(@RequestBody String text, HttpServletRequest request) throws IOException {
        int again = request.getInputStream().readAllBytes().length;
        return "처음 읽은 값=" + text + ", 다시 읽은 바이트 수=" + again;
    }
    // ...
}

    1단계: 바이트를 문자로 바꾸려면 문자 집합이 필요하다

    첫 줄이 이 절의 출발점이다. 네트워크로 온 것은 문자가 아니라 바이트 11개다. 이것을 UTF-8 규칙으로 읽으면 한글 한 글자가 3바이트씩이어서 다섯 글자(대, 출, 공백, 7, 일)가 되고, 1바이트를 한 글자로 보는 ISO-8859-1 규칙으로 읽으면 뜻 없는 열한 글자가 된다. 바이트 자체에는 자신이 어떤 규칙으로 인코딩되었는지 적혀 있지 않다. 그래서 읽는 쪽이 문자 집합(charset)을 정해야 하고, 틀리게 정하면 예외 없이 깨진 문자열이 만들어진다. 직접 스트림을 읽는 코드에서 StandardCharsets.UTF_8을 명시하는 이유다.

    2~4단계: 같은 일을 점점 덜 쓰고 한다

    stream(InputStream in, Writer out)은 요청 객체 전체가 아니라 필요한 것만 받는 형태다. 레퍼런스는 이 두 타입을 "서블릿 API가 노출하는 날것의 요청 바디와 응답 바디에 접근하기 위한 것"으로 설명한다. 스트림을 문자열로 바꾸는 일은 여전히 코드가 한다.

    HttpEntity부터는 변환을 스프링이 한다. HttpEntity는 헤더와 바디를 묶은 객체이고, 타입 인자 String이 "바디를 문자열로 달라"는 요청이다. 스프링은 HTTP 메시지 컨버터(HttpMessageConverter) 가운데 문자열을 다루는 것으로 바디를 읽는다. 반환 타입으로 쓰면 반대 방향, 곧 객체를 응답 바디로 쓰는 일도 맡는다. RequestEntity와 ResponseEntity는 여기에 각각 요청 메서드·URL과 응답 상태 코드를 더한 하위 타입이다.

    @RequestBody String text는 바디만 필요할 때의 가장 짧은 형태다. 헤더가 필요하면 @RequestHeader를 따로 받으면 된다. 메시지 컨버터가 무엇이고 어떤 기준으로 선택되는지는 07회에서 다루므로, 여기서는 "바디의 바이트를 매개변수 타입의 객체로 바꾸는 부품"이라고만 알아 둔다.

    스프링은 문자 집합을 어떻게 정했나

    3~4단계에서는 코드가 문자 집합을 정하지 않았는데도 한글이 깨지지 않았다. 누군가 대신 정했다는 뜻이다. 문자열 컨버터(StringHttpMessageConverter)의 소스를 보면 순서가 있다.

    1. Content-Type 헤더에 charset 매개변수가 있으면 그것을 쓴다.
    2. 없으면 컨버터의 기본 문자 집합을 쓴다(단, 미디어 타입이 application/json이나 application/*+json과 호환되면 UTF-8을 쓴다). 프레임워크의 기본값은 ISO-8859-1이다(Javadoc: 기본 생성자는 "ISO-8859-1"을 기본 문자 집합으로 쓴다).

    이대로라면 Content-Type: text/plain만 보낸 한글 요청은 깨져야 한다. 깨지지 않은 이유는 스프링 부트가 두 군데를 손봤기 때문이다. 하나는 앞에서 본 CharacterEncodingFilter다. 이 필터가 요청의 문자 인코딩을 UTF-8로 지정해 두면, 스프링은 요청 헤더를 읽을 때 Content-Type에 charset이 없는 경우 요청의 문자 인코딩을 charset으로 덧붙인다. /echo/entity의 응답에서 클라이언트가 보낸 text/plain이 text/plain;charset=UTF-8로 보인 것이 그 흔적이다. 다른 하나는 컨버터의 기본값이다. 부트는 문자열 컨버터를 같은 설정의 문자 집합(기본 UTF-8)으로 만들어 등록하고, 레퍼런스에도 문자열이 기본적으로 UTF-8로 인코딩된다고 적혀 있다. Content-Type 헤더가 아예 없는 요청에서도 한글이 살아남은 것은 이 둘째 장치 덕분이다.

    응답 쪽은 사정이 다르다. 부트의 필터 설정에서 강제 적용의 기본값은 요청에만 해당한다. 그래서 /echo/stream처럼 Writer에 직접 쓰는 핸들러가 한글을 내보내면, 응답의 문자 인코딩을 따로 지정하지 않는 한 깨진다. 실험에서 응답의 인코딩을 지정하지 않고 Writer에 한글을 썼을 때 클라이언트는 ??를 받았다. /echo/servlet이 response.setCharacterEncoding("UTF-8")을 호출하는 이유다. 문자 집합은 읽을 때도 쓸 때도 누군가는 정해야 하고, 편의 기능을 쓸수록 그 "누군가"가 코드에서 보이지 않게 될 뿐이다.

    바디는 한 번만 읽힌다, 그리고 없으면 400이다

    /echo/twice는 @RequestBody로 바디를 받은 뒤 요청 객체에서 입력 스트림을 다시 읽었고, 0바이트를 얻었다. 요청 파라미터 절에서 본 스트림의 성질이 그대로 나타난 것이다. 스프링이 인자를 만들면서 이미 스트림을 끝까지 읽었다. 필터나 인터셉터에서 로깅을 위해 바디를 먼저 읽어 버리면 컨트롤러의 @RequestBody가 빈 바디를 만나게 되는 것도 같은 원리다.

    빈 바디로 /echo/body를 호출하면 400이 응답되고 로그에 HttpMessageNotReadableException: Required request body is missing이 남는다. @RequestBody도 required 속성을 가지며 기본값이 true이기 때문이다.

    이 장의 핵심

    요청 파라미터를 읽는 수단(@RequestParam, @ModelAttribute)과 메시지 바디를 읽는 수단(@RequestBody, HttpEntity)은 이름이 비슷할 뿐 서로 다른 장치다. 앞의 것은 서블릿 컨테이너가 쿼리 스트링과 폼 바디를 파싱해 만든 이름-값 표를 조회하고, 뒤의 것은 바디 스트림을 통째로 읽어 메시지 컨버터로 변환한다. 어느 쪽을 써야 하는지는 데이터가 요청의 어디에 어떤 형식으로 실려 있는가, 곧 Content-Type이 결정한다.

    HTTP 요청 메시지 - JSON: Content-Type이 변환기를 고른다

    HTTP API에서 가장 흔한 바디 형식은 JSON이다. 텍스트 바디를 읽을 줄 알면 JSON은 한 걸음이다. 읽어 낸 문자열을 객체로 바꾸는 단계가 하나 더 붙는다. 이 변환을 하는 라이브러리가 Jackson이고 중심 클래스가 ObjectMapper다.

    // BodyController 안
// Spring Boot 3.x(Jackson 2)에서는 com.fasterxml.jackson.databind.ObjectMapper,
// 실험에 쓴 Spring Boot 4.x(Jackson 3)에서는 tools.jackson.databind.ObjectMapper를 import한다.
private final ObjectMapper objectMapper = new ObjectMapper();

@PostMapping("/loans/json-manual")
public String jsonManual(HttpServletRequest request) throws IOException {
    String text = StreamUtils.copyToString(request.getInputStream(), StandardCharsets.UTF_8);
    LoanRequest loan = objectMapper.readValue(text, LoanRequest.class);
    return "manual: " + loan;
}

@PostMapping("/loans/json")
public String json(@RequestBody LoanRequest loan) {
    return "json: " + loan;
}

@PostMapping("/loans/json-entity")
public String jsonEntity(HttpEntity request) {
    return "entity: " + request.getBody();
}

@PostMapping("/loans/json-omitted")
public String jsonOmitted(LoanRequest loan) {
    return "omitted: " + loan;
}

    jsonManual이 원리를 그대로 드러낸 형태다. 바이트를 문자열로, 문자열을 객체로 바꾼다. json은 같은 일을 @RequestBody에 맡겼다. 매개변수 타입을 String에서 LoanRequest로 바꾸기만 하면 스프링이 문자열 컨버터 대신 JSON 컨버터를 골라 쓴다. 스프링 MVC의 디버그 로그를 켜고 {"borrower":"kim","days":7}을 보내면 과정이 보인다.

    DispatcherServlet                        : POST "/loans/json", parameters={}
RequestMappingHandlerMapping             : Mapped to study.mvc.BodyController#json(LoanRequest)
  LoanRequest() 생성
  setBorrower(kim)
  setDays(7)
RequestResponseBodyMethodProcessor       : Read "application/json;charset=UTF-8" to [LoanRequest(borrower=kim, days=7)]

    첫 줄의 parameters={}가 이 요청에 요청 파라미터가 하나도 없음을 말해 준다. JSON 바디는 파라미터가 아니다. 가운데 세 줄의 흔적은 @ModelAttribute 때와 똑같아 보이지만 호출한 주체가 다르다. 이번에는 스프링의 데이터 바인더가 아니라 Jackson이 JSON의 필드 이름을 보고 이 클래스의 기본 생성자와 세터를 호출했다. 겉으로 같은 객체가 만들어져도 재료(파라미터 표와 바디 스트림)와 만드는 주체가 다르다는 점이 이 회차 전체의 요점이다.

    요청이 조금씩 어긋날 때

    요청(POST /loans/json, 따로 적지 않으면 Content-Type은 application/json)응답서버 로그의 원인

    위쪽 세 줄은 Content-Type의 역할을 보여 준다. 스프링은 바디의 내용을 들여다보고 형식을 추측하지 않는다. 헤더가 말하는 미디어 타입과 매개변수의 타입을 들고 "이 조합을 읽을 수 있는 컨버터"를 찾는다. JSON 컨버터가 지원하는 미디어 타입은 application/json과 application/*+json이고(415 응답의 Accept 헤더에 이 두 값이 실려 왔다), 헤더가 없는 요청은 application/octet-stream으로 취급되어 맞는 컨버터가 없다. 바디가 완벽한 JSON이어도 헤더가 틀리면 415다. 요청 파라미터 절의 4번 실험과 같은 교훈이다. 바이트의 해석 방법은 내용이 아니라 헤더가 정한다.

    이 415는 요청 매핑 절에서 본 consumes 불일치의 415와 상태 코드는 같지만 발생 지점이 다르다. 디버그 로그를 보면 Mapped to study.mvc.BodyController#json(LoanRequest)가 먼저 찍히고 그다음에 Could not resolve parameter [0]이 찍힌다. 핸들러는 정해졌고, 인자를 만들다가 실패한 것이다. 매핑에 consumes = "application/json"을 적어 두면 같은 요청이 매핑 단계에서 걸러지고, 같은 URL에 다른 미디어 타입을 받는 핸들러를 따로 둘 수 있게 된다.

    가운데 줄들은 JSON 변환 자체의 실패와 관용을 보여 준다. 문법이 깨졌거나 타입이 맞지 않으면 객체가 완성되기 전에 변환이 실패하고 400이 응답된다. 이 실패는 컨트롤러 메서드가 호출되기 전에, 객체가 만들어지기도 전에 일어나므로 @ModelAttribute의 타입 오류처럼 BindingResult에 담아 컨트롤러 안에서 처리할 수가 없다. 모르는 필드 memo가 무시된 것은, Jackson 2를 쓰는 기준 버전(Spring Boot 3.x)에서는 스프링 쪽 설정의 결과다. Jackson 2에서 DeserializationFeature.FAIL_ON_UNKNOWN_PROPERTIES는 기본으로 켜져 있는데, Spring Framework 6.2 레퍼런스는 스프링의 Jackson2ObjectMapperBuilder가 이 기능을 끈다고 적는다. 클라이언트가 필드를 추가해도 서버가 깨지지 않게 하려는 선택이다. 실험에 쓴 Jackson 3(3.1.7)에서는 이 기능의 기본값 자체가 꺼짐(false)이다.

    가장 조용한 실수: @RequestBody를 빠뜨렸을 때

    마지막 줄을 보자. jsonOmitted(LoanRequest loan)에 올바른 JSON을 보냈는데 상태 코드는 200이고 객체는 비어 있다. 서버 콘솔에는 LoanRequest() 생성 한 줄만 찍혔다. 생략 규칙을 적용해 보면 당연한 결과다. LoanRequest는 단순 타입이 아니므로 애너테이션이 없으면 @ModelAttribute로 처리된다. 스프링은 빈 객체를 만들고 요청 파라미터에서 borrower와 days를 찾았는데, JSON 바디는 파라미터가 아니므로 아무것도 찾지 못했고 세터를 한 번도 호출하지 않았다. 규칙대로 동작했기 때문에 오류가 없다.

    이 실수가 위험한 이유는 실패가 신호를 내지 않는다는 데 있다. 415나 400은 원인을 알려 주지만, 조용히 비어 있는 객체는 한참 뒤 "저장된 값이 전부 null"이라는 다른 증상으로 발견된다. @RequestParam과 @ModelAttribute는 생략할 수 있지만 @RequestBody는 생략할 수 없다는 비대칭을 기억해 두자. 바디를 읽겠다는 의사는 반드시 적어야 한다.

    끝으로 jsonManual의 objectMapper 필드에 대해 한마디 덧붙인다. 컨트롤러는 싱글톤이므로 이 필드는 모든 요청 스레드가 공유한다. 01회에서 본 대로 공유 필드는 조심해야 하지만, ObjectMapper는 설정을 마친 뒤에는 여러 스레드가 함께 써도 안전하도록 설계된 객체여서 이렇게 한 번 만들어 재사용한다. 스프링이 @RequestBody를 처리할 때 쓰는 것도 컨테이너에 등록된 하나의 매퍼다.

    요청을 읽는 수단 정리

    수단읽는 곳값을 만드는 방법어긋났을 때
    @PathVariableURL 경로의 변수 자리문자열을 매개변수 타입으로 변환변환 실패 400
    @RequestHeader, @CookieValue헤더문자열을 매개변수 타입으로 변환필수인데 없으면 예외
    @RequestParam요청 파라미터(쿼리 스트링 + 폼 바디)문자열을 매개변수 타입으로 변환필수 누락·변환 실패 400, 기본형에 null이면 500
    @ModelAttribute요청 파라미터객체 생성 후 세터 호출(또는 생성자 인자)누락은 그대로 둠, 변환 실패 400
    @RequestBody, HttpEntity메시지 바디HTTP 메시지 컨버터(문자열, JSON 등)미디어 타입 불일치 415, 변환 실패·바디 없음 400

    이 표의 "값을 만드는 방법" 칸을 실제로 수행하는 객체들, 곧 인자 리졸버와 메시지 컨버터가 어디에 모여 있고 어떤 순서로 선택되는지가 07회의 주제다. 07회는 같은 장치가 응답 방향으로는 어떻게 쓰이는지도 함께 다룬다.
    SLF4J와 Logback
    코드는 SLF4J의 Logger 인터페이스만 부르고, 실제 출력은 구현체가 한다. 스프링 부트 스타터의 기본 구현체는 Logback이다.
    유효 레벨과 기본 선택 규칙
    로거는 이름의 점 구분으로 계층을 이루고, 자기 레벨이 없으면 가장 가까운 조상의 레벨을 물려받는다. 요청 레벨이 유효 레벨 이상일 때만 출력된다. 부트의 기본은 INFO다.
    자리 표시자 로깅
    자바는 메서드 호출 전에 인자를 평가하므로 문자열 연결은 로그가 버려져도 실행된다. {} 방식은 참조만 넘기고 출력이 결정된 뒤에 포매팅한다.
    요청 매핑 등록부
    RequestMappingHandlerMapping이 시작 시점에 @Controller 빈의 메서드를 훑어 RequestMappingInfo(경로, 메서드, params, headers, consumes, produces) → 핸들러 메서드의 맵을 만든다. 키가 같은 항목이 둘이면 시작이 실패한다.
    핸들러 선택과 실패 코드
    직접 경로 조회 → 조건 검사 → 전체 훑기 → 비교자로 최선 선택. 못 고르면 경로만 맞는 항목을 분석해 405·415·406·400을 내고, 그것도 없으면 404로 이어진다.
    -parameters와 이름 생략
    @PathVariable·@RequestParam의 이름을 생략하면 스프링은 리플렉션으로 매개변수 이름을 읽는다. 이 이름은 -parameters로 컴파일해야 클래스 파일의 MethodParameters 속성에 남는다.
    요청 파라미터
    서블릿 명세는 쿼리 스트링과 POST 폼 바디를 하나의 파라미터 집합으로 합친다. 파싱은 첫 조회 때 일어나고, 폼 바디를 파라미터로 읽으면 입력 스트림은 비며 그 반대도 성립한다.
    @RequestParam과 @ModelAttribute
    둘 다 요청 파라미터를 읽는다. 앞의 것은 값 하나를 타입 변환해 넣고, 뒤의 것은 객체를 만들어 같은 이름의 프로퍼티 세터를 호출한다. 애너테이션을 생략하면 단순 타입은 앞의 것으로, 나머지 객체는 뒤의 것으로 처리된다.
    @RequestBody와 HttpEntity
    메시지 바디 스트림을 읽어 HTTP 메시지 컨버터로 변환한다. 어떤 컨버터가 쓰일지는 Content-Type과 매개변수 타입이 정하며, 생략할 수 없다.

    실무에서 다시 판단하면, 이 회차의 지식은 장애 대응에서 "어느 층에서 실패했는가"를 좁히는 데 가장 자주 쓰인다. 404는 경로가 등록부에 없다는 뜻이고(끝 슬래시, 대소문자, 컨텍스트 경로를 먼저 본다), 405는 경로는 맞지만 메서드가 다르다는 뜻이며, 415는 Content-Type과 서버가 읽을 수 있는 형식의 불일치다. 400은 핸들러까지는 정해졌고 인자를 만들다 실패했다는 신호이고, 같은 자리에서 500이 난다면 클라이언트가 아니라 서버 코드(기본형에 null, 빠진 -parameters, 모호한 매핑)를 봐야 한다. 상태 코드와 서버 로그의 예외 이름을 함께 읽는 습관이 원인까지의 거리를 크게 줄인다.

    애너테이션 생략은 팀 규칙으로 정해 둘 문제다. 생략형은 짧지만 이름이 빌드 설정에 의존하고, 필수 여부가 달라지며, @RequestBody를 빠뜨린 실수와 겉모습이 같아 리뷰에서 걸러 내기 어렵다. 외부에 공개되는 API일수록 @RequestParam("name"), @PathVariable("id")처럼 이름을 명시하면 매개변수 이름을 리팩터링해도 계약이 바뀌지 않는다. 바인딩 대상 객체는 요청 전용 타입으로 따로 두고 엔티티를 직접 받지 않는다. 세터가 열려 있는 프로퍼티는 모두 클라이언트가 채울 수 있기 때문이다.

    바디가 한 번만 읽힌다는 제약은 공통 기능을 만들 때 반드시 부딪힌다. 요청 바디를 감사 로그로 남기는 필터를 무심코 만들면 컨트롤러가 빈 바디를 받는다. 이런 요구에는 읽은 내용을 보관해 두는 요청 래퍼(스프링의 ContentCachingRequestWrapper 같은 것)를 쓰거나, 컨트롤러가 변환한 뒤의 객체를 기록하는 쪽으로 설계를 바꾼다. 큰 바디를 메모리에 복사해 두는 비용이 따르므로 크기 제한과 함께 판단해야 한다.

    로깅은 운영에서 비용과 위험을 함께 갖는다. 레벨은 환경별로 다르게 두고(개발은 내 패키지만 DEBUG, 운영은 INFO), 운영 중 문제를 추적할 때는 특정 패키지의 레벨만 일시적으로 내린다. 로그 문장은 자리 표시자로 쓰고, 인자 자리에 비싼 호출을 직접 두지 않는다. 요청 파라미터와 헤더에는 인증 정보가 섞여 있으므로 값을 통째로 남기는 로그는 피한다. 스프링이 디버그 로그에서조차 파라미터를 가리는 기본값을 택한 이유를 그대로 따르면 된다.

    로거에 실제로 적용되는 레벨. 자기 자신에서 루트 쪽으로 올라가며 처음 만나는 지정된 레벨이다.
    요청 매핑(request mapping)
    요청의 경로·메서드·헤더 등의 조건과 그것을 처리할 핸들러 메서드를 연결하는 일. 스프링 MVC에서는 RequestMappingHandlerMapping이 담당한다.
    RequestMappingInfo
    @RequestMapping 한 건을 객체로 옮긴 것. 경로 패턴, HTTP 메서드, params, headers, consumes, produces 조건을 담고 등록부의 키로 쓰인다.
    합성 애너테이션(composed annotation)
    다른 애너테이션을 메타 애너테이션으로 가지면서 그 속성 일부를 고정하거나 다시 선언한 애너테이션. @GetMapping은 @RequestMapping(method = GET)의 합성이다.
    경로 변수(path variable)
    URL 경로 패턴에서 {이름}으로 표시한 자리. 매칭된 문자열이 @PathVariable 인자로 전달된다.
    MethodParameters 속성
    클래스 파일에서 메서드의 매개변수 이름을 기록하는 속성. javac -parameters로 컴파일해야 생기며 리플렉션의 Parameter.getName()이 이것을 읽는다.
    요청 파라미터(request parameter)
    서블릿 명세의 개념으로, 쿼리 스트링과 POST 폼 바디(application/x-www-form-urlencoded)에서 얻은 이름-값 쌍의 집합.
    데이터 바인딩(data binding)
    이름-값 문자열들을 객체의 프로퍼티에 타입 변환과 함께 채워 넣는 일. @ModelAttribute가 이 방식으로 객체를 만든다.
    HTTP 메시지 컨버터(HttpMessageConverter)
    HTTP 바디의 바이트와 자바 객체 사이를 변환하는 스프링의 부품. 미디어 타입과 대상 타입에 따라 선택된다.
