    주소창의 한 줄이 풀어야 하는 문제

    01회에서 네 가지 도구를 얻었다. IP는 호스트까지 패킷을 실어 나르고, TCP는 그 위에 순서가 보장되는 연결을 만들고, 포트는 한 호스트 안에서 어느 프로세스와 이야기할지를 가리며, DNS는 사람이 읽는 이름을 IP 주소로 바꿔 준다. 그런데 이 네 가지를 모두 갖추어도 웹은 아직 성립하지 않는다. 서버 프로세스와 연결이 닿은 뒤에 "당신이 가진 수많은 것 가운데 바로 이것을 달라"고 지목할 방법이 없기 때문이다.

    또 하나의 문제는 사람이다. 사용자는 프로토콜, 호스트 이름, 포트 번호, 원하는 대상의 이름을 따로따로 입력하지 않는다. 주소창에 문자열 한 줄을 넣거나 링크 하나를 누를 뿐이다. 그 한 줄 안에 "어떤 방식으로, 어느 서버의, 무엇을"이 모두 들어 있어야 하고, 브라우저는 그것을 기계적으로 분해해 DNS 조회와 TCP 연결과 HTTP 메시지로 옮길 수 있어야 한다.

    이 한 줄이 URI다. 이 장의 앞 절반은 URI라는 문자열의 문법을 RFC 3986을 기준으로 끝까지 따져 보고, 뒤 절반은 그 문자열이 실제 네트워크 동작으로 번역되어 서버에 닿았다가 응답으로 돌아오는 과정을 계층별로 추적한다. 두 주제는 따로 떨어져 있지 않다. URI의 각 조각은 요청 흐름의 특정 단계에서 쓰이고, 어느 조각이 어느 단계에서 쓰이는지를 아는 것이 이 장의 목표다.

    URI, URL, URN: 식별자와 위치와 이름

    URI는 Uniform Resource Identifier의 약자다. 세 단어를 뒤에서부터 읽으면 뜻이 잡힌다. 식별자(Identifier)는 어떤 대상을 다른 모든 대상과 구별하는 데 필요한 정보다. 자원(Resource)은 그 식별의 대상인데, RFC 9110은 HTTP 요청의 대상을 자원이라 부른다고만 정의하고 자원의 성격은 제한하지 않는다고 적는다. HTML 문서나 이미지 파일처럼 손에 잡히는 것만이 아니라 "JVM으로 검색한 결과의 두 번째 쪽", "주문 1042번", "지금 이 순간의 재고 수량"처럼 요청할 때마다 계산되는 것도 식별할 수만 있으면 자원이다. 통일(Uniform)은 자원의 종류나 접근 방법이 달라도 하나의 문법 틀로 적는다는 뜻이다. 덕분에 새로운 스킴이 생겨도 기존 파서가 큰 구조를 그대로 해석할 수 있다.

    URL과 URN은 URI를 더 좁힌 말이다. RFC 3986 1.1.3절은 URI가 위치 지정자(locator), 이름(name), 또는 둘 다로 더 분류될 수 있다고 쓴다. 같은 절에 따르면 URL(Uniform Resource Locator)은 자원을 식별하는 데 그치지 않고 주된 접근 방법, 곧 네트워크상의 위치를 기술해 그 자원을 찾아갈 수단까지 주는 URI의 부분집합이다. URN(Uniform Resource Name)은 역사적으로 urn 스킴을 쓰는 URI, 곧 자원이 사라지거나 접근할 수 없게 되어도 전역적으로 유일하고 영속적으로 남아야 하는 이름을 가리켜 왔고, 이름의 성질을 가진 그 밖의 URI를 부르는 데도 쓰였다.

    +--------------------------- URI (식별자) ---------------------------+
|                                                                    |
|   +------- URL (위치) -------+      +------- URN (이름) -------+   |
|   |  https://books.example…  |      |  urn:isbn:…              |   |
|   |  ftp://files.example…    |      |                          |   |
|   |  "어디에서 어떻게 얻는가" |      |  "그것이 무엇인가"        |   |
|   +--------------------------+      +--------------------------+   |
|                                                                    |
+--------------------------------------------------------------------+

    예를 들어 urn:isbn: 뒤에 ISBN을 붙인 이름은 어떤 책인지를 가리키지만, 그 책을 어느 서버에서 어떤 프로토콜로 받을 수 있는지는 말하지 않는다. 반대로 https://books.example.com/catalog/java/list는 "HTTPS로 books.example.com에 접속해 이 경로를 달라고 하라"는 접근 방법이 식별자 안에 들어 있다. 위치로 식별한다는 것은 약점이기도 하다. 자원이 다른 호스트나 다른 경로로 옮겨지면 식별자 자체가 틀린 것이 된다. 06회에서 볼 리다이렉트 상태 코드가 필요한 이유가 여기에 있다.

    흔한 오해는 URI와 URL을 서로 다른 두 종류로 보는 것이다. 둘은 포함 관계다. 그리고 그 분류도 깔끔한 이분법이 아니다. RFC 3986은 개별 스킴이 이름과 위치 가운데 하나로만 분류될 필요가 없다고 하면서, 앞으로의 명세와 문서는 더 제한적인 "URL", "URN" 대신 일반 용어인 "URI"를 쓰라고 권고한다. 실제로 HTTP 명세인 RFC 9110은 본문 전체에서 URI라는 말을 쓴다. 한편 브라우저가 주소를 해석할 때 따르는 WHATWG의 표준은 이름이 "URL Standard"다. 그래서 현장에서는 두 말이 섞여 쓰인다. 웹 개발에서 다루는 http·https 식별자는 URL이면서 URI이므로 어느 쪽으로 불러도 틀리지 않는다.

    일반 문법: 다섯 조각으로 자르는 규칙

    RFC 3986 3절은 모든 URI에 공통인 문법을 다음과 같이 정한다. 표기는 ABNF이고, 대괄호는 "있어도 되고 없어도 된다"는 뜻이다.

    URI       = scheme ":" hier-part [ "?" query ] [ "#" fragment ]

hier-part = "//" authority path-abempty
          / path-absolute
          / path-rootless
          / path-empty

    스킴(scheme)과 콜론은 반드시 있어야 하고, 그 뒤의 계층 부분(hier-part)은 네 형태 가운데 하나다. //로 시작하면 authority가 나오고 이어서 비어 있거나 /로 시작하는 경로가 온다. //가 없으면 authority 없이 경로만 온다. 그 뒤에 ?로 시작하는 쿼리(query)와 #으로 시작하는 프래그먼트(fragment)가 선택적으로 붙는다. 이렇게 해서 URI는 최대 다섯 조각이 된다.

      https://books.example.com:8443/catalog/java/list?keyword=jvm&page=2#result
  \___/   \____________________/\________________/ \________________/ \____/
    |                |                   |                  |            |
  scheme         authority              path              query      fragment
    하나의 URI 문자열을 다섯 구성 요소로 색을 달리해 나누고, 각 조각이 무엇을 결정하는지 한 줄씩 붙인다. 흰 배경의 깔끔한 기술 도해. 화면 가운데에 고정폭 글꼴로 한 줄의 문자열 "https://books.example.com:8443/catalog/java/list?keyword=jvm&page=2#result" 를 크게 적는다. 문자열을 다섯 구간으로 나누어 서로 다른 옅은 색 띠로 밑칠한다: "https"(파랑), "books.example.com:8443"(초록), "/catalog/java/list"(주황), "keyword=jvm&page=2"(보라), "result"(회색). 구분 기호 "://", "?", "#" 는 색을 칠하지 않고 검은색으로 둔다. 각 구간 아래로 가는 선을 내려 라벨 상자를 단다. 라벨 문구는 정확히: "scheme · 어떤 방식으로", "authority · 어느 서버의 어느 포트", "path · 서버 안의 어느 자원", "query · 자원을 좁히는 조건", "fragment · 받은 뒤 볼 위치". 초록 구간 위쪽에는 작은 중괄호로 다시 둘로 나누어 "host" 와 "port" 라벨을 붙인다. 장식 없이 평면적이고 차분한 색조. URI의 다섯 구성 요소. 구분 기호 ://, ?, #이 경계를 만든다.

    분해 규칙은 사람의 감이 아니라 결정적인 절차다. RFC 3986 부록 B는 URI 참조를 구성 요소로 나누는 정규식 하나를 싣고 있다. 이 정규식을 자바에서 그대로 돌려 보면 규칙이 한눈에 보인다.

    import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class UriSplit {
    // RFC 3986 부록 B에 실린 정규식 그대로
    private static final Pattern URI_REFERENCE = Pattern.compile(
            "^(([^:/?#]+):)?(//([^/?#]*))?([^?#]*)(\\?([^#]*))?(#(.*))?");

    public static void main(String[] args) {
        split("https://books.example.com:8443/catalog/java/list?keyword=jvm&page=2#result");
        split("mailto:reader@example.com");
        split("/catalog/java?sort=new");
        split("https://books.example.com/a?next=/b?c#d/e?f");
    }

    private static void split(String text) {
        Matcher m = URI_REFERENCE.matcher(text);
        if (!m.matches()) {
            throw new IllegalArgumentException(text);
        }
        System.out.println(text);
        System.out.println("  scheme=" + m.group(2) + ", authority=" + m.group(4)
                + ", path=" + m.group(5) + ", query=" + m.group(7) + ", fragment=" + m.group(9));
    }
}
    https://books.example.com:8443/catalog/java/list?keyword=jvm&page=2#result
  scheme=https, authority=books.example.com:8443, path=/catalog/java/list, query=keyword=jvm&page=2, fragment=result
mailto:reader@example.com
  scheme=mailto, authority=null, path=reader@example.com, query=null, fragment=null
/catalog/java?sort=new
  scheme=null, authority=null, path=/catalog/java, query=sort=new, fragment=null
https://books.example.com/a?next=/b?c#d/e?f
  scheme=https, authority=books.example.com, path=/a, query=next=/b?c, fragment=d/e?f

    정규식을 왼쪽부터 읽으면 다섯 개의 규칙이 된다. 첫째, 문자열 맨 앞에서 :, /, ?, #이 아닌 문자가 이어지다가 :을 만나면 거기까지가 스킴이다. 둘째, 그 뒤가 //로 시작하면 다음 /, ?, #이 나오기 직전까지가 authority다. 셋째, 거기서부터 ?나 #이 나오기 직전까지가 경로다. 넷째, ? 뒤부터 # 직전까지가 쿼리다. 다섯째, 처음 만나는 # 뒤의 나머지 전부가 프래그먼트다.

    이 절차에서 중요한 성질은 "왼쪽에서 오른쪽으로 가면서 처음 만난 구분자로 자른다"는 것이다. 네 번째 입력이 그것을 보여 준다. 쿼리는 첫 ?에서 시작해 첫 # 직전에서 끝나므로, 쿼리 안에 다시 나오는 /와 ?는 구분자가 아니라 데이터다. 그래서 쿼리는 next=/b?c가 된다. 프래그먼트 안의 /와 ?도 마찬가지다. 반대로 #은 어디에서 나오든 처음 나온 자리에서 프래그먼트를 시작시킨다. 쿼리 값에 #을 글자로 넣고 싶다면 뒤에서 볼 퍼센트 인코딩을 써야 하는 이유다.

    두 번째와 세 번째 입력도 볼 만하다. mailto:reader@example.com에는 //가 없으므로 authority가 없고, 콜론 뒤 전체가 경로다. ABNF의 path-rootless 형태에 해당한다. /catalog/java?sort=new에는 스킴이 없다. 이것은 URI가 아니라 상대 참조(relative reference)이고, 어떤 기준 URI에 대해 해석해야 비로소 완전한 URI가 된다. 결과에 찍힌 null은 그 구성 요소가 "비어 있다"가 아니라 "없다"는 뜻이다. http://example.com?처럼 구분자만 있고 내용이 없는 경우는 쿼리가 빈 문자열로 존재하는 것이어서 둘은 구별된다.

    스킴과 authority: 어디에, 어떤 방식으로 연결할 것인가

    스킴

    스킴은 영문자로 시작하고 영문자, 숫자, +, -, .로 이어지는 이름이다. 스킴이 정하는 것은 "나머지 부분을 어떤 규칙으로 해석할 것인가"다. 일반 문법은 조각의 경계만 정할 뿐이고, 각 조각의 의미는 스킴의 명세가 정한다. RFC 3986에 따르면 스킴은 대소문자를 구분하지 않지만 정규형은 소문자이고, 구현은 HTTP를 http와 같게 받아들이되 만들어 낼 때는 소문자만 써야 한다.

    http와 https 스킴의 의미는 RFC 9110이 정한다. http URI에서 원 서버(origin server)는 authority 구성 요소로 식별되고, 포트가 비어 있거나 주어지지 않으면 TCP 80번이 기본값이다. https는 기본 포트가 TCP 443번이고 TLS로 보호된 연결을 쓴다. 곧 스킴 하나가 세 가지를 결정한다. authority 뒤쪽을 HTTP의 규칙으로 해석하라는 것, 포트가 생략되었을 때 무엇으로 채울지, 그리고 연결 위에 TLS를 올릴지 여부다. 또 RFC 9110은 호스트가 비어 있는 http URI를 만들어서는 안 된다고 못박는다.

    authority = userinfo, host, port

    authority는 [ userinfo "@" ] host [ ":" port ] 구조다. 가운데의 host가 핵심이고 세 가지 형태가 있다. 192.0.2.10 같은 IPv4 주소, 대괄호로 감싼 IPv6 주소, 그리고 등록된 이름(reg-name)이다. 등록된 이름은 대개 DNS 이름이며, 이 경우 01회에서 본 DNS 조회를 거쳐야 IP 주소가 된다. IPv6 주소를 대괄호로 감싸는 이유는 문법에 있다. IPv6 주소 표기에는 콜론이 들어가는데, authority 안에서 콜론은 포트의 구분자이기도 하다. 대괄호가 없으면 어디까지가 주소이고 어디부터 포트인지 가를 수 없다.

    host는 대소문자를 구분하지 않는다. 그리고 한글 같은 비 ASCII 문자가 든 도메인 이름은 DNS에 그대로 질의할 수 없다. RFC 3986 3.2.2절은 그런 이름이 DNS로 해석될 국제화 도메인 이름이라면 조회 전에 IDNA 인코딩으로 변환해야 한다고 적는다. 변환 결과는 xn--로 시작하는 ASCII 문자열이다.

    port는 숫자열이고 생략할 수 있다. 여기서 놓치기 쉬운 점은 "기본 포트"라는 지식이 일반 문법이 아니라 스킴에 속한다는 것이다. URI 파서는 포트가 적혀 있지 않다는 사실만 알고, 그 자리를 80이나 443으로 채우는 것은 스킴의 의미를 아는 HTTP 클라이언트의 일이다. 자바의 java.net.URI로 확인해 보자.

    import java.net.IDN;
import java.net.URI;

public class Authority {
    public static void main(String[] args) {
        URI full = URI.create("https://books.example.com:8443/catalog");
        URI bare = URI.create("http://books.example.com");
        URI v6 = URI.create("http://[2001:db8::1]:8080/");

        System.out.println(full.getHost() + " | " + full.getPort());
        System.out.println(bare.getHost() + " | " + bare.getPort() + " | [" + bare.getRawPath() + "]");
        System.out.println(v6.getHost() + " | " + v6.getPort());
        System.out.println(IDN.toASCII("자바.example"));
    }
}

    둘째 줄을 보면 포트가 없는 URI에서 getPort()는 80이 아니라 -1을 돌려준다. Javadoc의 표현으로는 "포트가 정의되지 않았다"는 뜻이다. 경로도 /가 아니라 빈 문자열이다. 일반 문법 수준에서는 http://books.example.com에 포트도 경로도 없다. 이것을 "80번 포트의 /"로 읽는 것은 한 단계 위, HTTP의 규칙이다. 넷째 줄은 한글 이름이 DNS 조회에 쓰일 ASCII 형태로 바뀐 결과다.

    userinfo는 host 앞에 @로 구분해 붙이는 사용자 정보다. RFC 3986은 여기에 user:password 형식을 쓰는 것을 폐기 대상(deprecated)으로 규정했고, RFC 9110은 한 걸음 더 나아가 송신자가 http·https URI에 userinfo를 생성해서는 안 된다고 한다. 비밀번호가 주소에 평문으로 남는다는 문제 외에 눈속임 문제가 있다. https://books.example.com@evil.example/login이라는 문자열을 문법대로 자르면 authority는 books.example.com@evil.example이고, @ 앞은 userinfo이므로 실제 host는 evil.example이다. 사람의 눈은 앞쪽의 익숙한 이름에 머무르지만 연결은 뒤쪽 호스트로 간다. RFC 9110이 신뢰할 수 없는 출처에서 받은 URI에 userinfo가 있으면 오류로 취급하라고 권하는 까닭이다.

    RFC 9110은 스킴, 호스트, 포트 세 가지를 묶어 출처(origin)라고 정의한다. 스킴과 호스트를 소문자로 정규화한 뒤의 세 값이 모두 같아야 같은 출처다. 경로가 달라도 출처는 같고, 포트만 달라도 출처는 다르다. 브라우저의 보안 정책이 "같은 사이트인가"를 따질 때 쓰는 단위가 이것이어서, authority를 정확히 읽는 일은 뒤의 여러 주제에서 다시 쓰인다.

    경로, 쿼리, 프래그먼트: 무엇을 요청하고 어디를 볼 것인가

    경로

    경로(path)는 /로 나뉜 세그먼트(segment)들의 나열이다. RFC 3986은 URI 문법이 왼쪽에서 오른쪽으로 갈수록 범위가 좁아지는 계층으로 짜여 있다고 설명하는데, 경로가 그 성질을 가장 잘 보여 준다. /catalog/java/list는 "카탈로그 안의, 자바 안의, 목록"으로 읽힌다. 다만 이 계층은 식별자의 구조일 뿐이고 서버의 디렉터리 구조와 일치할 필요가 없다. 경로를 파일에 대응시킬지, 데이터베이스 조회에 대응시킬지, 자바 메서드 호출에 대응시킬지는 전적으로 서버가 정한다.

    경로는 스킴이나 호스트와 달리 대소문자를 구분한다. RFC 3986은 스킴과 호스트 외의 구성 요소는 스킴이 따로 정하지 않는 한 대소문자를 구분하는 것으로 본다고 하고, RFC 9110도 http URI에서 스킴과 호스트만 대소문자를 무시한다고 정한다. 그러므로 /Cart와 /cart는 다른 식별자다. 서버가 두 경로에 같은 내용을 내주도록 구현할 수는 있지만, 캐시나 검색 엔진이나 중간 장비가 둘을 같은 자원으로 취급해 줄 근거는 없다.

    경로에는 특별한 세그먼트 두 가지가 있다. .은 현재 위치, ..은 한 단계 위를 뜻하는 점 세그먼트(dot-segment)이고, 상대 참조를 해석할 때 제거된다. 또 authority가 있는 URI에서 경로가 비어 있을 수 있는데, HTTP에서는 빈 경로를 /와 같다고 본다. 반면 /catalog/java와 /catalog/java/처럼 끝의 슬래시 유무만 다른 두 경로는 정규화로 같아지지 않는 별개의 URI다. 이 차이가 실제로 문제를 일으키는 장면은 상대 참조 절에서 확인한다.

    쿼리

    쿼리(query)는 첫 ? 뒤부터 # 직전까지다. RFC 3986은 쿼리를 "경로와 함께 자원을 식별하는 비계층적 데이터"라고 정의한다. 두 가지를 읽어 내야 한다. 하나는 쿼리도 식별의 일부라는 점이다. ?page=2와 ?page=3은 서로 다른 URI이고, 캐시는 둘을 따로 저장한다. 다른 하나는 RFC 3986이 쿼리의 내부 구조를 정하지 않는다는 점이다. 명세는 쿼리가 key=value 쌍의 형태로 자주 쓰인다고 언급할 뿐이다.

    이름=값을 &로 잇는 익숙한 형식은 HTML 폼 전송에서 온 관례이고, 오늘날에는 WHATWG URL 표준이 application/x-www-form-urlencoded라는 이름으로 그 직렬화와 해석 절차를 정의한다. 따라서 ?tag=a&tag=b처럼 같은 이름이 두 번 나올 때 목록으로 받을지, 값 없이 ?debug만 있을 때 어떻게 볼지는 URI 명세의 문제가 아니라 그 쿼리를 해석하는 쪽의 규칙이다. 서버 프레임워크마다 동작을 확인해야 하는 이유다.

    프래그먼트

    프래그먼트(fragment)는 # 뒤의 나머지다. 앞의 네 조각이 가리키는 자원을 일차 자원이라 할 때, 프래그먼트는 그 자원을 가져온 뒤에 그 안의 일부분이나 그에 딸린 보조 자원을 가리킨다. HTML 문서라면 같은 값의 id를 가진 요소가 대상이 되고, 브라우저는 그 위치로 스크롤한다. 프래그먼트를 어떻게 해석할지는 가져온 표현의 미디어 타입에 달려 있다.

    프래그먼트의 결정적인 성질은 서버로 전송되지 않는다는 것이다. RFC 3986 3.5절은 프래그먼트 식별자가 역참조(dereference) 이전에 URI의 나머지 부분에서 분리되고, 오직 사용자 에이전트가 처리한다고 적는다. RFC 9110 7.1절도 요청의 대상 URI(target URI)는 참조의 프래그먼트를 제외한 것이라고 정의한다. 여기서 세 가지 결과가 따라 나온다. 서버의 접근 로그에는 프래그먼트가 남지 않는다. 서버 코드는 프래그먼트 값을 읽을 수 없다. 그리고 현재 문서와 프래그먼트만 다른 링크를 누르면 같은 문서 안의 이동으로 처리되어 새 요청이 나가지 않는다.

    URI의 앞부분(스킴과 authority)은 "어디에 어떻게 연결할지"를 정하고, 가운데(경로와 쿼리)는 "연결한 뒤 무엇을 달라고 할지"를 정하며, 끝(프래그먼트)은 "받은 뒤 어디를 볼지"를 정한다. 앞부분은 DNS와 TCP가 쓰고, 가운데는 HTTP 메시지에 실려 서버 애플리케이션이 쓰고, 끝은 브라우저만 쓴다.

    문자 집합과 퍼센트 인코딩

    URI는 아무 문자로나 쓸 수 없다. RFC 3986의 문법은 US-ASCII 문자 가운데서도 일부만 허용한다. 이유는 URI가 구분자로 조각을 가르는 문자열이기 때문이다. /, ?, #이 경계를 뜻하는 이상, 데이터에 같은 문자가 들어 있으면 경계와 데이터를 가를 수 없다. 그래서 문자를 두 무리로 나눈다.

    • 비예약 문자(unreserved): 영문자, 숫자, 그리고 - . _ ~. 어디서든 글자 그대로 쓸 수 있고 특별한 뜻이 없다.
    • 예약 문자(reserved): 구분자로 쓰일 수 있는 문자. 일반 구분자 : / ? # [ ] @와 하위 구분자 ! $ & ' ( ) * + , ; =로 나뉜다.

    이 두 무리에 들지 않는 문자(공백, 큰따옴표, 꺾쇠, 중괄호, 그리고 모든 비 ASCII 문자)는 URI에 그대로 쓸 수 없다. 또 예약 문자를 구분자가 아닌 데이터로 쓰고 싶을 때도 그대로 쓸 수 없다. 이때 쓰는 것이 퍼센트 인코딩(percent-encoding)이다. 바이트 하나를 %와 16진수 두 자리로 적는다. 16진수의 대소문자는 같은 것으로 보지만 RFC 3986은 대문자를 쓰라고 권한다. % 자체를 데이터로 쓰려면 %25로 적어야 한다.

    비 ASCII 문자는 한 단계를 더 거친다. RFC 3986 2.5절에 따라 문자를 먼저 UTF-8로 바이트열로 바꾼 뒤 바이트마다 퍼센트 인코딩한다. 한글 "자"를 손으로 계산해 보자. "자"의 유니코드 코드 포인트는 U+C790이고 2진수로 1100 0111 1001 0000이다. UTF-8에서 이 범위의 문자는 3바이트 틀 1110xxxx 10xxxxxx 10xxxxxx에 16비트를 4·6·6으로 나눠 채운다. 1100, 011110, 010000을 넣으면 11101100 10011110 10010000, 16진수로 EC 9E 90이다. 그래서 "자"는 %EC%9E%90이 된다. 글자 하나가 URI에서는 아홉 글자가 되는 셈이다.

    import java.net.URI;
import java.net.URLDecoder;
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;
import java.util.HexFormat;

public class Encode {
    public static void main(String[] args) throws Exception {
        // 1. 문자 -> UTF-8 바이트 -> %XX
        byte[] utf8 = "자바".getBytes(StandardCharsets.UTF_8);
        System.out.println(HexFormat.ofDelimiter(" ").withUpperCase().formatHex(utf8));

        // 2. 폼 인코딩(application/x-www-form-urlencoded)
        String value = "자바 & C++";
        String form = URLEncoder.encode(value, StandardCharsets.UTF_8);
        System.out.println(form);
        System.out.println(URLDecoder.decode(form, StandardCharsets.UTF_8));
        System.out.println(URLEncoder.encode("a-b_c.d~e*f", StandardCharsets.UTF_8));

        // 3. 구성 요소별 생성자: 경로의 공백은 %20
        URI uri = new URI("https", "books.example.com", "/책/자바 입문", "q=자바", null);
        System.out.println(uri.toASCIIString());

        // 4. 디코딩은 구성 요소로 나눈 뒤에
        URI tricky = URI.create("https://books.example.com/a%2Fb/c?title=1%262&page=3");
        System.out.println(tricky.getRawPath() + " | " + tricky.getPath());
        System.out.println(tricky.getRawQuery() + " | " + tricky.getQuery());

        // 5. 이중 인코딩
        String once = URLEncoder.encode("100%", StandardCharsets.UTF_8);
        String twice = URLEncoder.encode(once, StandardCharsets.UTF_8);
        System.out.println(once + " | " + twice);
        System.out.println(URLEncoder.encode("https://books.example.com/a?x=1&y=2", StandardCharsets.UTF_8));
    }
}

    첫 줄은 방금 손으로 계산한 바이트와 일치한다. 둘째 줄부터는 주의할 점이 여럿 들어 있다. URLEncoder는 이름과 달리 URI 일반 문법의 인코더가 아니다. Javadoc이 밝히듯 HTML 폼 인코딩, 곧 application/x-www-form-urlencoded 형식으로 바꾸는 도구다. 이 형식에서는 공백이 %20이 아니라 +가 된다. 그래서 데이터로서의 +는 공백과 구별되도록 %2B로, 쌍의 구분자인 &는 %26으로 바뀌었다. 넷째 줄에서는 비예약 문자인 ~가 %7E로 인코딩되고 *는 그대로 남았는데, 이것도 URI 일반 문법이 아니라 폼 인코딩의 문자 집합을 따른 결과다.

    공백의 두 표기는 쓰이는 자리가 다르다. +가 공백을 뜻하는 것은 폼 인코딩으로 해석되는 쿼리 문자열 안에서만이다. 경로에서 +는 그냥 더하기 기호다. 다섯째 줄이 이를 보여 준다. 구성 요소별로 값을 받는 URI 생성자는 경로의 공백을 %20으로 적었다. 경로에 넣을 값을 URLEncoder로 인코딩하면 공백이 +로 바뀌어 서버가 더하기 기호가 든 다른 경로로 읽게 된다.

    여섯째와 일곱째 줄은 디코딩의 순서 문제다. %2F는 /를 데이터로 쓴 것이므로 /a%2Fb/c의 세그먼트는 a/b와 c 두 개다. 그런데 전체를 먼저 디코딩해 /a/b/c로 만들면 세그먼트가 세 개로 보인다. 쿼리도 같다. title=1%262&page=3은 쌍이 두 개인데, 먼저 디코딩한 title=1&2&page=3에서는 세 개로 보인다. RFC 3986은 예약 문자를 퍼센트 인코딩한 것과 하지 않은 것이 동등하지 않다고 명시한다. 그러므로 올바른 순서는 언제나 "구분자로 먼저 자르고, 잘라 낸 조각을 디코딩한다"이다. 만들 때는 그 반대로, 각 값을 먼저 인코딩한 뒤 구분자로 이어 붙인다.

    마지막 두 줄은 실무에서 자주 겪는 두 상황이다. 이미 인코딩된 문자열을 한 번 더 인코딩하면 %가 %25로 바뀌어 100%2525가 된다. 받는 쪽이 한 번만 디코딩하면 100%25라는 엉뚱한 값이 남는다. 인코딩은 값이 URI에 들어가는 경계에서 한 번만 해야 한다. 그리고 URI 하나를 통째로 다른 URI의 쿼리 값으로 넣을 때는 마지막 줄처럼 :, /, ?, =, &가 모두 인코딩되어야 바깥 URI의 구조를 깨뜨리지 않는다.

    상대 참조와 정규화: 같은 자원, 다른 표기

    HTML 문서 안의 링크와 이미지 주소는 대부분 완전한 URI가 아니라 상대 참조다. 브라우저는 요청을 보내기 전에 상대 참조를 문서의 기준 URI(base URI)에 대해 해석해 절대 URI로 만든다. RFC 3986 4.2절은 상대 참조를 시작 문자에 따라 나눈다. //로 시작하면 스킴만 물려받는 네트워크 경로 참조, / 하나로 시작하면 스킴과 authority를 물려받는 절대 경로 참조, 그 밖에는 기준 경로의 위치에서 출발하는 상대 경로 참조다. #만으로 이루어진 참조는 같은 문서를 가리킨다.

    import java.net.URI;

public class Resolve {
    public static void main(String[] args) {
        URI base = URI.create("https://books.example.com/catalog/java/list.html?page=2");
        String[] refs = {
                "detail.html", "./detail.html", "../spring/list.html", "img/cover.png",
                "/cart", "//cdn.example.net/app.js", "#reviews", "https://pay.example.org/checkout"
        };
        for (String ref : refs) {
            System.out.printf("%-34s -> %s%n", ref, base.resolve(ref));
        }
        System.out.println(URI.create("https://books.example.com/a/./b/../c").normalize());
        System.out.println(base.resolve("?page=3"));
        System.out.println(base.resolve(""));
        System.out.println(base.resolve("../../../cart"));

    아홉째 줄부터 세 줄은 명세와 구현의 차이를 보여 주는 사례다. RFC 3986 5.4절의 예제에 따르면 쿼리만 있는 참조는 기준 경로를 유지한 채 쿼리만 바꾸고, 빈 참조는 프래그먼트를 뺀 기준 URI 그대로이며, 계층보다 많은 ..은 루트에서 멈춘다. 그 규칙대로라면 결과는 차례로 …/catalog/java/list.html?page=3, …/catalog/java/list.html?page=2, https://books.example.com/cart여야 한다. 그런데 OpenJDK 21의 java.net.URI는 위와 같이 다른 결과를 낸다. Javadoc이 밝히듯 이 클래스는 RFC 3986의 전신인 RFC 2396을 기준으로 정의되어 있기 때문이다. 브라우저는 또 다른 문서인 WHATWG URL 표준을 따른다. 경계 사례에서는 "URI를 다루는 도구들이 같은 답을 낸다"고 가정하면 안 된다.

    마지막 다섯 줄은 동등성 비교다. RFC 3986 6.2절과 RFC 9110 4.2.3절이 말하는 정규화를 모으면 이렇다. 스킴과 호스트는 소문자로, 퍼센트 인코딩의 16진수는 대문자로, 비예약 문자를 굳이 인코딩한 것은 디코딩하고, 점 세그먼트는 지우고, 기본 포트는 생략하고, 빈 경로는 /로 바꾼다. 이 기준으로 RFC 3986은 http://example.com, http://example.com/, http://example.com:/, http://example.com:80/을 모두 동등하다고 예시한다. 자바의 URI.equals는 이 가운데 일부만 한다. 스킴·호스트의 대소문자와 16진수의 대소문자는 무시하지만(첫째, 셋째 줄), 기본 포트와 빈 경로, 비예약 문자의 인코딩은 정규화하지 않는다(넷째, 다섯째 줄). 둘째 줄의 false는 정당하다. 경로는 대소문자를 구분하기 때문이다.

    문자열이 다르다고 다른 자원이 아니고, 라이브러리의 equals가 false라고 다른 자원인 것도 아니다. URI를 캐시의 키나 중복 판정, 접근 제어의 기준으로 쓸 때는 비교하기 전에 어떤 정규화를 거쳤는지부터 확인해야 한다.

    요청 흐름 1: URL에서 TCP 연결까지

    이제 문자열이 동작으로 바뀌는 과정을 따라간다. 사용자가 주소창에 다음 한 줄을 넣고 엔터를 눌렀다고 하자.

    https://books.example.com/catalog/search?keyword=jvm&page=2#result

    전체 흐름을 먼저 한 번 훑고, 단계별로 내려가 보자.

    1단계: 파싱

    브라우저는 입력을 앞 절의 규칙대로 자른다. 스킴은 https, 호스트는 books.example.com, 포트는 없음, 경로는 /catalog/search, 쿼리는 keyword=jvm&page=2, 프래그먼트는 result다. 포트가 없으므로 스킴의 기본값 443을 쓰기로 한다. 프래그먼트는 여기서 떼어 내 나중을 위해 보관한다. 이 시점에 브라우저는 "443번 포트에 TLS로 연결해야 한다"는 것까지 알지만, 연결할 상대의 IP 주소는 아직 모른다.

    2단계: 이름 해석

    호스트가 IP 주소 리터럴이면 이 단계는 필요 없다. 등록된 이름이면 01회에서 본 DNS 조회로 IP 주소를 얻는다. 여기서는 결과가 203.0.113.10이었다고 하자. 조회 결과는 일정 시간 캐시되므로 같은 이름에 대해 요청할 때마다 질의가 나가는 것은 아니다. 눈여겨볼 점은 DNS에 건네지는 것이 호스트 이름뿐이라는 사실이다. 경로와 쿼리는 이름 해석과 아무 관계가 없다.

    3단계: TCP 연결

    브라우저는 운영체제에 소켓을 요청하고 목적지 203.0.113.10의 443번 포트로 연결을 건다. 커널은 출발지 IP 주소와 비어 있는 임시 포트를 골라 붙이고 SYN을 보낸다. 서버가 SYN+ACK로 답하고 클라이언트가 ACK를 보내면 연결이 성립한다. 01회에서 본 3-way handshake다. 이제 이 연결은 출발지 IP, 출발지 포트, 목적지 IP, 목적지 포트의 네 값으로 식별된다. 예를 들어 (192.0.2.25, 51734, 203.0.113.10, 443)이다.

    여기까지 오는 데 쓰인 URI의 조각은 스킴, 호스트, 포트뿐이다. DNS 서버도, 패킷을 넘겨주는 라우터도, 서버의 TCP 계층도 경로와 쿼리가 무엇인지 모른다. 연결이라는 통로가 만들어졌을 뿐이고, 그 통로로 무엇을 요청할지는 아직 한 바이트도 전해지지 않았다.

    4단계: TLS 핸드셰이크

    스킴이 https이므로 브라우저는 방금 만든 TCP 연결 위에서 TLS 핸드셰이크를 수행한다. 이 과정에서 서버를 인증하고 암호화에 쓸 키를 합의한다. 그 뒤에 보내는 HTTP 메시지는 암호화된 채로 TCP에 실린다. 경로상의 장비는 패킷의 IP 주소와 포트는 볼 수 있지만 요청 줄과 헤더와 본문은 암호문으로만 본다. 스킴이 http였다면 이 단계가 없고, 다음 단계의 메시지가 평문 그대로 흘러간다. TLS의 내부 동작은 이 권의 범위 밖이다.

    브라우저가 요청마다 이 단계들을 모두 되풀이하는 것은 아니다. HTTP/1.1은 여러 요청과 응답이 연결 하나를 함께 쓰는 지속 연결(persistent connection)을 기본으로 한다. 같은 서버로 가는 다음 요청은 이미 열려 있는 연결을 재사용할 수 있다. 연결을 유지하는 것과 서버가 상태를 기억하지 않는 것의 관계는 03회에서 다룬다.
    브라우저가 URL을 받아 DNS 조회, TCP 연결, TLS, HTTP 요청과 응답을 차례로 수행하는 순서를 세 참여자 사이의 화살표로 보여 준다. 흰 배경의 시퀀스 다이어그램. 위쪽에 세 개의 참여자 상자를 가로로 배치한다. 왼쪽부터 "브라우저", "DNS", "서버 203.0.113.10:443". 각 상자에서 아래로 점선 생명선을 내린다. 위에서 아래로 다음 화살표를 순서대로 그리고 번호를 붙인다. (1) 브라우저 생명선 위의 자기 자신으로 돌아오는 작은 화살표, 라벨 "URL 파싱 · 포트 443 결정". (2) 브라우저에서 DNS로 실선 화살표 "books.example.com 의 주소는?", DNS에서 브라우저로 점선 화살표 "203.0.113.10". (3) 브라우저와 서버 사이에 세 개의 얇은 화살표 묶음 "SYN", "SYN+ACK", "ACK", 묶음 옆에 "TCP 연결". (4) 브라우저와 서버 사이 양방향 굵은 화살표 "TLS 핸드셰이크". (5) 브라우저에서 서버로 굵은 실선 화살표 "GET /catalog/search?keyword=jvm&page=2". (6) 서버에서 브라우저로 굵은 점선 화살표 "200 OK + HTML". (7) 브라우저 생명선 위의 자기 화살표 "렌더링 · #result 로 이동". 3번까지의 구간 왼쪽 여백에 세로 괄호로 "스킴·호스트·포트만 사용", 5번 이후 구간에 "경로·쿼리 사용" 이라고 적는다. 평면적이고 차분한 색조, 장식 없음. 연결이 만들어질 때까지는 스킴·호스트·포트만 쓰이고, 경로와 쿼리는 그 뒤 HTTP 메시지에 실린다.

    요청 흐름 2: HTTP 요청 메시지와 캡슐화

    5단계: 요청 메시지 만들기

    연결이 준비되면 브라우저는 HTTP 요청 메시지를 만든다. HTTP/1.1의 메시지 문법은 RFC 9112가 정한다. 메시지는 시작 줄 하나, 0개 이상의 헤더 필드 줄, 빈 줄 하나, 그리고 있을 수도 없을 수도 있는 본문으로 이루어지고, 줄은 CRLF로 끝난다. 요청의 시작 줄인 요청 줄(request line)은 메서드, 요청 대상(request target), HTTP 버전을 공백 하나씩으로 띄워 적는다.

    HTTP-message = start-line CRLF
               *( field-line CRLF )
               CRLF
               [ message-body ]

request-line = method SP request-target SP HTTP-version

    우리 예에서 만들어지는 메시지의 뼈대는 이렇다. 브라우저는 여기에 여러 헤더 필드를 더 붙이는데, 헤더는 07회의 주제다.

    GET /catalog/search?keyword=jvm&page=2 HTTP/1.1
Host: books.example.com

    요청 줄에 URI 전체가 들어가지 않는다는 점을 보자. 원 서버에 직접 보내는 요청에서 요청 대상은 경로와 쿼리만으로 이루어진 원본 형식(origin-form)이다. RFC 9112는 이때 URI의 경로가 비어 있으면 클라이언트가 /를 경로로 보내야 한다고 정한다. 스킴과 authority가 요청 줄에서 빠진 이유는 간단하다. 그 정보는 연결을 만드는 데 이미 쓰였고, 서버는 자기에게 온 연결이라는 사실로 그것을 안다고 가정했던 것이다.

    그런데 그 가정은 서버 하나가 호스트 이름 하나만 서비스할 때만 맞다. 같은 IP 주소와 포트에서 여러 호스트 이름의 사이트를 함께 서비스하면, TCP 연결만으로는 어느 이름을 향한 요청인지 알 수 없다. TCP가 아는 것은 IP 주소와 포트이지 이름이 아니다. 그래서 Host 헤더 필드가 있다. RFC 9112는 클라이언트가 모든 HTTP/1.1 요청 메시지에 Host를 보내야 하고, 그 값은 대상 URI의 authority와 같아야 한다고 정한다. 서버 쪽에는 Host가 없는 HTTP/1.1 요청에 400(Bad Request)으로 응답하라고 요구한다.

    요청 대상에는 원본 형식 외에 세 가지 형식이 더 있다. 프록시에 보내는 요청은 URI 전체를 적는 절대 형식(absolute-form)을 쓰고, 서버는 이 형식도 받아들여야 한다. CONNECT 요청은 호스트와 포트만 적는 authority 형식을, 서버 전체를 대상으로 하는 OPTIONS 요청은 * 하나만 적는 별표 형식을 쓴다. 일상적인 요청은 거의 모두 원본 형식이다.

    URI의 조각이 메시지의 어디로 가는지를 표로 정리하면 다음과 같다. 오른쪽 열은 HTTP/2의 경우다. HTTP/2는 요청 줄이라는 텍스트 한 줄 대신 :으로 시작하는 의사 헤더 필드(pseudo-header field)에 같은 정보를 싣는다. RFC 9113에 따르면 :path는 대상 URI의 경로와 쿼리를, :authority는 authority를 담는다. 표현 방식은 달라도 URI에서 뽑아 보내는 값은 같다.

    URI의 조각HTTP/1.1HTTP/2
    scheme메시지에 없음. 서버는 연결이 TLS인지로 판단:scheme

    URI 문자열의 조각마다 화살표를 내려, 그 조각이 DNS 질의, TCP 목적지, 요청 줄, Host 헤더 가운데 어디에 쓰이는지와 프래그먼트가 브라우저에 남는 것을 보여 준다. 흰 배경의 대응 다이어그램. 맨 위에 고정폭 글꼴로 "https://books.example.com/catalog/search?keyword=jvm&page=2#result" 를 한 줄로 적고 조각별로 옅은 색을 칠한다: "https" 파랑, "books.example.com" 초록, "/catalog/search?keyword=jvm&page=2" 주황, "#result" 회색. 아래쪽에 네 개의 상자를 가로로 놓는다. 첫째 상자 제목 "DNS 질의", 내용 "books.example.com → 203.0.113.10". 둘째 상자 제목 "TCP 연결", 내용 "목적지 203.0.113.10 : 443". 셋째 상자 제목 "HTTP 요청 메시지", 안에 두 줄의 고정폭 글 "GET /catalog/search?keyword=jvm&page=2 HTTP/1.1" 과 "Host: books.example.com". 넷째 상자 제목 "브라우저에 보관", 내용 "#result". 화살표: 파랑 조각에서 둘째 상자의 ": 443" 으로 "기본 포트" 라벨이 붙은 화살표. 초록 조각에서 첫째 상자로, 그리고 셋째 상자의 Host 줄로 각각 화살표. 주황 조각에서 셋째 상자의 첫 줄로 화살표. 회색 조각에서 넷째 상자로 점선 화살표, 라벨 "서버로 가지 않음". 평면적이고 차분한 색조. URI의 조각은 서로 다른 계층에서 한 번씩 쓰인다. 프래그먼트만 네트워크로 나가지 않는다.

    바이트가 선로에 실리기까지

    브라우저가 한 일은 이 메시지의 바이트를 소켓에 써 넣은 것이 전부다. 그 아래는 운영체제의 프로토콜 스택이 맡는다. 각 계층은 위에서 받은 데이터 앞에 자기 헤더를 붙여 아래로 내린다. 이것을 캡슐화(encapsulation)라 한다.

    [HTTP 메시지]   GET /catalog/search?keyword=jvm&page=2 HTTP/1.1 ...
                (https이면 TLS가 이 바이트를 암호화한다)
     |
     v   커널의 TCP: 바이트 스트림을 잘라 TCP 헤더를 붙인다
[TCP 세그먼트]  { 출발지 포트 51734, 목적지 포트 443, 순서 번호 } + HTTP 바이트
     |
     v   IP: IP 헤더를 붙인다
[IP 패킷]       { 출발지 IP 192.0.2.25, 목적지 IP 203.0.113.10 } + TCP 세그먼트
     |
     v   링크 계층: 프레임 헤더를 붙인다
[프레임]        { 다음 홉의 MAC 주소 } + IP 패킷

    이 그림에서 읽어야 할 것은 각 계층이 자기 헤더만 본다는 점이다. 경로상의 라우터는 IP 헤더의 목적지 주소를 보고 다음 홉을 정할 뿐, 그 안의 TCP 세그먼트나 HTTP 메시지는 해석하지 않는다. 프레임 헤더는 링크 하나를 건널 때마다 새로 붙고, 그 안의 IP 패킷이 목적지를 향해 전달된다. 서버의 TCP는 포트 번호로 연결을 찾아 바이트를 올려 줄 뿐이다. 우리가 공들여 분석한 경로와 쿼리는 가장 안쪽 상자에만 들어 있고, 그것을 뜻으로 읽는 것은 양 끝의 애플리케이션과 HTTP를 이해하는 중간 서버뿐이다.

    또 하나 중요한 사실은 TCP가 메시지의 경계를 모른다는 것이다. TCP가 제공하는 것은 순서가 보장되는 바이트 스트림이다. HTTP 메시지 하나가 여러 세그먼트로 나뉘어 갈 수도 있고, 받는 쪽이 읽기를 한 번 호출했을 때 메시지의 일부만 돌아올 수도 있다. 그래서 HTTP/1.1은 경계를 메시지 안에 스스로 적는다. 헤더 구획의 끝은 빈 줄이 알린다. 본문의 길이는 RFC 9112 6.3절의 규칙에 따라 Content-Length의 값이나 청크 전송 부호화로 정해지고, 응답에 길이 표시가 없으면 서버가 연결을 닫을 때까지 받은 바이트가 본문이 된다.

    HTTP 메시지가 아래 계층으로 내려가며 TCP 헤더, IP 헤더, 프레임 헤더가 차례로 앞에 붙는 모습을 네 개의 가로 띠로 보여 준다. 흰 배경의 계층 다이어그램. 위에서 아래로 네 개의 가로 띠를 계단처럼 배치하되, 아래로 갈수록 왼쪽으로 한 칸씩 길어진다. 첫째 띠: 주황색 상자 하나, 라벨 "HTTP 메시지", 안에 작은 고정폭 글씨 "GET /catalog/search?keyword=jvm&page=2 HTTP/1.1". 둘째 띠: 왼쪽에 파란 상자 "TCP 헤더 · 포트 51734 → 443", 오른쪽에 첫째 띠와 같은 폭의 주황 상자. 셋째 띠: 왼쪽에 초록 상자 "IP 헤더 · 192.0.2.25 → 203.0.113.10", 오른쪽에 둘째 띠 전체. 넷째 띠: 왼쪽에 회색 상자 "프레임 헤더 · 다음 홉 MAC", 오른쪽에 셋째 띠 전체. 각 띠의 왼쪽 바깥에 계층 이름을 적는다: "애플리케이션", "전송(TCP)", "인터넷(IP)", "링크". 오른쪽 바깥에 위에서 아래로 향하는 긴 화살표와 "보낼 때: 헤더를 붙인다", 그 옆에 아래에서 위로 향하는 화살표와 "받을 때: 헤더를 벗긴다". 평면적이고 차분한 색조. 캡슐화. URI의 경로와 쿼리는 가장 안쪽의 HTTP 메시지에만 들어 있다.

    서버가 요청을 받아 응답하기까지

    6단계: 서버 처리

    서버 호스트에 도착한 프레임은 보낼 때의 반대 순서로 풀린다. 커널이 프레임 헤더와 IP 헤더와 TCP 헤더를 차례로 해석하고, 네 값(출발지와 목적지의 IP 주소와 포트)으로 이 세그먼트가 속한 연결을 찾는다. 3-way handshake 때 이미 만들어진 그 연결의 수신 버퍼에 데이터가 순서대로 쌓인다. 443번 포트에서 연결을 기다리던 서버 프로그램은 연결을 넘겨받아 그 버퍼에서 바이트를 읽는다. 스프링 부트 애플리케이션이라면 내장 톰캣 같은 서블릿 컨테이너가 이 일을 한다.

    서버 프로그램은 빈 줄이 나올 때까지 읽어 헤더 구획을 얻고, 첫 줄을 공백으로 나눠 메서드와 요청 대상과 버전을 얻는다. 그러고는 클라이언트가 갖고 있던 대상 URI를 다시 조립한다. RFC 9112 3.3절이 그 절차를 정한다. 스킴은 서버 설정이나 신뢰하는 게이트웨이가 알려 준 값이 있으면 그것을 쓰고, 없으면 요청이 보안 연결로 왔는지에 따라 https 또는 http로 본다. authority는 Host에서, 경로와 쿼리는 요청 대상에서 가져온다. 결과는 https://books.example.com/catalog/search?keyword=jvm&page=2다. 브라우저가 갖고 있던 URI에서 프래그먼트만 빠진 것이다.

    그다음은 애플리케이션의 영역이다. 서버는 경로 /catalog/search를 보고 이 요청을 처리할 코드를 고르고, 쿼리 문자열을 &와 =로 잘라 디코딩해 keyword가 jvm이고 page가 2라는 것을 얻는다. 그 값으로 도서를 검색해 결과를 HTML로 만든다. 이 자원은 디스크에 놓인 파일이 아니라 요청이 올 때 계산되는 것이지만, 클라이언트에게는 구별되지 않는다. URI가 식별하는 것은 구현이 아니라 자원이기 때문이다.

    7단계: 응답

    서버는 응답 메시지를 만들어 같은 TCP 연결의 반대 방향으로 써 보낸다. 응답의 시작 줄인 상태 줄(status line)은 HTTP 버전, 상태 코드, 선택적인 사유 구절로 이루어진다. 그 뒤에 본문의 형식과 길이를 알리는 헤더 필드가 오고, 빈 줄, 본문이 이어진다. 이 바이트들도 요청과 똑같이 TCP 세그먼트와 IP 패킷으로 캡슐화되는데, 이번에는 출발지와 목적지가 뒤바뀐다. 응답 메시지의 실제 모습은 다음 절에서 직접 받아 본다.

    8단계: 렌더링과 추가 요청

    브라우저는 상태 줄에서 요청이 성공했는지를 확인하고, Content-Type 헤더로 본문을 어떻게 해석할지를 정한다. HTML이면 파싱해 화면에 그릴 구조를 만든다. 그 과정에서 <img src>, <link href>, <script src> 같은 참조를 만나면 앞에서 본 규칙대로 문서의 URI를 기준으로 절대 URI를 만들고, 각각에 대해 지금까지의 흐름을 다시 수행한다. 같은 서버의 자원이면 열려 있는 연결을 재사용할 수 있고, 다른 호스트의 자원이면 이름 해석과 연결부터 새로 한다. 웹 페이지 하나가 화면에 나오기까지는 요청 한 번이 아니라 여러 번이 오간다.

    마지막으로 브라우저는 처음에 떼어 두었던 프래그먼트를 꺼낸다. 받은 HTML에서 id가 result인 요소를 찾아 그 위치로 화면을 옮긴다. 주소 한 줄의 다섯 조각이 이렇게 모두 쓰였다.

    일상에서 가져온 비유관공서에서 서류 떼기

    큰 청사에 서류를 떼러 간다고 하자. 청사의 이름으로 지도에서 주소를 찾는 것이 DNS 조회, 그 주소의 건물에 들어가 정해진 창구 앞에 서는 것이 IP와 포트로 TCP 연결을 맺는 일이다. 창구에서 "주민등록 등본, 최근 5년 주소 변동 포함"이라고 말하는 것이 경로와 쿼리를 담은 요청이다. 받은 서류의 셋째 쪽을 펼쳐 보는 것은 창구 직원에게 말할 필요가 없는, 나 혼자 하는 일이다. 이것이 프래그먼트다. 비유가 맞지 않는 곳도 있다. 실제 서버는 한 창구(같은 IP와 포트)에서 여러 기관의 업무를 함께 볼 수 있어서 어느 기관에 온 것인지를 Host로 따로 말해야 하고, 서류 이름(경로)을 어떻게 해석할지도 창구마다 자유롭게 정한다.

    직접 확인: 소켓에 HTTP 메시지를 써 넣기

    지금까지의 설명이 맞다면 브라우저 없이도 TCP 연결에 올바른 글자를 써 넣기만 하면 서버가 응답해야 한다. JDK에 들어 있는 간단한 HTTP 서버(com.sun.net.httpserver.HttpServer)를 띄우고, HTTP 클라이언트 라이브러리를 쓰지 않고 Socket만으로 요청해 보자.

    import com.sun.net.httpserver.HttpServer;

import java.io.OutputStream;
import java.net.InetSocketAddress;
import java.net.Socket;
import java.nio.charset.StandardCharsets;

public class RawHttp {
    public static void main(String[] args) throws Exception {
        // 서버: 127.0.0.1의 18080번 포트에서 TCP 연결을 기다린다
        HttpServer server = HttpServer.create(new InetSocketAddress("127.0.0.1", 18080), 0);
        server.createContext("/", exchange -> {
            System.out.println("[서버] 메서드    = " + exchange.getRequestMethod());
            System.out.println("[서버] 요청 대상 = " + exchange.getRequestURI());
            System.out.println("[서버] Host      = " + exchange.getRequestHeaders().getFirst("Host"));
            byte[] body = "
    JVM 도서 3건
    ".getBytes(StandardCharsets.UTF_8);
            exchange.getResponseHeaders().set("Content-Type", "text/html; charset=UTF-8");
            exchange.sendResponseHeaders(200, body.length);
            try (OutputStream out = exchange.getResponseBody()) {
                out.write(body);
            }
        });
        server.start();

        // 클라이언트: TCP 연결을 맺고 HTTP 요청을 글자 그대로 써 보낸다
        try (Socket socket = new Socket("127.0.0.1", 18080)) {
            System.out.println("[클라이언트] 목적지 = " + socket.getRemoteSocketAddress());
            String request = "GET /catalog/search?keyword=jvm&page=2 HTTP/1.1\r\n"
                    + "Host: 127.0.0.1:18080\r\n"
                    + "Connection: close\r\n"
                    + "\r\n";
            OutputStream out = socket.getOutputStream();
            out.write(request.getBytes(StandardCharsets.US_ASCII));
            out.flush();

            byte[] bytes = socket.getInputStream().readAllBytes();
            System.out.println("[클라이언트] 받은 바이트 수 = " + bytes.length);
            System.out.println(new String(bytes, StandardCharsets.UTF_8));
        }
        server.stop(0);
    }
}

    JVM 도서 3건

    한 줄씩 추적해 보자. new Socket("127.0.0.1", 18080)이 반환되었다는 것은 3-way handshake가 끝나 연결이 성립했다는 뜻이다. 호스트를 IP 주소로 직접 적었으므로 DNS 조회는 없었다. 이어서 프로그램은 문자열 네 줄을 ASCII 바이트로 바꿔 소켓에 썼다. 첫 줄이 요청 줄, 다음 두 줄이 헤더 필드, 마지막의 \r\n 하나가 헤더 구획의 끝을 알리는 빈 줄이다. 서버가 출력한 세 줄은 서버가 그 바이트에서 정확히 메서드, 요청 대상, Host를 읽어 냈음을 보여 준다. HTTP 요청이란 TCP 연결 위에 약속된 형식으로 적은 글자라는 것이 확인된다.

    Connection: close는 이 실험을 위한 장치다. 앞에서 보았듯 HTTP/1.1은 지속 연결이 기본이어서, 이 헤더가 없으면 서버가 응답 뒤에도 연결을 열어 둔다. 그러면 스트림의 끝까지 읽는 readAllBytes()는 끝을 만나지 못하고 기다리게 된다. 이 헤더로 응답 뒤에 연결을 닫아 달라고 알렸기 때문에 읽기가 끝난다. 브라우저 같은 실제 클라이언트는 연결이 닫히기를 기다리지 않고 Content-length의 값만큼 읽고 멈춘다. TCP가 메시지 경계를 알려 주지 않는다는 말의 실제 모습이 이것이다.

    받은 140바이트를 세어 보면 메시지의 구조가 그대로 드러난다. 상태 줄 HTTP/1.1 200 OK가 15바이트에 CRLF 2바이트를 더해 17바이트다. 같은 방식으로 Date 줄이 37바이트, Content-type 줄이 40바이트, Content-length 줄이 20바이트이고, 빈 줄이 2바이트, 본문이 24바이트다. 합하면 140이다. 본문의 글자 수는 18자인데 Content-length는 24다. 한글 세 글자("도", "서", "건")가 UTF-8로 3바이트씩이어서 6바이트가 더해졌다. 이 헤더가 세는 단위는 문자가 아니라 바이트다.

    작은 관찰 하나를 더하자. 코드에서는 헤더 이름을 Content-Type으로 적었는데 JDK의 서버는 Content-type으로 내보냈다. HTTP에서 필드 이름은 대소문자를 구분하지 않으므로 둘은 같은 필드다. 그리고 이 프로그램에서 Host 줄을 빼고 보내면 JDK 21의 내장 서버는 핸들러를 부르지 않고 HTTP/1.1 400 Bad Request로 응답한다. 앞에서 본 RFC 9112의 요구 그대로다.

    이번에는 클라이언트를 JDK의 HttpClient로 바꾸고 프래그먼트가 붙은 URI를 준다. 서버 쪽 핸들러는 요청 대상과 Host를 출력한 뒤 본문 없는 204로 응답한다.

    import com.sun.net.httpserver.HttpServer;

import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;

public class ClientView {
    public static void main(String[] args) throws Exception {
        HttpServer server = HttpServer.create(new InetSocketAddress("127.0.0.1", 18080), 0);
        server.createContext("/", exchange -> {
            System.out.println("[서버] 요청 대상 = " + exchange.getRequestURI());
            System.out.println("[서버] Host      = " + exchange.getRequestHeaders().getFirst("Host"));
            exchange.sendResponseHeaders(204, -1);
            exchange.close();
        });
        server.start();

        URI uri = URI.create("http://127.0.0.1:18080/catalog/java/list.html?page=2#reviews");
        HttpClient client = HttpClient.newHttpClient();
        HttpResponse response = client.send(
                HttpRequest.newBuilder(uri).build(), HttpResponse.BodyHandlers.discarding());
        System.out.println("[클라이언트] 상태 코드 = " + response.statusCode());
        server.stop(0);
    }
}

[서버] Host      = 127.0.0.1:18080
[클라이언트] 상태 코드 = 204

    코드 어디에도 요청 줄이나 Host를 만드는 부분이 없다. 클라이언트 라이브러리가 URI를 분해해 호스트와 포트로 연결을 맺고, 경로와 쿼리로 요청 대상을, authority로 Host를 만들었다. 그리고 서버가 받은 요청 대상에는 #reviews가 없다. 프래그먼트는 클라이언트에서 떨어져 나갔다. 브라우저가 하는 일도 본질적으로 이와 같다.

    흔한 오해와 함정

    • "서버는 주소창의 URL 전체를 받는다." 원본 형식의 요청 줄에 실리는 것은 경로와 쿼리뿐이다. 호스트는 Host 헤더로 따로 오고, 스킴은 메시지에 없어 서버가 연결의 성격으로 추정하며, 프래그먼트는 오지 않는다. 서버 코드가 "전체 URL"을 돌려준다면 그것은 이 정보들로 다시 조립한 결과다.
    • "공백은 +로 쓴다." 폼 인코딩으로 해석되는 쿼리 문자열 안에서만 그렇다. 경로에서 +는 더하기 기호이고 공백은 %20이다. 쿼리에 값을 넣는 도구와 경로에 값을 넣는 도구를 구분해서 써야 한다.
    • "URL은 대소문자를 가리지 않는다." 스킴과 호스트만 그렇다. 경로와 쿼리는 대소문자를 구분하는 것이 명세의 기본이다.
    • "한글 주소는 한글 그대로 전송된다." 브라우저가 주소창에 한글을 보여 주더라도 요청 줄에 실리는 경로와 쿼리는 UTF-8 바이트를 퍼센트 인코딩한 ASCII이고, 한글 도메인 이름은 xn--로 시작하는 ASCII 이름으로 바뀌어 DNS에 질의된다.
    • "경로는 서버의 파일 경로다." 경로는 식별자의 일부일 뿐이다. 파일에 대응시키는 서버도 있지만, 대응 방식은 서버가 정하며 URI 명세는 관여하지 않는다. 경로에 ..을 넣어 의도하지 않은 파일에 닿으려는 공격이 가능한 것은 서버가 경로를 파일 경로로 옮기는 과정에서 정규화를 빠뜨렸을 때다.
    • "쿼리 문자열의 형식은 URI 표준이 정한다." RFC 3986은 쿼리의 범위와 허용 문자만 정한다. 이름=값을 &로 잇는 형식은 폼 인코딩의 규칙이고, 중복된 이름이나 값 없는 이름의 처리는 해석하는 쪽에 달려 있다.
    • "요청 한 번에 DNS 조회 한 번, 연결 한 번." 조회 결과는 캐시되고 연결은 재사용된다. 반대로 페이지 하나를 그리는 데는 요청이 여러 번 나간다. 요청 수, 연결 수, 조회 수는 서로 다른 값이다.

    다음 주제와의 연결

    이 장의 내용은 뒤의 회차에서 계속 바탕이 된다. 03회는 방금 직접 만들어 본 HTTP 메시지의 구조를 정식으로 다루고, 서버가 요청 사이의 상태를 기억하지 않는다는 무상태(stateless)와 연결을 유지하지 않는 모델이 무엇을 뜻하는지 살핀다. 04회와 05회의 메서드에서는 "자원은 URI로 식별하고, 그 자원에 할 일은 메서드로 표현한다"는 분업이 설계의 기준이 된다. 그 기준을 적용하려면 무엇이 경로에 들어가고 무엇이 쿼리에 들어가는지를 구별할 수 있어야 한다. 08회의 캐시는 URI를 기준으로 응답을 저장하므로, 쿼리까지 포함해 어떤 URI가 같은 것으로 취급되는지가 그대로 캐시 적중률의 문제가 된다.

    이 권 다음에 배울 서블릿과 스프링 MVC에서도 같은 조각들을 만난다. 서블릿 API의 HttpServletRequest에서 getRequestURI()는 요청 줄의 요청 대상 가운데 쿼리 앞까지를 돌려주고, getQueryString()은 쿼리 문자열을 돌려준다. Javadoc은 두 값 모두 컨테이너가 디코딩하지 않는다고 밝힌다. 구분자로 먼저 자른 뒤에 디코딩해야 한다는 이 장의 원칙이 API의 모양에 반영되어 있는 셈이다. 프레임워크가 제공하는 경로 변수와 요청 파라미터는 결국 이 경로와 쿼리를 잘라 디코딩한 값이다.
    URI·URL·URN
    URI는 자원을 식별하는 문자열의 총칭이다. 접근 방법(위치)까지 담은 것이 URL, 위치와 무관하게 유일하고 영속적인 이름이 URN이며 둘 다 URI에 포함된다.
    일반 문법
    scheme ":" hier-part [ "?" query ] [ "#" fragment ]. 왼쪽부터 처음 만나는 구분자로 자르므로 쿼리 안의 /와 ?는 데이터다.
    스킴과 authority
    스킴은 해석 규칙과 기본 포트(http 80, https 443)를 정하고, authority의 host와 port는 연결할 상대를 정한다. 스킴·호스트·포트의 묶음이 출처(origin)다.
    경로와 쿼리
    둘이 함께 서버 안의 자원을 식별한다. 경로는 계층적이고 대소문자를 구분하며, 쿼리의 이름=값 형식은 URI 명세가 아니라 폼 인코딩의 관례다.
    프래그먼트
    받은 표현 안의 위치를 가리키며 클라이언트만 사용한다. 요청을 보내기 전에 분리되므로 서버에 전송되지 않는다.
    퍼센트 인코딩
    문자를 UTF-8 바이트로 바꾸고 바이트마다 %XX로 적는다. 만들 때는 값을 인코딩한 뒤 이어 붙이고, 읽을 때는 구분자로 자른 뒤 디코딩한다.
    상대 참조와 정규화
    상대 참조는 기준 URI의 마지막 슬래시 뒤를 버리고 붙여 해석한다. 표기가 달라도 정규화하면 같은 URI가 있으며, 라이브러리마다 정규화 범위가 다르다.
    요청 흐름
    파싱 → 이름 해석 → TCP 연결 → (TLS) → HTTP 요청 → 서버 처리 → HTTP 응답 → 렌더링과 추가 요청. 연결까지는 스킴·호스트·포트만 쓰인다.
    요청 대상과 Host
    HTTP/1.1 요청 줄에는 경로와 쿼리만 실리고(origin-form), authority는 Host 헤더로 따로 간다. TCP 연결은 IP와 포트만 알기 때문이다.

    URI에 무엇을 넣을지는 보안 판단이기도 하다. TLS는 전송 구간에서 요청 줄을 암호화하지만, URI는 브라우저의 방문 기록과 북마크에 남고, 서버와 프록시의 접근 로그에 기록되며, 사람이 복사해 공유한다. RFC 9110의 보안 고려 사항도 URI는 공유되도록 만들어진 것이니 민감하거나 개인을 식별할 수 있는 정보를 넣지 말라고 권한다. 비밀번호나 장기간 유효한 토큰을 쿼리에 싣는 설계는 "HTTPS니까 괜찮다"로 정당화되지 않는다. 프래그먼트는 서버로 가지 않으니 안전하다고 여기기도 쉽지만, 방문 기록과 공유 경로에는 똑같이 남는다.

    서버가 자기 주소를 스스로 조립할 수 있다고 가정하면 운영 환경에서 어긋난다. 리버스 프록시나 로드 밸런서가 TLS를 끝내고 뒤의 서버와 평문으로 통신하면, 서버가 보는 연결은 보안 연결이 아니므로 스킴을 http로 판단한다. 그 결과 리다이렉트 주소나 절대 링크가 http://로 만들어지는 장애가 생긴다. RFC 9112가 스킴을 서버 설정이나 신뢰하는 게이트웨이가 준 값으로 정할 수 있다고 한 것이 이 상황을 위한 것이다. 다만 프록시가 전해 주는 정보를 받아들이는 설정은 그 프록시를 신뢰할 수 있을 때만 켜야 한다. 아무나 보낼 수 있는 헤더를 믿으면 주소 위조의 통로가 된다.

    정규화는 캐시 효율과 접근 제어 양쪽에 걸린다. 같은 자원을 가리키는 표기가 여럿이면 캐시가 조각나고 검색 엔진에는 중복 페이지로 보인다. 그래서 한 가지 표기를 정본으로 정하고 나머지는 리다이렉트로 모으는 설계를 한다. 접근 제어에서는 문제가 더 심각하다. 앞단의 필터가 정규화하지 않은 문자열로 경로를 검사하고 뒷단의 서버가 점 세그먼트를 지우거나 디코딩한 경로로 자원을 찾으면, 두 계층이 같은 요청을 다르게 읽는다. 검사와 처리가 같은 해석을 쓰는지 확인하는 것이 원칙이다.

    URI의 길이에는 명세상 상한이 없지만 현실의 구현에는 있다. RFC 9112는 최소한 8000옥텟 길이의 요청 줄을 지원하라고 권장할 뿐이고, 서버는 받아들일 수 없이 긴 요청 대상에 414(URI Too Long)로 응답할 수 있다. 검색 조건이 계속 늘어나는 화면처럼 쿼리가 커질 수 있는 기능은 이 한계를 염두에 두어야 한다. 조건을 본문으로 옮기면 길이 문제는 풀리지만 URI로 결과를 식별하고 공유하고 캐시하는 이점을 잃는다. 어느 쪽을 택할지는 04회와 05회의 메서드 선택과 함께 판단할 일이다.
  • http://shop.example.com:8080/items/42/reviews?sort=new&size=10#r7을 다섯 조각으로 나누고, (가) DNS에 질의되는 값, (나) TCP 연결의 목적지 포트, (다) HTTP/1.1 요청 줄 전체, (라) Host 헤더의 값, (마) 서버로 전송되지 않는 부분을 각각 적어라.
  • 문자열 커피 1+1을 (가) 폼 인코딩 방식의 쿼리 값으로, (나) 경로 세그먼트로 넣을 때의 인코딩 결과를 각각 적어라. "커"는 U+CEE4, "피"는 U+D53C다. UTF-8 바이트를 직접 계산해 보라.
  • 기준 URI가 https://books.example.com/catalog/java일 때와 https://books.example.com/catalog/java/일 때, 상대 참조 detail.html과 ../cart가 각각 어떤 절대 URI가 되는지 구하라. 결과가 달라지는 이유를 설명하라.
  • 로그인 뒤 돌아갈 주소를 넘기려고 /login?next=/orders?status=paid&page=2라는 링크를 만들었다. 그런데 로그인 뒤에 이동한 곳은 /orders?status=paid였고 2쪽이 아니라 1쪽이 나왔다. 원인을 URI 문법으로 설명하고 올바른 링크를 적어라.
  • https://books.example.com/catalog/java/로 받은 HTML이 style.css, img/a.png, img/b.png, //cdn.example.net/app.js를 참조한다. 네 참조의 절대 URI를 적고, 이 페이지를 그리기 위한 HTTP 요청의 수와 이름 해석이 필요한 서로 다른 호스트 이름의 수를 구하라(캐시는 비어 있다고 가정한다).
    •

    1. 스킴 http, authority shop.example.com:8080(호스트 shop.example.com, 포트 8080), 경로 /items/42/reviews, 쿼리 sort=new&size=10, 프래그먼트 r7이다. (가) DNS에는 호스트 이름 shop.example.com만 질의된다. (나) 포트가 명시되어 있으므로 기본값 80이 아니라 8080이다. (다) 요청 줄은 GET /items/42/reviews?sort=new&size=10 HTTP/1.1이다. 원본 형식이므로 경로와 쿼리만 들어간다. (라) Host의 값은 authority와 같은 shop.example.com:8080이다. (마) 프래그먼트 r7은 전송되지 않는다. 스킴도 HTTP/1.1 메시지에는 실리지 않는다.

    2. U+CEE4는 2진수로 1100 1110 1110 0100이다. 3바이트 틀에 4·6·6비트로 나눠 넣으면 1110 1100, 10 111011, 10 100100이므로 EC BB A4다. U+D53C는 1101 0101 0011 1100이고 같은 방식으로 ED 94 BC가 된다. (가) 폼 인코딩에서는 공백이 +, 데이터인 +가 %2B이므로 %EC%BB%A4%ED%94%BC+1%2B1이다. (나) 경로에서는 공백이 %20이고 +는 하위 구분자로서 그대로 쓸 수 있으므로 %EC%BB%A4%ED%94%BC%201+1이다. 경로에 (가)의 결과를 넣으면 서버는 공백이 아니라 더하기 기호가 든 이름으로 읽는다.

    3. 기준이 …/catalog/java이면 마지막 슬래시 뒤의 세그먼트 java가 버려져 detail.html은 https://books.example.com/catalog/detail.html, ../cart는 /catalog/에서 한 단계 올라가 https://books.example.com/cart가 된다. 기준이 …/catalog/java/이면 버릴 것이 빈 세그먼트뿐이어서 detail.html은 https://books.example.com/catalog/java/detail.html, ../cart는 https://books.example.com/catalog/cart가 된다. 상대 경로 참조는 기준 경로의 마지막 슬래시까지를 "현재 디렉터리"로 삼기 때문에, 끝 슬래시 하나가 현재 위치를 한 단계 바꾼다.

    4. URI는 왼쪽부터 처음 만나는 구분자로 잘린다. 이 링크의 쿼리는 첫 ? 뒤 전체인 next=/orders?status=paid&page=2이고, 폼 인코딩 규칙으로 &에서 자르면 next의 값은 /orders?status=paid, page의 값은 2인 두 개의 파라미터가 된다. page=2가 돌아갈 주소의 일부가 아니라 /login의 파라미터로 읽힌 것이다. 값으로 넣을 URI 안의 예약 문자를 인코딩해야 한다. 올바른 링크는 /login?next=%2Forders%3Fstatus%3Dpaid%26page%3D2다. 서버가 next의 값을 디코딩하면 원래의 /orders?status=paid&page=2가 복원된다.

    5. 기준 경로가 슬래시로 끝나므로 상대 경로 참조는 그 뒤에 그대로 붙는다. https://books.example.com/catalog/java/style.css, https://books.example.com/catalog/java/img/a.png, https://books.example.com/catalog/java/img/b.png이고, 네트워크 경로 참조는 스킴만 물려받아 https://cdn.example.net/app.js가 된다. HTTP 요청은 HTML 한 번과 하위 자원 네 번을 합해 다섯 번이다. 이름 해석이 필요한 호스트 이름은 books.example.com과 cdn.example.net 두 개다. 요청 수와 조회 수가 다르다는 점, 그리고 같은 호스트로 가는 네 번의 요청은 연결을 재사용할 수 있다는 점을 확인하면 된다.

     https://books.example.com/a?next=/b?c#d/e?f에서 쿼리 구성 요소는 무엇인가? next=/b next=/b?c next=/b?c#d/e?f c 쿼리는 처음 만나는 ? 뒤에서 시작해 처음 만나는 # 직전에서 끝난다. 그 안에 다시 나오는 /와 ?는 구분자가 아니라 데이터이므로 next=/b?c다. # 뒤의 d/e?f는 통째로 프래그먼트이고, 그 안의 ?도 쿼리를 시작시키지 않는다. HTTP/1.1 요청에 Host 헤더 필드가 반드시 있어야 하는 근본 이유는 무엇인가? TCP 연결은 IP 주소와 포트로만 식별되고 원본 형식의 요청 줄에는 authority가 없어서, 같은 IP와 포트를 쓰는 여러 호스트 이름 가운데 어느 것을 향한 요청인지 메시지 안에서 알려야 하기 때문이다. DNS 서버가 Host 헤더를 읽어 IP 주소를 찾기 때문이다. 라우터가 Host 헤더를 보고 패킷을 보낼 경로를 고르기 때문이다. 서버가 응답을 돌려보낼 클라이언트의 주소를 Host에서 얻기 때문이다. 이름은 DNS 조회에서 IP 주소로 바뀐 뒤 사라지고, TCP 연결과 요청 줄 어디에도 호스트 이름이 남지 않는다. 서버가 한 주소에서 여러 이름을 서비스하려면 메시지에 이름이 실려야 한다. DNS 조회는 HTTP 메시지가 만들어지기 전에 끝나고, 라우터는 IP 헤더만 보며, 응답을 돌려보낼 주소는 TCP 연결의 출발지 IP와 포트로 이미 정해져 있다. 사용자가 https://shop.example.com/guide#refund를 열었는데 서버의 접근 로그에는 /guide만 기록되었다. 이유로 옳은 것은? TLS가 프래그먼트 부분만 따로 암호화해서 서버가 복호화하지 못하기 때문이다. 프래그먼트가 DNS 조회 단계에서 소비되기 때문이다. 클라이언트가 요청을 보내기 전에 프래그먼트를 URI에서 분리하고, 요청의 대상 URI에 포함하지 않기 때문이다. 서버가 프래그먼트를 받기는 하지만 로그에 쓸 때 잘라 내는 것이 표준 동작이기 때문이다. RFC 3986은 프래그먼트가 역참조 전에 분리되어 사용자 에이전트만 처리한다고 정하고, RFC 9110은 대상 URI가 프래그먼트를 제외한다고 정한다. 서버는 프래그먼트를 받은 적이 없으므로 기록할 것이 없다. TLS는 메시지 전체를 암호화할 뿐 조각을 가려 다루지 않고, DNS에는 호스트 이름만 전달된다. 값 a b+c를 폼 인코딩 방식의 쿼리 파라미터 값으로 넣을 때 올바른 결과와 그 이유는? a%20b+c. 공백만 인코딩하면 되고 +는 하위 구분자라 그대로 두어도 원래 값으로 복원된다. a+b+c. 공백과 더하기 기호는 같은 문자로 취급되므로 구별할 필요가 없다. a+b%2Bc. 폼 인코딩에서 +는 공백을 뜻하므로, 데이터인 더하기 기호는 %2B로 적어야 구별된다. a b%2Bc. 공백은 비예약 문자여서 그대로 쓸 수 있다. 폼 인코딩은 공백을 +로 적고, 해석할 때 +를 공백으로 되돌린다. 따라서 원래 값에 있던 +를 그대로 두면 받는 쪽은 공백으로 읽는다. 첫째 보기의 a%20b+c를 폼 방식으로 디코딩하면 a b c가 되어 값이 바뀐다. 공백은 비예약 문자가 아니며 URI에 그대로 쓸 수 없다. HTTP/1.1 메시지가 헤더의 끝을 빈 줄로, 본문의 길이를 Content-Length 등으로 스스로 표시해야 하는 이유는? TCP는 순서가 보장되는 바이트 스트림만 제공하고 메시지의 경계는 보존하지 않으므로, 어디까지가 한 메시지인지를 상위 프로토콜이 정해야 하기 때문이다. IP 패킷 하나에 HTTP 메시지 하나가 정확히 실리는데, 그 대응을 수신 측 IP 계층이 검증해야 하기 때문이다. 포트 번호만으로는 요청과 응답을 구별할 수 없기 때문이다. DNS 응답의 길이와 HTTP 본문의 길이를 맞춰야 하기 때문이다. TCP는 보낸 쪽이 몇 번에 나눠 썼는지를 받는 쪽에 알려 주지 않는다. 메시지 하나가 여러 세그먼트로 나뉘거나 한 번의 읽기에 일부만 돌아올 수 있으므로, HTTP가 빈 줄과 길이 정보로 경계를 정한다. IP 패킷과 HTTP 메시지는 일대일로 대응하지 않으며, DNS는 이 문제와 관계가 없다.
    URI(Uniform Resource Identifier)
    자원을 식별하는 문자열. 스킴, authority, 경로, 쿼리, 프래그먼트로 이루어지며 문법은 RFC 3986이 정한다.
    authority
    URI에서 // 뒤부터 다음 /, ?, # 전까지. 선택적인 userinfo, 호스트, 선택적인 포트로 이루어진다.
    출처(origin)
    스킴, 호스트, 포트의 묶음. 세 값이 모두 같아야 같은 출처다.
    예약 문자(reserved character)
    URI에서 구분자로 쓰일 수 있는 문자. 데이터로 쓰려면 퍼센트 인코딩해야 하며, 인코딩한 것과 하지 않은 것은 동등하지 않다.
    퍼센트 인코딩(percent-encoding)
    바이트 하나를 %와 16진수 두 자리로 적는 방법. 비 ASCII 문자는 UTF-8 바이트로 바꾼 뒤 적용한다.
    폼 인코딩(application/x-www-form-urlencoded)
    이름=값 쌍을 &로 잇고 공백을 +로 적는 형식. HTML 폼 전송에서 유래했고 WHATWG URL 표준이 정의한다.
    상대 참조(relative reference)
    스킴이 없는 URI 참조. 기준 URI에 대해 해석해야 절대 URI가 된다.
    요청 대상(request target)
    HTTP/1.1 요청 줄에서 메서드와 버전 사이에 오는 값. 일반 요청에서는 경로와 쿼리만 적는 원본 형식(origin-form)을 쓴다.
    대상 URI(target URI)
    요청이 향하는 자원의 절대 URI. 프래그먼트는 포함하지 않으며, 서버는 요청 대상과 Host와 연결 정보로 이를 재구성한다.
    캡슐화(encapsulation)
    각 계층이 위 계층의 데이터 앞에 자기 헤더를 붙여 아래로 내리는 것. HTTP 메시지는 TCP 세그먼트, IP 패킷, 프레임 순으로 싸인다.
