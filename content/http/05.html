    메서드는 정했는데, 데이터는 어디에 싣는가

    04회에서 메서드가 요청의 의도를 나타낸다는 것을 봤다. GET은 조회, POST는 처리 요청, PUT은 교체, PATCH는 부분 변경, DELETE는 삭제이고, 여기에 안전(safe), 멱등(idempotent), 캐시 가능(cacheable)이라는 속성이 붙는다. 그런데 의도만으로는 요청이 완성되지 않는다. "회의실을 조회한다"에는 몇 층의 회의실인지가, "예약을 등록한다"에는 어느 방을 누가 무슨 일로 쓰는지가 따라와야 한다. 이 회차의 첫 번째 질문은 그 데이터를 요청 메시지의 어디에, 어떤 형식으로 싣느냐다.

    이 질문이 사소하지 않은 이유는 HTTP 메시지가 결국 TCP 연결 위를 흐르는 바이트의 나열이기 때문이다. 서버는 받은 바이트 가운데 어디부터 어디까지가 데이터이고 그것을 어떤 규칙으로 풀어야 하는지를 메시지 자체에서 알아내야 한다. 클라이언트와 서버가 이 규칙을 다르게 이해하면 값이 깨지거나 비어서 도착한다. 폼으로 보낸 값이 서버에서 null로 보이는 일, 한글이나 + 기호가 엉뚱한 문자로 바뀌는 일, 필터에서 본문을 한 번 읽었더니 뒤쪽 코드가 빈 본문을 받는 일은 모두 이 층에서 일어난다.

    두 번째 질문은 설계다. 데이터를 싣는 방법을 알았다면 "어떤 URI에 어떤 메서드로 보낼 것인가"를 정해야 한다. 같은 등록이라도 POST로 할 수 있고 PUT으로 할 수도 있다. 둘의 차이는 취향이 아니라 새로 만들어지는 자원의 식별자를 누가 정하느냐에서 나오고, 그 차이는 네트워크 장애 때 재시도가 안전한가로 이어진다. 회차의 뒤쪽 절반은 회의실 예약 시스템을 예로 이 판단을 따라간다.

    요청 메시지에서 데이터가 실리는 두 자리

    03회에서 본 요청 메시지의 구조를 다시 꺼내 보자. 요청 줄, 헤더 필드, 빈 줄, 본문이다. 이 가운데 애플리케이션이 자유롭게 데이터를 실을 수 있는 자리는 두 곳이다. 하나는 요청 줄의 요청 대상(request target)에 들어 있는 URI의 쿼리(query)이고, 다른 하나는 빈 줄 뒤에 오는 본문이다. RFC 9110은 이 본문을 콘텐츠(content)라고 부른다.

    POST /reservations?notify=true HTTP/1.1      ← 요청 줄: 메서드, 요청 대상(경로 + "?" + 쿼리), 버전
Host: api.example.com                        ← 헤더: 메시지와 본문에 대한 메타데이터
Content-Type: application/json               ←   본문을 무엇으로 해석할지
Content-Length: 59                           ←   본문이 몇 바이트인지
                                             ← 빈 줄: 헤더의 끝
{"room":"A-301","title":"주간 회의","attendees":[7,12]}      ← 본문(content): 옥텟의 나열

            자리 ①  쿼리   : notify=true           (URI 의 일부)
            자리 ②  본문   : {"room": ... }        (URI 바깥, Content-Type 이 형식을 알림)

    경로와 헤더에도 값이 실리기는 한다. 그러나 역할이 다르다. 경로는 어떤 자원인지를 계층적으로 가리키는 이름이고, 헤더는 메시지와 본문, 그리고 클라이언트에 관한 메타데이터다. 사용자가 입력한 검색 조건이나 등록할 예약 내용 같은 애플리케이션의 데이터는 쿼리 아니면 본문으로 간다. 그래서 클라이언트에서 서버로 데이터를 보내는 방법은 크게 둘, 쿼리 파라미터를 통한 전송과 메시지 본문을 통한 전송으로 나뉜다.

    쿼리는 URI의 일부다. 그래서 쿼리에 실린 데이터는 "무엇을 요청하는가"를 식별하는 데 참여하고, URI가 닿는 모든 곳(캐시, 북마크, 로그)에 함께 간다. 본문은 URI 바깥에 있다. 형식은 Content-Type이 알려 주고 크기에 여유가 있지만, 그 요청이 무엇을 가리키는지에는 관여하지 않는다. "조회 조건은 쿼리로, 등록하거나 변경할 내용은 본문으로"라는 관례는 이 차이 하나에서 나온다.

    요청 메시지 한 통을 요청 줄, 헤더, 빈 줄, 본문으로 나누고, 데이터가 실리는 자리가 쿼리와 본문 두 곳임을 강조한다. 쿼리는 URI에 속하고 본문은 Content-Type이 설명한다는 관계를 보여 준다. 깔끔한 기술 문서용 평면 다이어그램. 흰 배경. 가운데에 세로로 쌓인 네 개의 가로 띠로 HTTP 요청 메시지를 그린다. 맨 위 띠에는 고정폭 글꼴로 "POST /reservations?notify=true HTTP/1.1" 을 적고 그중 "?notify=true" 부분만 주황색으로 강조한다. 두 번째 띠에는 "Content-Type: application/json" 과 "Content-Length: 59" 두 줄을 적는다. 세 번째 띠는 얇은 빈 띠이며 라벨 "빈 줄". 네 번째 띠는 파란색으로 강조하고 안에 "{"room":"A-301", ...}" 를 적는다. 왼쪽에는 띠 이름 라벨 "요청 줄", "헤더", "본문" 을 세로로 배치한다. 오른쪽에는 설명 상자 두 개: 주황색 상자 "자리 1: 쿼리 — URI의 일부" 에서 맨 위 띠의 강조 부분으로 화살표, 파란색 상자 "자리 2: 본문 — URI 바깥" 에서 네 번째 띠로 화살표. 두 번째 띠의 "Content-Type" 에서 네 번째 띠로 점선 화살표를 그리고 라벨 "형식을 알림" 을 붙인다. 장식 없이 선과 글자만, 한국어 라벨은 따옴표 안 문구 그대로. 데이터가 실리는 자리는 쿼리와 본문 두 곳이다. 쿼리는 URI에 속하고, 본문의 형식은 Content-Type 헤더가 알려 준다.

    문법이 정한 것과 관례가 정한 것

    02회에서 본 RFC 3986의 문법으로 쿼리는 첫 번째 ? 다음부터 # 앞 또는 URI의 끝까지다. 문법이 정하는 것은 그 안에 올 수 있는 문자뿐이다. ABNF로는 query = *( pchar / "/" / "?" )이고, 쿼리 안에서는 /와 ?도 데이터로 쓸 수 있다. 이름=값을 &로 잇는 모양은 이 문법에 없다. RFC 3986 §3.4는 쿼리가 "key=value" 쌍의 형태로 자주 쓰인다고 언급할 뿐이다.

    그 관례에 실제 규칙을 준 것은 HTML 폼이다. 폼이 값을 직렬화하는 형식에 application/x-www-form-urlencoded라는 이름이 붙었고, 지금은 WHATWG URL 표준이 직렬화와 파싱 절차를 정의한다. 이 표준은 이 형식이 오랜 세월 구현상의 우연과 타협이 쌓인 결과라고 스스로 밝힌다. 그런데도 HTML 폼 때문에 널리 쓰이고 있어 그대로 규정해 둔 것이다. 직렬화 절차는 짧다.

    1. 이름과 값을 각각 인코딩한다. ASCII 영문자와 숫자, 그리고 *, -, ., _ 네 문자는 그대로 둔다.
    2. 공백은 +로 바꾼다.
    3. 나머지 문자는 지정한 인코딩(기본은 UTF-8)의 바이트로 바꾼 뒤 바이트마다 %XX로 적는다.
    4. 인코딩한 이름과 값을 =로 붙이고, 쌍과 쌍 사이에 &를 넣는다.

    파싱은 그 반대다. 입력을 &로 자르고, 빈 조각은 버린다. 조각마다 첫 번째 =를 찾아 앞을 이름, 뒤를 값으로 삼고, =가 없으면 조각 전체가 이름이며 값은 빈 문자열이다. 그다음 +를 공백으로 바꾸고, %XX를 바이트로 되돌린 뒤 UTF-8로 해석한다. 결과는 맵이 아니라 (이름, 값) 쌍의 목록이라는 점에 주의하자. 같은 이름이 여러 번 나올 수 있고 나온 순서가 보존된다. tag=a&tag=b는 덮어쓰기가 아니라 값이 두 개인 파라미터다.

    + 와 %20: 두 인코딩 규칙이 만나는 곳

    02회의 퍼센트 인코딩은 URI 일반 규칙이었다. 거기서 공백은 %20이고 +는 그냥 +라는 문자다. 폼 형식은 여기에 규칙 하나를 더해 +를 공백의 표기로 쓴다. 자바 표준 라이브러리에는 두 규칙이 모두 들어 있다. URLEncoder는 이름과 달리 URL 전체가 아니라 폼 형식의 값 하나를 인코딩하는 도구이고(Javadoc이 "HTML 폼 인코딩을 위한 유틸리티"라고 소개한다), 구성 요소를 따로 받는 java.net.URI의 생성자와 toASCIIString()은 URI 규칙에 따라 퍼센트 인코딩한다.

    import java.net.URI;
import java.net.URLDecoder;
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;

public class EncodingRules {
    public static void main(String[] args) throws Exception {
        String name = "회의실 A";

        // 폼 형식(application/x-www-form-urlencoded): 공백은 +
        System.out.println(URLEncoder.encode(name, StandardCharsets.UTF_8));

        // URI 일반 규칙(RFC 3986): 공백은 %20
        URI uri = new URI("http", "example.com", "/meeting rooms", "name=" + name, null);
        System.out.println(uri.toASCIIString());

        // 폼 파서는 + 를 공백으로 되돌린다
        System.out.println(URLDecoder.decode("1+1=2", StandardCharsets.UTF_8));
        System.out.println(URLDecoder.decode("1%2B1%3D2", StandardCharsets.UTF_8));
    }
}

1+1=2

    한글 세 글자는 두 규칙에서 똑같이 UTF-8 아홉 바이트가 되어 %XX 아홉 개로 적힌다. 달라지는 것은 공백뿐이다. 서버의 폼 파서는 %20도 +도 공백으로 되돌리므로 첫째 줄과 둘째 줄의 값은 서버에서 같은 문자열로 도착한다. 문제가 되는 것은 셋째 줄이다. 값에 진짜 +가 들어 있는데 인코딩하지 않고 쿼리에 넣으면 서버는 그것을 공백으로 읽는다. 국가 번호가 붙은 전화번호, Base64 문자열, 수식처럼 +가 들어갈 수 있는 값은 반드시 %2B로 보내야 한다. 쿼리 문자열을 문자열 이어 붙이기로 직접 만들 때 가장 자주 나오는 버그다.

    URI의 일부라는 사실이 가져오는 결과

    첫째, 쿼리는 식별에 참여한다. /rooms?floor=3과 /rooms?floor=4는 서로 다른 URI다. 캐시는 메서드와 대상 URI를 기본 키로 삼아 응답을 저장하므로(08회) 두 응답은 따로 저장된다. 북마크와 링크 공유도 URI 단위로 이루어진다. 검색 결과 화면의 주소를 복사해 동료에게 보내면 같은 결과가 열리는 것은 검색 조건이 URI 안에 들어 있기 때문이다.

    둘째, 쿼리는 흔적을 남긴다. URI는 브라우저의 방문 기록, 서버의 액세스 로그, 중간 프록시의 로그에 기록된다. RFC 9110 §17.9는 URI가 공유되라고 만든 것이지 보호되라고 만든 것이 아니라는 점을 분명히 하고, 민감한 폼 데이터에는 데이터를 URI가 아닌 본문에 싣는 POST가 선호된다고 적는다. 비밀번호, 토큰, 개인 식별 번호를 쿼리에 넣지 않는 이유다. HTTPS를 쓰면 전송 구간에서는 요청 줄까지 암호화되지만, 양 끝에서는 복호화된 URI가 그대로 로그와 기록에 남는다.

    셋째, 쿼리는 길이의 제약을 받는다. HTTP 명세는 URI 길이의 상한을 정하지 않는다. RFC 9110 §4.1은 송신자와 수신자 모두 최소 8000옥텟 길이의 URI를 지원하라고 권장할 뿐이고, 실제 한도는 구현이 정한다. Tomcat 10.1의 HTTP 커넥터는 요청 줄과 헤더를 합친 크기를 maxHttpRequestHeaderSize로 제한하는데, 지정하지 않으면 maxHttpHeaderSize의 기본값인 8192바이트가 된다. 한도가 있는 이유는 서버의 동작 순서에 있다. 서버는 요청 줄과 헤더를 끝까지 읽어야 이 요청을 누구에게 넘길지 정할 수 있으므로 그 부분을 담을 버퍼를 요청마다 잡는다. Tomcat 문서는 이 값을 키우면 지정한 크기 전체가 요청마다 할당되어 동시 요청 수만큼 힙 사용이 늘어난다고 경고한다. 서버가 감당하려는 길이를 넘는 URI에 대해서는 414(URI Too Long)라는 상태 코드가 마련되어 있다.

    쿼리는 봉투 겉면에 적은 글씨, 본문은 봉투 속 내용물에 가깝다. 겉면에 적은 것은 배달 과정에 관여하는 모든 사람이 보고 장부에 옮겨 적는다. 그래서 주소처럼 "어디로 가는 무엇인지"를 가리는 정보만 겉면에 쓴다. 다만 비유는 두 곳에서 깨진다. HTTPS에서는 겉면에 해당하는 요청 줄도 전송 중에는 암호화되고, 본문이라고 해서 받는 쪽 서버가 못 보는 것도 아니다. 차이는 비밀 유지 능력이 아니라 "기록되고 공유되는 것이 정상인 자리인가"에 있다.

    메시지 본문: Content-Type이 해석 규칙을 정한다

    HTTP의 눈에 본문은 헤더 구역 뒤에 오는 옥텟의 흐름일 뿐이다(RFC 9110 §6.4). 그 안이 문자인지 이미지인지, 어디에서 끊어 읽어야 하는지 HTTP는 알지 못한다. 그래서 본문에는 두 가지 정보가 헤더로 따라붙는다.

    • 어디까지가 본문인가. Content-Length는 본문의 길이를 옥텟 수의 십진수로 알린다. TCP는 메시지 경계가 없는 바이트 스트림이므로(01회) 수신자는 이 숫자를 보고 정확히 그만큼만 읽는다. HTTP/1.1에는 길이를 미리 알 수 없을 때 쓰는 청크 전송 방식도 있지만 원리는 같다. 본문의 끝은 본문 안이 아니라 본문 바깥의 프레이밍 정보가 정한다.
    • 무엇으로 해석할 것인가. Content-Type은 본문의 미디어 타입을 알린다. 같은 바이트열이라도 이 값에 따라 폼 필드의 목록이 되기도, JSON 문서가 되기도, 사진 한 장이 되기도 한다.

    Content-Type이 없으면 어떻게 될까. RFC 9110 §8.3에 따르면 수신자는 application/octet-stream이라고 가정하거나 데이터를 조사해 타입을 추측할 수 있다. 서버 쪽 프레임워크는 대개 추측하지 않는다. 처리할 수 없는 형식의 본문을 받은 서버가 요청을 거절할 때 쓰는 상태 코드가 415(Unsupported Media Type)다. 본문을 보내는 클라이언트는 Content-Type을 정확히 적어야 하고, 서버는 그 값에 맞는 해석기를 고른다. 요청 본문에 주로 쓰이는 형식은 셋이다.

    미디어 타입본문의 모양값의 인코딩어울리는 데이터

    multipart/form-data경계 문자열로 나뉜 여러 파트. 파트마다 헤더가 있다없다. 바이트를 그대로 싣는다파일, 바이너리와 텍스트의 혼합

    같은 데이터를 다섯 가지로 보내 보기

    설명만으로는 감이 오지 않으니 실제 바이트를 보자. 아래 프로그램은 두 부분으로 되어 있다. 아래쪽 serve는 02회의 소켓 예제처럼 ServerSocket으로 연결을 받아 요청 바이트를 그대로 출력하는 덤프 서버다. 위쪽 main은 JDK의 HttpClient로 다섯 가지 요청을 보낸다. 쿼리 파라미터, 폼 본문, JSON 본문, multipart 본문, 그리고 본문이 달린 GET이다.

    import java.io.*;
import java.net.*;
import java.net.http.*;
import java.net.http.HttpRequest.BodyPublishers;
import java.net.http.HttpResponse.BodyHandlers;
import java.nio.charset.StandardCharsets;

public class WireDump {
    static int count = 0;

    public static void main(String[] args) throws Exception {
        try (ServerSocket server = new ServerSocket(0)) {
            Thread t = new Thread(() -> serve(server));
            t.setDaemon(true);
            t.start();

            HttpClient client = HttpClient.newBuilder()
                    .version(HttpClient.Version.HTTP_1_1).build();
            String base = "http://localhost:" + server.getLocalPort();

            // 1) 쿼리 파라미터
            String q = "floor=3&name=" + URLEncoder.encode("회의실 A", StandardCharsets.UTF_8);
            send(client, HttpRequest.newBuilder(URI.create(base + "/rooms?" + q)).GET().build());

            // 2) 폼 본문 (application/x-www-form-urlencoded)
            String form = "room=A-301"
                    + "&title=" + URLEncoder.encode("주간 회의", StandardCharsets.UTF_8)
                    + "&memo=" + URLEncoder.encode("1+1=2 & 끝", StandardCharsets.UTF_8);
            send(client, HttpRequest.newBuilder(URI.create(base + "/reservations"))
                    .header("Content-Type", "application/x-www-form-urlencoded")
                    .POST(BodyPublishers.ofString(form)).build());

            // 3) JSON 본문
            String json = "{\"room\":\"A-301\",\"title\":\"주간 회의\",\"attendees\":[7,12]}";
            send(client, HttpRequest.newBuilder(URI.create(base + "/reservations"))
                    .header("Content-Type", "application/json")
                    .POST(BodyPublishers.ofString(json)).build());

            // 4) multipart/form-data (경계 문자열을 직접 정한다)
            String b = "XyZ123";
            String multipart =
                    "--" + b + "\r\n"
                    + "Content-Disposition: form-data; name=\"title\"\r\n"
                    + "\r\n"
                    + "주간 회의\r\n"
                    + "--" + b + "\r\n"
                    + "Content-Disposition: form-data; name=\"agenda\"; filename=\"agenda.txt\"\r\n"
                    + "Content-Type: text/plain\r\n"
                    + "\r\n"
                    + "1. budget\n2. hiring\r\n"
                    + "--" + b + "--\r\n";
            send(client, HttpRequest.newBuilder(URI.create(base + "/reservations"))
                    .header("Content-Type", "multipart/form-data; boundary=" + b)
                    .POST(BodyPublishers.ofString(multipart)).build());

            // 5) 본문이 달린 GET
            send(client, HttpRequest.newBuilder(URI.create(base + "/rooms"))
                    .header("Content-Type", "application/json")
                    .method("GET", BodyPublishers.ofString("{\"floor\":3}")).build());
        }
    }

    static void send(HttpClient client, HttpRequest request) throws Exception {
        client.send(request, BodyHandlers.discarding());
    }

    static void serve(ServerSocket server) {
        while (true) {
            try (Socket s = server.accept()) {
                InputStream in = s.getInputStream();
                ByteArrayOutputStream head = new ByteArrayOutputStream();
                int c;
                while ((c = in.read()) != -1) {                    // 빈 줄(CRLF CRLF)까지가 헤더
                    head.write(c);
                    if (head.toString(StandardCharsets.ISO_8859_1).endsWith("\r\n\r\n")) break;
                }
                String headText = head.toString(StandardCharsets.ISO_8859_1);
                int length = 0;
                for (String line : headText.split("\r\n")) {
                    if (line.toLowerCase().startsWith("content-length:")) {
                        length = Integer.parseInt(line.substring(15).trim());
                    }
                }
                byte[] body = in.readNBytes(length);                // Content-Length 만큼만 본문
                System.out.println("===== 요청 " + (++count) + " =====");
                System.out.print(headText);
                System.out.println(new String(body, StandardCharsets.UTF_8));
                System.out.println("(본문 " + body.length + "바이트)\n");
                s.getOutputStream().write(
                        "HTTP/1.1 200 OK\r\nContent-Length: 0\r\nConnection: close\r\n\r\n"
                                .getBytes(StandardCharsets.US_ASCII));
            } catch (IOException e) {
                return;
            }
        }
    }
}

    먼저 serve가 하는 일을 보자. 한 바이트씩 읽다가 \r\n\r\n, 즉 빈 줄을 만나면 헤더가 끝났다고 판단한다. 그다음 헤더에서 Content-Length를 찾아 그 숫자만큼만 더 읽는다. 서버가 본문의 끝을 아는 방법은 이것뿐이다. 본문의 내용을 들여다보고 끝을 추측하지 않으며, 메서드가 무엇인지도 보지 않는다. 이 관찰은 뒤에서 다시 쓰인다. 처음 세 요청의 출력은 다음과 같다. 포트 번호는 실행마다 다르고 User-Agent의 버전은 JDK에 따라 다르다.

    ===== 요청 1 =====
GET /rooms?floor=3&name=%ED%9A%8C%EC%9D%98%EC%8B%A4+A HTTP/1.1
Host: localhost:55449
User-Agent: Java-http-client/21.0.13


(본문 0바이트)

===== 요청 2 =====
POST /reservations HTTP/1.1
Content-Length: 83
Host: localhost:55449
User-Agent: Java-http-client/21.0.13
Content-Type: application/x-www-form-urlencoded

room=A-301&title=%EC%A3%BC%EA%B0%84+%ED%9A%8C%EC%9D%98&memo=1%2B1%3D2+%26+%EB%81%9D
(본문 83바이트)

===== 요청 3 =====
POST /reservations HTTP/1.1
Content-Length: 59
Host: localhost:55449
User-Agent: Java-http-client/21.0.13
Content-Type: application/json

{"room":"A-301","title":"주간 회의","attendees":[7,12]}
(본문 59바이트)

    요청 1에는 본문도 Content-Length도 Content-Type도 없다. 데이터는 전부 요청 줄 안에 있다. 요청 2의 본문은 요청 1의 쿼리와 형식이 같다. 이름=값이 &로 이어져 있고, 공백은 +, 한글은 %XX다. 폼 본문이란 쿼리 문자열을 URI에서 떼어 본문 자리로 옮긴 것이라고 봐도 된다. 그래서 값 안에 있던 +, =, &가 각각 %2B, %3D, %26으로 바뀌었다. 바꾸지 않으면 구분자와 데이터를 가릴 수 없기 때문이다.

    길이를 세어 보면 형식의 성격이 드러난다. "주간 회의"는 UTF-8로 한글 네 글자 12바이트에 공백 1바이트, 모두 13바이트다. 요청 3의 JSON은 이 13바이트를 그대로 싣는다. 요청 2의 폼 형식에서는 한글 한 글자의 3바이트가 %XX 세 개, 즉 9바이트가 되므로 같은 값이 37바이트(9 × 4 + + 1)를 차지한다. 폼 본문 83바이트는 room=A-301 10, &title= 7, 값 37, &memo= 6, 메모 값 23을 더한 것이다. ASCII 영숫자가 아닌 바이트는 세 배가 된다는 이 성질이 파일 전송에서 문제가 된다.

    JSON 본문의 문자 인코딩은 따로 협상하지 않는다. RFC 8259는 닫힌 생태계 밖에서 교환하는 JSON 텍스트를 UTF-8로 인코딩하라고 요구하고, application/json 미디어 타입에는 charset 파라미터를 정의하지 않았다. 요청 3이 Content-Type: application/json만으로 한글을 온전히 전달하는 근거다.

    본문이 달린 GET은 왜 피하는가

    다섯 번째 요청은 GET에 본문을 붙인 것이다. 출력은 이렇다.

    ===== 요청 5 =====
GET /rooms HTTP/1.1
Content-Length: 11
Host: localhost:55449
User-Agent: Java-http-client/21.0.13
Content-Type: application/json

{"floor":3}
(본문 11바이트)

    전송은 된다. 메시지에 본문이 있는지, 얼마나 긴지는 Content-Length 같은 프레이밍 정보가 정하고 메서드는 관여하지 않기 때문이다. RFC 9110 §9.3.1도 요청 메시지의 프레이밍은 메서드와 독립적이라고 적는다. 우리 덤프 서버가 메서드를 보지 않고 Content-Length만큼 읽은 것과 같은 이야기다.

    그러나 같은 절은 곧바로 제동을 건다. GET 요청으로 받은 본문에는 일반적으로 정의된 의미가 없고, 그 본문이 요청의 의미나 대상을 바꿀 수 없으며, 요청 스머글링 공격에 악용될 수 있어 어떤 구현은 그런 요청을 거부하고 연결을 닫을 수도 있다는 것이다. 그래서 클라이언트는 원 서버(origin server)에 직접 보내는 요청이고 그 서버가 지원한다고 미리 밝힌 경우가 아니라면 GET에 본문을 만들지 말아야 한다(SHOULD NOT).

    이유를 GET의 의미에서 찾을 수 있다. GET은 "대상 URI가 가리키는 자원의 현재 표현을 달라"는 요청이다. 무엇을 달라는지는 URI가 전부 말해야 한다. 캐시가 메서드와 URI를 키로 응답을 저장하는 것도 이 전제 위에 서 있다. 본문에 조건을 실어 보내면 본문만 다른 두 GET 요청을 캐시는 같은 요청으로 취급하고, 한쪽의 응답을 다른 쪽에 돌려줄 수 있다. 클라이언트와 서버 사이에 놓인 프록시나 HTTP 라이브러리가 GET의 본문을 전달한다는 보장도 없다.

    그러면 조회 조건이 쿼리에 담기 어려울 만큼 크고 복잡할 때는 어떻게 하는가. 흔한 타협은 검색을 POST로 보내는 것이다. 본문에 조건을 자유롭게 실을 수 있는 대신 안전하고 캐시 가능하다는 GET의 약속과, 주소를 복사해 같은 결과를 다시 여는 능력을 포기한다. RFC 9110이 414(URI Too Long)가 발생하는 드문 상황의 예로 클라이언트가 POST 요청을 긴 쿼리가 달린 GET으로 잘못 바꾼 경우를 드는 것도 같은 맥락이다. 참고로 DELETE의 본문도 GET과 마찬가지로 일반적으로 정의된 의미가 없다(§9.3.5).

    네 가지 전송 상황

    쿼리와 본문이라는 두 자리, 그리고 메서드를 조합하면 클라이언트가 서버에 데이터를 보내는 상황을 넷으로 정리할 수 있다.

    상황메서드데이터가 실리는 자리형식
    정적 데이터 조회GET없다. 경로만으로 충분하다해당 없음
    동적 데이터 조회GET쿼리이름=값 관례
    HTML 폼 전송GET 또는 POSTGET이면 쿼리, POST면 본문urlencoded 또는 multipart/form-data
    HTTP API 전송GET, POST, PUT, PATCH, DELETEGET이면 쿼리, 그 외에는 본문주로 application/json

    정적 데이터 조회

    이미지, 스타일시트, 미리 만들어 둔 문서처럼 서버가 저장해 둔 그대로 돌려주는 자원이다. 요청마다 달라지는 조건이 없으므로 경로만으로 자원이 정해지고, 쿼리도 본문도 필요 없다. GET /static/floor-map.png HTTP/1.1이 전부다. 서버가 하는 일은 경로를 저장소의 한 파일에 대응시키는 것이다. 같은 URI에 대한 응답이 누구에게나 같으므로 캐시하기에 가장 좋은 대상이기도 하다.

    동적 데이터 조회

    검색 결과나 목록처럼 요청의 조건에 따라 서버가 결과를 계산해 만드는 자원이다. 조건은 쿼리 파라미터로 보낸다. 쓰임은 대개 세 가지로, 결과를 걸러 내는 필터(filter), 순서를 정하는 정렬(sort), 일부만 잘라 받는 페이지(page)다. GET /rooms?floor=3&capacity=8&sort=name&page=2는 "3층에 있고 8명이 들어가는 회의실을 이름순으로 정렬한 두 번째 페이지"다. 조회이므로 GET을 쓴다. GET이어서 안전하고 캐시할 수 있으며, 조건이 URI 안에 있어서 링크로 공유할 수 있다.

    HTML 폼 전송

    브라우저에서 사용자가 값을 입력하고 제출 버튼을 누르는 경우다. 여기서 요청 메시지를 만드는 주체는 개발자의 코드가 아니라 브라우저이고, 브라우저는 WHATWG HTML 표준의 폼 제출 알고리즘을 따른다. 알고리즘의 뼈대는 이렇다.

    GET 폼부터 보자. 아래 폼에 3과 "회의실 A"를 입력하고 제출하면 브라우저는 GET /rooms?floor=3&name=%ED%9A%8C%EC%9D%98%EC%8B%A4+A를 보낸다. 앞의 실험에서 요청 1로 본 것과 같은 요청 줄이다. 본문은 없다.

    여기에 함정이 둘 있다. 첫째, GET 제출에서 브라우저는 쿼리를 "덧붙이는" 것이 아니라 "설정"한다. action="/rooms?lang=ko"처럼 action에 이미 쿼리가 있으면 그 쿼리는 폼 데이터로 대체되어 사라진다. 고정으로 보낼 값은 type="hidden"인 input으로 폼 안에 넣어야 한다. 둘째, method에 put이나 delete를 적어도 오류가 나지 않는다. 올바르지 않은 값의 기본 동작이 GET이므로 폼 데이터가 쿼리에 실린 GET 요청이 조용히 나간다. HTML 폼이 만들 수 있는 요청은 GET과 POST뿐이다.

    GET 폼으로 등록이나 삭제 같은 변경 작업을 하면 안 되는 이유도 여기서 분명해진다. GET은 안전한 메서드, 즉 서버의 상태를 바꾸지 않는다고 약속된 메서드다. 브라우저와 중간 장비는 이 약속을 믿고 GET 요청을 사용자의 의도와 무관하게 다시 보내거나 미리 보낼 수 있다. 변경을 일으키는 폼은 POST로 보낸다.

    POST 폼은 enctype에 따라 본문 형식이 갈린다. enctype의 값은 application/x-www-form-urlencoded, multipart/form-data, text/plain 셋이고, 적지 않으면 첫 번째가 기본이다. 아래 폼에 A-301, 주간 회의, 1+1=2 & 끝을 입력해 제출하면 본문은 앞 실험의 요청 2와 같은 83바이트가 된다.

    
  
  
  
  

    POST /reservations HTTP/1.1
Host: booking.example.com
Content-Type: application/x-www-form-urlencoded
Content-Length: 83

room=A-301&title=%EC%A3%BC%EA%B0%84+%ED%9A%8C%EC%9D%98&memo=1%2B1%3D2+%26+%EB%81%9D
    하나의 폼 항목 목록이 method가 get이면 URL의 쿼리로, post이면 enctype에 따라 urlencoded 본문 또는 multipart 본문으로 바뀌는 분기를 보여 준다. 깔끔한 평면 순서도. 흰 배경, 왼쪽에서 오른쪽으로 흐른다. 맨 왼쪽에 폼을 나타내는 상자 "HTML 폼" 이 있고 그 안에 작은 입력 칸 두 개와 버튼 하나를 단순한 사각형으로 그린다. 오른쪽으로 화살표가 나가 상자 "항목 목록 (이름, 값)" 으로 이어진다. 그다음 마름모 분기 "method" 가 있다. 마름모 위쪽 가지에는 라벨 "get" 이 붙고 주황색 상자 "쿼리로 직렬화" 로 이어지며, 그 오른쪽 끝에 고정폭 글꼴의 결과 상자 "GET /rooms?floor=3" 이 있다. 마름모 아래쪽 가지에는 라벨 "post" 가 붙고 두 번째 마름모 "enctype" 으로 이어진다. 두 번째 마름모에서 두 갈래: 위 가지는 파란색 상자 "urlencoded 본문", 아래 가지는 초록색 상자 "multipart 본문" 으로 이어지고, 둘 다 오른쪽 끝의 결과 상자 "POST /reservations + 본문" 으로 모인다. 화살표는 얇은 실선, 색은 주황·파랑·초록 세 가지만 쓴다. 한국어 라벨은 따옴표 안 문구 그대로. 폼의 항목 목록은 하나지만 method와 enctype에 따라 쿼리, urlencoded 본문, multipart 본문 가운데 하나로 실린다.

    파일을 보낼 때: multipart/form-data

    urlencoded 형식은 파일에 맞지 않는다. 이유는 둘이다. 하나는 크기다. 이 형식에서 영숫자와 네 가지 기호, 그리고 공백을 뺀 나머지 바이트는 %XX 세 바이트가 된다. 바이트 값 256가지 가운데 한 바이트로 남는 것은 67가지(영숫자 62, 기호 4, +로 바뀌는 공백 1)뿐이므로, 바이트 값이 고르게 분포한 바이너리라면 평균 (67 × 1 + 189 × 3) ÷ 256 ≈ 2.5배로 불어난다. 다른 하나는 메타데이터다. 파일에는 내용 말고도 파일 이름과 미디어 타입이 따라다니는데, 이름=값 한 쌍에는 그것을 적을 자리가 없다. 실제로 파일 선택 input이 있는 폼을 urlencoded로 제출하면 브라우저는 파일의 내용이 아니라 이름만 값으로 보낸다.

    multipart/form-data는 이 두 문제를 본문을 여러 파트로 나누는 것으로 푼다. 폼에 enctype="multipart/form-data"를 적으면 된다. 앞 실험의 요청 4가 그 모양을 손으로 만든 것이다. 실제 브라우저는 경계 문자열을 임의로 만들어 쓴다는 점만 다르다.

    ===== 요청 4 =====
POST /reservations HTTP/1.1
Content-Length: 214
Host: localhost:55449
User-Agent: Java-http-client/21.0.13
Content-Type: multipart/form-data; boundary=XyZ123

--XyZ123
Content-Disposition: form-data; name="title"

주간 회의
--XyZ123
Content-Disposition: form-data; name="agenda"; filename="agenda.txt"
Content-Type: text/plain

1. budget
2. hiring
--XyZ123--

(본문 214바이트)
    Content-Type: multipart/form-data; boundary=XyZ123     ← 경계 문자열을 헤더의 파라미터로 알린다

--XyZ123                                               ← 구분선: "--" + 경계 문자열
Content-Disposition: form-data; name="title"           ← 파트 헤더: 어느 폼 필드인가
                                                       ← 빈 줄: 파트 헤더의 끝
주간 회의                                               ← 파트 내용: 인코딩 없이 바이트 그대로
--XyZ123                                               ← 다음 파트의 시작
Content-Disposition: form-data; name="agenda"; filename="agenda.txt"
Content-Type: text/plain                               ← 이 파트만의 미디어 타입
                                                       ← 빈 줄
1. budget                                              ← 파일의 바이트 그대로
2. hiring
--XyZ123--                                             ← 닫는 구분선: 끝에 "--" 가 하나 더 붙는다

    구조를 보면 작은 HTTP 메시지 여러 개가 본문 안에 들어 있는 모양이다. 파트마다 헤더가 있고, 빈 줄이 있고, 내용이 있다. 규칙은 RFC 7578이 정한다. 경계 문자열(boundary)은 Content-Type의 필수 파라미터이고, 구분선은 줄바꿈(CRLF)과 --와 경계 문자열로 만든다. 각 파트에는 Content-Disposition: form-data 헤더가 반드시 있어야 하며 그 안에 폼 필드 이름을 담은 name 파라미터가 필요하다. 파일이면 filename 파라미터를 함께 넣는 것이 권장된다. 파트의 Content-Type은 선택이고 생략하면 text/plain으로 본다. 한 필드에 파일을 여러 개 고르면 같은 name을 가진 파트가 파일 수만큼 생긴다.

    파트 내용은 인코딩하지 않는다. "주간 회의"는 요청 2에서 37바이트였지만 여기서는 UTF-8 13바이트 그대로다. 대신 파트마다 구분선과 헤더라는 고정 비용이 붙는다. 텍스트 필드 두세 개뿐인 폼이라면 urlencoded 쪽이 작고, 바이너리 파일이 들어가면 multipart 쪽이 훨씬 작다. 한 가지 제약은 구분선이 파트 내용 안에 나타나면 안 된다는 것이다. 수신자는 길이를 미리 듣는 것이 아니라 본문을 훑으며 구분선을 찾아 파트를 자르기 때문이다. 그래서 송신자는 내용과 겹치지 않을 문자열을 경계로 고른다.

    본문 하나가 구분선으로 잘린 두 개의 파트로 이루어지고, 파트마다 헤더와 빈 줄과 내용이 있다는 것, 그리고 경계 문자열이 바깥 Content-Type 헤더에서 선언된다는 것을 보여 준다. 깔끔한 평면 구조도. 흰 배경. 위쪽에 가로로 긴 회색 상자가 있고 고정폭 글꼴로 "Content-Type: multipart/form-data; boundary=XyZ123" 이 적혀 있다. 그 아래에 세로로 긴 큰 상자가 있고 라벨은 "본문". 큰 상자 안에는 위에서 아래로 다음 요소가 쌓인다: 주황색 얇은 띠 "--XyZ123", 파란색 상자(라벨 "파트 1: 텍스트 필드") 안에 세 칸 "파트 헤더", "빈 줄", "주간 회의", 다시 주황색 얇은 띠 "--XyZ123", 초록색 상자(라벨 "파트 2: 파일") 안에 세 칸 "파트 헤더 + filename", "빈 줄", "파일 바이트", 마지막으로 진한 주황색 얇은 띠 "--XyZ123--". 위쪽 회색 상자의 "boundary=XyZ123" 부분에서 세 개의 주황색 띠로 점선 화살표를 그리고 라벨 "구분선" 을 붙인다. 맨 아래 띠 옆에 작은 라벨 "닫는 구분선". 장식 없이 선과 글자만, 한국어 라벨은 따옴표 안 문구 그대로. multipart 본문은 구분선으로 잘린 파트의 나열이다. 파트는 저마다 헤더와 내용을 갖고, 내용은 인코딩 없이 그대로 실린다.

    HTTP API 전송

    네 번째는 사람이 폼을 제출하는 것이 아니라 프로그램이 직접 요청을 만드는 경우다. 서버가 다른 서버를 호출할 때, 모바일 앱이 서버와 통신할 때, 웹 페이지의 자바스크립트가 화면 전환 없이 서버에 요청할 때가 여기에 든다. 요청을 코드가 만들므로 폼의 제약이 없다. GET과 POST뿐 아니라 PUT, PATCH, DELETE를 모두 쓸 수 있고 본문 형식도 자유롭게 고른다.

    이때 본문 형식으로 JSON이 주로 쓰이는 까닭은 표현력이다. urlencoded는 문자열 쌍이 한 줄로 늘어선 평평한 목록이어서 중첩된 구조나 타입을 담을 표준적인 방법이 없다. JSON은 객체 안에 객체와 배열을 넣을 수 있고 숫자, 불리언, null을 문자열과 구분한다. 앞의 예에서 참석자 목록 "attendees":[7,12]는 JSON에서는 숫자 배열이지만, 폼 형식이라면 attendees=7&attendees=12처럼 같은 이름을 반복하는 관례에 기대야 하고 값은 모두 문자열로 도착한다. 조회는 여전히 GET과 쿼리 파라미터로 하고, 등록과 변경은 POST, PUT, PATCH의 본문에 JSON을 싣는 것이 HTTP API의 일반적인 모습이다.

    서버는 이 데이터를 어떻게 꺼내는가

    이제 받는 쪽으로 내려가 보자. 쿼리 문자열과 urlencoded 본문은 형식이 같으므로 파서 하나로 둘 다 읽을 수 있다. WHATWG 표준의 파싱 절차를 그대로 옮기면 열 줄 남짓이다.

    import java.net.URLDecoder;
import java.nio.charset.StandardCharsets;
import java.util.ArrayList;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class FormParse {
    public static void main(String[] args) {
        String query = "tag=a&tag=b&flag";
        String body = "room=A-301&title=%EC%A3%BC%EA%B0%84+%ED%9A%8C%EC%9D%98&memo=1%2B1%3D2+%26+%EB%81%9D&tag=c";

        Map> params = new LinkedHashMap<>();
        parse(query, params);   // 쿼리 문자열을 먼저
        parse(body, params);    // 그다음 폼 본문을
        params.forEach((name, values) -> System.out.println(name + " = " + values));
    }

    static void parse(String input, Map> params) {
        for (String pair : input.split("&")) {                  // 1. & 로 자른다
            if (pair.isEmpty()) {
                continue;
            }
            int eq = pair.indexOf('=');                         // 2. 첫 번째 = 로 이름과 값을 나눈다
            String name = eq < 0 ? pair : pair.substring(0, eq);
            String value = eq < 0 ? "" : pair.substring(eq + 1);
            params.computeIfAbsent(decode(name), k -> new ArrayList<>())
                  .add('"' + decode(value) + '"');
        }
    }

    static String decode(String s) {                            // 3. + 는 공백, %XX 는 바이트, 바이트는 UTF-8
        return URLDecoder.decode(s, StandardCharsets.UTF_8);
    }
}
    tag = ["a", "b", "c"]
flag = [""]
room = ["A-301"]
title = ["주간 회의"]
memo = ["1+1=2 & 끝"]

    이름이 같은 tag는 쿼리의 두 값 뒤에 본문의 값이 붙어 세 개가 되었고, =가 없는 flag는 빈 문자열 값을 얻었다. 메모는 원래의 문자열 1+1=2 & 끝으로 돌아왔다. 값 안의 +, =, &를 미리 %XX로 바꿔 두었기에 구분자와 섞이지 않은 것이다. 순서가 중요하다. &와 =로 먼저 자르고 그다음에 디코딩해야 한다. 거꾸로 하면 %26이 &로 돌아온 뒤 구분자로 오인된다.

    서블릿 컨테이너의 요청 파라미터

    자바 웹 애플리케이션에서는 이 일을 서블릿 컨테이너가 한다. Jakarta Servlet 명세 §3.1은 쿼리 문자열의 데이터와 POST 본문의 데이터가 하나의 요청 파라미터 집합으로 합쳐지고, 쿼리 문자열의 데이터가 본문의 데이터보다 앞에 온다고 규정한다. 명세가 드는 예는 쿼리가 a=hello이고 본문이 a=goodbye&a=world이면 파라미터가 a=(hello, goodbye, world)가 된다는 것이다. 위 예제가 쿼리를 먼저 파싱한 것은 이 규칙을 흉내 낸 것이다. getParameter("a")는 첫 번째 값을 돌려주므로 hello이고, 전부를 얻으려면 getParameterValues("a")를 쓴다.

    애플리케이션 코드에서 request.getParameter("title")이 쿼리로 온 값과 폼 본문으로 온 값을 가리지 않고 돌려주는 이유가 이것이다. 두 자리는 다르지만 형식이 같고, 컨테이너가 합쳐서 내준다. 다만 본문 쪽이 파라미터로 들어오려면 조건이 있다. 명세 §3.1.1이 정한 조건은 네 가지다.

    1. 요청이 HTTP 또는 HTTPS 요청이다.
    2. 메서드가 POST다.
    3. Content-Type이 application/x-www-form-urlencoded다.
    4. 서블릿이 요청 객체에 대해 getParameter 계열 메서드를 처음으로 호출했다.

    네 번째 조건은 파싱이 게으르게(lazy) 일어난다는 뜻이다. 컨테이너는 누군가 파라미터를 달라고 할 때 비로소 본문을 읽어 파싱한다. 그리고 명세는 양쪽 경우를 모두 적어 두었다. 조건이 충족되지 않아 폼 데이터가 파라미터 집합에 들어가지 않았다면 그 데이터는 요청의 입력 스트림으로 여전히 읽을 수 있어야 한다. 조건이 충족되어 파라미터로 들어갔다면 그 데이터는 더 이상 입력 스트림에서 직접 읽을 수 없다.

    본문은 한 번만 읽을 수 있다

    왜 둘 중 하나만 되는가. 서블릿 API가 본문을 스트림으로 내주기 때문이다. 본문은 소켓에서 흘러 들어오는 바이트이고, 스트림은 읽으면 소비된다. 컨테이너가 본문 전체를 메모리에 올려 두고 몇 번이고 읽게 해 주는 모델이 아니다. 수 기가바이트짜리 업로드도 본문이라는 점을 생각하면 당연한 선택이다. 요청 줄과 헤더는 크기 한도가 있으니 미리 다 읽어 객체로 만들어 두지만, 본문은 필요한 쪽이 직접 읽어 가게 한다.

    여기서 실무에서 자주 만나는 증상 두 가지가 설명된다. 로깅용 필터가 입력 스트림에서 본문을 읽어 버리면 뒤에 있는 컨트롤러는 빈 본문을 받는다. 반대로 앞쪽 필터가 POST 폼 요청에 대해 getParameter를 한 번이라도 호출하면 컨테이너가 본문을 소비하므로, 뒤에서 입력 스트림으로 본문을 읽으려는 코드는 아무것도 얻지 못한다. 본문을 두 번 봐야 한다면 누군가 읽은 바이트를 복사해 보관해야 한다. 스프링의 ContentCachingRequestWrapper 같은 래퍼가 그 일을 한다.

    컨테이너의 한도와 문자 인코딩

    파라미터 파싱에는 따로 한도가 있다. Tomcat 10.1의 maxPostSize는 컨테이너가 요청 파라미터로 변환할 본문의 최대 바이트 수이며 기본값은 2,097,152바이트(2MiB)다. 문서가 강조하듯 이것은 POST 본문 전체의 크기 제한이 아니다. 컨테이너가 urlencoded 본문이나 multipart의 텍스트 파트를 파라미터로 바꿀 때에만 적용되고, 애플리케이션이 입력 스트림으로 직접 읽는 JSON 본문에는 적용되지 않는다. 본문을 파라미터로 바꾼다는 것은 그 내용을 통째로 메모리에 올려 문자열로 만든다는 뜻이므로 상한을 두는 것이다.

    문자 인코딩도 두 자리가 따로 정해진다. Tomcat 10.1에서 URI 바이트를 문자로 바꾸는 인코딩은 URIEncoding 속성이 정하고 기본값은 UTF-8이다. 본문 쪽은 요청의 문자 인코딩을 따르는데, Tomcat 문서는 그것을 알 수 없으면 기본 인코딩이 ISO-8859-1이라고 적는다. 쿼리로 보낸 한글은 멀쩡한데 폼 본문으로 보낸 한글만 깨지는 고전적인 증상의 원인이고, 요청의 문자 인코딩을 UTF-8로 지정하는 필터가 웹 애플리케이션에 들어가는 이유다.

    POST가 아닌 폼, 파일, 그리고 JSON

    조건 2 때문에 PUT이나 PATCH 요청의 본문에 폼 형식 데이터를 실어 보내면 서블릿 API의 getParameter로는 읽히지 않는다. 스프링은 이 틈을 메우는 FormContentFilter를 제공한다. 이 필터는 Content-Type이 application/x-www-form-urlencoded인 PUT, PATCH, DELETE 요청의 본문을 읽고, 요청 객체를 감싸 getParameter 계열 메서드로 그 값을 꺼낼 수 있게 한다.

    multipart/form-data는 별도의 경로로 처리된다. 서블릿 명세 §3.2에 따르면 요청을 처리하는 서블릿에 @MultipartConfig가 붙어 있거나 배포 서술자에 multipart-config가 있을 때 컨테이너가 본문을 파트로 나누고, getParts()와 getPart(name)으로 파트를 내준다. filename이 없는 파트, 즉 일반 텍스트 필드의 값은 getParameter로도 얻을 수 있다. 그래서 multipart 폼의 텍스트 필드도 애플리케이션에서는 쿼리 파라미터와 같은 방식으로 읽힌다.

    JSON 본문은 컨테이너의 파라미터 체계 밖에 있다. 컨테이너는 application/json 본문을 건드리지 않고, 애플리케이션이나 프레임워크가 입력 스트림을 읽어 직접 해석한다. 스프링 MVC의 애노테이션은 이 구분을 그대로 반영한다.

    스프링 MVC읽는 곳대응하는 전송 방식
    @RequestParam서블릿 요청 파라미터. 쿼리 파라미터 또는 폼 데이터GET 쿼리, POST 폼
    @ModelAttribute요청 파라미터를 객체의 프로퍼티에 바인딩GET 쿼리, POST 폼
    @RequestBody본문. Content-Type에 맞는 HttpMessageConverter가 객체로 변환JSON 등 HTTP API 본문

    JSON으로 보냈는데 @RequestParam이 값을 못 찾는 것, 폼으로 보냈는데 @RequestBody로 받으려다 415가 나는 것은 프레임워크의 변덕이 아니다. 데이터가 실린 자리와 형식이 읽으려는 방식과 맞지 않는 것이다. 요청 메시지를 덤프해 Content-Type과 본문을 눈으로 확인하면 대부분 바로 원인이 보인다.

    HTTP API 설계: 새 자원의 식별자는 누가 정하는가

    데이터를 싣는 방법은 정리됐다. 이제 회의실 예약 시스템의 API를 설계해 보자. 출발점은 앞 회차에서 본 원칙이다. URI는 자원을 식별하고, 그 자원에 무엇을 할지는 메서드가 말한다. 예약이라는 자원이 있다면 예약들의 목록은 /reservations, 예약 한 건은 /reservations/{id}가 된다. 조회, 등록, 수정, 삭제라는 행위는 URI에 적지 않고 메서드로 구분한다.

    기능메서드와 URI데이터
    예약 목록 조회GET /reservations?room=A-301&page=2쿼리
    예약 등록POST /reservationsJSON 본문
    예약 한 건 조회GET /reservations/{id}없음
    예약 수정PATCH /reservations/{id}JSON 본문(바꿀 부분만)
    예약 삭제DELETE /reservations/{id}없음

    수정에 PATCH를 쓴 것은 04회에서 본 차이 때문이다. PUT은 대상 자원의 상태를 본문의 표현으로 통째로 교체하므로 본문에서 빠진 필드는 없어진 것으로 처리된다. 제목만 바꾸려는 요청이라면 PATCH가 맞고, 예약 전체를 새 내용으로 갈아 끼우는 요청이라면 PUT이 맞다.

    이 표에서 가장 따져 볼 것은 등록이다. 등록은 아직 존재하지 않는 자원을 만드는 일이므로 "그 자원의 URI를 누가 정하는가"라는 질문이 생긴다. 답은 둘이고, 각각 다른 메서드와 다른 장애 특성으로 이어진다.

    POST 기반 등록: 서버가 식별자를 정하는 컬렉션

    클라이언트는 새 예약의 번호를 모른다. 그래서 새 예약의 URI가 아니라 예약들이 모여 있는 /reservations에 요청을 보낸다. 뜻은 "이 목록에 항목 하나를 추가해 달라"다. 서버는 요청을 처리하면서 식별자를 만들고(대개 데이터베이스의 시퀀스나 자동 증가 키다) 그것으로 새 자원의 URI를 만든다. 클라이언트에게 그 주소를 알려 주는 수단이 Location 헤더다.

    POST /reservations HTTP/1.1
Host: api.example.com
Content-Type: application/json
Content-Length: 59

{"room":"A-301","title":"주간 회의","attendees":[7,12]}
    HTTP/1.1 201 Created
Location: /reservations/1001
Content-Length: 0

    RFC 9110 §9.3.3은 POST 요청을 처리한 결과로 원 서버에 자원이 하나 이상 만들어졌다면 201(Created) 응답을 보내고, 거기에 새로 만든 주 자원의 식별자를 담은 Location 헤더를 넣어야 한다고 적는다(SHOULD). §10.2.2도 201 응답의 Location 값은 요청으로 생성된 주 자원을 가리킨다고 정의한다. 클라이언트는 이 값을 읽기 전에는 새 자원의 주소를 알 수 없다.

    /reservations처럼 서버가 관리하는 자원의 디렉터리를 컬렉션(collection)이라고 부른다. 컬렉션의 특징은 그 안에 무엇이 들어가고 각 항목의 URI가 무엇이 될지를 서버가 정한다는 것이다. 클라이언트는 추가를 요청할 뿐이다.

    이 방식의 약점은 POST가 멱등이 아니라는 데서 온다. 클라이언트가 응답을 받지 못했을 때를 생각해 보자.

    POST 기반 등록에서 응답이 유실되면

    │── POST /reservations ──────────────────────────────▶│
    │                                                      │ 예약 1001 저장

    │ 타임아웃. 처리됐는지 알 수 없다
    │── POST /reservations (같은 본문으로 재시도) ───────▶│

    │          ✕ ◀── 201 Created ─────────────────────────│   (응답이 도중에 사라짐)

    │◀── 204 No Content ──────────────────────────────────│

    클라이언트 입장에서 "요청이 서버에 닿지 못했다"와 "서버가 처리했지만 응답이 돌아오지 못했다"는 구분되지 않는다. 어느 쪽이든 응답이 오지 않고 타임아웃이 날 뿐이다. 멱등 메서드라면 같은 요청을 다시 보내면 된다. RFC 9110 §9.2.2가 멱등 메서드를 따로 구분하는 이유가 바로 통신 실패 때 요청을 자동으로 반복할 수 있다는 점이다. POST는 그렇지 않으므로 무심코 재시도하면 예약이 두 건 생긴다.

    대처는 세 갈래다. 재시도하기 전에 목록을 조회해 앞 요청이 처리됐는지 확인할 수 있다. 클라이언트가 요청마다 고유한 키를 만들어 함께 보내고, 서버가 같은 키를 가진 요청을 한 번만 처리하도록 만들 수도 있다. 마지막은 식별자를 클라이언트가 정하도록 설계를 바꾸는 것이고, 그것이 PUT 기반 등록이다.

    PUT 기반 등록: 클라이언트가 식별자를 정하는 스토어

    클라이언트가 새 자원의 URI를 이미 알고 있다면 그 URI에 직접 PUT을 보낼 수 있다. 예약 시스템에 개인 메모 기능이 있다고 하자. 앱은 네트워크가 끊긴 상태에서도 메모를 만들 수 있어야 하므로 식별자를 서버에 묻지 않고 스스로 만든다. 연결이 돌아오면 그 식별자를 URI에 넣어 올린다.

    PUT /notes/7f3a HTTP/1.1
Host: api.example.com
Content-Type: text/plain; charset=utf-8
Content-Length: 16

회의록 초안
    HTTP/1.1 201 Created

    RFC 9110 §9.3.4에 따르면 PUT은 대상 자원의 상태를 요청에 담긴 표현으로 생성하거나 교체해 달라는 요청이다. 대상 자원에 현재 표현이 없어서 새로 만들었다면 서버는 201(Created)을 보내야 하고, 있던 표현을 바꿨다면 200(OK)이나 204(No Content)를 보내야 한다(둘 다 MUST). 같은 절은 POST와 PUT의 근본적인 차이가 본문에 담긴 표현의 용도에 있다고 설명한다. POST에서는 대상 자원이 받은 표현을 자기 나름의 의미에 따라 처리한다. PUT에서는 받은 표현이 대상 자원의 상태를 대체한다. POST의 대상은 "처리를 맡을 자원"이고 PUT의 대상은 "만들어지거나 바뀔 자원 자신"이다.

    /notes처럼 클라이언트가 관리하는 자원 저장소를 스토어(store)라고 부른다. 스토어에서는 클라이언트가 URI를 정해 자원을 넣고, 꺼내고, 지운다. 서버는 받은 URI 자리에 저장할 뿐 URI를 새로 만들어 내지 않는다.

    이 방식의 이점은 앞의 그림 아래쪽에 있다. PUT은 멱등이므로 응답을 받지 못했을 때 같은 요청을 그대로 다시 보내면 된다. 첫 요청이 처리됐든 안 됐든 결과는 그 URI에 그 내용의 자원이 하나 있는 상태다. 대가는 덮어쓰기다. PUT은 전체 교체이므로 본문에서 빠뜨린 부분은 사라진다. 그리고 두 클라이언트가 같은 URI를 고르면 나중 요청이 앞선 자원을 지운다. 그래서 스토어를 여는 서버는 식별자의 형식을 강제하고, 그 URI가 요청한 사용자의 영역인지 검사해야 한다. 이미 있는 자원을 모르고 덮어쓰는 일은 조건부 요청으로 막을 수 있는데 이것은 08회에서 다룬다.

    조심할 것재시도로 인한 중복의도하지 않은 덮어쓰기

    실제 서비스의 등록은 대부분 POST 기반 컬렉션이다. 식별자 발급을 서버가 쥐고 있으면 유일성, 형식, 권한을 한곳에서 관리할 수 있기 때문이다. PUT 기반 스토어가 어울리는 경우는 따로 있다. 파일 이름이나 설정 키처럼 이름이 곧 식별자인 경우, 프로필 사진처럼 상위 자원에 하나만 딸린 자원이어서 /users/7/avatar처럼 주소가 미리 정해지는 경우, 그리고 앞의 메모처럼 클라이언트가 서버보다 먼저 자원을 만들어야 하는 경우다.

    왼쪽은 클라이언트가 컬렉션에 POST를 보내고 서버가 식별자를 만들어 Location으로 돌려주는 흐름, 오른쪽은 클라이언트가 스스로 정한 URI에 PUT을 보내는 흐름. 식별자를 만드는 주체가 어디인지가 한눈에 보여야 한다. 깔끔한 평면 시퀀스 다이어그램 두 개를 좌우로 나란히 배치. 흰 배경. 왼쪽 패널 제목 "POST 기반 등록 (컬렉션)", 오른쪽 패널 제목 "PUT 기반 등록 (스토어)". 각 패널에는 왼쪽에 "클라이언트", 오른쪽에 "서버" 라는 세로 생명선이 있다. 왼쪽 패널: 클라이언트에서 서버로 가는 화살표 "POST /reservations", 서버 생명선 위에 주황색 작은 상자 "식별자 생성: 1001", 서버에서 클라이언트로 돌아오는 화살표 "201 Created, Location: /reservations/1001". 오른쪽 패널: 클라이언트 생명선 위에 주황색 작은 상자 "식별자 생성: 7f3a", 클라이언트에서 서버로 가는 화살표 "PUT /notes/7f3a", 서버에서 클라이언트로 돌아오는 화살표 "201 Created". 두 패널에서 주황색 상자가 놓인 위치(왼쪽은 서버 쪽, 오른쪽은 클라이언트 쪽)가 대비되도록 같은 색과 크기로 그린다. 각 패널 아래에 한 줄 요약: 왼쪽 "두 번 보내면 자원이 둘", 오른쪽 "두 번 보내도 자원은 하나". 화살표는 얇은 실선, 글자는 고정폭 글꼴과 고딕을 섞어 쓴다. 한국어 라벨은 따옴표 안 문구 그대로. 식별자를 서버가 만들면 POST와 Location, 클라이언트가 만들면 PUT이다. 재시도했을 때의 결과가 여기서 갈린다.

    직접 확인: 컬렉션과 스토어를 한 서버에 올리기

    지금까지의 설계를 돌아가는 코드로 확인하자. JDK에는 jdk.httpserver 모듈이 제공하는 간단한 HTTP 서버 API(com.sun.net.httpserver)가 있다. 실제 서비스에는 서블릿 컨테이너를 쓰지만 메서드와 URI에 따라 상태 코드가 어떻게 갈리는지 보기에는 이것으로 충분하다. 예약은 컬렉션으로, 메모는 스토어로 만들고, 예약 취소를 위한 URI를 하나 더 둔다.

    import com.sun.net.httpserver.HttpExchange;
import com.sun.net.httpserver.HttpServer;
import java.io.IOException;
import java.net.InetSocketAddress;
import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpRequest.BodyPublishers;
import java.net.http.HttpResponse;
import java.net.http.HttpResponse.BodyHandlers;
import java.nio.charset.StandardCharsets;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ConcurrentSkipListMap;
import java.util.concurrent.atomic.AtomicLong;

public class ReservationApi {
    // 컬렉션: 식별자를 서버가 만든다
    static final Map reservations = new ConcurrentSkipListMap<>();
    static final AtomicLong sequence = new AtomicLong(1000);
    // 스토어: 식별자를 클라이언트가 정한다
    static final Map notes = new ConcurrentHashMap<>();

    public static void main(String[] args) throws Exception {
        HttpServer server = HttpServer.create(new InetSocketAddress("localhost", 0), 0);
        server.createContext("/reservations", ReservationApi::handleReservations);
        server.createContext("/notes/", ReservationApi::handleNotes);
        server.start();
        String base = "http://localhost:" + server.getAddress().getPort();

        call(base, "POST", "/reservations", "{\"room\":\"A-301\"}");
        call(base, "POST", "/reservations", "{\"room\":\"A-301\"}");
        call(base, "GET", "/reservations", null);
        call(base, "PUT", "/notes/7f3a", "v1");
        call(base, "PUT", "/notes/7f3a", "v1");
        call(base, "GET", "/notes/7f3a", null);
        call(base, "POST", "/reservations/1002/cancel", "");
        call(base, "POST", "/reservations/1002/cancel", "");
        call(base, "DELETE", "/reservations/1001", null);
        call(base, "DELETE", "/reservations/1001", null);
        call(base, "PATCH", "/reservations", "{}");
        server.stop(0);
    }

    static void handleReservations(HttpExchange ex) throws IOException {
        ex.getRequestBody().readAllBytes();                       // 본문을 끝까지 읽어 둔다
        String[] seg = ex.getRequestURI().getPath().split("/");   // "", "reservations", "1002", "cancel"
        String method = ex.getRequestMethod();
        if (seg.length == 2) {                                    // 컬렉션 /reservations
            if (method.equals("POST")) {
                long id = sequence.incrementAndGet();             // 새 식별자는 서버가 정한다
                reservations.put(id, "BOOKED");
                ex.getResponseHeaders().add("Location", "/reservations/" + id);
                respond(ex, 201, "");
            } else if (method.equals("GET")) {
                respond(ex, 200, reservations.toString());
            } else {
                ex.getResponseHeaders().add("Allow", "GET, POST");
                respond(ex, 405, "");
            }
            return;
        }
        long id = Long.parseLong(seg[2]);
        if (seg.length == 3 && method.equals("DELETE")) {         // 문서 /reservations/{id}
            respond(ex, reservations.remove(id) != null ? 204 : 404, "");
        } else if (seg.length == 4 && seg[3].equals("cancel") && method.equals("POST")) {
            if (!reservations.containsKey(id)) {                  // 컨트롤 URI /reservations/{id}/cancel
                respond(ex, 404, "");
            } else if (reservations.replace(id, "BOOKED", "CANCELLED")) {
                respond(ex, 200, "CANCELLED");
            } else {
                respond(ex, 409, "already cancelled");
            }
        } else {
            respond(ex, 404, "");
        }
    }

    static void handleNotes(HttpExchange ex) throws IOException {
        String body = new String(ex.getRequestBody().readAllBytes(), StandardCharsets.UTF_8);
        String key = ex.getRequestURI().getPath().substring("/notes/".length());
        switch (ex.getRequestMethod()) {
            case "PUT" -> respond(ex, notes.put(key, body) == null ? 201 : 204, "");   // 없으면 생성, 있으면 교체
            case "GET" -> {
                String note = notes.get(key);
                respond(ex, note != null ? 200 : 404, note != null ? note : "");
            }
            default -> {
                ex.getResponseHeaders().add("Allow", "GET, PUT");
                respond(ex, 405, "");
            }
        }
    }

    static void respond(HttpExchange ex, int status, String body) throws IOException {
        byte[] bytes = body.getBytes(StandardCharsets.UTF_8);
        ex.sendResponseHeaders(status, bytes.length == 0 ? -1 : bytes.length);   // -1: 본문 없음
        if (bytes.length > 0) {
            ex.getResponseBody().write(bytes);
        }
        ex.close();
    }

    static final HttpClient client = HttpClient.newHttpClient();

    static void call(String base, String method, String path, String body) throws Exception {
        HttpRequest request = HttpRequest.newBuilder(URI.create(base + path))
                .method(method, body == null ? BodyPublishers.noBody() : BodyPublishers.ofString(body))
                .build();
        HttpResponse response = client.send(request, BodyHandlers.ofString());
        StringBuilder line = new StringBuilder(String.format("%-6s %-26s -> %d", method, path, response.statusCode()));
        response.headers().firstValue("Location").ifPresent(v -> line.append("  Location: ").append(v));
        response.headers().firstValue("Allow").ifPresent(v -> line.append("  Allow: ").append(v));
        if (!response.body().isEmpty()) {
            line.append("  ").append(response.body());
        }
        System.out.println(line);
    }
}

POST   /reservations              -> 201  Location: /reservations/1002
GET    /reservations              -> 200  {1001=BOOKED, 1002=BOOKED}
PUT    /notes/7f3a                -> 201
PUT    /notes/7f3a                -> 204
GET    /notes/7f3a                -> 200  v1

POST   /reservations/1002/cancel  -> 409  already cancelled

    한 줄씩 읽어 보자. 1행과 2행은 본문이 똑같은 POST다. 서버는 두 요청이 같은 예약인지 알 방법이 없다. sequence.incrementAndGet()이 호출될 때마다 새 식별자가 나오고, 응답의 Location이 1001과 1002로 달라진다. 3행의 목록 조회가 자원이 둘임을 확인해 준다. 컬렉션에서 식별자를 만드는 코드는 서버 안에만 있고, 클라이언트 코드 어디에도 1001이라는 숫자는 없다는 점을 눈여겨보자.

    4행과 5행은 본문이 똑같은 PUT이다. 이번에는 식별자 7f3a가 클라이언트 코드에 적혀 있다. 서버는 notes.put(key, body)의 반환값으로 그 자리에 이전 값이 있었는지만 본다. 없었으면 생성이므로 201, 있었으면 교체이므로 204다. 응답 코드는 달라졌지만 서버에 남은 상태는 메모 하나로 같다. 멱등은 응답이 같다는 뜻이 아니라 여러 번 보낸 요청이 서버에 남기는 효과가 한 번 보낸 것과 같다는 뜻임을 여기서 확인할 수 있다. 9행과 10행의 DELETE도 마찬가지다. 두 번째 응답은 404지만 예약 1001이 없다는 서버의 상태는 같다.

    마지막 행은 컬렉션에 정의하지 않은 메서드를 보낸 경우다. RFC 9110 §15.5.6에 따라 405(Method Not Allowed) 응답에는 그 자원이 지원하는 메서드의 목록을 담은 Allow 헤더가 있어야 한다. 7행과 8행의 취소는 다음 절의 주제다.

    HTML 폼만 쓸 수 있을 때와 컨트롤 URI

    같은 예약 시스템을 자바스크립트 없이 순수한 HTML 폼 화면으로 만든다고 하자. 앞에서 본 대로 폼이 보낼 수 있는 요청은 GET과 POST뿐이다. PUT, PATCH, DELETE를 쓸 수 없으니 앞의 API 표를 그대로 옮길 수 없다. 흔히 쓰는 모양은 다음과 같다.

    기능메서드와 URI
    예약 목록GET /reservations
    예약 등록 폼GET /reservations/new
    예약 등록 처리POST /reservations/new 또는 POST /reservations
    예약 상세GET /reservations/{id}
    예약 수정 폼GET /reservations/{id}/edit
    예약 수정 처리POST /reservations/{id}/edit
    예약 삭제 처리POST /reservations/{id}/delete

    API 표에 없던 URI가 두 종류 생겼다. 하나는 GET으로 여는 /new, /edit처럼 입력 화면 자체를 가져오는 URI다. 화면도 서버가 내주는 자원이니 주소가 필요하다. 다른 하나는 POST로 보내는 /edit, /delete처럼 수행할 동작을 이름에 담은 URI다. 쓸 수 있는 변경 메서드가 POST 하나뿐이어서 수정과 삭제를 메서드로 구분할 수 없으니 그 구분을 URI로 옮긴 것이다. 이렇게 동작을 이름에 담은 URI를 컨트롤 URI(control URI)라고 하고, 그것이 가리키는 자원을 컨트롤러(controller)라고 부른다.

    등록 폼을 보여 주는 URI와 등록을 처리하는 URI를 /reservations/new 하나로 맞추면 화면 하나에 대한 조회와 제출이 같은 주소에 묶인다. 처리에 실패해 폼을 다시 보여 줄 때도 주소가 바뀌지 않는다. 처리 URI를 컬렉션인 /reservations로 두는 설계도 가능하다. 어느 쪽이든 한 시스템 안에서 일관되게 쓰면 된다.

    폼 처리에는 따라오는 문제가 하나 있다. POST 요청에 대한 응답으로 결과 화면을 바로 내주면, 사용자가 새로고침할 때 브라우저가 같은 POST를 다시 보내 등록이 중복될 수 있다. RFC 9110은 303(See Other)이 주로 POST 동작의 결과를 다른 자원으로 리다이렉트하는 데 쓰인다고 설명한다. 등록을 처리한 뒤 상세 화면의 URI로 리다이렉트하면 브라우저에 남는 마지막 요청은 GET이 된다. 리다이렉트는 06회에서 자세히 본다.

    서버에서 메서드를 바꿔 주는 필터

    폼의 제약을 서버 쪽에서 가리는 방법도 있다. 스프링의 HiddenHttpMethodFilter가 그 예다. 폼에 _method라는 이름의 숨은 필드를 두고 실제로 쓰고 싶은 메서드를 값으로 넣어 POST로 제출하면, 필터가 이 파라미터를 읽어 getMethod()가 그 값을 돌려주도록 요청을 감싼다. 허용되는 값은 PUT, DELETE, PATCH뿐이다.

    이 기법이 바꾸는 것과 바꾸지 못하는 것을 구분해야 한다. 서버 애플리케이션 안에서는 이 요청이 DELETE로 보이므로 API와 같은 URI 설계를 쓸 수 있다. 그러나 네트워크에 흐르는 요청은 여전히 POST다. 브라우저와 중간의 프록시는 이것을 POST로 다루므로, 멱등 메서드여서 얻는 자동 재시도 같은 성질은 생기지 않는다. 이 필터는 숨은 필드를 읽기 위해 요청 파라미터를 조회한다는 점도 기억해 두자. 앞에서 본 대로 POST 폼 요청에서 파라미터를 조회하면 본문이 소비된다.

    컨트롤 URI는 폼만의 것이 아니다

    HTTP API에서도 컨트롤 URI가 필요한 때가 있다. 예약 취소를 생각해 보자. 취소는 예약 레코드를 지우는 일이 아니다. 취소 가능한 상태인지 확인하고, 상태를 바꾸고, 참석자에게 알리는 절차이며 취소된 예약은 기록으로 남는다. 표현할 방법은 셋쯤 있다.

    표현뜻따져 볼 점
    DELETE /reservations/1002이 자원을 없애 달라취소된 예약을 나중에 조회해야 한다면 의미가 맞지 않는다
    PATCH /reservations/1002와 상태 필드상태 필드를 이 값으로 바꿔 달라클라이언트가 상태 값을 직접 지정하므로 허용되지 않는 전이를 서버가 걸러야 하고, 알림 같은 부수 효과가 필드 변경 뒤에 숨는다
    POST /reservations/1002/cancel이 예약에 대해 취소 절차를 수행해 달라URI에 동사가 들어간다. 대신 의도가 그대로 드러난다

    순서는 정해져 있다. 먼저 자원과 메서드만으로 표현해 본다. 단순한 값의 변경이라면 PATCH로 충분하다. 그것으로 담기지 않는 절차, 즉 검증과 상태 전이와 부수 효과가 한 덩어리로 묶인 동작이 남으면 그때 컨트롤 URI를 쓴다. 컨트롤 URI에는 대개 POST를 쓴다. 서버 상태를 바꾸는 임의의 처리를 요청하는 메서드가 POST이기 때문이다.

    앞 실험의 7행과 8행이 이 컨트롤 URI다. 첫 호출은 200으로 성공했고 두 번째 호출은 409(Conflict)를 받았다. 409는 요청이 대상 자원의 현재 상태와 충돌해 완료될 수 없음을 뜻한다. 이것은 여러 선택지 가운데 하나다. POST는 멱등을 약속하지 않지만, 서버가 특정 POST 동작을 멱등하게 구현하는 것까지 막지는 않는다. 이미 취소된 예약에 대한 취소 요청에 다시 200을 돌려주도록 만들면 클라이언트는 타임아웃 뒤에 마음 놓고 재시도할 수 있다. 재시도가 잦은 환경이라면 이쪽이 클라이언트 코드를 단순하게 만든다.

    URI 설계 어휘: 문서, 컬렉션, 스토어, 컨트롤러

    지금까지 나온 네 낱말을 한자리에 모으자. 이 낱말들은 HTTP 명세의 용어가 아니다. RFC 9110에는 자원(resource)이라는 개념만 있을 뿐 그 종류를 나누지 않는다. 네 가지 분류는 API 설계 문헌에서 자원의 원형(archetype)을 가리키는 말로 통용되는 것으로, Mark Massé의 『REST API Design Rulebook』(O'Reilly)이 제시한 분류다.

    원형뜻예주로 쓰는 메서드
    문서(document)단일한 개념 하나. 객체 하나, 데이터베이스의 행 하나에 해당한다/reservations/1001, /notes/7f3aGET, PUT, PATCH, DELETE
    컬렉션(collection)서버가 관리하는 자원 디렉터리. 항목의 URI를 서버가 만든다/reservationsGET(목록), POST(항목 추가)
    스토어(store)클라이언트가 관리하는 자원 저장소. 항목의 URI를 클라이언트가 정한다/notesGET(목록), 항목에 대한 PUT과 DELETE
    컨트롤러(controller)위 셋으로 표현하기 어려운 절차. 실행할 수 있는 동작이다/reservations/1002/cancelPOST

    이름 짓는 관례도 여기에 맞춰진다. 컬렉션과 스토어에는 복수 명사를 쓰고, 그 아래의 문서는 식별자로 가리키며, 컨트롤러에는 동사를 쓴다. "URI에는 명사를 쓰고 동사는 메서드에 맡긴다"는 원칙을 들어 봤을 텐데, 컨트롤러는 그 원칙이 감당하지 못하는 부분을 받아 내는 자리다. 원칙을 지키려고 취소를 억지로 DELETE에 끼워 넣는 것보다 예외를 예외로 드러내는 편이 읽는 사람에게 정직하다.

    새 API를 설계할 때 질문을 이 순서로 던지면 된다. 다루려는 대상이 하나의 문서인가, 문서의 모음인가. 모음이라면 그 안에 들어갈 항목의 식별자를 서버가 정하는가, 클라이언트가 정하는가. 그리고 조회·등록·교체·부분 변경·삭제로 표현되지 않는 절차가 남는가. 첫 질문이 URI의 모양을, 둘째 질문이 POST와 PUT 가운데 무엇으로 등록할지를, 셋째 질문이 컨트롤 URI가 필요한지를 정한다.

    흔한 오해와 함정

    "POST가 GET보다 안전하다." 두 가지 뜻이 섞여 있다. HTTP 용어로 안전(safe)은 서버의 상태를 바꾸지 않는다는 뜻이고, 이 의미에서 안전한 쪽은 GET이다. 보안의 뜻이라면 POST의 본문도 암호화되지 않은 HTTP에서는 평문으로 흐른다. 전송 구간의 기밀성은 TLS가 맡는다. 민감한 데이터에 POST를 쓰는 이유는 본문이 암호화되어서가 아니라 URI처럼 기록과 로그에 남지 않기 때문이다.

    "GET의 길이 제한은 표준에 정해져 있다." HTTP 명세에는 상한이 없고 최소 8000옥텟을 지원하라는 권장만 있다. 실제 한도는 브라우저, 프록시, 서버가 각자 정하며 서버에서는 요청 줄과 헤더를 담는 버퍼의 크기가 그 한도가 된다. 조건이 길어질 수 있는 조회를 설계할 때는 지나가는 모든 구간의 한도 가운데 가장 작은 값이 기준이 된다.

    "쿼리 파라미터와 폼 데이터는 서버에서 따로 읽어야 한다." 형식이 같고, 서블릿 컨테이너가 둘을 하나의 파라미터 집합으로 합쳐 준다. 반대 방향의 오해도 있다. JSON 본문은 이 집합에 들어오지 않는다. 파라미터 조회로 JSON의 필드를 얻으려 하면 아무것도 나오지 않는다.

    "PUT으로 바꿀 필드만 보내면 나머지는 유지된다." PUT은 교체다. 서버가 명세대로 구현되어 있다면 보내지 않은 필드는 없어진다. 일부만 바꾸려면 PATCH를 쓰거나, 현재 표현을 GET으로 받아 고친 뒤 전체를 PUT으로 보낸다.

    "등록은 POST, 수정은 PUT이다." 메서드는 등록·수정이라는 업무 용어가 아니라 대상 자원과의 관계로 정해진다. PUT은 URI를 아는 자원을 만들 때도 쓰이고, POST는 등록 말고도 메서드로 표현되지 않는 온갖 처리에 쓰인다. 기준은 식별자를 누가 정하는가, 그리고 본문이 대상 자원의 상태를 대체하는가다.

    "multipart는 파일 전용이다." multipart 폼의 텍스트 필드도 파트 하나로 실리고, 서버에서는 일반 파라미터처럼 읽힌다. 반대로 파일 선택 input이 있는 폼에 enctype을 적지 않으면 urlencoded로 제출되어 파일 내용이 아니라 이름만 전송된다. 파일 업로드가 안 될 때 가장 먼저 볼 곳이 폼의 enctype과 요청의 Content-Type이다.

    "본문은 필요할 때마다 다시 읽으면 된다." 본문은 스트림이고 한 번 읽으면 소비된다. 필터, 인터셉터, 컨트롤러 가운데 누가 먼저 읽는지에 따라 뒤쪽이 빈 본문을 받는다. 파라미터 조회도 POST 폼 요청에서는 본문을 읽는 행위라는 점을 잊기 쉽다.

    다음 주제와의 연결

    이 회차에서는 201, 204, 303, 405, 409, 414, 415 같은 상태 코드가 설명 없이 여러 번 등장했다. 서버가 요청을 어떻게 처리했는지를 알리는 이 숫자들의 체계는 06회에서 정리한다. Content-Type으로 대표되는 표현 헤더와 콘텐츠 협상은 07회, 캐시가 URI를 키로 쓴다는 것과 덮어쓰기를 막는 조건부 요청은 08회의 주제다.

    로드맵의 뒤쪽에서도 이 내용은 계속 쓰인다. 스프링 MVC에서 요청 파라미터를 받는 @RequestParam과 @ModelAttribute, 본문을 받는 @RequestBody와 HttpMessageConverter, 파일 업로드, 폼 처리 뒤의 리다이렉트는 모두 이 회차의 전송 방식 위에 올라가 있다. 컬렉션에서 서버가 식별자를 정한다는 것은 데이터베이스와 JPA에서 기본 키를 누가 언제 만드는가의 문제로 다시 나타난다. 응답을 받지 못한 요청을 다시 보내도 되는가라는 질문은 서버 사이의 통신에서 타임아웃과 재시도를 설계할 때 그대로 돌아온다.
    데이터가 실리는 두 자리
    요청 메시지에서 애플리케이션 데이터는 URI의 쿼리 또는 본문에 실린다. 쿼리는 URI의 일부여서 자원 식별에 참여하고 기록에 남으며, 본문은 URI 바깥에 있고 Content-Type이 형식을 알린다.
    application/x-www-form-urlencoded
    이름=값 쌍을 &로 잇는 형식. 영숫자와 * - . _ 외의 바이트는 %XX로, 공백은 +로 적는다. 쿼리 문자열과 POST 폼 본문이 같은 형식을 쓴다.
    multipart/form-data
    본문을 경계 문자열로 나눈 여러 파트로 구성하는 형식. 파트마다 Content-Disposition 헤더로 필드 이름과 파일 이름을 알리고 내용은 인코딩 없이 싣는다. 파일 전송에 쓴다.
    Content-Length와 Content-Type
    본문은 옥텟의 나열일 뿐이다. 어디까지인지는 Content-Length 같은 프레이밍 정보가, 무엇으로 해석할지는 Content-Type이 정한다. 프레이밍은 메서드와 무관하지만 GET의 본문에는 정의된 의미가 없다.
    HTML 폼의 제약
    폼이 만들 수 있는 요청은 GET과 POST뿐이다. GET이면 폼 데이터가 action URL의 쿼리를 대체하고, POST면 enctype에 따라 본문이 된다.
    서블릿 요청 파라미터
    컨테이너는 쿼리와 POST urlencoded 본문을 하나의 파라미터 집합으로 합치며 쿼리가 먼저 온다. 본문은 파라미터를 처음 조회할 때 읽히고, 스트림이므로 한 번만 읽을 수 있다.
    POST 기반 등록
    컬렉션에 POST를 보내면 서버가 식별자를 만들고 201과 Location으로 새 URI를 알린다. 멱등이 아니므로 재시도하면 자원이 중복될 수 있다.
    PUT 기반 등록
    클라이언트가 정한 URI에 PUT을 보내 자원을 만들거나 교체한다. 생성이면 201, 교체면 200이나 204다. 멱등이어서 재시도가 안전하지만 덮어쓰기를 조심해야 한다.
    컨트롤 URI
    자원과 메서드로 표현되지 않는 절차를 동사가 들어간 URI로 나타낸 것. HTML 폼의 수정·삭제 처리, API의 취소·승인 같은 동작에 쓰고 대개 POST로 호출한다.

    실무에서 다시 판단하면, 쿼리와 본문의 선택은 대개 장애와 보안 사고의 형태로 되돌아온다. 인증 토큰이나 개인 정보를 쿼리에 실은 API는 기능상 아무 문제 없이 돌아가다가 액세스 로그를 외부 분석 도구로 보내는 순간 유출 경로가 된다. URI는 기록되는 것이 정상인 자리이므로 로그를 가리는 것보다 애초에 URI에 싣지 않는 것이 근본 대책이다. 반대로 조회 조건을 본문으로 옮기면 캐시와 링크 공유를 잃는다. 조건이 복잡해 POST 검색으로 넘어갈 때는 그 조회가 캐시되어야 하는지, 주소로 공유되어야 하는지를 먼저 확인한다.

    등록 API에서 POST와 PUT의 선택은 "타임아웃이 났을 때 클라이언트가 무엇을 할 수 있는가"로 판단한다. 내부망의 관리 화면처럼 재시도가 드물고 중복이 눈에 띄는 곳에서는 POST 컬렉션으로 충분하다. 모바일 네트워크처럼 응답 유실이 일상인 환경에서 결제나 주문을 등록한다면, 클라이언트가 만든 고유 키로 중복을 걸러 내거나 식별자를 클라이언트가 정하게 해서 요청 자체를 멱등하게 만들어야 한다. 이때 스토어의 덮어쓰기 위험이 새로 생기므로 식별자의 형식과 소유 범위 검증이 함께 들어가야 한다.

    "값이 안 넘어온다"는 문의의 대부분은 요청 메시지를 덤프하면 끝난다. 확인할 것은 세 가지다. 데이터가 쿼리에 있는가 본문에 있는가, Content-Type이 실제 본문 형식과 일치하는가, 서버 코드가 그 자리와 형식에 맞는 방법으로 읽고 있는가. 여기에 본문이 필터에서 먼저 소비되지 않았는지, 컨테이너의 파라미터 크기 한도나 헤더 크기 한도에 걸리지 않았는지를 더하면 거의 모든 경우가 설명된다.

    컨트롤 URI는 남용과 기피 양쪽 모두를 경계한다. 모든 동작을 /doSomething으로 만들면 URI가 자원을 식별한다는 전제가 무너져 캐시, 권한, 문서화가 모두 어려워진다. 반대로 동사를 한사코 피하려고 절차를 상태 필드 변경으로 위장하면 서버의 전이 규칙이 클라이언트로 새어 나간다. 자원과 메서드로 먼저 표현하고, 남는 절차만 이름을 붙여 드러내는 것이 균형점이다.

    1. GET /rooms?floor=3&name=%EB%8C%80+%ED%9A%8C%EC%9D%98%EC%8B%A4 HTTP/1.1이다. GET 제출에서 브라우저는 폼 데이터를 직렬화한 문자열로 action URL의 쿼리를 설정하므로 원래 있던 lang=ko는 사라진다. 한글은 UTF-8 바이트마다 %XX가 되고 공백은 폼 형식의 규칙에 따라 +가 된다. name 속성이 없는 버튼은 항목에 들어가지 않는다. lang=ko를 유지하려면 type="hidden" input으로 폼 안에 넣어야 한다.

    2. getParameterValues("a")는 ["0", "1", "2"]다. 쿼리 문자열의 데이터가 본문의 데이터보다 앞에 오기 때문이다. getParameter("a")는 첫 번째 값인 "0"이다. b는 +가 공백으로 바뀌어 "x y", c는 %2B가 디코딩되어 "+", d는 =가 없으므로 빈 문자열이다. 자르기를 먼저 하고 디코딩을 나중에 하므로 %2B에서 나온 +는 다시 공백으로 바뀌지 않는다.

    3. POST이고 Content-Type이 urlencoded인 요청에서 getParameter 계열을 처음 호출하면 컨테이너가 본문을 읽어 파라미터 집합에 넣는다. 명세는 이 경우 폼 데이터를 더 이상 입력 스트림에서 직접 읽을 수 없다고 규정한다. 본문은 스트림이어서 한 번 읽으면 소비되기 때문이다. JSON 요청은 Content-Type 조건을 만족하지 않으므로 getParameter를 호출해도 컨테이너가 본문을 건드리지 않고(쿼리 문자열만 본다), 본문은 입력 스트림에 그대로 남는다. 해결하려면 필터가 쿼리 문자열만 직접 확인하게 하거나, 기존 서블릿이 파라미터 API로 값을 읽도록 바꾼다.

    4. 클라이언트가 관찰하는 것은 "응답이 오지 않았다"는 사실 하나뿐이다. 요청이 서버에 닿지 못한 경우와, 서버가 주문을 저장했지만 응답이 돌아오다 유실된 경우가 똑같이 타임아웃으로 보인다. POST는 멱등이 아니므로 뒤의 경우에 재시도하면 서버는 새 식별자로 주문을 하나 더 만든다. PUT 기반으로 바꾸면 앱이 주문 식별자를 스스로 만들고(예를 들어 임의의 긴 식별자) PUT /orders/{그 식별자}로 보낸다. 첫 요청이 처리되면 201, 같은 요청의 재시도는 이미 있는 자원을 같은 내용으로 교체하므로 200이나 204이고 주문은 한 건으로 남는다. 새로 떠안는 위험은 덮어쓰기다. 다른 주문과 식별자가 겹치거나 본문이 달라진 채로 같은 URI에 다시 PUT이 오면 기존 주문이 바뀐다. 서버는 식별자 형식과 소유자를 검증하고, 필요하면 조건부 요청으로 기존 자원의 덮어쓰기를 막아야 한다.

    5. (가) GET /rooms?floor=3&sort=name. 조회 조건이므로 쿼리에 싣는다. (나) POST /reservations에 JSON 본문. 예약 번호는 서버가 정하므로 컬렉션에 POST하고 201과 Location을 받는다. (다) PATCH /reservations/{id}에 바꿀 필드만 담은 본문. PUT을 쓰면 전체를 보내야 한다. (라) POST /reservations/{id}/approve. 검증, 상태 전이, 기록, 알림이 묶인 절차이므로 컨트롤 URI가 의도를 드러낸다. 본문에는 승인 사유처럼 절차에 필요한 값만 싣는다. (마) PUT /users/{id}/avatar에 이미지 바이트를 본문으로, Content-Type은 이미지의 미디어 타입으로 보낸다. 사용자당 하나여서 URI가 미리 정해져 있고, 다시 올리면 교체되는 것이 원하는 동작이므로 PUT이 맞다. HTML 폼에서 올려야 한다면 multipart/form-data로 POST하는 설계가 된다.
    안에 name이 q인 입력 칸 하나가 있다. "a b"를 입력해 제출하면 브라우저가 요청하는 대상은 무엇인가? /search?type=room&q=a+b /search?type=room&q=a%20b /search?q=a+b /search이고 본문에 q=a+b가 실린다 GET 제출에서 브라우저는 폼 데이터를 urlencoded로 직렬화한 문자열을 action URL의 쿼리로 "설정"한다. 덧붙이는 것이 아니므로 기존의 type=room은 사라진다. 폼 형식의 직렬화에서 공백은 %20이 아니라 +다. GET 폼은 본문을 만들지 않으므로 마지막 보기도 틀리다. 서블릿 필터에서 POST 폼 요청(urlencoded)에 대해 getParameter를 호출한 뒤, 뒤쪽 코드가 입력 스트림으로 본문을 읽으면 비어 있다. 가장 정확한 설명은? 컨테이너가 보안을 위해 폼 요청의 본문을 항상 지우기 때문이다 본문은 한 번 읽으면 소비되는 스트림이고, 파라미터를 처음 조회할 때 컨테이너가 그 본문을 읽어 파라미터로 바꾸기 때문이다 POST 요청의 본문은 쿼리 문자열로 옮겨지므로 본문 자체가 원래 없기 때문이다 Content-Length가 0으로 다시 계산되어 클라이언트에 재전송을 요청하기 때문이다 서블릿 명세는 POST이고 Content-Type이 urlencoded인 요청에서 getParameter 계열을 처음 호출할 때 폼 데이터를 파라미터 집합에 넣고, 그 경우 입력 스트림에서는 더 이상 직접 읽을 수 없다고 규정한다. 본문이 소켓에서 흘러오는 스트림이라는 구조에서 나오는 결과다. 컨테이너가 본문을 항상 지우는 것도 아니고(파라미터를 조회하지 않으면 스트림에 남는다), 본문이 쿼리로 옮겨지지도 않는다. 응답을 받지 못한 클라이언트가 같은 등록 요청을 한 번 더 보냈다. POST 기반 등록과 PUT 기반 등록의 결과가 다른 근본 이유는? POST에서는 서버가 요청마다 새 식별자를 만들고, PUT에서는 클라이언트가 정한 같은 URI의 상태를 같은 표현으로 다시 대체하기 때문이다 PUT 요청은 TCP가 중복을 감지해 서버에 한 번만 전달하기 때문이다 POST는 본문을 쓸 수 있지만 PUT은 본문을 쓸 수 없어서 서버가 저장할 것이 없기 때문이다 PUT의 응답은 캐시되므로 두 번째 요청이 서버에 도달하지 않기 때문이다 차이는 식별자를 누가 정하느냐에 있다. 컬렉션에 대한 POST는 "하나 추가해 달라"는 요청이어서 올 때마다 새 자원이 생긴다. PUT은 대상 URI의 상태를 본문의 표현으로 만들거나 대체하는 요청이어서 몇 번을 보내도 그 URI에 그 내용의 자원이 하나 있는 상태로 끝난다. TCP는 애플리케이션 수준의 요청 중복을 알지 못하고, PUT도 본문을 가지며, 두 번째 PUT도 서버에 도달해 처리된다. 파일을 폼으로 보낼 때 urlencoded가 아니라 multipart/form-data를 쓰는 이유로 맞는 것은? urlencoded 본문은 Content-Length를 쓸 수 없어 큰 데이터의 끝을 알릴 수 없기 때문이다 multipart는 본문을 암호화하므로 파일이 노출되지 않기 때문이다 urlencoded는 GET에서만 쓸 수 있는 형식이기 때문이다 urlencoded에서는 영숫자와 몇 가지 기호 외의 바이트가 세 바이트로 늘어나고 파일 이름과 미디어 타입을 실을 자리도 없지만, multipart는 파트마다 헤더를 두고 내용을 그대로 싣기 때문이다 urlencoded는 대부분의 바이너리 바이트를 %XX 세 글자로 바꾸어 크기가 불어나고, 이름=값 한 쌍에는 파일 이름이나 파트별 Content-Type 같은 메타데이터를 실을 자리가 없다. multipart는 파트마다 Content-Disposition과 Content-Type 헤더를 두고 내용을 인코딩 없이 싣는다. urlencoded 본문도 Content-Length로 길이를 알리며 POST 본문으로 쓰이고, multipart는 암호화와 무관하다. GET 요청에 Content-Length와 본문을 붙여 보내면 서버 소켓에는 본문 바이트가 도착한다. 그런데도 조회 조건을 GET의 본문에 싣는 설계를 피하는 이유는? HTTP/1.1 문법상 GET 요청에는 Content-Length 헤더를 쓸 수 없어서 요청 자체가 문법 오류이기 때문이다 GET 본문에는 정의된 의미가 없어 무엇을 요청하는지는 URI만으로 정해져야 하고, 캐시나 중간 장비가 본문을 무시하거나 요청을 거부할 수 있기 때문이다 GET 요청은 UDP로 전송되어 본문이 유실될 수 있기 때문이다 서블릿 컨테이너가 GET의 본문을 자동으로 쿼리 문자열에 합치기 때문이다 메시지 프레이밍은 메서드와 독립적이어서 전송은 되지만, RFC 9110은 GET 요청의 본문에 일반적으로 정의된 의미가 없고 요청의 의미나 대상을 바꿀 수 없으며 일부 구현은 그런 요청을 거부할 수 있다고 적는다. 캐시는 본문이 아니라 메서드와 URI를 키로 삼으므로 본문에 조건을 실으면 서로 다른 조회가 같은 요청으로 취급될 수 있다. 문법 오류는 아니고, HTTP/1.1은 TCP 위에서 동작하며, 컨테이너가 GET 본문을 쿼리에 합치는 일도 없다.
    쿼리 파라미터(query parameter)
    URI의 쿼리 구성 요소에 이름=값 형태로 실은 데이터. 문법이 아니라 관례이며 형식은 application/x-www-form-urlencoded를 따른다.
    콘텐츠(content)
    RFC 9110이 메시지 본문을 가리키는 말. 헤더 구역 뒤에 오는 옥텟의 나열이며 프레이밍 정보로 길이가 정해진다.
    application/x-www-form-urlencoded
    HTML 폼에서 유래한 직렬화 형식. 이름과 값을 퍼센트 인코딩하되 공백을 +로 적고, 쌍을 &로 잇는다. WHATWG URL 표준이 정의한다.
    multipart/form-data
    경계 문자열로 본문을 여러 파트로 나누는 미디어 타입. 파트마다 Content-Disposition 헤더를 가진다. RFC 7578이 정의한다.
    경계 문자열(boundary)
    multipart 본문에서 파트를 구분하는 문자열. Content-Type의 필수 파라미터로 알리며 파트 내용 안에 나타나서는 안 된다.
    요청 파라미터(request parameter)
    서블릿 컨테이너가 쿼리 문자열과 POST 폼 본문에서 뽑아 합친 이름-값 집합. getParameter 계열 메서드로 읽는다.
    컬렉션(collection)
    서버가 관리하는 자원 디렉터리. POST로 항목 추가를 요청하면 서버가 새 자원의 URI를 정한다.
    스토어(store)
    클라이언트가 관리하는 자원 저장소. 클라이언트가 URI를 정해 PUT으로 자원을 넣는다.
    컨트롤 URI(control URI)
    자원과 메서드만으로 표현하기 어려운 절차를 동사로 드러낸 URI. 컨트롤러라고도 하며 대개 POST로 호출한다.
    Location 헤더
    응답과 관련된 자원의 URI를 알리는 헤더. 201 응답에서는 요청으로 만들어진 주 자원을 가리킨다.
