    이 회차의 질문: 글자 네 줄 뒤에 있는 설계 결정

    02회의 끝에서 우리는 TCP 연결에 글자 네 줄을 써 넣어 서버의 응답을 받아 냈다. HTTP 요청이 "약속된 형식으로 적은 글자"라는 것은 그때 확인했다. 그런데 그 형식은 우연히 그렇게 생긴 것이 아니다. 누가 먼저 말하는지, 서버가 무엇을 기억하는지, 연결을 언제까지 쥐고 있는지, 메시지 하나에 무엇을 담아야 하는지에 대한 결정이 그 몇 줄에 들어 있다. 이 회차는 그 결정들을 하나씩 꺼내 본다.

    질문을 네 개로 나눌 수 있다. 첫째, 왜 항상 클라이언트가 먼저 말하고 서버는 대답만 하는가. 둘째, 서버는 왜 바로 앞의 요청을 기억하지 않도록 설계되었고, 그러면 여러 단계로 이루어진 일은 어떻게 처리하는가. 셋째, 응답을 보낸 뒤 TCP 연결은 어떻게 되며, 유지하는 것과 끊는 것은 각각 무엇을 아끼고 무엇을 치르는가. 넷째, 메시지는 왜 시작 줄과 헤더와 빈 줄과 본문이라는 모양이며, 받는 쪽은 그 끝을 어떻게 아는가.

    이 네 질문의 답은 서로 얽혀 있다. 서버가 대화를 기억하지 않기 때문에 메시지 하나가 스스로를 설명해야 하고, 메시지가 스스로를 설명하기 때문에 어느 연결로 오든 어느 서버가 받든 상관이 없어진다. 이 연결 고리를 이해하면, 뒤의 회차에서 배울 메서드와 상태 코드와 헤더가 왜 그렇게 정의되었는지, 그리고 서버를 여러 대로 늘리는 일이 왜 가능한지가 한 줄로 이어진다. 메서드(04·05회), 상태 코드(06회), 개별 헤더 필드(07·08회)의 세부는 각 회차의 몫으로 남기고, 여기서는 그것들이 올라설 바닥을 다진다.

    모든 것이 HTTP: 한 프로토콜에 실리는 것들

    HTTP는 HyperText Transfer Protocol의 약자다. 이름대로 처음에는 하이퍼텍스트 문서를 가져오는 용도였다. RFC 9110 1.2절은 HTTP가 1990년에 도입되었고, 처음에는 주어진 경로의 하이퍼텍스트 문서를 요청하는 메서드 하나(GET)만 있는 단순한 장치였다고 적는다. 그 뒤 요청과 응답을 메시지로 감싸고, 미디어 타입으로 임의의 데이터 형식을 실어 나르고, 중개자를 거쳐 요청을 전달하도록 확장되었다.

    지금 HTTP 메시지의 본문에 실리는 것은 HTML만이 아니다. 일반 텍스트, 이미지, 음성, 영상, 내려받는 파일, JSON이나 XML로 표현한 데이터가 모두 같은 형식의 메시지에 실린다. 이것이 가능한 이유는 HTTP가 본문을 해석하지 않기 때문이다. 프로토콜의 눈에 본문은 바이트의 나열일 뿐이고, 그 바이트가 무엇인지는 Content-Type 헤더 필드가 미디어 타입으로 알려 준다. HTTP는 "바이트 덩어리와 그것을 설명하는 이름표"를 나르는 일만 하고, 이름표를 읽어 화면에 그리거나 객체로 바꾸는 일은 양 끝의 프로그램이 한다.

    사용하는 쪽도 브라우저만이 아니다. 모바일 앱이 서버의 API를 부를 때, 서버가 다른 서버의 기능을 호출할 때, 명령줄 도구가 파일을 받을 때에도 HTTP를 쓴다. RFC 9110 3.5절은 요청을 시작하는 클라이언트 프로그램을 통틀어 사용자 에이전트(user agent)라 부르고, 브라우저는 그 가운데 가장 익숙한 형태일 뿐 구현 전체에서는 일부라고 말한다. 스프링으로 만드는 서버 애플리케이션도 브라우저의 요청을 받는 한편, 다른 시스템의 HTTP API를 부를 때에는 스스로 사용자 에이전트가 된다.

    이렇게 넓게 쓰일 수 있는 까닭을 RFC 9110 1.1절은 균일한 인터페이스(uniform interface)로 설명한다. HTTP는 서비스가 어떻게 구현되어 있는지를 감추고, 자원의 종류와 무관한 같은 인터페이스를 클라이언트에 내놓는다. 서버도 클라이언트 각각의 목적을 알 필요가 없다. 요청 하나하나를 특정한 종류의 클라이언트나 미리 정해진 절차의 한 단계로 보지 않고 따로 떼어 다룰 수 있기 때문이다. 그래서 브라우저, 웹 서버, 프록시, 캐시, 클라이언트 라이브러리 같은 범용 구현을 여러 맥락에서 그대로 쓸 수 있다.

    TCP 위에 자기만의 프로토콜을 직접 만드는 경우와 견주어 보면 이 말의 무게가 드러난다. 그렇게 하려면 메시지의 경계를 어떻게 표시할지, 성공과 실패를 어떻게 알릴지, 데이터 형식과 길이 같은 부가 정보를 어디에 적을지를 모두 새로 정하고, 그 규약을 이해하는 클라이언트와 진단 도구도 따로 만들어야 한다. HTTP는 이 모든 것에 이미 답을 정해 두었고, 그 답을 구현한 소프트웨어가 어디에나 있다. 새 서비스는 "어떤 자원에 어떤 메서드를 허용할 것인가"만 정하면 된다.

    클라이언트 서버 구조: 먼저 말하는 쪽과 기다리는 쪽

    HTTP의 통신 단위는 요청(request) 하나와 그에 대한 응답(response)이다. RFC 9110 3.3절은 두 참여자를 이렇게 정의한다. 클라이언트(client)는 HTTP 요청을 보낼 목적으로 서버에 연결을 맺는 프로그램이고, 서버(server)는 요청을 처리해 응답을 보내기 위해 연결을 받아들이는 프로그램이다. 이 짧은 정의에 비대칭이 두 겹으로 들어 있다.

    첫째 비대칭은 연결을 여는 방향이다. 01회에서 본 대로 서버 프로세스는 포트에 묶인 리스닝 소켓을 열어 두고 연결 요청을 기다리고, 클라이언트는 필요해진 순간에 그 주소와 포트로 연결을 건다. 서버는 클라이언트가 누구이고 어디에 있는지 미리 알 필요가 없지만, 클라이언트는 서버의 위치를 알아야 한다. URI의 호스트와 포트가 바로 그 정보다. 그래서 서버는 고정된 주소에 계속 떠 있는 프로세스가 되고, 클라이언트는 생겼다 사라져도 되는 프로세스가 된다.

    둘째 비대칭은 말을 시작하는 방향이다. 응답은 언제나 어떤 요청에 대한 응답이다. 서버는 클라이언트에게 알릴 일이 생겨도 요청이 오기 전에는 보낼 수단이 없고, 요청이 오면 그 응답에 실어 보낼 뿐이다. HTTP 명세의 저자 가운데 한 사람인 필딩(Roy Fielding)의 박사 학위 논문은 이 관계를 한 문장으로 옮겨 적는다. 클라이언트는 일을 일으키는 프로세스이고 서버는 반응하는 프로세스라는 것이다. 클라이언트는 자기가 고른 시점에 활동을 시작하고, 서버는 요청을 기다렸다가 반응한다.

    역할은 프로그램이 아니라 연결에 붙는다

    "클라이언트"와 "서버"를 기계나 프로그램의 종류로 생각하기 쉽지만, 명세는 그렇게 정의하지 않는다. RFC 9110은 이 용어가 특정 연결에서 프로그램이 수행하는 역할만을 가리키며, 같은 프로그램이 어떤 연결에서는 클라이언트로, 다른 연결에서는 서버로 동작할 수 있다고 적는다. 주문을 처리하는 서버 애플리케이션을 떠올려 보자. 브라우저와 맺은 연결에서는 서버이지만, 주문을 처리하다가 결제 시스템의 API를 부르는 순간 그 연결에서는 클라이언트다.

           브라우저 = 클라이언트                주문 애플리케이션 = 클라이언트
           주문 애플리케이션 = 서버             결제 시스템 = 서버

    이 구분은 실무에서 장애를 읽을 때 쓰인다. 연결 ②에서 결제 시스템의 응답이 늦어지면, 주문 애플리케이션은 연결 ①의 응답을 만들지 못한 채 기다린다. 사용자가 보기에는 "주문 서버가 느리다"이지만, 원인은 주문 애플리케이션이 클라이언트 역할을 하는 쪽에 있다. 한 프로세스가 맡은 두 역할을 따로 볼 수 있어야 어느 쪽 설정(받는 쪽의 스레드 수인지, 거는 쪽의 타임아웃인지)을 살펴야 하는지 판단할 수 있다.

    사이에 서는 프로그램들: 프록시, 게이트웨이, 터널

    클라이언트와 서버 사이에는 다른 HTTP 프로그램이 끼어 있을 수 있다. RFC 9110 3.7절은 이들을 중개자(intermediary)라 부르고 세 가지 형태를 든다. 프록시(proxy)는 클라이언트가 고른 중개자로, 클라이언트 대신 요청을 전달한다. 게이트웨이(gateway)는 바깥에서 보기에 원 서버(origin server)처럼 행동하면서 받은 요청을 안쪽의 다른 서버로 넘기는 중개자이고, 리버스 프록시(reverse proxy)라고도 부른다. 명세는 게이트웨이의 쓰임새로 캐시를 통한 성능 향상과 여러 기계에 걸친 부하 분산을 든다. 터널(tunnel)은 메시지를 바꾸지 않고 두 연결 사이를 그대로 이어 주는 중계다.

    여기서 원 서버는 대상 자원에 대해 권위 있는 응답을 만들어 낼 수 있는 프로그램을 가리킨다(RFC 9110 3.6절). 중개자가 있어도 클라이언트 서버 구조는 깨지지 않는다. 중개자는 자기 앞의 연결에서는 서버이고 자기 뒤의 연결에서는 클라이언트다. 사용자 에이전트와 원 서버 사이에 중개자가 셋 있으면 메시지는 서로 다른 연결 네 개를 차례로 지난다.

      사용자 에이전트 ==== 프록시 ==== 게이트웨이(부하 분산) ==== 원 서버 1
       (UA)                                         \==== 원 서버 2
                                                     \=== 원 서버 3
       연결 하나          연결 하나          서버마다 연결이 따로 있다

    RFC 9110은 이 사슬을 설명하며 한 가지를 덧붙인다. 나중의 요청은 부하 분산을 위한 동적 설정에 따라 다른 경로의 연결로 보내질 수 있다는 것이다. 같은 사용자가 연달아 보낸 두 요청이 서로 다른 원 서버에 도착할 수 있다는 뜻이다. 이 사실은 뒤에서 다룰 무상태가 왜 필요한지의 전제가 된다.

    왜 둘로 나누는가

    필딩의 논문 3.4.1절은 클라이언트 서버 구조의 바탕을 관심사의 분리(separation of concerns)라고 설명한다. 사용자 인터페이스에 관한 기능을 클라이언트로 옮기면 서버가 단순해져 확장성이 좋아지고, 인터페이스가 바뀌지 않는 한 두 쪽이 서로 독립적으로 발전할 수 있다는 것이다. 여기서 바뀌지 않아야 할 인터페이스가 HTTP 메시지다.

    이 분리는 양쪽에 자유를 준다. 서버 쪽에서는 데이터베이스를 바꾸거나, 구현 언어를 바꾸거나, 한 대이던 서버를 열 대로 늘려도 같은 요청에 같은 의미의 응답을 주는 한 클라이언트는 알 수 없고 알 필요도 없다. 클라이언트 쪽에서는 브라우저가 새 버전으로 바뀌거나 화면 구성이 달라져도 서버는 손댈 것이 없다. 같은 서버 API를 웹 화면과 모바일 앱이 함께 쓸 수 있는 것도 화면에 관한 일이 서버 바깥에 있기 때문이다.

    서버가 먼저 말할 수 없다는 제약은 실시간 알림 같은 기능에서 부담이 된다. 클라이언트가 주기적으로 물어보는 방식이 그래서 나왔고, WebSocket(RFC 6455)처럼 HTTP 요청으로 시작해 다른 프로토콜로 전환하는 방식도 있다. 이 권의 범위는 요청과 응답으로 이루어지는 HTTP 자체다.

    상태 유지와 무상태 ①: 대화의 맥락을 누가 들고 있는가

    요청 하나로 끝나지 않는 일이 있다. 열차표 예매를 세 단계로 나눠 보자. 구간을 고르고, 좌석을 고르고, 결제 수단을 고른다. 세 번째 단계에서 표를 발행하려면 앞의 두 단계에서 고른 값이 필요하다. 이렇게 여러 요청에 걸쳐 이어지는 대화의 맥락을 여기서는 상태(state)라 부른다. 더 정확히는 세션 상태(session state)다. 설계의 갈림길은 이 맥락을 누가 들고 있느냐에 있다.

    [상태 유지(stateful)]                                서버가 기억하는 것
  요청 1   구간=서울-부산                      -->   { 구간 }
  요청 2   좌석=12A                            -->   { 구간, 좌석 }
  요청 3   결제=카드                           -->   { 구간, 좌석, 결제 }  => 발권

[무상태(stateless)]                                  서버가 기억하는 것
  요청 1   구간=서울-부산                      -->   (없음)
  요청 2   구간=서울-부산, 좌석=12A            -->   (없음)
  요청 3   구간=서울-부산, 좌석=12A, 결제=카드 -->   (없음)                => 발권

    상태 유지 방식에서 요청 2의 좌석=12A는 그것만으로는 뜻이 완성되지 않는다. "어느 열차의 12A인가"는 서버가 요청 1에서 기억해 둔 값에 기대야만 정해진다. 요청의 의미가 서버의 기억에 걸쳐 있는 셈이다. 무상태 방식에서는 요청 하나가 필요한 값을 전부 싣고 온다. 요청 3만 떼어서 보아도 무엇을 하려는 요청인지 빠짐없이 알 수 있다. 맥락은 사라지지 않았다. 클라이언트가 들고 있다가 매번 다시 보낼 뿐이다.

    HTTP는 뒤쪽을 택했다. RFC 9110 3.3절은 HTTP가 무상태 프로토콜로 정의되며, 그 뜻은 각 요청 메시지의 의미를 다른 요청과 떼어 놓고 이해할 수 있고, 연결과 그 위의 메시지 사이의 관계가 메시지의 해석에 영향을 주지 않는다는 것이라고 적는다. 필딩의 논문 3.4.3절은 같은 제약을 이렇게 표현한다. 클라이언트에서 서버로 가는 각 요청은 그 요청을 이해하는 데 필요한 정보를 모두 담아야 하고, 서버에 저장된 맥락에 기댈 수 없으며, 세션 상태는 전부 클라이언트에 둔다.

    상태를 유지하는 프로토콜과 비교하면 차이가 분명해진다. 파일 전송 프로토콜인 FTP(RFC 959)에서는 로그인한 사용자와 현재 작업 디렉터리를 서버가 제어 연결 단위로 기억한다. 디렉터리를 바꾸는 명령을 보내고 나면, 그 뒤에 보내는 같은 파일 이름의 요청이 다른 파일을 가리키게 된다. HTTP에는 이런 "현재 위치"가 없다. 02회에서 본 상대 참조를 떠올려 보자. ../img/a.png 같은 상대 참조를 절대 URI로 푸는 일은 브라우저가 했고, 서버로 가는 요청에는 언제나 온전한 경로가 실렸다. 서버가 "이 클라이언트가 지금 어느 문서를 보고 있는지"를 기억하지 않기 때문에 그렇게 설계된 것이다.

    일상에서 가져온 비유신청서를 누가 들고 다니는가

    여러 창구를 차례로 거쳐야 하는 민원을 생각해 보자. 한 방식은 첫 창구의 담당자가 내 신청서를 자기 서랍에 넣어 두고 접수 번호만 불러 주는 것이다. 다음에 올 때 그 담당자가 자리에 없거나 다른 창구로 안내되면, 새 담당자는 내 신청서를 볼 수 없다. 다른 방식은 신청서를 내가 들고 다니는 것이다. 어느 창구에 가든 지금까지 채운 신청서를 통째로 내밀면, 담당자는 누구든 그것만 보고 다음 일을 할 수 있다. 창구를 늘리는 것도, 담당자가 바뀌는 것도 문제가 되지 않는다. 비유가 맞지 않는 곳도 있다. 종이 신청서는 한 번 들고 가면 그만이지만, HTTP에서는 요청마다 같은 내용을 네트워크로 다시 보내야 하므로 그만큼 전송량이 늘어난다. 그리고 내가 들고 다니는 신청서는 내가 고쳐 쓸 수도 있으니, 받는 쪽은 그 내용을 그대로 믿어서는 안 된다.

    코드로 옮겨 보기

    두 방식의 차이는 결국 "값이 어느 프로세스의 메모리에 놓이는가"다. 네트워크를 걷어 내고 그 점만 남긴 프로그램으로 확인해 보자. 서버 한 대를 객체 하나로, 서버의 메모리를 그 객체의 필드로, 요청을 메서드 호출로 나타낸다. 서버가 두 대일 때는 요청을 번갈아 보낸다. 이것은 부하 분산기가 가장 단순하게 하는 일이다.

    import java.util.HashMap;
import java.util.Map;

public class StateDemo {

    // 상태 유지 서버: 손님별 진행 상황을 자기 힙의 Map에 기억한다
    static class StatefulServer {
        final String name;
        final Map> memory = new HashMap<>();

        StatefulServer(String name) {
            this.name = name;
        }

        String handle(String client, String key, String value) {
            Map context = memory.computeIfAbsent(client, c -> new HashMap<>());
            context.put(key, value);
            if (!key.equals("결제")) {
                return name + ": " + key + " 기억함";
            }
            String route = context.get("구간");
            String seat = context.get("좌석");
            if (route == null || seat == null) {
                return name + ": 오류! 구간=" + route + ", 좌석=" + seat;
            }
            memory.remove(client);
            return name + ": 발권 " + route + " " + seat + " (" + value + ")";
        }
    }

    // 무상태 서버: 손님에 관한 필드가 없다. 판단에 필요한 값은 모두 요청으로 들어온다
    static class StatelessServer {
        final String name;

        StatelessServer(String name) {
            this.name = name;
        }

        String handle(String route, String seat, String pay) {
            if (pay == null) {
                return name + ": 확인 구간=" + route + ", 좌석=" + seat;
            }
            if (route == null || seat == null) {
                return name + ": 오류! 구간=" + route + ", 좌석=" + seat;
            }
            return name + ": 발권 " + route + " " + seat + " (" + pay + ")";
        }
    }

    public static void main(String[] args) {
        String[][] steps = {{"구간", "서울-부산"}, {"좌석", "12A"}, {"결제", "카드"}};

        System.out.println("== 상태 유지, 서버 1대 ==");
        StatefulServer single = new StatefulServer("A");
        for (String[] step : steps) {
            System.out.println(single.handle("kim", step[0], step[1]));
        }
        System.out.println("A가 기억하는 손님 수 = " + single.memory.size());

        System.out.println("== 상태 유지, 서버 2대에 번갈아 ==");
        StatefulServer[] stateful = {new StatefulServer("A"), new StatefulServer("B")};
        for (int i = 0; i < steps.length; i++) {
            StatefulServer target = stateful[i % stateful.length];
            System.out.println(target.handle("kim", steps[i][0], steps[i][1]));
        }
        System.out.println("A가 기억하는 손님 수 = " + stateful[0].memory.size()
                + ", B가 기억하는 손님 수 = " + stateful[1].memory.size());

        System.out.println("== 무상태, 서버 2대에 번갈아 ==");
        StatelessServer[] stateless = {new StatelessServer("A"), new StatelessServer("B")};
        // 진행 상황은 클라이언트가 들고 있다가 요청마다 전부 실어 보낸다
        System.out.println(stateless[0].handle("서울-부산", null, null));
        System.out.println(stateless[1].handle("서울-부산", "12A", null));
        System.out.println(stateless[0].handle("서울-부산", "12A", "카드"));
    }
}
    == 상태 유지, 서버 1대 ==
A: 구간 기억함
A: 좌석 기억함
A: 발권 서울-부산 12A (카드)
A가 기억하는 손님 수 = 0
== 상태 유지, 서버 2대에 번갈아 ==
A: 구간 기억함
B: 좌석 기억함
A: 오류! 구간=서울-부산, 좌석=null
A가 기억하는 손님 수 = 1, B가 기억하는 손님 수 = 1
== 무상태, 서버 2대에 번갈아 ==
A: 확인 구간=서울-부산, 좌석=null
B: 확인 구간=서울-부산, 좌석=12A
A: 발권 서울-부산 12A (카드)

    첫 시나리오부터 따라가 보자. 서버가 한 대일 때 상태 유지 방식은 아무 문제 없이 동작한다. 첫 호출에서 computeIfAbsent가 "kim"의 맥락을 담을 HashMap을 만들어 memory에 넣고 구간을 기록한다. 둘째 호출은 같은 맵을 찾아 좌석을 더한다. 셋째 호출에서 키가 결제이므로 맵에서 구간과 좌석을 꺼내 표를 발행하고, 다 쓴 맥락을 memory.remove로 지운다. 마지막 줄의 0은 이 정리가 이루어졌음을 보여 준다.

    둘째 시나리오에서는 같은 세 요청을 서버 두 대에 번갈아 보낸다. i % 2에 따라 요청 1은 A, 요청 2는 B, 요청 3은 다시 A로 간다. A는 요청 1에서 구간을 기억했다. B는 요청 2를 받았을 때 "kim"을 처음 보므로 빈 맥락을 새로 만들고 거기에 좌석만 적는다. B는 이 좌석이 어느 구간의 것인지 모르지만, 모른다는 사실조차 알지 못한다. 요청 3을 받은 A가 자기 맵에서 좌석을 찾으면 null이 나온다. 좌석은 B의 메모리에 있기 때문이다. 세 값이 모두 서버에 도착했는데도 발권은 실패한다.

    셋째 시나리오의 무상태 서버에는 손님에 관한 필드가 없다. handle이 판단에 쓰는 값은 전부 매개변수로 들어온다. 그래서 A가 받든 B가 받든 결과가 같고, 마지막 요청은 어느 서버에 가더라도 표를 발행한다. 주석에 적었듯 진행 상황은 클라이언트의 몫이다. 이 프로그램에서는 main이 클라이언트 역할을 하며, 요청을 보낼 때마다 지금까지 고른 값을 다시 적어 넣고 있다.

    상태 유지와 무상태 ②: 서버를 늘리고 갈아 끼울 수 있는 이유

    방금 본 실패를 메모리 그림으로 옮기면 원인이 한눈에 들어온다. 서버 프로세스는 저마다 자기 힙을 갖는다. 자바 객체는 그 객체를 만든 JVM의 힙에 있고, 다른 기계에서 도는 다른 JVM은 그 객체를 볼 수 없다. 상태 유지 방식은 대화의 맥락을 특정 프로세스의 힙에 묶어 두는 방식이다.

    [상태 유지: 둘째 시나리오가 끝난 뒤]

  서버 A의 힙                                   서버 B의 힙
  memory --> { "kim" --> { 구간=서울-부산,       memory --> { "kim" --> { 좌석=12A } }
                           결제=카드 } }

  발권에 필요한 세 값이 두 프로세스의 힙에 흩어졌다. 어느 쪽도 혼자서는 완성하지 못한다.
  두 맵은 지워 줄 요청이 오지 않으므로 계속 남는다.

[무상태: 셋째 요청을 처리하는 순간]

  클라이언트의 메모리                            서버 A
  구간=서울-부산, 좌석=12A, 결제=카드  ------>   handle 호출의 스택 프레임: route, seat, pay
                                                 (메서드가 끝나면 프레임이 사라진다)
                                                 힙: 손님에 관한 객체 없음

    이 그림에서 무상태의 이점 세 가지를 읽어 낼 수 있다. 첫째는 수평 확장(scale-out)이다. 요청이 늘어 서버를 한 대 더 띄웠을 때, 새 서버는 지금까지의 대화를 하나도 모르는 채로 시작한다. 무상태라면 그래도 된다. 모든 요청이 스스로 완결되어 있으므로 부하 분산기는 요청을 아무 서버에나 보낼 수 있다. RFC 9110도 많은 구현이 프록시 연결을 재사용하거나 요청을 여러 서버에 동적으로 분산하기 위해 HTTP의 무상태 설계에 의존한다고 적는다.

    둘째는 장애와 교체에 대한 내성이다. 상태 유지 서버가 죽으면 그 힙에 있던 모든 대화가 함께 사라지고, 그 서버와 대화하던 사용자는 처음부터 다시 해야 한다. 새 버전을 배포하려고 프로세스를 재시작하는 것도 힙의 관점에서는 죽는 것과 같다. 무상태 서버는 처리 중이던 요청 하나만 실패하고, 클라이언트가 같은 요청을 다른 서버에 다시 보내면 된다. 서버 한 대가 "언제든 버리고 새로 띄워도 되는 것"이 된다.

    셋째는 메모리다. 상태 유지 서버의 힙 사용량은 처리 중인 요청의 수가 아니라 대화를 진행 중인 사용자의 수에 비례한다. 그리고 실행 결과의 "기억하는 손님 수 = 1"이 보여 주듯, 대화를 끝맺지 않고 떠난 사용자의 맥락은 누군가 지워 주기 전까지 남는다. 맵이 그 객체를 참조하고 있으므로 가비지 컬렉터는 회수할 수 없다. 그래서 상태 유지 방식에는 "얼마 동안 소식이 없으면 버린다"는 만료 정책이 반드시 따라붙는다. 무상태 서버에서 요청 처리에 쓰인 객체는 응답을 보낸 뒤 어디에서도 참조되지 않으므로 곧 회수 대상이 된다.

    필딩은 이 제약이 개선하는 성질을 세 가지로 정리했다. 가시성(visibility)은 모니터링하는 쪽이 요청 하나만 보고 그 요청의 전모를 알 수 있어서 좋아진다. 신뢰성(reliability)은 부분 장애에서 회복하기가 쉬워져서 좋아진다. 확장성(scalability)은 요청 사이에 상태를 저장하지 않으니 서버가 자원을 빨리 풀 수 있고 구현도 단순해져서 좋아진다. 가시성은 개발자에게도 그대로 이득이다. 문제를 일으킨 요청 하나를 로그에서 찾아 그대로 다시 보내면 같은 상황이 재현된다. 상태 유지 방식이라면 그 요청 앞에 있었던 대화 전체를 재현해야 한다.

    왼쪽은 대화의 조각이 두 서버의 메모리에 흩어져 실패하는 모습, 오른쪽은 요청이 모든 값을 싣고 와서 어느 서버든 처리하는 모습을 나란히 보여 준다. 흰 배경을 좌우 두 패널로 나눈 비교 다이어그램. 왼쪽 패널 제목 "상태 유지", 오른쪽 패널 제목 "무상태". 두 패널 모두 같은 배치: 맨 왼쪽에 사람 아이콘과 노트북(클라이언트), 가운데에 세로로 긴 회색 상자 "부하 분산기", 오른쪽에 위아래로 서버 상자 두 개 "서버 A", "서버 B". 왼쪽 패널: 클라이언트에서 나가는 작은 봉투 세 개에 각각 "구간", "좌석", "결제" 라벨. 부하 분산기에서 서버 A로 "구간"과 "결제" 화살표, 서버 B로 "좌석" 화살표. 서버 A 안에 메모 상자 "구간, 결제", 서버 B 안에 메모 상자 "좌석". 서버 A 옆에 빨간 X 표시와 "좌석을 모른다". 오른쪽 패널: 클라이언트 옆에 메모 상자 "구간, 좌석, 결제". 클라이언트에서 나가는 봉투 세 개가 점점 커지며 마지막 봉투에 "구간+좌석+결제" 라벨. 부하 분산기에서 두 서버로 화살표가 번갈아 간다. 두 서버 안의 메모 상자는 비어 있고 "기억 없음" 라벨. 서버 A 옆에 초록 체크 표시와 "발권". 평면적이고 차분한 색조, 고딕체 한국어 라벨. 상태 유지 방식에서는 대화의 조각이 서버마다 흩어진다. 무상태 방식에서는 요청이 맥락을 싣고 오므로 어느 서버가 받아도 된다.

    값도 치른다. 필딩은 단점을 분명히 적었다. 서버의 공유 맥락에 둘 수 없는 데이터를 요청마다 되풀이해 보내야 하므로 네트워크 성능이 떨어질 수 있다는 것이다. 실제 HTTP 요청에서도 이 반복을 볼 수 있다. HTTP 인증을 쓰는 클라이언트는 자격 증명을 Authorization 헤더 필드에 실어 요청마다 보내고, 쿠키를 받은 브라우저는 그 쿠키를 Cookie 헤더 필드에 실어 요청마다 보낸다. 서버가 "아까 그 사용자"를 기억하지 않으니, 클라이언트가 매번 자기를 다시 밝히는 것이다.

    무상태의 한계: 그래도 필요한 상태는 어디에 두는가

    모든 기능을 무상태로 만들 수 있는 것은 아니다. 로그인이 대표적이다. 사용자가 로그인했다는 사실은 그 뒤의 모든 요청에 영향을 주어야 하는데, 비밀번호를 요청마다 다시 받을 수는 없다. 장바구니처럼 여러 화면에 걸쳐 쌓이는 정보도 있다. 이런 기능 앞에서 물어야 할 것은 "상태를 없앨 수 있는가"가 아니라 "상태를 어디에 두고, 요청은 무엇을 싣고 다닐 것인가"다. 선택지는 크게 셋이다.

    상태를 두는 곳요청이 싣는 것서버를 늘릴 때치르는 값
    클라이언트필요한 값 전부아무 서버나 처리할 수 있다요청이 커진다. 클라이언트가 값을 바꿔 보낼 수 있으므로 서버가 변조 여부를 검증할 수단이 필요하다
    서버 프로세스의 메모리맥락을 찾을 식별자같은 사용자의 요청을 같은 서버로 보내 주어야 한다그 서버가 죽거나 재시작하면 사라진다. 부하를 고르게 나누기 어려워진다
    서버들이 함께 쓰는 저장소맥락을 찾을 식별자아무 서버나 처리할 수 있다요청마다 저장소를 조회한다. 저장소가 새로운 병목이자 장애 지점이 된다

    표의 둘째와 셋째 줄은 서버에 상태가 있는데도 HTTP의 무상태를 어기지 않는다는 점에 주목하자. 요청은 식별자를 싣고 오고, 그 식별자가 가리키는 것을 찾아오는 일은 서버 애플리케이션이 한다. 프로토콜의 관점에서는 여전히 요청 하나가 자기 해석에 필요한 것을 모두 싣고 있다. 이 식별자를 요청마다 자동으로 실어 보내게 해 주는 장치가 쿠키다. 쿠키를 정의한 RFC 6265는 첫머리에서 그 목적을 이렇게 밝힌다. 서버가 사용자 에이전트에 상태를 저장하게 해서, 대체로 무상태인 HTTP 프로토콜 위에서 상태 있는 세션을 유지할 수 있게 한다는 것이다. 쿠키의 동작은 07회에서 다룬다.

    둘째 줄의 방식에서 "같은 사용자의 요청을 같은 서버로" 보내는 부하 분산 설정을 흔히 고정 세션(sticky session)이라 부른다. 이것은 앞 절에서 얻은 이점 세 가지를 그만큼 되돌려 놓는다. 서버를 늘려도 기존 사용자는 원래 서버에 묶여 있고, 서버 한 대가 죽으면 그 서버에 묶인 사용자의 대화가 사라진다. 그래서 서버가 여러 대인 환경에서는 셋째 줄처럼 맥락을 프로세스 밖의 공유 저장소로 옮기거나, 첫째 줄처럼 클라이언트가 들고 다니게 하는 쪽을 택하는 경우가 많다. 어느 쪽이든 "서버 프로세스의 힙에는 대화의 맥락을 두지 않는다"는 점이 같다.

    여기서 용어의 범위를 분명히 해 두자. 무상태는 서버에 데이터가 없다는 뜻이 아니다. 데이터베이스에 저장된 회원 정보나 주문 내역은 자원의 상태이고, 어느 서버가 요청을 받든 같은 저장소에서 같은 값을 읽는다. 무상태가 금지하는 것은 "이 클라이언트와 지금 어디까지 이야기했는가"라는 대화의 맥락을 요청과 요청 사이에 서버가 붙들고 있는 것이다. 서버 설계에서 실제로 내리는 판단은 대개 이렇게 정리된다. 대화의 맥락은 가능한 한 요청에 실어 받고, 꼭 서버 쪽에 두어야 하는 것은 최소한으로 줄여 프로세스 바깥에 둔다.

    비연결성 ①: 연결 하나에 드는 값

    상태 다음으로 따져 볼 것은 연결이다. 01회에서 본 대로 TCP 연결은 두 기계를 잇는 선이 아니라, 양 끝의 운영체제가 저마다 메모리에 유지하는 상태다. 어디까지 보냈고 어디까지 받았는지를 적은 순서 번호, 상대가 받을 수 있는 양, 아직 확인받지 못한 데이터가 그 안에 들어 있다. 그러니 "연결을 유지한다"는 말은 "양쪽 커널이 이 연결에 대한 기록을 계속 들고 있다"는 뜻이다.

    서버의 입장에서 연결 하나는 세 층에서 자원을 차지한다. 커널에서는 연결마다 소켓과 송신·수신 버퍼가 잡힌다. 프로세스에서는 연결마다 파일 디스크립터가 하나씩 쓰이는데, 한 프로세스가 열 수 있는 개수에는 운영체제가 정한 상한이 있다. 애플리케이션에서는 연결마다 읽기 버퍼와 "메시지를 어디까지 읽었는지"에 대한 기록이 필요하고, 스레드 하나가 연결 하나를 전담하는 구조라면 연결마다 스레드와 그 스택 메모리까지 묶인다. 이 자원들은 그 연결로 데이터가 한 바이트도 오가지 않는 동안에도 반납되지 않는다.

    그런데 웹의 사용 방식은 연결이 대부분의 시간 동안 쉬는 방식이다. 사람은 페이지를 받은 뒤 한참 읽고 나서야 다음 링크를 누른다. 숫자를 가정해서 계산해 보자. 1만 명이 페이지를 열어 두고 있고, 한 사람이 평균 30초에 한 번 요청을 보내며, 요청 하나를 처리하는 데 0.1초가 걸린다고 하자. 1초에 들어오는 요청은 약 333건이고, 어느 한 순간에 처리 중인 요청은 평균 33건쯤이다. 1만 명 모두와 연결을 유지한다면 서버는 연결 1만 개분의 자원을 쥐고 있어야 하지만, 그 가운데 실제로 일하고 있는 연결은 수십 개뿐이다.

    초기의 HTTP는 이 계산에서 단순한 결론을 냈다. 응답을 보냈으면 연결을 끊는다. HTTP/1.0을 기술한 RFC 1945는 당시의 관행을 이렇게 적는다. 클라이언트가 요청마다 그에 앞서 연결을 맺고, 서버가 응답을 보낸 뒤 연결을 닫는다. 이렇게 하면 서버가 쥐고 있는 연결의 수는 "접속해 있는 사용자 수"가 아니라 "지금 이 순간 처리 중인 요청 수"에 가까워진다. 서버가 클라이언트와의 연결을 유지하지 않는 이 모델을 흔히 비연결성(connectionless)이라 부른다.

    용어를 조심해서 쓰자. 전송 계층에서 "비연결(connectionless)"은 UDP처럼 연결 설정이라는 절차 자체가 없는 통신을 가리킨다. HTTP는 그런 뜻의 비연결 프로토콜이 아니다. RFC 9110 3.3절은 HTTP가 신뢰성 있는 전송 계층 또는 세션 계층의 "연결" 위에서 동작한다고 정의하고, HTTP/1.1과 HTTP/2는 연결 지향인 TCP를 쓴다. 이 장에서 말하는 비연결성은 "요청과 응답 한 번이 끝나면 그 연결을 계속 쥐고 있을 이유가 없다"는 HTTP의 사용 모델을 가리킨다.

    이 모델이 성립하는 것은 앞에서 본 무상태 덕분이다. 서버가 연결 단위로 기억하는 맥락이 없으니, 연결을 끊어도 잃는 것이 없다. 다음 요청은 새 연결로 와도 이전 연결로 온 것과 똑같이 해석된다. FTP처럼 로그인 여부와 현재 디렉터리를 연결에 묶어 두는 프로토콜이라면 연결을 끊는 순간 대화가 처음으로 돌아간다. HTTP에서 연결은 메시지를 나르는 통로일 뿐이고, 대화의 일부가 아니다.

    비연결성 ②: 매번 새로 맺는 비용과 지속 연결

    연결을 끊으면 서버의 자원은 아끼지만 시간이 든다. 보통의 TCP 연결 설정에서는 SYN과 SYN+ACK가 한 번 오가야 하므로, 클라이언트는 한 번의 왕복을 기다린 뒤에야 요청의 첫 바이트를 보낼 수 있다. https라면 그 위에 TLS 핸드셰이크가 더 오간다. 게다가 새 TCP 연결은 혼잡 제어의 slow start에서 출발한다(RFC 5681). 한 번에 보낼 수 있는 양을 작은 값에서 시작해 늘려 가므로, 방금 맺은 연결은 한동안 제 속도를 내지 못한다. 연결을 닫을 때에도 종료를 알리는 세그먼트가 오간다.

    이 비용은 요청 한 번이라면 감수할 만하다. 문제는 웹 페이지 하나가 요청 한 번이 아니라는 데 있다. 02회의 마지막 단계에서 보았듯 브라우저는 HTML을 받은 뒤 그 안에서 참조하는 스타일시트, 스크립트, 이미지를 각각 따로 요청한다. 자원이 수십 개인 페이지를 자원마다 새 연결로 받으면, 같은 서버를 상대로 연결 설정을 수십 번 되풀이하게 된다.

    [요청마다 새 연결]                      [연결 하나를 계속 사용]

  클라이언트          서버                클라이언트          서버
     | --- SYN -------> |                    | --- SYN -------> |
     | <-- SYN+ACK ---- |                    | <-- SYN+ACK ---- |
     | --- ACK -------> |                    | --- ACK -------> |
     | --- 요청 1 ----> |                    | --- 요청 1 ----> |
     | <-- 응답 1 ----- |                    | <-- 응답 1 ----- |
     |   (연결 종료)    |                    | --- 요청 2 ----> |
     | --- SYN -------> |                    | <-- 응답 2 ----- |
     | <-- SYN+ACK ---- |                    | --- 요청 3 ----> |
     | --- ACK -------> |                    | <-- 응답 3 ----- |
     | --- 요청 2 ----> |                    |                  |
     | <-- 응답 2 ----- |                    |  (한동안 요청이 없으면
     |   (연결 종료)    |                    |   어느 한쪽이 닫는다)
     |       ...        |

    HTTP/1.1은 기본값을 뒤집었다. RFC 9112 9.3절은 HTTP/1.1이 지속 연결(persistent connection)을 기본으로 쓰며, 하나의 연결로 여러 요청과 응답을 나를 수 있다고 정한다. 수신자는 가장 최근에 받은 메시지의 프로토콜 버전과 Connection 헤더 필드를 보고, 지금 응답이 끝난 뒤 연결이 유지될지를 다음 순서로 판단한다.

    1. close 연결 옵션이 있으면, 연결은 현재 응답 뒤에 유지되지 않는다.
    2. 그렇지 않고 받은 프로토콜이 HTTP/1.1 이상이면, 연결은 유지된다.
    3. 그렇지 않고 받은 프로토콜이 HTTP/1.0이면서 keep-alive 연결 옵션이 있고, 수신자가 프록시가 아니거나 그 메시지가 응답이며, 수신자가 HTTP/1.0의 이 방식을 따르기로 했으면, 연결은 유지된다.
    4. 그 밖에는 현재 응답 뒤에 연결을 닫는다.

    Connection은 현재 연결에 대한 제어 옵션을 적는 헤더 필드다(RFC 9110 7.6.1절). 02회의 실험에서 요청에 Connection: close를 넣었던 것이 첫째 규칙을 쓴 것이다. 아무것도 적지 않은 HTTP/1.1 요청은 둘째 규칙에 따라 연결을 유지한다. 흔히 "keep-alive"라고 부르는 것이 이 지속 연결이며, HTTP/1.1에서는 따로 요청하지 않아도 켜져 있는 기본 동작이다. 셋째 규칙의 Connection: keep-alive는 기본값이 "닫는다"였던 HTTP/1.0에서 연결 유지를 청하던 방식의 흔적이다.

    그렇다고 연결을 영원히 쥐고 있는 것은 아니다. RFC 9112 9.5절은 서버가 보통 비활성 연결을 더 유지하지 않을 시간 제한을 둔다고 적으면서도 그 길이는 정하지 않는다. 그리고 클라이언트, 서버, 프록시 누구든 언제든지 전송 연결을 닫을 수 있다고 정한다. 지속 연결은 "요청이 이어지는 동안은 재사용하고, 한동안 조용하면 닫는다"는 절충이다. 앞 절의 계산으로 돌아가면, 서버가 쥐는 연결의 수는 접속한 사용자 수와 처리 중인 요청 수 사이의 어딘가가 되고, 그 위치를 유휴 시간 제한이 정한다.

    한 연결 위의 순서 문제, 그리고 HTTP/2와 HTTP/3

    지속 연결에는 한 가지 제약이 따라온다. RFC 9112 9.2절에 따르면 HTTP/1.1에는 요청과 응답을 짝지어 줄 요청 식별자가 없다. 그래서 같은 연결에서 응답이 도착하는 순서가 요청을 보낸 순서와 정확히 같다는 것에 의존한다. 클라이언트가 응답을 기다리지 않고 요청을 잇달아 보내는 파이프라이닝(pipelining)이 허용되어 있지만, 서버는 요청을 받은 순서대로 응답을 보내야 한다. 앞의 응답이 늦어지면 뒤의 응답은 준비가 끝났어도 기다린다. 그래서 HTTP/1.1 클라이언트는 같은 서버에 연결을 여러 개 열어 요청을 나눠 보내는 방법으로 병렬성을 얻는다. RFC 9112 9.4절은 클라이언트가 한 서버에 동시에 여는 연결의 수를 제한할 것을 권하면서도 구체적인 숫자는 정하지 않는다.

    HTTP/2는 이 제약을 메시지 문법에서 풀었다. RFC 9113에 따르면 HTTP/2의 기본 단위는 프레임이고, 요청과 응답의 교환 하나하나가 자기 스트림(stream)에 속한다. 프레임마다 스트림 식별자가 붙어 있으므로 여러 교환의 프레임을 한 연결에 섞어 보내도 받는 쪽이 다시 가려낼 수 있다. 한 스트림이 막혀도 다른 스트림은 진행한다. 연결 하나로 병렬성을 얻으니 연결을 여러 개 열 이유가 줄어든다.

    다만 그 프레임들은 여전히 TCP 연결 하나를 지난다. 01회에서 보았듯 TCP는 바이트를 순서대로만 올려 주므로, 패킷 하나가 유실되면 그 뒤에 도착한 바이트는 전부 재전송을 기다린다. RFC 9114는 이 점을 HTTP/3의 동기로 든다. HTTP/2 다중화의 병렬성은 TCP의 손실 복구에 보이지 않아서, 패킷 하나의 유실이나 순서 뒤바뀜이 그 패킷과 무관한 교환까지 멈춰 세운다는 것이다. HTTP/3은 전송 계층을 UDP 위의 QUIC으로 바꿔, 스트림을 전송 계층이 직접 알도록 했다.

    흐름을 정리하면 이렇다. HTTP/1.0은 요청마다 연결을 맺었고, HTTP/1.1은 연결을 재사용하되 한 번에 한 교환씩 차례로 했고, HTTP/2와 HTTP/3은 연결 하나에서 여러 교환을 동시에 한다. 버전이 올라갈수록 연결은 적게 맺고 오래 쓰는 쪽으로 움직였다. 그 사이 무상태라는 성질은 한 번도 바뀌지 않았다. 연결을 어떻게 쓸지는 성능을 위한 선택이고, 메시지의 의미와는 다른 층의 문제이기 때문이다.

    왼쪽은 요청마다 handshake와 종료가 반복되는 모습, 오른쪽은 handshake 한 번 뒤에 요청과 응답만 세 번 오가는 모습을 나란히 보여 준다. 흰 배경을 좌우 두 패널로 나눈 시퀀스 다이어그램. 왼쪽 패널 제목 "요청마다 새 연결", 오른쪽 패널 제목 "지속 연결". 각 패널에 세로 생명선 두 개, 위에 "클라이언트"와 "서버" 라벨. 왼쪽 패널: 위에서 아래로 같은 묶음이 세 번 반복된다. 한 묶음은 회색 화살표 세 개(오른쪽, 왼쪽, 오른쪽)로 된 "연결 설정" 구간, 파란 오른쪽 화살표 "요청", 주황 왼쪽 화살표 "응답", 그리고 생명선을 가로지르는 점선 "연결 종료". 세 묶음의 회색 구간 옆에 작은 시계 아이콘을 붙인다. 오른쪽 패널: 맨 위에 회색 화살표 세 개로 된 "연결 설정" 구간이 한 번만 있고, 그 아래로 파란 "요청"과 주황 "응답" 화살표가 세 쌍 이어진다. 맨 아래에 점선과 "유휴 시간 뒤 종료" 라벨. 오른쪽 패널의 전체 높이는 왼쪽보다 눈에 띄게 짧다. 평면적이고 차분한 색조, 고딕체 한국어 라벨. 같은 세 요청을 처리하는 두 방식. 지속 연결은 연결 설정의 왕복을 한 번만 치른다.

    직접 확인: 소켓으로 만든 작은 HTTP 서버

    02회에서는 JDK의 HTTP 서버를 상대로 소켓 클라이언트를 만들었다. 이번에는 서버 쪽도 소켓으로 직접 만든다. 연결을 받아들이고, 바이트 스트림에서 메시지의 경계를 찾고, 연결을 유지할지 닫을지를 정하는 일이 서버 안에서 어떻게 일어나는지를 보려는 것이다. 학습용이므로 오류 처리와 청크 전송은 뺐고, 스레드 하나가 연결을 차례로 처리한다. 클라이언트는 같은 세 요청을 한 번은 요청마다 새 연결로, 한 번은 연결 하나로 보낸다.

    import java.io.ByteArrayOutputStream;
import java.io.IOException;
import java.io.InputStream;
import java.io.OutputStream;
import java.net.InetAddress;
import java.net.ServerSocket;
import java.net.Socket;
import java.nio.charset.StandardCharsets;
import java.util.LinkedHashMap;
import java.util.List;
import java.util.Map;

public class MiniHttp {

    // ---- 메시지 읽기: 요청을 읽는 서버와 응답을 읽는 클라이언트가 같이 쓴다 ----

    // 줄 끝(LF)까지 읽어 CR을 떼고 돌려준다. 상대가 연결을 닫아 더 읽을 것이 없으면 null
    static String readLine(InputStream in) throws IOException {
        ByteArrayOutputStream line = new ByteArrayOutputStream();
        int b;
        while ((b = in.read()) != -1) {
            if (b == '\n') {
                String s = line.toString(StandardCharsets.ISO_8859_1);
                return s.endsWith("\r") ? s.substring(0, s.length() - 1) : s;
            }
            line.write(b);
        }
        return null;
    }

    // 빈 줄이 나올 때까지 헤더 필드 줄을 읽는다. 필드 이름은 소문자로 통일해 담는다
    static Map readHeaders(InputStream in) throws IOException {
        Map headers = new LinkedHashMap<>();
        String line;
        while ((line = readLine(in)) != null && !line.isEmpty()) {
            int colon = line.indexOf(':');
            headers.put(line.substring(0, colon).toLowerCase(), line.substring(colon + 1).trim());
        }
        return headers;
    }

    // Content-Length가 말한 바이트 수만큼만 읽는다. 없으면 본문은 0바이트
    static byte[] readBody(InputStream in, Map headers) throws IOException {
        int length = Integer.parseInt(headers.getOrDefault("content-length", "0"));
        return in.readNBytes(length);
    }

    // ---- 서버 ----

    static void serve(ServerSocket listener) {
        int connections = 0;
        try {
            while (true) {
                try (Socket socket = listener.accept()) {      // handshake가 끝난 연결 하나를 꺼낸다
                    connections++;
                    System.out.println("[서버] 연결 #" + connections + " 수락, 상대 포트 " + socket.getPort());
                    InputStream in = socket.getInputStream();
                    OutputStream out = socket.getOutputStream();
                    int requests = 0;
                    String requestLine;
                    while ((requestLine = readLine(in)) != null) {   // 이 연결에서 다음 요청을 기다린다
                        Map headers = readHeaders(in);
                        byte[] body = readBody(in, headers);
                        requests++;
                        System.out.println("[서버]   연결 #" + connections + "의 요청 " + requests + ": "
                                + requestLine + " (본문 " + body.length + "바이트)");

                        boolean close = "close".equalsIgnoreCase(headers.get("connection"));
                        byte[] content = (requestLine.split(" ")[1] + " 처리 완료").getBytes(StandardCharsets.UTF_8);
                        String head = "HTTP/1.1 200 OK\r\n"
                                + "Content-Type: text/plain; charset=UTF-8\r\n"
                                + "Content-Length: " + content.length + "\r\n"
                                + (close ? "Connection: close\r\n" : "")
                                + "\r\n";
                        out.write(head.getBytes(StandardCharsets.US_ASCII));
                        out.write(content);
                        out.flush();
                        if (close) {
                            break;                               // 응답을 보냈으니 연결을 닫는다
                        }
                    }
                }
            }
        } catch (IOException e) {
            // main이 listener를 닫으면 accept()가 예외를 던지고 서버 스레드가 끝난다
        }
    }

    // ---- 클라이언트 ----

    static String exchange(Socket socket, String request) throws IOException {
        OutputStream out = socket.getOutputStream();
        out.write(request.getBytes(StandardCharsets.US_ASCII));
        out.flush();

        InputStream in = socket.getInputStream();
        String statusLine = readLine(in);
        Map headers = readHeaders(in);
        byte[] body = readBody(in, headers);
        return statusLine + " | " + new String(body, StandardCharsets.UTF_8);
    }

    public static void main(String[] args) throws Exception {
        ServerSocket listener = new ServerSocket(18080, 50, InetAddress.getLoopbackAddress());
        new Thread(() -> serve(listener)).start();
        String host = "Host: 127.0.0.1:18080\r\n";

        System.out.println("== 요청마다 새 연결 ==");
        for (String path : List.of("/a", "/b", "/c")) {
            try (Socket socket = new Socket("127.0.0.1", 18080)) {
                String request = "GET " + path + " HTTP/1.1\r\n" + host + "Connection: close\r\n\r\n";
                System.out.println("[클라이언트] " + exchange(socket, request));
            }
        }

        System.out.println("== 연결 하나를 계속 사용 ==");
        try (Socket socket = new Socket("127.0.0.1", 18080)) {
            System.out.println("[클라이언트] " + exchange(socket, "GET /a HTTP/1.1\r\n" + host + "\r\n"));
            String form = "seat=12A";
            String post = "POST /b HTTP/1.1\r\n" + host
                    + "Content-Type: application/x-www-form-urlencoded\r\n"
                    + "Content-Length: " + form.length() + "\r\n"
                    + "\r\n"
                    + form;
            System.out.println("[클라이언트] " + exchange(socket, post));
            System.out.println("[클라이언트] " + exchange(socket, "GET /c HTTP/1.1\r\n" + host + "\r\n"));
        }
        listener.close();
    }
}

    서버의 뼈대는 이중 반복문이다. 바깥 반복문은 listener.accept()로 연결을 하나씩 꺼낸다. accept()가 돌려주는 Socket은 커널이 이미 3-way handshake를 끝내 둔 연결이다. 안쪽 반복문은 그 연결에서 메시지를 하나씩 읽는다. readLine이 요청 줄을 돌려주면 요청이 하나 온 것이고, null을 돌려주면 상대가 연결을 닫은 것이다. 연결이 지속되는지는 이 안쪽 반복문을 몇 번 도느냐로 드러난다.

    첫 구간에서 클라이언트는 요청마다 new Socket으로 연결을 새로 맺고 Connection: close를 적어 보냈다. 서버는 요청을 처리한 뒤 이 옵션을 보고 응답에도 Connection: close를 넣은 다음 안쪽 반복문을 빠져나가고, try-with-resources가 소켓을 닫는다. 그래서 수락이 세 번 일어났다. 세 연결의 상대 포트가 모두 다르다는 점을 보자. 01회에서 본 대로 TCP 연결은 출발지와 목적지의 IP 주소와 포트, 네 값으로 구별된다. 서버 쪽 세 값이 같으니 클라이언트의 운영체제가 연결마다 다른 임시 포트를 골라 준 것이고, 그래서 세 연결은 커널이 보기에 서로 다른 연결이다.

    둘째 구간에서는 수락이 한 번뿐이다. 클라이언트가 소켓 하나를 열어 두고 요청을 세 번 썼고, 서버는 안쪽 반복문을 세 번 돌았다. 요청에 Connection 헤더가 없으니 앞에서 본 판단 순서의 둘째 규칙에 따라 연결이 유지된 것이다. 마지막에 클라이언트가 소켓을 닫으면 서버의 readLine이 null을 돌려주어 안쪽 반복문이 끝난다.

    연결이 닫히지 않는다면 메시지가 어디서 끝나는지는 어떻게 아는가. 02회의 클라이언트는 연결이 닫힐 때까지 전부 읽는 readAllBytes()로 응답을 받았다. 지속 연결에서는 그 방법을 쓸 수 없다. 이번의 exchange는 상태 줄을 읽고, 빈 줄이 나올 때까지 헤더를 읽고, Content-Length가 말한 바이트 수만큼만 본문을 읽고 멈춘다. 서버도 같은 세 함수로 요청을 읽는다. 둘째 요청의 (본문 8바이트)가 그 결과다. 서버가 seat=12A의 8바이트를 정확히 읽어 냈기 때문에, 다음 readLine은 셋째 요청의 첫 글자 G에서 시작할 수 있었다. 연결 하나에 여러 메시지를 실으려면 메시지가 자기 길이를 스스로 알려야 한다는 것이 코드에서 그대로 드러난다.

    같은 연결로 왔다는 사실에는 의미가 없다

    두 구간에서 클라이언트가 받은 응답을 비교해 보자. /a, /b, /c에 대한 응답이 똑같다. 연결 세 개로 나눠 보냈는지 하나로 보냈는지는 결과에 영향을 주지 않았다. 서버 코드를 보아도 그렇다. 응답의 내용을 정하는 데 쓰인 것은 방금 읽은 요청 줄과 헤더뿐이고, 같은 연결의 앞선 요청에서 넘어온 값은 없다. requests 변수는 로그에 번호를 찍는 데만 쓰였다. 이 서버는 지속 연결을 지원하지만 여전히 무상태다.

    RFC 9110은 이것을 서버의 의무로 못박는다. 연결이 보안 처리되어 있고 특정 에이전트 전용인 경우가 아니라면, 서버는 같은 연결의 두 요청이 같은 사용자 에이전트에서 왔다고 가정해서는 안 된다. 중개자를 떠올리면 이유가 분명하다. 게이트웨이는 원 서버와 맺어 둔 연결 몇 개를 계속 재사용하면서, 수많은 사용자의 요청을 그 연결들에 섞어 보낸다. 원 서버가 보기에 연결 하나로 잇달아 들어온 두 요청은 서로 다른 사람의 것일 수 있다.

      사용자 1 --\                                     연결 A:  [1의 요청] [3의 요청] [2의 요청] ...
  사용자 2 ----> [ 게이트웨이 ] ===================>                                          [ 원 서버 ]
  사용자 3 --/     (연결을 몇 개만 맺어 두고 재사용)  연결 B:  [2의 요청] [1의 요청] [3의 요청] ...

  원 서버가 "연결 A의 주인"을 사용자로 착각하면, 한 사람의 정보가 다른 사람에게 새어 나간다.

    연결을 유지하는 것과 상태를 유지하는 것을 같은 것으로 여기기 쉽지만, 둘은 층이 다르다. 연결 유지는 "같은 통로를 다시 쓸 것인가"라는 전송의 문제이고, 무상태는 "요청의 의미가 앞선 요청에 기대는가"라는 의미의 문제다. HTTP는 뒤쪽을 고정해 두었기 때문에 앞쪽을 자유롭게 바꿀 수 있었다. 연결을 끊어도, 재사용해도, 남의 요청과 섞어도 메시지의 뜻이 달라지지 않는다.

    쉬고 있는 연결이 스레드를 붙잡는다

    이 작은 서버에서 지속 연결의 비용도 볼 수 있다. 서버에는 스레드가 하나뿐이고, 연결 #4가 열려 있는 동안 그 스레드는 안쪽 반복문의 readLine에서 다음 요청을 기다리며 멈춰 있다. 바깥 반복문의 accept()로 돌아가지 못하므로 다른 클라이언트를 받을 수 없다. 실제로 연결 하나를 열어 요청을 한 번 주고받은 뒤 닫지 않은 채로 두 번째 소켓을 열어 요청을 보내 보면, 두 번째 소켓의 연결 자체는 성공하지만 응답은 오지 않는다. 연결 설정은 커널이 끝내고 대기 큐에 넣어 두기 때문에 성공하고(ServerSocket 생성자의 둘째 인자 50이 이 큐의 길이로 요청한 값이다), 그 연결을 꺼내 읽을 스레드가 없어서 응답이 없는 것이다. 첫 번째 연결을 닫는 순간에야 두 번째 요청이 처리된다.

    아무 일도 하지 않는 연결이 서버의 스레드를 통째로 차지한 것이다. 스레드를 연결마다 하나씩 붙이는 구조로 바꾸면 다른 클라이언트를 받을 수는 있지만, 이번에는 쉬고 있는 연결의 수만큼 스레드가 묶인다. 앞에서 "연결을 유지하는 데 드는 값"이라고 한 것의 실체가 이것이다. 그래서 실제 서버에는 유휴 연결을 얼마나 기다려 줄지와 연결 하나로 요청을 몇 번까지 받을지를 정하는 설정이 있다.

    스프링 부트가 기본으로 내장하는 톰캣을 예로 들면, Tomcat 10.1의 HTTP 커넥터 설정 문서는 다음 값을 기본으로 적고 있다. 요청을 처리하는 스레드 수의 상한 maxThreads는 200, 동시에 받아들여 처리하는 연결 수의 상한 maxConnections는 8192, 그 상한에 찼을 때 운영체제의 대기 큐에 둘 연결 수 acceptCount는 100이다. 다음 요청을 기다려 주는 시간 keepAliveTimeout은 따로 정하지 않으면 connectionTimeout의 값을 쓰고(기본 60000밀리초이며, 톰캣에 함께 들어 있는 server.xml은 이를 20000으로 설정한다), 한 연결에서 처리할 요청 수의 상한 maxKeepAliveRequests는 100이다.

    연결 상한이 스레드 상한보다 훨씬 크다는 점이 눈에 띈다. 같은 문서의 커넥터 비교표에 따르면 NIO 커넥터는 다음 요청을 기다리는 동안 블로킹하지 않는다. 쉬고 있는 연결은 스레드를 차지하지 않고, 읽을 데이터가 도착했을 때에만 스레드가 배정된다는 뜻이다. 우리 서버의 문제였던 "쉬는 연결 하나에 스레드 하나"를 이렇게 풀어서, 스레드 200개로 수천 개의 지속 연결을 감당한다. 서블릿 컨테이너의 스레드 모델은 스프링 MVC 권에서 다시 다룬다.

    HTTP 메시지 ①: 공통 구조와 시작 줄

    지금까지의 이야기는 모두 메시지에 무거운 책임을 지운다. 서버가 대화를 기억하지 않고 연결에도 의미가 없다면, 수신자가 알아야 할 것은 전부 메시지 안에 있어야 한다. RFC 9110 6절은 이 성질을 자기 서술적(self-descriptive)이라고 부른다. 수신자는 메시지 자체만 보고 그 메시지에 관해 알아야 할 것을 모두 알 수 있어야 하고, 앞선 메시지들로 만들어진 송신자의 애플리케이션 상태를 이해할 필요가 없어야 한다.

    같은 절은 버전과 무관한 메시지의 추상 구조를 네 부분으로 정의한다. 메시지를 설명하고 전달 경로를 정하는 제어 데이터(control data), 이름과 값의 쌍으로 된 헤더, 길이에 제한이 없을 수 있는 바이트 스트림인 내용(content), 그리고 내용을 보내는 동안 얻은 정보를 싣는 트레일러다. 요청의 제어 데이터는 메서드와 요청 대상과 프로토콜 버전이고, 응답의 제어 데이터는 상태 코드와 선택적인 사유 구절과 프로토콜 버전이다.

    이 순서에는 이유가 있다. 명세는 메시지가 스트림으로 처리된다고 설명한다. 제어 데이터는 수신자가 즉시 알아야 하는 것이고, 헤더는 내용을 받기 전에 알아야 하는 것이며, 트레일러는 내용을 보내기 전에는 알 수 없었던 것이다. 서버는 메시지 전체가 도착하기를 기다리지 않고, 요청 줄과 헤더까지만 읽은 시점에 이 요청을 어느 코드에 넘길지, 받아들일지 거절할지를 정할 수 있다. 수 기가바이트의 본문이 붙은 요청도 처음 몇백 바이트만 보고 판단할 수 있는 것이다.

    HTTP/1.1은 이 추상 구조를 텍스트 줄로 적는다. 02회에서 본 문법을 다시 적으면 start-line CRLF *( field-line CRLF ) CRLF [ message-body ]이다. 제어 데이터가 시작 줄(start-line)에 들어가고, 헤더가 필드 줄들이 되고, 빈 줄 하나를 사이에 두고 내용이 본문(message body)으로 이어진다. 앞의 실험에서 연결 #4로 오간 둘째 요청과 그 응답을 그대로 적어 각 부분에 이름을 붙이면 다음과 같다.

    [요청 메시지: 119바이트]
POST /b HTTP/1.1                                   <- 시작 줄(요청 줄)          18바이트
Host: 127.0.0.1:18080                              <- 헤더 필드 줄              23바이트
Content-Type: application/x-www-form-urlencoded    <- 헤더 필드 줄              49바이트
Content-Length: 8                                  <- 헤더 필드 줄              19바이트
                                                   <- 빈 줄: 헤더 구획의 끝      2바이트
seat=12A                                           <- 본문                       8바이트

[응답 메시지: 96바이트]
HTTP/1.1 200 OK                                    <- 시작 줄(상태 줄)          17바이트
Content-Type: text/plain; charset=UTF-8            <- 헤더 필드 줄              41바이트
Content-Length: 16                                 <- 헤더 필드 줄              20바이트
                                                   <- 빈 줄                      2바이트
/b 처리 완료                                       <- 본문                      16바이트

(줄마다 끝의 CR, LF 2바이트를 포함한 크기다. 본문의 한글 네 글자는 UTF-8로 3바이트씩이다.)

    요청 줄: 무엇을, 어디에, 어느 버전으로

    요청 줄의 문법은 method SP request-target SP HTTP-version이다. 세 요소를 공백 한 칸씩으로 띄운다. 메서드는 대상 자원에 수행할 동작의 이름이고, RFC 9112 3.1절은 메서드가 대소문자를 구분한다고 정한다. get은 GET이 아니다. 요청 대상은 02회에서 본 대로 대개 경로와 쿼리로 이루어진 원본 형식이다. HTTP 버전은 HTTP/1.1처럼 적으며, 이름 HTTP도 대소문자를 구분한다.

    요청 줄의 길이에 명세가 정한 상한은 없다. 대신 RFC 9112는 모든 송신자와 수신자가 최소 8000옥텟 길이의 요청 줄을 지원할 것을 권고하고, 서버가 자기가 처리하려는 것보다 긴 요청 대상을 받으면 414(URI Too Long)로 응답해야 한다고 정한다. 구현에는 실제 한계가 있다. Tomcat 10.1은 요청 줄과 헤더를 합친 크기를 기본 8192바이트로 제한한다(maxHttpRequestHeaderSize). 쿼리 문자열에 데이터를 끝없이 붙일 수 없는 이유가 여기에 있다.

    상태 줄: 프로그램은 숫자를 읽는다

    응답의 시작 줄인 상태 줄의 문법은 HTTP-version SP status-code SP [ reason-phrase ]이다. 상태 코드는 세 자리 숫자이고, 사유 구절(reason phrase)은 OK나 Not Found처럼 사람이 읽으라고 붙인 글이다. 대괄호가 말하듯 사유 구절은 없어도 된다. RFC 9112는 클라이언트가 사유 구절의 내용을 무시해야 한다고 권고한다. 다른 언어로 번역되어 있을 수도, 중개자가 덮어썼을 수도, 다른 버전의 HTTP를 거치며 버려졌을 수도 있기 때문이다. 실제로 HTTP/2 응답에는 사유 구절을 실을 자리가 없다. 응답에 정의된 제어 데이터 필드가 상태 코드를 싣는 :status 하나뿐이다. 응답의 성공과 실패는 숫자로만 판단해야 한다.

    응답 메시지를 다시 보면 눈에 띄는 것이 하나 있다. 어떤 요청에 대한 응답인지가 어디에도 적혀 있지 않다. 메서드도 경로도 없다. 그래서 RFC 9110은 자기 서술성에 단서를 단다. 클라이언트는 응답을 해석할 때 자기가 보낸 요청을 기억하고 있어야 한다. 예를 들어 HEAD 요청에 대한 응답은 GET에 대한 응답의 앞부분과 똑같이 생겼지만 본문이 오지 않으므로, 요청을 기억하지 못하면 올바르게 읽을 수 없다. 서버는 지난 요청을 잊어도 되지만, 클라이언트는 아직 응답받지 못한 자기 요청만큼은 기억해야 한다. HTTP/1.1에서 응답이 요청 순서대로 와야 했던 이유가 이것이다.

    글자가 아니라 바이트로 읽는다

    HTTP/1.1 메시지는 사람 눈에 텍스트로 보이지만, 명세는 그것을 문자열로 읽지 말라고 한다. RFC 9112 2.2절은 수신자가 메시지를 US-ASCII의 상위 집합인 인코딩의 옥텟 시퀀스로 파싱해야 한다고 정하고, 인코딩을 고려하지 않고 유니코드 문자의 스트림으로 파싱하면 보안 취약점이 생긴다고 경고한다. 잘못된 멀티바이트 시퀀스 안에 줄 바꿈 바이트가 들어 있을 때 문자열 처리 라이브러리마다 다르게 다루기 때문이다. MiniHttp가 바이트를 하나씩 읽어 줄 바꿈 바이트를 직접 찾고, 한 줄을 다 모은 뒤에야 바이트 하나가 문자 하나에 대응하는 ISO-8859-1로 문자열을 만든 것이 이 원칙을 따른 것이다.

    줄의 끝은 CR과 LF 두 바이트다. 다만 명세는 수신자가 LF 하나만 있어도 줄의 끝으로 인정하고 그 앞의 CR을 무시해도 된다고 허용한다. readLine이 LF를 기준으로 줄을 자르고 끝에 CR이 있으면 떼어 내는 것은 이 허용 범위 안의 구현이다. 서버 쪽에는 요청 줄 앞에 온 빈 줄을 적어도 하나는 무시하라는 권고도 있다. 보내는 쪽은 엄격하게, 받는 쪽은 정해진 범위 안에서 너그럽게 하도록 되어 있다.

    HTTP 메시지 ②: 헤더 필드, 빈 줄, 본문의 끝

    헤더 필드 줄

    헤더 필드 줄의 문법은 field-name ":" OWS field-value OWS이다. OWS는 있어도 되고 없어도 되는 공백(optional whitespace)이다. 필드 이름 뒤에 콜론이 바로 붙고, 값의 앞뒤 공백은 값에 포함되지 않는다. readHeaders가 첫 콜론에서 줄을 자르고 값에 trim()을 부른 것이 이 문법을 옮긴 것이다. 필드 이름은 대소문자를 구분하지 않는다(RFC 9110 5.1절). 그래서 이름을 소문자로 통일해 맵에 넣었다. Content-Length로 왔든 content-length로 왔든 같은 키로 찾기 위해서다. HTTP/2는 아예 필드 이름을 소문자로 바꿔 보내도록 정했다.

    사소해 보이는 규칙 하나가 엄격하게 정해져 있다. 필드 이름과 콜론 사이에는 공백이 올 수 없고, 서버는 그런 요청을 400(Bad Request)으로 거절해야 한다. RFC 9112 5.1절은 이유를 적어 두었다. 과거에 이 공백을 구현마다 다르게 처리한 탓에 요청 라우팅과 응답 처리에서 보안 취약점이 생겼다는 것이다. 메시지를 여러 프로그램이 차례로 읽는 구조에서는, 한 프로그램이 너그럽게 받아 준 것을 다음 프로그램이 다르게 해석하는 순간 틈이 생긴다. 이 문제는 본문의 길이에서 더 크게 나타난다.

    헤더는 HTTP가 확장되는 자리이기도 하다. 새 기능이 필요하면 새 필드 이름을 정의하면 되고, 메시지의 문법은 바뀌지 않는다. RFC 9110은 프록시가 모르는 헤더 필드를 그대로 전달해야 하고, 그 밖의 수신자는 모르는 필드를 무시하도록 권고하며, 이 요구를 지키면 이미 배치된 중개자를 고치지 않고도 HTTP의 기능을 확장할 수 있다고 설명한다. 어떤 필드들이 있고 각각 무엇을 뜻하는지는 07회와 08회에서 다룬다.

    빈 줄

    헤더 구획의 끝은 CRLF만으로 된 빈 줄이 알린다. 본문이 없는 메시지에도 빈 줄은 반드시 있어야 한다. 헤더 필드가 몇 줄 올지 미리 알려 주는 것이 없으므로, 수신자는 빈 줄을 만나기 전까지 "헤더가 더 온다"고 볼 수밖에 없다. 요청을 손으로 만들 때 마지막 \r\n을 빠뜨리면 서버는 오류를 내지 않고 그저 기다린다. 서버가 보기에 그 요청은 아직 쓰는 중이기 때문이다.

    본문은 어디서 끝나는가

    빈 줄 뒤의 바이트가 본문이다. 본문은 HTML일 수도, JSON일 수도, 이미지의 바이트일 수도 있고, HTTP/1.1의 문법은 그 내용에 관여하지 않는다. 문법이 책임지는 것은 본문이 몇 바이트이고 어디서 끝나는가다. 이것을 메시지 프레이밍(message framing)이라 한다. 02회에서 보았듯 TCP는 메시지의 경계를 알려 주지 않으므로, 경계는 메시지가 스스로 밝혀야 한다.

    요청에서는 규칙이 간단하다. RFC 9112 6절에 따르면 요청에 본문이 있다는 것은 Content-Length 또는 Transfer-Encoding 헤더 필드로 알린다. 둘 다 없으면 본문의 길이는 0이다. MiniHttp의 readBody가 Content-Length가 없을 때 0바이트를 읽는 것이 이 규칙이다. 명세는 요청의 프레이밍이 메서드의 의미와 무관하다는 점도 밝힌다. 본문을 읽을지 말지는 메서드 이름이 아니라 이 두 헤더로 정해진다. 응답은 조금 더 복잡해서, 어떤 메서드의 요청에 대한 응답인지와 상태 코드까지 보아야 한다. RFC 9112 6.3절은 본문의 길이를 정하는 규칙 여덟 개를 우선순위 순으로 나열한다.

    순위조건본문의 길이
    1HEAD 요청에 대한 응답, 그리고 1xx·204·304 응답헤더 뒤의 빈 줄에서 끝난다. 어떤 헤더가 있든 본문은 없다
    2CONNECT 요청에 대한 2xx 응답빈 줄 직후부터 연결이 터널이 된다. 길이에 관한 헤더는 무시한다
    3Transfer-Encoding과 Content-Length가 함께 있다Transfer-Encoding이 우선한다. 공격 시도일 수 있으므로 오류로 다루는 것이 마땅하다
    4Transfer-Encoding이 있고 마지막 부호화가 chunked다청크를 끝 표시가 나올 때까지 읽어 복원한다
    5Transfer-Encoding 없이 Content-Length의 값이 유효하지 않다복구할 수 없는 오류다. 요청이라면 서버는 400으로 응답하고 연결을 닫는다
    6유효한 Content-Length가 있다그 값이 본문의 옥텟 수다. 다 받기 전에 연결이 닫히면 불완전한 메시지다
    7요청이고, 위의 어느 것도 아니다0이다. 본문이 없다
    8응답이고, 위의 어느 것도 아니다서버가 연결을 닫을 때까지 받은 바이트 전부다

    넷째 규칙의 청크 전송 부호화(chunked transfer coding)는 보내는 쪽이 전체 길이를 미리 알 수 없을 때 쓴다. 본문을 조각으로 나누고, 조각마다 그 크기를 16진수로 한 줄 적은 뒤 데이터를 붙인다. 크기가 0인 조각이 끝을 알린다. 서버가 응답을 만들어 가면서 곧바로 내보낼 수 있고, 그러면서도 메시지의 끝이 분명하다.

    HTTP/1.1 200 OK
Content-Type: text/plain
Transfer-Encoding: chunked

5
hello
6
 world
0

    이 응답의 본문은 5바이트 hello와 6바이트 world를 이은 11바이트다. 0 한 줄과 그 뒤의 빈 줄이 메시지의 끝이다. 여덟째 규칙, 곧 "연결이 닫힐 때까지가 본문"이라는 방식은 02회의 실험에서 본 것인데 약점이 둘 있다. 응답을 다 보내고 닫은 것인지 도중에 끊긴 것인지를 받는 쪽이 구별할 수 없고, 연결을 닫아야만 끝이 나므로 그 연결을 다시 쓸 수 없다. RFC 9112 9.3절이 지속 연결의 조건으로 연결의 모든 메시지가 스스로 정의한 길이를 가져야 한다고 적은 것이 이 때문이다. 지속 연결과 메시지 프레이밍은 한 쌍이다.

    셋째 규칙에 "공격 시도"라는 말이 나오는 이유도 짚어 두자. 메시지가 중개자와 원 서버를 차례로 지날 때, 두 프로그램이 메시지의 끝을 다르게 판단하면 문제가 생긴다. 앞의 프로그램이 본문의 일부로 보고 넘긴 바이트를 뒤의 프로그램이 다음 요청의 시작으로 해석할 수 있다. 공격자가 이 불일치를 이용해 다른 사용자의 요청 앞에 자기 요청을 끼워 넣는 것을 요청 밀반입(request smuggling)이라 부른다. 그래서 명세는 두 헤더가 함께 온 요청을 서버가 거절하거나 Transfer-Encoding만으로 처리하도록 하고, 어느 쪽이든 응답한 뒤에는 연결을 닫도록 요구한다. 프레이밍 규칙이 이렇게 세밀한 것은 메시지를 읽는 프로그램이 하나가 아니기 때문이다.

    같은 메시지를 HTTP/2는 이렇게 적는다

    마지막으로 처음의 그림으로 돌아가 보자. 지금까지 읽은 텍스트 줄은 HTTP/1.1의 문법이고, 의미론은 버전과 무관하다고 했다. 같은 요청을 HTTP/2는 다음과 같이 싣는다. 제어 데이터는 :으로 시작하는 의사 헤더 필드가 되고, 헤더 필드와 함께 HEADERS 프레임에 들어간다. 본문은 DATA 프레임에 들어간다. 메시지의 끝은 길이를 세어 찾는 것이 아니라 마지막 프레임에 붙는 END_STREAM 플래그가 알린다.

      HTTP/1.1 (텍스트 줄)                               HTTP/2 (이진 프레임, 스트림 하나)

  POST /b HTTP/1.1                                   HEADERS 프레임
  Host: 127.0.0.1:18080                                :method = POST
  Content-Type: application/x-www-form-urlencoded      :scheme = http
  Content-Length: 8                                    :authority = 127.0.0.1:18080
                                                       :path = /b
  seat=12A                                             content-type = application/x-www-form-urlencoded
                                                       content-length = 8
                                                     DATA 프레임 (END_STREAM)
                                                       seat=12A

    적는 방법은 전혀 다르지만 담긴 것은 같다. 메서드, 대상, 헤더 필드, 내용이라는 네 요소가 그대로 있고, 서버 애플리케이션이 받는 요청의 의미도 같다. 서블릿이나 스프링 MVC로 작성한 코드가 요청이 HTTP/1.1로 왔는지 HTTP/2로 왔는지를 신경 쓰지 않아도 되는 것이 이 때문이다. 프레임과 스트림은 서버 소프트웨어가 처리하고, 애플리케이션은 그 위의 의미만 다룬다.

    요청과 응답이 같은 네 부분 구조를 가지며 시작 줄만 다르다는 것, 그리고 Content-Length가 본문의 바이트 수를 가리킨다는 것을 보여 준다. 흰 배경의 구조 다이어그램. 좌우에 세로로 긴 문서 모양 상자 두 개. 왼쪽 상자 위에 제목 "요청 메시지", 오른쪽 상자 위에 제목 "응답 메시지". 각 상자는 위에서 아래로 네 구획으로 나뉘고 구획마다 옅은 색이 다르다. 왼쪽 상자: 첫 구획(파랑)에 고정폭 글씨 "POST /b HTTP/1.1", 둘째 구획(초록)에 세 줄 "Host: 127.0.0.1:18080", "Content-Type: application/x-www-form-urlencoded", "Content-Length: 8", 셋째 구획(회색, 얇게)은 비어 있고, 넷째 구획(주황)에 "seat=12A". 오른쪽 상자: 첫 구획(파랑)에 "HTTP/1.1 200 OK", 둘째 구획(초록)에 두 줄 "Content-Type: text/plain; charset=UTF-8", "Content-Length: 16", 셋째 구획(회색, 얇게)은 비어 있고, 넷째 구획(주황)에 "/b 처리 완료". 두 상자 사이 가운데에 네 구획의 높이에 맞춰 공통 라벨 네 개를 세로로 적는다: "시작 줄", "헤더 필드", "빈 줄 (CRLF)", "본문". 왼쪽 상자의 "Content-Length: 8"에서 주황 구획 "seat=12A"로 휘어진 화살표를 그리고 "8바이트" 라벨을 붙인다. 평면적이고 차분한 색조, 고딕체 한국어 라벨. 요청과 응답은 같은 뼈대를 쓴다. 다른 것은 시작 줄뿐이고, 본문의 끝은 헤더가 알려 준다.
    이 장의 핵심

    HTTP는 요청 하나가 자기 해석에 필요한 것을 모두 싣도록 정했다. 그래서 서버는 대화를 기억하지 않아도 되고, 요청이 어느 연결로 오든 어느 서버에 닿든 뜻이 같다. 서버를 늘리고, 연결을 끊거나 재사용하고, 중개자를 끼워 넣고, 메시지 문법을 텍스트에서 이진 프레임으로 바꾸는 일이 모두 이 한 가지 결정 위에서 가능해졌다. 치르는 값은 요청마다 되풀이되는 데이터와, 메시지가 스스로 경계를 밝혀야 하는 엄격한 문법이다.

    흔한 오해와 함정

    • "무상태 서버에는 데이터가 없다." 무상태가 가리키는 것은 요청과 요청 사이의 대화 맥락이다. 데이터베이스에 저장된 회원이나 주문은 자원의 상태이고, 어느 서버가 받든 같은 저장소에서 읽으므로 무상태와 충돌하지 않는다.
    • "세션이나 쿠키를 쓰면 HTTP가 상태 유지 프로토콜이 된다." 요청마다 식별자를 실어 보내고 서버가 그것으로 맥락을 찾는 것은 프로토콜 위에서 애플리케이션이 하는 일이다. 요청 메시지는 여전히 그 자체로 해석된다. 달라지는 것은 맥락을 어디에 두었느냐이고, 그 위치에 따라 서버를 늘릴 때의 제약이 달라진다.
    • "keep-alive는 상태를 유지하는 기능이다." 지속 연결은 TCP 연결을 재사용하는 것이고 요청의 의미에는 영향을 주지 않는다. 같은 연결로 온 두 요청도 서로 독립적으로 해석된다.
    • "같은 연결로 온 요청은 같은 사용자의 것이다." 게이트웨이는 여러 사용자의 요청을 같은 연결에 섞어 보낸다. 사용자를 식별할 근거는 연결이 아니라 요청에 실려 온 정보여야 한다.
    • "HTTP는 비연결 프로토콜이니 연결을 맺지 않는다." HTTP/1.1과 HTTP/2는 연결 지향인 TCP 위에서 동작한다. 비연결성은 요청과 응답이 끝난 뒤 연결을 계속 쥐고 있지 않아도 된다는 사용 모델을 가리키는 말이고, HTTP/1.1부터는 그마저도 재사용이 기본이다.
    • "클라이언트는 브라우저이고 서버는 서버 컴퓨터다." 두 용어는 연결마다의 역할이다. 서버 애플리케이션이 다른 시스템의 API를 부르는 연결에서는 클라이언트이고, 그쪽의 타임아웃과 연결 관리는 따로 살펴야 한다.
    • "응답이 OK인지 보고 성공을 판단한다." 사유 구절은 사람을 위한 글이고 없을 수도 있다. 판단은 상태 코드의 숫자로 한다.
    • "HTTP/2와 HTTP/3은 다른 프로토콜이니 처음부터 다시 배워야 한다." 달라진 것은 메시지를 적는 방법과 전송 계층이다. 메서드, 상태 코드, 헤더 필드의 의미는 RFC 9110 하나를 공유한다.

    다음 주제와의 연결

    이 장에서 세운 바닥 위에 뒤의 회차가 올라선다. 04회와 05회의 메서드에서는 안전과 멱등이라는 성질을 배운다. 이 성질이 왜 중요한지는 이 장의 연결 모델에서 나온다. 연결은 어느 쪽이든 언제든 닫을 수 있으므로, 클라이언트는 요청을 보냈는데 응답을 받지 못하는 상황을 만난다. 그때 같은 요청을 다시 보내도 되는지를 메서드의 성질이 정한다. 06회의 상태 코드는 응답의 제어 데이터를 다루고, 07회는 헤더 필드와 쿠키를, 08회는 캐시를 다룬다. 캐시가 가능한 것도 이 장의 두 성질 덕분이다. 요청이 스스로 완결되어 있고 응답이 스스로를 설명하므로, 중개자가 응답을 저장해 두었다가 같은 요청에 다시 내줄 수 있다.

    이 권 다음의 서블릿과 스프링 MVC에서는 MiniHttp가 한 일을 서블릿 컨테이너가 대신한다. 연결을 받아들이고, 바이트에서 요청 줄과 헤더와 본문을 가려내고, 그 결과를 요청 객체에 담아 애플리케이션 코드에 넘긴다. 그리고 서버의 메모리에 대화의 맥락을 두고 식별자를 쿠키로 주고받는 방식, 곧 앞의 표에서 둘째 줄에 해당하는 방식이 세션이라는 이름의 표준 기능으로 제공된다. 그 기능을 쓸지, 쓴다면 맥락을 어디에 둘지를 정할 때 이 장의 판단 기준이 그대로 쓰인다.

    이미 읽은 스프링 핵심 원리와도 이어진다. 싱글톤 빈은 여러 스레드가 함께 쓰므로 특정 클라이언트에 관한 값을 필드에 두면 안 된다고 배웠다. StatefulServer의 memory 필드가 문제였던 것과 뿌리가 같다. 한 프로세스 안에서는 필드가 여러 요청에 공유되어서 문제가 되고, 여러 프로세스 사이에서는 필드가 공유되지 않아서 문제가 된다. 두 경우 모두 해법은 같다. 요청 처리에 필요한 값은 요청과 함께 들어와 지역 변수로 머물다 사라지게 하고, 오래 남아야 하는 값은 모두가 함께 보는 저장소에 둔다.
    의미론과 문법의 분리
    메서드, 상태 코드, 헤더 필드의 의미는 RFC 9110이 버전과 무관하게 정의한다. HTTP/1.1(텍스트 줄, TCP), HTTP/2(이진 프레임, TCP), HTTP/3(QUIC, UDP)은 그것을 적고 나르는 방법만 다르다.
    클라이언트 서버 구조
    클라이언트가 연결을 맺어 요청하고 서버가 받아들여 응답한다. 두 용어는 연결마다의 역할이며, 한 프로그램이 두 역할을 함께 맡을 수 있다. 사이에는 프록시, 게이트웨이, 터널이 끼어들 수 있다.
    무상태
    각 요청의 의미를 다른 요청과 떼어 놓고 이해할 수 있다. 대화의 맥락을 서버가 요청 사이에 붙들지 않으므로 어느 서버가 받아도 결과가 같고, 서버를 늘리거나 교체할 수 있다.
    무상태의 값과 한계
    같은 데이터를 요청마다 되풀이해 보내야 한다. 로그인처럼 꼭 필요한 맥락은 클라이언트, 서버 메모리, 공유 저장소 가운데 어디에 둘지 골라야 하고, 서버 메모리에 두면 확장과 장애 대응에 제약이 생긴다.
    비연결성
    무상태이므로 요청과 응답이 끝나면 연결을 끊어도 잃는 맥락이 없다. 서버가 쥐는 연결의 수를 접속자 수가 아니라 처리 중인 요청 수에 가깝게 줄일 수 있다.
    지속 연결
    요청마다 연결을 새로 맺는 비용을 줄이려고 HTTP/1.1은 연결 재사용을 기본으로 했다. Connection: close가 없으면 유지되고, 유휴 시간이 지나면 어느 쪽이든 닫을 수 있다. HTTP/2와 HTTP/3은 한 연결에서 여러 교환을 동시에 한다.
    메시지 구조
    시작 줄, 헤더 필드 줄, 빈 줄, 본문. 요청의 시작 줄은 메서드·요청 대상·버전, 응답의 시작 줄은 버전·상태 코드·사유 구절이다. 메시지는 자기 서술적이어야 한다.
    메시지 프레이밍
    본문의 끝은 Content-Length나 청크 전송 부호화로 메시지가 스스로 밝힌다. 요청에 둘 다 없으면 본문은 0바이트이고, 응답에 둘 다 없으면 연결이 닫힐 때까지가 본문이다.

    실무에서 가장 자주 내리는 판단은 로그인 같은 맥락을 어디에 둘 것인가다. 서버가 한 대이고 재시작할 때 사용자가 다시 로그인해도 괜찮다면, 서버 메모리에 두는 방식이 가장 단순하고 충분하다. 서버가 여러 대가 되거나 사용자가 눈치채지 못하게 배포해야 하는 순간 그 선택은 부담이 된다. 고정 세션으로 버틸 수는 있지만 서버 한 대의 장애가 그 서버에 묶인 사용자 전체에게 번지고, 서버를 늘려도 기존 사용자는 옮겨 가지 않는다. 그때는 맥락을 공유 저장소로 옮기거나 클라이언트가 들고 다니게 바꾸는데, 앞의 것은 저장소라는 새 장애 지점을, 뒤의 것은 요청 크기와 변조 검증이라는 부담을 가져온다. 어느 쪽이 맞는지는 맥락의 크기, 강제로 무효화해야 하는 요구가 있는지, 저장소를 운영할 여력이 있는지에 달려 있다.

    지속 연결은 간헐적 오류의 원인으로 자주 등장한다. RFC 9112가 예로 든 경합이 그것이다. 서버나 중간의 부하 분산기가 유휴 연결을 닫기로 한 바로 그 순간에 클라이언트가 그 연결로 새 요청을 쓰기 시작할 수 있다. 서버가 보기에는 쉬던 연결을 닫은 것이지만 클라이언트가 보기에는 요청이 진행 중이었다. 서버가 다른 서버를 호출하는 구조에서 연결 풀을 쓸 때 이 현상이 "가끔 연결이 끊긴다"는 증상으로 나타난다. 연결을 거는 쪽의 유휴 시간을 받는 쪽보다 짧게 잡아 닫힌 연결을 집어 들 가능성을 줄이고, 실패했을 때 자동으로 다시 보내는 것은 다시 보내도 안전한 요청으로 한정하는 것이 일반적인 대응이다. 그 "안전한 요청"이 무엇인지는 04회에서 배운다.

    무상태가 확장의 문제를 전부 풀어 주는 것은 아니라는 점도 기억해야 한다. 무상태 서버는 늘릴 수 있지만, 그 서버들이 함께 보는 데이터베이스와 세션 저장소는 그대로다. 요청이 몰릴 때 애플리케이션 서버를 두 배로 늘리면 병목은 그 뒤의 공유 자원으로 옮겨 간다. 무상태 설계가 주는 것은 "쉽게 늘릴 수 있는 층"과 "늘리기 어려운 층"을 갈라 놓는 것이고, 그래서 어려운 쪽에 가는 요청을 줄이는 캐시 같은 수단이 다음 과제가 된다.

    장애를 조사할 때 무상태는 직접적인 도움이 된다. 실패한 요청의 메서드, 대상, 헤더, 본문을 그대로 다시 보내면 같은 상황이 재현되어야 한다. 재현되지 않는다면 그 요청의 결과가 메시지 밖의 무언가에 달려 있다는 뜻이다. 특정 서버의 메모리에만 있는 값일 수도, 그사이에 바뀐 자원의 상태일 수도 있다. "요청 하나로 재현되는가"라는 질문은 숨어 있는 상태를 찾아내는 첫 단서다.

TCP는 바이트의 순서만 보장하고 메시지의 경계를 표시하지 않으므로, 앞 메시지의 길이를 한 번 잘못 세면 뒤의 모든 메시지가 어긋난다. 요청 밀반입이 바로 이 어긋남을 의도적으로 만드는 공격이다.

    4. Y의 new Socket은 성공한다. 연결 설정은 서버 프로그램이 accept()를 부르지 않아도 서버의 커널이 끝내고 대기 큐에 넣어 두기 때문이다. 그러나 Y는 응답을 받지 못하고 기다린다. 서버의 하나뿐인 스레드가 X의 연결에서 다음 요청 줄을 기다리며 readLine에 멈춰 있어서, Y의 연결을 큐에서 꺼낼 수 없다. X가 소켓을 닫으면 서버의 readLine이 null을 돌려주어 안쪽 반복문이 끝나고, 서버가 accept()로 돌아가 Y의 연결을 꺼낸 뒤 커널 버퍼에 이미 도착해 있던 Y의 요청을 읽어 응답한다. 쉬고 있는 지속 연결 하나가 스레드를 차지하는 비용을 보여 주는 예다.

(나) 본문은 없다. 204 응답도 규칙 1에 해당한다. (다) 서버가 연결을 닫을 때까지 받은 바이트 전부가 본문이다(규칙 8). 이 연결은 재사용할 수 없고, 도중에 끊긴 것인지 구별할 수도 없다. (라) Transfer-Encoding이 우선하므로 청크를 읽어 길이를 정하는 것이 규칙 3과 4의 답이지만, 이런 요청은 요청 밀반입 시도일 수 있다. 서버는 요청을 거절하거나 Transfer-Encoding만으로 처리할 수 있고, 어느 쪽이든 응답 뒤에 연결을 닫아야 한다.

     HTTP가 무상태 프로토콜이라는 말의 뜻으로 가장 정확한 것은? 서버는 데이터베이스를 포함해 어떤 데이터도 저장하지 않는다. 각 요청 메시지의 의미를 다른 요청과 떼어 놓고 이해할 수 있으며, 어느 연결로 왔는지가 해석에 영향을 주지 않는다. 요청과 응답이 끝날 때마다 TCP 연결을 반드시 끊는다. 클라이언트가 요청 사이에 아무 값도 기억하지 않는다. RFC 9110 3.3절의 정의가 둘째 보기다. 무상태는 대화의 맥락에 관한 것이지 저장된 자원 데이터에 관한 것이 아니므로 첫째는 틀리다. 연결을 끊는지는 무상태와 다른 층의 문제이고 HTTP/1.1은 연결 재사용이 기본이므로 셋째도 틀리다. 넷째는 반대다. 무상태에서는 세션 상태를 클라이언트가 들고 있다가 요청마다 싣는다. 로그인 정보를 각 서버 프로세스의 메모리에 두는 애플리케이션을 서버 두 대로 늘리고, 부하 분산기가 요청을 번갈아 보내게 했다. 예상되는 현상과 그 원인으로 옳은 것은? 문제가 없다. 두 서버가 같은 코드를 실행하므로 메모리의 내용도 같다. 문제가 없다. HTTP가 무상태이므로 프로토콜이 로그인 정보를 다른 서버로 옮겨 준다. 로그인한 사용자의 다음 요청이 다른 서버에 가면 로그인하지 않은 것으로 처리된다. 맥락이 처음 요청을 받은 프로세스의 힙에만 있기 때문이다. 두 번째 서버가 요청을 받을 때마다 TCP 연결 오류가 난다. 연결이 첫 번째 서버에 묶여 있기 때문이다. 프로세스의 힙은 프로세스마다 따로이므로 한 서버가 기억한 맥락을 다른 서버는 볼 수 없다. 같은 코드를 실행한다고 메모리가 같아지지 않으며, HTTP는 서버 사이에 아무것도 옮겨 주지 않는다. 무상태 프로토콜이라는 것은 그런 맥락을 서버에 두지 않는 설계를 전제한다는 뜻이다. 연결 오류와는 관계가 없다. 요청은 정상적으로 도착하고 다만 맥락을 찾지 못할 뿐이다. 클라이언트가 GET /a HTTP/1.1과 Host 헤더만 보내고 Connection 헤더는 보내지 않았다. 서버가 응답을 보낸 뒤 이 연결은 어떻게 되는가? 유지된다. HTTP/1.1은 close 옵션이 없으면 지속 연결이 기본이다. 닫힌다. 연결을 유지하려면 Connection: keep-alive를 반드시 보내야 한다. 닫힌다. HTTP는 비연결 프로토콜이므로 응답마다 연결을 끊도록 명세가 요구한다. 유지된다. 다만 서버는 이후 같은 연결로 오는 요청을 같은 사용자의 것으로 간주해야 한다. RFC 9112 9.3절의 판단 순서에서 close가 없고 프로토콜이 HTTP/1.1 이상이면 연결은 유지된다. keep-alive 옵션은 HTTP/1.0에서 쓰던 방식이다. 명세는 응답마다 연결을 끊으라고 요구하지 않는다. 넷째 보기는 앞부분만 맞다. RFC 9110은 서버가 같은 연결의 두 요청을 같은 사용자 에이전트의 것으로 가정해서는 안 된다고 정한다. 지속 연결로 받은 HTTP/1.1 요청에 Content-Length도 Transfer-Encoding도 없다. 서버는 이 요청의 본문을 어떻게 다뤄야 하는가? 클라이언트가 연결을 닫을 때까지 읽은 바이트 전부를 본문으로 본다. 메서드가 POST이면 다음 빈 줄이 나올 때까지를 본문으로 본다. 본문의 길이를 알 수 없으므로 일정 시간 기다린 뒤 도착한 만큼을 본문으로 본다. 본문의 길이는 0이다. 빈 줄 바로 다음 바이트부터는 다음 요청이다. RFC 9112 6.3절의 규칙 7에 따라, 요청에 두 헤더가 모두 없으면 본문은 없다. 연결이 닫힐 때까지 읽는 방식은 응답에만 적용되는 규칙 8이다. 요청의 프레이밍은 메서드와 무관하므로 둘째는 틀리고, 시간에 기대는 셋째 방식은 명세에 없다. 길이를 메시지가 스스로 밝히지 않으면 한 연결에 여러 메시지를 실을 수 없다. HTTP/1.1에서 HTTP/2로 바뀌어도 서버 애플리케이션의 요청 처리 코드가 그대로 동작할 수 있는 근본적인 이유는? HTTP/2도 요청 줄과 헤더 줄을 CRLF로 구분한 텍스트로 보내기 때문이다. HTTP/2가 TCP 대신 UDP를 써서 메시지의 경계가 보존되기 때문이다. 메서드, 대상, 헤더 필드, 내용이라는 메시지의 의미는 버전과 무관하게 정의되고, 버전마다 다른 것은 그것을 바이트로 적는 방법이기 때문이다. HTTP/2에서는 서버가 요청 사이의 상태를 대신 기억해 주기 때문이다. RFC 9110이 의미론을 버전과 무관하게 정의하고, 각 버전은 자기 문법으로 그것을 싣는다. HTTP/2는 텍스트 줄이 아니라 이진 프레임을 쓰므로 첫째는 틀리다. HTTP/2는 TCP 위에서 동작하며 UDP 위의 QUIC을 쓰는 것은 HTTP/3이므로 둘째도 틀리다. 무상태는 모든 버전에서 유지되므로 넷째도 틀리다.
    사용자 에이전트(user agent)
    요청을 시작하는 클라이언트 프로그램. 브라우저뿐 아니라 앱, 명령줄 도구, 다른 서버를 호출하는 서버 프로그램도 포함한다.
    원 서버(origin server)
    대상 자원에 대해 권위 있는 응답을 만들어 낼 수 있는 프로그램.
    중개자(intermediary)
    클라이언트와 원 서버 사이에서 메시지를 전달하는 프로그램. 클라이언트가 고른 프록시, 원 서버처럼 보이며 안쪽으로 넘기는 게이트웨이(리버스 프록시), 내용을 건드리지 않는 터널이 있다.
    무상태(stateless)
    각 요청의 의미를 다른 요청이나 연결과 떼어 놓고 이해할 수 있는 성질. 서버가 요청 사이에 대화의 맥락을 붙들지 않는다.
    세션 상태(session state)
    여러 요청에 걸쳐 이어지는 대화의 맥락. 저장소에 있는 자원의 상태와 구별된다.
    지속 연결(persistent connection)
    하나의 연결로 여러 요청과 응답을 주고받는 것. HTTP/1.1의 기본 동작이며 흔히 keep-alive라고 부른다.
    시작 줄(start-line)
    HTTP/1.1 메시지의 첫 줄. 요청에서는 요청 줄(메서드, 요청 대상, 버전), 응답에서는 상태 줄(버전, 상태 코드, 사유 구절)이다.
    헤더 필드(header field)
    이름과 값의 쌍으로 메시지와 본문에 관한 정보를 싣는 줄. 이름은 대소문자를 구분하지 않는다.
    메시지 프레이밍(message framing)
    바이트 스트림에서 메시지 하나의 시작과 끝을 정하는 규칙. HTTP/1.1에서는 빈 줄, Content-Length, 청크 전송 부호화가 맡는다.
    자기 서술적 메시지(self-descriptive message)
    수신자가 알아야 할 것을 송신자의 이전 상태에 기대지 않고 메시지 자체에서 알 수 있도록 만든 메시지.
