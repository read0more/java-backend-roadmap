    이 회차의 질문: 쿼리 문자열의 오류는 언제 드러나는가

    JPA 기본편과 스프링 데이터 JPA 권에서 쿼리는 대부분 문자열이었다. em.createQuery("select b from Book b where b.title = :title")처럼 JPQL을 문자열로 적고, 이름 붙은 파라미터에 값을 묶어 실행한다. 이 방식은 SQL을 아는 사람에게 익숙하고 표현력도 충분하다. 문제는 자바 컴파일러에게 이 문자열이 그냥 String이라는 점이다. 컴파일러는 따옴표 안의 b.title이 엔티티의 실제 필드인지, where의 철자가 맞는지, 비교하는 값의 타입이 맞는지 전혀 검사하지 않는다.

    그러면 오류는 언제 드러날까. 답은 "그 문자열이 Hibernate에 처음 넘어가는 순간"이다. 그 코드 경로가 테스트에서 한 번도 실행되지 않았다면 운영 환경의 특정 요청에서 처음 터질 수도 있다. 검색 화면처럼 조건 조합이 많은 쿼리일수록 모든 경로를 테스트로 덮기 어렵다. Querydsl은 이 문제를 쿼리를 문자열이 아니라 자바 객체로 된 식(expression)의 트리로 만드는 방법으로 푼다. 객체의 필드와 메서드는 javac가 검사하므로, 문자열이었다면 실행 중에 드러났을 오류의 상당수가 컴파일 시점으로 당겨진다.

    이 회차는 섹션 「기본 문법」의 앞부분, 곧 JPQL과 Querydsl의 비교, 기본 Q 타입 활용, 검색 조건, 결과 조회, 정렬, 페이징, 집합을 다룬다. 각 문법을 소개하는 데서 멈추지 않고, Querydsl이 만든 JPQL과 Hibernate가 만든 SQL을 함께 보며 "이 메서드 호출이 DB에서 무엇이 되는가"를 끝까지 따라간다. 조인, 서브쿼리, case, 상수와 문자 더하기는 03회, 프로젝션과 동적 쿼리는 04회의 몫이다. 01회에서 다룬 애노테이션 프로세서와 Q 타입 생성은 필요한 만큼만 상기한다.

    실험은 Java 21(Temurin 21.0.13), Hibernate ORM 6.6.53.Final, Querydsl 5.1.0(jakarta 분류자), H2 2.3.232 메모리 DB로 돌렸다. 라이브러리 버전은 Spring Boot 3.5.16의 의존성 관리(BOM)가 고르는 것을 그대로 썼고, 스프링 없이 Hibernate의 Configuration으로 SessionFactory를 만들어 EntityManagerFactory로 사용했다. Hibernate 6의 SessionFactory는 EntityManagerFactory를 구현하므로 그대로 JPA API로 쓸 수 있다. SQL은 hibernate.show_sql=true로 표준 출력에 찍었다. MySQL 방언의 SQL은 MySQLDialect를 지정해 Hibernate가 만든 SQL 문자열을 확인한 뒤, 그 SQL을 같은 데이터를 넣은 MySQL 8.0.46과 8.4.13 서버에서 직접 실행해 결과를 확인했다(자바 프로그램을 MySQL에 연결해 돌린 것은 아니다). 예제 도메인은 이 회차를 위해 새로 만든 도서 엔티티 하나다.

    시작: 문자열 JPQL이 실패하는 네 가지 시점

    먼저 문자열 JPQL이 틀렸을 때 무슨 일이 일어나는지 직접 보자. 아래 네 쿼리는 모두 javac를 아무 문제 없이 통과한다. 따옴표 안의 내용은 컴파일러가 보기에 그저 문자 배열이기 때문이다.

    // 1) 필드 이름 오타: titel
em.createQuery("select b from Book b where b.titel = :title", Book.class);

// 2) 숫자 필드와 문자열 리터럴 비교
em.createQuery("select b from Book b where b.price = '만원'", Book.class);

// 3) 키워드 오타: wehre
em.createQuery("select b from Book b wehre b.price > 1", Book.class);

// 4) 쿼리는 맞지만 파라미터 값의 타입이 틀림
TypedQuery q = em.createQuery("select b from Book b where b.price = :p", Book.class);
q.setParameter("p", "만원");

    예외의 종류를 보면 Hibernate가 문자열을 처리하는 단계가 그대로 드러난다. 3번의 SyntaxException은 문법 분석(parsing) 단계에서 났다. Hibernate 6은 HQL/JPQL 문자열을 ANTLR로 만든 파서로 읽어 구문 트리를 만드는데, Book b 다음에 wehre라는 낯선 토큰이 오자 "여기에는 WHERE, JOIN, ORDER 같은 토큰이 와야 한다"며 멈췄다. 1번과 2번은 문법은 맞지만 의미 분석(semantic analysis)에서 걸렸다. 구문 트리를 Hibernate의 의미 모델인 SQM(Semantic Query Model)으로 바꾸려면 b.titel이 메타모델의 어떤 속성인지 찾아야 하는데 그런 속성이 없고(UnknownPathException), Integer 속성과 문자열 리터럴은 비교할 수 없다(SemanticException). 4번은 쿼리 자체는 멀쩡해서 SQM까지 만들어졌고, 값이 들어오는 순간 기대 타입과 비교해 거부되었다. JPA 3.1 명세 3.10절도 파라미터 타입이 쿼리에 맞지 않으면 바인딩할 때 IllegalArgumentException을 던지거나 실행이 실패할 수 있다고 적고 있다.

    핵심은 네 경우 모두 그 줄이 실행되어야 오류가 드러난다는 점이다. 같은 실수를 Querydsl로 쓰면 어떻게 될까. 아래 클래스는 01회에서 본 애노테이션 프로세서가 생성한 QBook을 쓴다.

    두 오류가 모두 컴파일 단계에서 잡혔다. 첫 번째는 평범한 필드 접근 실패다. QBook에는 엔티티의 속성마다 public final 필드가 하나씩 있고, titel이라는 필드는 없으니 javac가 이름을 해석하지 못했다. 두 번째는 제네릭과 오버로딩 해석의 결과다. book.price의 타입은 NumberPath이고, 그 조상인 SimpleExpression의 eq는 eq(T right)와 eq(Expression right) 두 가지뿐이다. T가 Integer로 고정되어 있으니 String 인자를 받을 수 있는 후보가 없다. JPQL 문자열에서는 Hibernate가 실행 중에 했던 의미 분석의 일부를, Querydsl에서는 javac의 이름 해석과 타입 검사가 대신한 셈이다.

    그렇다고 Querydsl이 모든 오류를 컴파일 시점으로 옮기는 것은 아니다. 문법에 맞게 조립된 식이라도 그 결과가 데이터베이스에서 의미가 있는지는 여전히 실행해 봐야 안다. 예를 들어 바로 뒤에서 볼 eq(null)은 컴파일되지만 실행 중에 예외가 난다. 또 Querydsl이 만든 JPQL을 최종적으로 해석하는 것은 여전히 Hibernate이므로, Hibernate가 지원하지 않는 함수나 구문을 쓰면 그 오류는 실행 시점에 나온다. 정확히 말하면 Querydsl은 "엔티티 속성의 이름과 타입"에 관한 오류를 컴파일 시점으로 옮겨 준다.

    일상에서 가져온 비유손글씨 주문서와 키오스크

    문자열 JPQL은 손글씨 주문서와 같다. 메뉴에 없는 음식을 적어도 종이는 아무 말이 없고, 주방(Hibernate)에 도착해서야 "그런 메뉴 없음"으로 돌아온다. Querydsl은 키오스크다. 화면에 있는 메뉴(Q 타입의 필드)만 누를 수 있고, 수량 칸에 글자를 넣을 수도 없다(제네릭 타입 검사). 다만 키오스크도 재료가 떨어졌는지(실제 데이터와 DB의 지원 여부)는 모른다. 그 확인은 여전히 주방에서 일어난다.

    식 트리에서 SQL까지: Querydsl이 실제로 하는 일

    Querydsl이 컴파일 시점 검사를 줄 수 있는 이유는 쿼리를 객체로 표현하기 때문이다. 그 객체가 실제로 무엇인지 들여다보자. 아래 코드는 조건식 하나를 만들고 그 내부 구조를 출력한다.

    book.title.eq(...)는 아무것도 실행하지 않는다. 연산자 Ops.EQ와 두 인자, 곧 경로(path) book.title과 상수(constant) "SQL 첫걸음"을 담은 BooleanOperation 객체 하나를 만들어 돌려줄 뿐이다. 경로 객체는 다시 "부모 경로 book의 title 속성"이라는 메타데이터를 가진다. 이렇게 식은 연산자를 마디(node)로, 경로와 상수를 잎(leaf)으로 하는 트리가 된다. 마지막 두 줄은 이 식 객체들이 값 객체(value object)처럼 다뤄진다는 것을 보여 준다. 같은 식을 두 번 만들면 서로 다른 객체가 생기지만(==는 false), 구조가 같으면 equals는 true다. 식 객체는 만든 뒤 바뀌지 않으므로 여러 쿼리에서 같은 조건식을 재사용해도 안전하다.

    반면 쿼리 객체 JPAQuery는 바뀌는(mutable) 빌더다. where, orderBy, offset을 부를 때마다 내부의 QueryMetadata에 조건과 정렬과 수정자(modifier)가 쌓인다. 그래서 JPAQueryFactory는 select나 selectFrom을 부를 때마다 새 JPAQuery를 만든다. Querydsl 5.1.0의 바이트코드를 보면 JPAQueryFactory.query()가 템플릿을 지정한 팩토리라면 new JPAQuery(entityManager.get(), templates)를, new JPAQueryFactory(em)처럼 템플릿 없이 만든 팩토리라면 new JPAQuery(entityManager.get())을 호출하는데, 여기서 entityManager는 생성자에서 받은 EntityManager를 감싼 Supplier다(EntityManager를 받는 생성자 기준). 스프링 환경에서 이 EntityManager가 트랜잭션마다 실제 대상을 바꿔 주는 프록시라는 점과 그것이 스레드 안전성에 주는 의미는 05회에서 다룬다.

    트리가 실제 쿼리가 되는 것은 fetch() 계열 메서드를 부를 때다. javap -c로 AbstractJPAQuery.createQuery를 읽으면 순서가 그대로 보인다. 먼저 serialize로 JPQLSerializer를 돌려 JPQL 문자열을 만들고, EntityManager.createQuery(String)에 넘긴다. 그다음 직렬화하면서 모아 둔 상수 목록을 JPAUtil.setConstants로 위치 파라미터에 하나씩 바인딩하고, 수정자에 limit와 offset이 있으면 setMaxResults와 setFirstResult를 호출한다. 잠금 모드와 플러시 모드, 힌트를 설정한 뒤 마지막으로 프로젝션에 맞게 결과 변환을 준비한다. 이 마지막 단계가 뒤의 집계 절에서 다룰 숫자 변환이 결과에 걸리는 지점이다.

    직렬화된 JPQL은 JPAQuery의 toString()으로 볼 수 있고, Hibernate 설정 hibernate.use_sql_comments=true를 켜면 실행된 SQL 앞에 주석으로도 붙는다. Querydsl 코드를 디버깅할 때 가장 먼저 켜 볼 설정이다.

    파라미터 바인딩이 계획 캐시에 주는 영향

    위 흐름에서 눈여겨볼 점은 상수가 JPQL 문자열에 들어가지 않는다는 것이다. Querydsl은 eq("SQL 첫걸음")의 값을 ?1이라는 위치 파라미터(positional parameter)로 바꾸고 값은 따로 바인딩한다. JPA 3.1 명세 4.6.4.1절은 위치 파라미터를 물음표 뒤에 정수를 붙여 ?1처럼 쓰며 1부터 센다고 정의한다. 값이 SQL 문장 안에 섞이지 않으니 SQL 주입(SQL injection)이 원천적으로 막히고, 하나가 더 있다. 값이 달라도 JPQL 문자열이 같다는 점이다.

    Hibernate는 JPQL 문자열을 파싱하고 SQM을 거쳐 SQL로 바꾸는 작업의 결과를 쿼리 계획 캐시(query plan cache)에 보관한다. Hibernate 6.6의 QuerySettings에는 hibernate.query.plan_cache_max_size 설정이 있고, QueryEngine.DEFAULT_QUERY_PLAN_MAX_COUNT 상수의 값은 2048이다. 캐시의 키에는 쿼리 문자열이 들어가므로, 문자열이 같아야 재사용된다. 통계(hibernate.generate_statistics=true)를 켜고 같은 조건을 값만 바꿔 세 번 실행해 보았다.

    for (String c : new String[]{"java", "db", "web"})       // (A) Querydsl
    queryFactory.selectFrom(book).where(book.category.eq(c)).fetch();

for (String c : new String[]{"java", "db", "web"})       // (B) 문자열 이어 붙이기
    em.createQuery("select b from Book b where b.category = '" + c + "'", Book.class).getResultList();

for (String c : new String[]{"java", "db", "web"})       // (C) 이름 붙은 파라미터
    em.createQuery("select b from Book b where b.category = :c", Book.class)
      .setParameter("c", c).getResultList();
    (A) Querydsl        hit=4 miss=2
(B) 문자열 이어 붙이기  hit=0 miss=6
(C) 이름 붙은 파라미터  hit=4 miss=2

    이 버전의 Hibernate는 쿼리 한 번 실행에 캐시 조회를 두 번 집계했다. (A)와 (C)는 첫 실행에서 두 번 실패하고 나머지 두 번의 실행에서 네 번 모두 적중했다. 반면 (B)는 세 번 모두 다른 문자열이 되어 여섯 번 모두 실패했다. 로그에 찍힌 SQL도 (B)만 where b1_0.category='java'처럼 값이 SQL 안에 박혀 있었다. 값이 화면 입력에서 온다면 (B)는 주입 공격의 통로가 되고, 계획 캐시 2048칸을 서로 다른 문자열로 채우며 매번 파싱 비용을 다시 낸다. Querydsl을 쓰면 이 실수를 하려고 해도 하기 어렵다. 조건 값은 항상 상수 객체로 트리에 들어가고, 직렬화기가 그것을 파라미터로 바꾸기 때문이다.

    기본 Q 타입 활용: 변수 하나가 JPQL 식별 변수 하나다

    Q 타입은 애노테이션 프로세서가 엔티티마다 만들어 주는 쿼리용 타입이다. 생성된 QBook의 핵심 부분은 이렇다.

    public class QBook extends EntityPathBase {

    public static final QBook book = new QBook("book");

    public final StringPath category = createString("category");
    public final NumberPath id = createNumber("id", Long.class);
    public final NumberPath pages = createNumber("pages", Integer.class);
    public final NumberPath price = createNumber("price", Integer.class);
    public final StringPath title = createString("title");

    public QBook(String variable) {
        super(Book.class, forVariable(variable));
    }
    // 다른 생성자 ...
}

    세 가지를 읽어 낼 수 있다. 첫째, 엔티티의 속성 하나가 public final 필드 하나가 된다. 문자열 속성은 StringPath, 숫자 속성은 NumberPath가 되고, 원시 타입 int price도 NumberPath로 박싱된 타입을 쓴다. 이 타입들이 contains나 between 같은 메서드를 어느 속성에서 쓸 수 있는지를 정한다. StringPath에는 like와 contains가 있고 NumberPath에는 goe와 sum이 있다. 둘째, 생성자의 문자열 인자 variable이 forVariable을 거쳐 경로의 루트가 된다. 이 문자열이 JPQL의 식별 변수(identification variable), 흔히 별칭이라 부르는 것이 된다. 셋째, 미리 만들어 둔 정적 인스턴스 QBook.book의 별칭은 "book"이다.

    Querydsl 레퍼런스의 「Using query types」 절도 같은 두 가지 사용법을 보여 준다. 정적 필드로 노출된 기본 인스턴스를 쓰거나, new QCustomer("myCustomer")처럼 별칭을 직접 정해 새 인스턴스를 만드는 것이다. 두 방식이 만드는 JPQL을 비교해 보자.

    import static lab.QBook.book;   // 정적 임포트로 기본 인스턴스 사용

queryFactory.selectFrom(book).where(book.title.eq("SQL 첫걸음"));

QBook b = new QBook("b");        // 별칭을 직접 지정
queryFactory.selectFrom(b).where(b.price.gt(20000));
    select book
from Book book
where book.title = ?1

select b
from Book b
where b.price > ?1

    보통은 정적 임포트한 기본 인스턴스가 가장 읽기 좋다. 그런데 기본 별칭이 항상 클래스 이름의 첫 글자를 소문자로 바꾼 것은 아니다. 이 실험에서 엔티티 Member와 Order를 함께 만들어 보니 생성된 코드는 new QMember("member1"), new QOrder("order1")이었다. JPA 3.1 명세 4.4.1절의 예약 식별자 목록에 MEMBER(MEMBER OF 연산자)와 ORDER(ORDER BY)가 있고, 같은 절은 예약 식별자를 식별 변수로 쓰면 안 된다고 규정한다. Querydsl 코드 생성기(querydsl-codegen)에도 Keywords.JPA라는 예약어 목록이 들어 있으며 그 안에 MEMBER와 ORDER가 있다. 이름이 예약어와 겹치면 뒤에 1을 붙여 충돌을 피한 것이다. 로그에서 member1이라는 별칭을 보고 당황할 필요가 없다.

    명세 4.4.2절은 식별 변수가 같은 영속성 유닛의 엔티티 이름과 같아서는 안 되며 식별 변수는 대소문자를 구분하지 않는다고도 적는다. 이 기준을 엄격히 적용하면 Book book은 엔티티 이름 Book과 겹친다. 그러나 이번 실험의 Hibernate 6.6은 select book from Book book을 아무 문제 없이 처리했다. 다른 JPA 구현체로 옮길 일이 있다면 별칭을 명시하는 편이 안전하다.

    같은 엔티티를 두 번 써야 할 때

    별칭을 직접 정해야 하는 진짜 이유는 같은 엔티티를 한 쿼리에서 두 번 참조할 때 생긴다. 예를 들어 "「HTTP 완벽 정리」보다 비싼 책"을 구하려면 기준이 되는 책과 비교 대상이 되는 책이 각각 필요하다. 같은 인스턴스를 두 번 넘기면 어떻게 될까.

    queryFactory.select(book.title).from(book, book);           // 같은 인스턴스 두 번

QBook other = new QBook("other");
queryFactory.select(book.title).from(book, other)
    .where(other.title.eq("HTTP 완벽 정리"), book.price.gt(other.price));
    select book.title
from Book book

select book.title
from Book book, Book other
where other.title = ?1 and book.price > other.price

    같은 인스턴스를 두 번 넘긴 첫 쿼리는 from 절에 Book book이 한 번만 남았다. 오류도 경고도 없이 조용히 하나로 합쳐진 것이다. Q 타입 인스턴스 하나가 곧 식별 변수 하나이므로, 같은 인스턴스는 몇 번을 넘겨도 같은 행을 가리키는 같은 변수다. 서로 다른 두 행을 비교하려면 별칭이 다른 인스턴스가 두 개 있어야 한다. 이 원리는 03회에서 서브쿼리를 쓸 때 다시 중요해진다. 바깥 쿼리와 서브쿼리가 같은 엔티티를 대상으로 할 때 같은 인스턴스를 쓰면 두 쿼리의 변수가 뒤섞이기 때문이다. 두 번째 쿼리처럼 from에 엔티티를 나열하는 세타 조인 자체도 03회에서 다룬다.

    검색 조건 쿼리: 메서드 하나가 JPQL 연산자 하나로

    검색 조건은 경로 객체의 메서드로 만든다. 메서드 이름은 SQL 연산자를 영어 약어로 옮긴 것이 대부분이라 금방 익숙해진다. 중요한 것은 각 메서드가 어떤 JPQL을 만드는지 정확히 아는 것이다. 아래 표의 오른쪽 열은 추측이 아니라 각 조건으로 만든 쿼리의 toString() 결과에서 where 절만 옮긴 것이다.

    Querydsl만들어진 JPQL where 절뜻
    book.title.eq("A")book.title = ?1같다
    book.title.ne("A")book.title <> ?1같지 않다
    book.title.eq("A").not()not book.title = ?1"같다"의 부정
    book.pages.isNull() / isNotNull()book.pages is null / is not nullNULL 검사

    goe, gt, loe, lt>=, >, <=, <크기 비교

    contains, startsWith, endsWithbook.title like ?1 escape '!'패턴을 대신 만들어 줌

    몇 가지는 설명이 필요하다. between은 양 끝을 포함한다. JPA 3.1 명세 4.6.8절은 x BETWEEN y AND z가 y <= x AND x <= z와 의미가 같다고 정의한다. 실제로 book.price.between(21000, 28000)은 정확히 21000원인 「HTTP 완벽 정리」와 28000원인 「자바 동시성」을 모두 포함해 세 권(자바 동시성, 인덱스 설계, HTTP 완벽 정리)을 돌려주었다. 반쯤 열린 구간(예: 이상·미만)이 필요하면 where(book.price.goe(a), book.price.lt(b))처럼 두 조건으로 쓴다. 날짜 구간을 다룰 때 특히 중요하다. "하루 전체"를 between으로 쓰면 다음 날 0시 정각이 포함되기 때문이다.

    in의 JPQL에는 ?1 하나만 있다. Querydsl은 값 목록 전체를 컬렉션 하나로 묶어 파라미터 하나에 바인딩하고, Hibernate가 SQL로 바꿀 때 원소 수만큼 자리표시자를 펼친다. 실행된 SQL은 where b1_0.category in (?,?)였고 java 두 권과 db 세 권, 모두 다섯 권이 나왔다. 원소 수가 바뀌면 SQL 문자열의 자리표시자 수도 바뀐다는 점은 기억해 둘 만하다. JPQL 문자열은 같아도 최종 SQL은 원소 수마다 다른 문장이 된다.

    eq(null)은 왜 막혀 있는가: 3값 논리

    쪽수를 모르는 책을 찾으려고 book.pages.eq(null)을 쓰면 컴파일은 되지만 실행 중에 이런 예외가 난다.

    java.lang.IllegalArgumentException: eq(null) is not allowed. Use isNull() instead

    Querydsl이 일부러 막아 둔 것이다. 이유는 SQL의 NULL 의미론에 있다. JPA 3.1 명세 4.11절은 SQL의 NULL 의미론을 따른다고 하면서, NULL과의 비교나 산술 연산은 항상 알 수 없음(unknown)을 낳고 두 NULL도 같은 것으로 보지 않는다고 요약한다. where pages = NULL은 어떤 행에서도 참이 될 수 없으므로 항상 빈 결과를 낸다. 사용자는 "NULL인 행"을 원했을 텐데 조용히 빈 목록이 나오면 버그를 찾기 어렵다. 그래서 Querydsl은 이 경우를 예외로 바꾸고 isNull()을 쓰라고 알려 준다. 명세 4.11절이 적듯 IS NULL과 IS NOT NULL은 NULL을 참·거짓으로 바꿔 주는 연산자다.

    같은 3값 논리 때문에 ne도 주의해야 한다. "쪽수가 240이 아닌 책"을 구하면 쪽수를 모르는 두 권은 빠진다.

    queryFactory.select(book.title).from(book).where(book.pages.ne(240)).fetch();
queryFactory.select(book.title).from(book).where(book.pages.ne(240).or(book.pages.isNull())).fetch();
    where b1_0.pages<>?                      → [JVM 밑바닥, 인덱스 설계, 100% 실전 SQL]
where b1_0.pages<>? or b1_0.pages is null → [JVM 밑바닥, 자바 동시성, 인덱스 설계, HTTP 완벽 정리, 100% 실전 SQL]

    NULL인 행에서 pages <> 240은 참도 거짓도 아닌 알 수 없음이 되고, WHERE 절은 참인 행만 통과시키므로 그 행은 버려진다. "240이 아닌 것"에 "모르는 것"까지 넣고 싶다면 두 번째 줄처럼 isNull()을 or로 명시해야 한다. 이것은 Querydsl의 성질이 아니라 SQL의 성질이다. 문자열 JPQL이든 Querydsl이든 똑같이 일어난다.

    like와 이스케이프: contains가 대신해 주는 일

    표에서 like와 contains는 똑같이 like ?1 escape '!'를 만들었다. 차이는 JPQL 문자열이 아니라 바인딩되는 값에 있다. JPQLSerializer를 직접 돌려 직렬화 결과와 상수 목록을 함께 찍어 보았다. 이 실험에는 제목이 「A_B 패턴」, 「AXB 패턴」인 책 두 권을 추가로 넣었다.

    JPQLSerializer s = new JPQLSerializer(HQLTemplates.DEFAULT);
s.serialize(query.getMetadata(), false, null);
System.out.println(s + "   constants=" + s.getConstants());
    Querydsl바인딩된 값일치한 제목
    title.like("A_B%")A_B%A_B 패턴, AXB 패턴
    title.contains("A_B")%A!_B%A_B 패턴
    title.contains("%")%!%%100% 실전 SQL
    title.startsWith("100%")100!%%100% 실전 SQL
    title.like("100!%%")100!!%%없음
    title.like("100#%%", '#')100#%% (JPQL은 escape '#')100% 실전 SQL
    title.containsIgnoreCase("sql")%sql% (왼쪽은 lower(book.title))—

    규칙이 보인다. like는 넘긴 패턴을 거의 그대로 쓴다. %와 _는 와일드카드로 남으므로 like("A_B%")의 _는 "아무 글자 하나"가 되어 「AXB 패턴」까지 일치했다. 반면 contains, startsWith, endsWith는 사용자가 넘긴 문자열을 글자 그대로 찾는다. 그래서 값 안의 %와 _ 앞에 이스케이프 문자 !를 붙이고, 앞뒤에 필요한 %만 덧붙인다. 검색창에 사용자가 %를 입력해도 와일드카드로 해석되지 않는 이유다.

    흥미로운 줄은 like("100!%%")다. !를 이스케이프 문자로 써서 "100%로 시작"을 표현하려 했지만 아무것도 찾지 못했다. 바인딩된 값을 보면 !가 !!로 두 번 쓰였다. Querydsl은 like의 패턴 안에 있는 이스케이프 문자 자체를 다시 이스케이프한다. 그 결과 패턴은 "100!로 시작하는 문자열"이 되어 버렸다. 사용자가 직접 이스케이프하고 싶다면 마지막에서 두 번째 줄처럼 이스케이프 문자를 인자로 받는 like(String, char)를 쓰면 된다. 그러면 JPQL이 escape '#'로 바뀌고 패턴은 그대로 바인딩된다.

    패턴의 모양은 인덱스 사용과 직결된다. MySQL 8.0 레퍼런스 매뉴얼의 B-tree와 해시 인덱스 비교 절은 LIKE의 인자가 와일드카드로 시작하지 않는 상수 문자열이면 B-tree 인덱스를 쓸 수 있다고 설명하고, '%Patrick%'처럼 와일드카드로 시작하는 패턴은 인덱스를 쓰지 않는 예로 든다. B+Tree는 키를 정렬된 순서로 저장하므로 접두사가 정해져 있으면 그 접두사가 시작하는 지점과 끝나는 지점 사이의 구간만 읽으면 된다. 접두사가 없으면 시작 지점을 정할 수 없다. 따라서 startsWith는 인덱스 범위 탐색이 가능한 패턴(100!%%처럼 앞부분이 고정)을, contains는 원리상 범위 탐색이 불가능한 패턴(%...%)을 만든다. 메서드 이름 하나를 고르는 일이 실행 계획을 고르는 일이기도 하다.

    MySQL 8.4.13에서 앞의 여섯 권을 넣은 book 테이블의 title에 인덱스를 만들고 두 패턴의 실행 계획을 비교했다. 8.0.46에서도 같은 계획이 나왔다. 행 수 추정치는 통계에 따라 달라진다.

    explain select id, title from book b1_0 where b1_0.title like '100!%%' escape '!';   -- startsWith
explain select id, title from book b1_0 where b1_0.title like '%sql%' escape '!';    -- contains
    type   key        rows  filtered  Extra
range  idx_title     1    100.00  Using where; Using index     -- startsWith
index  idx_title     6     16.67  Using where; Using index     -- contains

    접두사가 고정된 패턴은 range, 곧 인덱스의 한 구간만 읽었다. %로 시작하는 패턴은 index, 곧 인덱스 전체를 처음부터 끝까지 훑으며 한 항목씩 패턴과 맞춰 보았다. 여기서 인덱스를 쓴 것은 고른 열(id, title)이 모두 인덱스 안에 있어 테이블보다 작은 인덱스를 훑는 편이 싸기 때문이지, 패턴으로 구간을 좁혔기 때문이 아니다.

    containsIgnoreCase는 열에 lower()를 씌운다. 인덱스는 열의 원래 값으로 정렬되어 있으므로 함수를 거친 값으로는 그 순서를 쓸 수 없다. 게다가 MySQL 8.0의 기본 콜레이션 utf8mb4_0900_ai_ci는 이름의 ci(case-insensitive)가 뜻하듯 이미 대소문자를 구분하지 않고 비교한다. 이런 환경이라면 contains만으로도 대소문자 구분 없는 검색이 되고, containsIgnoreCase는 함수 호출만 더할 뿐이다. 실제로 MySQL 8.0.46과 8.4.13(데이터베이스 기본 콜레이션 utf8mb4_0900_ai_ci)에서 select 'HTTP' = 'http'는 1(참)이었고, contains("sql")에 해당하는 like '%sql%' escape '!'만으로 「100% 실전 SQL」과 「SQL 첫걸음」이 모두 나왔다. lower()를 씌운 쿼리도 같은 두 행을 돌려주었다. 반대로 H2의 기본 설정처럼 대소문자를 구분하는 DB에서는 의미가 있다(H2 2.3.232에서 'HTTP' = 'http'는 거짓이었다). 같은 Querydsl 코드라도 DB와 콜레이션에 따라 결과와 비용이 달라진다.

    and, or, 그리고 where의 가변 인자

    조건을 조합하는 방법은 두 가지다. 조건 객체의 and(), or()를 이어 부르거나, where()에 조건을 쉼표로 여러 개 넘기는 것이다. Querydsl 레퍼런스는 where를 "가변 인자(varargs)로 쉼표로 나누거나 and 연산자로 이어서" 필터를 추가하는 곳이라고 설명한다. 쉼표로 넘긴 조건들은 and로 묶인다. 괄호가 어떻게 붙는지 보자.

    // (1)
book.category.eq("java").and(book.price.gt(30000)).or(book.pages.isNull())
// (2)
book.category.eq("java").and(book.price.gt(30000).or(book.pages.isNull()))
// (3) where 가변 인자, 가운데에 null
queryFactory.selectFrom(book).where(book.category.eq("java"), null, book.price.gt(30000));
    (1) where book.category = ?1 and book.price > ?2 or book.pages is null
(2) where book.category = ?1 and (book.price > ?2 or book.pages is null)
(3) where book.category = ?1 and book.price > ?2

    (1)에는 괄호가 없고 (2)에는 있다. JPA 3.1 명세 4.6.6절의 연산자 우선순위에서 논리 연산자는 NOT, AND, OR 순으로 강하다. 따라서 (1)의 JPQL은 (category = ?1 and price > ?2) or pages is null로 읽히고, 이것은 자바 코드에서 and를 먼저 부르고 그 결과에 or를 부른 트리 구조와 정확히 같다. 괄호가 없어도 의미가 같으니 직렬화기가 괄호를 생략했다. (2)는 or가 and의 오른쪽 자식인 트리다. 우선순위만으로는 이 구조를 표현할 수 없으니 괄호가 붙었다. 자바 코드의 메서드 호출 구조가 곧 트리 구조이고, 직렬화기는 그 트리를 우선순위 규칙에 맞춰 최소한의 괄호로 적는다.

    (3)은 where에 넘긴 null이 조용히 무시된다는 것을 보여 준다. 이 성질은 조건이 있을 때만 식을 만들고 없으면 null을 돌려주는 메서드를 여러 개 두고, 그 결과를 그대로 where에 넘기는 동적 쿼리 기법의 바탕이 된다. 동적 쿼리는 04회에서 BooleanBuilder와 함께 자세히 다룬다. 여기서는 "where의 가변 인자는 and로 결합되고 null은 건너뛴다"는 사실만 기억하자. 앞에서 본 eq(null)과 혼동하지 말아야 한다. 조건 값이 null인 것(eq(null), 예외)과 조건 식이 null인 것(where(..., null, ...), 무시)은 전혀 다른 경우다.

    결과 조회: fetch, fetchOne, fetchFirst

    쿼리를 다 조립했으면 결과를 꺼내야 한다. Querydsl 5의 Fetchable 인터페이스가 정의하는 결과 조회 메서드 가운데 이 회차에서 다룰 것은 다섯 가지다. 목록을 받는 fetch(), 한 건을 받는 fetchOne(), 첫 건을 받는 fetchFirst(), 그리고 개수가 붙은 fetchResults()와 개수만 받는 fetchCount()다. 앞의 세 개부터 실행해 보자.

    List none = queryFactory.selectFrom(book).where(book.category.eq("none")).fetch();
Book web   = queryFactory.selectFrom(book).where(book.category.eq("web")).fetchOne();
Book nobody = queryFactory.selectFrom(book).where(book.category.eq("none")).fetchOne();
Book java  = queryFactory.selectFrom(book).where(book.category.eq("java")).fetchOne();   // 두 권
Book first = queryFactory.selectFrom(book).where(book.category.eq("java")).fetchFirst();

    fetch()는 결과가 없으면 null이 아니라 빈 목록을 준다. 호출하는 쪽에서 null 검사를 할 필요가 없다. fetchOne()은 결과가 없으면 null, 한 건이면 그 객체, 두 건 이상이면 예외다. 예외의 모양을 보면 Querydsl이 하는 일이 드러난다. 바깥은 Querydsl의 com.querydsl.core.NonUniqueResultException이고 그 원인(cause)은 JPA의 jakarta.persistence.NonUniqueResultException이다. 바이트코드를 보면 fetchOne()은 JPA의 Query.getSingleResult()를 호출하고, JPA가 던지는 NoResultException은 null로, NonUniqueResultException은 Querydsl의 같은 이름 예외로 바꾼다. JPA의 getSingleResult()는 결과가 없으면 예외를 던지는데 Querydsl은 그것을 null로 완화한 것이다.

    SQL을 다시 보자. fetchOne()의 SQL에는 행 수 제한이 없다. 조건이 실제로 유일한지 DB에 묻는 장치가 따로 있는 것이 아니라, 일단 결과를 받아 보고 개수를 세는 것이다. 테이블 전체를 대상으로 queryFactory.selectFrom(book).fetchOne()을 실행하자 SQL은 조건 없는 select ... from Book b1_0이었고 예외 메시지는 "6 results were returned"였다. 즉 Hibernate는 여섯 행을 모두 읽은 뒤에야 유일하지 않다는 것을 알렸다. 조건이 유일하다고 착각한 쿼리가 수십만 행에 일치한다면, 그 행을 모두 전송받고 엔티티로 만든 뒤에 예외가 난다. fetchOne()은 기본 키나 유니크 제약이 걸린 열처럼 유일성이 DB에서 보장되는 조건에만 쓰는 것이 맞다.

    fetchFirst()는 Querydsl 안에서 limit(1).fetchOne()으로 구현되어 있다. 그래서 SQL에 fetch first ? rows only가 붙었고(H2 방언), 두 권 중 한 권만 돌아왔다. 그런데 "첫 번째"란 무엇일까. 이 쿼리에는 orderBy가 없다. SQL에서 ORDER BY가 없는 결과의 순서는 정의되지 않으므로, 이번에 「JVM 밑바닥」이 나온 것은 H2가 이번에 그 순서로 읽었기 때문일 뿐이다. 실행 계획이나 데이터 배치가 바뀌면 다른 책이 나올 수 있다. 의미 있는 "첫 번째"가 필요하면 반드시 정렬 기준을 함께 준다.

    fetchResults와 fetchCount는 왜 폐기 예정이 되었나

    목록 화면에는 보통 "전체 몇 건 중 몇 번째 페이지"가 필요하다. 이 요구를 한 번에 해결해 주던 것이 fetchResults()다. 실행하면 두 개의 SQL이 나간다.

    QueryResults r = queryFactory.selectFrom(book)
        .orderBy(book.price.desc())
        .offset(1).limit(2)
        .fetchResults();
System.out.println(r.getTotal() + " " + r.getOffset() + " " + r.getLimit() + " " + r.getResults());

    첫 SQL은 같은 조건으로 만든 count 쿼리다. 정렬은 개수에 영향이 없으므로 order by가 빠졌고, 페이징도 빠졌다. 두 번째가 실제 내용을 가져오는 쿼리다. 조건에 맞는 행이 0건이면 어떻게 될까. where(book.category.eq("none"))으로 실행하자 count 쿼리 하나만 나가고 결과는 0 []였다. 개수가 0이면 내용 쿼리를 생략하는 최적화가 들어 있다. fetchCount()는 이 중 count 쿼리만 실행한다.

    편리해 보이는 이 두 메서드는 Querydsl 5.1.0에서 폐기 예정 상태다. javap -v로 확인하면 Fetchable 인터페이스의 선언에는 표시가 없지만, JPA 모듈의 구현인 com.querydsl.jpa.impl.AbstractJPAQuery의 fetchCount()와 fetchResults()에는 @Deprecated가 붙어 있다. Javadoc은 이유를 이렇게 설명한다. 두 메서드는 count 쿼리를 계산해야 하는데, JPQL은 서브쿼리를 프로젝션의 대상으로 삼는 것, 곧 select count(*) from (원래 쿼리) 같은 형태를 허용하지 않는다. 그래서 어떤 쿼리든 감싸서 셀 수 있는 일반적인 방법이 없다. 특히 group by가 여러 개인 쿼리와 having이 있는 쿼리가 문제이며, 그런 경우에는 개수를 메모리에서 계산한다.

    실제로 어떻게 동작하는지 세 경우를 비교했다.

    // (1) group by 하나
queryFactory.select(book.category).from(book).groupBy(book.category).fetchCount();
// (2) group by 하나 + having
queryFactory.select(book.category).from(book).groupBy(book.category)
        .having(book.count().gt(1L)).fetchCount();
// (3) group by 둘
queryFactory.select(book.category, book.pages).from(book)
        .groupBy(book.category, book.pages).fetchCount();

    (1)에서 Querydsl은 "그룹의 개수 = 그룹 키의 서로 다른 값의 개수"라는 성질을 이용해 count(distinct category)로 바꿨다. 여기까지는 JPQL로 표현된다. (2)는 그렇게 바꿀 수 없다. having은 그룹을 만든 뒤 집계 결과로 그룹을 거르는 조건이라, 서로 다른 키의 개수만 세서는 몇 그룹이 살아남는지 알 수 없다. (3)도 마찬가지다. 여러 열의 조합을 세려면 count(distinct category, pages) 같은 식이 필요한데, Javadoc의 설명대로 이것은 여러 SQL 방언에서 쓰이지만 JPQL에서는 유효하지 않다. 그래서 (2)와 (3)은 원래 쿼리를 그대로 실행해 결과를 전부 받아 온 뒤 목록의 크기를 센다. 결과는 맞지만, 그룹이 수십만 개라면 개수 하나를 얻으려고 수십만 행을 전송받는다. JUL(java.util.logging)로 찍힌 경고가 유일한 신호인데, 로그 설정에 따라 이 경고는 보이지 않을 수도 있다.

    그래서 권장하는 방법은 count 쿼리를 직접 쓰는 것이다. 목록 쿼리와 같은 조건을 쓰되, 프로젝션을 개수로 바꾼다.

    Long total = queryFactory
        .select(book.count())
        .from(book)
        .where(book.price.gt(20000))
        .fetchOne();          // 집계 결과는 항상 한 행이므로 fetchOne이 안전하다

    직접 쓰면 무엇을 세는지 코드에 드러나고, 목록 쿼리에는 필요하지만 개수에는 필요 없는 부분(정렬, 결과에 영향이 없는 조인 등)을 빼서 더 가볍게 만들 수 있다. 그래도 count 쿼리가 공짜는 아니라는 점은 알아 두자. 아래 페이징 절의 H2 실험에서 10만 행 중 price > 50000인 행을 세는 count(*)는 인덱스를 쓰면서도 scanCount: 50001을 기록했다. 개수를 알려면 조건에 맞는 항목을 하나씩 다 지나가야 한다. 스프링 데이터의 Page와 결합할 때 count 쿼리를 생략할 수 있는 경우를 골라내는 기법은 06회에서 다룬다.

    정렬: 방향, 우선순위, 그리고 NULL의 자리

    정렬은 orderBy()에 정렬 지정자(OrderSpecifier)를 넘겨 한다. 숫자, 문자열처럼 비교 가능한 식에는 asc()와 desc()가 있다. 여러 개를 넘기면 왼쪽이 우선이다. JPA 3.1 명세 4.9절도 여러 정렬 항목이 있으면 왼쪽에서 오른쪽 순서가 우선순위를 정한다고 규정한다.

    queryFactory.selectFrom(book).orderBy(book.price.desc(), book.id.asc()).fetch();
    Hibernate: select ... from Book b1_0 order by b1_0.price desc,b1_0.id

    SQL에서 b1_0.id 뒤에 asc가 없는 것은 오름차순이 기본값이기 때문이다. 가격이 모두 달라 두 번째 기준 id는 이 데이터에서는 결과에 영향을 주지 않았다. 그래도 붙여 두는 이유가 있다. MySQL 8.0 레퍼런스 매뉴얼의 「LIMIT Query Optimization」 절은 여러 행이 ORDER BY 열에서 같은 값을 가지면 서버는 그 행들을 어떤 순서로든 돌려줄 수 있고, 실행 계획에 따라 다르게 돌려줄 수도 있다고 적는다. 그리고 LIMIT이 있을 때와 없을 때 같은 순서를 보장하려면 순서를 결정적으로 만드는 열을 ORDER BY에 추가하라고 권한다. 정렬 키가 겹칠 수 있는 데이터를 페이징하면 같은 행이 두 페이지에 나오거나 어느 페이지에도 나오지 않을 수 있다. 기본 키처럼 유일한 열을 마지막 정렬 기준으로 두면 이 문제가 사라진다.

    NULL은 어디에 놓이는가

    쪽수(pages)로 정렬하면 쪽수를 모르는 두 권은 어디로 갈까. JPA 3.1 명세 4.9절은 SQL 규칙에 따라 모든 NULL이 모든 비NULL 값보다 앞에 오거나 모두 뒤에 와야 하지만, 어느 쪽인지는 정하지 않는다고 적는다. 즉 DB마다 다르다. MySQL 8.0 매뉴얼의 「Working with NULL Values」 절은 ORDER BY ... ASC에서는 NULL이 먼저, DESC에서는 나중에 나온다고 밝힌다. NULL을 가장 작은 값처럼 다루는 것이다. 이번 실험의 H2도 같은 결과를 냈고, 같은 여섯 행을 넣은 MySQL 8.0.46과 8.4.13에서 order by b1_0.pages와 order by b1_0.pages desc를 직접 실행한 결과도 아래 H2 결과와 순서가 같았다(NULL 두 권끼리의 순서까지 같았지만, 이것은 보장된 것이 아니다).

    orderBy(book.pages.asc())  → order by b1_0.pages

    NULL 두 권끼리의 순서는 정렬 키가 같으므로 앞 단락의 설명대로 보장되지 않는다. Querydsl은 NULL의 위치를 명시하는 nullsFirst()와 nullsLast()를 제공한다. 이것은 JPQL로 nulls first, nulls last가 된다. JPA 3.1 명세의 ORDER BY 문법에는 없는 구문이지만, Hibernate 6.6의 HQL 문법은 nullsPrecedence로 이것을 지원한다. 흥미로운 것은 같은 JPQL이 DB 방언에 따라 다른 SQL이 된다는 점이다.

H2Dialect와 MySQLDialect의 getNullOrdering()은 모두 NullOrdering.SMALLEST, 곧 "NULL은 가장 작은 값"을 돌려준다. 그러면 desc nulls last는 그 DB가 원래 하는 동작이므로 굳이 적을 필요가 없어 생략된다. 첫 두 줄이 그렇다. 기본 동작과 다를 때(asc nulls last)는 방언의 supportsNullPrecedence()를 묻는다. NULL이면 1, 아니면 0인 case 식을 먼저 정렬 키로 두어 비NULL 행(0)이 앞에, NULL 행(1)이 뒤에 오게 한 다음 원래 열로 정렬하는 것이다. 반대 경우인 desc().nullsFirst()도 MySQL 방언에서 확인했는데, 이번에는 0과 1이 뒤바뀐 order by case when (b1_0.pages) is null then 0 else 1 end,b1_0.pages desc가 나왔다.

    H2에서 orderBy(book.pages.asc().nullsLast(), book.title.asc())의 결과는 [SQL 첫걸음(240), 인덱스 설계(310), 100% 실전 SQL(400), JVM 밑바닥(520), HTTP 완벽 정리(null), 자바 동시성(null)]이었다. 두 번째 기준인 제목 덕분에 NULL 두 권의 순서도 결정되었다(H의 코드 값이 한글 자보다 작다). MySQL 방언이 만든 order by case when (b1_0.pages) is null then 1 else 0 end,b1_0.pages에 ,b1_0.title을 덧붙여 MySQL 8.0.46과 8.4.13에서 직접 실행해도 똑같은 순서가 나왔다. desc().nullsFirst()의 SQL은 NULL 두 권을 앞에 두고 520, 400, 310, 240 순서로 이어졌다. 반대로 order by b1_0.pages asc nulls last를 MySQL에 그대로 보내면 두 버전 모두 ERROR 1064 (42000): You have an error in your SQL syntax; ... near 'NULLS LAST'로 거부했다. 방언이 supportsNullPrecedence()에 false를 답하는 이유다.

    페이징: offset과 limit은 JPQL이 아니라 Query 객체에 실린다

    출력된 JPQL에는 offset도 limit도 없다. 페이징 정보는 JPQL 문자열이 아니라 JPA Query 객체의 setFirstResult(2)와 setMaxResults(2)로 전달된다. 앞에서 본 createQuery 바이트코드의 순서 그대로다. Querydsl은 이 표준 메서드를 쓰는 쪽을 택했으므로, 실제 SQL 구문은 Hibernate 방언이 정한다.

MySQL 8.0.46과 8.4.13에서 값을 채워 직접 실행해도 같았다. order by b1_0.price desc limit 2,2는 「자바 동시성」, 「인덱스 설계」를, limit 3,2147483647은 나머지 세 권(「인덱스 설계」, 「HTTP 완벽 정리」, 「SQL 첫걸음」)을, limit 10,2는 빈 결과를 돌려주었다. 정렬 없이 페이징만 하면 어떻게 될까. offset(1).limit(2)를 정렬 없이 실행한 결과는 「자바 동시성」, 「SQL 첫걸음」이었는데, 이것은 이번 실행에서 H2가 읽은 순서일 뿐이다. 순서가 정의되지 않은 결과를 잘라 페이지를 만들면 페이지 사이에 중복과 누락이 생길 수 있다. 페이징에는 항상 결정적인 정렬이 짝으로 따라와야 한다.

    오프셋의 비용: 건너뛴 행도 읽는다

    "앞의 N개를 건너뛴다"는 말은 DB가 그 N개를 읽지 않는다는 뜻이 아니다. H2에서 10만 행짜리 테이블에 가격 인덱스를 만들고, EXPLAIN ANALYZE로 실제로 몇 행을 훑었는지 확인했다.

    create table item(id bigint primary key, price int, name varchar(50));
create index idx_price on item(price);
insert into item select x, mod(x*7919, 100000), 'n'||x from system_range(1, 100000);

explain analyze select id, price, name from item order by price offset 0 rows fetch first 10 rows only;
explain analyze select id, price, name from item order by price offset 50000 rows fetch first 10 rows only;
explain analyze select id, price, name from item where price > 99000 order by price fetch first 10 rows only;

/* PUBLIC.IDX_PRICE */  /* scanCount: 50010 */  OFFSET 50000 ROWS FETCH NEXT 10 ROWS ONLY  /* index sorted */
/* PUBLIC.IDX_PRICE: PRICE > 99000 */  /* scanCount: 11 */  FETCH FIRST 10 ROWS ONLY  /* index sorted */

    세 쿼리 모두 가격 인덱스를 정렬 순서로 그대로 따라갔다(index sorted). 따로 정렬하지 않으니 첫 페이지는 10행만 읽고 끝났다. 그러나 오프셋이 50000인 페이지는 같은 10행을 얻으려고 50010행을 훑었다. scanCount가 보여 주듯 엔진은 건너뛸 5만 개 항목도 인덱스를 따라 하나씩 지나간 뒤에야 돌려줄 행에 도달했다. 오프셋은 "읽지 않는다"가 아니라 "읽고 버린다"는 뜻이다. 페이지 번호가 커질수록 비용이 선형으로 늘어나는 이유다. MySQL 8.0 매뉴얼의 「LIMIT Query Optimization」 절은 LIMIT row_count를 ORDER BY와 함께 쓰면 정렬된 결과의 처음 row_count 행을 찾는 즉시 정렬을 멈춘다고 설명한다. 행 수 제한이 비용을 줄이는 원리는 "앞쪽 일부만 만들면 된다"는 데 있고, 오프셋이 크면 그 "앞쪽"이 오프셋만큼 길어진다.

    같은 테이블과 데이터(10만 행, 가격은 0부터 99999까지 모두 다른 값)를 MySQL에 만들어 EXPLAIN ANALYZE로 확인했다. 데이터는 system_range 대신 재귀 CTE로 만들었고, 페이징은 MySQL 문법인 limit 오프셋, 개수로 썼다. 실행 시간과 비용 추정치는 실행 환경과 통계에 따라 달라진다.

    insert into item
with recursive s(x) as (select 1 union all select x+1 from s where x < 100000)
select x, mod(x*7919, 100000), concat('n', x) from s;   -- cte_max_recursion_depth를 세션에서 100000으로 올렸다

explain analyze select id, price, name from item order by price limit 50000, 10;

MySQL 8.0.46에서도 네 쿼리의 계획과 실제 행 수가 같았다.

    세 번째 쿼리는 다른 길을 보여 준다. 마지막으로 본 값(여기서는 99000)보다 큰 행부터 10개를 가져오면, 엔진은 인덱스에서 99000 다음 위치로 바로 내려가 11행만 훑었다. 이것이 키셋 페이징(keyset pagination, seek 방식)의 원리다. Querydsl로는 where(book.price.gt(lastPrice)).orderBy(book.price.asc()).limit(10)처럼 쓴다. 대신 "37페이지로 바로 이동" 같은 임의 접근은 할 수 없고, 정렬 키가 겹칠 수 있으면 기본 키까지 묶어 비교하는 조건이 필요하다. 어느 쪽을 쓸지는 화면 요구와 데이터 크기로 정한다.

    SUM의 반환 타입: 명세는 Long, Querydsl은 Integer

    위 결과에서 이상한 점이 하나 있다. book.price.sum()의 결과가 java.lang.Integer다. 그런데 JPA 3.1 명세 4.8.5절은 집계 결과의 자바 타입을 이렇게 정한다. COUNT는 Long, MAX와 MIN은 적용한 필드의 타입, AVG는 Double, 그리고 SUM은 정수 타입 필드(BigInteger 제외)에 적용하면 Long이다. Hibernate 6.6 HQL 가이드의 sum() 결과 타입 표도 같다. 문자열 JPQL로 같은 집계를 실행해 보면 명세대로다.

        .groupBy(book.category)
        .having(book.count().gt(1L))
        .orderBy(book.category.asc())

JPA 3.1 명세 4.7절도 HAVING을 "그룹에 대한 제약"으로 정의한다. 그래서 count(book) > 1 같은 집계 조건은 where에 쓸 수 없고, 반대로 개별 행 조건(예: 가격이 20000원 이상인 책만 집계)은 where에 두어야 그룹을 만들기 전에 행 수가 줄어 DB가 할 일이 줄어든다. 같은 결과를 내는 조건이라도 having보다 where에 둘 수 있으면 where에 두는 것이 원칙이다.

    이 예제는 Tuple을 그대로 썼다. Tuple은 Querydsl의 타입이고 값을 꺼내려면 쿼리에 쓴 식 객체가 있어야 하므로, 리포지토리 바깥으로 내보내면 서비스나 컨트롤러가 Querydsl에 의존하게 된다. 리포지토리 안에서 DTO로 바꿔 내보내는 프로젝션 기법은 04회에서 다룬다.

    흔한 오해와 함정

    • "Querydsl을 쓰면 쿼리 오류가 전부 컴파일 시점에 잡힌다." 속성 이름과 비교 값의 타입 오류가 잡힐 뿐이다. eq(null)은 실행 중에 예외가 나고, DB가 지원하지 않는 구문, 의도와 다른 조건(ne가 NULL을 빼는 것), 성능 문제는 여전히 실행해 봐야 안다.
    • "QBook.book을 여러 번 쓰면 같은 테이블을 여러 번 참조할 수 있다." 같은 인스턴스는 같은 식별 변수다. from(book, book)은 조용히 하나로 합쳐졌다. 서로 다른 행을 비교하려면 별칭이 다른 인스턴스를 만든다.
    • "like와 contains는 같은 것이다." JPQL은 같아도 바인딩 값이 다르다. like는 %와 _를 와일드카드로 두고, contains는 그것들을 이스케이프해 글자 그대로 찾는다. 앞에 %가 붙는 패턴은 B-tree 인덱스로 범위 탐색을 할 수 없다.
    • "fetchOne()은 한 행만 가져온다." 행 수 제한 없이 전부 읽은 뒤 개수를 센다. 행 수를 제한하는 것은 fetchFirst()다.
    • "fetchResults()의 count는 언제나 count 쿼리다." having이나 여러 group by가 있으면 원래 쿼리 결과를 전부 받아 메모리에서 센다. 그래서 폐기 예정이 되었고, count 쿼리는 직접 쓰는 것이 권장된다.
    • "NULL은 항상 정렬의 끝에 온다." 명세는 위치를 정하지 않고 DB마다 다르다. MySQL과 H2는 NULL을 가장 작은 값처럼 다룬다. nullsLast()는 방언에 따라 생략되거나, 그대로 출력되거나, case 식으로 흉내 내어진다.
    • "sum()의 결과 타입은 DB가 정한다." Querydsl에서는 식의 선언 타입이 정한다. NumberPath의 합계는 Integer로 축소 변환되어 범위를 넘으면 조용히 틀린 값이 된다. 금액 합계에는 longValue()를 쓴다.
    • "offset이 크면 DB가 그만큼 건너뛰어 준다." 건너뛸 행도 읽는다. H2 실측에서 offset 50000은 50010행을 훑었다.
    이 장의 핵심

    Querydsl의 기본 문법은 JPQL 연산자 하나하나에 대응하는 메서드의 모음이고, 그 메서드들이 만드는 것은 바뀌지 않는 식 트리다. 트리는 fetch 계열 메서드가 불릴 때 JPQL 문자열과 상수 목록으로 직렬화되고, 페이징은 setFirstResult·setMaxResults로, 결과는 식의 선언 타입에 맞춘 변환을 거쳐 돌아온다. 그래서 메서드가 무엇을 만드는지(JPQL), Hibernate가 그것을 어떤 SQL로 바꾸는지(방언), DB가 그 SQL을 어떻게 실행하는지(인덱스와 스캔), 결과가 어떤 자바 타입으로 돌아오는지(변환) 네 층을 함께 볼 때 Querydsl을 제대로 쓸 수 있다.

    다른 회차와의 연결

    이 회차에서 본 별칭 규칙은 03회의 조인과 서브쿼리에서 곧바로 다시 쓰인다. 조인 대상마다, 서브쿼리마다 별칭이 다른 Q 타입 인스턴스가 필요하기 때문이다. 페이징과 컬렉션 페치 조인의 충돌도 03회의 주제다. Tuple 대신 DTO로 결과를 받는 프로젝션, where의 null 무시를 이용한 동적 쿼리, 벌크 연산은 04회에서 다룬다. 05회에서는 JPAQueryFactory를 스프링 빈으로 등록할 때 주입되는 EntityManager 프록시와 스레드 안전성을, 06회에서는 이 회차에서 따로 작성한 count 쿼리를 스프링 데이터의 Page와 결합하고 필요 없을 때 생략하는 방법을 본다. 07회는 스프링 데이터 JPA가 제공하는 Querydsl 지원 기능을 다룬다.
    식 트리(expression tree)
    Querydsl의 조건과 프로젝션은 연산자를 마디로, 경로와 상수를 잎으로 하는 바뀌지 않는 객체 트리다. fetch 계열 메서드가 불릴 때 JPQL로 직렬화된다.
    Q 타입과 별칭
    Q 타입 인스턴스 하나가 JPQL 식별 변수 하나다. 기본 인스턴스의 별칭은 보통 소문자 클래스 이름이지만 JPQL 예약어와 겹치면 member1처럼 바뀐다.
    위치 파라미터 바인딩
    조건 값은 ?1 같은 위치 파라미터로 바인딩된다. 값이 달라도 JPQL 문자열이 같아 Hibernate 쿼리 계획 캐시를 재사용하고 SQL 주입을 막는다.
    검색 조건과 NULL
    eq(null)은 예외로 막혀 있고 isNull()을 써야 한다. NULL과의 비교는 알 수 없음이 되므로 ne는 NULL 행을 빼고 돌려준다.
    like와 contains
    like는 패턴을 그대로 쓰고, contains·startsWith·endsWith는 %와 _를 !로 이스케이프한다. 와일드카드로 시작하는 패턴은 B-tree 인덱스 범위 탐색을 쓸 수 없다.
    fetchOne과 fetchFirst
    fetchOne()은 제한 없이 읽어 0건이면 null, 2건 이상이면 예외다. fetchFirst()는 limit(1).fetchOne()이며 정렬 없이는 어떤 행이 나올지 정해지지 않는다.
    count 쿼리
    JPQL에는 FROM 절 서브쿼리가 없어 모든 쿼리를 감싸 셀 수 없다. 그래서 fetchResults·fetchCount는 폐기 예정이고, select(book.count())로 count 쿼리를 직접 쓴다.
    정렬과 페이징
    NULL 위치는 DB마다 다르며 Hibernate가 방언에 맞게 생략·출력·흉내를 고른다. offset·limit은 setFirstResult·setMaxResults로 전달되고, 큰 offset은 건너뛸 행까지 읽는다.
    집계 결과 타입
    명세상 SUM(정수)은 Long이지만 Querydsl은 식의 선언 타입으로 변환해 Integer로 자른다. 범위를 넘으면 조용히 틀린 값이 되므로 longValue()로 타입을 넓힌다.

    Q 타입(Q-type)
    애노테이션 프로세서가 엔티티마다 생성하는 Querydsl 쿼리 타입. 엔티티 속성마다 타입이 정해진 경로 필드를 가진다.
    식별 변수(identification variable)
    JPQL의 FROM 절에서 선언하는 변수, 흔히 별칭이라 부른다. Q 타입 생성자의 문자열 인자가 이것이 된다.
    위치 파라미터(positional parameter)
    JPQL에서 ?1처럼 물음표와 1부터 시작하는 정수로 표시하는 입력 파라미터. Querydsl은 상수를 이것으로 바인딩한다.
    쿼리 계획 캐시(query plan cache)
    Hibernate가 JPQL/HQL 문자열을 해석하고 변환한 결과를 보관하는 캐시. 6.6의 기본 최대 크기 상수는 2048이다.
    SQM(Semantic Query Model)
    Hibernate 6이 HQL/JPQL을 파싱해 만드는 의미 모델. 속성 확인과 타입 검사가 이 단계에서 이루어진다.
    3값 논리(three-valued logic)
    참, 거짓에 알 수 없음(unknown)을 더한 SQL의 논리 체계. NULL과의 비교는 알 수 없음이 되고 WHERE는 참인 행만 남긴다.
    NULL 정렬 우선순위(null precedence)
    정렬에서 NULL을 맨 앞(nulls first)이나 맨 뒤(nulls last)에 둘지 정하는 지정. 기본 위치는 DB마다 다르다.
    키셋 페이징(keyset pagination)
    offset 대신 마지막으로 본 정렬 키보다 큰(또는 작은) 행부터 가져오는 페이징. 인덱스에서 시작 위치로 바로 내려가므로 offset처럼 앞의 행을 읽고 버리지 않는다.
    축소 기본 변환(narrowing primitive conversion)
    long을 int로 바꾸는 것처럼 표현 범위가 좁은 타입으로의 변환. 정수 간 변환은 하위 비트만 남기고 예외를 던지지 않는다.
