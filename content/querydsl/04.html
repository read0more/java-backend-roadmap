    이 회차의 질문: select와 where에 놓은 "식"은 어디로 가는가

    앞 회차들에서 Querydsl 쿼리의 기본 문법을 보았다. Q 타입이라는 생성된 클래스의 필드(book.title)가 JPQL의 경로 표현식이 되고, where, orderBy, join을 메서드로 이어 붙이면 Querydsl이 그것을 JPQL 문자열로 직렬화해서 EntityManager에 넘긴다. 이번 회차는 그 위에서 두 가지 질문을 끝까지 따라간다.

    첫째, select 절에 무엇을 놓느냐가 결과 객체의 모양을 정한다. 엔티티 하나를 놓으면 엔티티가, 컬럼 하나를 놓으면 그 값이, 여러 개를 놓으면 Tuple이, Projections.bean(...)을 놓으면 DTO가 나온다. 그런데 데이터베이스가 돌려주는 것은 언제나 JDBC ResultSet의 행, 즉 값의 나열뿐이다. 그 행이 누구의 손을 거쳐 DTO가 되는지, 그 과정에서 리플렉션이 어떤 규칙으로 생성자와 setter와 필드를 고르는지, 규칙이 어긋나면 언제 어떤 오류가 나는지를 본다.

    둘째, where 절에 놓은 조건 식의 트리가 SQL의 모양을 정한다. 검색 화면처럼 조건이 있을 수도 없을 수도 있는 쿼리(동적 쿼리)에서 Querydsl은 null 조건을 건너뛰고 나머지를 and로 묶는다. 이 동작이 Querydsl 코드의 어디에서 일어나는지, 조건 조합마다 JPQL 문자열이 달라지는 것이 Hibernate의 쿼리 해석 캐시에 어떤 의미인지까지 내려간다. 이어서 select가 아닌 쿼리, 즉 UPDATE와 DELETE를 한 번에 실행하는 벌크 연산이 영속성 컨텍스트와 어떻게 어긋나는지, JPQL에 없는 SQL 함수를 어떻게 부르는지를 다룬다.

    공개된 커리큘럼에서 이 회차가 맡는 수업 주제는 프로젝션과 결과 반환(기본, DTO 조회, @QueryProjection), 동적 쿼리(BooleanBuilder 사용, where 다중 파라미터 사용), 수정·삭제 벌크 연산, SQL function 호출하기다. Q 타입이 애노테이션 프로세서로 생성되는 과정은 01회, 조인과 서브쿼리의 제약은 03회, 여기서 만든 동적 조건을 리포지토리와 페이징에 실제로 적용하는 일은 05회와 06회의 몫이다.

    이 회차의 실험은 모두 Querydsl 5.1.0(jakarta 분류자) + Hibernate ORM 6.6.53.Final + H2 2.3.232 + JDK 21에서 직접 실행했다. 스프링 없이 Hibernate의 Configuration으로 EntityManagerFactory를 만들고, 그 EntityManager로 JPAQueryFactory를 직접 생성했다. Querydsl이 만든 JPQL은 쿼리 객체의 toString()으로, Hibernate가 만든 SQL은 hibernate.show_sql로 찍었다. SQL의 별칭(b1_0)과 함수 렌더링은 데이터베이스 방언(dialect)에 따라 달라지므로 MySQL에서는 모양이 다를 수 있다. 내부 클래스 이름과 동작은 위 버전의 jar를 javap로 열어 확인한 것이며 다른 버전에서는 달라질 수 있다.

    프로젝션의 기본: 대상이 하나일 때와 여럿일 때

    프로젝션(projection)은 select 절에 무엇을 가져올지 정하는 일이다. 관계 대수에서 릴레이션의 일부 속성만 뽑아내는 연산을 프로젝션이라고 부르는 데서 온 말이다. Querydsl에서는 select(...)에 넘기는 식이 프로젝션이고, 그 식의 타입이 곧 fetch()가 돌려주는 리스트의 원소 타입이다.

    대상이 여럿: Tuple

    제목과 가격을 함께 가져오면 결과 타입은 무엇이 되어야 할까. 자바에는 "String 하나와 Integer 하나의 쌍"을 나타내는 기본 타입이 없다. 순수 JPA의 createQuery("select b.title, b.price from Book b")는 행마다 Object[]를 돌려주고, 꺼내 쓰는 쪽이 인덱스와 형변환을 책임진다. Querydsl은 여기에 자기 타입인 com.querydsl.core.Tuple을 씌운다.

    List rows = queryFactory
        .select(book.title, book.price)
        .from(book)
        .where(book.author.eq("kim"))
        .fetch();

for (Tuple row : rows) {
    String title = row.get(book.title);     // 식을 열쇠로 꺼낸다
    Integer price = row.get(book.price);
    System.out.println(title + " / " + price + " / " + row.getClass().getName());
}

    row.get(book.title)의 반환 타입이 String이라는 점이 Object[]와의 차이다. Tuple.get의 시그니처는 T get(Expression expr)이므로, 넘긴 식의 타입 매개변수가 그대로 반환 타입이 된다. 형변환은 컴파일러가 제네릭으로 대신 검사한다.

    그렇다면 get은 어떻게 몇 번째 값인지 알까. jar를 javap로 열어 보면 구조가 단순하다. select에 넘긴 식 목록으로 QTuple이라는 객체가 만들어지고, 이 객체는 식을 열쇠로, 위치를 값으로 하는 Map, Integer> bindings를 갖는다. 행마다 만들어지는 TupleImpl은 값 배열 Object[] a만 들고 있고, get(expr)은 bindings.get(expr)로 위치를 찾은 다음 그 칸을 돌려준다. 따라서 열쇠가 되는 것은 식 객체의 동일성이 아니라 동등성(equals)이다. 실험으로 확인해 보자.

    별칭이 같은 새 QBook 인스턴스로 꺼내도 값이 나온다. 경로 식은 "별칭 book의 속성 title"이라는 경로 정보로 비교되기 때문이다. 별칭이 다르면 다른 경로이므로 null이다. 주의할 점은 select에 없던 식으로 꺼내도 예외가 아니라 null이 나온다는 것이다. 오타 하나가 "값이 없는 행"처럼 보이는 버그가 될 수 있다.

    Tuple을 어디까지 들고 다닐지는 설계 판단이다. Tuple은 com.querydsl.core 패키지의 타입이고, 꺼내려면 QBook 같은 Q 타입의 식이 필요하다. 서비스나 컨트롤러가 Tuple을 받으면 그 계층도 Querydsl과 Q 타입에 의존하게 되고, 나중에 조회 기술을 바꿀 때 영향이 리포지토리 밖으로 번진다. 그래서 Tuple은 리포지토리 안에서 꺼내 쓰고, 계층 밖으로는 DTO로 바꿔 내보내는 쪽이 의존 방향을 지키기 쉽다.

    엔티티 조회와 DTO 조회는 메모리에서 무엇이 다른가

    DTO 조회의 방법을 보기 전에, 왜 엔티티 대신 DTO로 조회하는지를 메모리 관점에서 정리해 두자. selectFrom(book)으로 엔티티를 조회하면 Hibernate는 행마다 다음 일을 한다.

    1. 행의 식별자로 영속성 컨텍스트(1차 캐시)를 찾는다. 이미 있으면 그 인스턴스를 쓰고 행의 나머지 값은 버린다.
    2. 없으면 엔티티 인스턴스를 만들고 모든 컬럼 값을 채운 뒤 영속성 컨텍스트에 등록한다.
    3. 변경 감지(dirty checking)를 위해 로딩 시점의 속성 값 배열을 따로 보관한다. Hibernate 6.6의 EntityEntry 인터페이스에 있는 getLoadedState()가 돌려주는 Object[]가 그것이다. flush 시점에 현재 값과 이 배열을 비교해 UPDATE를 만든다.

    즉 엔티티 하나를 읽으면 엔티티 객체, 그 상태 사본, 영속성 컨텍스트의 맵 항목이 함께 힙에 남고, 이것들은 영속성 컨텍스트가 닫히거나 clear()될 때까지 가비지 컬렉션 대상이 되지 않는다. 화면에 제목과 가격만 보여 줄 목록이라면 이 비용은 쓸모가 없다. DTO 조회는 필요한 컬럼만 SELECT하고, 결과 객체를 영속성 컨텍스트에 등록하지 않는다. 그래서 변경 감지도 없고, 조회한 DTO의 값을 바꿔도 아무 SQL도 나가지 않는다. 읽기 전용 화면에 DTO 조회가 어울리는 이유가 이것이다. 반대로 조회한 뒤 상태를 바꾸어 저장해야 하는 경우에는 엔티티로 조회해야 변경 감지를 쓸 수 있다.

    Hibernate의 행 읽기기(StandardRowReader)가 JDBC 행을 읽다가, 동적 인스턴스화(dynamic instantiation)를 담당하는 조립기가 java.lang.reflect.Constructor.newInstance로 생성자를 호출한다. JPQL의 new는 Hibernate가 해석하는 문법이고, 객체를 만드는 것도 Hibernate다. 이 사실을 기억해 두고 Querydsl의 방법과 비교해 보자.

    Querydsl의 DTO 조회: bean, fields, constructor

    Querydsl은 DTO 조회를 위해 com.querydsl.core.types.Projections라는 팩토리 클래스를 제공한다. Javadoc의 설명대로 이 클래스는 FactoryExpression 인스턴스를 만드는 팩토리이고, 대표적인 메서드는 세 가지다.

    메서드만드는 식DTO에 값을 넣는 방법DTO에 필요한 것
    Projections.bean(T.class, ...)QBean기본 생성자로 만든 뒤 setter 호출인자 없는 생성자, 속성 이름과 같은 setter
    Projections.fields(T.class, ...)QBean(필드 접근 모드)기본 생성자로 만든 뒤 필드에 직접 대입인자 없는 생성자, 속성 이름과 같은 필드
    Projections.constructor(T.class, ...)ConstructorExpression인자 타입이 맞는 생성자 호출식의 타입·순서와 맞는 생성자

    실험용 DTO는 세 방식을 모두 받을 수 있게 만들었다.

    public class BookDto {
    private String title;
    private int price;

    public BookDto() {}                        // bean, fields가 쓴다
    public BookDto(String title, int price) {  // constructor가 쓴다
        this.title = title;
        this.price = price;
    }
    public String getTitle() { return title; }
    public void setTitle(String title) { this.title = title; }
    public int getPrice() { return price; }
    public void setPrice(int price) { this.price = price; }
    @Override public String toString() { return "BookDto(" + title + ", " + price + ")"; }
}

        .select(Projections.bean(BookDto.class, book.title, book.price))
        .from(book).where(book.author.eq("kim")).fetch();

        .select(Projections.fields(BookDto.class, book.title, book.price))
        .from(book).where(book.author.eq("kim")).fetch();

List byConstructor = queryFactory
        .select(Projections.constructor(BookDto.class, book.title, book.price))
        .from(book).where(book.author.eq("kim")).fetch();

Querydsl의 fetch()가 JPA의 getResultList()를 부르고, Hibernate가 JDBC 행을 읽어 값 배열을 만든 다음, 그 배열을 Querydsl이 끼워 넣은 변환기 FactoryExpressionTransformer에 넘긴다. 변환기는 QBean.newInstance나 ConstructorExpression.newInstance를 부르고, 거기서 리플렉션(Method.invoke, Constructor.newInstance)으로 DTO가 만들어진다. JPQL new와 비교하면 SQL은 같지만, 객체를 만드는 주체가 Hibernate의 동적 인스턴스화가 아니라 Querydsl의 FactoryExpression이다.

    변환기는 언제 끼워지는가

    AbstractJPAQuery.createQuery의 바이트코드를 보면 순서가 이렇다. JPQL 문자열로 EntityManager.createQuery를 호출해 JPA Query를 만들고 파라미터를 바인딩한 뒤, 프로젝션이 FactoryExpression이면 QueryHandler.transform(query, projection)을 호출한다. Hibernate를 쓸 때 쓰이는 HibernateHandler의 transform은 JPA Query를 org.hibernate.query.Query로 unwrap한 다음 setResultTransformer(new FactoryExpressionTransformer(projection))을 부르고 true를 돌려준다. Hibernate 6.6에서 setResultTransformer는 deprecated 상태의 default 메서드로 남아 있고, 내부적으로 행 단위 변환기(TupleTransformer)를 설정한다. 스택에 보인 RowTransformerTupleTransformerAdapter가 그 어댑터다.

    transform이 false를 돌려주는 경우, 예컨대 unwrap이 실패해 PersistenceException이 난 경우에는 Querydsl이 프로젝션을 필드에 기억해 두었다가 getResultList()가 끝난 뒤 결과 리스트를 한 바퀴 돌며 행마다 projection.newInstance(Object[])를 직접 호출한다. 어느 경로든 DTO를 만드는 코드는 FactoryExpression.newInstance 하나다. 단지 Hibernate의 행 읽기 루프 안에서 불리느냐, 그 루프가 끝난 뒤 Querydsl의 루프에서 불리느냐가 다르다.

    JPQL에는 new가 없고, Hibernate의 행 읽기 루프 안에서 Querydsl의 변환기가 리플렉션으로 DTO를 만든다는 것을 보여 준다. 가로로 긴 시퀀스 다이어그램. 왼쪽부터 세로 생명선 5개: "Querydsl JPAQuery", "Hibernate Query", "JDBC ResultSet", "FactoryExpressionTransformer", "BookDto". 위에서 아래로 화살표: (1) "Querydsl JPAQuery"에서 "Hibernate Query"로 "select book.title, book.price" 라벨. (2) "Querydsl JPAQuery"에서 "Hibernate Query"로 "변환기 등록" 라벨. (3) "Hibernate Query"에서 "JDBC ResultSet"으로 "SQL 실행". (4) "JDBC ResultSet"에서 "Hibernate Query"로 돌아오는 점선 화살표 "행: [JPA Basics, 30000]". (5) "Hibernate Query"에서 "FactoryExpressionTransformer"로 "newInstance(배열)". (6) "FactoryExpressionTransformer"에서 "BookDto"로 "리플렉션: 생성자 / setter". 4~6번 화살표를 감싸는 사각 틀에 "행마다 반복" 라벨. 오른쪽 아래에 작은 메모 상자 "영속성 컨텍스트에 등록되지 않음". Querydsl의 DTO 프로젝션은 JPQL에서 평범한 스칼라 조회이고, 객체 생성은 Hibernate가 부르는 Querydsl 변환기 안에서 일어난다.

    bean과 fields: 이름으로 짝을 짓는다

    QBean은 select에 넘긴 식마다 "속성 이름"을 정한다. 식이 경로(book.title)면 경로의 마지막 이름(title)이 속성 이름이고, 별칭을 붙인 식(book.title.as("name"))이면 별칭이 속성 이름이다. 그리고 DTO 클래스에서 그 이름의 setter(bean 모드) 또는 필드(fields 모드)를 찾는다. 결과 행이 오면 newInstance가 먼저 DTO의 인자 없는 생성자로 빈 객체를 만들고, 값을 하나씩 setter나 필드로 넣는다.

    fields 모드는 java.lang.reflect.Field에 setAccessible(true)를 걸고 Field.set으로 값을 넣는다. 그래서 private 필드여도 되고 setter가 없어도 된다. 접근 제한자를 리플렉션으로 넘는 이 일은 자바 모듈 시스템이 허용하는 범위에서만 가능하다. 일반적인 애플리케이션처럼 DTO가 이름 없는 모듈(클래스패스)에 있으면 문제가 없다.

    constructor: 타입과 순서로 짝을 짓는다

    ConstructorExpression은 이름을 보지 않는다. 인자 식들의 타입 배열을 만들고(book.title은 String, book.price는 Integer), Querydsl의 ConstructorUtils.getConstructor로 그 타입 배열을 받을 수 있는 생성자를 찾는다. book.price의 타입은 NumberPath라 Integer인데, BookDto(String, int)가 선택된 것을 보면 원시 타입과 래퍼 타입의 대응을 고려해 찾는다는 것을 알 수 있다. 생성자는 식을 만드는 시점에 한 번 찾아 두고, 행마다 Constructor.newInstance만 호출한다.

    그래서 DTO의 필드 이름이 엔티티와 달라도 constructor 방식은 상관없다. 대신 순서와 타입이 맞아야 한다. 이름으로 짝을 짓는 bean·fields와 타입·순서로 짝을 짓는 constructor는 실수했을 때의 증상도 완전히 다르다. 다음 절에서 하나씩 일부러 틀려 본다.

    이름과 타입이 어긋날 때: 언제, 어떤 오류가 나는가

    오류는 일찍 드러날수록 싸다. 컴파일 오류는 코드를 쓰는 순간, 식을 만드는 시점의 예외는 그 코드가 처음 실행되는 순간, 결과 변환 시점의 예외는 SQL까지 실행한 뒤에 드러난다. 가장 나쁜 것은 오류 없이 값이 조용히 사라지는 경우다. 이 회차의 실험 결과를 이 기준으로 정리하면 다음과 같다.

    이름이 다르면 bean·fields는 조용히 건너뛴다

    엔티티의 title을 DTO의 name 필드에 담고 싶다고 하자.

    public class UserView {
    private String name;   // 엔티티의 title과 이름이 다르다
    private int price;
    // getter, toString() ...
}

    예외가 없다. title이라는 이름의 필드를 찾지 못하자 QBean은 그 값을 버렸다. javap로 보면 QBean에는 propertyNotFound(Expression, String)라는 protected 메서드가 있고, 기본 구현은 아무것도 하지 않는다. setter 모드(Projections.bean)도 같은 메서드를 거치므로, 이름에 맞는 setter가 없는 속성은 역시 예외 없이 건너뛰었다. 해결책은 별칭이다.

    queryFactory.select(Projections.fields(UserView.class, book.title.as("name"), book.price))
        .from(book).where(book.author.eq("kim")).fetch();

    서브쿼리 별칭으로 sub라는 새 Q 타입 인스턴스를 만든 이유는 바깥 쿼리의 book과 다른 별칭이 필요해서다. 덧붙이면 Jakarta Persistence 3.1 명세 4.6.16절은 서브쿼리를 WHERE 절과 HAVING 절에서 쓸 수 있다고 정하고, 각주에서 이 버전에서는 서브쿼리가 그 두 절로 제한된다고 밝힌다. select 절 서브쿼리는 Hibernate가 HQL 확장으로 지원하는 것이고, 서브쿼리의 제약은 03회에서 자세히 다룬다.

    타입이 다르면 식을 만드는 순간 실패한다

    이 예외는 쿼리를 실행하기 전, Projections.fields를 호출하는 순간에 났다. QBean은 생성될 때 속성마다 필드(또는 setter)를 찾고 식의 타입이 대입 가능한지 검사한다. 이름이 없으면 넘어가지만, 이름이 있는데 타입이 맞지 않으면 예외를 던진다. setter 모드(Projections.bean)로 같은 실수를 해도 같은 메시지가 났다.

    constructor는 인자 순서가 틀리면 식을 만드는 순간 실패한다

    NULL은 원시 타입에서 0이 된다

    데이터베이스의 NULL은 자바의 null로 오는데, DTO 필드가 int라면 어떻게 될까. 조건에 맞는 행이 없어 max가 NULL을 돌려주는 서브쿼리를 가격 자리에 넣고 네 방식을 모두 돌려 보았다.

        JPAExpressions.select(sub.price.max()).from(sub).where(sub.author.eq("nobody")),
        "price");

    앞 절의 표에서 @QueryProjection 열만 "컴파일 오류"였던 이유가 이것이다. 제네릭 타입 검사는 컴파일러가 하는 일이고, @QueryProjection은 DTO 생성자의 시그니처를 제네릭 시그니처로 옮겨 적어 그 검사를 받게 만든다. 다만 같은 타입의 인자끼리 순서가 바뀌는 실수(String 두 개)는 여전히 컴파일러도 구분할 수 없다.

    대가: DTO가 Querydsl을 안다

    이 안전성에는 비용이 있다. BookQDto는 com.querydsl.core.annotations.QueryProjection을 import하므로 DTO가 Querydsl 라이브러리에 컴파일 의존성을 갖는다. DTO는 보통 리포지토리에서 서비스, 컨트롤러, 때로는 API 응답까지 여러 계층을 오간다. 그 모든 계층이 Querydsl jar를 클래스패스에 두어야 하고, 나중에 조회 기술을 바꾸면 DTO도 고쳐야 한다. 또 DTO 생성자를 바꿀 때마다 애노테이션 프로세서가 다시 돌아 Q 타입이 재생성되어야 한다(빌드 도구가 보통 컴파일 단계에서 자동으로 한다).

    정리하면 선택지는 "어디서 실수를 잡을 것인가"와 "의존성을 어디까지 허용할 것인가"의 교환이다. DTO를 순수한 자바 객체로 두고 싶다면 constructor 방식(혹은 record + constructor)에 테스트로 실행 경로를 확인하는 방법이 있고, 조회 전용 DTO를 리포지토리 계층 안에 가둘 수 있다면 @QueryProjection의 컴파일 시점 검사를 누리는 방법이 있다. 어느 쪽이든 JPQL과 SQL은 같다는 사실을 알고 고르면 된다.

    동적 쿼리 1: BooleanBuilder

    검색 화면을 생각해 보자. 저자 입력란과 최소 가격 입력란이 있고, 사용자는 둘 다 채울 수도, 하나만 채울 수도, 아무것도 채우지 않을 수도 있다. 조건 두 개면 조합은 네 가지, 조건 n개면 2의 n제곱 가지다. JPQL을 문자열로 이어 붙이는 방식에서는 "첫 조건 앞에는 where, 그다음부터는 and"를 직접 관리해야 하고, 공백 하나만 빠져도 실행 시점에 문법 오류가 난다. Querydsl은 조건을 문자열이 아니라 객체로 다루므로 이 문제를 객체 조립으로 바꾼다. 첫 번째 도구가 BooleanBuilder다.

    static BooleanBuilder searchCondition(String author, Integer minPrice) {
    BooleanBuilder builder = new BooleanBuilder();
    if (author != null) {
        builder.and(book.author.eq(author));
    }
    if (minPrice != null) {
        builder.and(book.price.goe(minPrice));
    }
    return builder;
}

List result = queryFactory
        .selectFrom(book)
        .where(searchCondition(author, minPrice))
        .fetch();

    네 가지 조합을 모두 실행했다. getValue()는 빌더가 지금까지 조립한 조건 식을 돌려주는 메서드다.

    (kim, 26000)  getValue()=book.author = kim && book.price >= 26000
  JPQL: select book from Book book where book.author = ?1 and book.price >= ?2
  [Book(JPA Basics, kim, 30000)]
(kim, null)   getValue()=book.author = kim
  JPQL: select book from Book book where book.author = ?1
  [Book(JPA Basics, kim, 30000), Book(Spring Data, kim, 25000)]

  JPQL: select book from Book book where book.price >= ?1
  [Book(JPA Basics, kim, 30000), Book(Java Threads, lee, 32000)]
(null, null)  getValue()=null  hasValue=false
  JPQL: select book from Book book
  [Book(JPA Basics, kim, 30000), Book(Spring Data, kim, 25000), Book(Java Threads, lee, 32000), Book(SQL Tuning, park, 28000)]

    세 가지를 읽을 수 있다. 첫째, 들어온 조건만 and로 묶였고 where와 and의 배치는 Querydsl이 알아서 했다. 둘째, 조건이 하나도 없을 때 빌더의 값은 null이고, 그 빌더를 where에 넘겼더니 where 절 자체가 사라졌다. 셋째, getValue()의 toString()은 &&를 쓰지만 JPQL에는 and가 나간다. 식 객체의 toString()은 디버깅용 기본 템플릿으로 출력되고, JPQL은 JPQL용 템플릿으로 따로 직렬화되기 때문이다. 같은 식 트리를 다른 문법으로 출력하는 것이다.

    빌더는 가변 객체다

    BooleanBuilder는 이름 그대로 빌더다. 내부에 조건 식 하나(Predicate)를 담는 칸이 있고, and(조건)을 부를 때마다 그 칸의 값을 "기존 값 and 새 조건"으로 바꾼 뒤 자기 자신을 돌려준다. 칸이 비어 있을 때는 새 조건이 그대로 들어간다. 인자로 null을 넘기면 아무것도 바꾸지 않는다. 그래서 위 코드는 if 없이 builder.and(author != null ? book.author.eq(author) : null)처럼 써도 같은 결과가 된다.

    가변이라는 성질은 공유할 때 문제가 된다. 아래 실험에서 alias는 shared와 같은 객체를 가리킨다.

    BooleanBuilder shared = new BooleanBuilder(book.author.eq("kim"));
BooleanBuilder alias = shared;
alias.and(book.price.gt(26000));
System.out.println(shared + "  같은 객체? " + (shared == alias));

BooleanExpression e1 = book.author.eq("kim");
BooleanExpression e2 = e1.and(book.price.gt(26000));
System.out.println("e1=" + e1 + "  e2=" + e2);
    book.author = kim && book.price > 26000  같은 객체? true
e1=book.author = kim  e2=book.author = kim && book.price > 26000

    alias에 조건을 더했는데 shared가 바뀌었다. 힙에 빌더 객체가 하나뿐이고 두 지역 변수가 같은 참조를 들고 있기 때문이다. 공통 조건을 담은 빌더를 필드나 정적 변수에 두고 여러 쿼리가 가져다 and를 부르면, 앞선 요청의 조건이 뒤 요청에 누적되는 버그가 생긴다. 여러 스레드가 동시에 같은 빌더를 건드리면 데이터 경쟁(data race)까지 생긴다. 반면 BooleanExpression.and는 e1을 바꾸지 않고 새 식 e2를 만들어 돌려준다. 이 차이가 다음 절의 출발점이다.

    동적 쿼리 2: where 다중 파라미터

    두 번째 도구는 빌더를 아예 쓰지 않는다. where 메서드는 가변 인자 where(Predicate... o)로 선언되어 있어서 조건을 여러 개 받을 수 있고, 받은 조건들을 and로 묶는다. 그리고 null인 인자는 건너뛴다. 그래서 조건 하나하나를 "값이 없으면 null을 돌려주는 메서드"로 만들면 된다.

    static BooleanExpression authorEq(String author) {
    return author != null ? book.author.eq(author) : null;
}

static BooleanExpression priceGoe(Integer minPrice) {
    return minPrice != null ? book.price.goe(minPrice) : null;
}

List result = queryFactory
        .selectFrom(book)
        .where(authorEq(author), priceGoe(minPrice))
        .fetch();
    (kim, 26000)  select book from Book book where book.author = ?1 and book.price >= ?2
(kim, null)   select book from Book book where book.author = ?1
(null, 29000) select book from Book book where book.price >= ?1
(null, null)  select book from Book book

    BooleanBuilder와 정확히 같은 JPQL이다. 두 방식은 Querydsl 안에서 같은 길로 합류한다. where에 넘긴 인자는 쿼리 메타데이터(DefaultQueryMetadata)의 addWhere로 하나씩 들어가는데, javap로 보면 이 메서드는 첫 줄에서 인자가 null이면 바로 반환한다. null이 아니면 ExpressionUtils.extract로 실제 식을 꺼낸다. BooleanBuilder를 넘기면 이 단계에서 빌더 안의 식(getValue())이 꺼내지고, 빈 빌더라면 꺼낸 값이 null이라 역시 무시된다. 살아남은 조건은 기존 where 조건과 and로 합쳐진다.

    조건 메서드의 진짜 장점: 이름과 재사용

    where 다중 파라미터 방식에서 조건은 이름을 가진 메서드가 된다. where(authorEq(author), priceGoe(minPrice))는 쿼리가 무엇을 거르는지 메서드 이름만으로 읽힌다. BooleanBuilder 방식에서는 빌더를 만드는 메서드의 if 문을 따라 읽어야 같은 정보를 얻는다. 또 authorEq는 다른 쿼리의 where에도, 프로젝션만 다른 DTO 조회에도, 05회와 06회에서 다룰 count 쿼리에도 그대로 넣을 수 있다. 메서드가 돌려주는 BooleanExpression은 불변이므로 공유해도 앞 절의 누적 버그가 생기지 않는다.

    조합할 때의 함정: null.and(...)

    조건 메서드를 다시 조합해 "저자와 가격 조건을 한 번에" 같은 메서드를 만들고 싶을 수 있다. 그대로 이으면 터진다.

    BooleanExpression all = authorEq(null).and(priceGoe(26000));
    java.lang.NullPointerException: Cannot invoke "com.querydsl.core.types.dsl.BooleanExpression.and(com.querydsl.core.types.Predicate)" because the return value of "exp.Main.authorEq(String)" is null

    where가 null을 너그럽게 받아 준다고 해서 null에 메서드를 호출할 수 있는 것은 아니다. authorEq(null)은 객체가 아니라 null 참조를 돌려주었고, 그 위에서 and를 호출하면 JVM은 invokevirtual 명령을 실행하다가 수신 객체가 null이라 NullPointerException을 던진다. JDK 21의 예외 메시지는 어떤 메서드의 반환값이 null이었는지까지 알려 준다.

    반대 방향은 안전하다. BooleanExpression.and(Predicate right)의 바이트코드를 보면 인자를 ExpressionUtils.extract로 꺼낸 뒤 null이면 새 식을 만들지 않고 this를 돌려준다. 실제로 book.author.eq("kim").and(null)의 결과는 book.author = kim이었다. 즉 왼쪽만 null이 아니면 된다. 조합 메서드를 안전하게 만드는 방법은 몇 가지가 있다.

    • 조합 메서드에서 new BooleanBuilder().and(authorEq(a)).and(priceGoe(p))처럼 빌더를 출발점으로 삼는다. 빌더의 and는 null을 무시하고, 빌더는 Predicate이므로 where에 그대로 넣을 수 있다. 매번 새 빌더를 만드니 공유 문제도 없다.
    • 조합하지 않고 where(authorEq(a), priceGoe(p))처럼 가변 인자로 넘긴다. 대부분의 경우 이것으로 충분하다.
    • 조건 메서드가 null 대신 "항상 참"인 식을 돌려주게 만드는 방법도 생각할 수 있지만, 그러면 JPQL에 의미 없는 조건이 남는다. null을 건너뛰는 Querydsl의 규칙을 그대로 쓰는 편이 SQL도 깔끔하다.

    조건 트리와 괄호: 직렬화가 우선순위를 지키는 방법

    book.author.eq("kim")은 문자열이 아니라 객체다. 연산자 Ops.EQ와 인자 두 개(경로 book.author, 상수 "kim")를 가진 연산 노드다. and와 or는 이런 노드 두 개를 자식으로 갖는 새 노드를 만든다. 결국 where 조건은 하나의 트리이고, JPQL 직렬화는 이 트리를 깊이 우선으로 순회하며 문자열을 쓰는 일이다.

    트리를 문자열로 펼칠 때 문제는 우선순위다. SQL과 JPQL에서 and는 or보다 먼저 결합한다. 그래서 트리 모양을 문자열로 정확히 옮기려면, 자식 노드의 연산자가 부모보다 약하게 결합할 때 괄호를 쳐야 한다. 실험으로 확인했다.

    BooleanExpression a = book.author.eq("kim");
BooleanExpression b = book.author.eq("lee");
BooleanExpression c = book.price.gt(26000);

queryFactory.selectFrom(book).where(a.or(b).and(c));    // (1)
queryFactory.selectFrom(book).where(a.or(b.and(c)));    // (2)
queryFactory.selectFrom(book).where(a.or(b), c);        // (3)
    (1) select book from Book book where (book.author = ?1 or book.author = ?2) and book.price > ?3
(2) select book from Book book where book.author = ?1 or book.author = ?2 and book.price > ?3
(3) select book from Book book where (book.author = ?1 or book.author = ?2) and book.price > ?3

    (1)은 트리의 뿌리가 AND이고 왼쪽 자식이 OR이다. OR이 AND보다 약하게 결합하므로 직렬화기가 왼쪽 자식을 괄호로 감쌌다. (2)는 뿌리가 OR이고 오른쪽 자식이 AND다. AND는 원래 먼저 결합하므로 괄호가 필요 없고, 실제로 붙지 않았다. 괄호 없는 문자열 a or b and c가 SQL에서 a or (b and c)로 해석되니 트리와 의미가 같다. (3)은 where 가변 인자가 a.or(b)와 c를 AND로 묶은 것이므로 (1)과 같은 트리, 같은 JPQL이 되었다.

    (1)을 실행하면 SQL은 where (b1_0.author=? or b1_0.author=?) and b1_0.price>?이고 결과는 [Book(JPA Basics, kim, 30000), Book(Java Threads, lee, 32000)]이다. kim의 책 중 26000 이하인 Spring Data와, 저자가 park인 SQL Tuning이 빠졌다. 메서드 체인을 쓸 때 "점으로 이은 순서가 곧 괄호"라는 점을 기억하면 된다. a.or(b).and(c)에서 a.or(b)가 먼저 하나의 노드가 되고, 그 노드에 and(c)가 걸린다. 문자열로 JPQL을 이어 붙일 때 흔히 생기는 "or 조건에 괄호를 빠뜨려 권한 조건이 무력화되는" 종류의 버그는, 조건을 트리로 조립하고 직렬화기가 괄호를 결정하는 구조에서는 생기지 않는다.

      a.or(b).and(c)                    a.or(b.and(c))

        AND                              OR
       /    \                          /    \
     OR      c                        a     AND
    /  \                                   /   \
   a    b                                 b     c

  → (a or b) and c                  → a or b and c
    자식 OR이 부모 AND보다 약함        자식 AND가 부모 OR보다 강함
    → 괄호 필요                        → 괄호 불필요
    메서드 체인이 만든 조건 트리 두 개를 나란히 놓고, 자식 연산자가 부모보다 약하게 결합할 때만 괄호가 붙는다는 것을 보여 준다. 좌우 2분할 그림. 왼쪽 위 제목 "a.or(b).and(c)", 그 아래 트리: 뿌리 원 "AND", 왼쪽 자식 원 "OR", 오른쪽 자식 사각형 "c: price > 26000", "OR"의 자식 사각형 "a: author = kim", "b: author = lee". "OR" 원 주위를 주황색 점선 괄호로 감싸고 라벨 "괄호 필요". 트리 아래 결과 상자 "(a or b) and c". 오른쪽 위 제목 "a.or(b.and(c))", 그 아래 트리: 뿌리 원 "OR", 왼쪽 자식 사각형 "a", 오른쪽 자식 원 "AND", "AND"의 자식 사각형 "b", "c". "AND" 원 옆에 회색 라벨 "괄호 불필요". 트리 아래 결과 상자 "a or b and c". 두 트리 사이 가운데 세로선. 맨 아래 공통 캡션 상자 "and가 or보다 먼저 결합한다". Querydsl은 조건을 트리로 들고 있다가, 자식 연산자의 결합 순위가 부모보다 낮을 때만 괄호를 쳐서 JPQL로 펼친다.

    조건 조합의 수와 Hibernate의 쿼리 해석 캐시

    지금까지의 JPQL을 다시 보면 값이 문자열에 들어가지 않았다. book.author = ?1처럼 JPA의 위치 기반 파라미터(positional parameter)가 들어가고, 실제 값 "kim"은 Query.setParameter로 따로 바인딩된다. 앞에서 문자열 JPQL에 'kim'을 직접 적었을 때는 SQL에도 where b1_0.author='kim'처럼 리터럴이 그대로 나갔던 것과 대조된다.

    이 차이는 보안(SQL 인젝션)만의 문제가 아니다. Hibernate는 JPQL(HQL) 문자열을 받으면 그것을 파싱해 의미 모델(SQM 트리)로 바꾸고 다시 SQL로 번역한다. 이 해석은 비싸므로 결과를 캐시해 두고, 같은 문자열이 다시 오면 재사용한다. 동적 쿼리에서 조건 조합마다 JPQL 문자열이 달라진다면, 캐시에는 얼마나 많은 항목이 생길까. Hibernate의 내부 캐시 객체(QueryInterpretationCache)에서 캐시된 HQL 해석의 수를 직접 세어 보았다.

    QueryInterpretationCache cache = emf.unwrap(SessionFactoryImplementor.class)
        .getQueryEngine().getInterpretationCache();

int base = cache.getNumberOfCachedHqlInterpretations();
String[] authors = {"kim", null, "lee", "park", null};
Integer[] prices  = {26000, 29000, null, 10000, null};
for (int round = 0; round < 3; round++)          // 값을 바꿔 가며 3바퀴, 총 15회 실행
    for (int i = 0; i < authors.length; i++)
        queryFactory.selectFrom(book)
                .where(authorEq(authors[i]),
                       priceGoe(prices[i] == null ? null : prices[i] + round))
                .fetch();
System.out.println(cache.getNumberOfCachedHqlInterpretations() - base);

base = cache.getNumberOfCachedHqlInterpretations();
for (int p = 20000; p < 20010; p++)              // 값을 문자열에 붙인 JPQL 10회
    em.createQuery("select b from Book b where b.price >= " + p, Book.class).getResultList();
System.out.println(cache.getNumberOfCachedHqlInterpretations() - base);
    Querydsl 15회 실행 후 새로 캐시된 HQL 해석 수: 4
값을 문자열로 붙인 JPQL 10회 실행 후: 10

    Querydsl 쪽은 값이 매번 달랐는데도 해석이 4개만 생겼다. 조건 두 개의 있고 없음으로 만들어지는 JPQL 문자열이 정확히 네 종류(둘 다, 저자만, 가격만, 둘 다 없음)이기 때문이다. 값은 파라미터로 빠졌으므로 문자열을 바꾸지 않는다. 반면 값을 문자열에 붙인 쪽은 실행할 때마다 새 문자열이 되어 10번 실행에 10개가 쌓였다. Hibernate 6.6.53에서 이 캐시의 기본 최대 크기는 QueryEngine.DEFAULT_QUERY_PLAN_MAX_COUNT 상수에 정해진 2048이고, hibernate.query.plan_cache_max_size 설정으로 바꾼다. 값이 문자열에 섞이면 캐시가 금방 차서 쓸모 있는 항목까지 밀려나고, 매번 파싱 비용을 다시 치른다.

    따라서 동적 쿼리가 만드는 서로 다른 JPQL의 수는 "조건 조합의 수"로 상한이 정해진다. 선택 조건이 n개면 최대 2의 n제곱 가지다. 조건이 몇 개 수준이면 문제가 되지 않지만, 조건마다 정렬 방향이나 조인 여부까지 달라지면 조합이 곱으로 늘어난다는 점은 알고 있어야 한다. 이 원리는 데이터베이스 쪽에도 이어진다. 바인딩 파라미터를 쓰는 SQL은 텍스트가 같으므로 데이터베이스와 드라이버 수준의 문장 캐시(prepared statement cache)에서도 같은 문장으로 취급될 수 있다.

    값을 파라미터로 바인딩하면 캐시 항목이 조건 조합 수만큼만 생기고, 값을 문자열에 붙이면 실행 횟수만큼 생긴다는 대비를 보여 준다. 좌우 비교 그림. 왼쪽 패널 제목 "파라미터 바인딩 (Querydsl)". 위쪽에 실행 요청 카드 15장이 3줄로 쌓여 있고 각 카드에 작은 값 표시(예: "kim, 26000", "kim, 26001"). 아래로 깔때기 모양 화살표가 4개의 상자로 모인다: "author = ?1 and price >= ?2", "author = ?1", "price >= ?1", "조건 없음". 상자 묶음 아래 라벨 "캐시 항목 4개". 오른쪽 패널 제목 "값을 문자열에 붙임". 실행 카드 10장 각각에서 화살표가 개별 상자로 이어진다: "price >= 20000", "price >= 20001", ..., "price >= 20009". 아래 라벨 "캐시 항목 10개". 두 패널 사이 세로 구분선. 맨 아래 가운데 작은 상자 "Hibernate HQL 해석 캐시 (기본 최대 2048)". 동적 쿼리가 만드는 JPQL의 종류는 값이 아니라 조건 조합의 수로 정해진다.

    모든 조건이 빠지면 무슨 일이 생기는가

    네 번째 조합(null, null)을 다시 보자. where 절이 사라져 테이블 전체를 읽었다. 예제 테이블은 네 행이지만 운영 테이블이 수백만 행이라면, 데이터베이스는 전체를 스캔하고, JDBC 드라이버는 그 결과를 네트워크로 받아 오고, Hibernate는 행마다 엔티티와 상태 사본을 만들어 영속성 컨텍스트에 쌓는다. 힙이 감당하지 못하면 OutOfMemoryError로 이어진다. Querydsl의 null 건너뛰기는 문법적으로 정확한 쿼리를 만들어 줄 뿐, 그 쿼리가 안전한지는 판단하지 않는다. 그래서 검색 쿼리에는 06회에서 다룰 페이징으로 결과 크기에 상한을 두거나, 최소한 하나의 조건을 요구하는 검증을 호출하는 쪽에 둔다.

    수정·삭제 벌크 연산: 영속성 컨텍스트를 건너뛰는 쿼리

    JPA에서 엔티티를 수정하는 기본 방법은 변경 감지다. 엔티티를 조회해 값을 바꾸면 flush 시점에 UPDATE가 나간다. 이 방식은 엔티티 하나당 UPDATE 하나다. "가격이 30000원 미만인 책을 모두 1000원 올린다"를 변경 감지로 하면, 대상 행을 모두 메모리로 읽어 들이고 행 수만큼 UPDATE를 보내야 한다. 벌크 연산(bulk operation)은 이것을 SQL 한 문장으로 끝낸다.

    long count = queryFactory
        .update(book)
        .set(book.price, book.price.add(1000))
        .where(book.price.lt(30000))
        .execute();

long deleted = queryFactory
        .delete(book)
        .where(book.price.gt(50000))
        .execute();
    JPQL: update Book book
set book.price = book.price + ?1
where book.price < ?2
Hibernate: update Book b1_0 set price=(b1_0.price+cast(? as integer)) where b1_0.price ?1
Hibernate: delete from Book b1_0 where b1_0.price>?

    update(book)은 JPAUpdateClause를, delete(book)은 JPADeleteClause를 만든다. set에는 상수뿐 아니라 book.price.add(1000)이나 book.price.multiply(2) 같은 식도 넣을 수 있고, 이 식은 SQL에서 현재 행의 값을 읽어 계산하는 price = price + ?가 된다. execute()는 JPA의 Query.executeUpdate()를 호출하고, 영향받은 행 수를 long으로 돌려준다. H2 방언은 파라미터에 cast(? as integer)를 씌웠는데, 이것은 방언의 렌더링 방식이므로 MySQL에서는 다르게 나올 수 있다.

    중요한 것은 이 SQL이 영속성 컨텍스트를 거치지 않고 데이터베이스로 바로 간다는 점이다. Jakarta Persistence 3.1 명세 4.10절(Bulk Update and Delete Operations)은 이것을 분명히 적는다. 벌크 UPDATE는 데이터베이스의 UPDATE로 곧바로 옮겨지며 낙관적 락 검사를 건너뛰고, 영속성 컨텍스트는 벌크 UPDATE·DELETE의 결과와 동기화되지 않으며, 벌크 DELETE는 연관 엔티티로 전파(cascade)되지 않는다. 이 세 문장이 무엇을 뜻하는지 실험으로 하나씩 확인한다.

    실행 순서 추적: 1차 캐시가 데이터베이스와 어긋나는 과정

    List before = queryFactory.selectFrom(book).orderBy(book.price.asc()).fetch();
System.out.println("before: " + before);
Book spring = before.get(0);          // Spring Data, 25000
spring.setPrice(26000);               // 아직 flush하지 않은 변경

long n = queryFactory.update(book)
        .set(book.price, book.price.add(1000))
        .where(book.price.lt(30000))
        .execute();
System.out.println("변경 행 수: " + n);

System.out.println("after(clear 전): " + after);
System.out.println("같은 인스턴스? " + after.contains(spring));

em.clear();
System.out.println("after(clear 후): " + queryFactory.selectFrom(book).orderBy(book.price.asc()).fetch());

Hibernate: update Book set author=?,price=?,publisher_id=?,title=? where id=?
Hibernate: update Book b1_0 set price=(b1_0.price+cast(? as integer)) where b1_0.price

    한 줄씩 따라가 보자.

    1. 첫 조회. 책 네 권이 엔티티로 만들어져 영속성 컨텍스트에 들어가고, 각각의 로딩 시점 상태 사본도 함께 보관된다. 이때 메모리와 데이터베이스의 값은 같다.
    2. spring.setPrice(26000). 힙의 엔티티 필드만 바뀌었다. 데이터베이스는 아직 25000이다.
    3. execute(). SQL이 두 개 나갔다. 먼저 update Book set author=?,price=?,publisher_id=?,title=? where id=?, 즉 2번의 변경을 반영하는 flush다. Hibernate의 기본 flush 모드(AUTO)에서는 쿼리를 실행하기 전에 그 결과에 영향을 줄 수 있는 대기 중 변경을 먼저 데이터베이스에 보낸다. 이 덕분에 벌크 UPDATE의 where 조건은 26000이라는 최신 값을 보고 판단했다. 이어서 벌크 UPDATE가 실행되어 Spring Data는 26000에서 27000으로, SQL Tuning은 28000에서 29000으로 바뀌었다. JPA Basics(30000)는 30000 미만이 아니므로 제외되어 변경 행 수는 2다.
    4. 두 번째 조회. SQL은 분명히 실행되었고, 데이터베이스는 27000과 29000을 돌려주었다. 그런데 결과에는 26000과 28000이 찍혔다. Hibernate는 행을 읽을 때 식별자로 영속성 컨텍스트를 먼저 찾고, 이미 관리 중인 엔티티가 있으면 그 인스턴스를 그대로 돌려주고 행의 값은 버린다. "같은 인스턴스? true"가 이를 보여 준다. 한 영속성 컨텍스트 안에서 같은 식별자는 같은 객체라는 동일성 보장이, 벌크 연산 뒤에는 낡은 값을 고집하는 결과가 된다.
    5. flush()와 clear(). flush는 대기 중 변경을 보내는 일이고(이 시점에는 보낼 것이 없다), clear는 영속성 컨텍스트를 비우는 일이다. 비운 뒤의 조회는 행마다 엔티티를 새로 만들므로 비로소 27000과 29000이 보인다.

---------------------------  -------------------------------  -----------------------
1. 첫 조회                   Spring 25000 / SQL 28000          Spring 25000 / SQL 28000
2. setPrice(26000)           Spring 26000 / SQL 28000          Spring 25000 / SQL 28000
3a. 자동 flush               Spring 26000 / SQL 28000          Spring 26000 / SQL 28000
3b. 벌크 UPDATE (+1000)      Spring 26000 / SQL 28000  (그대로) Spring 27000 / SQL 29000
4. 다시 조회                 Spring 26000 / SQL 28000  (행 값 버림)  "
5. clear 후 조회             Spring 27000 / SQL 29000          Spring 27000 / SQL 29000
    벌크 UPDATE가 데이터베이스만 바꾸고, 이어지는 조회가 행 값을 버리고 1차 캐시의 낡은 인스턴스를 돌려준다는 것을 시간 순서로 보여 준다. 가로 3단계 타임라인. 각 단계마다 위쪽 상자 "영속성 컨텍스트", 아래쪽 원통 "데이터베이스". 1단계 제목 "벌크 UPDATE 전": 위 상자 안 카드 "Spring Data 26000", "SQL Tuning 28000", 아래 원통 안 같은 값. 2단계 제목 "벌크 UPDATE 직후": 위 상자는 그대로 "26000", "28000"(회색), 아래 원통은 "27000", "29000"(초록 강조), 원통으로 내려가는 굵은 화살표 라벨 "SQL 직접 실행". 3단계 제목 "다시 조회": 원통에서 위로 올라오는 화살표 "행: 27000, 29000"이 위 상자 앞에서 X 표시로 막히고 라벨 "같은 id → 기존 인스턴스 반환". 위 상자의 카드에 빨간 라벨 "낡은 값". 오른쪽 끝에 작은 상자 "해결: flush → clear". 벌크 연산은 영속성 컨텍스트를 거치지 않으므로, 이미 관리 중인 엔티티는 clear하기 전까지 데이터베이스와 다른 값을 들고 있다.

    낡은 엔티티가 벌크 결과를 덮어쓰는 경우

    낡은 값을 읽는 것보다 더 위험한 것은 낡은 엔티티를 수정하는 것이다. 책 한 권을 조회한 뒤, 벌크 UPDATE로 그 책의 저자를 바꾸고, clear 없이 같은 엔티티의 가격을 수정해 flush해 보았다.

    Book b = queryFactory.selectFrom(book).where(book.title.eq("SQL Tuning")).fetchOne();
queryFactory.update(book).set(book.author, "unknown")
        .where(book.title.eq("SQL Tuning")).execute();   // DB: author = unknown
b.setPrice(30000);                                       // 낡은 엔티티(author = park) 수정
em.flush();
em.clear();
System.out.println(queryFactory.selectFrom(book).fetch());
    Hibernate: update Book b1_0 set author=? where b1_0.title=?
Hibernate: update Book set author=?,price=?,publisher_id=?,title=? where id=?
[Book(SQL Tuning, park, 30000)]

    벌크 UPDATE가 바꾼 unknown이 사라지고 park로 되돌아갔다. 원인은 변경 감지가 만든 UPDATE에 있다. 가격만 바꿨는데도 SQL은 set author=?,price=?,publisher_id=?,title=?로 모든 컬럼을 덮어썼다. Hibernate가 기본적으로 엔티티의 모든 컬럼을 갱신하는 UPDATE를 쓰기 때문이고, 그 값은 힙에 있는 낡은 엔티티에서 왔다. 벌크 연산의 결과가 예외도 경고도 없이 유실된 것이다. 벌크 연산 뒤에 em.flush()와 em.clear()를 습관처럼 붙이는 이유가 여기에 있다. 스프링 데이터 JPA의 @Modifying이 flushAutomatically = true로 실행 전 flush를, clearAutomatically = true로 실행 뒤 clear를 자동으로 해 준다는 것은 앞 권에서 보았다.

    clear의 대가도 알아 두어야 한다. clear는 영속성 컨텍스트의 모든 엔티티를 준영속 상태로 만든다. clear 전에 들고 있던 엔티티 참조는 더 이상 변경 감지 대상이 아니다. 아직 초기화되지 않은 지연 로딩 프록시도 마찬가지여서, 책의 getPublisher()로 얻어 둔 출판사 프록시에 clear 뒤 처음 접근했더니 LazyInitializationException: Could not initialize proxy [exp.Publisher#1] - no session이 났다. 그래서 벌크 연산은 트랜잭션의 맨 앞에서 실행하거나, 벌크 연산 직후 clear하고 필요한 엔티티를 다시 조회하는 흐름으로 짠다.

    낙관적 락과 cascade도 건너뛴다

    명세가 말하는 나머지 두 가지도 같은 원리에서 나온다. 엔티티에 @Version 필드가 있으면 변경 감지로 나가는 UPDATE는 where id=? and version=?로 버전을 검사하고 버전을 올린다. 벌크 UPDATE는 엔티티를 거치지 않는 SQL이므로 이 검사를 하지 않는다. 다른 트랜잭션이 들고 있는 엔티티의 버전이 그대로이니, 그 트랜잭션은 벌크 UPDATE가 있었다는 사실을 버전으로 알아챌 수 없다. 버전을 함께 올려야 한다면 set에 버전 컬럼을 직접 넣어야 한다.

    벌크 DELETE는 연관 엔티티로 전파되지 않는다. 책이 참조하는 출판사를 벌크로 지워 보았다.

    queryFactory.delete(publisher).where(publisher.name.eq("River Books")).execute();
    Hibernate: delete from Publisher p1_0 where p1_0.name=?
org.hibernate.exception.ConstraintViolationException
  원인: org.h2.jdbc.JdbcSQLIntegrityConstraintViolationException: Referential integrity constraint violation: "FKRB2NJMKVIO5MHE42EMPUAIPHU: PUBLIC.BOOK FOREIGN KEY(PUBLISHER_ID) REFERENCES PUBLIC.PUBLISHER(ID) ..."

    Hibernate는 출판사를 참조하는 책이 있는지 보지 않고 DELETE를 그대로 보냈고, 데이터베이스의 외래 키 제약이 거부했다. 엔티티 매핑에 cascade나 orphanRemoval을 설정해 두었더라도, 그것은 em.remove()로 엔티티를 지울 때 영속성 컨텍스트가 수행하는 동작이라 벌크 DELETE와는 무관하다. 자식부터 지우는 순서는 직접 짜야 한다.

    execute()가 돌려주는 숫자의 의미

    execute()의 반환값은 결국 JDBC 드라이버가 알려 주는 갱신 행 수(update count)다. 여기에는 데이터베이스별 미묘함이 있다. MySQL C API 문서에 따르면 MySQL 서버가 UPDATE에 대해 기본으로 돌려주는 affected-rows 값은 실제로 값이 바뀐 행의 수이고, 접속할 때 CLIENT_FOUND_ROWS 플래그를 주면 WHERE에 일치한 행의 수가 된다. 그런데 MySQL Connector/J의 useAffectedRows 속성은 기본값이 false이고, 이 속성의 설명은 "CLIENT_FOUND_ROWS 플래그를 설정하지 않는다"는 것이다. 즉 기본 설정의 Connector/J는 이 플래그를 설정하므로, 이미 같은 값을 가진 행에 같은 값을 넣는 UPDATE도 일치한 행으로 세어 돌려준다. 같은 SQL을 mysql 명령줄 클라이언트에서 실행했을 때 보이는 "Changed" 수와 자바에서 받은 숫자가 다를 수 있는 이유다. 반환값으로 "실제 변경이 있었는가"를 판단하는 로직이라면 이 차이를 알고 써야 한다.

    SQL 함수 호출: JPQL에 없는 함수를 부르는 길

    JPQL은 데이터베이스 독립적인 언어라서 표준 함수의 수가 적다. 문자열의 일부를 바꾸는 replace 같은 함수는 대부분의 데이터베이스에 있지만 Jakarta Persistence 3.1 명세의 표준 함수 목록에는 없다(3.2 명세에서 REPLACE가 표준 문자열 함수로 추가되었다). Querydsl에서 이런 함수를 부르는 일반적인 방법은 템플릿 식(template expression)이다.

    List replaced = queryFactory
        .select(Expressions.stringTemplate(
                "function('replace', {0}, {1}, {2})", book.title, "a", "@"))
        .from(book)
        .fetch();
    JPQL: select function('replace', book.title, ?1, ?2)
from Book book
Hibernate: select replace(b1_0.title,?,?) from Book b1_0
[JPA B@sics, Spring D@t@, J@v@ Thre@ds, SQL Tuning]

    세 층을 거친 과정을 보자. Expressions.stringTemplate은 템플릿 문자열과 인자 목록을 받아 String 타입의 식을 만든다. {0}, {1}, {2}는 인자의 자리다. 직렬화할 때 경로 인자 book.title은 경로로, 식이 아닌 상수 "a"와 "@"는 파라미터 ?1, ?2로 바뀌어 들어갔다. 템플릿 안의 'replace'는 따옴표까지 문자 그대로 JPQL에 복사된다. 그 결과가 JPQL의 function('replace', ...)이다.

    function('이름', 인자...)은 JPA 표준 문법이다. Hibernate 6.6의 HQL 가이드는 네이티브 함수나 사용자 정의 함수를 JPQL의 function 문법으로 부를 수 있다고 설명한다. Hibernate는 이름 replace를 자기 함수 등록부(function registry)에서 찾는다. HQL 가이드의 문자열 함수 표에는 replace(str, patt, rep)가 있고, JPA 표준도 ANSI SQL 표준도 아닌 함수로 표시되어 있다. Hibernate가 이 함수를 알고 있으므로, H2 방언에 맞게 replace(b1_0.title,?,?)로 렌더링했다. 같은 이유로 템플릿을 "replace({0}, {1}, {2})"처럼 function 없이 써도 이 실험에서는 똑같은 SQL이 나왔다. 다만 그것은 HQL 확장 문법에 기대는 것이고, function(...) 형식이 JPA 표준 문법이다.

    표준 함수는 Querydsl 메서드로

    JPQL 표준에 있는 함수는 템플릿이 필요 없다. Querydsl의 식 타입이 메서드로 제공하고, Querydsl이 JPQL 함수로 옮긴다.

    queryFactory.select(book.title).from(book)
        .where(book.author.eq(book.author.lower()))      // 저자가 이미 소문자인 책
        .fetch();

queryFactory.select(book.title).from(book)
        .where(book.title.eq(Expressions.stringTemplate("function('lower', {0})", book.title)))
        .fetch();
    JPQL: select book.title
from Book book
where book.author = lower(book.author)
Hibernate: select b1_0.title from Book b1_0 where b1_0.author=lower(b1_0.author)
[JPA Basics, Spring Data, Java Threads, SQL Tuning]

JPQL: select book.title
from Book book
where book.title = function('lower', book.title)
Hibernate: select b1_0.title from Book b1_0 where b1_0.title=lower(b1_0.title)
[]

    첫 쿼리는 lower() 메서드가 JPQL lower(...)가 된 경우이고, 둘째는 같은 함수를 템플릿으로 부른 경우다. 두 경로 모두 같은 SQL 함수로 렌더링되었다. 모든 저자 이름이 소문자이므로 첫 쿼리는 네 권을 다 돌려주고, 모든 제목에 대문자가 있으므로 둘째 쿼리는 빈 리스트다. 차이는 타입 안전성에 있다. lower() 메서드는 StringExpression에만 있으므로 숫자 경로에 부를 수 없지만, 템플릿은 문자열이라 함수 이름의 오타도 인자 개수의 실수도 컴파일러가 잡지 못한다. 메서드가 있으면 메서드를 쓰고, 없을 때만 템플릿을 쓴다.

    등록되지 않은 함수의 오류는 어디서 나는가

    Hibernate가 모르는 이름을 넣으면 어떻게 될까.

    queryFactory.select(Expressions.stringTemplate("function('my_func', {0})", book.title))
        .from(book).fetch();
    JPQL: select function('my_func', book.title)
from Book book
Hibernate: select my_func(b1_0.title) from Book b1_0
org.hibernate.exception.SQLGrammarException: could not prepare statement [Function "MY_FUNC" not found; SQL statement: ...
  원인: org.h2.jdbc.JdbcSQLSyntaxErrorException: Function "MY_FUNC" not found; SQL statement: ...

    Hibernate 6.6.53은 등록부에 없는 이름을 거부하지 않고 my_func(...)로 SQL에 그대로 옮겼다. 오류를 낸 것은 H2였다. 드라이버가 SQL을 준비(prepare)하는 단계에서 데이터베이스가 함수를 찾지 못했고, Hibernate는 그 SQLException을 SQLGrammarException으로 감쌌다. 오타가 난 함수 이름은 JPQL 해석 단계가 아니라 데이터베이스 왕복이 일어난 뒤에야 드러난다는 뜻이다. 이 성질은 장점이기도 하다. 데이터베이스에 직접 만든 함수(저장 함수)를 별도 등록 없이 function 문법으로 부를 수 있다.

    함수를 정식으로 등록하는 길도 있다. HQL 가이드는 사용자 정의 함수를 FunctionContributor 구현으로 등록할 수 있고, 커스텀 Dialect가 initializeFunctionRegistry()를 재정의해 네이티브 함수를 추가할 수 있다고 설명한다(Hibernate 6.6의 org.hibernate.boot.model.FunctionContributor는 추상 메서드로 contributeFunctions(FunctionContributions) 하나를 가진 인터페이스다. default 메서드 ordinal()도 함께 있다). 등록하면 반환 타입을 Hibernate가 알게 되고, function 없이 HQL에서 이름으로 직접 부를 수 있다. 시작할 때 어떤 함수가 등록되었는지 보려면, 가이드의 안내대로 로그 카테고리 org.hibernate.HQL_FUNCTIONS를 debug로 켜면 된다.

    함수와 인덱스

    SQL 함수를 where 절에 쓸 때는 실행 계획을 함께 생각해야 한다. B+Tree 인덱스는 컬럼 값의 순서로 정렬되어 있다. where author = ?는 그 정렬을 따라 내려가 범위를 좁힐 수 있지만, where lower(author) = ?는 비교 대상이 컬럼 값이 아니라 함수의 결과라 컬럼 값의 정렬을 그대로 이용할 수 없다. MySQL은 8.0.13부터 식의 값을 인덱싱하는 함수 키 파트(functional key part)를 지원하는데, MySQL 매뉴얼은 이 인덱스를 쓰려면 쿼리의 식이 인덱스 정의의 식과 일치해야 한다고 설명한다. Querydsl이 만든 식이 SQL에서 정확히 어떤 함수 호출로 렌더링되는지 show_sql로 확인해야 하는 이유이기도 하다. 예를 들어 Querydsl의 concat과 stringValue()는 JPQL에서 concat(...)과 str(...)이 되었다가 H2의 SQL에서는 || 연산자와 cast(... as varchar)로 바뀌었다. 같은 Querydsl 코드라도 방언마다 SQL의 모양이 다르다.

    이 회차의 지식이 다시 쓰이는 곳

    이 회차에서 본 것은 결국 두 개의 변환 경로다. 하나는 식 트리 → JPQL 문자열 → SQL의 경로로, where 조건과 함수 호출이 이 길을 따라간다. Querydsl은 트리를 들고 있다가 템플릿에 따라 괄호와 파라미터를 결정하고, Hibernate는 그 문자열을 해석해 캐시하고 방언에 맞는 SQL로 렌더링한다. 다른 하나는 JDBC 행 → 값 배열 → 객체의 경로로, 프로젝션이 이 길을 따라간다. 엔티티라면 Hibernate가 영속성 컨텍스트를 거쳐 만들고, DTO라면 Querydsl의 FactoryExpression이 리플렉션으로 만든다. 벌크 연산은 첫 번째 경로만 쓰고 두 번째 경로, 즉 영속성 컨텍스트를 거치지 않는다는 점에서 특별했다.

    05회에서는 이 회차의 동적 조건과 DTO 프로젝션을 순수 JPA 리포지토리에 넣고, JPAQueryFactory를 스프링 빈으로 공유해도 되는 이유(트랜잭션 범위의 EntityManager 프록시)를 다룬다. 06회에서는 같은 조건 메서드를 페이징 쿼리와 count 쿼리에 재사용하는데, 조건을 이름 있는 BooleanExpression 메서드로 만들어 두는 방식이 그때 효과를 낸다. 07회의 스프링 데이터 JPA 연동 기능은 이 회차에서 본 Predicate를 리포지토리 메서드의 인자로 받는다.

    이 장의 핵심

    Querydsl의 DTO 프로젝션은 JPQL에서 평범한 스칼라 조회이고, DTO는 Hibernate의 행 읽기 루프 안에서 Querydsl의 변환기가 리플렉션으로 만든다. 그래서 이름으로 짝을 짓는 bean·fields는 불일치를 조용히 넘기고, 타입으로 짝을 짓는 constructor는 런타임에, @QueryProjection은 컴파일 시점에 실패한다. where 조건은 불변 식 트리로 조립되며 null은 메타데이터에 들어가기 전에 버려지고, 값은 파라미터로 빠지므로 JPQL의 종류는 조건 조합 수로 제한된다. 벌크 연산은 영속성 컨텍스트를 건너뛰므로, 실행 뒤 flush·clear 없이 남은 엔티티는 낡은 값을 보여 주고 심하면 벌크 결과를 덮어쓴다.
    프로젝션과 Tuple
    select에 넘긴 식의 타입이 결과 타입이 된다. 식이 여럿이면 Querydsl은 식을 열쇠로 위치를 찾는 Tuple을 돌려주며, select에 없던 식으로 꺼내면 예외가 아니라 null이 나온다.
    DTO 프로젝션의 실행 경로
    bean, fields, constructor, @QueryProjection 모두 JPQL에는 컬럼만 나열한다. Hibernate가 JDBC 행을 값 배열로 만들면 Querydsl의 FactoryExpressionTransformer가 리플렉션으로 DTO를 만든다.
    짝을 짓는 방식과 실패 시점
    bean·fields는 이름으로 짝을 지어 불일치를 조용히 건너뛰고 타입 불일치는 식 생성 시 예외를 낸다. constructor는 타입·순서로 짝을 지어 식 생성 시 예외를 내며, @QueryProjection은 컴파일 오류로 잡는다.
    NULL과 record
    NULL은 네 방식 모두에서 원시 타입 필드의 기본값(0)이 된다. record는 인자 없는 생성자가 없고 필드를 리플렉션으로 바꿀 수 없으므로 constructor 계열로만 담는다.
    BooleanBuilder
    조건 하나를 담는 가변 빌더다. and(null)은 무시되고, 빈 빌더는 where에서 사라진다. 공유하면 조건이 누적된다.
    where 다중 파라미터
    가변 인자의 null은 addWhere에서 버려진다. 조건을 이름 있는 BooleanExpression 메서드로 만들어 재사용하되, null을 돌려줄 수 있는 메서드 위에서 and를 호출하면 NullPointerException이 난다.
    쿼리 해석 캐시
    Querydsl은 값을 파라미터로 바인딩하므로 동적 쿼리의 JPQL 종류는 조건 조합의 수로 제한되고, Hibernate는 같은 문자열의 해석 결과를 재사용한다(6.6.53 기본 최대 2048).
    벌크 연산
    UPDATE·DELETE를 SQL 한 문장으로 실행하며 영속성 컨텍스트, 낙관적 락 검사, cascade를 모두 건너뛴다. 실행 뒤에는 flush와 clear로 영속성 컨텍스트를 비운다.
    SQL 함수 템플릿
    Expressions.stringTemplate("function('이름', {0})", ...)은 JPQL의 function 문법이 되고, Hibernate의 함수 등록부를 거쳐 방언의 SQL로 렌더링된다. 모르는 함수는 SQL로 그대로 넘어가 데이터베이스에서 실패한다.

    DTO 프로젝션 방식을 고를 때 실무에서 실제로 문제가 되는 것은 "어느 것이 더 편한가"보다 "실수가 언제 드러나는가"다. 엔티티 필드 이름을 리팩터링했는데 DTO 필드 이름은 그대로 둔 경우, fields 방식은 예외 없이 그 값만 비운 채 화면에 내보낸다. 이런 버그는 대개 사용자 신고로 발견된다. 반대로 constructor 방식은 첫 실행에서 예외가 나므로 테스트 한 번이면 잡힌다. 팀이 DTO에 Querydsl 의존성을 허용할 수 있다면 @QueryProjection이 가장 이르게 잡아 준다. 판단이 달라지는 조건은 DTO가 어느 계층까지 흘러가는가, 그리고 DTO가 API 계약처럼 외부에 노출되는가다.

    동적 쿼리에서 장애로 이어지는 패턴은 대부분 "모든 조건이 빠진 경우"다. 관리자 검색 화면에서 필터를 모두 비우고 조회를 누르면 where 없는 쿼리가 전체 테이블을 읽고, 결과가 엔티티라면 영속성 컨텍스트에 수십만 개의 객체와 상태 사본이 쌓인다. Querydsl은 이 쿼리를 정확하게 만들어 줄 뿐 막아 주지 않는다. 페이징을 강제하거나, 조건이 하나도 없을 때의 동작을 명시적으로 정하는 것은 호출하는 쪽의 책임이다. 또 값을 문자열에 이어 붙이는 코드가 섞이면 Hibernate의 해석 캐시가 값의 수만큼 늘어나 캐시 적중률이 떨어진다는 점도 성능 문제를 진단할 때 떠올릴 만하다.

    벌크 연산은 "한 문장으로 빠르다"는 장점만 보고 쓰기 쉽지만, 영속성 컨텍스트와의 관계를 놓치면 데이터가 조용히 되돌아가는 사고가 난다. 이 회차의 실험처럼 벌크 UPDATE 뒤에 같은 트랜잭션에서 낡은 엔티티를 수정하면, 전 컬럼 UPDATE가 벌크 결과를 덮어쓴다. 서비스 메서드 안에서 벌크 연산을 쓴다면 메서드의 맨 앞에 두거나, 직후에 flush·clear하고 필요한 엔티티를 다시 읽는 흐름으로 짠다. @Version으로 동시성을 관리하는 엔티티라면 벌크 UPDATE가 버전을 올리지 않는다는 점도 설계에 반영해야 한다.

    1번. QBean은 select 식마다 속성 이름(경로의 마지막 이름 title)을 정하고 DTO에서 같은 이름의 필드를 찾는다. UserView에는 title 필드가 없으므로 찾지 못하고, 이때 호출되는 propertyNotFound의 기본 구현이 아무것도 하지 않아 그 값은 버려진다. 고치는 방법은 별칭을 주는 것(book.title.as("name"))과 DTO 필드 이름을 title로 바꾸는 것이다. Projections.constructor는 이름을 보지 않으므로 UserView에 (String, int) 생성자가 있다면 정상 동작하고, 없다면 식을 만드는 순간 "No constructor found" 예외가 난다. @QueryProjection도 이름을 보지 않으며 생성자 시그니처로 생성된 Q 타입을 쓰므로, 타입이 맞으면 컴파일되고 정상 동작한다.

    2번. (가) 두 인자가 모두 null이라 addWhere에서 버려지고 where 절이 없는 JPQL이 된다. (나) authorEq("kim").or(authorEq("lee"))가 OR 노드 하나가 되고 가격 조건과 AND로 묶이므로 where (book.author = ?1 or book.author = ?2) and book.price >= ?3이다. 자식 OR이 부모 AND보다 약하게 결합하므로 괄호가 붙는다. (다) authorEq(null)이 null을 돌려주고 그 위에서 or를 호출하므로 NullPointerException이다. where가 null을 너그럽게 다루는 것은 인자로 받은 null에 한해서다. (라) 빌더의 and(null)은 무시되어 빌더가 빈 상태로 남고, 빈 빌더에 or(조건)을 하면 그 조건이 그대로 값이 된다. 결과는 where book.price >= ?1이다.

    3번. 벌크 UPDATE는 데이터베이스에서 27000 미만인 Spring Data만 50000으로 바꾸고(SQL Tuning 28000은 제외), 변경 행 수는 1이다. clear 없이 다시 조회하면 SQL은 실행되지만 두 엔티티 모두 이미 영속성 컨텍스트에 있으므로 행 값이 버려지고 Spring Data 25000, SQL Tuning 28000이 출력된다. 데이터베이스는 50000과 28000이다. SQL Tuning의 제목을 바꾸고 flush하면 Hibernate는 모든 컬럼을 쓰는 UPDATE를 보내고 가격 칸에는 힙의 값 28000을 넣는다. SQL Tuning은 벌크 대상이 아니었으므로 이 경우 데이터베이스의 가격은 여전히 28000으로 우연히 일치한다. 만약 Spring Data를 수정해 flush했다면 데이터베이스의 50000이 25000으로 덮어써졌을 것이다. 같은 실수가 어떤 엔티티에서는 무해하고 어떤 엔티티에서는 데이터를 되돌린다는 점이 이 버그를 찾기 어렵게 만든다.

    4번. 조건 다섯 개의 있고 없음이 2의 5제곱 = 32가지, 정렬 방향이 2가지이므로 최대 64개다. 값은 파라미터로 바인딩되므로 사용자가 어떤 값을 넣든 JPQL 문자열은 이 64개 중 하나이고, Hibernate의 해석 캐시(6.6.53 기본 최대 2048)에 넉넉히 들어가 처음 몇 번 이후로는 해석을 재사용한다. 정렬 컬럼 이름을 사용자 입력 문자열로 JPQL에 붙이면 두 가지가 달라진다. 입력값의 종류만큼 JPQL 문자열이 늘어날 수 있어 캐시 항목 수의 상한이 사라지고, 문자열이 그대로 쿼리에 들어가므로 인젝션의 통로가 된다. 정렬 컬럼은 허용 목록에서 Q 타입의 경로(book.price 등)로 바꿔 넣어야 한다.

     queryFactory.select(Projections.constructor(BookDto.class, book.title, book.price))를 Hibernate 6.6에서 실행할 때 일어나는 일로 옳은 것은? Querydsl이 JPQL select new exp.BookDto(book.title, book.price)를 만들고 Hibernate의 동적 인스턴스화가 생성자를 호출한다. JPQL에는 book.title, book.price만 나열되고, Hibernate가 행을 읽을 때 Querydsl이 설정한 변환기가 Constructor.newInstance로 DTO를 만든다. Querydsl이 엔티티 전체를 조회한 뒤 메모리에서 필요한 필드만 복사해 DTO를 만든다. 생성자는 컴파일 시점에 결정되므로 인자 순서가 틀리면 컴파일 오류가 난다. 실험에서 세 DTO 방식 모두 JPQL은 select book.title, book.price였고 new는 없었다. 호출 스택은 Hibernate의 StandardRowReader → FactoryExpressionTransformer.transformTuple → ConstructorExpression.newInstance → Constructor.newInstance였다. 엔티티를 조회하지 않으므로 SQL에도 두 컬럼만 나가고, 생성자 탐색은 식을 만드는 런타임에 일어나므로 순서 오류는 컴파일 오류가 아니라 ExpressionException이다. DTO의 int price 필드에 조회 결과가 NULL인 값을 담으면 어떻게 되는가? (Querydsl 5.1.0 기준) bean과 fields는 0이 되고, constructor는 원시 타입에 null을 넣을 수 없어 IllegalArgumentException이 난다. 네 방식 모두 NullPointerException이 난다. bean, fields, constructor, @QueryProjection 모두 예외 없이 0이 된다. Hibernate가 NULL 행을 결과에서 제외한다. QBean.newInstance는 값이 null이면 대입을 건너뛰어 필드가 기본값 0으로 남는다. ConstructorExpression은 생성자 호출 전에 원시 타입 매개변수 자리의 null을 기본값으로 바꾸는 변환기를 거친다. @QueryProjection의 Q 타입은 ConstructorExpression을 상속하므로 같다. 실험에서 네 방식 모두 price=0이었다. 그래서 NULL을 구분해야 하는 필드는 래퍼 타입으로 선언한다. 책 엔티티 하나를 조회해 둔 상태에서 벌크 UPDATE로 그 책의 저자를 바꾸고, clear 없이 같은 엔티티의 가격을 수정해 flush했다. 데이터베이스의 저자 컬럼은 어떻게 되는가? 변경 감지의 UPDATE가 모든 컬럼을 힙의 값으로 쓰므로 저자가 벌크 이전 값으로 되돌아간다. Hibernate가 벌크 UPDATE를 감지해 엔티티를 자동으로 새로 고치므로 저자는 벌크 결과대로 남는다. 가격만 바뀌었으므로 UPDATE는 가격 컬럼만 쓰고 저자는 벌크 결과대로 남는다. 영속성 컨텍스트와 데이터베이스가 다르므로 flush에서 OptimisticLockException이 난다. 벌크 연산은 영속성 컨텍스트와 동기화되지 않으므로 엔티티의 저자 필드는 옛 값이다. 실험의 flush SQL은 update Book set author=?,price=?,publisher_id=?,title=? where id=?로 모든 컬럼을 썼고, 결과는 Book(SQL Tuning, park, 30000)으로 저자가 되돌아갔다. @Version이 없는 엔티티이므로 낙관적 락 예외도 없다. 저자와 최소 가격 두 조건을 where 다중 파라미터로 받는 동적 쿼리를 서로 다른 값으로 1000번 실행했다. Hibernate의 HQL 해석 캐시에 새로 생기는 항목 수의 최댓값과 그 이유로 옳은 것은? 1000개. 값이 달라질 때마다 JPQL 문자열이 달라진다. 2개. 조건이 두 개이기 때문이다. 1개. Querydsl은 항상 같은 JPQL을 만들고 null 조건은 SQL 단계에서 제거된다. 4개. 값은 파라미터로 바인딩되고, JPQL 문자열은 두 조건의 있고 없음 조합(4가지)으로만 달라진다. Querydsl은 상수를 ?1 같은 파라미터로 직렬화하므로 값은 JPQL 문자열에 영향을 주지 않는다. null 조건은 JPQL을 만들기 전 addWhere에서 버려지므로 조건 조합마다 문자열이 달라진다. 실험에서 15회 실행 후 새 항목은 4개였고, 값을 문자열에 붙인 JPQL은 10회 실행에 10개가 생겼다. Expressions.stringTemplate("function('my_func', {0})", book.title)에서 my_func가 데이터베이스에도 Hibernate 등록부에도 없는 이름이라면, Hibernate 6.6.53 + H2에서 오류는 어디서 나는가? Querydsl이 템플릿을 직렬화할 때 알 수 없는 함수라며 예외를 던진다. Hibernate는 SQL에 my_func(...)를 그대로 렌더링하고, 데이터베이스가 문장을 준비하는 단계에서 함수를 찾지 못해 실패한다. Hibernate가 JPQL을 해석하는 단계에서 등록되지 않은 함수라며 SemanticException을 던진다. 컴파일 시점에 Q 타입 생성기가 함수 이름을 검사해 오류를 낸다. 실험에서 Hibernate는 select my_func(b1_0.title) from Book b1_0를 만들었고, H2가 Function "MY_FUNC" not found로 거부했다. Hibernate는 이를 SQLGrammarException("could not prepare statement")으로 감쌌다. 템플릿은 문자열이므로 컴파일러와 Querydsl은 함수 이름을 검사하지 않는다.
    프로젝션(projection)
    select 절에서 무엇을 가져올지 정하는 일. Querydsl에서는 select에 넘긴 식이 프로젝션이고, 그 식의 타입이 결과 원소의 타입이 된다.
    FactoryExpression
    값 배열을 받아 객체를 만드는 newInstance(Object...)를 가진 Querydsl 식. QTuple, QBean, ConstructorExpression, @QueryProjection이 생성한 Q 타입이 모두 이것이다.
    생성자 표현식(constructor expression)
    JPQL select 절의 new 패키지.클래스(...) 문법. JPA 명세상 클래스 이름은 완전한 이름이어야 하며, 객체는 JPA 구현체가 만든다.
    @QueryProjection
    DTO 생성자에 붙이면 애노테이션 프로세서가 그 생성자의 시그니처를 제네릭 매개변수로 옮긴 Q 타입(ConstructorExpression의 하위 클래스)을 생성하는 Querydsl 애노테이션.
    BooleanBuilder
    조건 식 하나를 담고 and, or 호출마다 그 값을 바꾸는 가변 Predicate. null 인자는 무시한다.
    벌크 연산(bulk operation)
    여러 행을 UPDATE나 DELETE 한 문장으로 바꾸는 JPQL 연산. 영속성 컨텍스트, 낙관적 락 검사, cascade를 거치지 않는다.
    HQL 해석 캐시(query interpretation cache)
    Hibernate가 HQL/JPQL 문자열을 해석한 결과를 보관해 같은 문자열이 다시 오면 재사용하는 캐시. 6.6.53의 기본 최대 크기는 2048이다.
    함수 등록부(function registry)
    Hibernate가 HQL에서 쓸 수 있는 함수와 그 SQL 렌더링 방식을 모아 둔 곳. 방언과 FunctionContributor가 함수를 등록한다.
