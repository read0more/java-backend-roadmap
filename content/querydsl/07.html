    이 회차의 질문: 스프링 데이터가 Querydsl에 내민 네 가지 손

    06회에서는 스프링 데이터 JPA 리포지토리에 Querydsl을 붙이는 정공법을 썼다. 사용자 정의 인터페이스를 하나 만들고, 이름이 Impl로 끝나는 구현 클래스에서 JPAQueryFactory로 쿼리를 작성하고, 그 인터페이스를 리포지토리 인터페이스가 상속하게 했다. 이 방식은 무엇이든 할 수 있지만 매번 조립할 부품이 많다. 인터페이스, 구현 클래스, 페이징 처리 코드, count 쿼리까지 직접 써야 한다. 그래서 스프링 데이터는 Querydsl을 위한 기능을 몇 가지 직접 내놓았다. 이 회차는 그 기능들이 실제로 어떻게 동작하는지, 그리고 어디서 한계에 부딪히는지를 다룬다.

    다룰 기능은 넷이다. 앞의 셋은 스프링 데이터가 제공하는 것이고, 마지막 하나는 앞의 셋을 써 본 뒤 그 한계를 메우려고 우리가 직접 만드는 것이다. 각 기능의 사용법은 몇 줄이면 끝나지만, 그 몇 줄 아래에는 스프링 데이터의 리포지토리 프록시, 스프링 MVC의 인자 리졸버, Querydsl의 경로 변환 규칙이 깔려 있다. 문제는 대개 그 아래층에서 생기므로, 이 회차는 사용법보다 아래층에 더 많은 지면을 쓴다.

    눈여겨볼 것은 findOne이다. SQL 끝에 fetch first ? rows only가 붙었는데, 구현 소스를 보면 이 자리에 들어가는 값은 1이 아니라 2다. 소스는 createQuery(predicate).select(path).limit(2).fetchOne()이라고 되어 있다. 결과가 하나인지 확인하려면 최소 두 행을 읽어 봐야 하기 때문이다. 한 행만 가져오면 "정확히 하나"인지 "여러 개 중 첫 번째"인지 구분할 수 없다. 두 행이 돌아오면 JPA의 NonUniqueResultException이 나고, Querydsl의 fetchOne()이 이를 Querydsl 자체의 com.querydsl.core.NonUniqueResultException으로 감싸 던지며, 구현체가 그것을 잡아 스프링의 IncorrectResultSizeDataAccessException으로 바꿔 던진다. 실행 기록의 메시지에 JPA 예외가 찍힌 것은 Querydsl 예외의 메시지가 감싼 원인 예외의 문자열이기 때문이다. 조건이 아무리 넓어도 DB에서 읽는 행은 최대 두 개로 제한되므로, 실수로 넓은 조건을 넘겨도 테이블 전체를 메모리에 올리지는 않는다.

    마지막 findBy는 2.6에서 추가된 유창한(fluent) 쿼리 API다. 두 번째 인자로 받은 함수 안에서 정렬, 프로젝션, 결과 형태(all(), first(), page(...) 등)를 고른다. 이 함수는 반드시 쿼리 결과를 반환해야 하고 FluentQuery 객체 자체를 반환하면 예외가 난다. 구현 소스의 메시지가 이유를 밝힌다. 쿼리가 findBy(...) 메서드의 범위 안에서 실행되도록 보장하려는 것이다. 메서드 밖으로 미완성 쿼리 객체가 새 나가면 트랜잭션과 영속성 컨텍스트가 이미 닫힌 뒤에 실행될 수 있다.

EmployeeRepository가 QuerydslPredicateExecutor를 상속하므로 프록시는 findAll(Predicate)를 가진 객체로 보인다. 둘째, 프록시의 타깃(target)은 SimpleJpaRepository다. 그런데 SimpleJpaRepository는 QuerydslPredicateExecutor를 구현하지 않는다. 타깃에 없는 메서드를 누군가는 처리해야 한다. 셋째, 인터셉터 체인의 끝 쪽에 ImplementationMethodExecutionInterceptor가 있다. 이것이 그 누군가다.     조립 과정은 RepositoryFactorySupport.getRepository(...)에 있다. 3.5.13 소스를 요약 없이 순서대로 따라가면 이렇다. 먼저 리포지토리 인터페이스의 메타데이터를 읽고 조각 구성(RepositoryComposition)을 만든다. 구성에는 사용자 정의 구현 조각(06회의 Impl 클래스)이 먼저 들어가고, 그 뒤에 저장소 모듈이 덧붙이는 조각(repository aspects)이 들어간다. JPA 모듈에서 이 덧붙임을 담당하는 것이 JpaRepositoryFactory.getRepositoryFragments(...)이고, 그 안에 Querydsl 판정이 있다.

    // JpaRepositoryFactory (spring-data-jpa 3.5.13), 주석 제거
boolean isQueryDslRepository = QUERY_DSL_PRESENT
        && QuerydslPredicateExecutor.class.isAssignableFrom(metadata.getRepositoryInterface());

if (isQueryDslRepository) {
    // ... 리액티브 리포지토리와 섞였으면 예외
    QuerydslJpaPredicateExecutor querydslJpaPredicateExecutor = new QuerydslJpaPredicateExecutor<>(
            getEntityInformation(metadata.getDomainType()), entityManager, resolver, crudMethodMetadata);
    invokeAwareMethods(querydslJpaPredicateExecutor);
    return RepositoryFragments.just(querydslJpaPredicateExecutor);
}
return RepositoryFragments.empty();

    판정 조건은 두 개다. QUERY_DSL_PRESENT는 QuerydslUtils의 정적 상수로, 클래스 로더에서 com.querydsl.core.types.Predicate 클래스를 찾을 수 있는지를 클래스 초기화 시점에 한 번 확인한 값이다. 다른 하나는 리포지토리 인터페이스가 QuerydslPredicateExecutor의 하위 타입인지 보는 Class.isAssignableFrom 검사다. 둘 다 참이면 QuerydslJpaPredicateExecutor 객체를 하나 만들어 조각으로 반환한다. 이 객체는 리포지토리 하나에 하나씩 만들어지는 평범한 자바 객체이며 스프링 빈이 아니다.

    그다음 getRepository(...)는 타깃 객체 SimpleJpaRepository를 만들어 구성의 맨 뒤에 붙이고, ProxyFactory에 타깃과 인터페이스(리포지토리 인터페이스, Repository, TransactionalProxy)를 넣는다. 인터셉터는 정해진 순서로 추가된다. 인터페이스에 디폴트 메서드가 있으면 DefaultMethodInvokingMethodInterceptor, 쿼리 메서드(findByName 같은 이름 기반 메서드와 @Query)를 처리하는 QueryExecutorMethodInterceptor, 마지막으로 구성의 조각들에 호출을 넘기는 ImplementationMethodExecutionInterceptor다. 트랜잭션과 예외 변환 인터셉터는 리포지토리 프록시 후처리기들이 앞쪽에 끼워 넣는다.

    호출 시점에는 이렇게 흘러간다. repo.findAll(predicate)를 부르면 JDK 프록시의 호출 핸들러가 인터셉터 체인을 차례로 실행한다. findAll(Predicate)는 디폴트 메서드도 쿼리 메서드도 아니므로 앞의 인터셉터들은 그냥 다음으로 넘긴다. ImplementationMethodExecutionInterceptor는 구성에서 이 메서드 시그니처를 가진 첫 번째 조각을 찾는다. RepositoryComposition은 조각들의 메서드를 순서대로 훑어 처음 일치하는 것을 고르므로, 조각의 순서가 곧 우선순위다. 사용자 정의 구현 → Querydsl 조각 → SimpleJpaRepository 순이므로 findAll(Predicate)는 Querydsl 조각에서 찾아지고, 리플렉션으로 그 객체의 메서드가 호출된다. 스프링 데이터 레퍼런스의 사용자 정의 구현 절도 "사용자 정의 구현은 기본 구현과 리포지토리 애스펙트보다 우선순위가 높다"고 적고 있다. 이 순서 덕분에 Impl 클래스에 같은 시그니처의 findAll(Predicate)를 만들면 Querydsl 조각의 구현을 덮어쓸 수 있다.

    Q 타입은 어떻게 찾아오는가

    QuerydslJpaPredicateExecutor는 생성자에서 resolver.createPath(entityInformation.getJavaType())를 호출해 엔티티에 대응하는 Q 타입의 인스턴스를 얻는다. 여기서 쓰이는 기본 구현이 SimpleEntityPathResolver이고, 그 동작은 순수한 리플렉션이다. 도메인 클래스 lab.Employee의 패키지 이름과 단순 이름으로 lab.QEmployee라는 클래스 이름을 조립하고(중첩 클래스라면 바깥 클래스 이름과 밑줄이 앞에 붙는다), 도메인 클래스의 클래스 로더로 그 클래스를 로딩한다. 그다음 선언된 필드 가운데 static이면서 타입이 그 Q 클래스 자신인 필드를 찾아 값을 읽는다. 01회에서 본 것처럼 애너테이션 프로세서가 만든 Q 클래스에는 public static final QEmployee employee = new QEmployee("employee");가 있으므로 이 필드가 선택된다.

    이 규칙에서 두 가지 결론이 나온다. 하나는 Q 클래스가 컴파일되어 있지 않으면 애플리케이션 시작 시점에 실패한다는 것이다. 클래스를 찾지 못하면 "Did not find a query class %s for domain class %s" 형식의 메시지와 함께 IllegalArgumentException이 난다. 기본 설정에서 리포지토리 프록시는 빈 생성 시점에 만들어지므로, 문제는 첫 요청이 아니라 컨텍스트 기동 때 드러난다. 다른 하나는 Querydsl 조각이 쓰는 경로 변수의 이름이 언제나 정적 필드의 변수 이름, 즉 employee라는 것이다. 생성자는 이 Q 객체의 타입과 메타데이터로 PathBuilder를 만들고 그것을 Spring Data JPA의 Querydsl 헬퍼에 넘긴다. 이 이름이 뒤에서 Sort를 다룰 때 중요한 역할을 한다.

    QuerydslJpaPredicateExecutor가 만드는 쿼리

    이제 Querydsl 조각 안으로 들어가자. 모든 조회 메서드는 같은 출발점을 공유한다. doCreateQuery는 querydsl.createQuery(path)로 from Employee employee를 가진 쿼리를 만들고, 넘겨받은 Predicate를 where에 넣고, 쿼리 힌트를 설정한다. 여기에 메서드마다 select(path), limit(2), select(Expressions.ONE) 같은 마무리만 다르게 붙는다. 정리하면 이 조각이 실행하는 JPQL의 모양은 언제나 아래 틀 하나다.

    select employee
from Employee employee
where <넘겨받은 Predicate>
[order by ]

    Querydsl 헬퍼의 createQuery()는 EntityManager에서 JPA 구현체를 판별해(PersistenceProvider.fromEntityManager) Hibernate면 HQLTemplates.DEFAULT, EclipseLink면 EclipseLinkTemplates.DEFAULT를 고르고, 나머지는 표준 JPQLTemplates.DEFAULT를 쓴다. 템플릿은 Querydsl 연산을 JPQL 문자열로 직렬화하는 규칙 묶음이다. 같은 Predicate라도 구현체에 따라 다른 문자열이 나올 수 있다는 뜻이며, 스프링 데이터가 이 선택을 대신 해 준다. 쿼리 객체는 JPAQuery를 상속한 패키지 전용 클래스 SpringDataJpaQuery로 만들어지는데, 이 클래스는 JPQL 문자열을 만든 뒤 entityManager.createQuery(...)로 넘기고 상수를 바인딩하고 offset·limit을 setFirstResult·setMaxResults로 옮기는 일을 한다. 여기서 entityManager는 05회에서 본 공유 프록시이므로 실제 실행은 현재 스레드에 묶인 영속성 컨텍스트에서 일어난다.

    페이징과 count 쿼리

    findAll(Predicate, Pageable)의 구현은 인자 검증을 빼면 세 줄이다.

    // QuerydslJpaPredicateExecutor (spring-data-jpa 3.5.13)
final JPQLQuery countQuery = createCountQuery(predicate);
JPQLQuery query = querydsl.applyPagination(pageable, createQuery(predicate).select(path));
return PageableExecutionUtils.getPage(query.fetch(), pageable, countQuery::fetchCount);

    count 쿼리 객체를 먼저 만들지만 실행은 미룬다. 세 번째 인자 countQuery::fetchCount는 메서드 참조로 만든 LongSupplier이고, 실제로 getAsLong()이 불려야 SQL이 나간다. 언제 부르는지는 PageableExecutionUtils.getPage가 정한다. Spring Data Commons 3.5.13의 판정 규칙은 다음과 같다.

    1. pageable이 페이징하지 않는 요청(Pageable.unpaged())이면 내용의 크기를 전체 개수로 쓴다. count 없음.
    2. 가져온 내용이 페이지 크기보다 작고(부분 페이지) 첫 페이지면, 내용의 크기가 곧 전체 개수다. count 없음.
    3. 부분 페이지이고 첫 페이지가 아니지만 내용이 비어 있지 않으면, 이 페이지가 마지막 페이지이므로 offset + 내용 크기가 전체 개수다. count 없음.
    4. 그 밖의 경우, 즉 페이지가 꽉 찼거나 첫 페이지가 아닌데 내용이 비었을 때만 count를 실행한다.

    세 가지 요청으로 확인해 보자. 조건은 모두 employee.age.goe(28)이고, 해당하는 사람은 lee(31), park(40), choi(35), kang(28)의 네 명이다.

    === PageRequest.of(0, 2, Sort.by("age").descending())
select ... from employee e1_0 where e1_0.age>=? order by e1_0.age desc offset ? rows fetch first ? rows only
select count(e1_0.id) from employee e1_0 where e1_0.age>=?
  → park choi total=4
=== PageRequest.of(0, 10)
select ... from employee e1_0 where e1_0.age>=? offset ? rows fetch first ? rows only
  → lee park choi kang total=4
=== PageRequest.of(1, 3, Sort.by("age"))
select ... from employee e1_0 where e1_0.age>=? order by e1_0.age offset ? rows fetch first ? rows only
  → park total=4

    첫 요청은 두 칸짜리 페이지가 꽉 찼으므로 규칙 4에 따라 count가 실행되었다. 두 번째는 열 칸 중 네 칸만 찬 첫 페이지라 규칙 2가 적용되어 count 없이 전체 개수 4가 정해졌다. 세 번째는 두 번째 페이지(offset 3)에서 한 명만 나왔으므로 규칙 3에 따라 3 + 1 = 4가 되었다. 세 경우 모두 total은 4로 같지만, 실제 count SQL은 첫 경우에만 나갔다. 목록 화면에서 결과가 한 페이지에 다 들어가는 검색이 많다면 이 최적화로 쿼리 하나를 아낀다. 다만 이 최적화는 내용 쿼리와 count 쿼리가 같은 행 집합을 센다는 가정에 기댄다. 그 가정이 깨지는 경우(예를 들어 내용 쿼리만 컬렉션 페치 조인으로 행이 불어나는 경우)는 06회에서 다룬 count 쿼리 분리의 영역이다.

    count 쿼리 자체는 Querydsl의 fetchCount()로 실행된다. Querydsl 5.1.0의 AbstractJPAQuery에서 fetchCount()와 fetchResults()는 @Deprecated가 붙어 있다. 같은 소스를 보면 group by 항목이 둘 이상이거나 having이 있으면 count를 DB에서 세지 않고 전체 결과를 가져와 메모리에서 크기를 재며 경고 로그를 남긴다. QuerydslJpaPredicateExecutor에는 group by가 들어갈 자리가 없으므로 이 경로를 밟지는 않지만, 스프링 데이터가 아직 폐기 예정 API에 기대고 있다는 점은 알아 둘 만하다. count(Predicate) 메서드도 같은 fetchCount()를 쓴다.

    조인을 고를 수 없다: 암묵적 조인이 행을 지울 때

    앞의 JPQL 틀에는 join이 들어갈 자리가 없다. Predicate는 where 절에 들어갈 조건일 뿐이고, 조인을 선언하는 문법은 Predicate가 아니라 쿼리 객체의 join(), leftJoin() 메서드에 있다. 그래서 QuerydslPredicateExecutor로 연관 엔티티의 속성을 조건에 쓰려면 employee.department.name처럼 경로로 따라가는 수밖에 없다. 이런 경로를 암묵적 조인(implicit join)이라고 한다. 문제는 암묵적 조인의 종류를 우리가 정할 수 없다는 것이다.

    Hibernate 6.6 쿼리 언어 가이드의 "Implicit association joins (path expressions)" 절은 "암묵적 조인은 언제나 내부 조인으로 취급된다(Implicit joins are always treated as inner joins)"고 적고 있다. 내부 조인은 조인 상대가 없는 행을 결과에서 뺀다. 이것이 OR 조건과 만나면 직관과 다른 결과가 나온다. "dev 부서 소속이거나 32세 초과"인 직원을 찾아보자. 손으로 따지면 kim(dev), lee(dev), park(40), choi(35)의 네 명이어야 한다.

    repo.findAll(employee.department.name.eq("dev").or(employee.age.gt(32)));
    select employee from Employee employee
where employee.department.name = ?1 or employee.age > ?2            ← Querydsl이 만든 JPQL

select e1_0.id,e1_0.age,e1_0.department_id,e1_0.name from employee e1_0
join department d1_0 on d1_0.id=e1_0.department_id
where d1_0.name=? or e1_0.age>?
  → kim lee park

    choi가 빠졌다. JPQL에는 join이라는 단어가 없지만, Hibernate가 경로 employee.department.name을 해석하면서 join department(내부 조인)를 SQL에 넣었다. SQL은 FROM과 JOIN으로 행 집합을 먼저 만들고 그 위에 WHERE를 평가한다. choi는 department_id가 null이라 조인 단계에서 이미 사라졌으므로, WHERE의 두 번째 조건 e1_0.age>?를 만족하더라도 평가될 기회조차 없다. 조건문만 보면 OR인데 결과는 "부서가 있는 사람 중에서"라는 숨은 AND가 붙은 셈이다. 명시적 조인을 쓸 수 있었다면 leftJoin(employee.department, department)로 해결했겠지만, QuerydslPredicateExecutor에는 그 수단이 없다.

    order by의 경로는 왜 left join이 되는가

    흥미롭게도 같은 경로를 정렬에 쓰면 결과가 다르다.

    repo.findAll(employee.age.goe(0), Sort.by("department.name"));
repo.findAll(employee.age.goe(0), employee.department.name.asc());
    select e1_0.id,e1_0.age,e1_0.department_id,e1_0.name from employee e1_0
left join department d1_0 on d1_0.id=e1_0.department_id
where e1_0.age>=? order by d1_0.name
  → choi kim lee park kang

    이번에는 left join이고 choi도 살아 있다. Hibernate의 규칙이 바뀐 것이 아니라, Hibernate가 보기 전에 Querydsl이 JPQL을 바꿨다. 같은 정렬을 JPAQuery로 직접 만들어 JPQL을 출력하면 이렇다.

    select employee
from Employee employee
  left join employee.department as employee_department
where employee.age >= ?1
order by employee_department.name asc

    근거는 Querydsl의 JPAQueryMixin에 있다. 이 클래스의 convert(expr, role)은 역할이 ORDER_BY인 경로에 대해 convertPathForOrder를 호출한다. 이 메서드는 경로가 세 단계 이상(employee.department.name)이고, 그 경로나 부모 경로(employee.department)가 select·where·group by·having 어디에도 쓰이지 않았으면 부모 경로를 "줄인다(shorten)". 줄이는 방법은 부모가 엔티티 경로일 때 leftJoin(employee.department, employee_department)를 쿼리에 추가하고, 정렬 경로를 새 별칭 기준(employee_department.name)으로 바꾸는 것이다. 별칭 이름은 ExpressionUtils.createRootVariable이 경로 문자열의 점을 밑줄로 바꿔 만든다. 그 결과 정렬에만 쓰인 연관 경로 때문에 내부 조인이 생겨 행이 사라지는 일은 일어나지 않는다.

    그렇다면 where 절에서 같은 경로를 이미 쓰고 있으면 어떻게 될까. 위 조건 "그 경로나 부모 경로가 where에 쓰이지 않았으면"이 거짓이 되므로 Querydsl은 경로를 그대로 두고, Hibernate는 where와 order by의 같은 경로를 하나의 암묵적 조인, 즉 내부 조인으로 처리한다. 조건과 정렬에 같은 연관 경로가 있으면 다시 내부 조인 세계로 돌아간다는 뜻이다. 정리하면 QuerydslPredicateExecutor에서 조인의 종류는 우리가 쓴 코드가 아니라 경로가 놓인 자리와 두 라이브러리의 규칙이 정한다.

    경로가 놓인 자리누가 조인을 만드는가SQL 조인부서 없는 choi
    where (Predicate 안)Hibernate의 암묵적 조인join (내부)사라진다
    order by만 (Sort 또는 OrderSpecifier)Querydsl JPAQueryMixin이 left join 추가left join남는다
    where와 order by 둘 다Querydsl은 손대지 않음 → Hibernatejoin (내부)사라진다

    페치 조인이 없다는 것: N+1과 @EntityGraph

    조인을 고를 수 없다는 말에는 페치 조인도 포함된다. findAll(Predicate)로 직원을 읽고 각 직원의 부서 이름에 접근하면, 지연 로딩 프록시가 초기화될 때마다 부서를 조회하는 SQL이 추가로 나간다(서로 다른 부서 수만큼). JPA 활용 2편에서 본 N+1 문제가 그대로 생긴다. 그런데 Querydsl 조각에는 우회로가 하나 열려 있다. 앞의 소스에서 createQuery가 getQueryHints().withFetchGraphs(entityManager)로 힌트를 설정하던 것을 기억하자. 이 힌트는 CrudMethodMetadata, 즉 프록시의 첫 번째 인터셉터가 "지금 호출된 리포지토리 메서드에 붙은 애너테이션"을 기록해 둔 정보에서 온다. 따라서 리포지토리 인터페이스에서 메서드를 다시 선언하고 @EntityGraph를 붙이면 Querydsl 조각이 그 그래프를 적용한다.

    public interface EmployeeRepository extends JpaRepository,
        QuerydslPredicateExecutor {

    @Override
    @EntityGraph(attributePaths = "department")
    List findAll(Predicate predicate);   // Iterable을 List로 좁혀 재선언
}
    === findAll(Predicate) — @EntityGraph 재선언
select e1_0.id,e1_0.age,d1_0.id,d1_0.name,e1_0.name from employee e1_0
left join department d1_0 on d1_0.id=e1_0.department_id where e1_0.age>=?
=== findAll(Predicate, Sort) — 재선언하지 않은 메서드
select e1_0.id,e1_0.age,e1_0.department_id,e1_0.name from employee e1_0 where e1_0.age>=? order by e1_0.age
select d1_0.id,d1_0.name from department d1_0 where d1_0.id=?      ← lee의 부서 접근 시
select d1_0.id,d1_0.name from department d1_0 where d1_0.id=?      ← park의 부서 접근 시

    재선언한 메서드는 부서 열까지 한 번에 읽는 left join SQL이 되었고, 재선언하지 않은 메서드는 지연 로딩 SQL이 따로 나갔다. 부서가 없는 choi는 접근할 프록시가 없으므로 추가 SQL도 없다.

    여기에는 05회의 공유 EntityManager와 같은 모양의 장치가 하나 더 숨어 있다. QuerydslJpaPredicateExecutor는 리포지토리마다 하나뿐인 객체이고 여러 요청 스레드가 동시에 호출한다. 그런데 "지금 호출된 메서드"는 스레드마다 다르다. 그래서 조각이 생성자로 받는 CrudMethodMetadata는 실제 메타데이터가 아니라 프록시다. CrudMethodMetadataPostProcessor의 소스를 보면 이 프록시의 타깃 소스(ThreadBoundTargetSource)는 호출될 때마다 ThreadLocal에 저장된 현재 호출(MethodInvocation)을 꺼내고, 그 메서드를 키로 TransactionSynchronizationManager의 스레드 바인딩 리소스 맵에서 메타데이터를 찾아 돌려준다. 프록시 맨 앞의 인터셉터가 호출 직전에 메타데이터를 바인딩하고 호출이 끝나면 해제한다. 공유되는 것은 "찾아가는 방법"이고, 찾아지는 값은 스레드마다 따로 있다.

    애너테이션은 메서드 단위로 기록되므로 오버로드마다 따로 재선언해야 한다. 이 방법은 페치할 연관을 고정할 뿐이고, 조건에 쓸 조인의 종류(내부냐 외부냐)는 여전히 고를 수 없다.

    이 장의 핵심

    QuerydslPredicateExecutor는 리포지토리 프록시의 조각 구성에 끼워 넣어진 QuerydslJpaPredicateExecutor가 select 엔티티 from 엔티티 where Predicate라는 고정된 틀로 쿼리를 만드는 기능이다. 틀이 고정되어 있으므로 조인은 경로가 놓인 자리에 따라 Hibernate(내부 조인)나 Querydsl(정렬용 외부 조인)이 대신 정하고, 우리가 명시할 수 없다. 단순한 단일 엔티티 조회에는 충분하지만 조인이 결과를 좌우하는 순간 통제권이 없다는 것이 드러난다.

    설계 관점의 비용도 하나 있다. findAll(Predicate)를 부르는 쪽은 Predicate를 만들어야 하므로, 서비스 계층이나 컨트롤러가 Querydsl의 Q 타입과 BooleanExpression에 의존하게 된다. 리포지토리가 감추어야 할 저장 기술의 세부가 호출자 쪽으로 새는 것이다. 리포지토리 안에서만 Predicate를 만들고 밖으로는 검색 조건 객체만 받는 06회의 구조와 비교하면, 의존 방향이 어떻게 달라지는지가 분명하다.

    Querydsl Web 지원: 쿼리 문자열이 Predicate가 된다

    검색 화면의 요청은 대개 GET /employees?name=kim&age=31 같은 쿼리 문자열로 온다. 05회에서는 이것을 검색 조건 객체로 바인딩한 뒤 조건마다 메서드를 만들어 Predicate를 조립했다. 스프링 데이터의 Querydsl Web 지원은 이 조립을 통째로 건너뛴다. 컨트롤러 메서드의 파라미터를 Predicate 타입으로 선언하고 @QuerydslPredicate를 붙이면, 쿼리 파라미터 이름을 엔티티의 속성 경로로 해석해 Predicate를 만들어 넘겨준다. 받은 Predicate는 그대로 QuerydslPredicateExecutor에 넘길 수 있다.

    @RestController
public class EmployeeController {
    private final EmployeeRepository repository;

    public EmployeeController(EmployeeRepository repository) { this.repository = repository; }

    @GetMapping("/employees")
    public List search(@QuerydslPredicate(root = Employee.class) Predicate predicate) {
        System.out.println("[web] predicate=" + predicate);
        return StreamSupport.stream(repository.findAll(predicate).spliterator(), false)
                .map(Employee::getName).sorted().toList();
    }
}

    스프링 데이터 JPA 레퍼런스는 기본 바인딩 규칙을 세 줄로 정리한다. 단순 속성에 값 하나가 오면 eq, 컬렉션 속성에 값이 오면 contains, 단순 속성에 값이 여러 개 오면 in이다. MockMvc로 여러 요청을 보내 실제로 만들어지는 Predicate와 SQL을 기록했다. 결과 목록은 컨트롤러에서 이름순으로 정렬했다.

    요청만들어진 Predicate (toString)SQL의 조건결과
    ?name=kimemployee.name = kimwhere e1_0.name=?kim
    ?name=Kimemployee.name = Kimwhere e1_0.name=?(없음)
    ?age=25&age=40employee.age in [25, 40]where e1_0.age in (?,?)kim, park
    ?department.name=dev&age=31employee.department.name = dev && employee.age = 31join department ... where d1_0.name=? and e1_0.age=?lee
    ?id=1employee.id = 1where e1_0.id=?kim (이 실행에서 kim의 식별자가 1)
    ?nmae=kim (오타)빈 BooleanBuilder조건 없음다섯 명 전부
    ?name= (빈 값)빈 BooleanBuilder조건 없음다섯 명 전부
    파라미터 없음빈 BooleanBuilder조건 없음다섯 명 전부
    ?age=abc(만들어지지 않음)-ConversionFailedException

    표에서 다섯 가지를 읽어 낼 수 있다. 첫째, 문자열 비교는 eq이므로 대소문자까지 정확히 같아야 한다. "Kim"으로는 아무도 찾지 못한다. 둘째, 같은 이름의 파라미터를 여러 번 보내면 in이 된다. 범위 검색(between)이 아니라는 점에 주의하자. 셋째, 점으로 이어진 파라미터 이름 department.name은 연관 경로로 해석되고, 앞 절에서 본 대로 where의 암묵적 조인이므로 내부 조인이 된다. 넷째, 해석할 수 없는 이름(오타)이나 빈 값은 오류 없이 조용히 무시된다. 조건이 하나도 남지 않으면 빈 BooleanBuilder가 넘어가고, 05회에서 본 대로 값이 null인 빌더는 where에 아무것도 추가하지 않으므로 전체 조회가 된다. 다섯째, 형식이 맞지 않는 값은 타입 변환에서 실패하는데, 이 예외를 처리하는 HandlerExceptionResolver가 없어서 MockMvc에서는 ServletException("Request processing failed")으로 감싸져 던져졌다. 서블릿 컨테이너에서는 처리되지 않은 예외이므로 400이 아니라 500 응답으로 끝난다.

    넷째 항목은 운영에서 특히 위험하다. 클라이언트가 파라미터 이름을 잘못 쓰면 "결과 없음"이나 "400 Bad Request"가 아니라 테이블 전체가 돌아온다. 엔티티의 필드 이름을 리팩터링으로 바꿨을 때도 마찬가지다. 예전 이름으로 요청하던 클라이언트는 오류를 받지 못한 채 전체 목록을 받게 되고, 행이 많은 테이블이라면 그 요청 하나가 커넥션과 메모리를 오래 붙잡는다. 페이징을 함께 쓰면 피해는 줄지만, 조건이 무시되었다는 사실은 여전히 드러나지 않는다.

    한 층 아래: 요청에서 Predicate까지의 경로

    이 기능은 어떻게 켜졌을까. 우리는 설정을 하나도 추가하지 않았다. 출발점은 Spring Boot의 SpringDataWebAutoConfiguration이다. 3.5.16 소스에서 이 자동 구성 클래스는 서블릿 웹 애플리케이션이고, PageableHandlerMethodArgumentResolver와 WebMvcConfigurer가 클래스패스에 있으며, PageableHandlerMethodArgumentResolver 빈이 따로 없을 때 활성화되고, 클래스에 @EnableSpringDataWebSupport가 붙어 있다. 그리고 @EnableSpringDataWebSupport는 @Import로 세 클래스를 가져오는데, 그중 QuerydslActivator라는 ImportSelector가 앞에서 본 QUERY_DSL_PRESENT가 참일 때만 QuerydslWebConfiguration을 설정 클래스로 등록한다. 스프링 데이터 레퍼런스가 "클래스패스에 Querydsl이 있으면 @EnableSpringDataWebSupport와 함께 자동으로 활성화된다"고 쓴 문장의 실체가 이 선택자다.

    QuerydslWebConfiguration은 WebMvcConfigurer를 구현한 설정 클래스로, 두 개의 @Lazy 빈을 정의한다. querydslBindingsFactory는 EntityPathResolver 빈이 하나 있으면 그것을, 없으면 앞에서 본 SimpleEntityPathResolver.INSTANCE를 쓴다. querydslPredicateArgumentResolver는 이름이 mvcConversionService인 변환 서비스(스프링 MVC가 @RequestParam 변환에 쓰는 것과 같은 서비스)를 받는다. 그리고 addArgumentResolvers에서 이 리졸버를 사용자 정의 인자 리졸버 목록의 0번 자리에 넣는다. 실험에서도 컨텍스트에 querydslPredicateArgumentResolver라는 이름의 빈이 있음을 확인했다.

    요청이 들어오면 스프링 MVC는 핸들러 메서드의 파라미터마다 인자 리졸버들에게 "이 파라미터를 처리할 수 있는가"를 묻는다(스프링 MVC 1편의 HandlerMethodArgumentResolver). QuerydslPredicateArgumentResolverSupport.supportsParameter의 판정은 파라미터 타입이 Predicate이거나 Optional인지다. 애너테이션 유무가 아니라 타입으로 판정한다는 점이 흥미롭다. @QuerydslPredicate를 붙이지 않은 Predicate 파라미터도 이 리졸버가 맡고, 그때는 루트 타입을 애너테이션 대신 메서드의 반환 타입에서 추론한다. 반대로 @QuerydslPredicate를 Predicate가 아닌 타입에 붙이면 IllegalArgumentException이 난다.

    세 번째 단계가 앞 절의 "조용한 무시"를 만든다. QuerydslPredicateBuilder.getPredicate의 반복문에는 continue가 세 번 나온다. 빈 값일 때, bindings.isPathAvailable(path, type)이 거짓일 때, 경로 정보가 null일 때다. 경로 해석은 QuerydslBindings.getPropertyPath가 하는데, 이 메서드는 PropertyPath.from이 던지는 PropertyReferenceException을 잡아 null을 반환하도록 작성되어 있다. 즉 "모르는 이름은 무시한다"는 것은 실수가 아니라 의도된 동작이다. 같은 요청에 page, size, sort 같은 페이징 파라미터가 섞여 와도 Predicate 생성이 깨지지 않는 것이 이 덕분이다. 실험에서 /employees/page?age=28&page=0&size=2&sort=age,desc를 보내자 Predicate는 employee.age = 28만 되었고, 나머지 셋은 Pageable 인자 리졸버가 따로 가져갔다.

    네 번째 단계의 변환 실패는 반대로 조용하지 않다. age는 int 필드이므로 "abc"를 int로 바꾸려다 NumberFormatException이 나고, ConversionService가 이를 ConversionFailedException으로 감싼다. 실험의 예외 연쇄는 ServletException → ConversionFailedException("Failed to convert from type [java.lang.String] to type [int] for value [abc]") → NumberFormatException이었다. @RequestParam int age였다면 스프링 MVC가 변환 실패를 MethodArgumentTypeMismatchException으로 바꿔 400으로 응답했겠지만, 이 리졸버는 그런 변환을 하지 않는다. 클라이언트 입력 오류를 400으로 돌려주고 싶다면 @ExceptionHandler나 @ControllerAdvice에서 ConversionFailedException을 직접 처리해야 한다.

    성능 측면에서 하나 더 보자. 두 번째 단계의 QuerydslBindings는 요청마다 새로 만들어지지만, 비싼 부분은 캐시된다. 도메인 타입별 Q 객체는 QuerydslBindingsFactory의 ConcurrentHashMap에, 경로 정보로부터 만든 Querydsl 경로 객체는 QuerydslPredicateBuilder의 ConcurrentHashMap에 저장된다. 리졸버 빈은 싱글톤이고 여러 요청 스레드가 동시에 쓰므로, 공유 캐시가 동시성 컬렉션인 것은 필연이다. 반면 바인딩 정의(QuerydslBindings)와 사용자 정의 적용은 요청마다 새로 이루어진다.

    쿼리 문자열의 파라미터 세 개가 경로 해석·타입 변환·바인딩을 거쳐 하나의 Predicate로 합쳐지고, 오타 파라미터는 중간에서 버려지는 모습. 왼쪽에 브라우저 주소창 모양의 상자가 있고 안에 "?name=kim&age=31&nmae=lee"라고 적혀 있다. 여기서 세 개의 작은 카드가 오른쪽으로 흘러간다: "name=kim", "age=31", "nmae=lee". 카드들은 차례로 세 개의 세로 관문을 통과한다. 관문 이름은 왼쪽부터 "경로 해석", "타입 변환", "바인딩". "nmae=lee" 카드는 첫 관문 "경로 해석"에서 아래쪽 휴지통으로 떨어지고, 휴지통에 "조용히 무시"라는 라벨이 붙어 있다. "age=31" 카드는 "타입 변환" 관문을 지나며 글자가 "31 (int)"로 바뀐다. "바인딩" 관문을 지난 두 카드는 각각 "name = kim", "age = 31"이 되어 오른쪽의 깔때기로 들어가고, 깔때기 출구에 "BooleanBuilder.and()"라는 라벨과 최종 결과 상자 "Predicate"가 있다. 맨 위에 작은 글씨로 "QuerydslPredicateArgumentResolver"라는 제목. 평면 다이어그램, 흰 배경, 파란 계열 강조색. 해석할 수 없는 파라미터는 경로 해석 단계에서 버려지고, 남은 조건만 AND로 결합된다.

    바인딩 사용자 정의와 그 비용

    기본 규칙만으로는 실무 검색 화면을 만들기 어렵다. 이름은 부분 일치로, 나이는 범위로 찾고 싶고, 식별자로 검색하는 것은 막고 싶다. 이런 요구는 QuerydslBinderCustomizer로 표현한다. 이 인터페이스의 메서드는 customize(QuerydslBindings bindings, T root) 하나이고, root로 Q 타입 인스턴스가 넘어온다. 별도 클래스로 만들어 @QuerydslPredicate(bindings = ...)로 지정하는 방법부터 보자.

    public class EmployeeBindings implements QuerydslBinderCustomizer {
    @Override
    public void customize(QuerydslBindings bindings, QEmployee root) {
        System.out.println("[bindings] customize called, this=" + System.identityHashCode(this));
        bindings.bind(root.name).first(StringExpression::containsIgnoreCase);
        bindings.bind(root.age).all((path, values) -> {
            Iterator it = values.iterator();
            Integer from = it.next();
            if (!it.hasNext()) return Optional.of(path.goe(from));
            return Optional.of(path.between(from, it.next()));
        });
        bindings.excluding(root.id);
    }
}

// 컨트롤러
@GetMapping("/employees/custom")
public List custom(
        @QuerydslPredicate(root = Employee.class, bindings = EmployeeBindings.class) Predicate predicate) {
    // ... 앞과 같다
}

    bind(경로).first(...)는 넘긴 SingleValueBinding에 그 파라미터의 첫 번째 값만 꺼내 주는 바인딩을 등록하고, all(...)은 값 전체를 받는 MultiValueBinding을 등록한다. 위 코드는 나이 값이 하나면 하한(goe), 둘이면 범위(between)로 해석한다. all의 람다는 값이 하나 이상일 때만 불린다. 기본 바인딩과 마찬가지로 빈 값은 그 전에 걸러지기 때문이다. excluding(root.id)는 그 경로를 거부 목록에 넣는다.

    /employees/custom?name=K          → containsIc(employee.name,K)
   where lower(e1_0.name) like ? escape '!'           → ["kang","kim","park"]
/employees/custom?age=30          → employee.age >= 30  → ["choi","lee","park"]
/employees/custom?age=26&age=35   → employee.age between 26 and 35 → ["choi","kang","lee"]
/employees/custom?id=1            → 빈 BooleanBuilder (id는 거부 목록) → 다섯 명 전부
[bindings] customize called, this=122661394
[bindings] customize called, this=663646750
[bindings] customize called, this=1086330138   ← 요청마다 다른 객체

    containsIgnoreCase는 컬럼에 lower()를 씌운 like가 되었다. 사용자 입력이 like 패턴 안에 들어가므로, 입력값의 %나 _를 패턴 문자가 아닌 글자로 다룰 수 있게 SQL에 escape '!' 절이 붙었다. 컬럼에 lower()를 씌운 조건은 일반적인 B+Tree 인덱스(데이터베이스 기본편)를 탈 수 없고, 앞에 %가 붙는 부분 일치 역시 인덱스의 정렬 순서를 쓸 수 없으므로 이 바인딩은 전체 스캔을 각오해야 한다.

    마지막 세 줄의 식별값(System.identityHashCode, 실행마다 다르다)이 모두 다르다는 것에 주목하자. EmployeeBindings 객체가 요청마다 새로 만들어졌다는 뜻이다. QuerydslBindingsFactory.createQuerydslBinderCustomizer는 애너테이션에 지정된 클래스로 beanFactory.getBean(type)을 먼저 시도하고, 빈이 없어서 NoSuchBeanDefinitionException이 나면 beanFactory.createBean(type)으로 새 객체를 만들어 의존성을 주입한다. createBean은 객체를 싱글톤 레지스트리에 등록하지 않으므로, 다음 요청에서 또 예외를 거쳐 또 만든다. 이 클래스를 @Component로 등록해 두면 getBean이 바로 성공해 같은 객체를 재사용한다. 그때는 이 객체가 여러 스레드에서 동시에 쓰이므로 상태를 갖지 않게 작성해야 한다.

    리포지토리 인터페이스의 디폴트 메서드로 정의하기

    두 번째 방법은 리포지토리 인터페이스가 QuerydslBinderCustomizer까지 상속하고 customize를 디폴트 메서드로 구현하는 것이다. 스프링 데이터 레퍼런스도 이 방식을 예제로 보여 준다. 이 경우 @QuerydslPredicate에 bindings를 지정하지 않으면 팩토리가 Repositories에서 그 도메인 타입의 리포지토리를 찾고, 그 객체가 QuerydslBinderCustomizer의 인스턴스이면 사용자 정의 객체로 쓴다. 소스상 우선순위는 애너테이션의 bindings가 먼저이고, 그것이 기본값일 때만 리포지토리를 본다.

    public interface DepartmentRepository extends JpaRepository,
        QuerydslPredicateExecutor, QuerydslBinderCustomizer {

    @Override
    default void customize(QuerydslBindings bindings, QDepartment root) {
        boolean viaInterceptor = Arrays.stream(new Throwable().getStackTrace())
                .anyMatch(f -> f.getClassName().contains("DefaultMethodInvokingMethodInterceptor"));
        System.out.println("[dept-customize] viaDefaultMethodInterceptor=" + viaInterceptor);
        bindings.bind(root.name).first(StringExpression::startsWithIgnoreCase);
    }
}
    [dept-customize] viaDefaultMethodInterceptor=true
[web-dept] predicate=startsWithIgnoreCase(department.name,D)
select d1_0.id,d1_0.name from department d1_0 where lower(d1_0.name) like ? escape '!'
  → ["dev"]

    여기서 질문 하나가 생긴다. 리포지토리 빈은 JDK 동적 프록시다. 프록시에서 customize를 부르면 호출 핸들러로 들어오는데, 타깃인 SimpleJpaRepository에는 이 메서드가 없고 조각 구성에도 없다. 그러면 인터페이스에 적힌 디폴트 메서드의 본문은 누가 실행할까. 실행 기록이 보여 주듯 앞에서 본 인터셉터 체인의 DefaultMethodInvokingMethodInterceptor다. 그 소스는 호출된 메서드가 Method.isDefault()이면 MethodHandles.privateLookupIn(선언 인터페이스, lookup)으로 접근 권한을 얻고 lookup.findSpecial(...)로 메서드 핸들을 찾아, 프록시 객체에 묶은 뒤(bindTo(proxy)) 호출한다. 핸들은 메서드별로 ConcurrentHashMap에 캐시된다.

    왜 그냥 method.invoke(proxy, args)가 아닐까. 리플렉션 호출은 가상 메서드 호출(virtual method invocation)이므로 실제 객체의 클래스, 즉 프록시 클래스에서 메서드를 다시 찾는다. 프록시 클래스의 customize는 호출 핸들러로 가는 코드이므로 같은 인터셉터로 되돌아와 무한 재귀가 된다. findSpecial로 얻은 핸들은 바이트코드의 invokespecial과 같은 의미로, 동적 디스패치 없이 "그 인터페이스에 적힌 바로 그 구현"을 실행한다. 자바의 super.method() 호출이 하위 클래스의 재정의를 건너뛰는 것과 같은 원리다. 참고로 JDK 16부터는 같은 목적의 InvocationHandler.invokeDefault(proxy, method, args)가 표준 API로 들어왔다.

    노출 범위를 좁혀라: 허용 목록과 별칭

    기본 설정에서는 루트 엔티티에서 도달할 수 있는 모든 속성 경로가 검색 조건이 된다. 앞의 실험에서 ?id=1이 그대로 조건이 된 것처럼, 화면에 보이지 않는 필드나 연관 엔티티의 깊은 경로까지 열려 있다. 엔티티에 외부에 알려져서는 안 되는 필드(비밀번호 해시, 내부 등급 같은 것)가 있다면, 그 필드로 조건을 걸고 결과가 나오는지만 보는 방식으로 값을 한 글자씩 추측할 수 있다. 스프링 데이터 레퍼런스의 예제가 bindings.excluding(user.password)를 넣은 이유가 이것이다. 또 임의의 연관 경로로 조건을 걸 수 있다는 것은 인덱스가 없는 컬럼에 대한 조인과 스캔을 외부에서 마음대로 일으킬 수 있다는 뜻이기도 하다.

    거부 목록(excluding)은 새 필드가 추가될 때마다 빠뜨릴 위험이 있으므로 허용 목록이 더 안전하다. QuerydslBindings의 소스에서 경로 가시성 판정을 읽으면 규칙은 다음과 같다. 허용 목록(including으로 채운다)이 비어 있지 않으면 목록에 있는 경로만 보인다. 연관 경로 department.name은 앞부분 department가 목록에 없더라도 전체 경로가 목록에 있으면 보인다. 허용 목록이 비어 있으면 거부 목록에 없는 경로가 모두 보인다. 그리고 bind(경로).as("별칭")으로 바인딩하면 파라미터 이름으로 별칭을 쓰게 되고, 원래 경로는 거부 목록에 들어간다. 다만 허용 목록이 비어 있지 않으면 거부 목록은 판정에 쓰이지 않으므로, 원래 경로까지 허용 목록에 넣으면 원래 이름도 계속 조건이 된다(as의 Javadoc도 원래 경로를 남기려면 허용 목록에 넣으라고 적는다). 엔티티의 내부 구조를 HTTP 계약에서 감추는 데 쓸 수 있다.

    @Override
public void customize(QuerydslBindings bindings, QEmployee root) {
    bindings.including(root.name, root.age);    // 이 둘과 아래 별칭 dept만 검색 가능
    bindings.bind(root.department.name).as("dept").first(StringExpression::eq);
    // 이제 ?dept=dev 는 조건이 되고, ?department.name=dev 는 무시된다
}

    그래도 남는 한계가 있다. 조건은 언제나 AND로만 결합되고 OR를 표현할 문법이 없다. 파라미터 이름이 엔티티의 속성 이름이므로 HTTP API의 계약이 엔티티 설계에 묶인다. 그리고 컨트롤러가 QEmployee와 Querydsl의 Predicate에 직접 의존한다. 화면 하나를 빨리 만드는 관리자 도구라면 이 거래가 남는 장사일 수 있지만, 외부에 공개하는 API라면 검색 조건 DTO를 받아 리포지토리 안에서 Predicate를 조립하는 05·06회의 방식이 계약을 더 분명하게 지킨다.

    QuerydslRepositorySupport: 사용자 정의 구현의 기반 클래스

    이제 리포지토리 내부로 돌아가자. 06회의 사용자 정의 구현 클래스는 JPAQueryFactory를 주입받아 쿼리를 썼다. 스프링 데이터 JPA는 이 구현 클래스가 상속할 수 있는 추상 클래스 QuerydslRepositorySupport를 제공한다. Javadoc의 설명은 "Querydsl 라이브러리로 리포지토리를 구현하기 위한 기반 클래스"다. 3.5.13 소스에서 이 클래스가 가진 것을 정리하면 아래와 같다.

    구성 요소내용

    생성자QuerydslRepositorySupport(Class domainClass) — new PathBuilderFactory().create(domainClass)로 PathBuilder를 만들어 둔다

    이 클래스로 06회와 같은 사용자 정의 구현을 써 보자. 클래스 이름이 리포지토리 인터페이스 이름 + Impl이므로 스프링 데이터가 사용자 정의 조각으로 찾아 앞에서 본 조각 구성의 맨 앞에 넣는다.

    public interface EmployeeRepositoryCustom {
    Page searchBySupport(String deptName, Pageable pageable);
}

public record EmployeeRow(String name, int age, String deptName) {}

public class EmployeeRepositoryImpl extends QuerydslRepositorySupport
        implements EmployeeRepositoryCustom {

    public EmployeeRepositoryImpl() {
        super(Employee.class);
        System.out.println("[impl] constructor, em=" + getEntityManager());
    }

    @Override
    public Page searchBySupport(String deptName, Pageable pageable) {
        JPQLQuery query = from(employee)
                .leftJoin(employee.department, department)
                .where(deptName == null ? null : department.name.eq(deptName))
                .select(Projections.constructor(EmployeeRow.class,
                        employee.name, employee.age, department.name));
        JPQLQuery paged = getQuerydsl().applyPagination(pageable, query);
        System.out.println("[impl] jpql=" + paged);
        List content = paged.fetch();
        long total = paged.fetchCount();
        return new PageImpl<>(content, pageable, total);
    }
}

    첫 줄이 객체의 생애 순서를 보여 준다. 생성자가 실행될 때 EntityManager는 아직 null이다. 스프링 핵심 원리에서 본 대로 세터 주입은 생성자로 객체가 만들어진 다음 의존성 주입 단계에서 일어나고, @PostConstruct 콜백은 그 뒤 초기화 단계에서 불린다. 따라서 생성자에서 from(...)을 부르면 IllegalStateException("Querydsl is null")이 난다. validate()가 @PostConstruct인 이유도 이 순서 때문이다. 주입이 끝난 직후에 빠진 것이 없는지 확인해, 문제를 첫 쿼리가 아니라 기동 시점에 드러낸다. 주입되는 EntityManager는 05회에서 본 공유 프록시이므로 이 싱글톤 객체를 여러 스레드가 동시에 써도 각 스레드는 자기 영속성 컨텍스트로 쿼리를 실행한다.

    JPQL을 보면 applyPagination이 한 일이 드러난다. Pageable의 정렬 age가 order by employee.age asc가 되었고, offset·limit은 JPQL이 아니라 쿼리 수식자(modifier)로 들어가 SQL의 offset ? rows fetch first ? rows only가 되었다. 같은 쿼리 객체로 부른 fetchCount()는 정렬과 offset·limit을 뺀 count SQL이 되었다. Querydsl이 count용으로 직렬화할 때 이 둘을 빼기 때문이다. 이 실행에서 Hibernate는 count SQL에서 결과에 쓰이지 않는 left join도 생략했는데, 이런 생략은 JPA 구현체의 최적화이므로 count 쿼리를 가볍게 만드는 판단은 우리가 직접 쿼리를 나누어 하는 편이 확실하다(06회의 주제). 또 이 코드는 count를 항상 실행한다. 앞에서 본 PageableExecutionUtils를 쓰지 않았기 때문이다.

    Querydsl 헬퍼가 Sort를 경로로 바꾸는 규칙과 그 한계

    QuerydslRepositorySupport와 QuerydslPredicateExecutor는 정렬 처리를 같은 Querydsl 헬퍼에 맡긴다. 그 헬퍼의 applySorting(sort, query)는 정렬이 없으면 그대로 반환하고, Sort가 Querydsl 전용 하위 클래스 QSort이면 그 안의 OrderSpecifier를 그대로 orderBy에 넣는다. 일반 Sort면 정렬 항목마다 toOrderSpecifier를 만들고, 그 핵심이 buildOrderPropertyPathFrom이다.

    // Querydsl (spring-data-jpa 3.5.13) buildOrderPropertyPathFrom, 주석과 인자 검증 제거
QueryUtils.checkSortExpression(order);
try {
    PropertyPath path = PropertyPath.from(order.getProperty(), builder.getType());
    Expression sortPropertyExpression = builder;
    while (path != null) {
        sortPropertyExpression = !path.hasNext() && order.isIgnoreCase() && String.class.equals(path.getType())
                ? Expressions.stringPath((Path) sortPropertyExpression, path.getSegment()).lower()
                : Expressions.path(path.getType(), (Path) sortPropertyExpression, path.getSegment());
        path = path.next();
    }
    return sortPropertyExpression;
} catch (PropertyReferenceException e) {
    if (order instanceof JpaSort.JpaOrder jpaOrder && jpaOrder.isUnsafe()) {
        return Expressions.template(Object.class, order.getProperty());
    } else {
        throw e;
    }
}

    규칙은 두 가지로 요약된다. 첫째, 정렬 문자열은 PropertyPath.from(문자열, 도메인 타입)으로 엔티티의 속성에 대해 검증된다. 둘째, 검증된 경로는 builder, 즉 생성 시점에 만든 PathBuilder를 뿌리로 이어 붙인 Querydsl 경로가 된다. QuerydslRepositorySupport의 PathBuilder는 PathBuilderFactory.create(Employee.class)가 만들고, Querydsl 5.1.0 소스에서 그 변수 이름은 단순 클래스 이름의 첫 글자를 소문자로 바꾼 employee다. QuerydslPredicateExecutor의 PathBuilder는 Q 클래스의 정적 필드 메타데이터를 쓰므로 역시 employee다. 이 두 규칙에서 세 가지 결과가 나온다. 실험으로 확인했다.

    첫 번째는 잘 동작한 경우다. 헬퍼가 만든 정렬 경로는 employee.department.name인데 JPQL에는 department.name이 찍혔다. 앞 절에서 본 JPAQueryMixin이 order by 경로를 줄일 때, leftJoin(employee.department, department)가 등록해 둔 별칭 맵에서 employee.department의 별칭 department를 찾아 재사용했기 때문이다. 그래서 조인이 하나만 생겼고, 명시적 외부 조인 덕분에 부서 없는 choi도 남았다(null이 정렬에서 어디에 놓이는지는 DB마다 다르며, 이 H2 실행에서는 맨 앞이었다).

    두 번째는 DTO 필드 이름으로 정렬하려는 경우다. 화면은 deptName으로 정렬해 달라고 하지만, 헬퍼는 그 이름을 Employee의 속성으로 해석하려 하고 그런 속성은 없다. select 절의 별칭이나 DTO의 필드는 헬퍼가 알 방법이 없다. JpaSort.unsafe(...)로 만든 정렬은 속성 검증에 실패해도 문자열을 그대로 템플릿으로 JPQL에 넣는데, 이름 그대로 검증 없이 쿼리 문자열에 들어가므로 사용자 입력을 그 경로로 흘려서는 안 된다.

    세 번째가 가장 헷갈리는 경우다. 쿼리를 별칭 e로 만들었는데 헬퍼는 여전히 employee를 뿌리로 정렬 경로를 만든다. JPQL의 FROM 절에는 employee라는 식별 변수가 없으므로 Hibernate가 경로를 해석하지 못한다. 셀프 조인이나 서브쿼리 때문에 기본 별칭이 아닌 Q 인스턴스를 쓰는 순간, 바깥에서 받은 Sort는 깨진다. 컴파일러도, 기동 시 검증도 이것을 잡지 못하고 그 정렬이 처음 요청될 때 드러난다.

    Sort 문자열 "age"가 PathBuilder의 뿌리 이름 employee에 붙어 employee.age가 되고, FROM 절의 별칭이 employee면 맞고 e면 어긋나는 대비. 왼쪽에 "Sort.by('age')"라고 적힌 카드. 카드에서 오른쪽 상자 "PathBuilder (뿌리: employee)"로 화살표가 가고, 상자 출구에서 "employee.age"라는 결과 카드가 나온다. 이 결과 카드에서 오른쪽으로 두 갈래 화살표가 나뉜다. 위 갈래는 "from Employee employee"라고 적힌 쿼리 상자에 꽂히며 초록 체크 표시와 "일치"라는 라벨. 아래 갈래는 "from Employee e"라고 적힌 쿼리 상자에 닿지만 빨간 X 표시와 "해석 실패"라는 라벨. 그림 아래쪽에 별도의 작은 카드 "Sort.by('deptName')"가 "PathBuilder" 상자 입구에서 튕겨 나오고 "엔티티에 없는 속성"이라는 라벨이 붙어 있다. 깔끔한 평면 도해, 흰 배경. 헬퍼는 Sort 문자열을 엔티티 속성으로 검증한 뒤 기본 별칭(employee)을 뿌리로 경로를 만든다. 쿼리가 다른 별칭을 쓰면 정렬이 어긋난다.

    해결책은 세 갈래다. 정렬을 받는 쿼리에서는 Q 타입의 기본 인스턴스를 쓴다. 내부 코드에서 정렬을 만든다면 Sort 대신 QSort(또는 QPageRequest)에 OrderSpecifier를 담아 넘긴다. 헬퍼가 QSort를 만나면 문자열 변환을 건너뛰므로 별칭 문제도, DTO 필드 문제도 없다. 외부에서 문자열로 정렬 키가 들어온다면 허용할 키와 OrderSpecifier를 짝지은 맵을 두고 직접 바꾼다. 이 마지막 방법은 노출 범위를 통제한다는 점에서 앞 절의 허용 목록과 같은 생각이다.

    QuerydslRepositorySupport에는 구조적인 아쉬움도 있다. 쿼리를 from(...)으로 시작해야 해서 JPAQueryFactory의 select(...).from(...) 순서와 반대로 읽힌다. JPAQueryFactory를 갖고 있지 않으므로 selectFrom 같은 시작 메서드를 쓸 수 없다. 페이징의 count 처리는 각 메서드가 스스로 해야 하는데, 가장 손쉬운 길이 폐기 예정인 fetchCount()다. 이 아쉬움들을 메우는 기반 클래스를 직접 만들어 보자.

    Querydsl 지원 클래스 직접 만들기

    설계 목표를 먼저 정한다. 남길 것은 Querydsl 헬퍼다. Pageable을 offset·limit·정렬로 옮기는 일을 다시 짜지 않으려는 것이다. 더할 것은 세 가지다. 쿼리를 select나 selectFrom으로 시작할 수 있게 JPAQueryFactory를 들고 있는다. 내용 쿼리와 count 쿼리를 따로 받아서 count 쿼리를 가볍게 쓸 수 있게 한다. count 쿼리의 실행은 PageableExecutionUtils에 맡겨 필요할 때만 일어나게 한다. 생명 주기는 QuerydslRepositorySupport와 같은 방식(세터 주입 + @PostConstruct 검증)을 따른다.

    public abstract class JpaQuerySupport {

    private final Class domainClass;
    private EntityManager entityManager;
    private Querydsl querydsl;
    private JPAQueryFactory queryFactory;

    protected JpaQuerySupport(Class domainClass) {
        Assert.notNull(domainClass, "domainClass must not be null");
        this.domainClass = domainClass;
    }

    @Autowired
    public void setEntityManager(EntityManager entityManager) {
        Assert.notNull(entityManager, "EntityManager must not be null");
        PathBuilder builder = new PathBuilderFactory().create(domainClass);
        this.entityManager = entityManager;
        this.querydsl = new Querydsl(entityManager, builder);
        this.queryFactory = new JPAQueryFactory(entityManager);
    }

    @PostConstruct
    public void validate() {
        Assert.notNull(entityManager, "EntityManager must not be null");
        Assert.notNull(querydsl, "Querydsl must not be null");
        Assert.notNull(queryFactory, "JPAQueryFactory must not be null");
    }

    protected EntityManager getEntityManager() { return entityManager; }
    protected JPAQueryFactory getQueryFactory() { return queryFactory; }

    protected  JPAQuery select(Expression expr) {
        return queryFactory.select(expr);
    }

    protected  JPAQuery selectFrom(EntityPath from) {
        return queryFactory.selectFrom(from);
    }

    protected  Page applyPagination(Pageable pageable,
                                          Function> contentQuery,
                                          Function> countQuery) {
        JPAQuery query = contentQuery.apply(queryFactory);
        List content = querydsl.applyPagination(pageable, query).fetch();
        JPAQuery count = countQuery.apply(queryFactory);
        return PageableExecutionUtils.getPage(content, pageable, count::fetchOne);
    }
}

    applyPagination이 함수 두 개를 받는 이유를 짚어 보자. 쿼리를 만드는 시점과 실행하는 시점을 기반 클래스가 쥐기 위해서다. 내용 쿼리는 만들자마자 헬퍼로 페이징과 정렬을 입히고 실행한다. count 쿼리는 객체만 만든다. Querydsl 쿼리 객체를 만드는 것은 메모리에서 메타데이터를 쌓는 일일 뿐 DB에 아무것도 보내지 않는다. 실행은 count::fetchOne이라는 LongSupplier로 감싸 PageableExecutionUtils에 넘기므로, 앞에서 본 규칙 1~3에 해당하면 count SQL은 끝내 나가지 않는다. fetchOne()은 Long을 반환하고 LongSupplier의 getAsLong()으로 쓰일 때 언박싱되는데, 집계 함수 count는 행이 없어도 0을 담은 한 행을 돌려주므로 null이 될 일은 없다. 이 클래스를 상속한 리포지토리는 이렇게 쓴다.

    @Repository
public class EmployeeQueryRepository extends JpaQuerySupport {

    public EmployeeQueryRepository() {
        super(Employee.class);
    }

    public Page search(String deptName, Integer minAge, Pageable pageable) {
        return applyPagination(pageable,
                qf -> qf.select(Projections.constructor(EmployeeRow.class,
                                employee.name, employee.age, department.name))
                        .from(employee)
                        .leftJoin(employee.department, department)
                        .where(deptNameEq(deptName), ageGoe(minAge)),
                qf -> qf.select(employee.count())
                        .from(employee)
                        .leftJoin(employee.department, department)
                        .where(deptNameEq(deptName), ageGoe(minAge)));
    }

    private BooleanExpression deptNameEq(String deptName) {
        return deptName == null ? null : department.name.eq(deptName);
    }

    private BooleanExpression ageGoe(Integer minAge) {
        return minAge == null ? null : employee.age.goe(minAge);
    }
}

    동시성도 확인하자. EmployeeQueryRepository는 싱글톤 빈이다. 필드 넷은 빈 초기화 단계에서 한 번 쓰이고 그 뒤로는 읽기만 한다. EntityManager는 스레드마다 다른 영속성 컨텍스트로 위임하는 공유 프록시이고, JPAQueryFactory와 Querydsl 헬퍼는 호출마다 새 쿼리 객체를 만들어 줄 뿐 요청별 상태를 담지 않는다. 쿼리 객체(JPAQuery)는 조건을 쌓아 가는 가변 객체지만 메서드 안에서 만들어지고 버려지므로 스레드 사이에 공유되지 않는다. 05회에서 JPAQueryFactory는 공유하고 JPAQuery는 공유하지 말라고 한 원칙이 기반 클래스의 구조로 굳어진 것이다.

    이 지원 클래스가 해결하지 못한 것도 분명히 해 두자. 정렬은 여전히 Querydsl 헬퍼가 처리하므로 앞 절의 규칙이 그대로 적용된다. 내용 쿼리는 기본 별칭 employee를 써야 하고, DTO 필드 이름으로는 정렬할 수 없다. 화면의 정렬 키를 받아야 한다면 정렬 키와 OrderSpecifier를 짝지은 맵으로 바꾸는 메서드를 기반 클래스에 하나 더 두는 것이 다음 단계다. 또 내용 쿼리와 count 쿼리의 조건을 두 번 적어야 하므로, 둘의 조건이 어긋나지 않게 조건 메서드(deptNameEq, ageGoe)를 공유하는 습관이 중요하다.

    일상에서 가져온 비유주문서 양식과 자유 메모

    QuerydslPredicateExecutor와 Web 지원은 칸이 정해진 주문서 양식과 같다. 칸에 값만 채우면 주방이 알아서 만들지만, 양식에 없는 요청("소스는 따로")은 적을 곳이 없고, 칸 이름을 잘못 읽은 주문은 그냥 무시된 채 기본 메뉴가 나온다. 직접 만든 지원 클래스는 주방장에게 자유 메모를 넘기되, 계산(페이징)과 영수증 양식(Page)만 표준으로 맞춘 것이다. 비유가 깨지는 지점도 있다. 실제 주방은 무시한 주문을 다시 묻기라도 하지만, Querydsl Web 지원은 아무 신호 없이 전체 목록을 돌려준다.

    네 도구를 고르는 기준과 다른 주제와의 연결

    도구얻는 것내주는 것어울리는 곳
    QuerydslPredicateExecutor구현 없이 Predicate 조회·count·exists·페이징조인 선택(내부/외부, 페치), 서비스 계층의 Querydsl 독립성단일 엔티티의 단순 조건 조회, 테스트 코드

    이 회차의 지식은 여러 곳과 이어진다. 리포지토리 프록시의 조각 구성은 스프링 데이터 JPA 권에서 본 프록시 생성의 연장이고, 그 안의 CrudMethodMetadata 프록시는 05회의 공유 EntityManager와 같은 "스레드에 묶인 대상으로 위임하는 프록시" 패턴이다. 인자 리졸버와 ConversionService는 스프링 MVC 권의 요청 매핑 구조 위에서 돌아가고, 변환 실패가 500이 되는 이유는 그 구조에서 어떤 예외를 누가 처리하는지로 설명된다. 암묵적 조인이 행을 지우는 현상은 SQL의 실행 순서(FROM·JOIN 다음 WHERE)라는 데이터베이스의 기본에서 나오고, lower()를 씌운 like가 인덱스를 못 타는 것은 B+Tree의 정렬 구조에서 나온다. 06회에서 다룬 count 쿼리 분리는 이 회차의 지원 클래스에서 Function 두 개로 정형화되었다.
    QuerydslPredicateExecutor
    리포지토리 인터페이스가 상속하면 Predicate를 받는 findOne·findAll·count·exists·findBy가 생긴다. 구현은 리포지토리 프록시의 조각 구성에 끼워 넣어진 QuerydslJpaPredicateExecutor가 맡는다.
    조각 구성(RepositoryComposition)
    사용자 정의 구현 → 모듈 조각(Querydsl) → SimpleJpaRepository 순으로 쌓이고, 호출된 메서드는 앞에서부터 시그니처가 맞는 첫 조각이 실행한다. 그래서 Impl 클래스로 Querydsl 메서드를 덮어쓸 수 있다.
    고정된 쿼리 틀
    Querydsl 조각의 JPQL은 언제나 select 엔티티 from 엔티티 where Predicate다. 조인은 명시할 수 없고, where의 연관 경로는 Hibernate의 암묵적 내부 조인, order by에만 쓰인 경로는 Querydsl이 붙인 left join이 된다.
    지연 count
    PageableExecutionUtils.getPage는 첫 페이지가 덜 찼거나, 마지막 페이지가 덜 찼으되 비어 있지 않으면 count를 실행하지 않고 전체 개수를 계산한다.
    Querydsl Web 지원
    @EnableSpringDataWebSupport(Boot 자동 구성)가 Querydsl이 있으면 QuerydslWebConfiguration을 등록하고, 인자 리졸버가 파라미터마다 경로 해석·타입 변환·바인딩을 거쳐 AND로 결합된 Predicate를 만든다.
    조용한 무시
    해석할 수 없는 파라미터 이름과 빈 값은 오류 없이 건너뛰므로, 오타나 필드 이름 변경이 전체 조회로 이어질 수 있다. 반면 타입 변환 실패는 ConversionFailedException으로 올라가 500이 된다.
    QuerydslBindings 가시성
    허용 목록이 있으면 목록의 경로만, 없으면 거부 목록에 없는 모든 경로가 검색 조건이 된다. 별칭을 붙이면 원래 경로는 거부 목록에 들어가지만, 허용 목록에 원래 경로가 있으면 그 경로는 계속 보인다.
    Sort 경로 변환
    Querydsl 헬퍼는 Sort 문자열을 엔티티 속성으로 검증하고 기본 별칭(employee)을 뿌리로 경로를 만든다. DTO 필드 이름이나 다른 별칭과는 맞지 않으며, QSort는 이 변환을 건너뛴다.
    직접 만든 지원 클래스
    JPAQueryFactory로 쿼리를 시작하고, Querydsl 헬퍼로 Pageable을 적용하고, count 쿼리는 LongSupplier로 넘겨 필요할 때만 실행한다.

    장애 분석에서 이 회차의 지식이 가장 자주 쓰이는 곳은 "조건을 바꾸지 않았는데 결과가 갑자기 많아졌다"는 신고다. Querydsl Web 지원을 쓰는 API라면 먼저 요청 파라미터 이름과 엔티티 필드 이름이 지금도 일치하는지 본다. 엔티티 필드를 리팩터링한 배포 직후라면 거의 확실하다. 로그에 찍힌 SQL에 where 절이 없는지 확인하면 바로 판정된다. 반대로 "OR 조건인데 결과가 적다"는 신고라면 Predicate 안의 연관 경로가 만든 내부 조인을 의심한다. SQL에 join이 있는데 null 허용 외래 키라면 그것이 원인이다.

    설계 결정에서는 누가 Predicate를 만드는지가 판단의 축이다. 리포지토리 바깥(서비스, 컨트롤러, HTTP 클라이언트)이 Predicate를 만들게 하는 QuerydslPredicateExecutor와 Web 지원은 개발 속도를 주는 대신 조인 제어와 계약의 안정성을 내준다. 엔티티 하나에 단순 조건만 붙는 내부 도구라면 이 거래가 이득이고, 조인이 결과를 좌우하거나 외부에 공개되는 API라면 검색 조건 DTO를 받아 리포지토리 안에서 쿼리를 조립하는 쪽이 낫다. 그 경우에도 Web 지원을 쓰고 싶다면 허용 목록과 별칭으로 노출 범위를 먼저 닫는다.

    성능 판단에서는 count 쿼리의 실행 조건을 아는 것이 중요하다. 목록 API의 응답 시간이 페이지 번호에 따라 들쭉날쭉하다면, 덜 찬 첫 페이지에서는 count가 생략되고 꽉 찬 페이지에서는 실행되기 때문일 수 있다. 큰 테이블의 count가 병목이라면 조인과 정렬을 뺀 count 전용 쿼리를 따로 쓰는 지원 클래스 구조가 효과적이고, 그래도 느리면 전체 개수를 보여 주지 않는 화면 설계(Slice, 무한 스크롤)로 문제 자체를 바꾸는 판단이 필요하다.

Querydsl이 OR 조건을 AND로 바꿔 직렬화했다. where 절의 연관 경로가 Hibernate의 암묵적 조인, 즉 내부 조인이 되어 부서가 없는 행이 WHERE 평가 전에 사라졌다. Querydsl이 order by용으로 left join을 추가하면서 조건이 바뀌었다. null과 비교하는 조건은 항상 거짓이므로 OR 전체가 거짓이 되었다. JPQL은 where employee.department.name = ?1 or employee.age > ?2로 OR가 그대로였다. Hibernate는 암묵적 조인을 언제나 내부 조인으로 처리하고, SQL은 FROM·JOIN으로 행 집합을 만든 뒤 WHERE를 평가하므로 조인 상대가 없는 행은 두 번째 조건을 볼 기회가 없다. left join 추가는 order by에만 쓰인 경로에 대한 Querydsl의 동작이라 이 쿼리와 무관하고, SQL의 OR는 한쪽이 참이면 참이므로 네 번째 설명도 틀렸다. Querydsl Web 지원을 쓰는 API에 GET /employees?nmae=kim(오타)이 들어왔다. 무슨 일이 일어나는가? 스프링 MVC가 알 수 없는 파라미터로 400 응답을 보낸다. PropertyReferenceException이 올라가 500 응답이 된다. 그 파라미터는 경로 해석 단계에서 조용히 건너뛰어지고, 남은 조건이 없으므로 전체 조회가 실행된다. 결과가 없는 빈 목록이 돌아온다. QuerydslBindings.getPropertyPath는 PropertyReferenceException을 잡아 null을 반환하고, QuerydslPredicateBuilder는 그 파라미터를 continue로 건너뛴다. 예외를 잡아 null로 바꾸도록 작성된 동작이고, 그 덕분에 page, sort 같은 다른 파라미터와 공존할 수 있다. 조건이 하나도 없으면 빈 BooleanBuilder가 넘어가 where 절 없는 SQL이 실행된다. 예외로 끝나는 것은 경로 해석이 아니라 타입 변환에 실패한 경우다. QuerydslRepositorySupport를 상속한 구현에서 new QEmployee("e")로 쿼리를 만들고 getQuerydsl().applyPagination(PageRequest.of(0, 10, Sort.by("age")), query)를 실행하자 Hibernate가 'employee.age' 경로를 해석하지 못했다. 이유는? 헬퍼는 Sort 문자열을 생성자에서 만든 PathBuilder(변수 이름 employee)를 뿌리로 경로로 바꾸므로, FROM 절의 별칭 e와 맞지 않는다. age가 int라서 Sort가 지원하지 않는 타입이다. Sort는 DTO 프로젝션과 함께 쓸 수 없다. Hibernate 6은 order by 절에서 경로 표현식을 허용하지 않는다. buildOrderPropertyPathFrom은 PropertyPath를 builder(=PathBuilderFactory가 만든 employee 변수)에 이어 붙여 employee.age를 만든다. 쿼리가 다른 별칭을 쓰면 JPQL에 존재하지 않는 식별 변수를 참조하게 된다. 같은 쿼리를 기본 별칭으로 만들면 DTO 프로젝션이 있어도 age 정렬은 정상 동작했으므로 나머지 보기는 틀렸다. PageableExecutionUtils.getPage로 페이지를 만든다. 조건에 맞는 행이 7개일 때 PageRequest.of(1, 5) 요청에서 일어나는 일은? 페이지가 꽉 차지 않았으므로 count를 실행해 정확한 개수를 구한다. 첫 페이지가 아니므로 항상 count를 실행한다. 내용이 2개이므로 total을 2로 정한다. count를 실행하지 않고 offset 5에 내용 크기 2를 더해 total을 7로 정한다. 내용이 페이지 크기 5보다 작은 부분 페이지이고, 첫 페이지는 아니지만 비어 있지 않으므로 이 페이지가 마지막 페이지임이 확실하다. 그래서 offset + content.size() = 5 + 2 = 7을 전체 개수로 쓴다. count는 페이지가 꽉 찼거나, 첫 페이지가 아닌데 비어 있을 때만 실행된다. 리포지토리 인터페이스에 QuerydslPredicateExecutor만 상속했는데 findAll(Predicate)가 동작하는 이유로 옳은 것은? 스프링 데이터가 기동 시 바이트코드를 생성해 SimpleJpaRepository에 메서드를 추가한다. SimpleJpaRepository가 QuerydslPredicateExecutor를 구현하고 있다. JpaRepositoryFactory가 Querydsl이 클래스패스에 있고 인터페이스가 그 타입을 상속하면 QuerydslJpaPredicateExecutor 조각을 구성에 넣고, 프록시의 마지막 인터셉터가 호출을 그 조각으로 보낸다. QueryExecutorMethodInterceptor가 메서드 이름 findAll을 파싱해 쿼리를 만든다. getRepositoryFragments의 판정(QUERY_DSL_PRESENT와 isAssignableFrom)이 참이면 조각이 추가되고, ImplementationMethodExecutionInterceptor가 조각 구성에서 시그니처가 맞는 첫 조각을 찾아 실행한다. SimpleJpaRepository는 이 인터페이스를 구현하지 않으며, 쿼리 메서드 인터셉터는 이름 기반 메서드와 @Query만 다룬다. 바이트코드 생성으로 클래스에 메서드를 추가하는 것이 아니라 JDK 동적 프록시의 위임 구조다.
    리포지토리 조각(repository fragment)
    리포지토리 프록시가 메서드 호출을 위임하는 구현 단위. 사용자 정의 구현, 모듈이 추가한 구현(Querydsl 등), 기본 구현이 순서대로 RepositoryComposition을 이룬다.
    암묵적 조인(implicit join)
    employee.department.name처럼 경로 표현식으로 연관을 따라가 생기는 조인. Hibernate 6.6 가이드에 따르면 언제나 내부 조인으로 취급된다.
    EntityPathResolver
    도메인 클래스에 대응하는 Querydsl EntityPath(Q 타입 인스턴스)를 찾는 전략. 기본 구현 SimpleEntityPathResolver는 Q 클래스를 이름으로 로딩해 같은 타입의 정적 필드를 읽는다.
    HandlerMethodArgumentResolver
    스프링 MVC가 핸들러 메서드의 파라미터 값을 만들 때 쓰는 전략 인터페이스. QuerydslPredicateArgumentResolver가 Predicate 파라미터를 맡는다.
    QuerydslBindings
    요청 파라미터를 어떤 경로에 어떤 연산으로 묶을지와 경로의 노출 여부(허용·거부 목록, 별칭)를 담은 설정 객체. 요청마다 새로 만들어진다.
    PathBuilder
    문자열 속성 이름으로 Querydsl 경로를 동적으로 만드는 도구. PathBuilderFactory는 클래스 단순 이름의 첫 글자를 소문자로 바꾼 변수 이름을 쓴다.
    QSort
    Querydsl의 OrderSpecifier를 담는 Sort의 하위 클래스. Querydsl 헬퍼는 이를 문자열 변환 없이 그대로 order by에 넣는다.
    invokespecial / findSpecial
    동적 디스패치 없이 지정한 클래스·인터페이스의 구현을 그대로 호출하는 의미. MethodHandles.Lookup.findSpecial로 같은 의미의 메서드 핸들을 얻는다.
