    이 회차의 질문: 테스트 밖으로 나온 Querydsl

    앞 회차까지 Querydsl은 주로 테스트 메서드 안에서 쓰였다. 테스트 클래스가 EntityManager를 받아 JPAQueryFactory를 만들고, 쿼리를 하나 만들어 실행하고 결과를 확인했다. 실행하는 스레드는 테스트 스레드 하나였고, 트랜잭션도 테스트가 열고 닫았다. 이 회차는 같은 도구를 실제 애플리케이션 구조 안으로 옮긴다. 쿼리는 리포지토리 클래스 안에 들어가고, 리포지토리는 스프링 빈이 되며, 그 빈을 웹 요청을 처리하는 여러 스레드가 동시에 호출한다.

    이렇게 옮기는 순간 세 가지 질문이 생긴다. 첫째는 동시성이다. Jakarta Persistence 명세 7.2절은 엔티티 매니저를 동시에 실행되는 여러 스레드가 공유해서는 안 되며 한 스레드에서만 접근해야 한다고 적고 있다. 그런데 스프링 빈은 기본적으로 싱글톤이고, 우리는 그 싱글톤 리포지토리의 필드에 EntityManager를 넣고, 그것으로 만든 JPAQueryFactory도 필드에 넣는다. 명세를 어기는 것처럼 보이는 이 구성이 왜 안전한지 설명할 수 있어야 한다. 둘째는 동적 쿼리다. 화면의 검색 폼은 어떤 칸은 채우고 어떤 칸은 비운 채 요청을 보낸다. 비어 있는 조건을 빼고 쿼리를 조립하는 방법과, 그 방법이 내부에서 어떻게 동작하는지가 필요하다. 셋째는 성능이다. 목록 화면에 필요한 것은 엔티티 전체가 아니라 몇 개의 열이므로, 엔티티를 읽어 바꾸는 대신 처음부터 필요한 모양으로 조회하는 편이 낫다.

    순수 JPA 리포지토리에 Querydsl 더하기

    "순수 JPA 리포지토리"는 스프링 데이터 JPA의 인터페이스 기반 리포지토리를 쓰지 않고, 클래스를 직접 만들어 EntityManager로 저장과 조회를 구현한 리포지토리를 말한다. 여기에 Querydsl을 더하는 일은 어렵지 않다. 필드에 JPAQueryFactory를 하나 더 두면 된다. 먼저 엔티티부터 보자.

    @Entity
public class Department {
    @Id @GeneratedValue
    private Long id;
    private String name;

    protected Department() {}
    public Department(String name) { this.name = name; }
    public Long getId() { return id; }
    public String getName() { return name; }
}

@Entity
public class Employee {
    @Id @GeneratedValue
    private Long id;
    private String name;
    private int age;

    @ManyToOne(fetch = FetchType.LAZY)
    @JoinColumn(name = "department_id")
    private Department department;

    protected Employee() {}
    public Employee(String name, int age, Department department) {
        this.name = name; this.age = age; this.department = department;
    }
    // getter 생략
}

    리포지토리는 EntityManager와 JPAQueryFactory를 생성자로 받는다. 같은 조회를 JPQL 문자열과 Querydsl로 한 번씩 구현해 두었다.

    import static lab.QEmployee.employee;

@Repository
public class EmployeeJpaRepository {

    private final EntityManager em;
    private final JPAQueryFactory queryFactory;

    public EmployeeJpaRepository(EntityManager em, JPAQueryFactory queryFactory) {
        this.em = em;
        this.queryFactory = queryFactory;
    }

    public void save(Employee e) { em.persist(e); }

    public Optional findById(Long id) {
        return Optional.ofNullable(em.find(Employee.class, id));
    }

    public List findByName(String name) {          // JPQL 문자열
        return em.createQuery("select e from Employee e where e.name = :name", Employee.class)
                .setParameter("name", name)
                .getResultList();
    }

    public List findByNameQuerydsl(String name) {  // Querydsl
        return queryFactory.selectFrom(employee)
                .where(employee.name.eq(name))
                .fetch();
    }
}

    JPAQueryFactory는 애플리케이션 클래스(설정 클래스)에서 빈으로 등록했다. 빈 메서드의 매개변수로 EntityManager를 받으면 스프링이 그 자리에 무엇을 넣는지가 이 회차의 첫 번째 주제다.

    @SpringBootApplication
public class LabApplication {
    public static void main(String[] args) { SpringApplication.run(LabApplication.class, args); }

    @Bean
    JPAQueryFactory jpaQueryFactory(EntityManager em) {
        return new JPAQueryFactory(em);
    }
}

    두 조회 메서드를 같은 데이터로 실행하면 Hibernate가 내보내는 SQL은 글자 하나 다르지 않다. Querydsl은 결국 JPQL 문자열을 만들어 EntityManager.createQuery()에 넘기는 도구이기 때문이다.

    select e1_0.id,e1_0.age,e1_0.department_id,e1_0.name from employee e1_0 where e1_0.name=?
jpql -> 1
select e1_0.id,e1_0.age,e1_0.department_id,e1_0.name from employee e1_0 where e1_0.name=?
querydsl -> 1

    차이는 오류를 발견하는 시점에 있다. JPQL 문자열에서 e.name을 e.nmae로 잘못 쓰면 컴파일은 통과하고, 그 메서드가 처음 실행되어 Hibernate가 문자열을 해석할 때 예외가 난다. Querydsl에서 employee.nmae라고 쓰면 QEmployee에 그런 필드가 없으므로 javac가 컴파일을 거부한다. 이 차이는 이 권의 앞 회차에서 다뤘으니 여기서는 상기만 하고, 리포지토리 구조 자체로 넘어간다.

    팩토리를 어디서 만들지는 두 가지 방식이 흔하다. 위처럼 빈으로 등록해 주입받는 방식과, 리포지토리 생성자 안에서 this.queryFactory = new JPAQueryFactory(em)으로 직접 만드는 방식이다. 둘 다 결과적으로 같은 공유 프록시를 감싼 팩토리를 갖게 되므로 동작은 같다. 빈으로 등록하면 생성 방식(예를 들어 어떤 JPQLTemplates를 쓸지)을 한 곳에서 정할 수 있고, 생성자에서 만들면 리포지토리를 테스트할 때 EntityManager 하나만 준비하면 된다는 편리함이 있다. 어느 쪽이 안전한가의 문제는 아니다. 왜 둘 다 안전한지가 다음 절의 주제다.

    주입된 EntityManager의 정체

    리포지토리가 받은 EntityManager가 무엇인지 직접 들여다보자. 테스트에서 같은 타입을 주입받아 클래스, 호출 처리기(invocation handler), 구현 인터페이스, toString()을 출력하고, 컨텍스트에 등록된 EntityManager 타입 빈의 이름도 함께 찍었다. 리포지토리 내부 필드에 들어 있는 객체와도 비교했다.

    한 줄씩 읽어 보자. jdk.proxy3.$Proxy113은 java.lang.reflect.Proxy가 런타임에 만든 JDK 동적 프록시 클래스다. 번호는 그 JVM에서 프록시 클래스가 만들어진 순서에 따라 정해지므로 실행 환경마다 다르다. 이 프록시의 모든 메서드 호출은 SharedEntityManagerInvocationHandler.invoke()로 들어간다. 즉 우리가 받은 것은 진짜 엔티티 매니저가 아니라, 호출이 들어올 때마다 "지금 이 호출을 처리할 진짜 엔티티 매니저"를 찾아 넘겨주는 대리인이다. 스프링 프레임워크 레퍼런스의 JPA 장은 이것을 실제 트랜잭션용 EntityManager에 대한 "shared, thread-safe proxy"라고 부른다.

    구현 인터페이스가 jakarta.persistence.EntityManager가 아니라 org.hibernate.Session인 점도 눈여겨볼 만하다. Session은 EntityManager를 상속하므로 EntityManager 타입 자리에 그대로 들어간다. 스프링의 HibernateJpaVendorAdapter가 엔티티 매니저 인터페이스로 Session.class를 지정하고(소스 주석에 "as of Spring 5.3"이라고 적혀 있다), 공유 프록시는 그 인터페이스로 만들어진다. 두 번째 인터페이스 EntityManagerProxy는 스프링이 정의한 것으로, 프록시 뒤의 실제 대상을 꺼내는 getTargetEntityManager() 메서드를 제공한다. 아래 실험에서 이 메서드로 실제 대상을 확인한다.

    EntityManager 타입 빈이 두 개 등록된 것은 스프링 데이터 JPA의 작업이다. jpaSharedEM_entityManagerFactory는 JpaRepositoryConfigExtension이 리포지토리 내부용으로 등록하며 자동 주입 후보에서 빠지도록(setAutowireCandidate(false)) 설정된다. jpaSharedEM_AWC_entityManagerFactory는 EntityManagerBeanDefinitionRegistrarPostProcessor가 등록하는 빈으로, SharedEntityManagerCreator.createSharedEntityManager()를 팩토리 메서드로 쓰는 빈 정의다. 생성자나 빈 메서드 매개변수로 EntityManager를 받을 수 있는 것은 이 두 번째 빈 덕분이다. 스프링 프레임워크 레퍼런스도 @PersistenceContext 방식의 공유 EntityManager는 그대로는 타입 기반 의존성 주입 대상이 아니므로, @Autowired로 받으려면 SharedEntityManagerBean이나 SharedEntityManagerCreator를 쓰는 @Bean을 함께 정의하라고 안내한다. 스프링 데이터 JPA가 그 정의를 대신 등록해 준 셈이다. 필드에 @PersistenceContext를 붙이는 전통적인 방식은 스프링 프레임워크의 PersistenceAnnotationBeanPostProcessor가 처리하는데, 이 역시 SharedEntityManagerCreator로 같은 종류의 공유 프록시를 만든다. 어느 경로로 받든 받는 것은 공유 프록시다.

    리포지토리 자신의 클래스가 EmployeeJpaRepository$$SpringCGLIB$$0로 찍힌 것도 같은 맥락이다. 스프링 부트는 PersistenceExceptionTranslationPostProcessor를 자동 구성하고, 이 후처리기는 @Repository가 붙은 빈을 프록시로 감싸 영속성 예외를 스프링의 DataAccessException 계층으로 바꾼다. 부트의 자동 구성은 spring.aop.proxy-target-class 속성(기본값 true)을 읽어 클래스 기반 프록시를 쓰도록 설정하므로 CGLIB 서브클래스가 만들어졌다. 그래서 리포지토리 필드를 리플렉션으로 읽으려면 AopTestUtils.getTargetObject()로 프록시 뒤의 원본을 꺼내야 했다. 원본 리포지토리의 em 필드와 테스트가 받은 em은 같은 객체(true)였다. 애플리케이션 전체에서 EntityManager를 주입받는 모든 빈이 프록시 객체 하나를 함께 쓰고 있다는 뜻이다.

    일상에서 가져온 비유대표 번호와 상담원

    회사의 대표 전화번호는 하나지만, 전화를 거는 사람마다 다른 상담원에게 연결된다. 번호(공유 프록시)는 모든 고객이 공유해도 문제가 없다. 대화 내용(영속성 컨텍스트)은 연결된 상담원(실제 SessionImpl)이 갖고 있고, 상담원은 한 번에 한 고객만 상대한다. 비유가 깨지는 지점도 있다. 진행 중인 트랜잭션이 없으면 이 프록시는 호출 하나마다 새 상담원을 붙였다가 바로 돌려보낸다. 같은 고객이 두 번 전화하면 두 번째 상담원은 첫 대화를 모른다. 트랜잭션 밖에서 조회한 엔티티가 곧바로 준영속 상태가 되는 이유가 이것이다.

    호출 하나가 실제 EntityManager를 찾아가는 길

    공유 프록시가 "지금의 진짜 엔티티 매니저"를 어떻게 찾는지 SharedEntityManagerInvocationHandler.invoke()의 소스(Spring Framework 6.2.19)를 따라가 보자. 메서드는 두 번의 분기로 나뉜다. 첫 분기에서는 대상 엔티티 매니저 없이 처리할 수 있는 메서드를 걸러낸다. equals는 프록시가 동일한지만 보고, hashCode와 toString은 처리기 자신의 값을 쓰며, getEntityManagerFactory, getCriteriaBuilder, getMetamodel은 팩토리에서 바로 꺼낸다. isOpen은 항상 true, close는 무시하고, getTransaction은 공유 엔티티 매니저에서 트랜잭션을 만들 수 없다는 IllegalStateException을 던진다. unwrap(타입)은 요청한 타입이 프록시 자신의 인스턴스이면 프록시를 그대로 돌려준다.

    나머지 메서드는 EntityManagerFactoryUtils.doGetTransactionalEntityManager()를 호출해 대상을 구한다. 이 메서드는 TransactionSynchronizationManager.getResource(emf)로 현재 스레드에 묶인 EntityManagerHolder가 있는지 본다. 있으면 그 안의 엔티티 매니저가 대상이다. 없고 트랜잭션 동기화도 활성화되어 있지 않으면 null을 돌려준다. 대상이 null인데 호출된 메서드가 persist, merge, remove, flush, refresh, joinTransaction 중 하나이면 트랜잭션이 반드시 필요한 연산이므로 TransactionRequiredException을 던진다. 그 밖의 메서드라면 팩토리에서 새 엔티티 매니저를 만들어 호출 하나를 처리하고 곧바로 닫는다. 레퍼런스가 설명하는 "트랜잭션이 없으면 연산마다 새 EntityManager"가 이 코드다.

    조회에는 예외가 하나 있다. createQuery()처럼 Query 객체를 돌려주는 메서드는 그 자리에서 엔티티 매니저를 닫으면 안 된다. 쿼리는 나중에 getResultList()로 실행되기 때문이다. 그래서 새로 만든 엔티티 매니저에서 Query가 나오면 처리기는 그것을 다시 JDK 프록시로 감싸 DeferredQueryInvocationHandler에 맡기고, 엔티티 매니저를 닫는 일을 미룬다. 이 처리기는 getResultList, getSingleResult, getSingleResultOrNull, getResultStream, executeUpdate, execute, Hibernate의 list와 scroll 같은 "쿼리를 끝내는 메서드"가 호출된 뒤에 엔티티 매니저를 닫는다.

    스레드에 엔티티 매니저를 묶어 두는 곳은 TransactionSynchronizationManager다. 이 클래스는 ThreadLocal> 타입의 정적 필드 resources를 갖고 있고, 그 이름은 "Transactional resources"다. 스레드마다 자기만의 맵이 있고, 그 맵에 EntityManagerFactory를 키로, EntityManagerHolder를 값으로 넣는다. 넣는 쪽은 JpaTransactionManager다. 트랜잭션을 시작할 때(doBegin) 스레드에 묶인 홀더가 없으면 새 엔티티 매니저를 만들어 bindResource(emf, holder)로 묶고, 트랜잭션이 끝나면 풀고 닫는다. 같은 맵에 JDBC 커넥션 홀더도 DataSource를 키로 묶이는데, 이것은 스프링 DB 1편에서 본 트랜잭션 동기화와 같은 구조다.

    두 스레드로 확인하기

    이제 원래 질문으로 돌아가자. 두 스레드가 동시에 같은 리포지토리, 같은 프록시, 같은 팩토리를 쓰면 실제로 어떤 엔티티 매니저가 쓰이는가. 스레드 두 개를 띄워 각자 트랜잭션을 열고, CyclicBarrier로 두 트랜잭션이 확실히 겹치도록 맞춘 다음, 같은 queryFactory로 쿼리를 실행했다.

    queryFactory.selectFrom(employee).fetch();        // 같은 팩토리로 쿼리 실행
    await(barrier);                                    // 두 스레드가 모두 조회를 마칠 때까지 대기
    return new Object[]{Thread.currentThread().getName(), session, em, queryFactory};
});

    두 스레드는 같은 프록시(same em proxy? true)와 같은 팩토리(same factory? true)를 썼지만, 쿼리를 실제로 실행한 세션은 서로 달랐다(same session? false). 각 트랜잭션이 자기 스레드의 맵에 자기 세션을 묶었고, 프록시는 호출이 들어온 스레드의 맵에서 대상을 찾았기 때문이다. 로그 줄의 순서와 해시 값은 스레드 스케줄링에 따라 실행마다 다르다. 결정적인 것은 "두 세션이 다르다"는 사실뿐이다.

    여기서 "싱글톤에 EntityManager를 넣으면 모든 요청이 영속성 컨텍스트 하나를 공유한다"는 흔한 오해가 풀린다. 공유되는 것은 상태가 없는 대리인이다. 프록시의 처리기가 가진 필드는 대상 팩토리, 속성 맵, 트랜잭션 동기화 여부, 클래스 로더처럼 생성 뒤에 바뀌지 않는 값들이고, 1차 캐시나 쓰기 지연 저장소 같은 영속성 컨텍스트의 상태는 하나도 없다. 상태는 스레드에 묶인 SessionImpl에만 있다. 반대로 이 보장이 성립하지 않는 경우도 분명히 알아 두어야 한다. 트랜잭션 안에서 다른 스레드를 만들어 그 스레드에서 같은 프록시를 호출하면, 새 스레드의 맵은 비어 있으므로 호출자의 영속성 컨텍스트를 이어받지 못한다. 그 스레드에서의 조회는 "연산마다 새 엔티티 매니저" 경로로 가고, persist는 TransactionRequiredException을 낸다. 스레드 로컬은 스레드를 넘어가지 않는다.

    하나의 공유 프록시를 두 스레드가 함께 쓰지만, 각 호출이 스레드 로컬 맵을 거쳐 서로 다른 SessionImpl로 가는 구조를 보여 준다. 가로로 넓은 기술 다이어그램. 위쪽 가운데에 "힙(공유)" 영역을 회색 테두리 박스로 그리고, 그 안에 "EmployeeJpaRepository (싱글톤)"와 "JPAQueryFactory (싱글톤)" 상자 두 개가 있으며 둘 다 화살표로 가운데 "공유 EntityManager 프록시" 상자를 가리킨다. 아래쪽 왼편에 "스레드 A" 세로 기둥, 오른편에 "스레드 B" 세로 기둥을 그린다. 각 기둥 안에 "ThreadLocal 맵" 상자가 있고, 그 안에 "emf → EntityManagerHolder" 항목과 그 아래 "SessionImpl A"(왼쪽), "SessionImpl B"(오른쪽) 상자가 있다. 공유 프록시에서 두 갈래 점선 화살표가 내려가 각 스레드의 "ThreadLocal 맵"으로 들어가고, 화살표 라벨은 "getResource(emf)". 각 SessionImpl 옆에 작은 원통 "1차 캐시"를 붙인다. 색은 공유 영역 파란색, 스레드 영역 주황색. 라벨은 모두 따옴표 안 문구 그대로. 프록시는 하나지만, 실제로 쿼리를 실행하는 세션은 스레드마다 다르다.

    JPAQueryFactory는 공유해도 되고 JPAQuery는 안 되는 이유

    공유 프록시가 안전하다는 것을 확인했으니, 그 프록시를 감싼 JPAQueryFactory를 보자. Querydsl 5.1.0의 소스에서 이 클래스가 가진 필드는 두 개뿐이다.

    public class JPAQueryFactory implements JPQLQueryFactory {

    @Nullable
    private final JPQLTemplates templates;
    private final Supplier entityManager;

    public JPAQueryFactory(final EntityManager entityManager) {
        this.entityManager = () -> entityManager;   // 받은 객체를 늘 그대로 돌려주는 Supplier
        this.templates = null;
    }

    public  JPAQuery selectFrom(EntityPath from) {
        return select(from).from(from);
    }

    public JPAQuery query() {
        if (templates != null) {
            return new JPAQuery(entityManager.get(), templates);
        } else {
            return new JPAQuery(entityManager.get());
        }
    }
    // select(), update(), delete(), insert() 생략
}

    두 필드는 모두 final이고, 생성자가 끝난 뒤 어떤 메서드도 이 값을 바꾸지 않는다. select, selectFrom, from은 모두 결국 query()를 부르고, query()는 호출될 때마다 new JPAQuery로 새 객체를 만든다. 실험에서도 queryFactory.query() != queryFactory.query()가 true였다. 즉 팩토리는 상태 없는 생성기이고, 여러 스레드가 동시에 불러도 각자 자기 쿼리 객체를 받는다. 한 가지 덧붙이면, 5.1.0의 jakarta 분류자 jar를 javap로 보면 생성자 매개변수가 java.util.function.Supplier다. 생성자에 Supplier를 넘기면 쿼리를 만들 때마다 그 공급자에게서 엔티티 매니저를 받아 오는데, 스프링 환경에서는 공유 프록시 자체가 이미 스레드별 위임을 하므로 엔티티 매니저를 받는 생성자로 충분하다.

    팩토리의 안전성은 전적으로 "그 안에 든 것이 공유 프록시"라는 데 기대고 있다는 점을 놓치면 안 된다. 싱글톤 빈 안에서 new JPAQueryFactory(emf.createEntityManager())처럼 팩토리에서 진짜 엔티티 매니저를 하나 직접 만들어 넣으면, 모든 스레드가 그 하나의 SessionImpl과 1차 캐시를 함께 쓰게 된다. 이것이야말로 명세 7.2절이 금지하는 구성이다. 겉모습은 같은 JPAQueryFactory여도 안에 든 것이 다르면 안전성도 다르다.

    반대로 JPAQuery는 상태 덩어리다. AbstractJPAQuery는 생성될 때 받은 엔티티 매니저, 쿼리 힌트 맵, 락 모드, 플러시 모드, 프로젝션을 필드로 갖고, 부모 클래스 JPAQueryBase는 템플릿과 JPAQueryMixin을, 그 믹스인은 DefaultQueryMetadata를 갖는다. 메타데이터에는 조인 목록, where 조건, group by와 having, 정렬, limit과 offset, 파라미터 값이 들어 있고 대부분 바뀌는 필드나 가변 컬렉션이다. where()를 부르면 DefaultQueryMetadata.addWhere()가 where = and(where, e)로 기존 조건에 새 조건을 AND로 덧붙인다. 그래서 같은 쿼리 객체를 두 번 쓰면 조건이 누적된다. 쿼리 객체를 필드에 담아 재사용한 경우를 흉내 낸 실험이다.

    JPAQuery base = queryFactory.selectFrom(employee);
base.where(employee.name.eq("a"));
System.out.println("1st: " + base);
base.where(employee.name.eq("b"));     // 두 번째 요청이 같은 객체를 다시 썼다고 하자
System.out.println("2nd: " + base);
    1st: select employee
from Employee employee
where employee.name = ?1
2nd: select employee

    JPAQuery.toString()은 현재 메타데이터를 JPQL로 직렬화한 문자열을 돌려주므로 디버깅할 때 쓸모가 있다. 두 번째 출력에는 첫 번째 조건이 그대로 남아 있다. 한 스레드에서 순서대로 재사용해도 이렇게 틀린 쿼리가 나오고, 두 스레드가 같은 쿼리 객체를 동시에 건드리면 동기화 없이 같은 필드를 읽고 쓰는 데이터 경쟁이 된다. 그러니 쿼리 객체는 메서드 안에서 만들고 그 메서드 안에서 실행하고 버리는 지역 객체로만 쓴다. 반면 QEmployee.employee 같은 Q 타입 인스턴스는 생성된 코드에서 public static final이고, 그 안의 경로 필드(name, age, department)도 모두 public final이다. 경로 객체는 만들어진 뒤 바뀌지 않으므로 정적 임포트해서 어디서든 공유한다.

    new JPAQuery(em)처럼 템플릿 없이 쿼리를 만들면 생성자가 JPAProvider.getTemplates(em)을 호출해 JPA 구현체에 맞는 JPQL 템플릿을 고른다. 이 메서드는 클래스패스에 있는 구현체별 클래스(Hibernate라면 org.hibernate.Session)에 대해 em.unwrap(그 클래스)를 부르고, 결과가 그 타입이면 해당 템플릿을 돌려준다. 공유 프록시는 Session을 구현하므로 unwrap(Session.class)는 첫 분기에서 프록시 자신을 돌려주고, 실제 엔티티 매니저는 만들어지지 않는다.     동적 쿼리 ① BooleanBuilder로 조건 쌓기

    검색 화면의 입력은 조건 객체 하나로 받는다. 이름, 부서 이름, 최소 나이, 최대 나이 네 칸이다. 나이를 int가 아니라 Integer로 둔 것은 "입력하지 않음"을 null로 표현하기 위해서다. 기본형 int는 0과 "없음"을 구분할 수 없다.

    public record EmployeeSearchCond(String name, String deptName, Integer ageGoe, Integer ageLoe) {}

    04회에서 본 BooleanBuilder로 조건을 쌓는 조회 메서드는 다음과 같다. select 절의 QEmployeeDeptDto는 뒤의 "성능 최적화 조회" 절에서 설명하므로, 지금은 where 절에만 집중하자.

    public List searchByBuilder(EmployeeSearchCond cond) {
    BooleanBuilder builder = new BooleanBuilder();
    if (StringUtils.hasText(cond.name())) {
        builder.and(employee.name.eq(cond.name()));
    }
    if (StringUtils.hasText(cond.deptName())) {
        builder.and(department.name.eq(cond.deptName()));
    }
    if (cond.ageGoe() != null) {
        builder.and(employee.age.goe(cond.ageGoe()));
    }
    if (cond.ageLoe() != null) {
        builder.and(employee.age.loe(cond.ageLoe()));
    }
    return queryFactory
            .select(new QEmployeeDeptDto(employee.id, employee.name, employee.age,
                    department.id, department.name))
            .from(employee)
            .leftJoin(employee.department, department)
            .where(builder)
            .fetch();
}

    문자열 조건에 != null 대신 스프링의 StringUtils.hasText()를 쓴 이유는 웹에서 오는 값의 모양 때문이다. 검색 폼의 빈 칸은 보통 null이 아니라 빈 문자열로 전송된다. hasText는 null, 빈 문자열, 공백만 있는 문자열에 대해 모두 false를 돌려주므로 세 경우를 한 번에 "조건 없음"으로 처리한다. 실험에서 이름에 "", 부서 이름에 " "를 넣은 조건은 where 절이 아예 없는 쿼리가 되었다.

    BooleanBuilder가 하는 일을 소스로 확인하자. 이 클래스는 Predicate를 구현하고, 안에 predicate 필드 하나를 갖는다. 처음에는 null이다. and(right)는 right가 null이면 아무것도 하지 않고, 지금까지 쌓인 것이 없으면 right를 그대로 저장하며, 이미 있으면 ExpressionUtils.and(기존, right)로 새 AND 노드를 만들어 필드를 교체한다. or()도 같은 구조다. Querydsl 레퍼런스도 이 클래스를 가변(mutable)이며 처음에는 null을, 이후에는 각 and·or 호출의 결과를 나타낸다고 설명한다. 즉 빌더는 조건 트리의 루트를 하나 들고 있다가 호출마다 루트를 더 큰 트리로 바꿔 끼우는 객체다.

    빌더를 where()에 넘기면 JPA용 JPAQueryMixin.convert()가 ExpressionUtils.extract()로 빌더 안의 값을 꺼낸다. 아무 조건도 쌓이지 않은 빌더에서는 null이 나오고, addWhere()는 null을 받으면 그냥 돌아간다. 그래서 빈 빌더를 넘겨도 예외가 나지 않고 where 절이 사라진다. 아래 출력의 두 번째가 그 경우다. 세 번째는 or를 두 번 한 뒤 and를 한 경우인데, 빌더가 왼쪽부터 트리를 키우므로 (a or b) and c가 되고, 직렬화기가 트리 구조에 맞춰 괄호를 넣는다. 조건을 쌓는 순서가 곧 괄호 구조라는 뜻이다.

    동적 쿼리 ② where 다중 파라미터

    같은 검색을 where 다중 파라미터 방식으로 쓰면 이렇게 된다. 조건 하나하나를 메서드로 빼고, 조건이 없으면 null을 돌려준다.

    public List search(EmployeeSearchCond cond) {
    return queryFactory
            .select(new QEmployeeDeptDto(employee.id, employee.name, employee.age,
                    department.id, department.name))
            .from(employee)
            .leftJoin(employee.department, department)
            .where(nameEq(cond.name()),
                   deptNameEq(cond.deptName()),
                   ageGoe(cond.ageGoe()),
                   ageLoe(cond.ageLoe()))
            .fetch();
}

private BooleanExpression nameEq(String name) {
    return StringUtils.hasText(name) ? employee.name.eq(name) : null;
}
private BooleanExpression deptNameEq(String deptName) {
    return StringUtils.hasText(deptName) ? department.name.eq(deptName) : null;
}
private BooleanExpression ageGoe(Integer ageGoe) {
    return ageGoe != null ? employee.age.goe(ageGoe) : null;
}
private BooleanExpression ageLoe(Integer ageLoe) {
    return ageLoe != null ? employee.age.loe(ageLoe) : null;
}

    null이 들어가도 괜찮은 이유는 QueryMixin.where(Predicate... o)에 있다. 이 메서드는 가변 인자 배열을 돌며 원소마다 metadata.addWhere(convert(e, Role.WHERE))를 부른다. convert는 null을 null 그대로 통과시키고, addWhere는 첫 줄에서 null이면 돌아간다. null이 아닌 조건만 기존 where에 AND로 붙는다. QueryBase.where(Predicate...)의 Javadoc에도 null 인자를 건너뛴다고 적혀 있고, Querydsl 레퍼런스는 where에 조건을 쉼표로 구분한 가변 인자로 주거나 and 연산자로 이어 줄 수 있다고 설명한다. 두 방식이 만든 JPQL을 출력해 보면 같은 문자열이다.

    whereParam JPQL:                     ← where(nameEq(null), deptNameEq("dev"), ageGoe(30), ageLoe(null))
select employee.name
from Employee employee
  left join employee.department as department
where department.name = ?1 and employee.age >= ?2

    앞 절 표의 네 조건으로 두 방식을 모두 실행해 결과 목록을 equals로 비교했더니 네 번 모두 true였고, 내보낸 SQL도 같았다. 결과가 같다면 무엇이 다른가. 차이는 코드의 모양과 재사용성에 있다. 빌더 방식에서는 쿼리 본문 위에 if 문이 늘어서고, 쿼리를 읽으려면 빌더가 무엇을 쌓았는지 위로 올라가 확인해야 한다. 다중 파라미터 방식에서는 쿼리 본문이 조건의 목록으로 읽히고, 각 조건은 이름 있는 메서드가 된다. 그 메서드들은 다른 쿼리에서도 그대로 쓸 수 있다. 예를 들어 06회에서 다룰 페이징의 count 쿼리는 내용 쿼리와 같은 where 조건을 가져야 하는데, 조건 메서드가 있으면 두 쿼리가 같은 메서드를 부르기만 하면 된다.

    조건 메서드 조합의 함정: 수신 객체가 null일 때

    조건 메서드가 BooleanExpression을 돌려주면 둘을 이어 더 큰 조건을 만들고 싶어진다. 나이 범위를 하나의 메서드로 묶어 보자.

    BooleanExpression ageBetween(Integer goe, Integer loe) {
    return ageGoe(goe).and(ageLoe(loe));
}
    between(30,40) = employee.age >= 30 && employee.age <= 40
NPE: Cannot invoke "com.querydsl.core.types.dsl.BooleanExpression.and(com.querydsl.core.types.Predicate)" because the return value of "lab.EmployeeJpaRepository.ageGoe(java.lang.Integer)" is null
between(30,null) = employee.age >= 30

    세 줄의 결과가 비대칭이다. 두 값이 다 있으면 정상이고, 최소 나이만 비면 NullPointerException이 나는데, 최대 나이만 비면 다시 정상이다. 이유는 두 층에 있다. 먼저 Querydsl 층이다. BooleanExpression.and(right)는 인자를 추출한 결과가 null이면 새 식을 만들지 않고 this를 돌려준다. 그래서 인자 자리의 null은 안전하다. 다음은 JVM 층이다. ageGoe(goe).and(...)는 바이트코드에서 ageGoe의 반환값을 수신 객체로 삼아 and를 가상 호출하는 invokevirtual 명령이 된다. JVM 명세의 invokevirtual 설명은 수신 객체 참조(objectref)가 null이면 NullPointerException을 던진다고 정한다. 인자는 null이어도 메서드 안에서 처리할 기회가 있지만, 수신 객체가 null이면 메서드에 들어가 보지도 못한다. 위 메시지는 JDK 21에서 실행했을 때 나온 것으로, 어느 메서드의 반환값이 null이었는지까지 알려 준다.

    고치는 방법은 수신 객체가 null이 될 수 없는 자리에서 조합하는 것이다. 두 가지가 흔하다. 하나는 ExpressionUtils.allOf(...)를 쓰는 것이다. 이 메서드는 인자를 돌며 null을 건너뛰고 나머지를 AND로 묶으며, 전부 null이면 null을 돌려준다. 그 null은 다시 where()가 건너뛴다. 다른 하나는 새 BooleanBuilder에 쌓아서 돌려주는 것이다. 빌더 자체는 null이 아니므로 호출하는 쪽에서 계속 and()를 이어 붙여도 안전하고, 비어 있으면 앞에서 본 대로 where 절에서 사라진다. 빌더는 가변 객체이므로 메서드를 부를 때마다 새로 만들어 돌려주고, 필드에 담아 공유하지 않는다.

    Predicate ageBetween(Integer goe, Integer loe) {            // 전부 null이면 null
    return ExpressionUtils.allOf(ageGoe(goe), ageLoe(loe));
}

BooleanBuilder ageRange(Integer goe, Integer loe) {         // 절대 null이 아니다
    return new BooleanBuilder().and(ageGoe(goe)).and(ageLoe(loe));
}
    조건 메서드가 null을 돌려주는 설계는 "where에 넘길 때만" 안전하다. 그 반환값에 메서드를 호출하는 순간 null은 다시 위험해진다. 조건 메서드를 조합용으로도 쓸 계획이라면 처음부터 빌더나 allOf 쪽으로 감싸 두는 편이 낫다.

    성능 최적화 조회: 엔티티 대신 DTO로 가져오기

    목록 화면에 필요한 것은 직원 ID, 이름, 나이, 부서 ID, 부서 이름 다섯 개 값이다. 이것을 얻는 방법은 세 가지가 있고, 각각이 내보내는 SQL이 다르다. 먼저 엔티티를 조회한 뒤 자바 코드로 DTO를 만드는 방법이다. 나이 30 이상 직원을 조회하고 각 직원의 부서 이름을 읽었다.

    select e1_0.id,e1_0.age,e1_0.department_id,e1_0.name from employee e1_0 where e1_0.age>=?
select d1_0.id,d1_0.name from department d1_0 where d1_0.id=?
select d1_0.id,d1_0.name from department d1_0 where d1_0.id=?
dtos = 4, managed = true

    직원 네 명(lee, park, choi, jung)을 읽은 뒤, 부서는 지연 로딩이므로 이름을 읽는 순간 부서 조회가 나갔다. 부서가 둘이므로 두 번이다. 같은 부서의 두 번째 직원은 영속성 컨텍스트에 이미 올라온 부서를 쓰므로 추가 쿼리가 없고, 부서가 없는 jung은 읽을 것이 없다. 이것이 JPA 활용 2편에서 본 N+1 문제의 축소판이다. 결과 엔티티는 영속 상태(managed = true)이므로 Hibernate는 변경 감지를 위해 읽은 시점의 상태를 따로 보관한다. 두 번째 방법은 페치 조인이다.

    select e1_0.id,e1_0.age,d1_0.id,d1_0.name,e1_0.name from employee e1_0 left join department d1_0 on d1_0.id=e1_0.department_id where e1_0.age>=?

    쿼리는 한 번으로 줄었지만 두 엔티티의 모든 열을 읽고, 결과는 여전히 영속 엔티티다. 이 예제의 엔티티는 열이 몇 개 안 되지만, 실제 테이블에 긴 텍스트나 많은 열이 있다면 화면에 쓰지 않을 데이터까지 네트워크와 메모리로 옮기게 된다. 세 번째가 DTO 프로젝션이다. 04회에서 본 @QueryProjection을 레코드의 생성자에 붙였다.

    위는 Querydsl이 만든 JPQL, 아래는 Hibernate가 내보낸 SQL이다. SELECT 목록에 정확히 다섯 열만 있다. JPQL에 select new ... 구문이 없다는 점을 눈여겨보자. Querydsl은 생성자 인자에 해당하는 경로를 평범한 SELECT 목록으로 직렬화하고, DTO는 자바 쪽에서 만든다. 애노테이션 프로세서가 만든 QEmployeeDeptDto는 ConstructorExpression를 상속하며, 이 객체가 생성될 때 대상 클래스에서 맞는 생성자를 찾아 Constructor 객체를 필드에 보관한다. 결과 행이 오면 행마다 newInstance(Object... args)가 그 Constructor로 리플렉션 생성자 호출을 한다. 결과 DTO는 엔티티가 아니므로 영속성 컨텍스트에 올라가지 않고, 변경 감지용 상태도 보관되지 않으며, 지연 로딩 프록시도 담기지 않는다.

    생성된 QEmployeeDeptDto의 생성자 매개변수는 Expression, Expression, Expression 같은 타입이다. 인자 개수나 타입이 DTO 생성자와 어긋나면 javac가 컴파일을 거부하므로, 실행해 봐야 알 수 있는 Projections.constructor(...) 방식보다 일찍 오류를 잡는다. 대가는 의존성이다. DTO 클래스가 com.querydsl.core.annotations.QueryProjection을 임포트하므로, 이 DTO를 컨트롤러가 그대로 응답으로 쓰면 웹 계층의 타입까지 Querydsl에 묶인다. 이 실험에서는 Querydsl 5.1.0이 레코드의 간결한 정식 생성자(compact canonical constructor)에 붙인 @QueryProjection도 처리해 주었다.

    left join과 where, 그리고 조건이 모두 비었을 때

    조회 쿼리가 부서와 inner join이 아니라 left join을 쓰는 이유는 부서가 없는 직원도 목록에 나와야 하기 때문이다. 실제로 나이 조건만 준 검색(30~40)의 결과에는 EmployeeDeptDto[employeeId=5, name=jung, age=33, deptId=null, deptName=null]이 들어 있었다. 부서 쪽 열이 null로 채워진 행이다. 그런데 부서 이름 조건을 함께 주면 jung은 사라진다. 조건 (null, "dev", 30, null)의 결과는 lee 하나였다.

    이것은 SQL이 조인과 WHERE를 처리하는 순서의 결과다. left join은 조인 단계에서 짝이 없는 왼쪽 행을 버리지 않고 오른쪽 열을 NULL로 채워 남긴다. 그다음 WHERE가 그 결과에 적용되는데, d1_0.name = 'dev'에서 d1_0.name이 NULL이면 비교 결과는 참도 거짓도 아닌 UNKNOWN이고, WHERE는 참인 행만 통과시킨다. 그래서 부서 열에 조건을 걸면 left join으로 살려 둔 행이 WHERE에서 걸러지고, 결과는 inner join과 같아진다. 동적 쿼리에서는 이 일이 조건 조합에 따라 일어났다 안 일어났다 한다는 점이 함정이다. "left join이니까 부서 없는 직원도 항상 나온다"는 기대는 부서 조건이 비어 있을 때만 맞다. 부서 조건이 있을 때도 부서 없는 직원을 남기고 싶다면, 그 요구가 무엇인지(조인 대상을 거르는 것인지, 결과 행을 거르는 것인지)를 먼저 정해야 한다. 조인 대상만 거르려면 03회에서 본 조인의 on 절에 조건을 넣고, 결과 행을 거르되 부서 없는 직원도 허용하려면 조건 메서드가 department.name.eq(x).or(department.id.isNull())을 돌려주게 한다.

    마지막으로 모든 조건이 비었을 때를 보자. 네 칸이 모두 비면 두 방식 모두 where 절 없는 SQL을 만들고 테이블 전체를 돌려준다. 실험 데이터는 다섯 명이지만 실제 테이블이 수백만 행이라면, 데이터베이스는 모든 행을 읽어 보내고, 애플리케이션은 그 행마다 DTO를 만들어 메모리에 리스트로 쥐고, 다시 그것을 JSON으로 직렬화한다. 검색 화면을 처음 열 때 아무 조건 없이 요청이 오는 것은 흔한 일이므로 이것은 드문 사고가 아니다. 막는 방법은 세 가지 층에서 생각할 수 있다. 입력 검증에서 조건이 하나도 없으면 거부하거나 기본 조건(예: 최근 한 달)을 채우는 방법, 쿼리에 limit()을 걸어 최대 행 수를 제한하는 방법(Querydsl의 limit은 createQuery()에서 setMaxResults로 전달된다), 그리고 06회에서 다룰 페이징이다. 어느 쪽이든 "조건이 비면 전부"라는 동적 쿼리의 기본 동작을 의식적으로 다뤄야 한다.

    OSIV는 요청 하나에서 EntityManager 개수를 바꾼다

    애플리케이션을 띄우면 스프링 부트는 이런 경고를 남긴다: "spring.jpa.open-in-view is enabled by default. Therefore, database queries may be performed during view rendering." 부트의 JpaBaseConfiguration은 spring.jpa.open-in-view 속성이 없으면 켜진 것으로 보고 OpenEntityManagerInViewInterceptor를 등록한다. 이 인터셉터는 요청이 컨트롤러에 들어가기 전에 엔티티 매니저를 만들어 TransactionSynchronizationManager.bindResource(emf, holder)로 요청 스레드에 묶고, 요청이 끝나면 풀고 닫는다. 앞에서 본 스레드 로컬 맵에 트랜잭션 관리자 대신 인터셉터가 홀더를 넣는 것이다.

OSIV를 끄면 묶인 것이 없으므로 쿼리마다 임시 엔티티 매니저가 하나씩, 모두 두 번 만들어지고 닫혔다. 켠 쪽의 n1=4는 앞의 컨트롤러 실험과 같은 네 명 데이터를 썼기 때문이고, 끈 쪽의 결과가 0건인 것은 그 컨텍스트가 데이터를 넣지 않은 별도의 메모리 DB를 썼기 때문이고, 확인하려던 것은 엔티티 매니저의 개수다. 리포지토리 코드는 한 글자도 바뀌지 않았는데 실행 경로가 달라졌다는 점이 핵심이다. 리포지토리는 "현재 스레드에 무엇이 묶여 있는가"를 모른 채 공유 프록시에 위임하고, 무엇이 묶여 있는지는 트랜잭션 관리자와 웹 인터셉터가 정한다.

    이 API는 DTO를 돌려주므로 응답을 만드는 동안 지연 로딩이 일어날 일이 없다. 즉 이 API만 보면 OSIV가 필요하지 않다. 그렇다고 OSIV를 끌지 말지를 이 API 하나로 정할 수는 없다. 엔티티를 응답까지 끌고 가는 다른 API가 있는지, 요청 처리 시간 동안 데이터베이스 자원을 붙잡아 두는 비용이 얼마인지는 JPA 활용 2편에서 다룬 판단이다. 조회 메서드에 @Transactional(readOnly = true)를 붙이면, OSIV가 켜진 상태에서는 JpaTransactionManager가 이미 스레드에 묶인 엔티티 매니저를 찾아 그것으로 트랜잭션을 진행하고, OSIV가 꺼진 상태에서는 트랜잭션마다 엔티티 매니저를 새로 연다.

    손으로 두드려 볼 데이터: 프로필과 @PostConstruct의 함정

    API를 브라우저나 HTTP 클라이언트로 직접 호출해 보려면 애플리케이션이 뜰 때 예제 데이터가 들어 있어야 한다. 그러나 그 데이터가 테스트에도 들어가면 테스트의 기대값이 흔들린다. 그래서 흔히 프로필을 나눈다. 메인 설정 파일에서 spring.profiles.active: local을 켜고 데이터를 넣는 빈에 @Profile("local")을 붙이며, 테스트 쪽 설정 파일에서는 다른 프로필을 켠다. 이때 두 설정 파일이 어떻게 읽히는지 정확히 알아 두어야 한다. 메인 src/main/resources/application.yml에만 lab.marker: from-main을 넣고, 테스트 src/test/resources/application.yml에는 넣지 않은 뒤 테스트에서 값을 읽었다.

    plain active = [test]
plain lab.marker = null
app yml urls = [file:.../build/resources/test/application.yml, file:.../build/resources/main/application.yml]

    클래스패스에는 두 파일이 모두 있고, 테스트 실행 시 클래스패스에서 테스트 리소스 디렉터리가 메인보다 앞에 있다. 스프링 부트의 StandardConfigDataLocationResolver는 패턴이 아닌 위치(classpath:/application.yml)를 리소스 하나로 해석하고, 클래스패스 리소스는 클래스로더가 먼저 찾은 파일 하나가 된다. 그래서 테스트에서는 메인 설정 파일이 덮어써지는 정도가 아니라 아예 읽히지 않는다. lab.marker가 null인 것이 그 증거다. 메인 파일에 둔 데이터소스나 JPA 설정에 테스트가 기대고 있었다면 테스트 쪽 파일에 같은 내용을 다시 적어야 한다.

    이제 데이터를 넣는 빈이다. 가장 먼저 떠오르는 코드는 초기화 메서드에 @PostConstruct와 @Transactional을 함께 붙이는 것이다. 실험을 위해 pc 프로필로 이 빈을 띄웠다.

    @Profile("pc")
@Component
public class SampleData {
    private final EntityManager em;
    private final Inserter inserter;
    // 생성자 생략

    @PostConstruct
    @Transactional
    public void init() {
        System.out.println("@PostConstruct this = " + getClass().getName());
        System.out.println("@PostConstruct txActive = " + TransactionSynchronizationManager.isActualTransactionActive());
        try {
            em.persist(new Department("from-postconstruct"));
        } catch (Exception e) {
            System.out.println("@PostConstruct persist -> " + e.getClass().getSimpleName());
        }
        inserter.insert();                        // 다른 빈의 @Transactional 메서드
    }

    @Profile("pc")
    @Component
    static class Inserter {
        private final EntityManager em;
        Inserter(EntityManager em) { this.em = em; }

        @Transactional
        public void insert() {
            System.out.println("Inserter txActive = " + TransactionSynchronizationManager.isActualTransactionActive());
            em.persist(new Department("from-inserter"));
        }
    }
}

    @PostConstruct 메서드 안의 this는 lab.SampleData, 즉 프록시가 아닌 원본 객체였고 트랜잭션은 없었다. 그래서 persist는 공유 프록시의 트랜잭션 필수 연산 검사에 걸려 TransactionRequiredException을 냈다. 그런데 테스트가 주입받은 최종 빈은 SampleData$$SpringCGLIB$$0, 트랜잭션 프록시다. 프록시는 분명 만들어졌지만 초기화 메서드는 그보다 먼저, 원본에 대해 호출된 것이다. 스프링 프레임워크 레퍼런스의 빈 생명주기 장은 초기화 콜백이 의존성 주입 직후 원본 빈 참조에 대해 호출되며, AOP 인터셉터는 아직 적용되지 않은 상태이고, 대상 빈이 완전히 만들어진 뒤에 프록시가 씌워진다고 설명한다. @Transactional은 프록시의 인터셉터가 처리하는 애노테이션이므로, 프록시를 거치지 않는 호출에서는 아무 효과가 없다. 스프링 DB 2편에서 본 트랜잭션 AOP의 "초기화 시점" 주의 사항과 "프록시 내부 호출" 문제가 모두 이 한 가지 사실에서 나온다.

    해결은 트랜잭션이 필요한 일을 프록시를 거치는 호출로 옮기는 것이다. 위 실험의 Inserter처럼 별도 빈의 @Transactional 메서드를 부르면, 그 빈은 이미 프록시로 완성되어 주입되었으므로 트랜잭션이 열린다(Inserter txActive = true). 레퍼런스는 같은 장에서, 초기화 메서드가 싱글톤 생성 잠금 안에서 실행되므로 무거운 초기화 후 작업은 SmartInitializingSingleton.afterSingletonsInstantiated()를 구현하거나 컨텍스트 갱신 이벤트(ContextRefreshedEvent)를 받아서 하라고 권한다. 이 시점에는 모든 싱글톤의 생성과 프록시 적용이 끝나 있으므로, 이벤트 리스너에서 다른 빈의 트랜잭션 메서드를 부르는 구성도 자연스럽다.

    빈 생성 과정에서 초기화 콜백이 원본 객체에 대해 실행되고, 그 뒤에야 트랜잭션 프록시가 씌워지는 순서를 보여 준다. 세로 생명선 네 개를 가진 시퀀스 다이어그램. 왼쪽부터 "스프링 컨테이너", "SampleData 원본", "트랜잭션 프록시", "공유 EntityManager 프록시". 위에서 아래로 메시지: 1) 컨테이너 → 원본 "생성자 호출·의존성 주입", 2) 컨테이너 → 원본 "@PostConstruct init()", 3) 원본 → 공유 EntityManager 프록시 "persist()" 이고 그 옆에 빨간 X 표시와 "TransactionRequiredException", 4) 그 다음에야 컨테이너 → 트랜잭션 프록시 "프록시 생성(초기화 후)" 이 나타나며 트랜잭션 프록시 생명선이 이 지점부터 시작한다. 맨 아래 주석 상자에 "초기화 콜백 시점에는 아직 프록시가 없다". 차분한 색, 빨간색은 예외 표시에만. 초기화 콜백은 프록시가 생기기 전에 원본에서 실행되므로 @Transactional이 적용되지 않는다.

    정리: 이 회차의 구조를 한 장으로

    이 회차에서 본 것들은 한 줄로 이어진다. 싱글톤 리포지토리에는 상태 없는 것만 공유된다. 공유 EntityManager 프록시, JPAQueryFactory, Q 타입 인스턴스가 그렇다. 상태를 가진 것은 모두 호출 단위나 스레드 단위로 만들어진다. JPAQuery와 BooleanBuilder는 메서드 호출 하나 동안 살고, SessionImpl은 트랜잭션이나 요청 하나 동안 스레드 로컬 맵에 묶여 산다. 그 맵에 무엇을 넣을지는 리포지토리가 아니라 트랜잭션 관리자와 OSIV 인터셉터가 정한다. 동적 쿼리의 null 처리는 Querydsl의 두 지점(BooleanBuilder.and()와 addWhere())이 맡고, 그 앞단에서 웹 바인딩이 null과 빈 문자열을 어떻게 만드는지가 조건 메서드의 설계를 결정한다.

    이 장의 핵심

    싱글톤에 넣은 EntityManager는 상태 없는 공유 프록시이고, 호출마다 현재 스레드의 스레드 로컬 맵에서 실제 SessionImpl을 찾아 위임한다. 그래서 그것을 감싼 JPAQueryFactory도 공유할 수 있지만, 가변 메타데이터를 가진 JPAQuery는 호출마다 새로 만든다. 동적 쿼리에서 null 조건은 BooleanBuilder.and()와 addWhere()가 버리지만, null인 식에 메서드를 호출하는 순간 JVM이 NullPointerException을 던진다. 목록 조회는 필요한 열만 DTO로 가져오고, 조건이 모두 빈 경우와 left join 뒤의 where 조건을 따로 점검한다.

    다음 06회에서는 같은 쿼리를 스프링 데이터 JPA 리포지토리 인터페이스에 붙인다. 인터페이스 기반 리포지토리에는 Querydsl 코드를 직접 넣을 수 없으므로 사용자 정의 리포지토리 조각으로 구현을 섞고, 이 회차에서 만든 조건 메서드를 내용 쿼리와 count 쿼리가 함께 쓰는 페이징으로 확장한다. 07회는 스프링 데이터가 직접 제공하는 Querydsl 연동 기능과 그 한계를 본다.
    공유 EntityManager 프록시
    SharedEntityManagerCreator가 만드는 JDK 동적 프록시. 스스로는 영속성 컨텍스트를 갖지 않고, 호출마다 현재 스레드에 묶인 실제 EntityManager를 찾아 위임하며, 없으면 연산마다 임시로 만들고 닫는다.
    트랜잭션 리소스 바인딩
    TransactionSynchronizationManager의 ThreadLocal 맵에 EntityManagerFactory를 키로 EntityManagerHolder를 넣는 일. JpaTransactionManager와 OSIV 인터셉터가 넣고 뺀다.
    JPAQueryFactory
    final 템플릿과 EntityManager 공급자만 가진 상태 없는 생성기. 호출마다 새 JPAQuery를 만든다. 공유 프록시를 감쌌을 때만 공유가 안전하다.
    JPAQuery
    조인, where, 정렬, 파라미터를 담은 가변 메타데이터를 가진 쿼리 객체. where()는 기존 조건에 AND로 누적되므로 재사용하거나 스레드 간에 공유하지 않는다.
    BooleanBuilder
    조건 트리의 루트를 하나 들고 있는 가변 Predicate. null 인자를 무시하고, 비어 있으면 where에서 사라지며, 쌓는 순서가 괄호 구조가 된다.
    where 다중 파라미터
    where(Predicate...)가 원소마다 addWhere()를 불러 null을 건너뛰고 나머지를 AND로 묶는 방식. 조건을 이름 있는 메서드로 나눠 재사용할 수 있다.
    DTO 프로젝션
    필요한 열만 SELECT하고 행마다 생성자를 리플렉션으로 호출해 DTO를 만드는 조회. 결과는 영속성 컨텍스트 밖에 있어 스냅샷과 지연 로딩이 없다.
    left join 뒤의 where
    조인 단계에서 살린 NULL 행도 오른쪽 열에 대한 where 비교에서 UNKNOWN이 되어 걸러진다. 결과는 inner join과 같아진다.
    초기화 콜백과 프록시
    @PostConstruct는 원본 빈에서 프록시 적용 전에 실행되므로, 같은 메서드의 @Transactional은 효과가 없다.

    운영 중에 "어떤 요청에서 엔티티 수정이 저장되지 않는다"거나 "목록 조회 후 연관 데이터를 읽다가 LazyInitializationException이 난다"는 보고를 받으면, 먼저 그 코드가 어느 스레드에서 무엇이 묶인 상태로 실행되었는지를 묻는다. 트랜잭션 밖이면 공유 프록시는 연산마다 임시 엔티티 매니저를 쓰므로 변경 감지가 일어날 영속성 컨텍스트가 없고, 조회 결과는 반환 즉시 준영속이다. OSIV가 켜져 있으면 같은 코드가 요청 범위의 엔티티 매니저를 쓰므로 증상이 사라진다. 그래서 "로컬 웹 요청에서는 되는데 배치 작업이나 메시지 리스너, 직접 만든 스레드에서는 안 된다"는 형태로 나타나는 일이 많다. 웹 요청 스레드에만 인터셉터가 홀더를 묶어 주기 때문이다.

    리포지토리 설계에서는 무엇을 필드로 두는지가 곧 동시성 설계다. JPAQueryFactory를 필드에 두는 것은 안전하지만, 공통 조건을 미리 걸어 둔 JPAQuery나 BooleanBuilder를 필드로 두면 조건이 누적되거나 스레드 간 경쟁이 생긴다. 공통 조건을 재사용하고 싶다면 상태가 아니라 메서드(조건 메서드, 쿼리를 새로 만들어 돌려주는 메서드)로 재사용한다. 테스트에서 이런 버그는 잘 드러나지 않는다. 테스트는 보통 한 스레드에서 메서드를 한 번씩만 부르기 때문이다.

    동적 검색 API는 조건이 하나도 없는 요청에 대한 정책을 반드시 갖는다. 데이터가 적은 개발 환경에서는 전체 조회가 빠르게 끝나서 문제가 보이지 않다가, 운영 데이터가 쌓인 뒤 검색 화면의 첫 진입이 느려지거나 메모리를 크게 쓰는 형태로 드러난다. 판단은 데이터 규모와 화면 요구에 따라 달라진다. 몇백 행짜리 코드 테이블이라면 전체 조회가 오히려 단순하고 옳다. 행 수가 계속 늘어나는 테이블이라면 기본 조건이나 최대 행 수, 페이징 중 하나는 있어야 한다. left join과 부서 조건처럼 조건 조합에 따라 결과 의미가 바뀌는 곳은 요구 사항 문장으로 먼저 확정하고 쿼리로 옮긴다.
  • OSIV를 끈 애플리케이션에서, @Transactional이 없는 서비스 메서드가 리포지토리의 search()를 세 번 부른다. 공유 프록시가 만들고 닫는 엔티티 매니저는 모두 몇 개인가? 같은 서비스 메서드에 @Transactional(readOnly = true)를 붙이면 어떻게 달라지는가? 근거를 SharedEntityManagerInvocationHandler의 분기로 설명하라.
  • 두 요청 스레드가 동시에 search()를 실행하는 순간의 메모리를 그려라. 힙에 있는 객체(리포지토리, 공유 프록시, 팩토리, 각 요청의 JPAQuery와 SessionImpl)와 각 스레드의 스레드 로컬 맵을 구분하고, 어느 객체가 몇 개 있는지 적어라. 트랜잭션 없이 OSIV만 켜져 있다고 가정한다.

    1. 세 개다. 서비스와 리포지토리 어디에도 트랜잭션이 없고 OSIV도 꺼져 있으므로 스레드 맵에 홀더가 없다. 각 search()는 createQuery()에서 공유 프록시를 거치는데, 대상이 null이므로 새 엔티티 매니저를 만들고, 결과 Query를 지연 닫기 프록시로 감싼 뒤 getResultList()가 끝나면 닫는다. 쿼리를 만드는 단계의 JPAProvider.getTemplates()는 unwrap(Session.class)가 프록시 자신을 돌려주므로 엔티티 매니저를 만들지 않는다. @Transactional(readOnly = true)를 붙이면 JpaTransactionManager가 트랜잭션 시작 때 하나를 만들어 스레드에 묶고, 세 번의 조회가 모두 그것을 쓰므로 하나가 된다(이것은 공유 프록시가 아니라 트랜잭션 관리자가 만든다).

    2. 힙에는 리포지토리 원본과 그 CGLIB 프록시가 각각 하나, 공유 EntityManager 프록시 하나, JPAQueryFactory 하나, Q 타입 정적 인스턴스가 있다. 요청마다 JPAQuery 하나와 그 메타데이터, OSIV가 만든 SessionImpl 하나가 있으므로 이것들은 두 개씩이다. 스레드마다 스레드 로컬 맵이 있고, 각 맵에는 emf → EntityManagerHolder(자기 SessionImpl)가 들어 있다. 트랜잭션이 없으므로 커넥션 홀더는 맵에 없다. 그림의 요점은 공유 객체에서 나가는 화살표가 스레드 맵을 거쳐 서로 다른 세션으로 갈라진다는 것이다.

    3. n이 null이거나 공백뿐이면 nameEq(n)이 null을 돌려주고, null을 수신 객체로 and를 호출하는 invokevirtual에서 NullPointerException이 난다. goe만 null인 경우는 BooleanExpression.and(null)이 this를 돌려주므로 실패하지 않는다. 고친 예: Predicate cond(String n, Integer goe) { return ExpressionUtils.allOf(nameEq(n), ageGoe(goe)); } 또는 BooleanBuilder cond(...) { return new BooleanBuilder().and(nameEq(n)).and(ageGoe(goe)); }. 앞의 것은 모두 비면 null을, 뒤의 것은 빈 빌더를 돌려주며 둘 다 where()에서 사라진다.

    4. nameEq와 ageGoe는 null이므로 where 절은 where d1_0.name=? and e1_0.age<=?이고, ops 부서이면서 40세 이하인 park 한 명이 나온다. choi는 42세라 빠지고, jung은 부서 열이 NULL이라 이름 비교가 UNKNOWN이 되어 빠진다. 요구를 반영하려면 deptNameEq가 department.name.eq(deptName).or(department.id.isNull())을 돌려주게 한다. 그러면 jung(33세)도 나이 조건을 통과하므로 결과는 park과 jung이 된다. 부서 이름 조건을 조인의 on으로 옮기는 방법도 있지만, 그러면 다른 부서 직원도 부서 열만 NULL인 채로 모두 나오므로 이 요구와는 다르다.

    5. 스프링 부트는 classpath:/application.yml을 리소스 하나로 해석하고, 테스트 클래스패스에서는 테스트 리소스 디렉터리가 앞에 있어 테스트 쪽 파일만 읽힌다. 메인 파일의 설정은 덮어써지는 것이 아니라 전혀 읽히지 않는다. 해결책은 테스트 쪽 파일에 필요한 설정을 모두 다시 적는 것, 또는 테스트 쪽 파일 이름을 application.yml이 아닌 프로필 전용 파일(예: application-test.yml)로 바꾸고 테스트에서 그 프로필을 활성화해 메인 파일 위에 차이만 얹는 것이다.

     두 요청 스레드가 같은 싱글톤 리포지토리의 search()를 동시에 실행한다. 각자 서비스 계층의 트랜잭션 안에 있다. 다음 중 옳은 것은? 두 스레드는 같은 SessionImpl을 쓰므로 1차 캐시가 공유되어 서로의 엔티티가 보인다. 두 스레드는 같은 공유 프록시를 거치지만, 프록시가 각 스레드의 스레드 로컬 맵에서 대상을 찾으므로 서로 다른 SessionImpl로 쿼리가 실행된다. 공유 프록시는 동기화(synchronized)로 호출을 직렬화하므로 두 쿼리는 차례로 실행된다. JPAQueryFactory가 스레드마다 복제되므로 안전하다. 공유 프록시의 처리기는 TransactionSynchronizationManager.getResource(emf)로 호출한 스레드의 홀더를 찾는다. 각 트랜잭션은 자기 스레드 맵에 자기 세션을 묶었으므로 대상이 다르다. 프록시는 상태가 없을 뿐 잠금으로 직렬화하지 않으며, 팩토리는 복제되지 않고 하나를 공유한다. 실험에서도 같은 프록시와 팩토리, 서로 다른 세션이 관찰되었다. 리포지토리 필드에 JPAQuery base = queryFactory.selectFrom(employee)를 두고, 메서드마다 base.where(employee.name.eq(name)).fetch()를 호출했다. 한 스레드에서 "a", "b" 순서로 호출하면 두 번째 호출의 JPQL은? where employee.name = ?1 (값은 "b") 예외가 난다. 한 번 실행한 쿼리는 다시 실행할 수 없다. where employee.name = ?1 and employee.name = ?2 where 절이 없다. fetch()가 끝나면 조건이 초기화된다. DefaultQueryMetadata.addWhere()는 where = and(where, e)로 기존 조건에 새 조건을 AND로 붙인다. 쿼리 객체는 가변이고 실행 뒤에도 조건이 남아 있으므로 두 조건이 함께 걸려 결과가 비게 된다. 실험의 toString() 출력이 이를 보여 준다. 그래서 JPAQuery는 메서드 안의 지역 객체로만 쓴다. ageGoe(Integer)와 ageLoe(Integer)는 값이 null이면 null을 돌려준다. 다음 중 NullPointerException이 나는 호출은? ageGoe(null).and(ageLoe(40)) ageGoe(30).and(ageLoe(null)) queryFactory.selectFrom(employee).where(ageGoe(null), ageLoe(null)).fetch() new BooleanBuilder().and(ageGoe(null)).and(ageLoe(40)) 첫 번째는 null을 수신 객체로 and를 호출하므로 JVM의 invokevirtual이 NullPointerException을 던진다. 두 번째는 인자가 null인 경우로, BooleanExpression.and()가 this를 돌려준다. 세 번째는 addWhere()가 null을 건너뛰어 where 없는 쿼리가 된다. 네 번째는 빌더가 null 인자를 무시한다. OSIV가 켜진(기본값) 스프링 부트 애플리케이션에서 트랜잭션 없는 컨트롤러가 리포지토리 조회를 두 번 호출했다. 공유 프록시의 "Creating new EntityManager for shared EntityManager invocation" 로그는 몇 번 찍히는가? 두 번. 트랜잭션이 없으면 연산마다 새로 만든다. 한 번. 첫 조회에서 만든 것을 두 번째 조회가 재사용한다. 네 번. 쿼리 생성과 실행에서 각각 하나씩 만든다. 0번. OSIV 인터셉터가 요청 시작 때 묶어 둔 엔티티 매니저를 두 조회가 모두 쓴다. OpenEntityManagerInViewInterceptor가 요청 스레드에 EntityManagerHolder를 묶으므로 doGetTransactionalEntityManager()가 그것을 찾아 돌려준다. 대상이 null이 아니므로 공유 프록시가 새로 만들 일이 없다. 실험에서 emBound=true, txActive=false였고 해당 로그가 없었다. OSIV를 끄면 조회마다 한 번씩, 두 번 찍혔다. @PostConstruct와 @Transactional을 함께 붙인 초기화 메서드에서 em.persist()가 TransactionRequiredException을 냈다. 가장 정확한 설명은? @PostConstruct 메서드는 별도 스레드에서 실행되어 트랜잭션 맵이 비어 있다. 초기화 콜백은 프록시가 씌워지기 전 원본 객체에 대해 호출되므로 트랜잭션 인터셉터를 거치지 않는다. 프로필이 활성화되기 전에 실행되어 JpaTransactionManager 빈이 아직 없다. @Transactional은 public이 아닌 메서드에만 적용된다. 스프링은 의존성 주입 직후 원본 빈에 대해 초기화 콜백을 호출하고, AOP 프록시는 그 뒤에 적용한다(스프링 레퍼런스의 빈 생명주기 설명). 실험에서 콜백 안의 this는 lab.SampleData였고 최종 빈은 CGLIB 프록시였다. 콜백은 같은 컨테이너 스레드에서 실행되며, 별도 빈의 트랜잭션 메서드를 부르자 트랜잭션이 정상적으로 열렸다.
    공유 EntityManager(shared EntityManager)
    스프링이 주입하는 트랜잭션 인식 EntityManager 프록시. 실제 대상은 호출 시점에 현재 스레드에서 찾는다.
    EntityManagerHolder
    스레드 로컬 리소스 맵에 EntityManager를 묶어 둘 때 쓰는 스프링의 보관 객체. 트랜잭션 진행 여부 같은 부가 정보도 함께 담는다.
    트랜잭션 동기화(transaction synchronization)
    트랜잭션 범위의 자원을 스레드에 묶고, 트랜잭션 완료 시점에 정리 콜백을 실행하는 스프링의 구조. TransactionSynchronizationManager가 담당한다.
    지연 닫기 쿼리 프록시(DeferredQueryInvocationHandler)
    트랜잭션 밖에서 임시로 만든 EntityManager의 Query를 감싸, 쿼리를 끝내는 메서드가 호출된 뒤에 EntityManager를 닫게 하는 처리기.
    동적 쿼리(dynamic query)
    입력 값에 따라 조건, 조인, 정렬이 실행 시점에 달라지는 쿼리. Querydsl에서는 조건 식 객체를 조립해 만든다.
    DTO 프로젝션(DTO projection)
    엔티티 대신 필요한 값만 골라 데이터 전송 객체로 조회하는 방식. 결과는 영속성 컨텍스트가 관리하지 않는다.
    OSIV(Open Session In View)
    웹 요청의 시작부터 끝까지 EntityManager를 요청 스레드에 묶어 두는 방식. 스프링 부트에서는 spring.jpa.open-in-view로 켜고 끄며 기본값은 켜짐이다.
    초기화 콜백(initialization callback)
    빈의 의존성 주입이 끝난 직후 컨테이너가 호출하는 메서드. @PostConstruct가 대표적이며 원본 빈에 대해 호출된다.
