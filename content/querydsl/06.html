    이 회차의 질문: 인터페이스뿐인 리포지토리에 Querydsl을 어떻게 넣는가

    앞 회차는 리포지토리를 클래스로 직접 만들었다. 클래스가 EntityManager와 JPAQueryFactory를 필드로 받고, 저장·단건 조회·전체 조회·검색 메서드를 하나씩 손으로 구현했다. 이 회차는 그 리포지토리를 스프링 데이터 JPA로 바꾼다. 스프링 데이터 JPA는 인터페이스만 선언하면 구현을 실행 시점에 만들어 준다. 저장과 조회 같은 반복 코드가 사라지는 대신, 새로운 문제가 하나 생긴다. Querydsl 쿼리는 JPAQueryFactory를 들고 있는 객체의 메서드 본문으로 쓰여야 하는데, 인터페이스에는 필드가 없고 스프링 데이터가 만들어 주는 구현에는 우리가 코드를 넣을 자리가 없다.

    그래서 첫 질문은 "인터페이스뿐인 리포지토리에 직접 쓴 구현을 어떻게 섞는가"다. 답은 사용자 정의 리포지토리(custom repository)라는 장치인데, 이 장치는 이름 규칙 하나로 동작하기 때문에 원리를 모르고 쓰면 이름이 한 글자만 틀려도 엉뚱한 오류 메시지를 만나게 된다. 두 번째 질문은 페이징이다. 목록 화면은 한 페이지 분량의 내용과 전체 개수를 함께 요구하고, 전체 개수를 얻기 위해 count 쿼리가 하나 더 나간다. 그 count 쿼리가 언제 필요 없는지, 필요할 때는 얼마나 가볍게 만들 수 있는지를 따진다. 세 번째 질문은 HTTP 요청의 page=2&size=20 같은 문자열이 어떻게 Pageable 객체가 되고, 결과 Page가 어떤 JSON이 되는가다.

    스프링 데이터 JPA 리포지토리로 변경

    바꾸는 작업 자체는 짧다. 05회의 리포지토리 클래스를 지우고 인터페이스를 하나 선언한다.

    package lab;

import org.springframework.data.jpa.repository.JpaRepository;
import java.util.List;

public interface EmployeeRepository extends JpaRepository {
    List findByName(String name);
}

    JpaRepository의 두 타입 인자는 이 리포지토리가 다루는 엔티티 타입과 식별자 타입이다. Spring Data JPA 3.5.13의 JpaRepository는 ListCrudRepository, ListPagingAndSortingRepository, QueryByExampleExecutor를 상속한다. 그래서 이 인터페이스 하나로 save, findById, findAll, count, delete 같은 기본 메서드와 findAll(Pageable), findAll(Sort)가 생긴다. 05회의 메서드가 어디로 가는지 정리하면 다음과 같다.

    구현 클래스 없는 빈의 정체: 리포지토리 프록시 해부

    우리는 EmployeeRepository를 구현하는 클래스를 한 줄도 쓰지 않았다. 그런데도 컨테이너는 이 타입의 빈을 주입해 준다. 그 객체를 해부해 보자. 테스트에서 주입받은 리포지토리의 클래스, 구현한 인터페이스, 프록시가 감싼 대상(target), 붙어 있는 어드바이스(advice)를 차례로 출력했다.

    네 가지를 읽을 수 있다. 첫째, 빈의 클래스 이름 $Proxy124는 소스 어디에도 없다. JDK의 java.lang.reflect.Proxy가 실행 중에 바이트코드를 만들어 정의한 클래스이고, 뒤의 숫자는 그 JVM에서 몇 번째로 만들어진 프록시 클래스인지에 따라 실행마다 달라질 수 있다. 둘째, 이 클래스는 EmployeeRepository를 구현한다. 그래서 EmployeeRepository 타입의 필드에 주입될 수 있다. 셋째, 프록시가 감싼 실제 객체는 SimpleJpaRepository다. findAll 트랜잭션의 이름이 SimpleJpaRepository.findAll이었던 이유가 여기 있다. 넷째, &employeeRepository로 꺼낸 빈 정의의 실체는 JpaRepositoryFactoryBean이다. 이름 앞의 &는 스프링 컨테이너에서 "팩토리 빈이 만든 객체 말고 팩토리 빈 자신을 달라"는 표기다. 컨테이너는 employeeRepository라는 이름에 이 팩토리 빈을 등록해 두고, 누군가 그 빈을 요청하면 팩토리 빈의 getObject()가 돌려준 객체, 즉 프록시를 준다.

    JDK 동적 프록시(dynamic proxy)의 동작은 단순하다. Proxy가 만든 클래스는 지정한 인터페이스의 모든 메서드를 구현하는데, 각 메서드의 본문은 똑같이 "생성할 때 받은 InvocationHandler의 invoke(proxy, method, args)를 부른다"다. 어떤 메서드가 불렸는지는 java.lang.reflect.Method 객체로, 인자는 Object[]로 전달된다. 스프링 AOP에서는 JdkDynamicAopProxy가 이 InvocationHandler 역할을 한다. 이 핸들러는 호출된 메서드에 적용할 인터셉터 목록을 구한 뒤, 목록의 첫 인터셉터부터 차례로 부른다. 각 인터셉터는 자기 일을 하고 invocation.proceed()를 불러 다음 인터셉터로 넘기거나, proceed()를 부르지 않고 스스로 결과를 돌려줘 체인을 끝낼 수 있다. 위 출력의 어드바이스 일곱 줄이 바로 그 체인의 순서다.

    이 프록시를 조립하는 코드는 Spring Data Commons의 RepositoryFactorySupport.getRepository()에 있다. 3.5.13 소스를 따라가면 순서는 이렇다.

    3번에서 SimpleJpaRepository가 받는 EntityManager는 JpaRepositoryFactoryBean.setEntityManager()에 붙은 @PersistenceContext로 주입된 것이다. 05회에서 본 공유 EntityManager 프록시, 즉 호출될 때마다 현재 스레드의 트랜잭션에 묶인 실제 EntityManager를 찾아가는 그 프록시다. 싱글톤 리포지토리를 여러 요청 스레드가 동시에 불러도 되는 이유는 05회의 설명과 같다. 어드바이스 일곱 개의 역할은 다음과 같다.

    순서인터셉터하는 일
    1CrudMethodMetadataPopulatingMethodInterceptor지금 불린 메서드의 메타데이터(락 모드, 쿼리 힌트 등)를 스레드에 노출해 SimpleJpaRepository가 읽게 한다.
    2PersistenceExceptionTranslationInterceptorJPA·Hibernate 예외를 스프링의 DataAccessException 계층으로 바꾼다.
    3TransactionInterceptor메서드의 트랜잭션 속성을 계산해 있으면 트랜잭션을 열고, 없으면 그냥 다음으로 넘긴다.
    4DefaultMethodInvokingMethodInterceptor인터페이스의 default 메서드면 그 본문을 실행한다. 상속한 인터페이스에 default 메서드가 하나라도 있으면 붙는데, JpaRepository에는 deleteInBatch라는 default 메서드가 있다.
    5QueryExecutorMethodInterceptor쿼리 메서드(findByName 같은)면 미리 만들어 둔 쿼리를 실행하고 끝낸다. 아니면 proceed().
    6ImplementationMethodExecutionInterceptor조합에서 메서드를 구현한 조각을 찾아 그 객체의 메서드를 호출한다. proceed()를 부르지 않으므로 체인은 여기서 끝난다.
    7PersistenceExceptionTranslationInterceptor같은 예외 변환 인터셉터가 한 번 더 있다. 6번이 proceed()를 부르지 않으므로 호출이 이 인터셉터까지 내려오지는 않는다.
    6번이 체인을 끝낸다는 것은 ImplementationMethodExecutionInterceptor.invoke() 소스에서 확인한 사실이다. 이 메서드는 composition.invoke(...)의 결과를 그대로 돌려주고, InvocationTargetException이면 원래 예외를 꺼내 다시 던질 뿐 invocation.proceed()를 부르지 않는다. 프록시의 대상으로 지정된 SimpleJpaRepository도 프록시가 직접 부르는 것이 아니라 조합의 마지막 조각으로서 호출된다.

    사용자 정의 리포지토리: 인터페이스 둘, 클래스 하나

    이제 Querydsl 검색 메서드를 옮길 차례다. 인터페이스에 메서드를 선언만 하면 스프링 데이터는 그것을 메서드 이름 쿼리로 해석하려 한다. default 메서드로 본문을 쓰는 방법도 떠올릴 수 있지만, 인터페이스는 인스턴스 필드를 가질 수 없어서 주입받은 JPAQueryFactory를 담아 둘 곳이 없다. 스프링 데이터가 내놓은 해법은 "구현을 직접 쓴 클래스 하나를 리포지토리에 조각으로 끼워 넣는 것"이다. 구성 요소는 셋이다.

    2. 구현 클래스 EmployeeRepositoryCustomImpl: 조각 인터페이스를 구현한다. 이름이 "조각 인터페이스 이름 + Impl"이어야 한다.
    3. 리포지토리 인터페이스 EmployeeRepository: JpaRepository와 함께 조각 인터페이스도 상속한다.

    검색 메서드의 본문은 05회의 search와 같다. where 다중 파라미터에 null을 넘기면 그 조건이 빠지는 원리도 05회에서 소스로 확인했다. 달라진 것은 이 코드가 놓인 자리다. 서비스나 컨트롤러는 이제 EmployeeRepository 하나만 주입받아 save, findByName, search를 모두 부른다. 호출하는 쪽에서 보면 세 메서드의 출처(스프링 데이터의 기본 구현, 메서드 이름 쿼리, 직접 쓴 Querydsl 코드)가 구별되지 않는다.

    구현 클래스에는 @Repository도 @Component도 붙이지 않았다. 그런데도 이 클래스는 빈으로 등록되고, 생성자의 JPAQueryFactory도 주입된다. 앞 절의 테스트에 한 줄을 더해 EmployeeRepositoryCustomImpl 타입의 빈 이름을 찍어 보면 impl bean = employeeRepositoryCustomImpl이 나온다. 클래스 단순 이름의 첫 글자를 소문자로 바꾼 이름이다. 누가 이 클래스를 찾아 빈으로 만들었는지가 다음 절의 내용이다. Spring Data Commons 문서도 구현 클래스는 스프링 데이터에 의존하지 않는 평범한 스프링 빈이 될 수 있고, 따라서 다른 빈을 주입받거나 애스펙트에 참여할 수 있다고 설명한다.

    사용자 정의 리포지토리가 유일한 길은 아니다. 조회 전용 Querydsl 코드를 EmployeeQueryRepository 같은 별도 클래스(평범한 @Repository 빈)에 모으고, 서비스가 두 리포지토리를 함께 주입받는 구성도 가능하다. 사용자 정의 리포지토리는 호출하는 쪽에 진입점을 하나로 모아 주는 대신 이름 규칙과 프록시 합성이라는 보이지 않는 연결에 의존한다. 별도 클래스는 연결이 눈에 보이는 대신 호출하는 쪽이 두 타입을 알아야 한다. 어느 쪽이 나은지는 쿼리가 특정 화면에 얼마나 묶여 있는지에 달려 있다.

    이름 하나로 연결되는 원리: 조각 탐지와 등록

    애플리케이션이 시작할 때 로그에 Bootstrapping Spring Data JPA repositories in DEFAULT mode.와 Finished Spring Data repository scanning in 23 ms. Found 1 JPA repository interface.가 찍힌다(걸린 시간은 실행마다 다르다). 이 스캔 단계에서 구현 클래스의 탐지와 등록이 함께 일어난다. Spring Data Commons 3.5.13의 RepositoryBeanDefinitionBuilder를 따라가면 리포지토리 하나에 대해 다음 일이 벌어진다.

    1. 리포지토리 인터페이스 찾기: 기준 패키지(base package) 아래에서 Repository를 상속한 인터페이스를 찾는다. 스프링 부트에서는 @SpringBootApplication이 붙은 클래스의 패키지가 기준이 된다.
    2. 조각 인터페이스 나열: 리포지토리 인터페이스가 상속한 인터페이스들 가운데 조각 후보를 나열한다. EmployeeRepositoryCustom이 여기에 걸린다.
    3. 구현 클래스 이름 만들기: 조각 인터페이스의 단순 이름에 접미사(postfix)를 붙인다. 기본 접미사는 Impl이고 @EnableJpaRepositories(repositoryImplementationPostfix = "...")로 바꿀 수 있다. 결과는 EmployeeRepositoryCustomImpl이다.
    4. 클래스 찾기: 기준 패키지를 스캔한 후보 클래스 가운데 단순 이름이 정확히 같고, 패키지가 조각 인터페이스의 패키지로 시작하는 클래스를 고른다(DefaultImplementationLookupConfiguration.matches()).
    5. 빈 정의 등록: 찾은 클래스를 빈으로 등록한다. 같은 이름의 빈 정의가 이미 있으면 그것을 쓴다.
    6. 조각 목록 등록: 조각 빈 이름들을 RepositoryFragmentsFactoryBean에 담아 등록하고, 리포지토리 팩토리 빈이 그것을 받아 앞 절의 2번 단계(조합)에 쓴다.
    리포지토리 인터페이스에서 출발해 조각 인터페이스 이름에 Impl을 붙여 클래스를 찾고, 빈으로 등록한 뒤 프록시 조합에 넣는 흐름을 보여 준다. 왼쪽에서 오른쪽으로 흐르는 깔끔한 순서도. 맨 왼쪽 상자 "EmployeeRepository" 안에 작은 칩 두 개 "JpaRepository"와 "EmployeeRepositoryCustom"이 있다. "EmployeeRepositoryCustom" 칩에서 화살표가 나와 둥근 상자 "이름 + Impl"로 가고, 그 상자에서 "EmployeeRepositoryCustomImpl"이라는 클래스 카드로 화살표가 이어진다. 클래스 카드 아래에 돋보기 아이콘과 라벨 "기준 패키지 스캔"이 있다. 클래스 카드에서 오른쪽 원통 모양 "빈 등록"으로 화살표, 다시 오른쪽 큰 상자 "RepositoryComposition"으로 화살표가 이어진다. "RepositoryComposition" 상자 안에는 위에서 아래로 두 칸 "사용자 정의 조각"(위, 강조색)과 "SimpleJpaRepository"(아래, 회색)가 쌓여 있다. 맨 오른쪽에 "프록시"라는 방패 모양 아이콘이 상자를 감싼다. 흰 배경, 파란색과 회색 위주의 평면 스타일. 조각 인터페이스 이름에 접미사 Impl을 붙인 클래스를 찾아 빈으로 만들고, 조합의 앞쪽에 둔다. SimpleJpaRepository는 언제나 맨 뒤다.

    이 규칙의 핵심은 연결 고리가 타입이 아니라 이름이라는 점이다. EmployeeRepositoryCustomImpl이 EmployeeRepositoryCustom을 구현한다는 사실은 탐지 조건이 아니다. 이름이 틀리면 어떻게 되는지 직접 확인해 보자. 별도 패키지에 조각 인터페이스 BrokenRepositoryCustom과 그것을 구현한 클래스 BrokenRepositoryCustomImple(끝이 Impl이 아니다)을 두고 애플리케이션을 띄웠다.

RepositoryInformationSupport.isQueryMethodCandidate()는 리포지토리 인터페이스의 메서드가 다음 조건을 모두 만족하면 쿼리 메서드 후보로 본다: 브리지 메서드가 아니고, default 메서드가 아니고, static이 아니며, @Query 같은 쿼리 애노테이션이 있거나 사용자 정의 조각도 기본 클래스도 그 메서드를 구현하지 않는다. 구현 클래스를 못 찾았으니 search는 어떤 조각에도 속하지 않고, SimpleJpaRepository에도 없다. 그래서 쿼리 메서드로 분류되고, 메서드 이름 파서는 search를 엔티티 속성 이름으로 읽으려다 실패한다.

    오류가 첫 호출 때가 아니라 애플리케이션 시작 시점, 리포지토리 빈을 만드는 단계에서 났다는 점도 기억해 두자. QueryExecutorMethodInterceptor는 생성자에서 쿼리 메서드 후보 전부에 대해 쿼리 객체를 미리 만든다(mapMethodsToQuery). 메서드 이름 쿼리의 오타가 배포 직후가 아니라 시작 시점에 드러나는 것도 같은 이유다.

    이름 규칙에는 오래된 형태가 하나 더 있다. 조각 인터페이스 이름이 아니라 리포지토리 인터페이스 이름에 Impl을 붙이는 방식이다. LegacyRepository라는 리포지토리가 조각 인터페이스 LegacyCustom을 상속하고, 구현 클래스 이름을 LegacyRepositoryImpl로 지어 실험했다. Spring Data 3.5.13에서도 이 구현은 탐지되어 정상 동작했다. 다만 Spring Data Commons 문서는 이 "리포지토리 하나에 사용자 정의 구현 하나" 방식의 이름 짓기를 폐기 예정(deprecated)으로 간주하며 쓰지 말고 조각 기반 모델로 옮기라고 권한다. 새 코드는 조각 인터페이스 이름 + Impl로 짓는 편이 문서와 맞는다. 문서는 또 서로 다른 패키지에 같은 이름의 구현 클래스가 여러 개 있으면 빈 이름으로 어느 것을 쓸지 정한다고 적고 있다.

    호출 하나가 구현 클래스에 닿기까지

    시작 시점의 준비가 끝나면 리포지토리 프록시 안의 RepositoryComposition에는 조각이 순서대로 들어 있다. 앞쪽에 사용자 정의 조각(EmployeeRepositoryCustomImpl 빈), 맨 뒤에 기본 조각(SimpleJpaRepository)이다. 이제 서비스가 repo.search(cond)를 부르면 무슨 일이 일어나는지 따라가 보자.

    프록시로 들어온 호출이 인터셉터 체인을 지나 쿼리 메서드는 5번에서, 나머지는 6번에서 조합을 거쳐 사용자 정의 구현 또는 SimpleJpaRepository로 가는 것을 보여 준다. 가로로 긴 시퀀스 다이어그램. 맨 왼쪽에 "호출하는 쪽" 막대, 그 오른쪽에 "프록시" 막대가 있다. 프록시 안에 위에서 아래로 쌓인 인터셉터 상자 다섯 개: "예외 변환", "트랜잭션", "default 메서드", "쿼리 메서드 실행", "조각 호출". 화살표 세 개가 왼쪽에서 들어온다. 첫째 화살표 라벨 "findByName"은 "쿼리 메서드 실행" 상자에서 꺾여 오른쪽 "DB" 원통으로 간다. 둘째 화살표 "search"는 "조각 호출" 상자에서 오른쪽의 "EmployeeRepositoryCustomImpl" 상자로 간다. 셋째 화살표 "findAll"은 "조각 호출" 상자에서 그 아래 "SimpleJpaRepository" 상자로 간다. 두 오른쪽 상자는 "조합"이라는 점선 테두리 안에 위아래로 놓인다. 흰 배경, 세 화살표는 서로 다른 색. 메서드 이름 쿼리는 5번 인터셉터에서 끝나고, 나머지는 6번 인터셉터가 조합에서 구현을 찾아 호출한다.

    같은 길에서 findByName은 5번에서 갈라진다. 시작 시점에 쿼리 메서드로 분류되어 쿼리 객체가 만들어져 있으므로 QueryExecutorMethodInterceptor가 그 쿼리를 실행하고 proceed() 없이 결과를 돌려준다. findAll은 6번까지 내려와 조합을 훑는데, 사용자 정의 조각에는 findAll이 없으므로 맨 뒤의 SimpleJpaRepository에서 찾는다.

    조각을 앞에서부터 훑는다는 사실에서 중요한 결론이 하나 나온다. 사용자 정의 조각이 기본 조각과 같은 시그니처의 메서드를 가지면 사용자 정의 쪽이 이긴다. Spring Data Commons 문서도 사용자 정의 구현이 기본 구현과 리포지토리 애스펙트보다 우선순위가 높다고 적고, 이 순서 덕분에 기본 메서드를 재정의할 수 있다고 설명한다. 확인을 위해 LegacyCustom 조각에 long count()를 선언하고 구현 클래스에서 -1을 돌려주게 했다.

    #### legacy count = -1

    JpaRepository가 물려준 count()는 원래 select count(*)에 해당하는 쿼리를 실행해야 하지만, 조합에서 사용자 정의 조각이 먼저 걸렸으므로 쿼리 없이 -1이 나왔다. 실무에서 이 성질은 save나 delete에 특별한 동작을 덧씌우는 데 쓰이지만, 실수로 같은 이름의 메서드를 조각에 만들면 기본 동작이 조용히 사라진다는 뜻이기도 하다. 여러 조각이 같은 시그니처를 내놓으면 리포지토리 인터페이스의 extends 목록에 선언한 순서로 우선순위가 정해진다고 문서는 적고 있다.

    트랜잭션은 누가 거는가

    이제 첫 절에서 미뤄 둔 질문으로 돌아가자. findAll은 읽기 전용 트랜잭션을 열었고 findByName은 열지 않았다. 사용자 정의 메서드는 어떨까. 조각 인터페이스에 현재 트랜잭션 상태를 돌려주는 진단용 메서드 txState()를 하나 추가하고, 구현에서 TransactionSynchronizationManager의 값을 읽어 문자열로 돌려주게 했다. 테스트 메서드에는 @Transactional을 붙이지 않았다.

    사용자 정의 메서드에는 트랜잭션이 없다. 세 결과는 하나의 규칙으로 설명된다. 리포지토리 프록시의 TransactionInterceptor는 TransactionalRepositoryProxyPostProcessor 안의 RepositoryAnnotationTransactionAttributeSource로 메서드마다 트랜잭션 속성을 계산한다. 호출된 메서드에 대응하는 메서드가 프록시의 대상 클래스(SimpleJpaRepository)에 있으면, 인터페이스 쪽(그 메서드와 메서드를 선언한 인터페이스)에 @Transactional이 없는 한 대상 클래스의 메서드와 클래스에서 속성을 찾는다. SimpleJpaRepository는 클래스에 @Transactional(readOnly = true)가 붙어 있고 save, delete 같은 쓰기 메서드에는 메서드 단위 @Transactional이 따로 붙어 있다. 그래서 findAll은 읽기 전용, save는 읽기·쓰기 트랜잭션을 얻는다.

    반면 findByName과 txState는 SimpleJpaRepository에 없는 메서드다. 계산은 대상 클래스에서 같은 메서드를 찾지 못하고, 메서드가 선언된 인터페이스(EmployeeRepository, EmployeeRepositoryCustom)의 메서드와 타입에서 @Transactional을 찾는데 거기에도 없다. 마지막으로 "대상 클래스에 대응하는 메서드"를 구하지만 그 결과가 원래 메서드와 같으므로 null을 돌려준다. Spring Data JPA 문서의 트랜잭션 절도 같은 내용을 적고 있다. CrudRepository에서 물려받은 메서드는 SimpleJpaRepository의 트랜잭션 설정을 따르고(읽기 연산은 readOnly가 참), 선언한 쿼리 메서드(default 메서드 포함)에는 기본으로 어떤 트랜잭션 설정도 적용되지 않는다.

    사용자 정의 메서드에 트랜잭션이 필요하면 어디에 @Transactional을 붙여야 할까. 구현 클래스는 평범한 스프링 빈이라는 점이 답을 준다. 구현 클래스나 그 메서드에 @Transactional을 붙이면, 리포지토리 프록시와는 별개로 스프링의 일반 AOP가 그 빈 자체를 프록시로 감싼다. 조합에 들어가는 조각 객체도 컨테이너에서 꺼낸 그 빈이다. 실험의 LegacyRepositoryImpl.hello()에 @Transactional(readOnly = true)를 붙이고 트랜잭션 없이 리포지토리를 통해 호출했다.

    #### legacy hello = hello from legacy.LegacyRepositoryImpl tx=true readOnly=true
#### impl bean class = legacy.LegacyRepositoryImpl$$SpringCGLIB$$0

    구현 빈의 클래스가 LegacyRepositoryImpl$$SpringCGLIB$$0, 즉 CGLIB로 만든 하위 클래스 프록시다. 호출은 리포지토리의 JDK 프록시를 거쳐 조합에서 이 CGLIB 프록시를 찾고, CGLIB 프록시를 지나 실제 메서드로 들어간다. 프록시가 두 겹인 셈이다. 다만 같은 실행의 DEBUG 로그를 보면 읽기 전용 트랜잭션을 연 쪽은 CGLIB 프록시가 아니다. 먼저 Creating new transaction with name [...SimpleJpaRepository.hello]가 찍혀 리포지토리 프록시의 TransactionInterceptor가 트랜잭션을 열었고, 이어서 CGLIB 프록시의 인터셉터는 Participating in existing transaction으로 거기에 참여했다. 이 오래된 이름 방식의 구현은 조각 인터페이스 없이 구현 객체의 클래스가 시그니처를 제공하는 조각으로 조합에 들어가므로, 앞의 계산 마지막 단계("대상 클래스에 대응하는 메서드")가 구현 클래스의 hello를 찾아 그 @Transactional을 읽기 때문이다(Spring Data Commons 3.5.13 소스 기준). 조각 인터페이스로 등록되는 EmployeeRepositoryCustomImpl 방식에서는 이 단계가 인터페이스의 메서드를 돌려주므로 구현 클래스의 애노테이션을 읽지 않는다. 메서드 본문 안의 getClass()가 프록시가 아닌 원래 클래스 이름을 찍은 것은, 본문이 실행될 때의 this가 CGLIB 프록시가 아니라 프록시가 위임한 원본 객체이기 때문이다. 문서의 예처럼 리포지토리 인터페이스에 @Transactional(readOnly = true)를 붙이는 방법도 있다. 그러면 위의 계산이 "메서드가 선언된 인터페이스" 단계에서 속성을 찾는다. 여기에 함정이 있다. EmployeeRepository에 그 애노테이션을 붙이고 같은 테스트를 다시 돌리면 다음과 같이 나온다.

    findByName은 이제 읽기 전용 트랜잭션을 얻었지만 txState는 여전히 트랜잭션이 없다. findByName은 EmployeeRepository에 선언되어 있어 "선언한 타입"이 애노테이션이 붙은 그 인터페이스인 반면, txState를 선언한 타입은 EmployeeRepositoryCustom이기 때문이다. 리포지토리 인터페이스에 붙인 @Transactional은 조각 메서드를 덮지 않는다. 사용자 정의 메서드의 트랜잭션은 구현 클래스나 조각 인터페이스 쪽에 붙여야 한다. 조각 인터페이스 EmployeeRepositoryCustom에 붙여 보면 txState가 active=true, readOnly=true를 돌려주는데, 로그의 트랜잭션 이름은 SimpleJpaRepository.txState로 찍힌다. 트랜잭션 이름이 프록시 대상 클래스 이름으로 만들어지기 때문이며, 실제로 실행된 코드는 SimpleJpaRepository가 아니다. 같은 로그에 Participating in existing transaction이 한 번 더 나오는 것은 인터페이스의 애노테이션 때문에 구현 빈 자신도 트랜잭션 프록시로 감싸져, 리포지토리 프록시가 연 트랜잭션에 참여했기 때문이다. 로그의 이름만 보고 어느 코드가 실행됐는지 판단하면 안 된다.

    트랜잭션이 없으면 무엇이 달라지는가. 페이징 메서드는 내용 쿼리와 count 쿼리, 두 번 DB에 간다. 05회에서 본 공유 EntityManager 프록시는 현재 스레드에 묶인 EntityManager가 없으면 호출마다 새 EntityManager를 만든다. 로그 수준을 올리고 트랜잭션 없이 searchPageSimple을 직접 불렀다가, 같은 일을 MockMvc를 통해 웹 요청으로 다시 했다(OSIV는 스프링 부트 기본값인 켜짐).

    직접 호출에서는 쿼리마다 EntityManager가 새로 만들어졌다. 웹 요청에서는 OSIV 인터셉터가 요청 시작 때 연 EntityManager 하나를 두 쿼리가 함께 썼다. 그러나 어느 쪽이든 트랜잭션은 없다. JDBC 커넥션은 기본적으로 자동 커밋(auto-commit) 모드이고, 스프링의 트랜잭션 매니저가 트랜잭션을 시작할 때만 자동 커밋을 끈다. MySQL 문서는 InnoDB에서 모든 사용자 활동이 트랜잭션 안에서 일어나며, 자동 커밋이 켜져 있으면 SQL 문 하나하나가 각자 하나의 트랜잭션이 된다고 설명한다. 따라서 트랜잭션 없이 실행된 내용 쿼리와 count 쿼리는 서로 다른 트랜잭션이고, 서로 다른 시점의 데이터를 본다. 두 쿼리 사이에 다른 트랜잭션이 행을 넣고 커밋하면 내용은 옛 상태, 전체 개수는 새 상태일 수 있다.

    두 쿼리를 하나의 트랜잭션으로 묶으면 MySQL InnoDB에서는 격리 수준에 따라 결과가 갈린다. 기본 격리 수준인 REPEATABLE READ에서는 같은 트랜잭션 안의 모든 일관된 읽기(consistent read)가 그 트랜잭션의 첫 읽기가 만든 스냅숏을 읽는다. READ COMMITTED에서는 일관된 읽기마다 새 스냅숏을 만든다. 즉 REPEATABLE READ의 트랜잭션 안에서라야 내용과 개수가 같은 스냅숏에서 나온다. 완벽한 일치가 꼭 필요한 화면은 드물지만, 어느 경우에 어긋날 수 있는지는 알고 있어야 한다. 흥미롭게도 PageImpl의 생성자 Javadoc은 마지막 페이지에서 전체 개수를 내용 길이에 맞춰 보정하며 그 목적이 "불일치 완화"라고 적고 있다. 그 보정이 무엇인지는 다음 절에서 본다.

    Querydsl 페이징 연동: Pageable에서 SQL까지

    스프링 데이터의 페이징은 두 타입으로 이루어진다. 요청 쪽의 Pageable은 "몇 번째 페이지를, 몇 개씩, 어떤 순서로"를 담고, 응답 쪽의 Page는 "이 페이지의 내용과 전체 개수"를 담는다. Pageable의 대표 구현은 PageRequest이고 PageRequest.of(page, size)나 PageRequest.of(page, size, sort)로 만든다. 페이지 번호는 0부터 센다. 사용자 정의 리포지토리는 이 Pageable을 받아 Querydsl 쿼리에 옮겨 적고, 결과로 Page를 만들어 돌려주면 된다. 가장 단순한 형태부터 보자.

    @Override
public Page searchPageSimple(EmployeeSearchCond cond, Pageable pageable) {
    List content = queryFactory
        .select(new QEmployeeDeptDto(employee.id, employee.name, employee.age, department.id, department.name))
        .from(employee)
        .leftJoin(employee.department, department)
        .where(nameEq(cond.name()), deptNameEq(cond.deptName()),
               ageGoe(cond.ageGoe()), ageLoe(cond.ageLoe()))
        .orderBy(employee.id.asc())
        .offset(pageable.getOffset())
        .limit(pageable.getPageSize())
        .fetch();

    Long total = queryFactory
        .select(employee.count())
        .from(employee)
        .leftJoin(employee.department, department)
        .where(nameEq(cond.name()), deptNameEq(cond.deptName()),
               ageGoe(cond.ageGoe()), ageLoe(cond.ageLoe()))
        .fetchOne();

    return new PageImpl<>(content, pageable, total);
}

    PageRequest.of(1, 3)으로 호출했을 때를 한 줄씩 따라가 보자. pageable.getOffset()은 AbstractPageRequest에 (long) pageNumber * (long) pageSize로 구현되어 있으므로 3이다. 곱하기 전에 둘 다 long으로 바꾸기 때문에 int 곱셈의 넘침은 없다. PageRequest.of(Integer.MAX_VALUE, 2000).getOffset()은 4294967294000이다. Querydsl의 offset(3)과 limit(3)은 쿼리 문자열이 아니라 쿼리 메타데이터의 QueryModifiers에 저장된다. fetch()가 불리면 AbstractJPAQuery.createQuery()가 JPQL 문자열로 JPA Query를 만든 다음 query.setMaxResults(3)과 query.setFirstResult(3)을 부른다. JPA의 두 메서드는 int를 받으므로 Querydsl은 long 값을 바꾸는데, QueryModifiers.toInt()는 Integer.MAX_VALUE보다 큰 값을 Integer.MAX_VALUE로 잘라 낸다. JPQL에 offset과 limit이 나타나지 않는다는 사실은 02회에서 확인했다. 그 값으로 SQL의 어느 문법을 쓸지는 Hibernate의 방언(dialect)이 정한다. H2에서는 이렇게 나왔다.

    select e1_0.id,e1_0.name,e1_0.age,d1_0.id,d1_0.name from employee e1_0 left join department d1_0 on d1_0.id=e1_0.department_id order by e1_0.id offset ? rows fetch first ? rows only
select count(e1_0.id) from employee e1_0
content=3 total=7 pages=3

    offset과 limit은 SQL 리터럴이 아니라 바인딩 파라미터(?)로 들어갔다. 덕분에 페이지 번호가 바뀌어도 SQL 문자열은 같고 바뀌는 것은 바인딩 값뿐이다. 내용은 offset 3부터 세 행, 즉 id 4·5·6(choi, jung, kang)이다. 페이지 번호와 크기를 바꿔 가며 실행한 결과는 다음과 같다. 이 단순한 형태는 매번 count 쿼리를 실행한다.

    결과를 담는 PageImpl은 내용 목록, Pageable, 전체 개수 세 가지를 받는다. 전체 페이지 수는 getTotalPages()가 크기가 0이면 1, 아니면 Math.ceil((double) total / size)로 계산하고, 다음 페이지 여부는 hasNext()가 현재 번호 + 1 < 전체 페이지 수로 판단한다. 7개를 3개씩 나누면 3페이지다. 범위를 벗어난 5번 페이지를 요청해도 예외는 없고, 내용은 비어 있으며 getNumber()는 5, hasNext()는 거짓이다.

    생성자에는 앞 절에서 예고한 보정이 하나 숨어 있다. Spring Data Commons 3.5.13의 소스는 이렇다.

    public PageImpl(List content, Pageable pageable, long total) {
    super(content, pageable);
    this.total = pageable.toOptional().filter(it -> !content.isEmpty())
            .filter(it -> it.getOffset() + it.getPageSize() > total)
            .map(it -> it.getOffset() + content.size())
            .orElse(total);
}

    내용이 비어 있지 않고 "offset + 페이지 크기"가 넘겨받은 전체 개수보다 크면, 즉 이 페이지가 마지막 페이지라고 판단되면 전체 개수를 넘겨받은 값 대신 "offset + 실제 내용 수"로 바꾼다. 마지막 페이지에서는 내용 쿼리가 본 행 수가 전체 개수를 정확히 말해 주기 때문이다. count 쿼리가 6을 돌려줬는데 2번 페이지(offset 6, 크기 3)의 내용이 두 행이라면, new PageImpl<>(List.of("a", "b"), PageRequest.of(2, 3), 6)의 getTotalElements()는 6이 아니라 8이다. 직접 실행해서 확인한 값이다. 앞 절에서 본 것처럼 두 쿼리가 서로 다른 스냅숏을 볼 수 있다는 점을 생각하면 이 보정의 의도가 보인다. 다만 마지막 페이지가 아닌 곳에서 생긴 불일치는 그대로 남는다.

    마지막으로 orderBy(employee.id.asc())가 왜 들어갔는지 짚자. 페이징은 "정렬된 결과를 잘라 낸다"는 전제 위에 서 있다. MySQL 문서는 ORDER BY 열의 값이 같은 행들은 서버가 어떤 순서로든 돌려줄 수 있고, 실행 계획에 따라 그 순서가 달라질 수 있으며, LIMIT이 실행 계획에 영향을 주므로 LIMIT이 있을 때와 없을 때 순서가 다를 수 있다고 적고 있다. 나이로만 정렬하면 같은 나이의 직원이 1페이지와 2페이지에 중복해서 나오거나 어느 페이지에도 나오지 않을 수 있다는 뜻이다. 정렬 기준의 맨 끝에 유일한 열(여기서는 식별자)을 두면 순서가 하나로 정해진다. 02회에서 본 대로 Querydsl 5.0부터 fetchResults()와 fetchCount()가 폐기 예정이 되었으므로, count는 처음부터 별도 쿼리로 작성했다.

    한 층 아래: offset과 count는 DB에서 얼마인가

    페이징 쿼리는 요청마다 두 번 DB에 간다. 각각이 DB 안에서 어떤 일을 시키는지 보자. 먼저 offset이다. "앞에서 n개를 건너뛰고 m개"라는 요청을 받은 DB는 n번째 행이 어디인지 바로 알 수 없다. 정렬 순서대로 행을 만들어 가며 앞의 n개를 버려야 한다. H2 2.3.232에서 직원 10만 명을 넣고 EXPLAIN ANALYZE로 읽은 행 수(scanCount)를 확인했다. JDBC만 쓰는 작은 프로그램이다.

    import java.sql.*;

public class OffsetScan {
    public static void main(String[] args) throws Exception {
        try (Connection c = DriverManager.getConnection("jdbc:h2:mem:t");
             Statement s = c.createStatement()) {
            s.execute("create table employee(id bigint primary key, name varchar(20), age int)");
            s.execute("insert into employee select x, 'e' || x, mod(x, 50) from system_range(1, 100000)");
            for (int offset : new int[]{0, 1000, 50000, 99990}) {

    다음은 count다. H2는 조건 없는 count(*)를 행을 읽지 않고 답했다(direct lookup). 표의 행 수를 따로 관리하고 있기 때문이다. 하지만 조건이 붙는 순간 표 전체 10만 행을 읽었다. MySQL InnoDB는 조건이 없어도 이런 지름길이 없다. MySQL 문서는 InnoDB가 표의 행 수를 내부에 따로 세어 두지 않는 이유를, 동시에 실행되는 트랜잭션들이 같은 순간에 서로 다른 행 수를 "볼" 수 있기 때문이라고 설명한다. MVCC 아래에서 행 수는 하나의 값이 아니라 트랜잭션마다 다른 값이고, 그래서 SELECT COUNT(*)는 현재 트랜잭션에 보이는 행만 센다. 같은 문서에 따르면 InnoDB는 SELECT COUNT(*)를 처리할 때 인덱스나 옵티마이저 힌트가 달리 지시하지 않으면 가장 작은 보조 인덱스를 훑고, 보조 인덱스가 없으면 클러스터드 인덱스를 훑는다. 결국 count 쿼리의 비용은 조건에 맞는 행 수에 비례한다. 목록 화면의 매 요청이 이 비용을 낸다는 것이 count 최적화가 필요한 이유다.

    JPQL 쪽의 표현도 하나 확인해 두자. Querydsl의 employee.count()는 JPQL count(employee)가 되고, Hibernate는 이것을 count(e1_0.id)로 바꿨다. Wildcard.count(com.querydsl.core.types.dsl.Wildcard)는 SQL count(*)가 된다. MySQL 문서에 따르면 COUNT(expr)는 expr이 NULL이 아닌 값의 개수를, COUNT(*)는 NULL 포함 여부와 관계없이 행의 개수를 센다. 식별자는 기본 키라 NULL일 수 없으므로 두 결과는 같고, 이번 실행에서도 둘 다 7이었다. 또 InnoDB는 COUNT(*)와 COUNT(1)을 같은 방식으로 처리하며 성능 차이가 없다고 문서는 적고 있다.

    정렬된 인덱스 위에서 offset 방식은 처음부터 n개를 지나가야 하고, 키셋 방식은 시작 위치로 바로 찾아간다는 것을 대비해 보여 준다. 위아래 두 줄로 나뉜 그림. 각 줄에는 왼쪽에서 오른쪽으로 길게 늘어선 작은 칸 띠가 있고 띠 위에 라벨 "id 순서로 정렬된 인덱스"가 있다. 위쪽 줄 제목 "offset 50000": 띠의 왼쪽 끝부터 긴 회색 화살표가 칸들을 하나씩 훑으며 지나가고 그 구간에 라벨 "읽고 버리는 50000행"이 붙는다. 화살표 끝의 짧은 파란 구간에 "반환하는 10행". 아래쪽 줄 제목 "id > 99990": 띠 위에서 아래로 꽂히는 파란 화살표가 띠의 오른쪽 부분에 바로 내려앉고, 그 뒤 짧은 파란 구간에 "반환하는 10행". 오른쪽 여백에 숫자 비교 "scanCount 50010"과 "scanCount 11". 흰 배경, 단순한 평면 스타일. H2 실험에서 offset 방식은 offset + 10행을 읽었고, 키셋 방식은 11행만 읽었다.

    CountQuery 최적화 ①: 실행하지 않아도 되는 count

    앞의 실행 표를 다시 보자. PageRequest.of(0, 10)에서 내용 쿼리는 7행을 돌려줬다. 첫 페이지인데 한 페이지 크기(10)보다 적게 나왔다는 것은 전체가 7행이라는 뜻이다. count 쿼리를 실행할 필요가 없었다. PageRequest.of(2, 3)도 마찬가지다. offset 6에서 1행만 나왔으니 이것이 마지막 페이지이고 전체는 6 + 1 = 7이다. 스프링 데이터는 이 판단을 PageableExecutionUtils.getPage()로 제공한다. Spring Data Commons 3.5.13에서는 org.springframework.data.support 패키지에 있고 Javadoc에 @since 2.4로 표시되어 있다. 소스의 핵심은 이렇다.

    public static  Page getPage(List content, Pageable pageable, LongSupplier totalSupplier) {
    // null 검사 생략
    if (pageable.isUnpaged()) {
        return new PageImpl<>(content, pageable, content.size());
    }
    if (isPartialPage(content, pageable)) {          // pageSize > content.size()
        if (isFirstPage(pageable)) {                  // offset == 0
            return new PageImpl<>(content, pageable, content.size());
        } else if (!content.isEmpty()) {
            return new PageImpl<>(content, pageable, pageable.getOffset() + content.size());
        }
    }
    return new PageImpl<>(content, pageable, totalSupplier.getAsLong());
}

    전체 개수를 내용만으로 확정할 수 있는 경우는 셋이다. 페이징하지 않은 요청이면 내용의 크기가 곧 전체다. 첫 페이지에서 내용이 페이지 크기보다 적게 나오면 내용의 크기가 전체다. 첫 페이지가 아니고 내용이 비어 있지 않으면서 페이지 크기보다 적게 나오면 "offset + 내용 수"가 전체다. 나머지 경우, 즉 내용이 페이지를 꽉 채웠거나(뒤에 더 있을 수 있다) 내용이 비어 있는(범위를 벗어난 요청일 수 있다) 경우에만 세 번째 인자 totalSupplier를 부른다. 이 인자를 long 값이 아니라 LongSupplier로 받는다는 점이 핵심이다. 값이 필요할 때까지 count 쿼리의 실행을 미루기 위해서다.

Querydsl 코드에는 leftJoin(employee.department, department)가 있었는데 Hibernate 6.6.53이 만든 SQL에는 조인이 없다. 이 쿼리에서 department는 select에도 where에도 쓰이지 않았고, 다대일 외부 조인은 직원 행을 없애지도(외부 조인이므로) 늘리지도(상대가 최대 하나이므로) 않는다. 결과에 영향이 없는 조인을 Hibernate가 SQL에서 생략한 것이다. 이 생략은 이번 버전에서 관찰한 동작이므로, 다른 버전이나 다른 구현체에 기대지 말고 count 쿼리에서 직접 빼는 편이 확실하다. 두 번째 관찰은 내부 조인이다. 같은 다대일이라도 내부 조인은 부서가 없는 jung을 걸러 내므로 결과가 6으로 바뀌었고, Hibernate도 조인을 생략하지 않았다. 내용 쿼리가 내부 조인이라면 count에도 같은 내부 조인이 있어야 한다. 세 번째 관찰은 일대다(to-many) 조인이다. 부서 2개를 직원과 외부 조인하면 행이 부서별 직원 수만큼 늘어나 count가 6이 된다. 이 조인은 행 집합을 바꾸므로 Hibernate도 생략하지 않았다. 컬렉션을 조인한 채로 "부서 수"를 세려면 countDistinct()로 중복을 제거해야 하고, 그러면 SQL이 count(distinct d1_0.id)가 된다. 중복 제거라는 작업이 하나 더 붙으므로, 내용 쿼리가 컬렉션 조인을 정말로 필요로 하는지부터 다시 보는 것이 순서다.

    페치 조인은 count 쿼리에 아예 들어갈 수 없다. 내용 쿼리에서 페치 조인을 쓰던 코드를 복사해 select만 count로 바꾸면 이렇게 된다.

    searchPageOptimized는 이 원칙을 조건부 조인으로 적용했다. 검색 조건이 부서 이름을 볼 때만 부서를 조인한다. 부서 조건을 준 호출의 count SQL은 이렇다.

    select e1_0.id,e1_0.name,e1_0.age,d1_0.id,d1_0.name from employee e1_0 left join department d1_0 on d1_0.id=e1_0.department_id where d1_0.name=? order by e1_0.id offset ? rows fetch first ? rows only
select count(e1_0.id) from employee e1_0 left join department d1_0 on d1_0.id=e1_0.department_id where d1_0.name=?
content=[EmployeeDeptDto[employeeId=1, name=kim, age=25, deptId=1, deptName=dev], EmployeeDeptDto[employeeId=2, name=lee, age=31, deptId=1, deptName=dev]] total=3

    첫 페이지가 꽉 찼으므로(2/2) count가 실행됐고, 부서 조건 때문에 조인이 들어갔다. 05회에서 본 대로 외부 조인한 테이블의 열에 where 조건을 걸면 그 조건을 만족하지 못하는 NULL 행이 걸러지므로, 이 SQL은 결과적으로 내부 조인과 같은 행을 센다. 조건이 없을 때의 count는 앞의 실행 기록대로 select count(e1_0.id) from employee e1_0이다. count를 더 줄이는 방법(예: 정확한 전체 개수 대신 "다음 페이지가 있는가"만 알려 주는 Slice, 화면에서 전체 개수를 빼는 설계)은 화면 요구 사항의 문제이므로 여기서는 이름만 적어 둔다.

    컨트롤러 개발: 쿼리 문자열이 Pageable이 되기까지

    이제 HTTP로 열자. 컨트롤러는 검색 조건과 Pageable을 받아 리포지토리에 넘기기만 한다.

    @RestController
public class EmployeeController {
    private final EmployeeRepository employeeRepository;

    public EmployeeController(EmployeeRepository employeeRepository) {
        this.employeeRepository = employeeRepository;
    }

    @GetMapping("/v2/employees")
    public Page searchV2(EmployeeSearchCond cond, Pageable pageable) {
        return employeeRepository.searchPageSimple(cond, pageable);
    }

    @GetMapping("/v3/employees")
    public Page searchV3(EmployeeSearchCond cond, Pageable pageable) {
        return employeeRepository.searchPageOptimized(cond, pageable);
    }
}

    EmployeeSearchCond가 쿼리 파라미터로 채워지는 과정(애노테이션 없는 단순하지 않은 타입은 @ModelAttribute로 처리된다)은 05회에서 봤다. 새로운 것은 Pageable 파라미터다. 스프링 MVC는 이 타입을 기본으로는 모른다. Spring Boot 3.5.16의 SpringDataWebAutoConfiguration에 @EnableSpringDataWebSupport가 붙어 있고, 이 애노테이션이 PageableHandlerMethodArgumentResolver와 SortHandlerMethodArgumentResolver를 등록해 Pageable과 Sort를 컨트롤러 인자로 쓸 수 있게 만든다. 이 자동 구성은 서블릿 웹 애플리케이션이고, 사용자가 PageableHandlerMethodArgumentResolver 빈을 직접 등록하지 않았을 때만 동작한다. 스프링 부트의 설정 속성과 기본값은 다음과 같다(SpringDataWebProperties 소스 기준).

    속성기본값의미
    spring.data.web.pageable.page-parameterpage페이지 번호 파라미터 이름
    spring.data.web.pageable.size-parametersize페이지 크기 파라미터 이름
    spring.data.web.pageable.default-page-size20크기가 없거나 1보다 작을 때 쓰는 값
    spring.data.web.pageable.max-page-size2000크기의 상한
    spring.data.web.pageable.one-indexed-parametersfalse요청의 페이지 번호를 1부터 세는가
    spring.data.web.pageable.prefix빈 문자열파라미터 이름 앞에 붙일 접두사
    spring.data.web.pageable.serialization-modedirectPage를 JSON으로 내보내는 방식
    spring.data.web.sort.sort-parametersort정렬 파라미터 이름

    리졸버가 문자열을 숫자로 바꾸는 규칙은 경계값에서 드러난다. Pageable을 그대로 문자열로 돌려주는 진단용 핸들러를 두고 여러 쿼리 문자열을 보냈다.

    ####  -> Page request [number: 0, size 20, sort: UNSORTED] offset=0
#### ?page=2&size=5 -> Page request [number: 2, size 5, sort: UNSORTED] offset=10
#### ?page=-1 -> Page request [number: 0, size 20, sort: UNSORTED] offset=0
#### ?size=5000 -> Page request [number: 0, size 2000, sort: UNSORTED] offset=0
#### ?size=0 -> Page request [number: 0, size 20, sort: UNSORTED] offset=0
#### ?size=-3 -> Page request [number: 0, size 20, sort: UNSORTED] offset=0
#### ?page=abc&size=x -> Page request [number: 0, size 20, sort: UNSORTED] offset=0
#### ?page=3000000000 -> Page request [number: 0, size 20, sort: UNSORTED] offset=0

    잘못된 값에도 오류 응답(400)은 없다. 모두 어떤 값으로 보정되었다. 그 규칙은 PageableHandlerMethodArgumentResolverSupport의 두 메서드에 있다. parseAndApplyBoundaries()는 문자열이 비어 있으면 "값 없음"을, 정수로 파싱되지 않으면 0을, 파싱되면 음수는 0으로 상한을 넘으면 상한으로 바꾼 값을 돌려준다. 페이지 번호의 상한은 Integer.MAX_VALUE, 크기의 상한은 maxPageSize(2000)다. 3000000000은 int 범위를 넘어 Integer.parseInt가 NumberFormatException을 던지므로 0이 되었다. 이어서 getPageable()은 값이 없으면 기본값(PageRequest.of(0, 20) 또는 @PageableDefault로 지정한 값)을 쓰고, 크기가 1보다 작으면 기본 크기로 바꾸고, 마지막으로 크기를 상한으로 자른다. size=x가 20이 된 경로는 "파싱 실패 → 0 → 1보다 작음 → 기본값 20"이다.

    크기에 상한이 있는 이유는 소스의 Javadoc에 적혀 있다. 최대 크기는 OutOfMemoryError를 일으키려는 공격을 막기 위한 것이다. size=100000000 같은 요청이 그대로 통과하면 내용 쿼리가 표 전체를 읽어 DTO 목록으로 힙에 올리게 된다. 기본 상한 2000도 화면에 따라서는 크다. 목록 API마다 실제로 필요한 최대 크기를 정하고 max-page-size나 PageableHandlerMethodArgumentResolverCustomizer 빈으로 낮추는 것을 고려할 만하다.

    one-indexed-parameters를 켜면 요청의 page=1이 내부의 0번 페이지가 된다. 실험에서 page=1과 page=0이 모두 number: 0이 되었는데, 0에서 1을 뺀 -1이 다시 0으로 보정되었기 때문이다. 이 설정은 요청을 해석하는 쪽에만 작용한다는 점을 주의해야 한다. 같은 설정에서 page=2&size=3을 요청한 응답 JSON의 페이지 번호는 아래 절에서 보듯 "number":1, 즉 0부터 센 값이었다. 클라이언트가 응답의 번호를 다음 요청에 그대로 쓰면 한 페이지씩 어긋난다.

    정렬과 JSON 응답: 검증하지 않는 Sort, 안정적이지 않은 PageImpl

    정렬 파라미터의 형식은 property,property(,ASC|DESC)(,IgnoreCase)이고, 방향을 바꾸려면 sort 파라미터를 여러 번 쓴다. 방향은 마지막 원소에서만 인식된다.

    #### ?sort=age,desc&sort=name -> Page request [number: 0, size 20, sort: age: DESC,name: ASC] offset=0
#### ?sort=age,desc,name -> Page request [number: 0, size 20, sort: age: ASC,desc: ASC,name: ASC] offset=0

    두 번째 요청에서 desc는 맨 끝이 아니므로 방향이 아니라 속성 이름으로 해석되었고, 존재하지 않는 desc라는 속성이 정렬 목록에 들어갔다. 이것이 가능한 이유를 Spring Data Commons 문서가 명시한다. 요청 파라미터에서 만들어진 Sort.Order는 속성 이름을 그대로 실어 나르는 전송 객체일 뿐 도메인 모델에 대해 검증되지 않으며, 검증은 애플리케이션의 책임이다.

    그런데 우리의 searchPageOptimized는 pageable.getSort()를 아예 쓰지 않는다. 정렬은 orderBy(employee.id.asc())로 고정되어 있다. 스프링 데이터의 기본 메서드(findAll(Pageable))는 Sort를 쿼리의 정렬로 바꿔 주지만, 사용자 정의 메서드에서는 Sort를 Querydsl의 OrderSpecifier로 바꾸는 일을 직접 해야 한다. 가장 쉬운 방법은 PathBuilder로 속성 이름을 경로로 바꾸는 것이다.

    PathBuilder path = new PathBuilder<>(Employee.class, "employee");
OrderSpecifier[] specs = sort.stream()
    .map(o -> new OrderSpecifier(o.isAscending() ? Order.ASC : Order.DESC, path.get(o.getProperty())))
    .toArray(OrderSpecifier[]::new);

    Sort.by(Sort.Order.desc("age"), Sort.Order.asc("name"))에 대해 이 코드는 order by e1_0.age desc,e1_0.name을 만들었다. 문제는 존재하지 않는 속성이다. salary로 정렬하게 하면 쿼리 실행 시점에 다음 예외가 난다.

    EX: java.lang.IllegalArgumentException: org.hibernate.query.sqm.UnknownPathException: Could not resolve attribute 'salary' of 'lab.Employee' [select employee.name ...

    요청 하나로 서버 쪽 예외를 일으킬 수 있고, 별도의 처리가 없으면 500 응답이 된다. 또 이 방식은 클라이언트가 엔티티의 아무 속성으로나, 연관 경로가 허용된다면 조인이 필요한 경로로도 정렬을 요구할 수 있게 만든다. 인덱스가 없는 열로 큰 표를 정렬하게 되는 것도 그 연장선이다. 그래서 정렬 키는 허용 목록(whitelist)으로 받는 편이 낫다. API가 공개하는 정렬 키 이름과 Querydsl 식을 직접 연결한다.

    private static final Map> SORTABLE = Map.of(
    "name", employee.name,
    "age", employee.age,
    "deptName", department.name);

public static OrderSpecifier[] toOrderSpecifiers(Sort sort) {
    List> result = new ArrayList<>();
    for (Sort.Order o : sort) {
        ComparableExpressionBase expr = SORTABLE.get(o.getProperty());
        if (expr == null) {
            throw new IllegalArgumentException("정렬할 수 없는 속성: " + o.getProperty());
        }
        result.add(o.isAscending() ? expr.asc() : expr.desc());
    }
    result.add(employee.id.asc());   // 같은 값끼리의 순서를 정하는 마지막 기준
    return result.toArray(OrderSpecifier[]::new);
}

    Sort.by(Sort.Order.asc("deptName"), Sort.Order.desc("age"))로 부서를 외부 조인한 쿼리에 적용하면 SQL은 order by d1_0.name,e1_0.age desc,e1_0.id가 되고 결과는 [jung, lee, kang, kim, choi, yoon, park]였다. 부서가 없는 jung이 맨 앞에 온 것은 H2가 오름차순에서 NULL을 앞에 두었기 때문이다. 허용 목록에 없는 salary는 쿼리를 만들기 전에 IllegalArgumentException으로 걸러지므로, 컨트롤러 조언(@RestControllerAdvice) 등에서 400 응답으로 바꿀 수 있다. 외부에 공개하는 이름(deptName)과 내부 경로(department.name)가 분리된다는 것도 장점이다. 엔티티 필드 이름을 바꿔도 API는 그대로다. 스프링 데이터가 제공하는 Querydsl 정렬 변환 도구는 07회에서 다룬다.

    흔한 오해와 함정, 그리고 다음 회차와의 연결

    "구현 클래스에는 @Repository를 붙여야 빈이 된다." 붙이지 않아도 리포지토리 설정 단계가 클래스를 찾아 빈으로 등록한다. 실험의 employeeRepositoryCustomImpl 빈이 그 증거다. 연결 고리는 애노테이션이 아니라 이름이다. 반대로 이름이 틀리면 애노테이션을 붙여 빈이 되더라도 조각으로 연결되지 않으며, 그 메서드는 쿼리 메서드로 해석되어 No property ... found로 실패한다. 이 오류 메시지를 보면 메서드 이름보다 구현 클래스의 이름과 패키지를 먼저 의심해야 한다.

    "리포지토리의 모든 메서드는 트랜잭션 안에서 실행된다." SimpleJpaRepository가 구현한 메서드만 그렇다. 메서드 이름 쿼리와 사용자 정의 메서드에는 기본 트랜잭션이 없고, 리포지토리 인터페이스에 붙인 @Transactional은 메서드 이름 쿼리에는 적용되어도 조각 메서드에는 적용되지 않았다. 트랜잭션이 없으면 내용 쿼리와 count 쿼리가 서로 다른 트랜잭션, 서로 다른 스냅숏에서 실행된다. 보통은 서비스 계층의 @Transactional(readOnly = true)가 바깥에서 트랜잭션을 열어 이 문제를 덮는데, 컨트롤러가 리포지토리를 직접 부르는 구조에서는 덮어 줄 바깥 트랜잭션이 없다.

    "PageableExecutionUtils를 쓰면 count가 사라진다." 첫 페이지에서 결과가 한 페이지를 못 채울 때와, 마지막 페이지에서 결과가 일부만 찰 때만 사라진다. 결과가 많은 검색의 앞 페이지에서는 매번 실행된다. 그래서 count 쿼리 자체를 가볍게 하는 작업(불필요한 조인·정렬·페치 조인 제거)은 여전히 필요하다.

    "count 쿼리에서 조인은 다 빼도 된다." 행 집합을 바꾸지 않는 다대일 외부 조인만 그렇다. 내부 조인은 연관이 없는 행을 걸러 내고, 일대다 조인은 행을 늘린다. 조건이 조인한 테이블을 볼 때는 당연히 조인이 필요하다. Hibernate 6.6이 쓰이지 않는 다대일 외부 조인을 SQL에서 생략해 준 것은 이번 버전에서 관찰한 동작일 뿐이다.

    "Page를 그대로 반환해도 응답 모양은 변하지 않는다." 그 모양은 PageImpl의 getter가 정하고, 스프링 데이터는 그 안정성을 보장하지 않는다고 경고 로그와 문서로 밝히고 있다. PagedModel이나 직접 만든 응답 DTO로 계약을 고정한다.

    이 회차의 지식은 몇 군데로 이어진다. 리포지토리가 JDK 동적 프록시와 인터셉터 체인으로 만들어진다는 사실은 스프링 AOP 전체의 구조와 같다. 프록시 팩토리, 어드바이저, 메서드 호출 체인은 이 로드맵의 스프링 핵심 원리 고급편에서 바닥부터 다시 다룬다. offset 페이징의 비용과 키셋 페이징, count와 인덱스의 관계는 DB 설계·성능 권에서 인덱스 구조와 함께 본다. 그리고 07회는 이 회차에서 손으로 한 일 가운데 일부를 스프링 데이터가 대신하는 기능, 즉 리포지토리가 Querydsl의 Predicate를 직접 받는 QuerydslPredicateExecutor, 페이징과 정렬 변환을 도와주는 QuerydslRepositorySupport, 요청 파라미터를 Predicate로 바꾸는 웹 지원을 다루고 그 한계를 따진다.

    이 장의 핵심

    스프링 데이터 리포지토리 빈은 JDK 동적 프록시이고, 호출은 인터셉터 체인을 지나 메서드 이름 쿼리로 끝나거나 조각 조합에서 구현을 찾아 들어간다. 사용자 정의 구현은 "조각 인터페이스 이름 + Impl"이라는 이름 하나로 그 조합의 앞자리에 들어가며, 트랜잭션은 자동으로 따라오지 않는다. 페이징은 offset·limit을 Query 객체에 싣는 내용 쿼리와, 내용만으로 전체 개수를 알 수 없을 때만 실행되는 가벼운 count 쿼리의 조합이고, 컨트롤러는 경계값을 보정한 Pageable을 받아 안정적인 모양의 응답으로 돌려준다.
    리포지토리 프록시
    JpaRepositoryFactoryBean이 만드는 JDK 동적 프록시. 대상은 SimpleJpaRepository이고, 호출은 예외 변환·트랜잭션·쿼리 실행·조각 호출 인터셉터를 차례로 지난다.
    조각(fragment)과 조합
    리포지토리 인터페이스가 상속한 조각 인터페이스마다 구현 객체를 찾아 RepositoryComposition에 순서대로 넣는다. 사용자 정의 조각이 앞, SimpleJpaRepository가 맨 뒤이며 앞의 것이 우선한다.
    Impl 이름 규칙
    구현 클래스는 "조각 인터페이스 단순 이름 + Impl"이어야 탐지된다. 틀리면 그 메서드가 쿼리 메서드로 해석되어 시작 시점에 PropertyReferenceException이 난다.
    리포지토리 트랜잭션
    SimpleJpaRepository의 메서드만 기본 트랜잭션을 갖는다. 메서드 이름 쿼리와 사용자 정의 메서드에는 없으며, 조각 메서드의 트랜잭션은 구현 클래스나 조각 인터페이스에 붙인다.
    Querydsl 페이징
    offset(pageable.getOffset()), limit(pageable.getPageSize())는 JPQL이 아니라 setFirstResult·setMaxResults로 전달되고, SQL 문법은 방언이 정한다. 정렬 끝에 유일한 열을 둔다.
    PageImpl의 보정
    내용이 비어 있지 않고 offset + 크기가 전체 개수보다 크면 전체 개수를 offset + 내용 수로 바꾼다. 두 쿼리의 불일치를 마지막 페이지에서 완화한다.
    count 생략
    PageableExecutionUtils.getPage()는 첫 페이지가 덜 찼거나 마지막 페이지가 일부만 찬 경우 count를 부르지 않는다. LongSupplier로 받아 실행을 미룬다.
    가벼운 count
    count는 같은 행 집합을 세기만 하면 된다. 다대일 외부 조인·정렬은 빼고, 내부 조인·조건에 쓰인 조인은 남기고, 일대다 조인은 행을 늘리며, 페치 조인은 쓸 수 없다.
    Pageable 바인딩과 직렬화
    잘못된 page·size는 오류 대신 0·기본값·상한으로 보정된다. 정렬 속성은 검증되지 않으므로 허용 목록으로 받고, 응답은 PagedModel(VIA_DTO)로 모양을 고정한다.

    사용자 정의 리포지토리와 관련된 장애는 대개 시작 시점에 난다. 배포한 애플리케이션이 No property 'xxx' found for type으로 뜨지 않는다면 메서드 이름이 아니라 구현 클래스를 먼저 봐야 한다. 리팩터링 도구로 조각 인터페이스 이름만 바꾸고 구현 클래스 이름을 함께 바꾸지 않았거나, 구현 클래스를 다른 패키지로 옮겼거나, 멀티 모듈에서 리포지토리 스캔 범위 밖에 두었을 때 똑같은 메시지가 나온다. 반대로 조각에 기본 메서드와 같은 시그니처(count(), save() 등)를 실수로 만들면 아무 오류 없이 기본 동작이 바뀐다. 이름에 기대는 연결이므로 코드 리뷰에서 조각 인터페이스의 메서드 목록을 JpaRepository와 대조해 볼 가치가 있다.

    페이징 성능 문제는 대개 "뒤 페이지가 느리다"와 "목록 API가 전체적으로 느리다"로 나타난다. 앞의 것은 offset이 페이지 번호에 비례해 읽는 행을 늘리기 때문이고, 화면이 깊은 페이지 이동을 꼭 허용해야 하는지부터 따질 문제다. 뒤의 것은 매 요청마다 나가는 count가 원인인 경우가 많다. count에서 불필요한 조인을 빼고, 첫 페이지와 마지막 페이지에서는 count를 생략하고, 그래도 비싸면 화면에서 정확한 전체 개수가 정말 필요한지(다음 페이지 유무만으로 충분한지) 기획과 다시 이야기한다. 판단의 근거는 언제나 실행 계획과 실제로 읽은 행 수여야 한다.

    트랜잭션 경계는 일관성 요구에 따라 달라진다. 내용과 전체 개수가 잠깐 어긋나도 괜찮은 일반 목록이라면 트랜잭션 없이 두 쿼리를 따로 실행해도 큰 문제는 없고, PageImpl의 보정이 마지막 페이지의 어긋남을 줄여 준다. 정산 화면처럼 개수와 내용이 반드시 같은 시점을 반영해야 한다면, 두 쿼리를 하나의 읽기 전용 트랜잭션에 넣고 MySQL InnoDB의 기본 격리 수준(REPEATABLE READ)에서 같은 스냅숏을 보게 해야 한다. READ COMMITTED로 운영하는 DB라면 트랜잭션으로 묶어도 문장마다 새 스냅숏이므로 이 보장은 사라진다.

RepositoryComposition은 조각을 앞에서부터 훑어 시그니처가 맞는 첫 메서드를 호출하고, 사용자 정의 조각은 SimpleJpaRepository보다 앞에 놓인다. 문서도 사용자 정의 구현이 기본 구현보다 우선한다고 적고 있고, 실험에서도 -1이 나왔다. 선언 순서는 사용자 정의 조각끼리의 우선순위를 정할 뿐이고, 모호성 오류는 나지 않는다. count()는 기본 클래스나 조각이 구현하므로 쿼리 메서드 후보가 아니다. 트랜잭션이 없는 상태에서 리포지토리의 다음 메서드를 각각 호출했다. 트랜잭션이 열리는 것은? (리포지토리 인터페이스와 조각에는 @Transactional이 없다) 메서드 이름 쿼리 findByName 사용자 정의 메서드 search 위의 둘 모두 상속한 findAll 트랜잭션 속성은 대상 클래스 SimpleJpaRepository와 메서드를 선언한 타입에서 @Transactional을 찾아 계산한다. findAll은 SimpleJpaRepository의 클래스 수준 @Transactional(readOnly = true)를 얻는다. findByName과 search는 SimpleJpaRepository에 없는 메서드이고 선언한 인터페이스에도 애노테이션이 없으므로 속성이 null이다. 문서도 선언한 쿼리 메서드에는 기본 트랜잭션 설정이 적용되지 않는다고 적고 있다. 전체 25행인 검색을 PageableExecutionUtils.getPage()로 페이징한다. count 쿼리가 실행되는 요청은? PageRequest.of(0, 30) PageRequest.of(2, 10) PageRequest.of(1, 10) 셋 모두 실행되지 않는다 (0, 30)은 첫 페이지에서 25행이 나와 크기 30보다 적으므로 전체 = 25로 확정된다. (2, 10)은 offset 20에서 5행이 나와 부분 페이지이고 비어 있지 않으므로 전체 = 20 + 5 = 25로 확정된다. (1, 10)은 offset 10에서 10행이 나와 페이지가 꽉 찼으므로 뒤에 더 있는지 알 수 없어 count를 실행한다. 내용 쿼리가 직원과 부서를 leftJoin하고(직원→부서는 다대일) 부서 이름을 DTO로 select한다. 검색 조건에 부서 관련 조건이 없을 때 count 쿼리에서 부서 조인을 빼도 되는 이유로 가장 정확한 것은? 다대일 외부 조인은 직원 행을 없애지도 늘리지도 않으므로 세는 행 집합이 같다. count 쿼리에서는 조인이 항상 무시되므로 넣든 빼든 같다. 부서 테이블이 직원 테이블보다 작으므로 조인 비용이 무시할 만하다. 외부 조인을 하면 NULL이 생기는데 count(*)는 NULL을 세지 않기 때문이다. 외부 조인이므로 부서가 없는 직원도 남고(행이 줄지 않음), 다대일이므로 한 직원에 부서가 최대 하나라 행이 늘지 않는다. 따라서 조인이 있든 없든 직원 행 집합은 같다. 조인이 항상 무시되는 것은 아니다. 내부 조인은 6, 일대다 외부 조인은 부풀린 값을 만들었다. count(*)는 NULL 포함 여부와 관계없이 행을 센다. 스프링 부트 기본 설정의 컨트롤러가 Pageable을 받는다. ?page=-5&size=9999 요청에서 만들어지는 Pageable은? 400 Bad Request 응답이 나가고 컨트롤러는 호출되지 않는다. 번호 -5, 크기 9999 번호 0, 크기 2000 번호 0, 크기 20 parseAndApplyBoundaries()는 음수 번호를 0으로 바꾸고, 크기는 max-page-size 기본값 2000으로 자른다. 파싱에 실패해도 오류 응답 대신 0을 쓰므로 400은 나지 않는다. 크기가 기본값 20으로 바뀌는 것은 1보다 작을 때다.
    JDK 동적 프록시(dynamic proxy)
    java.lang.reflect.Proxy가 실행 중에 만드는 클래스. 지정한 인터페이스를 구현하고, 모든 메서드 호출을 InvocationHandler.invoke()로 넘긴다.
    팩토리 빈(FactoryBean)
    스프링 컨테이너에 등록되어 다른 객체를 만들어 주는 빈. 빈 이름으로 요청하면 getObject()의 결과를, 이름 앞에 &를 붙이면 팩토리 자신을 준다.
    리포지토리 조각(repository fragment)
    리포지토리 인터페이스가 상속한 인터페이스 하나와 그 구현 객체의 묶음. 여러 조각이 RepositoryComposition으로 합쳐져 하나의 리포지토리가 된다.
    구현 접미사(implementation postfix)
    조각 구현 클래스를 찾을 때 인터페이스 이름 뒤에 붙이는 문자열. 기본값은 Impl이고 repositoryImplementationPostfix로 바꾼다.
    쿼리 메서드(query method)
    리포지토리 인터페이스에 선언만 하고, 메서드 이름이나 @Query로부터 스프링 데이터가 쿼리를 만들어 실행하는 메서드.
    Pageable / Page
    페이징 요청(번호, 크기, 정렬)과 그 결과(내용, 전체 개수, 페이지 정보)를 나타내는 스프링 데이터 타입. 대표 구현은 PageRequest와 PageImpl이다.
    키셋 페이징(keyset pagination)
    offset 대신 직전 페이지의 마지막 정렬 키보다 큰(또는 작은) 행을 조건으로 다음 페이지를 읽는 방식. 인덱스에서 시작 위치로 바로 찾아간다.
    PagedModel
    Spring Data 3.3에 추가된 org.springframework.data.web의 응답용 타입. Page를 감싸 content와 page(size, number, totalElements, totalPages)만으로 직렬화한다.
