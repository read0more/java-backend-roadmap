    HTTP는 문자열만 실어 온다

    HTTP 웹 기본 지식과 스프링 MVC 1편에서 본 것을 다시 떠올려 보자. 브라우저가 서버로 보내는 것은 TCP 연결 위를 흐르는 바이트이고, 서블릿 컨테이너는 그 바이트를 HTTP 메시지로 해석한다. 쿼리 스트링이든 application/x-www-form-urlencoded 본문이든 데이터는 이름=값 쌍의 텍스트이며, 퍼센트 인코딩을 풀고 나면 자바의 String이 된다. 그래서 HttpServletRequest.getParameter()의 반환 타입은 언제나 String이다. 사용자가 수량 칸에 10을 입력했어도 서버에 도착한 것은 숫자 10이 아니라 문자 '1'과 '0'의 나열이다. 회선 위에는 타입 정보가 없다.

    그런데 스프링 MVC 1편에서는 컨트롤러 파라미터에 @RequestParam Integer quantity라고 쓰기만 하면 정수가 들어왔다. 상품 폼을 @ModelAttribute로 받을 때도 price 필드는 Integer로 채워졌다. 누군가 중간에서 문자열을 정수로 바꾼 것이다. 이 회차의 질문은 그 "누군가"가 누구이고, 언제 호출되며, 어떤 규칙으로 변환기를 고르는가다. 반대 방향도 있다. 모델에 담긴 Integer 10000이나 LocalDate를 HTML로 그리려면 다시 문자열로 바꿔야 하고, 이때는 "10,000"이나 "25. 3. 1."처럼 사람이 읽는 형태, 그것도 사용자의 언어권에 맞는 형태가 필요하다.

    스프링 애플리케이션에서 이런 타입 변환이 일어나는 자리는 생각보다 많다. 요청 파라미터(@RequestParam), URL 경로 변수(@PathVariable), 폼 객체 바인딩(@ModelAttribute), 설정 값 주입(@Value), 그리고 뷰 렌더링이다. 정수나 불리언 같은 기본 타입은 스프링이 미리 준비한 변환기로 처리되지만, 애플리케이션이 직접 만든 타입은 사정이 다르다. 예를 들어 지도 서비스가 위치를 37.5665,126.9780(위도,경도) 같은 문자열로 주고받는다고 하자. 변환 장치가 없다면 컨트롤러마다 다음 코드를 반복해야 한다.

    @GetMapping("/places/near")
public String near(HttpServletRequest request) {
    String raw = request.getParameter("at");              // "37.5665,126.9780"
    String[] parts = raw.split(",");
    GeoPoint at = new GeoPoint(Double.parseDouble(parts[0]),
                               Double.parseDouble(parts[1]));
    // ... 형식이 틀렸을 때의 처리도 컨트롤러마다 따로 만들어야 한다
    return "places";
}

    파싱 코드가 흩어지면 형식이 바뀔 때 모든 곳을 고쳐야 하고, 잘못된 입력을 어떤 응답으로 돌려줄지도 컨트롤러마다 달라진다. 원하는 모습은 @RequestParam("at") GeoPoint at이라고 선언만 하고, "문자열을 GeoPoint로 바꾸는 방법"은 한 곳에 한 번만 등록해 두는 것이다. 그 한 곳이 스프링의 타입 변환 시스템, 곧 Converter와 ConversionService이고, 문자열과 로케일을 다루도록 특화한 것이 Formatter다.

    실험 환경

    스프링 MVC와 타임리프를 함께 쓰려면 Spring Boot 프로젝트에 spring-boot-starter-web과 spring-boot-starter-thymeleaf를 넣으면 된다. 다만 이 회차의 주인공들은 웹 모듈에 있지 않다. Converter와 ConversionService는 spring-core의 org.springframework.core.convert 패키지에, Formatter와 FormattingConversionService는 spring-context의 org.springframework.format 패키지에 있다. 웹 바깥에서도 쓰이는 범용 장치라는 뜻이다. 그래서 이 회차의 예제 대부분은 서버 없이 main()으로 돌린다. 예제는 JDK 21(Temurin 21.0.13)과 Spring Framework 7.0.10의 spring-core·spring-beans·spring-context jar로 직접 실행한 결과이며, 본문이 근거로 삼은 내부 규칙은 기준 버전인 Spring Framework 6.1.x 소스에서도 같은지 확인했다. 7.x 소스에는 JSpecify의 @Nullable이 타입에 붙어 있지만 동작은 같다.

    HTTP 요청의 문자열이 컨버전 서비스를 거쳐 자바 객체가 되고, 렌더링 때 다시 같은 서비스를 거쳐 문자열이 되는 왕복을 한 화면에 보여 준다. 왼쪽에서 오른쪽으로 흐르는 가로 흐름도. 맨 왼쪽에 브라우저 아이콘과 말풍선 "at=37.5665,126.9780". 화살표가 가운데의 큰 둥근 사각형 "ConversionService"로 들어가고, 그 안에 작은 카드 세 장 "Converter", "Formatter", "기본 컨버터"가 겹쳐 있다. 위쪽 경로 화살표 라벨 "요청: 문자열 → 객체", 오른쪽 위 상자 "컨트롤러 파라미터 GeoPoint". 오른쪽 상자에서 아래로 내려온 화살표가 "모델"을 지나 다시 가운데 ConversionService로 돌아오고, 아래쪽 경로 화살표 라벨 "응답: 객체 → 문자열". 맨 왼쪽 아래에 HTML 문서 아이콘과 텍스트 "37.5665,126.978". 평면 일러스트, 흰 배경, 파란색과 주황색 두 가지 강조색. 같은 컨버전 서비스가 요청 쪽(문자열→객체)과 렌더링 쪽(객체→문자열)을 모두 맡는다.

    컨버전 서비스 이전: PropertyEditor와 그 한계

    스프링이 처음부터 지금의 변환 시스템을 가졌던 것은 아니다. 초기 스프링은 자바빈즈(JavaBeans) 명세의 java.beans.PropertyEditor로 문자열을 객체로 바꿨다. 이 인터페이스는 원래 GUI 빌더의 속성 편집 창을 위해 만들어졌고, 핵심 메서드는 setAsText(String), getValue(), setValue(Object), getAsText()다. 변환 결과를 반환값으로 돌려주지 않고 편집기 객체 안에 저장해 두었다가 꺼내 가는 구조라는 점이 중요하다.

    import java.beans.PropertyEditorSupport;

public class GeoPointEditor extends PropertyEditorSupport {

    @Override
    public void setAsText(String text) {
        String[] parts = text.split(",");
        setValue(new GeoPoint(Double.parseDouble(parts[0].trim()),
                              Double.parseDouble(parts[1].trim())));
    }
}

// 사용하는 쪽
GeoPointEditor editor = new GeoPointEditor();
editor.setAsText("37.5,127.0");          // ① 편집기의 내부 상태를 바꾼다
GeoPoint p = (GeoPoint) editor.getValue(); // ② 그 상태를 읽는다

    ①과 ②가 두 번의 호출로 나뉘어 있고, 그 사이의 결과는 PropertyEditorSupport 안의 필드에 들어 있다. 상태를 가진(stateful) 객체이므로 여러 스레드가 하나의 편집기를 공유하면 결과가 섞인다. 서블릿 컨테이너는 요청마다 스레드 풀의 스레드 하나를 배정하므로, 싱글톤 편집기 하나를 모든 요청이 함께 쓰면 다음과 같은 일이 일어날 수 있다.

    요청 스레드 A                     공유된 GeoPointEditor.value        요청 스레드 B
---------------------------------------------------------------------------------------
setAsText("37.5,127.0")   ──▶   GeoPoint(37.5, 127.0)
                                 GeoPoint(35.1, 129.0)   ◀──   setAsText("35.1,129.0")
getValue()                ◀──   GeoPoint(35.1, 129.0)          (A가 B의 값을 받는다)
                                                         ──▶   getValue()

    그래서 스프링의 BeanWrapper와 DataBinder는 편집기를 공유하지 않고 인스턴스마다 따로 가진다. 기본 편집기 묶음도 PropertyEditorRegistrySupport의 인스턴스 필드에 처음 필요할 때 만들어 담는다. 스프링 MVC는 요청마다 바인더를 새로 만들기 때문에 결국 편집기도 요청마다 새로 생긴다. 안전하지만, 변환 로직이 상태를 가질 이유가 전혀 없는데도 객체를 계속 만들어야 하는 구조다. 게다가 PropertyEditor는 "문자열 ↔ 객체"만 다룬다. Long을 Instant로, 엔티티 ID를 엔티티로 바꾸는 것처럼 문자열이 끼지 않는 변환은 표현할 수 없다.

    Spring Framework 3.0에서 이 문제를 풀기 위해 org.springframework.core.convert 패키지가 들어왔다(Converter와 ConversionService의 Javadoc에 @since 3.0이 적혀 있다). 상태 없는 변환기를 한 번 만들어 모든 스레드가 공유하고, 임의의 타입 쌍을 다룬다. 다만 PropertyEditor가 사라진 것은 아니다. 스프링 공식 문서는 ConversionService가 등록되어 있지 않으면 원래의 PropertyEditor 기반 시스템이 쓰인다고 적고 있고, 뒤에서 보듯 컨트롤러의 @InitBinder로 등록한 사용자 정의 편집기는 지금도 컨버전 서비스보다 먼저 시도된다.

    Converter: 한 방향, 한 쌍의 변환

    새 시스템의 기본 단위는 org.springframework.core.convert.converter.Converter다. 널 관련 애노테이션을 빼고 보면 선언은 다음과 같다.

    @FunctionalInterface
public interface Converter {

    T convert(S source);

    // 5.3부터: 이 변환 결과를 다른 변환기로 이어 붙인다
    default  Converter andThen(Converter after) {
        // ...
    }
}

    원본 타입 S를 받아 대상 타입 T를 돌려주는 메서드 하나가 전부다. PropertyEditor와 달리 결과를 반환값으로 돌려주므로, 구현이 필드를 쓰지만 않는다면 상태가 없다. 공식 문서는 구현이 스레드 안전(thread-safe)해야 하며, 원본 값이 잘못되었을 때는 IllegalArgumentException을 던지라고 요구한다. 또 하나의 약속이 있다. 원본이 null인 경우는 변환기까지 오지 않는다. 등록된 변환기를 감싸는 ConverterAdapter가 source == null이면 변환기를 부르지 않고 대상 타입이 Optional이면 Optional.empty()를, 아니면 null을 돌려준다. 그래서 convert() 안에서 널 검사를 할 필요가 없다.

    위치 타입과 두 방향의 변환기를 만들어 보자. 변환기는 한 방향만 다루므로 양방향이 필요하면 두 개를 만든다. 이름은 원본To대상으로 짓는 것이 스프링 내부 클래스들의 관례다.

    public record GeoPoint(double lat, double lng) {}
    import org.springframework.core.convert.converter.Converter;

public class StringToGeoPointConverter implements Converter {

    @Override
    public GeoPoint convert(String source) {
        String[] parts = source.split(",");
        if (parts.length != 2) {
            throw new IllegalArgumentException("위도,경도 형식이 아니다: " + source);
        }
        double lat = Double.parseDouble(parts[0].trim());
        double lng = Double.parseDouble(parts[1].trim());
        return new GeoPoint(lat, lng);
    }
}
    import org.springframework.core.convert.converter.Converter;

public class GeoPointToStringConverter implements Converter {

    @Override
    public String convert(GeoPoint source) {
        return source.lat() + "," + source.lng();
    }
}

    두 변환기 모두 필드가 없다. 인스턴스 하나를 여러 요청 스레드가 동시에 호출해도 각 호출의 지역 변수(parts, lat, lng)는 호출한 스레드의 스택 프레임에 따로 생기므로 서로 간섭하지 않는다. Double.parseDouble이 형식이 틀린 문자열에 던지는 NumberFormatException은 IllegalArgumentException의 하위 클래스라서 계약도 지킨다. 한 가지 눈여겨볼 점은 문자열 왕복이 항등이 아니라는 것이다. "126.9780"을 double로 바꾼 뒤 다시 문자열로 만들면 Double.toString 규칙에 따라 "126.978"이 된다. 객체 → 문자열 → 객체는 같은 값을 돌려주지만 문자열 → 객체 → 문자열은 표기가 바뀔 수 있다. 폼에 다시 표시되는 값이 사용자가 입력한 글자와 다를 수 있다는 뜻이다.

    이 변환기를 직접 new StringToGeoPointConverter().convert("...")로 불러 쓸 수도 있지만, 그러면 처음의 파싱 코드를 클래스로 옮긴 것에 지나지 않는다. 변환기의 가치는 중앙의 등록소에 넣어 두고, 변환이 필요한 쪽은 "이 값을 이 타입으로 바꿔 달라"고만 요청하는 데서 나온다. 그런데 등록소가 변환기를 받아 색인하려면 이 변환기가 어떤 타입에서 어떤 타입으로 바꾸는지 알아야 한다. 자바의 제네릭은 컴파일 후에 지워진다고 배웠는데, 스프링은 이것을 어떻게 알아낼까?

    한 층 아래: 지워진 제네릭을 스프링은 어떻게 읽는가

    컨버전 서비스의 등록 메서드는 addConverter(Converter converter) 형태로, 변환기 객체 하나만 받는다. 실행 시점의 객체에는 타입 인자가 붙어 있지 않다. 자바의 제네릭은 소거(type erasure) 방식이라서 메서드 디스크립터에서 타입 변수는 상한 타입(여기서는 Object)으로 바뀐다. 컴파일된 StringToGeoPointConverter를 javap -c -p로 열어 보면 이 사실이 그대로 드러난다.

JVMS 4장의 메서드 플래그 표는 ACC_BRIDGE(0x0040)를 컴파일러가 생성한 브리지 메서드라고 정의한다. 인터페이스 Converter의 convert는 소거 후 (Ljava/lang/Object;)Ljava/lang/Object;라는 디스크립터를 가지므로, 인터페이스를 통해 부르는 코드는 이 디스크립터로 호출한다. 실제로 Converter 타입 변수로 convert("1,2")를 부르는 메서드를 컴파일하면 invokeinterface ... Converter.convert:(Ljava/lang/Object;)Ljava/lang/Object;가 나온다. JVM은 이 호출을 브리지 메서드로 연결하고, 브리지는 인자를 checkcast로 String으로 확인한 뒤 진짜 메서드를 invokevirtual로 부른다.

    이 구조 덕분에 컨버전 서비스는 모든 변환기를 Converter로 다룰 수 있다. 실제로 GenericConversionService의 ConverterAdapter는 등록된 변환기를 Converter로 형변환해 필드에 보관하고 this.converter.convert(source)로 부른다. 그 대가로 타입 검사는 실행 시점의 checkcast로 미뤄진다. 원시 타입(raw type)으로 정수를 넘기면 컴파일러는 경고만 하고 넘어가지만, 실행하면 브리지의 checkcast에서 다음 예외가 난다.

    class java.lang.Integer cannot be cast to class java.lang.String (java.lang.Integer and java.lang.String are in module java.base of loader 'bootstrap')

    그렇다면 타입 인자 는 어디에 남아 있을까? 소거는 메서드 디스크립터와 바이트코드에서 타입 인자를 지우지만, 클래스·필드·메서드 선언의 제네릭 정보는 클래스 파일의 Signature 속성(JVMS §4.7.9, 클래스 파일 버전 49.0, 곧 Java SE 5.0부터)에 따로 기록된다. javap -v의 마지막 부분에 다음 줄이 있다.

    Signature: #55    // Ljava/lang/Object;Lorg/springframework/core/convert/converter/Converter;

    Converter만으로 부족할 때: ConverterFactory와 GenericConverter

    Converter는 정확히 한 쌍만 다룬다. 그런데 "문자열을 아무 열거형(enum)으로"나 "문자열을 아무 Number 하위 타입으로" 같은 변환을 대상 타입마다 하나씩 등록하는 것은 불가능하다. 열거형은 애플리케이션이 계속 새로 만들기 때문이다. 이런 계층 단위의 변환을 위해 ConverterFactory가 있다. 이 인터페이스의 메서드는 Converter getConverter(Class targetType) 하나이며, 대상 타입을 받아 그 타입 전용 변환기를 만들어 준다. 공식 문서도 클래스 계층 전체의 변환 로직을 한곳에 모아야 할 때(예: String에서 Enum으로) 쓰라고 설명한다. 스프링의 StringToEnumConverterFactory와 StringToNumberConverterFactory가 대표적이다. 후자는 (String, Number) 쌍으로 한 번만 등록되지만 Integer, Long, BigDecimal 등 모든 숫자 타입을 처리한다.

    GenericConverter는 가장 일반적인 형태다. Set getConvertibleTypes()로 다룰 수 있는 쌍을 여러 개 선언하고, convert(Object source, TypeDescriptor sourceType, TypeDescriptor targetType)로 변환한다. 핵심은 TypeDescriptor다. 이 객체는 Class만이 아니라 제네릭 타입 인자와 애노테이션까지 담는다. 예를 들어 "1,2,3"을 List로 바꾸는 StringToCollectionConverter는 대상 TypeDescriptor에서 원소 타입이 Integer라는 것을 읽고, 쉼표로 나눈 조각 하나하나를 다시 컨버전 서비스에 맡겨 정수로 바꾼다. 필드에 붙은 @NumberFormat을 보고 형식을 고르는 것도 TypeDescriptor가 애노테이션을 실어 나르기 때문에 가능하다. 공식 문서는 GenericConverter가 더 복잡한 SPI이므로 꼭 필요할 때만 쓰고 기본 변환에는 Converter나 ConverterFactory를 쓰라고 권한다.

    ConditionalGenericConverter는 GenericConverter에 matches(TypeDescriptor, TypeDescriptor) 조건을 더한 것이다. 쌍이 맞더라도 조건이 거짓이면 다음 후보로 넘어간다. 흥미로운 예가 기본 등록되는 ObjectToObjectConverter다. Javadoc에 적힌 알고리즘은 이렇다. 원본 객체에 to대상타입이름() 메서드가 있으면 그것을 부르고, 없으면 대상 타입의 정적 valueOf(원본)·of(원본)·from(원본) 메서드를, 그것도 없으면 원본 하나를 받는 생성자를 리플렉션으로 호출한다. matches()는 그런 메서드나 생성자가 있는지를 검사한다.

    ConversionService: 등록하는 쪽과 쓰는 쪽을 나눈다

    변환기들을 모아 두고 "이 값을 저 타입으로"라는 요청을 처리하는 것이 ConversionService다. 이 인터페이스에는 canConvert(...)와 convert(...)만 있고, 변환기를 넣는 메서드는 없다. 등록은 별도의 ConverterRegistry 인터페이스(addConverter, addConverterFactory, removeConvertible)가 맡는다. 둘을 합친 것이 ConfigurableConversionService이고, 그 구현이 GenericConversionService, 여기에 기본 변환기를 미리 채운 것이 DefaultConversionService다. 계층을 그리면 다음과 같다.

    이제 실제로 써 보자. 앞에서 만든 두 변환기를 등록하고, 기본 변환기의 동작도 함께 확인한다.

    ⑤는 사용자 정의 변환기를 등록하기 전이라 false이고, ⑥과 ⑦은 등록한 변환기가 동작한 결과다. ⑦에서 "126.978"이 나오는 것은 앞에서 말한 Double.toString 표기 때문이다. ⑧에서 정수 변환기는 쉼표를 모르므로 Integer 파싱 중에 NumberFormatException이 난다. 그런데 바깥으로 나온 예외는 ConversionFailedException이다. 컨버전 서비스는 변환기를 직접 부르지 않고 ConversionUtils.invokeConverter()를 거치는데, 이 메서드가 ConversionFailedException이 아닌 모든 Throwable을 잡아 원본 타입, 대상 타입, 원본 값을 담은 ConversionFailedException으로 감싼다. 변환기 작성자가 어떤 예외를 던지든 호출하는 쪽은 한 종류의 예외만 다루면 된다. 사람이 읽는 "1,000"을 받으려면 정수 변환기가 아니라 뒤에서 볼 포맷터가 필요하다.

    원본이 null인 경우도 짚어 두자. 대상이 참조 타입이면 결과는 null이다. 대상이 int 같은 기본 타입이면 null을 담을 수 없으므로 GenericConversionService가 "A null value cannot be assigned to a primitive type"을 원인으로 하는 ConversionFailedException을 던진다. 웹 요청에서 기본 타입 파라미터의 값이 아예 오지 않은 경우는 이보다 앞에서 인자 리졸버가 따로 검사하는데, 이것은 함정 절에서 다시 본다.

    GenericConversionService 안에서 컨버터를 고르는 규칙

    등록된 변환기는 GenericConversionService 내부의 Converters 객체에 들어간다. 자료 구조는 단순하다. (원본 클래스, 대상 클래스)를 묶은 ConvertiblePair를 키로, 그 쌍을 다루는 변환기 목록 ConvertersForPair를 값으로 하는 ConcurrentHashMap이 하나 있다. 그리고 getConvertibleTypes()가 null을 돌려주는 조건부 변환기들은 쌍과 무관하게 globalConverters라는 CopyOnWriteArraySet에 들어간다. Converter는 ConverterAdapter로, ConverterFactory는 ConverterFactoryAdapter로 감싸져 모두 GenericConverter 모양으로 저장된다.

    ConvertersForPair의 목록은 ConcurrentLinkedDeque이고, 추가는 addFirst()로 한다. 같은 쌍에 변환기가 여럿이면 나중에 등록한 것이 앞에 선다. 앞의 RegistrationDemo에서 ②의 람다 뒤에 ③의 StringToGeoPointConverter를 같은 (String, GeoPoint) 쌍으로 등록하자 결과가 GeoPoint[lat=0.0, lng=0.0]에서 GeoPoint[lat=37.5, lng=127.0]로 바뀐 것이 이 규칙이다. 이 규칙은 사용자 정의 변환기가 기본 변환기를 덮어쓸 수 있는 근거이기도 하다. 기본 변환기는 컨버전 서비스의 생성자에서 먼저 등록되고, 애플리케이션의 변환기는 그 뒤에 등록되기 때문이다.

    변환 요청이 오면 getConverter(sourceType, targetType)가 다음 순서로 움직인다.

String -> [String, Serializable, Comparable, CharSequence, Constable, ConstantDesc, Object]
int -> [Integer, Number, Comparable, Constable, ConstantDesc, Serializable, Object]

    상위 클래스는 현재 후보 바로 뒤에 끼워 넣고 인터페이스는 목록 끝에 붙이기 때문에, Integer의 상위 클래스 Number가 Integer의 인터페이스들보다 앞에 오고 Number가 구현하는 Serializable은 그 뒤에 온다. 인터페이스 순서는 JDK 소스의 implements 선언 순서를 따른다. "7"을 Integer로 바꾸는 요청이라면 탐색은 (String, Integer), (String, Number), (String, Comparable) … (String, Object)를 먼저 모두 보고, 그다음에야 (Serializable, Integer)로 넘어간다. 원본 타입의 구체성이 대상 타입의 구체성보다 우선한다.

ConverterAdapter.matches()의 첫 줄이 this.typeInfo.getTargetType() != targetType.getObjectType()이면 false를 돌려주기 때문이다. Converter는 대상 타입이 정확히 T일 때만 쓰인다. 대상이 Number인 요청에서는 정확히 일치하므로 호출되었다. 반면 ConverterFactoryAdapter에는 이 검사가 없어서 같은 칸의 StringToNumberConverterFactory가 선택되고, 결과는 7이다. "Converter를 만들면 모든 숫자 타입에 적용되겠지"라는 기대는 틀린다. 계층 전체를 맡기려면 ConverterFactory를 써야 한다. 뒤에서 볼 포맷터는 또 다르게 동작하니 함께 기억해 두자.

    마지막으로 동시성이다. 변환 요청은 요청 스레드 수십 개에서 동시에 들어온다. 맵은 ConcurrentHashMap, 쌍별 목록은 ConcurrentLinkedDeque, 전역 목록은 CopyOnWriteArraySet, 캐시는 ConcurrentReferenceHashMap이라서 조회가 서로를 막지 않는다. 등록은 캐시를 통째로 비우므로 실행 중에 자주 하면 모든 조회가 다시 탐색을 해야 한다. 등록은 시작할 때 끝내고 이후에는 읽기만 한다는 설계 의도가 자료 구조에서도 드러난다.

    원본 타입 계층(세로)과 대상 타입 계층(가로)이 만드는 격자를 위에서 아래, 왼쪽에서 오른쪽으로 훑으며 첫 번째로 맞는 변환기를 고르는 과정을 보여 준다. 격자 표 그림. 세로 축 제목 "원본 계층", 행 라벨 위에서부터 "String", "Serializable", "Object". 가로 축 제목 "대상 계층", 열 라벨 왼쪽부터 "Integer", "Number", "Object". 첫 행 첫 칸은 비어 있는 회색 칸. 첫 행 둘째 칸에 카드 두 장이 세로로 쌓여 있다: 위 카드 "Converter"에 빨간 X 표시와 작은 말풍선 "대상 정확 일치 아님", 아래 카드 "ConverterFactory"에 초록 체크 표시. 첫 행 왼쪽에서 오른쪽으로 점선 화살표가 지나가며 둘째 칸에서 멈춘다. 위쪽에 작은 라벨 "나중 등록이 앞에". 오른쪽 아래 구석에 작은 상자 "캐시". 평면 스타일, 흰 배경. 원본 계층을 바깥 반복으로, 대상 계층을 안쪽 반복으로 훑는다. 같은 칸에서는 나중에 등록한 변환기가 먼저 검사된다.

    스프링 MVC에 컨버터 적용하기

    이제 웹으로 돌아오자. 스프링 MVC에 변환기를 등록하는 공식 통로는 WebMvcConfigurer의 addFormatters(FormatterRegistry registry)다. 이름에 포맷터가 들어 있지만 FormatterRegistry는 ConverterRegistry를 상속하므로 변환기도 여기서 넣는다.

Spring Boot를 쓴다면 설정 클래스 없이 변환기를 빈으로 등록하기만 해도 된다. Spring Boot 레퍼런스는 스프링 MVC 자동 구성 기능으로 Converter, GenericConverter, Formatter 빈의 자동 등록을 명시한다. 내부적으로는 Boot의 WebMvcAutoConfigurationAdapter.addFormatters()가 ApplicationConversionService.addBeans(registry, beanFactory)를 불러 빈 팩토리에서 이런 타입의 빈을 찾아 등록한다.

    그 registry는 어디서 왔을까? 스프링 MVC 설정의 뼈대인 WebMvcConfigurationSupport에는 mvcConversionService라는 빈 메서드가 있고, 기본 구현은 DefaultFormattingConversionService를 만든 뒤 addFormatters(conversionService)를 부른다. @EnableWebMvc가 쓰는 DelegatingWebMvcConfiguration은 이 addFormatters를 등록된 모든 WebMvcConfigurer에 위임한다. Spring Boot는 이 빈 메서드를 덮어써서 WebConversionService(DefaultFormattingConversionService의 하위 클래스)를 만들고, 날짜 형식 설정을 반영한 기본 포맷터를 생성자에서 등록한 뒤 addFormatters를 부른다. 어느 쪽이든 기본 변환기가 먼저, 사용자 변환기가 나중에 들어가므로 앞 절의 addFirst 규칙에 따라 같은 쌍에서는 사용자 변환기가 이긴다.

    요청 하나가 변환기에 닿기까지

    컨트롤러 메서드의 파라미터 값은 핸들러 어댑터가 호출 직전에 파라미터마다 맞는 HandlerMethodArgumentResolver를 골라 만든다(스프링 MVC 1편에서 본 구조다). @RequestParam을 처리하는 RequestParamMethodArgumentResolver와 @PathVariable을 처리하는 PathVariableMethodArgumentResolver는 모두 AbstractNamedValueMethodArgumentResolver를 상속하고, 변환은 이 부모 클래스의 convertIfNecessary()에서 일어난다.

    바인더는 요청마다, 그것도 변환이 필요한 파라미터마다 새로 만들어진다. 반면 그 안에 꽂히는 컨버전 서비스는 애플리케이션 전체에 하나뿐인 싱글톤이다. 상태를 가질 수 있는 바인더(바인딩 결과, 사용자 정의 편집기)는 요청 범위로 짧게 살고, 상태 없는 변환 로직은 길게 살며 공유된다. 앞에서 본 PropertyEditor의 동시성 문제를 이 분리가 해결한다. 같은 이유로 @InitBinder에서 binder.registerCustomEditor(...)로 편집기를 등록하는 것은 지금도 안전하다. 그 편집기는 그 요청의 그 바인더만 쓴다. 그리고 4단계의 순서 때문에, 어떤 타입에 사용자 정의 편집기와 변환기가 함께 있으면 편집기가 이긴다.

    변환이 실패하면

    GET /places/near?at=abc를 보내 보자. 변환기가 IllegalArgumentException을 던지고, 컨버전 서비스가 이것을 ConversionFailedException으로 감싼다. TypeConverterDelegate는 이 예외를 잠시 보관하고 기본 편집기로 한 번 더 시도하는데, GeoPoint용 편집기는 없으므로 보관한 예외를 다시 던진다. 바인더의 상위 클래스 TypeConverterSupport는 ConversionException과 IllegalArgumentException을 TypeMismatchException으로, ConverterNotFoundException과 IllegalStateException을 ConversionNotSupportedException으로 바꾼다. 리졸버는 이것을 다시 MethodArgumentTypeMismatchException이나 MethodArgumentConversionNotSupportedException으로 감싸 던진다. 어떤 HTTP 상태 코드가 나가는지는 8·9회의 예외 처리 주제에서 등장하는 스프링 기본 예외 처리기 DefaultHandlerExceptionResolver가 정한다.

    상황리졸버가 던지는 예외DefaultHandlerExceptionResolver의 응답
    변환기가 있는데 값이 잘못됨 (at=abc)MethodArgumentTypeMismatchException (TypeMismatchException의 하위 클래스)400 Bad Request
    변환기 자체가 없음 (등록을 잊음)MethodArgumentConversionNotSupportedException (ConversionNotSupportedException의 하위 클래스)500 Internal Server Error

    두 경우가 다른 상태 코드를 받는 데는 이유가 있다. 앞의 것은 클라이언트가 형식에 맞지 않는 값을 보낸 것이고, 뒤의 것은 서버가 그 타입을 다룰 준비를 하지 않은 프로그래밍 오류다. 변환기 등록을 잊으면 사용자는 400이 아니라 500을 받는다. 한 가지 주의할 것은 ConversionNotSupportedException이 TypeMismatchException을 상속한다는 점이다. 그래서 DefaultHandlerExceptionResolver는 ConversionNotSupportedException을 먼저 검사한다. 예외 처리기를 직접 만들 때 TypeMismatchException만 잡으면 두 경우를 구분하지 못한다.

    @ModelAttribute 폼 객체는 경로가 조금 다르다. ModelAttributeMethodProcessor가 바인더를 만들고 bind()를 부르면, 바인더는 대상 객체를 감싼 BeanWrapper로 요청 파라미터를 프로퍼티마다 설정한다. 프로퍼티 값 변환은 같은 TypeConverterDelegate가 하므로 컨버전 서비스도 같다. 다른 것은 실패 처리다. 예외를 던지는 대신 실패를 BindingResult에 FieldError로 기록한다. 4회에서 본 바로 그 동작을 서버 없이 DataBinder로 재현해 보자.

    public class Shop {

    DispatcherServlet에서 사용자 변환기까지의 호출이 어떤 객체들을 거치는지, 요청마다 새로 생기는 객체와 공유되는 싱글톤을 구분해 보여 준다. 가로 시퀀스 다이어그램. 위쪽에 왼쪽부터 생명선 일곱 개: "DispatcherServlet", "HandlerAdapter", "ArgumentResolver", "WebDataBinder", "TypeConverterDelegate", "ConversionService", "StringToGeoPointConverter". "WebDataBinder" 머리 상자는 주황색이고 그 아래 작은 라벨 "요청마다 새로 생성". "ConversionService"와 "StringToGeoPointConverter" 머리 상자는 파란색이고 라벨 "싱글톤, 공유". 화살표는 왼쪽에서 오른쪽으로 차례대로: "handle()", "resolveArgument()", "createBinder()", "convertIfNecessary()", "convert()", "convert(String)". 마지막 생명선에서 왼쪽으로 돌아오는 점선 반환 화살표 라벨 "GeoPoint". 흰 배경, 깔끔한 선. 바인더는 요청마다 새로 만들어지고, 그 안에 꽂힌 컨버전 서비스와 변환기는 모든 요청이 공유한다.

    뷰 템플릿에 컨버터 적용하기

    타임리프는 스프링의 컨버전 서비스를 어떻게 찾는가

    타임리프는 스프링과 별개의 라이브러리이므로, 템플릿을 렌더링하는 시점에 스프링 MVC의 컨버전 서비스를 받아 올 통로가 필요하다. 그 통로는 요청 속성(request attribute)이다. WebMvcConfigurationSupport는 핸들러 매핑에 인터셉터를 붙일 때 사용자가 등록한 인터셉터 뒤에 ConversionServiceExposingInterceptor를 항상 추가한다. 이 인터셉터는 preHandle()에서 request.setAttribute(ConversionService.class.getName(), conversionService)를 한다. thymeleaf-spring6의 ThymeleafView는 렌더링할 때 같은 이름의 요청 속성에서 컨버전 서비스를 꺼내(소스 주석에 "might be null!"이라고 적혀 있다) ThymeleafEvaluationContext를 만들고, 이 평가 컨텍스트를 모델 변수에 넣는다. 두 겹 중괄호 변수 식을 평가하는 SPELVariableExpressionEvaluator는 설정된 변환 서비스가 SpringStandardConversionService이면 SpEL 식을 getValue(평가 컨텍스트, 루트, String.class)로 평가하고, 이때 문자열 변환은 평가 컨텍스트의 타입 변환기, 곧 ThymeleafEvaluationContext가 꺼내 온 컨버전 서비스로 만든 StandardTypeConverter가 맡는다.

    Formatter: 문자열과 로케일을 위한 변환

    지금까지의 Converter는 임의의 두 타입 사이를 잇는 범용 장치다. 그런데 웹 애플리케이션에서 일어나는 변환의 대부분은 특정한 모양을 가진다. 요청을 받을 때는 문자열을 객체로, 화면을 그릴 때는 객체를 문자열로 바꾸고, 그 문자열은 사용자의 언어권에 맞아야 한다. 한국과 미국에서는 1234567을 "1,234,567"로 쓰지만 독일에서는 "1.234.567"로 쓴다. 스프링 공식 문서는 범용 Converter SPI가 이런 포맷 요구를 직접 다루지 않기 때문에 Formatter SPI를 제공한다고 설명하고, 일반 타입 변환에는 Converter를, 웹 같은 클라이언트 환경에서 지역화된 필드 값을 파싱·출력할 때는 Formatter를 쓰라고 정리한다.

    package org.springframework.format;

public interface Formatter extends Printer, Parser {
}

public interface Printer {
    String print(T object, Locale locale);
}

public interface Parser {
    T parse(String text, Locale locale) throws ParseException;
}

    Converter와 세 가지가 다르다. 한쪽 타입이 String으로 고정되어 있고, 한 객체가 출력(print)과 파싱(parse) 양방향을 맡으며, 두 메서드 모두 Locale을 받는다. 파싱이 실패하면 ParseException이나 IllegalArgumentException을 던지라는 것이 문서의 계약이고, 스레드 안전해야 한다는 요구도 같다. 로케일에 따라 숫자를 묶음 표기하는 포맷터를 만들어 보자.

    import java.text.NumberFormat;
import java.text.ParseException;
import java.util.Locale;
import org.springframework.format.Formatter;

public class LocalizedNumberFormatter implements Formatter {

    @Override
    public Number parse(String text, Locale locale) throws ParseException {
        return NumberFormat.getNumberInstance(locale).parse(text);
    }

    @Override
    public String print(Number object, Locale locale) {
        return NumberFormat.getNumberInstance(locale).format(object);
    }
}

    메서드를 호출할 때마다 NumberFormat을 새로 만드는 데는 이유가 있다. JDK의 NumberFormat Javadoc은 숫자 포맷이 일반적으로 동기화되어 있지 않으며, 여러 스레드가 동시에 접근하려면 외부에서 동기화해야 한다고 적는다. 포맷터 인스턴스는 컨버전 서비스 안에서 모든 요청 스레드가 공유하므로, NumberFormat을 필드에 두고 재사용하면 동시 요청에서 결과가 깨질 수 있다. 앞에서 본 PropertyEditor의 문제가 포맷터 안에서 되살아나는 셈이다. 이제 이 포맷터를 DefaultFormattingConversionService에 넣고 로케일을 바꿔 가며 써 보자.

    import java.util.Locale;
import org.springframework.context.i18n.LocaleContextHolder;
import org.springframework.format.support.DefaultFormattingConversionService;

public class FormatterDemo {
    public static void main(String[] args) {
        DefaultFormattingConversionService fcs = new DefaultFormattingConversionService();
        fcs.addFormatter(new LocalizedNumberFormatter());

        for (Locale locale : new Locale[] {Locale.KOREA, Locale.GERMANY, Locale.US}) {
            LocaleContextHolder.setLocale(locale);
            System.out.println(locale + " -> " + fcs.convert(1234567, String.class));
        }

        LocaleContextHolder.setLocale(Locale.KOREA);
        Integer price = fcs.convert("12,500", Integer.class);
        System.out.println(price + " (" + price.getClass().getSimpleName() + ")");
        System.out.println(fcs.convert("   ", Integer.class));
        System.out.println(fcs.convert("12abc", Integer.class));

        LocaleContextHolder.setLocale(Locale.GERMANY);
        System.out.println(fcs.convert("12,500", Double.class));
    }
}

    세 가지를 눈여겨보자. 첫째, convert()에 로케일을 넘긴 적이 없는데 출력이 로케일마다 다르다. 포맷터에 전달되는 로케일은 LocaleContextHolder에서 온다. 둘째, Formatter로 등록했는데 Integer 요청에 쓰였고, 결과도 정확히 Integer다. 앞 절에서 Converter는 Integer 요청에 쓰이지 않았던 것과 대조된다. 셋째, "12abc"가 오류 없이 12가 되었다. 이 셋은 각각 로케일 전달 경로, FormattingConversionService의 어댑터 구조, NumberFormat의 파싱 규칙에서 나온다. 차례로 내려가 보자.

    로케일은 어디에서 오는가: 요청 스레드의 ThreadLocal

    LocaleContextHolder는 정적 메서드만 가진 클래스이고, 내부에 ThreadLocal 필드(이름이 "LocaleContext"인 NamedThreadLocal)를 둔다. ThreadLocal은 스레드마다 따로 값을 보관하는 변수다. JDK 구현에서는 각 Thread 객체가 threadLocals라는 자기 맵(ThreadLocal.ThreadLocalMap)을 갖고, ThreadLocal 객체는 그 맵의 키 역할을 한다. 그래서 같은 정적 필드라도 요청 스레드 A에서 읽으면 A의 로케일이, B에서 읽으면 B의 로케일이 나온다. 포맷터 메서드에 로케일 파라미터를 일일이 전달하지 않아도 각 요청의 로케일이 섞이지 않는 이유다.

    값을 넣는 쪽은 DispatcherServlet의 상위 클래스 FrameworkServlet이다. processRequest()는 먼저 이 스레드에 있던 이전 LocaleContext를 지역 변수에 보관하고, buildLocaleContext(request)로 이 요청의 로케일 컨텍스트를 만들어 LocaleContextHolder에 넣은 뒤 doService()를 부른다. 그리고 finally 블록에서 보관해 둔 이전 값으로 되돌린다. DispatcherServlet의 buildLocaleContext()는 3회에서 본 LocaleResolver에 로케일을 묻고, 기본 전략인 AcceptHeaderLocaleResolver는 Accept-Language 요청 헤더를 본다. 컨트롤러 호출과 뷰 렌더링이 모두 doService() 안에서 일어나므로, 파라미터 파싱과 두 겹 중괄호 출력이 같은 요청 로케일을 쓴다.

    finally에서 되돌리는 단계가 중요한 이유는 서블릿 컨테이너가 스레드를 풀에서 재사용하기 때문이다. 정리하지 않으면 다음 요청을 받은 같은 스레드가 이전 사용자의 로케일을 그대로 보게 된다. 반대로 요청 스레드가 아닌 곳, 예를 들어 스케줄러 스레드나 직접 만든 스레드에서 포맷터를 부르면 LocaleContextHolder에는 아무것도 없다. 이때 getLocale()은 setDefaultLocale()로 지정한 기본값이 있으면 그것을, 없으면 JVM 기본 로케일(Locale.getDefault())을 돌려준다. FrameworkServlet의 threadContextInheritable 속성 기본값은 false라서 요청 스레드가 만든 자식 스레드도 로케일을 물려받지 않는다. 같은 코드가 요청 안에서는 "12,500"을, 배치 작업에서는 서버 OS 설정에 따른 다른 표기를 내는 일이 여기서 생긴다.

    두 요청 스레드가 같은 포맷터 인스턴스를 공유하면서도 각자의 ThreadLocal에 담긴 로케일로 다른 결과를 내는 모습을 보여 준다. 가로로 긴 구조도. 왼쪽에 위아래로 두 개의 가로 띠, 위 띠 라벨 "요청 스레드 A", 아래 띠 라벨 "요청 스레드 B". 각 띠의 왼쪽 끝에 HTTP 헤더 말풍선, 위는 "Accept-Language: ko-KR", 아래는 "Accept-Language: de-DE". 각 띠 안에 작은 금고 모양 상자 "ThreadLocal", 위 금고 안에 "ko_KR", 아래 금고 안에 "de_DE". 두 띠의 오른쪽에서 화살표가 가운데의 공유 상자 하나 "LocalizedNumberFormatter (싱글톤)"로 모인다. 공유 상자에서 다시 오른쪽으로 두 화살표가 나가 결과 카드 두 장으로 간다: 위 카드 "1,234,567", 아래 카드 "1.234.567". 아래쪽 띠 밖에 작은 주석 "finally에서 원래 값으로 복원". 평면 일러스트, 흰 배경. 포맷터 인스턴스는 하나지만 로케일은 스레드마다 따로 보관된다. FrameworkServlet이 요청 시작 때 넣고 끝날 때 되돌린다.

    포맷터를 지원하는 컨버전 서비스와 그 적용

    컨버전 서비스의 탐색 장치는 GenericConverter만 안다. 포맷터를 그 장치에 태우려면 변환기 모양으로 바꿔야 하는데, 이 일을 하는 것이 FormattingConversionService다. 이 클래스는 GenericConversionService를 상속하면서 FormatterRegistry를 구현한다. addFormatter(formatter)를 부르면 먼저 GenericTypeResolver.resolveTypeArgument()로 Formatter의 T를 알아낸다. 앞에서 본 Signature 속성을 읽는 같은 원리다. 그다음 두 개의 변환기를 등록한다.

    // FormattingConversionService (요지만 발췌)
public void addFormatterForFieldType(Class fieldType, Formatter formatter) {
    addConverter(new PrinterConverter(fieldType, formatter, this));   // (fieldType → String)
    addConverter(new ParserConverter(fieldType, formatter, this));    // (String → fieldType)
}

    LocalizedNumberFormatter라면 (Number, String) 쌍에 PrinterConverter가, (String, Number) 쌍에 ParserConverter가 들어간다. 이 두 어댑터는 ConverterAdapter와 달리 조건 없는 평범한 GenericConverter다. 대상 타입 정확 일치 검사가 없으므로 클래스 계층 탐색에서 (String, Number) 칸에 닿기만 하면 선택된다. Formatter가 Integer 요청에 쓰인 이유가 이것이다. 그리고 등록이 addFirst이므로 같은 칸에 먼저 있던 기본 StringToNumberConverterFactory보다 앞에 선다.

    "12,500"을 Integer로 바꾸는 요청을 끝까지 따라가 보자.

    마지막 단계는 편리하지만 함정도 숨어 있다. 같은 포맷터에 독일 로케일로 "12,500"을 Integer로 요청하면 결과는 12다. 독일어에서 쉼표는 소수점이므로 파서는 Double 12.5를 돌려주고, 후속 변환에서 NumberUtils.convertNumberToTargetClass()가 범위 넘침만 검사하고 Integer.valueOf(number.intValue())로 값을 만들기 때문이다. Double.intValue()는 소수부를 버린다. 오류 없이 값이 바뀐다. 출력 쪽 PrinterConverter는 원본이 프린터가 받는 타입이 아니면 먼저 변환하고, 원본이 null이면 빈 문자열을 돌려준 다음 printer.print(source, LocaleContextHolder.getLocale())를 부른다.

    "12abc"가 12가 되는 이유와 고치는 법

    NumberFormat.parse(String)의 Javadoc에는 이 메서드가 주어진 문자열 전체를 쓰지 않을 수 있다고 적혀 있다. 앞에서부터 숫자로 읽을 수 있는 데까지 읽고 나머지는 무시한다. 그래서 "12abc"는 12가 된다. 스프링이 제공하는 숫자 포맷터들의 부모 클래스 AbstractNumberFormatter는 이 문제를 ParsePosition으로 막는다. 파싱이 끝난 위치가 문자열 길이와 다르면 ParseException을 던진다. 같은 방식으로 고쳐 보자.

    import java.text.NumberFormat;
import java.text.ParseException;
import java.text.ParsePosition;
import java.util.Locale;
import org.springframework.format.Formatter;

public class StrictNumberFormatter implements Formatter {

    @Override
    public Number parse(String text, Locale locale) throws ParseException {
        NumberFormat format = NumberFormat.getNumberInstance(locale);
        ParsePosition position = new ParsePosition(0);
        Number number = format.parse(text, position);
        if (position.getErrorIndex() != -1 || position.getIndex() != text.length()) {
            throw new ParseException(text, position.getIndex());
        }
        return number;
    }

    @Override
    public String print(Number object, Locale locale) {
        return NumberFormat.getNumberInstance(locale).format(object);
    }
}

                                       cause = java.lang.IllegalArgumentException: Parse attempt failed for value [12abc]

    예외가 감싸이는 순서가 그대로 보인다. 포맷터의 ParseException을 ParserConverter가 IllegalArgumentException으로, 그것을 ConversionUtils가 ConversionFailedException으로 감쌌다. 웹에서는 여기에 바인더가 TypeMismatchException 층을 더하므로, 이 입력은 @RequestParam이라면 400 응답이, @ModelAttribute라면 typeMismatch 필드 오류가 된다.

    스프링 MVC에 포맷터 적용하기

    등록 방법은 변환기와 같다. addFormatters()에서 registry.addFormatter(new StrictNumberFormatter())를 부르거나, Spring Boot라면 포맷터를 빈으로 등록한다. 등록하고 나면 @RequestParam Integer price에 price=12,500을 보내도 12500이 들어오고, 앞의 템플릿에서 ${{number}}는 한국어 요청에서 10,000을 출력한다. th:field로 그린 Integer 필드도 묶음 표기로 나타나고, 사용자가 그 값을 그대로 제출해도 다시 정수로 바인딩된다.

    그러나 이 등록은 전역이다. (String, Number)와 (Number, String) 칸의 맨 앞에 서므로, 애플리케이션의 모든 숫자 파라미터와 모든 숫자 출력이 이 포맷터를 거친다. 상품 ID를 받는 @PathVariable Long id도, 페이지 번호도 마찬가지다. 앞의 "12abc" 문제를 고치지 않은 포맷터를 전역으로 등록했다면 잘못된 입력이 조용히 다른 값으로 바뀌는 범위가 애플리케이션 전체로 넓어진다. 특정 필드에만 형식을 적용하고 싶다면 다음 절의 애노테이션 방식이 더 맞다. 같은 칸에 기본 변환기와 사용자 변환기가 모두 있을 때 사용자 것이 이기는 이유, 그리고 (String, Integer)처럼 더 구체적인 칸에 변환기가 있으면 그것이 (String, Number) 칸의 포맷터보다 먼저 선택되는 이유는 모두 앞에서 본 탐색 순서로 설명된다.

    정리하면 DefaultFormattingConversionService는 생성자에서 DefaultConversionService.addDefaultConverters(this)로 기본 변환기를 모두 넣고, addDefaultFormatters(this)로 기본 포맷터를 넣는다. 기본 포맷터에는 @NumberFormat 처리기, 클래스패스에 JSR-354(javax.money)가 있을 때의 화폐 포맷터, java.time 타입용 DateTimeFormatterRegistrar, java.util.Date 계열용 DateFormatterRegistrar가 들어 있다. 스프링 MVC가 이 클래스를 기본으로 쓰는 것은 웹이 바로 문자열과 로케일의 세계이기 때문이다.

    스프링이 제공하는 기본 포맷터: @NumberFormat과 @DateTimeFormat

    전역 포맷터가 타입 단위라면, 애노테이션 포맷터는 필드 단위다. org.springframework.format.annotation 패키지의 @NumberFormat은 숫자 필드에, @DateTimeFormat은 java.util.Date·Calendar·Long과 java.time 타입 필드에 붙인다. @NumberFormat은 style(NUMBER, CURRENCY, PERCENT)이나 pattern을, @DateTimeFormat은 pattern이나 iso(DATE, TIME, DATE_TIME)를 지정한다. 공식 문서가 강조하듯 ISO 형식이나 직접 정한 패턴을 쓰면 로케일과 시스템에 무관하게 파싱·출력할 수 있다.

    import java.time.LocalDateTime;
import org.springframework.format.annotation.DateTimeFormat;
import org.springframework.format.annotation.NumberFormat;

public class OrderForm {

    @NumberFormat(pattern = "#,##0")
    private Long amount;

    @DateTimeFormat(pattern = "yyyy-MM-dd HH:mm:ss")
    private LocalDateTime orderedAt;

    // getter, setter ...
}

    애노테이션과 포맷터를 잇는 것은 AnnotationFormatterFactory다. 이 인터페이스는 다룰 필드 타입 집합(getFieldTypes())과 애노테이션 값을 받아 프린터·파서를 만드는 메서드(getPrinter, getParser)를 가진다. @NumberFormat용 NumberFormatAnnotationFormatterFactory의 필드 타입은 Byte부터 BigDecimal까지의 표준 숫자 타입이다. addFormatterForFieldAnnotation()은 이 필드 타입마다 AnnotationPrinterConverter와 AnnotationParserConverter를 등록하는데, 이 둘은 조건부 변환기이고 matches()는 TypeDescriptor에 해당 애노테이션이 있는지만 본다. 애노테이션 값별로 만든 프린터·파서는 (애노테이션, 필드 타입)을 키로 캐시한다.

    그렇다면 필드의 애노테이션은 어떻게 TypeDescriptor에 실려 오는가? @ModelAttribute 바인딩에서 BeanWrapper는 프로퍼티의 필드·게터·세터에서 TypeDescriptor를 만들고, @RequestParam 같은 메서드 파라미터는 MethodParameter에서 만든다. 그래서 @RequestParam("date") @DateTimeFormat(iso = DateTimeFormat.ISO.DATE) LocalDate date처럼 파라미터에 붙여도 동작한다. 서버 없이 확인할 때는 리플렉션으로 필드의 TypeDescriptor를 직접 만들면 된다.

    import java.time.LocalDate;
import java.time.LocalDateTime;
import java.util.Locale;
import org.springframework.context.i18n.LocaleContextHolder;
import org.springframework.core.convert.TypeDescriptor;
import org.springframework.format.support.DefaultFormattingConversionService;

public class AnnotationFormatDemo {
    public static void main(String[] args) throws Exception {
        DefaultFormattingConversionService fcs = new DefaultFormattingConversionService();
        TypeDescriptor string = TypeDescriptor.valueOf(String.class);
        TypeDescriptor amount = new TypeDescriptor(OrderForm.class.getDeclaredField("amount"));
        TypeDescriptor orderedAt = new TypeDescriptor(OrderForm.class.getDeclaredField("orderedAt"));

        System.out.println(fcs.convert(9876543L, amount, string));                    // ①
        System.out.println(fcs.convert("9,876,543", string, amount));                 // ②
        System.out.println(fcs.convert(LocalDateTime.of(2025, 3, 1, 9, 5), orderedAt, string)); // ③
        System.out.println(fcs.convert("2025-03-01 09:05:00", string, orderedAt));    // ④

        try {
            fcs.convert("9,876,543", Long.class);                                     // ⑤
        } catch (Exception e) {
            System.out.println(e.getClass().getSimpleName());
        }

        LocalDate date = LocalDate.of(2025, 3, 1);                                    // ⑥
        for (Locale locale : new Locale[] {Locale.KOREA, Locale.US, Locale.GERMANY}) {
            LocaleContextHolder.setLocale(locale);
            System.out.println(locale + " -> " + fcs.convert(date, String.class));
        }
    }
}

    ①과 ②는 amount 필드의 TypeDescriptor가 @NumberFormat을 싣고 있어서 (Long, String), (String, Long) 칸의 조건부 변환기가 선택된 결과다. ③은 패턴대로 출력되고, ④의 결과는 LocalDateTime 객체이며 화면에 보이는 것은 그 toString()이다. ⑤는 같은 문자열이지만 애노테이션 없는 Long 요청이라 기본 StringToNumberConverterFactory로 가서 실패한다. 같은 Long 타입이라도 어느 필드에 담기느냐에 따라 다른 변환기가 쓰인다는 것, 그 차이를 TypeDescriptor가 만든다는 것이 핵심이다.

    ⑥은 애노테이션이 없는 LocalDate다. DateTimeFormatterRegistrar는 따로 형식을 지정받지 않으면 DateTimeFormatter.ofLocalizedDate(FormatStyle.SHORT)를 쓴다. 그래서 로케일마다 표기가 다르고, 한국어에서는 "25. 3. 1."처럼 연도가 두 자리로 줄어든다. 스프링 MVC 문서도 기본적으로 날짜를 파싱·출력할 때 요청 로케일을 고려한다고 적는다. 그런데 HTML의 는 로케일과 무관하게 yyyy-MM-dd 형식의 값을 주고받는다. 파싱 쪽은 Spring Framework 6.0 이후 소스의 TemporalAccessorParser가 지정된 형식으로 실패하면 ISO 형식으로 한 번 더 시도하므로 "2025-03-01"도 받아들인다(Spring Framework 7.0.10에서 실행해 확인했다). 출력 쪽은 그렇지 않다. 같은 값을 th:field로 날짜 입력 칸에 다시 그리면 "25. 3. 1."이 value에 들어가고, 이것은 날짜 입력 칸이 받는 형식이 아니다. 스프링 MVC 문서는 이런 경우를 위해 DateTimeFormatterRegistrar의 setUseIsoFormat(true)로 등록하는 방법을 보여 준다.

    Spring Boot에서는 설정 속성으로도 바꿀 수 있다. Spring Boot 레퍼런스는 spring.mvc.format.date(LocalDate와 java.util.Date), spring.mvc.format.time, spring.mvc.format.date-time을 설정하지 않으면 각각 ofLocalizedDate·ofLocalizedTime·ofLocalizedDateTime의 FormatStyle.SHORT를 쓴다고 표로 정리한다. 값으로 패턴 문자열을 주거나, Boot의 DateTimeFormatters 소스에 따르면 iso를 주어 DateTimeFormatter.ISO_LOCAL_DATE 같은 ISO 형식을 고를 수 있다.

    spring.mvc.format.date=iso
spring.mvc.format.date-time=yyyy-MM-dd HH:mm:ss

    이 속성이 하나라도 설정되면 Boot의 WebConversionService는 기본 포맷터 대신 설정된 형식으로 DateTimeFormatterRegistrar를 구성해 등록한다. 같은 레퍼런스는 이 웹용 컨버전 서비스가 application.properties 값을 바인딩하는 컨버전 서비스와 다르다는 점도 밝힌다. 설정 파일의 30s 같은 Duration 표기를 해석하는 변환기들이 웹 쪽에는 없다는 뜻이다.

    흔한 오해와 함정

    "JSON 요청 본문도 컨버전 서비스가 바꾼다"

    가장 흔한 오해다. @RequestBody로 받는 JSON과 @ResponseBody로 내보내는 JSON은 HttpMessageConverter가 처리하고, 스프링 MVC 1편에서 본 것처럼 JSON이라면 그 구현은 Jackson의 ObjectMapper를 쓴다. 이 경로에는 데이터 바인더도 TypeConverterDelegate도 등장하지 않는다. 그래서 StringToGeoPointConverter를 등록해도 {"location":"37.5,127.0"}은 GeoPoint로 바뀌지 않고, DTO 필드에 붙인 @DateTimeFormat이나 @NumberFormat도 JSON 본문에는 적용되지 않는다. JSON 쪽 형식은 Jackson의 @JsonFormat, 사용자 정의 직렬화기·역직렬화기, Jackson 모듈로 정한다. 같은 컨트롤러 안에서도 쿼리 파라미터와 본문이 서로 다른 변환 체계를 쓴다는 점을 기억하자.

    요청 데이터의 위치                          처리 경로                                    형식 지정 수단
쿼리 파라미터, 폼, 경로 변수      →  ArgumentResolver → WebDataBinder → ConversionService   Converter, Formatter, @DateTimeFormat
요청 본문 (JSON)                  →  HttpMessageConverter → Jackson ObjectMapper             @JsonFormat, Jackson 모듈

    "Converter는 람다로 등록하면 간단하다"

    addConverter(Converter) 한 인자 버전은 클래스의 Signature 속성에서 타입 인자를 읽으므로 람다나 타입 인자를 확정하지 않은 제네릭 클래스에는 쓸 수 없다. 람다를 쓰려면 addConverter(String.class, GeoPoint.class, lambda)처럼 타입을 직접 넘긴다. 같은 이유로 class MyConverter implements Converter처럼 타입 변수를 남겨 둔 클래스도 등록 시점에 실패한다.

    "상위 타입으로 만든 Converter는 하위 타입에도 적용된다"

    Converter는 대상 타입이 정확히 T일 때만 쓰인다. 하위 타입 전체를 맡기려면 ConverterFactory를 쓴다. 포맷터는 이 제한이 없어서 Formatter는 모든 숫자 타입에 적용된다. 세 장치의 범위가 서로 다르다는 것을 모르면 "등록했는데 안 불린다"와 "등록했더니 예상보다 넓게 불린다"를 모두 겪는다.

    "변환기에 상태를 두어도 요청마다 새로 생기니 괜찮다"

    변환기와 포맷터는 컨버전 서비스 안에 한 번 등록되어 모든 요청 스레드가 공유한다. 바인더는 요청마다 새로 생기지만 그 안에 꽂히는 컨버전 서비스는 싱글톤이다. 필드에 SimpleDateFormat이나 NumberFormat, 계산 중간값을 두면 동시 요청에서 결과가 섞인다. 스레드 안전한 DateTimeFormatter를 쓰거나 호출마다 새로 만든다.

    "@InitBinder로 등록한 것과 컨버전 서비스는 같은 층이다"

    TypeConverterDelegate는 사용자 정의 PropertyEditor를 먼저 찾고, 없을 때만 컨버전 서비스를 쓴다. 어떤 컨트롤러의 @InitBinder에서 registerCustomEditor(GeoPoint.class, ...)를 했다면 그 컨트롤러에서는 전역 변환기가 무시된다. DataBinder.addCustomFormatter()(4.2부터)도 내부에서 포맷터를 PropertyEditor 어댑터로 감싸 사용자 정의 편집기로 등록하므로 같은 우선순위를 가진다. 컨트롤러 하나에만 다른 형식을 적용할 때는 이 성질이 유용하지만, 의도하지 않았다면 디버깅이 어렵다.

    "기본 타입 파라미터도 값이 없으면 0이 된다"

    @RequestParam(required = false) int page에 값이 오지 않으면 변환할 원본이 없다. AbstractNamedValueMethodArgumentResolver는 변환을 시도하기 전에 이 경우를 검사해서, 파라미터 타입이 boolean이면 false를 넣고 그 밖의 기본 타입이면 "Optional int parameter 'page' is present but cannot be translated into a null value due to being declared as a primitive type."으로 시작하는 IllegalStateException을 던진다. 0이 들어가지 않으며, 이 예외는 DefaultHandlerExceptionResolver가 다루는 종류가 아니어서 서버 오류로 끝난다. 선택 파라미터라면 Integer로 받거나 defaultValue를 준다. 폼 객체라면 visitors 예제처럼 변환 실패 시 필드에 기본값 0이 그대로 남아 있으므로, 0이 사용자의 입력인지 실패의 흔적인지는 BindingResult를 보고 판단해야 한다.

    다른 주제와의 연결

    이 회차의 장치들은 앞뒤 회차와 다른 권의 여러 곳에서 다시 나온다. 4회의 typeMismatch 오류 코드는 이번에 본 TypeMismatchException이 바인더 안에서 FieldError로 바뀐 결과였고, 3회의 LocaleResolver는 포맷터가 받는 로케일의 출처였다. MethodArgumentTypeMismatchException 같은 예외를 사용자에게 보여 줄 오류 응답으로 바꾸는 일은 8회와 9회의 예외 처리 주제와 이어지고, 11회의 파일 업로드에서는 문자열이 아닌 요청 데이터(MultipartFile)를 컨트롤러 파라미터로 받는 다른 경로가 등장한다.

    스프링 MVC 밖에서도 같은 원리가 쓰인다. Spring Boot의 @ConfigurationProperties 바인딩은 ApplicationConversionService라는 별도의 컨버전 서비스로 설정 문자열을 Duration이나 DataSize로 바꾼다. 스프링 데이터의 웹 지원은 경로 변수의 ID를 엔티티로 바꾸는 변환기를 컨버전 서비스에 등록한다. 지워진 제네릭을 Signature 속성과 ResolvableType으로 읽는 기법은 스프링 컨테이너가 List 타입의 의존관계를 주입할 때, 이벤트 리스너의 이벤트 타입을 찾을 때에도 쓰인다. 요청 스레드에 정보를 묶어 두는 ThreadLocal 패턴은 RequestContextHolder, 트랜잭션 동기화, 스프링 시큐리티의 인증 정보 보관으로 이어진다.

    이 장의 핵심

    HTTP는 문자열만 실어 오고 화면도 문자열만 받는다. 스프링은 그 사이를 상태 없는 변환기들의 등록소인 컨버전 서비스 하나로 잇는다. 등록은 시작할 때 FormatterRegistry로, 사용은 요청마다 새로 만든 바인더와 뷰가 ConversionService로 한다. 어떤 변환기가 선택될지는 (원본 계층 × 대상 계층) 탐색, 나중 등록 우선, Converter의 대상 정확 일치 규칙으로 정해지고, 포맷터의 로케일은 요청 스레드의 ThreadLocal에서 온다.
    Converter
    원본 타입 S를 대상 타입 T로 바꾸는 상태 없는 단방향 변환기. 등록 시 클래스의 제네릭 선언에서 S와 T를 읽고, 대상 타입이 정확히 T일 때만 선택된다.
    ConverterFactory / GenericConverter
    ConverterFactory는 한 원본에서 어떤 계층의 모든 하위 타입으로 가는 변환을, GenericConverter는 TypeDescriptor(제네릭, 애노테이션)를 보고 여러 쌍을 다루는 변환을 맡는다.
    ConversionService
    변환을 요청받는 인터페이스. 등록 인터페이스(ConverterRegistry, FormatterRegistry)와 분리되어 있고, 애플리케이션 시작 때 만들어 모든 스레드가 공유한다.
    컨버터 탐색 규칙
    캐시를 먼저 보고, 원본 계층(바깥)과 대상 계층(안쪽)의 쌍을 차례로 검사한다. 같은 쌍에서는 나중에 등록한 변환기가 앞에 서며, 결과는 NO_MATCH까지 캐시된다.
    바인더와 변환 경로
    요청마다 새로 만든 WebDataBinder가 TypeConverterDelegate를 통해 사용자 정의 PropertyEditor, ConversionService, 기본 편집기 순서로 변환을 시도한다. 실패는 400(TypeMismatch), 500(ConversionNotSupported), typeMismatch 필드 오류로 갈린다.
    Formatter
    문자열과 객체 사이의 양방향 변환을 로케일과 함께 다루는 SPI. FormattingConversionService가 PrinterConverter와 ParserConverter로 감싸 등록하며, 대상 정확 일치 제한이 없다.
    LocaleContextHolder
    요청 로케일을 담는 ThreadLocal 보관소. FrameworkServlet이 요청 시작 때 넣고 finally에서 되돌리며, 요청 밖의 스레드에서는 기본 로케일을 돌려준다.
    @NumberFormat / @DateTimeFormat
    필드나 파라미터의 TypeDescriptor에 실린 애노테이션을 조건으로 선택되는 포맷터. 타입 단위 전역 포맷터와 달리 필드마다 형식을 정한다.
    뷰와 JSON의 경계
    타임리프의 ${{...}}와 th:field는 요청 속성으로 전달된 같은 ConversionService를 쓰지만, @RequestBody·@ResponseBody JSON은 HttpMessageConverter와 Jackson이 처리한다.

    실무에서 타입 변환 문제는 대개 "왜 400이 나지?" 또는 "왜 값이 이상하게 들어오지?"로 시작한다. 첫 번째 질문에는 변환이 어느 경로에서 일어났는지부터 확인하는 것이 빠르다. 쿼리 파라미터나 폼이라면 바인더와 컨버전 서비스의 문제이고 MethodArgumentTypeMismatchException이나 BindingResult의 typeMismatch를 보면 된다. JSON 본문이라면 Jackson의 역직렬화 오류이므로 변환기를 아무리 등록해도 해결되지 않는다. 사용자 정의 타입 파라미터가 400이 아니라 500으로 끝난다면 변환기 등록이 빠졌다는 신호다.

    두 번째 질문, 값이 조용히 바뀌는 문제는 더 위험하다. 이 회차에서만도 "12abc"가 12가 되는 관대한 파싱, 독일어 로케일의 "12,500"이 12가 되는 소수부 절삭, 문자열 왕복에서 바뀌는 실수 표기를 보았다. 금액·수량처럼 틀리면 안 되는 값은 전체 문자열 소비를 검사하는 파서를 쓰고, 로케일에 의존하지 않는 형식(ISO, 고정 패턴)을 계약으로 정하는 편이 안전하다. 로케일 의존 형식은 사람이 보는 출력에만 쓰고, 서버가 다시 읽어야 하는 값에는 쓰지 않는다는 원칙이 판단을 단순하게 만든다.

    전역 등록과 필드 단위 등록 사이의 선택도 자주 마주친다. 모든 숫자에 묶음 표기를 적용하는 전역 포맷터는 화면을 한 번에 바꾸지만 ID, 페이지 번호, 내부 API 파라미터까지 함께 바뀐다. 영향 범위를 예측할 수 없다면 @NumberFormat·@DateTimeFormat으로 필요한 필드에만 거는 쪽이 낫다. 반대로 GeoPoint처럼 애플리케이션 전체에서 표기가 하나로 정해진 도메인 타입은 전역 변환기가 맞다. 변환기와 포맷터는 공유되는 싱글톤이므로 상태를 두지 않는다는 원칙은 어느 쪽이든 같다.

Converter를 감싼 ConverterAdapter.matches()는 등록된 대상 타입(Number)과 요청 대상 타입(Long)이 정확히 같을 때만 참이다. 탐색은 (String, Long) 칸을 거쳐 (String, Number) 칸에 이르는데, 그 칸의 맨 앞에 있는 사용자 변환기는 탈락하고 다음 순서의 StringToNumberConverterFactory가 선택되어 12L을 만든다. Formatter라면 ParserConverter는 조건이 없는 GenericConverter이므로 같은 칸에서 바로 선택되고, 파싱 결과가 Long이 아니면 컨버전 서비스로 후속 변환까지 한다.

    2. @InitBinder가 있는 컨트롤러에서는 GeoPointEditor가 변환한다. TypeConverterDelegate가 사용자 정의 편집기를 먼저 찾고, 있으면 컨버전 서비스를 시도하지 않기 때문이다. 다른 컨트롤러에서는 바인더에 편집기가 없으므로 컨버전 서비스가 쓰이고, ConvertersForPair가 addFirst로 쌓이므로 나중에 등록한 B가 선택된다. 편집기는 그 요청의 바인더에만 등록되므로 다른 컨트롤러로 새지 않는다.

    3. 첫째, NumberFormat을 필드에 두고 공유한다. 포맷터는 모든 요청 스레드가 함께 쓰는 싱글톤인데 NumberFormat은 동기화되어 있지 않으므로, 동시 요청이 많을 때 간헐적으로 잘못된 값이나 예외가 나올 수 있다. 재현이 어려워 부하 테스트나 운영에서 처음 드러나는 종류의 버그다. 둘째, 파라미터로 받은 로케일 l을 무시하고 언제나 한국 형식을 쓴다. 다른 언어권 사용자에게도 한국식 표기가 나가고, 로케일별 입력을 기대하는 화면과 어긋난다. 덧붙여 parse(String)은 문자열 전체를 소비했는지 확인하지 않으므로 "12abc"를 12로 받아들인다. 호출마다 NumberFormat.getNumberInstance(l)을 만들고 ParsePosition으로 끝 위치를 검사하면 세 문제가 모두 해결된다.

    4. 12다. FrameworkServlet이 AcceptHeaderLocaleResolver로 de_DE를 얻어 LocaleContextHolder에 넣는다. 리졸버가 만든 바인더가 컨버전 서비스에 String → Integer를 요청하고, 탐색은 (String, Number) 칸의 ParserConverter를 고른다. 독일어 NumberFormat에서 쉼표는 소수점이므로 파싱 결과는 Double 12.5다. Double은 Integer에 대입되지 않으므로 컨버전 서비스가 NumberToNumberConverterFactory로 후속 변환을 하고, 이때 소수부가 버려져 12가 된다. 예외가 나지 않으므로 사용자도 서버도 알아차리지 못한다. 실제로 같은 포맷터와 Locale.GERMANY로 convert("12,500", Integer.class)를 실행하면 12가 나온다.

    5. @ModelAttribute 쪽은 바인더가 date 프로퍼티의 TypeDescriptor에서 @DateTimeFormat을 발견하고, 조건부 변환기 AnnotationParserConverter가 yyyy.MM.dd 패턴으로 파싱해 2025-03-01이 들어간다. @RequestBody 쪽은 Jackson이 역직렬화하며 스프링의 @DateTimeFormat을 보지 않는다. Jackson의 LocalDate 역직렬화는 별도 설정이 없으면 ISO 형식을 기대하므로 "2025.03.01"을 읽지 못해 HttpMessageNotReadableException이 되고, DefaultHandlerExceptionResolver는 이것을 400으로 응답한다. JSON 쪽 형식은 @JsonFormat(pattern = "yyyy.MM.dd") 같은 Jackson 수단으로 지정해야 한다.

     DefaultConversionService에 Converter 구현 L을 등록한 뒤 convert("7", Integer.class)를 부르면 무엇이 변환하는가? L. 나중에 등록한 변환기가 언제나 우선하기 때문이다. StringToNumberConverterFactory. L은 대상 타입이 정확히 Number일 때만 선택되기 때문이다. ObjectToObjectConverter. Integer.valueOf(String)이 있기 때문이다. 아무것도 없어 ConverterNotFoundException이 난다. L과 기본 팩터리는 모두 (String, Number) 칸에 있고 L이 앞에 있다. 그러나 ConverterAdapter.matches()는 대상 타입 정확 일치를 요구하므로 L은 탈락하고, 이 검사가 없는 ConverterFactoryAdapter가 선택된다. 나중 등록 우선은 같은 칸 안에서 조건을 통과한 것끼리의 규칙이다. ObjectToObjectConverter는 (Object, Object) 칸이라 그보다 훨씬 뒤에 검사되며, 변환이 가능하므로 예외도 나지 않는다. cs.addConverter((Converter) s -> ...)가 IllegalArgumentException으로 실패하는 근본 원인은? 람다는 함수형 인터페이스가 아닌 Converter를 구현할 수 없기 때문이다. 컨버전 서비스가 람다의 바이트코드를 실행할 수 없기 때문이다. 실행 중에 만들어진 람다의 숨은 클래스에는 타입 인자를 기록한 Signature 속성이 없어 리플렉션으로 S와 T를 알 수 없기 때문이다. 제네릭 소거 때문에 모든 Converter 구현 클래스는 타입 인자를 잃기 때문이다. 소거는 메서드 디스크립터에서 타입 인자를 지우지만, 클래스 선언의 제네릭 정보는 Signature 속성으로 남아 getGenericInterfaces()로 읽을 수 있다. 일반 클래스는 그래서 등록된다. 람다 클래스는 런타임에 생성되는 숨은 클래스라 이 정보가 없다. Converter는 @FunctionalInterface이므로 람다로 구현하는 것 자체는 가능하다. 포맷터의 print(T, Locale)에 전달되는 로케일은 스프링 MVC 요청 처리 중 어디에서 오는가? FrameworkServlet이 요청 시작 때 LocaleResolver의 결과를 넣어 두는 ThreadLocal 기반의 LocaleContextHolder 포맷터를 등록할 때 함께 지정한 로케일 언제나 JVM 기본 로케일(Locale.getDefault()) ConversionService 인스턴스가 필드로 보관하는 마지막 요청의 로케일 PrinterConverter와 ParserConverter는 LocaleContextHolder.getLocale()을 부른다. 이 값은 FrameworkServlet.processRequest()가 요청마다 스레드에 넣고 finally에서 되돌린다. JVM 기본 로케일은 요청 밖에서 컨텍스트가 비어 있을 때의 대체값일 뿐이다. 컨버전 서비스는 공유 싱글톤이므로 요청 로케일을 필드에 보관하면 스레드 사이에 값이 섞인다. 사용자 정의 타입 GeoPoint를 @RequestParam으로 받는데 변환기 등록을 잊었다. 이 요청은 기본 설정에서 어떤 응답으로 끝나는가? 400. 클라이언트가 보낸 문자열이 GeoPoint가 아니기 때문이다. 200. 파라미터에 null이 들어가고 메서드가 실행된다. 400. ConversionFailedException은 언제나 400이기 때문이다. 500. 변환기를 찾지 못한 것이 ConversionNotSupportedException 계열로 바뀌어 서버 오류로 처리되기 때문이다. 컨버전 서비스가 canConvert()에 거짓으로 답하고 편집기도 없으면 TypeConverterDelegate가 "no matching editors or conversion strategy found" 메시지의 IllegalStateException을 던지고, 이것이 TypeConverterSupport에서 ConversionNotSupportedException으로, 리졸버에서 MethodArgumentConversionNotSupportedException으로 바뀐다. DefaultHandlerExceptionResolver는 이것을 TypeMismatchException보다 먼저 검사해 서버 오류로 응답한다. 값이 잘못된 경우(변환기가 예외를 던진 경우)만 400이다. DTO 필드에 @DateTimeFormat(pattern = "yyyy.MM.dd")를 붙였는데 @RequestBody JSON 요청에서 형식이 적용되지 않는다. 이유로 가장 정확한 것은? @DateTimeFormat은 LocalDate에는 쓸 수 없고 java.util.Date에만 쓸 수 있다. JSON 본문은 HttpMessageConverter(Jackson)가 역직렬화하므로 데이터 바인더와 컨버전 서비스를 거치지 않는다. DateTimeFormatterRegistrar가 등록되지 않았기 때문이다. 요청에 Accept-Language 헤더가 없어서 로케일을 결정하지 못했기 때문이다. @DateTimeFormat은 java.time 타입에도 적용되고 기본 등록되어 있다. 문제는 경로다. @ModelAttribute·@RequestParam은 바인더를 통해 컨버전 서비스를 쓰지만 @RequestBody는 메시지 컨버터가 Jackson으로 처리하며, 그곳의 형식은 @JsonFormat 같은 Jackson 수단으로 정한다. 패턴을 명시했으므로 로케일과도 무관하다.
    타입 변환기(Converter)
    원본 타입 S의 값을 대상 타입 T로 바꾸는 스프링의 단방향 변환 인터페이스. Spring Framework 3.0에서 도입되었다.
    컨버전 서비스(ConversionService)
    등록된 변환기들 가운데 알맞은 것을 찾아 변환을 수행하는 서비스 인터페이스. 상태 없이 여러 스레드가 공유한다.
    포맷터(Formatter)
    객체와 문자열 사이의 출력(print)과 파싱(parse)을 로케일과 함께 다루는 인터페이스. Printer와 Parser를 합친 것이다.
    타입 기술자(TypeDescriptor)
    변환의 원본·대상 타입을 Class뿐 아니라 제네릭 타입 인자와 애노테이션까지 포함해 기술하는 스프링의 객체.
    속성 편집기(PropertyEditor)
    자바빈즈의 문자열↔객체 변환 인터페이스. 변환 결과를 내부 상태로 보관하므로 스레드 사이에 공유할 수 없다.
    브리지 메서드(bridge method)
    제네릭 인터페이스를 구현할 때 소거된 시그니처와 실제 메서드를 잇기 위해 컴파일러가 만드는 합성 메서드. ACC_BRIDGE 플래그가 붙는다.
    Signature 속성(Signature attribute)
    클래스·필드·메서드의 제네릭 선언을 기록하는 클래스 파일 속성(JVMS §4.7.9). 리플렉션이 지워진 타입 인자를 읽는 근거다.
    스레드 로컬(ThreadLocal)
    스레드마다 독립된 값을 보관하는 변수. 스프링은 요청 로케일을 LocaleContextHolder의 ThreadLocal에 담아 전달한다.
