    로그인 확인은 어디에 있어야 하는가

    06회에서 세션으로 로그인 상태를 만들었다. 로그인에 성공하면 서버가 세션 저장소에 회원 정보를 넣고, 브라우저는 JSESSIONID 쿠키로 그 세션을 다시 가리킨다. 그런데 로그인 상태를 만들었다고 해서 화면이 보호되는 것은 아니다. 로그인하지 않은 사용자에게 상품 목록 링크를 숨기더라도, /items나 /items/1/edit 같은 URL을 주소창에 직접 치면 서버가 확인하지 않는 한 화면이 그대로 열린다. HTTP 요청은 링크를 눌러서만 생기는 것이 아니다. 주소창, 북마크, curl, 다른 사이트의 폼이 모두 같은 요청을 만들 수 있다.

    가장 단순한 해결은 보호해야 할 컨트롤러 메서드마다 맨 앞에서 세션을 꺼내 회원이 있는지 확인하는 것이다. 이 방식은 동작은 하지만 세 가지 문제가 있다. 첫째, 같은 코드가 수십 곳에 복사된다. 둘째, 확인 규칙이 바뀌면(예: 관리자 권한 확인 추가) 수십 곳을 함께 고쳐야 한다. 셋째이자 가장 위험한 것은 새 메서드를 추가하면서 한 줄을 빠뜨리면 그 URL만 조용히 열린다는 점이다. 보안 검사가 "모든 곳에 기억해서 넣어야 하는 코드"라면 언젠가는 빠진다.

    이처럼 여러 기능에 공통으로 걸쳐 있으면서 각 기능의 본래 목적과는 다른 관심사를 공통 관심사(cross-cutting concern)라고 한다. 로그인 확인, 요청 로그, 실행 시간 측정, 인코딩 설정이 대표적이다. 공통 관심사는 개별 메서드가 아니라 요청이 지나가는 길목에 한 번만 두는 것이 맞다. 그러면 새 URL이 생겨도 그 길목을 지나지 않을 방법이 없으므로 빠뜨릴 수가 없다. 스프링 AOP로도 공통 처리를 할 수 있지만(스프링 핵심 원리 고급편의 주제다), 웹 요청에 관한 처리는 URL과 HTTP 요청·응답 객체를 직접 받아야 하므로 웹 계층에 전용 길목이 따로 마련되어 있다.

    그 길목은 두 층에 있다. 하나는 서블릿 컨테이너(톰캣)가 서블릿 앞에 세우는 서블릿 필터(Servlet Filter)이고, 다른 하나는 스프링 MVC의 DispatcherServlet이 컨트롤러 앞에 세우는 핸들러 인터셉터(HandlerInterceptor)다. 이번 회차는 두 길목을 각각 만들어 보고, 둘이 같은 스레드의 호출 스택 안에서 정확히 어떤 순서로 불리는지 톰캣과 스프링의 소스, 그리고 실제 실행 결과로 확인한다. 마지막으로 컨트롤러가 세션을 직접 뒤지지 않고 파라미터로 로그인 회원을 받도록 인자 리졸버(argument resolver)를 만든다.

    서블릿 필터: 컨테이너가 서블릿 앞에 세우는 관문

    필터는 서블릿 명세(Jakarta Servlet)가 정의한 표준 인터페이스다. 스프링이 없어도 존재하고, 톰캣·제티·언더토우 같은 모든 서블릿 컨테이너가 같은 방식으로 다룬다. Jakarta Servlet 6.0의 jakarta.servlet.Filter는 메서드 세 개로 이루어져 있다.

    public interface Filter {
    default void init(FilterConfig filterConfig) throws ServletException {}

    void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException;

    default void destroy() {}
}

    init과 destroy는 아무것도 하지 않는 기본 메서드(default method)이므로 보통은 doFilter 하나만 구현한다. init은 컨테이너가 필터 객체를 만든 뒤 필터를 쓰기 전에 정확히 한 번 호출하고, destroy는 필터를 서비스에서 내릴 때 doFilter 안에 있던 스레드가 모두 빠져나간 뒤(또는 시간 초과 뒤) 한 번 호출한다. 톰캣 11 소스를 보면 필터 인스턴스가 이미 주어진 경우 컨텍스트가 시작될 때 ApplicationFilterConfig를 만들면서 곧바로 init을 부른다. 즉 첫 요청이 오기 전에 초기화가 끝나 있다.

    여기서 가장 중요한 사실은 필터 객체가 몇 개 만들어지는가다. 서블릿 명세는 "배포 서술자의 필터 선언 하나당 컨테이너의 JVM 하나에 인스턴스 하나만 만든다"고 정한다. 요청이 천 개 동시에 들어와도 AccessLogFilter 객체는 하나이고, 천 개의 작업 스레드가 그 한 객체의 doFilter를 동시에 실행한다. 메서드의 지역 변수는 각 스레드의 스택 프레임에 따로 생기므로 섞이지 않지만, 필드는 힙에 있는 한 객체에 하나뿐이므로 모든 스레드가 공유한다. 이 사실은 뒤에서 인터셉터를 만들 때 다시 결정적인 역할을 한다.

    doFilter의 파라미터 타입이 HttpServletRequest가 아니라 ServletRequest라는 점도 눈여겨보자. 서블릿 API는 처음에 HTTP가 아닌 프로토콜도 염두에 두고 설계되어서 최상위 타입이 프로토콜 중립적이다. 실무에서 만나는 요청은 사실상 모두 HTTP이므로 필터 안에서 HttpServletRequest로 캐스팅해서 쓴다. 실제로 톰캣이 넘겨주는 객체는 내부 Request 객체를 감싼 RequestFacade이고, 이것은 HttpServletRequest를 구현한다.

    명세가 제시하는 doFilter의 전형적인 흐름은 다섯 단계다. 요청을 살핀다 → 필요하면 요청 객체를 감싼다(wrap) → 필요하면 응답 객체를 감싼다 → chain.doFilter로 다음 단계를 부르거나, 부르지 않고 처리를 막는다 → 다음 단계가 끝난 뒤 응답에 후처리를 한다. 이 다섯 단계에 필터가 할 수 있는 일이 모두 들어 있다. 특히 "부르지 않고 막는다"와 "다른 객체로 감싸서 넘긴다"는 인터셉터에는 없는 필터만의 능력이다. 예를 들어 스프링의 ContentCachingRequestWrapper 같은 래퍼로 요청을 감싸 넘기면 그 뒤의 모든 단계(다른 필터, 서블릿, 컨트롤러)는 원래 요청 대신 래퍼를 받는다.

    필터 체인은 재귀 호출이다

    필터가 여러 개면 컨테이너는 요청마다 필터 체인(filter chain)을 만든다. 서블릿 명세가 정한 체인 구성 순서는 이렇다. 먼저 URL 패턴으로 매칭된 필터 매핑을 선언된 순서대로, 그다음 서블릿 이름으로 매칭된 필터 매핑을 선언된 순서대로 넣는다. 그리고 체인의 끝에는 요청 URL에 매핑된 서블릿이 온다. 스프링 MVC 애플리케이션이라면 그 서블릿은 DispatcherServlet이다.

    "체인"이라는 이름 때문에 컨테이너가 필터들을 반복문으로 차례차례 호출한다고 생각하기 쉽지만 실제 구조는 다르다. 톰캣 11.0.27의 ApplicationFilterChain.doFilter에서 핵심만 남기면 다음과 같다.

    private ApplicationFilterConfig[] filters = new ApplicationFilterConfig[0];
private int pos = 0;   // 다음에 부를 필터의 위치
private int n = 0;     // 이 요청에 걸린 필터 수
private Servlet servlet = null;

public void doFilter(ServletRequest request, ServletResponse response)
        throws IOException, ServletException {
    if (pos < n) {
        ApplicationFilterConfig filterConfig = filters[pos++];
        Filter filter = filterConfig.getFilter();
        // ... 비동기 지원 여부 처리
        filter.doFilter(request, response, this);   // 체인 자신을 넘긴다
        return;
    }
    // 체인의 끝에서 떨어지면 서블릿을 호출한다
    servlet.service(request, response);
}

    반복문이 없다. 체인은 pos번째 필터를 꺼내 pos를 1 늘린 다음, 그 필터의 doFilter에 자기 자신을 chain 인자로 넘긴다. 필터가 chain.doFilter(...)를 부르면 다시 이 메서드로 들어와 다음 필터를 꺼낸다. 마지막 필터가 chain.doFilter를 부르면 pos == n이므로 servlet.service가 호출된다. 결국 필터 1의 doFilter 프레임 위에 체인 프레임, 그 위에 필터 2의 프레임, 그 위에 체인 프레임, 그 위에 서블릿 프레임이 쌓이는 상호 재귀(mutual recursion)다. (톰캣 10.1에서는 같은 로직이 internalDoFilter라는 별도 메서드에 들어 있을 뿐 구조는 같다.)

SignInRequiredFilter의 chain.doFilter 다음 줄, 그다음 AccessLogFilter의
chain.doFilter 다음 줄이 실행된다.

    이 그림 하나로 필터의 동작 규칙이 모두 설명된다. chain.doFilter 앞의 코드는 요청이 들어갈 때 순서대로 실행되고, 뒤의 코드는 응답이 나올 때 역순으로 실행된다. 스택이기 때문이다. 필터가 chain.doFilter를 부르지 않고 반환하면 그 위의 프레임은 아예 쌓이지 않으므로 뒤의 필터도 서블릿도 실행되지 않는다. 그리고 안쪽에서 던진 예외는 스택을 거꾸로 타고 올라오며 각 필터의 doFilter를 통과하므로, 필터는 try/finally로 예외가 났을 때도 후처리를 할 수 있다.

    체인 객체의 수명도 소스에서 확인할 수 있다. ApplicationFilterFactory.createFilterChain은 톰캣의 내부 Request 객체에 붙어 있는 체인을 꺼내 재사용하거나 없으면 새로 만들고, 컨텍스트의 필터 매핑을 돌면서 디스패처 타입과 URL이 맞는 필터만 addFilter로 넣는다. 요청 처리가 끝나면 StandardWrapperValve가 filterChain.release()를 불러 배열을 비우고 pos와 n을 0으로 되돌린다. pos는 요청마다 따로 있는 상태라서 체인 객체는 공유되지 않지만, 체인이 가리키는 필터 인스턴스는 모든 요청이 공유한다.

    요청 로그 필터 만들기

    첫 번째 필터는 모든 요청의 시작과 끝을 기록한다. 요청마다 짧은 식별자를 붙여, 동시에 들어온 여러 요청의 로그가 섞여도 어떤 줄이 같은 요청에 속하는지 구분할 수 있게 한다.

    package shop.web;

import jakarta.servlet.Filter;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.ServletRequest;
import jakarta.servlet.ServletResponse;
import jakarta.servlet.http.HttpServletRequest;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;

import java.io.IOException;
import java.util.UUID;

public class AccessLogFilter implements Filter {

    private static final Logger log = LoggerFactory.getLogger(AccessLogFilter.class);

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        String uri = httpRequest.getRequestURI();
        String requestId = UUID.randomUUID().toString().substring(0, 8);
        long start = System.nanoTime();

        log.info("REQ [{}] {} {}", requestId, httpRequest.getMethod(), uri);
        try {
            chain.doFilter(request, response);   // 다음 필터로, 마지막이면 서블릿으로
        } finally {
            long tookMs = (System.nanoTime() - start) / 1_000_000;
            log.info("RES [{}] {} {}ms", requestId, uri, tookMs);
        }
    }
}

    한 줄씩 보자. requestId, uri, start는 모두 지역 변수라서 각 요청 스레드의 스택 프레임에만 존재한다. 필터 객체는 하나지만 이 값들은 스레드마다 따로이므로 안전하다. chain.doFilter를 try 안에 두고 응답 로그를 finally에 둔 이유는, 컨트롤러에서 예외가 터져 스택을 타고 올라와도 응답 로그가 반드시 남게 하기 위해서다. 예외를 catch로 삼키지 않았으므로 예외는 그대로 컨테이너까지 올라간다. UUID 값과 소요 시간은 실행할 때마다 달라진다.

    스프링 부트에서 필터를 등록하는 가장 명시적인 방법은 FilterRegistrationBean을 빈으로 등록하는 것이다.

    @Configuration
public class WebConfig implements WebMvcConfigurer {

    @Bean
    public FilterRegistrationBean accessLogFilter() {
        FilterRegistrationBean bean = new FilterRegistrationBean<>(new AccessLogFilter());
        bean.setOrder(1);            // 작은 값이 바깥쪽(먼저)
        bean.addUrlPatterns("/*");
        return bean;
    }
    // ... 다른 필터, 인터셉터, 리졸버 등록은 뒤에서 추가한다
}

    부트는 애플리케이션이 시작될 때 이런 등록 빈들을 순서 값으로 정렬한 뒤 서블릿 컨텍스트에 필터를 하나씩 추가한다. 순서 값이 작을수록 체인의 앞(호출 스택의 아래, 즉 바깥쪽)에 놓인다. 등록 빈의 순서 기본값은 Ordered.LOWEST_PRECEDENCE(가장 낮은 우선순위)다. URL 패턴을 하나도 주지 않으면 /*로 매핑된다. 스프링 부트 문서는 필터 빈은 대개 순서를 지정하지 않아도 되지만, 순서가 필요하면 필터 클래스에 @Order를 붙이거나 Ordered를 구현하거나 등록 빈의 setOrder를 쓰라고 안내한다. @Bean 메서드에 @Order를 붙이는 방식으로는 필터 순서가 정해지지 않는다는 점도 문서에 명시되어 있다.

    URL 패턴 /*는 서블릿 명세의 매핑 규칙을 따른다. 명세가 정한 패턴은 다섯 종류뿐이다. /로 시작하고 /*로 끝나는 경로 매핑(/admin/*), *.로 시작하는 확장자 매핑(*.do), 애플리케이션의 컨텍스트 루트에만 정확히 맞는 빈 문자열(""), 단독 /인 기본 서블릿, 그리고 나머지 모두는 정확히 일치(exact match)다. /items/*/edit처럼 가운데에 와일드카드를 넣는 문법은 없다. 그래서 필터는 보통 /*로 모든 요청을 받고, 세밀한 경로 판단은 필터 코드 안에서 한다. 뒤에서 볼 인터셉터의 경로 패턴은 이것과 전혀 다른 문법이다.

    등록에 관해 하나 더 알아 둘 것이 디스패처 타입(dispatcher type)이다. 같은 요청 안에서도 서블릿 컨테이너는 포워드(FORWARD), 인클루드(INCLUDE), 오류 페이지 처리(ERROR), 비동기 재디스패치(ASYNC)로 서블릿을 다시 부를 수 있다. 처음 클라이언트가 보낸 요청은 REQUEST다. 스프링 부트 3.5 소스의 AbstractFilterRegistrationBean은 디스패처 타입을 지정하지 않으면 REQUEST만 쓰고, 필터가 스프링의 OncePerRequestFilter를 상속한 경우에만 모든 타입을 쓴다. 우리 필터는 REQUEST에만 걸리므로, 예외가 나서 컨테이너가 오류 페이지로 다시 디스패치할 때는 실행되지 않는다. 이 동작이 어떤 의미가 있는지는 08회에서 오류 페이지와 함께 다룬다. OncePerRequestFilter는 요청 속성에 필터이름.FILTERED 표시를 남겨, 같은 요청 안에서 포워드 등으로 체인을 다시 지나도 본체(doFilterInternal)가 한 번만 실행되도록 막아 주는 스프링의 필터 기반 클래스다.

    스프링 부트 3.5 문서는 요청 본문을 읽는 필터를 Ordered.HIGHEST_PRECEDENCE에 두지 말라고 경고한다. 문자 인코딩을 설정하는 필터보다 먼저 본문을 읽으면 인코딩 설정이 무시될 수 있기 때문이다. 순서 값은 "내 필터가 먼저 실행되면 좋겠다"가 아니라 "내 필터가 다른 필터의 어떤 결과를 전제로 하는가"로 정한다.

    이 필터에는 숨은 함정이 하나 있다. 응답 로그에 상태 코드를 함께 찍고 싶어서 finally 안에서 ((HttpServletResponse) response).getStatus()를 부르면, 컨트롤러가 처리되지 않은 예외를 던진 요청의 상태가 500이 아니라 200으로 찍힌다. 뒤에서 보여 줄 실험(톰캣 11.0.27)에서도 클라이언트는 500을 받았는데 필터의 finally에서 읽은 상태는 200이었다. 예외는 아직 스택을 타고 올라가는 중이고, 응답 상태를 500으로 바꾸는 것은 예외가 필터 체인을 모두 빠져나간 뒤 톰캣의 StandardWrapperValve가 하는 일이기 때문이다. 상태 코드를 정확히 기록하려면 예외를 잡아 "예외로 끝남"을 따로 기록한 뒤 다시 던져야 한다.

    요청 단위 값은 어디에 두는가: 스레드와 싱글톤

    요청 로그 필터에서 requestId를 지역 변수로 둔 것은 우연이 아니다. 필터는 인스턴스가 하나이고 여러 스레드가 동시에 실행하므로, 요청마다 달라야 하는 값을 필드에 두면 다른 요청이 덮어쓴다. 이 회차 뒤에서 만들 인터셉터도 스프링 빈으로 하나만 만들어 공유하므로 똑같다. 인터셉터는 preHandle과 afterCompletion이 서로 다른 메서드라서 값을 넘겨주고 싶은 유혹이 더 크다. 실제로 섞이는지 확인해 보자. 두 스레드의 실행 순서를 래치로 고정해 경쟁 상황을 결정적으로 재현했다.

    import java.util.concurrent.CountDownLatch;

public class SharedFieldRace {

    // 인터셉터처럼 하나의 인스턴스를 모든 요청이 공유한다
    static class BadLogInterceptor {
        private String requestId; // 요청마다 달라야 할 값을 필드에 둔 실수

        void preHandle(String id) { this.requestId = id; }
        String afterCompletion() { return this.requestId; }
    }

    public static void main(String[] args) throws InterruptedException {
        BadLogInterceptor shared = new BadLogInterceptor();
        CountDownLatch aStarted = new CountDownLatch(1);
        CountDownLatch bStarted = new CountDownLatch(1);

        Thread a = new Thread(() -> {
            shared.preHandle("A");
            aStarted.countDown();
            await(bStarted);                       // B가 preHandle을 끝낼 때까지 기다린다
            System.out.println("요청 A의 afterCompletion이 본 ID = " + shared.afterCompletion());
        }, "exec-1");

        Thread b = new Thread(() -> {
            await(aStarted);                       // A가 preHandle을 끝낸 뒤에 시작한다
            shared.preHandle("B");
            bStarted.countDown();
            System.out.println("요청 B의 afterCompletion이 본 ID = " + shared.afterCompletion());
        }, "exec-2");

        a.start(); b.start();
        a.join(); b.join();
    }

    static void await(CountDownLatch latch) {
        try { latch.await(); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }
}
    요청 A의 afterCompletion이 본 ID = B
요청 B의 afterCompletion이 본 ID = B

    요청 A는 자신이 넣은 "A" 대신 "B"를 읽었다. 필드 requestId는 힙의 BadLogInterceptor 객체 하나에 한 칸뿐이고, 두 스레드가 그 한 칸에 번갈아 쓰기 때문이다. 실제 서버에서는 래치가 없으므로 섞임이 가끔, 부하가 높을 때만 나타나고, 그래서 개발 중에는 발견되지 않다가 운영에서 "다른 사람의 로그 ID가 찍힌다"는 형태로 드러난다. 같은 실수를 로그인 회원 같은 값으로 저지르면 다른 사용자의 정보가 보이는 사고가 된다.

    요청 하나에 속한 값을 메서드 사이에 넘기는 올바른 자리는 세 곳이다. 첫째, 한 메서드 안에서 끝나면 지역 변수. 둘째, 같은 요청을 처리하는 여러 콜백 사이라면 요청 속성(request.setAttribute)이다. 요청 객체는 요청마다 따로 있고, 필터·인터셉터·컨트롤러가 모두 같은 요청 객체를 받으므로 그 요청에만 보이는 저장소가 된다. 셋째, 요청 객체를 인자로 받지 못하는 깊은 계층(로깅 프레임워크 등)까지 값을 전하려면 스레드 로컬(ThreadLocal)을 쓴다. 한 요청은 처음부터 끝까지 한 스레드에서 처리되므로(비동기 처리를 쓰지 않는 한), 스레드에 값을 묶어 두면 그 요청 처리 중 어디서나 꺼낼 수 있다. SLF4J의 MDC(Mapped Diagnostic Context)가 이런 방식으로 스레드마다 로그 문맥을 들고 다니며, 스프링의 FrameworkServlet도 요청 처리 직전에 RequestContextHolder(스레드 로컬)에 현재 요청을 묶고 finally에서 원래대로 되돌린다.

    스레드 로컬에는 반드시 지켜야 할 규칙이 있다. 넣은 쪽이 끝날 때 지운다. 톰캣의 작업 스레드는 요청마다 새로 만들어지지 않고 스레드 풀에서 재사용된다. 앞 요청이 남긴 값을 지우지 않으면 같은 스레드를 받은 다음 요청이 그 값을 본다. 스레드가 하나뿐인 풀로 재사용을 확정적으로 만들어 확인해 보자.

    import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;

public class ThreadLocalLeak {

    static final ThreadLocal CURRENT_USER = new ThreadLocal<>();

    public static void main(String[] args) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(1); // 스레드 하나를 재사용하는 풀

        pool.submit(() -> {
            CURRENT_USER.set("member-7");            // 요청 1: 값을 넣고
            System.out.println("[" + Thread.currentThread().getName() + "] 요청 1 처리, user=" + CURRENT_USER.get());
            // remove()를 하지 않고 끝낸다
        }).get();

        pool.submit(() -> {
            // 요청 2: 로그인하지 않은 사용자의 요청이라고 하자
            System.out.println("[" + Thread.currentThread().getName() + "] 요청 2 처리, user=" + CURRENT_USER.get());
        }).get();

        pool.shutdown();
    }
}
    [pool-1-thread-1] 요청 1 처리, user=member-7
[pool-1-thread-1] 요청 2 처리, user=member-7

    로그인하지 않은 요청 2가 요청 1의 회원으로 처리되었다. 스레드 로컬의 값은 Thread 객체가 가진 맵에 들어 있으므로 스레드가 살아 있는 한 사라지지 않는다. 그래서 필터에서 스레드 로컬을 쓴다면 chain.doFilter를 감싼 finally에서 remove()를, 인터셉터에서 쓴다면 예외가 나도 호출되는 afterCompletion에서 지워야 한다. 앞의 요청 로그 필터가 try/finally 구조를 가진 것이 바로 이런 정리 작업을 위한 자리다.

    인증 체크 필터: 허용 목록과 리다이렉트

    이제 본론인 로그인 확인이다. 정책부터 정하자. 보호할 경로를 나열하는 방식(거부 목록, denylist)과 로그인 없이 열어 둘 경로를 나열하는 방식(허용 목록, allowlist)이 있다. 거부 목록은 새 URL이 생길 때마다 목록에 추가하는 것을 잊으면 그 URL이 열린다. 허용 목록은 잊으면 그 URL이 닫힐 뿐이다. 실수가 났을 때 안전한 쪽으로 실패하는(fail-safe) 허용 목록을 쓰는 것이 보안 검사의 기본이다.

    package shop.web;

import jakarta.servlet.Filter;
import jakarta.servlet.FilterChain;
import jakarta.servlet.ServletException;
import jakarta.servlet.ServletRequest;
import jakarta.servlet.ServletResponse;
import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.servlet.http.HttpSession;
import org.springframework.util.PatternMatchUtils;

import java.io.IOException;
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;

public class SignInRequiredFilter implements Filter {

    // 로그인 없이 열어 두는 경로(허용 목록)
    private static final String[] PUBLIC_PATHS = {"/", "/members/new", "/login", "/logout", "/css/*"};

    @Override
    public void doFilter(ServletRequest request, ServletResponse response, FilterChain chain)
            throws IOException, ServletException {
        HttpServletRequest httpRequest = (HttpServletRequest) request;
        HttpServletResponse httpResponse = (HttpServletResponse) response;
        String uri = httpRequest.getRequestURI();

        if (!PatternMatchUtils.simpleMatch(PUBLIC_PATHS, uri)) {
            HttpSession session = httpRequest.getSession(false);   // 없으면 만들지 않는다
            if (session == null || session.getAttribute(SessionKeys.SIGNED_IN_MEMBER) == null) {
                String back = URLEncoder.encode(uri, StandardCharsets.UTF_8);
                httpResponse.sendRedirect("/login?redirectURL=" + back);
                return;                                            // 체인을 더 진행하지 않는다
            }
        }
        chain.doFilter(request, response);
    }
}

    SessionKeys.SIGNED_IN_MEMBER는 로그인할 때 세션에 회원을 넣은 키를 모아 둔 상수("signedInMember")다. 이 필터에서 판단이 갈리는 지점은 세 곳이다.

    첫째, getSession(false). 인자 없는 getSession()은 세션이 없으면 새로 만든다. 인증 확인 코드에서 그렇게 하면 로그인하지 않은 방문자, 검색 엔진 로봇, 단순 스캐너가 보호된 URL을 두드릴 때마다 서버 메모리에 빈 세션이 하나씩 생기고 응답마다 새 JSESSIONID 쿠키가 나간다. 세션은 만료 시간이 지나야 사라지므로 공격자가 반복 요청만으로 서버 메모리를 채울 수 있다. 확인만 하는 코드는 false로 "있으면 달라"고만 묻는다.

    둘째, return. 앞에서 본 호출 스택을 떠올리면 이 return의 의미가 분명하다. chain.doFilter를 부르지 않았으므로 체인의 pos는 다음 필터로 넘어가지 않고, DispatcherServlet도 컨트롤러도 실행되지 않는다. 필터는 sendRedirect로 302 응답과 Location 헤더를 직접 만들어 놓고 스택을 되돌아간다. 바깥쪽의 요청 로그 필터는 finally에서 이 요청의 응답 로그를 정상적으로 남긴다. 순서 값을 요청 로그 필터 1, 인증 체크 필터 2로 둔 이유가 여기 있다. 반대로 두면 인증에 실패한 요청은 로그에 아예 남지 않는다.

    셋째, 돌아갈 주소를 쿼리 파라미터로 붙이는 부분이다. 사용자가 /items/1/edit를 열려다가 로그인 화면으로 밀려났다면, 로그인 후 첫 화면이 아니라 원래 보려던 화면으로 보내 주는 것이 친절하다. URI를 쿼리 파라미터 값으로 넣을 때는 URLEncoder.encode로 인코딩해야 ?, &, # 같은 문자가 쿼리 구조를 깨뜨리지 않는다. 그 결과 Location: /login?redirectURL=%2Fitems%2F1%2Fedit가 나간다. 이 코드는 getRequestURI()만 쓰므로 원래 요청의 쿼리 문자열(getQueryString())은 버려진다는 점도 알아 두자.

    허용 목록 비교에 쓴 PatternMatchUtils.simpleMatch는 스프링 코어의 단순 문자열 와일드카드 비교다. 여기서 *는 경로 구분자 /를 포함한 임의의 문자열과 맞는다. Spring Framework 7.0.10으로 확인한 결과는 다음과 같다.

    마지막 줄처럼 simpleMatch의 *는 경로 단계를 넘나든다. 허용 목록에 /public*처럼 쓰면 /publicity/admin까지 열린다. 허용 목록의 패턴은 의도보다 넓게 열리지 않는지 하나씩 따져 봐야 한다.

    로그인 컨트롤러는 이 값을 받아 로그인 성공 후 그곳으로 보낸다. 로그인 폼이 redirectURL을 POST 요청에 다시 실어 보내야 하는데, 폼에 action 속성을 비워 두면 브라우저는 현재 문서의 URL(쿼리 문자열 포함)로 제출하므로 가장 간단히 해결된다. hidden 필드로 실어도 된다.

    @PostMapping("/login")
public String login(@RequestParam String loginId, @RequestParam String password,
                    @RequestParam(defaultValue = "/") String redirectURL,
                    HttpServletRequest request) {
    Member member = authenticate(loginId, password);
    if (member == null) {
        return "loginForm";                  // 실패 처리(오류 메시지 등)는 // ...
    }
    request.getSession().setAttribute(SessionKeys.SIGNED_IN_MEMBER, member);
    return "redirect:" + sameSiteOnly(redirectURL);
}

// 같은 사이트 안의 경로만 돌려보낸다
static String sameSiteOnly(String target) {
    boolean local = target.startsWith("/")
            && !target.startsWith("//")
            && !target.startsWith("/\\");
    return local ? target : "/";
}

    sameSiteOnly를 빼먹으면 오픈 리다이렉트(open redirect) 취약점이 된다. 공격자가 https://우리사이트/login?redirectURL=https://evil.example/login 같은 링크를 메일로 뿌리면, 피해자는 진짜 우리 사이트에서 로그인한 직후 공격자의 가짜 화면으로 넘어간다. 주소창의 첫 도메인이 진짜였으므로 의심하기 어렵다. /로 시작하는지만 보는 것으로는 부족하다. //evil.example은 RFC 3986의 네트워크 경로 참조(network-path reference)라서 브라우저가 다른 호스트로 해석하고, 브라우저가 따르는 WHATWG URL 표준은 http, https 같은 특수 스킴에서 역슬래시를 슬래시처럼 다루므로 /\evil.example도 같은 결과가 된다. 더 엄격하게 하려면 허용할 경로 목록과 비교한다.

    로그인 성공을 처리하는 컨트롤러는 getSession()(기본값 true)을 써야 한다. 로그인 성공 시점은 세션을 만들어야 하는 곳이기 때문이다. 반대로 확인만 하는 필터, 인터셉터, 리졸버는 모두 getSession(false)를 쓴다. 같은 API라도 "만드는 곳"과 "묻는 곳"을 구분하는 습관이 세션 남용을 막는다.

    스프링 인터셉터: DispatcherServlet 안쪽의 관문

    필터만으로도 로그인 확인은 충분히 된다. 그런데 필터는 서블릿 컨테이너의 부품이라서 스프링 MVC가 무엇을 하려는지 모른다. 필터가 아는 것은 URL과 요청·응답 객체뿐이다. 이 요청을 어느 컨트롤러의 어느 메서드가 처리할지, 그 메서드에 어떤 애너테이션이 붙어 있는지, 컨트롤러가 어떤 모델과 뷰를 돌려줬는지는 DispatcherServlet 안에서만 알 수 있다. 스프링 MVC는 그 안쪽에 또 하나의 길목을 마련해 두었고, 이것이 핸들러 인터셉터다.

    public interface HandlerInterceptor {

    default boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws Exception {
        return true;
    }

    default void postHandle(HttpServletRequest request, HttpServletResponse response, Object handler,
            @Nullable ModelAndView modelAndView) throws Exception {
    }

    default void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler,
            @Nullable Exception ex) throws Exception {
    }
}

    세 메서드 모두 기본 메서드이므로 필요한 것만 재정의한다. 필터의 doFilter 하나가 "앞 코드 → chain.doFilter → 뒤 코드"로 요청과 응답을 모두 감싸는 데 비해, 인터셉터는 그 구간을 세 시점으로 쪼갠다.

    콜백호출 시점호출 조건순서
    preHandle핸들러를 정한 뒤, 핸들러 어댑터가 핸들러를 실행하기 전항상(앞의 인터셉터가 true를 돌려준 경우)등록 순
    postHandle핸들러가 정상 반환한 뒤, 뷰 렌더링 전핸들러에서 예외가 나지 않았을 때만역순
    afterCompletion뷰 렌더링까지 모두 끝난 뒤자신의 preHandle이 true로 끝났다면 예외 여부와 관계없이역순

    세 메서드 모두 세 번째 인자로 Object handler를 받는다. 필터는 받을 수 없는 정보다. @RequestMapping 계열 컨트롤러가 처리하는 요청이면 이 객체는 HandlerMethod로, 어떤 빈의 어떤 메서드가 호출될지를 담고 있다. 정적 리소스 요청이면 ResourceHttpRequestHandler다. 인터셉터는 이것을 보고 "이 메서드에 특정 애너테이션이 붙어 있으면 확인을 건너뛴다" 같은 판단을 할 수 있다.

    preHandle의 반환값의 의미는 Javadoc에 정확히 적혀 있다. true면 다음 인터셉터나 핸들러로 진행하고, false면 DispatcherServlet은 이 인터셉터가 응답을 이미 스스로 처리했다고 가정한다. 즉 false를 돌려줄 때는 리다이렉트든 오류 응답이든 인터셉터가 응답을 만들어야 한다. 아무것도 쓰지 않고 false만 돌려주면 클라이언트는 본문 없는 200 응답을 받는다.

    실행 체인의 세 루프

    인터셉터가 언제 불리는지는 DispatcherServlet.doDispatch를 보면 정확히 알 수 있다. 다음은 Spring Framework 6.2 소스에서 이 회차와 관련된 줄만 남긴 것이다.

    HandlerExecutionChain mappedHandler = null;
try {
    ModelAndView mv = null;
    Exception dispatchException = null;
    try {
        // ... 멀티파트 요청 확인
        mappedHandler = getHandler(processedRequest);       // 핸들러 + 이 요청에 걸린 인터셉터들
        if (mappedHandler == null) {
            noHandlerFound(processedRequest, response);
            return;
        }
        HandlerAdapter ha = getHandlerAdapter(mappedHandler.getHandler());
        // ... Last-Modified 처리
        if (!mappedHandler.applyPreHandle(processedRequest, response)) {
            return;
        }
        mv = ha.handle(processedRequest, response, mappedHandler.getHandler());
        // ... 비동기 처리가 시작되었으면 반환
        applyDefaultViewName(processedRequest, mv);
        mappedHandler.applyPostHandle(processedRequest, response, mv);
    }
    catch (Exception ex) {
        dispatchException = ex;
    }
    // ... Throwable도 ServletException으로 감싸 dispatchException에 담는다
    processDispatchResult(processedRequest, response, mappedHandler, mv, dispatchException);
}
catch (Exception ex) {
    triggerAfterCompletion(processedRequest, response, mappedHandler, ex);
}
// ... finally: 비동기 처리, 멀티파트 정리

    getHandler는 등록된 핸들러 매핑(handler mapping)들에게 차례로 물어 이 요청을 처리할 핸들러를 찾고, 결과를 HandlerExecutionChain이라는 객체로 돌려준다. 이 객체를 만드는 것은 AbstractHandlerMapping.getHandlerExecutionChain인데, 요청마다 new HandlerExecutionChain(handler)로 새로 만들고 매핑에 등록된 인터셉터를 하나씩 보면서 경로 패턴이 있는 인터셉터(MappedInterceptor)는 이 요청의 경로와 맞을 때만 넣는다. 그러므로 어떤 인터셉터가 실행될지는 preHandle이 시작되기 전, 핸들러를 찾는 시점에 이미 정해진다. 핸들러를 찾지 못하면(mappedHandler == null) 체인이 없으므로 인터셉터는 하나도 실행되지 않는다.

    체인 안의 세 메서드는 이렇게 생겼다. Spring Framework 6.2와 7.0.10의 이 부분 코드는 오류 로그 문구 하나만 다르다.

    private int interceptorIndex = -1;   // preHandle이 true로 끝난 마지막 인터셉터의 위치

boolean applyPreHandle(HttpServletRequest request, HttpServletResponse response) throws Exception {
    for (int i = 0; i < this.interceptorList.size(); i++) {
        HandlerInterceptor interceptor = this.interceptorList.get(i);
        if (!interceptor.preHandle(request, response, this.handler)) {
            triggerAfterCompletion(request, response, null);
            return false;
        }
        this.interceptorIndex = i;
    }
    return true;
}

void applyPostHandle(HttpServletRequest request, HttpServletResponse response, @Nullable ModelAndView mv)
        throws Exception {
    for (int i = this.interceptorList.size() - 1; i >= 0; i--) {
        HandlerInterceptor interceptor = this.interceptorList.get(i);
        interceptor.postHandle(request, response, this.handler, mv);
    }
}

void triggerAfterCompletion(HttpServletRequest request, HttpServletResponse response, @Nullable Exception ex) {
    for (int i = this.interceptorIndex; i >= 0; i--) {
        HandlerInterceptor interceptor = this.interceptorList.get(i);
        try {
            interceptor.afterCompletion(request, response, this.handler, ex);
        }
        catch (Throwable ex2) {
            logger.error("HandlerInterceptor.afterCompletion threw exception", ex2);
        }
    }
}

    필터 체인이 재귀였다면 인터셉터 체인은 세 개의 반복문이다. 필터는 스택을 이용해 역순을 자연스럽게 얻었지만, 인터셉터는 역방향 루프로 역순을 직접 만든다. 그리고 "누가 preHandle을 통과했는가"를 스택 대신 interceptorIndex라는 정수 하나로 기억한다. 이 코드에서 다음 규칙들이 그대로 읽힌다.

    • preHandle은 0번부터 순서대로 불린다. i번째가 true를 돌려줄 때마다 interceptorIndex가 i로 올라간다.
    • i번째가 false를 돌려주면 interceptorIndex는 i−1에 머문 채로 triggerAfterCompletion이 불린다. 따라서 앞서 통과한 0 ~ i−1번의 afterCompletion만 역순으로 실행되고, false를 돌려준 자신과 그 뒤의 인터셉터는 afterCompletion을 받지 못한다.
    • i번째의 preHandle이 false 대신 예외를 던지면 applyPreHandle 안에서는 아무 정리도 하지 않고 예외가 doDispatch로 올라간다. 그 뒤 processDispatchResult나 바깥 catch가 triggerAfterCompletion을 부르므로 결과는 같다. 0 ~ i−1번만 afterCompletion을 받는다.
    • postHandle은 핸들러가 예외 없이 반환한 경우에만, 마지막 인터셉터부터 역순으로 불린다. 예외가 나면 try 블록을 벗어나므로 applyPostHandle 줄에 도달하지 않는다.
    • afterCompletion 안에서 터진 예외는 로그만 남기고 삼킨다. 한 인터셉터의 정리 작업 실패가 다른 인터셉터의 정리 작업을 막지 않게 하려는 것이다.

    afterCompletion이 받는 예외 인자 ex에도 규칙이 있다. processDispatchResult는 예외가 있으면 먼저 예외 리졸버(exception resolver, 09회의 주제)에게 처리를 맡기고, 처리되었으면 뷰를 렌더링한 뒤 triggerAfterCompletion(request, response, null)을 부른다. 처리되지 못한 예외는 다시 던져져 바깥 catch에서 triggerAfterCompletion(..., ex)로 전달되고, 그 뒤 다시 던져진다. 그래서 Javadoc의 표현대로 ex에는 "예외 리졸버가 처리한 예외는 포함되지 않는다". @ExceptionHandler가 처리한 예외를 afterCompletion에서 기다리고 있으면 영원히 null만 보게 된다.

    Spring Framework 7.0에서는 doDispatch가 조금 바뀌어 핸들러 어댑터 조회가 applyPreHandle 뒤로 옮겨졌고 Last-Modified 처리 블록이 빠졌다. 인터셉터 세 콜백의 호출 순서와 조건은 같다.

    실제로 돌려 본 호출 순서

    소스를 읽은 결론이 맞는지 직접 확인해 보자. 스프링 부트 없이 내장 톰캣 11.0.27과 Spring Framework 7.0.10으로 작은 서버를 띄우고, 필터 두 개(F1, F2)와 인터셉터 세 개(I1, I2, I3)를 걸었다. 각 콜백은 자기 이름을 출력한다. I2는 /blocked 요청에만 false를 돌려주며 리다이렉트한다. postHandle은 응답이 이미 커밋되었는지(isCommitted())를 출력한 뒤 응답 헤더 X-I1 등을 추가해 본다.

    static class TraceFilter implements Filter {
    final String name;
    TraceFilter(String name) { this.name = name; }
    public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) throws IOException, ServletException {
        log(name + " 들어감 (" + req.getClass().getSimpleName() + ", chain=" + chain.getClass().getSimpleName() + ")");
        try { chain.doFilter(req, res); }
        finally { log(name + " 나옴 status=" + ((HttpServletResponse) res).getStatus()); }
    }
}

static class TraceInterceptor implements HandlerInterceptor {
    final String name; final boolean block;
    TraceInterceptor(String name, boolean block) { this.name = name; this.block = block; }
    public boolean preHandle(HttpServletRequest req, HttpServletResponse res, Object handler) throws Exception {
        boolean go = !(block && req.getRequestURI().equals("/blocked"));
        log(name + ".preHandle -> " + go + " handler=" + handler.getClass().getSimpleName());
        if (!go) res.sendRedirect("/login?redirectURL=" + req.getRequestURI());
        return go;
    }
    public void postHandle(HttpServletRequest req, HttpServletResponse res, Object handler, ModelAndView mv) {
        log(name + ".postHandle mv=" + (mv == null ? "null" : "있음") + " committed=" + res.isCommitted());
        res.setHeader("X-" + name, "post");
    }
    public void afterCompletion(HttpServletRequest req, HttpServletResponse res, Object handler, Exception ex) {
        log(name + ".afterCompletion ex=" + (ex == null ? "null" : ex.getClass().getSimpleName()));
    }
}

    인터셉터로 다시 쓴 요청 로그와 인증 체크

    이제 같은 두 기능을 인터셉터로 만들어 보자. 요청 로그 인터셉터는 preHandle에서 만든 ID를 afterCompletion에서 써야 한다. 앞 절의 실험대로 필드에 둘 수는 없으므로 요청 속성에 담는다. 키는 다른 코드의 속성과 겹치지 않도록 클래스 이름을 접두어로 쓴다.

    package shop.web;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.web.method.HandlerMethod;
import org.springframework.web.servlet.HandlerInterceptor;
import org.springframework.web.servlet.ModelAndView;

import java.util.UUID;

public class AccessLogInterceptor implements HandlerInterceptor {

    private static final Logger log = LoggerFactory.getLogger(AccessLogInterceptor.class);
    private static final String REQUEST_ID = AccessLogInterceptor.class.getName() + ".REQUEST_ID";

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        String requestId = UUID.randomUUID().toString().substring(0, 8);
        request.setAttribute(REQUEST_ID, requestId);           // 필드가 아니라 요청에 둔다

        if (handler instanceof HandlerMethod hm) {
            log.info("REQ [{}] {} -> {}#{}", requestId, request.getRequestURI(),
                    hm.getBeanType().getSimpleName(), hm.getMethod().getName());
        } else {
            log.info("REQ [{}] {} -> {}", requestId, request.getRequestURI(),
                    handler.getClass().getSimpleName());
        }
        return true;
    }

    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response,
                           Object handler, ModelAndView modelAndView) {
        log.info("POST [{}] view={}", request.getAttribute(REQUEST_ID),
                modelAndView == null ? null : modelAndView.getViewName());
    }

    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response,
                                Object handler, Exception ex) {
        log.info("RES [{}] status={}", request.getAttribute(REQUEST_ID), response.getStatus());
        if (ex != null) {
            log.error("처리되지 않은 예외", ex);
        }
    }
}

    필터 버전과 비교하면 두 가지가 나아졌다. 로그에 어떤 컨트롤러의 어떤 메서드가 처리하는지(HandlerMethod) 남길 수 있고, postHandle에서 선택된 뷰 이름도 볼 수 있다. 대신 try/finally 하나로 끝나던 것이 세 메서드로 나뉘면서 값을 요청 속성으로 넘겨야 하는 수고가 생겼다. afterCompletion에서 읽은 상태 코드는 필터의 finally보다 정확할까? 그렇지 않다. 예외 리졸버가 처리하지 못한 예외라면 이 시점에도 컨테이너가 아직 500을 설정하지 않았으므로 같은 문제가 있다. 대신 ex 인자로 "처리되지 않은 예외로 끝났다"는 사실을 알 수 있다.

    인증 체크 인터셉터는 preHandle 하나면 된다.

    package shop.web;

import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import jakarta.servlet.http.HttpSession;
import org.springframework.web.servlet.HandlerInterceptor;

import java.io.IOException;
import java.net.URLEncoder;
import java.nio.charset.StandardCharsets;

public class SignInRequiredInterceptor implements HandlerInterceptor {

    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler)
            throws IOException {
        HttpSession session = request.getSession(false);
        if (session == null || session.getAttribute(SessionKeys.SIGNED_IN_MEMBER) == null) {
            String back = URLEncoder.encode(request.getRequestURI(), StandardCharsets.UTF_8);
            response.sendRedirect("/login?redirectURL=" + back);
            return false;      // 핸들러도, 뒤의 인터셉터도 실행되지 않는다
        }
        return true;
    }
}

    필터 버전에 있던 허용 목록 비교가 사라졌다. 어디에 적용할지는 코드가 아니라 등록할 때 정한다.

    @Override
public void addInterceptors(InterceptorRegistry registry) {
    registry.addInterceptor(new AccessLogInterceptor())
            .order(1)
            .addPathPatterns("/**")
            .excludePathPatterns("/css/**", "/*.ico", "/error");

    registry.addInterceptor(new SignInRequiredInterceptor())
            .order(2)
            .addPathPatterns("/**")
            .excludePathPatterns("/", "/members/new", "/login", "/logout",
                    "/css/**", "/*.ico", "/error");
}

    이 메서드는 앞에서 만든 WebConfig(WebMvcConfigurer 구현)에 추가한다. 경로 패턴이 하나라도 지정되면 등록 객체는 인터셉터를 MappedInterceptor로 감싸고, 핸들러 매핑이 실행 체인을 만들 때 matches로 요청 경로를 비교한다. 이때 제외 패턴을 먼저 검사해서 하나라도 맞으면 즉시 제외하고, 그다음 포함 패턴을 본다. 포함 패턴을 하나도 주지 않으면 제외에 걸리지 않은 모든 경로가 대상이다. order의 기본값은 0이며, 같은 값끼리는 등록한 순서를 유지한다.

    /error를 제외하는 이유는 08회에서 자세히 보는데, 요약하면 처리되지 않은 예외나 sendError가 생기면 컨테이너가 오류 페이지 경로(부트의 기본값 /error)로 ERROR 디스패치를 하고, 그때 DispatcherServlet이 다시 실행되면서 인터셉터도 다시 실행되기 때문이다. 제외하지 않으면 요청 로그가 두 번 찍히고, 인증 인터셉터는 오류 화면을 로그인 화면으로 바꿔 버린다.

    여기서 쓰는 패턴은 서블릿 URL 패턴이 아니라 스프링의 PathPattern 문법이다. Spring Framework 6.0부터 스프링 MVC는 기본으로 PathPattern을 쓴다. 헷갈리기 쉬운 경우를 Spring Framework 7.0.10의 PathPatternParser로 직접 확인했다.

    패턴경로일치설명
    /css/**/csstrue**는 0개 이상의 경로 단계
    /css/**/css/a/b.csstrue여러 단계도 일치
    /items/*/itemsfalse*는 한 단계 안의 0개 이상 문자. 단계 자체가 없으면 불일치
    /items/*/items/1/editfalse*는 /를 넘지 못한다
    /*.ico/favicon.icotrue한 단계 안에서 확장자 일치
    /*.ico/img/favicon.icofalse단계가 하나 더 있다
    /**/true모든 경로

    필터의 simpleMatch에서 /css/*가 /css/a/b.css와 맞았던 것과 달리, PathPattern의 *는 경로 단계 하나 안에서만 맞는다. 여러 단계를 넘으려면 **를 써야 하고, **는 패턴의 가운데에 둘 수 없다. 7.0.10에서 /css/**/x.css를 파싱하면 PatternParseException이 나고, 6.2 문서도 /resources/**/file.png를 잘못된 패턴으로 예시한다.

    그렇다면 로그인 확인은 어디가 맞는가? 스프링 프레임워크 레퍼런스는 이 질문에 대해 분명한 입장을 적어 두었다. 인터셉터의 경로 매칭과 애노테이션 컨트롤러의 경로 매칭이 서로 어긋날 가능성이 있으므로 인터셉터는 보안 계층으로 이상적이지 않으며, 스프링 시큐리티나 그와 비슷하게 서블릿 필터 체인에 통합되어 가능한 한 일찍 적용되는 방식을 권장한다는 것이다. 이유를 풀어 보면, 인터셉터의 포함·제외 패턴은 컨트롤러의 @RequestMapping과는 별개로 평가되는 또 하나의 목록이다. 두 목록이 언제나 같은 URL 집합을 가리킨다는 보장은 사람의 주의력에만 달려 있다. 또 인터셉터는 DispatcherServlet을 지나는 요청만 보므로, 다른 서블릿이 처리하는 요청이나 핸들러를 찾지 못한 요청에는 끼어들 수 없다.

    실제로 스프링 시큐리티의 서블릿 지원은 서블릿 필터 위에 만들어져 있다. 서블릿 컨테이너에는 DelegatingFilterProxy라는 필터를 등록하고, 이 필터가 스프링 빈인 FilterChainProxy에 일을 넘기며, FilterChainProxy가 요청에 맞는 SecurityFilterChain을 골라 그 안의 보안 필터들을 실행한다. 컨테이너는 스프링 빈을 모르므로 둘 사이를 잇는 다리가 필요한 것이다. 이번 회차에서 만든 인증 필터는 그 구조의 가장 단순한 형태라고 볼 수 있다.

    그렇다고 인터셉터가 쓸모없는 것은 아니다. 핸들러 정보가 필요한 일(어떤 컨트롤러 메서드가 호출되는지에 따른 처리, 모델에 공통 값 추가), 스프링 빈과 설정을 자연스럽게 쓰는 일, 경로 패턴으로 적용 범위를 선언적으로 관리하는 일에는 인터셉터가 더 편하다. 정리하면 이렇다. 요청·응답 객체 자체를 바꾸거나, 스프링 MVC 바깥의 요청까지 다뤄야 하거나, 보안처럼 가능한 한 일찍 막아야 하는 일은 필터에 둔다. 스프링 MVC의 핸들러 문맥이 필요한 일은 인터셉터에 둔다.

    ArgumentResolver로 로그인 회원 꺼내기

    인증 체크가 길목으로 빠졌어도 컨트롤러에는 여전히 반복이 남는다. 로그인한 회원의 정보가 필요한 컨트롤러는 매번 세션을 꺼내 속성을 읽고 캐스팅해야 한다. 스프링의 @SessionAttribute로 줄일 수는 있지만, 세션 키 문자열이 모든 컨트롤러에 퍼지고 "로그인 회원을 어디서 어떻게 가져오는가"라는 결정이 컨트롤러마다 박힌다. 원하는 모습은 이렇다.

    @GetMapping("/")
public String home(@CurrentMember Member member, Model model) {
    if (member == null) {
        return "home";                       // 로그인 전 첫 화면
    }
    model.addAttribute("member", member);
    return "signedInHome";
}

    컨트롤러는 "현재 회원을 달라"고만 말하고, 그것이 세션에서 오는지 토큰에서 오는지는 모른다. @RequestParam, @ModelAttribute, HttpServletRequest 같은 파라미터를 채우는 것은 RequestMappingHandlerAdapter가 들고 있는 핸들러 메서드 인자 리졸버(HandlerMethodArgumentResolver)들이다. 같은 인터페이스를 구현해 목록에 하나 더 끼워 넣으면 된다. 먼저 표시용 애너테이션을 만든다.

import jakarta.servlet.http.HttpServletRequest;

import org.springframework.web.method.support.ModelAndViewContainer;

public class CurrentMemberArgumentResolver implements HandlerMethodArgumentResolver {

    @Override
    public boolean supportsParameter(MethodParameter parameter) {
        return parameter.hasParameterAnnotation(CurrentMember.class)
                && Member.class.isAssignableFrom(parameter.getParameterType());
    }

    @Override
    public Object resolveArgument(MethodParameter parameter, ModelAndViewContainer mavContainer,
                                  NativeWebRequest webRequest, WebDataBinderFactory binderFactory) {
        HttpServletRequest request = webRequest.getNativeRequest(HttpServletRequest.class);
        HttpSession session = request.getSession(false);
        if (session == null) {
            return null;
        }
        return session.getAttribute(SessionKeys.SIGNED_IN_MEMBER);
    }
}
    @Override
public void addArgumentResolvers(List resolvers) {
    resolvers.add(new CurrentMemberArgumentResolver());
}

    supportsParameter는 애너테이션과 타입을 함께 확인한다. 애너테이션만 보면 누군가 @CurrentMember String name처럼 잘못 쓴 경우 resolveArgument가 Member를 돌려주어 호출 직전에 타입 불일치 오류가 난다. 둘 다 확인하면 잘못 쓴 파라미터는 이 리졸버의 대상이 아니게 된다. resolveArgument는 인터셉터와 마찬가지로 getSession(false)로 묻기만 하고, 세션이나 회원이 없으면 null을 돌려준다. 로그인 전에도 열리는 첫 화면(/)에서 null로 분기할 수 있는 이유다. 이 리졸버 역시 하나의 인스턴스를 모든 요청이 공유하므로 필드에 아무 상태도 두지 않았다.

    리졸버는 어떤 순서로 선택되는가

    addArgumentResolvers로 추가한 리졸버는 목록의 어디에 들어갈까? Spring Framework 6.2의 RequestMappingHandlerAdapter.getDefaultArgumentResolvers는 리졸버 목록을 네 구역으로 만든다.

    구역예판단 기준
    1. 애너테이션 기반@RequestParam, @PathVariable, @ModelAttribute, @RequestBody, @RequestHeader, @CookieValue, @SessionAttribute, @RequestAttribute 등해당 애너테이션이 붙었는가
    2. 타입 기반ServletRequest, ServletResponse, HttpEntity, RedirectAttributes, Model, Map, Errors, SessionStatus, UriComponentsBuilder파라미터 타입
    3. 사용자 정의addArgumentResolvers로 넣은 것각 리졸버의 supportsParameter
    4. 나머지 전부(catch-all)Principal, 애너테이션 없는 단순 타입 → @RequestParam, 애너테이션 없는 그 밖의 타입 → @ModelAttribute앞에서 아무도 맡지 않은 파라미터

    사용자 정의 리졸버는 기본 리졸버 뒤, 마지막 catch-all 앞에 들어간다. WebMvcConfigurer의 Javadoc도 이 방법은 기본 인자 처리를 덮어쓰지 않으며, 기본 처리를 바꾸려면 RequestMappingHandlerAdapter를 직접 설정하라고 적고 있다. 그래서 @CurrentMember Member는 안전하게 우리 리졸버에 도달한다. 구역 1의 리졸버들은 자기 애너테이션이 아니므로 지나치고, 구역 2의 리졸버들은 Member 타입을 모르므로 지나친다. 구역 1의 @ModelAttribute 리졸버는 애너테이션이 붙은 경우만 맡도록 설정된 인스턴스라서 역시 지나친다.

    매 요청마다 수십 개의 supportsParameter를 차례로 부르는 것은 아니다. HandlerMethodArgumentResolverComposite는 파라미터(MethodParameter)를 키로 하는 ConcurrentHashMap 캐시를 두고, 처음 한 번만 목록을 훑어 찾은 리졸버를 저장한다. 실험에서 supportsParameter에 출력을 넣고 같은 URL을 네 번 요청했더니 출력은 첫 요청에서 한 번만 나왔다. 따라서 supportsParameter는 요청 내용(세션, 헤더)에 따라 답이 달라지면 안 된다. 메서드 시그니처만 보고 판단해야 한다. 요청에 따라 달라지는 판단은 resolveArgument의 몫이다.

    파라미터 "@CurrentMember Member member" 의 리졸버 찾기 (첫 요청)

  [구역 1] RequestParam(애너테이션 필수) ...... @RequestParam 없음 → 통과
           PathVariable / ModelAttribute(애너테이션 필수) / RequestBody ... → 통과
  [구역 2] ServletRequest / Model / Map / Errors ... 타입 불일치 → 통과
  [구역 3] CurrentMemberArgumentResolver ....... 애너테이션 O, 타입 O → 선택!
           → 캐시에 (이 파라미터 → 이 리졸버) 저장
  [구역 4] (도달하지 않음)

  두 번째 요청부터: 캐시에서 바로 꺼낸다

    이 순서 때문에 생기는 함정이 두 가지 있다. 첫째, 등록을 빠뜨렸을 때다. 리졸버를 만들고 addArgumentResolvers에 넣는 것을 잊으면 예외가 날 것 같지만 그렇지 않다. 구역 4의 catch-all이 Member를 애너테이션 없는 객체 파라미터로 보고 @ModelAttribute처럼 처리한다. 즉 새 Member를 만들고 요청 파라미터를 바인딩한다. 실험(Spring Framework 7.0.10, Member는 레코드, -parameters 옵션으로 컴파일)에서 리졸버 등록을 뺀 채 GET /me?id=1&loginId=admin&name=x를 보내자 컨트롤러는 Member[id=1, loginId=admin, name=x]를 받았다. 로그인하지 않은 사용자가 쿼리 파라미터만으로 아무 회원이나 될 수 있는 것이다. 이 실수는 컴파일도 되고 기동도 되며 오류 로그도 남기지 않는다.

    둘째, @Retention(RUNTIME)을 빠뜨렸을 때다. 결과는 첫째와 같다. 리졸버를 등록했어도 hasParameterAnnotation이 false를 돌려주므로 catch-all까지 떨어진다. 원인은 JLS §9.6.4.2에 있다. 애너테이션 인터페이스에 @Retention이 없으면 컴파일러는 RetentionPolicy.CLASS로 취급하고, 실행 시점에 리플렉션으로 볼 수 있게 보장되는 것은 RUNTIME뿐이다. 바이트코드에서 직접 확인할 수 있다.

    import java.lang.annotation.*;
import java.lang.reflect.Method;
import java.util.Arrays;

public class RetentionCheck {
    @Target(ElementType.PARAMETER)
    @interface NoRetention {}                       // @Retention을 생략했다

    @Target(ElementType.PARAMETER)
    @Retention(RetentionPolicy.RUNTIME)
    @interface RuntimeRetention {}

    void a(@NoRetention String s) {}
    void b(@RuntimeRetention String s) {}

    public static void main(String[] args) throws Exception {
        for (String name : new String[]{"a", "b"}) {
            Method m = RetentionCheck.class.getDeclaredMethod(name, String.class);
            System.out.println(name + " 파라미터 애너테이션 = " + Arrays.toString(m.getParameterAnnotations()[0]));
        }
    }
}
    a 파라미터 애너테이션 = []
b 파라미터 애너테이션 = [@RetentionCheck.RuntimeRetention()]

  void a(java.lang.String);
    RuntimeInvisibleParameterAnnotations:
      parameter 0:
        0: #52()
          RetentionCheck$NoRetention
  void b(java.lang.String);
    RuntimeVisibleParameterAnnotations:
      parameter 0:
        0: #54()
          RetentionCheck$RuntimeRetention

    두 애너테이션 모두 클래스 파일에는 기록되었다. 차이는 어느 속성(attribute)에 들어갔느냐다. @Retention을 생략한 쪽은 RuntimeInvisibleParameterAnnotations에, RUNTIME 쪽은 RuntimeVisibleParameterAnnotations에 들어갔다. JLS는 RUNTIME 보존 애너테이션만 리플렉션 라이브러리가 실행 시점에 제공하도록 요구하며, JDK 21의 getParameterAnnotations()도 a에 대해 빈 배열을 돌려주었다. 스프링의 MethodParameter.hasParameterAnnotation도 결국 이 리플렉션 결과를 쓰므로 같은 이유로 false가 된다. 프레임워크가 읽어야 하는 애너테이션을 만들 때 @Retention(RetentionPolicy.RUNTIME)은 선택이 아니다.

    컨트롤러 파라미터 하나에 대해 리졸버 목록을 위에서부터 훑어 처음 supportsParameter가 true인 리졸버를 고르고 캐시에 저장하는 과정, 그리고 등록을 빠뜨렸을 때 catch-all로 떨어지는 경로를 보여 준다. Vertical flowchart, white background.     마지막으로, 리졸버는 인터셉터가 대신할 수 있는 일을 하는 것이 아니라 그 뒤를 잇는 것이다. 인증 인터셉터(또는 필터)가 "로그인하지 않은 요청은 들어오지 못한다"를 보장하고, 리졸버는 "들어온 요청에서 회원을 꺼내 준다"를 맡는다. 리졸버만 있고 인증 길목이 없으면 보호된 화면에서 member가 null인 채로 실행된다. 반대로 인증 길목만 있으면 컨트롤러마다 세션 꺼내기가 반복된다. 둘을 함께 두면 "보호"와 "조회"가 각각 한 곳에만 존재하게 된다.

    이 장의 핵심

    요청 하나는 한 작업 스레드의 호출 스택 위에서 처리된다. 필터는 서블릿 컨테이너가 그 스택의 바깥쪽에 재귀로 쌓는 관문이고, 인터셉터는 DispatcherServlet이 안쪽에서 반복문과 interceptorIndex로 관리하는 관문이며, 인자 리졸버는 컨트롤러 호출 직전에 파라미터를 채우는 마지막 단계다. 셋 다 인스턴스 하나를 모든 스레드가 공유하므로 요청별 값은 지역 변수, 요청 속성, 그리고 반드시 지우는 스레드 로컬에만 둔다. 보안 검사는 빠뜨릴 수 없는 길목(가능하면 필터)에, 허용 목록 방식으로, getSession(false)로 묻는다.
    공통 관심사와 길목
    로그인 확인·요청 로그처럼 여러 기능에 걸친 처리는 요청이 반드시 지나는 길목에 한 번만 둔다. 웹 계층의 길목은 서블릿 필터와 스프링 인터셉터 두 층이다.
    필터 인스턴스와 스레드
    서블릿 명세는 필터 선언 하나당 JVM에 인스턴스 하나만 만든다. 여러 작업 스레드가 같은 doFilter를 동시에 실행하므로 요청별 값은 필드에 두지 않는다.
    필터 체인의 재귀 구조
    톰캣 ApplicationFilterChain은 pos번째 필터에 자신을 넘기고, 필터가 chain.doFilter를 부르면 다음 필터로, 끝이면 서블릿으로 간다. 앞 코드는 순서대로, 뒤 코드는 역순으로 실행된다.
    필터 등록과 순서
    부트의 FilterRegistrationBean은 순서 값이 작은 것을 바깥에 둔다. 기본 순서는 가장 낮은 우선순위, 기본 URL은 /*, 기본 디스패처 타입은 REQUEST(OncePerRequestFilter면 전부)다.
    인터셉터 세 콜백
    preHandle은 등록 순, postHandle과 afterCompletion은 역순이다. postHandle은 핸들러가 정상 반환할 때만, afterCompletion은 자신의 preHandle이 true였으면 항상 불린다.
    interceptorIndex
    preHandle을 통과한 마지막 위치를 기억하는 정수다. false나 예외가 나면 그 위치부터 0번까지 역순으로 afterCompletion을 부른다.
    응답 커밋과 postHandle
    @ResponseBody나 ResponseEntity는 핸들러 어댑터 안에서 본문을 쓰고 커밋하므로 postHandle에서 헤더를 바꿀 수 없다. 이때는 ResponseBodyAdvice를 쓴다.
    PathPattern과 제외 우선
    인터셉터 경로는 PathPattern 문법으로 *는 한 단계, **는 0개 이상 단계이며 패턴 가운데에 둘 수 없다. 제외 패턴이 포함 패턴보다 먼저 검사된다.
    사용자 정의 인자 리졸버
    기본 리졸버 뒤, catch-all 앞에 들어가며 파라미터별로 캐시된다. 등록이나 @Retention(RUNTIME)을 빠뜨리면 파라미터가 @ModelAttribute처럼 요청 파라미터로 바인딩된다.

    운영 중인 서비스에서 "가끔 다른 사람 이름이 화면에 보인다"는 신고가 들어오면 가장 먼저 의심할 곳이 싱글톤 컴포넌트의 필드와 지우지 않은 스레드 로컬이다. 필터, 인터셉터, 리졸버, 컨트롤러, 서비스는 모두 인스턴스 하나를 수백 개의 작업 스레드가 공유하고, 작업 스레드는 풀에서 재사용된다. 이 현상은 동시 요청이 몰릴 때만 드러나므로 개발 환경의 단건 테스트로는 재현되지 않는다. 코드 리뷰에서 이런 클래스에 변경 가능한 인스턴스 필드가 보이면 그 값이 요청마다 달라지는지를 바로 물어야 한다.

    로그인 확인을 필터에 둘지 인터셉터에 둘지는 "무엇이 그 길목을 우회할 수 있는가"로 판단한다. 애플리케이션이 DispatcherServlet 하나만 쓰고 정적 리소스도 그 안에서 처리된다면 인터셉터로도 대부분의 요청을 덮는다. 그러나 다른 서블릿이 함께 있거나, 오류 디스패치나 포워드 경로가 섞이거나, 인증 규칙이 복잡해지면 경로 목록 두 개(인터셉터 패턴과 컨트롤러 매핑)를 사람이 맞춰야 하는 부담이 커진다. 스프링 레퍼런스가 보안을 필터 체인에 두라고 권하는 이유가 이것이고, 규모가 커지면 직접 만든 필터 대신 스프링 시큐리티로 옮겨 가는 것이 자연스럽다.

    장애 분석에서는 실행 순서 지식이 직접 쓰인다. 예외가 났는데 인터셉터의 postHandle에서 남기려던 로그가 없다면 정상이다. afterCompletion의 ex가 null인데 사용자는 오류 화면을 봤다면 예외 리졸버가 예외를 처리한 것이다. 필터의 응답 로그에 200이 찍혔는데 클라이언트는 500을 받았다면 예외가 필터를 통과한 뒤 컨테이너가 상태를 바꾼 것이다. 각 관찰이 호출 스택의 어느 지점에서 이루어졌는지를 알면 로그끼리 모순처럼 보이는 상황도 설명된다.
  • 필터 F1(order 1), F2(order 2)와 인터셉터 I1, I2, I3(이 순서로 등록)가 있다. 컨트롤러는 정상이고, I3의 preHandle이 false를 돌려주는 대신 RuntimeException을 던진다. 예외 리졸버는 이 예외를 처리하지 못한다. 출력될 콜백 순서를 모두 쓰고, 각 afterCompletion이 받는 ex가 무엇인지 적어라.
  • 동료가 인증 필터에서 getSession(false) 대신 getSession()을 쓰고 있다. 로그인 확인 결과 자체는 똑같이 나온다. 그렇다면 무엇이 문제인지, 로그인하지 않은 클라이언트가 쿠키 없이 보호된 URL을 1만 번 요청하는 상황으로 설명하라.
  • 요청 로그 인터셉터를 private String requestId; 필드에 ID를 저장하도록 작성했더니, 부하 테스트에서 REQ [3f2a...]와 짝이 맞지 않는 RES 로그가 생겼다. 원인을 메모리(힙의 객체와 스레드 스택) 그림으로 설명하고, 두 가지 수정 방법을 제시하라.
  • @CurrentMember 애너테이션과 리졸버를 만들고 컨트롤러 orders(@CurrentMember Member member)를 작성했지만 WebConfig에 등록하는 것을 잊었다. 로그인하지 않은 상태에서 GET /orders?id=3&loginId=admin을 보내면 member에는 무엇이 들어오는가? 인증 인터셉터가 /orders를 보호하고 있을 때와 없을 때로 나누어 답하라.
  • 요청 로그 필터의 finally에서 getStatus()를 찍었더니 처리되지 않은 예외로 끝난 요청도 200으로 기록된다. 호출 스택 관점에서 이유를 설명하고, 필터 코드만 고쳐서 "예외로 끝났음"을 정확히 기록하는 방법을 써라.

    1. F1 들어감 → F2 들어감 → I1.preHandle → I2.preHandle → I3.preHandle(예외) → I2.afterCompletion(ex=RuntimeException) → I1.afterCompletion(ex=RuntimeException) → F2 나옴 → F1 나옴. applyPreHandle은 i=0, 1에서 interceptorIndex를 1까지 올렸고, i=2에서 예외가 나자 루프 안에서는 아무 정리 없이 예외가 doDispatch로 올라간다. 핸들러와 postHandle은 실행되지 않는다. processDispatchResult가 예외 리졸버에 넘겼지만 처리되지 않아 다시 던져지고, 바깥 catch의 triggerAfterCompletion(..., ex)가 interceptorIndex 1부터 역순으로 부른다. I3는 preHandle을 성공적으로 마치지 못했으므로 afterCompletion을 받지 않는다. 그 뒤 예외는 필터를 거쳐 컨테이너까지 올라간다.

    2. getSession()은 세션이 없으면 새로 만든다. 쿠키가 없는 클라이언트는 매 요청마다 세션이 없으므로 1만 번의 요청이 서버 메모리에 빈 세션 1만 개를 만들고, 각각이 만료 시간까지 남는다. 응답마다 새 JSESSIONID 쿠키도 내려간다. 확인 결과(속성이 null이므로 리다이렉트)는 같지만 서버 자원이 공격자의 요청 수에 비례해 소모된다. 확인만 하는 코드는 getSession(false)로 바꾸고, 세션 생성은 로그인 성공 지점 한 곳에만 둔다.

    3. 인터셉터 빈은 힙에 객체 하나뿐이고 requestId 필드도 한 칸이다. 스레드 A가 preHandle에서 "A"를 쓰고 컨트롤러를 실행하는 사이 스레드 B가 같은 칸에 "B"를 쓰면, A의 afterCompletion은 "B"를 읽는다. 각 스레드의 스택 프레임에는 그 객체를 가리키는 참조만 있을 뿐 값은 공유된다. 수정 방법은 (1) request.setAttribute로 요청 객체에 저장하고 afterCompletion에서 getAttribute로 읽는 것, (2) ThreadLocal에 저장하고 afterCompletion에서 반드시 remove()하는 것이다. (2)는 값을 더 깊은 계층까지 전해야 할 때 쓰며, 지우지 않으면 스레드 풀 재사용으로 다음 요청에 값이 샌다.

    4. 리졸버가 등록되지 않았으므로 Member 파라미터는 catch-all인 ServletModelAttributeMethodProcessor가 맡아 요청 파라미터로 새 객체를 만든다. 인증 인터셉터가 /orders를 보호하고 있다면 로그인하지 않은 요청은 preHandle에서 리다이렉트되어 컨트롤러까지 오지 않는다. 그러나 로그인한 사용자가 같은 쿼리를 붙이면 세션의 회원 대신 id=3, loginId=admin으로 채워진 객체가 들어온다. 인증 길목이 없다면 로그인하지 않은 사용자도 그 객체를 받는다. 어느 경우든 오류 없이 조용히 일어나므로 리졸버를 만든 직후 등록 여부와 @Retention(RUNTIME)을 함께 확인해야 한다.

    5. 예외는 컨트롤러에서 시작해 스택을 거꾸로 올라오며 필터의 finally를 실행시키는데, 그 시점에는 예외가 아직 필터 체인 안에 있다. 응답 상태를 500으로 바꾸는 것은 예외가 체인을 완전히 빠져나간 뒤 톰캣 StandardWrapperValve가 하는 일이므로 필터는 기본값 200을 본다. 다음처럼 예외를 잡아 기록하고 다시 던지면 된다.

    boolean failed = false;
try {
    chain.doFilter(request, response);
} catch (IOException | ServletException | RuntimeException e) {
    failed = true;
    throw e;                       // 삼키지 않고 그대로 올려 보낸다
} finally {
    int status = ((HttpServletResponse) response).getStatus();
    log.info("RES [{}] {} status={}{}", requestId, uri, status, failed ? " (처리되지 않은 예외)" : "");
}

    서블릿 필터(Servlet Filter)
    서블릿 컨테이너가 서블릿 앞에 두는 표준 컴포넌트. doFilter에서 요청을 검사·변환하고 chain.doFilter로 다음 단계를 부르거나 부르지 않아 처리를 막는다.
    필터 체인(FilterChain)
    한 요청에 적용될 필터들과 마지막 서블릿을 묶은 객체. 톰캣은 위치 계수기 pos로 다음 필터를 꺼내며, 필터와 체인이 서로를 호출하는 재귀 구조로 동작한다.
    디스패처 타입(DispatcherType)
    서블릿이 어떤 경로로 호출되었는지를 나타내는 값. REQUEST, FORWARD, INCLUDE, ERROR, ASYNC가 있으며, 필터 매핑은 지정한 타입에서만 동작한다.
    핸들러 인터셉터(HandlerInterceptor)
    스프링 MVC의 DispatcherServlet이 핸들러 실행 전후와 완료 후에 호출하는 콜백 인터페이스. preHandle, postHandle, afterCompletion으로 이루어진다.
    실행 체인(HandlerExecutionChain)
    핸들러 하나와 그 요청에 적용될 인터셉터 목록을 묶은 객체. 요청마다 새로 만들어지며 interceptorIndex로 preHandle을 통과한 위치를 기억한다.
    응답 커밋(response commit)
    상태 줄과 헤더가 클라이언트 쪽으로 이미 내보내진 상태. 커밋 뒤에는 상태 코드나 헤더를 바꿀 수 없다.
    허용 목록(allowlist)
    허용할 대상만 나열하고 나머지는 모두 막는 정책. 목록 갱신을 잊어도 기본이 차단이므로 보안 검사에 적합하다.
    오픈 리다이렉트(open redirect)
    사용자 입력으로 받은 주소로 검증 없이 리다이렉트해서, 신뢰받는 사이트가 공격자 사이트로 가는 발판이 되는 취약점.
    핸들러 메서드 인자 리졸버(HandlerMethodArgumentResolver)
    컨트롤러 메서드 파라미터 하나에 넣을 값을 만드는 전략 인터페이스. supportsParameter로 대상을 고르고 resolveArgument로 값을 만든다.
    스레드 로컬(ThreadLocal)
    스레드마다 독립된 값을 보관하는 자바 표준 클래스. 스레드 풀에서는 스레드가 재사용되므로 사용이 끝나면 remove()로 지워야 한다.
