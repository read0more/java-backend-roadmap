    이 회차의 질문: 서버가 HTML을 "만든다"는 것은 무슨 일인가

    스프링 MVC 1편에서 요청이 DispatcherServlet을 지나 컨트롤러에 닿고, 컨트롤러가 반환한 뷰 이름이 뷰 리졸버(view resolver)를 거쳐 뷰 객체가 되는 과정을 보았다. 그 마지막 칸, 뷰가 모델을 받아 HTML을 써 내려가는 부분은 "타임리프가 렌더링한다"는 한 줄로 넘어갔다. 이 권은 그 칸을 여는 것으로 시작한다.

    서버 사이드 렌더링(server-side rendering)은 서버가 완성된 HTML 문서를 응답 본문으로 보내는 방식이다. 브라우저 입장에서는 정적 파일을 받은 것과 구별되지 않는다. 차이는 서버 안에 있다. 정적 파일은 디스크의 바이트를 그대로 내보내면 되지만, 동적 페이지는 요청마다 다른 데이터를 HTML 사이에 끼워 넣어 문자열을 새로 조립해야 한다.

    이 조립을 자바 코드로 직접 하면 곧바로 세 가지가 곤란해진다. 첫째, HTML이 자바 문자열 리터럴 안에 흩어져 화면의 구조가 보이지 않는다. 둘째, 데이터에 <나 &가 들어 있으면 브라우저가 그것을 태그로 해석해 화면이 깨지거나 공격 코드가 실행된다. 셋째, 머리글·바닥글처럼 여러 페이지가 공유하는 부분을 재사용할 방법이 없다. 템플릿 엔진(template engine)은 이 셋을 맡는 도구다. HTML을 중심에 두고 데이터가 들어갈 자리만 표시하게 하며, 출력할 때 문자를 안전하게 바꾸고, 템플릿을 조각내 조합하는 수단을 준다.

    타임리프(Thymeleaf)의 문법은 양이 많아 보이지만 밑에 깔린 장치는 몇 개뿐이다. 이 회차는 문법을 나열하기 전에 그 장치부터 세운다. 답하려는 질문은 다음과 같다.

    • 템플릿 파일은 언제 읽히고, 어떤 형태로 메모리에 남으며, 요청마다 무엇이 다시 실행되는가.
    • th:text="${book.title}" 한 줄에서 누가 ${...}를 해석하고, 누가 getTitle()을 호출하는가.
    • 같은 값을 HTML 본문, 속성, URL, 자바스크립트 안에 넣을 때 왜 문자 변환 규칙이 서로 달라야 하는가.
    • 한 태그에 속성 여러 개를 쓰면 어떤 순서로 실행되는가. 내가 쓴 순서인가.
    • 레이아웃 파일 하나로 여러 페이지의 뼈대를 공유할 때, 페이지와 레이아웃 사이에 무엇이 오가는가.
    이 회차의 타임리프 규칙과 출력 예시는 Thymeleaf 3.1 공식 튜토리얼(Using Thymeleaf, Thymeleaf + Spring)과 Standard URL Syntax 문서에서 확인한 것만 적었다. SpringEL 평가 결과는 JDK 21.0.13에서 spring-expression 7.0.10으로 직접 실행해 얻었고, 규칙은 Spring Framework 6.2 레퍼런스로 교차 확인했다. 타임리프 엔진 자체는 이 원고를 쓰는 환경에서 실행하지 못했으므로, 문서에 출력이 명시되지 않은 세부(예: 따옴표가 어떤 문자 참조로 바뀌는지)는 적지 않았다.

    프로젝트 구성과 타임리프가 끼어드는 자리

    스프링 부트에서 타임리프를 쓰려면 웹 스타터와 타임리프 스타터 두 개면 된다. 그레이들 기준으로 의존성은 다음과 같다.

    dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-thymeleaf'
}

    스프링 부트 3.5의 의존성 버전 표를 보면 이 스타터가 끌어오는 것은 org.thymeleaf:thymeleaf와 org.thymeleaf:thymeleaf-spring6의 3.1 계열이다. 앞의 것이 템플릿 엔진 본체이고, 뒤의 것이 스프링 프레임워크 6과 엔진을 잇는 통합 모듈이다. 통합 모듈은 스프링 버전별로 따로 있어서 스프링 5용은 thymeleaf-spring5다.

    스타터를 넣으면 부트의 자동 구성이 세 가지 객체를 빈으로 등록한다. 템플릿 파일을 찾아 읽는 템플릿 리졸버(SpringResourceTemplateResolver), 템플릿을 처리하는 엔진(SpringTemplateEngine), 스프링 MVC의 뷰 리졸버 인터페이스를 구현한 ThymeleafViewResolver다. 설정값은 spring.thymeleaf.* 프로퍼티로 바꾸는데, 스프링 부트 3.5 소스의 ThymeleafProperties에 적힌 기본값은 아래와 같다.

    프로퍼티기본값의미
    spring.thymeleaf.prefixclasspath:/templates/뷰 이름 앞에 붙는 경로
    spring.thymeleaf.suffix.html뷰 이름 뒤에 붙는 확장자
    spring.thymeleaf.modeHTML템플릿 모드
    spring.thymeleaf.encodingUTF-8템플릿 파일 인코딩
    spring.thymeleaf.cachetrue파싱한 템플릿을 캐시할지
    spring.thymeleaf.enable-spring-el-compilerfalseSpringEL 컴파일러 사용 여부

    컨트롤러가 "books/list"를 반환하면 리졸버는 접두사와 접미사를 붙여 classpath:/templates/books/list.html을 찾는다. 소스 트리에서는 src/main/resources/templates/books/list.html이다. 여기까지는 1편에서 본 뷰 리졸버의 일반 규칙과 같다. 달라지는 것은 그다음이다. JSP였다면 서블릿 컨테이너가 JSP 파일을 자바 서블릿으로 번역해 실행했겠지만, 타임리프 뷰는 서블릿 컨테이너의 도움 없이 엔진이 직접 템플릿을 읽고 처리해 응답의 Writer에 쓴다.

    뷰 이름 하나가 응답 HTML이 되기까지 거치는 객체들과, 템플릿 캐시가 파일 읽기와 파싱을 건너뛰게 하는 지점을 보여 준다. 왼쪽에서 오른쪽으로 흐르는 깔끔한 순서도. 상자 여섯 개를 가로로 배치하고 화살표로 잇는다. 첫 상자 "컨트롤러" 아래에 작은 글씨로 "뷰 이름 + 모델". 둘째 상자 "뷰 리졸버". 셋째 상자 "템플릿 엔진". 넷째 상자는 원통 모양의 "템플릿 캐시"로, 템플릿 엔진 상자 바로 아래에 두고 양방향 화살표로 연결하며 화살표 옆에 "있으면 재사용"이라고 적는다. 템플릿 캐시 왼쪽 아래에 문서 아이콘 "템플릿 파일"을 두고 캐시로 향하는 점선 화살표에 "없을 때만 읽고 파싱"이라고 적는다. 다섯째 상자 "속성 프로세서 실행" 아래에 작은 글씨로 "표현식 평가". 여섯째 상자 "HTML 응답". 흰 배경, 파란색과 회색 위주의 평면 스타일, 한국어 라벨은 따옴표 안의 문구 그대로. 템플릿 파일을 읽고 파싱하는 일은 캐시가 켜져 있으면 처음 한 번뿐이고, 요청마다 반복되는 것은 프로세서 실행과 표현식 평가다.

    캐시 설정은 개발과 운영에서 뜻이 다르다. 타임리프 튜토리얼은 캐시가 담는 것을 "템플릿 파일을 읽고 파싱해 얻은 이벤트의 열"이라고 설명하고, 템플릿 캐시의 기본 최대 크기를 200개 항목으로 적는다. 운영에서는 이 캐시 덕분에 요청마다 디스크를 읽고 파싱하는 비용이 사라진다. 반대로 개발 중에는 템플릿을 고쳐도 캐시된 옛 결과가 계속 쓰인다. 스프링 부트 레퍼런스에 따르면 spring-boot-devtools를 넣으면 spring.thymeleaf.cache가 false로 맞춰진다. 템플릿을 고쳤는데 화면이 그대로일 때는 캐시 설정과, 실행 중인 클래스패스에 고친 파일이 실제로 복사되었는지를 먼저 확인한다.

    타임리프가 템플릿을 처리하는 방식: 태그는 그대로 두고 속성으로 지시한다

    타임리프 템플릿의 가장 눈에 띄는 특징은 템플릿이 그 자체로 올바른 HTML 파일이라는 점이다. JSP의 <% %>나 다른 엔진의 중괄호 블록처럼 HTML 바깥의 문법을 끼워 넣지 않고, 기존 태그에 th:로 시작하는 속성을 덧붙여 지시를 내린다.

    

도서 목록

  
    가게 이름 자리

    이 파일을 브라우저로 직접 열면 브라우저는 모르는 속성인 th:text를 무시하고 "가게 이름 자리"를 보여 준다. 서버를 거치면 엔진이 th:text의 표현식을 평가해 태그 본문을 그 값으로 바꾸고, th:text 속성 자체는 결과에서 지운다. 한 파일이 디자인 시안과 실제 템플릿을 겸한다. 타임리프는 이것을 내추럴 템플릿(natural template)이라고 부른다. xmlns:th 선언은 템플릿 처리에는 영향이 없고, 편집기가 th: 속성을 오류로 표시하지 않게 하는 용도다.

    엔진 안에서 일어나는 일을 한 단계 내려가 보자. 엔진은 템플릿을 문자열 치환 대상으로 다루지 않는다. 파서가 파일을 읽어 "h1 여는 태그(속성 th:text 포함)", "텍스트", "h1 닫는 태그" 같은 이벤트의 열로 바꾼다. 처리 단계에서는 이 이벤트를 차례로 흘려보내다가, 태그에 붙은 속성 이름과 짝이 맞는 프로세서(processor)가 있으면 그 프로세서를 실행한다. th:text 프로세서는 속성값을 표현식으로 평가하고, 결과를 태그의 본문으로 설정한 뒤, 자신의 속성을 제거한다.

    어떤 속성 이름에 어떤 프로세서가 대응하는지를 묶어 놓은 것이 방언(dialect)이다. 타임리프가 기본으로 제공하는 것이 표준 방언(Standard Dialect)이고, 튜토리얼은 표준 방언의 프로세서 대부분이 속성 프로세서라고 적는다. 스프링과 함께 쓸 때는 표준 방언을 확장한 스프링 표준 방언(SpringStandard Dialect)이 적용된다. 이 회차에서 다루는 th:text, th:each, th:if는 표준 방언에서 온 것이고, 폼 처리를 위한 th:field 같은 속성은 스프링 표준 방언이 추가한 것으로 다음 회차에서 다룬다.

    일상에서 가져온 비유교정 부호가 적힌 원고

    인쇄소에 넘기는 원고에 "이 줄은 굵게", "여기에 날짜 삽입" 같은 교정 부호를 연필로 적어 두는 것과 비슷하다. 원고는 부호가 있든 없든 읽을 수 있는 글이고, 조판자는 부호가 붙은 자리에서만 작업한 뒤 부호를 지운다. 다만 이 비유는 한 군데서 깨진다. 교정 부호는 한 번 적용하면 끝이지만, 타임리프는 같은 원고(캐시된 이벤트 열)를 요청마다 다른 데이터로 다시 조판한다.

    두 가지를 덧붙인다. 첫째, HTML5는 data-로 시작하는 사용자 정의 속성을 허용하므로 th:text 대신 data-th-text로 써도 된다. 튜토리얼은 두 표기가 완전히 같은 뜻이며 서로 바꿔 쓸 수 있다고 적는다. 둘째, 엔진이 처리할 수 있는 템플릿은 HTML만이 아니다. 템플릿 모드(template mode)는 HTML, XML, TEXT, JAVASCRIPT, CSS, RAW 여섯 가지이고, 뒤에서 볼 자바스크립트 인라인은 HTML 템플릿 안의 스크립트 블록을 자바스크립트 문맥에 맞게 처리하는 기능이다.

    텍스트 출력: th:text, th:utext와 이스케이프

    가장 기본이 되는 속성은 태그의 본문을 바꾸는 th:text다. 컨트롤러가 모델에 notice라는 이름으로 문자열 신간 입고를 담았다고 하자.

    공지 자리
    

    공지 자리
    신간 &lt;b&gt;입고&lt;/b&gt;
    

    신간 입고

    첫 줄은 화면에 신간 입고라는 글자가 그대로 보이고, 둘째 줄은 "입고"가 굵게 보인다. th:text는 값을 출력하기 전에 HTML 이스케이프(escape)를 하고, th:utext(unescaped text)는 하지 않는다. 튜토리얼은 이스케이프가 th:text의 기본 동작이라고 못 박는다.

    이스케이프가 막는 것

    왜 기본이 이스케이프인지는 브라우저의 HTML 파서가 일하는 방식에서 나온다. 파서는 받은 문자열을 앞에서부터 읽다가 <를 만나면 태그가 시작되었다고 판단하고, &를 만나면 문자 참조(character reference)가 시작되었다고 판단한다. 파서는 그 문자가 템플릿에 원래 있던 것인지, 데이터에서 온 것인지 알 방법이 없다. 서버가 보낸 것은 구분 없는 문자열 하나이기 때문이다.

    그래서 사용자가 입력한 값에 라는 끝 태그를 찾을 때까지의 글자를 그대로 자바스크립트 엔진에 넘긴다. 따라서 값 속의 큰따옴표를 &quot;로 바꿔 넣으면 자바스크립트는 &quot;라는 여섯 글자를 그대로 받는다. 스크립트 문맥에서 위험한 문자도 다르다. 문자열을 끝내는 따옴표, 역슬래시, 줄바꿈, 그리고 HTML 파서가 스크립트를 끝내 버리게 만드는 문자열이다. 문맥이 다르면 이스케이프 규칙도 달라야 한다.

    자바스크립트 인라인은 th:inline="javascript"로 명시적으로 켜야 한다. 켜면 스크립트 블록의 내용이 JAVASCRIPT 템플릿 모드로 처리되고, [[...]]의 결과는 HTML 이스케이프가 아니라 자바스크립트 문법에 맞는 리터럴로 출력된다. 모델의 pick이 Tom's "pick"이라면 첫 줄은 다음과 같이 된다.

    const pick  = "Tom's \"pick\"";

    튜토리얼의 표현대로 인라인 결과는 따옴표로 감싸지고 내용은 자바스크립트용으로 이스케이프되어, 언제나 올바른 자바스크립트 문자열 리터럴이 된다. 반대로 [(${pick})]처럼 이스케이프하지 않으면 따옴표 없이 Tom's "pick"이 그대로 들어가 문법 오류가 난다. 비이스케이프 인라인은 스크립트 코드 조각 자체를 조립할 때만 쓰는 도구다.

    자바스크립트 내추럴 템플릿

    둘째 줄의 /*[[${book.title}]]*/ "시안용 제목"은 HTML의 내추럴 템플릿을 스크립트에 옮긴 것이다. 튜토리얼에 따르면 타임리프는 표현식을 감싼 주석 뒤부터 세미콜론 앞까지의 내용을 무시한다. 서버를 거치면 "시안용 제목"은 사라지고 주석 자리에 실제 값이 들어간다. 정적으로 열면 표현식은 자바스크립트 주석이라 무시되고 "시안용 제목"이 값으로 쓰이므로, 스크립트가 문법 오류 없이 실행된다.

    객체 직렬화와 이스케이프 규칙

    넷째 줄처럼 객체를 통째로 넘길 수도 있다. 튜토리얼은 문자열, 숫자, 불리언, 배열, 컬렉션, 맵, 그리고 게터를 가진 빈(bean)을 자바스크립트 문법으로 바꿔 쓴다고 설명한다. Book 객체는 {"id":1, "price":30000, ...} 같은 객체 리터럴이 된다. 이 변환을 맡는 것이 IStandardJavaScriptSerializer이고, 기본 구현은 클래스패스에 Jackson이 있으면 Jackson을 쓰고 없으면 내장 직렬화기를 쓴다. 스프링 부트의 웹 스타터는 Jackson을 포함하므로 보통은 Jackson 경로를 탄다.

    타임리프 3.1.3 소스의 Jackson 설정을 보면 문자열에 적용되는 이스케이프 규칙이 정확히 드러난다. JSON의 표준 이스케이프(큰따옴표, 역슬래시, 제어 문자)에 더해 /를 \/로, &를 \u0026으로 바꾸고, ASCII가 아닌 문자는 모두 \uXXXX 형태로 바꾸도록(ESCAPE_NON_ASCII) 설정되어 있다. /를 바꾸는 것이 앞에서 말한 문제의 해법이다. 값에 가 들어 있어도 출력은 <\/script>가 되므로 HTML 파서는 그것을 끝 태그로 인식하지 못한다. 자바스크립트 엔진은 문자열 리터럴 안의 \/를 /로 읽으므로 값은 손상되지 않는다. 한글 제목이 페이지 소스에서 \u로 시작하는 기호열로 보이는 것도 이 설정 때문이며, 실행 시점의 문자열은 원래 한글과 같다.

    타임리프 3.1 튜토리얼(문서가 대상으로 하는 3.1.7 기준) 부록 D는 몇몇 위치의 표현식을 제한 모드(restricted expression evaluation mode)로 평가한다고 적는다. th:utext와 비이스케이프 인라인, th:onclick 같은 th:on* 이벤트 핸들러 속성, 조각 표현식의 템플릿 이름 등이 그 대상이다. 제한 모드에서는 ${param.*} 접근, 객체 생성, T(...) 같은 정적 클래스 접근, @빈이름 접근이 금지되고, th:on* 속성에서는 숫자나 불리언이 아닌 결과를 내는 변수 표현식이 금지된다. 도서 제목을 th:onclick에 직접 넣으면 실행 중 예외가 나는 이유다. 그런 값은 th:data-title로 data-* 속성에 담고 스크립트에서 읽는다. 튜토리얼은 이 제한이 입력 검증을 대신하지 않는다고 거듭 강조한다.

    스타일 블록에도 같은 장치가 있다. th:inline="css"를 붙인 style 블록에서 [[...]]는 CSS 식별자 규칙으로 이스케이프된다. 튜토리얼의 예로는 main elems라는 값이 main\ elems로 출력된다. /*[[${align}]]*/ left 같은 CSS 내추럴 템플릿도 자바스크립트와 같은 방식으로 동작한다.

    페이지가 열 개를 넘어가면 머리글, 메뉴, 바닥글을 페이지마다 복사해 둘 수 없다. 메뉴 항목 하나를 바꾸려고 열 개 파일을 고치게 되기 때문이다. 타임리프는 템플릿의 일부를 조각(fragment)으로 이름 붙이고, 다른 템플릿에서 그 조각을 가져다 쓰는 방법을 제공한다.

    두 속성의 차이는 호스트 태그(host tag), 즉 속성이 붙어 있던 div를 남기느냐에 있다. th:insert는 조각을 호스트 태그의 본문으로 넣고, th:replace는 호스트 태그 자체를 조각으로 바꾼다. 3.1 계열 소스의 AbstractStandardFragmentInsertionTagProcessor를 보면 이 차이가 메서드 하나로 갈린다. 조각의 이벤트 열(템플릿 모델)을 얻은 뒤 th:replace면 structureHandler.replaceWith(...)를, th:insert면 structureHandler.setBody(...)를 호출한다. 조각은 문자열로 복사되는 것이 아니라 이벤트 열로 끼워 넣어지고, 조각 안의 th:* 속성은 삽입된 뒤 그 자리의 컨텍스트에서 실행된다. 그래서 조각은 자신을 포함한 템플릿의 변수를 그대로 읽을 수 있다. 조각을 담은 파일도 다른 템플릿처럼 템플릿 리졸버로 찾고 캐시되므로, 조각 파일을 매 요청 다시 파싱하지 않는다.

    이전 버전의 자료에서 볼 수 있는 th:include는 조각의 바깥 태그를 떼고 안쪽 내용만 넣는 속성이었다. 타임리프 3.1.2 API 문서는 이 프로세서를 3.0부터 권장하지 않았고, 3.1부터 경고를 내며, 3.2 또는 4.0에서 제거할 예정이라고 적는다. 대신 th:insert를 쓴다.

    조각 표현식 ~{...}

    조각을 가리키는 값이 조각 표현식(fragment expression)이다. 형식은 세 가지다.

    형식뜻
    ~{템플릿이름 :: 선택자}그 템플릿에서 선택자에 맞는 조각. 선택자는 th:fragment 이름이어도 되고 #copy-section, div.content 같은 마크업 선택자여도 된다
    ~{템플릿이름}템플릿 전체
    ~{::선택자}, ~{this::선택자}현재 템플릿에서 선택자에 맞는 조각. 없으면 템플릿 호출 스택을 따라 처음 처리를 시작한 템플릿 쪽으로 거슬러 올라가며 찾는다

    선택자로 id나 클래스를 쓸 수 있다는 것은 th:fragment를 붙이지 않은 마크업, 심지어 타임리프를 전혀 모르는 HTML의 일부도 조각으로 가져올 수 있다는 뜻이다. 선택자 문법은 타임리프가 쓰는 파서 라이브러리 AttoParser에서 온 것으로 XPath, CSS 선택자와 닮았고 튜토리얼 부록 C에 정리되어 있다.

    타임리프 3.0에서는 th:replace="fragments/footer :: copy"처럼 ~{...}를 생략한 형태도 받아들였다. 3.1 계열 소스를 보면 이런 형태를 만났을 때 "Deprecated unwrapped fragment expression"으로 시작하는 경고를 로그에 남기고, ~{...}로 감싼 완전한 문법을 쓰라고 안내하며, 옛 문법은 이후 버전에서 제거된다고 적는다. 오래된 예제를 옮겨 왔는데 로그에 이 경고가 쌓인다면 ~{ }로 감싸 주면 된다.

    th:fragment에 파라미터 목록을 적으면 조각이 함수처럼 동작한다. 인자는 순서대로 넘길 수도 있고 이름을 붙여 넘길 수도 있으며, 이름을 붙이면 순서는 상관없다. 소스에서 보면 넘긴 인자는 조각의 시그니처에 맞춰 이름이 붙은 뒤 structureHandler.setLocalVariable(...)로 조각 범위의 지역 변수가 된다. th:with로 만든 지역 변수와 같은 장치다. 튜토리얼은 이렇게 지역 변수를 지정해도 컨텍스트가 비워지지는 않아서, 조각이 호출한 템플릿의 다른 변수도 계속 읽을 수 있다고 덧붙인다. th:assert는 쉼표로 나열한 식이 모두 참인지 검사하고 하나라도 거짓이면 예외를 낸다. 필수 인자를 빠뜨린 호출을 조각 쪽에서 바로 잡아낼 수 있다.

    조각이 조각을 부르는 것도 가능하다. 다만 실수로 자기 자신을 다시 포함하면 끝없이 깊어지므로, 타임리프 3.1.5부터는 포함 깊이가 100(MAX_FRAGMENT_INCLUSION_DEPTH)에 이르면 "재귀적인 템플릿 포함 때문일 가능성이 크다"는 문구와 함께 예외를 낸다. 자바 메서드의 무한 재귀가 StackOverflowError로 끝나는 것과 같은 상황을 엔진이 미리 막는 것이다.

    레이아웃: 마크업을 인자로 넘기기

    여기까지는 페이지가 공통 조각을 가져다 쓰는 구조였다. 레이아웃은 방향이 반대다. 공통 뼈대가 주인이 되고, 페이지는 뼈대의 빈칸에 들어갈 자기 내용을 넘긴다. 이것을 가능하게 하는 것은 조각 표현식의 결과가 문자열이나 숫자가 아니라 "마크업 조각"이라는 값이고, 그 값을 다른 조각의 인자로 넘길 수 있다는 점이다.

    페이지가 레이아웃을 부르면서 자신의 마크업 일부를 인자로 넘기고, 레이아웃이 그 인자로 빈칸을 채우는 방향을 보여 준다. 가로로 세 개의 문서 모양 패널을 둔다. 왼쪽 패널 제목 "페이지 템플릿", 안에 두 블록 "title: 도서 목록"(파란색), "section: 목록 본문"(초록색). 가운데 패널 제목 "레이아웃 템플릿", 안에 위에서부터 "title 빈칸"(파란 점선 테두리), "공통 메뉴"(회색), "content 빈칸"(초록 점선 테두리), "공통 바닥글"(회색). 왼쪽 파란 블록에서 가운데 파란 빈칸으로, 왼쪽 초록 블록에서 가운데 초록 빈칸으로 곡선 화살표를 긋고 화살표 위에 각각 "~{::title}", "~{::section}"이라고 적는다. 가운데에서 오른쪽으로 굵은 화살표, 오른쪽 패널 제목 "최종 HTML", 안에 위에서부터 "도서 목록"(파란색), "공통 메뉴"(회색), "목록 본문"(초록색), "공통 바닥글"(회색). 흰 배경, 평면 스타일, 한국어 라벨은 따옴표 안 문구 그대로. 페이지는 자기 마크업의 일부를 조각 값으로 넘기고, 레이아웃은 그 값으로 빈칸을 채운다. 선택되지 않은 페이지의 나머지 마크업은 결과에 남지 않는다.

    4단계에서 페이지의 html 요소가 통째로 교체된다는 점을 기억하자. 페이지에서 ~{::title}과 ~{::section}으로 고르지 않은 마크업은 결과에 남지 않는다. 페이지에 추가 스크립트가 필요하다면 레이아웃에 그것을 받을 파라미터를 하나 더 만들고 페이지에서 ~{::script}처럼 넘겨야 한다.

    모든 페이지가 모든 빈칸을 채우지는 않는다. 튜토리얼은 이를 위해 두 가지 값을 준다. 빈 조각(empty fragment) ~{}을 넘기면 그 빈칸은 아무것도 출력하지 않는다. 소스에서는 th:replace가 빈 조각을 받으면 호스트 태그를 지우고, th:insert는 본문만 지운다. 무연산 토큰 _을 넘기면 빈칸을 채우는 th:replace 자체가 실행되지 않은 것처럼 되어 레이아웃에 적힌 기본 마크업(위 예에서는 "레이아웃 제목", "레이아웃 본문 자리")이 그대로 남는다. 리터럴 절에서 본 무연산 토큰이 레이아웃에서는 "기본값 사용"이라는 뜻이 된다. 한 레이아웃을 여러 조각(머리글, 바닥글)으로 나누어 조합하는 것도 같은 원리를 반복하는 것이다.

    이 장의 핵심

    타임리프는 템플릿을 이벤트의 열로 파싱해 캐시하고, 요청마다 그 이벤트를 흘려보내며 th:* 속성에 대응하는 프로세서를 우선순위 순서로 실행한다. 표현식은 두 층이어서 중괄호 안은 SpringEL이 리플렉션으로, 밖은 타임리프 엔진이 평가한다. 출력은 문맥(HTML 본문, 속성, URL, 스크립트)마다 다른 규칙으로 이스케이프되고, 조각과 레이아웃은 이벤트 열을 다른 이벤트 열에 끼워 넣는 일이다. 문법이 낯설 때는 "이 속성은 몇 번째로 실행되고, 이 식은 누가 평가하며, 이 값은 어느 문맥에 들어가는가"를 물으면 결과를 예측할 수 있다.

    이 회차의 문법은 다음 회차에서 스프링과 만난다. 2회차는 th:object와 선택 변수 표현식 *{...}, th:field로 폼과 모델 객체를 묶는 법을, 3회차는 메시지 표현식 #{...}과 국제화를 다룬다. 4·5회차의 검증 오류 출력, 6회차의 세션 값 출력도 모두 이 회차의 변수 표현식과 조건부 평가 위에서 동작한다.
    템플릿 캐시와 이벤트 열
    타임리프는 템플릿 파일을 여는 태그·텍스트·닫는 태그 같은 이벤트의 열로 파싱해 캐시한다. 운영에서는 파싱이 처음 한 번뿐이고, 요청마다 반복되는 것은 프로세서 실행과 표현식 평가다.
    th:text와 th:utext
    th:text와 [[...]]는 HTML 이스케이프를 해서 데이터 속 꺾쇠가 태그로 해석되지 않게 한다. th:utext와 [(...)]는 이스케이프하지 않으므로 서버가 모든 글자를 통제한 값에만 쓴다.
    변수 표현식과 SpringEL
    ${...} 안은 SpringEL이 노드 트리로 해석해 평가한다. 프로퍼티 읽기는 컨텍스트 변수 접근자, 맵 접근자, 리플렉션 접근자 순서로 시도되며 게터를 찾아 Method.invoke로 호출한다.
    두 평가기
    중괄호 바깥의 리터럴과 연산은 타임리프 엔진이, 안쪽은 SpringEL이 계산한다. 나눗셈(BigDecimal 대 정수 나눗셈)과 엘비스 연산자(null만 대 빈 문자열까지)처럼 규칙이 다른 곳이 있다.
    th:each와 상태 변수
    반복은 요소의 이벤트를 원소마다 다시 처리하며 반복 변수와 상태 변수를 지역 변수로 넣는 일이다. even/odd는 1부터 세는 count 기준이라 첫 행이 odd다.
    th:if의 참 판정
    null은 거짓, 숫자는 0이 아니면 참, 문자열은 "false", "off", "no"가 아니면 참, 그 밖의 객체는 참이다. 거짓이면 태그가 안쪽까지 결과에서 사라진다.
    속성 우선순위
    한 태그의 th:* 속성은 적은 순서가 아니라 고유 우선순위(조각 포함, 반복, 조건, 지역 변수, 속성 수정, 본문 수정 순)로 실행된다. 같은 태그의 th:if는 th:with 변수를 볼 수 없다.
    주석과 th:block
    HTML 주석은 브라우저까지 가고, 파서 수준 주석은 파싱 때 사라지며, 프로토타입 전용 주석은 서버에서만 마크업이 된다. th:block은 속성만 실행하고 자기 태그는 지운다.
    조각과 레이아웃
    th:insert는 호스트 태그의 본문을, th:replace는 호스트 태그 자체를 조각의 이벤트로 바꾼다. 조각 표현식의 결과를 인자로 넘기면 공통 뼈대가 페이지의 마크업으로 빈칸을 채우는 레이아웃이 된다.

    실무에서 타임리프 관련 장애는 대부분 표현식 평가에서 난다. 컨트롤러가 어떤 조건에서만 모델에 객체를 담지 않으면, 그 경로로 들어온 요청에서만 ${book.title}이 EL1007E를 내며 템플릿 처리 예외가 되고 사용자는 오류 페이지를 본다. 테스트에서 늘 데이터가 있는 경로만 돌렸다면 운영에서 처음 발견된다. 값이 없을 수 있는 자리인지는 템플릿이 아니라 컨트롤러의 분기를 보고 판단하고, 없을 수 있다면 ?.와 th:if로 템플릿에서 명시적으로 처리한다. 반대로 반드시 있어야 하는 값이라면 오류가 나는 편이 조용히 빈 화면을 내는 것보다 낫다. 이 판단은 "그 값이 없는 것이 정상 상태인가"에 달려 있다.

    보안 쪽에서는 이스케이프 문맥을 맞추는 것이 전부다. 게시판 본문에 서식을 허용하려고 th:utext를 쓰는 순간 XSS 방어의 책임은 타임리프에서 애플리케이션의 정제 로직으로 넘어간다. 그 결정을 내릴 때는 허용 태그 목록 기반의 정제가 저장 시점이나 출력 전에 반드시 수행되는지를 함께 확인해야 한다. 스크립트에 값을 넘길 때는 문자열을 이어 붙여 스크립트를 만들지 말고 th:inline="javascript"의 직렬화를 쓰거나 data-* 속성을 거친다. 3.1에서 강화된 제한 모드 때문에 오래된 템플릿이 업그레이드 후 예외를 내기 시작했다면, 튜토리얼의 권고대로 제한을 피하는 우회로를 찾기보다 그 값을 컨트롤러에서 검증해 모델로 넘기도록 고치는 것이 맞다.

    성능 판단은 캐시 설정에서 시작한다. 운영에서 spring.thymeleaf.cache=false가 남아 있으면 요청마다 템플릿과 조각 파일을 읽고 파싱하므로, 트래픽이 늘수록 CPU와 디스크 읽기가 함께 늘어난다. 설정 파일을 프로필별로 나눌 때 가장 먼저 확인할 항목이다. 캐시가 켜져 있으면 남는 비용은 표현식 평가인데, 이것은 리플렉션 호출과 문자열 쓰기가 대부분이라 보통은 데이터베이스 조회보다 훨씬 작다. 따라서 화면이 느릴 때는 템플릿 문법보다 템플릿이 호출하는 게터가 지연 로딩 같은 무거운 일을 하지 않는지를 먼저 의심한다. 템플릿에서 프로퍼티 하나를 읽는 것이 실제로는 메서드 호출이라는 이 회차의 내용이 그 판단의 근거다.

HTML 이스케이프를 했다면 &lt;/script&gt;가 들어가는데, script 내용은 원시 텍스트라 브라우저가 문자 참조를 되돌리지 않으므로 자바스크립트는 &lt;라는 네 글자를 그대로 받는다. 값이 틀어진다. 또 HTML 이스케이프는 따옴표로 감싸 주지 않고 역슬래시나 줄바꿈 같은 자바스크립트 특수 문자를 처리하지 않으므로, 문자열 리터럴을 깨뜨릴 수 있어 안전하지도 않다.

    를 정가 1만 원짜리 도서로 처리하면 어떻게 되는가?     도서 제목이 출력된다. th:with가 먼저 실행되어 cheap이 true이기 때문이다. p 태그가 통째로 사라진다. th:if가 th:with보다 먼저 실행되어 그 시점의 cheap은 null이기 때문이다. 템플릿 처리 예외가 난다. 같은 태그에서 만든 지역 변수는 어떤 속성에서도 읽을 수 없기 때문이다. "제목"이 출력된다. 속성은 적은 순서대로 실행되고, 첫 속성인 th:if가 거짓이면 나머지만 건너뛰기 때문이다. 속성은 적은 순서가 아니라 우선순위로 실행된다. 조건부 평가(3)가 지역 변수 정의(4)보다 먼저이므로 th:if가 볼 때 cheap은 아직 없고 null로 평가되어 거짓이다. 거짓이면 태그와 내용이 함께 제거된다. 지역 변수 자체는 같은 태그에서도 우선순위가 더 낮은 속성(예: th:text)에서는 읽을 수 있으므로 셋째 보기도 틀리다.     원소가 세 개인 리스트를 th:each="x, st : ${list}"로 반복할 때 ${st.odd}가 true인 행은? 2번째 행만. index가 1로 홀수이기 때문이다. 모든 행. size가 3으로 홀수이기 때문이다. 1번째와 3번째 행. 홀짝 판정이 1부터 세는 count 기준이기 때문이다. 3번째 행만. 마지막 행의 index가 2이기 때문이다. 타임리프의 상태 변수는 짝수 여부를 (index + 1) % 2 == 0, 곧 count 기준으로 계산하고 odd는 그 반대다. count가 1, 3인 1번째와 3번째 행이 odd다. 0부터 세는 index로 생각하면 반대로 예측하게 된다. 모델의 nickname이 빈 문자열 ""일 때 th:text="${nickname} ?: '익명'"과 th:text="${nickname ?: '익명'}"의 출력은 각각 무엇인가? 첫째는 빈 본문, 둘째는 "익명". 첫째는 타임리프가 null만 검사하고, 둘째는 SpringEL이 빈 문자열도 검사한다. 둘 다 "익명". 엘비스 연산자는 어디서나 빈 값을 같은 규칙으로 검사한다. 둘 다 빈 본문. 엘비스 연산자는 null만 검사한다. 첫째는 "익명", 둘째는 빈 본문. 중괄호 안에서는 연산자가 무시된다. 중괄호 바깥의 ?:는 타임리프의 기본값 식으로, 소스상 왼쪽이 null일 때만 오른쪽을 쓴다. 중괄호 안의 ?:는 SpringEL의 엘비스 연산자이고, 스프링 레퍼런스와 실행 결과 모두 빈 문자열도 비어 있는 값으로 취급함을 보여 준다. 같은 기호라도 평가 주체가 다르면 규칙이 다르다.

HTML 이스케이프는 한글을 처리하지 못하기 때문이다. 브라우저의 HTML 파서가 script 내용을 원시 텍스트로 다뤄 문자 참조를 되돌리지 않으므로, HTML 이스케이프한 글자가 그대로 자바스크립트에 전달되기 때문이다. 자바스크립트 엔진이 & 문자를 문법 오류로 처리하기 때문이다. 타임리프가 script 안에서는 표현식을 평가하지 않기 때문이다. 이스케이프는 "값이 들어가는 문맥의 해석기"에 맞춰야 한다. script 내용은 HTML 파서가 문자 참조를 해석하지 않고 그대로 자바스크립트 엔진에 넘기므로 &quot; 같은 HTML 이스케이프는 값을 망가뜨린다. 그 문맥에서 필요한 것은 따옴표로 감싼 문자열 리터럴과 역슬래시 이스케이프, 그리고 가 끝 태그로 인식되지 않게 하는 처리다. 셋째 보기처럼 &가 문법 오류인 것도 아니고, 넷째 보기와 달리 인라인을 켜면 표현식은 평가된다.
    서버 사이드 렌더링(server-side rendering)
    서버가 데이터를 끼워 넣은 완성된 HTML 문서를 응답 본문으로 보내는 방식. 브라우저는 정적 파일을 받은 것과 구별하지 못한다.
    내추럴 템플릿(natural template)
    브라우저로 직접 열어도 올바르게 보이는 템플릿. 타임리프는 HTML 태그에 th:* 속성을 덧붙이는 방식으로 이를 지원한다.
    방언(dialect)과 프로세서(processor)
    프로세서는 태그나 속성에 붙어 실행되는 처리 단위이고, 방언은 프로세서와 표현식 객체의 묶음이다. 스프링 환경에서는 표준 방언을 확장한 스프링 표준 방언이 쓰인다.
    이스케이프(escape)
    값 속의 특수 문자를 그 문맥의 해석기가 데이터로 읽도록 바꾸는 일. HTML 본문, 속성, URL, 자바스크립트, CSS마다 규칙이 다르다.
    리터럴 토큰(literal token)
    따옴표 없이 쓴 낱말 리터럴. 영문자, 숫자, 대괄호, 점, 하이픈, 밑줄만 허용하며 공백과 쉼표는 허용하지 않는다.
    상태 변수(status variable)
    th:each가 반복마다 제공하는 위치 정보 객체. index, count, size, current, even/odd, first/last를 가진다.
    속성 우선순위(attribute precedence)
    한 태그에 붙은 th:* 속성의 실행 순서를 정하는 고유한 순위. 속성을 적은 순서와 무관하다.
    조각 표현식(fragment expression)
    ~{템플릿 :: 선택자} 형태로 마크업 조각을 가리키는 표현식. 결과는 문자열이 아닌 마크업 조각 값이며 다른 조각의 인자로 넘길 수 있다.
    무연산 토큰(no-operation token)
    _로 쓰며, 그 속성이 없었던 것처럼 아무것도 하지 않게 한다. 시안 문구나 레이아웃의 기본 마크업을 기본값으로 쓰는 데 활용한다.
