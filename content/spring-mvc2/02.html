    이 회차의 질문: 폼은 출력으로 끝나지 않고 왕복한다

    앞 회차에서 다룬 타임리프의 기본 기능은 모두 한 방향이었다. 모델에 담긴 값을 꺼내 HTML의 텍스트나 속성으로 내보내면 일이 끝났다. 폼은 다르다. 서버가 객체를 HTML 입력 요소로 내보내고, 사용자가 그 값을 고치고, 브라우저가 고친 값을 HTTP 요청으로 돌려보내고, 서버가 그것을 다시 객체로 만든다. 입력이 잘못되면 같은 폼을 사용자가 입력한 값 그대로 다시 그려 줘야 한다. 데이터가 객체에서 출발해 문자열이 되었다가 다시 객체로 돌아오는 왕복이다.

      서버                                              브라우저
  ────                                              ────────
  RoomForm 객체
     │ ① 렌더링: 프로퍼티 → 입력 요소의 name, value
     ▼
    ───────▶  화면에 폼 표시
                                                       │ ② 사용자가 값을 고친다
                                                       ▼
  name=%EC%98%A4...&open=true&...          ◀───────  ③ 직렬화: 입력 요소 → 이름=값 쌍
     │ ④ 파싱: 본문 → 요청 파라미터(Map)
     ▼
  WebDataBinder
     │ ⑤ 바인딩: 파라미터 이름 → 프로퍼티 경로, 문자열 → 타입 변환
     ▼
  RoomForm 객체 (새로 만든 것)

    이 왕복에서 양쪽을 이어 주는 것은 입력 요소의 name 속성 하나뿐이다. ①에서 서버는 프로퍼티 이름을 name에 적어 내보내고, ⑤에서 스프링은 돌아온 파라미터 이름을 프로퍼티 경로로 해석해 setter를 부른다. 둘이 한 글자라도 어긋나면 오류는 나지 않고 값만 조용히 사라진다. HTML을 손으로 쓰면 한 필드에 같은 이름을 여러 번 적게 된다.

    텍스트 입력 하나에 name이라는 글자가 네 번 나온다(for, id, name, th:value). 체크박스와 셀렉트 박스는 "지금 값이 이 선택지와 같은가"를 선택지마다 조건식으로 적어야 한다. 그리고 뒤에서 보겠지만 체크박스에는 이것만으로는 해결되지 않는 문제가 하나 더 숨어 있다. 타임리프의 스프링 통합 기능은 이 반복을 줄이는 데서 그치지 않고, 스프링의 데이터 바인딩이 가진 정보를 템플릿 쪽에서 읽어 쓰게 해 준다. 이 회차에서 답할 질문은 다음과 같다.

    • 표준 타임리프와 "스프링 통합" 타임리프는 무엇이 다른가. 스프링 부트는 그 사이에서 무엇을 대신 해 주는가.
    • th:field="*{name}" 한 줄이 어떻게 id, name, value 세 속성이 되는가. 그 값은 어디에서 읽어 오는가.
    • 체크박스, 라디오 버튼, 셀렉트 박스는 HTTP 본문에 어떤 모양으로 실리는가. 선택하지 않은 것은 어떻게 표현되는가.
    • 체크를 해제한 체크박스를 서버가 알아차리려면 무엇이 필요한가. 스프링은 그것을 어디에서 처리하는가.
    이 회차의 데이터 바인딩 실험(ServletRequestDataBinder, BindStatus)은 로컬에 있는 Spring Framework 7.0.10과 spring-test의 Mock 서블릿 객체로 JDK 21에서 실행했다. 이 강좌의 기준은 Spring Framework 6.x이므로 규칙은 6.2.x의 WebDataBinder Javadoc으로 다시 확인했고, 여기서 다루는 범위에서는 두 버전의 동작이 같다. 타임리프가 만들어 내는 HTML은 thymeleaf-spring6 3.1.5와 Spring Framework 6.2.19로 실제 렌더링한 결과에서 해당 부분만 옮긴 것이다.
    서버의 객체가 입력 요소가 되고, 브라우저가 이름=값 쌍으로 직렬화해 돌려보내며, 서버가 다시 객체로 바인딩하는 왕복에서 name 속성이 유일한 연결 고리임을 보여 준다. 가로로 긴 시퀀스 다이어그램. 왼쪽에 세로 띠 "서버", 오른쪽에 세로 띠 "브라우저". 서버 띠 위쪽에 상자 "RoomForm 객체". 그 아래로 화살표가 내려가 상자 "타임리프 렌더링"에 닿고, 거기서 오른쪽 브라우저 띠로 가는 긴 화살표에 라벨 "HTML: name, value". 브라우저 띠 안에 폼 모양 아이콘과 라벨 "사용자가 값 수정". 브라우저에서 서버로 돌아오는 긴 화살표에 라벨 "HTTP 본문: 이름=값 쌍". 서버 띠 아래쪽에 상자 "요청 파라미터", 그 아래 상자 "WebDataBinder", 그 아래 상자 "새 RoomForm 객체"가 화살표로 이어진다. 두 긴 화살표 사이 가운데에 강조된 열쇠 모양 아이콘과 라벨 "name 속성 = 프로퍼티 이름". 평면적인 기술 문서 스타일, 흰 배경, 파란색과 회색 위주, 장식 없음. 폼 데이터는 객체 → HTML → HTTP 본문 → 객체로 왕복한다. 양쪽을 잇는 것은 입력 요소의 name 속성이다.

    프로젝트 설정: 스타터 하나가 등록하는 것

    스프링 부트 프로젝트에서 타임리프를 쓰려면 의존성 하나를 추가한다. 웹 스타터와 함께 쓰는 최소 구성은 다음과 같다.

    dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-thymeleaf'
}

    이 한 줄로 클래스패스에 타임리프 엔진과 스프링 통합 모듈(thymeleaf-spring6)이 들어온다. 스프링 부트의 ThymeleafAutoConfiguration은 클래스패스에 타임리프의 TemplateMode와 SpringTemplateEngine 클래스가 있을 때 활성화되고, 개발자가 대신할 빈을 직접 등록하지 않았다면 다음 세 가지를 등록한다(Spring Boot 3.5.x 소스 기준). 템플릿 리졸버는 defaultTemplateResolver, 뷰 리졸버는 thymeleafViewResolver라는 이름의 빈이다.

    역할타입하는 일
    템플릿 리졸버SpringResourceTemplateResolver뷰 이름에 접두사·접미사를 붙여 템플릿 파일을 스프링의 리소스 로딩 방식으로 찾는다.
    템플릿 엔진SpringTemplateEngine템플릿을 파싱하고 프로세서를 실행한다. 스프링용 방언이 기본으로 설정된 엔진이다.
    뷰 리졸버ThymeleafViewResolver컨트롤러가 반환한 뷰 이름을 받아 ThymeleafView 객체를 만들어 준다.

    스프링 MVC 1편에서 본 대로 DispatcherServlet은 컨트롤러가 반환한 뷰 이름을 등록된 뷰 리졸버들에게 차례로 물어 View를 얻는다. 타임리프 뷰 리졸버가 그 목록에 들어가는 것이 "통합"의 첫 번째 접점이다. 부트는 이 리졸버의 순서를 Ordered.LOWEST_PRECEDENCE - 5로 지정해 목록의 뒤쪽에 둔다. 다른 리졸버가 먼저 처리할 기회를 갖고, 남는 뷰 이름을 타임리프가 맡는 배치다.

    자동 구성의 동작은 spring.thymeleaf.* 프로퍼티로 조정한다. 자주 보는 것과 그 기본값은 다음과 같다(Spring Boot 3.5.x의 ThymeleafProperties 기준).

    프로퍼티기본값의미
    spring.thymeleaf.prefixclasspath:/templates/뷰 이름 앞에 붙는 경로
    spring.thymeleaf.suffix.html뷰 이름 뒤에 붙는 확장자
    spring.thymeleaf.modeHTML템플릿 모드
    spring.thymeleaf.encodingUTF-8템플릿 파일의 인코딩
    spring.thymeleaf.cachetrue템플릿 캐시 사용 여부
    spring.thymeleaf.servlet.content-typetext/html응답의 Content-Type
    spring.thymeleaf.render-hidden-markers-before-checkboxesfalse체크박스의 히든 마커를 체크박스 앞에 둘지 여부

    컨트롤러가 "rooms/addForm"을 반환하면 템플릿 리졸버는 classpath:/templates/rooms/addForm.html을 찾는다. 프로젝트의 src/main/resources/templates/rooms/addForm.html이 빌드 후 클래스패스의 그 위치에 놓인다. 마지막 프로퍼티는 이 회차의 뒤쪽에서 다시 나온다.

    cache의 기본값이 true라는 점은 알아 둘 만하다. 타임리프는 템플릿 파일을 읽어 파싱한 결과를 캐시에 두고 다음 요청부터 재사용한다. 운영에서는 요청마다 파일을 다시 읽고 파싱하지 않아도 되니 유리하지만, 개발 중에는 템플릿을 고쳐도 화면이 바뀌지 않는 원인이 된다. 개발 환경에서는 spring.thymeleaf.cache=false로 꺼 두는 것이 보통이다.

    타임리프 스프링 통합: 엔진에 무엇이 끼워지는가

    타임리프 자체는 스프링에 의존하지 않는 템플릿 엔진이다. 스프링 없이도 엔진 객체를 만들어 문자열 템플릿을 처리할 수 있다. 타임리프가 템플릿에서 인식하는 속성(th:text, th:each 같은 것)과 표현식에서 쓸 수 있는 객체의 묶음을 방언(dialect)이라고 부르는데, 엔진은 어떤 방언을 쓸지 설정에 따라 달라진다. 표준 타임리프는 표준 방언(Standard Dialect)을 쓰고, 스프링 통합 모듈의 SpringTemplateEngine은 이를 확장한 스프링 표준 방언(SpringStandard Dialect)을 쓴다. 공식 튜토리얼이 밝히는 차이는 다음과 같다.

    • 표현식 언어가 SpEL이다. ${...}와 *{...} 안의 식을 OGNL 대신 스프링 표현 언어(Spring Expression Language, SpEL)로 평가한다. ${room.name}은 SpEL의 프로퍼티 접근 규칙에 따라 getName()을 부른다.
    • 스프링 빈에 접근할 수 있다. ${@roomService.count()}처럼 @빈이름으로 애플리케이션 컨텍스트의 빈을 부를 수 있다.
    • 폼 처리용 속성이 추가된다. th:field, th:errors, th:errorclass가 새로 생기고, th:object가 폼의 커맨드 객체를 선택하는 구현으로 바뀐다.
    • 스프링의 변환 서비스를 쓴다. th:field는 값을 문자열로 만들 때 스프링에 등록된 변환 서비스(Conversion Service)를 적용한다. 변환 서비스 자체는 10회차의 주제다.

    이 차이들이 실제로 연결되는 곳은 뷰 객체다. ThymeleafViewResolver가 만들어 준 ThymeleafView의 render()가 호출되면, 템플릿 엔진을 돌리기 전에 스프링 쪽의 정보를 타임리프의 컨텍스트로 옮겨 싣는 준비가 이루어진다. thymeleaf-spring6의 ThymeleafView.renderFragment() 소스를 따라가면 순서는 다음과 같다.

    두 번째 단계가 이 회차의 중심이다. RequestContext는 스프링 MVC가 JSP 폼 태그 시절부터 뷰 기술에 제공해 온 객체로, "이 모델 객체의 이 프로퍼티는 지금 어떤 값이고 어떤 오류가 있는가"를 답해 준다. 타임리프의 th:field는 프로퍼티 값을 SpEL로 직접 읽지 않고 이 창구를 통해 묻는다. 그 차이가 왜 중요한지는 조금 뒤에 실험으로 확인한다.

    네 번째 단계의 소스에는 평가 컨텍스트를 렌더링마다 새로 만드는 이유가 주석으로 적혀 있다. 스프링의 평가 컨텍스트는 스레드 안전하지 않기 때문이다. 템플릿 엔진과 파싱된 템플릿은 모든 요청 스레드가 공유하지만, 요청마다 달라지는 것(모델, 로케일, 평가 컨텍스트)은 렌더링 한 번에 속한 객체로 따로 만든다. 싱글톤 빈이 상태를 갖지 않아야 한다는 원칙이 여기서도 같은 모양으로 지켜진다.

    여섯 번째 단계에서 기본 writer가 응답의 writer라는 것은 타임리프가 만든 출력이 완성되기를 기다리지 않고 만들어지는 대로 응답 버퍼에 쓰인다는 뜻이다(spring.thymeleaf.servlet.produce-partial-output-while-processing의 기본값이 true다). 메모리에 전체 HTML을 한 번 더 쌓지 않아도 되는 대신, 렌더링 도중 예외가 나면 그 시점에 이미 응답의 앞부분이 버퍼에 쓰여 있을 수 있다. 예외와 오류 페이지의 관계는 8회차에서 다룬다.

    입력 폼 처리: th:object와 th:field

    숙소의 객실을 등록하는 폼을 예제로 쓴다. 먼저 폼의 내용을 담을 객체다. 처음에는 텍스트 입력 두 개만 둔다.

    public class RoomForm {

    private String name;     // 객실 이름
    private Integer price;   // 1박 요금

    public String getName() { return name; }
    public void setName(String name) { this.name = name; }
    public Integer getPrice() { return price; }
    public void setPrice(Integer price) { this.price = price; }
}

    컨트롤러는 등록 폼을 보여 줄 때 비어 있는 객체를 모델에 넣는다. 아직 입력된 것이 없는데 객체를 만들어 넘기는 것이 낭비처럼 보이지만, 폼을 그리는 쪽이 이 객체를 기준으로 삼기 때문에 필요하다.

    @Controller
@RequestMapping("/rooms")
public class RoomController {

    private final Map store = new ConcurrentHashMap<>();
    private final AtomicLong sequence = new AtomicLong();

    @GetMapping("/add")
    public String addForm(Model model) {
        model.addAttribute("room", new RoomForm());
        return "rooms/addForm";
    }

    @PostMapping("/add")
    public String add(@ModelAttribute("room") RoomForm form) {
        long id = sequence.incrementAndGet();
        store.put(id, form);
        return "redirect:/rooms/" + id;
    }

    // ... 상세 조회, 수정 폼은 생략
}

    템플릿에서는 form 태그에 th:object로 이 객체를 지정하고, 입력 요소마다 th:field로 프로퍼티를 가리킨다.

    th:object="${room}"은 이 태그 안쪽에서 쓸 "선택된 객체"를 정한다. 그 안에서 *{name}이라고 쓰면 선택된 객체에 대해 평가되므로 ${room.name}과 같은 값을 가리킨다. 앞 회차에서 본 선택 변수 표현식(selection expression)이 폼에서 쓰이는 자리다. 스프링 통합 모듈은 여기에 제약을 둔다. 공식 튜토리얼에 따르면 폼 태그의 th:object 값은 모델 속성의 이름만 지정하는 변수 표현식이어야 한다. ${room}은 되지만 ${room.detail}처럼 프로퍼티를 타고 들어가는 식은 안 되고, 폼 안에 th:object를 중첩할 수도 없다. 그리고 th:field의 값은 선택 변수 표현식 *{...}이어야 한다. 이 제약은 th:field가 "모델 속성 이름 + 프로퍼티 경로"라는 모양의 바인딩 경로(room.name)를 만들어 스프링에 물어야 하기 때문에 생긴다.

    th:field가 하는 일은 텍스트 입력의 경우 세 가지다. 프로세서(SpringInputGeneralFieldTagProcessor)의 소스를 따라가면 순서는 이렇다.

    1. 바인딩 경로에서 프로퍼티 부분(name)을 얻는다. 이것이 name 속성이 된다.
    2. id를 정한다. 태그에 id 속성이 이미 있으면 그것을 쓰고, 없으면 프로퍼티 이름에서 만든다.
    3. 현재 값을 문자열로 만들어 value 속성에 넣는다. 이 문자열은 HTML 이스케이프를 거친다.

    그래서 위 템플릿은 등록 폼을 처음 열었을 때 다음과 같은 HTML이 된다. 객체의 필드가 모두 null이므로 value는 빈 문자열이다.

    같은 템플릿 조각에 값이 채워진 객체를 넘기면 수정 폼이 된다. 컨트롤러가 저장소에서 꺼낸 객체를 "room"이라는 이름으로 모델에 넣으면 value="오션 스위트"처럼 현재 값이 들어간 채로 렌더링된다. 등록 폼과 수정 폼이 입력 요소의 선언을 그대로 공유할 수 있는 것은 th:field가 "어떤 프로퍼티인가"만 적고 값은 객체에서 읽어 오기 때문이다.

    필드 이름에 오타를 냈을 때의 차이도 크다. name="nmae"라고 손으로 쓴 HTML은 문제없이 렌더링되고, 전송된 값은 대응하는 프로퍼티가 없어 조용히 버려진다. th:field="*{nmae}"는 렌더링 시점에 객체에서 nmae 프로퍼티를 찾지 못해 예외가 난다. 폼을 열어 보는 순간 드러나는 오류가 운영에서 값이 저장되지 않는 오류보다 훨씬 다루기 쉽다.

    한 층 아래: th:field는 값을 어디에서 읽는가

    공식 튜토리얼은 텍스트 입력의 th:field가 id와 name을 붙이고 th:value="*{name}"을 쓴 것과 "비슷하다"고 설명한 뒤, 실제로는 그보다 많은 일을 한다고 덧붙인다. 그 차이가 어디에서 나오는지 보려면 값을 읽는 경로를 따라가야 한다. th:field 프로세서는 프로퍼티를 SpEL로 직접 평가하지 않는다. 앞에서 본 RequestContext에 바인딩 경로 room.name을 넘겨 BindStatus라는 객체를 얻고, 거기서 이름과 값과 타입을 꺼낸다. BindStatus는 스프링 MVC의 클래스이므로 타임리프 없이도 그 동작을 관찰할 수 있다. 모델의 상태를 세 가지로 바꿔 가며 실험해 보자. RoomForm은 뒤에서 추가할 필드(open, facilities, roomType)까지 가진 버전이다. 실행 결과에서 setter가 찍는 추적 줄과 이 설명에 쓰지 않는 줄은 뺐다.

    static void show(RequestContext rc, String path) {
    BindStatus s = rc.getBindStatus(path);
    Object v = s.getValue();
    System.out.println("  " + path + " -> expression=" + s.getExpression() + ", value=" + v
            + " (" + (v == null ? "null" : v.getClass().getSimpleName()) + "), valueType="
            + (s.getValueType() == null ? null : s.getValueType().getSimpleName())
            + ", actualValue=" + s.getActualValue() + ", error=" + s.isError());
}

// [A] 모델에 값이 채워진 객체만 있다 (수정 폼을 GET으로 여는 상황)
//     model = { "room": room }
// [B] 모델에 "room"이 없다
// [C] 변환 서비스(DefaultFormattingConversionService)를 붙인 바인더로
//     POST의 name=방, roomType=PENTHOUSE, _open=on 을 바인딩한 뒤
//     binder.getBindingResult().getModel() 을 모델로 쓴다
    [A] 모델에 객체만 있을 때
  room.name -> expression=name, value=오션 스위트 (String), valueType=String, actualValue=오션 스위트, error=false
  room.open -> expression=open, value=true (Boolean), valueType=boolean, actualValue=true, error=false
  room.facilities -> expression=facilities, value=[WIFI, POOL] (ArrayList), valueType=List, actualValue=[WIFI, POOL], error=false
  room.roomType -> expression=roomType, value=SUITE (RoomType), valueType=RoomType, actualValue=SUITE, error=false
[B] 모델에 객체가 없을 때
  IllegalStateException: Neither BindingResult nor plain target object for bean name 'room' available as request attribute
[C] 바인딩에 실패한 뒤(BindingResult가 모델에 있을 때)
  model keys=[org.springframework.validation.BindingResult.room, room]
  room.name -> expression=name, value=방 (String), valueType=String, actualValue=방, error=false
  room.roomType -> expression=roomType, value=PENTHOUSE (String), valueType=RoomType, actualValue=null, error=true
  room.open -> expression=open, value=false (String), valueType=boolean, actualValue=false, error=false
  target.roomType=null

    [A]부터 보자. 경로 room.name은 첫 번째 점을 기준으로 빈 이름 room과 표현식 name으로 나뉜다. expression이 th:field가 name 속성에 쓰는 값이다. 모델에 객체만 있을 때 BindStatus는 그 객체를 BeanWrapper로 감싸 프로퍼티 값과 타입을 읽는다. valueType이 함께 나온다는 점을 기억해 두자. 체크박스 프로세서는 이 타입이 boolean인지 보고 동작을 정한다.

    [B]는 등록 폼에서 빈 객체를 모델에 넣지 않았을 때 만나는 예외다. 메시지는 "빈 이름 room에 대한 BindingResult도 대상 객체도 요청 속성에 없다"는 뜻이다. th:object와 th:field를 쓰는 폼에서 이 메시지를 보면 컨트롤러가 모델에 넣은 이름과 템플릿의 th:object 이름이 일치하는지부터 확인하면 된다. 앞에서 "비어 있는 객체라도 넘겨야 한다"고 한 이유가 이것이다.

    [C]가 핵심이다. POST 요청의 roomType=PENTHOUSE는 열거형에 없는 값이라 바인딩에 실패했고, 객체의 roomType 필드는 null로 남았다(마지막 줄). 그런데 BindStatus의 value는 null이 아니라 사용자가 보낸 문자열 PENTHOUSE다. 모델에 org.springframework.validation.BindingResult.room이라는 키로 BindingResult가 들어 있으면, BindStatus는 객체보다 그것을 먼저 보고 getFieldValue()로 값을 얻는다. BindingResult는 바인딩에 실패한 필드에 대해 거부된 원래 입력값을 기억하고 있다. 스프링 MVC는 @ModelAttribute 파라미터를 바인딩한 뒤 이 BindingResult를 자동으로 모델에 넣어 두므로, 같은 요청 안에서 폼을 다시 렌더링하면 th:field는 사용자가 입력했던 값을 그대로 보여 줄 수 있다.

    이것이 th:value="*{roomType}"과 th:field="*{roomType}"의 실질적인 차이다. 앞의 것은 객체의 필드만 보므로 실패한 입력을 잃어버린다. 뒤의 것은 바인딩 결과를 거쳐 읽으므로 타입이 맞지 않아 객체에 담기지 못한 입력까지 되돌려 준다. 이 구조 위에 오류 메시지 출력(th:errors)과 검증이 올라가는데, 그것은 4회차의 몫이다.

    [C]의 첫 줄도 눈여겨보자. name으로 들어온 방은 값으로는 그대로 보관된다. th:field는 이 값을 value 속성에 넣을 때 항상 HTML 이스케이프를 적용하고, 튜토리얼에 따르면 이를 끄는 방법은 제공하지 않는다. 사용자가 입력한 문자열이 속성 값을 빠져나와 태그로 해석되는 일을 막기 위한 것이다.

    th:field가 프로퍼티를 직접 읽지 않고 RequestContext → BindStatus를 거치며, BindStatus는 BindingResult가 있으면 그것을, 없으면 모델 객체를 본다는 분기를 보여 준다. 왼쪽에서 오른쪽으로 흐르는 순서도. 맨 왼쪽 상자에 코드처럼 보이는 글자 "th:field=\"*{roomType}\"" 와 그 위 작은 상자 "th:object=\"${room}\"". 두 상자에서 화살표가 합쳐져 상자 "바인딩 경로 room.roomType"로 간다. 다음 상자 "RequestContext". 다음 상자 "BindStatus". BindStatus에서 마름모 "BindingResult가 모델에 있는가?"로 간다. 마름모의 위쪽 가지 라벨 "있다" → 상자 "BindingResult: 거부된 입력값 포함". 아래쪽 가지 라벨 "없다" → 상자 "모델 객체의 프로퍼티". 두 상자에서 화살표가 맨 오른쪽 상자 "id, name, value 속성"으로 모인다. 평면적인 기술 문서 스타일, 흰 배경, 파란색과 주황색 강조, 장식 없음. th:field는 RequestContext에 바인딩 경로를 물어 BindStatus를 얻는다. BindingResult가 있으면 객체보다 그것이 우선이다.

    요구사항 추가: 선택 입력 네 가지와 폼 전송 규칙

    텍스트 입력만으로는 폼이 완성되지 않는다. 객실 등록 폼에 다음 요구사항이 추가되었다고 하자.

    요구사항성격HTML 요소자바 타입
    예약 공개 여부예/아니오체크박스 하나boolean open
    부대시설(와이파이, 수영장, 조식)여러 개 중 0개 이상체크박스 여러 개List facilities
    객실 종류(싱글, 더블, 스위트)여러 개 중 하나라디오 버튼RoomType roomType (열거형)
    전망(바다, 도심, 정원)여러 개 중 하나셀렉트 박스String viewCode

    네 가지 모두 사용자가 글자를 치지 않고 "고르는" 입력이다. 이런 입력을 다루려면 서버 코드보다 먼저 브라우저가 폼을 어떻게 요청으로 바꾸는지 알아야 한다. HTML 표준은 폼을 제출할 때 엔트리 목록(entry list)을 만드는 알고리즘을 정해 두었다. 폼 안의 제출 가능한 요소를 문서에 나온 순서대로 훑으면서 이름과 값의 쌍을 목록에 추가하는데, 그 과정에서 건너뛰는 요소가 있다. 대표적인 것은 다음과 같다.

    • 비활성화된(disabled) 요소
    • name 속성이 없거나 빈 문자열인 요소
    • 체크되지 않은 체크박스와 선택되지 않은 라디오 버튼
    • 버튼 중에서 이번 제출을 일으킨 버튼이 아닌 것

    건너뛰지 않은 요소는 종류에 따라 엔트리를 만든다. 체크박스와 라디오 버튼은 value 속성이 있으면 그 값을, 없으면 문자열 on을 값으로 쓴다. select 요소는 선택된 상태이고 비활성화되지 않은 option마다 엔트리를 하나씩 만든다. 정리하면 다음과 같다.

    요소와 상태만들어지는 엔트리
    텍스트 입력, 비어 있음name= (빈 문자열 값으로 전송된다)
    체크박스, 체크됨, value 없음open=on
    체크박스, 체크됨, value="true"open=true
    체크박스, 체크 안 됨없음
    같은 name의 체크박스 세 개 중 둘 체크facilities=WIFI, facilities=BREAKFAST (같은 이름으로 두 개)
    라디오 그룹, 아무것도 선택 안 됨없음
    라디오 그룹, 하나 선택roomType=SUITE
    셀렉트 박스(단일 선택)viewCode=OCEAN (선택된 option의 값)

    이렇게 만든 엔트리 목록은 폼의 enctype에 따라 직렬화된다. 기본값은 application/x-www-form-urlencoded이고, 이름과 값을 퍼센트 인코딩한 뒤 이름=값을 &로 이어 붙여 요청 본문에 싣는다. 완성된 폼에서 객실 이름에 "오션 스위트", 요금에 180000을 넣고, 공개에 체크하고, 부대시설 세 개 중 와이파이와 조식을 고르고, 스위트와 바다 전망을 선택해 제출하면 본문은 다음과 같다(_open, _facilities는 뒤에서 설명할 히든 마커다). 본문 길이는 195바이트다.

Host: localhost:8080
Content-Type: application/x-www-form-urlencoded
Content-Length: 195

name=%EC%98%A4%EC%85%98+%EC%8A%A4%EC%9C%84%ED%8A%B8&price=180000&open=true&_open=on&facilities=WIFI&_facilities=on&_facilities=on&facilities=BREAKFAST&_facilities=on&roomType=SUITE&viewCode=OCEAN

    한글 다섯 글자는 UTF-8로 글자당 3바이트이고 바이트마다 %XX 세 문자가 되므로 45문자로 늘어난다. 공백은 +가 된다. 체크하지 않은 수영장은 facilities 값으로는 어디에도 나타나지 않는다. 서버에서는 서블릿 컨테이너가 이 본문을 파싱해 요청 파라미터로 만든다. 같은 이름이 여러 번 나올 수 있으므로 파라미터는 이름 하나에 문자열 배열이 대응하는 구조이고(getParameterValues()), 스프링의 데이터 바인더는 이 전체를 받아 프로퍼티 값 목록으로 삼는다.

    이 장의 핵심

    HTTP 폼 전송에는 "선택하지 않았다"를 나타내는 표현이 없다. 체크하지 않은 체크박스와 선택하지 않은 라디오 버튼은 값이 비어서 오는 것이 아니라 이름째로 오지 않는다. 그래서 서버는 파라미터가 없을 때 "사용자가 선택을 해제했다"와 "그 입력 요소가 폼에 처음부터 없었다"를 구분하지 못한다. 이 회차의 체크박스 이야기는 전부 이 한 가지 사실에서 나온다.

    체크 박스 — 단일 1: HTML 체크박스만으로는 부족한 이유

    요구사항에 맞춰 폼 객체에 필드를 추가한다. 이후의 예제는 모두 이 버전을 쓴다. 객실 종류는 화면에 보일 이름을 함께 가진 열거형(enum)으로 둔다.

    public class RoomForm {

    private String name;
    private Integer price;
    private boolean open;              // 예약 공개 여부
    private List facilities;   // 부대시설 코드 목록
    private RoomType roomType;         // 객실 종류
    private String viewCode;           // 전망 코드

    // getter, setter ...
}

public enum RoomType {
    SINGLE("싱글"), DOUBLE("더블"), SUITE("스위트");

    private final String label;
    RoomType(String label) { this.label = label; }
    public String getLabel() { return label; }
}

    이 체크박스에는 value 속성이 없다. 앞 절의 엔트리 목록 규칙에 따라 체크된 상태로 제출하면 open=on이 전송된다. 문자열 "on"을 boolean 필드에 넣을 수 있을까. 스프링의 변환 서비스는 문자열을 불리언으로 바꿀 때 true, on, yes, 1을 참으로, false, off, no, 0을 거짓으로 받아들이고, 대소문자를 가리지 않는다. 빈 문자열은 null이 되고, 그 밖의 문자열은 변환 실패다(DefaultFormattingConversionService로 직접 변환해 확인했다). 그래서 체크한 경우는 문제없이 true가 된다.

    체크 박스 — 단일 2: 히든 마커와 th:field

    히든 입력은 엔트리 목록 규칙에서 항상 전송된다. 그래서 체크박스 옆에 체크박스와 짝을 이루는 히든 입력을 하나 둔다. 이름은 필드 이름 앞에 밑줄을 붙인 것이다.

    이제 체크한 채 제출하면 open=on&_open=on이, 체크를 해제하고 제출하면 _open=on만 전송된다. 이 밑줄 규칙을 해석하는 쪽은 타임리프가 아니라 스프링의 WebDataBinder(spring-web 모듈)다. 타임리프는 마커를 렌더링해 줄 뿐이고, 마커를 손으로 쓴 HTML이든 다른 뷰 기술이 만든 HTML이든 서버 쪽 처리는 같다. WebDataBinder의 Javadoc은 필드 마커를 "필드가 폼에 존재했지만 비어 있어서 요청 파라미터를 만들지 않은 상태"를 감지하기 위한 장치로 설명한다. 바인딩의 핵심 메서드 doBind()는 실제로 프로퍼티에 값을 넣기 전에 파라미터 목록을 세 번 손본다.

    두 번째 단계가 체크박스 문제의 해결책이다. 소스의 조건을 그대로 옮기면, 마커 _open에서 필드 이름 open을 얻은 뒤 ① 그 필드가 바인딩 허용 대상이고 ② 쓰기 가능한 프로퍼티이며 ③ 파라미터 목록에 open이 없을 때만 빈 값을 추가한다. 마커는 조건과 상관없이 목록에서 지운다. 빈 값은 getEmptyValue()가 필드 타입을 보고 정한다.

    세 가지 세부 사항을 짚어 두자. 첫째, 조건 ③은 요청 전체에서 만든 파라미터 목록을 대상으로 검사하므로 본문에서 마커가 체크박스보다 앞에 오든 뒤에 오든 결과가 같다. 스프링 부트의 spring.thymeleaf.render-hidden-markers-before-checkboxes가 히든 입력의 위치를 바꿔도 바인딩 결과는 달라지지 않는다. 둘째, Javadoc에 따르면 마커의 값은 의미가 없고 아무 값이나 써도 된다. on이든 1이든 이름만 맞으면 된다. 셋째, 같은 마커가 여러 번 와도 이름 하나에 값 배열이 붙은 파라미터 하나로 처리되므로 결과는 한 번 온 것과 같다.

    이제 th:field로 같은 체크박스를 쓰면 무엇이 렌더링되는지 보자.

    체크박스 프로세서(SpringInputCheckboxFieldTagProcessor)의 소스를 따라가면 각 속성이 어디에서 왔는지 알 수 있다.

    • name: BindStatus의 expression, 즉 open이다. 텍스트 입력과 같다.
    • id: 태그에 id 속성이 있으면 그것을 그대로 쓰고, 없으면 필드 이름에 순번을 붙인다. 순번은 템플릿 컨텍스트가 가진 IdentifierSequences가 이름별로 세며 1부터 시작한다. 그래서 open이 아니라 open1이 된다. 체크박스는 같은 필드에 여러 개가 붙을 수 있으므로 id가 겹치지 않게 하려는 것이다.
    • value: 필드 타입이 boolean이나 Boolean이면 항상 "true"다. 그 밖의 타입이면 태그에 value 속성이 반드시 있어야 하고, 없으면 "Attribute "value" is required in "input(checkbox)" tags when binding to non-boolean values"라는 메시지의 TemplateProcessingException이 난다.
    • checked: 불리언 필드면 바인딩된 값 자체로, 그 밖의 타입이면 뒤에서 볼 SpringSelectedValueComparator로 정한다. 참이면 checked="checked"를 붙이고, 거짓이면 템플릿에 적혀 있던 checked도 지운다.
    • 히든 마커: 이름은 WebDataBinder.DEFAULT_FIELD_MARKER_PREFIX(밑줄)에 필드 이름을 붙인 것, 값은 on이다. 기본으로는 체크박스 바로 뒤에, 앞의 부트 프로퍼티를 켜면 바로 앞에 삽입된다.

    id에 순번이 붙는다는 점이 처음 보는 사람을 자주 당황시킨다. 레이블에 for="open"이라고 손으로 쓰면 체크박스의 실제 id인 open1과 맞지 않아, 레이블을 눌러도 체크박스가 토글되지 않고 스크린 리더가 둘을 연결하지 못한다. 타임리프는 이를 위해 #ids 유틸리티 객체를 준다. #ids.prev('open')은 그 이름으로 마지막에 발급한 순번을 붙인 값이므로 체크박스 뒤에 오는 레이블에 쓰고, #ids.next('open')은 다음에 발급될 순번이므로 체크박스 앞에 오는 레이블에 쓴다. 아직 한 번도 발급하지 않은 이름에 prev를 부르면 "Cannot obtain previous ID count for ID"로 시작하는 메시지의 예외가 난다. 태그에 id를 직접 적으면 순번이 붙지 않으므로 그 방법도 있다.

    체크박스에 disabled를 붙이면 히든 마커가 만들어지지 않는다는 점도 소스에서 확인할 수 있다. 엔트리 목록 규칙에서 비활성화된 요소는 체크 여부와 상관없이 전송되지 않으므로, 비활성 체크박스는 값도 마커도 보내지 않는다. 서버에서 보면 그 필드는 폼에 없었던 것과 같고, 바인더는 필드를 건드리지 않는다. "이번 수정의 대상이 아니다"라는 비활성의 의미와 일치하는 동작이다.

    체크했을 때와 해제했을 때 전송되는 파라미터가 어떻게 다르고, WebDataBinder의 checkFieldMarkers가 마커를 보고 빈 값을 넣거나 마커를 버리는 분기를 보여 준다. 좌우 두 열로 나뉜 순서도. 왼쪽 열 맨 위 상자 "체크함", 오른쪽 열 맨 위 상자 "체크 해제". 각 상자 아래에 전송된 파라미터를 보여 주는 작은 상자: 왼쪽 "open=true, _open=on", 오른쪽 "_open=on". 두 열의 화살표가 가운데 아래의 큰 상자 "checkFieldMarkers"로 모인다. 그 아래 마름모 "open 파라미터가 있는가?". 마름모 왼쪽 가지 라벨 "있다" → 상자 "마커만 버린다 → open=true". 오른쪽 가지 라벨 "없다" → 상자 "빈 값 추가 → open=false". 두 상자 아래에 공통 상자 "setter 호출". 평면적인 기술 문서 스타일, 흰 배경, 파란색과 회색, 마름모만 주황색, 장식 없음. 마커는 "이 필드가 폼에 있었다"는 신호다. 실제 값이 없을 때만 타입별 빈 값으로 바뀌고, 어느 경우든 마커 자체는 버려진다.

    선택지를 모델에 공급하기: @ModelAttribute 메서드

    여러 개의 체크박스, 라디오 버튼, 셀렉트 박스는 모두 "고를 수 있는 선택지 목록"이 있어야 그릴 수 있다. 등록 폼, 수정 폼, 검증 실패 후 다시 그리는 폼이 모두 같은 목록을 필요로 하므로, 핸들러 메서드마다 model.addAttribute()를 반복하는 대신 컨트롤러에 @ModelAttribute를 붙인 메서드를 둔다.

    스프링 레퍼런스는 이런 메서드가 "같은 컨트롤러의 모든 @RequestMapping 메서드보다 먼저 호출된다"고 설명한다. 반환값은 지정한 이름으로 모델에 들어간다. 여기서 "모든"이라는 말을 비용의 관점에서 읽어야 한다. 이 컨트롤러로 들어오는 요청이라면 등록 폼 GET뿐 아니라 저장 후 곧바로 리다이렉트하는 POST, 선택지를 전혀 쓰지 않는 상세 조회까지 매번 세 메서드가 실행된다. 위 예제는 작은 맵과 리스트를 만들 뿐이라 부담이 없지만, 선택지를 데이터베이스에서 조회하도록 바꾸는 순간 쓰지도 않을 조회가 모든 요청에 붙는다. 바뀌지 않는 목록이라면 static final 상수로 한 번만 만들어 두고 메서드는 그것을 반환하게 하는 편이 낫다. @ControllerAdvice에 두면 여러 컨트롤러가 공유할 수 있지만, 그만큼 호출되는 범위도 넓어진다.

    이름을 생략하면 반환 타입에서 이름을 지어 낸다. 레퍼런스는 그 규칙을 Conventions 클래스에 맡기는데, 스프링 MVC가 실제로 쓰는 ModelFactory.getNameForReturnValue()로 확인하면 RoomType[]은 roomTypeList, List은 stringList, Map은 map이 된다(Spring Framework 7.0.10에서 실행). 템플릿에서 이 이름을 짐작하며 쓰는 것보다 위 예제처럼 이름을 명시하는 편이 읽기 쉽고 안전하다.

    선택지 컬렉션을 고를 때 알아 둘 JDK의 동작이 둘 있다. 첫째, 화면에 보일 순서가 중요하면 Map.of()를 쓰면 안 된다. Map 인터페이스의 Javadoc은 Map.of()가 만든 맵의 반복 순서가 정해져 있지 않고 바뀔 수 있다고 밝힌다. OpenJDK 21의 ImmutableCollections 소스를 보면 반복 순서를 흔드는 값 SALT32L을 클래스 초기화 시점의 System.nanoTime()에서 얻는다. 같은 코드라도 JVM을 다시 띄우면 체크박스 순서가 바뀔 수 있다는 뜻이다. 키 네 개짜리 Map.of()의 keySet()을 출력하는 프로그램을 JDK 21에서 여섯 번 실행했더니 [BREAKFAST, POOL, WIFI, GYM], [GYM, WIFI, POOL, BREAKFAST], [WIFI, POOL, BREAKFAST, GYM] 등 실행마다 다른 순서가 나왔다(어떤 순서가 나올지는 실행마다 다르다). 넣은 순서를 지키는 LinkedHashMap을 쓴 이유가 이것이다. 둘째, 열거형의 values()는 호출할 때마다 새 배열을 만든다. JDK 21의 javac로 컴파일한 열거형을 javap -c로 보면 확인할 수 있다.

      public static RoomType[] values();

    컴파일러가 만든 숨은 정적 필드 $VALUES에 상수 배열이 하나 있고, values()는 그것을 clone()해서 돌려준다. 배열은 변경할 수 있는 객체이므로 내부 배열을 그대로 내주면 호출한 쪽이 원소를 바꿔 넣을 수 있기 때문에 복사본을 주는 것이다. 그래서 RoomType.values() == RoomType.values()는 false다. 요청마다 원소 세 개짜리 배열 하나가 힙에 만들어졌다가 버려지는 정도라 성능 문제로 삼을 일은 아니지만, @ModelAttribute 메서드가 모든 요청에서 실행된다는 사실과 합치면 "요청마다 무엇이 새로 만들어지는가"를 따져 보는 습관을 들이기에 좋은 예다.

    체크 박스 — 멀티: 컬렉션 필드와 선택 판정

    부대시설은 여러 개를 고를 수 있으므로 같은 name을 가진 체크박스 여러 개로 그린다. th:each로 선택지 맵을 돌면서 체크박스마다 같은 th:field를 걸고, 각자의 값은 th:value로 준다. 맵을 th:each로 돌면 반복 변수는 Map.Entry이므로 key와 value 프로퍼티로 꺼낸다.

    수정 폼에서 객체의 facilities가 [WIFI, POOL]이라면 다음과 같이 렌더링된다(thymeleaf-spring6 3.1.5로 렌더링한 결과).

    순번이 facilities1부터 facilities3까지 이어지는 것이 단일 체크박스에서 open1이 나온 이유다. 히든 마커는 체크박스마다 하나씩, 모두 세 개가 생긴다. 앞에서 본 대로 같은 마커가 여러 번 와도 결과는 같으므로 해가 없다. value는 필드 타입이 List라서 불리언 규칙이 적용되지 않고 th:value가 준 값이 쓰인다. th:value를 빠뜨리면 앞에서 본 "value is required" 예외가 난다.

    남은 질문은 checked를 어떻게 정하느냐다. 체크박스의 값은 문자열 "WIFI"이고, 필드 값은 List다. 둘을 비교하는 일은 SpringSelectedValueComparator가 맡는다. 이 클래스는 소스 주석에 스프링의 SelectedValueComparator(JSP 폼 태그가 쓰는 것)의 동작을 그대로 따른다고 적혀 있고, 라디오 버튼과 셀렉트 박스의 옵션도 같은 비교기를 쓴다. 판정 순서는 다음과 같다.

    1. BindStatus.getValue()(화면용 값)가 후보 값과 같으면 선택이다.
    2. getActualValue()(변환 전의 실제 값)가 있고 그것이 후보 값과 같으면 선택이다.
    3. 바인딩된 값이 배열이면 리스트로 바꾸고, 컬렉션이면 contains(후보 값)를 먼저 시도한다. 맵이면 containsKey를 시도한다.
    4. 그래도 못 찾으면 원소를 하나씩 꺼내 비교한다. 원소가 열거형이면 후보 문자열을 name(), toString()과 비교하고, 그 밖에는 양쪽의 문자열 표현을 비교하며, 프로퍼티 에디터가 등록되어 있으면 그것으로 변환해 비교한다.

    지금 예제는 3단계의 contains("WIFI")에서 바로 끝난다. 4단계가 필요한 경우를 생각해 보자. 부대시설 코드를 정수로 바꿔 필드를 List로 선언했다면, 템플릿의 th:value가 만든 후보 값은 문자열 "1"이므로 contains("1")은 거짓이다. 이때 원소 1의 문자열 표현 "1"과 후보 값을 비교하는 4단계 덕분에 체크 상태가 맞게 그려진다. 렌더링은 어차피 문자열의 세계이므로 비교기는 최후에 문자열로 맞춰 본다고 이해하면 된다. 1단계가 getValue()부터 보는 것도 의미가 있다. 앞 절의 실험 [C]에서 보았듯 바인딩에 실패한 뒤에는 getValue()가 사용자가 보낸 원래 문자열이므로, 다시 그린 폼은 객체가 아니라 사용자가 고른 상태를 기준으로 체크된다.

    제출 쪽은 이미 본 것과 같다. 와이파이와 조식만 체크하면 본문의 해당 부분은 facilities=WIFI&_facilities=on&_facilities=on&facilities=BREAKFAST&_facilities=on이다. 서블릿 컨테이너는 이를 facilities → ["WIFI", "BREAKFAST"], _facilities → ["on", "on", "on"] 두 파라미터로 만든다. 바인더는 facilities가 있으므로 마커를 버리고, 문자열 배열을 List로 변환해 넣는다(실험 [7]). 아무것도 체크하지 않으면 마커만 남으므로 facilities는 null이 아니라 빈 ArrayList가 된다(실험 [3]). 필드가 Set이었다면 LinkedHashSet이 들어간다. 서비스 코드가 form.getFacilities().size()처럼 컬렉션을 바로 쓰더라도 마커가 있는 폼에서는 NullPointerException을 만나지 않는다. 다만 이것은 마커가 렌더링된 폼에서 온 요청일 때의 이야기이고, 다른 클라이언트가 보낸 요청에서는 여전히 null일 수 있다.

    라디오 버튼: 하나만 고르는 입력과 열거형 바인딩

    객실 종류는 셋 중 하나만 고른다. 라디오 버튼은 같은 name을 가진 것끼리 그룹을 이루고, 그룹 안에서는 하나만 체크될 수 있다. 템플릿은 멀티 체크박스와 거의 같다.

    라디오 프로세서(SpringInputRadioFieldTagProcessor)는 체크박스 프로세서와 세 가지가 같고 하나가 다르다. id에 순번을 붙이고, value 속성을 필수로 요구하며(없으면 "Attribute "value" is required in "input(radio)" tags"), checked를 같은 비교기로 정한다. 열거형 필드이므로 비교기의 4단계에서 후보 값 "SUITE"가 상수의 name()과 비교된다. 다른 점은 히든 마커를 만들지 않는다는 것이다.

    마커가 없어도 되는 이유는 라디오 그룹의 성질과 빈 값 규칙을 합쳐 보면 나온다. 이미 체크된 라디오 버튼을 다시 눌러도 체크가 풀리지 않는다. 같은 그룹의 다른 버튼을 고를 수 있을 뿐이다. 따라서 폼을 그릴 때 하나라도 체크되어 있었다면 제출할 때도 반드시 어떤 값이 전송되고, "해제했는데 서버가 모른다"는 체크박스의 문제가 생기지 않는다. 처음부터 아무것도 체크되지 않은 그룹을 그대로 제출하면 파라미터가 없는데, 설령 마커가 있었다 해도 열거형 필드의 빈 값은 null이다(앞의 빈 값 표). 새 객체에 바인딩하는 한 마커가 있든 없든 결과는 null로 같다. 선택을 강제하고 싶다면 그것은 검증의 일이며 4회차에서 다룬다.

    이제 서버 쪽에서 문자열 "SUITE"가 열거형 상수가 되는 과정을 한 층 내려가 보자. 스프링의 변환 서비스에 등록된 StringToEnumConverterFactory의 변환기를 javap -c로 보면(spring-core 7.0.10) 하는 일은 두 가지다. 문자열이 비어 있으면 null을 반환하고, 아니면 앞뒤 공백을 trim()한 문자열로 Enum.valueOf(열거형 클래스, 이름)을 호출한다. 실험 [8]에서 SUITE가 들어간 것과 [10]에서 빈 문자열이 오류 없이 null이 된 것이 이 두 갈래다.

    Enum.valueOf()는 JDK 21 소스에서 enumClass.enumConstantDirectory().get(name) 한 줄로 상수를 찾는다. Class 객체가 가진 이 "상수 디렉터리"는 처음 필요할 때 만들어지는 HashMap으로, values()를 리플렉션으로 한 번 호출해 얻은 상수들을 name()을 키로 넣어 둔 것이다. 만들어진 맵은 Class 객체의 필드에 캐시되므로 두 번째 호출부터는 해시 조회 한 번이다. 키가 name() 그대로이므로 조회는 대소문자를 구분한다. 실험 [9]에서 suite가 실패한 이유가 여기 있다. 맵에서 찾지 못하면 IllegalArgumentException이 던져지고, 스프링의 바인더는 이를 잡아 typeMismatch 필드 오류로 BindingResult에 기록한다. 실행 결과에 찍힌 네 개의 오류 코드(typeMismatch.room.roomType부터 typeMismatch까지)는 오류 메시지를 찾을 때 구체적인 것부터 차례로 시도하는 키 목록인데, 이것은 3회차와 4회차에서 메시지 소스와 함께 다룬다.

    템플릿에서 th:value="${type.name()}"이라고 name()을 명시한 것도 이 흐름과 연결된다. 서버의 변환기가 받아들이는 문자열은 정확히 name()이다. 화면에 보일 이름은 label로 따로 두고, 전송되는 값은 상수 이름으로 고정해 두면 표시 문구를 바꿔도 바인딩이 깨지지 않는다.

    셀렉트 박스: 옵션까지 전달되는 th:field

    전망은 셀렉트 박스로 받는다. th:field는 select 태그에만 붙이고, 각 option에는 th:value만 준다. 맨 앞에는 "선택 안 함"을 뜻하는 안내용 옵션을 둔다.

    select의 id에는 순번이 붙지 않는다. 셀렉트 프로세서(SpringSelectFieldTagProcessor)는 computeId를 순번 없이 호출한다. 필드 하나에 셀렉트 요소는 하나이기 때문이다. 흥미로운 것은 옵션이 선택 상태를 아는 방법이다. 옵션 태그에는 th:field가 없는데 어떻게 바인딩된 값을 알까. 셀렉트 프로세서는 자기의 th:field 속성 이름과 값을 지역 변수로 남겨 두고, SpringOptionInSelectFieldTagProcessor가 모든 option 요소에 대해 동작하면서 그 지역 변수가 있으면 셀렉트의 th:field를 옵션에 그대로 옮겨 붙인다. 그다음 옵션용 프로세서가 그 속성을 처리해 비교기로 선택 여부를 정하고 selected="selected"를 붙인다.

    "모든 옵션"이라는 점에서 함정이 하나 생긴다. 타임리프 속성이 하나도 없는 안내용 옵션도 이 처리를 받는다. 옵션 프로세서는 value 속성을 필수로 요구하므로, 안내용 옵션을 처럼 value 없이 쓰면 "Attribute "value" is required in "option" tags"라는 템플릿 처리 예외가 난다. 같은 옵션을 th:field가 없는 셀렉트 안에 두면 아무 문제가 없으니 더 헷갈린다. 위 예제처럼 value=""를 명시하면 된다.

    그 value=""가 서버에서 어떻게 보이는지도 알아야 한다. HTML 표준의 선택 상태 설정 알고리즘에 따르면 multiple이 없는 일반 셀렉트 박스는 선택된 옵션이 하나도 없으면 비활성화되지 않은 첫 옵션을 선택 상태로 만든다. 그래서 단일 셀렉트 박스는 (비활성화되지 않은 한) 항상 값을 하나 보낸다. 사용자가 안내용 옵션을 그대로 두고 제출하면 viewCode=가 전송되고, String 필드에는 null이 아니라 빈 문자열이 들어간다(실험 [8]의 viewCode=""). 같은 상황에서 필드가 열거형이었다면 변환기의 첫 갈래 때문에 null이 된다. 문자열 필드에서도 빈 값을 null로 받고 싶다면 컨트롤러의 @InitBinder 메서드에서 StringTrimmerEditor(true)를 등록하는 방법이 있다. 생성자 인자 true는 공백을 잘라 낸 결과가 빈 문자열이면 null로 바꾸라는 뜻이다.

    여러 개를 고르는 multiple 셀렉트 박스는 체크박스와 같은 문제를 가진다. 아무것도 선택하지 않으면 엔트리가 하나도 생기지 않는다. 그래서 셀렉트 프로세서는 태그에 multiple이 있고 disabled가 없을 때 히든 마커를 만든다. 이름은 역시 밑줄 접두사, 값은 1이다. 위치는 체크박스와 달리 항상 앞이다. 소스의 주석이 이유를 밝히는데, select는 본문을 가진 열린 요소라서 "뒤에 삽입"하면 히든 입력이 select 안쪽에 들어가 버리기 때문이다. 그래서 을 앞에 거느린 채 렌더링된다. 마커의 값이 on이 아니라 1이어도 앞에서 본 대로 바인더는 값을 보지 않으므로 상관없다.

    지금까지의 네 가지 선택 입력을 th:field의 처리 방식으로 비교하면 다음과 같다.

    입력idvalue선택 표시히든 마커

    체크박스(그 밖의 필드)순번 붙음필수비교기체크박스마다 하나

    마커가 있는 행과 없는 행을 가르는 기준은 하나다. 사용자가 "아무것도 고르지 않은 상태"를 만들 수 있고, 그 상태가 엔트리를 하나도 만들지 않는 입력에만 마커가 붙는다.

    서버는 선택지를 믿지 않는다

    선택 입력은 사용자가 화면에 있는 것만 고를 수 있으니 안전하다고 느끼기 쉽다. 하지만 선택지는 브라우저의 화면을 제한할 뿐 HTTP 요청을 제한하지 않는다. 개발자 도구로 옵션의 value를 고치거나, 폼 없이 요청을 직접 보내면 서버는 어떤 문자열이든 받는다.

    curl -d 'name=test&price=1&viewCode=MOON&roomType=PENTHOUSE&facilities=SPA&_open=on' \
     http://localhost:8080/rooms/add

    지금까지 본 규칙으로 결과를 예측할 수 있다. viewCode는 String 필드이므로 "MOON"이 아무 오류 없이 들어간다. facilities도 List이므로 목록에 없는 "SPA"가 그대로 담긴다. roomType만 열거형이라 Enum.valueOf()가 실패해 typeMismatch 오류가 된다. _open=on은 사용자가 체크를 해제한 것과 같은 효과를 낼 뿐이라 이것으로 얻는 권한은 없다. 열거형은 타입 자체가 허용 값의 목록이라 변환 단계에서 공짜 검사를 해 주지만, 문자열 코드는 서버가 "허용된 코드 목록에 있는가"를 직접 확인해야 한다. 그 확인을 어디에서 어떻게 하는지가 4회차와 5회차의 검증 주제다.

    더 위험한 것은 폼에 없는 필드다. 폼 객체에 화면에 없는 필드(예를 들어 관리자만 바꿀 수 있는 승인 여부)가 있다면, 요청에 그 이름의 파라미터를 끼워 넣는 것만으로 값을 바꿀 수 있다. 바인더는 "이 필드가 폼에 그려져 있었는가"를 알지 못하고, 쓰기 가능한 프로퍼티면 값을 넣는다. 이런 공격을 대량 할당(mass assignment)이라고 부른다. 대응은 두 가지다. 화면에서 받을 필드만 가진 전용 폼 객체를 쓰고 도메인 객체나 엔티티를 바인딩 대상으로 직접 쓰지 않는 것, 그리고 필요하면 @InitBinder에서 setAllowedFields()로 바인딩할 필드를 명시하는 것이다. 이 회차의 RoomForm이 별도 클래스인 이유이기도 하다. disabled나 readonly도 브라우저의 화면 동작일 뿐 서버를 보호하지 않는다는 점은 같은 원리다.

    흔한 오해와 함정

    지금까지의 내용을 자주 틀리는 문장으로 다시 정리해 보자. 각 항목은 앞에서 실험이나 소스로 확인한 사실에 근거한다.

    • "체크를 안 하면 false가 전송된다." 아무것도 전송되지 않는다. false는 서버의 WebDataBinder가 마커를 보고 만들어 낸 값이거나, 기본형 필드의 초깃값이 우연히 남은 것이다. 래퍼형이나 기존 객체에서는 그 차이가 드러난다(실험 [1], [5]).
    • "히든 마커는 타임리프의 기능이다." 마커를 해석하는 것은 스프링의 WebDataBinder다. 타임리프는 그것을 대신 그려 줄 뿐이므로, 자바스크립트로 폼 데이터를 직접 만들어 보내는 화면에서는 마커를 직접 넣어야 같은 효과를 얻는다.
    • "th:field는 th:value의 축약이다." 값을 객체에서 직접 읽지 않고 BindStatus를 거치므로 바인딩에 실패한 입력을 되살린다. 체크박스에서는 마커를, 셀렉트에서는 옵션의 선택 상태까지 처리한다.
    • "레이블은 필드 이름을 for에 적으면 된다." 체크박스와 라디오 버튼의 id에는 순번이 붙는다. #ids.prev()나 #ids.next()를 쓰거나 id를 직접 지정한다.
    • "안내용 옵션에는 value가 필요 없다." th:field가 붙은 셀렉트 안에서는 모든 옵션이 처리 대상이라 value가 없으면 예외가 난다. 그리고 value=""는 문자열 필드에 빈 문자열로 들어온다.
    • "화면에 없는 값은 들어올 수 없다." 선택지와 disabled는 브라우저의 제약이다. 서버는 받은 문자열을 타입이 허락하는 한 그대로 바인딩한다.

    정리: 다른 회차와의 연결

    이 회차는 폼 왕복의 두 끝을 따라갔다. 나가는 쪽에서는 ThymeleafView가 RequestContext를 준비하고, th:field가 그 창구로 BindStatus를 얻어 id, name, value, 선택 상태, 히든 마커를 만든다. 들어오는 쪽에서는 브라우저가 엔트리 목록 규칙으로 고른 이름=값 쌍만 보내고, WebDataBinder가 기본값 파라미터와 마커를 먼저 처리한 뒤 변환 서비스로 문자열을 필드 타입에 맞춰 넣는다. 체크박스와 다중 셀렉트의 마커는 "선택 안 함"을 표현할 수 없는 프로토콜의 빈틈을 메우는 장치다.

    여기서 남겨 둔 것들은 이후 회차에서 이어진다. 레이블과 안내 문구를 템플릿에 한글로 박아 둔 것은 3회차에서 메시지 소스와 #{...} 표현식으로 바꾼다. 실험 [9]의 typeMismatch 오류 코드와 BindingResult, 그리고 th:errors로 오류를 보여 주는 방법은 4회차의 중심이다. th:field가 값을 문자열로 만들 때 적용한다고 한 변환 서비스와 포매터의 구조는 10회차에서 다룬다.
    스프링 통합 타임리프
    SpringTemplateEngine이 SpEL, 빈 접근, th:field 같은 폼 속성, 변환 서비스를 더한 방언을 쓴다. 부트는 템플릿 리졸버, 엔진, 뷰 리졸버를 자동으로 등록한다.
    th:object와 th:field
    폼의 커맨드 객체를 고르고 프로퍼티를 가리키면, th:field가 바인딩 경로로 id, name, value와 선택 상태를 만든다.
    BindStatus
    th:field가 값을 읽는 창구다. 모델에 BindingResult가 있으면 그것을 먼저 보므로 타입 변환에 실패한 입력도 다시 그릴 수 있다.
    폼 엔트리 목록
    브라우저는 체크되지 않은 체크박스, 선택되지 않은 라디오, 비활성 요소를 건너뛴다. 폼 전송에는 "선택하지 않음"을 나타내는 표현이 없다.
    필드 마커
    _필드이름 히든 파라미터. WebDataBinder는 실제 값 파라미터가 없을 때만 타입별 빈 값(불리언은 false, 컬렉션은 빈 컬렉션, 그 밖은 null)을 넣고, 마커 자체는 항상 버린다.
    선택 판정
    체크박스, 라디오, 옵션의 선택 상태는 SpringSelectedValueComparator가 정한다. 동등 비교, 컬렉션 포함 여부, 열거형 이름, 문자열 표현 순으로 맞춰 본다.
    id 순번과 #ids
    체크박스와 라디오의 id에는 1부터 시작하는 순번이 붙는다. 레이블은 #ids.prev()나 #ids.next()로 연결한다.
    @ModelAttribute 메서드
    같은 컨트롤러의 모든 핸들러보다 먼저, 요청마다 호출되어 반환값을 모델에 넣는다. 이름을 명시하고, 무거운 조회를 넣지 않는다.

    "체크를 풀고 저장했는데 그대로 체크되어 있다"는 버그 신고를 받으면, 먼저 브라우저 개발자 도구에서 실제로 전송된 요청 본문을 본다. 체크박스 값이 없는 것은 정상이고, 확인할 것은 _필드이름 마커가 있는가다. 마커가 없다면 그 폼은 th:field 없이 손으로 쓴 HTML이거나, 자바스크립트로 폼 데이터를 직접 조립해 보내는 화면일 가능성이 높다. 마커가 있는데도 값이 바뀌지 않는다면 서버 쪽에서 바인딩 이후에 폼 객체의 값을 도메인 객체로 옮기는 코드가 null이나 false를 "변경 없음"으로 해석하고 있지 않은지 본다. 바인딩 대상이 새 객체인지, 모델이나 세션에서 온 기존 객체인지에 따라 같은 요청의 결과가 달라진다는 점이 진단의 열쇠다.

    JSON을 주고받는 API에는 이 회차의 마커 이야기가 적용되지 않는다. @RequestBody는 WebDataBinder가 아니라 HTTP 메시지 컨버터로 본문을 객체로 바꾸고, JSON은 false와 빈 배열을 명시적으로 표현할 수 있다. 같은 기능을 HTML 폼과 API 두 경로로 제공한다면 "값이 없다"를 해석하는 규칙이 두 군데에 생긴다는 뜻이므로, 두 경로가 결국 같은 의미로 수렴하는지 테스트로 확인해 두는 편이 안전하다.

    선택지 목록은 처음에는 코드에 박힌 몇 개의 값이지만, 운영 중에는 관리 화면에서 바뀌는 데이터가 되기 쉽다. 그때 @ModelAttribute 메서드에 조회를 넣으면 그 컨트롤러의 모든 요청에 조회가 붙는다. 목록이 자주 바뀌지 않는다면 캐시를 두고, 폼을 그리는 핸들러에서만 모델에 넣는 방식도 고려한다. 그리고 목록이 어디에서 오든 서버는 제출된 코드가 그 목록에 있는지 다시 확인해야 한다. 화면의 선택지는 사용 편의를 위한 것이지 입력 검증이 아니다.
  • 부대시설 멀티 체크박스(와이파이, 수영장, 조식 순서) 템플릿이 있고, 수정 폼을 열 때 객체의 facilities는 [POOL]이다. ① 렌더링된 세 체크박스의 id와 checked 여부를 적어라. ② 사용자가 수영장을 해제하고 와이파이만 체크해 제출했을 때 본문 중 부대시설 부분을 순서대로 적고, 바인딩 후 facilities의 값을 적어라.
  • 컨트롤러가 @SessionAttributes("room")으로 수정 중인 객체를 세션에 두고, 템플릿은 로 손으로 작성되어 있다. 세션 객체의 open이 true일 때 사용자가 체크를 해제하고 저장하면 open은 무엇이 되는가. 원인을 설명하고 고치는 방법을 두 가지 제시하라.
  • 필드가 Set tags, Boolean pet, String memo, String[] codes인 새 객체에 요청 _tags=1&_pet=on&_memo=x&_codes=on&codes=A를 바인딩한다. 네 필드의 값을 예측하고 각각의 이유를 checkFieldMarkers의 조건으로 설명하라.
  • th:field="*{viewCode}"가 붙은 셀렉트 안에 을 두었더니 템플릿 처리 예외가 났다. 같은 옵션을 th:field 없는 셀렉트에 두면 괜찮은 이유를 설명하고, value=""로 고친 뒤 사용자가 그 옵션을 그대로 두고 제출하면 String viewCode와 RoomType roomType(같은 방식의 셀렉트라고 가정)에 각각 무엇이 들어가는지 적어라.
  • 누군가 roomType=suite로 요청을 보냈고, 컨트롤러는 바인딩 오류가 있으면 같은 폼 템플릿을 다시 렌더링한다. 다시 그린 라디오 버튼 세 개 중 체크되는 것은 무엇인가. BindStatus와 비교기의 판정 순서로 설명하라.
    •

    1. ① id는 순서대로 facilities1, facilities2, facilities3이다. 비교기가 [POOL].contains(후보 값)를 보므로 facilities2(수영장)만 checked="checked"를 받는다. ② 히든 마커가 각 체크박스 바로 뒤에 있으므로 본문은 facilities=WIFI&_facilities=on&_facilities=on&_facilities=on이다. 수영장은 체크가 풀려 값이 빠지고 마커만 남는다. 바인더는 facilities 파라미터가 있으므로 마커를 버리고 ["WIFI"]를 리스트로 넣는다. 결과는 [WIFI]다.

    2. open은 true로 남는다. 체크를 해제하면 open 파라미터가 전송되지 않고, 마커도 없으니 바인더는 이 필드를 건드리지 않는다. 바인딩 대상이 새 객체가 아니라 세션에서 꺼낸 기존 객체이므로 이전 값이 그대로 남는다(실험 [5]와 같은 상황). 고치는 방법은 ① 체크박스 옆에 을 직접 넣거나, ② 템플릿을 th:object와 th:field="*{open}"으로 바꿔 타임리프가 마커를 렌더링하게 하는 것이다. 어느 쪽이든 마커만 온 요청에서 getEmptyValue(boolean)이 false를 넣는다.

    3. tags는 빈 LinkedHashSet, pet은 false, memo는 null, codes는 ["A"]다. 앞의 셋은 실제 값 파라미터가 없으므로 마커가 타입별 빈 값을 넣는다. 컬렉션은 CollectionFactory가 Set에 대해 LinkedHashSet을 만들고, 래퍼형 Boolean도 Boolean.FALSE를 받으며, String은 "그 밖의 타입"이라 null이다. 마커의 값(1, x)은 의미가 없다. codes는 같은 이름의 파라미터가 있으므로 조건 ③에서 마커가 무시되고 지워진다.

    4. th:field가 붙은 셀렉트 프로세서는 자기의 th:field를 지역 변수로 남기고, SpringOptionInSelectFieldTagProcessor가 그 안의 모든 옵션에 그것을 옮겨 붙인다. 옵션 프로세서는 value 속성을 필수로 요구하므로 예외가 난다. th:field 없는 셀렉트에서는 지역 변수가 없어 옵션이 처리 대상이 아니다. value=""로 고치면 viewCode=가 전송되어 String 필드에는 빈 문자열 ""이 들어가고(실험 [8]), 열거형 필드는 변환기가 빈 문자열을 null로 바꾼다(실험 [10]).

    5. 아무것도 체크되지 않는다. Enum.valueOf()는 대소문자를 구분하므로 바인딩에 실패하고, 필드는 null로 남는다. 다시 렌더링할 때 BindStatus는 BindingResult를 먼저 보므로 getValue()는 거부된 문자열 "suite"이고 실제 값은 없다(앞의 실험 [C]에서 PENTHOUSE가 그랬던 것과 같다). 비교기는 후보 값 "SINGLE", "DOUBLE", "SUITE"를 "suite"와 비교하는데, 동등 비교와 문자열 표현 비교 어디에도 대소문자를 무시하는 단계가 없으므로 모두 거짓이다.

     th:field="*{open}"(불리언 필드)으로 렌더링한 체크박스의 체크를 해제하고 제출했다. 요청 본문에서 이 필드와 관련된 부분은 무엇인가? open=false&_open=on _open=on open=&_open=on 아무것도 없다 체크되지 않은 체크박스는 엔트리 목록에서 빠지므로 open은 이름째로 전송되지 않는다. 히든 입력은 항상 전송되므로 _open=on만 남는다. false는 브라우저가 보내는 값이 아니라 서버의 WebDataBinder가 마커를 보고 넣는 값이다. "아무것도 없다"는 마커 없이 손으로 쓴 체크박스의 경우다. 요청 본문이 _open=on&open=true처럼 마커가 실제 값보다 앞에 온다. 바인딩 후 boolean open은? false. 마커가 먼저 처리되어 빈 값이 들어간 뒤 덮어쓰이지 않는다. true. 마커는 요청 전체에 open 파라미터가 있는지 보고, 있으면 버려진다. 바인딩 오류가 난다. 같은 필드에 값이 두 번 들어간다. 마커의 값 on이 변환되어 true가 된다. checkFieldMarkers는 본문의 순서가 아니라 요청 전체에서 만든 파라미터 목록에 open이 있는지를 검사한다. 있으므로 마커는 빈 값을 넣지 않고 지워진다. 그래서 부트의 마커 위치 설정은 바인딩 결과에 영향을 주지 않는다. 마커의 값은 바인더가 보지 않으므로 마지막 보기도 틀렸다. 다음에 을 손으로 썼다. 무엇이 잘못되는가? 아무 문제 없다. th:field가 id="open"을 만든다. 템플릿 처리 예외가 난다. 체크박스에는 레이블을 붙일 수 없다. 체크박스의 id는 open1이 되므로 레이블이 연결되지 않는다. 레이블의 for가 name과 같아서 값이 두 번 전송된다. 체크박스와 라디오 버튼은 같은 필드에 여러 개가 있을 수 있어 th:field가 1부터 시작하는 순번을 id에 붙인다. 레이블을 눌러도 체크박스가 토글되지 않고 보조 기술도 둘을 연결하지 못한다. th:for="${#ids.prev('open')}"을 쓰거나 id를 직접 지정해야 한다. 레이블은 전송되는 요소가 아니다. multiple 셀렉트 박스에 th:field를 붙이면 히든 마커가 select 태그 앞에 렌더링된다. 체크박스처럼 뒤에 두지 않는 이유는? 스프링은 마커가 값보다 먼저 와야 인식한다. 셀렉트 박스는 항상 값을 보내므로 마커가 필요 없어서 무시되도록 앞에 둔다. HTML 표준이 히든 입력을 셀렉트 앞에 두도록 요구한다. select는 본문을 가진 열린 요소라 뒤에 삽입하면 마커가 select 안쪽에 들어가기 때문이다. 셀렉트 프로세서 소스의 주석이 밝히는 이유다. 체크박스 input은 본문이 없는 요소라 바로 뒤에 붙여도 되지만, select는 여는 태그 뒤가 옵션들의 자리다. 바인더는 순서와 무관하게 동작하므로 첫 보기는 틀렸고, 다중 셀렉트는 아무것도 선택하지 않으면 값을 보내지 않으므로 마커가 필요하다. 컨트롤러에 @ModelAttribute("viewOptions") 메서드가 있고, 그 메서드가 데이터베이스에서 전망 목록을 조회한다. 같은 컨트롤러의 등록 POST 핸들러가 저장 후 redirect:를 반환할 때, 이 조회는 어떻게 되는가? POST 핸들러보다 먼저 실행된다. 렌더링하지 않는 요청에도 조회 비용이 든다. 뷰를 렌더링하지 않으므로 실행되지 않는다. 템플릿에서 ${viewOptions}를 처음 읽을 때 지연 실행된다. 애플리케이션 시작 시 한 번만 실행되고 결과가 캐시된다. 스프링 레퍼런스에 따르면 @ModelAttribute 메서드는 같은 컨트롤러의 모든 @RequestMapping 메서드보다 먼저 호출된다. 핸들러가 무엇을 반환할지는 호출 시점에 알 수 없으므로 리다이렉트하는 요청에서도 실행된다. 지연 실행이나 자동 캐시는 없다.
    방언(Dialect)
    타임리프가 템플릿에서 인식하는 속성 프로세서와 표현식 객체의 묶음. 스프링 통합 모듈은 표준 방언을 확장한 스프링 표준 방언을 쓴다.
    선택 변수 표현식(selection variable expression)
    *{...} 형태의 표현식. th:object로 선택한 객체를 기준으로 평가된다. th:field의 값은 이 형태여야 한다.
    BindStatus
    스프링 MVC가 뷰 기술에 제공하는, 바인딩 경로 하나의 상태 객체. 표현식(필드 이름), 화면용 값, 실제 값, 값의 타입, 오류 여부를 담는다.
    엔트리 목록(entry list)
    HTML 표준이 폼 제출 시 만드는 이름과 값 쌍의 목록. 이것이 enctype에 따라 요청 본문으로 직렬화된다.
    필드 마커(field marker)
    밑줄로 시작하는 파라미터(_open). 필드가 폼에 있었음을 알려, 값 파라미터가 없을 때 WebDataBinder가 빈 값을 넣게 한다.
    필드 기본값(field default)
    느낌표로 시작하는 파라미터(!roomType). 값 파라미터가 없을 때 빈 값 대신 지정한 값을 넣게 한다.
    SpringSelectedValueComparator
    타임리프 스프링 모듈에서 체크박스, 라디오, 옵션의 선택 상태를 정하는 비교기. 스프링 JSP 폼 태그의 SelectedValueComparator와 같은 규칙을 따른다.
    대량 할당(mass assignment)
    요청에 화면에 없는 필드 이름의 파라미터를 끼워 넣어, 바인더가 의도하지 않은 프로퍼티까지 값을 넣게 만드는 공격.
