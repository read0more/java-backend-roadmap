    API의 오류 응답은 왜 따로 설계해야 하는가

    08회에서 본 오류 페이지는 사람을 위한 것이었다. 브라우저 사용자는 상태 코드를 읽지 않는다. 화면에 "요청하신 페이지를 찾을 수 없습니다"라는 문장과 홈으로 돌아가는 링크가 보이면 충분하다. 서블릿 컨테이너가 예외나 sendError를 감지해 /error 같은 오류 경로로 요청을 한 번 더 보내고, 그 경로가 상태 코드에 맞는 HTML 템플릿을 그려 주는 구조는 이 목적에 잘 맞는다. 오류 화면은 4xx 한 장, 5xx 한 장 정도면 대부분의 경우를 덮는다.

    API의 상대는 사람이 아니라 프로그램이다. 모바일 앱, 다른 서버, 프런트엔드 자바스크립트가 응답을 받아 코드로 분기한다. 이들에게 HTML 오류 페이지는 파싱할 수 없는 잡음이다. 클라이언트는 상태 코드로 큰 분류(내 잘못인가, 서버 잘못인가, 다시 시도해도 되는가)를 정하고, 본문에 실린 오류 코드로 세부 분기(재고 부족이면 수량 입력란을 다시 보여 준다, 인증 만료면 로그인 화면으로 보낸다)를 한다. 따라서 API 오류 응답은 정상 응답과 똑같이 계약(contract)이다. 필드 이름이 하나 바뀌면 클라이언트가 깨진다.

    이 계약에는 세 가지 요구가 겹친다. 첫째, 상태 코드가 정확해야 한다. 클라이언트가 보낸 값이 잘못되었는데 500을 돌려주면 클라이언트는 "서버가 잠시 아픈가 보다" 하고 같은 요청을 재시도한다. 둘째, 본문의 형식이 일정해야 한다. 어떤 API는 {"error": "..."}를, 다른 API는 {"message": "..."}를 돌려주면 클라이언트는 오류 처리 코드를 API마다 따로 써야 한다. 셋째, 내부 정보가 새어 나가면 안 된다. 스택 트레이스, SQL 문장, 클래스 이름은 공격자에게 서버 구조를 알려 주는 지도다.

    이 회차는 이 세 요구를 스프링 MVC가 어떤 장치로 해결하는지 따라간다. 출발점은 스프링 부트가 아무 설정 없이 해 주는 기본 오류 처리이고, 그다음 그 기본 동작이 어디서 결정되는지, 즉 DispatcherServlet이 예외를 잡아 HandlerExceptionResolver 목록에 넘기는 지점으로 내려간다. 그 위에 스프링이 기본으로 등록하는 세 리졸버, @ExceptionHandler와 @ControllerAdvice, 스프링 6의 ProblemDetail을 차례로 쌓는다. 예제는 스프링 프레임워크 6.x와 부트 3.x를 기준으로 쓰고, 실행 결과를 보여 줄 때는 실제로 돌린 버전을 함께 적는다.

    스프링 부트의 기본 오류 처리: /error가 JSON도 만든다

    먼저 아무것도 하지 않았을 때 무슨 일이 일어나는지 보자. 아래 컨트롤러는 주문 하나를 조회하는 API다. 주문 번호가 0이면 IllegalArgumentException을 던진다. 예외를 처리하는 코드는 하나도 없다.

    @RestController
@RequestMapping("/api/orders")
public class OrderApiController {

    @GetMapping("/{id}")
    public OrderDto find(@PathVariable long id) {
        if (id == 0) {
            throw new IllegalArgumentException("주문 번호는 0일 수 없습니다");
        }
        return new OrderDto(id, "책");
    }
}

public record OrderDto(long id, String item) {}

    이 API를 Accept: application/json으로 호출하면 스프링 부트 3.x 애플리케이션은 HTML이 아니라 JSON을 돌려준다. 본문의 모양은 다음과 같다. timestamp의 값은 요청 시각이므로 실행마다 다르다.

    {
  "timestamp": "…요청 시각…",
  "status": 500,
  "error": "Internal Server Error",
  "path": "/api/orders/0"
}

    같은 URL을 브라우저로 열면 "Whitelabel Error Page"라는 HTML이 나온다. 하나의 경로가 클라이언트에 따라 두 가지 표현을 돌려주는 셈이다. 스프링 부트 레퍼런스는 이를 "기계 클라이언트에게는 오류 세부 정보·HTTP 상태·예외 메시지를 담은 JSON을, 브라우저 클라이언트에게는 같은 데이터를 HTML로 그린 whitelabel 뷰를" 준다고 설명한다. 이 분기는 BasicErrorController의 두 메서드에서 일어난다. 부트 3.5 소스에서 핵심만 옮기면 이렇다.

    @Controller
@RequestMapping("${server.error.path:${error.path:/error}}")
public class BasicErrorController extends AbstractErrorController {

    @RequestMapping(produces = MediaType.TEXT_HTML_VALUE)
    public ModelAndView errorHtml(HttpServletRequest request, HttpServletResponse response) {
        // ... HTML 오류 뷰를 고른다 (08회)
    }

    @RequestMapping
    public ResponseEntity> error(HttpServletRequest request) {
        HttpStatus status = getStatus(request);
        if (status == HttpStatus.NO_CONTENT) {
            return new ResponseEntity<>(status);
        }
        Map body = getErrorAttributes(request, getErrorAttributeOptions(request, MediaType.ALL));
        return new ResponseEntity<>(body, status);
    }
}

    두 메서드는 경로가 같고 produces 조건만 다르다. 브라우저처럼 Accept 헤더에 text/html을 명시한 요청은 produces = text/html 조건이 붙은 errorHtml로 가고, Accept: application/json을 보낸 API 클라이언트의 요청은 errorHtml의 조건과 맞지 않으므로 조건 없는 error로 간다. 스프링 MVC 1편에서 본 요청 매핑의 내용 협상(content negotiation)이 오류 처리에서도 그대로 쓰이는 것이다. error는 ResponseEntity를 돌려주므로 HTTP 메시지 컨버터가 맵을 JSON으로 직렬화한다.

    스프링 부트 4.x에서는 이 클래스가 spring-boot-webmvc 모듈로 옮겨졌고 경로 프로퍼티도 spring.web.error.path로 바뀌었다(4.1.2 소스 기준). 3.x에서는 server.error.path다.

    그렇다면 컨트롤러 안에서 던진 예외가 어떻게 /error까지 가는가. 08회에서 본 길을 API 관점에서 다시 짚으면 이렇다. 예외는 DispatcherServlet 밖으로 빠져나가 톰캣까지 전파된다. 톰캣은 예외를 잡아 응답 상태를 500으로 정하고, 스프링 부트가 컨테이너에 "전역(global) 오류 페이지"로 등록해 둔 /error로 요청을 내부 포워드한다. 이때 디스패처 타입은 ERROR이고, 요청 속성에 jakarta.servlet.error.status_code, jakarta.servlet.error.exception, jakarta.servlet.error.request_uri 같은 값이 채워진다. 포워드된 요청은 다시 DispatcherServlet으로 들어가 BasicErrorController에 매핑된다. getStatus는 jakarta.servlet.error.status_code 속성을 읽어 상태를 정한다.

    본문은 DefaultErrorAttributes가 만들고, 대부분은 지운다

    JSON 본문의 내용은 ErrorAttributes 빈이 만든다. 기본 구현인 DefaultErrorAttributes(부트 3.x 패키지 org.springframework.boot.web.servlet.error)는 LinkedHashMap에 timestamp, status, error를 넣고, 예외가 있으면 exception(클래스 이름)과 필요하면 trace를, 이어서 예외 유무와 관계없이 message(바인딩·검증 오류가 있으면 errors도)를 넣은 뒤, 마지막에 path를 넣는다. 그리고 ErrorAttributeOptions.retainIncluded로 허용되지 않은 키를 지운다. 부트 3.5의 ErrorAttributeOptions.defaults()는 PATH, STATUS, ERROR만 포함하므로, timestamp를 빼면 이 세 키만 남는다. 위 JSON에 예외 메시지가 없었던 이유가 이것이다. 메시지는 계산은 되었지만 응답에 실리기 전에 제거되었다.

    무엇을 남길지는 server.error.* 프로퍼티가 정한다. 부트 3.5 공식 프로퍼티 목록의 기본값은 다음과 같다.

    프로퍼티기본값켜면 추가되는 키
    server.error.include-exceptionfalseexception (예외 클래스 이름)
    server.error.include-messagenevermessage
    server.error.include-binding-errorsnevererrors (바인딩·검증 오류 목록)
    server.error.include-stacktracenevertrace
    server.error.include-pathalwayspath
    server.error.path/error오류 컨트롤러의 경로

    never/always 외에 on_param도 있다. on_param으로 두면 요청 파라미터(예: message, trace)가 있을 때만 해당 키를 넣는다. 운영 환경에서 이 값을 바꾸는 것은 위험하다. include-stacktrace=on_param이면 누구든 URL 끝에 파라미터 하나를 붙여 스택 트레이스를 받아 갈 수 있다. 예외 메시지도 마찬가지다. 라이브러리가 만든 예외 메시지에는 SQL 일부, 파일 경로, 내부 호스트 이름이 섞이기 쉽다. 기본값이 모두 "숨김"인 이유는 오류 응답이 외부로 나가는 출구이기 때문이다.

    기본 처리만으로 부족한 이유

    BasicErrorController는 HTML 오류 화면에는 충분하지만 API 계약으로는 세 군데가 모자라다. 첫째, 상태 코드가 예외의 의미를 모른다. 위 예제에서 0번 주문은 클라이언트 입력이 잘못된 경우다. 400이어야 하는데, 컨테이너는 예외 종류를 해석하지 않으므로 처리되지 않은 예외는 모두 500이 된다. 둘째, 본문 형식이 하나뿐이다. API마다, 또는 예외마다 다른 오류 코드나 추가 필드(재고 부족이면 남은 수량)를 넣을 방법이 없다. ErrorAttributes 빈을 바꾸면 형식은 바꿀 수 있지만 모든 오류가 한 형식을 공유한다. 셋째, 요청이 두 번 처리된다. 예외 한 번에 DispatcherServlet을 두 번 통과하고, 그사이 필터와 인터셉터가 다시 실행될 수 있다(07·08회에서 DispatcherType과 excludePathPatterns("/error")로 다룬 문제다).

    이 세 문제를 풀려면 예외가 DispatcherServlet을 빠져나가기 전에 잡아야 한다. 예외를 잡을 수 있는 위치, 그리고 잡은 다음 응답을 어떻게 확정하느냐가 이 회차의 나머지 전부다.

    DispatcherServlet이 예외를 붙잡는 자리

    예외 처리의 입구는 DispatcherServlet.doDispatch다. 스프링 프레임워크 6.2 소스의 뼈대를 예외 처리 관점에서 줄이면 다음과 같다.

    protected void doDispatch(HttpServletRequest request, HttpServletResponse response) throws Exception {
    HandlerExecutionChain mappedHandler = null;
    try {
        ModelAndView mv = null;
        Exception dispatchException = null;
        try {
            mappedHandler = getHandler(processedRequest);           // 1. 핸들러 찾기
            // ...
            if (!mappedHandler.applyPreHandle(processedRequest, response)) {
                return;                                              // 2. 인터셉터 preHandle
            }
            mv = ha.handle(processedRequest, response, mappedHandler.getHandler()); // 3. 컨트롤러 호출
            mappedHandler.applyPostHandle(processedRequest, response, mv);
        }
        catch (Exception ex) {
            dispatchException = ex;                                  // 여기까지의 예외를 기록만 한다
        }
        catch (Throwable err) {
            dispatchException = new ServletException("Handler dispatch failed: " + err, err);
        }
        processDispatchResult(processedRequest, response, mappedHandler, mv, dispatchException);
    }
    catch (Exception ex) {
        // 해결 못 한 예외: afterCompletion(ex)를 부른 뒤 ex를 다시 던진다
        triggerAfterCompletion(processedRequest, response, mappedHandler, ex);
    }
    // ...
}

    안쪽 try는 핸들러 조회, 인터셉터 preHandle, 핸들러 어댑터 호출, postHandle을 감싼다. 이 구간에서 나온 예외는 곧바로 던져지지 않고 dispatchException 변수에 담긴다. Error 계열(StackOverflowError 같은 것)도 ServletException으로 감싸 같은 길로 보낸다. 소스 주석에 따르면 4.3부터 핸들러 메서드가 던진 Error도 @ExceptionHandler로 처리할 수 있게 하려는 것이다. 그리고 정상 결과든 예외든 processDispatchResult라는 한 곳으로 모인다.

    private void processDispatchResult(HttpServletRequest request, HttpServletResponse response,
        HandlerExecutionChain mappedHandler, ModelAndView mv, Exception exception) throws Exception {
    boolean errorView = false;
    if (exception != null) {
        // ...
        Object handler = (mappedHandler != null ? mappedHandler.getHandler() : null);
        mv = processHandlerException(request, response, handler, exception); // 해결 못 하면 여기서 throw
        errorView = (mv != null);
    }
    if (mv != null && !mv.wasCleared()) {
        render(mv, request, response);                                      // 오류 뷰도 같은 render
        // ...
    }
    // ...
    if (mappedHandler != null) {
        mappedHandler.triggerAfterCompletion(request, response, null);      // 예외는 이미 처리됨
    }
}

    마지막 줄의 주석이 중요하다. 원본 소스에도 "Exception (if any) is already handled.."라는 주석이 붙어 있다. 리졸버가 예외를 해결하면 인터셉터의 afterCompletion에는 예외 인자로 null이 전달된다. 07회에서 afterCompletion의 네 번째 인자로 예외를 받을 수 있다고 했는데, 그 값이 채워지는 것은 어떤 리졸버도 해결하지 못해 바깥 catch로 빠졌을 때뿐이다. 인터셉터에서 "예외가 났으면 로그를 남긴다"는 코드를 ex != null로만 판단하면, @ExceptionHandler로 처리한 예외는 하나도 기록되지 않는다.

    예외를 실제로 처리하는 곳은 processHandlerException이다.

    protected ModelAndView processHandlerException(HttpServletRequest request, HttpServletResponse response,
        Object handler, Exception ex) throws Exception {
    request.removeAttribute(HandlerMapping.PRODUCIBLE_MEDIA_TYPES_ATTRIBUTE);
    try {
        response.setHeader(HttpHeaders.CONTENT_TYPE, null);
        response.setHeader(HttpHeaders.CONTENT_DISPOSITION, null);
        response.resetBuffer();
    }
    catch (IllegalStateException illegalStateException) {
        // 이미 커밋된 응답이면 그대로 둔다
    }
    ModelAndView exMv = null;
    if (this.handlerExceptionResolvers != null) {
        for (HandlerExceptionResolver resolver : this.handlerExceptionResolvers) {
            exMv = resolver.resolveException(request, response, handler, ex);
            if (exMv != null) {
                break;                                   // 처음으로 null이 아닌 값을 준 리졸버에서 멈춘다
            }
        }
    }
    if (exMv != null) {
        if (exMv.isEmpty()) {
            request.setAttribute(EXCEPTION_ATTRIBUTE, ex);
            return null;                                 // 빈 ModelAndView: 응답은 리졸버가 이미 끝냈다
        }
        // ... 뷰 이름이 없으면 기본 뷰 이름을 붙이고, 오류 요청 속성을 노출한다
        WebUtils.exposeErrorRequestAttributes(request, ex, getServletName());
        return exMv;                                     // 오류 뷰를 렌더링하게 한다
    }
    throw ex;                                            // 아무도 해결 못 함: 컨테이너로 전파
}

    세 가지를 읽어 낼 수 있다. 첫째, 리졸버 목록은 책임 연쇄(chain of responsibility)다. 앞에서부터 하나씩 묻고, 처음으로 null이 아닌 값을 돌려준 리졸버에서 멈춘다. 둘째, 리졸버를 부르기 전에 Content-Type 헤더와 응답 버퍼를 비운다(6.2 소스 기준). 컨트롤러가 정상 응답을 쓰다가 중간에 예외가 났더라도, 아직 커밋되지 않았다면 오류 응답을 깨끗한 상태에서 다시 쓸 수 있게 하려는 것이다. 핸들러 매핑이 기록해 둔 "생산 가능한 미디어 타입" 속성도 지운다. 정상 응답이 produces = "application/xml"로 묶여 있어도 오류 응답의 형식은 그 제약을 받지 않는다는 뜻이다. 셋째, 아무도 해결하지 못하면 원래 예외를 다시 던진다. 이 예외가 DispatcherServlet 밖, FrameworkServlet을 지나 톰캣까지 올라가는 것이 앞 절의 /error 경로다.

    스프링 부트 애플리케이션의 리졸버 목록

    DispatcherServlet은 초기화할 때 애플리케이션 컨텍스트에서 HandlerExceptionResolver 타입의 빈을 모두 찾아 AnnotationAwareOrderComparator로 정렬해 둔다(detectAllHandlerExceptionResolvers가 기본값 true일 때). 스프링 부트 3.x 웹 애플리케이션에서는 대체로 두 개의 빈이 잡힌다.

    handlerExceptionResolvers (정렬 후)
 ├─ [0] DefaultErrorAttributes             order = HIGHEST_PRECEDENCE  (부트)
 │       └ 예외를 요청 속성에 저장만 하고 null 반환
 └─ [1] HandlerExceptionResolverComposite  order = 0                   (스프링 MVC 설정)
         ├─ ExceptionHandlerExceptionResolver   @ExceptionHandler 메서드 호출
         ├─ ResponseStatusExceptionResolver     @ResponseStatus, ResponseStatusException
         └─ DefaultHandlerExceptionResolver     스프링 MVC 내부 예외 → 4xx/5xx

    첫 번째 DefaultErrorAttributes는 리졸버이면서 동시에 앞 절의 ErrorAttributes 구현이다. resolveException은 예외를 자기 전용 요청 속성에 저장하고 무조건 null을 돌려준다. 그래서 체인을 멈추지 않는다. 이 단계가 있기 때문에 나중에 /error로 재디스패치되었을 때 DefaultErrorAttributes가 원래 예외를 꺼내 exception, message 같은 값을 계산할 수 있다. 가장 높은 우선순위를 받은 이유도 같다. 다른 리졸버가 예외를 처리해 버리기 전에 먼저 기록해 두어야 한다.

    두 번째 HandlerExceptionResolverComposite는 리졸버 세 개를 묶은 리졸버다. WebMvcConfigurationSupport.handlerExceptionResolver()가 만드는데, 소스를 보면 configureHandlerExceptionResolvers로 받은 목록이 비어 있을 때만 addDefaultHandlerExceptionResolvers로 위 세 개를 순서대로 넣고, 그다음 extendHandlerExceptionResolvers를 호출해 목록을 확장할 기회를 준다. 이 순서가 뒤에서 직접 만든 리졸버를 등록할 때 중요해진다. 이제 이 체인에 직접 끼어드는 것부터 해 보자.

    HandlerExceptionResolver 시작: 계약 세 줄

    HandlerExceptionResolver는 메서드가 하나뿐인 인터페이스다.

    public interface HandlerExceptionResolver {
    @Nullable
    ModelAndView resolveException(HttpServletRequest request, HttpServletResponse response,
                                  @Nullable Object handler, Exception ex);
}

    인자로 요청과 응답, 예외를 일으킨 핸들러(애너테이션 컨트롤러라면 HandlerMethod), 예외 자체를 받는다. 핸들러를 찾기 전에 예외가 났다면(예: 멀티파트 파싱 실패) handler는 null이다. 스프링 프레임워크 레퍼런스는 이 인터페이스의 계약을 다음 세 줄로 정리한다.

    반환값뜻DispatcherServlet이 하는 일
    뷰를 가리키는 ModelAndView이 오류는 이 화면으로 보여 달라체인을 멈추고, 오류 요청 속성을 노출한 뒤 그 뷰를 render한다
    빈 ModelAndView (new ModelAndView())리졸버 안에서 이미 처리했다체인을 멈추고 아무것도 렌더링하지 않는다. 정상 흐름처럼 반환한다
    null내 담당이 아니다다음 리졸버에게 묻는다. 마지막까지 null이면 예외를 다시 던진다

    여기서 가장 오해하기 쉬운 것이 두 번째 줄이다. "빈 ModelAndView를 돌려주면 응답 본문이 비어 나간다"가 아니다. 정확히는 "DispatcherServlet은 더 할 일이 없다"는 뜻이다. 응답에 무엇이 실리는지는 리졸버가 그 전에 응답 객체에 무엇을 했느냐로 정해진다. 상태 코드만 바꾸고 끝낼 수도, 본문을 직접 쓸 수도, sendError로 컨테이너에 오류 페이지를 요청할 수도 있다. 이 차이를 예제로 확인하자.

    첫 번째 리졸버는 IllegalArgumentException을 400으로 바꾼다. 앞에서 500이 나왔던 0번 주문 요청을 고치려는 것이다.

    public class IllegalArgumentToBadRequestResolver implements HandlerExceptionResolver {

    @Override
    public ModelAndView resolveException(HttpServletRequest request, HttpServletResponse response,
                                         Object handler, Exception ex) {
        if (!(ex instanceof IllegalArgumentException)) {
            return null;                                   // 내 담당이 아니다: 다음 리졸버로
        }
        try {
            response.sendError(HttpServletResponse.SC_BAD_REQUEST, ex.getMessage());
            return new ModelAndView();                     // 처리 끝
        } catch (IOException e) {
            return null;                                   // 실패하면 원래 예외 처리를 계속하게 둔다
        }
    }
}

    이 리졸버가 등록된 상태에서 GET /api/orders/0이 들어오면 무슨 일이 일어나는지 순서대로 따라가 보자.

    4단계와 6단계 사이의 연결이 핵심이다. 서블릿 API의 sendError Javadoc은 이 메서드가 "지정한 상태 코드로 오류 응답을 보내고 출력 버퍼를 비우며", 해당 상태 코드에 대한 오류 페이지 선언이 있으면 그것을 우선해서 돌려준다고 설명한다. 또 호출 뒤에는 응답이 커밋된 것으로 보고 더 쓰지 말아야 한다고 적혀 있다. 톰캣 구현(11.0 소스 기준)을 보면 sendError는 응답에 "오류 상태"라는 표시를 남길 뿐 그 자리에서 오류 페이지를 그리지 않는다. 서블릿이 반환하고 필터 체인이 모두 풀린 뒤, StandardHostValve가 response.isError()를 확인하고 상태 코드에 맞는 오류 페이지(없으면 기본 오류 페이지)로 포워드한다. 그래서 sendError를 쓰는 리졸버는 상태 코드만 정하고 본문은 컨테이너의 오류 경로에 위임하는 방식이다.

    이 위임은 MockMvc로 테스트하면 눈에 보인다. MockMvc는 서블릿 컨테이너 없이 DispatcherServlet만 돌리므로 6단계 이후가 없다. 스프링 프레임워크 7.0.10의 MockMvc로 이 리졸버를 등록해 호출한 결과는 다음과 같다.

    /api/orders/0 -> 400 errorMessage=주문 번호는 0일 수 없습니다 contentType=null body=

    상태는 400이고 sendError에 넘긴 메시지는 응답 객체의 오류 메시지 필드에 기록되었지만, 본문은 비어 있다. 실제 톰캣에서는 이 빈자리를 /error가 채운다. 이때 본문에 메시지가 실리는지는 앞의 server.error.include-message 설정에 달려 있다. 톰캣은 sendError의 메시지를 jakarta.servlet.error.message 요청 속성에 넣고, DefaultErrorAttributes는 메시지를 고를 때 이 속성을 예외 자신의 메시지보다 먼저 본다. 기본값 never에서는 계산된 메시지가 결국 지워진다.

    HandlerExceptionResolver 활용: 응답을 그 자리에서 끝내기

    sendError 방식은 상태 코드 문제는 풀었지만 앞에서 든 나머지 두 문제(본문 형식이 하나뿐, 요청이 두 번 처리됨)는 그대로다. 리졸버가 응답 본문을 직접 쓰면 둘 다 사라진다. 두 번째 리졸버는 재고 부족 예외를 409와 약속된 JSON으로 바꾼다.

    public class StockShortageException extends RuntimeException {
    public StockShortageException(String message) {
        super(message);
    }
}

public record ApiError(String code, String message) {}

public class StockShortageJsonResolver implements HandlerExceptionResolver {

    private final ObjectMapper objectMapper;

    public StockShortageJsonResolver(ObjectMapper objectMapper) {
        this.objectMapper = objectMapper;
    }

    @Override
    public ModelAndView resolveException(HttpServletRequest request, HttpServletResponse response,
                                         Object handler, Exception ex) {
        if (!(ex instanceof StockShortageException e)) {
            return null;
        }
        try {
            response.setStatus(HttpServletResponse.SC_CONFLICT);
            response.setContentType(MediaType.APPLICATION_JSON_VALUE);
            response.setCharacterEncoding("UTF-8");
            String json = objectMapper.writeValueAsString(new ApiError("STOCK_SHORTAGE", e.getMessage()));
            response.getWriter().write(json);
            return new ModelAndView();
        } catch (IOException ioe) {
            return null;
        }
    }
}

    패턴 변수 e는 if 블록이 return으로 끝나므로 그 아래에서도 쓸 수 있다(자바 16부터의 instanceof 패턴 매칭 규칙). ObjectMapper.writeValueAsString이 던지는 JsonProcessingException은 IOException의 하위 타입이라 같은 catch에 걸린다. MockMvc로 확인한 결과는 다음과 같다(같은 환경, JSON 직렬화 부분만 문자열 조립으로 바꿔 실행).

    /api/orders/409 -> 409 errorMessage=null contentType=application/json;charset=UTF-8 body={"code":"STOCK_SHORTAGE","message":"재고 부족"}

    이번에는 sendError를 부르지 않았으므로 톰캣의 응답에는 오류 표시가 없다. 상태가 409여도 컨테이너 입장에서는 정상적으로 끝난 응답이다. StandardHostValve는 isError()가 거짓이면 오류 페이지를 찾지 않는다. /error 재디스패치가 일어나지 않으므로 필터와 인터셉터가 두 번 실행될 일도, BasicErrorController가 형식을 덮어쓸 일도 없다. 응답이 리졸버 안에서 완결된다.

    같은 예외를 sendError로 처리할 때는 요청이 /error로 한 번 더 DispatcherServlet을 지나고, 본문을 직접 쓸 때는 첫 디스패치에서 끝난다는 차이를 보여 준다. Two-row sequence diagram on white background.     리졸버 등록: configure와 extend의 차이

    직접 만든 리졸버는 WebMvcConfigurer로 등록한다. 여기에 비슷한 이름의 메서드가 두 개 있고, 잘못 고르면 스프링 MVC의 기본 예외 처리 전체가 꺼진다.

    @Configuration
public class WebConfig implements WebMvcConfigurer {

    private final ObjectMapper objectMapper;

    public WebConfig(ObjectMapper objectMapper) {
        this.objectMapper = objectMapper;
    }

    @Override
    public void extendHandlerExceptionResolvers(List resolvers) {
        resolvers.add(new IllegalArgumentToBadRequestResolver());
        resolvers.add(new StockShortageJsonResolver(objectMapper));
    }
}

    WebMvcConfigurer Javadoc의 설명을 소스와 함께 읽으면 차이가 분명하다. configureHandlerExceptionResolvers가 받는 목록은 처음에 비어 있고, 이 목록이 비어 있을 때만 프레임워크가 기본 리졸버 셋을 채운다. 여기에 하나라도 넣으면 "애플리케이션이 넘겨받아 완전히 초기화된 리졸버를 모두 직접 제공해야" 한다. 즉 @ExceptionHandler 처리, @ResponseStatus 처리, 스프링 MVC 내부 예외의 4xx 변환이 한꺼번에 사라진다. 반면 extendHandlerExceptionResolvers(4.3부터)는 기본 셋이 채워진 뒤의 목록을 받는다. 기본 동작을 유지하면서 끼워 넣을 때는 이쪽을 쓴다.

    목록 안의 위치도 신경 써야 한다. resolvers.add(...)는 목록 끝에 붙이므로 위 설정의 결과는 [ExceptionHandlerExceptionResolver, ResponseStatusExceptionResolver, DefaultHandlerExceptionResolver, 직접 만든 둘] 순서다. 직접 만든 리졸버는 기본 셋이 모두 null을 돌려준 예외만 받는다. 같은 예외를 @ExceptionHandler로도 처리하고 있다면 그쪽이 먼저 이긴다. 기본 셋보다 먼저 보려면 resolvers.add(0, ...)로 맨 앞에 넣어야 한다. 그 대신 그 리졸버가 너무 넓은 타입(예: Exception)을 잡으면 스프링 MVC 내부 예외까지 가로채 400이어야 할 응답을 엉뚱하게 바꾼다. 리졸버의 순서는 곧 "누가 먼저 판단할 권리를 갖는가"다.

    직접 작성 방식은 강력하지만 대가가 있다. 응답 형식(JSON인지, 문자 인코딩은 무엇인지), Accept 헤더 협상, 직렬화 실패 처리를 모두 손으로 해야 한다. 스프링이 컨트롤러 반환값에 대해 해 주던 일, 즉 메시지 컨버터 선택과 내용 협상을 리졸버 안에서 다시 구현하는 셈이다. 다음 절의 ExceptionHandlerExceptionResolver는 바로 이 부분을 프레임워크가 대신 해 주는 리졸버다.

    스프링이 제공하는 리졸버 1: ResponseStatusExceptionResolver

    기본 셋의 두 번째인 ResponseStatusExceptionResolver부터 보자. 이 리졸버는 두 종류의 예외를 상태 코드로 바꾼다. 클래스에 @ResponseStatus가 붙은 예외와, ResponseStatusException이다. 스프링 6.2 소스의 판단 순서는 다음과 같다.

    protected ModelAndView doResolveException(HttpServletRequest request, HttpServletResponse response,
                                          Object handler, Exception ex) {
    try {
        if (ex instanceof ResponseStatusException rse) {
            return resolveResponseStatusException(rse, request, response, handler);
        }
        ResponseStatus status = AnnotatedElementUtils.findMergedAnnotation(ex.getClass(), ResponseStatus.class);
        if (status != null) {
            return resolveResponseStatus(status, request, response, handler, ex);
        }
        if (ex.getCause() instanceof Exception cause) {
            return doResolveException(request, response, handler, cause);   // 원인으로 재귀
        }
    }
    catch (Exception resolveEx) {
        // 경고 로그
    }
    return null;
}

protected ModelAndView applyStatusAndReason(int statusCode, String reason, HttpServletResponse response)
        throws IOException {
    if (!StringUtils.hasLength(reason)) {
        response.sendError(statusCode);
    }
    else {
        String resolvedReason = (this.messageSource != null ?
                this.messageSource.getMessage(reason, null, reason, LocaleContextHolder.getLocale()) :
                reason);
        response.sendError(statusCode, resolvedReason);
    }
    return new ModelAndView();
}

    네 가지를 확인할 수 있다. 첫째, 애너테이션은 findMergedAnnotation으로 찾으므로 상위 클래스에 붙은 @ResponseStatus도 하위 예외에 적용된다. 둘째, 예외 자신에게 해당 사항이 없으면 원인(cause)으로 재귀한다. 다른 예외로 감싸진 @ResponseStatus 예외도 상태 코드가 살아남는다. 셋째, 결론은 결국 sendError다. 이 리졸버는 본문을 쓰지 않고 앞 절의 첫 번째 방식처럼 컨테이너의 /error에 위임한다. 넷째, reason은 메시지 코드로 먼저 해석된다. WebMvcConfigurationSupport가 이 리졸버를 만들 때 애플리케이션 컨텍스트를 MessageSource로 넣어 주므로, 03회에서 본 메시지 소스 기능이 그대로 쓰인다. 코드를 찾지 못하면 기본 메시지 인자로 넘긴 reason 문자열 자체가 쓰인다.

    @ResponseStatus(code = HttpStatus.NOT_FOUND, reason = "error.order.notfound")
public class OrderNotFoundException extends RuntimeException {
    public OrderNotFoundException(long id) {
        super("order " + id);
    }
}
    error.order.notfound=주문을 찾을 수 없습니다

    @ResponseStatus는 자기가 만든 예외 클래스에만 붙일 수 있다. 라이브러리의 예외나, 같은 예외인데 상황마다 다른 상태를 주고 싶을 때는 ResponseStatusException을 직접 던진다. 이 예외는 생성자로 상태 코드와 이유를 받고, 리졸버는 예외가 가진 헤더까지 응답에 복사한 뒤 같은 applyStatusAndReason을 탄다. 스프링 6.0부터 ResponseStatusException은 ErrorResponseException을 상속해 ErrorResponse 인터페이스도 구현한다(이 인터페이스는 뒤의 ProblemDetail 절에서 다시 나온다).

    @GetMapping("/{id}")
public OrderDto find(@PathVariable long id) {
    // ...
    if (id == 404) {
        throw new OrderNotFoundException(id);
    }
    if (id == 410) {
        throw new ResponseStatusException(HttpStatus.GONE, "삭제된 주문");
    }
    return new OrderDto(id, "책");
}

    이 컨트롤러를 예외 처리 설정 없이 MockMvc로 호출한 결과는 다음과 같다. MockMvc의 독립 실행(standalone) 설정에는 messages.properties를 읽는 메시지 소스가 없어서 reason이 코드 그대로 나왔다. 메시지 소스가 구성된 스프링 부트 애플리케이션이라면 "주문을 찾을 수 없습니다"로 해석된다.

    /api/orders/404 -> 404 errorMessage=error.order.notfound body=
/api/orders/410 -> 410 errorMessage=삭제된 주문 body=

    두 경우 모두 본문이 비어 있다는 점에 주목하자. 실제 서버에서는 /error가 기본 JSON을 채운다. 따라서 @ResponseStatus와 ResponseStatusException은 상태 코드를 정확히 하는 도구이지, API 오류 본문을 설계하는 도구가 아니다. 이유 문자열이 클라이언트에 보이는지도 server.error.include-message에 달려 있다.

    스프링이 제공하는 리졸버 2: DefaultHandlerExceptionResolver

    기본 셋의 마지막 DefaultHandlerExceptionResolver는 스프링 MVC 자신이 던지는 예외를 맡는다. 클라이언트가 /api/orders/abc처럼 숫자 자리에 문자를 보내면 long id로 변환하다가 MethodArgumentTypeMismatchException이 난다. 이것은 서버 버그가 아니라 클라이언트의 잘못이므로 400이어야 한다. 아무 설정이 없어도 이 요청이 500이 아니라 400이 되는 것은 이 리졸버 덕분이다.

    경고: Resolved [org.springframework.web.method.annotation.MethodArgumentTypeMismatchException: Method parameter 'id': Failed to convert value of type 'java.lang.String' to required type 'long'; For input string: "abc"]
/api/orders/abc -> 400 errorMessage=null body=

    첫 줄의 경고 로그도 이 리졸버가 남긴 것이다. 생성자에서 경고 로그 카테고리를 자기 클래스 이름으로 정해 두었기 때문에, 처리한 예외를 WARN 수준으로 "Resolved [...]"라고 기록한다. 소스의 handleTypeMismatch는 두 줄이다. response.sendError(SC_BAD_REQUEST)를 부르고 빈 ModelAndView를 돌려준다. 이 리졸버 역시 상태 코드만 정하고 본문은 컨테이너의 오류 경로에 맡긴다. 클래스 Javadoc에 실린 대응표 중 자주 만나는 것을 옮기면 다음과 같다.

    예외상태언제 나는가
    HttpRequestMethodNotSupportedException405매핑에 없는 HTTP 메서드로 요청
    HttpMediaTypeNotSupportedException415요청 본문의 Content-Type을 읽을 컨버터가 없음
    HttpMediaTypeNotAcceptableException406Accept가 원하는 형식으로 응답을 만들 수 없음
    MissingServletRequestParameterException400필수 요청 파라미터 누락
    TypeMismatchException400파라미터·경로 변수 타입 변환 실패
    HttpMessageNotReadableException400요청 본문 JSON 파싱 실패
    MethodArgumentNotValidException400@Valid 검증 실패(05회)

    HttpMessageNotWritableException500응답 객체를 직렬화하지 못함

    스프링 6에서 이 리졸버의 구조가 바뀌었다. 6.2 소스의 doResolveException은 먼저 ex instanceof ErrorResponse인지 본다. 스프링 레퍼런스에 따르면 스프링 MVC의 예외들은 모두 ErrorResponse를 구현하고, 이 인터페이스는 상태 코드·헤더·본문(ProblemDetail)을 스스로 노출한다. 예외별 처리 메서드(handleHttpRequestMethodNotSupported 등, 기본 구현은 null을 돌려준다)가 따로 응답을 만들지 않으면 handleErrorResponse가 예외가 알려 주는 상태와 헤더(예: 405의 Allow)로 sendError를 호출한다. 예외가 자기 HTTP 표현을 알고, 리졸버는 그것을 응답에 옮기는 구조다. TypeMismatchException처럼 웹 계층 밖(빈 프로퍼티 변환)에서 온 낮은 수준의 예외는 그 아래의 별도 분기에서 처리된다.

    여기서 하나의 함정을 짚어 두자. 응답이 이미 커밋되었다면 sendError는 IllegalStateException을 던진다. 그래서 이 리졸버의 여러 메서드는 response.isCommitted()를 먼저 확인하고, 커밋된 경우 경고 로그만 남긴다. 큰 응답을 스트리밍하다가 중간에 예외가 나면 클라이언트는 이미 200 상태 줄과 일부 본문을 받았다. 이 시점 이후로는 어떤 리졸버도 상태 코드를 바꿀 수 없다. HTTP 응답의 상태 줄은 본문보다 먼저 나가기 때문이다. 예외 처리의 모든 장치는 "응답이 아직 커밋되지 않았다"는 전제 위에서만 동작한다.

    @ExceptionHandler: 예외 처리용 컨트롤러 메서드

    기본 셋의 첫 번째, 그리고 실무에서 가장 많이 쓰는 것이 ExceptionHandlerExceptionResolver다. 이 리졸버는 @ExceptionHandler가 붙은 메서드를 찾아 컨트롤러 메서드처럼 호출한다. "컨트롤러 메서드처럼"이 핵심이다. 스프링 MVC 1편에서 본 RequestMappingHandlerAdapter의 구조, 즉 인자 리졸버(HandlerMethodArgumentResolver)가 파라미터를 채우고 반환값 처리기(HandlerMethodReturnValueHandler)가 반환값을 응답으로 바꾸는 구조가 예외 처리 메서드에도 그대로 적용된다. WebMvcConfigurationSupport는 이 리졸버를 만들 때 컨트롤러 쪽과 같은 메시지 컨버터, 사용자 정의 인자 리졸버, 반환값 처리기, 그리고 내용 협상 관리자를 넣어 준다. 그래서 @ResponseBody 객체를 돌려주면 Accept 헤더에 맞춰 JSON으로 직렬화된다. 앞 절에서 손으로 하던 일이 사라진다.

    @RestController
@RequestMapping("/api/orders")
public class OrderApiController {

    @GetMapping("/{id}")
    public OrderDto find(@PathVariable long id) {
        // ... (앞의 예제와 같음)
    }

    @ExceptionHandler
    public ApiError badArgument(IllegalArgumentException e) {
        return new ApiError("BAD_ARGUMENT", e.getMessage());
    }
}

    @ExceptionHandler의 값을 비워 두면 메서드 파라미터 중 Throwable 하위 타입이 처리 대상이 된다. 위 메서드는 IllegalArgumentException과 그 하위 예외를 맡는다. 값과 파라미터 어디에서도 예외 타입을 찾지 못하면 "No exception types mapped to"로 시작하는 IllegalStateException이 난다. 이제 GET /api/orders/0을 보내 보자. 기대하는 것은 400과 ApiError JSON이다.

    /api/orders/0 -> 200 errorMessage=null body={"code":"BAD_ARGUMENT","message":"주문 번호는 0일 수 없습니다"}

    본문은 기대대로인데 상태가 200이다. 이유는 processHandlerException을 다시 보면 나온다. DispatcherServlet은 리졸버를 부르기 전에 헤더와 버퍼를 비울 뿐 상태 코드를 바꾸지 않는다. 서블릿 응답의 상태는 기본값 200 그대로이고, 예외 처리 메서드는 상태에 대해 아무 말도 하지 않았다. 반환값 처리기는 받은 객체를 현재 상태로 써 내려갈 뿐이다. 이 예외 처리 메서드는 "예외를 정상 응답으로 바꾼" 셈이 되었다. 클라이언트는 성공으로 판단하고 ApiError를 OrderDto로 파싱하려다 실패한다.

    상태를 정하는 방법은 둘이다. 메서드에 @ResponseStatus를 붙이거나, ResponseEntity를 돌려준다.

    @ResponseStatus(HttpStatus.BAD_REQUEST)
@ExceptionHandler
public ApiError badArgument(IllegalArgumentException e) {
    return new ApiError("BAD_ARGUMENT", e.getMessage());
}

@ExceptionHandler
public ResponseEntity stock(StockShortageException e) {
    return ResponseEntity.status(HttpStatus.CONFLICT)
            .body(new ApiError("STOCK_SHORTAGE", e.getMessage()));
}
    /api/orders/0 -> 400 errorMessage=null body={"code":"BAD_ARGUMENT","message":"주문 번호는 0일 수 없습니다"}
/api/orders/409 -> 409 errorMessage=null body={"code":"STOCK_SHORTAGE","message":"재고 부족"}

    메서드에 붙은 @ResponseStatus는 예외 클래스에 붙은 것과 동작이 다르다. ServletInvocableHandlerMethod.setResponseStatus를 보면, reason이 없을 때는 response.setStatus만 호출하고, reason이 있을 때는 response.sendError(status, reason)를 호출한 뒤 요청을 처리 완료로 표시해 반환값을 쓰지 않는다. 즉 @ExceptionHandler 메서드에 reason까지 적으면 본문을 직접 만들겠다는 의도와 달리 다시 /error 위임으로 돌아간다. API 예외 처리 메서드에는 reason 없이 상태 코드만 적는다.

    두 경우 모두 sendError가 없으므로 응답은 첫 디스패치에서 끝난다. doResolveHandlerMethodException의 마지막 부분을 보면, 반환값 처리기가 응답을 직접 썼을 때(mavContainer.isRequestHandled()가 참) 리졸버는 빈 ModelAndView를 돌려준다. 앞 절에서 손으로 만든 "직접 작성" 리졸버와 결과가 같다. 반대로 메서드가 뷰 이름 문자열이나 ModelAndView를 돌려주면 뷰가 있는 ModelAndView가 만들어져 DispatcherServlet이 렌더링한다. 같은 장치로 HTML 오류 화면도 만들 수 있는 이유다.

    여러 메서드가 맞을 때: 예외 깊이와 원인 체인

    한 클래스에 @ExceptionHandler가 여러 개 있으면 어느 것이 선택되는가. 이 일은 클래스마다 하나씩 만들어지는 ExceptionHandlerMethodResolver가 한다. 6.2 소스의 규칙은 다음과 같다.

    1. 던져진 예외의 클래스에 대해, 선언된 예외 타입이 그 클래스에 대입 가능한(상위 타입이거나 같은) 매핑을 모두 모은다.
    2. 여러 개면 ExceptionDepthComparator로 정렬한다. 던져진 예외에서 상속 계층을 몇 단계 올라가야 선언된 타입에 닿는지가 깊이이고, 가장 가까운 것이 이긴다. IllegalArgumentException을 던졌을 때 IllegalArgumentException 처리 메서드(깊이 0)는 RuntimeException 처리 메서드(깊이 1)와 Exception 처리 메서드(깊이 2)를 이긴다. 6.2부터는 같은 깊이일 때 produces로 선언한 미디어 타입이 동점을 가른다.
    3. 아무것도 맞지 않으면 getCause()로 원인 예외를 꺼내 1부터 다시 한다. 레퍼런스에 따르면 5.3부터는 원인의 원인까지 임의의 깊이로 내려간다.
    4. 조회 결과는 예외 타입과 미디어 타입 쌍을 키로 캐시된다. 같은 예외가 반복될 때 매번 계층을 훑지 않는다.

    같은 클래스 안에서 같은 예외 타입을 두 메서드가 선언하면 "Ambiguous @ExceptionHandler method mapped for"로 시작하는 IllegalStateException이 난다. 이 검사는 ExceptionHandlerMethodResolver를 만들 때 일어난다. @ControllerAdvice의 리졸버는 애플리케이션 시작 시점(리졸버의 afterPropertiesSet)에 만들어지므로 기동이 실패하지만, 컨트롤러 자신의 리졸버는 그 컨트롤러에서 처음 예외가 났을 때 computeIfAbsent로 만들어진다. 같은 실수가 어디에 있느냐에 따라 기동 실패가 되기도, 운영 중 첫 예외에서야 드러나는 오류가 되기도 한다.

    원인 체인 매칭은 편리하지만 의외의 결과를 낳는다. 앞의 badArgument(상태 지정 없는 첫 버전)가 있는 상태에서 /api/orders/abc를 보내 보았다.

    /api/orders/abc -> 200 errorMessage=null body={"code":"BAD_ARGUMENT","message":"For input string: \"abc\""}

    원래라면 DefaultHandlerExceptionResolver가 400으로 처리했을 타입 변환 실패가 IllegalArgumentException 처리 메서드로 들어왔다. 던져진 MethodArgumentTypeMismatchException은 IllegalArgumentException의 하위 타입이 아니지만, 그 원인이 NumberFormatException이고 이것이 IllegalArgumentException의 하위 타입이다. 3단계의 원인 매칭에 걸린 것이다. 그리고 ExceptionHandlerExceptionResolver는 체인에서 DefaultHandlerExceptionResolver보다 앞에 있으므로 먼저 이긴다. 메시지에 원인 예외의 메시지가 찍힌 것도 이유가 있다. 리졸버는 메서드를 호출할 때 던져진 예외와 그 원인들을 모두 "제공된 인자" 후보로 넘기고, 인자 해석은 파라미터 타입에 대입 가능한 첫 후보를 고른다. 파라미터가 IllegalArgumentException이므로 감싼 예외가 아니라 원인인 NumberFormatException이 들어왔다. 파라미터를 Exception으로 선언했다면 감싼 예외가 들어온다.

    교훈은 넓은 표준 예외를 처리 대상으로 삼지 말라는 것이다. IllegalArgumentException, IllegalStateException, RuntimeException은 JDK와 라이브러리 곳곳에서 원인으로 쓰인다. 애플리케이션이 의미를 정할 수 있는 예외는 애플리케이션이 직접 정의한 예외뿐이다. 도메인 예외 계층(예: BusinessException을 루트로 하는 계층)을 만들고 그것을 처리 대상으로 삼으면 이런 충돌이 없다.

    마지막으로 예외 처리 메서드 자신이 예외를 던지면 어떻게 되는가. 6.2 소스의 doResolveHandlerMethodException은 호출 중 생긴 예외를 잡아, 원래 예외(또는 그 원인)와 다른 예외라면 "Failure in @ExceptionHandler"로 경고 로그를 남기고 null을 돌려준다. 원래 예외는 체인의 다음 리졸버로 넘어간다. 레퍼런스는 이 성질을 의도적으로 쓰는 방법도 소개한다. 예외 처리 메서드가 받은 예외를 그대로 다시 던지면 "이 메서드가 처음부터 맞지 않았던 것처럼" 나머지 체인이 처리를 이어 간다.

    @ControllerAdvice: 예외 처리를 컨트롤러 밖으로

    컨트롤러 안의 @ExceptionHandler는 그 컨트롤러에서 난 예외만 처리한다. API가 수십 개면 같은 처리 메서드가 수십 번 복사된다. @ControllerAdvice는 @ExceptionHandler, @InitBinder, @ModelAttribute 메서드를 여러 컨트롤러가 공유하도록 모으는 @Component의 특수화다. @RestControllerAdvice는 @ControllerAdvice에 @ResponseBody를 합친 애너테이션(4.3부터)으로, 모든 예외 처리 메서드의 반환값이 응답 본문이 된다.

    @RestControllerAdvice(basePackages = "com.example.shop.api")
public class ApiExceptionAdvice {

    @ResponseStatus(HttpStatus.BAD_REQUEST)
    @ExceptionHandler
    public ApiError badArgument(IllegalArgumentException e) {
        return new ApiError("BAD_ARGUMENT", e.getMessage());
    }

    @ExceptionHandler
    public ResponseEntity stock(StockShortageException e) {
        return ResponseEntity.status(HttpStatus.CONFLICT)
                .body(new ApiError("STOCK_SHORTAGE", e.getMessage()));
    }

    @ResponseStatus(HttpStatus.INTERNAL_SERVER_ERROR)
    @ExceptionHandler
    public ApiError unexpected(Exception e) {
        // 원인 추적을 위해 서버 로그에는 예외 전체를 남긴다 (...)
        return new ApiError("INTERNAL_ERROR", "일시적인 오류가 발생했습니다");
    }
}

    마지막 메서드처럼 Exception을 잡는 최후 처리기를 두면 어떤 예외든 약속된 형식으로 나간다. 다만 두 가지를 의식해야 한다. 첫째, 클라이언트에게는 예외 메시지를 그대로 보내지 않는다. 앞에서 본 정보 노출 문제가 여기서 다시 생긴다. 둘째, Exception 처리기는 ExceptionHandlerExceptionResolver가 체인의 앞에 있기 때문에 스프링 MVC 내부 예외까지 가로챈다. 타입 변환 실패, 필수 파라미터 누락, 지원하지 않는 메서드가 모두 500이 된다. 이 문제의 해법은 뒤의 ResponseEntityExceptionHandler에서 다룬다.

    처리 메서드를 찾는 순서

    ExceptionHandlerExceptionResolver.getExceptionHandlerMethod가 처리 메서드를 찾는 순서는 다음과 같다.

    getExceptionHandlerMethod(handlerMethod, exception)
 1. 예외를 던진 컨트롤러 클래스 자신
      └ ExceptionHandlerMethodResolver(컨트롤러 클래스)에서 매칭 시도
        → 하나라도 맞으면 즉시 반환 (깊이·원인 규칙은 이 클래스 안에서만)
 2. @ControllerAdvice 빈들, 우선순위 순서대로
      for advice in exceptionHandlerAdviceCache:
        if advice.isApplicableToBeanType(컨트롤러 타입):   ← basePackages 등 선택자 검사
          ExceptionHandlerMethodResolver(advice)에서 매칭 시도
          → 맞으면 즉시 반환
 3. 아무도 없으면 null → 다음 리졸버(ResponseStatus, Default)

    "즉시 반환"이 이 표의 핵심이다. 예외 깊이를 비교하는 것은 한 클래스 안에서만이다. 컨트롤러에 @ExceptionHandler(Exception.class)가 하나라도 있으면, 어드바이스에 아무리 정확한 IllegalArgumentException 처리 메서드가 있어도 컨트롤러 쪽이 이긴다. 실험으로 확인해 보자. 아래 컨트롤러는 자기 안에 Exception 처리 메서드를 갖고 있고, 어드바이스에는 IllegalArgumentException 처리 메서드가 있다.

    @RestController
public class LegacyController {

    @GetMapping("/legacy")
    public String legacy() {
        throw new IllegalArgumentException("legacy");
    }

    @ExceptionHandler(Exception.class)
    public ApiError onAny(Exception e) {
        return new ApiError("LOCAL", e.getClass().getSimpleName());
    }
}
    /legacy -> 200 errorMessage=null body={"code":"LOCAL","message":"IllegalArgumentException"}

    어드바이스 사이에서도 같은 규칙이 적용된다. @ControllerAdvice 빈들은 ControllerAdviceBean.findAnnotatedBeans가 Ordered 구현이나 @Order·@Priority 선언으로 정렬하고, 리졸버는 그 순서대로 묻다가 처음 맞는 어드바이스에서 멈춘다. @ControllerAdvice Javadoc은 이를 분명히 적는다. 한 어드바이스 안에서는 원인 매칭보다 루트 예외 매칭이 우선하지만, 우선순위가 높은 어드바이스의 원인 매칭이 낮은 어드바이스의 어떤 매칭보다도 우선한다. 그래서 문서는 주요 루트 예외 매핑을 적절한 순서를 가진 우선 어드바이스에 선언하라고 권한다. @Order를 하나도 주지 않으면 모든 어드바이스가 같은 최저 우선순위가 되어, 실제 순서는 정렬 전 빈 조회 순서에 좌우된다. 이것은 코드로 약속된 계약이 아니다. 어드바이스가 둘 이상이면 순서를 명시한다.

    선택자(selector)는 어드바이스가 적용될 컨트롤러를 좁힌다. basePackages(별칭 value), 타입 안전한 basePackageClasses, 특정 타입에 대입 가능한 컨트롤러를 고르는 assignableTypes, 특정 애너테이션이 붙은 컨트롤러를 고르는 annotations가 있다. 여러 선택자를 함께 쓰면 OR로 결합된다. 아무것도 지정하지 않으면 모든 컨트롤러에 적용된다. Javadoc은 선택자 검사가 런타임에 이루어지므로 많이 쓰면 성능과 복잡도에 영향을 줄 수 있다고 경고한다. 위 표의 isApplicableToBeanType이 그 검사다. 웹 화면용 컨트롤러와 API 컨트롤러가 한 애플리케이션에 섞여 있다면, API용 어드바이스를 API 패키지로 한정해 HTML 컨트롤러의 예외가 JSON으로 바뀌지 않게 하는 것이 전형적인 사용법이다.

    ProblemDetail과 ErrorResponse: 스프링 6의 표준 오류 본문

    지금까지 만든 ApiError는 각자 정한 형식이다. 팀마다 code, errorCode, message, detail처럼 이름이 제각각이다. HTTP API의 오류 본문 형식을 표준으로 정한 것이 RFC 9457 "Problem Details for HTTP APIs"다. 스프링 프레임워크는 6.0부터 이 형식을 지원한다(6.0·6.1의 ProblemDetail Javadoc은 이전 판인 RFC 7807을 가리킨다. RFC 9457은 2023년 7월에 RFC 7807을 대체했다). 레퍼런스가 소개하는 구성 요소는 넷이다.

    • ProblemDetail: RFC 9457 문제 상세의 표현. 표준 필드(type, title, status, detail, instance)와 비표준 필드를 담는 단순한 컨테이너다.
    • ErrorResponse: 상태 코드, 응답 헤더, RFC 9457 형식의 본문을 노출하는 계약. 스프링 MVC의 예외들이 모두 이것을 구현한다.
    • ErrorResponseException: 다른 예외가 상속해 쓰기 좋은 ErrorResponse 기본 구현. ResponseStatusException이 이것을 상속한다.
    • ResponseEntityExceptionHandler: 스프링 MVC 예외 전부와 모든 ErrorResponseException을 처리해 본문 있는 오류 응답을 만드는 @ControllerAdvice용 기반 클래스.

    @ExceptionHandler 메서드는 ProblemDetail이나 ErrorResponse를 그대로 돌려줄 수 있다. 상태 코드는 ProblemDetail의 status가 정하므로 앞의 200 함정도 없다.

    @RestControllerAdvice
public class ProblemAdvice {

    @ExceptionHandler
    public ProblemDetail stock(StockShortageException e) {
        return ProblemDetail.forStatusAndDetail(HttpStatus.CONFLICT, e.getMessage());
    }
}
    /pd status=409 contentType=application/problem+json body={"detail":"stock empty","instance":"/pd","status":409,"title":"Conflict"}
    /pd status=409 contentType=application/problem+json body={"type":"about:blank","title":"Conflict","status":409,"detail":"stock empty","instance":"/pd"}

    두 가지가 자동으로 일어났다. 레퍼런스에 따르면 ProblemDetail의 instance는 비어 있으면 현재 URL 경로로 채워지고, 잭슨 JSON 코덱은 ProblemDetail에 대해 application/problem+json을 생산 가능한 미디어 타입으로 쓴다. 클라이언트는 Content-Type만 보고도 이 본문이 표준 문제 상세임을 안다. 두 출력을 비교하면 상태, Content-Type, instance는 같지만, 기준 버전인 6.2.19에서는 본문에 "type":"about:blank"가 더 실리고 필드 순서도 다르다. 6.2의 레퍼런스로 확인되는 것은 이 두 동작(instance 채움, application/problem+json)과 status가 HTTP 상태를 정한다는 점이다. 표준 필드 외의 값(예: 남은 재고 수량)은 setProperty로 properties 맵에 넣으면 잭슨이 최상위 JSON 속성으로 펼쳐 준다.

    이제 앞 절에서 남긴 문제, 즉 Exception 최후 처리기가 스프링 MVC 내부 예외까지 500으로 만드는 문제를 풀 수 있다. 어드바이스가 ResponseEntityExceptionHandler를 상속하면, 이 기반 클래스가 스프링 MVC 예외들을 위한 @ExceptionHandler 메서드를 이미 갖고 있다. 기반 클래스가 선언한 TypeMismatchException, HttpRequestMethodNotSupportedException 같은 구체 타입이 같은 어드바이스 안에서 Exception보다 던져진 예외에 가까우므로 먼저 선택되어, 각 예외가 노출하는 상태 코드(400, 405, 415…)와 ProblemDetail 본문으로 응답한다. 이 기반 클래스는 ErrorResponse가 노출하는 type·title·detail의 메시지 코드(problemDetail.title. + 예외의 정규 클래스 이름 같은 형식)를 MessageSource로 해석하므로, 03회의 국제화 방식 그대로 문구를 바꿀 수 있다.

    스프링 부트는 이 구성을 프로퍼티 하나로 켜 준다. 부트 3.5에서 spring.mvc.problemdetails.enabled의 기본값은 false이고, true로 두면 WebMvcAutoConfiguration이 ResponseEntityExceptionHandler를 상속한 ProblemDetailsExceptionHandler를 @Order(0)의 어드바이스로 등록한다. 이 빈은 @ConditionalOnMissingBean(ResponseEntityExceptionHandler.class) 조건이 붙어 있어서, 애플리케이션이 직접 ResponseEntityExceptionHandler 하위 어드바이스를 만들면 물러난다.

    ProblemDetail은 새 리졸버가 아니다. 지금까지 본 체인은 그대로이고, @ExceptionHandler의 반환값 종류가 하나 늘었을 뿐이다. 반대로 ErrorResponse 예외가 @ExceptionHandler에서 처리되지 않고 DefaultHandlerExceptionResolver까지 가면, 그 리졸버는 6.2 소스 기준으로 상태와 detail을 sendError에 넘길 뿐이므로 본문은 여전히 /error의 기본 JSON이 된다. 문제 상세 본문을 원한다면 ResponseEntityExceptionHandler 계열 어드바이스가 있어야 한다.

    필터에서 난 예외는 어떤 어드바이스로도 잡을 수 없다는 점이 실무에서 자주 문제가 된다. 인증 필터에서 토큰 검증 예외를 던지고 @RestControllerAdvice로 401 JSON을 만들려는 시도는 동작하지 않는다. 예외는 컨테이너의 오류 경로로 가서 BasicErrorController의 500 JSON이 된다. 필터에서는 필터가 직접 응답(상태와 본문)을 쓰고 체인을 진행하지 않는 방식으로 처리해야 한다. 스프링 시큐리티도 인증 실패 응답을 DispatcherServlet이 아니라 자신의 필터 체인 안에서 만든다.

    또 하나, 컨트롤러가 handler를 찾지 못한 경우도 있다. 6.1부터는 컨트롤러에 매핑되지 않은 경로가 정적 리소스 처리기(ResourceHttpRequestHandler)로 넘어가 리소스를 찾지 못하면 NoResourceFoundException이 던져지고, 이것이 DefaultHandlerExceptionResolver에서 404로 바뀐다. 그런데 6.2 소스의 ExceptionHandlerExceptionResolver.shouldApplyTo는 핸들러가 ResourceHttpRequestHandler이고 전역 예외 처리기가 있으면 이 리졸버를 적용한다. 선택자가 없는 전역 어드바이스는 컨트롤러 타입이 없어도 적용 대상이 되므로, 그 어드바이스의 Exception 최후 처리기가 이 404를 먼저 잡아 500으로 바꾼다. 최후 처리기를 둘 때 ResponseEntityExceptionHandler를 함께 쓰라는 앞 절의 권고가 여기서도 같은 문제를 막는다.

    이 장의 핵심

    API 예외 처리는 DispatcherServlet의 processHandlerException에서 HandlerExceptionResolver들이 순서대로 "내 담당인가"를 판단하는 책임 연쇄다. sendError를 부르는 리졸버는 상태 코드만 정하고 본문은 컨테이너의 /error에 맡기며, 응답을 직접 쓰는 리졸버와 @ExceptionHandler는 첫 디스패치에서 응답을 완결한다. @ExceptionHandler는 컨트롤러 자신 → 우선순위 순 어드바이스에서 처음 맞는 곳이 이기고, 깊이 비교와 원인 체인 매칭은 그 클래스 안에서만 일어난다. 상태 코드를 명시하지 않으면 200이 나간다.

    다음 10회에서는 이 회차에서 400의 원인으로 여러 번 등장한 타입 변환, 즉 문자열 "abc"를 long으로 바꾸려다 실패하는 그 과정을 맡는 ConversionService와 Formatter를 다룬다. 바인딩과 변환 단계에서 난 예외가 어떤 타입으로 감싸져 이 회차의 리졸버 체인에 도착하는지가 그 연결 고리다.
    BasicErrorController
    스프링 부트가 /error에 매핑한 오류 컨트롤러. Accept가 text/html이면 errorHtml, 아니면 error가 선택되어 ErrorAttributes가 만든 맵을 JSON으로 돌려준다.
    DefaultErrorAttributes
    최우선 리졸버로 예외를 요청 속성에 기록하고 null을 돌려주며, 오류 본문의 키를 만든 뒤 server.error.include-* 설정에 없는 키를 지운다.
    HandlerExceptionResolver 계약
    뷰가 있는 ModelAndView는 오류 뷰 렌더링, 빈 ModelAndView는 처리 완료, null은 다음 리졸버로. 모두 null이면 예외가 컨테이너로 전파된다.
    sendError 위임
    ResponseStatusExceptionResolver와 DefaultHandlerExceptionResolver는 sendError로 상태만 정하고, 본문은 톰캣의 ERROR 디스패치로 /error가 만든다.
    configure vs extend
    configureHandlerExceptionResolvers에 하나라도 넣으면 기본 리졸버 셋이 꺼진다. 기본을 유지하며 추가하려면 extendHandlerExceptionResolvers를 쓰고, 목록 내 위치로 우선순위를 정한다.
    @ExceptionHandler
    예외 처리용 컨트롤러 메서드. 인자 리졸버와 반환값 처리기, 메시지 컨버터를 그대로 쓰며, 상태를 지정하지 않으면 200으로 응답한다.
    예외 매칭 규칙
    한 클래스 안에서 ExceptionDepthComparator로 가장 가까운 타입이 이기고, 맞는 것이 없으면 원인 체인을 따라 내려간다. 컨트롤러 자신이 어드바이스보다, 우선순위 높은 어드바이스가 낮은 어드바이스보다 먼저다.
    @ControllerAdvice
    여러 컨트롤러가 공유하는 @ExceptionHandler 등을 모은 컴포넌트. 선택자로 적용 범위를 좁히고 @Order로 순서를 정한다. @RestControllerAdvice는 @ResponseBody를 더한 것이다.
    ProblemDetail
    RFC 9457 오류 본문의 스프링 6 표현. @ExceptionHandler에서 돌려주면 status로 상태가 정해지고 application/problem+json으로 직렬화된다.

    운영 중인 API에서 "클라이언트 오류인데 500이 찍혀 알람이 울린다"는 문제는 대개 이 회차의 체인 중 어느 단계가 빠졌는지로 설명된다. 처리되지 않은 도메인 예외가 컨테이너까지 올라가 500이 되었거나, 어드바이스의 Exception 최후 처리기가 스프링 MVC 내부 예외를 가로채 500으로 바꿨거나, 필터에서 난 예외라 어드바이스가 애초에 볼 수 없었던 경우다. 로그에서 "Resolved [...]" 경고(DefaultHandlerExceptionResolver)가 보이는지, "Failure in @ExceptionHandler"가 보이는지, 스택 트레이스가 FrameworkServlet 밖까지 올라갔는지를 보면 어느 단계에서 결정되었는지 좁힐 수 있다.

    반대 방향의 사고도 흔하다. 오류인데 200이 나가는 경우다. 상태를 지정하지 않은 @ExceptionHandler, 혹은 원인 체인 매칭으로 엉뚱한 처리 메서드가 선택된 경우가 그렇다. 200 오류는 모니터링의 오류율에 잡히지 않으므로 500보다 늦게 발견된다. 예외 처리 메서드는 반드시 @ResponseStatus, ResponseEntity, ProblemDetail 중 하나로 상태를 명시하고, MockMvc 테스트에서 본문뿐 아니라 상태 코드까지 검증하는 습관이 이 사고를 막는다.

    설계 판단은 조건에 따라 달라진다. 화면과 API가 섞인 애플리케이션이라면 API용 어드바이스를 패키지나 애너테이션 선택자로 한정해야 HTML 화면의 오류 페이지(08회)가 망가지지 않는다. 외부에 공개하는 API이거나 여러 팀이 클라이언트를 만든다면 자체 형식보다 RFC 9457 ProblemDetail을 기본으로 삼고, 필요한 필드만 properties로 확장하는 편이 계약을 설명하기 쉽다. 반대로 이미 클라이언트가 의존하는 자체 형식이 있다면 형식을 바꾸는 것 자체가 호환성 깨짐이므로, ResponseEntityExceptionHandler의 처리 메서드를 재정의해 기존 형식으로 응답하게 맞춘다.
  • 어드바이스 없이 extendHandlerExceptionResolvers로 IllegalArgumentToBadRequestResolver만 등록한 스프링 부트 애플리케이션에 GET /api/orders/0(Accept: application/json)을 보낸다. 톰캣 기준으로 DispatcherServlet이 몇 번 호출되는지, 각 호출의 디스패처 타입과 최종 응답의 상태 코드, 본문 키 목록(기본 설정)을 적어라.

    1번. 두 번이다. 첫 호출은 REQUEST 디스패치로 컨트롤러가 IllegalArgumentException을 던지고, DefaultErrorAttributes가 기록한 뒤 기본 리졸버 세 개가 모두 null을 돌려주고, 직접 만든 리졸버가 sendError(400, 메시지)를 부르고 빈 ModelAndView를 돌려준다. DispatcherServlet은 정상 반환하고, 톰캣의 StandardHostValve가 오류 표시를 보고 /error로 ERROR 디스패치한다. 두 번째 호출에서 BasicErrorController.error가 선택되어 상태 400의 JSON을 만든다. 본문 키는 timestamp, status, error, path다. 메시지는 계산되지만 include-message=never 때문에 지워진다.

    2번. (가)는 목록이 비어 있지 않으므로 addDefaultHandlerExceptionResolvers가 호출되지 않아 ExceptionHandlerExceptionResolver, ResponseStatusExceptionResolver, DefaultHandlerExceptionResolver가 모두 빠진다. 합성 리졸버에는 재고 리졸버 하나만 있다. (나)는 기본 셋 뒤에 덧붙는다. (가)에서 /api/orders/abc는 MethodArgumentTypeMismatchException을 처리할 리졸버가 없으므로(재고 리졸버는 null) 예외가 컨테이너로 올라가 500이 된다. 기본 설정이었다면 400이었을 요청이다. @ExceptionHandler와 @ResponseStatus도 함께 무력화된다.

    3번. (1) 컨트롤러 A 자신의 처리기가 먼저 검사되고, RuntimeException은 MyBusinessException에 대입 가능하므로 즉시 A의 메서드가 선택된다. 어드바이스 Y에 더 정확한 처리기가 있어도 비교되지 않는다. (2) B에는 로컬 처리기가 없으므로 어드바이스를 순서대로 본다. 우선순위가 높은 X의 IllegalStateException 처리기가 맞으므로(깊이 1) X에서 멈춘다. Y의 깊이 0 처리기는 검사조차 되지 않는다. 깊이 비교는 한 클래스 안에서만 일어나기 때문이다. Y를 쓰고 싶다면 Y의 우선순위를 X보다 높이거나, 도메인 예외 처리기를 X에 두어야 한다.

    4번. processDispatchResult는 리졸버가 예외를 해결하면 마지막에 triggerAfterCompletion(request, response, null)을 호출한다. 원본 소스의 주석대로 예외는 이미 처리된 것으로 본다. ex가 채워지는 것은 아무 리졸버도 해결하지 못해 doDispatch의 바깥 catch로 빠졌을 때뿐이다. 방법으로는, processHandlerException이 빈 ModelAndView를 받았을 때 요청 속성 DispatcherServlet.EXCEPTION_ATTRIBUTE에 예외를 넣어 두므로 afterCompletion에서 이 속성을 읽거나, 응답 상태 코드(response.getStatus())가 4xx·5xx인지로 판단할 수 있다. 다만 뷰를 렌더링한 경우에는 이 속성이 설정되지 않으므로, 어드바이스 안에서 직접 로그를 남기는 편이 가장 확실하다.

     컨트롤러가 던진 예외를 처리하는 @RestControllerAdvice 메서드가 ApiError 객체만 반환하고 상태 관련 지정(@ResponseStatus, ResponseEntity)이 전혀 없다. 클라이언트가 받는 상태 코드는? 500. 예외가 발생했으므로 DispatcherServlet이 자동으로 500을 설정한다. 400. @ExceptionHandler는 기본적으로 클라이언트 오류로 취급한다. 200. DispatcherServlet은 상태를 바꾸지 않고, 반환값 처리기는 현재 상태(기본 200)로 본문을 쓴다. 상태 없이 연결이 끊긴다. processHandlerException은 리졸버 호출 전 Content-Type·Content-Disposition 헤더와 버퍼만 비우고 상태 코드는 건드리지 않는다. ExceptionHandlerExceptionResolver는 예외 처리 메서드를 컨트롤러 메서드처럼 호출하므로, 상태를 지정하지 않으면 서블릿 응답의 기본값 200이 그대로 나간다. 500은 예외가 처리되지 않고 컨테이너까지 갔을 때의 결과다. @ResponseStatus(code = HttpStatus.NOT_FOUND, reason = "error.order.notfound")가 붙은 예외를 컨트롤러에서 던졌다. 스프링 부트 기본 설정에서 API 클라이언트가 받는 응답에 대한 설명으로 옳은 것은? 상태 404와 함께 "error.order.notfound"를 메시지 소스로 해석한 문장이 본문 message 키에 실린다. 리졸버는 sendError(404, 해석된 이유)만 호출하고, 본문은 /error의 기본 JSON이 만든다. 기본 설정에서는 message 키가 지워진다. ResponseStatusExceptionResolver가 이유 문자열을 그대로 응답 본문에 텍스트로 쓴다. @ResponseStatus는 @ExceptionHandler가 없으면 무시되어 500이 된다. applyStatusAndReason은 이유를 MessageSource로 해석해 sendError에 넘기고 빈 ModelAndView를 돌려줄 뿐 본문을 쓰지 않는다. 본문은 톰캣의 ERROR 디스패치로 BasicErrorController가 만들고, DefaultErrorAttributes는 server.error.include-message의 기본값 never에 따라 message를 제거한다. 어드바이스에 @ExceptionHandler로 IllegalArgumentException 처리 메서드를 두었더니, @PathVariable long id에 "abc"를 보낸 요청까지 이 메서드로 들어왔다. 그 이유는? MethodArgumentTypeMismatchException이 IllegalArgumentException을 상속하기 때문이다. DefaultHandlerExceptionResolver가 처리한 뒤 결과를 ExceptionHandlerExceptionResolver에 다시 넘기기 때문이다. 스프링이 모든 타입 변환 실패를 IllegalArgumentException으로 바꿔 다시 던지기 때문이다. 던져진 예외 자체는 맞지 않지만 그 원인인 NumberFormatException이 IllegalArgumentException의 하위 타입이라 원인 체인 매칭에 걸렸고, 이 리졸버가 DefaultHandlerExceptionResolver보다 먼저 묻기 때문이다. ExceptionHandlerMethodResolver는 예외 자신의 타입으로 맞는 매핑이 없으면 getCause()를 따라 내려가 다시 찾는다. MethodArgumentTypeMismatchException은 TypeMismatchException 계열이지 IllegalArgumentException의 하위 타입이 아니다. 기본 셋에서 ExceptionHandlerExceptionResolver가 첫 번째이므로 원인 매칭으로 먼저 처리해 버린다. 인증 필터(OncePerRequestFilter)에서 토큰이 만료되면 TokenExpiredException을 던지고, @RestControllerAdvice에 이 예외의 401 처리 메서드를 두었다. 실제 결과는? 필터는 DispatcherServlet 바깥에서 실행되므로 리졸버 체인을 거치지 않고, 예외가 컨테이너로 전파되어 /error의 500 응답이 된다. 어드바이스는 전역이므로 필터 예외도 처리되어 401이 된다. 필터 예외는 DefaultHandlerExceptionResolver가 처리해 400이 된다. 필터가 예외를 던지면 요청이 컨트롤러로 그대로 넘어간다. 리졸버 체인은 doDispatch 안의 processHandlerException에서만 동작한다. 필터는 서블릿보다 바깥의 필터 체인에서 실행되므로 그 예외는 DispatcherServlet을 거치지 않고 톰캣까지 올라가고, 톰캣이 500으로 정한 뒤 /error로 포워드한다. 필터에서는 응답을 직접 써야 한다.
    HandlerExceptionResolver
    DispatcherServlet이 핸들러 실행 중 생긴 예외를 넘기는 전략 인터페이스. 반환값으로 오류 뷰, 처리 완료, 미처리를 알린다.
    책임 연쇄(chain of responsibility)
    요청을 처리자 목록에 차례로 넘겨 처음으로 처리한 객체에서 멈추는 구조. 리졸버 목록과 어드바이스 목록이 모두 이 방식이다.
    sendError
    서블릿 응답에 오류 상태를 표시하는 메서드. 호출 뒤 응답은 커밋된 것으로 보며, 컨테이너가 해당 상태의 오류 페이지로 디스패치한다.
    ERROR 디스패치(DispatcherType.ERROR)
    컨테이너가 오류 페이지로 요청을 내부 포워드할 때의 디스패처 타입. jakarta.servlet.error.* 요청 속성이 함께 채워진다.
    ExceptionDepthComparator
    던져진 예외에서 선언된 예외 타입까지의 상속 거리로 후보를 정렬하는 비교기. 가장 가까운 처리 메서드가 선택된다.
    원인 체인(cause chain)
    getCause()로 이어지는 감싼 예외들의 목록. @ExceptionHandler 매칭과 @ResponseStatus 해석에서 모두 탐색된다.
    응답 커밋(committed response)
    상태 줄과 헤더가 이미 클라이언트로 전송된 상태. 이후에는 상태 코드를 바꾸거나 sendError를 호출할 수 없다.
    RFC 9457 Problem Details
    HTTP API의 오류 본문 표준 형식. type, title, status, detail, instance 필드와 application/problem+json 미디어 타입을 정의한다.
