    검증은 어디에서, 누구를 위해 하는가

    스프링 MVC 1편의 마지막 회차에서 만든 상품 등록 폼은 들어온 값을 그대로 저장했다. 이름을 비워도, 가격에 0을 넣어도 저장소에 들어간다. 가격 칸에 abc를 넣으면 사정이 더 나쁘다. 사용자는 자신이 쓰던 폼 대신 400 오류 화면을 보게 되고, 무엇을 잘못했는지 알 길이 없다. 이번 회차의 주제는 이 두 가지를 고치는 일이다. 잘못된 값은 저장하지 않고, 사용자에게는 입력하던 폼을 그대로 돌려주면서 어디가 왜 잘못되었는지 알려 준다.

    먼저 검증을 어디에서 해야 하는지부터 정하자. 브라우저에서 자바스크립트나 HTML의 required 속성으로 검사하는 것을 클라이언트 검증(client-side validation), 서버가 요청을 받은 뒤 검사하는 것을 서버 검증(server-side validation)이라고 한다. 클라이언트 검증은 서버까지 왕복하지 않고 바로 알려 주므로 사용하기 편하다. 그러나 서버 입장에서 믿을 수 있는 것은 아니다. 서버가 받는 것은 브라우저가 아니라 TCP 연결 위로 흘러온 HTTP 메시지이고, 그 메시지는 누구나 어떤 도구로든 만들 수 있다.

    curl -i -X POST http://localhost:8080/products/add \
     -d "name=" -d "price=-1" -d "quantity=99999999"

    이 요청은 화면의 자바스크립트를 한 줄도 거치지 않는다. 그러므로 원칙은 단순하다. 클라이언트 검증은 편의이고, 서버 검증은 관문이다. 서버 검증은 생략할 수 없고, 클라이언트 검증은 그 위에 얹는 선택 사항이다. 이번 회차와 다음 회차는 모두 서버 검증만 다룬다.

    검증할 내용은 성격이 다른 세 종류로 나뉜다. 이 구분이 회차 전체의 뼈대가 된다.

    종류예실패가 드러나는 시점
    타입 검증가격 칸에 abc문자열을 Integer로 바꾸는 도중(바인딩 중)
    필드 검증이름이 비어 있다, 가격이 범위를 벗어났다객체가 만들어진 뒤, 필드 하나를 보고 판단
    객체 검증(전역 검증)가격 × 수량이 상한을 넘는다객체가 만들어진 뒤, 여러 필드를 함께 보고 판단

    타입 검증만 시점이 다르다는 점을 눈여겨보자. 필드 검증과 객체 검증은 우리가 쓴 코드가 객체를 들여다보고 판단하지만, 타입 오류는 객체에 값이 들어가기도 전에 스프링 내부에서 터진다. 직접 만든 검증 코드가 이 오류를 잡지 못하는 이유가 여기에 있고, BindingResult가 필요한 이유도 여기에 있다.

    이 회차에서 쓸 검증 규칙은 다음과 같다. 예제 도메인은 MVC 1편에서 쓰던 Product(이름, 가격, 수량)를 그대로 쓴다.

    • 이름: 필수. 공백만 있는 값도 허용하지 않는다.
    • 가격: 필수. 100원 이상 5,000,000원 이하.
    • 수량: 필수. 1개 이상 999개 이하.
    • 가격 × 수량은 50,000,000원을 넘을 수 없다(특정 필드 하나의 문제가 아닌 규칙).
    • 검증에 실패하면 저장하지 않고, 입력하던 값이 남아 있는 폼을 다시 보여 주며, 오류 메시지를 해당 칸 옆에 표시한다.

    실패한 요청이 받아야 할 응답: 리다이렉트가 아니라 같은 요청 안에서 다시 그리기

    코드를 쓰기 전에 응답의 모양부터 정한다. 등록에 성공한 POST는 302 응답으로 상세 화면에 리다이렉트한다. 새로고침으로 같은 POST가 다시 전송되는 것을 막는 PRG(Post/Redirect/Get) 패턴이고, MVC 1편에서 다뤘다. 실패한 POST는 다르게 처리한다. 리다이렉트하지 않고, 그 요청을 처리하는 도중에 폼 템플릿을 다시 렌더링해 응답 본문으로 내보낸다.

    이유는 데이터가 사는 곳에 있다. 사용자가 입력한 값과 오류 정보는 이 요청을 처리하는 동안만 존재하는 모델(model)에 담긴다. 모델은 요청 하나에 딸린 맵이고, 응답이 나가면 버려진다. 리다이렉트는 브라우저에게 "다른 URL로 새 요청을 보내라"고 지시하는 것이므로, 새 요청이 도착했을 때 서버에는 이전 요청의 모델이 남아 있지 않다. 입력값과 오류를 화면에 보여 주려면 그것들이 살아 있는 지금 이 요청에서 화면을 그려야 한다.

    브라우저가 폼을 전송할 때 서버가 받는 HTTP 메시지를 한 번 더 확인해 두자. application/x-www-form-urlencoded 본문에는 타입 정보가 없다. 이름 칸을 비우면 파라미터가 사라지는 것이 아니라 name=처럼 빈 문자열이 온다. 숫자 칸에 넣은 값도 문자열이다. 서버가 보는 것은 아래의 27바이트가 전부다.

    POST /products/add HTTP/1.1
Host: localhost:8080
Content-Type: application/x-www-form-urlencoded
Content-Length: 27

name=&price=abc&quantity=10

    도메인 객체와 폼을 보여 주는 GET 핸들러는 다음과 같다. 폼 템플릿이 th:object로 객체를 참조하므로(02회), 빈 폼을 보여 줄 때도 비어 있는 Product를 모델에 넣어 준다.

    검증 직접 처리: 오류를 Map에 담아 보기

    프레임워크의 도움 없이 요구사항을 구현해 보자. 직접 해 보면 무엇이 되고 무엇이 안 되는지가 드러나고, 그 "안 되는 것"이 스프링의 검증 기능이 존재하는 이유다. 방법은 단순하다. 필드 이름을 키로, 오류 메시지를 값으로 하는 맵을 만들고, 규칙을 어길 때마다 맵에 넣는다. 맵이 비어 있지 않으면 폼을 다시 그린다.

    @PostMapping("/add")
public String add(@ModelAttribute Product product, Model model) {
    Map errors = new HashMap<>();

    if (!StringUtils.hasText(product.getName())) {
        errors.put("name", "상품 이름을 입력해 주세요.");
    }
    if (product.getPrice() == null || product.getPrice() < 100 || product.getPrice() > 5_000_000) {
        errors.put("price", "가격은 100원 이상 5,000,000원 이하로 입력해 주세요.");
    }
    if (product.getQuantity() == null || product.getQuantity() < 1 || product.getQuantity() > 999) {
        errors.put("quantity", "수량은 1개 이상 999개 이하로 입력해 주세요.");
    }
    if (product.getPrice() != null && product.getQuantity() != null) {
        long total = (long) product.getPrice() * product.getQuantity();
        if (total > 50_000_000L) {
            errors.put("globalError", "가격 × 수량은 50,000,000원을 넘을 수 없습니다. 현재 " + total + "원");
        }
    }

    if (!errors.isEmpty()) {
        model.addAttribute("errors", errors);
        return "products/addForm";      // 같은 요청 안에서 폼을 다시 그린다
    }

    Product saved = productStore.save(product);
    return "redirect:/products/" + saved.getId();
}

    name=&price=50&quantity=10 요청으로 한 줄씩 따라가 보자. 스프링이 Product를 만들고 setter를 호출해 name="", price=50, quantity=10을 채운 뒤 메서드를 호출한다. StringUtils.hasText("")는 false이므로 name 오류가 들어간다. 50은 100보다 작으므로 price 오류가 들어간다. 수량 10은 통과한다. 총액은 500원이라 전역 규칙도 통과한다. 맵에 두 건이 있으므로 모델에 errors를 넣고 폼 뷰 이름을 반환한다. 저장소는 호출되지 않았다.

    이름 검사에 == null이 아니라 StringUtils.hasText를 쓴 이유는 앞에서 본 HTTP 메시지에 있다. 빈 칸은 name=으로 전송되고, 문자열 필드에는 null이 아니라 길이 0인 문자열이 들어간다. hasText는 null, 빈 문자열, 공백만 있는 문자열을 모두 false로 판정한다.

    총액 계산의 (long) 캐스팅도 장식이 아니다. 두 int의 곱은 int로 계산되고, 결과가 2,147,483,647을 넘으면 예외 없이 상위 비트가 잘려 나간다. 가격 4,300,000원에 수량 999개를 직접 돌려 보면 차이가 보인다.

    int price = 4_300_000, quantity = 999;
System.out.println(price * quantity);          // 732704
System.out.println((long) price * quantity);   // 4295700000

    캐스팅이 없으면 42억 원어치 주문이 73만 원으로 계산되어 "5천만 원 이하" 검사를 통과한다. 두 필드가 각각 범위 검사를 통과했더라도 둘을 조합한 값은 타입의 표현 범위를 넘을 수 있다. 검증 코드 자체가 검증 대상만큼 꼼꼼해야 한다는 점을 보여 주는 예다.

    errors?.containsKey(...)의 ?.는 스프링 표현식 언어(SpEL)의 안전 탐색 연산자다. GET으로 빈 폼을 열 때는 모델에 errors가 없어 null인데, 그 상태에서 errors.containsKey를 호출하면 예외가 난다. ?.는 왼쪽이 null이면 메서드를 호출하지 않고 null을 돌려주고, th:if는 null을 거짓으로 취급한다.

    입력값은 어떻게 폼에 남았을까. @ModelAttribute가 붙은 객체는 스프링이 모델에 자동으로 넣는다. 실패해서 폼을 다시 그릴 때 템플릿의 th:field="*{price}"는 모델의 product에서 값을 읽으므로, 사용자가 입력한 50이 그대로 칸에 나타난다. 여기까지는 요구사항을 만족한 것처럼 보인다.

    직접 처리의 한계: 컨트롤러에 도달하지도 못하는 오류

    이제 가격에 abc를 넣어 보낸다. 결과는 오류 메시지가 달린 폼이 아니라 400 응답이다. 컨트롤러 메서드 첫 줄에 로그를 찍어 두어도 출력되지 않는다. 이 실험은 Spring Framework 7.0.10의 MockMvc로 돌려 확인했고, 6.0.7 이후의 6.x에서도 같은 예외 타입과 상태 코드가 나온다(5.3과 6.0.6까지는 예외 타입이 BindException이었다).

    POST /products/add  name=키보드 price=abc quantity=10
  status=400  resolvedException=MethodArgumentNotValidException
  (컨트롤러 메서드는 호출되지 않음)

    왜 우리 코드가 실행조차 되지 않았는지는 호출 순서를 보면 분명하다. 자바에서 메서드를 호출하려면 인자가 먼저 준비되어야 한다. 스프링 MVC도 마찬가지로, 컨트롤러 메서드를 리플렉션으로 호출하기 전에 파라미터마다 인자 해석기(argument resolver)를 돌려 값을 만든다. Product 인자를 만드는 도중에 "abc"를 Integer로 바꾸지 못했고, 인자가 준비되지 않았으니 메서드를 부를 수 없다.

    요청 스레드의 호출 스택 (위가 바깥, 아래가 안쪽)

DispatcherServlet.doDispatch
 └ RequestMappingHandlerAdapter.handle
    └ InvocableHandlerMethod.invokeForRequest
       ├ getMethodArgumentValues            ← ① 인자를 먼저 전부 만든다
       │   └ ModelAttributeMethodProcessor.resolveArgument
       │       ├ 객체 생성, 요청 파라미터 → 필드 (바인딩)
       │       │     "abc" → Integer 변환 실패
       │       └ 오류가 있는데 받아 줄 파라미터가 없다
       │             → 예외를 던진다                 ✕ 여기서 중단
       └ doInvoke(args)                     ← ② 컨트롤러 메서드 호출 (도달하지 못함)

예외는 DispatcherServlet까지 올라가고,
DefaultHandlerExceptionResolver가 400 응답으로 바꾼다.

    직접 처리 방식의 한계를 정리하면 세 가지다.

    1. 타입 오류를 잡을 수 없다. 오류가 컨트롤러 호출보다 앞 단계에서 예외로 터지므로, 컨트롤러 안의 어떤 코드도 그것을 볼 수 없다.
    2. 설령 호출되더라도 입력값을 보존할 수 없다. Product.price는 Integer다. Integer 타입 필드에는 "abc"라는 문자열을 담을 방법이 없다. 사용자가 입력한 값을 폼에 되돌려 주려면 객체 바깥 어딘가에 따로 보관해야 한다.
    3. 중복과 흩어짐. 메시지가 자바 코드에 문자열로 박혀 있고, 수정 폼에도 같은 검사를 복사해야 하며, 템플릿은 맵의 키 이름이라는 약속에 의존한다.
    이 장의 핵심

    검증에 필요한 것은 "오류 목록"만이 아니다. 바인딩 실패를 예외가 아니라 데이터로 바꿔 주는 장치, 객체에 담지 못한 원래 입력값을 보관할 장소, 오류와 메시지를 연결하는 규칙이 함께 있어야 한다. 스프링에서 이 세 가지를 한 객체가 맡는데, 그것이 BindingResult다.

    BindingResult: 바인딩 실패를 예외가 아니라 값으로 받기

    BindingResult는 이름 그대로 바인딩의 결과를 담는 객체다. 컨트롤러 메서드에서 검증할 객체 바로 다음 파라미터로 선언하면, 스프링은 바인딩 중에 생긴 오류를 예외로 던지지 않고 이 객체에 담아 컨트롤러를 호출한다.

    @PostMapping("/add")
public String add(@ModelAttribute Product product, BindingResult bindingResult) {
    // 타입 오류가 있어도 이 메서드는 호출된다
    // ...
}

    (Product p, Model m, BindingResult br)price=abc400, 컨트롤러 호출 안 됨
    (Product p, Model m, BindingResult br)price=10컨트롤러 호출됨

    세 번째와 네 번째 줄이 "바로 다음"이라는 규칙의 실체를 보여 준다. 이 분기를 만드는 코드는 ModelAttributeMethodProcessor에 있는데, 판단 기준은 놀랄 만큼 단순하다. 현재 파라미터의 인덱스가 i일 때 i + 1번째 파라미터의 타입이 Errors(BindingResult의 상위 인터페이스)에 대입 가능한지만 본다. 한 칸 건너에 있는 BindingResult는 고려 대상이 아니다. 그래서 사이에 Model이 끼어 있으면 바인딩 오류가 났을 때 예외가 던져진다. 오류가 없을 때는 동작하므로, 정상 입력만으로 테스트하면 이 버그는 드러나지 않는다.

    ModelAttributeMethodProcessor.resolveArgument가 하는 일을 순서대로 적으면 다음과 같다(Spring Framework 6.2 소스 기준).

    1. 모델 속성의 이름을 정한다. @ModelAttribute에 이름을 주지 않으면 타입 이름의 첫 글자를 소문자로 바꾼 product가 된다.
    2. 이 인자 전용의 WebDataBinder를 만든다. 이때 컨트롤러의 @InitBinder 메서드가 호출된다.
    3. 대상 객체를 생성한다. 6.1부터는 바인더가 생성자를 호출해 객체를 만들고, 6.0까지는 객체를 먼저 만든 뒤 바인더를 만들었다. 이 순서 차이는 뒤에서 검증기를 등록할 때 다시 나온다.
    4. 요청 파라미터를 객체의 프로퍼티에 넣는다(setter 호출). 변환에 실패한 필드는 오류로 기록한다.
    5. 파라미터에 검증 애노테이션이 있으면 바인더에 등록된 검증기를 실행한다.
    6. 오류가 있고 바로 다음 파라미터가 Errors 타입이 아니면 MethodArgumentNotValidException을 던진다.
    7. 그렇지 않으면 객체와 BindingResult를 모델에 넣고 객체를 인자로 돌려준다.

    7번이 중요하다. BindingResult는 컨트롤러 파라미터로만 전달되는 것이 아니라 모델에도 들어간다. 키는 org.springframework.validation.BindingResult.에 객체 이름을 붙인 문자열이다. 컨트롤러 안에서 모델의 키를 출력해 보면 다음과 같다.

    modelKeys=[product, org.springframework.validation.BindingResult.product]

    우리가 model.addAttribute를 부른 적이 없는데도 뷰가 오류 정보를 읽을 수 있는 이유가 이것이다. 타임리프의 th:errors나 #fields는 이 키로 모델에서 BindingResult를 찾는다. 그리고 이어지는 BindingResult 파라미터의 인자 해석기는 새 객체를 만드는 것이 아니라 모델의 마지막 키가 이 접두사로 시작하는지 보고 그 값을 꺼내 준다. 컨트롤러가 받은 bindingResult와 모델에 있는 것은 같은 인스턴스다.

    바인딩 오류가 생긴 뒤 "다음 파라미터가 Errors 타입인가"라는 한 가지 질문으로 400 응답과 컨트롤러 호출이 갈리는 것을 보여 준다. 가로로 흐르는 깔끔한 순서도. 왼쪽에 둥근 상자 "요청 파라미터 price=abc". 오른쪽으로 화살표가 가서 사각형 "WebDataBinder: 문자열을 필드 타입으로 변환". 그 오른쪽에 사각형 "변환 실패 → FieldError 기록". 다음에 마름모 "다음 파라미터가 Errors 타입인가?". 마름모에서 위쪽으로 "아니오" 화살표가 나가 빨간 테두리 상자 "예외 던짐 → 400 응답"으로 간다. 마름모에서 오른쪽으로 "예" 화살표가 나가 초록 테두리 상자 "컨트롤러 호출 (오류는 BindingResult 안에)"로 간다. 초록 상자 아래에 작은 원통 모양 "모델"을 그리고 그 안에 두 줄 "product", "BindingResult.product" 를 적는다. 초록 상자에서 모델로 점선 화살표. 흰 배경, 평면 벡터 스타일, 한국어 라벨은 따옴표 안 문구 그대로. 바인딩 오류를 예외로 던질지 값으로 넘길지는 바로 다음 파라미터의 타입 하나로 정해진다.
    일상에서 가져온 비유반려 사유가 적힌 접수증

    관공서 창구에 신청서를 냈는데 날짜 칸에 글자를 써넣었다고 하자. 한 창구는 서류를 받지 않고 "접수 불가"라고만 말한다. 다른 창구는 신청서를 일단 받아 두고, 어느 칸이 왜 잘못되었는지 적은 메모를 붙여 담당자에게 넘긴다. BindingResult가 없는 컨트롤러는 첫 번째 창구이고, 있는 컨트롤러는 두 번째 창구다. 다만 비유가 맞지 않는 곳이 있다. 실제 신청서에는 잘못 쓴 글자가 그대로 남아 있지만, 자바 객체의 Integer 필드에는 "abc"가 들어가지 못한다. 그래서 스프링은 원래 입력값을 신청서가 아니라 메모(FieldError) 쪽에 적어 둔다.

    한 층 아래: 타입 변환 실패가 FieldError가 되기까지

    "abc"가 오류 객체 하나로 바뀌는 과정을 따라가 보자. 웹 계층을 걷어 내고 DataBinder만으로 같은 일을 재현할 수 있다. WebDataBinder는 DataBinder를 상속해 체크박스용 필드 마커 같은 웹 전용 기능을 더한 것이고, 서블릿 요청의 파라미터를 프로퍼티 값 목록으로 바꾸는 일은 그 하위 클래스인 ServletRequestDataBinder가 맡는다. 바인딩과 오류 기록의 핵심은 DataBinder에 있다.

    Product product = new Product();
DataBinder binder = new DataBinder(product, "product");

MutablePropertyValues values = new MutablePropertyValues();
values.add("name", "");
values.add("price", "abc");
values.add("quantity", "");
binder.bind(values);

BindingResult result = binder.getBindingResult();
System.out.println(product.getName().isEmpty() + " " + product.getPrice() + " " + product.getQuantity());
for (FieldError e : result.getFieldErrors()) {
    System.out.println(e.getField() + " / " + e.getRejectedValue() + " / " + e.isBindingFailure());
    System.out.println(Arrays.toString(e.getCodes()));
    System.out.println(e.getDefaultMessage());
}

    내부에서 일어난 일은 이렇다. DataBinder는 대상 객체를 BeanWrapper로 감싼다. BeanWrapper는 프로퍼티 이름으로 setter를 찾아 리플렉션으로 호출하는 도구이고, 호출 전에 값을 setter의 파라미터 타입으로 변환한다. "abc"를 Integer로 바꾸는 과정에서 NumberFormatException이 나고, 이것이 TypeMismatchException으로 감싸진다. 기본 메시지 끝의 For input string: "abc"가 원래 예외의 메시지다.

    중요한 점은 한 필드의 실패가 나머지 필드의 바인딩을 멈추지 않는다는 것이다. 프로퍼티를 하나씩 설정하다가 예외가 나면 그 예외를 목록에 모아 두고 다음 프로퍼티로 넘어간다. 전부 끝난 뒤 모아 둔 예외를 PropertyBatchUpdateException 하나로 묶어 던지고, DataBinder가 이를 잡아 예외마다 FieldError를 만들어 BindingResult에 넣는다. 그래서 위 결과에서 price는 실패했지만 name은 정상적으로 채워졌다. 사용자가 폼을 다시 받았을 때 한 칸의 오류 때문에 다른 칸이 비워지지 않는 것은 이 설계 덕분이다.

    예외를 오류 객체로 바꾸는 이 작업을 맡는 DefaultBindingErrorProcessor가 만드는 FieldError에는 네 가지가 담긴다. 오류 코드는 TypeMismatchException의 오류 코드인 typeMismatch에서 출발한 코드 목록이다. 거절된 값(rejected value)은 변환하려던 원래 값 "abc"다. 바인딩 실패 여부(bindingFailure)는 true다. 기본 메시지는 예외의 메시지다. 코드가 왜 네 개인지는 조금 뒤 메시지 코드 절에서 다룬다.

    빈 문자열의 처리도 같은 실험으로 확인할 수 있다. 필드 타입에 따라 결과가 다르다.

    필드 타입요청 파라미터바인딩 결과
    Stringname=빈 문자열 "". null이 아니다.
    Integerquantity=null. 오류 없음.
    intstock=typeMismatch 오류. 필드는 기본값 0 그대로.
    아무 타입파라미터 자체가 없음setter가 호출되지 않는다. 필드는 생성 직후의 값 그대로, 오류 없음.

    폼을 받는 객체의 숫자 필드를 int가 아니라 Integer로 선언하는 이유가 이 표에 있다. 기본형은 "입력하지 않음"을 표현할 값이 없다. 빈 칸을 0으로 받아들이면 "0을 입력했다"와 구별할 수 없고, 스프링은 그렇게 하지 않고 타입 오류로 처리한다. Integer는 null로 "값 없음"을 표현할 수 있으므로 빈 칸이 타입 오류가 아니라 필수 값 누락이라는 올바른 종류의 오류로 이어진다.

    FieldError와 ObjectError: 오류 하나를 표현하는 객체

    바인딩 오류는 스프링이 넣어 주지만, 범위 검사 같은 비즈니스 규칙의 오류는 우리가 넣어야 한다. BindingResult에 넣는 오류는 두 종류다. 특정 필드에 대한 오류는 FieldError, 특정 필드에 속하지 않는 객체 전체의 오류는 ObjectError다. 화면에서는 앞의 것을 해당 칸 옆에, 뒤의 것을 폼 상단에 보여 주는 것이 보통이며, 후자를 전역 오류(global error)라고 부른다.

    FieldError가 ObjectError를 상속하고, ObjectError가 MessageSourceResolvable의 구현이라는 점을 기억해 두자. 오류 객체가 곧 "메시지로 풀 수 있는 것"이라는 뜻이고, 메시지 처리 절에서 이 사실이 그대로 쓰인다. 먼저 가장 단순한 생성자로 오류를 넣어 본다.

    @PostMapping("/add")
public String add(@ModelAttribute Product product, BindingResult bindingResult) {
    if (!StringUtils.hasText(product.getName())) {
        bindingResult.addError(new FieldError("product", "name", "상품 이름을 입력해 주세요."));
    }
    if (product.getPrice() == null || product.getPrice() < 100 || product.getPrice() > 5_000_000) {
        bindingResult.addError(new FieldError("product", "price",
                "가격은 100원 이상 5,000,000원 이하로 입력해 주세요."));
    }
    // quantity 도 같은 모양 ...
    if (product.getPrice() != null && product.getQuantity() != null) {
        long total = (long) product.getPrice() * product.getQuantity();
        if (total > 50_000_000L) {
            bindingResult.addError(new ObjectError("product",
                    "가격 × 수량은 50,000,000원을 넘을 수 없습니다. 현재 " + total + "원"));
        }
    }

    if (bindingResult.hasErrors()) {
        return "products/addForm";
    }
    Product saved = productStore.save(product);
    return "redirect:/products/" + saved.getId();
}

    첫 번째 인자 "product"는 객체 이름으로, 모델 속성 이름과 같아야 한다. 맵을 직접 모델에 넣던 코드가 사라졌고, 타입 오류 요청도 이제 컨트롤러까지 온다. 그런데 이 코드에는 사용자가 바로 알아챌 결함이 있다. 가격에 50을 넣어 전송하면 오류 메시지는 나오지만 가격 칸이 비어 버린다. 컨트롤러에서 BindingResult에 값을 물어보면 원인이 보인다.

    POST price=50   → product.getPrice()=50   bindingResult.getFieldValue("price")=null
POST price=abc  → product.getPrice()=null bindingResult.getFieldValue("price")=abc

    객체에는 50이 들어 있는데 getFieldValue는 null을 돌려준다. 반대로 타입 오류일 때는 객체에 값이 없는데 abc가 나온다. 이 동작은 AbstractBindingResult.getFieldValue의 규칙에서 나온다.

    • 그 필드에 FieldError가 있으면, 첫 번째 오류의 거절된 값을 돌려준다.
    • 오류가 없으면, 대상 객체에서 그 프로퍼티의 현재 값을 읽어 돌려준다.

    타임리프의 th:field는 입력 칸의 value를 객체에서 직접 읽지 않고 스프링의 BindStatus를 거쳐 이 getFieldValue로 얻는다. 그래서 타입 오류 때 객체에 담기지 못한 abc가 폼에 다시 나타날 수 있다. 직접 처리 방식의 두 번째 한계, 곧 "객체에 담을 수 없는 입력값을 어디에 보관할 것인가"의 답이 FieldError의 거절된 값이다. 그리고 인자 세 개짜리 생성자는 거절된 값을 받지 않으므로 null로 남고, 오류가 있는 필드는 거절된 값을 우선하는 규칙 때문에 칸이 비게 된다.

    FieldError에는 생성자가 둘 있다. 모든 정보를 받는 쪽을 쓰면 문제가 풀린다.

    // FieldError(String objectName, String field, String defaultMessage)
// FieldError(String objectName, String field, Object rejectedValue, boolean bindingFailure,
//            String[] codes, Object[] arguments, String defaultMessage)

bindingResult.addError(new FieldError("product", "price", product.getPrice(), false,
        null, null, "가격은 100원 이상 5,000,000원 이하로 입력해 주세요."));

    rejectedValue에는 사용자가 입력한 값을, bindingFailure에는 타입 변환 실패인지 여부를 넣는다. 우리가 넣는 것은 변환에 성공한 뒤의 규칙 위반이므로 false다. codes와 arguments는 메시지 코드와 메시지 인자인데 다음 절에서 채운다. ObjectError도 같은 방식으로 (objectName, defaultMessage)와 (objectName, codes, arguments, defaultMessage) 두 생성자가 있다.

    뷰 쪽은 맵을 뒤지던 코드가 타임리프의 스프링 통합 기능으로 바뀐다.

    GET으로 빈 폼을 열 때도 이 템플릿은 문제없이 동작한다. 핸들러가 반환된 뒤 스프링의 ModelFactory가 모델 속성(product)에 대응하는 BindingResult가 없으면 비어 있는 것을 만들어 넣어 주므로, 타임리프는 오류가 없는 BindingResult를 읽게 된다(Spring Framework 7.0.10의 MockMvc에서 GET 응답의 모델 키가 [product, org.springframework.validation.BindingResult.product]인 것을 확인했다). 맵을 직접 다룰 때처럼 null 여부를 신경 쓸 필요가 없다.

    오류 코드와 메시지 1: 메시지를 코드 밖으로 꺼내기

    지금까지의 코드는 오류 메시지를 자바 문자열로 들고 있다. 문구 하나를 고치려고 컨트롤러를 수정해 다시 배포해야 하고, 같은 문구가 등록 폼과 수정 폼에 흩어진다. 03회에서 화면 문구를 messages.properties로 꺼낸 것과 같은 일을 오류 메시지에도 한다. 오류 객체가 메시지 문자열 대신 메시지 코드를 들고 있게 하고, 실제 문구는 프로퍼티 파일에서 찾는다.

    오류 메시지 전용 파일을 하나 더 두고 스프링 부트에 알려 준다. 스프링 부트 문서에 따르면 spring.messages.basename은 여러 위치의 목록을 받는다.

    spring.messages.basename=messages,errors
    required.product.name=상품 이름을 입력해 주세요.
range.product.price=가격은 {0}원 이상 {1}원 이하로 입력해 주세요.
range.product.quantity=수량은 {0}개 이상 {1}개 이하로 입력해 주세요.
totalAmountMax=가격 × 수량은 {0}원을 넘을 수 없습니다. 현재 {1}원

    이제 앞 절에서 비워 두었던 codes와 arguments를 채운다. 기본 메시지 자리는 null로 둔다.

    bindingResult.addError(new FieldError("product", "price", product.getPrice(), false,
        new String[]{"range.product.price"}, new Object[]{100, 5_000_000}, null));

bindingResult.addError(new ObjectError("product",
        new String[]{"totalAmountMax"}, new Object[]{50_000_000L, total}, null));

    codes가 문자열 하나가 아니라 배열이라는 점이 눈에 띈다. 이 배열이 메시지를 찾는 순서를 정한다. 뷰가 오류 메시지를 요청하면 타임리프는 스프링의 MessageSource에 오류 객체를 통째로 넘긴다. 오류 객체는 MessageSourceResolvable이므로 코드 목록, 인자, 기본 메시지를 스스로 내놓을 수 있다. AbstractMessageSource.getMessage(MessageSourceResolvable, Locale)의 규칙은 세 단계다.

    1. codes를 앞에서부터 하나씩 찾는다. 처음으로 메시지가 발견된 코드에서 멈추고, 그 메시지의 {0}, {1}에 arguments를 채워 돌려준다.
    2. 어느 코드에도 메시지가 없으면 기본 메시지를 돌려준다.
    3. 기본 메시지도 null이면 NoSuchMessageException을 던진다. 이 예외는 템플릿을 렌더링하는 도중에 나므로 폼 화면 자체가 그려지지 못한다.

    3번 때문에 메시지 코드의 오타는 검증이 실패하는 요청에서만 드러나는 오류가 된다. 정상 입력만 시험해서는 발견할 수 없으므로, 검증 실패 경로마다 화면이 실제로 그려지는지 확인하는 테스트가 필요하다.

    인자 치환에서 하나 알아 둘 것이 있다. 메시지의 {0}은 자바의 java.text.MessageFormat이 처리하고, 인자가 숫자이면 로케일의 숫자 형식을 적용한다. 그래서 정수 5000000을 넘기면 한국어 로케일에서 자릿수 구분 기호가 붙는다.

    System.out.println(MessageFormat.format("{0} / {0,number,#}", 5000000));
// 5,000,000 / 5000000

    가격처럼 쉼표가 있는 편이 읽기 좋은 값에는 도움이 되지만, 연도나 식별자 같은 숫자를 인자로 넘기면 2,024처럼 나온다. 구분 기호 없이 출력하려면 메시지 쪽에서 {0,number,#}처럼 형식을 지정하거나 인자를 문자열로 넘긴다.

    오류 코드와 메시지 2: rejectValue와 reject

    인자 일곱 개짜리 생성자는 정확하지만 번거롭다. 객체 이름을 매번 문자열로 적고, 거절된 값을 직접 꺼내 넘기고, 코드 배열을 손으로 만든다. 그런데 이 정보의 대부분은 BindingResult가 이미 알고 있다. BindingResult는 특정 객체의 바인딩 결과이므로 대상 객체와 그 이름을 갖고 있고, 필드 이름만 알려 주면 현재 값과 타입을 스스로 읽을 수 있다. 그래서 Errors 인터페이스에는 더 짧은 메서드가 있다.

    bindingResult.rejectValue("price", "range", new Object[]{100, 5_000_000}, null);
bindingResult.reject("totalAmountMax", new Object[]{50_000_000L, total}, null);

// 인자와 기본 메시지가 필요 없으면
bindingResult.rejectValue("name", "required");

    rejectValue(field, errorCode, errorArgs, defaultMessage)는 필드 오류를, reject(errorCode, errorArgs, defaultMessage)는 전역 오류를 등록한다. AbstractBindingResult.rejectValue의 구현은 세 줄로 요약된다. 대상 객체에서 그 필드의 현재 값을 읽어 거절된 값으로 삼고, 오류 코드와 필드 이름으로 메시지 코드 목록을 만들고, 이 둘로 FieldError를 생성해 addError한다. 결국 앞 절의 긴 생성자 호출을 대신해 주는 것이다. 가격 50으로 호출한 뒤 등록된 오류를 출력하면 이렇다.

    FieldError  field=price  rejectedValue=50  bindingFailure=false
  codes=[range.product.price, range.price, range.java.lang.Integer, range]
  arguments=[100, 5000000]
ObjectError
  codes=[totalAmountMax.product, totalAmountMax]

    우리는 range라고만 썼는데 코드가 네 개가 되었다. errors.properties에는 range.product.price만 있는데도 메시지가 정상적으로 나오는 것은 목록의 첫 번째가 바로 그 코드이기 때문이다. 이 목록을 만드는 규칙이 다음 절의 주제다.

    rejectValue가 필드의 현재 값을 실제로 읽는다는 사실에서 한 가지 주의점이 나온다. 존재하지 않는 프로퍼티 이름을 넘기면 값을 읽으려는 시점에 NotReadablePropertyException이 난다. 필드 이름을 문자열로 쓰는 이상 컴파일러는 오타를 잡아 주지 못한다. 대신 실패가 조용히 묻히지 않고 예외로 드러난다.

    오류 코드와 메시지 3: MessageCodesResolver가 코드를 여러 개 만드는 이유

    오류 코드 하나를 메시지 코드 여러 개로 펼치는 일은 MessageCodesResolver가 맡는다. 메서드는 둘이다. 객체 오류용은 오류 코드와 객체 이름을 받고, 필드 오류용은 여기에 필드 이름과 필드 타입을 더 받는다. 기본 구현인 DefaultMessageCodesResolver를 직접 호출해 보자.

    MessageCodesResolver resolver = new DefaultMessageCodesResolver();
System.out.println(Arrays.toString(
        resolver.resolveMessageCodes("required", "product")));
System.out.println(Arrays.toString(
        resolver.resolveMessageCodes("required", "product", "name", String.class)));
System.out.println(Arrays.toString(
        resolver.resolveMessageCodes("required", "order", "lines[0].quantity", Integer.class)));
    [required.product, required]
[required.product.name, required.name, required.java.lang.String, required]
[required.order.lines[0].quantity, required.order.lines.quantity, required.lines[0].quantity, required.lines.quantity, required.quantity, required.java.lang.Integer, required]

    DefaultMessageCodesResolver의 Javadoc이 정한 규칙은 다음과 같다. 순서가 곧 우선순위다.

    대상순서만들어지는 코드예 (required, product, name)
    객체 오류1코드.객체이름required.product
    객체 오류2코드required
    필드 오류1코드.객체이름.필드required.product.name
    필드 오류2코드.필드required.name
    필드 오류3코드.필드타입required.java.lang.String
    필드 오류4코드required

    세 번째 출력처럼 필드 경로에 배열이나 리스트의 인덱스가 있으면 특정 원소용 코드와 컬렉션 전체용 코드가 함께 만들어져 개수가 늘어난다. 필드 타입은 클래스의 전체 이름이고, 기본형이면 int처럼 타입 이름 그대로다.

    이렇게 설계한 이유는 목록의 방향에 있다. 앞쪽은 구체적이고 뒤쪽은 범용적이다. 메시지를 찾을 때 앞에서부터 찾으므로, 구체적인 메시지가 있으면 그것을 쓰고 없으면 범용 메시지로 내려간다. 덕분에 메시지 파일을 층으로 설계할 수 있다. 대부분의 필드는 범용 문구 하나로 처리하고, 문구가 특별해야 하는 필드만 구체적인 코드로 덮어쓴다.

    # 범용: 어느 객체의 어느 필드든
required=필수 값입니다.
range=허용 범위는 {0} ~ {1} 입니다.

# 구체적: 이 객체의 이 필드만
required.product.name=상품 이름을 입력해 주세요.
range.product.price=가격은 {0}원 이상 {1}원 이하로 입력해 주세요.

# 전역 오류
totalAmountMax=가격 × 수량은 {0}원을 넘을 수 없습니다. 현재 {1}원

    이 파일을 두고 수량에 1000을 넣었을 때 메시지가 정해지는 과정을 따라가 보자. rejectValue("quantity", "range", new Object[]{1, 999}, null)이 만든 코드는 range.product.quantity, range.quantity, range.java.lang.Integer, range다. 앞의 셋은 파일에 없고 네 번째 range에서 메시지가 발견된다. 결과는 "허용 범위는 1 ~ 999 입니다."다. 가격은 첫 번째 코드 range.product.price에서 바로 발견되어 "가격은 100원 이상 5,000,000원 이하로 입력해 주세요."가 된다.

    나중에 수량의 문구를 바꾸고 싶다면 range.product.quantity=... 한 줄을 파일에 추가하면 된다. 자바 코드는 건드리지 않는다. 컨트롤러와 검증기는 "범위를 벗어났다"는 사실만 range라는 코드로 말하고, 그 사실을 어떤 문장으로 표현할지는 메시지 파일이 정한다. 오류의 종류와 표현을 분리한 것이다.

    시점도 구분해 두자. 코드 목록은 오류를 등록하는 순간(rejectValue 호출 시)에 만들어져 오류 객체 안에 문자열 배열로 저장된다. 메시지를 실제로 찾는 일은 뷰를 렌더링할 때 일어난다. 따라서 로케일에 따른 언어 선택은 등록 시점이 아니라 렌더링 시점에 정해지고, 같은 오류 객체가 요청의 로케일에 따라 다른 언어의 문구로 풀린다.

    rejectValue의 오류 코드 하나가 네 개의 메시지 코드가 되고, errors.properties에서 위에서부터 차례로 찾아 처음 발견된 것이 선택되는 사다리 구조를 보여 준다. 왼쪽에서 오른쪽으로 세 구역으로 나뉜 평면 벡터 개념도. 왼쪽 구역: 코드 상자 하나에 "rejectValue(\"quantity\", \"range\")". 가운데 구역: 위에서 아래로 쌓인 네 칸짜리 사다리. 위 칸부터 "range.product.quantity", "range.quantity", "range.java.lang.Integer", "range". 사다리 왼쪽에 위에서 아래로 향하는 세로 화살표와 라벨 "구체적 → 범용". 왼쪽 상자에서 사다리로 화살표, 라벨 "MessageCodesResolver". 오른쪽 구역: 문서 모양 아이콘 "errors.properties". 사다리의 위 세 칸에서 문서로 가는 점선 화살표 끝에 작은 X 표시, 맨 아래 칸 "range"에서 문서로 가는 실선 화살표 끝에 체크 표시. 문서 아래에 결과 말풍선 "허용 범위는 1 ~ 999 입니다." 흰 배경, 파란색과 회색 위주, 선택된 칸만 초록색 강조. 메시지 코드는 구체적인 것부터 범용적인 것 순으로 만들어지고, 처음 발견된 메시지가 쓰인다.

    필수 값 검사처럼 자주 반복되는 코드에는 ValidationUtils가 있다. ValidationUtils.rejectIfEmptyOrWhitespace(errors, "name", "required")는 필드 값이 null이거나 빈 문자열이거나 공백뿐이면 rejectValue("name", "required")를 호출해 준다. 앞에서 StringUtils.hasText로 쓴 조건문과 같은 일을 한다.

    오류 코드와 메시지 4: 스프링이 만든 typeMismatch도 같은 길을 간다

    오류를 만드는 주체는 둘이다. 하나는 우리가 쓴 검증 코드이고, 다른 하나는 바인딩 중에 타입 변환 실패를 기록하는 스프링이다. 앞에서 본 것처럼 스프링이 만든 FieldError에도 코드 목록이 들어 있다. 스프링도 typeMismatch라는 오류 코드를 같은 MessageCodesResolver에 통과시켜 등록하기 때문이다.

    [typeMismatch.product.price, typeMismatch.price, typeMismatch.java.lang.Integer, typeMismatch]

    메시지 파일에 이 코드들이 하나도 없으면 탐색은 2단계로 내려가 기본 메시지가 출력된다. 그 기본 메시지는 Failed to convert property value of type 'java.lang.String' to required type 'java.lang.Integer' ...로 시작하는 문장이다. 사용자에게 의미가 없을 뿐 아니라 서버 내부의 클래스 이름을 그대로 노출한다. 우리가 직접 등록한 오류와 같은 방법으로 해결한다. 코드를 고칠 필요 없이 파일에 두 줄을 더한다.

    typeMismatch.java.lang.Integer=숫자를 입력해 주세요.
typeMismatch=형식이 올바르지 않습니다.

    세 번째 순위인 "코드.필드타입"이 여기서 쓸모를 드러낸다. 가격이든 수량이든 Integer 필드의 타입 오류는 모두 "숫자를 입력해 주세요."로 처리되고, 그 밖의 타입은 맨 아래의 범용 문구로 내려간다.

    타입 오류가 컨트롤러까지 오게 되면서 생기는 부작용이 하나 있다. price=abc 요청에서 바인딩이 실패하면 객체의 price는 null로 남는다. 이어서 실행되는 우리 검증 코드는 price == null을 보고 필수 값 오류를 또 등록한다. 한 칸에 메시지가 두 줄 나온다.

    POST price=abc
  getFieldErrorCount("price") = 2      ← typeMismatch + 직접 등록한 오류
  getFieldValue("price") = abc         ← 첫 번째 오류(바인딩 실패)의 거절된 값

    사용자는 숫자가 아닌 값을 넣었을 뿐인데 "숫자를 입력해 주세요."와 "필수 값입니다."를 함께 보게 된다. 두 번째 메시지는 사실과 다르다. 해결책은 필드 검증을 시작하기 전에 그 필드에 이미 오류가 있는지 확인하는 것이다. 바인딩에 실패한 필드는 값 자체가 없으므로 값에 대한 규칙을 따질 대상이 아니다.

    if (!bindingResult.hasFieldErrors("price")) {
    Integer price = product.getPrice();
    if (price == null) {
        bindingResult.rejectValue("price", "required");
    } else if (price < 100 || price > 5_000_000) {
        bindingResult.rejectValue("price", "range", new Object[]{100, 5_000_000}, null);
    }
}

    Validator 분리: 검증 로직을 컨트롤러 밖으로

    컨트롤러 메서드를 다시 보면 대부분이 검증 코드다. 요청을 받아 흐름을 정하는 일(성공하면 저장하고 리다이렉트, 실패하면 폼)과 값이 올바른지 판단하는 일이 한 메서드에 섞여 있다. 수정 폼을 만들면 같은 검증이 한 벌 더 생긴다. 검증을 별도의 클래스로 꺼낸다. 스프링은 이 용도의 인터페이스를 정해 두었다.

    public interface Validator {
    boolean supports(Class clazz);
    void validate(Object target, Errors errors);
}

    supports는 이 검증기가 주어진 클래스의 인스턴스를 검증할 수 있는지 답하고, validate는 객체를 검증해 오류를 Errors에 등록한다. validate가 BindingResult가 아니라 그 상위 인터페이스인 Errors를 받는 점을 보자. rejectValue, reject, hasFieldErrors는 모두 Errors에 정의되어 있어서 검증기는 그것만으로 충분하다. 지금까지의 검증 코드를 그대로 옮긴다.

    @Component
public class ProductValidator implements Validator {

    @Override
    public boolean supports(Class clazz) {
        return Product.class.isAssignableFrom(clazz);
    }

    @Override
    public void validate(Object target, Errors errors) {
        Product product = (Product) target;

        if (!StringUtils.hasText(product.getName())) {
            errors.rejectValue("name", "required");
        }
        if (!errors.hasFieldErrors("price")) {
            Integer price = product.getPrice();
            if (price == null) {
                errors.rejectValue("price", "required");
            } else if (price < 100 || price > 5_000_000) {
                errors.rejectValue("price", "range", new Object[]{100, 5_000_000}, null);
            }
        }
        if (!errors.hasFieldErrors("quantity")) {
            Integer quantity = product.getQuantity();
            if (quantity == null) {
                errors.rejectValue("quantity", "required");
            } else if (quantity < 1 || quantity > 999) {
                errors.rejectValue("quantity", "range", new Object[]{1, 999}, null);
            }
        }
        if (product.getPrice() != null && product.getQuantity() != null) {
            long total = (long) product.getPrice() * product.getQuantity();
            if (total > 50_000_000L) {
                errors.reject("totalAmountMax", new Object[]{50_000_000L, total}, null);
            }
        }
    }
}

    supports의 Product.class.isAssignableFrom(clazz)는 clazz가 Product이거나 그 하위 클래스일 때 true다. equals로 비교하면 하위 클래스의 인스턴스를 거절하게 되므로 보통 이 형태로 쓴다. validate의 파라미터가 Object라서 첫 줄에서 캐스팅을 한다. 이 캐스팅이 안전하다는 보장은 "supports가 true를 돌려준 타입의 객체만 넘긴다"는 호출 쪽의 약속에서 나온다.

    이 검증기는 @Component로 등록한 싱글톤 빈이다. 서블릿 컨테이너의 요청 스레드 여럿이 같은 인스턴스의 validate를 동시에 호출한다. 위 코드가 안전한 이유는 필드가 하나도 없기 때문이다. 검증 대상 객체와 오류 목록은 모두 메서드 인자로 들어오고, price, total 같은 중간값은 각 스레드의 스택에 있는 지역 변수다. 검증기에 "현재 검증 중인 객체"나 "오류 개수" 같은 것을 인스턴스 필드로 두면 요청끼리 값이 섞인다. 반대로 BindingResult는 요청마다, 인자마다 새로 만들어지는 객체라서 한 요청의 스레드만 접근한다.

    컨트롤러는 검증기를 주입받아 한 줄로 호출한다.

    @PostMapping("/add")
public String add(@ModelAttribute Product product, BindingResult bindingResult) {
    productValidator.validate(product, bindingResult);

    if (bindingResult.hasErrors()) {
        return "products/addForm";
    }
    Product saved = productStore.save(product);
    return "redirect:/products/" + saved.getId();
}

    이것만으로 컨트롤러는 흐름만 남고, 수정 폼도 같은 검증기를 재사용한다. 그런데 이렇게 직접 부를 것이라면 굳이 스프링의 Validator 인터페이스를 구현할 이유가 없다. 아무 클래스의 아무 메서드여도 같은 일을 할 수 있다. 인터페이스를 맞추는 이유는 스프링이 대신 호출하게 만들 수 있기 때문이다.

    WebDataBinder, @InitBinder, @Validated: 프레임워크가 검증기를 부르게 하기

    앞에서 resolveArgument의 순서를 적을 때 5번이 "검증 애노테이션이 있으면 바인더에 등록된 검증기를 실행한다"였다. 바인딩과 검증은 원래 한 객체, WebDataBinder의 일이다. 바인더에 검증기를 등록해 두고 파라미터에 표시만 하면 바인딩 직후에 검증이 자동으로 이어진다.

    @Controller
@RequestMapping("/products")
public class ProductFormController {

    private final ProductStore productStore;
    private final ProductValidator productValidator;

    public ProductFormController(ProductStore productStore, ProductValidator productValidator) {
        this.productStore = productStore;
        this.productValidator = productValidator;
    }

    @InitBinder("product")
    void initBinder(WebDataBinder binder) {
        binder.addValidators(productValidator);
    }

    @PostMapping("/add")
    public String add(@Validated @ModelAttribute Product product, BindingResult bindingResult,
                      RedirectAttributes redirectAttributes) {
        if (bindingResult.hasErrors()) {
            return "products/addForm";
        }
        Product saved = productStore.save(product);
        redirectAttributes.addAttribute("productId", saved.getId());
        return "redirect:/products/{productId}";
    }
}

    컨트롤러 메서드에서 검증기를 호출하는 줄이 사라졌다. 요청 하나가 처리되는 순서는 다음과 같다.

    검증기가 바인딩과 같은 BindingResult에 오류를 쌓는다는 점이 핵심이다. 그래서 검증기 안의 errors.hasFieldErrors("price")가 바인딩 단계에서 생긴 타입 오류를 볼 수 있다. 완성된 컨트롤러에 요청 다섯 개를 보낸 결과다.

    요청 파라미터등록된 오류(첫 번째 코드)화면 메시지

    첫 번째 줄에서 오류의 순서가 바인딩 오류 먼저, 검증 오류 나중인 것도 처리 순서 그대로다. 실험은 Spring Framework 7.0.10의 MockMvc로 돌렸고, 메시지는 앞 절의 errors.properties 내용을 한국어 로케일로 풀었다.

    @Validated가 하는 일, 빠뜨렸을 때 생기는 일

    @Validated는 그 자체로 검증을 수행하지 않는다. 인자 해석기가 "이 파라미터는 바인딩 뒤에 검증까지 하라"는 표시로 읽을 뿐이다. 해석기는 파라미터의 애노테이션을 훑어 스프링의 @Validated, Jakarta Validation의 jakarta.validation.Valid, 또는 이름이 Valid로 시작하는 애노테이션이 있으면 binder.validate()를 호출한다. 여기서는 둘 중 어느 것을 써도 결과가 같다. @Valid는 Jakarta Validation API가 클래스패스에 있어야 쓸 수 있고, 그 의존성과 두 애노테이션의 차이는 05회에서 다룬다.

    표시이므로 빠뜨려도 컴파일 오류나 예외가 나지 않는다. @InitBinder로 검증기를 등록해 두고 @Validated를 잊으면 @InitBinder는 호출되지만 검증기는 호출되지 않고, bindingResult.hasErrors()는 타입 오류가 없는 한 false다. 잘못된 값이 조용히 저장된다. 검증 실패 경로를 테스트해야 하는 또 하나의 이유다.

    @InitBinder의 적용 범위와 버전에 따른 차이

    WebDataBinder는 싱글톤이 아니다. 요청마다, 그리고 바인딩이 필요한 인자마다 새로 만들어지고, 만들어질 때마다 @InitBinder 메서드가 호출된다. @InitBinder에 이름을 주지 않으면 그 컨트롤러에서 만들어지는 모든 바인더에 적용된다. 다른 타입의 모델 객체를 위한 바인더에도 ProductValidator가 등록된다는 뜻이다.

    이때 무슨 일이 생기는지는 버전에 따라 다르다. DataBinder.addValidators는 대상 객체가 이미 있을 때 supports를 호출해 보고, false면 IllegalStateException(Invalid target for Validator)을 던진다. Spring Framework 6.0까지는 객체를 먼저 만들고 바인더를 만들었으므로 @InitBinder 시점에 대상이 있었고, 맞지 않는 타입이면 이 예외로 바로 드러났다. 6.1부터는 바인더를 먼저 만들고 그 바인더가 객체를 생성하므로 @InitBinder 시점의 대상은 null이고 이 확인이 건너뛰어진다. 이후 binder.validate()는 등록된 검증기의 validate를 supports 확인 없이 호출한다. 7.0.10에서 이름 없는 @InitBinder로 ProductValidator를 등록하고 다른 타입의 인자에 @Validated를 붙여 요청을 보내면 supports는 한 번도 호출되지 않고, validate 첫 줄의 캐스팅에서 ClassCastException이 난다.

    어느 버전이든 대응은 같다. 특정 타입 전용 검증기는 @InitBinder("product")처럼 모델 속성 이름을 지정해 그 바인더에만 등록한다. 위 컨트롤러가 그렇게 한 이유다.

    모든 컨트롤러에 적용되는 전역 검증기는 WebMvcConfigurer.getValidator()를 구현해 지정한다. 다만 스프링 MVC는 Bean Validation이 클래스패스에 있으면 그 검증기(LocalValidatorFactoryBean)를 기본 전역 검증기로 등록하는데, getValidator()가 돌려준 검증기는 이 자리를 차지한다. 전역 검증기를 직접 지정할 일은 드물고, 05회의 Bean Validation이 그 자리를 그대로 쓴다.

    흔한 오해와 함정, 그리고 다음 회차와의 연결

    이 회차의 내용에서 자주 틀리는 지점을 모아 둔다.

    • "BindingResult는 @ModelAttribute 뒤 어딘가에만 있으면 된다." 바로 다음 파라미터여야 한다. 사이에 다른 파라미터가 끼면 정상 입력에서는 동작하고 바인딩·검증 오류가 있을 때만 400이 된다.
    • "BindingResult가 있으면 타입 오류 때 컨트롤러가 호출되지 않는다." 반대다. 호출되며, 실패한 필드는 대입되지 않은 채(보통 null) 넘어온다. 그 값을 그대로 저장하지 않도록 hasErrors() 확인이 저장보다 앞에 있어야 한다.
    • "오류가 있으면 폼 화면으로 리다이렉트하면 된다." 리다이렉트는 새 요청이다. 모델에 있던 객체와 BindingResult가 함께 사라져 입력값도 메시지도 보이지 않는다.
    • "FieldError에 메시지만 넣으면 충분하다." 거절된 값을 넣지 않으면 오류가 난 칸의 입력값이 사라진다. rejectValue를 쓰면 이 값이 자동으로 채워진다.
    • "메시지 코드는 내가 쓴 문자열 하나다." 등록되는 것은 코드 목록이고, 메시지 파일에서 구체적인 것부터 탐색된다. 어느 코드에도 메시지가 없고 기본 메시지도 없으면 렌더링 중에 예외가 난다.
    • "Validator를 빈으로 등록하면 자동으로 적용된다." 바인더에 등록하고(@InitBinder 또는 전역 설정), 파라미터에 @Validated나 @Valid를 붙여야 호출된다.

    이 회차에서 세운 구조는 뒤의 회차들이 그대로 올라타는 바닥이다. 05회의 Bean Validation은 @NotBlank, @Range 같은 애노테이션으로 규칙을 선언하게 해 주지만, 그 결과는 결국 같은 BindingResult에 FieldError로 등록되고 같은 MessageCodesResolver를 거친 코드 목록을 갖는다. 오류 코드가 required 대신 애노테이션 이름이 될 뿐이다. BindingResult가 없을 때 던져지는 예외와 400 응답이 어떤 화면이나 JSON으로 바뀌는지는 08회와 09회에서 예외 처리 흐름으로 다룬다. "abc"를 Integer로 바꾸려다 실패한 그 변환 단계를 확장하는 방법, 곧 문자열을 임의의 타입으로 바꾸는 컨버터와 포매터는 10회의 주제다.
    서버 검증과 세 종류의 검증
    클라이언트 검증은 편의이고 서버 검증은 생략할 수 없는 관문이다. 타입 검증은 바인딩 도중에, 필드 검증과 객체(전역) 검증은 바인딩이 끝난 뒤에 이루어진다.
    실패 응답의 형태
    검증에 실패한 POST는 리다이렉트하지 않고 같은 요청 안에서 폼을 다시 그린다. 입력값과 오류가 요청 범위의 모델에 있기 때문이다.
    BindingResult
    바인딩과 검증의 오류를 모으는 객체다. 검증 대상 바로 다음 파라미터로 선언하면 바인딩 오류가 예외 대신 이 객체에 담겨 컨트롤러가 호출되고, org.springframework.validation.BindingResult.객체이름 키로 모델에도 들어간다.
    FieldError와 ObjectError
    필드 하나의 오류와 객체 전체의 오류를 표현한다. FieldError의 거절된 값이 폼에 다시 표시되므로, 객체에 담지 못한 잘못된 입력도 보존된다.
    rejectValue와 reject
    BindingResult가 대상 객체를 알고 있으므로 필드 이름과 오류 코드만으로 거절된 값과 메시지 코드 목록을 채워 오류를 등록한다.
    MessageCodesResolver
    오류 코드 하나를 "코드.객체.필드 → 코드.필드 → 코드.타입 → 코드" 순의 메시지 코드 목록으로 펼친다. 메시지는 앞에서부터 찾으므로 구체적인 문구가 범용 문구를 덮는다.
    typeMismatch
    타입 변환 실패 시 스프링이 등록하는 오류 코드다. 같은 규칙으로 코드 목록이 만들어지므로 메시지 파일에 정의하면 기본 영어 메시지 대신 출력된다.
    Validator와 WebDataBinder
    Validator 구현을 @InitBinder에서 바인더에 등록하고 파라미터에 @Validated를 붙이면, 바인딩 직후 같은 BindingResult를 대상으로 검증기가 호출된다.

    실무에서 검증 문제는 대개 "검증을 안 했다"가 아니라 "검증이 실패하는 경로를 확인하지 않았다"에서 나온다. 이 회차에서 본 결함들의 공통점이 그것이다. BindingResult의 위치가 한 칸 밀린 컨트롤러, @Validated를 빠뜨린 파라미터, 오타가 난 메시지 코드, 캐스팅 없는 int 곱셈은 모두 정상 입력에서는 아무 문제 없이 동작한다. 잘못된 입력이 들어왔을 때만 400이 나거나, 잘못된 데이터가 저장되거나, 화면 렌더링이 실패한다. 폼 하나를 만들 때 타입 오류, 빈 값, 범위 초과, 복합 규칙 위반을 각각 보내 보는 테스트를 함께 두는 것이 가장 값싼 방어다.

    검증을 어느 계층에 둘지는 한 가지 답으로 정해지지 않는다. 여기서 다룬 것은 웹 계층의 입력 형식 검증이다. 값이 비었는가, 범위 안인가 같은 판단은 요청 객체만 보고 끝낼 수 있어 컨트롤러 진입 시점에 하는 것이 맞다. 반면 "같은 이름의 상품이 이미 있는가", "재고가 충분한가"처럼 저장소의 현재 상태에 달린 규칙은 성격이 다르다. 검증 시점과 저장 시점 사이에 다른 요청이 끼어들 수 있으므로 Validator에서 조회로 확인하는 것만으로는 보장되지 않고, 트랜잭션과 데이터베이스의 유일 제약 같은 장치가 최종 방어선이 된다. 웹 계층의 검증은 사용자에게 친절한 메시지를 일찍 주기 위한 것이고, 데이터의 무결성은 더 안쪽 계층이 책임진다고 보는 편이 안전하다.

    메시지 코드의 계층 설계는 처음에는 과해 보이지만 폼이 수십 개로 늘면 차이가 난다. 범용 코드(required, range, typeMismatch)의 문구를 먼저 갖춰 두면 새 폼은 메시지 파일을 건드리지 않고도 최소한의 안내를 내보낼 수 있고, 기본 메시지도 코드도 없어서 렌더링이 실패하는 사고를 막는다. 구체적인 코드는 기획에서 문구를 지정한 필드에만 추가한다. 반대로 모든 필드에 구체적인 코드를 하나씩 만들기 시작하면 메시지 파일이 필드 수만큼 불어나고 누락이 곧 장애가 된다.

    서버 검증(server-side validation)
    서버가 요청을 받은 뒤 수행하는 검증. HTTP 메시지는 누구나 만들 수 있으므로 클라이언트 검증 여부와 관계없이 반드시 필요하다.
    데이터 바인딩(data binding)
    문자열인 요청 파라미터를 대상 객체의 프로퍼티 타입으로 변환해 채워 넣는 과정. 스프링에서는 DataBinder(웹에서는 WebDataBinder)가 맡는다.
    BindingResult
    특정 객체에 대한 바인딩·검증 오류를 담는 인터페이스. Errors를 확장하며, 대상 객체와 객체 이름을 알고 있다.
    FieldError / ObjectError
    필드 하나에 대한 오류와 객체 전체에 대한 오류(전역 오류)를 표현하는 클래스. 둘 다 메시지 코드 목록, 인자, 기본 메시지를 가진다.
    거절된 값(rejected value)
    FieldError가 보관하는, 오류를 일으킨 원래 입력값. 폼을 다시 그릴 때 입력 칸에 표시된다.
    MessageCodesResolver
    오류 코드 하나를 구체적인 것부터 범용적인 것 순서의 메시지 코드 목록으로 바꾸는 전략 인터페이스. 기본 구현은 DefaultMessageCodesResolver다.
    typeMismatch
    바인딩 중 타입 변환에 실패했을 때 스프링이 등록하는 오류 코드.
    Validator
    스프링의 검증기 인터페이스. supports(Class)로 지원 타입을 밝히고 validate(Object, Errors)로 오류를 등록한다.
    @InitBinder
    컨트롤러에서 WebDataBinder가 만들어질 때마다 호출되어 바인더를 초기화하는 메서드에 붙이는 애노테이션. 이름을 지정하면 그 모델 속성의 바인더에만 적용된다.
    @Validated
    컨트롤러 파라미터에 붙여 바인딩 뒤에 검증기를 실행하도록 표시하는 스프링 애노테이션.
