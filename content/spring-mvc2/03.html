    문구가 HTML에 박혀 있으면 생기는 일

    도서 대여점의 관리 화면을 만든다고 하자. 목록 화면, 등록 폼, 수정 폼, 상세 화면에 모두 "제목", "대여료", "저장" 같은 문구가 들어간다. 이 문구를 템플릿마다 직접 적어 두면 처음에는 아무 문제가 없다. 문제는 기획이 "대여료"를 "하루 대여료"로 바꾸자고 하는 날 시작된다. 네 개 화면, 열 군데가 넘는 위치를 사람이 찾아 고쳐야 하고, 한 곳을 빠뜨리면 화면마다 용어가 달라진다.

    원인은 같은 뜻의 문구가 여러 곳에 값으로 복사되어 있다는 데 있다. 프로그래밍에서 이런 중복을 없애는 방법은 늘 같다. 값에 이름을 붙이고, 쓰는 쪽은 이름만 참조하게 한다. 상수를 뽑는 것과 같은 발상이다. 화면 문구에 이 발상을 적용한 것이 메시지(message) 기능이다. 문구를 label.book.price=대여료처럼 키와 값으로 한 파일에 모아 두고, 템플릿은 키 label.book.price만 적는다.

    문구가 한 파일에 모이면 두 번째 이득이 따라온다. 그 파일을 언어별로 여러 벌 두고, 요청을 보낸 사용자에 맞는 벌을 골라 쓰면 같은 템플릿으로 한국어 화면과 영어 화면을 모두 만들 수 있다. 이것이 국제화(internationalization)다. 단어가 길어서 첫 글자 i와 마지막 글자 n 사이의 글자 수 18을 넣어 i18n이라고 줄여 쓴다. 국제화는 프로그램이 여러 언어·지역을 수용할 수 있는 구조를 갖추는 일이고, 특정 언어의 번역본과 형식을 실제로 채워 넣는 일은 지역화(localization, l10n)라고 구분해 부른다.

    문구를 값으로 복사한 구조와 키로 간접 참조하는 구조를 좌우로 나란히 보여 주고, 간접 참조 쪽에서 로케일이 파일을 고르는 스위치 역할을 한다는 점을 드러낸다. 깔끔한 평면 벡터 다이어그램, 흰 배경, 좌우 2분할. 왼쪽 패널 제목 "직접 적기": 세로로 놓인 문서 아이콘 네 개, 각 문서 안에 같은 글자 "대여료"가 적혀 있고 문서마다 빨간 연필 아이콘이 붙어 있다. 오른쪽 패널 제목 "키로 참조하기": 같은 문서 아이콘 네 개에서 화살표 네 개가 가운데의 작은 상자 "label.book.price"로 모이고, 그 상자에서 갈림길 스위치를 거쳐 두 개의 파일 카드로 화살표가 나간다. 위 카드 라벨 "messages.properties", 카드 안 글자 "대여료". 아래 카드 라벨 "messages_en.properties", 카드 안 글자 "Rental fee". 스위치 옆에 라벨 "로케일". 색은 파랑과 회색 위주, 스위치만 주황색으로 강조. 그 밖의 글자는 넣지 않는다. 메시지 기능은 문구에 이름을 붙여 한곳에 모으는 간접 참조이고, 국제화는 그 참조가 로케일에 따라 다른 파일로 향하게 하는 것이다.

    이 회차에서 볼 것은 세 층이다. 맨 아래에는 JDK가 제공하는 ResourceBundle과 MessageFormat이 있고, 그 위에 스프링의 MessageSource가 있으며, 맨 위에 웹 요청에서 로케일을 뽑아내는 LocaleResolver와 타임리프의 #{...} 표현식이 있다. 위층의 동작 대부분은 아래층의 규칙을 그대로 물려받은 것이라서, 아래에서부터 올라가면 "왜 영어가 나오지?", "왜 작은따옴표가 사라지지?" 같은 증상의 원인을 구조에서 바로 찾을 수 있다.

    프로젝트 설정: 실습에 필요한 뼈대

    실습에는 스프링 부트 3.x 웹 프로젝트 하나면 충분하다. 웹 MVC와 타임리프 스타터가 있으면 메시지 기능에 필요한 클래스는 모두 들어온다. MessageSource는 spring-context에, LocaleResolver는 spring-webmvc에 있고 둘 다 웹 스타터가 끌어온다. 메시지 기능을 위해 따로 추가할 라이브러리는 없다.

    dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-thymeleaf'
    testImplementation 'org.springframework.boot:spring-boot-starter-test'
}

    화면은 이 권의 앞 회차와 MVC 1편에서 만들던 것과 같은 종류의 관리 화면이면 된다. 여기서는 도서 한 권이 제목과 대여료를 갖는 작은 도서 관리 화면을 가정한다. 메시지 파일은 클래스패스 루트, 곧 src/main/resources 바로 아래에 둔다. 파일 이름에는 규칙이 있어서 기본 이름(basename) 뒤에 밑줄과 로케일을 붙인다.

    로케일: 언어와 지역을 가리키는 값

    국제화의 모든 단계는 "이 요청은 어느 언어·지역의 사용자가 보냈는가"라는 값 하나를 주고받는다. 자바에서 이 값은 java.util.Locale 객체다. 로케일(locale)은 언어(language), 문자 체계(script), 국가·지역(country), 변형(variant)으로 이루어지고, 보통은 언어와 국가 두 부분만 쓴다. Locale.KOREAN은 언어만 있는 ko이고 Locale.KOREA는 언어와 국가가 모두 있는 ko_KR이다. 둘은 서로 다른 객체이며 equals로 비교하면 다르다.

    로케일을 글자로 적는 방식은 두 가지를 구분해야 한다. Locale.toString()은 ko_KR처럼 밑줄로 잇고, 메시지 파일 이름의 접미사가 이 형식을 따른다. HTTP 헤더에 쓰는 언어 태그(language tag)는 ko-KR처럼 하이픈으로 잇는다. 같은 로케일이 파일 이름에서는 messages_ko_KR.properties, 헤더에서는 Accept-Language: ko-KR로 나타나는 이유다.

    또 하나 기억할 값이 JVM 기본 로케일이다. Locale.getDefault()가 돌려주는 값으로, JVM이 시작할 때 운영체제의 설정에서 정해진다. -Duser.language=en -Duser.country=US 같은 시스템 프로퍼티로 바꿔서 시작할 수도 있다. 이 값은 "요청한 사람"과 아무 관계가 없고 "서버가 떠 있는 기계"의 설정이다. 그런데도 메시지 조회 결과에 끼어드는 경우가 있어서, 개발자 PC에서는 한국어가 나오던 화면이 서버에서는 영어로 나오는 일이 생긴다. 이 문제는 뒤에서 실험으로 재현한다.

    한 층 아래: JDK의 ResourceBundle이 파일을 고르는 규칙

    스프링이 기본으로 쓰는 메시지 구현체는 JDK의 java.util.ResourceBundle 위에 얹혀 있다. 그러니 "어느 파일의 값이 선택되는가"의 규칙은 스프링이 아니라 JDK가 정한 것이다. ResourceBundle.getBundle("messages", locale)을 호출하면 JDK는 주어진 로케일에서 후보 로케일 목록을 만든다. 가장 구체적인 것에서 시작해 한 부분씩 떼어 내고, 마지막은 아무것도 없는 루트 로케일이다.

    실험용으로 파일 세 개를 만들자. 일부러 키가 조금씩 빠져 있다.

    hello=안녕
hello.name=안녕 {0}

    import java.text.MessageFormat;
import java.util.Locale;
import java.util.ResourceBundle;

public class BundleLab {
    public static void main(String[] args) {
        ResourceBundle.Control control =
                ResourceBundle.Control.getControl(ResourceBundle.Control.FORMAT_PROPERTIES);
        System.out.println(control.getCandidateLocales("messages", Locale.US));

        for (Locale locale : new Locale[]{Locale.US, Locale.UK, Locale.KOREA}) {
            ResourceBundle bundle = ResourceBundle.getBundle("messages", locale);
            System.out.println(locale + " -> [" + bundle.getLocale() + "] "
                    + bundle.getString("hello") + " / " + bundle.getString("only.default"));
        }

        System.out.println(MessageFormat.format("가격은 {0}원", 10000));
        System.out.println(MessageFormat.format("가격은 {0}원", "10000"));
        System.out.println(MessageFormat.format("It's {0}", "x"));
        System.out.println(MessageFormat.format("It''s {0}", "x"));
        System.out.println(MessageFormat.format("{1}가 {0}에게", "철수", "영희"));
    }
}

    첫 줄이 후보 목록이다. en_US를 요청하면 후보는 en_US, en, 그리고 빈 문자열로 찍힌 루트 로케일 세 개다. JDK는 이 순서대로 messages_en_US.properties, messages_en.properties, messages.properties를 찾는다. 둘째 줄을 보면 en_US 요청에는 messages_en_US가 선택되어 hello(US)가 나왔다.

    그런데 같은 줄의 only.default는 messages_en_US에도, messages_en에도 없는 키인데 값이 나왔다. 이것이 부모 체인(parent chain)이다. JDK는 선택한 번들 하나만 쓰는 것이 아니라, 후보 목록의 나머지 번들을 부모로 줄줄이 연결해 둔다. getString은 먼저 자기 번들에서 키를 찾고, 없으면 부모에게 묻고, 또 없으면 그 부모에게 묻는다. 그래서 언어별 파일에는 기본 파일과 달라지는 키만 적어도 되고, 빠진 키는 기본 파일의 값으로 채워진다.

    getBundle("messages", en_US)가 만든 체인

  messages_en_US  ──parent──▶  messages_en  ──parent──▶  messages (루트)
  hello=hello(US)              hello=hello               hello=안녕
                               hello.name=hello {0}      hello.name=안녕 {0}
                               price=price: {0}          price=가격은 {0}원
                                                         only.default=기본에만 있음

  getString("hello")         → 첫 번들에서 발견            → hello(US)
  getString("price")         → 첫 번들에 없음 → 부모에서 발견 → price: {0}
  getString("only.default")  → 두 번 올라가 루트에서 발견   → 기본에만 있음
  getString("nope")          → 끝까지 없음                → MissingResourceException
    후보 로케일 목록이 세 개의 번들 체인이 되고, 키마다 체인의 서로 다른 지점에서 값이 발견된다는 것을 보여 준다. 깔끔한 평면 벡터 다이어그램, 흰 배경. 왼쪽에서 오른쪽으로 카드 세 장이 가로로 놓여 있고 카드 사이에 "부모" 라벨이 붙은 화살표가 오른쪽을 향한다. 첫 카드 제목 "messages_en_US", 둘째 카드 제목 "messages_en", 셋째 카드 제목 "messages". 첫 카드에는 줄 하나, 둘째 카드에는 줄 셋, 셋째 카드에는 줄 넷이 회색 막대로 그려져 있다(실제 글자 대신 막대). 카드 아래쪽에 조회 화살표 세 개: 초록 화살표는 첫 카드에서 멈추고 라벨 "hello", 파란 화살표는 첫 카드를 지나 둘째 카드에서 멈추고 라벨 "price", 주황 화살표는 첫째와 둘째 카드를 지나 셋째 카드에서 멈추고 라벨 "only.default". 맨 위에 작은 라벨 "요청 로케일 en_US". 그 밖의 글자는 넣지 않는다. 언어별 번들은 덜 구체적인 번들을 부모로 갖는다. 자기에게 없는 키는 부모가 답하므로, 언어별 파일에는 달라지는 키만 적으면 된다.

    en_GB(영국 영어) 요청은 messages_en_GB가 없으므로 다음 후보 messages_en이 선택되었다. 출력의 대괄호 안이 실제로 선택된 번들의 로케일이다. ko_KR 요청은 messages_ko_KR도 messages_ko도 없어서 루트인 messages가 선택되었고 대괄호 안이 비어 있다. 한국어를 기본 파일에 적어 둔 구성에서는 이것이 의도한 결과다.

    여기에 규칙이 하나 더 있고, 이것이 함정의 뿌리다. JDK는 요청 로케일의 후보에서 루트 말고는 아무 번들도 찾지 못하면, 바로 루트를 쓰지 않고 JVM 기본 로케일로 후보 목록을 다시 만들어 한 번 더 찾는다. Java SE API 문서는 이 단계를 기본 컨트롤의 getFallbackLocale이 현재 기본 로케일을 돌려주고, 그 로케일로 후보를 다시 만들어 찾는다고 설명한다. 루트 번들은 그래도 못 찾았을 때의 마지막 선택이다. 위 실행에서는 JVM 기본 로케일이 ko_KR이라 다시 찾아도 결과가 같았을 뿐이다. 기본 로케일이 en_US인 기계라면 ko_KR 요청이 messages_en_US로 빠진다.

    properties 파일의 인코딩: Java SE 21의 PropertyResourceBundle 문서에 따르면 입력 스트림으로 읽는 properties 번들은 UTF-8로 읽고, 잘못된 바이트열을 만나면 ISO-8859-1로 다시 읽는다. 위 실험의 한글이 변환 없이 읽힌 이유다. 다만 스프링의 메시지 구현체는 파일을 읽는 부분을 자기 코드로 바꿔 두었기 때문에 이 규칙이 그대로 적용되지 않는다. 그 차이는 메시지 소스 설정에서 다룬다.

    MessageFormat: {0}이 값으로 바뀌는 규칙

    번들에서 꺼낸 값은 아직 안녕 {0} 같은 패턴이다. 여기에 인자를 끼워 완성된 문장을 만드는 것은 java.text.MessageFormat의 일이다. {0}, {1}은 인자 배열의 인덱스다. 위 실행 결과의 마지막 줄처럼 패턴이 {1}가 {0}에게이면 두 번째 인자가 먼저 나온다. 번역하면 어순이 바뀌는 문장도 인자 순서를 바꾸지 않고 패턴만 고쳐서 대응할 수 있다는 뜻이고, 문장을 자바 코드에서 +로 이어 붙이면 안 되는 이유이기도 하다.

    인자의 타입이 결과를 바꾼다는 점은 자주 놓친다. {0}에 정수 10000을 넣으면 10,000이 되고, 문자열 "10000"을 넣으면 10000 그대로다. MessageFormat은 인자가 숫자면 로케일에 맞는 숫자 형식을 적용하고, 문자열이면 그대로 붙인다. 숫자 형식은 로케일마다 달라서 같은 값이 독일 로케일에서는 10.000으로 찍힌다. 주문 번호나 우편번호처럼 숫자 모양이지만 수량이 아닌 값을 숫자 타입으로 넘기면 쉼표가 끼어들므로, 그런 값은 문자열로 넘기거나 패턴에 {0,number,#}처럼 형식을 명시한다.

    가장 유명한 함정은 작은따옴표다. MessageFormat 패턴에서 작은따옴표는 "여기부터는 패턴 문법으로 해석하지 말라"는 인용 기호다. 그래서 It's {0}이라는 패턴은 ' 뒤의 s {0} 전체가 인용된 글자로 취급되고, 따옴표 자신은 출력에서 사라져 Its {0}이 된다. 닫는 따옴표가 없으면 패턴 끝에서 닫힌 것으로 본다는 것도 API 문서에 적혀 있다. 작은따옴표 글자 자체를 출력하려면 It''s {0}처럼 두 번 적는다. 영어 메시지에 아포스트로피가 흔하기 때문에 영어 번역 파일을 추가한 직후에 자주 만나는 문제다.

    마지막으로 MessageFormat 객체는 스레드 안전하지 않다. API 문서가 "여러 스레드가 동시에 접근하면 외부에서 동기화해야 한다"고 명시한다. 패턴을 해석하는 비용이 있으니 객체를 재사용하고 싶지만, 요청 스레드 여럿이 하나를 같이 쓰면 깨질 수 있다는 뜻이다. 스프링이 이 둘을 어떻게 양립시키는지는 조금 뒤에서 본다.

    스프링 메시지 소스 설정

    스프링은 메시지 조회를 MessageSource라는 인터페이스로 추상화한다. 메서드는 사실상 "코드, 인자, 로케일을 주면 문자열을 돌려준다" 하나이고, 기본 메시지를 받는 변형과 MessageSourceResolvable 객체를 받는 변형이 더 있다. 구현체는 스프링 레퍼런스가 세 가지를 든다. JDK ResourceBundle에 얹힌 ResourceBundleMessageSource, 클래스패스 밖의 파일도 읽고 변경된 파일을 다시 읽어 들일 수 있는 ReloadableResourceBundleMessageSource, 코드로 메시지를 넣는 StaticMessageSource다.

    직접 등록한다면 다음과 같다. 주의할 것은 빈 이름이다. ApplicationContext는 그 자체가 MessageSource이기도 한데, 컨텍스트가 초기화될 때 이름이 정확히 messageSource인 빈을 찾아 메시지 조회를 그 빈에 위임한다. 그런 빈이 없으면 아무 메시지도 갖지 않은 DelegatingMessageSource를 대신 만들어 둔다. 그래서 다른 이름으로 등록하면 오류 없이 시작하지만 컨텍스트를 통한 메시지 조회는 전부 실패한다.

    import org.springframework.context.MessageSource;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.context.support.ResourceBundleMessageSource;

@Configuration
public class MessageConfig {

    @Bean
    public MessageSource messageSource() {   // 메서드 이름이 곧 빈 이름이다
        ResourceBundleMessageSource messageSource = new ResourceBundleMessageSource();
        messageSource.setBasenames("messages", "errors");
        messageSource.setDefaultEncoding("UTF-8");
        return messageSource;
    }
}

    setBasenames에는 기본 이름을 여러 개 줄 수 있고, 앞에 적은 것부터 차례로 찾는다. 기본 이름은 JDK ResourceBundle의 관례를 따르므로 점은 패키지 구분자로 해석된다. config.i18n.messages라고 적으면 클래스패스의 config/i18n/messages.properties를 가리킨다.

    setDefaultEncoding("UTF-8")은 빼면 안 되는 줄이다. ResourceBundleMessageSource는 클래스패스의 properties 파일을 자기가 직접 열어 읽는데, 이때 쓰는 문자 집합의 기본값이 ISO-8859-1이다. 클래스의 Javadoc이 이 기본값을 밝히면서 UTF-8로 바꾸는 것을 고려하라고 적어 두었다. 이 줄을 빼고 UTF-8로 저장한 한글 파일을 읽으면 어떻게 되는지 직접 돌려 보면 다음과 같다.

    UTF-8로 저장된 "안녕"의 바이트 :  EC 95 88 EB 85 95
읽어 들인 문자열의 길이       :  6
읽어 들인 문자열의 코드 포인트 :  U+00EC U+0095 U+0088 U+00EB U+0085 U+0095

    "안녕"은 UTF-8에서 글자당 3바이트, 합쳐서 6바이트다. ISO-8859-1은 바이트 하나를 글자 하나로 읽는 인코딩이라 6바이트가 6글자가 되었고, 각 글자의 코드 포인트가 원래 바이트 값과 똑같다. 이 가운데 U+0095, U+0088, U+0085는 보이는 글자가 아닌 제어 문자이므로, 화면에는 원래 글자와 무관한 문자가 나오거나 일부가 보이지 않는다. 깨진 글자가 "원래 글자 수의 세 배쯤 되는 서유럽 문자"라면 UTF-8 바이트를 1바이트 인코딩으로 읽었다는 신호다. 이 지식은 메시지 파일만이 아니라 HTTP 본문, DB 연결, 로그 파일에서도 그대로 쓰인다.

    스프링 부트의 자동 설정

    스프링 부트를 쓰면 위 설정 클래스를 만들 필요가 없다. 부트의 MessageSourceAutoConfiguration이 ResourceBundleMessageSource를 messageSource라는 이름으로 등록해 준다. 설정은 spring.messages.* 프로퍼티로 바꾼다. 스프링 부트 3.5 소스의 MessageSourceProperties에서 확인한 기본값은 다음과 같다.

    프로퍼티기본값뜻
    spring.messages.basenamemessages기본 이름. 쉼표로 여러 개를 줄 수 있다
    spring.messages.encodingUTF-8파일을 읽는 문자 집합. 부트가 ISO-8859-1 대신 UTF-8을 넣어 준다
    spring.messages.fallback-to-system-localetrue요청 로케일의 파일이 없을 때 JVM 기본 로케일의 파일을 먼저 찾을지
    spring.messages.cache-duration지정 없음번들 캐시 유지 시간. 지정하지 않으면 한 번 읽은 번들을 계속 쓴다
    spring.messages.always-use-message-formatfalse인자가 없는 메시지도 MessageFormat으로 해석할지
    spring.messages.use-code-as-default-messagefalse메시지를 못 찾으면 예외 대신 코드 자체를 돌려줄지

    자동 설정에는 조건이 두 개 붙어 있다. 첫째, 이름이 messageSource인 빈을 개발자가 이미 등록했으면 물러난다. 둘째, 설정된 기본 이름의 기본 파일이 클래스패스에 있어야 적용된다. 부트 레퍼런스는 번들에 언어별 파일만 있다면 기본 파일을 추가해야 한다고 명시한다. messages_ko.properties와 messages_en.properties만 만들고 messages.properties를 만들지 않으면 자동 설정이 통째로 꺼지고, 컨텍스트는 빈 DelegatingMessageSource를 쓰게 되어 모든 메시지 조회가 실패한다. 내용이 없더라도 기본 파일은 반드시 둔다.

    spring.messages.basename=messages,config.i18n.messages
spring.messages.fallback-to-system-locale=false

    이제 MessageSource를 직접 호출해 보자. 앞에서 만든 파일 세 개에 작은따옴표 실험용 키 세 개를 기본 파일에 더한다.

    quote=It's {0}
quote2=It''s {0}

    import java.util.Locale;
import org.springframework.context.NoSuchMessageException;
import org.springframework.context.support.ResourceBundleMessageSource;

public class MessageSourceLab {
    public static void main(String[] args) {
        ResourceBundleMessageSource ms = new ResourceBundleMessageSource();
        ms.setBasenames("messages");
        ms.setDefaultEncoding("UTF-8");

        System.out.println(ms.getMessage("hello", null, null));                               // 1
        System.out.println(ms.getMessage("hello", null, Locale.KOREA));                       // 2
        System.out.println(ms.getMessage("hello", null, Locale.ENGLISH));                     // 3
        System.out.println(ms.getMessage("hello", null, Locale.US));                          // 4
        System.out.println(ms.getMessage("only.default", null, Locale.US));                   // 5
        System.out.println(ms.getMessage("hello.name", new Object[]{"Spring"}, Locale.KOREA)); // 6
        System.out.println(ms.getMessage("hello.name", null, Locale.KOREA));                  // 7
        System.out.println(ms.getMessage("price", new Object[]{10000}, Locale.KOREA));        // 8
        System.out.println(ms.getMessage("price", new Object[]{10000}, Locale.GERMANY));      // 9
        System.out.println(ms.getMessage("no_code", null, "기본 메시지", Locale.KOREA));        // 10
        try {
            ms.getMessage("no_code", null, Locale.KOREA);                                     // 11
        } catch (NoSuchMessageException e) {
            System.out.println(e.getMessage());
        }
        System.out.println(ms.getMessage("quote", new Object[]{"x"}, Locale.KOREA));          // 12
        System.out.println(ms.getMessage("quote2", new Object[]{"x"}, Locale.KOREA));         // 13
        System.out.println(ms.getMessage("noarg", null, Locale.KOREA));                       // 14
    }
}

    이 회차의 스프링 실행 결과는 로컬에 있던 Spring Framework 7.0.10과 JDK 21로 돌린 것이다. 기준 버전인 6.x와 다르지 않은지는 6.2.x 소스(AbstractMessageSource, ResourceBundleMessageSource, AcceptHeaderLocaleResolver)와 스프링 부트 3.5.x 소스를 열어 해당 로직을 대조했다. 본문에서 설명하는 규칙은 두 버전에서 같다.

    1번은 로케일에 null을 넘긴 경우다. AbstractMessageSource는 로케일이 null이면 Locale.getDefault()로 바꿔 쓴다. 그러니 1번의 결과는 "기본 파일의 값"이 아니라 "JVM 기본 로케일로 조회한 값"이다. 지금은 기본 로케일이 ko_KR이고 한국어 전용 파일이 없어서 기본 파일의 안녕이 나왔을 뿐이다. 테스트에서 null 로케일로 기대값을 단정하면 그 테스트는 실행하는 기계의 로케일에 따라 성공과 실패가 갈린다.

    2번부터 5번은 JDK의 후보 목록과 부모 체인이 그대로 드러난 결과다. ko_KR은 루트로, en은 messages_en으로, en_US는 messages_en_US로 갔고, 5번의 only.default는 영어 번들 둘을 거슬러 올라가 기본 파일에서 발견되었다. 6번은 인자 배열의 첫 원소가 {0}에 들어갔다.

    8번과 9번은 같은 정수 10000인데 구분 기호가 다르다. 9번에서 문장 자체는 독일어 파일이 없으니 기본 파일의 한국어 패턴이 선택되었지만, 숫자는 독일식 10.000으로 찍혔다. 스프링은 MessageFormat을 만들 때 "값을 찾은 번들의 로케일"이 아니라 요청한 로케일을 넘기기 때문이다. 문장을 고르는 일과 숫자·날짜의 형식을 정하는 일은 서로 다른 단계에서 일어난다.

    10번과 11번은 코드를 못 찾았을 때의 두 갈래다. 기본 메시지를 받는 메서드는 그 기본 메시지를 돌려주고, 받지 않는 메서드는 NoSuchMessageException을 던진다. 예외 메시지에 코드와 로케일이 함께 찍히므로, 운영 로그에서 이 예외를 보면 어떤 키가 어떤 로케일에서 빠졌는지 바로 알 수 있다.

    인자가 있을 때와 없을 때 경로가 갈린다

    7번, 12번, 14번은 한 묶음으로 봐야 한다. 7번은 인자 없이 hello.name을 조회했더니 {0}이 그대로 나왔다. 12번은 It's {0}에 인자를 줬더니 따옴표가 사라지고 {0}도 치환되지 않았다. 14번은 같은 작은따옴표가 들어 있는데도 It's ok가 멀쩡히 나왔다. 일관성이 없어 보이지만 AbstractMessageSource.getMessageInternal의 분기를 보면 한 가지 규칙에서 나온 결과다.

    getMessage(code, args, locale)
   │
   ├─ locale == null 이면 Locale.getDefault()로 대체
   │
   ├─ [args가 비어 있고 alwaysUseMessageFormat == false]
   │      번들에서 문자열을 꺼내 그대로 반환          ← MessageFormat을 거치지 않는다
   │      (7번: "안녕 {0}" 그대로,  14번: "It's ok" 그대로)
   │
   └─ [그 밖의 경우: args가 있다]
          번들에서 꺼낸 문자열로 MessageFormat을 만들거나 캐시에서 꺼내
          synchronized(messageFormat) { format(args) }  ← 작은따옴표 규칙이 적용된다
          (12번: "It's {0}" → "Its {0}",  13번: "It''s {0}" → "It's x")

    인자가 없으면 패턴을 해석할 이유가 없으므로 스프링은 MessageFormat을 건너뛰고 원문을 돌려준다. 소스의 주석도 이것을 "인자가 없으니 MessageFormat이 필요 없는 최적화된 조회"라고 설명한다. 그 결과 같은 파일 안에서 인자가 있는 메시지는 작은따옴표를 두 번 적어야 하고, 인자가 없는 메시지는 한 번만 적어야 하는 비대칭이 생긴다. 인자 없는 메시지에 ''를 적으면 따옴표 두 개가 그대로 출력된다. 이 비대칭이 번역자에게 부담이라면 always-use-message-format을 true로 바꿔 모든 메시지를 MessageFormat 규칙으로 통일하는 선택지가 있다. 이 경우 모든 메시지에서 작은따옴표를 두 번 적는 것으로 규칙이 하나가 된다.

    분기 아래쪽의 synchronized도 눈여겨보자. ResourceBundleMessageSource는 번들과 MessageFormat을 각각 ConcurrentHashMap에 캐시한다. 번들 캐시는 기본 이름과 로케일로, 포맷 캐시는 번들·코드·로케일로 찾는다. 메시지 소스는 싱글톤 빈이므로 이 캐시의 MessageFormat 객체 하나를 요청 스레드 여럿이 함께 쓰게 되는데, 앞에서 본 대로 MessageFormat은 스레드 안전하지 않다. 그래서 스프링은 포맷 객체 하나를 모니터로 잡고 format을 호출한다. 패턴 해석 비용은 한 번만 치르고, 동시 호출은 그 메시지 하나에 대해서만 직렬화되는 구조다.

    캐시 유지 시간의 기본값은 "계속 유지"다. 애플리케이션이 떠 있는 동안 properties 파일을 고쳐도 반영되지 않는다. 메시지 파일은 보통 jar 안에 들어 있어 배포 없이 바뀔 일이 없으므로 합리적인 기본값이다. 실행 중에 파일을 바꿔 반영해야 하는 요구가 있다면 캐시 시간을 지정하거나, 클래스패스 밖의 파일을 읽고 다시 읽어 들이는 기능을 가진 ReloadableResourceBundleMessageSource를 검토한다.

    함정: 서버의 기본 로케일이 끼어드는 경우

    해결책은 셋 중에서 고른다. 폴백을 끄거나, 기본 파일과 같은 내용의 messages_ko.properties를 따로 두어 한국어 요청이 폴백까지 가지 않게 하거나, 서버 JVM의 기본 로케일을 명시적으로 고정하는 것이다. 세 번째는 메시지 말고도 날짜·숫자 형식 등 로케일에 기대는 다른 코드에까지 영향을 주므로 범위가 넓다. 어느 쪽을 택하든 "개발 PC와 서버의 기본 로케일이 다를 수 있다"는 사실을 테스트에 반영해 두는 것이 안전하다.

    웹 애플리케이션에 메시지 적용하기

    이제 화면으로 올라가자. 도서 관리 화면에서 쓸 문구를 기본 파일에 모은다. 키 이름은 종류.대상.속성처럼 점으로 계층을 주면 찾기 쉽다. 점은 단지 이름의 일부이고 메시지 소스가 계층으로 해석하지는 않는다.

    태그 안에 원래 적혀 있던 "도서 목록", "제목" 같은 글자는 지우지 않았다. 1회차에서 본 대로 th:text는 렌더링할 때 태그의 내용을 바꿔치기하므로, 파일을 브라우저로 직접 열면 원래 글자가 보이고 서버를 거치면 메시지 소스의 값이 보인다. 템플릿을 정적 파일로 열어도 화면 모양을 확인할 수 있다는 성질이 메시지를 적용한 뒤에도 유지된다.

    #{...}가 평가될 때 일어나는 일을 따라가 보자. 스프링과 통합된 타임리프의 템플릿 엔진 SpringTemplateEngine은 스프링의 메시지 소스를 쓰는 메시지 리졸버를 갖고 있다. 이 리졸버(SpringMessageResolver)의 소스를 보면 하는 일이 한 줄이다. 표현식의 키, 괄호 안 인자의 배열, 그리고 템플릿 컨텍스트의 로케일을 들고 messageSource.getMessage(key, messageParameters, context.getLocale())을 호출한다. 앞 절에서 손으로 호출한 바로 그 메서드다. #{books.count(${books.size()})}라면 먼저 안쪽의 ${books.size()}가 평가되어 정수 3이 되고, 그것이 인자 배열에 담겨 전체 {0}권에 끼워져 전체 3권이 된다. 인자가 정수이므로 천 권이 넘으면 1,000처럼 구분 기호가 들어간다.

    키를 못 찾으면 어떻게 될까. 리졸버는 NoSuchMessageException을 잡고 다른 방법을 시도한 뒤, 끝내 못 찾으면 "없는 메시지 표시"를 만든다. 타임리프 3.1 소스에서 이 표시는 ??키_로케일?? 형식이다. 화면에 ??label.book.isbn_ko_KR??이 보인다면 오류 페이지 대신 화면은 그려졌지만 그 키가 그 로케일에서 조회되지 않았다는 뜻이다. 원인은 넷 중 하나다. 키의 오타, 파일에 키가 없음, 메시지 파일이 클래스패스에 실리지 않음, 그리고 앞에서 본 대로 기본 파일이 없어 자동 설정이 꺼진 경우다. 모든 키가 한꺼번에 물음표로 나오면 마지막 두 가지를 먼저 의심한다.

    메시지 값에 HTML 태그를 넣고 th:utext로 출력하는 방법은 조심해서 쓴다. th:utext는 이스케이프를 하지 않으므로, 인자로 사용자 입력이 들어가는 메시지라면 그 입력이 그대로 HTML로 해석된다. 강조 같은 마크업은 가능하면 템플릿 쪽에 두고 메시지에는 글자만 둔다.

    웹 애플리케이션에 국제화 적용하기

    메시지를 적용했다면 국제화는 파일 하나를 더 만드는 것으로 끝난다. 템플릿과 컨트롤러는 한 글자도 바꾸지 않는다.

    page.books=Books
page.book.add=Add a book
label.book.title=Title
label.book.price=Rental fee
button.add=Add
button.save=Save
books.count={0} books in total

    남은 질문은 하나다. 서버는 이 요청이 영어 화면을 원한다는 것을 어떻게 아는가. 답은 HTTP 요청 헤더 Accept-Language다. HTTP 웹 기본 지식에서 본 콘텐츠 협상(content negotiation) 헤더 가운데 하나로, 브라우저가 자신의 언어 설정을 요청마다 실어 보낸다.

    GET /books HTTP/1.1
Host: localhost:8080
Accept-Language: ko-KR,ko;q=0.9,en-US;q=0.8,en;q=0.7

    쉼표로 나뉜 항목 하나하나가 언어 범위이고, ;q= 뒤의 숫자가 품질 값(quality value)이다. RFC 9110에 따르면 가중치는 0에서 1 사이이고, q가 없으면 1이며, 0은 "받지 않겠다"는 뜻이다. 위 헤더는 "한국어(대한민국)를 가장 원하고, 그다음은 지역을 가리지 않는 한국어, 그다음은 미국 영어, 그다음은 영어 일반"이라는 선호 목록이다. RFC는 적힌 순서를 우선순위로 믿을 수 없다고도 적고 있어서, 브라우저들은 순서대로 적으면서 q 값도 서로 다르게 매겨 보낸다.

    서블릿 컨테이너는 이 헤더를 해석해 request.getLocale()과 request.getLocales()로 제공한다. 서블릿 API 문서에 따르면 getLocale()은 헤더를 근거로 클라이언트가 가장 선호하는 로케일을 돌려주고, 헤더가 없으면 서버의 기본 로케일을 돌려준다. getLocales()는 선호도가 높은 것부터 내림차순으로 나열한다. 헤더가 ko;q=0.5,en;q=0.9처럼 적힌 순서와 q 값이 어긋나 있어도 q 값이 큰 en이 먼저 나온다.

    확인하는 방법은 두 가지다. 브라우저의 언어 설정에서 영어를 맨 위로 올리고 새로 고치거나, 헤더를 직접 지정해 요청을 보낸다. 뒤쪽이 재현하기 쉽다.

    curl -s -H "Accept-Language: en" http://localhost:8080/books
curl -s -H "Accept-Language: ko-KR,ko;q=0.9" http://localhost:8080/books

    첫 요청의 HTML에는 Books, Title, Rental fee가, 둘째 요청에는 도서 목록, 제목, 대여료가 들어 있다. 같은 URL, 같은 컨트롤러, 같은 템플릿이고 달라진 것은 요청 헤더 한 줄뿐이다.

    LocaleResolver: 요청에서 로케일을 꺼내는 전략

    헤더에서 로케일을 꺼내 타임리프에 넘겨주는 것은 누구일까. 스프링 MVC는 "이 요청의 로케일은 무엇인가"를 정하는 일을 LocaleResolver라는 전략 인터페이스로 분리해 두었다. DispatcherServlet은 초기화할 때 이름이 localeResolver인 빈을 찾고, 없으면 AcceptHeaderLocaleResolver를 기본으로 쓴다. MVC 1편에서 본 핸들러 매핑, 핸들러 어댑터, 뷰 리졸버와 같은 방식으로 끼워 넣는 부품이다. 스프링 부트는 localeResolver 빈이 없을 때 AcceptHeaderLocaleResolver를 등록하고, spring.web.locale에 값이 있으면 그것을 이 리졸버의 기본 로케일로 넣어 준다.

    AcceptHeaderLocaleResolver의 판단 순서는 짧다. 기본 로케일이 설정되어 있고 요청에 Accept-Language 헤더가 없으면 기본 로케일을 돌려준다. 그 밖에는 request.getLocale()을 쓴다. 지원 로케일 목록을 지정해 두었다면 한 단계가 더 있어서, 요청의 선호 목록을 순서대로 훑으며 지원 목록에 있는 것을 찾고, 언어만 일치하는 것도 후보로 삼는다. 지원 목록을 한국어와 영어로, 기본을 한국어로 두고 Accept-Language: fr-FR,en-US;q=0.8을 보내면 프랑스어는 건너뛰고 영어가 선택되는 것을 실행해 확인했다. 헤더가 없으면 기본인 한국어가 나온다.

    요청 하나가 처리되는 동안 로케일이 흘러가는 길을 소스의 순서대로 정리하면 다음과 같다.

    요청 헤더의 언어 정보가 어느 객체에서 Locale이 되고, 어느 객체가 그 Locale로 메시지 파일을 고르며, 응답 헤더에 어떻게 되돌아가는지를 한 줄로 이어 보여 준다. 깔끔한 평면 벡터 시퀀스 다이어그램, 흰 배경. 위쪽에 참여자 상자 다섯 개가 가로로 나란히: "브라우저", "DispatcherServlet", "LocaleResolver", "타임리프 뷰", "MessageSource". 각 상자에서 아래로 점선 생명선. 화살표 순서: (1) 브라우저에서 DispatcherServlet으로 실선 화살표, 라벨 "Accept-Language: en". (2) DispatcherServlet에서 LocaleResolver로 화살표, 라벨 "resolveLocale", 되돌아오는 점선 화살표 라벨 "Locale en". (3) DispatcherServlet에서 타임리프 뷰로 화살표, 라벨 "render (en)". (4) 타임리프 뷰에서 MessageSource로 화살표, 라벨 "getMessage", 되돌아오는 점선 화살표 라벨 "Books". (5) DispatcherServlet에서 브라우저로 되돌아오는 실선 화살표, 라벨 "Content-Language: en". MessageSource 상자 아래에 작은 파일 아이콘 두 개가 겹쳐 있고 그중 하나만 주황색으로 강조. 색은 파랑과 회색 위주. 그 밖의 글자는 넣지 않는다. 로케일은 요청 헤더에서 한 번 결정되어 템플릿의 모든 메시지 조회에 인자로 전달되고, 응답의 Content-Language로 되돌아간다.

    이 흐름을 눈으로 확인하려고, 뷰 안에서 세 가지 값을 찍는 컨트롤러를 만들어 요청을 보내 봤다. 핸들러 인자로 받은 Locale, 스레드 로컬에서 꺼낸 로케일, 그리고 메시지 소스가 돌려준 문구다.

    // import 생략
@Controller
public class GreetingController {

    private final MessageSource messageSource;

    public GreetingController(MessageSource messageSource) {
        this.messageSource = messageSource;
    }

    @GetMapping("/greeting")
    public View greeting(Locale locale) {
        return (model, request, response) -> {
            response.setContentType("text/plain;charset=UTF-8");
            response.getWriter().write(messageSource.getMessage("hello", null, locale)
                    + " | arg=" + locale
                    + " | holder=" + LocaleContextHolder.getLocale());
        };
    }
}
    요청 헤더응답 본문응답의 Content-Language
    Accept-Language: en-US,en;q=0.9,ko;q=0.8hello(US) | arg=en_US | holder=en_USen-US
    Accept-Language: ko-KR,ko;q=0.9안녕 | arg=ko_KR | holder=ko_KRko-KR

    세 값이 모두 같은 로케일을 가리킨다. 그리고 요청이 끝난 뒤 같은 스레드에서 LocaleContextHolder.getLocaleContext()를 찍으면 null이었다. 요청 스레드는 스레드 풀에서 재사용되므로, 정리하지 않으면 앞 요청의 로케일이 다음 요청에 남는다. FrameworkServlet이 finally에서 이전 값으로 되돌리는 이유다. 반대 방향의 함정도 있다. LocaleContextHolder는 스레드 로컬이므로, 요청 스레드가 아닌 다른 스레드에서 실행되는 코드에서는 요청의 로케일이 보이지 않고 JVM 기본 로케일이 나온다. 비동기로 메일 본문을 만드는 코드라면 로케일을 스레드 로컬에서 꺼내지 말고 값으로 넘겨야 한다.

    응답의 Content-Language는 response.setLocale의 결과다. 서블릿 API 문서는 HTTP의 경우 로케일이 Content-Language 헤더로 전달된다고 적고 있다. 브라우저나 중간의 캐시는 이 헤더로 응답이 어떤 언어인지 알 수 있다. 요청의 Accept-Language에 서버가 Content-Language로 답하는, 협상의 왕복이 완성된다.

    사용자가 언어를 직접 고르게 하려면

    Accept-Language는 브라우저 설정이지 사용자의 선택이 아니다. 회사 PC의 브라우저가 영어로 설치되어 있어도 사용자는 한국어 화면을 원할 수 있다. 그래서 많은 사이트가 화면에 언어 선택 메뉴를 두고, 한 번 고른 언어를 기억한다. 이때 필요한 것은 두 가지다. 선택을 어디에 기억할지와, 선택이 바뀌는 요청을 어떻게 알아챌지다.

    기억하는 쪽은 LocaleResolver 구현체를 바꿔서 해결한다. CookieLocaleResolver는 쿠키에, SessionLocaleResolver는 서블릿 컨테이너의 HttpSession에 로케일을 저장한다. 스프링 레퍼런스는 세션 쪽의 설정이 세션마다 일시적이어서 세션이 끝나면 사라진다고 설명한다. 알아채는 쪽은 LocaleChangeInterceptor가 맡는다. 요청 파라미터(기본 이름 locale)가 있으면 그 값을 로케일로 바꿔 현재 리졸버의 setLocale을 호출하는 인터셉터다.

    // import 생략
@Configuration
public class LocaleConfig implements WebMvcConfigurer {

    @Bean
    public LocaleResolver localeResolver() {      // 빈 이름이 localeResolver여야 한다
        return new CookieLocaleResolver("lang");
    }

    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        LocaleChangeInterceptor interceptor = new LocaleChangeInterceptor();
        interceptor.setParamName("lang");
        registry.addInterceptor(interceptor);
    }
}

    첫 요청에서 인터셉터가 lang=en을 보고 리졸버에 로케일을 설정했고, 리졸버는 그것을 쿠키로 내려보냈다. 헤더는 한국어를 원한다고 했지만 화면은 영어다. 둘째 요청에는 파라미터가 없지만 브라우저가 쿠키를 되돌려 보내므로 영어가 유지된다. 쿠키도 파라미터도 없는 셋째 요청은 헤더의 로케일로 돌아간다. 쿠키와 세션이 요청 사이에 상태를 이어 주는 원리, 그리고 인터셉터가 호출되는 정확한 시점은 6회차와 7회차의 주제이므로 여기서는 "로케일을 기억하는 수단으로 쓰인다"는 것만 짚는다.

    기본 리졸버를 그대로 둔 채 인터셉터만 등록하면 어떻게 될까. ?lang=en 요청에서 UnsupportedOperationException이 난다. 메시지는 "Cannot change HTTP Accept-Language header - use a different locale resolution strategy"다. AcceptHeaderLocaleResolver가 읽는 대상은 클라이언트가 보낸 헤더이고 서버가 그것을 바꿀 방법은 없으므로 setLocale을 지원하지 않는 것이다. 언어 선택 기능에는 리졸버 교체와 인터셉터 등록이 짝으로 필요하다.

    흔한 오해와 함정

    "기본 파일은 요청 로케일의 파일이 없을 때 바로 쓰인다." 기본 설정에서는 그 사이에 JVM 기본 로케일의 파일을 찾는 단계가 있다. 서버의 기본 로케일에 해당하는 언어 파일이 존재하면 그 파일이 먼저 선택된다. 기본 파일이 곧 기본 언어이기를 원하면 폴백을 끈다.

    "언어별 파일만 잘 만들면 된다." 스프링 부트의 자동 설정은 기본 파일이 있어야 켜진다. 또 언어별 파일에서 빠진 키는 부모 체인을 따라 기본 파일에서 채워지므로, 기본 파일에는 모든 키가 있어야 화면에 물음표가 나오지 않는다. 기본 파일은 "모든 키의 기준 목록" 역할을 한다.

    "작은따옴표는 항상 두 번 쓴다" 또는 "항상 한 번 쓴다." 기본 설정에서는 인자가 넘어오는 메시지만 MessageFormat을 거친다. 메시지 문자열에 {0}이 있느냐가 아니라 호출하는 쪽이 인자를 넘겼느냐가 기준이라는 점도 주의한다. 같은 키라도 인자 없이 조회하면 원문이 그대로 나온다.

    "한글이 깨지면 템플릿 인코딩 문제다." 메시지에서 온 글자만 깨지고 템플릿에 직접 적은 글자는 멀쩡하다면 원인은 메시지 파일 쪽이다. 파일을 저장한 인코딩과 메시지 소스가 읽는 인코딩 가운데 하나가 UTF-8이 아니다. 부트의 기본값은 UTF-8이므로 부트를 쓰는데 깨진다면 파일이 다른 인코딩으로 저장된 경우이고, 메시지 소스를 직접 등록했다면 setDefaultEncoding을 빠뜨린 경우다.

    "메시지 파일을 고쳤는데 반영이 안 된다." 번들은 캐시되고 기본값은 계속 유지다. 또 실행 중인 애플리케이션이 읽는 것은 소스 디렉터리의 파일이 아니라 빌드 결과물에 복사된 파일이다. 파일을 고친 뒤에는 다시 빌드해 재시작한다.

    "문장은 코드에서 조립하면 된다." 이름 + "님 환영합니다"처럼 코드에서 이어 붙인 문장은 번역할 수 없다. 언어마다 어순이 다르고 조사와 복수형이 다르기 때문이다. 문장 전체를 하나의 메시지로 두고 변하는 부분만 {0}으로 남긴다.

    이 지식이 다시 쓰이는 곳

    메시지 소스는 화면 라벨만을 위한 것이 아니다. 바로 다음 4회차와 5회차의 검증에서, 입력 오류를 사용자에게 알려 주는 문구가 같은 MessageSource에서 나온다. 오류 하나가 여러 개의 메시지 코드 후보를 갖고 그중 처음 발견된 것이 쓰이는 구조인데, 이번 회차에서 본 MessageSourceResolvable을 받는 getMessage가 바로 그 용도다. 오류 코드를 만드는 규칙과 BindingResult는 4회차의 몫이다.

    10회차의 타입 컨버터와 포매터에서는 로케일이 다시 등장한다. 숫자 10000을 문자열 10,000으로, 날짜를 지역에 맞는 형식으로 바꾸는 포매터는 변환할 때 현재 로케일을 받는다. 그 로케일의 출처가 이번 회차의 LocaleContextHolder와 LocaleResolver다. 8회차와 9회차의 오류 응답 문구도 다국어로 내보내려면 같은 메시지 소스를 쓴다.

    더 넓게 보면 이 회차의 구조는 스프링이 반복해서 쓰는 설계다. 변하는 값을 코드 밖으로 빼고(메시지 파일), 그것을 읽는 방법을 인터페이스로 추상화하고(MessageSource), 요청마다 달라지는 판단을 전략으로 분리하며(LocaleResolver), 요청 범위의 값을 스레드 로컬로 전달한다(LocaleContextHolder). 트랜잭션 동기화나 요청 속성 보관에서도 같은 스레드 로컬 패턴을 다시 만나게 된다.

    이 장의 핵심

    메시지 기능은 문구에 이름을 붙이는 간접 참조이고, 국제화는 그 참조에 로케일이라는 선택 기준을 더한 것이다. 어느 파일의 값이 나오는지는 JDK의 후보 목록·부모 체인·기본 로케일 폴백이 정하고, 인자가 어떻게 끼워지는지는 MessageFormat이 정하며, 요청의 로케일이 무엇인지는 LocaleResolver가 정한다. 증상이 생기면 이 셋 중 어느 단계의 규칙인지부터 가른다.
    메시지 기능
    화면 문구를 키와 값으로 한 파일에 모으고 템플릿은 키만 참조하게 하는 간접 참조다. 문구 변경이 한 줄 수정으로 끝난다.
    국제화와 로케일
    메시지 파일을 로케일별로 여러 벌 두고 요청의 로케일에 맞는 것을 고른다. 로케일은 언어와 지역을 담은 값이며 파일 이름에서는 ko_KR, HTTP 헤더에서는 ko-KR로 적는다.
    후보 목록과 부모 체인
    JDK는 요청 로케일을 구체적인 것에서 루트까지 줄여 가며 번들을 찾고, 찾은 번들들을 부모로 연결한다. 언어별 파일에 없는 키는 부모가 답한다.
    시스템 로케일 폴백
    요청 로케일의 파일이 없으면 기본 파일보다 JVM 기본 로케일의 파일을 먼저 찾는다. fallback-to-system-locale=false로 끌 수 있다.
    MessageFormat
    {0}에 인자를 끼운다. 숫자 인자는 로케일의 숫자 형식을 따르고, 작은따옴표는 인용 기호라서 글자로 쓰려면 두 번 적는다. 객체는 스레드 안전하지 않다.
    MessageSource
    코드·인자·로케일로 문자열을 돌려주는 스프링의 추상화. 빈 이름이 messageSource여야 하고, 부트는 기본 파일이 있을 때 UTF-8로 읽는 구현체를 자동 등록한다.
    인자 유무에 따른 경로
    인자가 없으면 번들의 원문을 그대로 돌려주고, 인자가 있으면 캐시된 MessageFormat을 동기화해 호출한다. 작은따옴표 처리의 비대칭이 여기서 나온다.
    Accept-Language와 LocaleResolver
    브라우저가 보낸 선호 언어 목록을 서블릿이 Locale로 해석하고, LocaleResolver가 이번 요청의 로케일을 확정한다. 기본 구현은 헤더를 따른다.
    로케일의 전달
    확정된 로케일은 스레드 로컬(LocaleContextHolder)과 뷰 렌더링 인자로 전달되어 타임리프 #{...}의 메시지 조회에 쓰이고, 응답의 Content-Language가 된다.

    실무에서 메시지 기능을 도입할지 고민하는 시점은 대개 "지금은 한국어만 쓰는데 굳이?"다. 판단 기준은 다국어 계획이 아니라 문구의 중복과 변경 빈도다. 같은 용어가 여러 화면에 나오고 기획·법무 검토로 문구가 자주 바뀌는 서비스라면 한국어 하나만 써도 메시지 파일로 모으는 편이 싸다. 반대로 화면이 몇 개 안 되는 내부 도구라면 키를 짓고 관리하는 비용이 이득보다 클 수 있다. 다만 나중에 다국어가 필요해졌을 때 문구가 템플릿과 자바 코드 곳곳에 흩어져 있으면 뽑아내는 작업이 훨씬 크므로, 사용자에게 보이는 문구를 코드에서 문자열 연결로 만드는 일만큼은 처음부터 피한다.

    장애로 이어지는 것은 대부분 환경 차이다. 개발 PC에서는 한국어가 나오는데 서버에서만 영어가 나온다면 서버 JVM의 기본 로케일과 폴백 설정을 본다. 특정 키만 물음표로 나오면 키 누락이고, 전부 물음표면 메시지 파일이 배포물에 들어 있는지와 기본 파일이 있는지를 본다. 한글만 깨지면 파일 저장 인코딩과 읽는 인코딩을 맞춘다. 이 세 가지는 로컬에서 재현되지 않는 경우가 많으므로, 테스트에서 로케일을 명시적으로 넘기고 기본 로케일을 바꿔 가며 돌려 보는 검증을 한 번 만들어 두면 배포 전에 걸러진다.

    로케일을 어디서 얻을지도 설계 결정이다. 헤더만 따르는 기본 방식은 서버에 상태가 없어 단순하고 캐시하기도 쉽지만 사용자가 언어를 고를 수 없다. 쿠키나 세션에 기억하면 선택은 가능해지지만, 같은 URL이 사용자에 따라 다른 언어로 응답하므로 중간 캐시와 검색 노출에서 따져 볼 것이 늘어난다. 공개 콘텐츠 사이트는 언어를 URL 경로에 넣는 방식을 택하기도 한다. 어느 방식이든 스프링에서는 LocaleResolver 구현을 바꾸는 한 지점에서 결정이 끝나고, 템플릿과 메시지 파일은 그대로다.
  • 클래스패스에 messages.properties(greet=안녕, bye=잘 가), messages_en.properties(greet=hi), messages_ja.properties(greet=やあ)가 있다. JVM 기본 로케일이 ja_JP이고 폴백 설정은 기본값이다. getMessage("greet", null, Locale.KOREA), getMessage("bye", null, Locale.KOREA), getMessage("bye", null, Locale.UK)의 결과를 각각 예측하고, 후보 목록과 부모 체인으로 이유를 설명하라.
  • 기본 파일에 warn=Don't delete {0}과 tip=Don't panic이 있다. 기본 설정의 ResourceBundleMessageSource에서 getMessage("warn", new Object[]{"book"}, Locale.ENGLISH)와 getMessage("tip", null, Locale.ENGLISH)의 결과를 예측하라. 두 메시지가 모두 의도대로 출력되게 하려면 파일을 어떻게 고쳐야 하는가.
  • 스프링 부트 프로젝트에 messages_ko.properties와 messages_en.properties만 만들었더니 모든 화면의 라벨이 ??label.book.title_ko_KR?? 같은 모양으로 나온다. 예외는 없다. 무슨 일이 일어났는지 애플리케이션 시작 시점부터 순서대로 설명하라.
  • 기본 구성(헤더 기반 리졸버)의 서버에 Accept-Language: ko;q=0.3, en-GB;q=0.8, fr;q=0 헤더로 요청을 보냈다. 메시지 파일은 messages(한국어)와 messages_en이 있고 폴백은 꺼져 있다. 화면에 어떤 언어가 나오는지, 응답의 Content-Language 값이 무엇인지 단계별로 추적하라.
  • 주문 완료 메일을 비동기 스레드에서 만들어 보내는 코드가 메시지 조회에 LocaleContextHolder.getLocale()을 쓴다. 영어 사용자에게 한국어 메일이 나간다는 신고가 들어왔다(서버 기본 로케일은 ko_KR). 원인을 설명하고 고치는 방향을 제시하라.

    1번. greet/ko_KR: 후보는 messages_ko_KR, messages_ko, 루트다. 앞의 둘이 없으므로 폴백 로케일인 JVM 기본 로케일 ja_JP로 다시 찾고, messages_ja가 선택된다. 결과는 やあ다. bye/ko_KR: 선택된 번들은 역시 messages_ja인데 거기에 bye가 없다. 부모인 루트 messages로 올라가 잘 가를 얻는다. 한 화면에 일본어와 한국어가 섞여 나오는 이유가 이것이다. bye/en_GB: 후보 messages_en_GB는 없고 messages_en이 있어 선택된다. 폴백은 일어나지 않는다. messages_en에 bye가 없으므로 부모인 루트에서 잘 가가 나온다.

    2번. warn은 인자가 있으므로 MessageFormat을 거친다. 작은따옴표가 인용을 열고 닫히지 않으니 패턴 끝까지가 인용된 글자가 되어 Dont delete {0}이 출력된다. 따옴표는 사라지고 {0}은 치환되지 않는다. tip은 인자가 없어 원문이 그대로 반환되므로 Don't panic이다. 고치는 방법은 warn=Don''t delete {0}으로 따옴표를 두 번 적고 tip은 그대로 두는 것이다. 규칙을 하나로 통일하고 싶다면 always-use-message-format을 켜고 tip도 Don''t panic으로 적는다.

    3번. 부트의 메시지 소스 자동 설정은 기본 이름의 기본 파일, 곧 messages.properties가 클래스패스에 있을 때만 적용된다. 이 파일이 없으므로 조건이 맞지 않아 messageSource 빈이 등록되지 않는다. 애플리케이션 컨텍스트는 초기화하면서 messageSource라는 이름의 빈을 찾지 못해 아무 메시지도 없는 DelegatingMessageSource를 만든다. 요청이 오면 타임리프의 메시지 리졸버가 이 메시지 소스에 getMessage를 호출하고, 코드를 찾지 못했다는 예외를 리졸버가 잡은 뒤 ??키_로케일?? 표시를 만들어 출력한다. 그래서 예외 없이 모든 라벨이 물음표로 나온다. 빈 파일이라도 messages.properties를 추가하면 해결된다. 기본 언어의 내용을 그 파일로 옮기는 편이 더 좋다.

    4번. q 값은 en-GB 0.8, ko 0.3, fr 0(받지 않음)이다. 서블릿의 getLocale()은 가장 선호하는 en_GB를 돌려준다. 헤더 기반 리졸버에 지원 목록이 없으므로 이 값이 그대로 요청의 로케일이 된다. 메시지 조회의 후보는 messages_en_GB, messages_en, 루트이고 messages_en이 선택되어 영어 화면이 나온다. messages_en에 없는 키가 있다면 그 키만 한국어로 나온다. 응답의 Content-Language는 메시지를 찾은 파일의 로케일이 아니라 리졸버가 정한 로케일이므로 en-GB다.

    5번. LocaleContextHolder는 스레드 로컬이다. 요청 스레드에는 디스패처 서블릿이 요청의 로케일을 넣어 두지만, 메일을 만드는 비동기 스레드에는 아무것도 없다. 값이 없으면 JVM 기본 로케일인 ko_KR이 반환되므로 모든 메일이 한국어로 만들어진다. 고치려면 요청 스레드에서 로케일을 값으로 꺼내 비동기 작업의 인자로 넘기고, 메시지 조회에 그 값을 명시적으로 전달한다. 사용자가 고른 언어를 회원 정보에 저장해 두고 메일은 그 값을 쓰는 것이 더 견고하다. 메일은 요청과 무관한 시점(배치, 재발송)에도 만들어지기 때문이다.

     클래스패스에 messages.properties(한국어)와 messages_en.properties만 있다. JVM 기본 로케일이 en_US인 서버에서 기본 설정의 ResourceBundleMessageSource로 Locale.KOREA 메시지를 조회하면 영어가 나온다. 이유로 옳은 것은? ResourceBundleMessageSource가 요청 로케일을 무시하고 항상 JVM 기본 로케일로 조회하기 때문이다. ko_KR과 ko의 파일이 없으면 기본 파일로 가기 전에 JVM 기본 로케일(en_US)의 후보를 먼저 찾고, 그 후보 중 messages_en이 존재하기 때문이다. messages.properties는 로케일 표시가 없어서 어떤 요청에도 선택될 수 없기 때문이다. Accept-Language 헤더가 없으면 스프링이 영어를 기본 언어로 쓰도록 정해져 있기 때문이다. 요청 로케일의 후보(ko_KR, ko)에서 번들을 찾지 못하면 폴백 로케일인 JVM 기본 로케일로 후보를 다시 만들어 찾는다. en_US의 후보 가운데 messages_en이 있으므로 그것이 선택된다. 요청 로케일을 무시하는 것이 아니며(Locale.ENGLISH 요청은 기본 로케일과 무관하게 messages_en으로 간다), 기본 파일은 폴백에서도 못 찾았을 때 선택된다. 메시지 소스 단계에는 Accept-Language가 관여하지 않는다. 폴백을 끄면 한국어가 나온다. 기본 설정의 스프링 메시지 소스에서 note=It's {0} 을 인자와 함께 조회하면 Its {0} 이 나오고, plain=It's ok 를 인자 없이 조회하면 It's ok 가 그대로 나온다. 두 결과가 다른 까닭은? properties 파일을 읽을 때 중괄호가 있는 줄에서만 작은따옴표가 제거되기 때문이다. 영어 로케일과 한국어 로케일에서 작은따옴표를 처리하는 규칙이 다르기 때문이다. 인자가 넘어온 조회만 MessageFormat을 거치고, MessageFormat에서 작은따옴표는 인용 기호로 해석되기 때문이다. 인자 없는 조회는 캐시된 값을 쓰고 인자 있는 조회는 파일을 다시 읽기 때문이다. 스프링은 인자가 비어 있고 always-use-message-format이 꺼져 있으면 번들의 문자열을 그대로 돌려준다. 인자가 있으면 그 문자열을 MessageFormat 패턴으로 해석하는데, 패턴에서 작은따옴표는 인용의 시작이라 따옴표 자신은 출력되지 않고 뒤의 {0}도 글자로 취급된다. 파일을 읽는 단계에서는 따옴표가 바뀌지 않고, 로케일과도 무관하며, 두 경로 모두 캐시를 쓴다. 타임리프 템플릿의 #{label.book.title}이 영어 사용자에게 Title로 렌더링될 때, 이 표현식이 사용할 로케일은 어디에서 오는가? DispatcherServlet이 LocaleResolver로 구한 요청의 로케일이 뷰에 전달되고, 타임리프는 그 로케일을 MessageSource.getMessage의 인자로 넘긴다. 타임리프가 템플릿 파일 이름의 접미사를 보고 로케일을 추측한다. MessageSource가 조회할 때마다 스스로 HTTP 요청 헤더를 읽는다. 애플리케이션이 시작할 때 JVM 기본 로케일로 고정된다. 로케일을 확정하는 것은 LocaleResolver이고, DispatcherServlet이 렌더링 직전에 그 값을 구해 뷰 쪽에 넘긴다. 타임리프의 스프링 메시지 리졸버는 컨텍스트의 로케일을 인자로 MessageSource를 호출할 뿐이다. MessageSource는 웹을 모르는 계층이라 요청 헤더를 읽지 않으며, 로케일이 시작 시점에 고정된다면 요청마다 언어가 달라질 수 없다. FrameworkServlet은 요청 처리를 시작할 때 LocaleContextHolder에 로케일 컨텍스트를 넣고, finally 블록에서 이전 값으로 되돌린다. 되돌리는 단계가 없다면 어떤 문제가 생길 수 있는가? 메시지 파일의 캐시가 요청마다 비워져 성능이 떨어진다. Accept-Language 헤더를 다음 요청에서 다시 해석할 수 없게 된다. 싱글톤인 MessageSource 빈의 필드가 여러 요청에 의해 덮어써진다. 요청 스레드가 스레드 풀로 돌아가 재사용될 때, 앞 요청의 로케일이 그 스레드에 남아 무관한 코드가 그것을 읽을 수 있다. LocaleContextHolder는 스레드 로컬이고 서블릿 컨테이너의 요청 스레드는 풀에서 재사용된다. 값을 치우지 않으면 스레드에 묶인 값이 다음 작업까지 살아남는다. 스레드 로컬을 쓰는 코드가 반드시 finally에서 정리하는 이유다. 메시지 캐시나 헤더 해석, MessageSource의 필드와는 관계가 없다. AcceptHeaderLocaleResolver를 그대로 둔 채 LocaleChangeInterceptor만 등록하고 /books?locale=en 을 요청하면 UnsupportedOperationException이 발생한다. 가장 정확한 설명은? locale 파라미터 이름은 예약어라서 다른 이름으로 바꿔야 한다. 헤더 기반 리졸버는 클라이언트가 보낸 헤더를 읽기만 할 뿐 선택을 저장할 곳이 없으므로 setLocale을 지원하지 않는다. 쿠키나 세션에 저장하는 리졸버로 바꿔야 한다. 인터셉터는 컨트롤러가 실행된 뒤에만 로케일을 바꿀 수 있기 때문이다. messages_en.properties가 없으면 로케일을 en으로 바꿀 수 없기 때문이다. LocaleChangeInterceptor는 파라미터를 로케일로 바꿔 현재 LocaleResolver의 setLocale을 호출한다. AcceptHeaderLocaleResolver가 따르는 Accept-Language는 클라이언트 소유의 값이라 서버가 바꿀 수 없고, 그래서 setLocale이 예외를 던진다. 파라미터 이름 locale은 인터셉터의 기본값이고, 메시지 파일의 존재 여부는 로케일 변경과 무관하다.
    국제화(internationalization, i18n)
    프로그램이 여러 언어와 지역을 수용할 수 있도록 문구와 형식을 코드에서 분리해 두는 일.
    지역화(localization, l10n)
    국제화된 프로그램에 특정 언어·지역의 번역과 형식을 실제로 채워 넣는 일.
    로케일(Locale)
    언어, 문자 체계, 국가·지역, 변형으로 이루어진 값. 자바에서는 java.util.Locale 객체로 표현한다.
    기본 이름(basename)
    메시지 파일 묶음을 가리키는 공통 이름. messages라면 messages.properties, messages_en.properties 등이 한 묶음이다.
    리소스 번들(ResourceBundle)
    로케일별 자원을 담는 JDK의 추상화. 후보 로케일 목록으로 파일을 찾고 부모 체인으로 빠진 키를 채운다.
    부모 체인(parent chain)
    선택된 번들이 덜 구체적인 로케일의 번들을 부모로 연결한 구조. 자기에게 없는 키는 부모에서 찾는다.
    메시지 포맷(MessageFormat)
    {0} 같은 자리 표시자에 인자를 끼워 문장을 만드는 JDK 클래스. 작은따옴표를 인용 기호로 쓴다.
    메시지 소스(MessageSource)
    코드, 인자, 로케일을 받아 메시지 문자열을 돌려주는 스프링의 인터페이스.
    Accept-Language
    클라이언트가 선호하는 자연어 목록을 품질 값과 함께 서버에 알리는 HTTP 요청 헤더.
    로케일 리졸버(LocaleResolver)
    요청의 로케일을 결정하는 스프링 MVC의 전략 인터페이스. 헤더, 쿠키, 세션, 고정 값 기반 구현이 있다.
