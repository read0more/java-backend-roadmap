    규칙을 코드가 아니라 선언으로: Bean Validation이 푸는 문제

    04회에서 만든 상품 검증기를 떠올려 보자. 이름이 비었는지, 가격이 100원 이상 5,000,000원 이하인지, 수량이 1개 이상 999개 이하인지를 if 문으로 하나씩 확인하고, 실패하면 rejectValue로 오류를 등록했다. 동작은 정확했지만 코드를 다시 읽으면 대부분이 같은 모양의 반복이다. "이 필드는 비어 있으면 안 된다", "이 필드는 이 범위 안에 있어야 한다"는 규칙은 사실 필드에 대한 정보인데, 그 정보가 필드 선언과 멀리 떨어진 다른 클래스의 메서드 안에 흩어져 있다. 필드를 하나 추가하면 검증기도 함께 고쳐야 하고, 그것을 잊어도 컴파일러는 아무 말도 하지 않는다.

    Bean Validation은 이 규칙을 필드 옆에 애노테이션으로 선언하자는 생각에서 출발한다. @NotBlank를 붙이면 "비어 있으면 안 된다", @Max(999)를 붙이면 "999 이하여야 한다"가 된다. 선언은 데이터일 뿐 스스로 아무것도 검사하지 않는다. 검사는 이 선언을 읽어 해석하는 별도의 엔진, 즉 검증기(validator)가 한다. 코드로 쓰던 규칙이 메타데이터(metadata)로 바뀌고, 메타데이터를 실행하는 일은 범용 엔진이 맡는 구조다. 스프링이 @Transactional이나 @RequestMapping을 다루는 방식과 같은 계열이다.

    이 구조가 주는 이득은 반복 제거만이 아니다. 규칙이 데이터이므로 여러 계층이 같은 규칙을 공유할 수 있다. 웹 계층의 바인딩 직후 검증, 서비스 메서드의 인자 검증, JPA 엔티티를 저장하기 직전의 검증이 모두 같은 애노테이션을 읽는다. 오류 메시지도 규칙과 함께 표준화된다. 모든 구현이 @NotBlank를 같은 의미로 해석하도록 명세가 정해 두었기 때문에, 구현체를 바꿔도 규칙의 의미는 달라지지 않는다.

    대가도 있다. 애노테이션으로 표현하기 쉬운 것은 필드 하나만 보면 판단할 수 있는 규칙이다. "가격 × 수량은 50,000,000원 이하"처럼 여러 필드를 함께 봐야 하는 규칙, "등록할 때와 수정할 때 규칙이 다르다" 같은 상황 의존적인 규칙은 선언 하나로 깔끔하게 표현되지 않는다. 이 회차의 후반부는 거의 이 한계를 다루는 데 쓰인다. 먼저 엔진이 어떻게 생겼는지부터 보자.

    명세와 구현: jakarta.validation과 Hibernate Validator

    Bean Validation은 라이브러리 이름이 아니라 자바 진영의 표준 명세(specification) 이름이다. 명세는 애노테이션(@NotNull, @Max 등), 인터페이스(Validator, ConstraintValidator, ConstraintViolation), 그리고 그것들이 어떻게 동작해야 하는지를 문서로 정한다. 처음에는 Java EE의 JSR(Java Specification Request)로 만들어졌고, 스프링 소스 곳곳에 남아 있는 "JSR-303"이라는 이름이 그 첫 버전을 가리킨다. Java EE가 이클립스 재단으로 옮겨 Jakarta EE가 된 뒤로는 Jakarta Bean Validation이라는 이름으로 이어졌다. Jakarta EE 9에 해당하는 3.0에서 패키지가 javax.validation에서 jakarta.validation으로 바뀌었고, Jakarta EE 11에 해당하는 버전은 Jakarta Validation 3.1이다. Spring Framework 6과 Spring Boot 3은 jakarta.* 네임스페이스를 쓰므로 import jakarta.validation.constraints.NotBlank로 시작한다.

    명세는 실행되지 않는다. 실행되는 것은 구현체(provider)다. 사실상 표준 구현은 Hibernate Validator이고, Hibernate Validator 8.0이 Jakarta Bean Validation 3.0의 참조 구현(reference implementation)이다. 이름에 Hibernate가 들어 있지만 JPA나 ORM과는 별개의 라이브러리다. 의존성을 나눠 보면 이렇다.

    의존성담긴 것역할

    hibernate-validator각 제약의 실제 검사 코드, 메시지 번역 파일, 추가 제약(@Range, @ScriptAssert 등)구현. 선언을 읽고 실행하는 엔진

    스프링 부트에서는 spring-boot-starter-validation 하나를 추가하면 이 셋이 함께 들어온다. Spring Boot 3.3의 스타터는 hibernate-validator와 tomcat-embed-el에 의존하고, 이 버전이 관리하는 jakarta.validation-api는 3.0.2이고, hibernate-validator는 3.3.0에서 8.0.1.Final, 이후 패치 릴리스(예: 3.3.13)에서 8.0.2.Final이다. 웹 스타터에는 검증 스타터가 포함되어 있지 않으므로 직접 추가해야 한다.

    dependencies {
    implementation 'org.springframework.boot:spring-boot-starter-web'
    implementation 'org.springframework.boot:spring-boot-starter-thymeleaf'
    implementation 'org.springframework.boot:spring-boot-starter-validation'
}

    애플리케이션 코드는 가능하면 명세의 API에만 의존한다. 위반 결과를 받는 타입도, 대부분의 애노테이션도 jakarta.validation 패키지에 있다. 다만 org.hibernate.validator.constraints 패키지의 @Range처럼 구현체 전용 애노테이션도 편해서 자주 쓰인다. 이것을 쓰는 순간 그 코드는 Hibernate Validator에 묶인다는 점만 알고 쓰면 된다. 이 회차는 비교를 위해 일부러 둘을 섞어 쓴다.

    명세의 API만 있고 구현체가 없으면 검증기를 만들 수 없다. Validation.buildDefaultValidatorFactory()는 클래스패스에서 META-INF/services/jakarta.validation.spi.ValidationProvider 파일을 찾아 구현체를 고르는데, 이것은 자바 표준의 서비스 로더(ServiceLoader) 방식이다. 스프링 부트의 검증 자동 구성도 바로 이 파일이 클래스패스에 있는지를 조건으로 건다.

    스프링 없이 검증기 직접 돌려 보기

    스프링에 연결하기 전에 엔진만 따로 돌려 보면 스프링이 어디서부터 끼어드는지가 분명해진다. 상품 클래스에 규칙을 선언한다. 04회와 같은 규칙이다. 가격에는 Hibernate Validator의 @Range를, 수량에는 표준의 @Min, @Max를 썼다.

    import jakarta.validation.constraints.Max;
import jakarta.validation.constraints.Min;
import jakarta.validation.constraints.NotBlank;
import jakarta.validation.constraints.NotNull;
import org.hibernate.validator.constraints.Range;

public class Product {

    private Long id;

    @NotBlank
    private String name;

    @NotNull
    @Range(min = 100, max = 5_000_000)
    private Integer price;

    @NotNull
    @Min(1)
    @Max(999)
    private Integer quantity;

    public Product() {
    }

    // getter, setter ...
}

    검증기를 만들고 객체 하나를 검사하는 코드는 다음과 같다. ValidatorFactory는 AutoCloseable을 구현하므로 try-with-resources로 닫을 수 있다.

    import jakarta.validation.ConstraintViolation;
import jakarta.validation.Validation;
import jakarta.validation.Validator;
import jakarta.validation.ValidatorFactory;
import java.util.Set;

public class BeanValidationBasics {
    public static void main(String[] args) {
        try (ValidatorFactory factory = Validation.buildDefaultValidatorFactory()) {
            Validator validator = factory.getValidator();

            Product product = new Product();
            product.setName("   ");      // 공백만 있다
            product.setPrice(10);        // 범위 밖
            product.setQuantity(null);   // 비어 있다

            Set> violations = validator.validate(product);
            for (ConstraintViolation v : violations) {
                System.out.println(v.getPropertyPath() + " | " + v.getInvalidValue() + " | " + v.getMessage());
            }
        }
    }
}
    name |     | 공백일 수 없습니다
price | 10 | 100에서 5000000 사이여야 합니다
quantity | null | 널이어서는 안됩니다

    결과를 한 줄씩 읽어 보자. 위반 하나는 ConstraintViolation 객체 하나다. 여기에는 어느 경로의 값이 어긋났는지(getPropertyPath()), 그 값이 무엇이었는지(getInvalidValue()), 어떤 제약이 어긋났는지(getConstraintDescriptor()), 사람이 읽을 메시지(getMessage())가 들어 있다. 이 네 가지가 뒤에서 스프링이 FieldError를 만들 때 쓰는 재료 전부다.

    validate의 반환 타입은 Set이다. Set 인터페이스는 순회 순서를 약속하지 않고, 명세도 반환되는 위반의 순서를 정하지 않는다. 그래서 위 출력의 줄 순서는 보장되지 않는다. 화면에 오류를 보여 줄 때 순서가 중요하다면 위반 목록의 순서에 기대지 말고 템플릿에서 필드별로 꺼내야 한다. 실제로 타임리프의 th:errors="*{name}"는 필드 이름으로 오류를 찾으므로 순서와 무관하다.

    메시지는 두 가지를 알려 준다. 첫째, Hibernate Validator는 언어별 기본 메시지 파일을 갖고 있다. @NotBlank의 message 속성 기본값은 {jakarta.validation.constraints.NotBlank.message}라는 키이고, 한국어 파일(ValidationMessages_ko.properties)에서 이 키가 "공백일 수 없습니다"로 풀렸다. 스프링 없이 실행하면 메시지 파일을 고르는 로캘은 JVM 기본 로캘(Locale.getDefault())이다. 영어 로캘에서 같은 코드를 돌리면 영어 메시지가 나온다. 둘째, @Range의 메시지 템플릿 {min}에서 {max} 사이여야 합니다의 {min}, {max}는 같은 이름의 애노테이션 속성 값으로 치환되었다. 이때 숫자는 toString()으로 문자열이 되므로 천 단위 구분 기호가 없는 5000000이 된다. 뒤에서 스프링의 메시지 소스가 같은 값을 5,000,000으로 찍는 것과 대비된다.

    Hibernate Validator 문서는 메시지 보간(message interpolation)의 순서를 이렇게 정리한다. 먼저 {...} 안의 이름을 애플리케이션의 ValidationMessages 번들에서 찾고, 다음으로 구현체에 내장된 표준 메시지 번들에서 찾고, 그래도 남은 것은 같은 이름의 애노테이션 속성 값으로 바꾸며, 마지막으로 ${...} 식을 EL로 평가한다. EL 구현이 의존성에 필요한 이유가 이 마지막 단계다.

    여기까지의 핵심

    검증 엔진의 입력은 "객체 하나와 검사할 그룹 목록"이고, 출력은 "위반의 집합"이다. 엔진은 BindingResult도, 오류 코드도, errors.properties도 모른다. 그것들은 전부 스프링이 이 출력을 받아 04회의 구조로 옮기면서 생긴다.

    한 층 아래: 애노테이션은 클래스 파일 어디에 있고, 엔진은 그것을 어떻게 읽는가

    애노테이션은 주석이 아니다. 컴파일러는 애노테이션을 클래스 파일에 기록하고, JVM은 그것을 리플렉션 API로 꺼내 준다. 다만 모든 애노테이션이 실행 중에 보이는 것은 아니다. 애노테이션 타입에 붙은 @Retention이 그 수명을 정한다. SOURCE는 컴파일러만 보고 버리고, CLASS는 클래스 파일에 기록하지만 실행 중 리플렉션에는 보이지 않으며, RUNTIME이어야 리플렉션으로 읽힌다. 검증 애노테이션은 모두 RUNTIME이다. 그렇지 않으면 실행 중인 엔진이 규칙을 읽을 방법이 없다.

    이것을 눈으로 확인하기 위해 Bean Validation 라이브러리 없이 JDK만으로 작은 검증 엔진을 만들어 보자. 실제 Hibernate Validator의 구조를 흉내 낸 것이 아니라, "애노테이션을 읽어 규칙을 실행한다"는 원리만 떼어 낸 실험이다. 일부러 CLASS 수명의 애노테이션도 하나 섞었다.

    import java.lang.annotation.*;
import java.lang.reflect.Field;
import java.util.*;

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.FIELD)
@interface MyNotBlank { String message() default "공백일 수 없습니다"; }

@Retention(RetentionPolicy.RUNTIME) @Target(ElementType.FIELD)
@interface MyRange { long min(); long max(); String message() default "범위를 벗어났습니다"; }

@Retention(RetentionPolicy.CLASS) @Target(ElementType.FIELD)
@interface InvisibleRule { }

class Product {
    @MyNotBlank String name;
    @MyRange(min = 100, max = 5_000_000) Integer price;
    @MyRange(min = 1, max = 999) @InvisibleRule Integer quantity;
    Product(String name, Integer price, Integer quantity) {
        this.name = name; this.price = price; this.quantity = quantity;
    }
}

public class MiniValidator {
    static List validate(Object target) throws IllegalAccessException {
        List violations = new ArrayList<>();
        Field[] fields = target.getClass().getDeclaredFields();
        Arrays.sort(fields, Comparator.comparing(Field::getName)); // 순서를 고정한다
        for (Field f : fields) {
            f.setAccessible(true);
            Object value = f.get(target);
            MyNotBlank nb = f.getAnnotation(MyNotBlank.class);
            if (nb != null && (value == null || value.toString().isBlank())) {
                violations.add(f.getName() + ": " + nb.message());
            }
            MyRange r = f.getAnnotation(MyRange.class);
            if (r != null && value != null) { // null은 범위 검사 대상이 아니다
                long v = ((Number) value).longValue();
                if (v < r.min() || v > r.max()) {
                    violations.add(f.getName() + "=" + value + ": " + r.message());
                }
            }
            System.out.println(f.getName() + " annotations=" + f.getDeclaredAnnotations().length);
        }
        return violations;
    }

    public static void main(String[] args) throws Exception {
        System.out.println(validate(new Product("  ", 10, null)));
    }
}
    name annotations=1
price annotations=1
quantity annotations=1
[name: 공백일 수 없습니다, price=10: 범위를 벗어났습니다]

    세 가지를 관찰할 수 있다. 첫째, quantity에는 애노테이션이 두 개 붙어 있지만 리플렉션은 하나만 돌려준다. @InvisibleRule은 CLASS 수명이라 실행 중에는 보이지 않는다. 둘째, quantity는 null인데 범위 위반이 나오지 않았다. null은 범위 검사 대상이 아니라고 코드에 적었기 때문이다. 이것은 실제 Bean Validation 명세의 규칙이기도 하다. 셋째, getDeclaredFields()의 반환 순서는 Javadoc상 정해져 있지 않으므로 출력 순서를 고정하려고 이름순으로 정렬했다. 실제 엔진의 위반 순서가 보장되지 않는 것과 같은 맥락이다.

    컴파일된 클래스 파일을 javap -v -p Product.class로 열어 보면 애노테이션이 어디에 기록되는지 보인다.

        InvisibleRule

    RUNTIME 애노테이션은 필드 정보의 RuntimeVisibleAnnotations 속성에, CLASS 애노테이션은 RuntimeInvisibleAnnotations 속성에 들어간다. JVM은 클래스를 로딩할 때 앞의 것만 리플렉션으로 노출한다. #22, #23 같은 번호는 상수 풀(constant pool) 항목을 가리키는데, #22는 애노테이션 타입 LMyRange;, #23은 속성 이름 min, #29는 long 상수 1이다. 즉 @MyRange(min = 1, max = 999)라는 선언은 "타입 이름과 (속성 이름, 상수) 쌍의 목록"으로 직렬화되어 클래스 파일에 들어간다. 사용 지점에 적지 않은 message는 여기에 없다. 기본값은 애노테이션 타입 쪽 클래스 파일, 곧 MyRange.class의 message() 메서드에 AnnotationDefault 속성으로 한 번만 기록되고, 리플렉션이 값을 돌려줄 때 채워진다.

    실제 엔진이 하는 일도 뼈대는 같다. 차이는 규모와 일반성에 있다. Bean Validation 애노테이션에는 @Constraint(validatedBy = ...)라는 메타 애노테이션이 붙어 "이 제약은 어떤 ConstraintValidator 구현이 검사하는가"를 알려 준다. 표준 제약은 명세가 규칙만 정하고 검사 코드는 구현체가 제공하므로 validatedBy가 비어 있고, 구현체가 내부에서 짝을 맞춘다. 직접 만드는 제약은 여기에 검사 클래스를 적는다. 엔진은 클래스의 필드와 게터와 클래스 자체에 붙은 제약을 모아 메타데이터를 만들고, 각 제약에 맞는 검사기를 골라 값과 함께 호출한다.

    값을 읽는 방법도 명세가 정해 두었다. 필드에 붙인 제약은 엔진이 필드에 직접 접근해 값을 읽고, 게터에 붙인 제약은 게터를 호출해 그 반환값을 검사한다(명세 5.1.2절). 게터가 계산된 값을 돌려주거나 지연 로딩 프록시처럼 동작하는 객체라면 두 방식의 결과가 다를 수 있으므로 한 클래스 안에서는 한 방식으로 통일하는 편이 안전하다. 또 Validator 구현은 스레드 안전해야 한다고 명세의 Javadoc이 요구한다. 그래서 요청마다 검증기를 새로 만들 필요가 없고, 스프링은 애플리케이션 전체에서 하나를 공유한다.

    null은 누구의 책임인가

    실험에서 일부러 흉내 낸 규칙을 실제 명세로 확인해 두자. @Max의 Javadoc은 지원 타입(BigDecimal, BigInteger, byte, short, int, long과 각각의 래퍼)을 나열한 뒤 "null elements are considered valid"라고 적는다. @Min, @Size, @Pattern 같은 대부분의 표준 제약이 같은 태도를 갖는다. 명세는 "값의 내용 검사"와 "값의 존재 검사"를 분리하는 것을 좋은 설계로 보고, 존재 검사는 @NotNull 계열에 맡긴다. 그래서 가격 필드에 @NotNull과 @Range를 함께 붙였다. @Range만 붙였다면 가격 칸을 비운 요청이 검증을 통과한다.

    문자열과 컬렉션에서 "비어 있음"을 다루는 세 제약은 기준이 다르다.

    제약거부하는 값지원 타입
    @NotNullnull모든 타입
    @NotEmptynull, 길이(크기)가 0인 값CharSequence, Collection, Map, 배열
    @NotBlanknull, 공백이 아닌 문자가 하나도 없는 값CharSequence

    " "은 @NotEmpty를 통과하지만 @NotBlank는 통과하지 못한다. Hibernate Validator 8.0의 검사기(NotBlankValidator)는 문자열을 trim()한 뒤 길이가 0보다 큰지로 판정한다. 상품 이름처럼 사람이 입력하는 문자열에는 대개 @NotBlank가 맞다.

    표준 제약을 조합해 새 제약을 만들 수도 있다. Hibernate Validator의 @Range가 그 예다. 소스를 보면 @Range 애노테이션 타입 자체에 @Min(0), @Max(Long.MAX_VALUE), @ReportAsSingleViolation이 붙어 있고, min, max 속성이 @OverridesAttribute로 각각 @Min과 @Max의 value를 덮어쓴다. 검사는 @Min과 @Max가 하고, @ReportAsSingleViolation 때문에 둘 중 무엇이 실패하든 위반은 @Range의 것 하나로 보고된다. 구성 요소가 @Min, @Max이니 null을 허용하는 성질도 그대로 물려받는다.

    스프링에 연결하기: 검증기가 모든 WebDataBinder에 들어가는 경로

    이제 같은 Product를 컨트롤러에서 검증하게 하자. 04회에서 만든 상품 컨트롤러를 복사해 새 버전을 만들되, 직접 만든 ProductValidator와 그것을 등록하던 @InitBinder는 지운다. 컨트롤러의 등록 메서드는 거의 그대로다.

    @Controller
@RequestMapping("/v3/products")
public class ProductControllerV3 {

    private final ProductRepository productRepository;

    public ProductControllerV3(ProductRepository productRepository) {
        this.productRepository = productRepository;
    }

    @PostMapping("/add")
    public String add(@Validated @ModelAttribute Product product, BindingResult bindingResult,
                      RedirectAttributes redirectAttributes) {
        if (bindingResult.hasErrors()) {
            return "v3/products/addForm";
        }
        Product saved = productRepository.save(product);
        redirectAttributes.addAttribute("productId", saved.getId());
        return "redirect:/v3/products/{productId}";
    }

    // 목록, 상세, 등록 폼, 수정 ...
}

    검증기를 등록하는 코드가 한 줄도 없는데 @NotBlank가 동작한다. 누가 검증기를 바인더에 넣었는지 추적해 보자. 출발점은 스프링 부트의 자동 구성이다. Spring Boot 3.3의 ValidationAutoConfiguration은 클래스패스에 jakarta.validation.executable.ExecutableValidator가 있고 META-INF/services/jakarta.validation.spi.ValidationProvider 리소스가 있을 때만 동작한다. 앞의 것은 명세 API가 있다는 뜻이고, 뒤의 것은 구현체가 있다는 뜻이다. 조건이 맞으면 jakarta.validation.Validator 빈이 따로 없을 때 defaultValidator라는 이름으로 스프링의 LocalValidatorFactoryBean을 등록한다.

    LocalValidatorFactoryBean은 이중 신분을 가진 객체다. 안에 Bean Validation의 ValidatorFactory와 Validator를 품고 있으면서, 스프링의 org.springframework.validation.Validator 인터페이스도 구현한다. 이 연결 고리가 SpringValidatorAdapter다. 04회에서 직접 만든 검증기가 구현했던 바로 그 스프링 인터페이스(supports, validate(Object, Errors))를 구현하면서, 실제 검사는 안에 품은 Bean Validation 검증기에 위임하고 결과를 Errors에 옮겨 적는다. 스프링 쪽에서 보면 Bean Validation도 그냥 검증기 하나일 뿐이다.

    다음은 스프링 MVC 쪽이다. 스프링 MVC 설정 클래스는 mvcValidator라는 빈으로 "모든 바인더에 넣을 전역 검증기"를 정한다. Spring Framework의 기본 구현은 WebMvcConfigurer.getValidator()가 돌려준 검증기가 있으면 그것을, 없고 클래스패스에 Bean Validation이 있으면 OptionalValidatorFactoryBean을 쓴다. 스프링 부트는 이 메서드를 재정의한다. 역시 WebMvcConfigurer.getValidator()가 돌려준 것이 있으면 그것을 감싸 쓰고, 없으면 컨텍스트에 이미 있는 jakarta.validation.Validator 빈, 곧 앞의 defaultValidator를 찾아 ValidatorAdapter로 감싸 쓴다. 이 전역 검증기는 바인더를 초기화하는 ConfigurableWebBindingInitializer에 들어가고, 이 초기화기는 요청마다 새로 만들어지는 모든 WebDataBinder에 대해 supports가 참이면 binder.setValidator(전역 검증기)를 호출한다. SpringValidatorAdapter.supports는 안에 Bean Validation 검증기가 있으면 타입을 묻지 않고 참을 돌려주므로, 결국 모든 바인더가 Bean Validation 검증기를 갖게 된다.

    애플리케이션 시작 시 검증기가 만들어져 전역 검증기로 지정되고, 요청마다 바인더에 들어가 바인딩 뒤에 실행되어 위반이 FieldError로 바뀌는 흐름을 보여 준다. A clean two-lane sequence diagram on a white background. Top lane labeled "애플리케이션 시작" contains three boxes left to right connected by arrows: "LocalValidatorFactoryBean" (with a small inner box labeled "Hibernate Validator"), "mvcValidator (ValidatorAdapter)", "ConfigurableWebBindingInitializer". Bottom lane labeled "요청 하나" contains five boxes left to right connected by arrows: "WebDataBinder 생성", "바인딩", "binder.validate()", "SpringValidatorAdapter", "BindingResult". A dashed arrow goes from "ConfigurableWebBindingInitializer" down to "WebDataBinder 생성" labeled "setValidator". Under "SpringValidatorAdapter" draw a small arrow labeled "ConstraintViolation → FieldError" pointing into "BindingResult". Under "바인딩" a small red note labeled "typeMismatch" also pointing into "BindingResult". Flat vector style, muted blue and gray, no 3D. 검증기는 시작할 때 한 번 만들어져 모든 요청의 바인더가 공유하고, 바인딩 오류와 검증 오류는 같은 BindingResult에 모인다.

    이 경로를 알면 자주 겪는 두 가지 현상이 설명된다. 하나는 @InitBinder에서 04회처럼 binder.addValidators(productValidator)로 직접 만든 검증기를 추가하면 Bean Validation과 직접 만든 검증기가 둘 다 실행된다는 것이다. addValidators는 목록에 덧붙이고, DataBinder.validate는 목록의 모든 검증기를 같은 BindingResult로 차례로 호출한다. 반대로 binder.setValidator(productValidator)를 쓰면 setValidator가 목록을 비운 뒤 하나만 넣으므로 그 바인더에서는 Bean Validation이 빠진다. 다른 하나는 WebMvcConfigurer를 구현해 getValidator()로 검증기를 돌려주면 스프링 부트가 그것을 전역 검증기로 쓰므로 애노테이션 검증이 애플리케이션 전체에서 사라진다는 것이다. 둘 다 오류 없이 조용히 일어난다.

    위 클래스 이름과 조건은 Spring Boot 3.3 소스 기준이다. Spring Boot 4.x에서는 검증 자동 구성이 별도 모듈로 옮겨져 패키지가 바뀌었지만(org.springframework.boot.validation.autoconfigure), mvcValidator()가 getValidator() 결과를 먼저 쓰고 없으면 기존 검증기 빈을 감싸는 구조는 Boot 4.1 소스에서도 같다.

    바인딩에 실패한 필드는 검증 결과에서 빠진다

    04회에서 바인딩과 검증은 같은 BindingResult를 공유한다고 했다. 그러면 가격 칸에 abc를 넣었을 때는 어떻게 될까. 바인딩 단계에서 "abc"를 Integer로 바꾸지 못해 typeMismatch 오류가 등록되고, 가격 필드는 대입되지 않은 채 null로 남는다. 이어서 검증이 실행되면 @NotNull이 붙은 가격이 null이니 위반이 하나 더 생긴다. 사용자는 "숫자를 입력하세요"와 "값을 입력하세요"를 동시에 보게 될 것 같다. 실제로는 그렇지 않다.

    이유는 SpringValidatorAdapter가 위반을 옮겨 적는 메서드 processConstraintViolations에 있다. Spring Framework 7.0 소스는 먼저 BindingResult의 모든 오류를 훑어 isBindingFailure()가 참인 FieldError의 필드 이름을 모아 두고, 위반 하나하나에 대해 그 필드가 목록에 있으면 건너뛴다. 소스의 주석은 이것을 "바인딩이 성공한 필드에 대해서만" 위반을 오류로 바꾼다고 설명한다. Spring Framework 6.1 소스는 필드별로 errors.getFieldError(field)를 꺼내 그것이 바인딩 실패가 아닐 때만 진행하는 형태로 같은 일을 한다. 엔진은 객체 전체를 검사하지만, 스프링이 결과를 옮겨 적으며 걸러 내는 것이다.

    Set failedFields = new HashSet<>();
if (errors.hasErrors()) {
    for (ObjectError error : errors.getAllErrors()) {
        if (error instanceof FieldError fieldError && fieldError.isBindingFailure()) {
            failedFields.add(fieldError.getField());
        }
    }
