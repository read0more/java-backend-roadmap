    예외는 결국 누가 받는가

    주문 상세를 보여 주는 컨트롤러가 존재하지 않는 주문 번호를 받아 IllegalStateException을 던졌다고 해 보자. 평범한 자바 프로그램이라면 이 예외를 아무도 잡지 않을 때 스레드가 끝나고, 기본 처리기가 스택 트레이스를 표준 오류에 찍는다. 그런데 웹 애플리케이션에서 요청을 처리하는 스레드는 서블릿 컨테이너의 스레드 풀에서 빌려 온 작업자 스레드다. 이 스레드가 예외 하나 때문에 죽어 버리면 풀은 스레드를 다시 만들어야 하고, 무엇보다 요청을 보낸 클라이언트는 아무 응답도 받지 못한 채 연결만 끊긴다. 그래서 요청 처리의 호출 스택 어딘가에는 반드시 "마지막으로 예외를 받아 주는 곳"이 있어야 하고, 그 자리를 차지하는 것이 서블릿 컨테이너다.

    예외가 위로 올라가는 과정은 JVM 수준에서는 단순하다. 메서드 안에서 예외가 발생하면 JVM은 그 메서드의 예외 테이블(exception table)에서 현재 명령 위치를 덮는 처리기를 찾는다. 찾지 못하면 그 메서드 호출은 갑작스럽게 완료(complete abruptly)되고 프레임이 스택에서 제거된 뒤, 호출한 쪽에서 같은 예외를 다시 찾는다(JVMS §2.10). 이 과정에서 finally 블록은 실행되므로, 필터의 finally에 쓴 로그는 예외가 지나가는 길에도 찍힌다. 요청 하나의 호출 스택을 위에서부터 적으면 "커넥터의 프로세서 → 엔진·호스트·컨텍스트·래퍼의 밸브 → 필터 체인 → 서블릿(DispatcherServlet) → 인터셉터 → 컨트롤러" 순서이고, 컨트롤러에서 던진 예외는 이 프레임들을 아래에서 위로 하나씩 되감으며 올라간다.

    이 회차는 그 되감기가 어디에서 멈추고, 멈춘 뒤 컨테이너가 무엇을 하는지를 다룬다. 결론부터 말하면 컨테이너는 예외를 받아 상태 코드 500을 정하고, 등록된 오류 페이지가 있으면 같은 요청 객체로 오류 페이지 경로를 한 번 더 호출한다. 이 두 번째 호출을 오류 디스패치(error dispatch)라고 부른다. 필터와 인터셉터가 한 요청에서 두 번 불리는 현상, 오류 페이지에서 원래 요청 URI를 꺼낼 수 있는 이유, 스프링 부트의 /error가 아무 설정 없이 동작하는 이유가 모두 이 재호출에서 나온다.

    실험 환경도 정리해 두자. 서블릿 수준 동작은 스프링 없이 내장 Tomcat만으로 확인하는 편이 군더더기가 없다. 이 회차의 서블릿 실험은 JDK 21과 tomcat-embed-core 11.0.27(Servlet 6.1)로 직접 실행했고, 스프링 쪽 설명은 Spring Boot 3.5.0과 Spring Framework 6.2.7 소스를 기준으로 했다. Boot 3.5.0이 기본으로 쓰는 Tomcat은 10.1.41(Servlet 6.0)인데, 이 회차에서 따라가는 StandardHostValve의 예외 처리·forward 코드를 두 버전에서 비교해 보면 Servlet 6.1에 새로 생긴 요청 속성 두 개를 채우는 줄과 디버그 로그 한 줄 말고는 같다. 스프링 부트 프로젝트로 따라 하려면 spring-boot-starter-web과 spring-boot-starter-thymeleaf 의존성이면 충분하다.

    컨테이너가 알아듣는 두 가지 오류 신호

    서블릿이나 필터가 "이 요청은 실패했다"고 컨테이너에 알리는 방법은 두 가지뿐이다. 첫째는 예외를 던져 컨테이너까지 전파하는 것이다. Servlet.service()와 Filter.doFilter()의 시그니처가 선언한 검사 예외는 ServletException과 IOException뿐이므로, 컨테이너까지 올라올 수 있는 것은 이 둘(과 하위 타입), 그리고 선언 없이 던질 수 있는 RuntimeException과 Error다. Jakarta Servlet 명세 §10.9.2도 서블릿이나 필터가 던질 수 있는 예외를 이 세 부류로 적는다. 다른 검사 예외는 컴파일러가 막기 때문에 ServletException으로 감싸서 던져야 한다.

    둘째는 HttpServletResponse.sendError(int) 또는 sendError(int, String)을 호출하는 것이다. 이 메서드는 예외를 던지지 않는다. 메서드는 정상적으로 반환하고, 호출 스택도 평소처럼 되감긴다. 다만 응답 객체에 "오류로 끝났다"는 표시가 남는다. Tomcat 11.0.27의 org.apache.catalina.connector.Response.sendError()를 열어 보면 하는 일이 분명하다. 응답이 이미 커밋되었으면 IllegalStateException을 던지고, 아니면 오류 플래그를 켜고(setError()), 상태 코드와 메시지를 저장하고, 지금까지 버퍼에 쓴 본문을 비우고(resetBuffer()), 응답을 일시 중지(suspended) 상태로 바꾼다. 일시 중지된 응답의 출력 버퍼는 write와 flush 호출을 그냥 무시하므로, sendError 뒤에 본문을 써도 클라이언트에게 가지 않는다.

    여기서 자주 헷갈리는 것이 setStatus(404)다. setStatus는 상태 코드 숫자만 바꾸고 오류 플래그를 켜지 않는다. 명세는 컨테이너와 기본 서블릿이 4xx·5xx 응답에는 sendError를 써서 오류 페이지 메커니즘이 동작하게 하고, 2xx·3xx에는 setStatus를 써서 오류 페이지 메커니즘을 부르지 않는다고 적는다(§10.9.2). 즉 오류 페이지를 띄우는 스위치는 상태 코드 값이 아니라 sendError 호출 여부다. 뒤의 실험에서 setStatus(404)만 한 요청은 404 상태로 나가지만 오류 페이지 없이 서블릿이 쓴 본문 그대로 나가는 것을 볼 수 있다.

    신호호출 스택응답 객체에 남는 것오류 페이지 탐색 기준
    예외 전파예외로 되감김(필터의 finally는 실행됨)컨테이너가 잡아서 요청 속성에 예외 저장, 상태 500, 오류 플래그예외 타입 → (못 찾으면) 상태 코드 → 기본 페이지

    setStatus(code)정상 반환상태 코드만오류 페이지를 찾지 않음

    오류 페이지를 등록하고 찾는 규칙

    오류 페이지는 원래 배포 서술자(web.xml)의 error-page 요소로 등록한다. 요소 하나는 exception-type(예외 클래스 이름)이나 error-code(상태 코드) 중 하나와 location(오류 페이지 경로)을 가진다. 둘 다 없는 error-page는 기본 오류 페이지(default error page)가 된다. 명세 §10.9.2는 매칭 규칙을 다음과 같이 정한다. 예외가 전파되면 exception-type 선언들과 비교하되 클래스 계층에서 가장 가까운 것이 이긴다. 맞는 것이 없고 던져진 예외가 ServletException이면 getRootCause()로 감싸인 예외를 꺼내 한 번 더 비교한다. sendError가 호출되었으면 error-code 선언과 비교한다.

    
    java.lang.RuntimeException
    /error-page/runtime


    404
    /error-page/404


    
    /error-page/default

    Tomcat은 이 규칙을 org.apache.catalina.util.ErrorPageSupport로 구현한다. 예외 타입 매칭은 예외 객체의 클래스 이름으로 맵을 찾고, 없으면 getSuperclass()로 한 단계씩 올라가며 Object 직전까지 반복한다. 그래서 IllegalStateException을 던지면 IllegalStateException → RuntimeException → Exception → Throwable 순서로 찾고, 처음 걸리는 선언이 "가장 가까운 것"이 된다. 인터페이스는 이 탐색에 들어가지 않는다. 상태 코드 매칭은 정수 키로 맵을 찾을 뿐이고, 기본 오류 페이지는 상태 코드 0번 자리에 저장되어 있다. StandardHostValve.status()는 findErrorPage(statusCode)가 null이면 findErrorPage(0)을 한 번 더 부른다.

    두 탐색이 이어지는 방식도 알아 둘 만하다. Tomcat의 StandardHostValve.throwable()은 예외 타입으로 페이지를 찾지 못하면 포기하지 않고, 응답 상태가 400 미만이면 500으로 바꾸고 오류 플래그를 켠 뒤 status()로 넘어간다. 그래서 예외가 전파되었는데 예외 타입 페이지가 없으면 "500번 페이지 → 기본 페이지" 순서로 다시 찾는다. 결과적으로 예외 하나에 대한 탐색 순서는 "예외 타입(계층) → 루트 원인 타입(계층) → 상태 코드 → 기본 페이지"가 된다. 기본 페이지까지 없으면 컨테이너가 스스로 만든 오류 화면이 나간다.

    스프링 부트처럼 내장 서버를 쓰면 web.xml이 없다. 대신 부트의 ErrorPage 객체를 ErrorPageRegistry에 등록한다. 내장 서버 팩토리(ConfigurableWebServerFactory)가 이 인터페이스를 구현하고 있어서, ErrorPageRegistrar 빈을 하나 두면 부트가 팩토리를 초기화할 때 그 빈을 호출해 준다(ErrorPageRegistrarBeanPostProcessor). 아래 코드는 위의 web.xml과 같은 의미다.

    import org.springframework.boot.web.server.ErrorPage;
import org.springframework.boot.web.server.ErrorPageRegistrar;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.http.HttpStatus;

@Configuration(proxyBeanMethods = false)
public class ContainerErrorPageConfig {

    @Bean
    public ErrorPageRegistrar containerErrorPages() {
        return registry -> registry.addErrorPages(
                new ErrorPage(RuntimeException.class, "/error-page/runtime"), // 예외 타입
                new ErrorPage(HttpStatus.NOT_FOUND, "/error-page/404"),       // 상태 코드
                new ErrorPage("/error-page/default"));                        // 기본(전역) 페이지
    }
}

    부트의 ErrorPage는 상태와 예외가 모두 없으면 isGlobal()이 참이고, getStatusCode()는 상태가 없을 때 0을 돌려준다. Boot 3.5.0의 TomcatServletWebServerFactory는 부트 ErrorPage를 Tomcat의 ErrorPage로 옮기면서 setErrorCode(errorPage.getStatusCode())를 호출하므로, 전역 페이지는 Tomcat 안에서 정확히 "0번 상태 코드 = 기본 오류 페이지" 자리에 들어간다. 부트의 추상화가 서블릿 명세의 기본 오류 페이지와 그대로 연결되는 지점이다.

    오류 페이지는 같은 요청의 재디스패치다

    오류 페이지를 찾으면 컨테이너는 그 경로를 호출한다. 이때 클라이언트에게 302 응답을 보내 다시 요청하게 하는 것이 아니다. Tomcat의 StandardHostValve.custom()은 ServletContext.getRequestDispatcher(location)으로 디스패처를 얻어 forward()를 호출한다. 명세 §10.9.1도 오류 처리 자원이 서블릿이나 JSP라면 컨테이너가 만든 원래의 요청·응답 객체를 넘기고, 요청 경로와 속성은 RequestDispatcher.forward를 한 것처럼 설정한다고 적는다. 그래서 오류 페이지를 처리하는 동안 request.getRequestURI()는 오류 페이지 경로를 돌려주지만, 브라우저 주소창의 URL은 원래 요청 그대로이고 HTTP 요청·응답도 한 쌍뿐이다. 같은 작업자 스레드가 같은 요청 객체를 들고 오류 페이지 서블릿까지 내려간다.

    오류 페이지를 호출하기 전에 Tomcat은 요청에 오류 정보를 속성으로 붙이고(setRequestErrorAttributes()), forward() 직전에 응답 버퍼를 비우되 상태 코드와 메시지는 남기고(resetBuffer(true)), 콘텐츠 길이를 초기화한다. 명세가 반드시 설정하라고 정한 속성은 아래 여섯 개다(표 10-1). Servlet 6.1에서는 원래 요청의 HTTP 메서드와 쿼리 문자열을 담는 두 속성이 추가되었고, Tomcat 11은 이것도 채운다. Tomcat 10.1(Servlet 6.0)에는 이 두 상수가 없다.

    이 이름들은 RequestDispatcher.ERROR_STATUS_CODE, ERROR_EXCEPTION 같은 상수로 정의되어 있어서 코드에서는 상수를 쓰면 된다. 명세는 예외 객체 속성이 2.3 버전에 추가된 뒤로 예외 타입과 메시지 속성은 중복이지만 하위 호환을 위해 남겨 둔다고 적는다. 그리고 컨테이너는 이 디스패치의 종류를 DispatcherType.ERROR로 표시한다. Tomcat은 내부 속성에 DispatcherType.ERROR를 넣어 두고, 필터 체인을 만들 때 이 값을 읽어 어떤 필터를 끼울지 고른다. 다음 절의 실험에서 이 모든 것을 출력으로 확인한다.

    하나의 HTTP 요청 안에서 REQUEST 디스패치가 예외로 되감긴 뒤, 컨테이너가 같은 요청 객체로 ERROR 디스패치를 다시 수행하는 흐름을 보여 준다. 가로 16:9 시퀀스 다이어그램. 왼쪽부터 세로 생명선 6개: "클라이언트", "Tomcat 밸브", "필터", "DispatcherServlet", "컨트롤러", "/error 컨트롤러". 위쪽 절반은 "REQUEST 디스패치" 라벨이 붙은 회색 박스로 묶는다: 클라이언트에서 Tomcat 밸브로 "GET /orders/7" 화살표, 밸브→필터→DispatcherServlet→컨트롤러로 이어지는 실선 화살표, 컨트롤러에서 빨간 번개 아이콘과 "예외 발생" 라벨, 그 뒤 컨트롤러→DispatcherServlet→필터→Tomcat 밸브로 되돌아가는 빨간 점선 화살표. Tomcat 밸브 옆에 "오류 페이지 탐색" 메모. 아래쪽 절반은 "ERROR 디스패치" 라벨이 붙은 연한 주황 박스: Tomcat 밸브에서 필터로 "forward /error" 화살표, 필터→DispatcherServlet→/error 컨트롤러로 실선, /error 컨트롤러에서 밸브로 "오류 HTML" 응답 화살표. 마지막으로 밸브에서 클라이언트로 "500 응답 (URL 그대로)" 화살표. 클라이언트와 밸브 사이에 "HTTP 요청·응답은 한 쌍" 메모. 컨트롤러의 예외는 REQUEST 디스패치를 되감아 컨테이너까지 올라가고, 컨테이너는 같은 요청으로 오류 페이지를 ERROR 디스패치한다.

    아래 프로그램은 스프링 없이 내장 Tomcat에 서블릿 두 개와 필터 두 개를 올린다. /ex 서블릿은 쿼리 파라미터 t에 따라 런타임 예외, ServletException으로 감싼 예외, IOException, sendError(404), setStatus(404), 응답을 내보낸 뒤의 예외를 각각 일으킨다. /error-page/* 서블릿은 오류 페이지 역할을 하며 받은 요청 속성을 모두 출력한다. 필터 reqOnly는 REQUEST 디스패치에만, reqErr는 REQUEST와 ERROR 디스패치에 매핑했다. 오류 페이지는 RuntimeException 타입, 404, 500 세 개를 등록했다.

    import jakarta.servlet.*;
import jakarta.servlet.http.*;
import org.apache.catalina.Context;
import org.apache.catalina.startup.Tomcat;
import org.apache.tomcat.util.descriptor.web.*;
import java.io.*;
import java.net.URI;
import java.net.http.*;

public class ErrExp {
    static class LogFilter implements Filter {
        final String name;
        LogFilter(String name) { this.name = name; }
        public void doFilter(ServletRequest req, ServletResponse res, FilterChain chain) throws IOException, ServletException {
            HttpServletRequest r = (HttpServletRequest) req;
            System.out.println("[" + name + "] in  " + r.getDispatcherType() + " " + r.getRequestURI());
            try {
                chain.doFilter(req, res);
            } catch (Exception e) {
                System.out.println("[" + name + "] saw " + e.getClass().getSimpleName());
                throw e;
            } finally {
                System.out.println("[" + name + "] out " + r.getDispatcherType());
            }
        }
    }
    static class ExServlet extends HttpServlet {
        protected void doGet(HttpServletRequest req, HttpServletResponse resp) throws IOException, ServletException {
            String t = req.getParameter("t");
            if ("rt".equals(t)) throw new IllegalStateException("boom");
            if ("wrap".equals(t)) throw new ServletException("wrapped", new IllegalArgumentException("inner"));
            if ("io".equals(t)) throw new IOException("disk");
            if ("404".equals(t)) { resp.sendError(404, "no item"); return; }
            if ("status".equals(t)) { resp.setStatus(404); resp.getWriter().write("plain 404 body"); return; }
            if ("commit".equals(t)) { resp.getWriter().write("partial"); resp.flushBuffer(); throw new IllegalStateException("late"); }
            resp.getWriter().write("ok");
        }
    }
    static class ErrServlet extends HttpServlet {
        protected void service(HttpServletRequest req, HttpServletResponse resp) throws IOException {
            System.out.println("  error page: type=" + req.getDispatcherType() + " uri=" + req.getRequestURI()
                + " status_code=" + req.getAttribute(RequestDispatcher.ERROR_STATUS_CODE)
                + " exception_type=" + req.getAttribute(RequestDispatcher.ERROR_EXCEPTION_TYPE)
                + " message=" + req.getAttribute(RequestDispatcher.ERROR_MESSAGE)
                + " exception=" + req.getAttribute(RequestDispatcher.ERROR_EXCEPTION)
                + " request_uri=" + req.getAttribute(RequestDispatcher.ERROR_REQUEST_URI)
                + " servlet_name=" + req.getAttribute(RequestDispatcher.ERROR_SERVLET_NAME)
                + " resp.status=" + resp.getStatus());
            resp.setContentType("text/plain");
            resp.getWriter().write("custom error page " + req.getRequestURI());
        }
    }
    public static void main(String[] args) throws Exception {
        boolean withPages = args.length == 0;   // 인자를 주면 오류 페이지 없이 실행
        Tomcat tomcat = new Tomcat();
        tomcat.setPort(0);                      // 빈 포트를 OS가 고른다
        tomcat.setBaseDir(new File("tc").getAbsolutePath());
        Context ctx = tomcat.addContext("", null);
        Tomcat.addServlet(ctx, "ex", new ExServlet()); ctx.addServletMappingDecoded("/ex", "ex");
        Tomcat.addServlet(ctx, "err", new ErrServlet()); ctx.addServletMappingDecoded("/error-page/*", "err");
        addFilter(ctx, "reqOnly", new LogFilter("reqOnly"), "REQUEST");
        addFilter(ctx, "reqErr", new LogFilter("reqErr"), "REQUEST", "ERROR");
        if (withPages) {
            ErrorPage p1 = new ErrorPage(); p1.setExceptionType("java.lang.RuntimeException"); p1.setLocation("/error-page/runtime"); ctx.addErrorPage(p1);
            ErrorPage p2 = new ErrorPage(); p2.setErrorCode(404); p2.setLocation("/error-page/404"); ctx.addErrorPage(p2);
            ErrorPage p3 = new ErrorPage(); p3.setErrorCode(500); p3.setLocation("/error-page/500"); ctx.addErrorPage(p3);
        }
        tomcat.getConnector();
        tomcat.start();
        int port = tomcat.getConnector().getLocalPort();
        HttpClient c = HttpClient.newHttpClient();
        for (String t : new String[]{"rt", "wrap", "io", "404", "status", "commit"}) {
            System.out.println("=== GET /ex?t=" + t);
            try {
                HttpResponse r = c.send(HttpRequest.newBuilder(URI.create("http://localhost:" + port + "/ex?t=" + t)).build(), HttpResponse.BodyHandlers.ofString());
                String body = r.body().replaceAll("\\s+", " ");
                System.out.println("  client: " + r.statusCode() + " body=" + (body.length() > 120 ? body.substring(0, 120) + "..." : body));
            } catch (IOException e) {
                System.out.println("  client: " + e);
            }
            Thread.sleep(100);
        }
        tomcat.stop(); tomcat.destroy();
    }
    static void addFilter(Context ctx, String name, Filter f, String... types) {
        FilterDef d = new FilterDef(); d.setFilterName(name); d.setFilter(f); ctx.addFilterDef(d);
        FilterMap m = new FilterMap(); m.setFilterName(name); m.addURLPattern("/*");
        for (String t : types) m.setDispatcher(t);
        ctx.addFilterMap(m);
    }
}

    런타임 예외(t=rt). 필터는 등록 순서대로 reqOnly, reqErr 순으로 들어갔다. 서블릿이 던진 IllegalStateException은 안쪽 필터 reqErr의 catch를 먼저 지나고 바깥 reqOnly를 나중에 지난다. 두 필터 모두 finally의 out을 찍었다. 스택이 되감기는 순서 그대로다. 그다음 줄에서 reqErr만 ERROR 디스패치로 다시 들어온다. 오류 페이지 서블릿 안에서 getRequestURI()는 /error-page/runtime이지만 jakarta.servlet.error.request_uri는 원래 경로 /ex다. forward가 경로를 바꾼다는 것과, 원래 경로는 속성으로 보존된다는 것이 동시에 보인다. 클라이언트는 500 상태와 오류 페이지 본문을 한 번의 응답으로 받았다.

    감싼 예외(t=wrap). 던진 것은 ServletException이고, 이 클래스는 Exception을 상속하지 RuntimeException을 상속하지 않는다. 그래서 첫 번째 탐색(던진 예외 자체의 계층)은 실패하고, 루트 원인 IllegalArgumentException으로 두 번째 탐색을 해서 RuntimeException 페이지가 걸렸다. 속성을 자세히 보면 exception_type과 exception은 루트 원인인데 message는 바깥 예외의 메시지 wrapped다. Tomcat의 throwable()이 속성을 채울 때 타입과 예외 객체에는 루트 원인을, 메시지에는 원래 던져진 예외의 getMessage()를 넘기기 때문이다. 명세가 정한 것이 아니라 Tomcat 구현(10.1.41, 11.0.27 모두 같음)에서 나온 결과이므로, 오류 페이지에서 메시지를 보여 주고 싶다면 메시지 속성보다 예외 객체를 직접 보는 편이 의도가 분명하다.

    검사 예외(t=io). IOException은 RuntimeException 계열이 아니고 ServletException도 아니므로 예외 타입 탐색은 두 번 다 실패한다. Tomcat은 상태를 500으로 두고 status()로 넘어가 500번 페이지를 찾았다. 이 경로는 "상태 코드로 찾은 오류"이므로 exception_type을 채우지 않고, 메시지는 sendError로 지정된 메시지가 없어 빈 문자열이다. 그런데 exception 속성에는 IOException이 들어 있다. 이 값은 오류 페이지를 찾기 전에, 서블릿을 호출한 StandardWrapperValve가 예외를 잡은 순간 이미 요청 속성에 넣어 둔 것이기 때문이다. 같은 500 오류라도 어떤 경로로 페이지가 선택되었느냐에 따라 채워지는 속성이 다르다는 점이 중요하다.

    sendError(t=404)와 setStatus(t=status). sendError(404, "no item")에서는 두 필터의 catch가 아무것도 보지 못했다. 예외가 없었으니 당연하다. 그래도 컨테이너는 응답의 오류 플래그를 보고 404번 페이지로 ERROR 디스패치를 했고, 메시지 속성에는 sendError의 두 번째 인자가 그대로 들어왔다. 반면 setStatus(404)는 오류 디스패치 자체가 일어나지 않았다. 클라이언트는 404 상태와 서블릿이 쓴 본문 plain 404 body를 받았다. 마지막 t=commit은 응답을 먼저 내보낸 뒤 예외를 던진 경우로, 조금 뒤에 따로 다룬다.

    같은 프로그램을 오류 페이지 없이(인자를 하나 주고) 실행하면 t=rt, t=wrap, t=io는 모두 500, t=404는 404 상태로 끝나고, 본문은 Tomcat이 직접 만든 HTML(</code>이 <code>HTTP Status 500 – Internal Server Error</code>인 문서)이다. 필터 <code>reqErr</code>의 <code>ERROR</code> 줄은 하나도 찍히지 않는다. 오류 페이지가 없으면 ERROR 디스패치도 없다.</p> <h3>한 층 아래: Tomcat 밸브 파이프라인</h3> <p>Tomcat은 요청을 컨테이너 계층(엔진 → 호스트 → 컨텍스트 → 래퍼)을 따라 내려보내고, 각 계층은 밸브(valve)의 사슬인 파이프라인을 가진다. 각 파이프라인의 마지막 밸브(basic valve)가 다음 계층의 파이프라인을 부른다. 오류 처리에 관여하는 밸브는 세 개다. 래퍼 계층의 <code>StandardWrapperValve</code>, 호스트 계층의 <code>StandardHostValve</code>, 그리고 호스트 파이프라인에서 <code>StandardHostValve</code>보다 앞에 끼워지는 <code>ErrorReportValve</code>다(<code>StandardHost</code>가 시작할 때 <code>errorReportValveClass</code> 속성의 밸브를 파이프라인에 추가한다).</p> <pre class="diagram">작업자 스레드 └ CoyoteAdapter.service() └ [Engine 파이프라인] StandardEngineValve └ [Host 파이프라인] ErrorReportValve ──▶ StandardHostValve(basic) (3) 커밋 안 됐으면 (2) 오류 플래그를 보고 Tomcat 기본 HTML 작성 오류 페이지 탐색 → forward └ [Context 파이프라인] StandardContextValve └ [Wrapper 파이프라인] StandardWrapperValve (1) 필터 체인·서블릿 호출을 try로 감싸고 예외를 잡으면: 요청 속성에 예외 저장, 상태 500, 오류 플래그 └ ApplicationFilterChain → 필터1 → 필터2 → Servlet.service()</pre> <p><b>(1) 예외를 잡는 곳.</b> <code>StandardWrapperValve.invoke()</code>는 <code>filterChain.doFilter(...)</code> 호출을 <code>try</code>로 감싸고 <code>IOException</code>, <code>ServletException</code>, <code>Throwable</code> 등을 차례로 잡는다. 대부분의 경우 private 메서드 <code>exception()</code>을 부르는데, 하는 일은 세 줄이다. 요청 속성 <code>jakarta.servlet.error.exception</code>에 예외를 넣고, 상태를 500으로 바꾸고, 응답의 오류 플래그를 켠다. 예외는 여기서 삼켜지고 더 위로 올라가지 않는다. 예외 몇 가지는 다르게 다룬다. 잘못된 요청을 뜻하는 Tomcat 내부 예외(<code>BadRequestException</code>)는 500 대신 400을 쓰고, <code>UnavailableException</code>은 서블릿을 사용 불가 상태로 표시하는 별도 경로로 간다. Tomcat 11.0.27 소스의 <code>ExceptionUtils.handleThrowable()</code>은 <code>StackOverflowError</code>는 삼키지만 <code>OutOfMemoryError</code> 같은 <code>VirtualMachineError</code>는 다시 던지므로, 그런 오류는 이 회차의 오류 페이지 경로를 타지 않는다.</p> <p><b>(2) 오류 페이지를 고르는 곳.</b> 컨텍스트 파이프라인 호출이 돌아오면 <code>StandardHostValve.invoke()</code>는 요청 속성에서 예외를 꺼내고, 응답이 오류 보고를 필요로 하는지(<code>isErrorReportRequired()</code>) 확인한다. 예외가 있으면 <code>throwable()</code>, 없으면 <code>status()</code>를 부른다. 앞에서 본 매칭 규칙과 <code>custom()</code>의 forward가 모두 이 클래스 안에 있다. forward가 성공하면 <code>response.finishResponse()</code>로 응답을 끝내 버린다. 이 시점에 응답은 커밋되고 클라이언트로 나간다.</p> <p><b>(3) 마지막 안전망.</b> <code>ErrorReportValve.invoke()</code>는 먼저 다음 밸브(<code>StandardHostValve</code>)를 부르고, 돌아온 뒤 응답이 이미 커밋되었으면 오류 화면을 쓰지 않는다(아직 오류 보고 표시가 없으면 남은 출력을 내보내고 연결만 닫는다). 오류 페이지가 성공적으로 그려졌다면 여기서 끝난다. 커밋되지 않았는데 오류 상태라면 Tomcat이 직접 HTML 오류 보고서를 쓴다. 오류 페이지를 등록하지 않았을 때 본 <code>HTTP Status 500 – Internal Server Error</code> 화면이 이것이다. 이 화면에는 기본 설정에서 예외 보고와 서버 정보가 들어갈 수 있는데, Spring Boot 3.5.0의 <code>TomcatWebServerFactoryCustomizer</code>는 <code>server.error.include-stacktrace</code>가 기본값 <code>never</code>일 때 이 밸브를 <code>setShowReport(false)</code>, <code>setShowServerInfo(false)</code>로 다시 등록한다. 부트 애플리케이션에서 Tomcat 기본 화면까지 떨어지더라도 스택 트레이스와 서버 버전이 노출되지 않는 이유다.</p> <p>이 구조는 "오류 페이지가 또 실패하면 무한히 재시도하는가"라는 질문에도 답을 준다. <code>custom()</code>은 forward 전체를 <code>try</code>로 감싸고 <code>Throwable</code>을 잡으면 로그를 남긴 뒤 <code>false</code>를 반환한다. 오류 페이지를 다시 찾지 않는다. 실제로 기본 오류 페이지 <code>/error</code>로 등록한 서블릿이 항상 예외를 던지게 해 보면, 그 서블릿은 <code>ERROR</code> 디스패치로 딱 한 번 호출되고 클라이언트는 Tomcat 기본 화면(500)을 받는다. 같은 서블릿을 기본 페이지가 아니라 <code>RuntimeException</code> 타입 페이지로 등록하면 결과가 조금 다르다. 역시 한 번만 호출되지만 클라이언트는 본문이 빈 500 응답을 받는다. 예외 타입 경로(<code>throwable()</code>)는 forward하기 <b>전에</b> 응답에 "오류 보고 완료" 표시(<code>setErrorReported()</code>)를 하고, 상태 코드 경로(<code>status()</code>)는 forward가 <b>성공한 뒤에</b> 표시한다. <code>ErrorReportValve</code>는 이 표시가 이미 되어 있으면 기본 화면을 쓰지 않기 때문이다.</p> 계층별 파이프라인을 중첩 상자로 그리고, 예외를 잡는 곳·오류 페이지를 고르는 곳·기본 화면을 쓰는 곳을 번호로 표시한다. 세로 4:3 구조도. 바깥에서 안쪽으로 중첩된 둥근 사각형 4개: 가장 바깥 "Engine", 그 안 "Host", 그 안 "Context", 가장 안쪽 "Wrapper". StandardHostValve 옆에 번호 2와 라벨 "오류 페이지 forward".     응답이 이미 커밋되었다면

    커밋(commit)은 상태 줄과 헤더가 이미 소켓으로 나갔다는 뜻이다. 서블릿이 응답 본문을 쓰면 우선 응답 버퍼에 쌓이고, 버퍼가 가득 차거나 flushBuffer()를 부르면 그 순간 상태 줄과 헤더가 함께 전송된다. 한 번 나간 상태 줄은 되돌릴 수 없다. 실험의 t=commit 케이스는 partial을 쓰고 flushBuffer()로 200 응답을 커밋한 뒤 예외를 던졌다.

    Tomcat의 custom()은 이 상황을 따로 처리한다. 응답이 커밋되었으면 forward 대신 include()로 오류 페이지를 부르고, 버퍼를 비운 뒤, 연결을 즉시 닫는다(ActionCode.CLOSE_NOW). 소스의 주석은 이것을 "할 수 있는 최선"이라고 적고, 연결을 닫는 것은 클라이언트에게 무언가 잘못되었다는 추가 신호라고 설명한다. 실험 출력이 정확히 그렇다. 오류 페이지 서블릿은 type=INCLUDE로 호출되었고, include는 요청 경로를 바꾸지 않으므로 uri=/ex가 찍혔다. status_code 속성은 500이지만 실제 응답 상태는 이미 나간 resp.status=200이다. ERROR 디스패치가 아니므로 reqErr 필터도 불리지 않았다. 청크 전송 인코딩(chunked transfer encoding)으로 나가던 응답이 마지막 청크 없이 끊겼기 때문에, 클라이언트(JDK HttpClient)는 응답을 완성하지 못하고 IOException을 던졌다. 오류 페이지를 등록하지 않은 실행에서도 ErrorReportValve가 같은 방식으로 연결을 닫아 같은 결과가 나온다.

    이 케이스는 실무에서 대용량 파일 다운로드, CSV 스트리밍, 템플릿이 중간에 버퍼를 비운 뒤의 렌더링 실패처럼 "쓰는 도중에 실패"하는 곳에서 나타난다. 이때는 어떤 오류 페이지 설정도 상태 코드를 바꿀 수 없다. 스프링 부트의 화이트라벨 뷰(StaticView)도 응답이 커밋되어 있으면 아무것도 쓰지 않고 Cannot render error page for request [...] as the response has already been committed.로 시작하는 오류 로그만 남긴다. 스트리밍 응답은 시작하기 전에 실패할 수 있는 검증(권한, 존재 여부, 파일 열기)을 모두 끝내 두는 것이 유일한 방어다.

    필터는 오류 디스패치에서 다시 불린다: DispatcherType

    한 요청 안에서 서블릿이 여러 번 호출될 수 있기 때문에, 서블릿 명세는 "이번 호출이 어떤 경로로 들어왔는가"를 jakarta.servlet.DispatcherType 열거형으로 구분한다. 값은 다섯 개다. 클라이언트에서 직접 온 REQUEST, RequestDispatcher.forward()의 FORWARD, include()의 INCLUDE, 오류 페이지 메커니즘의 ERROR, 비동기 처리의 AsyncContext.dispatch()로 들어온 ASYNC다. request.getDispatcherType()으로 현재 값을 읽을 수 있다.

    필터 매핑은 이 값 중 어떤 디스패치에 필터를 끼울지 고를 수 있고, 명세 §6.2.5는 dispatcher 요소가 하나도 없으면 REQUEST로 간주한다고 정한다. Tomcat은 필터 체인을 만들 때(ApplicationFilterFactory) 현재 디스패치 타입을 읽어 각 필터 매핑의 디스패처 비트와 비교하고, 맞는 필터만 체인에 넣는다. 실험에서 reqOnly가 오류 디스패치에 보이지 않고 reqErr만 두 번 보인 것이 이 비교의 결과다. 즉 07회에서 만든 로그 필터나 로그인 체크 필터는, 디스패처 타입을 지정하지 않았다면 오류 페이지 호출에서는 실행되지 않는다.

    스프링 부트의 FilterRegistrationBean도 같은 기본값을 따르되 한 가지 예외가 있다. Boot 3.5.0의 AbstractFilterRegistrationBean.determineDispatcherTypes()는 디스패처 타입을 지정하지 않았을 때, 필터가 스프링의 OncePerRequestFilter이면 모든 타입(EnumSet.allOf)을, 그 밖의 필터면 REQUEST만 쓴다. 오류 디스패치에서도 필터를 실행하고 싶다면 직접 지정한다.

    import jakarta.servlet.DispatcherType;
import jakarta.servlet.Filter;
import org.springframework.boot.web.servlet.FilterRegistrationBean;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class FilterConfig {

    @Bean
    public FilterRegistrationBean accessLogFilter() {
        FilterRegistrationBean bean = new FilterRegistrationBean<>();
        bean.setFilter(new AccessLogFilter());   // AccessLogFilter: jakarta.servlet.Filter 구현 // ...
        bean.setOrder(1);
        bean.addUrlPatterns("/*");
        bean.setDispatcherTypes(DispatcherType.REQUEST, DispatcherType.ERROR);
        return bean;
    }
}

    그렇다면 OncePerRequestFilter는 모든 디스패치에 등록되니 오류 디스패치에서 두 번 실행될까? 아니다. Spring Framework 6.2.7의 OncePerRequestFilter.doFilter()는 먼저 skipDispatch()를 확인한다. 요청에 jakarta.servlet.error.request_uri 속성이 있고(즉 오류 디스패치이고) shouldNotFilterErrorDispatch()가 참이면 자기 로직을 건너뛰고 체인만 넘긴다. 이 메서드의 기본 반환값이 true다. 비동기 디스패치도 shouldNotFilterAsyncDispatch()의 기본값 true로 같은 처리를 한다. 오류 디스패치에서도 실행되기를 원하면 하위 클래스에서 shouldNotFilterErrorDispatch()가 false를 반환하도록 재정의한다. 이 클래스는 한 요청에서 이미 실행되었는지를 "필터이름.FILTERED" 형태의 요청 속성으로 기록하고, 자기 로직이 끝나면 그 속성을 지운다. 컨테이너 수준의 등록(모든 타입)과 필터 내부의 판단(오류 디스패치는 건너뜀)을 분리해 둔 설계다.

    어느 쪽이 옳은 기본값인지는 필터가 하는 일에 달려 있다. 요청 수를 세거나 접근 로그를 남기는 필터를 ERROR에도 걸면 실패한 요청이 두 번 기록된다. 반대로 응답 헤더를 붙이거나 요청 추적 정보를 설정하는 필터가 오류 디스패치에서 빠지면, 오류 페이지를 그리는 동안에는 그 정보가 없을 수 있다.

    인터셉터는 디스패치 타입을 모른다

    스프링 인터셉터(HandlerInterceptor)는 서블릿 컨테이너가 아니라 DispatcherServlet 안에서 동작한다. 컨테이너가 오류 페이지 /error로 ERROR 디스패치를 하면 그 요청도 DispatcherServlet을 지나고, 핸들러 매핑은 /error에 매핑된 컨트롤러를 찾아 등록된 인터셉터와 함께 HandlerExecutionChain을 만든다. 인터셉터 등록에는 디스패치 타입을 고르는 설정이 없으므로, 경로 패턴이 맞으면 오류 디스패치에서도 preHandle이 다시 불린다. 그래서 인터셉터에서는 오류 경로를 경로 패턴으로 빼는 것이 일반적인 방법이다. 경로 비교는 현재 디스패치의 경로로 하므로, ERROR 디스패치에서는 원래 URI가 아니라 /error로 비교된다.

    import jakarta.servlet.http.HttpServletRequest;
import jakarta.servlet.http.HttpServletResponse;
import org.springframework.context.annotation.Configuration;
import org.springframework.web.servlet.HandlerInterceptor;
import org.springframework.web.servlet.ModelAndView;
import org.springframework.web.servlet.config.annotation.InterceptorRegistry;
import org.springframework.web.servlet.config.annotation.WebMvcConfigurer;

class DispatchTraceInterceptor implements HandlerInterceptor {
    @Override
    public boolean preHandle(HttpServletRequest request, HttpServletResponse response, Object handler) {
        System.out.println("preHandle " + request.getDispatcherType() + " " + request.getRequestURI());
        return true;
    }
    @Override
    public void postHandle(HttpServletRequest request, HttpServletResponse response, Object handler,
                           ModelAndView modelAndView) {
        System.out.println("postHandle " + request.getDispatcherType());
    }
    @Override
    public void afterCompletion(HttpServletRequest request, HttpServletResponse response, Object handler,
                                Exception ex) {
        System.out.println("afterCompletion " + request.getDispatcherType() + " ex=" + ex);
    }
}

@Configuration
public class InterceptorConfig implements WebMvcConfigurer {
    @Override
    public void addInterceptors(InterceptorRegistry registry) {
        registry.addInterceptor(new DispatchTraceInterceptor())
                .order(1)
                .addPathPatterns("/**")
                .excludePathPatterns("/error", "/error-page/**"); // 이 줄을 빼면 오류 디스패치에서도 호출된다
    }
}

    예외가 났을 때 인터셉터의 세 메서드가 어떻게 불리는지는 DispatcherServlet.doDispatch()를 읽으면 정확히 알 수 있다. 6.2.7 소스의 뼈대는 이렇다. applyPreHandle → ha.handle(...)(컨트롤러 호출) → applyPostHandle이 하나의 try 안에 있고, 여기서 난 예외는 dispatchException 변수에 담긴다. 그다음 processDispatchResult()가 예외를 HandlerExceptionResolver들에게 넘긴다. 아무 리졸버도 처리하지 못하면 예외를 다시 던지고, 바깥 catch가 triggerAfterCompletion(..., ex)을 부른 뒤 또 다시 던진다. 결과적으로 다음이 성립한다.

    • 컨트롤러가 예외를 던지면 applyPostHandle에 도달하지 못하므로 postHandle은 호출되지 않는다.
    • afterCompletion은 preHandle이 true를 반환한 인터셉터에 대해 역순으로 호출된다(HandlerExecutionChain이 기록한 interceptorIndex부터 0까지). afterCompletion 안에서 난 예외는 로그만 남기고 삼킨다.
    • 리졸버가 예외를 처리하지 못했을 때 afterCompletion의 ex는 컨트롤러가 던진 바로 그 예외 객체다. 반대로 리졸버가 처리했다면(@ExceptionHandler 등) processDispatchResult()가 정상 경로로 triggerAfterCompletion(request, response, null)을 부르므로 ex는 null이다. "afterCompletion의 ex가 null이면 성공한 요청"이라고 판단하면 틀릴 수 있다.

    제외 패턴 줄을 지운 채로 /orders/7에서 IllegalStateException이 나는 경우를 소스대로 추적하면(직접 실행한 결과가 아니라 위의 분기를 따라 정한 순서다) 출력은 다음 순서가 된다. ERROR 디스패치에서 BasicErrorController는 정상적으로 반환하므로 그때는 postHandle이 불리고 ex는 null이다.

    preHandle REQUEST /orders/7
afterCompletion REQUEST ex=java.lang.IllegalStateException: ...
preHandle ERROR /error
postHandle ERROR
afterCompletion ERROR ex=null

DispatcherServlet.processHandlerException()은 등록된 HandlerExceptionResolver들을 순서대로 부르고, 처음으로 null이 아닌 ModelAndView를 돌려준 리졸버에서 멈춘다. 모두 null이면 throw ex로 예외를 그대로 다시 던진다. 스프링 부트에서는 이 목록의 맨 앞에 DefaultErrorAttributes가 있다. 이 클래스는 ErrorAttributes이면서 HandlerExceptionResolver이기도 하고, 순서가 Ordered.HIGHEST_PRECEDENCE다. 하는 일은 예외를 자기만 아는 요청 속성(DefaultErrorAttributes.class.getName() + ".ERROR")에 저장하고 null을 반환하는 것뿐이다. 예외를 처리하지는 않고 기록만 해 두었다가, 나중에 오류 디스패치에서 오류 정보를 만들 때 다시 꺼내 쓴다. 나머지 리졸버(@ExceptionHandler를 처리하는 리졸버 등)의 동작은 09회 「API 예외 처리」에서 자세히 다룬다.

    리졸버가 모두 포기한 예외는 doDispatch()와 doService()를 지나 FrameworkServlet.processRequest()에 도착한다. 6.2.7 소스에서 이 메서드는 ServletException과 IOException은 그대로 다시 던지고, 그 밖의 모든 Throwable은 new ServletException("Request processing failed: " + ex, ex)로 감싸 던진다. HttpServlet.service()의 시그니처가 허용하는 예외로 바꾸는 것이다. 그래서 컨트롤러의 IllegalStateException은 컨테이너에 ServletException으로 도착하고, Tomcat은 그 루트 원인을 꺼내 로그를 찍고 오류 페이지를 찾는다. 앞의 명세 규칙에서 "ServletException이면 루트 원인으로 한 번 더 찾는다"가 왜 필요한지가 여기서 드러난다. 프레임워크가 예외를 감싸도 원래 예외 타입으로 오류 페이지를 고를 수 있어야 하기 때문이다.

    오류 디스패치로 가는 또 하나의 길은 리졸버가 예외를 sendError로 바꾸는 경우다. 예를 들어 Spring Framework 6.1부터 정적 자원 처리기(ResourceHttpRequestHandler)는 요청한 파일을 찾지 못하면 NoResourceFoundException을 던지고, DefaultHandlerExceptionResolver는 이 예외를 받아 response.sendError(404, 상세 메시지)를 호출한 뒤 빈 ModelAndView를 반환한다. 빈 ModelAndView는 "처리 완료, 그릴 뷰 없음"이라는 뜻이라 예외는 더 올라가지 않는다. 서블릿은 정상 반환하지만 응답에는 오류 플래그와 404가 남아 있으므로, 컨테이너는 상태 코드 경로로 오류 페이지를 찾는다. 스프링 부트에서 없는 URL을 요청하면 /error가 404 화면을 그리는 것이 이 경로다. 정리하면 스프링 MVC 요청이 /error에 도달하는 길은 "예외가 컨테이너까지 전파"와 "리졸버나 코드가 sendError 호출" 두 가지이고, 이것은 서블릿 명세의 두 가지 오류 신호와 정확히 같다.

    스프링 부트가 /error를 만드는 방법

    스프링 부트로 웹 애플리케이션을 만들면 오류 페이지를 하나도 등록하지 않아도 브라우저에서는 화이트라벨 오류 페이지가, API 클라이언트에서는 JSON 오류 응답이 나온다. 부트 레퍼런스 문서는 이것을 "모든 오류를 처리하는 /error 매핑을 제공하고, 서블릿 컨테이너에 '전역' 오류 페이지로 등록한다"고 설명한다. 이 동작은 ErrorMvcAutoConfiguration이 등록하는 빈 몇 개의 협업이다(Boot 3.5.0 소스 기준).

    ErrorPageCustomizer가 등록한 전역 페이지는 앞에서 본 대로 Tomcat 안에서 상태 코드 0번, 즉 기본 오류 페이지가 된다. 이 사실에서 중요한 결론이 하나 나온다. 부트의 /error는 가장 마지막 후보다. 직접 ErrorPageRegistrar로 예외 타입 페이지나 상태 코드 페이지를 등록하면, Tomcat은 그것을 먼저 찾고 아무것도 맞지 않을 때만 /error로 간다. 컨테이너 수준 오류 페이지와 부트의 오류 컨트롤러는 경쟁 관계가 아니라 같은 탐색 순서의 앞뒤 자리에 있는 것이다.

    BasicErrorController는 같은 경로에 메서드 두 개를 둔다. errorHtml()은 produces = "text/html"이 붙어 있어 요청의 Accept 헤더가 HTML을 원할 때(브라우저) 선택되고, 오류 뷰를 찾아 ModelAndView를 반환한다. 다른 모든 요청은 error()가 받아 오류 정보 Map을 ResponseEntity 본문으로 돌려주고, 메시지 컨버터가 JSON으로 쓴다. 두 메서드 모두 상태 코드를 jakarta.servlet.error.status_code 요청 속성에서 읽는다(AbstractErrorController.getStatus()). 속성이 없거나 알 수 없는 값이면 500으로 본다. 상태 코드 결정 권한이 컨트롤러가 아니라 컨테이너가 남긴 속성에 있다는 점이, 오류 컨트롤러가 일반 컨트롤러와 다른 부분이다.

    오류 정보 모델은 DefaultErrorAttributes가 만든다. 상태는 jakarta.servlet.error.status_code에서, 경로는 jakarta.servlet.error.request_uri에서 가져온다. 예외는 자기가 리졸버 단계에서 저장해 둔 속성을 먼저 보고, 없으면 jakarta.servlet.error.exception을 본다. 꺼낸 예외가 ServletException이고 원인이 있으면 원인 쪽으로 계속 벗겨 낸다. 그래서 프레임워크가 감싼 ServletException이 아니라 컨트롤러가 던진 원래 예외의 클래스 이름이 exception 항목이 된다. 메시지는 jakarta.servlet.error.message가 비어 있지 않으면 그것을, 비어 있으면 예외의 메시지를, 둘 다 없으면 No message available을 쓴다. 실험의 t=io에서 본 것처럼 상태 코드 경로로 선택된 오류 페이지에서는 메시지 속성이 빈 문자열이므로, 부트에서 예외가 전파된 경우의 메시지는 대개 예외 객체의 메시지가 된다.

    어떤 오류 뷰가 선택되는가

    errorHtml()은 먼저 등록된 ErrorViewResolver들에게 뷰를 묻는다. 기본 구현 DefaultErrorViewResolver.resolveErrorView()의 규칙은 짧다. 먼저 상태 코드 그대로의 이름("500")으로 찾고, 없으면 상태 코드의 계열(series)이 4xx면 "4xx", 5xx면 "5xx"로 다시 찾는다. 이름 하나를 찾는 resolve()는 앞에 error/를 붙인 뒤, 그 이름의 템플릿이 있는지 템플릿 엔진별 TemplateAvailabilityProvider에게 묻고, 없으면 정적 자원 위치들(spring.web.resources.static-locations, 기본값은 classpath:/META-INF/resources/, classpath:/resources/, classpath:/static/, classpath:/public/)에서 error/500.html 파일을 찾는다. 여기서 순서를 정확히 읽어야 한다. 템플릿과 정적 파일을 한 이름 안에서 먼저 모두 본 다음에 계열 이름으로 넘어간다.

"템플릿이 정적 파일보다 우선"이라고 외워 두면 틀리는 지점이다. 정확한 규칙은 "구체적인 상태 코드가 계열보다 우선, 같은 이름 안에서는 템플릿이 정적 파일보다 우선"이다. 정적 HTML이 선택되면 부트는 그 파일을 그대로 복사해 응답하는 내부 뷰(HtmlResourceView)를 쓰므로 모델 값을 출력할 수 없다. 오류 정보(상태, 경로)를 화면에 넣고 싶다면 템플릿을 써야 한다.

    5번과 6번은 조건부 빈 등록으로 연결되어 있다. WhitelabelErrorViewConfiguration에는 ErrorTemplateMissingCondition이 붙어 있어서, 템플릿 엔진이 error라는 템플릿을 찾을 수 있으면 화이트라벨 뷰 빈 자체가 만들어지지 않는다. 그러면 ModelAndView("error")는 일반 뷰 리졸버(Thymeleaf)가 templates/error.html로 해석한다. 템플릿이 없으면 이름이 error인 StaticView 빈이 등록되고 BeanNameViewResolver가 그 빈을 찾는다. 이 뷰는 Whitelabel Error Page 제목과 This application has no explicit mapping for /error, so you are seeing this as a fallback. 문장, 시각, 오류 종류와 상태를 HTML 이스케이프해서 쓴다. server.error.whitelabel.enabled=false로 끄면 이 빈이 없어지고, error 뷰를 해석할 수 없으면 오류 디스패치 자체가 실패해 결국 앞에서 본 Tomcat 기본 화면까지 떨어진다.

    템플릿에서는 모델의 키를 그대로 쓴다. 기본으로 들어 있는 키는 timestamp, status, error(상태의 이유 문구), path이고, 다음 절의 설정에 따라 exception, message, trace, errors가 추가된다.

    오류 응답에 무엇을 남길 것인가: server.error 설정

    오류 정보는 디버깅에는 유용하지만 외부에 그대로 보이면 위험하다. 스택 트레이스는 내부 패키지 구조와 사용하는 라이브러리를 드러내고, 예외 메시지에는 SQL 일부나 내부 식별자, 사용자가 입력한 값이 섞여 있을 수 있다. 부트는 그래서 오류 모델에 들어갈 항목을 설정으로 고르게 하고, 위험한 항목은 기본으로 뺀다. Boot 3.5.0의 ErrorProperties 기본값은 다음과 같다.

    속성기본값모델의 키
    server.error.path/error(오류 컨트롤러 경로)
    server.error.include-exceptionfalseexception
    server.error.include-stacktracenevertrace
    server.error.include-messagenevermessage
    server.error.include-binding-errorsnevererrors
    server.error.include-pathalwayspath
    server.error.whitelabel.enabledtrue(화이트라벨 뷰 등록 여부)

    include-exception을 뺀 나머지 include-* 속성은 never, always, on-param 중 하나다. on-param이면 요청 파라미터로 켠다. BasicErrorController가 보는 파라미터 이름은 각각 trace, message, errors, path이고, 파라미터가 있으면서 값이 false가 아니면 켠 것으로 본다. 오류 디스패치는 원래 요청의 forward이므로 원래 요청의 쿼리 문자열이 그대로 보인다. 즉 on-param은 "누구든 URL에 ?trace를 붙이면 스택 트레이스를 볼 수 있다"는 뜻이 되므로, 운영 환경에서 켜는 것은 always와 크게 다르지 않다.

    구현은 "일단 다 만들고 허용되지 않은 키를 지우는" 방식이다. DefaultErrorAttributes는 시각, 상태, 이유 문구, 예외 클래스, 메시지, 경로를 모두 계산하고(스택 트레이스는 요청받았을 때만 계산), 마지막에 ErrorAttributeOptions.retainIncluded()가 포함되지 않은 키를 맵에서 제거한다. 3.5.0의 ErrorAttributeOptions.defaults()는 PATH, STATUS, ERROR를 포함하고, timestamp는 제거 대상 목록(Include 열거형)에 아예 없어서 항상 남는다. 결과적으로 기본 설정의 JSON 오류 응답은 timestamp, status, error, path 네 키로 이루어진다. 열거형의 STATUS와 ERROR에는 @since 3.2.7, PATH에는 @since 3.3.0이 붙어 있으니, 그보다 오래된 3.x에서는 이 키들을 옵션으로 지울 수 없었다.

    # 개발 중에만: 예외 클래스와 메시지를 응답에 포함
server.error.include-exception=true
server.error.include-message=always
# 스택 트레이스는 ?trace 파라미터가 있을 때만
server.error.include-stacktrace=on-param

    이 설정은 HTML 화면과 JSON 응답 양쪽의 모델에 똑같이 적용된다. 운영 환경에서는 기본값을 유지하고, 원인 분석은 응답이 아니라 서버 로그로 하는 것이 원칙이다. 앞에서 본 것처럼 Tomcat은 서블릿이 던진 예외를 잡을 때 루트 원인과 함께 오류 로그를 남기므로, 오류 응답에서 정보를 빼도 로그에는 스택 트레이스가 남는다.

    흔한 오해와 함정

    "오류 페이지로 리다이렉트된다." 리다이렉트는 3xx 응답과 클라이언트의 두 번째 요청이 필요하지만, 오류 페이지는 서버 안의 forward다. 주소창은 바뀌지 않고, 응답 상태는 원래 오류 상태 그대로다. 그래서 오류 페이지 컨트롤러가 redirect:를 반환하는 식으로 "오류 화면으로 이동"을 흉내 내면 상태 코드가 3xx로 바뀌어 검색 엔진이나 API 클라이언트가 오류를 오류로 인식하지 못한다.

    "404 상태를 주면 404 페이지가 뜬다." 오류 페이지 메커니즘의 스위치는 sendError다. setStatus(404)나 ResponseEntity.status(404).body(...)는 상태만 정할 뿐 오류 디스패치를 일으키지 않는다. 반대로 @ResponseStatus를 붙인 예외나 ResponseStatusException처럼 스프링이 sendError로 바꿔 주는 경로는 오류 디스패치로 이어진다(이 변환의 자세한 규칙은 09회의 몫이다).

    "RuntimeException 오류 페이지를 등록하면 모든 예외가 잡힌다." 검사 예외인 IOException은 RuntimeException의 하위 타입이 아니어서 걸리지 않는다. ServletException도 마찬가지인데, 이 경우는 루트 원인으로 다시 찾으므로 원인이 런타임 예외면 걸린다. 모든 예외를 한 페이지로 보내려면 Throwable이나 Exception으로 등록하거나 기본 오류 페이지를 두어야 한다. 또 Exception으로 등록하면 ServletException 자체가 첫 번째 탐색에서 걸리므로, 루트 원인 타입별로 나눈 페이지들은 두 번째 탐색까지 가지 못한다는 점도 기억하자.

    "오류 페이지에서 또 오류가 나면 무한 루프가 생긴다." Tomcat은 오류 페이지 forward 중의 예외를 잡아 로그만 남기고 다시 오류 페이지를 찾지 않는다. 결과는 기본 오류 페이지(부트의 /error)가 실패했을 때는 Tomcat 기본 화면, 예외 타입 페이지가 실패했을 때는 빈 본문의 500 응답이다. 무한 루프는 없어도, 오류 페이지가 실패하면 사용자에게는 서버 정보가 담길 수 있는 기본 화면이나 빈 화면이 보이고 원래 예외와 오류 페이지의 예외가 로그에 함께 남아 원인 분석이 어려워진다. 오류 페이지는 데이터베이스 조회나 세션 접근처럼 실패할 수 있는 일을 최소화한다.

    "필터 로그가 두 번 찍히는 것은 버그다." ERROR 디스패치에 매핑된 필터라면 정상 동작이다. 원래 요청과 오류 페이지 호출을 구분하려면 request.getDispatcherType()을 함께 찍는다. 같은 맥락에서 인터셉터의 preHandle이 오류 경로에서 다시 불려 로그인 검사가 오류 화면 요청까지 막는 일이 생기므로, 07회의 로그인 인터셉터에도 /error 제외가 필요하다.

    "오류 페이지에서 request.getRequestURI()로 실패한 경로를 알 수 있다." forward 이후의 getRequestURI()는 오류 페이지 경로다. 실패한 원래 경로는 jakarta.servlet.error.request_uri 속성에 있고, 부트의 오류 모델에서는 path다. 응답이 커밋되어 include로 처리된 경우만 예외적으로 getRequestURI()가 원래 경로를 돌려준다.

    정리: 오류 한 건이 화면이 되기까지

    이 장의 핵심

    서블릿 컨테이너가 이해하는 오류 신호는 "예외 전파"와 "sendError" 두 가지뿐이고, 둘 다 같은 결말로 이어진다. 컨테이너가 오류 페이지를 고른 뒤 같은 요청 객체로 그 경로를 ERROR 디스패치하는 것이다. 필터가 두 번 불리는 현상, 오류 속성으로 원래 경로를 아는 방법, 부트의 /error가 아무 설정 없이 동작하는 이유, 커밋된 응답에서 오류 페이지가 무력한 이유가 모두 이 재디스패치 하나로 설명된다.

    다음 09회 「API 예외 처리」에서는 같은 문제를 반대쪽에서 본다. 이 회차의 방식은 예외가 DispatcherServlet 밖으로 나가 컨테이너를 한 바퀴 돈 뒤 다시 들어오는 구조인데, JSON을 주고받는 API에서는 이 왕복 없이 DispatcherServlet 안에서 HandlerExceptionResolver와 @ExceptionHandler로 예외를 끝내는 경우가 많다. 그 경우 이 회차에서 본 ERROR 디스패치가 아예 일어나지 않는다는 점이 두 회차를 잇는 연결 고리다.
    두 가지 오류 신호
    서블릿·필터가 컨테이너에 실패를 알리는 방법은 예외를 전파하는 것과 sendError를 호출하는 것뿐이다. setStatus는 상태만 바꾸고 오류 페이지를 부르지 않는다.
    오류 페이지 매칭
    예외 타입은 클래스 계층에서 가장 가까운 선언이 이기고, 못 찾으면 ServletException의 루트 원인으로 다시 찾는다. 그래도 없으면 상태 코드, 마지막으로 기본 오류 페이지(Tomcat 내부 코드 0)를 본다.
    ERROR 디스패치
    오류 페이지는 리다이렉트가 아니라 같은 요청 객체로 하는 forward다. DispatcherType.ERROR로 표시되고 jakarta.servlet.error.* 속성에 원래 상태·예외·URI가 담긴다.
    Tomcat 밸브
    StandardWrapperValve가 예외를 잡아 기록하고, StandardHostValve가 오류 페이지로 forward하며, 응답이 비어 있으면 ErrorReportValve가 기본 화면을 쓴다.
    커밋된 응답
    이미 헤더가 나간 응답에서는 상태를 바꿀 수 없어 Tomcat이 오류 페이지를 include하고 연결을 닫는다. 클라이언트는 잘린 응답을 받는다.
    필터와 DispatcherType
    필터 매핑의 기본은 REQUEST뿐이다. 부트의 FilterRegistrationBean은 OncePerRequestFilter만 모든 타입에 등록하고, 그 필터는 기본적으로 오류 디스패치를 스스로 건너뛴다.
    인터셉터와 오류 경로
    인터셉터는 디스패치 타입을 구분하지 않으므로 /error를 excludePathPatterns로 빼야 한다. 예외가 나면 postHandle은 생략되고 afterCompletion이 역순으로 불린다.
    부트의 /error
    ErrorPageCustomizer가 /error를 전역 오류 페이지로 등록하고, BasicErrorController가 HTML이면 뷰를, 그 밖에는 JSON을 만든다.
    오류 뷰 우선순위
    정확한 코드(템플릿 → 정적) → 계열 4xx/5xx(템플릿 → 정적) → error 템플릿 → 화이트라벨 순이다. 노출 항목은 server.error.include-*로 정하며 기본은 시각·상태·이유 문구·경로뿐이다.

    장애 대응에서 이 지식이 가장 먼저 쓰이는 곳은 "사용자는 500을 봤다는데 로그에 컨트롤러 예외가 없다"는 신고다. 오류 디스패치가 있다는 것을 알면 확인할 곳이 늘어난다. 원래 요청이 sendError로 끝났을 수도 있고(리졸버나 필터가 호출), 오류 페이지 자체가 실패해 Tomcat 기본 화면이 나갔을 수도 있고, 응답이 커밋된 뒤 예외가 나서 연결이 끊겼을 수도 있다. 접근 로그에 같은 요청이 두 번 찍힌다면 로그 필터가 ERROR 디스패치에도 걸려 있는지부터 본다. getDispatcherType()과 jakarta.servlet.error.request_uri를 로그에 남겨 두면 이런 분석이 훨씬 빨라진다.

    설계 판단에서는 "오류를 어느 층에서 끝낼 것인가"가 핵심 질문이다. 서버가 HTML을 그리는 애플리케이션이라면 컨테이너의 오류 페이지와 부트의 error/ 템플릿 규칙만으로 충분한 경우가 많다. 상태 코드별 화면을 만들고 계열 템플릿으로 나머지를 덮으면 된다. 반면 JSON API라면 컨테이너를 한 바퀴 도는 구조는 응답 형식을 통제하기 어렵고 필터·인터셉터가 두 번 실행되는 비용도 있어서, DispatcherServlet 안에서 예외를 끝내는 쪽을 선호하게 된다. 같은 애플리케이션에서 두 방식이 섞이면, 어떤 예외가 어느 쪽으로 가는지 표로 정리해 두는 것이 좋다.

    보안 관점의 판단은 단순하다. 운영 환경에서 include-stacktrace와 include-message는 기본값 never를 유지하고, on-param을 쓰지 않는다. 오류 메시지를 사용자에게 보여 주어야 한다면 예외 메시지를 그대로 노출하지 말고, 미리 정의한 안전한 메시지(03회의 메시지 소스를 쓸 수 있다)로 바꿔 템플릿에서 출력한다. 조건이 달라지는 경우는 내부망 전용 관리 도구처럼 접근이 통제된 환경뿐인데, 그때도 스택 트레이스보다 상관관계 ID(요청 추적 번호)를 화면에 보여 주고 로그에서 찾게 하는 방식이 더 안전하다.

(a)에서 jakarta.servlet.error.exception_type과 jakarta.servlet.error.message의 값도 예측하라.
  • 스프링 부트 애플리케이션에서 컨트롤러 메서드가 HttpServletResponse를 파라미터로 받아 response.sendError(404, "없음")을 호출하고 반환 타입 void로 끝난다. REQUEST와 ERROR에 모두 매핑된 필터 하나, /error를 제외하지 않은 인터셉터 하나가 있을 때 필터의 doFilter 진입, 인터셉터의 세 메서드, 오류 컨트롤러 호출을 시간 순서대로 적어라.
  • 요청 수를 세는 Filter를 FilterRegistrationBean으로 등록하면서 setDispatcherTypes(DispatcherType.REQUEST, DispatcherType.ERROR)를 지정했더니, 모니터링 대시보드에서 오류 요청이 정상 요청보다 두 배로 집계되었다. 원인을 설명하고 고치는 방법 두 가지를 제시하라.
  • CSV 다운로드 컨트롤러가 응답 스트림에 데이터를 쓰는 도중(이미 여러 번 버퍼가 비워진 뒤) 데이터베이스 예외를 맞았다. templates/error/5xx.html을 잘 만들어 두었는데 사용자가 받은 것은 무엇이며, 왜 오류 페이지가 도움이 되지 않는지 Tomcat의 custom() 동작으로 설명하라.
  • src/main/resources 아래에 templates/error/4xx.html, static/error/404.html, templates/error.html이 있다. 브라우저로 (a) 없는 URL을 요청했을 때(404), (b) 405 오류가 났을 때, (c) 500 오류가 났을 때 각각 어떤 파일이 선택되는지 DefaultErrorViewResolver의 규칙으로 답하라.

    1. (a) Tomcat은 먼저 던져진 예외 자체(ServletException)의 계층을 ServletException → Exception 순으로 올라가며 찾고, Exception에서 /x가 걸린다. 첫 번째 탐색에서 찾았으므로 루트 원인으로 다시 찾는 단계는 없다. 하지만 속성을 채울 때 Tomcat(10.1.41, 11.0.27)은 타입에는 루트 원인의 클래스를, 메시지에는 던져진 예외의 메시지를 넘기므로 exception_type은 IllegalStateException, message는 outer다. exception 속성도 루트 원인이다. (b) 예외가 아니므로 상태 코드 500으로 찾는데 500 페이지도, 기본 페이지도 없다. 오류 디스패치 없이 ErrorReportValve가 Tomcat 기본 500 화면을 쓴다. (c) NullPointerException → RuntimeException → Exception에서 /x가 걸린다.

    2. 필터 진입(REQUEST) → 인터셉터 preHandle(REQUEST) → 컨트롤러가 sendError 후 정상 반환 → 예외가 없으므로 postHandle(REQUEST) → afterCompletion(REQUEST, ex=null) → 필터에서 나옴 → 컨테이너가 오류 플래그를 보고 404 페이지를 찾음(부트에서는 기본 페이지 /error) → 필터 진입(ERROR) → preHandle(ERROR) → BasicErrorController → postHandle(ERROR) → afterCompletion(ERROR, ex=null) → 필터에서 나옴. 컨트롤러가 정상 반환했기 때문에 REQUEST 디스패치에서도 postHandle이 불린다는 점이 예외 전파의 경우와 다르다.

    3. 실패한 요청은 REQUEST 디스패치에서 한 번, 오류 페이지를 그리는 ERROR 디스패치에서 또 한 번 필터를 지나므로 두 번 집계된다. 고치는 방법은 (1) 디스패처 타입을 REQUEST만 남기는 것(지정하지 않으면 일반 필터는 REQUEST만), (2) ERROR에도 등록해야 하는 이유가 있다면 필터 안에서 request.getDispatcherType() == DispatcherType.ERROR일 때 집계를 건너뛰는 것이다. OncePerRequestFilter를 상속하면 기본 설정만으로 오류 디스패치를 건너뛰는 동작을 얻는다.

    4. 사용자는 200 상태와 CSV 일부를 받다가 연결이 끊긴다. 버퍼를 비우는 순간 200 상태 줄과 헤더가 이미 나갔으므로 상태를 500으로 바꿀 수 없다. Tomcat의 custom()은 커밋된 응답에서 오류 페이지를 forward 대신 include로 부르고 연결을 즉시 닫는다. include된 오류 페이지가 무언가를 쓰더라도 이미 나간 CSV 뒤에 이어 붙을 뿐이고(화이트라벨 뷰는 커밋된 응답에는 아무것도 쓰지 않고 로그만 남긴다), 청크 응답은 끝맺음 없이 끊긴다. 화면을 보여 줄 기회는 첫 바이트를 보내기 전에만 있다.

    5. (a) 404: resolve("404")에서 템플릿 error/404는 없고 정적 error/404.html이 있으므로 static/error/404.html. (b) 405: error/405는 템플릿도 정적 파일도 없고, 계열 4xx에서 템플릿 error/4xx가 있으므로 templates/error/4xx.html. (c) 500: error/500, error/5xx 모두 없어 DefaultErrorViewResolver는 null을 돌려주고, errorHtml()이 ModelAndView("error")를 반환해 templates/error.html이 선택된다. error 템플릿이 있으므로 화이트라벨 뷰는 등록되지도 않는다.

     오류 페이지가 RuntimeException → /a, 상태 500 → /b, 기본 페이지 → /c로 등록되어 있다. 서블릿이 throw new IOException("disk")를 하면 어떤 경로가 호출되는가? /a /b /c 오류 페이지 없이 Tomcat 기본 화면 IOException은 RuntimeException의 하위 타입이 아니고 ServletException도 아니어서 예외 타입 탐색이 실패한다. Tomcat은 상태를 500으로 두고 상태 코드 탐색으로 넘어가 /b를 찾는다. 기본 페이지 /c는 500 페이지가 없을 때만 쓰인다. 이 경로에서는 exception_type 속성이 채워지지 않지만 exception 속성에는 IOException이 들어 있다. 스프링 부트 기본 설정에서 컨트롤러가 response.setStatus(404)를 하고 본문으로 "없음"을 쓴 뒤 정상 반환했다. 클라이언트가 받는 것은? 302 응답으로 /error로 이동한다 404 상태와 BasicErrorController가 만든 오류 화면 404 상태와 컨트롤러가 쓴 "없음" 500 상태와 화이트라벨 페이지 오류 페이지 메커니즘은 sendError로 켜진 오류 플래그를 보고 동작한다. setStatus는 상태 숫자만 바꾸므로 오류 디스패치가 일어나지 않고, 서블릿이 쓴 본문이 그대로 나간다. 오류 페이지는 리다이렉트가 아니므로 302는 어떤 경우에도 답이 아니다. jakarta.servlet.Filter를 직접 구현한 로그 필터를 FilterRegistrationBean으로 등록하면서 디스패처 타입을 지정하지 않았다. 컨트롤러가 예외를 던져 부트의 /error가 오류 화면을 그릴 때, 이 필터의 doFilter는 몇 번 호출되는가? 0번 1번 2번 인터셉터의 excludePathPatterns 설정에 따라 1번 또는 2번 Boot의 AbstractFilterRegistrationBean은 디스패처 타입이 비어 있으면 OncePerRequestFilter가 아닌 필터를 REQUEST에만 등록한다. 따라서 원래 요청에서 한 번 호출되고 ERROR 디스패치에서는 체인에 들어가지 않는다. 인터셉터 설정은 DispatcherServlet 안의 일이라 필터 등록과 무관하다. templates/error/5xx.html(Thymeleaf)과 static/error/500.html이 모두 있다. 브라우저 요청에서 상태 500 오류가 나면 무엇이 렌더링되는가? templates/error/5xx.html. 템플릿이 정적 파일보다 항상 우선이다 화이트라벨 페이지. 두 파일이 충돌하면 기본 뷰로 떨어진다 templates/error.html을 찾다가 없어서 Tomcat 기본 화면 static/error/500.html. 정확한 상태 코드 이름을 계열 이름보다 먼저 확인한다 DefaultErrorViewResolver는 resolve("500")에서 템플릿과 정적 파일을 모두 확인한 뒤에야 resolve("5xx")로 넘어간다. 템플릿 우선은 같은 이름 안에서만 성립한다. 따라서 정적 error/500.html이 계열 템플릿보다 먼저 선택된다. 인터셉터를 /**에 등록하고 /error를 제외하지 않았다. 컨트롤러가 예외를 던졌고 어떤 HandlerExceptionResolver도 처리하지 못했다. 이 요청 전체에서 인터셉터 메서드 호출로 옳은 것은? preHandle(REQUEST) → afterCompletion(REQUEST, 예외) → preHandle(ERROR) → postHandle(ERROR) → afterCompletion(ERROR, null) preHandle(REQUEST) → postHandle(REQUEST) → afterCompletion(REQUEST, 예외) preHandle(REQUEST) → afterCompletion(REQUEST, 예외)만 호출되고 오류 디스패치에서는 인터셉터가 불리지 않는다 preHandle(REQUEST) → preHandle(ERROR) → afterCompletion(ERROR, 예외) doDispatch()에서 컨트롤러가 예외를 던지면 applyPostHandle에 도달하지 못하고, 리졸버가 처리하지 못한 예외와 함께 afterCompletion이 불린다. 이후 컨테이너가 /error로 ERROR 디스패치를 하면 그 요청도 DispatcherServlet을 지나므로, 경로를 제외하지 않은 인터셉터가 다시 호출되고 이번에는 오류 컨트롤러가 정상 반환하므로 postHandle과 ex=null인 afterCompletion이 이어진다.
    오류 디스패치(error dispatch)
    컨테이너가 오류 페이지를 호출하기 위해 같은 요청·응답 객체로 오류 페이지 경로에 forward하는 것. DispatcherType.ERROR로 표시된다.
    DispatcherType
    현재 서블릿 호출이 어떤 경로로 들어왔는지를 나타내는 열거형. REQUEST, FORWARD, INCLUDE, ERROR, ASYNC가 있다.
    기본 오류 페이지(default error page)
    예외 타입도 상태 코드도 지정하지 않은 오류 페이지 선언. 다른 선언이 맞지 않을 때 쓰이며, 스프링 부트의 /error가 이 자리에 등록된다.
    루트 원인(root cause)
    ServletException이 감싸고 있는 원래 예외. getRootCause()로 얻으며, 예외 타입 오류 페이지의 두 번째 탐색에 쓰인다.
    커밋(commit)
    응답의 상태 줄과 헤더가 클라이언트로 전송된 상태. 이후에는 상태 코드와 헤더를 바꿀 수 없고 sendError도 IllegalStateException을 던진다.
    밸브(valve)
    Tomcat 컨테이너 계층마다 있는 파이프라인의 처리 단계. StandardWrapperValve, StandardHostValve, ErrorReportValve가 오류 처리를 나눠 맡는다.
    화이트라벨 오류 페이지(whitelabel error page)
    error 템플릿이 없을 때 스프링 부트가 등록하는 기본 오류 뷰. server.error.whitelabel.enabled로 끌 수 있다.
    ErrorViewResolver
    상태 코드와 오류 모델을 받아 오류 뷰를 고르는 부트의 인터페이스. 기본 구현 DefaultErrorViewResolver는 error/코드와 error/4xx·error/5xx를 찾는다.
