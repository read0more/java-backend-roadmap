CAS의 단위는 변수 하나라는 점과, 두 값을 불변 객체 하나로 묶어 AtomicReference로 바꾸는 해법 쓰는 메서드만 synchronized로 잠그고 읽는 메서드는 잠그지 않는다 setter나 갱신 메서드에는 synchronized를 붙이고 getter는 "읽기만 하니까" 그냥 둔다. 모니터 규칙의 happens-before는 같은 모니터를 unlock한 스레드와 그 뒤에 lock한 스레드 사이에서만 성립하므로, 락을 잡지 않는 읽기는 갱신된 값을 본다는 보장이 없고 여러 필드를 고치는 도중의 중간 상태도 볼 수 있다. synchronized의 가시성 보장이 "같은 모니터"일 때만 성립하는 이유 연습 3 "쓰기만 잠그고 읽기는 잠그지 않는 코드"의 두 가지 문제 volatile 없이 이중 검사 잠금(double-checked locking)으로 지연 초기화한다 싱글톤을 if (instance == null) { synchronized (...) { if (instance == null) instance = new X(); } }로 만들면서 instance 필드를 volatile로 선언하지 않는다. 락 밖의 첫 번째 읽기와 락 안의 쓰기 사이에는 happens-before가 없어서, 다른 스레드가 null이 아닌 참조를 받고도 그 객체의 필드는 기본값(0, null)으로 볼 수 있다. 이중 검사 잠금 코드에서 반쯤 초기화된 객체가 보이는 경로와 volatile이 고치는 이유 싱글톤을 지연 생성하는 방법들의 비교 생성자 안에서 this를 다른 스레드가 볼 수 있는 곳에 넘긴다 생성자에서 자기 자신을 리스너로 등록하거나, this를 넘겨 스레드를 시작하거나, 정적 레지스트리에 넣는다. 등록된 순간부터 다른 스레드가 이 객체의 메서드를 부를 수 있는데 생성자는 아직 끝나지 않았으므로, final 필드조차 0이나 null로 보인다. 틈이 대입문 몇 줄 길이여서 테스트에서는 거의 재현되지 않는다. final 필드의 초기화 보장과 그 보장이 깨지는 조건(this 탈출) "생성자가 끝난 객체는 다 만들어진 상태로 보인다"가 성립하지 않는 경우 스레드가 하나여도 생기는 같은 구멍: 생성자가 끝나기 전에 this를 static 필드나 다른 객체의 목록에 등록하면 반쯤 초기화된 객체에 닿을 수 있다(this 유출)

실수가 나오는 코드

시세가 올 때마다 한도를 검사하는 객체다. 생성자의 첫 줄에서 자신을 시세 피드에 등록하고, 그다음 줄에서 필드를 채운다. 시세를 발행하는 스레드는 따로 돌고 있다.

import java.util.List;
import java.util.concurrent.CopyOnWriteArrayList;
import java.util.concurrent.atomic.AtomicInteger;

public class ThisEscape {
    interface Listener { void onPrice(int price); }

    static class PriceFeed {
        private final List listeners = new CopyOnWriteArrayList<>();
        void register(Listener l) { listeners.add(l); }
        void unregister(Listener l) { listeners.remove(l); }
        void publish(int price) { for (Listener l : listeners) l.onPrice(price); }
    }

    static final AtomicInteger sawZeroLimit = new AtomicInteger();
    static final AtomicInteger npe = new AtomicInteger();

    static class LimitChecker implements Listener {
        private final int limit;
        private final int[] history;

        LimitChecker(PriceFeed feed, int limit) {
            feed.register(this);          // 생성자가 끝나기 전에 this가 다른 스레드에게 보인다
            this.limit = limit;
            this.history = new int[8];
        }

        @Override public void onPrice(int price) {
            if (limit == 0) sawZeroLimit.incrementAndGet();   // final인데 0으로 보인다
            try {
                history[price % 8] = price;
            } catch (NullPointerException e) {
                npe.incrementAndGet();                        // final인데 null로 보인다
            }
        }
    }

    public static void main(String[] args) throws Exception {
        PriceFeed feed = new PriceFeed();
        Thread publisher = new Thread(() -> {
            int p = 1;
            while (!Thread.currentThread().isInterrupted()) feed.publish(p++ & 0xFFFF);
        }, "publisher");
        publisher.start();

        int created = 2_000_000;
        for (int i = 0; i < created; i++) {
            LimitChecker c = new LimitChecker(feed, 100);
            feed.unregister(c);
        }
        publisher.interrupt();
        publisher.join();
        System.out.println("만든 객체 = " + created);
        System.out.println("limit이 0으로 보인 횟수 = " + sawZeroLimit.get());
        System.out.println("history가 null이어서 NPE가 난 횟수 = " + npe.get());
    }
}

limit에는 언제나 100을 넘겼고 history는 생성자에서 반드시 채운다. 둘 다 final이다. 그런데 발행 스레드는 limit == 0인 객체를 수만~수십만 번, history == null인 객체를 백만 번 안팎 만났다(검수하며 다시 돌린 두 번은 각각 105,726번·1,115,153번과 36,084번·843,436번이었다). history 쪽이 많은 것은 history의 대입이 limit의 대입보다 뒤에 있어서, history가 null로 보이는 구간이 limit가 0으로 보이는 구간을 포함하기 때문이다. 이 실험은 발행 스레드가 쉬지 않고 돌기 때문에 횟수가 크게 나왔다. 시세가 초당 몇 번 오는 실제 서비스라면 발행이 그 짧은 구간과 겹칠 때만 나타나므로 훨씬 드물게, NullPointerException 한 줄로 나타난다. 그때 스택 트레이스가 가리키는 필드는 코드상 null일 수 없는 final 필드다.

왜 그런가

JLS §12.5는 객체를 만들 때 먼저 모든 인스턴스 변수를 기본값으로 채우고, 그 뒤에 생성자 본문을 실행한다고 정한다. 그러므로 feed.register(this)가 실행되는 순간의 객체는 limit = 0, history = null인 상태로 힙에 실제로 존재한다. 그 참조가 리스너 목록에 들어가면 발행 스레드는 그 객체의 onPrice를 부를 수 있고, 생성 스레드가 다음 두 줄을 실행하기 전이라면 기본값을 본다. 재정렬이나 캐시 같은 메모리 모델의 미묘한 문제가 아니라, 시간 순서 그대로 아직 대입이 일어나지 않은 것이다.

final도 막아 주지 못한다. JLS §17.5는 객체가 완전히 초기화된 시점을 "생성자가 끝났을 때"로 정의하고, 그 뒤에야 참조를 볼 수 있는 스레드에게만 final 필드의 올바른 값을 보장한다. 같은 절은 final 필드의 사용 모델을 이렇게 적는다. 생성자에서 final 필드를 설정하고, 생성 중인 객체의 참조를 생성자가 끝나기 전에 다른 스레드가 볼 수 있는 곳에 쓰지 말라. 이 코드는 그 조건을 어겼으므로 보장 전체가 사라진다.

같은 실수의 다른 모양도 흔하다.

  • 생성자에서 new Thread(this::run).start()나 executor.submit(this::poll)을 부른다.
  • 생성자에서 Registry.INSTANCES.add(this)처럼 정적 컬렉션에 자신을 넣는다.
  • 생성자에서 익명 클래스나 람다를 리스너로 등록한다. 그 안에서 바깥 객체의 필드나 메서드를 쓰면 람다가 this를 붙잡고 있으므로 this를 넘긴 것과 같다.

"등록을 생성자의 마지막 줄로 옮기면 된다"는 답도 충분하지 않다. JLS §12.5의 순서에서 상위 클래스 생성자는 하위 클래스의 필드 초기화와 생성자 본문보다 먼저 실행된다. 누군가 이 클래스를 상속하면, 상위 클래스 생성자의 마지막 줄이 실행되는 시점에 하위 클래스의 필드는 아직 기본값이다. JDK 21의 javac는 -Xlint:this-escape 옵션으로 이런 자리를 찾아 준다. 상속할 수 있는 공개 클래스의 생성자에서 this를 다른 메서드에 넘기면 다음 경고가 나온다.

고치는 법

만드는 일과 알리는 일을 나눈다. 생성자는 필드만 채우고, 등록은 생성자가 끝난 뒤에 한다. 생성자를 private으로 막고 정적 팩토리 메서드에서 두 단계를 차례로 실행하면 호출하는 쪽이 등록을 빠뜨릴 수도 없다.

static class LimitChecker implements Listener {
    private final int limit;
    private final int[] history;

    private LimitChecker(int limit) {
        this.limit = limit;
        this.history = new int[8];
    }

    static LimitChecker create(PriceFeed feed, int limit) {
        LimitChecker c = new LimitChecker(limit);   // 생성자가 끝난 뒤에
        feed.register(c);                           // 등록한다
        return c;
    }
    // onPrice는 그대로
}

이제 발행 스레드는 생성자가 끝난 뒤에야 참조를 얻으므로 JLS §17.5의 보장이 final 필드에 적용된다. final이 아닌 필드까지 안전한 것은 참조를 넘기는 통로 덕분이다. java.util.concurrent 패키지 문서는 어떤 스레드가 객체를 동시성 컬렉션에 넣기 전에 한 동작들이, 다른 스레드가 그 원소를 컬렉션에서 꺼내거나 접근한 뒤의 동작보다 happens-before 관계로 앞선다고 정한다. 여기서는 CopyOnWriteArrayList가 그 통로다. 평범한 ArrayList나 일반 필드로 참조를 넘겼다면 생성자가 끝난 뒤에 넘겼더라도 final이 아닌 필드의 가시성은 따로 확보해야 한다.

스레드를 시작해야 하는 객체도 같은 방식으로 고친다. 생성자에서는 Thread 객체를 만들기만 하고, start()는 별도의 start() 메서드나 팩토리에서 부른다.
  • JLS §17.5 final Field Semantics — 생성자가 끝나야 완전히 초기화된 객체로 본다는 정의와, 생성 중인 객체의 참조를 다른 스레드가 볼 수 있는 곳에 쓰지 말라는 사용 모델
  • JLS §12.5 Creation of New Class Instances — 인스턴스 변수를 기본값으로 채운 뒤 상위 클래스 생성자, 필드 초기화, 생성자 본문 순으로 실행하는 절차
  • java.util.concurrent 패키지 요약 (Java SE 21) — 동시성 컬렉션에 객체를 넣기 전의 동작과 꺼낸 뒤의 동작 사이의 happens-before
    •      싱글톤 객체(스프링 빈, 서블릿)의 인스턴스 필드에 요청별 값을 둔다 컨트롤러·서비스 같은 싱글톤 빈의 필드에 "지금 처리 중인 사용자"나 계산 중간값을 저장한다. 객체가 하나면 필드도 힙에 한 칸뿐이고 모든 요청 스레드가 그 칸을 함께 쓰므로, 요청이 겹치면 A 사용자의 요청이 B 사용자의 값을 읽어 응답한다. 혼자 요청을 보내는 개발 환경에서는 나타나지 않는다. 두 스레드의 값이 섞이는 과정을 힙과 스택으로 추적하고 무상태로 고친다 싱글톤 추적기의 필드를 두 요청이 번갈아 고쳐 로그가 뒤섞이는 실행 SimpleDateFormat을 static 상수로 두고 여러 스레드가 함께 쓴다 포맷터를 매번 만드는 것이 아까워 private static final SimpleDateFormat 하나를 모든 요청이 공유한다. 이 클래스는 변환 중간값을 자기 필드에 담아 두므로 두 스레드가 겹치면 서로의 날짜가 섞인다. 가끔 NumberFormatException이 나기도 하지만, 훨씬 자주 예외 없이 엉뚱한 날짜가 반환되어 그대로 DB에 저장된다. 옛 날짜 API의 네 가지 문제 중 하나로 포맷터의 스레드 안전성을 든다 불변이고 스레드 안전한 DateTimeFormatter 사용법 스프링에서 같은 실수가 나오는 자리: 컨버전 서비스에 등록한 변환기·포맷터는 모든 요청 스레드가 공유하므로 필드에 SimpleDateFormat을 두면 결과가 섞인다

    실수가 나오는 코드

    스레드 네 개가 각자 다른 날짜 문자열 하나를 받아, 공유 포맷터로 읽었다가(parse) 다시 문자열로 쓴다(format). 포맷터가 정상이라면 넣은 문자열이 그대로 나와야 한다.

    import java.text.SimpleDateFormat;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class SharedFormat {
    // 흔한 형태: 포맷터를 상수로 빼 두고 모든 스레드가 함께 쓴다
    private static final SimpleDateFormat FORMAT = new SimpleDateFormat("yyyy-MM-dd");

    public static void main(String[] args) throws Exception {
        String[] inputs = {"2024-01-15", "2025-06-30", "2026-11-20", "1999-12-31"};
        AtomicInteger ok = new AtomicInteger(), wrong = new AtomicInteger();
        Map errors = new ConcurrentHashMap<>();
        Map wrongSamples = new ConcurrentHashMap<>();

        ExecutorService pool = Executors.newFixedThreadPool(4);
        for (int t = 0; t < 4; t++) {
            String input = inputs[t];
            pool.execute(() -> {
                for (int i = 0; i < 100_000; i++) {
                    try {
                        String back = FORMAT.format(FORMAT.parse(input));   // 읽었다가 그대로 다시 쓴다
                        if (back.equals(input)) ok.incrementAndGet();
                        else { wrong.incrementAndGet(); wrongSamples.putIfAbsent(input, back); }
                    } catch (Exception e) {
                        errors.merge(e.getClass().getName(), 1, Integer::sum);
                    }
                }
            });
        }
        pool.shutdown();
        pool.awaitTermination(1, TimeUnit.MINUTES);

        System.out.println("정상 = " + ok.get());
        System.out.println("예외 없이 틀린 값 = " + wrong.get());

    왜 그런가

    SimpleDateFormat의 Javadoc에는 "Synchronization" 항목이 따로 있다. 날짜 포맷은 동기화되어 있지 않고, 스레드마다 별도의 인스턴스를 만들기를 권하며, 여러 스레드가 한 포맷에 동시에 접근한다면 바깥에서 동기화해야 한다는 내용이다. 이유는 OpenJDK 21 소스(src.zip)에서 바로 보인다.

    • 부모 클래스 DateFormat에 protected Calendar calendar; 필드가 있다. SimpleDateFormat에서 실제 변환을 맡는 비공개 format 메서드는 맨 먼저 calendar.setTime(date)로 변환할 날짜를 이 필드에 넣고, 그다음 패턴을 따라가며 같은 calendar에서 연·월·일을 하나씩 꺼내 문자열을 만든다.
    • parse는 읽어 낸 필드 값을 모은 뒤 calb.establish(calendar).getTime()으로 같은 calendar에 써 넣고 시각을 계산한다.
    • 숫자를 읽는 일은 protected NumberFormat numberFormat; 필드의 DecimalFormat이 맡고, DecimalFormat은 자릿수를 모으는 버퍼 digitList를 다시 자기 필드로 가진다. 위 스택 트레이스의 DigitList가 이것이다.

    즉 변환 한 번은 "공유 필드에 쓰고, 조금 뒤에 그 필드에서 읽는" 여러 단계로 되어 있다. 스레드 A가 calendar에 자기 날짜를 넣고 연도를 꺼낸 직후 스레드 B가 calendar를 자기 날짜로 덮으면, A는 연도는 자기 것, 월과 일은 B의 것으로 문자열을 만든다. 여러 스레드의 필드가 섞이므로 아무도 넣지 않은 날짜가 나온다. digitList가 겹치면 한 스레드가 비워 놓은 버퍼를 다른 스레드가 숫자로 바꾸려다 빈 문자열을 만나고, 그것이 NumberFormatException이다. 어느 쪽이 될지는 겹친 지점에 달려 있고, 버퍼가 깨지는 경우보다 값만 섞이는 경우가 훨씬 많다.

    이 실수가 치명적인 이유는 결과의 모양에 있다. 틀린 날짜도 형식은 완벽한 날짜여서 검증을 통과하고, 그대로 주문일·만료일·생년월일로 저장된다. 동시 요청이 드문 시간대에는 나타나지 않으므로 부하 테스트 없이는 발견하기 어렵다.

    실수가 나오는 코드

    시세판(PriceBoard)은 값이 바뀌면 리스너들에게 알린다. 포트폴리오(Portfolio)는 리스너이면서, 총액을 계산할 때 시세판에 값을 묻는다. 두 클래스 모두 "메서드마다 synchronized"라는 가장 흔한 방식으로 스레드 안전하게 만들었다.

    import java.lang.management.ManagementFactory;
import java.lang.management.ThreadInfo;
import java.lang.management.ThreadMXBean;
import java.util.ArrayList;
import java.util.HashMap;
import java.util.List;
import java.util.Map;

public class AlienCall {
    interface PriceListener { void onPrice(String code, int price); }

    static class PriceBoard {
        private final Map prices = new HashMap<>();
        private final List listeners = new ArrayList<>();

        synchronized void addListener(PriceListener l) { listeners.add(l); }
        synchronized int price(String code) { return prices.getOrDefault(code, 0); }

        synchronized void update(String code, int price) {
            prices.put(code, price);
            for (PriceListener l : listeners) l.onPrice(code, price);   // 락을 쥔 채 남의 코드를 부른다
        }
    }

    static class Portfolio implements PriceListener {
        private final PriceBoard board;
        private final Map quantity = new HashMap<>();
        private int lastValue;

        Portfolio(PriceBoard board) { this.board = board; quantity.put("A", 10); }

        @Override public synchronized void onPrice(String code, int price) {
            lastValue = quantity.getOrDefault(code, 0) * price;
        }

        synchronized int total() {
            pause(100);                                   // 두 스레드가 엇갈리도록 넣은 지연
            int sum = 0;
            for (var e : quantity.entrySet()) sum += e.getValue() * board.price(e.getKey());
            return sum;
        }
    }

    static void pause(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { Thread.currentThread().interrupt(); }
    }

    public static void main(String[] args) throws Exception {
        PriceBoard board = new PriceBoard();
        Portfolio portfolio = new Portfolio(board);
        board.addListener(portfolio);

        Thread reader = new Thread(() -> System.out.println("total = " + portfolio.total()), "reader");
        Thread updater = new Thread(() -> {
            pause(50); board.update("A", 1200); System.out.println("update 끝");
        }, "updater");
        reader.setDaemon(true); updater.setDaemon(true);
        reader.start(); updater.start();

        Thread.sleep(1000);
        ThreadMXBean mx = ManagementFactory.getThreadMXBean();
        long[] ids = mx.findDeadlockedThreads();
        if (ids == null) { System.out.println("교착 상태 없음"); return; }
        for (ThreadInfo info : mx.getThreadInfo(ids)) {
            System.out.println(info.getThreadName() + " : " + info.getThreadState()
                    + ", 기다리는 락 = " + info.getLockName().replaceAll("@.*", "")
                    + ", 그 락의 주인 = " + info.getLockOwnerName());
        }
    }
}

    왜 그런가

    두 스레드가 락을 잡은 순서를 적어 보면 이렇다.

    reader  : portfolio.total()   Portfolio 락 획득 ──▶ board.price()        PriceBoard 락 대기
updater : board.update()      PriceBoard 락 획득 ──▶ listener.onPrice()   Portfolio 락 대기

    두 락을 서로 반대 순서로 잡는, 교착 상태의 가장 기본적인 모양이다. 다른 점은 이 순서가 소스 어디에도 중첩된 synchronized로 적혀 있지 않다는 것이다. PriceBoard.update를 쓴 사람이 본 것은 l.onPrice(...) 한 줄이고, 그 뒤에서 어떤 락이 잡히는지는 리스너를 구현한 쪽만 안다. 리스너는 인터페이스이므로 내일 추가되는 구현이 무엇을 잠글지는 아무도 모른다. 락을 쥔 채 자기가 통제하지 못하는 코드를 호출하면, 락 순서를 정할 권한을 그 코드에 넘겨주는 셈이다.

    JLS §17.1은 자바 언어가 교착 상태를 막지도, 탐지를 요구하지도 않는다고 적고, 여러 객체의 락을 (직접이든 간접이든) 쥐는 프로그램은 교착 상태를 피하는 기법을 써야 한다고 덧붙인다. "간접적으로"가 바로 이 경우다. synchronized는 락을 기다리는 데 시간 제한이 없으므로 한 번 걸리면 스스로 풀리지 않는다. 위 출력은 ThreadMXBean.findDeadlockedThreads()로 얻은 것이다. 이 메서드는 객체 모니터나 소유 가능한 동기화기를 기다리며 순환을 이룬 플랫폼 스레드를 찾아 주고, 없으면 null을 돌려준다. jstack이 보여 주는 "Found one Java-level deadlock"과 같은 정보다.

    남의 코드에 해당하는 것은 리스너만이 아니다. 인자로 받은 람다나 Runnable, 하위 클래스가 재정의할 수 있는 메서드, 다른 팀이 만든 객체의 메서드가 모두 같다. 교착 상태까지 가지 않더라도, 락을 쥔 채 부른 코드가 느리면 그 락을 기다리는 모든 스레드가 함께 느려진다.

큐에 있던 작업은 흔적 없이 사라진다. 풀 스레드가 JVM 종료를 막는 이유와 우아한 종료가 필요한 이유 shutdown, awaitTermination, shutdownNow를 두 단계로 엮는 구현 요청(메서드 호출)마다 새 스레드 풀을 만든다 메서드 안에서 Executors.newFixedThreadPool(4)로 풀을 만들어 병렬로 일을 시키고 그대로     import java.lang.management.ManagementFactory;
import java.util.ArrayList;
import java.util.List;
import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.concurrent.Future;

public class PoolPerCall {
    // 요청 하나를 처리하는 메서드라고 하자. 조회 네 건을 동시에 보내려고 풀을 만든다.
    static int handleRequest(int requestId) throws Exception {
        ExecutorService pool = Executors.newFixedThreadPool(4);   // 호출마다 새 풀
        List> futures = new ArrayList<>();
        for (int i = 0; i < 4; i++) {
            int part = i;
            futures.add(pool.submit(() -> requestId + part));
        }
        int sum = 0;
        for (Future f : futures) sum += f.get();
        return sum;                                               // shutdown 없이 돌아간다
    }

    static int liveThreads() {
        return ManagementFactory.getThreadMXBean().getThreadCount();
    }

    public static void main(String[] args) throws Exception {
        System.out.println("시작: 살아 있는 스레드 = " + liveThreads());
        for (int n = 1; n <= 1000; n++) {
            handleRequest(n);
            if (n == 1 || n == 10 || n == 100 || n == 1000)
                System.out.println("요청 " + n + "건 처리 후: 살아 있는 스레드 = " + liveThreads());
        }
        System.gc();
        Thread.sleep(2000);
        System.out.println("System.gc() 2초 뒤: 살아 있는 스레드 = " + liveThreads());
        System.out.println("main 끝");
    }
}

    왜 그런가

    Executors.newFixedThreadPool의 Javadoc 마지막 문장은 풀의 스레드가 명시적으로 shutdown될 때까지 존재한다고 적는다. 일을 마친 작업 스레드는 다음 작업을 받으려고 큐에서 기다린다. 위 덤프의 WAITING (parking)이 그 자리다. ThreadPoolExecutor Javadoc에 따르면 유지 시간(keep-alive) 정책은 기본적으로 코어 수를 넘는 스레드에만 적용되고, 고정 풀은 스레드가 모두 코어 스레드이므로 아무리 오래 쉬어도 끝나지 않는다.

    풀을 가리키던 지역 변수 pool이 사라졌는데 왜 회수되지 않을까. 같은 Javadoc의 "Reclamation" 항목이 조건을 적어 두었다. 프로그램에서 더 이상 참조되지 않고 남은 스레드도 없는 풀만 명시적인 종료 없이 회수될 수 있다. 살아 있는 스레드는 그 자체로 가비지 컬렉션의 출발점이고, OpenJDK 21 소스에서 작업 스레드가 실행하는 Worker는 ThreadPoolExecutor의 내부 클래스(private final class Worker)여서 바깥 풀 객체를 참조한다. 스레드가 살아 있는 한 풀도, 풀의 큐도 살아 있다. 이 풀의 스레드가 기다리기를 그만두게 하려면 shutdown()(또는 shutdownNow()·close())을 불러야 한다. 같은 "Reclamation" 항목은 명시적인 종료 없이 스레드가 사라지게 하려면 코어 스레드 수를 0으로 두거나 allowCoreThreadTimeOut(boolean)으로 코어 스레드에도 유지 시간을 적용하라고 안내하는데, newFixedThreadPool이 만드는 풀은 그렇게 설정되어 있지 않다.

    플랫폼 스레드는 운영체제 스레드와 스택 메모리를 하나씩 차지하고, 프로세스가 만들 수 있는 스레드 수에는 한도가 있다. 이 실험은 4,000개에서 멈췄지만 서버는 멈추지 않으므로, 계속 쌓이면 강의에서 재현한 OutOfMemoryError: unable to create native thread에 닿는다(이 부록에서는 그 지점까지 돌리지 않았다). 그 오류가 나는 곳은 대개 이 코드와 무관한, 그 순간 스레드를 만들려던 다른 기능이다.

    shutdown만 추가하면 되는가

    메서드 끝에서 풀을 닫으면 누수는 사라진다. ExecutorService는 Java 19부터 close()를 가지므로 try (ExecutorService pool = Executors.newFixedThreadPool(4)) { ... }로 쓸 수 있고, close()의 기본 구현은 shutdown()을 부른 뒤 작업이 끝나기를 기다린다. 그래도 요청마다 풀을 만드는 구조에는 두 가지가 남는다. 첫째, 요청마다 스레드 네 개를 만들고 없애는 비용을 치른다. 풀을 쓰는 이유가 그 비용을 한 번만 치르는 것이었다. 둘째, 동시에 실행되는 스레드 수에 상한이 없다. 요청 500개가 동시에 들어오면 풀 500개, 스레드 2,000개가 한꺼번에 생긴다. "최대 4개"는 요청 하나 안에서만 성립하고, 서버 전체로는 아무것도 제한하지 않는다.

    고치는 법

    풀은 애플리케이션에 하나(용도별로 하나씩) 두고 모든 요청이 함께 쓴다. 만든 쪽이 애플리케이션이 내려갈 때 끈다.

    // import 문은 앞의 PoolPerCall과 같다
public class SharedPool {
    // 풀은 애플리케이션에 하나. 만든 쪽이 끌 책임도 진다.
    private static final ExecutorService POOL = Executors.newFixedThreadPool(4);

    static int handleRequest(int requestId) throws Exception {
        List> futures = new ArrayList<>();
        for (int i = 0; i < 4; i++) {
            int part = i;
            futures.add(POOL.submit(() -> requestId + part));
        }
        int sum = 0;
        for (Future f : futures) sum += f.get();
        return sum;
    }

    public static void main(String[] args) throws Exception {
        int before = ManagementFactory.getThreadMXBean().getThreadCount();
        for (int n = 1; n <= 1000; n++) handleRequest(n);
        System.out.println("시작 " + before + " -> 요청 1000건 처리 후 "
                + ManagementFactory.getThreadMXBean().getThreadCount());
        POOL.shutdown();          // 애플리케이션이 내려갈 때 한 번
        System.out.println("main 끝");
    }
}

    스프링에서는 풀을 빈으로 등록해 주입받는다. 빈은 싱글톤이므로 풀이 하나임이 보장되고, 종료도 컨테이너가 맡는다. @Bean의 Javadoc에 따르면 컨테이너는 @Bean 메서드가 돌려준 객체에서 인자 없는 공개 메서드 close나 shutdown을 찾아 소멸 메서드로 등록하고, 애플리케이션 컨텍스트를 닫을 때 호출한다. ExecutorService에는 두 메서드가 모두 있다. JDK 21과 Spring Framework 6.2.19에서 ThreadPoolExecutor를 @Bean으로 등록하고 컨텍스트를 닫아 보면 close()가 호출되었고, close()는 앞에서 본 대로 shutdown()을 부른 뒤 실행 중인 작업이 끝나기를 기다린다.

    풀을 공유하면 새로 따져야 할 것이 생긴다. 모든 요청이 스레드 네 개를 나눠 쓰므로 풀의 크기와 큐의 용량이 서버 전체의 처리량을 정한다. 그리고 풀의 작업이 같은 풀에 다시 작업을 넣고 기다리면 스레드 기아 교착이 생긴다. 둘 다 이 부록의 바로 옆 항목들이 가리키는 강의에서 다룬다.
  • Executors (Java SE 21 API) — newFixedThreadPool: "The threads in the pool will exist until it is explicitly shutdown."
  • ThreadPoolExecutor (Java SE 21 API) — Reclamation 항목(참조되지 않고 남은 스레드도 없는 풀만 회수될 수 있다)과 Keep-alive times 항목(기본적으로 코어 스레드에는 유지 시간이 적용되지 않는다)
  • ExecutorService (Java SE 21 API) — 쓰지 않는 ExecutorService는 종료해야 자원이 회수된다는 문장, Java 19에 추가된 close()의 기본 구현
  • @Bean Javadoc (Spring Framework 6.2) — destroyMethod 추론: 인자 없는 공개 메서드 close 또는 shutdown을 찾아 컨텍스트를 닫을 때 호출한다
    •      풀의 작업이 같은 풀에 작업을 넣고 그 결과를 기다린다 고정 크기 풀에서 실행 중인 작업이 같은 풀에 하위 작업을 submit하고 Future.get()으로 기다린다. 바깥 작업들이 풀의 스레드를 모두 차지하면 하위 작업은 큐에 들어가 있는데 실행할 스레드가 없고, 바깥 작업들은 그 결과를 영원히 기다린다. 락이 얽힌 것이 아니어서 교착 상태로 탐지되지 않고, 부하가 낮을 때는 스레드가 남아 정상 동작한다. 스레드 하나짜리 풀에서 바깥 작업이 안쪽 작업을 기다리다 멈추는 실행(스레드 기아 교착) 재귀 분할을 일반 스레드 풀에 맡겼을 때 모든 스레드가 get()에서 멈추는 과정 submit()으로 넘긴 작업의 Future를 버린다 executor.submit(task)의 반환값을 받지 않는다. submit은 작업을 FutureTask로 감싸고, 작업이 던진 예외는 그 안에 저장될 뿐 어디에도 출력되지 않는다. 누군가 get()을 불러야 드러나는데 Future를 버렸으므로 실패는 영원히 묻힌다. "작업이 실패했는데 로그가 하나도 없다"는 장애가 된다. Callable·submit·execute 세 경우에 예외가 어디로 가는지 실행으로 비교한다 FutureTask.run이 모든 Throwable을 잡아 outcome에 저장하는 코드 ScheduledExecutorService의 주기 작업에서 예외가 빠져나가도록 둔다 scheduleAtFixedRate나 scheduleWithFixedDelay로 등록한 작업이 한 번이라도 예외를 던지면 그 뒤의 실행이 모두 취소된다. 로그는 한 줄도 남지 않고, 스케줄러와 그 스레드는 멀쩡히 살아 있다. 캐시 갱신, 토큰 재발급, 하트비트 같은 작업이 어느 날부터 조용히 돌지 않는다. 작업의 예외가 FutureTask 안에 갇히는 같은 원리

    실수가 나오는 코드

    1초마다 외부 시스템과 동기화하는 작업이다. 세 번째 실행에서 원격 서버가 응답하지 않아 예외가 난다고 하자.

    import java.time.LocalTime;
import java.util.concurrent.Executors;
import java.util.concurrent.ScheduledExecutorService;
import java.util.concurrent.ScheduledFuture;
import java.util.concurrent.TimeUnit;
import java.util.concurrent.atomic.AtomicInteger;

public class SilentStop {
    public static void main(String[] args) throws Exception {
        ScheduledExecutorService scheduler = Executors.newScheduledThreadPool(1);
        AtomicInteger run = new AtomicInteger();

        ScheduledFuture future = scheduler.scheduleAtFixedRate(() -> {
            int n = run.incrementAndGet();
            System.out.println(LocalTime.now().withNano(0) + " 동기화 " + n + "회차");
            if (n == 3) throw new IllegalStateException("원격 서버 응답 없음");   // 한 번의 실패
        }, 0, 1, TimeUnit.SECONDS);

        Thread.sleep(8000);
        System.out.println(LocalTime.now().withNano(0) + " 8초 뒤: 실행 횟수 = " + run.get()
                + ", isDone = " + future.isDone() + ", 풀 종료 여부 = " + scheduler.isShutdown());
        try {
            future.get();
        } catch (Exception e) {
            System.out.println("future.get() -> " + e);
        }
        scheduler.shutdown();
    }
}

    세 번째 실행 뒤로 6초 동안 아무 일도 일어나지 않았다. 예외 메시지도 스택 트레이스도 없다. 예외가 있었다는 사실은 프로그램이 일부러 future.get()을 불렀을 때에야 나왔다. 스케줄러는 종료되지 않았으므로(isShutdown() == false) 스레드 덤프를 떠도 스케줄러 스레드는 다음 작업을 기다리는 정상적인 모습이다. 큐가 비어 있을 뿐이다.

    왜 그런가

    명세가 그렇게 정했다. ScheduledExecutorService.scheduleAtFixedRate의 Javadoc은 작업의 반복 실행이 끝나는 경우를 세 가지로 적는다. 반환된 future로 작업을 취소했을 때, 실행기가 종료되었을 때, 그리고 작업의 어느 한 실행이 예외를 던졌을 때다. 세 번째의 경우 future의 get()이 그 예외를 원인으로 담은 ExecutionException을 던진다고 하고, 이어서 "Subsequent executions are suppressed", 즉 이후의 실행은 억제되며 isDone()은 true를 돌려준다고 적는다. scheduleWithFixedDelay의 문서도 같은 문장을 담고 있다.

    구현은 OpenJDK 21의 ScheduledThreadPoolExecutor.ScheduledFutureTask.run()에서 확인된다.

    public void run() {
    if (!canRunInCurrentRunState(this))
        cancel(false);
    else if (!isPeriodic())
        super.run();
    else if (super.runAndReset()) {      // 주기 작업: 정상적으로 끝났을 때만
        setNextRunTime();
        reExecutePeriodic(outerTask);    // 다음 실행을 큐에 다시 넣는다
    }
}

    주기 작업은 "한 번 실행하고, 성공하면 자기 자신을 다음 시각으로 큐에 다시 넣는" 방식으로 반복된다. FutureTask.runAndReset()은 작업을 try 안에서 호출하고 catch (Throwable ex)에서 setException(ex)로 예외를 future에 저장한 뒤 false를 돌려준다. false면 다시 넣는 줄이 실행되지 않는다. 그것으로 끝이다. 예외는 submit의 경우와 똑같이 FutureTask 안에 갇히고, 작업 스레드 입장에서는 run()이 정상적으로 돌아왔으므로 잡히지 않은 예외 처리기도 불리지 않는다.

    일회성 작업이라면 누군가 get()으로 결과를 확인할 수 있다. 그런데 주기 작업의 future는 정상일 때 영원히 끝나지 않으므로 get()을 부르고 기다리는 코드가 보통 없다. 그래서 이 예외는 구조적으로 아무도 보지 않는다.

    고치는 법

    주기 작업의 본문 전체를 try-catch로 감싸, 예외가 run() 밖으로 나가지 않게 한다. 실패는 기록하고 다음 주기를 기다린다.

    스프링의 @Scheduled는 이 문제를 프레임워크가 막아 준다. 같은 작업을 @Scheduled(fixedRate = 1000) 메서드로 옮겨 Spring Framework 6.2.19에서 돌리면, 세 번째 실행에서 TaskUtils$LoggingErrorHandler가 "Unexpected error occurred in scheduled task"와 스택 트레이스를 오류 수준으로 기록하고 네 번째, 다섯 번째 실행이 이어졌다. TaskUtils의 Javadoc은 기본 오류 처리기가 반복 작업에서는 오류를 기록하고 억제해 이후 실행이 막히지 않게 하고, 일회성 작업에서는 다시 던진다고 설명한다. 그러니 이 함정은 ScheduledExecutorService를 직접 쓸 때의 것이다. 다만 스프링에서도 실패는 로그 한 번으로만 남으므로, 그 로그를 보는 사람이나 알림이 없으면 "매번 실패하는 작업"은 여전히 조용하다.
