ArrayList.contains나 HashSet처럼 equals(Object)를 부르는 라이브러리 안에서는 Object의 동일성 비교가 실행되어, 값이 같은 객체를 찾지 못한다. 변수의 선언 타입에 따라 다른 메서드가 선택되는 것을 바이트코드로 확인하고, @Override로 컴파일 시점에 막는 법 equals만 재정의하고 hashCode는 재정의하지 않는다 equals로는 같은 두 객체가 서로 다른 해시 코드를 갖게 되어 대부분 다른 버킷으로 간다. HashSet에 같은 값이 중복으로 들어가고 HashMap에 넣은 값을 같은 내용의 키로 찾지 못한다. 가끔 우연히 같은 버킷에서 만나면 정상처럼 보여서 재현도 일정하지 않다. 둘 다 없을 때, hashCode만 있을 때, equals만 있을 때 해시 셋에서 각각 무슨 일이 생기는지 equals와 hashCode 규약이 서로 묶여 있는 이유 HashSet·HashMap에 넣은 객체의 equals·hashCode에 쓰이는 필드를 바꾼다 해시 컬렉션은 넣는 순간의 해시 코드로 버킷을 정한다. 들어 있는 동안 그 필드를 바꾸면 contains와 remove가 새 해시 코드의 버킷을 찾아가 실패한다. 순회하면 보이는데 찾을 수도 지울 수도 없는 원소가 컬렉션에 남는다. 넣은 뒤에 내용을 바꾼 원소가 어느 버킷에 남고 조회가 어느 버킷으로 가는지 추적한 예제 배열을 Map의 키, Set의 원소, 레코드의 구성 요소로 쓴다 배열은 equals와 hashCode를 재정의하지 않으므로 내용이 같은 두 배열도 서로 다른 키다. byte[]를 키로 쓴 HashMap은 같은 내용의 배열로 조회해도 null을 돌려주고, 캐시라면 적중 없이 항목만 늘어난다. 배열을 구성 요소로 가진 레코드의 equals도 같은 이유로 거짓이 된다. 배열이 Object의 equals·toString을 그대로 쓴다는 점과 Arrays.equals, Arrays.toString 해시 컬렉션이 hashCode로 버킷을 고르고 equals로 확인하는 과정

토큰의 해시값, 암호화 키, 좌표 쌍처럼 "내용이 같으면 같은 것"으로 다루고 싶은 값이 배열로 표현될 때가 있다. 그 배열을 그대로 키나 원소로 쓰면 다음과 같이 된다. JDK 21(Temurin 21.0.13)에서 실행한 결과다.

import java.util.*;

public class ArrayKey {
    record Token(byte[] value) { }

    public static void main(String[] args) {
        byte[] k1 = {1, 2, 3};
        byte[] k2 = {1, 2, 3};                       // 내용이 같은 다른 배열

        System.out.println(k1.equals(k2));           // (1)
        System.out.println(Arrays.equals(k1, k2));   // (2)

        Map cache = new HashMap<>();
        cache.put(k1, "A");
        System.out.println(cache.get(k2));           // (3)
        cache.put(k2, "B");
        System.out.println(cache.size());            // (4)

        seen.add(new int[]{7, 8});
        System.out.println(seen.contains(new int[]{7, 8}));        // (5)
        System.out.println(List.of(k1).contains(k2));              // (6)
        System.out.println(new Token(k1).equals(new Token(k2)));   // (7)
    }

컴파일러는 경고를 하나도 내지 않는다. (3)에서 캐시는 방금 넣은 값을 찾지 못하고, (4)에서 내용이 같은 키가 두 개가 된다. 이 맵이 "같은 입력의 결과를 다시 계산하지 않기 위한 캐시"였다면 적중은 한 번도 일어나지 않고, 요청이 올 때마다 항목이 하나씩 늘어난다. 틀린 결과로 시작해서 메모리 문제로 끝나는 경로다.

왜 그런가

JLS §10.7은 배열 타입의 멤버를 세 가지로 정한다. length 필드, Object의 것을 재정의한 clone 메서드, 그리고 Object에서 상속한 나머지 멤버 전부다. 곧 배열의 equals와 hashCode는 Object의 것이다. Object.equals는 API 문서에 적힌 대로 두 참조가 같은 객체를 가리킬 때만(x == y) 참이고, Object.hashCode는 서로 다른 객체에 대해 가능한 한 서로 다른 정수를 돌려주도록 구현된다. 배열의 내용은 어느 쪽에도 쓰이지 않는다.

해시 컬렉션은 키의 hashCode()로 버킷을 고르고 그 버킷 안에서 equals()로 확인한다. cache.get(k2)는 k2의 해시 코드로 버킷을 찾는데, 이 값은 k1의 것과 무관하므로 대개 다른 버킷으로 간다. 우연히 같은 버킷에 닿더라도 equals가 참조 비교라서 실패한다. (5)의 HashSet도 같다. (6)의 List.contains는 해시를 쓰지 않지만 원소마다 equals를 부르므로 결과가 같다.

(7)은 레코드를 쓰면 equals가 자동으로 해결된다고 믿을 때 걸린다. Record.equals의 API 문서는 자동으로 만들어지는 구현이 참조 타입 구성 요소를 Objects.equals(this.c, r.c)로 비교한다고 정한다. 구성 요소가 배열이면 그 호출은 다시 배열의 equals, 곧 참조 비교가 된다. 자동 생성된 hashCode와 toString도 사정이 같다. JDK 21에서 위의 Token 둘의 hashCode()를 비교하면 서로 다르고, toString()은 Token[value=[B@…] 꼴로 배열의 내용이 아닌 식별 해시를 찍는다(뒤의 16진수는 실행마다 다르다).

고치는 법

두 배열을 한 번 비교하거나 출력하는 것이라면 Arrays.equals, Arrays.hashCode, Arrays.toString을 쓴다. 키나 원소로 써야 한다면 배열을 내용으로 비교되는 값으로 바꿔야 한다. 방법은 둘이다. 배열을 감싸는 타입을 만들어 equals와 hashCode를 내용 기준으로 재정의하거나, String처럼 이미 내용으로 비교되는 불변 값으로 변환한다.

import java.util.*;

public class ArrayKey2 {
    // 배열을 감싸고, 내용으로 비교하도록 직접 재정의한다
    record Token(byte[] value) {
        Token {
            value = value.clone();                   // 바깥의 배열과 끊는다
        }
        @Override public byte[] value() {
            return value.clone();                    // 내부 배열을 내보내지 않는다
        }
        @Override public boolean equals(Object o) {
            return o instanceof Token t && Arrays.equals(value, t.value);
        }
        @Override public int hashCode() {
            return Arrays.hashCode(value);
        }
        @Override public String toString() {
            return "Token" + Arrays.toString(value);
        }
    }

    public static void main(String[] args) {
        byte[] k1 = {1, 2, 3};
        byte[] k2 = {1, 2, 3};

        Map cache = new HashMap<>();
        cache.put(new Token(k1), "A");
        System.out.println(cache.get(new Token(k2)));              // (1)

        k1[0] = 9;                                                 // 넣은 뒤에 원래 배열을 바꿔도
        System.out.println(cache.get(new Token(k2)));              // (2)
        System.out.println(cache.keySet());                        // (3)

        Map byHex = new HashMap<>();               // 문자열로 바꿔 키로 쓰는 방법
        byHex.put(HexFormat.of().formatHex(k2), "A");
        System.out.println(byHex);                                 // (4)

        int[][] a = {{1, 2}, {3}};
        int[][] b = {{1, 2}, {3}};
        System.out.println(Arrays.equals(a, b) + " " + Arrays.deepEquals(a, b));   // (5)
    }
}

Arrays.hashCode(byte[])의 API 문서는 Arrays.equals(a, b)가 참인 두 배열에 대해 같은 값을 돌려준다고 보장하므로, 위의 equals와 hashCode는 규약에 맞는 짝이다. 생성자와 접근자에서 clone()으로 복사하는 것은 꾸밈이 아니다. 배열은 가변이라서, 복사하지 않으면 (2)처럼 맵에 넣은 뒤 바깥에서 배열을 바꾸는 순간 해시 코드가 달라져 그 항목을 다시 찾을 수 없게 된다. 이 영역의 "넣은 객체의 필드를 바꾼다" 항목과 같은 문제다. (4)의 HexFormat은 Java 17에 들어온 클래스다.

(5)는 다차원 배열에서 한 번 더 걸리는 자리다. Arrays.equals(Object[], Object[])는 원소 쌍을 Objects.equals로 비교한다. 바깥 배열의 원소가 다시 배열이면 그 비교는 참조 비교가 되어 거짓이 나온다. 안쪽까지 내용으로 비교하려면 Arrays.deepEquals, Arrays.deepHashCode, Arrays.deepToString을 쓴다.

NaN은 자기 자신과도 같지 않아서 x == Double.NaN은 언제나 거짓이고, 크기 비교도 모두 거짓이다. 실수를 허용 오차로 비교해야 하는 이유, NaN의 비교 규칙(JLS §15.21.1)과 Double.isNaN 0.1이 이진 부동소수점으로 정확히 표현되지 않는 이유 금액을 double로 계산하거나 new BigDecimal(0.1)로 만든다 0.1은 이진 부동소수점으로 정확히 표현되지 않아, double로 열 번 더하면 1.0이 아니라 0.9999999999999999가 된다. new BigDecimal(0.1)은 그 오차가 든 이진 값을 그대로 십진수로 펼친 수가 되므로 BigDecimal로 옮겨도 오차가 따라온다. 합계와 정산 금액이 1원 단위로 어긋난다. new BigDecimal(double)이 보여 주는 실제 저장값, 문자열 생성자와의 차이, DECIMAL과 BigDecimal의 짝 0.1을 double과 BigDecimal로 각각 열 번 더한 결과 비교 부동소수점의 비트 표현과 오차가 생기는 원리 BigDecimal의 값이 같은지를 equals로 묻는다 BigDecimal.equals는 값과 소수 자릿수(scale)가 모두 같아야 참이다. 1.0과 1.00은 equals로는 다르고 compareTo로는 같다. 그래서 같은 두 값이 HashSet에는 둘 다 들어가고 TreeSet에는 하나만 남으며, equals로 쓴 금액 일치 검사는 자릿수 표기만 달라도 실패한다. BigDecimal("1.0")과 BigDecimal("1.00")을 HashSet과 TreeSet에 넣었을 때의 차이 equals와 compareTo가 어긋나는 표준 라이브러리 사례로서의 BigDecimal BigDecimal.divide를 자릿수와 반올림 방식 없이 호출한다 a.divide(b)는 정확한 몫을 돌려주려고 하므로, 몫이 무한 소수가 되는 입력에서 ArithmeticException: Non-terminating decimal expansion을 던진다. 2·4·5·10으로 나누는 테스트는 통과하고, 3명이 나눠 내거나 1.1로 나누는 요청에서만 예외가 난다. 금액에 BigDecimal을 쓰는 이유와 값·스케일 표현

    금액을 double에서 BigDecimal로 옮긴 코드에서 덧셈, 뺄셈, 곱셈은 메서드 이름만 바꾸면 끝난다. 나눗셈도 같은 식으로 옮기면 다음 코드가 된다. JDK 21(Temurin 21.0.13)에서 실행했다.

    import java.math.BigDecimal;

public class Divide {
    // 총액을 인원수로 나눈 1인당 금액
    static BigDecimal perPerson(BigDecimal total, int people) {
        return total.divide(BigDecimal.valueOf(people));
    }

    // 부가세 10%가 포함된 금액에서 공급가액을 구한다
    static BigDecimal supplyPrice(BigDecimal priceWithVat) {
        return priceWithVat.divide(new BigDecimal("1.1"));
    }

    public static void main(String[] args) {
        BigDecimal total = new BigDecimal("10000");
        System.out.println(perPerson(total, 2));
        System.out.println(perPerson(total, 4));
        System.out.println(perPerson(total, 8));
        System.out.println(supplyPrice(new BigDecimal("11000")));
        try {
            System.out.println(perPerson(total, 3));
        } catch (ArithmeticException e) {
            System.out.println(e);
        }
        try {
            System.out.println(supplyPrice(new BigDecimal("10000")));
        } catch (ArithmeticException e) {
            System.out.println(e);
        }
    }
}

    왜 그런가

    BigDecimal의 API 문서는 MathContext를 받지 않는 산술 메서드가 정확한 결과를 돌려준다고 정한다. 덧셈, 뺄셈, 곱셈의 정확한 결과는 언제나 유한한 자릿수로 쓸 수 있다. 나눗셈은 그렇지 않다. 문서는 1을 3으로 나누는 경우를 예로 들면서, 몫의 십진 전개가 끝나지 않는데 정확한 결과를 돌려주도록 지정된 연산이면 ArithmeticException을 던진다고 적는다. divide(BigDecimal)의 설명도 같다. 정확한 몫을 표현할 수 없으면(십진 전개가 끝나지 않으면) 예외를 던진다.

    어떤 나눗셈이 끝나지 않는지는 산수로 정해진다. 몫을 기약분수로 썼을 때 분모의 소인수가 2와 5뿐이면 유한 소수가 되고, 다른 소인수가 하나라도 있으면 무한 소수가 된다. 10000 ÷ 2, ÷ 4, ÷ 8은 분모에 2만 있어서 통과한다. 10000 ÷ 3은 분모가 3이다. 11000 ÷ 1.1은 10000으로 나누어떨어지지만 10000 ÷ 1.1은 100000/11이어서 분모에 11이 남는다. 테스트 데이터를 "계산하기 편한 수"로 고르면 바로 이 통과하는 경우만 고르게 된다.

    넷째 줄의 1.000E+4도 눈여겨볼 만하다. 예외는 나지 않았지만 기대한 10000이 아니다. divide(BigDecimal)의 문서는 결과의 선호 스케일(preferred scale)을 this.scale() - divisor.scale()로 정한다. 정확한 몫을 그 스케일로 나타낼 수 있으면 그 스케일이 쓰이고, 여기서는 0 − 1 = −1이다. 스케일이 음수인 값의 toString()은 지수 표기를 쓴다. 값은 10000과 같고 toPlainString()은 10000을 돌려주지만, 이 문자열이 그대로 화면이나 JSON으로 나가면 다른 종류의 버그가 된다. 스케일을 정하지 않은 나눗셈은 성공할 때도 결과의 형태를 입력에 맡긴다.

    고치는 법

    나눗셈에는 "소수 몇째 자리까지, 어떤 방식으로 끊는가"를 인자로 넘긴다. 이 둘은 코드가 아니라 업무 규칙이 정하는 값이다.

    import java.math.BigDecimal;
import java.math.MathContext;
import java.math.RoundingMode;

public class DivideFixed {
    public static void main(String[] args) {
        BigDecimal total = new BigDecimal("10000");
        BigDecimal three = BigDecimal.valueOf(3);

        System.out.println(total.divide(three, 0, RoundingMode.DOWN));       // (1) 원 단위, 버림
        System.out.println(total.divide(three, 2, RoundingMode.HALF_UP));    // (2) 소수 둘째 자리, 반올림
        System.out.println(total.divide(three, RoundingMode.HALF_UP));       // (3) 자릿수 생략
        System.out.println(total.divide(three, MathContext.DECIMAL64));      // (4) 유효 숫자 16자리
        System.out.println(new BigDecimal("10000").divide(new BigDecimal("1.1"), 0, RoundingMode.HALF_UP));   // (5)

        BigDecimal share = total.divide(three, 0, RoundingMode.DOWN);
        System.out.println(share.multiply(three));                           // (6)
        BigDecimal[] qr = total.divideAndRemainder(three);
        System.out.println(qr[0] + " 나머지 " + qr[1]);                       // (7)

        try {
            new BigDecimal("3333.335").setScale(2);                          // (8)
        } catch (ArithmeticException e) {
            System.out.println(e);
        }
        System.out.println(new BigDecimal("3333.335").setScale(2, RoundingMode.HALF_UP));   // (9)
    }
}

    고쳐도 남는 것

    예외가 사라졌다고 계산이 끝난 것은 아니다. (6)에서 버림으로 구한 1인당 3,333원에 3을 곱하면 9,999원이다. 1원이 어디에도 속하지 않는다. 반올림을 골라도 방향만 바뀔 뿐 같은 일이 생긴다. 나눈 값들의 합이 원래 총액과 같아야 하는 계산(분할 결제, 정산, 안분)에서는 남는 금액을 누가 부담하는지까지 규칙으로 정해야 한다. (7)의 divideAndRemainder는 정수 몫과 나머지를 함께 돌려주므로 "3,333원씩 받고 남은 1원은 첫 번째 사람에게 더한다" 같은 규칙을 그대로 코드로 옮길 수 있다.

    import java.util.*;

public class SubListView {
    public static void main(String[] args) {
        List orders = new ArrayList<>(List.of("o1", "o2", "o3", "o4", "o5"));

        // (1) "앞의 3건"을 잘라 둔다
        List firstPage = orders.subList(0, 3);
        System.out.println(firstPage + " " + firstPage.getClass().getName());

        // (2) 잘라 낸 쪽을 고치면 원본이 바뀐다
        firstPage.set(0, "X");
        firstPage.remove("o2");

        // (3) 원본에 하나 추가한 뒤 잘라 둔 쪽을 읽는다
        orders.add("o6");
        try {
            System.out.println(firstPage.size());
        } catch (ConcurrentModificationException e) {
            System.out.println("size(): " + e);
        }
        try {
            for (String s : firstPage) { System.out.println(s); }
        } catch (ConcurrentModificationException e) {
            System.out.println("for-each: " + e);
        }

        // (4) 원본의 값만 바꾸는 것(set)은 구조적 수정이 아니다
        List view = orders.subList(0, 2);
        orders.set(0, "CHANGED");
        System.out.println(view);

        // (5) 복사해 두면 서로 독립이다
        List copy = new ArrayList<>(orders.subList(0, 2));

        orders.subList(1, 3).clear();

    왜 그런가

    List.subList의 API 문서는 이 메서드가 지정한 범위의 뷰(view)를 돌려주며, 돌려준 리스트는 원래 리스트에 의해 뒷받침되므로(backed by) 한쪽의 비구조적 변경이 다른 쪽에 반영된다고 적는다. 그리고 이렇게 덧붙인다. 원래 리스트가 돌려준 리스트를 거치지 않은 방법으로 구조적으로 수정되면, 돌려준 리스트의 의미는 정의되지 않는다. 문서가 말하는 구조적 수정은 리스트의 크기를 바꾸거나, 진행 중인 순회가 틀린 결과를 낼 수 있게 리스트를 흐트러뜨리는 수정이다.

    OpenJDK 21의 ArrayList.SubList를 보면 이 문장들이 그대로 구현되어 있다. 이 클래스가 선언한 필드는 root(원본 ArrayList), parent(뷰의 뷰일 때 바로 위의 뷰), offset, size 네 개뿐이고, 여기에 상위 클래스 AbstractList에서 물려받은 modCount가 더해진다. 원소를 담는 배열이 없다. get(index)는 root.elementData(offset + index)로 원본의 배열을 읽고, set은 원본의 배열에 쓴다. 그래서 (2)와 (4)처럼 양쪽의 변경이 서로에게 보인다.

    뷰는 만들어질 때 원본의 modCount를 복사해 두고, get, set, size를 포함한 거의 모든 메서드의 첫머리에서 root.modCount != modCount이면 ConcurrentModificationException을 던진다. (3)에서 orders.add가 원본의 modCount를 올렸고, 뷰는 그 사실을 다음 호출에서 발견했다. 원본의 크기가 바뀌면 뷰의 offset과 size가 더는 믿을 수 없는 값이 되므로 틀린 원소를 돌려주느니 실패하는 쪽을 고른 것이다. 다만 이 예외는 ArrayList라는 구현이 해 주는 일이다. 명세가 약속하는 것은 "정의되지 않는다"까지이므로, 다른 List 구현의 뷰가 같은 식으로 알려 준다고 기대해서는 안 된다.

    조각이 원본 전체를 붙잡는다

    뷰가 root 참조를 쥐고 있다는 사실에서 두 번째 문제가 나온다. 뷰가 살아 있는 한 원본 리스트와 그 배열 전체가 도달 가능하다. 다음은 "최근 3건만 남긴다"를 subList로 구현한 코드다. 힙을 32MB로 제한해 실행했다.

    import java.util.*;

            if (i % 100 == 0) System.out.println(i + "번째: size=" + recent.size());
        }
    }

    고치는 법

    subList의 결과를 그 줄을 넘어서까지 살려 둔다면 복사한다. (5)가 그 두 가지 형태다. new ArrayList<>(list.subList(a, b))는 수정할 수 있는 사본을, List.copyOf(list.subList(a, b))는 수정할 수 없는 사본을 만든다. List.copyOf는 문서에 적힌 대로 null 원소가 있으면 받지 않는다. 사본은 원본의 이후 변경에 영향을 받지 않고, 원본을 붙잡지도 않는다.

    반대로 뷰라는 성질이 필요한 자리도 있다. (6)의 list.subList(from, to).clear()는 List의 문서가 직접 드는 관용구로, 범위 삭제 메서드가 따로 없어도 구간을 지울 수 있게 해 준다. 뷰를 만든 그 식 안에서 쓰고 버리므로 앞의 문제가 생길 틈이 없다.

    복사해도 남는 것이 하나 있다. 사본이 복사하는 것은 원소의 참조다. 원소가 가변 객체라면 사본과 원본이 같은 객체를 가리키므로, 원소의 필드를 바꾸면 양쪽에서 보인다. (5)에서 사본이 독립적으로 보인 것은 원소가 불변인 String이기 때문이다.
  • List (Java SE 21 API) — subList가 뷰이고 원본이 구조적으로 수정되면 의미가 정의되지 않는다는 규정, 범위 삭제 관용구, List.copyOf의 null 금지
  • OpenJDK 21 ArrayList.java — 중첩 클래스 SubList의 필드(root, parent, offset, size)와 checkForComodification
  • OutOfMemoryError (Java SE 21 API) — 가비지 컬렉터가 메모리를 더 확보하지 못해 객체를 할당할 수 없을 때 던진다는 정의
    •      List를 구현을 모른 채 get(i) 반복문으로 순회한다 for (int i = 0; i < list.size(); i++) list.get(i)는 ArrayList에서는 원소 수만큼만 일하지만, LinkedList에서는 get(i)가 매번 가까운 쪽 끝에서 노드를 다시 건너가므로 전체가 O(n²)이다. 원소 5만 개를 도는 데 노드를 약 6억 2천만 번 건넌다. 결과는 같아서 데이터가 적을 때는 드러나지 않고, 건수가 2배가 되면 일이 4배가 된다. 같은 합계를 인덱스와 반복자로 구할 때 노드 이동 횟수가 어떻게 달라지는지, RandomAccess 표지 인터페이스의 용도 향상된 for문이 반복자로 풀리고, 반복자가 연결 리스트에서 시간 복잡도를 바꾸는 이유 가변 객체(배열·컬렉션)를 복사하지 않고 필드에 보관하거나 그대로 내준다 생성자가 받은 리스트를 그대로 필드에 넣거나 접근자가 내부 리스트를 그대로 돌려주면, 객체 바깥의 코드가 그 참조로 내부 상태를 바꾼다. 필드가 final이고 setter가 없어도 막지 못한다. 생성자에서 검증을 통과한 뒤에 내용이 바뀌므로, 규칙이 깨진 객체가 예외 없이 돌아다닌다. 들어오는 쪽(생성자 인자)과 나가는 쪽(접근자 반환값)의 두 구멍, 방어적 복사와 List.copyOf로 막는 법 방어적 복사가 컴파일러의 도움 없이 경계마다 반복해야 하는 방법인 이유 static 컬렉션(캐시·등록부)에 넣기만 하고 빼지 않는다 static 필드나 싱글톤 객체의 필드가 가리키는 맵·리스트에 요청마다 항목을 더하고 버리는 규칙이 없으면, 가비지 컬렉터는 그 항목을 끝까지 회수하지 못한다. 키의 가짓수가 몇 개뿐인 테스트에서는 크기가 멈춘다. 사용자 ID나 요청 파라미터처럼 새 키가 계속 들어오는 운영에서는 힙이 조금씩 차오르다가 OutOfMemoryError로 끝난다. 버리는 규칙이 없는 캐시는 이름만 캐시일 뿐 누수라는 점과, 엔트리 하나의 크기에서 상한을 어림하는 법 싱글톤 빈의 맵에 만료 없이 쌓이는 세션 저장소가 왜 회수되지 않는지 가비지 컬렉터가 회수하는 기준이 "다 썼는가"가 아니라 "참조를 따라 닿을 수 있는가"라는 점 접근 순서와 removeEldestEntry로 항목 수에 상한을 둔 LRU 캐시 split·replaceAll에 구분 문자를 그대로 넘긴다 String.split과 replaceAll의 첫 인자는 문자열이 아니라 정규 표현식이다. "192.168.0.1".split(".")은 길이 0인 배열을, split("|")은 글자 하나씩 자른 배열을 예외 없이 돌려주고, replaceAll(".", "-")은 모든 글자를 바꾼다. replaceAll의 둘째 인자에 $나 \가 든 값이 들어오면 예외가 난다. String의 메서드가 무엇을 돌려주는지와, split의 인자가 정규 표현식이라는 한 줄 언급 split(regex)가 끝의 빈 문자열을 버려 배열 길이가 달라지는 예와 limit에 음수를 주는 해법

    문자열을 구분자로 자르거나 일부를 바꿀 때 가장 먼저 손이 가는 메서드가 split과 replaceAll이다. 쉼표나 공백으로 자를 때는 기대대로 동작하므로, 인자가 "구분 문자"라고 믿게 된다. 구분자가 점, 세로 막대, 더하기 기호로 바뀌면 다음과 같이 된다. JDK 21(Temurin 21.0.13)에서 실행했다.

    import java.util.Arrays;
import java.util.function.Supplier;

public class SplitRegex {

    public static void main(String[] args) {

    왜 그런가

    String.split(String regex)의 API 문서 첫 문장은 "이 문자열을 주어진 정규 표현식에 일치하는 부분을 기준으로 나눈다"이고, replaceAll(String regex, String replacement)도 "주어진 정규 표현식에 일치하는 부분 문자열을 모두 바꾼다"이다. 매개변수 이름부터 regex다. Pattern의 문서가 정한 문법에서 예제의 세 구분자는 모두 특별한 뜻을 가진다.

    넘긴 문자열정규식으로서의 뜻결과
    .아무 문자 하나모든 글자가 구분자가 된다
    |왼쪽 또는 오른쪽(X|Y). 양쪽이 비어 있으므로 빈 문자열에 일치한다모든 글자 사이가 구분자가 된다
    +앞의 것을 한 번 이상(X+). 앞에 아무것도 없다문법 오류, PatternSyntaxException

    (1)에서 글자 11개가 전부 구분자이면 그 사이사이의 조각은 모두 빈 문자열이다. 그리고 split(regex)는 split(regex, 0)과 같고, 문서는 limit이 0이면 끝에 붙은 빈 문자열들을 버린다고 정한다. 조각 전부가 빈 문자열이므로 전부 버려져 길이 0인 배열이 남는다. (3)에서는 빈 문자열에 일치하는 폭 0짜리 구분자가 글자마다 놓여 글자 단위로 잘린다. 문서는 문자열 맨 앞의 폭 0짜리 일치는 앞쪽에 빈 문자열을 만들지 않는다고 적는데, 결과의 첫 원소가 빈 문자열이 아니라 k인 것이 그 규칙이다. (5)는 같은 .이 replaceAll에서 모든 글자에 일치한 결과다.

    (6)~(8)은 둘째 인자의 문제다. replaceAll의 문서는 바꿔 넣을 문자열 안의 역슬래시와 달러 기호 때문에 결과가 문자 그대로 바꿨을 때와 달라질 수 있다고 경고한다. Matcher의 문서에 규칙이 있다. $g는 g번째 캡처 그룹이 일치한 내용으로 바뀌고, $ 뒤의 첫 숫자는 언제나 그룹 번호의 일부로 읽히며, 역슬래시는 다음 글자를 문자 그대로 넣으라는 뜻이다. "$15.00"은 "1번 그룹"으로 읽히는데 패턴에 그룹이 없으므로, 문서에 적힌 대로 존재하지 않는 캡처 그룹을 가리킬 때의 IndexOutOfBoundsException이 난다. (7)은 $ 뒤에 번호가 없고 (8)은 역슬래시 뒤에 글자가 없어서 IllegalArgumentException이 났다(메시지는 OpenJDK 21의 것이다). 바꿔 넣을 값이 상수가 아니라 금액, 사용자가 입력한 이름, 파일 경로처럼 밖에서 오는 데이터라면, 그 값에 $나 \가 처음 들어오는 날 이 예외가 난다.

    고치는 법

    정규식이 필요하지 않다면 정규식을 받지 않는 메서드를 쓰고, split처럼 정규식만 받는 메서드에는 문자 그대로 일치하도록 감싼 패턴을 넘긴다.

    import java.util.Arrays;
import java.util.regex.Matcher;
import java.util.regex.Pattern;

public class SplitFixed {
    public static void main(String[] args) {
        System.out.println(Arrays.toString("192.168.0.1".split("\\.")));                 // (1)
        System.out.println(Arrays.toString("192.168.0.1".split("[.]")));                 // (2)
        System.out.println(Arrays.toString("kim|30|seoul".split(Pattern.quote("|"))));   // (3)
        System.out.println(Pattern.quote("|"));

        System.out.println("010.1234.5678".replace(".", "-"));                           // (4)

        String template = "결제 금액: {amount}";
        System.out.println(template.replace("{amount}", "$15.00"));                      // (5)
        System.out.println(template.replaceAll("\\{amount\\}",
                Matcher.quoteReplacement("$15.00")));                                    // (6)
        System.out.println(Matcher.quoteReplacement("$15.00"));

        String line = "kim,30,,";                                                        // 뒤의 두 열이 비어 있다
        System.out.println(line.split(",").length + " " + Arrays.toString(line.split(",")));           // (7)
        System.out.println(line.split(",", -1).length + " " + Arrays.toString(line.split(",", -1)));   // (8)
    }
}
