JDK 17 이하이거나 -Dfile.encoding이 다른 서버에서는 같은 코드가 다른 바이트를 만들고, 한글이 물음표나 대체 문자로 저장되어 되돌릴 수 없게 된다. JDK 18(JEP 400)을 경계로 바뀐 기본값과, 로캘·file.encoding에 따라 달라지는 실제 값 쓴 쪽과 다른 문자 집합으로 읽으면 어떤 글자가 나오는가 버퍼로 읽은 조각마다 new String을 만든다 고정 크기 버퍼로 읽은 바이트를 그때그때 new String(buf, 0, n, UTF_8)로 바꿔 이어 붙이면, 여러 바이트로 된 문자가 버퍼 경계에 걸릴 때마다 양쪽 조각이 모두 대체 문자(U+FFFD)가 된다. 영문만 있는 시험 데이터에서는 드러나지 않고 한글이 섞인 실제 데이터에서 글자가 깨진다. "가나다" 9바이트를 4바이트 버퍼로 읽었을 때의 결과와 UTF-8 바이트 구조로 본 원인 덜 끝난 바이트를 들고 있다가 이어 붙이는 디코더, 곧 InputStreamReader를 써야 하는 이유 크기를 모르는 파일·응답을 통째로 메모리에 올린다 readAllBytes()와 Files.readString()은 내용 전체를 힙의 배열 하나로 만들고, Files.readAllLines()는 모든 줄을 리스트 하나에 담는다. 작은 파일로 시험할 때는 편하지만 수백 MB짜리 파일이나 업로드가 들어오는 날 OutOfMemoryError가 난다. 배열 하나로 읽는 쪽은 2GB를 넘으면 힙 크기와 무관하게 실패한다. 동시에 여러 요청이 이렇게 읽으면 한도는 그만큼 더 낮아진다. 배열 길이 한계와 Required array size too large, 힙과 네이티브 메모리에 한 벌씩 생기는 사본 힙 64MB로 200MB 파일을 옮길 때 readAllBytes만 실패하는 실험과 스트리밍 대안 스트림·소켓·채널을 닫지 않는다 열어 둔 파일이나 소켓을 예외 경로에서 닫지 않으면 그 자리에서는 아무 증상이 없다. 파일 디스크립터가 하나씩 새다가 프로세스 한도에 닿는 날 Too many open files로 새 연결의 accept()와 파일 열기가 한꺼번에 실패하고, 서버 전체가 요청을 받지 못한다. GC는 힙이 부족할 때 움직이지 디스크립터가 부족할 때 움직이지 않는다. 파일 디스크립터의 한도와 Cleaner라는 안전망의 한계 닫지 않은 소켓이 커널에 어떤 상태로 남는가. 이어지는 절들이 try-with-resources까지의 정리 방법을 다룬다 Files.lines·Files.list·Files.walk가 돌려준 스트림을 닫지 않는다 이 메서드들이 돌려주는 Stream은 열린 파일이나 디렉터리를 붙들고 있고, 최종 연산이 끝났다고 저절로 닫히지 않는다. 컬렉션에서 만든 스트림처럼 Files.lines(path).filter(...).count() 한 줄로 쓰면 호출할 때마다 파일 디스크립터가 남아, 바로 위 항목과 같은 한도에 닿는다. 닫아야 하는 스트림과 닫지 않아도 되는 스트림을 가르는 기준(소스가 I/O 채널인가) Files.list가 열려 있는 동안 프로세스의 디스크립터 수가 늘어나는 실험 File.delete()·mkdir()·renameTo()의 반환값을 확인하지 않는다 java.io.File의 이 메서드들은 실패해도 예외를 던지지 않고 false만 돌려준다. 반환값을 버리면 지워지지 않은 임시 파일, 만들어지지 않은 디렉터리, 옮겨지지 않은 파일을 "처리했다"고 믿고 다음 단계로 넘어간다. 실패 원인(권한, 디스크, 대상 없음)도 알 수 없다. 원인이 서로 다른 일곱 개의 false와, 오류 번호가 버려지는 지점 같은 실패를 Files가 어떤 예외로 알려 주는가 기존 파일을 제자리에서 덮어써서 저장한다 new FileOutputStream(file)은 여는 순간 파일 길이를 0으로 만든다. 그 뒤의 쓰기가 예외, 디스크 가득 참, 프로세스 종료로 중단되면 새 내용도 옛 내용도 없는 파일만 남는다. 항목 하나를 추가하려다 전체를 잃는다. 쓰기 실패 뒤 파일에 남는 것, 그리고 임시 파일에 쓴 뒤 ATOMIC_MOVE로 교체하는 방법 사용자가 준 파일 이름을 그대로 경로에 붙인다 요청 경로나 업로드된 파일의 원래 이름을 baseDir.resolve(name)에 그대로 넘기면 ../../etc/passwd 같은 이름이 기준 디렉터리 밖을 가리킨다. 내려받기에서는 서버의 임의 파일이 읽히고, 업로드에서는 다른 파일이 덮어써진다. 같은 이름을 올린 두 사용자의 파일이 서로를 덮어쓰는 것도 같은 실수에서 나온다. normalize와 toRealPath의 차이, 문자열 startsWith로는 막지 못하는 경우 getOriginalFilename()이 돌려주는 값과, 저장 이름을 서버가 새로 만드는 설계 압축 파일의 엔트리 이름을 그대로 경로에 붙여 푼다 업로드받은 ZIP을 targetDir.resolve(entry.getName())으로 풀면, 이름이 ../로 시작하는 엔트리가 대상 디렉터리 밖에 쓰인다. 압축을 풀었을 뿐인데 설정 파일이나 실행 스크립트가 공격자가 넣은 내용으로 바뀐다. 정규화한 경로를 이름 요소 단위로 비교하는 검사와 심볼릭 링크가 끼었을 때의 차이

압축 파일을 푸는 코드는 대개 다음 모양이다. 엔트리를 하나씩 꺼내 대상 디렉터리 아래에 같은 이름으로 쓴다. 아래 예제는 이 코드에 엔트리 이름이 ../app/config.properties인 압축 파일을 넣어 본다. 압축 파일은 메모리에서 만들고, 임시 디렉터리 아래에 풀 곳인 uploads와 그 옆의 app/config.properties를 준비한다.

import java.io.*;
import java.nio.file.*;
import java.util.zip.*;

public class ZipSlip {
    public static void main(String[] args) throws IOException {
        // 공격자가 만든 압축 파일: 엔트리 이름에 ../ 가 들어 있다
        ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        try (ZipOutputStream zip = new ZipOutputStream(bytes)) {
            zip.putNextEntry(new ZipEntry("readme.txt"));
            zip.write("hello".getBytes());
            zip.putNextEntry(new ZipEntry("../app/config.properties"));
            zip.write("admin.password=attacker".getBytes());
        }

        Path base = Files.createTempDirectory("zipslip");
        Path uploads = Files.createDirectories(base.resolve("uploads"));
        Path config = Files.createDirectories(base.resolve("app")).resolve("config.properties");
        Files.writeString(config, "admin.password=original");

        unzipNaive(bytes.toByteArray(), uploads);
        System.out.println("config = " + Files.readString(config));

        Files.writeString(config, "admin.password=original");
        try {
            unzipChecked(bytes.toByteArray(), uploads);
        } catch (IOException e) {
            System.out.println(e.getMessage());
        }
        System.out.println("config = " + Files.readString(config));
    }

    static void unzipNaive(byte[] archive, Path targetDir) throws IOException {
        try (ZipInputStream zip = new ZipInputStream(new ByteArrayInputStream(archive))) {
            for (ZipEntry e; (e = zip.getNextEntry()) != null; ) {
                Path out = targetDir.resolve(e.getName());          // 이름을 그대로 붙인다
                System.out.println("풀기: " + e.getName() + " -> "
                        + targetDir.getParent().relativize(out.normalize()));
                Files.copy(zip, out, StandardCopyOption.REPLACE_EXISTING);
            }
        }
    }

    static void unzipChecked(byte[] archive, Path targetDir) throws IOException {
        Path root = targetDir.toRealPath();
        try (ZipInputStream zip = new ZipInputStream(new ByteArrayInputStream(archive))) {
            for (ZipEntry e; (e = zip.getNextEntry()) != null; ) {
                Path out = root.resolve(e.getName()).normalize();
                if (!out.startsWith(root)) {
                    throw new IOException("압축 대상 디렉터리를 벗어나는 엔트리: " + e.getName());
                }
                Files.copy(zip, out, StandardCopyOption.REPLACE_EXISTING);
            }
        }
    }
}

압축 대상 디렉터리를 벗어나는 엔트리: ../app/config.properties
config = admin.password=original

첫 번째 풀기에서 두 번째 엔트리는 uploads가 아니라 그 옆의 app/config.properties에 쓰였고, 원래 설정은 공격자의 값으로 바뀌었다. 예외도 경고도 없다.

왜 그렇게 되는가

ZIP 형식에서 엔트리 이름은 압축 파일을 만든 쪽이 적어 넣은 문자열일 뿐이다. ZipEntry의 Javadoc이 이름에 거는 제약은 null이 아닐 것과 0xFFFF바이트를 넘지 않을 것 두 가지뿐이고, 경로 구분자나 ..에 대한 규칙은 없다. 위 예제에서도 new ZipEntry("../app/config.properties")가 아무 문제 없이 만들어졌다. 읽는 쪽의 ZipInputStream.getNextEntry()도 그 이름을 그대로 돌려준다. 평범한 압축 도구는 이런 이름을 만들지 않으므로 시험할 때는 드러나지 않는다. 하지만 압축 파일은 바이트 배열이고, 바이트 배열은 누구든 원하는 대로 만들 수 있다.

그다음은 경로 이탈 항목과 같은 이야기다. Path.resolve는 기준 경로 뒤에 상대 경로를 이어 붙일 뿐 결과가 기준 경로 아래에 머무는지 검사하지 않는다. 운영체제는 uploads/../app/config.properties를 열 때 ..을 따라 올라간다. 엔트리 이름이 /로 시작하는 절대 경로라면 resolve는 기준 경로를 버리고 그 절대 경로를 돌려준다. Oracle의 Secure Coding Guidelines for Java SE는 Guideline 5-1에서 신뢰할 수 없는 입력을 쓰기 전에 검증하라고 하면서 그 예로 파일 이름에 "../"를 넣는 디렉터리 순회 공격을 든다. 압축 파일의 엔트리 이름은 파일 이름이 한꺼번에 여러 개 들어오는 입력이다.

고치는 법

unzipChecked가 한 것이 전부다. 엔트리 이름을 붙인 경로를 normalize()로 정규화한 뒤, 그 결과가 대상 디렉터리로 시작하는지 Path.startsWith로 확인하고, 아니면 압축 풀기 전체를 중단한다. 문자열의 startsWith가 아니라 Path의 것을 써야 한다. 문자열 비교는 /srv/uploads-old를 /srv/uploads 아래로 잘못 판단한다. 기준 디렉터리는 toRealPath()로 실제 경로를 구해 둔다. 대상 디렉터리 안에 심볼릭 링크가 이미 있을 수 있는 환경이라면 정규화만으로는 부족하다는 점은 위 강의의 절이 다룬다.

고쳐도 남는 것

이름을 검사해도 크기 문제가 남는다. 같은 가이드라인의 Guideline 1-1은 자원을 지나치게 쓰게 만드는 입력의 예로 아주 높은 비율로 압축된 "zip bomb"을 들고, 압축을 풀 때는 압축된 크기나 메타데이터를 믿지 말고 풀려 나온 데이터의 크기에 한도를 두라고 권한다. SEI CERT의 IDS04-J도 같은 두 가지, 곧 엔트리 경로 검증과 풀린 크기·엔트리 수의 한도를 요구하고, ZipEntry.getSize()가 알려 주는 값은 믿을 수 없으므로 실제로 읽은 바이트를 세라고 한다. 위 예제의 Files.copy(zip, out)는 엔트리가 끝날 때까지 한도 없이 쓰므로, 신뢰할 수 없는 압축 파일을 받는 서비스라면 읽은 바이트 수를 세면서 직접 복사하고 한도를 넘으면 중단해야 한다.
  • Secure Coding Guidelines for Java SE — Guideline 5-1(입력 검증과 "../" 디렉터리 순회), Guideline 1-1(zip bomb과 풀린 크기의 한도)
  • SEI CERT Oracle Coding Standard for Java: IDS04-J — ZipInputStream에서 파일을 풀 때의 경로 검증과 크기·개수 한도
  • Java SE 21 API: ZipEntry — 엔트리 이름에 대한 제약은 null 여부와 길이뿐이다
    •      자식 프로세스의 출력을 읽지 않고 waitFor()로 기다린다 ProcessBuilder로 외부 명령을 실행하고 출력 스트림은 읽지 않은 채 waitFor()를 부르면, 출력이 적은 동안에는 잘 끝난다. 출력이 파이프 버퍼보다 커지는 날 자식은 쓰다가 멈추고 부모는 자식이 끝나기를 기다리며 둘 다 영원히 멈춘다. 프로세스가 서로 격리되어 있다는 것과, ProcessBuilder가 자식의 표준 출력을 파이프로 연결하고 부모가 getInputStream()으로 그 반대쪽 끝을 읽는다는 것

    이미지 변환기, 압축 도구, 셸 스크립트를 자바에서 실행할 때 결과는 종료 코드만 보면 된다고 생각하고 출력은 건드리지 않는 코드가 흔하다. 아래 예제는 표준 출력으로 정해진 바이트 수만큼 쓰고 끝나는 자식 프로세스를 만들어, 출력을 읽지 않고 3초 동안 종료를 기다린다. 바이트 수만 바꿔 세 번 실행한다.

    import java.io.OutputStream;
import java.util.concurrent.TimeUnit;

public class ProcessHang {
    public static void main(String[] args) throws Exception {
        for (int bytes : new int[] {60_000, 70_000, 1_000_000}) {
            // 표준 출력으로 bytes 바이트를 쓰고 끝나는 자식 프로세스
            Process p = new ProcessBuilder("sh", "-c", "head -c " + bytes + " /dev/zero").start();
            boolean exited = p.waitFor(3, TimeUnit.SECONDS);      // 출력은 읽지 않고 끝나기만 기다린다
            System.out.println(bytes + "바이트 출력, 읽지 않음: 3초 안에 종료 = " + exited);
            p.destroyForcibly();
        }

        Process drained = new ProcessBuilder("sh", "-c", "head -c 1000000 /dev/zero").start();
        long n = drained.getInputStream().transferTo(OutputStream.nullOutputStream());
        System.out.println("읽으면서 기다림: " + n + "바이트, 종료 코드 = " + drained.waitFor());

        Process redirected = new ProcessBuilder("sh", "-c", "head -c 1000000 /dev/zero")
                .redirectOutput(ProcessBuilder.Redirect.DISCARD)
                .redirectError(ProcessBuilder.Redirect.DISCARD)
                .start();
        System.out.println("DISCARD로 버림: 3초 안에 종료 = " + redirected.waitFor(3, TimeUnit.SECONDS));
    }
}

    왜 그렇게 되는가

    Process의 Javadoc에 따르면 기본 설정에서 자식 프로세스는 자신의 터미널을 갖지 않고, 표준 입력·출력·오류가 모두 부모 프로세스로 연결된다. 부모는 getInputStream(), getErrorStream()으로 그 출력을 읽는다. 이 연결은 운영체제의 파이프이고 파이프는 커널 안의 크기가 정해진 버퍼다. 리눅스의 pipe(7) 매뉴얼은 파이프의 용량이 한정되어 있고, 가득 찬 파이프에 대한 write는 읽는 쪽이 충분히 읽어 갈 때까지 블로킹된다고 적는다. 같은 매뉴얼에 따르면 리눅스 2.6.11부터 그 용량은 16페이지(페이지가 4,096바이트인 시스템에서 65,536바이트)이고, 구현마다 한도가 다르므로 특정 용량에 기대지 말라고 한다. 위 실험의 macOS에서도 경계가 60,000과 70,000 사이에 있었다.

    자식이 파이프를 채우고 나면 다음 write에서 멈춘다. 자식은 부모가 읽어 주기를 기다리고, 부모는 자식이 끝나기를 기다린다. 락은 하나도 없지만 서로가 서로를 기다리는 교착 상태다. Process의 Javadoc도 이 점을 직접 경고한다. 일부 플랫폼은 표준 입출력 스트림에 제한된 크기의 버퍼만 제공하므로, 자식의 출력 스트림을 제때 읽지 않으면 자식 프로세스가 블로킹되거나 교착 상태에 빠질 수 있다는 것이다.

    표준 오류도 똑같은 파이프다. 표준 출력만 읽고 표준 오류를 내버려 두면, 자식이 오류 메시지를 많이 쓰는 경우에 같은 일이 생긴다. 표준 오류로 1,000,000바이트를 쓴 뒤 표준 출력에 한 줄을 쓰는 명령(head -c 1000000 /dev/zero 1>&2; echo done)을 실행하고 표준 출력만 읽게 했더니 3초 안에 끝나지 않았고, redirectErrorStream(true)로 두 스트림을 합쳐 읽자 1,000,005바이트를 읽고 종료 코드 0으로 끝났다.

    고치는 법

    • 출력이 필요 없으면 연결 자체를 바꾼다. redirectOutput(Redirect.DISCARD)와 redirectError(Redirect.DISCARD)는 출력을 버리고, Redirect.to(file)은 파일로 보내고, inheritIO()는 부모의 표준 입출력을 그대로 물려준다. 어느 쪽이든 부모가 읽어야 하는 파이프가 없어진다.
    • 출력이 필요하면 끝까지 읽은 다음에 기다린다. redirectErrorStream(true)로 표준 오류를 표준 출력에 합치면 읽을 스트림이 하나가 된다. 그 스트림을 EOF까지 읽고 나서 waitFor()를 부른다. 두 스트림을 따로 받아야 한다면 스트림마다 읽는 스레드를 따로 두어야 한다. 한 스레드가 하나를 끝까지 읽는 동안 다른 쪽 파이프가 찰 수 있기 때문이다.
    • 기다림에 한도를 둔다. waitFor(timeout, unit)이 false를 돌려주면 destroyForcibly()로 정리한다. 외부 명령이 다른 이유로 멈추는 경우까지 막아 주는 안전망이다.

    출력을 읽기로 했다면 얼마나 읽을지도 정해야 한다. 자식이 끝없이 출력하는 경우 readAllBytes()는 그것을 모두 힙에 올린다. 필요한 만큼만 읽고 나머지는 버리거나, 파일로 보낸 뒤 파일을 처리하는 편이 안전하다.

    XML을 받는 API, 엑셀·문서 파일(내부가 XML이다) 업로드, 외부 시스템과의 연동에서 다음 코드는 아주 흔하다. 아래 예제는 같은 디렉터리에 db.password=s3cret-from-server-file 한 줄이 든 secret.properties를 두고, 그 파일을 가리키는 엔티티를 선언한 XML을 네 가지 설정의 파서로 읽는다.

import java.nio.charset.StandardCharsets;
import java.nio.file.Path;
import javax.xml.XMLConstants;
import javax.xml.parsers.DocumentBuilderFactory;
import org.w3c.dom.Document;

public class Xxe {
    public static void main(String[] args) throws Exception {
        String secret = Path.of("secret.properties").toUri().toString();   // file:///.../secret.properties
        // 클라이언트가 보낸 XML 이라고 하자
        String xml = """
                
                 ]>
                &x;
                """.formatted(secret);

        DocumentBuilderFactory factory = DocumentBuilderFactory.newInstance();     // 기본 설정
        System.out.println("기본 설정      : " + parse(factory, xml));

        DocumentBuilderFactory secure = DocumentBuilderFactory.newInstance();
        secure.setFeature(XMLConstants.FEATURE_SECURE_PROCESSING, true);
        System.out.println("SECURE_PROCESSING만: " + parse(secure, xml));

        noDoctype.setFeature("http://apache.org/xml/features/disallow-doctype-decl", true);

        DocumentBuilderFactory noExternal = DocumentBuilderFactory.newInstance();
        noExternal.setAttribute(XMLConstants.ACCESS_EXTERNAL_DTD, "");
        noExternal.setAttribute(XMLConstants.ACCESS_EXTERNAL_SCHEMA, "");
        System.out.println("외부 접근 금지 : " + parse(noExternal, xml));
    }

    static String parse(DocumentBuilderFactory factory, String xml) {
        try {
            Document doc = factory.newDocumentBuilder()
                    .parse(new ByteArrayInputStream(xml.getBytes(StandardCharsets.UTF_8)));
            return "memo = [" + doc.getElementsByTagName("memo").item(0).getTextContent().strip() + "]";
        } catch (Exception e) {
            return e.getClass().getName() + ": " + e.getMessage();
        }
    }

    왜 그렇게 되는가

    XML 문서는 DOCTYPE 선언 안에서 엔티티(이름이 붙은 치환 문자열)를 정의할 수 있고, 엔티티의 내용을 문서 안에 직접 적는 대신 SYSTEM "URI"로 바깥의 자원을 가리킬 수 있다. 이것이 외부 엔티티다. 파서는 &x;를 만나면 그 URI를 열어 읽은 내용으로 바꿔 넣는다. 문서를 쓴 사람과 파서를 돌리는 사람이 같을 때는 편리한 기능이지만, 문서를 쓴 사람이 외부인이면 "서버의 권한으로 이 URI를 읽어 달라"는 요청을 문서에 실어 보낼 수 있게 된다. URI가 file:이면 서버의 파일이 읽히고, http:이면 서버가 자기 내부망으로 요청을 보낸다.

    JDK의 기본 설정은 이것을 막지 않는다. Java SE 21의 JAXP Security Guide는 JDK의 XML 프로세서가 기본적으로 XML에 적힌 외부 자원에 연결해 읽어 오려 한다고 적고, 외부 접근을 제한하는 속성 javax.xml.accessExternalDTD의 JDK 기본값이 모든 프로토콜을 허용하는 all이라고 밝힌다. 헷갈리기 쉬운 것이 보안 처리 기능(FEATURE_SECURE_PROCESSING, FSP)이다. 같은 가이드에 따르면 JDK는 SAX·DOM 팩토리에서 FSP를 기본으로 켜 두지만, 기본으로 켜진 상태에서는 외부 연결이 막히지 않는다. 외부 접근까지 제한하려면 FSP를 코드에서 명시적으로 설정해야 한다. 실행 결과의 첫 줄과 둘째 줄의 차이가 그것이다. 기본으로 켜져 있는 FSP는 엔티티 확장 횟수 같은 한도를 걸어 줄 뿐이다.

    고치는 법

    DTD가 필요 없으면 DOCTYPE 선언 자체를 금지하는 것이 가장 단순하다. 셋째 줄처럼 http://apache.org/xml/features/disallow-doctype-decl 기능을 true로 두면 DOCTYPE이 있는 문서는 파싱 단계에서 치명적 오류로 거부된다. JAXP Security Guide는 DTD가 필요 없다면 DTD 처리를 끄는 것으로 서비스 거부, XXE, 서버 측 요청 위조(SSRF)를 포함한 DTD 관련 공격을 한꺼번에 막을 수 있다고 설명하고, OWASP의 XXE 예방 문서도 가능하면 DTD를 끄는 것을 첫 번째 방어로 든다. DTD를 써야 하는 문서라면 넷째 줄처럼 ACCESS_EXTERNAL_DTD와 ACCESS_EXTERNAL_SCHEMA를 빈 문자열로 두어 모든 프로토콜의 외부 접근을 거부한다.

    두 가지를 함께 기억해 둔다. 첫째, 설정은 파서 종류마다 따로 해야 한다. 같은 가이드는 SAX에는 SAXParserFactory에 같은 기능을, StAX에는 XMLInputFactory.SUPPORT_DTD 속성을 false로 두는 예를 따로 싣는다. 팩토리를 만드는 코드를 한곳에 모아 두지 않으면 어느 한 곳에서 빠진다. 둘째, 설정이 실패하면 계속 진행하지 않는다. OWASP 문서는 지원되지 않는 보안 설정을 구성 실패로 다루라고 한다. setFeature가 던진 예외를 잡아서 무시하면 기본 설정의 파서로 돌아간다.

    고쳐도 남는 것

    직접 만든 파서만 고쳐서는 끝나지 않는다. Oracle의 Secure Coding Guidelines for Java SE는 Guideline 3-5에서 XXE를 설명하면서, 이 문제가 XML API가 아니면서 내부적으로 XML을 쓰는 API에도 일반적으로 해당한다고 덧붙인다. 문서 파일을 읽는 라이브러리, XML 메시지 변환기, 설정 파일 로더가 안에서 어떤 파서를 어떤 설정으로 만드는지는 그 라이브러리의 문서로 확인해야 한다.

    방문한 주소를 기억하는 집합, 주소별 설정을 담은 맵처럼 URL을 키로 쓰는 코드는 자연스럽게 java.net.URL을 고른다. 아래 예제는 호스트 이름이 다른 두 URL을 비교하고 맵과 집합에 넣는다. 결과를 누구나 다시 만들 수 있도록 이름 조회는 파일로 고정했다. OpenJDK 21의 InetAddress는 시스템 속성 jdk.net.hosts.file이 주어지면 운영체제에 묻는 대신 그 파일(/etc/hosts와 같은 형식)만 본다. hosts.txt에는 두 이름을 같은 주소로 적었다. 서버 한 대가 여러 사이트를 함께 서비스하는 흔한 구성이다.

    192.0.2.10 shop-a.example
192.0.2.10 shop-b.example
    import java.net.*;
import java.util.*;

public class UrlEquals {
    public static void main(String[] args) throws Exception {
        // 같은 서버(IP 하나)에 올라가 있는 서로 다른 두 사이트
        URL a = URI.create("http://shop-a.example/orders").toURL();
        URL b = URI.create("http://shop-b.example/orders").toURL();

        System.out.println("a.equals(b)            = " + a.equals(b));
        System.out.println("a.hashCode()==b.hashCode() = " + (a.hashCode() == b.hashCode()));

        Map owner = new HashMap<>();
        owner.put(a, "A 상점");
        owner.put(b, "B 상점");
        System.out.println("map = " + owner);

        Set visited = new HashSet<>(List.of(a));
        System.out.println("visited.contains(b)    = " + visited.contains(b));

        // 같은 일을 URI 로
        Map owner2 = new HashMap<>();
        owner2.put(a.toURI(), "A 상점");
        owner2.put(b.toURI(), "B 상점");
        System.out.println("URI map = " + owner2);
    }
}
    a.equals(b)            = true
a.hashCode()==b.hashCode() = true
map = {http://shop-a.example/orders=B 상점}
visited.contains(b)    = true
URI map = {http://shop-a.example/orders=A 상점, http://shop-b.example/orders=B 상점}

    문자열이 다른 두 URL이 같다고 나온다. 맵에는 항목이 하나만 남았고, A 상점의 주소에 B 상점의 값이 들어 있다. 가 본 적 없는 B 상점의 주소는 이미 방문한 것으로 판정된다. 예외는 없다. 같은 프로그램을 내용이 없는 hosts 파일로, 곧 두 이름이 모두 조회되지 않는 상태로 실행하면 결과가 뒤집힌다.

    a.equals(b)            = false
a.hashCode()==b.hashCode() = false
map = {http://shop-a.example/orders=A 상점, http://shop-b.example/orders=B 상점}
visited.contains(b)    = false
URI map = {http://shop-a.example/orders=A 상점, http://shop-b.example/orders=B 상점}

    코드는 한 글자도 바뀌지 않았는데 이름 조회의 결과에 따라 답이 달라졌다. URI로 만든 맵은 두 실행에서 똑같다.

    왜 그렇게 되는가

    URL.equals의 Javadoc이 규칙을 그대로 적어 두었다. 두 URL은 프로토콜, 포트, 파일, 프래그먼트가 같고 "동등한 호스트"를 가리킬 때 같다. 두 호스트는 양쪽 이름이 같은 IP 주소로 해석되면 동등하고, 어느 한쪽이라도 해석되지 않으면 이름을 대소문자 구분 없이 비교한다. 이어서 두 문장이 붙어 있다. 호스트 비교에 이름 해석이 필요하므로 이 연산은 블로킹 연산이다. 그리고 equals에 정의된 이 동작은 HTTP의 가상 호스팅과 맞지 않는 것으로 알려져 있다. hashCode의 Javadoc도 해시 코드가 URL 비교에 쓰이는 모든 구성 요소를 바탕으로 하므로 블로킹 연산이라고 적는다.

    OpenJDK 21의 소스에서 이 규칙이 실행되는 자리는 URLStreamHandler다. hashCode(URL)은 호스트 부분의 해시를 구할 때 먼저 InetAddress.getByName(host)로 주소를 얻어 그 주소의 해시를 더하고, 주소를 얻지 못했을 때만 호스트 이름 문자열의 해시를 더한다. hostsEqual은 두 URL의 주소를 모두 얻었으면 주소끼리 비교하고, 아니면 이름을 비교한다. 첫 실행에서는 두 이름이 모두 192.0.2.10으로 해석되어 해시도 같고 equals도 참이었다. HashMap은 해시가 같고 equals가 참인 키를 같은 키로 보므로 두 번째 put이 첫 번째 값을 덮어썼다. 가상 호스팅에서는 IP 주소 하나가 여러 사이트를 맡고 어느 사이트인지는 요청의 Host 헤더가 정한다. IP가 같다고 같은 자원인 것이 아닌데 URL은 그렇게 판정한다.

    조회에 성공한 주소와 계산한 해시 코드는 URL 객체마다 한 번 구해 필드에 보관한다. 그래서 같은 문자열로 만든 두 URL 객체라도, 하나는 조회가 될 때 해시를 계산했고 다른 하나는 조회가 안 될 때 계산했다면 해시 코드가 서로 다르다. 앞의 두 실행에서 a.hashCode()==b.hashCode()가 뒤집힌 것과 같은 이유다.

    블로킹이라는 말이 뜻하는 비용도 재 보았다. DNS에 없는 이름 20개로 URI와 URL을 만들어 각각 HashSet에 넣는다. 이번에는 hosts 파일 없이 운영체제의 이름 조회를 그대로 쓴다.

    import java.net.*;
import java.util.*;

public class UrlTiming {
    public static void main(String[] args) throws Exception {
        List uris = new ArrayList<>();
        List urls = new ArrayList<>();
        for (int i = 0; i < 20; i++) {
            URI u = URI.create("http://host-" + i + ".invalid/page");   // DNS 에 없는 이름
            uris.add(u);
            urls.add(u.toURL());
        }
        long t = System.nanoTime();
        new HashSet<>(uris);
        System.out.println("HashSet 에 20개: " + (System.nanoTime() - t) / 1_000_000 + "ms");
        t = System.nanoTime();
        new HashSet<>(urls);
        System.out.println("HashSet 에 20개: " + (System.nanoTime() - t) / 1_000_000 + "ms");
    }
}
    HashSet 에 20개: 0ms
HashSet 에 20개: 118ms

    곧바로 다시 실행했을 때 둘째 줄은 32ms였다. 숫자 자체보다, 메모리 안의 연산이어야 할 HashSet 삽입에 네트워크 조회 시간이 들어간다는 점이 문제다. 이름 서버가 느리거나 응답하지 않는 환경에서는 이 시간이 그만큼 늘어나고, 그동안 스레드는 컬렉션 연산 안에서 멈춰 있다.

    고치는 법

    주소를 값으로 다룰 때, 곧 비교하고 저장하고 키로 쓸 때는 java.net.URI를 쓴다. URI의 equals와 hashCode는 구성 요소의 문자열만 보며 네트워크에 나가지 않는다. URL은 실제로 연결을 열어야 하는 순간에 uri.toURL()로 만들어 그 자리에서만 쓴다. JDK 20부터 URL의 공개 생성자에는 모두 @Deprecated(since = "20")이 붙어 있고(제거 예정 표시는 아니다), 클래스의 Javadoc은 URL 문자열을 해석하거나 만들 때는 URI를 쓰고 연결을 열 때만 URI.toURL()로 바꾸라고 안내한다.

    고쳐도 남는 것

    URI의 비교는 문자열 비교에 가깝다는 점을 알고 써야 한다. 직접 실행해 확인한 결과로, http://Shop-A.example/orders와 http://shop-a.example/orders는 같다(호스트는 대소문자를 구분하지 않는다). 그러나 http://shop-a.example:80/orders와 포트를 생략한 주소는 다르고, http://shop-a.example/a/../orders와 http://shop-a.example/orders도 다르다. 뒤의 것은 normalize()를 부른 뒤에 같아진다. 같은 자원을 가리키는 여러 표기를 하나로 볼 것인지는 키를 만드는 쪽이 정해서 맞춰 넣어야 한다.

"한 번 읽으면 메시지 하나"라고 짠 코드는 로컬 시험에서는 통과하다가, 메시지가 커지거나 네트워크가 느려지면 메시지 하나가 여러 조각으로 읽히거나 두 개가 붙어 읽혀 파싱이 어긋난다. 두 번의 write가 경계 없이 읽히는 실험과, 경계를 정하는 세 가지 방법(구분자, 길이 접두어, 연결 종료) HTTP가 본문의 끝을 정하는 규칙 Content-Length에 바이트 수가 아니라 문자 수를 적는다 본문 문자열의 length()를 Content-Length로 쓰면 ASCII만 있을 때는 우연히 맞는다. 한글이 섞이면 실제 바이트가 더 많아서, 클라이언트는 적힌 만큼만 읽고 글자 중간에서 잘린 본문을 받는다. 연결을 재사용하는 클라이언트는 남은 바이트를 다음 응답의 시작으로 읽어 그 연결의 이후 응답까지 어긋난다. 15바이트를 보내면서 길이를 5로 적은 서버와, 그 응답을 받은 클라이언트가 실제로 읽은 다섯 바이트 길이를 실제보다 작게 적었을 때와 크게 적었을 때 수신자에게 일어나는 일 연결·요청마다 스레드를 한도 없이 만든다 accept()할 때마다 new Thread(...).start()를 하면 동시 연결 수만큼 스레드와 파일 디스크립터가 늘어난다. 평소에는 문제가 없다가 접속이 몰리거나 느린 클라이언트가 연결을 붙들면 스레드 스택 메모리와 디스크립터 한도가 먼저 바닥나 서버가 새 연결을 받지 못한다. 연결당 스레드 모델과 그 한계, 디스크립터 한도에 닿았을 때의 예외 스레드 수에 한도를 두고 초과분은 작업 큐에서 기다리게 하는 스레드 풀. 톰캣의 한도들은 바로 다음 절이 다룬다 소켓과 HTTP 클라이언트에 타임아웃을 설정하지 않는다 소켓의 read()는 기본 설정에서 시간 제한 없이 기다리고, new Socket(host, port)의 연결 시도는 운영체제가 포기할 때까지 이어진다. 그 위에 만든 HttpClient.newHttpClient(), HttpURLConnection, new RestTemplate(), RestClient.create()도 타임아웃을 주지 않으면 응답을 기한 없이 기다린다. 호출하는 외부 API 하나가 응답을 멈추거나 상대 컴퓨터의 전원이 꺼지면 예외도 없이 요청 스레드가 하나씩 묶이고, 풀이 바닥나면 그 API와 무관한 요청까지 모두 멈춘다. 소켓 수준의 연결 타임아웃과 읽기 타임아웃(SO_TIMEOUT)이 각각 무엇을 기다리는가, 타임아웃이 없을 때 운영체제가 연결을 포기하기까지 걸리는 시간, 쓰기에는 옵션이 없다는 점 작업 스레드가 모두 묶였을 때 뒤의 요청이 어디에서 기다리는가

    외부 API를 부르는 코드에서 가장 자주 빠지는 설정이다. 아래 예제의 서버는 포트를 열어 두기만 하고 아무것도 하지 않는다. 연결은 커널이 받아 주므로 클라이언트의 연결은 성공하지만 응답은 영원히 오지 않는다. 결제 대행사나 사내의 다른 서비스가 과부하로 멈춘 상황과 같다.

    import java.net.*;
import java.net.http.*;
import java.time.Duration;

public class NoTimeout {
    public static void main(String[] args) throws Exception {
        // 연결은 받아 주지만 응답은 영원히 보내지 않는 서버
        ServerSocket blackHole = new ServerSocket(0, 50, InetAddress.getLoopbackAddress());
        URI uri = URI.create("http://127.0.0.1:" + blackHole.getLocalPort() + "/pay");

        HttpClient client = HttpClient.newHttpClient();
        System.out.println("connectTimeout = " + client.connectTimeout());
        HttpRequest plain = HttpRequest.newBuilder(uri).build();
        System.out.println("request timeout = " + plain.timeout());

        Thread caller = new Thread(() -> {
            try {
                client.send(plain, HttpResponse.BodyHandlers.ofString());
            } catch (Exception e) {
                System.out.println("끝: " + e);
            }
        }, "caller");
        caller.setDaemon(true);
        caller.start();
        for (int sec = 2; sec <= 6; sec += 2) {
            caller.join(2000);
            System.out.println(sec + "초 뒤 caller 상태 = " + caller.getState());
        }

        HttpRequest limited = HttpRequest.newBuilder(uri).timeout(Duration.ofSeconds(1)).build();
        long start = System.nanoTime();
        try {
            client.send(limited, HttpResponse.BodyHandlers.ofString());
        } catch (Exception e) {
            System.out.println(e + " after " + (System.nanoTime() - start) / 1_000_000 + "ms");
        }

        HttpURLConnection legacy = (HttpURLConnection) uri.toURL().openConnection();
        System.out.println("HttpURLConnection connect/read timeout = "
                + legacy.getConnectTimeout() + "/" + legacy.getReadTimeout());
    }
}

request timeout = Optional.empty
2초 뒤 caller 상태 = WAITING
4초 뒤 caller 상태 = WAITING
6초 뒤 caller 상태 = WAITING
java.net.http.HttpTimeoutException: request timed out after 1008ms
HttpURLConnection connect/read timeout = 0/0

    caller 스레드는 6초 뒤에도 WAITING이고, 프로그램을 끝내지 않는 한 계속 그 상태다. 예외도 로그도 없다. 같은 요청에 timeout(Duration.ofSeconds(1))을 주면 1초 뒤 HttpTimeoutException으로 끝난다.

    기본값이 "무한"이다

    출력의 처음 두 줄과 마지막 줄이 기본값을 보여 준다. java.net.http의 경우 HttpRequest.Builder.timeout의 Javadoc이 이렇게 적는다. 타임아웃을 설정하지 않은 효과는 무한한 Duration을 설정한 것과 같다, 곧 영원히 블로킹한다. 연결 타임아웃도 HttpClient.Builder.connectTimeout으로 주지 않으면 비어 있다(Optional.empty). HttpURLConnection은 연결·읽기 타임아웃이 모두 0으로 시작하고, URLConnection의 Javadoc은 0을 무한 타임아웃으로 해석한다고 정한다.

    스프링의 클라이언트도 같은 기본값을 물려받는다. 스프링 프레임워크 6.2.19의 spring-web만 클래스패스에 두고 같은 서버를 호출해 보았다(watch는 호출을 다른 스레드에서 실행하고 5초 뒤 그 스레드의 상태를 찍는 도우미다).

new RestTemplate(factory).getForObject(url, String.class);   // 예외와 걸린 시간을 찍는다

RestTemplate: 5초 뒤 상태 = RUNNABLE

    둘 다 5초 뒤에도 돌아오지 않았다. RestTemplate의 상태가 RUNNABLE인 것은 소켓 읽기에서 멈춘 스레드가 자바의 스레드 상태로는 그렇게 보이기 때문이다. 소스를 보면 이유가 분명하다. new RestTemplate()의 기본 요청 팩토리는 HttpURLConnection을 쓰는 SimpleClientHttpRequestFactory이고, 이 클래스의 connectTimeout과 readTimeout 필드는 -1로 시작하며, 값이 0 이상일 때만 연결 객체에 타임아웃을 설정한다. 설정하지 않았으니 앞에서 본 JDK의 기본값 0, 곧 무한이 그대로 쓰인다. RestClient.create()는 클래스패스를 보고 Apache HttpClient 5, Jetty, Reactor Netty, JDK HttpClient, HttpURLConnection의 순서로 팩토리를 고르는데, 이 실험에서는 JDK HttpClient를 쓰는 JdkClientHttpRequestFactory가 선택되었고 그 readTimeout 필드도 설정하기 전에는 null이다. 다른 HTTP 라이브러리를 쓴다면 기본값은 그 라이브러리가 정하므로 문서에서 직접 확인해야 한다.

    왜 서버 전체가 멈추는가

    서블릿 컨테이너는 정해진 개수의 작업 스레드로 요청을 처리한다. 응답하지 않는 외부 API를 부르는 요청이 들어올 때마다 작업 스레드 하나가 그 호출에 묶인 채 돌아오지 않는다. 그 요청의 비중이 작더라도 묶인 스레드는 풀에 돌아오지 않으므로 시간이 지나면 풀 전체가 같은 호출에서 멈춰 있게 된다. 그 뒤에 온 요청은 외부 API와 아무 관계가 없는 것이라도 스레드를 얻지 못해 대기열에서 기다린다. 장애가 난 것은 남의 서버인데 멈춘 것은 내 서버다. 예외가 나지 않으므로 오류 로그도 남지 않는다.

    고치는 법

    연결 타임아웃과 응답 타임아웃을 둘 다 명시한다. 값은 상대 서비스의 평소 응답 시간과, 이 호출을 기다려 주는 내 쪽 요청의 한도를 보고 정한다. 아래의 숫자는 형식을 보여 주는 예일 뿐이다.

    HttpClient client = HttpClient.newBuilder()
        .connectTimeout(Duration.ofSeconds(2))      // 연결을 맺는 데까지
        .build();
HttpRequest request = HttpRequest.newBuilder(uri)
        .timeout(Duration.ofSeconds(3))             // 응답을 받는 데까지
        .build();

    RestTemplate과 RestClient는 요청 팩토리에 타임아웃을 준다. 스프링 부트 3.5에는 자동 구성되는 클라이언트 전체에 적용되는 spring.http.client.connect-timeout과 spring.http.client.read-timeout 속성이 있고, 이 두 속성에는 기본값이 없다. 적지 않으면 위에서 본 라이브러리의 기본값이 그대로 쓰인다는 뜻이다.

    고쳐도 남는 것

    타임아웃은 "기다리지 않겠다"는 결정일 뿐 요청이 처리되지 않았다는 증거가 아니다. 응답을 기다리다 포기한 요청을 상대 서버는 끝까지 처리했을 수 있다. 그래서 타임아웃 뒤에 같은 요청을 다시 보내도 되는지는 메서드의 멱등성으로 따로 판단해야 한다(이 영역의 "타임아웃 뒤에 POST를 그대로 다시 보낸다" 항목). 또 소켓 수준의 읽기 타임아웃은 읽기 한 번에 대한 한도이지 응답 전체에 대한 한도가 아니라는 점은 위 강의의 절이 설명한다.
  • Java SE 21 API: HttpRequest.Builder — timeout을 설정하지 않으면 무한 Duration과 같다(block forever)
  • Java SE 21 API: HttpClient — connectTimeout()은 빌더에서 설정하지 않으면 빈 Optional이다
  • Java SE 21 API: URLConnection — setConnectTimeout·setReadTimeout에서 0은 무한 타임아웃
  • Spring Framework 6.2 API: SimpleClientHttpRequestFactory — 타임아웃의 기본값은 시스템(JDK)의 기본 타임아웃
  • Spring Boot 3.5 Reference: Calling REST Services — 클라이언트 라이브러리 선택 순서와 spring.http.client.* 타임아웃 속성
  • Spring Boot 3.5 Reference: Common Application Properties — spring.http.client.connect-timeout과 spring.http.client.read-timeout의 기본값 칸이 비어 있다
    •      HTTP 클라이언트를 요청마다 새로 만든다 메서드 안에서 매번 HttpClient.newHttpClient()를 부르면 요청마다 TCP 연결(HTTPS라면 TLS 핸드셰이크까지)을 새로 맺는다. 버려진 클라이언트마다 딸린 스레드는 GC가 그 클라이언트를 수거할 때까지, 풀에 든 연결은 유휴 시간 제한(기본 30초)이 지날 때까지 남는다. 호출량이 늘면 지연이 커지고 스레드와 파일 디스크립터가 쌓인다. 연결을 새로 맺는 비용과 지속 연결이 그것을 어떻게 줄이는가

    "필요할 때 만들어 쓰고 버린다"는 습관대로 쓴 코드다. 아래 예제는 같은 서버에 요청 200개를 두 가지 방식으로 보낸다. 서버는 받은 연결 수를 세려고 accept를 직접 하는 작은 지속 연결(keep-alive) 서버다.

    import java.net.*;
import java.net.http.*;
import java.util.concurrent.atomic.AtomicInteger;

public class ClientPerRequest {
    static final AtomicInteger connections = new AtomicInteger();

    public static void main(String[] args) throws Exception {
        // 연결 수를 세려고 accept 를 직접 하는 작은 keep-alive 서버
        ServerSocket server = new ServerSocket(0, 200, InetAddress.getLoopbackAddress());
        Thread acceptor = new Thread(() -> {
            try {
                while (true) {
                    Socket s = server.accept();
                    connections.incrementAndGet();
                    Thread.ofVirtual().start(() -> serve(s));
                }
            } catch (Exception e) { }
        });
        acceptor.setDaemon(true);
        acceptor.start();
        URI uri = URI.create("http://127.0.0.1:" + server.getLocalPort() + "/");

        for (int i = 0; i < 200; i++) {
            HttpClient client = HttpClient.newHttpClient();          // 요청마다 새로 만든다
            client.send(HttpRequest.newBuilder(uri).build(), HttpResponse.BodyHandlers.ofString());
        }
        report("요청마다 새 클라이언트");
        System.gc();
        Thread.sleep(1000);
        report("System.gc() 1초 뒤");

        connections.set(0);
        HttpClient shared = HttpClient.newHttpClient();              // 하나를 같이 쓴다
        for (int i = 0; i < 200; i++) {
            shared.send(HttpRequest.newBuilder(uri).build(), HttpResponse.BodyHandlers.ofString());
        }
        report("클라이언트 하나를 공유");
    }

    static void report(String label) {
        long selectors = Thread.getAllStackTraces().keySet().stream()
                .filter(t -> t.getName().contains("SelectorManager")).count();
        System.out.println(label + ": 서버가 받은 연결 " + connections.get()
                + "개, 살아 있는 SelectorManager 스레드 " + selectors + "개");
    }

    static void serve(Socket s) {
        try (s) {
            var in = new java.io.BufferedReader(new java.io.InputStreamReader(s.getInputStream()));
            var out = s.getOutputStream();
            while (true) {
                String line = in.readLine();
                if (line == null) return;
                while (!in.readLine().isEmpty()) { }
                out.write("HTTP/1.1 200 OK\r\nContent-Length: 2\r\n\r\nok".getBytes());
                out.flush();
            }
        } catch (Exception e) { }
    }
}
    요청마다 새 클라이언트: 서버가 받은 연결 200개, 살아 있는 SelectorManager 스레드 152개
System.gc() 1초 뒤: 서버가 받은 연결 200개, 살아 있는 SelectorManager 스레드 0개
클라이언트 하나를 공유: 서버가 받은 연결 1개, 살아 있는 SelectorManager 스레드 1개

    요청 200개에 연결 200개를 맺었고, 루프가 끝난 시점에 클라이언트에 딸린 스레드 152개가 아직 살아 있었다. 힙 크기를 지정하지 않고 실행했을 때는 이 수가 41개였다. 루프 도중에 GC가 얼마나 돌았느냐에 따라 달라지는 값이다. 클라이언트 하나를 같이 쓰면 연결도 스레드도 하나다.

    왜 그렇게 되는가

    HttpClient의 Javadoc은 이 클래스가 요청 하나를 나타내는 객체가 아니라 자원을 공유하는 단위라고 설명한다. 한 번 만들어진 HttpClient는 불변이고 여러 요청을 보내는 데 쓸 수 있으며, 인스턴스마다 자신의 연결 풀을 관리한다. 연결 풀은 보통 인스턴스 사이에 공유되지 않으므로, 작업마다 새 클라이언트를 만들면 가능하기는 해도 대개 연결을 재사용하지 못하게 된다고 적혀 있다. 응답을 받은 뒤의 연결은 그 클라이언트의 풀로 돌아가는데, 그 클라이언트를 다시 쓰는 코드가 없으니 재사용될 기회가 없다. 다음 요청은 새 클라이언트의 빈 풀에서 시작해 3-way handshake부터 다시 한다. HTTPS라면 TLS 핸드셰이크도 매번 다시 한다.

    자원이 남는 것은 OpenJDK 21의 구현 때문이다. 이 구현의 클라이언트는 만들어질 때 이름이 HttpClient-N-SelectorManager인 스레드를 하나씩 띄운다(두 개를 만들면 HttpClient-1-SelectorManager, HttpClient-2-SelectorManager가 생긴다). 이 스레드는 지역 변수가 범위를 벗어났다고 바로 사라지지 않고, 실험의 둘째 줄처럼 GC가 그 클라이언트를 수거한 뒤에야 끝난다. 풀에 든 연결의 수명은 따로 정해져 있다. java.net.http 모듈 문서에 따르면 풀에 든 유휴 연결은 기본 30초(jdk.httpclient.keepalive.timeout) 동안 유지된다. 둘을 나눠 확인해 보았다. 힙을 2GB로 고정하고 클라이언트 30개를 요청 하나씩에 쓰고 버린 뒤 System.gc()를 부르지 않고 지켜보니, 서버 쪽에 열려 있는 연결은 20초 뒤에 30개 그대로였다가 35초 뒤에는 0개였고, SelectorManager 스레드는 35초 뒤에도 30개 그대로였다가 System.gc()를 부른 뒤에야 0개가 되었다. 힙이 넉넉해 GC가 드물게 도는 서버에서는 스레드가 다음 GC까지, 소켓이 30초씩 쌓인다. 쌓인 소켓이 프로세스의 디스크립터 한도에 닿으면 "스트림·소켓·채널을 닫지 않는다" 항목과 같은 장애가 된다.

    고치는 법

    클라이언트를 한 번 만들어 계속 쓴다. 불변이므로 static final 필드나 스프링 빈으로 두고 여러 스레드가 함께 써도 된다. 요청마다 달라지는 것(URI, 헤더, 타임아웃)은 HttpRequest에 담는다.

    public class PaymentGateway {
    private static final HttpClient CLIENT = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(2))
            .build();
    // 메서드에서는 CLIENT.send(request, ...) 만 한다
}

    스프링의 RestTemplate과 RestClient도 같은 구조다. 스프링 프레임워크 6.2.19의 JdkClientHttpRequestFactory는 기본 생성자에서 HttpClient.newHttpClient()를 한 번 불러 필드에 보관한다. 그러니 RestClient.create()나 new RestTemplate()을 메서드 안에서 매번 부르면 위 실험과 같은 일이 한 겹 위에서 일어난다. 빈으로 하나 만들어 주입받아 쓴다.

    클라이언트를 정말로 짧게 쓰고 버려야 하는 경우에는 닫는다. HttpClient는 JDK 21부터 close()를 제공하므로 try-with-resources에 넣을 수 있고, Javadoc은 클라이언트를 닫으면 할당된 자원을 일찍 회수할 수 있다고 적는다. 다만 이렇게 해도 연결은 재사용되지 않으므로, 반복해서 호출하는 경로라면 공유가 맞다.
  • Java SE 21 API: HttpClient — 인스턴스마다 연결 풀을 관리하고 인스턴스 사이에는 공유하지 않는다는 설명, close()(21부터)
  • Java SE 21 API: java.net.http 모듈 — jdk.httpclient.keepalive.timeout(기본 30초), jdk.httpclient.connectionPoolSize
    •      응답 본문 스트림을 끝까지 읽지도 닫지도 않는다 상태 코드만 확인하고 InputStream으로 받은 응답 본문을 그대로 두면 그 연결은 풀로 돌아가지 못하고 열린 채 남는다. 요청할 때마다 연결이 하나씩 새서, 내 쪽에서는 소켓이 쌓이고 상대 서버에서는 응답을 쓰다 멈춘 스레드가 쌓인다. 한 연결에서 다음 응답이 시작되려면 앞 응답의 본문이 끝까지 지나가야 하는 이유

    큰 응답을 메모리에 올리지 않으려고 본문을 스트림으로 받는 것은 옳은 선택이다. 그런데 스트림으로 받는 순간 본문을 소비할 책임이 호출한 쪽으로 넘어온다. 아래 예제의 서버는 요청마다 1MiB의 본문을 보낸다. 클라이언트는 하나를 공유하고, 요청 50개를 보내면서 처음에는 상태 코드만 보고, 다음에는 본문을 끝까지 읽고 닫는다.

    import java.io.InputStream;
import java.net.*;
import java.net.http.*;
import java.util.concurrent.atomic.AtomicInteger;

public class BodyNotConsumed {
    static final AtomicInteger accepted = new AtomicInteger();
    static final AtomicInteger open = new AtomicInteger();
    static final byte[] BODY = new byte[1024 * 1024];   // 1MiB 응답 본문

    public static void main(String[] args) throws Exception {
        ServerSocket server = new ServerSocket(0, 200, InetAddress.getLoopbackAddress());
        Thread acceptor = new Thread(() -> {
            try {
                while (true) {
                    Socket s = server.accept();
                    accepted.incrementAndGet();
                    open.incrementAndGet();
                    Thread.ofVirtual().start(() -> serve(s));
                }
            } catch (Exception e) { }
        });
        acceptor.setDaemon(true);
        acceptor.start();
        URI uri = URI.create("http://127.0.0.1:" + server.getLocalPort() + "/report");
        HttpClient client = HttpClient.newHttpClient();
        HttpRequest request = HttpRequest.newBuilder(uri).build();

        for (int i = 0; i < 50; i++) {
            HttpResponse response = client.send(request, HttpResponse.BodyHandlers.ofInputStream());
            if (response.statusCode() != 200) { /* ... */ }
            // 상태 코드만 보고 본문 스트림은 읽지도 닫지도 않는다
        }
        report("본문을 읽지도 닫지도 않음");

        accepted.set(0);
        for (int i = 0; i < 50; i++) {
            HttpResponse response = client.send(request, HttpResponse.BodyHandlers.ofInputStream());
            try (InputStream body = response.body()) {
                body.readAllBytes();                    // 끝까지 읽고 닫는다
            }
        }
        report("본문을 끝까지 읽고 닫음");
    }

    static void report(String label) throws InterruptedException {
        Thread.sleep(500);
        System.out.println(label + ": 새로 맺은 연결 " + accepted.get() + "개, 서버 쪽에 열려 있는 연결 " + open.get() + "개");
    }

    static void serve(Socket s) {
        try (s) {
            var in = new java.io.BufferedReader(new java.io.InputStreamReader(s.getInputStream()));
            var out = s.getOutputStream();
            while (true) {
                String line = in.readLine();
                if (line == null) return;
                while (!in.readLine().isEmpty()) { }
                out.write(("HTTP/1.1 200 OK\r\nContent-Length: " + BODY.length + "\r\n\r\n").getBytes());
                out.write(BODY);                        // 상대가 읽지 않으면 여기서 막힌다
                out.flush();
            }
        } catch (Exception e) {
        } finally {
            open.decrementAndGet();
        }
    }
}
    본문을 읽지도 닫지도 않음: 새로 맺은 연결 50개, 서버 쪽에 열려 있는 연결 50개
본문을 끝까지 읽고 닫음: 새로 맺은 연결 1개, 서버 쪽에 열려 있는 연결 51개

    본문을 내버려 둔 요청 50개는 연결 50개를 새로 맺었고 그 50개는 모두 열린 채 남았다. 본문을 끝까지 읽은 요청 50개는 연결 하나를 맺어 계속 재사용했다. 둘째 줄의 51은 앞에서 샌 50개가 여전히 열려 있다는 뜻이다. 첫 루프 뒤에 System.gc()를 부르고 1.5초를 기다리게 고쳐 실행해도 열린 연결은 50개 그대로였다. 클라이언트 객체가 살아 있는 한 이 연결들은 GC로도 정리되지 않는다.

    왜 그렇게 되는가

    HTTP/1.1의 지속 연결에서 응답은 한 연결 위를 차례로 흐른다. 앞 응답의 본문 바이트가 아직 연결에 남아 있으면 그 연결로 다음 요청의 응답을 구별해 받을 수 없으므로, 클라이언트는 본문이 끝까지 소비된 연결만 풀에 돌려놓는다. BodyHandlers.ofInputStream()은 헤더를 다 읽은 시점에 send가 돌아오고 본문은 호출한 쪽이 스트림에서 읽어 가는 방식이다. 읽지 않으면 본문은 끝나지 않고, 연결은 "응답을 받는 중"인 상태로 남는다. BodySubscribers.ofInputStream()의 Javadoc은 이 책임을 명시한다. 교환에 딸린 모든 자원이 제대로 해제되도록, 호출자는 EOF에 닿을 때까지 모든 바이트를 읽거나, 그럴 수 없다면 InputStream.close()를 불러야 한다.

    상대 서버에도 흔적이 남는다. 클라이언트가 읽지 않으면 클라이언트의 수신 버퍼와 서버의 송신 버퍼가 차고, 서버의 write는 거기서 막힌다. 실험에서 "서버 쪽에 열려 있는 연결"이 줄지 않은 것은 서버 스레드 50개가 out.write(BODY)에서 멈춰 있기 때문이다. 내 실수가 상대 서버의 스레드를 묶는다.

    이 실수는 시험에서 잘 드러나지 않는다. 본문을 2바이트로 줄여 같은 실험을 하면 읽지 않은 50개 요청이 새로 맺은 연결은 2개뿐이었다. 작은 본문은 헤더와 함께 한꺼번에 도착해 클라이언트 안에서 이미 끝까지 받아졌기 때문이다. 응답이 클 때에만, 곧 실제 데이터에서만 샌다.

    고치는 법

    • 스트림으로 받은 본문은 try-with-resources로 감싼다. 정상 경로에서는 끝까지 읽고, 예외로 빠져나가는 경로에서는 close()가 연결을 정리한다.
    • 본문이 필요 없으면 처음부터 버리는 핸들러를 쓴다. BodyHandlers.discarding()은 본문을 읽어서 버리므로 연결이 재사용된다. 본문 전체가 메모리에 올라가도 되는 크기라면 BodyHandlers.ofString()이나 ofByteArray()가 send 안에서 끝까지 읽어 준다.
    • 오류 응답에도 본문이 있다. 상태 코드가 4xx·5xx일 때 예외를 던지고 빠져나가는 분기에서 본문을 닫지 않는 경우가 가장 흔하다.

    읽지 않고 close()만 하는 것은 누수는 막지만 재사용은 포기하는 선택이다. Javadoc도 스트림을 다 읽기 전에 닫으면 아래의 HTTP 연결이 닫혀 이후 작업에 재사용되지 못할 수 있다고 적는다. 위 실험에서 읽지 않고 닫기만 하도록 바꾸면 요청 50개가 연결 50개를 새로 맺었고, 열려 있는 연결은 늘지 않았다. 남은 본문이 작다면 끝까지 읽는 편이, 크다면 닫아 버리는 편이 싸다.
  • Java SE 21 API: HttpResponse.BodySubscribers — ofInputStream()의 API Note: EOF까지 읽거나 close()를 불러야 자원이 해제된다
  • Java SE 21 API: HttpResponse.BodyHandlers — ofInputStream()은 헤더를 읽은 시점에 응답 객체를 돌려준다
  • Java SE 21 API: HttpClient — 스트림을 닫거나 끝까지 읽지 않으면 요청이 완료되지 못할 수 있다는 구현 노트
    •      인증서 오류를 없애려고 모든 인증서를 신뢰하는 TrustManager를 넣는다 자체 서명 인증서를 쓰는 서버에 붙을 때 나는 SSLHandshakeException을 없애려고 아무것도 검사하지 않는 X509TrustManager를 붙여 넣으면 오류는 사라진다. 그 대신 그 클라이언트는 누가 만든 인증서든 받아들인다. 통신 경로에 끼어든 쪽이 직접 만든 인증서로 응답해도 연결이 맺어지고, 요청과 응답은 암호화된 채로 그쪽에 넘어간다.         KeyStore trustStore = KeyStore.getInstance(KeyStore.getDefaultType());

        HttpClient careful = HttpClient.newBuilder().sslContext(pinned).build();
        System.out.println("신뢰 저장소, 진짜 서버 : " + get(careful, real));

    static String get(HttpClient client, URI uri) {
        try {
            return client.send(HttpRequest.newBuilder(uri).build(), HttpResponse.BodyHandlers.ofString()).body();
        } catch (Exception e) {
            return e.getClass().getName() + ": " + e.getMessage();
        }
    }

    // 주어진 키 저장소의 인증서로 루프백에 HTTPS 서버를 띄운다
    static URI startServer(String keyStoreFile, String body) throws Exception {
        KeyStore ks = KeyStore.getInstance("PKCS12");
        try (FileInputStream in = new FileInputStream(keyStoreFile)) {
            ks.load(in, "changeit".toCharArray());
        }
        KeyManagerFactory kmf = KeyManagerFactory.getInstance(KeyManagerFactory.getDefaultAlgorithm());
        kmf.init(ks, "changeit".toCharArray());
        SSLContext ctx = SSLContext.getInstance("TLS");
        ctx.init(kmf.getKeyManagers(), null, null);
        HttpsServer server = HttpsServer.create(new InetSocketAddress(InetAddress.getLoopbackAddress(), 0), 0);
        server.setHttpsConfigurator(new HttpsConfigurator(ctx));
        server.createContext("/", ex -> {
            byte[] bytes = body.getBytes(java.nio.charset.StandardCharsets.UTF_8);
            ex.sendResponseHeaders(200, bytes.length);
            ex.getResponseBody().write(bytes);
            ex.close();
        });
        server.start();
        return URI.create("https://localhost:" + server.getAddress().getPort() + "/account");
    }

    왜 그렇게 되는가

    TLS는 통신을 암호화하는 일과 상대가 누구인지 확인하는 일을 함께 한다. 자바에서 뒤쪽을 맡는 것이 TrustManager다. Java SE 21의 JSSE Reference Guide는 TrustManager의 일차적인 책임이 상대가 제시한 인증 자격 증명을 신뢰할지 결정하는 것이고, 신뢰하지 않으면 연결이 종료된다고 설명한다. 서버가 핸드셰이크에서 내미는 인증서는 누구나 만들 수 있는 데이터다. 위에서 keytool 명령 하나로 이름이 localhost인 인증서를 두 벌 만들었듯이, 인증서에 적히는 이름은 만드는 사람이 정한다. 그 이름을 믿을 근거는 클라이언트가 신뢰하는 인증 기관이 그 인증서에 서명했다는 사실 하나뿐이고, 그 확인이 checkServerTrusted 안에서 일어난다. 이 메서드의 본문을 비우면 어떤 인증서든 통과한다.

    그 뒤에도 통신은 암호화된다. 그래서 "HTTPS이니 안전하다"고 느끼기 쉽다. 하지만 암호화가 보장하는 것은 핸드셰이크를 한 상대 말고는 내용을 읽지 못한다는 것뿐이다. 그 상대가 누구인지 확인하지 않았다면, 통신 경로에 끼어든 쪽과 암호화 통신을 하고 있을 수 있다. 같은 가이드는 TLS 프로토콜 자체는 받은 자격 증명이 기대한 상대의 것과 일치해야 한다고 규정하지 않으며, 연결이 악의적인 상대에게로 돌려졌더라도 그 상대의 자격 증명이 현재의 신뢰 자료로 받아들여진다면 그 연결은 유효한 것으로 간주된다고 적는다. "모두 신뢰"는 모든 자격 증명이 받아들여지는 신뢰 자료다.

    첫 줄의 예외는 고장이 아니라 이 검사가 일한 결과다. 가이드에 따르면 시스템 속성 javax.net.ssl.trustStore를 지정하지 않았을 때 기본 신뢰 저장소는 JDK 설치 경로의 lib/security/jssecacerts, 그 파일이 없으면 lib/security/cacerts다. 자체 서명 인증서는 거기 든 어느 인증 기관으로도 이어지지 않으므로 "요청한 대상까지의 유효한 인증 경로를 찾을 수 없다"는 메시지가 나온다.

    이름 검사는 남아 있지 않은가

    인증서에 적힌 이름과 접속하려는 호스트 이름을 대조하는 검사는 인증서 체인 검증과 별개다. 실험의 "모두 신뢰" 클라이언트로, 이름이 other.example인 인증서를 단 서버에 https://localhost로 접속해 보았다. 결과는 SSLHandshakeException: (certificate_unknown) No subject alternative DNS name matching localhost found.였다. JDK 21에서 이 이름 검사는 빈 X509TrustManager를 넣은 뒤에도 수행되었다. 그러나 이 검사는 위 실험의 공격자를 막지 못한다. 인증서를 직접 만드는 쪽은 이름 칸에 무엇이든 적을 수 있고, 예제의 공격자 인증서도 이름이 localhost였다.

    "모두 신뢰" 코드와 짝을 이뤄 함께 복사되는 것이 HttpsURLConnection의 setHostnameVerifier((host, session) -> true)다. JSSE Reference Guide는 HostnameVerifier를 표준 호스트 이름 검증이 실패했을 때 호출되어 그 연결을 허용할지 답하는 콜백으로 설명한다. 같은 other.example 서버에 HttpsURLConnection과 빈 X509TrustManager로 접속하면 위와 같은 예외로 거부되었고, 언제나 true를 돌려주는 검증기를 더하자 응답 본문을 받아 왔다. 두 가지를 함께 넣은 클라이언트에는 상대를 확인하는 수단이 하나도 없다.

    고치는 법

    오류 메시지는 "이 서버를 보증하는 쪽을 모른다"는 뜻이다. 검사를 끄지 말고 보증하는 쪽을 알려 준다. 예제의 3번이 그 방법이다. 서버의 인증서, 또는 그 인증서를 발급한 사내 인증 기관의 인증서를 KeyStore에 넣고, 그것으로 TrustManagerFactory를 초기화해 얻은 TrustManager로 SSLContext를 만들어 그 서버를 부르는 클라이언트에 준다. 다섯째 줄의 signature check failed는 공격자의 인증서가 신뢰 저장소에 든 인증서의 키로 서명되지 않았다는 뜻이다.

    코드를 고치지 않고 JVM 전체의 신뢰 저장소를 바꾸는 방법도 있다. -Djavax.net.ssl.trustStore로 파일을 지정하면 기본 SSLContext가 그 저장소를 쓴다. 다만 가이드가 적은 탐색 순서대로 이 속성은 cacerts에 더해지는 것이 아니라 그 자리를 대신한다. 지정한 파일에 공인 인증 기관들이 들어 있지 않으면 그 JVM의 다른 HTTPS 호출이 첫 줄과 같은 예외로 실패한다. 특정 상대에게만 필요한 신뢰는 예제처럼 그 클라이언트 전용 SSLContext에 두는 편이 영향 범위가 좁다.

    고쳐도 남는 것

    • 신뢰 저장소도 관리 대상이다. 서버 인증서 자체를 넣었다면 서버가 인증서를 교체할 때 클라이언트의 저장소도 함께 바꿔야 한다. 예제의 인증서는 유효 기간을 30일로 만들었다. 발급한 인증 기관의 인증서를 넣으면 서버 인증서가 바뀌어도 저장소는 그대로 쓸 수 있다.
    • "개발 환경에서만"은 코드가 보장하지 않는다. 빈 TrustManager가 소스에 있으면 같은 코드가 배포된 곳 어디에서나 똑같이 동작한다.
    • 기본값을 바꾸는 호출은 범위가 넓다. SSLContext.setDefault는 이후 SSLContext.getDefault()가 돌려주는 컨텍스트를 바꾼다. "모두 신뢰" 컨텍스트를 여기에 넣으면 직접 쓴 호출 하나가 아니라 기본 컨텍스트를 쓰는 모든 코드가 검증 없이 연결한다.

    •      사용자가 준 URL로 서버가 요청을 보낸다 링크 미리 보기, URL로 이미지 등록, 웹훅처럼 클라이언트가 적어 준 주소를 서버가 대신 호출하는 기능에서 그 주소를 검사하지 않으면, 밖에서는 닿지 않는 내부망의 관리 주소나 클라우드 메타데이터 주소를 서버가 대신 읽어 응답으로 돌려준다(SSRF, 서버 측 요청 위조). 호스트 문자열을 차단 목록과 비교하는 검사는 같은 주소의 다른 표기로 우회된다. 호스트 이름이 InetAddress로 바뀐 뒤에야 연결이 시작된다는 것

    기능 자체는 평범하다. 주소를 받아서 가져온다. 아래 예제에는 루프백에만 열려 있는 관리용 서버가 하나 있다. 밖에서는 이 서버에 연결할 수 없다. fetch는 사용자가 준 URL의 내용을 가져오는 기능이고, 같은 입력 네 개를 검사 없이, 문자열 차단 목록을 거쳐서, 해석한 주소를 검사해서 각각 실행한다. 마지막 입력의 이름은 공격자가 자기 도메인의 DNS 레코드를 내부 주소로 적어 둔 경우다. 실험에서는 127.0.0.1 img.attacker.example 한 줄을 적은 파일을 -Djdk.net.hosts.file로 주어 같은 상황을 만들었다.

    import com.sun.net.httpserver.HttpServer;
import java.net.*;
import java.net.http.*;
import java.time.Duration;
import java.util.Set;

public class Ssrf {
    static final HttpClient CLIENT = HttpClient.newBuilder().connectTimeout(Duration.ofSeconds(2)).build();

    public static void main(String[] args) throws Exception {
        // 내부망에서만 쓰는 관리용 서버. 루프백에만 열려 있어 밖에서는 닿지 않는다
        HttpServer admin = HttpServer.create(new InetSocketAddress(InetAddress.getLoopbackAddress(), 0), 0);
        admin.createContext("/internal/config", ex -> {
            byte[] body = "db.password=s3cret".getBytes();
            ex.sendResponseHeaders(200, body.length);
            ex.getResponseBody().write(body);
            ex.close();
        });
        admin.start();
        int port = admin.getAddress().getPort();

        String[] inputs = {
                "http://127.0.0.1:" + port + "/internal/config",
                "http://2130706433:" + port + "/internal/config",
                "http://[::ffff:127.0.0.1]:" + port + "/internal/config",
                "http://img.attacker.example:" + port + "/internal/config",
        };
        for (String input : inputs) {
            String shown = input.replace(":" + port, ":PORT");
            System.out.println(shown);
            System.out.println("  검사 없음       : " + run(() -> fetch(input)));
            System.out.println("  문자열 차단 목록: " + run(() -> { denyByString(input); return fetch(input); }));
            System.out.println("  해석한 주소 검사: " + run(() -> { denyByAddress(input); return fetch(input); }));
        }
        admin.stop(0);
    }

    // "URL 을 주면 서버가 대신 가져온다": 링크 미리 보기, URL 로 프로필 사진 등록, 웹훅 호출
    static String fetch(String url) throws Exception {
        HttpRequest request = HttpRequest.newBuilder(URI.create(url)).timeout(Duration.ofSeconds(2)).build();
        return CLIENT.send(request, HttpResponse.BodyHandlers.ofString()).body();
    }

    static void denyByString(String url) {
        String host = URI.create(url).getHost();
        if (Set.of("localhost", "127.0.0.1").contains(host) || host.startsWith("10.") || host.startsWith("192.168.")) {
            throw new IllegalArgumentException("내부 주소는 허용하지 않는다: " + host);
        }
    }

    static void denyByAddress(String url) throws UnknownHostException {
        String host = URI.create(url).getHost();
        for (InetAddress addr : InetAddress.getAllByName(host)) {
            if (addr.isLoopbackAddress() || addr.isAnyLocalAddress() || addr.isSiteLocalAddress()
                    || addr.isLinkLocalAddress() || addr.isMulticastAddress()) {
                throw new IllegalArgumentException("내부 주소로 해석된다: " + host + " -> " + addr.getHostAddress());
            }
        }
    }

    interface Call { String get() throws Exception; }

    static String run(Call call) {
        try {
            return "응답 = " + call.get();
        } catch (Exception e) {
            return "거부 (" + e.getMessage() + ")";
        }
    }
}

    검사가 없으면 네 입력 모두 관리용 서버의 설정이 응답으로 나온다. 밖에서는 연결조차 할 수 없는 서버의 내용을, 밖에서 온 요청 하나가 받아 간다. 문자열 차단 목록은 첫 입력만 막았다. 나머지 셋은 127.0.0.1이라는 글자가 없을 뿐 같은 곳으로 간다.

    왜 그렇게 되는가

    방화벽과 네트워크 분리는 밖에서 안으로 들어오는 연결을 막는다. 서버가 보내는 요청은 안에서 출발한다. 서버는 루프백, 같은 내부망의 다른 서비스, 클라우드의 메타데이터 주소에 닿을 수 있는 자리에 있고, "주소를 주면 대신 가져오는" 기능은 그 자리를 요청한 사람에게 빌려준다. OWASP의 SSRF 예방 문서는 이 공격을 애플리케이션을 악용해 내부·외부 네트워크나 그 기기 자체와 상호작용하게 만드는 것으로 정의하고, 대표적인 자리로 사용자가 준 URL에서 아바타 이미지를 가져오는 기능과 사용자가 콜백 URL을 지정하는 웹훅을 든다. 같은 문서는 클라우드 환경에서 SSRF가 메타데이터 서비스의 자격 증명과 접근 토큰을 훔치는 데 자주 쓰인다고 적고, 최소한의 차단 대상에 169.254.169.254를 넣는다.

    문자열 검사가 뚫리는 것은 "어디로 가는가"를 정하는 것이 글자가 아니라 해석된 주소이기 때문이다. 세 우회는 모두 JDK의 문서에 적힌 정상 동작이다.

    • 2130706433: Inet4Address의 Javadoc은 IPv4 주소의 문자열 표현으로 네 부분짜리 말고도 세 부분, 두 부분, 한 부분짜리를 받는다고 정하고, 한 부분만 주어지면 그 값을 바이트 재배열 없이 그대로 주소에 저장한다고 적는다. 2130706433은 127 × 16,777,216 + 1, 곧 맨 앞 바이트가 127이고 맨 뒤 바이트가 1인 값이므로 127.0.0.1이다.
    • [::ffff:127.0.0.1]: IPv4 주소를 IPv6 형식으로 적은 IPv4 매핑 주소다. Inet6Address의 Javadoc에 따르면 자바는 이 형식을 입력으로 받되 IPv4 주소로 바꾼다. 실행 결과에서도 127.0.0.1로 해석되었다.
    • img.attacker.example: 이름이 어떤 주소로 해석될지는 그 도메인의 주인이 정한다. 자기 도메인의 레코드에 내부 주소를 적는 것을 막을 방법은 없다.

    OWASP 문서가 차단 목록은 우회되기 쉬우니 허용 목록을 우선하라고 하는 이유가 이것이다. 같은 문서는 IPv4 매핑 주소 ::ffff:169.254.169.254가 IPv4 표기와 같은 호스트에 닿는다는 점도 직접 경고한다.

    고치는 법

    1. 갈 곳이 정해져 있으면 허용 목록으로 제한한다. 연동하는 상대가 몇 군데로 정해진 기능이라면 그 호스트 목록에 있는 주소만 받는다. 사용자에게서 URL 전체가 아니라 목록 안의 선택지나 경로만 받도록 기능을 바꿀 수 있으면 더 좋다.
    2. 임의의 외부 주소를 받아야 하면 해석한 주소를 검사한다. 예제의 denyByAddress처럼 이름을 InetAddress.getAllByName으로 해석해 나온 주소 전부를 본다. 루프백, 와일드카드(0.0.0.0), 사설 대역(isSiteLocalAddress: OpenJDK 21 소스 기준 10/8, 172.16/12, 192.168/16), 링크 로컬(isLinkLocalAddress: 169.254/16) 가운데 하나라도 있으면 거부한다. 169.254.169.254는 이 가운데 링크 로컬에 해당한다.
    3. 스킴을 http와 https로 제한한다. java.net.URL의 openStream()으로 가져오는 코드에 file: 주소를 주면 서버의 로컬 파일이 읽힌다. 실험에서 db.password=s3cret 한 줄이 든 파일의 file: URI를 toURL().openStream()에 넘기자 그 내용이 그대로 나왔다. java.net.http는 같은 URI에 IllegalArgumentException: invalid URI scheme file을 던졌다.
    4. 리다이렉트를 자동으로 따라가지 않는다. 검사를 통과한 외부 주소가 302로 내부 주소를 가리키면 검사는 소용이 없다. OWASP 문서도 입력 검증의 우회를 막기 위해 웹 클라이언트의 리다이렉트 추적을 끄라고 한다. 기본값은 클라이언트마다 다르다. 직접 찍어 본 값으로 HttpClient.newHttpClient().followRedirects()는 NEVER이고 HttpURLConnection.getFollowRedirects()는 true다. 스프링 프레임워크 6.2.19의 SimpleClientHttpRequestFactory는 소스에서 GET 요청일 때 연결의 리다이렉트 추적을 켠다. 따라가야 한다면 3xx 응답을 직접 받아 Location의 주소를 같은 검사에 다시 통과시킨다.
    5. 네트워크에서도 막는다. OWASP 문서는 애플리케이션 계층의 검사와 함께 네트워크 계층의 방어를 권한다. 이 기능을 수행하는 서버가 꼭 필요한 목적지로만 나갈 수 있게 경로와 방화벽 규칙을 두어, 코드의 검사가 뚫려도 갈 수 있는 곳이 없게 한다.

    고쳐도 남는 것

    첫째, 검사와 연결 사이에 틈이 있다. denyByAddress가 이름을 해석해 검사한 뒤, fetch 안의 HTTP 클라이언트가 같은 이름을 다시 해석해 연결한다. 두 번의 조회 사이에 답이 바뀌면 검사한 주소와 연결한 주소가 달라진다(DNS 리바인딩). OWASP 문서는 검증과 연결 사이에 검사받지 않는 두 번째 DNS 조회가 있으면 이 검사가 우회될 수 있다고 적고, 해석된 주소를 검증한 다음 HTTP 클라이언트가 검증된 그 주소로만 연결하게 하라고 한다. InetAddress에는 조회 결과의 캐시가 있지만, 성공한 조회를 얼마 동안 보관하는지는 JDK 문서에 구현에 따른다고 되어 있어 보장으로 삼을 수 없다.

    둘째, InetAddress의 분류 메서드가 내부 주소를 모두 덮지는 않는다. 직접 확인한 결과로, IPv6 고유 로컬 주소인 fd00::1은 isSiteLocalAddress()를 포함해 예제가 쓴 다섯 검사 가운데 어느 것에도 걸리지 않았고, 100.64.0.1도 마찬가지였다. 차단 목록은 빠진 범위가 하나라도 있으면 뚫린다. 그래서 순서가 위와 같다. 허용 목록으로 풀 수 있는 기능이면 허용 목록이 먼저이고, 주소 검사는 그것이 불가능할 때의 차선이며, 네트워크 수준의 제한이 그 둘을 받친다.
