Future를 돌려받고 결과를 확인하지 않으면 로그조차 남지 않는다. 메일 발송이나 외부 연동이 실패했는데 주문은 정상 완료로 기록된다. 스프링 없이 본 같은 구조. 다른 스레드에서 난 예외는 Future에 담기고, get()으로 꺼내 보지 않으면 어디에도 드러나지 않는다

메서드에 @Async를 붙이면 호출이 곧바로 반환된다. 평소라면 메서드 안에서 난 예외가 호출 스택을 타고 올라와 try/catch에 걸리거나 트랜잭션을 롤백시키지만, 비동기 메서드의 본문은 다른 스레드의 스택에서 실행되므로 그 경로가 없다.

@Configuration
@EnableAsync
class Config { }

@Service
class MailService {
    @Async
    public void send(String to) {
        System.out.println("  send 실행 스레드 = " + Thread.currentThread().getName());
        throw new IllegalStateException("SMTP 연결 실패: " + to);
    }

    @Async
    public CompletableFuture sendWithResult(String to) {
        System.out.println("  sendWithResult 실행 스레드 = " + Thread.currentThread().getName());
        throw new IllegalStateException("SMTP 연결 실패: " + to);
    }
}

[1]에서 catch 블록은 실행되지 않았다. 호출한 쪽은 성공한 줄 알고 다음 일을 하고, 실패는 로그에만 남는다. [2]는 더 조용하다. 예외가 났는데 로그가 한 줄도 없다.

왜 돌아오지 않는가

@EnableAsync는 @Async가 붙은 빈을 프록시로 감싼다. 프록시의 인터셉터(AsyncExecutionInterceptor)는 원래 메서드를 호출하는 일을 작업으로 포장해 실행기에 넘기고 바로 반환한다. 본문은 실행기의 스레드에서 돌고, 거기서 던져진 예외를 받는 것은 호출한 코드가 아니라 그 작업을 감싼 인터셉터다. 6.2.19의 AsyncExecutionAspectSupport.handleError를 javap -c로 열어 보면 분기는 하나다. 메서드의 반환 타입이 Future에 대입 가능하면 예외를 다시 던져 그 Future가 예외로 완료되게 하고, 아니면 AsyncUncaughtExceptionHandler.handleUncaughtException에 넘긴다. 기본 처리기는 SimpleAsyncUncaughtExceptionHandler이고 하는 일은 위 출력에 보이는 오류 로그 한 건이다.

스프링 레퍼런스도 같은 말을 한다. 반환 타입이 Future면 get을 부를 때 예외가 던져지므로 다루기 쉽지만, void면 예외는 잡히지 않고 전달될 수도 없으며 기본 동작은 로그를 남기는 것뿐이라고 적는다. [2]에 로그가 없는 이유도 여기서 나온다. 예외는 CompletableFuture 안에 정확히 담겼다. 그것을 꺼내 본 코드가 없었을 뿐이다. 이 경우는 "처리되지 않은 예외"로 분류되지 않으므로 처리기도 불리지 않는다.

고치는 법

  • 실패를 알아야 하는 일이면 결과를 받는다. 반환 타입을 CompletableFuture로 하고 [3]처럼 whenComplete·exceptionally로 실패를 처리하거나, 결과가 있어야 다음으로 갈 수 있다면 join()으로 기다린다. 기다릴 것이라면 처음부터 비동기로 만들 이유가 있는지 다시 본다.
  • void로 두려면 실패를 메서드 안에서 끝낸다. 비동기 메서드 본문을 try/catch로 감싸 실패를 저장해 둔다(발송 상태 열을 FAILED로 바꾼다, 재시도 대상 테이블에 넣는다). 호출한 쪽이 이미 떠난 뒤이므로 실패를 기록할 수 있는 곳은 그 메서드뿐이다.
  • 놓친 예외가 로그에만 묻히지 않게 한다. AsyncConfigurer.getAsyncUncaughtExceptionHandler()를 구현하면 void 메서드에서 빠져나온 예외를 한곳에서 받는다. 아래 처리기를 등록하고, IllegalStateException("보고서 1번 생성 실패")를 던지는 void 비동기 메서드 build를 호출하자 [알림] build 실패: 보고서 1번 생성 실패가 찍혔다.
@Configuration
@EnableAsync
class AsyncConfig implements AsyncConfigurer {
    @Override
    public AsyncUncaughtExceptionHandler getAsyncUncaughtExceptionHandler() {
        return (ex, method, params) ->
                System.out.println("  [알림] " + method.getName() + " 실패: " + ex.getMessage());
    }
}

처리기를 두어도 달라지지 않는 것이 있다. 처리기는 이미 끝난 실패를 통지받을 뿐이고, 호출한 쪽의 흐름을 되돌리지 못한다. 주문을 저장하고 비동기로 결제 연동을 부른 뒤 커밋했다면, 연동이 실패해도 주문은 저장된 채로 남는다. 실패했을 때 되돌려야 하는 일은 비동기로 떼어 내지 않거나, 떼어 낸다면 실패 상태를 데이터로 남기고 그것을 다시 처리하는 경로를 만들어야 한다.

    @Async 한 줄은 "이 일을 다른 스레드에 맡긴다"까지만 말한다. 어떤 스레드 풀이 맡는지, 일이 밀리면 어떻게 되는지는 실행기(Executor)가 정하는데, 따로 정하지 않으면 환경에 따라 전혀 다른 기본값이 쓰인다.

    실수가 나오는 코드

    @Service
class ReportService {
    static final AtomicInteger running = new AtomicInteger();

    @Async
    public void build(int no) throws InterruptedException {
        running.incrementAndGet();
        if (no == 1 || no == 500) {
            System.out.println("  build(" + no + ") 스레드 = " + Thread.currentThread().getName());
        }
        Thread.sleep(2000);                       // 느린 외부 호출을 흉내 낸다
        running.decrementAndGet();
    }
}

    왜 이렇게 되는가

    [A] 호출마다 스레드. @EnableAsync의 Javadoc에 따르면 스프링은 컨텍스트에서 유일한 TaskExecutor 빈을 찾고, 없으면 이름이 taskExecutor인 Executor 빈을 찾으며, 둘 다 없으면 SimpleAsyncTaskExecutor를 쓴다. 출력의 INFO 줄이 그 탐색이 실패했다는 기록이다. SimpleAsyncTaskExecutor의 Javadoc은 이 구현이 작업마다 새 스레드를 띄우고 스레드를 재사용하지 않으며, 동시 실행 수는 기본으로 제한이 없다고 적는다. 요청이 몰리는 만큼 스레드가 생긴다. Thread의 Javadoc(Java SE 21)에 따르면 플랫폼 스레드는 보통 운영체제 스레드에 일대일로 대응하고, 큰 스택과 운영체제가 관리하는 자원을 따로 갖는다. 그런 스레드의 수를 정하는 것이 풀이 아니라 그 순간 밀려 있는 작업의 수가 된다. 느린 작업이 쌓일수록 스레드와 스택도 함께 쌓이고, 운영체제가 더는 스레드를 만들어 주지 않는 지점에 닿으면 Thread.start()가 OutOfMemoryError를 던진다(HotSpot 기준. 자바 고급 1편 13회가 이 한도를 실제로 넘겨 본다).

    [B] 스레드 8개와 끝없는 큐. 스프링 부트는 Executor 빈이 없으면 실행기를 자동으로 구성한다. 레퍼런스는 이 풀이 코어 스레드 8개를 쓴다고 적고, 3.5.16의 TaskExecutionProperties에서 읽은 큐 용량과 최대 크기의 기본값은 위 출력대로 둘 다 Integer.MAX_VALUE(2147483647)다. 최대 크기가 21억이니 필요하면 늘어날 것 같지만 그렇지 않다. ThreadPoolExecutor의 Javadoc이 정한 규칙은 "코어 크기 이상의 스레드가 돌고 있으면 새 스레드를 만들기보다 큐에 넣는 쪽을 항상 먼저 택한다"이고, 상한 없는 큐를 쓰면 코어 크기보다 많은 스레드는 결코 만들어지지 않아 최대 크기 값은 아무 효과가 없다고 적혀 있다. 스레드는 큐가 가득 찼을 때만 늘어나는데, 21억 칸짜리 큐는 가득 차기 전에 힙이 먼저 찬다. 위 실험에서 2초짜리 작업 500개는 8개씩 처리되므로 500번째 작업은 2분쯤 뒤에야 시작된다. 그동안 호출한 쪽은 아무 오류도 보지 못한다.

    스프링 부트에서 spring.threads.virtual.enabled=true(Java 21 이상)를 켜면 자동 구성 실행기는 가상 스레드를 쓰는 SimpleAsyncTaskExecutor가 된다고 레퍼런스는 적는다. 이 경우는 여기서 실행해 보지 않았다.

    고치는 법

    실행기를 직접 정의하고, 스레드 수와 큐 길이 모두에 상한을 둔다. 스프링 부트라면 spring.task.execution.pool.max-size, queue-capacity 속성으로도 같은 일을 할 수 있다.

    @Configuration
@EnableAsync
class AsyncConfig {
    @Bean
    ThreadPoolTaskExecutor taskExecutor() {
        ThreadPoolTaskExecutor executor = new ThreadPoolTaskExecutor();
        executor.setCorePoolSize(4);
        executor.setMaxPoolSize(8);
        executor.setQueueCapacity(100);              // 큐에 상한을 둔다
        executor.setThreadNamePrefix("report-");
        return executor;
    }
}

    상한을 두면 넘친 작업을 어떻게 할지를 정해야 한다. 같은 500번 호출을 이 실행기로 돌린 결과다(Spring Framework 6.2.19). 둘째 경우는 setRejectedExecutionHandler(new ThreadPoolExecutor.CallerRunsPolicy())를 더한 것이고, 호출한 스레드가 실행한 작업 수는 실행마다 다르다.

    [1] 기본 거부 정책
  109번째 호출에서 org.springframework.core.task.TaskRejectedException
  받아들인 작업 = 108, 풀 크기 = 8, 호출한 스레드가 직접 실행한 작업 = 0
[2] CallerRunsPolicy
  받아들인 작업 = 500, 풀 크기 = 8, 호출한 스레드가 직접 실행한 작업 = 44

    큐 100칸이 차자 스레드가 4개에서 8개로 늘었고, 그것도 차자(8 + 100 = 108) 기본 정책은 호출한 쪽에 TaskRejectedException을 던졌다. 이제 과부하가 예외로 드러나므로 호출한 쪽이 "지금은 처리할 수 없다"고 응답할 수 있다. CallerRunsPolicy는 넘친 작업을 호출한 스레드가 직접 실행하게 한다. 작업을 버리지 않는 대신 호출한 스레드(웹 요청이라면 톰캣의 작업 스레드)가 그 시간만큼 붙잡혀, 밀려드는 속도가 저절로 늦춰진다. 어느 쪽이 맞는지는 그 작업을 잃어도 되는지에 달려 있다. 숫자를 고르는 기준은 작업의 성격이다. 외부 호출을 기다리는 작업이면 스레드 수가 곧 그 외부 시스템에 동시에 보내는 요청 수가 되므로, 상대가 감당할 수 있는 수를 넘기지 않는다.

    •      @Async 메서드 안에서 호출한 쪽 스레드의 ThreadLocal 값을 읽는다 로그인 사용자, 요청 추적 ID처럼 ThreadLocal에 넣어 둔 값은 그 스레드의 것이라 비동기 스레드로 따라가지 않는다. @Async 메서드 안에서는 null이 나오고, InheritableThreadLocal로 바꾸면 스레드 풀에서는 스레드가 만들어질 때의 낡은 값, 곧 다른 요청의 값이 보인다. 값이 스레드 경계에서 끊기는 이유, InheritableThreadLocal이 풀에서 틀리는 실험, TaskDecorator로 제출 시점에 옮기는 방법 @Async·@Scheduled 스레드에는 OSIV도 없어 웹에서 되던 지연 로딩이 예외가 된다 @Scheduled 작업들이 스레드 하나를 나눠 쓴다는 것을 모르고 느린 작업을 넣는다 스케줄러의 기본 스레드는 하나다. 작업 하나가 느린 쿼리나 응답 없는 외부 호출에 걸려 있으면 그동안 애플리케이션의 다른 @Scheduled 작업이 전부 실행되지 않는다. 1초마다 돌아야 할 작업이 몇 분씩 멈췄다가 한꺼번에 몰아서 실행된다. 스레드 수보다 많은 작업이 들어오면 나머지는 기다린다는 스레드 풀의 기본 동작

    @Scheduled를 붙인 메서드들은 서로 관계없는 일처럼 보인다. 결제 상태를 확인하는 작업과 통계를 다시 만드는 작업은 클래스도 주기도 다르다. 그런데 기본 설정에서는 이 둘이 같은 스레드 하나를 차례로 쓴다.

    실수가 나오는 코드

    @Configuration
@EnableScheduling
class Config { }

@Component
class Jobs {
    @Scheduled(fixedRate = 1000)                         // 1초마다: 결제 대기 주문 확인
    public void pollPayments() {
        System.out.println(at() + "  pollPayments   [" + Thread.currentThread().getName() + "]");
    }

    @Scheduled(initialDelay = 2500, fixedDelay = 60000)  // 가끔 도는 무거운 작업
    public void rebuildReport() throws InterruptedException {
        System.out.println(at() + "  rebuildReport 시작 [" + Thread.currentThread().getName() + "]");
        Thread.sleep(5000);                              // 느린 쿼리나 응답 없는 외부 API
        System.out.println(at() + "  rebuildReport 끝");
    }
}

    왜 그런가

    @EnableScheduling의 Javadoc은 스케줄러를 찾는 순서를 적어 둔다. 컨텍스트에서 유일한 TaskScheduler 빈, 없으면 이름이 taskScheduler인 빈, 그다음 같은 방식으로 ScheduledExecutorService 빈을 찾고, 어느 것도 없으면 "스레드 하나짜리 기본 스케줄러를 만들어 쓴다". 출력 첫 줄의 INFO가 그 경우에 찍히는 기록이다. 스프링 부트를 쓰면 스케줄러 빈이 자동으로 구성되지만 사정은 같다. 레퍼런스는 가상 스레드를 켜지 않았을 때 자동 구성되는 ThreadPoolTaskScheduler가 기본으로 스레드 하나를 쓴다고 적고, Spring Boot 3.5.16의 TaskSchedulingProperties에서 spring.task.scheduling.pool.size의 기본값을 읽어 보면 1이다.

    스레드가 하나이면 한 번에 실행되는 작업도 하나다. 실행 시각이 된 작업은 큐에서 그 스레드가 비기를 기다린다. 밀린 실행이 한꺼번에 나온 것은 고정 주기 방식의 규칙 때문이다. ScheduledExecutorService.scheduleAtFixedRate의 Javadoc에 따르면 실행은 처음 지연 뒤, 그다음 주기 뒤, 그다음 두 주기 뒤에 시작하도록 정해지며, 어떤 실행이 주기보다 오래 걸리면 다음 실행들이 늦게 시작할 수 있다. 예정 시각이 이미 지난 실행들은 스레드가 풀리는 즉시 차례로 실행된다. 느린 작업 하나가 다른 작업을 멈추게 하고, 풀린 직후에는 그 작업이 몰아서 실행되어 부하를 한 번 더 만든다.

    운영에서는 이것이 "가끔 배치가 안 돈다"로 보인다. 평소에는 모든 작업이 금방 끝나서 스레드 하나로도 문제가 없다가, 외부 API가 응답하지 않는 날 타임아웃 없는 호출 하나가 스케줄러 스레드를 붙잡으면 그 애플리케이션의 모든 예약 작업이 함께 멈춘다.

    왜 그런가

    @Scheduled 메서드는 컨테이너가 뜰 때 그 컨테이너의 스케줄러에 등록된다. @EnableScheduling의 Javadoc이 설명하는 스케줄러는 컨텍스트 안의 빈이거나, 없을 때 그 자리에서 만드는 지역 스케줄러다. 어느 쪽이든 그 JVM의 스레드가 그 JVM의 시계를 보고 메서드를 부른다. 인스턴스 사이에 "이번 실행은 누가 맡는다"를 정하는 장치는 스프링 프레임워크의 이 기능 안에 없다. cron = "0 0 9 * * *"는 "아침 9시에 한 번"이 아니라 "이 프로세스가 아침 9시에 한 번"이다.

    인스턴스가 평소 한 대뿐이어도 안심할 수 없다. 새 버전을 먼저 띄우고 옛 버전을 내리는 방식으로 배포하면 두 인스턴스가 함께 떠 있는 시간이 생기고, 그 사이에 실행 시각이 오면 둘 다 실행한다.

BindingResult 유무와 위치에 따라 컨트롤러가 호출되는지, 실패한 필드에 무엇이 들어 있는지 실행해 본 표 hasErrors() 확인이 저장보다 앞에 있어야 하는 이유와, BindingResult의 자리가 틀렸을 때의 동작 검증과 값 제한을 브라우저(자바스크립트, required, disabled, 선택 목록)에만 둔다 서버가 받는 것은 브라우저가 아니라 HTTP 메시지이고, 그 메시지는 화면을 거치지 않고도 만들 수 있다. 자바스크립트 검사, 입력 칸의 속성, 선택 목록에 없는 값이라는 사실은 서버를 보호하지 못해, 음수 가격이나 목록에 없는 코드가 그대로 저장된다. 클라이언트 검증은 편의이고 서버 검증이 관문인 이유를 curl 요청 한 줄로 보인다 체크박스·셀렉트 박스에 없는 값, 폼에 없는 필드, disabled·readonly가 서버에서 아무 의미가 없다는 것 @ExceptionHandler에서 오류 본문만 돌려주고 상태 코드를 정하지 않는다 예외 처리 메서드가 오류 객체를 반환만 하면 응답 상태는 서블릿의 기본값 200 그대로 나간다. 본문에는 오류가 적혀 있는데 상태가 성공이라, 클라이언트·모니터링·재시도 로직이 모두 실패를 성공으로 본다. 범위가 넓은 처리 메서드는 스프링이 400으로 처리했을 예외까지 가로채 200으로 바꾼다. 상태를 정하지 않은 처리 메서드가 200을 내는 것과, 원인 예외 매칭으로 타입 변환 실패까지 잡아채는 것을 실행해 확인한다 오류 응답에 예외 메시지와 스택 트레이스를 그대로 싣는다 server.error.include-stacktrace·include-message를 always나 on-param으로 둔 채 운영에 나가거나 예외 메시지를 응답 본문에 그대로 넣으면, 내부 패키지 구조, 쓰는 라이브러리, SQL 조각, 내부 식별자가 누구에게나 보인다. on-param은 URL에 ?trace만 붙이면 켜지므로 always와 다르지 않다. server.error.include-* 속성의 기본값과 on-param의 의미, 운영에서는 응답이 아니라 로그로 원인을 본다는 원칙 인터셉터의 정리 코드를 postHandle에 둔다 postHandle은 컨트롤러가 예외 없이 반환했을 때만 호출된다. ThreadLocal 비우기, 자원 반납, 요청 종료 로그를 여기에 두면 예외가 난 요청에서는 실행되지 않아, 스레드 풀에서 재사용되는 스레드에 앞 요청의 값이 남는다. 정리는 afterCompletion의 몫이다. preHandle·postHandle·afterCompletion이 각각 언제 불리고 언제 건너뛰는지를 HandlerExecutionChain 소스로 읽는다 스레드 풀이 스레드를 재사용할 때 지우지 않은 ThreadLocal 값이 다음 요청에 보이는 실험 로그인에 성공한 뒤에도 세션 ID를 바꾸지 않는다 공격자가 자기가 받은 세션 ID를 피해자의 브라우저에 심어 두면, 피해자가 그 세션으로 로그인하는 순간 공격자가 알고 있는 ID가 로그인된 세션이 된다(세션 고정). getSession()은 이미 있는 세션을 그대로 돌려주므로 로그인 코드는 아무 이상도 느끼지 못한다. 세션 고정 공격의 순서와, 로그인 시점에 changeSessionId()로 ID를 바꾼 뒤 이전 ID가 무효가 되는 것을 실행해 확인한다 세션 ID가 URL에 ;jsessionid=로 붙어 나가도록 둔다 세션 추적 방식에 URL이 포함되어 있으면 톰캣은 세션을 막 만든 요청(쿠키로 들어온 세션 ID가 없는 요청)의 리다이렉트 주소에 세션 ID를 붙인다. 로그인 직후가 바로 그 경우다. 주소는 브라우저 기록, 접근 로그, Referer 헤더에 남고 사용자가 복사해 공유하기도 하므로 세션을 가로챌 길이 넓어지고, 세션 고정 공격에서 ID를 심는 통로도 된다. URL 재작성이 일어나는 세 조건과 server.servlet.session.tracking-modes=cookie로 막는 방법 세션에 조회 결과나 엔티티 그래프 같은 큰 객체를 넣는다 세션은 타임아웃이 지날 때까지 서버 힙에 남는다. 필요한 메모리는 동시에 살아 있는 세션 수와 세션 하나의 크기를 곱한 값이라, 세션 하나가 100배 커지면 필요한 힙도 100배가 된다. 평소에는 버티다가 사용자가 몰리는 날 힙이 모자라게 되고, 계정 객체를 통째로 넣었다면 비밀번호까지 세션에 실린다. 세션 메모리를 정하는 두 인자와 만료된 세션이 실제로 지워지는 시점, 세션에는 식별에 필요한 최소한만 넣는다는 원칙 로그인했는지만 확인하고, 그 데이터를 볼 권한이 있는지는 확인하지 않는다 로그인한 사용자가 URL의 주문 번호를 하나 바꾸면 남의 주문이 보인다. 화면에서 버튼을 숨겨 둔 관리자 기능도 주소를 직접 호출하면 실행된다. 인터셉터의 로그인 검사는 통과했으므로 서버는 정상 요청으로 처리하고 로그에도 이상이 남지 않는다. 로그인 여부를 확인하는 필터와 인터셉터를 만드는 과정. 이 항목은 그다음 단계의 검사를 다룬다 세션에 넣어 둔 로그인 정보를 컨트롤러 파라미터로 받는 방법

    "이 사용자는 누구인가"(인증)와 "이 사용자가 이 일을 해도 되는가"(인가)는 다른 질문이다. 로그인 필터나 인터셉터는 앞의 질문에만 답한다. 뒤의 질문은 어떤 데이터를 다루는지 알아야 답할 수 있는데, 그것을 아는 곳은 컨트롤러와 서비스다.

    왜 뚫리는가

    인터셉터가 본 것은 "세션에 회원 번호가 있는가"가 전부다. 그 뒤 컨트롤러가 받은 id는 경로에 적힌 값, 곧 요청을 보낸 사람이 고른 값이다. 서버 코드 어디에도 "102번 주문이 1번 회원의 것인가"를 묻는 줄이 없으므로 조회는 성공한다. 식별자가 1씩 늘어나는 숫자라면 공격자는 추측할 필요도 없이 번호를 차례로 넣어 전체를 긁어 갈 수 있다. 이런 취약점을 안전하지 않은 직접 객체 참조(IDOR, insecure direct object reference)라고 부른다.

    관리자 기능 쪽은 같은 실수의 다른 모습이다. 템플릿에서 th:if로 버튼을 그리지 않은 것은 HTML에 그 태그가 없다는 뜻일 뿐, 그 주소로 가는 요청을 막지 않는다. 요청은 화면을 거치지 않고도 만들 수 있다. OWASP Top 10(2021)은 이 부류를 "접근 제어 실패(Broken Access Control)"로 묶어 1위에 두었고, 대표적인 형태로 URL을 고쳐 접근 제어를 우회하는 것, 고유 식별자를 넣어 남의 계정을 보거나 고치는 것, POST·PUT·DELETE에 접근 제어가 빠진 API를 든다. 같은 문서는 접근 제어가 공격자가 고칠 수 없는 서버 쪽 코드에서만 효과가 있다고 적는다.

String detailV2(@PathVariable long id, @SessionAttribute long memberId) {
    Order o = ORDERS.get(id);
    if (o == null || o.memberId() != memberId) throw new ResponseStatusException(HttpStatus.NOT_FOUND);
    return o.address();
}

    저장소가 DB라면 같은 뜻의 쿼리가 된다. 주문 번호로 찾은 뒤 비교하는 대신 where id = ? and member_id = ?로 찾으면, 남의 주문은 처음부터 "없는 주문"이 된다. OWASP의 IDOR 대응 문서가 권하는 것도 이 모양이다. 기본 키로 객체를 찾을 때 그 사용자가 접근할 수 있는 범위 안에서 찾으라는 것이다. 남의 주문에 403이 아니라 404를 준 것은 그 번호의 주문이 존재하는지조차 알려 주지 않기 위해서다. 어느 쪽을 쓸지는 정책이지만, 응답으로 존재 여부가 드러난다는 점은 알고 골라야 한다.

    관리자 기능은 서버에서 역할을 검사한다. 로그인할 때 세션에 넣어 둔 역할을 읽어 관리자가 아니면 거부하는 검사를 관리자 경로 전체에 걸고, 새 경로를 만들 때 빠뜨리지 않도록 기본값을 "거부"로 둔다. 허용할 것을 나열하고 나머지는 막는 방식이어야 목록을 고치는 것을 잊었을 때 열리는 것이 아니라 닫힌다.

    고쳐도 남는 것이 있다. 식별자를 순번 대신 추측하기 어려운 값(UUID 등)으로 바꾸면 번호를 차례로 넣어 보는 공격은 어려워지지만, OWASP 문서는 이것을 추가 방어로만 보고 복잡한 식별자를 쓰더라도 접근 제어 검사가 필수라고 적는다. 주소는 로그나 공유로 새어 나갈 수 있기 때문이다. 그리고 이 실수는 기능 테스트로는 드러나지 않는다. 자기 데이터를 조회하는 테스트는 모두 통과한다. "다른 사용자로 로그인해 남의 식별자를 요청하면 거부되는가"를 묻는 테스트를 자원마다 따로 두어야 한다.

    •      비밀번호를 평문이나 SHA-256 한 번으로 저장한다 회원 테이블이 한 번 새어 나가면(SQL 인젝션, 백업 파일, 내부자) 평문은 그대로, 빠른 해시는 사실상 그대로 비밀번호가 드러난다. 솔트 없는 해시는 같은 비밀번호가 같은 값이 되어 미리 계산한 표로 한꺼번에 풀리고, 사용자가 다른 사이트에서도 쓰는 비밀번호라 피해가 그 사이트 밖으로 번진다. 로그인 예제가 비밀번호를 평문으로 두었다는 것과 실제로는 솔트를 넣은 단방향 해시로 저장한다는 언급

    비밀번호를 그대로 저장하면 안 된다는 것은 누구나 안다. 그래서 흔한 실수는 한 단계 뒤에 있다. 해시 함수를 한 번 돌려 저장하고 "암호화했다"고 여기는 것이다.

    실수가 나오는 코드

    static String sha256(String password) throws Exception {
    byte[] d = MessageDigest.getInstance("SHA-256").digest(password.getBytes(StandardCharsets.UTF_8));
    return HexFormat.of().formatHex(d);
}

// [1] 같은 비밀번호를 쓰는 두 회원
System.out.println("kim: " + sha256("qwer1234"));
System.out.println("lee: " + sha256("qwer1234"));

// [2] 스레드 하나로 1초에 계산할 수 있는 SHA-256 의 수
MessageDigest md = MessageDigest.getInstance("SHA-256");
// ... (측정 전에 같은 계산을 30만 번 돌려 JIT 컴파일이 끝나게 했다)
long t0 = System.nanoTime();
int n = 2_000_000;
for (int i = 0; i < n; i++) md.digest(("pw" + i).getBytes(StandardCharsets.UTF_8));
double sec = (System.nanoTime() - t0) / 1e9;
System.out.printf("SHA-256 한 번: 초당 약 %,d개%n", (long) (n / sec));
    kim: 4d4f26369171994f3a46776ee2d88494fb9955800a5bb6261c016c4bb9f30b56
lee: 4d4f26369171994f3a46776ee2d88494fb9955800a5bb6261c016c4bb9f30b56
SHA-256 한 번: 초당 약 12,399,611개

    왜 이것으로는 부족한가

    해시는 되돌릴 수 없지만 맞혀 볼 수는 있다. 공격자는 유출된 표를 가져가 자기 장비에서 후보 비밀번호를 해시해 보고 표의 값과 비교한다. 서버의 로그인 횟수 제한은 이 과정에 끼어들지 못한다. 그러니 방어의 기준은 "후보 하나를 시험하는 데 얼마나 드는가"다.

    • 솔트가 없으면 계산 한 번이 모든 회원에게 쓰인다. 위 출력에서 kim과 lee의 값이 같다. 표를 본 사람은 둘의 비밀번호가 같다는 것을 바로 알고, qwer1234의 SHA-256 값을 한 번 계산하면 그 비밀번호를 쓰는 회원 전부를 찾는다. 자주 쓰이는 비밀번호의 해시를 미리 계산해 둔 표가 그대로 통한다. OWASP 문서는 이런 사전 계산 공격을 막기 위해 비밀번호마다 고유한 솔트를 더해야 한다고 적는다.
    • 빠른 해시는 공격자에게도 빠르다. OWASP 문서는 비밀번호를 저장하는 해시는 느려야 하는데 MD5나 SHA-1 같은 알고리즘은 빠르도록 설계되었다고 구분하고, SHA-256 같은 빠른 해시 알고리즘은 비밀번호 저장에 적합하지 않다고 적는다. 위 실험에서 스레드 하나가 1초에 약 1,200만 개를 계산했다. 스프링 시큐리티 문서는 SHA-256 같은 암호학적 해시가 이제 비밀번호 저장에 안전하지 않은 이유로, 현대 하드웨어가 초당 수십억 번의 해시 계산을 할 수 있어 비밀번호를 하나씩 쉽게 풀 수 있다는 점을 든다. 솔트는 사전 계산을 막을 뿐 회원 한 명에 대한 추측 속도를 늦추지 못한다.

    고치는 법

    비밀번호 저장 전용으로 설계된, 일부러 느린 단방향 함수를 쓴다. 솔트를 회원마다 무작위로 만들고, 계산 비용(작업 계수)을 설정값으로 둔다. OWASP의 비밀번호 저장 문서는 Argon2id를 먼저 권하고, 쓸 수 없으면 scrypt, 기존 시스템의 bcrypt는 작업 계수 10 이상, FIPS-140 준수가 필요하면 PBKDF2를 HMAC-SHA-256과 60만 회 이상의 반복으로 쓰라고 적는다. 이 가운데 JDK만으로 돌릴 수 있는 PBKDF2로 차이를 확인했다.

    static byte[] pbkdf2(char[] password, byte[] salt, int iterations) throws Exception {
    PBEKeySpec spec = new PBEKeySpec(password, salt, iterations, 256);
    try {
        return SecretKeyFactory.getInstance("PBKDF2WithHmacSHA256").generateSecret(spec).getEncoded();
    } finally {
        spec.clearPassword();
    }
}

byte[] salt = new byte[16];
new SecureRandom().nextBytes(salt);                  // 회원마다 새로 만든다
byte[] h1 = pbkdf2("qwer1234".toCharArray(), salt, 600_000);
// ... (걸린 시간을 재는 코드와, 다른 솔트로 lee 의 값을 만드는 코드는 생략)

// 로그인: 저장해 둔 솔트와 반복 횟수로 같은 계산을 한 뒤 비교한다
byte[] attempt = pbkdf2("qwer1234".toCharArray(), salt, 600_000);
System.out.println("일치 = " + MessageDigest.isEqual(h1, attempt));
    PBKDF2-HMAC-SHA256 60만 회: 한 번에 0.14초 -> 초당 약 6.9개
kim: f74a3d0d51a7a1037d37c6cc16d91af9...
lee: 7461786078f6b9fbf7442be60ddea6f3...
일치 = true

    같은 비밀번호인데 두 회원의 값이 다르고, 후보 하나를 시험하는 비용이 같은 장비에서 초당 1,200만 개에서 7개 수준으로 올라갔다. 사용자는 로그인할 때 0.14초를 한 번 치르지만 공격자는 후보마다, 회원마다 그 비용을 치른다. 솔트와 반복 횟수는 비밀이 아니므로 해시 옆에 함께 저장한다. 그래야 나중에 반복 횟수를 올려도 예전 값으로 저장된 회원을 검증할 수 있다. 비교에 MessageDigest.isEqual을 쓴 것은 OpenJDK 21 소스의 구현 노트에 적힌 대로 이 메서드의 계산 시간이 내용에 좌우되지 않기 때문이다.

    스프링 애플리케이션에서는 이것을 직접 짜지 않고 스프링 시큐리티의 PasswordEncoder를 쓰는 것이 보통이다(이 부록에서는 실행하지 않았고 문서 기준이다). 문서에 따르면 PasswordEncoderFactories.createDelegatingPasswordEncoder()가 만드는 인코더는 결과를 {bcrypt}$2a$10$...처럼 {id}인코딩된값 형식으로 저장해, 알고리즘을 바꾼 뒤에도 예전 형식의 비밀번호를 검증할 수 있게 한다. BCryptPasswordEncoder의 기본 강도는 10이고, 문서는 검증 한 번에 1초쯤 걸리도록 자기 시스템에서 강도를 조정해 보라고 권한다.

    함수를 바꿔도 남는 것은 비밀번호 자체의 약함이다. qwer1234처럼 흔한 비밀번호는 후보 목록의 맨 앞에 있어서, 느린 해시로도 오래 버티지 못한다. 저장 방식은 유출 뒤에 시간을 벌어 주는 장치이고, 유출을 알았을 때 비밀번호를 재설정하게 하는 절차를 대신하지 않는다.

Accept에 따라 PNG가 image/avif로, 텍스트가 text/html로 나가는 실험과 서버가 형식을 정해 내려보내는 세 가지 규칙 파일 이름·Content-Type·내용 가운데 무엇이 클라이언트 마음대로인지와 저장 이름을 서버가 만드는 이유 요청 객체를 통째로 로그에 남겨 비밀번호·토큰이 로그 파일에 쌓인다 디버깅하려고 넣은 log.info("요청: {}", form) 한 줄이 toString()을 거쳐 비밀번호, 카드 번호, 인증 토큰을 평문으로 로그에 쓴다. 로그는 파일과 수집 시스템에 오래 남고 DB보다 훨씬 많은 사람이 읽을 수 있어, DB에서는 해시해 둔 비밀번호가 로그에서는 그대로 읽힌다. 스프링 MVC가 디버그 로그에서도 요청 파라미터를 기본으로 가려 두는 것과, 비밀 값은 레벨과 무관하게 로그 문장에 넣지 않는다는 원칙 toString()의 결과가 로그 파일과 예외 메시지로 흘러가므로 비밀번호·개인 정보 필드는 빼야 한다는 언급

    로그에 비밀번호를 남기겠다고 마음먹는 사람은 없다. 실수는 객체를 로그 인자로 넘기는 평범한 줄에서 나온다. 그 객체 안에 무엇이 들어 있는지를 그 줄에서는 볼 수 없기 때문이다.

    실수가 나오는 코드

    record LoginForm(String loginId, String password) { }

static final Logger log = LoggerFactory.getLogger(LogDemo.class);

log.info("로그인 시도: {}", new LoginForm("kim", "qwer1234!"));
    INFO  LogDemo - 로그인 시도: LoginForm[loginId=kim, password=qwer1234!]

    왜 그렇게 되는가

    SLF4J는 {} 자리에 인자의 toString() 결과를 넣는다. 레코드는 toString()을 따로 쓰지 않아도 컴파일러가 만들어 준다. java.lang.Record의 API 문서에 따르면 이 암묵적 구현은 레코드 클래스의 이름, 구성 요소의 이름, 구성 요소 값의 문자열 표현을 담은 문자열을 돌려준다. 구성 요소 전부가 대상이고 예외는 없다. Lombok의 @ToString도 문서에 적힌 기본 동작이 "모든 비정적 필드를 출력"이다. 필드에 password를 추가한 사람과 그 객체를 로그에 넘기는 줄을 쓴 사람이 다르면, 어느 쪽도 자기 변경이 비밀번호를 로그에 쓰게 만들었다는 것을 알기 어렵다.

    로그가 DB보다 위험한 이유는 다루는 방식에 있다. 로그는 서버의 파일로 남고, 수집 시스템으로 복사되고, 장애 분석을 위해 여러 사람이 검색하며, 보관 기간이 길다. 접근 권한도 운영 DB보다 느슨한 경우가 많다. OWASP의 로깅 문서는 로그에 직접 기록하지 말고 지우거나 가리거나 해시해야 할 데이터로 인증 비밀번호, 세션 식별 값, 액세스 토큰, DB 연결 문자열, 암호화 키, 결제 카드 정보, 민감한 개인 정보를 든다. 앞 항목처럼 비밀번호를 느린 해시로 저장해 두어도, 로그인 요청을 로그에 남기면 같은 비밀번호가 평문으로 또 하나 저장되는 셈이다.

    고치는 법

    • 요청에서 온 객체를 통째로 로그에 넘기지 않는다. 필요한 식별자만 골라 쓴다. log.info("로그인 시도: loginId={}", form.loginId()).
    • 비밀 값을 가진 타입은 toString()에서 그 값을 뺀다. 누가 실수로 넘겨도 새지 않게 타입 쪽에서 막는 방법이다. 레코드는 toString()을 직접 재정의하고, Lombok을 쓴다면 해당 필드에 @ToString.Exclude를 붙인다.
    record SafeLoginForm(String loginId, String password) {
    @Override public String toString() { return "SafeLoginForm[loginId=" + loginId + ", password=****]"; }
}

log.info("로그인 시도: {}", new SafeLoginForm("kim", "qwer1234!"));
    INFO  LogDemo - 로그인 시도: SafeLoginForm[loginId=kim, password=****]

    toString()을 고쳐도 막히는 것은 그 경로 하나다. form.password()를 직접 로그에 넘기는 코드, 요청 본문이나 Authorization 헤더를 그대로 찍는 필터, 비밀 값을 그대로 품은 예외 메시지는 여전히 샌다. 요청 전체를 기록하는 로그 필터를 둘 때는 무엇을 가릴지를 먼저 정하고, 이미 로그에 남은 값은 노출된 것으로 보고 폐기·재발급한다.
  • java.lang.Record (Java SE 21) — 암묵적으로 제공되는 toString()이 레코드 이름, 구성 요소 이름, 구성 요소 값의 문자열 표현을 담는다는 명세
  • Project Lombok — @ToString — 기본으로 모든 비정적 필드를 출력하고 @ToString.Exclude로 필드를 뺄 수 있다는 설명
  • OWASP Cheat Sheet — Logging — 로그에 직접 기록하지 말아야 할 데이터 목록(비밀번호, 세션 식별 값, 액세스 토큰, 연결 문자열, 암호화 키 등)
    •      DB 비밀번호와 API 키를 application.properties에 적어 저장소에 커밋한다 설정 파일에 적은 비밀 값은 저장소를 받는 모든 사람과 빌드 서버, 그리고 배포되는 jar 안으로 복사된다. 나중에 그 줄을 지우는 커밋을 올려도 이전 커밋에는 값이 그대로 남아 있어, 저장소가 한 번 공개되거나 유출되면 운영 DB와 결제 API의 열쇠가 함께 나간다. 프로필과 application.properties로 환경마다 다른 구성을 고르는 방법 접속 정보를 코드에 상수로 둔 것은 학습용 단순화이고 실제로는 비밀번호를 설정이나 환경 변수로 뺀다는 언급

    스프링 부트는 application.properties에 값을 적으면 바로 동작한다. 그래서 개발 중에 쓰던 DB 비밀번호와 외부 API 키가 그 파일에 들어가고, 그 파일은 소스와 함께 커밋된다.

    실수가 나오는 코드

    # src/main/resources/application.properties
payment.secret=sk_live_51Hxxxxxxxxxxxxxxxx

    뒤늦게 깨닫고 값을 파일에서 지우는 커밋을 올렸다고 하자. 임시 저장소에서 그대로 해 보았다.

    git commit -qm "설정 추가"                      # 비밀 값이 든 파일을 커밋
# ... 파일의 값을 ${PAYMENT_SECRET} 로 바꾸고
git commit -qam "비밀 값 제거"
grep payment application.properties            # 현재 파일
git show HEAD~1:application.properties | grep payment   # 한 커밋 전의 파일
    payment.secret=${PAYMENT_SECRET}
payment.secret=sk_live_51Hxxxxxxxxxxxxxxxx

    현재 파일에서는 사라졌지만 이전 커밋에서 그대로 읽힌다. 커밋 기록은 저장소를 복제한 모든 곳에 함께 복사되어 있다.

    왜 위험한가

    소스 저장소와 운영 비밀 값은 볼 수 있는 사람의 범위가 다르다. 저장소는 개발자 전원, 빌드 서버, 코드 검색 도구, 때로는 외주 인력과 공개 저장소까지 닿는다. 거기에 운영 DB의 비밀번호가 있으면 그 범위 전체가 운영 DB에 들어갈 수 있다는 뜻이 된다. 파일은 빌드 결과물에도 들어간다. 아래 실험에서 스프링 부트가 이 값을 읽어 온 곳은 class path resource [application.properties], 곧 애플리케이션과 함께 묶이는 클래스패스의 파일이다. jar를 받은 사람은 압축을 풀어 값을 읽을 수 있다.

    한 번 커밋된 값은 "지운다"로 끝나지 않는다. 기록을 다시 쓰더라도 이미 복제된 저장소와 만들어진 jar에는 남아 있다. 그러므로 커밋된 비밀 값은 노출된 것으로 보고 그 값을 폐기한 뒤 새로 발급받아야 한다.

    고치는 법

    비밀 값은 저장소 밖에 두고 실행할 때 넣는다. 스프링 부트는 같은 이름의 속성이 여러 곳에 있을 때 어느 것이 이기는지를 정해 두었다. 레퍼런스의 목록에서 설정 파일(Config data)은 3번, 운영체제 환경 변수는 5번, 명령줄 인자는 11번이고, 뒤에 있는 소스가 앞의 값을 덮어쓴다. 이름은 느슨하게 대응된다. 레퍼런스의 규칙은 점을 밑줄로 바꾸고, 대시를 지우고, 대문자로 바꾸는 것이다(spring.datasource.password는 SPRING_DATASOURCE_PASSWORD). 실제로 확인해 보았다(Spring Boot 3.5.16, Spring Framework 6.2.19). Environment.getProperty("payment.secret")의 값과, 그 이름의 값을 가진 프로퍼티 소스를 찍는 프로그램이다.

    --- [1] 파일에 값이 있고 환경 변수는 없다
payment.secret = sk_live_51Hxxxxxxxxxxxxxxxx
  값을 가진 프로퍼티 소스: Config resource 'class path resource [application.properties]' via location 'optional:classpath:/'
--- [2] 같은 파일, 환경 변수 PAYMENT_SECRET=from-env-var
payment.secret = from-env-var
  값을 가진 프로퍼티 소스: systemEnvironment
  값을 가진 프로퍼티 소스: Config resource 'class path resource [application.properties]' via location 'optional:classpath:/'
--- [3] 파일에 payment.secret=${PAYMENT_SECRET}, 환경 변수 없음
Exception in thread "main" org.springframework.util.PlaceholderResolutionException: Could not resolve placeholder 'PAYMENT_SECRET' in value "${PAYMENT_SECRET}"
--- [4] 같은 파일, 환경 변수 PAYMENT_SECRET=from-env-var
payment.secret = from-env-var

    [1]·[2]·[4]에 함께 찍힌 configurationProperties 줄은 뺐고, [4]의 소스 목록은 [2]와 같아 생략했다. configurationProperties는 다른 소스들을 감싸 이름 대응을 맡는 소스다. [2]에서 환경 변수가 파일의 값을 이겼다. 같은 jar를 고치지 않고 환경마다 다른 값으로 실행할 수 있다는 뜻이다. 다만 [2]의 방식은 파일에 값이 남아 있어도 동작하므로 실수를 가려 준다. [3]처럼 파일에는 자리 표시자만 두면 값이 저장소에 들어갈 자리가 없어지고, 환경 변수를 빠뜨렸을 때 엉뚱한 기본값으로 뜨는 대신 그 값을 읽는 순간 예외로 드러난다.

    환경 변수가 유일한 답은 아니다. 스프링 부트 레퍼런스는 값을 비밀로 지켜야 할 때 환경 변수에 두는 것에도 단점이 있다고 적고, 대안으로 플랫폼이 파일로 마운트해 주는 비밀 값을 spring.config.import=optional:configtree:/run/secrets/처럼 설정 트리로 읽는 방법을 소개한다(이 부록에서는 실행하지 않았다). 어느 방식을 쓰든 원칙은 같다. 저장소에는 "어떤 이름의 값이 필요한가"만 남기고, 값 자체는 그 환경을 운영하는 쪽이 넣는다. 로컬 개발용 값을 파일로 두고 싶다면 그 파일을 버전 관리 대상에서 빼고, 운영과 같은 값을 쓰지 않는다.
