    반쯤 만들어진 객체라는 문제

    앞 회차에서 데이터와 그 데이터를 다루는 메서드를 한 클래스 안에 모았다. 그런데 객체가 만들어지는 순간에 대해서는 아직 아무 규칙도 세우지 않았다. 택배 한 건을 나타내는 클래스를 예로 들어 보자. 받는 사람, 무게, 요금을 필드로 갖고, 운송장을 출력하는 메서드가 하나 있다.

    public class Parcel {
    String receiver;   // 받는 사람
    int weightGram;    // 무게(g)
    int fee;           // 요금(원)

    void printLabel() {
        System.out.println(receiver + " / " + weightGram + "g / " + fee + "원");
    }
}
    public class ParcelMain {
    public static void main(String[] args) {
        Parcel p = new Parcel();
        p.receiver = "김자바";
        p.weightGram = 2500;
        p.printLabel();

        Parcel q = new Parcel();
        q.printLabel();
    }
}
    김자바 / 2500g / 0원
null / 0g / 0원

    이 코드는 컴파일되고, 예외 없이 끝까지 실행된다. 그런데 결과는 둘 다 틀렸다. p는 요금 계산을 빠뜨려서 요금이 0원이고, q는 아무 값도 넣지 않아서 받는 사람이 null인 택배가 되었다. 컴파일러가 이 실수를 잡아 주지 못하는 이유는 언어 규칙에 있다. 지역 변수는 값을 넣기 전에 읽으면 컴파일 오류가 나지만, 인스턴스 변수는 객체가 만들어질 때 타입별 기본값으로 채워진다(JLS 4.12.5). int는 0, boolean은 false, 참조형은 null이다. "값이 없다"는 상태가 없고 항상 어떤 값이 들어 있으므로, 읽는 쪽에서는 그것이 의도한 0인지 빠뜨린 0인지 구별할 수 없다.

    여기서 불변식(invariant)이라는 말을 꺼낼 수 있다. 불변식은 객체가 살아 있는 동안 항상 참이어야 하는 조건이다. 택배 객체라면 "받는 사람이 있다", "무게는 0보다 크다", "요금은 무게로부터 계산된 값이다" 같은 것이다. 위 코드의 p와 q는 불변식이 깨진 채로 프로그램 안을 돌아다닌다. 이런 객체가 다른 메서드로 넘어가면 문제가 드러나는 지점은 만든 곳에서 멀어지고, 원인을 찾기 어려워진다.

    초기화 코드를 메서드로 묶으면 조금 나아진다. 필드 세 개를 한 번에 채우는 init 메서드를 클래스에 넣는 것이다.

    void init(String receiver, int weightGram) {
    this.receiver = receiver;
    this.weightGram = weightGram;
    this.fee = 3000 + (weightGram / 1000) * 500;   // 기본 3000원 + 1kg마다 500원
}

    요금 계산을 빠뜨릴 일은 없어졌다. 하지만 세 가지 약점이 그대로 남는다. 첫째, init을 부르는 것은 여전히 호출하는 사람의 선택이다. new Parcel()만 쓰고 잊어버려도 컴파일된다. 둘째, new Parcel()과 init(...) 사이에는 불변식이 깨진 객체가 존재하는 구간이 있다. 그 사이에 다른 코드가 끼어들면 반쯤 만들어진 객체를 보게 된다. 셋째, init을 두 번 부르는 것도 막을 수 없다. 필요한 것은 "객체를 만드는 일"과 "객체를 유효한 상태로 채우는 일"을 호출하는 쪽에서 떼어 놓을 수 없게 만드는 언어 차원의 장치다. 그것이 생성자(constructor)다.

    this: 지금 다루고 있는 바로 그 객체

    생성자로 넘어가기 전에 위 init 메서드에 나온 this를 정확히 해 두자. 매개변수 이름을 필드 이름과 똑같이 receiver, weightGram으로 지었다. 이름이 같은 선언이 둘 있으면 어느 쪽을 가리키는지 정하는 규칙이 필요하다. JLS 6.4.1은 매개변수나 지역 변수의 선언이 그 유효 범위 안에서 같은 이름의 필드를 가린다(shadowing)고 정한다. 그래서 메서드 본문에서 그냥 receiver라고 쓰면 필드가 아니라 매개변수다.

    가려진 필드에 닿으려면 "어느 객체의 필드인지"를 명시해야 하고, 그 객체를 가리키는 말이 this다. JLS 15.8.3에 따르면 this는 인스턴스 메서드에서는 그 메서드가 호출된 대상 객체를, 생성자에서는 지금 만들어지고 있는 객체를 가리키는 참조값이다. 쓸 수 있는 자리는 인스턴스 메서드 본문, 생성자 본문, 인스턴스 초기화 블록, 인스턴스 변수의 초기화식이다. 객체 없이 실행되는 static 메서드에는 this가 없는데, 그 이유는 6회에서 다룬다.

    그러면 this는 어디에 들어 있는 값일까. 클래스에 메서드 코드는 하나뿐인데, a.printLabel()과 b.printLabel()이 서로 다른 객체의 필드를 읽는다. 이것이 가능한 이유는 호출할 때마다 대상 객체의 참조가 숨은 인자로 함께 전달되기 때문이다. JVMS 2.6.1은 인스턴스 메서드가 호출되면 그 메서드의 스택 프레임에서 0번 지역 변수가 항상 대상 객체의 참조를 담는다고 정한다. 소스 코드에 적은 매개변수는 1번부터 차례로 들어간다. this라는 키워드는 0번 지역 변수를 읽으라는 뜻이다.

    init("김자바", 2500) 이 실행되는 동안의 스택 프레임

  지역 변수 배열
  ┌─────┬──────────────────────────┐
  │  0  │ this  ──────────────┐    │   참조값(예: x001)
  │  1  │ receiver = "김자바"  │    │   매개변수
  │  2  │ weightGram = 2500   │    │   매개변수
  └─────┴─────────────────────┼────┘
                              ▼
                 힙:  Parcel 인스턴스 (x001)
                      receiver   = null → "김자바"
                      weightGram = 0    → 2500
                      fee        = 0    → 4000

    이 그림을 머리에 두면 초보자가 자주 만드는 버그 하나가 바로 설명된다. this.을 빼고 receiver = receiver;라고 쓰면 어떻게 될까. 좌변도 우변도 매개변수이므로, 1번 지역 변수의 값을 읽어 1번 지역 변수에 다시 넣는다. 실제로 javap -c로 보면 이 문장은 aload_1(1번 지역 변수를 스택에 올림)과 astore_1(스택의 값을 1번 지역 변수에 저장) 두 명령으로 컴파일된다. 힙에 있는 객체의 필드에는 아무 일도 일어나지 않고, 필드는 기본값 null로 남는다. 컴파일 오류가 아니라는 점이 이 버그를 까다롭게 만든다.

    반대로 이름이 겹치지 않으면 this.을 생략할 수 있다. printLabel() 안의 fee는 지역 변수나 매개변수 중에 그런 이름이 없으므로 필드로 해석되고, 컴파일러는 this.fee라고 쓴 것과 같은 바이트코드(aload_0으로 this를 올린 뒤 getfield로 필드를 읽음)를 만든다. 즉 this.을 쓰느냐 마느냐는 가려진 경우를 빼면 표기의 선택이고, 실행되는 코드는 같다.

    생성자를 도입한다

    init 메서드를 생성자로 바꾸면 다음과 같다. 바뀐 곳은 선언부 한 줄이다.

    public class Parcel {
    String receiver;
    int weightGram;
    int fee;

    Parcel(String receiver, int weightGram) {
        this.receiver = receiver;
        this.weightGram = weightGram;
        this.fee = 3000 + (weightGram / 1000) * 500;
    }

    void printLabel() {
        System.out.println(receiver + " / " + weightGram + "g / " + fee + "원");
    }
}
    public class ParcelMain {
    public static void main(String[] args) {
        Parcel p = new Parcel("김자바", 2500);
        p.printLabel();   // 김자바 / 2500g / 4000원
    }
}

    생성자 선언에는 메서드와 다른 규칙이 두 가지 있다(JLS 8.8). 이름은 반드시 그 클래스의 단순 이름과 같아야 하고, 반환 타입을 적지 않는다. void도 적지 않는다. 그 밖의 모양은 반환값이 없는 메서드 선언과 같아서 매개변수 목록, 본문, 접근 제어자를 가질 수 있다. 무게 2500g의 요금은 3000 + (2500 / 1000) * 500인데, int끼리의 나눗셈은 소수점 아래를 버리므로 2500 / 1000은 2이고 요금은 4000원이 된다.

    모양은 메서드와 닮았지만 언어 명세에서 생성자는 메서드가 아니다. JLS 8.8은 생성자 선언이 클래스의 멤버가 아니며, 상속되지 않고, 따라서 오버라이딩의 대상도 아니라고 적는다. 또 생성자는 메서드 호출식으로는 부를 수 없다. p.Parcel("이름", 100) 같은 코드는 생성자를 부르지 못한다. 생성자가 실행되는 길은 new로 시작하는 클래스 인스턴스 생성식과, 생성자 안에서 다른 생성자를 부르는 this(...)·super(...)뿐이다(문자열 연결 연산처럼 언어가 내부적으로 객체를 만드는 경우는 제외하고 말한 것이다).

    이 제한이 바로 원하던 보장을 만든다. 생성자를 선언한 뒤 예전 방식으로 객체를 만들려고 하면 컴파일이 되지 않는다.

    Parcel p = new Parcel();   // 컴파일 오류
    error: constructor Parcel in class Parcel cannot be applied to given types;
  required: String,int
  found:    no arguments
  reason: actual and formal argument lists differ in length

    Parcel 객체를 얻는 방법은 이제 new Parcel(받는 사람, 무게) 하나뿐이고, 이 식은 생성자 본문이 끝난 뒤에야 참조값을 돌려준다. 호출하는 쪽에서는 받는 사람과 무게와 요금이 채워지지 않은 Parcel을 손에 쥘 방법이 없다. 초기화 누락이라는 런타임 버그가 컴파일 오류로 옮겨 왔고, 생성과 초기화 사이의 빈 구간도 사라졌다.

    이 장의 핵심

    생성자는 "객체를 만드는 문법"이 아니라 "만들어진 객체가 유효한 상태가 된 뒤에야 바깥으로 나가게 하는 관문"이다. 메모리를 잡는 일은 new가 하고, 생성자는 그 메모리를 의미 있는 객체로 초기화한다. 언어와 JVM은 이 두 단계를 호출하는 쪽에서 분리할 수 없게 묶어 둔다.

    new 식 한 줄이 하는 일: new, dup, invokespecial

    new Parcel("김자바", 2500)은 소스에서는 식 하나지만 JVM이 실행하는 명령으로는 여러 단계다. 위 ParcelMain을 컴파일한 뒤 javap -c ParcelMain으로 main 메서드의 바이트코드를 보면 다음과 같다(JDK 21의 javac 출력이며, #7 같은 상수 풀 번호는 소스 내용이나 컴파일러 버전에 따라 달라질 수 있다).

     0: new           #7     // class Parcel
 3: dup
 4: ldc           #9     // String 김자바
 6: sipush        2500
 9: invokespecial #11    // Method Parcel."":(Ljava/lang/String;I)V
12: astore_1
13: aload_1
14: invokevirtual #14    // Method Parcel.printLabel:()V
17: return

    JVM은 스택 기반 기계다. 명령은 값을 피연산자 스택(operand stack)에 올리고, 다음 명령이 그 값을 꺼내 쓴다. 0번부터 12번까지가 Parcel p = new Parcel("김자바", 2500); 한 줄에 해당한다. 명령 하나하나가 스택과 힙을 어떻게 바꾸는지 따라가 보자.

    명령                        피연산자 스택 (왼쪽이 바닥)        힙의 Parcel 인스턴스
──────────────────────────────────────────────────────────────────────────────────
 0: new Parcel              ref                               receiver=null, weightGram=0, fee=0
                                                              (메모리만 잡힌 상태, 초기화 전)
 3: dup                     ref, ref
 4: ldc "김자바"             ref, ref, "김자바"
 6: sipush 2500             ref, ref, "김자바", 2500
 9: invokespecial     ref                               receiver="김자바", weightGram=2500, fee=4000
                                                              (생성자가 끝난 상태)
12: astore_1                (비어 있음)                        지역 변수 1번(p)에 ref 저장
    1. new: JVMS의 new 명령 설명에 따르면, 이 명령은 가비지 컬렉션이 되는 힙에서 그 클래스의 인스턴스를 위한 메모리를 할당하고, 인스턴스 변수들을 기본값으로 초기화한 다음, 그 인스턴스의 참조를 피연산자 스택에 올린다. 클래스가 아직 초기화되지 않았다면 이때 클래스 초기화도 일어난다. 이 시점의 객체는 필드가 전부 기본값이고 생성자는 아직 한 줄도 실행되지 않았다.
    2. dup: 스택 맨 위의 값을 하나 더 복사해 올린다. 같은 참조가 두 개가 된다.
    3. ldc, sipush: 생성자에 넘길 인자인 문자열 참조와 정수 2500을 차례로 올린다.
    4. invokespecial: 생성자를 호출한다. 스택에서 인자 두 개와 그 아래의 참조 하나를 꺼내 새 스택 프레임의 지역 변수 2번, 1번, 0번으로 넘긴다. 0번으로 들어간 참조가 생성자 안의 this다.
    5. astore_1: 스택에 남은 참조를 1번 지역 변수, 곧 p에 저장한다(0번은 main의 매개변수 args다).

    dup이 왜 필요한지가 이 흐름의 요점이다. 생성자는 값을 반환하지 않는다. invokespecial은 대상 객체의 참조를 스택에서 소비해 버리고, 생성자가 끝나도 스택에 아무것도 돌려놓지 않는다. 미리 참조를 하나 더 복사해 두지 않으면 초기화가 끝난 뒤 그 객체를 가리킬 방법이 없어진다. 흔히 "생성자가 객체를 반환한다"고 말하지만, 실제로 new 식의 값이 되는 것은 new 명령이 올리고 dup이 복사해 둔 참조다.

    JVMS는 new 명령의 설명 끝에 이 명령만으로는 인스턴스 생성이 완전히 끝나지 않으며, 초기화되지 않은 인스턴스에 대해 인스턴스 초기화 메서드가 호출되어야 생성이 완료된다고 덧붙인다. "객체 생성"이라는 한 단어 뒤에 할당과 초기화라는 두 단계가 있고, 생성자는 두 번째 단계를 맡는다.

    new 명령 직후에는 기본값만 든 객체가 힙에 있고, dup으로 참조가 둘이 되었다가 생성자 호출이 하나를 소비하고 남은 하나가 지역 변수 p에 저장된다는 흐름을 네 장면으로 보여 준다. 가로로 나란히 놓인 네 개의 패널로 구성된 깔끔한 기술 다이어그램. 각 패널 위에 제목 라벨: "1. new", "2. dup", "3. invokespecial (생성자 실행)", "4. astore_1". 각 패널의 왼쪽에는 세로로 쌓이는 상자 모양의 "피연산자 스택", 오른쪽에는 둥근 사각형의 "힙" 영역이 있다. 패널 1: 스택에 "ref" 상자 하나, 힙에는 "Parcel" 객체 상자가 있고 안에 "receiver = null", "weightGram = 0", "fee = 0"이 흐린 회색으로 적혀 있다. ref에서 객체로 화살표. 패널 2: 스택에 "ref" 상자 두 개가 쌓여 있고 둘 다 같은 객체를 가리키는 화살표. 패널 3: 스택에 "ref" 하나만 남고, 힙의 객체 안 값이 "receiver = 김자바", "weightGram = 2500", "fee = 4000"으로 진하게 바뀌어 있다. 패널 4: 스택은 비어 있고, 그 아래 "지역 변수 p" 상자에서 객체로 화살표가 간다. 패널 사이에는 오른쪽 방향 화살표. 흰 배경, 얇은 선, 파랑과 주황 두 가지 강조색, 한국어 라벨은 따옴표 안의 문구 그대로. 할당(new)과 초기화(생성자 호출)는 별개의 명령이다. dup으로 복사해 둔 참조가 new 식의 결괏값이 된다.

    생성자는 클래스 파일에서 메서드가 된다

    위 바이트코드의 9번 줄에서 호출 대상이 Parcel."":(Ljava/lang/String;I)V로 적혀 있었다. 소스 코드의 생성자는 클래스 파일 안에서 이라는 특별한 이름의 메서드로 저장된다. JVMS 2.9.1은 이것을 인스턴스 초기화 메서드(instance initialization method)라고 부르고, 클래스에 정의되어 있고 이름이 이며 반환 타입이 void인 메서드라고 정의한다. 괄호 안의 Ljava/lang/String;I는 매개변수가 String과 int라는 뜻이고, 끝의 V는 void다.

    이 정의에서 세 가지를 읽을 수 있다. 첫째, 은 꺾쇠가 들어 있어 자바 소스에서 쓸 수 있는 식별자가 아니다. 그래서 개발자가 만든 어떤 메서드와도 이름이 겹치지 않고, 소스 코드에서 직접 호출할 수도 없다. 둘째, 반환 타입이 void다. 생성자가 값을 돌려주지 않는다는 앞 절의 설명과 맞는다. 셋째, JVMS는 인스턴스 초기화 메서드를 invokespecial 명령으로만, 그것도 아직 초기화되지 않은 인스턴스에 대해서만 호출할 수 있다고 제한한다. 이미 완성된 객체에 생성자를 다시 실행하는 바이트코드는 허용되지 않는다. init 메서드의 약점이었던 "두 번 부를 수 있다"가 JVM 수준에서 막혀 있는 것이다.

    객체가 초기화되는 순서 (JLS 12.5)

    필드를 선언하면서 값을 주는 초기화식(int count = 1;), 중괄호만으로 이루어진 인스턴스 초기화 블록(instance initializer), 그리고 생성자 본문. 객체의 필드에 값을 넣을 수 있는 자리는 세 군데다. 이들이 어떤 순서로 실행되는지는 JLS 12.5가 정확히 정해 두었다. 새 인스턴스가 만들어질 때마다 다음 일이 순서대로 일어난다.

    세 가지가 눈에 띈다. 필드 초기화식은 "선언과 동시에" 실행되는 것이 아니라 생성자가 호출될 때마다 상위 클래스 생성자 다음, 본문 앞에서 실행된다. 필드 초기화식과 초기화 블록 사이에는 우선순위가 없고 오직 소스에 적힌 순서만 있다. 그리고 this(...)로 다른 생성자에 일을 넘긴 생성자는 필드 초기화 단계를 다시 수행하지 않는다. 초기화식이 두 번 실행되는 일을 막기 위해서다.

    규칙만으로는 감이 오지 않으니 일부러 순서가 드러나게 만든 클래스를 실행해 보자. 평소라면 이렇게 쓰지 않을 코드지만, 한 줄씩 추적하기에 좋다.

    public class Order {
    int count = 1;
    String memo;

    {
        System.out.println("초기화 블록: count=" + count + ", memo=" + memo);
        memo = "없음";
    }

    int total = price() * count;

    Order() {
        this(5);
        System.out.println("Order(): count=" + count);
    }

    Order(int count) {
        System.out.println("Order(int) 시작: count=" + this.count + ", memo=" + memo + ", total=" + total);
        this.count = count;
    }

    int price() {
        System.out.println("price(): total=" + total);
        return 1000;
    }

    public static void main(String[] args) {
        Order o = new Order();
        System.out.println("완성: count=" + o.count + ", memo=" + o.memo + ", total=" + o.total);
    }
}

    new Order() 한 번에 일어난 일을 절차에 맞춰 따라가면 다음과 같다.

    1. 힙에 Order 인스턴스의 메모리가 잡히고 count=0, memo=null, total=0으로 채워진다.
    2. 인자 없는 Order()가 선택된다. 이 생성자는 this(5)로 시작하므로 먼저 Order(int)를 처리한다. 매개변수 count에 5가 들어간다.
    3. Order(int)는 this(...)로 시작하지 않는다. 따라서 암묵적인 super(), 곧 Object의 생성자가 먼저 실행된다.
    4. 이어서 Order의 초기화식과 초기화 블록이 소스 순서대로 실행된다. count = 1이 먼저다. 다음으로 초기화 블록이 실행되어 count=1, memo=null을 출력하고 memo에 "없음"을 넣는다. 마지막으로 total = price() * count가 실행된다. price()가 호출된 시점에는 total의 초기화식이 아직 끝나지 않았으므로 total=0이 출력된다. price()가 1000을 돌려주고 count는 1이므로 total은 1000이 된다.
    5. Order(int) 본문의 나머지가 실행된다. 필드는 이미 count=1, memo=없음, total=1000이다. 그다음에야 this.count = count로 count가 5가 된다.
    6. Order()로 돌아와 this(5) 다음 문장이 실행되어 count=5를 출력한다. 초기화식은 다시 실행되지 않는다.

    최종 결과에서 count는 5인데 total은 5000이 아니라 1000이다. total의 초기화식은 생성자 본문보다 먼저, count가 아직 1일 때 한 번 계산되고 끝났기 때문이다. 필드 초기화식은 다른 필드가 나중에 바뀌어도 다시 계산되지 않는다. 생성자 인자에 따라 달라지는 값은 초기화식이 아니라 생성자 본문에서 계산해야 한다.

    컴파일러는 이 순서를 어떻게 만드는가

    클래스 파일에는 "필드 초기화식"이나 "초기화 블록"을 위한 별도의 자리가 없다. javap -c -p Order로 확인하면 javac는 초기화식과 초기화 블록의 코드를 소스 순서대로 이어 붙여 상위 클래스 생성자를 호출하는 생성자의 안에, super() 호출 바로 뒤에 넣는다. Order(int)의 은 Object의 호출, count에 1을 쓰는 putfield, 초기화 블록의 코드, price() 호출과 total에 쓰는 putfield, 그리고 본문 순서로 이루어져 있다. 반면 this(5)로 시작하는 Order()의 에는 다른 호출과 본문의 출력문만 있고 초기화식의 코드는 들어 있지 않다. JLS 12.5의 4단계와 5단계는 이렇게 컴파일러가 코드를 배치하는 방식으로 구현된다.

    생성자를 세 개 선언하고 그 셋이 모두 super()로 시작한다면, 초기화식의 코드는 세 에 똑같이 복사된다. 어느 생성자로 들어오든 초기화식이 정확히 한 번 실행되어야 하기 때문이다.

    기본값이 눈에 보이는 순간

    위 예제에서 price(): total=0이라는 출력은 평소에는 가려져 있는 "기본값 단계"가 드러난 것이다. 초기화가 진행 중인 객체의 메서드를 호출하면, 그 메서드는 아직 초기화식이 실행되지 않은 필드에서 기본값을 읽는다. 컴파일러는 이런 실수를 일부만 막아 준다. 초기화식에서 자기보다 아래에 선언된 필드를 단순 이름으로 읽으면 컴파일 오류다(JLS 8.3.3).

    class Sample {
    int a = b + 1;   // 컴파일 오류: illegal forward reference
    int b = 2;
}

    하지만 이 검사는 초기화식에 직접 적힌 단순 이름만 본다. Order 예제처럼 메서드를 거쳐서 읽는 경우는 검사 대상이 아니어서 그대로 컴파일되고, 실행하면 기본값이 보인다. 초기화 도중에 인스턴스 메서드를 부르는 코드가 위험한 이유가 여기에 있다.

    메모리 할당과 기본값 채우기 다음에 생성자가 this()로 시작하는지에 따라 갈라지고, 필드 초기화식과 초기화 블록이 생성자 본문보다 먼저 실행된다는 흐름을 보여 준다. 위에서 아래로 흐르는 세로 순서도. 맨 위 둥근 상자 "new 식 실행". 그 아래 직사각형 "1. 메모리 할당", 이어서 "2. 모든 필드를 기본값으로". 그 아래 직사각형 "3. 인자를 생성자 매개변수에 대입". 그 아래 마름모 "생성자가 this(...)로 시작하는가?". 마름모에서 왼쪽으로 "예" 라벨이 붙은 화살표가 직사각형 "다른 생성자를 같은 절차로 먼저 처리"로 가고, 거기서 아래로 내려가 맨 아래 상자로 합류한다. 마름모에서 아래로 "아니오" 라벨이 붙은 화살표가 직사각형 "4. 상위 클래스 생성자 실행"으로, 이어서 강조색으로 칠한 직사각형 "5. 필드 초기화식과 초기화 블록 (소스 순서대로)"으로 간다. 두 경로가 모두 직사각형 "6. 생성자 본문의 나머지"로 모이고, 맨 아래 둥근 상자 "참조 반환"으로 끝난다. 흰 배경, 얇은 회색 선, 강조색은 파랑 하나. 한국어 라벨은 따옴표 안의 문구 그대로. this(...)로 시작한 생성자는 필드 초기화 단계를 건너뛴다. 위임받은 생성자가 이미 한 번 수행했기 때문이다.

    기본 생성자: 컴파일러가 대신 써 주는 조건

    지금까지 생성자를 하나도 쓰지 않은 클래스도 new Parcel()로 객체를 만들 수 있었다. 생성자 없이 객체가 만들어진 것이 아니다. JLS 8.8.9는 클래스에 생성자 선언이 하나도 없으면 컴파일러가 기본 생성자(default constructor)를 암묵적으로 선언한다고 정한다. 그 형태도 정해져 있다.

    • 매개변수가 없다.
    • 접근 제어자는 클래스의 접근 제어자와 같다. public class이면 public 생성자가 되고, 클래스에 접근 제어자가 없으면 생성자도 접근 제어자가 없는 패키지 접근이 된다.
    • throws 절이 없다.
    • 본문은 상위 클래스의 인자 없는 생성자를 호출하는 것뿐이다. 곧 super(); 한 줄이다.

      10: return
}

    소스에 없던 public Empty()가 클래스 파일에 들어 있다. 본문은 Object의 호출과, 앞 절에서 본 대로 그 뒤에 복사된 필드 초기화식(value = 7)이다. JVM의 관점에서는 "생성자가 없는 클래스의 객체 생성"이라는 것이 따로 없다. new 명령 다음에는 언제나 호출이 따라오고, 기본 생성자는 그 호출 대상이 반드시 존재하도록 컴파일러가 채워 넣는 것이다.

    조건을 다시 읽어 보자. "생성자 선언이 하나도 없으면"이다. 매개변수 있는 생성자를 하나라도 직접 선언하면 기본 생성자는 만들어지지 않는다. 앞에서 Parcel(String, int)를 선언하자 new Parcel()이 컴파일되지 않았던 이유가 이것이다. 이 규칙 덕분에 "값을 받아야만 만들 수 있는 클래스"를 표현할 수 있다. 개발자가 필수 값을 요구하는 생성자를 썼는데 컴파일러가 인자 없는 생성자를 슬쩍 추가해 준다면, 생성자로 세운 보장에 뒷문이 생기는 셈이다.

    이 규칙은 실무에서 생각보다 자주 발에 걸린다. 생성자가 없던 클래스에 매개변수 있는 생성자를 추가하는 순간, 프로젝트 곳곳에 있던 new 클래스이름()이 한꺼번에 컴파일 오류가 된다. 인자 없이 만드는 방법도 계속 남겨 두고 싶다면 인자 없는 생성자를 직접 써 줘야 한다.

    용어를 구분해 두면 문서를 읽을 때 덜 헷갈린다. 기본 생성자(default constructor)는 JLS의 용어로, 컴파일러가 암묵적으로 선언한 생성자만을 가리킨다. 개발자가 직접 쓴 매개변수 없는 생성자는 인자 없는 생성자(no-arg constructor)다. 한국어에서는 둘 다 "기본 생성자"라고 부르는 일이 흔하므로, 문맥을 보고 어느 쪽인지 판단해야 한다.

    생성자 오버로딩과 this()

    택배의 무게를 재지 않고 접수하는 경우에는 1000g으로 간주한다고 하자. 받는 사람만 받는 생성자를 하나 더 두면 된다. 메서드와 마찬가지로 생성자도 매개변수 목록이 다르면 여러 개 선언할 수 있다. 이것이 생성자 오버로딩(overloading)이다. 처음에는 이렇게 쓰게 된다.

    Parcel(String receiver) {
    this.receiver = receiver;
    this.weightGram = 1000;
    this.fee = 3000 + (1000 / 1000) * 500;
}

Parcel(String receiver, int weightGram) {
    this.receiver = receiver;
    this.weightGram = weightGram;
    this.fee = 3000 + (weightGram / 1000) * 500;
}

    동작은 하지만 요금 계산식이 두 군데에 있다. 요금 체계가 바뀌면 두 곳을 모두 고쳐야 하고, 한쪽만 고치면 어떤 생성자로 만들었느냐에 따라 요금이 달라지는 객체가 생긴다. 초기화 로직을 한 곳에만 두려면 한 생성자가 다른 생성자에게 일을 넘길 수 있어야 한다. 그 문법이 this(...)다.

    public class Parcel {
    String receiver;
    int weightGram;
    int fee;

    Parcel(String receiver) {
        this(receiver, 1000);
    }

    Parcel(String receiver, int weightGram) {
        if (weightGram <= 0) {
            throw new IllegalArgumentException("무게는 0보다 커야 한다: " + weightGram);
        }
        this.receiver = receiver;
        this.weightGram = weightGram;
        this.fee = 3000 + (weightGram / 1000) * 500;
    }

    void printLabel() {
        System.out.println(receiver + " / " + weightGram + "g / " + fee + "원");
    }

    public static void main(String[] args) {
        Parcel a = new Parcel("김자바", 2500);
        Parcel b = new Parcel("이스프링");
        a.printLabel();
        b.printLabel();
    }
}
    김자바 / 2500g / 4000원
이스프링 / 1000g / 3500원

    검증과 요금 계산은 인자 두 개짜리 생성자 한 곳에만 있고, 다른 생성자는 빠진 인자를 채워 그쪽으로 넘긴다. 필드를 실제로 채우는 생성자를 하나로 모으고 나머지는 그 생성자를 호출하게 만드는 구조다.

    어느 생성자가 호출될지는 실행 중에 정해지지 않는다. JLS 8.8.8은 생성자 오버로딩이 메서드 오버로딩과 같은 방식으로 컴파일 타임에, new 식마다 결정된다고 적는다. 컴파일러는 인자의 타입을 보고 생성자 하나를 골라 그 시그니처를 클래스 파일에 기록한다. new Parcel("이스프링")은 Parcel."":(Ljava/lang/String;)V 호출로, new Parcel("김자바", 2500)은 Parcel."":(Ljava/lang/String;I)V 호출로 컴파일된다. JVM이 보기에 둘은 이름만 같고 서술자가 다른 별개의 메서드다.

    this(receiver, 1000)의 바이트코드도 지금까지 본 것과 다르지 않다.

    Parcel(java.lang.String);
  Code:
     0: aload_0
     1: aload_1
     2: sipush        1000
     5: invokespecial #1     // Method "":(Ljava/lang/String;I)V
     8: return

    this(0번 지역 변수)와 인자 두 개를 올리고 같은 클래스의 다른 을 invokespecial로 호출한다. Object의 호출은 없다. 상위 클래스 생성자 호출은 위임받은 쪽이 하기 때문이다. 이 생성자에는 new 명령도 없다는 점도 확인해 두자. this(...)는 객체를 새로 만들지 않고, 지금 초기화 중인 같은 객체를 다른 생성자에게 넘겨 초기화를 이어 가게 한다.

    this()의 규칙

    Java 21을 기준으로 this(...)에는 다음 제약이 있다(JLS 8.8.7, 8.8.7.1).

    • 생성자 본문의 첫 문장이어야 한다. 다른 문장 뒤에 쓰면 call to this must be first statement in constructor 오류가 난다. 첫 문장 자리는 하나뿐이므로 한 생성자에서 this(...)를 두 번 쓸 수 없고, this(...)와 super(...)를 함께 쓸 수도 없다.
    • 생성자 본문에서만 쓸 수 있다. 일반 메서드에서는 다른 생성자를 호출할 방법이 없다.
    • 돌고 도는 호출은 금지다. A()가 this(1)을, A(int)가 this()를 부르면 recursive constructor invocation 컴파일 오류가 난다. JLS 8.8.7은 생성자가 this를 통한 호출을 거쳐 직접이든 간접이든 자기 자신을 호출하는 것을 컴파일 오류로 규정한다.
    • 인자에서 지금 만들고 있는 객체를 참조할 수 없다. this(...) 문장은 정적 문맥(static context)으로 취급되어, 그 안에서는 this와 인스턴스 필드, 인스턴스 메서드를 쓸 수 없다. 예를 들어 필드 base를 인자로 넘기는 this(base)는 cannot reference base before supertype constructor has been called 오류가 난다. 매개변수, 리터럴, static 멤버는 쓸 수 있다.

    마지막 제약은 초기화 순서를 떠올리면 자연스럽다. this(...)의 인자를 계산하는 시점에는 상위 클래스 생성자도, 필드 초기화식도 아직 실행되지 않았다. 그때 인스턴스 필드를 읽으면 기본값만 보일 것이고, 인스턴스 메서드를 호출하면 초기화가 전혀 되지 않은 객체 위에서 코드가 돌게 된다. 언어는 이 가능성을 문법 단계에서 차단한다.

    "첫 문장이어야 한다"는 제약은 버전에 따라 다르다. JDK 25에서 확정된 JEP 513(Flexible Constructor Bodies)은 this(...)나 super(...) 앞에 문장을 둘 수 있게 했다. 다만 그 앞부분의 문장은 만들고 있는 객체를 참조할 수 없다는 조건이 붙는다(같은 클래스에 선언되고 초기화식이 없는 필드에 값을 대입하는 것은 허용된다). 이 강좌의 기준인 Java 21에서는 첫 문장이어야 한다.
    new는 한 번만 일어나고, 인자 하나짜리 생성자가 인자 둘짜리 생성자에게, 그 생성자가 Object 생성자에게 같은 객체를 넘기며 초기화가 안쪽에서 바깥쪽 순서로 끝난다는 것을 보여 준다. 시퀀스 다이어그램. 위쪽에 가로로 네 개의 참여자 상자: "main", "Parcel(String)", "Parcel(String, int)", "Object()". 각 상자에서 아래로 세로 점선 생명선. 오른쪽 끝에는 별도로 "힙의 객체 x002" 라고 적힌 객체 상자가 있고 안에 "receiver", "weightGram", "fee" 세 칸. 메시지 화살표를 위에서 아래 순서로: main에서 Parcel(String)으로 실선 화살표 "① 생성자 호출 (this = x002)"; Parcel(String)에서 Parcel(String, int)로 실선 화살표 "② this(receiver, 1000)"; Parcel(String, int)에서 Object()로 실선 화살표 "③ super()"; Object()에서 Parcel(String, int)로 점선 반환 화살표; Parcel(String, int) 생명선 위의 활성 막대 옆에 메모 "④ 검증 후 필드 세 개 대입"과 객체 상자로 향하는 화살표; Parcel(String, int)에서 Parcel(String)으로 점선 반환 화살표; Parcel(String)에서 main으로 점선 반환 화살표 "⑤ 초기화 완료". 흰 배경, 얇은 선, 강조색 파랑. 한국어 라벨은 따옴표 안의 문구 그대로. this(...)는 객체를 새로 만들지 않는다. 생성자 세 개가 모두 같은 객체를 this로 받는다.

    초기화가 끝나지 않은 객체를 JVM이 다루는 방식

    지금까지의 규칙은 대부분 컴파일러가 검사한다. 그런데 클래스 파일은 javac만 만드는 것이 아니다. 누군가 new 명령 뒤에 호출을 빼먹은 바이트코드를 직접 만들어 JVM에 넣는다면 초기화되지 않은 객체가 돌아다닐 수 있을까. JVM은 이것을 클래스를 연결(link)하는 과정의 검증(verification) 단계에서 막는다.

    JVMS 4.10.2.4에 따르면 검증기는 new 명령이 스택에 올린 참조를 일반 객체 타입이 아니라 "초기화되지 않은 객체"를 뜻하는 특별한 타입으로 추적한다. 그 참조에 대해 알맞은 이 호출된 다음에야 검증기의 모델에서 그 타입이 보통의 클래스 타입으로 바뀐다. 명세는 검증기가 초기화 전에 새 객체를 사용하는 코드와 객체를 두 번 초기화하는 코드를 거부한다고 적는다. 생성자 안에서도 마찬가지다. 의 0번 지역 변수는 처음에 초기화되지 않은 객체 타입으로 시작하고, 같은 클래스나 직속 상위 클래스의 을 호출한 뒤에야 온전한 this가 된다. 그 전에 할 수 있는 일은 자기 클래스에 선언된 필드에 값을 대입하는 것뿐이다.

    정리하면 "new 다음에는 반드시 생성자가 실행되고, 생성자는 반드시 상위 클래스 생성자를 거친다"는 규칙은 컴파일러가 한 번, JVM이 클래스를 받아들일 때 또 한 번 확인한다. 자바 소스에서 this(...)와 super(...)의 위치를 엄격하게 제한하는 것은 이 JVM 규칙을 언어 쪽에서 표현한 것이기도 하다.

    생성자가 예외로 끝나면

    위 Parcel의 생성자는 무게가 0 이하면 예외를 던진다. 이때 객체는 어떻게 될까.

    Parcel c = null;
try {
    c = new Parcel("박제이", 0);
} catch (IllegalArgumentException e) {
    System.out.println("생성 실패: " + e.getMessage());
}
System.out.println(c);
    생성 실패: 무게는 0보다 커야 한다: 0
null

    힙에는 이미 메모리가 잡혔고 필드는 기본값으로 채워졌다. 하지만 JLS 12.5는 생성자가 예외로 끝나면 초기화 절차 전체가 같은 이유로 갑자기 끝난다(completes abruptly)고 정하고, 그러면 new 식도 값을 내지 못하고 예외를 전파한다. 바이트코드로 보면 invokespecial이 정상적으로 돌아오지 않았으므로 그다음의 astore가 실행되지 않는다. 대입이 일어나지 않아서 c는 null 그대로다. 잡혀 있던 메모리는 어떤 변수도 가리키지 않으므로 프로그램에서 닿을 수 없는 객체가 되고, 가비지 컬렉터가 회수할 수 있다.

    이것이 생성자에서 인자를 검증하는 방식이 효과적인 이유다. 유효하지 않은 값으로는 객체가 "실패한 상태로 만들어지는" 것이 아니라 아예 호출자의 손에 들어오지 않는다. 불변식을 지키지 못하는 객체는 존재하지 않게 만드는 것이다.

    단, 한 가지 구멍이 있다. 생성자가 끝나기 전에 this를 바깥에 넘기는 경우다. 생성자 안에서 자기 자신을 static 필드나 다른 객체의 리스트에 등록하면, 그 뒤에 예외가 나거나 아직 대입하지 않은 필드가 남아 있어도 다른 코드가 그 참조를 통해 반쯤 초기화된 객체에 닿을 수 있다. 이를 this 유출(this escape)이라고 부른다. 생성자 안에서는 필드를 채우는 일만 하고, 자신을 바깥에 알리는 일은 생성이 끝난 뒤로 미루는 것이 안전하다.

    흔한 오해와 함정

    void를 붙이면 생성자가 아니다

    생성자에 실수로 반환 타입을 적으면 컴파일 오류가 날 것 같지만 그렇지 않다. 클래스 이름과 같은 이름의 메서드가 될 뿐이다.

    class Counter {
    int count;

    void Counter(int count) {     // 생성자가 아니라 메서드
        this.count = count;
    }

    public static void main(String[] args) {
        Counter c = new Counter();    // 기본 생성자가 호출된다
        System.out.println(c.count);  // 0
        c.Counter(3);                 // 메서드이므로 이렇게 호출할 수 있다
        System.out.println(c.count);  // 3
    }
}

    이 클래스에는 생성자 선언이 없으므로 컴파일러가 기본 생성자를 만들고, new Counter()가 컴파일된다. 반대로 new Counter(3)은 그런 생성자가 없어서 컴파일 오류다. "생성자를 만들었는데 값이 들어가지 않는다"는 증상을 만나면 선언에 반환 타입이 붙어 있지 않은지부터 본다.

    생성자가 객체를 만든다는 말

    일상적으로는 "생성자로 객체를 만든다"고 말하고, 그렇게 말해도 의사소통에는 문제가 없다. 하지만 동작을 추론할 때는 구분이 필요하다. 메모리를 잡고 기본값으로 채우는 일은 생성자가 실행되기 전에 끝난다. 생성자의 첫 줄이 실행되는 시점에 객체는 이미 존재하고 this로 가리킬 수 있다. 생성자는 그 객체의 필드를 의미 있는 값으로 바꾸는 초기화 코드다. 이 구분이 있어야 "생성자 안에서 필드를 읽었더니 0이 나왔다" 같은 현상을 설명할 수 있다.

    생성자 안에서 부르는 인스턴스 메서드

    Order 예제의 price()는 초기화가 덜 된 객체 위에서 실행되어 total=0을 보았다. 생성자나 초기화식에서 인스턴스 메서드를 호출하면 그 메서드는 "모든 필드가 채워져 있다"는 가정 없이 실행된다는 점을 기억해야 한다. 상속이 끼면 문제가 더 커진다. JLS 12.5는 자바가 객체 생성 중이라고 해서 메서드 호출 규칙을 바꾸지 않으며, 하위 클래스가 오버라이딩한 메서드가 있으면 객체가 완전히 초기화되기 전이라도 그 메서드가 실행된다고 명시한다. 상위 클래스 생성자가 호출한 메서드가 아직 초기화되지 않은 하위 클래스의 필드를 읽게 되는 것이다. 이 함정은 상속과 오버라이딩을 배운 뒤 8회에서 다시 살핀다.

    this(...)와 this.의 혼동

    this.receiver의 this는 값이다. 0번 지역 변수에 든 참조를 읽는 식이고, 인스턴스 메서드와 생성자 어디서든 쓸 수 있다. this(...)는 문장이다. 같은 클래스의 다른 생성자를 호출하는 명시적 생성자 호출(explicit constructor invocation)이고, 생성자 본문의 정해진 자리에서만 쓸 수 있다. 키워드가 같을 뿐 문법 범주가 다르다. 같은 관계가 super.method()와 super(...) 사이에도 있다.

    다른 주제와의 연결

    이 회차의 내용은 뒤에서 여러 번 다시 쓰인다. 7회에서 배울 final 필드는 한 번만 값을 넣을 수 있는 필드인데, 초기화식으로 값을 주지 않았다면 어느 생성자로 만들든 그 생성자가 끝나는 시점까지 정확히 한 번 대입되어 있어야 한다. 컴파일러가 "모든 생성자 경로에서 대입되었는가"를 검사할 수 있는 것은 객체가 반드시 생성자를 거쳐서만 완성되기 때문이다. 생성자에서 모든 필드를 채우고 이후에는 바꾸지 않는 객체가 불변 객체이고, 이는 중급 1편에서 다룬다.

    상속에서는 super(...)가 주제가 된다. 이 회차에서 본 "생성자 본문은 다른 생성자 호출로 시작하고, 쓰지 않으면 super()가 들어간다"는 규칙이 상위 클래스에 인자 없는 생성자가 없을 때 어떤 컴파일 오류를 만드는지, 부모와 자식의 필드가 어떤 순서로 초기화되는지가 8회의 내용이다. JLS 12.5의 절차는 그때도 그대로 적용된다.

    스프링 프레임워크의 의존관계 주입 가운데 생성자 주입은 이 회차의 원리를 그대로 이용한다. 스프링 레퍼런스 문서는 생성자 주입을 권하는 이유로 컴포넌트를 불변 객체로 만들 수 있고, 필수 의존관계가 null이 아님을 보장하며, 생성자로 주입받은 컴포넌트는 언제나 완전히 초기화된 상태로 호출 코드에 전달된다는 점을 든다. 필수 값을 생성자 매개변수로 강제하면 초기화 누락이 불가능해진다는, 이 회차 첫머리의 논리와 같다.

    JPA에서는 기본 생성자 규칙이 직접 문제가 된다. Jakarta Persistence 명세는 엔티티 클래스가 인자 없는 생성자를 반드시 가져야 하고 그 생성자는 public 또는 protected여야 한다고 요구한다. 엔티티에 필수 값을 받는 생성자를 추가하면 컴파일러가 만들어 주던 기본 생성자가 사라지므로, 인자 없는 생성자를 직접 선언해 줘야 한다. "생성자를 하나라도 선언하면 기본 생성자는 없다"는 JLS 8.8.9의 규칙을 알고 있으면 이때 왜 오류가 나는지 바로 이해할 수 있다.
    생성자의 역할
    객체를 만드는 일과 유효한 상태로 채우는 일을 호출하는 쪽에서 분리할 수 없게 묶는다. 초기화 누락을 런타임 버그에서 컴파일 오류로 바꾼다.
    this
    인스턴스 메서드와 생성자의 스택 프레임에서 0번 지역 변수에 든 대상 객체의 참조다. 매개변수가 같은 이름의 필드를 가릴 때 this.필드로 필드를 가리킨다.
    new 식의 실행
    new(할당과 기본값) → dup(참조 복사) → 인자 적재 → invokespecial(생성자 호출) 순서다. 생성자는 값을 반환하지 않고, dup으로 남겨 둔 참조가 식의 값이 된다.
    메서드
    생성자가 클래스 파일에 저장되는 형태. 반환 타입은 void이고 초기화되지 않은 인스턴스에 대해 invokespecial로만 호출된다.
    초기화 순서 (JLS 12.5)
    메모리 할당 → 기본값 → 인자 대입 → this(...) 또는 super(...) → 필드 초기화식과 초기화 블록(소스 순서) → 생성자 본문의 나머지.
    기본 생성자
    생성자 선언이 하나도 없을 때만 컴파일러가 만든다. 매개변수가 없고, 접근 제어자는 클래스와 같으며, 본문은 super()뿐이다.
    this(...)
    같은 클래스의 다른 생성자에 초기화를 위임한다. Java 21에서는 첫 문장이어야 하고, 순환 호출과 인자에서의 인스턴스 멤버 참조가 금지된다.
    생성자의 예외
    생성자가 예외로 끝나면 new 식은 참조를 내놓지 않는다. 유효하지 않은 객체는 호출자에게 전달되지 않는다.

    실무에서 생성자를 설계할 때 먼저 물어야 할 것은 "이 객체가 의미를 가지려면 최소한 무엇이 있어야 하는가"다. 그 값들은 생성자 매개변수로 받고, 받자마자 검증한다. 이렇게 하면 이후의 모든 메서드는 "필수 값은 이미 있고 유효하다"는 전제 위에서 작성할 수 있어 null 검사와 방어 코드가 줄어든다. 반대로 인자 없는 생성자와 설정 메서드 조합으로 객체를 채우는 방식은 호출 순서와 누락을 사람이 관리해야 하므로, 프레임워크가 요구하는 경우(예: JPA 엔티티의 인자 없는 생성자)가 아니면 필수 값에 대해서는 피하는 편이 낫다.

    판단이 달라지는 조건도 있다. 매개변수가 많아지고 그중 다수가 선택 값이면 생성자 오버로딩의 조합이 급격히 늘고, 같은 타입의 인자가 나란히 있으면 순서를 바꿔 넣는 실수를 컴파일러가 잡지 못한다. 이때는 필드를 실제로 채우는 생성자 하나를 두고 나머지는 this(...)로 위임하는 구조를 유지하되, 이름 있는 정적 메서드나 빌더로 생성 경로를 감싸는 선택을 검토한다. 어느 쪽이든 "검증과 대입은 한 곳에서만"이라는 원칙은 같다.

    장애 분석에서는 초기화 순서 지식이 직접 쓰인다. 필드가 분명히 초기화식을 갖고 있는데 0이나 null로 관찰된다면, 그 필드를 읽은 코드가 초기화식보다 먼저 실행되었을 가능성을 먼저 의심한다. 전형적인 경로는 생성자나 초기화식에서 호출한 인스턴스 메서드, 그리고 생성자 안에서 다른 객체에 넘겨 버린 this다. 스택 트레이스에 이 보이면 그 프레임은 생성자이고, 그 프레임에서 호출되어 실행된 코드(스택 트레이스에서는 그보다 위쪽 줄)는 아직 완성되지 않은 객체를 다루고 있을 수 있다는 뜻이다.

Parcel(String)는 this(...) 뒤에 문장이 없으므로 값이 그대로다. new 명령은 main에서 한 번만 실행된다. this(...)와 super()는 invokespecial로 같은 객체의 을 부를 뿐 새 객체를 할당하지 않는다.

    4. 생성자의 스택 프레임에서 0번 지역 변수는 this, 1번은 매개변수 name이다. 매개변수가 필드를 가리므로 name = name의 양쪽 name은 모두 1번 지역 변수다. 1번의 값을 읽어 1번에 다시 쓰는 것이어서 힙의 객체에는 아무 변화가 없고, 필드 name은 기본값 null로 남는다. this.name = name;으로 고치면 0번 지역 변수가 가리키는 객체의 필드에 1번의 값을 쓰게 된다.

     new Parcel("김자바", 2500)의 바이트코드에서 new 명령 바로 뒤에 dup이 오는 이유는 무엇인가? 생성자가 실패할 경우에 대비해 객체의 복사본을 힙에 하나 더 만들어 두기 위해서 생성자 호출이 스택의 참조를 소비하고 아무 값도 돌려주지 않으므로, 식의 결과로 쓸 참조를 하나 더 남겨 두기 위해서 생성자가 반환한 참조와 new가 만든 참조가 같은지 비교하기 위해서 인자 두 개를 넘기려면 참조도 두 개가 필요하기 때문에 은 반환 타입이 void이고, invokespecial은 대상 객체의 참조를 스택에서 꺼내 써 버린다. dup으로 복사해 둔 참조가 남아 변수에 저장된다. dup은 스택 위의 참조값을 복사할 뿐 힙의 객체를 복사하지 않으며, 생성자는 참조를 반환하지 않으므로 비교할 것도 없다. 인자의 개수와 dup은 관계가 없다. 본문의 Order 예제에서 new Order()로 만든 객체의 count는 5인데 total(int total = price() * count;)은 1000이다. 이유로 옳은 것은? this(5)로 위임받은 생성자는 필드 초기화식을 실행하지 않기 때문에 price()가 호출될 때 count가 기본값 0이어서 계산이 틀어졌기 때문에 필드 초기화식은 생성자 본문보다 먼저 한 번만 실행되고, 그 시점의 count는 초기화식이 넣은 1이었기 때문에 필드 초기화식은 클래스가 로딩될 때 한 번만 계산되어 모든 객체가 공유하기 때문에 JLS 12.5에서 필드 초기화식과 초기화 블록은 상위 클래스 생성자 다음, 생성자 본문의 나머지보다 앞에서 실행된다. this.count = count는 그 뒤에 실행되므로 total에 반영되지 않는다. 필드 초기화를 건너뛰는 쪽은 this(...)로 시작한 생성자이지 위임받은 생성자가 아니다. count = 1이 total 초기화식보다 위에 있으므로 그 시점의 count는 0이 아니라 1이다. 인스턴스 변수의 초기화식은 객체마다 실행된다. 생성자가 없던 public class Config에 Config(String path) 생성자를 추가했더니 다른 파일의 new Config()가 컴파일되지 않게 되었다. 가장 정확한 설명은? 생성자 선언이 생겼으므로 컴파일러가 기본 생성자를 암묵적으로 선언하지 않게 되었다 오버로딩된 생성자 가운데 어느 것을 부를지 컴파일러가 결정하지 못하게 되었다 기본 생성자는 여전히 있지만 접근 제어자가 private으로 바뀌었다 기본 생성자는 실행 중에 JVM이 만들어 주는데, 생성자를 선언하면 그 기능이 꺼진다 JLS 8.8.9는 클래스에 생성자 선언이 하나도 없을 때만 기본 생성자를 암묵적으로 선언한다. 생성자를 추가하면 인자 없는 생성자는 존재하지 않게 된다. 호출 가능한 후보가 여럿이라 모호한 것이 아니라 인자 없는 후보가 아예 없는 것이다. 기본 생성자의 접근 제어자는 클래스의 접근 제어자를 따르며, 기본 생성자는 컴파일러가 클래스 파일에 으로 넣는 것이지 실행 중에 JVM이 만드는 것이 아니다. this(...)의 인자에서 인스턴스 필드나 인스턴스 메서드를 쓸 수 없게 한 규칙과 가장 관련이 깊은 사실은? this(...)가 실행되면 새 객체가 하나 더 만들어지므로 어느 객체의 필드인지 모호해진다 생성자 안에서는 원래 this를 쓸 수 없다 인스턴스 필드는 클래스가 초기화될 때 값이 정해지므로 생성자에서 읽을 필요가 없다 인자를 계산하는 시점에는 상위 클래스 생성자와 필드 초기화식이 아직 실행되지 않아, 객체가 초기화 전 상태다 JLS 12.5의 순서에서 this(...)의 인자 계산은 상위 클래스 생성자 호출과 필드 초기화보다 앞선다. 그 시점의 객체는 기본값만 들어 있으므로 언어는 그 문장을 정적 문맥으로 취급해 인스턴스 멤버 참조를 금지한다. this(...)는 객체를 새로 만들지 않고 같은 객체의 초기화를 다른 생성자에 위임한다. 생성자 본문에서는 this를 쓸 수 있고, 인스턴스 필드는 객체마다 생성 시점에 초기화된다.
    생성자(constructor)
    클래스 인스턴스를 만들 때 실행되어 객체를 초기화하는 선언. 이름이 클래스의 단순 이름과 같고 반환 타입이 없다. 클래스의 멤버가 아니며 상속되지 않는다.
    불변식(invariant)
    객체가 살아 있는 동안 항상 참이어야 하는 조건. 생성자는 불변식이 성립하는 상태로 객체를 내보낼 책임을 진다.
    가리기(shadowing)
    매개변수나 지역 변수의 선언이 그 유효 범위 안에서 같은 이름의 필드를 단순 이름으로 가리킬 수 없게 만드는 것(JLS 6.4.1).
    인스턴스 초기화 메서드()
    생성자가 클래스 파일에서 갖는 형태. 이름이 이고 void이며 invokespecial로만 호출된다(JVMS 2.9.1).
    인스턴스 초기화 블록(instance initializer)
    클래스 본문에 중괄호만으로 쓴 블록. 인스턴스가 만들어질 때 필드 초기화식과 함께 소스 순서대로 실행된다.
    기본 생성자(default constructor)
    클래스에 생성자 선언이 하나도 없을 때 컴파일러가 암묵적으로 선언하는, 매개변수 없이 super()만 호출하는 생성자.
    인자 없는 생성자(no-arg constructor)
    매개변수가 없는 생성자. 기본 생성자와 개발자가 직접 선언한 것을 모두 포함하는 말이다.
    명시적 생성자 호출(explicit constructor invocation)
    생성자 본문에서 this(...)나 super(...)로 다른 생성자를 호출하는 문장.
    invokespecial
    인스턴스 초기화 메서드, 상위 클래스 메서드 등을 호출하는 JVM 명령. 생성자 호출은 항상 이 명령으로 컴파일된다.
