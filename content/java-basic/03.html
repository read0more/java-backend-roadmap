    코드를 무엇을 중심으로 묶을 것인가

    01회의 Book 클래스에는 데이터만 있었다. 02회에서 책을 만들고 할인하고 출력하는 코드는 createBook, discount, printBook이라는 static 메서드가 되어 BookFactoryMain이라는 다른 클래스에 놓였다. 데이터의 정의는 여기에, 그 데이터를 다루는 코드는 저기에 있는 셈이다. 이번 회차의 질문은 이것이다. 데이터와 그것을 다루는 코드를 어디에 둘 것인가.

    이 질문에 대한 두 가지 답에 이름이 붙어 있다. 절차 지향 프로그래밍(procedural programming)은 프로그램을 "무엇을 어떤 순서로 처리하는가"를 중심으로 조직한다. 데이터는 데이터대로 있고, 절차(함수)가 그 데이터를 넘겨받아 처리한다. 객체 지향 프로그래밍(object-oriented programming, OOP)은 데이터와 그 데이터를 다루는 기능을 객체라는 하나의 단위로 묶고, 프로그램을 그런 객체들의 조합으로 조직한다. 오라클의 자바 튜토리얼은 소프트웨어 객체를 "상태와 그에 관련된 동작으로 이루어진 것"으로 설명하고, 객체는 상태를 필드에 저장하고 동작을 메서드로 드러낸다고 적는다.

    두 방식은 서로를 배제하지 않는다. 객체 지향으로 짠 프로그램도 메서드 안에서는 문장이 순서대로 실행되고, 자바로 작성했다고 해서 저절로 객체 지향 프로그램이 되는 것도 아니다. 차이는 문법이 아니라 코드를 묶는 기준에 있다. 이 차이를 말로만 들으면 와닿지 않으므로, 작은 프로그램 하나를 절차 지향으로 시작해 한 단계씩 고쳐 나가며 각 단계에서 무엇이 달라지는지 확인한다.

    절차 지향 1: 변수와 순서대로 나열한 코드

    건물의 물탱크를 다루는 프로그램을 만든다. 탱크에는 이름, 용량, 현재 수위가 있다. 규칙은 두 가지다. 물을 채우면 수위가 올라가되 용량을 넘을 수 없고(넘치는 양은 버려진다), 물을 빼면 수위가 내려가되 0 아래로 내려갈 수 없다. 가장 직접적인 구현은 변수 세 개를 두고 할 일을 순서대로 적는 것이다.

    public class TankMain1 {
    public static void main(String[] args) {
        String name = "옥상 탱크";
        int capacity = 100;
        int level = 0;

        // 60을 채운다
        level = level + 60;
        if (level > capacity) {
            level = capacity;
        }
        System.out.println(name + ": 60 채움 → 수위 " + level);

        // 70을 더 채운다
        level = level + 70;
        if (level > capacity) {
            level = capacity;
        }
        System.out.println(name + ": 70 채움 → 수위 " + level);

        // 30을 뺀다
        level = level - 30;
        if (level < 0) {
            level = 0;
        }
        System.out.println(name + ": 30 배수 → 수위 " + level);

        // 상태를 출력한다
        System.out.println(name + ": 수위 " + level + " / 용량 " + capacity);
    }
}
    옥상 탱크: 60 채움 → 수위 60
옥상 탱크: 70 채움 → 수위 100
옥상 탱크: 30 배수 → 수위 70
옥상 탱크: 수위 70 / 용량 100

    프로그램은 위에서 아래로 읽히고 결과도 맞다. 60을 채우고, 70을 더 채우려 했지만 용량 100에서 멈추고, 30을 빼서 70이 되었다. 그러나 이 코드를 조금만 키우려 하면 문제가 드러난다. 첫째, "용량을 넘으면 용량으로 맞춘다"는 규칙이 채울 때마다 복사되어 있다. 지금은 두 군데지만 채우는 곳이 열 군데가 되면 열 번 복사된다. 규칙이 바뀌면 모든 복사본을 찾아 고쳐야 하고, 하나를 빠뜨리면 그곳만 다르게 동작하는 버그가 된다. 둘째, name, capacity, level이 한 탱크의 것이라는 사실이 코드 어디에도 없다. 탱크가 하나 더 생기면 변수 세 개를 더 만들고 위의 코드를 전부 복사해 변수 이름을 바꿔야 한다. 01회의 책 예제에서 본 문제와 같다. 셋째, 각 덩어리가 무슨 일을 하는지는 주석으로만 알 수 있다. 주석과 코드가 어긋나도 컴파일러는 모른다.

    절차 지향 2: 데이터를 묶는다

    둘째 문제는 01회에서 배운 방법으로 해결한다. 함께 다니는 데이터를 클래스로 묶어 타입으로 만든다.

    public class TankData {
    String name;
    int capacity;
    int level;
}
    public class TankMain2 {
    public static void main(String[] args) {
        TankData tank = new TankData();
        tank.name = "옥상 탱크";
        tank.capacity = 100;

        // 60을 채운다
        tank.level = tank.level + 60;
        if (tank.level > tank.capacity) {
            tank.level = tank.capacity;
        }
        System.out.println(tank.name + ": 60 채움 → 수위 " + tank.level);

        // ... 70 채우기, 30 배수, 상태 출력도 변수 이름 앞에 tank. 만 붙여 같은 방식으로 쓴다
    }
}

    출력은 같다. level에 0을 대입하는 줄이 사라진 것은 필드가 기본값 0으로 초기화되기 때문이다. 달라진 것은 데이터의 구조다. 세 값이 TankData라는 한 타입의 인스턴스 안에 모였으므로, 탱크가 두 개가 되어도 new TankData()를 한 번 더 하면 되고, 탱크 하나를 통째로 변수에 담거나 메서드에 넘길 수 있다. 하지만 첫째와 셋째 문제는 그대로다. 채우는 규칙은 여전히 복사되어 있고, main이 탱크의 내부 사정(수위를 더하고, 용량과 비교하고, 맞추는 일)을 전부 직접 하고 있다.

    절차 지향 3: 메서드를 추출한다

    반복되는 코드 덩어리에 이름을 붙여 메서드로 뽑아낸다. 02회에서 보았듯 참조값을 인자로 넘기면 호출된 메서드가 그 객체를 고칠 수 있으므로, 각 메서드는 다룰 탱크를 매개변수로 받는다.

    public class TankMain3 {
    public static void main(String[] args) {
        TankData tank = new TankData();
        tank.name = "옥상 탱크";
        tank.capacity = 100;

        fill(tank, 60);
        fill(tank, 70);
        drain(tank, 30);
        showStatus(tank);
    }

    static void fill(TankData tank, int amount) {
        tank.level = tank.level + amount;
        if (tank.level > tank.capacity) {
            tank.level = tank.capacity;
        }
        System.out.println(tank.name + ": " + amount + " 채움 → 수위 " + tank.level);
    }

    static void drain(TankData tank, int amount) {
        tank.level = tank.level - amount;
        if (tank.level < 0) {
            tank.level = 0;
        }
        System.out.println(tank.name + ": " + amount + " 배수 → 수위 " + tank.level);
    }

    static void showStatus(TankData tank) {
        System.out.println(tank.name + ": 수위 " + tank.level + " / 용량 " + tank.capacity);
    }
}

    출력은 여전히 같고 코드는 눈에 띄게 좋아졌다. 용량 규칙은 fill 한 곳에만 있어서 고칠 곳이 하나다. main은 주석 없이도 읽힌다. 채우고, 채우고, 빼고, 상태를 본다. 메서드 이름이 주석의 역할을 하고, 이름과 내용이 어긋나면 호출 결과로 드러난다. 여기까지가 잘 짜인 절차 지향 프로그램의 모습이다. 데이터 구조가 하나 있고, 그것을 넘겨받아 처리하는 함수들이 있다. C 언어에서 구조체와 함수로 프로그램을 짜는 방식이 이 형태다.

    그런데 이 구조에는 코드를 아무리 다듬어도 사라지지 않는 성질이 있다. 데이터와 그 데이터를 다루는 기능이 서로 다른 곳에 있다는 것이다. 탱크의 데이터는 TankData에, 탱크의 규칙은 TankMain3의 메서드들에 있다. 이 분리에서 세 가지 불편이 나온다.

    • 변경이 흩어진다. TankData의 필드를 바꾸면(예: 수위의 단위를 바꾸거나 필드 이름을 바꾸면) 그 필드를 만지는 메서드를 프로그램 전체에서 찾아 고쳐야 한다. 그런 메서드가 TankMain3에만 있다는 보장이 없다.
    • 쓰는 사람이 찾아다녀야 한다. TankData라는 타입만 보아서는 이 데이터로 무엇을 할 수 있는지 알 수 없다. 탱크를 채우는 메서드가 어느 클래스에 있는지 따로 알아야 한다.
    • 규칙을 건너뛸 수 있다. fill을 쓰지 않고 누구든 tank.level = tank.level + 60;이라고 직접 쓸 수 있다. 그 코드는 용량 규칙을 지키지 않는다. 규칙이 한 곳에 모였어도 그곳을 거치라고 강제할 방법이 없다.

    세 불편의 뿌리는 같다. "탱크의 수위는 0 이상 용량 이하"라는 규칙은 탱크 데이터에 딸린 것인데, 코드에서는 데이터와 떨어진 곳에 적혀 있다. 그렇다면 규칙을 구현한 메서드를 데이터가 있는 곳으로 옮기면 어떨까.

    절차 지향에서는 데이터 클래스와 그것을 다루는 메서드들이 떨어져 있고 누구나 데이터에 직접 닿을 수 있지만, 객체 지향에서는 데이터와 메서드가 한 상자 안에 있다는 구조 차이를 보여 준다. 깔끔한 기술 교재풍 비교 그림. 화면을 좌우 두 패널로 나눈다. 왼쪽 패널 제목은 "절차 지향", 오른쪽 패널 제목은 "객체 지향". 왼쪽 패널에는 상자 두 개를 떨어뜨려 놓는다. 위쪽 상자의 제목은 "TankData (데이터)"이고 안에 한 줄 "name, capacity, level"이 있다. 아래쪽 상자의 제목은 "TankMain3 (기능)"이고 안에 두 줄 "fill(tank, amount)", "drain(tank, amount)"가 있다. 아래쪽 상자의 각 줄에서 위쪽 상자로 화살표를 그린다. 왼쪽 패널 바깥쪽에서 위쪽 상자로 직접 들어가는 빨간 점선 화살표를 하나 더 그리고 "규칙을 건너뛴 직접 수정"이라고 적는다. 오른쪽 패널에는 큰 상자 하나를 두고 제목을 "WaterTank"라고 적는다. 상자 안은 위아래 두 칸으로 나누어 위 칸에는 "name, capacity, level", 아래 칸에는 두 줄 "fill(amount)", "drain(amount)"를 적는다. 두 칸이 한 테두리 안에 있다는 점이 눈에 띄게 그린다. 흰 배경, 절제된 색, 또렷한 선과 글자. 절차 지향에서는 데이터와 기능이 따로 있고, 객체 지향에서는 한 클래스 안에 함께 있다.

    클래스와 메서드: 기능을 데이터가 있는 곳으로

    자바의 클래스는 필드뿐 아니라 메서드도 멤버로 가질 수 있다. 물탱크를 옮기기 전에, 필드 하나짜리 작은 클래스로 문법과 원리를 먼저 본다. Gauge는 눈금 하나를 가진 계기다. 같은 일을 하는 메서드를 두 가지 방식으로 나란히 넣었다.

    public class Gauge {
    int level;

    static void addStatic(Gauge gauge, int amount) {
        gauge.level = gauge.level + amount;
    }

    void add(int amount) {
        level = level + amount;
    }
}
    public class GaugeMain {
    public static void main(String[] args) {
        Gauge gauge = new Gauge();
        Gauge.addStatic(gauge, 30);
        gauge.add(30);
        System.out.println(gauge.level);
    }
}
    60

    addStatic은 앞 절의 fill과 같은 형태다. 다룰 객체를 매개변수로 받고, 호출할 때 인자로 넘긴다. 달라진 것은 메서드가 놓인 위치뿐이다. add는 새로운 형태다. 선언에 static이 없고, 다룰 객체를 받는 매개변수도 없으며, 본문에서 필드를 gauge.level이 아니라 그냥 level이라고 쓴다. 호출하는 쪽도 달라서, gauge.add(30)처럼 참조 뒤에 점을 찍고 메서드 이름을 쓴다. 필드에 접근할 때 쓰던 점과 같은 점이다.

    static이 붙지 않은 메서드를 인스턴스 메서드(instance method)라고 한다. JLS §8.4.3.2는 인스턴스 메서드를 "언제나 어떤 객체에 대해 호출되는" 메서드로 정의하고, 그 객체가 메서드 본문이 실행되는 동안의 현재 객체가 된다고 설명한다. gauge.add(30)은 "gauge가 가리키는 객체에 대해 add를 호출한다"는 뜻이고, 본문의 level은 바로 그 객체의 level이다. 서로 다른 Gauge 객체 둘에 대해 각각 add를 호출하면 각자의 level이 따로 바뀐다. static 메서드(클래스 메서드)의 정확한 의미는 06회에서 다루므로, 지금은 "특정 객체 없이 호출되는 메서드"라는 정도로만 알아 두자.

    두 메서드의 명령은 한 글자도 다르지 않다. 둘 다 지역 변수 0번에서 참조를 꺼내(aload_0) 그 객체의 level을 읽고(getfield), 지역 변수 1번의 정수를 더해(iload_1, iadd), 다시 그 객체의 level에 쓴다(putfield). addStatic에서 0번이 매개변수 gauge, 1번이 amount인 것은 02회에서 본 규칙 그대로다. 그런데 add에서도 0번에 참조가 들어 있고 amount는 1번으로 밀려나 있다.

    눈여겨볼 곳은 args_size=2다. add의 디스크립터 (I)V는 "int 하나를 받고 반환값이 없다"는 뜻이어서 소스 코드의 선언과 같다. 그런데도 JVM이 이 메서드에 전달하는 인자의 수는 둘이다. 소스에 쓰지 않은 인자가 하나 더 있는 것이다. JVMS §2.6.1이 이 규칙을 정해 두었다. 클래스 메서드를 호출할 때는 매개변수가 지역 변수 0번부터 전달되지만, 인스턴스 메서드를 호출할 때는 "지역 변수 0번이 언제나 그 메서드가 호출된 객체에 대한 참조(자바 언어의 this)를 전달하는 데 쓰이고", 매개변수는 1번부터 이어진다.

    자바 소스에서 이 0번 칸의 값을 가리키는 이름이 this다. JLS §15.8.3은 this를 "인스턴스 메서드가 호출된 대상 객체에 대한 참조"를 나타내는 값이라고 정의한다. 본문에 그냥 level이라고 쓴 것은 this.level을 줄여 쓴 것과 같아서, add의 본문을 this.level = this.level + amount;로 바꿔 컴파일해도 위와 똑같은 바이트코드가 나온다. this라는 키워드를 직접 써야 하는 경우는 04회에서 다룬다. 지금 중요한 것은 this가 특별한 장치가 아니라 컴파일러가 대신 선언해 주는 첫 번째 매개변수라는 사실이다.

    호출하는 쪽: 점 앞의 참조가 인자가 된다

    인자를 넘기는 쪽의 바이트코드도 확인하자. GaugeMain의 두 호출이다.

     8: aload_1
 9: bipush        30
11: invokestatic  #10                 // Method Gauge.addStatic:(LGauge;I)V
14: aload_1
15: bipush        30
17: invokevirtual #14                 // Method Gauge.add:(I)V

    Gauge.addStatic(gauge, 30)과 gauge.add(30)은 호출 직전까지 완전히 같은 일을 한다. 지역 변수 1번(gauge)의 참조를 피연산자 스택에 올리고(aload_1), 정수 30을 올린다(bipush 30). 스택에는 [참조, 30]이 쌓인다. 소스 코드에서 괄호 안에 쓴 gauge와 점 앞에 쓴 gauge가 똑같이 "스택에 올리는 첫 번째 값"이 된 것이다. 다른 것은 마지막 명령뿐이다.

    JVMS는 invokevirtual의 동작을 이렇게 설명한다. 피연산자 스택에서 인자 값들과 객체 참조(objectref)를 꺼내고, 호출될 메서드를 위한 새 프레임을 만든 뒤, "objectref와 인자 값들을 새 프레임의 지역 변수 값으로 차례로 넣되, objectref는 지역 변수 0번에, 첫 번째 인자는 지역 변수 1번에" 넣는다. 그러고 나서 새 프레임을 현재 프레임으로 삼아 메서드의 첫 명령부터 실행한다. JLS §15.12.4.5도 같은 일을 언어 수준에서 서술한다. 새 활성화 프레임에는 대상 참조(target reference)와 인자 값들이 담기고, 대상 참조는 this로 쓸 수 있게 된다.

    gauge.add(30) 실행 중

  스택                                     힙
  +--[ add 프레임 ]----------------+
  | 0: this   = (참조값) ---------------+
  | 1: amount = 30                |     |
  +-------------------------------+     +--->  Gauge 인스턴스 { level = 30 -> 60 }
  +--[ main 프레임 ]---------------+     |
  | 0: args                       |     |
  | 1: gauge  = (참조값) ---------------+
  +-------------------------------+
    인스턴스 메서드 호출에서 점 앞의 참조가 피연산자 스택을 거쳐 호출된 메서드의 지역 변수 0번으로 들어가고, 그것이 this라는 것을 보여 준다. 깔끔한 기술 교재풍 다이어그램. 왼쪽에서 오른쪽으로 세 단계가 화살표로 이어진다. 첫 번째 단계 상자의 제목은 "main의 피연산자 스택"이고 안에 위아래로 쌓인 칸 두 개가 있는데 아래 칸에 "gauge의 참조값", 위 칸에 "30"이라고 적는다. 두 번째 단계는 가운데의 굵은 화살표이며 그 위에 "invokevirtual"이라고 적는다. 세 번째 단계 상자의 제목은 "add()의 새 프레임"이고 안에 가로로 긴 칸 두 개가 위아래로 있는데 위 칸에 "지역 변수 0: this", 아래 칸에 "지역 변수 1: amount = 30"이라고 적는다. 그림 맨 오른쪽에는 둥근 모서리 상자 "Gauge 인스턴스"를 두고 안에 "level"이라고 적으며, "지역 변수 0: this" 칸에서 이 상자로 화살표를 그린다. 그림 아래쪽에 한 줄 "점 앞의 참조가 숨은 첫 번째 인자가 된다"를 적는다. 흰 배경, 절제된 두세 가지 색, 또렷한 선과 글자. gauge.add(30)에서 점 앞의 참조는 인자와 함께 스택에 올라가, 호출된 메서드의 지역 변수 0번(this)이 된다.

    이 그림은 02회에서 addTenTo(counter)를 추적하며 그린 그림과 구조가 같다. 호출한 쪽의 변수와 호출된 쪽의 0번 칸이 같은 객체를 가리키고, 호출된 메서드는 그 참조를 따라가 객체를 고친다. 인스턴스 메서드 호출은 새로운 원리가 아니다. "참조값을 인자로 넘겨 객체를 고치는 메서드"를 언어가 문법으로 지원한 것이다. 넘기는 인자를 괄호 안이 아니라 점 앞에 쓰고, 받는 매개변수를 프로그래머 대신 컴파일러가 선언할 뿐이다.

    숨은 매개변수를 소스에 드러내는 문법도 실제로 있다. void add(Gauge this, int amount)처럼 첫 자리에 this를 적을 수 있고, 이를 수신자 매개변수(receiver parameter)라고 한다. 다만 JLS §8.4는 이것이 타입에 애너테이션을 붙일 자리를 마련하기 위한 표기일 뿐 형식 매개변수가 아니며 실행 시점에 아무 효과도 없다고 못박는다. 실제로 이렇게 선언해도 디스크립터는 (I)V 그대로이고 호출 방법도 달라지지 않는다. 평소에 쓸 일은 없지만, this가 "첫 번째 인자 자리"에 있다는 감각을 확인하기에는 좋은 예다.

    그러면 static 메서드와 무엇이 다른가

    본문의 바이트코드가 같다고 해서 두 메서드가 같은 것은 아니다. 호출 명령이 invokestatic과 invokevirtual로 다르고, 그 차이가 세 가지 결과를 낳는다. 첫째는 null을 만났을 때다. 변수 gauge가 null인 상태에서 두 방식으로 호출해 보면 예외가 나는 위치가 다르다.

    Exception in thread "main" java.lang.NullPointerException: Cannot invoke "Gauge.add(int)" because "" is null
    at NullCallMain.main(NullCallMain.java:4)
    Exception in thread "main" java.lang.NullPointerException: Cannot read field "level" because "" is null
    at Gauge.addStatic(Gauge.java:5)
    at NullStaticMain.main(NullStaticMain.java:4)

    인스턴스 메서드는 호출 자체가 실패한다. 스택 트레이스에 add의 프레임이 없다. JVMS는 invokevirtual에 대해 "objectref가 null이면 NullPointerException을 던진다"고 정하고, JLS §15.12.4.4도 대상 참조가 null이면 "이 시점에" 예외가 던져진다고 적는다. 메서드 본문은 한 줄도 실행되지 않는다. 따라서 인스턴스 메서드 안에서는 this가 null일 수 없다. static 메서드는 다르다. null도 인자로 전달할 수 있는 값이므로 호출은 성공하고, 본문에서 그 참조를 따라가는 getfield에 이르러서야 실패한다. 02회에서 본 "null을 넘긴 곳과 예외가 나는 곳은 다르다"의 사례다.

    둘째는 실행할 메서드를 정하는 방식이다. invokestatic은 명령이 가리키는 바로 그 메서드를 호출한다. 대상 객체가 없으니 고를 것도 없다. invokevirtual은 JVMS의 한 줄 요약이 "인스턴스 메서드를 호출하되 클래스에 따라 디스패치한다"인 명령으로, 대상 객체가 실제로 어느 클래스의 인스턴스인지를 보고 실행할 메서드를 고른다. 지금은 Gauge라는 클래스 하나뿐이어서 차이가 드러나지 않는다. 08회에서 상속을, 09회에서 메서드 오버라이딩과 다형성을 배우면 이 차이가 객체 지향의 핵심 기능이 된다. 01회에서 HotSpot의 모든 객체가 헤더를 통해 자기 클래스를 가리킨다고 한 것이 이때 쓰인다.

    셋째는 소속이다. add는 Gauge라는 타입의 일부다. "Gauge로 무엇을 할 수 있는가"라는 질문의 답이 타입 정의 안에 들어 있고, 호출하는 코드는 대상 객체에서 출발한다. 이 차이는 JVM의 동작이 아니라 코드의 조직에 관한 것이며, 다음 절의 주제다.

    객체 지향 프로그래밍: 물탱크를 객체로

    이제 물탱크로 돌아가 TankMain3의 메서드들을 데이터가 있는 클래스 안으로 옮긴다. 변환은 기계적이다. static을 떼고, 탱크를 받던 매개변수를 지우고(그 자리는 this가 대신한다), 본문의 tank.level을 level로 바꾼다. 데이터만 있다는 뜻의 이름 TankData도 WaterTank로 바꾼다.

    public class WaterTank {
    String name;
    int capacity;
    int level;

    void fill(int amount) {
        level = level + amount;
        if (level > capacity) {
            level = capacity;
        }
        System.out.println(name + ": " + amount + " 채움 → 수위 " + level);
    }

    void drain(int amount) {
        level = level - amount;
        if (level < 0) {
            level = 0;
        }
        System.out.println(name + ": " + amount + " 배수 → 수위 " + level);
    }

    void showStatus() {
        System.out.println(name + ": 수위 " + level + " / 용량 " + capacity);
    }
}
    public class TankMain4 {
    public static void main(String[] args) {
        WaterTank tank = new WaterTank();
        tank.name = "옥상 탱크";
        tank.capacity = 100;

        tank.fill(60);
        tank.fill(70);
        tank.drain(30);
        tank.showStatus();
    }
}
    옥상 탱크: 60 채움 → 수위 60
옥상 탱크: 70 채움 → 수위 100
옥상 탱크: 30 배수 → 수위 70
옥상 탱크: 수위 70 / 용량 100

    출력은 네 단계 내내 같다. 달라진 것은 코드가 놓인 자리다. 탱크의 데이터와 탱크의 규칙이 WaterTank라는 한 클래스에 모였다. main에는 탱크의 내부 사정이 한 줄도 없다. 용량을 넘으면 어떻게 되는지, 수위를 어떤 변수에 담는지 모른 채 "채워라", "빼라", "상태를 보여라"라고 요청할 뿐이다. tank.fill(60)은 "tank 객체에게 60을 채우라고 시킨다"로 읽힌다. 객체는 데이터를 담는 그릇에서, 자기 데이터를 스스로 관리하는 단위가 되었다.

    앞에서 인용한 정의를 다시 보면 이 클래스가 정확히 그 모습이다. 객체는 상태(state)를 필드에 저장하고 동작(behavior)을 메서드로 드러낸다. 그리고 동작의 결과는 상태에 달려 있다. 같은 메서드를 같은 인자로 호출해도 객체가 다르면 결과가 다르다.

    public class TwoTanksMain {
    public static void main(String[] args) {
        WaterTank roof = new WaterTank();
        roof.name = "옥상 탱크";
        roof.capacity = 100;

        WaterTank basement = new WaterTank();
        basement.name = "지하 탱크";
        basement.capacity = 500;

        roof.fill(150);
        basement.fill(150);

        roof.showStatus();
        basement.showStatus();
    }
}
    옥상 탱크: 150 채움 → 수위 100
지하 탱크: 150 채움 → 수위 150
옥상 탱크: 수위 100 / 용량 100
지하 탱크: 수위 150 / 용량 500

    fill(150)이라는 같은 코드가 한 번은 수위 100을, 한 번은 150을 만들었다. 실행된 바이트코드는 같은 fill이고, 다른 것은 지역 변수 0번에 들어온 this다. 첫 호출에서는 this가 용량 100인 객체를 가리켰고 두 번째 호출에서는 용량 500인 객체를 가리켰다. 본문의 capacity와 level은 매번 this를 따라가 읽은 값이다.

    객체 안에서 다른 메서드를 호출할 때

    메서드가 같은 클래스의 다른 메서드를 부르는 경우도 같은 원리로 설명된다. 한 탱크의 물을 다른 탱크로 옮기는 메서드를 WaterTank에 추가한다.

        void pourInto(WaterTank other, int amount) {
        if (amount > level) {
            amount = level;
        }
        drain(amount);
        other.fill(amount);
    }
    public class PourMain {
    public static void main(String[] args) {
        WaterTank roof = new WaterTank();
        roof.name = "옥상 탱크";
        roof.capacity = 100;
        roof.fill(50);

        WaterTank basement = new WaterTank();
        basement.name = "지하 탱크";
        basement.capacity = 500;

        roof.pourInto(basement, 80);

        roof.showStatus();
        basement.showStatus();
    }
}
    옥상 탱크: 50 채움 → 수위 50
옥상 탱크: 50 배수 → 수위 0
지하 탱크: 50 채움 → 수위 50
옥상 탱크: 수위 0 / 용량 100
지하 탱크: 수위 50 / 용량 500

    80을 옮기려 했지만 옥상 탱크에는 50뿐이어서 50만 옮겨졌다. pourInto의 본문에는 두 가지 호출이 있다. drain(amount)에는 점이 없고, other.fill(amount)에는 점 앞에 other가 있다. 바이트코드를 보면 둘의 차이는 스택에 올리는 참조가 무엇이냐뿐이다.

    13: aload_0
14: iload_2
15: invokevirtual #38                 // Method drain:(I)V
18: aload_1
19: iload_2
20: invokevirtual #42                 // Method fill:(I)V

    pourInto는 인스턴스 메서드이므로 프레임의 지역 변수 0번이 this, 1번이 other, 2번이 amount다. 점 없이 쓴 drain(amount)는 aload_0, 곧 this를 대상 참조로 올린다. 컴파일러가 this.drain(amount)로 처리한 것이다. JLS §15.12.4.1도 메서드 이름만 쓴 호출의 대상 참조는 this라고 정한다. other.fill(amount)는 aload_1로 other를 올린다. roof.pourInto(basement, 80)의 실행 중에 drain은 this가 옥상 탱크인 채로, fill은 this가 지하 탱크인 채로 실행된다. 어떤 메서드든 실행되는 동안에는 "지금의 this가 누구인가"가 항상 하나로 정해져 있다.

    메서드의 코드는 클래스에 하나, 인스턴스에는 필드만

    "객체가 데이터와 기능을 함께 가진다"는 말을 듣고 객체마다 메서드가 들어 있다고 상상하기 쉽다. 메모리에서 일어나는 일은 그렇지 않다. JVMS §2.5.4는 메서드 영역(method area)을 클래스별 구조, 곧 런타임 상수 풀, 필드와 메서드의 정보, 그리고 "메서드와 생성자의 코드"를 저장하는 곳으로 정의한다. 메서드의 바이트코드는 클래스마다 한 벌만 있고 모든 인스턴스가 그것을 함께 쓴다. 힙의 인스턴스에 들어 있는 것은 01회에서 본 대로 필드의 값(그리고 HotSpot에서는 헤더)뿐이다.

      메서드 영역: 클래스마다 한 벌            힙: 인스턴스마다 하나

  +--[ WaterTank 클래스 ]----------+       +--[ roof가 가리키는 인스턴스 ]------+
  | fill(int)     의 바이트코드     | <---- | (헤더: 자기 클래스를 가리킨다)      |
  | drain(int)    의 바이트코드     |       | name, capacity = 100, level       |
  | showStatus()  의 바이트코드     |       +-----------------------------------+
  | pourInto(...) 의 바이트코드     |
  +-------------------------------+       +--[ basement가 가리키는 인스턴스 ]--+
                 ^                         | (헤더: 자기 클래스를 가리킨다)      |
                 +------------------------ | name, capacity = 500, level       |
                                           +-----------------------------------+
    인스턴스가 몇 개든 메서드의 바이트코드는 클래스 쪽에 한 벌뿐이고, 인스턴스에는 필드 값만 있으며, 어느 인스턴스에 대해 실행할지는 this로 전달된다는 것을 보여 준다. 깔끔한 기술 교재풍 메모리 구조도. 왼쪽에 큰 상자 하나를 두고 영역 라벨 "메서드 영역"을 붙인다. 상자 제목은 "WaterTank 클래스"이고 안에 세 줄 "fill() 코드", "drain() 코드", "showStatus() 코드"를 적는다. 오른쪽에는 영역 라벨 "힙"을 붙이고 둥근 모서리 상자 두 개를 위아래로 둔다. 위 상자 안에는 "capacity = 100", "level = 100", 아래 상자 안에는 "capacity = 500", "level = 150"이라고 적는다. 두 인스턴스 상자에서 왼쪽 클래스 상자로 각각 얇은 화살표를 그린다. 클래스 상자의 "fill() 코드" 줄에서 오른쪽 두 인스턴스로 향하는 점선 화살표 두 개를 그리고 그 사이에 "this로 대상이 정해진다"라고 적는다. 그림 아래에 한 줄 "코드는 한 벌, 필드는 인스턴스마다"를 적는다. 흰 배경, 메서드 영역은 회색 계열, 힙은 주황 계열, 또렷한 선과 글자. 메서드의 코드는 클래스에 한 벌만 있다. 인스턴스는 필드만 가지며, 호출할 때 this로 "어느 인스턴스인가"가 전달된다.

    이 구조는 관찰로도 확인된다. Temurin 21(HotSpot, 64비트, 기본 옵션)에서 메서드가 없는 TankData와 메서드가 세 개 있는 WaterTank의 인스턴스를 1,000개씩 만들고 jcmd GC.class_histogram으로 보면, 두 클래스 모두 인스턴스 1,000개에 24,000바이트다. 필드 구성이 같으니 인스턴스 크기도 같다. 메서드를 추가해서 커진 것은 클래스 쪽이다. 같은 컴파일러로 만든 클래스 파일의 크기는 TankData.class가 265바이트, WaterTank.class가 1,316바이트였다. 이 수치들은 구현과 버전에 따라 달라지는 값이지만, "메서드는 인스턴스의 크기를 늘리지 않는다"는 구조는 명세가 메서드의 코드를 클래스별 구조로 정의한 데서 나온다.

    이제 숨은 인자 this가 왜 필요한지도 분명해진다. 코드가 한 벌뿐이므로, fill의 바이트코드 자체에는 "어느 탱크를 채울지"가 적혀 있을 수 없다. 그 정보는 호출할 때마다 밖에서 넣어 주어야 하고, 그 통로가 지역 변수 0번이다. 인스턴스 1,000개가 fill 하나를 공유하면서도 각자 자기 수위를 바꿀 수 있는 것은 호출마다 다른 this가 전달되기 때문이다. 메서드 영역이 스택, 힙과 함께 JVM 메모리를 어떻게 이루는지는 06회에서 정리한다.

    캡슐화의 출발점: 좋아진 것과 아직 남은 것

    데이터와 기능을 한 클래스에 모아서 얻은 것을 정리하자. 첫째, 변경의 범위가 좁아졌다. "수위는 0 이상 용량 이하"라는 규칙을 바꾸거나 수위를 저장하는 방식을 바꿀 때 고칠 곳은 WaterTank 안이다. 이렇게 객체가 언제나 지켜야 하는 조건을 불변식(invariant)이라고 하는데, 불변식을 지키는 코드가 그 데이터 바로 옆에 있게 된 것이다. 둘째, 사용하는 쪽이 단순해졌다. main은 메서드 이름과 인자만 알면 되고, 내부가 바뀌어도 메서드의 사용법이 그대로면 main은 고칠 필요가 없다. 셋째, 타입이 스스로를 설명한다. WaterTank의 메서드 목록이 곧 "탱크로 할 수 있는 일"의 목록이다.

    자바 튜토리얼은 데이터 캡슐화(data encapsulation)를 "내부 상태를 숨기고, 모든 상호작용이 객체의 메서드를 통해 이루어지도록 요구하는 것"이라고 정의하고 객체 지향의 기본 원리로 꼽는다. 이 정의에는 두 가지가 들어 있다. 상호작용의 통로가 되는 메서드가 있을 것, 그리고 내부 상태가 숨겨져 있을 것. 지금까지 한 일은 앞의 절반이다. 통로는 만들었지만 그 통로를 거치라고 강제하지는 못한다.

    public class HoleMain {
    public static void main(String[] args) {
        WaterTank tank = new WaterTank();
        tank.name = "옥상 탱크";
        tank.capacity = 100;

        tank.level = 500;                    // fill을 거치지 않고 필드를 직접 고친다
        tank.showStatus();

        WaterTank blank = new WaterTank();   // 이름과 용량을 넣지 않았다
        blank.fill(60);
    }
}
    옥상 탱크: 수위 500 / 용량 100
null: 60 채움 → 수위 0

    두 줄 모두 말이 안 되는 결과인데 컴파일도 실행도 문제없이 된다. 첫 줄은 용량 100인 탱크의 수위가 500이다. 필드에 누구나 직접 접근할 수 있는 한, fill에 넣어 둔 규칙은 "지켜 주면 좋은 권고"일 뿐이다. 둘째 줄은 이름이 null이고 용량이 0인 탱크다. new WaterTank() 직후의 객체는 모든 필드가 기본값이어서, 필요한 값을 넣는 일을 깜빡하면 불완전한 객체가 그대로 쓰인다. 용량이 0이니 60을 채워도 곧바로 0으로 맞춰진다.

    이 두 구멍이 다음 회차들의 주제다. 객체가 만들어지는 순간에 필요한 값을 반드시 받도록 하는 것이 04회의 생성자이고, 필드를 외부에서 직접 만지지 못하게 막는 것이 05회의 접근 제어자다. 둘을 갖춘 뒤에야 "내부 상태를 숨기고 메서드를 통해서만 상호작용한다"는 캡슐화가 완성된다. 이번 회차에서 한 일, 곧 데이터와 그 데이터를 다루는 기능을 한 단위로 묶는 것은 그 출발점이다. 묶여 있지 않은 것은 숨길 수도 없기 때문이다.

    • "객체마다 메서드가 들어 있다." 메서드의 코드는 클래스에 한 벌만 있다. 인스턴스가 가진 것은 필드 값이고, 어느 인스턴스를 다룰지는 호출할 때 this로 전달된다.
    • "인스턴스 메서드는 인자 없이도 자기 필드를 저절로 안다." 저절로 아는 것이 아니다. 점 앞의 참조가 숨은 첫 번째 인자로 전달되고, 본문의 level은 this.level이다.
    • "tank.fill(60)과 fill(tank, 60)은 완전히 같다." 참조가 전달되는 방식은 같지만, 인스턴스 메서드는 호출 시점에 null을 검사하고 대상 객체의 클래스에 따라 실행할 메서드가 정해진다.
    • "메서드를 클래스 안에 넣었으니 캡슐화가 끝났다." 필드에 직접 접근하는 길이 열려 있으면 규칙은 건너뛸 수 있다. 숨기는 일은 접근 제어자의 몫이다.

    이 지식이 다시 쓰이는 곳

    04회의 생성자는 오늘 본 인스턴스 메서드의 특수한 형태다. 01회에서 Book.의 첫 명령이 aload_0이었던 것을 기억하자. 생성자도 지역 변수 0번으로 "초기화할 객체 자신"을 받는다. 04회에서는 매개변수 이름과 필드 이름이 같을 때 둘을 구별하기 위해 this를 직접 쓰게 된다. 06회에서 배울 static 메서드의 제약도 오늘의 그림으로 설명된다. static 메서드에는 this가 전달되지 않으므로, 그 안에서 인스턴스 필드를 이름만으로 쓸 수 없다. 따라갈 참조가 없기 때문이다. JLS §8.4.3.2는 static 메서드 안에서 this와 인스턴스 변수에 대한 한정되지 않은 참조를 금지한다.

    09회의 다형성은 invokevirtual이 대상 객체의 클래스를 보고 메서드를 고른다는 사실 위에 서 있다. 같은 tank.fill(60)이라는 코드가 tank가 실제로 어떤 클래스의 인스턴스냐에 따라 다른 메서드를 실행하게 된다. 이 권을 넘어 스프링으로 가면 프로그램 전체가 서로의 메서드를 호출하는 객체들로 이루어진다. 어떤 객체가 어떤 데이터를 책임지고 어떤 메서드를 내놓을지를 정하는 일이 설계의 대부분이 되고, 그 판단의 가장 작은 단위가 오늘 한 일, "이 규칙은 어느 데이터에 딸린 것인가"를 묻고 그 데이터 곁에 메서드를 두는 것이다.

    이 장의 핵심

    객체 지향은 데이터와 그 데이터를 다루는 기능을 한 클래스에 묶는 데서 시작한다. 인스턴스 메서드 호출 tank.fill(60)은 점 앞의 참조값을 숨은 첫 번째 인자 this(지역 변수 0번)로 전달하는 호출이며, 메서드의 코드는 클래스에 한 벌만 있고 인스턴스는 필드만 가진다. 묶는 것은 캡슐화의 절반이고, 나머지 절반인 숨기기는 생성자와 접근 제어자가 맡는다.
    절차 지향 프로그래밍
    처리 순서와 기능을 중심으로 코드를 조직한다. 데이터 구조와 그것을 넘겨받아 처리하는 함수가 서로 다른 곳에 있다.
    객체 지향 프로그래밍
    데이터(상태)와 그 데이터를 다루는 기능(동작)을 객체라는 한 단위로 묶어 조직한다. 규칙이 데이터 곁에 놓인다.
    인스턴스 메서드
    static이 없는 메서드. 언제나 어떤 객체에 대해 호출되며, 본문에서 그 객체의 필드를 이름만으로 쓴다.
    숨은 인자 this
    인스턴스 메서드를 호출하면 점 앞의 참조값이 새 프레임의 지역 변수 0번으로 전달된다. 소스에서 그 값을 가리키는 이름이 this이고, level은 this.level의 줄임이다.
    invokestatic과 invokevirtual
    둘 다 스택의 값을 새 프레임의 지역 변수로 옮긴다. invokevirtual은 대상 참조를 0번에 넣고, null이면 호출 전에 예외를 던지며, 대상 객체의 클래스에 따라 메서드를 고른다.
    메서드 코드의 위치
    메서드의 바이트코드는 클래스에 한 벌만 있다. 인스턴스에는 필드 값만 있어서, 메서드를 추가해도 인스턴스 크기는 늘지 않는다.
    캡슐화의 출발점
    데이터와 기능을 묶으면 불변식을 지키는 코드가 한 곳에 모인다. 그러나 필드 직접 수정과 불완전한 초기 상태는 막지 못하며, 접근 제어자와 생성자가 이를 보완한다.

    실무 코드에서 "필드만 있는 클래스"와 "그 객체를 받아 처리하는 메서드가 모인 클래스"의 조합은 흔하다. 이것이 언제나 잘못은 아니다. 요청이나 응답을 실어 나르기만 하는 데이터에는 지켜야 할 규칙이 없으므로 필드만 있어도 충분하다. 판단 기준은 규칙의 유무다. "수량은 음수가 될 수 없다", "상태는 정해진 순서로만 바뀐다" 같은 규칙이 딸린 데이터인데 그 규칙이 여러 클래스의 메서드에 흩어져 있다면, 규칙이 바뀔 때 한 곳을 빠뜨리는 사고가 난다. 그 필드를 고치는 코드가 프로그램에 몇 군데 있는지 세어 보는 것이 가장 빠른 점검이다.

    메서드를 어느 클래스에 둘지 고민될 때는 그 메서드가 주로 읽고 쓰는 데이터가 어디 있는지를 본다. 인자로 받은 객체의 필드를 여러 개 꺼내 계산하고 다시 그 객체의 필드에 써넣는 메서드는 그 객체의 인스턴스 메서드가 될 후보다. 반대로 여러 객체를 조율하는 흐름(조회하고, 계산을 시키고, 저장하는 순서)은 특정 객체의 데이터에 딸린 규칙이 아니므로 바깥에 두는 편이 자연스럽다. 객체 지향 프로그램에도 절차는 남고, 그 절차가 놓일 자리를 고르는 것이 설계다.

WaterTank tank = null; 상태에서 tank.showStatus();를 실행하면 어떻게 되는가? showStatus가 실행되어 "null: 수위 0 / 용량 0"이 출력된다. showStatus 본문이 실행되다가 name 필드를 읽는 순간 예외가 난다. 컴파일 오류가 난다. showStatus 본문에 들어가기 전에, 호출하는 지점에서 NullPointerException이 난다. 인스턴스 메서드 호출은 invokevirtual이고, 이 명령은 대상 참조가 null이면 새 프레임을 만들기 전에 예외를 던진다(JLS §15.12.4.4). 스택 트레이스에는 showStatus의 프레임이 없고 메시지는 Cannot invoke로 시작한다. null인지 여부는 실행 중에만 알 수 있으므로 컴파일 오류는 아니다. 데이터와 메서드를 한 클래스에 묶기만 한 WaterTank(접근 제어자와 생성자를 쓰지 않은 상태)가 보장하지 못하는 것은? fill을 호출하면 용량을 넘지 않도록 수위가 맞춰진다. 용량 규칙을 바꿀 때 fill 한 곳만 고치면 된다. 외부 코드가 fill을 거치지 않고 level을 직접 바꾸는 일이 없다. 인스턴스마다 수위가 따로 관리된다. 묶는 것만으로는 필드에 대한 직접 접근을 막지 못한다. tank.level = 500 같은 코드가 컴파일되고 실행된다. 내부 상태를 숨겨 메서드를 통해서만 접근하게 하는 것은 접근 제어자의 역할이고, 그때 캡슐화가 완성된다.
    절차 지향 프로그래밍(procedural programming)
    처리 순서와 기능을 중심으로 프로그램을 조직하는 방식. 데이터와 그것을 처리하는 함수가 분리되어 있다.
    객체 지향 프로그래밍(object-oriented programming)
    데이터와 그 데이터를 다루는 기능을 객체로 묶고, 객체들의 조합으로 프로그램을 조직하는 방식.
    인스턴스 메서드(instance method)
    static이 붙지 않은 메서드. 언제나 특정 객체에 대해 호출되고, 그 객체가 본문 실행 중의 현재 객체가 된다.
    this
    인스턴스 메서드가 호출된 대상 객체에 대한 참조. JVM에서는 지역 변수 0번으로 전달된다.
    대상 참조(target reference)
    메서드 호출식에서 점 앞의 식을 평가한 참조값. 호출된 메서드 안에서 this가 된다. null이면 호출 시점에 예외가 난다.
    invokevirtual
    인스턴스 메서드를 호출하는 JVM 명령. 대상 참조와 인자를 스택에서 꺼내 새 프레임의 지역 변수 0번부터 넣고, 대상 객체의 클래스에 따라 메서드를 선택한다.
    상태와 동작(state and behavior)
    객체가 필드에 저장한 값이 상태, 메서드로 드러낸 기능이 동작이다. 동작의 결과는 상태에 따라 달라진다.
    불변식(invariant)
    객체가 언제나 만족해야 하는 조건. 예: 수위는 0 이상 용량 이하.
    캡슐화(encapsulation)
    내부 상태를 숨기고 모든 상호작용이 객체의 메서드를 통해 이루어지게 하는 것. 데이터와 기능을 묶는 것이 그 출발점이다.
