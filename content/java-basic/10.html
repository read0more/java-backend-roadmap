    앞 회차에서 가져올 것과 이 회차의 질문

    09회에서 두 가지를 확인했다. 첫째, 부모 타입의 변수는 자식 인스턴스를 가리킬 수 있고, 컴파일러는 변수에 선언된 타입만 보고 어떤 메서드를 호출할 수 있는지 판단한다. 둘째, 오버라이딩된 인스턴스 메서드는 변수의 타입이 아니라 실행 중에 그 변수가 가리키는 객체의 클래스를 기준으로 선택된다. 앞의 것이 다형적 참조이고 뒤의 것이 동적 디스패치(dynamic dispatch)다.

    이 회차는 그 두 규칙을 실제 코드에 적용할 때 생기는 질문을 다룬다. 부모 클래스가 여러 자식을 묶는 용도로만 존재한다면, 누군가 그 부모를 직접 생성하는 일을 어떻게 막을 것인가. 자식 클래스가 꼭 재정의해야 하는 메서드를 빠뜨렸을 때 컴파일러가 잡아 주게 할 수 있는가. 한 객체가 서로 무관한 두 가지 능력을 함께 가져야 한다면 부모를 둘 둘 수 있는가. 자바는 앞의 두 질문에 추상 클래스(abstract class)로, 세 번째 질문에 인터페이스(interface)로 답한다.

    문법 자체는 짧다. 지면의 대부분은 그 문법 아래에서 자바 언어 명세(JLS)가 정한 규칙, 컴파일러가 만들어 내는 클래스 파일, JVM이 호출할 메서드를 찾는 절차에 쓴다. 예제는 사무실의 출력 장치를 다루는 작은 프로그램 하나를 단계마다 고쳐 가는 식으로 진행한다. 실행 결과와 javap 출력은 모두 JDK 21에서 직접 컴파일해 확인한 것이다.

    다형성을 쓰지 않으면: 타입 수만큼 늘어나는 코드

    잉크젯 프린터, 레이저 프린터, 그리고 종이 대신 파일을 만드는 PDF 출력기가 있다. 셋 다 문서를 받아 출력한다는 점은 같지만, 아직은 서로 아무 관계가 없는 클래스다. 이 장치들로 같은 문서를 두 부씩 뽑는 프로그램을 만든다.

    class InkjetPrinter {
    void print(String doc) {
        System.out.println("[잉크젯] " + doc);
    }
}

class LaserPrinter {
    void print(String doc) {
        System.out.println("[레이저] " + doc);
    }
}

class PdfWriter {
    void print(String doc) {
        System.out.println("[PDF 파일] " + doc);
    }
}

public class NoPolyMain {
    public static void main(String[] args) {
        InkjetPrinter inkjet = new InkjetPrinter();
        LaserPrinter laser = new LaserPrinter();
        PdfWriter pdf = new PdfWriter();

        printTwice(inkjet, "회의록");
        printTwice(laser, "회의록");
        printTwice(pdf, "회의록");
    }

    static void printTwice(InkjetPrinter p, String doc) {
        p.print(doc);
        p.print(doc);
    }

    static void printTwice(LaserPrinter p, String doc) {
        p.print(doc);
        p.print(doc);
    }

    static void printTwice(PdfWriter p, String doc) {
        p.print(doc);
        p.print(doc);
    }
}

    printTwice가 세 개다. 본문은 글자 하나 다르지 않은데 매개변수 타입만 다르다. 하나로 합칠 수 없는 이유는 컴파일러의 규칙에 있다. 컴파일러는 p.print(doc)라는 식을 만나면 p에 선언된 타입에 print(String)이 있는지를 확인한다. 세 클래스에 이름이 같은 메서드가 있다는 것은 사람 눈에만 보이는 우연이고, 컴파일러에게 InkjetPrinter.print와 LaserPrinter.print는 서로 무관한 두 메서드다. 세 클래스의 공통 상위 타입은 Object뿐인데 Object에는 print가 없으니, 매개변수를 Object로 받아도 호출할 수 없다.

    세 장치를 배열 하나에 담아 반복문으로 돌리고 싶어도 같은 벽에 부딪힌다. 배열의 원소 타입으로 쓸 수 있는 것이 Object뿐이므로, 꺼낸 뒤에 원래 타입을 하나씩 물어보고 다운캐스팅해야 한다.

    static void printAll(Object[] devices, String doc) {
    for (Object d : devices) {
        if (d instanceof InkjetPrinter) {
            ((InkjetPrinter) d).print(doc);
        } else if (d instanceof LaserPrinter) {
            ((LaserPrinter) d).print(doc);
        } else if (d instanceof PdfWriter) {
            ((PdfWriter) d).print(doc);
        }
    }
}

    이 코드의 문제는 길이가 아니라 변경이 퍼지는 범위다. 장치 종류가 T개이고 장치를 다루는 기능(두 부 출력, 전체 출력, 양면 출력 등)이 M개라면, 중복된 메서드나 분기 가지가 T×M개 생긴다. 네 번째 장치인 감열 프린터를 추가하려면 새 클래스를 쓰는 것으로 끝나지 않고, 기존의 모든 기능 코드를 찾아 오버로딩을 하나씩 더하거나 else if를 하나씩 끼워 넣어야 한다.

    더 나쁜 것은 빠뜨렸을 때의 증상이다. 오버로딩을 빠뜨리면 컴파일 오류가 나므로 그나마 낫다. 분기를 빠뜨린 printAll은 컴파일도 되고 예외도 내지 않는다. 감열 프린터 객체는 어느 조건에도 걸리지 않고 조용히 건너뛰어지며, 출력물이 한 부 모자란다는 사실은 한참 뒤에 사람이 발견한다. 타입에 따라 갈라지는 분기는 컴파일러가 빠진 가지를 알려 주지 않는다.

    정리하면 필요한 것은 하나다. print(String)이 선언되어 있는 타입이면서, 세 클래스의 인스턴스를 모두 가리킬 수 있는 타입. 그런 타입이 있으면 컴파일러는 그 타입의 변수에 대한 print 호출을 허용하고, 실제로 어느 클래스의 print가 실행될지는 동적 디스패치가 정한다.

    공통 부모 타입으로 묶기, 그리고 남는 두 구멍

    09회의 도구를 그대로 쓴다. Printer라는 부모 클래스를 만들어 print를 선언하고, 세 장치가 이를 상속해 오버라이딩한다.

    class Printer {
    void print(String doc) {
        System.out.println("(아무 장치도 아님) " + doc);
    }
}

class InkjetPrinter extends Printer {
    @Override
    void print(String doc) {
        System.out.println("[잉크젯] " + doc);
    }
}

class LaserPrinter extends Printer {
    @Override
    void print(String doc) {
        System.out.println("[레이저] " + doc);
    }
}

class PdfWriter extends Printer {
    @Override
    void print(String doc) {
        System.out.println("[PDF 파일] " + doc);
    }
}

public class PolyMain {
    public static void main(String[] args) {
        Printer[] printers = {new InkjetPrinter(), new LaserPrinter(), new PdfWriter()};
        for (Printer p : printers) {
            printTwice(p, "회의록");
        }
    }

    static void printTwice(Printer p, String doc) {
        p.print(doc);
        p.print(doc);
    }
}

    실행 결과는 앞의 프로그램과 같은 여섯 줄이다. 달라진 것은 코드의 모양이다. printTwice는 하나만 남았고, 배열의 원소 타입은 Printer가 되었으며, instanceof는 사라졌다. printTwice 안의 p.print(doc) 한 줄을 추적해 보자. 컴파일할 때 p의 타입은 Printer이고 Printer에 print(String)이 있으므로 호출이 허용된다. 실행할 때 p가 가리키는 객체가 LaserPrinter 인스턴스라면 JVM은 그 객체의 클래스에서 출발해 print를 찾고, LaserPrinter가 재정의한 메서드를 실행한다.

    이제 감열 프린터를 추가하는 일은 Printer를 상속한 클래스 하나를 새로 쓰는 것으로 끝난다. printTwice도, 배열을 도는 반복문도 손댈 필요가 없다. 타입에 따른 분기를 사람이 if로 쓰는 대신 JVM의 메서드 선택에 맡긴 결과다. T×M개였던 코드가 T개의 클래스와 M개의 기능으로, 곱셈이 덧셈으로 바뀌었다.

    왼쪽은 장치 종류마다 if 분기가 늘어나는 구조, 오른쪽은 부모 타입 하나로 호출하고 JVM이 실제 객체의 메서드를 고르는 구조를 나란히 보여 준다. 좌우 2분할 비교 다이어그램. 흰 배경, 얇은 선, 차분한 파랑과 회색. 왼쪽 패널 제목 "다형성 없음": 위에 상자 "printAll(Object[])", 그 아래로 마름모 세 개가 세로로 이어지고 각각 "InkjetPrinter인가?", "LaserPrinter인가?", "PdfWriter인가?" 라벨, 각 마름모 오른쪽으로 화살표가 나가 작은 상자 "캐스팅 후 print"로 연결. 맨 아래에 점선 마름모 "새 장치?"와 빨간 글씨 "분기를 직접 추가". 오른쪽 패널 제목 "다형성 사용": 위에 상자 "printAll(Printer[])", 아래로 화살표 하나가 "p.print(doc)" 상자로, 거기서 세 갈래 화살표가 "InkjetPrinter", "LaserPrinter", "PdfWriter" 상자로 향함. 세 갈래 화살표 옆에 라벨 "실행 중 객체의 클래스로 선택". 오른쪽 끝에 점선 상자 "새 장치"와 초록 글씨 "클래스만 추가". 타입마다 갈라지는 분기를 사람이 쓰느냐, JVM의 메서드 선택에 맡기느냐의 차이다.

    그런데 이 설계에는 구멍이 둘 있다. 다음 두 줄을 main에 더해 보자. ThermalPrinter는 Printer를 상속했지만 print를 재정의하는 것을 잊은 클래스다.

    class ThermalPrinter extends Printer {
    // print()를 재정의하는 것을 잊었다
}

// main 안에서
new Printer().print("회의록");
new ThermalPrinter().print("회의록");

    첫 번째 구멍은 new Printer()가 가능하다는 것이다. Printer는 세 장치를 한 타입으로 묶으려고 만든 개념일 뿐 실제로 존재하는 장치가 아니다. 그런데도 일반 클래스이므로 인스턴스를 만들 수 있고, 그 인스턴스는 Printer[] 배열에 섞여 들어가 의미 없는 출력을 낸다. 두 번째 구멍은 ThermalPrinter다. 부모의 print에 본문이 있으니 재정의하지 않아도 상속 규칙상 아무 문제가 없고, 컴파일러는 침묵한다. 앞 절에서 본 "조용히 틀리는" 문제가 자리만 옮겨 다시 나타났다.

    두 구멍의 원인은 같다. Printer.print의 본문은 호출을 가능하게 하려고 억지로 채운 것인데, 언어 입장에서는 정상적인 구현과 구별할 방법이 없다. 필요한 것은 "이 클래스는 완성되지 않았으니 직접 생성하지 말라"와 "이 메서드는 선언만 있고 구현은 자식이 반드시 채워야 한다"를 컴파일러가 검사하는 규칙으로 표현하는 수단이다.

    추상 클래스: 불완전하다고 선언한 클래스

    클래스 선언 앞에 abstract를 붙이면 추상 클래스가 된다. JLS 8.1.1.1은 추상 클래스를 이렇게 정의한다. "An abstract class is a class that is incomplete, or to be considered incomplete." 불완전하거나, 불완전하다고 간주해야 하는 클래스라는 뜻이다. 뒤쪽 표현이 중요하다. 추상 메서드가 하나도 없어도 설계자가 "이 클래스만으로는 쓸 수 없다"고 판단하면 abstract를 붙일 수 있다.

    이 선언이 만들어 내는 규칙은 다음과 같다.

    • 직접 생성할 수 없다. new Printer()처럼 클래스 인스턴스 생성식으로 추상 클래스의 인스턴스를 만들려고 하면 컴파일 오류다(JLS 8.1.1.1). javac는 "Printer is abstract; cannot be instantiated"라고 알린다.
    • 추상 메서드를 가질 수 있는 것은 추상 클래스뿐이다. 추상 클래스가 아닌 일반 클래스가 추상 메서드를 가지면 컴파일 오류다. 여기서 "가진다"에는 직접 선언한 것뿐 아니라 상속받고 구현하지 않은 것도 포함된다.
    • 그 밖에는 보통 클래스와 같다. 인스턴스 필드, 생성자, 본문이 있는 메서드, static 멤버를 모두 가질 수 있다. 다른 클래스를 상속할 수 있고, 다른 클래스의 부모가 될 수 있다.
    • final과 함께 쓸 수 없다. 추상 클래스는 상속되어야 완성되는데 final은 상속을 막으므로 서로 모순이다. javac는 "illegal combination of modifiers: abstract and final"로 거부한다.

    생성할 수 없는 클래스에 생성자가 있다는 점이 처음에는 어색하다. 추상 클래스의 생성자는 new로 직접 불리는 것이 아니라 자식 클래스의 생성자가 super(...)로 부른다. JLS는 이를 명시한다. 추상 클래스의 하위 클래스 중 추상이 아닌 것은 인스턴스화할 수 있고, 그 결과 추상 클래스의 생성자가 실행되며 그 클래스 인스턴스 변수의 필드 초기화식도 실행된다(JLS 8.1.1.1). 상속에서 부모 생성자가 먼저 실행된다는 08회의 규칙이 추상 클래스에도 그대로 적용되는 것이다.

    Printer를 추상 클래스로 바꾸면서, 모든 프린터가 공유하는 상태와 절차를 부모로 올려 보자. 장치 이름과 작업 횟수는 어떤 프린터에나 있고, "작업 횟수를 올리고 머리말을 찍은 뒤 실제 인쇄를 한다"는 순서도 공통이다. 장치마다 다른 것은 실제로 인쇄하는 방식뿐이다.

    abstract class Printer {
    private final String name;
    private int jobCount;

    protected Printer(String name) {
        this.name = name;
        System.out.println("Printer 생성자: " + name);
    }

    void print(String doc) {
        jobCount++;
        System.out.println(name + " 작업 #" + jobCount);
        render(doc);
    }

    abstract void render(String doc);

    int jobCount() {
        return jobCount;
    }
}

class InkjetPrinter extends Printer {
    InkjetPrinter(String name) {
        super(name);
    }

    @Override
    void render(String doc) {
        System.out.println("  잉크를 분사해 인쇄: " + doc);
    }
}

class LaserPrinter extends Printer {
    private int toner = 100;

    LaserPrinter(String name) {
        super(name);
    }

    @Override
    void render(String doc) {
        toner -= 5;
        System.out.println("  토너를 정착시켜 인쇄: " + doc + " (토너 " + toner + "%)");
    }
}

public class AbstractMain {
    public static void main(String[] args) {
        Printer[] printers = {new InkjetPrinter("1층 잉크젯"), new LaserPrinter("3층 레이저")};
        for (Printer p : printers) {
            p.print("회의록");
        }
        printers[1].print("계약서");
        System.out.println("3층 레이저 작업 수 = " + printers[1].jobCount());
    }
}

    이 그림에서 두 가지를 확인해 둔다. 하나는 Printer[]라는 배열은 만들 수 있다는 점이다. 배열을 만드는 것은 Printer 타입 참조를 담을 칸을 만드는 것이지 Printer 인스턴스를 만드는 것이 아니므로 추상 클래스의 규칙에 걸리지 않는다. new Printer[2]로 만든 배열의 칸에는 처음에 null이 들어 있다. 다른 하나는 추상 클래스가 "객체 없는 클래스"가 아니라는 점이다. 추상 클래스에 선언한 인스턴스 필드는 자식 객체마다 하나씩 실제로 메모리를 차지하고, 추상 클래스의 메서드는 그 필드를 읽고 쓴다.

    생성 금지는 컴파일러만의 규칙이 아니다. 추상 클래스를 컴파일한 클래스 파일에는 ACC_ABSTRACT 플래그가 기록된다. javap -v로 Printer를 보면 flags: (0x0420) ACC_SUPER, ACC_ABSTRACT가 찍힌다. JVM 명세는 new 명령이 가리키는 심벌릭 참조가 인터페이스나 추상 클래스로 해석되면 InstantiationError를 던진다고 정한다(JVMS 6.5 new). 정상적으로 컴파일한 프로그램에서는 볼 일이 없지만, 어떤 클래스를 나중에 추상 클래스로 바꾸고 그 클래스를 생성하던 쪽은 다시 컴파일하지 않았을 때 이 오류가 실행 중에 나타난다. 소스에서 한 번, 실행할 때 한 번, 두 겹으로 막혀 있는 셈이다.

    추상 메서드: 구현을 자식에게 넘기는 선언

    위 예제의 abstract void render(String doc);가 추상 메서드다. JLS 8.4.3.1의 표현으로는, 추상 메서드 선언은 메서드를 멤버로 도입하면서 시그니처와 반환 타입, throws 절은 제공하지만 구현은 제공하지 않는다. 그래서 본문 자리에 중괄호 대신 세미콜론이 온다. 본문을 쓰면 "abstract methods cannot have a body" 오류가 난다. 반대로 추상이 아닌 메서드를 명세는 구체 메서드(concrete method)라고 부른다.

    추상 메서드가 만드는 규칙은 두 방향으로 작용한다. 선언하는 쪽에서는, 추상 메서드는 추상 클래스 안에 직접 선언되어야 한다(열거형 선언 안에서도 쓸 수 있는데 이는 중급편의 주제다). 상속받는 쪽에서는, 추상 클래스의 하위 클래스 중 추상이 아닌 것은 모두 그 메서드의 구현을 제공해야 하며 그렇지 않으면 컴파일 오류다(JLS 8.4.3.1). 앞 절의 ThermalPrinter처럼 재정의를 잊으면 이제 컴파일러가 이렇게 알려 준다.

    error: ThermalPrinter is not abstract and does not override abstract method render(String) in Printer

    오류 문장을 그대로 읽으면 선택지가 둘이라는 것을 알 수 있다. render를 구현하거나, ThermalPrinter도 abstract로 선언해 구현을 한 단계 더 아래로 미루는 것이다. 어느 쪽이든 "구현이 빠진 메서드를 가진 채로 인스턴스가 만들어지는 일"은 일어나지 않는다. 이것이 추상 클래스와 추상 메서드가 함께 지키는 불변식이다. 인스턴스를 만들 수 있는 클래스는 호출 가능한 모든 메서드에 구현이 있다.

    추상 메서드에 함께 쓸 수 없는 제어자도 이 불변식에서 나온다. JLS 8.4.3은 abstract가 붙은 메서드 선언에 private, static, final, native, strictfp, synchronized 중 어느 하나라도 있으면 컴파일 오류라고 정한다. 앞의 셋은 이유가 분명하다. private 메서드는 자식에게 상속되지 않으므로 자식이 구현할 길이 없다. static 메서드는 객체가 아니라 클래스에 속하고 동적 디스패치의 대상이 아니므로, 자식이 같은 이름의 메서드를 써도 재정의가 아니다. final은 재정의를 금지하는 선언이니 "반드시 재정의하라"와 정면으로 충돌한다.

    이제 부모의 구체 메서드 print가 추상 메서드 render를 호출하는 부분을 보자. Printer를 컴파일하는 시점에는 render의 구현이 어디에도 없다. 그런데도 컴파일되는 이유는 호출 명령이 구현의 위치가 아니라 이름과 디스크립터만 기록하기 때문이다.

          29: aload_0
      30: aload_1
      31: invokevirtual #36                 // Method render:(Ljava/lang/String;)V
      34: return

    aload_0은 this를, aload_1은 doc을 피연산자 스택에 올린다. invokevirtual은 스택에 놓인 this가 가리키는 객체의 클래스에서 출발해 render(String)을 찾는다. Printer는 생성할 수 없으므로 this는 언제나 InkjetPrinter나 LaserPrinter 같은 구체 클래스의 인스턴스이고, 그 클래스에는 반드시 render의 구현이 있다. 부모가 절차의 뼈대를 정하고 자식이 빈칸을 채우는 구조가 성립하는 것은 "추상 클래스는 생성 불가"와 "구체 클래스는 구현 필수"라는 두 규칙이 맞물려 있기 때문이다.

    클래스 파일에서도 차이가 보인다. javap -v 출력에서 render는 flags: (0x0400) ACC_ABSTRACT만 있고 Code: 항목이 없다. JVM 명세가 추상 메서드의 method_info에는 Code 속성이 있어서는 안 된다고 정하기 때문이다(JVMS 4.7.3). 추상 메서드는 메서드 영역에 이름과 디스크립터로만 존재하고 실행할 바이트코드가 없다. 만약 따로 컴파일된 클래스들이 어긋나서 실행 중에 선택된 메서드가 추상 메서드라면, invokevirtual은 AbstractMethodError를 던진다(JVMS 6.5 invokevirtual).

    추상 메서드에 관한 두 가지 추가 규칙(JLS 8.4.3.1). 추상 클래스는 물려받은 추상 메서드를 다시 추상 메서드로 선언해 재정의할 수 있다. 그리고 추상이 아닌 인스턴스 메서드를 추상 메서드로 재정의할 수도 있다. 예를 들어 추상 클래스에 public abstract String toString();을 선언하면, Object에 구현이 있는데도 모든 구체 하위 클래스가 toString을 직접 구현해야 컴파일된다.

    순수 추상 클래스에서 인터페이스로

    추상 클래스에서 공유 상태와 구체 메서드를 모두 걷어 내고 추상 메서드만 남긴 형태를 생각해 보자. 관용적으로 순수 추상 클래스라고 부른다.

    abstract class Printer {
    abstract void print(String doc);
}

    이 클래스는 물려줄 코드가 하나도 없다. 하는 일은 "Printer라면 print(String)을 할 수 있다"는 약속을 타입으로 선언하는 것뿐이다. 호출하는 쪽은 이 약속만 믿고 코드를 쓰고, 구현하는 쪽은 이 약속을 채운다. 구현을 물려주는 수단이었던 상속이, 여기서는 순전히 규격을 강제하는 수단으로 쓰이고 있다.

    그런데 규격만 선언하는 용도로 쓰기에 클래스는 값이 비싸다. 자바의 클래스는 부모 클래스를 하나만 가질 수 있으므로, 어떤 장치가 Printer를 상속하는 순간 다른 클래스를 상속할 기회가 사라진다. 인쇄도 하고 스캔도 하는 복합기를 만들려는데 Printer와 PageScanner가 둘 다 순수 추상 클래스라면 둘 중 하나밖에 고를 수 없다. 규격은 여러 개를 동시에 만족할 수 있어야 자연스럽다.

    자바는 "구현 없이 규격만 선언하는 타입"을 클래스와 별도의 종류로 제공한다. 인터페이스다. JLS 9장의 도입부는 인터페이스의 쓰임을 두 가지로 적는다. 서로 관련 없는 클래스들에 공통 상위 타입을 제공하는 것, 그리고 관련 있는 클래스들이 공통의 추상 상위 클래스를 공유하지 않아도 되게 하는 것이다. 순수 추상 클래스의 역할은 그대로 가지면서 단일 상속의 제약에서 벗어난 타입이다.

    인터페이스의 멤버 규칙: 생략된 제어자 복원하기

    인터페이스는 class 대신 interface 키워드로 선언한다. 아래에서 첫 번째가 보통 쓰는 모양이고, 두 번째가 컴파일러가 받아들이는 실제 의미다.

    // 소스에 쓰는 모양
interface PageScanner {
    int MAX_DPI = 1200;

    String scan();
}

// 컴파일러가 해석하는 선언 (제어자를 모두 적은 것)
interface PageScanner {
    public static final int MAX_DPI = 1200;

    public abstract String scan();
}

    두 선언을 각각 컴파일해 비교하면 클래스 파일이 바이트 단위로 같다. 제어자를 생략할 수 있는 것은 편의 기능이 아니라 다른 선택지가 없기 때문이다. JLS 9장이 정한 규칙을 항목별로 보면 다음과 같다.

    대상암묵적으로 붙는 것근거와 결과
    인터페이스 자체abstract모든 인터페이스는 암묵적으로 추상이다(JLS 9.1.1.1). new PageScanner()는 컴파일 오류다.
    필드public static final인터페이스 본문의 모든 필드 선언은 암묵적으로 public, static, final이다(JLS 9.3). 인스턴스 변수는 가질 수 없고, 초기화식 없이는 선언할 수 없다.
    메서드의 접근 수준public접근 제어자를 쓰지 않으면 public이다. protected나 패키지 접근은 선언할 수 없다(JLS 9.4).
    메서드의 구현 여부abstractprivate, default, static 중 어느 것도 붙지 않은 메서드는 암묵적으로 추상이고, 본문 대신 세미콜론을 쓴다(JLS 9.4).
    생성자없음인터페이스에는 생성자를 선언할 수 없다. 초기화할 인스턴스 상태가 없기 때문이다.

    클래스 파일에서 이 규칙을 직접 볼 수 있다. 제어자를 하나도 쓰지 않은 첫 번째 소스를 컴파일한 뒤 javap -v로 열면 생략했던 제어자가 모두 플래그로 기록되어 있다.

    interface PageScanner
  flags: (0x0600) ACC_INTERFACE, ACC_ABSTRACT
  ...
  public static final int MAX_DPI;
    flags: (0x0019) ACC_PUBLIC, ACC_STATIC, ACC_FINAL
    ConstantValue: int 1200

  public abstract java.lang.String scan();
    flags: (0x0401) ACC_PUBLIC, ACC_ABSTRACT

    이것은 컴파일러의 습관이 아니라 JVM 명세의 요구다. 클래스 파일에 ACC_INTERFACE 플래그가 있으면 ACC_ABSTRACT도 반드시 있어야 하고(JVMS 4.1), 인터페이스의 필드는 ACC_PUBLIC, ACC_STATIC, ACC_FINAL이 모두 설정되어 있어야 한다(JVMS 4.5). 인터페이스 자체에 public을 붙이지 않아 패키지 안에서만 보이는 인터페이스여도 그 멤버는 public이라는 점도 위 출력에서 확인된다.

    구현하는 쪽의 규칙

    클래스는 implements로 인터페이스를 구현한다. 추상 클래스를 상속할 때와 같은 의무가 생긴다. 클래스가 추상이 아니라면 직접 상위 인터페이스의 모든 추상 메서드를 구현해야 한다(JLS 8.1.5). 이때 처음 인터페이스를 쓰는 사람이 가장 자주 만나는 오류가 있다.

    interface Printer {
    void print(String doc);
}

class LaserPrinter implements Printer {
    void print(String doc) {          // public을 빠뜨렸다
        System.out.println("[레이저 인쇄] " + doc);
    }
}
    error: print(String) in LaserPrinter cannot implement print(String) in Printer
  attempting to assign weaker access privileges; was public

    인터페이스의 print는 적지 않았어도 public이다. 클래스에서 접근 제어자를 생략하면 패키지 접근이 되므로, 구현 메서드가 원래 메서드보다 접근 범위를 좁힌 꼴이 된다. JLS 8.4.8.3은 재정의하는 메서드가 재정의되는 메서드 이상의 접근을 제공해야 하고, 원래 메서드가 public이면 재정의하는 메서드도 public이어야 한다고 정한다. 이 규칙이 없다면 Printer 타입 변수로는 호출할 수 있는 메서드가 LaserPrinter 타입 변수로는 호출할 수 없게 되어, 자식 인스턴스를 부모 타입 자리에 넣어도 된다는 다형성의 전제가 깨진다. 같은 인터페이스 선언에서 생략 가능했던 public이 구현 클래스에서는 필수인 이유다.

    implements도 타입 사이의 상위·하위 관계를 만든다. Printer p = new LaserPrinter();가 성립하고, 09회에서 다룬 다형적 참조, instanceof, 캐스팅의 규칙이 클래스 상속과 똑같이 적용된다. 인터페이스 타입 변수로 toString()이나 equals()를 부를 수 있는 것도 규칙으로 정해져 있다. 상위 인터페이스가 없는 인터페이스는 Object의 public 인스턴스 메서드 각각에 대응하는 public abstract 메서드를 암묵적으로 선언한 것으로 본다(JLS 9.2).

    인터페이스의 상수는 컴파일할 때 복사된다

    인터페이스의 필드는 static final이므로 객체마다 있는 것이 아니라 인터페이스에 하나만 있다. 게다가 MAX_DPI처럼 기본형이나 String이고 상수식으로 초기화된 필드는 상수 변수(constant variable)여서, 그것을 읽는 코드에는 필드 참조가 아니라 값 자체가 박힌다. "스캔 이미지(" + MAX_DPI + "dpi)"라는 식을 가진 메서드를 컴파일해 보면 바이트코드에 필드를 읽는 getstatic이 없고, 이미 합쳐진 문자열 "스캔 이미지(1200dpi)"를 올리는 ldc 하나만 있다. JLS 13.1이 상수 변수에 대한 참조는 컴파일할 때 그 값으로 해석되어야 한다고 정하기 때문이다.

    이 동작은 실무에서 함정이 된다. 인터페이스의 상수 값을 2400으로 고치고 인터페이스만 다시 컴파일하면, 그 상수를 쓰던 다른 클래스 파일에는 여전히 1200이 들어 있다. 명세도 이 경우 기존 바이너리가 실행은 되지만 다시 컴파일하기 전에는 새 값을 보지 못한다고 적고 있다(JLS 13.4.9). 서로 다른 JAR에 나뉘어 배포되는 코드에서 상수를 바꿀 때는 그 상수를 쓰는 쪽도 함께 다시 빌드해야 한다.

    인터페이스에 본문이 있는 메서드를 둘 수 있게 된 것은 나중 일이다. Java SE 7 명세까지는 인터페이스의 모든 메서드가 암묵적으로 public abstract였다. Java SE 8에서 default 메서드와 static 메서드가, Java SE 9에서 private 메서드가 추가되었다. 이 회차에서 default 메서드는 충돌 규칙과 관련된 부분만 언급하고 넘어간다.

    왜 클래스는 하나만 상속하고 인터페이스는 여러 개 구현하는가

    문법부터 다르다. extends 뒤에는 클래스 타입 하나만 올 수 있고, implements 뒤에는 쉼표로 구분한 인터페이스 목록이 올 수 있다(JLS 8.1.4, 8.1.5). class Mfd extends PrinterBase, ScannerBase라고 쓰면 타입 검사까지 가지도 못하고 구문 오류로 끝난다. JLS 8장의 첫머리는 이 구조를 한 문장으로 적는다. Object를 제외한 모든 클래스는 기존 클래스 하나의 확장이고, 인터페이스들을 구현할 수 있다.

    클래스 상속을 하나로 제한한 이유는 부모가 둘일 때 답할 수 없는 질문이 생기기 때문이다. 흔히 다이아몬드 문제(diamond problem)라고 부르는 상황을 가정해 보자. 사용 횟수 필드와 상태 출력 메서드를 가진 Device가 있고, 이를 상속한 PrinterBase와 ScannerBase가 각자 status()를 재정의했다. 복합기 Mfd가 이 둘을 모두 상속할 수 있다고 하자.

                     Device
            usage 필드, status()
              ▲            ▲
     PrinterBase          ScannerBase
   status() 재정의       status() 재정의
              ▲            ▲
              └─── Mfd ────┘        ← 자바에서는 선언할 수 없다

질문 1 (상태)  Mfd 객체 안에 usage는 하나인가, 둘인가?
질문 2 (구현)  mfd.status()는 어느 부모의 status()를 실행하는가?
질문 3 (생성)  Device의 생성자는 한 번 실행되는가, 두 번 실행되는가?

    세 질문 모두 "어느 쪽이든 말이 된다"는 것이 문제다. usage가 둘이면 인쇄 횟수와 스캔 횟수가 따로 세어져서 좋을 수도 있고, 하나의 장치인데 사용 횟수가 둘로 갈라져서 틀릴 수도 있다. status()도 마찬가지다. 언어가 한쪽으로 정해 버리면 프로그래머는 그 규칙을 외워야 하고, 부모 클래스의 내부가 바뀔 때마다 자식의 동작이 예상 밖으로 달라질 수 있다. 자바는 부모 클래스를 하나로 제한해 이 질문이 생기지 않게 했다. 그 결과 객체의 필드 구성은 Object에서 자기 클래스까지 이어지는 한 줄의 상속 사슬만 보면 결정되고, 부모 생성자가 실행되는 순서도 한 줄로 정해진다.

    클래스 둘을 상속하면 상태와 구현이 두 경로로 내려와 충돌하지만, 인터페이스 둘을 구현하면 내려오는 것이 선언뿐이라 충돌할 것이 없음을 대비해 보여 준다. 좌우 2분할 구조 다이어그램. 흰 배경, 얇은 선. 왼쪽 패널 제목 "클래스 다중 상속 (금지)": 마름모꼴 배치로 맨 위 상자 "Device" 안에 작은 글씨 "usage, status()", 중간 좌우에 상자 "PrinterBase"와 "ScannerBase", 맨 아래 상자 "Mfd". 아래에서 위로 향하는 실선 화살표 네 개. "Mfd" 상자 옆에 빨간 물음표와 라벨 "usage는 몇 개?" 그리고 "어느 status()?". 패널 전체에 옅은 빨간 금지 표시. 오른쪽 패널 제목 "인터페이스 다중 구현 (허용)": 위쪽에 점선 테두리 상자 두 개 "Printer"와 "PageScanner", 각 상자 안에 작은 글씨 "print() 선언만", "scan() 선언만". 그 아래 실선 상자 "MultiFunctionDevice" 안에 "print() 구현", "scan() 구현". 아래 상자에서 위 두 상자로 향하는 점선 화살표. 옆에 초록 라벨 "필드 없음, 구현은 한 곳". 충돌의 원인은 두 경로로 내려오는 상태와 구현이다. 선언만 내려오면 충돌할 것이 없다.

    인터페이스를 여러 개 구현해도 되는 이유는 위 세 질문의 원인이 인터페이스에는 없기 때문이다. 질문 1은 인스턴스 필드가 두 경로로 내려와서 생기는데, 인터페이스에는 인스턴스 변수가 없다. 질문 3은 생성자 때문에 생기는데, 인터페이스에는 생성자가 없다. 질문 2는 구현이 둘이어서 생기는데, 추상 메서드에는 구현이 없다. 두 인터페이스가 우연히 똑같은 시그니처의 추상 메서드를 선언했더라도 실행될 수 있는 본문은 구현 클래스에 있는 하나뿐이다. JLS 8.1.5는 클래스의 메서드 선언 하나가 둘 이상의 상위 인터페이스의 메서드를 구현하는 것을 허용한다고 명시한다.

    충돌이 전혀 없는 것은 아니다. 두 인터페이스가 이름과 매개변수는 같은데 반환 타입이 서로 호환되지 않는 메서드를 선언했다면, 한 메서드로 둘을 동시에 만족시킬 수 없으므로 두 인터페이스를 함께 구현하는 클래스는 컴파일되지 않는다(JLS 8.4.8.3, 8.4.8.4). 그리고 Java 8에서 default 메서드가 들어오면서 "구현이 두 경로로 내려오는" 상황이 인터페이스에서도 가능해졌다. 자바는 이 경우를 조용히 한쪽으로 정하지 않는다. 클래스가 시그니처가 같은 default 메서드를 두 인터페이스에서 물려받으면 컴파일 오류이고, 그 클래스가 직접 메서드를 재정의해 어떻게 할지 적어야 한다. 상태는 여전히 물려받지 않으므로 질문 1과 3은 생기지 않는다.

    클래스와 인터페이스를 함께 쓰기

    실제 코드에서는 둘을 섞어 쓴다. 공유할 상태와 코드는 추상 클래스에, 외부에 약속하는 능력은 인터페이스에 둔다. 사무실 장치라면 이름과 사용 횟수는 모든 장치의 공통 상태이고, 인쇄와 스캔은 장치에 따라 있기도 하고 없기도 한 능력이다. 선언할 때는 extends를 먼저, implements를 나중에 쓴다.

    interface Printer {
    void print(String doc);
}

interface PageScanner {
    int MAX_DPI = 1200;

    String scan();
}

abstract class OfficeDevice {
    private final String name;
    private int usage;

    protected OfficeDevice(String name) {
        this.name = name;
    }

    protected void used() {
        usage++;
    }

    String status() {
        return name + ": " + usage + "회 사용";
    }
}

class LaserPrinter extends OfficeDevice implements Printer {
    LaserPrinter(String name) {
        super(name);
    }

    @Override
    public void print(String doc) {
        used();
        System.out.println("[레이저 인쇄] " + doc);
    }
}

class MultiFunctionDevice extends OfficeDevice implements Printer, PageScanner {
    MultiFunctionDevice(String name) {
        super(name);
    }

    @Override
    public void print(String doc) {
        used();
        System.out.println("[복합기 인쇄] " + doc);
    }

    @Override
    public String scan() {
        used();
        return "복합기 스캔 이미지(" + MAX_DPI + "dpi)";
    }
}

public class OfficeMain {
    public static void main(String[] args) {
        MultiFunctionDevice mfd = new MultiFunctionDevice("2층 복합기");
        LaserPrinter laser = new LaserPrinter("3층 레이저");

        Printer[] printers = {laser, mfd};
        printAll(printers, "계약서");

        PageScanner scanner = mfd;
        System.out.println(scanner.scan());

        OfficeDevice[] devices = {laser, mfd};
        for (OfficeDevice d : devices) {
            System.out.println(d.status());
        }
    }

    static void printAll(Printer[] printers, String doc) {
        for (Printer p : printers) {
            p.print(doc);
        }
    }
}
    [레이저 인쇄] 계약서
[복합기 인쇄] 계약서
복합기 스캔 이미지(1200dpi)
3층 레이저: 1회 사용
2층 복합기: 2회 사용

    복합기 객체는 힙에 하나뿐이다. 그 안에 들어 있는 인스턴스 필드는 OfficeDevice에 선언된 name과 usage 둘이 전부다. Printer와 PageScanner는 객체의 메모리 구성에 아무것도 보태지 않는다. 인터페이스가 하는 일은 이 객체를 가리킬 수 있는 타입을 늘리는 것이다. 같은 객체를 mfd, printers[1], scanner, devices[1]이라는 네 참조가 서로 다른 타입으로 가리키고 있고, 인쇄 한 번과 스캔 한 번이 같은 usage를 올렸기 때문에 마지막 줄이 2회로 찍힌다.

    변수 (선언 타입)                     힙의 객체 하나
mfd         (MultiFunctionDevice) ─┐
printers[1] (Printer)             ─┼──▶ MultiFunctionDevice 인스턴스
scanner     (PageScanner)         ─┤       name  = "2층 복합기"
devices[1]  (OfficeDevice)        ─┘       usage = 2

선언 타입별로 컴파일러가 허용하는 호출
  MultiFunctionDevice : print, scan, status, used, Object의 메서드
  Printer             : print, Object의 메서드
  PageScanner         : scan, Object의 메서드
  OfficeDevice        : status, used, Object의 메서드

    변수의 타입은 객체를 들여다보는 창의 크기를 정한다. Printer 타입 변수로는 print만 보이므로 printers[1].scan()은 컴파일되지 않는다. 객체가 실제로 스캔할 수 있는지와 무관하게, 컴파일러는 선언 타입에 있는 메서드만 허용한다. printAll 메서드가 받는 것은 "인쇄할 수 있는 것들"이고, 그 안에 복합기가 섞여 있는지 알 필요도 없고 알 수도 없다.

    인터페이스 타입에서 다른 인터페이스 타입으로 캐스팅할 때는 클래스 캐스팅과 다른 점이 하나 있다.

    Printer p = new MultiFunctionDevice("2층 복합기");
PageScanner s = (PageScanner) p;        // 컴파일 성공, 실행 성공
System.out.println(s.scan());

Printer laser = new LaserPrinter("3층 레이저");
System.out.println(laser instanceof PageScanner);   // false
PageScanner s2 = (PageScanner) laser;   // 컴파일 성공, 실행 중 ClassCastException

    Printer와 PageScanner는 서로 상속 관계가 없는데도 캐스팅이 컴파일된다. 서로 무관한 두 클래스 사이의 캐스팅이 컴파일 오류인 것과 대조된다. 클래스는 부모가 하나이므로 두 클래스가 무관하면 한 객체가 둘 다일 수 없다는 것을 컴파일러가 증명할 수 있다. 인터페이스는 여러 개를 구현할 수 있으므로, Printer 변수가 가리키는 객체의 클래스가 PageScanner도 구현했을 가능성을 컴파일러가 배제하지 못한다. 그래서 판단을 실행 시점으로 미룬다. 컴파일러는 그 자리에 checkcast 명령을 넣고, JVM이 실제 객체를 검사해 아니라면 ClassCastException을 던진다. 캐스팅 전에 instanceof로 확인해야 한다는 09회의 원칙은 인터페이스에서 더 중요하다. 컴파일러가 거부하는 경우도 있기는 하다. 변수의 타입이 final 클래스이고 그 클래스가 대상 인터페이스를 구현하지 않았다면, 하위 클래스가 생길 수 없으니 캐스팅이 성공할 가능성이 없다는 것을 컴파일러가 알 수 있다.

    한 층 아래: invokevirtual과 invokeinterface

    앞 예제의 OfficeMain에는 다형적 호출이 두 군데 있다. OfficeDevice 타입 변수로 부르는 d.status()와 Printer 타입 변수로 부르는 p.print(doc)다. 소스에서는 똑같이 점 하나로 쓰는 호출인데 바이트코드에서는 서로 다른 명령이 된다.

    main 메서드의 d.status()
      98: aload         9
     100: invokevirtual #48                 // Method OfficeDevice.status:()Ljava/lang/String;

printAll 메서드의 p.print(doc)
      20: aload         5
      22: aload_1
      23: invokeinterface #51,  2           // InterfaceMethod Printer.print:(Ljava/lang/String;)V

    어느 명령을 쓸지는 컴파일할 때 정해진다. JLS 15.12.3은 메서드 호출마다 호출 모드(invocation mode)를 계산하는 규칙을 둔다. 메서드가 static이면 static 모드, super.로 부르면 super 모드이고, 그 밖의 경우에 호출의 한정 타입이 인터페이스이면 interface 모드, 아니면 virtual 모드다. 한정 타입은 점 앞에 있는 식의 컴파일 시점 타입이다. 즉 기준은 객체가 아니라 변수의 선언 타입이다. 같은 LaserPrinter 객체의 같은 print 메서드라도 LaserPrinter 타입 변수로 부르면 invokevirtual LaserPrinter.print가, Printer 타입 변수로 부르면 invokeinterface Printer.print가 만들어진다. 실행되는 메서드는 둘 다 LaserPrinter.print다.

    가장 중요한 줄은 메서드 선택이다. 두 명령은 같은 절차를 쓴다. 스택에 놓인 객체 참조가 가리키는 객체의 클래스를 C라고 할 때, C에 해석된 메서드를 재정의하는 선언이 있으면 그것을, 없으면 C의 상위 클래스를 차례로 올라가며 찾고, 그래도 없으면 상위 인터페이스에서 추상이 아닌 메서드가 정확히 하나인지를 본다(JVMS 5.4.6). 09회에서 배운 "실제 객체의 클래스에서 출발해 위로 찾는다"는 규칙은 인터페이스 호출에서도 그대로다. 인터페이스 타입 변수로 호출한다고 해서 인터페이스에 있는 무언가가 실행되는 것이 아니다.

    차이는 두 가지다. 하나는 심벌릭 참조의 종류다. 호출하는 쪽의 클래스 파일에는 대상이 클래스인지 인터페이스인지가 상수 풀 항목의 종류로 기록되고, 실행 중에 해석해 보니 그 반대라면 연결 오류가 난다. 어떤 타입을 클래스에서 인터페이스로 바꾸고 그것을 호출하던 코드는 다시 컴파일하지 않았을 때 IncompatibleClassChangeError를 보게 되는 이유다. 다른 하나는 수신 객체에 대한 실행 시점 검사다. invokeinterface는 객체의 클래스가 정말 그 인터페이스를 구현하는지를 호출할 때 확인한다.

    이 검사가 호출 시점에 있는 이유는 클래스 파일 검증기의 타입 규칙에 있다. JVM은 클래스를 연결할 때 바이트코드의 타입을 검증하지만, 명세는 대입 가능성 검사에서 인터페이스를 Object처럼 취급한다고 적는다(JVMS 4.10.1.2). 검증기는 "이 참조가 가리키는 객체가 Printer를 구현한다"는 것까지는 증명하지 않는다는 뜻이다. javac가 만든 정상적인 클래스 파일에서는 컴파일러의 타입 검사와 checkcast 덕분에 이 검사가 실패할 일이 없지만, JVM은 컴파일러를 믿지 않고 스스로 확인한다.

    피연산자가 두 바이트 더 많은 것은 역사적 흔적이다. count는 인자 값의 개수를 나타내는데(long과 double 값은 2로 센다), 명세의 주석은 이 정보를 메서드의 디스크립터에서도 얻을 수 있으며 중복은 역사적인 것이라고 적는다. 위 javap 출력에서 #51 뒤의 2가 count로, 수신 객체 참조와 String 인자 하나를 합친 값이다. 인자가 없는 scan() 호출에서는 1이 찍힌다. 네 번째 바이트는 항상 0이어야 하고, 호환성을 위해 남아 있다(JVMS 6.5 invokeinterface).

    HotSpot의 구현: vtable과 itable

    여기부터는 명세가 아니라 구현 이야기다. JLS는 동적 메서드 탐색 절차를 설명한 뒤, 이 절차가 실제로는 클래스별 메서드 디스패치 표를 만들고 사용하는 과정에서 암묵적으로 구현되는 경우가 많다고 덧붙인다(JLS 15.12.4.4). 표를 어떻게 만들지는 JVM 구현체의 몫이다. 아래 내용은 OpenJDK 21의 HotSpot 소스(klassVtable.hpp, klassVtable.cpp, instanceKlass.cpp)에서 확인한 것이며, 다른 JVM이나 다른 버전에서는 다를 수 있다.

    HotSpot은 클래스마다 가상 메서드 표(vtable)를 둔다. 자식 클래스의 vtable은 부모 클래스의 vtable을 앞부분에 그대로 복사한 뒤, 자식의 메서드를 하나씩 대조해 재정의이면 복사해 온 칸의 내용을 바꾸고 새 메서드이면 끝에 덧붙여 만든다. 그 결과 어떤 메서드의 칸 번호는 그 메서드를 처음 선언한 클래스와 모든 하위 클래스에서 같다. OfficeDevice.status()가 n번 칸이라면 LaserPrinter에서도 MultiFunctionDevice에서도 n번 칸이다. 그래서 invokevirtual은 수신 객체의 클래스가 무엇이든 "vtable의 n번 칸에 있는 메서드를 실행한다"로 처리할 수 있다. 이 방식이 성립하는 근거는 클래스의 부모가 하나라는 사실이다.

    인터페이스에는 이 근거가 없다. Printer를 구현하는 클래스들은 Object 말고는 공통 부모가 없을 수 있다. 각 클래스는 자기 상속 사슬에 따라 vtable을 만들므로, print가 어느 클래스에서는 앞쪽 칸에, 다른 클래스에서는 뒤쪽 칸에 놓인다. 모든 구현 클래스에 통하는 칸 번호가 없는 것이다. 그래서 HotSpot은 클래스마다 인터페이스 메서드 표(itable)를 따로 둔다. 소스 주석에 그려진 itable의 형식은 두 부분이다. 앞쪽에는 그 클래스가 구현하는 인터페이스마다 "인터페이스, 그 인터페이스용 메서드 표의 위치"를 적은 오프셋 표가 있고, 뒤쪽에는 인터페이스별 메서드 표가 이어진다.

    인터페이스 호출의 기본 경로는 두 단계다. 수신 객체의 클래스에서 오프셋 표를 훑어 해당 인터페이스의 항목을 찾고, 거기서 가리키는 메서드 표를 인터페이스 안에서의 메서드 번호로 읽는다. HotSpot의 탐색 함수는 오프셋 표에서 인터페이스를 찾지 못하면 IncompatibleClassChangeError를, 찾았는데 메서드 칸이 비어 있으면 AbstractMethodError를 던지도록 되어 있다. 앞에서 본 명세의 실행 시점 예외 두 가지가 이 탐색의 두 실패 경우에 대응한다.

    클래스 타입 호출은 고정된 칸 번호로 한 번에 메서드를 찾고, 인터페이스 타입 호출은 인터페이스 항목을 먼저 찾은 뒤 그 인터페이스의 메서드 표에서 찾는 두 단계임을 보여 준다. 위아래 2단 메모리 구조 다이어그램. 흰 배경, 얇은 선, 고정폭 글꼴 느낌. 위쪽 단 제목 "invokevirtual": 왼쪽에 둥근 상자 "수신 객체", 오른쪽으로 화살표가 큰 상자 "클래스 메타데이터"로 연결. 큰 상자 안에 가로로 긴 칸 배열, 라벨 "vtable". 배열의 앞쪽 절반은 회색으로 칠하고 라벨 "부모에게서 복사", 뒤쪽은 흰색이고 라벨 "자식이 추가". 회색 영역의 한 칸을 파랗게 강조하고 아래에 라벨 "n번 칸 = status()". 옆에 초록 글씨 "한 단계". 아래쪽 단 제목 "invokeinterface": 같은 "수신 객체"와 "클래스 메타데이터" 구도. 큰 상자 안에 위쪽 가로 배열 라벨 "itable 오프셋 표", 칸에 "Printer", "PageScanner" 글자. "Printer" 칸에서 아래로 화살표가 내려가 작은 배열 "Printer용 메서드 표"의 칸 "print()"를 가리킴. 화살표에 번호 "①", "②". 옆에 주황 글씨 "두 단계". 그림 맨 아래 작은 글씨 "HotSpot 구현 기준". 단일 상속 덕분에 클래스 메서드는 칸 번호가 고정된다. 인터페이스 메서드는 클래스마다 위치가 달라 한 단계를 더 거친다(HotSpot 구현 기준).

    이 구조를 근거로 "인터페이스 호출은 느리니 피해야 한다"고 결론 내리면 지나치다. 소스에서 확인되는 사실은 기본 경로에 탐색 단계가 하나 더 있다는 것까지다. 실제 실행 시간은 JIT 컴파일러가 호출 지점을 어떻게 최적화하느냐에 따라 달라지고, 이 강좌는 확인하지 않은 수치를 적지 않는다. 여기서 가져갈 것은 속도가 아니라 구조다. 단일 상속이라는 언어의 제약이 메서드 표를 단순하게 만들고, 다중 구현이라는 자유가 표 하나를 더 요구한다.

    둘의 차이를 한 표로 모으면 다음과 같다. Java 21 기준이다.

    고를 때는 "무엇을 물려주려는가"를 먼저 묻는다. 물려주려는 것이 상태와 그 상태를 다루는 코드라면 추상 클래스가 필요하다. 이름과 사용 횟수를 모든 장치가 똑같은 방식으로 관리해야 한다면, 그 필드를 private으로 감추고 생성자에서 채우는 일은 클래스만 할 수 있다. 물려주려는 것이 호출하는 쪽과의 약속뿐이라면 인터페이스가 맞다. 약속에는 상태가 필요 없고, 구현하는 클래스가 이미 다른 부모를 갖고 있어도 지킬 수 있어야 한다.

    다음으로 "누가 이 타입을 쓰는가"를 묻는다. printAll처럼 객체를 받아 쓰는 쪽은 그 객체가 어떤 상태를 어떻게 관리하는지 알 필요가 없다. 받는 쪽이 의존하는 타입은 인터페이스로 두는 편이 구현 클래스에 주는 제약이 가장 적다. 반대로 구현하는 쪽의 중복을 줄이는 것이 목적이라면 추상 클래스가 일을 한다. 그래서 둘을 겹쳐 쓰는 구성이 흔하다. 타입은 인터페이스로 공개하고, 그 인터페이스의 일부를 미리 구현한 추상 클래스를 함께 제공하는 것이다.

    JDK 자체가 이 구성을 쓴다. java.util.List는 인터페이스이고, java.util.AbstractList는 List를 구현하는 추상 클래스다. AbstractList의 Javadoc은 이 클래스가 List 인터페이스의 뼈대 구현을 제공해 구현에 드는 수고를 줄인다고 설명하고, 수정할 수 없는 리스트를 만들려면 이 클래스를 상속해 get(int)와 size()만 구현하면 된다고 적는다. 리스트를 쓰는 코드는 List 타입만 알고, 리스트를 만드는 코드는 AbstractList의 도움을 받는다. 앞 절의 OfficeDevice와 Printer도 같은 역할 분담이다.

    어느 쪽인지 판단이 서지 않을 때 기본값으로 삼을 만한 것은 인터페이스다. 인터페이스로 시작한 타입에 나중에 추상 클래스를 덧붙이는 것은 기존 구현 클래스를 건드리지 않고 할 수 있다. 추상 클래스로 시작한 타입은 모든 구현 클래스의 extends 자리를 이미 차지하고 있어서, 나중에 인터페이스로 바꾸려면 구현 클래스를 전부 고쳐야 하고 앞에서 본 것처럼 호출하는 쪽도 다시 컴파일해야 한다.

    흔한 오해와 함정

    "추상 클래스에는 추상 메서드가 있어야 한다"

    추상 메서드가 있으면 클래스가 추상이어야 하는 것이지, 그 반대는 아니다. 추상 메서드가 하나도 없는 추상 클래스는 문법상 문제가 없고, "직접 생성하지 말고 상속해서 쓰라"는 의도를 표현할 때 쓴다. 명세의 정의가 "불완전하다고 간주해야 하는 클래스"를 포함하는 이유다.

    "생성자에서 추상 메서드를 불러도 안전하다"

    부모 생성자 안에서 추상 메서드를 부르면, 자식의 필드가 초기화되기 전에 자식의 메서드가 실행된다. 부모 생성자가 끝나야 자식의 필드 초기화식이 실행되기 때문이다.

    abstract class Printer {
    protected Printer() {
        selfTest();              // 자식이 구현한 메서드가 실행된다
    }

    abstract void selfTest();
}

class LaserPrinter extends Printer {
    private int toner = 100;

    @Override
    void selfTest() {
        System.out.println("자가 진단: 토너 " + toner + "%");
    }
}

    toner에 100이 들어가는 것은 Printer 생성자가 반환한 다음이므로, 생성자 안에서 호출된 selfTest는 기본값 0을 읽는다. 컴파일 오류도 예외도 없이 틀린 값이 나오는 종류의 버그다. 생성자에서는 재정의될 수 있는 메서드를 호출하지 않는 것이 안전하다.

    "인터페이스 타입으로 부르면 인터페이스의 메서드가 실행된다"

    변수의 타입이 정하는 것은 두 가지뿐이다. 컴파일러가 어떤 호출을 허용하는가, 그리고 어떤 호출 명령을 쓰는가. 어느 본문이 실행되는가는 객체의 클래스가 정한다. 추상 메서드에는 실행할 바이트코드 자체가 없다.

    "인터페이스에 메서드 하나 추가하는 것은 사소한 변경이다"

    인터페이스에 추상 메서드를 추가하면 그 인터페이스를 구현한 모든 클래스가 다음 컴파일에서 오류를 낸다. 구현 클래스가 다른 팀이나 외부 라이브러리에 있다면 문제는 더 미묘하다. 명세상 인터페이스에 추상 메서드를 추가하는 것은 기존 바이너리와의 연결을 깨뜨리지 않으므로(JLS 13.5.4), 다시 컴파일하지 않은 옛 구현 클래스도 로딩과 실행은 된다. 그러다 누군가 새 메서드를 그 객체에 대해 호출하는 순간 그 객체의 클래스에서 구현을 찾을 수 없으므로 AbstractMethodError가 난다. 이미 공개된 인터페이스는 바꾸기 어렵다는 말의 구체적인 내용이 이것이다. default 메서드는 이런 상황에서 옛 구현 클래스와의 호환성을 지키면서 인터페이스에 기능을 더할 수 있게 해 주는 수단이다.

    "인터페이스에 상수를 모아 두면 편하다"

    인터페이스의 필드가 자동으로 public static final이 되는 점을 이용해 상수 묶음으로 쓰는 코드가 있다. 동작은 하지만, 앞에서 본 것처럼 상수 값은 사용하는 클래스 파일로 복사되므로 값을 바꿀 때 사용하는 쪽을 모두 다시 빌드해야 한다. 그리고 그 인터페이스를 implements한 클래스는 상수들을 자기 타입의 공개 멤버로 영구히 노출하게 된다. 인터페이스는 타입과 약속을 선언하는 용도로 쓰고, 상수는 그 약속에 속하는 것만 둔다.

    다음 회차로 이어지는 것

    이 회차에서 얻은 것은 세 가지 도구다. 추상 클래스는 공유 상태와 절차의 뼈대를 물려주면서, 생성 금지와 구현 강제를 컴파일러가 검사하게 한다. 인터페이스는 상태도 구현도 없이 약속만 선언해서, 서로 다른 계층의 클래스들을 한 타입으로 묶고 한 클래스가 여러 약속을 지킬 수 있게 한다. 그리고 그 아래에서 JVM은 두 경우 모두 실제 객체의 클래스를 기준으로 메서드를 선택한다.

    printAll(Printer[] printers, String doc)를 다시 보자. 이 메서드의 소스에는 LaserPrinter도 MultiFunctionDevice도 등장하지 않는다. 컴파일된 바이트코드에도 Printer.print에 대한 invokeinterface 하나만 있다. 새 장치가 열 개 추가되어도 이 메서드는 소스도 바이트코드도 한 글자 바뀌지 않는다. 호출하는 쪽이 인터페이스에만 의존할 때 생기는 이 성질이 다음 회차의 주제다. 11회에서는 이것을 역할과 구현의 분리, 그리고 개방-폐쇄 원칙(OCP)이라는 설계의 언어로 다시 읽는다.

    이 장의 핵심

    추상 클래스는 "불완전한 클래스"이고 인터페이스는 "구현 없는 약속"이다. 클래스 상속이 하나로 제한된 것은 상태와 구현이 두 경로로 내려올 때의 충돌을 없애기 위해서이고, 인터페이스를 여러 개 구현할 수 있는 것은 내려오는 것이 선언뿐이기 때문이다. 변수의 타입은 허용되는 호출과 호출 명령(invokevirtual, invokeinterface)을 정하고, 실행되는 본문은 언제나 객체의 클래스가 정한다.
    다형성 없는 코드의 비용
    공통 상위 타입이 없으면 타입마다 같은 메서드를 반복해 쓰거나 instanceof로 분기해야 한다. 타입 T개와 기능 M개가 곱해져 늘어나고, 분기를 빠뜨려도 컴파일러가 알려 주지 않는다.
    추상 클래스
    불완전하다고 선언한 클래스다. new로 생성할 수 없지만 필드, 생성자, 구체 메서드를 가질 수 있고, 생성자는 자식 인스턴스가 만들어질 때 실행된다(JLS 8.1.1.1).
    추상 메서드
    시그니처만 있고 본문이 없는 메서드다. 추상이 아닌 하위 클래스는 반드시 구현해야 하며, private, static, final과 함께 쓸 수 없다(JLS 8.4.3.1, 8.4.3).
    인터페이스의 암묵적 제어자
    필드는 public static final, 메서드는 public이며 private, default, static이 없으면 abstract다(JLS 9.3, 9.4). 인스턴스 변수와 생성자는 없다.
    구현 메서드의 public
    재정의하는 메서드는 원래 메서드보다 접근 범위를 좁힐 수 없으므로(JLS 8.4.8.3), 인터페이스 메서드를 구현할 때는 public을 명시해야 한다.
    단일 상속과 다중 구현
    클래스를 둘 상속하면 상태와 구현, 생성자 실행이 두 경로로 내려와 충돌한다. 인터페이스는 선언만 물려주므로 여러 개를 구현해도 충돌할 것이 없다.
    호출 모드
    점 앞 식의 컴파일 시점 타입이 인터페이스이면 invokeinterface, 클래스이면 invokevirtual로 컴파일된다(JLS 15.12.3). 실행할 메서드를 고르는 절차는 둘이 같다(JVMS 5.4.6).
    vtable과 itable
    HotSpot 구현에서 클래스 메서드는 상속 사슬 전체에서 칸 번호가 같은 vtable로, 인터페이스 메서드는 인터페이스 항목을 먼저 찾는 itable로 조회한다. 명세가 아니라 구현 세부다.
    선택 기준
    상태와 생성 절차를 공유해야 하면 추상 클래스, 호출하는 쪽과의 약속만 필요하면 인터페이스다. 타입은 인터페이스로 공개하고 공통 구현은 추상 클래스로 돕는 구성도 흔하다.

    실무에서 추상 클래스와 인터페이스 중 무엇을 쓸지는 "이 타입을 누가 구현하는가"에 따라 달라진다. 구현 클래스가 모두 같은 저장소 안에 있고 한 번에 고칠 수 있다면 어느 쪽으로 시작해도 나중에 바꿀 수 있다. 구현 클래스가 다른 팀이나 외부 사용자의 코드에 있다면 사정이 다르다. 공개된 인터페이스에 추상 메서드를 하나 추가하는 일은 모든 구현자의 빌드를 깨뜨리고, 다시 빌드하지 않은 구현은 실행 중에 AbstractMethodError를 낸다. 그런 인터페이스는 처음부터 메서드를 적게 두고, 확장이 필요해지면 default 메서드나 별도의 하위 인터페이스로 푸는 쪽을 검토한다.

    추상 클래스로 절차의 뼈대를 물려주는 방식은 중복을 확실히 줄여 주지만, 자식 클래스가 부모의 내부 동작에 묶이는 대가가 있다. 부모가 어떤 순서로 추상 메서드를 부르는지, 생성자에서 무엇을 하는지가 바뀌면 자식의 동작이 달라진다. 생성자에서 재정의 가능한 메서드를 부르는 코드는 이 결합이 가장 나쁜 형태로 드러나는 경우다. 공유하려는 것이 상태가 아니라 몇 줄의 계산이라면, 상속 대신 그 계산을 가진 객체를 필드로 받아 쓰는 구성도 선택지가 된다. 이 방향은 다음 회차의 역할과 구현 분리로 이어진다.

    운영 중에 IncompatibleClassChangeError, AbstractMethodError, InstantiationError를 만났다면 코드의 논리 오류보다 따로 컴파일된 클래스 파일끼리의 불일치를 먼저 의심한다. 이 오류들은 클래스였던 것이 인터페이스로 바뀌었거나, 인터페이스에 메서드가 추가되었거나, 일반 클래스가 추상 클래스로 바뀌었는데 호출하는 쪽이 옛 버전을 기준으로 컴파일되어 있을 때 나온다. 대개 의존 라이브러리의 버전이 섞인 것이 원인이므로, 클래스패스에 같은 라이브러리의 다른 버전이 함께 올라와 있는지부터 확인하는 것이 빠르다.

    인터페이스 호출의 비용을 이유로 설계를 바꾸는 것은 측정한 뒤의 일이다. HotSpot의 itable 조회에 단계가 하나 더 있다는 것은 사실이지만, 그 차이가 프로그램 전체에서 의미가 있는지는 호출 빈도와 JIT 최적화에 달려 있어 코드를 읽는 것만으로는 알 수 없다. 대부분의 업무 코드에서는 타입을 인터페이스로 두어 얻는 변경 용이성이 훨씬 큰 값을 가진다.

    interface Greeter {
    String PREFIX = "안녕, ";

    String greet(String name);
}

abstract class BaseGreeter implements Greeter {
    private int count;

    @Override
    public String greet(String name) {
        count++;
        return PREFIX + decorate(name) + " (" + count + ")";
    }

    protected abstract String decorate(String name);
}

class LoudGreeter extends BaseGreeter {
    @Override
    protected String decorate(String name) {
        return name.toUpperCase() + "!";
    }
}

class PoliteGreeter extends BaseGreeter {
    @Override
    protected String decorate(String name) {
        return name + "님";
    }
}

public class GreetMain {
    public static void main(String[] args) {
        Greeter a = new LoudGreeter();
        Greeter b = new PoliteGreeter();
        System.out.println(a.greet("kim"));
        System.out.println(a.greet("lee"));
        System.out.println(b.greet("park"));
    }
}

LaserPrinter의 usage는 인쇄 한 번으로 1, 복합기의 usage는 인쇄 한 번과 스캔 한 번으로 2다. 복합기 객체를 가리키는 참조는 넷이다. 지역 변수 mfd(MultiFunctionDevice 타입), printers[1](Printer 타입), 지역 변수 scanner(PageScanner 타입), devices[1](OfficeDevice 타입)이다. Printer는 인터페이스이고 OfficeDevice는 추상 클래스이므로 둘 다 인스턴스를 만들 수 없다. OfficeDevice에 선언된 name과 usage는 자식 객체 안의 필드로 존재하고, Printer는 객체의 메모리에 아무것도 보태지 않고 그 객체를 가리킬 수 있는 타입만 하나 늘린다. 완료 기준: 그림에 객체가 정확히 넷(문자열 제외)이고, 복합기 객체로 들어오는 화살표가 넷이다.

    4번. 인터페이스로 선언한다. 예를 들어 interface PowerSaving { void sleep(); }를 두고 두 클래스가 각자의 extends는 유지한 채 implements PowerSaving을 더한다. 추상 클래스로는 안 되는 이유는 두 클래스가 이미 서로 다른 부모(StorageDevice, OfficeDevice)를 갖고 있고 클래스는 부모를 하나만 가질 수 있기 때문이다. 두 계층의 꼭대기에 공통 추상 클래스를 끼워 넣는 방법은 절전 기능이 없는 다른 장치들까지 그 타입에 속하게 만든다. 반복문 for (PowerSaving d : devices) d.sleep();의 호출은 d의 선언 타입이 인터페이스이므로 invokeinterface PowerSaving.sleep으로 컴파일되고, 실행 중에 각 객체의 클래스에서 sleep이 선택된다.

    5번. MAX_PAGES는 인터페이스 필드이므로 public static final이고, int 리터럴로 초기화되었으므로 상수 변수다. 상수 변수에 대한 참조는 컴파일할 때 값으로 바뀌므로(JLS 13.1), PrintQueue.class 안에는 Limits.MAX_PAGES를 읽는 명령이 없고 숫자 50이 직접 들어 있다. Limits만 다시 컴파일해서는 PrintQueue.class의 50이 바뀌지 않는다. 해결은 PrintQueue를 포함해 그 상수를 쓰는 모든 클래스를 다시 컴파일하는 것이다. 운영 중에 바뀔 수 있는 값이라면 애초에 컴파일 시점 상수로 두지 말고 메서드로 읽거나 설정에서 읽게 한다.

     Printer가 인터페이스이고 LaserPrinter가 이를 구현한 클래스일 때, Printer p = new LaserPrinter("A"); p.print("문서");에 대한 설명으로 옳은 것은? Printer.print에 본문이 없으므로 p.print 호출은 컴파일되지 않는다. 객체가 LaserPrinter이므로 컴파일러는 invokevirtual LaserPrinter.print를 만든다. invokeinterface Printer.print로 컴파일되고, 실행 중에 객체의 클래스를 기준으로 LaserPrinter.print가 선택된다. 실행 중에 Printer.print가 선택되어 AbstractMethodError가 발생한다. 호출 명령은 변수의 선언 타입으로 정해진다. 선언 타입이 인터페이스이므로 invokeinterface이고 심벌릭 참조는 Printer.print다. 실행할 메서드는 수신 객체의 클래스에서 출발해 찾으므로 LaserPrinter.print가 선택된다. 컴파일러는 객체의 실제 클래스를 기준으로 명령을 고르지 않으며, 구현을 찾지 못해 AbstractMethodError가 나는 일은 구현 클래스가 그 메서드를 구현하지 않은 불일치 상황에서만 일어난다. 추상 클래스는 new로 생성할 수 없는데도 생성자를 가질 수 있다. 그 생성자의 역할로 옳은 것은? 추상 클래스의 static 필드를 초기화하기 위해 클래스 로딩 때 한 번 실행된다. 자식 클래스의 인스턴스가 만들어질 때 super(...)를 통해 실행되어, 그 객체 안에 있는 부모 쪽 필드를 초기화한다. 추상 클래스 타입의 배열을 만들 때 각 칸을 채우기 위해 실행된다. 실행되는 일이 없고, 문법상 허용될 뿐이다. 추상 클래스에 선언한 인스턴스 필드는 자식 객체 안에 실제로 존재하며, 자식을 인스턴스화하면 추상 클래스의 생성자가 실행된다(JLS 8.1.1.1). static 초기화는 생성자가 아니라 클래스 초기화의 일이고, 배열 생성은 참조를 담을 칸만 만들 뿐 원소 타입의 생성자를 부르지 않는다. 자바가 클래스의 다중 상속은 금지하면서 인터페이스의 다중 구현은 허용하는 근본 이유는? 클래스는 인스턴스 상태와 메서드 구현을 물려주므로 두 경로로 내려오면 충돌하지만, 인터페이스는 상태가 없고 추상 메서드에는 구현이 없어 충돌할 것이 없기 때문이다. 인터페이스 호출이 클래스 메서드 호출보다 항상 빠르기 때문이다. 인터페이스는 컴파일 후 클래스 파일로 만들어지지 않아 실행 중에 존재하지 않기 때문이다. 인터페이스의 메서드는 static이라서 객체와 무관하기 때문이다. 다이아몬드 문제의 원인은 필드가 몇 벌 있어야 하는지, 어느 구현을 실행할지, 공통 조상의 생성자를 몇 번 실행할지가 정해지지 않는다는 것이다. 인터페이스에는 인스턴스 변수와 생성자가 없고 추상 메서드에는 본문이 없으므로 이 질문들이 생기지 않는다. 인터페이스도 클래스 파일로 컴파일되고, 그 추상 메서드는 인스턴스 메서드이며, 호출 속도는 허용 여부의 이유가 아니다. 인터페이스의 메서드를 구현하는 클래스에서 public을 빼고 void print(String doc) { ... }라고 쓰면 컴파일 오류가 난다. 이유는? 인터페이스를 구현한 클래스는 반드시 public 클래스여야 하기 때문이다. 접근 제어자를 생략하면 메서드가 private이 되기 때문이다. @Override 애너테이션을 붙이지 않았기 때문이다. 인터페이스의 메서드는 암묵적으로 public이고, 재정의하는 메서드는 원래 메서드보다 접근 범위를 좁힐 수 없기 때문이다. 인터페이스 메서드는 접근 제어자를 쓰지 않아도 public이다(JLS 9.4). 클래스에서 제어자를 생략하면 패키지 접근이 되어 접근 범위가 좁아지는데, 이는 JLS 8.4.8.3이 금지한다. 범위를 좁힐 수 있다면 부모 타입 변수로는 되는 호출이 자식 타입 변수로는 안 되는 모순이 생긴다. 구현 클래스 자체가 public일 필요는 없고, @Override는 선택 사항이다. HotSpot이 인터페이스 메서드 호출에 vtable의 고정 칸 번호를 그대로 쓰지 못하고 itable을 따로 두는 이유는? 인터페이스 메서드는 실행 중에 이름 문자열을 비교해서만 찾을 수 있도록 명세가 정했기 때문이다. 한 인터페이스를 구현하는 클래스들이 공통 부모 클래스를 갖지 않을 수 있어, 그 메서드가 놓이는 vtable 칸 번호가 클래스마다 달라질 수 있기 때문이다. 인터페이스에는 인스턴스 필드가 있어서 객체 크기가 달라지기 때문이다. JVM 명세가 itable이라는 자료 구조를 사용하도록 요구하기 때문이다. vtable의 칸 번호가 고정되는 것은 자식이 부모의 표를 앞부분에 복사해 쓰기 때문이고, 이는 부모가 하나일 때만 성립한다. 인터페이스 구현 클래스들은 서로 다른 상속 사슬에 있을 수 있으므로 공통 번호가 없다. 명세는 메서드 선택의 결과만 정하고 표의 형태는 정하지 않는다. itable은 HotSpot의 구현 세부다.
    추상 클래스(abstract class)
    abstract로 선언해 불완전하다고 표시한 클래스. 인스턴스를 직접 만들 수 없고, 추상 메서드를 가질 수 있다.
    추상 메서드(abstract method)
    시그니처, 반환 타입, throws 절만 선언하고 구현을 제공하지 않는 메서드. 클래스 파일에서 Code 속성이 없다.
    구체 메서드(concrete method)
    추상이 아닌, 본문이 있는 메서드. JLS 8.4.3.1의 용어다.
    인터페이스(interface)
    인스턴스 변수 없이 상수와 메서드 선언으로 이루어진 참조 타입. 클래스가 implements로 구현하며 여러 개를 동시에 구현할 수 있다.
    상수 변수(constant variable)
    기본형이나 String 타입의 final 변수로 상수식으로 초기화된 것. 참조하는 코드에 컴파일 시점에 값이 복사된다.
    다이아몬드 문제(diamond problem)
    한 클래스가 공통 조상을 가진 두 부모를 상속할 때 상태와 구현이 두 경로로 내려와 어느 것을 쓸지 정할 수 없게 되는 문제.
    호출 모드(invocation mode)
    컴파일러가 메서드 호출마다 계산하는 값(static, super, interface, virtual). 어떤 호출 명령을 쓸지를 정한다(JLS 15.12.3).
    invokeinterface
    인터페이스 메서드에 대한 심벌릭 참조로 인스턴스 메서드를 호출하는 JVM 명령. 수신 객체의 클래스를 기준으로 메서드를 선택한다.
    vtable / itable
    HotSpot이 클래스 메타데이터 안에 두는 메서드 표. vtable은 클래스 메서드용, itable은 인터페이스 메서드용이다. 명세가 아닌 구현 세부다.
    뼈대 구현(skeletal implementation)
    인터페이스의 일부를 미리 구현해 둔 추상 클래스. java.util.AbstractList가 예다.
