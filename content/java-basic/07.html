    바뀌면 안 되는 값을 누가 지키는가

    프로그램에는 한 번 정해지면 바뀌면 안 되는 값이 많다. 회원의 식별자, 회의실의 정원, 시스템이 허용하는 최대 접속자 수 같은 것들이다. 그런데 지금까지 배운 변수는 언제든 다시 대입할 수 있다. "바뀌면 안 된다"는 사실은 코드를 쓴 사람의 머릿속이나 주석에만 있고, 컴파일러와 JVM은 그 약속을 알지 못한다.

    public class MeetingRoom {
    int capacity = 4;      // 정원. 만들어진 뒤에는 바뀌면 안 된다(는 약속)
}

public class MeetingRoomMain {
    public static void main(String[] args) {
        MeetingRoom room = new MeetingRoom();
        room.capacity = 400;                 // 약속을 어겼지만 컴파일된다
        System.out.println(room.capacity);
    }
}
    400

    주석은 실행되지 않는다. 그래서 이 코드는 아무 경고 없이 컴파일되고 400을 출력한다. 더 큰 문제는 이런 대입이 MeetingRoom을 만든 곳에서 멀리 떨어진 코드에서, 한참 뒤에, 다른 사람의 손으로 일어난다는 점이다. 정원이 400이 된 회의실은 예약 검증을 통과하고, 잘못은 전혀 다른 화면에서 드러난다. 값이 바뀐 지점과 증상이 나타난 지점이 멀수록 원인을 찾는 비용은 커진다.

    final은 이 약속을 사람에게서 컴파일러로 옮기는 키워드다. 자바 언어 명세(JLS §4.12.4)의 정의는 짧다. final 변수에는 한 번만 대입할 수 있다. 두 번째 대입을 시도하는 코드는 실행되기 전에, 컴파일 단계에서 거부된다. 버그가 실행 중의 증상이 아니라 빌드 실패로 나타나게 되는 것이다.

    이 회차는 이 한 문장이 변수의 종류마다 어떤 모습으로 나타나는지를 차례로 본다. 지역 변수와 매개변수, 인스턴스 필드, static 필드의 순서다. 그 과정에서 컴파일러가 "한 번"을 어떻게 세는지, 상수라고 부르는 것이 클래스 파일에서 실제로 어떻게 취급되는지, final을 붙였는데도 객체의 내용이 바뀌는 이유가 무엇인지를 확인한다.

    final은 변수 말고 클래스와 메서드에도 붙는다. 그때의 뜻은 "상속할 수 없다", "오버라이딩할 수 없다"이다. 상속을 알아야 설명할 수 있으므로 다음 회차에서 다룬다.

    final 지역 변수와 매개변수

    가장 단순한 형태부터 보자. 지역 변수에 final을 붙이면 그 변수에는 한 번만 값을 넣을 수 있다. 선언과 동시에 초기화해도 되고, 선언만 해 두었다가 나중에 한 번 대입해도 된다. 선언에 초기화 식이 없는 final 변수를 JLS는 blank final이라고 부른다.

    public class LocalFinal {
    static int grade(int score) {
        final int max = 100;          // 선언과 동시에 초기화
        final int bonus;              // blank final: 아직 값이 없다
        if (score >= 90) {
            bonus = 10;               // 이 경로에서 한 번
        } else {
            bonus = 0;                // 저 경로에서 한 번
        }
        return Math.min(score + bonus, max);
    }

    public static void main(String[] args) {
        System.out.println(grade(95));
        System.out.println(grade(70));
    }
}
    100
70

    bonus = 10과 bonus = 0이라는 대입문이 소스에 두 번 적혀 있지만 오류가 아니다. "한 번"은 소스에 적힌 대입문의 개수가 아니라 실행 경로를 기준으로 센다. 어떤 실행에서도 bonus에 대입이 두 번 일어날 수 없으므로 규칙을 지킨 것이다. grade(95)는 95 + 10 = 105를 100으로 잘라 100을, grade(70)은 70 + 0 = 70을 돌려준다.

    반대로 아래 코드는 줄마다 다른 이유로 컴파일되지 않는다. 오류 메시지는 JDK 21의 javac가 실제로 출력하는 문구다.

    public class LocalFinalError {
    static void m1(boolean flag) {
        final int a;
        if (flag) {
            a = 1;
        }
        System.out.println(a);      // (1) variable a might not have been initialized
    }

    static void m2() {
        final int b;
        b = 1;
        b = 2;                      // (2) variable b might already have been assigned
    }

    static void m3() {
        final int c;
        for (int i = 0; i < 3; i++) {
            c = i;                  // (3) variable c might be assigned in loop
        }
    }

    static void m4(final int d) {
        d = 10;                     // (4) final parameter d may not be assigned
    }
}

    (1)은 final과 무관하게 모든 지역 변수에 적용되는 규칙이다. flag가 false인 경로에서는 a에 값이 없는 채로 읽게 된다. (2)는 가장 직접적인 위반이다. (3)은 반복문이 두 번째 바퀴를 돌 때 이미 대입된 변수에 다시 대입하게 되므로 거부된다. (4)는 매개변수다. 매개변수는 메서드가 호출되는 순간 인자 값으로 이미 한 번 초기화된 변수이므로, final 매개변수에는 메서드 본문에서 대입할 기회가 아예 없다.

    final 매개변수가 호출하는 쪽에 주는 영향은 없다. 자바는 인자를 값으로 전달하므로 매개변수는 호출자의 변수와 별개인 복사본이다. 매개변수에 final이 붙든 안 붙든 호출자의 변수는 바뀌지 않는다. final 매개변수는 "이 메서드 안에서 이 변수를 다른 값으로 덮어쓰지 않겠다"는, 메서드 구현 내부를 향한 약속이다. 메서드 시그니처는 이름과 매개변수 타입으로 정해지므로(JLS §8.4.2) final 여부는 시그니처에 들어가지 않는다.

    컴파일러는 "한 번"을 어떻게 세는가: 확정 할당과 확정 미할당

    메시지에 들어 있는 "might"라는 단어에 주목하자. 컴파일러는 프로그램을 실행해 보지 않는다. 조건식의 값이 실행 중에 무엇이 될지 모르는 상태에서, 가능한 모든 실행 경로를 놓고 판정해야 한다. JLS 16장은 이 판정을 두 개의 성질로 정의한다.

    • 확정 할당(definitely assigned): 어떤 지점에 도달하는 모든 경로에서 그 변수에 대입이 이미 일어났다. 변수를 읽으려면 그 지점에서 확정 할당 상태여야 한다.
    • 확정 미할당(definitely unassigned): 어떤 지점에 도달하는 모든 경로에서 그 변수에 대입이 아직 한 번도 일어나지 않았다. blank final 변수에 대입하려면 그 지점에서 확정 미할당 상태여야 한다.

    일반 지역 변수에는 첫 번째 규칙만 적용된다. final 변수에는 두 규칙이 모두 적용된다. 읽기 전에는 "반드시 대입됐음"을, 쓰기 전에는 "반드시 대입된 적 없음"을 컴파일러가 증명할 수 있어야 한다. 두 성질은 서로의 부정이 아니라는 점이 중요하다. 어떤 경로에서는 대입됐고 다른 경로에서는 안 됐다면, 그 지점은 확정 할당도 아니고 확정 미할당도 아니다. 그런 지점에서는 읽을 수도, 대입할 수도 없다.

    final int bonus;                     상태: 확정 미할당
        │
   score >= 90 ?
   ┌────┴─────┐
  true       false
   │          │
bonus = 10  bonus = 0                두 대입 모두 직전 상태가 확정 미할당 → 허용
   │          │
   └────┬─────┘
        ▼
return score + bonus;                모든 경로에서 대입됨 → 확정 할당 → 읽기 허용

    이 분석은 보수적이다. 컴파일러는 조건식끼리의 논리적 관계를 추론하지 않는다. 다음 코드를 사람이 읽으면 a에는 정확히 한 번 대입된다. flag가 true면 첫 번째 if에서, false면 두 번째 if에서다. 그러나 컴파일러는 두 조건이 서로 배타적이라는 사실을 이용하지 않는다.

    static void m(boolean flag) {
    final int a;
    if (flag) {
        a = 1;
    }
    if (!flag) {
        a = 2;                  // error: variable a might already have been assigned
    }
    System.out.println(a);      // error: variable a might not have been initialized
}

    첫 번째 if가 끝난 지점에서 a는 "대입됐을 수도, 안 됐을 수도 있는" 상태다. 따라서 두 번째 if 안의 대입은 확정 미할당 조건을 만족하지 못하고, 마지막 줄의 읽기는 확정 할당 조건을 만족하지 못한다. 한 변수에 대해 "이미 대입됐을 수 있다"와 "아직 초기화되지 않았을 수 있다"라는 오류가 동시에 나오는 것은 모순이 아니라, 두 성질 중 어느 쪽도 증명되지 않았다는 뜻이다. 이런 코드는 if-else로 고쳐 쓰면 통과한다.

    예외 처리에서도 같은 일이 생긴다. try 블록에서 대입하고 catch 블록에서 대체 값을 대입하는 코드는 일반 변수라면 문제가 없지만 final 변수라면 거부된다. 컴파일러가 보기에 예외는 try 블록의 어느 지점에서든 던져질 수 있으므로, catch 블록에 들어왔을 때 대입이 이미 끝났을 가능성을 배제할 수 없기 때문이다.

    static int parse(String text) {
    final int n;
    try {
        n = Integer.parseInt(text);
    } catch (NumberFormatException e) {
        n = -1;                 // error: variable n might already have been assigned
    }
    return n;
}

    지역 변수의 final은 실행 시간의 잠금장치가 아니다

    이 검사는 전부 컴파일 시점의 일이다. 위의 grade 메서드에서 bonus의 final을 지우고 다시 컴파일해도 바이트코드는 한 글자도 달라지지 않는다. javap -c로 본 결과는 다음과 같다.

       1: bipush        90
       3: if_icmplt     12
       6: bipush        10
       8: istore_1

      12: iconst_0

      22: ireturn

    bonus는 1번 지역 변수 슬롯에 istore_1로 저장되고 iload_1로 읽힌다. JVM의 지역 변수는 스택 프레임 안의 번호 붙은 칸일 뿐이고, 칸마다 "변경 금지" 표시를 다는 장치는 없다. 지역 변수의 final은 소스 코드를 읽는 사람과 컴파일러 사이의 계약이다. 이 점은 뒤에서 볼 필드의 final과 다르다. 필드의 final은 클래스 파일에 기록되고 JVM도 그것을 검사한다.

    그런데 이 바이트코드에는 눈에 띄는 점이 하나 있다. max라는 변수가 보이지 않는다. 슬롯에 저장하는 명령도 읽는 명령도 없고, Math.min을 호출하기 직전에 bipush 100으로 숫자 100이 직접 스택에 올라간다. max의 final을 지우면 이 부분은 달라져서 100을 슬롯에 저장했다가 다시 읽는 코드가 된다. 리터럴로 초기화한 final 변수는 컴파일러가 변수가 아니라 값 자체로 취급한다는 뜻이다. 이것이 뒤에서 다룰 상수 변수의 첫 번째 모습이다.

    final을 붙이지 않았더라도 초기화 뒤에 한 번도 다시 대입되지 않는 지역 변수를 JLS는 사실상 final(effectively final)이라고 부른다(§4.12.4). 지역 클래스, 익명 클래스, 람다가 바깥의 지역 변수를 사용할 때 이 성질이 요구된다. 그 이유는 중급 1편의 중첩 클래스 회차에서 변수 캡처와 함께 다룬다.

    final 필드 ①: 생성자에서 한 번, 그 뒤로는 읽기만

    인스턴스 필드에 final을 붙이면 "이 객체가 만들어지는 동안 한 번 정해지고, 그 뒤로는 바뀌지 않는 값"이 된다. 회원의 식별자가 좋은 예다. 별명은 바꿀 수 있어도 식별자가 바뀌면 그것은 다른 회원이다.

    public class Member {
    private final String id;          // blank final: 생성자에서 한 번 정한다
    private String nickname;          // 언제든 바꿀 수 있다

    public Member(String id, String nickname) {
        this.id = id;
        this.nickname = nickname;
    }

    public Member(String id) {

    final 인스턴스 필드에 값을 넣을 수 있는 자리는 세 곳이다. 필드 선언의 초기화 식, 인스턴스 초기화 블록, 그리고 생성자다. 일반 메서드에서는 대입할 수 없다. JLS §8.3.1.2는 blank final 인스턴스 변수가 그 클래스의 모든 생성자의 끝에서 확정 할당 상태여야 한다고 규정한다. 지역 변수에서 본 흐름 분석이 생성자 단위로 그대로 적용되는 것이다.

    public class MemberError {
    private final String id;
    private final int level;

    public MemberError(String id) {
        this.id = id;
    }                               // (1) error: variable level might not have been initialized

    public MemberError(String id, int level) {
        this(id);
        this.level = level;         // (2) error: variable level might already have been assigned
    }

    public void rename(String id) {
        this.id = id;               // (3) error: cannot assign a value to final variable id
    }
}

    (1)은 생성자가 끝나는 지점에서 level이 대입되지 않았기 때문이다. 오류 위치가 생성자의 닫는 중괄호라는 점이 "생성자의 끝에서 검사한다"는 규칙을 그대로 보여 준다. (3)은 생성자가 아닌 메서드에서의 대입이므로 흐름 분석을 할 것도 없이 거부된다. 실제로 JDK 21의 javac로 이 파일을 컴파일하면 (3)만 먼저 보고되고, (3)을 지운 뒤에야 흐름 분석 단계의 오류인 (1)과 (2)가 보고된다.

    (2)는 조금 미묘하다. this(id)로 같은 클래스의 다른 생성자에게 일을 넘기면, 넘겨받은 생성자가 모든 blank final 필드를 채웠어야 한다. 그래서 JLS §16.9는 this(...) 호출 직후에 모든 blank final 필드를 확정 할당 상태로 간주한다. 그 뒤에 오는 대입은 "이미 대입된 변수에 다시 대입"이 되어 거부된다. final 필드를 가진 클래스에서 생성자를 여러 개 둘 때는 실제로 필드를 채우는 생성자를 하나로 정하고 나머지는 this(...)로 그 생성자에 위임하는 구조가 자연스럽게 만들어진다.

    인스턴스 필드에 값을 쓰는 바이트코드 명령은 putfield다. JVM 명세(JVMS §6.5 putfield)는 대상 필드가 final이면 그 필드가 현재 클래스에 선언돼 있어야 하고, 명령이 그 클래스의 인스턴스 초기화 메서드(, 생성자가 컴파일된 것) 안에 있어야 하며, 그렇지 않으면 IllegalAccessError를 던진다고 규정한다. 컴파일러를 거치지 않고 만들어진 클래스 파일이 final 필드를 덮어쓰려 해도 JVM이 막는다는 뜻이다. final 필드는 컴파일러와 JVM이 이중으로 지키는 약속이다.

    final 필드도 기본값에서 출발한다

    final 필드는 "값이 하나뿐인 필드"처럼 보이지만 엄밀히는 그렇지 않다. 객체를 만드는 과정을 다시 떠올려 보자. new가 실행되면 먼저 힙에 객체의 공간이 잡히고 모든 필드가 타입별 기본값(숫자는 0, boolean은 false, 참조는 null)으로 채워진다(JLS §4.12.5, §15.9.4). 생성자는 그다음에 실행된다. final 필드도 예외가 아니어서, 생성자가 대입하기 전까지는 기본값을 담고 있다.

    컴파일러는 생성자 안에서 대입 전에 final 필드를 직접 읽는 코드를 막는다. this.limit = limit; 앞에서 System.out.println(this.limit);을 쓰면 "variable limit might not have been initialized" 오류가 난다. 하지만 메서드 호출을 한 번 거치면 컴파일러의 시야에서 벗어난다.

    public class Leak {
    private final int limit;

    public Leak(int limit) {
        print();                 // 아직 limit에 대입하기 전
        this.limit = limit;
        print();
    }

    private void print() {
        System.out.println("limit = " + limit);
    }

    public static void main(String[] args) {
        new Leak(50);
    }
}
    limit = 0
limit = 50

    같은 final 필드가 한 번은 0으로, 한 번은 50으로 읽혔다. 확정 할당 분석은 생성자나 메서드 하나의 본문 안에서만 이루어진다. print()의 본문은 그 자체로 아무 문제가 없는 코드이고, 컴파일러는 "이 메서드가 생성자의 어느 시점에 호출되는가"까지 따라가지 않는다. 그래서 final 필드가 보장하는 것을 정확히 말하면 "값이 항상 같다"가 아니라 "대입은 한 번뿐이다"이고, "항상 같은 값으로 보인다"는 보장은 생성자가 끝난 뒤부터 성립한다.

    여기서 실용적인 규칙이 하나 나온다. 생성자 안에서는 필드를 모두 채우기 전에 this를 통해 다른 코드를 실행시키지 않는다. 자기 메서드를 호출하는 것, this를 다른 객체에 넘기는 것이 모두 해당한다. 이 문제는 다음 회차에서 더 날카로운 형태로 다시 나온다. 부모 클래스의 생성자가 호출한 메서드가 자식 클래스에서 오버라이딩돼 있으면, 자식의 final 필드가 채워지기도 전에 그 메서드가 실행된다.

    final 필드 ②: 모든 객체가 같은 값을 갖는다면 static final

    final 인스턴스 필드를 선언과 동시에 초기화하면 어떻게 될까. 예를 들어 별명의 최대 길이를 Member에 private final int maxNicknameLength = 12;로 두었다고 하자. 이 필드는 생성자가 값을 정할 여지가 없으므로 모든 Member 객체에서 12다. 그런데 인스턴스 필드는 객체마다 따로 존재한다. 회원이 십만 명이면 힙에는 12라는 같은 값이 십만 개 들어 있게 된다.

    낭비도 문제지만 의미가 더 문제다. 인스턴스 필드는 "객체마다 다를 수 있는 상태"를 나타내는 자리인데, 이 값은 객체의 상태가 아니라 클래스 전체에 대한 사실이다. 앞 회차에서 본 것처럼 클래스에 하나만 존재하는 값은 static 필드로 둔다. final과 static을 함께 붙이면 "클래스에 하나뿐이고, 한 번 정해지면 바뀌지 않는 값"이 된다. 자바에서 흔히 상수(constant)라고 부르는 것이 이것이다.

    public class Policy {
    public static final int MAX_USERS = 100;
    public static final String ID_PREFIX = "user-";
}

    상수의 이름은 대문자와 밑줄로 쓰는 것이 관례다. 사용하는 쪽에서는 Policy.MAX_USERS처럼 클래스 이름으로 접근한다. 코드 곳곳에 100이라는 숫자를 직접 쓰는 대신 상수를 쓰면 두 가지를 얻는다. 숫자에 이름이 붙어 의미가 드러나고, 값을 바꿀 때 고칠 곳이 한 군데가 된다.

    static final 필드도 blank final일 수 있다. 그 경우에는 생성자가 아니라 static 초기화 블록에서 대입해야 한다. static 필드는 객체가 아니라 클래스에 속하므로, "한 번"의 기준이 객체 생성이 아니라 클래스 초기화이기 때문이다(JLS §8.3.1.2). 대입하지 않으면 필드 선언 위치에서 "variable MAX might not have been initialized" 오류가 난다.

    public class Limits {
    static final int MIN;
    static final int MAX;           // error: variable MAX might not have been initialized

    static {
        MIN = 1;
    }
}

    상수 변수와 컴파일 타임 상수: 값이 사용하는 쪽으로 복사된다

    "static final이면 상수"라는 일상적인 말과 별개로, 자바 언어 명세에는 상수 변수(constant variable)라는 정확한 용어가 있다. JLS §4.12.4의 정의는 이렇다. 상수 변수란 기본형 또는 String 타입의 final 변수 중에서 상수 표현식(constant expression)으로 초기화된 것이다. 세 조건이 모두 필요하다. final이어야 하고, 타입이 기본형이나 String이어야 하고, 초기화 식이 상수 표현식이어야 한다.

    상수 표현식은 JLS §15.29가 정의한다. 컴파일러가 프로그램을 실행하지 않고도 값을 계산할 수 있는 식이라고 이해하면 된다. 기본형 리터럴과 문자열 리터럴, 그것들에 대한 산술·비교·논리·비트 연산, 기본형이나 String으로의 형변환, 삼항 연산자, 그리고 다른 상수 변수의 이름으로만 구성된 식이다. 메서드 호출, new, 증감 연산자, instanceof가 하나라도 들어가면 상수 표현식이 아니다.

    선언상수 변수인가이유

    static final String ID_PREFIX = "user-";예String, 리터럴

    static final Integer BOXED = 100;아니오타입이 기본형도 String도 아니다
    static final int PARSED = Integer.parseInt("100");아니오메서드 호출은 상수 표현식이 아니다
    static final long STARTED = System.currentTimeMillis();아니오메서드 호출
    static final int[] LEVELS = {1, 2, 3};아니오배열은 기본형도 String도 아니다
    final int max = 100; (지역 변수 또는 인스턴스 필드)예static 여부는 조건이 아니다

    이 구분이 왜 중요한가. 상수 변수는 컴파일러가 변수로 취급하지 않기 때문이다. 상수 변수를 읽는 코드는 "그 변수에 가서 값을 읽어 온다"가 아니라 "그 값 자체"로 컴파일된다. JLS §13.1은 상수 변수인 필드에 대한 참조가 컴파일 시점에 값으로 치환되어야 하고, static 상수 변수라면 그 필드에 대한 참조가 바이너리 코드에 남지 않아야 한다고 규정한다. 흔히 상수 인라이닝(inlining)이라고 부르는 동작이다. 직접 확인해 보자.

    public class Policy {
    public static final int MAX_USERS = 100;                        // 상수 변수
    public static final int PARSED_MAX = Integer.parseInt("100");   // 상수 변수가 아니다

    static {
        System.out.println("Policy 클래스 초기화");
    }
}

    public static void main(String[] args) {

        System.out.println("MAX_USERS = " + a);
        int b = Policy.PARSED_MAX;

    JLS §13.4.9는 이 현상을 직접 언급하면서, 널리 배포되는 코드에서는 static 상수 변수를 정말로 바뀔 일이 없는 값에만 쓰라고 권고한다. 수학 상수 같은 것이 그렇다. 버전 번호, 제한 값, 서버 주소처럼 나중에 바뀔 수 있는 값을 다른 모듈에 공개해야 한다면, 필드 대신 값을 돌려주는 메서드를 제공하거나 위의 PARSED_MAX처럼 상수 변수가 되지 않는 형태로 초기화하는 방법이 있다.

[Policy.java만 500으로 고쳐 다시 컴파일]

    상수 변수의 값이 사용하는 클래스 파일에 복사되고, 정의한 쪽만 다시 컴파일하면 옛 값이 남는다는 것을 두 단계로 보여 준다. 흰 배경의 2단 비교 다이어그램. 위쪽 단 제목 "처음 컴파일", 아래쪽 단 제목 "Policy만 다시 컴파일". 각 단에는 문서 모양 아이콘 두 개가 좌우로 놓인다. 위쪽 단: 왼쪽 문서 라벨 "Policy.class" 안에 "MAX_USERS = 100", 오른쪽 문서 라벨 "PolicyMain.class" 안에 "bipush 100". 왼쪽에서 오른쪽으로 가는 굵은 화살표에 "값 복사" 라벨. 아래쪽 단: 왼쪽 문서 "Policy.class" 안의 값이 "MAX_USERS = 500" 으로 바뀌어 초록색으로 강조되고, 오른쪽 문서 "PolicyMain.class" 안의 "bipush 100" 은 빨간 테두리로 강조되며 옆에 "옛 값 그대로" 라벨. 아래쪽 단에는 두 문서 사이에 화살표가 없고 끊어진 점선만 있다. 색은 회색, 초록, 빨강만 사용하고 글자는 고딕체로 선명하게. 상수 변수는 읽는 쪽 클래스 파일에 값으로 복사된다. 정의한 쪽만 다시 컴파일하면 두 클래스가 서로 다른 값을 갖게 된다.

    결과 3: 상수 표현식이 필요한 자리에 쓸 수 있다

    자바 문법에는 컴파일 시점에 값이 정해져 있어야 하는 자리가 있다. 정수나 문자열로 분기하는 switch의 case 라벨이 대표적이다. 상수 변수는 이런 자리에 쓸 수 있고, 상수 변수가 아닌 static final 필드는 쓸 수 없다.

    public class Level {
    static final int LOW = 1;
    static final int HIGH = Integer.parseInt("2");

    static String name(int level) {
        switch (level) {
            case LOW: return "low";
            case HIGH: return "high";     // error: constant expression required
            default: return "?";
        }
    }
}

    문자열에서도 같은 원리가 보인다. 상수 표현식끼리의 + 연산은 컴파일러가 미리 계산해서 하나의 문자열 리터럴로 만든다. 그리고 JLS §15.29에 따라 String 타입의 상수 표현식은 같은 내용이면 같은 객체를 공유한다.

    public class StringConstant {
    public static void main(String[] args) {
        final String a = "he";      // 상수 변수
        String b = "he";            // 일반 변수
        String s1 = a + "llo";      // 컴파일러가 "hello"로 계산한다
        String s2 = b + "llo";      // 실행 중에 새 문자열을 만든다
        System.out.println(s1 == "hello");
        System.out.println(s2 == "hello");
        System.out.println(s2.equals("hello"));
    }
}

false
true

    ==는 두 참조가 같은 객체를 가리키는지를 비교한다. s1은 컴파일 시점에 이미 "hello"라는 문자열 상수가 되었으므로 리터럴 "hello"와 같은 객체다. s2는 실행 중에 만들어진 별개의 객체라서 내용은 같아도 참조는 다르다. final 한 단어가 프로그램의 출력을 바꾼 셈이다. 문자열은 equals로 비교해야 한다는 규칙의 배경이기도 한데, 문자열 상수가 공유되는 구조는 중급 1편의 String 회차에서 자세히 다룬다.

    클래스 파일에서 본 상수 변수

    상수 변수인 static 필드는 클래스 파일 안에서도 다르게 기록된다. 필드 정보에 ConstantValue라는 속성이 붙어 값이 직접 적힌다(JVMS §4.7.2). 상수 변수가 아닌 static final 필드에는 이 속성이 없고, 대신 static 초기화 코드() 안에서 값을 계산해 putstatic으로 넣는다.

      public static final int MAX_USERS;
    descriptor: I
    flags: (0x0019) ACC_PUBLIC, ACC_STATIC, ACC_FINAL
    ConstantValue: int 100

  public static final int PARSED_MAX;
    descriptor: I

    JVMS §4.7.2에 따르면 ConstantValue 속성이 붙은 static 필드는 클래스 초기화 과정에서, 클래스 초기화 메서드가 호출되기 전에 그 값으로 설정된다. JLS §12.4.2의 초기화 절차도 상수 변수인 static 필드를 가장 먼저 초기화하도록 정하고 있다. 그래서 static 상수 변수는 기본값 0인 상태로 관찰되는 일이 없다. 앞에서 본 "final 필드도 기본값에서 출발한다"는 사실의 예외에 해당한다.

    상수 표현식으로 초기화한 final 인스턴스 필드도 상수 변수다. 그런 필드를 읽는 코드 역시 필드 접근이 아니라 값으로 컴파일된다(JLS §13.1). 다만 모든 객체가 같은 값을 갖는 필드를 인스턴스에 둘 이유는 거의 없으므로, 실무에서 상수 변수는 대부분 static final 필드다.

    final과 참조: 고정되는 것은 화살표다

    지금까지의 예는 기본형과 String이었다. final이 참조형 변수에 붙으면 무엇이 고정되는가. 기본형과 참조형 회차에서 변수에는 값이 하나 들어 있고, 참조형 변수의 값은 객체의 위치를 가리키는 참조값이라고 배웠다. final은 "변수에 든 값을 바꿀 수 없다"는 규칙이므로, 참조형 변수에서 고정되는 것은 참조값이다. 그 참조값이 가리키는 객체의 내용은 final과 상관이 없다.

    public class Counter {
    int count;
}

public class FinalReferenceMain {
    public static void main(String[] args) {
        final Counter counter = new Counter();
        counter.count = 10;          // 가능: 객체의 상태를 바꾼다
        counter.count++;             // 가능
        // counter = new Counter();  // 컴파일 오류: 참조값을 바꾸려 한다

        final int[] scores = {70, 80, 90};
        scores[0] = 100;             // 가능: 배열의 요소를 바꾼다
        // scores = new int[3];      // 컴파일 오류

        Counter alias = counter;     // 참조값 복사
        alias.count = 0;
        System.out.println(counter.count);
        System.out.println(scores[0]);
    }
}
    0
100

    한 줄씩 따라가 보자. counter는 final이므로 처음 대입된 참조값(그림의 x001)을 끝까지 유지한다. counter.count = 10은 counter라는 변수를 바꾸는 것이 아니라, x001에 있는 객체의 count 필드를 바꾸는 것이다. count 필드는 final이 아니므로 허용된다. counter.count++로 11이 된다. 이어서 alias에 같은 참조값이 복사되고, alias.count = 0으로 같은 객체의 값을 0으로 바꾼다. counter로 읽어도 0이 나온다. final 변수가 가리키는 객체가, final이 아닌 다른 변수를 통해서 바뀐 것이다.

    스택 (main의 프레임)                          힙
┌───────────────────────────┐
│ counter [final]   x001  ──┼────────▶  Counter 객체 (x001)
│ alias             x001  ──┼────────▶    count = 0          ← 바꿀 수 있다
│ scores  [final]   x002  ──┼───┐
└───────────────────────────┘   └────▶  int[3] 배열 (x002)
                                          [0]=100 [1]=80 [2]=90  ← 바꿀 수 있다

final이 고정하는 것 : 변수 칸에 들어 있는 참조값 (x001, x002)
final이 상관하지 않는 것 : 그 참조값이 가리키는 객체 안의 필드와 요소

    JLS §4.12.4도 이 점을 명시한다. final 변수가 객체에 대한 참조를 담고 있으면 객체의 상태는 그 객체에 대한 연산으로 바뀔 수 있지만, 변수는 항상 같은 객체를 가리킨다. 배열도 객체이므로 마찬가지여서, 배열의 요소는 바뀔 수 있지만 변수는 항상 같은 배열을 가리킨다.

    final이 잠그는 것은 스택 변수 칸의 참조값이고, 힙에 있는 객체의 필드는 잠기지 않는다는 것을 자물쇠의 위치로 보여 준다. 흰 배경의 메모리 구조도. 왼쪽에 세로로 긴 상자 "스택" 이 있고 그 안에 가로 칸 두 개가 위아래로 놓인다. 위 칸에는 "counter" 와 값 "x001", 칸 왼쪽에 잠긴 자물쇠 아이콘과 라벨 "final". 아래 칸에는 "alias" 와 값 "x001", 자물쇠 없음. 오른쪽에 큰 상자 "힙" 이 있고 그 안에 둥근 모서리 상자 "Counter 객체 x001" 이 있으며 안에 필드 칸 "count = 0" 이 있다. 필드 칸 옆에는 열린 자물쇠 아이콘과 라벨 "변경 가능". 스택의 두 칸에서 각각 화살표가 나와 같은 Counter 객체를 가리킨다. counter 칸에서 나온 화살표는 굵은 실선, alias 칸에서 나온 화살표는 가는 실선. 그림 아래 한 줄 설명 "final은 화살표를 고정한다". 색은 남색, 주황, 회색만 사용하고 글자는 고딕체로 선명하게. final 참조 변수는 다른 객체를 가리키도록 바꿀 수 없을 뿐, 가리키는 객체의 상태는 얼마든지 바뀔 수 있다.
    일상에서 가져온 비유바꿀 수 없는 집 주소, 바꿀 수 있는 집 안

    등기부에 적힌 내 집의 주소를 고칠 수 없다고 해 보자. 주소가 고정됐다고 집 안의 가구까지 고정되는 것은 아니다. 가구는 얼마든지 옮기고 바꿀 수 있다. final 참조 변수는 고정된 주소이고, 객체의 필드는 집 안의 가구다. 이 비유가 맞지 않는 지점도 있다. 주소는 집 하나에 하나지만, 같은 객체를 가리키는 참조 변수는 여러 개일 수 있고 그 가운데 일부만 final일 수 있다.

    변수의 final과 객체의 변경 가능성은 서로 독립된 두 축이다. 네 가지 조합이 모두 가능하다.

    객체의 상태를 바꿀 수 있다객체의 상태를 바꿀 수 없다
    변수가 finalfinal Counter c: 다른 객체를 가리킬 수는 없지만 c.count는 바뀐다final String s: 가리키는 대상도, 문자열의 내용도 바뀌지 않는다
    변수가 final이 아님Counter c: 둘 다 바뀔 수 있다String s: 문자열의 내용은 바뀌지 않지만 s는 다른 문자열을 가리킬 수 있다

    객체의 상태를 바꿀 수 없게 만드는 것은 변수에 붙이는 final이 아니라 클래스의 설계다. 클래스의 모든 필드가 final이고, 그 필드들이 가리키는 객체도 바뀌지 않거나 밖으로 노출되지 않아야 한다. String이 그런 클래스이며, Java SE API 문서는 문자열이 생성된 뒤에는 값이 바뀌지 않는다고 설명한다. 이런 불변 객체를 만드는 방법은 중급 1편에서 한 회차를 들여 다룬다.

    이 구분을 놓치면 생기는 흔한 실수가 "상수 배열"이다. public static final int[] LEVELS = {1, 2, 3};이라고 선언하면 LEVELS가 다른 배열을 가리키게 할 수는 없다. 그러나 어느 코드에서든 Policy.LEVELS[0] = 99;를 실행할 수 있고, 그 순간 프로그램 전체가 공유하는 "상수"의 내용이 바뀐다. 이름이 대문자라는 사실은 아무것도 막아 주지 않는다.

    한 층 아래: final 필드와 스레드

    final 필드에는 "다시 대입할 수 없다" 말고도 명세가 부여한 성질이 하나 더 있다. 여러 스레드가 객체를 공유할 때의 보장이다. 아직 스레드를 배우지 않았으므로 여기서는 그런 것이 있다는 정도만 짚어 둔다.

    JLS §17.5는 객체의 생성자가 끝났을 때 그 객체가 완전히 초기화되었다고 정의한다. 그리고 완전히 초기화된 뒤에야 객체의 참조를 볼 수 있었던 스레드는 그 객체의 final 필드에 대해 올바르게 초기화된 값을 본다고 보장한다. final이 아닌 필드에는 이런 보장이 없다. 같은 절의 예제는 final이 아닌 필드를 다른 스레드가 기본값 0으로 읽을 수 있다고 설명한다. 동기화 없이도 안전하게 공유할 수 있는 불변 객체를 final 필드로 만들 수 있는 근거가 이 조항이다.

    이 보장에는 조건이 있다. 생성자가 끝나기 전에 만들고 있는 객체의 참조를 다른 스레드가 볼 수 있는 곳에 써서는 안 된다. 앞에서 본 "생성자 안에서 this를 밖으로 내보내지 않는다"는 규칙과 같은 내용이다. 단일 스레드에서는 기본값이 잠깐 보이는 문제였지만, 멀티스레드에서는 명세가 주는 보장 자체가 사라진다. 이 주제는 고급 1편에서 자바 메모리 모델과 함께 다시 다룬다.

    같은 절은 final 필드를 다루는 컴파일러의 재량도 언급한다. final 필드는 한 번 초기화되면 정상적인 상황에서는 바뀌지 않으므로, 컴파일러는 final 필드의 값을 레지스터에 보관해 두고 메모리에서 다시 읽지 않아도 된다고 허용한다. "정상적인 상황"이라는 단서가 붙은 것은 리플렉션 같은 수단으로 final 필드를 바꿀 수 있는 경우가 있기 때문이다(JLS §17.5.3). 이것은 역직렬화처럼 객체를 복원하는 특수한 용도를 위한 것이고, 일반 코드에서 final 필드의 값을 바꾸는 수단으로 쓸 것은 아니다. 특히 상수 변수는 값이 이미 사용하는 쪽 코드에 복사돼 있으므로, 필드를 바꿔도 그 변경이 보이지 않을 수 있다.

    흔한 오해와 함정

    • "final을 붙였으니 이 객체는 바뀌지 않는다." final은 변수에 대한 규칙이지 객체에 대한 규칙이 아니다. final Counter c의 c.count는 바뀐다. 객체가 바뀌지 않는지는 그 객체의 클래스가 어떻게 설계됐는지에 달려 있다.
    • "static final이면 전부 컴파일 타임 상수다." 타입이 기본형이나 String이고 상수 표현식으로 초기화된 것만 상수 변수다. static final Integer, 메서드 호출로 초기화한 값, 배열과 일반 객체는 실행 중에 필드에서 읽는다. 클래스 초기화 시점과 재컴파일 문제는 상수 변수에만 해당한다.
    • "final 필드는 언제 읽어도 같은 값이다." 생성자가 대입하기 전에는 기본값이다. 생성자 안에서 호출한 메서드나, 생성 도중에 this를 넘겨받은 다른 객체는 그 기본값을 볼 수 있다.
    • "상수는 정의한 클래스만 다시 빌드하면 반영된다." 상수 변수의 값은 사용하는 클래스 파일에 복사돼 있다. 사용하는 쪽도 다시 컴파일해야 새 값이 반영된다.
    • "final 매개변수는 호출하는 쪽의 변수를 보호한다." 인자는 값으로 복사되므로 호출자의 변수는 final 여부와 상관없이 바뀌지 않는다. 그리고 매개변수가 참조형이면, final이어도 그 참조로 객체의 상태를 바꿀 수 있다.
    • "if 두 개로 나눠 써도 논리적으로 한 번만 대입되니 괜찮다." 컴파일러는 조건식의 논리 관계를 추론하지 않는다. 확정 할당과 확정 미할당은 흐름의 모양만 보고 판정한다. 배타적인 조건은 if-else로 써야 한다.

    어디서 다시 만나는가

    final은 이 뒤로 여러 번 다시 나온다. 다음 회차에서는 클래스와 메서드에 붙는 final을 본다. 상속을 금지하는 final 클래스, 오버라이딩을 금지하는 final 메서드다. 부모 생성자가 자식의 final 필드를 기본값으로 관찰하는 문제도 거기서 다시 등장한다.

    중급 1편에서는 final 필드로 불변 객체를 만들고, 불변 객체가 왜 공유하기 안전한지를 본다. String과 래퍼 클래스가 대표적인 불변 객체다. 열거형(enum)은 "상수의 집합"을 타입으로 만든 것으로, static final 정수 상수가 가진 한계를 해결한다. 지역 클래스와 익명 클래스, 그리고 람다가 바깥 지역 변수를 쓸 때 사실상 final을 요구하는 이유도 중급 과정에서 설명한다.

    스프링을 쓸 때는 의존하는 객체를 생성자로 받아 final 필드에 저장하는 코드를 자주 쓰게 된다. 이 회차의 내용으로 그 이점을 설명할 수 있다. 필드가 final이면 대입을 빠뜨린 생성자가 컴파일 오류가 되고, 객체가 만들어진 뒤에는 의존 대상이 다른 객체로 바뀌지 않는다는 것을 컴파일러가 보장한다. 그리고 고급 1편에서 멀티스레드를 배울 때, final 필드가 주는 초기화 안전성이 불변 객체를 스레드 사이에 공유할 수 있게 하는 근거로 다시 나온다.

    이 장의 핵심

    final은 "값이 변하지 않는다"가 아니라 "변수에 대입이 한 번만 일어난다"는 규칙이다. 컴파일러는 확정 할당과 확정 미할당이라는 흐름 분석으로 그 한 번을 검사한다. 참조형 변수에서 고정되는 것은 참조값이지 객체가 아니다. 그리고 기본형·String 타입에 상수 표현식으로 초기화된 final 변수는 상수 변수가 되어, 읽는 쪽 코드에 값으로 복사된다.
    final 변수
    한 번만 대입할 수 있는 변수다(JLS §4.12.4). "값이 변하지 않는다"가 아니라 "대입이 한 번뿐이다"가 정확한 뜻이다.
    확정 할당과 확정 미할당
    컴파일러의 흐름 분석이다. 읽으려면 모든 경로에서 대입이 끝나 있어야 하고, blank final에 대입하려면 모든 경로에서 대입된 적이 없어야 한다. 두 성질 중 어느 쪽도 성립하지 않는 지점이 있다.
    final 인스턴스 필드
    선언, 인스턴스 초기화 블록, 생성자에서만 대입할 수 있고 모든 생성자의 끝에서 확정 할당돼 있어야 한다. 클래스 파일에 ACC_FINAL로 기록되며 JVM도 생성자 밖의 대입을 거부한다.
    기본값에서 출발
    final 필드도 객체가 할당될 때는 기본값이다. 생성자가 대입하기 전에 호출된 메서드는 그 기본값을 볼 수 있다.
    static final과 상수
    클래스에 하나뿐이고 다시 대입할 수 없는 값. 선언이나 static 초기화 블록에서 한 번 대입한다. 이름은 대문자와 밑줄로 쓴다.
    상수 변수
    기본형 또는 String 타입이고 상수 표현식으로 초기화된 final 변수. 읽는 쪽 코드에 값으로 복사되므로 클래스 초기화를 일으키지 않고, 값을 바꾸면 사용하는 쪽도 다시 컴파일해야 한다.
    final 참조
    고정되는 것은 변수에 든 참조값이다. 그 참조가 가리키는 객체나 배열의 내용은 바뀔 수 있다.
    final 필드와 스레드
    생성자가 끝난 뒤에 공개된 객체의 final 필드는 다른 스레드에서도 올바르게 초기화된 값으로 보인다(JLS §17.5). 생성 도중 this를 내보내면 이 보장이 깨진다.

    실무에서 다시 판단하면, final은 "기본으로 붙이고, 바뀌어야 할 이유가 있을 때만 뗀다"는 쪽이 유지보수에 유리하다. 필드가 final이면 그 값이 어디서 정해지는지 찾을 곳이 생성자로 좁혀진다. 장애를 추적할 때 "이 값을 누가 바꿨는가"라는 질문 자체가 사라지는 필드가 많을수록 조사 범위가 줄어든다. 반대로 요청마다 값이 누적되거나 상태가 전이되는 필드는 final일 수 없고, 그런 필드가 어디서 바뀌는지를 메서드로 드러내는 것이 설계의 일이 된다.

    상수를 공개할 때는 값이 정말 바뀌지 않는지를 먼저 묻는다. 공용 라이브러리의 public static final 기본형·String 상수는 사용하는 쪽 클래스 파일에 복사된다. 타임아웃, 페이지 크기, 버전 문자열처럼 나중에 조정할 가능성이 있는 값을 이렇게 공개하면, 라이브러리만 교체한 배포에서 옛 값과 새 값이 섞여 동작한다. 이런 값은 메서드로 제공하거나 설정으로 빼는 편이 안전하다. 같은 저장소 안에서 항상 함께 빌드되는 코드라면 이 문제는 일어나지 않으므로 과하게 피할 필요는 없다.

    코드 리뷰에서 "final이니까 안전하다"는 말이 나오면 무엇이 final인지 다시 확인한다. final 필드가 배열이나 변경 가능한 객체를 가리키고 그 참조가 getter로 그대로 나간다면, 외부에서 내용을 바꿀 수 있다. 식별자나 금액처럼 바뀌면 안 되는 값은 필드를 final로 두는 것에 더해, 그 타입 자체가 변경 불가능한지까지 봐야 한다.

    생성자에서 메서드를 호출하거나 this를 다른 객체에 등록하는 코드는 따로 표시해 두고 살핀다. 단일 스레드에서는 final 필드가 기본값으로 보이는 문제로, 멀티스레드에서는 초기화가 끝나지 않은 객체가 공유되는 문제로 나타난다. 두 경우 모두 증상이 드물게, 그리고 생성 지점과 먼 곳에서 나타나기 때문에 원인을 찾기 어렵다.

     final 지역 변수에 대해 컴파일러가 대입을 허용하는 조건으로 가장 정확한 것은? 소스 코드에 그 변수에 대한 대입문이 정확히 하나만 적혀 있어야 한다. 실행 중에 대입이 두 번 일어나면 JVM이 예외를 던지므로 컴파일러는 검사하지 않는다. 대입 지점에 도달하는 모든 경로에서 그 변수에 아직 대입된 적이 없음을 컴파일러가 증명할 수 있어야 한다. 대입 지점에 도달하는 경로 중 하나라도 대입된 적이 없으면 된다. blank final에 대입하려면 그 지점에서 확정 미할당이어야 한다(JLS 16장). 모든 경로에서 대입 전이라는 뜻이다. if와 else 양쪽에 대입문이 하나씩 있어도 되므로 대입문의 개수와는 무관하다. 지역 변수의 final은 바이트코드에 남지 않아 JVM은 검사하지 않는다. 일부 경로에서만 대입 전인 경우는 "might already have been assigned" 오류가 된다. public static final int SIZE = 10;을 가진 클래스 A와, int n = A.SIZE;를 실행하는 클래스 B가 있다. B의 이 문장이 실행될 때 일어나는 일로 옳은 것은? A가 초기화되고 static 초기화 블록이 실행된 뒤 필드에서 10을 읽는다. B의 바이트코드에 10이 직접 들어 있으므로 A의 초기화는 일어나지 않는다. A의 객체가 하나 만들어지고 그 객체의 필드에서 10을 읽는다. A가 로드되지 않았으면 0이 읽힌다. SIZE는 기본형이고 리터럴로 초기화된 final 변수이므로 상수 변수다. 컴파일러는 A.SIZE를 값 10으로 치환하고(JLS §13.1), 상수 변수를 읽는 것은 클래스 초기화를 일으키지 않는다(JLS §12.4.1). static 필드는 객체와 무관하며, 값이 이미 복사돼 있으므로 0이 읽힐 일도 없다. final Counter c = new Counter(); 다음에 올 수 있는 문장 가운데 컴파일 오류가 나는 것은? (Counter에는 final이 아닌 int count 필드가 있다.) c.count = 5; Counter d = c; d.count = 7; c.count++; c = new Counter(); final은 변수 c에 든 참조값을 고정한다. c가 다른 객체를 가리키게 하는 대입만 금지된다. c가 가리키는 객체의 필드를 바꾸는 것, 같은 참조값을 다른 변수에 복사해 그 변수로 객체를 바꾸는 것은 모두 허용된다. final 인스턴스 필드에 대한 설명으로 옳지 않은 것은? final 필드는 객체가 할당되는 순간부터 최종 값을 갖고 있으므로 기본값으로 관찰될 수 없다. blank final 필드는 모든 생성자의 끝에서 확정 할당돼 있어야 한다. this(...)로 다른 생성자를 호출한 뒤에는 blank final 필드에 대입할 수 없다. 클래스 파일에 ACC_FINAL 플래그로 기록되고, 생성자 밖에서의 대입은 JVM 수준에서도 거부된다. final 필드도 객체가 할당될 때는 기본값이고 생성자가 대입해야 최종 값이 된다. 생성자가 대입 전에 호출한 메서드는 기본값을 읽을 수 있다. 나머지는 각각 JLS §8.3.1.2, JLS §16.9, JVMS §6.5 putfield의 규칙이다. 다음 중 상수 변수(constant variable)가 아닌 것은? static final int A = 60 * 60; static final String B = "id-" + 1; static final Integer C = 3600; final boolean D = true; 상수 변수는 기본형 또는 String 타입의 final 변수가 상수 표현식으로 초기화된 것이다. Integer는 참조형(래퍼 클래스)이므로 초기화 식이 리터럴이어도 상수 변수가 아니다. 나머지는 타입이 기본형이나 String이고, 리터럴과 그 연산만으로 초기화됐다. static 여부는 조건이 아니다.
    final 변수(final variable)
    한 번만 대입할 수 있는 변수. 지역 변수, 매개변수, 인스턴스 필드, static 필드에 모두 붙일 수 있다.
    blank final
    선언에 초기화 식이 없는 final 변수. 나중에 정확히 한 번 대입해야 한다.
    확정 할당(definite assignment)
    어떤 지점에 도달하는 모든 실행 경로에서 변수에 대입이 일어났음이 컴파일 시점에 증명되는 상태. 변수를 읽기 위한 조건이다.
    확정 미할당(definite unassignment)
    어떤 지점에 도달하는 모든 실행 경로에서 변수에 대입이 일어나지 않았음이 증명되는 상태. blank final에 대입하기 위한 조건이다.
    상수 표현식(constant expression)
    리터럴, 상수 변수, 그리고 그것들에 대한 연산만으로 이루어져 컴파일 시점에 값이 결정되는 기본형 또는 String 타입의 식(JLS §15.29).
    상수 변수(constant variable)
    기본형 또는 String 타입이고 상수 표현식으로 초기화된 final 변수(JLS §4.12.4). 사용하는 곳에 값으로 치환된다.
    상수 인라이닝(constant inlining)
    상수 변수를 읽는 코드를 필드 접근 대신 값 자체로 컴파일하는 것. 사용하는 쪽 클래스 파일에 값이 복사된다.
    사실상 final(effectively final)
    final을 붙이지 않았지만 초기화 뒤 다시 대입되지 않아 final을 붙여도 오류가 나지 않는 지역 변수.
    ConstantValue 속성
    클래스 파일의 필드 정보에 붙어 상수 표현식의 값을 직접 기록하는 속성(JVMS §4.7.2). JVM은 static 필드에 붙은 것만 사용해, 클래스 초기화 메서드를 호출하기 전에 그 값을 필드에 설정한다.
    불변 객체(immutable object)
    생성된 뒤 상태가 바뀌지 않는 객체. 변수의 final이 아니라 클래스의 설계로 만들어진다.
