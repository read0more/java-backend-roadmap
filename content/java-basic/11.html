    문법에서 설계로

    10회의 마지막에 printAll(Printer[] printers, String doc)라는 메서드를 다시 보았다. 그 메서드의 소스와 바이트코드에는 인터페이스 Printer만 등장하고, 어떤 구현 클래스의 이름도 없었다. 그래서 장치가 몇 종류 추가되든 그 메서드는 바뀌지 않는다. 09회와 10회에서 익힌 다형적 참조, 동적 디스패치, 인터페이스라는 문법이 만들어 낸 결과다.

    이 회차에는 새 문법이 없다. 같은 문법을 놓고 질문을 바꾼다. 프로그램은 한 번 쓰고 끝나지 않고 계속 바뀐다. 요구가 하나 바뀔 때 몇 개의 파일을 열어야 하는가, 고치지 않은 코드를 다시 검증해야 하는가, 바꾸려는 것과 상관없는 코드가 함께 깨지지는 않는가. 설계는 이 변경의 범위를 다루는 일이다. 다형성은 그 범위를 좁히는 데 자바가 제공하는 가장 강한 도구다.

    막연한 말로 끝내지 않기 위해 이 회차는 변경의 범위를 직접 센다. 온도 조절기 프로그램 하나를 세 가지 구조로 쓰고, 난방 장치가 추가될 때마다 어느 소스 파일이 바뀌는지, 어느 클래스 파일이 바이트 단위로 그대로인지, 실행 중에 어느 클래스가 메모리에 올라오는지를 확인한다. 실행 결과와 도구 출력은 JDK 21(Temurin 21.0.13)에서 확인한 것이다.

    좋은 객체 지향 프로그래밍이란 무엇인가

    객체 지향 프로그램은 객체들이 서로 요청을 주고받으며 일을 해내는 구조다. 한 객체가 모든 일을 하지 않고, 자기가 못 하는 일은 다른 객체에게 메서드 호출로 부탁한다. 이때 부탁하는 쪽을 클라이언트(client), 부탁을 받아 처리하는 쪽을 서버(server)라고 부른다. 네트워크 용어가 아니라 두 객체 사이의 역할을 가리키는 말이다. 같은 객체가 어떤 호출에서는 클라이언트이고 다른 호출에서는 서버가 된다.

    객체 지향의 특징으로 흔히 추상화, 캡슐화, 상속, 다형성 네 가지를 든다. 이 권에서 모두 한 번씩 다뤘다. 캡슐화는 한 객체의 내부를 감춰 그 객체 안의 변경이 밖으로 새지 않게 한다. 상속은 코드를 물려준다. 다형성이 하는 일은 종류가 다르다. 다형성은 객체 하나의 내부가 아니라 두 객체 사이의 연결을 다룬다. 클라이언트가 서버를 구체적인 클래스가 아닌 상위 타입으로 알고 있으면, 그 자리에 들어오는 서버 객체를 클라이언트를 건드리지 않고 바꿀 수 있다.

    그래서 이 회차는 "좋은 객체 지향 설계"를 다음과 같이 좁혀서 쓴다. 요구가 바뀌었을 때 부품을 갈아 끼우듯 일부만 바꿀 수 있는 설계다. 판단 기준은 세 가지로 적을 수 있다.

    • 변경이 한 곳에 모인다. 하나의 요구 변경이 여러 클래스에 흩어진 수정으로 번지지 않는다.
    • 바꾸지 않은 코드는 다시 검증할 필요가 없다. 소스가 그대로이고 클래스 파일도 그대로라면 그 코드의 동작은 이전과 같다.
    • 새 기능은 기존 코드의 수정이 아니라 새 코드의 추가로 들어온다. 잘 돌아가던 코드를 열어 고치는 일은 그 자체가 위험이다.

    세 기준은 서로 다른 말이 아니다. 클라이언트와 서버 사이의 연결이 구체 클래스에 묶여 있으면 셋 다 깨지고, 그 연결을 다형성으로 풀면 셋이 함께 좋아진다. 그 연결을 푸는 방법에 붙은 이름이 역할과 구현의 분리다.

    역할과 구현을 나눈다는 것

    일상에서 가져온 비유벽의 콘센트 규격

    전기 제품을 만드는 회사는 발전소를 모른다. 아는 것은 벽의 콘센트 규격뿐이다. 구멍의 모양, 전압, 주파수가 정해져 있고, 제품은 그 규격에 맞는 플러그만 달면 된다. 콘센트 뒤의 전기가 화력 발전소에서 왔는지 태양광 패널에서 왔는지는 제품의 설계에 영향을 주지 않는다. 발전 방식이 바뀌어도 집 안의 제품을 하나도 고치지 않는 이유는 제품이 "전기를 공급하는 것"이라는 역할에만 맞춰져 있기 때문이다. 이 비유가 맞지 않는 지점도 있다. 콘센트 규격은 국가가 정해 수십 년간 유지하지만, 프로그램의 인터페이스는 우리가 직접 정하고 때로는 잘못 정한다. 규격 자체를 고쳐야 하는 날이 오면 그 규격에 맞춘 모든 것을 고쳐야 한다는 점은 프로그램에서도 같다.

    역할(role)은 "무엇을 해 줄 수 있는가"의 약속이고, 구현(implementation)은 "그것을 실제로 어떻게 하는가"다. 자바에서 역할은 주로 인터페이스로, 구현은 그 인터페이스를 구현한 클래스로 표현한다. 10회에서 인터페이스를 "구현 없는 약속"이라고 정리했는데, 설계의 말로 옮기면 그 약속이 역할이다. 역할과 구현을 나눈다는 것은 클라이언트의 코드가 역할의 이름만 알고 구현의 이름은 모르게 만든다는 뜻이다.

    클라이언트가 역할만 알 때 얻는 것을 먼저 적어 두고, 뒤의 예제에서 하나씩 확인하겠다.

    1. 클라이언트는 서버의 내부 구조를 몰라도 된다. 역할에 선언된 메서드만 알면 호출할 수 있다.
    2. 서버의 내부가 바뀌어도 클라이언트는 영향을 받지 않는다. 구현 클래스의 본문을 고쳐도 역할이 그대로이면 클라이언트는 다시 컴파일할 필요조차 없다.
    3. 서버를 다른 구현으로 통째로 바꿔도 클라이언트는 바뀌지 않는다. 아직 존재하지 않는 구현으로도 바꿀 수 있다.
    4. 클라이언트를 구현 없이 개발하고 시험할 수 있다. 역할만 정해지면 진짜 구현이 완성되기 전에 가짜 구현을 꽂아 클라이언트의 논리를 검증할 수 있다.

    이것이 가능한 근거는 앞의 두 회차에 있다. 역할 타입의 변수가 구현 클래스의 인스턴스를 가리킬 수 있고(다형적 참조), 그 변수로 호출한 메서드는 실행 중에 객체의 클래스에서 선택된다(동적 디스패치). 설계 원칙은 이 두 가지 언어 기능을 어떤 방향으로 쓸지에 관한 이야기다.

    예제 1: 구현에 직접 의존하는 클라이언트

    실내 온도를 목표 온도로 유지하는 온도 조절기를 만든다. 온도 조절기는 스스로 열을 내지 못하므로 난방 장치에게 부탁한다. 온도 조절기가 클라이언트이고 난방 장치가 서버다. 첫 버전에서 난방 장치는 가스 보일러 하나뿐이다.

    public class GasBoiler {
    public void ignite() {
        System.out.println("가스 보일러 점화");
    }

    public void shutOff() {
        System.out.println("가스 보일러 소화");
    }
}
    public class Thermostat {
    private final GasBoiler boiler = new GasBoiler();
    private final int target;
    private boolean heating;

    public Thermostat(int target) {
        this.target = target;
    }

    public void onTemperature(int current) {
        if (current < target && !heating) {
            boiler.ignite();
            heating = true;
        } else if (current >= target && heating) {
            boiler.shutOff();
            heating = false;
        }
    }
}
    public class HomeMain {
    public static void main(String[] args) {
        Thermostat thermostat = new Thermostat(22);
        int[] readings = {19, 20, 23, 24, 21};
        for (int t : readings) {
            System.out.println("현재 " + t + "도");
            thermostat.onTemperature(t);
        }
    }
}

    온도 조절기의 논리를 먼저 추적해 두자. 이 논리는 예제가 끝날 때까지 바뀌지 않는다. 19도가 들어오면 목표 22도보다 낮고 아직 난방 중이 아니므로 장치를 켜고 heating을 true로 바꾼다. 20도는 여전히 낮지만 이미 난방 중이므로 아무 일도 하지 않는다. 23도가 되면 목표 이상이고 난방 중이므로 장치를 끄고 heating을 false로 돌린다. 24도에서는 할 일이 없고, 21도에서 다시 켠다. 상태가 바뀔 때만 장치에 명령을 보내는 것이 이 클래스의 핵심 논리다.

    프로그램은 정확히 동작한다. 문제는 Thermostat이 GasBoiler에 묶여 있는 방식이다. 묶인 지점은 세 군데다.

    • 타입 선언. 필드의 타입이 GasBoiler다. 이 필드에는 가스 보일러 말고는 아무것도 넣을 수 없다.
    • 객체 생성. new GasBoiler()를 Thermostat이 직접 실행한다. 어떤 장치를 쓸지를 온도 조절기가 스스로 결정하고 있다.
    • 구현 고유의 메서드 이름. ignite()와 shutOff()는 불을 붙이고 끄는 보일러의 어휘다. 불을 쓰지 않는 장치에는 이런 메서드가 없다.

    이 묶임은 소스에만 있는 것이 아니다. javap -v Thermostat으로 상수 풀을 보면 클래스 파일에 GasBoiler라는 이름이 그대로 적혀 있다.

       #7 = Class              #8             // GasBoiler
   #9 = Methodref          #7.#3          // GasBoiler."":()V
  #24 = Methodref          #7.#25         // GasBoiler.ignite:()V
  #27 = Methodref          #7.#28         // GasBoiler.shutOff:()V

    상수 풀은 클래스 파일이 바깥 세계를 가리키는 이름들의 목록이다. 여기에 GasBoiler가 있다는 것은 Thermostat.class가 GasBoiler라는 이름의 클래스, 그 클래스의 생성자와 두 메서드가 존재한다고 가정하고 만들어졌다는 뜻이다. 가스 보일러를 다른 장치로 바꾸려면 이 클래스 파일이 다시 만들어져야 한다.

    예제 2: 구현이 하나 늘면 클라이언트가 바뀐다

    전기 히터를 쓰는 집에도 이 온도 조절기를 팔기로 했다. 전기 히터를 만든 사람은 자기 장치에 맞는 이름을 붙였다.

    public class ElectricHeater {
    public void switchOn() {
        System.out.println("전기 히터 켬");
    }

    public void switchOff() {
        System.out.println("전기 히터 끔");
    }
}

    두 장치를 모두 지원하려면 Thermostat을 고쳐야 한다. 구조를 그대로 둔 채 할 수 있는 일은 장치 종류를 문자열로 받아 분기하는 것이다.

    public class Thermostat {
    private final String type;
    private final GasBoiler boiler = new GasBoiler();
    private final ElectricHeater electric = new ElectricHeater();
    private final int target;
    private boolean heating;

    public Thermostat(String type, int target) {
        this.type = type;
        this.target = target;
    }

    public void onTemperature(int current) {
        if (current < target && !heating) {
            if (type.equals("gas")) {
                boiler.ignite();
            } else if (type.equals("electric")) {
                electric.switchOn();
            }
            heating = true;
        } else if (current >= target && heating) {
            if (type.equals("gas")) {
                boiler.shutOff();
            } else if (type.equals("electric")) {
                electric.switchOff();
            }
            heating = false;
        }
    }
}

    new Thermostat("electric", 22)로 실행하면 "전기 히터 켬", "전기 히터 끔"이 같은 시점에 출력된다. 동작은 맞다. 그러나 무엇이 바뀌었는지 세어 보면, 난방 장치가 하나 늘었을 뿐인데 온도 조절기의 필드가 둘 늘었고, 생성자의 매개변수가 바뀌었고, 메서드 본문에 분기가 두 군데 들어갔다. 생성자가 바뀌었으니 HomeMain도 고쳐야 한다. 온도를 비교하고 상태를 기억하는 논리는 그대로인데, 그 논리가 들어 있는 클래스 전체가 수정 대상이 되었다.

    이 구조의 문제를 구체적으로 적으면 다음과 같다.

    • 분기가 장치 수에 비례해 늘어난다. 세 번째 장치인 히트펌프가 오면 필드 하나와 else if 두 개가 또 들어간다. 장치에게 시키는 일의 종류가 늘면 분기 지점도 그만큼 늘어난다. 10회 첫머리에서 본 T×M의 곱셈이 클라이언트 안에서 다시 벌어진다.
    • 쓰지 않는 구현까지 만든다. 전기 히터 집에서도 GasBoiler 객체가 생성된다. 실제 장치라면 생성자에서 가스 밸브를 점검할 수도 있다.
    • 잘못된 선택이 조용히 통과한다. new Thermostat("elektric", 22)처럼 문자열을 틀리게 쓰면 컴파일도 되고 예외도 없다. 어느 분기에도 걸리지 않아 아무 장치도 켜지지 않는데 heating만 true가 되고, 집은 계속 춥다.
    • 클라이언트를 컴파일하려면 모든 구현이 있어야 한다. ElectricHeater 없이 이 Thermostat을 컴파일하면 "cannot find symbol" 오류가 난다. 가스 보일러만 쓰는 집에 납품할 때도 전기 히터 클래스가 함께 가야 한다.
    • 손대지 않으려던 논리를 다시 검증해야 한다. 분기를 끼워 넣다가 heating = true 줄을 분기 안쪽으로 잘못 옮기는 식의 실수가 가능하므로, 가스 보일러용 동작도 다시 시험해야 한다.

    원인은 예제 1에서 본 세 가지 묶임이 구현의 수만큼 복제된 것이다. 온도 조절기가 알아야 할 것은 "켤 수 있고 끌 수 있는 난방 장치가 하나 있다"는 사실뿐인데, 코드는 모든 장치의 이름과 생성 방법과 고유한 메서드 이름을 알고 있다.

    예제 3: 역할을 세우고 구현을 주입받는다

    온도 조절기가 알아야 할 것만 따로 꺼내 인터페이스로 만든다. 이것이 난방 장치라는 역할이다. 메서드 이름은 특정 장치의 어휘(점화, 스위치)가 아니라 클라이언트가 원하는 일(난방을 켠다, 끈다)로 짓는다.

    public interface Heater {
    void heatOn();

    void heatOff();
}
    public class GasBoiler implements Heater {
    @Override
    public void heatOn() {
        System.out.println("가스 보일러 점화");
    }

    @Override
    public void heatOff() {
        System.out.println("가스 보일러 소화");
    }
}
    public class ElectricHeater implements Heater {
    @Override
    public void heatOn() {
        System.out.println("전기 히터 켬");
    }

    @Override
    public void heatOff() {
        System.out.println("전기 히터 끔");
    }
}

    클라이언트는 세 가지 묶임을 모두 푼다. 필드의 타입을 역할로 바꾸고, 객체를 직접 생성하지 않고 생성자로 건네받으며, 역할에 선언된 메서드만 호출한다.

    public class Thermostat {
    private final Heater heater;
    private final int target;
    private boolean heating;

    public Thermostat(Heater heater, int target) {
        this.heater = heater;
        this.target = target;
    }

    public void onTemperature(int current) {
        if (current < target && !heating) {
            heater.heatOn();
            heating = true;
        } else if (current >= target && heating) {
            heater.heatOff();
            heating = false;
        }
    }
}
    public class HomeMain {
    public static void main(String[] args) {
        Heater heater = new GasBoiler();
        Thermostat thermostat = new Thermostat(heater, 22);

        int[] readings = {19, 20, 23, 24, 21};
        for (int t : readings) {
            System.out.println("현재 " + t + "도");
            thermostat.onTemperature(t);
        }
    }
}

    실행 결과는 예제 1과 한 글자도 다르지 않다. 달라진 것은 Thermostat 안에서 문자열 비교와 분기가 사라지고, 예제 1의 단순한 논리가 그대로 돌아왔다는 점이다. 필요한 객체를 스스로 만들지 않고 밖에서 건네받는 방식을 의존성 주입(dependency injection)이라고 하고, 그중 생성자의 매개변수로 받는 형태를 생성자 주입이라고 부른다. 필드가 final이므로 한 번 주입된 난방 장치는 이 온도 조절기가 살아 있는 동안 바뀌지 않는다.

    main이 두 객체를 만든 직후의 메모리는 다음과 같다.

    스택(main의 프레임)               힙
heater     ───────────────────▶ GasBoiler 인스턴스
(Heater 타입)                         ▲
                                      │
thermostat ──▶ Thermostat 인스턴스    │
                 heater  ─────────────┘   (Heater 타입 필드)
                 target  = 22
                 heating = false

    Thermostat 인스턴스 안의 heater 필드에는 참조값 하나가 들어 있을 뿐이다. 그 참조가 가리키는 객체가 GasBoiler라는 사실은 힙에 있는 객체 쪽에 기록되어 있고, Thermostat의 코드 어디에도 없다. heater.heatOn()이 실행될 때 일어나는 일은 10회에서 본 그대로다. 컴파일러는 선언 타입이 인터페이스이므로 invokeinterface Heater.heatOn을 만들어 두었고, JVM은 필드에서 꺼낸 참조가 가리키는 객체의 클래스 GasBoiler에서 heatOn을 선택해 실행한다.

    컴파일 타임 의존성과 런타임 의존성

    "A가 B에 의존한다"는 말은 B가 바뀌면 A가 영향을 받을 수 있다는 뜻이다. 예제 3을 정확히 이해하려면 이 말을 두 시점으로 나누어야 한다. 프로그램을 실행하지 않고 코드만 읽어서 알 수 있는 의존이 있고, 프로그램이 실행되어 객체가 만들어진 뒤에야 생기는 의존이 있다.

    컴파일 타임 의존성: 소스에 적힌 이름

    컴파일 타임 의존성은 클래스와 인터페이스라는 타입 사이의 관계다. 어떤 소스 파일에 다른 타입의 이름이 등장하고, 그 타입의 정의가 없으면 컴파일할 수 없을 때 의존한다고 한다. 예제 3의 Thermostat.java에 등장하는 다른 타입의 이름은 Heater 하나다. 이 사실은 컴파일 결과물에서 그대로 확인된다.

       #7 = Fieldref           #8.#9          // Thermostat.heater:LHeater;
  #21 = InterfaceMethodref #22.#23        // Heater.heatOn:()V
  #22 = Class              #24            // Heater
  #26 = InterfaceMethodref #22.#27        // Heater.heatOff:()V

    예제 1의 상수 풀에 있던 GasBoiler가 사라지고 Heater만 남았다. 상수 풀 전체를 보아도 클래스 이름은 java/lang/Object, Thermostat, Heater 셋뿐이다. 실험으로도 확인할 수 있다. 구현 클래스의 소스를 모두 치워 두고 javac Heater.java Thermostat.java만 실행해도 컴파일이 성공한다. 온도 조절기는 난방 장치의 구현이 세상에 하나도 없는 상태에서 완성될 수 있다. 앞에서 적은 네 번째 이득, 곧 구현 없이 클라이언트를 개발할 수 있다는 말의 근거가 이것이다.

    런타임 의존성: 힙에서 맺어진 참조

    런타임 의존성은 실행 중인 객체 사이의 관계다. 앞의 메모리 그림에서 Thermostat 인스턴스의 heater 필드가 GasBoiler 인스턴스를 가리키고 있었다. 이 연결은 Thermostat.java를 아무리 읽어도 알 수 없다. 연결을 정한 것은 HomeMain의 new GasBoiler()와 new Thermostat(heater, 22) 두 줄이고, 그 줄이 실행되는 순간에 맺어진다. 같은 Thermostat.class가 어떤 실행에서는 가스 보일러와, 다른 실행에서는 전기 히터와 연결된다.

    JVM이 클래스를 다루는 방식에서도 두 의존의 차이가 보인다. HotSpot의 -Xlog:class+load 옵션으로 HomeMain을 실행하면 로드되는 클래스가 한 줄씩 찍힌다. 그중 이 프로그램의 클래스만 추리면 다음과 같다(시각과 경로는 실행 환경마다 다르므로 생략했다).

    [info][class,load] HomeMain source: ...
[info][class,load] Heater source: ...
[info][class,load] GasBoiler source: ...
[info][class,load] Thermostat source: ...

    ElectricHeater는 클래스 파일이 같은 디렉터리에 있는데도 목록에 없다. 이번 실행에서 아무도 그 클래스를 필요로 하지 않았기 때문이다. 여기에는 명세가 정한 부분과 구현에 맡긴 부분이 섞여 있다. 클래스가 초기화되는 계기는 JLS 12.4.1이 나열하는데(인스턴스 생성, static 메서드 호출, 상수가 아닌 static 필드의 사용 등), ElectricHeater에 대해서는 그중 어느 것도 일어나지 않았다. 한편 로딩과 연결을 언제 할지에 대해 JVM 명세는 구현에 재량을 주며, 심벌릭 참조를 쓰일 때마다 하나씩 해석하는 "게으른" 방식과 한꺼번에 해석하는 "이른" 방식을 모두 예로 든다(JVMS 5.4). 위 출력은 HotSpot에서 관찰한 결과다.

    반대로 예제 2의 구조로 같은 실험을 하면, 가스 보일러만 쓰도록 실행해도 GasBoiler와 ElectricHeater가 둘 다 로드된다. 클라이언트가 두 구현을 모두 필드 초기화식에서 생성하기 때문이다. 컴파일 타임에 묶인 것은 런타임에도 끌려온다.

    두 그림을 나란히 놓으면

    컴파일 타임 의존성 (타입 사이, 소스와 클래스 파일에 적힌 이름)

  예제 1      Thermostat ────────▶ GasBoiler

  예제 3      Thermostat ────────▶ Heater ◀──────── GasBoiler
                                        ◀──────── ElectricHeater
              HomeMain ──▶ Thermostat, Heater, GasBoiler

런타임 의존성 (객체 사이, 힙의 참조)

  예제 3      Thermostat 인스턴스 ── heater ──▶ GasBoiler 인스턴스
              (다른 실행에서는)   ── heater ──▶ ElectricHeater 인스턴스

    예제 1에서는 두 그림이 같은 모양이었다. 타입 사이의 화살표와 객체 사이의 화살표가 겹쳐 있어서, 런타임의 연결을 바꾸려면 소스를 바꿔야 했다. 예제 3에서는 두 그림이 달라졌다. 컴파일 타임의 Thermostat은 Heater까지만 알고, 그 뒤에 무엇이 올지는 런타임에 결정된다. 역할과 구현을 분리한다는 것을 한 문장으로 줄이면, 컴파일 타임 의존성과 런타임 의존성을 다르게 만드는 것이다. 자바에서 이 둘을 다르게 만드는 수단이 다형성이다.

    같은 프로그램을 타입 사이의 의존(소스 기준)과 객체 사이의 의존(힙 기준) 두 관점으로 나란히 그려, 클라이언트가 컴파일 타임에는 역할만 알고 런타임에는 구현 객체와 연결됨을 보여 준다. 좌우 2분할 구조 다이어그램. 흰 배경, 얇은 선, 파랑과 회색. 왼쪽 패널 제목 "컴파일 타임: 타입 사이의 의존". 가운데 위에 점선 테두리 상자 "Heater (역할)". 왼쪽에 실선 상자 "Thermostat", 여기서 "Heater"로 향하는 실선 화살표에 라벨 "사용". 오른쪽 아래에 실선 상자 세 개 "GasBoiler", "ElectricHeater", "HeatPump"가 세로로 놓이고 각각 "Heater"로 향하는 점선 화살표에 라벨 "구현". "Thermostat"과 구현 상자들 사이에는 화살표가 없고 그 사이에 옅은 회색 글씨 "서로 모른다". 오른쪽 패널 제목 "런타임: 객체 사이의 참조". 둥근 모서리 상자 "Thermostat 인스턴스" 안에 작은 칸 "heater". 그 칸에서 오른쪽 둥근 상자 "GasBoiler 인스턴스"로 굵은 실선 화살표. 그 아래 흐린 점선 둥근 상자 "ElectricHeater 인스턴스"로 향하는 흐린 점선 화살표에 라벨 "다른 실행에서는". 두 패널 사이 아래쪽에 한 줄 글씨 "소스는 같고, 연결만 달라진다". 왼쪽 그림은 코드를 읽으면 알 수 있고, 오른쪽 그림은 실행해야 정해진다. 둘이 달라지는 지점이 역할이다.

    의존의 방향이 뒤집힌다

    컴파일 타임 그림에서 화살표의 방향을 보자. 예제 1에서는 Thermostat에서 GasBoiler로 향했다. 온도를 언제 올리고 내릴지를 정하는 쪽이 장치를 어떻게 켜는지를 아는 쪽에 의존했다. 예제 3에서는 GasBoiler에서 Heater로 향하는 화살표가 생겼다. implements Heater라고 쓴 순간 구현 클래스는 인터페이스의 이름과 메서드 시그니처에 의존하게 된다. 실행 중의 호출은 여전히 온도 조절기에서 보일러로 흐르는데, 소스의 의존은 보일러에서 역할 쪽으로, 호출 흐름과 반대로 향한다.

    로버트 C. 마틴은 이 방향을 의존 역전 원칙(Dependency Inversion Principle, DIP)이라는 이름으로 정리했다. 그가 2020년 글 「Solid Relevance」에서 요약한 표현은 "Depend in the direction of abstraction. High level modules should not depend upon low level details."다. 추상화가 있는 방향으로 의존하고, 상위 수준의 모듈이 하위 수준의 세부에 의존하지 않게 하라는 말이다. 이 예제에서 상위 수준은 온도를 유지하는 정책이고, 하위 수준의 세부는 가스 밸브를 여는 방법이다. 정책이 세부를 모르게 되면 세부를 갈아 끼울 수 있다.

    한 가지 실용적인 귀결이 있다. Heater라는 역할은 구현하는 쪽이 아니라 사용하는 쪽의 필요에서 나왔다. 메서드 이름이 ignite가 아니라 heatOn인 것은 온도 조절기가 원하는 것이 "난방을 켜라"이기 때문이다. 역할을 구현의 사정에 맞춰 정하면(예를 들어 openGasValve()를 인터페이스에 넣으면) 다른 구현이 그 역할을 지킬 수 없게 된다.

    이제 세 번째 장치인 히트펌프를 추가한다. 예제 3의 구조에서 해야 할 일은 두 가지다. 새 클래스를 하나 쓰고, 구현을 고르는 한 줄을 바꾼다.

    "변경 없음"은 소스에만 해당하는 말이 아니다. 히트펌프를 추가하기 전과 후에 각각 전체를 컴파일해 Thermostat.class를 비교하면 두 파일은 바이트 단위로 같다. 당연한 결과다. 컴파일러가 Thermostat.class를 만들 때 쓰는 입력은 Thermostat.java와 그 안에서 이름이 불린 Heater의 선언뿐이고, 둘 다 그대로이기 때문이다. 아예 다시 컴파일하지 않아도 된다. 기존의 Heater.class와 Thermostat.class를 그대로 둔 채 HeatPump.java와 HomeMain.java만 컴파일해 실행해도 위와 같은 결과가 나온다.

    이것이 앞에서 세운 두 번째 기준, "바꾸지 않은 코드는 다시 검증할 필요가 없다"의 실제 모습이다. 온도 조절기의 클래스 파일이 같으니 그 동작도 같다. 온도 조절기를 만든 팀은 히트펌프가 추가되는 줄도 모르고 지나갈 수 있다. 히트펌프를 만드는 팀은 Heater 인터페이스 하나만 보고 일할 수 있다.

    히트펌프를 추가할 때, 구현에 직접 의존하는 구조에서는 클라이언트까지 수정되지만 역할에 의존하는 구조에서는 새 클래스와 구성 코드만 바뀐다는 것을 색으로 구분해 보여 준다. 좌우 2분할 비교 다이어그램. 흰 배경, 얇은 선. 범례: 빨강 "수정", 초록 "새로 추가", 회색 "그대로". 왼쪽 패널 제목 "구현에 직접 의존". 위에 빨간 상자 "HomeMain", 가운데 큰 빨간 상자 "Thermostat" 안에 작은 글씨 "if gas / electric / heatpump", 아래에 회색 상자 "GasBoiler", 회색 상자 "ElectricHeater", 초록 상자 "HeatPump". "Thermostat"에서 아래 세 상자로 각각 실선 화살표. 오른쪽 패널 제목 "역할에 의존". 위에 빨간 상자 "HomeMain" 옆에 작은 글씨 "한 줄", 가운데 회색 상자 "Thermostat", 그 오른쪽에 회색 점선 상자 "Heater". "Thermostat"에서 "Heater"로 실선 화살표. "Heater" 아래에 회색 상자 "GasBoiler", 회색 상자 "ElectricHeater", 초록 상자 "HeatPump"가 놓이고 각각 "Heater"로 점선 화살표. 오른쪽 패널의 "Thermostat" 위에 자물쇠 아이콘과 라벨 "클래스 파일 동일". 같은 요구를 처리하는데 빨간 상자의 수와 크기가 다르다. 오른쪽에서 빨간 것은 구성 코드 한 줄뿐이다.

    가짜 구현으로 클라이언트만 시험하기

    역할에만 의존하는 클라이언트는 진짜 장치 없이도 시험할 수 있다. 호출 횟수만 세는 구현을 하나 만들어 꽂으면 된다.

    public class FakeHeater implements Heater {
    int onCount;
    int offCount;

    @Override
    public void heatOn() {
        onCount++;
    }

    @Override
    public void heatOff() {
        offCount++;
    }
}
    public class ThermostatCheck {
    public static void main(String[] args) {
        FakeHeater fake = new FakeHeater();

    켜기 2회, 끄기 1회

    다섯 번의 온도 변화에 대해 켜기 명령이 두 번, 끄기 명령이 한 번 나갔다. 20도와 24도에서 중복 명령을 보내지 않는다는 온도 조절기의 논리가 장치와 무관하게 확인되었다. 예제 1의 구조에서는 이런 시험이 불가능하다. Thermostat이 new GasBoiler()를 직접 실행하므로, 온도 조절기를 시험하려면 반드시 보일러가 함께 움직인다. 실제 프로그램에서 서버 쪽이 데이터베이스나 외부 결제 시스템이라면 이 차이는 시험이 몇 초 걸리느냐 몇 분 걸리느냐, 혹은 시험을 할 수 있느냐 없느냐의 차이가 된다.

    OCP: 확장에는 열려 있고 수정에는 닫혀 있다

    앞 절에서 관찰한 성질에는 이름이 있다. 개방-폐쇄 원칙(Open-Closed Principle, OCP)이다. 출처부터 확인해 두자. 로버트 C. 마틴은 2014년 글 「The Open Closed Principle」에서 이 원칙을 1988년에 버트런드 메이어(Bertrand Meyer)가 저서 『Object Oriented Software Construction』에서 정의했다고 적는다. 마틴이 인용한 메이어의 정의에 따르면 모듈은 확장할 수 있으면 열려 있다고 하고, 다른 모듈이 사용할 수 있는 상태이면 닫혀 있다고 한다. 마틴 자신은 같은 글에서 이 원칙을 "You should be able to extend the behavior of a system without having to modify that system."이라고 풀어 쓴다. 시스템을 수정하지 않고도 시스템의 동작을 확장할 수 있어야 한다는 것이다.

    OCP는 흔히 SOLID라는 이름으로 묶이는 다섯 원칙 가운데 O에 해당한다. 마틴은 「Solid Relevance」에서 OCP를 "A Module should be open for extension but closed for modification."이라는 한 줄로 요약한다. 앞에서 본 DIP는 같은 묶음의 D다.

    처음 들으면 모순처럼 들린다. 기능을 늘리려면 코드를 고쳐야 하는데, 고치지 말고 늘리라는 말이기 때문이다. 예제에 대입하면 모순이 풀린다. "확장"은 히트펌프라는 새 동작이 시스템에 들어온 것이고, "수정에 닫혀 있다"는 그 과정에서 Thermostat의 소스도 클래스 파일도 바뀌지 않았다는 것이다. 열림과 닫힘은 같은 코드에 대한 말이 아니다. 새 구현이 들어올 자리(Heater라는 역할)가 열려 있고, 그 역할을 사용하는 기존 코드(Thermostat)가 닫혀 있다. 다형성이 이 둘을 동시에 성립하게 한다.

    OCP를 정확히 쓰려면 "무엇에 대해 닫혀 있는가"를 함께 말해야 한다. 예제 3의 Thermostat은 난방 장치의 종류가 늘어나는 변경에 대해 닫혀 있다. 다른 종류의 변경에는 닫혀 있지 않다. 목표 온도 근처에서 켜고 끄기를 되풀이하지 않도록 1도의 여유를 두자는 요구가 오면 Thermostat을 고쳐야 하고, 그것은 원칙 위반이 아니다. 온도를 어떻게 유지할지는 온도 조절기 자신의 책임이기 때문이다. 어떤 코드도 모든 종류의 변경에 닫혀 있을 수는 없다. 설계자가 하는 일은 자주 일어날 변경의 축을 골라 그 축에 역할을 세우는 것이다.

    그래서 OCP는 "인터페이스를 많이 만들라"는 규칙이 아니다. 마틴 자신도 2009년 글 「Getting a SOLID start」에서 SOLID 원칙들은 규칙이 아니며 휴리스틱이라고 적었다. 난방 장치가 영원히 하나뿐일 프로그램이라면 예제 1이 더 짧고 읽기 쉽다. 역할을 세우는 데는 파일 하나와 간접 단계 하나라는 비용이 들고, 그 비용은 변경이 실제로 왔을 때 회수된다. 두 번째 구현이 필요해지는 순간이 역할을 도입하기에 가장 정보가 많은 시점이다. 예제 2에서 본 것처럼 그때 분기를 택하면 세 번째, 네 번째에서 비용이 계속 불어난다.

    전략 패턴: 이 구조에 붙은 이름

    예제 3의 구조는 설계 패턴 목록에서 전략 패턴(Strategy pattern)이라는 이름으로 불린다. 이 이름은 감마, 헬름, 존슨, 블리시디스가 1994년에 낸 책 『Design Patterns: Elements of Reusable Object-Oriented Software』에서 왔다. 바꿔 끼울 수 있는 처리 방법들을 각각 객체로 감싸고 하나의 공통 타입으로 묶어서, 그 방법을 쓰는 쪽과 무관하게 방법을 교체할 수 있게 하는 구조다. 패턴의 용어로 예제를 다시 읽으면 다음과 같다.

    패턴의 참여자예제에서하는 일
    컨텍스트(Context)Thermostat변하지 않는 논리를 갖고, 변하는 부분은 전략에게 위임한다
    전략(Strategy)Heater변하는 부분의 역할을 선언한다
    구체 전략(Concrete Strategy)GasBoiler, ElectricHeater, HeatPump역할을 각자의 방식으로 구현한다

    패턴 이름을 아는 것의 쓸모는 구조를 한 단어로 전달할 수 있다는 데 있다. 구조 자체는 이미 다 보았다. 변하지 않는 코드와 변하는 코드를 가르고, 변하는 쪽에 역할을 세우고, 변하지 않는 쪽이 그 역할을 필드로 들고 있다가 호출한다. 예제 2에서 if (type.equals(...))로 쓰던 분기가 "어떤 객체를 꽂았는가"로 바뀐 것이다. 조건문으로 쓰던 선택을 객체의 종류로 옮기는 일은 다형성으로 할 수 있는 가장 흔한 리팩터링이다.

    JDK 안에서도 같은 구조를 쉽게 찾을 수 있다. 정렬이 대표적이다. 배열을 정렬하는 절차는 하나인데 무엇을 앞에 둘지의 기준은 상황마다 다르다. JDK는 그 기준을 java.util.Comparator라는 인터페이스로 분리했다. Comparator의 Javadoc은 비교자를 정렬 메서드(Collections.sort나 Arrays.sort 같은)에 넘겨 정렬 순서를 정밀하게 제어할 수 있다고 설명한다.

    import java.util.Arrays;
import java.util.Comparator;

public class SortDemo {
    public static void main(String[] args) {
        String[] names = {"park", "kim", "Lee"};

        Arrays.sort(names);
        System.out.println(Arrays.toString(names));

        Arrays.sort(names, String.CASE_INSENSITIVE_ORDER);
        System.out.println(Arrays.toString(names));

        Arrays.sort(names, Comparator.reverseOrder());
        System.out.println(Arrays.toString(names));
    }
}
    [Lee, kim, park]
[kim, Lee, park]
[park, kim, Lee]

    첫 정렬은 문자열의 기본 순서를 쓴다. 대문자 L의 문자 코드가 소문자들보다 작아서 Lee가 맨 앞에 온다. 두 번째와 세 번째 호출에서 달라진 것은 두 번째 인자로 넘긴 Comparator 객체뿐이다. 대소문자를 무시하는 비교자를 넘기면 kim이 앞으로 오고, 역순 비교자를 넘기면 순서가 뒤집힌다. Arrays.sort의 정렬 절차는 온도 조절기처럼 닫혀 있고, 새로운 정렬 기준은 Comparator를 구현한 객체를 추가하는 것으로 얼마든지 늘릴 수 있다. JDK를 만든 사람들은 우리가 어떤 기준으로 정렬할지 알 수 없었지만, 역할을 열어 두었기 때문에 Arrays.sort를 고치지 않고도 우리가 원하는 기준을 꽂을 수 있다.

    10회의 추상 클래스 예제와 비교해 두면 좋다. 그때 Printer는 공통 절차를 부모의 print에 두고 달라지는 부분을 추상 메서드 render로 남겨 자식이 채우게 했다. 변하는 부분을 상속으로 끼워 넣은 것이다. 전략 패턴은 변하는 부분을 별도의 객체로 만들어 필드로 들고 있다가 위임한다. 상속으로 끼운 부분은 클래스를 정의할 때 고정되지만, 필드로 들고 있는 객체는 생성할 때 정해지고 조립하는 쪽에서 자유롭게 고를 수 있다. 두 방식은 로드맵 뒤쪽의 스프링 핵심 원리 고급편에서 템플릿 메서드 패턴과 전략 패턴이라는 이름으로 다시 만난다.

    구현을 선택하고 주입하는 코드는 사라지지 않는다

    여기까지 읽으면 구현 클래스의 이름을 아는 코드가 프로그램에서 완전히 없어진 것처럼 보일 수 있다. 그렇지 않다. 인터페이스는 인스턴스를 만들 수 없으므로, 프로그램 어딘가에서 누군가는 new GasBoiler()나 new HeatPump()를 실행해야 한다. 예제 3에서 그 일을 한 것은 HomeMain이다. 히트펌프를 추가했을 때 표에서 "수정"으로 남은 유일한 기존 파일이 HomeMain.java였다는 점을 다시 보자. 수정은 0이 된 것이 아니라 한 곳으로 모였다.

    이 관찰을 구조로 정리하면 프로그램의 코드가 두 영역으로 나뉜다.

    • 사용 영역. 역할만 알고 일하는 코드다. Thermostat이 여기 속한다. 구현의 이름을 모르고, 구현이 늘어도 바뀌지 않는다. 프로그램의 대부분을 차지해야 하는 코드다.
    • 구성 영역. 어떤 구현을 쓸지 선택해 객체를 만들고(생성), 만든 객체를 필요한 곳에 건네 연결하는(주입) 코드다. HomeMain의 처음 두 줄이 여기 속한다. 구현의 이름을 알고, 구성이 달라지면 바뀐다. 작고 한곳에 모여 있어야 하는 코드다.

    OCP가 닫아 주는 것은 사용 영역이다. 구성 영역은 원래 바뀌라고 있는 곳이다. 그래서 "역할과 구현을 분리했는데도 main을 고쳐야 하니 OCP를 지키지 못했다"고 볼 일이 아니다. 지켜야 할 것은 구성 영역의 코드가 사용 영역으로 새어 들어가지 않게 하는 것이다. Thermostat 안에 new GasBoiler()가 한 번이라도 등장하면 두 영역이 섞이고, 예제 1의 문제가 되돌아온다.

    구현 클래스의 이름을 아는 구성 코드가 객체를 만들어 사용 영역의 클라이언트에 주입하고, 사용 영역은 역할만 안다는 경계를 보여 준다. 가로로 긴 구조 다이어그램. 흰 배경, 얇은 선. 화면을 세로 점선으로 좌우로 나눈다. 왼쪽 영역 상단 라벨 "구성 영역" 아래 작은 글씨 "구현의 이름을 안다". 그 안에 상자 "HomeMain"이 있고 상자 안에 두 줄 "new HeatPump()"와 "new Thermostat(heater, 22)". 오른쪽 영역 상단 라벨 "사용 영역" 아래 작은 글씨 "역할만 안다". 그 안에 왼쪽부터 상자 "Thermostat", 점선 상자 "Heater", 그리고 맨 오른쪽에 세로로 상자 "GasBoiler", "ElectricHeater", "HeatPump". "Thermostat"에서 "Heater"로 실선 화살표, 세 구현 상자에서 "Heater"로 점선 화살표. "HomeMain"에서 점선 경계를 넘어 "HeatPump"로 향하는 주황 화살표에 라벨 "생성", "HomeMain"에서 "Thermostat"으로 향하는 주황 화살표에 라벨 "주입". 왼쪽 영역 아래에 글씨 "구성이 바뀌면 여기만 수정", 오른쪽 영역 아래에 글씨 "구현이 늘어도 그대로". 구현의 이름을 아는 코드는 없어지지 않는다. 한곳에 모일 뿐이다.

    분기도 한 곳으로 모인다

    어떤 구현을 쓸지를 실행할 때 입력으로 받아야 한다면 조건 분기가 다시 필요하다. 그 분기를 둘 자리가 구성 영역이다.

    public class Heaters {
    public static Heater of(String kind) {
        switch (kind) {
            case "gas":
                return new GasBoiler();
            case "electric":
                return new ElectricHeater();
            case "heatpump":
                return new HeatPump();
            default:
                throw new IllegalArgumentException("알 수 없는 난방 장치: " + kind);
        }
    }
}
    public class HomeMain2 {
    public static void main(String[] args) {
        String kind = args.length > 0 ? args[0] : "gas";
        Heater heater = Heaters.of(kind);
        Thermostat thermostat = new Thermostat(heater, 22);
        thermostat.onTemperature(19);
    }
}

    인자 없이 실행하면 "가스 보일러 점화"가, electric을 주면 "전기 히터 켬"이, heatpump를 주면 "히트펌프 난방 운전"이 출력된다. 예제 2에 있던 종류별 분기가 돌아온 것처럼 보이지만 차이가 셋 있다. 분기가 프로그램 전체에 딱 한 군데다. 예제 2에서는 장치를 쓰는 지점마다 분기가 있었다. 분기가 하는 일이 객체 생성뿐이어서 온도 조절 논리와 섞이지 않는다. 그리고 잘못된 종류가 들어오면 조용히 넘어가지 않고 프로그램이 시작할 때 예외로 드러난다. 네 번째 장치가 추가되면 Heaters에 case 하나가 늘 뿐 Thermostat은 여전히 닫혀 있다.

    구성 코드를 소스 밖으로 내보내는 방법들

    구성 코드가 "구현의 이름을 아는 유일한 코드"라면, 그 이름을 자바 소스가 아닌 다른 곳에 적어 두는 길도 생각할 수 있다. JDK에는 이를 위한 표준 장치인 java.util.ServiceLoader가 있다. Javadoc의 용어로 서비스(service)는 잘 알려진 인터페이스나 클래스이고, 서비스 제공자(service provider)는 그것을 구현하거나 상속한 클래스다. Javadoc은 애플리케이션 코드가 서비스만 참조하고 서비스 제공자는 참조하지 않는다고 적는다. 클래스패스에 놓이는 JAR은 META-INF/services 디렉터리의 제공자 설정 파일에 구현 클래스의 이름을 적어 자신을 알린다. 구현의 이름이 자바 소스에서 배포물의 설정 파일로 옮겨 간 것이다.

    데이터베이스 접속에 쓰는 JDBC가 이 구조의 익숙한 예다. 애플리케이션은 java.sql 패키지의 인터페이스에 대고 코드를 쓰고, 실제 구현인 드라이버는 데이터베이스 회사가 만든다. DriverManager의 Javadoc은 DriverManager가 초기화될 때 java.sql.Driver의 서비스 제공자를 서비스 제공자 로딩 방식으로 읽어 들인다고 설명한다. 애플리케이션 소스에 특정 데이터베이스 드라이버 클래스의 이름이 없어도, 클래스패스에 어떤 드라이버 JAR을 올려 두느냐에 따라 연결되는 구현이 정해진다.

    스프링 프레임워크는 이 생각을 애플리케이션 전체로 넓힌다. 객체가 수백 개인 프로그램에서는 누가 누구를 생성해 누구에게 건네는지를 적은 구성 코드가 그 자체로 큰 덩어리가 된다. 스프링의 IoC 컨테이너는 그 구성 영역을 맡는 도구다. 스프링 공식 문서는 의존성 주입을, 객체가 자신의 의존 대상을 생성자 인자 등으로만 정의하고 컨테이너가 빈을 만들 때 그 의존 대상을 주입하는 과정이라고 정의한다. 그리고 이것이 객체가 클래스를 직접 생성해 의존 대상을 스스로 마련하던 것과 정반대여서 제어의 역전(Inversion of Control)이라는 이름이 붙었다고 설명한다. 문서가 말하는 "직접 생성"이 예제 1의 new GasBoiler()이고, "생성자 인자로만 정의"가 예제 3의 Thermostat(Heater heater, int target)이다.

    그러니 스프링은 새로운 원리를 들여오는 것이 아니다. 이 회차에서 손으로 쓴 HomeMain의 두 줄, 곧 구현을 골라 생성하고 클라이언트에 주입하는 일을 대신해 주는 것이다. 로드맵의 스프링 핵심 원리 기본편에서 이 주제를 이어서 만난다. 다형성만으로는 클라이언트가 구현을 선택하는 책임까지 떼어 낼 수 없고, 그 책임을 맡을 별도의 존재가 필요하다. 그때 이 회차의 온도 조절기를 떠올리면 된다.

    흔한 오해와 함정

    "인터페이스 타입으로 선언했으니 분리가 끝났다"

    필드를 private final Heater heater = new GasBoiler();로 쓰는 코드를 자주 본다. 타입 선언은 역할이지만 생성이 구현에 묶여 있다. 이 클래스의 상수 풀에는 GasBoiler가 그대로 남고, 구현을 바꾸려면 이 클래스를 고쳐야 한다. 세 가지 묶임 가운데 하나만 푼 것이다. 역할과 구현의 분리는 new를 클라이언트 밖으로 내보내야 완성된다.

    "필요하면 클라이언트가 구현을 확인하면 된다"

    역할 타입으로 받아 놓고 안에서 if (heater instanceof GasBoiler)로 구현을 확인해 다운캐스팅하는 코드는 예제 2로 돌아가는 길이다. 클라이언트가 다시 구현의 이름을 알게 되고, 새 구현이 들어오면 그 분기를 빠져나가 조용히 다르게 동작한다. 특정 구현에만 필요한 처리가 있다면 그 처리는 구현 클래스 안으로 들어가야 한다. 가스 밸브 점검이 필요하면 GasBoiler.heatOn()이 스스로 하면 된다.

    "메서드 시그니처만 맞추면 역할을 구현한 것이다"

    컴파일러가 검사하는 것은 시그니처까지다. heatOff()를 호출해도 실제로는 멈추지 않는 구현, heatOn()을 두 번 부르면 예외를 던지는 구현도 컴파일은 된다. 그러나 온도 조절기는 "끄라고 하면 꺼진다"는 것을 전제로 heating 상태를 관리하므로, 그런 구현이 꽂히면 클라이언트의 논리가 틀어진다. 역할은 메서드 목록에 더해 그 메서드가 지켜야 할 동작의 약속까지 포함한다. 마틴은 SOLID의 L에 해당하는 리스코프 치환 원칙을 "A program that uses an interface must not be confused by an implementation of that interface."라고 요약한다. 인터페이스를 사용하는 프로그램이 그 구현 때문에 혼란에 빠져서는 안 된다는 뜻이다. 구현을 갈아 끼울 수 있다는 다형성의 이득은 모든 구현이 이 약속을 지킬 때만 유효하다.

    "역할은 한 번 정하면 그만이다"

    구현의 변경은 싸지만 역할의 변경은 비싸다. Heater에 세기를 조절하는 setPower(int level)을 추가하면 모든 구현 클래스가 컴파일되지 않고, 다시 컴파일하지 않은 옛 구현은 그 메서드가 호출되는 순간 AbstractMethodError를 낸다(10회). 역할은 클라이언트와 모든 구현이 함께 기대고 있는 지점이어서, 흔들리면 양쪽이 다 흔들린다. 역할에는 클라이언트가 실제로 필요로 하는 최소한의 메서드만 두고, 특정 구현에서만 의미 있는 것을 넣지 않는다.

    "코드를 읽으면 무엇이 실행되는지 알 수 있다"

    컴파일 타임 의존성과 런타임 의존성을 다르게 만든 대가가 있다. Thermostat.java만 읽어서는 heater.heatOn()이 어느 클래스의 코드를 실행하는지 알 수 없다. 답은 구성 영역에 있다. 구성 코드가 한곳에 모여 있으면 그곳만 보면 되지만, new가 여기저기 흩어져 있거나 설정 파일과 조건에 따라 달라지면 추적이 어려워진다. 유연함을 얻은 만큼 "지금 어떤 구현이 연결되어 있는가"를 쉽게 확인할 수 있게 해 두는 것이 설계의 일부다.

    기본편을 마치며: 이어지는 길

    이 권은 데이터를 묶는 클래스에서 출발해 참조, 생성자, 접근 제어, 메모리 구조와 static, final, 상속, 다형성까지 왔다. 앞쪽의 주제들이 객체 하나를 올바르게 만드는 방법이었다면, 상속과 다형성은 객체와 객체를 연결하는 방법이었다. 그리고 이 회차에서 그 연결을 어떤 방향으로 맺어야 변경에 강한지를 보았다. 클라이언트는 역할에 의존하고, 구현도 역할에 의존하며, 둘을 맺어 주는 일은 제삼의 코드가 한다.

    이 구조는 뒤에서 계속 다시 나온다. 중급편에서 다루는 컬렉션은 List라는 역할과 ArrayList, LinkedList라는 구현으로 되어 있어서, 역할 타입으로 받은 코드는 구현을 바꿔도 그대로다. 스프링 핵심 원리 기본편은 구성 영역을 컨테이너에 맡기는 이야기이고, 고급편의 프록시는 같은 역할을 구현하면서 다른 구현을 감싸는 객체를 꽂아 기존 코드를 고치지 않고 기능을 더하는 이야기다. 어느 쪽이든 바닥에는 이 권의 09회부터 11회까지에서 본 것, 곧 역할 타입의 참조와 객체의 클래스를 기준으로 한 메서드 선택이 있다.

    이 장의 핵심

    역할과 구현을 분리한다는 것은 컴파일 타임 의존성과 런타임 의존성을 다르게 만드는 일이다. 클라이언트의 소스와 클래스 파일에는 역할의 이름만 남기고, 실제 구현과의 연결은 실행할 때 구성 코드가 맺는다. 그러면 새 구현이 추가되어도 클라이언트는 바이트 하나 바뀌지 않는다(OCP). 구현의 이름을 아는 코드는 사라지지 않고 구성 영역 한곳으로 모이며, 그 영역을 맡아 주는 도구가 스프링의 DI 컨테이너다.
    클라이언트와 서버
    메서드 호출로 일을 부탁하는 객체가 클라이언트, 부탁을 받아 처리하는 객체가 서버다. 설계는 이 둘 사이의 연결을 어떻게 맺을지를 다룬다.
    역할과 구현의 분리
    클라이언트가 "무엇을 해 주는가"(역할, 인터페이스)만 알고 "어떻게 하는가"(구현 클래스)는 모르게 하는 것. 타입 선언, 객체 생성, 호출하는 메서드 이름 세 곳에서 구현의 흔적을 지워야 완성된다.
    컴파일 타임 의존성
    타입 사이의 관계로, 소스와 클래스 파일의 상수 풀에 적힌 이름으로 확인된다. 역할에 의존하는 클라이언트의 상수 풀에는 구현 클래스의 이름이 없다.
    런타임 의존성
    실행 중인 객체 사이의 참조 관계로, 구성 코드가 객체를 만들어 연결할 때 정해진다. 같은 클래스 파일로도 실행마다 달라질 수 있다.
    의존 방향의 역전(DIP)
    클라이언트가 구현에 의존하던 화살표를, 클라이언트와 구현이 모두 역할에 의존하도록 바꾼다. 호출은 클라이언트에서 구현으로 흐르지만 소스 의존은 구현에서 역할로 향한다.
    OCP
    확장에는 열려 있고 수정에는 닫혀 있어야 한다는 원칙. 버트런드 메이어가 1988년에 정의했다. 새 구현이 추가되어도 역할을 사용하는 기존 코드는 바뀌지 않는다는 뜻이며, 어떤 변경의 축에 대해 닫혀 있는지를 함께 말해야 한다.
    전략 패턴
    변하지 않는 논리(컨텍스트)가 변하는 부분(전략)을 역할 타입의 필드로 들고 위임하는 구조. Arrays.sort와 Comparator가 JDK의 예다.
    구성 영역과 의존성 주입
    구현을 선택해 생성하고 클라이언트에 건네는 코드는 사라지지 않고 한곳에 모인다. 필요한 객체를 스스로 만들지 않고 생성자 등으로 건네받는 것이 의존성 주입이고, 이 구성 영역을 맡는 도구가 스프링의 DI 컨테이너다.

    역할을 언제 세울지는 원칙이 아니라 변경의 예측으로 정한다. 구현이 하나뿐이고 바뀔 조짐이 없는 값 객체나 단순 계산 클래스에 인터페이스를 씌우면 파일과 간접 단계만 늘어난다. 반면 클라이언트 바깥의 세계와 닿는 지점, 곧 데이터베이스, 외부 시스템 호출, 파일, 현재 시각처럼 시험할 때 진짜를 쓰기 어렵거나 나중에 교체될 가능성이 큰 곳은 구현이 하나여도 역할을 먼저 세울 값어치가 있다. 가짜 구현을 꽂아 클라이언트만 시험할 수 있다는 이득이 첫날부터 생기기 때문이다. 판단이 서지 않으면 두 번째 구현이 실제로 필요해졌을 때 도입해도 늦지 않다. 그때 분기를 택하지 않는 것이 중요하다.

    코드 리뷰에서 가장 먼저 볼 것은 인터페이스의 유무가 아니라 new의 위치다. 협력 객체를 클래스 안에서 직접 생성하고 있다면 그 클래스는 구현에 묶여 있다. 생성이 한곳(구성 코드, 팩토리, 컨테이너 설정)에 모여 있고 나머지 코드가 역할 타입으로 받아 쓰고 있다면 구조는 건강하다. 반대로 역할 타입으로 받은 뒤 instanceof로 구현을 확인하는 코드가 보이면, 역할이 클라이언트의 필요를 다 담지 못했거나 특정 구현의 사정이 클라이언트로 새어 나온 신호다.

    이 구조에는 운영에서 치르는 비용도 있다. 어떤 구현이 실행될지가 소스가 아니라 구성에서 정해지므로, 잘못된 구현이 연결되는 실수는 컴파일 오류가 아니라 실행 중의 이상 동작으로 나타난다. 시험 환경에서는 가짜 구현이, 운영 환경에서는 진짜 구현이 꽂히는 식의 구성 차이가 장애 원인이 되기도 한다. 그래서 구성 결과를 눈으로 확인할 수 있게 해 두는 편이 좋다. 애플리케이션이 시작할 때 어떤 구현이 선택되었는지 로그로 남기고, 알 수 없는 선택값은 조용히 기본값으로 넘기지 말고 시작 단계에서 실패하게 한다.

    역할 자체의 변경은 가장 신중해야 할 변경이다. 구현 클래스의 내부는 마음대로 고쳐도 다른 코드에 영향이 없지만, 인터페이스의 메서드를 바꾸면 클라이언트와 모든 구현이 함께 움직여야 한다. 다른 팀이나 외부에 공개한 역할이라면 사실상 되돌릴 수 없다. 역할은 구현의 편의가 아니라 클라이언트가 필요로 하는 것을 기준으로 작게 정의하고, 한 역할이 여러 클라이언트의 서로 다른 요구를 모두 떠안아 커지기 시작하면 역할을 나누는 것을 검토한다.

Thermostat.java가 이름으로 참조하는 다른 타입은 Heater뿐이고, Thermostat.java와 Heater의 선언이 모두 그대로이기 때문이다. HeatPump가 실행 중에 로드되지 않았기 때문이다. 클래스 파일의 내용은 그 소스와 소스가 참조하는 타입의 선언으로 정해진다. 역할에만 의존하는 클라이언트는 구현이 몇 개 추가되든 컴파일 입력이 달라지지 않는다. 이것이 컴파일 타임 의존성이 역할에서 멈춘다는 말의 구체적인 의미다. 전체를 다시 컴파일했으므로 건너뛴 것이 아니고, final 여부나 실행 중의 로딩은 컴파일 결과와 무관하다. OCP에서 "수정에 닫혀 있다"는 말의 의미로 가장 알맞은 것은? 기능이 추가될 때 프로그램의 어떤 파일도 수정되지 않는다. 새 구현이 추가될 때, 그 역할을 사용하는 기존 클라이언트 코드를 고치지 않아도 된다. 클래스를 final로 선언해 상속을 막는다. 필드를 private으로 선언해 외부에서 값을 바꾸지 못하게 한다. 닫혀 있는 것은 역할을 사용하는 쪽의 코드다. 구현을 골라 주입하는 구성 코드는 새 구현을 쓰려면 수정되므로 "어떤 파일도 수정되지 않는다"는 과장이다. final 클래스나 private 필드는 각각 상속 금지와 캡슐화의 이야기로, OCP가 말하는 폐쇄와 다른 주제다. 클라이언트 클래스가 필드를 private final Heater heater = new GasBoiler();로 선언했다. 이 코드에 대한 설명으로 옳은 것은? 필드 타입이 인터페이스이므로 이 클래스의 상수 풀에는 GasBoiler가 등장하지 않는다. 다형적 참조를 쓰고 있으므로 구현을 바꿀 때 이 클래스를 고칠 필요가 없다. 인터페이스 타입 필드에는 구현 객체를 대입할 수 없으므로 컴파일 오류다. 타입 선언은 역할이지만 생성이 구현에 묶여 있어, 구현을 바꾸려면 이 클래스를 수정해야 한다. 클라이언트가 구현에 묶이는 지점은 타입 선언, 객체 생성, 구현 고유의 메서드 호출 세 곳이다. 이 코드는 첫째만 풀었다. new GasBoiler()가 있으므로 클래스 파일에 GasBoiler와 그 생성자에 대한 참조가 남고, 다른 구현을 쓰려면 이 줄을 고쳐야 한다. 생성을 클래스 밖으로 내보내고 생성자로 주입받아야 분리가 완성된다. 컴파일 타임 의존성과 런타임 의존성에 대한 설명으로 옳은 것은? 컴파일 타임 의존성은 타입 사이의 관계로 소스를 읽어 알 수 있고, 런타임 의존성은 객체 사이의 참조로 실행할 때 구성 코드가 맺는다. 역할을 두면 둘이 서로 달라질 수 있다. 둘은 항상 같은 모양이다. 소스에 없는 관계가 실행 중에 생길 수는 없다. 런타임 의존성은 클래스 파일의 상수 풀에 기록되어 있다. 인터페이스를 쓰면 컴파일 타임 의존성이 완전히 사라진다. 역할 타입의 필드는 컴파일 타임에는 역할까지만 가리키고, 실행 중에는 그 역할을 구현한 어떤 객체든 가리킬 수 있다. 그래서 타입 사이의 그림과 객체 사이의 그림이 달라진다. 상수 풀에 기록되는 것은 컴파일 타임의 이름들이고, 인터페이스를 써도 클라이언트는 그 인터페이스에, 구현은 그 인터페이스에, 구성 코드는 구현에 여전히 의존한다. 역할과 구현을 분리한 뒤에도 프로그램 안에 구현 클래스의 이름을 아는 코드가 남아야 하는 이유는? 자바 컴파일러가 인터페이스마다 기본 구현 클래스를 하나씩 지정하도록 요구하기 때문이다. JVM이 invokeinterface를 실행하려면 호출하는 쪽의 상수 풀에 구현 클래스 이름이 있어야 하기 때문이다. 인터페이스는 인스턴스를 만들 수 없으므로, 누군가는 구현 클래스를 골라 객체를 생성하고 클라이언트에 건네야 하기 때문이다. 구현 클래스의 이름을 모르면 클라이언트가 메서드 시그니처를 알 수 없기 때문이다. 객체는 구체 클래스로만 만들 수 있다. 그래서 구현을 선택해 생성하고 주입하는 구성 코드가 반드시 필요하고, 설계의 목표는 그 코드를 한곳에 모으는 것이다. 그 자리를 손으로 쓴 것이 예제의 main이고, 대신 맡아 주는 것이 스프링의 DI 컨테이너다. invokeinterface는 인터페이스 메서드에 대한 참조만으로 동작하며, 시그니처는 인터페이스에 선언되어 있다.
    클라이언트와 서버(client, server)
    객체 협력에서 요청을 보내는 객체와 요청을 받아 처리하는 객체. 네트워크가 아니라 두 객체 사이의 역할을 가리킨다.
    역할(role)
    서버가 클라이언트에게 해 주기로 한 일의 약속. 자바에서는 주로 인터페이스로 표현한다.
    구현(implementation)
    역할의 약속을 실제로 수행하는 코드. 인터페이스를 구현한 클래스.
    컴파일 타임 의존성(compile-time dependency)
    소스에 이름이 등장해 컴파일에 필요한 타입 사이의 관계. 클래스 파일의 상수 풀에 흔적이 남는다.
    런타임 의존성(run-time dependency)
    실행 중에 한 객체가 다른 객체를 참조하는 관계. 힙의 참조로 존재한다.
    개방-폐쇄 원칙(Open-Closed Principle, OCP)
    모듈은 확장에는 열려 있고 수정에는 닫혀 있어야 한다는 원칙. 버트런드 메이어가 1988년 저서에서 정의했고, 로버트 C. 마틴이 SOLID의 하나로 소개했다.
    의존 역전 원칙(Dependency Inversion Principle, DIP)
    추상화가 있는 방향으로 의존하고, 상위 수준의 모듈이 하위 수준의 세부에 의존하지 않게 하라는 원칙.
    전략 패턴(Strategy pattern)
    바꿔 끼울 처리 방법을 역할 타입의 객체로 분리해, 그것을 쓰는 쪽을 고치지 않고 교체할 수 있게 하는 구조.
    의존성 주입(dependency injection)
    객체가 필요한 협력 객체를 스스로 만들지 않고 생성자 인자 등으로 밖에서 건네받는 방식. 생성자로 받는 형태가 생성자 주입이다.
    구성 코드
    어떤 구현을 쓸지 선택해 객체를 생성하고 서로 연결하는 코드. 구현 클래스의 이름을 아는 유일한 영역이어야 한다.
