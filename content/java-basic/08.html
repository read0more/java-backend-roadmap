    같은 코드를 여러 번 쓰는 문제

    회사의 직원을 다루는 프로그램을 만든다고 하자. 관리자와 개발자가 있다. 둘 다 이름과 기본급이 있고, 업무를 하고, 월급을 받는다. 관리자는 여기에 더해 팀원 수를 갖고 결재를 하며, 개발자는 주로 쓰는 언어를 갖고 서비스를 배포한다. 지금까지 배운 것만으로 이 둘을 클래스로 만들면 다음과 같다.

    public class Manager {
    String name;
    int baseSalary;
    int teamSize;

    void work() {
        System.out.println(name + ": 업무를 처리한다");
    }

    int monthlyPay() {
        return baseSalary;
    }

    void approve() {
        System.out.println(name + ": 결재한다 (팀원 " + teamSize + "명)");
    }
}

public class Engineer {
    String name;
    int baseSalary;
    String language;

    void work() {
        System.out.println(name + ": 업무를 처리한다");
    }

    int monthlyPay() {
        return baseSalary;
    }

    void deploy() {
        System.out.println(name + ": " + language + " 서비스를 배포한다");
    }
}

    name, baseSalary, work(), monthlyPay()가 두 클래스에 글자 그대로 반복된다. 직원의 종류가 디자이너, 영업 담당으로 늘어나면 같은 코드가 그 수만큼 늘어난다. 중복된 코드는 분량의 문제가 아니라 일관성의 문제다. "업무를 처리한다"는 문구를 고치거나 월급 계산에 공통 수당을 넣으려면 모든 클래스를 빠짐없이 고쳐야 하고, 한 곳이라도 빠뜨리면 직원의 종류에 따라 다르게 동작하는 프로그램이 된다.

    두 클래스가 공유하는 부분은 우연히 같은 것이 아니다. 관리자도 개발자도 직원이기 때문에 같다. 이 "직원이라면 누구나 갖는 것"을 한 곳에 정의해 두고, 관리자와 개발자는 거기에 자기만의 것을 더하는 식으로 클래스를 만들 수 있으면 중복이 사라진다. 이것이 상속(inheritance)이다.

    상속 관계: extends가 정하는 것

    공통 부분을 Employee라는 클래스로 뽑아내고, Manager와 Engineer가 extends 키워드로 그것을 물려받게 한다.

    public class Employee {
    String name;
    int baseSalary;

    void work() {
        System.out.println(name + ": 업무를 처리한다");
    }

    int monthlyPay() {
        return baseSalary;
    }
}

public class Manager extends Employee {
    int teamSize;

    void approve() {
        System.out.println(name + ": 결재한다 (팀원 " + teamSize + "명)");
    }
}

public class Engineer extends Employee {
    String language;

    void deploy() {
        System.out.println(name + ": " + language + " 서비스를 배포한다");
    }
}

public class CompanyMain {
    public static void main(String[] args) {
        Manager manager = new Manager();
        manager.name = "한지우";        // Employee에 선언된 필드
        manager.baseSalary = 5_000_000;
        manager.teamSize = 4;           // Manager에 선언된 필드
        manager.work();                 // Employee에 선언된 메서드
        manager.approve();              // Manager에 선언된 메서드

        Engineer engineer = new Engineer();
        engineer.name = "오세린";
        engineer.language = "Java";
        engineer.work();
        engineer.deploy();
    }
}

    Manager 클래스의 소스에는 name도 work()도 적혀 있지 않지만, Manager 타입의 변수로 둘 다 사용할 수 있다. 용어를 정리하자. 물려주는 클래스를 부모 클래스 또는 슈퍼클래스(superclass), 물려받는 클래스를 자식 클래스 또는 서브클래스(subclass)라고 한다. 여기서는 Employee가 부모, Manager와 Engineer가 자식이다.

    상속 관계에는 몇 가지 구조적 규칙이 있다.

    • 방향이 있다. 자식 클래스의 선언에 부모가 적힌다. 부모 클래스의 소스에는 자식에 대한 정보가 전혀 없다. Employee는 자신을 상속한 클래스가 몇 개인지, 무엇인지 알지 못한다. 그래서 Employee 타입으로는 approve()를 호출할 수 없다.
    • 부모는 하나다. JLS 8장은 Object를 제외한 모든 클래스가 정확히 하나의 기존 클래스를 확장한다고 규정한다. extends 뒤에는 클래스를 하나만 쓸 수 있다. 부모가 둘이면 양쪽에 같은 이름의 필드나 같은 시그니처의 메서드가 있을 때 어느 쪽을 물려받는지 정할 수 없게 되는데, 자바는 클래스에 대해서는 이 가능성을 문법 단계에서 없앴다.
    • 모든 클래스의 꼭대기에는 Object가 있다. extends를 쓰지 않은 클래스의 직접 슈퍼클래스는 Object다(JLS §8.1.4). Employee는 Object를 상속하고, Manager는 Employee를 거쳐 Object까지 물려받는다. 상속은 여러 단계로 이어질 수 있다.
    • 자식은 부모보다 넓다. extends는 "확장한다"는 뜻이다. 자식은 부모가 가진 것을 모두 갖고 거기에 자기 것을 더한다. 관리자는 직원이지만(is-a) 직원이 모두 관리자인 것은 아니다.
                Object
              ▲
              │ extends (생략됨)
           Employee          name, baseSalary, work(), monthlyPay()
           ▲      ▲
  extends  │      │  extends
       Manager  Engineer
   teamSize      language
   approve()     deploy()

화살표는 자식에서 부모를 향한다. 자식이 부모를 안다.

    무엇이 상속되는가

    "물려받는다"는 말을 명세의 용어로 정확히 하면 이렇다. JLS §8.2에 따르면 클래스의 멤버(member)는 그 클래스 본문에 선언된 필드·메서드와, 직접 슈퍼클래스에서 상속받은 멤버로 이루어진다. 그리고 다음 두 가지는 상속되지 않는다고 명시한다.

    • private으로 선언된 멤버는 자식 클래스에 상속되지 않는다. (다른 패키지의 자식에게는 protected와 public 멤버만 상속된다. 접근 제어는 뒤에서 따로 다룬다.)
    • 생성자, static 초기화 블록, 인스턴스 초기화 블록은 멤버가 아니므로 상속되지 않는다.

    여기서 주의할 것이 있다. "상속되지 않는다"는 "자식 클래스의 멤버로 취급되지 않아서 자식의 코드에서 이름으로 쓸 수 없다"는 뜻이지, "자식 객체 안에 존재하지 않는다"는 뜻이 아니다. 부모의 private 필드는 자식 객체 안에 분명히 들어 있다. 이 차이는 메모리 구조를 보면 분명해진다.

    상속과 메모리 구조: 객체는 하나, 그 안에 부모 부분이 있다

    new Manager()를 실행하면 힙에 무엇이 만들어지는가. 흔한 오해는 Employee 객체와 Manager 객체가 따로 만들어져 서로 연결된다는 것이다. 그렇지 않다. 만들어지는 객체는 하나이고, 참조값도 하나다. 그 하나의 객체 안에 Employee에 선언된 필드와 Manager에 선언된 필드가 모두 들어 있다.

    JLS §12.5는 이를 이렇게 규정한다. 새 클래스 인스턴스가 만들어질 때, 그 클래스에 선언된 모든 인스턴스 변수와 각 슈퍼클래스에 선언된 모든 인스턴스 변수를 담을 공간이 할당된다. 숨겨진(hidden) 인스턴스 변수도 포함한다. Manager 객체 하나에는 name, baseSalary, teamSize 세 개의 필드를 위한 자리가 있다.

    메서드는 객체 안에 없다. 앞 회차에서 본 것처럼 메서드의 코드는 클래스 단위로 메서드 영역에 한 벌만 있고, 객체는 인스턴스 필드의 값만 가진다. 상속에서도 마찬가지다. work()의 코드는 Employee 클래스 정보에 한 벌 있을 뿐이고, Manager 객체가 백 개 만들어져도 복사되지 않는다. Manager 클래스 정보는 자신의 슈퍼클래스가 Employee라는 사실을 기록하고 있어서, JVM은 필요할 때 이 연결을 따라 올라간다.

    클래스도 부모가 먼저 준비된다

    Manager 객체가 Employee에 선언된 필드를 포함해야 하므로, JVM은 Manager를 쓰기 전에 Employee에 대해 알아야 한다. JLS §12.4.1은 클래스가 초기화될 때 그 슈퍼클래스가 아직 초기화되지 않았다면 먼저 초기화된다고 규정한다. static 초기화 블록으로 확인할 수 있다.

    class Employee {
    static { System.out.println("Employee 클래스 초기화"); }
    Employee() { System.out.println("Employee 생성자"); }
}

class Manager extends Employee {
    static { System.out.println("Manager 클래스 초기화"); }
    Manager() { System.out.println("Manager 생성자"); }
}

public class InitOrder {
    public static void main(String[] args) {
        System.out.println("main 시작");
        new Manager();
        new Manager();
    }
}

    HotSpot에서의 객체 배치

    객체 안에서 필드가 실제로 어떤 순서로 놓이는지는 명세가 정하지 않는다. JVMS §2.7은 JVM이 객체의 내부 구조를 특정 형태로 요구하지 않는다고 밝힌다. 따라서 아래 내용은 OpenJDK의 HotSpot 구현에 한정된 설명이다.

    HotSpot 용어집은 모든 객체가 헤더로 시작하며, 헤더는 동기화 상태와 해시 코드 등을 담는 mark word와 그 객체의 클래스 메타데이터를 가리키는 klass pointer로 이루어진다고 설명한다. 객체가 "나는 Manager다"라는 사실을 아는 것은 이 klass pointer 덕분이다. 헤더 뒤에 인스턴스 필드가 놓인다. OpenJDK 21의 필드 배치 코드는 클래스의 배치를 계산할 때 먼저 슈퍼클래스의 배치를 그대로 재구성하고, 그다음에 현재 클래스가 선언한 필드를 배치한다.

    이 방식의 결과로 Employee에 선언된 필드는 Employee 객체에서든 Manager 객체에서든 객체 시작점에서 같은 거리에 놓인다. Employee의 메서드 work()는 this.name을 읽을 때 자신이 받은 객체가 실제로 Employee인지 Manager인지 구분할 필요가 없다. 부모에 선언된 필드의 위치가 자식 객체에서도 그대로이기 때문이다. 다만 자식의 필드가 항상 부모의 필드 뒤에만 놓이는 것은 아니다. OpenJDK 21의 기본 설정(UseEmptySlotsInSupers)에서는 부모의 배치에 정렬 때문에 남은 빈 자리가 있으면 자식의 필드가 그 자리에 들어갈 수 있다. "자식 객체 안에 부모 부분이 들어 있다"는 말은 구현에서 "부모의 필드가 부모 객체에서와 같은 위치에 들어 있다"는 뜻으로 성립한다.

    new Manager()로 힙에 객체가 하나만 만들어지고, 그 안에 Employee에 선언된 필드와 Manager에 선언된 필드가 함께 있으며, 메서드 코드는 메서드 영역의 클래스 정보에 있다는 것을 보여 준다. 흰 배경의 메모리 구조도. 세 영역을 좌에서 우로 배치한다. 왼쪽 영역 제목 "스택": 작은 칸 하나에 "manager" 와 값 "x001". 가운데 영역 제목 "힙": 큰 둥근 사각형 하나, 위쪽 띠에 "Manager 객체 x001". 이 사각형은 내부가 위아래 두 층으로 나뉜다. 위층은 연한 파랑 바탕에 라벨 "Employee 부분" 과 필드 "name", "baseSalary". 아래층은 연한 주황 바탕에 라벨 "Manager 부분" 과 필드 "teamSize". 스택의 manager 칸에서 이 객체로 화살표 하나. 오른쪽 영역 제목 "메서드 영역": 위아래로 상자 두 개. 위 상자 "Employee 클래스" 안에 "work()", "monthlyPay()". 아래 상자 "Manager 클래스" 안에 "approve()". 아래 상자에서 위 상자로 향하는 화살표에 라벨 "슈퍼클래스". 힙의 객체에서 오른쪽 "Manager 클래스" 상자로 점선 화살표. 객체는 반드시 하나만 그리고 두 개로 나누어 그리지 않는다. 색은 파랑, 주황, 회색만 사용하고 글자는 고딕체로 선명하게. 상속 관계의 객체를 생성해도 힙에 만들어지는 객체는 하나다. 부모에 선언된 필드와 자식에 선언된 필드가 그 안에 함께 있다.

    멤버를 찾는 순서

    manager.work()라는 호출은 어떻게 Employee의 코드에 도달하는가. "자식에 없으면 부모에서 찾는다"는 직관은 맞지만, 실제로는 이 탐색이 컴파일 시점과 실행 시점에 각각 한 번씩, 서로 다른 목적으로 일어난다.

    4단계의 "메서드 선택"은 지금은 아무 일도 하지 않는 것처럼 보인다. 이 단계가 의미를 갖는 것은 자식이 부모의 메서드를 다시 정의했을 때다. 곧 볼 메서드 오버라이딩이 동작하는 자리가 바로 여기이고, 다음 회차의 다형성은 이 단계를 중심으로 전개된다.

    manager.work() 호출이 Manager 클래스에서 시작해 Employee 클래스에서 메서드를 찾고, 실행될 때 this는 여전히 같은 Manager 객체라는 것을 보여 준다. 흰 배경의 다이어그램. 왼쪽에 코드 조각 상자 "manager.work()". 가운데에 위아래로 쌓인 상자 두 개: 아래 상자 "Manager 클래스" 안에 메서드 목록 "approve()", 위 상자 "Employee 클래스" 안에 메서드 목록 "work()", "monthlyPay()". 코드 조각에서 아래 상자로 향하는 화살표에 번호 라벨 "1 Manager에서 찾는다" 그리고 아래 상자 옆에 작은 회색 글씨 "없음". 아래 상자에서 위 상자로 향하는 화살표에 번호 라벨 "2 부모로 올라간다". 위 상자의 "work()" 항목을 초록색으로 강조하고 옆에 "3 찾음". 오른쪽에 힙 객체 상자 "Manager 객체 x001" 을 그리고, 위 상자의 work() 에서 이 객체로 향하는 점선 화살표에 라벨 "this = x001". 색은 초록, 파랑, 회색만 사용하고 글자는 고딕체로 선명하게. 메서드 탐색은 호출에 쓰인 타입에서 시작해 부모 방향으로 올라간다. 부모의 코드가 실행되더라도 this는 처음 그 객체다.

    상속과 기능 추가

    상속 구조를 만들어 두면 기능을 추가하는 위치에 따라 영향 범위가 정해진다. 모든 직원에게 필요한 기능은 부모에 추가한다. 예를 들어 휴가 신청 기능을 Employee에 넣는다.

    public class Employee {
    String name;
    int baseSalary;

    void work() {
        System.out.println(name + ": 업무를 처리한다");
    }

    int monthlyPay() {
        return baseSalary;
    }

    void takeLeave(int days) {                       // 새로 추가
        System.out.println(name + ": 휴가 " + days + "일을 신청한다");
    }
}

    Manager와 Engineer의 소스는 한 글자도 고치지 않았지만, 이제 manager.takeLeave(3)과 engineer.takeLeave(3)을 호출할 수 있다. 실제로 Employee.java만 다시 컴파일하고 예전에 만들어 둔 Manager.class를 그대로 둔 채 manager.takeLeave(3)을 실행해도 "한지우: 휴가 3일을 신청한다"가 출력된다. 앞에서 본 대로 자식의 클래스 파일에는 부모의 코드가 복사돼 있지 않고, 실행할 때 부모의 클래스 정보에서 찾아 쓰기 때문이다.

    특정 종류에만 필요한 기능은 그 자식에 추가한다. Engineer에 코드 리뷰 기능을 넣으면 Engineer만 그 기능을 갖는다. 새로운 종류의 직원이 생기면 Employee를 상속하는 클래스를 하나 더 만든다. 새 클래스는 공통 기능을 다시 쓸 필요 없이 자기만의 것만 정의하면 된다.

    이 편리함에는 대가가 따른다. 부모를 고치면 모든 자식이 영향을 받는다. 그것이 의도일 때는 장점이지만, 부모의 메서드 동작을 조금 바꿨을 뿐인데 그 동작에 기대고 있던 어떤 자식이 깨질 수도 있다. 상속은 부모와 자식을 강하게 묶는다. 이 점은 회차의 끝에서 다시 짚는다.

    메서드 오버라이딩과 그 규칙

    부모에게 물려받은 기능을 그대로 쓸 수 없는 경우가 있다. 관리자의 월급은 기본급에 직책 수당이 더해진다고 하자. Employee의 monthlyPay()는 기본급만 돌려주므로 관리자에게는 맞지 않는다. 자식 클래스는 상속받은 메서드를 같은 이름, 같은 매개변수로 다시 정의할 수 있다. 이것을 메서드 오버라이딩(method overriding)이라고 한다.

    public class Employee {
    String name;
    int baseSalary;

    void work() {
        System.out.println(name + ": 업무를 처리한다");
    }

    int monthlyPay() {
        return baseSalary;
    }

    Employee copy() {
        Employee e = new Employee();
        e.name = name;
        e.baseSalary = baseSalary;
        return e;
    }
}

public class Manager extends Employee {
    int teamSize;

    void approve() {
        System.out.println(name + ": 결재한다 (팀원 " + teamSize + "명)");
    }

    @Override
    int monthlyPay() {
        return super.monthlyPay() + teamSize * 100_000;   // 부모의 계산 + 직책 수당
    }

    @Override
    Manager copy() {                                      // 반환 타입이 Employee가 아니라 Manager
        Manager m = new Manager();
        m.name = name;
        m.baseSalary = baseSalary;
        m.teamSize = teamSize;
        return m;
    }
}

public class PayMain {
    public static void main(String[] args) {
        Employee employee = new Employee();
        employee.name = "오세린";
        employee.baseSalary = 4_000_000;

        Manager manager = new Manager();
        manager.name = "한지우";
        manager.baseSalary = 5_000_000;
        manager.teamSize = 4;

        System.out.println(employee.monthlyPay());
        System.out.println(manager.monthlyPay());
    }
}

    manager.monthlyPay()를 앞 절의 탐색 순서로 따라가 보자. 컴파일러는 Manager 타입에서 monthlyPay()를 찾는다. 이번에는 Manager 자신이 선언한 것이 있다. 실행 시점의 메서드 선택에서도 객체의 클래스인 Manager에서 출발하므로 Manager.monthlyPay()가 선택된다. 그 안의 super.monthlyPay()는 부모의 메서드를 직접 호출하는 문법으로, 5,000,000을 돌려받아 400,000을 더한다. super는 뒤에서 자세히 다룬다.

    오버라이딩은 아무 메서드나 같은 이름으로 만들면 성립하는 것이 아니다. JLS §8.4.8이 조건을 정한다. 핵심 규칙을 표로 정리한다.

    왜 이런 규칙인가

    규칙들은 제각각으로 보이지만 한 가지 원칙에서 나온다. 부모 타입을 기준으로 작성된 코드는 자식 객체를 만나도 깨지지 않아야 한다. 다음 회차에서 보겠지만 자바에서는 Employee 타입의 변수가 Manager 객체를 가리킬 수 있다. 그 변수로 monthlyPay()를 호출하는 코드는 Employee의 선언만 보고 작성되고 컴파일된다.

    그 코드는 Employee의 선언을 근거로 몇 가지를 믿는다. 이 메서드를 호출할 권한이 있다는 것, int가 돌아온다는 것, 선언되지 않은 체크 예외는 나오지 않는다는 것이다. 자식이 접근 범위를 좁히면 호출할 수 있던 메서드가 호출할 수 없는 메서드로 바뀐다. 반환 타입을 long으로 바꾸면 int 변수에 받던 코드가 성립하지 않는다. 새로운 체크 예외를 던지면 그것을 처리하지 않은 호출 코드에 구멍이 생긴다. 오버라이딩 규칙은 이런 일이 생기지 않도록, 자식의 메서드가 부모의 메서드가 한 약속의 범위 안에 머물게 한다. 약속보다 더 많이 지키는 것(접근을 넓히는 것, 더 구체적인 타입을 돌려주는 것, 예외를 덜 던지는 것)은 허용된다.

    @Override: 의도를 컴파일러에게 알린다

    @Override는 "이 메서드는 상위 타입의 메서드를 오버라이딩한 것이다"라는 의도를 표시하는 애너테이션이다. 붙이지 않아도 오버라이딩은 성립한다. 그런데도 붙이는 이유는, 오버라이딩에 실패했을 때 그것이 오류가 아니라는 데 있다. 이름이나 매개변수가 조금만 달라도 오버라이딩이 아니라 새 메서드의 추가가 되고, 그 코드는 문법적으로 완전히 유효하다.

    public class Engineer extends Employee {
    String language;

    int monthlypay() {                     // p가 소문자다
        return baseSalary + 300_000;
    }

    int monthlyPay(int months) {           // 매개변수가 있다
        return baseSalary * months;
    }
}

    이 클래스는 문제없이 컴파일된다. 그러나 engineer.monthlyPay()를 호출하면 여전히 Employee의 것이 실행되어 기술 수당이 빠진다. 첫 번째 메서드는 이름이 다른 새 메서드이고, 두 번째는 이름은 같지만 매개변수가 다른 오버로딩이다. 두 메서드에 @Override를 붙이면 컴파일러가 "method does not override or implement a method from a supertype"라는 오류로 알려 준다. JLS §9.6.4.4는 이 애너테이션의 목적을 오버라이딩하려다 오버로딩하는 실수를 일찍 발견하는 것이라고 설명한다. 오버라이딩할 의도라면 항상 붙인다.

    관계이름이 같고 매개변수가 다른 메서드를 여러 개 둔다상속받은 메서드를 같은 시그니처로 다시 정의한다
    위치같은 클래스 안, 또는 부모와 자식에 걸쳐부모와 자식 사이
    반환 타입·접근 제어자제약 없음부모의 선언에 의해 제약됨

    공변 반환 타입과 브리지 메서드

    앞의 예에서 Manager.copy()는 반환 타입이 Employee가 아니라 Manager인데도 오버라이딩으로 인정됐다. 참조형 반환 타입은 하위 타입으로 좁힐 수 있기 때문이다. 이를 공변 반환 타입(covariant return type)이라고 한다(JLS §8.4.5). Manager를 돌려받은 호출자는 그것을 Employee로 취급할 수 있으므로, 부모의 약속을 깨지 않는다. Manager 타입으로 호출한 쪽은 캐스팅 없이 Manager를 받을 수 있어 편리하다.

    여기에는 한 층 아래의 사정이 있다. JVM이 "어떤 메서드가 다른 메서드를 오버라이딩할 수 있는가"를 판단하는 기준(JVMS §5.4.5)은 이름과 디스크립터가 같은 것이다. 디스크립터에는 반환 타입이 포함된다. Employee copy()의 디스크립터는 ()LEmployee;이고 Manager copy()는 ()LManager;라서, JVM의 눈에 둘은 서로 다른 메서드다. 자바 언어는 오버라이딩이라고 하는데 JVM은 아니라고 하는 틈이 생긴다. 컴파일러는 이 틈을 메우는 메서드를 하나 더 만들어 넣는다.

    소스에는 copy()가 하나인데 클래스 파일에는 둘이다. 두 번째 것은 디스크립터가 부모와 같은 ()LEmployee;이고, 하는 일은 진짜 copy()를 호출해 결과를 그대로 돌려주는 것뿐이다. ACC_BRIDGE와 ACC_SYNTHETIC 플래그는 컴파일러가 만든 연결용 메서드라는 표시다. 이런 메서드를 브리지 메서드(bridge method)라고 한다. Employee 타입으로 copy()를 호출하면 JVM은 ()LEmployee; 형태를 찾다가 이 브리지에 도달하고, 브리지가 Manager의 실제 구현으로 넘겨준다. 브리지 메서드는 중급 2편의 제네릭에서 다시 등장한다.

    필드는 오버라이딩되지 않는다: 숨김

    메서드를 다시 정의할 수 있다면 필드도 그럴 수 있을까. 자식 클래스에 부모와 같은 이름의 필드를 선언하는 것은 문법적으로 허용된다. 하지만 그 결과는 오버라이딩과 전혀 다르다. JLS §8.3은 이를 숨김(hiding)이라고 부른다. 자식의 필드가 부모의 필드를 대체하는 것이 아니라, 두 필드가 모두 존재하고 자식의 코드에서 그 이름을 쓰면 자식의 것이 먼저 보일 뿐이다.

    class Employee {
    String title = "사원";

    static String category() {
        return "Employee.category()";
    }
}

class Manager extends Employee {
    String title = "관리자";               // 필드 숨김: 오버라이딩이 아니다

    static String category() {             // static 메서드 숨김
        return "Manager.category()";
    }

    void show() {
        System.out.println(title);          // 이 클래스에 선언된 title
        System.out.println(this.title);     // 위와 같다
        System.out.println(super.title);    // 부모에 선언된 title
    }
}

public class HidingMain {
    public static void main(String[] args) {
        Manager manager = new Manager();
        manager.show();
        System.out.println(Employee.category());
        System.out.println(Manager.category());
    }
}

    왜 필드는 메서드처럼 동작하지 않는가. 필드 접근은 실행 중에 객체의 클래스를 보고 결정되지 않기 때문이다. JLS §15.11.1은 필드 접근에서 어느 필드를 쓸지는 그 식의 타입으로 정해지며, 실행 시점에 참조된 실제 객체의 클래스는 사용되지 않는다고 명시한다. Employee의 메서드 안에서 title이라고 쓰면 컴파일러는 그것을 Employee.title로 확정해 버린다. 그 메서드가 Manager 객체에 대해 실행되더라도 읽는 것은 Employee 부분의 title이다. 메서드 호출에만 있는 "실행 시점의 선택" 단계가 필드에는 없다.

    static 메서드도 같다. 자식에 같은 시그니처의 static 메서드를 선언하면 오버라이딩이 아니라 숨김이다(JLS §8.4.8.2). static 메서드는 객체가 아니라 클래스에 속하고, 어느 것이 호출될지는 호출에 쓰인 클래스 이름으로 컴파일 시점에 정해진다. Employee.category()와 Manager.category()는 이름만 같은 별개의 메서드다.

    멤버의 종류자식이 같은 이름으로 선언하면어느 것이 쓰일지 결정하는 것
    인스턴스 메서드오버라이딩실행 시점의 객체 클래스
    인스턴스 필드숨김컴파일 시점의 식의 타입
    static 메서드숨김컴파일 시점의 타입(클래스 이름)
    static 필드숨김컴파일 시점의 타입(클래스 이름)

    실무에서 필드 숨김을 의도적으로 쓸 일은 거의 없다. 같은 이름의 필드가 객체 안에 둘 있으면 어느 코드가 어느 것을 읽는지 추적하기 어렵고, 대부분은 실수다. 이 절의 목적은 숨김을 쓰라는 것이 아니라, 오버라이딩이 인스턴스 메서드에만 적용되는 특별한 동작임을 분명히 하는 데 있다. 이 차이는 다음 회차에서 부모 타입 변수로 자식 객체를 다룰 때 눈에 보이는 결과의 차이로 나타난다.

    자식이 부모와 같은 이름의 필드를 선언하면 대체되지 않고 객체 안에 두 필드가 공존하며, 어느 코드에서 읽느냐에 따라 다른 필드가 읽힌다는 것을 보여 준다. 흰 배경. 가운데에 세로로 긴 둥근 사각형 "Manager 객체" 를 그리고 내부를 위아래 두 층으로 나눈다. 위층은 연한 파랑 바탕, 라벨 "Employee 부분", 필드 칸 "title = 사원". 아래층은 연한 주황 바탕, 라벨 "Manager 부분", 필드 칸 "title = 관리자". 객체 왼쪽에 코드 꼬리표 두 개: 위쪽 꼬리표 "super.title" 에서 위층 필드로 화살표, 아래쪽 꼬리표 "this.title" 에서 아래층 필드로 화살표. 객체 오른쪽에 설명 상자 "오버라이딩이 아니라 숨김" 과 그 아래 작은 글씨 "두 필드가 모두 존재한다". 색은 파랑, 주황, 회색만 사용하고 글자는 고딕체로 선명하게. 필드는 오버라이딩되지 않는다. 같은 이름의 필드를 선언하면 부모의 필드가 숨겨질 뿐, 객체 안에는 둘 다 남아 있다.

    상속과 접근 제어

    지금까지의 예제는 필드에 접근 제어자를 붙이지 않았다. 캡슐화 회차에서 배운 대로라면 필드는 private이어야 한다. 그러면 자식 클래스는 부모의 필드를 어떻게 다루는가. 접근 제어자 네 가지가 상속 관계에서 각각 어떻게 동작하는지 패키지를 둘로 나눠 확인한다.

    package company.hr;

public class Employee {
    private int baseSalary;        // 이 클래스 안에서만
    String department;             // 같은 패키지에서만(package 접근)
    protected String name;         // 같은 패키지 + 다른 패키지의 자식
    public String email;           // 어디서나

    public Employee(String name, int baseSalary) {
        this.name = name;
        this.baseSalary = baseSalary;
    }

    public int monthlyPay() {
        return baseSalary;
    }

    protected void log(String message) {
        System.out.println("[" + name + "] " + message);
    }
}

    protected의 정확한 범위

    protected는 "자식이면 접근할 수 있다"로 흔히 요약되지만, 다른 패키지의 자식에게는 조건이 하나 더 붙는다. JLS §6.6.2는 protected 멤버를 그 객체의 구현을 책임지는 코드만 접근할 수 있다고 설명한다. 구체적으로, 다른 패키지에 있는 자식 클래스 S의 코드가 식.멤버 형태로 protected 인스턴스 멤버에 접근하려면 그 식의 타입이 S이거나 S의 하위 타입이어야 한다(JLS §6.6.2.1).

    package company.dev;

import company.hr.Employee;

public class Reviewer extends Employee {

    public Reviewer(String name, int baseSalary) {
        super(name, baseSalary);
    }

    public void test(Employee other, Reviewer peer) {
        System.out.println(this.name);     // 가능: this의 타입은 Reviewer
        System.out.println(peer.name);     // 가능: peer의 타입은 Reviewer
        System.out.println(other.name);    // error: name has protected access in Employee
    }
}

    Reviewer는 Employee의 자식이지만 Employee 타입 변수 other를 통해서는 name에 접근할 수 없다. other가 가리키는 객체는 Reviewer가 아니라 전혀 다른 자식 클래스의 객체일 수 있고, 그 객체의 구현에 대해 Reviewer는 책임이 없기 때문이다. protected는 "상속 계층에 속한 모든 객체의 속을 볼 권한"이 아니라 "내가 물려받은 부분을 다룰 권한"이다. 같은 패키지 안에서는 이 제한 없이 package 접근과 똑같이 동작한다.

    super ①: 부모의 멤버를 가리키기

    오버라이딩과 숨김이 일어나면 자식의 코드에서 같은 이름이 자식의 것을 가리키게 된다. 부모의 것을 명시적으로 쓰고 싶을 때 super 키워드를 사용한다. super.필드는 부모에 선언된 필드를, super.메서드()는 부모의 메서드를 뜻한다. 앞에서 본 Manager.monthlyPay()가 그 예다.

    @Override
int monthlyPay() {
    return super.monthlyPay() + teamSize * 100_000;
}

    여기서 super.를 빼고 monthlyPay() + teamSize * 100_000이라고 쓰면 어떻게 될까. monthlyPay()는 this.monthlyPay()와 같고, 객체의 클래스가 Manager이므로 Manager.monthlyPay() 자신이 다시 호출된다. 그 안에서 또 자신을 호출하고, 스택 프레임이 끝없이 쌓이다가 StackOverflowError로 끝난다. super.monthlyPay()는 이 순환을 끊는다. "객체의 클래스에서 다시 찾지 말고, 부모 클래스의 것을 실행하라"는 뜻이기 때문이다.

    이 차이는 바이트코드의 명령어 차이로 나타난다. 일반 인스턴스 메서드 호출은 invokevirtual로 컴파일되고, 이 명령은 실행 중에 객체의 클래스를 보고 메서드를 선택한다. super.메서드() 호출은 invokespecial로 컴파일된다.

      int monthlyPay();
    Code:
       0: aload_0
       1: invokespecial #33                 // Method Employee.monthlyPay:()I
       4: aload_0
       5: getfield      #19                 // Field teamSize:I
       8: ldc           #37                 // int 100000
      10: imul
      11: iadd
      12: ireturn

    JVMS는 두 명령의 차이를 이렇게 설명한다. invokevirtual은 객체의 클래스를 기준으로 메서드를 호출하고, invokespecial은 인스턴스 초기화 메서드(생성자)와 현재 클래스 및 그 상위 타입의 메서드를 직접 호출하는 데 쓰인다. super.monthlyPay()에서는 객체의 실제 클래스가 무엇이든 현재 클래스의 직접 슈퍼클래스에서 출발해 메서드를 찾는다. JLS §15.12.4.4도 호출 방식이 super이면 오버라이딩이 적용되지 않는다고 명시한다.

    super에 대해 알아 둘 점이 세 가지 더 있다. 첫째, super는 별개의 객체를 가리키는 참조가 아니다. 객체는 하나뿐이고, super.monthlyPay() 안에서 실행되는 부모 코드의 this도 같은 객체다. super는 "같은 객체를 대상으로 하되 멤버 탐색을 부모 클래스에서 시작하라"는 표시다. 둘째, super.super.monthlyPay()처럼 두 단계를 건너뛰는 문법은 없다. 직접 부모까지만 지정할 수 있다. 셋째, super는 this와 마찬가지로 객체가 있어야 의미가 있으므로 static 메서드 안에서는 쓸 수 없다.

    super ②: 생성자 연쇄

    자식 객체 안에 부모 부분이 들어 있다면, 그 부모 부분은 누가 초기화하는가. 부모의 필드가 private이면 자식의 생성자는 거기에 손을 댈 수조차 없다. 답은 단순하다. 부모 부분은 부모의 생성자가 초기화한다. 그래서 자바는 자식의 생성자가 반드시 부모의 생성자를 호출하도록 강제한다. 부모의 생성자를 호출하는 문법이 super(...)다.

    public class Employee {
    private final String name;
    private final int baseSalary;

    public Employee(String name, int baseSalary) {
        this.name = name;
        this.baseSalary = baseSalary;
    }

    public String name() {
        return name;
    }

    public int monthlyPay() {
        return baseSalary;
    }
}

public class Manager extends Employee {
    private final int teamSize;

    public Manager(String name, int baseSalary, int teamSize) {
        super(name, baseSalary);        // 부모 부분의 초기화를 부모 생성자에게 맡긴다
        this.teamSize = teamSize;       // 자기 부분을 초기화한다
    }

    @Override
    public int monthlyPay() {
        return super.monthlyPay() + teamSize * 100_000;
    }
}

    생성자와 관련된 규칙은 JLS §8.8.7과 §8.8.9에 있다.

    • 생성자 본문의 첫 문장으로 this(...)(같은 클래스의 다른 생성자) 또는 super(...)(직접 부모의 생성자)를 쓸 수 있다. 둘을 함께 쓸 수는 없다.
    • 둘 다 쓰지 않으면 컴파일러가 본문 맨 앞에 인자 없는 super();를 넣는다. Object의 생성자만 예외다.
    • 생성자를 하나도 선언하지 않은 클래스에는 기본 생성자가 만들어지는데, 그 본문은 super(); 한 줄이다. 앞에서 본 Manager의 바이트코드에 Employee의 생성자 호출이 들어 있던 이유다.
    • 따라서 부모에 인자 없는 생성자가 없으면, 자식은 반드시 super(인자)를 직접 써야 한다.

    마지막 규칙을 어기면 다음과 같은 오류를 만난다. 위의 Employee에는 인자 없는 생성자가 없다.

    class Manager extends Employee {
    int teamSize;

    Manager(String name, int teamSize) {
        this.teamSize = teamSize;        // super(...) 호출이 없다 → 컴파일러가 super();를 넣는다
    }
}
// error: constructor Employee in class Employee cannot be applied to given types;
//   required: String,int
//   found:    no arguments

class Intern extends Employee {
}
// 생성자가 없으므로 기본 생성자 Intern() { super(); } 가 만들어진다 → 같은 오류

    오류 메시지가 가리키는 것은 소스에 쓰지 않은 super() 호출이다. 보이지 않는 코드가 원인이라 처음 만나면 당황하기 쉽지만, "모든 생성자는 부모의 생성자를 호출하며, 쓰지 않으면 인자 없는 것이 호출된다"는 규칙을 알면 바로 읽힌다.

    실행 순서: JLS §12.5의 다섯 단계

    객체 생성 과정 전체를 순서대로 보자. new가 실행되면 먼저 힙에 공간이 할당되고 모든 필드(부모에 선언된 것 포함)가 기본값이 된다. 그다음 지정된 생성자가 호출되며, JLS §12.5는 각 생성자의 처리를 다섯 단계로 규정한다.

    3단계가 4, 5단계보다 앞에 있다는 것이 핵심이다. 어떤 클래스의 필드 초기화 식과 생성자 본문이 실행되는 시점에는 그 부모 클래스의 초기화가 이미 끝나 있다. 재귀적으로 적용하면 초기화는 Object에서 시작해 가장 아래 자식에서 끝난다. 세 단계 상속으로 확인해 보자.

    class Base {
    int a = Chain.log("1. Base 필드 초기화");

    Base() {
        Chain.log("2. Base() 본문");
    }
}

class Middle extends Base {
    int b = Chain.log("3. Middle 필드 초기화");

    Middle(int x) {
        // 여기에 super(); 가 숨어 있다
        Chain.log("4. Middle(int) 본문, x=" + x);
    }
}

class Leaf extends Middle {
    int c = Chain.log("5. Leaf 필드 초기화");

    Leaf() {
        this(7);
        Chain.log("7. Leaf() 본문");
    }

    Leaf(int x) {
        super(x);
        Chain.log("6. Leaf(int) 본문");
    }
}

public class Chain {
    static int log(String message) {
        System.out.println(message);
        return 0;
    }

    public static void main(String[] args) {
        new Leaf();
    }
}
    1. Base 필드 초기화
2. Base() 본문
3. Middle 필드 초기화
4. Middle(int) 본문, x=7
5. Leaf 필드 초기화
6. Leaf(int) 본문
7. Leaf() 본문

    new Leaf()를 절차대로 추적한다. Leaf()는 this(7)로 시작하므로 2단계에 따라 Leaf(int)를 처리한다. Leaf(int)는 super(x)로 시작하므로 3단계에 따라 Middle(int)를 처리한다. Middle(int)에는 명시적인 호출이 없으므로 암묵적 super()로 Base()를 처리한다. Base()는 다시 Object()를 처리하는데 여기에는 출력이 없다. 이제 되돌아오면서 실행된다. Base의 필드 초기화(1), Base() 본문(2), Middle의 필드 초기화(3), Middle(int) 본문(4), Leaf의 필드 초기화(5), Leaf(int) 본문(6) 순이다. 마지막으로 Leaf()는 2단계에서 곧장 5단계로 가므로 필드 초기화를 다시 하지 않고 본문의 나머지(7)만 실행한다.

    호출이 올라가는 방향 (생성자의 첫 문장)        실행이 내려오는 방향 (필드 초기화 → 본문)

new Leaf()
  └▶ Leaf()         this(7)
       └▶ Leaf(int)      super(x)
            └▶ Middle(int)    super()  ← 암묵적
                 └▶ Base()        super()  ← 암묵적
                      └▶ Object()
                                               1. Base 필드 초기화    2. Base() 본문
                                               3. Middle 필드 초기화  4. Middle(int) 본문
                                               5. Leaf 필드 초기화    6. Leaf(int) 본문
                                                                      7. Leaf() 본문
    자식 생성자가 첫 문장에서 부모 생성자를 호출하며 Object까지 올라간 뒤, 초기화는 Object 쪽에서 자식 쪽으로 내려오며 완료된다는 것을 보여 준다. 흰 배경의 계단형 다이어그램. 세로로 네 층의 가로 막대를 위에서 아래로 쌓는다: 맨 위 "Object", 그 아래 "Base", 그 아래 "Middle", 맨 아래 "Leaf". 막대 왼쪽에는 아래에서 위로 올라가는 파란 화살표 세 개가 층 사이를 잇고, 전체에 라벨 "호출: super(...) 로 위로 올라간다". 막대 오른쪽에는 위에서 아래로 내려오는 주황 화살표 세 개가 층 사이를 잇고, 전체에 라벨 "초기화: 부모부터 아래로 완료된다". Base, Middle, Leaf 막대 안에는 각각 작은 번호 꼬리표 두 개를 둔다: Base 안에 "1 필드 초기화", "2 생성자 본문", Middle 안에 "3 필드 초기화", "4 생성자 본문", Leaf 안에 "5 필드 초기화", "6 생성자 본문". 색은 파랑, 주황, 회색만 사용하고 글자는 고딕체로 선명하게. 생성자 호출은 자식에서 부모로 올라가지만, 실제 초기화가 끝나는 순서는 부모에서 자식으로 내려온다.

    바이트코드로 본 생성자

    컴파일러는 이 절차를 생성자의 바이트코드 안에 직접 펼쳐 넣는다. 클래스 파일에서 생성자는 라는 이름의 메서드다. Leaf(int)를 보자.

      Leaf(int);
    Code:
       0: aload_0
       1: iload_1
       2: invokespecial #15                 // Method Middle."":(I)V
       5: aload_0
       6: ldc           #18                 // String 5. Leaf 필드 초기화
       8: invokestatic  #9                  // Method Chain.log:(Ljava/lang/String;)I
      11: putfield      #20                 // Field c:I
      14: ldc           #24                 // String 6. Leaf(int) 본문
      16: invokestatic  #9                  // Method Chain.log:(Ljava/lang/String;)I
      19: pop
      20: return

    맨 앞에 부모의 호출(3단계)이 있고, 바로 뒤에 필드 c의 초기화 코드(4단계)가 있으며, 그다음이 소스에 쓴 본문(5단계)이다. 필드 선언 옆에 쓴 초기화 식 int c = ...는 소스에서는 생성자 밖에 있지만, 컴파일되면 super(...) 호출 직후의 위치로 생성자 안에 복사된다. this(7)로 시작하는 Leaf()의 바이트코드에는 이 필드 초기화 코드가 들어가지 않는다. 그래서 필드 초기화가 두 번 실행되지 않는다.

    왜 부모가 먼저인가

    자식의 코드는 부모의 것을 사용할 수 있다. 자식의 필드 초기화 식이나 생성자 본문은 상속받은 메서드를 호출하거나 부모의 필드를 읽을 수 있다. 그 시점에 부모 부분이 초기화돼 있지 않다면 자식은 기본값뿐인 부모 상태 위에서 동작하게 된다. 반대로 부모의 코드는 자식을 알지 못하므로 자식의 상태에 의존하지 않는다(원칙적으로는 그렇다. 바로 다음에 예외를 본다). 의존하는 쪽이 나중에 초기화되어야 하므로 순서는 부모 먼저가 된다.

    Java 21에서 super(...)나 this(...)는 생성자의 첫 문장이어야 하고, 그 인자에서 this나 인스턴스 필드, 인스턴스 메서드를 쓸 수 없다. JLS §8.8.7.1은 이 호출문이 static 문맥을 만든다고 표현한다. 아직 부모의 초기화조차 시작되지 않은 객체를 사용하는 것을 막기 위해서다.

    Manager(String name, int teamSize) {
    this.teamSize = teamSize;
    super(name, 0);              // error: call to super must be first statement in constructor
}

Manager(String name) {
    super(name + teamSize, 0);   // error: cannot reference teamSize before supertype constructor has been called
}

    이 규칙은 언어만의 것이 아니다. JVMS §4.10.2.4는 Object를 제외한 모든 인스턴스 초기화 메서드가 인스턴스 멤버에 접근하기 전에 자기 클래스의 다른 초기화 메서드나 직접 슈퍼클래스의 초기화 메서드를 호출해야 한다고 규정하고, 클래스 파일 검증기가 이를 검사한다.

    Java 25부터는 JEP 513(Flexible Constructor Bodies)에 따라 super(...)나 this(...) 앞에 문장을 둘 수 있게 되었다. 단, 그 문장들은 생성 중인 객체를 참조할 수 없고, 예외로 초기화 식이 없는 자기 클래스의 필드에 값을 대입하는 것만 허용된다. 인자를 검증하거나 계산하는 코드, 그리고 부모 생성자가 실행되기 전에 자기 필드를 채워 두는 코드를 부모 생성자 호출 앞에 쓸 수 있게 한 것이다. 부모 생성자 호출 뒤에 적힌 코드가 부모의 초기화가 끝난 다음에 실행된다는 점은 그대로다. 이 강좌의 기준인 Java 21에서는 첫 문장이어야 한다.

    함정: 부모 생성자에서 오버라이딩된 메서드 호출

    "부모의 코드는 자식의 상태에 의존하지 않는다"는 전제가 깨지는 경우가 하나 있다. 부모의 생성자가 메서드를 호출했는데 그 메서드를 자식이 오버라이딩한 경우다.

    class Report {
    Report() {
        System.out.println("제목: " + title());   // 오버라이딩될 수 있는 메서드를 생성자에서 호출
    }

    String title() {
        return "기본 보고서";
    }
}

class SalesReport extends Report {
    private final String region;
    private int year = 2026;

    SalesReport(String region) {
        super();
        this.region = region;
    }

    @Override
    String title() {
        return region + " 매출 보고서 " + year;
    }
}

public class ReportMain {
    public static void main(String[] args) {
        SalesReport report = new SalesReport("서울");
        System.out.println("제목: " + report.title());
    }
}
    제목: null 매출 보고서 0
제목: 서울 매출 보고서 2026

    첫 줄이 문제의 출력이다. 순서를 따라가 보자. new SalesReport("서울")로 객체가 할당되고 region은 null, year는 0이 된다. SalesReport의 생성자는 먼저 super()를 실행한다. Report()의 본문이 title()을 호출한다. 이 호출은 일반 인스턴스 메서드 호출이므로 객체의 실제 클래스인 SalesReport에서 메서드가 선택된다. JLS §12.5는 생성 도중에도 메서드 선택 규칙이 달라지지 않으며, 객체가 완전히 초기화되기 전이라도 오버라이딩한 메서드가 사용된다고 명시한다. 그런데 이 시점에 SalesReport의 필드 초기화(4단계)와 생성자 본문(5단계)은 아직 실행되지 않았다. year = 2026도, this.region = region도 실행 전이다. 그래서 기본값인 null과 0이 출력된다.

    region이 final 필드인데도 null로 읽혔다는 점을 눈여겨보자. 앞 회차에서 본 "final 필드도 기본값에서 출발한다"가 상속과 만나 드러난 것이다. 이 함정을 피하는 규칙은 간단하다. 생성자에서는 오버라이딩될 수 있는 메서드를 호출하지 않는다. 생성자에서 호출해도 안전한 것은 private 메서드, final 메서드, static 메서드처럼 자식이 바꿔 끼울 수 없는 것들이다.

    final 클래스와 final 메서드

    앞 회차에서 미뤄 둔 주제다. 변수에 붙은 final이 "다시 대입할 수 없다"였다면, 클래스와 메서드에 붙은 final은 "상속으로 바꿀 수 없다"는 뜻이다.

    final 클래스는 상속할 수 없다. JLS §8.1.1.2는 클래스의 정의가 완결되어 하위 클래스가 필요하지 않을 때 final로 선언할 수 있다고 설명한다. final 클래스를 extends 뒤에 쓰면 컴파일 오류다.

    final class Money {
    private final long amount;

    Money(long amount) {
        this.amount = amount;
    }

    long amount() {
        return amount;
    }
}

class BonusMoney extends Money {           // error: cannot inherit from final Money
    BonusMoney(long amount) {
        super(amount);
    }
}

    final 메서드는 오버라이딩할 수 없다(JLS §8.4.3.3). 클래스의 상속은 허용하되 특정 메서드의 동작만은 자식이 바꾸지 못하게 할 때 쓴다.

    class Account {
    private long balance;

    final void withdraw(long amount) {       // 자식이 검증 로직을 건너뛰지 못하게 한다
        if (amount > balance) {
            throw new IllegalArgumentException("잔액 부족");
        }
        balance -= amount;
    }
}

class FreeAccount extends Account {
    @Override
    void withdraw(long amount) {             // error: withdraw(long) in FreeAccount cannot override
    }                                        //        withdraw(long) in Account
}                                            //   overridden method is final

    상속을 막는 이유는 대체로 불변식의 보호다. 클래스가 "잔액은 음수가 되지 않는다" 같은 규칙을 자신의 메서드로 지키고 있을 때, 자식이 그 메서드를 오버라이딩해 검증을 생략하면 규칙이 깨진다. 표준 라이브러리의 String이 대표적인 final 클래스다. Java SE API 문서의 선언은 public final class String이다. 문자열의 내용이 바뀌지 않는다는 성질에 수많은 코드가 의존하는데, 누군가 String을 상속해 내용이 바뀌는 문자열을 만들 수 있다면 그 전제가 무너진다.

    JLS §8.4.3.3은 private 메서드와 final 클래스 안의 모든 메서드가 final인 것처럼 동작한다고 덧붙인다. 오버라이딩될 수 없기 때문이다. private 메서드와 같은 이름의 메서드를 자식에 선언하면 오버라이딩이 아니라 관계없는 새 메서드가 된다.

    class Base {
    private void helper() {
        System.out.println("Base.helper");
    }

    void run() {
        helper();
    }
}

class Derived extends Base {
    void helper() {                          // 오버라이딩이 아니다: 이름만 같은 새 메서드
        System.out.println("Derived.helper");
    }
}

public class PrivateMain {
    public static void main(String[] args) {
        new Derived().run();
    }
}
    Base.helper

    Derived 객체에 대해 run()을 실행했지만 Base의 helper()가 호출됐다. Derived.helper()에 @Override를 붙였다면 컴파일 오류로 이 사실을 바로 알 수 있었을 것이다.

    상속을 "전부 허용"과 "전부 금지" 사이에서 조절하는 방법도 있다. Java 17에서 정식 기능이 된 sealed 클래스(JEP 409)는 상속할 수 있는 자식 클래스의 목록을 부모가 직접 지정한다. 이 강좌의 범위를 넘으므로 존재만 알아 둔다.

    흔한 오해와 상속의 비용

    • "자식 객체를 만들면 부모 객체도 따로 만들어진다." 객체는 하나다. 그 안에 부모에 선언된 필드와 자식에 선언된 필드가 함께 있다. 부모의 생성자가 실행되는 것은 새 객체를 만들기 위해서가 아니라 같은 객체의 부모 부분을 초기화하기 위해서다.
    • "private 필드는 상속되지 않으니 자식 객체에는 없다." 상속되지 않는다는 것은 자식의 코드에서 이름으로 접근할 수 없다는 뜻이다. 필드는 자식 객체 안에 존재하고 부모의 메서드를 통해 읽고 쓰인다.
    • "필드도 메서드처럼 오버라이딩된다." 같은 이름의 필드를 선언하면 숨김이 일어나 객체 안에 필드가 둘 생긴다. 어느 것이 읽힐지는 그 코드가 어느 클래스에 쓰였는지로 컴파일 시점에 정해진다.
    • "super는 부모 객체를 가리킨다." 부모 객체는 따로 없다. super는 같은 객체에 대해 멤버 탐색을 부모 클래스에서 시작하게 하는 키워드다.
    • "생성자도 상속된다." 생성자는 멤버가 아니어서 상속되지 않는다. 부모에 Employee(String, int)가 있다고 new Manager("이름", 100)이 되는 것이 아니다. 자식은 자기 생성자를 선언하고 그 안에서 super(...)로 부모 생성자를 호출해야 한다.
    • "매개변수만 다르게 해도 오버라이딩이다." 시그니처가 다르면 오버로딩이다. 부모의 메서드는 그대로 남아 있고 새 메서드가 하나 추가될 뿐이다. @Override를 붙이면 이 실수를 컴파일러가 잡는다.

    상속은 코드 중복을 없애지만 공짜가 아니다. 자식은 부모의 구현에 기대어 동작한다. 부모의 메서드가 내부적으로 어떤 메서드를 호출하는지, 생성자가 무엇을 하는지 같은 세부 사항이 자식의 동작에 영향을 준다. 앞의 Report 예제가 그런 경우였다. 부모를 수정하는 사람은 자식들이 어떤 가정을 하고 있는지 모르고, 자식을 만드는 사람은 부모의 내부를 다 알지 못한다. 그래서 상속은 "코드를 재사용하고 싶다"는 이유만으로 쓰기보다, 두 클래스 사이에 "자식은 부모의 한 종류다"라는 관계가 실제로 성립할 때 쓰는 것이 안전하다.

    일상에서 가져온 비유기본 계약서와 특약

    보험이나 임대차 계약에는 표준 약관이 있고, 개별 계약은 거기에 특약을 더하거나 일부 조항을 고쳐 쓴다. 특약이 없는 사항은 표준 약관을 따른다. 자식 클래스가 부모를 상속하고 일부 메서드를 오버라이딩하는 것과 닮았다. 표준 약관이 개정되면 그것을 따르는 모든 계약이 영향을 받는다는 점도 같다. 다만 비유가 맞지 않는 지점이 있다. 계약서는 표준 약관과 특약이 별개의 문서지만, 자식 객체는 부모 부분과 자식 부분이 하나의 객체 안에 들어 있다.

    어디서 다시 만나는가

    이 회차는 상속이라는 구조를 세웠다. 다음 회차에서는 이 구조 위에서 다형성을 다룬다. 부모 타입의 변수가 자식 객체를 가리킬 수 있다는 것, 그리고 그때 오버라이딩된 메서드가 실행 시점에 선택된다는 것이다. 이번 회차의 "메서드 선택" 단계와 "필드는 컴파일 시점의 타입을 따른다"는 사실이 거기서 본격적으로 쓰인다. 그다음 회차의 추상 클래스와 인터페이스는 "자식이 반드시 오버라이딩해야 하는 메서드"를 언어 차원에서 표현하는 방법이다.

    중급 1편은 모든 클래스의 부모인 Object에서 시작한다. toString(), equals(), hashCode()를 오버라이딩하는 것은 이 회차의 규칙을 그대로 적용하는 일이다. 예외 처리에서는 예외 클래스들이 상속 계층을 이루고, 그 계층이 catch가 잡는 범위를 정한다.

    스프링에서도 상속의 규칙이 직접 영향을 준다. 스프링 프레임워크의 레퍼런스 문서에 따르면, 대상 객체가 인터페이스를 구현하지 않은 경우 스프링 AOP는 대상 클래스를 상속한 클래스를 실행 중에 만들어 프록시로 쓴다(CGLIB 프록시). 그 문서는 이 방식의 제약으로 final 클래스는 상속할 수 없어 프록시를 만들 수 없고, final 메서드와 private 메서드는 오버라이딩할 수 없어 부가 기능을 적용할 수 없다고 적고 있다. 이 회차에서 본 final 클래스, final 메서드, private 메서드의 규칙이 프레임워크의 동작 범위를 결정하는 것이다.

    이 장의 핵심

    상속 관계의 객체를 생성하면 힙에는 객체가 하나 만들어지고, 그 안에 부모에 선언된 필드와 자식에 선언된 필드가 함께 들어 있다. 멤버는 사용된 타입에서 시작해 부모 방향으로 찾는다. 인스턴스 메서드는 오버라이딩되어 실행 시점에 객체의 클래스를 기준으로 선택되지만, 필드와 static 메서드는 숨겨질 뿐이고 컴파일 시점의 타입을 따른다. 생성자는 부모의 것을 먼저 호출하므로 초기화는 항상 부모 부분에서 자식 부분으로 진행된다.
    상속과 extends
    자식 클래스가 부모 클래스의 멤버를 물려받아 확장한다. 부모는 하나뿐이고, extends를 쓰지 않은 클래스의 부모는 Object다. private 멤버와 생성자는 상속되지 않는다.
    상속과 메모리 구조
    자식 객체를 생성하면 힙에 객체가 하나 만들어지고 그 안에 부모와 자식에 선언된 모든 인스턴스 필드가 들어간다(JLS §12.5). 메서드 코드는 각 클래스의 정보로 메서드 영역에 따로 있다.
    멤버 탐색 순서
    컴파일러는 호출에 쓰인 타입의 멤버에서 찾고, JVM은 그 타입에서 시작해 슈퍼클래스 방향으로 올라가며 찾는다. 인스턴스 메서드는 여기에 더해 실행 시점에 객체의 클래스를 기준으로 선택된다.
    메서드 오버라이딩
    상속받은 인스턴스 메서드를 같은 시그니처로 다시 정의하는 것. 반환 타입은 같거나 하위 타입, 접근 범위는 같거나 넓게, 체크 예외는 부모가 선언한 범위 안이어야 한다(JLS §8.4.8).
    @Override
    오버라이딩 의도를 표시한다. 실제로 오버라이딩이 아니면 컴파일 오류가 나므로 이름 오타나 매개변수 불일치로 오버로딩이 되는 실수를 막는다.
    숨김(hiding)
    자식이 부모와 같은 이름의 필드나 같은 시그니처의 static 메서드를 선언하는 것. 대체되지 않고 둘 다 존재하며, 어느 것이 쓰일지는 컴파일 시점의 타입으로 정해진다.
    super
    super.멤버는 같은 객체에 대해 부모 클래스에서 멤버를 찾게 한다. super.메서드()는 invokespecial로 컴파일되어 오버라이딩이 적용되지 않는다.
    생성자 연쇄
    모든 생성자는 this(...) 또는 super(...)로 시작하고, 쓰지 않으면 super()가 삽입된다. 그 결과 필드 초기화와 생성자 본문은 Object 쪽에서 자식 쪽으로 차례로 실행된다.
    final 클래스와 final 메서드
    final 클래스는 상속할 수 없고 final 메서드는 오버라이딩할 수 없다. private 메서드도 오버라이딩되지 않는다.

    실무에서 다시 판단하면, 상속을 쓸지 말지는 "코드가 겹치는가"가 아니라 "자식을 부모 타입으로 다뤄도 말이 되는가"로 정한다. 관리자를 직원으로 취급하는 코드(급여 합산, 휴가 처리)가 실제로 있다면 상속이 맞다. 두 클래스가 우연히 같은 필드 몇 개를 가졌을 뿐이라면, 공통 부분을 별도 클래스로 만들어 필드로 갖는 편이 부모 변경의 영향을 덜 받는다. 한번 공개된 부모 클래스는 고치기 어렵다. 어떤 자식이 부모의 어떤 동작에 기대고 있는지 부모 쪽에서는 알 수 없기 때문이다.

    장애 분석에서 이 회차의 지식이 직접 쓰이는 대표적인 경우는 초기화 순서다. 객체가 만들어진 직후인데 필드가 null이나 0으로 보인다면, 부모 생성자가 오버라이딩된 메서드를 호출했는지, 생성 도중의 객체를 다른 곳에 등록했는지를 먼저 확인한다. 스택 트레이스에 부모 클래스의 가 있고 그 위에 자식 클래스의 메서드가 올라와 있다면 이 유형이다. 고치는 방법은 생성자에서 그 호출을 빼고, 객체가 완성된 뒤에 호출되는 별도의 초기화 메서드나 정적 팩터리 메서드로 옮기는 것이다.

    오버라이딩이 "되지 않은" 경우도 흔한 원인이다. 메서드 이름의 대소문자, 매개변수 타입 하나의 차이로 오버로딩이 되면 컴파일도 되고 테스트의 일부도 통과하지만 부모의 동작이 그대로 실행된다. @Override를 빠짐없이 붙이는 것은 취향이 아니라 이 부류의 버그를 컴파일 시점으로 끌어오는 수단이다. 같은 이유로 자식 클래스에 부모와 같은 이름의 필드가 보이면 의도를 확인한다. 대부분은 실수이고, 부모의 메서드와 자식의 메서드가 서로 다른 필드를 읽고 있을 가능성이 높다.

    클래스를 final로 둘지에 대한 판단은 프레임워크 사용 여부에 따라 달라진다. 상속을 염두에 두고 설계하지 않은 클래스는 final로 막는 것이 불변식을 지키는 데 유리하다. 반면 스프링 AOP의 CGLIB 프록시처럼 실행 중에 자식 클래스를 만들어 동작하는 기술의 대상이 되는 클래스는 final일 수 없고, 부가 기능을 적용받아야 하는 메서드도 final이나 private일 수 없다. 어떤 클래스가 프레임워크에 의해 상속될 수 있는지를 알고 정해야 한다.

Employee의 메서드 코드가 Manager 객체 안으로 복사된다. JLS §12.5에 따라 새 인스턴스에는 그 클래스와 모든 슈퍼클래스에 선언된 인스턴스 변수를 위한 공간이 할당된다. 객체는 하나이고 참조값도 하나다. 인스턴스 필드는 객체마다 있으므로 메서드 영역에서 공유되지 않으며, 메서드 코드는 클래스 정보에 있을 뿐 객체로 복사되지 않는다. 부모의 protected Number total() throws IOException을 오버라이딩하는 선언으로 허용되는 것은? (Integer는 Number의 하위 클래스다.) Number total() throws IOException (접근 제어자 없음) protected Number total() throws Exception public Integer total() protected int total() throws IOException 오버라이딩하는 메서드는 접근 범위를 넓힐 수 있고, 참조형 반환 타입을 하위 타입으로 좁힐 수 있으며, 체크 예외를 덜 선언할 수 있다. 세 번째 보기는 세 가지를 모두 허용된 방향으로 바꿨다. 첫 번째는 protected를 package로 좁혔고, 두 번째는 부모가 선언하지 않은 더 넓은 예외를 선언했으며, 네 번째는 참조형을 기본형으로 바꿨다(하위 타입 관계가 아니다). 부모 P에 int v = 1;과 int get() { return v; }가 있고, 자식 C extends P에 int v = 2;만 선언돼 있다. new C().get()의 결과와 그 이유로 옳은 것은? 1. get()은 P의 코드이고, 그 안의 v는 컴파일 시점에 P의 필드로 정해졌기 때문이다. 2. 객체의 실제 클래스가 C이므로 C의 필드가 읽힌다. 2. 자식의 필드가 부모의 필드를 덮어써서 객체에는 v가 하나뿐이다. 컴파일 오류. 부모와 같은 이름의 필드는 선언할 수 없다. 필드는 오버라이딩되지 않고 숨겨진다. 객체 안에는 v가 둘 있고, 필드 접근은 실행 시점의 객체 클래스가 아니라 그 식의 컴파일 시점 타입으로 결정된다(JLS §15.11.1). P.get() 안의 v는 P.v다. C가 get()을 오버라이딩해 그 안에서 v를 읽었다면 2가 됐을 것이다. 부모 클래스에 선언된 생성자가 Parent(String name) 하나뿐이다. 다음 자식 클래스 가운데 컴파일되는 것은? class A extends Parent { } class B extends Parent { B() { } } class C extends Parent { C(String n) { System.out.println(n); super(n); } } class D extends Parent { D() { super("기본"); } } 생성자는 this(...)나 super(...)로 시작해야 하고, 없으면 컴파일러가 인자 없는 super()를 넣는다. A는 기본 생성자가, B는 빈 생성자가 super()를 호출하게 되는데 부모에 인자 없는 생성자가 없어 오류다. C는 super(...)가 첫 문장이 아니어서 Java 21에서 오류다. D는 첫 문장에서 존재하는 부모 생성자를 호출하므로 컴파일된다. 자식 클래스의 오버라이딩한 메서드 안에서 super.pay()를 호출하는 것과 pay()를 호출하는 것의 차이로 옳은 것은? 차이가 없다. 둘 다 부모의 pay()를 실행한다. super.pay()는 객체의 클래스와 무관하게 부모 클래스에서 출발해 메서드를 찾고, pay()는 객체의 클래스를 기준으로 선택되므로 자기 자신이 다시 호출된다. super.pay()는 부모 객체를 새로 만들어 그 객체의 메서드를 호출한다. pay()는 컴파일 오류다. 오버라이딩한 메서드 안에서는 반드시 super를 붙여야 한다. super.메서드()는 invokespecial로 컴파일되어 오버라이딩이 적용되지 않고 직접 부모 클래스의 메서드가 실행된다. 그냥 pay()는 this.pay()이고 invokevirtual로 컴파일되어 객체의 클래스에서 메서드를 선택하므로, 오버라이딩한 메서드 자신이 재귀 호출되어 StackOverflowError로 이어진다. super는 별도의 객체를 만들지 않는다.
    상속(inheritance)
    기존 클래스의 멤버를 물려받아 새 클래스를 정의하는 것. 자바에서는 extends 키워드로 부모 클래스 하나를 지정한다.
    슈퍼클래스·서브클래스(superclass, subclass)
    상속 관계에서 물려주는 쪽이 슈퍼클래스(부모 클래스), 물려받는 쪽이 서브클래스(자식 클래스)다.
    메서드 오버라이딩(method overriding)
    상속받은 인스턴스 메서드를 자식 클래스에서 같은 시그니처로 다시 정의하는 것. 실행 시점에 객체의 클래스를 기준으로 선택된다.
    숨김(hiding)
    자식이 부모와 같은 이름의 필드 또는 같은 시그니처의 static 메서드를 선언해 부모의 것이 이름으로 직접 보이지 않게 되는 것. 부모의 것은 없어지지 않는다.
    공변 반환 타입(covariant return type)
    오버라이딩하는 메서드가 반환 타입을 부모 메서드의 반환 타입의 하위 타입으로 좁히는 것.
    브리지 메서드(bridge method)
    언어 수준의 오버라이딩과 JVM 수준의 디스크립터 일치 사이의 차이를 메우기 위해 컴파일러가 생성하는 연결용 메서드. ACC_BRIDGE 플래그가 붙는다.
    기호 참조(symbolic reference)
    클래스 파일에 메서드나 필드를 주소가 아니라 클래스 이름, 멤버 이름, 디스크립터로 적어 둔 것. JVM이 실행 중에 실제 대상으로 해석한다.
    super
    현재 객체에 대해 멤버 탐색을 직접 부모 클래스에서 시작하게 하는 키워드. super(...)는 부모 생성자 호출이다.
    생성자 연쇄(constructor chaining)
    자식 생성자가 부모 생성자를 호출하고 그 부모가 다시 자신의 부모 생성자를 호출해 Object까지 이어지는 것.
    final 클래스·final 메서드
    final 클래스는 상속할 수 없는 클래스, final 메서드는 오버라이딩할 수 없는 메서드다.
