    지금까지 미뤄 둔 질문들

    앞 회차들에서 여러 번 "그 값은 어디에 있는가"라는 질문을 임시 답으로 넘겼다. 2회에서는 참조형 변수에 참조값이 들어 있고 객체는 다른 곳에 있다고 했다. 4회에서는 this가 "스택 프레임의 0번 지역 변수"라고 했고, new가 "힙"에 메모리를 잡는다고 했다. 5회에서는 클래스가 "실제로 처음 쓰이는 시점에 메모리에 올라온다"고만 하고 지나갔다. 이 회차는 그 임시 답들을 하나의 그림으로 맞춘다.

    구체적으로 답하려는 질문은 이런 것들이다. 메서드가 다른 메서드를 부르고 돌아올 때 지역 변수는 어디에 보관되었다가 어떻게 사라지는가. 메서드가 끝난 뒤에도 그 안에서 만든 객체가 살아남는 이유는 무엇인가. 같은 클래스의 객체 백 개가 메서드 코드를 백 벌 갖고 있는가. 그리고 이 회차의 후반부 주제인 static이 붙은 변수와 메서드는 객체 없이 어떻게 존재하며, 왜 static 메서드 안에서는 인스턴스 변수를 쓸 수 없는가.

    이 질문들의 답은 자바 언어 문법이 아니라 자바 가상 머신(JVM)이 프로그램을 실행하면서 쓰는 메모리의 구조에 있다. 그 구조를 정의한 문서가 Java Virtual Machine Specification(JVMS)이고, 해당 부분이 2.5절 "런타임 데이터 영역(Run-Time Data Areas)"이다. 먼저 널리 쓰이는 단순한 모델을 보고, 이어서 명세의 정의로 정밀하게 다듬은 뒤, 실제 JVM 구현인 HotSpot이 그것을 어떻게 구현하는지를 구분해서 본다.

    메서드 영역은 주방에 한 권 있는 레시피 책이다. 요리를 백 접시 만들어도 레시피는 한 권이다. 힙은 손님 테이블 위에 놓인 접시들이다. 접시마다 담긴 양은 다르지만 모두 같은 레시피로 만들었다. 스택은 요리사가 지금 처리 중인 주문서를 꽂아 두는 꽂이다. 새 주문이 들어와 하던 일을 잠시 멈출 때는 새 주문서를 맨 위에 꽂고, 끝나면 뽑아 버린 뒤 아래 주문서로 돌아간다. 비유가 맞지 않는 부분은 요리사가 여러 명일 때다. 자바에서는 스레드마다 꽂이가 따로 있고 다른 스레드의 꽂이는 들여다볼 수 없지만, 테이블(힙)과 레시피 책(메서드 영역)은 모든 스레드가 함께 쓴다.

    JVMS가 정의한 런타임 데이터 영역 여섯 가지

    명세의 정의로 넘어가자. JVMS 2.5는 JVM이 프로그램을 실행하는 동안 쓰는 데이터 영역을 정의하면서 먼저 둘로 나눈다. JVM이 시작될 때 만들어져 JVM이 끝날 때 없어지는 영역이 있고, 스레드마다 따로 있어서 스레드가 만들어질 때 생기고 스레드가 끝날 때 없어지는 영역이 있다. 여섯 영역을 표로 먼저 본다.

    pc 레지스터

    JVM은 여러 스레드를 동시에 실행할 수 있고, 각 스레드는 자기만의 pc(program counter) 레지스터를 갖는다. 어느 시점이든 한 스레드는 메서드 하나의 코드를 실행하고 있는데, 그 메서드가 native가 아니면 pc 레지스터에는 지금 실행 중인 JVM 명령의 주소가 들어 있다. javap -c 출력에서 명령 앞에 붙은 0:, 3:, 4: 같은 숫자가 메서드 코드 안에서의 위치이고, pc는 그 위치를 따라 움직인다고 생각하면 된다. 실행 중인 메서드가 native이면 pc 레지스터의 값은 정의되지 않는다. 스레드마다 pc가 따로 있어야 하는 이유는 분명하다. 스레드 A가 실행을 잠시 멈추고 스레드 B가 실행되다가 다시 A로 돌아올 때, A가 어디까지 실행했는지를 A 자신의 pc가 기억하고 있어야 한다.

    JVM 스택

    각 스레드는 스레드와 동시에 만들어지는 자기만의 JVM 스택을 갖는다. JVM 스택은 프레임(frame)을 저장한다. 명세는 이것이 C 같은 전통적인 언어의 스택과 비슷해서 지역 변수와 중간 결과를 보관하고 메서드 호출과 반환에 관여한다고 설명한다. 프레임은 메서드가 호출될 때마다 하나 만들어지고 그 호출이 끝나면 없어진다. 프레임의 내부 구조는 뒤에서 자세히 본다.

    명세는 JVM 스택의 크기가 고정이어도 되고 계산에 따라 늘었다 줄었다 해도 된다고 허용한다. 그리고 두 가지 오류 조건을 정한다. 스레드의 계산이 허용된 것보다 큰 스택을 요구하면 JVM은 StackOverflowError를 던진다. 스택을 동적으로 늘릴 수 있는 구현에서 늘리려는데 메모리를 확보하지 못하거나, 새 스레드의 초기 스택을 만들 메모리가 없으면 OutOfMemoryError를 던진다.

    힙

    힙은 모든 스레드가 공유하는 영역이고, 모든 클래스 인스턴스와 배열의 메모리가 여기서 할당된다. JVM이 시작될 때 만들어진다. 명세는 객체가 차지한 힙 공간이 자동 저장소 관리 시스템, 곧 가비지 컬렉터(garbage collector)에 의해 회수되며 객체는 결코 명시적으로 해제되지 않는다고 적는다. 자바에 C의 free나 C++의 delete에 해당하는 문법이 없는 것이 이 때문이다. 어떤 방식의 가비지 컬렉터를 쓸지는 명세가 정하지 않고 구현에 맡긴다. 계산이 요구하는 만큼의 힙을 저장소 관리 시스템이 내주지 못하면 JVM은 OutOfMemoryError를 던진다.

    메서드 영역

    메서드 영역도 모든 스레드가 공유한다. 명세는 이것을 전통적인 언어에서 컴파일된 코드를 저장하는 영역, 또는 운영 체제 프로세스의 텍스트(text) 세그먼트에 비유한다. 여기에 저장되는 것은 클래스별 구조다. 런타임 상수 풀, 필드와 메서드에 관한 데이터, 메서드와 생성자의 코드가 들어가고, 4회에서 본 이나 이 회차에서 볼 같은 특별한 메서드의 코드도 포함된다.

    명세의 다음 문장은 뒤에서 구현을 볼 때 중요하다. 메서드 영역은 논리적으로는 힙의 일부이지만 단순한 구현은 이 영역을 가비지 컬렉션하거나 압축하지 않을 수도 있고, 명세는 메서드 영역의 위치나 컴파일된 코드를 관리하는 정책을 강제하지 않는다. 다시 말해 메서드 영역은 "무엇이 들어가는가"로 정의된 개념이지, 메모리의 어느 구역이라고 정해진 것이 아니다.

    런타임 상수 풀

    5회에서 javap -v로 본 상수 풀(#7 = Class ... // store/order/Item 같은 항목들)은 클래스 파일 안의 표였다. 런타임 상수 풀은 그 표가 실행 중의 JVM 안에 올라온 형태다. 클래스나 인터페이스마다 하나씩 있고, 숫자 리터럴처럼 컴파일 타임에 값이 정해진 상수부터 실행 중에 해석해야 하는 메서드·필드 참조까지 담는다. 명세는 이것이 전통적인 언어의 심벌 테이블과 비슷한 역할을 한다고 설명한다. 런타임 상수 풀은 메서드 영역에서 할당되고, JVM이 그 클래스를 만들 때 함께 만들어진다. 바이트코드의 invokestatic #7에서 #7이 바로 현재 클래스의 런타임 상수 풀 7번 항목을 가리킨다.

    네이티브 메서드 스택

    native 메서드는 자바가 아닌 언어(대개 C나 C++)로 작성된 메서드다. JVM 구현은 이런 메서드를 지원하기 위해 전통적인 스택, 흔히 "C 스택"이라고 부르는 것을 쓸 수 있다. 명세는 네이티브 메서드를 로딩할 수 없고 스스로도 전통적인 스택에 의존하지 않는 구현이라면 이 영역을 제공하지 않아도 된다고 적는다. 제공되는 경우 보통 스레드가 만들어질 때 스레드별로 할당되고, 오류 조건은 JVM 스택과 같다.

    여섯 영역을 세 영역 모델과 맞춰 보면, "스택 영역"은 JVM 스택(과 그 곁의 pc 레지스터, 네이티브 메서드 스택)에, "힙 영역"은 힙에, "메서드 영역"은 메서드 영역과 그 안의 런타임 상수 풀에 대응한다. 가장 중요한 구분은 스레드마다 있는가, 공유되는가다. 스택 쪽은 스레드마다 따로 있어서 다른 스레드가 볼 수 없고, 힙과 메서드 영역은 모든 스레드가 함께 본다. 이 구분은 나중에 멀티스레드를 배울 때 "지역 변수는 안전하고, 객체의 필드와 static 변수는 조심해야 한다"는 규칙의 근거가 된다.

    스레드마다 따로 있는 영역(pc 레지스터, JVM 스택, 네이티브 메서드 스택)과 모든 스레드가 공유하는 영역(힙, 메서드 영역과 그 안의 런타임 상수 풀)을 한눈에 구분해 보여 준다. 큰 둥근 사각형 하나가 전체 테두리이고 위쪽에 제목 라벨 "JVM 런타임 데이터 영역". 내부는 좌우 두 구역으로 나뉜다. 왼쪽 구역의 머리 라벨은 "스레드마다 따로"이고, 그 안에 세로로 긴 카드 두 장이 나란히 있다. 첫 번째 카드 제목 "스레드 1", 두 번째 카드 제목 "스레드 2". 각 카드 안에는 위에서 아래로 세 개의 상자: 작은 상자 "pc 레지스터", 프레임 세 칸이 쌓인 모양의 큰 상자 "JVM 스택", 작은 상자 "네이티브 메서드 스택". 오른쪽 구역의 머리 라벨은 "모든 스레드가 공유"이고, 그 안에 위아래로 큰 상자 두 개: 위 상자 "힙" 안에는 작은 동그라미 여러 개가 흩어져 있고 그 옆에 작은 글씨 "객체와 배열"; 아래 상자 "메서드 영역" 안에는 책 모양 아이콘 두 개와 작은 글씨 "클래스별 구조", 그리고 그 안쪽에 점선 테두리의 작은 상자 "런타임 상수 풀". 왼쪽 두 카드의 JVM 스택에서 오른쪽 힙의 동그라미로 향하는 얇은 화살표가 각각 하나씩 있다. 왼쪽 구역은 옅은 주황, 오른쪽 구역은 옅은 파랑 배경. 흰 바탕, 얇은 선, 한국어 라벨은 따옴표 안의 문구 그대로. pc 레지스터와 두 스택은 스레드의 것이고, 힙과 메서드 영역은 JVM 전체의 것이다.

    명세와 HotSpot 구현을 구분한다

    JVMS는 스스로를 추상 기계의 명세라고 밝히고, 런타임 데이터 영역의 메모리 배치나 가비지 컬렉션 알고리즘 같은 것은 구현자의 재량에 맡긴다고 적는다(JVMS 2장 서두). 따라서 "메서드 영역은 메모리의 어디에 있는가", "static 변수는 물리적으로 어디에 저장되는가"는 명세가 아니라 구현의 질문이다. 우리가 보통 쓰는 JDK의 JVM은 OpenJDK의 HotSpot이므로, 확인할 수 있는 범위에서 HotSpot의 구현을 정리한다. 아래 내용은 명세가 보장하는 것이 아니고 다른 JVM 구현이나 다른 버전에서는 달라질 수 있다.

    PermGen에서 메타스페이스로 (JDK 8, JEP 122)

    JDK 8보다 앞선 HotSpot에는 영구 세대(permanent generation, 줄여서 PermGen)라는 구역이 있었다. 이 구역을 없애자고 제안한 JEP 122는 당시 구조를 이렇게 설명한다. HotSpot이 자바 클래스를 표현하는 내부 데이터(클래스 메타데이터)는 자바 힙의 일부인 영구 세대에 저장되고, 인터닝된 문자열과 클래스의 static 변수도 영구 세대에 저장된다. 영구 세대는 애플리케이션이 쓰는 모든 클래스 메타데이터와 static 변수를 담을 만큼 커야 하며, 그 한계는 -XX:MaxPermSize 값으로 고정된다.

    JEP 122 "Remove the Permanent Generation"은 JDK 8에 반영되어 이 구역을 없앴다. JEP가 제시한 구현은 클래스 메타데이터를 네이티브 메모리에 할당하고, 인터닝된 문자열과 클래스의 static 변수를 자바 힙에 두는 것이다. 클래스 메타데이터를 담는 이 네이티브 메모리 영역이 메타스페이스(Metaspace)다. JDK 21의 HotSpot 가비지 컬렉션 튜닝 가이드는 JDK 8부터 영구 세대가 제거되어 클래스 메타데이터가 네이티브 메모리에 할당되고, 여기에 쓸 수 있는 네이티브 메모리의 양은 기본적으로 제한이 없으며 -XX:MaxMetaspaceSize로 상한을 둘 수 있다고 설명한다. 같은 문서는 클래스 메타데이터가 해당 자바 클래스가 언로드될 때 해제된다고도 적는다.

    static 변수는 실제로 어디에 있는가

    위 내용에서 눈여겨볼 점은 영구 세대가 없는 JDK 8 이후의 HotSpot에서 static 변수의 저장 위치가 메타스페이스가 아니라 자바 힙이라는 것이다. 더 구체적인 위치는 HotSpot 소스 코드에서 확인할 수 있다. HotSpot은 자바의 클래스 하나하나에 대해 그 클래스를 나타내는 java.lang.Class 객체를 힙에 두는데, instanceMirrorKlass.hpp의 주석은 java.lang.Class의 인스턴스가 Class 자신의 일반 필드에 더해 그 클래스의 static 필드들을 담고 있다고 설명한다. 즉 Ticket 클래스의 static 변수 nextNumber는 Ticket을 나타내는 Class 객체 안에 들어 있다.

    그러면 "static 변수는 메서드 영역에 있다"는 흔한 설명은 틀린 것일까. 명세의 층에서 보면 이 설명은 모델로서 유효하다. 명세가 static 변수에 대해 정하는 것은 클래스마다 정확히 하나 존재한다는 것, 클래스가 준비될 때 만들어진다는 것, 클래스가 언로드되면 사라진다는 것이다. 클래스 단위의 구조를 담는 곳이 메서드 영역이므로, static 변수를 메서드 영역 쪽에 그리는 것은 "객체가 아니라 클래스에 속한다"는 사실을 표현하는 자연스러운 방법이다. 다만 그것을 "HotSpot의 메타스페이스에 static 변수의 값이 들어 있다"는 물리적 주장으로 받아들이면 사실과 다르다. 이 강좌의 그림에서는 명세의 모델을 따라 static 변수를 클래스 쪽에 그리되, 물리적 위치를 말할 때는 "HotSpot에서는 힙의 Class 객체"라고 구분해서 말한다.

    프로그래머에게 실질적으로 중요한 것은 물리적 주소가 아니라 다음 세 가지다. static 변수는 객체를 몇 개 만들든 하나뿐이다. 모든 스레드가 공유한다. 그리고 클래스가 언로드되기 전에는 사라지지 않으므로, static 변수가 참조하는 객체는 가비지 컬렉션의 대상이 되지 않는다.

    프레임이 꼭 "스택이라는 연속된 메모리 구역"에 있어야 하는 것도 아니다. JVMS 2.5.2는 JVM 스택이 프레임을 넣고 빼는 것 외에는 직접 조작되지 않으므로 프레임이 힙에 할당되어도 된다고 적는다. 실제로 JDK 21에서 정식 기능이 된 가상 스레드(JEP 444)의 스택은 자바 힙에 스택 청크 객체로 저장된다. 명세의 "스택"은 후입선출이라는 동작 방식으로 정의된 것이지 메모리의 위치로 정의된 것이 아니다.

    스택과 큐 자료 구조

    "스택 영역"의 스택은 원래 자료 구조의 이름이다. 자료 구조는 데이터를 넣고 꺼내는 규칙을 정한 것인데, 가장 기본적인 두 가지가 스택과 큐다.

    • 스택(stack)은 나중에 넣은 것을 먼저 꺼낸다. 후입선출(LIFO, last-in-first-out)이라고 한다. 넣는 동작을 push, 꺼내는 동작을 pop이라고 부른다. 넣는 곳과 꺼내는 곳이 같은 한쪽 끝이다.
    • 큐(queue)는 먼저 넣은 것을 먼저 꺼낸다. 선입선출(FIFO, first-in-first-out)이라고 한다. 한쪽 끝으로 넣고 반대쪽 끝에서 꺼낸다.

    자바 표준 라이브러리로 두 동작을 확인할 수 있다. 컬렉션은 중급 2편에서 본격적으로 다루므로 여기서는 넣고 꺼내는 순서만 본다.

    import java.util.ArrayDeque;
import java.util.Deque;
import java.util.Queue;

public class DequeMain {
    public static void main(String[] args) {
        Deque stack = new ArrayDeque<>();
        stack.push(1);
        stack.push(2);
        stack.push(3);
        System.out.println(stack.pop() + " " + stack.pop() + " " + stack.pop());

        Queue queue = new ArrayDeque<>();
        queue.offer(1);
        queue.offer(2);
        queue.offer(3);
        System.out.println(queue.poll() + " " + queue.poll() + " " + queue.poll());
    }
}

1 2 3
    java.util에는 Stack이라는 클래스도 있지만, Javadoc은 Deque 인터페이스와 그 구현체가 더 완전하고 일관된 스택 연산을 제공하므로 Stack 대신 그것을 쓰라고 안내한다. ArrayDeque의 Javadoc도 이 클래스가 스택으로 쓸 때 Stack보다, 큐로 쓸 때 LinkedList보다 빠를 가능성이 높다고 적는다.

    메서드 호출을 관리하는 데 왜 큐가 아니라 스택이 쓰일까. 메서드 호출은 괄호처럼 중첩된다. main이 addTax를 부르고 addTax가 rate를 부르면, 가장 나중에 시작한 rate가 가장 먼저 끝나고, 그다음 addTax, 마지막으로 main이 끝난다. 호출한 메서드는 호출된 메서드가 끝날 때까지 자기 지역 변수를 그대로 둔 채 기다려야 하고, 돌아갈 곳은 언제나 "가장 최근에 멈춰 둔 메서드"다. 나중에 들어온 것이 먼저 나가는 이 순서가 정확히 스택이다. 반면 큐는 도착한 순서대로 처리해야 하는 대기열에 맞는다. 처리할 작업을 줄 세워 두는 자리에 큐가 쓰이고, 이는 멀티스레드를 다루는 고급 1편에서 다시 만난다.

    스택 프레임의 구조: 지역 변수 배열과 피연산자 스택

    JVM 스택에 쌓이는 단위가 프레임이다. JVMS 2.6에 따르면 프레임은 메서드가 호출될 때마다 새로 만들어지고, 그 호출이 정상적으로 끝나든 예외로 끝나든 호출이 완료되면 없어진다. 프레임은 그것을 만든 스레드의 JVM 스택에서 할당되고, 각 프레임은 세 가지를 갖는다.

    • 지역 변수 배열(local variables): 그 메서드 호출의 매개변수와 지역 변수가 들어가는 칸들.
    • 피연산자 스택(operand stack): 계산에 쓸 값을 잠깐 올려 두는 작업대.
    • 현재 메서드가 속한 클래스의 런타임 상수 풀에 대한 참조: 코드 안의 #7 같은 번호를 실제 클래스·필드·메서드로 연결(동적 링크)하는 데 쓴다.

    지역 변수 배열

    지역 변수 배열은 0번부터 번호가 매겨진 칸의 배열이다(JVMS 2.6.1). 칸 하나에는 boolean, byte, char, short, int, float, 참조(reference) 타입의 값 하나가 들어가고, long과 double은 연속된 칸 두 개를 차지한다. JVM은 메서드를 호출할 때 인자를 이 배열로 전달한다. 여기서 이 회차 후반부의 열쇠가 되는 규칙이 나온다.

    • 클래스 메서드(static 메서드)를 호출하면 인자가 0번 칸부터 차례로 들어간다.
    • 인스턴스 메서드를 호출하면 0번 칸에는 항상 그 메서드가 호출된 대상 객체의 참조(자바의 this)가 들어가고, 인자는 1번 칸부터 들어간다.

    피연산자 스택

    JVM의 명령은 대부분 피연산자를 명령 안에 적지 않고 피연산자 스택에서 꺼내 쓴다(JVMS 2.6.2). 프레임이 만들어질 때 피연산자 스택은 비어 있다. 상수나 지역 변수의 값을 스택에 올리는 명령이 있고, 스택에서 값을 꺼내 연산한 뒤 결과를 다시 스택에 올리는 명령이 있다. 명세가 드는 예가 iadd다. 이 명령은 스택 맨 위의 int 값 두 개를 꺼내 더하고 그 합을 스택에 올린다. 피연산자 스택은 메서드에 넘길 인자를 준비하는 데에도, 메서드가 돌려준 결과를 받는 데에도 쓰인다.

    이름이 비슷해서 헷갈리기 쉬운데, "JVM 스택"과 "피연산자 스택"은 층이 다르다. JVM 스택은 프레임들이 쌓이는 스택이고, 피연산자 스택은 프레임 하나의 내부에 있는 계산용 스택이다. 둘 다 후입선출이라는 점만 같다.

    크기는 컴파일할 때 정해진다

    지역 변수 배열의 길이와 피연산자 스택의 최대 깊이는 컴파일 타임에 결정되어 메서드의 코드와 함께 클래스 파일에 기록된다(JVMS 2.6). javap -v로 확인할 수 있다. 다음 절에서 추적할 예제의 main 메서드는 이렇게 나온다.

    public static void main(java.lang.String[]);
  descriptor: ([Ljava/lang/String;)V
  flags: (0x0009) ACC_PUBLIC, ACC_STATIC
  Code:
    stack=2, locals=3, args_size=1

    locals=3은 지역 변수 배열이 세 칸이라는 뜻이고(args, base, result), stack=2는 이 메서드를 실행하는 동안 피연산자 스택에 값이 최대 두 개까지 쌓인다는 뜻이다. args_size=1은 인자가 하나라는 뜻이다. JVM은 메서드를 호출하는 순간 이 숫자들로 프레임에 필요한 공간을 알 수 있다.

    프레임 하나 안에 번호가 붙은 지역 변수 배열과 계산용 피연산자 스택, 그리고 메서드 영역의 런타임 상수 풀을 가리키는 참조가 있다는 것을 보여 준다. 가운데에 큰 둥근 사각형 하나, 위쪽 머리 라벨 "프레임 (메서드 호출 한 번)". 사각형 내부는 세 구획. 왼쪽 구획 제목 "지역 변수 배열": 가로로 나란한 세 칸짜리 배열, 칸 아래에 인덱스 "0", "1", "2", 칸 안에는 각각 "this", "매개변수", "지역 변수". 0번 칸 위에 작은 말풍선 "인스턴스 메서드일 때". 가운데 구획 제목 "피연산자 스택": 세로로 쌓인 두 칸짜리 스택, 위 칸에 "10", 아래 칸에 "3", 스택 위쪽에 위아래 양방향 화살표와 라벨 "넣고 꺼냄". 오른쪽 구획 제목 "런타임 상수 풀 참조": 작은 상자 하나에서 프레임 바깥 오른쪽으로 화살표가 나가 별도의 상자 "메서드 영역의 런타임 상수 풀"을 가리킨다. 프레임 아래쪽 바깥에는 옅은 회색으로 같은 모양의 프레임 두 개가 살짝 어긋나게 겹쳐 쌓여 있고 라벨 "JVM 스택의 다른 프레임들". 흰 배경, 얇은 선, 파랑과 주황 두 가지 강조색, 한국어 라벨은 따옴표 안의 문구 그대로. 프레임은 메서드 호출 한 번의 작업 공간이다. 크기는 컴파일할 때 정해진다.

    메서드 호출과 반환을 단계별로 추적한다

    작은 프로그램 하나를 바이트코드 수준에서 끝까지 따라가 보자. 값에 10%를 더해 돌려주는 계산을 일부러 세 메서드로 나눴다.

    public class FrameMain {
    public static void main(String[] args) {
        int base = 10;
        int result = addTax(base);
        System.out.println(result);   // 11
    }

    static int addTax(int price) {
        int tax = rate(price);
        return price + tax;
    }

    static int rate(int price) {
        return price / 10;
    }
}

    호출과 반환에서 일어나는 일을 명세의 문장으로 확인해 두자. invokestatic의 설명(JVMS 6.5)에 따르면 인자 값들을 피연산자 스택에서 꺼내고, 호출되는 메서드를 위한 새 프레임을 JVM 스택에 만들고, 인자 값들을 새 프레임의 지역 변수 0번부터 차례로 넣고, 새 프레임을 현재 프레임으로 삼은 뒤, pc를 그 메서드의 첫 명령으로 맞춘다. 반환은 JVMS 2.6.4가 정한다. 메서드가 정상적으로 끝나면 호출자의 상태(지역 변수와 피연산자 스택)가 복원되고, 호출자의 pc는 호출 명령을 지난 다음 위치로 맞춰지며, 반환값이 있으면 호출자 프레임의 피연산자 스택에 올려진다. 단계 [6]에서 addTax가 4번 명령부터, 단계 [8]에서 main이 7번 명령부터 이어서 실행된 것이 이 규칙이다.

    이 추적에서 네 가지를 얻을 수 있다.

    1. 인자 전달은 값의 복사다. main의 base(1번 칸의 10)는 피연산자 스택을 거쳐 addTax 프레임의 0번 칸으로 복사되었다. 두 칸은 서로 다른 프레임에 있는 별개의 변수다. addTax가 자기 price를 바꿔도 main의 base는 변하지 않는다. 2회에서 본 "자바는 항상 변수의 값을 복사해서 전달한다"는 규칙의 실체가 이것이다.
    2. 지역 변수는 호출마다 새로 생긴다. addTax의 price와 rate의 price는 이름만 같을 뿐 다른 프레임의 다른 칸이다. 같은 메서드를 여러 번 호출해도, 메서드가 자기 자신을 다시 호출해도(재귀) 호출마다 프레임이 따로 만들어지므로 변수가 섞이지 않는다.
    3. 지역 변수의 수명은 프레임의 수명이다. 메서드가 반환하면 프레임이 통째로 버려지고 그 안의 지역 변수도 함께 사라진다. 따로 정리하는 코드가 필요 없다.
    4. 호출 깊이만큼 프레임이 쌓인다. 단계 [4]~[5]에서 프레임이 세 개 쌓여 있었다. 호출이 깊어질수록 스택은 높아진다.

    스택이 넘치면: StackOverflowError

    네 번째 관찰의 극단이 끝나지 않는 재귀다. 종료 조건 없이 자기 자신을 호출하는 메서드는 프레임을 계속 쌓기만 한다.

    public class Overflow {
    static int depth = 0;

    static void dive() {
        depth++;
        dive();
    }

    public static void main(String[] args) {
        try {
            dive();
        } catch (StackOverflowError e) {
            System.out.println("StackOverflowError, depth=" + depth);
        }
    }
}

    이 프로그램은 StackOverflowError, depth= 뒤에 숫자를 출력하고 끝난다. 숫자는 실행할 때마다, 그리고 환경마다 다르다. JVMS 2.5.2가 정한 대로 스레드의 계산이 허용된 것보다 큰 JVM 스택을 요구했기 때문에 JVM이 오류를 던진 것이다. StackOverflowError의 Javadoc도 이 오류를 애플리케이션이 너무 깊이 재귀해서 스택 오버플로가 일어날 때 던져진다고 설명한다. HotSpot에서 스레드의 스택 크기는 -Xss 옵션으로 정할 수 있고, java 명령 문서에 따르면 기본값은 플랫폼에 따라 다르다. 같은 프로그램을 -Xss256k처럼 스택을 줄여 실행하면 훨씬 얕은 깊이에서 오류가 난다. 실무에서 이 오류를 만났다면 대개 스택 크기를 키울 일이 아니라 종료 조건이 빠진 재귀나, 서로를 끝없이 호출하는 메서드를 찾아야 한다.

    호출할 때마다 프레임이 위에 쌓이고, 반환할 때마다 맨 위 프레임이 사라지며 반환값이 아래 프레임으로 전달되는 과정을 다섯 장면으로 보여 준다. 가로로 나란히 놓인 다섯 개의 패널, 각 패널은 아래에서 위로 쌓이는 상자 더미(스택)를 보여 준다. 패널 위에 순서 라벨: "① main 실행", "② addTax 호출", "③ rate 호출", "④ rate 반환", "⑤ addTax 반환". 패널 ①: 상자 하나 "main" 안에 작은 글씨 "base = 10". 패널 ②: 아래에 "main", 그 위에 새 상자 "addTax" 안에 "price = 10"; main에서 addTax로 위로 향하는 화살표와 라벨 "10 복사". 패널 ③: 아래부터 "main", "addTax", 맨 위에 새 상자 "rate" 안에 "price = 10". 패널 ④: "main", "addTax"만 남고 addTax 안에 "tax = 1"; 사라진 rate 자리는 점선 테두리로 표시하고 아래로 향하는 화살표와 라벨 "반환값 1". 패널 ⑤: "main"만 남고 안에 "result = 11"; 사라진 addTax 자리는 점선 테두리, 아래로 향하는 화살표와 라벨 "반환값 11". 맨 위에 쌓인 현재 프레임은 주황색, 대기 중인 프레임은 옅은 파랑. 패널 사이에는 오른쪽 방향 얇은 화살표. 흰 배경, 한국어 라벨은 따옴표 안의 문구 그대로. 가장 나중에 호출된 메서드가 가장 먼저 끝난다. 프레임이 사라질 때 그 안의 지역 변수도 함께 사라진다.

    스택 영역과 힙 영역: 참조는 프레임에, 객체는 힙에

    앞 예제는 기본형만 썼으므로 힙이 등장하지 않았다. 이번에는 객체를 만들어 메서드에 넘겨 본다.

    class Cart {
    int total;
}

public class HeapMain {
    public static void main(String[] args) {
        Cart cart = new Cart();
        add(cart, 3000);
        add(cart, 1500);
        System.out.println(cart.total);   // 4500
    }

    static void add(Cart target, int price) {
        target.total += price;
    }
}

    실행 순서대로 두 영역의 상태를 따라가면 다음과 같다. 참조값은 설명을 위해 x001로 적는다.

    1. new Cart()가 실행되면 힙에 Cart 인스턴스가 만들어지고(total = 0), 그 참조 x001이 main 프레임의 지역 변수 cart에 저장된다. 객체는 힙에, 객체를 가리키는 참조는 스택의 프레임에 있다.
    2. add(cart, 3000)이 호출되면 add 프레임이 쌓이고, 인자 두 개가 복사되어 지역 변수 target = x001, price = 3000이 된다. 복사된 것은 참조값이다. 객체는 여전히 하나이고, 이제 main의 cart와 add의 target이 같은 객체를 가리킨다.
    3. target.total += price는 target이 가리키는 힙의 객체에 가서 total을 3000으로 바꾼다.
    4. add가 반환하면 add 프레임이 버려지고 target과 price가 사라진다. 그러나 힙의 객체는 그대로다. main의 cart가 여전히 그 객체를 가리키고 있다.
    5. 두 번째 add(cart, 1500)도 같은 과정을 거쳐 total이 4500이 된다. 새로 만들어진 것은 프레임이지 객체가 아니다.
    6. main이 반환하면 main 프레임과 함께 cart 변수도 사라진다. 이제 x001 객체를 가리키는 참조는 어디에도 없다.

  ┌──────────────────────────────┐
  │ add 프레임                    │
  │   target = x001 ─────────────┼──┐
  │   price  = 1500              │  │      ┌──────────────────────┐
  ├──────────────────────────────┤  ├────▶ │ x001: Cart 인스턴스   │
  │ main 프레임                   │  │      │   total = 3000 → 4500│
  │   args                       │  │      └──────────────────────┘
  │   cart   = x001 ─────────────┼──┘
  └──────────────────────────────┘

    스택과 힙의 차이는 수명을 결정하는 방식에 있다. 프레임과 그 안의 지역 변수는 메서드가 반환하는 순간 확정적으로 사라진다. 힙의 객체는 그것을 만든 메서드와 수명이 묶여 있지 않다. 메서드 안에서 만든 객체라도 그 참조를 반환하거나 다른 객체의 필드, 또는 static 변수에 저장하면 메서드가 끝난 뒤에도 살아남는다. 반대로 어디에서도 참조하지 않게 된 객체는 메서드가 아직 실행 중이더라도 쓸 수 없는 객체가 된다.

    도달 가능성과 가비지 컬렉션

    힙의 객체가 언제 회수 대상이 되는지는 도달 가능성(reachability)으로 정해진다. JLS 12.6.1은 도달 가능한 객체를 "살아 있는 어떤 스레드에서든, 앞으로 계속될 수 있는 계산에서 접근될 수 있는 객체"로 정의한다. 실행 중인 스레드의 프레임에 있는 지역 변수가 가리키는 객체, 로딩된 클래스의 static 변수가 가리키는 객체, 그리고 그런 객체의 필드를 따라가서 닿을 수 있는 객체는 프로그램이 접근할 수 있으므로 도달 가능하다. 위 예제의 6단계처럼 어떤 변수로부터도 닿을 수 없게 된 객체는 프로그램이 다시는 쓸 방법이 없다. 가비지 컬렉터는 이런 객체가 차지한 힙 공간을 회수한다.

    명세가 보장하는 것은 여기까지다. 객체는 명시적으로 해제되지 않고 가비지 컬렉터가 회수한다는 것, 그리고 회수할 수 있는 조건이다. 언제 회수하는지, 어떤 알고리즘으로 하는지는 구현의 몫이다. HotSpot에는 여러 컬렉터가 있고, JDK 21의 튜닝 가이드에 따르면 대부분의 하드웨어·운영 체제 구성에서 G1이 기본으로 선택된다. 프로그램은 특정 시점에 객체가 회수된다고 가정해서는 안 된다. 가비지 컬렉터의 동작 방식은 그 자체로 큰 주제이므로, 여기서는 "도달할 수 없게 된 객체는 회수 대상이 되고, 회수 시점은 프로그램이 정하지 않는다"는 모델만 가지고 간다.

    JVM 스택의 프레임힙
    담는 것매개변수, 지역 변수, 계산 중간값객체와 배열(인스턴스 변수는 객체 안에)
    만들어지는 때메서드 호출new 실행
    없어지는 때메서드 반환 시 즉시도달할 수 없게 된 뒤 가비지 컬렉터가 회수(시점은 정해져 있지 않음)
    범위스레드마다 따로모든 스레드가 공유
    공간이 모자라면StackOverflowErrorOutOfMemoryError

    OutOfMemoryError의 Javadoc은 이 오류를 JVM이 메모리가 부족해 객체를 할당할 수 없고 가비지 컬렉터도 더 이상 메모리를 확보하지 못할 때 던져진다고 설명한다. 두 오류의 차이는 원인의 차이다. StackOverflowError는 호출이 너무 깊은 것이고, 힙의 OutOfMemoryError는 도달 가능한 객체가 너무 많은 것이다. 후자의 흔한 원인은 필요 없어진 객체를 어딘가에서 계속 참조하고 있어 가비지 컬렉터가 회수하지 못하는 경우이며, 뒤에서 볼 static 변수가 그 "어딘가"가 되기 쉽다.

    클래스가 메모리에 올라오는 과정: 로딩, 링크, 초기화

    스택과 힙을 봤으니 남은 것은 메서드 영역이다. 메서드 영역의 클래스 정보는 프로그램이 시작될 때 한꺼번에 채워지는 것이 아니다. 클래스 하나가 실행에 쓰일 수 있게 되기까지는 세 단계를 거치며, JLS 12장과 JVMS 5장이 이를 정의한다.

    준비와 초기화가 나뉘어 있다는 점을 기억해 두자. JLS 12.3.2는 준비 단계가 static 필드를 만들어 기본값으로 초기화하는 것이고, static 필드의 명시적인 초기화식은 준비가 아니라 초기화 단계에서 실행된다고 못 박는다. 4회에서 본 인스턴스의 경우(메모리 할당과 기본값 → 초기화식과 생성자)와 같은 두 단계 구조가 클래스 수준에도 있는 것이다.

    초기화는 언제 일어나는가 (JLS 12.4.1)

    세 단계 가운데 프로그램의 동작으로 관찰되는 것은 초기화다. static 초기화식과 초기화 블록은 개발자가 쓴 코드이고, 그 코드가 언제 실행되는지에 따라 출력이 달라지기 때문이다. JLS 12.4.1은 클래스 T가 다음 가운데 하나가 처음 일어나기 직전에 초기화된다고 정한다.

    • T의 인스턴스가 만들어진다.
    • T에 선언된 static 메서드가 호출된다.
    • T에 선언된 static 필드에 값이 대입된다.
    • T에 선언된 static 필드가 사용되고, 그 필드가 상수 변수(constant variable)가 아니다.

    그리고 명세는 이 밖의 상황(일부 리플렉션 메서드 호출, 하위 클래스가 초기화될 때의 상위 클래스 초기화 등 명시된 경우를 제외하고)에서는 클래스가 초기화되지 않는다고 덧붙인다. JVM 쪽의 정의도 같은 내용이다. JVMS 5.5는 클래스 초기화가 그 클래스를 참조하는 new, getstatic, putstatic, invokestatic 명령의 실행, 하위 클래스의 초기화, JVM 시작 시의 초기 클래스 지정 등의 결과로만 일어난다고 정한다. 네 명령은 위 네 조건을 바이트코드로 옮긴 것이다. 실험으로 확인해 보자.

    class Registry {
    static final int LIMIT = 100;
    static int created = log("static 변수 초기화식");

    static {
        log("static 초기화 블록");
    }

    int id = log("인스턴스 변수 초기화식");

    Registry() {
        log("생성자");
    }

    static int log(String step) {
        System.out.println("  [Registry] " + step);
        return 0;
    }
}

public class InitMain {
    public static void main(String[] args) {
        System.out.println("1. main 시작");
        Registry r = null;
        System.out.println("2. 변수 선언");
        System.out.println("3. 상수 읽기: " + Registry.LIMIT);
        System.out.println("4. 첫 번째 객체 생성");
        r = new Registry();
        System.out.println("5. 두 번째 객체 생성");
        r = new Registry();
    }
}
    1. main 시작
2. 변수 선언
3. 상수 읽기: 100
4. 첫 번째 객체 생성
  [Registry] static 변수 초기화식
  [Registry] static 초기화 블록
  [Registry] 인스턴스 변수 초기화식
  [Registry] 생성자
5. 두 번째 객체 생성
  [Registry] 인스턴스 변수 초기화식
  [Registry] 생성자

    출력에서 다섯 가지를 읽을 수 있다.

    1. Registry 타입의 변수를 선언하는 것만으로는 초기화가 일어나지 않는다. 2번 줄까지 [Registry] 출력이 없다. 변수 선언은 네 조건 어디에도 해당하지 않는다.
    2. 상수를 읽는 것도 초기화를 일으키지 않는다. LIMIT은 final이고 기본형이며 상수식으로 초기화되었으므로 JLS 4.12.4가 말하는 상수 변수다. 컴파일러는 상수 변수에 대한 참조를 그 값으로 바꿔서 컴파일한다(JLS 13.1). javap -c InitMain으로 보면 Registry.LIMIT을 읽는 getstatic 명령이 없다. 컴파일러가 100을 그 자리에 넣고 문자열 연결까지 끝낸 상수 "3. 상수 읽기: 100"이 들어 있을 뿐이다. 실행 중에 Registry를 건드리지 않으니 초기화될 이유가 없다. 상수는 7회에서 자세히 다룬다.
    3. 첫 new 직전에 초기화가 일어난다. static 변수 초기화식과 static 초기화 블록이 소스에 적힌 순서대로 실행되었다.
    4. 클래스 초기화가 끝난 뒤에 인스턴스 초기화가 시작된다. 인스턴스 변수 초기화식과 생성자는 4회에서 본 JLS 12.5의 순서로, 클래스 초기화 다음에 실행된다.
    5. 클래스 초기화는 한 번뿐이다. 두 번째 new에서는 인스턴스 쪽 두 줄만 다시 출력된다.

    로딩 시점도 관찰할 수 있다. HotSpot의 로그 옵션 -Xlog:class+load를 붙여 이 프로그램을 실행하면(JDK 21), Registry가 로딩되었다는 로그는 "4. 첫 번째 객체 생성" 출력 바로 다음에 나타난다. 이 실행에서 HotSpot은 Registry를 실제로 필요해진 순간에 로딩한 것이다. 다만 이것은 구현의 동작이다. JLS 12.2.1은 클래스 로더가 예상되는 사용에 맞춰 클래스를 미리 읽어 두는 것을 허용한다. 명세가 고정해 둔 것은 로딩 시점이 아니라 초기화 시점이다.

    static 초기화는 메서드가 된다

    4회에서 생성자와 인스턴스 초기화식이 메서드로 컴파일되는 것을 봤다. 클래스 쪽에도 짝이 있다. 컴파일러는 static 변수의 초기화식과 static 초기화 블록을 소스 순서대로 이어 붙여 이라는 이름의 메서드 하나로 만든다. JVMS 2.9.2는 이것을 클래스 초기화 메서드라고 부르고, 클래스는 이런 메서드를 최대 하나 가지며 JVM이 그 메서드를 호출함으로써 클래스가 초기화된다고 정한다. javap -c -p Registry에서는 static {}이라는 이름으로 보인다.

    static {};

    created의 초기화식(0~5번)과 static 블록의 본문(8~13번)이 한 메서드 안에 순서대로 들어 있다. LIMIT에 100을 넣는 코드는 여기에 없다. 상수 변수의 값은 코드가 아니라 클래스 파일의 필드 정보에 ConstantValue라는 속성으로 기록되어 있다. 도 처럼 자바 식별자로 쓸 수 없는 이름이어서 소스 코드에서 직접 호출할 수 없다.

    기본값이 보이는 순간, 그리고 초기화의 실패

    준비 단계의 기본값은 인스턴스에서와 같은 방법으로 드러난다.

    public class Fwd {
    static int a = next();
    static int b = 5;

    static int next() {
        return b + 1;
    }

    public static void main(String[] args) {
        System.out.println(a + " " + b);   // 1 5
    }
}

    a의 초기화식이 실행될 때 b는 준비 단계에서 받은 기본값 0이다. 그래서 next()는 1을 돌려주고, 그다음에야 b가 5가 된다. static 변수끼리 값을 주고받는 초기화식은 선언 순서에 의존하므로 주의해야 한다.

    초기화 과정에는 두 가지 보장과 한 가지 위험이 더 있다. JLS 12.4.2는 클래스마다 고유한 초기화 락을 두어, 한 스레드가 클래스를 초기화하는 동안 다른 스레드가 같은 클래스를 쓰려고 하면 초기화가 끝날 때까지 기다리게 한다. 여러 스레드가 동시에 처음 접근해도 static 초기화는 정확히 한 번만 실행된다. 위험은 static 초기화 중에 예외가 나는 경우다. 같은 절에 따르면 초기화식이 예외로 끝나면 JVM은 그 예외를 ExceptionInInitializerError로 감싸 던지고(원래 예외가 Error가 아닌 경우), 그 클래스를 오류 상태로 표시한다. 이후 그 클래스를 다시 쓰려는 시도는 NoClassDefFoundError가 된다. static 변수의 초기화식에 Integer.parseInt("abc")처럼 실패하는 코드를 두고 그 클래스의 static 메서드를 두 번 호출해 보면, 첫 번째는 ExceptionInInitializerError, 두 번째는 NoClassDefFoundError가 잡힌다. 클래스 파일이 멀쩡히 있는데도 NoClassDefFoundError가 난다면 그보다 앞선 로그에서 초기화 실패를 찾아야 한다.

    클래스가 로딩, 링크, 초기화를 차례로 거치고, static 변수가 준비 단계에서 기본값을 받았다가 초기화 단계에서 초기화식의 값을 받는다는 것을 보여 준다. 왼쪽에서 오른쪽으로 이어지는 세 개의 큰 단계 상자. 첫 번째 상자 제목 "로딩", 안에 파일 아이콘과 작은 글씨 "클래스 파일을 찾아 읽음". 두 번째 상자 제목 "링크", 안에 가로로 나란한 작은 상자 세 개 "검증", "준비", "해석". 세 번째 상자 제목 "초기화", 안에 작은 글씨 "static 초기화식과 static 블록 실행". 상자들 사이는 오른쪽 방향 굵은 화살표. 다이어그램 아래쪽에는 이 단계들과 세로로 정렬된 가로 띠가 하나 있고 왼쪽 끝 라벨 "static int nextNumber = 1 의 값". 띠 위에 "준비" 상자 바로 아래 위치에 동그라미와 라벨 "0 (기본값)", "초기화" 상자 바로 아래 위치에 동그라미와 라벨 "1 (초기화식)", 두 동그라미를 잇는 화살표. 세 번째 상자 위에는 말풍선 "처음 사용되기 직전, 한 번만". "준비" 작은 상자는 주황, "초기화" 상자는 파랑으로 강조. 흰 배경, 얇은 선, 한국어 라벨은 따옴표 안의 문구 그대로. static 변수는 준비 단계에서 기본값으로 만들어지고, 초기화 단계에서 초기화식의 값을 받는다.

    static 변수: 클래스에 하나뿐인 변수

    이제 static이 필요한 문제를 보자. 번호표를 발급하는 프로그램이다. 번호표 객체를 만들 때마다 1번, 2번, 3번 순서로 번호가 붙어야 한다. "다음에 발급할 번호"를 어딘가에 기억해야 하는데, 지금까지 배운 것만으로 쓰면 이렇게 된다.

    class Ticket {
    int nextNumber = 1;   // 다음에 발급할 번호
    int number;           // 이 번호표의 번호

    Ticket() {
        number = nextNumber;
        nextNumber++;
    }

    public static void main(String[] args) {
        Ticket a = new Ticket();
        Ticket b = new Ticket();
        Ticket c = new Ticket();
        System.out.println(a.number + " " + b.number + " " + c.number);   // 1 1 1
    }
}

    필요한 것은 어느 한 객체가 아니라 Ticket이라는 클래스에 속하는 변수, 객체를 몇 개 만들든 하나만 존재하는 변수다. 필드 선언에 static을 붙이면 그렇게 된다. JLS 8.3.1.1은 static으로 선언된 필드는 그 클래스의 인스턴스가 몇 개 만들어지든(0개여도) 정확히 하나만 존재한다고 정의하고, 이를 클래스 변수(class variable)라고 부른다. static이 없는 필드가 인스턴스 변수다.

    접근하는 표기

    static 변수는 Ticket.nextNumber처럼 클래스 이름으로 접근한다. 같은 클래스 안에서는 클래스 이름을 생략하고 nextNumber라고만 써도 된다. 문법상으로는 a.nextNumber처럼 참조 변수를 통해서도 접근할 수 있지만, 이렇게 쓰면 읽는 사람이 인스턴스 변수로 오해한다. 컴파일러는 이 식에서 a의 값이 아니라 타입만 사용한다. 그래서 다음 코드는 예외 없이 실행된다.

    Ticket t = null;
System.out.println(t.issuedCount());   // 0. NullPointerException이 나지 않는다
System.out.println(t.number);          // NullPointerException

    JLS의 예제 15.11.1-2도 null 참조로 static 변수에 접근해도 예외가 나지 않는다는 것을 보여 준다. static 멤버가 객체와 무관하다는 사실을 드러내는 동작이지만, 코드로서는 나쁜 표기다. javac에 -Xlint:static 옵션을 주면 이런 접근에 대해 "타입 이름으로 한정해야 한다"는 경고를 낸다. static 멤버는 항상 클래스 이름으로 접근한다.

    static 변수의 "사라지는 때"는 실질적으로 프로그램의 끝이다. JLS 12.7에 따르면 클래스는 그것을 정의한 클래스 로더가 가비지 컬렉터에 의해 회수될 수 있을 때에만 언로드될 수 있고, 부트스트랩 로더가 로딩한 클래스는 언로드되지 않는다. 클래스 로더가 살아 있는 동안에는 그 로더가 정의한 클래스의 static 변수도 계속 유지된다. 따라서 static 변수가 가리키는 객체는 프로그램이 접근할 수 있는, 곧 도달 가능한 객체로 남고 가비지 컬렉션의 대상이 되지 않는다. static 변수에 객체를 계속 쌓기만 하는 코드가 메모리를 조금씩 잠식하는 원인이 되는 이유다.

    Ticket 클래스의 static 변수 nextNumber는 클래스 쪽에 하나만 있고, 인스턴스 변수 number는 힙의 객체마다 따로 있으며, 세 객체의 생성자가 같은 nextNumber를 읽고 쓴다는 것을 보여 준다. 좌우 두 영역으로 나뉜 메모리 다이어그램. 왼쪽 영역은 옅은 파랑 배경의 큰 사각형, 머리 라벨 "메서드 영역 (클래스 단위)". 그 안에 카드 하나 "class Ticket", 카드 안에 강조된 주황색 상자 "static nextNumber = 4" 와 그 아래 회색 글씨 "메서드 코드". 오른쪽 영역은 옅은 초록 배경의 큰 사각형, 머리 라벨 "힙 (객체 단위)". 그 안에 세로로 나란한 객체 상자 세 개: "x001 Ticket" 안에 "number = 1", "x002 Ticket" 안에 "number = 2", "x003 Ticket" 안에 "number = 3". 세 객체 상자 각각에서 왼쪽의 주황색 nextNumber 상자로 향하는 얇은 화살표 세 개가 모이고, 화살표 묶음 옆에 라벨 "모든 객체가 같은 변수를 본다". 왼쪽 카드 아래에 작은 회색 주석 "객체가 0개여도 존재". 흰 바탕, 얇은 선, 한국어 라벨은 따옴표 안의 문구 그대로. static 변수는 객체 안에 들어 있지 않다. 객체의 개수와 관계없이 클래스에 하나만 있다.

    static 메서드: this가 없는 메서드

    Ticket의 issuedCount()에는 static이 붙어 있었다. 발급된 장수는 특정 번호표 한 장에 대한 질문이 아니라 클래스 전체에 대한 질문이다. 이 메서드가 인스턴스 메서드였다면 장수를 묻기 위해 아무 번호표나 하나 만들어야 했을 것이다. static을 붙인 메서드는 객체 없이 Ticket.issuedCount()로 호출한다. JLS 8.4.3.2는 static으로 선언된 메서드를 클래스 메서드(class method)라고 부르고, 클래스 메서드는 언제나 특정 객체에 대한 참조 없이 호출된다고 정의한다. static이 없는 메서드가 인스턴스 메서드이고, 인스턴스 메서드는 언제나 어떤 객체에 대해 호출되어 그 객체가 메서드 본문의 this가 된다.

    "객체에 대한 참조 없이 호출된다"는 말은 바이트코드에서 글자 그대로 확인된다. TicketMain에서 두 종류의 메서드를 호출하는 부분이다.

    인스턴스 멤버를 쓸 수 없는 이유

    여기까지 오면 static 메서드의 제약은 외울 규칙이 아니라 당연한 귀결이 된다. 인스턴스 메서드 안에서 number라고 쓰면 그것은 this.number의 줄임이고, 컴파일러는 aload_0으로 this를 올린 뒤 getfield로 그 객체의 필드를 읽는 코드를 만든다. static 메서드에는 this가 없다. 0번 지역 변수는 첫 번째 매개변수이거나 메서드 안에서 선언한 지역 변수이고, 둘 다 없으면 그 칸 자체가 없다. "어느 객체의 number인가"에 답할 재료가 프레임 안에 없으므로 컴파일러는 코드를 만들 수 없고, 컴파일 오류를 낸다.

    public class Bad {
    static int nextNumber = 1;
    int number;

    String label() { return "No." + number; }

    static void report() {
        System.out.println(number);        // 오류 (1)
        System.out.println(label());       // 오류 (2)
        System.out.println(this.number);   // 오류 (3)
    }
}
    (1) error: non-static variable number cannot be referenced from a static context
(2) error: non-static method label() cannot be referenced from a static context
(3) error: non-static variable this cannot be referenced from a static context

    오류 메시지의 "static context"는 JLS의 용어인 정적 문맥이다. JLS 8.1.3은 static 메서드, static 필드의 초기화식, static 초기화 블록 안의 코드가 정적 문맥에 있다고 정의하고, 정적 문맥의 목적을 "현재 인스턴스를 명시적으로든 암묵적으로든 참조해서는 안 되는 코드를 구분하는 것"이라고 설명한다. 그 안에서는 this와 super, 그리고 인스턴스 변수와 인스턴스 메서드를 한정 없이 쓰는 것이 금지된다. 4회에서 this(...)의 인자에 인스턴스 필드를 쓸 수 없었던 것도 그 자리가 정적 문맥이기 때문이었다.

    표의 세 번째 줄이 자주 잊힌다. static 메서드가 객체를 다룰 수 없는 것이 아니다. 없는 것은 "암묵적인 현재 객체"뿐이고, 객체의 참조를 매개변수나 지역 변수로 갖고 있으면 그 객체의 멤버에 얼마든지 접근할 수 있다.

    public class Greeter {
    String name = "kim";

    void greet() {
        System.out.println("hello " + name);
    }

    static boolean sameName(Greeter a, Greeter b) {
        return a.name.equals(b.name);      // 참조를 통한 접근: 가능
    }

    public static void main(String[] args) {
        Greeter g = new Greeter();
        g.greet();                                     // hello kim
        System.out.println(sameName(g, new Greeter())); // true
    }
}

    main도 static 메서드이므로 같은 클래스의 인스턴스 메서드 greet()를 그냥 greet();라고 호출하면 non-static method greet() cannot be referenced from a static context 오류가 난다. 위 코드처럼 객체를 만들어 그 참조로 호출해야 한다. 자바를 처음 배울 때 가장 먼저 만나는 오류 가운데 하나인데, 원인은 "main의 프레임에는 this가 없다"는 한 문장이다.

    실행할 메서드를 누가 정하는가

    앞의 표에서 "실행할 메서드의 결정" 줄은 뒤의 회차를 위한 복선이다. invokevirtual은 스택에서 꺼낸 참조가 실제로 가리키는 객체의 클래스를 보고 그 클래스에 맞는 메서드를 선택한다(JVMS의 invokevirtual 정의). 같은 호출 코드가 객체에 따라 다른 메서드를 실행할 수 있다는 뜻이고, 이것이 8회의 오버라이딩과 9회의 다형성을 가능하게 하는 장치다. invokestatic에는 객체가 관여하지 않는다. 호출할 메서드는 명령이 가리키는 클래스와 이름, 서술자로 정해지고 실행 중인 객체에 따라 달라지지 않는다. static 메서드가 오버라이딩의 대상이 되지 않는 이유가 여기에 있다.

    static을 쓰는 자리: 유틸리티, main, static import

    객체의 상태가 필요 없는 기능

    static 메서드가 어울리는 자리는 인스턴스 변수를 전혀 쓰지 않는 기능이다. 인자만으로 결과가 정해지는 계산이 대표적이다. Math.max(a, b)는 두 수만 있으면 답이 나오고, 기억해 둘 상태가 없다. 이런 메서드를 인스턴스 메서드로 만들면 호출할 때마다 의미 없는 객체를 만들어야 한다.

    public class Prices {
    private Prices() { }          // 객체를 만들 이유가 없으므로 생성을 막는다

    static int withTax(int price) {
        return price + price / 10;
    }

    public static void main(String[] args) {
        System.out.println(Prices.withTax(1000));   // 1100
    }
}

    static 메서드만 모아 둔 이런 클래스를 흔히 유틸리티 클래스라고 부른다. 인스턴스를 만들어도 쓸모가 없으므로 5회에서 본 private 생성자로 new를 막아 두는 것이 관례다.

    반대로, 메서드가 객체의 상태를 읽거나 바꾼다면 인스턴스 메서드여야 한다. 상태를 static 변수로 옮겨 놓고 static 메서드로 다루는 것은 객체 지향 이전의 전역 변수와 함수로 돌아가는 일이다. static 변수에 담을 만한 것은 클래스 전체에 대해 하나만 있어야 하는 값으로 한정하고, 바뀌는 값이라면 특히 신중해야 한다. 그 이유는 뒤의 함정 절에서 정리한다.

    main 메서드가 static인 이유

    프로그램의 시작점인 main은 왜 static일까. JLS 12.1.4는 Java 21 기준으로 main 메서드가 public, static, void로 선언되어야 하고 String 배열 타입의 매개변수를 가져야 한다고 정한다. JVM 쪽의 정의(JVMS 5.2)는 시작 과정을 이렇게 적는다. JVM은 초기 클래스를 만들고, 링크하고, 초기화한 다음, 그 클래스의 public static 메서드 void main(String[])을 호출한다.

    이 순서에 인스턴스를 만드는 단계가 없다는 점이 요점이다. 프로그램이 시작되는 순간 힙에는 개발자가 만든 객체가 하나도 없다. main이 인스턴스 메서드라면 JVM은 호출에 앞서 그 클래스의 객체를 만들어야 하고, 그러려면 어느 생성자를 어떤 인자로 호출할지를 정해야 한다. static 메서드는 클래스만 초기화되면 호출할 수 있으므로 이런 결정이 필요 없다. 앞에서 추적한 FrameMain의 첫 프레임에서 0번 지역 변수가 this가 아니라 args였던 것을 떠올리면 된다.

    버전에 따른 차이가 있다. JDK 25에서 확정된 JEP 512는 static이 아닌 인스턴스 main 메서드로도 프로그램을 시작할 수 있게 했다(JDK 21에서는 JEP 445로 미리 보기 기능이었다). 이 경우 JEP의 설명대로 클래스에는 매개변수 없는 non-private 생성자가 있어야 하고, 실행기(launcher)가 그 생성자로 객체를 먼저 만든 뒤 그 객체의 main을 호출한다. 인스턴스 메서드를 호출하려면 객체가 먼저 있어야 한다는 원리는 그대로다. 이 강좌의 기준인 Java 21의 정식 기능으로는 public static void main(String[] args)가 시작점이다.

    static import

    5회에서 미뤄 둔 import static은 다른 클래스의 static 멤버를 클래스 이름 없이 쓰게 해 주는 선언이다. JLS 7.5.3의 단일 정적 import(import static java.lang.Math.max;)는 이름 하나를, 7.5.4의 필요 시 정적 import(import static java.lang.Math.*;)는 그 클래스의 접근 가능한 static 멤버 전부를 단순 이름으로 쓸 수 있게 한다.

    import static java.lang.Math.PI;
import static java.lang.Math.max;

public class Geo {
    public static void main(String[] args) {
        double r = max(2.0, 3.0);
        System.out.println(PI * r * r);   // 28.274333882308138
    }
}

    일반 import와 마찬가지로 이것도 컴파일 타임의 이름 해석일 뿐이다. 컴파일된 코드에서 max(2.0, 3.0)은 Math.max(2.0, 3.0)이라고 썼을 때와 똑같이 invokestatic java/lang/Math.max:(DD)D 명령이 된다. PI는 상수 변수여서 getstatic조차 없이 값 3.141592653589793이 코드에 직접 들어간다. static import를 쓸지 말지는 읽기 편한가의 문제다. 한 파일에서 같은 클래스의 static 멤버를 반복해서 쓸 때는 코드가 간결해지지만, 남용하면 max가 이 클래스의 메서드인지 다른 클래스에서 온 것인지 한눈에 알기 어려워진다.

    흔한 오해와 함정

    "메서드가 끝나면 그 안에서 만든 객체도 사라진다"

    사라지는 것은 프레임과 그 안의 지역 변수, 곧 참조다. 객체는 힙에 있고 메서드와 수명이 묶여 있지 않다. 그 객체를 가리키는 참조가 반환값으로 호출자에게 건너갔거나, 다른 객체의 필드나 static 변수에 저장되었다면 객체는 계속 도달 가능하다. 어디에도 남지 않았을 때 비로소 회수 대상이 되고, 그때도 즉시 회수되는 것이 아니다.

    "클래스는 프로그램이 시작될 때 전부 올라온다"

    JLS가 정한 초기화 시점은 "처음 쓰이기 직전"이다. 프로그램에 클래스가 천 개 있어도 한 번도 쓰이지 않은 클래스의 static 초기화 블록은 실행되지 않는다. static 초기화 블록에 넣어 둔 코드가 "프로그램 시작 시 실행될 것"이라고 가정하면 안 된다. 그 클래스의 인스턴스 생성, static 메서드 호출, 상수가 아닌 static 변수 접근 가운데 하나가 처음 일어날 때 실행된다.

    "static 변수는 메서드 영역에 저장된다"

    명세의 모델로서는 맞는 그림이고, HotSpot의 물리적 배치에 대한 주장으로서는 맞지 않는다는 것을 앞에서 봤다. 면접이나 문서에서 이 문장을 만나면 어느 층의 이야기인지 구분해서 듣는다. "JDK 8에서 PermGen이 메타스페이스로 바뀌었다"는 말도 정확히는 클래스 메타데이터의 저장 위치가 네이티브 메모리로 옮겨졌다는 뜻이고, static 변수와 인터닝된 문자열은 자바 힙에 있다(JEP 122).

    static 변수는 모든 스레드가 공유한다

    static 변수는 클래스에 하나뿐이고 스레드별로 복사되지 않는다. 여러 스레드가 같은 static 변수를 동시에 읽고 쓰면, nextNumber++처럼 한 줄로 보이는 코드도 "읽기, 더하기, 쓰기"의 여러 명령(앞의 바이트코드에서 getstatic, iadd, putstatic)으로 나뉘어 실행되므로 서로의 결과를 덮어쓸 수 있다. 이 회차의 Ticket은 스레드가 하나일 때만 올바른 코드다. 여러 스레드에서 안전하게 만드는 방법은 고급 1편의 주제다. 스택의 지역 변수는 스레드마다 따로 있으므로 이 문제에서 자유롭다.

    바뀌는 static 상태가 만드는 문제

    값이 바뀌는 static 변수는 프로그램 어디서든 접근할 수 있는 전역 상태가 된다. 문제는 세 가지로 나타난다. 첫째, 누가 언제 값을 바꿨는지 추적하기 어렵다. 접근 제어자로 범위를 좁힐 수는 있지만 객체의 필드처럼 "이 객체의 것"으로 한정되지 않는다. 둘째, 한번 바뀐 값이 프로그램이 끝날 때까지 남으므로, 같은 클래스를 쓰는 코드들이 서로의 실행에 영향을 준다. 테스트를 연달아 실행할 때 앞 테스트가 남긴 static 상태 때문에 뒤 테스트가 실패하는 일이 전형적이다. 셋째, static 변수가 가리키는 객체는 회수되지 않으므로, static 변수에 객체를 쌓아 두는 구조는 메모리 사용량이 줄지 않는 원인이 된다. 변하지 않는 값(상수)에는 이런 문제가 없다. 그래서 static은 상수와 상태 없는 유틸리티 메서드에 주로 쓰고, 공유해야 하는 가변 상태는 객체로 만들어 필요한 곳에 전달하는 쪽을 먼저 검토한다.

    다른 주제와의 연결

    다음 7회의 final에서는 static final로 선언하는 상수를 다룬다. 이 회차에서 본 상수 변수의 성질, 곧 컴파일러가 값을 사용처에 직접 넣고 그 접근이 클래스 초기화를 일으키지 않는다는 점이 거기서 다시 쓰인다. 8회의 상속에서는 하위 클래스가 초기화되기 전에 상위 클래스가 먼저 초기화된다는 JLS 12.4.1의 규칙과, 객체 하나의 힙 메모리에 부모와 자식의 인스턴스 변수가 함께 들어 있는 구조를 본다. 9회의 다형성은 invokevirtual이 실행 중인 객체의 클래스를 보고 메서드를 고르는 동작 위에 서 있다.

    중급 1편에서는 클래스를 나타내는 Class 객체와 문자열 상수 풀을 다루고, 예외의 스택 트레이스를 읽는다. 스택 트레이스의 각 줄은 예외가 발생한 순간 JVM 스택에 쌓여 있던 프레임을 위에서부터 적은 것이므로, 이 회차의 단계별 추적이 그대로 읽는 법이 된다.

    고급 1편의 멀티스레드는 이 회차의 "스레드마다 있는 영역"과 "공유하는 영역"의 구분에서 출발한다. 스레드를 하나 만들면 그 스레드의 JVM 스택과 pc 레지스터가 새로 생기고, 힙과 메서드 영역은 기존 스레드들과 함께 쓴다. 동시성 문제는 전부 공유되는 쪽, 곧 객체의 필드와 static 변수에서 일어난다.

    스프링에서는 "애플리케이션 전체에 하나만 있어야 하는 것"을 static으로 만들지 않는다. 스프링 프레임워크 문서에 따르면 빈의 기본 스코프는 싱글톤이어서, 컨테이너가 빈 정의 하나에 대해 객체 인스턴스 하나를 만들어 관리하고 필요한 곳에 주입한다. 하나만 존재한다는 성질은 얻으면서, static 변수와 달리 일반 객체이므로 생성자로 의존관계를 받을 수 있고 다른 구현으로 바꿔 끼울 수 있다. 다만 하나의 객체를 여러 스레드가 함께 쓴다는 점은 static 변수와 같아서, 그 객체의 필드에 요청마다 달라지는 값을 두면 안 된다는 주의가 따라온다. 이 회차의 "공유되는 것과 스레드마다 있는 것"의 구분이 그 이유를 설명한다.
    런타임 데이터 영역 (JVMS 2.5)
    스레드마다 있는 pc 레지스터·JVM 스택·네이티브 메서드 스택과, 모든 스레드가 공유하는 힙·메서드 영역(그 안의 런타임 상수 풀)으로 이루어진다.
    프레임
    메서드 호출 한 번의 작업 공간. 지역 변수 배열, 피연산자 스택, 런타임 상수 풀 참조를 갖는다. 호출 때 만들어지고 반환 때 버려진다.
    호출과 반환
    호출 시 인자가 피연산자 스택에서 새 프레임의 지역 변수로 복사된다. 반환 시 프레임이 버려지고 반환값이 호출자의 피연산자 스택에 올라간다.
    스택과 힙
    지역 변수와 참조는 프레임에, 객체는 힙에 있다. 프레임은 반환 즉시 사라지고, 객체는 도달할 수 없게 된 뒤 가비지 컬렉터가 회수한다.
    로딩·링크·초기화
    클래스는 로딩되고, 링크(검증·준비·해석)되고, 처음 쓰이기 직전에 한 번 초기화된다. 준비 단계에서 static 변수가 기본값으로 만들어지고 초기화 단계에서 초기화식이 실행된다.
    static 변수(클래스 변수)
    객체의 수와 관계없이 클래스에 하나만 있는 변수. getstatic/putstatic으로 객체 참조 없이 접근하며, 모든 스레드가 공유한다.
    명세와 구현
    명세의 모델에서 static 변수는 클래스 단위에 속한다. HotSpot(JDK 8 이후)에서 클래스 메타데이터는 메타스페이스에, static 변수의 값은 자바 힙의 Class 객체 안에 있다.
    static 메서드(클래스 메서드)
    invokestatic으로 객체 없이 호출된다. 프레임의 0번 지역 변수에 this가 전달되지 않으므로 인스턴스 멤버를 단순 이름으로 쓸 수 없다.
    main과 static import
    JVM은 초기 클래스를 초기화한 뒤 객체 없이 main을 호출하므로 main은 static이다. import static은 static 멤버를 단순 이름으로 쓰게 하는 컴파일 타임 이름 해석이다.

    운영 중인 서비스의 메모리 문제를 볼 때 이 회차의 구분이 첫 번째 분류 기준이 된다. StackOverflowError는 한 스레드의 호출 깊이 문제이므로 스택 트레이스에서 반복되는 프레임 패턴을 찾는다. 서로를 호출하는 두 메서드, 종료 조건이 틀린 재귀, 양방향으로 참조하는 객체를 따라가는 출력 메서드가 흔한 원인이다. 힙의 OutOfMemoryError는 도달 가능한 객체가 쌓이는 문제이므로 "이 객체들을 붙잡고 있는 참조의 출발점이 어디인가"를 찾는다. 출발점은 결국 실행 중인 스레드의 프레임이거나 static 변수다. 클래스 메타데이터 쪽에서 나는 메모리 오류는 로딩되는 클래스의 수가 계속 늘어나는 경우이고, HotSpot에서는 힙 크기 설정과 별개로 메타스페이스 설정을 본다. 어느 영역의 문제인지를 오류 메시지에서 먼저 가려야 엉뚱한 옵션을 조정하지 않는다.

    static을 쓸지에 대한 판단은 "그 상태가 바뀌는가"와 "누가 공유하는가"로 갈린다. 변하지 않는 값과 상태 없는 계산은 static으로 두어도 문제가 없다. 바뀌는 상태를 static에 두면 접근 경로가 프로그램 전체로 열리고, 수명이 프로세스와 같아지며, 모든 스레드가 공유하게 된다. 캐시나 등록소처럼 정말로 프로세스에 하나여야 하는 것도 static 필드 대신 객체로 만들어 생성자로 전달하면, 테스트에서 새 인스턴스로 갈아 끼울 수 있고 수명과 공유 범위를 코드에서 통제할 수 있다. 프레임워크의 싱글톤 관리가 이 방식을 대신해 준다.

    static 초기화 블록에 무거운 작업이나 실패할 수 있는 작업을 넣는 것은 비용 대비 위험이 크다. 초기화는 처음 쓰이는 시점에 일어나므로 실행 시점을 예측하기 어렵고, 실패하면 그 클래스는 프로세스가 끝날 때까지 쓸 수 없게 되며 이후의 오류는 원인과 동떨어진 NoClassDefFoundError로 나타난다. 파일이나 네트워크에서 설정을 읽는 일처럼 실패 가능성이 있는 초기화는 명시적으로 호출되는 메서드나 객체의 생성 과정으로 옮기고, 실패를 호출한 쪽에서 다룰 수 있게 하는 편이 낫다.

     JVMS 2.5가 정의한 런타임 데이터 영역 가운데 스레드마다 따로 만들어지는 것만 모은 것은? 힙, 메서드 영역 JVM 스택, 힙 pc 레지스터, JVM 스택 메서드 영역, 런타임 상수 풀 pc 레지스터와 JVM 스택은 스레드가 만들어질 때 그 스레드를 위해 만들어지고 스레드가 끝나면 없어진다(네이티브 메서드 스택도 제공되는 경우 보통 스레드별이다). 힙과 메서드 영역은 JVM이 시작될 때 만들어져 모든 스레드가 공유하고, 런타임 상수 풀은 클래스마다 있으며 메서드 영역에서 할당된다. 메서드 A가 static 메서드 B를 호출하고 B가 int 값을 반환했다. JVM 스택에서 일어나는 일로 옳은 것은? B의 프레임은 A가 끝날 때까지 스택에 남아 있다가 A의 프레임과 함께 버려진다 호출 시 인자가 A의 피연산자 스택에서 B 프레임의 지역 변수로 복사되고, 반환 시 B의 프레임이 버려지며 반환값이 A의 피연산자 스택에 올라간다 호출 시 A의 지역 변수 배열이 B와 공유되므로 B가 매개변수를 바꾸면 A의 변수도 바뀐다 반환값은 힙에 저장되고 A는 그 참조를 받는다 JVMS의 호출 명령 정의와 2.6.4에 따르면 인자는 피연산자 스택에서 꺼내져 새 프레임의 지역 변수가 되고, 정상 반환 시 현재 프레임이 버려지면서 반환값이 호출자 프레임의 피연산자 스택에 올라간다. 프레임은 호출이 끝나는 즉시 없어지고, 프레임끼리 지역 변수를 공유하지 않는다. 기본형 반환값은 힙을 거치지 않는다. static 메서드 안에서 인스턴스 변수 number를 단순 이름으로 쓰면 컴파일 오류가 나는 근본 이유는? static 메서드는 메서드 영역에 있고 인스턴스 변수는 힙에 있어서, 서로 다른 영역 사이에는 접근이 금지되어 있다 static 메서드가 실행될 때는 아직 어떤 객체도 만들어져 있지 않기 때문이다 인스턴스 변수는 private이 기본이어서 static 메서드에서 보이지 않는다 static 메서드는 대상 객체의 참조 없이 호출되어 프레임에 this가 없으므로, 어느 객체의 number인지 정할 수 없다 인스턴스 변수의 단순 이름은 this.number의 줄임이다. invokestatic은 대상 객체의 참조를 전달하지 않으므로 static 메서드의 프레임 0번 지역 변수에는 this가 없다. 영역이 달라서가 아니다(인스턴스 메서드의 코드도 메서드 영역에 있다). 객체가 이미 많이 만들어져 있어도 마찬가지이며, 참조를 매개변수로 받아 t.number로 쓰는 것은 허용된다. 접근 제어자와는 관계가 없다. 클래스 Registry에 static final int LIMIT = 100;, static int created = 0;, 그리고 메시지를 출력하는 static 초기화 블록이 있다. 다음 가운데 Registry의 static 초기화 블록을 실행시키지 않는 것은? Registry r = null;로 변수를 선언하고, Registry.LIMIT을 읽는다 new Registry()로 인스턴스를 만든다 Registry.created를 읽는다 Registry에 선언된 static 메서드를 호출한다 JLS 12.4.1에서 초기화를 일으키는 것은 인스턴스 생성, static 메서드 호출, static 필드 대입, 상수 변수가 아닌 static 필드의 사용이다. 변수 선언은 여기에 없고, LIMIT은 상수 변수여서 컴파일러가 값을 사용처에 직접 넣으므로 실행 중에 Registry에 접근하지 않는다. created는 final이 아니므로 읽으면 초기화가 일어난다. "static 변수는 메서드 영역에 저장된다"는 설명에 대한 평가로 가장 정확한 것은? JVMS가 static 변수의 물리적 저장 위치를 메서드 영역으로 명시하므로 모든 JVM에서 참이다 static 변수가 클래스 단위로 하나 존재한다는 명세의 모델로는 유효하지만, JDK 8 이후의 HotSpot에서 값이 실제로 놓이는 곳은 자바 힙의 Class 객체다 JDK 8부터 static 변수는 메타스페이스에 저장되므로 힙 크기와 무관하다 static 변수는 스레드마다 스택에 복사되므로 메서드 영역과 관계가 없다 JVMS는 런타임 데이터 영역의 메모리 배치를 구현에 맡기며, 메서드 영역의 위치도 강제하지 않는다. 명세가 정하는 것은 static 변수가 클래스마다 하나이고 클래스가 준비될 때 만들어진다는 점이다. JEP 122는 클래스 메타데이터를 네이티브 메모리로, static 변수와 인터닝된 문자열을 자바 힙으로 두었고, HotSpot 소스는 java.lang.Class 인스턴스가 그 클래스의 static 필드를 담는다고 설명한다. static 변수는 스레드마다 복사되지 않고 공유된다.
    런타임 데이터 영역(run-time data areas)
    JVM이 프로그램 실행 중에 쓰는 메모리 영역들. JVMS 2.5가 pc 레지스터, JVM 스택, 힙, 메서드 영역, 런타임 상수 풀, 네이티브 메서드 스택을 정의한다.
    프레임(frame)
    메서드 호출 한 번마다 JVM 스택에 만들어지는 구조. 지역 변수 배열, 피연산자 스택, 현재 클래스의 런타임 상수 풀에 대한 참조를 갖는다.
    피연산자 스택(operand stack)
    프레임 안에 있는 계산용 후입선출 스택. 명령이 쓸 값을 올리고 꺼내며, 인자 전달과 반환값 수신에도 쓰인다.
    메서드 영역(method area)
    클래스별 구조(런타임 상수 풀, 필드와 메서드 데이터, 메서드와 생성자의 코드)를 담는 공유 영역. 위치는 명세가 정하지 않는다.
    런타임 상수 풀(run-time constant pool)
    클래스 파일의 상수 풀이 실행 중의 JVM에 올라온 형태. 상수와 심벌릭 참조를 담고 메서드 영역에서 할당된다.
    클래스 초기화(class initialization)
    static 변수의 초기화식과 static 초기화 블록을 소스 순서대로 실행하는 것. 클래스가 처음 쓰이기 직전에 한 번 일어나며 메서드의 실행으로 구현된다.
    클래스 변수(class variable, static 변수)
    static으로 선언한 필드. 인스턴스의 수와 관계없이 클래스에 하나만 존재한다.
    정적 문맥(static context)
    static 메서드, static 필드의 초기화식, static 초기화 블록 등 현재 인스턴스를 참조할 수 없는 코드 위치. this와 인스턴스 멤버의 단순 이름 사용이 금지된다.
    메타스페이스(Metaspace)
    JDK 8 이후의 HotSpot이 클래스 메타데이터를 저장하는 네이티브 메모리 영역. 영구 세대(PermGen)를 대체했다.
    도달 가능성(reachability)
    살아 있는 스레드에서 앞으로의 계산으로 객체에 접근할 수 있는가. 도달할 수 없는 객체는 가비지 컬렉터의 회수 대상이다.
