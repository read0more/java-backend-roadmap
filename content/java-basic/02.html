    같은 대입문, 다른 결과

    01회에서 클래스로 새 타입을 만들고, 변수에는 객체가 아니라 참조값이 들어간다는 것을 보았다. 이번 회차는 그 사실 하나에서 따라 나오는 결과들을 차례로 확인한다. 출발점은 다음 프로그램이다. Counter는 int 필드 하나만 가진 클래스다.

    public class Counter {
    int count;
}
    public class AssignMain {
    public static void main(String[] args) {
        int a = 10;
        int b = a;
        b = 20;
        System.out.println("a = " + a + ", b = " + b);

        Counter c1 = new Counter();
        c1.count = 10;
        Counter c2 = c1;
        c2.count = 20;
        System.out.println("c1.count = " + c1.count + ", c2.count = " + c2.count);
    }
}
    a = 10, b = 20
c1.count = 20, c2.count = 20

    앞의 세 줄과 뒤의 네 줄은 모양이 같다. 값을 하나 만들고, 다른 변수에 대입하고, 그 변수 쪽을 20으로 바꾼다. 그런데 int에서는 원래 변수 a가 그대로이고, Counter에서는 원래 변수 c1로 읽은 값까지 바뀌었다. 대입 연산자 =가 타입에 따라 다르게 동작하는 것처럼 보인다. 결론부터 말하면 =가 하는 일은 두 경우 모두 똑같다. 달라지는 것은 변수에 들어 있던 값의 종류다.

    두 종류의 타입, 두 종류의 값

    JLS §4.1은 자바의 타입을 두 종류로 나눈다. 기본형(primitive type)과 참조형(reference type)이다. 그리고 그에 대응해 "변수에 저장되고, 인자로 전달되고, 메서드가 반환하고, 연산의 대상이 되는" 값도 두 종류라고 말한다. 기본형 값(primitive value)과 참조값(reference value)이다. JVM도 같은 구분을 쓴다(JVMS §2.2). 자바 프로그램에서 변수에 들어갈 수 있는 것은 이 둘뿐이고, 객체 자체가 변수에 들어가는 일은 없다.

    구분기본형참조형
    변수에 저장되는 것값 자체(정수, 실수, 문자, 논리값)객체를 가리키는 참조값, 또는 null
    종류언어가 정한 8개(byte, short, int, long, char, float, double, boolean)클래스, 배열, 인터페이스 등. 프로그래머가 계속 새로 정의한다
    값의 크기명세가 정한다(int는 32비트 등)명세가 정하지 않는다(JVM 구현의 몫)
    값으로 할 수 있는 일산술, 비교, 논리 연산 등필드 접근(.), 메서드 호출, 배열 인덱스([]), ==·!= 비교 등
    필드일 때의 기본값0, falsenull

    기본형 변수에는 값이 직접 들어 있으므로 그 값으로 곧바로 계산할 수 있다. a + b는 두 변수에 든 정수를 더한다. 참조형 변수에 들어 있는 것은 "어느 객체인가"를 나타내는 값이어서 그 자체로는 계산할 것이 없다. Counter sum = c1 + c2;라고 쓰면 컴파일러가 bad operand types for binary operator '+'라는 오류를 낸다. 참조값으로 할 수 있는 일은 그것을 따라가는 것(필드 접근, 메서드 호출, 배열 인덱스)과 두 참조가 같은지 비교하는 것 정도다. c1.count + c2.count는 가능한데, 참조를 따라가서 꺼낸 count가 기본형 int 값이기 때문이다.

    타입 이름만 보고 구분하는 요령도 있다. 기본형 여덟 개는 모두 소문자로 시작하는 예약어이고, 그 밖의 타입은 전부 참조형이다. String도 대문자로 시작하는 클래스이므로 참조형이다. 다만 String은 큰따옴표 리터럴과 + 연결을 언어가 특별히 지원해서(JLS §4.3.1이 참조에 쓸 수 있는 연산으로 문자열 연결을 따로 든다) 기본형처럼 느껴질 뿐이다. String의 내부는 중급 1편에서 다룬다.

    JVM 명령어에도 이 구분이 그대로 드러난다. JVMS §2.2의 설명대로 JVM은 값마다 타입 표시를 붙여 둘 필요가 없도록, 다루는 타입마다 다른 명령을 쓴다. 지역 변수의 값을 피연산자 스택에 올리는 명령이 int용은 iload, 참조용은 aload인 식이다. 이름의 첫 글자 i와 a가 타입을 나타낸다. 01회에서 본 astore, aaload의 a가 바로 참조를 뜻했다.

    변수 대입: 복사되는 것은 언제나 변수에 든 값이다

    대입의 규칙은 하나다. 오른쪽 식을 계산한 값을 왼쪽 변수의 칸에 복사한다. 이 규칙을 두 경우에 그대로 적용해 보자. 먼저 기본형이다.

    int a = 10;          int b = a;           b = 20;

 a [ 10 ]             a [ 10 ]             a [ 10 ]
                      b [ 10 ]  (복사)      b [ 20 ]

    int b = a;는 a의 칸에 든 값 10을 b의 칸에 복사한다. 그 뒤로 두 칸은 아무 관계가 없다. b = 20;은 b의 칸만 바꾼다. JLS §4.2에는 이를 한 문장으로 못박은 구절이 있다. "기본형 값은 다른 기본형 값과 상태를 공유하지 않는다."

    이제 참조형이다. 같은 규칙을 적용하되, 변수의 칸에 든 값이 참조값이라는 점만 다르다.

    Counter c1 = new Counter();     Counter c2 = c1;                c2.count = 20;
c1.count = 10;

 c1 [참조]---> Counter{count=10}  c1 [참조]---> Counter{count=10}   c1 [참조]---> Counter{count=20}
                                  c2 [참조]-----^   (참조값 복사)    c2 [참조]-----^

    Counter c2 = c1;은 c1의 칸에 든 값을 c2의 칸에 복사한다. 그 값이 참조값이므로 복사된 것도 참조값이다. 객체는 복사되지 않았고 new도 실행되지 않았으니 힙의 Counter 인스턴스는 여전히 하나다. 두 변수가 같은 객체를 가리키게 되었을 뿐이다. 이렇게 한 객체를 둘 이상의 변수가 가리키는 상태를 별칭(aliasing)이라고 부른다. c2.count = 20;은 c2의 참조를 따라가 그 객체의 count를 20으로 바꾼다. c1.count는 c1의 참조를 따라가 같은 객체의 같은 필드를 읽으므로 20이다. JLS §4.3.1에는 이 프로그램과 구조가 같은 예제(Example 4.3.1-2)가 실려 있고, 결과를 "두 식이 단 하나의 객체에 있는 같은 인스턴스 변수를 가리키기 때문"이라고 설명한다.

    두 대입 모두 변수 칸의 내용을 복사하지만, 기본형은 독립된 값 두 개가 되고 참조형은 한 객체를 가리키는 화살표 두 개가 된다는 대비를 보여 준다. 깔끔한 기술 교재풍 비교 그림. 화면을 좌우 두 패널로 나눈다. 왼쪽 패널 제목은 "기본형: int b = a", 오른쪽 패널 제목은 "참조형: Counter c2 = c1". 왼쪽 패널에는 작은 상자 두 개를 위아래로 두고 위 상자 옆에 "a", 아래 상자 옆에 "b"라고 적으며 두 상자 안에는 각각 숫자 "10"을 적는다. 위 상자에서 아래 상자로 점선 화살표를 그리고 "값 10을 복사"라고 적는다. 오른쪽 패널에는 왼편에 작은 상자 두 개를 위아래로 두고 "c1", "c2"라고 적으며, 오른편에 둥근 모서리 상자 하나를 두고 제목 "Counter 인스턴스", 안쪽에 "count = 10"이라고 적는다. "c1" 상자와 "c2" 상자에서 각각 실선 화살표가 같은 Counter 인스턴스 상자로 향한다. "c1"에서 "c2"로 점선 화살표를 그리고 "참조값을 복사"라고 적는다. 오른쪽 패널 아래에 한 줄 "객체는 하나, 가리키는 변수는 둘"을 적는다. 흰 배경, 절제된 두 가지 색, 또렷한 선과 글자. 대입은 언제나 변수 칸의 내용을 복사한다. 기본형은 값이, 참조형은 참조값이 복사된다.

    객체를 고치는 것과 변수를 바꾸는 것

    참조형 변수가 등장하는 대입문은 두 가지로 나뉜다. 이 둘을 구별하는 것이 이번 회차 전체의 핵심 기술이다. 다음 프로그램은 앞의 것과 한 군데만 다르다. c2.count = …로 가기 전에 c2에 새 객체를 대입한다.

    일상에서 가져온 비유공유 문서의 링크

    문서 링크를 동료에게 보내면 문서가 복사되는 것이 아니라 링크 문자열이 복사된다. 동료가 그 링크로 들어가 문서를 고치면 내 링크로 열어도 고친 내용이 보인다(객체를 고치는 것). 동료가 자기 메모장에 적어 둔 링크를 지우고 다른 문서의 링크로 바꿔 적어도 내 메모장의 링크와 원래 문서는 그대로다(변수를 바꾸는 것). 비유가 깨지는 지점은 숫자 같은 기본형이다. 기본형에는 "따라가서 고칠 곳"이 없고, 값 그 자체가 오간다. 또 링크는 누구나 문자열로 읽고 조작할 수 있지만 자바의 참조값은 프로그램이 그 내용을 들여다볼 수 없다.

    메서드 호출: 인자 전달도 대입이다

    메서드를 호출할 때 인자가 매개변수로 넘어가는 과정에도 새 규칙은 없다. JLS §8.4.1은 "메서드가 호출되면 실제 인자 식의 값이, 새로 만들어진 매개변수 변수를 초기화한다"고 정한다. 매개변수는 호출될 때마다 새로 만들어지는 변수이고, 인자의 값이 거기에 대입된다. 그러니 앞에서 본 대입의 규칙이 그대로 적용된다. 값이 복사되고, 그 값이 기본형 값이냐 참조값이냐에 따라 결과가 갈린다.

    public class CallMain {
    public static void main(String[] args) {
        int n = 10;
        addTen(n);
        System.out.println("n = " + n);

        Counter counter = new Counter();
        counter.count = 10;
        addTenTo(counter);
        System.out.println("counter.count = " + counter.count);

        replace(counter);
        System.out.println("counter.count = " + counter.count);
    }

    static void addTen(int value) {
        value = value + 10;
    }

    static void addTenTo(Counter target) {
        target.count = target.count + 10;
    }

    static void replace(Counter target) {
        target = new Counter();
        target.count = 999;
    }
}
    n = 10
counter.count = 20
counter.count = 20

    세 호출을 하나씩 추적한다. addTen(n)이 호출되면 addTen을 위한 스택 프레임이 새로 만들어지고, 그 안의 매개변수 value에 n의 값 10이 복사된다. value = value + 10;은 addTen 프레임 안의 value를 20으로 바꾼다. 메서드가 끝나면 프레임이 사라지고 value도 함께 사라진다. main의 n은 한 번도 건드려지지 않았으므로 10이다.

    addTenTo(counter)에서는 매개변수 target에 counter의 값, 곧 참조값이 복사된다. 이 순간 main 프레임의 counter와 addTenTo 프레임의 target이 같은 객체를 가리킨다. target.count = target.count + 10;은 왼쪽에 점이 있는 대입이다. 참조를 따라가 힙의 객체를 고친다. 메서드가 끝나 target이 사라져도 객체는 힙에 남아 있고, main이 counter로 그 객체를 읽으면 20이 보인다.

    addTenTo(counter) 실행 중

  스택                                   힙
  +--[ addTenTo 프레임 ]--------+
  | target  = (참조값) --------------+
  +----------------------------+     |
  +--[ main 프레임 ]------------+     +--->  Counter 인스턴스 { count = 10 -> 20 }
  | n       = 10               |     |
  | counter = (참조값) --------------+
  +----------------------------+

  메서드가 끝나면 addTenTo 프레임과 target은 사라진다. 객체와 counter는 남는다.
    인자로 참조값이 복사되어, 서로 다른 스택 프레임에 있는 두 변수가 힙의 한 객체를 가리킨다는 것을 보여 준다. 깔끔한 기술 교재풍 메모리 구조도. 왼쪽 영역 라벨 "스택", 오른쪽 영역 라벨 "힙". 왼쪽에는 프레임 상자 두 개를 위아래로 쌓는다. 위 프레임의 제목은 "addTenTo() 프레임"이고 안에 칸 하나 "target"이 있다. 아래 프레임의 제목은 "main() 프레임"이고 안에 칸 두 개 "n = 10", "counter"가 있다. 오른쪽 힙 영역에는 둥근 모서리 상자 하나를 두고 제목 "Counter 인스턴스", 안쪽에 "count = 20"이라고 적는다. "target" 칸과 "counter" 칸에서 각각 화살표가 나와 같은 Counter 인스턴스 상자에 닿는다. "counter" 칸에서 "target" 칸으로 가는 점선 화살표를 그리고 "호출할 때 참조값 복사"라고 적는다. 위 프레임 옆에 작은 글씨로 "메서드가 끝나면 사라진다"라고 적는다. 흰 배경, 스택은 푸른 계열, 힙은 주황 계열, 또렷한 선과 글자. 인자 전달은 참조값의 복사다. 호출된 메서드는 같은 객체에 닿을 수 있지만, 호출한 쪽의 변수 칸에는 닿을 수 없다.

    replace(counter)도 시작은 같다. target에 참조값이 복사되어 두 변수가 같은 객체를 가리킨다. 그런데 target = new Counter();는 왼쪽이 변수 이름뿐인 대입이다. replace 프레임 안의 target 칸이 새 객체를 가리키도록 바뀔 뿐, main의 counter 칸에는 아무 일도 일어나지 않는다. 이어지는 target.count = 999;는 새 객체를 고친다. 메서드가 끝나면 target이 사라지고, 새 객체는 가리키는 변수가 하나도 없게 된다. main의 counter는 여전히 원래 객체를 가리키므로 출력은 20이다.

    JVM에서 일어나는 일

    호출되는 쪽 세 메서드의 바이트코드는 다음과 같다.

   1: bipush        10
   3: iadd
   4: istore_0
   5: return

  11: return

    호출하는 쪽 main에서 addTen(n)은 iload_1, invokestatic 두 명령이다. n의 값을 자기 피연산자 스택에 올리고 호출한다. JVMS는 invokestatic을 이렇게 설명한다. 인자 값들을 호출자의 피연산자 스택에서 꺼내고, 호출될 메서드를 위한 새 프레임을 만들고, 꺼낸 인자 값들을 새 프레임의 지역 변수 0번부터 차례로 넣는다. 그래서 addTen 안에서 value는 지역 변수 0번이다. istore_0은 addTen 자신의 프레임에 있는 0번 칸을 덮어쓸 뿐이다. JVM 명령어 중에는 다른 프레임의 지역 변수 칸을 가리키거나 고치는 명령이 없다. 호출된 메서드가 호출한 쪽의 변수를 바꿀 방법이 구조적으로 없는 것이다.

    addTenTo는 aload_0으로 자기 0번 칸의 참조를 올린 뒤 getfield와 putfield로 힙의 객체를 읽고 쓴다. 참조값은 복사본이지만 그것이 가리키는 객체는 호출한 쪽과 공유하는 바로 그 객체다. replace는 astore_0으로 자기 0번 칸을 새 참조로 덮어쓴 다음 그 새 객체에 putfield를 실행한다. 소스 코드에서 구별한 "변수를 바꾸는 것(astore)"과 "객체를 고치는 것(putfield)"이 명령 수준에서도 그대로 갈린다.

    자바의 인자 전달은 언제나 값에 의한 전달이다

    이 방식을 값에 의한 전달(pass by value)이라고 한다. 참조형을 넘길 때 호출된 쪽이 객체를 고칠 수 있다는 이유로 "참조에 의한 전달"이라고 부르는 경우가 있는데, 정확하지 않다. 전달되는 것은 참조값이라는 값이고, 그 값이 복사된다. 참조에 의한 전달을 지원하는 언어라면 호출된 함수가 호출한 쪽의 변수 자체를 다른 것으로 바꿀 수 있어야 한다. 자바에서 그것이 불가능하다는 것은 두 변수를 맞바꾸는 메서드를 만들어 보면 확인된다.

    public class SwapMain {
    public static void main(String[] args) {
        Counter a = new Counter();
        a.count = 1;
        Counter b = new Counter();
        b.count = 2;

        swap(a, b);
        System.out.println(a.count + ", " + b.count);

        swapCount(a, b);
        System.out.println(a.count + ", " + b.count);
    }

    static void swap(Counter x, Counter y) {
        Counter temp = x;
        x = y;
        y = temp;
    }

    static void swapCount(Counter x, Counter y) {
        int temp = x.count;
        x.count = y.count;
        y.count = temp;
    }
}
    1, 2
2, 1

    swap은 자기 매개변수 x와 y의 칸을 서로 바꿨을 뿐이다. main의 a와 b는 그대로 원래 객체를 가리키므로 첫 출력은 1, 2다. swapCount는 참조를 따라가 두 객체의 필드 값을 맞바꿨으므로 그 변화가 main에서도 보인다. 호출된 메서드가 호출한 쪽에 영향을 주는 길은 "넘겨받은 참조가 가리키는 객체를 고치는 것"과 "값을 반환하는 것" 둘뿐이다.

    참조형과 메서드 호출 활용: 만들고, 고치고, 읽는 메서드

    참조값을 주고받을 수 있다는 것은 객체를 다루는 코드를 메서드로 뽑아낼 수 있다는 뜻이다. 01회에서는 책 한 권을 만들 때마다 new 한 줄과 필드 대입 세 줄을 반복했다. 이 반복을 메서드로 옮기자. Book은 01회의 클래스(String title; int pages; int price;) 그대로다.

    public class BookFactoryMain {
    public static void main(String[] args) {
        Book book1 = createBook("자바의 기초", 320, 18000);
        Book book2 = createBook("운영체제 입문", 540, 27000);

        discount(book2, 10);

        printBook(book1);
        printBook(book2);
    }

    static Book createBook(String title, int pages, int price) {
        Book book = new Book();
        book.title = title;
        book.pages = pages;
        book.price = price;
        return book;
    }

    static void discount(Book book, int percent) {
        book.price = book.price * (100 - percent) / 100;
    }

    static void printBook(Book book) {
        System.out.println(book.title + " " + book.pages + "쪽 " + book.price + "원");
    }
}
    자바의 기초 320쪽 18000원
운영체제 입문 540쪽 24300원

    세 메서드는 참조값을 세 가지 방식으로 쓴다. printBook은 참조를 받아 객체를 읽기만 한다. discount는 참조를 받아 객체를 고친다. 반환값이 없어도 main의 book2로 읽은 가격이 24300으로 바뀌어 있는 것은 앞 절에서 본 그대로다. createBook은 방향이 반대다. 메서드 안에서 객체를 만들고 그 참조값을 반환한다.

    createBook에서 눈여겨볼 것은 객체의 수명이다. 지역 변수 book은 createBook의 프레임에 있고 메서드가 끝나면 사라진다. 하지만 new Book()으로 만든 객체는 프레임이 아니라 힙에 있다. return book;은 book에 든 참조값을 호출한 쪽에 돌려주고, main은 그것을 book1에 저장한다. 변수는 사라졌지만 객체는 남고, 이제 main의 변수가 그 객체를 가리킨다. 바이트코드로는 createBook의 마지막 두 명령이 aload_3, areturn이다. JVMS에 따르면 areturn은 현재 프레임의 피연산자 스택에서 참조를 꺼내 호출자 프레임의 피연산자 스택에 올려놓는다. 호출자 쪽에서는 invokestatic 바로 다음에 astore_1이 그 참조를 book1에 저장한다. 반환도 결국 참조값의 복사다.

    배열도 객체이므로 같은 규칙을 따른다. int[]처럼 구성 요소가 기본형인 배열이라도 배열 변수에 든 것은 참조값이다. 그래서 배열을 인자로 넘기면 호출된 메서드가 칸의 값을 바꿀 수 있고, 그 변화는 호출한 쪽에서 보인다. int[] scores = {70, 80};을 넘겨받은 메서드가 모든 칸에 5를 더하면 호출한 쪽에서 scores[0]은 75다. 자바 입문의 배열 회차에서 "배열 변수는 참조를 담는다"고 한 것이 이 동작의 근거다.

    메서드가 넘겨받은 객체를 고칠 수 있다는 것은 편리하면서 위험하다. discount(book2, 10)이라는 호출만 보아서는 book2가 바뀌는지 알 수 없고, 메서드 본문을 읽어야 안다. 한 객체를 여러 곳에서 참조하고 있다면 한 곳의 수정이 다른 모든 곳에 나타난다. 그래서 객체를 고치는 메서드는 이름으로 그 사실을 드러내고, 고칠 필요가 없는 메서드는 읽기만 하도록 작성하는 것이 기본 예절이다. 이 문제를 구조적으로 막는 방법(불변 객체)은 중급 1편에서 다룬다.

    변수와 초기화: 필드에는 기본값이 있고 지역 변수에는 없다

    변수가 어디에 선언되었느냐에 따라 첫 값이 정해지는 방식이 다르다. 클래스 본문에 선언한 필드(멤버 변수)는 01회에서 본 대로 객체가 만들어질 때 기본값을 받는다. 메서드 안에 선언한 지역 변수는 그렇지 않다.

    public class InitMain {
    public static void main(String[] args) {
        Counter counter = new Counter();
        System.out.println(counter.count);   // 필드: 값을 넣은 적이 없어도 0

        int local;
        System.out.println(local);           // 지역 변수: 컴파일 오류
    }
}
    InitMain.java:7: error: variable local might not have been initialized
        System.out.println(local);           // 지역 변수: 컴파일 오류
                           ^
1 error

    이 프로그램은 실행조차 되지 않는다. 0이 출력되는 것도, 쓰레기 값이 출력되는 것도 아니고 컴파일 단계에서 거부된다. JLS §4.12.5는 지역 변수에 대해 "사용되기 전에 초기화나 대입으로 명시적으로 값이 주어져야 하며, 그것을 확정 할당 규칙으로 검증할 수 있어야 한다"고 정한다. 확정 할당(definite assignment)은 JLS 16장 전체의 주제로, 그 생각은 한 문장으로 요약되어 있다. 지역 변수를 읽는 지점에 이르는 "가능한 모든 실행 경로에서" 그 변수에 대한 대입이 일어나야 한다는 것이다.

    "모든 경로"라는 말이 중요하다. 다음 코드는 대입문이 있는데도 컴파일되지 않는다.

    public class InitBranch {
    public static void main(String[] args) {
        int fee;
        if (args.length > 0) {
            fee = 500;
        }
        System.out.println(fee);   // error: variable fee might not have been initialized
    }
}

    조건이 거짓이면 fee에 대입하지 않은 채 출력문에 도달하는 경로가 있기 때문이다. 컴파일러는 실행 때 조건이 실제로 참일지 거짓일지를 따지지 않고 코드의 구조만 본다. else를 붙여 그쪽에서도 fee = 0;을 대입하거나, 선언할 때 int fee = 0;으로 초기화하면 모든 경로에서 대입이 보장되어 컴파일된다. 오류 메시지의 "might not have been"이라는 조심스러운 표현은 이 분석의 성격을 그대로 드러낸다. 초기화되지 않았다고 단정하는 것이 아니라, 초기화되었다고 증명할 수 없다는 뜻이다.

    같은 변수인데 왜 필드와 지역 변수의 규칙이 다를까. 명세가 이유를 적어 두지는 않았지만 두 변수의 쓰임을 보면 이해할 수 있다. 지역 변수는 선언된 블록 안에서만 쓰이므로, 메서드 하나의 코드만 읽으면 대입과 사용의 순서를 전부 따질 수 있다. 검사가 가능하니, 값을 넣지 않고 읽는 코드를 실수로 보고 막아 주는 편이 프로그래머에게 이롭다. 필드는 다르다. 객체가 살아 있는 동안 여러 메서드에서, 어떤 순서로든 읽히고 쓰일 수 있다. 어떤 메서드가 먼저 호출될지는 컴파일러가 알 수 없으므로 "읽기 전에 반드시 대입되었는가"를 일반적으로 판정할 수 없다. 그래서 필드에 대해서는 검사 대신 기본값을 보장하는 쪽을 택했다고 볼 수 있다.

    JVM 쪽에서 보아도 두 변수는 다르게 다뤄진다. 필드는 new 명령이 객체를 할당하면서 기본값으로 초기화한다. 반면 지역 변수는 선언만으로는 바이트코드가 한 줄도 생기지 않는다. int local; local = 5; 두 문장을 컴파일하면 iconst_5, istore_1 두 명령만 나온다. 선언은 "지역 변수 배열의 1번 칸을 이 이름으로 쓰겠다"는 컴파일러와의 약속일 뿐이다. 메서드가 호출될 때 프레임의 지역 변수 칸 중 값이 채워지는 것은 매개변수 칸뿐이다. 그리고 JVMS §4.10.2.2에 따르면 클래스 파일 검증기는 "적절한 타입의 값이 들어 있다고 알려진 경우가 아니면 지역 변수에 접근하지 않는다"는 것을 확인한다. 컴파일러의 검사와 JVM의 검증이 이중으로 초기화되지 않은 지역 변수의 사용을 막는 셈이다.

    표는 JLS §4.12.3이 나열한 변수의 종류 가운데 지금까지 만난 것들이다. static이 붙은 클래스 변수는 06회에서 다룬다. 지역 변수가 참조형이어도 규칙은 같다. Counter counter;만 선언하고 counter.count를 읽으려 하면 NullPointerException이 아니라 컴파일 오류가 난다. 지역 변수에는 "기본값 null"이 없기 때문이다. null을 넣고 싶다면 Counter counter = null;이라고 명시해야 한다.

    null: 아무 객체도 가리키지 않는 참조

    참조형 변수에는 객체의 참조 대신 넣을 수 있는 특별한 값이 하나 있다. null이다. JLS §4.3.1의 정의에서 참조값은 "객체를 가리키는 포인터, 그리고 아무 객체도 가리키지 않는 특별한 null 참조"였다. 소스 코드에서는 null이라는 리터럴로 쓴다.

    public class NullMain {
    public static void main(String[] args) {
        Counter counter = null;
        System.out.println(counter);
        System.out.println(counter == null);

        counter = new Counter();
        System.out.println(counter == null);
    }
}

    null의 성질을 명세에서 확인해 두자. null은 어떤 참조형에든 대입할 수 있다(JLS §4.1). Counter 변수에도, String 변수에도, 배열 변수에도 넣을 수 있다. 반대로 기본형에는 넣을 수 없다. int n = null;은 incompatible types: cannot be converted to int라는 컴파일 오류다. 기본형 변수의 칸에는 값 자체가 들어가야 하는데 null은 "가리키는 객체가 없다"는 참조값이어서 종류가 맞지 않는다. 참조형 필드와 배열 칸의 기본값이 null이라는 것은 01회에서 보았다. null이 실제로 어떤 비트열인지는 정해져 있지 않다. JVMS는 null을 스택에 올리는 aconst_null 명령의 설명에 "자바 가상 머신은 null의 구체적인 값을 강제하지 않는다"고 적어 두었다.

    null을 다루는 동작 가운데 안전한 것들을 먼저 정리하자. null을 변수에 대입하는 것, null이 든 변수를 다른 변수에 복사하는 것, ==나 !=로 null인지 비교하는 것, 그대로 출력하는 것(문자열 null이 나온다)은 모두 문제없이 실행된다. 이 동작들은 참조값을 값으로서 다룰 뿐 그것을 따라가지 않기 때문이다. null은 프로그램에서 "아직 대상이 정해지지 않았다" 또는 "대상이 없다"는 상태를 나타내는 데 쓰인다. 예약은 접수되었지만 책이 아직 배정되지 않았다면 그 예약의 book 필드는 null일 수 있다.

    null과 가비지 컬렉션: 도달 가능성

    참조형 변수에 null을 대입하면 그 변수가 가리키던 객체는 어떻게 될까. 대입의 규칙을 다시 떠올리면 답의 절반이 나온다. c1 = null;은 왼쪽이 변수 이름뿐인 대입이다. 변수 c1의 칸이 바뀔 뿐, 객체에는 아무 일도 일어나지 않는다.

    이런 객체를 찾아 메모리를 회수하는 것이 가비지 컬렉터(garbage collector, GC)다. JVMS §2.5.3은 힙의 객체가 자동 저장소 관리 시스템(가비지 컬렉터)에 의해 회수되며 "객체는 결코 명시적으로 해제되지 않는다"고 정한다. 자바에는 C의 free에 해당하는 문법이 없다. 회수의 기준은 JLS §12.6.1이 정의한 도달 가능성(reachability)이다. 도달 가능한(reachable) 객체란 "살아 있는 스레드가 앞으로 계속할 수 있는 어떤 계산에서든 접근될 수 있는 객체"다. 도달 불가능한 객체는 저장소가 회수될 수 있다.

    이 정의를 실용적으로 읽으면 이렇다. 실행 중인 코드가 직접 쓸 수 있는 변수들, 곧 스레드의 스택 프레임에 있는 지역 변수와 매개변수(그리고 06회에서 배울 static 변수)에서 출발한다. 거기 든 참조를 따라가 닿는 객체는 도달 가능하다. 그 객체의 필드나 배열 칸에 든 참조를 다시 따라가 닿는 객체도 도달 가능하다. 이렇게 화살표를 따라 닿을 수 있는 객체가 전부 살아 있는 것이고, 어떤 경로로도 닿을 수 없는 객체가 회수 대상이다. 기준은 "가리키는 참조가 몇 개인가"가 아니라 "출발점에서 닿을 수 있는가"다. 이 차이는 객체들이 서로를 가리킬 때 드러난다.

  스택에서 힙으로 들어가는 화살표가 하나도 없다. A와 B는 서로를 가리키지만 둘 다 도달 불가능하다.
    가비지 컬렉션의 기준이 참조의 개수가 아니라 스택의 변수에서 화살표를 따라 닿을 수 있는지라는 것, 서로를 가리키는 객체 묶음도 바깥에서 닿을 수 없으면 회수 대상이라는 것을 보여 준다. 깔끔한 기술 교재풍 개념도. 왼쪽에 세로로 긴 영역을 두고 라벨 "스택의 변수 (출발점)"을 붙이며 그 안에 칸 두 개 "book1", "books"를 그린다. 오른쪽 넓은 영역의 라벨은 "힙". 힙의 위쪽 절반에는 초록색 테두리의 객체 상자 세 개를 그린다. "book1" 칸에서 첫 번째 상자로 화살표, "books" 칸에서 두 번째 상자(배열 모양으로 칸이 나뉜 상자)로 화살표, 그 배열 상자의 한 칸에서 세 번째 상자로 화살표를 그린다. 이 세 상자 묶음 옆에 "도달 가능"이라고 적는다. 힙의 아래쪽 절반에는 회색 점선 테두리의 객체 상자 두 개를 나란히 그리고 서로를 향하는 화살표 두 개로 연결한다. 이 두 상자로 들어오는 화살표는 스택에서도 위쪽 객체에서도 하나도 없다. 이 묶음 옆에 "도달 불가능: 회수 대상"이라고 적는다. 그림 맨 아래에 한 줄 "기준은 참조의 개수가 아니라 출발점에서 닿을 수 있는가"를 적는다. 흰 배경, 또렷한 선과 글자. 스택의 변수에서 출발해 참조를 따라 닿는 객체만 살아 있다. 서로를 가리키더라도 바깥에서 닿을 수 없으면 회수 대상이다.

    A와 B에는 각각 자신을 가리키는 참조가 하나씩 남아 있다. 그러나 프로그램이 쓸 수 있는 어떤 변수에서도 이 둘에 닿는 길이 없으므로 둘 다 도달 불가능하고, 회수될 수 있다. JLS §12.6도 원형으로 연결된 객체 묶음이 도달 불가능해지는 경우를 예로 든다.

    회수가 "언제" 일어나는지는 명세가 정하지 않는다. JVMS는 특정한 저장소 관리 방식을 가정하지 않는다고 밝히고 있고, 도달 불가능해진 객체가 즉시 회수된다는 보장은 어디에도 없다. 프로그래머가 알아야 할 것은 조건이지 시점이 아니다. 여기서 실무적인 결론 두 가지가 나온다. 첫째, 메서드 안에서 만든 객체를 다 썼다고 변수에 일일이 null을 대입할 필요는 없다. 메서드가 끝나면 프레임과 함께 지역 변수가 사라지고, 그 변수에서 출발하던 화살표도 함께 없어진다. JLS §12.6.1은 더 나아가, 컴파일러나 코드 생성기가 앞으로 쓰이지 않을 변수를 null로 취급해 객체가 더 일찍 회수될 수 있게 하는 최적화도 허용한다고 적는다. 둘째, 반대로 오래 살아남는 객체의 필드나 배열 칸이 어떤 객체를 계속 가리키고 있으면, 프로그램이 그 객체를 다시 쓸 일이 없어도 회수되지 않는다. 자바에서 메모리 누수라고 부르는 현상은 대부분 이것, 곧 쓰지 않을 객체가 도달 가능한 채로 남는 것이다.

    NullPointerException: 참조를 따라가는 순간에 난다

    null이 든 변수로 할 수 없는 일은 하나다. 그 참조를 따라가는 것이다. 가리키는 객체가 없는데 "그 객체의 필드"를 읽거나 쓰려 하면 JVM은 NullPointerException(줄여서 NPE)을 던진다. 예외가 나는 지점을 정확히 짚어 보자.

    public class NpeMain {
    public static void main(String[] args) {
        Counter counter = null;             // 예외 없음: null을 대입할 뿐이다
        Counter copy = counter;             // 예외 없음: null을 복사할 뿐이다
        System.out.println(copy == null);   // 예외 없음: 비교할 뿐이다

        copy.count = 1;                     // 여기서 NullPointerException
        System.out.println("끝");           // 실행되지 않는다
    }
}

    at NpeMain.main(NpeMain.java:7)

    3~5번째 줄은 null을 값으로 다룰 뿐이어서 아무 문제가 없다. 7번째 줄 copy.count = 1;에서 처음으로 참조를 따라가려 하고, 그 순간 예외가 난다. 바이트코드로 보면 이 줄은 aload_2, iconst_1, putfield인데, 01회에서 보았듯 JVMS는 putfield와 getfield의 설명에 "객체 참조가 null이면 NullPointerException을 던진다"고 명시한다. 참조를 스택에 올리는 aload_2까지는 정상이고, 그 참조를 꺼내 객체에 접근하려는 명령에서 실패하는 것이다. 예외가 던져지면 그 뒤의 문장은 실행되지 않고, 예외를 처리하는 코드가 없으면 프로그램이 종료된다(예외 처리는 중급 1편에서 다룬다).

    NullPointerException의 Javadoc도 같은 목록을 든다. null인 객체의 인스턴스 메서드를 호출할 때, 필드에 접근하거나 수정할 때, null을 배열로 보고 길이를 얻거나 칸에 접근할 때다. 공통점은 모두 "점이나 대괄호의 왼쪽에 있는 참조가 null"이라는 것이다. NPE를 만났을 때 찾아야 할 것은 그 줄에서 따라가려 한 참조다.

    필드의 기본값 null과 연쇄 접근

    실제 코드에서 NPE는 null을 직접 대입한 변수보다 값을 넣지 않은 참조형 필드에서 더 자주 나온다. 도서 예약을 나타내는 클래스를 보자.

    public class Reservation {
    Book book;
    String memberName;
}
    public class ReservationMain {
    public static void main(String[] args) {
        Reservation reservation = new Reservation();
        reservation.memberName = "kim";

        System.out.println(reservation.book);
        System.out.println(reservation.book.title);
    }
}
    null
Exception in thread "main" java.lang.NullPointerException: Cannot read field "title" because ".book" is null
    at ReservationMain.main(ReservationMain.java:7)

    reservation 자체는 null이 아니다. new Reservation()으로 만든 객체를 가리킨다. 그러나 그 객체의 book 필드에는 아무것도 넣지 않았으므로 기본값 null이 들어 있다. reservation.book.title은 참조를 두 번 따라간다. 첫 번째 점은 reservation을 따라가 book 필드의 값(null)을 꺼내는 데 성공한다. 두 번째 점이 그 null을 따라가 title을 읽으려다 실패한다. 메시지도 정확히 그렇게 말한다. title 필드를 읽을 수 없었고, 이유는 .book이 null이기 때문이다. 점이 여러 개 이어진 식에서는 마지막 이름을 뺀 모든 구간이 null 후보다.

    at PassNull.main(PassNull.java:4)

    null을 인자로 넘기는 4번째 줄에서는 예외가 나지 않는다. 인자 전달은 값의 복사이고 null도 복사할 수 있는 값이다. printTitle은 정상적으로 시작해 첫 출력까지 마친다. 예외는 9번째 줄에서 target을 따라가려 할 때 난다. 스택 트레이스의 맨 윗줄이 예외가 실제로 발생한 위치이고, 아랫줄은 그 메서드를 호출한 곳이다. 여기서 NPE 진단의 어려움이 생긴다. 예외가 알려 주는 것은 null을 따라가려 한 곳인데, 고쳐야 할 곳은 대개 null을 만들어 넘긴 쪽이다. JEP 358도 이 한계를 분명히 적었다. 목표는 null 참조를 궁극적으로 만들어 낸 쪽을 추적하는 것이 아니라 그것을 만난 "운 없는 소비자"를 알려 주는 것이라고 한다. 원인을 찾으려면 스택 트레이스를 거슬러 올라가며 그 값이 어디서 왔는지를 따라가야 한다.

    평가 순서: 예외는 꼭 필요한 순간까지 미뤄진다

    "참조를 따라가는 순간"이 언제인지는 명세가 세밀하게 정해 두었다. book이 null일 때 book.price = computePrice();를 실행하면 computePrice()가 호출될까, 그 전에 예외가 날까.

    public class OrderMain {
    public static void main(String[] args) {
        Book book = null;
        book.price = computePrice();
    }

    static int computePrice() {
        System.out.println("computePrice 실행");
        return 18000;
    }
}
    computePrice 실행
Exception in thread "main" java.lang.NullPointerException: Cannot assign field "price" because "" is null
    at OrderMain.main(OrderMain.java:4)

    메서드가 먼저 실행된다. JLS §15.26.1은 필드에 대입하는 식 e.f = 값의 순서를 이렇게 정한다. 먼저 e를 평가하고, 다음으로 오른쪽 식을 평가하고, 그런 뒤에 e의 값이 null이면 NullPointerException을 던진다. e를 평가한다는 것은 변수에서 참조값을 꺼낸다는 뜻이지 따라간다는 뜻이 아니다. 바이트코드도 같은 순서다. aload_1로 참조(null)를 스택에 올리고, invokestatic으로 메서드를 호출해 결과를 올리고, 마지막 putfield에서 예외가 난다. NPE가 났다고 해서 그 줄의 다른 부분이 실행되지 않았다고 단정하면 안 되는 이유다.

    참조를 실제로 따라가지 않으면 null이어도 예외가 나지 않는다는 원칙의 극단적인 예가 있다. JLS §15.11.1에 따르면 static 필드를 참조변수.필드 형태로 접근할 때는 참조 식을 평가한 뒤 그 결과를 버린다. 객체를 따라갈 필요가 없기 때문이다. 그래서 변수가 null이어도 예외 없이 값이 읽힌다. 권장되는 코드는 아니며, static은 06회에서 다룬다.

    유용한 NPE 메시지 읽기 (JEP 358)

    앞의 예제들에서 예외 메시지가 "무엇을 하려다 실패했고, 어떤 참조가 null이었는지"를 알려 주었다. 이 메시지는 JEP 358 "Helpful NullPointerExceptions"로 도입된 기능이다. 이 기능이 없으면 같은 예외가 다음처럼만 출력된다.

    Exception in thread "main" java.lang.NullPointerException
    at ReservationMain.main(ReservationMain.java:7)

    알 수 있는 것은 7번째 줄이라는 사실뿐이다. 그 줄이 reservation.book.title이라면 reservation이 null인지 book이 null인지는 디버거를 붙이거나 코드를 쪼개 다시 실행해야 알 수 있었다. JEP 358은 JVM이 예외를 일으킨 바이트코드를 분석해 이 정보를 메시지로 만들어 주게 했다. JDK 14에 들어갈 때는 기본으로 꺼져 있었고(-XX:+ShowCodeDetailsInExceptionMessages로 켰다), JDK 15 릴리스 노트에 이 옵션의 기본값이 켜짐으로 바뀌었다고 기록되어 있다. 이 강좌의 기준인 Java 21에서는 별도 설정 없이 메시지가 나온다.

    메시지는 두 부분으로 이루어진다. JEP의 설명을 빌리면 앞부분은 NPE의 결과, 곧 "null 참조를 스택에서 꺼낸 명령이 하려던 일"이고, 뒷부분(because …)은 원인, 곧 "그 null을 스택에 올린 소스 코드 부분"을 재구성한 것이다. 앞부분은 예외를 일으킨 명령의 종류로 정해진다.

    null을 꺼낸 명령메시지의 앞부분소스 코드에서의 모습
    getfieldCannot read field "이름"x.field를 읽음
    putfieldCannot assign field "이름"x.field = …
    invokevirtual 등 호출 명령Cannot invoke "클래스.메서드(매개변수 타입)"x.method()
    arraylengthCannot read the array lengtharr.length
    iaload, aaload 등Cannot load from int array 등arr[i]를 읽음
    iastore, aastore 등Cannot store to int array 등arr[i] = …

    뒷부분은 JVM이 바이트코드를 거슬러 올라가며 만든다. getfield가 꺼낸 null을 누가 스택에 올렸는지 찾아보니 또 다른 getfield book이었고, 그 명령이 쓴 참조는 지역 변수 1번에서 왔다는 식이다. 그 결과가 ".book" is null이다. 여기서 변수 이름 대신 이 나오는 이유가 설명된다. 클래스 파일에는 기본적으로 지역 변수의 이름이 들어 있지 않다. javac 문서에 따르면 기본으로 생성되는 디버깅 정보는 줄 번호와 소스 파일 정보뿐이고, -g 옵션을 주어야 지역 변수 정보까지 포함된다. JEP 358은 지역 변수 표가 있으면 변수 이름을, 없으면 나 같은 표기를 쓴다고 정한다. 같은 프로그램을 javac -g로 컴파일해 실행하면 메시지가 이렇게 바뀐다.

    Exception in thread "main" java.lang.NullPointerException: Cannot read field "title" because "reservation.book" is null
    at ReservationMain.main(ReservationMain.java:7)

    번호만 나왔을 때 읽는 법도 어렵지 않다. static 메서드에서는 매개변수가 지역 변수 0번부터 자리를 받는다(JVMS §2.6.1). main(String[] args)라면 args가 0번이고, 본문에서 처음 선언한 지역 변수가 1번이다. long과 double은 두 칸을 차지한다는 점만 주의하면 된다. IDE나 빌드 도구로 실행했을 때 변수 이름이 보인다면 그 도구가 디버그 정보를 넣어 컴파일하고 있다는 뜻이다.

    이 기능의 경계도 알아 두자. 첫째, JEP에 따르면 이 메시지는 JVM이 직접 만들어 던진 NPE에만 붙는다. 프로그램 코드가 new NullPointerException()으로 만들어 던진 예외에는 붙지 않는다. 둘째, 메시지는 예외가 만들어질 때가 아니라 getMessage()가 호출될 때 계산된다. NPE를 잡아서 버리는 코드에 불필요한 비용을 지우지 않기 위해서다. 셋째, 메시지에는 필드 이름과 (디버그 정보가 있으면) 변수 이름이 들어간다. JDK 15 릴리스 노트는 이 메시지가 애플리케이션의 오류 화면 등에 그대로 노출되면 공격자에게 단서가 될 수 있으니 배포하는 쪽에서 출력을 점검하라고 권고한다. 예외 메시지는 로그에 남기고 사용자 화면에는 그대로 내보내지 않는 것이 원칙이다.

    자주 하는 오해

    • "객체를 다른 변수에 대입하면 객체가 복사된다." 복사되는 것은 참조값이다. 객체는 하나이고 가리키는 변수가 늘어날 뿐이다. 객체를 정말로 복제하려면 새 객체를 만들어 필드 값을 옮겨야 한다.
    • "참조형은 참조에 의한 전달이다." 자바의 인자 전달은 언제나 값의 복사다. 참조형이면 그 값이 참조값일 뿐이다. 호출된 메서드는 객체를 고칠 수 있어도 호출한 쪽의 변수를 다른 객체로 바꿀 수는 없다.
    • "지역 변수도 선언하면 0이나 null이 된다." 기본값은 필드와 배열의 칸에만 있다. 지역 변수는 대입하기 전에 읽으면 컴파일 오류다.
    • "null을 대입하면 객체가 지워진다." 그 변수의 칸이 바뀔 뿐이다. 다른 변수나 필드가 가리키고 있으면 객체는 그대로 살아 있고, 아무도 닿을 수 없게 되어야 회수 대상이 된다. 회수 시점은 정해져 있지 않다.
    • "서로를 참조하는 객체는 회수되지 않는다." 기준은 참조의 개수가 아니라 도달 가능성이다. 바깥에서 닿을 수 없는 묶음은 통째로 회수 대상이다.
    • "NPE는 null을 대입하거나 넘길 때 난다." null을 대입·복사·비교·전달하는 것은 모두 정상이다. 예외는 null인 참조를 따라가는 명령에서 난다. 그래서 예외가 난 줄과 null이 만들어진 줄은 대개 다르다.

    이 지식이 다시 쓰이는 곳

    바로 다음 03회에서 counter.increase()처럼 객체의 메서드를 호출하는 문법을 배운다. 점 앞의 참조값이 메서드에 인자처럼 전달된다는 점에서, 오늘 본 "참조값을 넘겨 객체를 고치는 메서드"의 연장이다. 07회의 final에서는 오늘의 구별이 그대로 쓰인다. JLS §4.12.4의 표현대로 final 변수가 객체의 참조를 담고 있으면 그 변수는 언제나 같은 객체를 가리키지만, 객체의 상태는 바뀔 수 있다. final이 막는 것은 "변수를 바꾸는 것"이지 "객체를 고치는 것"이 아니다.

    한 객체를 여러 곳에서 참조할 때 생기는 문제는 이후 과정 내내 다시 나온다. 중급 1편의 불변 객체는 공유된 객체가 뜻하지 않게 바뀌는 문제를 아예 차단하는 설계이고, ==와 equals()의 구별은 "같은 객체인가"와 "내용이 같은가"의 구별이다. 컬렉션에 객체를 넣는 것도 참조값을 넣는 것이어서, 꺼낸 객체를 고치면 컬렉션 안의 것이 바뀐다. 여러 스레드가 한 객체를 참조하며 고칠 때의 문제는 고급 1편(멀티스레드)의 중심 주제다. 이 모든 논의의 바닥에 "변수에는 참조값이 있고, 대입과 전달은 그 값을 복사한다"는 오늘의 그림이 놓여 있다.

    이 장의 핵심

    대입과 인자 전달은 언제나 변수에 든 값을 복사한다. 기본형 변수에는 값 자체가, 참조형 변수에는 참조값이 들어 있으므로 결과가 달라 보일 뿐이다. 참조형 변수가 나오는 코드에서는 "변수의 칸을 바꾸는가, 참조를 따라가 객체를 고치는가"를 구별하면 대입, 메서드 호출, null, 가비지 컬렉션, NullPointerException이 한 장의 그림으로 설명된다.
    기본형과 참조형
    기본형 변수에는 값 자체가, 참조형 변수에는 객체를 가리키는 참조값(또는 null)이 들어 있다. 자바의 타입은 이 두 종류뿐이다.
    대입은 값의 복사
    = 는 오른쪽 식의 값을 왼쪽 변수의 칸에 복사한다. 참조형이면 참조값이 복사되어 두 변수가 한 객체를 가리킨다.
    변수를 바꾸는 것과 객체를 고치는 것
    c = …는 변수의 칸만 바꾸고(astore), c.field = …는 참조를 따라가 힙의 객체를 바꾼다(putfield). 뒤의 것만 다른 변수에서 보인다.
    값에 의한 전달
    메서드를 호출하면 인자의 값이 새로 만들어진 매개변수에 복사된다. 호출된 메서드는 넘겨받은 참조로 객체를 고칠 수 있지만 호출한 쪽의 변수는 바꿀 수 없다.
    변수의 초기화
    필드와 배열의 칸은 기본값을 받는다. 지역 변수는 기본값이 없고, 모든 실행 경로에서 대입된 뒤에만 읽을 수 있다(확정 할당).
    null
    아무 객체도 가리키지 않는 참조값. 모든 참조형에 대입할 수 있고 기본형에는 대입할 수 없다. 대입·복사·비교·전달은 안전하다.
    도달 가능성과 GC
    스택의 변수 등에서 참조를 따라 닿을 수 없는 객체가 회수 대상이다. null 대입은 객체를 지우지 않으며, 회수 시점은 명세가 정하지 않는다.
    NullPointerException의 시점
    null인 참조를 따라가는 명령(필드 접근, 인스턴스 메서드 호출, 배열 접근)에서 발생한다. 메시지의 because 뒤가 null이었던 참조다.

    실무의 버그 가운데 상당수는 "이 객체를 누가 또 참조하고 있는가"를 놓쳐서 생긴다. 메서드에 넘긴 객체나 배열을 호출된 쪽이 고쳤는데 호출한 쪽은 그대로일 것이라 가정한 경우, 객체 하나를 두 군데에 저장해 두고 한쪽만 고쳤다고 생각한 경우가 전형적이다. 넘겨받은 객체를 고쳐도 되는지, 반환하는 객체를 호출한 쪽이 고쳐도 되는지는 코드 리뷰에서 명시적으로 확인할 항목이다. 고쳐서는 안 되는 데이터라면 새 객체로 복사해 넘기거나, 처음부터 바꿀 수 없는 객체로 설계한다.

    운영 중에 NPE가 나면 순서대로 본다. 먼저 메시지의 앞부분에서 무슨 동작이 실패했는지, because 뒤에서 어떤 참조가 null이었는지를 읽는다. 변수 이름 대신 번호가 나온다면 배포한 클래스에 디버그 정보가 없는 것이므로 줄 번호와 번호 규칙으로 해석한다. 그다음이 진짜 일이다. 스택 트레이스를 따라 올라가며 그 null이 어디서 만들어졌는지를 찾는다. 값을 넣지 않은 필드인지, 조회 결과가 없어서 null을 반환한 메서드인지에 따라 고칠 곳이 달라진다. null 검사를 예외가 난 줄에 덧붙이는 것은 증상만 가리는 경우가 많다. "이 값이 null일 수 있는 것이 정상인가"를 먼저 판단해야 한다.

    메모리가 계속 늘어나는 문제를 볼 때도 기준은 도달 가능성이다. GC가 "게을러서" 회수하지 않는 것이 아니라, 프로그램 어딘가가 그 객체들을 여전히 가리키고 있는 것이다. 오래 사는 객체가 가진 컬렉션에 계속 추가만 하고 빼지 않는 코드가 흔한 원인이다. 반대로 메서드 안의 지역 변수에 null을 대입해 GC를 돕겠다는 코드는 대부분 의미가 없다. null 대입이 의미를 갖는 것은 수명이 긴 객체의 필드나 배열 칸에서 더 쓰지 않을 참조를 끊을 때다.

    Counter x = new Counter();

NPE는 null을 읽거나 복사할 때가 아니라 따라갈 때 난다.
    기본형(primitive type)
    언어가 미리 정한 여덟 가지 타입. 변수에 값 자체가 저장되며 다른 값과 상태를 공유하지 않는다.
    참조형(reference type)
    클래스, 배열, 인터페이스 등 기본형이 아닌 모든 타입. 변수에는 객체를 가리키는 참조값이나 null이 저장된다.
    별칭(aliasing)
    한 객체를 둘 이상의 변수(또는 필드, 배열 칸)가 가리키는 상태. 한쪽으로 객체를 고치면 다른 쪽으로도 보인다.
    값에 의한 전달(pass by value)
    메서드 호출 때 인자의 값을 매개변수에 복사하는 방식. 자바는 기본형이든 참조형이든 이 방식만 쓴다.
    확정 할당(definite assignment)
    지역 변수를 읽는 지점에 이르는 모든 실행 경로에서 대입이 일어났음을 컴파일러가 확인하는 규칙(JLS 16장).
    null 참조(null reference)
    아무 객체도 가리키지 않는 참조값. 리터럴 null로 쓰며 참조형 필드의 기본값이다.
    도달 가능성(reachability)
    살아 있는 스레드가 앞으로의 계산에서 그 객체에 접근할 수 있는가. 도달 불가능한 객체가 가비지 컬렉션 대상이다.
    가비지 컬렉터(garbage collector)
    도달 불가능한 객체의 메모리를 자동으로 회수하는 JVM의 저장소 관리 시스템. 회수 시점과 방식은 구현의 몫이다.
    NullPointerException
    null인 참조로 필드 접근, 인스턴스 메서드 호출, 배열 접근 등을 시도할 때 JVM이 던지는 예외.
    널 상세 메시지(null-detail message)
    JEP 358이 도입한 NPE 메시지. 실패한 동작과 null이었던 식을 바이트코드 분석으로 알려 준다.
