    이 회차의 질문: 반복문은 무엇을 섞어 놓는가

    앞의 네 회차에서 람다와 함수형 인터페이스, 메서드 참조를 다졌다. 3회에서는 람다를 이용해 거르기(filter)와 바꾸기(map) 같은 도구를 직접 만들어 보기도 했다. 이 회차부터 세 회에 걸쳐 그 도구들의 완성형인 스트림 API(Stream API, java.util.stream)를 다룬다. 이번 회차는 스트림이 무엇이고 파이프라인이 어떻게 조립되며, 왜 "지연"되어 실행되는지를 바닥까지 판다. 스트림을 만드는 여러 방법과 중간·최종 연산의 목록은 6회, collect와 Collector의 구조는 7회, 병렬 스트림은 10회의 몫이다.

    출발점은 평범한 문제다. 단어 목록에서 길이가 5 이상인 단어를 골라 대문자로 바꾸고, 그중 처음 두 개만 얻고 싶다. 자바 입문편 이후 우리가 가장 익숙하게 쓰는 방법은 반복문 하나에 모든 것을 넣는 것이다.

    import java.util.ArrayList;
import java.util.List;

public class Start {
    public static void main(String[] args) {
        List words = List.of("apple", "kiwi", "banana", "fig", "cherry", "grape");

        // 1) 반복문 하나에 모두 섞어 쓴 방식
        List r1 = new ArrayList<>();
        for (String w : words) {
            if (w.length() >= 5) {          // 거르기
                r1.add(w.toUpperCase());    // 바꾸기 + 모으기
                if (r1.size() == 2) break;  // 개수 제한 + 조기 종료
            }
        }

        // 2) 단계마다 결과를 컬렉션에 담는 방식
        List longWords = new ArrayList<>();
        for (String w : words) if (w.length() >= 5) longWords.add(w);
        List upper = new ArrayList<>();
        for (String w : longWords) upper.add(w.toUpperCase());
        List r2 = upper.subList(0, Math.min(2, upper.size()));

        System.out.println(r1);
        System.out.println(r2);
        System.out.println(longWords.size() + " " + upper.size());
    }
}

    두 방식은 같은 답을 내지만 성격이 정반대다. 1번은 효율적이다. 목록을 한 번만 돌고, 중간 결과를 담는 컬렉션이 없고, 두 개를 찾자마자 break로 빠져나간다. 실제로 "apple", "kiwi", "banana" 세 단어만 보고 끝난다. 대신 읽기 어렵다. 거르기, 바꾸기, 모으기, 개수 제한, 조기 종료라는 다섯 가지 생각이 중첩된 if와 break 안에 한데 엉켜 있다. 조건 하나를 바꾸거나 단계를 하나 끼워 넣으려면 엉킨 실타래를 풀어야 한다.

    2번은 단계가 또렷하다. 거르는 반복문, 바꾸는 반복문, 자르는 줄이 따로 있다. 대신 비효율적이다. 목록 전체를 거른 결과 4개를 longWords에 담고, 4개 모두를 대문자로 바꿔 upper에 담은 뒤에야 앞의 두 개만 쓴다. 두 개만 필요했는데 여섯 단어를 모두 검사했고, 대문자 변환도 두 번 더 했고, 중간 리스트를 두 개나 만들었다. 단어가 백만 개라면 백만 개짜리 중간 리스트가 생긴다. 목록이 끝없이 이어진다면(예를 들어 계속 생성되는 수열이라면) 2번 방식은 아예 끝나지 않는다.

    이 딜레마의 뿌리는 반복을 누가 통제하는가에 있다. 두 방식 모두 반복문을 쓰는 우리 코드가 "다음 원소를 꺼내고, 검사하고, 담고, 멈출지 정하는" 반복의 절차를 직접 통제한다. 이것을 외부 반복(external iteration)이라고 부른다. 외부 반복에서는 효율을 얻으려면 절차를 손으로 합쳐야 하고(1번), 절차를 나누면 효율을 잃는다(2번). 스트림은 반복의 통제권을 라이브러리로 넘긴다. 우리는 "무엇을" 할지만 단계별로 선언하고, "어떻게" 반복할지는 라이브러리가 정한다. 이것이 내부 반복(internal iteration)이다.

    이 장의 핵심

    스트림의 중간 연산(filter, map, limit …)은 일을 하지 않는다. 호출할 때마다 "이전 단계에 이런 연산을 덧붙인다"는 설명서 한 장, 곧 새 파이프라인 단계 객체를 만들어 사슬로 이어 둘 뿐이다. 최종 연산이 호출되는 순간에야 라이브러리는 그 설명서를 거꾸로 읽어 원소를 받아 처리하는 Sink 객체들의 사슬을 조립하고, 소스의 원소를 하나씩 사슬 끝까지 밀어 넣는다. 그래서 여러 단계가 한 번의 순회로 합쳐지고(루프 융합), 필요한 만큼만 처리하고 멈출 수 있으며(단락), 소스의 성질을 미리 알면 단계 자체를 건너뛸 수도 있다. 2번처럼 단계별로 선언하면서 1번처럼 실행되는 것, 이것이 지연 연산이 존재하는 이유다.

    스트림 API 시작: 같은 문제를 스트림으로

    같은 문제를 스트림으로 쓰면 이렇다. 위 main에 이어 붙여 실행하면 된다.

    List r3 = words.stream()            // 소스: 리스트에서 스트림을 얻는다
        .filter(w -> w.length() >= 5)       // 중간 연산: 거르기
        .map(String::toUpperCase)           // 중간 연산: 바꾸기
        .limit(2)                           // 중간 연산: 처음 두 개만
        .toList();                          // 최종 연산: 리스트로 모으기
System.out.println(r3);                     // [APPLE, BANANA]

    읽기는 2번 방식처럼 단계가 하나씩 드러난다. 그런데 실행은 1번 방식과 같다. 뒤에서 실행 추적으로 확인하겠지만, 이 파이프라인은 "apple"을 거르고 바로 대문자로 바꿔 결과에 넣고, "kiwi"를 거르다 탈락시키고, "banana"를 거르고 바꿔 넣은 순간 두 개가 찼음을 알고 멈춘다. 나머지 세 단어는 쳐다보지도 않고, 중간 리스트도 만들지 않는다. toList()는 자바 16에 추가된 최종 연산으로, 수정할 수 없는(unmodifiable) 리스트를 돌려준다(API 문서: 변경 메서드를 부르면 항상 UnsupportedOperationException). 그 전 버전에서는 collect(Collectors.toList())를 썼다. 둘의 차이는 7회에서 다룬다.

    일상에서 가져온 비유작업 지시서를 쓰는 사람과 공장

    외부 반복은 공장장이 직접 컨베이어 앞에 서서 물건을 하나씩 집어 검사하고 포장하는 것과 같다. 스트림은 공장장이 "불량품은 빼고, 포장지를 씌우고, 두 개만 출고" 같은 작업 지시서를 단계별로 써서 공장에 넘기는 방식이다. 지시서를 쓰는 동안에는 컨베이어가 돌지 않는다. "출고" 지시가 내려오면 공장은 지시서 전체를 보고 라인을 한 번에 구성한 뒤에야 컨베이어를 돌리고, 물건은 하나씩 검사대와 포장대를 연달아 통과한다. 두 개가 출고되면 라인을 멈춘다. 비유가 깨지는 지점도 있다. 실제 공장은 지시서를 읽고 순서를 바꾸거나 단계를 합칠 수 있지만, 스트림 라이브러리는 람다의 내용을 해석하지 못한다. 그래서 filter와 map의 순서를 바꿔 주지는 않는다. 라이브러리가 아는 것은 람다의 속이 아니라 "이 단계가 원소 수를 바꿀 수 있는가, 정렬 상태를 깨는가" 같은 단계의 성질뿐이다.

    스트림 API란: 저장하지 않는 계산의 흐름

    java.util.stream 패키지 문서는 스트림을 "원소의 흐름에 대한 함수형 연산을 지원하는 클래스들"로 소개하고, 컬렉션과 다른 점을 다섯 가지로 정리한다. 하나씩 무엇을 뜻하는지, 실제로 무엇이 그렇게 만드는지까지 보자.

    1. 저장하지 않는다(No storage). 문서의 표현으로 스트림은 원소를 저장하는 자료 구조가 아니라, 자료 구조·배열·생성 함수·I/O 채널 같은 소스의 원소를 계산 연산의 파이프라인으로 "실어 나르는" 것이다. 뒤에서 볼 파이프라인 단계 객체에는 원소를 담는 배열이나 리스트 필드가 없다. 단계 객체가 가진 것은 소스를 가리키는 참조, 이전·다음 단계를 가리키는 참조, 그리고 이 단계에서 할 연산(람다)이다.
    2. 함수형이다(Functional in nature). 스트림 연산은 결과를 만들 뿐 소스를 바꾸지 않는다. 컬렉션에서 얻은 스트림을 거르면 걸러진 원소가 빠진 새 스트림이 생기는 것이지, 원본 컬렉션에서 원소가 삭제되는 것이 아니다. List.removeIf가 리스트 자체를 고치는 것과 대비된다.
    3. 지연을 추구한다(Laziness-seeking). 거르기, 바꾸기, 중복 제거 같은 많은 연산은 지연해서 구현할 수 있고, 그 덕에 최적화 기회가 생긴다. 문서는 중간 연산(intermediate operation, 스트림을 돌려주는 연산)과 최종 연산(terminal operation, 값이나 부수 효과를 만드는 연산)을 나누고, "중간 연산은 언제나 지연된다(Intermediate operations are always lazy)"고 못 박는다.
    4. 무한일 수 있다(Possibly unbounded). 컬렉션의 크기는 유한하지만 스트림은 그렇지 않아도 된다. limit(n)이나 findFirst() 같은 단락 연산이 무한 스트림 위의 계산을 유한한 시간에 끝낼 수 있게 해 준다. 무한 스트림이 가능한 것 자체가 "저장하지 않는다"와 "지연된다"의 결과다. 저장해야 했다면 무한한 원소를 담을 수 없고, 즉시 계산해야 했다면 끝나지 않는다.
    5. 소비된다(Consumable). 스트림의 원소는 스트림의 생애 동안 한 번만 방문된다. Iterator처럼, 같은 원소를 다시 방문하려면 소스에서 새 스트림을 얻어야 한다.

    이 다섯 가지를 컬렉션과 나란히 놓으면 차이가 분명해진다.

    타입 계층도 짚어 두자. 스트림의 공통 부모는 BaseStream이고, 참조형 원소를 다루는 Stream과 기본형을 다루는 IntStream, LongStream, DoubleStream이 그 아래에 있다. 기본형 특화 스트림이 왜 따로 있는지는 6회에서 다룬다. BaseStream은 AutoCloseable을 확장하므로 모든 스트림에 close()가 있다. 다만 Stream의 API 문서는 컬렉션·배열·생성 함수에 기반한 대부분의 스트림은 닫을 필요가 없고, Files.lines(Path)처럼 I/O 채널을 소스로 하는 스트림만 try-with-resources로 닫아야 한다고 설명한다. 스트림이 "저장하지 않고 소스에서 꺼내 온다"는 성질을 생각하면 자연스럽다. 소스가 파일이라면 파이프라인이 끝날 때까지 파일이 열려 있어야 한다.

    파이프라인 구성: 소스, 중간 연산, 최종 연산

    패키지 문서의 정의로 스트림 파이프라인(stream pipeline)은 하나의 소스(컬렉션, 배열, 생성 함수, I/O 채널 등), 0개 이상의 중간 연산(filter, map 등), 하나의 최종 연산(forEach, reduce 등)으로 이루어진다. 세 부분의 역할을 정리하면 이렇다.

    부분예반환 타입호출했을 때 일어나는 일
    소스list.stream(), Stream.of(...), Arrays.stream(arr), Stream.iterate(...)Stream소스를 감싼 첫 단계(Head) 객체를 만든다. 원소는 아직 읽지 않는다.
    중간 연산filter, map, sorted, distinct, limit, peekStream(새 단계)이전 단계에 연결된 새 단계 객체를 만든다. 원소를 처리하지 않는다.
    최종 연산toList, forEach, count, findFirst, anyMatch, collect, reduce값, Optional, 또는 void파이프라인 전체를 실행하고, 파이프라인을 "소비됨"으로 표시한다.

    중간 연산은 다시 두 부류로 나뉜다. 패키지 문서에 따르면 상태 없는(stateless) 연산은 filter, map처럼 새 원소를 처리할 때 앞서 본 원소의 상태를 들고 있지 않아 원소마다 독립적으로 처리할 수 있는 연산이고, 상태 있는(stateful) 연산은 distinct, sorted처럼 앞서 본 원소의 상태를 새 원소 처리에 반영할 수 있는 연산이다. 또 무한 입력에서 유한한 스트림을 만들어 낼 수 있는 중간 연산(limit), 무한 입력에서 유한한 시간에 끝날 수 있는 최종 연산(findFirst, anyMatch)을 단락(short-circuiting) 연산이라고 부른다. 이 분류가 뒤에서 볼 최적화가 가능한지 아닌지를 가른다.

    중간 연산 하나가 단계 객체 하나다

    "중간 연산은 새 스트림을 돌려준다"는 말을 그대로 확인해 보자. 각 연산의 반환값을 변수에 받아 클래스 이름과 동일성을 찍는다.

    import java.util.List;
import java.util.stream.Stream;

public class Stages {
    public static void main(String[] args) {
        List list = List.of(1, 2, 3, 4, 5, 6);
        Stream s0 = list.stream();
        Stream s1 = s0.filter(n -> n % 2 == 0);
        Stream s2 = s1.map(n -> n * 10);
        Stream s3 = s2.sorted();

        System.out.println(s0.getClass().getName());
        System.out.println(s1.getClass().getName());
        System.out.println(s2.getClass().getName());
        System.out.println(s3.getClass().getName());
        System.out.println(s0 == s1);

        try {
            s0.map(n -> n);                      // 이미 filter가 붙은 s0에 또 연산을 붙인다
        } catch (IllegalStateException e) {
            System.out.println("ISE: " + e.getMessage());
        }
        System.out.println(s3.toList());
        try {
            s3.toList();                         // 이미 실행된 파이프라인을 다시 실행한다
        } catch (IllegalStateException e) {
            System.out.println("ISE2: " + e.getMessage());
        }
    }
}

    네 변수가 가리키는 객체가 모두 다르다. list.stream()이 돌려준 것은 ReferencePipeline$Head, 곧 파이프라인의 머리 단계다. filter는 ReferencePipeline$2, map은 ReferencePipeline$3을 돌려줬다. 이름의 $2, $3은 익명 클래스라는 뜻이다(번호는 컴파일러가 소스 순서대로 붙이므로 JDK 버전이 바뀌면 달라질 수 있다. 여기 결과는 OpenJDK 21 기준이다). sorted는 별도 클래스 SortedOps$OfRef의 객체다. 파이프라인은 이렇게 단계(stage) 객체들의 사슬이다.

    이 클래스들의 공통 조상은 java.util.stream.AbstractPipeline이다. OpenJDK 21 소스에서 이 클래스가 단계마다 들고 있는 핵심 필드는 다음과 같다.

    필드뜻
    sourceStage사슬의 머리(Head) 단계. 머리 자신은 자기 자신을 가리킨다.
    previousStage바로 앞 단계. 머리는 null.
    nextStage바로 뒤 단계. 다음 연산이 붙을 때 채워진다.
    depth머리로부터의 거리. 머리는 0, 첫 중간 연산은 1.
    sourceSpliterator / sourceSupplier소스(머리에만 있음). 원소를 꺼내는 Spliterator 또는 그것을 나중에 만들어 줄 Supplier.
    sourceOrOpFlags, combinedFlags이 단계의 연산 플래그, 그리고 소스부터 이 단계까지 누적한 스트림 플래그(뒤에서 다룬다).
    linkedOrConsumed이 단계 뒤에 이미 다른 단계가 붙었거나 최종 연산이 실행되었으면 true.

    중간 연산이 새 단계를 만들 때 호출되는 AbstractPipeline의 생성자는 하는 일이 단순하다. 먼저 앞 단계의 linkedOrConsumed가 이미 true면 IllegalStateException("stream has already been operated upon or closed")을 던진다. 아니면 앞 단계의 linkedOrConsumed를 true로, 앞 단계의 nextStage를 자신으로 설정하고, 자신의 previousStage, sourceStage, depth(앞 단계 + 1)를 채운 뒤 플래그를 합친다. 원소를 읽는 코드는 어디에도 없다. 위 실행 결과의 첫 번째 예외가 바로 이 생성자에서 났다. s0에는 이미 filter 단계가 붙어 있었으므로 s0.map(...)이 만들려던 새 단계의 생성자가 예외를 던진 것이다. 중간 연산만 호출했는데도 예외가 난다는 점에 주목하자. "같은 스트림에 두 갈래 파이프라인을 붙이는 것"을 생성 시점에 막는 장치다.

    두 번째 예외는 최종 연산 쪽 검사다. 최종 연산이 실행되면 마지막 단계의 linkedOrConsumed가 true가 되고, 소스의 Spliterator 참조는 머리 단계에서 꺼내진 뒤 null로 지워진다. 같은 단계에 최종 연산을 다시 부르면 linkedOrConsumed 검사에서 같은 문구의 예외가 난다. 패키지 문서도 "최종 연산이 수행된 뒤 스트림 파이프라인은 소비된 것으로 간주되어 다시 쓸 수 없다"고 적고 있다.

    Stream의 API 문서는 재사용을 감지하면 구현이 IllegalStateException을 던질 "수 있다(may)"고만 쓰고, 어떤 연산은 새 스트림 대신 자기 자신을 돌려주기 때문에 모든 재사용을 감지하지는 못할 수 있다고 덧붙인다. OpenJDK에서 parallel()과 sequential()이 그런 예로, 머리 단계의 병렬 여부만 바꾸고 this를 돌려준다. 예외가 안 났다고 재사용이 허용된 것은 아니다. 규칙은 "스트림은 한 번만 연산한다"이다.

    힙에 생긴 사슬

    소스: Spliterator가 원소를 꺼내 준다

    머리 단계가 들고 있는 Spliterator(splittable iterator)는 스트림이 소스에서 원소를 꺼내는 통로다. Collection 인터페이스의 디폴트 메서드 stream()은 OpenJDK 21에서 StreamSupport.stream(spliterator(), false) 한 줄이고, StreamSupport.stream은 그 Spliterator와 거기서 뽑은 플래그로 ReferencePipeline.Head를 만든다. ArrayList는 stream()을 재정의하지 않으므로 이 경로를 그대로 탄다. API 문서에 따르면 Spliterator의 tryAdvance는 남은 원소가 있으면 하나에 대해 동작을 수행하고 true를, 없으면 false를 돌려주고, forEachRemaining은 남은 원소 전부에 대해 현재 스레드에서 순서대로 동작을 수행한다. 앞의 것은 "한 개씩, 멈출 수 있게", 뒤의 것은 "끝까지 한 번에"다. 이 두 메서드가 뒤에서 볼 단락 최적화의 갈림길이 된다. 이름에 "split"이 들어 있는 이유인 trySplit(원소를 둘로 나누기)은 병렬 스트림의 핵심이므로 10회에서 다룬다.

    Spliterator는 자기 소스의 성질을 특성(characteristics) 비트로 알려 준다. 몇 가지 소스의 특성을 찍어 보면 다음과 같다(OpenJDK 21 실행 결과).

    ArrayList  [ORDERED, SIZED, SUBSIZED]
HashSet    [DISTINCT, SIZED]
TreeSet    [ORDERED, DISTINCT, SORTED, SIZED]
Stream.iterate(1, n -> n + 1)  [ORDERED, IMMUTABLE]

    ArrayList는 순서가 있고(ORDERED) 크기를 정확히 안다(SIZED). HashSet은 중복이 없고(DISTINCT) 크기를 알지만 순서는 없다. TreeSet은 순서, 중복 없음, 정렬됨(SORTED), 크기까지 모두 안다. 무한 수열인 Stream.iterate는 크기를 모른다. 이 비트들이 파이프라인의 플래그로 옮겨져 뒤에서 볼 "건너뛰기" 최적화의 근거가 된다.

    지연 연산: 최종 연산이 없으면 아무 일도 없다

    이제 이 회차의 중심 주제다. 패키지 문서는 이렇게 설명한다. filter() 같은 중간 연산을 실행해도 실제로 거르는 일은 일어나지 않고, 순회될 때 조건에 맞는 원소를 내놓을 새 스트림이 만들어질 뿐이며, 파이프라인 소스의 순회는 최종 연산이 실행되어야 시작된다. 이것을 지연 연산(lazy evaluation)이라고 부른다. 람다 안에 출력문을 넣어 직접 확인한다.

    import java.util.List;
import java.util.stream.Stream;

public class LazyDemo {
    public static void main(String[] args) {
        List list = List.of(1, 2, 3, 4, 5, 6);
        Stream lazy = list.stream()
                .filter(n -> { System.out.println("filter " + n); return n % 2 == 0; })
                .map(n -> { System.out.println("map " + n); return n * 10; });
        System.out.println("파이프라인 조립 끝");

        List result = lazy.toList();
        System.out.println("결과 " + result);
    }
}

    둘째, 실행 순서가 "모든 원소를 거른 다음 모두 바꾸기"가 아니다. 1을 거르고(탈락), 2를 거르고 곧바로 2를 바꾸고, 3을 거르고(탈락), 4를 거르고 곧바로 4를 바꾼다. 원소 하나가 파이프라인의 끝까지 내려간 다음에 다음 원소가 출발한다. 같은 일을 단계마다 리스트를 만드는 즉시(eager) 방식으로 하면 순서가 이렇게 된다.

    위 표의 번호는 스트림이 실제로 일을 한 순서다. 번호가 열(원소)을 따라 위에서 아래로 내려간 뒤 오른쪽으로 이동한다. 즉시 방식이었다면 번호가 첫 행을 왼쪽에서 오른쪽으로 다 채운 뒤 둘째 행으로 내려갔을 것이다. 세로 방향 처리에서는 한 원소에 대한 계산이 끝나면 그 원소의 중간 값을 더 들고 있을 필요가 없다. 그래서 단계 사이에 중간 컬렉션이 필요 없고, 원하는 결과를 얻은 순간 멈출 수도 있다.

    소스도 늦게 묶인다: 늦은 바인딩과 간섭 금지

    지연은 연산에만 해당하지 않는다. 소스의 내용이 확정되는 시점도 늦춰진다. 패키지 문서가 드는 예를 실행해 보면 이렇다.

    List l = new ArrayList<>(List.of("one", "two"));
Stream sl = l.stream();          // 스트림을 먼저 얻고
l.add("three");                          // 그다음 소스를 고친다
System.out.println(sl.collect(Collectors.joining(" ")));   // one two three

    스트림을 얻은 뒤에 추가한 "three"까지 결과에 들어간다. 이유는 ArrayList의 Spliterator가 늦은 바인딩(late-binding)이기 때문이다. API 문서는 늦은 바인딩 Spliterator를 "생성될 때가 아니라 처음 순회하거나, 처음 분할하거나, 처음 크기 추정을 요청받을 때 소스에 묶이는" 것으로 정의한다. OpenJDK 21의 ArrayList.ArrayListSpliterator는 순회 끝 위치(fence)와 기대 변경 횟수(expectedModCount)를 생성 시점에 정하지 않고 -1로 비워 두었다가, 처음 쓰일 때 그때의 size와 modCount로 채운다. l.stream() 시점에는 Spliterator 객체만 생겼고, 크기 2는 기록되지 않았다. collect가 순회를 시작할 때 크기를 읽으니 3이다.

    반대로 최종 연산이 실행되는 동안 소스를 고치면 안 된다. 패키지 문서는 이것을 간섭 금지(non-interference)라고 부르며, 소스가 동시성 컬렉션이 아니라면 파이프라인 실행 중 소스를 수정하면 예외나 잘못된 결과가 생길 수 있다고 경고한다. 순차 스트림에도 적용되는 규칙이다.

    List l2 = new ArrayList<>(List.of("a", "b", "c"));
l2.stream().forEach(x -> { if (x.equals("a")) l2.add("z"); });
// java.util.ConcurrentModificationException

    OpenJDK 21의 ArrayListSpliterator.forEachRemaining을 보면 이 예외가 언제 나는지 정확히 알 수 있다. 순회를 시작할 때 크기(3)와 modCount를 지역 변수에 잡아 두고, 배열의 0번부터 2번까지 동작을 모두 수행한 다음 한 번만 modCount를 비교한다. 소스 주석에도 성능을 위해 forEach에서는 검사를 끝에서 한 번만 한다고 적혀 있다. 그래서 위 코드는 "a", "b", "c" 세 원소 모두에 대해 람다를 실행하고("z"는 순회 범위 밖이다), 리스트에는 "z"가 실제로 추가된 상태에서, 마지막에 예외를 던진다. 예외가 났다고 해서 부수 효과가 일어나지 않은 것이 아니다. API 문서가 이 감지를 "최선의 노력(best-effort)"이라고 부르는 이유이기도 하다. 감지되지 않는 간섭도 있을 수 있다.

    한 층 아래로: 최종 연산 안에서 일어나는 일

    지연 연산이 어떻게 구현되는지 OpenJDK 21 소스로 따라가 보자. 핵심 부품은 java.util.stream.Sink라는 패키지 전용 인터페이스다. Consumer를 확장하며, 핵심 메서드는 네 개다(기본형 스트림용 accept(int) 같은 오버로드는 여기서 생략한다).

    메서드역할
    begin(long size)원소를 받기 전에 한 번 호출된다. 보낼 원소 수를 알면 그 수, 모르면 -1.
    accept(T t)원소 하나를 받는다. Consumer.accept 그 자체다.
    end()모든 원소를 보낸 뒤 한 번 호출된다.
    cancellationRequested()"더 이상 원소를 보내지 않아도 된다"면 true. 기본값은 false.

    각 중간 연산의 단계 클래스는 opWrapSink(int flags, Sink downstream)이라는 메서드를 구현한다. "아래쪽(downstream) Sink를 받아, 원소를 받으면 이 단계의 일을 한 뒤 아래쪽에 넘기는 Sink를 만들어 돌려준다"는 뜻이다. OpenJDK 21의 filter 단계가 만드는 Sink를 풀어 쓰면 이렇다.

    // ReferencePipeline.filter가 만드는 Sink (OpenJDK 21 소스를 요약)
new Sink.ChainedReference(downstream) {
    public void begin(long size) {
        downstream.begin(-1);              // 몇 개가 통과할지 모르므로 크기를 -1로 알린다
    }
    public void accept(P_OUT u) {
        if (predicate.test(u))             // 캡처해 둔 Predicate로 검사하고
            downstream.accept(u);          // 통과하면 아래쪽으로 밀어 넣는다
    }
};

// ReferencePipeline.map이 만드는 Sink
new Sink.ChainedReference(downstream) {
    public void accept(P_OUT u) {
        downstream.accept(mapper.apply(u)); // 바꾼 값을 아래쪽으로 밀어 넣는다
    }
};

    Sink.ChainedReference는 begin, end, cancellationRequested를 모두 아래쪽 Sink에 그대로 전달하도록 구현된 추상 클래스다. 그래서 각 단계는 자기 일, 대개 accept 하나만 정의하면 된다. 최종 연산 toList()가 호출되면 OpenJDK 21에서는 다음 순서로 일이 진행된다.

    3단계가 이 구조의 열쇠다. 단계 객체의 사슬은 머리 → filter → map 순서로 연결되어 있지만, Sink는 거꾸로 만들어야 한다. filter Sink를 만들려면 "통과한 원소를 넘길 아래쪽"이 이미 있어야 하기 때문이다. 그래서 끝에서부터 만들고, 완성된 사슬은 filter Sink → map Sink → 최종 Sink 방향으로 원소를 밀어 보낸다. 이 사슬이 최종 연산 시점에야 만들어진다는 것이 곧 지연 연산이다. 중간 연산 호출 시점에는 "어떤 Sink를 만들지"를 아는 단계 객체만 있고, 원소를 받을 Sink는 아직 존재하지 않는다.

    import java.util.ArrayList;
import java.util.List;
import java.util.function.Consumer;
import java.util.function.Function;
import java.util.function.Predicate;

public class MiniPipe {

    // 원소를 하나씩 "밀어 넣는" 수신자. JDK의 java.util.stream.Sink를 흉내 낸 것이다.
    interface Sink extends Consumer {
        default boolean cancellationRequested() { return false; }
    }

    // S: 소스 원소 타입, T: 이 단계가 내보내는 원소 타입
    static final class Pipe {
        private final List source;
        private final Function, Sink> wrap; // 아래쪽 Sink를 받아 소스 쪽 Sink를 만든다

        private Pipe(List source, Function, Sink> wrap) {
            this.source = source;
            this.wrap = wrap;
        }

        static  Pipe of(List source) {
            return new Pipe<>(source, sink -> sink);
        }

        Pipe filter(Predicate predicate) {
            return new Pipe<>(source, down -> wrap.apply(new Sink() {
                public void accept(T t) { if (predicate.test(t)) down.accept(t); }
                public boolean cancellationRequested() { return down.cancellationRequested(); }
            }));
        }

         Pipe map(Function mapper) {
            return new Pipe(source, down -> wrap.apply(new Sink() {
                public void accept(T t) { down.accept(mapper.apply(t)); }
                public boolean cancellationRequested() { return down.cancellationRequested(); }
            }));
        }

        Pipe limit(long max) {
            return new Pipe<>(source, down -> wrap.apply(new Sink() {
                long remaining = max;
                public void accept(T t) { if (remaining > 0) { remaining--; down.accept(t); } }
                public boolean cancellationRequested() { return remaining == 0 || down.cancellationRequested(); }
            }));
        }

        // 최종 연산: 여기서 처음으로 Sink 사슬이 만들어지고 소스를 순회한다
        List toList() {
            List result = new ArrayList<>();
            Sink head = wrap.apply(result::add);
            for (S s : source) {
                if (head.cancellationRequested()) break;
                head.accept(s);
            }
            return result;
        }
    }

    public static void main(String[] args) {
        Pipe p = Pipe.of(List.of(1, 2, 3, 4, 5, 6))
            .filter(n -> { System.out.println("filter " + n); return n % 2 == 0; })
            .map(n -> { System.out.println("map " + n); return n * 10; })
            .limit(2);
        System.out.println("파이프라인 조립 끝");
        System.out.println(p.toList());
    }
}

Pipe.of는 "받은 Sink를 그대로 돌려주는" 항등 함수를 가진 머리 단계다. filter는 새 Pipe를 만들면서 함수 down -> wrap.apply(filterSink(down))을 넣는다. 즉 "아래쪽 Sink를 받으면, 그것을 감싼 filter Sink를 만들고, 그 filter Sink를 이전 단계의 wrap에 넘긴다". map과 limit도 똑같은 모양이다. 이 시점까지 만들어진 것은 함수 객체(람다)뿐이고, Sink는 하나도 없다. 그래서 "파이프라인 조립 끝"이 가장 먼저 찍힌다.

    toList()에서 wrap.apply(result::add)를 부르는 순간 연쇄가 풀린다. limit 단계의 wrap이 결과 Sink를 감싼 limit Sink를 만들어 map 단계의 wrap에 넘기고, map 단계의 wrap이 그것을 감싼 map Sink를 만들어 filter 단계의 wrap에 넘기고, filter 단계가 filter Sink를 만들어 머리의 항등 함수에 넘긴다. 마지막 단계부터 머리 쪽으로 거슬러 올라가며 Sink를 만드는 것, JDK의 wrapSink와 똑같은 순서다. 반환된 head는 filter Sink이고, 반복문은 소스 원소를 하나씩 거기에 밀어 넣는다. 4를 넣었을 때 limit Sink의 remaining이 0이 되고, 다음 바퀴의 head.cancellationRequested()가 filter → map → limit으로 전달되어 true가 되므로 반복이 멈춘다. 5와 6은 꺼내지도 않는다.

    JDK와 다른 점도 하나 있다. MiniPipe는 원소마다 언제나 cancellationRequested()를 묻지만, JDK는 파이프라인에 단락 연산이 있을 때만 그렇게 하고, 없으면 묻지 않고 forEachRemaining으로 한 번에 순회한다. 묻는 일 자체도 비용이기 때문이다. 이 구분은 단락을 다루는 절에서 다시 본다.

    지연 연산과 최적화 1: 루프 융합과 연산 순서

    패키지 문서는 지연 처리의 이점을 이렇게 요약한다. filter-map-sum 같은 파이프라인에서 거르기, 바꾸기, 합하기를 최소한의 중간 상태로 데이터에 대한 한 번의 통과로 합칠(fused) 수 있고, 필요하지 않을 때 모든 데이터를 검사하지 않을 수 있다. 첫 번째 이점을 루프 융합(loop fusion)이라고 부른다. 단계가 몇 개든 소스는 한 번만 순회되고, 원소 하나가 Sink 사슬을 통과하는 동안 단계 사이에 원소를 쌓아 둘 곳이 없다.

    즉시 방식과 비교해 무엇을 아끼는지 구체적으로 세어 보자. 원소가 N개이고 상태 없는 단계가 k개라고 하자. 단계마다 리스트를 만드는 즉시 방식은 단계 경계마다 중간 리스트를 하나씩 만들고, 각 리스트는 그 단계를 통과한 원소 수만큼 커진다. 원소 수가 줄지 않는 map만 이어진다면 최대 N칸짜리 리스트가 k개 생기는 셈이다(앞 리스트는 다음 단계가 끝나면 가비지가 되지만, 적어도 두 개는 동시에 살아 있다). 스트림은 상태 없는 단계만 있다면 단계 수와 관계없이 단계 사이에 원소를 쌓지 않는다. 최종 결과를 담는 공간만 필요하다. 단계 수만큼 생기는 것은 Sink 객체 k개뿐이고, 이것은 N과 상관없는 고정 비용이다. 이 차이는 실행 시간보다 메모리와 GC 부담에서 더 분명하게 드러난다. 중간 리스트는 만들어졌다가 곧 버려지는 객체이고, 할당이 많을수록 GC가 치워야 할 일도 늘어난다.

    이 회차는 스트림과 반복문의 속도를 수치로 비교하지 않는다. 결과는 JIT 컴파일 여부, 원소 수, 람다 호출의 인라이닝 같은 조건에 크게 좌우되고, 신뢰할 만한 비교는 JMH 같은 도구로 따로 측정해야 한다. 여기서 말하는 것은 구조적 사실뿐이다. 스트림은 단계마다 단계 객체와 Sink 객체, 그리고 원소마다 인터페이스 메서드 호출을 거치는 비용을 치르고, 그 대가로 중간 컬렉션과 불필요한 계산을 없앤다.

    순서는 라이브러리가 바꿔 주지 않는다

    루프 융합이 공짜로 모든 낭비를 없애 주지는 않는다. 다음 두 파이프라인은 같은 결과를 내지만 map의 호출 횟수가 다르다.

    int[] calls = new int[2];
List a = Stream.of("a", "bb", "ccc", "dddd", "eeeee")
        .map(s -> { calls[0]++; return s.toUpperCase(); })   // 먼저 바꾸고
        .filter(s -> s.length() >= 4)                         // 나중에 거른다
        .toList();
List b = Stream.of("a", "bb", "ccc", "dddd", "eeeee")
        .filter(s -> s.length() >= 4)                         // 먼저 거르고
        .map(s -> { calls[1]++; return s.toUpperCase(); })   // 나중에 바꾼다
        .toList();
System.out.println(a + " " + b + " mapCalls=" + calls[0] + "," + calls[1]);
// [DDDD, EEEEE] [DDDD, EEEEE] mapCalls=5,2

    먼저 바꾸면 다섯 원소 모두를 대문자로 바꾼 뒤 세 개를 버린다. 먼저 거르면 살아남은 두 원소만 바꾼다. 데이터베이스의 옵티마이저는 SQL의 WHERE 조건을 조인보다 먼저 적용하는 식으로 연산 순서를 바꿔 주지만, 스트림 라이브러리는 그러지 않는다. 이유는 앞에서 본 구조에 있다. wrapSink는 단계 사슬을 선언된 순서 그대로 감쌀 뿐이고, 라이브러리 입장에서 filter와 map에 넘어온 람다는 내용을 들여다볼 수 없는 객체다. map이 원소를 어떻게 바꾸는지 모르니 filter를 앞으로 옮겨도 결과가 같은지 판단할 수 없다. 연산 순서의 책임은 파이프라인을 쓰는 사람에게 있다. 원소 수를 줄이는 연산(filter, limit, distinct)은 가능한 한 앞에, 비싼 변환은 뒤에 둔다.

    지연 연산과 최적화 2: 단락, 필요한 만큼만 처리하고 멈추기

    두 번째 이점은 필요한 만큼만 보는 것이다. 첫 번째 짝수를 찾아 10배 하는 파이프라인을 실행해 보자.

    Optional first = List.of(1, 2, 3, 4, 5, 6).stream()
        .filter(n -> { System.out.println("filter " + n); return n % 2 == 0; })
        .map(n -> { System.out.println("map " + n); return n * 10; })
        .findFirst();
System.out.println("found " + first);
    filter 1
filter 2
map 2
found Optional[20]

    여섯 원소 중 두 개만 보고 끝났다. 3부터 6까지는 filter조차 거치지 않았다. 세로 방향 처리 덕분에 2가 결과 Sink에 도착한 시점에 다른 원소는 아직 출발하지 않았고, 라이브러리는 거기서 순회를 멈출 수 있다. findFirst가 돌려준 Optional은 8회에서 다룬다.

    OpenJDK 21에서 이 멈춤은 이렇게 구현된다. findFirst, findAny, anyMatch·allMatch·noneMatch, 그리고 limit과 takeWhile(자바 9)은 자기 연산 플래그에 SHORT_CIRCUIT 비트를 세운다. 최종 연산의 플래그는 실행 직전에 마지막 단계의 누적 플래그에 합쳐진다. copyInto는 이 비트를 보고 길을 나눈다. 비트가 없으면 begin → forEachRemaining → end로 한 번에 끝까지 순회하고, 비트가 있으면 copyIntoWithCancel로 가서 머리 단계의 forEachWithCancel을 부른다. 그 본체는 한 줄이다.

    // ReferencePipeline.forEachWithCancel (OpenJDK 21)
do { } while (!(cancelled = sink.cancellationRequested()) && spliterator.tryAdvance(sink));

    원소를 하나 꺼내기(tryAdvance) 전에 매번 Sink 사슬에 "그만해도 되는가"를 묻는다. 이 질문은 Sink.ChainedReference의 기본 구현을 따라 filter Sink → map Sink → 최종 Sink로 전달된다. findFirst의 Sink는 값을 하나 받은 순간부터 cancellationRequested()에 true를 답한다. limit(n)의 Sink는 남은 개수가 0이 되면 true를 답한다. 그 답이 사슬을 거슬러 올라오면 반복이 멈춘다. 앞에서 만든 MiniPipe가 한 일과 같다.

    무한 스트림이 끝나는 이유와 끝나지 않는 경우

    단락은 무한 스트림을 다룰 수 있게 해 준다. Stream.iterate(1, n -> n + 1)은 1, 2, 3, … 을 끝없이 만들어 내는 소스다.

    List multiplesOf3 = Stream.iterate(1, n -> n + 1)
        .filter(n -> n % 3 == 0)
        .limit(3)
        .toList();
System.out.println(multiplesOf3);   // [3, 6, 9]

    추적해 보면 소스는 1부터 9까지 아홉 개만 만든다. 3, 6이 통과할 때마다 limit Sink의 남은 개수가 2, 1로 줄고, 9가 통과해 0이 되면 다음 바퀴의 cancellationRequested()가 true를 돌려준다. 10은 만들어지지 않는다. 즉시 방식이었다면 첫 단계에서 무한 수열 전체를 리스트에 담으려다 끝나지 않았을 것이다.

    하지만 패키지 문서가 강조하듯 파이프라인에 단락 연산이 있다는 것은 무한 스트림 처리가 유한 시간에 끝나기 위한 필요조건일 뿐 충분조건은 아니다. 다음 코드는 findFirst가 있어도 끝나지 않는다.

    Stream.generate(() -> "x")          // "x"를 끝없이 만든다
      .filter(String::isEmpty)       // 빈 문자열만 통과 → 아무것도 통과하지 못한다
      .findFirst();                  // 첫 원소가 영원히 오지 않는다

    findFirst의 Sink는 값을 받아야 멈춤을 요청하는데, filter가 모든 원소를 막으므로 값이 끝내 도착하지 않는다. 데몬 스레드에서 이 코드를 돌리고 2초 뒤에 확인해 보면 여전히 실행 중이다. 단락은 "멈출 수 있는 기회"를 줄 뿐, 그 기회가 오는지는 데이터와 조건에 달려 있다.

    지연 연산과 최적화 3: 상태 있는 연산은 장벽이다

    세로 방향 처리에는 예외가 있다. sorted는 원소 하나만 보고는 그 원소를 내보낼 수 없다. 패키지 문서의 말대로 스트림의 모든 원소를 보기 전에는 정렬 결과를 하나도 만들 수 없다. 출력으로 확인한다.

    List sorted = Stream.of(3, 1, 2)
        .peek(n -> System.out.println("before " + n))
        .sorted()
        .peek(n -> System.out.println("after " + n))
        .toList();
System.out.println(sorted);
    before 3
before 1
before 2
after 1
after 2
after 3
[1, 2, 3]

    sorted 앞의 단계는 모든 원소를 먼저 통과시키고, sorted 뒤의 단계는 그다음에야 일한다. OpenJDK 21의 정렬 Sink(SortedOps.RefSortingSink, 크기를 알면 배열을 쓰는 SizedRefSortingSink)를 보면 이유가 보인다. begin에서 버퍼(리스트 또는 배열)를 만들고, accept는 원소를 버퍼에 넣기만 하고 아래쪽에 아무것도 넘기지 않는다. end가 호출되어야 버퍼를 정렬하고, 그제야 아래쪽 Sink에 begin을 부른 뒤 원소를 차례로 accept로 넘기고 end를 부른다. 하나의 Sink 사슬이 정렬 단계를 경계로 "모으기 구간"과 "내보내기 구간" 둘로 나뉘는 것이다. 이런 연산을 장벽(barrier)이라고 생각하면 된다. 장벽 앞에서는 루프 융합이 유지되지만 장벽에서 모든 원소가 버퍼에 쌓이므로, 정렬 단계는 원소 수만큼의 메모리를 쓴다.

    sorted 앞에서는 원소가 하나씩 내려와 버퍼에 쌓이기만 하고, 소스가 끝나 end()가 호출된 뒤에야 정렬된 원소가 아래 단계로 흘러간다는 것을 보여 준다. A horizontal flow diagram, flat vector, white background.     장벽 뒤의 단락은 장벽 앞을 줄이지 못한다

    정렬 뒤에 findFirst를 두면 어떻게 될까.

    Optional min = Stream.of(3, 1, 2)
        .peek(n -> System.out.println("before " + n))
        .sorted()
        .peek(n -> System.out.println("after " + n))
        .findFirst();
System.out.println(min);

before 1
before 2
after 1
Optional[1]

    "before"는 세 번 모두 찍혔고 "after"는 한 번만 찍혔다. 가장 작은 원소가 무엇인지는 모든 원소를 본 뒤에야 알 수 있으니 장벽 앞은 끝까지 돌아야 한다. OpenJDK 21의 정렬 Sink는 이를 이렇게 처리한다. 정렬 Sink의 cancellationRequested()는 언제나 false를 돌려주므로 위쪽 순회는 멈추지 않는다. 대신 "누군가 멈춤 여부를 물었다"는 사실(cancellationRequestedCalled)을 기록해 둔다. 이 질문은 파이프라인에 단락 연산이 있을 때만 오기 때문이다. end에서 정렬된 원소를 내보낼 때 이 기록이 있으면 원소마다 아래쪽의 cancellationRequested()를 확인하고 true가 되면 그만 보낸다. 그래서 "after 1" 뒤에 멈췄다.

    이 구조에서 바로 나오는 결론이 있다. 무한 스트림 뒤의 sorted는 끝나지 않는다. Stream.iterate(1, n -> n + 1).sorted().limit(3)은 limit이 뒤에 있어도 정렬 Sink가 멈춤 요청을 위로 전달하지 않으므로 소스를 끝없이 버퍼에 모으기만 한다. 반대로 Stream.iterate(1, n -> n + 1).limit(3).sorted()는 limit이 먼저 원소를 세 개로 자르므로 [1, 2, 3]을 내고 끝난다. 상태 있는 연산과 단락 연산의 상대 위치가 결과를 가른다.

    모든 상태 있는 연산이 완전한 장벽은 아니다. distinct도 상태 있는 연산이지만, OpenJDK 21의 순차 구현은 본 적 있는 원소를 HashSet에 기록하면서 처음 보는 원소는 곧바로 아래쪽에 넘긴다. 원소를 붙잡아 두지 않으므로 세로 방향 처리가 유지되고, 뒤에 limit이 있으면 무한 스트림에서도 멈출 수 있다. 다만 기록하는 집합은 서로 다른 원소 수만큼 커진다. "상태 있음"은 "앞서 본 원소의 정보를 들고 있다"는 뜻이고, 그 정보가 전부인지(sorted) 일부인지(distinct)는 연산마다 다르다.

    지연 연산과 최적화 4: 스트림 플래그로 일을 건너뛰기

    지연 연산이 주는 마지막 기회는 실행 전에 파이프라인 전체를 볼 수 있다는 점이다. 즉시 방식에서는 filter가 실행될 때 뒤에 무엇이 올지 모른다. 지연 방식에서는 최종 연산이 호출되는 순간 소스부터 최종 연산까지가 모두 확정되어 있다. OpenJDK 21은 이 정보를 스트림 플래그(StreamOpFlag)로 요약한다. 여기서 볼 플래그는 다섯 가지다(OpenJDK 21에는 skip·limit이 세우는 SIZE_ADJUSTING까지 여섯 가지가 정의되어 있다).

    플래그뜻예
    DISTINCT원소에 중복이 없다HashSet, TreeSet 소스 / distinct()가 세운다
    SORTED원소가 자연 순서로 정렬되어 있다TreeSet 소스 / sorted()가 세운다
    ORDERED원소에 정해진 만남 순서(encounter order)가 있다List, 배열, TreeSet 소스
    SIZED원소 수를 정확히 안다대부분의 컬렉션 소스 / filter가 지운다
    SHORT_CIRCUIT단락 연산이 있다limit, findFirst, anyMatch가 세운다

    StreamOpFlag의 소스 주석에 따르면 SHORT_CIRCUIT(과 SIZE_ADJUSTING)을 뺀 네 플래그는 Spliterator의 같은 이름 특성에서 나온다. 앞에서 찍어 본 특성이 머리 단계의 플래그가 되는 것이다. 각 중간 연산은 자기가 보존하지 못하는 성질의 플래그를 지우고, 보장하는 성질의 플래그를 세운다. 소스에서 확인한 몇 가지를 정리하면 이렇다.

    • filter: NOT_SIZED. 몇 개가 통과할지 모르므로 크기 정보를 지운다(앞에서 본 filter Sink가 downstream.begin(-1)을 부르는 것도 같은 이유다).
    • map: NOT_SORTED | NOT_DISTINCT. 바뀐 값이 여전히 정렬되어 있는지, 중복이 없는지 알 수 없다. 원소 수는 그대로이므로 SIZED는 남긴다.
    • sorted(): IS_ORDERED | IS_SORTED. sorted(comparator)는 IS_ORDERED | NOT_SORTED다. SORTED 플래그는 자연 순서 정렬만 뜻하기 때문이다.
    • distinct(): IS_DISTINCT | NOT_SIZED.

    실제로 TreeSet 스트림에 map을 붙이고 특성을 찍으면 [ORDERED, SIZED]만 남고, List 스트림에 filter를 붙이면 [ORDERED]만 남는다. 이 플래그를 이용해 OpenJDK 21이 일을 건너뛰는 경우를 세 가지 확인해 보자.

    이미 정렬된 소스의 sorted()

    비교 횟수를 세는 클래스를 만들어 TreeSet 스트림을 정렬해 본다.

    import java.util.List;
import java.util.TreeSet;

public class Sorted {
    static int compares = 0;

    record Box(int v) implements Comparable {
        public int compareTo(Box o) {
            compares++;
            return Integer.compare(v, o.v);
        }
    }

    public static void main(String[] args) {
        TreeSet set = new TreeSet<>(List.of(new Box(3), new Box(1), new Box(2)));
        compares = 0;
        System.out.println(set.stream().sorted().toList() + " compares=" + compares);

        List plain = List.of(new Box(3), new Box(1), new Box(2));
        compares = 0;
        System.out.println(plain.stream().sorted().toList() + " compares=" + compares);

        compares = 0;
        System.out.println(set.stream().map(b -> b).sorted().toList() + " compares=" + compares);

    TreeSet 스트림의 sorted()는 비교를 한 번도 하지 않았다. SortedOps.OfRef.opWrapSink는 위쪽 플래그에 SORTED가 있고 자기도 자연 순서 정렬이면 받은 Sink를 그대로 돌려준다. 정렬 Sink를 아예 만들지 않으니 장벽도 생기지 않는다. List 소스는 정렬되어 있다는 보장이 없으므로 실제로 정렬했다. 세 번째 줄이 흥미롭다. 원소를 그대로 돌려주는 map(b -> b) 하나를 끼웠을 뿐인데 정렬이 다시 일어났다. 라이브러리는 이 람다가 항등 함수인지 알 수 없으므로 map은 무조건 SORTED를 지운다. 이미 정렬된 원소를 다시 정렬하느라 비교를 두 번 했다(비교 횟수 자체는 정렬 알고리즘 구현에 따라 다르다. 중요한 것은 0인지 아닌지다).

    중복이 없는 소스의 distinct()

    DistinctOps의 opWrapSink도 같은 방식이다. 위쪽 플래그에 DISTINCT가 있으면(예: HashSet 소스) 받은 Sink를 그대로 돌려주어 HashSet을 만들지 않는다. SORTED만 있으면 정렬된 입력에서는 중복이 이웃해 있다는 점을 이용해 집합 대신 "바로 앞 원소" 하나만 기억하는 Sink를 쓴다. 둘 다 아니면 앞에서 본 HashSet 기반 Sink를 쓴다.

    크기를 아는 소스의 count()

long c1 = list.stream().peek(n -> System.out.println("peek " + n)).count();
long c2 = list.stream().peek(n -> System.out.println("peek2 " + n)).map(n -> n + 1).count();
long c3 = list.stream().filter(n -> n > 4).peek(n -> System.out.println("peek3 " + n)).count();
System.out.println(c1 + " " + c2 + " " + c3);

    첫 두 파이프라인에서는 peek이 한 번도 실행되지 않았다. map의 람다도 실행되지 않았다. OpenJDK 21의 count()(ReduceOps.makeRefCounting)는 실행 전에 파이프라인의 출력 크기를 정확히 알 수 있는지 먼저 묻고, 알 수 있으면 원소를 하나도 꺼내지 않고 그 크기를 돌려준다. peek과 map은 원소 수를 바꾸지 않으므로 SIZED가 살아 있고, 답은 리스트의 크기 6이다. 세 번째 파이프라인은 filter가 SIZED를 지웠으므로 실제로 순회해서 세야 했다. 이 동작은 구현의 선택이지만 API 문서가 허용한 것이다. 자바 9부터 count()의 API 문서에는 "소스에서 바로 개수를 계산할 수 있으면 구현은 파이프라인을 실행하지 않을 수 있고, 그 경우 소스 원소를 순회하지도 중간 연산을 평가하지도 않는다"는 API Note가 붙어 있고, 자바 8의 문서에는 이 문장이 없다. 같은 코드가 자바 8과 이후 버전에서 다른 출력을 낼 수 있다는 뜻이다.

    이 장의 핵심

    지연 연산이 주는 최적화는 세 겹이다. 단계를 한 번의 순회로 합치는 융합, 필요한 결과가 나오면 멈추는 단락, 그리고 실행 전에 파이프라인 전체의 성질(플래그)을 보고 단계 자체를 생략하는 것. 셋 다 "최종 연산 전까지 아무것도 하지 않는다"는 한 가지 결정에서 나온다. 반대로 라이브러리는 람다의 내용을 모르므로 연산 순서를 바꾸지 않고, 상태 있는 연산의 장벽을 없애지 못한다. 이 둘은 파이프라인을 쓰는 사람의 몫이다.

    한 층 더 아래: 스트림 플래그는 2비트씩 묶인 정수 하나다

    앞 절에서 "map이 SORTED를 지운다", "sorted()가 SORTED를 세운다"고 말했다. 이 말이 실제로 무엇을 하는지, 곧 플래그가 메모리에서 어떤 모양이고 단계를 지날 때 어떤 계산으로 합쳐지는지를 OpenJDK 21의 java.util.stream.StreamOpFlag 소스로 확인해 보자. 결론부터 말하면 단계마다 들고 있는 플래그는 int 하나이고, 성질 하나가 그 안의 2비트를 차지한다.

    왜 1비트가 아니라 2비트인가. StreamOpFlag의 소스 주석이 이유를 설명한다. 소스를 기술할 때는 "이 성질이 있다"만 말하면 되지만, 연산을 기술할 때는 그 성질을 "보존한다", "새로 세운다(inject)", "지운다(clear)" 중 무엇인지 말해야 한다. 세 가지 이상의 상태를 담으려면 성질마다 2비트가 필요하다. 소스에 정의된 비트 패턴은 셋이다.

    2비트 값소스의 상수 이름뜻코드에서 만드는 상수
    01SET_BITS성질이 있다 / 성질을 세운다IS_SORTED, IS_SIZED …
    10CLEAR_BITS성질을 지운다NOT_SORTED, NOT_SIZED …
    11PRESERVE_BITS보존한다(앞 단계의 값을 그대로 둔다)마스크 계산에 쓰인다
    00(없음)연산이 이 성질에 대해 아무 말도 하지 않는다

    각 성질의 자리는 enum 생성자에 넘기는 위치 번호에 2를 곱한 비트다. DISTINCT는 위치 0, SORTED는 1, ORDERED는 2, SIZED는 3, SHORT_CIRCUIT은 12, SIZE_ADJUSTING은 13이다. 그래서 "성질이 있다"(01)를 그 자리에 놓은 값은 DISTINCT 0x1, SORTED 0x4, ORDERED 0x10, SIZED 0x40, SHORT_CIRCUIT 0x01000000, SIZE_ADJUSTING 0x04000000가 된다. 여기서 눈여겨볼 점이 있다. 앞의 네 값은 Spliterator 인터페이스의 특성 상수와 똑같다. 실제로 Spliterator.DISTINCT, SORTED, ORDERED, SIZED를 출력하면 0x1, 0x4, 0x10, 0x40이 나온다. Spliterator의 특성 상수는 모두 짝수 비트에 놓여 있고, 스트림 플래그는 각 상수 바로 위의 홀수 비트를 "지운다" 표시로 쓴다. 덕분에 Spliterator 특성을 스트림 플래그로 바꾸는 StreamOpFlag.fromCharacteristics는 비트를 옮기는 계산 없이 마스크와 AND 한 번으로 끝난다. 소스 주석에는 위치 4~7(0x100, 0x400, 0x1000, 0x4000)을 Spliterator의 NONNULL, IMMUTABLE, CONCURRENT, SUBSIZED 자리로 일부러 비워 두었다는 설명도 있다.

    합치는 규칙: 말한 연산이 이기고, 침묵하면 보존된다

    단계가 붙을 때 AbstractPipeline의 생성자는 combinedFlags = StreamOpFlag.combineOpFlags(opFlags, previousStage.combinedFlags)를 계산한다. 그 본체는 다음 두 메서드다.

    // java.util.stream.StreamOpFlag (OpenJDK 21)
private static int getMask(int flags) {
    return (flags == 0)
           ? FLAG_MASK
           : ~(flags | ((FLAG_MASK_IS & flags) << 1) | ((FLAG_MASK_NOT & flags) >> 1));
}

static int combineOpFlags(int newStreamOrOpFlags, int prevCombOpFlags) {
    return (prevCombOpFlags & StreamOpFlag.getMask(newStreamOrOpFlags)) | newStreamOrOpFlags;
}

    getMask는 새 연산이 01이나 10을 적어 둔 2비트 칸을 11로 채운 뒤 전체를 뒤집는다(11로 채우는 계산은 FLAG_MASK_IS·FLAG_MASK_NOT가 덮는 네 스트림 성질 칸에만 적용된다. SHORT_CIRCUIT·SIZE_ADJUSTING 칸은 세운 비트만 꺼지지만, 이 두 성질에는 10이 쓰이지 않으므로 결과는 같다). 그러면 새 연산이 무언가를 말한 칸은 00, 아무 말도 하지 않은 칸은 11인 마스크가 된다. combineOpFlags는 이전 누적값을 이 마스크와 AND 해서 새 연산이 말한 칸만 비운 뒤, 새 연산의 비트를 OR로 써 넣는다. 결과는 단순하다. 연산이 세우거나 지운 성질은 그 값으로 덮어쓰이고, 언급하지 않은 성질은 앞 단계의 값이 그대로 남는다. 파이프라인 전체로 보면 "그 성질에 대해 마지막으로 말한 연산이 이긴다".

    머리 단계는 조금 다르게 시작한다. 생성자는 combinedFlags = (~(sourceOrOpFlags << 1)) & StreamOpFlag.INITIAL_OPS_VALUE를 계산한다(소스 주석에 combineOpFlags(sourceFlags, INITIAL_OPS_VALUE)를 최적화한 식이라고 적혀 있다). INITIAL_OPS_VALUE는 네 가지 스트림 성질 칸이 모두 11인 값이다. 소스에 있는 성질은 왼쪽으로 한 칸 민 뒤 뒤집어 그 칸의 "지운다" 비트를 끄므로 01이 되고, 소스에 없는 성질은 11로 남는다. 성질을 판정하는 isKnown(flags)는 (flags & preserve) == set, 즉 그 칸이 정확히 01일 때만 참이다. 그러니 머리 단계의 11은 "보존"이라기보다 "알 수 없음"으로 읽으면 된다.

    규칙을 실제 값으로 확인해 보자. AbstractPipeline은 패키지 전용 클래스이므로 실험용으로 --add-opens를 주고 리플렉션으로 각 단계의 sourceOrOpFlags(이 단계 자신의 플래그)와 combinedFlags(누적값)를 읽는다. 내부 필드를 읽는 것은 구조를 관찰하기 위한 실험일 뿐, 실제 코드에서 할 일은 아니다.
