    이 회차의 질문: 이미 배포된 인터페이스에 메서드를 더할 수 있는가

    자바 8에 람다와 스트림을 넣으려던 사람들은 곤란한 문제 하나를 안고 있었다. 람다가 쓸모 있으려면 컬렉션이 람다를 받아야 한다. list.forEach(x -> ...), list.removeIf(x -> ...), collection.stream() 같은 메서드가 Collection, List, Iterable에 있어야 한다는 뜻이다. 그런데 Collection과 List는 자바 1.2부터, Iterable은 자바 5부터 존재했고, JDK 바깥의 수많은 라이브러리와 애플리케이션이 이것을 직접 구현해 왔다. 인터페이스에 추상 메서드를 하나 더하면, 세상의 모든 구현 클래스가 그 메서드를 새로 구현해야 한다.

    OpenJDK의 JEP 126(Lambda Expressions & Virtual Extension Methods)은 이 상황을 "널리 쓰이는 인터페이스에 메서드를 추가할 수 없다는 오랜 제약"이라고 부르고, 그 원인을 소스 호환성 문제로 짚는다. 그리고 해법으로 가상 확장 메서드(virtual extension method)를 내놓는다. Collection이나 List 같은 기존 인터페이스에 구현이 딸린 메서드를 넣으면 기존 구현 클래스도 새로운 프로그래밍 방식에 참여할 수 있고, JDK 안팎의 구현 클래스는 그 기본 구현을 재정의해 더 빠르거나 특화된 구현을 줄 수 있다는 것이다. 이 기능이 자바 8에 디폴트 메서드(default method)라는 이름으로 들어왔다.

    이 회차는 먼저 "인터페이스에 메서드를 더하면 무엇이 깨지는가"를 실제로 깨뜨려 보면서 확인한다. 깨지는 방식은 두 가지다. 소스를 다시 컴파일하는 쪽과, 이미 컴파일된 클래스 파일을 그대로 실행하는 쪽이다. 그다음 디폴트 메서드의 문법 규칙, 클래스 파일에서의 모습, JVM이 실행할 메서드를 고르는 절차를 차례로 본다. 후반부는 여러 인터페이스가 같은 디폴트 메서드를 가질 때 무엇이 실행되는지를 정하는 해석 규칙, 분리 컴파일 때문에 실행 중에 드러나는 충돌, 표준 라이브러리의 실제 사례, 그리고 디폴트 메서드를 올바르게 쓰는 기준을 다룬다. 4회에서 람다는 디폴트 메서드를 재정의할 수 없고 다중 상속 규칙은 이번 회차에서 다룬다고 예고했는데, 그 이야기가 여기서 이어진다.

    이 장의 핵심

    디폴트 메서드는 "인터페이스를 고칠 때 기존 구현 클래스를 깨뜨리지 않기 위한" 장치다. 몸체가 있는 메서드는 인터페이스의 클래스 파일에만 들어가고 구현 클래스에 복사되지 않는다. 호출 시점에 JVM이 수신 객체의 클래스에서 출발해 상위 클래스를 먼저, 그다음 상위 인터페이스 중 가장 구체적인 것을 찾아 실행할 메서드를 고른다. 이 선택 순서가 곧 "클래스가 이긴다", "더 구체적인 인터페이스가 이긴다", "그래도 모호하면 직접 고른다"라는 언어의 세 규칙이 된다. 디폴트 메서드는 행동의 다중 상속을 허용하지만 상태의 다중 상속은 허용하지 않는다. 그래서 좋은 디폴트 메서드는 필드 없이 인터페이스의 다른 추상 메서드 위에 쌓인다.

    인터페이스에 메서드를 추가하면 무엇이 깨지는가

    호환성에는 두 종류가 있다. 소스 호환성(source compatibility)은 기존 소스 코드가 새 버전의 라이브러리와 함께 다시 컴파일되는가를 묻는다. 바이너리 호환성(binary compatibility)은 이미 컴파일된 .class 파일이 다시 컴파일하지 않고도 새 버전의 라이브러리와 링크되어 실행되는가를 묻는다. 자바 언어 명세(JLS) 13장은 바이너리 호환성을 다루는 장인데, 여기서 중요한 것은 기준이 "링크 시점에 오류가 생기는가"라는 점이다. 링크는 문제없이 되어도 실제로 그 메서드를 호출하는 순간 오류가 날 수 있다.

    직접 깨뜨려 보자. 라이브러리 1판에 인사 인터페이스가 있고, 사용자는 그것을 구현한 클래스를 만들어 컴파일해 두었다.

    // 1판 라이브러리: Greeting.java
public interface Greeting {
    String hello();
}

// 사용자 코드: OldGreeter.java (1판에 맞춰 컴파일해 둔 상태)
public class OldGreeter implements Greeting {
    public String hello() { return "hello"; }
}

    라이브러리 2판이 bye()라는 추상 메서드를 추가한다. 그리고 새 기능을 쓰는 코드가 등장한다.

    // 2판 라이브러리: Greeting.java
public interface Greeting {
    String hello();
    String bye();          // 새로 추가한 추상 메서드
}

// 2판을 쓰는 새 코드: Main.java
public class Main {
    public static void main(String[] args) {
        Greeting g = new OldGreeter();
        System.out.println(g.hello());
        System.out.println(g.bye());
    }
}

    먼저 사용자가 2판으로 올리면서 OldGreeter.java까지 다시 컴파일하는 경우다. 결과는 컴파일 오류다. 소스 호환성이 깨진 것이다.

    v1/OldGreeter.java:1: error: OldGreeter is not abstract and does not override abstract method bye() in Greeting
public class OldGreeter implements Greeting {
       ^
1 error

    이번에는 OldGreeter.class는 1판으로 컴파일된 그대로 두고, Greeting과 Main만 2판으로 컴파일해서 실행한다. 다른 회사가 만든 jar 안의 클래스가 이런 처지다. 그 jar는 다시 컴파일되지 않는다.

    hello
Exception in thread "main" java.lang.AbstractMethodError: Receiver class OldGreeter does not define or inherit an implementation of the resolved method 'abstract java.lang.String bye()' of interface Greeting.
	at Main.main(Main.java:5)

    두 가지를 눈여겨보자. 첫째, hello가 출력되었다. OldGreeter 클래스는 문제없이 로딩되고 링크되었으며 객체도 만들어졌다. JVM은 클래스를 로딩할 때 "추상 메서드를 전부 구현했는가"를 검사하지 않는다. 그런 검사는 컴파일러의 일이다. JLS §13.5.4가 "인터페이스에 abstract 메서드를 추가하는 것은 기존 바이너리와의 호환성을 깨지 않는다"고 적은 이유가 이것이다. 링크 오류가 나지 않으니 정의상 바이너리 호환이다. 둘째, 오류는 bye()를 실제로 호출하는 줄(Main.java:5)에서 났다. JVM이 OldGreeter에서 bye의 구현을 찾았지만 클래스에도, 상위 클래스에도, 상위 인터페이스에도 몸체가 있는 메서드가 없었다. JVM 명세(JVMS)의 invokeinterface 설명은 이렇게 선택된 메서드가 없고 추상이 아닌 후보도 없으면 AbstractMethodError를 던진다고 정한다.

    정리하면 추상 메서드 추가는 "소스는 깨지고, 바이너리는 링크는 되지만 호출하면 터지는" 변경이다. 라이브러리를 만드는 쪽에서 보면 어느 쪽도 받아들일 수 없다. 특히 JDK는 하위 호환성을 가장 중요한 약속으로 삼으므로, Collection에 추상 메서드를 하나 더하는 일은 불가능했다.

    이제 같은 자리에 디폴트 메서드를 넣고 Greeting과 Main만 다시 컴파일해 보자. OldGreeter.class는 여전히 1판 그대로다.

    public interface Greeting {
    String hello();
    default String bye() { return "bye (default)"; }
}
    hello
bye (default)

    이번에는 한 글자도 고치지 않은 옛 클래스가 새 메서드에 응답한다. OldGreeter.java를 다시 컴파일해도 오류가 나지 않는다. 소스와 바이너리 양쪽의 호환성이 지켜진 것이다. 어떻게 이것이 가능한지는 뒤에서 클래스 파일과 JVM의 메서드 선택 절차를 보며 확인한다.

    자바 8 이전의 우회책과 그 한계

    디폴트 메서드가 없던 시절에도 라이브러리 설계자는 기능을 더해야 했다. 흔히 쓰던 방법은 세 가지였고, 각각 분명한 한계가 있었다.

    첫째는 유틸리티 클래스의 정적 메서드다. java.util.Collections의 Javadoc은 이 클래스가 "컬렉션에 대해 동작하거나 컬렉션을 반환하는 정적 메서드만으로 이루어져 있다"고 소개한다. Collections.sort(list), Collections.reverse(list)가 그 예다. 인터페이스를 건드리지 않으니 호환성 문제는 없다. 대신 정적 메서드는 다형적이지 않다. Collections.sort는 자기가 받은 리스트가 배열 기반인지 연결 리스트인지 모른 채 한 가지 알고리즘으로 처리해야 하고, 특정 구현이 더 나은 방법을 알고 있어도 끼어들 수 없다. 기능이 타입 바깥에 있으니 list.을 찍어서 찾을 수도 없다.

    둘째는 골격 구현(skeletal implementation) 추상 클래스다. AbstractCollection의 Javadoc은 이 클래스가 "Collection 인터페이스의 골격 구현을 제공해 구현에 드는 노력을 최소화한다"고 적는다. 추상 클래스에는 구현이 있는 메서드를 얼마든지 더할 수 있으므로, 이 클래스를 상속한 구현은 새 메서드를 자동으로 얻는다. 하지만 자바 클래스는 상위 클래스를 하나만 가질 수 있다. 다른 클래스를 이미 상속해서 인터페이스를 직접 구현한 클래스에는 이 방법이 닿지 않는다. 그리고 인터페이스 타입으로 들고 있는 변수에서는 추상 클래스에만 있는 메서드를 부를 수 없다.

    셋째는 확장 인터페이스를 새로 만드는 것이다. 기존 인터페이스를 상속한 새 인터페이스에 메서드를 더하는 방식인데, 그러면 사용하는 쪽은 받은 객체가 새 인터페이스를 구현했는지 instanceof로 확인한 뒤 갈라 써야 한다. 판이 바뀔 때마다 인터페이스 이름이 늘어나고, 기존 API의 매개변수와 반환 타입은 여전히 옛 인터페이스라서 새 기능을 쓰려면 매번 형 변환이 필요하다.

    디폴트 메서드는 이 세 방법의 장점을 합친다. 메서드가 인터페이스 안에 있으니 타입만 보고 찾을 수 있고 다형적이다(구현 클래스가 재정의할 수 있다). 몸체가 있으니 옛 구현 클래스도 그대로 동작한다. 상위 클래스가 무엇이든 인터페이스만 구현했으면 혜택을 받는다. 그 결과로 흐름이 뒤집힌 곳이 있다. JDK 21의 Collections.sort(list, c)는 본문이 list.sort(c); 한 줄이고, Javadoc의 구현 노트도 "이 구현은 List.sort(Comparator)에 위임한다"고 적는다. 예전에는 유틸리티의 정적 메서드가 정렬 알고리즘을 쥐고 있었다면, 이제는 인터페이스의 디폴트 메서드가 기본 알고리즘을 갖고 ArrayList 같은 구현이 그것을 재정의하며, 정적 메서드는 그쪽으로 넘겨 줄 뿐이다.

    디폴트 메서드 소개: 문법과 규칙

    JLS §9.4는 디폴트 메서드를 "인터페이스에 default 제어자로 선언한 인스턴스 메서드"로 정의한다. 몸체는 언제나 블록이고, 그 블록은 메서드를 재정의하지 않은 구현 클래스에 대한 기본 구현이 된다. 같은 절은 디폴트 메서드가 클래스에 선언하는 구체 메서드(concrete method)와도, 상속도 재정의도 되지 않는 private 인터페이스 메서드와도 구별된다고 덧붙인다. 이 구별은 뒤의 다중 상속 규칙에서 중요해진다.

    public interface Shape {
    double area();                       // 추상 메서드 (암묵적으로 public abstract)

    default String describe() {          // 디폴트 메서드 (자바 8)
        return label() + " 넓이=" + area();
    }

    private String label() {             // private 인스턴스 메서드 (자바 9)
        return getClass().getSimpleName();
    }

    static Shape unit() {                // 정적 메서드 (자바 8)
        return () -> 1.0;
    }
}

    이 인터페이스 하나에 자바 21 인터페이스가 가질 수 있는 메서드 종류가 다 들어 있다. area()는 제어자가 없으므로 암묵적으로 추상이다. JLS §9.4는 private, default, static이 없는 인터페이스 메서드는 암묵적으로 abstract이고 몸체 대신 세미콜론을 갖는다고 정한다. describe()는 디폴트 메서드이고, 인터페이스의 다른 메서드인 label()과 area()를 불러 결과를 만든다. label()은 자바 9의 JEP 213(Milling Project Coin)이 들여온 private 인터페이스 메서드다. JEP 213은 이것이 자바 8 때 검토되었다가 빠졌고, 인터페이스의 추상이 아닌 메서드들이 코드를 공유할 수 있게 하려고 넣는다고 설명한다. unit()은 정적 메서드로, 람다를 이용해 Shape의 구현 객체를 만들어 돌려주는 팩토리다. Shape는 추상 메서드가 area 하나뿐이므로 함수형 인터페이스이기도 하다. 2회에서 본 대로 디폴트·정적·private 메서드는 추상 메서드 수에 들어가지 않는다.

    허용되지 않는 조합

    JLS §9.4는 인터페이스 메서드에 붙일 수 있는 제어자를 public, private, abstract, default, static, strictfp와 애너테이션으로 한정한다. 그리고 abstract·default·static 가운데 둘 이상을 함께 쓰는 것, private을 abstract나 default와 함께 쓰는 것을 컴파일 오류로 정한다(private static은 허용된다). final, synchronized, protected는 목록에 아예 없다. 클래스 파일 수준에서도 JVMS §4.6은 인터페이스 메서드에 ACC_PROTECTED, ACC_FINAL, ACC_SYNCHRONIZED, ACC_NATIVE 플래그를 허용하지 않는다.

    Object의 메서드는 디폴트로 정의할 수 없다

    JLS §9.4.1.2는 디폴트 메서드가 Object의 private이 아닌 메서드와 오버라이드 동등(override-equivalent)하면 컴파일 오류라고 정하고, 그 이유를 "인터페이스를 구현하는 모든 클래스는 그 메서드의 구현을 이미 물려받기 때문"이라고 설명한다.

    정적 메서드는 상속되지 않는다

    인터페이스의 정적 메서드는 반드시 인터페이스 이름으로 불러야 한다. JLS §8.4.8의 상속 규칙에서 클래스가 상위 인터페이스로부터 물려받는 것은 추상 메서드와 디폴트 메서드뿐이고, 정적 메서드는 들어 있지 않다. ArrayList는 List를 구현하지만 List.of를 물려받지 않는다.

    디폴트 메서드 안의 this와 클래스 파일

    디폴트 메서드 본문의 this는 무엇일까. 인터페이스는 객체를 만들 수 없으니, this는 언제나 그 인터페이스를 구현한 클래스의 객체다. 위 Shape를 구현하는 두 클래스와 실행 코드를 보자.

    public class Square implements Shape {
    public double area() { return 4.0; }
}

public class Circle implements Shape {
    private final double r;
    public Circle(double r) { this.r = r; }
    public double area() { return Math.PI * r * r; }

    @Override
    public String describe() {
        return "원: " + Shape.super.describe();   // 디폴트 구현을 직접 호출
    }
}

public class Main {
    public static void main(String[] args) {
        Shape s = new Square();
        System.out.println(s.describe());      // 인터페이스 타입으로 호출
        Square q = new Square();
        System.out.println(q.describe());      // 클래스 타입으로 호출
        System.out.println(new Circle(1).describe());
        System.out.println(Shape.unit().area());
    }
}

    첫 줄을 따라가 보자. s.describe()는 Shape의 디폴트 메서드를 실행한다. 그 안에서 label()이 getClass().getSimpleName()을 부르는데, this가 Square 객체이므로 "Square"가 나온다. 이어서 area()를 부르면 Square.area()가 실행되어 4.0이 된다. 디폴트 메서드는 "인터페이스가 정한 뼈대 안에서 구현 클래스가 채운 메서드를 부르는" 구조, 즉 템플릿 메서드 패턴을 상태 없이 표현한다. 세 번째 줄의 Circle은 describe()를 재정의하면서 Shape.super.describe()로 디폴트 구현을 불렀다. 그 디폴트 구현 안에서 다시 this는 Circle 객체이므로 "Circle"과 원의 넓이가 나온다.

    Main과 Circle의 호출 지점을 javap -c로 보면, 같은 디폴트 메서드가 부르는 방식에 따라 네 가지 명령어로 나타난다.

    소스명령어상수 풀 참조
    s.describe() (Shape 타입 변수)invokeinterfaceInterfaceMethod Shape.describe
    q.describe() (Square 타입 변수)invokevirtualMethod Square.describe
    Shape.super.describe() (Circle 안)invokespecialInterfaceMethod Shape.describe

JVM이 이 기호 참조를 해석할 때 Square와 그 상위 클래스에서 찾지 못하면 상위 인터페이스까지 찾기 때문이다. 세 번째 줄의 invokespecial은 상위 클래스의 메서드를 super.m()으로 부를 때와 같은 명령어다. 가상 호출이 아니라 "바로 이 인터페이스의 이 구현"을 지정해 부른다는 뜻이다. 그래서 Circle이 describe를 재정의했어도 무한 재귀에 빠지지 않고 Shape의 몸체가 실행된다. 정적 메서드 호출은 invokestatic이지만 참조 종류가 Methodref가 아니라 InterfaceMethodref라는 점이 클래스의 정적 메서드와 다르다.

    JVM은 실행할 메서드를 어떻게 찾는가: 해석과 선택

    JVM이 가상 호출을 처리하는 과정은 두 단계로 나뉜다. 해석(resolution)은 상수 풀의 기호 참조(Square.describe:()Ljava/lang/String; 같은 문자열)를 실제 메서드 하나에 연결하는 일이다. 호출 지점의 정적 타입을 기준으로 하고, 한 번 해석된 결과는 다시 쓴다. 선택(selection)은 호출할 때마다 스택에 놓인 수신 객체의 실제 클래스를 보고, 해석된 메서드를 재정의한 메서드 가운데 실제로 실행할 것을 고르는 일이다. 디폴트 메서드를 위해 자바 8에서 두 단계 모두에 "상위 인터페이스를 찾는다"는 단계가 들어갔다.

    가장 구체적인 상위 인터페이스 메서드

    두 단계가 공통으로 쓰는 개념이 JVMS §5.4.3.3에 정의된 가장 구체적인 상위 인터페이스 메서드(maximally-specific superinterface method)다. 클래스 C에 대해 이름과 디스크립터가 주어졌을 때 다음 조건을 모두 만족하는 메서드를 말한다.

    • C의 상위 인터페이스(직접이든 간접이든)에 선언되어 있다.
    • 주어진 이름과 디스크립터로 선언되어 있다.
    • ACC_PRIVATE도 ACC_STATIC도 아니다.
    • 그 메서드가 인터페이스 I에 선언되어 있을 때, I의 하위 인터페이스에 선언된 다른 후보가 없다.

    마지막 조건이 핵심이다. 하위 인터페이스가 같은 메서드를 다시 선언했으면 상위 인터페이스의 것은 후보에서 빠진다. "더 구체적인 쪽만 남긴다"는 뜻이고, 이것이 뒤에서 볼 두 번째 해석 규칙의 JVM 쪽 근거다.

    해석 절차

    JVMS §5.4.3.3의 메서드 해석(Methodref, 즉 invokevirtual이 쓰는 클래스 메서드 참조)은 다음 순서로 진행한다. C가 인터페이스이면 IncompatibleClassChangeError다. 아니면 먼저 C와 그 상위 클래스를 차례로 올라가며 이름과 디스크립터가 같은 메서드를 찾는다. 거기서 찾지 못하면 상위 인터페이스로 넘어간다. 가장 구체적인 상위 인터페이스 메서드 가운데 ACC_ABSTRACT가 없는 것이 정확히 하나면 그것을 고른다. 그렇지 않고 상위 인터페이스 어딘가에 private도 static도 아닌 같은 메서드가 있으면 그중 하나를 임의로 고른다. 그것도 없으면 해석이 실패한다.

    앞의 q.describe()에 적용해 보자. 기호 참조의 클래스는 Square다. Square에 describe() 선언이 없고, 상위 클래스 Object에도 없다. 상위 인터페이스로 가면 후보는 Shape.describe 하나이고 추상이 아니다. 해석은 Shape.describe로 끝난다.

    다중 상속 해석 규칙: 세 가지 원칙

    오라클의 자바 튜토리얼은 다중 상속을 세 가지로 나눈다. 여러 클래스로부터 필드를 물려받는 상태의 다중 상속, 여러 곳으로부터 메서드 정의를 물려받는 구현의 다중 상속, 여러 인터페이스를 구현해 여러 타입이 되는 타입의 다중 상속이다. 자바가 클래스를 하나만 상속하게 한 이유 중 하나는 상태의 다중 상속이 일으키는 문제(어느 상위 클래스의 생성자가 같은 필드를 초기화하는가)를 피하기 위해서다. 인터페이스는 인스턴스 필드를 가질 수 없으므로 상태 문제는 생기지 않는다. 그런데 튜토리얼이 적듯이 디폴트 메서드는 구현의 다중 상속의 한 형태를 들여왔다. 한 클래스가 같은 이름의 디폴트 메서드를 가진 인터페이스 둘을 구현하면, 어느 쪽을 쓸지 정하는 규칙이 필요하다.

    규칙은 세 가지이고, 위에서부터 차례로 적용한다. 다음 예제 하나에 세 규칙과 경계 사례 하나를 모두 담았다.

    public class Rules {
    // 규칙 1: 클래스가 이긴다
    interface Greeter { default String greet() { return "Greeter"; } }
    static class Base { public String greet() { return "Base"; } }
    static class Child extends Base implements Greeter { }

    // 규칙 2: 더 구체적인 인터페이스가 이긴다 (다이아몬드)
    interface Animal { default String sound() { return "Animal"; } }
    interface Dog extends Animal { default String sound() { return "Dog"; } }
    interface Pet extends Animal { }
    static class Puppy implements Dog, Pet { }
    static class Puppy2 implements Animal, Dog { }

    // 규칙 3: 직접 고른다
    interface Walker { default String move() { return "walk"; } }
    interface Swimmer { default String move() { return "swim"; } }
    static class Duck implements Walker, Swimmer {
        @Override public String move() {
            return Walker.super.move() + "+" + Swimmer.super.move();
        }
    }

    // 경계 사례: 상위 클래스가 물려받은 디폴트 vs 더 구체적인 인터페이스
    static class Plain implements Animal { }
    static class Hound extends Plain implements Dog { }

    public static void main(String[] args) {
        System.out.println(new Child().greet());
        System.out.println(new Puppy().sound());
        System.out.println(new Puppy2().sound());
        System.out.println(new Duck().move());
        System.out.println(new Hound().sound());
    }
}

    규칙 1: 클래스가 이긴다

    Child는 상위 클래스 Base에서 greet()을, 인터페이스 Greeter에서 같은 시그니처의 디폴트 메서드를 받는다. 결과는 Base다. JLS §8.4.8은 클래스가 상위 인터페이스로부터 디폴트 메서드를 물려받는 조건 중 하나로 "직접 상위 클래스로부터 물려받은 구체 메서드 가운데 시그니처가 같은(서브시그니처인) 것이 없을 것"을 든다. Base.greet()이 있으므로 Greeter.greet()은 Child에 아예 상속되지 않는다. JVM 쪽에서는 앞의 선택 순서 2단계(상위 클래스 사슬)가 3단계(인터페이스)보다 먼저라서 같은 결론이 나온다. 이 규칙이 있어야 인터페이스에 디폴트 메서드를 추가해도 같은 이름의 메서드를 이미 가진 기존 클래스의 동작이 바뀌지 않는다. Object의 메서드를 디폴트로 정의할 수 없는 것도 이 규칙의 결과였다.

    규칙 2: 더 구체적인 인터페이스가 이긴다

    Puppy는 Dog와 Pet을 구현하고, 둘 다 Animal을 상속한다. 전형적인 다이아몬드 구조다. Pet은 sound()를 다시 선언하지 않았으므로 Pet을 통해 오는 것은 Animal.sound이고, Dog를 통해 오는 것은 Dog.sound다. Dog가 Animal의 하위 인터페이스이고 그 메서드를 재정의했으므로, Animal.sound는 JVMS 정의의 마지막 조건("하위 인터페이스에 선언된 다른 후보가 없을 것")에 걸려 후보에서 빠진다. 남는 것은 Dog.sound 하나다. 언어 쪽에서는 JLS §8.4.8의 마지막 조건, "다른 상위 타입의 메서드가 이 메서드를 재정의하고 있으면 상속하지 않는다"가 같은 일을 한다. Puppy2처럼 Animal을 굳이 함께 나열해도 결과는 같다. JLS §8.4.8.4는 같은 메서드 선언이 여러 경로로 상속될 수 있지만 그것만으로는 아무 문제도 일으키지 않는다고 적는다.

    마지막 줄의 Hound는 함정이 많은 사례다. 상위 클래스 Plain은 Animal을 구현해서 sound()를 가지고 있고, Hound는 추가로 Dog를 구현한다. "클래스가 이긴다"를 적용하면 상위 클래스 쪽인 "Animal"이 나올 것 같지만 결과는 "Dog"다. 첫 번째 규칙의 "클래스"는 클래스에 선언된 메서드를 뜻하기 때문이다. JLS §9.4는 디폴트 메서드가 클래스에 선언하는 구체 메서드와 구별된다고 명시한다. Plain이 가진 sound()는 Animal의 디폴트 메서드를 물려받은 것일 뿐이므로, §8.4.8에서 상위 클래스로부터 물려받는 "구체 메서드"에 해당하지 않는다. 그다음에는 규칙 2가 적용되어 Dog.sound가 Animal.sound를 재정의하고 있으니 Dog.sound만 상속된다. JVM의 선택 절차로 보아도 같다. Hound, Plain, Object 어디에도 sound의 선언이 없으므로 3단계로 넘어가고, 가장 구체적인 상위 인터페이스 메서드는 Dog.sound 하나다.

    규칙 3: 그래도 모호하면 직접 고른다

    Walker와 Swimmer는 서로 아무 관계가 없고 둘 다 move()를 디폴트로 갖는다. 어느 쪽이 더 구체적이지도 않으니 규칙 1, 2로는 결정할 수 없다. 이때 클래스가 move()를 재정의하지 않으면 컴파일 오류다.

    JLS §8.4.8.4는 클래스가 디폴트 메서드를 물려받는데 그것과 오버라이드 동등한 다른 메서드도 함께 물려받으면 컴파일 오류라고 정한다. 해결은 직접 재정의하는 것이고, 재정의한 메서드 안에서 인터페이스이름.super.메서드() 문법으로 원하는 디폴트 구현을 부를 수 있다. 예제의 Duck은 둘을 모두 불러 "walk+swim"을 만들었다. 한쪽만 고를 수도 있고, 완전히 새로 구현할 수도 있다. 컴파일러가 강제하는 것은 "모호한 채로 두지 말라"는 것뿐이다.

    세 규칙만으로 정리되지 않는 경우들이 있다. 각각 컴파일러가 어떻게 반응하는지 보자.

    디폴트는 남의 추상 메서드를 대신 구현해 주지 않는다

    interface Walker { default String move() { return "walk"; } }

    Walker.move에 몸체가 있으니 Robot.move의 구현으로 써 줄 것 같지만 그렇지 않다. JLS §8.4.8.4는 디폴트 메서드와 오버라이드 동등한 다른 메서드를 함께 물려받는 것을, 그 다른 메서드가 추상이든 디폴트든 오류로 본다(인터페이스끼리 상속할 때도 §9.4.1.3이 같은 규칙을 둔다). Walker와 Robot은 서로를 모른다. Walker.move를 쓴 사람은 Robot.move의 계약을 본 적이 없으니, 그것이 Robot의 계약을 만족한다고 볼 근거가 없다. 구현 클래스가 명시적으로 재정의해서 "이 구현이 두 계약을 모두 만족한다"고 선언해야 한다. 같은 상황에서 클래스를 abstract로 선언해도 오류는 사라지지 않는다. 이때 javac는 "inherits abstract and default for move() from types ..."라는 문구로 보고한다.

    interface Shape { default double area() { return 0; } }
abstract class Base { public abstract double area(); }

    클래스 쪽에서 온 메서드가 이기는 규칙은 그 메서드가 추상이어도 적용된다. JLS §8.4.8.4는 상위 클래스에 선언된 추상 메서드가 있으면 디폴트-추상 충돌 규칙의 예외로 두면서, "상위 클래스 계층에서 온 추상이라는 주장이 사실상 디폴트 메서드를 이긴다"고 설명한다. Base가 "area는 하위 클래스가 반드시 구현해야 한다"고 선언했으니, 인터페이스의 디폴트가 그 요구를 몰래 채워 버리면 안 된다는 판단이다. 명세는 이 예외가 추상 메서드가 모두 인터페이스에서 온 경우에는 적용되지 않는다고 덧붙인다. 그것이 바로 앞의 Android 사례다.

    하위 인터페이스는 디폴트를 다시 추상으로 만들 수 있다

    interface Animal { default String sound() { return "..."; } }
interface Cat extends Animal { String sound(); }   // 재추상화
class Kitty implements Cat { }
    E10.java:3: error: Kitty is not abstract and does not override abstract method sound() in Cat
class Kitty implements Cat { }
^
1 error

    하위 인터페이스가 상위 인터페이스의 디폴트 메서드를 몸체 없이 다시 선언하면, 그 메서드는 이 인터페이스부터 다시 추상이 된다. 이를 재추상화(re-abstraction)라고 부른다. 상위 인터페이스의 기본 구현이 하위 인터페이스의 의미에는 맞지 않을 때, 구현 클래스가 반드시 자기 구현을 주도록 강제하는 수단이다. JVM 쪽에서 보면 Cat.sound가 Animal.sound보다 구체적인 후보이고 추상이므로, 옛 바이너리가 재정의 없이 실행되면 3단계에서 추상이 아닌 후보가 없어 AbstractMethodError가 난다.

    X.super.m()은 직접 상위 인터페이스만, 가려지지 않은 것만

    분리 컴파일이 만드는 충돌: 실행 중에 드러나는 다이아몬드

    규칙 3의 충돌은 컴파일러가 잡아 준다. 하지만 컴파일러는 자기가 컴파일하는 소스만 본다. 이미 컴파일된 클래스가 나중에 바뀐 인터페이스를 만나면 충돌은 실행 중에야 드러난다. 앞에서 추상 메서드 추가를 깨뜨려 본 것처럼, 이번에는 디폴트 메서드 추가를 깨뜨려 보자.

public interface Walker { }
public interface Swimmer { }
public class Duck implements Walker, Swimmer { }

public interface Swimmer { default String move() { return "swim"; } }

JLS §13.5.7은 바로 이 상황을 다룬다. 디폴트 메서드를 추가하거나 추상 메서드를 디폴트로 바꾸는 것은 기존 바이너리와의 호환성을 깨지 않지만, 호출의 한정 타입이 두 인터페이스 I와 J의 하위 타입이고 둘 다 같은 시그니처의 디폴트 메서드를 선언했으며 어느 쪽도 다른 쪽의 하위 인터페이스가 아니면 IncompatibleClassChangeError가 날 수 있다고 적는다. 그리고 "링크 시점에는 오류를 만들지 않으므로 바이너리 호환 변경이다. 컴파일 시점이나 호출 시점에 오류를 만들더라도 그렇다"고 덧붙인다.

    첫 번째 스택 트레이스에서 이상한 줄을 보자. at Duck.move(Duck.java)다. 그런데 javap -p Duck으로 열어 보면 Duck.class에는 생성자밖에 없다. 소스에도 클래스 파일에도 없는 Duck.move가 스택에 찍힌 것이다. 이것은 HotSpot이 메서드 선택이 실패하는 자리를 발견하면, 그 메서드가 호출되었을 때 올바른 예외를 던지도록 오버패스(overpass) 메서드라는 합성 메서드를 만들어 두기 때문이다. 스택 트레이스가 보여 주듯 이 메서드는 Duck에 속한 것으로 나타나지만 클래스 파일에는 없다. JVMS의 invokeinterface 런타임 예외 항목은 선택된 메서드가 없고 추상이 아닌 가장 구체적인 후보가 여럿이면 IncompatibleClassChangeError를 던지라고 정한다. 이 실험의 결과는 명세와 다르다. 위의 JDK-8356942가 바로 이 문제("invokeinterface Throws AbstractMethodError Instead of IncompatibleClassChangeError")다. 설명에 따르면 JDK 10 시절의 다른 수정(JDK-8186092)이 인터페이스의 itable을 초기화할 때 오버패스 메서드를 건너뛰게 만들었고, 그래서 invokeinterface 경로에서는 오버패스가 던질 ICCE 대신 AME가 나왔다. 수정은 2025년 7월 JDK 메인 라인에 통합되었고 jdk25 브랜치에도 백포트되었다. 이 실험에 쓴 OpenJDK 21.0.13에서는 여전히 AME가 나온다.

    HotSpot 안에서: 디폴트 메서드는 클래스를 로딩할 때 미리 골라 둔다

    앞에서는 JVMS §5.4.6의 선택 절차를 "호출할 때마다" 진행되는 것처럼 설명했고, HotSpot은 그 결과를 vtable과 itable에 담아 둔다고만 짧게 적었다. 명세가 정하는 것은 어떤 메서드가 선택되어야 하는가뿐이니, 실제로 언제 어떻게 고르는지는 구현을 열어 봐야 안다. 이 절은 OpenJDK 21 HotSpot 소스(github.com/openjdk/jdk21u의 src/hotspot/share 아래 classfile/classFileParser.cpp, classfile/defaultMethods.cpp, oops/klassVtable.cpp, interpreter/linkResolver.cpp)와 -Xlog:defaultmethods=debug 로그로 그 과정을 따라간다. 여기 나오는 함수 이름과 자료 구조는 모두 OpenJDK 21 HotSpot의 구현이고 명세가 아니다.

    언제: 클래스 파일을 파싱한 직후, 조상에 디폴트 메서드가 있을 때만

    ClassFileParser는 클래스 파일을 읽으면서 _has_nonstatic_concrete_methods라는 표시를 계산한다. 인터페이스가 static도 abstract도 아닌 메서드, 즉 몸체가 있는 인스턴스 메서드를 선언하면 이 표시가 켜지고, 클래스나 인터페이스는 직접 상위 인터페이스나 상위 클래스 가운데 하나라도 이 표시를 가지면 같이 켠다. 파싱을 마무리하는 단계의 소스에는 "Generate any default methods"라는 주석 아래 이 표시가 켜졌을 때만 DefaultMethods::generate_default_methods를 부르는 코드가 있다. 조상 어디에도 디폴트 메서드가 없는 클래스는 이 처리를 통째로 건너뛴다. 그리고 이 처리는 클래스마다 로딩할 때 한 번 일어난다. JVMS가 말하는 "가장 구체적인 상위 인터페이스 메서드" 계산은 HotSpot에서 호출 시점이 아니라 로딩 시점의 일이다.

    무엇을 채우는가: 빈 vtable 칸과 미란다 메서드

    파서는 vtable 크기를 계산하는 klassVtable::compute_vtable_size_and_num_mirandas에서 미란다 메서드(miranda method) 목록도 만든다. klassVtable.cpp의 주석은 미란다를 "이 클래스에서 재정의되지 않을, private이 아닌 추상 메서드"로 정의하고, 첫 계산에서는 vtable에 자리를 마련해 두려고 상위 인터페이스의 디폴트 메서드까지 후보에 넣는다고 적는다. 쉽게 말해 클래스 자신과 상위 클래스 사슬 어디에도 구현이 없는 인터페이스 메서드, 곧 JVMS 선택 절차의 1·2단계가 실패할 이름·디스크립터 쌍이다. generate_default_methods는 이 목록에 "상위 클래스가 디폴트나 오버패스로 채워 두었지만 이 클래스가 직접 구현하지 않은 메서드"를 더해 채워야 할 빈 칸(소스의 EmptyVtableSlot) 목록을 만든다. 상위 클래스가 채운 칸을 다시 보는 이유를 소스 주석은 "상위 클래스를 위한 디폴트 처리가 없었다면 미란다였을 메서드이므로, 새 문맥에서 다시 검토한다"고 설명한다. 예를 들어 Plain을 상속만 하고 인터페이스를 직접 나열하지 않은 class Sub extends Plain { }은 미란다 목록이 비지만, Plain이 디폴트로 채운 sound가 이 경로로 빈 칸 목록에 들어간다. 앞의 Hound는 Dog를 직접 나열하므로 sound가 이미 미란다 목록에 들어 있고, 이 경로에서는 같은 이름·디스크립터라 중복으로 걸러진다.

    어떻게 고르는가: 깊이 우선 탐색과 자격 박탈

    빈 칸마다 FindMethodsByErasedSig라는 방문자가 클래스 계층을 깊이 우선으로 걷는다. 클래스에서 같은 이름·디스크립터의 메서드를 만나면 set_target_if_empty로 그것을 곧바로 대상으로 정한다. 소스 주석은 이것을 "클래스의 메서드가 인터페이스의 메서드를 '이기는' 규칙"이라고 부르고, 단일 상속이기 때문에 이 방식이 성립한다고 적는다. 인터페이스에서 만나면 record_method_and_dq_further가 그 메서드를 기록한 뒤, 같은 경로에서 그보다 위쪽에서 만나는 같은 메서드를 모두 DISQUALIFIED(자격 박탈)로 기록한다. 경로를 빠져나오면 상태가 되돌아가고, 한 메서드가 어느 경로에서든 한 번이라도 박탈로 기록되면 박탈 상태가 유지된다. 그래서 방문 순서와 상관없이 하위 인터페이스에 가려진 메서드는 빠진다. 이것이 JVMS 정의의 마지막 조건("하위 인터페이스에 다른 후보가 없을 것")을 구현한 부분이다. 마지막으로 determine_target_or_set_exception_message가 자격이 남은 디폴트 메서드를 센다. 하나면 그것이 대상이다. 하나도 없으면 AbstractMethodError를, 둘 이상이면 "Conflicting default methods: ..." 메시지의 IncompatibleClassChangeError를 준비한다.

    결과 1: default_methods 배열, 복사가 아니라 포인터

    대상이 정해졌고 그것이 인터페이스의 메서드이면 create_default_methods가 그 메서드를 클래스의 _default_methods 배열에 넣는다. instanceKlass.hpp는 이 필드를 "인터페이스로부터 물려받은 구체 메서드"의 배열이라고 설명한다. 배열의 원소 타입은 Method*, 즉 인터페이스에 이미 있는 메서드 메타데이터를 가리키는 포인터다. 바이트코드를 복사한 새 메서드를 만들지 않는다. 함께 _default_vtable_indices 배열을 만들어 두고, 각 디폴트 메서드가 이 클래스의 vtable 몇 번째 칸에 들어가는지는 링크 때 vtable을 채우면서 이 배열에 기록한다.

    클래스를 링크할 때 klassVtable::initialize_vtable은 상위 클래스의 vtable을 복사한 뒤 이 클래스가 선언한 메서드를 재정의 칸이나 새 칸에 놓고, 이어서 default_methods의 메서드를 놓고, 마지막으로 남은 미란다를 채운다. 그래서 Square의 vtable에는 Shape.describe를 가리키는 칸이 생기고, invokevirtual Square.describe는 그 칸을 거쳐 인터페이스의 바이트코드를 곧장 실행한다. 링크 해석기가 수신 클래스에서 실행할 메서드를 찾을 때 쓰는 LinkResolver::lookup_instance_method_in_klasses도 같은 구조를 따른다. 수신 클래스와 그 상위 클래스들의 메서드 배열을 먼저 찾고, 거기서 찾지 못했을 때만 수신 클래스의 default_methods 배열을 본다. JVMS의 1·2단계(클래스 사슬)와 3단계(상위 인터페이스)가 "메서드 배열 다음에 디폴트 배열"이라는 두 번의 조회로 바뀐 것이고, 3단계에 필요한 계층 탐색은 로딩 때 이미 끝나 있다. 클래스에 선언된 메서드와 물려받은 디폴트가 HotSpot 안에서는 _methods와 _default_methods라는 서로 다른 배열에 산다는 점도 보자. Plain의 _methods에는 sound가 없으므로 Hound에서 상위 클래스 사슬을 뒤져도 걸리지 않는다.

    X.super.m()의 제약은 javac만 검사한다: invokespecial의 실제 선택

    앞에서 X.super.m()에는 두 제약이 있다고 했다. X는 직접 상위 인터페이스여야 하고, 다른 직접 상위 타입이 그 메서드를 재정의하고 있으면 안 된다(JLS §15.12.1, §15.12.3). 그런데 이 호출은 바이트코드에서 invokespecial로 굳어지고, JVM은 JLS가 아니라 JVMS를 따른다. JVMS §4.9.2의 구조 제약은 invokespecial이 가리킬 수 있는 대상을 "인스턴스 초기화 메서드, 현재 클래스의 메서드, 상위 클래스의 메서드, 현재 클래스의 직접 상위 인터페이스의 메서드, Object의 메서드"로 한정한다. 첫 번째 제약(직접 상위 인터페이스)은 JVMS도 요구하지만, 두 번째 제약(다른 경로의 재정의를 건너뛰지 말 것)은 목록에 없다.

    JVMS §6.5의 invokespecial 선택 절차를 보면 이유가 드러난다. 기호 참조가 인터페이스 C를 가리키면, C 자신에 같은 이름·디스크립터의 인스턴스 메서드 선언이 있을 때 그것이 실행할 메서드다. 없을 때만 Object의 public 메서드, 그다음 C의 상위 인터페이스 가운데 가장 구체적인 메서드를 본다. 수신 객체의 클래스나 다른 상위 인터페이스는 보지 않는다. 그래서 분리 컴파일을 끼우면 javac가 막은 우회가 실행 중에 그대로 일어난다.

    // 1판: Dog는 Animal과 아무 관계가 없다. 이 상태로 Puppy를 컴파일했다.
public interface Animal { default String sound() { return "Animal"; } }
public interface Dog { }
public class Puppy implements Animal, Dog {
    public String sound() { return "Puppy+" + Animal.super.sound(); }
}

    2판에서 Dog는 Animal.sound를 재정의했고, 소스로 보면 Puppy의 Animal.super.sound()는 이제 금지된 우회다. 하지만 이미 컴파일된 Puppy.class는 링크 오류 없이 실행되고 Animal의 몸체를 그대로 부른다. Animal은 여전히 Puppy의 직접 상위 인터페이스이므로 §4.9.2의 구조 제약을 만족하고, §6.5의 선택 1단계에서 Animal에 선언된 sound가 곧바로 골라지기 때문이다. Dog가 무엇을 재정의했는지는 이 명령어의 선택 절차에 들어오지 않는다. 같은 소스를 다시 컴파일하는 순간 앞에서 본 "redundant interface" 오류로 바뀐다.

    이 실험은 가상 호출과 invokespecial의 성격 차이를 보여 준다. invokevirtual과 invokeinterface는 실행할 때마다 수신 객체의 클래스에서 다시 고르므로, 계층이 바뀌면 바뀐 계층대로 동작한다. X.super.m()은 컴파일 시점에 "이 인터페이스의 이 구현"을 바이트코드에 고정해 넣는다. 그래서 그 뒤에 계층이 바뀌어도 반영되지 않는다. 하위 인터페이스의 재정의 결정을 존중하라는 JLS의 규칙은 소스를 다시 컴파일할 때만 지켜진다.

    표준 라이브러리는 디폴트 메서드를 어떻게 썼나

    JDK 8 이후의 컬렉션과 함수형 인터페이스에는 디폴트 메서드가 많다. 그 소스를 읽으면 디폴트 메서드를 어떻게 설계해야 하는지가 구체적으로 보인다. 아래는 모두 OpenJDK 21 소스(lib/src.zip)에서 확인한 내용이다.

    Iterable.forEach와 ArrayList의 재정의

    // java.lang.Iterable (OpenJDK 21)
default void forEach(Consumer action) {
    Objects.requireNonNull(action);
    for (T t : this) {
        action.accept(t);
    }
}

    디폴트 구현은 인터페이스가 이미 가진 추상 메서드 iterator()(향상된 for 문이 부르는 것) 위에 쌓여 있다. 어떤 Iterable이든 반복자만 줄 수 있으면 forEach가 동작한다. 그리고 ArrayList는 이것을 재정의한다. 반복자 객체를 만들지 않고 내부 배열 elementData를 인덱스로 직접 돌며, 반복 중에 구조가 바뀌었는지(modCount)를 확인해 ConcurrentModificationException을 던진다. "기본 구현은 계약만 지키는 일반적인 방법, 구현 클래스는 자기 내부 구조를 아는 빠른 방법"이라는 분업이다. JEP 126이 말한 "더 높은 성능이나 특화된 구현을 위해 디폴트 구현을 재정의할 수 있다"가 이것이다.

    Collection.removeIf: 반복자 위에 쌓은 기본 구현

    // java.util.Collection (OpenJDK 21)
default boolean removeIf(Predicate filter) {
    Objects.requireNonNull(filter);
    boolean removed = false;
    final Iterator each = iterator();
    while (each.hasNext()) {
        if (filter.test(each.next())) {
            each.remove();
            removed = true;
        }
    }
    return removed;
}

    역시 iterator()와 Iterator.remove()만으로 만든 구현이다. ArrayList에서 이 기본 구현을 그대로 쓰면, 반복자의 remove()는 지울 때마다 뒤쪽 원소를 한 칸씩 당기므로 지울 원소가 많을수록 배열 복사가 반복된다. 그래서 ArrayList는 removeIf를 재정의한다. 첫 번째 순회에서는 술어(filter.test)만 호출하며 지울 위치를 비트 배열에 표시하고, 두 번째 순회에서 살아남은 원소를 앞으로 모은 뒤 꼬리를 정리한다. 소스 주석은 이렇게 두 번 순회하는 이유를 "술어가 컬렉션을 재진입해서 읽는 것은 허용하기 위해서(쓰는 쪽은 여전히 CME를 받는다)"라고 적는다. 디폴트 구현이 정한 계약(술어가 참인 원소를 모두 지우고, 지웠으면 true)은 그대로 지키면서 구현 전략만 바꾼 것이다.

    List.sort와 Collections.sort

    // java.util.List (OpenJDK 21)
default void sort(Comparator c) {
    Object[] a = this.toArray();
    Arrays.sort(a, (Comparator) c);
    ListIterator i = this.listIterator();
    for (Object e : a) {
        i.next();
        i.set((E) e);
    }
}

    이 디폴트 구현의 Javadoc @implSpec은 모든 원소를 배열로 꺼내 정렬한 뒤 리스트 반복자로 각 위치에 다시 써 넣는다고 설명하고, 그 이유를 "연결 리스트를 제자리에서 정렬하려 할 때 생길 n² log(n) 성능을 피하기 위해서"라고 밝힌다. 연결 리스트는 인덱스 접근이 O(n)이므로 인덱스로 원소를 바꿔 가며 정렬하면 비싸다. 배열로 꺼내 정렬하고 순차적으로 다시 쓰면 그 비용을 피한다. LinkedList는 이 디폴트를 그대로 쓰고, ArrayList는 이미 배열이 있으므로 Arrays.sort((E[]) elementData, 0, size, c)로 내부 배열을 직접 정렬하도록 재정의한다. 앞에서 본 대로 Collections.sort는 이제 list.sort(c)에 위임한다. 같은 호출이 리스트의 실제 구현에 따라 가장 알맞은 알고리즘으로 연결되는 것, 정적 유틸리티로는 할 수 없던 일이다.

    추상에서 디폴트로: Iterator.remove

    자바 7까지 Iterator.remove()는 추상 메서드였다. 삭제를 지원하지 않는 반복자도 모두 이 메서드를 구현해 UnsupportedOperationException을 던져야 했다. 자바 8부터는 디폴트 메서드가 되었고, OpenJDK 21의 몸체는 throw new UnsupportedOperationException("remove"); 한 줄이다. @implSpec도 "기본 구현은 UnsupportedOperationException을 던지고 다른 동작은 하지 않는다"고 약속한다. JLS §13.5.7이 말한 "추상 메서드를 디폴트로 바꾸기"의 실제 예다. 이렇게 하면 이미 remove()를 구현한 옛 클래스는 규칙 1에 따라 자기 구현을 계속 쓰고, 새로 만드는 읽기 전용 반복자는 hasNext()와 next()만 구현하면 된다.

    Map의 디폴트 메서드와 원자성

    // java.util.Map (OpenJDK 21)
default V putIfAbsent(K key, V value) {
    V v = get(key);
    if (v == null) {
        v = put(key, value);
    }
    return v;
}

    이 코드는 get과 put이라는 두 번의 호출로 이루어져 있다. 두 호출 사이에 다른 스레드가 같은 키를 넣으면, 둘 다 "없다"고 판단하고 둘 다 put을 해서 한쪽 값이 덮인다. 자바 고급 1편에서 본 "확인 후 행동(check-then-act)" 경쟁 조건 그대로다. 그래서 Javadoc의 @implSpec은 "기본 구현은 이 메서드의 동기화나 원자성에 대해 아무것도 보장하지 않는다. 원자성을 보장하는 구현은 이 메서드를 재정의하고 그 동시성 특성을 문서화해야 한다"고 적는다. Map.java에서 이 문장과 비슷한 "makes no guarantees about synchronization or atomicity" 문구는 getOrDefault, forEach, replaceAll, putIfAbsent, remove, replace, computeIfAbsent, compute, merge 같은 디폴트 메서드 문서에 반복해서 나온다. 인터페이스는 구현이 어떤 락을 쓰는지 모르므로, 원자성이 필요한 구현(ConcurrentHashMap 같은)이 직접 재정의해야 한다는 뜻이다.

    함수형 인터페이스의 조합 메서드

    2회에서 본 Predicate의 디폴트 메서드도 같은 원칙을 따른다. OpenJDK 21에서 negate()는 return (t) -> !test(t);, and(other)는 return (t) -> test(t) && other.test(t);이다. 둘 다 유일한 추상 메서드 test만 써서 새 Predicate를 만든다. 람다로 만든 객체도 이 메서드들을 그대로 쓸 수 있는 이유는, 람다 객체의 숨겨진 클래스가 Predicate를 구현하고 디폴트 메서드는 앞의 선택 절차 3단계로 인터페이스에서 찾아지기 때문이다. 람다가 디폴트 메서드를 재정의할 수 없다는 4회의 제약은 거꾸로 말하면 "람다 객체의 디폴트 메서드 동작은 인터페이스가 완전히 정한다"는 뜻이다.

    자바 21의 SequencedCollection과 이름 충돌

    디폴트 메서드를 이용한 인터페이스 진화는 지금도 진행 중이다. 자바 21의 JEP 431(Sequenced Collections)은 SequencedCollection 인터페이스를 새로 만들고 List와 Deque가 그것을 상속하게 했다. OpenJDK 21의 List에는 addFirst, addLast, getFirst, getLast, removeFirst, removeLast, reversed가 디폴트 메서드로 들어 있다. 덕분에 자바 21 이전에 만든 List 구현도 다시 컴파일하지 않고 getFirst()에 응답한다.

    그런데 JEP 431의 "위험과 가정" 절은 상속 계층 높은 곳에 reversed(), getFirst() 같은 흔한 이름을 넣으면 충돌 위험이 있다고 인정한다. 특히 List와 Deque가 reversed()를 각자 자기 타입을 반환하도록 공변 재정의(covariant override)하므로, 두 인터페이스를 모두 구현한 기존 컬렉션과는 소스와 바이너리 양쪽에서 호환되지 않는다고 적는다. JDK 안의 LinkedList가 그런 클래스였고, LinkedList 자체에 reversed()의 공변 재정의를 추가해서 해결했다(OpenJDK 21 소스에 public LinkedList<E> reversed()가 @since 21로 있다). 같은 상황을 직접 만들어 보면 이렇다.

    디폴트 메서드의 올바른 사용법

    지금까지 본 규칙과 사례에서 디폴트 메서드를 설계할 때의 기준을 정리할 수 있다. 공식 문서가 "이렇게 써라"라고 목록으로 정해 둔 것은 아니지만, 아래 기준은 모두 앞에서 확인한 명세 규칙과 JDK 소스의 실제 선택에서 나온 것이다.

    1. 인터페이스의 다른 추상 메서드 위에 쌓을 수 있는 것만 디폴트로 만든다

    forEach는 iterator() 위에, removeIf는 iterator()와 Iterator.remove() 위에, negate는 test 위에, 이 회차의 Shape.describe는 area 위에 쌓였다. 디폴트 메서드가 쓸 수 있는 것은 인터페이스의 공개된 계약뿐이다. 그 계약만으로 정확하게 구현할 수 있다면 좋은 디폴트 메서드 후보이고, 특정 구현의 내부 구조를 알아야만 구현할 수 있다면 인터페이스에 둘 것이 아니다. 기본 구현이 느리더라도 정확하기만 하면, 빠른 구현은 구현 클래스가 재정의로 줄 수 있다. List.sort와 ArrayList.sort의 관계가 그렇다.

    2. 상태를 흉내 내지 않는다

    인터페이스에 선언한 필드는 암묵적으로 public static final이다. 인스턴스마다 다른 값을 둘 곳이 없다. 이 제약을 피하려고 인터페이스 안에 정적 Map을 두고 this를 키로 객체별 상태를 저장하는 방식이 가끔 보이는데, 이것은 디폴트 메서드의 취지를 거스른다. 그 맵이 모든 구현 객체를 강하게 참조해 가비지 컬렉션을 막고, 여러 스레드가 공유하는 전역 상태가 되어 동기화 문제를 만든다. 객체마다 상태가 필요한 기능은 상태를 가진 클래스, 즉 추상 클래스나 구현 클래스가 맡아야 한다. 튜토리얼이 정리한 대로 인터페이스가 허용하는 것은 구현의 다중 상속이지 상태의 다중 상속이 아니다.

    3. 구현 클래스의 불변식과 동기화 정책을 생각한다

    디폴트 메서드를 새로 추가하면, 그 메서드는 그 인터페이스를 구현한 모든 기존 클래스에 그 클래스 작성자의 검토 없이 들어간다. 기존 클래스가 지키던 규칙을 디폴트 메서드가 모르고 깨뜨릴 수 있다. 가장 분명한 예가 동기화 래퍼다. 자바 7 시절에 만든, 모든 메서드를 synchronized로 감싼 컬렉션 래퍼가 있다고 하자.

    import java.util.*;

public class LockCheck {
    // 자바 7 시절에 만들었다고 가정한 동기화 래퍼.
    // 그때 Collection에 있던 메서드만 synchronized로 감쌌다.
    static class OldSyncCollection extends AbstractCollection {
        private final Collection c;
        private final Object mutex = this;
        OldSyncCollection(Collection c) { this.c = c; }

        public int size()               { synchronized (mutex) { return c.size(); } }
        public boolean add(E e)         { synchronized (mutex) { return c.add(e); } }
        public boolean remove(Object o) { synchronized (mutex) { return c.remove(o); } }
        public Iterator iterator()   { return c.iterator(); } // 순회는 호출자가 직접 동기화
        @Override public String toString() { synchronized (mutex) { return c.toString(); } }
    }

    public static void main(String[] args) {
        Collection old = new OldSyncCollection<>(new ArrayList<>(List.of(1, 2, 3)));
        old.removeIf(x -> {
            System.out.println("old " + x + ": 락 보유 = " + Thread.holdsLock(old));
            return x == 2;
        });
        System.out.println(old);

        Collection jdk = Collections.synchronizedCollection(new ArrayList<>(List.of(1, 2, 3)));
        jdk.removeIf(x -> {
            System.out.println("jdk " + x + ": 락 보유 = " + Thread.holdsLock(jdk));
            return x == 2;
        });
        System.out.println(jdk);
    }
}
    old 1: 락 보유 = false
old 2: 락 보유 = false
old 3: 락 보유 = false
[1, 3]
jdk 1: 락 보유 = true
jdk 2: 락 보유 = true
jdk 3: 락 보유 = true
[1, 3]

    Thread.holdsLock(obj)는 현재 스레드가 그 객체의 모니터를 쥐고 있는지 알려 준다. 옛 래퍼의 removeIf는 Collection의 디폴트 구현이 실행되었다. AbstractCollection은 removeIf를 재정의하지 않는다. 디폴트 구현은 iterator()로 반복자를 얻어 each.remove()로 지우는데, 그 어디에도 래퍼의 락이 없다. 단일 스레드 실행 결과는 같아 보여도, 다른 스레드가 add를 하는 동안 이 removeIf가 돌면 래퍼가 약속한 "모든 연산이 상호 배제된다"는 불변식이 깨진다. 래퍼 작성자는 코드 한 줄 바꾸지 않았는데, 자바 8로 올리는 순간 동기화되지 않는 메서드가 생긴 것이다.

    JDK는 자기 래퍼에서 이 문제를 직접 막았다. Collections.SynchronizedCollection의 소스에는 "Override default methods in Collection"이라는 주석 아래 forEach와 removeIf를 synchronized (mutex)로 감싸 재정의한 코드가 있다. 래퍼의 mutex는 기본 생성자에서 this로 정해지므로 실행 결과에서 holdsLock(jdk)가 true였다. 같은 자리의 spliterator(), stream(), parallelStream()은 락 없이 위임하면서 "Must be manually synched by user!"라는 주석을 달았다. 스트림은 호출이 끝난 뒤에 소비되므로 메서드 안에서 락을 잡아도 소용이 없기 때문이다. SynchronizedMap도 "Override default methods in Map" 주석 아래 getOrDefault, putIfAbsent, computeIfAbsent 등을 락으로 감싸 재정의한다. 교훈은 이렇다. 디폴트 메서드를 추가하는 쪽은 그것이 기존 구현의 동기화·불변식과 어떻게 어울릴지 문서로 밝혀야 하고, 불변식을 가진 구현 클래스는 인터페이스가 새 디폴트 메서드를 얻을 때마다 재정의가 필요한지 검토해야 한다.

    4. 기본 구현이 무엇을 하는지 문서로 약속한다

    JDK 소스는 디폴트 메서드마다 Javadoc의 @implSpec 태그로 기본 구현의 동작을 적는다. Iterable.forEach는 "기본 구현은 for (T t : this) action.accept(t);처럼 동작한다", List.sort는 배열로 꺼내 정렬한 뒤 다시 쓴다, Map.putIfAbsent는 원자성을 보장하지 않는다고 적었다. 이것은 호출하는 사람보다 재정의하는 사람을 위한 정보다. 구현 클래스 작성자는 이것을 보고 기본 구현이 자기 클래스에서 정확한지(예: removeIf가 iterator().remove()를 쓰므로 반복자가 삭제를 지원해야 한다), 충분히 빠른지, 동기화 정책에 맞는지 판단한다. 기본 구현이 어떤 다른 메서드를 부르는지가 문서에 없으면, 구현 클래스는 그 메서드를 재정의했을 때 무슨 일이 생길지 알 수 없다.

    5. 이름과 시그니처를 신중히 고른다

    새 디폴트 메서드의 이름이 기존 구현 클래스에 이미 있는 메서드와 겹치면 두 가지 일이 생긴다. 시그니처가 같으면 규칙 1에 따라 클래스의 메서드가 조용히 그 디폴트를 재정의한 것이 된다. 그 메서드가 전혀 다른 의미였다면, 인터페이스 타입으로 부르는 새 코드는 엉뚱한 동작을 실행한다. 반환 타입이 다르면 그 클래스는 다음 재컴파일에서 오류가 난다. 그리고 앞에서 본 대로 함께 구현되는 다른 인터페이스에 같은 이름이 있으면 다이아몬드 충돌이 생긴다. JEP 431이 SequencedMap의 keySet()을 공변 재정의하는 대신 sequencedKeySet()이라는 새 이름을 만든 것도, 기존 하위 클래스를 무효로 만들 위험이 너무 크다고 판단했기 때문이라고 JEP 본문이 밝힌다.

    추상 클래스와 인터페이스, 무엇을 고를까

    디폴트 메서드가 생긴 뒤에도 추상 클래스가 필요한 자리는 분명히 있다. 둘의 차이는 모두 앞에서 확인한 규칙에서 나온다.

    타입을 정의하고 그 위에 상태 없는 편의 기능을 얹는 것이 목적이면 인터페이스와 디폴트 메서드가 맞다. 구현 클래스가 공유해야 할 상태, 반드시 지켜야 할 초기화 순서, 하위 클래스가 바꾸지 못하게 할 메서드(final), 하위 클래스에만 보여 줄 훅(protected)이 필요하면 추상 클래스가 맞다. 둘을 함께 쓰는 것도 흔하다. 인터페이스로 타입을 정의하고, 그것을 구현하기 쉽게 하는 골격 추상 클래스를 따로 두는 것이다. List와 AbstractList가 지금도 그렇게 짝을 이룬다.

    동적 프록시는 디폴트 메서드를 어떻게 다루는가

    디폴트 메서드를 가진 인터페이스는 프록시로 감싸지는 일이 많다. 스프링의 JDK 동적 프록시, 스프링 데이터 JPA의 리포지토리처럼 인터페이스만 있고 구현 클래스는 실행 중에 만들어지는 경우다. 이때 디폴트 메서드의 몸체가 실행되는지는 앞에서 본 선택 순서로 결정된다. java.lang.reflect.Proxy의 Javadoc은 프록시 인스턴스에 대한 인터페이스 메서드 호출이 인코딩되어 호출 핸들러의 invoke로 전달된다고 적는다. 디폴트 메서드도 인터페이스 메서드이므로 예외가 아니다. 앞의 Shape를 프록시로 감싸 보자.

    import java.lang.reflect.*;

public class ProxyDemo {
    public static void main(String[] args) {
        ClassLoader cl = Shape.class.getClassLoader();
        Class[] types = { Shape.class };

        // (1) 모든 호출을 직접 처리하는 핸들러
        Shape naive = (Shape) Proxy.newProxyInstance(cl, types, (proxy, method, a) -> {
            System.out.println("  handler: " + method.getName() + " (isDefault=" + method.isDefault() + ")");
            return method.getReturnType() == double.class ? 2.0 : "핸들러가 만든 값";
        });
        for (Method m : naive.getClass().getDeclaredMethods()) {
            if (m.getName().equals("describe") || m.getName().equals("area")) {
                System.out.println("프록시 클래스가 선언: " + m);
            }
        }
        System.out.println("(1) " + naive.describe());

        // (2) 디폴트 메서드는 invokeDefault로 인터페이스의 몸체를 실행
        Shape proper = (Shape) Proxy.newProxyInstance(cl, types, (proxy, method, a) -> {
            System.out.println("  handler: " + method.getName() + " (isDefault=" + method.isDefault() + ")");
            if (method.isDefault()) {
                return InvocationHandler.invokeDefault(proxy, method, a);
            }
            return 2.0;   // 추상 메서드 area()는 핸들러가 직접 답한다
        });
        System.out.println("(2) " + proper.describe());
    }
}

  handler: describe (isDefault=true)
  handler: area (isDefault=false)

    첫 두 줄이 핵심이다. JDK가 만든 프록시 클래스는 추상 메서드 area뿐 아니라 디폴트 메서드 describe도 public final 메서드로 직접 선언한다. 같은 실행에서 이 프록시 클래스의 선언 메서드를 모두 찍어 보면 describe, area, equals, hashCode, toString과 private 정적 메서드 proxyClassLookup이 나오고, private 인터페이스 메서드 label이나 정적 메서드 unit은 없다. 클래스에 describe가 선언되어 있으니 선택 1단계에서 프록시 클래스의 메서드가 골라지고, Shape의 디폴트 몸체는 저절로는 결코 실행되지 않는다. "클래스가 이긴다"는 규칙이 여기서도 그대로 작동한 것이다. (1)의 핸들러는 디폴트 메서드인지 신경 쓰지 않았으므로 describe()의 결과가 통째로 핸들러가 만든 값으로 바뀌었다. 인터페이스에 디폴트 메서드를 추가하면, 그 인터페이스를 프록시로 감싸는 모든 핸들러가 새 메서드 호출을 받게 된다는 뜻이기도 하다. 핸들러가 메서드 이름으로 분기하다가 모르는 메서드에 null을 돌려주는 식이라면, 디폴트 메서드 하나가 추가되는 것만으로 동작이 바뀐다.

    (2)는 자바 16에서 추가된 InvocationHandler.invokeDefault를 썼다. Javadoc은 이 메서드가 "프록시 클래스에서 invokespecial 명령어를 실행한 것처럼" 동작하며, X.super.m()을 호출하는 것과 같다고 설명한다. 구현을 보면 정말 그렇다. OpenJDK 21의 Proxy.invokeDefault는 프록시 인스턴스인지, 디폴트 메서드인지 확인한 뒤 Proxy.defaultMethodHandle로 메서드 핸들을 얻는데, 그 안에서 프록시 클래스의 proxyClassLookup으로 얻은 Lookup에 findSpecial(프록시 인터페이스, 이름, 타입, 프록시 클래스)를 호출한다. findSpecial은 invokespecial에 해당하는 메서드 핸들을 만드는 API다. 이렇게 실행된 Shape.describe의 몸체에서 this는 프록시 객체다. 그래서 label()의 getClass().getSimpleName()은 $Proxy0을 돌려주고, label() 호출 자체는 핸들러를 거치지 않는다(private 인터페이스 메서드는 해석된 메서드가 그대로 선택되고, 프록시 클래스도 그것을 선언하지 않는다). 반면 area()는 invokeinterface로 프록시의 area를 다시 부르므로 핸들러로 돌아가 2.0을 받는다. 출력의 "handler" 줄이 describe와 area 두 번뿐인 이유다.

    invokeDefault의 Javadoc은 인터페이스 진화와 관련된 경고도 단다. 핸들러가 특정 상위 인터페이스의 디폴트 메서드 Method 객체를 골라 invokeDefault에 넘기는데, 나중에 프록시 인터페이스가 그 메서드를 재정의하면 그 호출은 IllegalArgumentException으로 실패한다. 디폴트 메서드를 추가하거나 추상 메서드를 디폴트로 바꾸는 것이 이미 있는 invokeDefault 코드에 예외를 일으킬 수 있다는 것이다. 앞의 X.super 규칙과 같은 원칙이다. 하위 인터페이스가 재정의를 결정하면, 바깥에서 그 재정의를 건너뛰어 할아버지의 구현을 부를 수 없다.

    자바 16 이전의 라이브러리들은 같은 일을 MethodHandles.Lookup.findSpecial로 직접 했다. 스프링 데이터 커먼즈 3.2.x 소스에는 "리포지토리 프록시에서 디폴트 메서드를 호출하기 위한" 메서드 인터셉터 DefaultMethodInvokingMethodInterceptor가 있다. 이 인터셉터는 호출된 메서드가 디폴트가 아니면 다음 인터셉터로 넘기고(invocation.proceed()), 디폴트이면 MethodHandles.privateLookupIn으로 선언 인터페이스에 대한 Lookup을 얻어 findSpecial로 핸들을 만든 뒤 프록시에 묶어 호출한다. 이름은 달라도 원리는 같다. 프록시 클래스가 모든 인터페이스 메서드를 선언해 "클래스가 이기는" 자리를 차지하므로, 디폴트 몸체를 실행하려면 누군가 invokespecial에 해당하는 호출로 인터페이스의 구현을 직접 지목해야 한다.

    흔한 오해와 함정

    • "디폴트 메서드가 생겨서 인터페이스가 추상 클래스와 같아졌다." 아니다. 인터페이스는 여전히 인스턴스 필드도 생성자도 없고, protected·final·synchronized 메서드도 가질 수 없다. 같은 이름의 메서드와 경쟁하면 언제나 클래스 쪽에 진다. 디폴트 메서드는 상태 없는 행동만 물려줄 수 있다.
    • "디폴트 메서드는 컴파일할 때 구현 클래스에 복사된다." 아니다. javap -p Square에 describe가 없었다. 몸체는 인터페이스의 클래스 파일에만 있고, JVM이 실행 시점에 해석·선택 절차로 찾아간다. 그래서 다시 컴파일하지 않은 옛 클래스도 새 디폴트 메서드를 쓸 수 있다.
    • "상위 클래스에서 온 것이면 무엇이든 인터페이스를 이긴다." 상위 클래스에 선언된 메서드만 그렇다. 상위 클래스가 다른 인터페이스로부터 물려받은 디폴트는 구체 메서드가 아니므로, 더 구체적인 인터페이스의 디폴트에 진다(Hound 사례). 반대로 상위 클래스에 선언된 추상 메서드는 디폴트를 이긴다.
    • "X.super.m()으로 어느 조상 인터페이스든 부를 수 있다." 직접 상위 인터페이스만 쓸 수 있고, 다른 직접 상위 타입이 그 메서드를 재정의했으면 쓸 수 없다. 하위 인터페이스가 내린 재정의 결정을 구현 클래스가 건너뛰지 못하게 하려는 규칙이다.
    • "디폴트 메서드 추가는 언제나 안전하다." 바이너리 호환일 뿐이다. 이름이 같은 디폴트를 가진 다른 인터페이스와 함께 구현된 클래스에서는 호출 시점에 IncompatibleClassChangeError(OpenJDK 21의 invokeinterface 경로에서는 AbstractMethodError)가 나고, 재컴파일하면 컴파일 오류가 된다. 같은 시그니처의 메서드를 가진 기존 클래스에서는 의미가 다른 메서드가 조용히 재정의자가 되고, 동기화 래퍼 같은 클래스에서는 불변식이 깨질 수 있다.
    • "인터페이스에 toString() 디폴트를 두면 람다 객체의 출력을 바꿀 수 있다." 컴파일 오류다(JLS §9.4.1.2). 모든 클래스가 Object로부터 toString을 받으므로 그런 디폴트는 절대 선택될 수 없다.
    • "인터페이스의 정적 메서드도 구현 클래스로 부를 수 있다." 아니다. ArrayList.of(...)는 컴파일되지 않는다. 인터페이스 정적 메서드는 상속되지 않으며, 인스턴스 참조로 부르면 "illegal static interface method call" 오류가 난다.
    • "JVM이 클래스를 로딩할 때 추상 메서드를 다 구현했는지 확인한다." 아니다. 그 검사는 javac가 한다. JVM은 링크까지 문제없이 마치고, 구현이 없는 메서드를 실제로 호출할 때 AbstractMethodError를 던진다. 옛 바이너리가 로딩은 되는데 특정 호출에서만 실패하는 이유다.
    • "인터페이스를 프록시로 감싸도 디폴트 메서드는 인터페이스의 몸체가 실행된다." 아니다. JDK 동적 프록시 클래스는 디폴트 메서드까지 public final로 직접 선언하므로 호출은 모두 핸들러로 간다. 몸체를 실행하려면 핸들러가 InvocationHandler.invokeDefault(자바 16)나 findSpecial로 만든 메서드 핸들로 인터페이스의 구현을 직접 지목해야 한다.

    정리: 디폴트 메서드를 한 장으로

    이 회차의 내용을 처음 질문으로 돌아가 정리하자. 인터페이스에 추상 메서드를 추가하면 소스를 다시 컴파일하는 구현 클래스는 컴파일 오류가 나고, 이미 컴파일된 구현 클래스는 링크는 되지만 그 메서드를 호출하는 순간 AbstractMethodError가 난다. 디폴트 메서드는 몸체를 인터페이스의 클래스 파일에 두고, JVM이 호출 시점에 상위 인터페이스까지 찾아 실행하게 함으로써 두 문제를 모두 피한다. 이를 위해 자바 8은 언어(JLS §9.4), 클래스 파일 형식(버전 52.0부터 인터페이스 메서드의 몸체 허용), JVM의 해석·선택 절차(JVMS §5.4.3.3, §5.4.6)를 함께 바꿨다.

    어느 구현이 실행되는지는 JVM의 선택 순서가 정한다. 수신 객체의 클래스와 상위 클래스 사슬에 선언된 메서드가 먼저이고(클래스가 이긴다), 그다음 가장 구체적인 상위 인터페이스의 디폴트 메서드다(더 구체적인 인터페이스가 이긴다). 무관한 인터페이스의 디폴트가 둘 이상이면 컴파일러가 재정의를 요구하고, 구현 클래스는 X.super.m()으로 원하는 것을 고른다(직접 고른다). 분리 컴파일 때문에 컴파일러가 이 충돌을 보지 못하면, 충돌은 실행 중 호출 시점에 오류로 드러난다.

    표준 라이브러리는 디폴트 메서드를 "인터페이스의 추상 메서드만으로 만든 정확한 기본 구현"으로 쓰고, ArrayList나 동기화 래퍼 같은 구현 클래스가 성능과 동기화 정책 때문에 그것을 재정의하는 분업 구조를 택했다. 기본 구현의 동작과 보장하지 않는 것(원자성 등)은 @implSpec으로 문서화한다. 디폴트 메서드를 직접 설계할 때도 같은 기준을 따르면 된다. 상태를 갖지 않고, 다른 추상 메서드 위에 쌓고, 기존 구현의 불변식과 이름 충돌을 검토한다.

    이 지식은 뒤에서 다시 쓰인다. 다음 10회의 병렬 스트림은 Collection의 디폴트 메서드 parallelStream()에서 시작한다. 11회의 함수형 프로그래밍에서 함수를 조합하는 andThen, compose, negate도 모두 디폴트 메서드다. 앞서 읽은 스프링 MVC에서도 같은 진화가 있었다. 스프링 프레임워크 5.3 Javadoc은 WebMvcConfigurerAdapter를 폐기 예정으로 표시하면서 그 이유를 "5.0부터 WebMvcConfigurer가 디폴트 메서드를 가지므로(자바 8 기준선 덕분에) 이 어댑터 없이 직접 구현할 수 있다"고 적는다. 빈 메서드만 가진 어댑터 추상 클래스를 상속하던 방식이, 디폴트 메서드를 가진 인터페이스를 직접 구현하는 방식으로 바뀐 것이다. 앞에서 본 "골격 추상 클래스에서 디폴트 메서드로"의 흐름이 프레임워크에서도 그대로 일어났다.

    정리의 핵심

    디폴트 메서드는 인터페이스를 진화시키기 위한 장치이고, 그 동작은 "몸체는 인터페이스에 한 벌, 선택은 실행 시점에 클래스 사슬 먼저, 그다음 가장 구체적인 인터페이스"라는 한 문장으로 요약된다. 언어의 세 해석 규칙과 각종 컴파일 오류는 모두 이 선택 순서를 모호함 없이 만들기 위한 장치다. 좋은 디폴트 메서드는 상태 없이 인터페이스의 계약 위에 쌓이고, 무엇을 보장하고 무엇을 보장하지 않는지 문서로 밝힌다.
    디폴트 메서드의 존재 이유
    인터페이스에 추상 메서드를 더하면 구현 클래스의 소스는 컴파일 오류가 나고 옛 바이너리는 호출 시 AbstractMethodError가 난다. 몸체를 가진 디폴트 메서드는 두 호환성을 모두 지키며 인터페이스를 진화시킨다(JEP 126).
    문법 규칙
    default 제어자와 블록 몸체를 가진 public 인스턴스 메서드다. abstract·static·private와 함께 쓸 수 없고 final·synchronized도 불가하며, Object의 public 메서드를 재정의할 수 없다.
    정적·private 인터페이스 메서드
    정적 메서드(자바 8)는 상속되지 않아 인터페이스 이름으로만 부른다. private 메서드(자바 9, JEP 213)는 디폴트 메서드끼리 코드를 공유하기 위한 것이다.
    클래스 파일 표현
    인터페이스 안에서 ACC_ABSTRACT 없이 Code 속성을 가진 public 메서드다. 구현 클래스에 복사되지 않으며, 호출은 정적 타입에 따라 invokeinterface나 invokevirtual, X.super.m()은 invokespecial이 된다.
    메서드 선택 순서
    수신 객체의 클래스, 상위 클래스 사슬, 가장 구체적인 상위 인터페이스 메서드 순으로 찾는다(JVMS §5.4.6). 추상 아닌 후보가 여럿이면 IncompatibleClassChangeError, 없으면 AbstractMethodError다.
    세 해석 규칙
    클래스에 선언된 메서드가 이기고, 하위 인터페이스의 디폴트가 상위 인터페이스의 것을 이기며, 그래도 모호하면 재정의해서 X.super.m()으로 직접 고른다.
    규칙의 경계
    디폴트는 다른 인터페이스의 추상 메서드를 대신 구현하지 않고, 상위 클래스의 추상 메서드는 디폴트를 덮으며, 하위 인터페이스는 디폴트를 재추상화할 수 있다. X.super는 직접 상위 인터페이스이면서 다른 직접 상위 타입이 재정의하지 않은 경우에만 쓸 수 있다.
    분리 컴파일 충돌
    디폴트 추가는 링크 시점 오류를 만들지 않는 바이너리 호환 변경이지만, 두 인터페이스가 같은 디폴트를 얻으면 옛 클래스는 호출 시점에 실패한다. HotSpot은 오버패스 메서드로 이를 처리하며, OpenJDK 21의 invokeinterface 경로에서는 명세와 달리 AME가 난다(JDK-8356942).
    HotSpot의 디폴트 메서드 처리
    OpenJDK 21 HotSpot은 클래스를 로딩할 때 defaultMethods.cpp에서 빈 vtable 칸마다 가장 구체적인 디폴트를 미리 골라, 하나면 인터페이스 메서드 포인터를 _default_methods에 넣고, 없거나 여럿이면 예외를 던지는 오버패스를 클래스의 메서드 배열에 넣는다. X.super.m()의 invokespecial은 지목한 인터페이스에서 바로 고르므로 나중에 생긴 다른 경로의 재정의를 보지 않는다.
    올바른 사용법
    상태 없이 다른 추상 메서드 위에 쌓고, 기본 구현과 보장하지 않는 것을 @implSpec으로 밝히고, 기존 구현의 불변식·동기화 정책과 이름 충돌을 검토한다. 상태와 생성자가 필요하면 추상 클래스를 쓴다.

    사내 공통 모듈의 인터페이스를 고쳐야 하는 상황을 생각해 보자. 이 인터페이스를 구현한 클래스가 여러 팀의 서비스에 흩어져 있고, 각 서비스는 공통 모듈의 jar 버전을 서로 다른 시점에 올린다. 여기에 추상 메서드를 더하면 다음 빌드에서 모든 팀의 컴파일이 깨지고, 아직 다시 빌드하지 않은 서비스는 새 메서드를 부르는 순간 AbstractMethodError로 실패한다. 디폴트 메서드로 추가하면 두 문제를 모두 피할 수 있다. 다만 그 디폴트 구현이 기존 구현 클래스들의 전제와 맞는지, 특히 락이나 트랜잭션 경계를 가진 구현에서 정확히 동작하는지 따져야 한다. 동작을 보장할 수 없다면 기본 구현이 UnsupportedOperationException을 던지게 하고(Iterator.remove 방식) 그 사실을 문서화하는 편이 조용히 잘못 동작하는 것보다 낫다.

    운영 중에 IncompatibleClassChangeError나 AbstractMethodError가 나면, 원인은 거의 언제나 코드가 아니라 클래스 경로다. 오류 메시지의 "Receiver class X does not define or inherit an implementation of the resolved method"는 대개 X가 그 메서드를 모르는 시점에 컴파일되었다는 뜻이고(OpenJDK 21에서는 본문에서 본 대로 디폴트 충돌도 invokeinterface 경로에서 이 메시지로 나타난다), "Conflicting default methods: A.m B.m"은 X가 컴파일된 뒤에 A와 B가 각자 같은 디폴트를 얻었다는 뜻이다. 의존성 트리에서 같은 라이브러리의 여러 버전이 섞였는지, 플러그인 jar가 어느 버전의 API로 빌드되었는지를 먼저 확인한다. 소스를 다시 컴파일하면 이 오류가 컴파일 오류로 바뀌는지 보는 것이 가장 빠른 진단이다.

    판단이 달라지는 조건도 있다. 인터페이스를 구현하는 쪽이 전부 같은 저장소에 있고 항상 함께 컴파일된다면 추상 메서드 추가도 큰 문제가 아니다. 컴파일러가 빠뜨린 구현을 모두 찾아 주기 때문이다. 이때는 오히려 디폴트 메서드가 "구현을 빠뜨려도 컴파일되는" 위험을 만든다. 디폴트 메서드의 가치는 구현 클래스를 통제할 수 없을 때, 즉 공개 라이브러리나 플러그인 API에서 가장 크다. 반대로 구현 클래스마다 상태가 필요하거나 초기화 순서를 강제해야 한다면 디폴트 메서드로 버티지 말고 추상 클래스를 두는 것이 정직한 설계다. 스프링이 WebMvcConfigurerAdapter를 버리고 디폴트 메서드를 가진 WebMvcConfigurer로 옮긴 것은, 그 어댑터가 상태 없이 빈 메서드만 제공하던 경우였기 때문에 가능했다.

    5번. 메모리: 정적 맵이 모든 구현 객체를 키로 강하게 참조하므로, 다른 곳에서 더는 쓰지 않는 객체도 가비지 컬렉션되지 않는다. 객체가 생길 때마다 맵이 커진다. 동시성: HashMap은 스레드 안전하지 않으므로 여러 스레드가 동시에 merge하면 갱신이 사라지거나 내부 구조가 손상될 수 있다. ConcurrentHashMap으로 바꾸어도 메모리 문제는 그대로다. 동등성: 키 비교가 구현 클래스의 equals/hashCode를 따르므로, 값이 같은 서로 다른 두 객체가 같은 카운터를 공유하고, 가변 객체의 해시코드가 바뀌면 카운터를 잃는다. 결국 인터페이스가 구현 클래스의 동등성 정의라는 남의 계약에 의존하게 된다. 대안은 상태가 필요한 기능을 상태를 가진 쪽에 두는 것이다. 카운터 필드를 가진 추상 클래스를 두거나, 구현 클래스가 필드를 갖고 인터페이스에는 int count() 같은 추상 메서드만 두거나, 객체 바깥에서 세야 한다면 그 책임을 별도 객체(예: 동시성 안전한 카운터를 가진 서비스)로 분리한다.

JLS §8.4.8은 상위 클래스로부터 시그니처가 같은 구체 메서드를 물려받으면 인터페이스의 디폴트 메서드를 상속하지 않는다고 정하고, JVMS §5.4.6도 상위 클래스 사슬을 상위 인터페이스보다 먼저 본다. 이 규칙 덕분에 인터페이스에 같은 이름의 디폴트가 추가되어도 기존 클래스의 동작이 바뀌지 않는다. 클래스가 우선하므로 모호함이 없어 컴파일 오류도, 런타임 오류도 나지 않는다. interface Animal { default String sound() { return "Animal"; } }, interface Dog extends Animal { default String sound() { return "Dog"; } }, class Plain implements Animal { }, class Hound extends Plain implements Dog { }일 때 new Hound().sound()의 결과는? "Animal". 상위 클래스 Plain에서 온 메서드이므로 "클래스가 이긴다"가 적용된다. 컴파일 오류. Plain 경로와 Dog 경로의 구현이 서로 다르다. "Dog". Plain이 가진 것은 물려받은 디폴트일 뿐 클래스에 선언된 메서드가 아니고, Dog.sound가 Animal.sound보다 구체적이다. 실행 중 AbstractMethodError가 난다. JLS §9.4는 디폴트 메서드가 클래스에 선언된 구체 메서드와 구별된다고 명시하므로, Plain이 물려받은 Animal.sound는 "상위 클래스로부터 상속한 구체 메서드"가 아니다. JVM에서도 Hound, Plain, Object에 선언이 없어 상위 인터페이스 단계로 넘어가고, 가장 구체적인 후보는 Dog.sound 하나다. 그래서 모호함도 오류도 없다. 인터페이스 Walker와 Swimmer가 비어 있을 때 class Duck implements Walker, Swimmer를 컴파일해 두었다. 이후 두 인터페이스가 각자 default String move()를 추가했고, 인터페이스와 호출 코드만 다시 컴파일했다. Duck d = new Duck(); d.move();를 OpenJDK 21에서 실행하면? Duck은 정상 로딩되고 객체도 만들어지지만, d.move() 호출에서 "Conflicting default methods" IncompatibleClassChangeError가 난다. Duck을 로딩하는 시점에 VerifyError가 난다. implements 목록에서 먼저 나온 Walker.move가 실행되어 "walk"가 출력된다. JVM이 두 결과를 이어 붙여 "walkswim"을 반환한다. JLS §13.5.7에 따르면 디폴트 메서드 추가는 링크 시점 오류를 만들지 않는 바이너리 호환 변경이지만, 무관한 두 인터페이스가 같은 디폴트를 선언하면 호출 시점에 IncompatibleClassChangeError가 날 수 있다. JVM은 나열 순서로 고르지 않는다. 가장 구체적인 후보 중 추상이 아닌 것이 둘이면 선택에 실패한다. HotSpot은 이 자리에 예외를 던지는 오버패스 메서드를 합성하므로 스택 트레이스에 Duck.move가 찍힌다. 같은 상황을 Walker 타입으로 부르면 OpenJDK 21에서는 AbstractMethodError가 나는데, 이것은 JDK-8356942로 수정된 구현 결함이다. 인터페이스에 default String toString() { ... }을 선언하면 컴파일 오류가 나는 이유로 가장 정확한 것은? Object.toString()이 final이라서 재정의할 수 없기 때문이다. 인터페이스는 Object를 상속하지 않으므로 toString이라는 이름을 알 수 없기 때문이다. 디폴트 메서드는 반환 타입으로 String을 쓸 수 없기 때문이다. 모든 구현 클래스는 Object로부터 toString 구현을 물려받고 클래스 쪽이 디폴트보다 우선하므로, 그 디폴트는 결코 선택될 수 없기 때문이다. JLS §9.4.1.2는 디폴트 메서드가 Object의 private이 아닌 메서드와 오버라이드 동등하면 컴파일 오류라고 정하고, 그 이유로 구현 클래스가 그 메서드의 구현을 이미 물려받는다는 점을 든다. 클래스 사슬이 인터페이스보다 먼저 탐색되므로 그런 디폴트는 실행될 수 없다. Object.toString은 final이 아니다. 클래스는 얼마든지 재정의한다. 인터페이스도 Object의 public 메서드를 멤버로 가진다(Comparator가 equals를 추상으로 재선언하는 것이 그 예다). Square implements Shape이고 Shape에 디폴트 메서드 describe()가 있으며 Square는 그것을 재정의하지 않았다. 다음 중 옳은 것은? javac가 describe()의 바이트코드를 Square.class에 복사해 넣는다. 클래스 로딩 시 JVM이 Square.class 파일을 수정해 describe()를 추가한다. 바이트코드는 Shape.class에만 있고, Square 타입 변수로 부르면 invokevirtual Square.describe가 생성되며 JVM이 해석 단계에서 상위 인터페이스까지 찾아 연결한다. Square 타입 변수로는 describe()를 부를 수 없고 반드시 Shape 타입으로 변환해야 한다. javap -p Square에는 describe가 없다. 디폴트 메서드의 몸체는 인터페이스의 클래스 파일에만 있다. 클래스 타입 변수로 호출하면 상수 풀은 Square.describe를 가리키는데, JVMS §5.4.3.3의 메서드 해석은 클래스와 상위 클래스에서 찾지 못하면 가장 구체적인 상위 인터페이스 메서드를 찾는다. 이렇게 복사 없이 실행 시점에 찾아가기 때문에, 다시 컴파일하지 않은 옛 클래스도 새 디폴트 메서드에 응답할 수 있다.
    디폴트 메서드(default method)
    인터페이스에 default 제어자로 선언한, 몸체가 있는 인스턴스 메서드. 재정의하지 않은 구현 클래스에 기본 구현을 제공한다(JLS §9.4). JEP 126에서는 가상 확장 메서드(virtual extension method)라고 불렀다.
    소스 호환성(source compatibility)
    기존 소스 코드가 새 버전의 라이브러리와 함께 오류 없이 다시 컴파일되는 성질.
    바이너리 호환성(binary compatibility)
    이미 컴파일된 클래스 파일이 다시 컴파일하지 않고도 새 버전과 링크 오류 없이 연결되는 성질(JLS 13장). 링크는 되어도 특정 호출에서 오류가 날 수는 있다.
    메서드 해석(method resolution)
    상수 풀의 기호 참조를 실제 메서드 선언 하나에 연결하는 과정. 클래스와 상위 클래스를 먼저, 그다음 상위 인터페이스를 찾는다(JVMS §5.4.3.3).
    메서드 선택(method selection)
    호출할 때마다 수신 객체의 실제 클래스를 기준으로, 해석된 메서드를 재정의한 메서드 가운데 실행할 것을 고르는 과정(JVMS §5.4.6).
    가장 구체적인 상위 인터페이스 메서드(maximally-specific superinterface method)
    클래스의 상위 인터페이스에 선언된 private·static이 아닌 메서드 가운데, 그 인터페이스의 하위 인터페이스에 같은 메서드가 다시 선언되지 않은 것.
    재추상화(re-abstraction)
    하위 인터페이스가 상위 인터페이스의 디폴트 메서드를 몸체 없이 다시 선언해 추상 메서드로 되돌리는 것. 구현 클래스에 구현 의무가 다시 생긴다.
    오버패스 메서드(overpass method)
    HotSpot이 디폴트 메서드의 선택 오류(예: 충돌하는 디폴트)가 있는 자리에 합성해 넣는 메서드. 호출되면 해당 오류를 던진다. 클래스 파일에는 없다.
    미란다 메서드(miranda method)
    HotSpot 소스의 용어로, 클래스와 상위 클래스 어디에서도 구현되지 않는 private이 아닌 상위 인터페이스 메서드. 클래스의 vtable 끝에 칸이 마련되며, 디폴트 메서드 처리가 이 칸들을 채울 후보로 삼는다.
    골격 구현(skeletal implementation)
    인터페이스 구현을 쉽게 하려고 일부 메서드를 구현해 둔 추상 클래스. AbstractCollection, AbstractList가 대표적이다.
    @implSpec
    JDK 소스의 Javadoc에서 디폴트 메서드의 기본 구현이 무엇을 하는지(그리고 무엇을 보장하지 않는지) 적는 태그. 주로 재정의하는 사람을 위한 정보다.
