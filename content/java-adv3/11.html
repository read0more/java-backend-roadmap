    이 회차의 질문: 람다와 스트림을 쓰면 함수형 프로그래밍인가

    1회부터 10회까지 람다, 함수형 인터페이스, 메서드 참조, 스트림, 컬렉터, Optional, 디폴트 메서드, 병렬 스트림을 차례로 보았다. 모두 자바 8 이후에 들어온 기능이고, 흔히 한데 묶어 "자바의 함수형 프로그래밍 기능"이라고 부른다. 그렇다면 이 기능들을 쓰기만 하면 함수형 프로그래밍을 하고 있는 것일까. 다음 코드를 보자.

    List result = new ArrayList<>();
int[] count = {0};
names.stream().forEach(n -> {
    if (n.length() > 3) {
        result.add(n.toUpperCase());   // 바깥 리스트를 바꾼다
        count[0]++;                    // 바깥 배열을 바꾼다
    }
});

    람다도 있고 스트림도 있다. 하지만 이 코드가 하는 일은 평범한 for 문과 똑같다. 바깥에 만들어 둔 리스트와 배열을 원소 하나마다 고쳐 쓴다. 람다는 반복문의 본문을 다른 자리로 옮겨 놓았을 뿐이다. 반대로 static int square(int x) { return x * x; }라는 정적 메서드에는 람다도 스트림도 없지만, 이 회차에서 정의할 기준으로 보면 흠잡을 데 없는 함수다. 같은 인자에는 언제나 같은 값을 돌려주고, 그 밖에는 아무것도 바꾸지 않는다.

    이 대비가 이 회차의 출발점이다. 함수형 프로그래밍(functional programming)은 특정 문법이 아니라 프로그램이 상태와 효과를 다루는 방식에 대한 제약이다. 계산을 "값을 받아 새 값을 돌려주는 함수"의 조합으로 표현하고, 값을 고쳐 쓰는 일과 입출력은 드러난 몇 곳에 모아 둔다. 람다와 스트림은 이 방식을 자바에서 편하게 쓰게 해 주는 도구이지 그 자체가 목적이 아니다. 도구를 써도 제약을 어기면 함수형이 아니고, 도구 없이도 제약을 지키면 함수형이다.

    이 회차는 세 부분으로 나뉜다. 먼저 프로그래밍 패러다임이라는 큰 그림에서 명령형과 선언형이 무엇이 다른지, 그 뿌리인 두 계산 모델(기계와 치환)까지 정리한다. 다음으로 함수형 프로그래밍을 이루는 개념인 순수 함수, 부수 효과, 참조 투명성, 불변성, 일급 함수와 합성을 정의한다. 마지막으로 자바가 이 개념들을 어디까지 지원하고 어디서 지원하지 않는지 확인한다. 이 부분에서는 클로저의 캡처, 불변 데이터와 자바 메모리 모델의 final 필드 규칙, 합성과 재귀가 쌓는 스택 프레임, 메모이제이션과 HashMap의 구현, 봉인 타입과 패턴 매칭의 바이트코드까지 내려간다. 실행 결과는 모두 Temurin 21.0.13(OpenJDK 21)에서 얻은 것이다.

    프로그래밍 패러다임: 상태와 흐름을 어디에 두는가

    프로그래밍 패러다임(programming paradigm)은 프로그램을 무엇으로 구성하고 그 구성 요소들이 어떻게 상호 작용하는지에 대한 관점이다. 같은 계산을 하는 프로그램이라도 어떤 패러다임으로 쓰느냐에 따라 기본 단위가 달라지고, 코드를 읽을 때 머릿속에 따라가야 하는 것이 달라진다. 패러다임은 언어 하나에 고정된 속성이라기보다 코드의 속성에 가깝다. 대부분의 현대 언어는 여러 패러다임을 함께 지원하는 다중 패러다임(multi-paradigm) 언어이고, 자바도 객체지향을 바탕으로 절차적 코드와 함수형 코드를 모두 쓸 수 있다.

    가장 큰 구분은 명령형(imperative)과 선언형(declarative)이다. 명령형 프로그램은 어떻게 계산할지를 순서대로 적은 명령의 나열이다. 변수에 값을 넣고, 조건을 검사하고, 반복하면서 상태를 한 단계씩 바꿔 원하는 결과에 도달한다. 선언형 프로그램은 무엇을 원하는지를 적는다. 결과가 만족해야 할 조건을 기술하고, 그 조건을 만족시키는 구체적인 절차는 언어의 실행 체계나 라이브러리, 엔진이 정한다.

    선언형의 가장 익숙한 예는 SQL이다. SELECT name FROM member WHERE age >= 20 ORDER BY name은 "20세 이상인 회원의 이름을 이름순으로"라는 결과만 말한다. 테이블을 처음부터 끝까지 훑을지, 인덱스를 탈지, 정렬을 따로 할지 인덱스 순서를 그대로 쓸지는 데이터베이스의 옵티마이저가 정한다. 데이터베이스 기본편에서 실행 계획을 읽을 때 본 것처럼 같은 SQL이 데이터 분포와 인덱스에 따라 전혀 다른 절차로 실행된다. 선언형 코드는 "무엇"만 고정하고 "어떻게"를 바꿀 여지를 실행하는 쪽에 남긴다. 스트림이 같은 파이프라인을 순차로도 병렬로도 실행할 수 있는 것(10회)도 같은 성질에서 나온다.

    명령형과 선언형 안에서 다시 세부 패러다임이 나뉜다. 아래 표는 이 회차에서 비교할 세 가지를 "상태"와 "흐름"이라는 두 기준으로 정리한 것이다.

    패러다임기본 단위상태를 다루는 방식흐름을 표현하는 방식
    절차적(procedural)프로시저(함수, 메서드)프로시저가 공유 변수나 넘겨받은 데이터를 직접 바꾼다문장의 순서, 반복문, 조건문, 프로시저 호출
    객체지향(object-oriented)객체(상태 + 행동)상태를 객체 안에 숨기고, 그 객체의 메서드를 통해서만 바꾼다객체 사이의 메시지(메서드 호출), 다형성
    함수형(functional)함수(값을 받아 값을 돌려줌)상태를 바꾸지 않고 새 값을 만든다. 꼭 바꿔야 하는 상태는 프로그램의 경계로 밀어낸다함수의 합성, 고차 함수, 재귀

    절차적 패러다임과 객체지향은 모두 명령형에 속한다. 둘의 차이는 "상태를 누가 바꿀 수 있는가"다. 절차적 코드에서는 어떤 프로시저든 공유 데이터를 바꿀 수 있으므로, 데이터가 이상해지면 그 데이터에 닿는 모든 프로시저를 의심해야 한다. 객체지향은 상태를 객체 안에 캡슐화하고 메서드라는 문을 통해서만 바꾸게 해서 의심할 범위를 그 클래스로 줄인다. 함수형은 한 걸음 더 나가 "상태를 아예 바꾸지 않으면 어떨까"를 묻는다. 바뀌지 않는 값은 누가 언제 읽어도 같으므로, 무언가 잘못되었을 때 의심할 범위가 그 값을 만든 함수 하나로 줄어든다.

    객체지향과 함수형은 서로 반대말이 아니다. 자바 기본편에서 본 String은 메서드를 가진 객체이면서, 한 번 만들어지면 내용이 바뀌지 않는 불변 객체다. toUpperCase()는 자신을 바꾸지 않고 새 String을 돌려준다. 객체로 설계하되 객체의 상태를 바꾸지 않는 방식, 이것이 자바에서 함수형 스타일이 가장 자연스럽게 섞이는 지점이다. 이 회차의 뒷부분에서 레코드와 불변 컬렉션으로 이 방식을 다시 본다.

    같은 문제, 두 가지 코드: 상태는 어디로 갔는가

    패러다임의 차이를 말로만 비교하면 막연하다. 같은 문제를 두 방식으로 풀고, 실행 중에 무엇이 바뀌는지를 직접 추적해 보자. 문제는 이렇다. 단어 목록에서 길이가 4 이상인 단어만 골라 대문자로 바꾸고, 중복을 없앤 뒤 사전순으로 정렬해 앞의 세 개를 얻는다.

    import java.util.*;
import java.util.stream.*;

public class Words {
    static List imperative(List words) {
        Set seen = new HashSet<>();
        List result = new ArrayList<>();
        for (String w : words) {
            if (w.length() >= 4) {
                String u = w.toUpperCase();
                if (seen.add(u)) {
                    result.add(u);
                }
            }
        }
        Collections.sort(result);
        if (result.size() > 3) {
            result = result.subList(0, 3);
        }
        return result;
    }

    static List declarative(List words) {
        return words.stream()
                .filter(w -> w.length() >= 4)
                .map(String::toUpperCase)
                .distinct()
                .sorted()
                .limit(3)
                .toList();
    }

    public static void main(String[] args) {
        List words = List.of("stream", "jvm", "java", "lambda", "java", "fp", "optional");
        System.out.println(imperative(words));
        System.out.println(declarative(words));
    }
}

    이 코드를 이해하려면 이 표를 머릿속에서 만들어야 한다. result라는 이름은 루프의 어느 지점에서 보느냐에 따라 다른 내용을 가리키고, 마지막 if를 지나면 아예 다른 객체를 가리킨다. 그 객체도 함정을 품고 있다. subList는 복사본이 아니라 원래 ArrayList의 일부를 비춰 보는 뷰(view)라서, 호출자가 돌려받은 리스트에 원소를 넣으면 호출자에게는 보이지 않는 원래 리스트가 함께 바뀐다. 네 원소짜리 원래 리스트도 뷰가 살아 있는 동안 함께 살아 있다. 상태를 바꾸는 코드는 이렇게 "이 값이 지금 누구와 연결되어 있는가"를 계속 신경 쓰게 만든다.

    선언형 버전에는 다시 대입되는 지역 변수가 하나도 없다. 각 단계는 독립된 문장처럼 읽힌다. filter는 "길이 4 이상만", map은 "대문자로", distinct는 "중복 없이", sorted는 "사전순으로", limit은 "세 개까지"다. 단계의 순서에는 의미가 있지만(입력에 "Java"와 "java"가 섞여 있다면 distinct를 map보다 앞에 둘 때 결과에 JAVA가 두 번 나온다), 한 단계를 이해하는 데 다른 단계의 내부 상태를 알 필요는 없다. 결과도 toList()가 돌려준 수정 불가능한 새 리스트라서, 호출자가 받은 값이 다른 무엇과 연결되어 있을지 걱정할 필요가 없다.

    그렇다면 상태는 사라졌는가. 아니다. 6회에서 보았듯 distinct는 내부에 이미 본 원소의 집합을 갖고, sorted는 원소를 모아 둘 버퍼를 갖고, limit은 지금까지 몇 개를 내보냈는지 센다. 명령형 버전의 seen, 정렬, 자르기가 하던 일과 같다. 차이는 그 상태가 어디에 있는가다. 명령형 버전에서는 상태가 우리가 쓴 코드 한가운데 있고, 선언형 버전에서는 표준 라이브러리 안의 정해진 경계 뒤로 옮겨 갔다. 우리가 쓴 부분인 w -> w.length() >= 4와 String::toUpperCase에는 상태가 없다. 함수형 스타일의 실질은 상태를 없애는 것이 아니라, 상태를 다루는 책임을 검증된 좁은 곳으로 옮기고 나머지를 상태 없는 함수로 만드는 것이다.

JVM은 지역 변수 칸과 피연산자 스택이라는 상태를 명령으로 바꿔 가는 기계이고, 그 아래의 CPU도 레지스터와 메모리를 읽고 쓰는 기계다. 스트림 파이프라인도 결국 라이브러리 안의 반복문(5회에서 본 forEachRemaining)으로 실행된다. 즉 패러다임은 기계가 아니라 사람이 읽고 추론하는 수준의 코드를 어떻게 조직하느냐의 문제다. 선언형 코드가 주는 이득은 실행 속도가 아니라, 우리가 읽고 검증해야 하는 코드에서 시간에 따라 바뀌는 것을 줄이는 데 있다.

    두 계산 모델: 기계의 상태와 식의 치환

    명령형과 함수형의 차이는 계산을 설명하는 두 모델로 거슬러 올라간다. 첫째는 기계 모델이다. 튜링 기계(Turing machine)는 테이프의 칸을 읽고, 칸에 기호를 쓰고, 내부 상태를 바꾸는 단계를 되풀이한다. 오늘날 컴퓨터의 바탕인 폰 노이만 구조(von Neumann architecture)도 프로그램과 데이터를 같은 메모리에 두고, CPU가 명령을 하나씩 가져와 메모리를 읽고 쓰는 구조다. 명령형 언어의 대입문 x = x + 1은 이 모델을 그대로 옮긴 것이다. 여기서 변수 x는 값의 이름이 아니라 저장 칸의 이름이고, 칸의 내용은 시간이 지나면서 바뀐다. 그래서 "x는 얼마인가"라는 질문에는 "언제의 x인가"라는 질문이 따라붙는다.

    둘째는 람다 대수(lambda calculus)다. 람다 대수는 함수를 만드는 추상화(abstraction), 함수를 인자에 적용하는 적용(application), 그리고 적용을 계산하는 치환(substitution)만으로 이루어진 형식 체계다. λx.M은 "x를 받아 M을 돌려주는 함수"이고, 자바 문법으로 옮기면 x -> M이다. (λx.M) N을 계산하는 규칙인 베타 축약(β-reduction)은 M 안의 x 자리에 N을 끼워 넣는 것이 전부다. 스탠퍼드 철학 백과사전(SEP)의 람다 대수 항목은 함수 추상화를 λ로 표기한 처치(Alonzo Church)의 1932년 논문을 인용하고, 이 모델이 튜링 기계나 레지스터 기계 같은 다른 계산 모델과 정확히 같은 표현력을 가진다고 설명한다. 두 모델이 계산할 수 있는 것의 범위는 같다. 다른 것은 계산을 설명하는 방식, 그리고 그 설명으로 프로그램을 추론하는 방식이다.

    [기계 모델: 저장 칸이 바뀐다]              [치환 모델: 식이 값으로 줄어든다]

 x 칸: 3                                     square(3 + 4)
 x = x + 1   →  x 칸: 4                      → square(7)          (인자를 값으로)
 x = x * 2   →  x 칸: 8                      → 7 * 7              (본문의 x 자리에 7을 넣음)
                                             → 49
 "x"의 뜻은 언제 보느냐에 따라 다르다        "square(3 + 4)"의 값은 언제 보아도 49다

    치환 모델로 추론하려면 조건이 하나 필요하다. 식 안에서 저장 칸의 내용을 바꾸는 일이 일어나지 않아야 한다. 호출할 때마다 카운터를 1씩 올려 돌려주는 next()가 있다고 하자. 자바는 인자를 먼저 계산하므로 square(next())는 next()를 한 번 호출해 그 값을 제곱한다. 그런데 치환 모델로 생각하는 사람은 "square(x)의 본문 x * x에서 x 자리에 인자 식을 넣어도 같다"고 여길 것이고, 그렇게 바꿔 쓴 next() * next()는 서로 다른 두 값을 곱한다. 부수 효과가 없을 때에만 "인자를 먼저 계산해 넣든, 식을 그대로 넣든" 결과가 같다. 대입이 끼어드는 순간 "식을 그 값으로 바꿔 넣는다"는 추론 방법이 무너진다. 함수형 프로그래밍이 대입과 상태 변경을 피하는 이유는 취향이 아니라, 이 치환 모델을 추론의 도구로 계속 쓰기 위해서다. 다음 두 절에서 이 조건을 순수 함수와 참조 투명성이라는 이름으로 정확히 정의한다.

    함수형 프로그래밍이란 1: 순수 함수와 부수 효과

    함수형 프로그래밍의 기본 단위는 순수 함수(pure function)다. 메서드가 다음 두 조건을 모두 만족하면 순수 함수라고 한다.

    1. 결과가 인자에만 의존한다. 같은 인자로 호출하면 언제, 몇 번째로 호출하든 같은 결과를 돌려준다.
    2. 결과를 돌려주는 것 말고는 관찰 가능한 효과가 없다. 호출하기 전과 후에 프로그램의 나머지 부분이 볼 수 있는 상태가 달라지지 않는다.

    두 번째 조건을 어기는 것을 부수 효과(side effect)라고 한다. 자바 코드에서 부수 효과는 구체적으로 다음과 같은 일이다. 인스턴스 필드나 정적 필드의 값을 바꾼다. 인자로 받은 객체의 상태를 바꾼다(넘겨받은 List에 add하는 것). 콘솔, 파일, 네트워크, 데이터베이스에 무언가를 쓰거나 읽는다. 다른 스레드를 시작하거나 락을 잡는다. 첫 번째 조건을 어기는 것은 반대 방향의 일이다. 바뀔 수 있는 외부 상태를 읽는 것으로, 변하는 필드, 현재 시각(LocalDateTime.now()), 난수(Math.random()), 파일의 내용 같은 것이 결과에 들어가면 같은 인자에도 다른 결과가 나온다. 바뀌지 않는 상수(static final int)를 읽는 것은 인자와 다를 바 없으므로 순수성을 해치지 않는다.

    예외는 조금 다르게 보아야 한다. 같은 인자에 대해 언제나 같은 예외를 던지는 메서드(예를 들어 음수를 받으면 IllegalArgumentException을 던지는 메서드)는 첫 번째 조건을 어기지 않는다. 다만 예외는 반환 타입에 드러나지 않는 탈출 경로라서, 호출하는 쪽이 그 경로를 잊기 쉽다는 점에서 8회의 null과 비슷한 문제를 갖는다. 예상되는 실패를 Optional이나 실패를 담는 결과 타입처럼 반환값으로 표현하는 방식은 그 경로를 시그니처로 끌어올리는 방법이다. 이 회차에서는 "같은 입력에 같은 예외"는 결과의 일부로 보고, 입출력이나 외부 상태 때문에 어떤 때는 던지고 어떤 때는 던지지 않는 예외는 순수성을 깨는 것으로 본다.

    다음 프로그램으로 두 조건을 확인해 보자. 뒤 절에서도 이 프로그램을 계속 쓴다.

    public class Purity {
    static int base = 10;
    static int impure(int x) { return x + base; }        // 외부 상태를 읽는다
    static int pure(int x, int b) { return x + b; }       // 입력만으로 결과가 정해진다

    static int counter = 0;
    static int next() { return ++counter; }              // 외부 상태를 바꾼다

    public static void main(String[] args) {
        int a = impure(1);
        base = 20;
        int b = impure(1);
        System.out.println(a + " " + b);                  // 같은 인자, 다른 결과

        int s1 = next() + next();
        counter = 0;
        int v = next();
        int s2 = v + v;
        System.out.println(s1 + " " + s2);                // 치환하면 결과가 바뀐다

        System.out.println(pure(1, 10) + " " + pure(1, 10));

        String x = new String("ab");
        String y = new String("ab");
        System.out.println(x.equals(y) + " " + (x == y));
    }
}

    첫 줄이 첫 번째 조건 위반이다. impure(1)은 두 번 모두 인자 1을 받았지만 11과 21을 돌려주었다. 결과가 인자 말고도 base라는 바뀔 수 있는 필드에 의존하기 때문이다. 이 메서드의 시그니처 int impure(int)만 보고는 이 의존을 알 수 없다는 점이 핵심이다. 호출하는 쪽에서 보면 숨은 입력이 하나 더 있는 셈이다. pure(int, int)는 같은 계산을 하면서 그 숨은 입력을 매개변수로 드러냈다. 그러면 결과는 인자만으로 결정되고, 셋째 줄처럼 몇 번을 불러도 같다.

    순수성은 메서드 바깥에서 관찰되는 동작에 대한 성질이라는 점도 짚어 두자. 앞 절의 sumLoop는 안에서 지역 변수 acc와 n을 계속 덮어쓰지만, 그 변수들은 호출이 끝나면 프레임과 함께 사라지고 바깥에서는 볼 수 없다. 같은 n에 언제나 같은 값을 돌려주고 바깥의 아무것도 바꾸지 않으므로 sumLoop는 순수 함수다. "함수형이면 변수를 한 번도 바꾸면 안 된다"는 말은 지나친 일반화다. 바깥으로 새어 나가지 않는 지역 상태의 변경은 순수성을 해치지 않는다. 스트림 라이브러리가 안에서 상태를 쓰면서도 words.stream()...toList() 전체가 "리스트를 받아 새 리스트를 돌려주는 함수"로 동작하는 것도 같은 원리다.

    순수 함수가 주는 이득은 정의에서 바로 따라 나온다. 테스트는 "이 입력이면 이 출력"을 확인하는 것으로 끝나고, 미리 만들어 둘 환경이나 가짜 객체가 필요 없다. 메서드를 이해하려면 그 메서드의 본문만 읽으면 된다. 결과가 인자에만 의존하므로 한 번 계산한 결과를 저장해 두고 다시 쓸 수 있다(메모이제이션, 뒤에서 다룬다). 서로의 결과를 쓰지 않는 두 호출은 순서를 바꾸거나 동시에 실행해도 결과가 같으므로 병렬화의 전제 조건이 된다. 10회에서 병렬 스트림에 넘기는 함수가 상태를 갖지 않아야 한다고 한 것이 바로 이 조건이다. 그리고 공유된 가변 상태가 없으니 여러 스레드가 동시에 불러도 경쟁 조건(race condition)이 생기지 않는다.

    함수형 프로그래밍이란 2: 참조 투명성과 치환

    순수 함수와 짝을 이루는 개념이 참조 투명성(referential transparency)이다. 어떤 식을 그 식의 값으로 바꿔 넣어도(또는 반대로 값을 그 값을 만드는 식으로 바꿔 넣어도) 프로그램의 의미가 달라지지 않으면 그 식은 참조 투명하다. 앞 절의 치환 모델이 그대로 쓸 수 있는 식이라는 뜻이다. 순수 함수를 참조 투명한 인자로 호출한 식은 참조 투명하다. pure(1, 10)은 프로그램 어디에서든 11로 바꿔 써도 된다.

    Purity의 둘째 줄이 참조 투명하지 않은 식의 예다. 리팩터링에서 흔히 하는 일을 떠올려 보자. 같은 식이 두 번 나오면 변수 하나로 뽑아내는 "공통 부분식 추출"이다. next() + next()를 int v = next(); v + v로 바꾸는 것이 그것인데, 결과는 3에서 2로 바뀌었다. 첫 번째 식에서는 next()가 두 번 실행되어 1과 2를 더했고, 두 번째 식에서는 한 번 실행된 1을 두 번 더했다. 식 next()가 "부를 때마다 다른 값"이므로 그 값으로 바꿔 넣는 순간 의미가 바뀐다. 이 리팩터링이 안전한지는 IDE가 아니라 next()의 본문이 결정한다.

    컴파일러도 같은 원리를 따른다. JIT 컴파일러가 하는 공통 부분식 제거(common subexpression elimination) 같은 최적화는 두 계산 사이에 결과를 바꿀 수 있는 쓰기가 없음을 증명할 수 있을 때만 일어난다. next()처럼 필드를 쓰는 호출은 합치지 않는다. 최적화는 한 스레드 안에서 관찰되는 결과를 바꿀 수 없기 때문이다. 사람이 하는 리팩터링도 마찬가지 규칙을 지켜야 하는데, 사람은 증명 대신 짐작에 기대기 쉽다는 것이 차이다. 참조 투명한 코드에서는 그 짐작이 언제나 맞는다.

    넷째 줄은 자바에서만 생기는 미묘한 경우다. new String("ab")를 두 번 평가하면 equals로는 같지만 ==로는 다른 두 객체가 나온다. 자바 21에서 모든 객체는 정체성(identity)을 가지며 ==는 참조, 즉 정체성을 비교한다. 따라서 "같은 인자로 같은 객체를 만드는" 생성 식조차 ==로 관찰하면 참조 투명하지 않다. 자바에서 참조 투명성을 말할 때는 "equals 기준으로 같은 값"이라는 단서가 따라붙는다. 8회에서 Optional 같은 값 기반 클래스에 ==나 synchronized를 쓰지 말라고 한 이유가 여기에 있다. 정체성을 관찰하는 연산을 쓰지 않아야 "같은 값의 다른 인스턴스"를 서로 바꿔 써도 의미가 유지된다.

    이 장의 핵심

    순수 함수는 결과가 인자에만 의존하고 결과 말고는 아무 흔적도 남기지 않는 함수다. 그런 함수로 만든 식은 그 값으로 바꿔 넣어도 의미가 같다(참조 투명성). 이 성질 하나에서 테스트 용이성, 지역적 추론, 캐싱, 재배치와 병렬화, 스레드 안전성이 모두 따라 나온다. 자바에서는 여기에 "정체성을 관찰하지 않는다"는 조건을 더해야 한다.

    함수형 프로그래밍이란 3: 불변성, 일급 함수, 합성

    순수 함수는 "값을 받아 새 값을 돌려준다". 그렇다면 그 값 자체는 어떠해야 할까. 함수가 돌려준 객체를 누군가 나중에 고칠 수 있다면, 그 객체를 받은 다른 코드의 결과가 시간에 따라 달라진다. 그래서 함수형 프로그래밍은 불변성(immutability)을 함께 요구한다. 불변 값은 만들어진 뒤 내용이 바뀌지 않는다. "값을 바꾼다"는 일은 기존 값을 고치는 것이 아니라 바뀐 내용을 가진 새 값을 만드는 것으로 바뀐다. 다음 레코드가 그 모양이다.

    record Account(String id, long balance) {
    Account deposit(long amount) {
        if (amount <= 0) throw new IllegalArgumentException("amount must be positive");
        return new Account(id, balance + amount);   // 자신을 고치지 않고 새 값을 만든다
    }
}

Account a1 = new Account("A-1", 1_000);
Account a2 = a1.deposit(500);
System.out.println(a1 + " " + a2 + " " + (a1 == a2));

    입금 후에도 a1은 1000원 그대로다. a1을 쥐고 있던 다른 코드가 있었다면 그 코드가 보는 값도 그대로다. 힙에는 두 객체가 있고, 1000원짜리 객체는 아무도 참조하지 않게 되면 가비지 컬렉터가 회수한다. 대가는 할당이다. 변경할 때마다 새 객체를 만들고, 그 객체가 큰 컬렉션을 품고 있다면 복사 비용도 든다. 자바 표준 라이브러리의 불변 컬렉션(List.of 등)은 원소 하나를 바꾼 새 리스트를 만드는 연산을 제공하지 않으므로, 컬렉션을 "바꾸려면" 새로 만들어야 한다. 불변성은 공짜가 아니며, 그 대가를 치를 가치가 있는 곳을 고르는 것이 설계다.

    함수형 프로그래밍의 나머지 재료는 함수를 다루는 방식이다. 일급 함수(first-class function)는 함수를 다른 값과 똑같이 변수에 담고, 인자로 넘기고, 결과로 돌려줄 수 있다는 뜻이고, 함수를 받거나 돌려주는 함수를 고차 함수(higher-order function)라고 한다. 1회에서 보았듯 자바에는 함수 타입이 없고, 함수는 함수형 인터페이스를 구현한 객체로 표현된다. 그래서 자바의 함수는 "일급 객체로 포장된 함수"다. 이 포장 덕분에 함수에도 메서드를 붙일 수 있고, 그 메서드로 함수를 조립할 수 있다. 그 대표가 함수 합성(function composition)이다.

    수학에서 두 함수 f와 g의 합성 g∘f는 "x에 f를 적용하고 그 결과에 g를 적용하는 함수"다. java.util.function.Function은 이것을 디폴트 메서드 두 개로 제공한다. OpenJDK 21의 소스는 다음과 같다(주석 생략).

    default  Function compose(Function before) {
    Objects.requireNonNull(before);
    return (V v) -> apply(before.apply(v));
}

default  Function andThen(Function after) {
    Objects.requireNonNull(after);
    return (T t) -> after.apply(apply(t));
}

static  Function identity() {
    return t -> t;
}

    두 메서드는 모두 새 람다를 만들어 돌려주는 고차 함수다. f.andThen(g)는 "먼저 f, 그다음 g"이고, f.compose(g)는 "먼저 g, 그다음 f"다. 돌려주는 람다 본문의 apply(...)는 this.apply(...)이므로, 이 람다는 바깥 함수(this)와 인자로 받은 함수(before 또는 after)를 캡처한다. 함수 두 개를 붙잡은 새 함수 객체가 하나 생기는 것이다. 합성은 이런 객체를 사슬처럼 이어 붙인다. 이 사슬이 스택에서 어떻게 풀리는지는 뒤의 "한 층 아래" 절에서 다시 본다.

    import java.util.function.*;

public class Compose {
    public static void main(String[] args) {
        Function plus1 = x -> x + 1;
        Function times2 = x -> x * 2;
        System.out.println(plus1.andThen(times2).apply(5));   // (5+1)*2
        System.out.println(plus1.compose(times2).apply(5));   // 5*2+1

        Function> add = p -> q -> p + q;
        Function add10 = add.apply(10);
        System.out.println(add10.apply(5) + " " + add.apply(1).apply(2));

        Predicate empty = String::isEmpty;
        Predicate notEmpty = Predicate.not(empty);
        Predicate shortWord = s -> s.length() < 4;
        System.out.println(notEmpty.and(shortWord).test("abc") + " " + notEmpty.and(shortWord).test(""));
        // ... (뒤 절에서 이어진다)
    }
}

    합성이 쌓이면 코드는 "무엇을 할지"를 조립한 선언이 된다. 앞의 Words 파이프라인이 그 예이고, 8회의 Optional.map 사슬도 같다. 그리고 합성된 함수는 호출되기 전까지 아무것도 계산하지 않는다는 점에서, 8회에서 본 지연 평가(값 대신 값을 만드는 코드를 넘겨 필요할 때 계산하는 것)와도 이어진다. 불변 값, 순수 함수, 그 함수들의 합성. 이 세 가지가 함수형 프로그래밍의 뼈대다.

    자바와 함수형 프로그래밍 1: 도구 상자와 빈자리

    자바는 순수 함수형 언어가 아니다. 객체지향 언어로 출발해 버전마다 함수형 스타일을 쓰기 위한 도구를 더해 왔다. 아래 표는 이 강좌에서 다룬 것과 이 회차에서 다룰 것을 도입 버전 순으로 정리한 것이다. 버전은 JDK 21 소스의 @since 태그와 해당 JEP 문서로 확인했다.

    버전도입된 것함수형 관점에서의 의미

    도구가 많아졌지만, 자바가 하지 않는 일도 분명하다. 이 빈자리를 알아야 자바에서 함수형 스타일을 어디까지 믿을 수 있는지 판단할 수 있다.

    • 순수성을 강제하지 않는다. 메서드가 순수한지 표시하는 키워드가 없고, 컴파일러는 람다 본문이 필드를 바꾸든 파일을 쓰든 검사하지 않는다. 스트림 문서가 요구하는 "상태 없음"과 "간섭 없음"도 지키는 사람의 책임인 계약이다. 어겼을 때 일부 경우에만 ConcurrentModificationException 같은 예외로 드러난다.
    • 깊은 불변성을 표현할 방법이 없다. final은 변수나 필드에 다시 대입하는 것을 막을 뿐, 그 변수가 가리키는 객체의 내용은 막지 않는다. final List list에도 list.add는 된다. 레코드도 같은 이유로 얕은 불변이다(뒤에서 확인한다).
    • 함수 타입이 없다. 함수는 이름 있는 함수형 인터페이스의 인스턴스이고, 모양이 같아도 인터페이스가 다르면 서로 대입할 수 없다(1회, 2회).
    • 꼬리 호출 제거를 보장하지 않는다. 함수형 언어에서 반복을 대신하는 재귀가 자바에서는 호출마다 스택 프레임을 쌓는다(뒤에서 확인한다).
    • 검사 예외가 함수형 인터페이스와 맞지 않는다. Function.apply에는 throws 절이 없으므로 검사 예외를 던지는 메서드를 그대로 넘길 수 없다(2회).
    • 모든 객체가 정체성을 갖는다. 앞 절에서 본 것처럼 ==는 같은 값의 다른 객체를 구별해 낸다.

    정리하면 자바의 함수형 프로그래밍은 언어가 보장하는 성질이라기보다 규율(discipline)이다. 언어는 도구를 주고, 제약은 프로그래머가 지킨다. 그래서 자바에서 함수형 스타일을 쓸 때는 "이 람다가 정말 순수한가", "이 객체가 정말 불변인가"를 코드 리뷰에서 확인해야 하고, 그 확인을 돕는 것이 이 회차의 나머지 내용이다. 다음 세 절은 각각 부수 효과(클로저와 스트림), 불변 데이터(레코드와 컬렉션), 데이터와 함수의 분리(봉인 타입과 패턴 매칭)를 다룬다.

    자바와 함수형 프로그래밍 2: 클로저, 사실상 final, 그리고 부수 효과

    람다가 바깥 지역 변수를 쓰면 그 값이 람다 객체 안으로 복사된다는 것을 1회와 4회에서 바이트코드로 확인했다. 함수와, 그 함수가 만들어질 때의 환경(캡처한 값)을 함께 묶은 것을 클로저(closure)라고 부른다. 캡처가 복사이므로 원본 변수가 나중에 바뀌면 사본과 어긋난다. 그래서 자바는 람다가 쓰는 바깥 지역 변수가 final이거나 사실상 final(effectively final)이어야 한다고 정하고, 어기면 컴파일하지 않는다.

    int total = 0;
List.of(1, 2, 3).forEach(x -> total += x);

        List.of(1, 2, 3).forEach(x -> total += x);

    함수형의 관점에서 보면 이 규칙은 반쪽짜리 안전장치다. 막는 것은 변수에 대한 재대입이지, 변수가 가리키는 객체의 변경이 아니다. 그래서 다음 코드는 컴파일되고, 흔히 위 오류를 "피하는 요령"으로 쓰인다.

    import java.util.*;
import java.util.function.*;

public class Closure {
    static Supplier counter() {
        int[] box = {0};                 // 람다가 캡처하는 것은 배열 참조(사실상 final)
        return () -> ++box[0];           // 배열 내용은 바뀐다
    }
    static IntUnaryOperator adder(int n) {
        return x -> x + n;               // n의 값이 복사되어 캡처된다
    }
    public static void main(String[] args) {
        Supplier c1 = counter();
        Supplier c2 = counter();
        System.out.println(c1.get() + " " + c1.get() + " " + c2.get());
        IntUnaryOperator add5 = adder(5);
        System.out.println(add5.applyAsInt(1) + " " + add5.applyAsInt(1));
        System.out.println(List.of(1, 2, 3).stream().peek(System.out::println).count());
    }
}

    이 그림에서 클로저의 또 다른 성질도 보인다. counter()가 반환하는 순간 그 프레임과 지역 변수 box는 사라지지만, 배열 객체는 힙에 있고 람다 객체가 참조하고 있으므로 살아남는다. 클로저는 자신이 캡처한 환경의 수명을 늘린다. 4회에서 본 "리스너로 등록한 람다가 바깥 객체를 붙잡는" 문제와 같은 구조다.

    배열 우회로를 병렬 스트림이나 다른 스레드에 넘기면 문제가 순수성에서 정확성으로 커진다. ++box[0]은 바이트코드에서 배열 칸 읽기(iaload), 더하기(iadd), 쓰기(iastore)로 나뉘는 읽기-수정-쓰기 연산이라서, 두 스레드가 동시에 실행하면 갱신 하나가 사라질 수 있다(자바 고급 1편의 경쟁 조건). AtomicInteger로 바꾸면 원자성은 생기지만 함수는 여전히 호출 순서에 따라 다른 값을 돌려준다. 사실상 final 규칙을 통과했다는 것은 "컴파일된다"는 뜻일 뿐 "순수하다"는 뜻이 아니다.

    스트림은 부수 효과를 어떻게 다루는가

    스트림의 패키지 문서(java.util.stream의 Side-effects 절)는 이 문제를 직접 다룬다. 요지를 옮기면 이렇다. 스트림 연산에 넘기는 동작 매개변수(behavioral parameter)의 부수 효과는 일반적으로 권장하지 않는다. 부수 효과가 있다면, 따로 명시하지 않은 한 그 효과가 다른 스레드에 보이는지, 같은 원소에 대한 여러 연산이 같은 스레드에서 실행되는지, 그리고 동작 매개변수가 애초에 호출되기는 하는지를 보장하지 않는다. 결과에 영향을 주지 않는다는 것을 증명할 수 있으면 구현은 연산이나 단계 전체를 생략할 수 있다고 문서는 밝힌다.

    Closure의 셋째 출력이 그 생략의 실제 예다. peek(System.out::println)이 원소 세 개를 출력할 것 같지만, 실제 출력은 count()의 결과 3 하나뿐이다. List.of(1, 2, 3)은 크기를 정확히 아는 소스이고 peek은 원소 수를 바꾸지 않으므로, 구현은 파이프라인을 실행하지 않고 소스의 크기로 개수를 구했다. 5회에서 본 플래그 기반 최적화이고, Stream.count의 API 노트가 바로 이 peek 예를 들어 설명한다. 사이에 filter(x -> true)를 하나 끼우면 원소 수를 미리 알 수 없게 되어 파이프라인이 실제로 실행되고, peek도 세 번 호출된다(연습 문제에서 확인한다).

    이 생략이 정당한 이유가 앞 절의 참조 투명성이다. peek에 넘긴 함수가 순수했다면, 그 함수를 부르든 부르지 않든 관찰되는 결과는 같다. 라이브러리는 동작 매개변수가 순수하다는 가정 위에서 최적화했고, 그 가정을 깬 쪽은 출력이라는 부수 효과를 넣은 우리 코드다. 같은 이유로 회차 처음의 코드는 부수 효과 없이 다시 써야 한다. 패키지 문서도 forEach로 바깥 ArrayList에 담는 코드를 리덕션(toList())으로 바꾸는 예를 든다.

    List result = names.stream()
        .filter(n -> n.length() > 3)
        .map(String::toUpperCase)
        .toList();
int count = result.size();

    부수 효과를 가장자리로: 순수한 핵심과 입출력 껍질

    실제 프로그램은 부수 효과 없이는 쓸모가 없다. 결과를 화면에 보여 주고, 데이터베이스에 저장하고, 다른 서버에 요청을 보내야 한다. 함수형 프로그래밍의 답은 부수 효과를 없애는 것이 아니라 분리하는 것이다. 계산은 순수 함수로 하고, 입력을 읽고 결과를 내보내는 일은 프로그램의 가장자리에 모은다. 작은 예로 장바구니 계산을 보자.

    import java.util.*;

public class Shell {
    record Item(String name, int price, int qty) {}
    record Receipt(List items, int subtotal, int discount, int total) {}

    // 순수한 핵심: 입력만 보고 새 값을 만든다
    static int subtotal(List items) {
        return items.stream().mapToInt(i -> i.price() * i.qty()).sum();
    }
    static int discount(int subtotal) {
        return subtotal >= 50_000 ? subtotal / 10 : 0;
    }
    static Receipt checkout(List items) {
        int sub = subtotal(items);
        int dc = discount(sub);
        return new Receipt(List.copyOf(items), sub, dc, sub - dc);
    }

    // 바깥 껍질: 입력과 출력(부수 효과)은 여기서만
    public static void main(String[] args) {
        List cart = List.of(new Item("book", 18_000, 2), new Item("pen", 1_500, 10));
        Receipt r = checkout(cart);
        System.out.println(r.subtotal() + " - " + r.discount() + " = " + r.total());
    }
}

    계산을 따라가 보자. 책은 18,000원짜리 두 권이라 36,000원, 펜은 1,500원짜리 열 자루라 15,000원, 합계는 51,000원이다. 50,000원 이상이므로 10%인 5,100원이 할인되고 최종 금액은 45,900원이다. subtotal, discount, checkout은 모두 인자만 보고 새 값을 돌려준다. 필드를 읽지도 쓰지도 않고, 출력도 하지 않는다. checkout이 List.copyOf(items)로 장바구니를 복사해 영수증에 담는 것은, 호출자가 나중에 원래 리스트를 바꾸더라도 이미 발행된 영수증은 바뀌지 않게 하기 위해서다. 부수 효과는 main의 println 하나뿐이다.

    이렇게 나누면 핵심 계산은 assert checkout(List.of(...)).total() == 45900 같은 한 줄로 시험할 수 있다. 데이터베이스도, 가짜 객체도, 스프링 컨텍스트도 필요 없다. 할인 정책이 바뀌면 discount 하나만 고치고 그 함수의 입력과 출력만 다시 확인하면 된다. 실제 서비스에서는 main의 자리에 저장소에서 장바구니를 읽고 결과를 저장한 뒤 HTTP 응답을 만드는 코드가 온다. 그 코드가 껍질이고, 껍질은 얇을수록 좋다. 껍질에는 판단이 없고 핵심에는 효과가 없도록 나누는 것이 목표다.

    스프링과 JPA로 돌아가 보면 이 분리가 어디에 적용되는지 분명해진다. 서비스 계층의 흔한 메서드는 "엔티티 조회 → 계산 → 변경 → 저장"이다. 이 가운데 계산 부분을 순수한 메서드(또는 값 객체의 메서드)로 뽑으면 그 부분은 트랜잭션도 DB도 없이 단위 테스트할 수 있다. 반면 엔티티는 설계상 가변이다. JPA 기본편에서 본 변경 감지(dirty checking)는 영속성 컨텍스트가 보관한 스냅샷과 엔티티의 현재 필드 값을 플러시 시점에 비교하는 방식이고, 엔티티의 필드가 바뀐다는 것을 전제로 한다. Jakarta Persistence 3.1 명세의 §2.1은 엔티티 클래스가 final이면 안 되고, 메서드나 영속 인스턴스 변수도 final이면 안 되며, 인자 없는 public 또는 protected 생성자가 있어야 한다고 정한다. 레코드는 암묵적으로 final이고 필드도 final이므로 엔티티가 될 수 없다. 그래서 자바 웹 애플리케이션에서 함수형 스타일은 엔티티 바깥, 즉 계산 로직과 DTO, 값 객체에 적용하는 것이 자연스럽다.

    자바와 함수형 프로그래밍 3: 불변 데이터 만들기

    순수 함수가 주고받는 값은 불변이어야 한다. 자바에서 불변 클래스를 만드는 전통적인 규칙은 이렇다. 모든 필드를 private final로 두고, 상태를 바꾸는 메서드를 두지 않으며, 하위 클래스가 가변 상태를 덧붙이지 못하게 클래스를 final로 만들고, 가변 객체를 받거나 내보낼 때는 복사한다. 레코드(자바 16, JEP 395)는 이 중 앞의 세 가지를 자동으로 해 준다. JEP 395에 따르면 레코드의 각 구성 요소(component)마다 private final 필드와 같은 이름의 public 접근자가 생기고, 레코드 클래스는 암묵적으로 final이며 인스턴스 필드를 따로 선언할 수 없다. JEP는 구성 요소에서 나온 필드가 final인 것을 "기본적으로 불변(immutable by default)"이라는 방침으로 설명한다. 뒤 절의 Num 레코드를 javap -p로 보면 public final class Num extends java.lang.Record와 private final int value;가 그대로 보인다.

    하지만 네 번째 규칙인 복사는 레코드가 해 주지 않는다. 그래서 레코드는 얕은 불변(shallowly immutable)이다. 확인해 보자.

    import java.util.*;
import java.util.stream.*;

public class Immut {
    record Team(String name, List members) {}
    record SafeTeam(String name, List members) {
        SafeTeam {
            members = List.copyOf(members);
        }
    }
    public static void main(String[] args) {
        List src = new ArrayList<>(List.of("kim", "lee"));
        Team t = new Team("A", src);
        SafeTeam s = new SafeTeam("A", src);
        src.add("park");
        System.out.println(t.members() + " " + s.members());
        try { s.members().add("choi"); } catch (UnsupportedOperationException e) { System.out.println("UOE copyOf"); }

        List view = Collections.unmodifiableList(src);
        src.add("choi");
        System.out.println(view);

        List a = Stream.of(1, 2).collect(Collectors.toList());
        List b = Stream.of(1, 2).toList();
        a.add(3);
        System.out.println(a.getClass().getName() + " " + a);
        try { b.add(3); } catch (UnsupportedOperationException e) { System.out.println("UOE toList " + b.getClass().getName()); }
        List c = List.copyOf(s.members());
        System.out.println(c == s.members());
    }
}

    첫 줄이 얕은 불변의 증거다. Team의 members 필드는 final이지만, 그 필드가 가리키는 것은 호출자가 넘긴 src와 같은 ArrayList 객체다. final은 필드에 다른 리스트를 대입하지 못하게 할 뿐이므로, 호출자가 src에 "park"를 넣자 t.members()에도 나타났다. SafeTeam은 간결한 정규 생성자(compact canonical constructor)에서 매개변수 members를 List.copyOf의 결과로 바꿔 놓는다. 간결한 생성자에서는 본문이 끝난 뒤 매개변수의 값이 필드에 대입되므로, 필드에는 복사본이 들어간다. 그래서 src가 바뀌어도 [kim, lee]이고, 복사본은 수정 불가능하므로 둘째 줄처럼 add는 UnsupportedOperationException을 던진다.

    셋째 줄은 "수정 불가능(unmodifiable)"과 "불변(immutable)"이 다르다는 것을 보여 준다. Collections.unmodifiableList는 원본을 감싼 읽기 전용 뷰다. 뷰를 통한 수정은 막지만 원본이 바뀌면 그 내용이 그대로 비친다. 뷰를 받은 쪽에서는 리스트가 자기도 모르게 바뀌는 셈이다. 넷째와 다섯째 줄은 스트림의 두 수집 방법이다. Collectors.toList()의 Javadoc은 반환 리스트의 타입, 가변성, 직렬화 가능성, 스레드 안전성을 보장하지 않는다고 밝힌다. OpenJDK 21에서는 ArrayList가 나와서 add가 되었지만 이것은 구현일 뿐이다. 자바 16의 Stream.toList()는 수정 불가능한 리스트를 돌려준다고 Javadoc이 보장하고, 실제로 add가 예외를 던졌다. 구현 클래스 이름(ImmutableCollections$ListN)은 OpenJDK 내부 구현이므로 기대면 안 된다.

    마지막 줄은 불변성이 주는 이득 하나를 보여 준다. 이미 수정 불가능한 리스트를 List.copyOf에 넘기면 Javadoc 설명대로 대개 복사하지 않고, 여기서는 같은 객체가 그대로 돌아왔다(true). 아무도 바꿀 수 없는 값은 복사할 이유가 없다. 가변 객체는 "누가 바꿀지 모르니 복사해 두는" 방어적 복사가 필요하지만, 불변 객체는 마음껏 공유할 수 있다. 다섯 가지 방법을 정리하면 다음과 같다.

    null 열은 직접 실행해 확인했다. Stream.of("a", null).toList()는 [a, null]을 돌려주고, 같은 스트림을 Collectors.toUnmodifiableList()로 모으거나 List.of("a", null)을 호출하면 NullPointerException이 난다. 두 "수정 불가능한 리스트" 방법이 null에서 다르게 동작하므로, 바꿔 쓸 때 주의해야 한다.

    깊은 불변성은 한 단계 더 나아간다. List.copyOf로 만든 리스트도 원소가 StringBuilder처럼 가변 객체라면 원소의 내용은 여전히 바뀐다. 값이 정말로 불변이려면 그 값에서 참조를 따라 닿을 수 있는 모든 객체가 불변이어야 한다. String, Integer, LocalDate, 그리고 불변 타입만 구성 요소로 갖는 레코드가 그런 재료다. 자바에는 이것을 컴파일러가 검사하는 장치가 없으므로, 불변 타입으로만 조립하는 것이 사람의 규율이다.

    불변 컬렉션의 안쪽: 믿을 수 있는 배열과 흔들리는 반복 순서

    앞 절의 실험에는 설명하지 않고 넘어간 결과가 둘 있다. List.copyOf가 어떤 때는 같은 객체를 그대로 돌려준다는 것, 그리고 둘 다 "수정 불가능한 리스트"인 List.of와 Stream.toList()가 null에서 다르게 동작한다는 것이다. 이 둘은 Javadoc의 계약이기도 하지만, 그 계약이 어떤 자료구조로 지켜지는지를 보면 불변성이 구현에 무엇을 허락하는지가 보인다. 이 절의 내용은 OpenJDK 21의 java.util.ImmutableCollections 소스 기준이고, 클래스 이름과 동작은 모두 구현 세부라서 코드가 기대어서는 안 된다.

    원소 수에 따라 다른 클래스

    List.of가 돌려주는 객체는 한 종류가 아니다. 원소가 한두 개면 List12, 그 밖에는 ListN이다. List12는 배열 없이 필드 두 개(e0, e1)에 원소를 직접 담는 클래스라서, 원소 두 개짜리 리스트를 만들 때 배열 객체 하나를 아낀다. 빈 리스트는 새로 만들지 않고 미리 만들어 둔 EMPTY_LIST 하나를 모두가 공유한다. 바뀔 수 없는 빈 리스트는 몇 개가 있든 구별할 이유가 없기 때문이다. 같은 소스에는 이 공유 상수들을 CDS(Class Data Sharing) 아카이브에서 읽어 오는 코드도 있다.

    import java.util.*;
import java.util.stream.*;

public class Coll {
    public static void main(String[] args) {

Stream.toList()는 null 원소를 허용해야 하는데 List12는 그럴 수 없는 구조다. 생성자가 두 원소 모두 Objects.requireNonNull로 검사하고, 원소가 하나일 때는 두 번째 칸에 null 대신 EMPTY라는 표지 객체(sentinel)를 넣어 크기를 구별한다. 소스 주석은 null을 표지로 쓰지 않아야 원소 하나짜리 리스트에서도 상수 폴딩 최적화가 가능하다고 이유를 밝힌다(아래 @Stable 이야기와 이어진다). toList()가 부르는 생성 메서드의 주석도 null을 담을 수 없기 때문에 List12를 만들지 않는다고 적어 둔다.

    믿을 수 있는 배열과 allowNulls 플래그

    불변 리스트를 만드는 핵심 질문은 "넘겨받은 배열을 내부 저장소로 그대로 써도 되는가"다. 호출자가 그 배열의 참조를 계속 쥐고 있다면, 호출자가 배열을 고치는 순간 "불변" 리스트의 내용이 바뀐다. 그래서 OpenJDK는 두 가지 생성 경로를 둔다. listFromArray는 믿을 수 없는 배열을 받아 새 배열로 복사하면서 원소마다 null을 검사하고, listFromTrustedArray는 "호출자가 참조를 남겨 두지 않은" 배열을 복사 없이 저장소로 쓴다. 소스 주석은 믿을 수 있는 배열(trusted array)을 호출자가 참조를 보유하지 않으므로 방어적 복사 없이 내부 저장소로 재사용할 수 있는 배열이라고 정의한다.

    어느 경로를 타는지는 호출 모양이 정한다. 인자 개수가 고정된 List.of(e1, e2, e3)는 listFromTrustedArray(e1, e2, e3)를 부르는데, 이 가변 인자 배열은 List.of 안에서 방금 만들어진 것이라 바깥 누구도 참조를 갖지 않는다. 반면 List.of(E... elements)는 String[] arr = ...; List.of(arr)처럼 호출자가 만든 배열이 그대로 들어올 수 있으므로 listFromArray로 복사한다. 복사 주석에는 "TOCTOU를 피하려고 복사하면서 직접 검사한다"는 말이 붙어 있다. 검사한 시점(time of check)과 쓰는 시점(time of use) 사이에 호출자가 배열에 null을 넣는 일을 막으려면 검사와 복사를 한 번에 해야 한다는 뜻이다. Stream.toList()는 ReferencePipeline에서 다음처럼 재정의되어 있다.

    public List toList() {
    return SharedSecrets.getJavaUtilCollectionAccess().listFromTrustedArrayNullsAllowed(this.toArray());
}

    toArray()가 방금 만든 배열은 파이프라인 밖의 누구도 갖고 있지 않으므로 복사 없이 그대로 ListN의 저장소가 되고, 이때 ListN에는 allowNulls = true가 기록된다. 참고로 Stream 인터페이스 자체의 디폴트 toList()는 Collections.unmodifiableList(new ArrayList<>(Arrays.asList(this.toArray())))로, 표준 파이프라인이 아닌 다른 Stream 구현을 위한 것이다. 이제 List.copyOf의 구현을 보면 실험의 셋째 줄이 설명된다.

    static  List listCopy(Collection coll) {
    if (coll instanceof List12 || (coll instanceof ListN c && !c.allowNulls)) {
        return (List)coll;
    } else if (coll.isEmpty()) { // implicit nullcheck of coll
        return List.of();
    } else {
        return (List)List.of(coll.toArray());
    }
}

    List.copyOf의 계약은 "null 없는 수정 불가능한 리스트"다. List.of(1, 2, 3)의 결과는 이미 그 조건을 만족하는 ListN(allowNulls = false)이므로 복사할 이유가 없어 그대로 돌아온다(true). 반면 toList()의 결과는 같은 ListN 클래스이지만 null이 들어 있을 수 있다는 표시가 붙어 있으므로, copyOf는 그것을 믿지 못하고 List.of(coll.toArray())로 새로 만든다(false). 이 경로가 원소마다 null을 검사하므로, 앞 절의 표에서 List.copyOf가 null에 NullPointerException을 던지던 동작도 여기서 나온다. "수정할 수 없다"는 같은 성질이라도 "null이 없다"는 추가 불변식까지 함께 증명된 값만 공유할 수 있다는 것, 이것이 이 플래그가 하는 일이다.

    @Stable: 불변이라는 사실을 JIT에 알리기

    ListN의 필드는 @Stable private final E[] elements;로 선언되어 있다. jdk.internal.vm.annotation.Stable은 JDK 내부 애너테이션이고, 그 Javadoc은 이 표시가 붙은 필드는 null이 아닌 값이 한 번 들어가면 다시 바뀌지 않으며, 필드가 배열 타입이면 배열의 원소까지 그렇게 취급된다고 정의한다. 같은 문서는 HotSpot이 이 표시를 근거로 null이 아닌 값을 상수로 승격해 상수 폴딩(constant folding) 같은 최적화를 할 수 있다고 밝히고, 이 효과는 부트 클래스 로더가 읽은 클래스에만 적용된다고 적는다. 보통의 final 배열 필드는 배열 참조만 고정할 뿐 원소는 바뀔 수 있으므로 JIT가 원소를 상수로 볼 수 없다. 불변 컬렉션은 "원소까지 바뀌지 않는다"는 사실을 이 애너테이션으로 JIT에게 전달하는 것이다. 불변성은 사람에게만 주는 약속이 아니라, 지켜진다는 것을 보장할 수 있을 때 실행 엔진이 이용하는 정보이기도 하다. 뒤의 "final은 정말 바뀌지 않는가" 절에서 이 생각을 일반 final 필드로 넓혀 본다.

    Set.of의 반복 순서는 왜 실행마다 다른가

    실험 결과의 넷째 줄은 실행할 때마다 달라진다. 같은 프로그램을 여덟 번 실행해 Set.of("a", "b", "c", "d", "e")와 Map.of(...)의 출력, 그리고 비교를 위해 HashSet의 출력을 모아 보면 다음과 같다.

    [e, d, c, b, a] {3=z, 2=y, 1=x} [a, b, c, d, e]
[a, b, c, d, e] {2=y, 3=z, 1=x} [a, b, c, d, e]
[b, a, e, d, c] {3=z, 2=y, 1=x} [a, b, c, d, e]
[d, e, a, b, c] {1=x, 2=y, 3=z} [a, b, c, d, e]
[b, c, d, e, a] {1=x, 2=y, 3=z} [a, b, c, d, e]
[c, d, e, a, b] {1=x, 2=y, 3=z} [a, b, c, d, e]
[e, a, b, c, d] {1=x, 2=y, 3=z} [a, b, c, d, e]
[a, b, c, d, e] {3=z, 1=x, 2=y} [a, b, c, d, e]

    이 무작위성은 의도된 것이다. SetN은 원소 수의 두 배(EXPAND_FACTOR = 2) 길이의 배열에 원소를 선형 탐사(linear probing)로 넣는다. 첫 위치는 Math.floorMod(hashCode, 배열 길이)다. 원소가 다섯 개면 배열 길이는 10이고, "a"부터 "e"의 해시 코드는 97부터 101이므로 각각 7, 8, 9, 0, 1번 칸에 들어간다. 여기까지는 실행마다 같다. 달라지는 것은 반복자다. 반복자는 클래스 초기화 때 한 번 정해지는 값 SALT32L로 시작 칸을 고르고, 그 값의 최하위 비트로 정한 REVERSE에 따라 배열을 앞으로 또는 뒤로 돈다. SALT32L은 원주율의 일부를 잘라 만든 상수에 System.nanoTime()을 곱해 얻는다(CDS 아카이브를 만드는 -Xshare:dump 중에는 빌드마다 고정된 씨앗을 쓴다). 그래서 출력은 언제나 칸 순서 a, b, c, d, e를 어디서부터 어느 방향으로 읽느냐의 차이일 뿐이다. 셋째 줄의 [b, a, e, d, c]는 8번 칸(b)에서 시작해 뒤로 돌며 빈칸을 건너뛴 결과다. Map.of가 돌려주는 MapN의 반복자도 같은 SALT32L로 시작 위치를 고른다.

    소스 주석은 이 값이 진짜 난수일 필요는 없지만 반복 순서가 JVM 실행마다 달라질 만큼은 달라야 한다고 적고, Set의 Javadoc은 수정 불가능한 집합의 반복 순서가 정해져 있지 않으며 바뀔 수 있다고 명시한다. 같은 실험의 HashSet은 여덟 번 모두 같은 순서였지만, 이것도 명세가 약속한 순서가 아니라 해시 테이블 구현에서 나온 결과일 뿐이다. 반복 순서를 일부러 흔들어 두면, 우연히 맞아떨어진 순서에 기대는 코드가 개발 중에 드러난다.

    이 동작을 이 회차의 언어로 다시 읽어 보자. 마지막 줄처럼 원소를 다른 순서로 넣은 두 Set.of는 equals로 같은 값이다. 집합이라는 값에는 순서가 들어 있지 않다. 그런데 s.iterator().next()나 s.toString()처럼 반복 순서를 드러내는 연산은 같은 값에 대해 JVM 실행마다 다른 결과를 낸다(한 JVM 안에서는 SALT32L이 고정되어 있어 같다). 앞에서 자바의 참조 투명성에는 "equals 기준으로 같은 값"이라는 단서가 붙는다고 했다. 그 단서를 지키려면, 값을 받는 함수는 그 값의 equals가 구별하는 성질에만 의존해야 한다. 집합에서 "첫 원소"를 꺼내 쓰는 함수는 그 규칙을 어기고, 이 구현은 그런 코드를 일부러 흔들어서 드러낸다.

    한 층 아래 1: final 필드와 자바 메모리 모델

    "불변 객체는 스레드 안전하다"는 말은 흔하다. 바뀌지 않으니 경쟁할 것이 없다는 설명이다. 그런데 이 설명에는 구멍이 하나 있다. 불변 객체도 만들어지는 순간에는 필드에 값이 쓰인다. 한 스레드가 생성자에서 필드를 쓰고 그 객체의 참조를 공유 변수에 넣었을 때, 다른 스레드가 그 참조를 읽어 필드를 보면 생성자가 쓴 값이 보인다는 보장이 있는가. 자바 고급 1편에서 본 것처럼 락이나 volatile 없이 공유 변수로 값을 넘기는 것은 데이터 경합(data race)이고, 일반 필드라면 그런 보장이 없다. 컴파일러와 CPU는 생성자 안의 필드 쓰기와 참조를 공유 변수에 쓰는 일의 순서를 다른 스레드가 보기에 바꿔 놓을 수 있다.

    이 구멍을 메우는 것이 JLS §17.5의 final 필드 의미론이다. 명세는 생성자가 끝났을 때 객체가 "완전히 초기화되었다"고 하고, 완전히 초기화된 뒤에야 그 객체의 참조를 볼 수 있었던 스레드는 그 객체의 final 필드에 대해 올바르게 초기화된 값을 보장받는다고 정한다. 또 final 필드가 참조하는 객체나 배열도 적어도 그 final 필드만큼 최신인 상태로 보인다고 덧붙인다. 명세의 예제와 같은 구조를 직접 써 보면 다음과 같다.

    class Point {
    final int x;
    int y;
    static Point shared;              // volatile도 아니고 락도 없다

    Point() { x = 3; y = 4; }

    static void writer() {            // 스레드 A
        shared = new Point();
    }
    static void reader() {            // 스레드 B
        Point p = shared;
        if (p != null) {
            int i = p.x;              // 3이 보장된다
            int j = p.y;              // 0이 보일 수도 있다
        }
    }
}

    스레드 B가 shared에서 null이 아닌 참조를 읽었다면, final인 x는 반드시 3으로 보인다. final이 아닌 y에는 그런 보장이 없어서 기본값 0이 보일 수 있다. 데이터 경합이 있는데도 final 필드만은 안전하다는 것, 이것이 명세가 말하는 "동기화 없이 스레드 안전한 불변 객체"의 근거다. JLS는 이어지는 예제에서 String을 든다. String의 필드가 final이 아니라면 다른 스레드가 문자열을 잠깐 다른 내용으로 볼 수 있고, 자바의 여러 보안 기능이 문자열이 모든 스레드에 불변으로 보인다는 가정에 기대고 있으므로 이는 보안 문제가 된다. JDK 21의 String 소스에서 문자 데이터를 담는 필드는 private final byte[] value;다.

    이 보장에는 조건이 있다. 명세는 사용 모델로 "final 필드는 생성자에서 설정하고, 생성 중인 객체의 참조를 생성자가 끝나기 전에 다른 스레드가 볼 수 있는 곳에 쓰지 말라"고 정한다. 생성자 안에서 this를 리스너로 등록하거나, this를 넘겨 스레드를 시작하거나, this를 정적 필드에 넣으면 다른 스레드가 완전히 초기화되기 전의 객체를 볼 수 있고, 그 순간 final 필드의 보장도 사라진다. 이것을 생성 중 this 탈출(this escape)이라고 부른다.

    HotSpot은 이 보장을 어떻게 지킬까. OpenJDK 21의 C2 컴파일러 소스 parse1.cpp를 보면, 컴파일하는 메서드가 생성자이고 그 안에서 final 필드를 썼으면(wrote_final()) 생성자의 정상 종료 지점에 릴리스 메모리 장벽(MemBarRelease)을 넣는다. 장벽 앞의 쓰기(필드 초기화)가 장벽 뒤의 쓰기(참조를 공유 변수에 넣기)보다 늦게 보이지 않게 하는 장치다. 같은 곳의 주석은 생성자가 정상적으로 반환된 뒤에 처음 공개된 경우가 아니면 보장이 없다는 것(this 탈출)과, 예외로 끝난 생성자는 정상적으로 공개될 수 없으므로 장벽이 필요 없다는 것을 밝힌다. 이 장벽이 실제 기계어로 어떻게 바뀌는지는 CPU 아키텍처의 메모리 모델에 따라 다르다.

    레코드의 필드는 모두 final이므로 이 보장을 그대로 받는다. SafeTeam처럼 생성자에서 만든 복사본을 final 필드에 넣었다면, 복사본의 내용도 "적어도 final 필드만큼 최신"인 상태로 다른 스레드에 보인다. 반대로 Team처럼 바깥의 가변 리스트를 그대로 붙잡은 레코드는, 생성 뒤에 일어나는 src.add에 대해서는 아무 보장도 받지 못한다. 그 변경은 레코드와 무관한 일반 객체의 변경이고, 다른 스레드가 그것을 언제 보는지는 다시 데이터 경합의 영역이다. 방어적 복사는 캡슐화만이 아니라 메모리 가시성의 문제이기도 하다.

    스레드 A가 생성자에서 x(final)와 y를 쓰고 참조를 공유 변수에 넣을 때, 생성자 끝의 릴리스 장벽 덕분에 스레드 B는 x=3을 반드시 보지만 y는 0을 볼 수도 있음을 보여 준다.     final은 정말 바뀌지 않는가: 리플렉션, §17.5.3, 그리고 JIT가 믿는 final

    지금까지 final 필드를 "생성자에서 한 번 쓰이고 다시는 바뀌지 않는 칸"으로 다뤘다. 언어 수준에서는 맞다. 생성자 밖에서 final 필드에 대입하는 코드는 컴파일되지 않는다. 그런데 JLS에는 §17.5.3 "final 필드의 이후 변경(Subsequent Modification of final Fields)"이라는 절이 따로 있다. 역직렬화처럼 시스템이 생성 뒤에 final 필드를 바꿔야 하는 경우가 있고, final 필드는 리플렉션과 그 밖의 구현 의존적 수단으로 바뀔 수 있다고 명세 스스로 밝힌다. 불변 값을 설계의 바닥으로 삼으려면 이 예외가 어디까지 열려 있고, JVM이 그 예외를 어떻게 다루는지 알아야 한다.

    import java.lang.reflect.Field;

public class Fin {
    static final class Money { final long amount; Money(long a) { amount = a; } }
    record Point(int x, int y) {}

    public static void main(String[] args) throws Exception {
        Money m = new Money(100);
        Field fa = Money.class.getDeclaredField("amount");
        fa.setAccessible(true);
        fa.setLong(m, 999);
        System.out.println("Money.amount = " + m.amount);

        Point p = new Point(1, 2);
        Field fx = Point.class.getDeclaredField("x");
        fx.setAccessible(true);
        System.out.println("get x = " + fx.getInt(p));
        try {
            fx.setInt(p, 9);
        } catch (IllegalAccessException e) {
            System.out.println(e);
        }
    }
}

    일반 클래스의 final 필드는 setAccessible(true)를 거치면 리플렉션으로 바뀐다. 같은 일을 레코드에 하면 읽기는 되지만 쓰기는 IllegalAccessException으로 거부된다. 이 차이는 Field.set의 Javadoc에 정해져 있다. final 필드에 쓰기 권한이 생기려면 setAccessible(true)가 성공했고, 필드가 정적이 아니며, 필드를 선언한 클래스가 숨은 클래스(hidden class)도 레코드 클래스도 아니어야 한다. 정적 final 필드, 숨은 클래스의 필드, 레코드의 필드는 리플렉션으로도 바꿀 수 없다. 레코드의 "기본적으로 불변"은 final 키워드만이 아니라 이 규칙으로도 지켜지는 것이다.

    바꿀 수 있다고 해서 바뀐 값이 보이는 것은 아니다

    §17.5.3은 리플렉션 변경을 허용하면서도 그 의미를 좁게 묶는다. 합리적인 의미를 갖는 유일한 패턴은 "객체를 만들고, final 필드를 고치고, 그다음에 공개하는 것"이며, 고치는 작업이 끝나기 전에는 객체를 다른 스레드에 보이거나 그 final 필드를 읽어서는 안 된다고 정한다. 동결(freeze)은 생성자 끝에서 한 번, 그리고 리플렉션 등으로 final 필드를 고칠 때마다 그 직후에 일어난다. 그리고 명세는 두 가지 함정을 덧붙인다.

    첫째, 필드 선언에서 상수식(constant expression)으로 초기화한 final 필드는 바꿔도 그 변경이 보이지 않을 수 있다. 그 필드를 쓰는 곳이 컴파일할 때 상수 값으로 바뀌기 때문이다. 직접 확인해 보자.

    import java.lang.reflect.Field;

public class Konst {
    static class K { final int k = 5; final int m; K() { m = 5; } }

    public static void main(String[] args) throws Exception {
        K o = new K();
        for (String name : new String[]{"k", "m"}) {
            Field f = K.class.getDeclaredField(name);
            f.setAccessible(true);
            f.setInt(o, 7);
        }
        System.out.println(o.k + " " + o.m);
    }
}

    HotSpot은 어떤 final을 믿는가

    "공격적인 최적화"가 실제로 무엇인지는 HotSpot의 JIT 컴파일러 인터페이스 코드 ciField.cpp에서 볼 수 있다(OpenJDK 21 기준). 컴파일러는 필드마다 그 값을 컴파일 시점의 상수로 취급해도 되는지(_is_constant)를 정한다. 정적 final 필드는 System.in, System.out, System.err 세 개를 빼면 상수 후보다. 인스턴스 final 필드는 그렇지 않다. @Stable이 붙었거나 다음 함수가 참을 돌려줄 때만 상수로 취급한다.

    static bool trust_final_non_static_fields(ciInstanceKlass* holder) {
  ...
  // Even if general trusting is disabled, trust system-built closures in these packages.
  if (holder->is_in_package("java/lang/invoke") || ... || holder->is_in_package("java/lang"))
    return true;
  // Trust hidden classes. They are created via Lookup.defineHiddenClass and
  // can't be serialized, so there is no hacking of finals going on with them.
  if (holder->is_hidden())
    return true;
  // Trust final fields in all boxed classes
  if (holder->is_box_klass())
    return true;
  // Trust final fields in records
  if (holder->is_record())
    return true;
  // Trust final fields in String
  if (holder->name() == ciSymbols::java_lang_String())
    return true;
  ...
  return TrustFinalNonStaticFields;
}

    목록을 보면 기준이 분명하다. 레코드와 숨은 클래스는 앞의 Javadoc 규칙 때문에 리플렉션으로 final 필드를 바꿀 수 없고, 숨은 클래스는 주석이 말하듯 직렬화도 되지 않는다. java.lang 패키지의 클래스(박싱 클래스와 String 포함, 단 생략한 첫 줄들이 System은 믿지 않는다고 따로 막는다)와 java.lang.invoke, jdk.internal.reflect 같은 JDK 패키지도 믿는다. 람다 객체의 클래스는 LambdaMetafactory가 만드는 숨은 클래스이므로, 람다가 캡처한 값을 담은 final 필드도 이 목록에 들어간다. int n = 5; IntSupplier s = () -> n;에서 s.getClass().isHidden()은 true이고, 리플렉션으로 본 그 클래스의 필드는 private final int arg$1 하나였다. 나머지 일반 클래스의 final 인스턴스 필드는 실험용 플래그 TrustFinalNonStaticFields를 따르는데, 실험용 플래그는 -XX:+PrintFlagsFinal만으로는 목록에 나오지 않으므로 -XX:+UnlockExperimentalVMOptions를 함께 주어 보면 이 플래그의 기본값은 false다. 일반 클래스의 final은 리플렉션이나 역직렬화로 바뀔 수 있으므로, HotSpot은 기본적으로 그 값을 상수로 굳히지 않는다.

    이 선택이 왜 필요한지는 일부러 반대로 설정해 보면 드러난다. 정적 final 필드가 가리키는 일반 클래스 객체의 final 필드를 읽는 메서드를 충분히 호출해 JIT 컴파일되게 한 뒤, 리플렉션으로 필드를 바꾸고 다시 호출한다.

    import java.lang.reflect.Field;

public class Fold {
    static final class Box { final int v; Box(int v) { this.v = v; } }
    static final Box BOX = new Box(1);

    static int read() { return BOX.v; }

    public static void main(String[] args) throws Exception {
        long sum = 0;
        for (int i = 0; i < 2_000_000; i++) sum += read();   // read()가 JIT 컴파일되게 데운다
        Thread.sleep(500);
        Field f = Box.class.getDeclaredField("v");
        f.setAccessible(true);
        f.setInt(BOX, 2);
        System.out.println("field=" + f.getInt(BOX) + " read()=" + read() + " sum=" + sum);
    }
}

$ java -XX:+UnlockExperimentalVMOptions -XX:+TrustFinalNonStaticFields Fold

$ java -Xint -XX:+UnlockExperimentalVMOptions -XX:+TrustFinalNonStaticFields Fold

    기본 설정에서는 바뀐 값 2가 보인다. TrustFinalNonStaticFields를 켜면, 필드에는 분명히 2가 들어 있는데(f.getInt) read()는 1을 돌려준다. -XX:+PrintCompilation을 함께 주면 Fold::read가 4단계(C2)로 컴파일된 것이 보인다. C2는 BOX가 정적 final이라 상수이고 v도 믿을 수 있는 final이라고 보아, read()의 본문을 상수 1을 돌려주는 코드로 접어 버렸다. 그 뒤의 리플렉션 변경은 컴파일된 코드에 닿지 않는다. 인터프리터만 쓰는 -Xint에서는 매번 필드를 읽으므로 2가 보인다. 이 실험은 JIT 컴파일 시점에 따라 달라질 수 있는 구현 동작이며, 실험용 플래그는 운영에 쓰는 설정이 아니다.

    이 실험은 불변성의 의미를 한 번 더 정리해 준다. 레코드의 필드는 언어가 재대입을 막고(final), 리플렉션이 쓰기를 거부하고(Field.set의 규칙), 그래서 JIT가 그 값을 상수로 믿을 수 있다(trust_final_non_static_fields). 일반 클래스의 final은 첫 번째 단계까지만 보장되므로 JIT는 믿지 않는다. 값 객체를 레코드로 만들면 앞 절의 §17.5 가시성 보장에 더해, 실행 엔진까지 그 불변성을 전제로 동작하는 값이 된다. 반대로 리플렉션으로 final을 바꾸는 코드는 §17.5.3이 말하는 좁은 패턴(만들고, 고치고, 그다음에 공개) 밖에서는 결과를 보장받지 못한다.

    데이터와 함수의 분리: 봉인 인터페이스, 레코드, 패턴 매칭

    객체지향은 데이터와 그 데이터를 다루는 행동을 한 클래스에 묶는다. 함수형 스타일은 반대로 데이터를 단순한 불변 값으로 두고, 그 값을 받아 결과를 돌려주는 함수를 따로 둔다. 자바 21에는 이 방식을 위한 세 가지 도구가 모두 들어와 있다. 값을 표현하는 레코드, 가능한 종류의 목록을 닫는 봉인 인터페이스(자바 17, JEP 409), 그리고 종류에 따라 나누면서 값을 분해하는 switch 패턴 매칭과 레코드 패턴(자바 21, JEP 441과 JEP 440)이다. JEP 395는 레코드와 봉인 클래스의 조합을 대수적 데이터 타입(algebraic data type)이라고 부르며, 레코드는 곱(product)을, 봉인 클래스는 합(sum)을 표현한다고 설명한다. 곱은 "이것과 저것을 모두 가진 값"이고, 합은 "이것 아니면 저것인 값"이다.

    정수와 덧셈, 곱셈으로 이루어진 식을 표현하고 계산하는 예를 보자. 파일 다섯 개다.

    // Expr.java
public sealed interface Expr permits Num, Add, Mul {}
// Num.java
public record Num(int value) implements Expr {}
// Add.java
public record Add(Expr left, Expr right) implements Expr {}
// Mul.java
public record Mul(Expr left, Expr right) implements Expr {}
// Main2.java
public class Main2 { static Expr make() { return new Num(7); } }
    public class Eval {
    static int eval(Expr e) {
        return switch (e) {
            case Num n -> n.value();
            case Add(Expr l, Expr r) -> eval(l) + eval(r);
            case Mul(Expr l, Expr r) -> eval(l) * eval(r);
        };
    }
    static String show(Expr e) {
        return switch (e) {
            case Num n -> String.valueOf(n.value());
            case Add(var l, var r) -> "(" + show(l) + " + " + show(r) + ")";
            case Mul(var l, var r) -> show(l) + " * " + show(r);
        };
    }
    public static void main(String[] args) {
        Expr e = new Mul(new Add(new Num(1), new Num(2)), new Num(4));
        System.out.println(show(e) + " = " + eval(e));
        System.out.println(e);
        System.out.println(e.equals(new Mul(new Add(new Num(1), new Num(2)), new Num(4))));
        Expr neg = Main2.make();
        System.out.println(eval(neg));
    }
}

    Expr는 Num, Add, Mul 셋 중 하나이고(합), Add는 왼쪽 식과 오른쪽 식을 모두 가진다(곱). eval과 show는 이 데이터를 받아 값을 돌려주는 순수한 재귀 함수다. case Add(Expr l, Expr r)는 레코드 패턴으로, 값이 Add인지 검사하는 동시에 구성 요소를 꺼내 l과 r에 묶는다. 계산은 바깥 Mul에서 시작해 eval(Add(1, 2)) * eval(Num(4)), 즉 3 × 4 = 12다. 레코드가 자동으로 만든 toString은 구조를 그대로 보여 주고, 자동으로 만든 equals는 구성 요소를 재귀적으로 비교하므로 따로 만든 같은 구조의 식과 true가 된다. 정체성이 아니라 구조로 같음을 판단하는 값이다.

    한 층 아래 2: 합성, 재귀, 메모이제이션이 스택과 힙에서 하는 일

    함수형 스타일의 세 가지 단골 기법인 함수 합성, 재귀, 메모이제이션을 자바에서 쓰면 각각 JVM의 어떤 자원을 소비하는지 확인해 보자. JVMS §2.6은 메서드가 호출될 때마다 새 프레임이 만들어지고 호출이 끝나면(정상 종료든 예외든) 프레임이 사라진다고 정하고, §2.5.2는 스레드의 계산에 허용된 것보다 큰 JVM 스택이 필요하면 StackOverflowError를 던진다고 정한다. 이 두 규칙이 이 절의 실험을 설명한다.

    결과는 1000000이 아니라 StackOverflowError다. 원인은 andThen의 구현 (T t) -> after.apply(apply(t))에 있다. 반복문은 힙에 람다 객체 백만 개를 만들고, 각 객체는 직전의 chain(this)과 plus1(after)을 캡처한다. 가장 바깥 객체의 apply(0)은 after를 적용하기 전에 this.apply(0)을 먼저 계산해야 하고, 그 호출은 다시 자기 this.apply(0)을 먼저 부른다. 덧셈은 하나도 일어나지 않은 채 호출이 사슬의 맨 안쪽 identity까지 백만 단계 내려간다. 그동안 단계마다 프레임이 쌓인다.

    재귀와 꼬리 호출

    함수형 언어는 반복문 대신 재귀를 즐겨 쓴다. 반복문은 변수에 다시 대입하며 도는 구조이고, 재귀는 새 인자로 자기 자신을 호출하는 구조라서 대입이 필요 없기 때문이다. 1부터 n까지의 합을 누적 인자를 넘기는 재귀로 써 보자.

    메모이제이션과 computeIfAbsent의 함정

    순수 함수의 결과는 인자에만 의존하므로, 한 번 계산한 결과를 저장해 두고 같은 인자가 다시 오면 저장한 값을 돌려줘도 된다. 이것이 메모이제이션(memoization)이다. 참조 투명성의 관점에서 보면 "호출을 그 결과값으로 바꿔 넣는" 치환을 실행 중에 하는 것이고, 그래서 순수 함수에만 쓸 수 있다. 결과가 외부 상태에 의존하는 함수를 메모이제이션하면 낡은 결과를 돌려주게 된다. 재귀적으로 정의된 피보나치 수에 적용해 보자.

    import java.util.*;

public class Memo {
    static final Map cache = new HashMap<>();
    static long fib(int n) {
        if (n < 2) return n;
        return cache.computeIfAbsent(n, k -> fib(k - 1) + fib(k - 2));
    }
    static final Map cache2 = new HashMap<>();
    static long fib2(int n) {
        if (n < 2) return n;
        Long hit = cache2.get(n);
        if (hit != null) return hit;
        long r = fib2(n - 1) + fib2(n - 2);
        cache2.put(n, r);
        return r;
    }
    public static void main(String[] args) {
        System.out.println(fib2(90));
        try {
            System.out.println(fib(90));
        } catch (ConcurrentModificationException e) {
            System.out.println(e);
        }
    }
}

V v = mappingFunction.apply(key);
if (mc != modCount) { throw new ConcurrentModificationException(); }

    이 메서드는 키가 들어갈 버킷의 위치와 기존 노드를 먼저 찾아 둔 다음 매핑 함수를 호출하고, 함수가 돌아오면 찾아 둔 정보로 새 노드를 넣는다. 그런데 우리의 매핑 함수는 안에서 fib(k - 1)을 부르고, 그 호출이 다시 computeIfAbsent로 같은 맵에 값을 넣는다. 맵의 구조가 바뀌면(특히 테이블이 커지면) 바깥 호출이 찾아 둔 버킷 정보는 낡은 것이 된다. 그래서 구현은 함수 호출 전후의 수정 횟수(modCount)를 비교해 달라졌으면 예외를 던진다. 실제 흐름은 computeIfAbsent(90)에서 89, 88로 내려가다가, 가장 안쪽의 computeIfAbsent(2)가 처음으로 값을 넣고 돌아오면, 그 바깥의 computeIfAbsent(3)이 자기 매핑 함수가 끝난 뒤 수정 횟수가 달라진 것을 발견해 예외를 던지는 것이다. Map.computeIfAbsent의 Javadoc은 매핑 함수가 계산 중에 이 맵을 수정해서는 안 된다고 적고, HashMap의 Javadoc은 그런 수정을 감지하면 최선을 다해(best-effort) 이 예외를 던진다고 적는다.

    ConcurrentHashMap으로 바꿔도 해결되지 않는다. 같은 재귀를 ConcurrentHashMap으로 실행하자 이번 실행에서는 IllegalStateException: Recursive update가 났다. 이 문구는 ConcurrentHashMap 소스에 들어 있는 검사에서 나온다. 재귀하는 함수의 메모이제이션은 fib2처럼 조회와 저장을 분리하거나, 작은 값부터 차례로 채우는 반복문으로 바꾸는 것이 안전하다. 재귀하지 않는 순수 함수라면 다음처럼 캐시를 품은 클로저로 감쌀 수 있다.

    static  Function memoize(Function fn) {
    Map cache = new ConcurrentHashMap<>();
    return t -> cache.computeIfAbsent(t, fn);
}

Function slow = memoize(x -> { System.out.println("compute " + x); return x * x; });
System.out.println(slow.apply(4) + " " + slow.apply(4));

16 16

    두 번 호출했지만 계산은 한 번만 일어났다. 이 함수는 안에 가변 캐시를 품고 있지만, 감싼 fn이 순수하다면 바깥에서 관찰되는 동작은 원래 함수와 같다. 앞에서 본 "새어 나가지 않는 지역 상태는 순수성을 해치지 않는다"는 원리가 객체 수준으로 확장된 모습이다. 대신 캐시는 계속 커지므로, 인자의 종류가 끝없이 늘어나는 곳에서는 크기 제한이나 만료 정책이 있는 캐시가 필요하다.

    한 층 아래 3: StackOverflowError는 어떻게 만들어지는가

    앞 절에서 깊은 재귀와 긴 합성 사슬은 StackOverflowError로 끝났고, 우리는 그 오류를 catch로 잡은 뒤 프로그램을 계속 실행했다. JVMS §2.5.2는 "허용된 것보다 큰 스택이 필요하면 이 오류를 던진다"고만 정한다. 그런데 HotSpot이 메서드를 호출할 때마다 "남은 스택이 충분한가"를 비교한다면 모든 호출이 느려질 것이다. 실제로는 운영체제의 메모리 보호와 시그널을 이용한다. 이 절은 OpenJDK 21 HotSpot의 소스와, 이 실험 환경(macOS, Apple Silicon arm64, Temurin 21.0.13)에서 본 값을 기준으로 한다.

    main 스레드의 스택은 누가 만드는가

    main 메서드는 운영체제가 프로세스를 시작할 때 만든 첫 스레드에서 실행되지 않는다. java 런처의 java.c에 있는 ContinueInNewThread는 JVM을 만들고 main을 부를 스레드를 새로 만든다. 스택 크기는 -Xss로 준 값이고, 지정하지 않았으면 JVM에 기본값을 물어 쓴다. macOS용 런처 java_md_macosx.m의 CallJavaMainInNewThread는 이 값을 pthread_attr_setstacksize로 지정해 pthread_create를 호출하는데, 그 바로 앞에 pthread_attr_setguardsize(&attr, 0)을 부르고 "자바 스레드에는 pthread 가드 페이지를 두지 않는다"는 주석을 단다. 스택 끝의 보호는 운영체제의 스레드 라이브러리가 아니라 JVM이 직접 하겠다는 뜻이다. 이 Mac에서 기본 스택 크기와 보호 영역 관련 플래그를 보면 다음과 같다.

    intx StackRedPages        = 1      {pd product} {default}
intx StackReservedPages   = 1      {pd product} {default}
intx StackShadowPages     = 20     {pd product} {default}
intx StackYellowPages     = 2      {pd product} {default}
intx ThreadStackSize      = 2048   {pd product} {default}

    {pd product}는 플랫폼마다 기본값이 다른 플래그라는 표시다. ThreadStackSize는 킬로바이트 단위이므로 이 환경에서 자바 스레드의 기본 스택은 2MB다.

    스택 끝의 세 구역: 빨강, 노랑, 예약

    HotSpot은 스레드 스택의 끝(스택은 높은 주소에서 낮은 주소로 자라므로, 가장 낮은 주소 쪽)에 가드 영역(guard zone)을 둔다. stackOverflow.hpp의 주석이 그린 구조를 옮기면 다음과 같다.

    (낮은 주소)
 ┌──────────────────┐ ← stack_end()
 │  빨강 구역        │  닿으면 복구 불가: VM이 오류 보고를 남기고 종료
 ├──────────────────┤
 │  노랑 구역        │  닿으면 StackOverflowError를 만들어 던진다
 ├──────────────────┤
 │  예약 구역        │  @ReservedStackAccess 메서드가 있으면 잠시 열어 준다
 ├──────────────────┤ ← 여기까지가 메모리 보호(PROT_NONE)된 가드 영역
 │  섀도 영역 크기    │  현재 SP에서 이만큼 앞을 미리 "두드려" 본다
 │        ...        │
 │  프레임 n         │  ← 현재 SP 부근

 │  프레임 0         │

(높은 주소)

    각 구역의 크기는 StackRedPages, StackYellowPages, StackReservedPages 플래그로 정해진다. stackOverflow.cpp의 initialize_stack_zone_sizes는 이 값들이 4KB 단위라고 밝히고, 실제 크기를 운영체제의 페이지 크기에 맞춰 올림한다. 이 Mac의 페이지 크기는 16KB(pagesize 명령의 출력 16384)이므로 빨강 1 × 4KB, 노랑 2 × 4KB, 예약 1 × 4KB가 각각 16KB로 올라가 가드 영역은 모두 48KB가 된다. BSD 계열용 os_bsd.cpp의 os::guard_memory는 mprotect(..., PROT_NONE)을 호출하므로, 이 구역에 읽거나 쓰는 순간 하드웨어가 예외를 일으키고 운영체제가 시그널을 보낸다. 스레드 로그로 실제 위치를 확인해 보자.

    [info ][os,thread] Thread attached (tid: 5635, pthread id: 6139441152, stack: 0x000000016df07000 - 0x000000016dd04000 (2060K) ).
[debug][os,thread] Thread 5635 stack guard pages activated: 0x000000016dd04000-0x000000016dd10000.

    보호된 범위는 스택의 낮은 쪽 끝 0x16dd04000에서 시작하고, 길이는 0x16dd10000 - 0x16dd04000 = 0xC000, 곧 48KB다. 계산과 정확히 맞는다(로그의 스택 크기 2060K가 2048K와 조금 다른 이유는 이 회차에서 확인하지 않았다).

    스택을 미리 두드리고, 시그널로 오류를 만든다

    가드 영역을 쳐 두고 누군가 닿기를 기다리기만 하면, 트랩은 스택을 쓰는 아무 지점에서나 날 수 있다. stackOverflow.hpp의 주석은 실행 중인 자바 코드에서 난 뜻밖의 트랩도 처리하기 어렵지만, VM 코드나 네이티브 코드에서 난 트랩을 제대로 처리하는 것은 거의 불가능하다고 적는다. 그래서 HotSpot은 스택 두드리기(stack banging)를 쓴다. 메서드에 들어갈 때 현재 스택 포인터(SP)에서 섀도 영역(shadow zone) 크기만큼 앞쪽 주소를 미리 건드려 보는 것이다. 이 Mac에서 섀도 영역은 StackShadowPages 20 × 4KB = 80KB다. 주석에 따르면 이렇게 하면 네이티브·VM 코드가 이 여유 안에서는 따로 검사하지 않고 실행될 수 있고, 오버플로가 일어나더라도 런타임이 아는 코드 지점(메서드 입구)에서 트랩이 난다. 매번 페이지마다 두드리는 비용을 줄이기 위해, 컴파일러가 프레임 크기를 정확히 알 때 두드리기를 생략하거나(PhaseOutput::need_stack_bang) 이미 두드려 본 깊이(growth watermark)보다 위에 있으면 건너뛰는 최적화도 주석에 정리되어 있다.

    두드린 주소가 가드 영역이면 SIGSEGV나 SIGBUS가 난다. macOS arm64에서는 os_bsd_aarch64.cpp의 시그널 처리기가 두 시그널 모두를 받아 os_posix.cpp의 os::Posix::handle_stack_overflow를 부른다. 이 함수는 시그널이 난 주소가 어느 구역인지 본다.

    • 예약 구역: 호출 스택에 @ReservedStackAccess가 붙은 메서드가 있으면 예약 구역의 보호를 잠시 풀어 그 메서드가 끝까지 실행되게 한다. 없으면 노랑 구역과 같이 처리한다.
    • 노랑 구역: 노랑·예약 구역의 보호를 잠시 풀고(disable_stack_yellow_reserved_zone), 스레드가 자바 코드를 실행하던 중이었으면 실행을 StackOverflowError를 던지는 코드로 돌린다(SharedRuntime::continuation_for_implicit_exception에 STACK_OVERFLOW를 넘긴다). VM 코드나 네이티브 코드 안이었으면 보호만 풀고 그대로 계속 실행시킨다. 보호를 푸는 이유는 예외 처리기가 실행될 스택 공간을 주기 위해서다.
    • 빨강 구역: "An irrecoverable stack overflow has occurred."를 출력하고 VM을 비정상 종료시키는 경로로 간다. stackOverflow.hpp의 주석은 노랑 구역을 푼 뒤 예외 처리기마저 스택을 다 쓰면 빨강 구역에 닿아 VM이 죽는다고 적는다.

    잡은 뒤에 다시 잠근다

    노랑 구역의 보호를 풀어 둔 채로 두면 다음 오버플로는 곧장 빨강 구역으로 간다. 그래서 HotSpot은 스택이 충분히 풀린 뒤 보호를 다시 건다. 인터프리터에서는 예외 처리기를 찾는 InterpreterRuntime::exception_handler_for_exception이 처리기로 뛰기 전에 reguard_stack을 부르고, 아직 다시 잠글 만큼 스택이 풀리지 않았으면 이 메서드의 처리기로 가지 않고 프레임을 제거해 예외를 호출자 쪽으로 계속 넘긴다(소스 주석). VM 코드가 자바 메서드를 다시 부를 때도 JavaCalls::call_helper가 "자바로 다시 들어갈 때 노랑·예약 구역을 다시 켜야 한다"는 주석과 함께 reguard_stack_if_needed를 부른다. reguard_stack에는 "자바 코드는 결코 노랑 구역 안에서 실행되지 않는다"는 주석과, 그 조건이 깨지면 VM을 멈추는 guarantee가 있다. 이 과정을 거치기 때문에 오버플로를 몇 번이고 잡고 다시 일으킬 수 있다.

    public class Deep {
    static int depth;
    static void down() { depth++; down(); }

    static int measure() {
        depth = 0;
        try { down(); } catch (StackOverflowError e) { }
        return depth;
    }
    public static void main(String[] args) {
        for (int i = 0; i < 3; i++) System.out.print(measure() + " ");
        System.out.println();
    }
}

    세 번 모두 오버플로가 나고, 세 번 모두 잡혀서 다음 측정으로 넘어갔다. 가드 영역이 매번 다시 잠겼다는 증거다. 첫 측정의 깊이가 더 얕은 것은 앞 절에서 본 대로 처음에는 down이 인터프리터로 실행되어 프레임이 크고, 측정 중에 JIT 컴파일된 코드로 바뀌기 때문이다. 같은 프로그램을 -Xint로 돌리면 세 값이 모두 같았다(이번 실행에서 20593).

    이 구조에서 실무에 쓸 결론이 둘 나온다. 첫째, StackOverflowError는 깊이가 한계에 닿은 바로 그 메서드 입구에서 던져진다. 그 메서드가 우리 코드일지, 재귀 중간에 부른 라이브러리 메서드일지는 그때의 스택 사용량이 정하므로 코드만 보고 알 수 없다. 둘째, 잡은 직후의 처리기는 보호가 풀린 노랑 구역 근처에서 시작할 수 있고, 거기서 또 스택을 많이 쓰면 빨강 구역에 닿아 VM 자체가 죽는다. 그러니 catch (StackOverflowError e)는 이 회차의 실험처럼 현상을 보여 주는 용도까지이고, 설계의 답은 앞 절에서 정리한 대로 깊이가 입력 크기에 비례하지 않게 반복문으로 바꾸는 것이다. 꼬리 호출 제거를 보장하는 언어라면 꼬리 위치의 재귀는 프레임을 재사용하므로 이 한계에 닿지 않는다. 자바에서는 그 보장이 없으므로, 여기서 본 가드 영역과 스택 크기가 재귀의 한계를 정한다.

    정리: 흔한 오해와 다른 주제와의 연결

    이 회차의 흐름을 되짚어 보자. 패러다임은 상태와 흐름을 어디에 두느냐의 선택이었다. 명령형은 저장 칸을 바꿔 가는 기계 모델을 그대로 따르고, 함수형은 식을 값으로 치환해 가는 모델을 따른다. 치환으로 추론하려면 함수가 순수하고 식이 참조 투명해야 하며, 값은 불변이어야 한다. 자바는 이 원리를 위한 도구를 버전마다 더해 왔지만 그 원리를 강제하지는 않는다. 그래서 자바의 함수형 프로그래밍은 도구를 쓰는 일과 제약을 지키는 일, 두 가지로 이루어진다.

    자주 마주치는 오해를 정리하면 다음과 같다.

    • "람다와 스트림을 쓰면 함수형이다." 회차 처음의 forEach 코드처럼 람다 안에서 바깥 상태를 바꾸면 반복문과 다르지 않다. 기준은 문법이 아니라 순수성과 불변성이다.
    • "함수형 코드는 어떤 변수도 바꾸지 않는다." 바깥으로 새어 나가지 않는 지역 변수의 변경은 순수성을 해치지 않는다. 스트림 라이브러리와 memoize의 캐시가 그 예다. 함수형은 상태를 없애는 것이 아니라 상태의 위치와 범위를 통제하는 것이다.
    • "final이면 불변이다." final은 재대입만 막는다. 레코드도 얕은 불변이며, 가변 구성 요소는 생성자에서 복사해야 한다.
    • "unmodifiableList로 감싸면 불변이다." 뷰일 뿐이라 원본의 변경이 비친다. 독립된 값이 필요하면 List.copyOf나 toList()를 쓴다.
    • "사실상 final 규칙이 람다를 안전하게 만든다." 재대입만 막을 뿐, 배열이나 컬렉션 같은 가변 객체를 캡처해 바꾸는 것은 막지 않는다.
    • "재귀는 함수형이니 자바에서도 반복문 대신 써도 된다." 자바는 꼬리 호출 제거를 보장하지 않으므로 입력 크기에 비례하는 재귀는 StackOverflowError의 위험을 안는다. 합성 사슬도 마찬가지다.
    • "함수형 스타일은 느리다" 또는 "빠르다". 불변 값은 변경마다 할당이 생기고, 반대로 방어적 복사와 동기화가 필요 없어진다. 어느 쪽이 큰지는 코드와 데이터에 따라 다르므로 측정으로 판단한다.

    이 지식은 앞뒤의 여러 주제와 이어진다. 10회의 병렬 스트림이 동작 매개변수에 요구한 "상태 없음"과 "간섭 없음"은 이 회차의 순수 함수 조건 그 자체이고, 병렬 실행이 결과를 바꾸지 않는다는 보장은 참조 투명성 위에 서 있다. 자바 고급 1편의 메모리 가시성과 happens-before는 final 필드 규칙이라는 특별한 경우를 통해 불변 객체의 스레드 안전성으로 이어진다. 스프링에서 생성자 주입을 쓰면 의존 관계를 final 필드에 담아 생성 후 바뀌지 않게 할 수 있다는 점도 같은 원리이고, 싱글톤 빈이 여러 요청 스레드에 공유되어도 안전하려면 상태 없이 설계해야 한다는 원칙도 같은 뿌리다. JPA에서는 반대로 엔티티가 가변이어야 변경 감지가 동작하므로, 함수형 스타일은 엔티티 바깥의 계산과 DTO, 값 객체에 적용한다. 레코드는 DTO와 값 객체를 만드는 자연스러운 도구다.

    이 장의 핵심

    함수형 프로그래밍은 "값을 받아 새 값을 돌려주는 함수"로 계산을 짜고, 상태 변경과 입출력은 드러난 경계에 모으는 방식이다. 그 이득은 치환으로 추론할 수 있다는 데서 나온다. 자바는 람다·스트림·레코드·봉인 타입·패턴 매칭으로 이 방식을 쓰기 쉽게 해 주지만, 순수성도 깊은 불변성도 꼬리 호출 제거도 보장하지 않는다. 그 빈자리는 규율로 메운다. 그리고 그 규율이 지켜졌을 때 JMM의 final 필드 규칙, 스트림의 최적화, 병렬 실행이 비로소 안전해진다.
    명령형과 선언형
    명령형은 상태를 바꾸는 명령을 순서대로 적어 "어떻게"를 기술하고, 선언형은 결과의 조건만 적어 "무엇을"을 기술한다. 선언형 코드에서도 상태는 사라지지 않고 라이브러리나 엔진 안의 정해진 경계 뒤로 옮겨 간다.
    두 계산 모델
    명령형은 저장 칸을 읽고 쓰는 기계 모델(튜링 기계, 폰 노이만 구조)을, 함수형은 추상화·적용·치환만으로 계산하는 람다 대수를 따른다. 두 모델의 표현력은 같고, 추론하는 방식이 다르다.
    순수 함수와 부수 효과
    순수 함수는 결과가 인자에만 의존하고 결과를 돌려주는 것 말고는 관찰 가능한 효과가 없다. 필드·인자 객체 변경, 입출력이 부수 효과이고, 변하는 외부 상태를 읽는 것은 첫 조건을 깬다. 새어 나가지 않는 지역 상태 변경은 순수성을 해치지 않는다.
    참조 투명성
    식을 그 값으로 바꿔 넣어도 의미가 같으면 참조 투명하다. 공통 부분식 추출, 메모이제이션, 스트림의 연산 생략이 모두 이 성질을 전제로 한다. 자바에서는 정체성(==)을 관찰하지 않는다는 조건이 붙는다.
    클로저와 사실상 final
    람다는 캡처한 지역 변수의 값을 복사해 품으므로 그 변수는 final 또는 사실상 final이어야 한다. 이 규칙은 재대입만 막을 뿐, 캡처한 배열·컬렉션 같은 가변 객체의 변경은 막지 않는다.
    얕은 불변과 수정 불가능
    레코드의 필드는 final이지만 가리키는 객체까지 불변으로 만들지는 않는다. Collections.unmodifiableList는 원본의 뷰이고, List.copyOf·Stream.toList()는 독립된 수정 불가능 리스트를 만든다. 둘은 null 처리도 다르다.
    final 필드 의미론
    JLS §17.5에 따라, 생성자가 끝난 뒤에야 참조를 본 스레드는 데이터 경합이 있어도 final 필드의 올바른 초기값을 본다. 생성 중 this가 탈출하면 보장이 없다. OpenJDK 21의 C2는 final 필드를 쓴 생성자의 정상 종료 지점에 릴리스 장벽을 넣는다.
    대수적 데이터 타입
    레코드(곱)와 봉인 인터페이스(합)로 데이터를 표현하고 패턴 switch로 처리한다. 컴파일러가 망라성을 검사하며, 분리 컴파일로 새 하위 타입이 나타나면 합성 default가 MatchException을 던진다.
    스택과 재귀
    JVM은 호출마다 프레임을 만들고 꼬리 호출 제거를 보장하지 않는다. 입력에 비례하는 재귀와 긴 andThen 사슬은 StackOverflowError로 끝날 수 있으므로 반복으로 바꾼다. 재귀 메모이제이션에 computeIfAbsent를 쓰면 재귀 갱신 예외가 난다.
    구현이 이용하는 불변성
    OpenJDK 21의 불변 리스트는 아무도 참조를 갖지 않는 배열을 복사 없이 저장소로 쓰고, allowNulls 표시가 없는 것만 List.copyOf가 그대로 돌려준다. Set.of의 반복 순서는 실행마다 바뀐다. 레코드·숨은 클래스의 final 필드는 리플렉션으로 바꿀 수 없어 HotSpot JIT가 상수로 믿고, 일반 클래스의 final은 기본적으로 믿지 않는다.
    StackOverflowError의 구현
    HotSpot은 스레드 스택 끝에 메모리 보호된 빨강·노랑·예약 구역을 두고, 메서드 입구에서 섀도 영역만큼 앞을 두드려 본다. 노랑 구역에 닿으면 시그널 처리기가 보호를 잠시 풀고 오류를 던지며, 예외 처리 중에 보호를 다시 건다. 빨강 구역에 닿으면 VM이 종료된다.

    실무에서 이 회차의 지식이 가장 먼저 쓰이는 곳은 코드 리뷰다. 스트림의 forEach나 map 안에서 바깥 컬렉션에 add하거나, int[]·AtomicInteger로 사실상 final 규칙을 우회한 코드는 지금은 순차 실행이라 맞는 결과를 내더라도, 누군가 parallel()을 붙이거나 peek·count처럼 생략될 수 있는 연산과 섞이는 순간 결과가 달라진다. "이 람다를 호출하지 않거나, 다른 스레드에서 두 번 호출하면 무엇이 달라지는가"를 물어 보고, 달라진다면 리덕션이나 toList()로 바꾸는 것이 확실한 판단 기준이다.

    장애 분석에서는 "공유된 값이 바뀌었다"는 증상을 불변성의 경계로 추적한다. 캐시에 넣은 DTO가 다른 요청에서 바뀌어 보인다면, 그 DTO가 가변 리스트를 그대로 품은 레코드이거나 unmodifiableList 뷰를 넘긴 것은 아닌지 확인한다. 설정 객체가 가끔 기본값(0이나 null)으로 보이는 현상이 다중 스레드에서만 나타난다면, 락이나 volatile 없이 공개되는 객체의 필드가 final이 아니거나 생성자에서 this가 탈출했을 가능성을 본다. 둘 다 재현이 어렵고 테스트로 잡히지 않으므로, 설계 단계에서 값 객체의 필드를 final로, 가변 구성 요소를 복사로 고정해 두는 편이 비용이 적다.

    설계 판단에서는 "어디까지 함수형으로 할 것인가"가 문제다. 계산이 복잡하고 규칙이 자주 바뀌는 부분(가격 계산, 권한 판단, 상태 전이 규칙)은 순수 함수로 뽑아 입력과 출력만으로 시험할 수 있게 만드는 가치가 크다. 반대로 JPA 엔티티처럼 프레임워크가 가변성을 전제로 하는 부분, 대량 데이터를 다루며 할당 비용이 측정으로 문제가 된 부분에서는 명령형 코드가 더 맞을 수 있다. 재귀와 합성은 깊이가 입력 크기에 비례하는지 먼저 확인하고, 비례한다면 반복으로 바꾼다. 봉인 타입과 패턴 매칭은 종류가 안정적인 도메인 개념에 쓰고, 공개 라이브러리의 봉인 타입에 종류를 추가하는 것은 사용자 코드의 switch를 깨는 변경으로 취급한다.
  • 다음 코드의 출력을 예측하라. static int calls = 0; static int f(int x) { calls++; return x * 2; }가 있을 때 int a = f(3) + f(3); int t = f(3); int b = t + t; System.out.println(a + " " + b + " " + calls);. 그리고 a와 b가 같은데도 f(3)이 참조 투명하지 않다고 말할 수 있는 근거를 설명하라.
  • List l1 = new ArrayList<>(), l2 = new ArrayList<>();가 있을 때 List.of(1, 2, 3).stream().peek(l1::add).count()와 List.of(1, 2, 3).stream().filter(x -> true).peek(l2::add).count()를 실행한 뒤 두 개수와 l1, l2의 내용을 예측하고, 그 차이가 왜 생기는지 스트림 문서의 부수 효과 규칙으로 설명하라.
  • record Matrix(int[] cells) {}가 있다. (1) new Matrix(new int[]{1, 2}).equals(new Matrix(new int[]{1, 2}))의 결과와 그 이유, (2) m.cells()[0] = 9가 컴파일되는지와 그 결과, (3) 이 레코드를 진짜 불변 값으로 만들려면 무엇을 해야 하는지 답하라.
  • Function f = x -> x + 1; Function g = x -> x * 3;일 때 f.compose(g).andThen(f).apply(2)의 결과를 구하고, 호출 순서를 단계별로 적어라. 이어서 함수 수가 리스트 길이에 따라 달라지는 상황에서 reduce(Function.identity(), Function::andThen)로 합성하는 코드의 위험을 설명하라.
  • 스레드 A가 Config c = new Config(); c.timeout = 30; shared = c;(필드 timeout은 일반 int, shared는 일반 정적 필드)를 실행하고 스레드 B가 shared를 읽어 timeout을 출력한다. B가 볼 수 있는 값은 무엇이며, JLS §17.5의 보장을 받도록 고치려면 Config를 어떻게 바꿔야 하는가?

    1번. 출력은 12 12 3이다. a를 계산하며 f가 두 번, t를 계산하며 한 번 호출되어 calls는 3이다. 반환값만 보면 f(3)은 언제나 6이라 a와 b가 같다. 하지만 참조 투명성은 "식을 값으로 바꿔도 프로그램의 의미가 같은가"를 묻는다. f(3) + f(3)을 t + t로 바꾸면 calls의 최종 값이 달라지고(4가 아니라 3), calls를 읽는 코드가 있다면 그 결과도 달라진다. f는 정적 필드를 바꾸는 부수 효과가 있으므로 순수하지 않고, 그 호출은 참조 투명하지 않다. 통계용 카운터처럼 사소해 보이는 부수 효과도 치환 가능성을 깬다.

    2번. 두 개수는 모두 3이다. 그러나 l1은 [], l2는 [1, 2, 3]이다(OpenJDK 21에서 실행해 확인). 첫 파이프라인은 소스의 크기를 알고 peek이 원소 수를 바꾸지 않으므로 구현이 파이프라인을 실행하지 않고 소스 크기로 개수를 구한다. 두 번째는 filter가 원소 수를 바꿀 수 있어 크기를 미리 알 수 없으므로 파이프라인을 실제로 실행하고, 그 과정에서 peek이 세 번 호출된다. 스트림 문서는 부수 효과가 있는 동작 매개변수가 호출된다는 것 자체를 보장하지 않으며, 결과에 영향이 없으면 연산이나 단계를 생략할 수 있다고 밝힌다. 동작 매개변수가 순수하다면 이 차이는 관찰되지 않는다. 차이가 보이는 것은 우리가 부수 효과를 넣었기 때문이다.

    3번. (1) false다. 레코드의 자동 equals는 참조 타입 구성 요소를 Objects.equals로 비교하고, 배열의 equals는 정체성 비교이므로 내용이 같은 두 배열은 다르다고 판단된다(직접 실행해 확인). (2) 컴파일되고 실행도 된다. 접근자는 필드가 가리키는 배열 자체를 돌려주고, 배열은 가변이므로 레코드 안의 값이 9로 바뀐다. final은 필드 재대입만 막는다. (3) 간결한 생성자에서 cells = cells.clone();으로 복사해 저장하고, 접근자를 public int[] cells() { return cells.clone(); }로 재정의해 복사본을 내보내며, equals와 hashCode를 Arrays.equals·Arrays.hashCode로 재정의한다. 더 간단한 대안은 배열 대신 List.copyOf로 만든 List를 구성 요소로 쓰는 것이다.

    4번. 결과는 8이다. f.compose(g)는 "먼저 g, 그다음 f"이므로 2 × 3 = 6, 6 + 1 = 7이고, .andThen(f)가 그 결과에 다시 f를 적용해 8이 된다. 호출 순서로 보면 가장 바깥 객체(andThen이 만든 것)의 apply(2)가 먼저 this.apply(2), 즉 compose가 만든 객체를 부르고, 그 객체가 g.apply(2)로 6, f.apply(6)으로 7을 얻어 돌아오면, 바깥 객체가 f.apply(7)로 8을 만든다. reduce(Function.identity(), Function::andThen)은 순차 스트림에서 왼쪽부터 acc.andThen(f)를 반복하므로 리스트 길이만큼 중첩된 사슬을 만든다. 호출할 때 그 길이만큼 프레임이 쌓이므로, 길이가 커지면 StackOverflowError가 난다(함수 백만 개로 직접 확인). 길이가 데이터에 따라 정해지면 for 문으로 하나씩 적용한다.

    5번. B는 30을 볼 수도 있고 기본값 0을 볼 수도 있다. shared를 통한 전달이 데이터 경합이고, timeout은 final이 아니라 JMM이 생성 이후의 쓰기와 참조 공개의 순서를 다른 스레드에 보장하지 않기 때문이다. 게다가 이 코드는 생성자가 끝난 뒤에 필드를 쓰므로, 필드를 final로 바꾸는 것만으로는 부족하고 값도 생성자에서 넣어야 한다. final class Config { final int timeout; Config(int timeout) { this.timeout = timeout; } }로 만들고 shared = new Config(30);으로 공개하면, B가 null이 아닌 참조를 읽는 한 30을 본다. 생성자 안에서 this를 다른 곳에 넘기지 않는 것도 조건이다. 레코드 record Config(int timeout) {}도 같은 보장을 준다. 값이 바뀌어야 하는 설정이라면 shared를 volatile로 선언해 가시성을 보장하고, 바꿀 때마다 새 불변 객체로 통째로 교체하는 방식을 쓴다.

    프로그래밍 패러다임(programming paradigm)
    프로그램을 무엇으로 구성하고 구성 요소가 어떻게 상호 작용하는지에 대한 관점. 절차적, 객체지향, 함수형 등이 있고 한 언어가 여러 패러다임을 지원할 수 있다.
    선언형(declarative)
    결과가 만족해야 할 조건, 즉 "무엇"만 기술하고 절차는 실행 체계에 맡기는 방식. SQL과 스트림 파이프라인이 예다. 반대는 상태 변경 명령을 순서대로 적는 명령형(imperative)이다.
    순수 함수(pure function)
    결과가 인자에만 의존하고, 결과를 돌려주는 것 외에 관찰 가능한 효과가 없는 함수.
    부수 효과(side effect)
    결과 반환 외에 함수가 남기는 관찰 가능한 변화. 필드나 인자 객체의 변경, 입출력, 스레드 시작 등이다.
    참조 투명성(referential transparency)
    식을 그 식의 값으로 바꿔 넣어도 프로그램의 의미가 달라지지 않는 성질. 치환으로 추론하고 최적화할 수 있는 근거다.
    클로저(closure)
    함수와 그 함수가 만들어질 때 캡처한 환경을 함께 묶은 것. 자바 람다는 캡처한 지역 변수의 값을 람다 객체 안에 복사해 둔다.
    커링(currying)
    인자 여러 개를 받는 함수를, 인자 하나를 받아 나머지 인자를 받는 함수를 돌려주는 함수의 사슬로 바꾸는 것. 일부 인자를 미리 채우는 것을 부분 적용이라 한다.
    대수적 데이터 타입(algebraic data type)
    곱 타입(모든 구성 요소를 가짐)과 합 타입(여러 종류 중 하나)으로 데이터를 표현하는 방식. 자바에서는 레코드와 봉인 인터페이스의 조합이다.
    꼬리 호출 제거(tail call elimination)
    함수의 마지막 동작인 호출에서 현재 프레임을 재사용해 스택을 늘리지 않는 최적화. JVM 명세에는 이를 위한 명령이나 보장이 없다.
    메모이제이션(memoization)
    순수 함수의 결과를 인자별로 저장해 두고 같은 인자가 오면 저장된 값을 돌려주는 기법. 결과가 인자에만 의존해야 올바르다.
    상수 폴딩(constant folding)
    컴파일할 때 값이 바뀌지 않는다고 확인된 식을 그 결과 상수로 바꿔 넣는 최적화. HotSpot JIT는 정적 final 필드, @Stable 필드, 레코드처럼 믿을 수 있는 클래스의 final 인스턴스 필드에 적용한다.
    스택 가드 영역(stack guard zone)
    HotSpot이 스레드 스택의 끝에 두는 메모리 보호 구역(빨강·노랑·예약). 스택 두드리기가 여기에 닿으면 시그널이 나고, 노랑 구역이면 StackOverflowError가, 빨강 구역이면 VM 종료가 일어난다.
