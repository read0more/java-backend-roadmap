    람다는 무엇에 담기는가

    앞 회차에서 람다(lambda expression)를 "이름 없는 함수를 값처럼 넘기는 문법"으로 만났다. 그런데 자바에서 값은 반드시 타입을 가진다. int x = 3의 3은 int이고, "kim"은 String이다. 그렇다면 s -> s.length()라는 값의 타입은 무엇인가. 자바의 타입 시스템에는 (String) -> int 같은 함수 타입을 변수 선언에 직접 쓰는 문법이 없다. 변수의 타입 자리에 올 수 있는 것은 기본형, 클래스, 인터페이스, 배열, 타입 변수뿐이다.

    자바가 택한 해법은 새로운 종류의 타입을 만드는 대신 이미 있는 인터페이스를 재활용하는 것이었다. 추상 메서드가 딱 하나인 인터페이스가 있으면, 그 메서드 하나의 매개변수 목록과 반환 타입이 곧 "함수의 모양"이 된다. 람다는 그 모양에 맞으면 그 인터페이스를 구현한 객체로 만들어진다. 이 역할을 하는 인터페이스를 함수형 인터페이스(functional interface)라고 부른다. 람다는 함수형 인터페이스 없이는 존재할 수 없다.

    이 선택에는 대가가 따른다. 함수의 모양마다 인터페이스가 하나씩 필요하다. 문자열을 받아 정수를 돌려주는 함수, 정수 두 개를 받아 정수를 돌려주는 함수, 아무것도 받지 않고 값을 만들어 내는 함수가 모두 서로 다른 인터페이스여야 한다. 이 회차는 이 대가를 자바가 어떻게 줄였는지를 따라간다. 제네릭으로 모양의 수를 줄이고, 표준 라이브러리 java.util.function 패키지에 자주 쓰는 모양을 미리 정의해 두었으며, 기본형 때문에 생기는 비용은 특화 인터페이스로 다시 덜어 냈다. 그리고 그 과정에서 컴파일러가 람다의 타입을 정하는 규칙, 즉 타깃 타이핑(target typing)이 어떻게 작동하는지, 바이트코드에서는 이 모든 것이 어떻게 보이는지를 확인한다.

    함수형 인터페이스의 정의: 추상 메서드가 하나

    함수형 인터페이스는 Java Language Specification(JLS) §9.8이 정의한다. 요지는 sealed로 선언되지 않았고, Object의 메서드를 제외하면 추상 메서드가 하나뿐인 인터페이스다. 이 짧은 정의에 판정에 필요한 규칙이 여러 개 들어 있으니 하나씩 풀어 보자.

    첫째, 세는 대상은 추상 메서드뿐이다. 디폴트 메서드(default method)와 정적 메서드(static method), private 메서드는 몸체가 있으므로 세지 않는다. 그래서 Function은 andThen, compose라는 디폴트 메서드와 identity라는 정적 메서드를 가지고 있지만 추상 메서드는 apply 하나라서 함수형 인터페이스다. 디폴트 메서드가 몇 개든 상관없다.

    둘째, Object의 public 메서드와 시그니처가 같은 추상 메서드는 세지 않는다. 대표적인 예가 java.util.Comparator다. 이 인터페이스의 소스에는 int compare(T o1, T o2)와 함께 boolean equals(Object obj)도 추상 메서드로 선언되어 있다. 그런데도 함수형 인터페이스다. 어떤 클래스가 Comparator를 구현하든 그 클래스는 이미 Object로부터 public equals를 물려받으므로, 이 선언은 새로운 계약을 추가하지 않는다. JLS는 이 규칙이 바로 Comparator 같은 인터페이스를 함수형으로 다루기 위한 것이라고 설명한다.

    이 예외가 public 메서드에만 적용된다는 점이 중요하다. Object.clone()은 protected다. 인터페이스에 Object clone();을 선언하면 그것은 public 추상 메서드가 되고, 구현 클래스가 물려받은 protected clone으로는 채워지지 않는다. 그래서 JLS의 예제 9.8-1은 int m();과 Object clone();을 가진 인터페이스 Foo를 함수형이 아니라고 판정한다. Object의 멤버가 아닌 추상 메서드는 하나지만, Object의 public 멤버가 아닌 추상 메서드는 둘이기 때문이다.

    셋째, 상속받은 추상 메서드도 센다. 다만 상위 인터페이스 여러 곳에서 오버라이드 동등(override-equivalent)한 시그니처를 물려받으면 그것들은 논리적으로 메서드 하나로 본다. 넷째, sealed 인터페이스는 추상 메서드가 하나여도 함수형 인터페이스가 아니다. sealed 인터페이스는 허용된 구현 클래스 목록을 고정하는데, 람다는 이름 없는 새 구현 클래스를 만들어 내므로 그 목록과 충돌한다.

    public class Sealed {
    sealed interface Shape permits Circle { double area(); }
    record Circle(double r) implements Shape {
        public double area() { return Math.PI * r * r; }
    }

    interface Named { String name(); }
    interface Labeled extends Named {
        String name();                                   // 상속받은 것과 같은 시그니처: 여전히 하나
        default String label() { return "[" + name() + "]"; }  // 디폴트 메서드는 세지 않는다
    }

    public static void main(String[] args) {
        Labeled l = () -> "kim";
        System.out.println(l.label());   // [kim]
        Shape s = () -> 1.0;             // 컴파일 오류
    }
}

    @FunctionalInterface는 무엇을 약속하는가

    java.util.function의 인터페이스에는 모두 @FunctionalInterface 애너테이션이 붙어 있다. 이 애너테이션이 있어야 람다를 쓸 수 있다고 오해하기 쉽지만 그렇지 않다. FunctionalInterface의 Javadoc은 이 애너테이션이 없어도 컴파일러는 정의를 만족하는 인터페이스를 함수형 인터페이스로 다룬다고 명시한다. 앞의 Labeled에는 애너테이션이 없었지만 람다를 받았다.

    애너테이션이 하는 일은 하나다. 붙인 인터페이스가 함수형 인터페이스의 조건을 만족하지 않으면 컴파일 오류를 내게 한다(JLS §9.6.4.9). 추상 메서드를 두 개 선언하고 애너테이션을 붙여 보면 javac가 이렇게 거부한다.

    @FunctionalInterface
interface TwoMethods {
    void a();
    void b();
}

    이 검사가 왜 필요한지는 인터페이스가 시간이 지나며 바뀐다는 점을 생각하면 분명해진다. 어떤 라이브러리가 함수형 인터페이스를 공개했고 사용자 코드 수백 곳이 그것을 람다로 구현하고 있다고 하자. 누군가 이 인터페이스에 추상 메서드를 하나 더 추가하면 라이브러리 자체는 문제없이 컴파일되지만, 그 순간 사용자 코드의 모든 람다가 "is not a functional interface" 오류로 깨진다. 오류가 라이브러리가 아니라 사용하는 쪽에서 터지는 것이다. 애너테이션을 붙여 두면 이 실수가 인터페이스를 고치는 사람의 컴파일 단계에서 바로 드러난다. Javadoc의 표현대로 설계 의도를 기록하고 그 의도를 컴파일러가 지키게 하는 장치다.

    이 애너테이션은 @Retention(RetentionPolicy.RUNTIME)으로 선언되어 있어서 클래스 파일의 RuntimeVisibleAnnotations 속성에 남고 리플렉션으로도 읽을 수 있다. 그러나 런타임에 람다가 만들어지는 과정은 이 애너테이션을 보지 않는다. 람다 객체를 만드는 데 필요한 정보는 컴파일러가 이미 바이트코드에 다 적어 두었기 때문이다. 그 정보가 무엇인지는 잠시 뒤에 javap로 확인한다. 반대로 JLS는 우연히 함수형인 인터페이스도 있으므로 모든 함수형 인터페이스에 이 애너테이션을 붙이는 것이 필요하지도 바람직하지도 않다고 적고 있다. 람다로 구현되기를 의도한 인터페이스에만 붙이면 된다.

    타입마다 인터페이스를 만들면 생기는 일

    이제 함수 모양마다 인터페이스가 필요하다는 대가를 직접 치러 보자. 문자열을 받아 문자열을 돌려주는 함수와 정수를 받아 정수를 돌려주는 함수가 필요하다면 이렇게 두 개를 만들어야 한다.

    interface StringFunction  { String  apply(String s);  }
interface IntegerFunction { Integer apply(Integer n); }
interface StringToInteger { Integer apply(String s);  }
// 입력 타입 × 출력 타입의 조합마다 하나씩 ...

    입력 타입과 출력 타입의 조합마다 인터페이스가 늘어난다. 타입이 열 개면 단항 함수만 백 개다. 세 인터페이스의 구조는 완전히 같고 다른 것은 타입 이름뿐인데, 그 차이 때문에 코드를 복제해야 한다. 이 중복을 없애는 첫 번째 시도는 가장 일반적인 타입인 Object를 쓰는 것이다.

    interface ObjectFunction {
    Object apply(Object input);
}

public class ObjFn {
    public static void main(String[] args) {
        ObjectFunction upper = o -> ((String) o).toUpperCase();
        String s = (String) upper.apply("java");   // 쓸 때마다 캐스트
        System.out.println(s);
        Object r = upper.apply(10);                // 컴파일은 통과한다
    }
}

    인터페이스는 하나로 줄었지만 두 가지를 잃었다. 람다 안에서 ((String) o)처럼 직접 캐스트해야 하고, 결과를 받을 때도 (String) 캐스트가 필요하다. 더 큰 손실은 타입 안전성이다. upper.apply(10)은 명백히 잘못된 호출인데 컴파일러는 통과시킨다. 매개변수 타입이 Object이니 정수도 받을 자격이 있기 때문이다. 오류는 실행 중에, 그것도 호출한 곳이 아니라 람다 본문 안의 캐스트에서 터진다. 스택 트레이스의 lambda$main$0은 javac가 람다 본문을 옮겨 담은 private 정적 메서드의 이름이다.

    제네릭(generics)은 이 두 손실을 동시에 해결한다. 타입을 매개변수로 빼면 인터페이스 하나로 모든 조합을 표현하면서도, 사용하는 쪽에서 타입을 정해 컴파일러가 검사하게 할 수 있다.

    @FunctionalInterface
public interface GenericFunction {
    R apply(T t);
}

    입력 타입 T와 출력 타입 R을 타입 매개변수로 뺐다. 이 인터페이스를 쓰는 쪽은 다음과 같다.

    public class GenericMain {
    public static void main(String[] args) {
        GenericFunction length = s -> s.length();
        GenericFunction square = n -> n * n;
        Integer a = length.apply("hello");
        Integer b = square.apply(7);
        System.out.println(a + " " + b);   // 5 49
    }
}

    두 가지가 달라졌다. 첫째, 람다의 매개변수 s에 타입을 적지 않았는데도 s.length()를 부를 수 있다. 대입 대상의 타입 GenericFunction에서 함수 타입이 (String) -> Integer로 정해지고, 컴파일러가 그 매개변수 타입을 s에 준다. 둘째, length.apply(10)은 이제 컴파일 오류다. 타입 검사가 실행 시점에서 컴파일 시점으로 돌아왔다. 결과를 받을 때 캐스트를 쓰지도 않는다. 그렇다면 그 캐스트는 정말로 사라졌을까. 한 층 아래로 내려가 보자.

    바이트코드에서 본 제네릭 함수형 인터페이스

    자바 제네릭은 타입 소거(type erasure)로 구현된다. 타입 매개변수는 컴파일 후 그 상한(bound)으로 지워지는데, 상한을 적지 않은 T와 R은 Object가 된다. javap -s로 GenericFunction을 보면 소스의 R apply(T)가 JVM 수준에서 어떤 메서드인지 드러난다.

    public interface GenericFunction {
  public abstract R apply(T);
    descriptor: (Ljava/lang/Object;)Ljava/lang/Object;

    지금까지 본 람다 프록시 클래스에는 인터페이스 메서드가 하나뿐이었다. 함수형 인터페이스의 추상 메서드가 JVM 수준에서도 디스크립터 하나, (Object)Object로만 존재했기 때문이다. 그런데 언어 수준에서는 메서드 하나인데 JVM 수준에서는 디스크립터가 둘 이상인 경우가 있다. 제네릭 상위 인터페이스의 메서드를 하위 인터페이스가 구체적인 타입으로 다시 선언하는 경우, 그리고 소거 결과가 서로 다른 두 상위 인터페이스에서 같은 시그니처를 물려받는 경우다. 이때 무엇이 필요한지는 JVM이 호출할 메서드를 고르는 규칙에서 나온다.

    JVMS §5.4.6은 invokeinterface나 invokevirtual을 실행할 때, 수신 객체의 런타임 클래스에서 호출 지점이 해석해 둔 메서드를 오버라이드할 수 있는 메서드를 고른다고 정한다. 그리고 §5.4.5의 오버라이드 정의는 이름과 디스크립터가 같을 것을 요구한다. 그러니 JVM에게 apply(String)String과 apply(Object)Object는 이름만 같은 서로 다른 메서드다. 소스에서 Function 변수로 부른 호출 지점은 바이트코드에 apply:(Object)Object를 적고, 그 하위 인터페이스 변수로 부른 호출 지점은 apply:(String)String을 적는다. 같은 람다 객체가 두 경로 모두에서 같은 본문에 닿으려면 두 디스크립터가 다 구현되어 있어야 한다. 지워진 디스크립터를 구체적인 디스크립터로 이어 주는 이 메서드를 브리지 메서드(bridge method)라고 부른다. 누가 이 브리지를 만드는지는 경우에 따라 다르다.

    직렬화 가능한 람다: SerializedLambda와 $deserializeLambda$

    앞에서 교집합에 Serializable이 들어 있으면 javac가 FLAG_SERIALIZABLE을 켜고 람다를 만든 클래스 쪽에도 추가 지원 코드가 생긴다고만 적었다. 그 코드가 무엇이고 왜 필요한지 따라가 보면, 람다 객체가 겉으로는 평범한 인스턴스여도 JVM 안에서는 보통의 객체와 상당히 다르게 다뤄진다는 것이 드러난다. 출발점은 JLS §15.27.4다. 타깃 함수형 인터페이스 타입이 java.io.Serializable의 하위 타입이면 결과 객체는 직렬화 가능한 클래스의 인스턴스가 된다. 같은 절은 람다에서 나온 객체를 직렬화 가능하게 만드는 데에는 실행 시간 부담과 보안상의 함의가 따르므로 "기본으로" 직렬화 가능할 필요는 없다고 덧붙인다. 그래서 Serializable을 섞지 않은 보통의 람다를 ObjectOutputStream에 쓰면 NotSerializableException이 난다.

    직렬화 가능하게 만들 때의 문제는 무엇을 기록하느냐다. 람다 프록시는 숨겨진 클래스이고, 이름 뒤의 주소는 실행마다 달라질 수 있으며, 바이트를 읽는 다른 JVM에는 그 클래스가 아예 없다. 클래스 이름과 필드 값을 그대로 적는 보통의 직렬화로는 읽는 쪽이 같은 클래스를 찾을 수 없다. 그래서 OpenJDK는 람다 객체 자체가 아니라 그 람다를 다시 만드는 데 필요한 정보를 기록한다. 그 정보를 담는 그릇이 java.lang.invoke.SerializedLambda다. 직접 꺼내 보자.

    제네릭 메서드와 함수: 추론과 와일드카드

    함수형 인터페이스가 제네릭이 되면 이번에는 그 함수를 받는 메서드도 제네릭이 된다. 리스트의 원소마다 함수를 적용해 새 리스트를 만드는 메서드를 생각해 보자. 이런 메서드를 어떻게 쓰는지는 다음 회차에서 본격적으로 다루고, 여기서는 타입이 어떻게 결정되는지만 본다.

    static  List map(List list, Function f) {
    List result = new ArrayList<>();
    for (T t : list) result.add(f.apply(t));
    return result;
}

List names = List.of("kim", "lee");
List lengths = map(names, s -> s.length());   // [3, 3]

    호출 map(names, s -> s.length())에서 컴파일러는 타입 추론(type inference)으로 T와 R을 정한다. names가 List이므로 T는 String이다. 그러면 람다의 대상 타입이 Function이 되고, 매개변수 s는 String이 된다. 람다 본문 s.length()는 int를 내므로 박싱을 거쳐 Integer와 호환되고, 결과를 받는 변수가 List이므로 R은 Integer로 정해진다. 람다의 매개변수 타입은 바깥(T)에서 들어오고, 람다의 반환 타입은 다시 바깥(R)을 정하는 데 쓰인다. 람다와 제네릭 메서드는 이렇게 서로의 타입을 주고받는다.

    이 선언에는 숨은 약점이 있다. 이미 만들어 둔 함수 객체를 넘길 때 드러난다.

    첫 번째 오류부터 보자. describe는 어떤 객체든 받을 수 있는 함수이니 문자열을 넘기는 데 아무 문제가 없어야 한다. 그런데 List에서는 T = String이라는 제약이, Function에서는 T = Object라는 제약이 나온다. 제네릭 타입은 무공변(invariant)이어서 Function은 Function의 하위 타입이 아니고, 두 제약이 모두 "같아야 한다(equality)"이므로 충돌한다. 두 번째 오류는 반환 쪽에서 같은 일이 일어난 것이다. 결과를 List로 받으려니 R = Number인데, 넘긴 함수는 R = Integer로 고정되어 있다.

    세 번째 줄이 통과하는 이유가 흥미롭다. 람다는 미리 만들어진 객체가 아니라 문맥에 맞춰 타입이 정해지는 식이다. R = Number로 정해진 뒤 람다는 Function로 만들어지고, 본문의 int는 박싱되어 Integer가 되며 이는 Number에 대입 가능하다. 같은 계산이라도 람다로 바로 쓰면 통과하고 변수에 담아 두었다가 넘기면 실패하는 것은 이 차이 때문이다.

    해결책은 함수의 매개변수 자리를 ? super T로, 반환 자리를 ? extends R로 여는 것이다. 함수는 매개변수로 값을 소비하고 반환값으로 값을 생산한다. T를 받을 수 있는 함수라면 T의 상위 타입을 받는 함수여도 되고, R을 내야 하는 자리라면 R의 하위 타입을 내는 함수여도 된다. 선언을 Function f로 바꾸면 세 줄 모두 컴파일되고 결과는 [[kim], [lee]] [3, 3] [3, 3]이다. JDK의 API가 바로 이렇게 선언되어 있다.

    JDK 21의 선언와일드카드의 위치
    Stream.map(Function mapper)입력은 super, 출력은 extends
    Stream.filter(Predicate predicate)입력만 있으므로 super
    Iterable.forEach(Consumer action)입력만 있으므로 super
    Map.computeIfAbsent(K key, Function mappingFunction)입력은 super, 출력은 extends

    함수형 인터페이스와 제네릭이 만나는 곳에는 한 가지 제약이 더 있다. 인터페이스가 아니라 추상 메서드 자체가 제네릭이면 람다로 구현할 수 없다. JLS §15.27.3은 람다가 함수 타입과 맞으려면 그 함수 타입에 타입 매개변수가 없어야 한다고 정한다. 람다 문법에는 같은 타입 매개변수를 선언할 자리가 없기 때문이다.

    interface Identity {  T id(T t); }   // 메서드가 제네릭이다

Identity i = t -> t;                    // 컴파일 오류
    T2.java:12: error: incompatible types: invalid functional descriptor for lambda expression
        Identity i = t -> t;
                     ^
    method (T)T in interface Identity is generic
  where T is a type-variable:
    T extends Object declared in method id(T)

    Identity는 여전히 함수형 인터페이스이지만 람다는 받을 수 없다. 이 인터페이스는 static T same(T t) 같은 제네릭 메서드를 가리키는 메서드 참조(GenRef::same)로는 구현할 수 있다. 실제로 그렇게 하면 i.id("kim")과 i.id(7)이 각각 String과 Integer를 돌려준다. 메서드 참조의 규칙은 04회에서 다룬다. 실무에서는 타입 매개변수를 메서드가 아니라 인터페이스에 두는 것이 일반적이고, java.util.function의 인터페이스도 전부 그렇게 되어 있다.

    람다에는 스스로의 타입이 없다: 타깃 타입

    지금까지의 예제에서 람다의 타입은 늘 바깥에서 정해졌다. 변수 선언의 타입, 메서드 매개변수의 타입이 람다가 무엇이 될지를 결정했다. 이것은 우연이 아니라 람다라는 식(expression)의 본질이다. JLS는 람다를 폴리 식(poly expression)으로 분류한다. 폴리 식은 식 자체만 보고는 타입이 정해지지 않고, 그 식이 놓인 문맥이 기대하는 타입, 즉 타깃 타입(target type)을 알아야 타입이 정해지는 식이다. 3 + 4는 어디에 있든 int이지만, s -> s.length()는 어디에 있느냐에 따라 Function일 수도, ToIntFunction일 수도, 직접 만든 어떤 인터페이스일 수도 있다.

    그래서 JLS §15.27은 람다가 대입 문맥(assignment context), 호출 문맥(invocation context), 캐스트 문맥(casting context) 이외의 곳에 나타나면 컴파일 오류라고 정한다. 세 문맥은 모두 "이 자리에는 이런 타입이 와야 한다"는 정보를 가진 곳이다. 타깃 타입이 없거나, 있어도 함수형 인터페이스가 아니면 람다는 갈 곳이 없다. javac로 직접 확인해 보자.

    Object o = () -> System.out.println("hi");      // (1) 타깃 타입이 Object
var f = (String s) -> s.length();               // (2) 타깃 타입이 없다
(s -> s.length()).apply("x");                   // (3) 문맥이 없는 곳
Object o2 = (Runnable) () -> System.out.println("hi");   // (4) 캐스트 문맥: 통과
    T1.java:5: error: incompatible types: Object is not a functional interface
        Object o = () -> System.out.println("hi");
                   ^
T1.java:6: error: cannot infer type for local variable f
        var f = (String s) -> s.length();
            ^
  (lambda expression needs an explicit target-type)
T1.java:12: error: lambda expression not expected here
        (s -> s.length()).apply("x");
         ^

    (1)은 타깃 타입이 있지만 Object는 함수형 인터페이스가 아니다. 모든 람다 객체는 결국 Object이지만, 컴파일러는 Object에서 함수 타입을 끌어낼 수 없으니 람다를 어떤 인터페이스로 만들지 정할 수 없다. (2)는 반대 방향의 문제다. var는 오른쪽 식의 타입으로 왼쪽 변수의 타입을 정하는데, 람다는 왼쪽이 정해져야 자기 타입이 정해진다. 서로가 서로를 기다리므로 추론이 불가능하다. 매개변수 타입을 (String s)로 명시해도 소용없다. 매개변수 타입을 안다고 해서 그것이 Function인지 ToIntFunction인지 정해지지는 않기 때문이다. (3)은 메서드 호출의 수신 객체 자리로, 어떤 타입도 기대되지 않는 곳이다. (4)처럼 캐스트를 씌우면 캐스트가 타깃 타입을 제공하므로 통과한다.

    세 가지 기본 문맥만 있는 것 같지만 타깃 타입은 여러 겹으로 전달된다. 조건 연산자의 두 피연산자는 조건식 전체의 타깃 타입을 물려받고, return 문의 식은 메서드의 반환 타입을, 람다 본문의 식은 바깥 람다의 함수 타입이 정한 반환 타입을 물려받는다. 다음 코드는 모두 컴파일되고 inner, LOUD를 차례로 출력한다.

    static Runnable make(boolean loud) {
    // return 문 → 조건 연산자 → 두 람다 모두 Runnable
    return loud ? () -> System.out.println("LOUD") : () -> System.out.println("quiet");
}

Supplier factory = () -> () -> System.out.println("inner");  // 바깥 람다의 반환 타입이 안쪽 람다의 타깃
factory.get().run();   // inner
make(true).run();      // LOUD

    타깃 타입이 같은 람다 본문을 전혀 다른 객체로 만든다는 점도 기억해 두자. () -> System.out.println("same body")를 Runnable 변수에 대입하면 Runnable을 구현한 객체가 되어 new Thread(r)에 넘길 수 있다. 같은 일을 Callable로 하려면 본문이 값을 돌려줘야 하므로 () -> { System.out.println("same body"); return null; }로 써야 한다. 두 객체는 서로 다른 클래스의 인스턴스이고 서로 대입할 수 없다.

    타깃 타입이 와일드카드를 가질 때

    앞에서 본 Function처럼 타깃 타입에 와일드카드가 들어 있으면, 람다는 어떤 매개변수 타입과 반환 타입으로 만들어질까. 와일드카드 자체는 구체적인 타입이 아니므로 그대로는 함수 타입을 정할 수 없다. JLS §15.27.3은 이때 그라운드 타깃 타입(ground target type)을 따로 구한다고 정한다. 매개변수 타입을 생략한 람다라면 JLS §9.9의 "와일드카드가 아닌 매개변수화(non-wildcard parameterization)"를 쓴다. 규칙은 단순하다. ? super L은 L로, ? extends U는 U와 타입 매개변수 상한의 교집합으로, 아무 제한 없는 ?는 타입 매개변수의 상한으로 바꾼다.

    Function f = s -> s.length();
Number n = f.apply("abcd");   // 4

    이 경우 그라운드 타깃 타입은 Function다. 그래서 s는 String이 되어 s.length()를 부를 수 있고, 본문의 int는 박싱되어 Number 자리에 들어간다.

    명시한 매개변수 타입은 정확히 같아야 한다

    람다 매개변수에 타입을 직접 적으면 그 타입은 함수 타입의 매개변수 타입과 정확히 같아야 한다(JLS §15.27.3). 메서드 오버라이딩과 달리 더 넓은 타입을 받겠다고 선언할 수 없다. Object를 받는 함수는 String도 받을 수 있으니 논리적으로는 문제가 없어 보이지만 규칙이 허용하지 않는다.

    Function f = (Object o) -> o.hashCode();   // 컴파일 오류
Function g = (String s) -> s.length();     // 통과
    E.java:4: error: incompatible types: incompatible parameter types in lambda expression
        Function f = (Object o) -> o.hashCode();
                                      ^

    모양이 같아도 이름이 다르면 다른 타입이다

    람다가 문맥에 따라 어떤 인터페이스든 될 수 있다고 해서, 이미 만들어진 함수 객체도 그렇게 자유로운 것은 아니다. 자바의 타입 호환성은 구조가 아니라 이름과 선언된 상속 관계로 정해진다. 이를 명목적 타이핑(nominal typing)이라고 한다. 메서드 모양이 똑같은 두 인터페이스라도 상속 관계가 없으면 서로 대입할 수 없다.

    interface StringToInt { int convert(String s); }

Function fn = s -> s.length();
StringToInt sti = fn;            // 컴파일 오류
StringToInt ok  = s -> s.length();     // 람다: 새로 타입이 정해진다
StringToInt ok2 = fn::apply;           // 메서드 참조: fn을 감싼 새 객체
    T1.java:8: error: incompatible types: Function cannot be converted to StringToInt
        StringToInt sti = fn;
                          ^

    차이는 식인가, 값인가에 있다. 람다 s -> s.length()는 아직 타입이 정해지지 않은 식이므로 StringToInt 자리에 놓이면 StringToInt로 만들어진다. 반면 fn은 이미 만들어진 객체를 가리키는 변수이고, 그 객체의 클래스는 Function을 구현했을 뿐 StringToInt를 구현하지 않았다. 객체의 클래스는 만들어진 뒤 바뀌지 않으므로 대입은 일반 참조 타입 변환 규칙을 따르고, 상속 관계가 없으니 실패한다. 두 타입을 잇고 싶다면 fn::apply나 s -> fn.apply(s)처럼 기존 객체에 위임하는 새 객체를 만들어야 한다. 이때 호출이 한 단계 더 생긴다는 점도 알아 두자.

    상속 관계가 있으면 한 방향으로만 대입된다. UnaryOperator는 Function를 상속하므로 UnaryOperator은 Function 변수에 대입할 수 있다. 반대는 안 된다. List.replaceAll은 UnaryOperator를 받도록 선언되어 있어서, Function 변수를 넘기면 거부된다.

    Function f = s -> s.toUpperCase();
UnaryOperator u = f;              // 컴파일 오류
List names = new ArrayList<>(List.of("kim"));
names.replaceAll(f);                      // 컴파일 오류
names.replaceAll(f::apply);               // 통과: UnaryOperator로 감싼다
    Pred2.java:6: error: incompatible types: Function cannot be converted to UnaryOperator
        UnaryOperator u = f;
                                  ^
Pred2.java:8: error: incompatible types: Function cannot be converted to UnaryOperator
        names.replaceAll(f);
                         ^

    이 성질은 API를 설계할 때 중요한 판단 기준이 된다. 메서드 매개변수를 직접 만든 함수형 인터페이스로 선언하면, 호출하는 쪽이 람다를 바로 쓸 때는 불편이 없지만 이미 Function으로 가지고 있는 객체를 넘기려면 매번 감싸야 한다. 표준 인터페이스를 쓰면 이런 변환이 필요 없다. 반대로 도메인에서 의미가 분명한 이름(예: DiscountPolicy)이 주는 가독성을 택할 수도 있다. 어느 쪽이든 "모양이 같으니 알아서 맞춰지겠지"라는 기대는 람다 식에만 통한다.

    오버로딩과 람다: 컴파일러는 어느 메서드를 고르는가

    타깃 타입이 람다의 타입을 정한다면, 같은 이름의 메서드가 서로 다른 함수형 인터페이스를 받도록 오버로딩되어 있을 때는 어떻게 될까. 타깃 타입 후보가 둘이 되는 셈이다. 이 문제를 풀려면 먼저 람다 본문의 두 가지 성질을 알아야 한다.

    JLS §15.27.2는 블록 본문의 모든 return 문이 return; 꼴이면 void 호환(void-compatible), 블록이 정상적으로 끝날 수 없고 모든 return 문이 return 식; 꼴이면 값 호환(value-compatible)이라고 정의한다. 본문이 블록이 아니라 식 하나일 때는 그 식이 문장으로도 쓰일 수 있는 식(statement expression), 예를 들어 메서드 호출이나 대입이라면 void를 돌려주는 함수 타입과도 호환된다. 결과는 버려진다. JLS §15.27.3의 표현대로, () -> expr에서 expr이 문장 식이면 타깃 타입에 따라 () -> { return expr; }로도, () -> { expr; }로도 해석된다.

    List list = new ArrayList<>();
Consumer  adder  = s -> list.add(s);   // void로 해석: 반환값 boolean을 버린다
Predicate adder2 = s -> list.add(s);   // 값으로 해석: boolean을 돌려준다
adder.accept("a");
System.out.println(adder2.test("b") + " " + list);   // true [a, b]

    같은 본문 list.add(s)가 두 인터페이스 모두에 맞는다. 그렇다면 둘 다 받는 오버로딩이 있을 때는 어느 쪽인가. 다음 실험의 결과는 javac(JDK 21)로 확인한 것이다.

    static void run(Runnable r)       { System.out.println("Runnable"); r.run(); }
static  void run(Supplier s) { System.out.println("Supplier -> " + s.get()); }

static int counter = 0;
static int next() { return ++counter; }

run(() -> next());                         // Supplier -> 1
run(() -> { next(); });                    // Runnable
run(() -> System.out.println("print"));    // Runnable, 이어서 print

    둘째와 셋째는 쉽다. { next(); }는 return 문이 없는 블록이라 void 호환일 뿐 값 호환이 아니고, System.out.println(...)은 반환 타입이 void라 값이 될 수 없다. 후보가 Runnable 하나로 줄어든다. 문제는 첫째다. next()는 문장 식이면서 int 값을 내므로 두 메서드에 모두 맞는다. 이때는 JLS §15.12.2.5의 "가장 구체적인 메서드" 규칙이 작동한다. 이 규칙에 따르면 서로 상속 관계가 없는 두 함수형 인터페이스 S와 T에 대해, 인자가 명시적 타입 람다(explicitly typed lambda)이고 T의 함수 타입 반환형이 void이면 S가 더 구체적이다. 그래서 값을 돌려주는 Supplier 쪽이 선택된다.

    여기서 "명시적 타입 람다"라는 조건이 핵심이다. JLS §15.27.1은 모든 매개변수에 타입을 적은 람다를 명시적 타입, 모두 생략한 람다를 암묵적 타입이라 부르고, 매개변수가 없는 람다는 명시적 타입으로 본다. () -> next()는 매개변수가 없으니 명시적 타입이라 규칙이 적용되었다. 매개변수가 있는 람다에서는 결과가 달라진다.

    static void exec(Consumer c)          { System.out.println("Consumer"); }
static void exec(Function f) { System.out.println("Function"); }

exec(s -> s.length());            // 컴파일 오류: 모호하다
exec((String s) -> s.length());   // Function
    T5.java:6: error: reference to exec is ambiguous
        exec(s -> s.length());
        ^
  both method exec(Consumer) in T5 and method exec(Function) in T5 match

    암묵적 타입 람다 s -> s.length()는 반환형 비교 규칙의 대상이 아니므로 두 후보 중 어느 쪽도 더 구체적이지 않고, 모호하다는 오류가 난다. 매개변수 타입을 적으면 규칙이 적용되어 Function이 선택된다. 같은 본문인데 매개변수 타입 표기 하나로 결과가 갈리는 셈이다. 이런 미묘함 때문에 서로 다른 함수형 인터페이스를 받는 같은 이름의 메서드를 만들면 사용자는 매개변수 타입을 적느냐 마느냐에 따라 다른 결과를 만나게 된다. 함수를 받는 메서드를 설계할 때는 오버로딩 대신 이름을 나누는 쪽이 이 문제를 원천적으로 피한다.

    JDK에도 이런 오버로딩이 있다. ExecutorService.submit은 Runnable을 받는 것과 Callable를 받는 것이 있다. 자바 고급 1편의 스레드 풀에서 써 본 메서드다.

    ExecutorService es = Executors.newSingleThreadExecutor();
Future f1 = es.submit(() -> System.out.println("side effect"));   // void 호출: Runnable
Future f2 = es.submit(() -> 42);                                  // 값: Callable
System.out.println(f1.get() + " " + f2.get());
es.shutdown();
    side effect
null 42

    println은 void라 값 호환이 아니므로 Runnable 버전이 선택되고, 그 Future의 get()은 null을 돌려준다. 42는 문장 식이 아니므로 void 호환이 아니어서 Callable 버전이 선택된다. side effect가 항상 먼저 찍히는 이유는 f1.get()이 작업이 끝날 때까지 기다린 뒤에야 println의 인자가 완성되기 때문이다.

    기본 함수형 인터페이스: Function, Consumer, Supplier, Runnable

    함수 모양마다 인터페이스를 직접 만들 필요가 없도록 자바 8은 java.util.function 패키지를 추가했다. 패키지 문서는 이 인터페이스들이 모든 함수 모양을 망라하지는 않지만 흔한 요구를 충족하기에 충분하도록 골랐다고 밝힌다. 그 중심에는 네 가지 기본 모양이 있다. 여기에 이 패키지 밖에 있지만 같은 자리에 놓이는 Runnable을 함께 보자.

    인터페이스추상 메서드모양패키지(도입)
    FunctionR apply(T t)T 하나를 받아 R을 낸다java.util.function (1.8)
    Consumervoid accept(T t)T 하나를 받고 아무것도 내지 않는다java.util.function (1.8)
    SupplierT get()아무것도 받지 않고 T를 낸다java.util.function (1.8)
    Runnablevoid run()받지도 내지도 않는다java.lang (1.0)
    CallableV call() throws Exception받지 않고 V를 내며 검사 예외를 던질 수 있다java.util.concurrent (1.5)

    모양을 입력의 개수와 출력의 유무로 보면 체계가 보인다. 입력 1, 출력 1이 Function, 입력 1, 출력 0이 Consumer, 입력 0, 출력 1이 Supplier, 입력 0, 출력 0이 Runnable이다. Runnable과 Callable은 람다보다 훨씬 오래되었지만 추상 메서드가 하나뿐이었기 때문에 함수형 인터페이스의 정의를 그대로 만족한다. 두 인터페이스의 소스에는 지금 @FunctionalInterface가 붙어 있는데, 이 애너테이션 자체가 1.8에 생겼으니 붙은 시점도 그 이후다. 자바는 오래된 인터페이스를 버리지 않고 람다의 타깃으로 그대로 흡수했다. Comparator(1.2)도 마찬가지다.

    Function: 변환과 합성

    Function은 값을 다른 값으로 바꾸는 변환이다. 스트림의 map, Map.computeIfAbsent가 이것을 받는다. 추상 메서드 외에 디폴트 메서드 andThen과 compose, 정적 메서드 identity를 가진다. JDK 21 소스에서 andThen은 (T t) -> after.apply(apply(t))를, compose는 (V v) -> apply(before.apply(v))를 돌려준다. 둘 다 새 람다 객체를 만들어 돌려주며, 원래 함수 객체는 바뀌지 않는다.

    Function plus1  = x -> x + 1;
Function times2 = x -> x * 2;
System.out.println(plus1.andThen(times2).apply(5));   // 12: (5 + 1) * 2
System.out.println(plus1.compose(times2).apply(5));   // 11: (5 * 2) + 1

    a.andThen(b)는 "a를 먼저, 그다음 b", a.compose(b)는 "b를 먼저, 그 결과에 a"다. 수학의 함수 합성 (f ∘ g)(x) = f(g(x))가 f.compose(g)에 해당한다. 합성된 함수를 호출하면 호출이 겹겹이 일어난다는 점도 알아 두자. plus1.andThen(times2).apply(5)는 합성 람다의 apply가 plus1.apply를 부르고, 그 결과로 times2.apply를 부른다. 각 단계에서 Integer 박싱과 언박싱이 일어난다.

    Consumer: 부수 효과

    Consumer는 값을 받아 무언가를 하는 함수다. 반환값이 없으니 쓸모가 있으려면 출력, 컬렉션 변경, 필드 갱신 같은 부수 효과(side effect)를 일으켜야 한다. Iterable.forEach가 이것을 받는다. 디폴트 메서드 andThen으로 여러 동작을 순서대로 이을 수 있다.

    List log = new ArrayList<>();
Consumer print = s -> System.out.println("print " + s);
Consumer save  = s -> log.add(s);
print.andThen(save).accept("hello");   // print hello
System.out.println(log);               // [hello]

    부수 효과를 일으키는 함수라는 사실은 나중에 병렬 스트림을 다룰 때(10회) 다시 중요해진다. 여러 스레드가 동시에 save 같은 Consumer를 호출하면, 스레드 안전하지 않은 ArrayList에 동시에 쓰게 된다. 자바 고급 1편에서 본 경쟁 조건이 람다 안에서도 똑같이 일어난다.

    Supplier: 지연된 값

    Supplier는 입력 없이 값을 만들어 낸다. 같은 모양의 람다 () -> buildReport()와 그냥 buildReport()의 차이는 언제 계산되는가다. 메서드 인자로 buildReport()를 쓰면 메서드가 호출되기 전에 무조건 계산된다. 자바는 인자를 먼저 평가하고 메서드를 호출하기 때문이다. Supplier로 넘기면 계산하는 코드만 넘어가고, 실제 계산은 받는 쪽이 get()을 부를 때 일어난다.

    static String buildReport() {
    System.out.println("  (buildReport 실행)");
    return "report#1";
}

static void debug(boolean enabled, Supplier message) {
    if (enabled) {
        System.out.println("DEBUG " + message.get());
    }
}

debug(false, () -> buildReport());   // 아무것도 출력되지 않는다
debug(true,  () -> buildReport());
      (buildReport 실행)
DEBUG report#1

    첫 호출에서는 buildReport가 아예 실행되지 않았다. 이것이 지연 평가(lazy evaluation)의 가장 작은 형태다. JDK에도 이 모양이 여러 곳에 있다. Objects.requireNonNull(T obj, Supplier messageSupplier)는 객체가 null일 때만 메시지를 만들고, Optional.orElseGet(Supplier)는 값이 없을 때만 대체 값을 만든다. 후자는 08회에서 orElse와 비교해 다시 본다. 스트림 파이프라인의 지연 평가(05회)도 같은 생각을 더 크게 확장한 것이다.

    특화 함수형 인터페이스: Predicate, UnaryOperator, BinaryOperator

    기본 네 모양만으로도 대부분의 함수를 표현할 수 있다. 조건 검사는 Function, 같은 타입으로의 변환은 Function, 같은 타입 두 개를 합치는 연산은 BiFunction로 쓰면 된다. 그런데도 자바는 이 세 경우를 위해 별도의 인터페이스를 두었다. 각각 이유가 있다.

    Predicate: Function<T, Boolean>과 무엇이 다른가

    Predicate의 추상 메서드는 boolean test(T t)다. 반환형이 래퍼 Boolean이 아니라 기본형 boolean이라는 점이 첫 번째 차이다. Function은 반환형이 참조 타입이므로 null을 돌려줄 수 있고, 그 결과를 if에 쓰면 언박싱 과정에서 NullPointerException이 난다. Predicate는 이런 상태를 타입 수준에서 없앤다.

    Function isBlankFn = s -> s.isBlank() ? Boolean.TRUE : null;
if (isBlankFn.apply("x")) { /* ... */ }   // 언박싱에서 예외
    Exception in thread "main" java.lang.NullPointerException: Cannot invoke "java.lang.Boolean.booleanValue()" because the return value of "java.util.function.Function.apply(Object)" is null

    메시지가 정확히 무슨 일이 일어났는지 말해 준다. if 조건에 Boolean이 오면 javac는 booleanValue() 호출을 끼워 넣고, 그 수신 객체가 null이었다. 두 번째 차이는 조건 조합 메서드다. Predicate에는 디폴트 메서드 and, or, negate와 정적 메서드 isEqual, 그리고 Java 11에 추가된 정적 메서드 not이 있다. JDK 21 소스에서 and는 (t) -> test(t) && other.test(t), or는 (t) -> test(t) || other.test(t)로 구현되어 있다. 자바의 &&와 ||를 그대로 쓰므로 단락 평가(short-circuit)가 그대로 적용된다. 앞의 조건으로 결과가 정해지면 뒤의 Predicate는 호출되지 않는다.

    Predicate isBlank   = s -> s.isBlank();
Predicate notBlank  = isBlank.negate();
Predicate shortWord = s -> s.length() <= 3;
System.out.println(notBlank.and(shortWord).test("kim"));            // true
System.out.println(notBlank.and(shortWord).test("park"));           // false
System.out.println(Predicate.not(isBlank).or(shortWord).test(" "));  // true

    세 번째 줄을 추적해 보자. " "는 공백뿐이라 isBlank가 true, not(isBlank)가 false다. or이므로 뒤의 shortWord를 평가하고, 길이 1은 3 이하이므로 true가 된다. Predicate.not이 특히 쓸모 있는 곳은 메서드 참조와 함께 쓸 때다. String::isBlank라는 메서드 참조에는 .negate()를 바로 붙일 수 없다. 메서드 참조도 타깃 타입이 있어야 타입이 정해지는 폴리 식이기 때문이다. Predicate.not(String::isBlank)는 인자 자리라는 호출 문맥이 타깃 타입을 주므로 가능하다.

    UnaryOperator와 BinaryOperator: 입력과 출력의 타입이 같을 때

    UnaryOperator는 Function를 상속하고 추상 메서드를 새로 선언하지 않는다. 함수형 인터페이스로서의 추상 메서드는 상속받은 apply다. BinaryOperator도 BiFunction를 상속한다. 새로운 능력이 생기는 것이 아니라 타입 매개변수를 하나로 묶는다. 입력과 출력이 같은 타입이어야 한다는 제약을 이름과 타입으로 표현한 것이다.

    이 제약이 의미를 가지는 곳이 있다. List.replaceAll(UnaryOperator)는 리스트의 각 원소를 같은 자리에서 바꿔 끼운다. 결과가 다른 타입이면 List에 다시 넣을 수 없으니, 매개변수를 Function가 아니라 UnaryOperator로 선언한 것이다. Stream.reduce(T identity, BinaryOperator accumulator)도 마찬가지다. 누적값과 원소를 합친 결과가 다음 단계의 누적값이 되려면 세 타입이 모두 같아야 한다. 07회의 컬렉터와 10회의 병렬 리듀스에서 이 모양이 다시 나온다.

    두 인터페이스는 정적 팩터리도 제공한다. UnaryOperator.identity()는 받은 값을 그대로 돌려준다. BinaryOperator.minBy(Comparator)와 maxBy(Comparator)는 두 값 중 작은(큰) 것을 고르는 연산을 만든다. JDK 21 소스에서 minBy는 (a, b) -> comparator.compare(a, b) <= 0 ? a : b를 돌려준다. 비교 결과가 같으면(0이면) 첫 번째 인자를 고른다는 점이 소스에서 읽힌다.

    BinaryOperator shorter = BinaryOperator.minBy(Comparator.comparingInt(String::length));
System.out.println(shorter.apply("java", "go"));   // go
System.out.println(shorter.apply("ab", "cd"));     // ab: 길이가 같으면 첫 번째

    박싱의 비용은 메서드 호출 몇 번에 그치지 않는다. JIT 컴파일러가 이런 할당을 최적화로 없앨 수 있는 경우도 있지만 그것은 구현과 상황에 달린 일이고 언어가 약속하는 것이 아니다. 기본형 특화 인터페이스는 이 비용을 타입 수준에서 없애는 방법이다.

    박싱된 값을 ==로 비교하는 람다

    박싱은 비용 말고 정확성 문제도 만든다. 두 정수가 같은지 검사하는 BiPredicate를 만들어 보자.

    BiPredicate same = (x, y) -> x == y;
System.out.println(same.test(127, 127));   // true
System.out.println(same.test(128, 128));   // false
BiPredicate eq = (x, y) -> x.equals(y);
System.out.println(eq.test(128, 128));     // true

    람다 본문의 x와 y는 Integer다. 참조 타입끼리의 ==는 값이 아니라 같은 객체인지를 비교한다. 실제로 이 람다의 본문 메서드(위 코드만 컴파일하면 lambda$main$0(Integer, Integer))를 javap로 보면 숫자 비교 명령이 아니라 참조 비교 명령 if_acmpne가 들어 있다. 127은 캐시 범위 안이라 두 번의 Integer.valueOf(127)이 같은 객체를 돌려주므로 true, 128은 기본 설정에서 캐시 밖이라 서로 다른 객체가 만들어지므로 false다. 코드만 보면 숫자를 비교하는 것 같지만, 함수형 인터페이스의 제네릭 타입 인자가 매개변수를 참조 타입으로 바꿔 놓았다. 박싱된 값은 equals로 비교하거나, 처음부터 IntBinaryOperator나 IntPredicate 같은 기본형 특화 인터페이스를 쓰면 이 함정이 사라진다.

    이름 규칙과 43개의 인터페이스

    기본형 특화를 모든 조합에 대해 만들면 인터페이스가 끝없이 늘어난다. java.util.function은 int, long, double 세 기본형에 대해서만 체계적으로 특화를 제공하고, boolean은 BooleanSupplier 하나뿐이며, byte, short, char, float용은 없다. 작은 정수 타입은 int로 넓히는 변환(widening)이 자동으로 일어나므로 int 버전으로 다룰 수 있다. 예를 들어 IntUnaryOperator next = c -> c + 1;에 next.applyAsInt('a')를 호출하면 char가 int로 넓혀져 98이 나온다.

    패키지 문서(package-info.java)는 이름을 붙이는 규칙을 명시한다. 이 규칙을 알면 처음 보는 이름도 모양을 읽어 낼 수 있다.

    • 기본 모양: Function(T → R), Consumer(T → void), Predicate(T → boolean), Supplier(() → T).
    • 인자 개수 접두사: Bi를 붙이면 인자가 둘이다. BiFunction.
    • 파생 모양: UnaryOperator는 Function을, BinaryOperator는 BiFunction을 확장한다.
    • 기본형 접두사: 입력이 기본형이면 Int, Long, Double을 앞에 붙인다. IntFunction은 int를 받아 R을 낸다. 입력은 제네릭이고 반환만 기본형이면 ToXxx를 붙인다. ToIntFunction는 T를 받아 int를 낸다. 두 규칙은 합쳐질 수 있다. IntToDoubleFunction은 int를 받아 double을 낸다.
    • Obj 접두사: 왼쪽에서부터 특화하다가 특화하지 않을 인자를 건너뛸 때 Obj를 쓴다. ObjIntConsumer는 (T, int)를 받는다. 모든 인자에 특화 접두사가 있으면 인자 개수 접두사 Bi는 생략할 수 있다.

    함수형 인터페이스 호출 한 번: itable, 인라인 캐시, 타입 프로파일

    앞에서 Function가 호출마다 박싱을 일으키는 것을 바이트코드로 보았고, JIT 컴파일러가 그 할당을 없앨 수도 있지만 언어가 약속하는 일은 아니라고 했다. 그 "경우에 따라"가 무엇에 달려 있는지 OpenJDK 21 HotSpot 기준으로 한 층 내려가 보자. 출발점은 함수형 인터페이스를 거친 호출이 언제나 invokeinterface라는 사실이다. 함수를 받는 메서드의 바이트코드는 IntUnaryOperator.applyAsInt:(I)I 같은 인터페이스 메서드만 알 뿐이고, 실제로 실행할 코드는 실행 중 수신 객체의 클래스로 정해진다. 그리고 람다 식은 식마다 서로 다른 숨겨진 클래스가 되므로, 같은 호출 지점이 여러 클래스를 만날 수 있다.

    HotSpot은 클래스마다 인터페이스 메서드 표인 itable을 둔다. oops/klassVtable.hpp의 주석이 적은 형식은 다음과 같다. 앞쪽에 "구현한 인터페이스의 Klass 포인터와 그 인터페이스용 메서드 표의 위치" 쌍이 나열되고, 뒤쪽에 인터페이스마다 메서드 표가 이어진다.

    그러나 표를 훑는 비용보다 훨씬 큰 차이를 만드는 것은 인라이닝(inlining)이다. C2 컴파일러는 호출된 메서드의 본문을 호출 지점에 펼쳐 넣어야 그 너머까지 최적화를 이어 갈 수 있다. 인터페이스 호출은 대상이 고정되어 있지 않으므로 C2는 인터프리터와 C1이 모아 둔 타입 프로파일(type profile)을 본다. 호출 지점마다 지금까지 만난 수신 클래스와 횟수를 기록한 것으로, 기록하는 클래스의 수는 -XX:TypeProfileWidth(기본값 2)다. opto/doCall.cpp의 Compile::call_generator는 이 프로파일로 다음처럼 정한다.

    • 수신 클래스가 하나뿐이면 그 클래스의 메서드를 인라인하고, 다른 클래스가 오는 경로는 역최적화 트랩(uncommon trap)으로 둔다.
    • 둘이면(UseBimorphicInlining, 기본 true) 두 클래스를 차례로 검사해 둘 다 인라인한다.
    • 그보다 많으면 한 클래스가 전체 호출의 TypeProfileMajorReceiverPercent(기본 90) 퍼센트 이상일 때만 그 클래스를 인라인하고 나머지 경로는 가상 호출로 남긴다. 그런 클래스도 없으면 가상 호출만 남는다.

    여기서 기억할 점은 HotSpot의 프로파일이 메서드의 바이트코드 위치마다 하나라는 것이다. sum을 부르는 곳이 프로그램 여기저기에 있고 각자 다른 람다를 넘긴다면, 그 람다 클래스들이 모두 sum의 bci 12 한 곳에 섞여 기록된다. 함수형 인터페이스를 받는 범용 메서드는 쓰이는 곳이 많을수록 메가모픽이 되기 쉽다. 반대로 어떤 호출 지점을 지나가는 람다가 하나뿐이라면, 인터페이스를 거친다는 사실은 컴파일된 코드에서 클래스 검사 하나로 줄어들고 본문은 펼쳐진다. 함수형 인터페이스 호출의 성능은 인터페이스 자체가 아니라 그 호출 지점을 몇 종류의 람다가 지나가느냐로 정해진다.

    박싱 객체는 언제 실제로 힙에 생기는가

    이제 박싱 문제로 돌아오자. 인라이닝 여부가 바뀌면 박싱된 Integer의 운명도 바뀐다. 호출당 힙 할당량을 직접 재 보자. com.sun.management.ThreadMXBean.getCurrentThreadAllocatedBytes()(JDK 14부터)는 현재 스레드가 힙에 할당한 총 바이트 수의 근삿값을 돌려주는 JDK의 확장 API다. 호출 전후 값의 차이를 호출 횟수로 나누면 호출 한 번이 힙에 남긴 바이트를 알 수 있다.

    import java.lang.management.ManagementFactory;
import java.util.List;
import java.util.function.Function;
import java.util.function.IntUnaryOperator;

public class BoxCost {
    static final com.sun.management.ThreadMXBean MX =
            (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();

    static long boxed(Function f, int n) {
        long s = 0;
        for (int i = 0; i < n; i++) s += f.apply(1000 + i);   // 캐시 범위(-128~127) 밖의 값
        return s;
    }
    static long prim(IntUnaryOperator f, int n) {
        long s = 0;
        for (int i = 0; i < n; i++) s += f.applyAsInt(1000 + i);
        return s;
    }
    public static void main(String[] args) {
        int kinds = Integer.parseInt(args[0]);   // boxed에 넘길 람다 클래스의 수(1~3)
        List> fs = List.of(x -> x + 1, x -> x + 2, x -> x + 3);
        IntUnaryOperator pf = x -> x + 1;
        int n = 3_000_000;
        long sink = 0;
        for (int round = 1; round <= 5; round++) {
            long a0 = MX.getCurrentThreadAllocatedBytes();
            for (int k = 0; k < 30; k++) sink += boxed(fs.get(k % kinds), n / 30);
            long a1 = MX.getCurrentThreadAllocatedBytes();
            sink += prim(pf, n);
            long a2 = MX.getCurrentThreadAllocatedBytes();
            System.out.printf("round %d: Function %.1f B/call, IntUnaryOperator %.1f B/call%n",
                    round, (a1 - a0) / (double) n, (a2 - a1) / (double) n);
        }
        System.out.println(sink);   // 결과를 써서 루프가 통째로 지워지지 않게 한다
    }
}

    먼저 32바이트의 정체다. 호출 한 번에 Integer가 둘 생긴다. 인자 1000 + i를 넘기며 박싱한 것과, 람다 본문이 x + 1을 돌려주며 박싱한 것이다. 값이 1000 이상이라 Integer.valueOf의 캐시에 걸리지 않는다. 64비트 HotSpot의 기본 설정에서 Integer 하나는 마크 워드 8바이트, 압축된 클래스 포인터 4바이트, int 필드 4바이트를 합친 16바이트다. 압축 클래스 포인터를 끄면 클래스 포인터가 8바이트가 되어 합이 20바이트이고, 기본 객체 정렬(ObjectAlignmentInBytes = 8)에 맞춰 24바이트가 된다. 표의 48은 그 24바이트 객체 두 개다.

    인터프리터에서는 바이트코드에 적힌 박싱이 그대로 실행되므로 32바이트가 꾸준히 나온다. 기본 설정에서 람다가 하나뿐이면 둘째 라운드부터 0바이트가 된다. 앞 절의 실험처럼 C2가 boxed의 루프를 컴파일하면서 프록시의 apply와 람다 본문까지 인라인했고, 그러자 두 Integer가 컴파일된 코드 밖으로 나가지 않는다는 것이 드러났기 때문이다. 이 판정을 하는 것이 C2의 탈출 분석(escape analysis)이고, -XX:-DoEscapeAnalysis로 끄면 같은 모노모픽 호출에서도 32바이트로 돌아온다. 참고로 -XX:-EliminateAllocations와 -XX:-EliminateAutoBox를 각각 또는 함께 꺼도 이 실험에서는 0바이트였다. 탈출 분석 뒤의 어느 세부 단계가 할당을 지웠는지는 이 측정만으로는 가릴 수 없고, 확실한 것은 탈출 분석이 꺼지면 할당이 돌아온다는 데까지다.

    람다가 셋이면 JIT가 켜져 있어도 32바이트다. 앞 절에서 본 대로 이 호출 지점은 가상 호출로 남는다. C2의 탈출 분석(opto/escape.cpp)은 어떤 메서드가 불릴지 모르는 호출에 넘긴 객체를 최악으로 가정해 전역으로 탈출한다(GlobalEscape)고 표시한다. 그래서 인자로 넘기는 Integer는 힙에 만들어져야 하고, 돌려받는 Integer는 따로 컴파일된 람다 쪽 코드가 힙에 만들어 반환한 객체다. 박싱 비용이 사라질지는 결국 호출 지점을 몇 종류의 람다가 지나가느냐에 달려 있고, 이것은 소스 한 줄만 봐서는 알 수 없는 프로그램 전체의 성질이다. 오늘 모노모픽이던 호출 지점이 다른 곳에서 새 람다를 넘기기 시작하면 할당이 소리 없이 돌아온다.

    IntUnaryOperator 열은 측정한 모든 설정에서 0바이트다. 인터프리터에서도, 탈출 분석을 꺼도 그렇다. 기본형 특화 인터페이스의 이득은 JIT 최적화가 성공했을 때만 얻는 것이 아니라, 바이트코드에 박싱이 처음부터 없다는 데서 나온다. 앞에서 "JIT가 할당을 없앨 수 있는 경우도 있지만 언어가 약속하는 것이 아니다"라고 한 말의 구체적인 내용이 이것이다. 박싱을 없애는 일을 JIT의 조건부 최적화에 맡길지, 타입으로 확정할지의 차이다.

    기타 함수형 인터페이스: 인자 둘, 셋, 그리고 검사 예외

    인자가 둘인 함수는 Bi 계열이 맡는다. BiFunction의 R apply(T t, U u), BiConsumer의 void accept(T t, U u), BiPredicate의 boolean test(T t, U u)다. 가장 자주 만나는 곳은 Map이다. Map.forEach(BiConsumer)는 키와 값을 함께 넘기고, Map.replaceAll(BiFunction)는 키와 기존 값으로 새 값을 계산한다. Bi 계열에도 단항 계열과 같은 디폴트 메서드가 있다. BiFunction.andThen, BiPredicate.and, or, negate, BiConsumer.andThen이다. 단, Supplier에는 인자가 없으니 Bi 버전이 없다.

    인자가 셋 이상이면 직접 만든다

    java.util.function에는 인자가 셋 이상인 인터페이스가 없다. 필요하면 직접 정의한다. 앞에서 만든 GenericFunction과 같은 방식이다.

    @FunctionalInterface
interface TriFunction {
    R apply(A a, B b, C c);
}

TriFunction clamp =
        (value, min, max) -> Math.max(min, Math.min(max, value));
System.out.println(clamp.apply(15, 0, 10));   // 10
System.out.println(clamp.apply(-3, 0, 10));   // 0
System.out.println(clamp.apply(7, 0, 10));    // 7

    다만 인자가 셋 이상인 함수를 자주 만들게 된다면 그 인자들이 사실은 하나의 개념을 이루는 것은 아닌지 먼저 따져 볼 만하다. 위의 min과 max는 "범위"라는 하나의 값으로 묶을 수 있다. 레코드로 묶으면 함수는 다시 BiFunction이나 Function의 모양으로 돌아온다.

    검사 예외와 함수형 인터페이스

    람다 본문이 던질 수 있는 검사 예외(checked exception)는 람다 본문의 규칙이 아니라 함수형 인터페이스의 추상 메서드가 선언한 throws 절이 정한다. 람다 본문은 결국 그 메서드의 구현이기 때문이다. Function.apply에는 throws 절이 없다. 그래서 파일을 읽는 람다를 Function에 담으면 컴파일되지 않는다.

    Function read = path -> Files.readString(Path.of(path));   // 컴파일 오류
Callable c = () -> Files.readString(Path.of("a.txt"));             // 통과
    T3.java:6: error: unreported exception IOException; must be caught or declared to be thrown
        Function read = path -> Files.readString(Path.of(path));
                                                                ^

    Callable.call()은 throws Exception을 선언하므로 같은 본문이 통과한다. 스프링 DB 편에서 쓴 JdbcTemplate의 RowMapper도 같은 이유로 편하다. Spring Framework 6.1 Javadoc에서 RowMapper는 @FunctionalInterface이고, 추상 메서드 T mapRow(ResultSet rs, int rowNum)은 throws SQLException을 선언한다. 그래서 (rs, rowNum) -> rs.getString("name") 같은 람다 안에서 SQLException을 던지는 getString을 try 없이 부를 수 있고, 그 예외는 Javadoc 설명대로 호출한 JdbcTemplate이 잡아 처리한다.

    표준 인터페이스를 써야 하는데 본문이 검사 예외를 던진다면, 예외를 던질 수 있는 인터페이스를 따로 정의하고 표준 인터페이스로 바꿔 주는 어댑터를 둘 수 있다.

    @FunctionalInterface
interface ThrowingFunction {
    R apply(T t) throws Exception;
}

static  Function unchecked(ThrowingFunction f) {
    return t -> {
        try {
            return f.apply(t);
        } catch (RuntimeException e) {
            throw e;
        } catch (Exception e) {
            throw new RuntimeException(e);   // 원인을 감싸서 다시 던진다
        }
    };
}

Function read = unchecked(p -> Files.readString(Path.of(p)));
try {
    read.apply("no-such-file.txt");
} catch (RuntimeException e) {
    System.out.println(e.getCause().getClass().getSimpleName() + ": " + e.getCause().getMessage());
}
// NoSuchFileException: no-such-file.txt

    이 어댑터는 검사 예외를 언체크 예외로 바꿀 뿐 예외를 삼키지 않는다. 원인(cause)을 유지하므로 호출한 쪽에서 원래 예외를 꺼낼 수 있다. 다만 검사 예외의 목적은 호출자에게 처리를 강제하는 것이므로, 이렇게 감싸면 그 강제가 사라진다는 점을 알고 써야 한다. 스프링이 SQLException을 언체크 예외인 DataAccessException 계층으로 바꾸는 것도 같은 방향의 선택이었다.

    마지막으로, 함수형 인터페이스는 java.util.function에만 있는 것이 아니다. 패키지 문서도 특정 용도의 함수형 인터페이스는 그것이 쓰이는 패키지에 정의된다고 하며 java.io.FileFilter를 예로 든다. Runnable, Callable, Comparator, 스프링의 RowMapper가 모두 그렇다. 어떤 인터페이스든 추상 메서드가 하나면 람다의 타깃이 될 수 있다.

    상속받은 추상 메서드가 여럿일 때: 함수 타입의 반환형과 throws 절

    함수형 인터페이스의 정의를 다룰 때, 상위 인터페이스 여러 곳에서 오버라이드 동등한 시그니처를 물려받으면 그것들을 메서드 하나로 본다고 했다. 그런데 매개변수가 같다고 반환형과 throws 절까지 같은 것은 아니다. 그렇다면 그런 인터페이스의 함수 타입, 즉 람다 본문이 지켜야 할 계약은 무엇인가. JLS §9.9가 이 경우를 정확히 정한다. 인터페이스 I의 추상 메서드 집합을 M이라 할 때, 함수 타입의 매개변수와 반환형은 M의 모든 시그니처에 대해 하위 시그니처(subsignature)이면서 반환형이 모두와 같거나 모두의 하위 타입인 메서드에서 가져온다. 그런 메서드가 없으면 모두에 대해 반환 타입 대체 가능(return-type-substitutable)한 메서드에서 가져온다.

    throws 절의 규칙은 다르다. 제네릭이 아닌 경우 함수 타입의 throws 절에는 어느 한 throws 절에 적힌 타입 E 중에서, 모든 throws 절 각각에 대해 그 절에 적힌 어떤 타입의 하위 타입인 것만 들어간다. 쉽게 말해 모든 메서드가 함께 허락하는 예외만 남는 교집합이다. JLS는 그 이유를 이렇게 설명한다. 함수 타입은 M의 추상 메서드를 하나하나 오버라이드할 수 있는 메서드 타입이어야 하고, §8.4.6에 따라 오버라이드하는 메서드는 오버라이드되는 어느 메서드보다도 "더 많이" 던질 수 없다. JLS의 예제 9.9-1을 그대로 컴파일해 보자.

    import java.io.*;

public class Merge {
    interface X { void m() throws IOException; }
    interface Y { void m() throws EOFException; }
    interface Z { void m() throws ClassNotFoundException; }
    interface XY extends X, Y { }
    interface XYZ extends X, Y, Z { }

    static void callXY(XY xy) {
        try {
            xy.m();
        } catch (EOFException e) {            // IOException 을 잡지 않아도 된다
            System.out.println("caught " + e);
        }
    }
    static void callXYZ(XYZ xyz) {
        xyz.m();                              // 아무것도 잡지 않아도 된다
    }

    public static void main(String[] args) {
        XY a = () -> { throw new EOFException("eof"); };
        callXY(a);
        XYZ d = () -> System.out.println("no checked exception");
        callXYZ(d);
    }
}
    caught java.io.EOFException: eof
no checked exception

    XY의 함수 타입은 () -> void throws EOFException이다. EOFException은 X의 throws 절(IOException)에도, Y의 throws 절(EOFException)에도 덮이지만, IOException은 Y의 절에 덮이지 않으므로 빠진다. XYZ는 셋 모두가 덮는 예외가 없어 아무것도 던지지 않는 함수 타입이 된다. 같은 파일에 다음 두 줄을 넣으면 javac가 둘 다 거부한다.

    XY b = () -> { throw new FileNotFoundException("f"); };   // IOException 의 하위지만 EOFException 은 아니다
XYZ c = () -> { throw new EOFException("eof"); };        // XYZ 는 검사 예외를 하나도 허락하지 않는다
    Merge2.java:11: error: unreported exception FileNotFoundException; must be caught or declared to be thrown
        XY b = () -> { throw new FileNotFoundException("f"); };
                       ^
Merge2.java:12: error: unreported exception EOFException; must be caught or declared to be thrown
        XYZ c = () -> { throw new EOFException("eof"); };
                        ^

    이 규칙은 람다를 만드는 쪽에만 적용되는 것이 아니다. callXY의 xy.m()은 EOFException만 잡고도 컴파일되었고, callXYZ는 아무것도 잡지 않았다. JLS §15.12.2.5는 가장 구체적인 메서드 후보들이 모두 추상이고 시그니처가 오버라이드 동등할 때 호출이 던지는 예외 타입을 같은 교집합 규칙으로 정하고, 이 규칙이 함수 타입(§9.9)을 정할 때에도 쓰인다고 밝힌다. 람다 본문이 지켜야 할 계약과 호출하는 쪽이 대비해야 할 계약이 같은 계산에서 나오므로, 두 쪽이 어긋나지 않는다.

    반환형도 같은 방식으로 합쳐진다. interface P { Object get(); }와 interface Q { CharSequence get(); }를 함께 상속한 PQ의 함수 타입은 () -> CharSequence다. 그래서 PQ ok = () -> "kim";은 통과하고 ok.get()의 결과를 CharSequence로 받을 수 있지만, PQ bad = () -> 42;는 "bad return type in lambda expression ... int cannot be converted to CharSequence"로 거부된다. 바이트코드에서는 앞에서 본 브리지 이야기와 만난다. P.get의 디스크립터는 ()Object, Q.get은 ()CharSequence로 서로 다르고 PQ는 아무것도 선언하지 않았으니, javac는 altMetafactory에 FLAG_BRIDGES(4)와 추가 디스크립터 ()Ljava/lang/Object;를 넘긴다. JDK 21에서 직접 확인한 부트스트랩 인자가 정확히 그랬다.

    javac에서 이 계산을 하는 곳은 com.sun.tools.javac.code.Types다. JDK 21 소스에서 DescriptorCache.findDescriptorInternal은 인터페이스의 멤버 중 추상 메서드를 모으면서 이름이 다르거나 오버라이드 동등하지 않은 것이 나오면 곧바로 함수형 인터페이스가 아니라고 판정한다. 모인 것이 하나면 그것이 디스크립터이고, 둘 이상이면 mergeDescriptors를 거쳐 mergeAbstracts를 부른다. mergeAbstracts는 다른 모든 메서드의 하위 시그니처이면서 반환형 검사(MostSpecificReturnCheck)를 통과하는 메서드를 고르고, 그동안 chk.intersect로 throws 목록의 교집합을 쌓는다. 교집합이 원래 throws 절과 다르면 그 교집합을 throws로 가진 합성 MethodSymbol을 새로 만든다. 소스의 주석도 결과 메서드의 throws 절이 병합된 메서드들의 throws 절의 교집합이라고 적고 있다.

    한 가지 더 관찰해 둘 것이 있다. javap -v -p Merge로 보면 javac는 람다 본문 메서드 lambda$main$0에 Exceptions 속성 throws java.io.EOFException을 붙여 두었다. 그런데 dumpProxyClassFiles로 덤프한 XY용 프록시의 public void m()에는 Exceptions 속성이 아예 없다. 선언하지 않은 메서드를 통해 EOFException이 그대로 빠져나갔는데도 실행에는 아무 문제가 없었다. 이것이 무엇을 뜻하는지는 다음 절에서 본다.

    예외 타입을 타입 매개변수로: throws E의 추론

    앞에서 만든 unchecked 어댑터는 검사 예외를 언체크 예외로 감싸서 표준 인터페이스에 맞췄다. 다른 방법은 예외 타입 자체를 함수형 인터페이스의 타입 매개변수로 빼서, 람다 본문이 던지는 예외가 함수 타입의 throws 절로, 다시 그 함수를 받는 메서드의 throws 절로 흘러가게 하는 것이다. java.util.function에는 이런 인터페이스가 없으니 직접 만든다.

    import java.io.IOException;
import java.nio.file.Files;
import java.nio.file.Path;

public class Ex {
    @FunctionalInterface
    interface ThrowingSupplier {
        T get() throws E;
    }

    static  T call(ThrowingSupplier s) throws E {
        return s.get();
    }

    static String plain() {                         // throws 절이 없다
        return call(() -> "plain");
    }
    static String io() throws IOException {
        return call(() -> Files.readString(Path.of("no-such-file.txt")));
    }

    public static void main(String[] args) {
        System.out.println(plain());
        try {
            io();
        } catch (IOException e) {
            System.out.println("IOException: " + e.getClass().getSimpleName());
        }
    }
}
    plain
IOException: NoSuchFileException

    같은 call인데 plain()은 아무 예외도 선언하지 않았고, io()는 IOException을 선언해야 했다. io()의 throws IOException을 지우면 "unreported exception IOException"으로 실패한다. 그리고 람다 본문이 SQLException과 IOException을 둘 다 던질 수 있으면 오류 메시지는 "unreported exception Exception"이 된다. 세 경우의 E가 각각 RuntimeException, IOException, Exception으로 추론되었다는 뜻이다. 이 결과는 JLS 18장의 규칙 세 개로 설명된다.

    1. throws 경계를 단다. JLS §18.5.1에 따르면 제네릭 메서드의 타입 매개변수가 그 메서드의 throws 절에 나오면 해당 추론 변수에 throws α라는 경계(bound)가 붙는다. §18.1.3은 이 경계가 순전히 정보용이며, 가능하면 α를 검사 예외가 아닌 타입으로 정하도록 해석 단계를 이끈다고 설명한다.
    2. 람다 본문이 던지는 예외가 하한이 된다. §18.2.5의 검사 예외 제약은 함수 타입의 throws 절에 아직 정해지지 않은 타입 E가 있을 때, 람다 본문이 던질 수 있는 검사 예외 X마다(절의 확정된 타입에 덮이지 않는 것이라면) X <: E라는 제약을 만든다.
    3. 해석 순서. §18.4는 추론 변수에 하한이 있으면 하한들의 최소 상위 타입(lub)으로 정한다. 하한이 없고 throws α 경계가 있으며 확정된 상한이 모두 RuntimeException의 상위 타입이면 RuntimeException으로 정한다. 그 밖에는 상한들의 최대 하위 타입(glb)으로 정한다.

    () -> "plain"은 검사 예외를 던지지 않으므로 하한이 없고, 상한 Exception은 RuntimeException의 상위 타입이므로 둘째 규칙에 따라 E = RuntimeException이다. 그러면 call은 throws RuntimeException인 메서드가 되어 처리할 것이 없다. Files.readString은 IOException을 던지므로 하한이 IOException 하나이고 E = IOException이다. 두 예외를 함께 던지면 lub(IOException, SQLException), 곧 Exception이 되어 정밀도를 잃는다. 타입 매개변수 하나로는 서로 무관한 예외 둘을 따로 전달할 수 없다는 것이 이 방식의 한계다. javac에서는 comp/Infer.java의 InferenceStep.THROWS가 이 둘째 규칙을 구현한다. JDK 21 소스에서 이 단계는 추론 변수가 throws 변수이고 확정된 상한이 모두 RuntimeException의 상위 타입일 때만 적용되며, 해는 언제나 syms.runtimeExceptionType이다. 소스 주석도 throws 절에 나오는 미정 추론 변수를 RuntimeException으로 추론한다고 적는다.

    JVM은 검사 예외를 검사하지 않는다

    앞 절 끝에서 본 관찰로 돌아가자. 프록시의 m()은 아무 예외도 선언하지 않았는데 EOFException이 빠져나갔다. JVMS §4.7.5는 메서드가 던질 예외를 Exceptions 속성에 적는 규칙을 설명한 뒤, 이 요구 사항들은 JVM에서 강제되지 않고 컴파일 시점에만 강제된다고 명시한다. 검사 예외는 javac가 소스에 대해 확인하는 계약일 뿐이고, 바이트코드의 athrow는 어떤 Throwable이든 던진다. 방금 본 추론 규칙과 이 사실을 합치면 javac의 검사를 통째로 피하는 코드가 만들어진다.

    import java.io.IOException;

public class Sneaky {
    @SuppressWarnings("unchecked")
    static  void sneakyThrow(Throwable t) throws E {
        throw (E) t;                          // 소거 후에는 Throwable 로의 캐스트일 뿐이다
    }

    public static void main(String[] args) {  // throws 절이 없다
        sneakyThrow(new IOException("checked, but undeclared"));
    }
}
    Exception in thread "main" java.io.IOException: checked, but undeclared
	at Sneaky.main(Sneaky.java:10)

  static  void sneakyThrow(java.lang.Throwable) throws E;
    Code:
       0: aload_0
       1: athrow

    호출 sneakyThrow(...)에서 E는 어떤 인자와도 관련이 없으니 하한이 없고, 상한 Throwable은 RuntimeException의 상위 타입이다. 그래서 E = RuntimeException으로 추론되고, javac는 main이 처리할 검사 예외가 없다고 판단한다. 메서드 본문의 (E) t는 E의 소거가 Throwable이고 t도 Throwable이라 checkcast조차 남지 않았다. 바이트코드는 aload_0, athrow 두 줄이고, main에는 Exceptions 속성이 없다. 그런데도 JVM은 IOException을 그대로 전파했다.

    이 코드의 대가는 호출하는 쪽에 있다. 같은 호출을 try로 감싸고 catch (IOException e)를 쓰면 javac는 "exception IOException is never thrown in body of corresponding try statement"로 거부한다. JLS §11.2.3은 try 블록이 던질 수 없는 검사 예외 클래스를 잡는 catch 절을 컴파일 오류로 정하는데(Exception과 그 상위 타입은 예외), javac가 보기에 이 try 블록은 IOException을 던질 수 없기 때문이다. 실제로는 던지는 예외를 그 타입으로 잡을 길이 막히는 셈이다. 이 기법이 보여 주는 것은 함수 타입의 throws 절이 검사 예외를 전달하는 유일한 통로라는 사실이다. 앞 절의 교집합 규칙, 이 절의 throws E 추론, 그리고 Function.apply에 throws 절이 없어 파일을 읽는 람다가 거부되던 일까지 모두 javac가 그 통로 하나로 계약을 검사한 결과다. JVM은 그 계약을 모른다.

    정리: 함수형 인터페이스를 고르는 순서와 흔한 오해

    함수 모양이 주어졌을 때 인터페이스를 고르는 과정은 기계적으로 할 수 있다. 먼저 입력의 개수(0, 1, 2)와 출력의 종류(없음, boolean, 값)를 센다. 이것으로 기본 모양(Supplier, Consumer, Predicate, Function, Runnable)과 Bi 여부가 정해진다. 다음으로 입력과 출력의 타입이 같으면 UnaryOperator나 BinaryOperator를 고려한다. 그다음 입력이나 출력에 int, long, double이 있으면 기본형 특화 이름을 붙인다. 이 단계들로 맞는 것이 없거나(인자 셋 이상, 검사 예외), 도메인에서 의미 있는 이름이 필요하면 직접 정의한다.

    함수 모양고를 인터페이스
    (String, int) -> voidObjIntConsumer
    (int) -> StringIntFunction
    (String) -> intToIntFunction
    (long, long) -> longLongBinaryOperator
    () -> booleanBooleanSupplier
    (int) -> doubleIntToDoubleFunction

    이 회차에서 확인한 사실로 흔한 오해 몇 가지를 바로잡아 두자.

    • "@FunctionalInterface가 있어야 람다를 쓸 수 있다." 아니다. 컴파일러는 정의를 만족하는 모든 인터페이스를 함수형으로 다룬다. 애너테이션은 정의를 어기면 오류를 내게 하는 검사 장치다.
    • "디폴트 메서드가 있으면 함수형 인터페이스가 아니다." 아니다. 세는 것은 추상 메서드뿐이다. Function과 Predicate에도 디폴트 메서드가 여럿 있다.
    • "메서드 모양이 같은 인터페이스끼리는 서로 대입된다." 람다 식은 문맥에 맞춰지지만 이미 만들어진 객체는 그렇지 않다. 명목적 타이핑을 따르므로 상속 관계가 없으면 대입되지 않는다.
    • "제네릭은 컴파일이 끝나면 아무 검사도 하지 않는다." 타입 인자 자체는 지워지지만, 호출 지점의 checkcast와 람다 프록시 클래스의 checkcast가 남아 실행 중에도 타입을 확인한다. 로 타입으로 잘못된 값을 넣으면 프록시에서 ClassCastException이 난다.
    • "Function와 IntUnaryOperator는 같은 일을 한다." 결과는 같아도 바이트코드는 다르다. 전자는 호출마다 박싱·언박싱과 캐스트를 거치고, 박싱된 값을 ==로 비교하면 128 이상에서 틀린 결과가 나올 수 있다.

    이 회차의 내용은 이 권의 나머지 회차가 모두 딛고 서는 바닥이다. 03회는 이 인터페이스들을 받는 고차 함수를 직접 만들어 보고, 04회는 람다와 익명 클래스의 차이, 그리고 이 회차에서 잠깐 쓴 메서드 참조를 정식으로 다룬다. 05~07회의 스트림 API는 filter(Predicate), map(Function), forEach(Consumer), reduce(BinaryOperator)와 기본형 특화 스트림으로 가득하고, 09회는 andThen이나 negate 같은 디폴트 메서드가 인터페이스에 들어갈 수 있게 한 규칙을 다룬다.

    이 장의 핵심

    자바에는 함수 타입이 없고, 추상 메서드가 하나인 인터페이스가 그 역할을 대신한다. 람다는 스스로 타입을 갖지 않는 폴리 식이라 대입·호출·캐스트 문맥이 주는 타깃 타입에 맞춰 그 인터페이스의 객체가 된다. 제네릭은 함수 모양의 수를 줄이지만 타입 소거 때문에 JVM 수준에서는 (Object)Object 메서드와 두 개의 checkcast가 되고, 기본형을 다룰 때는 박싱 비용과 == 함정이 따라온다. java.util.function의 43개 인터페이스는 기본 모양 넷에 Bi, 파생, 기본형 접두사를 조합한 것이며, 이름 규칙만 알면 모양을 읽어 낼 수 있다.
    함수형 인터페이스
    sealed가 아니고, Object의 public 메서드를 제외한 추상 메서드가 하나뿐인 인터페이스(JLS §9.8). 디폴트·정적 메서드는 세지 않는다. 람다와 메서드 참조의 유일한 타깃이다.
    @FunctionalInterface
    붙인 인터페이스가 함수형 인터페이스가 아니면 컴파일 오류를 내게 하는 애너테이션. 없어도 람다는 쓸 수 있으며, 나중에 추상 메서드가 추가되어 사용자 코드가 깨지는 것을 막는 장치다.
    제네릭과 타입 소거
    R apply(T)는 디스크립터 (Object)Object로 컴파일된다. 출력 캐스트는 호출 지점의 checkcast가, 입력 캐스트는 dynamicMethodType에 따라 람다 프록시 클래스의 checkcast가 맡는다.
    와일드카드 선언
    함수를 받는 메서드는 Function처럼 입력은 super, 출력은 extends로 연다. 그래야 더 넓은 입력을 받거나 더 좁은 출력을 내는 기존 함수 객체를 넘길 수 있다.
    타깃 타입
    람다는 폴리 식이라 대입·호출·캐스트 문맥이 기대하는 타입으로 타입이 정해진다. 타깃이 없거나(var) 함수형이 아니면(Object) 컴파일 오류다. 와일드카드 타깃은 그라운드 타깃 타입으로 바뀐다.
    오버로딩 선택
    문장 식 본문은 void와 값 양쪽에 호환된다. 명시적 타입 람다(매개변수 없는 람다 포함)는 값을 돌려주는 쪽이 더 구체적이라 선택되고, 암묵적 타입 람다는 모호성 오류가 날 수 있다.
    기본·특화 인터페이스
    Function, Consumer, Supplier, Runnable이 기본 모양이고, Predicate는 기본형 boolean을 돌려주며, UnaryOperator와 BinaryOperator는 입력과 출력 타입을 하나로 묶는다.
    기본형 특화
    int, long, double용 인터페이스는 박싱·언박싱과 캐스트를 없앤다. 박싱된 값을 ==로 비교하면 캐시 범위(-128~127) 밖에서 참조 비교가 되어 틀린다.
    함수 타입의 throws 절
    추상 메서드를 여럿 물려받으면 함수 타입의 throws 절은 모든 throws 절이 함께 덮는 예외만 남긴 교집합이다(JLS §9.9). throws E로 선언하면 E는 람다 본문의 검사 예외로 추론되고, 없으면 RuntimeException이 된다(JLS §18.4). 이 검사는 javac만 하며 JVM은 강제하지 않는다(JVMS §4.7.5).
    직렬화 가능한 람다
    프록시의 writeReplace가 부트스트랩 인자와 캡처 값을 SerializedLambda로 기록하고, 읽을 때는 만든 클래스의 $deserializeLambda$가 합성 메서드 이름 등을 대조해 새 invokedynamic으로 다시 만든다. 그래서 그 클래스의 컴파일 결과에 묶인다.

    실무에서 함수형 인터페이스를 다시 판단하는 첫 장면은 API 설계다. 메서드가 함수를 받도록 만들 때 표준 인터페이스를 쓸지 직접 만들지를 정해야 한다. 표준 인터페이스는 이미 만들어진 함수 객체를 변환 없이 넘길 수 있고 andThen, negate 같은 조합 메서드가 딸려 온다. 직접 만든 인터페이스는 도메인 이름으로 의도를 드러내고, 필요하면 throws 절을 선언할 수 있다. 판단 기준은 그 함수가 "일반적인 변환·조건"인지 "도메인의 정책"인지다. 어느 쪽을 택하든 매개변수 선언에 ? super와 ? extends를 빠뜨리면 사용자가 넘길 수 있는 함수가 불필요하게 좁아진다는 점은 같다.

    두 번째 장면은 성능이다. 대량의 숫자를 다루는 코드에서 Function나 Stream를 쓰고 있다면 호출마다 박싱과 캐스트가 일어나고 캐시 범위 밖의 값은 새 객체가 된다. 프로파일러에서 Integer.valueOf나 Integer 할당이 눈에 띄면 기본형 특화 인터페이스와 기본형 스트림으로 바꾸는 것이 첫 번째 후보다. 반대로 원소 수가 적은 코드에서는 이 차이가 의미 있는 비용이 되지 않을 수 있으니, 측정 없이 모든 코드를 특화 인터페이스로 바꿀 필요는 없다.

    세 번째 장면은 정확성 문제다. BiPredicate에서 ==로 비교하는 코드는 테스트 데이터가 작은 수일 때는 통과하고 운영 데이터에서 틀린다. 리뷰에서 박싱된 타입 인자를 가진 함수형 인터페이스 안의 ==를 보면 의심해야 한다. 같은 맥락에서 Function은 null을 돌려줄 수 있어 조건문에서 NPE가 난다. 조건이라면 Predicate를 쓰는 것이 타입으로 이 경우를 막는 방법이다.

    마지막으로, 람다를 받는 메서드를 오버로딩할 때는 사용자가 어떤 람다를 쓸지 모두 예측할 수 없다. Consumer와 Function을 받는 같은 이름의 메서드는 매개변수 타입 표기 하나에 따라 모호성 오류와 정상 선택이 갈린다. 라이브러리를 만든다면 함수형 인터페이스 매개변수만 다른 오버로딩은 피하고, 이름으로 구분하는 편이 사용자를 덜 놀라게 한다.

BiPredicate same = (x, y) -> x == y;에서 same.test(127, 127)은 true, same.test(128, 128)은 false다(기본 JVM 설정). 이유로 가장 정확한 것은? 람다 본문의 x, y가 Integer라서 ==가 참조 비교(if_acmpne)가 되고, Integer.valueOf는 -128~127만 캐시를 보장하므로 128은 서로 다른 객체가 되기 때문이다. BiPredicate의 test가 128 이상의 값을 언박싱하지 못하기 때문이다. 람다 프록시 클래스가 127을 넘는 값을 Long으로 바꾸기 때문이다. JIT 컴파일러가 128 이상의 비교를 최적화하면서 결과가 달라지기 때문이다. 제네릭 타입 인자 때문에 람다 매개변수가 참조 타입 Integer가 되고, 참조 타입 사이의 ==는 같은 객체인지를 본다. 실제로 본문 메서드의 바이트코드는 if_acmpne다. 인자 127과 128은 호출 지점에서 Integer.valueOf로 박싱되는데, Javadoc은 -128~127을 항상 캐시한다고 약속하므로 127은 같은 객체, 128은 기본 설정에서 각각 새 객체가 된다. equals를 쓰거나 기본형 특화 인터페이스를 쓰면 해결된다. 나머지 보기는 이 동작과 관계없다. interface ThrowingSupplier { T get() throws E; }와 static T call(ThrowingSupplier s) throws E가 있다. throws 절이 없는 메서드 안에서 call(() -> "plain")을 쓰면 어떻게 되는가? E가 상한인 Exception으로 추론되어 "unreported exception Exception" 오류가 난다. 람다 본문이 검사 예외를 던지지 않아 E에 하한이 없고, throws E 경계 때문에 E가 RuntimeException으로 추론되어 그대로 컴파일된다. E를 정할 근거가 없으므로 타입 인자를 명시하라는 오류가 난다. 컴파일은 되지만 실행 중에 JVM이 Exceptions 속성을 검사해 예외를 던진다. JLS §18.5.1에 따라 throws 절에 나오는 타입 매개변수에는 throws α 경계가 붙는다. §18.2.5에서 람다 본문이 던지는 검사 예외가 하한이 되는데 () -> "plain"은 아무것도 던지지 않는다. §18.4의 해석은 하한이 없고 throws α가 있으며 상한(Exception)이 모두 RuntimeException의 상위 타입이면 RuntimeException을 고른다. 그래서 처리할 검사 예외가 없다. 상한으로 정하는 것은 이 규칙이 적용되지 않을 때의 마지막 단계이고, JVMS §4.7.5대로 JVM은 Exceptions 속성을 강제하지 않는다.
    함수형 인터페이스(functional interface)
    sealed가 아니며 Object의 public 메서드를 제외한 추상 메서드가 정확히 하나인 인터페이스. 람다 식과 메서드 참조의 타깃 타입이 된다.
    함수 타입(function type)
    함수형 인터페이스의 추상 메서드를 오버라이드할 수 있는 메서드 타입(매개변수 타입, 반환 타입, throws 절). javac 메시지에서는 함수 디스크립터(functional descriptor)라고도 부른다.
    폴리 식(poly expression)
    식 자체만으로는 타입이 정해지지 않고 문맥이 기대하는 타입에 따라 타입이 정해지는 식. 람다, 메서드 참조, 일부 제네릭 메서드 호출 등이 해당한다.
    타깃 타입(target type)
    대입·호출·캐스트 문맥이 그 자리의 식에 기대하는 타입. 람다는 이 타입의 함수형 인터페이스 객체로 만들어진다.
    그라운드 타깃 타입(ground target type)
    와일드카드가 들어간 함수형 인터페이스 타입에서 람다의 함수 타입을 정하기 위해 와일드카드를 구체 타입으로 바꾼 타입. Function는 Function가 된다.
    타입 소거(type erasure)
    제네릭 타입 정보를 컴파일 후 지우고 타입 변수를 상한 타입으로 바꾸는 자바 제네릭의 구현 방식. 필요한 곳에는 컴파일러가 checkcast를 넣는다.
    박싱(boxing)
    기본형 값을 대응하는 래퍼 객체로 바꾸는 변환. javac는 Integer.valueOf 같은 호출로 컴파일한다.
    throws 경계(throws bound)
    타입 추론에서 throws 절에 나오는 추론 변수에 붙는 정보용 경계(JLS §18.1.3). 하한이 없으면 그 변수를 검사 예외가 아닌 RuntimeException으로 정하게 한다.
    SerializedLambda
    직렬화 가능한 람다 대신 기록되는 객체. 만든 클래스, 인터페이스 메서드, 구현 메서드, 캡처 값을 담고, 읽을 때 readResolve가 만든 클래스의 $deserializeLambda$를 불러 람다를 다시 만든다.
    void 호환·값 호환(void-compatible, value-compatible)
    람다 본문이 void를 돌려주는 함수 타입에 맞는지, 값을 돌려주는 함수 타입에 맞는지를 나타내는 성질. 문장 식 하나로 된 본문은 둘 다에 맞을 수 있다.
