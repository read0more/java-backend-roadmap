    이 회차의 질문: 연산 하나는 무엇을 대가로 치르는가

    지난 회차에서 스트림 파이프라인의 뼈대를 세웠다. 소스에서 출발해 중간 연산을 거쳐 최종 연산으로 끝나고, 중간 연산은 지연(lazy)되어 최종 연산이 호출되기 전까지는 원소가 하나도 흐르지 않는다. 이번 회차는 그 뼈대 위에 올라가는 연산들을 하나씩 열어 본다. 스트림을 만드는 쪽, 원소가 거쳐 가는 쪽, 파이프라인을 끝내는 쪽, 그리고 기본형 전용 스트림이다.

    API 목록 자체는 Javadoc에 다 있다. 이 회차가 관심을 두는 것은 목록이 아니라 각 연산의 비용 모델이다. filter와 sorted는 둘 다 중간 연산이지만, filter는 원소 하나를 받아 넘기거나 버리고 바로 잊는 반면 sorted는 원소를 전부 받아 쌓아 둘 때까지 하나도 내보내지 못한다. limit는 소스 순회를 중간에 끊을 수 있지만 sorted 뒤에 놓이면 그 능력을 쓰지 못한다. Stream로 합계를 내면 원소마다 Integer 객체가 오가지만 IntStream에서는 그런 일이 없다.

    이 차이를 모르고 쓰면 실제로 이런 일을 만난다. 무한 스트림이 끝나지 않는다. 몇 개만 필요했는데 원본 전체를 읽는다. peek에 넣어 둔 로그가 한 줄도 찍히지 않는다. 정수 합계가 음수로 나온다. 모두 각 연산이 내부에서 무엇을 하는지 알면 실행하기 전에 예측할 수 있는 현상이다.

    내부 구현을 이야기할 때는 OpenJDK 21의 java.util.stream 소스를 기준으로 하고, 실행 결과는 Temurin 21.0.13에서 직접 돌린 것이다. Javadoc이 보장하는 동작과 OpenJDK가 그렇게 구현한 동작은 문장마다 구분해 적는다. 구현 세부는 버전이 바뀌면 달라질 수 있지만 명세는 그렇지 않다. 컬렉터는 07회, Optional의 자세한 사용법은 08회, 병렬 스트림은 10회에서 다룬다.

    스트림 생성: 모든 소스는 Spliterator로 바뀐다

    스트림을 만드는 방법은 여러 가지지만 안으로 들어가면 모두 한곳에서 만난다. 가장 많이 쓰는 Collection.stream()은 인터페이스의 디폴트 메서드이고, OpenJDK 21 소스에서 본문은 한 줄이다.

    // java.util.Collection (OpenJDK 21)
default Stream stream() {
    return StreamSupport.stream(spliterator(), false);
}

    spliterator()가 돌려주는 Spliterator(splittable iterator)는 Iterator처럼 원소를 차례로 꺼내는 객체인데, 할 수 있는 일이 세 가지 더 있다. 첫째, tryAdvance(action)로 원소 하나를 처리하거나 forEachRemaining(action)으로 남은 원소를 한꺼번에 처리한다. Iterator의 hasNext()와 next() 두 번 호출이 tryAdvance 한 번으로 합쳐진 셈이다. 둘째, trySplit()으로 자신을 둘로 쪼갤 수 있다. 병렬 스트림이 일을 나누는 바탕이며 10회에서 다룬다. 셋째, characteristics()로 자기 소스의 성질을 비트 플래그로 신고한다.

    StreamSupport.stream(spliterator, false)는 이 Spliterator를 파이프라인의 첫 단계(OpenJDK에서는 ReferencePipeline.Head)에 담아 스트림을 만든다. 두 번째 인자 false는 병렬이 아니라 순차(sequential) 스트림이라는 뜻이다. 이 시점에는 원소를 하나도 읽지 않는다. 소스 단계 객체가 Spliterator를 들고 있을 뿐이다.

    다른 생성 메서드도 결국 Spliterator를 하나 만든다. Stream.of(a, b, c)는 가변 인자 메서드라서 호출하는 쪽에서 배열이 만들어지고, OpenJDK의 본문은 return Arrays.stream(values);다. 인자가 하나인 Stream.of(t)는 원소 하나짜리 빌더 구현(Streams.StreamBuilderImpl)을 Spliterator로 쓴다. Stream.iterate는 Spliterators.AbstractSpliterator를 익명 클래스로 만들어 tryAdvance가 불릴 때마다 다음 값을 계산한다. 생성 방법을 정리하면 다음과 같다.

    Spliterator 특성: 소스가 스스로 신고하는 정보

    Spliterator의 characteristics()는 소스의 성질을 비트로 묶어 돌려준다. Javadoc의 정의를 짧게 옮기면 이렇다. ORDERED는 원소의 만남 순서(encounter order)가 정의되어 있다는 뜻이다. DISTINCT는 어떤 두 원소도 equals로 같지 않다는 뜻이고, SORTED는 만남 순서가 정해진 정렬 순서를 따른다는 뜻이다. SIZED는 순회 전에 estimateSize()가 돌려준 값이 정확한 원소 개수라는 뜻이고, SUBSIZED는 쪼개서 나온 Spliterator도 모두 SIZED라는 뜻이다. NONNULL은 null 원소가 없다는 보장, IMMUTABLE은 순회 중에 원소가 추가·교체·삭제될 수 없다는 보장이다.

    여러 소스의 특성을 직접 찍어 보자. 아래 프로그램의 ch는 특성 비트를 이름으로 바꿔 출력하는 도우미 메서드다.

    static String ch(Spliterator s) {
    int c = s.characteristics();
    List r = new ArrayList<>();
    if ((c & Spliterator.ORDERED) != 0) r.add("ORDERED");
    if ((c & Spliterator.DISTINCT) != 0) r.add("DISTINCT");
    if ((c & Spliterator.SORTED) != 0) r.add("SORTED");
    if ((c & Spliterator.SIZED) != 0) r.add("SIZED");
    if ((c & Spliterator.NONNULL) != 0) r.add("NONNULL");
    if ((c & Spliterator.IMMUTABLE) != 0) r.add("IMMUTABLE");
    if ((c & Spliterator.SUBSIZED) != 0) r.add("SUBSIZED");
    return r + " est=" + s.estimateSize();
}

    한 줄씩 읽어 보자. ArrayList는 인덱스 순서가 있으므로 ORDERED이고 크기를 정확히 안다. HashSet은 중복이 없으니 DISTINCT지만 ORDERED가 없다. 즉 HashSet에서 만든 스트림은 순서 없는(unordered) 스트림이다. TreeSet은 순서, 중복 없음, 정렬, 크기를 모두 신고한다. IntStream.range(0, 5)는 0부터 1씩 증가하는 정수열이므로 정렬되어 있고 중복이 없으며 null이 있을 수 없다는 것까지 신고한다.

    무한 소스 두 개가 흥미롭다. iterate와 generate는 SIZED가 없고 추정 크기로 Long.MAX_VALUE(9223372036854775807)를 낸다. "몇 개인지 모른다"는 신고다. 그리고 generate에는 ORDERED조차 없다. Javadoc도 generate를 "무한한 순차 비순서(sequential unordered) 스트림"을 돌려준다고 적는다. 공급자(Supplier)가 매번 만들어 내는 값에는 "몇 번째 원소"라는 의미가 없다는 판단이다.

    위 출력은 OpenJDK 21에서 각 소스가 실제로 신고한 값이다. Javadoc은 소스마다 어떤 특성을 신고해야 하는지 일부만 정해 두었고(예: generate는 unordered), 나머지는 구현이 정한다. 특정 특성 조합에 의존하는 코드를 쓰지 말고, 동작을 예측하는 도구로만 쓰자.

    이 특성은 단순한 참고 정보가 아니다. 파이프라인은 소스의 특성을 내부 플래그(OpenJDK의 StreamOpFlag)로 옮겨 적고, 중간 연산은 단계마다 이 플래그를 세우거나 지운다. 그리고 몇몇 연산은 이 플래그를 보고 일을 통째로 건너뛴다. 이미 정렬된 소스에 sorted()를 붙이면 아무 일도 하지 않고, 크기를 아는 파이프라인의 count()는 원소를 하나도 읽지 않을 수 있다. 뒤에서 실제로 확인한다.

    소스가 신고한 특성 비트가 파이프라인 단계를 지나며 세워지고 지워지고, 일부 연산이 그 플래그를 보고 일을 건너뛰는 구조. 가로로 긴 구조도. 왼쪽 끝에 "소스 (TreeSet)"라는 상자가 있고 그 아래에 작은 칩 네 개 "ORDERED", "DISTINCT", "SORTED", "SIZED"가 붙어 있다. 오른쪽으로 화살표가 이어지며 단계 상자 세 개가 나란히 있다: "filter", "map", "sorted()". 각 단계 상자 아래에는 그 단계를 지난 뒤 남은 칩들이 표시된다. "filter" 아래에서는 "SIZED" 칩에 빨간 X 표시와 "지움" 라벨. "map" 아래에서는 "SORTED", "DISTINCT" 칩에 X 표시. "sorted()" 아래에서는 "SORTED" 칩이 다시 초록색으로 켜지고 "세움" 라벨. 맨 위에 점선 말풍선으로 "플래그를 보고 일을 건너뛸 수 있다"라고 적고 sorted() 상자를 가리킨다. 흰 배경, 단순한 평면 스타일. 소스가 신고한 특성은 플래그가 되어 단계마다 세워지거나 지워진다. 일부 연산은 이 플래그만 보고 일을 생략한다.

    유한 소스와 무한 소스

    Stream.iterate(seed, f)는 seed, f(seed), f(f(seed))…를 끝없이 만든다. OpenJDK 21의 구현을 보면 무한 스트림이 어떻게 "필요한 만큼만" 값을 만드는지가 그대로 드러난다.

    // java.util.stream.Stream.iterate(T, UnaryOperator) 내부 (OpenJDK 21, 일부)
Spliterator spliterator = new Spliterators.AbstractSpliterator<>(Long.MAX_VALUE,
       Spliterator.ORDERED | Spliterator.IMMUTABLE) {
    T prev;
    boolean started;

    @Override
    public boolean tryAdvance(Consumer action) {
        Objects.requireNonNull(action);
        T t;
        if (started)
            t = f.apply(prev);
        else {
            t = seed;
            started = true;
        }
        action.accept(prev = t);
        return true;
    }
};
return StreamSupport.stream(spliterator, false);

    값은 미리 만들어 두지 않는다. tryAdvance가 호출될 때마다 직전 값 prev에 f를 한 번 적용해 다음 값을 만들고, 그 값을 action(하류의 Sink)에 넘긴다. 상태는 prev와 started 두 필드뿐이다. 그리고 tryAdvance는 언제나 true를 돌려준다. "아직 원소가 남았다"는 뜻이므로 소스 쪽에서는 절대 끝나지 않는다. 이 스트림을 멈추는 것은 하류의 몫이다.

    자바 9에 추가된 세 인자 버전 Stream.iterate(seed, hasNext, next)는 for (T x = seed; hasNext.test(x); x = next.apply(x))와 같은 모양이다. 조건이 거짓이 되는 순간 소스 쪽에서 끝나므로 유한 스트림이 된다. 다만 위 실험에서 보았듯 OpenJDK 21에서는 이 스트림도 SIZED가 아니다. 끝나기는 하지만 몇 개인지는 미리 모른다.

    System.out.println(Stream.iterate(1, x -> x <= 100, x -> x * 3).toList());
    [1, 3, 9, 27, 81]

    Stream.generate(supplier)는 이전 값과 상관없이 공급자를 계속 호출한다. 같은 상수를 반복하거나 난수를 만들 때 쓴다. 앞서 보았듯 순서 없는 스트림이라는 점이 iterate와 다르다. 순차 스트림에서는 실행해 보면 공급자가 만든 순서대로 원소가 흐르지만, 병렬 스트림에서 limit 같은 연산은 순서 없는 소스일 때 훨씬 싸게 동작할 수 있다고 Javadoc이 적고 있다. 이 차이는 10회에서 다시 본다.

    무한 스트림을 끝내려면 파이프라인에 단락(short-circuiting) 연산이 있어야 한다. 패키지 문서는 단락 연산을 이렇게 정의한다. 중간 연산은 무한한 입력을 받아도 유한한 스트림을 만들 수 있으면 단락 연산이고, 최종 연산은 무한한 입력을 받아도 유한한 시간에 끝날 수 있으면 단락 연산이다. 그리고 단락 연산이 있는 것은 무한 스트림 처리가 끝나기 위한 필요조건일 뿐 충분조건은 아니라고 덧붙인다. 예를 들어 Stream.iterate(1, x -> x + 1).filter(x -> x < 0).findFirst()에는 단락 연산 findFirst가 있지만 조건을 만족하는 원소가 영영 오지 않으므로 끝나지 않는다. 무한 스트림 뒤에 sorted()를 붙여도 끝나지 않는다. 정렬은 모든 원소를 받아야 시작할 수 있기 때문이다.

    IntStream.range(a, b)와 rangeClosed(a, b)는 Javadoc이 각각 for (int i = a; i < b; i++)와 for (int i = a; i <= b; i++)에 대응한다고 적어 둔 유한 소스다. 크기를 정확히 알고 정렬·중복 없음까지 신고하므로 뒤에 오는 연산들이 그 정보를 활용할 수 있다.

    닫아야 하는 스트림: Files.lines

    스트림의 최상위 인터페이스 BaseStream은 AutoCloseable을 구현한다. 그렇다고 모든 스트림을 닫아야 하는 것은 아니다. Stream Javadoc은 컬렉션이나 배열에서 만든 스트림은 특별한 자원 관리가 필요 없고, 일반적으로 Files.lines처럼 소스가 I/O 채널인 스트림만 닫아야 한다고 적는다. 닫아야 하는 스트림은 try-with-resources로 연다.

    try (Stream lines = Files.lines(Path.of("app.log"))) {
    long errors = lines.filter(line -> line.contains("ERROR")).count();
    System.out.println(errors);
} // 여기서 lines.close()가 호출되어 파일 핸들이 반납된다

    Files.lines가 돌려준 스트림은 내부에 열린 파일을 들고 있다. 최종 연산이 끝났다고 파일이 저절로 닫히지는 않으므로, 닫지 않으면 파일 디스크립터가 남는다. 뒤에서 볼 flatMap이 안쪽 스트림을 반드시 닫아 주는 이유도 이것이다.

    Stream.concat(a, b)는 두 스트림을 지연 연결한다. 두 스트림의 원소를 새 컬렉션에 복사하지 않는다. OpenJDK 구현은 앞 스트림의 Spliterator를 다 쓰면 뒤 스트림의 Spliterator로 넘어가는 Spliterator를 만든다. Javadoc의 구현 노트는 반복해서 연결하는 것을 조심하라고 경고한다. 깊게 중첩된 연결 스트림의 원소에 접근하면 호출 사슬이 깊어지고 StackOverflowError까지 날 수 있다. 반복문 안에서 result = Stream.concat(result, next)를 수천 번 하는 코드가 그런 예다. 이럴 때는 스트림들을 리스트에 모아 flatMap으로 펼치는 편이 안전하다.

    중간 연산의 공통 구조: 단계마다 Sink 하나

    지난 회차의 내용을 구현 관점에서 짧게 다시 세워 두자. 중간 연산을 호출할 때마다 새 파이프라인 단계 객체가 하나 생기고, 그 객체는 이전 단계를 가리킨다. 최종 연산이 호출되면 맨 마지막 단계부터 거꾸로 올라가며 각 단계의 opWrapSink(flags, downstream)를 호출해 Sink의 사슬을 만든다. Sink는 Consumer를 확장한 내부 인터페이스로 네 가지 메서드를 가진다.

    • begin(long size): 원소를 받기 전에 한 번 호출된다. 크기를 알면 정확한 값을, 모르면 -1을 받는다.
    • accept(T t): 원소 하나를 받는다.
    • end(): 모든 원소를 보낸 뒤 한 번 호출된다.
    • cancellationRequested(): "이제 그만 보내도 된다"를 알린다. 기본값은 false다.

    사슬이 만들어지면 소스 단계가 Spliterator의 원소를 첫 Sink에 밀어 넣는다. OpenJDK 21의 AbstractPipeline.copyInto는 파이프라인에 단락 연산이 있는지에 따라 두 갈래로 나뉜다.

    // java.util.stream.AbstractPipeline (OpenJDK 21)
final  void copyInto(Sink wrappedSink, Spliterator spliterator) {
    Objects.requireNonNull(wrappedSink);

    if (!StreamOpFlag.SHORT_CIRCUIT.isKnown(getStreamAndOpFlags())) {
        wrappedSink.begin(spliterator.getExactSizeIfKnown());
        spliterator.forEachRemaining(wrappedSink);
        wrappedSink.end();
    }
    else {
        copyIntoWithCancel(wrappedSink, spliterator);
    }
}

// ReferencePipeline.forEachWithCancel: copyIntoWithCancel이 begin과 end 사이에서 부른다
do { } while (!(cancelled = sink.cancellationRequested()) && spliterator.tryAdvance(sink));

    단락 연산이 없으면 forEachRemaining으로 원소를 끝까지 한 번에 밀어 넣는다. 확인할 것이 없으니 가장 빠른 길이다. 단락 연산이 있으면 원소 하나를 보내기 전마다 cancellationRequested()를 물어보고, true가 나오면 그 자리에서 순회를 멈춘다. 무한 스트림이 끝날 수 있는 이유는 이 루프 하나에 있다.

      최종 연산 호출
       │  wrapSink: 마지막 단계부터 거꾸로 Sink를 감싼다
       ▼
  소스 Spliterator ──accept──▶ [filter Sink] ──accept──▶ [map Sink] ──accept──▶ [최종 연산 Sink]
        ▲                                                                        │
        └──────────── cancellationRequested()? (단락 연산이 있을 때만 물어본다) ◀──┘

  begin(size) → accept(e1) → accept(e2) → ... → end()   (모든 Sink를 따라 전달된다)

    이 구조 위에서 중간 연산은 세 부류로 나뉜다. Javadoc도 연산마다 이 분류를 적어 둔다.

    • 무상태(stateless) 연산: accept에서 받은 원소를 처리해 바로 downstream.accept로 넘기거나 버린다. 이전 원소를 기억하지 않는다. filter, map, flatMap, peek.
    • 상태 있는(stateful) 연산: 이전 원소에 대한 정보를 들고 있다가 판단에 쓰거나, 원소를 쌓아 두었다가 나중에 내보낸다. distinct, sorted, skip, limit, takeWhile, dropWhile.
    • 단락(short-circuiting) 연산: cancellationRequested()가 true를 돌려줄 수 있다. 중간 연산 중에는 limit와 takeWhile이 "단락이면서 상태 있는" 연산이다.

    각 연산이 플래그를 어떻게 바꾸는지도 OpenJDK 21 소스에서 확인해 정리해 두자. 뒤에서 나올 최적화들이 모두 이 표에서 출발한다.

    연산분류(Javadoc)플래그 변화(OpenJDK 21)이유
    filter무상태SIZED 지움몇 개가 걸러질지 모른다
    map무상태SORTED, DISTINCT 지움변환 결과의 정렬·중복 여부를 모른다
    flatMap무상태SORTED, DISTINCT, SIZED 지움원소 수까지 바뀐다
    peek무상태변화 없음원소를 바꾸지 않는다
    distinct상태 있음DISTINCT 세움, SIZED 지움결과에는 중복이 없다
    sorted()상태 있음ORDERED, SORTED 세움자연 순서로 정렬된다
    sorted(comparator)상태 있음ORDERED 세움, SORTED 지움SORTED 플래그는 자연 순서만 뜻한다
    limit, skip상태 있음(limit는 단락)크기 조정(SIZE_ADJUSTING)크기를 알면 결과 크기도 계산할 수 있다
    takeWhile상태 있음, 단락SIZED 지움어디서 끊길지 모른다

    무상태 중간 연산: filter, map, peek

    filter의 Sink는 OpenJDK 21 소스에서 이렇게 생겼다. 무상태 연산이 얼마나 단순한지 그대로 보인다.

    // ReferencePipeline.filter의 opWrapSink가 만드는 Sink (OpenJDK 21)
return new Sink.ChainedReference(sink) {
    @Override
    public void begin(long size) {
        downstream.begin(-1);          // 몇 개가 통과할지 모르므로 -1
    }

    @Override
    public void accept(P_OUT u) {
        if (predicate.test(u))
            downstream.accept(u);      // 통과하면 바로 다음 Sink로
    }
};

    필드가 하나도 없다. 원소 하나가 들어오면 조건을 검사하고, 통과하면 그 자리에서 다음 Sink의 accept를 호출한다. 이것이 "원소 단위로 세로로 흐른다"는 말의 실체다. 중간 결과를 담는 컬렉션은 만들어지지 않는다. filter 다음 map이 있다면, 원소 하나가 filter의 accept 안에서 map의 accept를 부르고, 그 안에서 다시 최종 연산의 accept를 부르는 중첩 호출이 된다. 실행해서 확인하자.

    List out = Stream.of("a", "bb", "ccc", "dd")
    .filter(s -> { System.out.println("filter " + s); return s.length() >= 2; })
    .map(s -> { System.out.println("map " + s); return s.toUpperCase(); })
    .toList();
System.out.println(out);
    filter a
filter bb
map bb
filter ccc
map ccc
filter dd
map dd
[BB, CCC, DD]

    "a"는 filter에서 탈락했으므로 map까지 가지 않았다. 나머지 원소는 filter 직후에 곧바로 map을 지난다. "filter가 전체를 한 번 돌고, 그 결과를 map이 다시 한 번 돈다"는 가로 처리 모델은 틀렸다. 반복문으로 옮기면 원소마다 if와 변환을 차례로 하는 단일 루프와 같다.

    map은 Function을 받아 원소의 타입을 바꿀 수 있다. Stream에 map(String::length)를 적용하면 Stream가 된다. 이때 length()가 돌려준 int가 Integer로 박싱된다는 점을 기억해 두자. 기본형 특화 스트림에서 다시 다룬다. 플래그 쪽에서는 map이 SORTED와 DISTINCT를 지운다는 점이 중요하다. 정렬된 정수에 x -> -x를 적용하면 순서가 뒤집히고, 서로 다른 문자열에 String::length를 적용하면 중복이 생길 수 있다. 함수가 무엇을 하는지 파이프라인은 알 수 없으므로 보수적으로 지운다. 반면 SIZED는 남긴다. 원소 하나가 정확히 원소 하나로 바뀌므로 개수는 그대로다.

    peek과 count: 로그가 찍히지 않는 이유

    peek(action)은 원소를 바꾸지 않고 지나가는 원소마다 action을 실행한다. Javadoc은 이 메서드가 주로 디버깅을 돕기 위해 존재한다고 적는다. 그런데 peek으로 로그를 찍으려다 아무것도 나오지 않는 일을 겪곤 한다. 다음 네 파이프라인을 보자.

    long c1 = List.of(1, 2, 3).stream().peek(x -> System.out.println("peek1 " + x)).count();
System.out.println("c1=" + c1);
long c2 = List.of(1, 2, 3).stream().peek(x -> System.out.println("peek2 " + x))
        .filter(x -> x > 1).count();
System.out.println("c2=" + c2);
long c3 = List.of(1, 2, 3).stream().peek(x -> System.out.println("peek3 " + x)).skip(1).count();
System.out.println("c3=" + c3);
long c4 = List.of(1, 2, 3).stream().map(x -> { System.out.println("map4 " + x); return x; }).count();
System.out.println("c4=" + c4);
    c1=3
peek2 1
peek2 2
peek2 3
c2=2
c3=2
c4=3

    네 개 중 filter가 들어간 c2만 원소를 실제로 흘려보냈다. 이유는 count()의 구현에 있다. OpenJDK 21의 count()는 ReduceOps.makeRefCounting()을 평가하는데, 이 연산은 먼저 파이프라인 출력 크기를 정확히 알 수 있는지 묻고, 알 수 있으면 원소를 읽지 않고 그 크기를 바로 돌려준다.

    // ReduceOps.makeRefCounting()의 evaluateSequential (OpenJDK 21)
long size = helper.exactOutputSizeIfKnown(spliterator);
if (size != -1)
    return size;
return super.evaluateSequential(helper, spliterator);

    c1: List 소스는 SIZED이고 peek은 플래그를 바꾸지 않으므로 출력 크기는 3이다. 파이프라인은 실행되지 않는다. c4: map도 SIZED를 지우지 않는다. 그래서 map 안의 출력조차 찍히지 않았다. c3: OpenJDK 21에서 skip은 크기 조정(SIZE_ADJUSTING) 플래그를 가진 연산이라서, 순차 스트림일 때 "3개에서 1개를 건너뛰면 2개"를 계산으로 얻는다. c2: filter가 SIZED를 지웠으므로 크기를 알 수 없고, 원소를 하나씩 세는 수밖에 없다.

    이것은 구현의 우연이 아니라 명세가 허용한 동작이다. count()의 Javadoc API 노트는 구현이 스트림 소스에서 개수를 직접 계산할 수 있으면 파이프라인을 실행하지 않을 수 있고, 그 경우 소스 원소를 순회하지 않으며 중간 연산도 평가하지 않는다고 적는다. 그 예시로 든 코드가 바로 peek(System.out::println).count()다. 교훈은 명확하다. 중간 연산에 넘기는 함수에 꼭 실행되어야 하는 부수 효과(side effect)를 넣지 않는다. 그 함수가 몇 번 호출될지, 아예 호출될지는 최종 연산과 플래그에 달려 있다.

    상태 있는 중간 연산 1: distinct

    distinct()는 equals로 같은 원소를 하나만 남긴다. Javadoc은 순서 있는 스트림에서 선택이 안정적(stable)이라고 정한다. 중복된 원소 중에서는 만남 순서상 처음 나온 것이 남는다. 순서 없는 스트림에는 그런 보장이 없다.

    System.out.println(Stream.of("b", "a", "b", "c", "a").distinct().toList());
    [b, a, c]

    OpenJDK 21에서 순차 스트림의 distinct는 플래그에 따라 세 가지 Sink 중 하나를 고른다. 상류가 이미 DISTINCT면 아무 일도 하지 않고 하류 Sink를 그대로 돌려준다. 상류가 SORTED면 같은 값이 연달아 붙어 있을 수밖에 없으므로, 직전에 본 원소 하나(lastSeen)와만 비교한다. 둘 다 아니면 HashSet을 하나 만들어 seen.add(t)가 true일 때만 하류로 넘긴다.

    // DistinctOps의 일반적인 경우 (OpenJDK 21, 일부)
@Override
public void begin(long size) {
    seen = new HashSet<>();
    downstream.begin(-1);
}

@Override
public void accept(T t) {
    if (seen.add(t)) {          // 처음 보는 원소면 add가 true
        downstream.accept(t);
    }
}

    메모리 관점에서 이것은 무엇을 뜻할까. distinct는 원소를 즉시 하류로 넘기므로 세로 흐름을 막지는 않는다. 그러나 지금까지 본 서로 다른 원소를 모두 HashSet에 붙잡아 둔다. 서로 다른 값이 백만 개 지나가면 HashSet 안에 백만 개의 참조가 쌓이고, 그 원소들은 파이프라인이 끝날 때까지 가비지 컬렉션 대상이 되지 않는다. 무한 스트림에 distinct를 붙이면 하류의 limit가 일찍 끊어 주지 않는 한 이 집합은 끝없이 커진다. 판단 기준이 hashCode와 equals라는 점도 중요하다. 두 메서드를 재정의하지 않은 클래스는 객체 동일성으로 비교되므로 내용이 같아도 중복으로 보지 않는다. HashSet을 쓰는 이상 equals와 hashCode의 계약이 그대로 적용된다. 둘 중 하나만 재정의하면 같은 내용의 원소가 중복으로 남을 수 있다.

    상태 있는 중간 연산 2: sorted는 장벽이다

    sorted()는 자연 순서(natural order, Comparable)로, sorted(comparator)는 주어진 비교자로 정렬한다. Javadoc은 순서 있는 스트림에서 정렬이 안정적이라고, 즉 비교 결과가 같은 원소끼리는 원래 순서를 유지한다고 정한다. 정렬이 다른 연산과 근본적으로 다른 점은 마지막 원소를 보기 전에는 첫 번째로 내보낼 원소를 결정할 수 없다는 것이다. 패키지 문서도 상태 있는 연산은 결과를 내기 전에 입력 전체를 처리해야 할 수 있다며, 정렬을 그 예로 든다.

    OpenJDK 21의 정렬 Sink(크기를 모를 때 쓰는 RefSortingSink)는 그 사실을 코드로 옮긴 것이다.

    // SortedOps.RefSortingSink (OpenJDK 21)
@Override
public void begin(long size) {
    if (size >= Nodes.MAX_ARRAY_SIZE)
        throw new IllegalArgumentException(Nodes.BAD_SIZE);
    list = (size >= 0) ? new ArrayList<>((int) size) : new ArrayList<>();
}

@Override
public void end() {
    list.sort(comparator);
    downstream.begin(list.size());
    if (!cancellationRequestedCalled) {
        list.forEach(downstream::accept);
    }
    else {
        for (T t : list) {
            if (downstream.cancellationRequested()) break;
            downstream.accept(t);
        }
    }
    downstream.end();
    list = null;
}

@Override
public void accept(T t) {
    list.add(t);
}

    accept는 원소를 리스트에 넣기만 하고 하류로는 아무것도 보내지 않는다. 하류의 begin조차 아직 호출하지 않는다. 상류가 end()를 호출해야 비로소 정렬하고, 그다음에 하류에게 begin(정렬된 개수), accept 여러 번, end()를 차례로 보낸다. 원소의 흐름이 이 지점에서 한 번 완전히 끊겼다가 다시 시작되는 셈이다. 크기를 아는 경우에는 리스트 대신 정확한 크기의 배열을 쓰는 SizedRefSortingSink가 선택되지만 구조는 같다. 실행으로 확인하자.

    .sorted()
    .peek(x -> System.out.println("after " + x))
    .forEach(x -> System.out.println("forEach " + x));

    sorted 앞의 peek은 세 원소를 연달아 찍었다. 그동안 sorted 뒤로는 아무것도 흐르지 않았다. 세 원소가 모두 들어오고 end()가 호출된 뒤에야 정렬된 원소가 하나씩 내려가는데, 이때부터는 다시 세로 흐름이다. after 1 바로 다음에 forEach 1이 찍힌 것이 그 증거다. 이처럼 원소 흐름을 둘로 나누는 지점을 장벽(barrier)이라고 부른다. 장벽 앞쪽의 모든 원소는 장벽 안의 리스트에 동시에 존재하므로 메모리 사용량은 원소 수에 비례한다.

    sorted 앞에서는 원소가 쌓이기만 하고, end 신호 이후에 정렬된 원소가 다시 하나씩 하류로 흐르는 시간 순서. 세로 생명선 네 개가 있는 시퀀스 다이어그램. 왼쪽부터 "소스", "peek(before)", "sorted", "forEach". 위에서 아래로 시간이 흐른다. 먼저 소스에서 peek(before)로 3, 1, 2 세 개의 화살표가 차례로 가고, 각각 sorted로 이어져 sorted 생명선 옆의 작은 상자 "리스트 [3, 1, 2]"에 쌓인다. 그 구간 옆에 "쌓기만 한다"라는 라벨. 다음으로 소스에서 sorted로 "end()" 화살표가 가고, sorted 옆에 "정렬"이라는 작은 상자. 그 아래에서 sorted에서 forEach로 1, 2, 3 화살표가 하나씩 내려간다. 이 구간 옆에 "다시 원소 단위로 흐른다"라는 라벨. 두 구간 사이를 가로지르는 굵은 점선과 "장벽"이라는 라벨. 흰 배경, 단순한 선. sorted는 end()를 받을 때까지 원소를 쌓기만 한다. 장벽 뒤에서는 다시 원소 하나씩 흐른다.

    자연 순서로 정렬하려면 원소가 Comparable이어야 한다. 이 검사는 컴파일 시점이 아니라 정렬하는 순간에 이루어진다. sorted()의 시그니처가 Stream의 아무 T에나 열려 있기 때문이다. Comparable이 아닌 원소를 넣으면 최종 연산이 실행되는 순간 ClassCastException이 난다.

    Stream.of(new Object(), new Object()).sorted().toList();
    Exception in thread "main" java.lang.ClassCastException: class java.lang.Object cannot be cast to class java.lang.Comparable (java.lang.Object and java.lang.Comparable are in module java.base of loader 'bootstrap')

    이미 정렬된 소스에서는 sorted가 사라진다

    앞서 본 플래그가 여기서 일을 한다. OpenJDK 21의 SortedOps는 Sink를 만들 때 상류 플래그에 SORTED가 있고 이번 정렬도 자연 순서이면 하류 Sink를 그대로 돌려준다. 정렬 단계가 사실상 없어지는 것이다. 단, 소스가 SORTED를 신고해도 그 정렬이 자연 순서가 아니면(Spliterator의 getComparator()가 null이 아니면) 파이프라인은 SORTED 플래그를 옮겨 적지 않는다. 비교 횟수를 출력하는 원소로 확인하자. distinct도 같은 방식으로 DISTINCT 플래그를 보고 건너뛰므로, hashCode 호출도 함께 출력해 본다.

    슬라이스와 단락: limit, skip, takeWhile, dropWhile

    limit(n)은 앞에서부터 최대 n개만, skip(n)은 앞의 n개를 버리고 나머지를 내보낸다. Javadoc의 분류로 limit는 "단락이면서 상태 있는" 연산이고 skip은 상태 있는 연산이다. 상태라고 해 봐야 거창하지 않다. OpenJDK 21의 순차 Sink는 카운터 두 개를 들고 있다.

    // SliceOps.makeRef의 순차 Sink (OpenJDK 21)
return new Sink.ChainedReference<>(sink) {
    long n = skip;               // 아직 버려야 할 개수
    long m = normalizedLimit;    // 아직 내보낼 수 있는 개수

    @Override
    public void begin(long size) {
        downstream.begin(calcSize(size, skip, m));
    }

    @Override
    public void accept(T t) {
        if (n == 0) {
            if (m > 0) {
                m--;
                downstream.accept(t);
            }
        }
        else {
            n--;
        }
    }

    @Override
    public boolean cancellationRequested() {
        return m == 0 || downstream.cancellationRequested();
    }
};

    skip과 limit가 같은 Sink 하나로 구현되어 있다. skip(n)만 쓰면 m이 사실상 무한대가 되고, limit(m)만 쓰면 n이 0이 된다. 핵심은 cancellationRequested()다. 내보낼 수 있는 개수가 0이 되면 true를 돌려주고, 앞에서 본 forEachWithCancel 루프가 이것을 보고 소스 순회를 멈춘다. 무한 스트림 Stream.iterate(1, x -> x + 1).limit(5)가 끝나는 이유가 바로 이 한 줄이다.

    sorted와 limit의 순서는 의미와 비용을 모두 바꾼다

    단락 신호는 Sink 사슬을 따라 상류로 전달되어야 효과가 있다. 그런데 사슬 중간에 신호를 전달하지 않는 Sink가 있으면 어떻게 될까. 앞에서 본 RefSortingSink의 부모 클래스는 cancellationRequested()를 이렇게 구현한다.

    // SortedOps.AbstractRefSortingSink (OpenJDK 21)
@Override
public final boolean cancellationRequested() {
    // If this method is called then an operation within the stream
    // pipeline is short-circuiting (see AbstractPipeline.copyInto).
    // Note that we cannot differentiate between an upstream or
    // downstream operation
    cancellationRequestedCalled = true;
    return false;
}

    정렬 Sink는 언제나 false를 돌려준다. 하류의 limit가 "이제 그만"이라고 해도 정렬 Sink는 상류에 그 말을 전하지 않는다. 당연한 일이다. 가장 작은 두 개를 고르려면 모든 원소를 봐야 하기 때문이다. 대신 "누군가 단락을 원한다"는 사실만 기록해 두었다가, end()에서 정렬된 원소를 내보낼 때 원소마다 하류의 cancellationRequested()를 확인하고 멈춘다. 두 파이프라인을 비교해 보자.

    System.out.println("== sorted then limit");

      .sorted().limit(2).forEach(x -> System.out.println("got " + x));
System.out.println("== limit then sorted");
Stream.of(5, 4, 3, 2, 1).peek(x -> System.out.println("src " + x))

    sorted().limit(2)는 소스 다섯 개를 모두 읽고 가장 작은 두 개 1, 2를 냈다. limit(2).sorted()는 소스를 두 개만 읽고 그 둘을 정렬해 4, 5를 냈다. 비용만 다른 것이 아니라 답 자체가 다르다. 앞의 것은 "전체에서 가장 작은 두 개", 뒤의 것은 "앞의 두 개를 정렬한 것"이다. 원하는 의미에 맞게 순서를 정한 뒤, 그 의미에서 비용을 따져야 한다. 또 하나, OpenJDK 21의 정렬 Sink는 end()에서 리스트 전체를 list.sort로 정렬한다. 하류에 limit(2)가 있다고 해서 "상위 k개만 뽑는" 부분 정렬로 바뀌지는 않는다. 백만 개 중 열 개만 필요하다면 백만 개를 모두 메모리에 올리고 전부 정렬하는 비용을 치른다.

    takeWhile과 dropWhile: 조건으로 자르기

    자바 9에 추가된 takeWhile(p)는 순서 있는 스트림에서 조건 p를 만족하는 가장 긴 접두사(prefix)를 돌려준다. 조건을 처음으로 만족하지 않는 원소를 만나는 순간 끝난다. dropWhile(p)는 반대로 그 접두사를 버리고 나머지를 모두 돌려준다. 이름이 비슷한 filter와 비교하면 차이가 분명하다.

    System.out.println(Stream.of(1, 2, 3, 10, 4, 5).takeWhile(x -> x < 5).toList());
System.out.println(Stream.of(1, 2, 3, 10, 4, 5).dropWhile(x -> x < 5).toList());
System.out.println(Stream.of(1, 2, 3, 10, 4, 5).filter(x -> x < 5).toList());
    [1, 2, 3]
[10, 4, 5]
[1, 2, 3, 4]

    filter는 원소마다 독립적으로 판단하므로 10 뒤의 4도 통과시킨다. takeWhile은 10에서 멈추므로 4까지 가지 않는다. dropWhile은 10부터 끝까지 조건을 다시 보지 않고 모두 통과시킨다. 그래서 takeWhile과 dropWhile은 "지금까지 조건이 계속 참이었는가"라는 상태를 들고 있는 상태 있는 연산이다. takeWhile이 소스를 어디까지 읽는지도 확인하자.

    System.out.println(Stream.of(1, 2, 3, 4, 5, 6)
    .peek(x -> System.out.println("src " + x))
    .takeWhile(x -> x < 3)
    .toList());
    src 1
src 2
src 3
[1, 2]

    조건을 깬 원소 3은 소스에서 꺼내져 검사까지 받은 뒤 버려졌고, 그다음부터는 소스를 읽지 않았다. 정렬된 데이터에서 "어떤 값 이하인 동안만" 처리할 때 takeWhile은 filter보다 훨씬 적게 읽는다. 무한 스트림에서는 filter는 끝나지 않지만 takeWhile은 끝날 수 있다. 주의할 점은 순서 없는 스트림이다. Javadoc은 순서 없는 스트림에서 일부 원소만 조건을 만족하면 takeWhile의 동작이 비결정적이며, 조건을 만족하는 원소의 아무 부분 집합(빈 집합 포함)이나 가져갈 수 있다고 적는다. HashSet에서 만든 스트림에 takeWhile을 쓰면 결과를 예측할 수 없다는 뜻이다.

    flatMap: 원소 하나를 스트림 하나로 펼친다

    map은 원소 하나를 원소 하나로 바꾼다. 그런데 원소 하나가 여러 개의 결과를 낳는 경우가 있다. 주문 목록에서 주문마다 들어 있는 상품 목록을 모두 꺼내고 싶거나, 문장 목록을 단어 목록으로 바꾸고 싶을 때다. map으로 원소를 리스트의 스트림으로 바꾸면 결과는 Stream>처럼 스트림 안에 스트림이 든 모양이 된다. 우리가 원하는 것은 안쪽 스트림의 원소들을 한 줄로 펼친 Stream이다. flatMap이 그 일을 한다.

    // Stream의 메서드
 Stream flatMap(Function> mapper);

    함수의 반환 타입이 R이 아니라 Stream이라는 점이 map과 다르다. 원소 하나를 받아 "0개 이상의 원소를 담은 스트림"을 돌려주면, flatMap이 그 스트림의 원소를 하나씩 하류로 흘려보낸다. 빈 스트림을 돌려주면 그 원소는 아무것도 남기지 않는다. 그래서 flatMap은 1:N 변환이면서 동시에 1:0 변환, 즉 거르기도 할 수 있다.

    System.out.println(Stream.of(List.of(1, 2), List.of(), List.of(3))
        .flatMap(List::stream)
        .toList());
System.out.println(IntStream.range(0, 3)
        .mapToObj(i -> Stream.of(i, i))     // Stream>
        .flatMap(s -> s)                    // Stream
        .toList());
    [1, 2, 3]
[0, 0, 1, 1, 2, 2]

    두 번째 예는 map(여기서는 mapToObj)과 flatMap의 관계를 보여 준다. 먼저 원소마다 스트림을 만들어 스트림의 스트림을 얻고, flatMap(s -> s)로 한 겹을 벗긴다. flatMap(f)는 "map(f)을 한 뒤 한 겹 펼치기"와 같다.

    flatMap의 Sink 안에서 일어나는 일

    OpenJDK 21의 ReferencePipeline.flatMap이 만드는 Sink를 보면 펼치기가 어떻게 이루어지는지, 그리고 몇 가지 중요한 규칙이 어디서 나오는지 한 번에 보인다.

    // ReferencePipeline.flatMap의 opWrapSink (OpenJDK 21)
return new Sink.ChainedReference<>(sink) {
    // true if cancellationRequested() has been called
    boolean cancellationRequestedCalled;

    @Override
    public void begin(long size) {
        downstream.begin(-1);
    }

    @Override
    public void accept(P_OUT u) {
        try (Stream result = mapper.apply(u)) {
            if (result != null) {
                if (!cancellationRequestedCalled) {
                    result.sequential().forEach(downstream);
                }
                else {
                    var s = result.sequential().spliterator();
                    do { } while (!downstream.cancellationRequested() && s.tryAdvance(downstream));
                }
            }
        }
    }

    @Override
    public boolean cancellationRequested() {
        cancellationRequestedCalled = true;
        return downstream.cancellationRequested();
    }
};

    바깥 원소 u 하나가 들어오면 mapper로 안쪽 스트림을 만들고, 그 스트림 자체에 최종 연산 forEach(downstream)를 걸어 원소를 모두 하류 Sink로 밀어 넣는다. 안쪽 스트림 하나가 통째로 실행되는 것이 바깥 원소 하나의 처리다. 이 코드에서 다섯 가지 사실을 읽을 수 있다.

    1. 안쪽 스트림은 닫힌다. try-with-resources 안에서 만들어지므로 내용을 다 흘려보낸 뒤 close()가 호출된다. Javadoc도 각 매핑된 스트림은 그 내용이 이 스트림에 놓인 뒤 닫힌다고 정한다. 그래서 경로마다 Files.lines로 파일을 열어 그 스트림을 돌려주는 매퍼를 쓰더라도 안쪽 파일 핸들은 남지 않는다. 다만 Files.lines는 검사 예외 IOException을 던지므로 람다 안에서 따로 처리해야 하고, 바깥 스트림을 닫아야 하는지는 별개 문제다.
    2. null은 빈 스트림으로 취급된다. result != null 검사가 그것이다. Javadoc도 같은 규칙을 적고 있다. 그래도 일부러 null을 돌려주기보다 Stream.empty()를 돌려주는 편이 읽는 사람에게 의도가 분명하다.
    3. 안쪽 스트림은 순차로 실행된다. result.sequential() 때문이다. 안쪽 스트림을 parallel()로 만들어 돌려줘도 병렬로 돌지 않는다.
    4. 크기를 알 수 없다. begin(-1)을 보내고, 앞의 표에서 보았듯 SIZED·SORTED·DISTINCT 플래그를 모두 지운다.
    5. 단락을 존중한다. 하류에 단락 연산이 있으면 cancellationRequested()가 불리면서 cancellationRequestedCalled가 켜지고, 그때부터는 안쪽 스트림을 forEach 대신 tryAdvance로 한 원소씩 꺼내며 하류가 멈추라고 하는지 확인한다.

    닫힘 순서는 onClose로 직접 볼 수 있다. 안쪽 스트림의 원소가 모두 하류에 전달된 다음, 다음 바깥 원소로 넘어가기 전에 닫힌다.

    Stream.of(1, 2)
    .flatMap(x -> Stream.of(x, x * 10).onClose(() -> System.out.println("closed inner " + x)))
    .forEach(x -> System.out.println("fm " + x));
    fm 1
fm 10
closed inner 1
fm 2
fm 20
closed inner 2
    바깥 원소 하나마다 안쪽 스트림 하나가 만들어지고, 그 원소들이 하류 Sink로 한 줄로 이어 붙으며, 각 안쪽 스트림이 끝나면 닫힌다. 왼쪽에 세로로 쌓인 상자 두 개 "바깥 원소 1", "바깥 원소 2". 각 상자에서 오른쪽으로 화살표가 나가 "mapper" 라벨이 붙은 작은 원을 지나 "안쪽 스트림 [1, 10]", "안쪽 스트림 [2, 20]"이라는 가로 상자로 이어진다. 두 안쪽 스트림 상자에서 나온 화살표들이 오른쪽의 긴 가로 띠 하나로 모인다. 그 띠에는 칸 네 개 "1", "10", "2", "20"이 차례로 있고 위에 "하류 Sink로 한 줄로" 라벨. 각 안쪽 스트림 상자의 오른쪽 끝에 작은 자물쇠 아이콘과 "close()" 라벨. 아래쪽에 작은 점선 상자로 "하류가 멈추라고 하면 tryAdvance로 하나씩"이라는 메모. 흰 배경, 평면 스타일. flatMap은 바깥 원소마다 안쪽 스트림을 하나씩 실행해 하류에 이어 붙이고, 다 쓴 안쪽 스트림을 닫는다.

    flatMap과 무한 스트림: JDK 10에서 고쳐진 문제

    다섯 번째 사실에는 역사가 있다. 자바 8에 처음 들어간 flatMap 구현은 안쪽 스트림을 무조건 forEach로 끝까지 흘려보냈다. 하류에 limit나 findFirst가 있어도 안쪽 스트림 하나는 끝까지 소비해야 다음 판단을 할 수 있었다. 안쪽 스트림이 무한하면 영원히 끝나지 않았다. 이 문제는 OpenJDK 버그 JDK-8075939("Stream.flatMap() causes breaking of short-circuiting of terminal operations")로 보고되었고, 2017년 12월의 수정 커밋이 JDK 10 정식 릴리스에 들어갔다. 위 코드의 cancellationRequestedCalled 분기가 그 수정이다. 같은 커밋이 flatMapToInt 등 기본형 버전에도 같은 방식을 적용했다. 자바 21에서는 다음 코드가 바로 끝난다.

    System.out.println(Stream.of(1, 100)
        .flatMap(x -> Stream.iterate(x, i -> i + 1))   // 안쪽 스트림이 무한하다
        .limit(3)
        .toList());
    [1, 2, 3]

    첫 바깥 원소 1의 안쪽 스트림에서 1, 2, 3을 꺼내자 limit의 카운터가 0이 되고, 안쪽 루프가 downstream.cancellationRequested()에서 멈춘다. 바깥 루프도 같은 신호를 보고 100을 꺼내지 않는다.

    mapMulti: 스트림을 만들지 않는 펼치기

    flatMap은 바깥 원소마다 안쪽 스트림 객체를 하나씩 만든다. 스트림 하나는 파이프라인 단계 객체, Spliterator, 람다가 엮인 작지 않은 구조물이다. 원소 하나가 0~2개 정도의 결과만 낳는 경우라면 이 생성 비용이 처리 비용보다 클 수 있다. 자바 16에 추가된 mapMulti는 스트림 대신 "결과를 받을 Consumer"를 넘겨준다. Javadoc은 원소 하나를 적은 수(0개 포함)의 원소로 바꿀 때 flatMap이 요구하는 새 Stream 인스턴스 생성 비용을 피할 수 있다는 점을 mapMulti를 쓸 상황으로 든다.

    System.out.println(Stream.of("a,b", "c")
        .mapMulti((s, sink) -> {
            for (String part : s.split(",")) sink.accept(part);
        })
        .toList());
    [a, b, c]
