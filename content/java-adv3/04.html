    이 회차의 질문: 람다는 익명 클래스의 줄임말인가

    1회에서 우리는 익명 클래스에서 형식을 하나씩 걷어 내 람다에 도착했다. new Runnable() { public void run() { ... } }에서 인터페이스 이름, 메서드 이름, 반환 타입, 매개변수 타입을 지우면 () -> { ... }가 남는다. 이 과정을 거치고 나면 "람다는 익명 클래스를 짧게 쓰는 문법"이라고 정리하고 싶어진다. 실제로 많은 코드에서 둘을 바꿔 써도 실행 결과가 같다. 하지만 이 정리는 절반만 맞다.

    1회와 2회에서 이미 몇 가지 단서를 보았다. 람다의 본문은 별도 클래스가 아니라 감싼 클래스 안의 private 메서드 lambda$main$0으로 컴파일되었고, 람다를 평가하는 자리에는 new가 아니라 invokedynamic이 놓였다. 2회에서는 LambdaMetafactory가 실행 중에 만든 프록시 클래스를 덤프해 그 안에서 checkcast가 일어나는 것까지 확인했다. 익명 클래스였다면 컴파일러가 Outer$1.class라는 진짜 클래스 파일을 만들고 new로 객체를 만들었을 것이다. 생성 방식이 이렇게 다르다면 동작에도 차이가 있을 것이라고 짐작할 수 있다.

    이 회차의 앞 절반은 그 차이를 하나씩 확인한다. 이름과 this가 무엇을 가리키는지, 컴파일 결과로 무엇이 생기는지, 객체가 바깥 인스턴스를 붙잡는지, 같은 식을 두 번 평가하면 같은 객체가 나오는지를 javac와 javap, 그리고 JDK 21 실행 결과로 본다. 뒤 절반은 메서드 참조(method reference)다. 람다 본문이 메서드 하나를 그대로 호출하기만 할 때는 람다를 쓰는 대신 그 메서드 자체를 가리킬 수 있다. 메서드 참조는 매개변수 목록이 없는데도 컴파일러가 어떤 메서드를 어떤 인자로 호출할지 정확히 알아낸다. 그 규칙을 언어 명세(JLS §15.13)로 정리하고, 람다와 겉보기에 같은 메서드 참조가 실행 시점에 달라지는 경우도 살펴본다.

    이 회차의 모든 실행 결과는 Temurin 21.0.13(OpenJDK 21)에서 얻은 것이다. 클래스 이름 뒤에 붙는 /0x... 같은 16진수 주소는 실행마다 달라질 수 있으므로 그 값 자체에는 의미를 두지 않는다.

    람다 vs 익명 클래스 1: 무엇을 구현할 수 있는가

    먼저 두 문법이 각각 무엇을 만들 수 있는지부터 비교하자. 익명 클래스는 클래스 선언과 객체 생성을 한 식에 합친 것이다. JLS §15.9.5가 정한 대로 익명 클래스 본문은 클래스 본문이므로 필드, 여러 개의 메서드, 인스턴스 초기화 블록을 가질 수 있다. 상위 타입으로는 인터페이스 하나를 구현하거나 클래스 하나를 상속할 수 있고, 그 클래스가 추상 클래스여도 된다. 상속하는 경우 new Base(10) { ... }처럼 상위 클래스 생성자에 인자를 넘길 수도 있다.

    람다는 이 중 대부분을 할 수 없다. 람다의 타깃 타입은 반드시 함수형 인터페이스여야 하고(2회), 람다가 구현하는 것은 그 인터페이스의 추상 메서드 하나뿐이다. 추상 메서드가 하나뿐인 추상 클래스도 람다의 타깃이 될 수 없다. 다음 코드는 컴파일되지 않는다.

    abstract class Task { abstract void run(); }

public class Abs {
    public static void main(String[] args) {
        Task t = () -> System.out.println("x");
    }
}
    Abs.java:5: error: incompatible types: Task is not a functional interface
        Task t = () -> System.out.println("x");
                 ^
1 error

    추상 클래스를 막는 이유는 람다를 평가해서 얻는 객체가 "그 인터페이스를 구현한 어떤 클래스"의 인스턴스이기 때문이다. 추상 클래스에는 생성자와 필드, 초기화 순서가 있고, 하위 클래스는 생성자 안에서 상위 생성자를 호출해야 한다. 람다에는 그런 것을 적을 자리가 없다. 인터페이스는 인스턴스 상태도 생성자도 없으니 "추상 메서드 하나만 채우면 완성되는 타입"이라는 조건을 깔끔하게 만족한다.

    상태를 가질 수 있는가

    더 실무적인 차이는 상태다. 익명 클래스는 필드를 가질 수 있으므로 호출될 때마다 바뀌는 상태를 객체 안에 둘 수 있다. 람다는 자기 필드를 선언할 수 없고, 바깥의 지역 변수를 바꿀 수도 없다(사실상 final 규칙, 1회).

    import java.util.function.IntSupplier;

public class State {
    public static void main(String[] args) {
        IntSupplier anon = new IntSupplier() {
            private int count = 0;                 // 객체가 가진 상태
            public int getAsInt() { return ++count; }
        };
        System.out.println(anon.getAsInt() + " " + anon.getAsInt() + " " + anon.getAsInt());

        int count = 0;
        IntSupplier lambda = () -> ++count;        // 컴파일 오류
    }
}
    State.java:12: error: local variables referenced from a lambda expression must be final or effectively final
        IntSupplier lambda = () -> ++count;        // 컴파일 오류
                                     ^
1 error

    마지막 두 줄을 지우고 실행하면 1 2 3이 출력된다. 문자열 연결의 피연산자는 왼쪽부터 평가되므로 getAsInt()가 차례로 1, 2, 3을 돌려준다. 익명 클래스 객체 하나가 count 필드를 힙에 들고 있고, 메서드가 호출될 때마다 그 필드를 갱신한다. 람다로 같은 일을 하려면 AtomicInteger나 길이 1짜리 배열처럼 바깥에 있는 가변 객체의 참조를 캡처해야 한다. 참조 변수 자체는 다시 대입하지 않으므로 규칙은 통과하지만, 그때 상태는 람다 객체가 아니라 다른 객체에 있다. 람다는 "상태 없는 동작"을 표현하도록 설계된 문법이고, 상태가 동작의 일부라면 익명 클래스나 이름 있는 클래스가 더 정직한 표현이다.

    디폴트 메서드를 다시 정의할 수 있는가

    인터페이스에 디폴트 메서드가 있으면 차이가 하나 더 드러난다. 익명 클래스는 클래스이므로 디폴트 메서드를 재정의할 수 있고, 그 안에서 인터페이스이름.super.메서드()로 원래 구현을 부를 수도 있다. 람다는 추상 메서드 하나만 구현하며 디폴트 메서드는 인터페이스에 적힌 그대로 물려받는다.

    interface Greeter {
    String name();
    default String greet() { return "hello " + name(); }
}

public class Def {
    public static void main(String[] args) {
        Greeter anon = new Greeter() {
            public String name() { return "anon"; }
            public String greet() { return "[" + Greeter.super.greet() + "]"; }
        };
        Greeter lambda = () -> "lambda";
        System.out.println(anon.greet());
        System.out.println(lambda.greet());
    }
}
    [hello anon]
hello lambda

    디폴트 메서드 자체의 규칙(다중 상속 시 어느 구현이 이기는가)은 9회에서 다룬다. 여기서 기억할 것은 "람다는 메서드 하나를 채우는 것 외에는 아무것도 바꿀 수 없다"는 점이다. 이 제약이 오히려 람다를 단순하게 만든다. 람다 객체의 동작은 인터페이스의 디폴트 메서드와 람다 본문, 이 두 가지로 완전히 결정된다.

    람다 vs 익명 클래스 2: this와 이름이 가리키는 것

    두 번째 차이는 눈에 잘 띄지 않지만 버그로 이어지기 쉽다. 같은 메서드 안에 익명 클래스와 람다를 나란히 두고, 둘 다 this와 name이라는 이름을 쓰게 해 보자.

    public class Outer {
    private String name = "outer";

    void run() {
        Runnable anon = new Runnable() {
            private String name = "anon";
            @Override
            public void run() {
                System.out.println("anon this = " + this.getClass().getName());
                System.out.println("anon name = " + this.name);
                System.out.println("anon Outer.this.name = " + Outer.this.name);
            }
        };
        Runnable lambda = () -> {
            System.out.println("lambda this = " + this.getClass().getName());
            System.out.println("lambda name = " + this.name);
        };
        anon.run();
        lambda.run();
        System.out.println("anon class   = " + anon.getClass().getName());
        System.out.println("lambda class = " + lambda.getClass().getName());
    }

    public static void main(String[] args) {
        new Outer().run();
    }
}
    anon this = Outer$1
anon name = anon
anon Outer.this.name = outer
lambda this = Outer
lambda name = outer
anon class   = Outer$1
lambda class = Outer$$Lambda/0x0000008001000c48

    익명 클래스 안의 this는 익명 클래스 자신(Outer$1의 인스턴스)이다. 익명 클래스 본문은 새로운 클래스 선언이므로, 그 안에서 this는 언제나 "지금 실행 중인 메서드의 수신 객체"를 뜻한다. 바깥 Outer 객체에 닿으려면 한정된 this(qualified this)인 Outer.this를 써야 한다. 반면 람다 안의 this는 Outer다. 람다 객체의 실제 클래스는 Outer$$Lambda/0x...인데도, 람다 본문에서 this는 그 객체를 가리키지 않는다.

    이것은 구현의 우연이 아니라 명세가 정한 규칙이다. JLS §15.27.2는 이렇게 적는다. "Unlike code appearing in anonymous class declarations, the meaning of names and the this and super keywords appearing in a lambda body, along with the accessibility of referenced declarations, are the same as in the surrounding context (except that lambda parameters introduce new names)." 즉 람다 본문은 이름에 관해서 투명하다. 람다 매개변수가 새 이름을 들여오는 것을 빼면, 본문의 모든 이름과 this, super는 람다가 놓인 바깥 문맥에서 해석된다. 람다 본문이 바이트코드에서 Outer의 메서드(lambda$run$0)로 컴파일되는 것은 이 규칙을 구현하는 가장 자연스러운 방법이다. 본문이 정말로 Outer의 인스턴스 메서드이니 그 안의 this(지역 변수 0번 슬롯)는 당연히 Outer 객체다.

    같은 Outer.run() 안에 있는 익명 클래스와 람다가 각각 어떤 객체를 this로 보는지, 이름 검색이 어느 범위에서 시작하는지 보여 준다. A clean two-panel structural diagram on a white background, flat style, thin lines, sans-serif font.     이름 검색이 시작되는 곳

    이 규칙은 this를 명시하지 않은 단순 이름에도 똑같이 적용된다. 익명 클래스 본문에서 toString()이나 hashCode()를 그냥 부르면, 먼저 익명 클래스 자신의 멤버(그리고 Object에서 물려받은 멤버)에서 그 이름을 찾는다. 익명 클래스도 Object의 하위 클래스이므로 toString()은 언제나 거기서 찾아지고, 바깥 클래스가 재정의한 toString()은 가려진다. 람다 본문에서 같은 호출은 바깥 클래스의 toString()이 된다. JLS는 이 투명성의 이유로, 바깥 클래스의 이름(this, toString())을 가리고 싶지 않은 경우가 자기 자신을 가리켜야 하는 경우보다 훨씬 흔하다는 점을 든다.

    투명성은 인터페이스의 디폴트 메서드에도 적용된다. 앞의 Greeter를 람다로 구현하면서 본문에서 greet()을 부르면, 컴파일러는 그 이름을 Greeter가 아니라 람다를 감싼 클래스에서 찾는다.

    지역 변수 가리기

    범위가 다르다는 사실은 지역 변수 선언에서도 드러난다. 익명 클래스의 메서드는 새 메서드이므로 바깥 메서드의 지역 변수와 같은 이름의 필드나 지역 변수를 선언해 가릴(shadow) 수 있다. 람다 본문과 람다 매개변수는 바깥 메서드와 같은 블록 범위에 있으므로, 이미 있는 지역 변수 이름을 다시 선언하면 오류가 난다.

    실행 중에 람다 객체가 생기는 과정

    익명 클래스 객체가 만들어지는 과정은 익숙하다. 처음 new Outer$1을 실행할 때 클래스 로더가 디스크에서 Outer$1.class를 읽어 로딩·링킹·초기화를 하고, 그다음부터는 new가 실행될 때마다 힙에 객체를 할당한다. 람다는 클래스 파일이 없는데, 그렇다면 Outer$$Lambda라는 클래스는 언제 어디서 생기는 걸까. 1회에서 이 질문을 이 회차로 미뤄 두었다.

    단서는 LambdaMetafactory의 Javadoc에 있다. Javadoc은 함수 객체(function object)를 다루는 과정을 세 단계로 나눈다. 연결(linkage)은 메타팩토리 메서드가 호출되는 단계로, 구현할 인터페이스와 메서드, 실제 구현을 가리키는 메서드 핸들을 받아 함수 객체를 만들어 낼 수 있는 CallSite를 돌려준다. 포획(capture)은 그 CallSite의 타깃을 호출해 함수 객체를 얻는 단계이고, 하나의 CallSite에 대해 여러 번 일어날 수 있다. 호출(invocation)은 함수 객체의 인터페이스 메서드가 불리는 단계로, 캡처한 인자와 호출 인자를 함께 구현 메서드에 넘긴다. 람다 식을 "평가"하는 것은 포획이고, 람다 "본문이 실행"되는 것은 호출이다. 둘은 서로 다른 순간이다.

    1단계: 연결 — invokedynamic이 처음 실행될 때

    JVMS §6.5의 invokedynamic 설명에 따르면, 이 명령이 실행되면 상수 풀의 동적 호출 지점(dynamically-computed call site)에 대한 심볼릭 참조가 이 특정 invokedynamic 명령에 대해 해석되고, 그 결과로 얻은 java.lang.invoke.CallSite 인스턴스가 이 명령에 "묶인다(bound)". 해석은 부트스트랩 메서드를 호출하는 것으로 이루어진다. 람다의 부트스트랩 메서드는 BootstrapMethods 속성에 적힌 LambdaMetafactory.metafactory이고, 그 시그니처는 다음과 같다.

    public static CallSite metafactory(MethodHandles.Lookup caller,      // JVM이 채운다: 호출한 클래스의 권한
                                   String interfaceMethodName,       // JVM이 채운다: "getAsInt"
                                   MethodType factoryType,           // JVM이 채운다: (II)IntSupplier
                                   MethodType interfaceMethodType,   // 정적 인자 1: ()I
                                   MethodHandle implementation,      // 정적 인자 2: Cap.lambda$lambdaLocal$1
                                   MethodType dynamicMethodType)     // 정적 인자 3: ()I
        throws LambdaConversionException

    앞의 세 인자는 JVM이 invokedynamic의 이름과 서술자에서 채우고, 뒤의 세 인자는 javac가 클래스 파일의 BootstrapMethods 표에 적어 둔 정적 인자다. factoryType의 매개변수 목록 (II)가 앞에서 본 "캡처할 것의 목록"이고, 반환 타입이 만들어 낼 인터페이스다. 2회에서 본 dynamicMethodType은 제네릭이 지운 타입을 런타임에 다시 확인하는 데 쓰인다.

    OpenJDK 21의 구현 클래스 InnerClassLambdaMetafactory는 이 정보로 클래스 하나를 바이트코드로 직접 생성한다(소스의 spinInnerClass). 이름은 타깃클래스$$Lambda이고, Lookup.defineHiddenClass 계열의 경로로 숨겨진 클래스(hidden class)로 정의된다. 정의할 때 넘기는 옵션은 NESTMATE와 STRONG이다. 숨겨진 클래스는 JDK 15의 JEP 371로 도입되었는데, JEP는 숨겨진 클래스가 바이트코드 링크 과정에서도, Class::forName이나 ClassLoader::loadClass로도 발견되지 않는다고 설명한다. 람다 클래스의 이름에 /0x...가 붙어 있고 Class.forName으로 찾을 수 없는 이유가 이것이다. NESTMATE는 생성된 클래스를 람다를 정의한 클래스와 같은 네스트(nest)의 멤버로 만든다. 람다 본문 메서드 lambda$...는 private인데, 생성된 클래스가 같은 네스트에 속하므로 그 private 메서드를 직접 호출할 수 있다. STRONG은 MethodHandles.Lookup.ClassOption의 Javadoc 표현으로 숨겨진 클래스가 정의 클래스 로더와 일반 클래스와 같은 "강한" 관계를 가진다는 뜻이며, 그 클래스 로더에 더 이상 도달할 수 없을 때에만 언로드될 수 있다.

    클래스 로딩 로그로 두 방식의 차이를 직접 볼 수 있다. -Xlog:class+load=info를 주고 Outer를 실행해 관련 줄만 남기면 다음과 같다.

    [0.022s][info][class,load] Outer source: file:/.../lam/
[0.022s][info][class,load] Outer$1 source: file:/.../lam/
[0.024s][info][class,load] Outer$$Lambda/0x0000008001000c48 source: Outer

    Outer$1은 디스크의 클래스 파일에서 왔고, Outer$$Lambda는 출처(source)가 Outer로 표시된다. 파일이 아니라 Outer의 권한(Lookup)으로 메모리에서 정의된 클래스라는 뜻이다. 같은 프로그램에서 getClass()로 얻은 Class 객체를 조사하면 익명 클래스는 isAnonymousClass()가 true, isHidden()이 false이고, 람다 클래스는 isAnonymousClass()가 false, isHidden()과 isSynthetic()이 true였다. 자바 언어의 "익명 클래스"와 람다의 클래스는 리플렉션으로 보아도 다른 종류다.

    2단계: 포획 — 캡처 여부에 따라 달라지는 CallSite

    클래스를 만든 다음 메타팩토리는 CallSite를 돌려준다. OpenJDK 21의 InnerClassLambdaMetafactory.buildCallSite를 읽으면 여기서 분기가 있다. factoryType의 매개변수가 0개, 즉 아무것도 캡처하지 않는 람다라면 생성한 클래스의 인스턴스를 지금 하나 만들어 두고, 언제나 그 인스턴스를 돌려주는 상수 메서드 핸들(MethodHandles.constant)을 타깃으로 하는 ConstantCallSite를 만든다. 소스의 주석도 "non-capturing lambda"의 연결을 최적화하려고 인스턴스 하나를 미리 계산한다고 적고 있다. 캡처하는 람다라면 생성한 클래스의 생성자를 가리키는 메서드 핸들을 타깃으로 하는 ConstantCallSite를 만든다. 이 경우 포획할 때마다 생성자가 호출되어 새 객체가 생긴다.

    성능에 대해서도 이 그림에서 확실히 말할 수 있는 것만 정리하자. 연결 비용(부트스트랩 호출, 클래스 생성과 정의)은 invokedynamic 명령마다 처음 한 번 든다. 익명 클래스도 처음 쓸 때 클래스 파일을 읽고 정의하는 비용이 있으므로, 둘 다 "처음 한 번의 준비 비용 + 그 뒤의 객체 생성"이라는 구조는 같다. 다만 준비하는 주체가 다르다. 익명 클래스는 컴파일 시점에 클래스 파일을 만들어 두고 클래스 로더가 읽는 반면, 람다는 그 결정을 런타임의 메타팩토리에 미룬다. 람다를 어떤 클래스로 만들지가 클래스 파일에 박혀 있지 않으므로, JDK가 바뀌면 생성 전략도 클래스 파일을 다시 컴파일하지 않고 바뀔 수 있다. 실행 시간 수치는 JDK, 하드웨어, JIT 상태에 따라 달라지므로 여기서는 제시하지 않는다.

    HotSpot 안에서 본 연결: CallSite는 어디에 묶이고, 동시에 처음 실행하면 어떻게 되는가

    앞 절에서 "CallSite가 이 invokedynamic 명령에 묶인다"고 했다. JVMS는 무엇이 묶이는지만 정하고, 그것을 어디에 어떻게 저장할지는 구현에 맡긴다. 이 절은 OpenJDK 21 HotSpot의 소스(github.com/openjdk/jdk21u)를 따라가며 그 "묶임"의 실체를 확인한다. 여기 나오는 파일 이름, 함수 이름, 자료구조는 모두 OpenJDK 21 HotSpot 기준이며 다른 버전이나 다른 JVM에서는 다를 수 있다.

    명령마다 따로 있는 해석 결과 칸

    클래스가 링크될 때 HotSpot은 메서드의 바이트코드를 한 번 고쳐 쓴다(rewriter.cpp의 Rewriter::rewrite_invokedynamic). invokedynamic은 명령 바이트 뒤에 4바이트 피연산자를 갖는데, 클래스 파일에서는 앞 2바이트가 상수 풀 인덱스이고 뒤 2바이트는 0이어야 한다. Rewriter는 이 4바이트 전체를 "indy 인덱스"로 덮어쓴다. indy 인덱스가 가리키는 곳은 클래스의 상수 풀 캐시(constant pool cache) 안에 있는 ResolvedIndyEntry 배열의 한 원소다. 소스 주석은 같은 호출을 하는 명령이라도 바이트코드마다 항목이 하나씩 있어서 캐시와 상수 풀의 관계가 다대일이 되며, 그 많은 항목을 가리키려면 2바이트로는 모자라므로 이것이 invokedynamic이 5바이트 형식을 갖는 주된 이유라고 설명한다. 소스에서 람다 식의 위치가 다르면 내용이 같아도 연결이 따로 일어나고 클래스도 따로 생기는 이유가 이 구조에 있다.

    resolvedIndyEntry.hpp에 정의된 항목 하나는 다음 정보를 담는다. 해석이 끝난 뒤 실제로 호출할 어댑터 메서드(_method), 부트스트랩 결과로 얻은 객체("appendix")가 저장될 resolved_references 배열의 위치, 원래의 상수 풀 인덱스, 그리고 appendix가 있는지와 해석이 실패했는지를 나타내는 플래그다. _method가 비어 있으면 아직 해석되지 않은 명령이다.

    첫 실행: 인터프리터에서 부트스트랩까지

    인터프리터가 해석되지 않은 invokedynamic을 만나면 InterpreterRuntime::resolve_invokedynamic을 부른다. 소스 주석은 이 함수를 "First time execution: Resolve symbols, create a permanent CallSite object."라고 소개한다. 이 함수는 LinkResolver::resolve_invokedynamic을 거쳐 SystemDictionary::invoke_bootstrap_method로 부트스트랩 메서드를 실행하고, 결과를 ConstantPoolCache::set_dynamic_call로 그 명령의 항목에 기록한다. 부트스트랩 호출의 자바 쪽 입구는 MethodHandleNatives.linkCallSiteImpl이다. 이 메서드는 부트스트랩이 돌려준 CallSite가 ConstantCallSite이면 그 타깃 메서드 핸들을 appendix로, Invokers.linkToTargetMethod를 어댑터로 돌려준다. 타깃이 바뀔 수 있는 다른 CallSite라면 CallSite 객체 자체를 appendix로, linkToCallSiteMethod를 어댑터로 돌려준다. 람다의 CallSite는 앞에서 본 대로 언제나 ConstantCallSite이므로 첫 번째 길로 간다.

    이 과정은 -Xlog:methodhandles+indy=debug로 볼 수 있다. 캡처하는 람다를 두 번 평가하는 프로그램이다.

HotSpot 내부 로그에서는 숨겨진 클래스 이름의 /가 +로 표시된다. 셋째, 문자열 연결 "after second " + ...도 invokedynamic(JDK 9의 JEP 280, 부트스트랩 StringConcatFactory.makeConcatWithConstants)이라 별도의 항목 indy#1로, 그 명령이 처음 실행될 때 따로 해석되었다.

    여러 스레드가 같은 람다를 동시에 처음 평가하면

    연결이 "처음 한 번"이라는 말에는 단서가 있다. JVMS §5.4.3.6은 여러 스레드가 같은 심볼릭 참조를 동시에 해석하려 하면 부트스트랩 메서드가 동시에 여러 번 호출될 수 있다고 정한다. 그때 JVM은 그중 한 호출의 결과를 골라 모든 스레드에 보이게 설치하고, 나머지 호출은 끝까지 실행되게 두되 결과는 무시한다. 같은 절은 그래서 전역 데이터를 건드리는 부트스트랩 메서드는 경쟁 조건에 대비해야 한다고 덧붙인다.

    HotSpot에서 "하나를 골라 설치"하는 곳이 set_dynamic_call이다. 이 함수는 클래스의 resolved_references 배열에 대해 ObjectLocker로 잠금을 잡은 뒤, 그 항목의 _method가 이미 채워져 있으면 자기가 얻은 결과를 버리고 먼저 설치된 appendix를 돌려준다. 비어 있을 때만 자기 결과를 기록한다. LinkResolver::resolve_invokedynamic의 주석도 부트스트랩이 돌려준 연결 결과는 이 직렬화된 확인을 통과하기 전까지 "잠정적(provisional)"이라고 적고 있다. 실제로 경쟁을 만들어 보자.

    import java.util.Set;
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.CountDownLatch;

public class Race {
    static Runnable make() { return () -> {}; }      // 캡처 없는 람다 하나

    static final Set
