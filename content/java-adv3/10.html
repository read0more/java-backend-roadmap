    이 회차의 질문: 코어는 여덟 개인데 왜 하나만 일하는가

    5회부터 8회까지 스트림 파이프라인의 지연 평가, 컬렉터, Optional을 다졌고 9회에서 디폴트 메서드를 보았다. 지금까지 다룬 스트림은 모두 순차 스트림(sequential stream)이었다. 최종 연산을 호출한 스레드 하나가 소스에서 원소를 하나씩 꺼내 Sink 사슬로 끝까지 밀어 넣는다. 컴퓨터에 코어가 여덟 개 있어도 그 파이프라인을 실행하는 동안 일하는 코어는 하나다. 이 회차는 같은 파이프라인을 여러 코어에 나누어 실행하는 병렬 스트림(parallel stream)을 다룬다.

    병렬 스트림은 겉으로는 parallel() 한 줄이다. 하지만 그 한 줄 아래에는 자바 7에 들어온 포크/조인 프레임워크(Fork/Join framework)가 있고, 그 아래에는 작업자마다 하나씩 붙은 덱과 작업 훔치기(work stealing) 알고리즘, 그리고 JVM 전체가 공유하는 공용 풀(common pool)이 있다. 병렬 스트림의 함정은 거의 모두 이 아래층에서 나온다. 그래서 이 회차는 병렬 스트림에서 출발하지 않는다. 같은 계산을 단일 스레드, 스레드 직접 사용, 스레드 풀, 포크/조인 순서로 직접 병렬화해 보면서 단계마다 무엇이 불편해지는지 확인한다. 그다음 작업 훔치기와 공용 풀을 OpenJDK 21 소스로 내려가 보고, 마지막으로 병렬 스트림의 내부와 주의점을 정리한다. 순수 함수와 불변성이 왜 병렬 실행의 전제가 되는지는 11회에서 함수형 프로그래밍의 관점으로 다시 묶는다.

    실습 환경을 먼저 밝혀 둔다. 이 회차의 예제는 모두 Temurin 21.0.13, 논리 프로세서 8개인 macOS에서 실행했다. 실행 시간, 작업자 스레드 번호, 여러 스레드가 섞어 찍는 출력의 순서는 실행할 때마다 다르다. 본문에 적은 시간은 한 번 실행한 예이고, 따져야 할 것은 숫자 자체가 아니라 "100ms짜리 작업 몇 개가 몇 줄로 겹쳐 실행되었는가"라는 구조다.

    무거운 작업은 Thread.sleep(100)으로 흉내 낸다. 실행 시간을 머릿속으로 예측하기 쉽기 때문이다. 다만 sleep은 CPU를 쓰지 않고 기다리기만 하는 작업이라는 점을 기억해 두자. CPU를 계속 쓰는 계산이라면 코어 수가 속도의 상한이 되지만, 기다리는 작업은 스레드 수가 상한이 된다. 이 차이가 뒤의 "주의점"에서 결정적인 역할을 한다.

    public class Work {
    static int heavyTask(int i) {
        log("calculate " + i + " -> " + i * 10);
        sleep(100);                       // 100ms 걸리는 작업을 흉내 낸다
        return i * 10;
    }

    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); }
    }

    static void log(String msg) {
        System.out.println("[" + Thread.currentThread().getName() + "] " + msg);
    }
}

    단일 스트림: 기준선을 잰다

    1부터 8까지의 수 각각에 heavyTask를 적용하고 결과를 더하는 계산을 기준선으로 삼는다. 결과는 10+20+…+80 = 360이다.

    import java.util.stream.IntStream;

public class SingleStreamMain {
    public static void main(String[] args) {
        long start = System.currentTimeMillis();
        int sum = IntStream.rangeClosed(1, 8)
                .map(Work::heavyTask)
                .sum();
        long time = System.currentTimeMillis() - start;
        Work.log("sum=" + sum + ", time=" + time + "ms");
    }
}

    모든 줄이 [main]이다. 5회에서 본 대로 순차 스트림의 최종 연산은 AbstractPipeline.evaluate에서 evaluateSequential로 가고, 호출한 스레드가 직접 Spliterator.forEachRemaining을 돌며 원소를 map Sink, sum Sink로 밀어 넣는다. 다른 스레드가 끼어들 자리가 없다. 시간은 100ms 작업 여덟 번에 스트림 관련 클래스 로딩, 메서드 참조의 첫 연결(4회에서 본 invokedynamic 부트스트랩) 같은 첫 실행 비용이 더해진 값이다.

    이 계산의 구조를 보자. 여덟 번의 heavyTask는 서로의 결과를 쓰지 않는다. 3의 계산이 2의 결과를 기다릴 이유가 없다. 서로 독립인 작업이 차례로 줄 서 있으니 두 줄로 나누면 절반, 여덟 줄로 나누면 8분의 1의 시간에 끝날 수 있다. 마지막 덧셈만 모든 결과를 모아야 하지만, 덧셈은 순서를 바꾸어 묶어도 결과가 같으므로 각 줄이 부분합을 내고 마지막에 부분합끼리 더하면 된다. 이 "독립적인 부분 작업"과 "순서를 바꿔 묶어도 되는 결합"이 병렬화의 두 전제다. 이제 이 계산을 직접 나누어 보자.

    스레드 직접 사용: 나누기, 넘기기, 기다리기를 모두 손으로

    가장 원시적인 방법은 스레드를 두 개 만들어 앞 절반과 뒤 절반을 맡기는 것이다. 각 스레드가 계산한 부분합은 작업 객체의 필드에 담고, main은 두 스레드가 끝나기를 기다렸다가 필드를 읽어 더한다.

    public class ThreadMain {
    static class SumTask implements Runnable {
        private final int start, end;
        int result;                       // 작업 스레드가 쓰고, main이 join 뒤에 읽는다
        SumTask(int start, int end) { this.start = start; this.end = end; }
        @Override public void run() {
            int sum = 0;
            for (int i = start; i <= end; i++) sum += Work.heavyTask(i);
            result = sum;
            Work.log("작업 완료 result=" + result);
        }
    }

    public static void main(String[] args) throws InterruptedException {
        long start = System.currentTimeMillis();
        SumTask task1 = new SumTask(1, 4);
        SumTask task2 = new SumTask(5, 8);
        Thread t1 = new Thread(task1, "thread-1");
        Thread t2 = new Thread(task2, "thread-2");
        t1.start();
        t2.start();
        t1.join();
        t2.join();
        int sum = task1.result + task2.result;
        long time = System.currentTimeMillis() - start;
        Work.log("sum=" + sum + ", time=" + time + "ms");
    }
}

    시간이 절반 정도로 줄었다. 실행을 따라가 보자. main은 힙에 SumTask 두 개와 Thread 객체 두 개를 만든다. start()를 부르는 순간 HotSpot은 운영체제 스레드를 하나씩 만들어 붙이고(자바 고급 1편에서 본 대로 플랫폼 스레드는 OS 스레드와 1:1이다), 각 OS 스레드는 자기 스택에서 run()을 실행한다. main은 t1.join()에서 WAITING 상태로 들어가 thread-1이 끝나기를 기다리고, 이어서 t2.join()에서 다시 기다린다. 두 스레드는 운영체제 스케줄러가 서로 다른 코어에 올려 동시에 실행하므로, 100ms짜리 작업 네 개짜리 줄 두 개가 겹쳐 약 400ms에 끝난다.

    main이 task1.result를 읽는 것이 안전한 이유도 짚고 가자. result는 volatile도 아니고 락으로 보호되지도 않는다. 그런데도 main이 0이 아닌 값을 확실히 보는 것은 자바 메모리 모델 덕분이다. JLS §17.4.4는 스레드 T1의 마지막 동작이, T1이 종료했음을 감지한 다른 스레드의 동작과 synchronizes-with 관계라고 정하고, 그 감지 수단으로 T1.join()을 든다. 따라서 join()이 반환된 뒤의 읽기는 작업 스레드의 쓰기를 반드시 본다. join()을 빼고 적당히 sleep으로 기다렸다면 이 보장은 사라진다.

    이 방법의 문제를 정리하면 다음과 같다.

    • 분할을 사람이 정했다. 1~4, 5~8로 두 줄을 고정했다. 코어가 여덟 개여도 두 개만 쓴다. 코어 수에 맞추려면 분할 코드를 다시 써야 한다.
    • 결과와 예외를 넘기는 통로가 없다. 결과는 필드라는 임시 통로로 넘겼다. run()에서 예외가 나면 그 스레드는 기본 예외 처리기가 스택 트레이스를 찍고 종료할 뿐이고, main은 result가 0인 채로 아무 일 없다는 듯 합계를 낸다.
    • 스레드를 매번 만들고 버린다. 스레드 생성은 OS 스레드와 스택 메모리를 준비하는 일이어서 작업이 작고 많을수록 생성 비용이 이득을 갉아먹는다.
    • 일의 양이 고르지 않으면 한쪽이 논다. 이 예제는 모든 작업이 100ms라 두 줄이 동시에 끝났다. 작업 시간이 i에 비례한다면 5~8을 맡은 스레드가 훨씬 늦게 끝나고, 먼저 끝난 스레드는 도와줄 방법이 없다.

    스레드 풀 사용: 스레드는 재사용하지만 나누는 일은 여전히 사람 몫

    자바 고급 1편에서 다룬 ExecutorService를 쓰면 앞의 두 문제가 풀린다. 스레드를 미리 만들어 재사용하고, 결과와 예외는 Future가 실어 나른다.

    import java.util.concurrent.*;

public class PoolMain {
    static class SumTask implements Callable {
        private final int start, end;
        SumTask(int start, int end) { this.start = start; this.end = end; }
        @Override public Integer call() {
            int sum = 0;
            for (int i = start; i <= end; i++) sum += Work.heavyTask(i);
            Work.log("작업 완료 result=" + sum);
            return sum;
        }
    }

    public static void main(String[] args) throws Exception {
        ExecutorService es = Executors.newFixedThreadPool(2);
        long start = System.currentTimeMillis();
        Future f1 = es.submit(new SumTask(1, 4));
        Future f2 = es.submit(new SumTask(5, 8));
        int sum = f1.get() + f2.get();
        long time = System.currentTimeMillis() - start;
        Work.log("sum=" + sum + ", time=" + time + "ms");
        es.close();
    }
}

[pool-1-thread-1] calculate 4 -> 40

    Executors.newFixedThreadPool(2)는 작업자 스레드 두 개가 공유하는 무제한 큐 하나를 가진 ThreadPoolExecutor를 만든다. submit은 작업을 그 큐에 넣고, 놀고 있는 작업자가 큐에서 꺼내 실행한다. call()의 반환값이나 예외는 Future 안에 저장되고, get()은 그것을 꺼내 준다. 예외는 ExecutionException으로 감싸져 main에 전달되므로 조용히 0이 더해지는 일이 없다. 메모리 가시성도 java.util.concurrent 패키지 문서가 보장한다. Future가 나타내는 비동기 계산의 동작은 다른 스레드에서 Future.get()으로 결과를 얻은 뒤의 동작보다 happens-before다. 마지막 줄의 close()는 자바 19에서 ExecutorService에 추가된 메서드로, shutdown() 후 모든 작업이 끝날 때까지 기다린다.

    그러나 분할은 여전히 사람이 한다. 그리고 분할을 자동으로, 즉 재귀적으로 하려는 순간 더 근본적인 문제가 드러난다. "구간이 크면 둘로 나누어 각각을 풀에 제출하고, 두 결과를 기다려 더한다"를 그대로 코드로 옮겨 보자.

    import java.util.concurrent.*;

public class PoolRecursionMain {
    static final ExecutorService es = Executors.newFixedThreadPool(2);

    static int sum(int start, int end) throws Exception {
        if (end - start + 1 <= 2) {
            int s = 0;
            for (int i = start; i <= end; i++) s += Work.heavyTask(i);
            return s;
        }
        int mid = start + (end - start) / 2;
        Work.log("[분할] " + start + "~" + end);
        Future left = es.submit(() -> sum(start, mid));
        Future right = es.submit(() -> sum(mid + 1, end));
        return left.get() + right.get();        // 풀 스레드가 풀의 다른 작업을 기다린다
    }

    public static void main(String[] args) throws Exception {
        Future root = es.submit(() -> sum(1, 8));
        try {
            Work.log("sum=" + root.get(2, TimeUnit.SECONDS));
        } catch (TimeoutException e) {
            Work.log("2초 안에 끝나지 않음: " + e);
        }
        es.shutdownNow();
    }
}
    [pool-1-thread-1] [분할] 1~8
[pool-1-thread-2] [분할] 1~4
[main] 2초 안에 끝나지 않음: java.util.concurrent.TimeoutException

    100ms 작업 여덟 개짜리 계산이 2초 안에 끝나지 않는다. 정확히는 영원히 끝나지 않는다. 추적해 보자. thread-1이 루트 작업(1~8)을 꺼내 1~4와 5~8을 큐에 넣고 left.get()에서 멈춘다. thread-2가 큐 앞의 1~4를 꺼내 1~2와 3~4를 큐에 넣고 역시 get()에서 멈춘다. 이제 큐에는 [5~8, 1~2, 3~4]가 남아 있는데, 그것을 실행할 스레드가 하나도 없다. 두 스레드 모두 큐 안의 작업이 끝나기를 기다리고, 큐 안의 작업은 스레드가 비기를 기다린다. 이것이 스레드 기아 교착(thread starvation deadlock)이다.

    thread-1 : sum(1~8) 실행 중 ── left.get() 대기 ──▶ 1~4 의 완료를 기다림
thread-2 : sum(1~4) 실행 중 ── left.get() 대기 ──▶ 1~2 의 완료를 기다림

공유 큐   : [ 5~8 ][ 1~2 ][ 3~4 ]   ← 꺼내 줄 스레드가 없다

기다리는 쪽이 스레드를 쥔 채 놓지 않으므로, 기다림의 대상이 영원히 실행되지 않는다.

    스레드를 늘리면 해결될까? 이 예제라면 기다리는 내부 노드(1~8, 1~4, 5~8)만큼 스레드가 더 있으면 끝난다. 하지만 데이터가 커지면 기다리는 내부 노드도 늘어나고, 그만큼 스레드를 만들면 대부분은 아무 일 없이 기다리기만 하는 스레드가 된다. 스레드마다 스택 메모리와 OS 자원이 들고 문맥 전환 비용이 붙는다. 근본 원인은 "기다리는 스레드가 아무것도 하지 않는다"는 데 있다. 기다리는 동안 자기가 기다리는 바로 그 작업을, 혹은 그 작업을 앞당길 다른 작업을 직접 실행할 수 있다면 교착은 사라진다. 이 생각을 구현한 것이 포크/조인 프레임워크다.

    Fork/Join 패턴: 분할, 정복, 결합

    포크/조인 프레임워크를 보기 전에 그 프레임워크가 전제하는 계산의 모양부터 정리하자. 분할 정복(divide and conquer)은 세 단계로 이루어진다.

    임계값을 2로 두고 1~8의 합을 나누면 다음 트리가 생긴다. 잎(leaf)은 4개, 내부 노드는 3개, 작업 객체는 모두 7개다. 일반적으로 잎이 L개인 이진 분할 트리에는 내부 노드가 L-1개 있으므로 작업 객체는 2L-1개 만들어진다. 깊이는 대략 log₂(N/임계값)이다.

    Fork/Join 프레임워크 1: ForkJoinPool과 RecursiveTask

    포크/조인 프레임워크는 자바 7(@since 1.7)에 java.util.concurrent로 들어왔다. 등장인물은 다음과 같다.

    타입역할
    ForkJoinPoolExecutorService의 구현체. 작업 훔치기를 하는 작업자 스레드(ForkJoinWorkerThread)들을 관리한다.
    ForkJoinTask풀에서 실행되는 작업의 추상 기반 클래스. Javadoc의 표현으로 "가벼운 형태의 Future"이며, 스레드보다 훨씬 가벼운 "스레드 비슷한 실체"라서 적은 수의 스레드가 매우 많은 작업을 실행할 수 있다.
    RecursiveTask결과를 돌려주는 재귀 작업. protected V compute()를 구현한다.
    RecursiveAction결과가 없는 재귀 작업. protected void compute()를 구현한다. 배열을 제자리에서 바꾸는 작업 등에 쓴다.
    CountedCompleter하위 작업들이 끝나면 완료 동작이 연쇄로 실행되는 작업. join으로 기다리지 않는다. 병렬 스트림 내부가 이것을 쓴다.

    앞의 트리를 RecursiveTask로 옮기면 다음과 같다.

    import java.util.concurrent.RecursiveTask;

public class SumTask extends RecursiveTask {
    static int THRESHOLD = 4;            // 이 크기 이하면 더 쪼개지 않는다
    private final int start, end;        // [start, end] 닫힌 구간

    public SumTask(int start, int end) {
        this.start = start;
        this.end = end;
    }

    @Override
    protected Integer compute() {
        int size = end - start + 1;
        if (size <= THRESHOLD) {                         // 정복: 직접 계산
            Work.log("[처리 시작] " + start + "~" + end);
            int sum = 0;
            for (int i = start; i <= end; i++) sum += Work.heavyTask(i);
            Work.log("[처리 완료] " + start + "~" + end + " -> " + sum);
            return sum;
        }
        int mid = start + (end - start) / 2;             // 분할
        SumTask left = new SumTask(start, mid);
        SumTask right = new SumTask(mid + 1, end);
        Work.log("[분할] " + start + "~" + end + " -> " + start + "~" + mid + ", " + (mid + 1) + "~" + end);

        left.fork();                       // 왼쪽은 큐에 넣어 다른 스레드가 가져가게
        int rightResult = right.compute(); // 오른쪽은 지금 스레드가 직접
        int leftResult = left.join();      // 왼쪽 결과를 기다린다(또는 직접 처리한다)
        return leftResult + rightResult;   // 결합
    }
}
    import java.util.concurrent.ForkJoinPool;

public class ForkJoinMain {
    public static void main(String[] args) {
        if (args.length > 0) SumTask.THRESHOLD = Integer.parseInt(args[0]);
        ForkJoinPool pool = new ForkJoinPool(10);
        long start = System.currentTimeMillis();
        int sum = pool.invoke(new SumTask(1, 8));
        long time = System.currentTimeMillis() - start;
        Work.log("sum=" + sum + ", time=" + time + "ms");
        Work.log("pool=" + pool);
        pool.close();
    }
}

    compute() 한 줄씩 읽기

    left.fork()는 작업을 실행하지 않는다. 실행을 "예약"한다. OpenJDK 21의 fork()는 현재 스레드가 ForkJoinWorkerThread이면 그 작업자의 작업 큐에, 아니면 공용 풀의 제출 큐에 작업을 넣고 곧바로 반환한다. 그러면 놀고 있는 다른 작업자가 그 작업을 가져갈 수 있다.

    right.compute()는 그냥 메서드 호출이다. 작업 큐를 거치지 않고 지금 스레드의 스택에 compute() 프레임이 하나 더 쌓인다. 오른쪽 절반은 다른 스레드에 넘길 필요 없이 내가 하면 되기 때문이다. RecursiveTask Javadoc의 예제도 같은 모양(왼쪽을 fork, 오른쪽을 compute, 그다음 왼쪽을 join)에 "일의 절반 정도는 여기서 직접 한다"는 주석을 붙여 둔다.

    left.join()은 왼쪽 작업의 결과를 돌려준다. 이미 끝났으면 바로 반환한다. 아직이면 Thread.join처럼 무작정 잠들지 않는다. 먼저 그 작업이 아직 내 큐에 있는지 찾아보고, 있으면 꺼내서 직접 실행한다. 다른 작업자가 훔쳐 갔다면 그 작업자의 큐에서 일을 거들거나(helping), 그래도 안 되면 필요할 때 예비 스레드를 깨워 병렬성을 보충한다(compensating). 이 동작은 다음 절에서 소스로 확인한다. 이것이 고정 크기 스레드 풀의 교착을 없앤 핵심이다. 실제로 병렬성 2인 ForkJoinPool로 임계값 2의 같은 계산을 돌리면, 앞의 PoolRecursionMain과 스레드 수가 같은데도 교착 없이 끝난다.

    왜 둘 다 fork하지 않는가

    left.fork(); right.fork(); return left.join() + right.join();도 동작은 한다. 그러나 현재 스레드는 두 작업을 큐에 넣고 나서 할 일이 없어 곧바로 join에 들어가고, 큐 맨 위에는 나중에 넣은 right가 있는데 먼저 left를 찾게 된다. ForkJoinTask의 Javadoc은 재귀 호출의 반환처럼 join도 "가장 안쪽부터" 해야 한다며 a.fork(); b.fork(); b.join(); a.join();이 a를 먼저 join하는 것보다 상당히 효율적일 수 있다고 적는다. OpenJDK 21의 tryRemoveAndExec는 큐 위쪽부터 찾아 내려가 중간에 있는 작업을 꺼내고 나머지를 한 칸씩 당겨 메운다. 꺼낼 수는 있지만 그만큼 일이 늘고, 그 사이 큐에 생긴 틈은 훔치려는 다른 작업자를 잠시 멈추게 한다. 한쪽을 compute()로 직접 하는 형태는 이 문제를 아예 만들지 않는다. 같은 일을 하는 정적 메서드 ForkJoinTask.invokeAll(t1, t2)도 OpenJDK 21에서는 t2를 fork하고 t1은 현재 스레드에서 실행한 뒤 t2를 기다린다.

    외부에서 부르는 메서드와 안에서 부르는 메서드

    ForkJoinPool Javadoc은 작업 실행 메서드를 호출 위치로 나눈 표를 제공한다. 포크/조인 계산 바깥(예: main)에서는 풀의 메서드를, 이미 풀 안에서 실행 중인 작업 안에서는 작업의 메서드를 쓴다.

    하려는 일포크/조인 바깥에서포크/조인 계산 안에서
    비동기 실행 예약pool.execute(task)task.fork()
    실행하고 결과를 기다림pool.invoke(task)task.invoke()
    실행하고 Future를 받음pool.submit(task)task.fork() (작업 자체가 Future)

    ForkJoinMain의 출력에서 main이 계산에 한 번도 등장하지 않은 것은 pool.invoke(task) 때문이다. OpenJDK 21에서 이 메서드는 작업을 풀의 제출 큐에 넣고(poolSubmit) join()으로 기다린다. 이렇게 풀에 "제출"된 작업은 외부 스레드가 기다리면서 거들지 않는다(뒤의 공용 풀 절에서 이 규칙의 이유를 본다). 그래서 작업자 1이 루트를 가져갔다. 마지막 줄의 steals = 2는 getStealCount()의 값으로, Javadoc 정의는 "제출한 스레드가 아닌 다른 스레드가 실행을 마친 작업 수의 추정치"다. main이 제출한 루트를 작업자 1이 실행했고, 작업자 1이 fork한 1~4를 작업자 2가 실행했으니 2다.

    예외 처리도 다르다. compute()의 시그니처에는 throws가 없어 검사 예외를 던질 수 없다. Javadoc은 이것이 블로킹 I/O를 하지 말라는 지침을 "느슨하게 강제"하기 위한 것이라고 설명한다. 비검사 예외는 그 작업을 join하는 쪽으로 다시 던져지며, 가능하면 계산을 시작한 스레드와 실제로 예외를 만난 스레드의 스택 트레이스를 모두 담는다. 마지막 줄의 pool.close()는 자바 19에서 추가되었고, 공용 풀에 대해서는 아무 효과가 없다.

    Fork/Join 프레임워크 2: 작업 훔치기

    ThreadPoolExecutor는 작업자들이 큐 하나를 공유한다. 넣는 쪽도 꺼내는 쪽도 모두 같은 큐에 몰린다. 작업이 크고 드물면 문제가 없지만, 포크/조인처럼 작업이 잘게 쪼개져 초당 수많은 작업이 생기고 사라지면 이 큐 하나가 병목이 된다. 게다가 이 구조에서는 앞서 본 대로 기다리는 작업자가 큐의 다른 작업을 실행할 방법이 없다.

    ForkJoinPool은 다르게 생겼다. 작업자마다 자기 작업 큐(WorkQueue)를 하나씩 가진다. 이 큐는 양쪽 끝을 쓰는 덱이다. 작업자가 fork()한 작업은 자기 덱에 들어가고, 작업자는 평소에 자기 덱에서만 작업을 꺼낸다. 자기 덱이 비면 다른 작업자의 덱을 무작위로 골라 반대쪽 끝에서 작업을 하나 훔쳐 온다. Javadoc의 표현으로, 풀의 모든 스레드는 풀에 제출되었거나 다른 활성 작업이 만든 작업을 찾아 실행하려고 시도한다. OpenJDK 소스의 구현 개요는 이 방식을 생산자가 놀고 있는 스레드에 작업을 배정하는 "작업 배분(work dealing)"과 대비하면서, 신호를 받은 스레드가 깨어나는 동안(긴 시간이 걸릴 수 있다) 다른 일을 먼저 마친 스레드가 대신 그 작업을 가져갈 수 있어 처리량이 대개 더 좋다고 설명한다.

    일상에서 가져온 비유각자의 서류함과 남의 서류함 바닥

    사무실 직원마다 자기 서류함이 있다. 큰 업무를 받은 직원은 업무를 반으로 나눠 절반을 자기 서류함 맨 위에 올려 두고 나머지 절반을 붙잡고 일한다. 그 절반도 크면 또 나눠 올려 둔다. 자기 서류함이 빈 직원은 다른 직원의 서류함 맨 아래, 즉 가장 오래전에 올려 둔 서류를 빼 온다. 맨 아래 서류는 처음에 나눈 것이라 가장 큰 덩어리다. 주인은 위에서, 손님은 아래에서 빼니 둘이 손이 부딪히는 일은 서류가 한 장 남았을 때뿐이다. 비유가 깨지는 지점도 있다. 사람은 서로 말로 조율하지만 작업자 스레드는 대화하지 않고 원자적 연산(CAS)으로 누가 가져갈지 정한다. 또 "맨 아래가 가장 크다"는 것은 재귀적으로 반씩 나누는 작업에서만 성립하는 성질이다.

    이 구조가 주는 이득은 세 가지다. 첫째, 탈중앙화다. 작업자는 대부분의 시간에 자기 덱만 만지므로 공유 지점에서 경쟁하지 않는다. 구현 개요는 작업 훔치기의 처리량 이점이 "탈중앙화된 제어"에서 온다고 적는다. 둘째, 자동 부하 분산이다. 스레드를 직접 쓸 때 일의 양이 고르지 않으면 먼저 끝난 스레드가 놀았지만, 여기서는 먼저 끝난 작업자가 아직 바쁜 작업자의 덱에서 일을 가져온다. 사람이 미리 공평하게 나눌 필요가 없다. 셋째, join하는 스레드가 놀지 않는다. 앞 절에서 본 대로 기다리는 작업자는 자기 덱이나 자기 일을 훔쳐 간 작업자의 덱에서 일을 찾아 실행한다.

    작업 훔치기 알고리즘: 덱의 양 끝을 나눠 쓰는 이유

    이제 OpenJDK 21의 ForkJoinPool 소스 주석(구현 개요)과 코드로 내려가자. 아래 내용은 Javadoc이 보장하는 규약이 아니라 OpenJDK 21의 구현이다. 버전에 따라 세부는 바뀔 수 있다.

    WorkQueue: 배열 하나와 인덱스 두 개

    WorkQueue는 원형 버퍼로 쓰는 배열 array와 두 인덱스 base, top으로 이루어진다. 배열 크기는 항상 2의 거듭제곱이어서 나머지 연산 대신 비트 마스킹으로 인덱스를 계산한다. 소스 주석은 이 큐가 덱의 네 가지 끝 연산 중 세 가지만 지원한다고 설명한다.

    • push: 주인 스레드만 호출한다. 개념적으로 array[top++ % length] = task다.
    • pop: 주인 스레드만 호출한다. top - 1 칸의 작업을 원자적으로 꺼내(getAndSet으로 null로 바꾸며) top을 줄인다. 가장 최근에 넣은 것을 꺼내므로 LIFO다.
    • poll(=steal): 다른 스레드가 호출한다. base 칸의 작업을 CAS로 null로 바꾸는 데 성공하면 base를 올리고 그 작업을 가져간다. 가장 오래된 것을 가져가므로 FIFO다.

    주인과 도둑이 마지막 남은 작업 하나를 두고 동시에 달려들면 누가 이기는가? OpenJDK 구현은 이 경쟁을 인덱스가 아니라 배열의 칸 자체에 대한 원자 연산으로 판정한다. 칸을 먼저 null로 바꾼 쪽이 가져간다. 소스 주석은 이렇게 설계한 이유를 GC와 연결한다. 가져간 칸을 가능한 한 빨리 null로 비워 두어야, 작업을 엄청나게 많이 만드는 프로그램에서도 큐가 이미 끝난 작업 객체를 붙잡아 GC를 방해하지 않는다. 자바 고급 1편에서 본 CAS가 여기서 락 없이 주인과 도둑을 중재하는 도구로 쓰인다.

    주인은 LIFO, 도둑은 FIFO인 이유

    재귀 분할에서 덱에 쌓이는 작업의 모양을 생각해 보면 이 선택의 이유가 보인다. 작업자는 큰 작업을 반으로 나눠 절반을 push하고, 남은 절반을 다시 나눠 그 절반을 push한다. 그러므로 덱의 아래쪽(base)에는 일찍 나눈 큰 작업이, 위쪽(top)에는 최근에 나눈 작은 작업이 쌓인다.

    • 주인이 위에서 꺼내는 이유: 가장 최근에 fork한 작업은 방금 다루던 데이터 범위와 가깝고 크기도 작다. 주인이 이것부터 처리하는 것은 재귀 호출이 가장 안쪽부터 반환되는 것과 같은 순서여서, 앞에서 본 "join은 가장 안쪽부터" 규칙과 자연스럽게 맞아떨어진다.
    • 도둑이 아래에서 훔치는 이유: 가장 오래된 작업은 트리의 뿌리에 가까운 큰 덩어리다. 한 번 훔쳐 오면 그 안에서 다시 분할하며 오랫동안 혼자 일할 수 있으므로 훔치는 횟수가 줄어든다. 그리고 주인과 도둑이 서로 반대쪽 끝을 쓰므로 둘의 경쟁은 덱에 작업이 하나 남았을 때만 생긴다.

    소스 주석은 작업자가 자기 큐의 작업을 먼저 처리하고(모드에 따라 LIFO 또는 FIFO), 그다음 다른 큐에서 무작위로 고른 FIFO 훔치기를 한다는 우선순위를 밝혀 둔다. 생성자의 asyncMode를 true로 주면 주인도 자기 큐를 FIFO로 처리한다. Javadoc은 이 모드가 join되지 않는 이벤트 형태의 작업에 적합할 수 있다고 설명한다. 재귀 분할에는 기본값인 LIFO가 맞다.

    join이 기다리지 않고 하는 일

    t4와 t5의 join에서 일어난 일을 OpenJDK 21 코드로 확인하자. ForkJoinTask.join()은 작업이 아직 끝나지 않았으면 awaitDone으로 가고, 현재 스레드가 작업자라면 다음 순서로 시도한다.

    1. tryRemoveAndExec: 기다리려는 작업이 아직 내 덱에 있으면 꺼내서 바로 실행한다. 메서드 주석은 이것을 "top부터 훑어 작업을 찾으면 제거해 실행하고, 나머지를 당겨 빈 칸을 메우는" 깊은 형태의 pop이라고 설명한다. t4에서 두 작업자가 각자 한 일이 이것이다.
    2. helpJoin: 작업을 누가 훔쳐 갔다면, 훔쳐 간 작업자의 덱에서 작업을 가져와 실행한다. 구현 개요는 이를 "선형 도움(linear helping)"이라 부른다. 각 작업자는 마지막으로 훔쳐 온 큐를 source 필드에 기록하고, 기다리는 쪽은 이 표시를 따라 내 작업을 가져간 작업자를 찾는다. 그 결과 기다리는 쪽은 "도둑맞지 않았다면 자기 덱에 있었을" 작업을 실행하게 된다. t5에서 작업자 1이 이것을 시도했지만 작업자 2의 덱에 남은 일이 없었다.
    3. 보상(compensation): 거들 일도 찾지 못하면 필요할 때 예비 스레드를 만들거나 깨워 병렬성을 보충한 뒤 잠든다. 구현 개요는 대부분의 막힘이 GC나 OS 활동 같은 일시적인 원인이라 즉시 보상하면 오히려 스레드가 과잉이 될 수 있어, 기본 정책은 "명백히 굶주릴 때만" 스레드를 추가한다고 설명한다.

    외부 스레드의 제출도 같은 자료 구조로 처리된다. 풀의 queues 배열에서 작업자 큐는 홀수 인덱스에, 외부 제출용 공유 큐는 짝수 인덱스에 놓인다. 외부 스레드는 ThreadLocalRandom의 탐침값을 해시처럼 써서 제출 큐를 고르고, 공유 큐에 넣을 때는 간단한 스핀 락을 잡는다. 작업자 입장에서는 제출 큐도 훔칠 대상 중 하나다. t0에서 작업자 1이 루트를 가져온 것이 이 경로다.

    블로킹은 이 정교한 장치를 무력화한다. ForkJoinPool Javadoc은 풀이 작업이 다른 작업의 join을 기다리느라 멈춘 경우에도 충분한 스레드를 유지하려 하지만, 블로킹 I/O나 관리되지 않는 동기화 앞에서는 그런 조정이 보장되지 않는다고 적는다. 블로킹이 꼭 필요하면 ForkJoinPool.ManagedBlocker 인터페이스로 풀에 알려야 보상을 받을 수 있다.

    Fork/Join 프레임워크 3: 공용 풀

    지금까지는 new ForkJoinPool(10)처럼 풀을 직접 만들었다. 자바 8부터는 ForkJoinPool.commonPool()이라는 정적 풀이 JVM에 하나 있다(@since 1.8). Javadoc은 이 공용 풀이 대부분의 애플리케이션에 적합하며, 특정 풀에 명시적으로 제출되지 않은 모든 ForkJoinTask가 공용 풀을 쓴다고 정한다. main 같은 일반 스레드에서 task.fork()나 task.invoke()를 부르면 그 작업은 공용 풀로 간다. 앞에서 본 fork() 코드의 else 분기, 즉 "현재 스레드가 작업자가 아니면 공용 풀의 제출 큐에 넣는다"가 그 경로다.

    import java.util.concurrent.ForkJoinPool;

public class CommonPoolMain {
    public static void main(String[] args) {
        Work.log("processors=" + Runtime.getRuntime().availableProcessors());
        Work.log("commonPool parallelism=" + ForkJoinPool.getCommonPoolParallelism());
        long start = System.currentTimeMillis();
        int sum = new SumTask(1, 8).invoke();   // 풀을 지정하지 않았다 (임계값 4)
        long time = System.currentTimeMillis() - start;
        Work.log("sum=" + sum + ", time=" + time + "ms");
        Work.log("pool=" + ForkJoinPool.commonPool());
    }
}

    두 가지가 눈에 띈다. 첫째, 논리 프로세서가 8개인데 공용 풀의 병렬성은 7이다. 둘째, main이 계산에 직접 참여했다. 루트를 분할한 것도, 5~8을 처리한 것도 main이다. ForkJoinTask.invoke()의 Javadoc은 이 메서드가 의미상 fork(); join()과 같지만 "항상 현재 스레드에서 실행을 시작하려고 시도한다"고 정한다. 그래서 main이 루트의 compute()를 실행했고, 거기서 fork된 1~4를 공용 풀의 작업자 1이 훔쳐 갔다. 작업자가 하나만 필요했으므로 풀의 size도 1이다. 공용 풀은 작업자 스레드를 처음부터 다 만들어 두지 않고 필요할 때 만들며, Javadoc에 따르면 쓰이지 않는 동안에는 스레드를 천천히 회수했다가 다시 쓰일 때 되살린다.

    병렬성이 코어 수보다 하나 적은 이유

    OpenJDK 21의 공용 풀 생성자는 시스템 속성이 없으면 병렬성을 Math.max(1, Runtime.getRuntime().availableProcessors() - 1)로 정한다. 하나를 빼는 이유는 위 실행 결과에 그대로 나타난다. 공용 풀에 작업을 fork한 외부 스레드는 join하면서 자기 하위 작업을 직접 처리한다. 구현 개요는 이 "호출자도 돕는(caller-helps)" 정책 덕분에 공용 풀의 병렬성을 전체 코어 수보다 하나(또는 그 이상) 적게, 심지어 호출자만 실행하는 0으로 두는 것이 합리적이라고 설명한다. 작업자 7개와 호출 스레드 1개를 합치면 코어 8개를 모두 쓰는 셈이다. 다만 프로세서가 하나뿐이어도 병렬성은 최소 1이다.

    이 정책에는 조건이 있다. 같은 공용 풀이라도 ForkJoinPool.commonPool().invoke(task)로 "제출"하면 main은 돕지 않는다.

    [ForkJoinPool.commonPool-worker-1] [분할] 1~8 -> 1~4, 5~8
[ForkJoinPool.commonPool-worker-2] [처리 시작] 1~4
[ForkJoinPool.commonPool-worker-1] [처리 시작] 5~8
[ForkJoinPool.commonPool-worker-2] [처리 완료] 1~4 -> 100
[ForkJoinPool.commonPool-worker-1] [처리 완료] 5~8 -> 260
[main] sum=360

    구현 개요는 그 이유를 ExecutorService 규약에서 찾는다. 풀에 제출한 작업은 풀이 실행해야 하므로, 호출자 돕기는 fork로 들어온 작업에만 적용하고 submit류로 들어온 작업에는 적용하지 않는다. OpenJDK는 이를 작업의 상태 비트로 구분한다. 같은 계산이라도 task.invoke()는 호출 스레드를 일꾼으로 쓰고, pool.invoke(task)는 호출 스레드를 순수한 대기자로 둔다.

    설정과 생명 주기

    공용 풀은 생성자로 만들 수 없으므로 시스템 속성으로 설정한다. Javadoc이 정하는 속성은 네 가지다.

    시스템 속성의미
    java.util.concurrent.ForkJoinPool.common.parallelism병렬성. 음이 아닌 정수
    java.util.concurrent.ForkJoinPool.common.threadFactoryForkJoinWorkerThreadFactory 구현 클래스 이름. 시스템 클래스 로더로 읽는다
    java.util.concurrent.ForkJoinPool.common.exceptionHandlerUncaughtExceptionHandler 구현 클래스 이름
    java.util.concurrent.ForkJoinPool.common.maximumSpares목표 병렬성을 유지하려고 추가로 둘 수 있는 예비 스레드 최대 수. 기본값 256

    적용 시점이 중요하다. OpenJDK 21에서 공용 풀은 ForkJoinPool 클래스의 정적 초기화 블록에서 만들어지고, 위 속성은 그 생성자에서 한 번 읽힌다. 따라서 -Djava.util.concurrent.ForkJoinPool.common.parallelism=3처럼 JVM 시작 인자로 주는 것이 확실하다. 코드에서 System.setProperty로 바꾸면, 그 전에 병렬 스트림이나 CompletableFuture 같은 다른 코드가 이미 ForkJoinPool 클래스를 초기화했을 경우 아무 효과가 없다. 속성 값에 오류가 있으면 기본값이 쓰인다. 병렬성을 0으로 두는 것도 허용되지만, Javadoc은 그러면 join되지 않는 작업이 영영 실행되지 않을 수 있다고 경고한다.

    생명 주기도 일반 풀과 다르다. Javadoc에 따르면 공용 풀은 정적으로 만들어지며 shutdown()이나 shutdownNow()를 불러도 실행 상태가 바뀌지 않는다. 모든 작업자 스레드는 데몬 스레드로 초기화되므로 JVM은 공용 풀의 작업이 끝나기를 기다리지 않고 종료할 수 있다. 프로그램 종료 전에 비동기 작업이 끝나야 한다면 commonPool().awaitQuiescence(...)로 기다리라는 것이 Javadoc의 안내다.

    공용 풀을 쓰는 다른 API

    공용 풀은 병렬 스트림만의 것이 아니다. 같은 JVM 안에서 다음 API가 모두 같은 풀을 쓴다.

    • 병렬 스트림: 다음 절에서 본다.
    • CompletableFuture의 비동기 메서드: supplyAsync(supplier)처럼 Executor 인자가 없는 비동기 메서드는 공용 풀에서 실행된다. 단, Javadoc은 공용 풀이 병렬성 2 이상을 지원하지 않으면 작업마다 새 스레드를 만든다고 정한다. OpenJDK 21 코드도 getCommonPoolParallelism() > 1일 때만 공용 풀을 쓴다. 즉 availableProcessors()가 2 이하인 환경에서는 동작 방식이 바뀐다.
    • Arrays.parallelSort: Javadoc은 병렬 작업 실행에 포크/조인 공용 풀을 쓴다고 밝힌다.
    • 직접 만든 ForkJoinTask: 작업자가 아닌 스레드에서 fork()나 invoke()를 부르면 공용 풀로 간다.

    그러므로 공용 풀은 JVM 전체가 함께 쓰는 공유 자원이다. 어느 한 기능이 공용 풀의 작업자를 오래 붙잡으면, 그 기능과 아무 관련 없는 다른 기능의 병렬 스트림과 비동기 작업이 함께 느려진다. 이것이 뒤의 주의점 1의 출발점이다.

    작업자 스레드의 일생: pthread로 태어나 park로 잠들고 keepAlive로 사라진다

    앞 절에서 공용 풀은 작업자를 필요할 때 만들고, 쓰이지 않으면 천천히 회수한다고 했다. 병렬화의 고정 비용 목록에 "스레드 깨우기"가 들어가는 것도 같은 이야기다. 그렇다면 작업자는 정확히 언제 만들어지고, 일이 없을 때 어디서 무엇을 하며 기다리고, 언제 사라지는가. 이 절은 OpenJDK 21의 ForkJoinPool 코드, HotSpot의 C++ 코드(jdk21u 저장소), 그리고 macOS(이 실험 환경)에서 관찰한 결과로 그 일생을 따라간다. 모두 구현의 세부이며 Javadoc이 약속한 동작이 아니다.

    ctl: 64비트 하나에 담긴 풀의 상태

    풀의 활성화 상태는 volatile long ctl 필드 하나에 모여 있다. 소스 주석에 따르면 64비트를 16비트씩 네 칸으로 나누어 쓴다.

    비트  63        48 47        32 31        16 15         0
     ┌────────────┬────────────┬────────────┬────────────┐
ctl  │     RC     │     TC     │     SS     │     ID     │
     └────────────┴────────────┴────────────┴────────────┘
RC : 풀려난(released) 작업자 수 — 작업을 찾거나 실행 중인 작업자
TC : 전체 작업자 수             — getPoolSize() 가 이 칸을 읽는다
SS : 대기 스택 맨 위 작업자의 버전 카운터와 상태
ID : 대기 스택 맨 위 작업자의 큐 인덱스   (아래 32비트가 0이면 대기자가 없다)

    아래 32비트는 놀고 있는 작업자들이 쌓인 스택의 꼭대기다. 소스 주석은 이것을 트라이버 스택(Treiber stack), 즉 CAS로 꼭대기를 바꾸는 락 없는 연결 스택이라고 부른다. 각 작업자의 WorkQueue.stackPred 필드가 바로 아래 작업자를 가리키는데, 참조가 아니라 queues 배열의 인덱스를 담는다. 주석은 그 이유를 대기·신호·제어 경로가 작업자나 작업 객체를 붙잡아 GC를 방해하지 않게 하려는 것이라고 밝힌다. 개수 칸과 버전 칸이 같은 64비트 안에 있으므로 "스택에서 작업자 하나를 꺼내면서 RC를 1 올리기" 같은 여러 칸의 변경을 CAS 한 번으로 원자적으로 할 수 있고, 버전 값은 같은 인덱스가 빠졌다 다시 들어오는 ABA 문제를 막는다. 앞에서 출력한 풀 정보의 size가 TC 칸이고, getActiveThreadCount()가 RC 칸이다.

    태어남: signalWork에서 pthread_create까지

    작업이 큐에 들어가면 누군가 그것을 실행하도록 신호를 보내야 한다. 이 일을 하는 메서드가 signalWork()다. 줄여 말하면 이렇다. RC가 병렬성보다 작을 때만 움직인다. 대기 스택에 작업자가 있으면 CAS로 그 작업자를 꺼내 RC를 올리고, 그 작업자가 실제로 잠들어 있으면 LockSupport.unpark로 깨운다. 대기자가 없고 TC가 병렬성보다 작으면 TC를 먼저 올려 자리를 예약한 뒤 createWorker()로 새 스레드를 만든다. 구현 개요는 자원 사용을 줄이려고 "새로 만들기보다 놀고 있는 스레드를 다시 활성화하는 쪽"을 우선한다고 적는다.

    누가 signalWork()를 부르는지도 정해져 있다. fork()가 부르는 WorkQueue.push는 새 작업을 넣은 칸의 바로 앞 칸이 비어 있을 때, 즉 빈 큐에 작업을 넣었을 때 신호를 보낸다. scan으로 다른 큐에서 작업을 훔친 작업자는 그 큐에 작업이 더 남아 있으면 신호를 하나 더 보낸다. 구현 개요는 계산이 순수한 트리 구조라면 첫 규칙만으로도 작업자가 다른 작업자 하나를 깨우는 연쇄가 생겨 O(log(스레드 수)) 단계 만에 모두 활성화되고, 작업이 한 생산자에게서 차례로 들어오는 경우는 둘째 규칙이 같은 효과를 낸다고 설명한다. main 혼자 일곱 번 신호를 보내는 것이 아니라, 깨어난 작업자가 다음 작업자를 깨우는 나무 모양의 전파다.

    새 작업자는 결국 Thread.start()로 시작된다. HotSpot에서 이 호출은 JVM_StartThread(jvm.cpp)에 도착해 JavaThread 객체를 만들고, 그 생성자가 os::create_thread를 부른다. macOS용 구현(os_bsd.cpp)은 pthread 속성에 스택 크기와 detached 상태를 설정한 뒤 pthread_create를 호출하고, 성공하면 로그를 한 줄 남긴다. -Xlog:os+thread로 그 로그를 켜면 병렬 스트림 한 번에 OS 스레드가 몇 개 생기는지 볼 수 있다.

    잠듦: awaitWork에서 pthread_cond_wait까지

    작업자의 최상위 루프 runWorker는 scan으로 작업을 찾다가 찾지 못하면 awaitWork로 들어간다. 여기서 하는 일은 세 단계다. 첫째, 자기 phase 필드에 비활성 비트(부호 비트)를 세우고, CAS로 ctl의 대기 스택 꼭대기에 자신을 올리면서 RC를 1 내린다. 둘째, 곧바로 잠들지 않고 큐 배열 크기에 비례하는 짧은 횟수만큼 Thread.onSpinWait()를 부르며 신호를 기다린다. 구현 개요는 park/unpark가 느리고 들쭉날쭉할 수 있지만 계속 스캔하면 메모리와 CAS 경쟁이 커지므로, 비활성화와 활성화가 아슬아슬하게 엇갈리는 경우만 덮을 만큼 작은 값으로 정했다고 설명한다. 셋째, 그래도 신호가 없으면 access 필드를 PARKED로 바꿔 "깨우려면 unpark가 필요하다"고 알린 뒤 LockSupport.park()를 부른다. 앞의 signalWork가 access == PARKED일 때만 unpark를 부르는 이유가 이것이다. 아직 스핀 중인 작업자는 phase만 바꿔 주면 스스로 알아차린다.

    그 아래는 HotSpot이다. LockSupport.park는 Unsafe.park라는 네이티브 메서드를 부르고, HotSpot의 Unsafe_Park(unsafe.cpp)는 스레드 상태를 파킹으로 바꾼 뒤 스레드마다 하나씩 있는 Parker 객체의 park를 호출한다. POSIX용 구현(os_posix.cpp)의 Parker::park는 먼저 허가(permit) 카운터 _counter를 원자적으로 0으로 바꿔 보고, 원래 값이 1이었으면(누군가 먼저 unpark했으면) 잠들지 않고 바로 반환한다. 아니면 pthread 뮤텍스를 잡고 pthread_cond_wait로 조건 변수에서 잠든다(parkUntil처럼 기한이 있으면 pthread_cond_timedwait). Parker::unpark는 카운터를 1로 만들고, 그 스레드가 조건 변수에서 기다리는 중이면 pthread_cond_signal을 보낸다. unpark가 park보다 먼저 도착해도 깨움을 잃지 않는 것은 이 카운터 덕분이다.

    사라짐: keepAlive와 하나씩의 회수

    같은 덤프에서 공용 풀 작업자 일곱 중 여섯은 WAITING (parking)이었고, 하나(이 실행에서는 worker-5)만 TIMED_WAITING (parking)이었다. 이 차이도 awaitWork에 있다. 대기 스택에 올라가면서 RC를 0으로 만든 작업자, 즉 마지막으로 일을 놓은 작업자만 풀 전체가 쉬고 있을 수 있다고 보고(소스의 변수 이름으로 idle) LockSupport.parkUntil(현재 시각 + keepAlive)로 기한을 두고 잔다. 나머지는 기한 없는 park()로 잔다. Thread.State Javadoc이 정한 대로 기한 없는 park는 WAITING, parkUntil은 TIMED_WAITING으로 보인다.

    기한이 지나 깨어난 작업자는 tryTrim으로 물러나려 한다. 자신이 대기 스택의 꼭대기일 때만 CAS로 스택에서 빠지면서 TC를 1 내리고 루프를 끝낸다. 종료 처리(deregisterWorker)는 마지막에 signalWork()를 부르는데, 이때 RC는 0이고 대기 스택에는 다음 작업자가 있으므로 그 작업자가 깨어난다. 깨어난 작업자는 일을 찾지 못해 다시 awaitWork로 들어가고, 이번에는 자신이 RC를 0으로 만드는 마지막 작업자이므로 기한을 두고 잔다. 그래서 작업자는 keepAlive마다 하나씩 사라진다. 공용 풀의 keepAlive는 DEFAULT_KEEPALIVE = 60_000L, 60초다. 이 과정을 보려고 자바 9부터 있는 긴 생성자로 keepAlive를 1초로 줄인 풀을 만들었다.

    import java.util.*;
import java.util.concurrent.*;
import java.util.stream.IntStream;

public class Lifecycle {
    static void sleep(long ms) {
        try { Thread.sleep(ms); } catch (InterruptedException e) { throw new RuntimeException(e); }
    }

    static String states(ForkJoinPool pool) {      // 이 풀의 작업자 이름과 상태
        List list = new ArrayList<>();
        for (Thread t : Thread.getAllStackTraces().keySet())
            if (t instanceof ForkJoinWorkerThread w && w.getPool() == pool)
                list.add(t.getName().replace("ForkJoinPool-1-", "") + "=" + t.getState());
        Collections.sort(list);
        return list.toString();
    }

    public static void main(String[] args) throws Exception {
        ForkJoinPool pool = new ForkJoinPool(4, ForkJoinPool.defaultForkJoinWorkerThreadFactory,
                null, false, 0, 4, 1, null, 1, TimeUnit.SECONDS);    // 마지막 두 인자: keepAlive 1초
        int sum = pool.submit(() -> IntStream.rangeClosed(1, 8).parallel()
                .map(i -> { sleep(100); return i * 10; }).sum()).get();

        long start = System.currentTimeMillis();
        for (int k = 0; k < 12; k++) {
            System.out.printf("%5dms size=%d active=%d %s%n", System.currentTimeMillis() - start,
                    pool.getPoolSize(), pool.getActiveThreadCount(), states(pool));
            sleep(500);
        }
        pool.close();
    }
}

    availableProcessors()는 어디서 오는가: 공용 풀의 크기를 정하는 숫자

    공용 풀의 병렬성, 병렬 스트림의 잎 목표 수, CompletableFuture의 기본 실행기는 모두 Runtime.getRuntime().availableProcessors()라는 숫자 하나에서 갈라져 나온다. 이 숫자가 어디서 오는지 알아야 "개발 노트북에서는 빨랐는데 운영 컨테이너에서는 다르게 동작한다"는 현상을 설명할 수 있다.

    자바에서 커널까지

    availableProcessors()는 native 메서드다. JDK의 네이티브 코드(Runtime.c)는 곧바로 JVM_ActiveProcessorCount()를 부르고, HotSpot(jvm.cpp)은 이를 os::active_processor_count()로 넘긴다. 이 함수는 운영체제마다 구현이 다르다. jdk21u 소스로 확인한 내용은 다음과 같다.

    환경os::active_processor_count()가 돌려주는 값
    공통-XX:ActiveProcessorCount=N을 주면 다른 무엇보다 우선해 N
    macOS (os_bsd.cpp)JVM 초기화 때 sysctl(CTL_HW, HW_NCPU)로 읽어 둔 프로세서 수
    Linux (os_linux.cpp)sched_getaffinity로 얻은, 이 프로세스가 쓸 수 있는 CPU 수. 컨테이너 안이라고 판단되면(UseContainerSupport, 기본 true) cgroup의 CPU 쿼터로 계산한 값과 비교해 작은 쪽

    Linux의 쿼터 계산(cgroupUtil_linux.cpp의 CgroupUtil::processor_count)은 쿼터를 주기로 나눈 값을 올림한다. 호스트에 코어가 64개 있어도 컨테이너의 CPU 한도가 1.5코어, 즉 cgroup v2의 cpu.max가 "150000 100000"이라면 ceil(150000 / 100000) = 2가 되고, availableProcessors()는 2를 돌려준다. taskset 같은 도구로 CPU 친화도를 줄인 경우에도 sched_getaffinity 결과가 줄어 같은 효과가 난다.

    이 실험 환경의 Mac은 sysctl hw.ncpu가 8이고, 그 안에서 hw.perflevel0.logicalcpu(성능 코어)가 4, hw.perflevel1.logicalcpu(효율 코어)가 4다. HotSpot은 HW_NCPU 하나만 읽으므로 둘을 구분하지 않고 8로 센다. 공용 풀 작업자 7개와 main은 속도가 다른 두 종류의 코어 위에서 실행되고, 어느 스레드를 어느 코어에 올릴지는 macOS 스케줄러가 정한다. 같은 크기의 잎이라도 끝나는 시각이 달라질 수 있는 환경이며, 앞에서 본 4배 과분할과 작업 훔치기가 이런 불균형을 흡수하는 장치다.

    숫자는 시작할 때 한 번 굳는다

    Runtime.availableProcessors()의 Javadoc은 이 값이 JVM 실행 중에 바뀔 수 있으므로 프로세서 수에 민감한 애플리케이션은 가끔 다시 물어보고 자원 사용을 조정하라고 적는다. availableProcessors()는 자바 쪽에 캐시가 없는 native 메서드라 호출할 때마다 os::active_processor_count()까지 내려간다(위의 trace 로그에는 JVM 내부의 호출도 섞여 있다). 다만 그 아래에서 macOS 구현은 초기화 때 읽어 둔 HW_NCPU 값을 그대로 돌려주고, Linux 구현은 CPU 친화도와 cgroup 한도를 다시 읽는다(cgroup 쪽 결과는 잠깐 캐시한다). 그러나 공용 풀은 다시 묻지 않는다. OpenJDK 21에서 공용 풀의 병렬성은 ForkJoinPool 클래스 초기화 때 한 번 계산되고, 병렬 스트림의 LEAF_TARGET도 AbstractTask의 static final 필드로 그 클래스가 초기화될 때 한 번 정해진다. 실행 중에 컨테이너의 CPU 한도가 바뀌어도 이미 만들어진 공용 풀의 크기는 그대로다. 공용 풀의 병렬성만 고정하려면 앞에서 본 parallelism 시스템 속성을, JVM 전체가 보는 프로세서 수를 바꾸려면 -XX:ActiveProcessorCount를 쓴다. 후자는 HotSpot 내부에도 영향을 준다. 예를 들어 GC 작업자 스레드 수의 기본값을 정하는 WorkerPolicy(workerPolicy.cpp)도 JVM 시작 시점의 활성 프로세서 수를 쓴다.

    compute 반복문과 번갈아 fork하기

    AbstractTask.compute()의 반복문을 단순화하면 다음과 같다. 재귀 호출 대신 반복문을 쓰는 이유를 소스 주석은 깊은 재귀를 피하기 위해서라고 설명한다.

    rs = 이 작업의 spliterator
threshold = 루트 크기 / (병렬성 × 4)  (최소 1)
forkRight = false
while (rs의 크기 > threshold 이고 ls = rs.trySplit() 가 null 이 아님):
    왼쪽 자식(ls), 오른쪽 자식(rs) 생성
    if forkRight: 오른쪽 자식을 fork, 왼쪽 자식으로 계속 (rs = ls)
    else:         왼쪽 자식을 fork, 오른쪽 자식으로 계속
    forkRight = !forkRight
지금 붙잡은 자식에서 doLeaf() 실행 → tryComplete()

    fork할 쪽을 매번 바꾸는 이유도 주석에 있다. 왼쪽이나 오른쪽으로 체계적으로 치우쳐 쪼개지는 Spliterator에 대처하기 위해서다. 이제 IntStream.rangeClosed(1, 8)을 따라가 보자. 범위 스트림의 Spliterator(Streams.RangeIntSpliterator)는 크기가 2^24 미만이면 정확히 반으로 쪼갠다. 원소 8개에 대한 임계값은 아래에서 계산하듯 1이다.

    main: [1~8]  분할 → 왼쪽 [1~4] fork,   오른쪽 [5~8] 로 계속   (forkRight: false → true)

    그래서 main은 언제나 6을 가장 먼저 계산한다. 병렬성 3의 실행에서 main이 이어서 5를 계산한 것은 호출자 돕기다. 6을 마친 main은 루트의 완료를 기다리면서, 자기가 공용 풀에 넣었지만 아직 아무도 가져가지 않은 하위 작업(가장 마지막에 넣은 [5])을 직접 처리했다. 작업자가 넉넉한 첫 실행에서는 [5]를 이미 작업자 4가 가져갔으므로 그런 일이 없었다.

    잎의 크기는 어떻게 정해지는가

    임계값은 AbstractTask.suggestTargetSize가 정한다. 루트의 크기 추정값을 "잎 목표 수"로 나눈 값이고, 0이면 1로 올린다. 잎 목표 수(LEAF_TARGET)는 공용 풀 병렬성의 4배(getCommonPoolParallelism() << 2)다. 현재 스레드가 어떤 ForkJoinPool의 작업자라면 그 풀의 병렬성의 4배를 쓴다. 소스 주석은 4배로 "과분할(over-partition)"하는 이유를, 잎 작업의 크기가 고르지 않거나 일부 프로세서가 다른 일로 바쁠 때 다른 작업자가 도울 수 있게 하기 위해서라고 설명한다. 잎이 코어 수만큼만 있으면 늦게 끝나는 잎 하나가 전체를 붙잡지만, 코어당 네 개쯤 있으면 먼저 끝난 작업자가 남은 잎을 훔쳐 갈 수 있다.

    병렬 스트림 사용 시 주의점 1: 공용 풀은 JVM 전체가 나눠 쓴다

    단독 실행에서 병렬 스트림은 8배 가까이 빨랐다. 이제 서버처럼 여러 요청이 동시에 들어오는 상황을 흉내 내 보자. 요청 하나를 스레드 하나가 처리하고, 각 요청은 앞의 병렬 스트림 계산을 한 번씩 한다.

    import java.util.concurrent.ExecutorService;
import java.util.concurrent.Executors;
import java.util.stream.IntStream;

public class ServerSimMain {
    static int quietTask(int i) {      // 로그 없이 100ms 걸리는 작업
        Work.sleep(100);
        return i * 10;
    }

    static void handleRequest(String name) {
        long start = System.currentTimeMillis();
        int sum = IntStream.rangeClosed(1, 8)
                .parallel()
                .map(ServerSimMain::quietTask)
                .sum();
        long time = System.currentTimeMillis() - start;
        Work.log(name + " sum=" + sum + ", time=" + time + "ms");
    }

    public static void main(String[] args) throws InterruptedException {
        int requests = Integer.parseInt(args[0]);
        ExecutorService requestPool = Executors.newFixedThreadPool(requests);
        for (int i = 1; i <= requests; i++) {
            String name = "req" + i;
            requestPool.submit(() -> handleRequest(name));
        }
        requestPool.close();     // 제출한 요청이 모두 끝날 때까지 기다린다
    }
}

    공용 풀이 스레드를 더 만들어 주지 않는 이유는 작업이 sleep으로 막혀 있기 때문이다. 앞에서 본 보상 메커니즘은 join 때문에 막힌 작업자를 위한 것이다. ForkJoinPool Javadoc은 블로킹 I/O나 관리되지 않는 동기화 앞에서는 스레드 수 조정이 보장되지 않는다고 분명히 적는다. sleep 대신 원격 API 호출, DB 쿼리, 파일 읽기가 있어도 마찬가지다. 작업자는 CPU를 쓰지 않으면서 자리만 차지하고, 공용 풀의 다른 모든 사용자가 그 뒤에 줄을 선다.

    실제 서버로 옮겨 보면 위험이 더 분명해진다. 서블릿 컨테이너는 요청마다 스레드 풀의 스레드 하나를 배정한다(스프링 MVC 1편에서 본 구조다). 수백 개의 요청 스레드가 각자 병렬 스트림 안에서 외부 API를 부르면, JVM 하나에 고작 "코어 수 - 1"개뿐인 공용 풀 작업자가 모두 응답을 기다리며 묶인다. 그러면 그 API와 무관한 다른 기능의 병렬 스트림, Executor를 지정하지 않은 CompletableFuture.supplyAsync 작업, Arrays.parallelSort까지 함께 느려진다. 한 기능의 느린 외부 의존성이 공용 풀을 매개로 전체 서비스로 번지는 것이다. 이런 장애를 스레드 덤프로 보면 ForkJoinPool.commonPool-worker-N 스레드들이 모두 소켓 읽기나 대기 상태에 있다.

    CPU만 쓰는 계산이라면 괜찮을까? 그렇지도 않다. 서버는 이미 요청 단위로 병렬이다. 요청 스레드가 코어 수보다 많이 동시에 일하고 있다면 코어는 이미 바쁘고, 각 요청을 다시 잘게 쪼개 봐야 전체 CPU 작업량은 그대로이면서 분할, 작업 객체 생성, 훔치기, 결합 비용만 더해진다. 부하가 낮을 때 요청 하나의 응답 시간은 줄일 수 있지만 부하가 높을 때의 처리량은 늘지 않는다. 병렬 스트림이 가장 잘 맞는 곳은 배치 작업이나 단독으로 실행되는 계산처럼 "이 계산 하나가 기계를 독차지해도 되는" 상황이다.

    일상에서 가져온 비유건물 공용 화물 엘리베이터

    공용 풀은 건물 전체가 함께 쓰는 화물 엘리베이터 일곱 대와 같다. 짐을 빨리 옮기고 싶은 입주사가 엘리베이터를 잡아 두고 짐이 다 포장될 때까지(I/O를 기다리는 동안) 문을 열어 두면, 다른 층의 입주사들은 영문도 모르고 기다린다. 다만 비유와 다른 점도 있다. 공용 풀에서는 짐을 맡긴 사람(호출 스레드)이 자기 짐 일부를 직접 나르기도 하므로, 엘리베이터가 모두 묶여도 각자의 일이 완전히 멈추지는 않는다. 대신 그만큼 느려진다.

    병렬 스트림 사용 시 주의점 2: 풀을 분리하는 방법과 그 한계

    공용 풀을 오염시키지 않으려면 작업의 성격에 따라 실행할 곳을 분리해야 한다. 세 가지 선택지를 차례로 보자.

    선택 1: 전용 ForkJoinPool 안에서 병렬 스트림 실행하기

    import java.util.concurrent.ForkJoinPool;
import java.util.stream.IntStream;

public class CustomPoolMain {
    public static void main(String[] args) throws Exception {
        ForkJoinPool myPool = new ForkJoinPool(4);
        int sum = myPool.submit(() ->
                IntStream.rangeClosed(1, 8)
                        .parallel()
                        .map(Work::heavyTask)
                        .sum()
        ).get();
        Work.log("sum=" + sum);
        myPool.close();
    }
}

    스레드 이름이 ForkJoinPool.commonPool-worker-N이 아니라 ForkJoinPool-1-worker-N이다. 공용 풀을 전혀 쓰지 않았다. 원리는 앞에서 본 것들의 조합이다. 람다는 myPool의 작업자에서 실행되고, 그 안에서 ReduceTask.invoke()가 시작된다. 이후의 fork()는 Javadoc대로 "현재 작업이 실행 중인 풀"에 작업을 넣는다. 잎 목표 수도 AbstractTask.getLeafTarget()이 현재 작업자의 풀 병렬성(4)으로 계산한다. main은 submit으로 제출했으므로 거들지 않고 get()에서 기다린다.

    한계도 분명하다. 첫째, 스트림 API 문서는 병렬 스트림을 어느 풀에서 실행하는지 규정하지 않는다. 이 방법은 ForkJoinTask의 의미와 OpenJDK 구현에서 나오는 결과이지 스트림이 약속한 동작이 아니다. 둘째, 피해를 격리할 뿐 해결하지는 않는다. 블로킹 작업은 여전히 myPool의 작업자 4개를 붙잡는다. 셋째, 풀은 한 번 만들어 재사용하고 애플리케이션이 끝날 때 닫아야 한다. 요청마다 new ForkJoinPool()을 만들고 닫지 않으면 스레드가 계속 쌓인다.

    선택 2: I/O 작업은 대기에 맞게 크기를 정한 ExecutorService로

    병렬화하려는 것이 기다리는 작업이라면 애초에 포크/조인이 맞는 도구가 아니다. ForkJoinTask Javadoc은 분할 가능한 작업이 블로킹 I/O를 하지 않아야 한다고 적는다. 기다리는 작업은 동시에 기다릴 수 있는 수만큼 스레드를 가진 전용 풀에 맡긴다.

    import java.util.List;
import java.util.concurrent.*;
import java.util.stream.IntStream;

public class ExecutorIoMain {
    public static void main(String[] args) throws Exception {
        ExecutorService ioPool = Executors.newFixedThreadPool(8);   // I/O 대기용 전용 풀
        long start = System.currentTimeMillis();
        List> futures = IntStream.rangeClosed(1, 8)
                .mapToObj(i -> ioPool.submit(() -> Work.heavyTask(i)))
                .toList();                                   // 1단계: 모두 제출
        int sum = 0;
        for (Future f : futures) sum += f.get();    // 2단계: 모두 기다림
        long time = System.currentTimeMillis() - start;
        Work.log("sum=" + sum + ", time=" + time + "ms");
        ioPool.close();
    }
}

    여기에는 지연 평가와 관련된 함정이 하나 숨어 있다. 제출과 대기를 한 파이프라인에 이어 붙이면 어떻게 될까?

    int sum = IntStream.rangeClosed(1, 8)
        .mapToObj(i -> ioPool.submit(() -> Work.heavyTask(i)))
        .mapToInt(f -> {
            try { return f.get(); } catch (Exception e) { throw new RuntimeException(e); }
        })
        .sum();
    [main] sum=360, time=867ms

    스레드 8개짜리 풀을 썼는데 순차 실행과 같은 시간이 걸렸다. 5회에서 본 대로 순차 스트림은 원소 하나가 파이프라인 끝까지 내려간 뒤에 다음 원소가 출발한다(세로 방향 처리). 원소 1이 제출되자마자 같은 원소의 get()이 100ms를 기다리고, 그다음에야 원소 2가 제출된다. 풀에는 언제나 작업이 하나뿐이다. ExecutorIoMain은 toList()라는 최종 연산으로 "모두 제출"을 끝낸 뒤에 기다리기 시작하므로 여덟 작업이 겹쳐 실행되었다. CompletableFuture.supplyAsync(..., executor)로 바꿔도 같은 원리가 적용된다. 제출하는 단계와 기다리는 단계를 두 개의 파이프라인으로 나누어야 한다.

    자바 21에서는 가상 스레드(JEP 444)도 선택지다. Executors.newVirtualThreadPerTaskExecutor()(@since 21)는 작업마다 가상 스레드를 하나씩 만드는 실행기로, 블로킹 작업이 아주 많을 때 플랫폼 스레드 풀의 크기를 고민하는 문제를 덜어 준다. 가상 스레드 자체는 이 권의 범위를 벗어나므로 이름만 적어 둔다.

    선택 3: 꼭 블로킹해야 한다면 풀에 알린다

    포크/조인 계산 안에서 블로킹이 불가피하다면 ForkJoinPool.managedBlock(ManagedBlocker)로 감싸 풀에 "이 작업자는 지금부터 막힌다"고 알린다. 그러면 풀은 보상 스레드를 만들어 병렬성을 유지하려 한다. 구현 개요에 따르면 ManagedBlocker는 도움(helping)을 쓸 수 없어 보상에만 의존하고, 공용 풀의 보상 스레드 수는 maximumSpares(기본 256)로 제한된다.

    스레드에 묶인 문맥은 작업자에게 따라가지 않는다

    풀을 어떻게 고르든 병렬 스트림의 람다는 호출 스레드가 아닌 스레드에서도 실행된다. ThreadLocal에 담긴 문맥은 그 스레드에만 있으므로 작업자에게 전달되지 않는다. 가장 위험한 예가 스프링 트랜잭션이다. TransactionSynchronizationManager의 Javadoc 첫 문장은 이 클래스가 리소스와 트랜잭션 동기화를 "스레드별로" 관리한다는 것이다. 스프링 DB 편에서 본 대로 @Transactional 메서드의 커넥션은 이 스레드별 저장소에 묶인다. 그 메서드 안에서 병렬 스트림으로 리포지토리를 호출하면, 공용 풀 작업자에서 실행된 원소들은 트랜잭션에 참여하지 않는다. 더 고약한 것은 호출 스레드도 잎 몇 개를 직접 처리한다는 점이다. 원소 일부는 트랜잭션 안에서, 일부는 밖에서 실행되고, 어느 원소가 어느 쪽인지는 실행마다 다르다. 스프링 시큐리티의 SecurityContextHolder처럼 기본적으로 ThreadLocal에 보관하는 다른 문맥도 같은 문제를 겪는다.

    클래스 로더도 차이가 난다. Javadoc에 따르면 스레드 팩토리를 따로 지정하지 않은 공용 풀은 시스템 클래스 로더를 작업자의 스레드 문맥 클래스 로더(thread context class loader)로 쓴다. 애플리케이션 전용 클래스 로더를 쓰는 환경에서 문맥 클래스 로더로 클래스나 리소스를 찾는 라이브러리를 병렬 스트림 안에서 부르면, 호출 스레드에서와 다른 결과가 나올 수 있다.

    결과와 성능을 지키는 규칙

    패키지 문서는 실행이 순차든 병렬이든, findAny()처럼 명시적으로 비결정적인 연산을 제외하면 계산 결과가 바뀌어서는 안 된다고 정한다. 이 약속이 지켜지려면 사용자가 넘기는 람다(문서의 용어로 행동 매개변수, behavioral parameter)가 조건을 지켜야 한다. 다음 실험들은 조건을 어겼을 때 무슨 일이 일어나는지 보여 준다.

    공유 가변 상태를 건드리지 않는다

    List list = new ArrayList<>();
IntStream.range(0, 10_000).parallel().forEach(list::add);
System.out.println("size=" + list.size());
    size=3553
size=4927
size=5900

    10,000개를 넣었는데 절반 안팎만 남았다. 같은 코드를 200번 반복한 실험에서는 세 번 ArrayIndexOutOfBoundsException이 났다. ArrayList.add는 "현재 크기를 읽고, 필요하면 배열을 늘리고, 그 칸에 쓰고, 크기를 1 늘리는" 여러 단계로 이루어지며 어느 단계도 원자적이지 않다. 두 스레드가 같은 크기를 읽으면 같은 칸에 덮어써 값 하나가 사라진다. 한 스레드가 배열을 늘려 교체하는 동안 다른 스레드가 옛 크기를 기준으로 쓰면 범위를 벗어난다. 자바 고급 1편의 경쟁 상태(race condition) 그대로다.

    Collections.synchronizedList로 감싸면 안전해지지만, 패키지 문서의 표현대로 이것은 "나쁜 선택지" 중 하나다. 동기화하지 않으면 데이터 경쟁이고, 동기화하면 모든 스레드가 락 하나에 줄을 서서 병렬화의 이득이 사라진다. 올바른 방법은 가변 상태를 공유하지 않는 것이다. IntStream.range(0, 10_000).parallel().boxed().toList()는 크기 10,000에 첫 원소 0, 마지막 원소 9999로 정확하다. 7회에서 본 대로 컬렉터는 잎마다 자기 컨테이너를 따로 만들어 채우고, 결합 단계에서 트리 순서대로 합친다. 공유하는 것이 없으니 락도 필요 없다.

    항등원과 결합 법칙을 지킨다

    Stream.reduce(identity, accumulator)의 Javadoc은 두 조건을 요구한다. identity는 누산 함수의 항등원이어야 하고(모든 t에 대해 accumulator.apply(identity, t)가 t와 같아야 한다), 누산 함수는 결합 법칙을 만족해야 한다. 어기면 이렇게 된다.

    IntStream.rangeClosed(1, 8).reduce(10, Integer::sum);                 // 46
IntStream.rangeClosed(1, 8).parallel().reduce(10, Integer::sum);      // 116
IntStream.rangeClosed(1, 8).reduce(0, (a, b) -> a - b);               // -36
IntStream.rangeClosed(1, 8).parallel().reduce(0, (a, b) -> a - b);    // 0

    첫 번째 쌍에서 10은 덧셈의 항등원이 아니다. 순차 실행은 10에서 한 번 출발해 10+36 = 46이다. 병렬 실행은 잎마다 identity에서 출발한다. 앞에서 계산했듯 원소 8개는 잎 8개가 되므로 10이 여덟 번 더해져 36+80 = 116이 된다. 잎의 개수는 원소 수와 병렬성에 따라 바뀌므로, 이 값은 기계에 따라 달라질 수 있다.

    두 번째 쌍에서 뺄셈은 결합 법칙을 만족하지 않는다. 순차 실행은 ((((0-1)-2)-3)…-8) = -36이다. 병렬 실행에서는 잎 i가 0-i = -i를 내고, 결합이 "왼쪽 - 오른쪽"으로 일어난다. [1,2]는 (-1)-(-2) = 1, [3,4]도 1, 그래서 [1~4]는 1-1 = 0이다. [5~8]도 같은 방식으로 0이 되어 최종 결과는 0-0 = 0이다. 패키지 문서는 결합 법칙이 병렬 평가에 중요한 이유를 a op b op c op d == (a op b) op (c op d)로 설명한다. 이 등식이 성립해야 (a op b)와 (c op d)를 동시에 계산할 수 있다. 덧셈, 최솟값, 최댓값, 문자열 연결이 결합 법칙을 만족하는 예다. 문자열 연결은 교환 법칙을 만족하지 않지만 결합 법칙은 만족하므로 순서를 지키는 병렬 결합에 쓸 수 있다.

    순서에 기대지 않거나, 순서의 비용을 치른다

    IntStream.rangeClosed(1, 8).parallel().forEach(i -> System.out.print(i + " "));
IntStream.rangeClosed(1, 8).parallel().forEachOrdered(i -> System.out.print(i + " "));
IntStream.rangeClosed(1, 1000).parallel().filter(i -> i % 7 == 0).findFirst();   // 언제나 7
IntStream.rangeClosed(1, 1000).parallel().filter(i -> i % 7 == 0).findAny();     // 이 실행에서는 658
    5 6 7 4 3 8 2 1
1 2 3 4 5 6 7 8

    forEach는 원소를 처리한 스레드가 그 자리에서 동작을 실행하므로 순서가 없다. forEachOrdered는 만남 순서를 지키지만, 그러려면 앞쪽 원소의 동작이 끝날 때까지 뒤쪽 원소의 동작을 미뤄야 하므로 병렬성의 이득이 줄어든다. findAny의 Javadoc은 이 연산이 명시적으로 비결정적이며 병렬 연산에서 최대 성능을 내기 위해 아무 원소나 고를 수 있다고 하고, 안정된 결과가 필요하면 findFirst를 쓰라고 한다.

    limit, skip, takeWhile, dropWhile도 같다. Stream.limit의 API Note는 이 연산이 순차 파이프라인에서는 대개 싸지만 순서가 있는 병렬 파이프라인에서는 아무 n개가 아니라 "처음 n개"를 돌려줘야 하므로 상당히 비쌀 수 있다고 적는다. 의미상 허용된다면 unordered()로 순서 제약을 풀면 크게 빨라질 수 있고, 순서가 꼭 필요하다면 sequential()로 바꾸는 편이 나을 수 있다는 것이 문서의 안내다. 5회에서 본 sorted, distinct 같은 상태 있는 연산도 병렬에서는 잎의 결과를 모아야 하는 장벽이 된다.

    잘 쪼개지는 소스를 쓴다

    병렬 스트림의 분할은 소스의 Spliterator.trySplit()이 얼마나 잘 쪼개 주느냐에 달려 있다. 원소 10,000개짜리 소스들에 trySplit()을 한 번 불러 보자.

    static void show(String name, Spliterator right) {
    Spliterator left = right.trySplit();
    System.out.println(name + ": left=" + (left == null ? "null" : left.estimateSize())
            + ", right=" + right.estimateSize()
            + ", SIZED=" + right.hasCharacteristics(Spliterator.SIZED));
}
// data는 0~9999를 담은 리스트
show("ArrayList ", new ArrayList<>(data).spliterator());
show("LinkedList", new LinkedList<>(data).spliterator());
show("range     ", IntStream.range(0, 10_000).spliterator());
show("iterate   ", Stream.iterate(0, i -> i + 1).spliterator());
    ArrayList : left=5000, right=5000, SIZED=true
LinkedList: left=1024, right=8976, SIZED=true
range     : left=5000, right=5000, SIZED=true
iterate   : left=4611686018427387903, right=9223372036854775807, SIZED=false

    ArrayList와 범위 스트림은 인덱스 계산 한 번으로 정확히 반을 나눈다. 비용이 들지 않고, 나뉜 두 쪽의 크기를 정확히 안다(SIZED). 이런 소스는 앞에서 본 이진 분할 트리를 그대로 만든다.

    LinkedList는 다르다. 노드를 인덱스로 건너뛸 수 없으므로 반을 나누려면 절반까지 노드를 따라가야 한다. OpenJDK 21의 구현은 대신 앞에서부터 원소를 배열에 복사해 떼어 낸다. 떼어 내는 크기는 1024(BATCH_UNIT)에서 시작해 분할할 때마다 1024씩 커진다. 같은 Spliterator에 계속 trySplit()을 부르면 1024, 2048, 3072개를 떼어 내고, 네 번째에는 남은 3856개를 모두 떼어 낸다. 분할 자체가 순차 순회와 복사이고 나뉜 크기도 고르지 않다.

    Stream.iterate(seed, f)는 더 나쁘다. 각 원소가 이전 원소에 f를 적용해야 나오므로 본질적으로 순차다. 크기를 모르므로(SIZED=false) 추정값은 Long.MAX_VALUE이고, 떼어 낸 쪽의 추정값도 그 절반이라는 의미 없는 수다. 실제로 떼어 낸 것은 원소 1024개를 복사한 배열이다. 이 분할을 구현한 Spliterators.AbstractSpliterator의 주석은 등차적으로 커지는 배치로 쪼개며, 원소당 동작이 배열로 옮기는 비용보다 클 때만 병렬 성능이 좋아진다고 밝힌다. 같은 수열이라도 IntStream.range로 표현할 수 있다면 그쪽이 병렬에 훨씬 유리하다.

    원소당 비용과 박싱을 따진다

    병렬화에는 고정 비용이 있다. 분할, 작업 객체 생성, 큐에 넣고 훔치기, 스레드 깨우기, 결과 결합이다. 원소당 작업이 아주 가볍고(정수 덧셈처럼) 원소 수도 적으면 이 고정 비용이 계산 자체보다 크다. ForkJoinTask Javadoc의 "작업 하나당 기본 단계 100~10,000개"라는 경험 규칙이 같은 이야기다. Stream로 박싱된 값을 다루면 원소마다 객체를 만들고 참조를 따라가는 비용이 더해지므로(2회에서 본 기본형 특화의 이유), 수치 계산은 IntStream, LongStream, DoubleStream으로 하는 것이 순차든 병렬이든 유리하다.

    결국 병렬이 이득인지는 측정해야 안다. 측정할 때는 JIT 컴파일 전의 첫 실행이 느리다는 점, 공용 풀 스레드가 처음에는 아직 만들어지지 않았다는 점을 고려해 충분히 예열한 뒤 재야 한다. 이 회차의 System.currentTimeMillis() 측정은 구조를 보기 위한 것이지 성능 비교용이 아니다. 정밀한 비교에는 OpenJDK의 JMH 같은 마이크로벤치마크 도구를 쓴다.

    거짓 공유: 나눠 쓰지 않는 변수도 캐시 라인은 나눠 쓴다

    앞 절의 첫 규칙은 "가변 상태를 공유하지 않는다"였다. 그런데 코드에서 아무것도 공유하지 않아도 하드웨어 수준에서는 공유가 일어날 수 있다. 병렬 계산을 손으로 짤 때 흔한 모양이 "스레드마다 배열의 자기 칸에 부분 결과를 쌓고, 마지막에 칸들을 더한다"이다. 칸이 서로 다르니 데이터 경쟁은 없고 결과도 정확하다. 그런데 느릴 수 있다.

    import java.util.concurrent.atomic.AtomicLongArray;

public class FalseSharing {
    static final int THREADS = 4;
    static final long N = 50_000_000L;

    static long run(int stride) throws InterruptedException {
        AtomicLongArray counters = new AtomicLongArray(THREADS * stride);
        Thread[] ts = new Thread[THREADS];
        long start = System.nanoTime();
        for (int t = 0; t < THREADS; t++) {
            int idx = t * stride;                       // 스레드마다 자기 칸만 쓴다
            ts[t] = new Thread(() -> { for (long i = 0; i < N; i++) counters.getAndIncrement(idx); });
            ts[t].start();
        }
        for (Thread th : ts) th.join();
        return (System.nanoTime() - start) / 1_000_000;
    }

    public static void main(String[] args) throws InterruptedException {
        for (int round = 1; round <= 3; round++)
            System.out.printf("round %d: stride 1 (8바이트 간격) = %dms, stride 16 (128바이트 간격) = %dms%n",
                    round, run(1), run(16));
    }
}
    round 1: stride 1 (8바이트 간격) = 5275ms, stride 16 (128바이트 간격) = 1090ms
round 2: stride 1 (8바이트 간격) = 3241ms, stride 16 (128바이트 간격) = 1017ms
round 3: stride 1 (8바이트 간격) = 4920ms, stride 16 (128바이트 간격) = 1048ms

    두 실행이 하는 일은 같다. 스레드 넷이 각자 자기 칸만 5천만 번씩 증가시킨다. 다른 것은 칸 사이의 거리뿐인데 시간이 3~5배 차이 났다. 원인은 CPU 캐시가 데이터를 변수 단위가 아니라 캐시 라인(cache line) 단위로 다룬다는 데 있다. 이 Mac은 sysctl hw.cachelinesize가 128이다. 8바이트짜리 칸 넷이 붙어 있으면 모두 32바이트이므로 한 캐시 라인, 경계에 걸쳐도 많아야 두 라인 안에 들어간다. 여러 코어가 각자 캐시를 가진 시스템은 캐시 일관성(cache coherence)을 지키기 위해, 한 코어가 어떤 라인에 쓰려면 다른 코어 캐시에 있는 그 라인의 사본을 무효화하고 그 라인을 독점해야 한다. 네 코어가 같은 라인의 서로 다른 칸에 번갈아 쓰면 라인의 소유권이 코어 사이를 계속 오가고, 증가 연산 하나하나가 자기 캐시에서 끝나지 못하고 다른 코어와의 통신을 기다린다. 칸을 16개(128바이트) 간격으로 벌리면 어느 두 칸도 같은 128바이트 라인에 들어갈 수 없으므로 이 왕복이 사라진다. 프로그램은 아무것도 공유하지 않는데 캐시 라인이 공유되는 이 현상을 거짓 공유(false sharing)라고 한다.

    ForkJoinPool 자신의 방어: @Contended

    포크/조인 프레임워크는 이 문제를 정면으로 겪는 코드다. 작업자 큐의 top은 주인이 push/pop할 때마다 바뀌고, base는 도둑이 훔칠 때마다 바뀐다. 두 필드가 한 캐시 라인에 있으면 주인과 도둑이 덱의 서로 다른 끝을 쓰게 한 설계가 캐시 수준에서 무너진다. OpenJDK 21 ForkJoinPool의 구현 개요 중 "Memory placement" 부분은 거짓 공유로 인한 캐시 미스와 경쟁 때문에 일부 프로그램이 4배 넘게 느려지는 것이 관찰되었다고 적고, 그래서 ctl과 거짓 공유 미스를 가장 많이 일으키는 WorkQueue 필드들을 따로 떼어 둔다고 설명한다. 그 수단이 JDK 내부 애너테이션 @jdk.internal.vm.annotation.Contended다. WorkQueue의 top, access, phase, source, nsteals 다섯 필드에 같은 그룹 이름 "w"가, ForkJoinPool의 ctl과 parallelism에 그룹 "fjpctl"이 붙어 있다. 실제 배치를 sun.misc.Unsafe.objectFieldOffset으로 읽어 보았다(OpenJDK 21 HotSpot, 압축 참조가 켜진 이 실험 환경 기준).

    owner가 끝나는 32바이트와 top이 시작하는 160바이트 사이가 정확히 128바이트 비어 있다. HotSpot 플래그 ContendedPaddingWidth의 기본값 128만큼 채움(padding)을 넣은 것이다. 같은 그룹의 다섯 필드는 서로 붙어 있고, 도둑이 읽고 쓰는 base, array와는 128바이트 이상 떨어져 있으므로 이 환경의 캐시 라인 하나에 함께 들어갈 수 없다. 풀의 ctl도 마찬가지로 다른 필드들과 떨어져 있다. 이 애너테이션을 애플리케이션 클래스에 붙여도 기본 설정에서는 효과가 없다. HotSpot의 클래스 파일 파서(classFileParser.cpp)는 RestrictContended(기본 true)가 켜져 있으면 부트 또는 플랫폼 클래스 로더가 읽은 클래스처럼 VM 내부 애너테이션이 허용된 클래스에서만 이 애너테이션을 인정하고, 나머지 클래스에서는 조용히 무시한다.

    애플리케이션 코드가 가져갈 교훈은 간단하다. 반복문 안에서는 지역 변수에 누적하고, 공유 구조에는 끝날 때 한 번만 쓴다. 지역 변수는 스레드마다 따로 있는 스택이나 레지스터에 있으므로 다른 코어와 캐시 라인을 다툴 일이 없다. 병렬 스트림의 reduce와 collect가 잎마다 doLeaf()에서 자기 Sink를 새로 만들어 누적하고 결과를 트리로 결합하는 것도, 모든 스레드가 함께 쓰는 카운터 배열을 두지 않는다는 점에서 같은 방향이다. 경쟁이 심한 카운터라면 java.util.concurrent.atomic.LongAdder가 있다. 경쟁이 생기면 값을 여러 셀에 나누어 누적하는 클래스인데, 그 셀 클래스인 Striped64.Cell에도 @Contended가 붙어 있다.

    정리: 병렬 스트림을 켜기 전에

    이 회차는 같은 계산을 다섯 가지 방식으로 실행했다. 단일 스트림은 main 하나로 800ms를 썼다. 스레드를 직접 쓰면 시간은 줄었지만 나누기, 결과 전달, 예외, 스레드 생성을 모두 손으로 해야 했다. 스레드 풀은 재사용과 Future를 주었지만 재귀 분할에서는 기다리는 스레드가 풀을 막아 교착에 빠졌다. 포크/조인은 기다리는 스레드가 자기 덱의 작업을 직접 실행하고 남의 덱에서 일을 훔쳐 오게 해서 이 문제를 풀었다. 병렬 스트림은 그 포크/조인 위에서 Spliterator를 쪼개고 잎마다 순차 파이프라인을 돌린 뒤 결과를 트리 모양대로 결합한다.

    병렬 스트림의 함정은 모두 이 구조에서 나온다. 기본 실행 장소가 JVM 전체가 공유하는 공용 풀이라서 블로킹 작업 하나가 무관한 기능을 느리게 한다. 람다가 여러 스레드에서 동시에, 아무 순서로 실행되므로 공유 가변 상태와 스레드에 묶인 문맥이 깨진다. 결과가 트리 모양으로 결합되므로 결합 법칙과 항등원이 필요하다. 분할은 소스에 달려 있으므로 쪼개지지 않는 소스는 병렬로 만들어도 빨라지지 않는다.

    이 장의 핵심

    병렬 스트림은 "스트림을 빠르게 만드는 스위치"가 아니라 "이 계산을 공용 포크/조인 풀에서 분할 정복으로 실행하라"는 지시다. 그 지시가 이득이 되려면 계산이 CPU 중심이고, 원소가 충분히 많고 비싸며, 소스가 잘 쪼개지고, 람다가 공유 상태 없이 결합 법칙을 지키고, 그 계산이 공용 풀을 잠시 독차지해도 되는 상황이어야 한다. 하나라도 어긋나면 순차 스트림이나 전용 실행기가 낫다.

    다음 11회에서는 함수형 프로그래밍을 정리한다. 이 회차의 조건들, 즉 상태 없는 람다, 부수 효과 없음, 결합 법칙을 지키는 결합은 우연히 모인 규칙이 아니다. 같은 입력에 언제나 같은 출력을 내고 바깥을 바꾸지 않는 순수 함수와 불변 데이터가 왜 병렬 실행을 안전하게 만드는지를 거기서 원리로 묶는다.
    스레드 기아 교착(thread starvation deadlock)
    고정 크기 풀의 작업이 같은 풀에 제출한 하위 작업을 Future.get()으로 기다리면, 모든 스레드가 기다리기만 하고 큐의 하위 작업을 실행할 스레드가 없어 영원히 멈춘다. 재귀 분할에 일반 스레드 풀이 맞지 않는 이유다.
    분할 정복과 임계값
    문제를 독립적인 하위 문제로 나누고(분할), 임계값 이하가 되면 직접 풀고(정복), 결과를 합친다(결합). 임계값이 너무 크면 코어가 놀고, 너무 작으면 작업 관리 비용이 계산을 넘어선다.
    fork / compute / join
    fork()는 현재 작업자의 덱(작업자가 아니면 공용 풀)에 작업을 넣고 바로 반환한다. 한쪽은 compute()로 직접 실행하고 다른 쪽은 join()으로 받는다. join()은 잠들기 전에 그 작업을 직접 실행하거나 훔쳐 간 작업자를 돕는다.
    작업 훔치기(work stealing)
    작업자마다 덱을 가지며, 주인은 top에서 넣고 빼고(LIFO), 일이 없는 작업자는 다른 덱의 base에서 가장 오래된 작업을 훔친다(FIFO). 재귀 분할에서는 base 쪽 작업이 가장 크므로 훔치는 횟수가 적고, 양쪽 끝을 나눠 쓰므로 경쟁도 적다.
    공용 풀(common pool)
    JVM에 하나 있는 정적 ForkJoinPool. 기본 병렬성은 max(1, availableProcessors() - 1)이며, fork한 호출 스레드가 함께 일하기 때문에 하나를 뺀다. 병렬 스트림, CompletableFuture 기본 비동기 실행, Arrays.parallelSort가 함께 쓴다.
    병렬 스트림의 실행 경로
    parallel()은 소스 단계의 깃발만 세운다. 최종 연산이 ReduceTask 같은 CountedCompleter를 만들어 호출 스레드에서 invoke()하고, Spliterator를 쪼개며 fork하며, 잎은 순차 파이프라인을 돌리고, 결과는 트리 모양대로 결합된다.
    잎 목표 수
    OpenJDK 21은 병렬성의 4배만큼 잎을 만들도록 임계값(루트 크기 / (병렬성 × 4), 최소 1)을 정한다. 고르지 않은 잎이나 바쁜 코어가 있어도 다른 작업자가 도울 수 있게 일부러 과분할한다.
    공유 풀의 블로킹
    블로킹 I/O나 관리되지 않는 동기화는 보상 스레드를 부르지 않는다. 공용 풀 작업자가 대기로 묶이면 무관한 기능의 병렬 작업까지 함께 느려진다. 기다리는 작업은 크기를 맞춘 전용 ExecutorService로 보낸다.
    작업자의 잠과 회수
    OpenJDK 21에서 일이 없는 작업자는 ctl의 대기 스택에 올라가 잠깐 스핀한 뒤 LockSupport.park로 잠든다(HotSpot Parker::park → pthread_cond_wait). 마지막으로 잠든 하나만 keepAlive(공용 풀 60초) 기한을 두고 자므로 작업자는 keepAlive마다 하나씩 종료된다.
    availableProcessors의 출처
    HotSpot의 os::active_processor_count()가 -XX:ActiveProcessorCount, macOS의 hw.ncpu, Linux의 CPU 친화도와 cgroup CPU 쿼터에서 구한다. 공용 풀 병렬성과 병렬 스트림의 잎 목표 수는 클래스 초기화 때 한 번 굳는다.
    행동 매개변수의 조건
    병렬에서 결과가 바뀌지 않으려면 람다가 간섭하지 않고 상태가 없어야 하며, reduce의 초깃값은 진짜 항등원, 누산 함수는 결합 법칙을 만족해야 한다. 순서가 필요하면 그 비용(forEachOrdered, 순서 있는 limit)을 감수한다.

    병렬 스트림과 관련된 장애는 대개 "평소엔 멀쩡하다가 트래픽이 몰리면 전혀 관련 없는 API까지 느려지는" 모습으로 나타난다. 스레드 덤프에서 ForkJoinPool.commonPool-worker 스레드들이 소켓 읽기나 sleep, 락 대기에 모여 있다면 공용 풀이 블로킹 작업에 묶인 것이다. 원인을 찾으면 그 병렬 스트림을 순차로 되돌리거나, 블로킹 호출을 크기를 정한 전용 실행기로 옮긴다. Executor 없이 호출한 CompletableFuture.supplyAsync도 같은 풀을 쓰므로 함께 점검한다. 같은 이유로, 코드 리뷰에서 서버 코드의 parallelStream()을 보면 그 안에 I/O가 있는지, 이 계산이 공용 풀을 잠시 독차지해도 되는지부터 묻는 습관을 들이면 좋다.

    데이터 정합성 문제는 더 조용히 나타난다. @Transactional 메서드 안의 병렬 스트림에서 저장한 데이터 일부만 롤백되지 않거나, 병렬 forEach로 채운 리스트의 개수가 가끔 모자라거나, reduce 결과가 개발자 노트북과 운영 서버에서 다르게 나오는 식이다. 마지막 경우는 잎의 개수가 병렬성에 따라 달라지기 때문이다. 코어 수가 다른 환경에서만 재현되는 버그를 만나면 항등원과 결합 법칙을 먼저 의심한다.

    판단이 달라지는 조건도 분명히 하자. 배치 작업처럼 한 JVM에서 그 계산 하나만 돌고, 원소가 많고 원소당 계산이 무거우며, 소스가 배열이나 ArrayList이고, 람다가 순수하다면 병렬 스트림은 코드 한 줄로 코어를 모두 쓰게 해 주는 좋은 도구다. 반대로 서버의 요청 처리 경로라면 요청 자체가 이미 병렬이므로 기본값은 순차 스트림으로 두고, 측정으로 이득이 확인된 경우에만 전용 풀과 함께 병렬을 쓴다. availableProcessors()가 2 이하인 환경에서는 공용 풀의 병렬성이 1로 내려가고, 그러면 CompletableFuture의 기본 실행 방식까지 바뀐다는 점도 기억해 둔다.

(나)에서는 두 줄 모두 공용 풀 작업자가 찍고 main은 결과만 찍는다. pool.invoke(task)는 작업을 풀에 제출하고 기다리는데, OpenJDK는 ExecutorService 규약 때문에 제출된 작업에는 호출자 돕기를 적용하지 않는다. 그래서 작업자 하나가 루트를 가져가 분할하고 5~8을 직접 처리하며, 다른 작업자가 1~4를 훔친다.

    2번. 공용 풀 병렬성은 8-1 = 7, main은 작업자가 아니므로 잎 목표 수는 7×4 = 28이다. 임계값은 1,000,000 / 28 = 35,714(정수 나눗셈)다. 범위 Spliterator는 2^24 미만이면 반으로 쪼개므로 500,000 → 250,000 → 125,000 → 62,500 → 31,250으로 내려가고, 31,250 ≤ 35,714에서 멈춘다. 잎은 2^5 = 32개, 각 31,250개다. 병렬성을 3으로 주면 잎 목표 수 12, 임계값 83,333이므로 62,500에서 멈춰 잎 16개, 각 62,500개다. new ForkJoinPool(4)에 제출하면 람다가 그 풀의 작업자에서 실행되므로 getLeafTarget()이 그 풀의 병렬성 4를 써서 잎 목표 수 16, 임계값 62,500이 되고, 역시 62,500개짜리 잎 16개가 된다. 이때 공용 풀은 쓰이지 않는다.

    3번. 세 가지 문제가 있다. (1) 블로킹 I/O를 공용 풀에서 한다. externalApi.fetch가 응답을 기다리는 동안 공용 풀 작업자가 묶이고, 풀은 이를 보상하지 않으므로 같은 JVM의 다른 병렬 스트림과 기본 CompletableFuture 작업까지 느려진다. (2) 트랜잭션이 일부에만 적용된다. 스프링은 트랜잭션 리소스를 스레드별로 관리하므로 공용 풀 작업자에서 실행된 save는 이 트랜잭션에 참여하지 않는다. 호출 스레드도 잎 일부를 처리하므로 일부 원소만 트랜잭션 안에서 저장되고, 어느 원소인지는 실행마다 다르다. 예외가 나서 롤백되어도 작업자에서 저장한 것은 남을 수 있다. (3) forEach의 실행 순서가 없으므로 저장 순서에 의존하는 로직이 있다면 깨진다. 고치려면 외부 API 호출은 크기를 정한 전용 실행기로 먼저 "모두 제출한 뒤 모두 기다려" 결과를 모으고, 저장은 트랜잭션 스레드에서 순차로 한다.

    4번. OpenJDK 21의 LinkedList Spliterator는 앞에서부터 원소를 배열에 복사해 떼어 내며, 크기는 1024부터 호출마다 1024씩 늘어난다. 실측 결과는 1번째 (1024, 8976), 2번째 (2048, 6928), 3번째 (3072, 3856), 4번째에는 남은 3856개를 모두 떼어 내 (3856, 0)이다. 분할할 때마다 노드를 순차로 따라가며 복사해야 하고 나뉜 두 쪽의 크기가 고르지 않으므로, 분할 트리가 한쪽으로 치우친다. ArrayList는 인덱스 계산 한 번으로 (5000, 5000)처럼 정확히 반을 나누므로 균형 잡힌 이진 트리가 되고, 분할 비용도 거의 없다.

    5번. 내용 문제: 여러 스레드가 동기화 없이 ArrayList.add를 호출하므로 값이 사라지거나 ArrayIndexOutOfBoundsException이 날 수 있다(이 회차의 실험에서 10,000개 중 절반 안팎만 남았고, 200번 중 세 번 예외가 났다). 순서 문제: 운 좋게 모두 들어가도 forEach는 원소를 처리한 스레드가 그 자리에서 실행하므로 순서가 원래 순서와 다르다. 고친 코드는 List result = names.parallelStream().map(String::toUpperCase).toList();다. 컬렉터는 잎마다 따로 담고 트리 순서대로 결합하므로 공유 상태가 없고 만남 순서가 지켜진다.

     논리 프로세서 8개, 기본 설정인 JVM의 main에서 100ms씩 걸리는 원소 8개짜리 IntStream.rangeClosed(1, 8).parallel().map(...).sum()을 실행한다. 이 계산을 동시에 실행할 수 있는 스레드는 최대 몇 개이고, 그 이유는? 7개. 공용 풀의 병렬성이 availableProcessors() - 1이기 때문이다. 8개. 공용 풀 작업자 7개에 더해, 최종 연산을 호출한 main이 루트 작업을 직접 실행하며 함께 일하기 때문이다. 16개. 공용 풀은 코어당 두 개의 스레드를 만든다. 1개. IntStream.rangeClosed는 순차 스트림을 만들므로 parallel()이 무시된다. 병렬 스트림의 최종 연산은 ReduceTask.invoke()를 호출 스레드에서 실행하므로 main도 잎을 처리한다. 공용 풀 병렬성 7은 바로 이 호출자 참여를 고려해 하나를 뺀 값이다. 16개라는 규칙은 없고, rangeClosed가 순차 스트림을 만들어도 parallel()이 소스 단계의 깃발을 바꾸므로 병렬로 실행된다. Executors.newFixedThreadPool(2)에서 작업이 하위 작업 두 개를 같은 풀에 submit하고 get()으로 기다리는 재귀 합계가 끝나지 않았다. 같은 계산을 new ForkJoinPool(2)와 fork/join으로 바꾸자 끝났다. 차이를 가장 정확히 설명한 것은? ForkJoinPool은 작업이 막히면 즉시 스레드를 무제한으로 추가하기 때문이다. ForkJoinPool의 스레드가 데몬 스레드라서 교착이 생기지 않는다. join()은 무작정 잠들지 않고 기다리는 작업이 자기 덱에 있으면 직접 실행하며, 도둑맞았으면 훔쳐 간 작업자를 거든다. 그래서 기다리는 스레드가 하위 작업을 실행할 수 있다. ForkJoinPool은 작업을 LIFO로 처리하므로 교착이 원리적으로 불가능하다. Future.get()은 스레드를 잡은 채 잠들기 때문에 큐의 하위 작업을 실행할 스레드가 남지 않는다. join()은 tryRemoveAndExec와 helpJoin으로 기다리는 대상을 직접 실행하거나 도우므로 같은 스레드 수로도 끝난다. 보상 스레드는 "명백한 굶주림"일 때만 제한적으로 추가되며 무제한이 아니다. 데몬 여부는 JVM 종료와 관련이 있을 뿐 교착과 무관하고, LIFO 순서만으로 교착이 막히는 것도 아니다(join 대상이 순환하면 포크/조인도 교착할 수 있어 Javadoc은 의존 관계가 DAG일 때만 join이 적절하다고 한다). 작업 훔치기에서 일이 없는 작업자가 다른 작업자의 덱 base 쪽(가장 오래된 작업)에서 훔치는 이유로 옳은 것은? 재귀 분할에서는 일찍 fork된 base 쪽 작업이 큰 덩어리라 한 번 훔쳐 오면 오래 일할 수 있고, 주인이 쓰는 top 쪽과 반대 끝이라 경쟁이 줄기 때문이다. 가장 오래된 작업일수록 CPU 캐시에 남아 있을 가능성이 높아 훔친 작업자가 빨리 처리할 수 있기 때문이다. base 쪽 작업은 이미 실행이 시작된 작업이라 이어서 실행하기만 하면 되기 때문이다. 자바 언어 명세가 작업 훔치기를 FIFO로 하도록 정하고 있기 때문이다. 주인은 최근에 fork한 작고 데이터가 가까운 작업을 top에서 꺼내고, 도둑은 오래된 큰 작업을 base에서 가져간다. 그래서 훔치는 횟수가 적고 주인과 도둑의 경쟁은 작업이 하나 남았을 때만 생긴다. 캐시 지역성은 오히려 최근 작업(top) 쪽의 이점이고, 덱에 있는 작업은 아직 시작되지 않은 작업이다. 이 규칙은 JLS가 아니라 ForkJoinPool 구현의 설계다. 원소 8개가 잎 8개로 나뉘는 기계에서 IntStream.rangeClosed(1, 8).parallel().reduce(10, Integer::sum)의 결과는 116, 순차 실행은 46이었다. 원인으로 옳은 것은? 병렬 실행에서 덧셈의 순서가 바뀌었기 때문이다. 정수 덧셈은 순서에 따라 결과가 달라진다. 공유 변수에 대한 데이터 경쟁 때문에 일부 덧셈이 두 번 실행되었다. Integer::sum은 박싱을 일으키므로 병렬에서 쓸 수 없다. 병렬 리듀스는 잎마다 identity에서 출발하는데 10은 덧셈의 항등원이 아니어서, 잎 수만큼 10이 더해졌다. reduce의 Javadoc은 identity가 누산 함수의 항등원이어야 한다고 요구한다. 병렬 실행은 잎마다 identity로 시작하므로 36 + 10×8 = 116이 된다. 정수 덧셈은 (오버플로가 있어도 2의 보수 산술에서) 결합 법칙과 교환 법칙을 만족하고, 리듀스에는 공유 변수가 없으며, IntStream.reduce의 Integer::sum은 IntBinaryOperator로 쓰여 박싱이 없다. 다음 코드는 어떻게 실행되는가? list.stream().parallel().filter(x -> x > 0).sequential().map(x -> x * 2).toList() filter까지는 병렬로, map부터는 순차로 실행된다. 파이프라인 전체가 순차로 실행된다. 파이프라인 전체가 병렬로 실행된다. 한 번 parallel()이 불리면 되돌릴 수 없다. IllegalStateException이 난다. 같은 파이프라인에서 모드를 두 번 바꿀 수 없다. parallel()과 sequential()은 소스 단계 하나의 깃발을 바꿀 뿐이고, 패키지 문서는 가장 마지막 설정이 파이프라인 전체의 실행에 적용된다고 정한다. 이 회차의 실험에서도 parallel() 뒤에 sequential()을 부른 스트림의 isParallel()은 false였다. 구간마다 모드를 다르게 하는 방법은 없고, 모드를 바꾸는 것 자체는 예외를 일으키지 않는다.
    포크/조인 프레임워크(Fork/Join framework)
    자바 7에 추가된 java.util.concurrent의 분할 정복 실행 틀. ForkJoinPool, ForkJoinTask, RecursiveTask, RecursiveAction, CountedCompleter로 이루어진다.
    작업 훔치기(work stealing)
    작업자마다 자기 작업 큐를 두고, 자기 큐가 빈 작업자가 다른 작업자의 큐에서 작업을 가져와 실행하는 스케줄링 방식. 생산자가 놀고 있는 스레드에 작업을 배정하는 방식과 대비된다.
    덱(deque, double-ended queue)
    양쪽 끝에서 넣고 뺄 수 있는 큐. ForkJoinPool의 WorkQueue는 주인이 top에서 push/pop, 다른 스레드가 base에서 poll하는 세 연산만 지원한다.
    공용 풀(common pool)
    ForkJoinPool.commonPool()이 돌려주는 JVM 전역의 정적 풀. 명시적인 풀 없이 실행되는 ForkJoinTask, 병렬 스트림, CompletableFuture의 기본 비동기 실행이 쓴다.
    병렬성(parallelism)
    ForkJoinPool이 목표로 유지하려는 활성 작업자 스레드 수. 일반 풀의 기본값은 availableProcessors(), 공용 풀은 OpenJDK 21에서 max(1, availableProcessors() - 1)이다.
    임계값(threshold)
    분할 정복에서 더 나누지 않고 직접 계산하기로 정한 문제 크기. 병렬 스트림에서는 OpenJDK가 루트 크기와 병렬성으로 자동 계산한다.
    Spliterator.trySplit
    소스의 원소 일부를 떼어 새 Spliterator로 돌려주는 메서드. 병렬 스트림의 분할 품질은 이 메서드가 얼마나 싸고 고르게 나누는지에 달려 있다.
    CountedCompleter
    대기 중인 하위 작업 수를 세다가 모두 끝나면 완료 동작(onCompletion)을 실행하고 부모에게 완료를 전파하는 ForkJoinTask. join으로 블로킹하지 않으며 병렬 스트림의 내부 작업이 이를 상속한다.
    ManagedBlocker
    ForkJoinPool 안에서 블로킹할 때 풀에 이를 알려 보상 스레드로 병렬성을 유지하게 하는 인터페이스. ForkJoinPool.managedBlock으로 사용한다.
    거짓 공유(false sharing)
    서로 다른 스레드가 서로 다른 변수에 쓰지만 그 변수들이 같은 캐시 라인에 있어, 캐시 일관성 때문에 라인의 소유권이 코어 사이를 오가며 느려지는 현상. ForkJoinPool은 @Contended 채움으로 이를 피한다.
    스레드 기아 교착(thread starvation deadlock)
    풀의 스레드가 모두 같은 풀에 제출된 작업의 완료를 기다리느라 그 작업을 실행할 스레드가 남지 않아 진행이 멈추는 상태.
