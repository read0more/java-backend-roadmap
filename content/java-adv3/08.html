    이 회차의 질문: "값이 없음"을 누가 알려 주는가

    회원 번호로 회원을 찾는 메서드 Member findMember(long id)가 있다고 하자. 해당 번호의 회원이 없으면 이 메서드는 무엇을 돌려줘야 할까. 자바에서 가장 오래된 답은 null이다. 문제는 시그니처 어디에도 "null이 나올 수 있다"는 정보가 없다는 점이다. 호출하는 쪽은 문서를 읽거나 구현을 열어 보거나, 아니면 운영 중에 NullPointerException을 만나고 나서야 그 사실을 안다. 컴파일러는 아무것도 경고하지 않는다. 같은 시그니처를 가진 메서드라도 어떤 것은 절대 null을 돌려주지 않고, 어떤 것은 자주 돌려준다.

    자바 8은 이 정보를 타입에 싣는 도구로 java.util.Optional을 들여왔다. 반환 타입이 Optional라면 시그니처만 보고도 "결과가 없을 수 있다"는 사실을 알고, 값을 꺼내려면 "없을 때 무엇을 할지"를 반드시 코드로 적어야 한다. 이 회차는 먼저 null이 왜 문제가 되는지를 언어 명세와 JVM 수준에서 확인하고, Optional의 소스 코드를 한 줄씩 읽으며 생성·값 획득·값 처리 메서드가 실제로 무엇을 하는지 본다.

    후반부의 중심은 즉시 평가(eager evaluation)와 지연 평가(lazy evaluation)다. orElse와 orElseGet은 겉보기에 거의 같지만, 자바가 메서드 인자를 언제 계산하는지라는 언어 규칙 때문에 전혀 다르게 동작한다. 이 차이는 Optional만의 이야기가 아니라 로그 출력, 예외 생성, 캐시 조회, 그리고 5회에서 본 스트림의 지연 실행과 같은 뿌리를 가진다. 마지막으로 Optional 객체가 메모리에서 차지하는 크기, HotSpot JIT가 그 할당을 없애는 조건, 그리고 값 기반 클래스(value-based class)라는 지위에서 나오는 사용 규칙을 정리한다.

    이 장의 핵심

    Optional은 참조 하나를 감싼 불변 객체이고, 감싼 참조가 null이면 "비어 있음"으로 취급한다. 그 가치는 성능이 아니라 타입으로 남기는 약속에 있다. 반환 타입이 Optional이면 호출자는 값을 꺼내기 전에 빈 경우를 처리하는 코드를 써야 한다. 그 처리 코드에 값을 넘길지(orElse) 코드를 넘길지(orElseGet)는 자바의 인자 평가 규칙 때문에 실행 결과를 바꾼다. 자바는 메서드를 부르기 전에 인자를 모두 계산하므로, "필요할 때만 계산"하려면 계산 자체를 Supplier 객체로 감싸 넘겨야 한다.

    null은 모든 참조 타입의 값이다

    먼저 null이 타입 체계에서 어떤 자리에 있는지 보자. 자바 언어 명세(JLS) §4.1은 기본형과 참조형 말고 "특별한 null 타입(null type)"이 있다고 정의한다. 이 타입은 이름이 없어서 변수를 선언할 수 없고, 그 타입의 값은 null 참조 하나뿐이다. 그리고 null 참조는 언제나 어떤 참조 타입으로든 대입하거나 캐스팅할 수 있다. §4.10.2는 같은 사실을 하위 타입 관계로 적는다. null 타입의 직접 상위 타입은 null 타입 자신을 뺀 모든 참조 타입이다. 즉 String, Member, List 같은 어떤 참조 타입이든 그 값의 집합에 null이 들어 있다.

    이것이 null 문제의 뿌리다. 타입이 "이 변수에는 회원이 들어 있다"고 말해도, 언어 규칙상 그 변수에는 언제든 "아무것도 아님"이 들어갈 수 있다. 컴파일러는 member.address()라는 호출을 보고 member가 null일지 판단하지 않는다. 판단할 정보가 타입에 없기 때문이다. 그래서 null 검사는 전적으로 사람의 기억과 문서에 맡겨진다. 메서드 수백 개가 서로를 부르는 시스템에서 "이 반환값이 null일 수 있는가"를 모두 기억하는 것은 불가능에 가깝다.

    런타임에서는 JVM이 null을 만난 순간 예외를 던진다. 자바 가상 머신 명세(JVMS)는 invokevirtual, getfield, arraylength 같은 명령어마다 "대상 참조가 null이면 NullPointerException을 던진다"고 정해 둔다. JLS §15.12.4.4도 인스턴스 메서드 호출에서 대상 참조가 null이면 그 시점에 NPE가 발생한다고 적는다. 중요한 것은 예외가 null이 처음 생긴 곳이 아니라 처음 사용된 곳에서 터진다는 점이다. 회원 조회 메서드가 null을 돌려준 곳과, 그 값이 서너 단계 전달된 뒤 메서드 호출에 쓰여 터진 곳은 전혀 다른 파일일 수 있다.

    Helpful NullPointerException: JVM이 알려 주는 것

    예전 NPE는 스택 트레이스의 줄 번호만 알려 줬다. 한 줄에 a.b().c().d()처럼 호출이 이어져 있으면 그중 무엇이 null이었는지 알 수 없었다. JEP 358(Helpful NullPointerExceptions)은 JVM이 예외가 난 바이트코드를 분석해 "무엇이 null이었는지"를 메시지에 넣도록 했다. JEP 문서에 따르면 이 기능은 JDK 14에 들어왔고 처음에는 -XX:+ShowCodeDetailsInExceptionMessages 옵션을 켜야 했으며, JDK 15 릴리스 노트에 따라 JDK 15부터 기본으로 켜져 있다. 직접 확인해 보자.

    public class Npe {
    record Address(String city) {}
    record Member(String name, Address address) {}

    static String cityOf(Member member) {
        return member.address().city().toUpperCase();
    }

    public static void main(String[] args) {
        Member m = new Member("kim", null);
        System.out.println(cityOf(m));
    }
}
    Exception in thread "main" java.lang.NullPointerException: Cannot invoke "Npe$Address.city()" because the return value of "Npe$Member.address()" is null
	at Npe.cityOf(Npe.java:6)
	at Npe.main(Npe.java:11)

    메시지는 "Member.address()의 반환값이 null이어서 Address.city()를 호출할 수 없다"고 정확히 짚는다. JEP 358의 설명에 따르면 JVM은 메서드의 바이트코드에 간단한 데이터 흐름 분석을 수행해, 예외가 난 invokevirtual이 꺼낸 피연산자 스택 슬롯에 null을 올린 명령이 무엇인지 찾아내고 그것을 소스 코드 표현으로 바꿔 적는다. 지역 변수가 null인 경우에는 조금 다르다. String city = null; city.length(); 같은 코드를 그냥 javac로 컴파일하면 메시지가 because "" is null처럼 슬롯 번호로 나오고, javac -g로 디버그 정보(LocalVariableTable)를 넣어 컴파일해야 because "city" is null처럼 이름이 나온다. JEP 358도 클래스 파일에 디버그 정보가 있을 때만 지역 변수 이름이 출력된다고 밝힌다. -XX:-ShowCodeDetailsInExceptionMessages로 끄면 메시지 없이 예외 이름만 나온다.

    Helpful NPE는 "어디서 터졌는지"를 잘 알려 주지만 "왜 null이 거기까지 왔는지"는 알려 주지 않는다. address()가 null을 돌려준 것이 버그인지, 원래 주소 없는 회원이 있을 수 있는데 호출자가 그 경우를 잊은 것인지는 메시지만으로 알 수 없다. 이 판단에 필요한 정보, 곧 "이 값은 없을 수 있다"는 설계 의도를 코드에 남기는 것이 Optional의 역할이다.

    null 검사로 버티는 코드의 모양

    null을 반환하는 API를 안전하게 쓰려면 사용하는 쪽이 매 단계 검사해야 한다. 회원 → 주소 → 도시를 따라가는 코드는 이렇게 된다.

    static String cityByNullCheck(long id) {
    Member member = members.get(id);          // 없으면 null
    if (member != null) {
        Address address = member.address();  // 주소 미등록이면 null
        if (address != null) {
            String city = address.city();     // 도시 미입력이면 null
            if (city != null) {
                return city;
            }
        }
    }
    return "미등록";
}

    이 코드는 정확하지만 두 가지 약점이 있다. 첫째, 본래 하려던 일(회원의 도시를 얻는다)이 세 겹의 if 안에 묻힌다. 둘째, 검사를 하나 빠뜨려도 컴파일러가 잡아 주지 않는다. 어느 단계가 null을 돌려줄 수 있는지는 여전히 사람이 알아야 한다. 뒤에서 이 코드를 Optional로 다시 쓰면 "단계마다 값이 없을 수 있고, 하나라도 없으면 기본값"이라는 의미가 한 줄짜리 파이프라인으로 바뀐다.

    일상에서 가져온 비유송장이 붙은 상자

    택배 상자에 아무 표시가 없으면 받는 사람은 열어 보기 전까지 안에 물건이 있는지 모른다. 빈 상자를 그대로 다음 사람에게 넘기면 결국 누군가 물건을 쓰려는 순간에야 비어 있음을 알게 된다(NPE). Optional은 상자 겉에 "내용물이 없을 수도 있음"이라는 표시를 붙이고, 상자를 여는 방법도 "없으면 이것을 대신 써라", "없으면 반품하라"처럼 정해진 몇 가지로 제한한다. 다만 비유가 깨지는 지점도 있다. 상자 자체(Optional 참조)가 null이면 표시가 아무 소용이 없다. 그래서 Optional 타입의 변수는 절대 null이어서는 안 된다는 규칙이 따로 붙는다.

    한 층 아래: HotSpot은 null을 어떻게 발견하고 NPE를 만드는가

    JVMS는 getfield나 invokevirtual의 대상 참조가 null이면 NPE를 던진다고 결과만 정한다. null을 어떻게 알아낼지, 예외 객체를 언제 만들고 메시지를 언제 채울지는 구현이 정한다. 이 절은 OpenJDK 21 HotSpot의 소스(github.com/openjdk/jdk21u)와 JDK 21 실험으로 그 경로를 따라간다. 결론은 세 가지다. 첫째, HotSpot은 null 검사의 상당 부분을 비교 명령 없이 운영체제의 메모리 보호에 맡긴다. 둘째, 앞에서 본 친절한 메시지는 예외가 생길 때가 아니라 누군가 getMessage()를 부를 때 계산된다. 셋째, 같은 자리에서 NPE가 자주 나면 JIT가 스택 트레이스도 메시지도 없는 공용 예외 객체를 던지기 시작한다. 셋 모두 운영 중인 서버의 로그를 읽을 때 직접 부딪히는 사실이다.

    암묵적 null 검사: 비교 명령 대신 페이지 폴트

    필드를 읽는 기계어는 "객체 주소 + 필드 오프셋"에서 값을 읽는다. 참조가 null이면 읽으려는 주소는 0에 아주 가까운 값이 된다. macOS와 리눅스는 주소 0이 들어 있는 페이지를 프로세스에 매핑하지 않으므로 그 접근은 CPU의 페이지 폴트가 되고, 커널은 해당 스레드에 SIGSEGV나 SIGBUS 신호를 보낸다. HotSpot은 이 신호를 스스로 처리한다. 신호는 signals_posix.cpp의 javaSignalHandler가 먼저 받아 JVM_HANDLE_XXX_SIGNAL로 넘기고, 여기서 플랫폼별 처리 함수를 부른다. 이 실험 환경(macOS, AArch64)에서 그 함수는 os_bsd_aarch64.cpp의 PosixSignals::pd_hotspot_signal_handler다. 이 함수는 폴트 주소가 null 검사로 쓰는 범위인지 MacroAssembler::uses_implicit_null_check로 확인하고, 맞으면 SharedRuntime::continuation_for_implicit_exception(thread, pc, IMPLICIT_NULL)로 "이어서 실행할 주소"를 얻는다. 폴트가 난 명령이 인터프리터 코드 안이면 인터프리터의 NPE 던지기 진입점(Interpreter::throw_NullPointerException_entry())이, JIT가 만든 컴파일된 메서드(nmethod) 안이면 그 메서드가 컴파일 때 기록해 둔 암묵적 예외 표(ImplicitExceptionTable)에서 찾은 주소가 돌아온다. 신호 처리기가 끝나면 스레드는 폴트가 난 명령의 다음 줄이 아니라 그 주소에서 실행을 이어 가며 NPE를 던진다.

    이 방식은 접근 주소가 매핑되지 않은 첫 페이지 안에 떨어질 때만 성립한다. assembler.cpp의 MacroAssembler::needs_explicit_null_check(offset)는 오프셋이 음수이거나 페이지 크기 이상이면 명시적 검사가 필요하다고 판단한다. C2는 이 판단에 따라 비교 명령을 그대로 남기고(lcm.cpp의 PhaseCFG::implicit_null_check), 인터프리터와 C1이 쓰는 MacroAssembler::null_check는 비교 대신 주소 "참조 + 0"을 한 번 더 읽어 폴트를 일부러 일으킨다. 이 Mac의 페이지 크기는 getconf PAGESIZE로 16384바이트이고, Optional의 value 필드 오프셋은 Unsafe.objectFieldOffset으로 재면 12다(12바이트 헤더 바로 뒤). C2는 여기에 프로파일을 더한다. graphKit.cpp의 GraphKit::null_check_common은 처음에 "null은 나오지 않는다"고 가정해 not-null 확률을 최대로 두는데, 소스 주석은 이것이 암묵적 null 검사를 만들게 하는 설정이라고 적는다. 그 지점에서 이미 null 트랩이 기록되었다면(또는 메서드 전체의 트랩 수가 문턱을 넘었다면) 확률을 낮춰 명시적 비교를 만든다. 정리하면, C2가 컴파일한 코드에서 null이 나온 적 없는 역참조에는 null 비교 명령조차 없을 수 있고, null 트랩이 기록된 지점에는 비교가 생긴다. JVMS가 정한 "null이면 NPE"라는 결과는 같지만, 그 결과에 이르는 기계 수준의 경로는 실행 이력에 따라 다르다.

    Helpful NPE 메시지는 물어볼 때 만들어진다

    JEP 358의 메시지는 바이트코드 분석으로 만들므로 공짜가 아니다. 그래서 JDK는 이것을 이 회차의 주제인 지연 평가로 처리한다. JDK 21의 NullPointerException.java를 열면 메시지용 필드 두 개와 이를 다루는 메서드가 있다(주석은 우리말로 옮기고 줄였다).

    // 0: 스택 미기록, 메시지 미계산 / 1: 스택 기록됨, 메시지 미계산 / 2: 메시지 계산됨
private transient int extendedMessageState;
private transient String extendedMessage;

public synchronized Throwable fillInStackTrace() {
    // 스택이 바뀌면 메시지 분석이 틀어지므로 덮어쓰기 전에 미리 계산한다
    if (extendedMessageState == 0) {
        extendedMessageState = 1;
    } else if (extendedMessageState == 1) {
        extendedMessage = getExtendedNPEMessage();
        extendedMessageState = 2;
    }
    return super.fillInStackTrace();
}

public String getMessage() {
    String message = super.getMessage();
    if (message == null) {
        synchronized(this) {
            if (extendedMessageState == 1) {
                extendedMessage = getExtendedNPEMessage();
                extendedMessageState = 2;
            }
            return extendedMessage;
        }
    }
    return message;
}

private native String getExtendedNPEMessage();

    예외가 생성될 때(Throwable 생성자가 fillInStackTrace()를 부를 때) 일어나는 일은 상태를 0에서 1로 바꾸는 것뿐이다. 메시지는 getMessage()가 처음 불릴 때 네이티브 메서드로 계산되어 필드에 저장되고, 그 뒤로는 저장된 값이 돌아온다. 뒤의 "즉시 평가와 지연 평가 3"에서 "자바에서는 직접 만들어야 한다"고 할 필요에 의한 호출(call by need)이 바로 이 모양이다. 처음 필요할 때 한 번 계산하고, 결과를 기억하고, 여러 스레드가 동시에 물어볼 수 있으므로 synchronized로 감싼다. 그 결과 잡아서 무시하거나 메시지를 읽지 않는 NPE는 분석 비용을 치르지 않는다.

    네이티브 쪽은 jvm.cpp의 JVM_GetExtendedNPEMessage다. 이 함수는 ShowCodeDetailsInExceptionMessages가 꺼져 있으면 바로 null을 돌려주고, 아니면 예외 객체에 기록된 백트레이스에서 맨 위 메서드와 바이트코드 위치(bci)를 꺼낸다(java_lang_Throwable::get_top_method_and_bci). 꺼내지 못하거나 맨 위 메서드가 네이티브 메서드면 역시 null이다. 그다음 bytecodeUtils.cpp의 BytecodeUtils::get_NPE_message_at이 그 메서드의 바이트코드를 분석해 "Cannot invoke ... because ..." 문장을 만든다. 메시지의 재료가 백트레이스와 상태 필드라는 점이 다음 실험의 열쇠다.

    스택도 메시지도 없는 NPE: OmitStackTraceInFastThrow

    운영 서버 로그에 java.lang.NullPointerException 한 줄만 찍히고 스택 트레이스가 한 줄도 없는 경우가 있다. 다음 프로그램으로 재현할 수 있다. 같은 메서드에서 NPE를 계속 일으키면서, 스택이 빈 NPE가 처음 나오는 순간을 잡는다.

    public class FastThrow {
    record Box(String value) {}

    static int len(Box b) {
        return b.value().length();          // b가 null이면 NPE
    }

    public static void main(String[] args) {
        Box[] boxes = {new Box("ab"), null};
        NullPointerException first = null;
        for (int i = 0; i < 200_000; i++) {
            try {
                len(boxes[i % 2]);
            } catch (NullPointerException e) {
                if (first == null) {
                    first = e;
                    System.out.println("첫 NPE: i=" + i + ", 스택 깊이=" + e.getStackTrace().length
                            + ", 메시지=" + e.getMessage());
                }
                if (e.getStackTrace().length == 0) {
                    System.out.println("스택 없는 NPE: i=" + i + ", 메시지=" + e.getMessage());
                    NullPointerException again = null;
                    try { len(null); } catch (NullPointerException e2) { again = e2; }
                    System.out.println("다음 NPE와 같은 객체인가: " + (again == e));
                    return;
                }
            }
        }
        System.out.println("끝까지 스택이 있었다");
    }
}

스택 없는 NPE: i=5355, 메시지=null
다음 NPE와 같은 객체인가: true

첫 NPE: i=1, 스택 깊이=2, 메시지=Cannot invoke "FastThrow$Box.value()" because "" is null
끝까지 스택이 있었다

    처음 수천 번의 NPE는 정상이다(메시지의 은 -g 없이 컴파일해 매개변수 이름이 없어서 나온 것이다). 그러다 어느 순간 스택 깊이 0, 메시지 null인 NPE가 나오고, 그 뒤로 던져지는 NPE는 매번 같은 객체다. 그 순간은 실행마다 다르다. 세 번 실행했을 때 i=5355, 5407, 5361이었다. 원인은 C2다. graphKit.cpp의 GraphKit::builtin_throw는 null 검사 실패 경로를 만들 때, 이 지점의 예외가 "뜨겁다"고 판단하면(이 바이트코드에서 같은 이유의 트랩이 이미 기록되었거나 메서드 전체로 너무 많을 때, 또는 인라인 경로의 메서드에 예외 처리기가 있고 같은 이유의 트랩이 한 번 이상 기록되었을 때) 그리고 OmitStackTraceInFastThrow(기본값 true)가 켜져 있으면, 예외를 새로 만들지 않고 env()->NullPointerException_instance()가 돌려주는 미리 만들어 둔 예외 객체를 던지는 코드를 넣는다. 이때 그 객체의 메시지 필드(detailMessage)에 null을 쓰는 코드도 함께 넣는다. 같은 switch 문에서 ArithmeticException, ArrayIndexOutOfBoundsException, ClassCastException, ArrayStoreException도 같은 대우를 받는다. -XX:+UnlockDiagnosticVMOptions -XX:+LogCompilation으로 컴파일 로그를 남겨 보면, C2가 FastThrow.len을 컴파일한 작업 안에 요소가 찍혀 이 결정이 실제로 내려졌음을 확인할 수 있다.

    미리 만든 객체는 universe.cpp에서 VM이 시작할 때 allocate_instance로 할당만 한 것이다. 생성자가 실행되지 않았으므로 fillInStackTrace()도 불린 적이 없어 백트레이스가 비어 있고, extendedMessageState는 기본값 0 그대로다. 앞에서 본 getMessage()는 상태가 1일 때만 네이티브 분석을 부르므로 null을 돌려준다. Helpful NPE 메시지가 사라진 이유가 소스 두 곳으로 설명된다. 실무에서 스택 없는 NPE를 보면 두 가지를 한다. 같은 로그에서 더 이른 시각의 같은 예외를 찾는다. 위 실험의 첫 NPE처럼, JIT가 판단을 바꾸기 전의 예외에는 스택과 메시지가 온전히 있다. 그리고 재현 환경에서는 -XX:-OmitStackTraceInFastThrow로 이 최적화를 끄고 실행한다. 이 실험은 "값이 없을 수 있음"을 NPE와 catch로 처리하는 코드가 진단 정보까지 잃을 수 있다는 것도 보여 준다. 없을 수 있는 값은 예외가 아니라 타입과 분기로 다루라는 이 회차의 주장이 진단 측면에서도 근거를 하나 더 얻는다.

    Optional 해부: 필드 하나와 공유된 빈 객체

    Optional이 무엇인지는 소스 코드를 보면 가장 정확하다. JDK 설치 경로의 lib/src.zip에서 java.base/java/util/Optional.java를 열면(이 회차는 Temurin 21.0.13 기준) 상태를 이루는 부분은 이것이 전부다. 주석과 메서드 본문은 줄였다.

    @jdk.internal.ValueBased
public final class Optional {
    private static final Optional EMPTY = new Optional<>(null);

    private final T value;   // null이 아니면 값, null이면 "값 없음"

    private Optional(T value) {
        this.value = value;
    }

    public static  Optional of(T value) {
        return new Optional<>(Objects.requireNonNull(value));
    }

    public static  Optional ofNullable(T value) {
        return value == null ? (Optional) EMPTY
                             : new Optional<>(value);
    }

    public static  Optional empty() {
        return (Optional) EMPTY;
    }
    // ...
}

    읽을 거리가 몇 가지 있다. 첫째, 인스턴스 필드는 final T value 하나뿐이다. "값이 있음/없음"을 나타내는 별도의 boolean이 없고, value가 null인지로 판단한다. 그래서 Optional은 null을 값으로 담을 수 없다. "null이 들어 있는 Optional"과 "빈 Optional"을 구분할 방법이 구조적으로 없기 때문이다. Javadoc의 첫 문장도 "non-null 값을 담을 수도 있고 담지 않을 수도 있는 컨테이너 객체"라고 정의한다.

    둘째, 생성자가 private이고 클래스가 final이다. 외부에서는 정적 팩토리 메서드로만 만들 수 있고, 상속해서 동작을 바꿀 수도 없다. 필드가 final이고 값을 바꾸는 메서드가 없으므로 한 번 만든 Optional은 불변이다. map이나 filter는 기존 객체를 고치지 않고 새 Optional을 돌려주거나 자기 자신을 그대로 돌려준다.

    셋째, 빈 Optional은 클래스가 초기화될 때 한 번 만들어진 EMPTY 하나를 모두가 공유한다. empty()와 ofNullable(null)은 새 객체를 만들지 않고 이 정적 필드를 돌려준다. 제네릭 타입 인자는 컴파일 후 지워지므로(2회에서 본 타입 소거) Optional의 빈 값과 Optional의 빈 값이 같은 객체여도 런타임에는 아무 문제가 없다. 다만 Javadoc은 empty()에 대해 "싱글턴이라는 보장은 없으니 ==로 비교해 빈 값을 판정하지 말라"고 따로 적어 두었다. 현재 구현이 공유 객체를 쓰는 것과 API가 약속하는 것은 다르다.

"found" 칸에서 화살표가 힙의 상자 "Optional 객체"로 가고, 이 상자는 두 칸 "헤더 12바이트"와 "value"로 나뉜다. "value" 칸에서 다시 화살표가 오른쪽 상자 "String \"서울\""로 간다. 아래쪽에는 "메서드 영역: Optional 클래스" 상자가 있고 그 안에 "static EMPTY" 칸이 있다. "static EMPTY"에서 화살표가 힙의 또 다른 상자 "공유 빈 Optional"(두 칸: "헤더", "value = null")로 간다. "notFound" 칸에서도 화살표가 같은 "공유 빈 Optional" 상자로 간다. 두 화살표가 같은 상자로 모이는 점을 강조한다. 깔끔한 평면 다이어그램, 흰 배경, 파랑과 회색 계열. 값이 있는 Optional은 매번 새 객체지만, 빈 Optional은 현재 구현에서 클래스가 가진 EMPTY 하나를 공유한다.

    객체 하나는 몇 바이트인가

    위 그림의 "16바이트"는 추측이 아니라 측정값이다. HotSpot은 com.sun.management.ThreadMXBean으로 현재 스레드가 지금까지 할당한 바이트 수를 알려 준다. 미리 만든 배열에 Optional.of(s)를 백만 번 저장하면, 배열에 저장된 객체는 메서드 밖으로 탈출하므로 JIT가 할당을 지울 수 없다. 그때 늘어난 바이트를 백만으로 나누면 객체 하나의 크기가 나온다.

    import java.lang.management.ManagementFactory;
import java.util.Optional;

public class AllocSize {
    public static void main(String[] args) {
        var mx = (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
        int n = 1_000_000;
        Object[] box = new Object[n];      // 배열은 측정 전에 미리 만든다
        String s = "v";
        long before = mx.getCurrentThreadAllocatedBytes();
        for (int i = 0; i < n; i++) {
            box[i] = Optional.of(s);       // 배열에 저장하므로 객체가 탈출한다
        }
        long after = mx.getCurrentThreadAllocatedBytes();
        System.out.println("Optional 하나당 바이트 = " + (after - before) / (double) n);
    }
}
    Optional 하나당 바이트 = 16.000248
Optional 하나당 바이트 = 24.00028

    소수점 아래의 작은 값은 측정 코드 자체가 만든 할당이다. 기본 설정에서 객체 하나는 16바이트다. 64비트 HotSpot에서 객체 헤더는 마크 워드(mark word) 8바이트와 클래스 포인터로 이루어지는데, 기본으로 켜진 압축 클래스 포인터(compressed class pointers) 덕분에 클래스 포인터가 4바이트라 헤더가 12바이트가 된다. 여기에 압축 참조(compressed oops)로 4바이트가 된 value 필드를 더하면 정확히 16바이트다. -XX:-UseCompressedOops로 압축 참조를 끄면 value가 8바이트가 되어 12 + 8 = 20바이트이고, 객체는 8바이트 단위로 정렬되므로 24바이트가 된다. 어느 쪽이든 Optional로 감쌀 때마다 객체 하나와 참조 한 단계가 더해진다는 사실은 같다. 이 비용이 실제로 문제가 되는지는 뒤의 "한 층 아래" 절에서 JIT와 함께 다시 본다.

    Optional의 생성과 값 획득

    생성 방법은 세 가지다. 어느 것을 쓰느냐는 "넘기려는 값이 null일 수 있는가"에 대한 내 판단을 코드로 적는 일이다.

    메서드인자가 값일 때인자가 null일 때쓰는 자리
    Optional.of(v)새 Optional즉시 NullPointerExceptionnull이 아님을 확신할 때. null이면 버그이므로 바로 터지는 편이 낫다
    Optional.ofNullable(v)새 Optional빈 Optional(EMPTY)null을 돌려주는 기존 API와의 경계. Map.get 결과를 감쌀 때 등
    Optional.empty()인자 없음. 빈 Optional"결과 없음"을 명시적으로 돌려줄 때

    of가 null을 받으면 내부의 Objects.requireNonNull(value)가 메시지 없는 NPE를 던진다. 이것은 결함이 아니라 의도다. "여기에는 반드시 값이 있다"고 믿고 of를 썼는데 null이 왔다면 그 믿음이 틀린 것이고, 문제를 만든 지점에서 바로 실패(fail-fast)하는 편이 null이 멀리 흘러가 엉뚱한 곳에서 터지는 것보다 원인을 찾기 쉽다. 반대로 "값이 없을 수 있다"는 것이 정상적인 상황이라면 ofNullable을 쓴다.

    값을 꺼내는 메서드는 "비어 있을 때 무엇을 하는가"로 구분된다.

JDK 21의 get() Javadoc에는 "이 메서드보다 orElseThrow()를 쓰는 편이 바람직하다(preferred alternative)"는 API 노트가 붙어 있다.

    아래 프로그램은 생성과 획득의 경계 사례를 모아 실행한 것이다. 출력은 결정적이다.

    import java.util.NoSuchElementException;
import java.util.Optional;
import java.util.stream.Stream;

public class CreateAndGet {
    public static void main(String[] args) {
        Optional e = Optional.empty();
        System.out.println(e + " / " + Optional.of("a"));
        try { Optional.of(null); }
        catch (NullPointerException ex) { System.out.println("of(null) -> " + ex); }
        try { e.get(); }
        catch (NoSuchElementException ex) { System.out.println("get -> " + ex); }
        try { e.orElseThrow(); }
        catch (NoSuchElementException ex) { System.out.println("orElseThrow -> " + ex); }
        System.out.println(Optional.of("a").equals(Optional.of("a")));
        try { Stream.of((String) null, "b").findFirst(); }
        catch (NullPointerException ex) { System.out.println("findFirst -> " + ex); }
    }
}
    Optional.empty / Optional[a]
of(null) -> java.lang.NullPointerException
get -> java.util.NoSuchElementException: No value present
orElseThrow -> java.util.NoSuchElementException: No value present

    toString은 값이 있으면 Optional[값], 없으면 Optional.empty를 돌려준다. equals는 둘 다 Optional이고 Objects.equals(value, other.value)가 참이면 같다고 판단하므로, 서로 다른 객체 두 개라도 담은 값이 같으면 같다. 마지막 줄은 스트림과의 연결 지점이다. Stream.findFirst()는 결과를 Optional로 돌려주는데, 첫 원소 자체가 null이면 "원소가 없음"과 "null 원소가 있음"을 Optional로 구분할 수 없으므로 NPE를 던진다. Stream Javadoc의 findFirst에도 "선택된 원소가 null이면 NullPointerException"이라고 적혀 있다. Optional이 null을 담지 못한다는 구조적 제약이 API 계약으로 드러난 예다.

    isPresent()로 확인한 뒤 get()으로 꺼내는 코드는 문법상 문제가 없지만 if (x != null)을 다른 글자로 쓴 것에 지나지 않는다. 검사를 빠뜨려도 컴파일러가 잡아 주지 않는다는 null의 약점도 그대로 남는다. Optional의 이점은 다음 절의 메서드들로 "검사와 사용을 한 번에" 할 때 나온다.

    Optional 값 처리: map, flatMap, filter, or, stream

    Optional의 진짜 쓰임새는 값을 꺼내지 않고 안에 든 채로 다루는 메서드들이다. 각 메서드의 실제 구현을 보면 규칙이 명확하다(JDK 21 소스에서 null 검사 주석만 줄였다).

    public  Optional map(Function mapper) {
    Objects.requireNonNull(mapper);
    if (isEmpty()) {
        return empty();
    } else {
        return Optional.ofNullable(mapper.apply(value));
    }
}

public  Optional flatMap(Function> mapper) {
    Objects.requireNonNull(mapper);
    if (isEmpty()) {
        return empty();
    } else {
        Optional r = (Optional) mapper.apply(value);
        return Objects.requireNonNull(r);
    }
}

public Optional filter(Predicate predicate) {
    Objects.requireNonNull(predicate);
    if (isEmpty()) {
        return this;
    } else {
        return predicate.test(value) ? this : empty();
    }
}

    세 메서드 모두 첫 번째 분기가 같다. 비어 있으면 함수를 호출하지 않고 빈 값을 그대로 돌려준다. 이것이 "빈 값의 전파"다. 파이프라인 중간 어디에서든 값이 없어지면 그 뒤의 함수들은 한 번도 실행되지 않고 빈 값이 끝까지 흘러간다. null 검사 버전에서 if를 겹겹이 쓴 이유가 바로 이 동작이었는데, 그것이 메서드 안으로 들어간 것이다.

    두 번째 분기에는 미묘한 차이가 있다. map은 함수 결과를 ofNullable로 감싼다. 그래서 함수가 null을 돌려주면 예외 없이 빈 Optional이 된다. null을 돌려주는 기존 getter를 map(Member::address)처럼 그대로 이어 쓸 수 있는 이유가 이것이다. 반면 flatMap은 함수가 이미 Optional을 돌려준다고 가정하고 그 결과를 다시 감싸지 않는다. 함수가 Optional 대신 null을 돌려주면 requireNonNull(r)에서 NPE가 난다. Optional을 돌려주는 메서드가 null을 돌려주는 것은 계약 위반이기 때문이다. filter는 조건을 만족하면 자기 자신(this)을 돌려주므로 새 객체를 만들지 않는다.

    map과 flatMap의 타입 차이

    함수의 반환 타입이 이미 Optional인 경우 map을 쓰면 상자가 두 겹이 된다. Member에 Optional

    findAddress()라는 메서드가 있다고 하자. member.map(Member::findAddress)의 타입은 Optional>이다. 이 상태로는 .map(Address::city)를 이어 쓸 수 없다. 바깥 상자 안에 든 것이 Address가 아니라 Optional
    이기 때문이다. flatMap(Member::findAddress)는 함수가 돌려준 Optional을 감싸지 않고 그대로 결과로 쓰므로 타입이 Optional
    로 평평하게 유지된다. 이름의 flat이 이 "한 겹 벗기기"를 뜻한다. 6회에서 본 Stream.flatMap이 "원소 하나를 스트림으로 바꾸고 그 스트림들을 이어 붙이는" 것과 같은 모양이다. Optional을 원소가 0개 또는 1개인 컬렉션으로 보면 두 flatMap은 같은 연산이다.

    ifPresent, ifPresentOrElse, or, stream

    ifPresent(Consumer)는 값이 있을 때만 동작을 실행하고, Java 9에 추가된 ifPresentOrElse(Consumer, Runnable)는 없을 때 실행할 Runnable도 받는다. 둘 다 반환값이 없는 "끝내는" 연산이다. Java 9의 or(Supplier)는 값이 있으면 자신을, 없으면 공급자가 만든 다른 Optional을 돌려준다. orElseGet이 "없으면 이 값"이라면 or는 "없으면 이 다른 후보를 찾아봐"이고, 결과가 여전히 Optional이라 파이프라인을 이어 갈 수 있다. 캐시를 먼저 보고 없으면 원본을 조회하는 식의 대체 경로를 표현할 때 쓴다. 이 공급자 역시 값이 없을 때만 호출된다.

    Java 9의 stream()은 값이 있으면 원소 하나짜리 스트림, 없으면 빈 스트림을 돌려준다. Optional을 원소 0~1개짜리 컬렉션으로 보는 관점을 API로 만든 것이다. 그래서 Optional이 섞인 스트림에서 값만 골라낼 때 flatMap(Optional::stream)을 쓴다.

    List present = Stream.of(Optional.of(1), Optional.empty(), Optional.of(3))
        .flatMap(Optional::stream)
        .toList();
System.out.println(present);   // [1, 3]

    세 Optional 중 비어 있는 것은 빈 스트림이 되어 이어 붙일 때 사라지고, 값이 있는 두 개만 남는다. filter(Optional::isPresent).map(Optional::get)으로 쓸 수도 있지만 get()을 피하고 한 단계로 끝나는 쪽이 의도를 더 잘 드러낸다.

    값이 있는 경로는 함수를 차례로 통과하고, 어느 단계에서 null이 나오면 빈 경로로 갈아탄 뒤 남은 함수를 건너뛰어 마지막 orElse까지 가는 모습. 가로로 긴 두 줄의 선로 그림. 위 선로는 초록색 "값 있음", 아래 선로는 회색 "비어 있음"이다. 위 선로에 왼쪽부터 네 개의 역 상자 "findMember", "map(address)", "map(city)", "orElse"가 놓인다. "map(address)" 역에서 아래 선로로 내려가는 갈림길 화살표가 있고 그 옆에 라벨 "결과가 null"이 붙는다. 아래 선로에서는 "map(city)" 아래를 지나는 부분에 "함수 호출 안 함"이라는 라벨이 붙은 점선 우회가 있다. 두 선로가 마지막 "orElse" 역에서 만나고, 위 선로 끝에는 "값 반환", 아래 선로 끝에는 "기본값 반환" 라벨이 붙는다. 평면 인포그래픽, 흰 배경. map과 filter는 비어 있으면 함수를 부르지 않고 빈 값을 그대로 넘긴다. 빈 값은 한 번 생기면 끝까지 흘러간다.

    즉시 평가와 지연 평가 1: 자바는 인자를 먼저 계산한다

    이제 이 회차의 핵심인 평가 시점 문제로 들어간다. 먼저 언어 규칙부터 확인하자. JLS §15.7.4는 "메서드나 생성자 호출에서 각 인자 식은 그 오른쪽 인자 식의 어떤 부분보다도 먼저 완전히 평가되는 것처럼 보인다"고 정한다. 그리고 §15.12.4는 메서드 호출의 실행 단계를 순서대로 나열한다. 대상 참조 계산(§15.12.4.1), 인자 평가(§15.12.4.2), 접근성 확인(§15.12.4.3), 호출할 메서드 찾기(§15.12.4.4), 그리고 마지막으로 프레임을 만들고 제어를 넘기기(§15.12.4.5)다. 호출된 메서드의 첫 줄이 실행되기 전에 인자는 이미 모두 값이 되어 있다.

    이렇게 인자를 먼저 값으로 만든 다음 함수에 넘기는 방식을 즉시 평가 또는 엄격한 평가(strict evaluation)라고 한다. 자바의 인자 전달은 값에 의한 호출(call by value)이므로, 메서드가 받는 것은 식이 아니라 식을 계산한 결과값(기본형 값 또는 참조)이다. 메서드는 그 값이 어떤 계산으로 만들어졌는지 모르고, 계산을 취소하거나 미룰 수도 없다. 이미 끝난 일이기 때문이다.

    이 규칙에는 예외가 정확히 세 개 있다. JLS §15.7.2는 "모든 연산자의 피연산자는 연산 자체가 수행되기 전에 완전히 평가된다"고 정하면서 조건 연산자 &&, ||, ? :만 예외로 둔다. §15.23은 &&가 "왼쪽 피연산자의 값이 true일 때만 오른쪽 피연산자를 평가한다"고 적는다. member != null && member.isActive()가 안전한 이유가 이것이다. 즉 자바의 연산자 가운데 "필요할 때만 계산"하는 것은 이 세 개뿐이고, 메서드 호출에는 그런 장치가 없다. 메서드로 지연 평가를 흉내 내려면 다른 방법이 필요하다.

    바이트코드로 보는 순서

    orElse에 메서드 호출 결과를 넘기는 코드를 컴파일해 javap -c로 보면 규칙이 명령어 순서로 드러난다.

    String a = present.orElse(loadDefault());

19: invokestatic  #37      // Method loadDefault:()Ljava/lang/String;
22: invokevirtual #43      // Method java/util/Optional.orElse:(Ljava/lang/Object;)Ljava/lang/Object;
25: checkcast     #47      // class java/lang/String

    대상 참조 present를 피연산자 스택에 올리고(18), loadDefault()를 먼저 호출해 그 결과를 스택에 올린 다음(19), 그 둘을 가지고 orElse를 호출한다(22). orElse의 본문이 value != null ? value : other를 계산하는 시점에는 loadDefault()가 이미 끝나 있다. present에 값이 있어서 other를 쓰지 않더라도 그렇다. 반환 타입이 Object라서 뒤에 checkcast가 붙는 것은 제네릭이 소거되었기 때문이다.

    대상이 null이어도 인자는 평가된다

    단계 순서에서 나오는 경계 사례 하나를 보자. 대상 참조가 null인지는 §15.12.4.4(호출할 메서드 찾기)에서 확인하는데, 인자 평가는 그보다 앞선 §15.12.4.2다. 따라서 null인 참조에 인자가 있는 메서드를 호출하면 인자가 먼저 평가된 뒤 NPE가 난다.

    public class NullTarget {
    static String arg() { System.out.println("인자 평가"); return "x"; }

    public static void main(String[] args) {
        String target = null;
        try {
            target.concat(arg());
        } catch (NullPointerException e) {
            System.out.println("NPE: " + e.getMessage());
        }
    }
}
    인자 평가
NPE: Cannot invoke "String.concat(String)" because "" is null

    바이트코드로 보면 당연한 결과다. aload_1로 null 참조를 스택에 올리고, invokestatic arg로 인자를 계산한 다음, invokevirtual concat을 실행하는 순간 JVM이 대상이 null임을 발견한다. 인자 계산이 부작용(로그, DB 쓰기, 카운터 증가)을 가진다면, 호출이 실패해도 그 부작용은 이미 일어난 뒤다. 즉시 평가는 "결과가 쓰이지 않아도 계산은 일어난다"는 뜻이고, 이 성질이 다음 두 절의 모든 문제의 출발점이다.

    위 실행 결과의 은 실제 출력 문자열이다. -g 없이 컴파일해 지역 변수 이름이 클래스 파일에 없기 때문에 슬롯 번호로 나왔다.

    즉시 평가와 지연 평가 2: 계산을 객체로 감싸 미룬다

    즉시 평가가 실제로 비용이 되는 대표적인 장면은 로그다. 디버그 로그는 운영 환경에서 보통 꺼져 있다. 그런데 로그 메시지를 만드는 데 비싼 계산(큰 객체의 덤프, 문자열 연결, 직렬화)이 들어가면, 로그가 꺼져 있어도 그 계산은 인자 평가 단계에서 이미 일어난다. 메서드 안에서 "로그가 꺼져 있으니 출력하지 않겠다"고 판단하는 것은 인자가 다 만들어진 뒤다.

    import java.util.function.Supplier;

public class LazyLog {
    static boolean debugEnabled = false;

    static void debug(String message) {
        if (debugEnabled) {
            System.out.println("[DEBUG] " + message);
        }
    }

    static void debug(Supplier messageSupplier) {
        if (debugEnabled) {
            System.out.println("[DEBUG] " + messageSupplier.get());
        }
    }

    static String dump() {
        System.out.println("  dump() 실행: 큰 문자열을 만든다");
        return "상태=" + "x".repeat(10);
    }

    public static void main(String[] args) {
        System.out.println("1) 값 전달, debug 꺼짐");
        debug("현재 " + dump());

        System.out.println("2) Supplier 전달, debug 꺼짐");
        debug(() -> "현재 " + dump());

        debugEnabled = true;
        System.out.println("3) Supplier 전달, debug 켜짐");
        debug(() -> "현재 " + dump());
    }
}
    1) 값 전달, debug 꺼짐
  dump() 실행: 큰 문자열을 만든다
2) Supplier 전달, debug 꺼짐
3) Supplier 전달, debug 켜짐
  dump() 실행: 큰 문자열을 만든다
[DEBUG] 현재 상태=xxxxxxxxxx

    1번에서는 로그가 꺼져 있는데도 dump()가 실행된다. "현재 " + dump()라는 인자 식이 debug 호출 전에 평가되기 때문이다. 2번에서는 같은 식이 람다 본문 안에 들어가 있다. 이때 인자 평가 단계에서 계산되는 것은 람다 식이고, 람다 식을 평가한 결과는 Supplier를 구현한 객체의 참조다(1회, 4회에서 본 대로 invokedynamic이 이 객체를 만들어 준다). 본문 "현재 " + dump()는 그 객체의 get()이 호출될 때에야 실행된다. debug는 로그가 꺼져 있으면 get()을 부르지 않으므로 dump()는 한 번도 실행되지 않는다. 3번처럼 로그가 켜져 있을 때만 실행된다.

    정리하면, 자바에서 지연 평가를 얻는 방법은 "값" 대신 "값을 만드는 코드"를 넘기는 것이다. 언어가 인자를 미루어 주지 않으므로, 미루고 싶은 계산을 함수형 인터페이스의 메서드 본문으로 옮기고 그 객체를 넘긴다. 받는 쪽이 필요하다고 판단할 때 메서드를 호출해 계산을 실행한다. 2회에서 본 Supplier(인자 없이 값 하나를 돌려주는 함수)가 이 용도에 정확히 맞는 모양이다.

    if 검사와 비교하기

    지연 평가 없이 같은 효과를 내는 고전적인 방법은 호출하는 쪽에서 먼저 검사하는 것이다. SLF4J 같은 로깅 라이브러리를 쓰는 코드에서 if (log.isDebugEnabled()) { log.debug(...); } 같은 모양을 흔히 본다. 이 방법도 정확하지만 로그를 남기는 곳마다 같은 검사를 반복해야 하고, 검사 조건과 실제 로그 레벨이 어긋나는 실수(검사는 debug, 출력은 info)도 생길 수 있다. Supplier를 받는 API는 "언제 계산할지"의 판단을 그 판단에 필요한 정보를 가진 쪽(로거)으로 옮긴다.

    SLF4J의 log.debug("상태 {}", state)처럼 자리표시자({})를 쓰는 방식도 함께 짚어 두자. 이 방식은 로그가 꺼져 있을 때 문자열 조립을 건너뛰게 해 준다. 하지만 state 자리에 dump() 같은 메서드 호출을 쓰면 그 호출은 여전히 인자 평가 단계에서 일어난다. 자리표시자는 메시지 포맷팅을 미룰 뿐, 자바의 인자 평가 규칙을 바꾸지 못한다.

    JDK 안의 지연 평가 API

    자바 8은 람다와 함께 표준 라이브러리 곳곳에 Supplier를 받는 오버로드를 추가했다. 몇 가지를 JDK 21 소스로 확인해 보자.

    • java.util.logging.Logger.log(Level, Supplier)(@since 1.8): 본문은 if (!isLoggable(level)) return;으로 시작하고, 통과한 경우에만 msgSupplier.get()으로 메시지를 만든다. Javadoc도 "로그 레벨상 실제로 기록될 때만 메시지를 만든다"고 설명한다. fine(Supplier), info(Supplier) 같은 레벨별 메서드도 있다.
    • Objects.requireNonNull(T obj, Supplier messageSupplier)(@since 1.8): 객체가 null일 때만 메시지 공급자를 호출한다. 이 메서드의 Javadoc에는 흥미로운 경고가 붙어 있다. "메시지 공급자를 만드는 비용이 문자열 메시지를 직접 만드는 비용보다 작은지 주의하라." 람다 객체를 만드는 것도 공짜가 아니므로, 메시지가 상수 문자열이라면 문자열 버전이 낫다는 뜻이다.
    • Optional.orElseGet(Supplier), Optional.or(Supplier), Optional.orElseThrow(Supplier): 비어 있을 때만 공급자를 호출한다.
    • Map.computeIfAbsent(key, Function): 키에 값이 없을 때만(키가 없거나 null에 매핑되어 있을 때) 값을 만드는 함수를 호출한다. "없으면 만들어 넣는다" 패턴의 표준형이다.

    공통점은 분명하다. 계산 결과가 쓰일지 말지를 호출받는 쪽만 알 때, 호출하는 쪽은 결과 대신 계산을 넘긴다. 로그가 켜져 있는지는 로거가 알고, 값이 비어 있는지는 Optional이 알고, 키가 있는지는 맵이 안다.

    값을 넘기면 호출 전에 비싼 계산이 실행되고, Supplier를 넘기면 호출받은 쪽이 필요하다고 판단한 경우에만 계산이 실행된다는 시간 순서를 비교한다. 좌우로 나뉜 두 개의 시퀀스 다이어그램. 각 다이어그램에는 세 개의 세로 생명선 "호출자", "debug 메서드", "dump()"가 있다. 왼쪽 제목은 "값 전달(즉시 평가)": 호출자에서 먼저 "dump()"로 화살표 "1. 인자 계산"이 가고 돌아온 뒤, 호출자에서 "debug 메서드"로 화살표 "2. 호출"이 가며, debug 메서드 안에 "로그 꺼짐 → 버림" 상자가 있다. 오른쪽 제목은 "Supplier 전달(지연 평가)": 호출자에서 "debug 메서드"로 화살표 "1. 람다 객체 전달"이 가고, debug 메서드 안에 "로그 켜짐?" 마름모가 있으며, "예"일 때만 debug 메서드에서 "dump()"로 화살표 "2. get() 호출"이 간다. "아니오" 쪽에는 "dump() 실행 안 됨" 라벨. 깔끔한 UML 스타일, 흰 배경. 즉시 평가에서는 계산이 호출보다 먼저 일어난다. 지연 평가에서는 계산을 쓸지 아는 쪽이 계산을 실행한다.

    즉시 평가와 지연 평가 3: 무엇이 미뤄지고 무엇이 미뤄지지 않는가

    Supplier로 얻는 지연 평가를 정확히 이해하려면 "람다 식을 평가하는 시점"과 "람다 본문을 실행하는 시점"을 구분해야 한다. 람다 식 자체는 즉시 평가된다. 즉 그 줄에 도달하면 함수형 인터페이스 구현 객체가 만들어지고, 람다가 붙잡는(capture) 지역 변수의 값도 그 순간 객체 안에 복사된다(4회의 변수 캡처). 미뤄지는 것은 본문의 실행뿐이다. 본문이 읽는 필드나 정적 변수는 본문이 실행되는 순간의 값이다.

    import java.util.function.Supplier;

public class CallByName {
    static int counter = 0;

    static int next() {
        counter++;
        System.out.println("  next() 실행, counter=" + counter);
        return counter;
    }

    public static void main(String[] args) {
        Supplier s = () -> next();
        System.out.println("Supplier 생성 직후 counter=" + counter);
        int a = s.get();
        int b = s.get();
        System.out.println("a=" + a + ", b=" + b);

        int base = 10;
        Supplier plusBase = () -> base + counter;
        counter = 100;
        System.out.println("plusBase.get()=" + plusBase.get());
    }
}
    Supplier 생성 직후 counter=0
  next() 실행, counter=1
  next() 실행, counter=2
a=1, b=2
plusBase.get()=110

    한 줄씩 추적해 보자. s를 만든 직후 counter는 0이다. 람다 객체만 생겼고 next()는 실행되지 않았다. s.get()을 두 번 부르면 next()도 두 번 실행되어 a는 1, b는 2가 된다. Supplier는 결과를 기억하지 않는다. 부를 때마다 본문을 처음부터 다시 실행한다. 마지막 부분에서 base는 지역 변수이므로 람다 객체가 만들어질 때 값 10이 복사되고, counter는 정적 필드이므로 get()이 실행되는 순간의 값 100을 읽는다. 결과는 110이다.

    프로그래밍 언어 이론에서는 이 차이를 이름으로 구분한다. 인자를 계산하지 않고 "계산 방법"으로 넘겨 쓸 때마다 다시 계산하는 방식을 이름에 의한 호출(call by name), 처음 필요할 때 한 번 계산하고 그 결과를 기억해 다시 쓰는 방식을 필요에 의한 호출(call by need)이라고 한다. 자바의 Supplier가 기본으로 주는 것은 전자다. 같은 공급자를 두 번 호출하는 API에 비싼 계산이나 부작용이 있는 계산을 넘기면 두 번 실행된다. Optional의 메서드들은 공급자를 많아야 한 번만 호출하므로 이 문제가 없지만, 직접 Supplier를 받는 API를 만든다면 "몇 번 호출하는가"도 계약에 적어야 한다.

    결과를 기억하는 지연 값(memoization)이 필요하면 직접 만들어야 한다. 단일 스레드라면 필드 하나에 결과를 저장해 두면 되지만, 여러 스레드가 동시에 처음 호출할 수 있다면 고급 1편에서 본 가시성과 원자성 문제가 그대로 생긴다(두 스레드가 모두 계산을 실행하거나, 덜 초기화된 값을 보는 문제). 지연 평가는 "언제 실행되는가"를 호출자의 코드 위치에서 떼어 내는 일이므로, 실행 시점이 어느 스레드에서 오는지도 함께 따져야 한다.

    지연 평가가 이득이 아닌 경우

    지연 평가는 "계산을 건너뛸 가능성"과 "계산 비용"이 모두 클 때 이득이다. 기본값이 상수 문자열이나 이미 계산된 지역 변수라면, 그것을 람다로 감싸 봐야 아낄 계산이 없다. 오히려 람다가 지역 변수를 붙잡으면 호출할 때마다 람다 객체가 새로 만들어질 수 있다. 4회에서 본 대로 HotSpot에서 아무것도 붙잡지 않는 람다는 같은 객체를 재사용하지만, 값을 붙잡는 람다는 평가될 때마다 그 값을 담은 새 객체가 필요하다. Objects.requireNonNull의 Javadoc 경고가 바로 이 점을 말한다. 그리고 이 회차 뒤쪽의 측정에서 보듯 JIT가 그런 작은 객체를 지워 줄 때도 있지만, 그것은 보장이 아니라 최적화다.

    스트림과의 관계도 정리해 두자. 5회에서 본 스트림의 중간 연산(filter, map)은 최종 연산이 호출될 때까지 실행되지 않고, findFirst 같은 단락(short-circuit) 연산은 필요한 원소만 처리하고 멈춘다. 이것도 같은 원리다. 중간 연산에 넘긴 람다는 "나중에 실행할 계산"으로 파이프라인 객체에 저장될 뿐이고, 원소를 실제로 끌어오는 최종 연산이 그 계산들을 필요한 만큼만 실행한다. 반면 Optional의 map과 filter는 즉시 실행된다. 위의 소스에서 보듯 map은 호출되는 순간 함수를 적용해 새 Optional을 돌려준다. 이름이 같다고 실행 모델까지 같은 것은 아니다. Optional에서 지연되는 것은 orElseGet·or·orElseThrow에 넘긴 공급자뿐이다.

    필요에 의한 호출을 JVM이 해 주는 곳: 클래스 초기화

    앞 절에서 Supplier는 이름에 의한 호출이고, 결과를 기억하는 필요에 의한 호출은 직접 만들어야 하며 여러 스레드가 얽히면 가시성과 원자성 문제가 생긴다고 했다. 그런데 자바에는 "처음 필요할 때 딱 한 번, 스레드 안전하게 계산한다"를 언어 명세와 JVM이 함께 보장하는 장치가 이미 있다. 클래스 초기화다. 정적 필드의 초기화 식과 static 블록은 클래스가 로드될 때가 아니라 초기화될 때 실행되고, 언제 초기화되는지는 JLS §12.4.1이 정한다. 클래스 T는 다음 중 하나가 처음 일어나기 직전에 초기화된다. T의 인스턴스 생성, T가 선언한 정적 메서드 호출, T가 선언한 정적 필드에 대입, 그리고 T가 선언한 정적 필드를 사용하는데 그 필드가 상수 변수(constant variable)가 아닐 때다. 같은 절은 일부 리플렉션 메서드도 초기화를 일으킨다고 덧붙인 뒤 "그 밖의 상황에서는 초기화되지 않는다"고 못 박는다.

    이 규칙으로 "처음 읽을 때 계산되는 값"을 만들 수 있다. 값을 담을 정적 필드를 작은 중첩 클래스 하나에만 두는 홀더 클래스 관용구(holder class idiom)다. 아래 프로그램은 네 스레드가 동시에 그 값을 처음 읽게 만든다.

    import java.util.concurrent.CountDownLatch;

public class LazyHolder {
    static String expensive() {
        System.out.println("  expensive() 실행: " + Thread.currentThread().getName());
        try { Thread.sleep(200); } catch (InterruptedException e) { throw new RuntimeException(e); }
        return "설정값";
    }

    static class Holder {
        static final String VALUE = expensive();   // 상수 변수가 아니다(메서드 호출 결과)
    }

    static String value() {
        return Holder.VALUE;                        // 처음 읽을 때 Holder가 초기화된다
    }

    public static void main(String[] args) throws Exception {
        System.out.println("main 시작");
        CountDownLatch start = new CountDownLatch(1);
        Thread[] ts = new Thread[4];
        for (int i = 0; i < ts.length; i++) {
            ts[i] = new Thread(() -> {
                try { start.await(); } catch (InterruptedException e) { return; }
                System.out.println(Thread.currentThread().getName() + " -> " + value());
            }, "T" + i);
            ts[i].start();
        }
        System.out.println("스레드 시작, 아직 Holder 미초기화");
        start.countDown();
        for (Thread t : ts) t.join();
    }
}

    VALUE가 "설정값" 같은 상수 식으로 초기화되었다면 상수 변수가 되어, javac가 읽는 쪽에 값을 그대로 박아 넣으므로 Holder는 초기화조차 되지 않는다. 메서드 호출 결과이기 때문에 §12.4.1의 마지막 조건에 걸린다. -Xlog:class+init=debug를 붙여 실행하면 JVM이 초기화를 어떻게 처리하는지가 로그로 나온다(아래는 Holder와 관련된 줄과 프로그램 출력만 추린 것이다. 초기화를 맡는 스레드, 기다리는 순서, 시각은 실행마다 다르다).

    expensive()는 네 스레드 가운데 하나에서 한 번만 실행되었고, 나머지 셋은 그 결과를 받았다. 로그를 HotSpot 소스와 맞춰 보자. 초기화는 instanceKlass.cpp의 InstanceKlass::initialize_impl이 하고, 이 함수에는 JLS §12.4.2 절차의 번호가 "Step 1"부터 주석으로 달려 있다. 1단계에서 클래스마다 하나인 초기화 락(init_lock())을 잡는다. 2단계에서 다른 스레드가 초기화 중이면 wait_uninterruptibly로 기다린다. T1~T3의 "waiting for initialization" 줄이 이것이다. 3단계는 초기화 중인 스레드가 자기 자신이면 재귀 요청으로 보고 그냥 돌아간다. T0의 "recursively initializing" 줄은 안의 putstatic VALUE가 필드 참조를 해석하면서(linkResolver.cpp의 LinkResolver::resolve_field는 정적 필드면 그 클래스의 initialize를 부른다) 같은 클래스의 초기화를 다시 요청한 흔적이다. 4단계는 이미 초기화되었으면 그냥 돌아가는 것으로, 기다리던 세 스레드가 깨어나 찍은 "already initialized" 줄이다. 6단계에서는 상태를 being_initialized로, 초기화 스레드를 자신으로 기록하고 락을 놓은 뒤 초기화 식을 실행한다. 끝나면 set_initialization_state_and_notify가 락을 다시 잡고 상태를 바꾼 다음 notify_all로 기다리던 스레드를 깨운다. 두 타임스탬프의 차이 약 200밀리초는 세 스레드가 expensive()의 sleep 동안 막혀 있었다는 뜻이다.

    가시성은 명세가 보장한다. JLS §12.4.2는 초기화가 이미 끝났다고 판단할 수 있으면 1단계의 락 획득을 생략하는 최적화를 허용하되, 락을 잡았다면 존재했을 모든 happens-before 관계가 그대로 유지되어야 한다는 조건을 단다. 그래서 초기화가 끝난 클래스를 본 스레드는 초기화 식이 쓴 값을 온전히 본다. 홀더 관용구에 volatile도 synchronized도 필요 없는 이유다. 초기화가 끝난 뒤의 비용도 거의 없다. OpenJDK 21 HotSpot의 ciField.cpp를 보면 C2는 정적 final 필드를 상수로 취급하고(System.in·out·err 셋만 예외), ciField::constant_value()는 그 필드를 선언한 클래스가 이미 초기화된 경우에만 값을 돌려준다. 즉 컴파일 시점에 Holder가 초기화되어 있으면 Holder.VALUE를 읽는 컴파일된 코드는 그 문자열 객체를 상수로 쓴다.

    Optional도 같은 장치 위에 서 있다. 앞에서 본 공유 객체 EMPTY가 언제 만들어지는지 정적 초기화 메서드를 열어 보면 알 수 있다.

    한 번뿐인 계산: 실패도 기억된다

    클래스 초기화는 결과뿐 아니라 실패도 기억한다. JLS §12.4.2에 따르면 초기화 식이 예외로 끝나면 클래스는 오류 상태(erroneous)로 표시되고, 이후의 초기화 요청은 5단계에서 NoClassDefFoundError를 받는다. 다시 시도하지 않는다.

    public class Poisoned {
    static int attempts = 0;

    static String load() {
        attempts++;
        throw new IllegalStateException("설정 서버 연결 실패 #" + attempts);
    }

    static class Holder {
        static final String VALUE = load();
    }

    public static void main(String[] args) {
        for (int i = 1; i <= 2; i++) {
            try {
                System.out.println(Holder.VALUE);
            } catch (Throwable t) {

    orElse() vs orElseGet()

    이제 두 메서드의 차이를 정확히 말할 수 있다. 구현은 한 줄씩이다.

    public T orElse(T other) {
    return value != null ? value : other;
}

public T orElseGet(Supplier supplier) {
    return value != null ? value : supplier.get();
}

    두 메서드의 본문은 모두 값이 있으면 other나 supplier.get()을 쓰지 않는다. 조건 연산자 ? :는 선택된 쪽만 평가하므로 orElseGet에서 값이 있으면 supplier.get()은 호출되지 않는다. 차이는 메서드 안이 아니라 밖, 곧 인자를 만드는 단계에 있다. orElse의 인자 other는 이미 계산된 값이므로 그 값을 만드는 데 든 비용은 메서드에 들어오기 전에 치렀다. orElseGet의 인자는 계산을 담은 객체이므로 비용은 get()이 호출될 때만 치른다.

    import java.util.Optional;

public class EvalOrder {
    static String loadDefault() {
        System.out.println("  loadDefault() 실행");

    public static void main(String[] args) {

        System.out.println("  결과 = " + c);

        System.out.println("[4] empty.orElseGet");

    }

    부작용이 있으면 버그가 된다

    [1]이 단지 "조금 느린" 정도라면 큰 문제가 아니다. 기본값을 만드는 계산에 부작용이 있으면 이야기가 달라진다. 다음은 스프링 데이터 JPA의 findById(반환 타입이 Optional)를 쓰는 서비스에서 흔히 보는 형태를 단순화한 것이다.

    // 회원이 없으면 기본 회원을 만들어 저장하고 돌려주려는 의도

        .orElse(createAndSaveGuest(id));     // 버그: 회원이 있어도 항상 실행된다

Member fixed = memberRepository.findById(id)
        .orElseGet(() -> createAndSaveGuest(id));   // 없을 때만 실행된다

    첫 번째 코드는 회원이 이미 있을 때도 createAndSaveGuest(id)를 실행한다. 반환값은 기존 회원이므로 화면상 결과는 정상처럼 보이지만, 데이터베이스에는 쓰이지 않을 게스트 회원이 계속 쌓이거나, 같은 키로 넣으려다 제약 조건 위반 예외가 나서 멀쩡한 조회 요청이 실패한다. 결과값만 확인하는 테스트로는 잡히지 않고, "값이 있는 경우"에 숨은 부작용이라 원인을 찾기도 어렵다. 같은 이유로 orElse(new ArrayList<>())처럼 매번 객체를 만드는 기본값, orElse(remoteClient.fetchDefault())처럼 네트워크를 타는 기본값은 orElseGet으로 바꾸는 것이 맞다.

    orElseThrow(Supplier)가 공급자를 받는 이유

    orElseThrow가 예외 객체가 아니라 예외를 만드는 공급자를 받는 것도 같은 원리다. 예외 객체를 만드는 일은 생각보다 비싸다. Throwable의 생성자는 JDK 21 소스에서 첫 줄에 fillInStackTrace()를 호출하고, 이 메서드는 Javadoc 설명대로 현재 스레드의 스택 프레임 정보를 예외 객체 안에 기록한다. 호출 깊이가 깊은 서버 코드에서는 이 작업이 결코 작지 않다. 만약 orElseThrow(new NotFoundException(...))처럼 예외 객체를 직접 받는 API였다면, 값이 있는 정상 경로에서도 매번 스택을 기록한 예외 객체를 만들었다가 버렸을 것이다. 공급자를 받으므로 예외는 실제로 던질 때만 만들어진다. Javadoc의 API 노트가 권하는 대로 인자 없는 생성자라면 IllegalStateException::new 같은 생성자 참조를 넘길 수 있다.

    새 객체 생성, 컬렉션 생성orElseGet값이 있으면 버려질 할당을 피한다
    I/O, DB 조회, 원격 호출, 저장 같은 부작용orElseGet (필수)값이 있을 때 부작용이 일어나면 동작 자체가 틀린다
    대체 후보도 "없을 수 있음"or결과가 다시 Optional이라 파이프라인을 이어 갈 수 있다

    실전 활용 1: 주소 찾기

    앞에서 세 겹의 if로 쓴 "회원의 도시 찾기"를 Optional로 다시 써 보자. 도메인은 그대로다. 회원은 주소가 없을 수 있고, 주소는 도시가 비어 있을 수 있다. 회원 저장소는 Map이라 없는 번호를 찾으면 null을 돌려준다. 이 null을 받아들이는 지점을 한 곳으로 모으는 것이 첫 번째 설계 결정이다.

    import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

public class AddressLookup {
    record Address(String city, String street) {}        // city는 null일 수 있다
    record Member(String name, Address address) {}       // address는 null일 수 있다

    static final Map members = new HashMap<>();

    static Optional findMember(long id) {
        return Optional.ofNullable(members.get(id));     // 경계에서 null을 Optional로 바꾼다
    }

    static String cityByNullCheck(long id) {
        // ... 앞 절의 세 겹 if 버전과 같다
    }

    static String cityOf(long id) {
        return findMember(id)
                .map(Member::address)
                .map(Address::city)
                .orElse("미등록");
    }

    public static void main(String[] args) {
        members.put(1L, new Member("kim", new Address("서울", "세종대로")));
        members.put(2L, new Member("lee", null));
        members.put(3L, new Member("park", new Address(null, "중앙로")));

        for (long id = 1; id <= 4; id++) {
            System.out.println(id + ": " + cityOf(id) + " / " + cityByNullCheck(id));
        }
    }
}

2: 미등록 / 미등록
3: 미등록 / 미등록
4: 미등록 / 미등록

    네 경우는 각각 다른 지점에서 값이 사라진다. 1번은 끝까지 값이 있다. 2번은 map(Member::address)에서, 3번은 map(Address::city)에서 null이 나와 빈 값이 되고, 4번은 findMember에서부터 비어 있다. cityOf는 이 네 경우를 구분하는 분기 없이 같은 코드로 처리한다. 두 버전의 결과가 모두 같다는 것은 map의 "비어 있으면 건너뛰고, 결과가 null이면 비운다"는 규칙이 중첩 if와 정확히 같은 의미라는 뜻이다. 이 경우 기본값 "미등록"은 상수이므로 orElse가 알맞다.

    getter가 Optional을 돌려준다면: flatMap

    도메인 모델을 바꿀 수 있다면 "주소는 없을 수 있다"는 사실을 Member 자신이 타입으로 밝히게 할 수 있다. 필드는 그대로 두고 조회 메서드만 Optional을 돌려주게 하는 것이 일반적인 방법이다(필드를 Optional로 두지 않는 이유는 뒤의 베스트 프랙티스에서 본다).

    record Member(String name, Address address) {

    실전 활용 2: 배송

    두 번째 예제는 조금 더 실제 업무에 가깝다. 주문에는 배송 정보가 붙는데, 출고 전이면 배송 정보가 아직 없다(null). 배송 정보에는 상태가 있고, 취소된 배송은 "배송 정보 없음"으로 보여야 한다. 배송비는 주문 금액 3만 원 이상이면 무료이고, 존재하지 않는 주문으로 배송비를 계산하려 하면 예외여야 한다. 운송장 추적은 로컬 캐시를 먼저 보고, 없으면 택배사 시스템에 묻는다.

    import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

public class Shipping {
    enum Status { READY, SHIPPING, DONE, CANCELED }
    record Delivery(String trackingNo, Status status) {}
    record Order(long id, long amount, Delivery delivery) {}   // delivery가 null이면 아직 배송 등록 전

    static final Map orders = new HashMap<>();
    static final Map cache = new HashMap<>();

    static Optional findOrder(long id) {
        return Optional.ofNullable(orders.get(id));
    }

    static String deliveryMessage(long orderId) {
        return findOrder(orderId)
                .map(Order::delivery)
                .filter(d -> d.status() != Status.CANCELED)
                .map(d -> d.status() + " (" + d.trackingNo() + ")")
                .orElse("배송 정보 없음");
    }

    static long shippingFee(long orderId) {
        Order order = findOrder(orderId)
                .orElseThrow(() -> new IllegalArgumentException("주문 없음: " + orderId));
        return order.amount() >= 30_000 ? 0 : 3_000;
    }

    static Optional fromCache(String trackingNo) {
        return Optional.ofNullable(cache.get(trackingNo));
    }

    static Optional fromCarrier(String trackingNo) {
        System.out.println("  택배사 시스템 조회: " + trackingNo);
        return trackingNo.startsWith("T") ? Optional.of(new Delivery(trackingNo, Status.SHIPPING))
                                          : Optional.empty();
    }

    static Optional track(String trackingNo) {
        return fromCache(trackingNo).or(() -> fromCarrier(trackingNo));
    }

    public static void main(String[] args) {
        orders.put(10L, new Order(10L, 45_000, new Delivery("T-100", Status.SHIPPING)));
        orders.put(11L, new Order(11L, 12_000, null));
        orders.put(12L, new Order(12L, 8_000, new Delivery("T-102", Status.CANCELED)));
        cache.put("T-100", orders.get(10L).delivery());

        for (long id = 10; id <= 13; id++) {
            System.out.println(id + ": " + deliveryMessage(id));
        }
        System.out.println("배송비 10 = " + shippingFee(10));
        System.out.println("배송비 11 = " + shippingFee(11));
        try {
            shippingFee(13);
        } catch (IllegalArgumentException e) {
            System.out.println("예외: " + e.getMessage());
        }
        System.out.println("추적 T-100 -> " + track("T-100"));
        System.out.println("추적 T-555 -> " + track("T-555"));
        System.out.println("추적 X-1 -> " + track("X-1"));
    }
}

Optional은 "있다/없다" 두 상태만 표현한다. 없는 이유는 담지 못한다.

    shippingFee는 "주문이 없으면 계산을 진행할 수 없다"는 의미를 orElseThrow로 적었다. 예외를 만드는 람다는 orderId를 붙잡는 캡처 람다이고, 예외 객체와 그 메시지 문자열은 주문이 없을 때(13번)만 만들어진다. 금액 비교는 꺼낸 값으로 평범하게 한다. 모든 것을 map으로 이어 쓸 필요는 없다. 값이 반드시 있어야 하는 지점에서 꺼내고 나면 그 뒤는 일반 코드다.

    track은 or로 대체 경로를 만든다. T-100은 캐시에 있으므로 or의 공급자가 호출되지 않아 "택배사 시스템 조회" 줄이 출력되지 않는다. T-555는 캐시에 없어서 공급자가 호출되고, 택배사 쪽 결과가 그대로 반환된다. X-1은 두 곳 모두에 없어 빈 값이다. 만약 or가 공급자가 아니라 Optional 값을 받는 메서드였다면, 캐시에 있는 경우에도 택배사 조회가 매번 일어났을 것이다. 캐시의 존재 이유가 사라지는 셈이다. 이 예제 역시 지연 평가가 성능 문제가 아니라 동작의 정확성 문제라는 것을 보여 준다.

    예제의 도메인과 클래스 이름은 이 강좌에서 새로 만든 것이다. 실무에서는 Map 대신 리포지토리, 택배사 조회 대신 HTTP 클라이언트가 들어가지만, 경계에서 null을 Optional로 바꾸고 파이프라인 끝에서 한 번만 꺼내는 구조는 같다.

    한 층 아래: JIT는 Optional 할당을 지울 수 있는가

    앞에서 Optional 하나가 16바이트 객체라는 것을 측정했다. map을 세 번 이어 쓰면 값이 있는 경로에서는 최대 네 개의 Optional이 생겼다 사라진다. 이것이 GC 부담이 될까. 답은 "JIT가 그 할당을 지울 수 있는가"에 달려 있다. HotSpot의 C2 컴파일러는 탈출 분석(escape analysis)으로 객체가 만들어진 메서드(인라인된 범위 포함) 밖으로 새어 나가지 않는다는 것을 증명하면, 그 객체를 힙에 할당하지 않고 필드들을 지역 변수처럼 레지스터나 스택에 두는 스칼라 치환(scalar replacement)을 한다. 이것은 JVM 명세가 보장하는 동작이 아니라 HotSpot의 최적화이므로 실험으로 확인해야 한다.

    import java.lang.management.ManagementFactory;
import java.util.Optional;
import java.util.function.ToIntFunction;

public class Escape2 {
    static String[] all = {"a", "bb", "ccc", "dddd", "eeeee"};
    static String[] mixed = {"a", null, "ccc", null, "eeeee"};

    static int ofOnly(String s)      { return Optional.of(s).get().length(); }
    static int ofNullable(String s)  { return Optional.ofNullable(s).isPresent() ? 1 : 0; }

    static void run(String label, String[] data, ToIntFunction f) {
        var mx = (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
        long sum = 0, bytes = 0;
        for (int round = 0; round < 6; round++) {          // 앞 라운드는 JIT 컴파일 준비
            long before = mx.getCurrentThreadAllocatedBytes();
            for (int i = 0; i < 10_000_000; i++) sum += f.applyAsInt(data[i % data.length]);
            bytes = mx.getCurrentThreadAllocatedBytes() - before;
        }
        System.out.printf("%-24s 마지막 라운드 %,d bytes (sum=%d)%n", label, bytes, sum);
    }

    public static void main(String[] args) {
        run("of(s).get()", all, Escape2::ofOnly);
        run("ofNullable(all)", all, Escape2::ofNullable);
        run("ofNullable(mixed)", mixed, Escape2::ofNullable);
    }
}

    숫자를 읽어 보자. 탈출 분석을 끈 경우 of(s).get()은 천만 번 호출에 1억 6천만 바이트, 정확히 호출당 16바이트를 할당한다. 탈출 분석을 켜면 0바이트다. 만들어진 Optional이 메서드 밖으로 나가지 않고 곧바로 get()으로 풀리므로 C2가 객체를 아예 만들지 않은 것이다. ofNullable(all)도 켜면 0바이트다. 흥미로운 것은 세 번째 줄이다. 입력의 다섯 개 중 두 개가 null인 mixed 배열에서는 탈출 분석을 켜도 9천 6백만 바이트가 할당되었다. 천만 번 중 null이 아닌 육백만 번 × 16바이트와 정확히 일치한다. 값이 있는 경로의 할당이 하나도 지워지지 않았다.

    차이는 ofNullable의 두 갈래가 실제로 모두 실행되느냐에 있다. ofNullable은 null이면 기존 객체 EMPTY를, 아니면 새 객체를 돌려주고, 두 결과는 같은 변수로 합쳐진다. all 입력에서는 null 분기가 한 번도 실행되지 않았다. HotSpot C2는 실행 프로파일에 한 번도 나타나지 않은 분기를 정상 경로로 컴파일하지 않고, 만약 그 분기에 들어서면 컴파일된 코드를 버리고 인터프리터로 돌아가는(deoptimization) 장치만 남겨 둔다. 그러면 컴파일된 코드 안에는 "새 객체" 경로 하나만 남아 스칼라 치환이 가능해진다. mixed 입력에서는 두 분기가 모두 살아 있어서 새로 만든 객체와 기존 객체가 한 지점에서 합쳐지고, JDK 21의 C2는 이 실험에서 그 할당을 지우지 못했다. OpenJDK에서는 이렇게 할당과 다른 값이 합쳐지는 지점(allocation merge)을 줄이려는 C2 개선이 JDK 21 이후에도 이어지고 있다(예: 2024년에 통합된 JDK-8316991 "Reduce nullable allocation merges"). 따라서 같은 실험이라도 JDK 버전에 따라 결과가 달라질 수 있다.

    이 실험에서 끌어낼 결론은 두 가지다. 첫째, 메서드 안에서 만들고 바로 풀어 버리는 Optional(반환 직후 orElse로 꺼내는 대부분의 사용)은 JIT가 비용을 상당 부분 없앨 수 있다. 둘째, 그것은 보장이 아니다. 인라인 깊이, 분기 프로파일, JDK 버전에 따라 할당은 남을 수 있고, 필드나 컬렉션에 저장되는 Optional은 탈출하므로 언제나 할당된다. 초당 수백만 번 도는 핫 루프나 수백만 개 원소를 담는 자료구조에서는 Optional이 실제 비용이 되며, 그런 곳에서는 null 검사나 기본형 특화 타입이 낫다. 실무 코드 대부분에서는 이 비용이 DB 조회 한 번에 비해 무시할 만하므로, Optional을 쓸지 말지는 성능보다 API의 의미를 기준으로 정하는 것이 맞다.

    기본형 특화: OptionalInt, OptionalLong, OptionalDouble

    정수 하나를 Optional로 감싸면 Integer 박싱 객체와 Optional 객체가 겹으로 생길 수 있다(JLS가 캐시를 요구하는 -128~127 범위의 박싱은 새 객체를 만들지 않는다). OptionalInt는 소스에서 보듯 boolean isPresent와 int value 두 필드를 직접 가져 박싱이 없다. 6회의 IntStream.max()는 OptionalInt를, average()는 OptionalDouble을 돌려준다. 다만 API가 작다. getAsInt, orElse(int), orElseGet(IntSupplier), orElseThrow, ifPresent, ifPresentOrElse, stream은 있지만 map·flatMap·filter·or는 없다. 값을 변환하며 이어 가려면 Optional로 옮기거나 꺼낸 뒤 처리해야 한다.

    탈출 분석의 전제: 인라이닝이 Optional 체인을 한 덩어리로 만든다

    앞 절의 실험은 C2가 할당을 지울 때와 못 지울 때의 차이를 분기 프로파일로 설명했다. 그보다 앞선 조건이 하나 더 있다. 탈출 분석은 C2가 한 번에 컴파일하는 단위 안에서만 일어난다. OpenJDK 21의 escape.hpp가 정의하는 탈출 상태는 세 가지다. NoEscape는 객체가 메서드나 스레드 밖으로 나가지 않고 호출의 인자로도 넘겨지지 않는 경우로, 주석에 "스칼라로 대체될 수 있다"고 적혀 있다. ArgEscape는 메서드와 스레드 밖으로 나가지는 않지만 호출의 인자로 넘겨지거나 인자가 참조하는 경우다. GlobalEscape는 메서드나 스레드 밖으로 나가는 경우다. 그런데 Optional.of(s).map(f).orElse(x)는 소스로 보면 메서드 호출 세 번이고, 각 호출은 Optional을 돌려주거나 수신 객체(호출의 0번째 인자)로 받는다. 호출이 그대로 남아 있으면 이 Optional들은 NoEscape가 될 수 없다. 앞 절에서 할당이 0바이트가 될 수 있었던 것은 C2가 이 호출들을 호출한 쪽 코드 안으로 펼쳐 넣는 인라이닝(inlining)을 먼저 했기 때문이다.

    import java.lang.management.ManagementFactory;
import java.util.Optional;

public class Inl {
    static String[] data = {"a", "bb", "ccc", "dddd", "eeeee"};

    static int lengthOf(String s) {
        return Optional.of(s).map(String::length).orElse(0);
    }

    public static void main(String[] args) {
        var mx = (com.sun.management.ThreadMXBean) ManagementFactory.getThreadMXBean();
        long sum = 0, bytes = 0;
        for (int round = 0; round < 6; round++) {
            long before = mx.getCurrentThreadAllocatedBytes();
            for (int i = 0; i < 10_000_000; i++) sum += lengthOf(data[i % data.length]);
            bytes = mx.getCurrentThreadAllocatedBytes() - before;
        }
        System.out.printf("마지막 라운드 %,d bytes, 호출당 %.1f bytes (sum=%d)%n", bytes, bytes / 1e7, sum);
    }
}

    먼저 C2가 lengthOf를 컴파일할 때 무엇을 인라인했는지 보자. -XX:+PrintInlining은 진단 옵션이라 -XX:+UnlockDiagnosticVMOptions가 필요하고, 여러 컴파일러 스레드의 출력이 섞이지 않도록 컴파일을 순서대로 하게 만드는 -Xbatch를 함께 주었다.

    16바이트가 Optional 하나라는 것은 앞에서 측정했다. 네 경우 모두 sum=180000000으로 결과는 같다. of를 끊으면 첫 Optional은 of 메서드 안에서 할당되어 반환된다. lengthOf의 컴파일 단위 입장에서 그것은 자기가 할당한 객체가 아니라 호출의 결과이므로 지울 방법이 없다. 반면 map이 만드는 두 번째 Optional은 인라인된 orElse에서 바로 풀리므로 여전히 지워진다. map을 끊으면 둘 다 남는다. of의 결과는 인라인되지 않은 map 호출의 수신 객체로 넘겨지므로 ArgEscape가 되고, map의 결과는 map 안에서 할당되어 반환된다. orElse를 끊으면 of의 결과는 인라인된 map 안에서 소비되어 지워지고, map의 결과는 orElse 호출로 넘겨져 남는다. 문자열 길이 1~5와 기본값 0은 JLS가 캐시를 요구하는 -128~127 범위라서 Integer.valueOf는 어느 경우에도 새 객체를 만들지 않는다.

    이 결과가 "JIT가 Optional을 알아서 지워 준다"는 말의 정확한 조건이다. Optional을 만들고, 받아서 변환하고, 꺼내는 호출이 모두 하나의 컴파일 단위 안으로 인라인되어야 한다. 그중 하나라도 인라인되지 않으면 그 경계를 넘는 Optional은 힙에 할당된다. 인라이닝 여부는 피호출 메서드의 바이트코드 크기, 중첩 깊이, 이미 컴파일된 코드의 크기(InlineSmallCode) 같은 여러 조건으로 정해지므로, 예를 들어 Optional을 매개변수로 받는 큰 메서드에 넘기면 그 호출이 인라인되지 않아 할당이 남을 수 있다. 베스트 프랙티스의 "매개변수로 받지 않는다"는 규칙이 설계 이유 말고도 이런 실행상의 이유를 하나 더 갖는 셈이다. 할당이 문제가 될 만한 경로라면 추측하지 말고 앞의 측정 방법이나 JFR 할당 이벤트로 확인한다.

    값 기반 클래스: ==, 동기화, 직렬화

    Optional 클래스 선언에는 @jdk.internal.ValueBased 애노테이션이 붙어 있고, Javadoc은 이 클래스가 값 기반(value-based) 클래스라고 밝힌다. Java SE 21 문서의 정의에 따르면 값 기반 클래스는 final 인스턴스 필드만 갖고, equals·hashCode·toString을 식별자(identity)가 아니라 필드 값으로 계산하며, 같은 값의 두 인스턴스를 자유롭게 바꿔 써도 동작이 달라지지 않고, 접근 가능한 생성자를 두지 않으며, 팩토리 메서드가 "호출마다 고유한 식별자"를 약속하지 않는다. 같은 문서는 이런 클래스의 인스턴스에 대해 참조 비교(==), 동기화, 식별 해시, 직렬화 같은 식별자에 민감한 연산으로 두 인스턴스를 구별하려 하지 말라고 하고, "식별자 관련 동작은 향후 릴리스에서 바뀔 수 있다. 예를 들어 동기화가 실패할 수 있다"고 적는다.

    이 규칙이 실제로 무엇을 뜻하는지 하나씩 보자. 먼저 ==. 현재 구현에서 Optional.ofNullable(null) == Optional.empty()는 true를 출력한다. 둘 다 같은 EMPTY를 돌려주기 때문이다. 그러나 empty()의 Javadoc이 "싱글턴이라는 보장은 없다"고 명시하므로, 이 결과에 기대는 코드는 명세가 아니라 구현에 기대는 코드다. 빈 값 판정은 isEmpty()로, 값 비교는 equals로 한다.

    동기화는 컴파일러와 JVM이 함께 막는다. JEP 390(Warnings for Value-Based Classes, JDK 16)은 값 기반 클래스 타입의 피연산자로 synchronized 문을 쓰면 javac가 경고하도록 했다. 이 경고 범주는 기본으로 켜져 있다.

    Optional lock = Optional.of("x");
synchronized (lock) { System.out.println("in"); }
    Sync.java:5: warning: [synchronization] attempt to synchronize on an instance of a value-based class
        synchronized (lock) { System.out.println("in"); }
        ^
1 warning

    경고일 뿐 컴파일과 실행은 된다. 하지만 같은 JEP가 도입한 HotSpot 진단 옵션으로 실행하면 런타임에서도 잡을 수 있다. -XX:+UnlockDiagnosticVMOptions -XX:DiagnoseSyncOnValueBasedClasses=2는 [valuebasedclasses] Synchronizing on object ... of klass java.util.Optional 같은 로그를 남기고, =1은 해당 지점에서 JVM을 치명적 오류로 멈춘다. JDK 21에서 직접 실행해 두 동작을 모두 확인했다. 미래의 JDK에서 Optional 같은 클래스가 식별자 없는 값으로 바뀌면 모니터를 걸 객체 자체가 없어질 수 있다는 것이 이 경고의 배경이다.

    직렬화도 막혀 있다. Optional은 Serializable을 구현하지 않는다(Serializable.class.isAssignableFrom(Optional.class)는 false). 그래서 Serializable 클래스에 Optional 필드를 두고 ObjectOutputStream으로 쓰면 java.io.NotSerializableException: java.util.Optional이 난다. 이 역시 직접 실행해 확인한 결과다. 세션에 저장되는 객체, 원격 호출로 오가는 객체, 캐시에 직렬화되는 객체에 Optional 필드가 있으면 이 예외를 만난다.

    옵셔널 베스트 프랙티스

    지금까지의 원리에서 사용 규칙을 끌어내 보자. 출발점은 JDK 21 Optional Javadoc의 API 노트다. "Optional은 '결과 없음'을 나타낼 분명한 필요가 있고 null을 쓰면 오류를 일으키기 쉬운 곳에서 메서드 반환 타입으로 쓰는 것을 주된 의도로 한다. Optional 타입의 변수는 절대 그 자체로 null이어서는 안 되며 항상 Optional 인스턴스를 가리켜야 한다." 나머지 규칙은 대부분 이 두 문장과 앞의 구조적 사실에서 나온다.

    1. 반환 타입에 쓴다. "찾았는데 없을 수 있음"이 정상인 조회 메서드(findById, findFirst, max)가 가장 알맞은 자리다. 스프링 데이터의 CrudRepository.findById, 스트림의 findFirst·max, 7회의 Collectors.maxBy가 모두 이 형태다.
    2. Optional을 반환하는 메서드는 절대 null을 반환하지 않는다. 호출자는 반환값에 바로 .map을 부를 것이고, null이면 Optional을 쓴 의미가 없어지는 것은 물론 더 이상한 곳에서 NPE가 난다. 결과가 없으면 Optional.empty()를 돌려준다.
    3. 필드에 두지 않는다. 직렬화가 안 되고, 객체마다 16바이트와 참조 한 단계가 늘고, 필드 자체가 null인 상태(초기화 전, 역직렬화나 프레임워크가 리플렉션으로 채우는 경우)를 막지 못한다. 필드는 nullable로 두고, 앞의 findAddress()처럼 조회 메서드에서 Optional.ofNullable(field)로 감싸 내보낸다.
    4. 매개변수로 받지 않는다. void send(Optional memo)는 호출자에게 Optional.empty(), Optional.of(x), 그리고 여전히 가능한 null이라는 세 가지 "없음"을 열어 준다. 선택적 인자는 오버로드(send()와 send(String memo))로 나누거나 nullable 매개변수를 문서화하는 편이 단순하다. 호출자가 가진 것이 Optional이라면 호출하기 전에 그쪽에서 풀어서 넘긴다.
    5. 컬렉션은 Optional로 감싸지 않는다. Optional> 대신 빈 리스트를 돌려준다. 컬렉션은 이미 "원소 0개"라는 빈 상태를 표현할 수 있으므로 두 겹의 "없음"은 호출자에게 구분할 이유가 없는 경우를 하나 더 만든다. 같은 이유로 List>처럼 컬렉션의 원소로 두는 것도 피하고, 빈 원소는 담지 않는다.
    6. isPresent() + get() 대신 의도를 드러내는 메서드를 쓴다. 기본값이면 orElse/orElseGet, 필수 값이면 orElseThrow, 값이 있을 때만 할 일이면 ifPresent, 변환이면 map/flatMap/filter다. get()이 꼭 필요해 보이면 orElseThrow()로 바꿔 "없으면 예외"라는 사실을 드러낸다.
    7. 기본값이 비싸거나 부작용이 있으면 orElseGet. 앞 절의 표 그대로다.
    8. 단순한 null 검사를 대신하려고 Optional을 만들지 않는다. 메서드 안의 지역 변수 하나를 검사하려고 Optional.ofNullable(x).ifPresent(...)를 쓰는 것은 if (x != null)보다 읽기 어렵고 객체를 하나 더 만든다. Optional은 메서드 경계에서 "없을 수 있음"을 전달할 때 가치가 있다.
    9. 기본형에는 기본형 특화 타입을, 성능 민감 경로에서는 측정 후 판단. OptionalInt 등은 박싱을 피한다. 핫 루프에서는 앞의 실험처럼 할당이 남을 수 있으므로 프로파일러로 확인한 뒤 결정한다.
    10. ==와 synchronized를 쓰지 않는다. 값 기반 클래스 규칙이다.

    경계에서의 변환도 정리해 두자. null을 돌려주는 오래된 API를 부르는 곳에서는 Optional.ofNullable로 감싸 안쪽 코드를 Optional 세계로 들인다. 반대로 null을 기대하는 API(일부 프레임워크의 콜백, 오래된 라이브러리)에 값을 넘겨야 하면 orElse(null)로 다시 풀어 준다. 이 두 변환을 각각 한 곳에 모아 두면, 그 사이의 코드는 null을 의식하지 않고 쓸 수 있다.

    정리: Optional이 해결하는 것과 해결하지 않는 것

    Optional이 해결하는 문제는 "값이 없을 수 있다"는 정보가 시그니처에서 사라지는 것이다. 반환 타입이 그 정보를 싣고, 값을 꺼내는 모든 메서드가 빈 경우의 처리를 요구하므로, 호출자가 그 경우를 잊기 어렵다. 그리고 map·flatMap·filter로 빈 값이 자동으로 전파되므로 중첩 null 검사가 파이프라인으로 펴진다.

    해결하지 않는 문제도 분명하다. 자바의 타입 체계는 여전히 모든 참조 타입에 null을 허용하므로 Optional 변수 자체가 null일 수 있고, 컴파일러는 그것을 막지 않는다. 기존 API 대부분은 여전히 null을 돌려준다. 그리고 Optional은 "왜 없는지"를 담지 못한다. 이유가 중요한 실패는 예외나 별도의 결과 타입으로 표현해야 한다. 마지막으로 즉시 평가는 Optional과 무관한 언어 규칙이다. orElse의 함정은 Optional을 이해해서가 아니라 자바가 인자를 언제 계산하는지를 이해해야 피할 수 있다.

    이 회차의 지연 평가 감각은 다음 회차들에서 계속 쓰인다. 9회의 디폴트 메서드는 Iterable.forEach나 Map.computeIfAbsent처럼 함수를 받는 메서드를 기존 인터페이스에 추가한 장치이고, 10회의 병렬 스트림에서는 "람다가 언제, 어느 스레드에서 실행되는가"가 정확성 문제로 바뀐다. 11회의 함수형 프로그래밍에서는 Optional의 map·flatMap이 보여 준 "값을 감싼 채 함수를 이어 붙이는" 구조와 부작용 없는 함수라는 조건을 더 일반적인 원리로 정리한다. 스프링으로 돌아가면 스프링 데이터의 findById, 그리고 ObjectProvider나 트랜잭션 템플릿처럼 "필요할 때 계산하는 객체"를 넘기는 API가 모두 같은 원리 위에 있다.

    null 타입
    JLS §4.1의 이름 없는 타입으로, 모든 참조 타입의 하위 타입이다. 그래서 어떤 참조 변수에든 null이 들어갈 수 있고, 시그니처만으로는 "값이 없을 수 있음"을 알 수 없다.
    Optional의 구조
    final 필드 value 하나를 가진 불변 final 클래스다. value가 null이면 비어 있음이고, 빈 값은 현재 구현에서 공유 객체 EMPTY를 쓴다. 그래서 null을 값으로 담을 수 없다.
    생성과 획득
    of는 null이면 즉시 NPE, ofNullable은 null이면 빈 값이다. 꺼낼 때는 비어 있을 때의 처리를 이름으로 드러내는 orElse·orElseGet·orElseThrow를 쓰고, get() 대신 같은 동작의 orElseThrow()(Java 10)를 쓴다.
    빈 값의 전파
    map·flatMap·filter는 비어 있으면 함수를 호출하지 않고 빈 값을 그대로 돌려준다. map은 결과를 ofNullable로 감싸 null을 빈 값으로 바꾸고, flatMap은 함수가 돌려준 Optional을 그대로 쓴다.
    즉시 평가
    JLS §15.7.4·§15.12.4에 따라 자바는 메서드 본문을 실행하기 전에 인자를 왼쪽부터 모두 계산한다. 연산자 가운데 피연산자를 모두 계산하지 않는 예외는 &&, ||, ? :뿐이다.
    지연 평가
    값 대신 값을 만드는 코드를 Supplier 같은 함수형 인터페이스 객체로 넘기고, 받는 쪽이 필요할 때만 호출하게 하는 방식이다. 람다 식 자체와 캡처한 값은 즉시 정해지고, 본문 실행만 미뤄진다.
    orElse vs orElseGet
    값이 있을 때 orElse의 인자는 이미 계산되어 버려지고, orElseGet의 공급자는 호출되지 않는다. 기본값에 비용이나 부작용이 있으면 orElseGet이 필수다.
    JIT와 Optional
    Optional 하나는 기본 설정의 HotSpot에서 16바이트다. 탈출하지 않으면 C2가 할당을 지울 수 있지만, 분기 프로파일과 버전에 따라 남을 수 있으며 필드·컬렉션에 저장된 Optional은 항상 할당된다.
    사용 규칙
    반환 타입 전용, Optional 반환 메서드는 null 금지, 필드·매개변수·컬렉션에 쓰지 않음, 값 기반 클래스이므로 ==·동기화 금지, Serializable이 아님.
    암묵적 null 검사와 빠른 예외
    HotSpot은 null 참조를 통한 메모리 접근이 일으키는 SIGSEGV/SIGBUS를 신호 처리기에서 받아 NPE로 바꾼다. Helpful NPE 메시지는 getMessage()가 처음 불릴 때 계산된다. 같은 지점의 NPE가 잦으면 C2가 미리 만든 예외 객체를 던져 스택과 메시지가 사라지며, -XX:-OmitStackTraceInFastThrow로 끌 수 있다.
    클래스 초기화와 인라이닝
    클래스는 JLS §12.4.1의 조건이 처음 일어날 때 초기화 락 아래에서 한 번만 초기화되므로 홀더 클래스로 스레드 안전한 지연 초기화를 얻는다(실패하면 다시 시도하지 않는다). C2가 Optional 할당을 지우려면 Optional을 주고받는 호출이 모두 인라인되어야 한다.

    실무에서 Optional 관련 장애는 대부분 Optional 자체가 아니라 평가 시점에서 나온다. "회원이 있는데도 게스트 회원 행이 계속 생긴다", "캐시 적중률은 높은데 원격 API 호출 수가 줄지 않는다", "정상 요청에서 이유 없이 유니크 제약 위반이 난다" 같은 증상을 보면 orElse(부작용이 있는 호출)이나 공급자가 아닌 값을 받는 대체 경로를 먼저 의심한다. 결과값은 정상이라 단위 테스트로 잡히지 않으므로, 기본값 계산에 부작용이 있는 메서드가 orElse의 인자로 들어가는지를 코드 리뷰 체크 항목으로 두는 편이 확실하다.

    값 기반 클래스(value-based class)
    식별자가 아니라 필드 값으로 동등성을 정하고, 같은 값의 인스턴스를 바꿔 써도 되는 클래스. ==, 동기화, 식별 해시 같은 식별자 민감 연산을 쓰지 말아야 한다.
    즉시 평가(eager evaluation)
    식을 만나는 즉시 값으로 계산하는 방식. 자바의 메서드 인자는 호출 전에 모두 즉시 평가된다.
    지연 평가(lazy evaluation)
    값이 실제로 필요할 때까지 계산을 미루는 방식. 자바에서는 계산을 함수형 인터페이스 객체로 감싸 넘겨 구현한다.
    이름에 의한 호출(call by name)
    인자를 계산 방법으로 넘기고 쓸 때마다 다시 계산하는 평가 전략. Supplier의 기본 동작이 이와 같다.
    필요에 의한 호출(call by need)
    처음 필요할 때 한 번 계산하고 결과를 기억해 재사용하는 평가 전략. 자바에서는 메모이제이션을 직접 구현해야 한다.
    Helpful NullPointerException
    JEP 358로 JDK 14에 들어오고 JDK 15부터 기본으로 켜진 기능. JVM이 바이트코드를 분석해 무엇이 null이었는지 예외 메시지에 적는다.
    탈출 분석(escape analysis)과 스칼라 치환(scalar replacement)
    객체가 만들어진 범위 밖으로 나가지 않음을 증명해 힙 할당 없이 필드를 지역 값으로 다루는 HotSpot C2의 최적화. 명세가 보장하는 동작은 아니다.
    암묵적 null 검사(implicit null check)
    비교 명령 없이, null 참조로 메모리에 접근할 때 생기는 하드웨어 폴트(SIGSEGV/SIGBUS)를 신호 처리기가 받아 NPE로 바꾸는 HotSpot의 구현 방식. 필드 오프셋이 첫 페이지 안일 때만 쓴다.
    인라이닝(inlining)
    호출되는 메서드의 본문을 호출한 쪽 코드 안에 펼쳐 넣는 JIT 최적화. C2의 탈출 분석은 인라인된 범위 안에서만 객체가 탈출하지 않음을 증명할 수 있다.
