    이 회차의 질문: 스트림의 끝에서 무엇을 만들어 내는가

    앞 회차들에서 본 것처럼 스트림 파이프라인은 중간 연산을 쌓아 두기만 하고, 종단 연산(terminal operation)이 호출되는 순간 원소를 하나씩 끌어당기며 실행된다. 종단 연산은 파이프라인의 끝에서 "무엇을 만들어 낼지"를 정한다. forEach는 아무것도 만들지 않고 부수 효과만 일으키고, count나 reduce는 값 하나를 만든다. 그런데 실무 코드에서 가장 자주 쓰는 종단 연산은 결과를 리스트, 집합, 맵, 통계값 같은 그릇에 담아 내는 일이다. 주문 목록을 도시별로 묶고, 고객별 합계를 맵으로 만들고, 이름을 쉼표로 이어 붙이는 일이 모두 여기에 속한다.

    이 일을 앞 회차에서 본 reduce로 할 수 있을까? reduce(identity, accumulator)는 "지금까지의 결과"와 "다음 원소"를 받아 새 결과를 돌려주는 함수를 반복 적용한다. 정수의 합처럼 결과가 작은 불변 값이면 이 방식이 자연스럽다. 하지만 결과가 문자열이나 리스트처럼 원소를 계속 쌓아 가는 그릇이면 문제가 생긴다. 문자열을 reduce("", (x, y) -> x + y)로 이어 붙이면 단계마다 지금까지의 문자열 전체를 복사한 새 String이 만들어진다. 길이 1인 문자열 n개를 이으면 복사되는 글자 수가 1 + 2 + … + n, 곧 n의 제곱에 비례한다. 자바 API 문서의 java.util.stream 패키지 설명도 같은 예를 들며 결과를 StringBuilder 같은 가변 그릇에 쌓는 편이 더 효율적이라고 말한다.

    그렇다면 reduce의 identity 자리에 new ArrayList<>()를 넣고 accumulator에서 add한 뒤 같은 리스트를 돌려주면 어떨까? 순차 실행에서는 결과가 맞게 나오지만 reduce의 계약을 어긴 코드다. OpenJDK 21의 ReduceOps를 보면 reduce를 실행하는 싱크(sink)는 시작할 때 state = seed, 곧 우리가 넘긴 identity 객체 그 자체를 상태로 잡는다. 병렬 실행에서는 데이터 조각마다 싱크가 하나씩 만들어지는데, 그 모든 싱크가 같은 ArrayList 객체에서 출발한다. 여러 스레드가 스레드 안전하지 않은 리스트 하나를 동시에 고치게 되는 것이다. identity는 "결합해도 아무것도 바꾸지 않는 값"이어야 하는데, 고쳐지는 순간 identity가 아니게 된다.

    그래서 스트림 API는 별도의 종단 연산을 둔다. 결과를 바꿔 끼우는 대신 그릇의 상태를 고치는 리덕션, 곧 가변 리덕션(mutable reduction)이다. 이름은 collect이고, 그 전략을 재사용할 수 있는 객체로 포장한 것이 Collector, 자주 쓰는 컬렉터를 모아 둔 유틸리티 클래스가 Collectors다. 이 회차는 세 인자 collect에서 출발해 Collector 인터페이스를 분해하고, collect가 JDK 안에서 어떤 경로로 실행되는지 소스로 확인한 다음, 컬렉션·맵·통계값을 만드는 기본 컬렉터와 groupingBy·partitioningBy 같은 다운스트림 컬렉터(downstream collector)를 차례로 다룬다. maxBy가 돌려주는 Optional의 자세한 사용법은 8회, 병렬 스트림과 포크/조인의 내부는 10회에서 다루므로 여기서는 컬렉터에 필요한 만큼만 짚는다.

    이 장의 핵심

    컬렉터는 "그릇을 만드는 함수(supplier), 원소 하나를 그릇에 넣는 함수(accumulator), 두 그릇을 합치는 함수(combiner), 그릇을 최종 결과로 바꾸는 함수(finisher)"의 묶음에 특성(characteristics) 표시를 붙인 객체다. reduce가 매 단계 새 값을 만들어 바꿔 끼운다면, collect는 데이터 조각마다 새 그릇을 하나씩 만들어 그 안을 고친다. 그릇이 조각마다 따로 있기 때문에 병렬에서도 동기화 없이 안전하다. groupingBy 같은 다운스트림 컬렉터는 이 네 함수를 감싸고 바꿔 끼워 더 큰 컬렉터를 조립하는 함수일 뿐이다.

    가변 리덕션의 뼈대: 세 인자 collect

    Stream에는 collect가 두 개 있다. 먼저 함수 세 개를 직접 받는 형태부터 보자. 시그니처는 R collect(Supplier supplier, BiConsumer accumulator, BiConsumer combiner)다. Javadoc은 이 연산의 결과가 아래 반복문과 같다고 정의한다.

    R result = supplier.get();
for (T element : this stream)
    accumulator.accept(result, element);
return result;

    세 함수의 역할을 하나씩 보자. supplier는 빈 결과 그릇(result container)을 만든다. accumulator는 그릇과 원소 하나를 받아 그 원소를 그릇에 반영한다. 반환 타입이 void인 BiConsumer라는 점이 핵심이다. reduce의 accumulator는 새 결과를 돌려줘야 하지만, collect의 accumulator는 아무것도 돌려주지 않고 받은 그릇을 고친다. 세 번째 combiner는 부분 결과 그릇 두 개를 받아 두 번째 그릇의 내용을 첫 번째 그릇에 접어 넣는다(fold). 반복문 정의에는 combiner가 등장하지 않는다. combiner는 병렬 실행에서 데이터를 나눠 각자 만든 그릇을 합칠 때만 쓰인다.

    ArrayList names = ORDERS.stream()
    .map(Order::customer)
    .collect(ArrayList::new, ArrayList::add, ArrayList::addAll);
System.out.println(names);
    [민수, 지영, 민수, 현우, 지영, 서연, 현우]

    메서드 참조 세 개가 각각 어느 함수형 인터페이스로 타깃 타이핑되는지 따져 보면 4회에서 본 메서드 참조 규칙을 그대로 복습할 수 있다. ArrayList::new는 인자 없는 생성자 참조로 Supplier>가 된다. ArrayList::add는 "임의 객체의 인스턴스 메서드 참조"라서 첫 번째 인자(그릇)가 수신 객체, 두 번째 인자(원소)가 add의 인자가 된다. add는 boolean을 돌려주지만 타깃 함수 타입이 void를 돌려주므로 반환값은 버려진다. ArrayList::addAll도 같은 방식으로 BiConsumer, ArrayList>가 되어 "오른쪽 리스트를 왼쪽 리스트에 모두 넣는다"는 combiner가 된다.

    combiner가 BiConsumer라는 사실에도 의미가 있다. 반환값이 없으니 합친 결과는 반드시 첫 번째 그릇에 남아야 한다. Javadoc도 combiner가 두 번째 그릇의 원소를 첫 번째 그릇에 접어 넣어야 한다고 명시한다. 뒤에서 볼 Collector의 combiner는 BinaryOperator라서 두 그릇 중 어느 쪽이든 돌려줄 수 있고, 그 덕분에 "작은 쪽을 큰 쪽에 붓는" 최적화가 가능해진다. 같은 개념의 함수인데 시그니처가 다른 이유가 여기에 있다.

    기본형 스트림(IntStream, LongStream, DoubleStream)에는 Collector를 받는 collect가 없고, collect(Supplier, ObjIntConsumer, BiConsumer) 같은 세 인자 형태만 있다. 컬렉터를 쓰려면 boxed()로 참조형 스트림으로 바꿔야 한다. 이 경우의 컴파일 오류는 뒤의 "타입으로 읽는 컬렉터"에서 직접 본다.

    Collector 인터페이스: 네 함수와 세 특성

    세 인자 collect는 쓸 때마다 함수 세 개를 새로 적어야 한다. "리스트로 모으기", "도시별로 묶기" 같은 전략을 이름 붙여 재사용하고, 그 전략끼리 조립하려면 함수 묶음을 하나의 객체로 포장해야 한다. 그 포장이 java.util.stream.Collector다. OpenJDK 21 소스에서 주석을 걷어 내면 인터페이스의 몸체는 다음과 같다.

    public interface Collector {
    Supplier supplier();
    BiConsumer accumulator();
    BinaryOperator combiner();
    Function finisher();
    Set characteristics();

    enum Characteristics {
        CONCURRENT,
        UNORDERED,
        IDENTITY_FINISH
    }
    // ... static of(...) 팩터리 두 개
}

    타입 매개변수 세 개의 뜻부터 정확히 잡아 두자. T는 입력 원소의 타입, A는 누적에 쓰는 가변 그릇의 타입(accumulation type), R은 최종 결과 타입이다. Javadoc은 A에 대해 "흔히 구현 세부로 숨겨진다(often hidden as an implementation detail)"고 적는다. 실제로 Collectors의 메서드들은 반환 타입을 Collector처럼 가운데를 물음표로 선언한다. 사용하는 쪽은 "무엇을 넣으면 무엇이 나오는가"만 알면 되고, 중간에 어떤 그릇을 쓰는지는 몰라도 된다는 설계다.

    네 함수 가운데 세 개는 세 인자 collect와 같다. 새로 생긴 것이 finisher다. 그릇 타입과 결과 타입이 다를 수 있기 때문이다. 문자열 연결은 StringBuilder에 쌓고 마지막에 String으로 바꾸고, 평균은 합계와 개수를 쌓은 뒤 마지막에 나눗셈을 한다. 그릇이 곧 결과인 경우(리스트로 모으기)에는 finisher가 항등 함수가 된다.

    특성(characteristics)은 리덕션을 실행하는 쪽에 주는 힌트다. 세 가지가 있다.

    특성뜻실행하는 쪽이 얻는 것
    IDENTITY_FINISHfinisher가 항등 함수이고, 그릇 A를 R로 검사 없이 캐스팅해도 된다finisher 호출을 건너뛴다
    UNORDERED결과가 입력 원소의 만남 순서(encounter order)를 보존하지 않는다순서를 지키기 위한 제약을 풀 수 있다
    CONCURRENT여러 스레드가 그릇 하나에 accumulator를 동시에 호출해도 된다병렬일 때 그릇을 하나만 만들어 공유하는 동시 리덕션이 가능하다

    Collector의 Javadoc은 순차 실행과 병렬 실행의 결과가 같아지도록 두 가지 제약을 요구한다. 항등 제약(identity constraint)은 부분 결과 a를 빈 그릇과 합쳐도 같은 결과여야 한다는 것, 곧 combiner.apply(a, supplier.get())가 a와 동등해야 한다는 것이다. 결합 제약(associativity constraint)은 계산을 나눠서 해도 결과가 같아야 한다는 것이다. 원소 t1, t2를 한 그릇에 차례로 넣은 결과와, 각자 다른 그릇에 넣은 뒤 combiner로 합친 결과가 finisher를 거친 뒤 같아야 한다. 이 두 제약이 지켜지면 실행하는 쪽은 데이터를 마음대로 쪼개고 합칠 수 있다.

    반대 방향의 약속도 있다. Stream.collect처럼 컬렉터를 실행하는 라이브러리는 supplier·accumulator·combiner가 만든 결과를 다시 accumulator·combiner·finisher에 넘기거나 호출자에게 돌려주는 것 말고는 아무 일도 하지 않아야 하고, 한 번 combiner나 finisher에 넘긴 그릇을 다시 accumulator에 넘기지 않아야 한다. 또 동시성(CONCURRENT)이 없는 컬렉터라면 각 그릇은 한 번에 한 스레드에만 갇혀(serially thread-confined) 있어야 한다. Javadoc은 이 덕분에 컬렉터가 따로 동기화를 구현하지 않아도 병렬 수집이 가능하다고 설명한다. 컬렉터를 쓰는 우리가 ArrayList처럼 스레드 안전하지 않은 그릇을 마음 놓고 쓸 수 있는 근거가 바로 이 약속이다.

    Collector.of로 직접 만들고 호출 순서 관찰하기

    인터페이스를 직접 구현해도 되지만 보통은 정적 팩터리 Collector.of를 쓴다. 두 가지 형태가 있다. 함수 세 개만 받는 of(supplier, accumulator, combiner, characteristics...)는 그릇이 곧 결과인 컬렉터를 만들고, OpenJDK 21 소스를 보면 넘긴 특성에 IDENTITY_FINISH를 항상 더한다. finisher까지 받는 of(supplier, accumulator, combiner, finisher, characteristics...)는 넘긴 특성만 그대로 쓴다. 각 함수가 언제 불리는지 눈으로 보기 위해, 호출될 때마다 한 줄씩 출력하는 컬렉터를 만들어 보자.

    Collector, String> logging = Collector.of(
    () -> { System.out.println("  supplier"); return new ArrayList<>(); },
    (acc, s) -> { System.out.println("  accumulator(" + acc + ", " + s + ")"); acc.add(s); },
    (a, b) -> { System.out.println("  combiner"); a.addAll(b); return a; },
    acc -> { System.out.println("  finisher(" + acc + ")"); return String.join("/", acc); }
);
System.out.println("start");
String r = Stream.of("a", "b", "c").collect(logging);
System.out.println("result=" + r + " characteristics=" + logging.characteristics());

  finisher([a, b, c])
result=a/b/c characteristics=[]

    출력을 한 줄씩 추적하면 Javadoc의 반복문 정의와 정확히 일치한다. 순차 스트림에서 supplier는 한 번, accumulator는 원소마다 한 번, finisher는 마지막에 한 번 불렸고 combiner는 한 번도 불리지 않았다. 그릇은 하나뿐이니 합칠 상대가 없다. 특성을 넘기지 않았으므로 다섯 인자 of는 빈 집합을 특성으로 쓴다. 같은 컬렉터를 parallel() 스트림에 쓰면 supplier가 여러 번, combiner가 여러 번 불리는데, 그 횟수는 다음 절에서 실행 경로를 본 뒤에 설명한다.

    collect의 실행 경로: OpenJDK 21 소스로 따라가기

    컬렉터는 함수 묶음일 뿐이고, 그 함수들을 언제 몇 번 부를지는 Stream.collect의 구현이 정한다. 우리가 다루는 객체 스트림의 실제 클래스는 java.util.stream.ReferencePipeline이다. OpenJDK 21의 collect(Collector) 구현은 열다섯 줄 남짓이다.

    public final  R collect(Collector collector) {
    A container;
    if (isParallel()
            && (collector.characteristics().contains(Collector.Characteristics.CONCURRENT))
            && (!isOrdered() || collector.characteristics().contains(Collector.Characteristics.UNORDERED))) {
        container = collector.supplier().get();
        BiConsumer accumulator = collector.accumulator();
        forEach(u -> accumulator.accept(container, u));
    }
    else {
        container = evaluate(ReduceOps.makeRef(collector));
    }
    return collector.characteristics().contains(Collector.Characteristics.IDENTITY_FINISH)
           ? (R) container
           : collector.finisher().apply(container);
}

    분기는 두 갈래다. 첫 번째 갈래는 동시 리덕션(concurrent reduction)이다. 스트림이 병렬이고, 컬렉터가 CONCURRENT이며, 스트림에 순서가 없거나 컬렉터가 UNORDERED일 때만 탄다. 이때는 supplier를 딱 한 번 불러 그릇을 하나 만들고, 병렬 forEach로 모든 스레드가 그 그릇 하나에 accumulator를 호출한다. combiner는 쓰이지 않는다. 그래서 그릇 자체가 동시 접근에 안전해야 하고(ConcurrentHashMap 같은), 원소가 들어가는 순서는 결정되지 않는다. 세 조건은 java.util.stream 패키지 문서의 "동시 리덕션" 설명과 같다.

    나머지는 모두 두 번째 갈래로 간다. ReduceOps.makeRef(collector)는 컬렉터의 세 함수를 꺼내 "리듀싱 싱크(ReducingSink)"라는 지역 클래스를 만든다. 싱크는 OpenJDK 스트림 구현에서 파이프라인의 각 단계가 원소를 다음 단계로 밀어 넣을 때 쓰는 내부 인터페이스 Sink(Consumer를 확장한다)의 구현이다.

    class ReducingSink extends Box
        implements AccumulatingSink {
    @Override
    public void begin(long size) {
        state = supplier.get();          // 그릇을 새로 만든다
    }

    @Override
    public void accept(T t) {
        accumulator.accept(state, t);    // 그릇을 고친다
    }

    @Override
    public void combine(ReducingSink other) {
        state = combiner.apply(state, other.state);
    }
}

    이 회차의 첫 절에서 본 reduce용 싱크와 나란히 놓으면 두 연산의 차이가 코드 한 줄로 드러난다. reduce의 싱크는 begin에서 state = seed로 우리가 넘긴 identity 객체를 그대로 상태로 삼고, accept에서 state = reducer.apply(state, t)로 상태를 바꿔 끼운다. collect의 싱크는 begin에서 supplier로 새 그릇을 만들고, accept에서 상태 변수는 그대로 둔 채 그 그릇의 내용을 고친다. 싱크가 여러 개 만들어지는 병렬 실행에서 이 차이는 "모두가 같은 객체를 고친다"와 "각자 자기 그릇을 고친다"의 차이가 된다.

    순차 실행이면 evaluateSequential이 싱크를 하나 만들고 wrapAndCopyInto로 소스의 원소를 파이프라인 단계들을 거쳐 그 싱크에 흘려보낸다. begin이 한 번 불리므로 supplier도 한 번이고, combine은 불리지 않는다. 앞의 로그가 그 결과다. 병렬 실행이면 evaluateParallel이 ReduceTask를 만든다. 이 작업은 포크/조인 프레임워크 위에서 스플리터레이터(spliterator)를 trySplit으로 거듭 쪼개 작업 트리를 만들고, 잎(leaf) 작업마다 op.makeSink()로 새 싱크를 만들어 자기 몫의 원소를 처리한다. 잎이 아닌 작업은 두 자식이 끝나면 onCompletion에서 왼쪽 자식의 결과에 오른쪽 자식의 결과를 combine한다. 이진 트리에서 잎이 n개면 안쪽 노드는 n-1개이므로, supplier는 잎 수만큼, combiner는 그보다 하나 적게 불린다.

    AtomicInteger sup = new AtomicInteger(), comb = new AtomicInteger();
Collector, List> c = Collector.of(
    () -> { sup.incrementAndGet(); return new ArrayList<>(); },
    List::add,
    (x, y) -> { comb.incrementAndGet(); x.addAll(y); return x; });
List r = IntStream.range(0, 1000).boxed().parallel().collect(c);
System.out.println(r.equals(IntStream.range(0, 1000).boxed().toList())
    + " sup=" + sup + " comb=" + comb);
    true sup=32 comb=31

    supplier 32번, combiner 31번은 이 컴퓨터에서 나온 숫자다. 작업을 몇 조각으로 나눌지는 공용 풀의 병렬성(parallelism)과 데이터 크기에서 정해지므로 코어 수가 다르면 숫자가 달라진다. 달라지지 않는 것은 두 가지다. combiner 횟수는 supplier 횟수보다 하나 적고, 결과 리스트는 순차 실행과 같은 순서의 0부터 999까지다. 순서가 보존되는 것은 순서 있는(ORDERED) 스플리터레이터의 trySplit이 앞부분을 떼어 왼쪽 자식에게 주고, ReduceTask가 언제나 왼쪽 결과에 오른쪽 결과를 합치기 때문이다. 이 컬렉터는 UNORDERED가 아니므로 실행하는 쪽은 만남 순서를 지켜 합친다.

    마지막 줄의 삼항 연산자도 중요하다. 컬렉터가 IDENTITY_FINISH를 가지면 finisher를 부르지 않고 그릇을 (R) container로 캐스팅해 돌려준다. 제네릭은 소거(erasure)되므로 이 캐스팅은 실행 시점에 아무것도 검사하지 않는 비검사 캐스팅(unchecked cast)이다. 그렇다면 특성을 거짓으로 붙이면 어떻게 될까? 그릇은 StringBuilder, 결과는 String인 컬렉터에 IDENTITY_FINISH를 붙여 보자.

    Collector liar = Collector.of(
    StringBuilder::new, StringBuilder::append,
    (a, b) -> a.append(b),
    sb -> { System.out.println("  finisher called"); return sb.toString(); },
    Collector.Characteristics.IDENTITY_FINISH);
try {
    String s = Stream.of("x", "y").collect(liar);
    System.out.println(s);
} catch (ClassCastException e) {
    System.out.println(e.getMessage());
}
Object o = Stream.of("x", "y").collect(liar);
System.out.println("object result class=" + o.getClass().getName());

    "finisher called"는 한 번도 출력되지 않았다. 특성을 믿고 finisher를 건너뛴 것이다. 흥미로운 것은 예외가 터진 위치다. collect 안의 (R) container는 소거 후 아무 검사도 하지 않으므로 StringBuilder가 그대로 빠져나온다. 예외는 호출한 쪽에서 난다. 결과를 String 변수에 담는 메서드를 javap로 보면 컴파일러가 넣은 checkcast가 보이고, Object 변수에 담는 메서드에는 그 명령이 없다. 그래서 두 번째 호출은 예외 없이 StringBuilder를 돌려준다.

    바이트코드 수준에서 Stream.collect의 반환 타입은 Object다. 제네릭 타입 R은 컴파일러의 타입 검사에만 존재하고, 실제 타입 확인은 값을 구체 타입으로 쓰는 지점에 컴파일러가 넣는 checkcast가 맡는다. 특성은 이렇게 실행 경로를 실제로 바꾸는 약속이므로, 직접 컬렉터를 만들 때는 사실인 특성만 붙여야 한다.

    같은 컬렉터가 세 가지 실행 경로에서 그릇을 몇 개 만들고 combiner를 어디서 부르는지 한눈에 비교한다. 가로로 3개의 패널을 나란히 배치한 기술 다이어그램, 흰 배경, 플랫한 선 스타일. 왼쪽 패널 제목 "순차": 위에서 아래로 원소 아이콘 5개가 화살표를 따라 하나의 그릇(둥근 사각형, 라벨 "그릇 1개")으로 들어가고, 그 아래 "finisher" 상자로 이어진다. 가운데 패널 제목 "병렬": 위쪽에 데이터 막대가 4조각으로 쪼개지고, 각 조각 아래에 작은 그릇 4개가 있으며, 그릇 둘씩 아래로 모여 "combiner" 마름모 2개, 다시 둘이 모여 "combiner" 마름모 1개, 그 아래 "finisher" 상자로 이어지는 역삼각형 트리. 오른쪽 패널 제목 "동시 리덕션": 스레드 아이콘 4개에서 화살표가 모두 가운데의 큰 그릇 하나(라벨 "공유 그릇")로 들어가며, 그릇 옆에 "ConcurrentHashMap" 라벨이 있고 combiner는 없다. 각 패널 아래에 작은 회색 글씨로 "supplier 1회", "supplier = 잎 수", "supplier 1회"를 적는다. 같은 컬렉터라도 실행 경로에 따라 그릇의 수와 combiner 호출이 달라진다. 순서를 지키는 병렬 실행은 언제나 왼쪽에 오른쪽을 합친다.

    한 가지 더, ReduceOps.makeRef(collector)가 만드는 연산은 getOpFlags()에서 컬렉터가 UNORDERED면 StreamOpFlag.NOT_ORDERED 플래그를 돌려준다. 종단 연산이 "나는 순서를 신경 쓰지 않는다"고 파이프라인에 알리는 것이다. 이 플래그가 병렬 실행에서 어떤 최적화로 이어지는지는 10회에서 병렬 스트림과 함께 본다.

    컬렉터 1: 컬렉션으로 모으기

    이제 Collectors가 제공하는 기성 컬렉터를 보자. 가장 기본은 원소를 컬렉션에 그대로 담는 컬렉터들이다. OpenJDK 21 소스에서 toList()의 구현은 한 문장이다.

    public static 
Collector> toList() {
    return new CollectorImpl<>(ArrayList::new, List::add,
                               (left, right) -> { left.addAll(right); return left; },
                               CH_ID);
}

    CollectorImpl은 Collectors 안의 패키지 전용 레코드로, 네 함수와 특성 집합을 필드로 갖고 Collector를 구현한다. finisher를 받지 않는 생성자는 항등 캐스팅 함수를 채워 넣는다. CH_ID는 IDENTITY_FINISH 하나만 담은 불변 집합이다. 그러니 toList()는 "새 ArrayList를 만들고, 원소마다 add하고, 병렬이면 왼쪽에 오른쪽을 addAll하고, 그릇을 그대로 결과로 돌려주는" 컬렉터다. 그런데 Javadoc은 이 구현을 약속하지 않는다. "반환되는 List의 타입, 가변성, 직렬화 가능성, 스레드 안전성에 대해 아무것도 보장하지 않는다"고 적고, 더 많은 제어가 필요하면 toCollection(Supplier)를 쓰라고 한다.

    리스트로 모으는 방법은 세 가지가 더 있다. 자바 10에 들어온 Collectors.toUnmodifiableList(), 자바 16에 들어온 Stream.toList(), 그리고 그릇 종류를 직접 고르는 toCollection(ArrayList::new)다. 차이를 실행으로 확인해 보자.

    List a = Stream.of("p", "q").collect(Collectors.toList());
List b = Stream.of("p", "q").toList();
List c = Stream.of("p", "q").collect(Collectors.toUnmodifiableList());

a.add("r");                                   // 성공: [p, q, r]

    표의 마지막 열은 명세가 아니라 이번 실행에서 getClass()로 본 구현이다. 원소 두 개를 담은 toUnmodifiableList()는 원소 한두 개짜리 전용 클래스 List12를 썼고, Stream.toList()는 같은 원소 수에서도 ListN을 썼다. 이유는 소스에 있다. toUnmodifiableList()는 ArrayList에 모은 뒤 finisher에서 listFromTrustedArray로 불변 리스트를 만드는데, 이 경로는 null을 허용하지 않고 크기에 따라 전용 클래스를 고른다. Stream.toList()는 ReferencePipeline에서 재정의되어 컬렉터를 아예 쓰지 않고 toArray()로 배열을 만든 다음 listFromTrustedArrayNullsAllowed로 감싼다. null을 허용해야 하므로 null을 받을 수 있는 ListN을 쓴다. 인터페이스의 디폴트 구현은 Collections.unmodifiableList(new ArrayList<>(Arrays.asList(this.toArray())))과 같은 결과를 내도록 정해져 있다.

    그래서 선택 기준은 이렇게 정리된다. 결과를 읽기만 할 것이면 Stream.toList()가 가장 짧고, null이 섞일 수 있는 데이터에도 쓸 수 있다. null이 들어오는 것 자체를 버그로 보고 즉시 실패하게 하고 싶으면 toUnmodifiableList()를 쓴다. 결과에 원소를 더 추가해야 하면 Collectors.toList()가 지금 구현상 ArrayList를 주더라도 명세가 보장하지 않으므로 toCollection(ArrayList::new)로 의도를 드러내는 편이 안전하다. java.util.stream 패키지 문서가 드는 예처럼 forEach 안에서 바깥 ArrayList에 add하는 코드는 이 셋 중 하나로 바꿔야 한다. 그 코드는 병렬에서 스레드 안전하지 않은 리스트 하나를 여러 스레드가 고치게 만든다.

    집합 쪽도 같은 구조다. toSet()은 HashSet을 그릇으로 쓰고 특성은 UNORDERED와 IDENTITY_FINISH다. 이 컬렉터의 combiner는 조금 다르다. OpenJDK 21 구현은 두 집합의 크기를 비교해 작은 쪽을 큰 쪽에 붓고, 큰 쪽을 돌려준다. combiner가 BinaryOperator라서 어느 그릇이든 결과가 될 수 있기에 가능한 최적화다. 순서가 의미 없는 집합이라 왼쪽·오른쪽을 바꿔도 결과가 동등하다. toUnmodifiableSet()은 마지막에 Set.of(set.toArray())로 불변 집합을 만들고, 정렬된 집합이 필요하면 toCollection(TreeSet::new)을 쓴다.

    컬렉터 1 (계속): toMap과 중복 키

    원소 하나를 키와 값 한 쌍으로 바꿔 맵에 담는 컬렉터가 toMap이다. 인자는 키를 뽑는 함수(keyMapper)와 값을 뽑는 함수(valueMapper)다. 주문 데이터로 "고객 → 주문 금액" 맵을 만들어 보자. 민수는 주문이 두 건이다.

}

    return (map, element) -> {
    K k = keyMapper.apply(element);
    V v = Objects.requireNonNull(valueMapper.apply(element));
    V u = map.putIfAbsent(k, v);
    if (u != null) throw duplicateKeyException(k, u, v);
};

    세 가지가 읽힌다. 첫째, 값이 null이면 requireNonNull에서 즉시 NullPointerException이 난다. 둘째, 키는 검사하지 않으므로 그릇이 HashMap이면 null 키가 들어간다. 실제로 Stream.of("k").collect(toMap(k -> (String) null, k -> k))는 {null=k}를 만든다. 셋째, putIfAbsent가 기존 값을 돌려주면 중복이므로 예외를 던진다. 첫 번째 값은 이미 맵에 들어간 12000, 두 번째 값은 지금 넣으려던 89000이라 메시지가 그렇게 나온다. 병렬에서 쓰이는 combiner(uniqKeysMapMerger)도 오른쪽 맵의 항목을 하나씩 putIfAbsent하며 같은 방식으로 중복을 잡는다.

    중복이 정상인 데이터라면 세 번째 인자로 병합 함수(merge function)를 준다. 이 형태의 accumulator는 map.merge(key, value, mergeFunction) 한 줄이다. Map.merge는 키가 없으면 값을 넣고, 있으면 기존 값과 새 값을 병합 함수에 넘겨 그 결과로 바꾼다. 네 번째 인자로 맵 팩터리를 주면 그릇 종류도 고를 수 있다.

    Map sum = ORDERS.stream()
    .collect(toMap(Order::customer, Order::amount, Integer::sum, TreeMap::new));
Map last = ORDERS.stream()
    .collect(toMap(Order::customer, Order::amount, (x, y) -> y, LinkedHashMap::new));
Map hm = ORDERS.stream()
    .collect(toMap(Order::customer, Order::amount, Integer::sum));
System.out.println(sum);
System.out.println(last);

    TreeMap은 키의 자연 순서(문자열의 사전 순)로, LinkedHashMap은 키가 처음 들어간 순서로 순회한다. (x, y) -> y는 "나중 값이 이긴다"는 병합 함수라서 민수의 값이 89000으로 남았다. 맵 팩터리를 주지 않으면 그릇은 HashMap이고 순회 순서는 명세가 정하지 않는다. 세 번째 줄의 순서는 키 문자열의 해시값과 HashMap 구현에서 나온 것일 뿐이므로, 출력 순서가 의미 있는 코드라면 반드시 맵 팩터리를 지정해야 한다.

    병합 함수가 있는 경로에서도 null 값은 허용되지 않는다. 이번에는 requireNonNull 때문이 아니라 HashMap.merge가 첫 줄에서 value == null이면 NullPointerException을 던지기 때문이다. 그러니 toMap의 값 함수가 null을 돌려줄 수 있다면 형태와 상관없이 실패한다. 값이 없을 수 있는 데이터는 Optional이나 기본값으로 바꾸거나, groupingBy처럼 다른 컬렉터를 써야 한다. toUnmodifiableMap은 toMap의 결과를 collectingAndThen으로 감싸 Map.ofEntries로 불변 맵을 만드는 컬렉터이고, toConcurrentMap은 그릇이 ConcurrentHashMap이며 특성이 CONCURRENT, UNORDERED, IDENTITY_FINISH인 판이다.

    컬렉터 2: 하나의 값으로 줄이기

    두 번째 부류는 원소들을 개수, 합계, 평균, 최댓값, 문자열 하나처럼 값 하나로 줄이는 컬렉터다. 스트림에 이미 count(), max(), 기본형 스트림의 sum()이 있는데 왜 같은 일을 하는 컬렉터가 따로 있을까? 이 컬렉터들의 진짜 쓰임새는 단독이 아니라 다음 절의 groupingBy 안에 다운스트림으로 들어가 "그룹마다" 개수와 합계를 내는 데 있다. 스트림의 종단 연산은 스트림 전체에만 적용되지만, 컬렉터는 객체라서 다른 컬렉터에 인자로 넘길 수 있다.

    먼저 구현을 보면 공통 패턴이 하나 보인다. 그릇이 배열이다.

    public static  Collector
summingInt(ToIntFunction mapper) {
    return new CollectorImpl<>(
            () -> new int[1],
            (a, t) -> { a[0] += mapper.applyAsInt(t); },
            (a, b) -> { a[0] += b[0]; return a; },
            a -> a[0], CH_NOID);
}

public static  Collector
averagingInt(ToIntFunction mapper) {
    return new CollectorImpl<>(
            () -> new long[2],
            (a, t) -> { a[0] += mapper.applyAsInt(t); a[1]++; },
            (a, b) -> { a[0] += b[0]; a[1] += b[1]; return a; },
            a -> (a[1] == 0) ? 0.0d : (double) a[0] / a[1], CH_NOID);
}

public static  Collector
counting() {
    return summingLong(e -> 1L);
}

    왜 Integer가 아니라 길이 1짜리 int 배열일까? accumulator는 BiConsumer라서 새 값을 돌려줄 수 없고, 받은 그릇을 고쳐야 한다. 그런데 Integer는 불변 객체라 고칠 수 없다. 그래서 고칠 수 있는 칸 하나, 곧 원소가 하나인 배열을 가변 상자(mutable box)로 쓴다. 배열 객체는 힙에 하나 만들어지고, 누적하는 동안 그 칸의 int 값만 바뀐다. 원소마다 Integer 객체를 새로 만드는 박싱(boxing)이 없다는 것도 장점이다. 결과 Integer로의 박싱은 finisher a -> a[0]에서 한 번만 일어난다. finisher가 필요하므로 특성은 CH_NOID(빈 집합)다.

    그릇의 원소 타입은 결과에 그대로 영향을 준다. summingInt의 칸은 int라서 합이 int 범위를 넘으면 JLS의 정수 덧셈 규칙대로 조용히 넘친다(overflow). 반면 averagingInt는 합계를 long 칸에 쌓고, summarizingInt가 쓰는 IntSummaryStatistics도 합계 필드가 long이다. 같은 입력으로 확인해 보자.

    System.out.println(Stream.of(Integer.MAX_VALUE, 1).collect(summingInt(x -> x)));
System.out.println(Stream.of(Integer.MAX_VALUE, 1).collect(averagingInt(x -> x)));
System.out.println(Stream.of(Integer.MAX_VALUE, 1).collect(summarizingInt(x -> x)).getSum());

    합계가 int 범위를 넘을 수 있으면 summingLong을 쓰거나 summarizingInt의 getSum()을 쓴다. counting()이 summingLong(e -> 1L)로 구현되어 결과가 Long이라는 점도 기억해 두자. 이 타입 때문에 생기는 컴파일 오류를 뒤에서 본다. summingDouble과 averagingDouble은 double[3], double[4]를 그릇으로 쓰는데, 소스 주석이 설명하듯 보정 합산(compensated summation, 소스 주석의 표현으로는 Kahan summation)으로 반올림 오차를 줄이는 값과 단순 합계를 따로 들고 다니기 때문이다. Javadoc은 그래도 부동소수점 합은 값이 기록되는 순서에 따라 달라질 수 있다고 적는다.

    summarizingInt는 개수·합계·최솟값·최댓값·평균을 한 번에 모은다. 그릇 IntSummaryStatistics가 곧 결과이므로 특성은 IDENTITY_FINISH이고, 원소마다 accept(int)가 count를 늘리고 sum에 더하고 Math.min, Math.max로 최솟값과 최댓값을 갱신한다. 빈 스트림이면 최솟값과 최댓값이 초깃값 그대로 남는다.

    System.out.println(ORDERS.stream().filter(o -> o.city().equals("서울")).collect(summarizingInt(Order::amount)));
System.out.println(Stream.empty().collect(summarizingInt(Order::amount)));

    빈 입력의 최솟값이 Integer.MAX_VALUE로 나오는 것은 버그가 아니라 "아직 아무 값도 보지 않았다"는 초기 상태다. 그래서 통계 객체를 쓸 때는 getCount()가 0인지 먼저 확인해야 한다. toString의 형식은 Javadoc이 "명세하지 않으며 구현과 버전에 따라 달라질 수 있다"고 밝히므로 파싱 대상으로 삼지 않는다. 평균은 개수가 0이면 0.0을 돌려주도록 정해져 있다. averagingInt도 빈 입력에서 0.0을 돌려준다.

    최솟값과 최댓값은 minBy, maxBy가 맡는다. 결과 타입이 Optional인 이유는 빈 입력에서 돌려줄 원소가 없기 때문이다. 구현은 reducing(BinaryOperator.maxBy(comparator))이고, 이 reducing은 "값이 있는가"와 "현재 값"을 필드로 든 지역 클래스 OptionalBox를 그릇으로 쓴다. 첫 원소는 그대로 담고, 그다음부터는 이항 연산자로 줄이며, finisher가 Optional.ofNullable(a.value)로 포장한다. BinaryOperator.maxBy의 구현은 comparator.compare(a, b) >= 0 ? a : b라서 같은 크기의 원소가 여럿이면 먼저 누적된 쪽이 남는다. 금액이 같은 두 원소에 maxBy를 적용하면 순차 스트림에서 앞의 원소가 결과다.

    reducing은 세 가지 형태가 있다. reducing(identity, op)와 reducing(identity, mapper, op)는 new Object[] { identity }, 곧 identity를 담은 길이 1짜리 배열을 그릇으로 쓰고, 원소마다 a[0] = op.apply(a[0], t)로 칸의 값을 바꿔 끼운다. 그릇은 가변이지만 그 안에서 일어나는 일은 불변 리덕션이다. 이 구조 덕분에 reduce와 같은 계산을 groupingBy의 다운스트림 자리에서 쓸 수 있다. 다만 그룹마다 Integer 같은 불변 객체를 계속 새로 만드는 것은 reduce와 같으므로, 정수 합계라면 summingInt가 더 직접적이다.

    문자열 연결은 joining이다. 인자 없는 joining()은 StringBuilder를 그릇으로 쓰고 finisher StringBuilder::toString으로 마무리한다. 구분자·접두사·접미사를 받는 형태는 StringJoiner를 그릇으로 쓰고 combiner로 StringJoiner::merge를 쓴다. 이 회차 처음의 문제, 곧 reduce로 문자열을 이을 때 단계마다 전체를 복사하는 문제가 여기서 해결된다. 그릇 하나에 계속 덧붙이므로, 지금까지 쌓인 내용 전체를 옮기는 복사는 내부 버퍼가 모자라 커질 때만 일어난다. 입력 원소 타입이 CharSequence로 정해져 있어서, 주문 객체를 바로 넣을 수는 없고 map(Order::customer)나 다음 절의 mapping으로 문자열을 먼저 뽑아야 한다.

    그릇의 크기: 객체 헤더로 계산하는 summingInt와 reducing의 비용

    앞 절에서 summingInt는 박싱 없이 int[1]의 칸 하나를 고치고, reducing은 칸 안의 불변 값을 원소마다 새로 만든다고 했다. 이 차이가 실제로 몇 바이트인지 말하려면 객체 하나가 힙에서 몇 바이트를 차지하는지부터 알아야 한다. 그런데 이것은 명세가 정하지 않는다. JVMS 2.7은 자바 가상 머신이 객체의 내부 구조를 특정하게 강제하지 않는다고 적는다. 그래서 이 절의 숫자는 모두 OpenJDK 21 HotSpot, 64비트, 기본 옵션이라는 범위 안에서만 맞는 값이다.

    HotSpot에서 모든 자바 객체는 src/hotspot/share/oops/oop.hpp의 oopDesc로 시작한다. 첫 필드는 _mark(마크 워드, markWord)로 64비트 VM에서 8바이트이며 락 상태와 GC 나이(age), 식별 해시코드(identity hash)를 담는다. 둘째 필드 _metadata는 공용체(union)로, 객체의 클래스를 가리키는 Klass*이거나 그것을 32비트로 줄인 narrowKlass다. 압축 클래스 포인터(UseCompressedClassPointers)가 켜져 있으면 뒤의 것을 쓰므로 일반 객체의 헤더는 8 + 4 = 12바이트다. 배열은 여기에 길이가 붙는다. arrayOop.hpp의 주석은 배열의 배치를 "markWord, Klass*, length" 순서로 적고, 클래스 포인터가 압축되어 있으면 길이 필드가 _klass 필드의 나머지 절반을 차지한다고 설명한다. 그리고 header_size_in_bytes()는 길이 필드 끝을 HeapWordSize(8바이트)의 배수로 올린 값을 배열 헤더 크기로 쓴다. 마지막으로 객체 전체 크기는 ObjectAlignmentInBytes의 배수로 올린다. 이 환경에서 java -XX:+PrintFlagsFinal -version으로 본 값은 UseCompressedClassPointers = true, UseCompressedOops = true(참조 필드 4바이트), ObjectAlignmentInBytes = 8이다.
