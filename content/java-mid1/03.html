    문자열이 특별 대우를 받는 이유

    자바에서 문자 하나는 기본형 char다. 문자 여러 개를 이어 놓은 문자열을 기본형만으로 다루려면 char[] 배열을 쓸 수밖에 없다. 그러면 두 문자열이 같은지 보려고 반복문을 돌려야 하고, 뒤에 한 글자를 붙이려면 더 큰 배열을 만들어 옮겨 담아야 한다. 배열은 누구나 원소를 바꿀 수 있으니, 다른 메서드에 넘겨준 문자열이 돌아왔을 때 그대로일지도 장담할 수 없다.

    String 클래스가 이 일을 맡는다. java.lang 패키지에 있어서 import 없이 쓰고, 선언은 public final class String이다. 여기까지는 보통의 클래스와 다르지 않다. 다른 점은 언어가 이 클래스 하나를 위해 문법을 두 가지 마련해 두었다는 것이다. 큰따옴표로 감싼 문자열 리터럴(string literal, JLS 3.10.5)은 new 없이 String 객체를 가리키는 참조가 되고, + 연산자는 피연산자 가운데 하나가 String이면 문자열 연결(string concatenation, JLS 15.18.1)로 동작한다.

    이런 대우에는 이유가 있다. 문자열은 프로그램이 다루는 데이터의 큰 부분을 차지한다. 사용자 이름, 요청 경로, SQL, JSON, 로그 메시지가 전부 문자열이다. JDK의 문자열 표현을 바꾼 제안서인 JEP 254는 여러 애플리케이션에서 모은 자료를 근거로 문자열이 힙 사용량의 주요 구성 요소라고 적는다. 그래서 JDK와 JVM은 문자열에 대해서만 특별한 절약을 세 가지 한다. 같은 내용의 리터럴은 객체 하나를 함께 쓰고, 가능하면 한 글자를 1바이트로 저장하고, 연결 연산이 만드는 중간 객체를 줄인다.

    이 세 가지는 모두 "String 객체의 내용은 만들어진 뒤에 바뀌지 않는다"는 한 가지 성질에 기대고 있다. 이 회차는 String 객체의 속을 먼저 들여다본 다음, 풀, 비교, 불변, 주요 메서드, 연결의 컴파일, StringBuilder 순서로 그 구조를 따라간다. 불변 객체 일반의 이야기는 앞 회차에서 했으므로 여기서는 String이 불변성을 어디에 쓰는지에 집중한다.

    String 객체의 속: byte[]와 coder

    String 객체는 글자를 직접 품고 있지 않다. OpenJDK 21의 String 소스에서 인스턴스 필드만 뽑으면 다음 네 개다.

    public final class String
    implements java.io.Serializable, Comparable, CharSequence,
               Constable, ConstantDesc {

    private final byte[] value;   // 문자 데이터가 들어 있는 배열
    private final byte coder;     // value의 인코딩: LATIN1(0) 또는 UTF16(1)
    private int hash;             // 해시코드 캐시. 기본값 0
    private boolean hashIsZero;   // 계산한 해시코드가 실제로 0인지 기억
    // ...
}

    글자는 value가 가리키는 별도의 배열 객체에 들어 있다. 따라서 문자열 하나는 힙에서 객체 두 개다. String 객체 하나와 byte[] 배열 객체 하나다. 두 객체는 각각 객체 헤더를 가진다. JEP 450에 따르면 64비트 HotSpot에서 객체 헤더는 설정에 따라 12바이트에서 16바이트를 차지한다. 다섯 글자짜리 문자열이라도 실제로 차지하는 메모리는 글자 다섯 개 분량보다 훨씬 크다는 뜻이다.

    배열의 타입이 char[]가 아니라 byte[]인 데에는 역사가 있다. JDK 8까지 String은 글자를 char 배열에 저장했다. char는 16비트이므로 글자 하나에 항상 2바이트를 썼다. JEP 254는 대부분의 String 객체가 Latin-1 문자만 담고 있고, 그런 문자는 1바이트면 충분하므로 내부 char 배열 공간의 절반이 쓰이지 않고 있다고 지적했다. 그래서 JDK 9에서 내부 표현을 "UTF-16 char 배열"에서 "byte 배열 + 인코딩 표시 필드"로 바꿨다. 이것이 Compact Strings다.

    규칙은 단순하다. 문자열의 모든 문자가 Latin-1(ISO-8859-1) 범위, 곧 코드 값 0~255 안에 있으면 한 글자를 1바이트로 저장하고 coder를 LATIN1(0)로 둔다. 범위를 벗어나는 문자가 하나라도 있으면 문자열 전체를 UTF-16으로, 곧 한 코드 유닛을 2바이트로 저장하고 coder를 UTF16(1)으로 둔다. 영문·숫자·기호로 된 문자열은 앞쪽에, 한글이 한 글자라도 들어간 문자열은 뒤쪽에 해당한다.

    직접 들여다보기

    value와 coder는 private 필드여서 보통의 코드로는 볼 수 없다. 뒤 회차에서 맛볼 리플렉션(reflection)으로 열어 보자. JDK 내부 필드에 접근하는 것이므로 실행할 때 --add-opens 옵션으로 java.lang 패키지를 열어 주어야 한다. 학습용 실험이고, 실제 코드에서 쓸 방법은 아니다.

    import java.lang.reflect.Field;

public class PeekInside {
    public static void main(String[] args) throws Exception {
        peek("abc");
        peek("café");
        peek("가나다");
        peek("abc가");
        peek("😀");
    }

    static void peek(String s) throws Exception {
        Field value = String.class.getDeclaredField("value");
        Field coder = String.class.getDeclaredField("coder");
        value.setAccessible(true);
        coder.setAccessible(true);
        byte[] bytes = (byte[]) value.get(s);
        System.out.println(s + " length=" + s.length()
                + " coder=" + coder.getByte(s)
                + " value.length=" + bytes.length);
    }
}

    한 줄씩 읽어 보자. "abc"는 세 글자가 3바이트에 들어갔다. "café"의 é는 유니코드 U+00E9로 Latin-1 범위 안이어서 여전히 글자당 1바이트다. "가나다"는 세 글자가 6바이트다. "abc가"가 중요하다. 한글은 한 글자뿐인데 배열 길이는 8이다. 인코딩은 문자열 단위로 정해지므로 a, b, c까지 2바이트씩 쓰게 된 것이다.

    마지막 줄은 다른 사실을 보여 준다. 이모지 한 글자인데 length()가 2다. String의 Javadoc은 String이 UTF-16 형식의 문자열을 나타내고, length()는 유니코드 코드 유닛(code unit)의 수를 돌려준다고 정한다. U+FFFF를 넘는 문자(보충 문자)는 UTF-16에서 코드 유닛 두 개(서로게이트 쌍)로 표현되므로 길이가 2가 된다. 사람이 세는 글자 수에 가까운 값이 필요하면 codePointCount(0, s.length())를 쓴다. 이 예에서는 1이 나온다. charAt(i)와 substring의 인덱스도 모두 코드 유닛 기준이다.

    OpenJDK 21에서 length()의 구현은 return value.length >> coder(); 한 줄이다. coder()는 Compact Strings가 켜져 있으면(기본값) coder 필드의 값을 돌려주는 메서드다. coder가 0이면 배열 길이 그대로, 1이면 배열 길이를 2로 나눈 값이다. 인코딩 표시를 0과 1로 정해 둔 덕분에 인코딩별로 계산식을 나누지 않고 시프트 연산 하나로 길이를 구한다.

    이 표현은 OpenJDK 구현의 세부다. JEP 254는 이 변경이 구현만 바꾸고 공개 인터페이스는 바꾸지 않는다고 밝힌다. 프로그램이 보는 String은 언제나 "UTF-16 코드 유닛의 열"이고, 그 뒤에서 1바이트로 줄여 저장하느냐는 JVM의 사정이다. HotSpot에서는 -XX:-CompactStrings 옵션으로 이 기능을 끄고 모든 문자열을 UTF-16으로 저장하게 할 수 있다.
    문자열 하나가 String 객체와 byte 배열 객체 둘로 이루어지고, coder 값에 따라 글자당 1바이트 또는 2바이트로 저장된다는 것을 나란히 보여 준다. 흰 배경의 깔끔한 기술 다이어그램. 화면을 좌우 두 칸으로 나눈다. 왼쪽 칸 제목 "abc", 오른쪽 칸 제목 "abc가". 각 칸 위쪽에 둥근 모서리 상자 "String 객체"가 있고 안에 세 줄: "value", "coder", "hash". 왼쪽 상자의 coder 줄에는 "coder = 0 (LATIN1)", 오른쪽 상자의 coder 줄에는 "coder = 1 (UTF16)". 각 상자의 "value" 줄에서 아래로 화살표가 나와 가로로 긴 배열 그림을 가리킨다. 왼쪽 배열은 칸 3개로 각각 "a", "b", "c"가 적혀 있고 아래에 라벨 "byte[3] · 글자당 1바이트". 오른쪽 배열은 넓은 칸 4개로 각각 "a", "b", "c", "가"가 적혀 있고 각 칸이 두 조각으로 나뉘어 있으며 아래에 라벨 "byte[8] · 코드 유닛당 2바이트". 오른쪽 배열의 "가" 칸만 주황색으로 강조하고 그 옆에 작은 말풍선 "한 글자 때문에 전체가 2바이트". 맨 아래 가운데에 한 줄 "문자열 하나 = 객체 두 개". 선은 얇게, 색은 파랑과 주황 두 가지만 쓴다. Latin-1 범위를 벗어나는 문자가 하나라도 있으면 문자열 전체가 UTF-16으로 저장된다(OpenJDK 9 이상).

    문자열 리터럴과 문자열 풀

    이제 리터럴을 보자. JLS 3.10.5는 두 가지를 정한다. 첫째, 문자열 리터럴은 실행 시점에 String 클래스의 인스턴스를 가리키는 참조다. 둘째, 문자열 리터럴은 항상 같은 인스턴스를 가리킨다. 명세의 표현으로는 문자열 리터럴이, 더 일반적으로는 상수 표현식의 값인 문자열이 String.intern 메서드를 실행한 것처럼 "인턴(intern)"되어 유일한 인스턴스를 공유한다.

    이 "유일한 인스턴스들"을 모아 두는 곳이 문자열 풀(string pool)이다. String.intern()의 Javadoc은 String 클래스가 처음에는 비어 있는 문자열 풀을 비공개로 관리한다고 적는다. 흔히 문자열 상수 풀이라고도 부른다. 프로그램 어디에서든 "hello"라고 쓰면, 클래스가 다르고 패키지가 달라도 같은 JVM 안에서는 풀에 있는 그 String 객체 하나를 가리킨다.

    리터럴이 객체가 되기까지

    이 일이 일어나는 경로를 따라가 보자. 다음 두 줄을 컴파일한다.

    String a = "hello";
String b = "hello";
       #7 = String             #8             // hello
   #8 = Utf8               hello
   ...
       0: ldc           #7                  // String hello
       2: astore_1
       3: ldc           #7                  // String hello
       5: astore_2

    컴파일러는 리터럴의 글자들을 클래스 파일의 상수 풀(constant pool)에 한 번만 기록한다. 8번 항목이 글자 데이터이고, 7번 항목이 "이것은 문자열 상수"라는 표시다. 소스에 "hello"를 두 번 썼지만 항목은 하나다. 바이트코드에서는 두 줄 모두 ldc #7이다. ldc는 런타임 상수 풀의 항목을 오퍼랜드 스택에 올리는 명령이고, 항목이 문자열 상수이면 그 String 인스턴스의 참조를 올린다(JVMS 6.5).

    그 String 인스턴스를 누가 언제 만드는가는 JVMS 5.1이 정한다. JVM은 클래스 파일의 문자열 상수 항목에서 문자열 상수를 끌어낼 때, 같은 문자 시퀀스를 가진 String에 대해 이전에 String.intern이 호출된 적이 있으면 그 인스턴스를 쓴다. 없으면 그 내용을 담은 String 인스턴스를 새로 만들고 그것을 인턴한다. 다른 클래스의 "hello"가 같은 객체로 귀결되는 것은 이 규칙 때문이다.

    여기서 이름이 비슷한 세 가지를 구분해 두어야 한다.

    이름어디에 있는가무엇이 들어 있는가
    클래스 파일의 상수 풀.class 파일 안. 클래스마다 하나리터럴의 글자, 클래스·메서드·필드 이름 같은 기호 정보
    런타임 상수 풀JVM의 메서드 영역. 로드된 클래스마다 하나(JVMS 2.5.5)위 표를 실행 중에 쓸 수 있게 옮긴 것. 문자열 상수는 String 참조로 바뀐다
    문자열 풀JVM 전체에 하나인턴된 String 객체들. 내용이 같으면 하나만 있다

    클래스 A와 클래스 B가 각자 상수 풀에 hello를 기록해도, 두 런타임 상수 풀의 항목은 문자열 풀에 있는 같은 String 객체를 가리키게 된다.

    풀은 어디에 있는가

    명세는 풀이 메모리의 어느 영역에 있는지 정하지 않는다. JLS는 "같은 인스턴스"라는 결과만 요구하고, Javadoc은 풀을 String 클래스가 비공개로 관리한다고만 적는다. 위치는 구현의 몫이다. HotSpot은 JDK 6까지 인턴된 문자열을 영구 세대(permanent generation)라는 별도 영역에 두었다. JDK 7 릴리스 노트는 인턴된 문자열이 더 이상 영구 세대에 할당되지 않고, 애플리케이션이 만든 다른 객체들과 함께 힙의 주된 부분(young, old 세대)에 할당된다고 밝힌다. 영구 세대 자체는 JDK 8에서 없어졌다(JEP 122).

    따라서 지금의 HotSpot에서 "풀에 있는 문자열"은 보통의 힙 객체다. 다른 String과 구조가 같고 필드도 같다. 다른 점은 JVM이 그 객체를 "이 내용의 대표"로 등록해 두고 내용으로 찾아낼 수 있다는 것뿐이다. HotSpot은 이 등록부를 문자열 테이블(string table)이라는 내부 표로 관리하고, jcmd 도구의 VM.stringtable 명령으로 그 내용을 덤프할 수 있다. "풀"을 힙과 분리된 저장 공간으로 그리면 틀린 그림이 된다. 객체는 힙에 있고, 풀은 그 객체들을 가리키는 찾아보기다.

    일상에서 가져온 비유도서관의 대표 서지 목록

    도서관은 같은 책을 여러 사람이 찾으면 책을 새로 사지 않고 이미 있는 책의 위치를 알려 준다. 문자열 풀은 "이 제목의 책은 저 서가에 있다"는 목록이고, 책 자체는 다른 책들과 같은 서가(힙)에 꽂혀 있다. 비유가 맞지 않는 곳도 있다. 도서관 책은 한 사람이 빌려 가면 다른 사람이 못 보지만 String은 몇 명이 동시에 참조해도 된다. 그리고 책에 낙서를 하면 다음 사람이 피해를 보는데, String은 내용을 고칠 방법이 아예 없어서 그런 일이 생기지 않는다. 풀이 성립하는 조건이 바로 이 점이다.

    생성자가 하는 일도 볼 만하다. OpenJDK 21에서 String(String original) 생성자는 original의 value, coder, hash, hashIsZero를 새 객체의 필드에 그대로 대입한다. 배열을 복사하지 않는다. 새 String 객체는 생기지만 글자가 든 byte[]는 원본과 함께 쓴다. 내용을 바꿀 수 없으니 함께 써도 안전하다. Javadoc도 이 생성자에 대해, String은 불변이므로 원본의 명시적 복사본이 필요한 경우가 아니면 쓸 필요가 없다고 적어 둔다.

    이제 결과를 설명할 수 있다. 참조 타입끼리의 ==는 두 피연산자가 같은 객체를 가리키는지 본다(JLS 15.21.3). a와 b는 같은 리터럴이므로 같은 객체다. c와 d는 new가 각각 만든 서로 다른 객체이고, 풀의 객체와도 다르다. 반면 equals는 Javadoc의 정의대로 인자가 null이 아니고 같은 문자 시퀀스를 나타내는 String일 때 true다. 내용이 같으므로 a.equals(c)는 true다.

    OpenJDK 21의 equals 구현은 세 단계다. 먼저 this == anObject이면 곧바로 true를 돌려준다. 같은 객체라면 글자를 볼 필요가 없다. 다음으로 상대가 String이 아니거나 coder가 다르면 false다. 같은 내용은 항상 같은 인코딩으로 저장되므로 인코딩이 다르면 내용도 다르다. 마지막으로 두 byte[]의 길이와 내용을 비교한다. 풀을 공유하는 리터럴끼리는 첫 단계에서 끝난다.

    intern()

    c.intern() == a가 true인 이유는 intern()의 정의에 있다. Javadoc에 따르면 intern()이 호출되었을 때 풀에 이미 equals로 같은 문자열이 있으면 풀의 그 문자열을 돌려주고, 없으면 이 String 객체를 풀에 추가하고 이 객체의 참조를 돌려준다. c와 내용이 같은 "hello"가 리터럴 때문에 이미 풀에 있으므로 그 객체, 곧 a가 가리키는 객체가 돌아온다. c가 가리키는 객체 자체는 풀에 들어가지 않는다.

    Javadoc은 여기서 한 가지 성질을 끌어낸다. 임의의 두 문자열 s, t에 대해 s.intern() == t.intern()이 true인 것과 s.equals(t)가 true인 것은 같은 조건이다. 그렇다고 문자열 비교를 intern()과 ==로 하자는 뜻은 아니다. intern()은 풀을 찾아보는 비용이 들고, 실행 중에 만든 문자열을 계속 인턴하면 풀이 커진다. JDK 7 릴리스 노트도 String.intern()을 많이 쓰는 애플리케이션은 힙 사용량에서 더 큰 차이를 보게 된다고 적는다.

    이 장의 핵심

    문자열의 내용이 같은지 묻는다면 equals를 쓴다. ==는 "같은 객체인가"라는 다른 질문이고, 그 답은 문자열이 리터럴에서 왔는지, new나 런타임 연산에서 왔는지에 따라 달라진다. 파일에서 읽은 문자열, 네트워크로 받은 문자열, 사용자가 입력한 문자열은 모두 실행 중에 새로 만들어진 객체이므로 리터럴과 ==로 비교하면 내용이 같아도 false가 나온다.

    리터럴 변수 둘은 풀에 등록된 한 객체를 가리키고, new로 만든 변수 둘은 각각 다른 객체를 가리키며, intern이 풀의 객체를 돌려준다는 것을 보여 준다. 흰 배경의 메모리 구조 다이어그램. 왼쪽에 세로로 긴 상자 "스택: main 프레임"이 있고 안에 위에서 아래로 네 칸 "a", "b", "c", "d". 오른쪽 넓은 영역은 "힙"이라는 제목의 큰 둥근 상자. 힙 안 위쪽에 점선 테두리로 둘러싼 구역이 있고 라벨 "문자열 풀이 가리키는 객체". 그 구역 안에 상자 하나 "String ①". 힙 안 아래쪽에 상자 두 개 "String ②", "String ③". 힙 오른쪽 끝에 배열 그림 하나 "byte[5] h e l l o". 화살표: "a"와 "b"에서 각각 "String ①"로 파란 화살표. "c"에서 "String ②"로, "d"에서 "String ③"으로 주황 화살표. "String ①", "String ②", "String ③" 세 상자에서 모두 같은 배열 "byte[5] h e l l o"로 얇은 회색 화살표. "String ②"에서 "String ①"로 휘어지는 점선 화살표를 그리고 라벨 "c.intern()". 아래쪽에 작은 글씨 세 줄: "a == b : true", "a == c : false", "c.intern() == a : true". new는 항상 새 객체를 만들고, intern()은 풀에 등록된 객체를 돌려준다.

    String은 왜 불변인가

    String은 불변 객체(immutable object)다. 앞 회차의 기준으로 보면 조건을 모두 갖추고 있다. 클래스가 final이어서 하위 클래스가 내용을 바꾸는 메서드를 덧붙일 수 없다. 글자를 담는 value는 private final이고, 그 배열을 밖으로 내주거나 원소를 고치는 메서드가 없다. toCharArray()는 내부 배열이 아니라 새로 할당한 배열을 돌려준다. 그리고 내용을 바꾸는 것처럼 보이는 메서드는 전부 새 String을 만들어 돌려준다.

    public class Immutable {
    public static void main(String[] args) {
        String s = "java";
        s.concat(" 21");
        s.toUpperCase();
        System.out.println(s);

        String t = s.concat(" 21");
        System.out.println(t);
        System.out.println(s == t);
    }
}

    둘째, 셋째 줄의 concat과 toUpperCase는 새 String 객체를 만들어 돌려주지만 그 반환값을 받는 변수가 없다. 객체는 만들어지자마자 아무도 참조하지 않는 상태가 된다. s가 가리키는 객체는 그대로이므로 java가 출력된다. 반환값을 t에 받아야 결과를 쓸 수 있고, 그때 t는 s와 다른 객체다. "String 메서드를 호출했는데 값이 안 바뀐다"는 초보적인 버그는 모두 이 구조에서 나온다.

    String이 불변이어야 하는 이유는 앞에서 본 구조들과 묶여 있다.

    이유 1: 풀로 공유하려면 바뀌면 안 된다

    String의 Javadoc은 "String 객체는 불변이므로 공유할 수 있다"고 적는다. 반대로 생각해 보면 분명해진다. String에 내용을 바꾸는 setCharAt 같은 메서드가 있었다고 하자. 결제 모듈의 어떤 클래스가 String status = "OK";로 받은 문자열의 첫 글자를 바꾸면, 같은 JVM 안에서 "OK" 리터럴을 쓰는 모든 클래스가 영향을 받는다. 전부 풀의 같은 객체를 가리키기 때문이다. 관계없는 모듈의 로그 메시지와 조건문이 한꺼번에 달라진다. 앞 회차에서 본 공유 참조의 사이드 이펙트가 프로그램 전체 규모로 일어나는 셈이다. 리터럴을 공유해서 메모리를 아끼는 설계는 내용이 바뀌지 않는다는 보장이 있어야만 성립한다.

    new String(original)이 배열을 복사하지 않고 함께 쓰는 것, 뒤에서 볼 StringBuilder.toString()이 반대로 배열을 반드시 복사하는 것도 같은 원리다. 양쪽 다 불변이면 공유해도 되고, 한쪽이 가변이면 복사해야 한다.

    이유 2: 해시코드를 한 번만 계산해도 된다

    String의 hashCode()는 Javadoc에 계산식이 명시되어 있다. 길이가 n인 문자열 s에 대해 s[0]*31^(n-1) + s[1]*31^(n-2) + ... + s[n-1]을 int 산술로 계산한 값이다(^는 거듭제곱). 문자열 전체를 훑어야 하므로 길이에 비례하는 시간이 든다. 예를 들어 "abc"는 97×31×31 + 98×31 + 99 = 96354다.

    OpenJDK 21의 구현은 이 값을 hash 필드에 저장해 둔다. hashCode()가 처음 호출되면 계산해서 필드에 넣고, 그다음부터는 필드 값을 바로 돌려준다. 계산 결과가 정말 0인 문자열을 "아직 계산 안 함"과 구분하려고 hashIsZero 필드를 따로 둔다. 이 캐싱은 내용이 변하지 않을 때만 옳다. 내용이 바뀔 수 있다면 바뀔 때마다 캐시를 무효로 만들어야 하고, 그 String을 키로 넣어 둔 해시 기반 자료 구조는 엉뚱한 위치를 찾게 된다.

    hash 필드는 final이 아니다. 그런데도 String을 불변이라고 부르는 것은 불변성이 "밖에서 관찰할 수 있는 상태가 변하지 않는다"는 뜻이기 때문이다. hashCode()는 언제 호출해도 같은 값을 돌려준다. 소스의 주석은 이 필드에 여러 스레드가 동시에 접근해도 문제가 없는 이유를 적어 둔다. 계산이 불변인 상태에서만 나오고 몇 번을 해도 결과가 같으므로, 두 스레드가 동시에 계산해서 각자 저장해도 같은 값이 들어간다. 락 없이 캐시를 둘 수 있는 것도 불변 덕분이다.

    덧붙여 해시코드가 같다고 내용이 같은 것은 아니다. "Aa"와 "BB"는 식에 넣어 보면 둘 다 2112다(65×31+97, 66×31+66). int는 약 43억 가지 값밖에 없으므로 서로 다른 문자열이 같은 해시코드를 갖는 일은 피할 수 없다. 해시코드는 후보를 좁히는 데 쓰고, 최종 판정은 equals가 한다. 이 관계는 다음 권의 해시 자료 구조에서 다시 다룬다.

    이유 3: 스레드 사이에서, 검증 뒤에 안전하다

    불변 객체는 여러 스레드가 동시에 읽어도 동기화가 필요 없다. 읽는 도중에 다른 스레드가 내용을 바꿀 수 없기 때문이다. 문자열은 스레드 사이를 가장 많이 오가는 데이터이므로 이 성질의 효과가 크다. 같은 이유로, 문자열을 한 번 검사한 뒤에는 그 검사가 계속 유효하다. 파일 경로나 클래스 이름을 문자열로 받아 허용 여부를 확인했다면, 호출한 쪽이 같은 객체를 쥐고 있어도 확인 뒤에 내용을 바꿔치기할 수 없다.

    null과 관련한 두 가지도 정리한다. "a" + x에서 x가 null이면 예외가 나지 않고 "anull"이 된다. 문자열 변환 규칙(JLS 5.1.11)이 null 참조를 문자열 "null"로 바꾸기 때문이다. 반면 x.equals("hello")는 NullPointerException이다. 그래서 한쪽이 리터럴이면 "hello".equals(x)처럼 리터럴 쪽에서 호출하는 습관이 생겼다. 이 경우 x가 null이면 예외 없이 false가 나온다.

    + 연결은 무엇으로 컴파일되는가

    문자열을 이어 붙이는 +로 넘어가자. JLS 15.18.1이 연결의 결과에 대해 정하는 것은 하나다. 결과인 String 객체는 그 식이 상수 표현식(constant expression)이 아닌 한 새로 만들어진다. 어떤 절차로 만드는지는 정하지 않는다. 같은 절은 구현이 변환과 연결을 한 단계로 처리해서 중간 String 객체를 만들었다 버리는 일을 피해도 된다고 적고, 자바 컴파일러가 반복되는 연결의 성능을 높이려고 StringBuffer 클래스나 비슷한 기법을 써도 된다고 덧붙인다. 명세는 결과를 고정하고 방법은 컴파일러와 라이브러리에 맡겼다.

    그래서 소스에서는 똑같은 +라도 클래스 파일에 남는 모습은 세 가지로 갈린다. 컴파일할 때 계산이 끝나 버리는 경우, 실행 시점에 JDK 라이브러리가 연결 방법을 정하는 경우, 컴파일러가 StringBuilder 호출을 직접 늘어놓는 경우다. 어느 쪽이 되는지는 식의 모양과 컴파일 대상 버전이 정한다. javap로 하나씩 확인한다.

    경로 1: 상수 접기 — 컴파일할 때 끝난다

    JLS 15.29는 상수 표현식을 정의한다. 기본형이나 String 값을 나타내는 식 가운데 정해진 재료로만 이루어진 것이다. 재료 목록에는 문자열 리터럴과 텍스트 블록, +를 비롯한 연산자, 그리고 상수 변수(constant variable)를 가리키는 단순 이름이 들어 있다. 상수 변수는 final이면서 상수 표현식으로 초기화된 기본형 또는 String 변수다(JLS 4.12.4). 같은 절은 String 타입의 상수 표현식이 항상 인턴된다고 적는다. 컴파일러는 이런 식의 값을 컴파일할 때 계산해서 결과만 클래스 파일에 적는다. 이것을 상수 접기(constant folding)라고 부른다.

        System.out.println(s2 == hello);

    상수 접기 덕분에 소스를 읽기 좋게 나누어 쓰는 데에는 실행 비용이 들지 않는다. 긴 SQL이나 메시지를 여러 줄의 리터럴로 쪼개 +로 이어도 클래스 파일에는 문자열 하나만 남는다. Java 15부터는 텍스트 블록(""")을 같은 용도로 쓸 수 있고, 텍스트 블록도 상수 표현식의 재료다.

    OpenJDK 21의 라이브러리가 마련하는 연결 코드는 StringBuilder를 쓰지 않는다. java.lang.StringConcatHelper의 소스를 따라가면 순서는 이렇다. 먼저 이어 붙일 조각을 모두 훑어 결과의 전체 길이와 coder를 계산한다. 조각이 전부 Latin-1이면 결과도 Latin-1이고, 하나라도 UTF-16이면 결과는 UTF-16이다. 다음으로 정확히 그 크기의 byte[]를 한 번 할당한다. 그리고 각 조각을 배열의 제자리에 써 넣은 뒤, 그 배열을 복사하지 않고 그대로 품는 String을 만든다. 배열을 키우는 일도, 끝에서 한 번 더 복사하는 일도 없다. 식 하나 안에서는 이어 붙일 조각을 전부 알고 시작하므로 결과 길이를 먼저 셀 수 있다. 그래서 가능한 방법이다.

    n이 100,000이면 이 합은 5,000,050,000이다. 최종 결과는 10만 글자인데, 거기에 이르기까지 만들었다 버리는 문자열의 글자를 모두 세면 50억 개가 넘는다. String 객체도 반복 횟수만큼 생기고, 마지막 것을 뺀 나머지는 다음 반복에서 곧바로 아무도 참조하지 않는 객체가 된다. n이 10배가 되면 일의 양은 약 100배가 된다. 적은 데이터로 시험할 때는 드러나지 않다가 데이터가 커진 뒤에 나타나는 종류의 문제다.

    컴파일러가 이것을 대신 고쳐 주지 못하는 이유도 짚는다. s += "x"는 s + "x"의 결과를 s에 대입하는 식이고, JLS는 그 결과가 새로 만든 String 객체라고 정한다. 반복이 한 번 끝날 때마다 s는 완성된 String을 가리키고 있어야 한다. 경로 2의 최적화는 식 하나 안에서 중간 객체를 없애는 것이고, 반복과 반복 사이를 이어 주지는 않는다. Java 8 방식으로 컴파일해도 달라지지 않는다. 그때는 반복마다 new StringBuilder(), append(s), append("x"), toString()이 실행된다. 빌더를 쓰기는 하지만 반복마다 새로 만들어 전체를 옮겨 담으므로 복사량은 같다.

    정리하면 판단 기준은 "연결이 식 하나로 끝나는가"다.

    • 반복문 안에서 문자열을 누적할 때. 위에서 본 경우다. 반복 횟수가 입력 크기에 따라 달라진다면 반드시 빌더를 쓴다.
    • 조건에 따라 여러 문장에 걸쳐 조각을 붙일 때. if마다 s += ...를 하면 문장마다 새 String이 생긴다.
    • 문자열의 중간을 고치거나 뒤집을 때. insert, delete, reverse, setCharAt처럼 제자리에서 고치는 연산은 String에는 없다.
    • 반대로, 한 식으로 끝나는 연결은 +로 쓴다. "이름: " + name + ", 나이: " + age를 빌더로 풀어 쓰면 읽기만 어려워진다. Java 9 이상에서는 경로 2가 처리한다.
    • 구분자로 잇는 일이면 String.join을 쓴다. 구분자를 언제 넣을지 따지는 코드를 직접 쓸 필요가 없다.

    StringBuilder: 가변 문자열의 속

    StringBuilder의 Javadoc 첫 문장은 이 클래스를 가변 문자 시퀀스(mutable sequence of characters)라고 정의한다. String과 하는 일은 겹치지만 설계는 반대다. OpenJDK 21에서 StringBuilder의 상태는 패키지 전용 상위 클래스 AbstractStringBuilder에 들어 있다.

    abstract sealed class AbstractStringBuilder implements Appendable, CharSequence
    permits StringBuilder, StringBuffer {

    byte[] value;   // 문자 데이터. final이 아니다
    byte coder;     // LATIN1(0) 또는 UTF16(1)
    int count;      // 지금까지 채운 문자(코드 유닛) 수
    // ...
}

    String과 필드 구성이 닮았다. JEP 254가 String의 내부 표현을 바꾸면서 AbstractStringBuilder, StringBuilder, StringBuffer도 같은 표현을 쓰도록 고쳤기 때문이다. 다른 점은 세 가지다. value가 final이 아니어서 다른 배열로 바꿔 끼울 수 있다. 배열이 내용보다 클 수 있다. 그래서 "어디까지 찼는가"를 기억하는 count가 따로 있다. String에서는 배열 길이가 곧 내용의 길이였지만, 빌더에서는 배열 길이가 용량(capacity)이고 count가 길이(length)다.

    왜 한 칸씩이 아니라 두 배씩 늘리는가

    확장은 기존 내용을 전부 복사하는 비싼 연산이다. 그런데 빌더는 꽉 찰 때마다 필요한 만큼만 늘리지 않고 대략 두 배로 늘린다. 이유는 복사량의 합을 세어 보면 나온다. 만약 모자랄 때마다 딱 한 칸씩 늘린다면 글자 하나를 붙일 때마다 전체를 복사해야 한다. n글자를 붙이는 동안의 복사량은 0+1+2+...+(n-1)이 되어, 앞에서 본 반복문 안 +=와 같은 제곱 꼴이 된다. 가변 버퍼를 쓰는 의미가 없어진다.

    두 배씩 늘리면 확장이 일어나는 간격도 두 배씩 벌어진다. 앞의 계산을 다시 보자. 10만 글자를 붙이는 동안 확장은 13번이고, 복사량은 16+34+70+...+73,726으로 147,412다. 확장 때 옮긴 양을 모두 더해도 최종 용량 147,454보다 작다. 직전 용량들의 합이 마지막 용량을 넘지 못하는 것은 매번 두 배 이상으로 늘렸기 때문이다. 따라서 가끔 일어나는 확장의 비용을 모든 append에 고르게 나누면 append 한 번의 몫은 글자 수에 비례하는 작은 값이 된다. 이런 계산법을 분할 상환(amortized) 분석이라고 한다. 다음 권에서 다룰 배열 기반 리스트도 같은 원리로 배열을 키운다.

    대가는 빈자리다. 끝난 뒤의 빌더는 286칸 가운데 150칸만 쓰고 있다. 공간을 조금 더 쓰고 복사를 크게 줄이는 교환이다. 빌더는 보통 메서드 안에서 잠깐 쓰고 버리는 객체이므로 이 빈자리는 오래 남지 않는다.

    한글이 들어오면: 배열을 통째로 바꾼다

    빌더도 coder를 가진다. Latin-1 문자만 담고 있던 빌더에 한글 한 글자를 붙이면 어떻게 되는지 리플렉션으로 확인하면 다음과 같다. "abc"를 붙인 직후에는 count가 3, coder가 0, value.length가 16이다. 여기에 '가'를 붙이면 count가 4, coder가 1, value.length가 32가 된다. capacity()는 그대로 16이다. 글자 수 기준의 용량은 같지만, 한 글자가 2바이트를 차지하게 되었으므로 바이트 배열은 두 배 크기로 새로 만들어지고 기존 세 글자도 2바이트씩으로 옮겨 적힌다. String에서 본 "한 글자 때문에 전체가 UTF-16"이라는 규칙이 빌더에서는 실행 도중의 배열 교체로 나타난다.

    toString()은 반드시 복사한다

    public class BuilderCopy {
    public static void main(String[] args) {
        StringBuilder sb = new StringBuilder("abc");
        String s = sb.toString();
        sb.append("!").reverse();
        System.out.println(s);
        System.out.println(sb);

        StringBuilder x = new StringBuilder("abc");
        StringBuilder y = new StringBuilder("abc");
        System.out.println(x.equals(y));
        System.out.println(x.toString().equals(y.toString()));

    }

    s를 만든 뒤에 빌더를 고쳤는데 s는 그대로 abc다. OpenJDK 21의 StringBuilder.toString()은 한 줄이고, 그 위에 "복사본을 만든다, 배열을 공유하지 않는다"는 주석이 달려 있다. 앞에서 new String(original)이 배열을 공유하던 것과 대비된다. 그쪽은 양쪽이 모두 불변이라 공유해도 됐다. 여기서는 한쪽이 가변이다. 배열을 함께 쓴다면 빌더에 append하는 순간 이미 내보낸 String의 내용이 바뀌고, String의 불변성이 깨진다. 그래서 채워진 부분만큼의 새 배열을 만들어 복사한다. 복사본은 빈자리 없이 내용 크기에 맞춰진다.

    아래 세 줄은 비교에 관한 것이다. StringBuilder는 equals를 재정의하지 않는다. x.equals(y)는 Object의 기본 구현, 곧 같은 객체인지를 본다. 내용이 같아도 false다. 가변 객체는 내용이 계속 바뀌므로 내용 기준의 동등성과 해시코드를 주기 곤란하다는 사정이 있다. 내용을 비교하려면 String으로 바꿔 비교하거나, Java 11에 추가된 compareTo를 쓴다. 같은 이유로 빌더를 해시 기반 컬렉션의 키로 쓰면 안 된다.

    StringBuffer: 같은 구조에 synchronized

    StringBuffer는 자바 1.0부터 있던 가변 문자열 클래스다. 구조는 StringBuilder와 같다. 둘 다 AbstractStringBuilder를 상속하고 같은 배열 확장 규칙을 쓴다. 다른 점은 StringBuffer에서는 내용을 읽고 고치는 메서드들에 synchronized가 붙어 있다는 것이다. OpenJDK 21의 append(String) 선언은 public synchronized StringBuffer append(String str)이다. 메서드에 들어갈 때마다 그 객체의 모니터 락을 얻고 나올 때 놓는다. 여러 스레드가 한 버퍼에 동시에 append해도 내부 상태(count와 배열)가 어긋나지 않는다.

    StringBuilder는 Java 1.5에 추가되었다. Javadoc은 이 클래스가 StringBuffer와 호환되는 API를 제공하되 동기화는 보장하지 않으며, 버퍼를 스레드 하나가 쓰는 곳(대개 그렇다)에서 StringBuffer를 그대로 대체하도록 설계되었다고 적는다. 가능하면 StringBuilder를 쓰라고도 권한다. 메서드 안에서 지역 변수로 만든 빌더는 그 참조를 밖으로 내보내지 않는 한 다른 스레드가 접근할 길이 없다. 그런 객체에 락을 걸 이유가 없다.

    오해 하나를 막아 둔다. StringBuffer가 보장하는 것은 메서드 호출 하나의 원자성이다. buf.append(a).append(b)는 호출이 두 번이므로, 두 스레드가 같은 버퍼에 이 문장을 실행하면 한 스레드의 a와 b 사이에 다른 스레드의 조각이 끼어들 수 있다. 여러 호출을 한 덩어리로 묶으려면 호출하는 쪽에서 따로 동기화해야 한다. 모니터 락과 synchronized의 동작은 고급편의 동시성 회차에서 다룬다.

    StringBuilder 객체의 value가 가리키는 배열이 꽉 찼을 때 더 큰 배열로 복사해 옮기고 참조를 바꾸는 과정을 3단계로 보여 준다. 흰 배경의 3단계 메모리 다이어그램. 위에서 아래로 세 줄을 배치하고 각 줄 왼쪽에 단계 번호 동그라미 1, 2, 3을 둔다. 각 줄의 왼쪽에는 둥근 상자 "StringBuilder"가 있고 안에 두 줄 "value", "count". 1단계: count 줄에 "count = 16", value에서 오른쪽으로 화살표가 나와 칸 16개짜리 가로 배열을 가리킨다. 16칸 모두 파란색으로 채워져 있고 배열 아래 라벨 "capacity 16 · 가득 참". 2단계: 같은 16칸 배열 아래에 칸 34개짜리 더 긴 배열을 새로 그린다. 위 배열에서 아래 배열의 앞 16칸으로 여러 개의 얇은 화살표를 내려 그리고 라벨 "기존 내용 복사". 아래 배열 옆 라벨 "새 배열 capacity 34". 3단계: value의 화살표가 34칸 배열을 가리킨다. 앞 17칸이 채워져 있고 17번째 칸만 주황색, count 줄에 "count = 17". 옛 16칸 배열은 회색 점선 테두리로 흐리게 그리고 라벨 "참조가 끊긴 옛 배열". 맨 아래에 한 줄 "새 용량 = 기존 용량 × 2 + 2". 색은 파랑, 주황, 회색만 쓴다. 빈자리가 없으면 더 큰 배열로 옮겨 담는다. 두 배씩 늘리므로 확장은 갈수록 드물어진다.

    메서드 체이닝: 반환된 참조가 다음 호출의 대상이 된다

    append의 마지막 단계가 return this였다. 이 한 줄이 sb.append("a").append("b")처럼 호출을 줄줄이 잇는 문법, 곧 메서드 체이닝(method chaining)을 가능하게 한다. 특별한 문법이 아니라 "메서드 호출식의 값은 반환값"이라는 규칙의 결과다. 작은 클래스로 확인한다.

    public class Tally {
    private int total;

    public Tally add(int amount) {
        total += amount;
        return this;
    }

    public int total() {
        return total;
    }
}
    public class ChainMain {
    public static void main(String[] args) {
        Tally t1 = new Tally();
        t1.add(10);
        t1.add(20);
        t1.add(30);
        System.out.println(t1.total());

        Tally t2 = new Tally();
        Tally r1 = t2.add(10);
        Tally r2 = r1.add(20);
        System.out.println(r1 == t2);
        System.out.println(r2 == t2);

        Tally t3 = new Tally();
        int sum = t3.add(10).add(20).add(30).total();
        System.out.println(sum);
    }
}

true
true
60

    첫 번째 묶음은 반환값을 쓰지 않는다. add가 this를 돌려주지만 받는 곳이 없어 버려진다. 두 번째 묶음은 반환값을 변수에 받아 본다. r1 == t2와 r2 == t2가 모두 true다. add가 돌려준 참조는 호출된 바로 그 객체를 가리킨다. 힙에 있는 Tally 객체는 하나이고, t2, r1, r2 세 변수가 그것을 함께 가리킨다.

    세 번째 묶음이 체이닝이다. t3.add(10).add(20).add(30).total()은 왼쪽부터 평가된다. t3.add(10)이 실행되어 total이 10이 되고 참조가 돌아온다. 그 참조에 대해 .add(20)이 호출된다. 다시 돌아온 참조에 .add(30)이, 마지막 참조에 .total()이 호출되어 60이 나온다. 두 번째 묶음에서 r1, r2라는 이름을 붙여 받던 참조를 이름 없이 바로 쓰는 것이다.

    같은 객체를 돌려주는 체인과 새 객체를 돌려주는 체인

    문법이 같아 보여도 체인에는 두 종류가 있다. 메모리에서 벌어지는 일이 다르므로 구분해야 한다.

    public class ChainKinds {
    public static void main(String[] args) {
        StringBuilder sb = new StringBuilder();
        String r = sb.append("A").append(1).append('-').append(true).reverse().toString();
        System.out.println(r);

        StringBuilder same = sb.append("?");
        System.out.println(same == sb);

        String s = "  Hello  ";
        String u = s.strip().toUpperCase().concat("!");
        System.out.println(u);
        System.out.println("[" + s + "]");
    }
}

true
HELLO!

    StringBuilder의 체인은 처음부터 끝까지 객체 하나에 대한 호출이다. append 네 번으로 A1-true가 쌓이고, reverse()가 같은 배열 안에서 순서를 뒤집어 eurt-1A가 된다. 각 단계의 반환값은 모두 sb와 같은 참조다. same == sb가 true인 것이 그 확인이다. 새 객체는 맨 끝의 toString()에서만 생긴다.

    String의 체인은 단계마다 새 객체가 생긴다. s.strip()이 "Hello"라는 새 String을 돌려주고, 그 객체의 toUpperCase()가 "HELLO"라는 또 다른 String을, 그 객체의 concat("!")이 "HELLO!"를 돌려준다. 가운데 두 객체는 다음 호출의 대상으로만 쓰이고 버려진다. s는 끝까지 그대로다. 불변 객체의 체인은 "값을 받아 새 값을 내는 변환을 이어 붙인 것"이고, 가변 객체의 체인은 "한 객체에 명령을 차례로 내리는 것"이다.

    한 가지 세부를 더 본다. append는 상위 클래스 AbstractStringBuilder에 정의되어 있고 거기서의 반환 타입은 AbstractStringBuilder다. StringBuilder는 이 메서드들을 재정의하면서 반환 타입을 StringBuilder로 좁혔다. 재정의할 때 반환 타입을 하위 타입으로 바꾸는 것은 허용되며, javap -p -v java.lang.StringBuilder로 보면 반환 타입이 StringBuilder인 append와 함께 컴파일러가 만든 브리지 메서드(ACC_BRIDGE, ACC_SYNTHETIC 표시가 붙은, 반환 타입이 AbstractStringBuilder인 append)가 나란히 들어 있다. 이 덕분에 체인의 중간 결과가 계속 StringBuilder 타입이어서 StringBuilder에만 있는 메서드도 이어서 부를 수 있다.

    체인이 길어지면 호출마다 줄을 바꿔 쓴다. 읽기 쉬울 뿐 아니라, 예외의 스택 트레이스에는 소스의 줄 번호가 찍히므로 어느 호출에서 문제가 났는지 가려내기 쉬워진다. 체인 중간의 메서드가 null을 돌려줄 수 있다면 그다음 호출에서 NullPointerException이 난다는 점도 기억해 둔다. return this 방식의 체인에서는 이런 일이 생기지 않는다.

    적용: 같은 일을 세 가지 방법으로

    배운 것을 한 문제에 모아 본다. 이름 배열을 쉼표와 공백으로 이어 한 줄로 만드는 일이다.

    public class JoinThree {
    public static void main(String[] args) {
        String[] names = {"kim", "lee", "park"};

        String a = "";
        for (int i = 0; i < names.length; i++) {
            if (i > 0) {
                a += ", ";
            }
            a += names[i];
        }

        StringBuilder sb = new StringBuilder();
        for (int i = 0; i < names.length; i++) {
            if (i > 0) {
                sb.append(", ");
            }
            sb.append(names[i]);
        }
        String b = sb.toString();

        String c = String.join(", ", names);

        System.out.println(a);
        System.out.println(b);
        System.out.println(c);
        System.out.println(a.equals(b) && b.equals(c));
        System.out.println(a == b);
    }
}

kim, lee, park
kim, lee, park
true
false

    세 방법의 결과는 내용이 같다. 과정에서 생기는 객체가 다르다. 첫 번째 방법은 +=가 다섯 번 실행된다. a가 차례로 가리키는 문자열은 "kim", "kim, ", "kim, lee", "kim, lee, ", "kim, lee, park"이고, 앞의 넷은 다음 연결이 끝나는 순간 버려진다. 원소가 셋이라 표가 나지 않을 뿐, 원소 수가 늘면 앞 절의 계산대로 복사량이 제곱으로 는다.

    두 번째 방법은 빌더 하나와 배열 하나로 끝난다. 결과가 14글자여서 초기 용량 16 안에 들어가므로 확장도 일어나지 않는다. String은 toString()에서 하나 만들어진다. 세 번째 방법은 같은 일을 라이브러리에 맡긴 것이다. 구분자를 첫 원소 앞에는 넣지 않는다는 규칙을 직접 쓸 필요가 없다.

    마지막 줄의 a == b는 false다. 둘 다 실행 중에 만들어진 객체이고 서로 다른 경로로 만들어졌으므로 같은 객체일 이유가 없다. 내용 비교는 바로 윗줄처럼 equals로 한다. 이 회차의 앞부분에서 본 규칙이 여기에도 그대로 적용된다.

    흔한 오해 여섯 가지

    • "문자열 풀은 힙과 다른 곳에 있다." JDK 7 이후의 HotSpot에서 인턴된 문자열은 보통의 힙 객체다. 풀은 그 객체들을 내용으로 찾아 주는 표다.
    • "new String("hello")는 객체를 하나 만든다." 그 줄이 새로 만드는 String 객체는 하나지만, 인자인 리터럴의 객체가 풀에 따로 있다. 관여하는 String 객체는 둘이다.
    • "+는 항상 StringBuilder로 바뀐다." Java 8까지의 javac는 그렇게 했다. Java 9 이상을 대상으로 컴파일하면 invokedynamic이 되고, 상수 표현식이면 연결 자체가 사라진다.
    • "+는 느리니 언제나 StringBuilder를 써야 한다." 식 하나로 끝나는 연결은 +가 읽기 쉽고 충분히 손질되어 있다. 빌더가 필요한 곳은 연결이 반복문이나 여러 문장에 걸치는 곳이다.
    • "final이 붙은 문자열 변수는 상수다." 초기화 식까지 상수 표현식이어야 상수 변수다. 메서드 호출 결과나 매개변수로 초기화한 final 변수는 상수 변수가 아니다.
    • "빈 문자열을 더하면 원래 객체가 그대로 나온다." String b = a + "";에서 a가 상수 변수가 아니면 b == a는 false다. JLS 15.18.1이 상수 표현식이 아닌 연결의 결과는 새로 만든 객체라고 정하기 때문이다. OpenJDK 21의 연결 코드에도 이 경우에 새 String을 만들어야 한다는 주석이 달려 있다.
    이 장의 핵심

    String은 공유하기 위해 불변으로 만들어졌고, 불변이기 때문에 고칠 때마다 새 객체가 필요하다. StringBuilder는 그 반대편에 있다. 공유하지 않는 대신 제자리에서 고친다. 조립하는 동안에는 빌더를 쓰고, 조립이 끝나면 toString()으로 불변 String을 만들어 내보낸다. 두 클래스는 경쟁하는 선택지가 아니라 작업의 두 단계를 나누어 맡는다.

    다른 주제와의 연결

    이 회차의 내용은 뒤에서 여러 번 다시 쓰인다. 다음 회차의 래퍼 클래스에서는 Integer가 일정 범위의 값을 캐시해 두고 재사용하는 것을 본다. 불변 객체를 공유해 객체 수를 줄이고, 그 결과 ==와 equals의 답이 갈린다는 구조가 문자열 풀과 같다. 다음 권의 해시 기반 컬렉션에서는 String이 키로 가장 많이 쓰인다. 해시코드를 캐시하는 불변 객체라는 성질이 거기서 값을 한다.

    로그를 남길 때도 이 지식이 쓰인다. 메서드 호출의 인자는 호출 전에 평가되므로, log.debug("user=" + user)는 디버그 로그를 끈 상태에서도 연결을 먼저 수행한다. 로깅 라이브러리들이 메시지 틀과 인자를 따로 받는 메서드를 제공하는 것은 이 연결을 필요할 때까지 미루기 위해서다. 데이터베이스 권에서는 사용자 입력을 +로 이어 SQL을 만드는 일이 왜 위험한지, 그리고 값의 자리를 비워 둔 SQL과 값을 따로 보내는 방식이 그것을 어떻게 막는지를 다룬다.

    메서드 체이닝은 자바 라이브러리 전반에 퍼져 있다. 고급편의 스트림은 새 객체를 돌려주는 쪽의 체인이고, 설정 값을 차례로 채워 객체를 만드는 빌더 계열의 API는 대개 같은 객체를 돌려주는 쪽의 체인이다. 체인을 볼 때마다 "지금 돌아온 참조가 같은 객체인가, 새 객체인가"를 묻는 습관을 들이면 메모리에서 벌어지는 일을 놓치지 않는다.
    String의 내부 표현
    OpenJDK 9 이상에서 String은 byte[] value와 coder로 글자를 저장한다. 모든 문자가 Latin-1 범위면 글자당 1바이트, 하나라도 벗어나면 전체를 UTF-16으로 저장한다. length()가 세는 것은 UTF-16 코드 유닛이다.
    문자열 리터럴과 풀
    JLS 3.10.5에 따라 내용이 같은 리터럴과 String 상수 표현식은 인턴되어 같은 인스턴스를 가리킨다. HotSpot에서 그 객체는 JDK 7부터 보통의 힙에 있고, 풀은 내용으로 객체를 찾아 주는 표다.
    == 와 equals
    ==는 같은 객체인지, equals는 같은 문자 시퀀스인지를 본다. new나 실행 중 연결로 만든 문자열은 풀의 객체와 다른 객체이므로 내용 비교에는 항상 equals를 쓴다.
    불변성이 받치는 것

OpenJDK 21의 StringBuilder.toString()은 내부 배열을 복사해서 String을 만든다. 복사하지 않고 빌더의 배열을 String이 그대로 함께 쓰게 한다면 생기는 문제는? 가비지 컬렉터가 공유된 배열을 회수하지 못해 메모리 누수가 생긴다. 이후 빌더에 append나 reverse를 하면 이미 내보낸 String의 내용이 함께 바뀌어 String의 불변성이 깨진다. 빌더와 String이 같은 모니터 락을 쓰게 되어 교착 상태가 생긴다. String의 hashCode()가 호출될 때마다 예외가 발생한다. 배열을 공유해도 되는 것은 양쪽이 모두 불변일 때뿐이다. 빌더는 가변이므로 같은 배열을 쓰면 빌더의 변경이 String의 내용 변경으로 이어진다. 그러면 풀 공유와 해시 캐시를 비롯해 불변성에 기댄 것들이 모두 틀어진다. 여러 객체가 한 배열을 참조하는 것 자체는 가비지 컬렉션에 문제가 되지 않고, 락이나 예외와도 관계가 없다. sb.append("a").append("b")에서 두 번째 append가 첫 번째와 같은 빌더에 대해 실행되는 이유는? 컴파일러가 점(.)으로 이어진 호출을 발견하면 맨 앞의 변수를 각 호출의 대상으로 복사해 넣기 때문이다. append가 static 메서드여서 호출 대상 객체가 필요 없기 때문이다. StringBuilder가 final 클래스이기 때문이다. 첫 append가 자기 자신의 참조(this)를 돌려주고, 그 반환값이 다음 호출의 대상이 되기 때문이다. 메서드 호출식의 값은 반환값이고, 체인의 다음 호출은 그 값에 대해 이뤄진다. 바이트코드에서도 첫 invokevirtual이 오퍼랜드 스택에 남긴 반환값이 그대로 다음 invokevirtual의 호출 대상이 된다. 컴파일러가 변수를 복사해 넣는 것이 아니므로, 메서드가 다른 객체를 돌려주면(String의 메서드처럼) 다음 호출은 그 다른 객체에 대해 실행된다.
    문자열 리터럴(string literal)
    소스에서 큰따옴표로 감싼 문자열. 실행 시점에 String 인스턴스를 가리키는 참조가 되며, 내용이 같은 리터럴은 항상 같은 인스턴스를 가리킨다(JLS 3.10.5).
    문자열 풀(string pool)
    인턴된 String 객체를 내용으로 찾을 수 있게 String 클래스가 관리하는 모음. 같은 내용은 하나만 등록된다.
    인턴(intern)
    어떤 내용의 문자열에 대해 풀에 등록된 대표 객체를 얻는 일. String.intern()은 풀에 같은 내용이 있으면 그 객체를, 없으면 자신을 등록하고 자신을 돌려준다.
    Compact Strings
    JDK 9(JEP 254)에서 도입된 String의 내부 표현. byte 배열과 인코딩 표시 필드를 써서 Latin-1 문자열을 글자당 1바이트로 저장한다.
    코드 유닛(code unit)
    UTF-16에서 16비트 단위 하나. char 하나에 해당한다. U+FFFF를 넘는 문자는 코드 유닛 두 개(서로게이트 쌍)로 표현된다.
    상수 표현식(constant expression)
    리터럴, 상수 변수, 일부 연산자만으로 이루어져 컴파일할 때 값이 정해지는 식(JLS 15.29). String 타입이면 결과가 인턴된다.
    부트스트랩 메서드(bootstrap method)
    invokedynamic 명령이 처음 실행될 때 JVM이 호출하는 메서드. 그 호출 지점에서 실제로 실행할 코드를 정해 CallSite로 돌려준다. 문자열 연결에서는 StringConcatFactory의 메서드가 맡는다.
    용량(capacity)
    StringBuilder가 배열을 다시 할당하지 않고 담을 수 있는 문자 수. 실제로 담긴 문자 수인 길이(length)와 구분한다.
    분할 상환 분석(amortized analysis)
    가끔 일어나는 비싼 연산의 비용을 전체 연산에 나누어 평균을 내는 계산법. 배열을 두 배씩 키우는 append의 비용을 설명할 때 쓴다.
    메서드 체이닝(method chaining)
    메서드의 반환값에 대해 곧바로 다음 메서드를 호출하는 식으로 호출을 이어 쓰는 방식. 반환값이 this인지 새 객체인지에 따라 메모리에서 일어나는 일이 다르다.
