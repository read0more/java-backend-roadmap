    이 회차의 질문: 값의 범위를 타입으로 닫을 수 있는가

    프로그램에는 "정해진 몇 가지 중 하나"인 값이 자주 나온다. 요일은 일곱 가지이고, 주문 상태는 접수·결제 완료·배송 중·완료 같은 몇 가지이며, 배송 방식도 회사가 정한 몇 가지뿐이다. 이런 값을 변수에 담으려면 타입을 골라야 하는데, 지금까지 배운 타입 가운데 "이 세 가지 중 하나"를 그대로 표현하는 것은 없다. int는 약 43억 가지 값을 담고 String은 사실상 무한히 많은 값을 담는다.

    타입(type)은 변수에 들어갈 수 있는 값의 집합과 그 값으로 할 수 있는 연산을 정한다. 컴파일러가 해 주는 검사는 전부 이 집합을 기준으로 한다. 매개변수를 String으로 선언하면 컴파일러는 "문자열이기만 하면 된다"까지만 확인하고, 그 문자열이 의미 있는 세 가지 중 하나인지는 확인하지 않는다. 타입이 허용하는 집합이 프로그램이 실제로 처리할 수 있는 집합보다 넓으면, 그 차이만큼이 실행 중에야 드러나는 오류의 통로가 된다.

    이 회차는 그 통로를 좁혀 가는 과정을 따라간다. 문자열로 시작해서 문자열 상수, 정수 상수를 거치며 무엇이 해결되고 무엇이 남는지 본다. 그다음 클래스를 이용해 값의 집합을 정확히 세 개로 닫는 방법을 손으로 만들고, 자바의 열거형(enum)이 그 구조를 컴파일러가 대신 만들어 주는 문법이라는 것을 자바 언어 명세(JLS) 8.9절과 javap 출력으로 확인한다. 앞 회차에서 다룬 것 가운데 static 필드와 클래스 초기화, 참조 비교(==)와 동등성(equals), 불변 객체가 그대로 재료로 쓰인다. 본문의 실행 결과와 javap 출력은 모두 JDK 21에서 직접 컴파일해 확인한 것이다.

    문자열로 종류를 표현하면: 컴파일러가 아무것도 막지 않는다

    택배 요금을 계산하는 프로그램을 만든다. 배송 방식은 일반, 빠른 배송, 새벽 배송 세 가지이고 무게 1kg당 요금이 각각 500원, 800원, 1,200원이다. 배송 방식을 문자열로 받는 가장 단순한 구현은 다음과 같다.

    class ShippingCalculator {
    int fee(String method, int kg) {
        int perKg;
        if (method.equals("STANDARD")) {
            perKg = 500;

        } else if (method.equals("DAWN")) {
            perKg = 1200;
        } else {

        return kg * perKg;
    }

    마지막 else에서 예외를 던지도록 고치면 조용히 0원이 되는 일은 막을 수 있다. 그래도 오류가 드러나는 시점은 여전히 실행 중, 그것도 그 줄이 실제로 실행되는 순간이다. 잘 쓰이지 않는 경로에 숨은 오타는 테스트가 그 경로를 지나가지 않는 한 배포 뒤까지 살아남는다. 이 메서드가 받아들일 수 있는 값이 무엇인지도 시그니처에서는 알 수 없다. fee(String method, int kg)를 본 사람은 구현을 열어 보거나 문서를 찾아야 "STANDARD", "EXPRESS", "DAWN"이라는 세 문자열을 알게 된다.

    원인은 구현의 부주의가 아니라 타입 선택에 있다. String 타입의 값 집합은 모든 문자열이고, 이 메서드가 처리할 수 있는 값은 그중 셋이다. 컴파일러는 선언된 타입만 보므로 나머지 모든 문자열도 올바른 인자로 통과시킨다. 이렇게 컴파일러가 타입 정보만으로 잘못된 값의 사용을 막아 주는 성질을 타입 안전성(type safety)이라 하고, 지금 코드는 배송 방식에 대해 타입 안전성이 없다.

    String 매개변수가 받아들이는 넓은 집합 안에 유효한 값 세 개만 작게 들어 있고, enum 타입은 그 세 개만으로 이루어진 닫힌 집합이라는 대비를 보여 준다. 좌우 2분할 개념도. 흰 배경, 평면 벡터 스타일. 왼쪽 패널 제목 "String 매개변수". 큰 연한 회색 원 안에 작은 초록 원이 들어 있다. 작은 초록 원 안에 "STANDARD", "EXPRESS", "DAWN" 세 라벨. 초록 원 바깥, 회색 원 안쪽에는 빨간색 글씨로 "EXPRES", "express", "당일" 세 라벨이 흩어져 있고 그 옆에 "컴파일 통과" 라벨. 오른쪽 패널 제목 "enum 매개변수". 초록 원 하나만 있고 그 안에 "STANDARD", "EXPRESS", "DAWN". 원 바깥은 비어 있고 "다른 값은 컴파일 오류" 라벨이 원 밖에 붙어 있다. 두 패널 사이에 왼쪽에서 오른쪽으로 향하는 굵은 화살표와 "값의 집합을 닫는다" 라벨. String은 모든 문자열을 허용하므로 잘못된 값도 컴파일을 통과한다. enum 타입은 값의 집합 자체가 세 개로 닫혀 있다.

    문자열 상수와 정수 상수: 이름은 생겼지만 타입은 그대로다

    오타를 줄이는 첫 번째 시도는 문자열에 이름을 붙이는 것이다. 상수를 모아 둔 클래스를 만들고 호출할 때 그 상수를 쓴다.

    public class ShippingCodes {
    public static final String STANDARD = "STANDARD";
    public static final String EXPRESS = "EXPRESS";
    public static final String DAWN = "DAWN";
}

    이제 calc.fee(ShippingCodes.EXPRES, 3)처럼 상수 이름을 틀리면 컴파일러가 그런 필드가 없다고 알려 준다. 쓸 수 있는 값의 목록도 한 클래스에 모였다. 하지만 메서드의 매개변수 타입은 여전히 String이다. calc.fee("EXPRES", 3)처럼 상수를 거치지 않고 문자열을 직접 넘기는 코드는 전과 똑같이 컴파일된다. 상수 클래스는 "이것을 써 달라"는 권고일 뿐이고, 컴파일러에게 그 권고를 강제할 근거를 주지 못한다.

    문자열 대신 정수를 쓰는 방식도 오래 쓰였다. 정수는 비교가 빠르고 switch에 넣기 쉽다는 이유였다.

    세 방식에 공통된 한계는 하나다. 이름을 아무리 잘 붙여도 매개변수의 타입이 String이나 int인 한, 컴파일러가 아는 값의 집합은 넓은 그대로다. 필요한 것은 값이 정확히 세 개뿐인 타입이다.

    타입 안전 열거형 패턴: 클래스로 값의 집합을 닫는다

    자바에서 새 타입을 만드는 수단은 클래스다. 클래스 타입 변수에 들어갈 수 있는 값은 그 클래스의 인스턴스를 가리키는 참조(와 null)다. 그렇다면 인스턴스가 정확히 세 개만 존재하고 그 이상은 누구도 만들 수 없는 클래스를 만들면, 그 클래스 타입이 곧 "세 가지 중 하나"를 표현하는 타입이 된다. 인스턴스 수를 통제하는 도구는 이미 갖고 있다. 생성자를 private으로 막으면 클래스 바깥에서는 new를 쓸 수 없다.

    public class ShippingMethod {
    public static final ShippingMethod STANDARD = new ShippingMethod();
    public static final ShippingMethod EXPRESS = new ShippingMethod();
    public static final ShippingMethod DAWN = new ShippingMethod();

    private ShippingMethod() {
    }
}

    이 클래스가 하는 일을 한 줄씩 보자. private 생성자 때문에 인스턴스를 만들 수 있는 곳은 클래스 내부뿐이다. 클래스 내부에서는 static 필드의 초기화식에서 new를 세 번 호출한다. static 필드는 클래스가 초기화될 때 한 번만 초기화되므로 인스턴스는 정확히 세 개 만들어진다. 필드가 final이므로 그 참조를 다른 인스턴스로 바꿔 끼울 수도 없다. public이므로 어디서든 ShippingMethod.STANDARD라는 이름으로 그 인스턴스에 접근한다. 이 구조를 타입 안전 열거형 패턴(typesafe enum pattern)이라 부른다.

    [메서드 영역: ShippingMethod 클래스의 static 필드]         [힙]
  STANDARD ───────────────────────────────►  x001  ShippingMethod 인스턴스
  EXPRESS  ───────────────────────────────►  x002  ShippingMethod 인스턴스
  DAWN     ───────────────────────────────►  x003  ShippingMethod 인스턴스

[스택: main의 지역 변수]
  a ──────────────────────────────────────►  x002
  b ──────────────────────────────────────►  x002

  a == b                     → true   (둘 다 x002)
  a == ShippingMethod.DAWN   → false  (x002 과 x003)

    계산기의 매개변수 타입을 이 클래스로 바꾼다.

    public class ShippingCalculator {
    public int fee(ShippingMethod method, int kg) {
        int perKg;
        if (method == ShippingMethod.STANDARD) {
            perKg = 500;
        } else if (method == ShippingMethod.EXPRESS) {
            perKg = 800;
        } else if (method == ShippingMethod.DAWN) {
            perKg = 1200;
        } else {
            perKg = 0;
        }
        return kg * perKg;
    }
}

public class PatternMain {
    public static void main(String[] args) {
        ShippingCalculator calc = new ShippingCalculator();
        System.out.println(calc.fee(ShippingMethod.STANDARD, 3));
        System.out.println(calc.fee(ShippingMethod.DAWN, 3));

        ShippingMethod a = ShippingMethod.EXPRESS;
        ShippingMethod b = ShippingMethod.EXPRESS;
        System.out.println(a == b);
        System.out.println(a == ShippingMethod.DAWN);
        System.out.println(a);
    }
}

    이제 앞에서 통과하던 잘못된 호출이 전부 컴파일 단계에서 걸린다. calc.fee("EXPRES", 3)은 "String cannot be converted to ShippingMethod" 오류가 나고, 직접 새 값을 만들려는 new ShippingMethod()는 "ShippingMethod() has private access" 오류가 난다. 인자 순서를 바꾼 calc.fee(3, ShippingMethod.EXPRESS)도 타입이 맞지 않아 거부된다. 메서드 시그니처만 봐도 무엇을 넘겨야 하는지 알 수 있고, IDE는 ShippingMethod.까지 입력하면 가능한 값 세 개를 보여 준다.

    비교에 ==를 쓴 것도 우연이 아니다. ShippingMethod 타입의 변수가 null이 아니라면 그것이 가리킬 수 있는 대상은 x001, x002, x003 셋뿐이다. "같은 배송 방식인가"라는 질문과 "같은 인스턴스인가"라는 질문이 일치하므로, equals를 재정의할 필요 없이 참조값 비교로 충분하다.

    이 패턴은 목적을 이루지만 손으로 유지해야 할 것이 많다. 상수를 하나 추가할 때마다 public static final ... = new ...를 빠짐없이 써야 하고 누군가 실수로 private을 지우면 보장이 깨진다. 출력하면 ShippingMethod@6d06d69c처럼 Object.toString()의 기본 형식이 나오므로 이름을 보려면 필드와 toString()을 따로 넣어야 한다. 전체 값의 목록을 돌려주는 메서드, 이름으로 값을 찾는 메서드도 직접 써야 한다. switch의 case에도 쓸 수 없다. 그리고 뒤에서 실험으로 확인하겠지만 리플렉션과 직렬화를 이용하면 네 번째 인스턴스를 만들 수 있어서, "인스턴스는 셋뿐"이라는 전제가 언어 차원에서 보장되지는 않는다.

    enum 선언: 같은 구조를 컴파일러가 만들어 준다

    자바 5에서 추가된 열거형은 위 패턴을 언어 문법으로 올린 것이다. 선언은 한 줄이면 된다.

    public enum ShippingMethod {
    STANDARD, EXPRESS, DAWN
}

    JLS 8.9는 enum 선언이 "이름 붙은 인스턴스의 작은 집합을 정의하는, 제한된 종류의 클래스"인 열거형 클래스(enum class)를 만든다고 정의한다. 클래스라는 말이 비유가 아님을 컴파일 결과로 확인하자. 위 파일을 컴파일하고 javap -p ShippingMethod.class를 실행한 출력이다.

    public final class ShippingMethod extends java.lang.Enum {
  public static final ShippingMethod STANDARD;
  public static final ShippingMethod EXPRESS;
  public static final ShippingMethod DAWN;
  private static final ShippingMethod[] $VALUES;
  public static ShippingMethod[] values();
  public static ShippingMethod valueOf(java.lang.String);
  private ShippingMethod();
  private static ShippingMethod[] $values();
  static {};
}

    손으로 만든 클래스와 나란히 놓으면 뼈대가 같다. 상수 세 개는 자기 자신 타입의 public static final 필드이고 생성자는 private이다. 소스에 쓰지 않은 것들이 어디서 왔는지는 JLS 8.9가 항목별로 정해 두었다.

    클래스 파일에 있는 것JLS 8.9의 규칙
    extends java.lang.Enum열거형 클래스 E의 직접 상위 클래스 타입은 Enum다. extends 절을 쓸 수 없으므로 다른 클래스를 상속할 수 없다(§8.9).
    final class클래스 본문을 가진 상수가 하나도 없으면 암묵적으로 final이다. abstract, final 등을 직접 붙이면 컴파일 오류다(§8.9).
    public static final ShippingMethod STANDARD 등상수마다 같은 이름의 public static final 필드가 암묵적으로 선언되고, 그 초기화식이 E의 인스턴스를 만든다. 선언 순서는 상수 순서와 같고, 직접 선언한 static 필드보다 앞선다(§8.9.3).
    private ShippingMethod()생성자를 쓰지 않으면 private 기본 생성자가 암묵적으로 선언된다. 생성자에 public·protected를 붙이면 컴파일 오류이고, 접근 제어자를 생략한 생성자는 private이다(§8.9.2).
    values(), valueOf(String)상수를 선언 순서대로 담은 배열을 돌려주는 public static E[] values()와, 이름으로 상수를 찾는 public static E valueOf(String name)이 암묵적으로 선언된다(§8.9.3).

    $VALUES 필드와 $values() 메서드는 명세에 없는 이름이다. values()를 구현하려고 javac가 넣은 것이며, 다른 컴파일러는 다른 방식으로 구현해도 된다. 명세가 보장하는 것과 javac가 그렇게 구현한 것을 구분해서 읽어야 한다.

    인스턴스가 만들어지는 과정은 static {}, 곧 클래스 초기화 메서드에 들어 있다. javap -c로 본 앞부분이다.

    0번부터 10번까지가 손으로 쓴 STANDARD = new ShippingMethod()와 같은 일이다. new로 힙에 인스턴스를 만들고, 생성자를 호출하고, 그 참조를 static 필드에 저장한다. 다른 점은 생성자에 넘기는 인자다. 소스에서는 인자 없는 생성자였는데 클래스 파일의 생성자는 (String, int)를 받고, 컴파일러가 상수의 이름 문자열 "STANDARD"와 선언 순서 0을 넘긴다. 이 두 값은 그대로 상위 클래스의 생성자 Enum(String name, int ordinal)로 전달된다. Enum의 API 문서는 이 생성자를 프로그래머가 호출할 수 없고 컴파일러가 만들어 내는 코드가 쓰기 위한 것이라고 설명한다. 손으로 만든 패턴에서 아쉬웠던 "이름을 아는 인스턴스"가 여기서 해결된다.

    enum 상수 세 개가 클래스의 static final 필드이고, 각각 힙의 인스턴스 하나를 가리키며, 인스턴스가 name과 ordinal을 갖고 있음을 보여 준다. 가로형 메모리 구조도. 흰 배경, 평면 벡터 스타일. 왼쪽에 큰 둥근 사각형 "메서드 영역"이 있고 그 안에 상자 "ShippingMethod 클래스"가 있다. 상자 안에 세로로 네 칸: "STANDARD", "EXPRESS", "DAWN", "$VALUES". 오른쪽에 큰 둥근 사각형 "힙"이 있고 그 안에 세로로 객체 상자 세 개: 첫째 "name = STANDARD / ordinal = 0", 둘째 "name = EXPRESS / ordinal = 1", 셋째 "name = DAWN / ordinal = 2". 그 아래에 세 칸짜리 배열 상자 하나. 왼쪽 "STANDARD" 칸에서 첫째 객체로, "EXPRESS" 칸에서 둘째 객체로, "DAWN" 칸에서 셋째 객체로 실선 화살표. "$VALUES" 칸에서 배열 상자로 화살표, 배열의 세 칸에서 각각 세 객체로 얇은 점선 화살표. 힙 영역 하단에 "인스턴스는 상수 개수만큼만 존재" 라벨. enum 상수는 클래스의 static final 필드이고, 클래스 초기화 때 만들어진 인스턴스를 가리킨다.

    인스턴스가 만들어지는 시점도 일반 클래스의 규칙을 그대로 따른다. JLS 12.4.1에 따르면 클래스는 그 클래스의 static 필드가 처음 사용되거나 static 메서드가 처음 호출되기 직전에 초기화된다. 생성자에 출력문을 넣어 확인해 보자.

    enum Level {
    LOW, HIGH;

    Level() {
        System.out.println("생성: " + name() + ", ordinal=" + ordinal());
    }
}

public class InitMain {
    public static void main(String[] args) {
        System.out.println("main 시작");
        Level level = Level.HIGH;
        System.out.println("HIGH 사용 후");
        Level other = Level.LOW;
        System.out.println(level.compareTo(other));
    }
}

Level.HIGH를 처음 읽는 순간 Level 클래스가 초기화되고, 그때 HIGH만이 아니라 모든 상수가 선언 순서대로 한꺼번에 만들어진다. 그 뒤 Level.LOW를 읽을 때는 생성자가 다시 실행되지 않는다. 클래스 초기화는 클래스당 한 번뿐이기 때문이다. JLS 12.4.2는 여러 스레드가 동시에 같은 클래스를 초기화하려 할 때 클래스마다 있는 초기화 락으로 한 스레드만 초기화를 수행하도록 절차를 정해 두었다. 따라서 enum 상수는 별도의 동기화 코드 없이도 스레드가 몇 개든 정확히 한 번만 만들어진다.

    Enum 클래스가 물려주는 것: name, ordinal, 그리고 final 메서드들

    모든 열거형 클래스는 java.lang.Enum을 상속하므로 그 메서드를 쓸 수 있다. 여기에 컴파일러가 넣어 준 values()와 valueOf(String)이 더해진다. 한 번에 실행해 보자.

    import java.util.Arrays;

public class EnumMain {
    public static void main(String[] args) {
        ShippingMethod m = ShippingMethod.EXPRESS;
        System.out.println(m);
        System.out.println(m.name());
        System.out.println(m.ordinal());
        System.out.println(m.getClass().getSuperclass());
        System.out.println(m == ShippingMethod.EXPRESS);
        System.out.println(m.equals(ShippingMethod.DAWN));
        System.out.println(m.compareTo(ShippingMethod.DAWN));

        ShippingMethod[] all = ShippingMethod.values();
        System.out.println(Arrays.toString(all));
        System.out.println(all == ShippingMethod.values());
        System.out.println(all[0] == ShippingMethod.values()[0]);

        ShippingMethod parsed = ShippingMethod.valueOf("DAWN");
        System.out.println(parsed == ShippingMethod.DAWN);
        try {
            ShippingMethod.valueOf("dawn");
        } catch (IllegalArgumentException e) {
            System.out.println(e.getMessage());
        }
    }
}

    첫 줄에서 손으로 만든 패턴과의 차이가 바로 보인다. println(m)은 toString()을 호출하는데, Enum.toString()은 상수의 이름을 돌려주도록 구현되어 있어서 ShippingMethod@6d06d69c가 아니라 EXPRESS가 찍힌다. name()도 같은 문자열을 돌려주지만 둘의 지위는 다르다. name()은 final이라 재정의할 수 없고 언제나 선언에 쓴 식별자 그대로를 돌려준다. toString()은 재정의할 수 있어서 사람에게 보여 줄 다른 문자열로 바꿀 수 있다. 그래서 "정확한 이름이 필요한 곳"에는 name()을 써야 한다.

    ordinal()은 선언 순서를 0부터 센 정수다. compareTo()는 이 선언 순서를 기준으로 대소를 정하므로 EXPRESS.compareTo(DAWN)은 음수다. Enum이 Comparable를 구현하고 그 타입 인자가 자기 자신의 열거형 타입이기 때문에, 서로 다른 열거형의 상수끼리는 compareTo를 호출하는 코드 자체가 컴파일되지 않는다.

    equals()와 hashCode()도 final이다. JLS 8.9.1은 Enum의 equals가 Object의 것을 그대로 호출하는 final 메서드, 곧 동일성 비교라고 적고, 상수마다 인스턴스가 하나뿐이므로 equals 대신 ==를 써도 된다고 명시한다. 재정의를 금지한 이유는 분명하다. 누군가 equals를 다르게 구현할 수 있다면 "같은 상수 = 같은 인스턴스"라는 등식이 깨지기 때문이다.

    values()에 관한 두 줄은 눈여겨볼 만하다. all == ShippingMethod.values()가 false다. 호출할 때마다 다른 배열이 온다는 뜻이다. 반면 배열의 원소끼리 비교한 all[0] == values()[0]은 true다. 배열은 새로 만들지만 그 안의 참조는 같은 상수 인스턴스를 가리킨다. javac가 만든 values()의 바이트코드가 이 동작을 그대로 보여 준다.

    내부 배열 $VALUES를 그대로 돌려주지 않고 clone()한 복사본을 돌려준다. 자바의 배열은 원소를 바꿀 수 있는 가변 객체다. 내부 배열을 그대로 내주면 받은 쪽에서 all[0] = null 같은 대입으로 열거형 전체의 상수 목록을 망가뜨릴 수 있다. 불변 객체 회차에서 본 방어적 복사와 같은 이유다. 대가도 있다. values()는 호출할 때마다 배열 하나를 새로 할당하므로, 매우 자주 실행되는 반복문 안에서 매번 부르는 코드는 그만큼의 할당을 만든다.

    valueOf(String)은 이름이 정확히 일치하는 상수를 돌려준다. 대소문자가 다르거나 없는 이름이면 null을 돌려주는 것이 아니라 IllegalArgumentException을 던지고, 인자가 null이면 NullPointerException을 던진다. 외부에서 들어온 문자열을 상수로 바꿀 때는 이 예외를 처리할 자리를 마련해 두어야 한다. 예외의 구조와 처리 방법은 이 권의 09·10회에서 다룬다.

    ordinal에 의존하면 안 되는 이유

    ordinal()은 정수를 돌려주므로 쓰기 편해 보인다. 데이터베이스 컬럼이나 파일에 0, 1, 2를 저장하고, 읽을 때 values()[n]으로 되돌리면 저장 공간도 적게 든다. 그러나 이 숫자는 "선언에서 몇 번째에 적혀 있는가"일 뿐이고 상수의 의미와는 아무 관계가 없다. 선언이 바뀌면 숫자도 바뀐다.

      2            DAWN                 EXPRESS    ← 의미가 바뀜

    변경 전에 빠른 배송으로 저장된 주문은 1로 기록되어 있다. 변경 후의 프로그램이 그 1을 읽어 values()[1]로 되돌리면 SAME_DAY가 나온다. 예외는 나지 않는다. 1은 변경 후에도 유효한 인덱스이기 때문이다. 과거의 빠른 배송 주문이 전부 당일 배송으로, 새벽 배송 주문이 전부 빠른 배송으로 읽히고, 프로그램은 그 사실을 알 방법이 없다. 상수를 끝에만 추가하면 기존 숫자는 유지되지만, 그것은 "앞으로 누구도 중간에 넣거나 순서를 바꾸거나 지우지 않는다"는 약속을 소스 코드 밖에서 사람이 지켜야 한다는 뜻이다.

    상수 하나를 중간에 끼워 넣으면 이미 저장된 숫자가 다른 상수를 가리키게 된다는 것을 전후 비교로 보여 준다. 좌우 비교 다이어그램. 흰 배경, 평면 벡터 스타일. 왼쪽 열 제목 "변경 전". 세로로 쌓인 상자 세 개에 번호표와 이름: "0 STANDARD", "1 EXPRESS", "2 DAWN". 오른쪽 열 제목 "변경 후". 세로로 쌓인 상자 네 개: "0 STANDARD", "1 SAME_DAY"(주황색으로 강조), "2 EXPRESS", "3 DAWN". 가운데 아래에 원통 모양 데이터베이스 아이콘과 라벨 "저장된 값 1". 데이터베이스에서 왼쪽 "1 EXPRESS" 상자로 향하는 회색 점선 화살표에 "저장할 때" 라벨, 오른쪽 "1 SAME_DAY" 상자로 향하는 빨간 실선 화살표에 "읽을 때" 라벨. 그림 하단에 "예외 없이 다른 상수로 읽힌다" 라벨. 저장된 숫자는 그대로인데 그 숫자가 가리키는 상수가 바뀐다. 오류는 발생하지 않는다.

    Enum.ordinal()의 API 문서는 이 메서드의 용도를 스스로 제한한다. 대부분의 프로그래머는 이 메서드를 쓸 일이 없고, EnumSet과 EnumMap 같은 정교한 열거형 기반 자료 구조가 쓰도록 설계되었다는 것이다. 이 자료 구조들은 한 번의 JVM 실행 안에서만 ordinal을 쓴다. 실행 중에는 선언 순서가 바뀔 일이 없으므로 안전하다. 문제가 되는 것은 ordinal이 프로그램의 수명을 넘어 살아남는 곳, 곧 데이터베이스·파일·네트워크 메시지로 나갈 때다.

    JLS 13.4.26은 열거형 클래스에 상수를 추가하거나 순서를 바꾸는 것이 기존 바이너리와의 호환성을 깨지 않는다고 규정한다. 이미 컴파일된 다른 클래스들이 ordinal 값을 자기 안에 박아 두지 않기 때문에 가능한 규정이다. 뒤의 switch 절에서 javac가 enum에 대한 switch를 컴파일할 때조차 ordinal을 클래스 파일에 고정하지 않고 실행 시점에 다시 읽도록 코드를 만든다는 것을 볼 것이다. 컴파일러도 지키는 규칙을 응용 코드가 어길 이유는 없다.

    그러면 프로그램 밖에 무엇을 저장해야 하는가. 첫 번째 선택은 name()이다. 이름은 순서를 바꾸거나 중간에 상수를 넣어도 변하지 않는다. 상수의 이름을 바꾸면 깨지지만, 그때는 valueOf()가 IllegalArgumentException을 던지므로 조용히 다른 값으로 읽히지 않고 실패가 드러난다. 두 번째 선택은 상수마다 저장용 코드를 필드로 따로 두는 것이다. 자바 식별자와 저장되는 값을 분리하면 이름을 자유롭게 바꿀 수 있다. 이 방법은 뒤의 리팩토링 3에서 구현한다.

    리팩토링 1: 요금표를 상수 안으로 옮긴다

    enum으로 바꾼 뒤에도 계산기의 본문은 손으로 만든 패턴 때와 같다. method == ShippingMethod.STANDARD이면 500, EXPRESS이면 800으로 이어지는 분기가 그대로 남아 있다. 타입은 안전해졌지만 구조의 문제가 남았다. "일반 배송은 1kg당 500원"이라는 사실은 일반 배송이라는 값에 딸린 데이터인데, 그 데이터가 ShippingMethod가 아니라 ShippingCalculator의 분기문 속에 들어 있다.

    이 구조에서 당일 배송을 추가하려면 두 곳을 고쳐야 한다. enum에 상수를 추가하고, 계산기를 열어 분기를 하나 더 쓴다. 두 번째 작업을 잊어도 컴파일러는 알려 주지 않고 마지막 else가 0원을 돌려준다. 문자열을 쓸 때 보았던 조용한 0원이 자리만 옮겨 다시 나타난다.

    열거형 클래스는 클래스이므로 인스턴스 필드와 생성자를 가질 수 있다. 상수마다 달라지는 데이터를 필드로 옮긴다.

    public enum ShippingMethod {
    STANDARD(500), EXPRESS(800), DAWN(1200);

    private final int feePerKg;

    ShippingMethod(int feePerKg) {
        this.feePerKg = feePerKg;
    }

    public int feePerKg() {
        return feePerKg;
    }
}

    상수 이름 뒤의 괄호는 생성자에 넘길 인자다. STANDARD(500)은 이 상수의 인스턴스를 만들 때 생성자에 500을 넘기라는 뜻이다. JLS 8.9.3은 상수에 해당하는 필드의 초기화식이 상수의 인자를 생성자에 넘겨 인스턴스를 만든다고 규정하는데, 그 규칙이 이 문법에 대응한다. 상수 목록 뒤에 필드나 메서드가 이어지면 목록 끝에 세미콜론을 붙여야 한다. 생성자에는 접근 제어자를 쓰지 않았지만 enum의 생성자이므로 private이다.

    클래스 초기화 코드가 어떻게 달라졌는지 javap -c로 확인한다. 첫 번째 상수를 만드는 부분이다.

    name과 ordinal은 상위 클래스 Enum에 선언된 필드이고 feePerKg는 ShippingMethod에 선언된 필드다. 하위 클래스의 인스턴스 하나가 상위 클래스의 필드까지 함께 갖는다는 것은 자바 기본편의 상속에서 본 그대로다. 이제 계산기는 분기 없이 상수에게 값을 물어보면 된다.

    public class ShippingCalculator {
    public int fee(ShippingMethod method, int kg) {
        return kg * method.feePerKg();
    }
}

    세 가지 배송 방식으로 3kg의 요금을 계산하면 전과 같이 1500, 2400, 3600이 나온다. 달라진 것은 변경에 대한 반응이다. 당일 배송을 추가하는 작업은 상수 목록에 SAME_DAY(1000)을 적는 한 줄로 끝난다. 요금을 빠뜨리고 SAME_DAY라고만 쓰면 인자 없는 생성자가 없으므로 javac가 "constructor ShippingMethod in enum ShippingMethod cannot be applied to given types" 오류를 낸다. 잊을 수 있는 자리가 없어졌다.

    일상에서 가져온 비유계산원이 외운 가격과 상품에 붙은 가격표

    계산원이 모든 상품의 가격을 외워서 계산하는 가게에서는 신상품이 들어올 때마다 계산원에게 따로 알려 줘야 하고, 알려 주는 것을 잊으면 계산이 틀린다. 가격표가 상품에 붙어 있으면 계산원은 읽기만 하면 되고, 가격표 없는 상품은 진열 단계에서 걸러진다. 필드를 가진 enum이 뒤쪽 가게다. 비유가 맞지 않는 지점도 있다. 가게의 가격표는 영업 중에도 바꿔 붙일 수 있지만 enum의 final 필드는 소스에 적힌 값으로 고정되어 다시 컴파일하고 배포해야 바뀐다. 운영 중에 수시로 바뀌는 요금이라면 enum의 필드가 아니라 데이터베이스나 설정에 두어야 한다.

    필드를 final로 선언한 것에도 이유가 있다. enum 상수는 static 필드를 통해 프로그램 전체가 공유하는 인스턴스다. 언어 명세는 enum의 필드가 final이어야 한다고 요구하지 않으므로 값을 바꾸는 메서드를 만들 수도 있다. 그러나 그렇게 하면 불변 객체 회차에서 본 공유 참조의 부작용이 프로그램 전체 범위에서 일어난다. 한 곳에서 EXPRESS의 요금을 바꾸면 EXPRESS를 쓰는 모든 코드의 계산 결과가 바뀌고, 여러 스레드가 동시에 읽고 쓰면 동기화까지 필요해진다. enum의 필드는 final로 두고 생성자에서만 값을 정한다.

    리팩토링 2: 계산도 상수가 한다

    계산기에 남은 코드는 kg * method.feePerKg() 한 줄이다. 이 계산에 필요한 데이터는 전부 ShippingMethod가 갖고 있고, 계산기는 그것을 꺼내 곱할 뿐이다. 데이터를 가진 객체가 그 데이터를 쓰는 로직도 함께 갖게 하는 것이 자바 기본편에서 본 캡슐화다. 메서드를 enum 안으로 옮긴다.

    public enum ShippingMethod {
    STANDARD(500), EXPRESS(800), DAWN(1200);

    private final int feePerKg;

    ShippingMethod(int feePerKg) {
        this.feePerKg = feePerKg;
    }

    public int fee(int kg) {
        return kg * feePerKg;
    }
}

    ShippingCalculator 클래스는 더 필요하지 않다. 호출하는 쪽은 ShippingMethod.EXPRESS.fee(3)처럼 상수에게 직접 계산을 시킨다. 바깥에서 1kg당 요금을 알 필요가 없어졌으므로 feePerKg() 접근자도 지웠다. 요금 계산식이 바뀌어도 고칠 곳은 fee 메서드 한 곳이다.

    여기에 요구 사항이 하나 추가된다. 새벽 배송에는 무게와 관계없이 기본료 3,000원이 붙는다. fee 안에 if (this == DAWN) 분기를 넣어도 동작은 한다. 그러나 특별한 규칙을 가진 상수가 늘 때마다 분기가 늘어나서, 리팩토링 1에서 없앤 분기 사슬이 enum 안에서 다시 자란다. 자바에는 특정 상수에만 적용되는 메서드 본문을 그 상수 옆에 적는 문법이 있다. 상수 뒤에 중괄호로 클래스 본문을 붙이는 것으로, 상수별 클래스 본문(constant-specific class body)이라 부른다.

    public enum ShippingMethod {
    STANDARD(500),
    EXPRESS(800),
    DAWN(1200) {
        @Override
        public int fee(int kg) {
            return 3000 + super.fee(kg);
        }
    };

    private final int feePerKg;

    ShippingMethod(int feePerKg) {
        this.feePerKg = feePerKg;
    }

    public int fee(int kg) {
        return kg * feePerKg;
    }
}

    public static void main(String[] args) {
        for (ShippingMethod m : ShippingMethod.values()) {

        ShippingMethod dawn = ShippingMethod.DAWN;
        System.out.println(dawn.getClass());
        System.out.println(dawn.getDeclaringClass());
        System.out.println(ShippingMethod.EXPRESS.getClass());
        System.out.println(dawn.getClass() == ShippingMethod.class);

    }
}

    새벽 배송 3kg은 기본료 3,000원에 1,200원씩 3kg을 더해 6,600원이다. 눈에 띄는 것은 넷째 줄이다. DAWN의 getClass()가 ShippingMethod가 아니라 ShippingMethod$1을 돌려준다. JLS 8.9.1은 상수의 클래스 본문이 그 열거형 클래스의 직접 하위 클래스인 익명 클래스(anonymous class)를 암묵적으로 선언하며 그 클래스는 final이라고 규정한다. 컴파일 결과물에는 ShippingMethod$1.class 파일이 따로 생기고, javap -p로 열면 다음과 같다.

    final class ShippingMethod$1 extends ShippingMethod {
  private ShippingMethod$1(java.lang.String, int, int);
  public int fee(int);
}

    ShippingMethod 쪽 선언도 달라진다. 본문이 없을 때는 public final class ShippingMethod였는데 이제 final이 빠진 public class ShippingMethod로 나온다. 하위 클래스가 생겼으니 final일 수 없다. 그렇다고 아무나 상속할 수 있게 된 것은 아니다. JLS 8.9는 본문을 가진 상수가 하나라도 있는 열거형 클래스를 암묵적으로 sealed로 정하고, 허용되는 직접 하위 클래스를 그 익명 클래스들로 한정한다. javap -v 출력의 PermittedSubclasses: ShippingMethod$1 속성에서 이를 확인할 수 있다.

    [클래스 계층]
  java.lang.Enum   name, ordinal, final equals()/hashCode()/compareTo()
          ▲
  ShippingMethod                   feePerKg, fee(int)            암묵적 sealed
          ▲
  ShippingMethod$1                 fee(int) 재정의               익명 클래스, final

[힙의 인스턴스와 그 클래스]

    본문을 가진 상수 DAWN만 익명 하위 클래스의 인스턴스이고 나머지 상수는 enum 클래스 자체의 인스턴스이며, fee 호출이 인스턴스의 실제 클래스에 따라 갈린다는 것을 보여 준다. 좌우 2단 구성의 클래스 계층도. 흰 배경, 평면 벡터 스타일. 왼쪽에 세로로 쌓인 클래스 상자 세 개가 아래에서 위로 향하는 속이 빈 삼각형 화살표(상속)로 이어진다. 맨 위 상자 "Enum", 가운데 상자 "ShippingMethod" 안에 작은 글씨 "fee(kg)", 맨 아래 상자 "ShippingMethod$1" 안에 작은 글씨 "fee(kg) 재정의". 가운데 상자 옆에 "sealed" 라벨, 맨 아래 상자 옆에 "익명 클래스" 라벨. 오른쪽에 세로로 원형 객체 세 개: "STANDARD", "EXPRESS", "DAWN". "STANDARD"와 "EXPRESS"에서 가운데 상자 "ShippingMethod"로 점선 화살표, "DAWN"에서 맨 아래 상자 "ShippingMethod$1"로 주황색 점선 화살표. 점선 화살표 묶음 위에 "인스턴스의 실제 클래스" 라벨. 그림 하단에 "같은 fee 호출, 다른 본문 실행" 라벨. 본문을 가진 상수는 익명 하위 클래스의 인스턴스다. 같은 fee 호출이 인스턴스의 실제 클래스에 따라 다른 메서드로 이어진다.

    m.fee(3) 호출은 R2Main의 바이트코드에서 invokevirtual ShippingMethod.fee:(I)I 명령 하나다. 반복문이 세 번 도는 동안 같은 명령이 세 번 실행되지만, invokevirtual은 참조가 가리키는 인스턴스의 실제 클래스에서 메서드를 찾는다. 인스턴스가 x003일 때는 그 클래스인 ShippingMethod$1의 fee가 실행되고, 그 안의 super.fee(kg)가 ShippingMethod의 fee를 부른다. 자바 기본편에서 본 메서드 오버라이딩과 같은 동작이다. 상수별 본문은 새로운 실행 메커니즘이 아니라 상속과 오버라이딩을 enum 문법 안에 담은 것이다. 익명 클래스 자체는 이 권의 08회에서 다룬다.

    이 구조는 getClass()로 열거형 타입을 판별하는 코드를 깨뜨린다. 출력의 일곱째 줄처럼 dawn.getClass() == ShippingMethod.class는 false다. 어떤 상수가 어느 열거형에 속하는지 알고 싶다면 getDeclaringClass()를 써야 한다. Enum의 API 문서는 두 상수의 getDeclaringClass()가 같을 때에만 둘이 같은 열거형 타입이라고 정의하고, 상수별 본문이 있으면 이 값이 getClass()와 다를 수 있다고 밝힌다. instanceof는 하위 클래스의 인스턴스에도 참이므로 마지막 줄은 true다.

    모든 상수가 서로 다른 동작을 가져야 한다면 enum에 추상 메서드를 선언하고 상수마다 본문에서 구현하게 할 수 있다. 이 경우 본문 없는 상수가 하나라도 있으면 컴파일되지 않는다. JDK 21의 javac는 그 상수 위치에 "(열거형 이름) is abstract; cannot be instantiated" 오류를 낸다. 새 상수를 추가하는 사람이 동작을 빠뜨릴 수 없게 만드는 장치다. 연습 문제 3에서 이 형태를 직접 다룬다.

    리팩토링 3: 저장용 코드와 역방향 조회

    ordinal 절에서 미뤄 둔 문제로 돌아간다. 프로그램 밖에 저장할 값으로 name()을 쓰면 순서 변경에는 안전하지만 자바 식별자와 저장 형식이 한 몸이 된다. 데이터베이스에 "EXPRESS"가 저장되어 있다면 상수 이름을 FAST로 바꾸는 순간 기존 데이터를 읽지 못한다. 저장 형식을 식별자에서 떼어 내려면 상수마다 저장용 코드를 필드로 따로 둔다. 방법은 리팩토링 1과 같고, 코드로 상수를 찾는 역방향 조회가 추가된다.

    import java.util.HashMap;
import java.util.Map;

public enum ShippingMethod {
    STANDARD("S", 500),
    EXPRESS("E", 800),
    DAWN("D", 1200) {
        @Override
        public int fee(int kg) {
            return 3000 + super.fee(kg);
        }
    };

    private static final Map BY_CODE = new HashMap<>();

    static {
        for (ShippingMethod m : values()) {
            BY_CODE.put(m.code, m);
        }
    }

    private final String code;
    private final int feePerKg;

    ShippingMethod(String code, int feePerKg) {
        this.code = code;
        this.feePerKg = feePerKg;
    }

    public String code() {
        return code;
    }

    public int fee(int kg) {
        return kg * feePerKg;
    }

    public static ShippingMethod fromCode(String code) {
        ShippingMethod m = BY_CODE.get(code);
        if (m == null) {
            throw new IllegalArgumentException("알 수 없는 배송 코드: " + code);
        }
        return m;
    }
}

public class R3Main {
    public static void main(String[] args) {
        String stored = ShippingMethod.EXPRESS.code();
        System.out.println(stored);

        ShippingMethod restored = ShippingMethod.fromCode(stored);
        System.out.println(restored == ShippingMethod.EXPRESS);
        System.out.println(restored.fee(3));

        try {
            ShippingMethod.fromCode("X");
        } catch (IllegalArgumentException e) {
            System.out.println(e.getMessage());
        }
    }
}

    저장할 때는 code()가 돌려준 "E"를 내보내고, 읽을 때는 fromCode("E")로 상수를 되찾는다. 되찾은 참조는 새로 만든 객체가 아니라 맵에 들어 있던 기존 인스턴스이므로 == 비교가 true다. 알 수 없는 코드에는 null을 돌려주지 않고 예외를 던졌다. valueOf()와 같은 선택이며, 잘못된 데이터가 조용히 흘러가는 대신 읽는 자리에서 드러나게 한다.

    이 코드에서 주의해서 볼 곳은 BY_CODE를 채우는 위치다. 생성자 안에서 BY_CODE.put(code, this)를 호출하면 static 블록이 필요 없어 더 짧아 보인다. 그렇게 고쳐서 컴파일하면 다음 오류가 난다.

    error: illegal reference to static field from initializer
        BY_CODE.put(code, this);
        ^

    JLS 8.9.2는 enum의 생성자, 인스턴스 초기화 블록, 인스턴스 변수 초기화식에서 그 enum의 static 필드를 참조하는 것을 컴파일 오류로 정한다. 상수 변수만 예외다. 이유는 초기화 순서에 있다. 앞에서 본 것처럼 상수에 해당하는 static 필드는 직접 선언한 static 필드보다 앞에 선언된 것으로 취급되고, 클래스 초기화는 static 필드의 초기화식과 static 블록을 소스에 적힌 순서대로 실행한다. 따라서 세 상수의 생성자가 실행되는 시점에 BY_CODE는 아직 초기화되지 않은 null이다. 이 규칙이 없었다면 클래스 초기화 도중 NullPointerException이 났을 것이고, 명세는 그 실수를 컴파일 단계에서 막는다.

    맵을 쓰지 않고 fromCode 안에서 values()를 순회하며 코드가 같은 상수를 찾아도 결과는 같다. 다만 그렇게 하면 호출할 때마다 배열을 하나 복제하고 처음부터 차례로 비교한다. 맵은 클래스 초기화 때 한 번 채워 두고 그 뒤로는 조회만 한다. 표준 라이브러리도 같은 방식을 쓴다. OpenJDK 21의 Enum.valueOf(Class, String)은 Class 객체가 한 번 만들어 보관하는 "이름 → 상수" 맵에서 상수를 찾는다. BY_CODE가 동기화 없는 HashMap이어도 되는 까닭은 클래스 초기화를 수행하는 한 스레드만 이 맵에 값을 넣고, 초기화가 끝난 뒤에는 누구도 수정하지 않기 때문이다.

    이제 SAME_DAY("T", 1000)을 STANDARD와 EXPRESS 사이에 넣어도 저장되어 있던 "E"는 여전히 EXPRESS로 읽힌다. 상수 이름을 FAST로 바꿔도 코드가 "E"인 한 기존 데이터는 그대로 읽힌다. 대신 지켜야 할 약속이 코드 쪽으로 옮겨 온다. 한 번 밖으로 나간 코드는 바꾸지 않고, 다른 상수에 다시 쓰지 않는다. 두 상수에 같은 코드를 실수로 적어도 컴파일러는 알려 주지 않으며, HashMap.put은 같은 키가 이미 있으면 값을 덮어쓴다. put이 돌려주는 이전 값이 null이 아닐 때 예외를 던지도록 static 블록을 고치면 그 실수를 클래스 초기화 시점에 잡을 수 있다.

    switch와 enum: 빠뜨린 상수를 누가 알려 주는가

    상수에 따라 달라지는 로직을 전부 enum 안에 넣을 수는 없다. 화면에 보여 줄 문구나 다른 모듈의 정책처럼 enum이 알 필요가 없는 일은 바깥에서 상수에 따라 분기해야 하고, 그때 쓰는 것이 switch다. 손으로 만든 패턴의 인스턴스는 case에 쓸 수 없었지만 enum 상수는 쓸 수 있다. JLS 14.11.1은 case 상수가 상수식이거나 enum 상수의 이름이어야 한다고 규정한다. switch에는 문(statement)과 식(expression) 두 형태가 있고, 상수를 빠뜨렸을 때의 동작이 서로 다르다. 필드 없는 처음의 ShippingMethod로 실험한다.

    public class SwitchMain {
    static String byStatement(ShippingMethod m) {
        String label = "?";
        switch (m) {
            case STANDARD:
                label = "일반";
                break;
            case EXPRESS:
                label = "빠른";
                break;
        }
        return label;
    }

    static String byExpression(ShippingMethod m) {
        return switch (m) {
            case STANDARD -> "일반";
            case EXPRESS -> "빠른";
            case DAWN -> "새벽";
        };
    }

    public static void main(String[] args) {
        for (ShippingMethod m : ShippingMethod.values()) {
            System.out.println(m + " 문: " + byStatement(m));
        }
        for (ShippingMethod m : ShippingMethod.values()) {
            System.out.println(m + " 식: " + byExpression(m));
        }
    }
}

EXPRESS 문: 빠른

    byStatement에는 DAWN의 case가 없는데도 컴파일된다. 일치하는 라벨이 없으면 switch 문은 아무 일도 하지 않고 끝나므로 label은 초기값 "?" 그대로다. JLS 14.11.2는 그 이유를 호환성이라고 밝힌다. 선택자가 enum 타입이고 패턴이나 null 라벨을 쓰지 않는 예전 형태의 switch 문은 모든 경우를 다루지 않아도 된다. enum이 도입된 뒤로 작성된 기존 코드가 이 형태이기 때문이다.

    switch 식은 다르다. 식은 반드시 값을 내야 하므로 JLS 15.28.1은 모든 경우를 빠짐없이 다루지 않는(not exhaustive) switch 식을 컴파일 오류로 정한다. 선택자가 enum이면 모든 상수의 이름이 case에 나올 때 default 없이도 조건을 충족한다(JLS 14.11.1.1). byExpression에서 DAWN 줄을 지우고 컴파일하면 다음 오류가 난다.

    error: the switch expression does not cover all possible input values
        return switch (m) {
               ^

    이 오류가 리팩토링 1에서 아쉬웠던, 빠뜨린 곳을 컴파일러가 찾아 주는 장치다. 상수를 추가하면 그 상수를 다루지 않는 switch 식이 전부 컴파일 오류가 되어 고칠 곳의 목록이 만들어진다. 이 장치는 default를 넣는 순간 꺼진다. default가 있으면 새 상수는 오류 없이 그쪽으로 흘러간다. 모든 상수를 각각 다뤄야 하는 분기라면 default 없는 switch 식으로 쓰는 편이 안전하다.

    선택자가 null일 때는 두 형태가 같다. null을 받는 라벨이 없으면 NullPointerException이 발생한다. Java 21부터는 case null 라벨을 써서 null을 분기의 한 경우로 다룰 수 있다.

    javac가 enum switch를 번역하는 방법

JLS 13.4.26이 상수의 추가와 재배열을 기존 바이너리와 호환되는 변경으로 규정할 수 있는 근거가 여기에 있다. 둘째, switch 문은 모르는 상수 SAME_DAY를 만나도 아무 일도 하지 않는다. 셋째, switch 식은 MatchException을 던진다. JLS 15.28.2는 일치하는 라벨이 없고 선택자가 null도 아니면 이 예외를 던진다고 규정하고, 13.4.26도 상수 추가가 빠짐없는 switch의 실행을 실패하게 만들 수 있다고 경고한다. MatchException은 Java 21 기준이며, Java 17의 명세는 같은 상황에서 IncompatibleClassChangeError를 던진다고 적고 있다.

    언어와 라이브러리가 enum에만 해 주는 것

    인스턴스가 늘어나지 않는다는 보장

    타입 안전 열거형 패턴 절에서 손으로 만든 클래스는 "인스턴스는 셋뿐"이라는 전제를 언어가 보장해 주지 않는다고 했다. 실험으로 확인한다. 손으로 만든 클래스를 ManualMethod라는 이름으로 다시 쓰고, 직렬화 실험을 위해 Serializable을 구현하게 한다. 비교 대상인 enum은 필드 없는 처음의 ShippingMethod다.

    import java.io.ByteArrayInputStream;
import java.io.ByteArrayOutputStream;
import java.io.ObjectInputStream;
import java.io.ObjectOutputStream;
import java.io.Serializable;
import java.lang.reflect.Constructor;

class ManualMethod implements Serializable {
    public static final ManualMethod STANDARD = new ManualMethod();
    public static final ManualMethod EXPRESS = new ManualMethod();
    public static final ManualMethod DAWN = new ManualMethod();

    private ManualMethod() {
    }
}

public class BreakMain {
    public static void main(String[] args) throws Exception {
        // 1. 리플렉션으로 private 생성자 호출
        Constructor c = ManualMethod.class.getDeclaredConstructor();
        c.setAccessible(true);
        ManualMethod fourth = c.newInstance();
        System.out.println(fourth == ManualMethod.STANDARD
                || fourth == ManualMethod.EXPRESS
                || fourth == ManualMethod.DAWN);

        // 2. 직렬화했다가 역직렬화
        ManualMethod copy = (ManualMethod) roundTrip(ManualMethod.EXPRESS);
        System.out.println(copy == ManualMethod.EXPRESS);

        // 3. enum에 같은 일을 시도
        ShippingMethod e = (ShippingMethod) roundTrip(ShippingMethod.EXPRESS);
        System.out.println(e == ShippingMethod.EXPRESS);

        Constructor ec =
                ShippingMethod.class.getDeclaredConstructor(String.class, int.class);
        ec.setAccessible(true);
        try {
            ec.newInstance("SAME_DAY", 3);
        } catch (IllegalArgumentException ex) {
            System.out.println(ex.getMessage());
        }
    }

    static Object roundTrip(Object o) throws Exception {
        ByteArrayOutputStream bytes = new ByteArrayOutputStream();
        try (ObjectOutputStream out = new ObjectOutputStream(bytes)) {
            out.writeObject(o);
        }
        try (ObjectInputStream in =
                     new ObjectInputStream(new ByteArrayInputStream(bytes.toByteArray()))) {
            return in.readObject();
        }
    }
}

    첫 줄의 false는 리플렉션으로 만든 fourth가 세 상수 중 어느 것도 아니라는 뜻이다. 리플렉션(reflection)은 실행 중에 Class 객체에서 생성자나 메서드를 찾아 호출하는 기능이고, setAccessible(true)로 private 접근 검사를 끌 수 있다. 네 번째 인스턴스가 만들어졌으므로, ==로 세 상수와 비교하는 분기는 이 값을 어느 쪽으로도 분류하지 못한다. 둘째 줄의 false는 직렬화의 결과다. 객체를 바이트로 내보냈다가 다시 읽으면 역직렬화는 ManualMethod의 생성자를 거치지 않고 새 객체를 만든다. EXPRESS를 내보냈다가 읽었는데 돌아온 것은 EXPRESS가 아닌 다섯 번째 인스턴스다.

    enum은 두 시도를 모두 막는다. 셋째 줄에서 역직렬화한 enum 상수는 원래 상수와 ==로 같다. 자바 객체 직렬화 명세 1.12절에 따르면 enum 상수의 직렬화 형태는 이름뿐이고, 역직렬화는 그 이름으로 Enum.valueOf를 호출해 이미 있는 상수를 찾아 돌려준다. 넷째 줄은 리플렉션으로 enum의 생성자를 호출했을 때의 예외 메시지다. OpenJDK 21의 Constructor.newInstance는 대상 클래스에 enum 표시가 있으면 IllegalArgumentException을 던진다.

    JLS 8.9는 이 보장을 목록으로 적어 둔다. 열거형 클래스를 new로 직접 인스턴스화하는 것은 컴파일 오류다. javac의 문구는 "enum classes may not be instantiated"다. 그 밖에 세 가지 장치가 상수 이외의 인스턴스가 생기지 않게 한다. Enum의 clone이 final이어서 복제할 수 없고, 리플렉션을 통한 인스턴스 생성이 금지되며, 직렬화가 특별하게 처리된다. == 비교가 언제나 옳다는 성질이 관례가 아니라 언어와 표준 라이브러리의 규칙에서 나온다는 점이 손으로 만든 패턴과 가장 크게 다른 부분이다.

    EnumSet과 EnumMap: ordinal이 쓰이는 자리

    상수의 수가 고정되어 있고 각 상수가 0부터 시작하는 고유한 번호를 갖는다는 사실은 자료 구조를 단순하게 만든다. java.util에는 이 성질을 이용하는 enum 전용 컬렉션 두 개가 있다.

    import java.util.EnumMap;
import java.util.EnumSet;

public class EnumCollectionsMain {
    public static void main(String[] args) {
        EnumSet fast = EnumSet.of(ShippingMethod.DAWN, ShippingMethod.EXPRESS);
        System.out.println(fast);
        System.out.println(fast.contains(ShippingMethod.STANDARD));
        System.out.println(EnumSet.complementOf(fast));

        EnumMap count = new EnumMap<>(ShippingMethod.class);
        count.put(ShippingMethod.DAWN, 2);
        count.put(ShippingMethod.STANDARD, 5);
        System.out.println(count);
    }
}

    EnumSet의 API 문서는 내부 표현이 비트 벡터라고 밝힌다. OpenJDK 21의 구현에서는 상수가 64개 이하인 열거형이면 long 값 하나가 집합 전체이고, 상수를 넣는 연산은 1L << ordinal에 해당하는 비트를 켜는 것이다. EnumSet.of(DAWN, EXPRESS)는 2번과 1번 비트가 켜진 long 하나가 되고, contains는 비트 하나를 검사한다. 첫 줄의 출력이 넣은 순서가 아니라 [EXPRESS, DAWN]인 것도 이 때문이다. 순회 순서가 선언 순서라는 것은 API 문서가 보장한다. EnumMap도 비슷하다. OpenJDK 21의 구현은 값을 배열에 두고 키의 ordinal을 인덱스로 쓴다. 해시를 계산할 일도 충돌을 처리할 일도 없다.

    앞에서 ordinal에 의존하지 말라고 한 것과 모순되지 않는다. 이 컬렉션들은 실행 중인 JVM 안에서만 ordinal을 쓰고, 그 동안에는 선언 순서가 바뀔 일이 없다. 열거형을 원소로 하는 집합이나 열거형을 키로 하는 맵이 필요하면 HashSet, HashMap보다 이 둘을 먼저 고려한다.

    흔한 오해와 함정

    "enum은 정수에 이름을 붙인 것이다"

    정수 상수를 대신해 쓰이기 때문에 생기는 오해다. 자바의 enum 상수는 정수가 아니라 객체를 가리키는 참조다. int로 자동 변환되지 않고 산술 연산의 피연산자가 될 수 없으며, 지금까지 본 대로 필드와 메서드를 갖고 다형적으로 동작한다. 정수가 필요한 곳에 ordinal()을 꺼내 쓰기 시작하면 정수 상수의 문제를 그대로 다시 들여오게 된다.

    "enum 상수도 상수니까 사용하는 쪽에 값이 복사된다"

    정수·문자열 상수가 사용하는 쪽의 클래스 파일에 복사되는 것은 그것들이 상수 변수이기 때문이고, 상수 변수가 될 수 있는 것은 기본형과 String뿐이다. enum 상수를 읽는 코드는 실행할 때 필드를 읽는 명령으로 번역된다. return ShippingMethod.EXPRESS; 한 줄의 바이트코드다.

    0: getstatic     #7                  // Field ShippingMethod.EXPRESS:LShippingMethod;
3: areturn

    그래서 열거형만 다시 컴파일해도 사용하는 쪽은 새 클래스의 인스턴스를 본다. 반대로 상수를 삭제하면 그 필드를 읽는 기존 클래스는 실행 중에 실패한다. DAWN을 지우고 열거형만 다시 컴파일한 뒤 ShippingMethod.DAWN을 읽는 기존 클래스를 실행하면 JDK 21에서 java.lang.NoSuchFieldError: Class ShippingMethod does not have member field 'ShippingMethod DAWN'이 발생한다. JLS 13.4.26은 널리 배포된 열거형에서 상수를 삭제하는 변경을 권장하지 않는다고 적는다.

    "객체 비교이므로 equals를 써야 한다"

    enum에서는 ==가 더 나은 선택이고 이유는 세 가지다. 우선 의미가 같다. Enum.equals는 final이고 구현이 this == other다. 다음으로 null에 안전하다. 변수 m이 null일 때 m == ShippingMethod.EXPRESS는 false지만 m.equals(ShippingMethod.EXPRESS)는 NullPointerException을 던진다. 마지막으로 컴파일러가 타입을 검사한다. 서로 다른 열거형의 상수를 비교한 ShippingMethod.EXPRESS == Level.HIGH는 "incomparable types: ShippingMethod and Level" 오류로 거부된다. equals는 매개변수가 Object라서 같은 비교가 컴파일되고 언제나 false를 돌려준다.

    "toString()과 name()은 같은 값이다"

    재정의하지 않았을 때만 같다. toString()이 소문자 이름을 돌려주도록 재정의한 열거형 Size가 있다고 하자. Size.SMALL.toString()은 "small"이고, 이 문자열을 Size.valueOf()에 넘기면 "No enum constant Size.small" 예외가 난다. valueOf()는 toString()이 아니라 선언된 이름을 기준으로 찾기 때문이다. 저장하거나 다시 상수로 되돌릴 문자열은 name()이나 전용 코드에서 얻고, toString()은 사람에게 보여 주는 용도로만 쓴다.

    다른 주제와의 연결

    표준 라이브러리가 enum을 쓰는 방식에 이 회차의 내용이 그대로 들어 있다. 다음 회차에서 다룰 java.time의 DayOfWeek와 Month는 열거형이다. DayOfWeek의 API 문서는 요일의 숫자 표현을 얻으려고 ordinal()을 쓰지 말고 getValue()를 쓰라고 명시한다. MONDAY.ordinal()은 0이고 MONDAY.getValue()는 1이다. 동시성에서 만나게 될 Thread.State와 TimeUnit도 열거형이다. TimeUnit.SECONDS.toMillis(3)이 3000을 돌려주는 것처럼 TimeUnit의 상수는 자기 단위에 맞는 변환 로직을 갖고 있으며, 이는 리팩토링 2의 구조와 같다.

    JPA에서는 ordinal 문제가 데이터베이스에서 그대로 재현된다. 엔티티의 열거형 필드를 컬럼에 저장하는 방식은 @Enumerated로 정하는데, Jakarta Persistence API 문서에 따르면 방식을 지정하지 않거나 이 애너테이션을 쓰지 않으면 EnumType.ORDINAL로 간주한다. 기본값이 이 회차에서 피하라고 한 방식이다. 이름을 저장하는 EnumType.STRING을 명시하거나 리팩토링 3의 코드를 저장하도록 변환기를 두는 선택은 JPA를 다루는 권에서 이어진다.

    이 권 안에서는 상수별 본문이 08회의 익명 클래스로, valueOf()가 던지는 예외가 09·10회의 예외 처리로 이어진다. 클래스 초기화가 한 번만 일어나고 그 과정이 스레드에 안전하다는 성질은 인스턴스가 하나뿐이어야 하는 객체를 만들 때에도 쓰인다. 상수가 하나뿐인 enum은 인스턴스가 하나라는 것을 언어가 보장하는 클래스다.

    이 장의 핵심

    enum은 값의 집합을 닫은 클래스다. 상수는 클래스 초기화 때 한 번 만들어진 인스턴스를 가리키는 public static final 필드이고, 언어와 표준 라이브러리가 그 밖의 인스턴스가 생기지 않도록 막는다. 그래서 컴파일러는 잘못된 값을 거부하고 빠뜨린 분기를 찾아 줄 수 있으며, == 비교는 언제나 옳다. 상수의 순서 번호인 ordinal은 실행 중의 내부 구현에만 쓰고, 프로그램 밖으로 나가는 값에는 이름이나 전용 코드를 쓴다.
    타입 안전성
    컴파일러가 선언된 타입만으로 잘못된 값의 사용을 막아 주는 성질이다. String이나 int 매개변수는 허용하는 값의 집합이 넓어서, 정해진 몇 가지 종류를 표현할 때 이 성질을 주지 못한다.
    타입 안전 열거형 패턴
    private 생성자와 public static final 인스턴스로 인스턴스 수를 고정한 클래스다. 값의 집합을 닫아 주지만 리플렉션과 직렬화로 인스턴스가 늘 수 있고, 이름 출력이나 전체 목록 같은 기능을 직접 써야 한다.
    열거형 클래스
    enum 선언이 만드는 클래스다. java.lang.Enum을 상속하고, 상수마다 public static final 필드와 인스턴스가 하나씩 있으며, values()와 valueOf(String)이 암묵적으로 선언된다(JLS 8.9).
    name과 ordinal
    컴파일러가 생성자에 넘겨 주는 상수의 이름과 선언 순서다. name()은 final이라 선언한 식별자 그대로이고, ordinal()은 선언이 바뀌면 달라지므로 프로그램 밖에 저장하지 않는다.
    values()와 valueOf()
    values()는 호출할 때마다 내부 배열을 복제해 돌려준다. valueOf()는 이름이 정확히 일치하는 상수를 돌려주고, 없으면 IllegalArgumentException을 던진다.
    필드, 메서드, 상수별 본문
    상수마다 다른 데이터는 final 필드로, 공통 로직은 메서드로, 특정 상수만의 동작은 상수별 클래스 본문으로 둔다. 본문은 익명 하위 클래스가 되고 그 열거형 클래스는 암묵적으로 sealed가 된다.
    switch의 빠짐없음 검사
    switch 식은 모든 상수를 다루지 않으면 컴파일 오류다. enum에 대한 예전 형태의 switch 문은 이 검사를 하지 않고, 일치하는 case가 없으면 아무것도 실행하지 않는다.
    $SwitchMap 변환표
    JDK 21의 javac는 enum switch를, 실행 시점에 ordinal()을 호출해 채우는 int 배열을 거쳐 분기하도록 번역한다. ordinal이 클래스 파일에 고정되지 않으므로 상수의 추가와 재배열이 기존 바이너리를 깨지 않는다.
    인스턴스 통제
    new는 컴파일 오류, clone은 final, 리플렉션 생성은 예외, 역직렬화는 이름으로 기존 상수를 찾는다. 이 규칙들 때문에 enum 상수의 == 비교는 언제나 옳다.

    실무에서 enum을 쓸지 정하는 첫 기준은 "값이 추가될 때 코드도 함께 바뀌어야 하는가"다. 주문 상태나 결제 수단의 종류처럼 값에 따라 프로그램의 동작이 갈리는 닫힌 집합은 enum이 맞다. 상품 카테고리나 지점 목록처럼 운영자가 배포 없이 추가하고 지워야 하는 목록은 코드가 아니라 데이터이므로 테이블에 둔다. enum의 필드에 넣은 값은 다시 컴파일하고 배포해야 바뀐다는 점을 기준으로 삼으면 판단이 쉬워진다.

    enum이 프로세스 밖으로 나가는 경계에서는 표현을 명시적으로 정한다. 데이터베이스, JSON, 메시지에 실리는 순간 enum은 문자열이나 숫자가 되고, 그 값은 코드보다 오래 산다. ordinal은 쓰지 않는다. name()은 간편하지만 식별자 이름을 바꾸는 리팩토링이 곧 데이터 마이그레이션이 된다. 전용 코드는 그 결합을 끊어 주는 대신 중복 검사와 조회 메서드를 유지해야 한다. 서로 다른 버전이 동시에 떠 있는 배포에서는 순서도 따져야 한다. 새 상수를 내보내는 쪽이 먼저 배포되면 아직 그 상수를 모르는 쪽의 valueOf()가 예외를 던진다. 읽는 쪽을 먼저 배포하거나, 모르는 값을 만났을 때의 정책을 미리 정해 둔다.

    분기에서는 컴파일러의 검사를 살릴지 여부가 판단 대상이다. 같은 코드베이스에서 함께 컴파일되는 enum이라면 default 없는 switch 식으로 써서 상수가 추가될 때 고칠 곳을 컴파일 오류로 받는다. 따로 배포되는 라이브러리의 enum이라면 사정이 다르다. 내 코드가 컴파일된 뒤에 상수가 늘 수 있고, 그때 default 없는 switch 식은 MatchException으로 실패한다. 이런 경우에는 모르는 값에 대한 동작을 default에 직접 정해 두는 편이 낫다. 공개한 enum에서 상수를 지우는 변경은 사용하는 쪽에서 NoSuchFieldError가 되므로 피한다.

    로직을 enum에 넣는 범위에도 한계가 있다. 상수 자체의 성질에서 나오는 계산은 enum이 갖는 것이 좋다. 그러나 데이터베이스 조회나 외부 호출이 필요한 로직은 넣기 어렵다. enum의 인스턴스는 클래스 초기화 때 컴파일러가 만든 코드로 생성되므로, 실행 중에 만들어지는 객체를 생성자 인자로 넘겨줄 방법이 없다. 그런 로직은 enum을 인자로 받는 별도의 객체에 둔다.

Map이 불변 객체가 아니기 때문이다. 상수에 해당하는 static 필드가 직접 선언한 static 필드보다 먼저 초기화되므로, 생성자가 실행되는 시점에는 그 Map 필드가 아직 초기화되지 않았기 때문이다. JLS 8.9.3에 따라 상수 필드는 다른 static 필드보다 앞에 선언된 것으로 취급되고, 클래스 초기화는 소스 순서대로 진행된다. 생성자가 실행될 때 그 맵은 null이다. JLS 8.9.2는 이 실수를 컴파일 오류로 막고, 값이 클래스 파일에 박히는 상수 변수만 예외로 둔다. 접근 권한이나 불변 여부와는 관계가 없다. 열거형 값을 데이터베이스에 저장할 때 ordinal()을 쓰지 말아야 하는 이유로 가장 정확한 것은? ordinal은 프로그램을 실행할 때마다 다른 값이 나오기 때문이다. ordinal은 선언 순서일 뿐이어서, 상수를 중간에 추가하거나 순서를 바꾸면 저장된 숫자가 예외 없이 다른 상수로 읽히기 때문이다. 정수 컬럼이 문자열 컬럼보다 저장 공간을 더 많이 차지하기 때문이다. ordinal()이 호출될 때마다 배열을 복제해서 느리기 때문이다. ordinal은 같은 선언에 대해서는 항상 같은 값이지만 선언이 바뀌면 달라진다. 저장된 숫자는 바뀐 선언에서도 유효한 인덱스이므로 오류 없이 다른 상수로 해석된다. 배열을 복제하는 것은 ordinal()이 아니라 values()이고, 저장 공간은 이 판단의 근거가 아니다.
    타입 안전성(type safety)
    컴파일러가 타입 정보만으로 잘못된 값의 사용을 막아 주는 성질.
    타입 안전 열거형 패턴(typesafe enum pattern)
    private 생성자와 public static final 인스턴스로 값의 집합을 고정한 클래스를 손으로 작성하는 방법.
    열거형 클래스(enum class)
    enum 선언으로 만들어지는 클래스. JLS 8.9의 표현으로는 이름 붙은 인스턴스의 작은 집합을 정의하는 제한된 종류의 클래스다.
    열거 상수(enum constant)
    열거형 클래스의 본문에 나열한 이름. 같은 이름의 public static final 필드와 그 필드가 가리키는 인스턴스 하나에 대응한다.
    상수 변수(constant variable)
    상수식으로 초기화된 기본형 또는 String 타입의 final 변수. 값이 사용하는 쪽의 클래스 파일에 복사된다. enum 상수는 여기에 해당하지 않는다.
    ordinal
    열거 상수가 선언에서 몇 번째인지를 0부터 센 정수. EnumSet, EnumMap 같은 자료 구조의 내부 구현을 위한 값이다.
    상수별 클래스 본문(constant-specific class body)
    열거 상수 뒤에 붙이는 중괄호 본문. 그 열거형 클래스의 익명 하위 클래스를 선언하며, 상수 하나에만 적용되는 메서드 재정의를 담는다.
    빠짐없는 switch(exhaustive switch)
    선택자가 가질 수 있는 모든 값을 라벨이 다루는 switch. switch 식은 반드시 이 조건을 만족해야 한다.
    MatchException
    빠짐없는 switch가 실행 중에 일치하는 라벨을 찾지 못했을 때 던져지는 예외. Java 21 기준이며, enum에서는 컴파일 뒤에 상수가 추가된 경우에 발생한다.
    EnumSet · EnumMap
    열거형 전용 집합과 맵. 상수의 ordinal을 비트 위치나 배열 인덱스로 써서 구현된다.
