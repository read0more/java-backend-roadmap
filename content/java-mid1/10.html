    실패를 무시하는 프로그램에서 출발한다

    앞 회차에서는 예외가 Throwable 아래에 어떤 계층으로 놓이는지, 컴파일러가 체크 예외와 언체크 예외를 어떻게 다르게 다루는지를 규칙으로 정리했다. 이번 회차는 그 규칙을 작은 프로그램 하나에 적용한다. 오류 처리가 전혀 없는 코드에서 시작해 한 단계씩 고치면서, 단계마다 어떤 문제가 풀리고 어떤 문제가 새로 드러나는지를 실행 결과로 확인한다.

    프로그램이 하는 일은 원격 저장소에 파일 하나를 백업하는 것이다. 저장소와 세션을 열고, 파일을 올리고, 세션을 닫는다. 진짜 네트워크를 쓰면 실행 결과가 환경에 따라 달라지므로 통신은 출력문으로 대신하고, 실패는 입력값으로 일으킨다. 호스트 이름이 down으로 시작하면 세션 열기가 실패하고, 파일 이름이 .iso로 끝나면 용량 제한에 걸려 올리기가 실패한다.

    class StorageSession {
    private final String host;
    StorageSession(String host) { this.host = host; }

    String open() {
        if (host.startsWith("down")) return "OPEN_FAIL";
        System.out.println(host + " 세션 열림");
        return "OK";
    }
    String put(String name) {
        if (name.endsWith(".iso")) return "TOO_LARGE";
        System.out.println(host + " <- " + name);
        return "OK";
    }
    void close() { System.out.println(host + " 세션 닫힘"); }
}

class BackupJob {
    void run(String host, String name) {
        StorageSession s = new StorageSession(host);
        s.open();
        s.put(name);
        s.close();
    }
}

public class Main {
    public static void main(String[] args) {
        BackupJob job = new BackupJob();
        job.run("backup1", "a.txt");
        System.out.println("--");
        job.run("down1", "a.txt");
        System.out.println("--");
        job.run("backup1", "disk.iso");
    }
}

    StorageSession은 실패를 문자열 반환값으로 알린다. 그런데 BackupJob.run은 그 값을 받지 않는다. 메서드 호출을 문장으로 쓰면 반환값은 그냥 버려지고, 컴파일러는 아무 경고도 하지 않는다. 그 결과가 위 출력이다. 두 번째 요청은 세션이 열리지 않았는데도 파일을 올렸다고 출력하고, 열린 적 없는 세션을 닫는다. 세 번째 요청은 파일이 올라가지 않았는데 아무 말 없이 끝난다. 프로그램은 세 번 모두 정상 종료했고, 백업 두 건이 실패했다는 사실은 어디에도 남지 않았다.

    오류 처리를 다루는 이유가 여기에 있다. 실패 자체는 막을 수 없다. 저장소 서버는 내려갈 수 있고 디스크는 찰 수 있다. 프로그램이 할 수 있는 일은 실패를 실패로 알아차리고, 이어지는 작업을 멈추고, 누군가 알 수 있게 남기는 것이다.

    반환값으로 오류를 알릴 때의 한계

    반환값을 꼬박꼬박 검사하도록 run을 고쳐 보자. 열기가 실패하면 올리기를 건너뛰고, 올리기가 실패해도 열어 둔 세션은 닫는다.

    class BackupJob {
    void run(String host, String name) {
        StorageSession s = new StorageSession(host);
        String r = s.open();
        if (!r.equals("OK")) {
            System.out.println("[오류] " + r);
        } else {
            r = s.put(name);
            if (!r.equals("OK")) {
                System.out.println("[오류] " + r);
            }
            s.close();
        }
    }
}

    동작은 맞다. 하지만 이 방식에는 구조에서 오는 약점이 여러 개 있다.

    • 정상 흐름이 오류 처리에 묻힌다. 하려는 일은 열기, 올리기, 닫기 세 줄인데 그 사이사이에 검사와 분기가 끼어들었다. 단계가 다섯 개, 열 개로 늘면 들여쓰기가 깊어지고, 코드를 읽는 사람은 "이 메서드가 원래 하려던 일"을 조건문 틈에서 골라내야 한다.
    • 검사를 빠뜨려도 컴파일된다. 첫 번째 버전이 그 증거다. 반환값을 확인할지 말지는 전적으로 호출하는 쪽의 성실함에 달려 있다.
    • 반환 통로를 오류 코드가 차지한다. 메서드가 원래 돌려줘야 할 값이 있으면 곤란해진다. 예를 들어 올린 바이트 수를 int로 돌려주는 메서드가 실패를 -1로 알리기로 하면, 호출자는 정상 값과 오류 값을 같은 변수에서 구분해야 한다. 값의 범위 전체가 정상 결과인 경우에는 이 방법을 아예 쓸 수 없다. Integer.parseInt가 실패를 반환값이 아니라 NumberFormatException으로 알리는 것도 그래서다. -1도 0도 올바른 변환 결과이기 때문에 실패 표시로 쓸 숫자가 남아 있지 않다.
    • 여러 계층을 건너려면 중간 계층이 모두 중계해야 한다. 오류를 처리할 수 있는 곳이 세 단계 위의 메서드라면, 그 사이의 메서드들은 자기와 상관없는 오류 코드를 받아서 그대로 다시 반환하는 코드를 써야 한다.
    • 담을 수 있는 정보가 적다. 문자열 하나로는 어느 호스트에서, 어떤 파일을 다루다가, 어느 줄에서 실패했는지를 함께 전하기 어렵다.

    예외는 이 다섯 가지를 한꺼번에 겨냥한 장치다. 반환값과 별개의 통로로 실패를 전하고, 처리하지 않으면 호출 스택을 따라 저절로 올라가며, 객체이므로 필요한 정보를 필드로 담는다.

    예외로 바꾸기: 복구, 그리고 흐름의 분리

    실패를 반환값 대신 예외로 알리도록 바꾼다. 오류 코드와 메시지를 담는 예외 클래스를 하나 만들고, 우선 Exception을 상속해 체크 예외로 둔다.

    class StorageException extends Exception {
    private final String code;
    StorageException(String code, String message) {
        super(message);
        this.code = code;
    }
    String getCode() { return code; }
}

class StorageSession {
    private final String host;
    StorageSession(String host) { this.host = host; }

    void open() throws StorageException {
        if (host.startsWith("down")) {
            throw new StorageException("OPEN_FAIL", host + " 연결 불가");
        }
        System.out.println(host + " 세션 열림");
    }
    void put(String name) throws StorageException {
        if (name.endsWith(".iso")) {
            throw new StorageException("TOO_LARGE", name + " 용량 제한 초과");
        }
        System.out.println(host + " <- " + name);
    }
    void close() { System.out.println(host + " 세션 닫힘"); }
}

    open과 put의 반환 타입이 void로 돌아왔다. 성공하면 그냥 끝나고, 실패하면 throw로 빠져나간다. 호출하는 쪽에서 아무것도 잡지 않고 run과 main에 throws StorageException만 붙이면 어떻게 될까.

    class BackupJob {
    void run(String host, String name) throws StorageException {
        StorageSession s = new StorageSession(host);
        s.open();
        s.put(name);
        s.close();
    }
}

    여기서 필요한 것이 복구(recovery)다. 예외를 catch로 잡아 처리하면, 갑작스럽게 끝나던 흐름이 다시 정상 흐름으로 돌아온다. JLS 14.20.1의 규칙으로 말하면, try 블록이 예외로 끝났더라도 그 예외를 받은 catch 블록이 정상적으로 끝나면 try 문 전체가 정상 완료한 것이 된다. 그래서 try 문 다음 문장이 이어서 실행된다.

    class BackupJob {
    void run(String host, String name) {
        StorageSession s = new StorageSession(host);
        try {
            s.open();
            s.put(name);
            s.close();
        } catch (StorageException e) {
            System.out.println("[오류] " + e.getCode() + ": " + e.getMessage());
        }
    }
}

    세 요청이 모두 처리됐다. 코드의 모양도 달라졌다. try 블록 안에는 열기, 올리기, 닫기 세 줄이 조건문 없이 이어져 있다. 이것이 정상 흐름이다. 실패했을 때 할 일은 catch 블록에 따로 모였다. 이것이 예외 흐름이다. 두 번째 요청을 추적하면, s.open()이 예외를 던지는 순간 try 블록의 나머지 두 줄은 건너뛰고 제어가 곧바로 catch로 넘어간다. "열기가 실패하면 올리기를 하지 않는다"는 규칙을 조건문으로 쓰지 않았는데도 지켜진다.

    한 층 아래: 분기가 사라지고 표가 생긴다

    "흐름의 분리"는 소스 코드의 겉모습만 가리키는 말이 아니다. 바이트코드에서도 실제로 분리된다. 반환값을 검사하는 메서드와 예외를 잡는 메서드를 뼈대만 남겨 컴파일하고 javap -c로 열어 보면 차이가 드러난다. 왼쪽은 open()과 put()이 boolean을 돌려주고 호출자가 if로 검사하는 버전, 오른쪽은 두 메서드가 예외를 던지고 호출자가 try-catch로 감싼 버전이다.

    반환값 버전은 호출 하나마다 ifne 분기가 따라붙는다. 실패하든 성공하든 매번 검사 명령이 실행된다. 예외 버전의 0번과 3번 줄에는 호출 두 개만 연달아 있고 검사 명령이 없다. JVMS 3.12는 이를 두고 try 블록은 try가 없을 때와 똑같이 컴파일된다고 설명한다. catch가 만들어 낸 것은 메서드 코드 바깥에 붙은 예외 테이블(exception table)의 한 줄이다. 그 줄은 "바이트코드 0번 이상 6번 미만 구간을 실행하다가 StorageException이 던져지면 9번으로 가라"는 뜻이다. 구간의 끝이 열린 구간이라는 점은 JVMS 4.7.3이 정한다(start_pc는 포함, end_pc는 제외).

    예외가 실제로 던져졌을 때 JVM이 하는 일은 JVMS 2.10에 적혀 있다. 먼저 현재 메서드의 예외 테이블에서, 예외가 난 명령의 위치를 포함하는 구간이면서 던져진 객체의 클래스가 그 줄의 타입과 같거나 그 하위 클래스인 줄을 찾는다. 찾으면 그 줄이 가리키는 핸들러 코드로 분기한다. 못 찾으면 현재 메서드 호출은 갑작스럽게 완료된다. 그 프레임의 피연산자 스택과 지역 변수는 버려지고, 프레임이 스택에서 제거되고, 호출한 메서드의 프레임에서 같은 예외가 다시 던져진 것으로 처리된다. 이 과정이 호출 사슬을 따라 반복된다.

    두 번째 요청에 대입해 보자. StorageSession.open 안에서 athrow 명령이 실행된다. open에는 예외 테이블이 없으므로 open의 프레임이 제거된다. 제어는 BackupJob.run의 프레임으로 돌아오는데, 정상 복귀가 아니라 "open을 호출하던 그 명령에서 예외가 난 것"으로 돌아온다. 그 위치가 테이블의 구간 안이고 타입도 맞으므로 JVM은 핸들러로 분기한다. 핸들러의 첫 명령이 astore인 것은 JVM이 잡힌 예외 객체의 참조를 피연산자 스택에 올려 둔 채로 핸들러에 들어오기 때문이다. 그 참조를 지역 변수에 저장한 것이 catch (StorageException e)의 e다.

    반환값 방식은 단계마다 분기가 끼어들어 정상 흐름과 오류 처리가 섞이고, 예외 방식은 정상 흐름이 한 줄로 이어지며 실패 시에만 별도 경로로 빠진다는 대비를 보여 준다. 흰 배경의 깔끔한 순서도 두 개를 좌우로 나란히 놓은 비교 다이어그램. 왼쪽 제목 "반환값으로 알리기". 왼쪽에는 위에서 아래로 사각형 "열기", 마름모 "성공?", 사각형 "올리기", 마름모 "성공?", 사각형 "닫기"가 번갈아 놓이고, 각 마름모에서 오른쪽으로 빨간 화살표가 나와 작은 사각형 "오류 출력"으로 간다. 파란 세로 화살표가 마름모를 지날 때마다 꺾이도록 그려 흐름이 지그재그로 보이게 한다. 오른쪽 제목 "예외로 알리기". 오른쪽에는 파란 테두리의 큰 둥근 상자 "try: 정상 흐름"이 있고 그 안에 사각형 세 개 "열기", "올리기", "닫기"가 곧은 파란 세로 화살표 하나로 연결된다. 그 오른쪽에 빨간 테두리의 둥근 상자 "catch: 예외 흐름"이 있고 안에 사각형 "오류 출력". "열기"와 "올리기" 사각형의 오른쪽 변에서 각각 빨간 점선 화살표가 나와 "catch: 예외 흐름" 상자로 들어간다. 점선 화살표 옆에 라벨 "throw". 두 순서도 사이에 세로 점선. 색은 파랑(정상)과 빨강(예외) 두 가지만 쓴다. 예외를 쓰면 정상 흐름에서 검사와 분기가 빠지고, 실패했을 때의 경로가 따로 생긴다.

    리소스 반환 문제

    방금 출력에서 세 번째 요청을 다시 보자. "세션 열림"은 있는데 "세션 닫힘"이 없다. put이 예외를 던지면서 같은 try 블록의 다음 줄인 s.close()를 건너뛰었기 때문이다. 반환값 버전에서는 조건문 덕에 닫혔던 세션이, 예외로 바꾸자 열린 채로 남았다. 정상 흐름과 예외 흐름을 분리한 대가로 "어느 흐름으로 가든 반드시 해야 하는 일"을 둘 곳이 사라진 것이다.

    닫지 않은 세션이 왜 문제인지는 자원(resource)이 무엇인지에서 나온다. 자바 객체는 힙에 있고 GC가 회수한다. 하지만 파일, 소켓, 데이터베이스 커넥션은 JVM 바깥에 실체가 있다. 유닉스 계열 운영체제에서 프로세스가 파일이나 소켓을 열면 커널은 그 프로세스의 파일 디스크립터(file descriptor) 테이블에 항목을 하나 만들고 그 번호를 돌려준다. OpenJDK 21의 FileInputStream은 FileDescriptor 객체를 필드로 가지고 있고, 그 안의 int fd 필드에 이 번호가 들어 있다. 힙에 있는 것은 번호를 든 작은 객체뿐이고, 열린 파일의 상태는 커널이 가지고 있다.

    이 테이블의 칸 수에는 한도가 있다. 그리고 HotSpot의 GC는 힙이 얼마나 찼는지를 보고 움직이지, 파일 디스크립터가 얼마나 남았는지를 보고 움직이지 않는다. 그래서 힙은 넉넉한데 디스크립터가 먼저 바닥나는 일이 생긴다. 파일을 열기만 하고 닫지 않는 프로그램으로 확인할 수 있다.

    import java.io.FileInputStream;
import java.io.IOException;
import java.util.ArrayList;
import java.util.List;

public class Leak {
    public static void main(String[] args) {
        List opened = new ArrayList<>();
        try {
            while (true) {
                opened.add(new FileInputStream("Leak.java"));   // 닫지 않는다
            }
        } catch (IOException e) {
            System.out.println(opened.size() + "개를 연 뒤 실패");
            System.out.println(e);
        }
    }
}

    멀쩡히 존재하는 파일을 여는데 "파일을 찾을 수 없다"는 예외가 나오고, 괄호 안에 진짜 이유가 적혀 있다. 운영체제가 더는 열어 줄 수 없다고 거절한 것이다. 이 상태가 되면 같은 프로세스의 다른 코드도 새 파일이나 소켓을 열지 못한다. 서버라면 새 접속을 받지 못한다는 뜻이다. 자원 누수는 누수를 일으킨 코드가 아니라 엉뚱한 곳에서, 한참 뒤에 증상이 나타난다는 점에서 찾기가 어렵다.

    OpenJDK 21의 FileInputStream 생성자는 파일을 연 직후 정리 작업을 등록해 둔다(소스의 FileCleanable.register(fd)). 스트림을 닫지 않은 채 객체가 도달 불가능해지면 나중에 디스크립터를 닫아 주는 안전망이다. 하지만 이 정리는 GC가 그 객체를 도달 불가능하다고 판정한 뒤에야 실행되므로, 언제 일어날지 알 수 없다. 위 예제처럼 참조가 살아 있으면 아예 일어나지 않는다. 그리고 이것은 JDK가 자기 클래스에 넣어 둔 장치일 뿐, 우리가 만든 StorageSession이나 커넥션 풀에서 빌린 커넥션에는 해당하지 않는다. 자원은 다 쓴 시점에 코드가 직접 돌려줘야 한다.

    그럼 catch 블록에도 s.close()를 한 줄 넣으면 될까. 같은 코드가 두 군데에 생기는 것은 둘째 치고, 그래도 빠져나가는 길이 남는다. put에 파일 이름이 비어 있으면 IllegalArgumentException을 던지는 검사가 한 줄 있다고 하자. 이 예외는 StorageException이 아니므로 catch (StorageException e)에 걸리지 않고 그대로 run 밖으로 나간다. try 블록의 close()도, catch 블록의 close()도 실행되지 않는다. 필요한 것은 "어떤 이유로 블록을 떠나든 실행되는 자리"다.

    자바 객체는 힙에 있고 GC가 치우지만, 그 객체가 번호로 가리키는 파일 디스크립터 테이블의 칸은 커널에 있고 close를 호출해야 비워진다는 것을 보여 준다. 흰 배경의 메모리 구조 다이어그램. 화면을 세로 점선으로 좌우로 나눈다. 왼쪽 영역 제목 "JVM 프로세스", 오른쪽 영역 제목 "운영체제 커널". 왼쪽에 큰 둥근 상자 "힙"이 있고 그 안에 작은 상자 세 개가 세로로 놓인다. 각 상자에는 "스트림 객체"라고 적고 안에 작은 칸 "fd = 5", "fd = 6", "fd = 7"을 각각 넣는다. 맨 위 상자는 회색 점선 테두리로 그리고 옆에 라벨 "참조 없음: GC 대상". 오른쪽에는 세로로 긴 표 "파일 디스크립터 테이블"이 있고 칸 번호 "5", "6", "7"이 채워진 상태(주황색)로, 그 아래 빈 칸 몇 개(흰색)가 있다. 표 아래에 라벨 "칸 수 한도". 왼쪽의 "fd = 5", "fd = 6", "fd = 7"에서 오른쪽 표의 같은 번호 칸으로 각각 얇은 화살표. 화면 아래쪽 가운데에 두 줄 라벨: "GC는 힙만 본다", "close()를 불러야 칸이 빈다". 색은 파랑(힙)과 주황(커널 자원) 두 가지만 쓴다. 객체가 힙에서 사라지는 것과 운영체제 자원이 반납되는 것은 별개의 일이다.

    finally는 어떻게 컴파일되는가, 그리고 세 가지 함정

    "어떤 경로로 나가든 실행된다"를 JVM은 어떻게 보장할까. JVM에 finally라는 명령은 없다. 컴파일러가 finally 블록의 코드를 빠져나가는 경로마다 복사해 넣는다. try-catch-finally의 뼈대를 컴파일해서 확인한다.

    import java.io.IOException;

class FinallyShape {
    static void body() throws IOException {}
    static void recover() {}
    static void cleanup() {}

    static void run() {
        try {
            body();
        } catch (IOException e) {
            recover();
        } finally {
            cleanup();
        }
    }
}

    소스에 한 번 쓴 cleanup() 호출이 바이트코드에는 세 번 나온다. 정상 경로(3번), catch 블록 뒤(13번), 그리고 19번부터 시작하는 숨은 핸들러 안(20번)이다. 예외 테이블의 any는 타입을 가리지 않고 모든 예외를 받는다는 표시다. JVMS 4.7.3은 테이블 항목의 catch_type이 0이면 모든 예외에 대해 핸들러가 호출되고, 이것이 finally를 구현하는 데 쓰인다고 적는다. 둘째 줄은 try 본문(0~3)에서 IOException이 아닌 예외가 났을 때를, 셋째 줄은 catch 블록(9~13) 안에서 예외가 났을 때를 맡는다. 어느 쪽이든 19번으로 가서 예외를 지역 변수에 잠시 넣어 두고, cleanup()을 부르고, 넣어 둔 예외를 꺼내 athrow로 다시 던진다. 앞에서 "지나가는 예외를 세워 두고 자기 일을 한 뒤 다시 보낸다"고 한 것이 이 다섯 줄이다.

    JVMS 3.13은 finally를 jsr/ret 명령을 쓰는 서브루틴으로 컴파일하는 예를 보여 주는데, 그 절 첫머리에 클래스 파일 버전 50.0 이하를 가정한 설명이라고 밝혀 두었다. 위 출력처럼 OpenJDK 21의 javac는 그 명령을 쓰지 않고 블록을 복사한다. 어느 방식이든 "모든 예외를 받는 핸들러를 하나 두고, 정리한 뒤 다시 던진다"는 구조는 같다.

    이 구조를 알면 finally의 함정 세 가지가 왜 생기는지도 보인다.

    public class Puzzle {
    static int f() {
        int x = 1;
        try {
            return x;
        } finally {
            x = 2;
        }
    }

    static int g() {
        try {
            throw new IllegalStateException("사라지는 예외");
        } finally {
            return -1;
        }
    }

    static void h() {
        try {
            throw new IllegalStateException("본문의 예외");
        } finally {
            throw new IllegalArgumentException("finally의 예외");
        }
    }

    public static void main(String[] args) {
        System.out.println(f());
        System.out.println(g());
        try {
            h();
        } catch (RuntimeException e) {
            System.out.println(e);
            System.out.println(e.getCause());
        }
    }

    첫째, f()는 1을 돌려준다. return x는 두 단계로 실행된다. 먼저 돌려줄 값을 계산해 임시 지역 변수에 보관하고, finally의 코드를 실행한 뒤, 보관해 둔 값을 반환한다. 바이트코드로는 iload_0, istore_1(x의 값을 변수 1에 복사), iconst_2, istore_0(finally: x = 2), iload_1, ireturn 순서다. finally가 바꾼 것은 변수 0이고 반환되는 것은 변수 1의 복사본이다. 다만 반환값이 객체 참조라면 복사되는 것은 참조뿐이므로, finally에서 그 객체의 내용을 바꾸면 호출자에게 바뀐 내용이 보인다.

    둘째, g()는 예외를 삼킨다. try 블록이 예외를 던졌는데 메서드는 -1을 정상 반환했다. 표의 마지막 줄에 해당하는 경우로, JLS 14.20.2는 finally 블록이 어떤 이유 S로 갑작스럽게 끝나면 try 문은 S로 끝나고, 던져지던 값은 버려지고 잊힌다고 적는다. return도 갑작스러운 완료의 한 가지다. 바이트코드로 보면 숨은 핸들러가 예외를 지역 변수에 넣어 두기만 하고(astore_0), 이어지는 복사된 finally 코드가 iconst_m1, ireturn으로 반환해 버린다. OpenJDK 21의 javac는 이 핸들러에 예외를 다시 던지는 athrow를 아예 넣지 않는다. javac는 -Xlint:finally 옵션을 주면 이 코드에 finally clause cannot complete normally라는 경고를 낸다.

    셋째, h()는 예외를 바꿔치기한다. 호출자가 받은 것은 finally가 던진 IllegalArgumentException뿐이다. 본문이 던진 IllegalStateException은 원인(cause)으로도 남지 않았다. 이 함정이 실제로 문제가 되는 곳이 자원 정리다. 본문에서 진짜 문제가 터지고, 이어서 finally의 close()까지 실패하면, 로그에 남는 것은 close()의 예외뿐이고 진짜 원인은 사라진다. 이 문제는 뒤에서 try-with-resources가 해결한다.

    finally가 실행되지 않는 경우도 있다. try 블록 안에서 System.exit(0)을 호출하면 JVM이 그 자리에서 종료 절차에 들어가므로 finally의 출력문은 찍히지 않는다. 프로세스가 강제 종료되거나 전원이 나간 경우는 말할 것도 없다. finally는 "이 스레드가 이 try 문을 떠난다면"에 대한 보장이지, 프로그램이 어떻게 죽든 실행된다는 보장이 아니다.

    try 문을 빠져나가는 경로가 셋(정상, catch를 거침, 못 잡은 예외)이고, 세 경로 모두에 같은 finally 코드가 놓여 있으며, 셋째 경로는 finally 뒤에 예외를 다시 던진다는 것을 보여 준다. 흰 배경의 순서도. 맨 위에 둥근 사각형 "try 본문". 거기서 아래로 세 갈래 화살표가 나뉜다. 왼쪽 갈래 라벨 "예외 없음", 가운데 갈래 라벨 "IOException", 오른쪽 갈래 라벨 "그 밖의 예외". 가운데 갈래에는 사각형 "catch 블록"이 하나 끼어 있다. "catch 블록"에서 오른쪽 갈래로 가는 작은 점선 화살표를 그리고 라벨 "catch 안에서 예외". 세 갈래 모두 그 아래에 똑같은 모양의 주황색 사각형 "finally 코드"가 하나씩 놓인다(총 세 개, 가로로 나란히). 세 주황 사각형을 감싸는 얇은 점선 테두리와 라벨 "같은 코드의 복사본 3개". 왼쪽과 가운데 주황 사각형에서 아래로 파란 화살표가 내려와 하나로 합쳐져 둥근 사각형 "try 문 다음 문장"으로 간다. 오른쪽 주황 사각형에서 아래로 빨간 화살표가 내려가 둥근 사각형 "예외 다시 던짐"으로 간다. 색은 파랑(정상 진행), 빨강(예외 전파), 주황(finally) 세 가지만 쓴다. javac는 finally 블록을 탈출 경로마다 복사한다. 못 잡은 예외의 경로는 정리 뒤에 예외를 다시 던진다.

    예외 계층: 오류 코드 대신 타입으로 구분한다

    지금의 StorageException은 클래스가 하나뿐이고, 어떤 실패인지는 code 필드의 문자열이 말해 준다. 실패하면 무조건 한 줄을 출력하는 동안에는 그것으로 충분했다. 그런데 실패마다 대응을 달리해야 한다면 사정이 바뀐다. 세션을 열지 못한 것은 저장소 쪽 사정이니 예비 호스트로 돌려 볼 만하고, 용량 제한에 걸린 파일은 다시 올려 봐야 소용이 없으니 건너뛰는 편이 맞다. 예외 클래스가 하나라면 이 구분을 catch 블록 안에서 문자열 비교로 해야 한다.

    예외는 객체이고, 객체의 종류는 클래스로 나타낸다. 그러니 실패의 종류도 문자열이 아니라 클래스로 나누고, 공통 부모 아래에 묶으면 된다.

    셋째, 메서드 선언이 실패의 종류를 말한다. open() throws SessionOpenException이라는 한 줄에서 이 메서드가 어떤 식으로 실패하는지가 읽힌다. 넷째, 부모 타입이 있으므로 여러 실패를 묶어서 다룰 수 있다. 이 성질은 실패의 종류가 늘어날 때 힘을 낸다.

    멀티 캐치

    타입은 다르지만 대응이 같은 경우도 있다. 연결 실패와 전송 실패를 둘 다 "다음 주기에 재시도"로 처리하고 싶다고 하자. 같은 블록을 두 번 쓰는 대신 |로 타입을 나열하는 멀티 캐치(multi-catch)를 쓸 수 있다.

    } catch (SessionOpenException | UploadException e) {

} catch (StorageException e) {
    System.out.println("[저장소 오류] " + e.getMessage());
}

    행은 타입마다 하나씩 둘이 생겼는데 target이 둘 다 37이다. 핸들러 코드는 한 벌뿐이고, 두 종류의 예외가 같은 코드로 들어온다. 그 코드는 들어온 객체가 둘 중 어느 쪽인지 모르는 채로 컴파일되어야 하므로, 양쪽에 공통으로 있는 멤버만 쓸 수 있다. 타입별로 다른 멤버가 필요하다면 그때는 catch를 나눠야 한다.

    범위를 넓게 잡는 것과 지나치게 넓게 잡는 것은 다르다. 이 자리에서 catch (Exception e)를 쓰면 저장소 예외뿐 아니라 NullPointerException 같은 프로그램 버그까지 "저장소 오류"로 출력되고 넘어간다. 중간 계층의 catch는 자기가 대응 방법을 아는 타입까지만 잡는다.

    실무 예외 처리 방안: 처리할 수 없는 예외가 대부분이다

    여기까지 오면서 "복구"라고 부른 것을 솔직하게 다시 보자. catch 블록이 한 일은 한 줄을 출력한 것뿐이다. 저장소 서버가 내려갔을 때 백업 코드가 서버를 다시 켤 수는 없다. 이것은 예제만의 사정이 아니다. 데이터베이스가 응답하지 않는다, 설정 파일이 없다, 디스크가 가득 찼다, 보낸 SQL에 문법 오류가 있다. 이런 실패를 만난 코드가 그 자리에서 할 수 있는 일은 거의 없다.

    이런 실패에 실제로 필요한 조치는 네 가지다. 하던 작업 단위를 중단한다. 개발자와 운영자가 원인을 찾을 수 있게 자세히 기록한다. 사용자에게는 내부 사정을 드러내지 않는 안내를 보여 준다. 그리고 프로그램은 다음 요청을 계속 받는다. 네 가지 모두 예외가 난 자리나 중간 계층이 아니라 요청 처리의 맨 바깥에서 할 일이다. 그렇다면 중간 계층은 이 예외에 관여할 이유가 없다.

    체크 예외는 그 중간 계층을 전부 끌어들인다. 저수준 통신 코드가 IOException을 던지고, 그 위에 세션, 서비스, 야간 작업, main이 차례로 쌓인 구조를 보자.

    import java.io.IOException;

class Transport {
    static void connect(String host) throws IOException {
        if (host.startsWith("down")) throw new IOException(host + ": 연결 거부");
    }
}
class StorageSession {
    private final String host;
    StorageSession(String host) { this.host = host; }
    void open() throws IOException { Transport.connect(host); }
    void close() { }
}
class BackupService {
    void backup(String host, String name) throws IOException {
        StorageSession s = new StorageSession(host);
        s.open();
        s.close();
    }
}
class NightlyJob {
    private final BackupService service = new BackupService();
    void runAll() throws IOException {
        service.backup("backup1", "a.txt");
    }
}
public class Chain {
    public static void main(String[] args) throws IOException {
        new NightlyJob().runAll();
    }
}

    throws IOException이 다섯 번 나오는데, 그중 예외를 실제로 다루는 메서드는 하나도 없다. 여기서 문제가 세 갈래로 자란다.

    • 선언이 번진다. 예외를 다룰 능력이 없는 메서드까지 모두 throws를 달거나 try-catch를 써야 한다. 계층이 깊을수록 늘어난다.
    • 아래 계층의 구현 기술이 위로 새어 나온다. BackupService.backup의 선언만 봐도 그 아래에서 java.io를 쓴다는 사실이 드러난다. 저장 방식을 JDBC로 바꾸면 체크 예외인 java.sql.SQLException이 올라오고, 그것을 넘기는 모든 메서드의 선언을 고쳐야 한다. Throwable의 Javadoc도 이 점을 짚는다. 아래 계층의 예외를 그대로 밖으로 내보내면 그 예외가 체크 예외일 때 위 계층의 API가 구현 세부에 묶인다는 것이다.
    • throws Exception으로 달아난다. 선언을 고치는 일이 번거로워지면 모든 메서드에 throws Exception을 붙이고 싶어진다. 컴파일은 되지만 대가가 크다.

    그 대가는 실험으로 확인된다. backup 안에 Thread.sleep(10); 한 줄을 넣어 보자. sleep은 체크 예외 InterruptedException을 던질 수 있다. 선언이 throws IOException이면 javac가 error: unreported exception InterruptedException; must be caught or declared to be thrown이라고 막아 선다. 선언이 throws Exception이면 같은 코드가 아무 말 없이 컴파일된다. InterruptedException도 Exception의 하위 클래스라 이미 선언된 것으로 치기 때문이다. 체크 예외가 주는 이점은 "처리를 빠뜨리면 컴파일러가 알려 준다"는 것 하나인데, throws Exception은 그 알림을 꺼 버린다. 호출하는 쪽도 다시 throws Exception을 달거나 catch (Exception e)로 뭉뚱그려 잡을 수밖에 없으니 모호함이 위로 번진다.

    그래서 처리할 수 없는 예외가 대부분인 프로그램에서는 다음 구성이 널리 쓰인다.

    1. 예외는 언체크 예외를 기본으로 한다. RuntimeException을 상속하면 중간 계층은 선언도 catch도 쓰지 않는다. 예외는 호출 스택을 따라 저절로 올라간다.
    2. 아래 계층의 체크 예외는 경계에서 잡아 자기 계층의 언체크 예외로 바꿔 던진다. 이때 원래 예외를 원인(cause)으로 넣는다. JDK에도 같은 방식의 클래스가 있다. java.io.UncheckedIOException은 IOException을 언체크 예외로 감싸는 클래스다(Java 8부터).
    3. 요청 처리의 맨 바깥 한 곳에 공통 처리를 둔다. 기록, 사용자 안내, 다음 요청으로 넘어가기를 여기서 한다.
    4. 대응 방법이 있는 곳에서만 골라 잡는다. 예비 호스트가 있다면 그것을 아는 계층이 SessionOpenException만 잡는다.

    잃는 것도 있다. 언체크 예외는 선언과 처리가 강제되지 않으므로, 어떤 예외가 올라올 수 있는지를 컴파일러가 더는 알려 주지 않는다. 이 빈자리는 문서 주석의 @throws와, 놓친 예외를 마지막에 받아 내는 공통 처리가 메운다. 체크 예외가 쓸모없다는 뜻은 아니다. 호출자가 그 자리에서 대응할 수 있고 놓치면 안 되는 실패라면 컴파일러의 확인을 받는 편이 낫다. 기준은 "호출자가 이 예외로 무엇을 할 수 있는가"다.

    실무 예외 처리 구현: 원인을 품은 언체크 예외와 공통 처리

    백업 프로그램을 이 구성으로 옮긴다. 줄 번호가 뒤의 스택 트레이스에 나오므로 파일 전체를 싣는다. 통신을 흉내 내는 Transport만 체크 예외를 던지고, 그 위는 모두 언체크다.

    import java.io.IOException;

class StorageException extends RuntimeException {
    StorageException(String message, Throwable cause) { super(message, cause); }
}
class SessionOpenException extends StorageException {
    SessionOpenException(String host, Throwable cause) {
        super(host + " 세션을 열 수 없다", cause);
    }
}
class UploadException extends StorageException {
    UploadException(String name, Throwable cause) {
        super(name + " 파일을 올릴 수 없다", cause);
    }
}

class Transport {                         // 저수준 통신을 흉내 낸다. 체크 예외를 던진다
    static void connect(String host) throws IOException {
        if (host.startsWith("down")) throw new IOException(host + ": 연결 거부");
        System.out.println(host + " 세션 열림");
    }
    static void send(String host, String name) throws IOException {
        if (name.endsWith(".iso")) throw new IOException(name + ": 용량 제한 초과");
        System.out.println(host + " <- " + name);
    }
}

class StorageSession {
    private final String host;
    StorageSession(String host) { this.host = host; }

    void open() {
        try {
            Transport.connect(host);
        } catch (IOException e) {
            throw new SessionOpenException(host, e);    // 원인을 품고 언체크로 바꾼다
        }
    }
    void put(String name) {
        try {
            Transport.send(host, name);
        } catch (IOException e) {
            throw new UploadException(name, e);
        }
    }
    void close() { System.out.println(host + " 세션 닫힘"); }
}

class BackupService {
    void backup(String host, String name) {             // throws가 없다
        StorageSession s = new StorageSession(host);
        s.open();
        try {
            s.put(name);
        } finally {
            s.close();
        }
    }
}

public class Main {
    public static void main(String[] args) {
        BackupService service = new BackupService();
        String[][] requests = { {"backup1", "a.txt"}, {"down1", "a.txt"}, {"backup1", "disk.iso"} };
        for (String[] r : requests) {
            try {
                service.backup(r[0], r[1]);
            } catch (Exception e) {
                handle(e);                              // 공통 처리 한 곳
            }
            System.out.println("--");
        }
    }

    static void handle(Exception e) {
        System.out.println("[안내] 백업하지 못했습니다. 잠시 뒤 다시 시도해 주세요.");
        e.printStackTrace(System.out);                  // 예제에서는 표준 출력에, 실제로는 로그에 남긴다
    }
}

BackupService.backup에는 이 예외를 위한 코드가 한 줄도 없다. 52행의 s.open()은 try 블록보다 앞에 있으므로 finally도 관여하지 않고, 프레임이 제거되면서 예외가 main으로 올라간다. main의 catch (Exception e)가 받아 handle에 넘기고, 반복문은 다음 요청으로 간다.

    세 번째 요청에서는 put이 실패한다. 이번에는 try 블록 안이므로 finally의 close()가 먼저 실행되고("세션 닫힘"), 그다음 예외가 main에 닿는다. BackupService는 예외를 선언하지도 잡지도 않지만 정리는 빠뜨리지 않았다. 중간 계층에 남은 책임은 자원 정리 하나다.

    공통 처리가 Throwable이 아니라 Exception을 잡는 데에도 근거가 있다. JLS 11.1.1은 Error를 Exception과 별개의 가지로 둔 이유를, catch (Exception e)라는 관용구로 복구 가능성이 있는 예외를 모두 잡으면서 복구가 보통 불가능한 오류는 잡지 않게 하려는 것이라고 설명한다.

    Caused by와 ... n more 읽기

    출력된 스택 트레이스는 예외 두 개의 기록이 이어진 것이다. 위쪽 덩어리가 공통 처리에 도착한 SessionOpenException이고, Caused by: 아래가 그 원인인 IOException이다. 앞 회차에서 스택 트레이스는 예외 객체가 만들어진 순간의 호출 스택이라고 했다. 그래서 두 덩어리의 맨 윗줄은 각각 36행과 19행, 두 예외가 new로 만들어진 자리를 가리킨다.

    읽는 순서는 아래에서 위다. 가장 아래의 Caused by가 맨 처음 터진 일이고, 위로 갈수록 그 일을 각 계층이 자기 언어로 다시 말한 것이다. 프레임워크를 거친 실제 스택 트레이스는 Caused by가 여러 번 이어지고 수십 줄이 넘는데, 그럴 때도 맨 마지막 Caused by부터 본다.

    원인을 넘기지 않으면 어떻게 되는가. 36행을 new SessionOpenException(host, null)로 바꿔 실행하면 출력은 위쪽 네 줄에서 끝난다. "연결 거부"라는 진짜 이유도, 19행이라는 위치도 사라진다. 운영자는 세션을 열지 못했다는 사실만 알고 왜 그랬는지는 알 수 없다. 예외를 다른 예외로 바꿔 던질 때는 받은 예외를 생성자에 넘긴다. Throwable(String message, Throwable cause) 생성자가 이를 위한 것이고, 넘긴 예외는 getCause()로 꺼낼 수 있다. Javadoc은 원인의 메시지가 새 예외의 메시지에 자동으로 합쳐지지 않는다는 점도 적어 두었다. 그래서 위 출력에서도 두 메시지가 따로 찍혔다.

    같은 이유로 공통 처리에서 e.getMessage()만 기록하는 것도 피한다. 메시지 한 줄에는 호출 경로도 원인도 없다. 기록할 때는 예외 객체를 통째로 넘겨 스택 트레이스와 원인 사슬이 함께 남게 한다.

"통신 계층" 안에 빨간 카드 "IOException"과 그 옆 작은 라벨 "체크 예외". "통신 계층"과 "세션 계층" 사이에 가로 점선과 라벨 "경계: 여기서 바꾼다". "세션 계층" 안에는 주황 카드 "SessionOpenException"이 있고, 그 카드 안쪽에 더 작은 빨간 카드 "IOException"이 들어 있는 모습으로 그리며 옆에 라벨 "원인 포함". "서비스 계층"은 화살표가 그대로 통과하는 모습으로 그리고 옆에 회색 라벨 "코드 없음". 맨 위 "공통 처리" 상자 안에는 주황 카드가 도착해 있고 그 오른쪽에 작은 아이콘 세 개와 라벨 "기록", "사용자 안내", "다음 요청". 색은 빨강(체크 예외), 주황(언체크 예외), 회색(계층 상자) 세 가지만 쓴다. 체크 예외는 발생한 계층 바로 위에서 원인을 품은 언체크 예외로 바뀌고, 맨 바깥의 공통 처리 한 곳에 도착한다.

    대응 방법을 아는 계층이 있다면 그 계층만 골라 잡으면 된다. 예비 호스트를 아는 쪽에서 다음과 같이 쓰면, 연결 실패는 여기서 복구되고 그 밖의 예외는 계속 올라가 공통 처리에 닿는다.

    try {
    service.backup("down1", name);
} catch (SessionOpenException e) {
    service.backup("backup2", name);      // 대응 방법을 아는 곳에서만 잡는다
}

    try-with-resources: 닫는 일을 컴파일러에 맡긴다

    try-finally로 정리는 보장했다. 하지만 이 방식에는 아직 약점이 셋 남아 있다. 첫째, 자원이 늘면 중첩이 깊어진다. 자원 두 개를 안전하게 다루려면 획득할 때마다 try-finally를 하나씩 열어야 한다.

    Res r1 = new Res("A");
try {
    Res r2 = new Res("B");
    try {
        // r1, r2를 쓰는 본문
    } finally {
        r2.close();
    }
} finally {
    r1.close();
}

    둘째, 앞의 Puzzle.h()에서 본 대로 finally 안의 close()가 예외를 던지면 본문의 예외가 사라진다. 셋째, 이 모든 것을 사람이 써야 한다. finally를 빠뜨려도 컴파일은 된다. 자원 변수를 try 바깥에 선언해야 하므로, 닫은 뒤에도 변수가 살아 있어 닫힌 자원을 다시 쓰는 실수도 막지 못한다.

    Java 7에 들어온 try-with-resources 문은 이 셋을 언어 차원에서 정리한다. try 뒤의 괄호 안에 자원을 선언하면, 블록을 떠날 때 컴파일러가 만들어 넣은 코드가 close()를 호출한다. 조건은 자원의 타입이 java.lang.AutoCloseable을 구현하는 것 하나다. 이 인터페이스의 메서드는 void close() throws Exception 하나뿐이다.

    class Res implements AutoCloseable {
    private final String name;
    Res(String name) {
        if (name.startsWith("bad")) throw new IllegalStateException(name + " 초기화 실패");
        this.name = name;
        System.out.println(name + " 열림");
    }
    void use(boolean fail) {
        if (fail) throw new IllegalStateException(name + " 사용 중 오류");
        System.out.println(name + " 사용");
    }
    @Override
    public void close() {
        System.out.println(name + " 닫힘");
    }
}

public class Order {
    static void run(String a, String b, boolean fail) {
        try (Res r1 = new Res(a); Res r2 = new Res(b)) {

            System.out.println("catch: " + e.getMessage());

    세 경우를 차례로 읽는다. 첫 번째는 정상 경로다. 자원은 왼쪽에서 오른쪽으로 초기화되고, 본문이 끝나면 초기화의 역순으로 닫힌다. 나중에 만든 자원이 먼저 만든 자원에 기대고 있는 경우가 많으므로, 쌓은 순서의 반대로 허무는 것이다. 중첩된 try-finally에서 안쪽 finally가 먼저 실행되던 것과 같은 순서다.

    두 번째는 본문에서 예외가 난 경우다. 눈여겨볼 것은 "B 닫힘", "A 닫힘"이 "catch"보다 먼저 나온다는 점이다. try-with-resources에 붙은 catch와 finally는 자원이 모두 닫힌 뒤에 실행된다. 그래서 catch 블록이 실행될 때 자원은 이미 정리된 상태다.

    세 번째는 둘째 자원의 초기화가 실패한 경우다. 이미 초기화된 A만 닫히고, 만들어지지 못한 B에 대해서는 close()가 호출되지 않는다. "획득에 성공한 것만 닫는다"는, try-finally에서 손으로 지켜야 했던 원칙이 문법에 들어가 있다. 초기화에서 난 예외도 같은 문장의 catch가 받는다.

    JLS 14.20.3이 정한 규칙을 모으면 다음과 같다. 괄호 안의 오류 문구는 JDK 21의 javac가 내는 것이다.

    • 자원의 타입은 AutoCloseable의 하위 타입이어야 한다. try (String s = "x")는 incompatible types: try-with-resources not applicable to variable type으로 거절된다.
    • 괄호 안에서 선언한 자원 변수는 암묵적으로 final이다. 본문에서 다른 객체를 대입하면 auto-closeable resource r may not be assigned 오류가 난다. 닫을 대상이 중간에 바뀌는 일을 막는다.
    • 자원 변수의 범위는 try 블록까지다(범위 규칙 자체는 JLS 6.3에 적혀 있다). catch와 finally 블록에서는 그 이름이 보이지 않는다(cannot find symbol). 닫힌 자원을 다시 쓰는 코드를 쓸 수 없다.
    • 자원은 왼쪽부터 초기화되고 역순으로 닫힌다. 초기화 도중 예외가 나면 그때까지 초기화된 자원만 닫힌다.
    • null로 초기화된 자원은 닫지 않는다. NullPointerException이 나지 않고 그냥 건너뛴다.
    • 한 자원의 close()가 예외를 던져도 나머지 자원의 close()는 호출된다.
    • Java 9부터는 이미 선언된 final 또는 사실상 final인 변수를 try (r)처럼 이름만 적어 자원으로 쓸 수 있다. 같은 코드를 javac --release 8로 컴파일하면 variables in try-with-resources are not supported in -source 8이라는 오류가 난다.

    try-with-resources가 풀리는 모양과 suppressed 예외

    이 문장은 JVM에 새 기능을 요구하지 않는다. JLS 14.20.3.1은 try-with-resources의 의미를 평범한 try-catch-finally로 옮긴 코드로 정의한다. 자원이 하나인 try (Flaky f = new Flaky()) { f.work(); }를 그 정의대로 손으로 풀어 쓰면 다음과 같다(변수 이름은 읽기 쉽게 붙였다).

    final Flaky f = new Flaky();                 // ① 초기화는 try 바깥이다
Throwable primary = null;                    // ② 본문에서 난 예외를 기억할 자리
try {
    f.work();
} catch (Throwable t) {
    primary = t;                             // ③ 본문의 예외를 기억해 두고
    throw t;                                 //    그대로 다시 던진다
} finally {
    if (f != null) {
        if (primary != null) {
            try {
                f.close();
            } catch (Throwable fromClose) {
                primary.addSuppressed(fromClose);   // ④ 덮지 않고 덧붙인다
            }
        } else {
            f.close();                       // ⑤ 본문이 정상이면 close의 예외가 그대로 나간다
        }
    }
}

    지금까지 본 동작이 전부 이 코드에서 나온다. ①에서 초기화가 실패하면 try에 들어가기도 전이므로 close()는 호출되지 않는다. finally의 f != null 검사가 null 자원을 건너뛰게 한다. 자원이 둘 이상이면 이 번역이 되풀이 적용된다. 첫 자원을 푼 코드의 try 블록 안에 나머지 자원에 대한 try-with-resources가 통째로 들어가므로, 안쪽(나중에 선언한) 자원의 finally가 먼저 실행되어 역순 닫기가 된다. catch나 finally가 붙은 형태는 JLS 14.20.3.2가 따로 정한다. 자원 부분 전체를 바깥 try 블록 안에 넣고 거기에 catch와 finally를 붙인 것과 같다. 닫기가 catch보다 먼저인 이유, 초기화나 닫기에서 난 예외도 그 catch가 받는 이유가 여기서 나온다.

    핵심은 ③과 ④다. 본문과 close()가 둘 다 예외를 던졌을 때, 번역 코드는 본문의 예외를 주된 예외로 삼고 close()의 예외를 addSuppressed로 거기에 붙인다. 이렇게 붙은 예외를 suppressed 예외(억제된 예외)라고 한다. 실행해서 확인한다.

    class Flaky implements AutoCloseable {
    void work() {
        throw new IllegalStateException("본문의 예외");
    }
    @Override
    public void close() {
        throw new IllegalArgumentException("close의 예외");
    }
}

public class Sup {
    public static void main(String[] args) {
        try (Flaky f = new Flaky()) {
            f.work();
        } catch (RuntimeException e) {
            System.out.println(e);
            System.out.println(e.getCause());
            for (Throwable s : e.getSuppressed()) {
                System.out.println("suppressed: " + s);
            }
        }
        System.out.println("--");
        try (Flaky f = new Flaky()) {
            f.work();
        }
    }
}

    AutoCloseable과 Closeable

    자바에는 닫을 수 있는 자원을 나타내는 인터페이스가 둘 있다. java.io.Closeable은 AutoCloseable을 상속하므로 스트림 클래스들은 모두 try-with-resources에 쓸 수 있다. 차이는 계약의 엄격함이다. Closeable.close()는 IOException을 던지도록 선언되어 있고, 이미 닫힌 뒤에 다시 호출해도 아무 효과가 없어야 한다. AutoCloseable.close()는 Exception을 던지도록 넓게 선언되어 있고, 여러 번 호출해도 안전할 것이 요구되지는 않는다. 다만 Javadoc은 그렇게 만들기를 강하게 권한다.

    직접 구현할 때는 Javadoc의 조언 두 가지를 기억해 둘 만하다. 하나는 close()를 재정의할 때 더 구체적인 예외만 선언하거나, 실패할 수 없다면 아무 예외도 선언하지 않으라는 것이다. 재정의하면서 throws Exception을 그대로 두면 그 자원을 쓰는 모든 try-with-resources 문이 Exception을 처리해야 하고, 처리하지 않으면 javac가 exception thrown from implicit call to close() on resource variable이라는 설명과 함께 오류를 낸다. 다른 하나는 close()에서 InterruptedException을 던지지 말라는 것이다. 이 예외가 suppressed로 밀려나면 스레드의 인터럽트 상태와 얽혀 오동작하기 쉽다는 이유다.

    백업 프로그램에 적용하기

    마지막으로 백업 프로그램을 고친다. StorageSession이 AutoCloseable을 구현하고, 세션 열기를 생성자로 옮긴다.

    class StorageSession implements AutoCloseable {
    private final String host;

    StorageSession(String host) {                       // 생성이 곧 획득이다
        try {
            Transport.connect(host);
        } catch (IOException e) {
            throw new SessionOpenException(host, e);
        }
        this.host = host;
    }
    void put(String name) {
        try {
            Transport.send(host, name);
        } catch (IOException e) {
            throw new UploadException(name, e);
        }
    }
    @Override
    public void close() {                               // throws를 선언하지 않는다
        System.out.println(host + " 세션 닫힘");
    }
}

class BackupService {
    void backup(String host, String name) {
        try (StorageSession s = new StorageSession(host)) {

    앞에서 파일 디스크립터를 바닥낸 Leak 예제도 같은 방법으로 고친다. FileInputStream은 Closeable이므로 try (FileInputStream in = new FileInputStream("Leak.java")) { ... }로 열면 블록을 떠날 때 디스크립터가 반납된다. 읽다가 예외가 나도 마찬가지다.

    try (A a = ...; B b = ...) { 본문 } catch (...) { } finally { }

     │        │       │                        없으면 이 예외가 전파된다
     │        │       └─ 예외가 나도 두 close()는 실행된다

     └─ 실패하면 닫을 것 없이 catch로
    자원 초기화, 본문, 역순 닫기, catch, finally가 이 순서로 실행되고, 본문의 예외에 close의 예외가 suppressed로 달라붙는 모습을 한 줄의 시간축으로 보여 준다. 흰 배경의 가로 타임라인 다이어그램. 왼쪽에서 오른쪽으로 향하는 긴 회색 시간축 화살표 위에 일곱 개의 둥근 사각형을 차례로 놓는다. 라벨은 순서대로 "A 초기화", "B 초기화", "본문", "B 닫기", "A 닫기", "catch", "finally". "A 초기화"와 "B 초기화"는 파란색, "본문"은 흰색에 굵은 테두리, "B 닫기"와 "A 닫기"는 주황색, "catch"와 "finally"는 회색으로 칠한다. "A 초기화"에서 "A 닫기"로, "B 초기화"에서 "B 닫기"로 각각 위쪽으로 휘어지는 얇은 곡선을 그려 짝을 표시하고, 두 곡선이 서로를 감싸는 중첩 모양(A 곡선이 바깥, B 곡선이 안쪽)이 되게 한다. 곡선 위에 라벨 "역순으로 닫는다". "본문" 상자 아래에 빨간 카드 "본문의 예외"를 그리고, "B 닫기" 상자 아래에 작은 주황 카드 "close의 예외"를 그린다. 작은 주황 카드에서 빨간 카드로 향하는 화살표를 그리고 라벨 "suppressed로 붙는다". 빨간 카드에서 "catch" 상자로 향하는 빨간 점선 화살표를 그리고 라벨 "전달되는 것은 본문의 예외". 색은 파랑, 주황, 빨강, 회색만 쓴다. 자원은 선언 순서로 열리고 역순으로 닫히며, catch와 finally는 그 뒤에 실행된다. 닫다가 난 예외는 본문의 예외에 덧붙는다.

    정리: 한 프로그램이 거쳐 온 단계

    백업 프로그램은 일곱 단계를 거쳤다. 단계마다 무엇을 고쳤고 그 결과 어떤 문제가 새로 드러났는지를 한 표로 모은다.

    2반환값 검사실패를 알아차린다정상 흐름이 조건문에 묻히고, 검사를 빠뜨려도 컴파일된다
    3예외와 catch정상 흐름과 예외 흐름이 나뉘고, 처리하지 않은 실패는 저절로 올라간다예외가 close()를 건너뛴다
    4finally어떤 경로로 나가든 정리한다중첩이 깊어지고, 정리 중의 예외가 원래 예외를 덮는다
    5예외 계층실패의 종류를 타입으로 구분하고 부모로 묶는다체크 예외의 선언이 계층마다 번진다
    6언체크 예외, 원인 포함, 공통 처리중간 계층이 예외에서 손을 떼고, 기록과 안내가 한 곳에 모인다선언이 강제되지 않으므로 문서와 공통 처리에 기댄다
    7try-with-resources닫기를 컴파일러가 넣고, 정리 중의 예외는 suppressed로 남는다-

    일곱 단계 내내 JVM 쪽에서 쓰인 장치는 둘뿐이었다. 예외를 던지는 athrow 명령과, 구간·타입·핸들러 위치를 적은 예외 테이블이다. catch의 순서 규칙, 멀티 캐치, finally, try-with-resources는 모두 javac가 이 표의 행과 복사된 코드로 풀어 낸 것이다. 예외 처리 문법이 낯설게 동작할 때는 "이 코드가 예외 테이블의 어떤 행이 되는가"를 그려 보면 대개 답이 나온다.

    이 회차의 내용은 로드맵의 뒤쪽에서 계속 다시 나온다. JDBC의 java.sql.Connection은 AutoCloseable을 상속하므로, 데이터베이스 접근 코드에서 커넥션을 try-with-resources로 여닫게 된다. 반대로 try-finally가 여전히 필요한 곳도 있다. java.util.concurrent.locks.Lock은 AutoCloseable이 아니어서, 그 Javadoc은 lock()을 호출한 뒤 try 블록에서 작업하고 finally에서 unlock()을 부르는 형태를 보여 준다. 자원 획득을 try 바깥에 두고 해제를 finally에 두는, 이번 회차에서 세운 그 모양이다. 언체크 예외와 공통 처리라는 구성은 앞 회차의 끝에서 소개한 스프링의 예외 변환과 트랜잭션 롤백 규칙으로 이어진다.

    이 장의 핵심

    예외는 정상 흐름에서 검사를 걷어 내고 실패를 별도의 경로로 보낸다. 그 경로가 정리 코드를 건너뛰는 문제는 finally가, finally의 번거로움과 예외 덮어쓰기는 try-with-resources와 suppressed 예외가 푼다. 처리할 수 없는 예외는 언체크 예외로 흘려보내되 원인을 품게 하고, 맨 바깥 한 곳에서 기록한다. 이 모든 문법은 바이트코드에서 예외 테이블의 행과 복사된 정리 코드로 풀린다.
    정상 흐름과 예외 흐름의 분리
    반환값 검사는 호출마다 분기 명령을 남기지만, 예외를 쓰면 try 블록은 try가 없을 때와 같게 컴파일되고 실패 시의 경로는 예외 테이블의 행으로 따로 적힌다. 실패한 지점 뒤의 문장은 조건문 없이도 건너뛴다.
    리소스 반환 문제
    파일·소켓·커넥션은 JVM 밖(커널의 파일 디스크립터 테이블 등)에 실체가 있어 GC가 제때 치워 주지 않는다. 예외가 close()를 건너뛰면 자원이 새고, 증상은 한참 뒤 엉뚱한 곳에서 나타난다.
    finally
    try 문을 정상 완료, 잡힌 예외, 잡히지 않은 예외, return 어느 쪽으로 떠나든 실행된다. javac는 finally 코드를 탈출 경로마다 복사하고, 모든 예외를 받는 any 핸들러에서 정리한 뒤 예외를 다시 던진다. 자원 획득은 try 바깥에 둔다.
    finally의 함정
    finally가 return하거나 예외를 던지면 try 문은 그 이유로 끝나고 앞서 던져지던 예외는 버려진다(JLS 14.20.2). try의 return 값은 finally 실행 전에 따로 보관된다.
    예외 계층
    실패의 종류를 문자열 코드 대신 클래스로 나누고 공통 부모 아래에 둔다. 구분은 JVM의 타입 판정이 맡고, 예외마다 필요한 필드를 가지며, 받는 쪽은 자식별로 잡을지 부모로 묶어 잡을지를 고른다.
    catch 순서와 멀티 캐치
    예외 테이블은 위에서부터 검색되므로 자식을 먼저, 부모를 나중에 잡는다. 멀티 캐치는 타입마다 행을 만들되 핸들러는 하나라서, 파라미터의 타입은 공통 상위 타입이고 암묵적으로 final이며 상속 관계인 타입은 함께 나열할 수 없다.
    언체크 예외와 예외 변환
    처리할 수 없는 예외를 체크 예외로 올리면 throws가 계층마다 번지고 아래 계층의 기술이 선언에 드러난다. 경계에서 잡아 자기 계층의 언체크 예외로 바꾸고, 원래 예외를 원인으로 넣는다. throws Exception은 컴파일러의 누락 알림을 꺼 버린다.
    공통 예외 처리와 스택 트레이스
    요청 처리의 맨 바깥 한 곳에서 기록, 사용자 안내, 다음 요청으로의 진행을 맡는다. 스택 트레이스의 Caused by는 원인 예외이고 ... n more는 바깥 예외의 아래쪽 n개 프레임과 같아 생략했다는 표시다. 가장 아래의 Caused by가 최초의 실패다.
    try-with-resources와 suppressed 예외
    AutoCloseable 자원을 선언 순서로 초기화하고 역순으로 닫은 뒤 catch·finally를 실행한다. 본문과 close()가 모두 예외를 던지면 본문의 예외가 전파되고 close()의 예외는 addSuppressed로 붙는다.

    실무에서 다시 판단하면, 예외 처리의 대부분은 "어디서 잡을 것인가"의 문제다. 잡는 자리는 대응 방법을 아는 자리 하나와 맨 바깥의 공통 처리, 둘이면 대개 충분하다. 그 사이의 계층에서 예외를 잡아 로그만 찍고 다시 던지는 코드는 같은 실패를 여러 번 기록하게 만들어 로그를 읽기 어렵게 한다. 중간 계층이 예외에 손을 대는 정당한 이유는 두 가지다. 아래 계층의 예외를 자기 계층의 예외로 바꾸는 것, 그리고 자원을 정리하는 것. 앞의 경우에는 원인을 반드시 넘기고, 뒤의 경우에는 catch가 아니라 try-with-resources나 finally를 쓴다.

    체크와 언체크의 선택은 호출자가 그 예외로 무엇을 할 수 있는지에 달려 있다. 호출자가 그 자리에서 다른 경로를 택할 수 있고 놓치면 곤란한 실패라면 체크 예외로 컴파일러의 확인을 받을 만하다. 인프라의 장애나 프로그램의 버그처럼 호출자가 할 일이 없는 실패는 언체크로 둔다. 예외 계층을 얼마나 잘게 나눌지도 같은 기준으로 정한다. 받는 쪽이 다르게 대응할 종류만 클래스로 나누고, 나머지는 부모 타입과 메시지로 충분하다. 구분해서 잡을 사람이 없는 클래스를 늘리면 관리할 대상만 는다.

    자원 누수는 장애 현장에서 원인과 증상이 멀리 떨어져 나타난다. "Too many open files"는 파일을 열려던 무고한 코드에서 터지고, 실제 원인은 다른 곳에서 닫지 않은 스트림이다. 그래서 AutoCloseable인 것은 예외 없이 try-with-resources로 여는 것을 기본으로 삼고, 그렇지 않은 코드를 리뷰에서 걸러 내는 편이 싸다. 락처럼 AutoCloseable이 아닌 대상에는 try-finally가 그대로 필요하다. 이때 획득을 try 바깥에 두는 원칙을 지키지 않으면, 획득에 실패하고도 해제를 시도하는 두 번째 버그가 생긴다.

    로그를 읽는 쪽에서는 두 가지 습관이 시간을 줄여 준다. 긴 스택 트레이스는 맨 아래의 Caused by부터 읽는다. 그리고 Suppressed:가 보이면 정리 과정에서도 문제가 있었다는 뜻이므로 지나치지 않는다. 반대로 코드를 쓰는 쪽에서는 finally 안의 return, 원인을 빼고 새로 던지는 예외, e.getMessage()만 남기는 기록을 피한다. 셋 다 실패가 일어났다는 사실이나 그 이유를 지워 버리는 코드다.
