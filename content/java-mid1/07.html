    클래스 안에 클래스를 넣는다는 것: 이 회차의 질문

    기본편까지는 클래스를 소스 파일의 가장 바깥에 선언했다. 이렇게 컴파일 단위에 직접 선언한 클래스를 최상위 클래스(top level class)라 한다. 최상위 클래스에 붙일 수 있는 접근 제어자는 public이거나 아무것도 붙이지 않은 패키지 접근(package-private) 둘뿐이다. private과 protected는 멤버에만 쓸 수 있는 제어자여서 최상위 클래스에는 붙지 않는다.

    이 제약 때문에 곤란한 경우가 생긴다. 연결 리스트의 노드처럼 어떤 클래스 하나만 쓰는 보조 클래스가 있다고 하자. 최상위 클래스로 만들면 아무리 좁혀도 같은 패키지의 모든 클래스에 보인다. 패키지를 열어 본 사람은 이 클래스가 자기도 써도 되는 부품인지, 누군가의 내부 사정인지 이름만으로는 구분할 수 없다. 숨기고 싶은데 숨길 방법이 없는 것이다.

    반대 방향의 곤란함도 있다. 보조 클래스가 주인 클래스의 내부 상태를 읽어야 하는 경우다. 두 클래스가 따로 떨어져 있으면 주인 클래스는 보조 클래스 하나를 위해 getter나 변경 메서드를 열어야 하고, 한번 연 메서드는 다른 모든 클래스도 호출할 수 있다. 한 클래스를 돕자고 캡슐화의 벽에 구멍을 내는 셈이다.

    자바는 클래스의 본문 안에 다른 클래스를 선언하는 것을 허용한다. 이것이 중첩 클래스(nested class)다. 중첩 클래스는 필드나 메서드처럼 바깥 클래스의 멤버가 되므로 private을 붙여 숨길 수 있고, 바깥 클래스와 서로의 private 멤버를 읽을 수 있다. 위의 두 곤란함이 한꺼번에 풀린다.

    이 회차는 그 문법 아래에서 일어나는 일을 따라간다. 질문은 네 가지다. 중첩 클래스에는 어떤 종류가 있고 무엇으로 나뉘는가. static이 붙은 것과 안 붙은 것은 메모리에서 무엇이 다른가. 클래스 파일은 클래스마다 하나씩 따로 만들어지는데, JVM은 어떻게 "안쪽 클래스가 바깥 클래스의 private을 읽는 것"을 허용하는가. 안팎의 변수 이름이 겹치면 어느 것이 선택되는가. 메서드 안에 선언하는 지역 클래스와 익명 클래스는 다음 회차의 몫이므로 여기서는 분류표에서만 짚는다.

    중첩 클래스의 분류: 선언 위치와 static

    변수는 선언한 위치에 따라 성격이 달라졌다. static을 붙여 클래스에 선언하면 클래스 변수, static 없이 클래스에 선언하면 인스턴스 변수, 메서드 안에 선언하면 지역 변수다. 중첩 클래스도 같은 기준으로 나뉜다. 클래스를 변수와 같은 자리에 선언한다고 생각하면 분류가 그대로 겹친다.

    용어를 정확히 해 두자. 자바 언어 명세(JLS) 8장은 중첩 클래스를 "다른 클래스나 인터페이스의 본문 안에 선언된 모든 클래스"로 정의한다. 위치만 말하는 넓은 이름이다. 그 가운데 명시적으로든 암묵적으로든 static이 아닌 것을 내부 클래스(inner class)라 부른다(JLS §8.1.3). 따라서 표의 네 가지 중 정적 중첩 클래스만 내부 클래스가 아니고, 나머지 셋은 모두 내부 클래스다. 일상에서는 "내부 클래스"가 둘째 줄의 멤버 내부 클래스만 가리키는 말로도 쓰이는데, 이 회차에서도 따로 밝히지 않으면 그 뜻으로 쓴다.

    "중첩"과 "내부"의 차이는 단어의 뜻 그대로다. 중첩은 한 클래스의 선언이 다른 클래스의 선언 안에 놓여 있다는 소스 코드상의 위치를 말한다. 내부는 그 클래스의 인스턴스가 바깥 클래스의 인스턴스에 딸려 그 일부처럼 동작한다는 실행 시의 관계를 말한다. 정적 중첩 클래스는 위치만 안쪽이고 실행 시에는 바깥 인스턴스와 아무 관계가 없다. 내부 클래스는 위치도 안쪽이고 인스턴스도 바깥 인스턴스에 묶인다.

    static을 쓰지 않아도 암묵적으로 정적인 것이 있다. JLS §8.1.3은 멤버 enum 클래스, 멤버 레코드 클래스, 인터페이스 안에 선언한 멤버 클래스를 암묵적으로 static이라고 정한다. 중첩 인터페이스도 언제나 암묵적으로 static이어서 "내부 인터페이스"라는 것은 없다. 클래스 안에 enum을 선언하면 static을 쓰지 않아도 정적 중첩 클래스처럼 동작하는 이유가 이것이다.

    소스 파일은 하나인데 클래스 파일은 다섯 개다. JVM 명세는 클래스 파일 하나가 클래스(또는 인터페이스, 모듈) 하나의 정의를 담는다고 정한다. 클래스 파일 형식에는 "클래스 안의 클래스"를 한 파일에 겹쳐 담는 구조가 없다. 그래서 컴파일러는 중첩 클래스를 각각 독립된 클래스 파일로 떼어 내고, 이름으로만 소속을 표시한다.

    이름을 붙이는 규칙은 JLS §13.1이 정한다. 멤버 클래스의 바이너리 이름(binary name)은 바깥 클래스의 바이너리 이름 뒤에 $와 자신의 단순 이름을 붙인 것이다. 지역 클래스는 $ 뒤에 숫자와 단순 이름이, 익명 클래스는 $ 뒤에 숫자만 붙는다. getClass().getName()이 돌려주는 문자열이 이 바이너리 이름이고, 소스에서 쓰는 Outer.Inner는 점으로 이은 별도의 표기다.

    이 장의 핵심

    JVM이 보기에 중첩 클래스는 바깥 클래스와 별개의 클래스다. 따로 로딩되고, 따로 초기화되고, 힙에 따로 객체가 만들어진다. "안에 있다"는 것은 소스 코드와 이름, 그리고 클래스 파일에 적힌 몇 가지 속성에만 남는다. 이 회차의 나머지는 그 간극을 컴파일러와 JVM이 어떻게 메우는지에 대한 설명이다.

    중첩 클래스가 static 여부와 선언 위치에 따라 네 가지로 갈리고, 각각 별도의 클래스 파일이 된다는 것을 한 장에 보여 준다. 깔끔한 평면 스타일의 분류 트리 다이어그램. 흰 배경, 얇은 회색 선. 맨 위에 둥근 사각형 하나, 라벨 "중첩 클래스". 그 아래로 두 갈래: 왼쪽 상자 라벨 "정적 중첩 클래스", 오른쪽 상자 라벨 "내부 클래스". 오른쪽 "내부 클래스" 상자 아래로 다시 세 갈래의 작은 상자: "내부 클래스(멤버)", "지역 클래스", "익명 클래스". 왼쪽 가지의 선 위에 작은 꼬리표 "static 있음", 오른쪽 가지의 선 위에 꼬리표 "static 없음". 맨 아래 줄에는 네 개의 말단 상자 각각에서 아래로 점선 화살표가 내려와 파일 아이콘으로 이어진다. 파일 아이콘의 라벨은 왼쪽부터 "Outer$StaticNested.class", "Outer$Inner.class", "Outer$1Local.class", "Outer$1.class". 정적 중첩 클래스 상자는 파란색 계열, 내부 클래스 계열 상자들은 주황색 계열로 칠해 두 무리를 색으로 구분한다. 장식이나 인물 없이 도형과 글자만. 중첩 클래스는 static 여부로 먼저 갈리고, 내부 클래스는 선언 위치에 따라 다시 셋으로 나뉜다. 어느 것이든 컴파일하면 독립된 클래스 파일이 된다.

    정적 중첩 클래스: 바깥 인스턴스와 무관한 클래스

    정적 중첩 클래스는 클래스 본문 안에 static을 붙여 선언한다. 바깥 클래스의 클래스 변수 하나와 인스턴스 변수 하나, 그리고 정적 중첩 클래스 하나를 가진 예제로 접근 규칙을 확인한다.

    public class Library {
    private static int totalBooks = 120;   // 바깥 클래스의 클래스 변수
    private String branch = "central";     // 바깥 클래스의 인스턴스 변수

    static class Rule {
        private int maxDays = 14;

        void print() {
            System.out.println(maxDays);      // 자신의 인스턴스 변수
            System.out.println(totalBooks);   // 바깥 클래스의 private static 변수
            // System.out.println(branch);    // 컴파일 오류
        }
    }

    public static void main(String[] args) {
        Library.Rule rule = new Library.Rule();
        rule.print();
        System.out.println(rule.maxDays);     // 바깥 클래스에서 중첩 클래스의 private 변수
        System.out.println(rule.getClass().getName());
    }
}

    한 줄씩 보자. new Library.Rule()에서 Library 객체는 만들어지지 않는다. Library.Rule은 타입의 이름일 뿐이고, 점은 "Library 안에 선언된 Rule"이라는 소속을 나타낸다. 힙에는 Rule 객체 하나만 생기고 그 안에는 maxDays 필드 하나만 들어 있다. 바깥 클래스 안에서는 Library.을 생략하고 new Rule()이라고만 써도 된다.

    print()의 첫 줄은 자기 필드를 읽는다. 둘째 줄은 바깥 클래스의 private static 변수 totalBooks를 읽는데, 클래스 변수는 객체가 몇 개든 클래스당 하나만 있으므로 어떤 Library 객체인지 정할 필요가 없다. 그래서 읽을 수 있다. 주석 처리한 셋째 줄을 살리면 컴파일러는 다음 오류를 낸다.

    error: non-static variable branch cannot be referenced from a static context

    branch는 인스턴스 변수이므로 Library 객체마다 하나씩 있다. 읽으려면 "어느 객체의 branch인가"가 정해져야 하는데, Rule 객체는 어떤 Library 객체도 가리키고 있지 않다. 이것은 static 메서드 안에서 인스턴스 변수를 쓸 수 없는 것과 같은 이유다. JLS §8.1.1.4도 같은 식으로 설명한다. 정적 메서드의 본문에 현재 인스턴스가 없듯이, 정적 중첩 클래스의 본문에는 바깥 인스턴스가 없다. 물론 Library 객체의 참조를 매개변수나 필드로 받으면 그 참조를 통해 library.branch처럼 읽을 수는 있다. 막힌 것은 접근 권한이 아니라 "대상 객체가 정해지지 않은 접근"이다.

    main의 셋째 줄 rule.maxDays는 반대 방향의 접근이다. 바깥 클래스 Library의 코드가 중첩 클래스 Rule의 private 필드를 읽는다. 이것도 허용된다. 접근이 양방향으로 열려 있다는 점이 다음 절의 주제다.

    여기서 static은 "객체를 하나만 만든다"거나 "모든 곳에서 공유된다"는 뜻이 아니다. new Library.Rule()을 열 번 실행하면 Rule 객체 열 개가 생기고 각자 자기 maxDays를 갖는다. 정적 중첩 클래스의 static은 오직 "이 클래스의 인스턴스는 바깥 클래스의 인스턴스에 딸려 있지 않다"는 뜻이다.

    private의 경계는 최상위 클래스다: 네스트

    기본편에서 private은 "같은 클래스 안에서만 접근할 수 있다"고 배웠다. 중첩 클래스가 등장하면 이 문장을 더 정확히 해야 한다. JLS §6.6.1의 규칙은 이렇다. private 멤버에 대한 접근은 그 멤버의 선언을 감싸고 있는 최상위 클래스의 본문 안에서 일어나면 허용된다. 경계가 멤버를 선언한 클래스가 아니라 그것을 감싼 가장 바깥 클래스다.

    이 규칙에서 세 가지가 따라 나온다. 중첩 클래스는 바깥 클래스의 private 멤버에 접근할 수 있다. 바깥 클래스는 중첩 클래스의 private 멤버에 접근할 수 있다. 같은 최상위 클래스 안에 나란히 선언된 중첩 클래스들끼리도 서로의 private 멤버에 접근할 수 있다. 소스 코드의 관점에서는 최상위 클래스 하나와 그 안의 모든 중첩 클래스가 하나의 덩어리이고, private은 그 덩어리의 바깥을 막는 벽이다.

    그런데 앞 절에서 본 대로 JVM에게 Library와 Library$Rule은 서로 다른 클래스다. JVM은 실행 중에도 접근 제어를 검사한다. 다른 클래스의 private 필드를 읽는 바이트코드를 만나면 IllegalAccessError를 던지는 것이 원칙이다. 언어는 허용하는데 실행 환경은 금지하는 간극이 생긴다. 이 간극을 메우는 방식이 Java 11을 경계로 달라졌다.

    Java 10까지: 컴파일러가 몰래 만든 access$ 메서드

    JDK 21의 javac에 --release 8 옵션을 주면 Java 8용 클래스 파일을 만든다. 위의 Library를 이렇게 컴파일해 javap -p -c로 열면 소스에 없던 메서드가 보인다.

    Rule.print()는 totalBooks를 직접 읽지 않는다. 대신 Library.access$000()이라는 정적 메서드를 호출하고, 그 메서드가 Library 안에서 자기 클래스의 private 필드를 읽어 돌려준다. 반대 방향도 마찬가지여서 main의 rule.maxDays는 Library$Rule.access$100(rule) 호출로 바뀐다. 이 메서드들은 접근 제어자가 없는 패키지 접근 메서드다. 컴파일러가 private의 벽에 패키지 크기의 문을 내고 그 문으로 드나들게 만든 것이다.

    이 방식에는 대가가 있었다. 네스트 기반 접근 제어를 도입한 JEP 181은 이 다리 메서드들이 캡슐화를 약하게 만들고, 배포되는 프로그램의 크기를 조금 늘리며, 사용자와 도구를 혼란스럽게 한다고 적는다. 소스에서는 private인 필드가 클래스 파일 수준에서는 같은 패키지의 어떤 클래스든 access$000()을 호출해 읽을 수 있는 상태가 되기 때문이다. 리플렉션에서도 어긋남이 있었다. 소스에서는 되는 중첩 클래스 간 private 메서드 호출이 Method.invoke로는 거부되었다.

    Java 11부터: JVM이 네스트를 안다

    Java 11에 들어간 JEP 181은 JVM 자체에 네스트(nest)라는 개념을 넣었다. JVM 명세 §5.4.4의 정의로는 네스트는 서로의 private 멤버에 접근할 수 있는 클래스와 인터페이스의 집합이다. 그중 하나가 네스트 호스트(nest host)이고, 나머지는 네스트 멤버다. 같은 네스트에 속한 클래스들을 네스트메이트(nestmate)라 부른다. javac는 최상위 클래스를 호스트로, 그 안의 모든 중첩 클래스를 멤버로 기록한다.

    같은 Library를 옵션 없이 Java 21용으로 컴파일하면 access$ 메서드가 사라지고, 다른 클래스의 private 필드를 직접 읽는 명령이 그대로 들어간다. 클래스 파일 끝에는 두 클래스가 서로를 가리키는 속성이 붙는다.

    // Library$Rule.class 의 print()
      10: getstatic     #13                 // Field java/lang/System.out:Ljava/io/PrintStream;
      13: getstatic     #25                 // Field Library.totalBooks:I
      16: invokevirtual #19                 // Method java/io/PrintStream.println:(I)V

  Library$Rule

  static #37= #8 of #26;                  // Rule=class Library$Rule of class Library

    NestHost 속성은 "나는 Library가 호스트인 네스트에 속한다"는 멤버 쪽의 주장이다. NestMembers 속성은 "내 네스트에 속한다고 주장해도 되는 클래스는 이들이다"라는 호스트 쪽의 승인이다. JVM은 private 멤버에 대한 접근을 검사할 때 접근하는 클래스와 멤버를 선언한 클래스의 네스트 호스트를 각각 구해 같은지 비교한다. 이때 멤버의 주장만 믿지 않는다. 호스트의 NestMembers에 그 멤버의 이름이 실제로 올라 있고 둘이 같은 런타임 패키지에 있어야 인정한다. 한쪽만 주장하는 경우에는 그 클래스가 자기 혼자만의 네스트를 이루는 것으로 처리된다. 아무 클래스나 NestHost 속성을 달고 남의 private을 읽을 수는 없다는 뜻이다.

    명세가 정한 세부 하나를 더 보자. JVM은 클래스가 어느 네스트에 속하는지를 클래스를 로딩할 때가 아니라 접근 제어 검사를 하는 시점에 결정한다. 즉 클래스를 로딩했다고 해서 호스트 클래스를 찾아 확인하지는 않고, private 멤버에 대한 접근 제어 검사가 필요해졌을 때 확인한다. 다만 명세는 Java SE API의 일부 메서드가 그보다 먼저 네스트를 결정할 수 있고, 그때는 JVM이 그 결과를 따른다고 덧붙인다. 필요해질 때까지 일을 미루는 JVM의 일관된 태도가 여기에도 나타난다.

    InnerClasses 속성은 역할이 다르다. 이것은 소스 코드상의 중첩 관계를 적어 두는 기록이다. 어느 클래스의 멤버인지, 소스에서의 단순 이름이 무엇인지, 소스에서 static이나 private으로 선언되었는지가 들어 있다. 위 출력의 static이 그 표시다. JVM 명세는 이 속성의 접근 플래그 항목이 소스가 없을 때 컴파일러가 원래 정보를 복원하는 데 쓰인다고 설명하고, 오라클의 JVM 구현은 이 속성이 실제 클래스 파일과 일치하는지 검사하지 않는다고 덧붙인다. 접근 제어에 쓰이는 것은 NestHost와 NestMembers이고, InnerClasses는 컴파일러와 리플렉션을 위한 설명서다.

    같은 소스가 Java 11 이전에는 합성 다리 메서드를 거쳐, 이후에는 NestHost/NestMembers로 묶여 직접 private 필드를 읽는다는 차이를 좌우로 비교한다. 좌우 2분할 비교 다이어그램. 평면 벡터 스타일, 흰 배경. 왼쪽 패널 상단 제목 "Java 10까지", 오른쪽 패널 상단 제목 "Java 11부터". 각 패널에는 클래스 파일을 나타내는 둥근 사각형 두 개가 좌우로 놓인다. 왼쪽 상자 라벨 "Library.class", 오른쪽 상자 라벨 "Library$Rule.class". 왼쪽 패널: "Library.class" 상자 안에 자물쇠 아이콘과 함께 "private totalBooks", 그 아래에 작은 문 모양 아이콘과 "access$000()". "Library$Rule.class" 상자에서 나온 화살표가 문 아이콘 "access$000()"을 거쳐 "private totalBooks"로 꺾여 들어간다. 화살표 위 라벨 "다리 메서드 호출". 오른쪽 패널: 두 상자를 하나의 점선 테두리가 둘러싸고 테두리 위에 라벨 "같은 네스트". "Library.class" 상자 안에 "NestMembers", "Library$Rule.class" 상자 안에 "NestHost". "Library$Rule.class"에서 "private totalBooks"로 곧은 화살표가 직접 이어지고 화살표 위 라벨 "직접 접근". 왼쪽 패널의 화살표는 회색, 오른쪽 패널의 화살표는 초록색. Java 10까지는 컴파일러가 만든 패키지 접근 메서드를 거쳐야 했고, Java 11부터는 JVM이 같은 네스트의 private 접근을 직접 허용한다.

    정적 중첩 클래스의 활용: 한 클래스만 쓰는 부품을 안으로 넣기

    정적 중첩 클래스를 쓸 자리는 분명하다. 어떤 클래스가 다른 클래스 하나의 구현에만 쓰이고, 그 다른 클래스의 인스턴스 상태를 필요로 하지 않을 때다. 작업 이름을 쌓아 두는 간단한 스택을 예로 든다. 먼저 중첩 클래스를 쓰지 않은 형태다.

    // TaskStack.java
public class TaskStack {
    private Node top;
    private int size;
    // push, pop ...
}

// Node.java — 같은 패키지의 최상위 클래스
class Node {
    final String task;
    final Node next;

    Node(String task, Node next) {
        this.task = task;
        this.next = next;
    }
}

    동작에는 문제가 없지만 설계에는 세 가지 흠이 있다. 첫째, Node가 패키지 전체에 보인다. 같은 패키지의 다른 클래스가 Node를 가져다 쓰기 시작하면 TaskStack의 내부 구조를 바꿀 때 그 클래스들까지 고쳐야 한다. 둘째, Node라는 흔한 이름이 패키지의 이름 공간을 차지한다. 같은 패키지에 트리를 만들면서 또 다른 Node가 필요해지면 이름이 충돌한다. 셋째, TaskStack이 Node의 필드를 읽어야 하므로 필드를 private으로 만들 수 없다. 아래는 Node를 안으로 옮긴 형태다.

    public class TaskStack {
    private Node top;
    private int size;

    private static class Node {
        private final String task;
        private final Node next;

        private Node(String task, Node next) {
            this.task = task;
            this.next = next;
        }
    }

    public void push(String task) {
        top = new Node(task, top);
        size++;
    }

    public String pop() {
        if (top == null) {
            throw new IllegalStateException("empty");
        }
        String task = top.task;
        top = top.next;
        size--;
        return task;
    }

    public int size() {
        return size;
    }

    public static void main(String[] args) {
        TaskStack stack = new TaskStack();
        stack.push("compile");
        stack.push("test");
        stack.push("deploy");
        System.out.println(stack.pop());
        System.out.println(stack.pop());
        System.out.println(stack.size());
    }
}
    deploy
test
1

    Node는 이제 private이므로 TaskStack 바깥에서는 이름조차 쓸 수 없다. 필드와 생성자까지 모두 private이지만 TaskStack의 push와 pop은 new Node(...), top.task, top.next를 그대로 쓴다. 앞 절에서 본 네스트 규칙 덕분이다. 실행을 따라가 보면, push를 세 번 하고 나면 힙에는 Node 객체 세 개가 next 참조로 이어져 있다.

    push 세 번 뒤의 힙

TaskStack { top ─┐, size = 3 }
                 ▼
        Node { task → "deploy",  next ─┐ }
                                       ▼
                 Node { task → "test",    next ─┐ }
                                                ▼
                          Node { task → "compile", next = null }

Node 객체에는 task와 next 두 필드뿐이다. TaskStack을 가리키는 참조는 없다.

    첫 pop은 top이 가리키는 노드에서 "deploy"를 꺼내고 top을 다음 노드로 옮긴다. 둘째 pop은 "test"를 꺼낸다. 남은 것은 "compile" 하나이므로 size()는 1이다. 참조가 끊긴 두 노드는 어디에서도 도달할 수 없으므로 가비지 컬렉션 대상이 된다.

    Node에 static을 붙인 근거는 Node의 코드에 있다. Node는 TaskStack의 top이나 size를 한 번도 읽지 않는다. 노드는 자기가 어느 스택에 속하는지 알 필요가 없다. 바깥 인스턴스가 필요하지 않은 클래스에는 static을 붙이는 것이 기본이다. static을 빼면 어떻게 되는지는 내부 클래스를 본 뒤에 다시 따진다.

    JDK 자신도 이 형태를 널리 쓴다. JDK 21 소스에서 java.util.HashMap의 버킷에 들어가는 항목은 static class Node로, java.util.LinkedList의 노드는 private static class Node로 선언되어 있다. 4회에서 본 Integer의 캐시 배열을 쥐고 있는 IntegerCache는 private static final class다. Map.Entry는 인터페이스 안에 선언된 인터페이스여서 암묵적으로 static이다. 넷 모두 "바깥 타입의 구현이나 계약에 딸린 부품이지만 바깥 인스턴스를 가리킬 필요는 없는 타입"이다.

    초기화도 따로 일어난다

    중첩 클래스가 별개의 클래스라는 사실은 초기화 시점에서도 드러난다. JLS §12.4.1에 따르면 클래스는 그 클래스의 인스턴스를 만들거나, 그 클래스가 선언한 정적 메서드를 호출하거나, 상수가 아닌 정적 필드를 쓰는 등의 일이 처음 일어나기 직전에 초기화된다. 바깥 클래스가 초기화된다고 중첩 클래스가 함께 초기화된다는 조항은 없다.

    public class InitOrder {
    static {
        System.out.println("1. InitOrder 초기화");
    }

    static class Nested {
        static {
            System.out.println("3. Nested 초기화");
        }

        static void hello() {
            System.out.println("4. hello");
        }
    }

    public static void main(String[] args) {
        System.out.println("2. main 시작");
        Nested.hello();
    }
}
    1. InitOrder 초기화
2. main 시작
3. Nested 초기화
4. hello

    main을 실행하려면 InitOrder가 먼저 초기화되어야 하므로 1번이 찍힌다. 이때 Nested의 정적 초기화 블록은 실행되지 않는다. Nested.hello()가 처음 호출되기 직전에야 3번이 찍힌다. OpenJDK 21의 HotSpot에서 -Xlog:class+load 옵션으로 로딩 기록을 보면 InitOrder$Nested 클래스가 로딩되는 시점도 "2. main 시작"이 출력된 뒤다. 반대 방향도 독립적이다. 다른 클래스의 main에서 InitOrder.Nested.hello()만 호출하면 3번과 4번만 출력되고 InitOrder는 초기화되지 않는다. InitOrder의 인스턴스 생성, 정적 메서드 호출, 정적 필드 사용 가운데 어느 것도 일어나지 않았기 때문이다.

    이 성질은 무거운 준비 작업을 처음 필요해질 때까지 미루는 데 쓰인다. 준비 작업을 정적 중첩 클래스의 정적 필드나 정적 초기화 블록에 두면, 바깥 클래스가 아무리 일찍 쓰여도 그 중첩 클래스가 처음 쓰일 때까지 작업이 실행되지 않는다.

    내부 클래스: 바깥 인스턴스에 묶인 클래스

    이제 static을 뺀다. static 없이 클래스 본문에 선언한 클래스가 내부 클래스다. 정적 중첩 클래스가 클래스 변수의 자리에 선언한 클래스라면 내부 클래스는 인스턴스 변수의 자리에 선언한 클래스다. 인스턴스 변수가 객체마다 따로 있듯이, 내부 클래스의 인스턴스는 바깥 클래스의 특정 인스턴스 하나에 딸려 만들어진다.

    public class Office {
    private static int officeCount = 0;
    private final String city;

    public Office(String city) {
        this.city = city;
        officeCount++;
    }

    class Desk {
        private final int number;

        Desk(int number) {
            this.number = number;
        }

        void print() {
            System.out.println(number);        // 자신의 인스턴스 변수
            System.out.println(city);          // 바깥 인스턴스의 private 변수
            System.out.println(officeCount);   // 바깥 클래스의 private static 변수
        }
    }

    public static void main(String[] args) {
        Office seoul = new Office("Seoul");
        Office busan = new Office("Busan");

        Office.Desk d1 = seoul.new Desk(1);
        Office.Desk d2 = seoul.new Desk(2);
        Office.Desk d3 = busan.new Desk(1);

        d1.print();
        d2.print();
        d3.print();
        // Office.Desk d4 = new Desk(9);   // 컴파일 오류
    }
}

    정적 중첩 클래스와 달라진 점은 둘이다. 하나는 Desk.print()가 바깥 클래스의 인스턴스 변수 city를 아무 접두어 없이 읽는다는 것이다. 정적 중첩 클래스에서는 컴파일 오류였던 접근이다. 다른 하나는 객체를 만드는 문법이다. seoul.new Desk(1)처럼 new 앞에 바깥 객체의 참조를 적는다. 이 식은 "seoul이 가리키는 Office 객체에 딸린 Desk를 하나 만든다"는 뜻이다.

    실행 결과가 두 사실을 확인해 준다. d1과 d2는 둘 다 seoul에 딸려 만들었으므로 city를 읽으면 Seoul이 나오고, busan에 딸려 만든 d3는 Busan을 읽는다. 같은 메서드의 같은 코드 city가 객체에 따라 다른 Office의 필드를 읽은 것이다. 한 바깥 객체에 내부 객체를 여러 개 만들 수 있다는 것도 보인다. officeCount는 클래스 변수이므로 세 번 모두 2다. print()를 호출하기 전에 Office 객체가 이미 두 개 만들어졌기 때문이다.

    JLS §8.1.3은 이 관계에 이름을 붙인다. 내부 클래스의 인스턴스 i가 딸려 있는 바깥 클래스의 인스턴스를 i의 "직접 둘러싸는 인스턴스(immediately enclosing instance)"라 하고, 이것은 객체가 만들어질 때 결정된다. 이 회차에서는 줄여서 바깥 인스턴스라 부른다. 한번 정해진 바깥 인스턴스는 바꿀 수 없다. 그 이유는 다음 절에서 바이트코드로 확인한다.

    바깥 인스턴스가 정해지는 세 가지 경우

    바깥 인스턴스를 무엇으로 정하는지는 JLS §15.9.2가 규정한다. 식의 형태에 따라 셋으로 나뉜다.

    • 한정된 생성 식 seoul.new Desk(1): new 앞의 식이 가리키는 객체가 바깥 인스턴스가 된다. 바깥 클래스의 코드가 아닌 곳에서 내부 클래스 객체를 만들 때는 이 형태를 써야 한다.
    • 바깥 클래스의 인스턴스 메서드나 생성자 안의 new Desk(1): this.new Desk(1)의 줄임이다. 지금 실행 중인 메서드의 this가 바깥 인스턴스가 된다. 내부 클래스 객체는 대개 이 형태로 만든다.
    • 정적 문맥 안의 new Desk(9): 컴파일 오류다. 정적 메서드에는 this가 없으므로 바깥 인스턴스로 삼을 객체가 없다.

    예제에서 주석 처리한 마지막 줄이 셋째 경우다. 주석을 풀면 다음 오류가 난다. 소스에 this라는 글자가 없는데도 오류 문구에 this가 등장하는 것은 컴파일러가 new Desk(9)를 this.new Desk(9)로 해석하려 했기 때문이다.

    error: non-static variable this cannot be referenced from a static context

    한정된 생성 식에서 new 앞의 참조가 null이면 어떻게 될까. JLS §15.9.4는 이 경우 NullPointerException이 발생한다고 정한다. 바깥 인스턴스 없는 내부 클래스 객체는 정상적인 자바 코드로는 만들어지지 않는다.

    일상에서 가져온 비유지점 직원의 사원증

    본사 규정집은 어느 지점과도 무관하게 쓰이는 문서다. 정적 중첩 클래스가 이쪽이다. 지점 직원의 사원증에는 소속 지점이 찍혀 있어서, 직원이 "우리 지점 주소"라고 말하면 사원증에 찍힌 지점의 주소를 뜻한다. 내부 클래스 객체의 this$0가 그 소속란이다. 비유가 깨지는 지점도 있다. 현실의 직원은 전근을 갈 수 있지만 this$0는 final이어서 소속이 바뀌지 않는다. 또 지점은 소속 직원 명단을 갖고 있지만 바깥 객체는 내부 객체의 목록을 자동으로 갖지 않는다.

    내부 클래스 객체는 바깥 객체 안에 들어 있는 것이 아니라 힙에 따로 있으며, this$0 참조 하나로 바깥 객체와 이어진다는 것을 보여 준다. 평면 벡터 스타일의 메모리 구조도. 흰 배경. 왼쪽에 세로로 긴 영역, 상단 라벨 "스택 (main)". 그 안에 위에서부터 칸 다섯 개: "seoul", "busan", "d1", "d2", "d3". 오른쪽에 넓은 영역, 상단 라벨 "힙". 힙 영역의 위쪽에 큰 파란 상자 두 개가 좌우로 놓인다: 왼쪽 상자 제목 "Office", 안에 "city = Seoul"; 오른쪽 상자 제목 "Office", 안에 "city = Busan". 힙 영역의 아래쪽에 작은 주황 상자 세 개가 가로로 놓인다. 각 상자 제목은 "Desk"이고 안에 두 줄: "this$0", "number". 왼쪽 두 Desk 상자의 "this$0" 줄에서 왼쪽 위 Office(Seoul) 상자로 굵은 화살표가 각각 올라간다. 세 번째 Desk 상자의 "this$0" 줄에서 오른쪽 위 Office(Busan) 상자로 굵은 화살표가 올라간다. 스택의 "seoul", "busan" 칸에서 각각의 Office 상자로, "d1", "d2", "d3" 칸에서 각각의 Desk 상자로 가는 얇은 회색 화살표. Office 상자에서 Desk 상자로 내려오는 화살표는 그리지 않는다. 그림 아래쪽에 작은 글씨 라벨 "참조는 Desk → Office 한 방향". Desk 객체 셋은 힙에 따로 있고, 각자의 this$0가 자기를 만든 Office 객체를 가리킨다. 참조는 안쪽에서 바깥쪽으로만 나 있다.

    부모 생성자보다 먼저 저장되는 this$0

    생성자 바이트코드에서 순서가 눈에 띈다. this$0에 값을 넣는 putfield가 부모 생성자 호출보다 앞에 있다. 자바 소스에서는 super() 호출 앞에 필드 대입을 쓸 수 없지만, JVM 명세는 현재 클래스가 선언한 인스턴스 필드에 한해 다른 생성자를 호출하기 전에 putfield로 대입하는 것을 허용한다(JVMS §4.9.2). javac는 이 허용 범위를 이용한다. 순서가 왜 중요한지는 부모 생성자가 재정의된 메서드를 호출하는 경우에 드러난다.

    public class Early {
    private String label = "outer-label";

    static class Base {
        Base() {
            System.out.println("Base 생성자: " + describe());
        }

        String describe() {
            return "base";
        }
    }

    class Child extends Base {
        private String own = "own-field";

        @Override
        String describe() {
            return label + " / " + own;
        }
    }

    public static void main(String[] args) {
        Early early = new Early();
        Child child = early.new Child();
        System.out.println("생성 후: " + child.describe());
    }
}
    Base 생성자: outer-label / null
생성 후: outer-label / own-field

    Base의 생성자가 실행되는 시점에 Child의 필드 초기화는 아직 실행되지 않았다. 그래서 own은 기본값 null이다. 그런데 같은 시점에 바깥 인스턴스의 label은 정상적으로 읽힌다. this$0가 부모 생성자 호출 전에 이미 저장되었기 때문이다. 만약 this$0가 다른 필드처럼 부모 생성자 뒤에 저장되었다면 describe() 안의 label은 null인 this$0를 따라가다 NullPointerException을 냈을 것이다. 다만 이 예제는 원리를 보이기 위한 것이다. 생성자 안에서 재정의 가능한 메서드를 호출하면 own처럼 아직 초기화되지 않은 필드가 드러나므로 실제 코드에서는 피해야 한다.

    쓰지 않는 this$0는 생략된다 (JDK 18 이후)

    내부 클래스가 바깥 인스턴스를 전혀 쓰지 않으면 어떻게 될까. JDK 17까지의 javac는 쓰이든 말든 모든 내부 클래스에 this$0 필드를 만들었다. JDK 18 릴리스 노트에 따르면 JDK 18부터 javac는 바깥 인스턴스를 참조하는 내부 클래스에만 이 필드를 만들고, 쓰이지 않는 경우에는 생략한다. 생성자가 바깥 인스턴스를 인자로 받는 형태는 달라지지 않으며, java.io.Serializable을 구현한 클래스는 이 변경의 영향을 받지 않는다고 되어 있다.

    앞의 TaskStack에서 Node의 static을 지우면 이 차이를 볼 수 있다. JDK 21로 컴파일하면 TaskStack$Node에 this$0 필드는 없지만 생성자는 (TaskStack, String, TaskStack$Node)로 바뀐다. --release 17로 컴파일하면 필드까지 생겨서 모든 노드가 자기를 만든 스택을 가리키는 참조를 하나씩 더 갖는다. 어느 쪽이든 소스는 "노드는 스택 인스턴스에 딸려 있다"고 말하고 있는데 실제로는 그렇지 않다. 컴파일러의 최적화가 메모리 낭비를 줄여 주더라도, 바깥 인스턴스가 필요 없는 클래스에 static을 붙여 의도를 밝히는 일은 여전히 작성자의 몫이다.

    내부 클래스의 활용: 바깥 객체의 상태를 읽는 부품

    내부 클래스를 쓸 자리는 정적 중첩 클래스와 한 가지가 다르다. 한 클래스의 구현에만 쓰이는 부품이라는 점은 같고, 그 부품이 바깥 인스턴스의 상태를 읽거나 바꿔야 한다는 점이 다르다. 문자 배열을 감싼 버퍼와, 그 버퍼를 한 글자씩 읽어 나가는 커서로 예를 든다. 먼저 두 클래스를 따로 둔 형태다.

    public class TextBuffer {
    private final char[] chars;
    private int readCount;      // 이 버퍼에서 읽힌 글자 수의 합

    public TextBuffer(String text) {
        this.chars = text.toCharArray();
    }

    // TextCursor를 위해 열어 둔 메서드들
    public int length() { return chars.length; }
    public char charAt(int index) { return chars[index]; }
    public void increaseReadCount() { readCount++; }

    public int readCount() { return readCount; }
}

public class TextCursor {
    private final TextBuffer buffer;   // 어느 버퍼를 읽는지 직접 들고 있다
    private int pos;

    public TextCursor(TextBuffer buffer) {
        this.buffer = buffer;
    }

    public boolean hasNext() {
        return pos < buffer.length();
    }

    public char next() {
        buffer.increaseReadCount();
        return buffer.charAt(pos++);
    }
}

    TextCursor가 일을 하려면 버퍼의 길이와 글자를 읽고 읽은 횟수를 올려야 한다. 그래서 TextBuffer는 메서드 셋을 public으로 열었다. 그중 increaseReadCount()가 문제다. 커서만 호출해야 하는 메서드인데 이제 어떤 코드든 호출해 통계를 틀리게 만들 수 있다. 커서 하나를 위해 연 문으로 모두가 드나들 수 있게 된 것이다. 아래는 커서를 내부 클래스로 옮긴 형태다.

    public class TextBuffer {
    private final char[] chars;
    private int readCount;

    public TextBuffer(String text) {
        this.chars = text.toCharArray();
    }

    public class Cursor {
        private int pos;

        public boolean hasNext() {
            return pos < chars.length;   // 바깥 인스턴스의 private 필드
        }

        public char next() {
            readCount++;                 // 바깥 인스턴스의 private 필드를 변경
            return chars[pos++];
        }
    }

    public Cursor cursor() {
        return new Cursor();             // this.new Cursor()
    }

    public int readCount() {
        return readCount;
    }
}
    public class TextBufferMain {
    public static void main(String[] args) {
        TextBuffer a = new TextBuffer("AB");
        TextBuffer b = new TextBuffer("xyz");

        TextBuffer.Cursor c1 = a.cursor();
        TextBuffer.Cursor c2 = a.new Cursor();
        TextBuffer.Cursor c3 = b.new Cursor();

        System.out.println(c1.next());
        System.out.println(c1.next());
        System.out.println(c1.hasNext());
        System.out.println(c2.next());
        System.out.println(c3.next());

        System.out.println("a.readCount = " + a.readCount());
        System.out.println("b.readCount = " + b.readCount());
    }
}

false

x
a.readCount = 3
b.readCount = 1

    길이와 글자와 횟수를 위해 열었던 메서드 셋이 사라졌다. Cursor가 chars와 readCount를 직접 다루기 때문이다. TextBuffer가 바깥에 공개하는 것은 cursor()와 readCount()뿐이다. 커서를 얻는 방법은 둘 다 썼다. a.cursor()는 TextBuffer의 인스턴스 메서드 안에서 new Cursor()를 실행하므로 this, 곧 a가 바깥 인스턴스가 된다. a.new Cursor()는 같은 일을 바깥에서 직접 한 것이다. 보통은 앞의 형태처럼 바깥 클래스가 생성 메서드를 제공해 .new 문법이 호출하는 쪽에 드러나지 않게 한다.

    실행을 추적하자. c1.next()는 a의 readCount를 1로 올리고 'A'를 돌려준 뒤 c1의 pos를 1로 만든다. 한 번 더 호출하면 readCount는 2, 반환값은 'B', pos는 2다. c1.hasNext()는 2 < 2이므로 false다. c2는 같은 버퍼 a에 딸려 있지만 자기만의 pos를 가지므로 처음부터 읽어 'A'를 돌려주고 a의 readCount를 3으로 올린다. c3는 b에 딸려 있으므로 'x'를 읽고 b의 readCount를 1로 올린다.

    실행을 마친 시점의 힙

a  ───▶ [TextBuffer @A]  chars → ['A','B']       readCount = 3
b  ───▶ [TextBuffer @B]  chars → ['x','y','z']   readCount = 1

c1 ───▶ [TextBuffer$Cursor]  this$0 → @A   pos = 2
c2 ───▶ [TextBuffer$Cursor]  this$0 → @A   pos = 1
c3 ───▶ [TextBuffer$Cursor]  this$0 → @B   pos = 1

커서마다 다른 상태(pos)는 Cursor 객체에, 커서들이 함께 쓰는 상태(chars, readCount)는 TextBuffer 객체에 있다.

    두 형태를 나란히 놓으면 내부 클래스가 무엇을 대신해 주는지가 보인다. 분리된 TextCursor에는 private final TextBuffer buffer 필드와 그것을 받는 생성자가 있었다. 내부 클래스 Cursor에서는 그 필드가 this$0로, 생성자 매개변수가 숨은 첫 매개변수로 바뀌었을 뿐 구조는 같다. 내부 클래스는 "다른 객체의 참조를 필드로 들고 그 객체와 협력하는 클래스"를 쓰는 한 가지 방식이다. 컴파일러가 참조를 저장하고 따라가는 코드를 대신 써 주고, 언어가 private 접근을 허용해 준다.

    JDK의 컬렉션이 이 구조의 대표적인 사용처다. JDK 21 소스에서 java.util.ArrayList는 iterator()가 돌려주는 반복자를 private class Itr이라는 내부 클래스로 구현한다. Itr은 다음에 돌려줄 위치 cursor를 자기 필드로 갖고, 리스트의 size와 elementData, modCount는 바깥 인스턴스의 것을 직접 읽는다. 방금 만든 Cursor와 같은 구조다. 한 리스트에서 반복자를 여러 개 얻어도 서로의 위치가 섞이지 않는 것, 반복자가 자기를 만든 리스트의 변경을 알아채는 것이 모두 이 구조에서 나온다. 컬렉션의 내부는 다음 권에서 다룬다.

    같은 이름의 바깥 변수 접근: 섀도잉과 한정된 this

    내부 클래스의 메서드 안에서는 세 겹의 변수가 한꺼번에 보인다. 메서드의 지역 변수와 매개변수, 내부 클래스 자신의 필드, 바깥 클래스의 필드다. 이름이 서로 다르면 문제가 없다. 이름이 같으면 어느 것이 선택되는지 규칙을 알아야 한다.

    public class Building {
    private String name = "building";

    class Room {
        private String name = "room";

        void print(String name) {
            System.out.println(name);                 // 매개변수
            System.out.println(this.name);            // Room 객체의 필드
            System.out.println(Building.this.name);   // 바깥 Building 객체의 필드
        }

        class Locker {
            private String name = "locker";

            void print() {
                System.out.println(name);
                System.out.println(Room.this.name);
                System.out.println(Building.this.name);
            }
        }
    }

    public static void main(String[] args) {
        Building building = new Building();
        Building.Room room = building.new Room();
        room.print("parameter");

        Building.Room.Locker locker = room.new Locker();
        locker.print();
    }
}

    규칙의 이름은 섀도잉(shadowing)이다. JLS §6.4.1에 따르면 어떤 이름의 변수 선언은 자기 유효 범위 안에서, 그 지점에서 보이던 같은 이름의 다른 변수 선언을 가린다. 가려진 변수는 없어진 것이 아니라 단순 이름만으로는 가리킬 수 없게 된 것이다. 안쪽 선언이 바깥쪽 선언을 가리므로 단순 이름 name은 언제나 가장 가까운 선언을 뜻한다. Room.print 안에서는 매개변수가 Room의 필드를 가리고, Room의 필드가 Building의 필드를 가린다.

    가려진 변수를 쓰려면 "누구의 것인지"를 밝혀야 한다. this.name은 현재 객체, 곧 Room 객체의 필드다. 기본편에서 생성자 매개변수와 필드 이름이 같을 때 쓰던 바로 그 방법이다. 바깥 객체의 필드는 Building.this.name으로 쓴다. 클래스이름.this 형태를 한정된 this(qualified this)라 하고, JLS §15.8.4는 그 값을 "그 이름의 클래스에 해당하는 바깥 인스턴스"로 정의한다. Building.this는 Building 클래스의 정적 멤버를 뜻하는 것이 아니다. 지금 이 Room 객체가 딸려 있는 특정 Building 객체를 가리키는 참조다.

    컴파일 결과를 보면 한정된 this의 정체가 분명해진다. Room.print의 셋째 줄은 다음과 같다.

          20: aload_0
      21: getfield      #1                  // Field this$0:LBuilding;
      24: getfield      #31                 // Field Building.name:Ljava/lang/String;

    Building.this는 this.this$0다. 앞 절에서 단순 이름 city가 컴파일된 모양과 똑같다. 즉 이름이 겹치지 않을 때 컴파일러가 알아서 붙여 주던 바깥클래스.this.를, 이름이 겹칠 때는 사람이 직접 써 주는 것뿐이다.

    세 겹으로 중첩되면: this$1에서 this$0로

    예제의 Locker는 내부 클래스 Room 안의 내부 클래스다. Locker 객체의 바깥 인스턴스는 Room 객체이고, 그 Room 객체의 바깥 인스턴스가 Building 객체다. 그래서 room.new Locker()처럼 Room 객체를 통해 만든다. Locker.print에서 Room.this.name과 Building.this.name이 어떻게 컴파일되는지 보자.

          13: aload_0
      14: getfield      #1                  // Field this$1:LBuilding$Room;
      17: getfield      #31                 // Field Building$Room.name:Ljava/lang/String;
      ...
      26: aload_0
      27: getfield      #1                  // Field this$1:LBuilding$Room;
      30: getfield      #34                 // Field Building$Room.this$0:LBuilding;
      33: getfield      #38                 // Field Building.name:Ljava/lang/String;

    Locker의 숨은 필드는 이름이 this$1이고 타입은 Building$Room이다. javac는 중첩 깊이에 따라 숫자를 붙인다. Locker 객체는 Building 객체를 직접 가리키지 않는다. Building.this.name은 this$1로 Room 객체에 간 다음, 그 Room의 this$0로 Building 객체에 가서 name을 읽는다. 바깥 인스턴스들은 안쪽에서 바깥쪽으로 한 칸씩 이어진 사슬이고, 한정된 this는 그 사슬을 몇 칸 따라갈지를 클래스 이름으로 지정하는 문법이다. JLS가 이를 "n번째로 둘러싸는 인스턴스"라고 번호로 정의하는 까닭이다.

    locker ──▶ [Locker]  name → "locker"
              │ this$1
              ▼
           [Room]    name → "room"            ← Room.this
              │ this$0
              ▼
           [Building] name → "building"       ← Building.this

Locker 안에서:  name / this.name     → 0칸
               Room.this.name       → 1칸 (this$1)
               Building.this.name   → 2칸 (this$1 → this$0)
    세 겹으로 중첩된 내부 클래스에서 name, Room.this.name, Building.this.name이 각각 사슬의 몇 번째 객체에서 값을 읽는지 보여 준다. 세로 방향 참조 사슬 다이어그램. 평면 벡터 스타일, 흰 배경. 위에서 아래로 둥근 사각형 세 개가 일정한 간격으로 놓인다. 맨 위 상자 제목 "Locker", 안에 "name = locker". 가운데 상자 제목 "Room", 안에 "name = room". 맨 아래 상자 제목 "Building", 안에 "name = building". 맨 위 상자에서 가운데 상자로 내려가는 굵은 화살표, 화살표 옆 라벨 "this$1". 가운데 상자에서 맨 아래 상자로 내려가는 굵은 화살표, 화살표 옆 라벨 "this$0". 오른쪽에는 세 개의 말풍선형 꼬리표가 각 상자를 가리킨다: 맨 위 상자를 가리키는 꼬리표 "name", 가운데 상자를 가리키는 꼬리표 "Room.this.name", 맨 아래 상자를 가리키는 꼬리표 "Building.this.name". 세 상자는 위에서부터 연한 주황, 주황, 파랑으로 칠한다. 장식 없이 도형과 글자만. 바깥 인스턴스는 한 칸씩 이어진 사슬이다. 한정된 this는 사슬을 어디까지 따라갈지를 클래스 이름으로 지정한다.

    메서드 이름이 겹칠 때: 인자가 달라도 안쪽이 이긴다

    메서드는 변수보다 규칙이 까다롭다. 내부 클래스 안에서 log(404)처럼 메서드를 단순 이름으로 호출하면, 컴파일러는 먼저 "그 이름의 메서드를 멤버로 가진 가장 안쪽 클래스"를 하나 정한다. 그리고 그 클래스 안에서만 매개변수가 맞는 메서드를 찾는다(JLS §15.12.1). 안쪽 클래스에 이름만 같고 매개변수가 다른 메서드가 있으면, 바깥 클래스에 정확히 맞는 메서드가 있어도 거기까지 찾아가지 않는다.

    public class Printer {
    void log(int code) {
        System.out.println("printer log " + code);
    }

    class Job {
        void log(String message) {
            System.out.println("job log " + message);
        }

        void run() {
            log(404);                  // 컴파일 오류
            // Printer.this.log(404);  // 이렇게 써야 한다
        }
    }
}
    error: incompatible types: int cannot be converted to String
            log(404);
                ^

    오류 문구가 단서다. 컴파일러는 Printer.log(int)를 후보로 올리지 않았고, Job.log(String)에 int를 넘기려다 실패했다. Job이 부모 클래스에서 상속받은 메서드도 Job의 멤버이므로 같은 일이 생긴다. 내부 클래스가 어떤 클래스를 상속하고 있고 그 부모에 우연히 같은 이름의 메서드가 있으면, 바깥 클래스의 메서드를 부르려던 호출이 부모의 메서드로 향하거나 컴파일 오류가 된다. 필드도 마찬가지로, 내부 클래스가 상속받은 필드가 바깥 클래스의 같은 이름 필드를 가린다. 바깥 것을 뜻한다면 Printer.this.log(404)처럼 한정된 this를 쓴다.

    이 절의 실무적 결론은 간단하다. 안팎에 같은 이름을 두지 않는 것이 가장 좋다. 이름이 겹치면 읽는 사람이 매번 섀도잉 규칙을 떠올려야 하고, 나중에 안쪽 클래스에 필드나 메서드 하나를 추가한 것만으로 기존 코드의 의미가 조용히 바뀔 수 있다. 피할 수 없을 때는 단순 이름에 기대지 말고 this.와 바깥클래스.this.를 적어 의도를 드러낸다.

    흔한 오해와 함정

    "내부 클래스는 바깥 클래스를 상속한다"

    중첩과 상속은 관계가 없다. Office.Desk는 Office의 하위 타입이 아니므로 Office 타입 변수에 Desk 객체를 넣을 수 없고, Desk 객체 안에 city 필드가 들어 있지도 않다. 앞의 javap 출력에서 Desk의 생성자가 호출한 부모 생성자는 Object의 것이었다. 바깥 클래스의 멤버를 이름만으로 쓸 수 있어서 상속처럼 보일 뿐이고, 실제로는 this$0를 거친 다른 객체에 대한 접근이다. private 멤버까지 보이는 것도 상속으로는 설명되지 않는다. 상속받은 클래스는 부모의 private 멤버에 접근하지 못한다.

    "내부 클래스에는 static 멤버를 둘 수 없다"

    Java 15까지는 맞는 말이었다. 내부 클래스는 상수 변수를 제외한 static 멤버를 선언할 수 없었고, 선언하면 Illegal static declaration in inner class라는 컴파일 오류가 났다. 이 제한은 레코드를 정식 기능으로 넣은 JEP 395에서 풀렸다. JLS §8.1.3은 Java 16부터 내부 클래스가 static 멤버와 정적 초기화 블록을 선언할 수 있다고 적는다. 오래된 자료에는 예전 규칙이 그대로 남아 있는 경우가 많으니 기준 버전을 확인해야 한다.

    내부 객체가 바깥 객체를 붙잡는다

    가비지 컬렉터는 도달할 수 있는 객체를 살려 둔다. 내부 클래스 객체가 this$0를 갖고 있으면, 그 내부 객체에 도달할 수 있는 동안에는 바깥 객체에도 도달할 수 있다. 내부 객체를 메서드 밖으로 돌려주거나 오래 사는 컬렉션, 정적 필드, 다른 스레드에 넘기면 바깥 객체의 수명이 내부 객체의 수명만큼 늘어난다. 바깥 객체가 큰 배열이나 많은 객체를 쥐고 있다면 작은 내부 객체 하나가 그 전부를 메모리에 남겨 둔다. 내부 객체가 바깥 객체보다 오래 살아야 하는 구조라면 내부 클래스가 맞는 선택인지 다시 따져야 한다. 바깥 인스턴스의 상태가 필요 없다면 정적 중첩 클래스로 바꾸고, 일부만 필요하다면 필요한 값만 생성자로 넘긴다.

    인자 없는 생성자가 없다

    내부 클래스에 Desk() {}처럼 매개변수 없는 생성자를 선언해도 클래스 파일의 생성자는 (Office)를 받는다. 그래서 리플렉션으로 getDeclaredConstructor()를 호출해 인자 없는 생성자를 찾으면 NoSuchMethodException이 난다. 정적 중첩 클래스에서는 같은 호출이 성공한다. 인자 없는 생성자로 객체를 만들어 값을 채우는 방식의 도구에 넘길 클래스를 중첩해서 선언할 때 static을 빠뜨리면 안 되는 이유다.

    내부 클래스를 다른 클래스가 상속하는 것도 가능하지만, 하위 클래스의 생성자가 부모의 바깥 인스턴스를 직접 지정해야 한다. Sub(Outer o) { o.super(); }처럼 super 앞에 바깥 객체를 적는 문법(JLS §8.8.7.1)이 이를 위한 것이다. 생략하면 an enclosing instance that contains Outer.Inner is required라는 컴파일 오류가 난다. 실제로 쓸 일은 드물지만, 내부 클래스의 생성자가 언제나 바깥 인스턴스를 요구한다는 원리를 확인해 주는 문법이다. 또한 오라클의 자바 튜토리얼은 컴파일러가 만들어 넣는 합성 요소가 컴파일러 구현마다 다를 수 있다는 이유로 내부 클래스의 직렬화를 강하게 말린다.

    무엇을 고를 것인가, 그리고 이 지식이 쓰이는 곳

    지금까지의 내용을 선택 절차로 정리한다. 판단의 근거는 문법이 아니라 두 가지 질문이다. 이 클래스를 누가 쓰는가, 그리고 이 클래스가 바깥 인스턴스의 상태를 필요로 하는가.

    셋째 단계에서 static을 기본으로 삼는 근거는 앞에서 모두 나왔다. 정적 중첩 클래스는 숨은 참조가 없으므로 바깥 객체의 수명에 영향을 주지 않는다. 바깥 인스턴스 없이 어디서든 만들 수 있고, 리플렉션으로 다루기도 쉽다. 나중에 바깥 인스턴스가 필요해지면 static을 지우는 것은 쉽지만, 내부 클래스에서 static을 붙이려면 바깥 멤버를 쓰던 코드를 모두 고쳐야 한다.

    이 회차의 지식은 뒤에서 여러 번 다시 쓰인다. 다음 회차의 지역 클래스와 익명 클래스는 바깥 인스턴스에 더해 메서드의 지역 변수까지 붙잡는다. this$0라는 숨은 필드를 이해했다면 지역 변수를 붙잡는 방식도 같은 원리의 연장으로 읽힌다. 다음 권의 컬렉션에서는 HashMap의 Node, ArrayList의 Itr처럼 여기서 이름만 본 중첩 클래스들의 내부를 직접 읽게 된다. 리플렉션, 그리고 리플렉션으로 객체를 만드는 프레임워크를 다룰 때는 "내부 클래스의 생성자는 바깥 인스턴스를 받는다"는 사실이 오류의 원인을 찾는 단서가 된다. 스택 트레이스나 힙 덤프에서 Outer$Inner, Outer$1 같은 이름을 만났을 때 그것이 소스의 어느 선언인지 되짚는 데에도 이 회차의 이름 규칙이 쓰인다.
    중첩 클래스와 내부 클래스
    다른 클래스의 본문 안에 선언된 클래스가 중첩 클래스이고, 그중 static이 아닌 것이 내부 클래스다. 정적 중첩 클래스는 위치만 안쪽이고, 내부 클래스는 인스턴스까지 바깥 인스턴스에 묶인다.
    컴파일 결과
    중첩 클래스는 Outer$Inner.class처럼 이름에 $가 들어간 독립된 클래스 파일이 된다. JVM은 이들을 따로 로딩하고 따로 초기화한다.
    정적 중첩 클래스의 접근 범위
    바깥 클래스의 정적 멤버에는 접근할 수 있고 인스턴스 멤버에는 직접 접근할 수 없다. 가리킬 바깥 인스턴스가 없기 때문이며, 정적 메서드에서 인스턴스 변수를 쓸 수 없는 것과 같은 이유다.
    private의 경계
    언어 수준에서 private은 최상위 클래스의 본문 전체에서 접근할 수 있다. 바깥과 중첩, 중첩끼리 서로의 private 멤버를 읽을 수 있다.
    네스트 기반 접근 제어
    Java 11부터 JVM은 NestHost와 NestMembers 속성이 서로를 지목하는 클래스들을 같은 네스트로 보고 private 접근을 직접 허용한다. 그 전에는 javac가 access$000 같은 패키지 접근 메서드를 만들어 우회했다.
    this$0와 숨은 생성자 매개변수
    내부 클래스 객체는 바깥 객체의 참조를 final 합성 필드에 담고, 생성자의 첫 매개변수로 그 참조를 받는다. outer.new Inner()는 new Outer$Inner(outer)로 컴파일된다.
    섀도잉과 한정된 this
    같은 이름이면 가장 안쪽 선언이 선택된다. this.x는 현재 객체의 필드, Outer.this.x는 바깥 인스턴스의 필드이고, 후자는 this.this$0.x로 컴파일된다.
    선택 기준
    한 클래스에만 딸린 부품이면 중첩하고, 바깥 인스턴스의 상태가 필요하지 않으면 static을 붙인다. 내부 클래스는 바깥 객체를 붙잡으므로 수명을 함께 따져야 한다.

    실무에서 중첩 클래스를 두고 내리는 판단은 대부분 "static을 붙일 것인가" 하나로 모인다. 기본값은 붙이는 쪽이다. 응답 객체 안의 항목 타입, 빌더, 캐시의 엔트리, 자료 구조의 노드처럼 바깥 타입에 딸린 데이터 묶음은 거의 모두 바깥 인스턴스가 필요 없다. 여기서 static을 빠뜨리면 당장은 동작하지만, 그 클래스를 인자 없는 생성자로 만들려는 도구에서 실패하거나 정적 메서드 안에서 생성하려다 "non-static variable this" 오류를 만나게 된다. 이 오류 문구를 보면 내부 클래스의 생성 식이 숨은 this를 요구한다는 사실부터 떠올리면 된다.

    내부 클래스가 맞는 선택이 되는 조건은 좁다. 안쪽 객체가 바깥 객체의 비공개 상태를 읽고 바꿔야 하고, 안쪽 객체의 수명이 바깥 객체의 수명 안에 들어 있을 때다. 컬렉션의 반복자나 뷰가 그 예다. 조건의 뒤쪽이 깨지면 판단이 달라진다. 내부 클래스로 만든 리스너나 작업 객체를 오래 사는 레지스트리나 스레드 풀의 큐에 등록하면, 등록이 해제될 때까지 바깥 객체 전체가 회수되지 않는다. 힙 덤프에서 예상보다 오래 살아 있는 객체를 추적하다가 this$0라는 필드를 타고 올라가는 참조 경로를 만난다면 이 경우다. 해결은 필요한 값만 넘겨받는 정적 중첩 클래스로 바꾸거나 등록 해제를 보장하는 것이다.

    클래스 파일 수준의 지식은 버전이 섞일 때 쓸모가 있다. Java 8 대상으로 빌드된 라이브러리의 스택 트레이스에 소스에 없는 access$000 같은 프레임이 끼어 있는 것은 컴파일러가 만든 다리 메서드 때문이다. Java 11 이상으로 대상 버전을 올리면 이 메서드들이 사라지고, 대신 중첩 클래스 사이의 private 접근이 네스트 속성에 의존하게 된다. 바이트코드를 직접 만들거나 고치는 도구가 NestHost와 NestMembers를 맞추지 않으면 실행 중에 IllegalAccessError가 날 수 있다는 것도 같은 규칙의 결과다.

Office 객체 2개, Desk 객체 3개가 있다. seoul = null을 실행해도 "Seoul" Office 객체는 가비지 컬렉션 대상이 아니다. 스택의 d1에서 Desk 객체로, 그 객체의 this$0에서 Office 객체로 이어지는 경로가 남아 있기 때문이다. d2를 통한 경로도 있다. 이 Desk는 print()에서 city를 읽으므로 JDK 18 이후에도 this$0 필드가 생략되지 않는다. d1과 d2까지 null로 만들면 두 Desk 객체에 도달할 경로가 없어지고, 따라서 "Seoul" Office 객체에 도달할 경로도 없어져 셋 모두 회수 대상이 된다. 실제로 언제 회수되는지는 가비지 컬렉터가 정하므로 실행마다 다를 수 있다.

    5. 바꾸기 전의 Node는 내부 클래스이므로 어느 JDK로 빌드하든 생성자가 리스트 객체를 숨은 첫 매개변수로 받는다. JDK 17로 빌드하면 여기에 더해 모든 Node 객체가 this$0 필드를 갖고 자기를 만든 리스트를 가리킨다. 노드 수만큼 참조 필드가 더 생기고, 노드 하나라도 리스트 밖에서 살아 있으면 리스트 전체가 회수되지 않는다. JDK 21로 빌드하면 Node가 바깥 인스턴스를 쓰지 않으므로 this$0 필드는 생략되지만 생성자의 숨은 매개변수는 그대로다. 두 경우 모두 소스는 "노드는 특정 리스트 인스턴스에 딸려 있다"고 말하는데 실제 코드는 그 관계를 쓰지 않는다. static을 붙이면 의도가 선언에 드러나고, 정적 메서드에서도 노드를 만들 수 있으며, 빌드에 쓰는 JDK 버전에 따라 객체 구조가 달라지는 일이 없어진다.

     Java 21로 컴파일한 내부 클래스의 메서드가 바깥 객체의 private 인스턴스 필드를 읽을 수 있는 이유로 옳은 것은? 내부 클래스가 바깥 클래스를 상속하므로 부모의 필드를 물려받기 때문이다. 컴파일러가 바깥 객체의 필드 값을 내부 객체 안에 복사해 두기 때문이다. 내부 객체가 this$0 필드로 바깥 객체를 가리키고, JVM이 같은 네스트에 속한 클래스 사이의 private 접근을 허용하기 때문이다. 컴파일 과정에서 바깥 클래스의 private 필드가 public으로 바뀌기 때문이다. 내부 클래스의 코드는 this$0에 담긴 참조를 따라가 바깥 객체의 필드를 getfield로 직접 읽는다. 두 클래스는 NestHost/NestMembers로 같은 네스트임이 확인되므로 JVM의 접근 검사를 통과한다. 중첩은 상속이 아니며 상속받은 클래스는 오히려 부모의 private에 접근하지 못한다. 값이 복사된다면 바깥 필드의 변경이 내부에서 보이지 않을 텐데, 본문의 readCount 예제처럼 내부에서 바꾼 값이 바깥 객체에 그대로 반영된다. 필드의 접근 제어자는 클래스 파일에서도 private 그대로다. 바깥 클래스 Office의 static 메서드 main 안에서 내부 클래스 객체를 new Desk(9)로 만들려 하면 "non-static variable this cannot be referenced from a static context" 오류가 난다. 이유로 옳은 것은? 내부 클래스는 public으로 선언해야만 new로 생성할 수 있기 때문이다. new Desk(9)는 this.new Desk(9)의 줄임인데, 정적 문맥에는 this가 없어 바깥 인스턴스로 삼을 객체를 정할 수 없기 때문이다. 내부 클래스 객체는 바깥 클래스의 코드 밖에서만 만들 수 있기 때문이다. main이 실행되는 동안에는 Office 클래스의 초기화가 끝나지 않았기 때문이다. 내부 클래스의 생성자는 바깥 인스턴스를 첫 인자로 받아야 한다. 한정하지 않은 생성 식은 현재 메서드의 this를 그 인자로 쓰는데 정적 메서드에는 this가 없다. 오류 문구에 소스에 없는 this가 나오는 것이 그 때문이다. 접근 제어자와는 무관하고, 바깥 클래스의 인스턴스 메서드 안에서는 같은 식이 문제없이 컴파일된다. 클래스 초기화는 main 실행 전에 끝난다. 연결 리스트의 노드 클래스를 내부 클래스가 아니라 정적 중첩 클래스로 선언하는 근거로 가장 적절한 것은? 노드의 코드가 리스트 인스턴스의 멤버를 쓰지 않으므로 노드 객체를 특정 리스트 인스턴스에 묶을 이유가 없다. static을 붙여야 노드 객체를 여러 개 만들 수 있다. static이 아니면 리스트 클래스가 노드의 private 필드에 접근할 수 없다. 정적 중첩 클래스의 객체는 힙이 아닌 곳에 만들어져 가비지 컬렉션의 대상이 되지 않는다. static 여부를 가르는 기준은 바깥 인스턴스가 필요한가다. 필요 없는데 내부 클래스로 두면 생성자가 불필요한 바깥 참조를 받고, 컴파일러 버전에 따라서는 객체마다 참조 필드가 하나씩 더 생긴다. 내부 클래스도 객체를 여러 개 만들 수 있고, private 접근은 static 여부와 무관하게 같은 최상위 클래스 안이면 허용된다. 정적 중첩 클래스의 객체도 보통 객체와 똑같이 힙에 만들어지고 회수된다. Building 안에 내부 클래스 Room이, Room 안에 내부 클래스 Locker가 있다. Locker의 메서드에서 쓴 Building.this.name은 어떻게 실행되는가? Building 클래스의 정적 필드 name을 읽는다. 새 Building 객체를 만들고 그 객체의 name을 읽는다. Locker 객체가 Building 객체를 직접 가리키는 숨은 필드 하나를 따라가 name을 읽는다. Locker의 숨은 필드로 Room 객체에 간 뒤, 그 Room 객체의 숨은 필드로 Building 객체에 가서 name을 읽는다. 내부 클래스 객체는 자기 바로 바깥의 인스턴스만 가리킨다. Locker는 this$1으로 Room을, Room은 this$0로 Building을 가리킨다. 한정된 this는 이 사슬을 필요한 만큼 따라가도록 컴파일된다. Building.this는 특정 Building 객체에 대한 참조이지 정적 접근이 아니며, 새 객체를 만들지도 않는다. 같은 소스를 javac --release 8로 컴파일하면 클래스 파일에 access$000 같은 메서드가 생기고, Java 21 대상으로 컴파일하면 생기지 않는다. 이 차이의 원인은? Java 8의 언어 명세는 중첩 클래스가 바깥 클래스의 private 멤버에 접근하는 것을 금지했기 때문이다. Java 21의 javac는 중첩 클래스를 바깥 클래스와 같은 클래스 파일 하나에 합쳐 넣기 때문이다. Java 11부터 JVM이 NestHost와 NestMembers 속성으로 같은 네스트의 private 접근을 직접 허용하므로 우회용 메서드가 필요 없어졌기 때문이다. Java 21에서는 중첩 클래스가 쓰는 private 멤버가 컴파일할 때 패키지 접근으로 바뀌기 때문이다. 언어 규칙은 예전부터 같은 최상위 클래스 안의 private 접근을 허용했다. 달랐던 것은 JVM이다. Java 10까지의 JVM은 다른 클래스의 private 멤버 접근을 허용하지 않아 javac가 패키지 접근 다리 메서드를 만들어야 했고, JEP 181 이후에는 JVM이 네스트를 인식해 직접 접근을 허용한다. 클래스 파일은 지금도 클래스마다 하나씩이고, 멤버의 private 플래그도 그대로 유지된다.
    중첩 클래스(nested class)
    다른 클래스나 인터페이스의 본문 안에 선언된 클래스. 정적 중첩 클래스와 내부 클래스(멤버·지역·익명)를 모두 포함하는 이름이다.
    정적 중첩 클래스(static nested class)
    static으로 선언된 멤버 클래스. 바깥 인스턴스가 없으며, 바깥 클래스의 정적 멤버에만 직접 접근할 수 있다.
    내부 클래스(inner class)
    명시적으로도 암묵적으로도 static이 아닌 중첩 클래스. 인스턴스가 바깥 클래스의 인스턴스에 묶인다.
    바깥 인스턴스(immediately enclosing instance)
    내부 클래스의 인스턴스가 딸려 있는 바깥 클래스의 인스턴스. 객체를 생성할 때 정해지고 이후 바뀌지 않는다.
    합성 멤버(synthetic member)
    소스 코드에 대응하는 선언 없이 컴파일러가 만들어 넣은 필드나 메서드. this$0 필드와 Java 10 이전의 access$000 메서드가 그 예다.
    네스트(nest), 네스트 호스트(nest host)
    JVM이 서로의 private 멤버 접근을 허용하는 클래스들의 집합과 그 대표 클래스. javac는 최상위 클래스를 호스트로, 그 안의 중첩 클래스를 멤버로 기록한다.
    InnerClasses 속성
    클래스 파일에서 소스상의 중첩 관계, 단순 이름, 선언된 접근 플래그를 기록하는 속성. 컴파일러와 리플렉션이 참고하며 접근 제어에는 쓰이지 않는다.
    바이너리 이름(binary name)
    클래스 파일과 JVM이 쓰는 클래스 이름. 멤버 클래스는 바깥 클래스의 바이너리 이름에 $와 단순 이름을 붙인다.
    섀도잉(shadowing)
    안쪽 범위의 선언이 같은 이름의 바깥 선언을 가려, 단순 이름으로는 바깥 것을 가리킬 수 없게 되는 것.
    한정된 this(qualified this)
    클래스이름.this 형태의 식. 현재 객체에서 바깥 인스턴스 사슬을 따라가 그 클래스에 해당하는 바깥 인스턴스를 가리킨다.
