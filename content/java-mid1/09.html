    실패할 수 있는 일을 맡기는 순간

    이 권에서 지금까지 다룬 코드는 거의 전부 JVM 안의 메모리만 만졌다. 객체를 만들고, 비교하고, 문자열을 잇고, 날짜를 계산했다. 이런 코드는 우리가 올바르게 작성했다면 언제 실행해도 같은 결과를 낸다. 그런데 실제 프로그램은 JVM 바깥의 것에 일을 맡긴다. 파일을 읽고, 다른 서버에 접속하고, 데이터베이스에 질의한다. 이 일들은 우리 코드가 옳아도 실패한다. 디스크가 가득 찼을 수 있고, 상대 서버가 꺼져 있을 수 있고, 통신선이 중간에 끊길 수 있다.

    작은 프로그램 하나를 기준으로 삼자. 원격 서버에 파일을 백업하는 프로그램이다. 서버와의 연결을 나타내는 BackupLink가 있고, 이 객체는 세 가지 일을 한다. open()으로 서버에 연결하고, upload()로 파일을 보내고, close()로 연결을 끊는다. 백업 한 건을 수행하는 BackupJob은 이 셋을 순서대로 부른다.

    public class BackupJob {
    public void run(String host, String fileName) {
        BackupLink link = new BackupLink(host);
        link.open();
        link.upload(fileName);
        link.close();
        System.out.println("백업 완료: " + fileName);
    }
}

    몇 줄 안 되는 코드지만 외부 자원을 쓰는 코드의 성질이 모두 들어 있다. 첫째, 단계 사이에 전제가 있다. upload()는 open()이 성공했다고 믿고, "백업 완료"라는 보고는 upload()가 성공했다고 믿는다. 둘째, 얻은 것은 돌려줘야 한다. 연결을 열었다면 그 뒤에 무슨 일이 있었든 닫아야 한다. 셋째, 실패의 원인이 프로그램 밖에 있다. 코드를 아무리 다듬어도 서버가 꺼지는 것을 막을 수는 없다. 할 수 있는 일은 실패를 알아차리고, 알맞은 곳에서 대응하는 것뿐이다.

    이 회차는 그 "알아차리고 대응하는" 방법을 다룬다. 구체적으로는 다음 질문에 답한다.

    • 실패를 반환값으로 알리면 무엇이 곤란한가.
    • 자바의 예외는 어떤 클래스 계층으로 되어 있고, 그 계층의 어느 가지에 속하느냐에 따라 무엇이 달라지는가.
    • 예외가 던져지면 JVM은 무엇을 하는가. 어떤 코드는 건너뛰고 어떤 코드로 실행이 옮겨 가는가.
    • 체크 예외와 언체크 예외의 차이는 누가, 언제 검사하는 것인가.

    예외를 써서 위 백업 프로그램을 끝까지 고쳐 쓰는 일, finally와 try-with-resources로 자원을 정리하는 일은 다음 회차(10회)의 몫이다. 이번에는 규칙과 그 규칙이 실행 시점에 구현되는 방식에 집중한다.

    오류 상황 만들기: 실패를 모르는 프로그램

    실패를 다루려면 먼저 실패가 일어나야 한다. 실제 서버를 껐다 켜는 대신, 문자열 조건으로 실패를 흉내 낸다. 호스트 이름에 down이 들어 있으면 연결에 실패하고, 파일 이름에 huge가 들어 있으면 전송에 실패한다고 하자. 실패하면 오류 메시지를 출력하고 메서드를 끝낸다.

    public class BackupLink {
    private final String host;

    public BackupLink(String host) {
        this.host = host;
    }

    public void open() {
        if (host.contains("down")) {
            System.out.println("[오류] " + host + " 에 연결할 수 없음");
            return;
        }
        System.out.println(host + " 연결 성공");
    }

    public void upload(String fileName) {
        if (fileName.contains("huge")) {
            System.out.println("[오류] " + fileName + " 전송 실패");
            return;
        }
        System.out.println(host + " 로 " + fileName + " 전송");
    }

    public void close() {
        System.out.println(host + " 연결 해제");
    }
}
    public class BackupMain {
    public static void main(String[] args) {
        BackupJob job = new BackupJob();
        job.run("backup-1.example", "photo.zip");
        System.out.println();
        job.run("backup-down.example", "photo.zip");
        System.out.println();
        job.run("backup-1.example", "huge.iso");
    }
}

    둘째 실행을 보자. 연결에 실패했는데 프로그램은 파일을 "전송"했고, 열리지도 않은 연결을 "해제"했고, 끝으로 "백업 완료"라고 보고했다. 셋째 실행도 전송에 실패했는데 "백업 완료"가 찍혔다. 화면에 [오류]라는 글자가 지나가긴 했지만, 그것은 사람 눈에만 보이는 것이다. 프로그램 자신은 실패를 모른다.

    왜 모르는가. BackupJob.run()의 관점에서 link.open()은 두 경우 모두 똑같이 끝났기 때문이다. void 메서드가 호출자에게 돌려주는 정보는 "반환했다"는 사실 하나뿐이다. 성공해서 반환했는지 실패해서 반환했는지를 구별할 통로가 없다. 그래서 호출자는 다음 줄을 실행한다. 실패한 쪽은 알고 있고 호출한 쪽은 모르는 이 정보 격차가 문제의 출발점이다.

    이 프로그램이 저지른 잘못은 "멈추지 않은 것"보다 "거짓 보고를 한 것"이 더 크다. 사용자는 "백업 완료"를 믿고 원본을 지울 수 있다. 실패를 다루는 방법을 평가할 때는 이 기준을 기억해 두자. 실패했는데 성공한 것처럼 계속 진행하는 일이 얼마나 쉽게 일어나는가.

    반환값으로 오류 알리기와 그 한계

    호출자에게 통로가 없는 것이 문제라면 통로를 만들면 된다. 가장 먼저 떠오르는 통로는 반환값이다. open()과 upload()가 결과 코드를 문자열로 돌려주게 바꾼다. 성공이면 "OK", 실패면 실패의 종류를 나타내는 코드다.

    public class BackupLink {
    private final String host;

    public BackupLink(String host) {
        this.host = host;
    }

    public String open() {
        if (host.contains("down")) {
            return "E_OPEN";
        }
        System.out.println(host + " 연결 성공");
        return "OK";
    }

    public String upload(String fileName) {
        if (fileName.contains("huge")) {
            return "E_UPLOAD";
        }
        System.out.println(host + " 로 " + fileName + " 전송");
        return "OK";
    }

    public void close() {
        System.out.println(host + " 연결 해제");
    }
}
    public class BackupJob {
    public void run(String host, String fileName) {
        BackupLink link = new BackupLink(host);

        String opened = link.open();
        if (!opened.equals("OK")) {
            System.out.println("[오류] 연결 실패, 코드=" + opened);
            return;                       // 열지 못했으니 닫을 것도 없다
        }

        String uploaded = link.upload(fileName);
        if (!uploaded.equals("OK")) {
            System.out.println("[오류] 전송 실패, 코드=" + uploaded);
            link.close();                 // 열었으니 실패해도 닫아야 한다
            return;
        }

        link.close();
        System.out.println("백업 완료: " + fileName);
    }
}

    결과는 옳아졌다. 연결에 실패하면 전송하지 않고, 전송에 실패하면 "백업 완료"를 찍지 않고, 연결을 연 경우에는 닫는다. 그런데 이 코드를 읽어 보면 값을 치른 것이 보인다. 무엇을 치렀는지 하나씩 짚는다.

    정상 흐름이 오류 처리에 묻힌다

    이 메서드가 하려는 일은 여전히 "열고, 보내고, 닫고, 보고한다"의 네 단계다. 그런데 본문은 빈 줄을 빼고도 열네 줄로 늘었고, 늘어난 줄은 모두 "실패했으면"에 딸린 것이다. 읽는 사람은 조건문을 걷어 내야 이 메서드의 본래 목적을 알 수 있다. 단계가 셋이 아니라 열 개라면 조건문도 열 개다. 정상 흐름과 오류 처리 흐름이 한 줄씩 번갈아 나오는 구조는 단계 수에 비례해 나빠진다.

    검사를 빠뜨려도 아무 일도 일어나지 않는다

    반환값을 확인하는 것은 호출자의 성실함에 달려 있다. link.open();이라고만 쓰고 반환값을 버려도 자바 컴파일러는 오류를 내지 않는다. 그러면 프로그램은 앞 절의 "실패를 모르는 프로그램"으로 조용히 되돌아간다. 다시 말해 이 방식에서는 무시가 기본 동작이다. 올바른 동작을 얻으려면 호출하는 모든 곳에서 추가로 코드를 써야 하고, 한 곳이라도 빠뜨리면 실패가 성공으로 둔갑한다. 자바 언어 명세의 예외 장 머리말도 같은 지적을 한다. 명시적인 throw는 정상이라면 나올 수 없는 -1 같은 "이상한 값"을 돌려주는 옛 방식의 대안이며, 경험상 그런 값은 호출자가 무시하거나 확인하지 않는 일이 너무 잦다는 것이다(JLS 11장 서문).

    반환값이라는 통로를 오류 코드가 차지한다

    위 예제에서는 open()과 upload()가 원래 void였기 때문에 반환 자리가 비어 있었다. 그런데 원래 값을 돌려줘야 하는 메서드라면 어떻게 할까. 전송한 바이트 수를 long으로 돌려주는 upload()가 실패도 알려야 한다면, 선택지는 둘이다. 정상 결과로 나올 수 없는 특별한 값(이를테면 -1)을 실패의 뜻으로 정하거나, 결과와 오류 코드를 함께 담는 객체를 새로 만들어 돌려준다. 앞의 것은 "정상 결과로 나올 수 없는 값"이 정말 없을 때 무너진다.

    JDK에도 이런 모호함이 실제로 있다. Map.get(key)는 키가 없으면 null을 돌려주는데, 그 맵이 null 값을 허용한다면 null이 돌아왔다고 해서 키가 없다는 뜻은 아니다. 키에 null이 명시적으로 매핑되어 있을 수도 있기 때문이며, Map의 Javadoc은 두 경우를 구별하려면 containsKey를 쓰라고 적는다. 반환값 하나에 "결과"와 "결과 없음"이라는 두 가지 뜻을 실으면 이런 일이 생긴다.

    중간 계층이 손으로 전달해야 한다

    위 예제에서 BackupJob.run()은 실패를 알게 된 뒤 메시지를 찍고 끝냈다. 하지만 run()을 호출한 쪽(여기서는 main)도 백업이 실패했는지 알아야 하지 않을까. 그러려면 run()도 코드를 돌려줘야 하고, main도 그것을 검사해야 한다. 호출이 다섯 단계 깊이라면, 맨 아래에서 생긴 실패를 맨 위까지 올리기 위해 중간의 네 메서드가 모두 "받아서, 검사하고, 그대로 돌려주는" 코드를 가져야 한다. 그 넷 중 대부분은 그 실패에 대해 할 수 있는 일이 없는데도 그렇다.

    실패에 대한 정보가 빈약하다

    "E_UPLOAD"라는 문자열이 알려 주는 것은 실패의 종류 하나다. 어느 호출 경로에서 일어났는지, 그때의 상세한 사정이 무엇이었는지는 담기지 않는다. 더 담으려면 코드 체계를 넓히거나 별도의 객체를 설계해야 하고, 그 규약을 모든 호출자가 알아야 한다. 문자열 코드는 오타에도 약하다. "E_UPLAOD"와 비교하는 코드는 컴파일되고, 영원히 거짓이 된다.

    반환값이 언제나 나쁜 통로라는 뜻은 아니다. String.indexOf()가 찾는 문자가 없을 때 -1을 돌려주는 것처럼, "없음"이 그 연산의 정상적인 결과 중 하나라면 반환값이 자연스럽다. 문제가 되는 것은 호출자가 그대로 진행하면 안 되는 실패를 반환값에 실을 때다. JDK 안에서도 대비되는 쌍을 찾을 수 있다. java.io.File.delete()는 성공 여부를 boolean으로 돌려주는데, 이 메서드의 Javadoc은 java.nio.file.Files.delete()가 삭제할 수 없을 때 IOException을 던지도록 정의되어 있으며 그것이 오류 보고와 원인 진단에 쓸모 있다고 적어 두었다.
    이 장의 핵심

    실패를 알리는 수단에 바라는 것은 네 가지다. 아무 코드도 쓰지 않았을 때 실패가 묻히지 않을 것, 정상 흐름이 한눈에 읽힐 것, 실패를 다룰 수 없는 중간 계층은 손대지 않아도 될 것, 실패의 종류와 위치가 함께 전달될 것. 자바의 예외는 이 네 가지를 위해 반환과는 별개인 두 번째 출구를 메서드에 달아 준다. 그 출구로 나간 실패는 누군가 잡을 때까지 호출 스택을 거슬러 올라가고, 아무도 잡지 않으면 스레드를 끝낸다.

    반환 코드는 모든 계층이 손으로 검사하고 넘겨야 위로 올라가지만, 예외는 처리할 계층까지 중간 계층을 건너뛰어 올라간다는 차이를 나란히 보여 준다. 좌우로 나뉜 비교 다이어그램. 흰 배경, 얇은 선, 차분한 파랑과 주황. 왼쪽 패널 제목 "반환 코드". 위에서 아래로 상자 네 개를 세로로 쌓는다: "main", "BackupJob.run", "BackupLink.upload", 맨 아래에 번개 아이콘과 함께 "실패 발생". 아래에서 위로 올라가는 주황 화살표가 상자마다 끊겨 있고, 각 상자 옆에 작은 마름모 판단 기호와 라벨 "코드 검사 후 다시 반환". 한 상자의 마름모는 회색 점선으로 그리고 라벨 "검사를 빠뜨리면 여기서 사라진다". 오른쪽 패널 제목 "예외". 같은 상자 네 개. 맨 아래 "실패 발생"에서 출발한 주황 화살표 하나가 중간 상자 "BackupJob.run"을 곧게 지나쳐 "main" 상자 안의 작은 상자 "catch"에 도착한다. 지나치는 상자 옆에 라벨 "코드 없음, 그대로 통과". 화살표 옆에 라벨 "예외 객체: 종류, 메시지, 스택 트레이스". 두 패널 아래 공통 문구 "기본 동작: 왼쪽은 무시, 오른쪽은 전파". 반환 코드는 계층마다 검사해야 위로 올라가고, 한 곳에서 빠뜨리면 사라진다. 예외는 잡는 곳이 나올 때까지 스스로 올라간다.

    예외: 메서드의 두 번째 출구

    자바에서 메서드 호출이 끝나는 방식은 둘이다. 하나는 정상 완료(normal completion)다. return 문에 이르거나 본문의 끝에 이르러 호출자에게 값을 돌려주고(또는 void면 값 없이), 호출자는 호출 바로 다음 지점부터 실행을 잇는다. 다른 하나는 갑작스러운 완료(abrupt completion)다. JVM 명세는 메서드 안에서 예외가 던져졌는데 그 메서드 안에서 처리되지 않으면 그 호출이 갑작스럽게 완료된다고 정의하고, 이렇게 끝난 호출은 호출자에게 값을 돌려주지 않는다고 적는다(JVMS 2.6.5).

호출자 ◀─── 값 ─────── return           호출자 ◀── 예외 객체 ── throw

    예외를 일으키는 문법은 throw 문이다. throw 뒤에는 던질 객체를 가리키는 식이 온다.

    throw new IllegalStateException("연결되지 않은 상태에서 전송을 시도함");

    이 한 줄은 두 가지 일을 한다. new가 힙에 예외 객체를 만들고, throw가 그 객체의 참조를 들고 현재 실행 흐름을 끊는다. 아무 객체나 던질 수 있는 것은 아니다. Throwable의 Javadoc은 이 클래스(또는 그 하위 클래스)의 인스턴스만 JVM이 던지거나 throw 문으로 던질 수 있고, catch 절의 인자 타입도 이 클래스나 하위 클래스만 될 수 있다고 적는다. throw "실패";처럼 문자열을 던지는 코드는 컴파일되지 않는다.

    예외가 객체라는 점이 반환 코드와의 첫째 차이다. 예외 객체는 다음을 실어 나른다.

    • 타입: 객체의 클래스가 곧 실패의 종류다. "E_UPLOAD"라는 문자열 대신 클래스 이름이 종류를 나타내므로, 오타는 컴파일 오류가 되고 종류끼리 상속으로 묶을 수 있다.
    • 메시지: 생성자에 넘긴 문자열. getMessage()로 꺼낸다.
    • 스택 트레이스: 이 객체가 만들어진 시점에 그 스레드의 호출 스택이 어떤 모습이었는지에 대한 기록. 어느 메서드의 몇째 줄에서, 어떤 호출 경로를 거쳐 여기에 왔는지가 남는다.
    • 원인(cause): 이 예외를 만들게 한 다른 예외. 예외를 다른 예외로 바꿔 던질 때 원래 예외를 잃지 않게 해 준다. 10회에서 쓴다.

    둘째 차이는 기본 동작이다. 예외가 던져지면 그 뒤의 문장들은 실행되지 않는다. 호출자가 아무 코드도 쓰지 않았다면 호출자도 같은 방식으로 끝나고, 그 위의 호출자도 마찬가지다. 반환 코드에서는 아무것도 하지 않으면 실패가 사라졌지만, 예외에서는 아무것도 하지 않으면 실패가 계속 올라간다. 앞 절에서 본 "실패했는데 성공한 것처럼 진행하는" 일이 기본으로는 일어나지 않는다.

    셋째, 처리 코드의 자리가 따로 있다. try 블록에는 정상 흐름만 쓰고, 실패에 대한 대응은 catch 블록에 모은다. 반환 타입은 본래의 결과에만 쓰인다. 다만 예외가 저절로 해결해 주지 않는 것이 하나 있다. 반환 코드 버전에서 "열었으니 실패해도 닫아야 한다"고 적었던 link.close()다. 예외가 흐름을 끊고 올라가 버리면 그 아래의 close() 호출도 건너뛴다. 이 문제를 푸는 finally와 try-with-resources는 10회에서 다룬다.

    일상에서 가져온 비유현장에서 올려 보내는 사고 보고서

    창구 직원이 자기 권한으로 해결할 수 없는 일을 만나면 하던 업무를 멈추고 사고 보고서를 써서 윗선에 올린다. 팀장이 처리할 수 있으면 거기서 끝나고, 못 하면 부장에게, 그래도 못 하면 더 위로 간다. 보고서에는 무슨 일이, 어느 창구에서, 어떤 경위로 일어났는지가 적혀 있다. 예외 객체가 이 보고서이고, 호출 스택이 결재선이다. 비유가 맞지 않는 지점도 있다. 회사에서는 윗선이 결정하면 창구 직원이 하던 일로 돌아가 이어서 하지만, 자바에서는 예외를 던진 메서드와 그 위의 중간 메서드들이 하던 일을 버리고 끝난다. 잡은 쪽이 처리를 마쳐도 던진 지점으로 돌아가지 않는다.

    자바 예외 계층: Throwable, Error, Exception, RuntimeException

    예외도 객체이므로 클래스가 있고, 클래스이므로 상속 계층이 있다. 이 계층은 장식이 아니라 규칙의 뼈대다. 어느 가지에 속하느냐에 따라 컴파일러가 검사하는지가 갈리고, catch가 무엇을 잡는지가 정해진다. JLS 11.1.1이 정한 뼈대는 다음과 같다.

    클래스JLS 11.1.1의 설명컴파일러의 검사
    Throwable모든 예외는 이 클래스 또는 하위 클래스의 인스턴스로 표현된다. Object의 직접 하위 클래스다.체크
    Error보통의 프로그램이 복구하리라고 기대되지 않는 모든 예외의 상위 클래스언체크
    Exception보통의 프로그램이 복구하고 싶어 할 수 있는 모든 예외의 상위 클래스체크 (단, RuntimeException 가지는 제외)
    RuntimeException식을 평가하는 동안 여러 이유로 던져질 수 있지만 복구가 여전히 가능할 수 있는 모든 예외의 상위 클래스. Exception의 직접 하위 클래스다.언체크

    체크와 언체크의 정의는 이 계층 위에서 한 문장으로 끝난다. JLS 11.1.1에 따르면 언체크 예외 클래스(unchecked exception classes)는 런타임 예외 클래스들(RuntimeException과 그 하위 클래스)과 에러 클래스들(Error와 그 하위 클래스)이다. 체크 예외 클래스(checked exception classes)는 그 나머지 전부, 곧 Throwable과 그 하위 클래스 중 위 두 가지를 뺀 것이다. 판별법은 단순하다. 클래스의 부모를 따라 올라가다가 RuntimeException이나 Error를 만나면 언체크, 만나지 않고 Throwable에 닿으면 체크다.

    이 정의에서 눈여겨볼 점이 둘 있다. 첫째, Exception과 Throwable 자신은 체크 예외다. RuntimeException이 Exception의 자식인데도 언체크라는 것은, 체크 여부가 "어느 클래스의 자식인가"로 일관되게 내려가는 성질이 아니라 계층의 한 가지를 예외로 떼어 낸 규칙이라는 뜻이다. 둘째, Throwable을 직접 상속한 클래스도 체크 예외다. class Signal extends Throwable을 만들어 선언 없이 던지면 컴파일러는 뒤에서 볼 체크 예외 오류를 그대로 낸다. 다만 직접 만드는 예외는 Exception이나 RuntimeException 아래에 두는 것이 관례다.

    Error는 왜 따로 있는가

    Error 가지에는 메모리가 바닥났다(OutOfMemoryError), 호출이 너무 깊어 스택이 넘쳤다(StackOverflowError), 실행 중에 필요한 클래스 정의를 찾지 못했다(NoClassDefFoundError) 같은 것들이 있다. 공통점은 애플리케이션 코드가 잡는다고 해서 할 수 있는 일이 거의 없다는 것이다. 그래서 애플리케이션은 Error를 잡으려 하지 않는 것이 원칙이고, 같은 이유로 catch (Throwable t)도 쓰지 않는다. Throwable을 잡으면 그 아래의 Error까지 함께 잡히기 때문이다. 애플리케이션이 다루는 범위는 Exception부터다.

    Error가 언체크인 이유도 명세에 적혀 있다. 에러는 프로그램의 여러 지점에서 일어날 수 있고 복구가 어렵거나 불가능하므로, 그것을 일일이 선언하게 하면 프로그램이 쓸데없이 어수선해진다는 것이다(JLS 11.2). 메모리 부족은 객체를 만드는 모든 줄에서 일어날 수 있다. 그것을 선언하라고 하면 모든 메서드에 같은 선언이 붙을 것이고, 정보로서의 가치는 없다.

    예외는 누가 던지는가

    JLS 11.1.2는 예외가 던져지는 원인을 넷으로 나눈다. (1) throw 문이 실행되었다. (2) 활성화된 assert 문의 조건식이 거짓으로 평가되었다. (3) JVM이 비정상적인 실행 조건을 동기적으로 감지했다. (4) 비동기 예외가 발생했다. 이 가운데 (3)이 다시 셋으로 나뉜다. 식의 평가가 언어의 정상적인 의미를 위반한 경우(정수를 0으로 나누기가 명세의 예시다), 프로그램의 일부를 로딩·링크·초기화하다 오류가 난 경우(LinkageError의 하위 클래스가 던져진다), JVM의 내부 오류나 자원 한계 때문에 언어의 의미를 구현할 수 없게 된 경우(VirtualMachineError의 하위 클래스가 던져진다)다.

    이 분류는 계층의 가지와 잘 맞는다. NullPointerException, ArithmeticException, ArrayIndexOutOfBoundsException처럼 우리가 throw를 쓰지 않았는데 나오는 런타임 예외는 (3)의 첫째 경우로, JVM이 명령어를 실행하다가 직접 던진다. Error의 대표들은 (3)의 둘째와 셋째 경우다. 우리가 정의하고 throw로 던지는 예외는 (1)이다. JVM이 던지든 우리가 던지든 그 뒤의 전파와 처리 규칙은 똑같다.

    Throwable 아래 Error와 Exception이 갈리고, Exception 아래에서 RuntimeException 가지만 언체크로 떼어진다는 것을 색으로 구분해 보여 준다. 위에서 아래로 뻗는 나무 형태의 계층 다이어그램. 흰 배경, 얇은 선. 체크 예외는 파랑 테두리, 언체크 예외는 주황 테두리로 구분한다. 맨 위 회색 상자 "Object". 그 아래 파랑 상자 "Throwable". Throwable에서 두 갈래: 왼쪽 주황 상자 "Error", 오른쪽 파랑 상자 "Exception". Error 아래에 주황 상자 두 개 "OutOfMemoryError", "StackOverflowError". Exception 아래에 세 갈래: 파랑 상자 "IOException", 파랑 상자 "SQLException", 주황 상자 "RuntimeException". RuntimeException 아래에 주황 상자 두 개 "NullPointerException", "IllegalArgumentException". Error 가지 전체를 옅은 주황 배경으로 묶고 라벨 "언체크: 복구를 기대하지 않음". RuntimeException 가지 전체를 옅은 주황 배경으로 묶고 라벨 "언체크: 선언·처리 강제 없음". 나머지 파랑 영역에 라벨 "체크: 잡거나 throws로 선언해야 컴파일됨". 모든 자식 상자에서 부모 상자로 향하는 실선 화살표. 부모를 따라 올라가다 RuntimeException이나 Error를 만나면 언체크, 만나지 않고 Throwable에 닿으면 체크다.

    예외 기본 규칙: 잡거나, 던지거나

    예외에 대해 코드가 할 수 있는 일은 둘뿐이다. 잡아서 처리한다, 또는 처리하지 않고 호출자에게 던진다(밖으로 내보낸다). 여기에 계층에서 나오는 규칙 하나가 붙는다. 잡을 때든 던질 때든 지정한 타입의 하위 타입도 함께 대상이 된다. catch (Exception e)는 Exception과 그 모든 자식을 잡는다. 다형성에서 부모 타입 변수가 자식 객체를 가리킬 수 있었던 것과 같은 이치다.

    먼저 아무도 잡지 않는 경우를 본다. 여기서는 언체크 예외인 IllegalStateException을 쓴다. 체크 예외에서는 "던진다"에 선언이 추가로 필요한데, 그것은 뒤 절에서 다룬다.

    public class Propagate {
    public static void main(String[] args) {
        System.out.println("main 시작");
        first();
        System.out.println("main 끝");
    }

    static void first() {
        System.out.println("first 시작");
        second();
        System.out.println("first 끝");
    }

    static void second() {
        System.out.println("second 시작");
        throw new IllegalStateException("second에서 문제 발생");
    }
}

    한 줄씩 추적한다. main이 "main 시작"을 찍고 first()를 부른다. first가 "first 시작"을 찍고 second()를 부른다. second가 "second 시작"을 찍고 예외를 던진다. 여기서부터가 중요하다. second에는 이 예외를 잡는 코드가 없으므로 second 호출은 갑작스럽게 끝난다. first의 관점에서는 10행의 second() 호출이 값을 돌려주는 대신 예외를 내놓은 것이다. first에도 잡는 코드가 없으므로 11행 "first 끝"은 실행되지 않고 first도 갑작스럽게 끝난다. main도 마찬가지여서 5행 "main 끝"은 찍히지 않는다. main 위에는 더 올라갈 호출자가 없다. 이때 스레드가 종료되고, 그 직전에 예외의 내용이 출력된다. "first 끝"과 "main 끝"이 출력에 없다는 것이 이 예제의 요점이다.

    이번에는 중간에서 잡는다. first가 second() 호출을 try로 감싼다.

    public class CatchMiddle {
    public static void main(String[] args) {
        System.out.println("main 시작");
        first();
        System.out.println("main 끝");
    }

    static void first() {
        System.out.println("first 시작");
        try {
            second();
            System.out.println("first: second 정상 반환");
        } catch (IllegalStateException e) {
            System.out.println("first: 예외 처리, message=" + e.getMessage());
        }
        System.out.println("first 끝");
    }

    static void second() {
        System.out.println("second 시작");
        throw new IllegalStateException("second에서 문제 발생");
    }
}
    main 시작
first 시작
second 시작
first: 예외 처리, message=second에서 문제 발생
first 끝
main 끝

    second가 던진 예외는 first의 try 블록 안에서 나왔고, catch의 타입 IllegalStateException과 맞으므로 거기서 잡힌다. 세 가지를 확인하자. 첫째, try 블록의 나머지인 "first: second 정상 반환"은 실행되지 않는다. 예외가 나온 지점부터 try 블록 끝까지는 건너뛴다. 둘째, catch 블록이 끝나면 실행은 try 문 다음으로 이어진다. 그래서 "first 끝"이 찍힌다. 예외가 던져졌던 second 안으로 돌아가지 않는다. 셋째, main은 예외가 있었다는 사실 자체를 모른다. main이 보기에 first()는 정상적으로 반환했다. 예외를 잡는다는 것은 갑작스러운 완료를 그 자리에서 끊고 정상 흐름으로 되돌린다는 뜻이다.

    명세의 표현으로는 이렇다. 예외가 던져지면 제어는 예외를 일으킨 코드에서, 그 예외를 처리할 수 있는 가장 가까운, 동적으로 둘러싼 catch 절로 옮겨진다(JLS 11.3). "동적으로 둘러싼다"는 것은 소스 코드에서 중괄호로 감싸고 있다는 뜻이 아니라 실행 중의 호출 관계로 감싸고 있다는 뜻이다. second의 throw 문은 소스상으로는 어떤 try 안에도 없지만, first의 try 블록 안에서 호출되었으므로 그 try에 동적으로 둘러싸여 있다. 그리고 그 과정에서 JVM은 현재 스레드에서 시작했지만 아직 끝나지 않은 식, 문장, 메서드 호출을 하나씩 갑작스럽게 완료시킨다(JLS 11장 서문).

    타입으로 고르는 catch

    catch는 타입으로 예외를 고른다. 던져진 객체가 catch에 적힌 타입의 인스턴스이면(그 타입 자신이거나 하위 타입이면) 잡는다. catch 절이 여럿이면 위에서부터 차례로 맞춰 보고 처음 맞는 하나만 실행한다.

    public class Mixed {
    static void risky(int n) throws Exception {
        if (n == 1) throw new java.io.IOException("입출력");
        if (n == 2) throw new IllegalArgumentException("인자");
        System.out.println("정상 " + n);
    }

    public static void main(String[] args) {
        for (int n = 0; n < 3; n++) {
            try {
                risky(n);
            } catch (RuntimeException e) {
                System.out.println("런타임: " + e.getMessage());
            } catch (Exception e) {
                System.out.println("그 밖: " + e.getMessage());
            }
        }
    }
}
    정상 0
그 밖: 입출력
런타임: 인자

    n이 1일 때 던져진 IOException은 RuntimeException의 하위 타입이 아니므로 첫째 catch를 지나치고, Exception의 하위 타입이므로 둘째에서 잡힌다. n이 2일 때의 IllegalArgumentException은 RuntimeException의 하위 타입이므로 첫째에서 잡히고 둘째는 보지 않는다. 두 catch의 순서를 바꿔 Exception을 먼저 쓰면 어떻게 될까. 모든 예외가 첫째에서 잡히므로 둘째는 결코 실행될 수 없고, 자바는 이것을 컴파일 오류로 막는다. 바로 뒤에서 그 이유를 바이트코드로 본다.

    한 가지 더. 예외를 잡은 뒤 프로그램이 올바른 상태인지는 잡은 쪽이 책임진다. catch 블록을 비워 두면 예외는 조용히 사라지고, 프로그램은 실패를 모른 채 다음 줄로 간다. 이것은 반환 코드를 검사하지 않고 버리는 것과 결과가 같다. 예외가 준 "무시가 기본이 아니다"라는 이점을 스스로 되돌리는 셈이다.

    한 층 아래 ①: athrow와 예외 테이블, 스택 풀기

    "예외가 호출 스택을 거슬러 올라간다"는 말이 JVM 안에서 실제로 무엇인지 보자. 기본편에서 메서드를 호출할 때마다 그 스레드의 JVM 스택에 프레임(frame)이 하나씩 쌓이고, 프레임에는 지역 변수 배열과 피연산자 스택이 들어 있다고 배웠다. CatchMiddle을 컴파일한 뒤 javap -c -p CatchMiddle로 first와 second의 바이트코드를 연다.

    catch의 순서가 문법 규칙인 이유

    catch가 둘인 메서드의 예외 테이블을 보면 순서 규칙의 근거가 드러난다. 앞의 Mixed.main은 RuntimeException을 먼저, Exception을 나중에 잡았다. javap -c -p Mixed가 보여 주는 main의 예외 테이블이다.

        Exception table:
       from    to  target type
           7    11    14   Class java/lang/RuntimeException
           7    11    33   Class java/lang/Exception

    두 행의 범위는 같고, 소스의 catch 순서대로 적혀 있다. JVMS 2.10은 JVM이 예외 테이블의 행을 클래스 파일에 나타난 순서대로, 테이블의 처음부터 검색한다고 정한다. 처음 맞는 행에서 검색이 끝난다. 그러니 Exception 행이 먼저 오면 RuntimeException도 거기서 맞아 버리고, 둘째 행은 영원히 선택되지 않는다. 자바 언어는 이런 죽은 catch를 허용하지 않는다. JLS 11.2.3은 어떤 catch 절이 잡을 수 있는 예외 클래스를 같은 try 문의 앞선 catch 절이 이미(그 클래스 자체로든 상위 클래스로든) 잡을 수 있으면 컴파일 오류라고 정한다. Mixed에서 두 catch의 순서만 바꾼 MixedSwapped.java를 JDK 21의 javac로 컴파일하면 이렇게 나온다.

    MixedSwapped.java:14: error: exception RuntimeException has already been caught
            } catch (RuntimeException e) {
              ^

    그래서 catch는 구체적인 타입(자식)부터 일반적인 타입(부모) 순으로 쓴다. 외워야 할 관례가 아니라 "위에서부터 처음 맞는 것"이라는 검색 규칙의 결과다.

    divide의 바이트코드에는 new도 athrow도 없다. 네 명령어뿐이다. 그런데도 예외가 나온다. JVMS는 idiv 명령어의 설명에 "나누는 수가 0이면 idiv는 ArithmeticException을 던진다"고 적어 두었다. 예외 객체를 만들고 던지는 일을 JVM이 명령어 실행의 일부로 수행하는 것이다. 그 뒤의 과정, 곧 예외 테이블 검색과 스택 풀기는 athrow로 던진 경우와 똑같다.

    예외가 던져지면 현재 프레임의 예외 테이블을 위에서부터 검색하고, 맞는 행이 없으면 프레임을 버리고 호출자에서 같은 검색을 되풀이하는 과정을 보여 준다. 왼쪽에 세로로 쌓인 스택 프레임 세 개, 오른쪽에 예외 테이블 표를 둔 다이어그램. 흰 배경, 얇은 선, 파랑과 주황. 왼쪽 스택은 위에서부터 상자 "second 프레임", "first 프레임", "main 프레임". "second 프레임" 안에 주황 번개 아이콘과 라벨 "athrow". "second 프레임"에는 빨간 사선을 긋고 옆에 라벨 "핸들러 없음: 프레임 폐기". "second 프레임"에서 "first 프레임"으로 내려가는 굵은 주황 화살표, 라벨 "호출자에서 다시 던짐". "first 프레임" 오른쪽으로 점선이 이어져 표를 가리킨다. 표의 제목 "first의 예외 테이블", 열 머리 "from", "to", "target", "type", 한 행 "8", "19", "22", "IllegalStateException". 표 아래에 초록 체크 표시와 라벨 "pc 8이 범위 안, 타입 일치". 표에서 "first 프레임" 안의 작은 상자 "catch 블록 (pc 22)"로 향하는 초록 화살표. 스택 위쪽 바깥, 힙을 나타내는 둥근 영역에 상자 "예외 객체"를 두고 라벨 "힙에 있으므로 프레임이 버려져도 남는다". 맞는 핸들러가 없는 프레임은 버려지고, 호출자의 예외 테이블에서 같은 검색이 되풀이된다. 예외 객체는 힙에 있어 핸들러까지 전달된다.

    한 층 아래 ②: 아무도 잡지 않은 예외와 스택 트레이스

    Propagate의 마지막 출력 네 줄은 누가 찍은 것일까. 우리 코드에는 그런 출력문이 없다. JLS 11.3은 예외를 처리할 catch 절을 찾지 못하면 현재 스레드가 종료되며, 종료 전에 잡히지 않은 예외가 다음 규칙으로 처리된다고 정한다. 그 스레드에 잡히지 않은 예외 핸들러(uncaught exception handler)가 설정되어 있으면 그것이 실행된다. 없으면 스레드가 속한 ThreadGroup의 uncaughtException 메서드가 호출되고, 스레드 그룹들이 이 메서드를 재정의하지 않았다면 기본 핸들러의 uncaughtException이 호출된다.

    기본 핸들러도 따로 설정하지 않았을 때 무슨 일이 일어나는지는 JDK 소스에서 볼 수 있다. OpenJDK 21의 ThreadGroup.uncaughtException은 마지막 갈래에서 다음 두 줄을 실행한다.

    System.err.print("Exception in thread \"" + t.getName() + "\" ");
e.printStackTrace(System.err);

    출력의 첫 줄 앞부분 Exception in thread "main"은 여기서 온다. "main"은 스레드의 이름이다. 그리고 이 출력은 표준 출력이 아니라 표준 오류(System.err)로 나간다. 터미널에서는 둘이 섞여 보이지만 서로 다른 스트림이므로, 표준 출력만 파일로 돌려 저장하면 스택 트레이스는 파일에 남지 않는다.

    스택 트레이스 읽기

    Exception in thread "main" java.lang.IllegalStateException: second에서 문제 발생
	at Propagate.second(Propagate.java:16)
	at Propagate.first(Propagate.java:10)
	at Propagate.main(Propagate.java:4)

    첫 줄의 나머지는 예외의 클래스 이름과 메시지다. at으로 시작하는 줄 하나가 프레임 하나이고, 클래스.메서드(파일:행)의 형식이다. 맨 위가 가장 최근에 호출된 메서드이고 아래로 갈수록 호출자다. 그러니 아래에서 위로 읽으면 호출 순서가 된다. main의 4행이 first를 불렀고, first의 10행이 second를 불렀고, second의 16행에서 일이 벌어졌다. 앞의 "스택 풀기" 그림에서 ①의 스택을 위에서 아래로 그대로 적은 것과 같다.

    이 기록은 언제 만들어지는가. 프레임이 이미 다 버려진 뒤에 찍혔는데도 버려진 프레임들이 적혀 있다. 답은 "예외 객체가 만들어질 때"다. Throwable의 Javadoc은 throwable이 생성된 시점의 스레드 실행 스택의 스냅숏을 담는다고 적는다. OpenJDK 21의 소스에서도 Throwable의 public 생성자들이 fillInStackTrace()를 호출하고, 이 메서드가 네이티브 메서드를 통해 현재 스택을 기록한다. throw가 아니라 new가 기록 시점이라는 사실은 다음 예제로 확인된다.

    public class WhereCaptured {
    public static void main(String[] args) {
        RuntimeException prepared = create();   // 예외 객체를 만들기만 한다
        raise(prepared);                         // 던지는 것은 여기서 부른 raise다
    }

    static RuntimeException create() {
        return new RuntimeException("미리 만들어 둔 예외");
    }

    static void raise(RuntimeException e) {
        throw e;
    }
}
    Exception in thread "main" java.lang.RuntimeException: 미리 만들어 둔 예외
	at WhereCaptured.create(WhereCaptured.java:8)
	at WhereCaptured.main(WhereCaptured.java:3)

    예외를 실제로 던진 것은 12행의 raise인데, 스택 트레이스에는 raise가 없고 create가 있다. 스택 트레이스는 "어디서 던졌는가"가 아니라 "어디서 만들었는가"의 기록이다. 보통은 throw new …로 만들자마자 던지므로 둘이 같은 줄이라 구별할 일이 없다. 하지만 예외 객체를 미리 만들어 두고 재사용하면 스택 트레이스가 실제 실패 위치와 무관해진다는 점은 알아 둘 만하다.

    끝나는 것은 스레드다

    명세가 일관되게 쓰는 표현은 "스레드가 종료된다"이지 "프로그램이 종료된다"가 아니다. JVM 스택은 스레드마다 따로 있고(JVMS 2.5.2), 예외는 자기가 던져진 스레드의 스택만 거슬러 올라간다. 다른 스레드의 스택으로 넘어가지 않는다. main 스레드가 예외로 죽어도 다른 스레드가 살아 있으면 그 스레드는 계속 돈다.

    public class TwoThreads {
    public static void main(String[] args) {
        Thread worker = new Thread(() -> {
            try {
                Thread.sleep(500);
            } catch (InterruptedException e) {
                return;
            }
            System.out.println("worker: main이 죽은 뒤에도 실행된다");
        }, "worker");
        worker.start();

        throw new IllegalStateException("main에서 잡지 않은 예외");
    }
}
    Exception in thread "main" java.lang.IllegalStateException: main에서 잡지 않은 예외
	at TwoThreads.main(TwoThreads.java:13)
worker: main이 죽은 뒤에도 실행된다

    main 스레드는 13행에서 예외로 끝났지만, 0.5초 뒤에 worker 스레드가 자기 할 일을 마저 한다. 앞의 Propagate에서 프로그램 전체가 끝난 것은 스레드가 main 하나뿐이었기 때문이다. JDK 21의 java 실행기로 확인하면 main이 예외로 끝난 두 프로그램 모두 프로세스 종료 코드는 1이었다. 스레드와 스레드 풀은 로드맵의 뒤쪽 권에서 본격적으로 다루지만, "예외는 스레드 하나의 호출 스택 안에서만 전파된다"는 사실은 지금 확실히 해 두자. 서버에서 요청 하나를 처리하던 스레드에서 난 예외가 다른 요청에 영향을 주지 않는 것도, 반대로 다른 스레드에서 난 예외를 이쪽 스레드의 try-catch로 잡을 수 없는 것도 여기서 나온다.

    체크 예외: 컴파일러가 처리를 확인하는 예외

    지금까지의 예제는 모두 언체크 예외였다. 그래서 "잡거나 던지거나" 가운데 "던지거나"는 아무 코드 없이 저절로 이루어졌다. 체크 예외(checked exception)에서는 그 부분이 달라진다. 체크 예외를 직접 만들어 보자. Exception을 상속하면 된다. 부모를 따라 올라가는 길에 RuntimeException이 없으므로 정의에 따라 체크 예외다.

    public class QuotaExceededException extends Exception {
    public QuotaExceededException(String message) {
        super(message);
    }
}

    업로드할 크기가 할당량을 넘으면 이 예외를 던지는 메서드를 쓴다.

    upload는 자기가 던진 예외를 스스로 잡을 이유가 없으니 선언하는 쪽을 택한다. 메서드 이름과 매개변수 뒤에 throws 절을 붙인다.

    public class Uploader {
    void upload(long bytes) throws QuotaExceededException {
        if (bytes > 1_000) {
            throw new QuotaExceededException("할당량 초과: " + bytes);
        }
        System.out.println(bytes + "바이트 전송");
    }
}

    이제 Uploader는 컴파일된다. 그런데 공은 호출자에게 넘어갔다. upload()를 호출하는 코드는 "체크 예외를 던질 수 있는 문장"을 본문에 갖게 되므로, 호출자도 같은 두 선택 앞에 선다. 두 선택을 각각 택한 메서드를 나란히 둔다.

    public class UploadService {
    private final Uploader uploader = new Uploader();

    // 선택 1: 잡는다
    void runAndHandle(long bytes) {
        try {
            uploader.upload(bytes);
            System.out.println("업로드 완료");
        } catch (QuotaExceededException e) {
            System.out.println("업로드 실패 처리: " + e.getMessage());
        }
    }

    // 선택 2: 던진다(throws로 선언하고 호출자에게 넘긴다)
    void runAndPass(long bytes) throws QuotaExceededException {
        uploader.upload(bytes);
        System.out.println("업로드 완료");
    }
}

"main 끝"은 찍히지 않는다. 실행 시점의 움직임은 언체크 예외를 쓴 Propagate, CatchMiddle과 다를 것이 없다. 다른 것은 컴파일 시점뿐이다. runAndPass와 main에서 throws 절을 지우면 두 곳 모두에서 위와 같은 unreported exception 오류가 난다.

    컴파일러는 무엇을 보고 판단하는가

    컴파일러의 검사는 실제로 예외가 발생할지를 따지지 않는다. 선언만 본다. service.runAndPass(10)은 10이 1,000보다 작으므로 실행하면 절대 예외를 던지지 않는다. 그래도 이 호출을 잡지도 선언하지도 않은 메서드는 컴파일되지 않는다. runAndPass의 선언에 throws QuotaExceededException이 있다는 것만으로 그 호출식은 "이 체크 예외를 던질 수 있는 식"으로 분류되기 때문이다. JLS 11.2.1과 11.2.2가 식과 문장마다 "던질 수 있는(can throw)" 예외를 정하는 규칙이고, 메서드 호출식에 대해서는 호출되는 메서드의 throws 절이 그 근거다. 그래서 throws 절은 주석이 아니라 메서드 시그니처의 일부처럼 작동한다. JLS 11.2는 throws 절에 적힌 체크 예외 클래스들이 메서드의 구현자와 사용자 사이의 계약의 일부라고 표현한다.

    throws와 catch에 적는 타입에는 기본 규칙의 둘째 항목, 곧 하위 타입 포함이 그대로 적용된다. throws Exception이라고 선언하면 본문에서 어떤 체크 예외를 던져도 컴파일된다. 편해 보이지만 치르는 값이 있다. 그 메서드를 부르는 쪽은 "무엇이든 던질 수 있는 메서드"를 상대하게 되어 Exception을 통째로 잡거나 자기도 throws Exception을 달아야 한다. 어떤 실패가 가능한지 알려 주던 선언의 정보가 사라지고, catch (Exception e)는 의도한 체크 예외뿐 아니라 NullPointerException 같은 런타임 예외까지 함께 삼킨다.

    반대 방향의 검사: 던질 수 없는 체크 예외는 잡을 수도 없다

    컴파일러는 "던질 수 있는 체크 예외"를 알고 있으므로 반대 방향도 검사한다. try 본문이 던질 수 없는 체크 예외를 잡으려 하면 오류다.

    public class NeverThrown {
    void call() {
        try {
            System.out.println("예외를 던지지 않는 코드");
        } catch (QuotaExceededException e) {
            System.out.println("도달할 수 없다");
        }
    }
}
    NeverThrown.java:5: error: exception QuotaExceededException is never thrown in body of corresponding try statement
        } catch (QuotaExceededException e) {
          ^

    같은 자리에 catch (Exception e)를 쓰면 컴파일된다. JLS 11.2.3의 이 규칙에는 "잡으려는 클래스가 Exception이거나 Exception의 상위 클래스인 경우는 제외한다"는 단서가 붙어 있다. Exception의 하위에는 언체크인 RuntimeException 가지가 있고, 언체크 예외는 어느 코드에서든 나올 수 있다고 봐야 하므로 "절대 던져지지 않는다"고 단정할 수 없기 때문이다.

    오버라이딩과 throws

    throws가 계약이라면 상속에서도 지켜져야 한다. 재정의하는 메서드는 재정의되는 메서드가 선언하지 않은 체크 예외를 선언할 수 없다(JLS 8.4.8.3). 더 좁히는 것(하위 타입으로 바꾸거나 아예 빼는 것)은 된다.

    class Base {
    void work() { }
    void load() throws java.io.IOException { }
}

    체크 예외의 득과 실

    얻는 것은 분명하다. 처리를 빠뜨리면 컴파일러가 알려 준다. 반환 코드의 가장 큰 약점이던 "검사를 빠뜨려도 아무 일도 일어나지 않는다"를 언어 차원에서 막는다. 그리고 메서드 선언만 읽어도 어떤 실패가 가능한지 알 수 있다.

    치르는 것도 분명하다. 예외를 다룰 능력이 없는 중간 계층도 전부 throws를 달거나 try-catch를 써야 한다. 반환 코드에서 "중간 계층이 손으로 전달해야 한다"고 했던 문제가 선언의 형태로 일부 되돌아오는 것이다. 또 throws에 적힌 타입은 시그니처를 타고 위로 퍼진다. 맨 아래 계층이 throws SQLException이면 그것을 넘기는 모든 계층의 선언에 SQLException이 나타나고, 그 계층들이 모두 java.sql 패키지에 의존하게 된다. 귀찮음을 피하려고 catch 블록을 비우거나 throws Exception으로 뭉개면 체크 예외를 쓰는 이득마저 사라진다.

    언체크 예외: 컴파일러가 확인하지 않는 예외

    언체크 예외(unchecked exception)는 RuntimeException과 그 하위 클래스다(Error 가지도 언체크지만 애플리케이션이 만들어 던지는 대상이 아니므로 여기서는 런타임 예외만 말한다). 만드는 방법은 부모만 다르다.

    public class InvalidFileNameException extends RuntimeException {
    public InvalidFileNameException(String message) {
        super(message);
    }
}
    public class NameChecker {
    void check(String fileName) {                      // throws 선언이 없다
        if (fileName.isBlank()) {
            throw new InvalidFileNameException("파일 이름이 비어 있음");
        }
        System.out.println("이름 확인: " + fileName);
    }
}
    public class UncheckedMain {
    public static void main(String[] args) {
        NameChecker checker = new NameChecker();
        checker.check("photo.zip");                    // try도 throws도 없이 호출한다
        try {
            checker.check(" ");
        } catch (InvalidFileNameException e) {
            System.out.println("잡아서 처리: " + e.getMessage());
        }
        checker.check("");                             // 잡지 않으면 위로 올라간다
        System.out.println("이 줄은 실행되지 않는다");
    }

JLS 8.4.6은 언체크 예외 클래스를 throws 절에 언급하는 것이 허용되지만 요구되지는 않는다고 적는다. 적더라도 호출자에게 처리를 강제하는 효과는 없고, 읽는 사람을 위한 문서 구실만 한다.

    런타임 예외를 검사에서 뺀 이유를 명세는 이렇게 설명한다. 자바 언어의 많은 연산과 구문이 실행 시점에 예외를 낼 수 있고, 컴파일러가 가진 정보와 분석 수준으로는 그런 예외가 일어나지 않는다는 것을 대개 입증할 수 없다. 프로그래머에게는 자명해도 그렇다. 그런 예외를 선언하게 하는 것은 프로그램의 정확성을 세우는 데 그다지 도움이 되지 않고 프로그래머에게 짜증만 줄 것이라는 것이 언어 설계자들의 판단이었다(JLS 11.2). 배열 원소 접근마다 ArrayIndexOutOfBoundsException을, 참조를 통한 메서드 호출마다 NullPointerException을 선언하거나 잡아야 한다고 상상해 보면 이 판단을 이해할 수 있다.

    한 층 아래 ③: 체크 여부는 컴파일러만 안다

    체크 예외와 언체크 예외는 실행 시점에 다르게 취급될까. 클래스 파일을 열어 보면 답이 나온다. throws 절이 있는 Uploader.upload를 javap -v -p Uploader로 본다.

    두 가지가 보인다. 던지는 명령어는 언체크 예외 때와 같은 athrow다. 체크 예외용 명령어가 따로 있지 않다. 그리고 throws 절은 메서드의 Exceptions 속성으로 클래스 파일에 기록되었다. 메서드 디스크립터 (J)V에는 예외에 대한 정보가 없다. 같은 방법으로 NameChecker.check를 보면 athrow는 있고 Exceptions 속성은 없다.

    이 속성을 JVM이 실행할 때 검사할까. JVMS 4.7.5는 메서드가 예외를 던져도 되는 조건 세 가지를 나열한다. 그 예외가 RuntimeException 또는 그 하위 클래스의 인스턴스이거나, Error 또는 그 하위 클래스의 인스턴스이거나, Exceptions 속성에 적힌 클래스 또는 그 하위 클래스의 인스턴스일 것. 그리고 바로 이어서 이렇게 적는다. 이 요구 사항은 자바 가상 머신에서 강제되지 않으며, 컴파일 시점에만 강제된다. 곧 "체크 예외는 잡거나 선언해야 한다"는 규칙은 자바 언어의 규칙이고 javac가 지키게 한다. JVM은 athrow로 올라온 객체가 체크 예외인지 묻지 않는다. Exceptions 속성은 그 클래스를 사용하는 다른 소스를 나중에 컴파일할 때 컴파일러가 읽는 정보다.

    이것은 실험으로 확인할 수 있다. 다음 코드는 제네릭 메서드의 타입 인자를 이용해 컴파일러의 검사를 통과하면서 체크 예외를 선언 없이 던진다. 실제 코드에 쓰라는 것이 아니다. 검사가 어디에 있는지를 보이기 위한 것이다.

    public class Sneaky {
    @SuppressWarnings("unchecked")
    static  void sneakyThrow(Throwable t) throws E {
        throw (E) t;
    }

    static void noThrowsClause() {
        Sneaky.sneakyThrow(new QuotaExceededException("선언 없이 올라온 체크 예외"));
    }

    public static void main(String[] args) {
        try {
            noThrowsClause();
        } catch (Exception e) {
            System.out.println("잡힌 타입: " + e.getClass().getName());
            System.out.println("RuntimeException인가: " + (e instanceof RuntimeException));
        }
    }
}
    잡힌 타입: QuotaExceededException
RuntimeException인가: false

    noThrowsClause()에는 throws 절이 없고 본문에 try-catch도 없는데, 체크 예외인 QuotaExceededException이 그 메서드를 뚫고 main까지 올라왔다. 컴파일러가 속은 경위는 이렇다. 호출 지점에서 타입 변수 E를 RuntimeException으로 지정했으므로, 컴파일러가 보기에 이 호출이 던질 수 있는 것은 RuntimeException, 곧 언체크 예외다. 그래서 선언을 요구하지 않는다. sneakyThrow 안의 (E) t는 타입 변수로의 형변환이라 실행 시점에 검사되지 않는다. 실제로 이 메서드의 바이트코드는 aload_0과 athrow 두 명령어뿐이다. 그리고 JVM은 athrow에 올라온 객체가 무엇이든 Throwable이기만 하면 던진다.

    이 사실에서 실용적인 결론 두 가지가 나온다. 첫째, 체크·언체크의 구분은 실행 성능이나 전파 방식과 무관하다. 설계할 때 따질 것은 "호출자에게 처리를 강제할 것인가"라는 컴파일 시점의 문제 하나다. 둘째, 컴파일러의 보증은 "함께 컴파일된 소스" 범위의 보증이다. 따로 컴파일된 클래스 파일이 섞이거나 위와 같은 우회가 있으면, 선언에 없는 체크 예외가 실행 중에 올라올 수 있다. 가장 바깥의 방어선에서 catch (Exception e)로 넓게 잡는 코드가 존재하는 이유 가운데 하나다.

    체크 예외 규칙은 javac가 소스와 Exceptions 속성을 보고 검사할 뿐이며, JVM은 체크와 언체크를 구별하지 않고 같은 athrow와 예외 테이블로 처리한다는 것을 두 구역으로 나누어 보여 준다. 가로로 세 구역이 이어지는 구조 다이어그램. 흰 배경, 얇은 선, 파랑과 회색, 강조는 주황. 왼쪽 구역 제목 "소스 코드": 문서 아이콘 두 개, 위쪽 문서에 "throws QuotaExceededException", 아래쪽 문서에 "throw new InvalidFileNameException". 가운데 구역 제목 "javac (컴파일 시점)": 돋보기 아이콘이 있는 상자, 그 안에 문구 "체크 예외인가? 잡았는가, 선언했는가?", 상자 아래로 빨간 X 표시와 라벨 "아니면 컴파일 오류". 가운데에서 오른쪽으로 나가는 화살표 위에 문서 아이콘 "클래스 파일"과 작은 꼬리표 "Exceptions 속성". 오른쪽 구역 제목 "JVM (실행 시점)": 상자 하나에 세 줄 "athrow", "예외 테이블 검색", "스택 풀기". 상자 아래 라벨 "체크와 언체크를 구별하지 않는다". 가운데 구역과 오른쪽 구역 사이에 세로 점선을 긋고 점선 위에 라벨 "검사는 여기까지". 잡거나 선언하라는 규칙은 javac가 검사한다. JVM은 어떤 예외든 같은 방식으로 던지고 전파한다.

    흔한 오해와 함정

    "체크 예외는 컴파일할 때 발생하는 예외다"

    모든 예외는 프로그램이 실행되는 동안 발생한다. 컴파일할 때 생기는 것은 예외가 아니라 컴파일 오류다. "체크"가 뜻하는 것은 예외의 발생 시점이 아니라, 컴파일러가 그 예외에 대한 처리 코드가 있는지를 확인한다는 것이다. 같은 오해의 다른 얼굴이 "RuntimeException은 실행 시점에 발생하는 예외이고 나머지는 아니다"다. 이름이 주는 인상과 달리 IOException도 실행 시점에 발생한다. JLS 11.1.1이 RuntimeException에 대해 말하는 것은 식을 평가하는 동안 여러 이유로 던져질 수 있는 예외들의 상위 클래스라는 것이지, 실행 시점에 발생하는 예외가 이 가지뿐이라는 것이 아니다.

    throw와 throws를 섞어 쓴다

    throw는 문장이다. 메서드 본문 안에서 실행되고, 실행되면 예외가 던져진다. throws는 선언이다. 메서드 머리에 붙고, 아무것도 실행하지 않는다. "이 메서드는 이런 체크 예외로 끝날 수 있다"는 사실을 컴파일러와 호출자에게 알릴 뿐이다. throws가 있다고 예외가 던져지는 것이 아니고, throws가 없다고 예외가 못 올라오는 것도 아니다(언체크 예외는 선언 없이 올라온다).

    "catch (Exception e)면 무엇이든 잡힌다"

    Exception은 계층의 뿌리가 아니다. Error 가지는 Exception의 하위가 아니므로 잡히지 않는다.

    public class ErrorPass {
    static int depth = 0;

    static void recurse() {
        depth++;
        recurse();
    }

    public static void main(String[] args) {
        try {
            try {
                recurse();
            } catch (Exception e) {
                System.out.println("안쪽 catch (Exception): 여기로 오지 않는다");
            }
        } catch (Throwable t) {
            System.out.println("바깥 catch (Throwable): " + t.getClass().getName());
            System.out.println("Exception인가: " + (t instanceof Exception));
            System.out.println("Error인가: " + (t instanceof Error));
        }
    }
}
    바깥 catch (Throwable): java.lang.StackOverflowError
Exception인가: false
Error인가: true

    끝없는 재귀로 스택이 넘치면 JVM이 StackOverflowError를 던진다. 안쪽의 catch (Exception e)는 타입이 맞지 않아 지나치고, 바깥의 catch (Throwable t)에서야 잡힌다. 이 예제는 계층을 확인하려고 Throwable을 잡았을 뿐이다. 애플리케이션 코드에서 Throwable이나 Error를 잡아 계속 진행하려는 시도는 피한다. 그 시점의 JVM이 정상적으로 일을 계속할 수 있는 상태인지 보장할 수 없다.

    "예외를 잡으면 던진 곳으로 돌아가 이어서 실행한다"

    돌아가지 않는다. catch 블록이 끝나면 그 try 문의 다음 문장으로 간다. 스택 풀기에서 본 대로 던진 메서드의 프레임은 이미 버려졌다. 실패한 작업을 다시 하고 싶다면 그 작업을 처음부터 다시 호출하는 코드를 직접 써야 한다.

    빈 catch 블록

    체크 예외의 컴파일 오류를 없애는 가장 빠른 방법은 try { … } catch (Exception e) { }다. 컴파일러는 만족하고, 프로그램은 이 회차의 처음에 본 "실패를 모르는 프로그램"이 된다. 예외를 잡았으면 의미 있는 대응(복구, 대체 동작, 사용자에게 알림)을 하거나, 최소한 기록을 남기고 다시 던져야 한다. 할 수 있는 대응이 없다면 잡지 않는 것이 옳다.

    "스택 트레이스의 맨 윗줄은 예외를 던진 곳이다"

    대개는 맞지만 정확히는 예외 객체를 만든 곳이다. WhereCaptured에서 확인했다. 그리고 스택 트레이스의 행 번호는 클래스 파일에 기록된 행 번호 정보에서 온다. javap -v 출력의 LineNumberTable이라는 항목이 그것이다(앞의 Uploader 발췌에서는 생략한 부분에 있다). 소스와 다른 버전의 클래스 파일이 실행되고 있으면 행 번호가 지금 보고 있는 소스와 어긋난다.

    다른 주제와의 연결

    10회(예외 처리 2). 이번 회차에서 세운 규칙을 백업 예제에 적용한다. 반환 코드를 예외로 바꾸면 정상 흐름과 오류 처리가 어떻게 갈라지는지, 예외가 흐름을 끊어도 close()가 반드시 실행되게 하는 finally와 try-with-resources, 정리 도중에 난 예외가 원래 예외를 덮지 않게 하는 suppressed 예외, 예외 계층을 설계하는 방법과 체크·언체크 중 무엇을 기본으로 삼을지의 실무 판단이 거기서 나온다.

    스프링의 트랜잭션. 체크와 언체크의 구분은 프레임워크의 기본 동작에도 들어와 있다. Spring Framework Reference에 따르면 스프링의 트랜잭션 인프라는 기본 설정에서 런타임(언체크) 예외일 때만, 곧 던져진 예외가 RuntimeException의 인스턴스이거나 하위 클래스일 때만 트랜잭션을 롤백 대상으로 표시한다(Error도 기본적으로 롤백된다). 트랜잭션 메서드에서 던져진 체크 예외는 기본 설정에서 롤백을 일으키지 않는다. "예외가 났으니 롤백됐겠지"라는 짐작이 체크 예외에서는 틀린다는 뜻이고, 이번 회차의 계층도를 알아야 이 문장을 읽을 수 있다.

    데이터 접근 계층. JDBC의 SQLException은 계층도에서 본 대로 체크 예외다. Spring Framework Reference의 DAO 지원 절은 스프링이 SQLException 같은 기술별 예외를 DataAccessException을 뿌리로 하는 자체 예외 계층으로 변환해 주며, 그 덕분에 복구할 수 없는 대부분의 영속성 예외를 DAO에 번거로운 catch-and-throw 블록이나 예외 선언을 두지 않고 적절한 계층에서만 처리할 수 있다고 설명한다. "체크 예외의 득과 실"에서 본 시그니처 전파 문제를 프레임워크가 어떻게 다루는지의 실제 사례다.

    스레드와 서버. 예외는 스레드 하나의 호출 스택 안에서만 전파되고, 잡히지 않으면 그 스레드를 끝낸다. 요청마다 스레드를 배정하는 서버에서 요청 처리 코드의 맨 바깥에 공통 예외 처리가 있는 이유, 별도 스레드에 맡긴 작업의 예외가 맡긴 쪽의 try-catch에 잡히지 않는 이유가 여기서 나온다. 로드맵의 멀티스레드 권과 스프링 MVC 권에서 이 사실 위에 내용이 쌓인다.
    반환값으로 오류 알리기의 한계
    정상 흐름과 오류 처리가 섞이고, 검사를 빠뜨려도 드러나지 않으며(무시가 기본), 반환 통로를 오류 코드가 차지하고, 중간 계층이 손으로 전달해야 하고, 실패 정보가 빈약하다.
    예외와 갑작스러운 완료
    예외는 반환과 별개인 메서드의 두 번째 출구다. 예외로 끝난 호출은 값을 돌려주지 않고, 호출자가 잡지 않으면 호출자도 같은 방식으로 끝난다. 전파가 기본이다.
    예외 계층
    Throwable 아래에 Error와 Exception이 있고, Exception 아래에 RuntimeException이 있다. RuntimeException 가지와 Error 가지가 언체크, 나머지가 체크다(JLS 11.1.1).
    기본 규칙
    예외는 잡아서 처리하거나 호출자에게 던진다. catch와 throws에 지정한 타입은 그 하위 타입까지 포함한다. catch가 여럿이면 위에서부터 처음 맞는 하나만 실행된다.
    예외 테이블과 스택 풀기
    try-catch는 메서드의 예외 테이블 행(범위, 핸들러 위치, 타입)으로 컴파일된다. 예외가 나면 JVM은 현재 메서드의 테이블을 순서대로 검색하고, 맞는 행이 없으면 프레임을 버리고 호출자에서 되풀이한다.
    잡히지 않은 예외
    끝까지 핸들러가 없으면 그 스레드가 종료되고, 종료 전에 잡히지 않은 예외 핸들러가 실행된다. 기본 동작은 표준 오류에 스레드 이름과 스택 트레이스를 찍는 것이다. 다른 스레드는 영향을 받지 않는다.
    체크 예외
    잡거나 throws로 선언하지 않으면 컴파일 오류다. 처리 누락을 컴파일러가 잡아 주지만, 다룰 수 없는 계층까지 선언이 퍼지고 오버라이딩에서 새 체크 예외를 추가할 수 없다.
    언체크 예외
    선언과 처리를 강제하지 않는다. 중간 계층이 아무것도 쓰지 않아도 되지만, 처리 누락은 실행해 봐야 드러난다.
    검사의 주체
    체크 예외 규칙은 javac가 컴파일 시점에만 검사한다. throws는 클래스 파일의 Exceptions 속성으로 남지만 JVM은 그것을 강제하지 않고(JVMS 4.7.5), 체크와 언체크를 같은 athrow로 처리한다.

    실무에서 가장 자주 내리는 판단은 "여기서 잡을 것인가"다. 기준은 그 자리에서 의미 있는 일을 할 수 있느냐다. 재시도, 대체 경로, 사용자에게 보여 줄 응답 만들기, 더 알맞은 예외로 바꿔 던지기 가운데 하나라도 할 수 있으면 잡는다. 할 수 있는 일이 로그 한 줄 찍는 것뿐이라면 대개는 잡지 않고 올려 보내, 요청이나 작업 단위의 맨 바깥에 있는 공통 처리 지점 한 곳에서 기록하고 응답하게 한다. 중간 계층마다 잡아서 로그를 찍고 다시 던지면 같은 실패가 로그에 여러 번 남고, 중간에서 잡고 삼키면 이 회차 처음의 "백업 완료" 거짓 보고가 재현된다. 장애 분석에서 "예외가 났는데 로그에 없다"는 상황의 원인은 높은 비율로 빈 catch 블록이거나, 표준 오류로만 나간 스택 트레이스를 수집하지 않은 것이다.

    반환값과 예외 사이의 선택도 여전히 살아 있는 판단이다. 찾는 것이 없을 수 있는 조회, 스트림의 끝처럼 "없음"이 정상 결과의 하나라면 반환값으로 표현하는 편이 호출 코드가 단순하다. 호출자가 그대로 진행하면 안 되는 실패, 곧 무시되었을 때 데이터가 틀어지거나 거짓 성공이 보고되는 실패는 예외로 표현한다. 구별하는 질문은 "호출자가 이 결과를 확인하지 않고 다음 줄로 가도 괜찮은가"다. 괜찮지 않다면 무시가 기본인 통로에 실어서는 안 된다.

    체크 예외를 쓸지는 "호출자가 이 실패를 복구할 수 있고, 그 사실을 컴파일러가 강제할 가치가 있는가"로 정한다. 조건이 맞지 않는데 체크 예외를 쓰면 호출 사슬 전체에 throws가 퍼지고, 인터페이스에 구현 기술의 예외 타입이 새겨져 구현을 바꾸기 어려워진다. 반대로 언체크 예외만 쓰는 코드베이스에서는 어떤 예외가 올라올 수 있는지를 문서와 테스트로 관리해야 한다. 그리고 프레임워크의 기본값을 확인해야 한다. 스프링의 선언적 트랜잭션은 기본 설정에서 체크 예외에 롤백하지 않으므로, 체크 예외를 던지는 트랜잭션 메서드에서는 데이터가 반쯤 반영된 채 커밋될 수 있다. 이런 문제는 예외가 체크인지 언체크인지를 계층도에서 바로 판별할 수 있어야 코드 리뷰에서 걸러진다.

    4. (가) 컴파일되지 않는다. 인자가 10이라 실행하면 예외가 나지 않겠지만, 컴파일러는 runAndPass의 throws 절만 보고 이 호출식이 QuotaExceededException을 던질 수 있다고 본다. 잡지도 선언하지도 않았으므로 unreported exception 오류다. (나) 컴파일되지 않는다. try 본문이 던질 수 없는 체크 예외를 잡으려 했다(is never thrown in body of corresponding try statement). (다) 컴파일된다. JLS 11.2.3의 규칙은 Exception과 그 상위 클래스를 예외로 둔다. Exception의 하위에는 어디서든 나올 수 있는 언체크 예외가 있기 때문이다. (라) 컴파일되지 않는다. 재정의하는 메서드는 부모 메서드가 선언하지 않은 체크 예외를 선언할 수 없다. 부모 타입 변수로 호출하는 코드는 처리 없이 컴파일되어 있을 것이므로, 허용하면 컴파일러의 보증이 깨진다. (마) 컴파일된다. 예외를 줄이는 방향은 부모 타입으로 호출하는 코드의 처리를 불필요하게 만들 뿐 깨뜨리지 않는다.

    5. 출력은 업로드 완료 한 줄이다. upload(5_000)은 "전송" 메시지를 찍기 전에 예외를 던지고, 빈 catch가 그것을 삼키고, 실행은 try 문 다음의 출력문으로 간다. 실패했는데 성공을 보고한다는 점에서 "오류 상황 만들기" 절의 프로그램, 그리고 반환 코드를 검사하지 않은 프로그램과 같다. 예외가 준 "무시가 기본이 아니다"라는 성질을 빈 catch가 되돌린 것이다. 수정 방향은 둘이다. 이 메서드가 실패에 대응할 수 있다면 catch 안에서 실제로 대응하고(실패 메시지를 남기고 "업로드 완료"를 찍지 않도록 완료 출력을 try 블록 안으로 옮긴다), 대응할 수 없다면 try-catch를 없애고 메서드에 throws QuotaExceededException을 선언해 호출자에게 넘긴다.

     오류를 반환 코드로 알리는 방식과 예외로 알리는 방식의 가장 근본적인 차이는 무엇인가? 반환 코드는 문자열만 쓸 수 있지만 예외는 객체를 쓸 수 있다. 호출자가 아무 코드도 쓰지 않았을 때, 반환 코드는 무시되어 실행이 계속되고 예외는 호출 스택을 따라 계속 전파된다. 반환 코드는 실행 시점에 처리되고 예외는 컴파일 시점에 처리된다. 예외를 쓰면 실패 자체가 일어나지 않게 된다. 두 방식을 가르는 것은 기본 동작이다. 반환 코드는 검사하지 않으면 사라지므로 실패한 채로 다음 줄이 실행되고, 예외는 잡지 않으면 호출자에게 올라가 결국 스레드를 끝낸다. 반환 코드도 객체로 만들 수 있으므로 첫째 보기는 본질이 아니다. 예외도 실행 시점에 발생하고 처리되므로 셋째는 틀렸다. 예외는 실패를 알리는 수단일 뿐 실패를 없애지 않는다. 메서드 m의 try 블록 안에서 호출한 메서드가 예외를 던졌고, m의 catch 절이 그 예외를 잡았다. catch 블록이 정상적으로 끝난 뒤 실행은 어디로 가는가? 예외를 던진 메서드의 throw 문 다음 줄로 돌아간다. try 블록에서 예외가 난 호출의 다음 문장으로 돌아간다. 그 try 문 다음의 문장으로 간다. m이 즉시 반환하고 m의 호출자로 간다. catch 블록이 끝나면 try 문 전체가 정상적으로 완료된 것이 되어 그다음 문장이 실행된다. 예외를 던진 메서드의 프레임은 스택 풀기 과정에서 이미 버려졌으므로 그 안으로 돌아갈 수 없고, try 블록의 남은 부분도 건너뛴 채로 끝난다. m이 반환하는 것은 catch 블록이나 그 뒤의 코드가 return을 실행할 때뿐이다. 체크 예외에 대한 설명으로 옳은 것은? 잡거나 throws로 선언했는지를 컴파일러가 검사하며, JVM은 실행 시점에 체크 예외와 언체크 예외를 구별해 다루지 않는다. 컴파일하는 동안 발생하는 예외라서 실행 시점에는 발생하지 않는다. JVM이 메서드의 Exceptions 속성을 확인해, 선언되지 않은 체크 예외가 던져지면 실행을 거부한다. Exception을 상속한 모든 클래스가 체크 예외다. 체크 예외 규칙은 자바 언어의 규칙이고 javac가 컴파일 시점에만 강제한다. JVMS 4.7.5는 Exceptions 속성과 관련된 요구 사항이 JVM에서 강제되지 않는다고 명시하며, 던지는 명령어도 athrow로 같다. 모든 예외는 실행 시점에 발생한다. RuntimeException은 Exception을 상속하지만 언체크이므로 마지막 보기도 틀렸다. catch (Exception e)로 감싼 코드에서 끝없는 재귀가 일어나 StackOverflowError가 던져졌다. 이 catch가 그것을 잡지 못하는 이유는? StackOverflowError는 JVM이 던진 것이고 catch는 throw 문으로 던진 예외만 잡기 때문이다. StackOverflowError는 체크 예외라서 throws 선언이 있어야 잡을 수 있기 때문이다. 스택이 넘친 뒤에는 예외 테이블 검색이 수행되지 않기 때문이다. StackOverflowError는 Error의 하위 클래스이고, Error는 Exception의 하위 클래스가 아니기 때문이다. catch는 던져진 객체가 지정한 타입 또는 그 하위 타입일 때만 잡는다. StackOverflowError의 부모 사슬은 VirtualMachineError, Error, Throwable이고 Exception을 거치지 않는다. JVM이 던진 예외도 athrow로 던진 예외와 같은 방식으로 예외 테이블을 검색하므로 첫째와 셋째는 틀렸다. Error 가지는 언체크다. 스택 트레이스에 기록되는 호출 스택은 어느 시점의 것인가? 예외가 catch 블록에 도착한 시점 printStackTrace()가 호출된 시점 예외 객체가 생성된 시점 throw 문이 실행된 시점 Throwable의 Javadoc은 throwable이 생성된 시점의 스레드 실행 스택 스냅숏을 담는다고 적고, 생성자가 fillInStackTrace()를 호출한다. 그래서 미리 만들어 둔 예외를 다른 메서드에서 던지면 스택 트레이스에는 던진 메서드가 아니라 만든 메서드가 나온다. catch에 도착했을 때나 출력할 때는 관련 프레임이 이미 버려져 있어 그 시점의 스택으로는 발생 경로를 알 수 없다.
    예외(exception)
    정상적인 실행을 계속할 수 없는 상황을 나타내는 객체. Throwable 또는 그 하위 클래스의 인스턴스이며, 던져지면 처리할 핸들러를 찾을 때까지 호출 스택을 거슬러 올라간다.
    갑작스러운 완료(abrupt completion)
    메서드 호출이 값을 반환하지 않고 예외로 끝나는 것. 메서드 안에서 던져진 예외가 그 메서드 안에서 처리되지 않을 때 일어난다(JVMS 2.6.5).
    체크 예외(checked exception)
    Throwable의 하위 클래스 중 RuntimeException 가지와 Error 가지를 뺀 것. 잡거나 throws로 선언하지 않으면 컴파일 오류가 난다.
    언체크 예외(unchecked exception)
    RuntimeException과 그 하위 클래스, Error와 그 하위 클래스. 컴파일러가 처리나 선언을 요구하지 않는다.
    throws 절(throws clause)
    메서드나 생성자 선언에 붙어, 그 본문이 던질 수 있는 예외 클래스를 알리는 선언. 체크 예외에 대해서는 필수이고 클래스 파일의 Exceptions 속성으로 기록된다.
    예외 테이블(exception table)
    클래스 파일에서 메서드의 Code 속성에 딸린 표. 각 행이 핸들러 하나로, 유효 범위(start_pc 이상 end_pc 미만), 핸들러 시작 위치, 잡을 예외 타입을 담는다.
    스택 풀기(stack unwinding)
    맞는 핸들러가 없는 메서드의 프레임을 버리고 호출자의 프레임에서 핸들러 검색을 되풀이하는 과정. 버려진 프레임은 되살릴 수 없다.
    스택 트레이스(stack trace)
    예외 객체가 생성된 시점에 그 스레드의 호출 스택이 어땠는지에 대한 기록. 맨 위가 가장 최근에 호출된 메서드다.
    잡히지 않은 예외 핸들러(uncaught exception handler)
    어떤 catch에도 잡히지 않은 예외로 스레드가 종료되기 직전에 실행되는 핸들러. 따로 설정하지 않으면 표준 오류에 스레드 이름과 스택 트레이스가 출력된다.
