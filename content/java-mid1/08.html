    이 회차의 질문: 끝난 메서드의 지역 변수를 누가 들고 있는가

    앞 회차는 클래스 안에 선언하는 클래스, 곧 중첩 클래스(nested class) 가운데 클래스의 멤버 자리에 선언하는 정적 중첩 클래스와 내부 클래스를 다뤘다. 이번 회차는 남은 두 종류를 다룬다. 메서드 본문 같은 블록 안에 선언하는 지역 클래스(local class)와, 선언과 동시에 인스턴스를 만들고 이름은 붙이지 않는 익명 클래스(anonymous class)다. 자바 언어 명세(JLS) 8.1.3절은 static이 아닌 멤버 클래스, 지역 클래스(enum과 레코드를 뺀 일반 클래스), 익명 클래스를 묶어 내부 클래스(inner class)라고 정의한다.

    문법만 보면 새로울 것이 적다. 클래스 선언을 메서드 안으로 옮겼을 뿐이다. 그런데 선언 위치가 메서드 안이 되면 그 클래스의 코드가 메서드의 지역 변수와 매개변수를 쓸 수 있게 되고, 여기서 지금까지 배운 메모리 모델과 맞지 않아 보이는 일이 생긴다. 지역 변수는 메서드가 호출될 때 스택 프레임에 만들어지고 메서드가 끝나면 프레임과 함께 사라진다. 반면 지역 클래스로 만든 인스턴스는 힙에 있고, 메서드가 끝난 뒤에도 누군가 참조하고 있으면 계속 살아 있다. 살아남은 인스턴스가 이미 사라진 지역 변수를 읽는 코드가 컴파일되고 정상적으로 동작한다.

    이 회차의 앞쪽 절반은 이 현상의 설명이다. 자바 가상 머신 명세(JVMS)가 정한 프레임의 수명, 컴파일러가 클래스 파일에 넣어 두는 숨은 필드, 그 구조에서 따라 나오는 "사실상 final" 규칙을 차례로 본다. 뒤쪽 절반은 익명 클래스다. 익명 클래스는 지역 클래스와 같은 구조에서 이름만 뺀 것이므로 캡처 규칙이 그대로 적용된다. 익명 클래스가 주로 쓰이는 자리인 "코드 조각을 인자로 넘기기"를 중복 제거 과정으로 따라가고, 같은 자리를 람다가 대신할 때 컴파일 결과가 어떻게 달라지는지도 확인한다. 본문의 실행 결과, 컴파일 오류 문구, javap 출력은 모두 JDK 21(Temurin 21.0.13)에서 직접 실행해 확인한 것이다.

    지역 클래스: 블록 안에서 선언하는 클래스

    지역 클래스는 지역 변수와 같은 자리에 선언한다. 메서드 본문, 생성자 본문, 초기화 블록처럼 문장이 올 수 있는 블록 안이다. 선언 위치에서 나오는 규칙도 지역 변수와 닮았다(JLS 14.3, 6.3).

    • 접근 제어자를 붙일 수 없다. public, protected, private은 선언한 곳 바깥에서 누가 볼 수 있는지를 정하는데, 지역 클래스는 애초에 블록 밖에서 이름으로 가리킬 수 없다. static도 붙일 수 없다. abstract와 final은 붙일 수 있다.
    • 유효 범위(scope)는 선언한 곳부터 그 블록의 끝까지다. 자기 자신의 선언도 범위에 들어가므로 본문 안에서 자기 타입을 쓸 수 있다. 선언보다 앞선 줄에서 쓰면 cannot find symbol 오류가 난다.
    • 그 밖에는 보통 클래스와 같다. 필드, 메서드, 생성자를 가질 수 있고 클래스를 상속하거나 인터페이스를 구현할 수 있다.

    블록 밖에서는 지역 클래스의 이름을 쓸 수 없으므로, 지역 클래스로 만든 객체를 메서드 밖으로 내보내려면 밖에서도 보이는 상위 타입이 필요하다. 그래서 지역 클래스는 대개 인터페이스를 구현하거나 클래스를 상속하고, 호출자는 그 상위 타입으로 객체를 받는다. 다음 예제는 가격표 문구를 만드는 객체를 지역 클래스로 정의해 인터페이스 타입으로 돌려준다.

    public interface Labeler {
    String label(int price);
}
    public class Shop {
    private final String currency;

    public Shop(String currency) {
        this.currency = currency;
    }

    public Labeler labeler(String prefix) {
        int taxPercent = 10;

        class TaxLabeler implements Labeler {
            private int calls;

            @Override
            public String label(int price) {
                calls++;
                int total = price + price * taxPercent / 100;
                return prefix + total + currency + " (" + calls + "번째)";
            }
        }

        return new TaxLabeler();
    }

    public static void main(String[] args) {
        Shop shop = new Shop("원");
        Labeler labeler = shop.labeler("판매가 ");
        System.out.println(labeler.label(1000));
        System.out.println(labeler.label(25000));
        System.out.println(labeler.getClass().getName());
    }
}

    label() 메서드 한 곳에서 출처가 다른 네 종류의 이름을 쓰고 있다. 이 구분이 이 회차 전체의 뼈대이므로 표로 정리해 둔다.

    label()이 쓰는 이름선언된 곳종류
    price, totallabel() 자신자신의 매개변수와 지역 변수
    callsTaxLabeler자신의 인스턴스 필드

    첫 두 줄은 보통 클래스의 메서드가 늘 하던 일이다. 넷째 줄은 앞 회차의 내부 클래스와 같다. 인스턴스 메서드 안에서 선언한 지역 클래스는 내부 클래스이므로 바깥 인스턴스의 멤버에 접근할 수 있고, private 필드도 예외가 아니다. 새로운 것은 셋째 줄이다. 클래스의 메서드가 다른 메서드의 지역 변수를 읽는다.

    출력 셋째 줄의 Shop$1TaxLabeler는 이 클래스의 바이너리 이름(binary name)이다. JLS 13.1은 지역 클래스의 바이너리 이름을 "바깥 클래스의 바이너리 이름 + $ + 숫자열 + 지역 클래스의 단순 이름"으로 정한다. 숫자가 끼는 이유는 지역 클래스의 이름이 블록 안에서만 유일하면 되기 때문이다. 한 클래스의 두 메서드가 각각 Helper라는 지역 클래스를 선언해도 되고, 이때 JDK 21의 javac는 Outer$1Helper와 Outer$2Helper라는 두 클래스 파일을 만든다. 컴파일이 끝나면 지역 클래스도 독립된 .class 파일 하나가 되고, JVM은 이 클래스를 다른 클래스와 같은 방식으로 로딩하고 실행한다. 어느 메서드 안에서 선언되었는지는 클래스 파일의 속성에 기록으로만 남는데, 이 기록은 뒤에서 다시 본다.

    하나 더 확인할 것이 있다. 지역 클래스의 선언은 실행되는 문장이 아니다. labeler() 메서드의 바이트코드를 보면 taxPercent에 10을 넣는 명령어 다음이 곧바로 new다.

    클래스 선언에 해당하는 명령어는 없다. 클래스는 컴파일할 때 이미 만들어졌고, 실행 중에 메서드가 선언 위치를 지나가도 아무 일도 일어나지 않는다. 메서드를 백 번 호출해도 클래스는 하나이고, 호출마다 새로 생기는 것은 new가 만드는 인스턴스다. 7~10번 명령어에 소스에 없던 인자 세 개가 생성자로 넘어가는 것이 보이는데, 이것이 뒤에서 풀 캡처의 실체다.

    Java 16부터는 블록 안에 인터페이스, enum, 레코드도 선언할 수 있다(javac --release 15로 컴파일하면 지역 enum은 enum classes must not be local 오류가 난다). JLS 14.3은 이 셋이 암묵적으로 static이라고 정한다. 내부 클래스가 아니므로 바깥 메서드의 지역 변수를 쓸 수 없고, 쓰면 non-static variable x cannot be referenced from a static context 오류가 난다. 이 회차에서 말하는 지역 클래스는 일반 클래스로 선언한 것만 가리킨다.

    지역 변수 캡처 1: 변수와 인스턴스의 수명이 다르다

    변수가 어디에 저장되는지에 따라 수명이 정해진다. 지금까지 배운 것을 한 표로 모으면 다음과 같다.

    변수의 종류저장되는 곳생기는 때사라지는 때
    지역 변수, 매개변수스레드의 JVM 스택에 있는 프레임메서드 호출메서드 종료(정상 반환이든 예외든)
    인스턴스 필드힙의 객체 안객체 생성객체가 가비지 컬렉션으로 회수될 때
    static 필드클래스에 딸린 저장 공간클래스 준비·초기화클래스가 언로드될 때

    프레임(frame)의 수명은 JVMS 2.6이 정한다. 메서드가 호출될 때마다 새 프레임이 만들어지고, 그 호출이 끝나면 정상 종료든 예외로 인한 종료든 프레임이 파괴된다. 프레임은 자신만의 지역 변수 배열과 피연산자 스택을 갖는다. 그리고 JVMS 2.5.2에 따라 JVM 스택은 스레드마다 하나씩 따로 있다. 힙은 반대다. JVMS 2.5.3은 힙을 모든 스레드가 공유하는 영역으로, 모든 클래스 인스턴스와 배열이 할당되는 곳으로 정의한다. 객체는 메서드 호출의 시작과 끝에 묶여 있지 않고, 도달할 수 있는 참조가 남아 있는 한 살아 있다.

    이 규칙으로 앞의 main()을 한 줄씩 따라가 보자. 지역 변수 배열의 칸 번호는 위 바이트코드에서 읽은 것이다. 인스턴스 메서드의 0번 칸은 this이고, labeler()에서 1번 칸은 매개변수 prefix(aload_1), 2번 칸은 taxPercent(istore_2)다.

    ④에서 labeler()의 프레임은 파괴되었다. taxPercent가 들어 있던 2번 칸과 prefix가 들어 있던 1번 칸은 프레임과 함께 없어졌다. 그런데 ⑤에서 실행되는 label()의 본문에는 taxPercent와 prefix가 적혀 있고, 실행 결과는 10%를 더한 값과 "판매가 "를 정확히 출력했다.

    인스턴스가 사라진 프레임의 칸을 가리키고 있다가 읽는 것이 아닐까 생각할 수 있지만, JVM의 구조상 그런 일은 일어날 수 없다. 이유는 세 가지다. 첫째, 프레임은 메서드가 끝나면 파괴된다고 명세가 정하고 있으므로 가리킬 대상이 남아 있지 않다. 둘째, JVMS 2.4가 정의하는 참조(reference) 값은 클래스 인스턴스나 배열, 곧 힙의 객체를 가리키거나 null이다. 지역 변수 칸을 가리키는 참조라는 값의 종류는 없다. 셋째, JVMS 2.6은 한 스레드가 만든 프레임은 그 스레드에 국한되며 다른 스레드가 참조할 수 없다고 적는다. 힙의 객체는 다른 스레드로 넘겨질 수 있는데, 그 객체가 원래 스레드의 프레임 안을 들여다본다면 이 규칙이 깨진다.

    따라서 남는 방법은 하나다. 프레임이 살아 있는 동안 필요한 값을 프레임 밖, 곧 오래 사는 쪽인 인스턴스 안으로 옮겨 두는 것이다. 자바 컴파일러가 실제로 하는 일이 이것이고, 이 동작을 지역 변수 캡처(capture)라고 부른다.

    가로축을 시간으로 두고, 스택의 labeler 프레임 수명 막대는 짧게 끝나고 힙의 TaxLabeler 인스턴스 수명 막대는 그 뒤로도 이어지는 것을 보여 준다. label() 호출 시점에는 프레임이 이미 없다는 점이 핵심이다. 흰 배경의 평면 벡터 타임라인 다이어그램. 가로축은 왼쪽에서 오른쪽으로 흐르는 시간 화살표이며 라벨 "시간". 위아래 두 개의 레인으로 나눈다. 위 레인 제목 "스택 (main 스레드)", 아래 레인 제목 "힙". 위 레인에는 전체 길이의 긴 회색 막대 "main 프레임"이 있고, 그 위에 가운데 구간에만 걸친 짧은 파란 막대 "labeler 프레임"이 있다. 파란 막대 안에 작은 글씨 "prefix, taxPercent = 10". 파란 막대의 오른쪽 끝에 빨간 세로선과 라벨 "반환: 프레임 파괴". 아래 레인에는 파란 막대의 중간 지점에서 시작해 화면 오른쪽 끝까지 이어지는 초록 막대 "TaxLabeler 인스턴스". 파란 막대에서 초록 막대의 시작점으로 내려가는 굵은 주황 화살표와 라벨 "new 시점에 값 복사". 빨간 세로선보다 오른쪽 시점에 위 레인에 작은 보라 막대 "label 프레임"을 그리고, 거기서 초록 막대로 내려가는 화살표에 라벨 "필드에서 읽는다". 지역 변수는 프레임과 함께 사라지지만 인스턴스는 힙에 남는다. label()이 실행될 때 읽을 수 있는 것은 인스턴스 안에 있는 값뿐이다.

    참조형 변수는 참조값이 복사된다

    prefix는 String 타입의 변수였다. 변수에 들어 있던 것은 문자열 객체 자체가 아니라 그 객체를 가리키는 참조값이고, 복사되는 것도 참조값이다. 문자열 객체는 힙에 하나만 있고 프레임의 칸과 val$prefix 필드가 같은 객체를 가리켰다. 프레임이 사라지면 가리키는 쪽이 하나 줄어들 뿐 객체는 그대로다. 캡처한 것이 가변 객체라면 그 객체의 상태 변경은 양쪽에서 모두 보인다. 이 점은 뒤에서 배열을 이용한 우회를 볼 때 다시 나온다.

    무엇이 필드로 만들어지는지는 쓰임에 따라 달라진다

    컴파일러는 클래스 본문에서 실제로 쓴 것만 캡처한다. JDK 21의 javac로 몇 가지 경우를 컴파일해 javap -p -s로 확인한 결과는 다음과 같다. 바깥 클래스 이름은 Cap, 캡처하는 지역 변수는 int n이다.

    둘째 줄이 눈에 띈다. 인스턴스 메서드 안의 지역 클래스이므로 생성자는 바깥 인스턴스를 받지만, 본문이 바깥 인스턴스를 쓰지 않으면 this$0 필드는 만들어지지 않는다. JDK 21에 들어 있는 javac 소스(Lower.shouldEmitOuterThis)에 따르면 클래스 파일 대상 버전이 18 이상이고, 본문이 바깥 인스턴스를 쓰지 않으며, 클래스가 직렬화 가능(serializable)하지 않을 때 이 필드를 생략한다. 같은 소스를 javac --release 17로 컴파일하면 this$0 필드가 그대로 남는 것도 확인했다. 이것은 javac라는 구현의 동작이고 언어 명세가 정한 것은 아니다.

    셋째 줄은 명세가 정한 것이다. JLS 8.1.3은 static 문맥(static 메서드, static 초기화 블록 등)에서 선언한 지역 클래스와 익명 클래스의 인스턴스에는 바로 바깥 인스턴스가 없다고 정한다. static 메서드에는 this가 없으니 넘겨줄 바깥 인스턴스도 없다.

    넷째 줄은 상수의 경우다. JLS 4.12.4는 기본형이나 String 타입의 final 변수가 상수식으로 초기화되어 있으면 상수 변수(constant variable)라고 부른다. 컴파일러는 상수 변수를 쓴 자리에 값을 직접 써넣으므로 복사해 둘 필요가 없다. 실제로 이 경우 메서드의 바이트코드에는 필드 읽기 대신 bipush 100이 들어간다. 반대로 맨 처음 예제의 int taxPercent = 10;은 final을 붙이지 않았으므로 상수 변수가 아니고, 그래서 val$taxPercent 필드가 만들어졌다.

    val$이름, this$0이라는 필드 이름과 생성자 인자의 순서는 javac의 관례다. JLS는 지역 변수를 쓸 수 있다는 것과 그 변수가 지켜야 할 조건만 정하고, 어떤 이름의 필드로 구현할지는 정하지 않는다. 소스 코드에서 이 이름들을 직접 쓸 수도 없다.
    왼쪽 스택 프레임의 세 칸(this, prefix, taxPercent)에서 오른쪽 힙 인스턴스의 세 합성 필드(this$0, val$prefix, val$taxPercent)로 값이 복사되는 화살표를 보여 준다. 공유가 아니라 복사임이 드러나야 한다. 흰 배경의 평면 벡터 메모리 구조도. 좌우 2분할. 왼쪽 영역 제목 "스택: labeler 프레임", 오른쪽 영역 제목 "힙". 왼쪽에 세로로 쌓인 칸 세 개가 있는 상자: 위에서부터 "칸0 this", "칸1 prefix", "칸2 taxPercent = 10". 오른쪽 위에 작은 상자 "Shop"과 그 옆에 문자열 상자 "판매가 ". 오른쪽 아래에 큰 상자 "TaxLabeler 인스턴스"가 있고 그 안에 네 줄의 필드: "this$0", "val$prefix", "val$taxPercent = 10", "calls = 0". 왼쪽 칸 세 개에서 오른쪽 인스턴스의 대응하는 세 필드로 가는 주황색 점선 화살표 세 개를 그리고, 화살표 묶음 위에 라벨 "생성자 인자로 값 복사". "칸0 this"와 "this$0"에서 각각 "Shop" 상자로 가는 실선 화살표, "칸1 prefix"와 "val$prefix"에서 각각 "판매가 " 상자로 가는 실선 화살표. 왼쪽 프레임 상자 아래에 회색 글씨 "반환하면 사라진다", 오른쪽 인스턴스 상자 아래에 초록 글씨 "참조가 남아 있는 한 유지". 캡처는 변수 자체를 공유하는 것이 아니라 생성 시점의 값을 인스턴스의 합성 필드로 복사하는 것이다. 참조형은 참조값이 복사되어 같은 객체를 가리킨다.

    지역 변수 캡처 3: 캡처하는 변수는 사실상 final이어야 한다

    캡처가 값 복사라는 사실에서 제약 하나가 나온다. JLS 8.1.3은 내부 클래스가 쓰지만 그 안에서 선언하지는 않은 지역 변수, 매개변수, 예외 매개변수는 final이거나 사실상 final(effectively final)이어야 한다고 정한다. 사실상 final의 정의는 JLS 4.12.4에 있다. 선언할 때 초기화한 지역 변수라면 다음 세 조건을 모두 만족할 때다.

    • final로 선언되어 있지 않다.
    • 대입식의 왼쪽에 한 번도 나오지 않는다(선언문의 초기화는 대입식이 아니다).
    • ++, --의 피연산자로 한 번도 나오지 않는다.

    풀어 말하면 "final을 붙여도 컴파일 오류가 나지 않을 변수"다. 메서드 매개변수도 초기화된 지역 변수와 같은 기준으로 판단한다. 앞 예제의 taxPercent와 prefix는 선언 뒤 한 번도 값을 바꾸지 않았으므로 사실상 final이었다. Java SE 7 명세의 같은 절은 이런 변수를 반드시 final로 선언하라고 요구했고, Java SE 8 명세부터 "final이거나 사실상 final"로 완화되었다. 값이 바뀌지 않아야 한다는 조건 자체는 그대로다.

    규칙을 어기면 어떻게 되는지 보자. 지역 클래스를 선언한 뒤에 변수 값을 바꾸는 코드다.

    이 규칙이 없다면 생기는 일

    규칙이 없다고 가정하고 위 코드가 컴파일된다고 해 보자. new TaxLabeler()가 실행될 때 taxPercent의 값은 20이므로 필드에 20이 복사된다. 이번에는 대입과 생성의 순서를 바꿔 보자. new를 먼저 하고 그 뒤에 taxPercent = 20;을 실행하면 필드에는 10이 들어 있고 프레임의 칸에는 20이 들어 있다. 소스 코드에는 taxPercent라는 이름이 하나뿐인데 실행 중에는 값이 다른 두 개의 저장소가 있는 것이다. 메서드 본문은 20을 보고 지역 클래스의 메서드는 10을 본다.

    반대 방향도 마찬가지다. 지역 클래스 안에서 taxPercent++를 허용한다면 바뀌는 것은 인스턴스의 복사본이고, 바깥 메서드의 변수는 그대로다. 코드를 읽는 사람은 같은 변수를 고쳤다고 생각하지만 실제로는 다른 저장소를 고친 것이다. 어느 쪽이든 조용히 틀린 결과가 나오는 프로그램이 된다.

    언어 설계에는 두 가지 선택지가 있었다. 하나는 변수 자체를 공유하게 만드는 것이다. 그러려면 캡처되는 지역 변수를 프레임이 아니라 힙에 두어야 하고, 그 순간 지역 변수가 다른 스레드에서도 보일 수 있게 된다. 지역 변수는 프레임 안에 있어서 다른 스레드가 접근할 수 없다는 성질, 그래서 동기화 없이 써도 안전하다는 성질이 깨진다. 다른 하나는 값 복사를 유지하되 두 복사본이 어긋날 가능성을 없애는 것이다. 값이 한 번 정해지면 바뀌지 않는 변수만 캡처하게 하면 복사본이 몇 개든 항상 같은 값이므로 복사인지 공유인지를 구별할 수 없다. 자바는 뒤쪽을 택했다. JLS 15.27.2는 같은 제약을 람다에 대해 설명하면서 이유를 한 문장으로 적어 두었다. 동적으로 변하는 지역 변수를 캡처하면 동시성 문제를 일으키기 쉬우므로 그런 변수로의 접근을 금지한다는 것이다.

    일상에서 가져온 비유회의실 화이트보드와 사진

    회의가 끝나면 화이트보드는 지워진다. 회의 뒤에도 내용이 필요한 사람은 지워지기 전에 사진을 찍어 간다. 사진을 찍은 뒤 누가 보드의 숫자를 고치면 사진과 보드가 달라지고, 사진에 낙서를 해도 보드는 그대로다. "사진을 찍힌 뒤에는 보드를 고치지 않는다"는 약속이 있으면 사진을 보든 보드를 보든 같은 내용이므로 혼란이 없다. 지역 변수가 보드, 인스턴스의 합성 필드가 사진, 사실상 final 규칙이 그 약속이다. 비유가 맞지 않는 지점도 있다. 자바의 규칙은 사진을 찍은 뒤뿐 아니라 찍기 전의 수정도 금지한다. 변수가 선언된 뒤 한 번이라도 다시 대입되면 캡처 자체가 허용되지 않는다. 컴파일러가 실행 순서를 따지지 않고 변수 하나의 성질로 단순하게 판정하기 위해서다.

    반복문 변수와 초기화되지 않은 변수

    이 규칙이 가장 자주 걸리는 곳은 반복문이다. 기본 for 문의 i는 i++로 값이 바뀌므로 사실상 final이 아니다. 앞의 Snapshots 예제에서 getAsInt()가 snapshot 대신 i를 직접 돌려주게 고치면 같은 컴파일 오류가 난다. 해결 방법은 예제가 이미 보여 주었다. 반복문 본문 안에서 새 변수를 선언해 값을 옮겨 담는 것이다. 본문 블록 안에서 선언한 변수는 반복마다 새로 만들어지고 선언 뒤 바뀌지 않으므로 사실상 final이다. 향상된 for 문(for (String s : list))의 변수는 본문에서 다시 대입하지 않는 한 그대로 캡처할 수 있다.

    조건이 하나 더 있다. JLS 8.1.3은 내부 클래스가 쓰는 지역 변수가 그 클래스 본문보다 앞에서 확실히 대입(definitely assigned)되어 있어야 한다고 정한다. int n;으로 선언만 하고 지역 클래스가 n을 읽게 한 뒤 그 아래에서 n = 3;을 하면 variable n might not have been initialized 오류가 난다. 복사할 값이 아직 없는 변수는 캡처할 수 없다.

    규칙의 대상이 아닌 것: 필드

    이 규칙은 지역 변수와 매개변수에만 적용된다. 바깥 인스턴스의 필드, static 필드, 지역 클래스 자신의 필드는 얼마든지 바꿀 수 있다. 맨 처음 예제의 calls++가 문제없이 동작한 이유다. 차이는 저장 위치에 있다. 필드는 힙의 객체나 클래스에 딸린 공간에 있으므로 저장소가 하나뿐이다. 지역 클래스는 바깥 인스턴스의 필드를 복사해 두지 않고 this$0 참조를 따라가 매번 원본을 읽는다. 복사본이 없으니 어긋날 것도 없다. 물론 여러 스레드가 그 필드를 함께 쓴다면 동기화 문제가 생기지만, 그것은 필드를 쓰는 모든 코드가 원래 지고 있던 책임이다.

    배열로 감싸는 우회와 그 의미

    지역 클래스 안에서 바깥 메서드의 값을 꼭 바꿔야 할 때 흔히 쓰는 방법이 있다. 값을 길이 1짜리 배열이나 별도의 객체 안에 넣는 것이다.

    public class Holder {
    public static void main(String[] args) {
        int[] counter = {0};

        class Clicker implements Runnable {
            @Override
            public void run() {
                counter[0]++;
            }
        }

        Runnable clicker = new Clicker();
        clicker.run();
        clicker.run();
        counter[0] += 10;
        clicker.run();
        System.out.println(counter[0]);
    }
}

    이 코드는 규칙을 어기지 않는다. 변수 counter에 들어 있는 것은 배열의 참조값이고, 그 참조값은 선언 뒤 한 번도 바뀌지 않았다. counter[0]++는 변수 counter에 대입하는 것이 아니라 counter가 가리키는 배열의 원소를 바꾸는 것이다. 컴파일된 Holder$1Clicker에는 final int[] val$counter 필드가 있고 생성자 디스크립터는 ([I)V다. 복사된 것은 참조값이고, 배열 객체는 힙에 하나뿐이다.

    실행을 따라가면 run() 두 번으로 원소가 2가 되고, main이 10을 더해 12가 되고, 다시 run()으로 13이 된다. 양쪽이 같은 저장소를 보고 있으므로 어긋남이 없다. 우회의 정체는 바뀌는 상태를 프레임에서 힙으로 옮긴 것이다. 앞에서 본 설계 선택지 가운데 "변수를 힙에 두고 공유한다"를 프로그래머가 손으로 한 셈이다.

    그 대가도 그대로 따라온다. 힙으로 옮긴 상태는 그 객체에 도달할 수 있는 모든 스레드가 볼 수 있다. clicker를 다른 스레드에 넘겨 실행하면 counter[0]++는 동기화되지 않은 공유 변수 수정이 된다. 스레드가 하나뿐인 코드에서는 문제가 없지만, 이 우회를 쓸 때는 지역 변수가 주던 안전성을 스스로 포기했다는 것을 알고 있어야 한다. 바꿔야 할 상태가 그 객체만의 것이라면 처음 예제의 calls처럼 지역 클래스의 필드로 두는 편이 구조가 분명하다.

    값(int)을 캡처한 경우에는 복사본이 둘이고 서로 독립적이지만, 배열 참조를 캡처한 경우에는 참조만 둘이고 배열 객체는 하나라는 대비를 보여 준다. 흰 배경의 평면 벡터 비교 다이어그램. 좌우 2분할. 왼쪽 패널 제목 "int 값을 캡처". 위쪽에 스택 칸 "taxPercent = 10", 아래쪽에 힙 인스턴스 상자 안의 필드 "val$taxPercent = 10". 둘 사이에 주황 점선 화살표와 라벨 "값 복사". 두 상자 옆에 회색 글씨 "저장소 2개". 오른쪽 패널 제목 "배열 참조를 캡처". 위쪽에 스택 칸 "counter", 아래쪽에 힙 인스턴스 상자 안의 필드 "val$counter". 패널 오른쪽에 초록색 배열 상자 "int[1] { 13 }". 스택 칸 "counter"와 필드 "val$counter"에서 각각 배열 상자로 향하는 실선 화살표 두 개. 배열 상자 옆에 초록 글씨 "저장소 1개 (힙)". 두 패널 아래 가운데에 한 줄 라벨 "바뀌는 상태는 힙에 둘 때만 공유된다". 기본형 값은 복사본이 따로 생기지만, 참조를 캡처하면 참조값만 복사되고 객체는 하나다. 배열 우회는 바뀌는 상태를 프레임에서 힙으로 옮기는 방법이다.

    익명 클래스: 선언과 생성을 식 하나로

    처음 예제의 지역 클래스 TaxLabeler를 다시 보면, 이 이름이 쓰인 곳은 선언과 그 아래의 new TaxLabeler() 두 군데뿐이다. 한 번 선언해서 한 군데에서만 생성하는 클래스라면 이름은 두 문장을 이어 주는 역할밖에 하지 않는다. 익명 클래스는 이 두 문장을 식 하나로 합친다. labeler() 메서드를 익명 클래스로 다시 쓰면 다음과 같다.

    public Labeler labeler(String prefix) {
    int taxPercent = 10;

    return new Labeler() {
        private int calls;

        @Override
        public String label(int price) {
            calls++;
            int total = price + price * taxPercent / 100;
            return prefix + total + currency + " (" + calls + "번째)";
        }
    };
}

    이름이 없다는 것이 실행 중에 어떻게 드러나는지 리플렉션으로 확인해 보자. main()을 다음과 같이 바꿔 실행한다.

    • 상위 타입은 하나만 지정한다. new 뒤에 클래스 이름 하나 또는 인터페이스 이름 하나를 쓴다. 클래스를 상속하면서 인터페이스를 구현하거나 인터페이스 둘을 구현하는 익명 클래스는 문법으로 쓸 수 없다.
    • 생성자를 선언할 수 없다. 생성자는 클래스 이름으로 선언하는데 이름이 없다. 대신 컴파일러가 익명 생성자를 암묵적으로 만든다(JLS 15.9.5.1). new Base(인자) { … }처럼 괄호 안에 쓴 인자는 상위 클래스의 생성자로 전달된다. 초기화 코드가 필요하면 필드 초기화식이나 인스턴스 초기화 블록에 쓴다.
    • 항상 내부 클래스다. 인스턴스 메서드 안에서 만들면 바깥 인스턴스에 접근할 수 있고, static 문맥에서 만들면 바깥 인스턴스가 없다. abstract일 수 없고, 인스턴스 생성 식으로 선언한 익명 클래스는 final도 아니다. 다만 이름이 없으니 소스 코드에서 이 클래스를 상속할 방법이 없다.
    • 생성하는 자리가 한 곳이다. 그 식이 여러 번 실행되면 인스턴스는 여러 개 만들어지지만, 다른 위치에서 같은 클래스의 인스턴스를 만들 수는 없다. 두 곳 이상에서 필요하면 이름 있는 클래스로 선언해야 한다.
    • 새로 추가한 멤버는 밖에서 쓰기 어렵다. 변수의 타입이 상위 타입이므로 익명 클래스에서 새로 선언한 메서드는 그 변수로 호출할 수 없다. Object o = new Object() { void hello() {} }; 뒤에 o.hello()를 쓰면 cannot find symbol 오류가 난다. 익명 클래스 본문에는 상위 타입의 메서드 구현과, 그 구현이 내부적으로 쓰는 필드·보조 메서드를 둔다.

    익명 클래스 활용 1: 변하는 부분이 값이 아니라 코드일 때

    익명 클래스가 실제로 쓰이는 자리를 중복 제거 과정으로 따라가 보자. 건물 점검 절차를 출력하는 두 메서드가 있다.

    public class Checklist0 {

    static void lightsOff() {
        System.out.println("[시작] 소등");
        System.out.println("조명을 끈다");
        System.out.println("[완료] 소등");
    }

    static void lockDoors() {
        System.out.println("[시작] 잠금");
        for (int door = 1; door <= 2; door++) {
            System.out.println(door + "번 문을 잠근다");
        }
        System.out.println("[완료] 잠금");
    }

    public static void main(String[] args) {
        lightsOff();
        lockDoors();
    }
}
    [시작] 소등
조명을 끈다
[완료] 소등
[시작] 잠금
1번 문을 잠근다
2번 문을 잠근다
[완료] 잠금

    두 메서드는 구조가 같다. 시작을 알리고, 일을 하고, 완료를 알린다. 점검 항목이 열 개로 늘면 시작과 완료를 출력하는 코드도 열 번 반복되고, 출력 형식을 바꾸려면 열 군데를 고쳐야 한다. 중복을 없애려면 변하지 않는 부분은 한 곳에 두고 변하는 부분만 바깥에서 받아야 한다.

    변하는 부분은 두 가지다. 하나는 제목("소등", "잠금")이다. 이것은 값이므로 String 매개변수로 받으면 된다. 다른 하나는 가운데에서 하는 일이다. 한쪽은 출력 한 줄이고 다른 쪽은 반복문이다. 이것은 값이 아니라 코드다. int나 String 매개변수로는 "반복문을 돌려라"를 전달할 수 없다. 메서드에 코드 조각을 넘길 방법이 필요하다.

    자바에서 메서드가 인자로 받을 수 있는 것은 기본형 값과 참조값뿐이다. 코드 자체를 넘기는 문법은 없다. 그러나 객체는 넘길 수 있고, 객체는 메서드를 갖고 있다. 실행할 코드를 메서드에 담은 객체를 만들어 그 참조를 넘기면, 받은 쪽은 그 객체의 메서드를 호출함으로써 넘겨받은 코드를 실행할 수 있다. 다형성이 이 일을 가능하게 한다.

    익명 클래스 활용 2: 동작을 객체에 담아 넘긴다

    먼저 "가운데에서 하는 일"의 형식을 인터페이스로 정한다. 받는 쪽은 이 인터페이스만 알면 된다.

    public interface Step {
    void run();
}

    이제 변하지 않는 틀을 메서드 하나로 모으고, 변하는 코드는 Step을 구현한 클래스에 담는다.

    public class Checklist1 {

    static class LightsOff implements Step {
        @Override
        public void run() {
            System.out.println("조명을 끈다");
        }
    }

    static class LockDoors implements Step {
        @Override
        public void run() {
            for (int door = 1; door <= 2; door++) {
                System.out.println(door + "번 문을 잠근다");
            }
        }
    }

    static void perform(String title, Step step) {
        System.out.println("[시작] " + title);
        step.run();
        System.out.println("[완료] " + title);
    }

    public static void main(String[] args) {
        perform("소등", new LightsOff());
        perform("잠금", new LockDoors());
    }
}

    실행 결과는 앞과 같다. perform()은 step이 어떤 클래스의 객체인지 모른다. step.run()은 인터페이스 메서드 호출이고, 실제로 어느 메서드가 실행될지는 실행 시점에 그 참조가 가리키는 객체의 클래스에 따라 정해진다. 자바 기본편에서 본 동적 디스패치 그대로다. new LightsOff()를 넘기면 출력 한 줄이, new LockDoors()를 넘기면 반복문이 틀 안에서 실행된다. 시작과 완료를 출력하는 코드는 이제 한 곳에만 있다.

    중복은 사라졌지만 새 불편이 생겼다. 점검 항목 하나마다 클래스 하나를 선언해야 하고, 그 클래스들은 main()에서 한 번씩만 쓰인다. 쓰이는 곳과 선언된 곳이 떨어져 있어서 perform("소등", new LightsOff())를 읽는 사람은 무슨 일을 하는지 보려면 위로 올라가 클래스를 찾아야 한다. 쓰이는 메서드 안으로 선언을 옮기면 거리가 줄어든다. 지역 클래스로 바꾸면서, 지역 변수를 쓸 수 있다는 점도 활용해 보자.

    public class Checklist2 {

    static void perform(String title, Step step) {
        System.out.println("[시작] " + title);
        step.run();
        System.out.println("[완료] " + title);
    }

    public static void main(String[] args) {
        int floor = 3;

        class LightsOff implements Step {
            @Override
            public void run() {
                System.out.println(floor + "층 조명을 끈다");
            }
        }

        class LockDoors implements Step {
            @Override
            public void run() {
                for (int door = 1; door <= 2; door++) {
                    System.out.println(floor + "층 " + door + "번 문을 잠근다");
                }
            }
        }

        perform("소등", new LightsOff());
        perform("잠금", new LockDoors());
    }
}
    [시작] 소등
3층 조명을 끈다
[완료] 소등
[시작] 잠금
3층 1번 문을 잠근다
3층 2번 문을 잠근다
[완료] 잠금

    정적 중첩 클래스였을 때는 floor를 쓰려면 생성자로 받아 필드에 넣는 코드를 직접 써야 했다. 지역 클래스에서는 그 일을 컴파일러가 대신한다. perform()의 매개변수는 여전히 (String, Step)뿐이고 floor를 받는 자리가 없는데도 틀 안에서 실행되는 코드가 floor를 안다. 값이 객체 안에 실려서 함께 넘어갔기 때문이다. 동작을 객체로 넘기는 방식에서 캡처가 유용한 이유가 여기에 있다. 넘겨받는 쪽의 메서드 시그니처를 바꾸지 않고도, 넘기는 쪽의 문맥에 있는 값을 코드와 함께 전달할 수 있다.

    익명 클래스 활용 3: 이름을 지우고 인자 자리에 직접 쓴다

    LightsOff와 LockDoors는 선언한 바로 아래에서 한 번씩만 생성된다. 앞 절에서 본 익명 클래스의 조건에 그대로 들어맞는다. 먼저 변수에 담는 형태로 바꾸면 다음과 같다.

    Step lightsOff = new Step() {
    @Override
    public void run() {
        System.out.println(floor + "층 조명을 끈다");
    }
};

perform("소등", lightsOff);

    변수 lightsOff도 한 번만 쓰인다. 익명 클래스 생성은 식이므로 인자 자리에 직접 쓸 수 있다. 마지막 항목 하나는 뒤에서 설명할 람다로 써 두었다.

    public class Checklist {

    static void perform(String title, Step step) {
        System.out.println("[시작] " + title);
        step.run();
        System.out.println("[완료] " + title);
    }

    public static void main(String[] args) {
        int floor = 3;

        perform("소등", new Step() {
            @Override
            public void run() {
                System.out.println(floor + "층 조명을 끈다");
            }
        });

        perform("잠금", new Step() {
            @Override
            public void run() {
                for (int door = 1; door <= 2; door++) {
                    System.out.println(floor + "층 " + door + "번 문을 잠근다");
                }
            }
        });

        perform("보고", () -> System.out.println(floor + "층 점검 끝"));
    }
}

3층 조명을 끈다
[완료] 소등
[시작] 잠금
3층 1번 문을 잠근다
3층 2번 문을 잠근다
[완료] 잠금
[시작] 보고

[완료] 보고

    이제 호출하는 줄에 제목과 할 일이 함께 적혀 있다. perform("소등", …)을 읽으면 무엇을 하는지가 그 자리에서 보인다. 처음 코드와 비교하면 변하지 않는 틀은 perform() 한 곳에, 변하는 코드는 호출하는 자리에 놓였다. 컴파일하면 Checklist.class, Checklist$1.class, Checklist$2.class, Step.class 네 파일이 나온다. 익명 클래스 둘은 소스에 나온 순서대로 번호가 붙었다. javap -p -s 'Checklist$1'의 결과에는 final int val$floor 필드와 (I)V 생성자가 있다. main()이 static 메서드이므로 바깥 인스턴스는 넘어가지 않고 floor의 값만 복사된다.

    이 장의 핵심

    메서드에 코드를 넘기고 싶을 때 자바는 그 코드를 메서드로 가진 객체를 넘긴다. 지역 클래스와 익명 클래스는 그 객체의 클래스를 쓰는 자리 바로 옆에서 선언하게 해 주고, 캡처는 선언한 자리의 지역 변수 값을 객체 안에 복사해 함께 실어 보낸다. 복사이기 때문에 캡처되는 변수는 값이 바뀌지 않아야 한다.

    익명 클래스와 람다: 겉모습은 닮았지만 컴파일 결과가 다르다

    마지막 항목에 쓴 () -> System.out.println(floor + "층 점검 끝")이 람다 식(lambda expression)이다. 추상 메서드가 하나뿐인 인터페이스, 곧 함수형 인터페이스(functional interface)가 필요한 자리에는 익명 클래스 대신 람다를 쓸 수 있다. Step은 추상 메서드가 run() 하나이므로 조건을 만족한다. 람다는 로드맵의 뒤쪽 권에서 본격적으로 다루므로 여기서는 익명 클래스와 무엇이 같고 다른지만 확인한다.

    같은 점은 캡처 규칙이다. 람다 본문도 floor를 쓰고 있고, JLS 15.27.2는 람다가 쓰는 바깥 지역 변수에 내부 클래스와 같은 조건(final이거나 사실상 final)을 요구한다. 다른 점은 JDK 21의 javac가 만드는 컴파일 결과에 있다. 앞에서 컴파일 결과로 나온 클래스 파일은 넷이었고, 람다에 해당하는 Checklist$3.class는 없다. javap -p -c Checklist로 보면 람다가 어디로 갔는지 나온다.

    익명 클래스 두 개는 new 명령어로 Checklist$1, Checklist$2의 인스턴스를 만든다. 람다의 자리에는 new가 없고 invokedynamic이 있다. 람다의 본문은 별도 클래스가 아니라 Checklist 클래스 자신의 private static 메서드 lambda$main$0(int)로 컴파일되었다. 캡처한 floor는 필드가 아니라 이 메서드의 int 매개변수로 전달된다. invokedynamic 바로 앞의 iload_1이 floor의 값을 스택에 올리는 명령어이고, 디스크립터 (I)LStep;은 "int 하나를 받아 Step 객체를 돌려준다"는 뜻이다. javap -v로 보면 이 invokedynamic의 부트스트랩 메서드는 java.lang.invoke.LambdaMetafactory.metafactory다. Step을 구현하는 객체를 어떻게 만들지를 컴파일 시점이 아니라 실행 시점에 이 메서드가 정한다.

    비교 항목익명 클래스람다
    쓸 수 있는 상위 타입클래스, 추상 클래스, 인터페이스 모두함수형 인터페이스만
    컴파일 시 클래스 파일Outer$N.class가 생긴다생기지 않는다. 본문은 바깥 클래스의 private 메서드가 된다
    객체를 만드는 명령어new + 생성자 호출invokedynamic
    캡처한 값이 놓이는 곳합성 필드 val$이름람다 본문 메서드의 매개변수로 전달

    this익명 클래스의 인스턴스람다를 둘러싼 메서드의 this
    식을 다시 평가할 때항상 새 인스턴스새 인스턴스일 수도, 기존 인스턴스일 수도 있다

    마지막 줄은 명세의 차이다. 익명 클래스 식은 인스턴스 생성 식이므로 평가할 때마다 새 객체가 만들어진다. 람다에 대해서 JLS 15.27.4는 평가할 때마다 새 객체를 할당할 필요가 없다고 적어 구현에 재량을 준다. OpenJDK 21에서 실험해 보면 지역 변수도 this도 캡처하지 않는 람다 식은 두 번 평가해도 같은 객체가 나왔고(== 비교가 true), 지역 변수나 this를 캡처하는 람다 식은 평가마다 다른 객체가 나왔다. 그 객체의 클래스는 isHidden()이 true인 히든 클래스였다. 이것은 구현의 동작이므로 람다 객체의 동일성에 의존하는 코드를 쓰면 안 된다.

    표에서 보듯 람다가 익명 클래스를 전부 대신하지는 못한다. 추상 클래스를 상속해야 할 때, 구현할 메서드가 둘 이상일 때, 처음 예제의 calls처럼 객체가 자신만의 상태를 필드로 가져야 할 때는 익명 클래스(또는 이름 있는 클래스)가 필요하다.

    익명 클래스는 별도 클래스 파일과 new 명령어로, 람다는 바깥 클래스의 private 메서드와 invokedynamic으로 컴파일된다는 대비를 보여 준다. 흰 배경의 평면 벡터 비교 다이어그램. 좌우 2분할. 왼쪽 패널 제목 "익명 클래스". 위에 소스 조각을 나타내는 코드 상자 "new Step() { ... }". 아래로 화살표 "javac". 그 아래에 파일 아이콘 두 개: "Checklist.class"와 "Checklist$1.class". "Checklist.class" 안에 작은 글씨 "new Checklist$1", "Checklist$1.class" 안에 작은 글씨 "val$floor 필드". 오른쪽 패널 제목 "람다". 위에 코드 상자 "() -> ...". 아래로 화살표 "javac". 그 아래에 파일 아이콘 하나 "Checklist.class"만 있고 안에 두 줄 "invokedynamic", "lambda$main$0(int)". 그 파일 아이콘에서 오른쪽 아래로 점선 화살표가 나가 구름 모양 상자 "실행 중에 만들어지는 객체"로 이어지고 화살표 라벨 "LambdaMetafactory". 두 패널 사이 세로 구분선. 익명 클래스는 컴파일할 때 클래스 파일이 따로 생기고 new로 생성된다. 람다의 본문은 바깥 클래스의 메서드가 되고, 객체는 실행 시점에 invokedynamic을 통해 얻는다.

    this와 이름 가리기: 새 클래스인가, 같은 스코프인가

    익명 클래스와 람다의 차이 가운데 실제 코드에서 가장 자주 부딪히는 것은 이름이 무엇을 가리키는가다. 익명 클래스의 본문은 클래스 본문이다. 새로운 클래스가 하나 생기는 것이므로 그 안의 this는 익명 클래스의 인스턴스이고, 그 안에서 선언한 필드는 바깥의 같은 이름을 가린다(shadowing). 람다의 본문은 클래스 본문이 아니다. JLS 15.27.2는 람다 본문에 나오는 이름과 this, super의 의미가 람다를 둘러싼 문맥에서와 같다고 정한다.

    public class Scope {
    private String name = "바깥 필드";

    void show() {
        String name = "지역 변수";

        Runnable anonymous = new Runnable() {
            private String name = "익명 클래스 필드";

            @Override
            public void run() {
                System.out.println(name);
                System.out.println(this.name);
                System.out.println(Scope.this.name);
            }
        };
        anonymous.run();

        Runnable lambda = () -> {
            System.out.println(name);
            System.out.println(this.name);
        };
        lambda.run();
    }

    public static void main(String[] args) {
        new Scope().show();
    }
}

익명 클래스 필드
바깥 필드
지역 변수
바깥 필드

    익명 클래스의 run() 안에서 name은 가장 가까운 선언인 자신의 필드다. 지역 변수 name과 바깥 필드 name은 둘 다 가려졌다. this.name도 같은 필드이고, 바깥 인스턴스의 필드를 쓰려면 Scope.this.name이라고 한정해야 한다. 이 익명 클래스는 지역 변수 name을 쓰지 않으므로 캡처하지도 않는다. 실제로 Scope$1에는 val$name 필드가 없고 this$0만 있다.

    람다 안에서는 새 스코프가 생기지 않았으므로 name은 show()의 지역 변수이고, this는 show()를 실행 중인 Scope 인스턴스다. 그래서 this.name이 "바깥 필드"를 출력한다. 같은 이유로 람다 본문 안에서는 바깥 지역 변수와 같은 이름의 지역 변수를 새로 선언할 수 없다. 메서드에 int x가 있는데 람다 안에서 int x = 2;를 쓰면 variable x is already defined in method m() 오류가 난다. 익명 클래스의 메서드 안에서는 같은 선언이 허용된다. JLS 6.4가 지역 변수 이름의 재선언을 금지하면서 그 범위 안에 있는 클래스 선언 내부는 예외로 두기 때문이다.

    이 차이는 익명 클래스를 람다로 기계적으로 바꿀 때 문제가 된다. 익명 클래스 안에서 this를 자기 자신이라는 뜻으로 쓰고 있었다면(예를 들어 자신을 어딘가에 등록하거나 등록을 해제하는 코드) 람다로 바꾸는 순간 this가 바깥 객체로 바뀐다. 컴파일은 되는데 의미가 달라질 수 있다.

    한 층 아래: 초기화 순서와 클래스 파일에 남는 기록

    캡처한 값은 상위 생성자가 실행되기 전에 채워진다

    앞에서 본 생성자 바이트코드에서 합성 필드에 값을 넣는 putfield들이 Object의 생성자 호출보다 앞에 있었다. 이 순서가 눈에 보이는 차이를 만드는 경우가 있다. 상위 클래스의 생성자가 하위 클래스에서 재정의한 메서드를 호출하는 경우다.

    public class InitOrder {

    static abstract class Part {
        Part() {
            System.out.println("Part 생성자: " + describe());
        }

        abstract String describe();
    }

    public static void main(String[] args) {
        int size = 42;

        Part part = new Part() {
            private int weight = 5;

            @Override
            String describe() {
                return "size=" + size + ", weight=" + weight;
            }
        };

        System.out.println("생성 후: " + part.describe());
    }
}

    생성자는 세 단계로 실행된다. 캡처한 값을 val$size에 넣고(0~2), 상위 클래스 Part의 생성자를 호출하고(6), 그 뒤에 소스에 쓴 필드 초기화 weight = 5를 실행한다(9~11). Part의 생성자가 describe()를 호출하는 시점은 둘째 단계 도중이다. 이때 val$size에는 이미 42가 들어 있지만 weight는 아직 기본값 0이다. 그래서 첫 줄에 size=42, weight=0이 출력된다.

    자신이 선언한 필드는 상위 생성자가 끝난 뒤에 초기화된다는 것은 자바 기본편에서 본 객체 초기화 순서 그대로다. 캡처 필드만 그보다 앞서 채워지는 것은 컴파일러가 그렇게 코드를 만들기 때문이다. 캡처한 지역 변수는 소스 코드에서 보기에 필드가 아니라 이미 값이 정해진 변수이므로, 객체의 어느 메서드가 언제 실행되든 그 값이 보여야 자연스럽다. Java 21의 소스 코드로는 상위 생성자 호출보다 앞에 문장을 둘 수 없으므로 프로그래머가 같은 순서를 직접 쓸 수는 없다. 그리고 이 예제는 생성자에서 재정의 가능한 메서드를 호출하면 하위 클래스의 필드가 초기화되기 전 상태를 보게 된다는 오래된 함정을 다시 보여 주기도 한다.

    클래스 파일은 어디서 선언되었는지를 기록한다

    지역 클래스와 익명 클래스는 컴파일되면 독립된 클래스 파일이 되지만, 원래 어디에 있던 클래스인지에 대한 기록은 남는다. javap -v 'Shop$1'의 끝부분에는 다음 속성들이 있다.

    EnclosingMethod: #25.#45                // Shop.labeler
NestHost: class Shop
InnerClasses:
  #2;                                     // class Shop$1

    JVMS 4.7.7은 클래스가 지역 클래스이거나 익명 클래스일 때, 그리고 그때에만 EnclosingMethod 속성을 가져야 한다고 정한다. 이 속성은 그 클래스를 감싸는 가장 안쪽 클래스와, 클래스가 메서드나 생성자 바로 안에 있었다면 그 메서드를 가리킨다. 앞에서 호출한 getEnclosingMethod()가 Shop.labeler를 돌려준 것은 이 기록 덕분이다. 익명 클래스를 필드 초기화식이나 초기화 블록 안에 쓴 경우에는 감싸는 메서드가 없으므로 메서드 항목이 0이 된다. InnerClasses 속성에도 흔적이 있다. JVMS 4.7.6은 익명 클래스의 경우 원래의 단순 이름을 가리키는 항목(inner_name_index)이 0이어야 한다고 정한다. 이름이 없었다는 사실이 클래스 파일에 그대로 적히는 것이다. NestHost는 이 클래스가 Shop과 같은 네스트에 속한다는 표시로, 중첩 클래스가 바깥 클래스의 private 멤버에 접근할 수 있게 해 주는 장치다.

    이 기록은 실행 흐름에는 영향을 주지 않지만 디버깅할 때 쓰인다. 예외의 스택 트레이스에는 소스의 이름이 아니라 컴파일된 이름이 찍힌다. 익명 클래스의 메서드에서 예외가 나면 Trace$1.run(Trace.java:5), 지역 클래스라면 Trace$1Named.run(Trace.java:7), 람다라면 Trace.lambda$main$0(Trace.java:6)과 같은 형태다. $숫자는 익명 클래스, $숫자이름은 지역 클래스, lambda$메서드이름$숫자는 그 메서드 안의 람다라는 것을 알면 스택 트레이스에서 해당 코드를 바로 찾을 수 있다.

    흔한 오해와 함정

    "지역 클래스의 인스턴스는 메서드가 끝나면 사라진다"

    "지역"이라는 말 때문에 생기는 오해다. 지역인 것은 클래스 이름의 유효 범위다. 인스턴스는 다른 모든 객체처럼 힙에 있고, 수명은 도달 가능한 참조가 있는지로만 정해진다. 메서드가 인스턴스를 반환하거나 컬렉션에 넣거나 다른 객체의 필드에 저장했다면 그 인스턴스는 메서드보다 오래 산다. 반대로 메서드 안에서만 쓰고 참조를 밖으로 내보내지 않았다면 메서드가 끝난 뒤 가비지 컬렉션 대상이 된다.

    "캡처한 변수는 바깥 변수와 연결되어 있다"

    연결되어 있지 않다. 생성 시점에 값이 복사되고 그 뒤로는 서로 무관한 저장소다. 연결된 것처럼 보이는 이유는 사실상 final 규칙 때문에 양쪽 값이 달라질 기회가 없어서다. 참조형 변수를 캡처했을 때 객체의 변경이 양쪽에서 보이는 것은 변수가 연결되어서가 아니라 두 참조값이 같은 객체를 가리켜서다.

    "final을 붙여야 캡처할 수 있다"

    Java SE 7까지의 규칙이다. 지금은 선언 뒤 값을 바꾸지 않기만 하면 된다. 다만 final을 붙이는 것이 의미 없지는 않다. 누군가 나중에 그 변수에 대입하는 코드를 추가하면, final이 없을 때는 멀리 떨어진 지역 클래스 안의 줄에서 오류가 나고, final이 있을 때는 대입한 바로 그 줄에서 오류가 난다. 또 기본형이나 String의 final 변수를 상수식으로 초기화하면 상수 변수가 되어 캡처 필드 없이 값이 직접 들어간다.

    "익명 클래스 식이 실행될 때마다 클래스가 만들어진다"

    클래스는 컴파일할 때 하나 만들어져 .class 파일로 존재한다. 식이 반복문 안에서 천 번 실행되면 인스턴스가 천 개 만들어질 뿐이다. 앞의 리플렉션 예제에서 a.getClass() == b.getClass()가 true였던 것이 그 증거다.

    "익명 클래스는 바깥 객체와 상관없는 독립된 객체다"

    인스턴스 메서드 안에서 만든 익명 클래스나 지역 클래스가 바깥 인스턴스의 필드나 메서드를 쓰면 this$0 필드에 바깥 인스턴스의 참조가 들어간다. 이 익명 객체를 오래 사는 곳(예를 들어 애플리케이션이 끝날 때까지 유지되는 리스너 목록이나 static 컬렉션)에 등록하면, 그 객체가 도달 가능한 동안 바깥 인스턴스도 this$0을 통해 도달 가능하므로 가비지 컬렉션으로 회수되지 않는다. 바깥 객체가 큰 데이터를 들고 있다면 등록 해제를 잊은 콜백 하나가 그 전체를 붙잡는다. 앞에서 본 것처럼 JDK 21의 javac(대상 버전 18 이상)는 바깥 인스턴스를 쓰지 않는 경우 이 필드를 만들지 않지만, 바깥의 필드나 메서드를 하나라도 쓰면 참조가 유지된다. 바깥 인스턴스가 필요 없다면 static 메서드에서 만들거나 정적 중첩 클래스로 선언하는 것이 의도를 분명히 드러낸다.

    "람다는 익명 클래스를 짧게 쓴 문법이다"

    함수형 인터페이스를 구현하는 자리에서는 서로 바꿔 쓸 수 있는 경우가 많지만 같은 것은 아니다. 컴파일 결과가 다르고(new와 클래스 파일 대 invokedynamic과 메서드), this와 이름의 의미가 다르고, 객체가 매번 새로 만들어지는지에 대한 보장이 다르다. 상태를 가진 익명 클래스나 this를 자기 자신으로 쓰는 익명 클래스는 람다로 바꾸면 동작이 달라진다.

    다른 주제와의 연결

    동작을 객체로 넘기는 방식은 자바 표준 라이브러리 전반에 쓰인다. 정렬 기준을 넘기는 Comparator, 스레드가 실행할 작업을 넘기는 Runnable, 컬렉션을 순회하는 Iterator 구현이 모두 같은 구조다. 틀은 라이브러리가 갖고 있고, 변하는 코드는 인터페이스를 구현한 객체로 받는다. 이 로드맵의 컬렉션과 스레드를 다루는 권에서 익명 클래스나 람다로 이 인터페이스들을 구현하는 코드를 계속 보게 된다.

    스레드와 만나면 이 회차의 캡처 규칙이 실질적인 의미를 갖는다. Runnable 객체를 다른 스레드에 넘기면 그 객체의 run()은 다른 스레드의 스택에서 실행된다. 캡처한 값은 객체 안에 복사되어 있으므로 원래 스레드의 프레임이 사라졌든 아니든 안전하게 읽을 수 있고, 값이 바뀌지 않으니 동기화도 필요 없다. 반면 배열이나 가변 객체의 참조를 캡처해 상태를 공유하면 두 스레드가 같은 힙 객체를 읽고 쓰게 되어, 동시성을 다루는 권에서 배울 가시성과 경쟁 조건 문제가 그대로 나타난다.

    스프링에서도 같은 구조를 만난다. JdbcTemplate은 커넥션을 얻고, SQL을 실행하고, 자원을 정리하는 틀을 갖고 있고, 결과의 한 행을 객체로 바꾸는 코드만 RowMapper로 받는다. TransactionTemplate은 트랜잭션을 시작하고 커밋하거나 롤백하는 틀 안에서 실행할 코드를 콜백으로 받는다. 이 회차의 perform()과 Step의 관계와 같다. 넘기는 콜백이 호출하는 메서드의 지역 변수를 쓸 때 사실상 final 오류를 만나게 되는 것도 같다.

    이 권의 다음 두 회차는 예외 처리를 다룬다. 예외가 발생했을 때 출력되는 스택 트레이스에서 Shop$1.label이나 lambda$main$0 같은 이름을 만나면, 이 회차에서 본 컴파일 결과의 이름 규칙으로 소스의 어느 코드인지 되짚을 수 있다.
    지역 클래스(local class)
    메서드 본문 같은 블록 안에서 선언하는 클래스다. 이름의 유효 범위만 블록 안이고, 컴파일하면 Outer$1Name.class라는 독립된 클래스 파일이 되며 인스턴스는 힙에서 다른 객체와 같은 규칙으로 산다.
    프레임과 인스턴스의 수명 차이
    지역 변수는 스레드의 스택 프레임에 있고 메서드가 끝나면 프레임과 함께 파괴된다. 지역 클래스의 인스턴스는 힙에 있고 도달 가능한 참조가 있는 동안 유지되므로 메서드보다 오래 살 수 있다.
    지역 변수 캡처(capture)
    지역 클래스나 익명 클래스가 바깥 메서드의 지역 변수를 쓰면 컴파일러가 합성 필드 val$이름과 숨은 생성자 인자를 만들고, new가 실행되는 순간의 값을 인스턴스 안으로 복사한다. 참조형은 참조값이 복사된다.
    사실상 final(effectively final)
    선언 뒤 한 번도 다시 대입되지 않고 증감 연산의 대상도 되지 않는 지역 변수다. 캡처는 복사이므로 값이 바뀌면 프레임의 원본과 인스턴스의 복사본이 어긋난다. 자바는 바뀌지 않는 변수만 캡처하게 해서 이 불일치를 컴파일 시점에 막는다.
    규칙 밖에 있는 것
    필드는 힙이나 클래스에 저장소가 하나뿐이고 this$0을 따라가 원본을 읽으므로 자유롭게 바꿀 수 있다. 배열이나 가변 객체의 참조를 캡처해 내용을 바꾸는 것도 허용되지만, 그 상태는 힙에 있으므로 다른 스레드와 공유될 수 있다.
    익명 클래스(anonymous class)
    클래스 선언과 인스턴스 생성을 식 하나로 합친 것이다. 컴파일 결과는 지역 클래스와 같은 구조의 Outer$N.class이며 캡처 규칙도 같다. 이름이 없어서 상위 타입을 하나만 지정할 수 있고 생성자를 선언할 수 없다.
    동작을 객체로 넘기기
    변하는 부분이 값이 아니라 코드일 때, 그 코드를 인터페이스의 메서드로 구현한 객체를 인자로 넘긴다. 받는 쪽은 틀만 갖고 인터페이스 메서드를 호출하며, 실제로 실행될 코드는 동적 디스패치로 정해진다.
    익명 클래스와 람다의 차이
    익명 클래스는 클래스 파일이 생기고 new로 생성되며 본문이 새 클래스 스코프다. 람다는 본문이 바깥 클래스의 private 메서드로 컴파일되고 invokedynamic으로 객체를 얻으며, this와 이름의 의미가 둘러싼 문맥과 같다.
    클래스 파일에 남는 기록
    지역·익명 클래스의 클래스 파일에는 EnclosingMethod 속성이 있어 어느 클래스의 어느 메서드 안에서 선언되었는지가 남는다. 스택 트레이스에는 Outer$1, Outer$1Name, lambda$method$0 같은 컴파일된 이름이 찍힌다.

    실무에서 다시 판단하면, 첫 번째 결정은 한 번 쓰고 말 구현을 어떤 형태로 쓸지다. 구현할 메서드가 하나뿐인 인터페이스이고 구현이 상태를 갖지 않으며 this를 자기 자신으로 쓸 일이 없다면 람다가 가장 짧다. 추상 클래스를 상속해야 하거나, 메서드를 둘 이상 구현해야 하거나, 호출 횟수 같은 자신만의 상태를 필드로 가져야 한다면 익명 클래스가 맞다. 같은 구현을 두 곳 이상에서 생성하거나, 본문이 길어져 호출하는 줄의 흐름을 가리거나, 단위 테스트에서 그 구현만 따로 만들어 검증하고 싶다면 이름 있는 클래스로 꺼내는 편이 낫다. 익명 클래스는 선언한 자리 밖에서는 만들 수 없기 때문이다.

    두 번째는 메모리 문제를 볼 때다. 애플리케이션이 끝날 때까지 유지되는 컬렉션이나 다른 객체의 리스너 목록에 익명 객체를 등록하는 코드를 보면, 그 익명 클래스 본문이 바깥 인스턴스의 필드나 메서드를 쓰는지 확인한다. 쓴다면 익명 객체의 this$0이 바깥 인스턴스를 붙잡고 있고, 등록을 해제하지 않는 한 바깥 인스턴스와 그것이 참조하는 모든 객체가 회수되지 않는다. 코드에는 바깥 객체를 저장한다는 문장이 어디에도 없으므로 소스만 읽어서는 놓치기 쉽다. 컴파일러가 숨은 필드를 만든다는 사실을 알고 있어야 "작은 콜백 하나가 큰 객체를 붙잡는다"는 가설을 세울 수 있다. 판단이 달라지는 조건은 수명이다. 메서드 안에서 만들어 그 메서드 안에서만 쓰는 익명 객체라면 바깥 참조를 갖고 있어도 문제가 되지 않는다.

    세 번째는 사실상 final 오류를 만났을 때의 대응이다. 길이 1짜리 배열로 감싸면 컴파일은 되지만, 그 전에 왜 콜백 안에서 바깥 메서드의 변수를 바꾸려 했는지를 먼저 본다. 결과를 모으려는 것이라면 콜백이 값을 반환하게 인터페이스를 바꾸고 틀 쪽에서 모으는 구조가 더 단순한 경우가 많다. 객체 하나에 속한 상태라면 그 객체의 필드로 둔다. 그래도 공유 상태가 필요하다면 그 콜백이 어느 스레드에서 실행되는지를 확인해야 한다. 같은 스레드에서 곧바로 실행되고 끝나는 콜백이면 배열 우회는 안전하다. 스레드 풀이나 다른 스레드로 넘어가는 콜백이면 그 배열은 동기화가 필요한 공유 변수이고, 컴파일러가 막아 주던 문제를 직접 책임져야 한다.

    마지막으로 컴파일된 이름을 어디까지 믿을지다. JDK 21의 javac는 익명 클래스에 소스에 나온 순서대로 번호를 붙인다. 클래스 앞쪽에 익명 클래스를 하나 추가하고 다시 컴파일하면 뒤쪽에 있던 Outer$1이 Outer$2가 된다. 스택 트레이스를 읽을 때는 이름보다 함께 찍힌 줄 번호가 정확하고, 그 스택 트레이스가 어느 빌드에서 나온 것인지를 맞춰 봐야 한다. 로그 설정이나 다른 코드에서 Outer$1이라는 이름을 문자열로 적어 두는 것은 소스를 조금만 고쳐도 다른 클래스를 가리키게 되므로 피한다.

    public class Session {
    interface Task {
        void run();
    }

    static void inSession(String user, Task task) {
        System.out.println(user + " 로그인");
        task.run();
        System.out.println(user + " 로그아웃");
    }

    public static void main(String[] args) {
        int amount = 3000;

        inSession("kim", new Task() {
            @Override
            public void run() {
                System.out.println(amount + "원 결제");
            }
        });

        inSession("lee", new Task() {
            @Override
            public void run() {
                for (int i = 1; i <= 2; i++) {
                    System.out.println("주문 " + i + " 조회");
                }
            }
        });
    }
}

    변하는 부분 가운데 사용자 이름은 값이므로 String 매개변수로, 가운데에서 하는 일은 코드이므로 Task 객체로 받았다. 출력은 원래와 같은 일곱 줄이다. 클래스 파일은 Session.class, Session$Task.class, Session$1.class, Session$2.class 네 개가 생긴다. 중첩 인터페이스는 $이름, 익명 클래스는 소스에 나온 순서대로 $1, $2다. 결제 쪽 익명 클래스 Session$1은 amount를 캡처하므로 final int val$amount 필드와 (I)V 생성자를 갖는다. static 메서드 안이므로 바깥 인스턴스 인자는 없다. 조회 쪽 Session$2는 바깥의 어떤 변수도 쓰지 않으므로 합성 필드가 없고 생성자 디스크립터는 ()V다. inSession()의 시그니처에는 amount를 받는 자리가 없는데도 결제 금액이 틀 안에서 출력되는 것은 값이 Task 객체 안에 실려 넘어갔기 때문이다. Task는 추상 메서드가 하나이므로 두 익명 클래스 모두 람다로 바꿀 수 있고, 그렇게 하면 Session$1.class와 Session$2.class는 생기지 않는다.

     메서드가 반환해 프레임이 파괴된 뒤에도 지역 클래스의 인스턴스가 그 메서드의 지역 변수 값을 읽을 수 있는 이유는 무엇인가? JVM이 지역 클래스가 쓰는 지역 변수가 있는 프레임을 파괴하지 않고 힙으로 옮겨 보존하기 때문이다. 인스턴스가 생성될 때 컴파일러가 만든 생성자 인자를 통해 그 시점의 값이 인스턴스의 합성 필드로 복사되기 때문이다. 인스턴스가 프레임의 지역 변수 칸을 가리키는 참조를 갖고 있고, 가비지 컬렉터가 그 칸을 회수하지 않기 때문이다. 지역 클래스가 쓰는 지역 변수는 컴파일러가 자동으로 static 필드로 바꾸기 때문이다. 컴파일러는 지역 클래스에 val$이름 합성 필드와 숨은 생성자 인자를 만들고, new가 실행될 때 프레임에서 읽은 값을 그 필드에 넣는다. 그 뒤 메서드는 getfield로 자기 필드를 읽으므로 프레임이 없어도 된다. 프레임은 메서드 호출이 끝나면 파괴된다고 JVMS 2.6이 정하므로 보존되지 않는다. JVM의 참조 값은 힙의 객체를 가리키거나 null이며 지역 변수 칸을 가리키는 참조는 없다. static 필드로 바꾼다면 인스턴스마다 다른 값을 가질 수 없는데, 본문의 Snapshots 예제에서 세 인스턴스는 각자 0, 10, 20을 갖고 있었다. 자바가 내부 클래스와 람다에서 쓰는 바깥 지역 변수를 final이거나 사실상 final인 것으로 제한하는 근본 이유로 가장 알맞은 것은? final 변수는 JIT 컴파일러가 더 빠른 코드로 바꿀 수 있어서 성능을 위해 강제한다. 지역 변수는 스택에 있어서 가비지 컬렉터가 추적할 수 없으므로, 값이 바뀌면 메모리 누수가 생긴다. 캡처는 값 복사이므로 변수가 바뀔 수 있으면 프레임의 원본과 인스턴스의 복사본이 서로 다른 값을 갖게 되고, 변수 자체를 공유하게 만들면 지역 변수가 스레드에 국한된다는 성질이 깨지기 때문이다. 내부 클래스는 바깥 클래스의 private 멤버에 접근할 수 없으므로 지역 변수라도 고정해 두어야 하기 때문이다. 복사본이 둘인데 한쪽만 바뀌면 소스에서는 같은 이름인 변수가 실행 중에는 다른 값을 갖는다. 값이 바뀌지 않는 변수만 캡처하게 하면 복사인지 공유인지 구별할 수 없으므로 이 문제가 사라진다. 변수를 힙에 두고 공유하는 방법은 지역 변수를 다른 스레드에 노출시키며, JLS 15.27.2는 변하는 지역 변수의 캡처가 동시성 문제를 일으키기 쉽다는 점을 이유로 든다. 성능이나 메모리 누수는 이 규칙의 근거가 아니다. 내부 클래스는 바깥 클래스의 private 멤버에 접근할 수 있고, 필드에는 이 규칙이 적용되지 않는다. int[] counter = {0};을 선언하고 익명 클래스 안에서 counter[0]++를 실행하는 코드는 컴파일되고, 바깥 메서드에서도 바뀐 값이 보인다. 이 동작을 가장 정확하게 설명한 것은? 변수 counter에 든 참조값은 한 번도 바뀌지 않으므로 사실상 final이고, 복사된 참조값과 원래 참조값이 힙의 같은 배열 객체를 가리키므로 원소의 변경이 양쪽에서 보인다. 배열 타입의 변수에는 사실상 final 규칙이 적용되지 않도록 언어 명세가 예외를 두었다. 배열을 캡처하면 컴파일러가 배열 전체를 인스턴스 안으로 깊은 복사하고, 메서드가 끝날 때 원본에 다시 써 주기 때문이다. 익명 클래스가 바깥 메서드의 프레임에 있는 counter 칸을 직접 읽고 쓰기 때문이다. counter[0]++는 변수 counter에 대입하는 것이 아니라 그 변수가 가리키는 배열의 원소를 바꾸는 것이다. 변수의 값인 참조는 그대로이므로 규칙을 어기지 않는다. 컴파일된 클래스에는 final int[] val$counter 필드가 있고 여기에 참조값이 복사된다. 배열 객체는 힙에 하나뿐이다. 배열에 대한 예외 규정은 없고, 깊은 복사나 다시 써 주는 동작도 없다. 다른 메서드의 프레임 칸을 읽고 쓰는 방법은 JVM에 없다. 이 우회는 바뀌는 상태를 힙으로 옮긴 것이므로 다른 스레드와 공유되면 동기화가 필요해진다. 반복문 안에 new Runnable() { … } 식이 하나 있고 반복문이 다섯 번 돈다. 이때 만들어지는 클래스와 인스턴스의 수는? 실행 중에 클래스 5개가 만들어지고 각 클래스의 인스턴스가 1개씩 생긴다. 클래스 1개, 인스턴스 1개다. 같은 식이므로 JVM이 첫 인스턴스를 재사용한다. 클래스는 만들어지지 않고, 인터페이스 Runnable의 인스턴스 5개가 생긴다. 클래스는 컴파일할 때 만들어진 1개이고, 식이 실행될 때마다 그 클래스의 새 인스턴스가 만들어져 모두 5개다. 익명 클래스는 컴파일할 때 Outer$1.class라는 클래스 파일 하나로 만들어진다. 익명 클래스 식은 인스턴스 생성 식이므로 실행될 때마다 new 명령어가 새 객체를 만든다. 본문에서 labeler()를 두 번 호출해 얻은 두 객체의 getClass()가 같고 == 비교는 false였던 것과 같다. 평가할 때마다 새 객체를 만들 필요가 없다는 재량은 람다에 대해 JLS 15.27.4가 준 것이고 익명 클래스에는 해당하지 않는다. 인터페이스는 인스턴스를 만들 수 없으며, 만들어지는 것은 그 인터페이스를 구현한 이름 없는 클래스의 인스턴스다. 인스턴스 메서드 안에 있는 익명 클래스 new Runnable() { public void run() { register(this); } }를 람다 () -> register(this)로 바꿨다. 무엇이 달라지는가? 달라지는 것이 없다. 람다는 익명 클래스를 짧게 쓴 문법이므로 컴파일 결과가 같다. register()에 넘어가는 객체가 달라진다. 익명 클래스에서는 그 Runnable 객체 자신이, 람다에서는 람다를 둘러싼 메서드의 this인 바깥 인스턴스가 넘어간다. 람다 본문에서는 this를 쓸 수 없으므로 항상 컴파일 오류가 난다. 람다는 사실상 final 규칙의 적용을 받지 않으므로 바깥 지역 변수를 바꿀 수 있게 된다. 익명 클래스의 본문은 새 클래스의 본문이어서 this가 익명 클래스의 인스턴스다. 람다의 본문은 새 스코프를 만들지 않으며, JLS 15.27.2에 따라 this의 의미가 둘러싼 문맥과 같다. 그래서 같은 this라는 글자가 다른 객체를 가리킨다. 바깥 클래스가 register()의 매개변수 타입에 맞으면 컴파일도 되므로 조용히 동작이 바뀔 수 있다. 컴파일 결과도 다르다. 익명 클래스는 별도 클래스 파일과 new, 람다는 바깥 클래스의 메서드와 invokedynamic이다. 인스턴스 메서드 안의 람다는 this를 쓸 수 있고, 캡처하는 지역 변수에는 익명 클래스와 같은 사실상 final 조건이 적용된다.

    블록 안에서 선언한 클래스. 이름의 유효 범위가 선언한 곳부터 블록 끝까지이며 접근 제어자와 static을 붙일 수 없다.
    익명 클래스(anonymous class)
    new 상위타입() { 본문 } 형태의 식으로 선언과 동시에 인스턴스를 만드는 이름 없는 클래스. 항상 내부 클래스다.
    내부 클래스(inner class)
    명시적으로도 암묵적으로도 static이 아닌 중첩 클래스. static이 아닌 멤버 클래스, 일반 클래스로 선언한 지역 클래스, 익명 클래스가 여기에 속한다.
    지역 변수 캡처(variable capture)
    내부 클래스나 람다가 자신을 둘러싼 메서드의 지역 변수·매개변수를 쓸 때, 그 값이 생성 시점에 복사되어 함께 보관되는 것.
    사실상 final(effectively final)
    final로 선언하지 않았지만 대입식의 왼쪽이나 증감 연산의 피연산자로 한 번도 나오지 않는 지역 변수. JLS 4.12.4가 정의한다.
    상수 변수(constant variable)
    상수식으로 초기화된, 기본형 또는 String 타입의 final 변수. 컴파일러가 쓰는 자리에 값을 직접 넣으므로 캡처 필드가 필요 없다.
    합성 구성 요소(synthetic construct)
    소스 코드에 대응하는 선언 없이 컴파일러가 만들어 넣은 필드·메서드 등. 클래스 파일에 ACC_SYNTHETIC 플래그로 표시된다. val$이름, this$0이 그 예다.
    바이너리 이름(binary name)
    컴파일된 클래스가 갖는 이름. 지역 클래스는 바깥$숫자이름, 익명 클래스는 바깥$숫자 형태다.
    프레임(frame)
    메서드 호출마다 스레드의 JVM 스택에 만들어지는 구조. 지역 변수 배열과 피연산자 스택을 가지며 호출이 끝나면 파괴된다.
    함수형 인터페이스(functional interface)
    추상 메서드가 하나뿐인 인터페이스. 익명 클래스 대신 람다 식으로 구현할 수 있다.
