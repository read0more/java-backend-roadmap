    기본형은 객체가 아니다: 이 회차의 질문

    자바의 타입은 두 갈래다. int, double, boolean 같은 기본형(primitive type) 여덟 개와, 클래스·인터페이스·배열로 이뤄진 참조형(reference type)이다. 기본형 변수에는 값 자체가 들어 있고 참조형 변수에는 힙에 있는 객체를 가리키는 참조값이 들어 있다는 것은 기본편에서 다뤘다. 기본형은 값이 변수 안에 바로 있으므로 읽고 쓰는 데 거치는 단계가 없고 차지하는 공간도 값의 크기만큼이다.

    문제는 자바의 나머지 부분이 전부 객체 위에 세워져 있다는 점이다. 모든 클래스의 부모는 Object이고, 다형성은 참조를 통해 동작하고, "아무것도 가리키지 않음"을 뜻하는 null은 참조에만 있다. 다음 권에서 다룰 컬렉션과 제네릭도 참조형만 받는다. 기본형은 이 체계 바깥에 서 있다. 숫자 하나를 객체처럼 다뤄야 하는 순간이 오면 기본형만으로는 방법이 없다.

    이 회차의 앞쪽 절반은 그 틈을 메우는 래퍼 클래스(wrapper class)를 다룬다. 직접 만들어 보고, 자바가 제공하는 것을 쓰고, 컴파일러가 대신 써 주는 오토 박싱이 바이트코드에서 무엇이 되는지 확인한다. 뒤쪽 절반은 java.lang에 있는 Class, System, Math와 java.util의 Random을 본다. 넷은 서로 관련이 없어 보이지만 공통점이 있다. 실행 중인 JVM과 그 바깥의 운영체제가 가진 정보(클래스의 구조, 시계, 환경 변수, 프로세스 종료)를 자바 코드가 쓸 수 있는 형태로 꺼내 놓은 창구라는 점이다.

    기본형의 한계 ①: 메서드도 없고 Object도 아니다

    기본형 값은 객체가 아니므로 점(.)을 찍어 따라갈 대상이 없다. 다음 코드는 컴파일되지 않는다.

    int value = 10;
String s = value.toString();
    error: int cannot be dereferenced
        String s = value.toString();
                        ^

    오류 문구의 dereference는 "참조를 따라가 그 끝에 있는 객체에 닿는다"는 뜻이다. value 안에는 참조가 아니라 10이라는 값이 들어 있으므로 따라갈 것이 없다. 그래서 int에 관한 기능은 값의 바깥 어딘가에 static 메서드로 두고, 값을 인자로 넘겨서 쓸 수밖에 없다. 두 수를 비교하는 기능이 필요하면 compare(a, b) 같은 메서드를 어느 클래스엔가 만들어 둔다. 데이터와 그 데이터를 다루는 기능이 떨어져 있는, 기본편 3회차에서 본 절차 지향의 모습 그대로다.

    두 번째 문제는 기본형 값이 Object 타입의 자리에 들어가지 못한다는 것이다. Object[] 배열의 원소, Object를 받는 메서드의 인자, 그리고 타입 매개변수가 모두 참조형을 요구한다. 제네릭은 다음 권에서 다루지만 컴파일러의 반응만 미리 보면 다음과 같다.

    import java.util.List;

public class BadList {
    List xs;
}
    BadList.java:4: error: unexpected type
    List xs;
         ^
  required: reference
  found:    int

    "참조형이 필요한데 int가 왔다"는 말이다. 이 두 문제를 푸는 방법은 하나다. int 값 하나를 필드로 품은 객체를 만드는 것이다.

    public class IntBox {
    private final int value;

    public IntBox(int value) {
        this.value = value;
    }

    public int get() {
        return value;
    }

    public int compareTo(int other) {
        if (value < other) return -1;
        if (value > other) return 1;
        return 0;
    }

    @Override
    public String toString() {
        return String.valueOf(value);
    }
}
    public class IntBoxMain {
    public static void main(String[] args) {
        IntBox box = new IntBox(10);
        System.out.println(box.compareTo(20));
        System.out.println(box);

        Object[] things = { box, "text", new IntBox(7) };
        for (Object o : things) {
            System.out.println(o);
        }
    }
}

    이제 10이라는 값은 자기 메서드를 가진다. box.compareTo(20)은 값이 스스로 비교를 수행하는 모양이고, println(box)는 오버라이딩한 toString()을 부른다. IntBox는 Object의 자식이므로 Object[]에 문자열과 섞여 들어간다. 이렇게 기본형 값을 감싸서(wrap) 객체로 만든 클래스를 래퍼 클래스라고 부른다. 필드를 private final로 둔 것은 앞 회차에서 본 불변 객체의 설계다. 숫자 10이 어느 날 11이 되어서는 안 되기 때문이다.

    공짜는 아니다. 값 하나마다 힙에 객체 하나가 생기고, 값을 읽으려면 참조를 한 번 따라가야 한다. 이 비용이 얼마인지는 뒤에서 측정한다.

    기본형의 한계 ②: "없음"을 담을 수 없다

    기본형 변수는 언제나 값을 가진다. int는 32비트이고 그 비트 조합 232가지가 전부 유효한 정수에 대응한다. "값이 없다"를 나타내려고 남겨 둔 조합이 없다. 반면 참조형 변수에는 어떤 객체도 가리키지 않는다는 뜻의 null이 있다. 이 차이가 드러나는 전형적인 상황이 "찾았는데 없을 수도 있는" 조회다.

    public class FindDemo {
    public static void main(String[] args) {
        int[] winter = {5, -1, 8};
        int[] summer = {21, 25, 30};

        System.out.println(firstNegativeOrMinusOne(winter));
        System.out.println(firstNegativeOrMinusOne(summer));

        System.out.println(firstNegative(winter));
        System.out.println(firstNegative(summer));

        int t = firstNegative(summer);
        System.out.println(t);
    }

    static int firstNegativeOrMinusOne(int[] values) {
        for (int v : values) {
            if (v < 0) return v;
        }
        return -1;
    }

    static Integer firstNegative(int[] values) {
        for (int v : values) {
            if (v < 0) return v;
        }
        return null;
    }
}

    첫 번째 메서드는 반환 타입이 int여서 "못 찾았다"를 표현할 방법이 없다. 그래서 -1을 약속된 신호로 썼는데, 겨울 기온 배열에서 실제로 찾은 값도 -1이다. 출력의 첫 두 줄은 똑같이 -1이고, 호출한 쪽은 "영하 1도를 찾았다"와 "영하인 날이 없다"를 구분하지 못한다. 이런 특별한 값을 센티널(sentinel) 값이라 하는데, 데이터가 가질 수 있는 범위와 겹치는 순간 쓸모가 없어진다.

    두 번째 메서드는 반환 타입이 Integer다. 자바가 제공하는 int의 래퍼 클래스이고, 참조형이므로 null을 돌려줄 수 있다. 셋째 줄 -1은 찾은 값이고 넷째 줄 null은 없다는 뜻이다. 둘이 겹치지 않는다.

    대신 새로운 위험이 생긴다. 마지막 두 줄에서 null을 int 변수에 넣으려는 순간 NullPointerException이 났다. 메시지가 가리키듯 null에 대고 intValue()를 호출했기 때문이다. 소스에는 그런 호출이 없는데 어디서 나왔는지는 오토 박싱 절에서 바이트코드로 확인한다. 지금은 "없음을 표현할 수 있게 된 대가로, 없음을 확인할 책임이 호출하는 쪽에 생겼다"는 것만 기억해 두자.

    같은 차이가 필드의 기본값에도 나타난다. int score 필드는 초기화하지 않으면 0이고, Integer score 필드는 null이다. 시험 점수라면 0은 "0점을 받았다"와 "아직 채점하지 않았다"를 가르지 못하지만 null은 가른다. 어느 쪽을 쓸지는 "이 값이 없을 수 있는가"라는 질문에 달려 있다.

    이름은 대부분 기본형의 첫 글자를 대문자로 바꾼 것이고, int와 char만 Integer, Character로 풀어 썼다. 숫자를 감싸는 여섯 개는 추상 클래스 Number를 상속한다. Number에는 intValue(), longValue(), floatValue(), doubleValue()가 추상 메서드로 선언되어 있어서, 어떤 숫자 래퍼든 원하는 기본형으로 꺼낼 수 있다.

    OpenJDK 21의 Integer 소스에서 뼈대만 추리면 앞에서 만든 IntBox와 구조가 같다.

    public final class Integer extends Number
        implements Comparable, Constable, ConstantDesc {

    private final int value;

    public int intValue() {
        return value;
    }

    public boolean equals(Object obj) {
        if (obj instanceof Integer) {
            return value == ((Integer)obj).intValue();
        }
        return false;
    }

    public static int hashCode(int value) {
        return value;
    }
    // ...
}

    읽어 낼 것은 네 가지다. 클래스가 final이어서 상속할 수 없다. 필드가 private final int value 하나뿐이고 값을 바꾸는 메서드가 없으므로 불변 객체다. equals는 상대가 Integer일 때만 안에 든 값을 비교한다. 해시코드는 값 그 자체다. 1회차에서 본 equals/hashCode 규약을 가장 단순한 형태로 구현한 클래스라고 볼 수 있다.

    박싱과 언박싱

    기본형 값을 래퍼 객체로 바꾸는 것을 박싱(boxing), 래퍼 객체에서 기본형 값을 꺼내는 것을 언박싱(unboxing)이라고 한다. 상자에 넣고 꺼낸다는 뜻이다. 손으로 쓰면 박싱은 Integer.valueOf(값), 언박싱은 intValue()다.

    public class WrapperBasics {
    public static void main(String[] args) {
        Integer a = Integer.valueOf(1000);
        Integer b = Integer.valueOf(1000);
        int raw = a.intValue();

        System.out.println(a);
        System.out.println(raw + 1);
        System.out.println(a == b);
        System.out.println(a.equals(b));

        Integer before = a;
        a = Integer.valueOf(a.intValue() + 1);
        System.out.println(a + " " + before + " " + (a == before));
    }
}

    println(a)는 Integer.toString()이 돌려준 문자열을 찍는다. a == b는 두 변수에 든 참조값을 비교하는데, 1000을 감싼 객체가 두 개 만들어졌으므로 false다. a.equals(b)는 안의 값을 비교하므로 true다. 1회차의 동일성(identity)과 동등성(equality) 구분이 그대로 적용된다.

    마지막 세 줄은 불변성을 보여 준다. "a를 1 늘린다"는 일은 기존 객체의 value를 고치는 것이 아니라, 1001을 감싼 다른 객체의 참조로 변수 a를 바꾸는 것이다. before가 가리키던 객체는 여전히 1000이다. 여러 곳에서 같은 Integer 객체를 공유해도 한쪽의 계산이 다른 쪽에 새어 나가지 않는 이유가 여기에 있다.

    생성자 new Integer(10)도 아직 남아 있지만 JDK 9부터 사용 중단(deprecated)되었고, OpenJDK 21 소스에서는 @Deprecated(since="9", forRemoval = true)로 표시되어 있다. 컴파일하면 warning: [removal] Integer(int) in Integer has been deprecated and marked for removal이 나온다. Javadoc은 공간과 시간 성능이 더 나을 가능성이 큰 valueOf를 쓰라고 안내한다. 왜 더 나은지는 캐시 절에서 본다.

    메모리에서 본 int와 Integer

    int a = 1000;과 Integer b = 1000;은 소스에서는 한 글자 차이지만 메모리에서는 모양이 다르다. 두 변수가 메서드의 지역 변수라고 하자.

       스택 프레임 (지역 변수 배열)                힙

   +-----------+----------+
   | a  (int)  |   1000   |      값이 칸 안에 그대로 들어 있다
   +-----------+----------+
   | b (참조)  |   ●──────────────▶ +----------------------------+
   +-----------+----------+         | 객체 헤더 (12바이트)       |
                                    |   마크 워드 8 + 클래스 워드 4 |
                                    +----------------------------+
                                    | value : int = 1000 (4바이트) |
                                    +----------------------------+
                                      Integer 객체 하나 = 16바이트

    a를 읽는 것은 스택 프레임의 칸 하나를 읽는 일이다. b의 값을 읽으려면 칸에서 참조를 읽고, 그 참조가 가리키는 힙의 객체로 가서 value 필드를 읽어야 한다. 값 4바이트를 담으려고 객체 헤더 12바이트가 붙었고, 그 객체를 가리키는 참조도 따로 자리를 차지한다.

    "16바이트"는 추측이 아니라 측정한 값이다. JDK에 들어 있는 jcmd로 실행 중인 JVM의 클래스별 인스턴스 수와 바이트 수를 볼 수 있다. 값 100만 개를 int[]와 Integer[]에 똑같이 담고 비교해 보자.

    public class BoxedArray {
    public static void main(String[] args) throws Exception {
        int n = 1_000_000;
        int[] plain = new int[n];
        Integer[] boxed = new Integer[n];
        for (int i = 0; i < n; i++) {
            plain[i] = i + 1000;
            boxed[i] = i + 1000;
        }
        System.out.println("pid " + ProcessHandle.current().pid());
        Thread.sleep(60_000);
        System.out.println(plain.length + boxed.length);
    }
}

Integer 객체 하나가 16바이트라는 뜻이다. 인스턴스가 100만 개보다 262개 많은 것은 프로그램이 만든 것 말고도 JVM 안에 Integer 객체가 있기 때문인데, 그 가운데 256개의 정체는 캐시 절에서 밝혀진다. 셋째 행의 [Ljava.lang.Integer;는 Integer[] 배열의 클래스 이름이다. 배열 두 개 가운데 하나가 우리가 만든 것이고, 크기는 배열 헤더 16바이트에 참조 4바이트 100만 개를 더한 4,000,016바이트다. 나머지 1,040바이트는 원소 256개짜리 배열 하나(16 + 4 × 256)다.

    정리하면 값 100만 개를 int[]에 담으면 배열 하나 4,000,016바이트로 끝난다. Integer[]에 담으면 참조 배열 4,000,016바이트에 객체 100만 개 16,000,000바이트가 더해져 약 2,000만 바이트, 다섯 배다. 이 수치는 64비트 HotSpot이 참조와 클래스 포인터를 4바이트로 압축하는 기본 설정에서 나온 것이고, 옵션이나 JVM이 바뀌면 달라진다. 달라지지 않는 것은 구조다. 기본형 배열은 값이 연속으로 놓인 한 덩어리이고, 래퍼 배열은 참조가 연속으로 놓인 배열과 힙 여기저기에 놓인 객체들로 이뤄진다. 객체들이 힙의 어디에 놓일지는 할당 시점과 가비지 컬렉터가 정하며, 가비지 컬렉터가 살펴야 할 객체도 그만큼 늘어난다.

    int는 스택 칸에 값이 바로 있고, Integer는 스택 칸의 참조가 힙의 16바이트 객체(헤더 12 + 값 4)를 가리킨다는 것을 한눈에 보여 준다. 깔끔한 평면 기술 다이어그램. 왼쪽에 세로로 긴 상자 "스택 프레임"이 있고 그 안에 가로 칸 두 개. 위 칸에는 라벨 "int a"와 값 "1000"이 칸 안에 직접 적혀 있다. 아래 칸에는 라벨 "Integer b"와 검은 점 하나. 오른쪽에 큰 영역 "힙"이 있고 그 안에 상자 하나가 위아래 두 부분으로 나뉘어 있다. 윗부분 라벨 "객체 헤더 12바이트", 아랫부분 라벨 "value = 1000 (4바이트)". 상자 아래에 작은 글씨 "Integer 객체 16바이트". 아래 칸의 검은 점에서 힙의 상자로 화살표 하나가 이어지고 화살표 위에 라벨 "참조". 위 칸 옆에는 "값이 칸 안에 있다"라는 주석. 흰 배경, 얇은 선, 파란색과 회색 두 가지 색만 사용, 한국어 라벨은 따옴표 안 문구 그대로. 같은 1000이라도 int는 스택 칸 하나, Integer는 참조와 힙 객체 하나를 쓴다(Temurin 21 HotSpot 기본 옵션 기준 크기).

    오토 박싱과 오토 언박싱: 컴파일러가 써 넣는 메서드 호출

    기본형과 래퍼 사이를 오갈 때마다 Integer.valueOf(...)와 intValue()를 쓰는 것은 번거롭다. 자바 5부터는 이 변환을 컴파일러가 대신 써 넣는다. 언어 명세의 용어로는 박싱 변환(boxing conversion, JLS 5.1.7)과 언박싱 변환(unboxing conversion, JLS 5.1.8)이고, 프로그래머가 적지 않아도 자동으로 일어난다는 뜻에서 오토 박싱(autoboxing), 오토 언박싱이라고 부른다.

    public class AutoBox {
    public static void main(String[] args) {
        Integer a = 10;
        int b = a;
        Integer c = a + b;
        System.out.println(c);
    }
}

    실행하면 20이 나온다. Integer 타입 변수에 int 리터럴을 넣고, int 변수에 Integer를 넣고, 둘을 더했는데 오류가 없다. JLS 5.1.7은 박싱 변환의 결과를 "r.intValue() == p가 되는 Integer 타입의 참조 r"이라고만 정한다. 그 참조를 어떻게 얻을지는 컴파일러가 고른다. javac가 무엇을 골랐는지 javap -c AutoBox로 보자.

    • Integer a = 10;은 0~5번이다. 상수 10을 피연산자 스택에 올리고(bipush), static 메서드 Integer.valueOf(int)를 호출해(invokestatic) 돌려받은 참조를 지역 변수 1번에 저장한다(astore_1). 소스에 없던 valueOf 호출이 들어갔다.
    • int b = a;는 6~10번이다. 지역 변수 1번의 참조를 올리고 intValue()를 호출해(invokevirtual) 돌려받은 int를 지역 변수 2번에 저장한다(istore_2).
    • Integer c = a + b;는 11~20번이다. a를 언박싱하고, b를 올리고, int 덧셈을 한 다음(iadd), 결과를 다시 valueOf로 박싱한다. 덧셈은 객체끼리가 아니라 꺼낸 int끼리 한다.

    여기서 얻을 결론은 두 가지다. 첫째, 오토 박싱은 컴파일러가 하는 일이다. 클래스 파일에는 평범한 메서드 호출 명령만 있고 JVM은 "박싱"이라는 개념을 따로 알지 못한다. 저장할 때 쓰는 명령이 astore(참조)와 istore(int)로 갈리는 데서 보이듯, JVM 수준에서 Integer와 int는 여전히 다른 종류의 값이다. 둘째, 소스에서 보이지 않는 메서드 호출과 객체 생성이 숨어 있다. Integer 변수에 ++를 쓰거나 +=를 쓰는 것도 같은 방식으로 "언박싱, 계산, 박싱" 세 단계가 된다.

    언박싱과 NullPointerException

    앞 절의 예외가 어디서 나왔는지 이제 설명할 수 있다. int t = firstNegative(summer);는 반환된 참조에 대고 intValue()를 호출하는 코드로 컴파일된다. 반환값이 null이면 null에 대한 메서드 호출이 되고, JVM은 NullPointerException을 던진다. JLS 5.1.8도 언박싱 대상이 null이면 NullPointerException을 던진다고 적어 두었다. 메시지의 Cannot invoke "java.lang.Integer.intValue()"는 컴파일러가 써 넣은 그 호출을 가리킨다.

    소스만 보면 점(.)도 메서드 호출도 없는 줄에서 NPE가 난다는 점이 이 예외를 찾기 어렵게 만든다. 스택 트레이스가 가리키는 줄에 Integer, Long, Boolean 같은 래퍼 타입의 값이 기본형 자리로 들어가는 곳이 있는지 살피면 된다. 산술 연산, 비교 연산, if의 조건, 기본형 매개변수에 넘기는 인자가 모두 그런 자리다.

    Integer 캐시와 == 의 함정

    앞에서 Integer.valueOf(1000) 두 번은 서로 다른 객체를 돌려주었다. 숫자를 바꾸면 결과가 달라진다.

    Integer p = 127, q = 127;
Integer r = 128, s = 128;
System.out.println(p == q);   // true
System.out.println(r == s);   // false  (JVM 기본 옵션)

    127은 같은 객체이고 128은 다른 객체다. 이유는 valueOf의 구현에 있다.

    public static Integer valueOf(int i) {
    if (i >= IntegerCache.low && i <= IntegerCache.high)
        return IntegerCache.cache[i + (-IntegerCache.low)];
    return new Integer(i);
}

    IntegerCache는 Integer 안에 있는 중첩 클래스이고, low는 -128, high는 기본값 127이다. 이 클래스가 초기화되면 cache 배열에 -128부터 127까지 256개의 Integer 객체가 채워진다. valueOf는 인자가 이 범위 안이면 배열에서 꺼낸 기존 객체를, 범위 밖이면 새로 만든 객체를 돌려준다. 앞 절의 측정에서 남았던 인스턴스 256개와 원소 256개짜리 Integer[] 배열이 바로 이것이다.

    명세가 보장하는 것과 구현이 하는 것

    이 동작 가운데 어디까지가 약속인지 나눠 보자. JLS 5.1.7은 박싱하는 값이 상수식의 결과이고 그 값이 true, false, '\u0000'~'\u007f' 범위의 문자, -128~127 범위의 정수이면, 그 값을 두 번 박싱한 결과 a와 b에 대해 항상 a == b라고 정한다. 그 밖의 값에 대해서는 박싱된 객체의 동일성을 어느 쪽으로도 가정하지 못하게 한다. Integer.valueOf의 Javadoc도 -128~127은 항상 캐시하며 그 밖의 값도 캐시할 수 있다고 적는다.

    "그 밖의 값도 캐시할 수 있다"는 말은 빈말이 아니다. HotSpot에는 캐시의 상한을 올리는 옵션이 있다. 같은 코드를 java -XX:AutoBoxCacheMax=1000으로 실행하면 r == s가 true로 바뀐다. 소스가 한 글자도 달라지지 않았는데 JVM 옵션 하나로 ==의 결과가 뒤집힌다는 것은, 래퍼 객체의 == 비교 결과에 프로그램이 의존해서는 안 된다는 뜻이다.

    다른 래퍼의 valueOf도 사정이 비슷하다. OpenJDK 21 소스 기준으로 정리하면 다음과 같다.

    래퍼는 equals로 비교한다

    규칙은 하나로 줄어든다. 래퍼 객체끼리 값이 같은지 물을 때는 equals를 쓴다. 작은 수로 시험할 때는 ==가 우연히 맞아떨어지고, 운영 데이터에 128 이상의 값이 들어오는 날 조용히 틀리기 시작하는 것이 이 버그의 전형적인 경로다.

    한쪽이 기본형이면 사정이 다르다. JLS 15.21.1에 따르면 ==의 한쪽 피연산자가 숫자 타입이고 다른 쪽이 숫자 타입으로 변환할 수 있는 타입이면 이항 숫자 승격을 한다. 곧 래퍼 쪽을 언박싱해서 값끼리 비교한다. 양쪽이 모두 참조형이면 JLS 15.21.3의 참조 비교가 된다. Integer x = 1000; int z = 1000;일 때 x == z가 true인 것은 앞의 규칙 덕분이고, 이때 x가 null이면 언박싱에서 NPE가 난다.

    Integer의 Javadoc은 이 클래스를 값 기반 클래스(value-based class)라고 부르며, 동등한 인스턴스를 서로 바꿔 써도 되는 것으로 다루고 동기화에 쓰지 말라고 적는다. 실제로 Integer 객체를 synchronized의 락으로 쓰면 javac가 warning: [synchronization] attempt to synchronize on an instance of a value-based class를 낸다. "어느 객체인가"가 아니라 "무슨 값인가"만 의미가 있는 타입이라는 뜻이다.
    valueOf(127) 두 번은 캐시 배열의 같은 칸을 가리키고, valueOf(128) 두 번은 서로 다른 새 객체 두 개를 가리킨다는 대비를 보여 준다. 깔끔한 평면 기술 다이어그램, 좌우 두 부분으로 나뉜다. 왼쪽 부분 제목 "valueOf(127)을 두 번". 위쪽에 변수 상자 두 개 "p", "q"가 나란히 있고, 아래쪽에 가로로 긴 배열 그림 "IntegerCache.cache"가 있다. 배열은 칸 여러 개로 나뉘며 맨 왼쪽 칸에 "-128", 가운데 칸에 "0", 맨 오른쪽 칸에 "127"이 적혀 있다. p와 q에서 나온 화살표 두 개가 모두 맨 오른쪽 "127" 칸으로 모인다. 그 아래에 초록색 글씨 "p == q 는 true". 오른쪽 부분 제목 "valueOf(128)을 두 번". 위쪽에 변수 상자 두 개 "r", "s", 아래쪽에 서로 떨어진 객체 상자 두 개가 있고 각각 "128"이 적혀 있다. r의 화살표는 왼쪽 객체로, s의 화살표는 오른쪽 객체로 간다. 그 아래에 빨간색 글씨 "r == s 는 false". 흰 배경, 얇은 선, 색은 파랑·초록·빨강만 사용. 캐시 범위 안의 값은 미리 만들어 둔 객체 하나를 함께 쓰고, 범위 밖의 값은 호출마다 새 객체가 된다.

    박싱이 끼어드는 자리에서 생기는 함정

    오토 박싱은 편리하지만, 변환이 눈에 보이지 않기 때문에 타입 규칙을 정확히 모르면 결과를 잘못 예측하게 된다. 한 프로그램에 대표적인 경우를 모았다.

    public class Traps {
    static void f(long x)    { System.out.println("f(long)"); }
    static void f(Integer x) { System.out.println("f(Integer)"); }

    public static void main(String[] args) {
        Long big = 1L;
        System.out.println(big.equals(1));
        System.out.println(big.equals(1L));

        f(1);

        Integer count = null;
        boolean ready = false;
        Integer shown = ready ? 0 : count;
        System.out.println(shown);
    }
}

    equals에 넘긴 값도 박싱된다

    big.equals(1)이 false다. equals의 매개변수 타입은 Object이므로 인자 1은 박싱되는데, 리터럴 1의 타입은 int이므로 Integer가 된다. Long.equals는 Integer.equals와 같은 모양으로, 상대가 Long의 인스턴스가 아니면 값을 보지도 않고 false를 돌려준다. 값이 둘 다 1이어도 타입이 다르면 같지 않다. 1L을 넘겨야 Long으로 박싱되어 true가 된다.

    같은 뿌리의 컴파일 오류도 있다. Long a = 1;은 incompatible types: int cannot be converted to Long으로 거부된다. long a = 1;은 int를 long으로 넓히는 변환이라 되고, Long a = 1L;은 박싱이라 되지만, JLS 5.2가 대입에서 허용하는 변환 목록에 "넓힌 다음 박싱"은 없다. 컴파일러는 변환을 한 번에 한 종류씩, 정해진 조합으로만 적용한다.

    오버로딩: 박싱은 두 번째 순서다

    f(1)은 f(Integer)가 아니라 f(long)을 호출했다. JLS 15.12.2는 호출할 메서드를 세 단계로 찾는다. 첫 단계에서는 박싱·언박싱과 가변 인자를 쓰지 않고 맞는 메서드를 찾는다. 없으면 둘째 단계에서 박싱·언박싱을 허용하고, 그래도 없으면 셋째 단계에서 가변 인자까지 허용한다. int를 long으로 넓히는 것은 첫 단계에서 가능하므로 f(long)이 먼저 선택되고, 박싱이 필요한 f(Integer)는 검토 대상에 오르지도 않는다. 명세는 이렇게 단계를 나눈 이유를 자바 5 이전 언어와의 호환성이라고 밝힌다. 오토 박싱이 생기기 전에 컴파일되던 코드가 같은 메서드를 계속 부르게 하려는 것이다.

    조건 연산자가 타입을 하나로 맞춘다

    마지막 예외가 가장 알아채기 어렵다. ready ? 0 : count에서 선택된 것은 count이고, 그 값 null을 Integer 변수에 넣는 것이니 문제가 없어 보인다. 그런데 조건 연산자는 식 전체의 타입을 먼저 하나로 정한다. JLS 15.25에 따르면 둘째와 셋째 피연산자 가운데 하나가 기본형 T이고 다른 하나가 T를 박싱한 타입이면 식의 타입은 T다. 여기서는 0이 int, count가 Integer이므로 식의 타입은 int다. 그래서 count를 언박싱하고, 그 결과를 다시 박싱해 shown에 넣는 코드가 만들어진다. 언박싱에서 NPE가 난다.

    둘째 피연산자를 Integer.valueOf(0)으로 바꿔 양쪽을 모두 Integer로 맞추면 식의 타입이 Integer가 되어 언박싱이 사라지고, 프로그램은 null을 출력한다. 메시지의 ""는 디버그 정보 없이 컴파일해서 지역 변수 이름 대신 지역 변수 배열의 칸 번호가 나온 것이다. javac -g로 컴파일하면 "count"로 표시된다.

    박싱의 비용

    0부터 1억 미만까지 더하는 반복문을 기본형과 래퍼로 한 번씩 써 보자.

    public class SumLoop {
    public static void main(String[] args) {
        int n = 100_000_000;

        long t0 = System.nanoTime();
        long plain = 0;
        for (int i = 0; i < n; i++) {
            plain += i;
        }
        long t1 = System.nanoTime();

        Long boxed = 0L;
        for (int i = 0; i < n; i++) {
            boxed += i;
        }
        long t2 = System.nanoTime();

        System.out.println(plain + " " + boxed);
        System.out.println("기본형: " + (t1 - t0) / 1_000_000 + "ms");
        System.out.println("래퍼:   " + (t2 - t1) / 1_000_000 + "ms");
    }
}

    HotSpot의 JIT 컴파일러가 이런 낭비를 일부 지워 주기도 한다. JDK 21에서 java -XX:+PrintFlagsFinal -version을 실행하면 C2 컴파일러에 EliminateAutoBox라는 플래그가 기본값 true로 있는 것을 볼 수 있다. 다만 어떤 코드에서 박싱이 실제로 제거되는지는 JIT의 분석 결과에 달려 있어 소스만 보고 단정할 수 없고, 다른 JVM에서는 사정이 다를 수 있다. 최적화에 기대는 대신 처음부터 기본형으로 쓰는 편이 확실하다.

    그래서 선택 기준은 이렇게 잡는다. 계산에 쓰는 값, 반복문의 카운터와 누적 변수, 반드시 값이 있어야 하는 필드는 기본형으로 둔다. 래퍼는 두 경우에 쓴다. "값이 없음"을 null로 표현해야 할 때, 그리고 컬렉션이나 제네릭처럼 참조형만 받는 자리에 넣어야 할 때다. 수백, 수천 번 도는 코드에서 박싱 비용은 눈에 띄지 않는다. 유지보수하기 좋은 쪽을 먼저 고르고, 측정해서 병목으로 확인된 곳만 기본형으로 바꾸는 순서가 맞다.

    Class 클래스: 클래스를 설명하는 객체

    여기서부터는 주제가 바뀐다. 지금까지 클래스는 객체를 만들어 내는 틀이었고, 프로그램은 틀에서 나온 객체만 다뤘다. 그런데 실행 중인 프로그램이 틀 자체에 대해 묻고 싶을 때가 있다. 이 객체는 정확히 어느 클래스의 인스턴스인가, 그 클래스에는 어떤 필드와 메서드가 있는가, 설정 파일에 적힌 이름의 클래스로 객체를 만들 수 있는가. 이런 질문에 답하려면 클래스에 관한 정보가 프로그램이 만질 수 있는 형태로 존재해야 한다. 자바에서 그 형태가 java.lang.Class의 인스턴스다.

    Class의 Javadoc 첫 문장은 이 클래스의 인스턴스가 실행 중인 자바 애플리케이션의 클래스와 인터페이스를 나타낸다고 적는다. 이름이 헷갈리기 쉬운데, Class는 "클래스라는 것을 표현하는 클래스"다. String이라는 클래스를 나타내는 Class 객체가 하나 있고, Integer를 나타내는 Class 객체가 하나 있다. Class에는 public 생성자가 없다. Javadoc에 따르면 Class 객체는 JVM이 클래스 파일의 바이트에서 클래스를 만들어 낼 때 자동으로 만든다. 프로그램은 이미 만들어진 것을 얻어 쓸 뿐이다.

    기본편 6회차에서 클래스가 메모리에 올라오는 과정을 로딩, 링크, 초기화로 나눠 보았고, HotSpot에서는 클래스의 구조를 담은 메타데이터가 네이티브 메모리인 메타스페이스에, 그 클래스를 나타내는 Class 객체가 힙에 놓인다는 것도 확인했다. static 필드의 값이 들어 있는 곳도 그 Class 객체였다. 그때 스쳐 지나간 그 객체가 이 절의 주인공이다.

    Class 객체를 얻는 세 가지 방법

    예제로 쓸 클래스를 하나 만든다. 초기화 시점을 눈으로 볼 수 있게 static 초기화 블록에 출력문을 넣었다.

    package lab;

public class Sensor {
    public static int created;

    private final String name;
    private int level;

    static {
        System.out.println("[Sensor 초기화]");
    }

    public Sensor() {
        this("unnamed");
    }

    public Sensor(String name) {
        this.name = name;
        created++;
    }

    public int getLevel() {
        return level;
    }

    private void calibrate(int offset) {
        level += offset;
    }

    @Override
    public String toString() {
        return "Sensor(" + name + ", " + level + ")";
    }
}
    package lab;

public class ThreeWays {
    public static void main(String[] args) throws Exception {
        System.out.println("1. main 시작");

        Class a = Sensor.class;
        System.out.println("2. 클래스 리터럴: " + a.getName());

        Class b = Class.forName("lab.Sensor");
        System.out.println("3. forName 반환");

        Sensor sensor = new Sensor();
        Class c = sensor.getClass();
        System.out.println("4. " + (a == b) + " " + (b == c));
    }

    Class의 꺾쇠는 다음 권에서 다룰 제네릭 문법이다. 지금은 "어떤 클래스의 것이든 상관없는 Class 객체"라고 읽으면 된다. main에 붙은 throws Exception은 이 메서드 안의 호출이 실패할 수 있음을 컴파일러에 알리는 표시이고 9회차에서 다룬다.

    첫째 방법은 클래스 리터럴(class literal, JLS 15.8.2)이다. 타입 이름 뒤에 .class를 붙인다. 이름이 소스에 적혀 있으므로 컴파일러가 그 클래스의 존재를 확인한다. 바이트코드에서는 ldc 명령 하나가 되어 상수 풀의 클래스 항목을 피연산자 스택에 올린다. 출력에서 눈여겨볼 것은 "2." 줄이 "[Sensor 초기화]"보다 먼저 나왔다는 점이다. Sensor.class를 평가해 Class 객체를 얻고 이름까지 물었는데도 static 초기화 블록이 실행되지 않았다. JVMS 5.5는 클래스 초기화를 일으키는 계기를 new, getstatic, putstatic, invokestatic 명령의 실행, 특정 리플렉션 메서드의 호출 등으로 나열하는데, 클래스 리터럴이 컴파일된 ldc는 거기에 없다. 클래스는 로딩되었지만 아직 초기화되지 않은 상태다.

    둘째 방법은 Class.forName(String)이다. 클래스 이름을 문자열로 받는다. 문자열은 실행 중에 정해질 수 있으므로, 컴파일할 때 존재하지 않던 클래스도 이름만 알면 찾을 수 있다. 그 대신 컴파일러가 검사해 줄 수 없어서 이름이 틀리면 실행 중에 ClassNotFoundException이 난다. Javadoc은 forName("X") 호출이 클래스 X를 초기화시킨다고 적는다. 출력에서 "[Sensor 초기화]"가 이 호출 안에서 찍혔다. 초기화 여부를 인자로 고르는 세 인자짜리 forName도 있다.

    셋째 방법은 Object에 선언된 getClass()다. 이미 가지고 있는 인스턴스에서 출발한다. 돌려주는 것은 변수의 선언 타입이 아니라 그 객체의 실제 클래스다. Object o = "hello";일 때 o.getClass().getName()은 java.lang.String이다. 1회차에서 equals를 구현할 때 두 객체의 getClass() 결과를 ==로 비교하던 것이 이 메서드다.

    마지막 줄 "4. true true"는 세 방법이 돌려준 것이 같은 객체임을 보여 준다. equals가 아니라 ==로 비교해도 된다. 정확히 말하면 JVMS 5.3은 실행 중의 클래스가 이름만으로 정해지지 않고 이름과 그 클래스를 정의한 클래스 로더의 쌍으로 정해진다고 규정한다. 같은 클래스 로더 안에서는 이름 하나에 클래스 하나, Class 객체 하나다. 평범한 애플리케이션 코드에서는 이 조건이 늘 성립한다.

    Class 객체로 할 수 있는 일: 조회, 생성, 호출

    Class 객체는 클래스 파일에 적혀 있던 내용을 메서드로 물어볼 수 있게 해 준다. 실행 중에 프로그램이 자기 구조를 들여다보고 조작하는 이런 기능을 리플렉션(reflection)이라고 한다.

import java.lang.reflect.Field;
import java.lang.reflect.Method;
import java.lang.reflect.Modifier;

public class Inspect {
    public static void main(String[] args) throws Exception {
        Class type = Class.forName("lab.Sensor");

        System.out.println(type.getName());
        System.out.println(type.getSimpleName());
        System.out.println(type.getPackageName());
        System.out.println(type.getSuperclass().getName());

        for (Field f : type.getDeclaredFields()) {
            System.out.println("필드: " + Modifier.toString(f.getModifiers())
                    + " " + f.getType().getSimpleName() + " " + f.getName());
        }
        for (Method m : type.getDeclaredMethods()) {
            System.out.println("메서드: " + Modifier.toString(m.getModifiers())
                    + " " + m.getReturnType().getSimpleName() + " " + m.getName());
        }
    }
}

    System 클래스: JVM 바깥과 닿는 창구

    System은 인스턴스를 만들 수 없는 클래스다. 소스의 생성자가 private System() { }이고 모든 멤버가 static이다. 표준 입출력, 시계, 환경 변수와 시스템 속성, 배열 복사, 프로세스 종료처럼 JVM이나 운영체제에 물어봐야 하는 일들이 여기에 모여 있다.

    System.out은 final인데 왜 null이 아닌가

    입문에서부터 써 온 System.out의 선언을 OpenJDK 21 소스에서 보면 조금 이상하다.

    public final class System {
    private System() {
    }

    public static final InputStream in = null;
    public static final PrintStream out = null;
    public static final PrintStream err = null;

    private static native void setOut0(PrintStream out);
    // ...
}

    out은 static final이고 초깃값이 null이다. 기본편에서 배운 대로라면 다시 대입할 수 없으니 System.out.println은 NPE를 내야 한다. 그렇게 되지 않는 것은 JVM이 시작하는 과정에서 System의 초기화 메서드가 setOut0이라는 native 메서드를 호출해 이 필드에 실제 출력 스트림을 넣어 주기 때문이다. native 메서드는 본문이 자바가 아니라 JVM 안의 네이티브 코드로 구현된 메서드다. final은 자바 코드의 대입을 막는 언어 규칙이고, JVM 내부의 네이티브 코드는 그 규칙의 바깥에서 필드를 채울 수 있다. 표준 출력을 다른 곳으로 돌리는 System.setOut(...)도 같은 네이티브 메서드를 거친다. 일반 코드가 흉내 낼 수 있는 방법이 아니라 JDK가 자기 자신에게만 허용한 예외다.

Javadoc이 약속하는 것은 currentTimeMillis()보다 나쁘지 않은 해상도까지다.

    프로그램이 바깥에서 설정값을 받는 통로가 둘 있고, 출처가 다르다. 환경 변수(environment variable)는 운영체제가 프로세스마다 붙여 주는 이름과 값의 목록이다. Javadoc의 표현으로는 부모 프로세스에서 자식 프로세스로 전달되는, 시스템에 따라 달라지는 대응표다. 셸에서 java를 실행하면 JVM 프로세스가 셸의 환경 변수를 물려받고, System.getenv(이름)으로 읽는다. 없는 이름이면 null이다. 인자 없는 System.getenv()가 돌려주는 맵은 수정할 수 없다. 이미 시작한 프로세스가 물려받은 환경을 자바 코드가 바꾸는 길은 열려 있지 않다.

    시스템 속성(system property)은 JVM이 자기 안에 가지고 있는 이름과 값의 표다. java.version, os.name, user.dir처럼 JVM이 시작하면서 채워 넣는 것이 있고, 실행할 때 -D이름=값 옵션으로 추가할 수도 있다. 위 실행에서 -Dapp.mode=dev를 주었으므로 둘째 줄이 dev다. 이 옵션 없이 실행하면 둘째 줄은 null, 기본값을 준 셋째 줄은 local이 된다. 환경 변수는 운영체제 수준의 것이라 자바가 아닌 프로그램도 똑같이 읽고, 시스템 속성은 그 JVM 프로세스 안에서만 보인다.

    arraycopy와 identityHashCode

    System.arraycopy(src, srcPos, dest, destPos, length)는 배열의 한 구간을 다른 배열의 구간으로 복사한다. 다섯째 줄에서 src의 다섯 원소가 dst의 2번 칸부터 들어갔다. 여섯째 줄은 원본과 대상이 같은 배열이고 구간이 겹치는 경우다. 앞에서부터 한 칸씩 옮기는 반복문을 손으로 짜면 1이 계속 번져 [1, 1, 1, 1, 1]이 되겠지만 결과는 [1, 1, 2, 3, 4]다. Javadoc이 이 경우를 "임시 배열에 먼저 복사한 다음 옮긴 것처럼" 동작한다고 규정하기 때문이다.

    이 메서드는 native이고 소스에 @IntrinsicCandidate가 붙어 있다. 이 애너테이션의 설명에 따르면 HotSpot이 해당 메서드를 손으로 짠 어셈블리나 컴파일러 내부 표현으로 바꿔치기할 수 있다는 표시다(보장은 아니다). 원소를 하나씩 대입하는 자바 반복문 대신 메모리 구간을 통째로 옮기는 코드가 쓰일 수 있다는 뜻이다. 3회차에서 StringBuilder가 용량을 늘릴 때 배열을 새로 만들어 옮겨 담는다고 했는데, 그때 쓰이는 Arrays.copyOf의 본문도 새 배열을 만들고 System.arraycopy를 부르는 것이다. 참조형 배열을 복사하면 참조값이 복사될 뿐 객체가 복제되지는 않는다는 점은 대입과 같다.

    System.identityHashCode(객체)는 그 클래스가 hashCode()를 오버라이딩했든 말든 Object의 기본 hashCode()가 돌려줬을 값을 준다. 내용이 같은 두 String은 hashCode()가 같지만(일곱째 줄) 서로 다른 객체이므로 식별 해시코드는 대개 다르다(여덟째 줄). 서로 다른 객체의 값이 우연히 겹치는 것이 금지되어 있지는 않으므로 "다르면 다른 객체"까지만 믿을 수 있다.

    main이 끝까지 실행되어 끝나는 것과 달리 exit은 호출한 스레드뿐 아니라 JVM 전체를 내린다. 종료 절차에서는 미리 등록해 둔 종료 훅(shutdown hook)이 실행되지만, 호출 지점 뒤에 있던 코드는 실행되지 않는다. 10회차에서 배울 finally 블록도 마찬가지로 건너뛴다. 그래서 여러 요청을 처리하는 서버 프로그램 한가운데에서 System.exit을 부르면 진행 중이던 다른 작업까지 함께 끊긴다.

    올림, 내림, 반올림, 그리고 형변환

    ceil은 올림, floor는 내림이고 둘 다 double을 돌려준다. round는 double 인자에 대해 반올림한 long을 돌려준다. 음수에서 차이가 드러난다. ceil(-2.1)은 -2.0이고 floor(-2.1)은 -3.0이다. 올림과 내림은 "양의 무한대 쪽", "음의 무한대 쪽"이라는 방향으로 정의되기 때문이다. round(-2.5)는 -3이 아니라 -2다. Javadoc은 round를 "가장 가까운 정수, 정확히 중간이면 양의 무한대 쪽"으로 정의한다. 정수로의 형변환 (int)는 또 다르다. 소수 부분을 버리므로 0 쪽으로 간다. (int) -2.9는 -2다. 네 가지가 음수에서 모두 다른 방향으로 움직인다는 것을 알아 두면 "소수점 이하를 버렸는데 1이 차이 난다"는 종류의 버그를 빨리 찾는다.

    넘침은 조용히 일어난다

    Integer.MAX_VALUE + 1이 예외 없이 -2147483648이 되었다. 자바의 int 덧셈은 결과가 32비트를 넘으면 넘친 부분을 버리고 하위 32비트만 남긴다. 2의 보수 표현에서 가장 큰 양수 다음 비트 패턴이 가장 작은 음수이므로 이런 결과가 된다. 오류 신호가 전혀 없다는 것이 문제다. 넘침을 예외로 받고 싶으면 Math.addExact, subtractExact, multiplyExact를 쓴다. 마지막 줄처럼 ArithmeticException: integer overflow를 던진다.

    Math.abs(Integer.MIN_VALUE)가 음수인 것도 같은 뿌리다. int의 범위는 -2147483648부터 2147483647까지로 음수 쪽이 하나 더 많다. 2147483648은 int로 표현할 수 없으므로 최솟값의 부호를 뒤집으면 넘쳐서 자기 자신으로 돌아온다. Math.abs의 Javadoc에 이 경우 결과가 음수인 그 값 그대로라고 적혀 있다.

    이것이 실제 버그가 되는 자리가 있다. 해시코드로 배열의 칸 번호를 정하려고 Math.abs(hashCode) % 칸수라고 쓰는 코드다. 문자열 "polygenelubricants"의 해시코드는 마침 Integer.MIN_VALUE다. 절댓값을 취해도 음수이고, 자바의 %는 결과의 부호가 왼쪽 피연산자를 따르므로 10으로 나눈 나머지가 -8이 된다. 배열 인덱스로 쓰면 예외다. Math.floorMod는 결과의 부호가 오른쪽 피연산자를 따르므로 칸수가 양수이면 항상 0 이상의 값을 준다. 같은 입력에 2가 나왔다. -7 % 2가 -1이고 floorMod(-7, 2)가 1인 것도 같은 차이다.

    nextInt(10)은 0 이상 10 미만의 정수를 돌려준다. 상한은 포함되지 않으므로 1부터 6까지의 주사위는 nextInt(6) + 1이다. Math.random()은 0.0 이상 1.0 미만의 double을 돌려주는데, Javadoc에 따르면 처음 호출될 때 new java.util.Random()으로 생성기를 하나 만들어 두고 이후의 모든 호출에 그것을 쓴다.

    눈여겨볼 것은 첫 두 줄이 똑같다는 점이다. 우연이 아니다. Random의 Javadoc은 같은 시드(seed)로 만든 두 인스턴스에 같은 순서로 메서드를 호출하면 동일한 수열을 돌려준다고 보장하고, 이를 위해 알고리즘 자체를 문서에 명시해 모든 자바 구현이 그 알고리즘을 쓰도록 요구한다. 그래서 시드 42의 nextInt(10) 다섯 번은 어느 기계, 어느 JDK에서나 0 3 8 4 0이다. "난수"라고 부르지만 실제로는 시드에서 출발하는 정해진 계산의 결과이고, 정확한 이름은 의사 난수(pseudorandom number)다.

    그 계산이 무엇인지 Javadoc에 적힌 대로 직접 구현해 보면 분명해진다. Random은 48비트짜리 상태(시드)를 가지고, 수가 필요할 때마다 상태에 상수를 곱하고 더한 뒤 하위 48비트만 남긴다. 이런 방식을 선형 합동 생성기(linear congruential generator)라고 한다.

    import java.util.Random;

public class MyLcg {
    private static final long MULTIPLIER = 0x5DEECE66DL;
    private static final long ADDEND = 0xBL;
    private static final long MASK = (1L << 48) - 1;

    private long seed;

    MyLcg(long seed) {
        this.seed = (seed ^ MULTIPLIER) & MASK;
    }

    int next(int bits) {
        seed = (seed * MULTIPLIER + ADDEND) & MASK;
        return (int) (seed >>> (48 - bits));
    }

    public static void main(String[] args) {
        MyLcg mine = new MyLcg(42);
        Random jdk = new Random(42);
        for (int i = 0; i < 3; i++) {
            int a = mine.next(32);
            int b = jdk.nextInt();
            System.out.println(a + " " + b + " " + (a == b));
        }
    }
}

    0x5DEECE66D는 십진수로 25214903917이고 0xB는 11이다. & MASK는 하위 48비트만 남기는 연산이어서 248으로 나눈 나머지를 구하는 것과 같다. >>> (48 - bits)는 아래쪽 비트를 밀어서 버리고 위쪽 bits개만 남긴다. 생성자에서 시드를 곱수와 XOR해 하위 48비트만 남기는 것도 setSeed의 Javadoc에 적혀 있는 처리다. 상태가 48비트이므로 수열은 길어야 248개 뒤에 처음으로 돌아온다. Javadoc도 주기가 248에 불과하다고 적는다.

    시드를 주지 않는 new Random()은 어떻게 매번 다른 수열을 낼까. Javadoc은 다른 어떤 호출과도 겹치지 않을 가능성이 매우 높은 값으로 시드를 정한다고만 약속한다. OpenJDK 21의 구현은 호출할 때마다 달라지는 내부 값과 System.nanoTime()을 XOR해서 시드로 쓴다. 수열을 만드는 계산은 똑같고 출발점만 달라지는 것이다. nextInt(bound)는 bound가 2의 거듭제곱이면 이 계산으로 얻은 값의 상위 비트를 그대로 쓰고, 아니면 31비트 값을 bound로 나눈 나머지를 쓰되 231이 bound로 나누어떨어지지 않아 일부 값이 더 자주 나오게 되는 구간에 걸리면 버리고 다시 뽑는다고 Javadoc에 설명되어 있다.

    시드에서 출발한 48비트 상태가 같은 식으로 반복 갱신되고, 매번 상위 비트가 난수로 꺼내진다는 것, 같은 시드면 같은 수열이 된다는 것을 보여 준다. 깔끔한 평면 기술 다이어그램. 왼쪽 끝에 둥근 상자 "시드 42". 거기서 오른쪽으로 화살표가 나가 가로로 나란한 세 개의 직사각형 "상태 s1", "상태 s2", "상태 s3"로 차례로 이어진다. 상자와 상자 사이의 화살표마다 같은 라벨 "× 25214903917 + 11, 하위 48비트만". 각 상태 상자에서 아래로 짧은 화살표가 내려가 작은 상자에 닿고, 화살표 옆 라벨은 "상위 32비트". 작은 상자 세 개에는 차례로 "-1170105035", "234785527", "-1360544799"가 적혀 있다. 그림 맨 아래에 한 줄 글씨 "같은 시드에서 출발하면 언제나 같은 수열". 흰 배경, 얇은 선, 파랑과 주황 두 색. Random의 수열은 시드에서 출발해 같은 식을 되풀이한 결과다. 시드가 같으면 수열도 같다.

    이 구조에서 실무적인 결론이 세 가지 나온다. 첫째, 재현이 필요한 테스트나 시뮬레이션에서는 시드를 고정하면 매번 같은 "무작위" 입력을 얻는다. 둘째, Random의 Javadoc은 이 클래스가 암호학적으로 안전하지 않다고 밝히고 보안에 민감한 용도에는 java.security.SecureRandom을 쓰라고 한다. 인증 토큰이나 임시 비밀번호처럼 남이 맞히면 안 되는 값에 Random을 쓰면 안 된다. 셋째, Random 인스턴스는 스레드 안전하지만 여러 스레드가 한 인스턴스를 함께 쓰면 경합 때문에 성능이 나빠질 수 있으니 ThreadLocalRandom을 고려하라고 Javadoc이 안내한다. OpenJDK 21의 next는 상태를 AtomicLong에 두고 갱신에 성공할 때까지 되풀이하는 방식으로 구현되어 있는데, 이것이 무엇인지는 동시성을 다루는 권에서 본다.

    흔한 오해, 그리고 다른 주제와의 연결

    흔한 오해와 함정

    • "Integer끼리도 ==로 비교되더라." 캐시 범위 안의 작은 수로만 시험했기 때문이다. 두 래퍼의 ==는 참조 비교이고, 명세가 같은 객체를 보장하는 것은 상수식으로 박싱한 -128~127뿐이다. 값 비교는 equals로 한다.
    • "오토 박싱은 JVM이 해 주는 변환이다." 컴파일러가 valueOf와 xxxValue 호출을 써 넣는 것이다. 클래스 파일에는 평범한 메서드 호출만 남는다. 그래서 박싱은 객체 생성이 될 수 있고, 언박싱은 null에 대한 메서드 호출이 될 수 있다.
    • "Integer와 int는 쓰는 법이 같으니 같은 것이다." 메모리에서는 값 4바이트와 "참조 + 16바이트 객체"의 차이이고(HotSpot 기본 설정), 의미에서는 null이 있고 없고의 차이다. Long.equals(1)이 false인 것처럼 타입 규칙에서도 다르게 움직인다.
    • "Sensor.class와 Class.forName은 같은 일을 한다." 돌려주는 객체는 같지만 클래스 리터럴은 초기화를 일으키지 않고 forName(String)은 일으킨다. static 초기화 블록에 부수 효과가 있는 클래스에서는 이 차이가 실행 순서를 바꾼다.
    • "nanoTime은 현재 시각을 나노초로 준다." 원점이 정해져 있지 않은 값이다. 두 값의 차이만 의미가 있다. 시각을 기록하려면 currentTimeMillis()나 6회차에서 다룰 java.time을 쓴다.
    • "Random이 내는 수는 예측할 수 없다." 시드와 호출 순서가 같으면 수열이 같다. 예측 불가능성이 필요하면 SecureRandom이다.

    어디서 다시 만나는가

    다음 권에서 다룰 제네릭과 컬렉션은 참조형만 다룬다. 정수 목록을 담는 리스트의 원소는 int가 아니라 Integer이고, 넣고 꺼낼 때마다 이 회차에서 본 박싱과 언박싱이 일어난다. 컬렉션에 든 값을 ==로 비교하는 실수, null이 든 원소를 기본형 변수에 받다가 나는 NPE가 전부 여기서 설명한 원리 그대로다.

    데이터베이스를 다루는 권에서는 엔티티의 식별자를 long이 아니라 Long으로 선언하는 코드를 자주 보게 된다. 아직 저장되지 않아 식별자가 없는 상태를 0이 아니라 null로 나타내려는 것이다. 값이 없을 수 있는 컬럼을 기본형 필드에 대응시키면 "없음"이 0으로 뭉개진다는 판단도 같은 맥락이다.

    Class 객체와 리플렉션은 스프링과 JPA의 바닥에 깔려 있다. 프레임워크는 우리가 만든 클래스를 컴파일 시점에 알지 못한다. 클래스 이름이나 Class 객체에서 출발해 생성자를 찾아 객체를 만들고, 필드와 메서드를 조회해 값을 넣고 호출한다. 이 회차의 Create 예제가 그 일의 가장 작은 모형이다. 애너테이션을 읽는 것도 Class, Field, Method 객체를 통해서다.

    동시성을 다루는 권과도 접점이 있다. Object.getClass()의 Javadoc은 이 메서드가 돌려주는 Class 객체가 그 클래스의 static synchronized 메서드가 잠그는 객체라고 적는다. 클래스마다 Class 객체가 하나뿐이라는 사실이 거기서 다시 쓰인다. 다음 회차의 열거형도 연결된다. enum 상수는 enum 클래스가 초기화될 때 만들어지는 객체이고, 그 초기화가 언제 일어나는지는 이 회차에서 본 규칙을 따른다.

    이 장의 핵심

    래퍼 클래스는 기본형 값을 객체의 세계로 들여보내는 통로다. 오토 박싱은 그 통로를 드나드는 코드를 컴파일러가 대신 써 주는 것일 뿐이어서, 객체 생성과 참조 비교와 null이라는 객체의 성질이 그대로 따라온다. Class는 클래스 자체를 객체로 꺼내 놓은 것이고, System·Math·Random은 시계와 환경과 계산을 static 메서드로 꺼내 놓은 것이다. 겉으로 간단해 보이는 한 줄이 실제로 무엇을 호출하는지 아는 것이 이 회차의 목표다.
    래퍼 클래스
    기본형 값 하나를 private final 필드로 품은 불변 객체. 기본형이 가질 수 없는 메서드, Object 자리에 들어갈 자격, null을 얻는 대신 힙 객체 하나와 참조 한 번의 비용을 치른다.
    박싱과 언박싱
    박싱은 Integer.valueOf(int), 언박싱은 intValue()다. 오토 박싱은 javac가 이 호출을 써 넣는 것이고, 클래스 파일에는 invokestatic과 invokevirtual만 남는다.
    언박싱 NPE
    래퍼 참조가 null인데 기본형 자리로 들어가면 null.intValue()가 되어 NullPointerException이 난다. 조건 연산자가 식의 타입을 기본형으로 정하는 경우처럼 소스에서 보이지 않는 자리에서도 일어난다.
    Integer 캐시
    valueOf는 -128~127 범위의 값에 대해 미리 준비된 객체를 돌려준다. 그 밖의 값은 새 객체일 수 있으므로 래퍼끼리의 == 결과는 값과 JVM 옵션에 따라 달라진다. 값 비교는 equals로 한다.
    기본형과 래퍼의 선택
    계산과 반복, 반드시 값이 있어야 하는 필드는 기본형. "값 없음"을 표현해야 하거나 참조형만 받는 자리에는 래퍼.
    Class 객체
    로딩된 클래스 하나를 나타내는 java.lang.Class의 인스턴스. 같은 클래스 로더 안에서 클래스마다 하나이고, 클래스 리터럴·Class.forName·getClass()로 얻는다. 클래스 리터럴은 초기화를 일으키지 않고 forName(String)은 일으킨다.
    리플렉션
    Class 객체에서 필드·메서드·생성자를 조회하고, 이름만으로 객체를 만들고 메서드를 호출하는 기능. 컴파일러의 검사를 잃고 오류가 실행 시점으로 밀린다.
    System의 시계와 설정
    currentTimeMillis()는 벽시계 시각, nanoTime()은 경과 시간 측정용. 환경 변수는 운영체제가 프로세스에 물려준 것, 시스템 속성은 JVM 안의 표(-D 옵션)다.
    Math와 Random
    정수 연산의 넘침은 예외 없이 일어나며 Math.abs(Integer.MIN_VALUE)는 음수다. Random은 48비트 상태를 선형 합동식으로 갱신하는 의사 난수 생성기여서 시드가 같으면 수열이 같다.

    실무에서 다시 판단하면, 래퍼와 관련된 장애는 대부분 두 문장으로 요약된다. "테스트에서는 됐는데 운영에서 틀린다"와 "아무것도 호출하지 않는 줄에서 NPE가 난다"이다. 앞의 것은 식별자나 수량을 Long, Integer로 들고 다니다가 ==로 비교한 코드에서 나온다. 테스트 데이터의 식별자는 1, 2, 3이어서 캐시 범위 안이고, 운영 데이터는 128을 넘는다. 코드 리뷰에서 래퍼 타입 두 개 사이의 ==를 보면 값의 크기와 상관없이 고치는 것이 맞다. 뒤의 것은 값이 없을 수 있는 컬럼이나 응답 필드를 래퍼로 받아 놓고 산술식이나 조건식에 바로 넣은 코드에서 나온다. 스택 트레이스의 줄에 래퍼가 기본형 자리로 들어가는 곳이 있는지 보면 원인이 바로 잡힌다.

    필드 타입을 정할 때는 성능보다 의미를 먼저 묻는다. 외부에서 들어온 데이터를 객체에 채우는 과정에서 값이 오지 않았을 때 기본형 필드는 0이나 false로 남고, "0을 보냈다"와 구분할 수 없게 된다. 그 구분이 업무상 필요하면 래퍼가 맞고, 그러면 null을 처리할 책임이 따라온다. 반대로 반드시 값이 있어야 하는 필드를 래퍼로 두면 있을 수 없는 null 상태를 타입이 허용하게 된다. 박싱 비용은 수백만 건을 도는 집계나 큰 배열에서나 따질 문제이고, 그런 곳은 측정으로 확인한 뒤 기본형 배열이나 기본형 누적 변수로 바꾼다.

    리플렉션은 직접 쓸 일보다 읽을 일이 많다. 프레임워크가 던지는 ClassNotFoundException이나 NoSuchMethodException, "기본 생성자가 없다"는 종류의 오류 메시지는 이 회차의 Create 예제에서 본 실패와 같은 것이다. 설정에 적은 클래스 이름의 오타, 프레임워크가 요구하는 생성자의 누락을 의심하면 된다. 애플리케이션 코드에서 타입을 이미 아는데도 리플렉션으로 필드를 건드리는 것은 컴파일러의 보호를 스스로 버리는 일이므로 다른 방법이 없을 때로 한정한다.

    시간과 난수에서는 용도에 맞는 도구를 고르는 것이 전부다. 타임아웃이나 처리 시간 측정에 currentTimeMillis()의 차이를 쓰면 서버 시계가 조정되는 순간 잘못된 값이 나오므로 nanoTime()의 차이를 쓴다. 로그에 남길 시각은 반대로 벽시계가 맞다. 세션 식별자, 비밀번호 재설정 토큰처럼 추측당하면 안 되는 값은 SecureRandom으로 만들고, 재현해야 하는 테스트 데이터는 시드를 고정한 Random으로 만든다. 서버 코드에서 System.exit은 프로세스 전체를 내리는 결정이므로 시작 단계의 치명적 설정 오류 같은 경우로만 쓴다.

    5번. key.hashCode()가 Integer.MIN_VALUE인 키가 들어오면 실패한다.      Integer a = 128, b = 128;일 때 기본 옵션의 JVM에서 a == b가 false이고, Integer a = 127, b = 127;이면 true인 이유로 가장 정확한 것은? 127까지는 int로 저장되고 128부터 객체로 저장되기 때문이다 컴파일러가 써 넣는 Integer.valueOf가 -128~127 범위에서는 캐시의 기존 객체를, 그 밖에서는 새 객체를 돌려주고 ==는 참조를 비교하기 때문이다 ==가 127 이하에서는 값을, 128 이상에서는 참조를 비교하도록 정의되어 있기 때문이다 128은 byte 범위를 넘어 Integer가 아니라 Long으로 박싱되기 때문이다 두 경우 모두 변수에는 Integer 객체의 참조가 들어 있고 ==는 언제나 참조를 비교한다. 차이는 valueOf가 돌려주는 객체에 있다. 캐시 범위 안이면 같은 객체, 밖이면 호출마다 다른 객체다. 0번처럼 저장 방식이 값에 따라 바뀌지 않고, 2번처럼 연산자의 의미가 값에 따라 바뀌지도 않는다. int 리터럴 128은 Integer로 박싱되며 Long이 되는 일은 없다. Integer count = null; int n = count;를 실행하면 NullPointerException이 난다. 예외가 나는 직접적인 원인은? int 변수에는 null을 저장할 수 없다는 것을 JVM이 대입 명령에서 검사하기 때문이다 null이 0으로 변환되는 과정에서 넘침이 일어나기 때문이다 컴파일러가 언박싱을 위해 써 넣은 count.intValue() 호출이 null 참조에 대한 메서드 호출이 되기 때문이다 Integer 캐시에 null에 해당하는 칸이 없기 때문이다 오토 언박싱은 intValue() 호출로 컴파일된다. 참조가 null이면 그 호출에서 NPE가 나고, 예외 메시지에도 Cannot invoke "java.lang.Integer.intValue()"라고 나온다. JVM에 "int에 null을 넣는지" 검사하는 명령은 따로 없고, null이 0으로 바뀌는 변환도 없다. 캐시는 valueOf, 곧 박싱 쪽의 이야기라 언박싱과 무관하다. lab.Sensor가 아직 초기화되지 않은 상태에서 다음 가운데 Sensor의 static 초기화 블록을 실행시키지 않는 것은? Class c = Sensor.class; Class c = Class.forName("lab.Sensor"); Sensor s = new Sensor(); Sensor.created++; 클래스 리터럴은 ldc 명령으로 컴파일되어 Class 객체를 얻을 뿐이고, JVMS 5.5가 나열하는 초기화 계기에 들지 않는다. Class.forName(String)은 Javadoc에 적힌 대로 클래스를 초기화시킨다. new는 인스턴스 생성, created++는 상수가 아닌 static 필드를 읽고 쓰는 것이어서 둘 다 초기화를 일으킨다. 어떤 작업에 걸린 시간을 재려고 한다. 다음 가운데 올바른 방법과 이유를 고르면? currentTimeMillis()를 두 번 읽어 뺀다. 밀리초 단위가 나노초보다 안정적이기 때문이다 nanoTime()을 한 번 읽는다. 값 자체가 프로그램 시작 이후의 경과 시간이기 때문이다 currentTimeMillis()를 두 번 읽어 뺀다. 벽시계는 조정되지 않기 때문이다 nanoTime()을 두 번 읽어 뺀다. 이 값은 벽시계와 무관하고 두 값의 차이만 의미가 있기 때문이다 nanoTime()은 임의의 원점에서 흐른 나노초이므로 값 하나로는 의미가 없고 같은 JVM에서 얻은 두 값의 차이가 경과 시간이다. 원점이 프로그램 시작이라는 보장은 없으므로 1번은 틀렸다. currentTimeMillis()가 읽는 벽시계는 사람이나 시간 동기화에 의해 앞뒤로 조정될 수 있어서 차이를 경과 시간으로 쓰면 안 된다. new Random(42)로 만든 두 인스턴스에 nextInt(10)을 다섯 번씩 호출했더니 두 수열이 똑같았다. 이 현상에 대한 설명으로 옳은 것은? 두 인스턴스가 만들어진 시각이 거의 같아서 생긴 우연이며, 다시 실행하면 달라질 수 있다 Random은 시드로 정해진 상태에서 출발해 정해진 식으로 다음 상태와 출력을 계산하므로, 시드와 호출 순서가 같으면 수열이 같도록 Javadoc이 보장한다 JVM이 같은 시드의 인스턴스를 캐시에서 꺼내 같은 객체를 돌려주었기 때문이다 nextInt(10)의 결과가 10가지뿐이어서 다섯 번 정도는 겹치기 쉽기 때문이다 Random은 48비트 상태를 선형 합동식으로 갱신하는 의사 난수 생성기이고, 알고리즘이 Javadoc에 명시되어 있어 같은 시드에서는 어느 구현에서나 같은 수열이 나온다. 시각이 관여하는 것은 시드를 주지 않은 new Random()의 시드 결정뿐이다. new로 만든 두 인스턴스는 서로 다른 객체이며 Integer 같은 캐시가 없다. 다섯 개가 모두 우연히 같을 확률은 낮고, 여기서는 확률의 문제가 아니라 결정적인 계산의 결과다.
    래퍼 클래스(wrapper class)
    기본형 값을 감싸 객체로 다룰 수 있게 한 클래스. Integer, Long, Double, Boolean, Character 등 여덟 개가 java.lang에 있다.
    박싱(boxing) / 언박싱(unboxing)
    기본형 값을 대응하는 래퍼 객체의 참조로 바꾸는 변환과 그 반대 변환. JLS 5.1.7과 5.1.8에 정의되어 있다.
    오토 박싱(autoboxing)
    박싱·언박싱 변환을 컴파일러가 필요한 자리에 자동으로 적용하는 것. javac는 valueOf와 xxxValue 호출을 써 넣는다.
    Integer 캐시(IntegerCache)
    Integer.valueOf가 -128~127 범위의 값에 대해 돌려주는, 미리 준비된 Integer 객체들의 배열. HotSpot에서는 -XX:AutoBoxCacheMax로 상한을 올릴 수 있다.
    값 기반 클래스(value-based class)
    동등한 인스턴스를 서로 바꿔 써도 되는 것으로 다뤄야 하고, 동일성 비교나 동기화에 써서는 안 된다고 Javadoc이 지정한 클래스. 래퍼 클래스가 여기에 든다.
    Class 객체(Class object)
    로딩된 클래스·인터페이스 하나를 나타내는 java.lang.Class의 인스턴스. JVM이 클래스를 만들 때 함께 만들며, 기본형·배열·void에도 있다.
    클래스 리터럴(class literal)
    Sensor.class, int.class처럼 타입 이름 뒤에 .class를 붙여 그 타입의 Class 객체를 얻는 식(JLS 15.8.2). 클래스 초기화를 일으키지 않는다.
    리플렉션(reflection)
    실행 중에 Class, Field, Method, Constructor 객체를 통해 클래스의 구조를 조회하고 객체 생성·메서드 호출·필드 접근을 수행하는 기능.
    시스템 속성(system property) / 환경 변수(environment variable)
    시스템 속성은 JVM이 가진 이름-값 표로 -D 옵션이나 JVM이 채운다. 환경 변수는 운영체제가 프로세스에 물려주는 이름-값 목록이다.
    시드(seed) / 선형 합동 생성기(linear congruential generator)
    시드는 의사 난수 생성기의 처음 상태. 선형 합동 생성기는 상태에 상수를 곱하고 더한 뒤 나머지를 취해 다음 상태를 만드는 방식이며 java.util.Random이 이 방식을 쓴다.
