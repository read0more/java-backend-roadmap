    이 회차의 질문: "지금 몇 시인가"에는 답이 몇 개인가

    서울 사무실의 벽시계가 2024년 1월 1일 오전 9시를 가리키는 순간, 뉴욕 사무실의 벽시계는 2023년 12월 31일 오후 7시를 가리킨다. 두 시계가 보여 주는 숫자는 다르지만 가리키는 순간은 하나다. 반대의 경우도 있다. "1월 1일 오전 9시에 문을 엽니다"라는 안내문은 서울 지점과 뉴욕 지점에 똑같은 글자로 붙어 있지만, 두 지점이 실제로 문을 여는 순간은 14시간 떨어져 있다. 같은 순간이 다른 숫자로 보이기도 하고, 같은 숫자가 다른 순간을 뜻하기도 한다.

    프로그램이 "시간"이라고 부르는 것에는 성격이 다른 세 가지가 섞여 있다. 이 셋을 구분하는 것이 이 회차 전체의 뼈대다.

    • 시점(instant): 시간선(time-line) 위의 한 점이다. 결제가 승인된 순간, 로그가 찍힌 순간처럼 전 세계 어디에서 보아도 같은 하나의 순간을 뜻한다.
    • 지역 날짜·시각(local date-time): 어떤 지역의 달력과 벽시계가 보여 주는 값이다. "2024년 1월 1일 오전 9시"라는 값만으로는 어느 지역의 벽시계인지 알 수 없으므로 시점이 정해지지 않는다.
    • 시간의 양(amount of time): "90분", "한 달"처럼 길이를 나타낸다. 시간선 위의 어느 위치와도 묶여 있지 않다.

    날짜와 시간에서 생기는 버그는 대개 이 셋을 한 그릇에 담으면서 시작된다. 밀리초를 담은 long 하나, 혹은 "2024-01-01 09:00:00" 같은 문자열 하나로 모든 것을 표현하면, 그 값이 시점인지 지역 시각인지는 코드를 쓴 사람의 머릿속에만 남는다. 서버를 다른 시간대로 옮기거나 다른 나라 사용자가 생기는 날, 머릿속에만 있던 가정이 깨진다. 자바의 java.time 패키지는 이 구분을 타입으로 옮겨 놓았고, 이 회차는 각 타입이 무엇을 표현하며 메모리에 무엇을 들고 있는지를 따라간다.

    직접 계산하면 안 되는 이유

    "하루는 86,400초이니 밀리초에 86,400,000을 더하면 내일"이라는 식의 계산은 다음 다섯 가지 사실 때문에 틀린다.

    첫째, 달력이 규칙적이지 않다. 한 달은 28일에서 31일 사이이고, 2월의 길이는 윤년(leap year)에 따라 달라진다. 윤년 규칙도 "4년마다"가 전부가 아니다. OpenJDK 21의 IsoChronology.isLeapYear는 이 규칙을 한 줄로 적어 두었다.

    // java.time.chrono.IsoChronology (OpenJDK 21)
public boolean isLeapYear(long prolepticYear) {
    return ((prolepticYear & 3) == 0) && ((prolepticYear % 100) != 0 || (prolepticYear % 400) == 0);
}

    4로 나누어떨어지되, 100으로 나누어떨어지면 평년이고, 그중 400으로 나누어떨어지면 다시 윤년이다. 그래서 2024년과 2000년은 윤년이고 1900년과 2100년은 평년이다. prolepticYear & 3은 하위 두 비트가 0인지, 곧 4의 배수인지를 보는 비트 연산이다.

    둘째, 벽시계는 지역마다 다르다. 기준이 되는 시각을 협정 세계시(UTC, Coordinated Universal Time)라 하고, 각 지역의 벽시계가 UTC보다 얼마나 앞서거나 뒤처지는지를 오프셋(offset)이라고 한다. 한국의 현재 오프셋은 +09:00이다.

    셋째, 한 지역의 오프셋도 고정이 아니다. 일광 절약 시간(DST, Daylight Saving Time)을 쓰는 지역은 봄에 벽시계를 한 시간 앞으로 돌리고 가을에 한 시간 뒤로 돌린다. 그날 하루는 23시간이거나 25시간이고, 벽시계에 존재하지 않는 시각과 두 번 나타나는 시각이 생긴다.

    넷째, 그 규칙을 정하는 것은 물리 법칙이 아니라 각 나라의 법이다. 법이 바뀌면 오프셋의 역사도 바뀐다. 한국도 예외가 아니었다는 것을 JDK에 들어 있는 시간대 데이터로 확인할 수 있다.

    import java.time.Instant;
import java.time.ZoneId;
import java.time.zone.ZoneRules;

public class SeoulOffsetHistory {
    public static void main(String[] args) {
        ZoneRules rules = ZoneId.of("Asia/Seoul").getRules();
        String[] instants = {
            "1900-01-01T00:00:00Z", "1960-01-01T00:00:00Z",
            "1988-07-01T00:00:00Z", "2024-01-01T00:00:00Z"
        };
        for (String text : instants) {
            Instant instant = Instant.parse(text);
            System.out.println(text + " -> " + rules.getOffset(instant));
        }
    }
}
    1900-01-01T00:00:00Z -> +08:27:52
1960-01-01T00:00:00Z -> +08:30
1988-07-01T00:00:00Z -> +10:00
2024-01-01T00:00:00Z -> +09:00

    이 결과는 JDK가 싣고 있는 시간대 데이터에서 나온다(이 원고의 실행 환경은 Temurin 21.0.13이고 시간대 데이터 버전은 2026e다). 같은 Asia/Seoul인데 시점에 따라 오프셋이 네 가지로 나왔다. 분·초까지 붙은 +08:27:52 같은 값도 있고, 1988년 여름에는 +10:00이다. 이 시기에 대해 ZoneRules.isDaylightSavings를 호출하면 true가 나온다. "한국은 UTC+9"라는 지식을 상수 9로 코드에 박아 넣으면 과거 데이터를 다룰 때 틀린다는 뜻이다.

    다섯째, UTC 자체에도 윤초(leap second)가 있다. 지구 자전 속도가 일정하지 않아서 UTC는 필요할 때 하루를 86,401초나 86,399초로 만들 수 있다. 자바가 이것을 어떻게 다루는지는 Instant를 볼 때 다시 나온다.

    일상에서 가져온 비유한 번 울리는 종과 도시마다 다른 벽시계

    지구 전체에 동시에 들리는 종이 한 번 울린다고 하자. 종이 울린 순간이 시점이고, 그 순간 각 도시의 벽시계가 보여 주는 숫자가 지역 날짜·시각이다. 종소리에서 벽시계 숫자로 가는 방향은 도시마다 답이 정확히 하나다. 비유가 깨지는 곳은 반대 방향이다. 벽시계 숫자에서 종소리로 거슬러 올라가려면 어느 도시의 시계인지 알아야 하고, 알더라도 일광 절약 시간 전환일에는 해당하는 종소리가 없거나 두 번일 수 있다.

    Date와 Calendar가 남긴 문제

    자바에는 처음부터 날짜 타입이 있었다. JDK 1.0의 java.util.Date와 JDK 1.1에서 추가된 java.util.Calendar다. 지금도 오래된 코드와 라이브러리에서 만나게 되므로, 이들이 무엇을 잘못 섞었는지 실행 결과로 확인해 두자.

    import java.util.Calendar;
import java.util.Date;
import java.util.TimeZone;

public class LegacyDateMain {
    @SuppressWarnings("deprecation")
    public static void main(String[] args) {
        TimeZone.setDefault(TimeZone.getTimeZone("Asia/Seoul"));

        Date epoch = new Date(0L);
        System.out.println(epoch);                 // (1)

        Date wrong = new Date(2024, 1, 31);
        System.out.println(wrong);                 // (2)

        Calendar cal = Calendar.getInstance();
        cal.clear();
        cal.set(2024, 1, 31);
        System.out.println(cal.getTime());         // (3)

        Date shared = epoch;
        shared.setTime(86_400_000L);
        System.out.println(epoch);                 // (4)
    }
}
    Thu Jan 01 09:00:00 KST 1970
Sun Mar 02 00:00:00 KST 3924
Sat Mar 02 00:00:00 KST 2024
Fri Jan 02 09:00:00 KST 1970

    (1) Date의 핵심 필드는 long 하나(fastTime)이고, 여기에 1970년 1월 1일 0시(UTC)부터 지난 밀리초가 들어 있다. 이름은 Date(날짜)지만 실체는 시점이다. 그런데 toString()은 그 시점을 JVM의 기본 시간대로 바꿔서 출력한다. 0을 넣었는데 9시가 나오는 이유다. 같은 객체를 기본 시간대가 다른 서버에서 출력하면 다른 문자열이 나오므로, 출력만 보고 "지역 시각을 담는 객체"라고 오해하기 쉽다.

    (2) 연·월·일을 받는 생성자는 연도에서 1900을 뺀 값과 0부터 시작하는 월을 받는다. new Date(2024, 1, 31)은 3924년 2월 31일을 뜻하고, 2월 31일은 없으므로 3월로 넘어갔다. 이 생성자에는 JDK 1.1에서 이미 사용 중단(deprecated) 표시가 붙었다.

    (3) 대체품으로 나온 Calendar도 월은 여전히 0부터 센다(Calendar.JANUARY의 값이 0이다). set(2024, 1, 31)은 2월 31일이라는 없는 날짜인데, 예외 없이 3월 2일로 바뀌었다. 2024년은 윤년이라 2월이 29일까지이고, 31일은 거기서 이틀을 넘긴 날이기 때문이다. 잘못된 입력이 조용히 다른 날짜가 된다.

    (4) Date는 가변(mutable) 객체다. shared와 epoch는 같은 객체를 가리키므로 한쪽에서 setTime을 부르면 다른 쪽 값도 바뀐다. 02회에서 본 공유 참조의 부작용이 그대로 나타난다. 날짜 객체는 필드에 보관하거나 메서드 인자로 넘기는 일이 잦아서, 방어적 복사를 빠뜨리면 엉뚱한 곳에서 값이 바뀐다.

    여기에 문자열 변환을 맡는 SimpleDateFormat의 문제가 더해진다. 이 클래스의 Javadoc은 "Date formats are not synchronized."라고 적고, 스레드마다 별도 인스턴스를 만들라고 권한다. 여러 스레드가 인스턴스 하나를 동시에 쓰는 것을 클래스가 보호해 주지 않는다는 뜻이다. 정리하면 옛 API의 문제는 네 가지다. 시점과 지역 시각을 타입으로 구분하지 않았고, 객체가 가변이며, 숫자 체계가 직관과 어긋나고(1900 기준 연도, 0 기준 월), 포맷터가 스레드 안전하지 않다.

    java.time의 설계 원칙과 타입 지도

    Java 8은 java.time 패키지를 새로 넣었다(JSR 310). 옛 API를 고친 것이 아니라 처음부터 다시 설계한 것이고, 설계 원칙은 앞 절의 네 가지 문제를 하나씩 뒤집은 것으로 읽으면 된다.

    원칙 1. 개념마다 타입을 나눈다

    시점, 지역 날짜·시각, 시간의 양이 서로 다른 타입이다. 아래 표의 "내부 필드"는 OpenJDK 21 소스에서 확인한 인스턴스 필드다. 각 타입이 무엇을 들고 있는지 보면 그 타입이 무엇을 표현할 수 있고 무엇을 표현할 수 없는지가 드러난다.

    타입표현하는 것내부 필드(OpenJDK 21)toString 예
    LocalDate시간대 없는 날짜int year, short month, short day2024-01-31
    LocalTime시간대 없는 시각byte hour, byte minute, byte second, int nano09:00
    LocalDateTime시간대 없는 날짜와 시각LocalDate date, LocalTime time2024-01-31T09:00
    ZonedDateTime날짜·시각과 시간대(시점이 정해진다)LocalDateTime dateTime, ZoneOffset offset, ZoneId zone2024-01-01T09:00+09:00[Asia/Seoul]
    OffsetDateTime날짜·시각과 오프셋(시점이 정해진다)LocalDateTime dateTime, ZoneOffset offset2024-01-01T09:00+09:00
    Instant시간선 위의 시점long seconds, int nanos2024-01-01T00:00:00Z

    이 밖에 연도만 담는 Year, 연·월을 담는 YearMonth, 월·일을 담는 MonthDay, 그리고 열거형인 DayOfWeek와 Month가 있다. 05회에서 본 열거형이 요일과 월처럼 값의 범위가 닫힌 개념에 그대로 쓰였다.

    원칙 2. 모든 객체가 불변이다

    패키지 문서는 "All the classes are immutable and thread-safe."라고 밝힌다. 표의 모든 필드는 final이고 세터가 없다. 값을 바꾸는 것처럼 보이는 plusDays, withYear 같은 메서드는 기존 객체를 건드리지 않고 새 객체를 만들어 돌려준다. 02회에서 불변 객체가 공유 참조의 부작용을 없애는 방식을 보았는데, 날짜 타입은 그 원칙이 표준 라이브러리에 적용된 대표 사례다.

    원칙 3. 값 기반 클래스다

    표의 클래스는 모두 final이고 공개 생성자가 없다. 객체는 of, now, parse 같은 정적 팩토리 메서드로만 얻는다. Javadoc은 이들을 값 기반 클래스(value-based class)라고 부르며, equals로 같은 두 인스턴스를 서로 바꿔 써도 되는 것으로 취급하라고 요구한다. 객체의 정체성(identity)에 기대는 연산, 곧 == 비교나 synchronized의 잠금 대상으로 쓰는 일을 하지 말라는 뜻이다. JDK 21의 javac는 후자를 경고로 알려 준다.

    LocalDate d = LocalDate.of(2024, 1, 1);
synchronized (d) { System.out.println(d); }
    V.java:5: warning: [synchronization] attempt to synchronize on an instance of a value-based class
        synchronized (d) { System.out.println(d); }
        ^

    이 원고의 실행 환경에서 LocalDate.of(2024, 1, 31) == LocalDate.of(2024, 1, 31)은 false가 나오지만, 값 기반 클래스의 계약은 팩토리 메서드가 같은 값에 대해 같은 객체를 돌려줄 가능성도 열어 두고 있다. 어느 쪽이든 의존하면 안 되는 결과다. 비교는 equals, isBefore, isAfter로 한다.

    원칙 4. ISO-8601 달력과 사람이 읽는 숫자

    날짜 계산은 ISO-8601 달력 체계를 따른다. 지금의 그레고리력 규칙을 과거와 미래 전체에 똑같이 적용하는 방식이다(proleptic Gregorian). 월은 1부터 12까지이고, 요일은 월요일이 1, 일요일이 7이다. 기본 문자열 표현도 ISO-8601 형식이어서 toString()의 결과를 parse()에 그대로 넣을 수 있다.

    두 개의 시간선

    타입 지도를 한 장으로 줄이면 아래 그림이 된다. 위쪽은 전 세계가 공유하는 시간선이고 아래쪽은 한 지역의 달력과 벽시계가 그리는 지역 시간선이다. 둘 사이를 오가려면 반드시 오프셋이나 시간대가 필요하다.

    시간선(전 세계 공통)        ──●────────────────●──────────▶
                             Instant            Instant
                             (에포크 초, 나노초)
                               │  ▲
       시간대 규칙에서 오프셋을    │  │  시간대 규칙에서 오프셋을 구해 뺀다
       구해 더한다(답이 항상 1개)  ▼  │  (답이 0개 또는 2개일 수 있다)
지역 시간선(한 지역의 벽시계)  ──○────────────────○──────────▶
                             LocalDateTime = LocalDate + LocalTime

두 점을 한 객체에 묶은 것    ZonedDateTime  = LocalDateTime + ZoneOffset + ZoneId
                           OffsetDateTime = LocalDateTime + ZoneOffset
길이를 재는 자              Duration(초·나노초)      Period(연·월·일)
    Instant가 놓이는 시간선과 LocalDateTime이 놓이는 지역 시간선이 서로 다른 축이고, 둘을 잇는 것이 시간대 규칙이라는 점을 한눈에 보여 준다. 가로로 긴 평면 다이어그램. 위쪽에 굵은 수평 화살표 하나를 그리고 왼쪽 끝에 라벨 "시간선(전 세계 공통)"을 붙인다. 이 화살표 위에 점 하나를 찍고 라벨 "Instant"와 작은 글씨 "2024-01-01T00:00:00Z"를 붙인다. 아래쪽에 수평 화살표 두 개를 위아래로 나란히 그린다. 첫째 화살표 왼쪽 라벨은 "서울 벽시계", 그 위의 점에는 "LocalDateTime 09:00"을 붙인다. 둘째 화살표 왼쪽 라벨은 "뉴욕 벽시계", 그 위의 점에는 "LocalDateTime 전날 19:00"을 붙인다. 위쪽 Instant 점에서 아래 두 점으로 각각 세로 화살표를 내리고, 서울로 가는 화살표에는 "+09:00", 뉴욕으로 가는 화살표에는 "-05:00"을 적는다. 세로 화살표들 사이 가운데에 둥근 상자를 두고 "시간대 규칙(ZoneId)"이라고 적는다. 색은 시간선은 남색, 지역 시간선은 주황색, 규칙 상자는 회색. 배경은 흰색, 장식 없이 깔끔한 기술 문서 스타일. 하나의 Instant는 지역마다 다른 LocalDateTime으로 보인다. 둘을 잇는 것은 시간대 규칙이다.

    LocalDate, LocalTime, LocalDateTime: 벽에 걸린 달력과 시계

    이름의 Local은 "시간대 정보가 없다"는 뜻으로 읽어야 한다. LocalDate는 달력의 한 칸, LocalTime은 벽시계의 한 순간, LocalDateTime은 그 둘을 묶은 것이다. 어느 지역의 달력인지는 객체 안 어디에도 없다.

    import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;

public class LocalBasicsMain {
    public static void main(String[] args) {
        LocalDate date = LocalDate.of(2024, 1, 31);
        LocalTime time = LocalTime.of(9, 0);
        LocalDateTime dateTime = LocalDateTime.of(date, time);
        System.out.println(dateTime);                          // 2024-01-31T09:00

        dateTime.plusDays(1);                                  // 결과를 받지 않았다
        System.out.println(dateTime);                          // 2024-01-31T09:00

        LocalDateTime next = dateTime.plusDays(1);
        System.out.println(next);                              // 2024-02-01T09:00
        System.out.println(dateTime.isBefore(next));           // true

        System.out.println(date.plusMonths(1));                // 2024-02-29
        System.out.println(date.plusMonths(1).plusMonths(1));  // 2024-03-29
        System.out.println(date.plusMonths(2));                // 2024-03-31
        System.out.println(date.plusMonths(1).minusMonths(1)); // 2024-01-29
        System.out.println(LocalTime.of(23, 30).plusHours(1)); // 00:30
    }
}

    메모리에 있는 것

    스택(main 프레임)            힙
dateTime ─────────▶ LocalDateTime
                     ├ date ──▶ LocalDate { year = 2024, month = 1, day = 31 }
                     └ time ──▶ LocalTime { hour = 9, minute = 0, second = 0, nano = 0 }

next ─────────────▶ LocalDateTime            ← plusDays(1)이 새로 만든 객체
                     ├ date ──▶ LocalDate { year = 2024, month = 2, day = 1 }
                     └ time ──▶ (위와 같은 LocalTime 객체를 그대로 가리켜도 된다. 불변이므로)

    LocalDate는 연·월·일을 int 하나와 short 둘에 담는다. 필드 데이터만 세면 8바이트다. LocalTime은 시·분·초를 byte 셋에, 나노초를 int 하나에 담는다. LocalDateTime은 숫자를 직접 갖지 않고 이 두 객체에 대한 참조만 둔다. 어디에도 시간대나 오프셋을 담을 자리가 없다. 이것이 "LocalDateTime은 시점이 아니다"라는 말의 물리적인 근거다.

    팩토리 메서드는 객체를 만들기 전에 값을 검증한다. LocalDate.of(2023, 2, 29)는 DateTimeException: Invalid date 'February 29' as '2023' is not a leap year를 던지고, LocalDate.of(2024, 13, 1)은 Invalid value for MonthOfYear (valid values 1 - 12): 13을 던진다. Calendar처럼 없는 날짜를 조용히 다른 날짜로 바꾸지 않는다. 일단 만들어진 객체는 불변이므로, 존재하는 LocalDate는 언제나 달력에 실제로 있는 날짜다.

    같은 값, 다른 시점

    import java.time.LocalDateTime;
import java.time.ZoneId;

public class SameLocalDifferentInstant {
    public static void main(String[] args) {
        LocalDateTime nineAm = LocalDateTime.of(2024, 1, 1, 9, 0);
        System.out.println(nineAm.atZone(ZoneId.of("Asia/Seoul")).toInstant());       // 2024-01-01T00:00:00Z
        System.out.println(nineAm.atZone(ZoneId.of("Europe/London")).toInstant());    // 2024-01-01T09:00:00Z
        System.out.println(nineAm.atZone(ZoneId.of("America/New_York")).toInstant()); // 2024-01-01T14:00:00Z
    }
}

    세 줄 모두 같은 LocalDateTime 객체에서 출발했지만 결과는 서로 다른 세 시점이다. atZone으로 시간대를 붙이는 순간에 비로소 시점이 정해진다. 그러므로 "주문이 들어온 시각"처럼 전 세계에서 하나로 정해져야 하는 값을 LocalDateTime에 담으면, 어느 시간대 기준인지에 대한 약속이 코드 밖 어딘가에 따로 있어야 한다.

    불변: 결과를 받지 않으면 아무 일도 일어나지 않는다

    첫 예제의 dateTime.plusDays(1); 줄은 컴파일도 되고 실행도 되지만 아무 효과가 없다. plusDays는 새 LocalDateTime을 만들어 돌려주는데 그 참조를 받는 변수가 없으니, 새 객체는 어디에서도 참조되지 않은 채 버려진다. 03회에서 String의 메서드가 원본을 바꾸지 않던 것과 같은 구조다. 날짜 계산이 "먹히지 않는" 버그를 만나면 가장 먼저 반환값을 버리지 않았는지 본다.

    달력 산술은 숫자 산술과 다르다

    plusMonths의 결과는 달력 산술의 성질을 잘 보여 준다. 1월 31일에 한 달을 더하면 2월 31일이 되어야 하는데 그런 날은 없다. LocalDate는 이때 예외를 던지지 않고 그 달의 마지막 유효한 날로 내린다. OpenJDK 21 소스에서 이 일을 하는 메서드의 이름이 resolvePreviousValid다. 2월이면 윤년 여부에 따라 28일 또는 29일로, 4·6·9·11월이면 30일로 일(day)을 깎는다.

    이 보정 때문에 달력 산술에서는 익숙한 산술 법칙이 성립하지 않는다. 한 달을 두 번 더한 결과(3월 29일)와 두 달을 한 번에 더한 결과(3월 31일)가 다르다. 한 달을 더했다 빼도 원래 날짜(1월 31일)가 아니라 1월 29일이 된다. 중간에 2월 29일로 깎이면서 "원래 31일이었다"는 정보가 사라지기 때문이다. 매달 말일에 실행되는 일정을 "지난번 날짜 + 1개월"로 누적 계산하면 날짜가 한 번 깎인 뒤로는 계속 29일에 머문다. 기준일에서 n개월을 한 번에 더하는 식으로 계산해야 한다.

    반면 plusDays는 보정이 필요 없다. 하루 뒤는 달력에서 언제나 다음 칸이기 때문이다. LocalDate는 1970년 1월 1일을 0으로 하는 일련번호인 에포크 일(epoch day)로 바꿀 수 있고(toEpochDay()), 두 날짜 사이의 일수는 이 번호의 뺄셈이 된다. 2024년 1월 31일의 에포크 일은 19753이다. LocalTime의 덧셈은 자정을 넘으면 0시로 돌아간다. 23시 30분에 한 시간을 더하면 00시 30분이고, 넘어간 하루는 버려진다. 날짜까지 넘어가야 한다면 LocalDateTime으로 계산해야 한다.

    비교와 출력

    순서 비교는 isBefore, isAfter, isEqual로 한다. equals는 타입과 모든 필드가 같은지를 본다. LocalDateTime끼리는 isEqual과 equals의 결과가 같지만, 뒤에서 볼 ZonedDateTime에서는 둘이 달라진다. toString()에도 눈여겨볼 점이 있다. 초와 나노초가 0이면 생략되어 2024-01-31T09:00처럼 나온다. 초가 있으면 09:00:05, 밀리초가 있으면 09:00:05.001이 된다. 자릿수가 값에 따라 달라지므로, 고정 폭 문자열이 필요한 곳에는 toString()이 아니라 포맷터를 써야 한다.

    시간대: ZoneOffset, ZoneId, 그리고 규칙 데이터

    지역 시각을 시점으로 바꾸려면 "UTC와 얼마나 차이 나는가"를 알아야 한다. 자바는 이 정보를 두 단계로 나눠 표현한다. 둘을 구분하지 못하면 시간대를 다루는 코드를 읽을 수 없다.

    • ZoneOffset: UTC와의 차이 그 자체다. 값을 정하는 필드는 초 단위 정수 하나(totalSeconds)다. +09:00은 32400이다. 허용 범위는 -18:00부터 +18:00까지다.
    • ZoneId: Asia/Seoul, America/New_York 같은 지역 식별자다. 실제 객체는 ZoneRegion이라는 패키지 전용 클래스의 인스턴스이고, 식별자 문자열과 함께 그 지역의 규칙인 ZoneRules를 가리킨다.

    오프셋은 숫자이고, 시간대는 "어느 시점에 어느 오프셋을 쓰는가"를 알려 주는 함수다. 뉴욕의 오프셋은 겨울에 -05:00, 여름에 -04:00이다. "뉴욕은 -5"라고만 기억하면 일 년의 절반 넘게 한 시간씩 틀린다. 시간대를 알면 오프셋을 구할 수 있지만 오프셋만 알아서는 시간대를 알 수 없다. +09:00을 쓰는 지역은 서울만이 아니다.

    ZoneOffset은 ZoneId의 하위 클래스이기도 하다. ZoneId.of("+09:00")은 ZoneOffset 객체를 돌려주고, 그 규칙은 "언제나 이 오프셋"이다. 반면 ZoneId.of("KST")는 ZoneRulesException: Unknown time-zone ID: KST를 던진다. 세 글자 약어는 지역 식별자가 아니다.

    규칙은 어디에서 오는가

    ZoneId의 Javadoc에 따르면 기본 규칙 데이터는 IANA Time Zone Database(TZDB)에서 온다. OpenJDK는 이 데이터를 가공한 파일을 JDK 설치 디렉터리의 lib/tzdb.dat에 넣어 두고, 실행 중에 이 파일을 읽어 규칙을 얻는다. 시간대 규칙은 코드가 아니라 데이터다. 어떤 나라가 일광 절약 시간을 없애면 그 사실은 새 버전의 데이터에 반영되고, 새 데이터를 담은 JDK로 올려야 프로그램이 새 규칙을 알게 된다. 이 원고의 실행 환경에는 604개의 지역 식별자가 들어 있다(ZoneId.getAvailableZoneIds().size()). 이 수는 데이터 버전에 따라 달라진다.

    ZoneRules 안에는 과거에 오프셋이 바뀐 시점들이 정렬된 long 배열(에포크 초)로 들어 있고, 그 옆에 각 구간의 오프셋 배열이 있다. 어떤 시점의 오프셋을 물으면 Arrays.binarySearch로 그 시점이 속한 구간을 찾아 해당 오프셋을 돌려준다. 기록된 마지막 전환 이후에 대해서는 반복 규칙(ZoneOffsetTransitionRule)을 적용해 그 해의 전환 시점을 계산한다. 뉴욕의 getRules().getTransitionRules()를 출력하면 이 반복 규칙이 두 개 나온다.

    [TransitionRule[Gap -05:00 to -04:00, SUNDAY on or after MARCH 8 at 02:00 WALL, standard offset -05:00],
 TransitionRule[Overlap -04:00 to -05:00, SUNDAY on or after NOVEMBER 1 at 02:00 WALL, standard offset -05:00]]

    "3월 8일 또는 그 뒤의 첫 일요일, 벽시계 02:00에 -05:00에서 -04:00으로"와 "11월 1일 또는 그 뒤의 첫 일요일, 벽시계 02:00에 -04:00에서 -05:00으로"라는 두 규칙이다. 서울의 getTransitionRules()는 빈 목록이다. 현재 한국에는 반복되는 전환 규칙이 없다는 뜻이다. 그렇다고 서울의 규칙이 고정 오프셋인 것은 아니다. 앞에서 본 것처럼 과거 전환 기록이 있어서 isFixedOffset()은 false다.

    기본 시간대라는 숨은 입력

    ZoneId.systemDefault()는 JVM의 기본 시간대를 돌려준다. OpenJDK 21의 구현은 TimeZone.getDefault().toZoneId() 한 줄이다. 기본 시간대는 user.timezone 시스템 프로퍼티나 운영체제 설정에서 정해지므로, 같은 프로그램이 서울로 설정된 개발자의 컴퓨터와 UTC로 설정된 서버에서 다른 값을 얻는다. LocalDateTime.now(), LocalDate.now()처럼 지역 날짜·시각을 돌려주는 인자 없는 now()는 모두 이 기본 시간대를 쓴다. 코드에 보이지 않는 입력이 하나 있는 셈이다.

    ZonedDateTime: 지역 시각에 규칙을 붙여 시점으로 만든다

    ZonedDateTime은 지역 날짜·시각과 시간대를 한 객체에 묶은 것이다. Javadoc의 표현으로는 LocalDateTime, ZoneId, 그리고 해석된 ZoneOffset 세 객체에 해당하는 상태를 갖는다.

    ZonedDateTime
 ├ dateTime ──▶ LocalDateTime  2024-01-01T09:00
 ├ offset   ──▶ ZoneOffset     { totalSeconds = 32400 }           "+09:00"
 └ zone     ──▶ ZoneRegion     { id = "Asia/Seoul", rules ──▶ ZoneRules }

시점(에포크 초) = (지역 날짜·시각을 초로 바꾼 값) − offset.totalSeconds
              = 1704099600 − 32400 = 1704067200  →  2024-01-01T00:00:00Z

    오프셋을 따로 저장해 두어서 얻는 것은 두 가지다. 하나는 규칙을 다시 조회하지 않고도 시점을 계산할 수 있다는 것이다. 그림 아래의 식처럼 지역 날짜·시각과 오프셋만 있으면 에포크 초가 나온다. 다른 하나는 뒤에서 볼 overlap 때문이다. 같은 지역 시각이 두 번 나타나는 구간에서는 오프셋이 있어야 둘 중 어느 쪽인지 구별된다.

    import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class ZonedMain {
    public static void main(String[] args) {
        ZoneId seoul = ZoneId.of("Asia/Seoul");
        ZoneId newYork = ZoneId.of("America/New_York");

        ZonedDateTime inSeoul = ZonedDateTime.of(LocalDateTime.of(2024, 1, 1, 9, 0), seoul);
        ZonedDateTime inNewYork = inSeoul.withZoneSameInstant(newYork);

        System.out.println(inSeoul);                            // 2024-01-01T09:00+09:00[Asia/Seoul]
        System.out.println(inNewYork);                          // 2023-12-31T19:00-05:00[America/New_York]
        System.out.println(inSeoul.toInstant());                // 2024-01-01T00:00:00Z
        System.out.println(inNewYork.toInstant());              // 2024-01-01T00:00:00Z
        System.out.println(inSeoul.equals(inNewYork));          // false
        System.out.println(inSeoul.isEqual(inNewYork));         // true
        System.out.println(inSeoul.withZoneSameLocal(newYork)); // 2024-01-01T09:00-05:00[America/New_York]
    }
}

    한 줄씩 보자. ZonedDateTime.of는 서울의 규칙에 "2024-01-01T09:00에 유효한 오프셋"을 묻고 +09:00을 얻는다. withZoneSameInstant는 시점을 그대로 두고 시간대만 바꾼다. 시점(에포크 초 1704067200)을 기준으로 뉴욕의 규칙에서 그 시점의 오프셋 -05:00을 얻어 지역 필드를 다시 계산하므로 날짜까지 전날로 바뀐다. 두 객체의 toInstant()는 같다.

    equals가 false인 것은 equals가 지역 날짜·시각, 오프셋, 시간대 세 필드를 모두 비교하기 때문이다. 같은 순간인지 묻고 싶다면 isEqual을 쓰거나 toInstant()끼리 비교한다. ZonedDateTime을 HashMap의 키나 Set의 원소로 쓸 때 이 차이가 드러난다. 같은 순간이라도 시간대가 다르면 다른 키다. 마지막 줄의 withZoneSameLocal은 반대로 벽시계 숫자를 그대로 두고 시간대만 바꾸므로 시점이 14시간 달라진다.

    존재하지 않는 시각과 두 번 오는 시각

    시점에서 지역 시각으로 가는 방향은 언제나 답이 하나다. 반대 방향은 그렇지 않다. ZonedDateTime의 Javadoc은 지역 날짜·시각에 대해 유효한 오프셋이 한 개인 보통의 경우, 0개인 gap, 2개인 overlap 세 가지로 나눈다. 뉴욕의 2024년 전환일로 확인해 보자.

    [Gap] 2024-03-10, America/New_York — 벽시계가 한 시간을 건너뛴다
시점(UTC)    06:00Z   06:30Z   07:00Z   07:30Z
벽시계        01:00    01:30    03:00    03:30

[Overlap] 2024-11-03, America/New_York — 벽시계가 한 시간을 되돌아간다
시점(UTC)    05:00Z   05:30Z   06:00Z   06:30Z   07:00Z
벽시계        01:00    01:30    01:00    01:30    02:00
오프셋       -04:00   -04:00   -05:00   -05:00   -05:00
                               ▲ 01:59:59 다음이 다시 01:00:00. 01:00~01:59가 두 번 지나간다.
    import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZonedDateTime;

public class DstBoundaryMain {
    public static void main(String[] args) {
        ZoneId newYork = ZoneId.of("America/New_York");

        LocalDateTime inGap = LocalDateTime.of(2024, 3, 10, 2, 30);
        System.out.println(newYork.getRules().getValidOffsets(inGap));     // []
        System.out.println(ZonedDateTime.of(inGap, newYork));              // 2024-03-10T03:30-04:00[America/New_York]

        LocalDateTime inOverlap = LocalDateTime.of(2024, 11, 3, 1, 30);
        System.out.println(newYork.getRules().getValidOffsets(inOverlap)); // [-04:00, -05:00]
        ZonedDateTime earlier = ZonedDateTime.of(inOverlap, newYork);
        ZonedDateTime later = earlier.withLaterOffsetAtOverlap();
        System.out.println(earlier + " = " + earlier.toInstant());
        System.out.println(later + " = " + later.toInstant());
    }
}

    3월 10일 새벽, 뉴욕의 벽시계는 01:59:59 다음에 03:00:00이 된다. 02:30이라는 시각은 그날 뉴욕에 존재하지 않는다. getValidOffsets가 빈 목록을 돌려주는 것이 그 뜻이다. 이때 ZonedDateTime.of는 예외를 던지지 않는다. OpenJDK 21의 ZonedDateTime.ofLocal은 유효한 오프셋이 0개이면 gap의 길이만큼 지역 시각을 뒤로 밀고(02:30에서 03:30으로) 전환 뒤의 오프셋을 쓴다. 입력한 시각과 다른 시각이 조용히 만들어진다는 점을 기억해야 한다. 존재하지 않는 시각을 오류로 처리하고 싶다면 ZonedDateTime.ofStrict를 쓴다. 이 메서드는 gap에 해당하는 값에 대해 DateTimeException을 던진다.

    11월 3일 새벽에는 반대 일이 일어난다. 01:59:59 다음에 다시 01:00:00이 되어 01시대가 두 번 지나간다. 01:30은 오프셋이 -04:00일 때 한 번(05:30Z), -05:00일 때 한 번(06:30Z) 있다. ZonedDateTime.of는 둘 중 앞선 오프셋을 고른다. 뒤쪽을 원하면 withLaterOffsetAtOverlap()을 호출한다. 두 객체는 지역 날짜·시각과 시간대가 같고 오프셋만 다르다. 오프셋 필드가 없었다면 이 둘을 구별할 방법이 없다.

    한국은 현재 일광 절약 시간을 쓰지 않으므로 Asia/Seoul만 다루는 동안에는 이런 경계가 나타나지 않는다. 그래서 한 지역만 다루던 코드가 다른 지역 사용자를 받는 순간에야 문제가 드러난다. "매일 02:30에 실행" 같은 일정은 전환일에 해당 시각이 없거나 두 번 있다.

    시점 축은 끊김 없이 흐르는데 벽시계 축은 gap에서 한 시간을 건너뛰고 overlap에서 한 시간을 반복한다는 것을 나란히 보여 준다. 흰 배경의 기술 다이어그램을 좌우 두 칸으로 나눈다. 왼쪽 칸 제목은 "Gap (3월 10일)", 오른쪽 칸 제목은 "Overlap (11월 3일)". 각 칸에는 수평 축 두 개를 위아래로 그린다. 위 축 라벨은 "시점(UTC)", 아래 축 라벨은 "뉴욕 벽시계". 왼쪽 칸: 위 축에 눈금 네 개를 일정 간격으로 찍고, 각 눈금에서 아래 축으로 세로 점선을 내린다. 아래 축의 눈금 라벨은 왼쪽부터 "01:00", "01:30", "03:00", "03:30"이고, "01:30"과 "03:00" 사이 구간을 빗금으로 칠해 "02:00~02:59 없음"이라고 적는다. 오른쪽 칸: 위 축에 눈금 다섯 개를 찍고 세로 점선을 내린다. 아래 축의 눈금 라벨은 왼쪽부터 "01:00", "01:30", "01:00", "01:30", "02:00"이고, 앞의 두 눈금을 주황색 괄호로 묶어 "-04:00", 뒤의 두 눈금을 남색 괄호로 묶어 "-05:00"이라고 적는다. 장식 없이 선과 글자만 쓰는 깔끔한 스타일. 시점은 끊김 없이 흐르지만 벽시계는 gap에서 한 시간을 건너뛰고 overlap에서 한 시간을 다시 지난다.

    OffsetDateTime은 언제 쓰는가

    OffsetDateTime은 지역 날짜·시각과 오프셋만 갖고 시간대 규칙은 갖지 않는다. 시점은 정해지지만 "한 달 뒤 같은 벽시계 시각"처럼 규칙이 필요한 계산은 올바로 할 수 없다. 한 달 뒤에 그 지역의 오프셋이 바뀌어 있을 수 있기 때문이다. 대신 표현이 단순해서, 시스템 사이에 주고받는 2024-01-01T09:00+09:00 같은 문자열을 그대로 옮기는 데 맞는다. 지역의 규칙에 따라 계산해야 하면 ZonedDateTime, 이미 정해진 시점을 오프셋과 함께 기록·전달하는 것이 목적이면 OffsetDateTime이라고 구분하면 된다.

    Instant: 기계가 세는 시간

    사람은 연·월·일·시·분·초로 시간을 말하지만 기계에게 가장 다루기 쉬운 표현은 기준 시점에서부터 센 숫자다. Instant가 그 표현이다. 기준 시점은 1970-01-01T00:00:00Z이고 이를 에포크(epoch)라고 부른다. 끝의 Z는 오프셋이 0, 곧 UTC라는 표시다.

    import java.time.Instant;
import java.time.ZoneId;
import java.time.temporal.ChronoField;
import java.time.temporal.ChronoUnit;

public class InstantMain {
    public static void main(String[] args) {
        System.out.println(Instant.EPOCH);                            // 1970-01-01T00:00:00Z
        System.out.println(Instant.ofEpochSecond(1_704_067_200L));    // 2024-01-01T00:00:00Z

        Instant beforeEpoch = Instant.ofEpochMilli(-500);
        System.out.println(beforeEpoch);                              // 1969-12-31T23:59:59.500Z
        System.out.println(beforeEpoch.getEpochSecond() + " / " + beforeEpoch.getNano()); // -1 / 500000000

        System.out.println(Instant.ofEpochSecond(Integer.MAX_VALUE)); // 2038-01-19T03:14:07Z
        System.out.println(Instant.MAX);                              // +1000000000-12-31T23:59:59.999999999Z

        Instant t = Instant.parse("2024-01-01T00:00:00Z");
        System.out.println(t.atZone(ZoneId.of("Asia/Seoul")));        // 2024-01-01T09:00+09:00[Asia/Seoul]
        System.out.println(t.plus(1, ChronoUnit.DAYS));               // 2024-01-02T00:00:00Z
        System.out.println(t.isSupported(ChronoUnit.MONTHS));         // false
        System.out.println(t.isSupported(ChronoField.YEAR));          // false
    }
}

    내부 표현

    Instant의 필드는 에포크로부터의 초를 담는 long seconds와 그 초 안에서의 나노초를 담는 int nanos 두 개다. Javadoc은 표현하려는 범위가 long 하나로는 부족해서 둘로 나누었다고 설명한다. nanos는 언제나 0 이상 999,999,999 이하다. 에포크 이전 시점에서 이 규칙이 어떻게 적용되는지 예제의 셋째·넷째 출력이 보여 준다. 에포크보다 0.5초 앞선 시점은 "−0초, −500,000,000나노초"가 아니라 "−1초, +500,000,000나노초"로 저장된다. 초는 내림하고 나노초는 항상 0 이상으로 두는 방식이다. 이렇게 하면 초를 먼저 비교하고 같을 때 나노초를 비교하는 것만으로 시간 순서가 정해진다.

    long으로 초를 세므로 범위는 충분히 넓다. Instant.MAX는 10억 년의 12월 31일이다. 초를 부호 있는 32비트 정수로 세는 방식은 Integer.MAX_VALUE초가 되는 2038-01-19T03:14:07Z에서 표현 범위가 끝난다. 뒤에서 볼 MySQL TIMESTAMP 타입의 상한이 바로 이 값이다.

    Instant가 모르는 것

    Instant에는 연·월·일이 없다. isSupported(ChronoField.YEAR)가 false이고, get(ChronoField.YEAR)를 부르면 UnsupportedTemporalTypeException: Unsupported field: Year가 난다. 연도는 시점만으로 정해지지 않기 때문이다. 같은 시점이 서울에서는 2024년 1월 1일이고 뉴욕에서는 2023년 12월 31일이다. 같은 이유로 "한 달 더하기"도 지원하지 않는다(Unsupported unit: Months). 한 달의 길이는 달력의 어느 위치에 있느냐에 달려 있고, 달력의 위치는 시간대가 있어야 정해진다. 반면 plus(1, ChronoUnit.DAYS)는 된다. Instant에게 하루는 달력의 칸이 아니라 정확히 86,400초이기 때문이다. 사람에게 보여 주거나 달력 계산을 하려면 atZone(zone)으로 시간대를 붙여 ZonedDateTime으로 바꾼다.

    하루는 정확히 86,400초: 자바의 시간 척도

    앞에서 UTC에는 윤초가 있다고 했다. Instant의 Javadoc은 이 복잡함을 피하려고 자바 시간 척도(Java Time-Scale)를 따로 정의한다. 이 척도는 모든 날을 정확히 86,400개의 초로 나눈다. 윤초가 있는 날에 대해서는 그 1초를 하루의 마지막 1000초에 고르게 펴는 방식(UTC-SLS)과 같다고 정의하되, 구현이 실제로 그렇게 동작하는 시계를 제공해야 하는 것은 아니라고 덧붙인다. 요약하면 java.time의 세계에는 23:59:60이라는 시각이 없고, 두 Instant의 차이에는 그 사이에 있었던 윤초가 반영되지 않는다. 일반적인 업무 프로그램에는 이 단순화가 맞는다. 윤초까지 정확해야 하는 계산은 이 API가 다루는 범위 밖이다.

    now()는 무엇을 읽는가

    OpenJDK 21에서 Instant.now()는 Clock.currentInstant()를 부르고, 이 메서드는 jdk.internal.misc.VM.getNanoTimeAdjustment라는 네이티브 메서드로 현재 시각을 얻는다. 값의 해상도는 실행 환경이 제공하는 만큼이다. 이 원고의 실행 환경(macOS)에서는 2026-11-15T05:00:31.887197Z처럼 마이크로초 자리까지 나왔다. 실행할 때마다 값이 다르고, 환경에 따라 자릿수도 달라진다.

    이 시계는 벽시계다. 시스템의 시각이 보정되면 값이 앞이나 뒤로 움직일 수 있고, Javadoc도 시계가 단조롭게(monotonically) 나아가야 한다고 요구하지 않는다. 그러므로 "이 작업에 몇 밀리초 걸렸는가"를 재려고 Instant.now()나 System.currentTimeMillis()를 두 번 불러 빼는 것은 원칙적으로 안전하지 않다. 경과 시간에는 System.nanoTime()을 쓴다. 이 메서드의 Javadoc은 반환값이 경과 시간 측정에만 쓸 수 있고 벽시계 시각과는 관계가 없다고 명시한다. 벽시계는 "지금이 언제인가"에, nanoTime은 "얼마나 지났는가"에 쓴다.

    그렇다면 LocalDateTime.now()는 무엇을 하는가. 운영체제에 "지역 시각"을 묻는 것이 아니다. OpenJDK 21 소스를 따라가면 다음 순서다.

    마지막 단계가 중요하다. LocalDateTime.now()의 결과는 "이 JVM의 기본 시간대에서 본 지금"인데, 객체에는 그 기본 시간대가 무엇이었는지 남지 않는다. 같은 순간에 UTC 서버와 서울 서버가 각각 LocalDateTime.now()를 불러 저장하면 9시간 차이 나는 두 값이 저장되고, 나중에 값만 보아서는 어느 쪽이 어느 서버의 것인지 알 수 없다.

    import java.time.Clock;
import java.time.Instant;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.ZoneId;
import java.time.ZoneOffset;

public class ClockMain {
    public static void main(String[] args) {
        Instant fixedInstant = Instant.parse("2024-01-01T20:00:00Z");
        Clock utcClock = Clock.fixed(fixedInstant, ZoneOffset.UTC);
        Clock seoulClock = Clock.fixed(fixedInstant, ZoneId.of("Asia/Seoul"));

        System.out.println(Instant.now(utcClock));         // 2024-01-01T20:00:00Z
        System.out.println(Instant.now(seoulClock));       // 2024-01-01T20:00:00Z
        System.out.println(LocalDateTime.now(utcClock));   // 2024-01-01T20:00
        System.out.println(LocalDateTime.now(seoulClock)); // 2024-01-02T05:00
        System.out.println(LocalDate.now(utcClock));       // 2024-01-01
        System.out.println(LocalDate.now(seoulClock));     // 2024-01-02
    }
}

    Clock은 "지금"을 공급하는 객체다. now()에 Clock을 넘기면 시스템 시계 대신 그 시계를 읽는다. 예제는 시점을 2024-01-01T20:00:00Z로 고정한 시계 둘을 만들었다. Instant.now의 결과는 두 시계에서 같다. 시점은 시간대와 무관하기 때문이다. LocalDate.now의 결과는 다르다. UTC에서는 아직 1월 1일이고 서울에서는 이미 1월 2일이다. "오늘"이 며칠인지는 시점만으로는 정해지지 않는다. 시간에 의존하는 로직을 테스트할 때도 Clock을 주입받도록 만들어 두면 특정 날짜·시각의 동작을 재현할 수 있다.

    옛 API와의 다리도 Instant다. Date의 실체가 에포크 밀리초였으므로 date.toInstant()와 Date.from(instant)로 서로 바꿀 수 있다. 오래된 라이브러리가 Date를 요구하면 경계에서만 변환하고 내부 로직은 java.time 타입으로 유지한다.

    Duration은 Instant와 필드 구성이 같다. 초와 나노초다. Duration.ofDays(1)의 출력이 PT24H인 것에서 드러나듯 Duration에게 하루는 24시간, 곧 86,400초의 다른 이름일 뿐이다. 60분과 1시간은 같은 3,600초로 저장되므로 equals도 true다. 문자열 표현의 P는 기간(period)을, T는 그 뒤가 시간 단위임을 나타내는 ISO-8601 표기다.

    Period는 연·월·일 세 정수를 따로 든다. 세 값은 자동으로 환산되지 않는다. Period.ofMonths(14)는 P14M으로 남고, normalized()를 불러야 P1Y2M이 된다. 12개월과 1년은 달력에서 같은 양이지만 필드 값이 다르므로 equals는 false다. normalized()도 일(days)은 건드리지 않는다. 45일이 "1개월 14일"인지 "1개월 17일"인지는 어느 달에서 세느냐에 달려 있어서, 날짜 없이 양만 가지고는 환산할 수 없기 때문이다. Period가 세 필드를 합치지 않고 따로 들고 있는 이유가 이것이다.

    하루와 24시간이 갈라지는 날

    예제의 뒷부분은 두 자의 차이가 결과로 나타나는 경우다. 뉴욕의 2024년 3월 9일 정오에서 출발한다. 다음 날 새벽에 벽시계가 한 시간을 건너뛴다. Period.ofDays(1)을 더하면 달력에서 한 칸 뒤의 같은 벽시계 시각, 3월 10일 12:00이 된다. Duration.ofDays(1)을 더하면 시간선에서 86,400초 뒤이고, 그 시점의 뉴욕 벽시계는 13:00이다. 3월 9일 정오에서 3월 10일 정오까지가 뉴욕에서는 23시간이었기 때문이다. 마지막 줄의 PT23H가 그것을 확인해 준다.

    이 차이는 ZonedDateTime.plus의 구현에서 나온다. OpenJDK 21 소스는 단위가 날짜 기반(isDateBased())이면 지역 날짜·시각에 더한 다음 시간대 규칙으로 오프셋을 다시 구한다. 시간 기반이면 지역 날짜·시각에 더한 값을 기존 오프셋으로 시점으로 바꾸고, 그 시점에 유효한 오프셋으로 지역 시각을 다시 구한다. 앞의 경로는 지역 시간선에서, 뒤의 경로는 전 세계 시간선에서 계산하는 것이다. "내일 같은 시각에 알림"은 Period이고 "24시간 뒤 만료"는 Duration이다. 요구사항의 문장을 어느 쪽으로 읽을지 먼저 정해야 한다.

    두 값 사이의 양 구하기

    import java.time.Duration;
import java.time.LocalDate;
import java.time.LocalTime;
import java.time.Period;
import java.time.temporal.ChronoUnit;

public class BetweenMain {
    public static void main(String[] args) {
        LocalDate start = LocalDate.of(2023, 1, 15);
        LocalDate end = LocalDate.of(2024, 3, 20);

        Period period = Period.between(start, end);
        System.out.println(period);                                // P1Y2M5D
        System.out.println(period.getDays());                      // 5
        System.out.println(ChronoUnit.DAYS.between(start, end));   // 430
        System.out.println(ChronoUnit.MONTHS.between(start, end)); // 14

        Duration work = Duration.between(LocalTime.of(9, 0), LocalTime.of(17, 30));
        System.out.println(work);                                              // PT8H30M
        System.out.println(work.toMinutes());                                  // 510
        System.out.println(work.toHours() + "시간 " + work.toMinutesPart() + "분"); // 8시간 30분
    }
}

    Period.between은 두 날짜 사이를 "1년 2개월 5일"로 분해한다. 여기서 getDays()는 전체 일수가 아니라 분해한 결과의 일 부분인 5다. 남은 날수를 계산하려고 Period.between(...).getDays()를 쓰면 간격이 한 달을 넘는 순간부터 틀린 값이 나온다. 전체 일수는 ChronoUnit.DAYS.between이 준다(430). ChronoUnit.MONTHS.between은 꽉 찬 개월 수(14)를 준다. Duration에도 같은 구분이 있다. toMinutes()는 전체를 분으로 환산한 510이고, toMinutesPart()는 시간을 떼고 남은 30이다.

    Duration.between은 초 단위로 차이를 계산하므로 두 인자가 초를 지원해야 한다. Duration.between(LocalDate, LocalDate)는 컴파일은 되지만 실행하면 UnsupportedTemporalTypeException: Unsupported unit: Seconds가 난다. 같은 이유로 LocalDate에 Duration을 더할 수 없고(Unsupported unit: Seconds), LocalTime에 Period를 더할 수 없다(Unsupported unit: Days). 날짜만 있는 타입에는 초가 없고 시각만 있는 타입에는 날이 없다. 왜 이것이 컴파일 오류가 아니라 실행 중 예외인지는 다음 절의 인터페이스 구조가 설명한다.

    날짜와 시간의 핵심 인터페이스

    지금까지 본 타입은 열 개 가까이 되고, 표준 단위(초, 분, 일, 월 등)는 ChronoUnit에 16개, 표준 필드(연도, 요일, 분 등)는 ChronoField에 30개가 정의되어 있다. 모든 조합마다 메서드를 만들 수는 없으므로 java.time은 "무엇에", "얼마를", "어떤 단위로", "어떤 필드를"을 각각 인터페이스로 분리했다. 이들은 java.time.temporal 패키지에 있다.

   ▲ 구현

    • TemporalAccessor: 필드 값을 읽을 수 있는 것. 읽기 전용이다.
    • Temporal: 읽을 수 있고, 더하거나 빼거나 일부를 바꾼 사본을 만들 수 있는 것. 시점과 지역 날짜·시각 타입이 모두 여기에 속한다.
    • TemporalAmount: 시간의 양. Duration과 Period가 구현한다.
    • TemporalUnit: 양을 재는 단위. 표준 구현은 열거형 ChronoUnit이다.
    • TemporalField: 날짜·시각의 한 구성 요소. 표준 구현은 열거형 ChronoField다.
    • TemporalAdjuster: Temporal을 받아 조정된 Temporal을 돌려주는 전략 객체.

    단위와 필드는 헷갈리기 쉽다. 단위는 길이를 재는 눈금이고(ChronoUnit.HOURS: 3시간), 필드는 날짜·시각 안의 한 자리다(ChronoField.HOUR_OF_DAY: 15시). 단위는 plus, minus, between에 쓰이고 필드는 get, with에 쓰인다. 두 표준 구현이 모두 열거형이라는 점은 05회와 이어진다. 열거형 상수가 인터페이스를 구현하면 "값의 목록"이면서 동시에 "동작을 가진 객체"가 된다. DayOfWeek와 Month도 TemporalAccessor와 TemporalAdjuster를 구현한 열거형이다.

    호출이 흘러가는 길

    date.plus(Period.ofMonths(1)) 한 줄이 어떻게 처리되도록 설계되었는지 따라가 보자. Temporal 인터페이스의 기본 구현은 한 줄이다.

    // java.time.temporal.Temporal (OpenJDK 21)
default Temporal plus(TemporalAmount amount) {
    return amount.addTo(this);
}

    날짜가 스스로 계산하지 않고 양에게 "나에게 너를 더해 달라"고 넘긴다. Period.addTo는 자신의 필드를 보고 temporal.plus(totalMonths, MONTHS)와 temporal.plus(days, DAYS)를 차례로 부른다. 다시 날짜 쪽으로 돌아온 호출은 LocalDate.plus(long, TemporalUnit)에서 단위에 따라 plusMonths, plusDays 같은 구체 메서드로 갈라진다.

    OpenJDK 21의 LocalDate.plus(TemporalAmount)는 인자가 Period일 때 이 왕복을 건너뛰고 곧바로 plusMonths와 plusDays를 부르는 지름길을 두고 있지만 결과는 같다. 서로 상대에게 한 번씩 위임하는 이 구조 덕분에 새로운 양 타입이나 새로운 단위를 추가해도 기존 날짜 타입을 고칠 필요가 없다. Duration.addTo는 같은 방식으로 plus(seconds, SECONDS)와 plus(nanos, NANOS)를 부른다. LocalDate는 SECONDS를 지원하지 않으므로 앞 절에서 본 예외가 여기서 난다. 월을 먼저 더하고 일을 나중에 더하는 순서에도 의미가 있다. 1월 31일에 Period.of(0, 1, 1)을 더하면 먼저 2월 29일이 되고 거기에 하루를 더해 3월 1일이 된다.

    지원 여부는 실행 중에 결정된다

    get의 매개변수 타입은 TemporalField이고 plus의 매개변수 타입은 TemporalUnit이다. 컴파일러가 보는 것은 이 타입뿐이다. ChronoField.HOUR_OF_DAY는 TemporalField이므로 localDate.get(ChronoField.HOUR_OF_DAY)는 타입 검사를 통과한다. LocalDate에 시(hour)가 없다는 사실은 실행 중에 LocalDate의 코드가 필드를 보고 판단한다. 유연성을 얻은 대가로 일부 오류가 컴파일 시점에서 실행 시점으로 넘어간 것이다.

    그래서 isSupported(field)와 isSupported(unit)이 있다. 어떤 Temporal이 들어올지 모르는 범용 코드는 먼저 물어보고 호출한다. 타입을 아는 평범한 코드에서는 getYear(), plusDays()처럼 타입에 정의된 전용 메서드를 쓰는 편이 안전하다. 전용 메서드는 그 타입이 지원하는 것만 있으므로 잘못된 조합이 애초에 컴파일되지 않는다. LocalDate에는 getHour()가 없다.

    날짜·시각 타입, 양, 단위, 필드가 서로 다른 인터페이스로 분리되어 있고 plus 호출이 Temporal과 TemporalAmount 사이를 한 번 왕복한다는 것을 보여 준다. 흰 배경의 클래스 관계도. 왼쪽 위에 상자 "TemporalAccessor"를 두고 그 아래에 상자 "Temporal"을 두어 아래에서 위로 속이 빈 삼각형 화살표를 그린다. "Temporal" 아래에 상자 세 개 "LocalDate", "ZonedDateTime", "Instant"를 가로로 나란히 두고 각각 "Temporal"로 점선 삼각형 화살표를 그린다. 오른쪽 위에 상자 "TemporalAmount"를 두고 그 아래에 상자 두 개 "Duration", "Period"를 두어 점선 삼각형 화살표를 그린다. "Temporal"에서 "TemporalAmount"로 가는 굵은 실선 화살표에 "plus(amount)"라고 적고, "TemporalAmount"에서 "Temporal"로 되돌아오는 굵은 실선 화살표에 "addTo(temporal)"라고 적는다. 아래쪽 가운데에 둥근 상자 두 개 "ChronoUnit", "ChronoField"를 두고 "Temporal"과 얇은 선으로 잇는다. 인터페이스 상자는 남색 테두리, 클래스 상자는 회색 테두리, 열거형 상자는 주황색 테두리. 장식 없는 기술 문서 스타일. 날짜·시각은 Temporal, 양은 TemporalAmount, 단위와 필드는 열거형이다. plus는 양에게 위임되었다가 단위를 들고 되돌아온다.

    날짜와 시간 조회하고 조작하기

    앞 절의 인터페이스를 실제로 써 보자. 조회는 get, 계산은 plus와 minus, 일부 교체는 with, 차이는 until이다.

    import java.time.DayOfWeek;
import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;
import java.time.temporal.ChronoField;
import java.time.temporal.ChronoUnit;
import java.time.temporal.TemporalAdjusters;
import java.time.temporal.UnsupportedTemporalTypeException;

public class FieldUnitMain {
    public static void main(String[] args) {
        LocalDate date = LocalDate.of(2024, 2, 10);   // 토요일

        System.out.println(date.get(ChronoField.DAY_OF_YEAR));         // 41
        System.out.println(date.getLong(ChronoField.EPOCH_DAY));       // 19763
        System.out.println(date.range(ChronoField.DAY_OF_MONTH));      // 1 - 29
        System.out.println(date.isSupported(ChronoField.HOUR_OF_DAY)); // false

        System.out.println(date.plus(2, ChronoUnit.WEEKS));            // 2024-02-24
        System.out.println(date.with(ChronoField.DAY_OF_MONTH, 1));    // 2024-02-01
        System.out.println(date.with(TemporalAdjusters.lastDayOfMonth()));               // 2024-02-29
        System.out.println(date.with(TemporalAdjusters.next(DayOfWeek.FRIDAY)));         // 2024-02-16
        System.out.println(date.with(TemporalAdjusters.firstInMonth(DayOfWeek.MONDAY))); // 2024-02-05

        LocalDateTime dateTime = LocalDateTime.of(2024, 2, 10, 9, 37, 45);
        System.out.println(dateTime.with(LocalTime.of(18, 0)));        // 2024-02-10T18:00
        System.out.println(dateTime.truncatedTo(ChronoUnit.HOURS));    // 2024-02-10T09:00

        try {
            date.get(ChronoField.HOUR_OF_DAY);
        } catch (UnsupportedTemporalTypeException e) {
            System.out.println(e.getMessage());                        // Unsupported field: HourOfDay
        }
    }
}

    조회: get, getLong, range

    get(ChronoField.DAY_OF_YEAR)는 그 해의 몇 번째 날인지를 준다. 2월 10일은 31 + 10 = 41번째 날이다. 자주 쓰는 필드에는 getYear(), getMonthValue(), getDayOfMonth(), getDayOfWeek() 같은 전용 메서드가 있다. get은 int를 돌려주므로 값이 int 범위를 넘을 수 있는 필드는 getLong으로 읽어야 한다. date.get(ChronoField.EPOCH_DAY)는 Invalid field 'EpochDay' for get() method, use getLong() instead라는 예외를 낸다. 지금 값이 19763으로 작더라도, 그 필드가 가질 수 있는 범위를 기준으로 막는 것이다.

    range는 그 객체의 문맥에서 필드가 가질 수 있는 값의 범위를 준다. 2024년 2월의 날짜에 대해 range(DAY_OF_MONTH)는 1 - 29다. 필드 자체에 물으면(ChronoField.DAY_OF_MONTH.range()) 1 - 28/31이 나온다. 최댓값이 문맥에 따라 28에서 31 사이라는 뜻이다. 달의 길이를 직접 계산하는 코드를 쓰기 전에 이 메서드나 lengthOfMonth()를 떠올리면 된다.

    계산: plus, minus와 ChronoUnit

    plus(2, ChronoUnit.WEEKS)는 plusWeeks(2)와 같다. 단위를 변수로 받아야 할 때 이 형태가 쓸모 있다. ChronoUnit의 각 상수는 자신의 길이를 Duration으로 알고 있는데, 그 값이 정확한지 추정인지를 구분한다. ChronoUnit.HOURS.isDurationEstimated()는 false이고 ChronoUnit.DAYS.isDurationEstimated()는 true다. 하루는 일광 절약 시간 때문에, 한 달은 달마다 길이가 달라서 정확한 길이를 하나로 정할 수 없기 때문이다. 앞에서 본 Duration과 Period의 구분이 단위에도 그대로 들어 있다.

    교체: with와 조정기

    with(field, value)는 한 필드만 바꾼 사본을 만든다. withDayOfMonth(1) 같은 전용 메서드도 있다. 바꾼 결과가 유효하지 않을 때의 동작은 필드에 따라 다르다. 1월 31일에 withMonth(2)를 하면 plusMonths와 마찬가지로 2월 29일로 보정된다. 반면 2월 날짜에 with(ChronoField.DAY_OF_MONTH, 31)을 하면 DateTimeException: Invalid date 'FEBRUARY 31'이 난다. 월이나 연을 바꿀 때는 일을 깎아 주지만, 일 자체를 없는 값으로 지정하는 것은 오류로 본다.

    "이번 달 마지막 날", "다음 금요일"처럼 필드 하나를 바꾸는 것으로 표현되지 않는 조정은 with(TemporalAdjuster)로 한다. TemporalAdjusters 클래스가 자주 쓰는 조정기를 정적 메서드로 제공한다. next(DayOfWeek.FRIDAY)는 기준일 뒤에 오는 첫 금요일을 찾는다. 기준일이 금요일이어도 그날은 포함하지 않는다. 기준일을 포함하려면 nextOrSame을 쓴다. 2024년 2월 10일은 토요일이므로 다음 금요일은 2월 16일이다. firstInMonth(DayOfWeek.MONDAY)는 그 달의 첫 월요일인 2월 5일을 준다.

    dateTime.with(LocalTime.of(18, 0))이 동작하는 것은 LocalTime 자신이 TemporalAdjuster이기 때문이다. "대상의 시각 부분을 나로 바꾼다"는 조정이다. LocalDate도 마찬가지여서 dateTime.with(someDate)는 날짜 부분만 바꾼다. truncatedTo(ChronoUnit.HOURS)는 지정한 단위보다 작은 필드를 0으로 만든다. 시간 단위로 묶어 집계하는 일에 쓴다.

    차이: until과 between

    ChronoUnit.DAYS.between(a, b)의 구현은 a.until(b, this) 한 줄이다. 계산의 주체는 단위가 아니라 시작 쪽 Temporal이다. 결과는 꽉 찬 단위의 수이고 나머지는 버린다. 2024년 1월 15일에서 3월 20일까지는 꽉 찬 2개월에 5일이 남는데 MONTHS.between은 2만 준다. 끝점은 포함하지 않는다. 매개변수 이름부터 temporal1Inclusive, temporal2Exclusive다. 1월 1일에 입실해 1월 3일에 퇴실하는 숙박의 박 수는 DAYS.between이 주는 2가 맞지만, "며칠에 걸쳐 있는가"를 묻는다면 1을 더해 3이 된다. 끝점을 포함할지는 요구사항에서 먼저 정해야 한다.

    문자열 파싱과 포맷팅: DateTimeFormatter

    날짜 객체는 프로그램 안에서는 필드 몇 개지만 프로그램 밖(화면, 파일, 네트워크, 로그)에서는 문자열이다. 객체를 문자열로 바꾸는 것을 포맷팅(formatting), 문자열을 객체로 바꾸는 것을 파싱(parsing)이라고 한다.

    기본은 ISO-8601

    포맷터를 지정하지 않으면 ISO-8601 형식이 쓰인다. LocalDate.parse("2024-01-31"), LocalDateTime.parse("2024-01-01T09:00"), Instant.parse("2024-01-01T00:00:00Z"), ZonedDateTime.parse("2024-01-01T09:00+09:00[Asia/Seoul]")이 모두 그대로 동작한다. 날짜와 시각 사이의 구분자는 공백이 아니라 T다. LocalDateTime.parse("2024-01-01 09:00:00")은 DateTimeParseException: Text '2024-01-01 09:00:00' could not be parsed at index 10으로 실패한다. 10번 인덱스가 공백 자리다. 패키지 문서는 데이터베이스나 네트워크 같은 시스템 경계를 넘을 때 ISO-8601 기반의 이 타입들을 쓰라고 권한다. 시스템 사이에 주고받는 값은 기본 형식이 가장 덜 위험하다.

    패턴으로 만드는 포맷터

    import java.time.LocalDateTime;
import java.time.format.DateTimeFormatter;
import java.util.Locale;

public class FormatMain {
    public static void main(String[] args) {
        DateTimeFormatter formatter = DateTimeFormatter.ofPattern("yyyy-MM-dd HH:mm:ss");
        LocalDateTime dateTime = LocalDateTime.of(2024, 1, 1, 9, 0, 0);

        System.out.println(dateTime);                    // 2024-01-01T09:00
        System.out.println(dateTime.format(formatter));  // 2024-01-01 09:00:00
        System.out.println(LocalDateTime.parse("2024-01-01 09:00:00", formatter)); // 2024-01-01T09:00
        System.out.println(formatter);

        DateTimeFormatter korean = DateTimeFormatter.ofPattern("yyyy년 M월 d일 (E) a hh:mm", Locale.KOREA);
        System.out.println(dateTime.format(korean));     // 2024년 1월 1일 (월) 오전 09:00
    }
}

LocalDate를 HH가 든 패턴으로 포맷하면 Unsupported field: HourOfDay가 난다. 포맷터는 앞 절의 TemporalAccessor와 TemporalField 위에서 동작한다.

    요일이나 오전/오후처럼 글자로 나오는 필드는 로캘(locale)에 따라 달라진다. 예제는 Locale.KOREA를 지정해 (월)과 오전을 얻었다. 로캘을 주지 않으면 JVM의 기본 로캘이 쓰이므로 실행 환경에 따라 출력이 달라질 수 있다. 자주 쓰는 패턴 문자는 다음과 같다. 대문자와 소문자가 다른 필드를 뜻한다는 점이 함정이다.

    파싱은 두 단계다

    파싱은 포맷팅을 거꾸로 돌린 것이 아니다. 두 단계를 거친다. 첫 단계는 패턴을 따라 텍스트를 읽어 "필드와 값"의 표를 만드는 일이다. "2024-02-30"을 yyyy-MM-dd로 읽으면 {YearOfEra=2024, MonthOfYear=2, DayOfMonth=30}이 된다. 이 단계는 패턴이 정한 자릿수와 구분 문자대로 글자를 읽을 뿐, 읽은 값이 달력에서 말이 되는지는 따지지 않는다. 둘째 단계는 해석(resolve)이다. 흩어진 필드 값들을 모아 실제 날짜로 조립하고, 요청한 타입으로 바꾼다. LocalDate.parse(text, formatter)의 구현은 formatter.parse(text, LocalDate::from)이다. 해석이 끝난 중간 결과에 "LocalDate로 바꿔 달라"고 요청하는 것이다.

    해석 단계가 얼마나 엄격한지는 ResolverStyle이 정한다. STRICT, SMART, LENIENT 세 가지가 있고, ofPattern으로 만든 포맷터의 기본값은 SMART다. 이 기본값이 예상과 다른 결과를 만든다.

    import java.time.LocalDate;
import java.time.LocalDateTime;
import java.time.LocalTime;
import java.time.format.DateTimeFormatter;
import java.time.format.DateTimeParseException;
import java.time.format.ResolverStyle;
import java.util.Locale;

public class ParsePitfallMain {
    public static void main(String[] args) {
        DateTimeFormatter smart = DateTimeFormatter.ofPattern("yyyy-MM-dd");
        System.out.println(LocalDate.parse("2024-02-30", smart));         // 2024-02-29

        DateTimeFormatter strict = DateTimeFormatter.ofPattern("uuuu-MM-dd")
                .withResolverStyle(ResolverStyle.STRICT);
        try {
            LocalDate.parse("2024-02-30", strict);
        } catch (DateTimeParseException e) {
            System.out.println(e.getMessage());
        }

        DateTimeFormatter weekYear = DateTimeFormatter.ofPattern("YYYY-MM-dd", Locale.KOREA);
        System.out.println(LocalDate.of(2024, 12, 30).format(weekYear));  // 2025-12-30

        System.out.println(LocalTime.of(15, 5).format(DateTimeFormatter.ofPattern("hh:mm")));  // 03:05
        System.out.println(LocalDateTime.of(2024, 3, 5, 9, 7)
                .format(DateTimeFormatter.ofPattern("yyyy-mm-dd")));                           // 2024-07-05
    }
}

    첫 줄이 핵심이다. 2월 30일은 없는 날짜인데 예외가 아니라 2월 29일이 나왔다. SMART 해석은 일(day)이 1~31 범위 안이면 그 달의 마지막 유효한 날로 내려 준다. "2024-02-32"처럼 범위를 벗어난 값이어야 예외가 난다. 사용자가 입력한 잘못된 날짜가 검증을 통과해 다른 날짜로 저장될 수 있다는 뜻이다. 인자 없는 LocalDate.parse("2024-02-30")은 예외를 던지는데, 기본 ISO 포맷터(ISO_LOCAL_DATE)는 STRICT로 설정되어 있기 때문이다. 직접 만든 패턴에서 같은 엄격함을 얻으려면 withResolverStyle(ResolverStyle.STRICT)를 붙인다.

    이때 패턴의 연도 문자를 uuuu로 바꿔야 한다. STRICT에서 yyyy는 "연대 기준 연도"만 준 것이어서 어느 연대인지가 정해지지 않았다고 보고, 올바른 날짜인 2024-02-29조차 Unable to obtain LocalDate from TemporalAccessor로 시작하는 메시지로 거부한다. 메시지 뒤쪽의 중괄호 안에는 읽어 들인 필드 YearOfEra=2024, MonthOfYear=2, DayOfMonth=29가 나열되는데, 나열 순서는 실행에 따라 달라질 수 있다. uuuu는 연대와 무관한 연도여서 그대로 해석된다. LENIENT는 반대쪽 극단이다. 2월 30일을 3월 1일로 넘겨서 받아들인다.

    문자열이 먼저 필드 표로 읽히고, 그다음 해석 단계에서 ResolverStyle에 따라 예외·보정·넘김으로 갈라진다는 것을 보여 준다. 흰 배경의 왼쪽에서 오른쪽으로 흐르는 순서도. 맨 왼쪽에 문서 모양 상자를 두고 "2024-02-30"이라고 적는다. 오른쪽으로 화살표를 그려 사각 상자 "1단계: 패턴으로 읽기"에 연결한다. 다시 오른쪽으로 화살표를 그려 표 모양 상자에 연결하고, 표 안에 세 줄 "Year=2024", "MonthOfYear=2", "DayOfMonth=30"을 적는다. 다시 오른쪽으로 화살표를 그려 마름모 상자 "2단계: 해석"에 연결한다. 마름모에서 오른쪽으로 화살표 세 개가 위·가운데·아래로 갈라진다. 위 화살표 끝의 빨간 상자에는 "STRICT: 예외", 가운데 화살표 끝의 주황 상자에는 "SMART: 2024-02-29", 아래 화살표 끝의 회색 상자에는 "LENIENT: 2024-03-01"이라고 적는다. 장식 없이 선과 상자만 쓰는 기술 문서 스타일. 패턴 uuuu-MM-dd로 "2024-02-30"을 읽을 때. 읽기 단계는 같고, 해석 단계의 방식에 따라 결과가 셋으로 갈린다.

    패턴 문자를 잘못 고른 버그

    예제의 나머지 세 줄은 패턴 문자를 잘못 골랐을 때의 결과다. 대문자 YYYY는 달력 연도가 아니라 주 기준 연도다. 한 주가 어느 해에 속하는지를 기준으로 연도를 정하므로 연말과 연초의 며칠 동안 달력 연도와 어긋난다. 2024년 12월 30일을 Locale.KOREA에서 YYYY-MM-dd로 포맷하면 2025-12-30이 나온다. 일 년 중 며칠만 틀리므로 평소의 테스트로는 드러나지 않는다. 소문자 hh는 12시간제여서 오후 3시가 03으로 나오고, 오전/오후 표시가 없으면 정보가 사라진다. 이 패턴으로 "03:05"를 파싱하면 오전인지 오후인지 정할 수 없어서 실패한다. 소문자 mm은 분이다. yyyy-mm-dd는 월 자리에 분을 찍으므로, 3월 5일 9시 7분을 포맷하면 월 자리에 07이 나온다.

    Instant를 패턴으로 포맷하려 할 때 나는 예외도 지금까지의 내용으로 설명된다. DateTimeFormatter.ofPattern("yyyy-MM-dd").format(instant)는 Unsupported field: YearOfEra로 실패한다. Instant에는 연도가 없기 때문이다. 포맷터에 withZone(zone)으로 시간대를 주면 포맷터가 시점을 그 시간대의 날짜·시각으로 바꾼 뒤 필드를 읽는다.

    포맷터는 공유해도 된다

    DateTimeFormatter의 Javadoc은 이 클래스가 불변이고 스레드 안전하다고 명시한다. 패턴을 해석한 결과는 만들어진 뒤 바뀌지 않으므로, 포맷터를 static final 상수로 만들어 여러 스레드가 함께 써도 된다. 패턴 해석도 한 번만 하면 된다. 요청마다 ofPattern을 다시 부를 이유가 없다. 스레드마다 인스턴스를 따로 만들라고 권하던 SimpleDateFormat과 달라진 점이다.

    타입을 고르는 기준과 시스템 경계

    지금까지의 내용은 "이 값은 시점인가, 지역 날짜·시각인가, 양인가"라는 하나의 질문으로 모인다. 요구사항 문장을 이 질문에 대입하면 타입이 정해진다.

    요구사항성격타입
    주문이 접수된 순간, 로그의 타임스탬프이미 일어난 일의 시점Instant
    생일, 공휴일, 계약 시작일시간대와 무관한 날짜LocalDate
    매장이 문을 여는 시각, 알람 시각시간대와 무관한 벽시계 시각LocalTime
    특정 도시에서 열리는 내년의 회의한 지역의 미래 일정LocalDateTime과 ZoneId(또는 ZonedDateTime)
    외부 시스템이 보낸 2024-01-01T09:00+09:00오프셋이 붙은 시점OffsetDateTime
    토큰의 유효 시간 30분, 타임아웃시간선 위의 길이Duration
    구독 기간 1개월, 나이달력 위의 길이Period

    과거의 사건과 미래의 약속을 다르게 다루는 이유는 시간대 규칙이 바뀔 수 있기 때문이다. 이미 일어난 일은 시점이 확정되어 있으므로 Instant로 저장하면 어떤 규칙 변경에도 영향받지 않는다. 미래의 약속은 사정이 다르다. 사람들이 합의한 것은 "그 지역 벽시계로 오전 9시"이지 특정 에포크 초가 아니다. 그 사이에 해당 지역의 오프셋 규칙이 바뀌면, 미리 계산해 둔 Instant는 더 이상 그 지역의 오전 9시가 아니다. 지역 날짜·시각과 시간대 식별자를 저장해 두고, 필요한 때에 최신 규칙으로 시점을 계산해야 약속의 의미가 유지된다.

    패키지 문서는 가능하면 시간대가 없는 단순한 타입을 쓰라고 권하고, 많은 애플리케이션은 LocalDate, LocalTime, Instant만으로 작성하고 시간대는 사용자 인터페이스 계층에서 붙일 수 있다고 적는다. 서버 내부와 저장소에서는 시점을 시점으로 다루고, 사람에게 보여 주는 마지막 단계에서 그 사람의 시간대로 바꾸라는 뜻이다.

    LocalDateTime.now()가 위험해지는 곳

    LocalDateTime.now()는 JVM 기본 시간대라는 숨은 입력에 의존하고, 결과에 그 시간대를 남기지 않는다. 서버의 시간대 설정이 끝까지 바뀌지 않고 사용자도 모두 같은 지역에 있다면 문제가 드러나지 않는다. 가정 중 하나가 깨지면 문제가 된다. 개발 환경은 서울, 운영 환경은 UTC로 설정되어 있으면 "오늘 가입한 회원" 같은 조회가 9시간 어긋난 경계로 잘린다. 앞의 Clock 예제에서 같은 시점에 LocalDate.now가 1월 1일과 1월 2일로 갈렸던 것이 그 상황이다. 시점을 기록할 때는 Instant.now()를 쓰고, "오늘"이 필요할 때는 LocalDate.now(ZoneId.of("Asia/Seoul"))처럼 어느 지역의 오늘인지를 코드에 드러내는 편이 안전하다.

    데이터베이스로 넘어갈 때

    같은 구분이 데이터베이스 컬럼 타입에도 있다. MySQL 8.4 매뉴얼에 따르면 TIMESTAMP는 값을 저장할 때 현재 시간대에서 UTC로 바꾸고 조회할 때 다시 현재 시간대로 바꾸며, DATETIME 같은 다른 타입에는 이런 변환이 일어나지 않는다. TIMESTAMP의 범위는 '1970-01-01 00:00:01' UTC부터 '2038-01-19 03:14:07' UTC까지이고, DATETIME이 지원하는 범위는 '1000-01-01 00:00:00'부터 '9999-12-31 23:59:59'까지다. 성격으로 보면 TIMESTAMP는 시점에, DATETIME은 지역 날짜·시각에 가깝다. TIMESTAMP의 상한이 앞에서 본 32비트 초 카운터의 끝과 같다는 것도 눈에 들어올 것이다. 자바 타입과 컬럼 타입을 어떻게 짝지을지, JDBC 드라이버와 JPA 구현체가 그 사이에서 무엇을 변환하는지는 데이터베이스와 JPA를 다루는 권에서 이어진다.

    이 장의 핵심

    시간에 관한 값은 시점, 지역 날짜·시각, 양 가운데 하나다. Instant는 에포크로부터의 초와 나노초만 들고, LocalDateTime은 달력과 벽시계의 숫자만 들며, 둘 사이를 잇는 것은 시간대 규칙이다. 규칙은 지역마다 다르고 법에 따라 바뀌므로, 지역 시각에서 시점으로 가는 길은 답이 0개이거나 2개일 수 있다. 코드를 쓰기 전에 다루는 값이 셋 중 무엇인지 정하면 타입, 연산, 저장 형식이 함께 정해진다.
    시점과 지역 날짜·시각
    시점은 전 세계가 공유하는 시간선 위의 한 점이고, 지역 날짜·시각은 한 지역의 달력과 벽시계가 보여 주는 값이다. 지역 날짜·시각은 시간대가 주어져야 시점이 된다.
    LocalDate · LocalTime · LocalDateTime
    연·월·일, 시·분·초·나노초만 필드로 갖고 시간대나 오프셋은 갖지 않는다. 불변이라 plus, with는 새 객체를 돌려주며, 월 계산은 없는 날짜를 그 달의 마지막 날로 보정한다.
    ZoneOffset과 ZoneId
    오프셋은 UTC와의 차이(초 단위 정수)이고, 시간대는 시점마다 어느 오프셋을 쓰는지 알려 주는 규칙이다. 규칙은 JDK에 실린 시간대 데이터에서 오며 데이터가 갱신되면 바뀐다.
    ZonedDateTime
    지역 날짜·시각, 오프셋, 시간대를 함께 든다. 일광 절약 시간 전환일의 gap에서는 시각을 뒤로 밀고 overlap에서는 앞선 오프셋을 고른다. equals는 세 필드를, isEqual은 시점을 비교한다.
    Instant
    1970-01-01T00:00:00Z로부터의 초(long)와 나노초(int)다. 연·월 같은 달력 필드가 없고, 하루를 정확히 86,400초로 보는 자바 시간 척도 위에 있다.
    Clock과 now()
    now()는 시계에서 시점을 읽고 기본 시간대의 오프셋을 더해 지역 필드로 나눈다. LocalDateTime.now()의 결과에는 어느 시간대였는지가 남지 않는다. 경과 시간 측정에는 System.nanoTime()을 쓴다.
    Duration과 Period
    Duration은 초·나노초로 잰 시간선 위의 길이이고 Period는 연·월·일로 잰 달력 위의 길이다. 일광 절약 시간 전환일에는 하루(Period)와 24시간(Duration)이 다른 결과를 낸다.
    Temporal 계열 인터페이스
    날짜·시각은 Temporal, 양은 TemporalAmount, 단위는 ChronoUnit, 필드는 ChronoField다. 어떤 필드·단위를 지원하는지는 실행 중에 판단되므로 잘못된 조합은 UnsupportedTemporalTypeException이 된다.
    DateTimeFormatter
    패턴을 필드별 출력기·해석기 목록으로 바꿔 둔 불변 객체다. 파싱은 읽기와 해석 두 단계이고, ofPattern의 기본 해석 방식인 SMART는 2월 30일을 2월의 마지막 날로 바꾼다.

    실무에서 가장 먼저 내려야 하는 결정은 "무엇으로 저장하는가"다. 이미 일어난 일의 시각은 시점이므로 시간대에 흔들리지 않는 형태로 남기는 것이 기본이다. LocalDateTime으로 저장해도 문제가 없으려면 서버의 기본 시간대, 데이터베이스 세션의 시간대, 사용자의 시간대가 모두 같고 앞으로도 같다는 가정이 필요하다. 이 가정은 서버를 다른 환경으로 옮기거나, 기본 시간대가 다른 실행 환경에 배포하거나, 다른 지역의 사용자를 받는 순간에 깨진다. 가정이 깨졌을 때 이미 저장된 값에는 어느 시간대 기준이었는지가 남아 있지 않으므로 사후에 바로잡기가 어렵다. 가정을 유지하기로 했다면 적어도 그 가정을 설정과 코드에 명시해 두어야 한다(LocalDate.now(zone)처럼 시간대를 인자로 드러내는 식으로).

    일정과 반복 작업에서는 판단이 달라진다. 미래의 약속은 지역 날짜·시각과 시간대 식별자로 보관하고, 실행할 때 시점을 계산한다. 일광 절약 시간을 쓰는 지역이 대상에 들어 있으면 "매일 같은 벽시계 시각"과 "24시간마다"가 다른 요구사항이 되고, 전환일에는 지정한 시각이 없거나 두 번 온다. 어느 쪽 동작을 원하는지는 기술이 아니라 업무가 정할 문제이므로, 코드를 쓰기 전에 물어서 정해 두어야 한다. 월 단위 반복(정기 결제일, 말일 마감)은 직전 날짜에 한 달씩 누적해서 더하지 말고 기준일에서 n개월을 한 번에 더한다.

    입력과 출력의 경계에서는 포맷터의 기본 동작을 알고 있어야 한다. 직접 만든 패턴은 기본적으로 SMART로 해석되어 없는 날짜를 조용히 보정하므로, 사용자 입력을 검증하는 용도라면 uuuu와 STRICT를 함께 쓴다. YYYY처럼 일 년에 며칠만 틀리는 패턴은 평소의 테스트로는 잡히지 않는다. 시간에 의존하는 로직은 Clock을 주입받게 만들어 연말, 월말, 윤년의 2월 29일, 전환일 같은 경계 시각을 고정해 놓고 테스트한다. 마지막으로 시간대 규칙은 데이터라는 점을 기억한다. 규칙이 바뀐 지역을 다루는 서비스라면 JDK에 실린 시간대 데이터의 버전도 관리 대상이다.

LocalDateTime은 가변 객체라서 변환하는 도중에 값이 바뀔 수 있기 때문이다. LocalDateTime은 JVM 기본 시간대를 내부에 저장하고 있어서 다른 시간대로 바꿀 수 없기 때문이다. 정답은 두 번째다. LocalDateTime은 LocalDate와 LocalTime에 대한 참조만 갖고, 그 안에는 달력과 벽시계의 숫자뿐이다. 같은 값이 서울에서는 00:00Z, 뉴욕에서는 14:00Z가 된다. 두 타입 모두 나노초까지 표현하므로 첫 번째는 틀렸고, java.time의 클래스는 모두 불변이므로 세 번째도 틀렸다. 네 번째는 반대다. 기본 시간대는 now()를 계산할 때 쓰일 뿐 객체에 저장되지 않는다. 서울의 ZonedDateTime a(2024-01-01T09:00+09:00)와 b = a.withZoneSameInstant(ZoneId.of("America/New_York"))에 대한 설명으로 옳은 것은? a.equals(b)와 a.isEqual(b)가 모두 true다. 같은 순간이기 때문이다. a.equals(b)와 a.isEqual(b)가 모두 false다. 벽시계 숫자가 다르기 때문이다. a.equals(b)는 false, a.isEqual(b)는 true다. equals는 지역 날짜·시각, 오프셋, 시간대를 모두 비교하고 isEqual은 시점을 비교하기 때문이다. a.equals(b)는 true, a.isEqual(b)는 false다. isEqual은 시간대까지 비교하기 때문이다. 정답은 세 번째다. withZoneSameInstant는 시점을 유지한 채 시간대를 바꾸므로 두 객체의 toInstant()는 같고 isEqual은 true다. 그러나 b의 필드는 2023-12-31T19:00, -05:00, America/New_York으로 a와 모두 다르므로 equals는 false다. 해시 기반 컬렉션의 키로 쓸 때 같은 순간이 다른 키가 되는 이유이기도 하다. 뉴욕의 2024-03-09T12:00에 Period.ofDays(1)을 더하면 다음 날 12:00이 되고 Duration.ofDays(1)을 더하면 다음 날 13:00이 된다. 이 차이를 가장 잘 설명한 것은? Period의 하루는 지역 시간선에서 날짜를 한 칸 넘긴 뒤 오프셋을 다시 구하는 것이고, Duration의 하루는 시간선에서 86,400초를 나아가는 것인데, 그날 밤 뉴욕의 벽시계가 한 시간을 건너뛰기 때문이다. Duration은 윤초를 반영하고 Period는 반영하지 않기 때문이다. Duration.ofDays(1)은 내부적으로 25시간으로 저장되기 때문이다. Period는 ZonedDateTime에 더할 수 없어서 내부적으로 LocalDateTime으로 바꾼 뒤 시간대를 버리기 때문이다. 정답은 첫 번째다. ZonedDateTime.plus는 날짜 기반 단위를 지역 날짜·시각에 더한 뒤 규칙으로 오프셋을 다시 해석하고, 시간 기반 단위는 시점 기준으로 계산한다. 3월 10일 새벽의 gap 때문에 정오에서 정오까지가 23시간이라 24시간 뒤는 13:00이다. 자바 시간 척도에는 윤초가 드러나지 않으므로 두 번째는 틀렸고, Duration.ofDays(1)은 86,400초(PT24H)이므로 세 번째도 틀렸다. Period는 ZonedDateTime에 더할 수 있고 결과에도 시간대가 유지된다. LocalDate.of(2024, 1, 1).get(ChronoField.HOUR_OF_DAY)는 컴파일되지만 실행하면 UnsupportedTemporalTypeException이 난다. 컴파일 오류가 아닌 이유는? 자바 컴파일러는 열거형 상수를 인자로 넘기는 호출의 타입을 검사하지 않기 때문이다. LocalDate가 내부적으로 시각 필드도 갖고 있지만 값이 비어 있기 때문이다. 예외가 체크 예외라서 컴파일러가 실행 시점으로 검사를 미루기 때문이다. get의 매개변수 타입이 인터페이스 TemporalField이고 ChronoField.HOUR_OF_DAY는 그 타입에 맞으므로 타입 검사는 통과하며, 그 필드를 지원하는지는 LocalDate의 코드가 실행 중에 판단하기 때문이다. 정답은 네 번째다. 컴파일러는 인자가 매개변수 타입에 대입 가능한지만 본다. 어떤 필드를 지원하는지는 타입 시스템에 표현되어 있지 않고 각 클래스의 구현 안에 있다. 그래서 isSupported(field)가 따로 있고, 타입을 아는 코드에서는 getYear() 같은 전용 메서드를 쓰는 편이 안전하다. LocalDate의 필드는 연·월·일뿐이고, 이 예외는 RuntimeException 계열이다. LocalDate.parse("2024-02-30", DateTimeFormatter.ofPattern("yyyy-MM-dd"))의 결과와 그 이유로 옳은 것은? DateTimeParseException이 난다. 2월 30일은 없는 날짜이고 파서는 언제나 엄격하게 검사하기 때문이다. 2024-02-29가 나온다. ofPattern으로 만든 포맷터의 기본 해석 방식이 SMART이고, 이 방식은 1~31 범위의 일을 그 달의 마지막 유효한 날로 보정하기 때문이다. 2024-03-01이 나온다. 넘친 하루를 다음 달로 넘기기 때문이다. 2024-02-30이라는 값을 가진 LocalDate가 만들어진다. 파싱은 형식만 확인하기 때문이다. 정답은 두 번째다. 파싱은 텍스트를 필드 표로 읽는 단계와 그것을 실제 날짜로 해석하는 단계로 나뉘고, 해석의 엄격함은 ResolverStyle이 정한다. 예외를 원하면 uuuu 패턴에 STRICT를 붙인다. 3월 1일로 넘기는 것은 LENIENT의 동작이다. LocalDate는 생성 시 검증하므로 달력에 없는 날짜를 값으로 가질 수 없다.
    시점(instant)
    전 세계가 공유하는 시간선 위의 한 점. 자바에서는 Instant가 에포크로부터의 초와 나노초로 표현한다.
    에포크(epoch)
    시점을 세는 기준점. 자바에서는 1970-01-01T00:00:00Z다.
    협정 세계시(UTC)
    각 지역 시각의 기준이 되는 시각. 오프셋은 UTC와의 차이로 표시한다.
    오프셋(offset)
    지역의 벽시계가 UTC보다 얼마나 앞서거나 뒤처지는지를 나타내는 값. ZoneOffset은 이를 초 단위 정수로 든다.
    시간대(time zone)
    Asia/Seoul처럼 지역을 가리키는 식별자와, 그 지역이 시점마다 어느 오프셋을 쓰는지 정한 규칙의 묶음. ZoneId와 ZoneRules가 표현한다.
    일광 절약 시간(DST, Daylight Saving Time)
    한 해의 일정 기간 동안 벽시계를 앞당겨 쓰는 제도. 시작과 끝에서 오프셋이 바뀐다.
    gap과 overlap
    오프셋이 바뀌는 순간 지역 시간선에 생기는 불연속. gap은 벽시계에 존재하지 않는 구간이고 overlap은 두 번 나타나는 구간이다.
    값 기반 클래스(value-based class)
    필드 값만으로 동등성이 정해지고, equals로 같은 인스턴스끼리 바꿔 써도 되는 것으로 취급해야 하는 클래스. == 비교나 동기화의 잠금 대상으로 쓰지 않는다.
    자바 시간 척도(Java Time-Scale)
    java.time이 정의한 시간 척도. 모든 날을 정확히 86,400초로 나누어 윤초가 드러나지 않게 한다.
    해석 방식(ResolverStyle)
    파싱으로 읽은 필드 값들을 실제 날짜·시각으로 조립할 때의 엄격함. STRICT, SMART, LENIENT가 있다.
