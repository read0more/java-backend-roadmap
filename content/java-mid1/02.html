    값을 건넸을 뿐인데 남의 값이 바뀌었다

    회원 두 명이 가입했고, 두 사람의 지갑에 가입 축하금 1,000원을 넣어 주었다. 그 뒤 한 사람이 5,000원을 입금했다. 잔액을 출력해 보니 두 사람 모두 6,000원이다. 입금하는 코드에는 잘못이 없고, 지갑을 만드는 코드에도 눈에 띄는 잘못이 없다. 그런데 결과는 틀렸다.

    이런 버그는 어느 한 줄이 틀려서 생기지 않는다. 서로 떨어진 두 곳의 코드가 같은 객체를 가리키고 있었고, 그중 한 곳이 그 객체를 고쳤기 때문에 생긴다. 틀린 줄을 찾으려고 하면 찾을 수 없고, "누가 누구와 무엇을 함께 쓰고 있는가"를 물어야 보인다. 프로그램이 커질수록 이 질문에 답하기가 어려워진다.

    이 회차는 네 가지 질문에 차례로 답한다. 첫째, 이런 일은 왜 int에서는 일어나지 않고 객체에서만 일어나는가. 둘째, 막는 방법에는 무엇이 있고 그 가운데 컴파일러가 강제해 주는 것은 어느 쪽인가. 셋째, 내용을 바꿀 수 없는 객체만 가지고 값이 변하는 프로그램을 어떻게 작성하는가. 넷째, "바꿀 수 없다"는 약속은 컴파일러와 JVM의 어느 층이 어디까지 지켜 주며, 그 대가는 무엇인가.

    출발점은 자바 기본편에서 배운 두 가지다. 기본형과 참조형 회차에서 변수에는 값이 하나 들어 있고 참조형 변수의 값은 객체의 위치를 가리키는 참조값이라는 것을 배웠다. final 회차에서는 final 참조 변수가 고정하는 것은 참조값이지 객체의 내용이 아니라는 것을 보았고, 객체의 내용을 고정하는 방법은 중급 과정으로 미뤄 두었다. 이 회차가 그 미뤄 둔 부분이다.

    기본형과 참조형의 공유: 대입이 복사하는 것

    자바의 대입문 b = a가 하는 일은 타입과 관계없이 하나다. 변수 a에 들어 있는 값을 복사해 b에 넣는다. 결과가 달라지는 것은 그 "들어 있는 값"이 타입에 따라 다르기 때문이다. 기본형 변수에는 1000 같은 값 자체가 들어 있고, 참조형 변수에는 객체가 아니라 객체를 가리키는 참조값이 들어 있다. JLS §4.3.1은 참조값을 객체에 대한 포인터라고 정의한다.

    class Money {
    int amount;

    Money(int amount) {
        this.amount = amount;
    }
}

public class ShareMain {
    public static void main(String[] args) {
        int a = 1000;
        int b = a;          // 값 1000을 복사한다
        b = 3000;
        System.out.println("a = " + a + ", b = " + b);

        Money m1 = new Money(1000);
        Money m2 = m1;      // 참조값을 복사한다
        m2.amount = 3000;
        System.out.println("m1 = " + m1.amount + ", m2 = " + m2.amount);
        System.out.println(m1 == m2);
    }
}
    a = 1000, b = 3000
m1 = 3000, m2 = 3000
true

    b를 바꿔도 a는 그대로인데, m2를 통해 바꾼 값은 m1으로도 보인다. 두 경우에 컴파일러가 만든 코드를 javap -c ShareMain으로 꺼내 나란히 놓으면 무엇이 같고 무엇이 다른지가 드러난다. main은 static 메서드이므로 지역 변수 배열의 0번 칸에는 args가 있고, a, b, m1, m2가 차례로 1~4번 칸을 쓴다.

    int b = a는 iload_1과 istore_2 두 명령이고, Money m2 = m1은 aload_3과 astore 4 두 명령이다. 접두사 i는 int, a는 참조를 뜻할 뿐 두 쌍이 하는 일은 같다. 지역 변수 칸 하나의 내용을 피연산자 스택에 올렸다가 다른 칸에 내려놓는다. 주목할 것은 없는 명령이다. 객체를 복제하는 명령은 어디에도 없고, new는 23번에 한 번만 나온다. 힙에 만들어진 Money 객체는 하나뿐이고, 그 객체를 가리키는 참조값이 두 칸에 들어 있다.

    그다음 줄에서 차이가 난다. b = 3000은 istore_2로 2번 칸의 내용을 바꾼다. 다른 칸에는 영향이 없다. m2.amount = 3000은 4번 칸을 바꾸지 않는다. aload 4로 4번 칸의 참조값을 꺼낸 다음 putfield로 그 참조값이 가리키는 힙의 객체에 쓴다. 변수를 바꾸는 것과 변수가 가리키는 객체를 바꾸는 것은 서로 다른 연산이다. 3번 칸의 m1도 같은 객체를 가리키므로 m1.amount를 읽으면 바뀐 값이 나온다.

    명세도 이 차이를 직접 적어 둔다. JLS §4.2는 기본형 값이 다른 기본형 값과 상태를 공유하지 않는다고 하고, §4.3.1은 같은 객체에 대한 참조가 여럿 있을 수 있으며 두 변수가 같은 객체의 참조를 담고 있으면 한 변수를 통해 수정한 상태를 다른 변수를 통해 관찰할 수 있다고 한다. 같은 객체를 가리키는 참조가 둘 이상 있는 상태를 흔히 별칭(aliasing)이라고 부른다.

    여기서 두 가지 사실이 나온다. 첫째, 기본형은 공유할 방법이 없다. 자바에는 변수의 주소를 얻는 연산자가 없으므로 두 기본형 변수가 같은 저장 공간을 가리키게 만들 수 없다. 둘째, 참조형은 대입하면 반드시 공유가 된다. 객체를 복제해서 넣어 주는 대입 문법은 없다. 복제가 필요하면 new로 새 객체를 만드는 코드를 직접 써야 한다. JLS §4.3.1의 정의대로 배열도 객체이므로 int[] b = a 역시 배열 하나를 두 변수가 함께 가리키게 한다.

    기본형 대입 뒤에는 두 변수가 서로 독립된 값을 갖고, 참조형 대입 뒤에는 두 변수가 힙의 객체 하나를 함께 가리킨다는 대비를 좌우로 보여 준다. 흰 배경의 좌우 2분할 다이어그램. 왼쪽 패널의 머리 라벨은 "기본형: int b = a". 그 아래에 나란한 상자 두 개가 있고 왼쪽 상자에는 변수 이름 "a"와 값 "1000", 오른쪽 상자에는 변수 이름 "b"와 값 "3000". a 상자에서 b 상자로 향하는 점선 화살표 위에 라벨 "값 복사". 두 상자 아래에 작은 글씨 "서로 독립". 오른쪽 패널의 머리 라벨은 "참조형: Money m2 = m1". 왼편에 위아래로 놓인 상자 두 개가 있고 위 상자에는 "m1"과 값 "x001", 아래 상자에는 "m2"와 값 "x001". 두 상자 사이에 아래로 향하는 점선 화살표와 라벨 "참조값 복사". 오른편에는 둥근 모서리의 큰 상자 하나가 있고 제목 "Money 객체 x001", 안에 필드 칸 "amount = 3000". m1 상자와 m2 상자에서 각각 실선 화살표가 나와 같은 Money 객체를 가리킨다. 객체 아래에 작은 글씨 "객체는 하나". 왼쪽 패널은 옅은 주황, 오른쪽 패널은 옅은 파랑 배경. 얇은 선, 고딕체, 한국어 라벨은 따옴표 안의 문구 그대로. 대입은 언제나 변수에 든 값을 복사한다. 기본형은 값이 복사되어 따로 놀고, 참조형은 참조값이 복사되어 같은 객체를 함께 쓴다.

    공유 참조와 사이드 이펙트

    사이드 이펙트(side effect, 부수 효과)는 어떤 연산이 자기가 맡은 결과 말고 다른 곳의 상태까지 바꾸는 것을 가리킨다. 넓은 뜻으로는 필드에 값을 쓰는 것도, 화면에 출력하는 것도 사이드 이펙트다. 문제가 되는 것은 그 가운데 의도하지 않은 것, 즉 한 곳을 고치려고 한 변경이 고칠 생각이 없던 다른 곳에서도 관찰되는 경우다. 공유 참조가 바로 그 통로가 된다.

    도입부의 지갑 이야기를 코드로 옮긴다. Money는 금액 하나를 담는 클래스이고 값을 바꾸는 setAmount가 있다. Wallet은 소유자 이름과 잔액을 가진다.

    class Money {
    private int amount;

    Money(int amount) { this.amount = amount; }

    int getAmount() { return amount; }
    void setAmount(int amount) { this.amount = amount; }
}

class Wallet {
    private final String owner;
    private Money balance;

    Wallet(String owner, Money balance) {
        this.owner = owner;
        this.balance = balance;          // 받은 참조값을 그대로 필드에 넣는다
    }

    void deposit(int amount) {
        balance.setAmount(balance.getAmount() + amount);
    }

    @Override
    public String toString() {
        return owner + ": " + balance.getAmount();
    }
}

public class WalletMain {
    public static void main(String[] args) {
        Money welcome = new Money(1000);             // 가입 축하금
        Wallet kim = new Wallet("kim", welcome);
        Wallet lee = new Wallet("lee", welcome);
        System.out.println(kim);
        System.out.println(lee);

        kim.deposit(5000);
        System.out.println(kim);
        System.out.println(lee);
        System.out.println(welcome.getAmount());
    }
}

    kim만 입금했는데 lee의 잔액도, 축하금으로 쓰려던 welcome도 6,000이 되었다. 참조값을 x001처럼 적어 한 줄씩 따라가 보자. new가 실행된 것은 Money에 대해 한 번, Wallet에 대해 두 번이다. Money 객체는 처음부터 끝까지 하나다.

    이 버그가 찾기 어려운 이유를 구조에서 읽을 수 있다. 공유가 만들어진 곳은 main의 생성자 호출이고, 객체가 고쳐진 곳은 Wallet.deposit이며, 증상이 보이는 곳은 lee의 잔액을 출력하는 줄이다. 세 지점이 서로 다른 위치에 있고, 각 줄은 따로 떼어 보면 타당하다. 지갑을 하나만 만드는 테스트로는 드러나지도 않는다. 실제 프로그램에서는 이 세 지점이 서로 다른 클래스, 서로 다른 시각에 놓인다.

    지갑 객체는 둘이지만 잔액을 담은 Money 객체는 하나이고, 한 지갑을 통해 고친 값이 다른 지갑과 원래 변수에서도 보인다는 것을 화살표의 합류로 보여 준다. 흰 배경의 메모리 구조 다이어그램. 왼쪽에 세로로 긴 상자 "스택"이 있고 안에 칸 세 개가 위에서 아래로: "welcome", "kim", "lee". 가운데에는 둥근 모서리 상자 두 개가 위아래로 놓인다. 위 상자 제목 "Wallet (kim)", 안에 칸 "balance". 아래 상자 제목 "Wallet (lee)", 안에 칸 "balance". 오른쪽에는 굵은 테두리의 둥근 상자 하나, 제목 "Money 객체", 안에 값 칸 "amount = 6000"이 주황색으로 강조되어 있다. 스택의 "kim" 칸에서 위 Wallet 상자로, "lee" 칸에서 아래 Wallet 상자로 가는 얇은 화살표. 두 Wallet의 "balance" 칸에서 각각 화살표가 나와 오른쪽의 같은 Money 객체로 모인다. 스택의 "welcome" 칸에서도 화살표가 나와 같은 Money 객체를 가리킨다. 위 Wallet에서 Money로 가는 화살표 위에 라벨 "deposit(5000)으로 수정". 아래 Wallet에서 Money로 가는 화살표 위에 라벨 "같은 값을 읽음". Money 객체 아래에 작은 글씨 "객체는 하나, 참조는 셋". 색은 남색, 주황, 회색만 사용. 얇은 선, 고딕체, 한국어 라벨은 따옴표 안의 문구 그대로. 지갑은 둘이지만 잔액 객체는 하나다. 세 개의 참조 가운데 어느 것으로 고쳐도 나머지 둘이 그 변경을 본다.

    공유가 만들어지는 다른 경로들

    공유는 b = a 같은 대입문에서만 생기지 않는다. 참조값이 복사되는 모든 지점에서 생긴다. 위 예제에서 공유를 만든 것도 대입문이 아니라 생성자 호출과 필드 저장이었다.

    경로코드의 모양참조값이 복사되는 곳
    변수 대입Money b = a;변수에서 변수로
    인자 전달pay(a);호출한 쪽의 변수에서 매개변수로
    반환return balance;필드나 지역 변수에서 호출한 쪽으로
    필드 저장this.balance = balance;매개변수에서 객체의 필드로
    배열·컬렉션에 넣기list.add(a);변수에서 배열의 칸이나 컬렉션 내부로

    인자로 받은 객체를 "계산에 잠깐 쓰려고" 고치는 코드도 같은 문제를 일으킨다. 아래 withFee는 수수료를 더한 금액을 돌려주려는 메서드인데, 받은 객체를 직접 고쳐서 돌려준다.

    public class FeeMain {
    static Money withFee(Money base) {
        base.setAmount(base.getAmount() + 300);   // 받은 인자를 직접 고친다
        return base;
    }

    public static void main(String[] args) {
        Money price = new Money(5000);            // 앞의 가변 Money
        Money total = withFee(price);
        System.out.println(price.getAmount() + " " + total.getAmount() + " " + (price == total));
    }
}

    호출한 쪽은 원래 가격 5,000원과 수수료 포함 가격 5,300원을 둘 다 갖고 있다고 생각하지만, price와 total은 같은 객체다. 인자 전달로 참조값이 base에 복사되었고, 반환으로 같은 참조값이 total에 복사되었다. 메서드 시그니처 Money withFee(Money)만 보아서는 이 메서드가 인자를 고치는지 알 수 없다. 가변 객체를 주고받는 코드에서는 모든 메서드에 대해 "이 메서드가 내 객체를 고치는가"를 따로 확인해야 한다.

    첫 번째 해법: 공유하지 않기와 그 한계

    가장 먼저 떠오르는 해법은 공유하지 않는 것이다. 지갑마다 new Money(1000)을 따로 만들어 넘기면 객체가 둘이 되므로 문제가 사라진다. 하지만 이것은 호출하는 쪽이 조심해야 하는 방법이다. Wallet을 쓰는 모든 코드가 그 규칙을 알고 지켜야 한다. 받는 쪽에서 스스로 지키려면 받은 객체를 복사해서 보관한다. 이것을 방어적 복사(defensive copy)라고 한다.

    class Wallet {
    private final String owner;
    private Money balance;

    Wallet(String owner, Money balance) {
        this.owner = owner;
        this.balance = new Money(balance.getAmount());   // 받은 객체를 복사해서 보관한다
    }

    void deposit(int amount) {
        balance.setAmount(balance.getAmount() + amount);
    }

    Money getBalance() {
        return balance;                                  // 내부 객체의 참조값을 그대로 내준다
    }

    @Override
    public String toString() {
        return owner + ": " + balance.getAmount();
    }
}

public class WalletMain {
    public static void main(String[] args) {
        Money welcome = new Money(1000);                 // 앞의 가변 Money
        Wallet kim = new Wallet("kim", welcome);
        Wallet lee = new Wallet("lee", welcome);
        kim.deposit(5000);
        System.out.println(kim);
        System.out.println(lee);

        Money peek = lee.getBalance();
        peek.setAmount(0);
        System.out.println(lee);
    }
}
    kim: 6000
lee: 1000
lee: 0

    생성자에서 복사했으므로 두 지갑은 각자의 Money 객체를 가진다. kim의 입금이 lee에게 보이지 않는다. 그런데 한 곳을 막자 다른 곳이 드러난다. getBalance()가 내부 객체의 참조값을 그대로 돌려주므로, 잔액을 조회만 하려던 코드가 setAmount(0)으로 지갑의 잔액을 0으로 만들 수 있다. deposit을 거치지 않고 잔액이 바뀐 것이다. 이것도 막으려면 getBalance()에서 다시 복사본을 만들어 돌려줘야 한다.

    방어적 복사에는 구조적인 한계가 있다.

    • 언어가 강제하지 않는다. this.balance = balance는 언제나 컴파일된다. 복사를 빠뜨려도 컴파일러는 아무 말도 하지 않고, 테스트가 그 경로를 우연히 밟아야 드러난다.
    • 경계마다 반복해야 한다. 객체가 들어오는 곳(생성자, setter)과 나가는 곳(getter) 모두에서 복사해야 한다. 한 곳이라도 빠지면 거기로 공유가 샌다.
    • 책임이 흩어진다. 넘기는 쪽은 받는 쪽이 복사했으리라 여기고, 받는 쪽은 넘기는 쪽이 새 객체를 주었으리라 여기기 쉽다. Money를 쓰는 클래스가 열 개면 열 곳에서 같은 판단을 반복한다.
    • 필요 없는 복사도 해야 한다. 상대가 객체를 고치는지 알 수 없으므로, 실제로는 아무도 고치지 않는 경우에도 복사한다.

    원인을 다시 본다: 공유와 변경

    사이드 이펙트가 생기려면 두 조건이 함께 있어야 한다. 같은 객체를 둘 이상의 곳에서 가리키고(공유), 그 가운데 누군가가 객체를 고친다(변경). 어느 한쪽만 없어도 문제가 없다.

    객체를 고치지 않는다객체를 고친다
    공유하지 않는다안전하다안전하다. 변경을 보는 곳이 한 곳뿐이다
    공유한다안전하다. 누가 읽어도 같은 값이다의도하지 않은 사이드 이펙트가 생길 수 있다

    방어적 복사는 표의 아래 행에서 위 행으로 옮겨 가려는 시도다. 그런데 앞에서 보았듯 자바에서 참조형 대입은 곧 공유이고, 그것을 금지하는 문법은 없다. 공유는 언어 수준에서 막을 수 없다. 반면 변경은 막을 수 있다. 객체를 고치는 수단은 그 클래스가 제공하는 것이 전부이므로, 클래스가 고치는 수단을 하나도 제공하지 않으면 누구도 그 객체를 고칠 수 없다. 표의 오른쪽 열을 없애는 것이다. 고칠 곳은 사용하는 코드 전부가 아니라 클래스 정의 한 곳이다.

    일상에서 가져온 비유편집 권한이 있는 공유 문서와 인쇄된 공지문

    편집 권한이 있는 문서 링크를 열 사람에게 보내면, 한 사람이 고친 내용이 나머지 아홉 사람의 화면에서도 바뀐다. 사고를 막으려면 사람마다 사본을 만들어 주거나(방어적 복사), 문서를 읽기 전용으로 바꾸면 된다(불변). 읽기 전용 문서는 몇 명에게 링크를 보내든 걱정할 것이 없고, 내용을 바꿔야 하면 새 문서를 만들어 새 링크를 준다. 이 비유가 맞지 않는 지점도 있다. 문서의 읽기 전용 설정은 관리자가 나중에 풀 수 있지만, 불변 클래스의 객체는 만들어진 뒤에 가변으로 되돌릴 수 없다.

    불변 객체 도입: 정의와 만드는 규칙

    불변 객체(immutable object)는 생성된 뒤에 상태가 바뀌지 않는 객체다. 상태가 바뀔 수 있는 객체는 가변 객체(mutable object)라고 한다. 지금까지의 Money는 setAmount가 있으므로 가변이다. 불변으로 고친다.

    final class Money {
    private final int amount;

    Money(int amount) {
        this.amount = amount;
    }

    int amount() {
        return amount;
    }

    @Override
    public String toString() {
        return amount + "원";
    }
}

    바뀐 것은 세 가지다. 필드에 final이 붙었고, setAmount가 사라졌고, 클래스에 final이 붙었다. 접근자의 이름을 getAmount에서 amount로 바꾼 것과 출력에 쓰려고 toString을 넣은 것은 불변성과 관계가 없다. Oracle의 Java Tutorials는 불변 객체를 정의하는 간단한 전략으로 다음 네 가지 규칙을 든다.

    1. setter를 제공하지 않는다. 필드를 고치거나 필드가 가리키는 객체를 고치는 메서드를 두지 않는다.
    2. 모든 필드를 final이고 private으로 만든다.
    3. 하위 클래스가 메서드를 재정의하지 못하게 한다. 가장 간단한 방법은 클래스를 final로 선언하는 것이다. 생성자를 private으로 두고 팩터리 메서드에서 객체를 만드는 방법도 있다.
    4. 필드가 가변 객체를 가리킨다면 그 객체가 바뀌지 않게 한다. 그 객체를 고치는 메서드를 두지 않고, 그 객체의 참조를 밖과 공유하지 않는다. 생성자로 받은 가변 객체는 복사해서 보관하고, 내부의 가변 객체를 돌려줄 때는 복사본을 돌려준다.

    지금의 Money는 필드가 int 하나뿐이어서 1~3번만으로 충분하다. 4번이 필요한 경우와 3번이 필요한 이유는 뒤에서 따로 다룬다. 먼저 2번이 실제로 무엇을 막는지 확인한다. 불변 Money에 setter를 다시 넣으면 컴파일러가 거부한다.

    void setAmount(int amount) {
    this.amount = amount;       // 컴파일 오류
}
    error: cannot assign a value to final variable amount

    자바 기본편의 final 회차에서 본 대로 final 인스턴스 필드는 선언, 인스턴스 초기화 블록, 생성자에서 한 번만 대입할 수 있다. 메서드는 그 어느 것도 아니므로 대입할 수 없다. 1번 규칙(setter를 두지 않는다)은 사람이 지키는 약속이지만, 2번 규칙이 있으면 그 약속을 컴파일러가 대신 지킨다. 나중에 누군가 이 클래스에 메서드를 추가하면서 무심코 필드를 고치려 해도 컴파일이 되지 않는다.

    private도 함께 요구하는 이유는 필드가 참조형일 때 분명해진다. final은 필드에 든 참조값을 고정할 뿐이므로, 필드가 배열이나 리스트를 가리키고 그 필드가 밖에서 보이면 누구든 그 배열이나 리스트의 내용을 고칠 수 있다. 필드를 감추고 접근자를 통해서만 값을 내주어야 무엇을 내줄지를 클래스가 정할 수 있다.

    불변의 기준은 "모든 필드에 final이 붙었는가"가 아니라 "밖에서 관찰할 수 있는 상태가 변하지 않는가"다. 같은 튜토리얼도 불변으로 문서화된 클래스가 모두 이 규칙을 따르는 것은 아니며, 그런 설계에는 정교한 분석이 필요하다고 덧붙인다. 다음 회차에서 보는 String의 해시코드 캐시가 그런 예다. 직접 만드는 클래스에서는 네 규칙을 그대로 따르는 것이 안전하다.

    불변 객체 예제: 같은 객체를 공유해도 안전하다

    Money를 불변으로 바꾸면 처음의 Wallet은 컴파일되지 않는다. deposit이 부르던 setAmount가 더 이상 없기 때문이다. 객체를 고칠 수 없으니, 잔액을 바꾸려면 새 금액을 담은 새 Money 객체를 만들어 balance 필드가 그 객체를 가리키게 해야 한다. 생성자에서 하던 방어적 복사는 지우고, 처음처럼 받은 참조값을 그대로 보관한다.

    class Wallet {
    private final String owner;
    private Money balance;

    Wallet(String owner, Money balance) {
        this.owner = owner;
        this.balance = balance;                           // 복사하지 않는다
    }

    void deposit(int amount) {
        balance = new Money(balance.amount() + amount);   // 고치지 않고 새로 만든다
    }

    @Override
    public String toString() {
        return owner + ": " + balance;
    }
}

public class WalletMain {
    public static void main(String[] args) {
        Money welcome = new Money(1000);                  // 불변 Money
        Wallet kim = new Wallet("kim", welcome);
        Wallet lee = new Wallet("lee", welcome);          // 여전히 같은 객체를 공유한다

        kim.deposit(5000);
        System.out.println(kim);
        System.out.println(lee);
        System.out.println(welcome);
    }
}

    deposit은 x001에서 1000을 읽기만 하고, 6000을 담은 새 객체 x004를 만든 뒤 kim의 balance 필드에 든 참조값을 x004로 바꾼다. x001 객체에는 쓰기가 한 번도 일어나지 않는다. 그래서 x001을 가리키는 lee.balance와 welcome은 아무 영향을 받지 않는다. "객체의 내용을 고친다"가 "변수가 가리키는 객체를 바꾼다"로 바뀌었고, 그 변경이 보이는 범위는 kim의 지갑에 있는 필드 하나로 줄었다.

    Wallet 자체는 여전히 가변이다. balance 필드에 다른 참조값을 넣을 수 있기 때문이다. 이것은 결함이 아니다. 지갑은 시간이 지나며 잔액이 달라지는 대상이고, 같은 지갑을 가리키는 두 변수는 같은 잔액을 보는 것이 맞다. 반면 1,000원이라는 금액은 값이다. 값은 "1,000원이 6,000원으로 변한다"기보다 "1,000원 대신 6,000원을 쓴다"고 하는 편이 자연스럽다. 불변으로 만들 대상은 대개 이런 값을 표현하는 클래스다.

    입금 전에는 세 참조가 한 객체를 공유하고, 입금 후에는 kim의 참조만 새 객체로 옮겨 가며 원래 객체는 그대로라는 것을 전후 두 장면으로 보여 준다. 흰 배경에 좌우 두 패널. 왼쪽 패널 머리 라벨 "입금 전", 오른쪽 패널 머리 라벨 "입금 후". 두 패널 사이에 오른쪽 방향 굵은 화살표와 라벨 "kim.deposit(5000)". 왼쪽 패널: 왼편에 세로로 놓인 작은 상자 세 개 "kim.balance", "lee.balance", "welcome". 오른편에 둥근 모서리 상자 하나, 제목 "Money", 안에 "amount = 1000", 상자 모서리에 잠긴 자물쇠 아이콘. 세 작은 상자에서 나온 화살표 세 개가 모두 이 Money 상자를 가리킨다. 오른쪽 패널: 같은 작은 상자 세 개. 오른편에 Money 상자가 위아래로 두 개. 위 상자는 주황색 테두리, 제목 "Money (새 객체)", 안에 "amount = 6000", 자물쇠 아이콘. 아래 상자는 남색 테두리, 제목 "Money", 안에 "amount = 1000", 자물쇠 아이콘, 옆에 작은 글씨 "그대로". "kim.balance"에서 나온 화살표는 위의 새 객체를, "lee.balance"와 "welcome"에서 나온 화살표는 아래의 원래 객체를 가리킨다. 색은 남색, 주황, 회색만 사용. 얇은 선, 고딕체, 한국어 라벨은 따옴표 안의 문구 그대로. 불변 객체에서 "값을 바꾼다"는 것은 새 객체를 만들고 참조를 옮기는 일이다. 원래 객체를 가리키던 다른 참조는 영향을 받지 않는다.

    불변 객체의 값 변경: 새 객체를 돌려주는 메서드

    앞의 deposit은 new Money(balance.amount() + amount)라는 계산을 Wallet이 직접 했다. 금액에 금액을 더하는 일은 Money가 알아야 할 일이고, Money를 쓰는 다른 클래스도 같은 계산이 필요하다. 그 계산을 Money의 메서드로 옮긴다. 가변 클래스였다면 자기 필드를 고치고 끝났겠지만, 불변 클래스의 메서드는 자기 필드를 고칠 수 없으므로 결과를 담은 새 객체를 만들어 반환한다.

    final class Money {
    private final int amount;

    Money(int amount) { this.amount = amount; }

    int amount() { return amount; }

    Money plus(int delta) {
        return new Money(amount + delta);     // 자신은 그대로 두고 새 객체를 돌려준다
    }

    @Override
    public String toString() { return amount + "원"; }
}

class Wallet {
    private final String owner;
    private Money balance;

    Wallet(String owner, Money balance) {
        this.owner = owner;
        this.balance = balance;
    }

    void deposit(int amount) {
        balance = balance.plus(amount);       // 반환된 새 객체를 필드에 받는다
    }

    void depositWrong(int amount) {
        balance.plus(amount);                 // 반환값을 버린다
    }

    @Override
    public String toString() {
        return owner + ": " + balance;
    }
}

public class WalletMain {
    public static void main(String[] args) {
        Money welcome = new Money(1000);
        Wallet kim = new Wallet("kim", welcome);
        Wallet lee = new Wallet("lee", welcome);

        kim.deposit(5000);
        System.out.println(kim);
        System.out.println(lee);
        System.out.println(welcome);

        lee.depositWrong(700);
        System.out.println(lee);

        Money total = welcome.plus(500).plus(250);
        System.out.println(total + " / " + welcome);
    }
}

    이름으로 구분하기, 그리고 연쇄 호출

    이 실수를 줄이려고 불변 클래스의 값 변경 메서드에는 set으로 시작하는 이름을 피한다. setAmount라는 이름은 이 객체를 고친다는 뜻으로 읽히기 때문이다. JDK의 불변 클래스들도 그렇게 한다. LocalDate의 API 문서는 plusDays를 "지정한 일수를 더한 이 LocalDate의 사본을 반환한다"고, withYear를 "연도를 바꾼 사본을 반환한다"고 설명한다. plus, minus, with로 시작하는 이름은 새 객체가 돌아온다는 신호로 읽으면 된다. 날짜와 시간 클래스는 이 권의 6회에서 다룬다.

    반환 타입이 자기 자신과 같으므로 호출을 이어 쓸 수 있다. welcome.plus(500).plus(250)은 먼저 1,500원 객체를 만들고, 그 객체에 대해 다시 plus(250)을 불러 1,750원 객체를 만든다. 가운데의 1,500원 객체는 다음 호출의 출발점으로 한 번 쓰이고 버려진다. welcome은 끝까지 1,000원이다. 값을 한 번 바꿀 때마다 객체가 하나씩 생긴다는 점은 불변 객체의 비용이며, 뒤에서 따로 살핀다.

    final 필드만으로는 부족하다: 얕은 불변과 깊은 불변

    지금까지의 Money는 필드가 int 하나여서 final만 붙이면 끝났다. 필드가 참조형이면 이야기가 달라진다. final이 고정하는 것은 필드에 든 참조값이고, 그 참조값이 가리키는 객체의 내용은 고정하지 않는다. 필드가 가변 객체를 가리키면, 그 객체에 닿을 수 있는 다른 참조가 하나라도 있는 한 "불변 클래스"의 상태가 밖에서 바뀐다. 네 번째 규칙이 다루는 것이 이 경우다.

    import java.util.ArrayList;
import java.util.List;

final class Roster {                       // 명단
    private final List names;

    Roster(List names) {
        this.names = names;                // 구멍 1: 받은 리스트를 그대로 보관한다
    }

    List names() {
        return names;                      // 구멍 2: 내부 리스트를 그대로 내준다
    }

    int size() {
        return names.size();
    }
}

public class RosterMain {
    public static void main(String[] args) {
        List source = new ArrayList<>();
        source.add("kim");
        source.add("lee");

        Roster roster = new Roster(source);
        System.out.println(roster.size());

        source.add("park");                // 생성자에 넘겼던 원본을 고친다
        System.out.println(roster.size());

        roster.names().clear();            // 접근자로 받은 리스트를 고친다
        System.out.println(roster.size());
        System.out.println(source.size());
    }
}

    구멍은 둘이다. 들어오는 쪽에서는 생성자가 호출한 쪽의 리스트를 그대로 보관했고, 나가는 쪽에서는 접근자가 내부 리스트를 그대로 내주었다. 막는 방법은 앞에서 본 방어적 복사다. 불변 클래스를 만들 때 방어적 복사가 필요한 곳은 이렇게 클래스의 경계 안쪽으로 한정된다. 클래스를 쓰는 쪽은 더 이상 복사를 신경 쓸 필요가 없다.

    final class Roster {
    private final List names;

    Roster(List names) {
        this.names = List.copyOf(names);   // 수정할 수 없는 사본을 만들어 보관한다
    }

    List names() {
        return names;                      // 수정할 수 없는 리스트이므로 그대로 내줘도 된다
    }

    int size() {
        return names.size();
    }
}

public class RosterMain {
    public static void main(String[] args) {
        List source = new ArrayList<>(List.of("kim", "lee"));
        Roster roster = new Roster(source);

        source.add("park");
        System.out.println(roster.size());

        try {
            roster.names().add("choi");
        } catch (UnsupportedOperationException e) {
            System.out.println("UnsupportedOperationException");
        }
    }
}

UnsupportedOperationException

    List.copyOf는 Java 10에 추가된 메서드다. API 문서에 따르면 주어진 컬렉션의 원소를 담은 수정 불가(unmodifiable) 리스트를 반환하고, 주어진 컬렉션이 나중에 수정되어도 반환된 리스트에는 반영되지 않는다. 수정 불가 리스트에 add, remove, clear 같은 변경 메서드를 호출하면 항상 UnsupportedOperationException이 난다. 그래서 들어오는 쪽의 복사 한 번으로 나가는 쪽까지 막힌다. 원소로 null을 허용하지 않아 null이 들어 있으면 NullPointerException이 난다는 점은 알고 써야 한다.

    수정 불가 뷰는 사본이 아니다

    Collections.unmodifiableList도 수정할 수 없는 리스트를 돌려주지만 성격이 다르다. API 문서의 표현은 "지정한 리스트의 수정 불가 뷰(view)"다. 뷰는 원본을 감싼 창이어서, 뷰를 통해서는 고칠 수 없지만 원본을 직접 고치면 그 변경이 뷰로 보인다.

    List base = new ArrayList<>(List.of("a", "b"));
List view = Collections.unmodifiableList(base);   // 원본을 감싼 뷰
List copy = List.copyOf(base);                    // 독립된 사본
base.add("c");
System.out.println(view.size() + " " + copy.size());
    3 2

    생성자에서 Collections.unmodifiableList(names)로 감싸 보관하면 구멍 2는 막히지만 구멍 1은 그대로다. 호출한 쪽이 원본 리스트의 참조를 쥐고 있기 때문이다. 접근자에서 뷰를 돌려주는 것은 괜찮다. 내부 리스트를 고칠 수 있는 참조가 클래스 밖으로 나가지 않기 때문이다. 판단 기준은 하나다. 이 클래스의 상태를 이루는 가변 객체에 닿는 참조를 클래스 바깥의 누군가가 갖고 있는가.

    어디까지 내려가야 불변인가

    수정 불가 리스트로 바꿔도 끝이 아닐 수 있다. List의 API 문서는 수정 불가 리스트에 대해, 담긴 원소 자체가 가변이면 리스트의 내용이 바뀌는 것처럼 보일 수 있다고 적는다. 리스트가 고정하는 것은 "몇 번째 칸이 어느 객체를 가리키는가"이지 그 객체의 내용이 아니다. 위 예에서는 원소가 String이고 String은 불변이므로 여기서 멈춰도 된다. 원소가 가변 클래스의 객체라면 원소까지 복사하거나, 원소의 클래스를 불변으로 만들어야 한다.

    자기 필드만 고정된 상태를 얕은 불변(shallow immutability), 필드에서 참조를 따라 닿을 수 있는 모든 객체가 바뀌지 않는 상태를 깊은 불변(deep immutability)이라고 구분해 부른다. 공유해도 안전하다고 말할 수 있는 것은 깊은 불변일 때다. 실용적인 방법은 불변 클래스의 필드를 기본형, 다른 불변 클래스, 수정 불가 컬렉션(원소도 불변)으로만 구성하는 것이다. 그러면 층마다 따로 따져 볼 필요가 없다.

    배열은 특히 조심해야 한다. 배열에는 수정 불가 버전이 없다. 길이는 고정되지만 원소에는 언제든 대입할 수 있다. 배열 필드를 가진 클래스를 불변으로 만들려면 생성자에서 clone()으로 복사해 보관하고, 접근자에서도 clone()한 배열을 돌려줘야 한다. 들어오는 쪽과 나가는 쪽 양쪽에서 복사가 필요한 것이다.

    final이 잠그는 것은 필드의 참조값(화살표)뿐이고, 화살표 끝의 리스트는 클래스 밖에 남아 있는 참조를 통해 여전히 바뀔 수 있다는 것을 자물쇠의 위치로 보여 준다. 흰 배경의 메모리 구조 다이어그램. 가운데에 둥근 모서리 상자 "Roster 객체"가 있고 안에 필드 칸 "names"가 있다. 필드 칸 옆에 잠긴 자물쇠 아이콘과 라벨 "final: 화살표 고정". 오른쪽에 큰 둥근 상자 "ArrayList"가 있고 안에 가로로 나란한 세 칸 "kim", "lee", "park". 이 상자 옆에는 열린 자물쇠 아이콘과 라벨 "내용은 변경 가능". Roster의 names 칸에서 ArrayList로 가는 굵은 실선 화살표. 왼쪽 위에 작은 상자 "source 변수"가 있고 여기서 나온 주황색 화살표가 Roster를 거치지 않고 곧바로 같은 ArrayList를 가리키며 화살표 위에 라벨 "생성자에 넘긴 원본". 왼쪽 아래에 작은 상자 "names()의 반환값"이 있고 여기서 나온 주황색 화살표도 같은 ArrayList를 가리키며 라벨 "접근자가 내준 참조". Roster 객체 둘레에 점선 테두리와 라벨 "클래스의 경계"가 있고 두 주황색 화살표는 이 점선 바깥에서 출발한다. 색은 남색, 주황, 회색만 사용. 얇은 선, 고딕체, 한국어 라벨은 따옴표 안의 문구 그대로. final 필드는 화살표를 고정할 뿐이다. 화살표 끝의 가변 객체에 닿는 참조가 클래스 밖에 남아 있으면 불변이 아니다.

    하위 클래스라는 세 번째 구멍

    세 번째 규칙, 클래스를 final로 선언하는 이유도 코드로 확인한다. Money에서 클래스의 final만 뗀다. 필드는 여전히 private final이고 setter도 없다.

    class Money {                               // final이 아니다
    private final int amount;

    Money(int amount) { this.amount = amount; }

    int amount() { return amount; }
}

class LooseMoney extends Money {
    int bonus;                              // 가변 필드를 추가한다

    LooseMoney(int amount) { super(amount); }

    @Override
    int amount() { return super.amount() + bonus; }
}

public class SubMain {
    public static void main(String[] args) {
        LooseMoney loose = new LooseMoney(1000);
        Money money = loose;                // Money 타입 변수로 가리킨다
        System.out.println(money.amount());

        loose.bonus = 500;
        System.out.println(money.amount());
    }
}

1500

    Money에 선언된 amount 필드는 여전히 1000이다. 그러나 Money 타입 변수로 amount()를 호출해 얻는 값은 1000에서 1500으로 바뀌었다. 자바 기본편의 다형성 회차에서 본 대로 인스턴스 메서드 호출은 변수의 타입이 아니라 객체의 실제 클래스에 있는 메서드를 실행하기 때문이다. Money 타입의 매개변수를 받는 코드는 넘어온 객체가 Money인지 그 하위 클래스인지 구분하지 않으므로, "Money는 불변"이라는 가정이 타입만으로는 성립하지 않게 된다.

    클래스를 final로 선언하면 하위 클래스를 만들 수 없으므로 이 경로가 닫힌다. 변수의 타입이 Money이면 객체도 정확히 Money이고, 그 클래스의 코드만 읽으면 불변인지 판단할 수 있다. 불변성은 "이 타입의 객체는 모두 그렇다"고 말할 수 있을 때 쓸모가 있고, 그 말을 가능하게 하는 것이 final 클래스다.

    record: 언어가 만들어 주는 얕은 불변 클래스

    불변 클래스를 만드는 절차는 매번 같다. final 클래스, private final 필드, 필드를 채우는 생성자, 접근자. Java 16에 정식으로 들어온 레코드(record)는 이 반복을 선언 한 줄로 줄인다.

    record Money(int amount) {
    Money {                                   // 컴팩트 생성자
        if (amount < 0) {
            throw new IllegalArgumentException("금액은 음수일 수 없다: " + amount);
        }
    }

    Money plus(int delta) {
        return new Money(amount + delta);
    }
}
    final class Money extends java.lang.Record {
  private final int amount;
  Money(int);
  Money plus(int);
  public final java.lang.String toString();
  public final int hashCode();
  public final boolean equals(java.lang.Object);
  public int amount();
}

    컴파일 결과를 보면 손으로 쓰던 것과 같은 구조가 들어 있다. 클래스는 final이고(JLS §8.10은 레코드 클래스가 암묵적으로 final이라고 규정한다), 괄호 안에 적은 구성 요소마다 private final 필드와 같은 이름의 접근자가 생겼다. 생성자, toString, equals, hashCode도 컴파일러가 만들었다. 중괄호만 있고 매개변수 목록이 없는 Money { ... }는 컴팩트 생성자로, 본문이 끝난 뒤에 매개변수의 값이 필드에 대입된다. 그래서 그 안에서 인자를 검증할 수 있다.

    Money a = new Money(1000);
Money b = a.plus(500);
System.out.println(a + " " + b);
System.out.println(a.equals(new Money(1000)));
System.out.println(a == new Money(1000));

true
false

    자동으로 만들어진 equals는 구성 요소의 값을 비교하므로 금액이 같은 두 객체는 equals로 같다. ==는 참조값을 비교하므로 서로 다른 객체에 대해 false다. 값을 표현하는 불변 객체는 "어느 객체인가"가 아니라 "어떤 값인가"로 비교하는 것이 맞고, 이 구분은 앞 회차에서 다룬 동일성과 동등성의 구분 그대로다.

    레코드가 보장하는 것은 얕은 불변까지다. java.lang.Record의 API 문서는 레코드 클래스를 "얕게 불변인(shallowly immutable)" 값 운반체라고 정의하고, 정식 생성자를 직접 선언하는 주된 이유로 인자 검증과 가변 구성 요소의 방어적 복사를 든다. 구성 요소가 리스트라면 앞의 Roster와 같은 구멍이 생기고, 같은 방법으로 막는다.

    record Team(String name, List members) {
    Team {
        members = List.copyOf(members);       // 필드에 대입되기 전에 사본으로 바꾼다
    }
}

    컴팩트 생성자 안에서 매개변수 members에 사본을 다시 대입하면, 본문이 끝난 뒤 그 사본이 필드에 들어간다. 이 한 줄이 없으면 new Team("A", list)를 만든 뒤 list.add("lee")를 실행했을 때 team.members()의 크기가 함께 늘어난다.

    불변 객체가 주는 것: 한 번의 검증, 안전한 키, 스레드 안전

    사이드 이펙트를 없애는 것이 불변 객체의 첫 번째 효과라면, 같은 성질에서 따라 나오는 효과가 몇 가지 더 있다. 모두 "한 번 확인한 것이 계속 참이다"라는 한 문장으로 묶인다.

    검증은 생성자에서 한 번이면 된다

    final class Money {
    static final Money ZERO = new Money(0);

    private final int amount;

    Money(int amount) {
        if (amount < 0) {
            throw new IllegalArgumentException("금액은 음수일 수 없다: " + amount);
        }
        this.amount = amount;
    }

    int amount() { return amount; }

    Money plus(int delta) {
        return new Money(amount + delta);
    }

    @Override
    public String toString() { return amount + "원"; }
}

public class ValidMain {
    public static void main(String[] args) {
        Money a = Money.ZERO.plus(300);
        System.out.println(a + " / " + Money.ZERO);
        try {
            a.plus(-500);
        } catch (IllegalArgumentException e) {
            System.out.println(e.getMessage());
        }
        System.out.println(a);
    }
}

금액은 음수일 수 없다: -200

    "금액은 음수가 아니다"처럼 객체가 항상 만족해야 하는 조건을 불변식(invariant)이라고 한다. 불변 클래스에서는 이 검사를 생성자 한 곳에만 두면 된다. 모든 객체는 생성자를 통과해야 만들어지고, 만들어진 뒤에는 바뀌지 않으므로, 존재하는 Money 객체는 모두 조건을 만족한다. plus도 결과를 생성자로 만들기 때문에 a.plus(-500)은 음수 금액 객체를 만들지 못하고 예외로 끝난다. 예외가 난 뒤에도 a는 300원 그대로다. 가변 클래스였다면 필드를 고치는 메서드마다 같은 검사를 넣어야 하고, 검사를 통과한 뒤에 다른 참조를 통해 값이 바뀔 가능성까지 따져야 한다.

    ZERO처럼 자주 쓰는 값을 static final 상수로 두고 프로그램 전체가 함께 쓰는 것도 불변이어서 가능하다. 자바 기본편의 final 회차에서 본 "상수 배열" 문제, 즉 static final int[]의 원소를 누군가 바꾸면 프로그램 전체의 상수가 달라지는 문제는 가리키는 객체가 가변이어서 생긴 것이었다. 가리키는 객체가 불변이면 static final은 이름 그대로의 상수가 된다.

    해시 기반 컬렉션의 원소와 키로 쓸 수 있다

    HashSet이나 HashMap은 객체를 넣을 때 그 객체의 hashCode()로 보관할 자리를 정한다. 넣은 뒤에 객체의 내용이 바뀌어 hashCode()가 달라지면, 컬렉션은 그 객체를 다시 찾지 못한다.

    import java.util.HashSet;
import java.util.Objects;
import java.util.Set;

class Tag {
    String name;                             // 가변

    Tag(String name) { this.name = name; }

    @Override
    public boolean equals(Object o) {
        return o instanceof Tag other && Objects.equals(name, other.name);
    }

    @Override
    public int hashCode() { return Objects.hashCode(name); }
}

public class KeyMain {
    public static void main(String[] args) {
        Set tags = new HashSet<>();
        Tag tag = new Tag("java");
        tags.add(tag);
        System.out.println(tags.contains(tag));

        tag.name = "jvm";                    // 집합에 들어 있는 객체를 고친다
        System.out.println(tags.contains(tag));
        System.out.println(tags.contains(new Tag("java")));
        System.out.println(tags.size());
        System.out.println(tags.iterator().next() == tag);
    }
}

    집합의 크기는 1이고 그 안의 원소는 분명히 tag인데, contains(tag)는 false다. 집합은 "java"의 해시코드로 자리를 정해 두었고, 지금 tag의 해시코드는 "jvm"의 것이어서 저장할 때의 해시코드와 맞지 않는다. new Tag("java")로 찾으면 해시코드는 맞지만, 그 자리에 있는 객체의 name이 이제 "jvm"이므로 equals가 false다. 들어 있지만 찾을 수 없는 원소가 된 것이다. Set과 Map의 API 문서는 가변 객체를 원소나 키로 쓸 때 크게 주의하라고 하며, 들어 있는 동안 equals 비교에 영향을 주는 방식으로 값이 바뀌면 동작이 규정되지 않는다고 적는다. 불변 객체는 이 조건을 구조적으로 만족한다. 해시 자료 구조의 내부는 중급 2편에서 다룬다.

    여러 스레드가 함께 읽어도 된다

    이 회차에서 본 사이드 이펙트는 스레드가 하나일 때의 이야기였다. 스레드가 여럿이면 같은 객체를 한 스레드가 고치는 동안 다른 스레드가 읽는 상황이 더해지고, 문제는 훨씬 복잡해진다. 불변 객체는 고치는 연산이 아예 없으므로 이 상황이 생기지 않는다. JLS §17.5는 final 필드를 쓰면 동기화 없이도 스레드 안전한 불변 객체를 구현할 수 있다고 하고, 생성자가 끝난 뒤에야 객체의 참조를 볼 수 있었던 스레드는 그 객체의 final 필드에 대해 올바르게 초기화된 값을 본다고 보장한다. 조건은 생성자가 끝나기 전에 this를 다른 스레드가 볼 수 있는 곳에 내놓지 않는 것이다. 이 보장의 의미는 고급 1편에서 자바 메모리 모델과 함께 다룬다.

    한 층 아래 ①: 불변성은 어느 층에서 지켜지는가

    "이 객체는 바뀌지 않는다"는 약속을 실제로 지키는 것은 누구인가. 층을 나누어 보면 각 층이 막는 것과 막지 않는 것이 구분된다.

    컴파일러의 검사는 앞에서 보았다. 컴파일된 클래스 파일에도 그 정보가 남는다. javap -v -p Money로 필드를 보면 접근 플래그에 ACC_FINAL이 있다.

      private final int amount;
    descriptor: I
    flags: (0x0012) ACC_PRIVATE, ACC_FINAL

    JVM은 이 플래그를 직접 검사한다. JVMS §6.5의 putfield 항목은, 대상 필드가 final이면 그 필드가 현재 클래스에 선언되어 있어야 하고 명령이 현재 클래스의 인스턴스 초기화 메서드(, 곧 생성자) 안에 있어야 하며 그렇지 않으면 IllegalAccessError를 던진다고 규정한다. javac를 거치지 않고 만들어진 클래스 파일이 다른 클래스의 final 필드에 쓰려 해도 JVM이 막는다는 뜻이다. final 필드의 보호는 컴파일러의 예의가 아니라 JVM의 규칙이다.

    그 위에 예외적인 통로가 하나 있다. 실행 중에 클래스의 필드와 메서드를 이름으로 찾아 다루는 리플렉션(reflection) API다. 리플렉션은 뒤 과정에서 배우므로 여기서는 결과만 본다.

    import java.lang.reflect.Field;

final class Money {
    private final int amount;
    Money(int amount) { this.amount = amount; }
    int amount() { return amount; }
}

record Point(int x, int y) { }

public class ReflectMain {
    public static void main(String[] args) throws Exception {
        Money money = new Money(1000);
        Field f = Money.class.getDeclaredField("amount");
        f.setAccessible(true);
        f.setInt(money, 9999);
        System.out.println(money.amount());

        Point p = new Point(1, 2);
        Field x = Point.class.getDeclaredField("x");
        x.setAccessible(true);
        try {
            x.setInt(p, 100);
        } catch (IllegalAccessException e) {
            System.out.println(e.getClass().getSimpleName() + ": " + e.getMessage());
        }
        System.out.println(p);
    }
}
    9999
IllegalAccessException: Can not set final int field Point.x to (int)100
Point[x=1, y=2]

    일반 클래스의 private final 필드가 9999로 바뀌었다. Field.set의 API 문서(Java 21)는 final 필드에 쓸 수 있는 조건을 정해 둔다. setAccessible(true)가 성공했고, 필드가 static이 아니며, 필드를 선언한 클래스가 히든 클래스도 레코드 클래스도 아니어야 한다. 하나라도 어긋나면 IllegalAccessException이 난다. 레코드인 Point의 필드에 쓰려던 시도가 거부된 것이 이 규칙이다. 이 통로는 역직렬화처럼 객체를 복원하는 도구를 위해 남겨 둔 것이며, JLS §17.5.3은 이렇게 바꾼 값이 프로그램의 다른 부분에서 보이지 않을 수 있는 경우를 따로 경고한다.

    이 통로는 좁아지는 중이다. JEP 500은 리플렉션으로 final 필드를 바꾸면 기본 설정에서 실행 시 경고가 나오게 했고 JDK 26에 반영되었다. 이 JEP는 이후 릴리스에서 그런 변경을 기본으로 금지하는 것을 목표로 밝히고 있다. 정리하면, 불변 클래스가 주는 것은 정상적인 자바 코드에 대한 보장이다. JLS §17.5도 final 필드가 "정상적인 상황에서는" 바뀌지 않는다고 표현한다. 리플렉션은 일부러 호출해야만 열리는 경로이고, 대입이나 메서드 호출 같은 일상적인 코드에서 실수로 열리지 않는다. 이 회차가 막으려던 것은 실수로 생기는 사이드 이펙트였다.

    한 층 아래 ②: 매번 새 객체를 만드는 비용

    불변 객체는 값을 바꿀 때마다 객체를 하나 만든다. 가변 객체라면 필드에 한 번 쓰면 끝날 일이, 메모리를 할당하고 생성자를 실행하고 나중에 그 메모리를 회수하는 일로 바뀐다. 이 비용이 얼마나 부담이 되는지는 JVM이 객체를 만들고 버리는 방식에 달려 있다. 아래 내용은 명세가 아니라 HotSpot 구현에 관한 것이다.

    먼저 할당이다. JDK 21의 java 명령 문서는 -XX:+UseTLAB 옵션을 "젊은 세대 공간에서 스레드 로컬 할당 블록(TLAB)을 사용하게 한다"고 설명하고 기본으로 켜져 있다고 적는다. OpenJDK의 HotSpot 용어집은 TLAB를 동기화 없이 힙 공간을 빠르게 할당하는 데 쓰는 스레드 로컬 할당 버퍼라고 설명하고, 컴파일된 코드에는 현재 스레드의 TLAB 안에서 경계 표시를 앞으로 밀어 객체를 할당하는 명령 몇 개짜리 "빠른 경로"가 있다고 적는다. 스레드마다 힙의 한 구역을 미리 받아 두고 새 객체를 그 안에서 할당하므로 객체를 만들 때마다 다른 스레드와 힙을 두고 다툴 필요가 없고, 빠른 경로를 타는 할당은 표시 하나를 옮기는 일로 끝난다.

    다음은 회수다. Oracle의 가비지 컬렉션 튜닝 가이드는 세대별 수집의 바탕이 되는 관찰을 약한 세대 가설(weak generational hypothesis)이라고 부른다. 대부분의 객체는 짧은 시간만 살아남는다는 것이다. 그래서 대다수의 객체는 젊은 세대(young generation)에 할당되고 대부분 거기서 죽는다. 같은 문서는 젊은 세대 수집의 비용이 일차적으로 살아 있는 객체의 수에 비례하며, 죽은 객체로 가득한 젊은 세대는 매우 빨리 수집된다고 설명한다. welcome.plus(500).plus(250)의 가운데에서 만들어졌다가 곧바로 버려지는 1,500원 객체는 이 가정에 정확히 들어맞는 객체다.

    경우에 따라서는 할당 자체가 없어진다. Oracle의 HotSpot 성능 개선 문서는 탈출 분석(escape analysis)을, 서버 컴파일러가 새 객체의 사용 범위를 분석해 자바 힙에 할당할지를 결정하는 기법이라고 설명한다. 분석 결과 어디로도 빠져나가지 않는다고 판정된 객체(NoEscape)는 스칼라 치환이 가능한 객체이고, 그런 객체의 할당은 생성된 코드에서 제거될 수 있다. 같은 문서는 이것이 힙 할당을 스택 할당으로 바꾸는 것은 아니라고 명시한다. 객체가 스택으로 옮겨지는 것이 아니라, 객체를 만들 필요 없이 필드 값만 다루는 코드로 바뀌는 것이다. 다만 어떤 코드에 이 최적화가 적용되는지는 JIT 컴파일러의 분석 결과에 달려 있으므로, 적용된다고 전제하고 설계할 수는 없다.

    이런 장치들이 있어도 비용이 사라지는 것은 아니다. 큰 내용을 가진 불변 객체를 반복문 안에서 조금씩 바꾸면, 바꿀 때마다 내용 전체를 새 객체로 복사하게 된다. 문자열을 반복해서 이어 붙이는 경우가 대표적이고, 그래서 불변인 String에는 가변인 StringBuilder가 짝으로 제공된다. 여러 번 바꾸는 동안은 가변 객체로 작업하고, 결과가 확정되면 불변 객체로 만들어 내보내는 방식이다. 이 내용은 다음 회차에서 다룬다.

    반대 방향의 이득도 있다. 불변 객체는 복사할 필요가 없다. 방어적 복사가 사라지고, 같은 값을 나타내는 객체 하나를 여러 곳에서 재사용할 수 있다. List.copyOf의 구현 노트는 인자가 이미 수정 불가 리스트이면 일반적으로 사본을 만들지 않는다고 적는데, 바뀌지 않는 것을 복사할 이유가 없기 때문이다. 다음 회차의 문자열 풀과 그다음 회차의 Integer 캐시도 같은 원리 위에 있다. 불변성은 객체를 더 만들게도 하고 덜 만들게도 한다. 어느 쪽이 큰지는 사용 방식에 따라 다르므로, 성능을 이유로 가변을 선택할 때는 측정한 결과가 있어야 한다.

    흔한 오해와 함정

    "final 변수에 담았으니 불변 객체다"

    final Money m = new Money(1000);에서 final은 변수 m이 다른 객체를 가리키지 못하게 할 뿐이다. Money가 가변 클래스라면 m.setAmount(0)은 그대로 실행된다. 변수의 final과 객체의 불변성은 서로 독립된 성질이다. 불변성은 변수의 선언이 아니라 클래스의 설계에서 나온다.

    "불변 객체를 담은 변수는 값을 바꿀 수 없다"

    반대 방향의 오해다. Money m = new Money(1000); m = m.plus(500);은 문제없이 실행되고 m은 1,500원 객체를 가리키게 된다. 바뀌지 않는 것은 1,000원 객체이고, 변수 m은 얼마든지 다른 객체를 가리킬 수 있다. 불변 객체로 값이 변하는 프로그램을 짤 수 있는 것은 이 구분 덕분이다. 상태 변화는 객체 안이 아니라 변수(또는 가변 객체의 필드)에서 일어난다.

    "setter가 없으면 불변이다"

    이름이 set으로 시작하지 않아도 필드를 고치는 메서드는 얼마든지 있을 수 있다. 처음의 Wallet.deposit이 그랬다. 또 Roster에서 보았듯 setter가 하나도 없어도 가변 객체의 참조가 밖에 있으면 상태가 바뀐다. 확인할 것은 메서드의 이름이 아니라 네 규칙 전부다.

    "수정 불가 컬렉션으로 감쌌으니 불변이다"

    Collections.unmodifiableList가 돌려주는 것은 뷰다. 원본의 참조를 가진 쪽이 원본을 고치면 뷰의 내용도 달라진다. 사본을 만드는 List.copyOf와 구분해야 하고, 사본이라도 원소가 가변이면 원소의 내용은 바뀔 수 있다.

    "불변 객체의 메서드를 호출했는데 값이 그대로다"

    오해라기보다 흔한 실수다. money.plus(500);만 쓰고 반환값을 받지 않았다. 불변 객체의 메서드는 수신 객체를 고치지 않으므로, 결과는 반환값에만 있다. 컴파일러는 이 실수를 알려 주지 않는다.

    "모든 클래스를 불변으로 만들어야 한다"

    지갑, 주문, 계좌처럼 시간이 지나며 상태가 달라지고 "같은 그것"을 여러 곳에서 가리켜야 하는 대상은 가변이 자연스럽다. 불변으로 만들 대상은 금액, 좌표, 기간, 이름처럼 값을 표현하는 클래스다. 가변 객체가 불변 값을 필드로 갖는 조합이 일반적이며, 이때 변경은 가변 객체의 메서드(deposit)라는 정해진 지점에서만 일어난다.

    다른 주제와의 연결

    이 권의 뒤 회차들은 JDK가 제공하는 불변 클래스를 차례로 다룬다. 3회의 String은 final 클래스이고 setter가 없는 불변 클래스이며(OpenJDK 21 기준으로 앞에서 말한 해시코드 캐시용 필드만 final이 아니다), 문자열 리터럴을 풀에서 공유하는 설계가 불변성에 기대고 있다. 4회의 래퍼 클래스도 불변이며, 그 덕분에 자주 쓰는 값의 객체를 캐시해 두고 재사용한다. 5회의 열거형은 정해진 개수의 객체만 존재하도록 닫아 둔 타입이고, 6회의 java.time 클래스들은 API 문서가 "불변이고 스레드 안전하다"고 명시하며 plus, with 계열 메서드로 새 객체를 돌려준다. 이 회차의 Money.plus와 같은 구조다.

    중급 2편의 컬렉션에서는 해시 기반 자료 구조가 키의 hashCode와 equals가 변하지 않는다는 전제 위에 서 있다는 것을 내부 구조와 함께 본다. 고급 1편의 멀티스레드에서는 공유되는 가변 상태가 문제의 중심이 되고, 불변 객체는 동기화 없이 공유할 수 있는 수단으로 다시 등장한다.

    스프링에서는 컨테이너가 기본으로 하나만 만들어 여러 요청이 함께 쓰는 싱글턴 빈을 만나게 된다. 이 회차의 표로 보면 "공유한다" 행에 있는 객체이므로, 요청마다 달라지는 값을 그 객체의 필드에 써서는 안 된다는 결론이 바로 나온다. JPA에서 값 타입을 다룰 때는 같은 값 타입 객체를 두 엔티티가 함께 참조하면 한쪽을 고친 것이 다른 쪽의 데이터베이스 수정으로까지 이어지는 것을 보게 되고, 그 해법도 값 타입을 불변으로 만드는 것이다.

    이 장의 핵심

    자바에서 참조형 대입은 언제나 같은 객체를 공유하게 만들고, 언어는 그것을 막지 않는다. 사이드 이펙트는 공유와 변경이 함께 있을 때 생기므로, 막을 수 없는 공유 대신 변경을 없앤다. 불변 객체는 생성된 뒤 상태가 바뀌지 않는 객체이고, 값을 바꿔야 할 때는 새 객체를 만들어 돌려준다. final 필드는 참조값만 고정하므로 필드가 가리키는 가변 객체는 복사로 격리하고, 클래스는 final로 닫는다.
    대입이 복사하는 것
    대입은 변수에 든 값을 복사한다. 기본형은 값 자체가 복사되어 두 변수가 독립이고, 참조형은 참조값이 복사되어 두 변수가 객체 하나를 함께 가리킨다. 객체를 복제하는 대입은 없다.
    공유 참조와 사이드 이펙트
    같은 객체를 가리키는 참조가 여럿일 때 한 참조로 객체를 고치면 나머지 참조에서도 그 변경이 보인다. 공유는 대입뿐 아니라 인자 전달, 반환, 필드 저장, 컬렉션 저장에서도 만들어진다.
    공유와 변경
    사이드 이펙트는 공유와 변경이 함께 있을 때만 생긴다. 공유는 문법으로 막을 수 없지만 변경은 클래스 설계로 막을 수 있다.
    방어적 복사
    받은 객체나 내줄 객체의 사본을 만들어 공유를 끊는 방법이다. 컴파일러가 강제하지 않고 경계마다 반복해야 하므로 빠뜨리기 쉽다.
    불변 객체
    생성된 뒤 상태가 바뀌지 않는 객체다. setter를 두지 않고, 모든 필드를 private final로 하고, 클래스를 final로 닫고, 필드가 가리키는 가변 객체를 밖과 공유하지 않는다.
    값 변경 메서드
    불변 객체의 값을 바꾸는 메서드는 자신을 고치지 않고 새 객체를 만들어 반환한다. 반환값을 받지 않으면 결과가 버려지고, 컴파일러는 이를 알려 주지 않는다.
    얕은 불변과 깊은 불변
    final은 필드의 참조값만 고정한다. 필드가 가리키는 배열이나 컬렉션, 그 원소까지 바뀌지 않아야 공유해도 안전하다. List.copyOf는 사본이고 Collections.unmodifiableList는 뷰다.
    record
    final 클래스, private final 필드, 접근자, equals/hashCode/toString을 컴파일러가 만들어 주는 얕은 불변 클래스다. 가변 구성 요소는 컴팩트 생성자에서 복사해야 한다.
    보장의 범위와 비용
    final 필드는 컴파일러와 JVM(putfield 규칙)이 지키고, 리플렉션이라는 예외 통로가 있다. 새 객체를 만드는 비용은 HotSpot의 TLAB, 세대별 수집, 탈출 분석이 줄여 주지만 없어지지는 않는다.

    실무에서 다시 판단하면, "한 곳에서 고친 값이 다른 곳에서도 바뀌어 있다"는 증상을 만났을 때 먼저 의심할 것은 계산 로직이 아니라 공유된 가변 객체다. 캐시에서 꺼낸 객체를 호출한 쪽이 고쳐서 캐시의 내용이 달라진 경우, 기본 설정으로 쓰려고 static 필드에 둔 객체를 누군가 고친 경우, 접근자가 내준 내부 컬렉션을 호출한 쪽이 정렬하거나 비운 경우가 모두 같은 구조다. 조사할 때는 "이 값을 누가 계산했는가"보다 "이 객체를 가리키는 참조가 어디에 있는가"를 묻는 것이 빠르다.

    설계할 때의 기본값은 값을 표현하는 클래스를 불변으로 두는 것이다. 금액, 기간, 좌표, 식별자, 설정값 묶음이 여기에 든다. 이런 클래스는 여러 객체의 필드에 들어가고 메서드 사이를 자주 오가므로 공유가 가장 많이 일어난다. 반대로 주문이나 계좌처럼 수명 동안 상태가 달라지는 대상은 가변으로 두되, 상태를 바꾸는 지점을 의미 있는 이름의 메서드 몇 개로 좁힌다. 불변 값을 필드로 가진 가변 객체에서는 변경이 "필드가 가리키는 값 객체를 교체하는 일"이 되어 어디서 바뀌는지를 추적하기 쉽다.

    판단이 달라지는 조건은 주로 성능과 경계다. 큰 구조를 반복문 안에서 여러 번 바꿔야 한다면 그 구간에서는 가변 객체로 작업하고, 결과를 밖으로 내보낼 때 불변으로 고정하는 편이 낫다. 다만 이것은 측정으로 병목이 확인된 뒤의 선택이다. 방어적 복사도 마찬가지로, 같은 클래스나 같은 패키지 안에서만 오가는 컬렉션까지 매번 복사할 필요는 없다. 복사가 필요한 곳은 통제할 수 없는 코드와 만나는 경계, 즉 공개 생성자와 공개 접근자다.

    공유 참조(shared reference)
    둘 이상의 변수나 필드가 같은 객체의 참조값을 갖고 있는 상태. 별칭(aliasing)이라고도 한다. 참조형의 대입, 인자 전달, 반환, 필드 저장에서 만들어진다.
    사이드 이펙트(side effect)
    연산이 자기가 맡은 결과 외에 다른 곳의 상태를 바꾸는 것. 이 회차에서는 한 참조로 고친 객체의 변경이 의도하지 않은 다른 참조에서 관찰되는 경우를 가리킨다.
    가변 객체(mutable object)
    생성된 뒤에 상태를 바꿀 수 있는 객체.
    불변 객체(immutable object)
    생성된 뒤에 밖에서 관찰할 수 있는 상태가 바뀌지 않는 객체. 값을 바꿔야 할 때는 새 객체를 만든다.
    방어적 복사(defensive copy)
    밖에서 받은 가변 객체를 보관하기 전에, 또는 내부의 가변 객체를 내주기 전에 사본을 만들어 공유를 끊는 기법.
    얕은 불변(shallow immutability)
    객체 자신의 필드는 바뀌지 않지만 그 필드가 가리키는 객체의 내용은 바뀔 수 있는 상태. 참조를 따라 닿는 모든 객체가 바뀌지 않으면 깊은 불변이다.
    수정 불가 뷰(unmodifiable view)
    원본 컬렉션을 감싸 변경 메서드를 막은 컬렉션. 뷰를 통해서는 고칠 수 없지만 원본이 바뀌면 뷰의 내용도 달라진다.
    불변식(invariant)
    객체가 존재하는 동안 항상 참이어야 하는 조건. 불변 클래스에서는 생성자에서 한 번 검사하면 이후에도 유지된다.
    레코드(record)
    구성 요소를 선언하면 final 클래스, private final 필드, 접근자, 생성자, equals/hashCode/toString이 만들어지는 클래스 선언 형식. Java 16부터 정식 기능이며 얕은 불변을 보장한다.
    탈출 분석(escape analysis)
    새로 만든 객체가 메서드나 스레드 밖으로 나가는지를 JIT 컴파일러가 분석하는 기법. HotSpot의 서버 컴파일러는 밖으로 나가지 않는 객체의 할당을 생성된 코드에서 제거할 수 있다.
