    이 회차의 질문: 세로로 잇고, 바꿔 읽고, 이름을 붙인다

    앞의 세 회차는 여러 테이블을 엮는 방법을 다뤘다. 01회와 02회의 조인은 두 테이블의 행을 짝지어 열을 옆으로 늘렸고, 03회의 서브쿼리는 쿼리 안에 쿼리를 넣어 한 쿼리의 결과를 다른 쿼리의 재료로 썼다. 이 회차의 세 도구는 성격이 조금 다르다. UNION은 결과를 옆이 아니라 아래로 잇는다. CASE 식은 행을 늘리지도 줄이지도 않고 각 행의 값을 조건에 따라 다르게 읽는다. 뷰(view)는 쿼리 자체에 이름을 붙여 테이블처럼 다시 쓰게 한다.

    세 도구는 서로 무관해 보이지만 하나의 질문으로 묶인다. 저장된 모양과 보고 싶은 모양이 다를 때, 그 차이를 누가 언제 메우는가. 올해 주문과 지난해 주문이 두 테이블에 나뉘어 있는데 한 목록으로 보고 싶다면 UNION이 메운다. 주문 상태가 행마다 문자열로 저장되어 있는데 상태별 건수를 한 줄에 열로 보고 싶다면 CASE와 집계 함수가 메운다. 세 테이블을 조인해야 나오는 주문 상세를 매번 다시 쓰고 싶지 않다면 뷰가 메운다. 어느 경우든 데이터를 복사해 새로 저장하지 않고, 질의하는 순간에 모양을 바꾼다.

    질의하는 순간에 모양을 바꾼다는 것은 그 일을 엔진이 매번 한다는 뜻이다. 그래서 이 회차는 문법과 함께 엔진이 하는 일을 따라간다. UNION이 중복을 없앨 때 MySQL은 내부 임시 테이블(internal temporary table)을 만든다. CASE를 이용한 조건부 집계는 테이블을 한 번만 읽으면서 여러 개의 합계를 동시에 만든다. 뷰를 조회하면 MySQL은 뷰의 정의를 바깥 쿼리에 합쳐 넣거나(MERGE), 뷰의 결과를 임시 테이블로 만든 뒤 읽는다(TEMPTABLE). 어느 쪽이 선택되느냐에 따라 기반 테이블의 인덱스를 쓸 수 있는지, 뷰를 통해 데이터를 고칠 수 있는지가 갈린다.

    설명은 MySQL 8.0 이상과 InnoDB 저장 엔진을 기준으로 한다. 결과 표는 아래 실습 데이터를 MySQL 8.4.13과 8.0.46에서 실제로 실행해 얻은 값이고, 이 회차의 모든 예제에서 두 버전의 결과가 같았다. EXPLAIN의 rows, filtered, cost 같은 추정치는 실행 환경과 통계에 따라 달라지므로, 이 회차의 EXPLAIN 출력은 이 작은 실습 데이터에서 나온 한 예로 읽어야 한다. 이 권의 다른 회차와 범위를 나누어, 인덱스의 구조는 05회와 06회, 제약 조건은 07회, 트랜잭션과 잠금은 08회, 저장 프로시저 안에서 쓰는 CASE 문(statement)은 09회에서 다룬다. 이 회차의 CASE는 쿼리 안에서 값을 돌려주는 CASE 식(expression)이다.

    UNION: 결과 집합을 세로로 잇는다

    조인과 UNION은 둘 다 "두 쿼리를 합친다"고 말하지만 합치는 방향이 다르다. 조인은 왼쪽 행과 오른쪽 행을 짝지어 하나의 더 넓은 행을 만든다. 결과의 열 수는 두 테이블의 열을 더한 만큼 늘고, 행 수는 짝이 맞는 개수가 정한다. UNION은 짝을 찾지 않는다. 첫 번째 쿼리의 결과 행 아래에 두 번째 쿼리의 결과 행을 쌓는다. 열 수는 그대로이고 행 수가 더해진다. 중복 제거는 그다음 단계의 이야기다.

    조인: 가로로 붙인다                       UNION: 세로로 쌓는다

 A의 열        B의 열                       결과 열 (이름은 첫 블록에서)
+----+----+  +----+----+                   +------+------+
| a1 | a2 |--| b1 | b2 |  짝이 맞으면      |  x   |  y   |  블록 1의 행
+----+----+  +----+----+  한 줄로          |  ..  |  ..  |
                                           +------+------+
결과: | a1 | a2 | b1 | b2 |                  |  x   |  y   |  블록 2의 행
                                           |  ..  |  ..  |
                                           +------+------+
열 수 = A의 열 수 + B의 열 수               열 수 = 각 블록의 열 수 (같아야 한다)
행 수 = 짝의 개수                           행 수 = 블록 행 수의 합 (UNION은 중복 제거 뒤)
    같은 두 결과 집합을 조인과 UNION으로 합쳤을 때 결과의 모양이 어떻게 다른지 한눈에 보여 준다. 흰 배경의 깔끔한 교육용 다이어그램. 왼쪽 절반과 오른쪽 절반으로 나뉜다. 왼쪽 위에 "조인"이라는 제목, 그 아래 파란 표 A(2열)와 주황 표 B(2열)가 나란히 있고 같은 높이의 행끼리 회색 선으로 이어져 있으며, 아래쪽 화살표가 파란 2열과 주황 2열이 옆으로 붙은 4열짜리 넓은 표를 가리킨다. 넓은 표 아래 라벨 "열이 늘어난다". 오른쪽 위에 "UNION"이라는 제목, 그 아래 파란 표(2열, 3행)와 주황 표(2열, 3행)가 위아래로 놓여 있고, 화살표가 파란 행 3개 위에 주황 행 3개가 쌓인 2열 6행 표를 가리킨다. 그 표 옆 라벨 "행이 늘어난다", 표 머리 위 라벨 "열 이름은 첫 블록에서". 오른쪽 아래 작은 글씨 라벨 "UNION은 같은 행을 하나만 남긴다". 평면 스타일, 그림자 없음. 조인은 짝을 찾아 열을 옆으로 붙이고, UNION은 짝을 찾지 않고 행을 아래로 쌓는다.

    쌓으려면 모양이 맞아야 한다. MySQL 매뉴얼은 UNION에 참여하는 각 SELECT를 쿼리 블록(query block)이라고 부른다. 블록마다 고르는 열의 개수가 같아야 하고, 다르면 ERROR 1222 (21000): The used SELECT statements have a different number of columns 오류가 난다. 개수만 맞으면 MySQL은 열의 의미를 따지지 않는다. 고객 이름 아래에 상품 가격을 쌓아도 문법 오류는 아니다. 같은 위치의 열이 같은 의미가 되도록 맞추는 일은 쿼리를 쓰는 사람의 몫이다.

    결과 열의 이름은 첫 번째 쿼리 블록의 열 이름을 따른다. 두 번째 이후 블록에서 붙인 별칭은 결과에 나타나지 않는다. 결과 열의 타입과 길이는 첫 블록만 보고 정하지 않는다. 매뉴얼은 대응하는 열의 타입이 다르면 결과 열의 타입과 길이가 모든 쿼리 블록에서 가져온 값을 고려해 정해진다고 적고, 길이 1인 문자열을 고르는 블록과 길이 20인 문자열을 고르는 블록을 UNION해도 20글자 값이 잘리지 않는 예를 든다. 그래도 원칙은 같은 위치에 같은 타입을 두는 것이다. 숫자와 문자열을 같은 위치에 섞으면 결과 열이 어떤 타입이 되는지부터 따져야 하고, 그 열로 정렬하거나 비교할 때 뜻밖의 결과가 나온다. 이 문제는 CASE 식의 결과 타입을 다룰 때 다시 본다.

UNION

    한 단계씩 따라가 보자. 첫 블록은 서울, 부산, 서울, 대전, NULL 다섯 행을 낸다. 둘째 블록은 서울, 광주, 부산, NULL 네 행을 낸다. 아홉 행을 쌓은 다음 UNION이 중복을 지운다. 서울은 세 번, 부산은 두 번 나왔지만 한 번씩만 남는다. 눈여겨볼 것은 NULL이다. 정노을의 NULL과 새벽물산의 NULL도 하나로 합쳐졌다. 비교 연산으로는 NULL = NULL이 참이 아니라 알 수 없음(UNKNOWN)인데 왜 합쳐질까. 중복 제거는 등호 비교가 아니라 "두 행을 서로 구별할 수 있는가"를 따지기 때문이다. MySQL 매뉴얼은 DISTINCT, GROUP BY, ORDER BY에서 모든 NULL을 같은 값으로 본다고 적고 있고, UNION의 중복 제거도 NULL끼리를 중복으로 처리한다. WHERE 절에서 NULL끼리 같지 않던 것과 대비되는 지점이다.

    NULL이 맨 위에 온 것은 MySQL이 오름차순 정렬에서 NULL을 가장 앞에 두기 때문이다. ORDER BY를 빼면 행의 순서는 보장되지 않는다. 매뉴얼은 집합 연산이 만든 행에는 기본적으로 순서가 없다고 명시한다. 실행해 보면 대개 첫 블록의 행이 먼저 나오는 것처럼 보이지만, 그것은 현재 실행 방식이 우연히 만든 순서일 뿐 약속이 아니다. 순서가 필요하면 항상 ORDER BY를 쓴다.

    중복 판정은 행 전체를 기준으로 한다는 점도 중요하다. 같은 도시라도 다른 열이 함께 있으면 더 이상 중복이 아니다. 고객과 판매자를 한 연락처 목록으로 만들어 보자.

    아홉 행이 모두 남았다. 서울이라는 값은 여러 번 나오지만 (name, city, kind) 세 값의 조합이 같은 행은 하나도 없기 때문이다. 이 쿼리에는 자주 쓰는 기법 두 가지가 들어 있다. 첫째, 상수 열 kind로 각 행이 어느 블록에서 왔는지 표시했다. 결과만 봐서는 출처를 알 수 없는 UNION에 출처 꼬리표를 붙이는 방법이다. 둘째, 둘째 블록의 '판매자'에는 별칭을 붙이지 않았다. 결과 열 이름은 첫 블록의 kind로 정해지므로 붙여도 결과에 쓰이지 않는다.     UNION과 UNION ALL: 중복 제거에는 값이 따른다

    UNION 뒤에 아무것도 쓰지 않으면 중복을 제거한다. UNION DISTINCT라고 써도 같은 뜻이며, DISTINCT는 기본 동작을 드러내 적는 것일 뿐이다. UNION ALL은 중복을 제거하지 않고 모든 블록의 모든 행을 그대로 낸다. 도시 쿼리를 UNION ALL로 바꾸면 결과는 아홉 행이다.

    일상에서 가져온 비유명단 두 장을 합치는 두 가지 방법

    UNION ALL은 명단 두 장을 스테이플러로 이어 붙이는 일이다. 종이를 넘겨 가며 읽기만 하면 되고, 첫 장을 붙이는 순간 이미 읽을 수 있다. UNION은 새 종이에 두 명단을 옮겨 적으면서 매번 "이미 적은 줄인가"를 확인하는 일이다. 옮겨 적을 종이가 필요하고, 다 옮겨 적은 뒤에야 깨끗한 명단을 건넬 수 있다. 비유가 깨지는 지점도 있다. 사람은 이름만 보고 같은 사람이라고 판단하지만 UNION은 고른 열 전체가 같아야 중복으로 본다. 이름이 같아도 도시 열이 다르면 둘 다 남는다.

    MySQL이 UNION을 실행하는 방식

    MySQL 매뉴얼의 내부 임시 테이블 절은 서버가 임시 테이블을 만드는 경우로 UNION 문의 평가를 꼽고, 예외를 따로 적는다. 다음 세 조건을 모두 만족하는 UNION은 임시 테이블을 쓰지 않는다. 이때 서버는 결과 열의 타입 변환에 필요한 자료 구조만 준비하고, 테이블을 실제로 만들지 않으며, 행을 쓰지도 읽지도 않고 곧바로 클라이언트로 보낸다.

    • UNION ALL이다. UNION이나 UNION DISTINCT가 아니다.
    • 결과 전체에 거는 ORDER BY가 없다.
    • INSERT ... SELECT나 REPLACE ... SELECT 문의 최상위 쿼리 블록이 아니다.

    뒤집어 말하면 UNION(DISTINCT)은 임시 테이블을 거친다. 각 블록이 만든 행이 임시 테이블에 모이면서 중복이 걸러지고, 모든 블록이 끝나면 그 임시 테이블을 읽어 결과로 내보낸다. UNION ALL이라도 결과 전체를 정렬하려면 정렬할 재료를 모아 둘 곳이 필요하므로 임시 테이블을 쓴다.

    EXPLAIN으로 보면 이 구조가 행으로 드러난다. 표 형식의 EXPLAIN에서 첫 블록은 select_type이 PRIMARY, 둘째 이후 블록은 UNION으로 나오고, 임시 테이블을 읽는 단계가 select_type UNION RESULT, table 인 행으로 따로 나온다. 매뉴얼은 을 id가 M과 N인 행들의 합집합을 가리키는 표시로 설명하고, 이런 행의 id는 NULL일 수 있다고 적는다. 그러나 MySQL 8.4.13과 8.0.46에서 ORDER BY를 뺀 도시 UNION을 EXPLAIN하면 이 행의 id는 NULL이 아니라 3으로 나온다. 두 버전의 출력이 같다.

    EXPLAIN SELECT city FROM customers UNION SELECT city FROM sellers;
    +----+--------------+------------+------------+------+---------------+------+---------+------+------+----------+-----------------+
| id | select_type  | table      | partitions | type | possible_keys | key  | key_len | ref  | rows | filtered | Extra           |
+----+--------------+------------+------------+------+---------------+------+---------+------+------+----------+-----------------+
|  1 | PRIMARY      | customers  | NULL       | ALL  | NULL          | NULL | NULL    | NULL |    5 |   100.00 | NULL            |
|  2 | UNION        | sellers    | NULL       | ALL  | NULL          | NULL | NULL    | NULL |    4 |   100.00 | NULL            |
|  3 | UNION RESULT |  | NULL       | ALL  | NULL          | NULL | NULL    | NULL | NULL |     NULL | Using temporary |
+----+--------------+------------+------------+------+---------------+------+---------+------+------+----------+-----------------+

    id 1이 블록 1, id 2가 블록 2, id 3의 UNION RESULT 행이 임시 테이블을 읽는 단계다. 그 행의 Extra에 Using temporary가 붙어 있다. 앞의 세 조건을 만족해 임시 테이블을 쓰지 않는 UNION ALL에서는 이 UNION RESULT 행이 나타나지 않는다. 매뉴얼은 그 행이 임시 테이블을 읽는 부분에 해당하기 때문이라고 설명한다. 같은 쿼리를 UNION ALL로 바꿔 EXPLAIN하면 실제로 두 행만 나온다.

    +----+-------------+-----------+------------+------+---------------+------+---------+------+------+----------+-------+
| id | select_type | table     | partitions | type | possible_keys | key  | key_len | ref  | rows | filtered | Extra |
+----+-------------+-----------+------------+------+---------------+------+---------+------+------+----------+-------+
|  1 | PRIMARY     | customers | NULL       | ALL  | NULL          | NULL | NULL    | NULL |    5 |   100.00 | NULL  |
|  2 | UNION       | sellers   | NULL       | ALL  | NULL          | NULL | NULL    | NULL |    4 |   100.00 | NULL  |
+----+-------------+-----------+------------+------+---------------+------+---------+------+------+----------+-------+

    실행 계획에서 UNION RESULT 행이 보이는지 여부로 임시 테이블을 거치는지를 알 수 있는 셈이다.

    UNION(DISTINCT)은 두 블록의 행을 임시 테이블에 모아 중복을 거른 뒤 읽어 보내고, 조건을 만족하는 UNION ALL은 행을 곧바로 클라이언트에 보낸다는 차이를 보여 준다. 흰 배경의 실행 흐름도. 위아래 두 줄. 위쪽 줄 제목 "UNION": 왼쪽에 "블록 1" 상자와 "블록 2" 상자가 세로로 있고, 두 상자에서 나온 화살표가 가운데 원통 모양의 "임시 테이블" 로 들어간다. 원통 안에 작은 글씨 "중복 걸러 모으기". 원통에서 오른쪽으로 "UNION RESULT" 라벨이 붙은 화살표가 나가 오른쪽 끝의 "클라이언트" 상자로 간다. 아래쪽 줄 제목 "UNION ALL": "블록 1"과 "블록 2" 상자에서 나온 화살표가 원통을 거치지 않고 곧바로 오른쪽 "클라이언트" 상자로 간다. 아래쪽 화살표 위 라벨 "만드는 즉시 전송". 오른쪽 아래 작은 주석 "전체 ORDER BY가 있으면 UNION ALL도 임시 테이블". 파랑과 주황의 두 색, 평면 스타일. 중복 제거가 필요한 UNION은 임시 테이블에 행을 모았다가 읽어 내고, 조건을 만족하는 UNION ALL은 임시 테이블 없이 행을 바로 보낸다.

    임시 테이블이 비용이 되는 이유

    임시 테이블을 거친다는 것은 세 가지 비용을 뜻한다. 첫째, 모든 행을 한 번 더 쓰고 읽는다. 블록이 만든 행을 곧바로 내보내지 못하고 임시 테이블에 넣었다가 다시 꺼낸다. 둘째, 중복을 판정하려면 새 행이 들어올 때마다 이미 모인 행과 같은지 확인해야 한다. 고른 열 전체가 비교 대상이므로 열이 많고 값이 길수록 확인할 것이 많아진다. 셋째, 첫 행이 늦게 나온다. 임시 테이블을 다 채운 뒤에 읽기 시작하므로 클라이언트는 마지막 블록이 끝날 때까지 결과를 받지 못한다. 임시 테이블을 쓰지 않는 UNION ALL은 첫 블록이 행을 만드는 대로 보낸다.

    내부 임시 테이블은 처음에는 메모리에 만들어진다. MySQL 8.0에서 메모리 내부 임시 테이블의 기본 저장 엔진은 TempTable이고, internal_tmp_mem_storage_engine 변수로 MEMORY 엔진으로 바꿀 수 있다. 메모리 임시 테이블이 너무 커지면 서버가 자동으로 디스크 기반 임시 테이블로 바꾼다. 그 한도에는 tmp_table_size(MySQL 8.0 문서 기준 기본 16MiB)와 temptable_max_ram(MySQL 8.0 문서 기준 기본 1GiB) 같은 시스템 변수가 관여한다. 행이 많은 결과를 UNION으로 중복 제거하면 이 한도를 넘어 디스크 입출력이 생길 수 있다. 중복이 생길 수 없는 데이터에 습관처럼 UNION을 쓰면 아무 효과 없이 이 비용만 치른다.

    무엇을 고를 것인가

    선택 기준은 단순하다. 결과에 같은 행이 두 번 나오면 안 되고 실제로 중복이 생길 수 있을 때만 UNION을 쓴다. 블록끼리 겹칠 수 없다는 것을 데이터의 구조로 알고 있다면 UNION ALL을 쓴다. 올해 주문과 보관 주문은 order_id가 겹치지 않으므로, 두 테이블의 행을 order_id와 함께 이으면 중복이 생길 수 없다. 여기에 UNION을 쓰면 일어나지 않을 중복을 찾느라 임시 테이블을 채운다.

    SELECT order_id, customer_id, status, order_date FROM orders
UNION ALL
SELECT order_id, customer_id, status, order_date FROM orders_archive
ORDER BY order_date;

    더 위험한 쪽은 반대 방향의 실수, 곧 정당한 중복을 UNION이 지워 버리는 경우다. 올해와 지난해를 합쳐 고객별 완료 주문 수를 세는 쿼리를 보자.

    SELECT customer_id, COUNT(*) AS completed_orders
FROM (
    SELECT customer_id FROM orders         WHERE status = 'COMPLETED'
    UNION
    SELECT customer_id FROM orders_archive WHERE status = 'COMPLETED'
) AS t
GROUP BY customer_id
ORDER BY customer_id;

    첫 블록은 주문 1, 2, 6, 7에서 고객 번호 1, 1, 5, 3을 낸다. 둘째 블록은 주문 101, 102에서 1, 2를 낸다. UNION이 중복을 지우면 1, 5, 3, 2 네 행만 남고, 모든 고객의 완료 주문 수가 1이 된다. 김하늘은 실제로 세 건(1, 2, 101)을 완료했다. UNION ALL로 바꾸면 여섯 행이 그대로 남아 올바른 값이 나온다.

    함정의 핵심은 블록이 고른 열에 각 행을 구별하는 값이 없다는 데 있다. order_id를 고르지 않았으므로 서로 다른 주문이 같은 행 (1)로 보인다. 행 수를 세거나 금액을 더하는 쿼리의 재료를 UNION으로 만들 때는 거의 언제나 UNION ALL이 맞다. 오류도 경고도 나지 않고 숫자만 조용히 작아지기 때문에, 테스트 데이터에 중복이 없으면 발견되지 않다가 실제 데이터에서 드러나는 종류의 버그다.

    UNION과 UNION ALL을 섞으면

    한 문장에 둘을 섞을 수 있다. 매뉴얼의 규칙은 DISTINCT를 쓰는 집합 연산이 그 왼쪽에 있는 ALL 연산을 덮어쓴다는 것이다. A UNION ALL B UNION C에서는 마지막 UNION이 왼쪽의 UNION ALL까지 덮으므로 A와 B 사이의 중복도 결국 제거된다. 반대로 A UNION B UNION ALL C는 왼쪽부터 처리되어 A와 B 사이의 중복은 제거하지만, C에서 온 행은 앞쪽 결과와 같아도 남는다. 섞어 쓴 쿼리는 읽는 사람이 이 규칙을 떠올려야 해석되므로, 의도가 분명하지 않으면 괄호로 단계를 나누거나 한 가지로 통일하는 편이 낫다.

    MySQL 8.0.31부터는 UNION 외에 INTERSECT(교집합)와 EXCEPT(차집합)도 지원한다. 세 연산 모두 결과 열 이름은 첫 블록에서 가져오고 기본 동작은 중복 제거다. 매뉴얼에 따르면 INTERSECT는 UNION과 EXCEPT보다 먼저 평가되므로 TABLE x UNION TABLE y INTERSECT TABLE z는 TABLE x UNION (TABLE y INTERSECT TABLE z)로 처리된다. 8.0.19부터는 SELECT 자리에 TABLE 문이나 VALUES 문을 블록으로 쓸 수도 있다.

    UNION 결과의 정렬: ORDER BY와 LIMIT은 어디에 붙는가

    마지막 블록 뒤에 쓴 ORDER BY와 LIMIT은 마지막 블록이 아니라 UNION 결과 전체에 적용된다. 앞의 도시 쿼리에서 ORDER BY city가 판매자 도시만이 아니라 아홉 행을 합친 결과를 정렬한 것이 그 예다. 이 전체 정렬에는 매뉴얼이 정한 몇 가지 규칙이 있다. 이 규칙들은 "정렬 대상은 특정 테이블의 열이 아니라 합쳐진 결과의 열"이라는 한 가지 사실에서 나온다.

    • 전체 결과를 정렬하는 ORDER BY에는 tbl_name.col_name처럼 테이블 이름이 붙은 열 참조를 쓸 수 없다. 합쳐진 결과에는 테이블이 없고 결과 열만 있기 때문이다. 첫 블록에서 별칭을 붙이고 그 별칭으로 정렬한다.
    • 정렬할 열에 별칭을 붙였다면 ORDER BY는 반드시 별칭을 써야 한다. 원래 열 이름을 쓰면 Unknown column ... in 'order clause' 오류가 난다.
    • 열의 위치 번호(ORDER BY 2)로도 정렬할 수 있지만 매뉴얼은 이 용법을 사용 중단 예정(deprecated)으로 분류한다.
    • 집계 함수를 쓴 ORDER BY는 집합 연산에서 거부된다.
    -- 허용되지 않는다: 결과 전체 정렬에 테이블 이름이 붙은 열 참조
SELECT c.name, c.city FROM customers c
UNION
SELECT s.name, s.city FROM sellers s
ORDER BY c.name;

-- 결과 열 이름으로 정렬한다
SELECT c.name, c.city FROM customers c
UNION
SELECT s.name, s.city FROM sellers s
ORDER BY name;
    ERROR 1250 (42000): Table 'c' from one of the SELECTs cannot be used in global ORDER clause

    집계 함수를 쓴 ORDER BY(예: ORDER BY COUNT(*))는 같은 두 버전에서 ERROR 3028 (HY000): Expression #1 of ORDER BY contains aggregate function and applies to a UNION, EXCEPT or INTERSECT로 거부된다.

    블록 하나에만 정렬과 개수 제한을 걸고 싶을 때도 있다. 카테고리마다 가장 비싼 상품 두 개씩을 한 목록으로 뽑는 경우다. 매뉴얼의 규칙은 해당 블록을 괄호로 감싸고 ORDER BY와 LIMIT을 괄호 안에 두라는 것이다. 블록 안의 ORDER BY나 LIMIT을 쓰면서 전체 결과에도 ORDER BY나 LIMIT을 걸려면 그런 블록은 반드시 괄호로 감싸야 한다.

    (SELECT name, category, price FROM products
  WHERE category = '전자' ORDER BY price DESC LIMIT 2)
UNION ALL
(SELECT name, category, price FROM products
  WHERE category = '문구' ORDER BY price DESC LIMIT 2)
ORDER BY price DESC;
    name    category  price
------  --------  ------
모니터  전자      300000
키보드  전자       50000
노트    문구        3000
볼펜    문구        1500

    첫 블록은 전자 상품 세 개(키보드 50000, 마우스 20000, 모니터 300000)를 가격 내림차순으로 세운 뒤 위의 두 개, 모니터와 키보드만 남긴다. 마우스는 여기서 빠진다. 둘째 블록은 문구 두 개를 모두 남긴다. 괄호 안의 ORDER BY는 "어떤 두 개를 고를 것인가"를 정하는 데 쓰였고, 최종 결과의 순서는 마지막 줄의 ORDER BY가 정했다. 두 ORDER BY의 역할이 다르다.

    여기서 흔한 오해가 나온다. 괄호 안에 ORDER BY만 쓰고 LIMIT을 쓰지 않으면, 각 블록이 정렬된 상태로 이어 붙을 것이라고 기대하기 쉽다. 매뉴얼은 반대로 말한다. 집합 연산의 결과는 기본적으로 순서가 없으므로 블록 안의 ORDER BY는 최종 결과의 순서에 대해 아무것도 약속하지 않으며, LIMIT 없이 블록 안에 나타난 ORDER BY는 어차피 효과가 없으므로 최적화 과정에서 제거된다. 올해 주문을 먼저, 그 안에서 날짜순으로, 그다음 보관 주문을 날짜순으로 보고 싶다면 블록의 출처를 나타내는 정렬용 열을 만들어 전체 ORDER BY에 쓴다.

    SELECT 1 AS src, order_id, order_date FROM orders
UNION ALL
SELECT 2, order_id, order_date FROM orders_archive
ORDER BY src, order_date;

    결과는 src가 1인 일곱 행(주문 1부터 7까지, 날짜순) 다음에 src가 2인 세 행(101, 102, 103)이 온다. 순서를 원하면 그 순서를 정하는 값을 데이터로 만들어 정렬하라는 것이 이 절의 결론이다. 이 원칙은 다음 절의 CASE 식과도 이어진다. 상태를 PENDING, SHIPPED, COMPLETED 순으로 보고 싶을 때처럼 정렬 순서가 문자열 순서와 다르면, CASE로 정렬용 값을 만들어 ORDER BY에 쓴다.

    CASE 식 기본: 조건에 따라 다른 값을 돌려준다

    상품 목록에 재고 수 대신 '품절', '부족', '충분'을 보여 주고 싶다고 하자. 테이블에는 그 문자열이 없다. 애플리케이션에서 숫자를 받아 변환할 수도 있지만, 그 값으로 정렬하거나 묶거나 개수를 세려면 변환이 SQL 안에서 일어나야 한다. 행마다 조건을 따져 다른 값을 돌려주는 것이 CASE 식이다. MySQL 매뉴얼은 두 가지 형식을 정의한다.

    -- 단순 CASE (simple CASE): 값 하나를 여러 후보와 비교한다
CASE value WHEN compare_value THEN result
          [WHEN compare_value THEN result ...]
          [ELSE result]
END

-- 검색 CASE (searched CASE): WHEN마다 독립된 조건을 쓴다
CASE WHEN condition THEN result
    [WHEN condition THEN result ...]
    [ELSE result]
END

    매뉴얼의 규칙은 짧다. 단순 CASE는 value = compare_value 비교가 처음으로 참이 되는 WHEN의 result를 돌려준다. 검색 CASE는 처음으로 참이 되는 condition의 result를 돌려준다. 어떤 비교나 조건도 참이 아니면 ELSE 뒤의 값을 돌려주고, ELSE가 없으면 NULL을 돌려준다. 이 세 문장에서 실무에 중요한 성질 세 가지가 나온다. 위에서 아래로 보다가 첫 번째로 참인 WHEN에서 결과가 정해진다. 조건은 참이어야 하므로 거짓(FALSE)과 알 수 없음(UNKNOWN, 곧 NULL)은 똑같이 다음 WHEN으로 넘어간다. ELSE를 생략하는 것은 ELSE NULL을 쓰는 것과 같다.

    CASE는 식(expression)이므로 값이 들어갈 수 있는 자리라면 어디든 쓸 수 있다. SELECT 목록, WHERE, GROUP BY, HAVING, ORDER BY, UPDATE의 SET 절이 모두 그런 자리다. 저장 프로시저 안에서 쓰는 CASE 문은 이름이 같지만 다른 문법이다. 매뉴얼은 CASE 문이 ELSE NULL 절을 가질 수 없고 END가 아니라 END CASE로 끝난다는 차이를 명시한다. CASE 문은 09회에서 다룬다.

    SELECT name, stock,
       CASE
           WHEN stock = 0 THEN '품절'
           WHEN stock < 5 THEN '부족'
           ELSE '충분'
       END AS stock_status
FROM products;
    name    stock  stock_status
------  -----  ------------
키보드     10  충분
마우스      0  품절
모니터      3  부족
노트      120  충분
볼펜        4  부족

    행마다 따라가 보자. 키보드는 재고 10이다. stock = 0은 거짓, stock < 5도 거짓이므로 ELSE의 '충분'이 된다. 마우스는 재고 0이다. 첫 조건이 참이므로 '품절'이 되고 결과가 정해진다. 모니터는 첫 조건이 거짓이고 두 번째 조건 3 < 5가 참이므로 '부족'이다. 노트는 '충분', 볼펜은 4라서 '부족'이다.

    마우스 행이 첫 번째 성질을 보여 준다. 0은 5보다 작으므로 두 번째 조건도 참이지만 결과는 '부족'이 아니라 '품절'이다. 첫 번째로 참이 된 WHEN에서 결과가 정해지기 때문이다. 따라서 WHEN의 순서는 의미의 일부다. 조건의 범위가 겹칠 때는 더 좁은 조건을 위에 둬야 한다.

    조건의 순서가 바뀌면

    상품을 가격대로 나누는 CASE를 다음처럼 썼다고 하자. 10만 원 이상은 고가, 1만 원 이상은 중가, 나머지는 저가로 나누려는 의도다.

    SELECT name, price,
       CASE
           WHEN price >= 10000  THEN '중가'
           WHEN price >= 100000 THEN '고가'
           ELSE '저가'
       END AS price_band
FROM products;
    name    price   price_band
------  ------  ----------
키보드   50000  중가
마우스   20000  중가
모니터  300000  중가
노트      3000  저가
볼펜      1500  저가

    모니터가 중가로 분류되었다. 300000은 10000 이상이므로 첫 WHEN이 참이 되고, 두 번째 WHEN은 볼 기회조차 없다. '고가'라는 값은 이 CASE에서 영원히 나올 수 없다. 문법 오류도 경고도 없으므로 결과를 눈으로 확인하기 전에는 알아채기 어렵다. 고치는 방법은 두 가지다. 좁은 범위(price >= 100000)를 위로 올리거나, 각 WHEN이 서로 겹치지 않도록 price >= 10000 AND price < 100000처럼 범위를 양쪽으로 닫는다. 앞의 방법은 짧고, 뒤의 방법은 순서를 바꿔도 의미가 변하지 않아 안전하다.

    단순 CASE와 NULL

    등급마다 할인율을 붙이는 것처럼 한 열의 값을 여러 상수와 비교할 때는 단순 CASE가 읽기 쉽다.

    SELECT name, grade,
       CASE grade
           WHEN 'VIP'  THEN 0.10
           WHEN 'GOLD' THEN 0.05
           ELSE 0
       END AS discount_rate
FROM customers;

    결과는 김하늘이 0.10, 이바다와 정노을이 0.05, 박구름과 최별이 0이다. 단순 CASE는 검색 CASE의 줄임말이다. CASE grade WHEN 'VIP' THEN ...은 CASE WHEN grade = 'VIP' THEN ...과 같은 뜻이다. 매뉴얼이 단순 CASE의 규칙을 "value = compare_value 비교가 참"으로 적은 데서 알 수 있듯이, 내부적으로 등호 비교를 한다. 이 사실이 NULL과 만나면 함정이 된다.

    SELECT name, city,
       CASE city WHEN NULL THEN '미등록' ELSE city END       AS wrong_label,
       CASE WHEN city IS NULL THEN '미등록' ELSE city END    AS right_label
FROM customers;
    name    city  wrong_label  right_label
------  ----  -----------  -----------
김하늘  서울  서울         서울
이바다  부산  부산         부산
박구름  서울  서울         서울
최별    대전  대전         대전
정노을  NULL  NULL         미등록

    정노을 행에서 wrong_label은 '미등록'이 아니라 NULL이다. CASE city WHEN NULL은 city = NULL을 평가하는데, 이 비교는 city가 무엇이든 UNKNOWN이다. 참이 아니므로 ELSE로 넘어가고, ELSE가 돌려준 city 값이 NULL이었다. 결국 이 WHEN은 어떤 행에서도 참이 될 수 없는 죽은 분기다. NULL을 가려내려면 검색 CASE에서 IS NULL을 써야 한다. NULL을 다른 값으로 바꾸는 것이 목적이라면 IFNULL(city, '미등록')이나 COALESCE(city, '미등록')이 더 짧다.

    MySQL에는 두 갈래짜리 CASE를 줄여 쓰는 IF(expr1, expr2, expr3) 함수도 있다. 매뉴얼에 따르면 expr1이 참(0이 아니고 NULL도 아님)이면 expr2를, 아니면 expr3을 돌려준다. 여기서도 NULL은 참이 아닌 쪽으로 간다. IF 함수는 MySQL의 확장이고 CASE 식은 SQL 표준 문법이므로, 다른 데이터베이스로 옮길 가능성이 있는 쿼리라면 CASE를 쓰는 편이 안전하다.

    결과 타입: 모든 분기는 하나의 타입이 된다

    CASE 식 전체는 결과에서 하나의 열이 되므로 하나의 타입을 가져야 한다. 그런데 THEN과 ELSE에는 서로 다른 타입의 값이 올 수 있다. MySQL은 이 값들의 타입을 모아 하나의 집계된 타입(aggregated type)을 정한다. 매뉴얼에 적힌 규칙 가운데 자주 만나는 것을 추리면 다음과 같다.

    THEN·ELSE 값의 타입 구성CASE 결과 타입

    모두 문자열(CHAR, VARCHAR)VARCHAR, 길이는 가장 긴 값에 맞춘다

    앞의 할인율 CASE는 0.10, 0.05, 0이 섞여 있다. 실수가 없고 DECIMAL 리터럴이 있으므로 결과는 DECIMAL이다. 문제가 되는 것은 문자열과 숫자를 섞는 경우다. 재고가 0이면 '품절'이라고 쓰고 아니면 재고 수를 그대로 보여 주는 다음 CASE를 보자.

    SELECT name,
       CASE WHEN stock = 0 THEN '품절' ELSE stock END AS stock_label
FROM products
ORDER BY stock_label;

    THEN은 문자열, ELSE는 정수이므로 표의 마지막 규칙에 따라 결과 타입은 VARCHAR이다. 그러면 ORDER BY도 숫자가 아니라 문자열 비교로 정렬한다. 결과는 '10'(키보드), '120'(노트), '3'(모니터), '4'(볼펜), '품절'(마우스) 순이다. 문자열 비교는 첫 글자부터 하므로 '120'이 '3'보다 앞에 온다. 화면에 보이는 값은 멀쩡한데 정렬과 비교가 어긋나는 것이다. THEN과 ELSE의 타입을 맞추고, 표시용 문자열이 필요하면 숫자로 정렬하는 열을 따로 두거나 표시 변환을 애플리케이션으로 넘기는 것이 정석이다.

    CASE로 정렬 순서 만들기

    CASE는 ORDER BY에서도 쓸 수 있다. 주문을 처리가 급한 순서, 곧 PENDING, SHIPPED, COMPLETED, CANCELLED 순으로 보고 싶다고 하자. 이 순서는 알파벳 순서와 다르다. 상태마다 순번을 돌려주는 CASE를 정렬 키로 쓴다.

    SELECT order_id, status
FROM orders
ORDER BY CASE status
             WHEN 'PENDING'   THEN 1
             WHEN 'SHIPPED'   THEN 2
             WHEN 'COMPLETED' THEN 3
             ELSE 4
         END,
         order_id;
    order_id  status
--------  ---------
       4  PENDING
       3  SHIPPED
       1  COMPLETED
       2  COMPLETED
       6  COMPLETED
       7  COMPLETED
       5  CANCELLED

    정렬 키는 결과에 나타나지 않아도 된다. 행마다 계산된 1~4의 값으로 먼저 정렬하고, 같은 값끼리는 order_id로 정렬했다. 앞 절의 결론, 곧 원하는 순서를 값으로 만들어 정렬한다는 원칙을 그대로 적용한 것이다. 다만 이렇게 계산된 값으로 정렬하면 인덱스의 순서를 그대로 이용할 수 없으므로 엔진은 행을 모아 따로 정렬한다. 인덱스와 정렬의 관계는 05회와 06회에서 다룬다.

    CASE로 그룹 만들기

    GROUP BY는 같은 값을 가진 행을 하나로 묶는다. 그런데 묶고 싶은 기준이 테이블에 값으로 존재하지 않을 때가 많다. 가격대별 상품 수는 price 열로 묶으면 가격이 다른 상품마다 그룹이 생긴다. CASE로 가격대라는 값을 행마다 만들고 그 값으로 묶으면 된다.

    SELECT CASE
           WHEN price >= 100000 THEN '고가'
           WHEN price >= 10000  THEN '중가'
           ELSE '저가'
       END        AS price_band,
       COUNT(*)   AS product_count,
       SUM(stock) AS total_stock
FROM products
GROUP BY price_band;

    엔진이 하는 일을 순서대로 보면, 먼저 products의 각 행에서 CASE를 계산해 가격대를 붙이고, 그 값이 같은 행끼리 모은 뒤, 그룹마다 COUNT와 SUM을 계산한다.

    상품priceCASE 결과stock
    키보드50000중가10
    마우스20000중가0
    모니터300000고가3
    노트3000저가120
    볼펜1500저가4
    price_band  product_count  total_stock
----------  -------------  -----------
중가                    2           10
고가                    1            3
저가                    2          124

    여기에는 짚어 둘 것이 세 가지 있다. 첫째, 논리적 처리 순서로는 GROUP BY가 SELECT보다 먼저인데 GROUP BY에서 SELECT의 별칭 price_band를 썼다. 표준 SQL은 GROUP BY에 별칭을 허용하지 않는다. MySQL 매뉴얼은 이것을 표준을 확장한 기능으로 명시하고, 별칭을 GROUP BY 안의 열 식으로 취급한다고 설명한다. 같은 매뉴얼은 GROUP BY에 열이 아닌 식(예: FLOOR(value/100))을 쓰는 것도 MySQL의 확장이라고 적는다. 다른 데이터베이스와 함께 쓸 쿼리라면 CASE 식을 GROUP BY에 그대로 반복하거나, 03회에서 본 파생 테이블 안에서 CASE로 열을 만든 뒤 바깥에서 그 열로 묶는다.

    둘째, MySQL은 ONLY_FULL_GROUP_BY SQL 모드가 기본으로 켜져 있다. 이 모드에서는 SELECT 목록, HAVING, ORDER BY에 나오는 집계되지 않은 열이 GROUP BY에 있거나 GROUP BY 열에 함수적으로 종속되어야 한다. 위 쿼리에 name을 추가하면 거부된다. 한 그룹에 상품이 여럿인데 어느 이름을 보여 줄지 정해지지 않기 때문이다. GROUP BY에 열이 아닌 식을 쓴 경우, MySQL은 SELECT 목록에 똑같은 식이 있으면 둘을 같은 것으로 인식한다. 그래서 CASE 식을 GROUP BY와 SELECT에 똑같이 반복해 써도 이 모드를 통과한다. 반면 매뉴얼에 따르면 MySQL은 열이 아닌 GROUP BY 식에 대한 함수적 종속은 추론하지 않으므로, 그 식을 재료로 만든 다른 식을 SELECT에 넣으면 거부될 수 있다. 이때 매뉴얼이 권하는 우회로가 파생 테이블이다.

    셋째, 결과의 순서다. MySQL 8.0의 GROUP BY는 결과를 정렬해 주지 않으므로 순서가 필요하면 ORDER BY를 쓴다. 그런데 ORDER BY price_band로 정렬하면 문자열 순서로 고가, 저가, 중가가 된다. 사람이 기대하는 순서(고가, 중가, 저가)와 다르다. 그룹마다 대표 값을 집계로 구해 정렬하면 의미대로 정렬된다. ORDER BY MIN(price) DESC를 붙이면 고가(최저 300000), 중가(최저 20000), 저가(최저 1500) 순이 된다. 집계 함수이므로 ONLY_FULL_GROUP_BY 모드도 통과한다.

    엔진 쪽에서 보면 CASE 식의 값은 어디에도 저장되어 있지 않으므로 그 값 순서로 정렬된 인덱스가 있을 수 없다. 엔진은 행을 읽을 때마다 CASE를 계산하고 같은 값끼리 모아야 한다. 인덱스 순서를 따라 그룹을 차례로 완성할 수 없을 때 MySQL은 그룹별 중간 결과를 임시 테이블에 모으는 방식을 고를 수 있고, 그러면 EXPLAIN의 Extra 열에 Using temporary가 나타난다. 위의 가격대 쿼리를 MySQL 8.4.13과 8.0.46에서 EXPLAIN하면 products에 대한 SIMPLE 행 하나(type ALL)의 Extra에 실제로 Using temporary가 나온다. 이 쿼리처럼 상품 다섯 개라면 아무 문제가 없지만, 수백만 행을 이런 식으로 묶으면 UNION에서 본 것과 같은 임시 테이블 비용이 생긴다.

    CASE 그룹은 값의 범위를 나누는 데만 쓰이지 않는다. 여러 값을 하나로 합칠 때도 쓴다. CASE WHEN grade IN ('VIP', 'GOLD') THEN '우수' ELSE '일반' END로 묶으면 고객 다섯 명이 우수 3명(김하늘, 이바다, 정노을)과 일반 2명(박구름, 최별)으로 나뉜다. 저장된 분류 체계와 보고서가 원하는 분류 체계가 다를 때 테이블을 바꾸지 않고 질의 시점에 분류를 다시 짜는 방법이다.

    조건부 집계: 행을 열로 펼친다

    이번에는 고객별 주문 현황을 한 줄로 보고 싶다. 이름, 전체 주문 수, 완료 수, 취소 수, 진행 중(PENDING 또는 SHIPPED) 수를 열로 나란히 놓는 표다. GROUP BY customer_id, status로 묶으면 숫자는 나오지만 고객 한 명이 상태 개수만큼 여러 행으로 흩어진다. 원하는 것은 행 방향으로 흩어진 값을 열 방향으로 펼치는 것, 흔히 피벗(pivot)이라고 부르는 모양이다.

    열쇠는 두 가지 사실의 결합이다. 하나는 집계 함수가 NULL을 무시한다는 것이다. MySQL 매뉴얼은 COUNT(), MIN(), SUM() 같은 집계 함수가 NULL 값을 무시하며, 예외는 열 값이 아니라 행을 세는 COUNT(*)뿐이라고 적고 있다. 다른 하나는 CASE가 행마다 "이 행을 셀 값으로 쓸지, 0이나 NULL로 만들어 빼 버릴지"를 정할 수 있다는 것이다. 집계 함수 안에 CASE를 넣으면, 같은 그룹의 행들 가운데 조건에 맞는 행만 골라 집계하는 열을 여러 개 만들 수 있다. 이것을 조건부 집계(conditional aggregation)라고 부른다.

    SELECT c.name,
       COUNT(o.order_id)                                              AS total,
       SUM(CASE WHEN o.status = 'COMPLETED' THEN 1 ELSE 0 END)        AS completed,
       SUM(CASE WHEN o.status = 'CANCELLED' THEN 1 ELSE 0 END)        AS cancelled,
       COUNT(CASE WHEN o.status IN ('PENDING', 'SHIPPED') THEN 1 END) AS in_progress
FROM customers c
JOIN orders o ON o.customer_id = c.customer_id
GROUP BY c.customer_id, c.name
ORDER BY c.customer_id;

    엔진은 조인 결과의 각 행에서 세 CASE를 모두 계산한다. 아래 표가 그 중간 상태다. completed와 cancelled 열은 ELSE 0이 있어서 조건에 맞지 않으면 0이 되고, in_progress 열은 ELSE가 없어서 NULL이 된다.

    name    total  completed  cancelled  in_progress
------  -----  ---------  ---------  -----------

이바다      2          0          1            1

    최별은 결과에 없다. 올해 주문이 없어 내부 조인에서 짝을 찾지 못했기 때문이다. 주문이 없는 고객도 0으로 보여 주려면 02회의 외부 조인(LEFT JOIN)을 쓴다. 그때 COUNT(o.order_id)를 쓴 이유가 드러난다. 외부 조인에서 짝이 없는 고객 행은 o의 열이 모두 NULL이므로 COUNT(o.order_id)는 0을 세지만 COUNT(*)는 행이 하나 있으므로 1을 센다.

    주문 행마다 CASE가 1, 0, NULL을 붙이고, 고객별로 묶어 SUM과 COUNT가 그 값을 모으면 상태별 건수가 열로 펼쳐진다는 것을 보여 준다. 흰 배경, 왼쪽에서 오른쪽으로 세 단계로 흐르는 교육용 그림. 1단계(왼쪽): 세로로 긴 표 "주문 행", 각 행에 고객 이름과 상태 칸이 있고 상태 칸이 초록(COMPLETED), 빨강(CANCELLED), 노랑(PENDING/SHIPPED)으로 칠해져 있다. 2단계(가운데): 같은 행들 오른쪽에 세 개의 좁은 열이 붙어 있고 열 머리 라벨은 "완료", "취소", "진행 중". 각 칸에는 1, 0, 또는 회색 NULL이 적혀 있다. 이 단계 위에 라벨 "행마다 CASE 계산". 3단계(오른쪽): 고객 이름당 한 줄씩인 짧은 표, 열 머리 "완료", "취소", "진행 중" 아래에 합계 숫자. 2단계에서 3단계로 같은 고객의 행들이 깔때기 모양으로 모이는 화살표와 라벨 "고객별로 묶어 SUM / COUNT". 아래쪽에 작은 주석 "NULL은 집계에서 빠진다". 평면 스타일. CASE가 행마다 집계에 넣을 값을 정하고, GROUP BY와 집계 함수가 그 값을 고객별로 모은다.

    SUM과 COUNT, ELSE 0과 ELSE 생략

    조건에 맞는 행의 개수를 세는 방법은 두 가지다. SUM(CASE WHEN 조건 THEN 1 ELSE 0 END)은 맞는 행에 1, 아닌 행에 0을 주고 더한다. COUNT(CASE WHEN 조건 THEN 1 END)는 맞는 행에 1, 아닌 행에 NULL을 주고 NULL이 아닌 것을 센다. 둘 다 맞다. 위험한 것은 두 방식을 섞은 형태다.

    SELECT COUNT(CASE WHEN status = 'COMPLETED' THEN 1 ELSE 0 END) AS wrong_count,
       COUNT(CASE WHEN status = 'COMPLETED' THEN 1 END)        AS right_count
FROM orders;
    wrong_count  right_count
-----------  -----------
          7            4

    wrong_count는 완료 주문이 아니라 전체 주문 수 7을 셌다. COUNT는 값이 1인지 0인지 보지 않고 NULL인지 아닌지만 본다. 0은 NULL이 아니므로 모든 행이 세어진다. COUNT 안의 CASE에는 ELSE를 쓰지 않고, SUM 안의 CASE에는 ELSE 0을 쓴다고 기억하면 된다.

    ELSE 0을 쓰느냐는 조건에 맞는 행이 하나도 없을 때도 차이를 만든다. 아무 행도 맞지 않는 조건으로 집계해 보자. SUM(CASE WHEN status = 'REFUNDED' THEN 1 END)는 NULL이고, SUM(CASE WHEN status = 'REFUNDED' THEN 1 ELSE 0 END)는 0이다. 앞의 것은 더할 값이 모두 NULL이어서 무시되고, 더할 값이 하나도 없는 SUM은 NULL을 돌려준다. 보고서에서 "0건"과 "값 없음"은 다르게 읽히고, 애플리케이션에서 NULL을 숫자로 받다가 예외가 나기도 한다. 0이 필요한 자리라면 ELSE 0을 쓰거나 COALESCE(SUM(...), 0)으로 감싼다. 반면 COUNT(CASE ...)는 맞는 행이 없으면 NULL이 아니라 0을 돌려준다.

    MySQL에서 비교 연산의 결과는 1(참), 0(거짓), NULL이다. 그래서 MySQL에서는 SUM(status = 'COMPLETED')만으로도 완료 건수를 셀 수 있다. 짧지만 MySQL의 동작에 기대는 표현이므로, 다른 데이터베이스와 함께 쓰거나 읽는 사람이 다양하다면 CASE 형태가 의도를 더 분명히 드러낸다.

    금액 피벗: 카테고리 × 월

    조건부 집계는 개수만이 아니라 금액에도 쓴다. 취소를 뺀 올해 주문 금액을 카테고리별로, 1월부터 3월까지 월별 열로 펼쳐 보자. THEN 뒤에 1 대신 금액 식을 쓰면 된다.

    SELECT p.category,
       SUM(CASE WHEN o.order_date >= '2025-01-01' AND o.order_date < '2025-02-01'
                THEN p.price * o.quantity ELSE 0 END) AS jan,
       SUM(CASE WHEN o.order_date >= '2025-02-01' AND o.order_date < '2025-03-01'
                THEN p.price * o.quantity ELSE 0 END) AS feb,
       SUM(CASE WHEN o.order_date >= '2025-03-01' AND o.order_date < '2025-04-01'
                THEN p.price * o.quantity ELSE 0 END) AS mar
FROM orders o
JOIN products p ON p.product_id = o.product_id
WHERE o.status <> 'CANCELLED'
GROUP BY p.category
ORDER BY p.category;
    category  jan    feb     mar
--------  -----  ------  -----
문구          0   30000  30000
전자      90000  300000  20000

    확인해 보자. 취소된 5번 주문은 WHERE에서 빠진다. 전자의 1월은 주문 1(50000)과 주문 2(40000)를 더한 90000이다. 2월은 주문 3의 모니터 300000, 3월은 주문 7의 마우스 20000이다. 문구는 1월 주문이 없어 ELSE 0만 더해져 0이 되고, 2월은 주문 4의 노트 30000, 3월은 주문 6의 볼펜 30000이다. 날짜 조건을 MONTH(order_date) = 1이 아니라 범위로 쓴 것은 연도가 다른 1월(예: 보관 테이블의 행이 섞일 때)을 구분하기 위해서다.

    한 번 읽기와 여러 번 읽기

    같은 결과를 상태마다 쿼리를 따로 써서 만들 수도 있다. 완료 건수를 세는 쿼리, 취소 건수를 세는 쿼리, 진행 중 건수를 세는 쿼리를 각각 실행해 애플리케이션에서 합치거나, UNION ALL로 이어 붙인 뒤 다시 집계하는 식이다. 결과는 같아도 엔진이 하는 일은 다르다. status에 쓸 만한 인덱스가 없다면 쿼리 세 개는 orders를 처음부터 끝까지 세 번 읽는다. 조건부 집계는 orders를 한 번 읽으면서 행마다 CASE 세 개를 계산하고 세 개의 누적 값을 동시에 갱신한다. 행마다 하는 계산은 조금 늘지만 행을 읽는 횟수가 줄어든다. 큰 테이블에서 비용을 지배하는 것은 대개 행을 가져오는 일(페이지를 읽고 행을 해석하는 일)이므로 이 차이가 의미를 가진다.

    조건부 집계에도 한계가 있다. 결과에 어떤 열이 있는지는 쿼리를 쓰는 시점에 정해져야 한다. SQL 문장의 결과 열 목록은 실행 전에 확정되기 때문이다. 내일 'RETURNED'라는 새 상태가 생기면 GROUP BY customer_id, status로 쓴 행 방향 쿼리는 아무것도 고치지 않아도 새 상태를 보여 주지만, 조건부 집계 쿼리는 열을 하나 더 써 넣기 전까지 새 상태를 보여 주지 않는다. 그 상태의 주문은 어느 열에도 들어가지 않고 total에만 잡힌다. 값의 종류가 고정되어 있고 사람이 읽을 표가 필요하면 조건부 집계를, 값의 종류가 자주 바뀌거나 프로그램이 받아 가공할 데이터라면 행 방향 결과를 쓰는 편이 낫다.

    뷰: 쿼리에 이름을 붙인다

    주문 상세(누가, 무엇을, 얼마에)를 보려면 매번 세 테이블을 조인하고 금액을 계산해야 한다. 이 조인이 열 군데에 흩어져 있으면, 금액 계산 규칙이 바뀌는 날 열 군데를 모두 고쳐야 한다. 쿼리 자체에 이름을 붙여 데이터베이스에 저장해 두고 테이블처럼 부를 수 있다면 이 문제가 사라진다. 그것이 뷰다. 뷰는 결과를 저장하지 않는다. 저장하는 것은 SELECT 문, 곧 결과를 만드는 방법이다. 그래서 뷰를 가상 테이블(virtual table)이라고도 부른다.

    생성과 조회

    CREATE VIEW order_details AS
SELECT o.order_id,
       o.order_date,
       o.status,
       c.customer_id,
       c.name               AS customer_name,
       c.grade,
       p.product_id,
       p.name               AS product_name,
       p.category,
       p.price,
       o.quantity,
       p.price * o.quantity AS amount
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
JOIN products  p ON p.product_id  = o.product_id;

    별칭 customer_name과 product_name은 멋을 내려고 붙인 것이 아니다. customers와 products 모두 name 열을 가지고 있다. 매뉴얼은 뷰도 기본 테이블처럼 열 이름이 중복되지 않아야 한다고 정하고 있으므로, 별칭 없이 둘 다 고르면 뷰를 만들 수 없다(MySQL 8.4.13과 8.0.46에서 ERROR 1060 (42S21): Duplicate column name 'name'). 기본적으로 SELECT가 고른 열의 이름이 뷰의 열 이름이 되며, CREATE VIEW order_details (col1, col2, ...) AS ...처럼 뷰 이름 뒤에 열 이름 목록을 직접 줄 수도 있다. 이때 목록의 개수는 SELECT가 고르는 열의 개수와 같아야 한다.

    만든 뒤에는 테이블처럼 조회한다.

    SELECT customer_name, SUM(amount) AS total
FROM order_details
WHERE status = 'COMPLETED'
GROUP BY customer_id, customer_name
ORDER BY total DESC;
    customer_name  total
-------------  -----
김하늘         90000
정노을         30000
박구름         20000

    조회하는 쪽은 조인이 몇 개인지, 금액을 어떻게 계산하는지 몰라도 된다. 완료 주문은 1, 2(김하늘, 50000 + 40000), 6(정노을, 30000), 7(박구름, 20000)이다. 뷰 이름은 테이블과 같은 이름 공간(namespace)을 쓴다. 매뉴얼에 따르면 한 데이터베이스 안에서 기본 테이블과 뷰는 같은 이름을 가질 수 없다. SHOW FULL TABLES를 실행하면 뷰는 Table_type이 VIEW인 행으로 테이블과 함께 나온다.

    수정과 삭제

    뷰의 정의를 바꾸는 방법은 두 가지다. CREATE OR REPLACE VIEW는 같은 이름의 뷰가 없으면 새로 만들고, 있으면 정의를 바꿔 끼운다. ALTER VIEW는 이미 존재하는 뷰의 정의를 바꾸며 문법은 CREATE VIEW와 비슷하다. 뷰를 없애는 것은 DROP VIEW다. DROP VIEW IF EXISTS order_details처럼 쓰면 뷰가 없어도 오류가 나지 않는다. 뷰를 지워도 기반 테이블의 데이터는 그대로다. 지워지는 것은 저장된 쿼리뿐이다.

    -- 정의 바꾸기: 취소된 주문은 뷰에서 처음부터 빼 버린다
CREATE OR REPLACE VIEW order_details AS
SELECT o.order_id, o.order_date, o.status,
       c.customer_id, c.name AS customer_name, c.grade,
       p.product_id, p.name AS product_name, p.category, p.price,
       o.quantity, p.price * o.quantity AS amount
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
JOIN products  p ON p.product_id  = o.product_id
WHERE o.status <> 'CANCELLED';

-- 정의 확인
SHOW CREATE VIEW order_details;
SELECT TABLE_NAME, IS_UPDATABLE, CHECK_OPTION, SECURITY_TYPE
FROM INFORMATION_SCHEMA.VIEWS
WHERE TABLE_SCHEMA = DATABASE();

-- 삭제
DROP VIEW IF EXISTS order_details;

    이후 예제는 처음의 정의(취소 주문을 포함하는 order_details)를 기준으로 한다. 뷰의 정의는 MySQL 8.0에서 데이터 딕셔너리(data dictionary)에 저장되고, SHOW CREATE VIEW나 INFORMATION_SCHEMA.VIEWS의 VIEW_DEFINITION 열로 확인할 수 있다.

    정의는 만들 때 굳는다

    뷰에 관해 가장 자주 놀라는 사실은 정의가 생성 시점에 고정된다는 것이다. 매뉴얼의 표현으로는 뷰 정의가 생성 시점에 "동결(frozen)"되며 이후 기반 테이블의 정의 변경에 영향을 받지 않는다. 예를 들어 CREATE VIEW v AS SELECT * FROM customers로 뷰를 만든 뒤 customers에 email 열을 추가해도 v에는 email이 나타나지 않는다. 별표는 뷰를 만드는 순간의 열 목록으로 펼쳐져 저장되기 때문이다. SHOW CREATE VIEW로 보면 별표 대신 열 이름이 하나하나 나열되어 있다. MySQL 8.4.13과 8.0.46에서 실행하면 정의 부분이 select `customers`.`customer_id` AS `customer_id`,`customers`.`name` AS `name`,`customers`.`grade` AS `grade`,`customers`.`city` AS `city` from `customers`로 저장되어 있고, customers에 email 열을 추가한 뒤 SELECT * FROM v를 해도 결과 열은 네 개 그대로다.

    반대로 기반 테이블에서 뷰가 쓰는 열을 지우거나 테이블 자체를 지우면, 그 뷰를 쓰는 순간 오류가 난다. 매뉴얼은 이때 DROP TABLE이나 ALTER TABLE 시점에는 경고가 전혀 나오지 않고 뷰를 사용할 때 비로소 오류가 난다고 적고 있다. 스키마를 바꾼 배포가 성공한 뒤 며칠 동안 아무도 쓰지 않던 보고서 화면이 그제야 깨지는 일이 이렇게 생긴다. 매뉴얼이 권하는 점검 도구는 CHECK TABLE이며, 무효가 된 뷰를 찾아낸다. MySQL 8.4.13과 8.0.46에서 뷰가 쓰는 열을 ALTER TABLE ... DROP COLUMN으로 지우면 경고 없이 성공하고, 그 뒤 뷰를 조회하면 ERROR 1356 (HY000): View 'm_db_basic_04.v_t' references invalid table(s) or column(s) or function(s) or definer/invoker of view lack rights to use them이 난다(m_db_basic_04와 v_t는 확인에 쓴 데이터베이스와 뷰의 이름이다). 같은 뷰에 CHECK TABLE을 실행하면 Msg_type이 Error인 행에 같은 문구가, 이어지는 행에 Corrupt가 나온다.

    뷰 정의에 ORDER BY를 넣을 수는 있다. 그러나 매뉴얼에 따르면 뷰를 조회하는 문장에 자체 ORDER BY가 있으면 뷰 정의의 ORDER BY는 무시된다. 순서는 조회하는 쪽에서 정한다고 생각하는 편이 안전하다. 그 밖의 제약으로는 뷰 정의에서 시스템 변수나 사용자 변수, 준비된 문장의 매개변수를 참조할 수 없고, TEMPORARY 테이블을 참조할 수 없으며, 뷰에 트리거를 걸 수 없다는 것이 있다.

    뷰를 조회하면 일어나는 일: MERGE와 TEMPTABLE

    뷰가 쿼리를 저장한 것이라면, 뷰를 조회하는 쿼리는 결국 "쿼리를 재료로 쓰는 쿼리"다. 03회에서 본 FROM 절의 서브쿼리, 곧 파생 테이블(derived table)과 같은 구조다. MySQL이 이것을 처리하는 방법은 두 가지이고, 뷰를 만들 때 ALGORITHM 절로 지정할 수 있다. 매뉴얼의 정의는 다음과 같다.

    • MERGE: 뷰를 참조하는 문장의 텍스트와 뷰 정의를 합쳐, 뷰 정의의 각 부분이 문장의 해당 부분을 대신하게 한다.
    • TEMPTABLE: 뷰의 결과를 임시 테이블로 가져온 다음 그 임시 테이블로 문장을 실행한다.
    • UNDEFINED: MySQL이 고른다. 가능하면 TEMPTABLE보다 MERGE를 선호한다. MERGE가 대개 더 효율적이고, 임시 테이블을 쓰면 뷰를 갱신할 수 없기 때문이다.

    ALGORITHM 절을 생략하면 기본 동작은 optimizer_switch 시스템 변수의 derived_merge 플래그가 정하며, 이 플래그는 기본으로 켜져 있어 합칠 수 있는 뷰는 합친다. 합칠 수 없는 뷰에 ALGORITHM = MERGE를 지정하면 MySQL은 경고를 내고 알고리즘을 UNDEFINED로 바꾼다. MySQL 8.4.13과 8.0.46에서 GROUP BY가 있는 뷰를 ALGORITHM = MERGE로 만들면 뷰는 만들어지고 Warning (Code 1354): View merge algorithm can't be used here for now (assumed undefined algorithm)가 나온다.

    MERGE: 뷰가 사라진다

    order_details에서 주문 하나를 조회해 보자.

    SELECT customer_name, amount
FROM order_details
WHERE order_id = 3;

    MERGE로 처리하면 뷰 이름 자리에 뷰 정의의 FROM 절이 들어가고, 뷰의 열 이름은 정의 속의 식으로 바뀌며, 바깥 WHERE는 뷰 정의의 WHERE와 AND로 합쳐진다. 매뉴얼의 예는 뷰의 WHERE와 바깥 WHERE가 괄호로 감싸진 채 AND로 이어지는 모습을 보여 준다. order_details에는 WHERE가 없으므로 합친 결과는 다음과 같다.

    SELECT c.name AS customer_name, p.price * o.quantity AS amount
FROM orders o
JOIN customers c ON c.customer_id = o.customer_id
JOIN products  p ON p.product_id  = o.product_id
WHERE (o.order_id = 3);

    옵티마이저 앞에는 이제 뷰가 없다. 조인을 직접 쓴 쿼리와 같은 재료로 실행 계획을 세운다. o.order_id = 3은 orders의 기본 키 조건이므로 행 하나를 바로 찾고, 그 행의 customer_id와 product_id로 두 테이블을 기본 키로 찾아 들어간다. 결과는 이바다, 300000 한 행이다. EXPLAIN의 table 열에도 뷰 이름이 아니라 o, c, p가 나온다. 매뉴얼은 MERGE로 처리되는 뷰는 기반 테이블의 인덱스를 쓸 수 있다고 명시한다. 잘 정의된 MERGE 뷰는 실행 단계에서 조인을 직접 쓴 것과 같은 계획을 얻을 수 있다는 뜻이다.

    +----+-------------+-------+------------+-------+---------------+---------+---------+-------+------+----------+-------+
| id | select_type | table | partitions | type  | possible_keys | key     | key_len | ref   | rows | filtered | Extra |
+----+-------------+-------+------------+-------+---------------+---------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | o     | NULL       | const | PRIMARY       | PRIMARY | 4       | const |    1 |   100.00 | NULL  |
|  1 | SIMPLE      | c     | NULL       | const | PRIMARY       | PRIMARY | 4       | const |    1 |   100.00 | NULL  |
|  1 | SIMPLE      | p     | NULL       | const | PRIMARY       | PRIMARY | 4       | const |    1 |   100.00 | NULL  |
+----+-------------+-------+------------+-------+---------------+---------+---------+-------+------+----------+-------+

    세 행 모두 select_type이 SIMPLE이고 key가 PRIMARY다. 뷰 이름도, 파생 테이블도 계획에 나타나지 않는다. type이 const인 것은 기본 키 등호 조건으로 한 행만 나온다는 것을 옵티마이저가 실행 전에 알아냈다는 뜻이다.

    TEMPTABLE: 결과를 먼저 만든다

    모든 뷰를 합칠 수 있는 것은 아니다. 매뉴얼은 파생 테이블, 공통 테이블 식(CTE), 뷰에 공통으로 다음 구성 요소가 있으면 합칠 수 없다고 적는다.

    • 집계 함수나 윈도 함수(SUM(), MIN(), MAX(), COUNT() 등)
    • DISTINCT, GROUP BY, HAVING, LIMIT
    • UNION 또는 UNION ALL
    • SELECT 목록의 서브쿼리, 사용자 변수에 대한 대입
    • 리터럴 값만 참조하는 경우(기반 테이블이 없다)

    이유는 합쳐 넣는다는 조작의 성질에 있다. 바깥 WHERE를 뷰 안의 WHERE와 AND로 합치는 것은 뷰가 행을 하나씩 걸러 내는 일만 할 때 의미가 같다. 뷰가 행을 묶어 집계하거나(GROUP BY), 중복을 없애거나(DISTINCT, UNION), 개수를 자르면(LIMIT) 바깥 조건을 집계 전으로 옮기는 순간 결과가 달라진다. "금액 합계가 50000 이상인 고객"이라는 조건을 집계 전의 행 단위 조건으로 옮길 수는 없다. 이런 뷰는 결과를 먼저 만들어야 한다. 고객별 매출 뷰를 만들어 보자.

    CREATE VIEW customer_sales AS
SELECT customer_id,
       customer_name,
       COUNT(*)    AS order_count,
       SUM(amount) AS total_amount
FROM order_details
WHERE status <> 'CANCELLED'
GROUP BY customer_id, customer_name;

SELECT * FROM customer_sales WHERE total_amount >= 50000;
    customer_id  customer_name  order_count  total_amount
-----------  -------------  -----------  ------------
          1  김하늘                   2         90000
          2  이바다                   1        300000
          3  박구름                   2         50000

    customer_sales는 뷰 위에 만든 뷰다. 안쪽의 order_details는 합칠 수 있으므로 customer_sales의 정의 안으로 합쳐지고, customer_sales 자체는 GROUP BY 때문에 합칠 수 없다. 그래서 엔진은 취소가 아닌 주문 여섯 건을 고객별로 묶은 네 행(김하늘 2건 90000, 이바다 1건 300000, 박구름 2건 50000, 정노을 1건 30000)을 임시 테이블로 만들고, 그 임시 테이블에서 total_amount >= 50000을 만족하는 세 행을 고른다. 이것이 처리의 기본 모양이고, 뒤에서 볼 파생 조건 푸시다운이 적용되면 이 조건이 임시 테이블을 채우기 전 단계로 옮겨져 세 행만 임시 테이블에 들어간다. EXPLAIN에서는 table 열이 처럼 표시되는 행이 나타나고, 그 아래에 select_type이 DERIVED인 행들로 임시 테이블을 만드는 과정이 나온다. 매뉴얼은 을 id가 N인 행의 파생 테이블 결과를 가리키는 표시로 설명한다.

    EXPLAIN SELECT * FROM customer_sales WHERE total_amount >= 50000;
    +----+-------------+------------+------------+--------+---------------+---------+---------+----------------------------+------+----------+--------------------------------------------+
| id | select_type | table      | partitions | type   | possible_keys | key     | key_len | ref                        | rows | filtered | Extra                                      |
+----+-------------+------------+------------+--------+---------------+---------+---------+----------------------------+------+----------+--------------------------------------------+
|  1 | PRIMARY     |  | NULL       | ALL    | NULL          | NULL    | NULL    | NULL                       |    5 |   100.00 | NULL                                       |
|  2 | DERIVED     | c          | NULL       | ALL    | PRIMARY       | NULL    | NULL    | NULL                       |    5 |   100.00 | Using temporary                            |

|  2 | DERIVED     | p          | NULL       | eq_ref | PRIMARY       | PRIMARY | 4       | m_db_basic_04.o.product_id |    1 |   100.00 | NULL                                       |

    id 2의 DERIVED 행 세 개가 order_details의 세 테이블이다. 안쪽 뷰 order_details가 customer_sales 안으로 합쳐졌기 때문에 뷰 이름 대신 o, c, p가 직접 나온다. 그 결과가 임시 테이블이 되고, id 1의 PRIMARY 행이 그 임시 테이블 를 읽는다.

MERGE는 뷰를 바깥 쿼리 속으로 녹여 기반 테이블을 직접 읽고, TEMPTABLE은 뷰 결과를 임시 테이블로 만든 뒤 읽는다.

    TEMPTABLE의 비용은 UNION에서 본 임시 테이블 비용과 같은 종류다. 임시 테이블을 만드는 동안에는 기반 테이블의 인덱스를 쓸 수 있지만, 바깥 쿼리는 임시 테이블을 읽으므로 기반 테이블의 인덱스를 쓰지 못한다. 매뉴얼은 TEMPTABLE로 처리되는 뷰가 기반 테이블의 인덱스를 활용할 수 없다고 적는다. 그 대신 옵티마이저는 몇 가지 보완을 한다. 매뉴얼에 따르면 옵티마이저는 파생 테이블의 구체화(materialization)를 내용이 실제로 필요해질 때까지 미루므로, 조인 상대가 행을 하나도 내지 않으면 구체화를 아예 건너뛸 수 있다. 또 구체화한 임시 테이블에 인덱스를 붙여 ref 방식 접근을 가능하게 하는 것이 더 싸다고 판단하면 실행 중에 인덱스를 추가하기도 한다.

    MySQL 8.0.22부터는 파생 조건 푸시다운(derived condition pushdown)도 있다. 바깥 WHERE 조건을 구체화되는 파생 테이블 안으로 밀어 넣는 최적화이고, optimizer_switch의 derived_condition_pushdown 플래그가 기본으로 켜져 있다. 매뉴얼의 규칙에 따르면 파생 테이블에 GROUP BY가 있을 때 GROUP BY 열에 대한 바깥 조건은 안쪽 WHERE로, GROUP BY 열이 아닌 열(예: 집계 결과)에 대한 조건은 안쪽 HAVING으로 옮겨질 수 있다. 위의 total_amount >= 50000은 집계 결과에 대한 조건이므로 HAVING 쪽으로 옮겨질 수 있는 경우이고, WHERE customer_id = 1이었다면 집계 전의 WHERE로 옮겨져 다른 고객의 주문을 집계하지 않아도 된다. 다만 파생 테이블에 LIMIT이 있거나, 조건에 서브쿼리가 있는 경우 등 매뉴얼에 열거된 조건에서는 적용되지 않는다. 파생 테이블에 UNION이 있으면 쓸 수 없다는 제약은 8.0.29에서 풀렸다. 실제로 적용되었는지는 EXPLAIN으로 확인해야 한다. 표 형식의 EXPLAIN에는 잘 드러나지 않으므로 EXPLAIN FORMAT=TREE로 본다.

    -> Table scan on customer_sales  (cost=2.5..2.5 rows=0)
    -> Materialize  (cost=0..0 rows=0)
        -> Filter: (sum((p.price * o.quantity)) >= 50000)
            -> Table scan on 
                -> Aggregate using temporary table
                    -> Nested loop inner join  (cost=1.92 rows=0.714)
                        -> Inner hash join (o.customer_id = c.customer_id)  (cost=1.6 rows=0.714)
                            -> Filter: (o.`status` <> 'CANCELLED')  (cost=0.0901 rows=1)
                                -> Table scan on o  (cost=0.0901 rows=7)
                            -> Hash
                                -> Table scan on c  (cost=0.75 rows=5)
                        -> Single-row index lookup on p using PRIMARY (product_id=o.product_id)  (cost=0.07 rows=1)

    트리는 안쪽부터 읽는다. 세 테이블을 조인하고(Nested loop, Inner hash join), 고객별로 집계한 뒤(Aggregate using temporary table), Materialize 단계 안에서 Filter: (sum((p.price * o.quantity)) >= 50000)가 집계 결과를 거른다. 바깥의 total_amount >= 50000이 안쪽 HAVING 자리로 옮겨져, 임시 테이블에는 조건을 통과한 고객만 들어간다는 뜻이다. 같은 뷰에 WHERE customer_id = 1을 걸고 표 형식으로 EXPLAIN하면 DERIVED 단계의 c가 type const로 나와, 조건이 집계 전의 WHERE로 내려갔음을 보여 준다(같은 두 버전에서 확인).

    TEMPTABLE이 늘 손해인 것은 아니다. 매뉴얼은 TEMPTABLE을 명시하는 이유로 잠금 해제 시점을 든다. 임시 테이블을 만든 뒤 나머지 처리를 마치기 전에 기반 테이블의 잠금을 풀 수 있어서, MERGE보다 잠금을 빨리 놓아 다른 클라이언트를 덜 기다리게 할 수 있다는 것이다. 잠금이 무엇이고 언제 걸리는지는 08회에서 다룬다.

    일상에서 가져온 비유레시피를 녹여 넣을 것인가, 한 솥 끓여 둘 것인가

    뷰는 레시피 카드다. MERGE는 오늘 만들 요리의 순서표에 레시피의 단계를 그대로 옮겨 적어, 필요한 재료만 꺼내 한 번에 조리하는 방식이다. TEMPTABLE은 레시피대로 국을 한 솥 끓여 둔 뒤 필요한 만큼 떠 가는 방식이다. 오늘 필요한 것이 한 그릇이어도 한 솥을 끓여야 한다. 비유가 깨지는 지점은 보관이다. 부엌에서는 끓여 둔 국을 냉장고에 넣어 내일 다시 먹지만, TEMPTABLE의 임시 테이블은 그 문장이 끝나면 버려지고 다음 조회 때 처음부터 다시 만든다. 결과를 저장해 두는 뷰는 MySQL의 CREATE VIEW 문법에 없다.

    뷰를 통해 데이터 바꾸기: 갱신 가능한 뷰와 WITH CHECK OPTION

    뷰는 조회만 하는 대상이 아니다. 조건을 만족하면 뷰를 대상으로 UPDATE, DELETE, INSERT를 실행할 수 있고, 변경은 기반 테이블에 적용된다. 매뉴얼이 정한 기본 조건은 뷰의 행과 기반 테이블의 행 사이에 일대일 관계가 있어야 한다는 것이다. 뷰의 한 행을 고치라는 요청을 받았을 때 기반 테이블의 어느 행을 고쳐야 하는지 정확히 하나로 정해져야 한다는 뜻이다. 그래서 다음을 포함하는 뷰는 갱신할 수 없다.

    • 집계 함수나 윈도 함수, DISTINCT, GROUP BY, HAVING, UNION 또는 UNION ALL
    • SELECT 목록의 서브쿼리, FROM 절의 테이블을 참조하는 WHERE 절의 서브쿼리
    • 일부 조인, 갱신할 수 없는 뷰에 대한 참조, 리터럴 값만 참조하는 경우
    • ALGORITHM = TEMPTABLE (임시 테이블을 쓰면 항상 갱신할 수 없다)

    GROUP BY가 있는 customer_sales의 한 행은 여러 주문을 합친 것이다. 김하늘의 total_amount를 100000으로 바꾸라는 요청은 두 주문 중 무엇을 얼마나 바꾸라는 것인지 정할 수 없다. 일대일 관계가 깨진 것이다. INFORMATION_SCHEMA.VIEWS의 IS_UPDATABLE 열은 MySQL이 CREATE VIEW 시점에 판정해 둔 이 갱신 가능성을 보여 주며, customer_sales는 NO다. MySQL 8.4.13과 8.0.46에서 실제로 UPDATE customer_sales SET total_amount = 100000 WHERE customer_id = 1을 실행하면 ERROR 1288 (HY000): The target table customer_sales of the UPDATE is not updatable로 거부되고, order_details의 IS_UPDATABLE은 YES로 나온다.

    INSERT는 조건이 더 까다롭다. 매뉴얼에 따르면 갱신 가능한 뷰가 INSERT까지 가능하려면 뷰의 열 이름이 중복되지 않아야 하고, 기본값이 없는 기반 테이블의 열을 모두 포함해야 하며, 뷰의 열이 식이 아닌 단순한 열 참조여야 한다. 계산된 열이 있는 뷰는 그 열을 건드리지 않는 UPDATE는 가능하지만 INSERT는 할 수 없다. order_details의 amount가 그런 열이다. 조인 뷰에 대해서는 규칙이 문장마다 다르다. 조인 뷰가 MERGE로 처리되고 내부 조인이라면 UPDATE는 SET 절이 한 테이블의 열만 바꿀 때 가능하고, INSERT는 한 테이블에만 넣을 때 가능하며, DELETE는 조인 뷰에 대해 허용되지 않는다.

    UPDATE order_details SET quantity = 2 WHERE order_id = 1;                         -- 성공 (orders만 바뀐다)
UPDATE order_details SET quantity = 1, customer_name = 'x' WHERE order_id = 1;   -- 두 테이블의 열
UPDATE order_details SET amount = 1 WHERE order_id = 1;                           -- 계산 열
DELETE FROM order_details WHERE order_id = 1;                                     -- 조인 뷰에서 삭제
    ERROR 1393 (HY000): Can not modify more than one base table through a join view 'm_db_basic_04.order_details'
ERROR 1348 (HY000): Column 'amount' is not updatable
ERROR 1395 (HY000): Can not delete from join view 'm_db_basic_04.order_details'

    오류 문구의 m_db_basic_04는 실습에 쓴 데이터베이스 이름이다. 첫 문장으로 바꾼 주문 1의 수량은 실습 뒤 다시 1로 되돌려 둔다.

    뷰에서 사라지는 행

    등급이 VIP인 고객만 보여 주는 단일 테이블 뷰를 만들어 보자. 이 절에서 바꾸는 데이터는 이후 예제에서 쓰지 않는다.

    CREATE VIEW vip_customers AS
SELECT customer_id, name, grade, city
FROM customers
WHERE grade = 'VIP';

UPDATE vip_customers SET city = '인천' WHERE customer_id = 1;   -- customers의 1번 행이 바뀐다
INSERT INTO vip_customers VALUES (6, '한결', 'BASIC', '인천');   -- 성공한다
UPDATE vip_customers SET grade = 'GOLD' WHERE customer_id = 1;  -- 성공한다

    첫 UPDATE는 기대한 대로 동작한다. 뷰의 행 하나가 customers의 행 하나에 대응하므로 김하늘의 도시가 바뀐다. 문제는 다음 두 문장이다. INSERT는 성공해서 customers에 한결이 들어가지만, 등급이 BASIC이므로 vip_customers로 조회하면 보이지 않는다. 뷰에 넣었는데 뷰에서 볼 수 없는 행이 생겼다. 마지막 UPDATE도 성공하고, 김하늘은 등급이 GOLD가 되면서 뷰에서 사라진다. 뷰를 통해 고쳤는데 고친 결과가 뷰 밖으로 나가 버린 것이다. 뷰가 "VIP 고객만 다루는 창구"라는 의도로 만들어졌다면 두 문장 모두 의도를 벗어난다.

    WITH CHECK OPTION이 이 문제를 막는다. 매뉴얼에 따르면 이 절은 뷰 정의의 WHERE가 참이 아닌 행의 INSERT를 막고, WHERE가 참인 행을 거짓이 되도록 바꾸는 UPDATE, 곧 보이는 행을 보이지 않는 행으로 바꾸는 UPDATE를 막는다.

    CREATE OR REPLACE VIEW vip_customers AS
SELECT customer_id, name, grade, city
FROM customers
WHERE grade = 'VIP'
WITH CHECK OPTION;

INSERT INTO vip_customers VALUES (7, '서유리', 'BASIC', '인천');
    ERROR 1369 (HY000): CHECK OPTION failed 'm_db_basic_04.vip_customers'

    뷰가 다른 뷰 위에 정의되어 있을 때는 검사 범위를 LOCAL과 CASCADED로 정한다. 아무것도 쓰지 않으면 CASCADED다. 매뉴얼의 규칙을 정리하면, LOCAL은 자기 WHERE를 검사한 뒤 아래 뷰로 내려가 같은 규칙을 적용한다. 아래 뷰에 검사 옵션이 없으면 그 뷰의 WHERE는 검사하지 않는다. CASCADED는 자기 WHERE를 검사한 뒤 아래 뷰들에도 CASCADED 검사 옵션이 있는 것처럼 취급해 그 WHERE까지 모두 검사한다. 차이는 아래 뷰에 검사 옵션이 없을 때 드러난다.

    CREATE VIEW seoul_customers AS
SELECT * FROM customers WHERE city = '서울';                 -- 검사 옵션 없음

CREATE VIEW seoul_vip_local AS
SELECT * FROM seoul_customers WHERE grade = 'VIP'
WITH LOCAL CHECK OPTION;

CREATE VIEW seoul_vip_cascaded AS
SELECT * FROM seoul_customers WHERE grade = 'VIP'
WITH CASCADED CHECK OPTION;

INSERT INTO seoul_vip_local    VALUES (8, '강바람', 'VIP', '부산');  -- 성공
INSERT INTO seoul_vip_cascaded VALUES (9, '윤솔',   'VIP', '부산');  -- 실패 (ERROR 1369)

    첫 INSERT는 seoul_vip_local의 조건 grade = 'VIP'를 만족한다. 그다음 아래 뷰 seoul_customers로 내려가지만 그 뷰에는 검사 옵션이 없으므로 city = '서울'은 검사하지 않는다. 그래서 '서울 VIP' 뷰에 부산 고객이 들어간다. 둘째 INSERT는 CASCADED가 아래 뷰의 city = '서울'까지 검사하므로 실패한다. 뷰를 겹쳐 쓰는 구조에서 "이 뷰를 통해서는 이 범위의 데이터만 바뀐다"는 보장을 원하면 기본값인 CASCADED를 쓰는 편이 안전하다. 매뉴얼의 예처럼 아래 뷰에도 검사 옵션이 있다면 LOCAL이어도 아래 뷰의 규칙이 적용되어 실패한다.

    뷰의 장점과 단점

    지금까지 본 동작에서 뷰의 장단점이 자연스럽게 나온다. 장점은 모두 "쿼리에 이름을 붙여 한 곳에 둔다"는 데서, 단점은 대부분 "결과가 아니라 방법을 저장한다"는 데서 나온다.

    장점단점
    복잡한 조인과 계산 규칙을 한 곳에 두고 재사용한다이름 뒤에 숨은 비용이 보이지 않는다 (뷰 위의 뷰, TEMPTABLE)
    필요한 열과 행만 노출해 접근을 제한한다뷰에 인덱스를 만들 수 없고 인덱스 힌트도 쓸 수 없다
    테이블 구조가 바뀌어도 뷰 정의를 고쳐 바깥 모양을 유지한다정의가 생성 시점에 굳고, 기반 테이블 변경이 경고 없이 뷰를 깨뜨린다
    MERGE 뷰는 직접 쓴 쿼리와 같은 실행 계획을 얻을 수 있다갱신에 제약이 많고, 결과를 저장하지 않아 무거운 집계를 매번 다시 한다

    장점: 재사용, 보안, 독립성

    첫째 장점은 재사용과 일관성이다. 금액이 price * quantity라는 규칙이 order_details 한 곳에만 있으면, 할인이 도입되어 규칙이 바뀌는 날 뷰 하나만 고치면 된다. 쿼리를 쓰는 사람마다 금액을 조금씩 다르게 계산해 보고서끼리 숫자가 어긋나는 일도 줄어든다.

    둘째 장점은 보안이다. 고객 테이블에 전화번호나 주소 같은 민감한 열이 있다면, 그 열을 뺀 뷰를 만들고 특정 사용자에게는 테이블이 아니라 뷰에 대한 SELECT 권한만 줄 수 있다. 뷰의 WHERE로 볼 수 있는 행도 제한할 수 있다. 이것이 가능한 이유는 SQL SECURITY 특성에 있다. 매뉴얼에 따르면 기본값인 SQL SECURITY DEFINER에서는 뷰를 참조하는 문장을 실행할 때 뷰를 정의한 계정(DEFINER)의 권한으로 접근 권한을 검사한다. SQL SECURITY INVOKER로 바꾸면 호출한 사용자의 권한으로 검사한다. DEFINER를 생략하면 CREATE VIEW를 실행한 사용자가 정의자가 된다.

    셋째 장점은 논리적 독립성이다. 테이블을 둘로 나누는 식으로 구조를 바꿔야 할 때, 원래 테이블 이름의 뷰를 만들어 옛 모양을 재현하면 그 이름으로 조회하던 코드는 당분간 고치지 않아도 된다. 뷰가 저장된 구조와 보이는 구조 사이의 완충 지대가 되는 것이다. 다만 테이블과 뷰는 같은 이름 공간을 쓰므로, 원래 테이블의 이름을 먼저 바꾸거나 지운 뒤에야 같은 이름으로 뷰를 만들 수 있다.

    단점: 보이지 않는 비용과 깨지기 쉬운 연결

    가장 큰 단점은 비용이 이름 뒤에 숨는다는 것이다. SELECT * FROM customer_sales WHERE customer_id = 1은 고객 한 명을 조회하는 가벼운 쿼리처럼 보이지만, 그 뒤에는 세 테이블의 조인과 GROUP BY가 있다. 파생 조건 푸시다운이 적용되지 않는 조건이라면 모든 고객의 매출을 집계한 뒤 한 명을 고른다. 뷰 위에 뷰를 쌓으면 이 비용은 더 깊이 숨는다. 뷰를 쓰는 쿼리가 느릴 때 가장 먼저 할 일은 EXPLAIN에서 행, 곧 구체화가 일어났는지를 확인하는 것이다.

    둘째, 뷰는 자기 인덱스를 가질 수 없다. 매뉴얼은 뷰에 인덱스를 만들 수 없고, 뷰를 조회할 때 인덱스 힌트를 쓸 수 없다고 명시한다. 뷰의 성능은 기반 테이블의 인덱스와 옵티마이저가 뷰를 합칠 수 있는지에 달려 있다.

    셋째, 정의가 굳는다. 앞에서 본 것처럼 SELECT *는 생성 시점의 열 목록으로 고정되고, 기반 테이블의 열을 지우는 변경은 경고 없이 뷰를 깨뜨린다. 스키마를 바꾸는 배포 과정에 뷰 점검(CHECK TABLE 등)을 넣지 않으면 장애가 늦게 드러난다.

    넷째, 결과를 저장하지 않는다. 뷰는 매번 다시 계산된다. 집계가 무겁고 자주 조회된다면 뷰는 그 비용을 줄여 주지 않는다. MySQL의 CREATE VIEW 문법에는 결과를 저장해 두는 선택지가 없으므로, 그런 요구는 집계 결과를 담는 별도 테이블을 두고 주기적으로 갱신하는 식으로 풀어야 한다. 그 테이블을 언제 어떻게 갱신하느냐는 데이터의 신선도와 비용 사이의 설계 문제가 된다.

    적용 연습: 세 도구를 한 쿼리에

    요구 사항은 이렇다. 올해 주문과 보관 주문을 모두 합쳐 월별로 완료 금액, 진행 중(PENDING, SHIPPED) 금액, 취소 건수를 한 줄씩 보여 주는 보고서를 만들고, 다른 사람들도 쓸 수 있게 이름을 붙여 둔다. 세 도구의 역할이 나뉜다. 두 테이블을 잇는 일은 UNION ALL, 상태별 값을 열로 펼치는 일은 CASE를 쓴 조건부 집계, 이름을 붙이는 일은 뷰다.

    CREATE VIEW monthly_report AS
SELECT ym,
       SUM(CASE WHEN status = 'COMPLETED'             THEN amount ELSE 0 END) AS completed_amount,
       SUM(CASE WHEN status IN ('PENDING', 'SHIPPED') THEN amount ELSE 0 END) AS in_progress_amount,
       COUNT(CASE WHEN status = 'CANCELLED' THEN 1 END)                       AS cancelled_count
FROM (
    SELECT DATE_FORMAT(o.order_date, '%Y-%m') AS ym, o.status, p.price * o.quantity AS amount
    FROM orders o
    JOIN products p ON p.product_id = o.product_id
    UNION ALL
    SELECT DATE_FORMAT(a.order_date, '%Y-%m'), a.status, p.price * a.quantity
    FROM orders_archive a
    JOIN products p ON p.product_id = a.product_id
) AS all_orders
GROUP BY ym;

SELECT * FROM monthly_report ORDER BY ym;
    ym       completed_amount  in_progress_amount  cancelled_count
-------  ----------------  ------------------  ---------------
2024-11            300000                   0                0
2024-12             15000                   0                1
2025-01             90000                   0                0
2025-02                 0              330000                0
2025-03             50000                   0                1

    한 줄씩 확인해 보자. 2024-11은 보관 주문 101(모니터 300000, 완료) 하나다. 2024-12는 102(노트 3000 × 5 = 15000, 완료)와 103(취소)이다. 103의 금액 50000은 어느 금액 열에도 더해지지 않고 취소 건수 1로만 잡힌다. 2025-01은 주문 1과 2로 완료 90000이다. 2025-02는 주문 3(배송 중 300000)과 4(대기 30000)가 모두 진행 중이라 330000이고 완료는 ELSE 0만 더해져 0이다. 2025-03은 완료인 6(30000)과 7(20000)을 더한 50000에 취소 5번이 한 건이다.

    설계 판단을 하나씩 되짚어 보자. 파생 테이블 안에서 UNION이 아니라 UNION ALL을 쓴 이유는 앞의 고객별 완료 주문 수 예와 같다. 블록이 고르는 열은 (ym, status, amount)뿐이고 order_id가 없다. 같은 달에 같은 상태, 같은 금액의 주문이 두 건 있으면(예를 들어 3월에 마우스를 한 개씩 산 완료 주문이 두 건이면) UNION은 둘을 하나로 합쳐 금액을 절반으로 만든다. 현재 데이터에는 그런 행이 없어서 UNION으로 써도 결과가 같게 나오지만, 그것은 우연이다. 금액 열에는 ELSE 0을, 건수 열에는 ELSE 없는 COUNT를 썼다. 그래서 진행 중 주문이 없는 달도 NULL이 아니라 0이 나온다.

    이 뷰는 엔진 안에서 어떻게 처리될까. 정의에 GROUP BY가 있고, FROM 절의 파생 테이블에 UNION ALL이 있으므로 어느 쪽도 바깥 쿼리에 합쳐질 수 없다. 뷰를 조회하면 UNION ALL 파생 테이블과 월별 집계 결과가 구체화된다. 따라서 이 뷰는 갱신할 수 없고(INFORMATION_SCHEMA.VIEWS의 IS_UPDATABLE도 NO다), SELECT * FROM monthly_report WHERE ym = '2025-02'처럼 한 달만 조회해도 파생 조건 푸시다운이 그 조건을 안쪽으로 옮겨 주지 않는 한 전체 기간을 집계한 뒤 한 행을 고른다. MySQL 8.4.13과 8.0.46에서 이 조회를 EXPLAIN FORMAT=TREE로 보면 조건이 실제로 안쪽까지 내려간다.

    정리: 저장된 모양과 보고 싶은 모양 사이

    세 도구는 모두 데이터를 복사하지 않고 질의 시점에 모양을 바꾼다는 공통점이 있다. 그 대가로 엔진은 매번 일을 한다. UNION은 중복을 없애려고 임시 테이블을 채우고, CASE로 만든 그룹은 인덱스 순서를 따를 수 없어 행을 모아야 하며, 합칠 수 없는 뷰는 결과를 구체화한다. 반대로 UNION ALL은 조건이 맞으면 행을 곧바로 흘려보내고, 조건부 집계는 테이블을 한 번만 읽고 여러 합계를 만들며, MERGE 뷰는 뷰 자체를 없애 버려 기반 테이블의 인덱스를 그대로 쓰게 한다. 같은 결과를 내는 쿼리라도 엔진이 하는 일의 양이 다르다는 것, 그리고 그 차이는 EXPLAIN의 UNION RESULT 행, Using temporary, 같은 표시로 드러난다는 것이 이 회차의 요점이다.

    이 장의 핵심

    UNION은 행 전체를 기준으로 중복을 지우며 그 일을 위해 임시 테이블을 거친다. 중복이 생길 수 없거나 중복이 정당한 데이터라면 UNION ALL을 쓴다. CASE는 위에서부터 처음으로 참인 WHEN의 값을 돌려주고, 참이 아닌 UNKNOWN은 다음으로 넘기며, ELSE가 없으면 NULL을 돌려준다. 집계 함수가 NULL을 무시한다는 성질과 결합하면 한 번의 스캔으로 행을 열로 펼칠 수 있다. 뷰는 결과가 아니라 쿼리를 저장하며, MySQL은 그것을 바깥 쿼리에 합치거나(MERGE) 결과를 임시 테이블로 만든다(TEMPTABLE). 집계, DISTINCT, UNION, LIMIT이 있으면 합칠 수 없고, 합칠 수 없는 뷰는 갱신도 할 수 없다.

    이 지식은 뒤에서 여러 번 다시 쓰인다. 05회와 06회에서 인덱스를 배우면, MERGE 뷰가 왜 기반 테이블의 인덱스를 쓸 수 있고 계산된 값으로 정렬하거나 묶을 때 왜 인덱스의 순서를 쓸 수 없는지가 B+Tree의 구조로 설명된다. 08회의 트랜잭션과 잠금은 TEMPTABLE 뷰가 잠금을 일찍 놓을 수 있다는 이야기의 배경이 된다. JPA로 넘어가면 JPQL에도 CASE 식이 있다. 다만 Jakarta Persistence 3.1·3.2 명세의 JPQL 문법은 SUM 같은 집계 함수의 인수로 경로 식만 정의하므로, 이 회차에서 본 조건부 집계를 엔티티 쿼리에서 쓰는 것은 집계 함수 안에 식을 허용하는 Hibernate 6의 HQL 같은 구현에 기대는 일이다. 어떤 도구로 쿼리를 만들든, 결국 데이터베이스에 도착하는 것은 SQL이고 그 SQL을 엔진이 어떻게 실행하는지가 성능을 정한다.
    UNION과 UNION ALL
    여러 쿼리 블록의 결과를 세로로 잇는다. 블록마다 열 개수가 같아야 하고 결과 열 이름은 첫 블록에서 가져온다. UNION(DISTINCT)은 행 전체가 같은 중복을 지우며 NULL끼리도 같다고 보고, UNION ALL은 모든 행을 남긴다.
    UNION의 실행 비용
    MySQL은 UNION(DISTINCT)을 내부 임시 테이블로 처리하고 EXPLAIN에 UNION RESULT 행을 보인다. 전체 ORDER BY가 없는 UNION ALL 등 조건을 만족하면 임시 테이블 없이 행을 바로 보낸다.
    UNION 정렬 규칙
    마지막 ORDER BY는 결과 전체에 적용되며 테이블 이름이 붙은 열 참조를 쓸 수 없다. 블록별 ORDER BY와 LIMIT은 괄호 안에 쓰고, LIMIT 없는 블록 안 ORDER BY는 최적화 과정에서 제거된다.
    CASE 식
    단순 CASE는 등호 비교, 검색 CASE는 조건을 쓴다. 처음으로 참인 WHEN의 값을 돌려주고 ELSE가 없으면 NULL이다. CASE x WHEN NULL은 참이 될 수 없다.
    CASE의 결과 타입
    THEN과 ELSE 값의 타입을 모아 하나의 타입을 정한다. 문자열과 숫자가 섞이면 VARCHAR가 되어 정렬과 비교가 문자열 기준으로 바뀐다.
    조건부 집계
    SUM(CASE ... THEN 1 ELSE 0 END)나 COUNT(CASE ... THEN 1 END)처럼 집계 함수 안에 CASE를 넣어, 테이블을 한 번 읽으면서 조건별 합계를 열로 펼친다. COUNT 안의 CASE에 ELSE 0을 쓰면 모든 행이 세어진다.
    뷰
    이름이 붙은 저장된 SELECT다. 결과를 저장하지 않으며 정의는 생성 시점에 굳는다. CREATE VIEW, CREATE OR REPLACE VIEW, ALTER VIEW, DROP VIEW로 관리한다.
    MERGE와 TEMPTABLE
    MERGE는 뷰 정의를 바깥 쿼리에 합쳐 기반 테이블의 인덱스를 쓰게 하고, TEMPTABLE은 뷰 결과를 임시 테이블로 만든다. 집계, DISTINCT, GROUP BY, HAVING, LIMIT, UNION이 있으면 합칠 수 없다.
    갱신 가능한 뷰와 WITH CHECK OPTION
    뷰의 행과 기반 테이블의 행이 일대일일 때만 뷰를 통해 바꿀 수 있다. WITH CHECK OPTION은 뷰의 WHERE를 벗어나는 INSERT와 UPDATE를 막고, 기본값 CASCADED는 아래 뷰의 조건까지 검사한다.

    UNION과 UNION ALL의 선택은 성능 문제이기 전에 정확성 문제다. 집계의 재료를 UNION으로 모으는 실수는 오류도 경고도 없이 숫자만 작게 만든다. 테스트 데이터가 작고 깨끗하면 결과가 우연히 맞아 넘어가고, 실제 데이터에서 같은 금액의 주문이 같은 달에 두 번 들어오는 순간 보고서가 틀어진다. 리뷰에서 UNION을 보면 "이 블록들 사이에 중복이 생길 수 있는가, 생긴다면 지워야 하는가"를 묻는 습관이 필요하다. 둘 다 아니라면 UNION ALL이고, 그 선택은 임시 테이블 비용도 함께 없앤다.

    뷰는 팀 사이의 경계에서 특히 유용하다. 분석팀이나 다른 서비스에 테이블을 직접 열어 주는 대신 필요한 열과 행만 담은 뷰를 주면, 테이블 구조를 바꿀 때 뷰 정의만 맞춰 고치면 된다. 반대로 뷰가 경계라는 사실을 잊으면 장애가 된다. 컬럼을 지우는 마이그레이션은 경고 없이 통과하고, 그 뷰를 쓰는 화면이 다음에 열릴 때에야 오류가 난다. 스키마 변경 절차에 의존하는 뷰를 찾고 점검하는 단계를 넣는 것이 실무적인 대응이다.

    성능 문제로 뷰를 의심할 때의 판단 기준은 그 뷰가 합쳐지는가다. 단순한 조인과 필터만 있는 뷰는 MERGE로 사라지므로 뷰를 쓴다는 사실 자체가 성능에 영향을 주지 않는다. GROUP BY, DISTINCT, UNION, LIMIT이 들어간 뷰는 구체화되므로, 그 위에 조건을 걸어 조회할 때 조건이 안쪽으로 내려가는지(MySQL 8.0.22 이후의 파생 조건 푸시다운)를 EXPLAIN으로 확인해야 한다. 내려가지 않는다면 뷰를 매번 전체 집계하는 장치로 쓰고 있는 셈이고, 이때는 조건을 받는 쿼리를 따로 쓰거나 집계 결과를 저장하는 테이블을 두는 쪽으로 판단이 바뀐다.

    1번. (가) 첫 블록은 다섯 고객의 등급 VIP, GOLD, BASIC, BASIC, GOLD를 낸다. 둘째 블록은 도시가 NULL인 정노을의 GOLD 하나를 낸다. UNION ALL은 중복을 지우지 않으므로 여섯 행이다. (나) UNION은 행 전체를 기준으로 중복을 지우므로 VIP, GOLD, BASIC 세 행만 남는다. 행의 순서는 ORDER BY가 없으므로 보장되지 않는다. 두 경우 모두 결과 열 이름은 첫 블록의 열 이름인 grade다.

    2번. 수량은 주문 1부터 7까지 1, 2, 1, 10, 1, 20, 1이다. 모든 수량이 1 이상이므로 첫 WHEN이 항상 참이 되고 일곱 건 모두 '소량'이다. 10과 20도 첫 WHEN에서 결과가 정해져 두 번째 WHEN을 볼 기회가 없다. CASE는 위에서부터 처음으로 참인 WHEN의 값을 돌려주기 때문이다. 좁은 조건을 위로 올려 CASE WHEN quantity >= 10 THEN '대량' WHEN quantity >= 1 THEN '소량' END로 쓰거나, quantity >= 1 AND quantity < 10처럼 범위를 양쪽으로 닫는다. 고친 뒤에는 주문 4(수량 10)와 주문 6(수량 20)이 '대량'이다.

    4번. (가)는 성공한다. 도시를 바꿔도 grade = 'VIP'라는 뷰의 조건은 여전히 참이므로 행이 뷰에 남는다. (나)는 ERROR 1369로 실패한다. 보이는 행을 뷰 조건이 거짓이 되는 행으로 바꾸는 UPDATE이기 때문이다. 김하늘이 이미 GOLD라면 그 행은 처음부터 뷰에 보이지 않으므로 (가)의 WHERE에 걸리는 행이 없다. 오류 없이 0개 행이 바뀐다. 뷰를 통한 UPDATE는 뷰에 보이는 행만 대상으로 한다.

    5번. order_details는 내부 조인과 계산 열만 있으므로 MERGE로 합쳐지고, EXPLAIN에는 기반 테이블 o, c, p가 직접 나온다. customer_sales는 집계 함수와 GROUP BY가 있어 합칠 수 없으므로 구체화되고, table 열에 이 나타난다. UPDATE는 order_details에 대해서만 시도할 수 있다. 내부 조인 뷰이고 MERGE로 처리되므로, SET 절이 한 테이블의 열(예: orders의 quantity)만 바꾼다면 허용된다. 계산 열 amount는 바꿀 수 없다. customer_sales는 한 행이 여러 주문을 합친 것이라 기반 행과 일대일 관계가 없으므로 갱신할 수 없고, IS_UPDATABLE이 NO다.

ALGORITHM을 생략했으므로 항상 MERGE로 처리되어 기반 테이블의 인덱스를 쓴다. 뷰의 결과가 데이터베이스에 저장되어 있다가, 기반 테이블이 바뀔 때만 다시 계산된다. ALGORITHM 생략은 가능할 때 MERGE를 선호한다는 뜻일 뿐 항상 MERGE가 아니다. 뷰는 결과를 저장하지 않고 조회할 때마다 계산한다. WITH CHECK OPTION은 갱신 가능한 뷰의 변경 범위를 제한할 뿐, 갱신 불가능한 뷰를 갱신 가능하게 만들지 않는다.
    쿼리 블록(query block)
    UNION 같은 집합 연산에 참여하는 각각의 SELECT(MySQL 8.0.19부터는 TABLE, VALUES 문도 가능). 블록마다 열 개수가 같아야 하고 결과 열 이름은 첫 블록에서 온다.
    집합 연산(set operation)
    여러 쿼리 블록의 결과 행을 하나의 결과로 합치는 연산. MySQL은 UNION을, 8.0.31부터 INTERSECT와 EXCEPT도 지원하며 기본 동작은 중복 제거다.
    내부 임시 테이블(internal temporary table)
    서버가 문장을 처리하는 도중 스스로 만드는 임시 테이블. UNION의 중복 제거, 일부 GROUP BY, 구체화되는 뷰와 파생 테이블에 쓰이며, 메모리에서 시작해 너무 커지면 디스크 기반으로 바뀐다.
    CASE 식(CASE expression)
    조건에 따라 다른 값을 돌려주는 SQL 식. 처음으로 참인 WHEN의 값을, 없으면 ELSE의 값을, ELSE도 없으면 NULL을 돌려준다. 저장 프로그램의 CASE 문과는 다른 문법이다.
    조건부 집계(conditional aggregation)
    집계 함수 안에 CASE를 넣어 조건에 맞는 행만 집계하는 기법. 한 번의 스캔으로 여러 조건별 합계를 열로 펼칠 수 있다.
    뷰(view)
    이름이 붙은 저장된 SELECT 문. 테이블처럼 조회하지만 결과를 저장하지 않으며, 정의는 생성 시점의 열 목록으로 고정된다.
    구체화(materialization)
    뷰나 파생 테이블의 결과를 임시 테이블로 실제로 만들어 두는 처리. TEMPTABLE 알고리즘이 이 방식이며, 바깥 쿼리는 기반 테이블 대신 임시 테이블을 읽는다.
    갱신 가능한 뷰(updatable view)
    뷰의 행과 기반 테이블의 행이 일대일로 대응해 UPDATE, DELETE(경우에 따라 INSERT)를 뷰에 실행할 수 있는 뷰. INFORMATION_SCHEMA.VIEWS의 IS_UPDATABLE로 확인한다.
    WITH CHECK OPTION
    갱신 가능한 뷰를 통한 변경이 뷰의 WHERE 조건을 벗어나지 못하게 막는 절. LOCAL과 CASCADED(기본값)로 아래 뷰에 대한 검사 범위를 정한다.
