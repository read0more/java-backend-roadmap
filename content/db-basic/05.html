    이 회차의 질문: 전부 읽지 않고 찾을 수 있는가

    지금까지 이 권에서 쓴 쿼리는 모두 "무엇을 원하는가"만 적었다. 조인으로 어떤 행을 짝지을지, 서브쿼리로 어떤 값을 비교할지, UNION으로 어떤 결과를 합칠지를 선언했을 뿐 "어떻게 찾을지"는 데이터베이스에 맡겼다. 데이터가 수십 행일 때는 그 "어떻게"를 신경 쓸 이유가 없다. 데이터베이스가 처음부터 끝까지 다 읽어도 눈 깜짝할 사이에 끝나기 때문이다. 그런데 행이 수백만, 수억이 되면 사정이 달라진다. 같은 쿼리가 어제까지는 10밀리초에 끝나다가 데이터가 쌓이면서 몇 초, 몇십 초로 늘어난다.

    이 회차의 질문은 하나다. 원하는 행을 찾으려고 모든 행을 읽어야 하는가? 답은 "찾는 기준이 되는 값으로 미리 정렬해 둔 별도의 구조가 있다면 아니다"이다. 그 구조가 인덱스(index)다. 이 회차는 인덱스를 다섯 단계로 세운다. 먼저 인덱스가 없을 때 엔진이 실제로 무엇을 하는지 페이지 단위로 본다. 다음으로 정렬된 데이터에서 빨리 찾는 방법을 이진 탐색부터 따져 올라가 데이터베이스가 왜 B+Tree라는 넓고 낮은 트리를 쓰는지 이해한다. 셋째로 인덱스를 만들고 확인하고 지우는 문법과 그때 엔진 안에서 일어나는 일을 본다. 넷째로 동등 비교, 범위 검색, LIKE 검색, 정렬이 각각 인덱스를 어떻게 쓰는지, 언제 쓰지 못하는지 추적한다. 마지막으로 흔한 오해를 바로잡는다.

    설명은 MySQL 8.0의 InnoDB 저장 엔진을 기준으로 한다. 실행 계획(EXPLAIN)의 rows 같은 추정치와 실행 시간은 데이터 분포와 통계, 서버 설정에 따라 실행 환경마다 다르다. 이 회차의 SQL과 EXPLAIN 출력은 MySQL 8.0.46에서 실제로 실행한 것이고, 8.4.13에서도 같은 데이터로 돌려 type·key·Extra가 모두 같음을 확인했다. 출력에 보이는 rows, filtered, Cardinality, 실행 시간은 실행 환경과 통계에 따라 달라지는 값이니 그대로 재현되기를 기대하지 말자. 결과 행 수처럼 데이터에서 결정되는 값은 직접 계산해 적고 실행 결과와 맞춰 보았으며, 트리 탐색의 일의 양은 자바로 작은 B+Tree를 만들어 세어 본다. 이 권의 다른 회차와는 범위를 나눈다. 옵티마이저가 인덱스를 고르는 방식, 커버링 인덱스, 여러 열을 묶은 복합 인덱스, 인덱스 설계 지침과 단점은 06회에서 다룬다. 01회의 인덱스 중첩 루프 조인이 안쪽 테이블을 빨리 찾던 것이 바로 이 회차에서 보는 동등 검색이라는 점만 기억해 두면 된다.

    실습 데이터: 10만 행짜리 상품 테이블

    인덱스의 효과는 행이 적으면 드러나지 않는다. 그래서 이 회차에서는 10만 행짜리 테이블을 만들어 쓴다. 값은 무작위가 아니라 행 번호 n에서 계산되게 해서, 어떤 조건에 몇 행이 걸리는지를 누구나 똑같이 계산할 수 있게 했다. 테이블은 상품(item) 하나다. 기본 키 item_id, 이름 name, 분류 category, 가격 price, 재고 stock으로 이루어진다.

    CREATE TABLE item (
    item_id   BIGINT       NOT NULL,
    name      VARCHAR(50)  NOT NULL,
    category  VARCHAR(20)  NOT NULL,
    price     INT          NOT NULL,
    stock     INT          NOT NULL,
    PRIMARY KEY (item_id)
);

-- 재귀 CTE의 반복 깊이 기본 한도는 1000이므로 이 세션에서만 늘린다
SET SESSION cte_max_recursion_depth = 100000;

INSERT INTO item (item_id, name, category, price, stock)
WITH RECURSIVE seq (n) AS (
    SELECT 1
    UNION ALL
    SELECT n + 1 FROM seq WHERE n < 100000
)
SELECT n,
       CONCAT(ELT(n % 7 + 1, '무선 마우스', '무선 키보드', '유선 마우스',
                  '게이밍 헤드셋', '노트북 거치대', 'USB 허브', '모니터 암'),
              '-', LPAD(n, 6, '0')),
       ELT(n % 5 + 1, '도서', '가전', '식품', '의류', '완구'),
       (n % 1000) * 100 + 1000,
       n % 50
FROM seq;

ANALYZE TABLE item;

    몇 가지를 짚고 가자. WITH RECURSIVE는 03회의 서브쿼리와 짝을 이루는 공통 테이블 식(CTE)의 재귀형으로, 1에서 시작해 한 번에 1씩 늘려 가며 행을 만든다. MySQL 8.0 매뉴얼에 따르면 cte_max_recursion_depth의 기본값은 1000이라서, 1000단계를 넘게 재귀하면 서버가 실행을 중단한다. 8.0.46에서 한도를 그대로 둔 채 10만까지 세는 재귀 CTE를 실행하면 ERROR 3636 (HY000): Recursive query aborted after 1001 iterations. Try increasing @@cte_max_recursion_depth to a larger value. 오류가 난다. 그래서 세션 변수로 한도를 올렸다. 매뉴얼은 INSERT ... WITH ... SELECT 형태로 INSERT 안의 SELECT 앞에 WITH 절을 두는 것을 허용한다. ELT(k, s1, s2, ...)는 k번째 문자열을 돌려주는 함수이고, LPAD(n, 6, '0')은 숫자를 여섯 자리로 맞추려고 앞을 0으로 채운다. 마지막의 ANALYZE TABLE은 대량으로 넣은 뒤 옵티마이저가 쓰는 통계를 새로 모으게 한다.

    앞 몇 행을 손으로 계산해 보면 이렇다. MySQL 8.0.46에서 데이터를 넣고 SELECT * FROM item ORDER BY item_id LIMIT 8;로 조회한 결과도 이 표와 같았다. 이 표를 머리에 넣어 두면 뒤의 추적이 쉬워진다.

    이 정의에서 바로 계산되는 사실들이 있다. 이름은 끝의 여섯 자리 번호 때문에 모든 행이 서로 다르다. 분류는 n % 5로 정해지므로 다섯 분류가 정확히 2만 행씩이다. 가격은 n % 1000으로 정해지므로 1,000원부터 100,900원까지 100원 간격의 값 1,000가지가 각각 정확히 100행씩 있다. 예를 들어 가격 50,000원은 n % 1000 = 490인 행, 곧 item_id 490, 1490, 2490, …, 99490의 100행이다. 같은 가격의 행이 기본 키 순서로는 1,000씩 떨어져 흩어져 있다는 점이 뒤에서 중요해진다. 이름의 앞부분은 n % 7로 정해지므로 일곱 가지 상품명이 14,285행 또는 14,286행씩 있고, '무선'으로 시작하는 이름(무선 마우스와 무선 키보드)은 모두 28,571행이다. 8.0.46에서 GROUP BY로 직접 세어 보아도 분류마다 20,000행, 가격 1,000가지마다 100행이었고, 상품명은 무선 키보드·유선 마우스·게이밍 헤드셋·노트북 거치대·USB 허브가 14,286행, 모니터 암과 무선 마우스가 14,285행, '무선'으로 시작하는 이름은 28,571행이었다.

    인덱스가 없을 때 엔진이 하는 일

    이름으로 상품 하나를 찾는 쿼리를 생각해 보자.

    SELECT * FROM item WHERE name = '무선 키보드-000008';

    결과는 item_id 8인 한 행이다. 그런데 이 한 행을 찾으려고 엔진은 무엇을 읽을까? 이 테이블에는 name을 기준으로 정리된 구조가 아무것도 없다. 행들은 기본 키인 item_id 순서로 저장되어 있을 뿐이다. 그러니 엔진이 할 수 있는 일은 하나뿐이다. 첫 행부터 마지막 행까지 차례로 읽으며 각 행의 name이 찾는 값과 같은지 비교한다. 이것이 전체 테이블 스캔(full table scan)이다. EXPLAIN을 붙여 보면 type 열에 ALL, key 열에 NULL이 나온다. 매뉴얼은 ALL을 "전체 테이블 스캔"으로, key가 NULL인 것을 "더 효율적으로 실행할 인덱스를 찾지 못했다"는 뜻으로 설명한다.

    +----+-------------+-------+------------+------+---------------+------+---------+------+-------+----------+-------------+
| id | select_type | table | partitions | type | possible_keys | key  | key_len | ref  | rows  | filtered | Extra       |
+----+-------------+-------+------------+------+---------------+------+---------+------+-------+----------+-------------+
|  1 | SIMPLE      | item  | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 97340 |    10.00 | Using where |
+----+-------------+-------+------------+------+---------------+------+---------+------+-------+----------+-------------+

    rows는 10만이 아니라 97,340이다. 옵티마이저가 통계로 어림한 "검사할 행 수"라서 정확한 행 수와 다르고, 실행할 때마다 조금씩 달라질 수 있다. Extra의 Using where는 읽은 행마다 WHERE 조건을 평가해 걸러 냈다는 표시다.

    눈여겨볼 점이 있다. 찾는 행은 여덟 번째 행이라 아주 앞쪽에 있다. 그런데도 엔진은 거기서 멈추지 못한다. 이름이 같은 행이 뒤에 또 있을지 모르기 때문이다. 우리는 이름이 모두 다르다는 것을 데이터를 만든 방식으로 알지만, 엔진은 그런 보장(UNIQUE 제약)을 받은 적이 없다. 그래서 나머지 99,992행도 모두 읽어 확인한다. 만약 쿼리에 LIMIT 1을 붙였다면 첫 번째 일치를 찾는 순간 멈출 수 있지만, 그것은 찾는 행이 앞쪽에 있을 때의 운일 뿐이다. 찾는 행이 마지막 행이었다면 LIMIT이 있어도 10만 행을 다 읽는다.

    InnoDB에서 "테이블"은 기본 키로 정렬된 트리다

    "처음부터 끝까지 읽는다"를 조금 더 정확하게 말해 보자. InnoDB 테이블의 행은 아무 데나 쌓이지 않는다. MySQL 매뉴얼은 모든 InnoDB 테이블에 행 데이터를 저장하는 클러스터형 인덱스(clustered index)라는 특별한 인덱스가 있고, 기본 키를 정의하면 그것이 클러스터형 인덱스가 된다고 설명한다. 다시 말해 InnoDB에서 테이블 자체가 기본 키를 기준으로 정렬된 B-Tree다. 행 데이터는 그 트리의 맨 아래 단계인 리프 페이지(leaf page)에 기본 키 순서대로 들어 있다. 기본 키가 없으면 InnoDB는 모든 열이 NOT NULL인 첫 번째 UNIQUE 인덱스를 클러스터형 인덱스로 쓰고, 그것도 없으면 GEN_CLUST_INDEX라는 숨은 클러스터형 인덱스를 6바이트 행 ID로 만든다(매뉴얼, Clustered and Secondary Indexes).

    저장과 읽기의 단위는 행이 아니라 페이지(page)다. 매뉴얼에 따르면 InnoDB 인덱스 페이지의 기본 크기는 16KB이고, 인스턴스를 초기화할 때 innodb_page_size로 정해진다. 엔진은 행 하나가 필요해도 그 행이 든 16KB 페이지 전체를 메모리의 버퍼 풀(buffer pool)로 가져온다. 버퍼 풀에 이미 있는 페이지라면 디스크를 읽지 않아도 되지만, 그 경우에도 페이지 안의 모든 행을 하나씩 꺼내 조건을 평가하는 CPU 일은 그대로 남는다. 그러니 전체 테이블 스캔은 클러스터형 인덱스의 가장 왼쪽 리프 페이지에서 시작해 오른쪽 이웃 페이지로 계속 넘어가며 모든 리프 페이지의 모든 행을 평가하는 일이다.

    전체 테이블 스캔 (WHERE name = '무선 키보드-000008', name에 인덱스 없음)

클러스터형 인덱스 = 테이블 (item_id 순서)

            [ 루트 페이지 ]
           /       |       \
     [내부]      [내부]     [내부]  ...
     /   \        ...
 [리프1] → [리프2] → [리프3] → ... → [리프 마지막]
 id 1~?    다음 행들   ...              ... id 100000
   ↑
   스캔 시작: 리프를 오른쪽으로 따라가며 모든 행의 name을 비교
   id 8에서 일치를 찾아도 멈추지 않는다 (같은 name이 또 있을 수 있음)

    일의 양을 어림해 보자. 한 페이지에 행이 100개쯤 들어간다고 가정하면 10만 행은 리프 페이지 약 1,000개다. 행 하나를 찾으려고 페이지 1,000개를 거치고 비교를 10만 번 한다. 테이블이 1,000만 행으로 커지면 페이지 10만 개, 비교 1,000만 번이다. 일의 양이 테이블 크기에 정비례한다. 매뉴얼의 표현으로는 인덱스가 없으면 MySQL은 첫 행에서 시작해 테이블 전체를 읽어야 하고, 테이블이 클수록 비용이 커진다.

    대조를 위해 기본 키로 찾는 쿼리를 보자. SELECT * FROM item WHERE item_id = 8;의 EXPLAIN에서 type은 const다. 매뉴얼은 const를 "일치하는 행이 많아야 하나"인 경우로 정의하고, 기본 키나 UNIQUE 인덱스의 모든 부분을 상수와 비교할 때 쓰인다고 설명한다.

| id | select_type | table | partitions | type  | possible_keys | key     | key_len | ref   | rows | filtered | Extra |
+----+-------------+-------+------------+-------+---------------+---------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | item  | NULL       | const | PRIMARY       | PRIMARY | 8       | const |    1 |   100.00 | NULL  |
+----+-------------+-------+------------+-------+---------------+---------+---------+-------+------+----------+-------+

    이 쿼리는 클러스터형 인덱스의 루트에서 출발해 "8은 어느 자식 쪽인가"를 따라 내려가 리프 페이지 하나에 도착한다. 거치는 페이지는 트리의 높이만큼, 보통 서너 개다. 같은 테이블, 같은 한 행인데 기준이 기본 키냐 이름이냐에 따라 일의 양이 수백 배 차이 난다. 테이블은 이미 기본 키라는 인덱스를 하나 갖고 있는 셈이고, 문제는 기본 키가 아닌 다른 열로 찾을 때다.

    일상에서 가져온 비유목록 없는 도서관

    책이 등록 번호 순서로 꽂힌 도서관을 생각해 보자. 등록 번호를 알면 서가 번호를 따라가 바로 꺼낼 수 있다. 하지만 "저자가 홍길동인 책"을 찾으려면 모든 서가의 모든 책을 꺼내 저자를 확인해야 한다. 홍길동의 책을 한 권 찾았다고 멈출 수도 없다. 다른 책이 또 있을지 모르기 때문이다. 그래서 도서관은 저자 이름 순서로 정리한 목록 카드를 따로 둔다. 비유가 깨지는 지점도 있다. 도서관 목록은 책이 들어올 때만 고치면 되지만, 데이터베이스 인덱스는 행이 바뀔 때마다 즉시 함께 고쳐져야 하고, 그 비용은 쓰기 쿼리가 낸다.

    인덱스 없이 모든 리프 페이지를 훑는 경로와, 트리를 따라 위에서 아래로 몇 개 페이지만 거치는 경로를 나란히 보여 준다. 좌우 두 칸으로 나뉜 깔끔한 기술 도식. 왼쪽 칸 제목 "전체 테이블 스캔". 맨 아래에 작은 사각형 페이지 12개가 가로로 한 줄로 늘어서 있고 페이지 사이가 오른쪽 화살표로 이어져 있다. 모든 페이지가 주황색으로 칠해져 있고 그 위에 긴 화살표가 왼쪽 끝에서 오른쪽 끝까지 가로지르며 라벨 "모든 리프 페이지를 읽음". 아래에 "비교 횟수 = 전체 행 수". 오른쪽 칸 제목 "인덱스 탐색". 위가 좁고 아래가 넓은 삼각형 모양의 트리: 맨 위 페이지 1개 "루트", 가운데 페이지 4개 "내부", 맨 아래 페이지 12개 "리프". 루트에서 내부 페이지 하나, 거기서 리프 페이지 하나로 이어지는 굵은 파란 화살표 경로만 강조되고 그 세 페이지만 파란색, 나머지는 연한 회색. 라벨 "높이만큼만 읽음". 흰 배경, 단순한 평면 스타일. 인덱스가 없으면 리프 페이지 전체를 읽고, 인덱스가 있으면 트리의 높이만큼의 페이지만 거쳐 원하는 위치에 도착한다.

    인덱스란 무엇인가

    인덱스는 검색 기준이 되는 열의 값과, 그 값을 가진 행을 다시 찾아갈 수 있는 정보를 짝지어 값의 순서대로 정렬해 둔 별도의 자료 구조다. 책 뒤의 찾아보기를 떠올리면 된다. 찾아보기는 용어를 가나다순으로 늘어놓고 각 용어 옆에 쪽 번호를 적어 둔다. 용어가 정렬되어 있으니 원하는 용어를 빨리 찾을 수 있고, 쪽 번호를 따라 본문으로 갈 수 있다. 본문 자체를 용어 순서로 다시 쓸 필요는 없다.

    InnoDB에는 두 종류의 인덱스가 있다. 하나는 앞에서 본 클러스터형 인덱스다. 기본 키 순서로 정렬된 트리이고, 리프에 행 데이터 전체가 들어 있다. 테이블당 하나뿐이다. 다른 하나는 그 밖의 모든 인덱스, 곧 보조 인덱스(secondary index)다. name에 인덱스를 만들면 name 값의 순서로 정렬된 별도의 트리가 하나 더 생긴다. 이 트리의 리프 레코드에는 무엇이 들어 있을까? 매뉴얼은 InnoDB 보조 인덱스의 각 레코드가 인덱스로 지정한 열과 함께 그 행의 기본 키 열을 담고, InnoDB는 이 기본 키 값으로 클러스터형 인덱스에서 행을 찾는다고 설명한다.

    보조 인덱스 idx_item_name (name 순서로 정렬)     클러스터형 인덱스 (item_id 순서로 정렬)

리프 레코드: (name, item_id)                        리프 레코드: 행 전체
  ...                                                 ...
  ('무선 키보드-000001', 1)  ───────────────┐         (1, '무선 키보드-000001', '가전', 1100, 1)
  ('무선 키보드-000008', 8)  ──────────┐    └──────→  ...
  ('무선 키보드-000015', 15)           └───────────→  (8, '무선 키보드-000008', '의류', 1800, 8)
  ...                                                 ...

보조 인덱스에서 찾은 것은 "행"이 아니라 "기본 키 값"이다.
행을 얻으려면 그 기본 키로 클러스터형 인덱스를 한 번 더 탐색한다.

    여기서 책의 찾아보기 비유가 한 번 깨진다. 찾아보기의 쪽 번호는 물리적 위치다. InnoDB 보조 인덱스가 담는 것은 물리적 위치(몇 번 페이지의 몇 번째 칸)가 아니라 기본 키 값이다. 그래서 보조 인덱스로 행을 찾는 일은 두 번의 트리 탐색이 된다. 보조 인덱스 트리를 내려가 기본 키를 얻고, 그 기본 키로 클러스터형 인덱스 트리를 다시 내려간다. 대신 얻는 것도 있다. 행이 페이지 분할 같은 이유로 다른 페이지로 옮겨 가도 기본 키 값은 그대로이므로 보조 인덱스를 고칠 필요가 없다. 또 이 설계에서 기본 키의 길이는 모든 보조 인덱스의 크기에 영향을 준다. 매뉴얼도 기본 키가 길면 보조 인덱스가 공간을 더 쓰므로 기본 키를 짧게 두는 편이 유리하다고 적는다.

    보조 인덱스 레코드가 기본 키를 담는다는 사실에서 또 하나가 따라 나온다. MySQL 매뉴얼(Use of Index Extensions)은 InnoDB가 각 보조 인덱스 뒤에 기본 키 열을 자동으로 덧붙여 확장한다고 설명한다. name에 만든 인덱스는 내부적으로 (name, item_id)처럼 다뤄진다. 그래서 값이 같은 레코드끼리는 기본 키 순서로 정렬되어 있다. 가격처럼 같은 값이 100행씩 있는 열의 인덱스를 생각하면, 가격 50,000원인 레코드 100개가 item_id 490, 1490, 2490, … 순서로 나란히 붙어 있다는 뜻이다.

    인덱스는 공짜가 아니다. 보조 인덱스마다 별도의 트리가 디스크와 버퍼 풀의 공간을 차지하고, 행을 넣거나 인덱스 열을 바꾸거나 행을 지울 때마다 그 트리도 함께 고쳐야 한다. 이 비용과 인덱스를 고르는 기준은 06회에서 자세히 다룬다.

    트리 자료 구조: 이진 탐색에서 B+Tree까지

    "값의 순서대로 정렬해 둔 구조"를 무엇으로 만들지가 다음 질문이다. 가장 단순한 후보부터 하나씩 따져 보며, 데이터베이스가 왜 B+Tree에 도착하는지 보자.

    1단계: 정렬된 배열과 이진 탐색

    키를 정렬된 배열에 담아 두면 이진 탐색(binary search)을 쓸 수 있다. 가운데 값과 비교해 찾는 값이 더 작으면 왼쪽 절반, 크면 오른쪽 절반만 남긴다. 한 번 비교할 때마다 후보가 절반으로 줄어드므로 N개 가운데 하나를 찾는 데 비교가 약 log2 N번 필요하다. 100만 개라면 2의 20제곱이 약 105만이므로 20번 남짓이다. 처음부터 하나씩 비교하면 최악의 경우 100만 번이다. 탐색만 보면 정렬된 배열은 훌륭하다.

    문제는 데이터가 바뀐다는 데 있다. 정렬된 배열의 한가운데에 새 키를 넣으려면 그 뒤의 원소를 모두 한 칸씩 밀어야 한다. 평균적으로 원소의 절반을 옮기는 셈이다. 지우는 것도 마찬가지다. 행이 끊임없이 들어오고 바뀌는 데이터베이스에서 삽입마다 수십만 개를 옮기는 구조는 쓸 수 없다.

    2단계: 이진 탐색 트리와 균형

    삽입 문제를 풀려면 원소를 연속된 칸에 두지 않고 노드와 링크로 연결하면 된다. 이진 탐색 트리(binary search tree)는 노드마다 키 하나와 자식 링크 두 개를 두고, 왼쪽 자식 아래에는 더 작은 키, 오른쪽 자식 아래에는 더 큰 키만 오게 한다. 탐색은 루트에서 시작해 크기를 비교하며 한쪽으로만 내려가고, 삽입은 탐색이 끝난 빈자리에 노드를 하나 붙이면 된다. 원소를 밀 필요가 없다.

    그런데 탐색 비용은 트리의 높이에 달려 있고, 높이는 키가 들어온 순서에 달려 있다. 1, 2, 3, 4, …처럼 오름차순으로 키를 넣으면 새 키가 항상 가장 오른쪽 자식이 되어 트리가 한쪽으로만 길게 늘어진다. 사실상 연결 리스트가 되어 탐색이 다시 N번에 가까워진다. 데이터베이스에서 기본 키를 AUTO_INCREMENT로 쓰면 키는 바로 이 순서로 들어온다. 그래서 삽입 때마다 회전 같은 연산으로 높이를 log2 N 수준으로 유지하는 균형 트리(balanced tree)가 필요하다. 자바의 TreeMap이 쓰는 레드-블랙 트리가 그런 예다.

    3단계: 디스크에서는 노드 하나가 페이지 하나다

    균형 이진 트리면 충분할까? 메모리 안에서는 그렇다. 하지만 데이터베이스의 인덱스는 디스크에 저장되고 페이지 단위로 읽힌다. 트리의 노드 하나를 따라갈 때마다 다른 페이지를 읽어야 할 수 있다. 키 2,500만 개를 균형 이진 트리에 담으면 높이가 log2(25,000,000), 약 24.6이므로 25단계쯤 된다. 키 하나를 찾는 데 페이지를 25개 읽을 수 있다는 뜻이다. 게다가 16KB 페이지를 읽어 와서 쓰는 것은 그 안의 키 하나와 링크 두 개, 고작 수십 바이트다.

    해결책은 자연스럽다. 한 번 읽는 페이지를 꽉 채워 쓰면 된다. 노드 하나에 키를 수백 개 넣고 자식 링크도 수백 개 둔다. 노드 안에서는 정렬된 키들 사이를 이진 탐색해 어느 자식으로 내려갈지 정한다. 노드 안의 탐색은 이미 메모리로 가져온 페이지 안에서 일어나므로 싸다. 비싼 것은 페이지를 새로 가져오는 일이고, 그 횟수는 트리의 높이와 같다. 자식이 2개가 아니라 수백 개인 트리의 높이는 log2 N이 아니라 log_f N(f는 노드당 자식 수, 곧 팬아웃(fan-out))이다. 이것이 B-Tree의 발상이다. MySQL 매뉴얼의 용어집도 B-tree 노드는 자식을 많이 가질 수 있으므로 자식이 둘로 제한된 이진 트리(binary tree)와 같은 것이 아니라고 적는다.

    4단계: B-Tree에서 B+Tree로

    고전적인 B-Tree는 모든 노드에 키와 그 키의 데이터를 함께 둔다. 데이터베이스 인덱스가 실제로 쓰는 변형은 B+Tree라고 불리는 형태로, 두 가지가 다르다. 첫째, 실제 레코드는 맨 아래의 리프 노드에만 두고, 위쪽 노드에는 "어느 자식으로 내려갈지"를 가르는 구분 키와 자식 링크만 둔다. 위쪽 노드가 가벼워지니 노드 하나에 더 많은 자식을 담을 수 있고 트리가 더 낮아진다. 둘째, 리프 노드들을 키 순서대로 옆으로 연결한다. 그래서 어떤 키를 찾은 뒤 그다음 키들을 차례로 읽는 범위 검색을, 트리를 다시 오르내리지 않고 리프를 따라 옆으로 걸어가며 할 수 있다.

    InnoDB의 인덱스가 바로 이 구조다. 매뉴얼은 공간 인덱스를 제외한 InnoDB 인덱스가 B-tree 자료 구조이고 인덱스 레코드는 리프 페이지에 저장된다고 적는다. 또 용어집은 "B-tree"라는 말이 인덱스 설계의 일반적인 부류를 가리키며, MySQL 저장 엔진이 쓰는 구조는 고전 B-tree에 없는 개선이 들어간 변형으로 볼 수 있다고 덧붙인다. 그 변형의 세부는 InnoDB 소스 코드에서 확인할 수 있다. 리프가 아닌 페이지에는 노드 포인터(node pointer) 레코드가 있고, 그 레코드의 마지막 필드가 자식 페이지 번호다(btr0btr.h의 btr_node_ptr_get_child_page_no 설명). 페이지의 레벨은 리프가 0이고 위로 갈수록 커진다(btr_page_get_level 설명: "leaf level == 0"). 그리고 같은 레벨의 B-tree 페이지들은 파일 페이지 헤더의 FIL_PAGE_PREV와 FIL_PAGE_NEXT로 이어진 이중 연결 리스트로 유지된다(fil0types.h). 이전 페이지와 다음 페이지를 모두 가리키므로 리프를 오른쪽으로도, 왼쪽으로도 따라갈 수 있다. 이 사실은 뒤에서 내림차순 정렬을 볼 때 다시 쓴다.

    페이지 안에서도 탐색은 정렬을 이용한다. 한 페이지 안의 레코드들은 키 순서로 연결되어 있고, 페이지 끝부분의 페이지 디렉터리(page directory)가 몇 개 레코드마다 하나씩 레코드 위치를 기록해 둔다. 엔진은 이 디렉터리를 이진 탐색해 범위를 좁힌 다음 연결을 따라 몇 칸만 이동한다. 그래서 수백 개의 레코드가 든 페이지 안에서 원하는 위치를 찾는 데도 레코드를 처음부터 하나씩 볼 필요가 없다.

    InnoDB B+Tree (레벨 2, 높이 3)

레벨 2   [ 루트: (k0,p1) (k1,p2) (k2,p3) ... ]       노드 포인터 = (구분 키, 자식 페이지 번호)
              |        |        |
레벨 1   [내부 A]   [내부 B]   [내부 C]  ...         ← 같은 레벨끼리 PREV/NEXT로 연결
          /  |  \     ...
레벨 0  [리프] ⇄ [리프] ⇄ [리프] ⇄ [리프] ⇄ ...     ← 인덱스 레코드는 리프에만
         키 순서로 정렬, 양방향 연결

탐색: 루트 → 레벨 1 → 레벨 0, 레벨마다 페이지 1개 = 높이만큼 페이지를 읽는다
범위: 시작 키의 리프를 찾은 뒤 NEXT를 따라 오른쪽으로 걷는다

    높이는 얼마나 낮은가

    팬아웃이 트리 높이에 주는 효과를 숫자로 보자. 실제 팬아웃은 키의 크기, 레코드 형식, 페이지가 얼마나 차 있는지에 따라 달라지므로 아래는 가정에 따른 계산이다. 리프 페이지 하나에 레코드 100개, 내부 페이지 하나에 자식 500개가 들어간다고 가정하자. 리프 하나만 있으면(높이 1) 100행, 높이 2면 루트가 리프 500개를 가리키므로 5만 행, 높이 3이면 100 × 500 × 500 = 2,500만 행, 높이 4면 100 × 500^3 = 125억 행이다.

    트리 높이(읽는 페이지 수)담을 수 있는 행 수 (리프 100개, 팬아웃 500 가정)같은 행 수를 균형 이진 트리로 담을 때의 높이
    1100약 7
    250,000약 16
    325,000,000약 25
    412,500,000,000약 34

    높이는 행 수의 로그로 자라므로, 행이 500배 늘어도 높이는 1만 늘어난다. 행 수가 2,500만에서 125억으로 늘어도 키 하나를 찾는 데 읽는 페이지는 3개에서 4개가 될 뿐이다. 게다가 루트와 그 바로 아래 레벨의 페이지들은 거의 모든 탐색이 지나가므로 버퍼 풀에 머물러 있을 가능성이 높다. 실제로 디스크에서 새로 읽어야 하는 것은 주로 아래쪽 레벨의 페이지다.

    B+Tree가 낮고 고르게 유지되는 방식도 짚어 두자. 리프가 가득 찬 상태에서 새 레코드가 들어오면 그 페이지를 둘로 나누고(페이지 분할), 새 페이지를 가리키는 노드 포인터를 부모에 넣는다. 부모도 가득 차면 다시 나뉘고, 루트까지 나뉘면 그 위에 새 루트가 생기며 높이가 1 늘어난다. 트리는 아래로 자라는 것이 아니라 위로 자라기 때문에 모든 리프는 언제나 같은 깊이에 있다. 매뉴얼은 클러스터형 인덱스에 새 레코드를 넣을 때 앞으로의 삽입과 갱신을 위해 페이지의 1/16을 비워 두려 하며, 레코드가 순차적으로 들어오면 페이지가 약 15/16 차고 무작위 순서로 들어오면 1/2에서 15/16 사이로 찬다고 설명한다. 반대로 삭제로 페이지의 채움 비율이 MERGE_THRESHOLD(지정하지 않으면 50%) 아래로 떨어지면 InnoDB는 이웃 페이지와 합쳐 트리를 줄이려 한다.

    루트, 내부, 리프의 세 레벨과, 노드 포인터가 자식 페이지를 가리키는 방식, 리프 페이지끼리의 양방향 연결을 보여 준다. 위에서 아래로 세 층으로 된 트리 도식. 맨 위에 넓은 사각형 하나 "루트 (레벨 2)", 그 안에 칸 네 개가 있고 각 칸에 "구분 키 | 자식 페이지 번호". 각 칸에서 아래층의 사각형으로 화살표가 내려간다. 가운데 층에 사각형 네 개 "내부 페이지 (레벨 1)"가 있고, 각각 다시 아래층의 사각형 서너 개로 화살표가 내려간다. 맨 아래층에 작은 사각형 12개가 가로로 늘어서 있고 라벨 "리프 페이지 (레벨 0)". 리프 사이마다 양쪽 방향 화살표가 있고 라벨 "PREV / NEXT 양방향 연결". 리프 하나를 확대한 말풍선에 "키 순서로 정렬된 인덱스 레코드". 왼쪽 여백에 위에서 아래로 향하는 세로 화살표와 라벨 "탐색: 레벨마다 페이지 1개". 리프 층 아래에 왼쪽에서 오른쪽으로 가는 긴 화살표와 라벨 "범위 검색: 옆으로 걷기". 흰 배경, 파랑과 회색. InnoDB 인덱스는 리프에만 레코드를 두고 위쪽 페이지에는 노드 포인터만 둔다. 같은 레벨의 페이지는 앞뒤로 연결되어 있어 범위를 옆으로 읽어 나갈 수 있다.

    자바로 작은 B+Tree를 만들어 세어 보기

    지금까지의 이야기를 코드로 확인해 보자. 아래 프로그램은 정렬된 키 100만 개로 B+Tree를 아래에서 위로 쌓는다. 리프 하나에 키 100개, 내부 노드 하나에 자식 100개를 넣는다. 노드 하나를 페이지 하나로 보고, 탐색하면서 읽은 노드 수와 키 비교 횟수를 센다. 실제 InnoDB는 삽입과 분할로 트리를 키워 가지만, 여기서는 정렬된 데이터로 한 번에 쌓았다. 탐색 경로를 보려는 목적에는 충분하다.

    import java.util.ArrayList;
import java.util.List;

public class IndexSim {

    // 노드 하나 = 페이지 하나라고 생각한다. 리프는 키를, 내부 노드는 자식의 최소 키를 가진다.
    static final class Node {
        final int[] keys;
        final Node[] children;   // 리프면 null
        Node next;               // 같은 레벨의 오른쪽 이웃(리프에서만 사용)
        Node(int[] keys, Node[] children) { this.keys = keys; this.children = children; }
        boolean isLeaf() { return children == null; }
    }

    static int nodeReads = 0;    // 읽은 노드(페이지) 수
    static long comparisons = 0; // 키 비교 횟수

    // 정렬된 키로 아래에서 위로 트리를 쌓는다(정렬 후 일괄 생성).
    static Node build(int[] sorted, int leafCap, int fanout) {
        List level = new ArrayList<>();
        for (int i = 0; i < sorted.length; i += leafCap) {
            int end = Math.min(i + leafCap, sorted.length);
            int[] ks = new int[end - i];
            System.arraycopy(sorted, i, ks, 0, ks.length);
            Node leaf = new Node(ks, null);
            if (!level.isEmpty()) level.get(level.size() - 1).next = leaf;
            level.add(leaf);
        }
        int height = 1;
        while (level.size() > 1) {
            List upper = new ArrayList<>();
            for (int i = 0; i < level.size(); i += fanout) {
                int end = Math.min(i + fanout, level.size());
                Node[] ch = level.subList(i, end).toArray(new Node[0]);
                int[] ks = new int[ch.length];
                for (int j = 0; j < ch.length; j++) ks[j] = ch[j].keys[0];
                upper.add(new Node(ks, ch));
            }
            level = upper;
            height++;
        }
        System.out.println("트리 높이(레벨 수): " + height);
        return level.get(0);
    }

    // keys에서 key 이하인 마지막 위치(이진 탐색)
    static int floor(int[] keys, int key) {
        int lo = 0, hi = keys.length - 1, ans = 0;
        while (lo <= hi) {
            int mid = (lo + hi) >>> 1;
            comparisons++;
            if (keys[mid] <= key) { ans = mid; lo = mid + 1; } else { hi = mid - 1; }
        }
        return ans;
    }

    static Node descend(Node root, int key) {
        Node n = root;
        nodeReads++;
        while (!n.isLeaf()) {
            n = n.children[floor(n.keys, key)];
            nodeReads++;
        }
        return n;
    }

    static boolean pointLookup(Node root, int key) {
        Node leaf = descend(root, key);
        int i = floor(leaf.keys, key);
        return leaf.keys[i] == key;
    }

    static int rangeScan(Node root, int from, int to) {
        Node leaf = descend(root, from);
        int found = 0;
        int i = floor(leaf.keys, from);
        while (leaf != null) {
            for (; i < leaf.keys.length; i++) {
                comparisons++;
                if (leaf.keys[i] > to) return found;
                if (leaf.keys[i] >= from) found++;
            }
            leaf = leaf.next;
            if (leaf != null) nodeReads++;
            i = 0;
        }
        return found;
    }

    public static void main(String[] args) {
        int n = 1_000_000;
        int[] keys = new int[n];
        for (int i = 0; i < n; i++) keys[i] = i * 2;   // 0, 2, 4, ... 짝수만 있다

        // 1) 인덱스 없이 처음부터 끝까지 비교
        long scan = 0;
        int target = 1_999_998;
        for (int k : keys) { scan++; if (k == target) break; }
        System.out.println("전체 스캔 비교 횟수(마지막 키): " + scan);

        // 2) B+Tree: 리프 하나에 100개, 내부 노드 하나에 자식 100개
        Node root = build(keys, 100, 100);

        nodeReads = 0; comparisons = 0;
        boolean hit = pointLookup(root, target);
        System.out.println("동등 검색 " + target + " 존재=" + hit
                + " 읽은 노드=" + nodeReads + " 비교=" + comparisons);

        nodeReads = 0; comparisons = 0;
        hit = pointLookup(root, 777);
        System.out.println("동등 검색 777 존재=" + hit
                + " 읽은 노드=" + nodeReads + " 비교=" + comparisons);

        nodeReads = 0; comparisons = 0;
        int cnt = rangeScan(root, 100_000, 101_998);
        System.out.println("범위 검색 [100000, 101998] 결과=" + cnt
                + " 읽은 노드=" + nodeReads + " 비교=" + comparisons);
    }
}

    전체 스캔 비교 횟수(마지막 키): 1000000
트리 높이(레벨 수): 3
동등 검색 1999998 존재=true 읽은 노드=3 비교=21
동등 검색 777 존재=false 읽은 노드=3 비교=21
범위 검색 [100000, 101998] 결과=1000 읽은 노드=13 비교=1021

    한 줄씩 따라가 보자. 키는 0, 2, 4, …, 1,999,998의 짝수 100만 개다. 첫 줄은 인덱스가 없을 때의 상황이다. 마지막 키를 찾으려고 처음부터 하나씩 비교하니 100만 번이 걸렸다. 둘째 줄은 트리를 쌓은 결과다. 리프는 1,000,000 / 100 = 10,000개, 그 위 레벨은 10,000 / 100 = 100개, 그 위는 100 / 100 = 1개, 곧 루트다. 레벨이 셋이므로 높이는 3이다.

    셋째 줄에서 같은 마지막 키를 트리로 찾으니 읽은 노드는 3개다. 루트, 내부 노드 하나, 리프 하나다. 비교 21번은 세 노드에서 각각 키 100개 사이를 이진 탐색한 횟수의 합으로, 노드마다 7번 정도다. 100만 번과 21번, 그리고 페이지 기준으로는 리프 10,000개 전체와 노드 3개의 차이다. 넷째 줄은 존재하지 않는 키 777(홀수)을 찾은 결과다. 없는 키를 확인하는 데도 똑같이 노드 3개를 읽는다. 트리를 내려가 777이 있어야 할 자리에 도착했는데 거기 없으면 없는 것이다. 정렬되어 있지 않다면 "없다"를 확인하는 일이 가장 비싸다. 전체를 다 봐야 하기 때문이다.

    다섯째 줄은 범위 검색이다. 100,000 이상 101,998 이하의 짝수는 1,000개다. 엔진처럼 먼저 시작 키 100,000이 있을 리프를 찾아 내려가고(노드 3개), 거기서부터 리프의 다음 링크를 따라 오른쪽으로 걸었다. 100,000은 50,000번째 키(0부터 셈)이므로 501번째 리프의 첫 키이고, 1,000개는 리프 10개에 걸쳐 있다. 마지막 키 101,998을 읽은 뒤에도 "더 있는지"를 알려면 다음 리프의 첫 키 102,000을 봐야 범위를 벗어났음을 안다. 그래서 내려가며 읽은 3개에 옆으로 넘어간 리프 10개를 더해 13개가 되었다. 비교 1,021번은 내려가며 한 세 번의 이진 탐색 20번과, 리프에서 확인한 1,001개(결과 1,000개와 범위 밖의 첫 키 하나)의 합이다. 범위 검색의 비용은 "높이 + 결과가 걸친 리프 수"이고, 결과 행 수에 비례한다. 테이블 전체 크기와는 거의 상관이 없다.

    이 시뮬레이션의 트리는 정렬된 정수 배열 하나다. 실제 InnoDB 보조 인덱스에서는 리프에서 얻은 기본 키로 클러스터형 인덱스를 한 번 더 내려가야 행 전체를 얻는다. 그 비용은 결과 행마다 붙으며, 뒤의 동등 비교와 범위 검색 절에서 따로 계산한다.

    인덱스 생성, 조회, 삭제

    이제 실습 테이블에 인덱스를 만들어 보자. MySQL에서 보조 인덱스를 만드는 문법은 세 가지다. 결과는 같고, 쓰는 자리가 다를 뿐이다.

    -- 1) CREATE INDEX 문
CREATE INDEX idx_item_name ON item (name);

-- 2) ALTER TABLE 문
ALTER TABLE item ADD INDEX idx_item_price (price);
CREATE INDEX idx_item_category ON item (category);

-- 3) 테이블을 만들 때 함께 선언 (예시용 별도 테이블)
CREATE TABLE item_archive (
    item_id   BIGINT       NOT NULL,
    category  VARCHAR(20)  NOT NULL,
    PRIMARY KEY (item_id),
    INDEX idx_item_archive_category (category)
);

-- 같은 값을 두 번 허용하지 않는 유일 인덱스
-- CREATE UNIQUE INDEX uk_item_name ON item (name);

    인덱스 이름은 테이블 안에서 유일해야 하고, 실행 계획과 오류 메시지에 그대로 나오므로 무엇을 위한 인덱스인지 읽히게 짓는다. 여기서는 idx_테이블_열 형식을 썼다. 유일 인덱스(unique index)는 검색 구조이면서 동시에 같은 값이 두 번 들어오는 것을 막는 제약이다. 기본 키와 UNIQUE 제약을 선언하면 MySQL이 그에 해당하는 인덱스를 함께 만든다. 외래 키 제약을 걸 때도 InnoDB는 참조하는 쪽 열에 인덱스가 없으면 만들어 둔다. 제약 조건 자체는 07회의 주제다.

    이미 데이터가 있는 테이블에 인덱스를 만들 때

    10만 행이 들어 있는 테이블에 CREATE INDEX를 실행하면 엔진은 무엇을 할까? 행을 하나씩 꺼내 빈 트리에 한 건씩 넣는 방식은 페이지 분할을 수없이 일으킨다. MySQL 매뉴얼(Sorted Index Builds)에 따르면 InnoDB는 인덱스를 만들거나 다시 만들 때 레코드를 하나씩 넣지 않고 한꺼번에 적재하며, 이를 정렬 인덱스 빌드(sorted index build)라고 부른다. 과정은 세 단계다. 첫째, 클러스터형 인덱스를 훑으며 인덱스 항목을 만들어 정렬 버퍼에 담고, 버퍼가 차면 정렬해 임시 파일에 쓴다. 둘째, 임시 파일의 정렬된 묶음들을 병합 정렬한다. 셋째, 정렬된 항목을 B-tree에 넣는다. 앞의 자바 시뮬레이션이 정렬된 키로 리프부터 쌓아 올린 것과 같은 발상이다. 이때 페이지를 얼마나 채울지는 innodb_fill_factor로 정하는데, 매뉴얼은 기본값 100에서도 클러스터형 인덱스 페이지의 1/16은 앞으로의 증가를 위해 비워 둔다고 설명한다.

    운영 중인 테이블에 인덱스를 만들 때 가장 궁금한 것은 "그동안 테이블을 쓸 수 있는가"이다. MySQL 8.0 매뉴얼의 온라인 DDL 표에서 보조 인덱스 생성은 제자리(In Place) 작업이고, 테이블을 다시 만들지 않으며, 동시에 DML(INSERT, UPDATE, DELETE)을 허용한다. 인덱스를 만드는 동안 테이블은 읽기와 쓰기에 계속 쓰일 수 있다는 뜻이다. 다만 매뉴얼은 CREATE INDEX 문이 그 테이블에 접근 중인 모든 트랜잭션이 끝난 뒤에야 완료된다고 덧붙인다. 오래 열려 있는 트랜잭션이 있으면 인덱스 생성이 그만큼 끝나지 않는다. 같은 표에서 인덱스 삭제는 메타데이터만 바꾸는 작업으로 분류된다.

    인덱스 지우기와 숨기기

    DROP INDEX idx_item_category ON item;
-- 또는
ALTER TABLE item DROP INDEX idx_item_category;

-- MySQL 8.0: 지우지 않고 옵티마이저에게서만 숨기기
ALTER TABLE item ALTER INDEX idx_item_price INVISIBLE;
ALTER TABLE item ALTER INDEX idx_item_price VISIBLE;

    인덱스를 지우는 것은 간단하지만, 큰 테이블에서 지웠다가 "역시 필요했다"며 다시 만드는 것은 비싸다. MySQL 8.0은 그 사이에 쓸 수 있는 보이지 않는 인덱스(invisible index)를 지원한다. 매뉴얼에 따르면 보이지 않는 인덱스는 옵티마이저가 쓰지 않을 뿐, 행이 바뀔 때 계속 갱신되고 유일 인덱스라면 중복을 계속 막는다. 그래서 인덱스를 숨겨 두고 쿼리 성능에 문제가 없는지 지켜본 다음 지울 수 있고, 문제가 생기면 즉시 다시 보이게 하면 된다. 매뉴얼은 숨기기와 보이기가 빠른 제자리 작업이라고 설명한다. 8.0.46에서 idx_item_price를 INVISIBLE로 바꾸고 WHERE price = 50000을 EXPLAIN하면 type이 ALL, key가 NULL로 바뀌고, VISIBLE로 되돌리면 다시 인덱스를 쓴다. 기본 키(명시적이든 암묵적이든)는 숨길 수 없다. ALTER TABLE item ALTER INDEX `PRIMARY` INVISIBLE;을 실행하면 8.0.46에서 ERROR 3522 (HY000): A primary key index cannot be invisible 오류가 난다.

    인덱스와 동등 비교

    이제 idx_item_name이 있는 상태에서 처음의 쿼리를 다시 실행해 보자.

    EXPLAIN SELECT * FROM item WHERE name = '무선 키보드-000008';
-- 확인할 열: type = ref, key = idx_item_name
    +----+-------------+-------+------------+------+---------------+---------------+---------+-------+------+----------+-------+
| id | select_type | table | partitions | type | possible_keys | key           | key_len | ref   | rows | filtered | Extra |
+----+-------------+-------+------------+------+---------------+---------------+---------+-------+------+----------+-------+
|  1 | SIMPLE      | item  | NULL       | ref  | idx_item_name | idx_item_name | 202     | const |    1 |   100.00 | NULL  |
+----+-------------+-------+------------+------+---------------+---------------+---------+-------+------+----------+-------+

    EXPLAIN의 type은 ALL에서 ref로, key는 NULL에서 idx_item_name으로 바뀐다. 매뉴얼은 ref를 "인덱스 값이 일치하는 모든 행을 읽는" 접근 방식으로, 키가 기본 키나 UNIQUE 인덱스가 아니라서 값 하나로 행 하나를 고를 수 없을 때 쓰인다고 설명한다. =나 <=>로 비교하는 인덱스 열에 쓰인다. 엔진 안에서 일어나는 일을 단계별로 따라가 보자.

    읽은 페이지는 두 트리의 높이를 더한 정도, 대략 예닐곱 개다. 인덱스가 없을 때 리프 페이지 약 1,000개를 읽던 것과 비교하면 두 자릿수 이상 줄었다. 더 중요한 차이는 증가 속도다. 테이블이 1,000만 행이 되어도 트리 높이는 한두 단계 늘어날 뿐이므로 이 쿼리의 일은 거의 그대로다. 전체 스캔은 100배가 된다.

    마지막 단계의 "다음 레코드 확인"을 없애는 방법이 유일 인덱스다. name에 UNIQUE 인덱스를 만들었다면 같은 쿼리의 type은 const가 된다(8.0.46에서 CREATE UNIQUE INDEX uk_item_name ON item (name);을 만든 뒤 EXPLAIN하면 type은 const, key는 uk_item_name이었다). 매뉴얼의 정의대로 UNIQUE 인덱스의 모든 부분을 상수와 비교하면 일치하는 행이 많아야 하나이므로, 옵티마이저는 쿼리를 시작할 때 그 행을 한 번 읽고 나머지 계산에서 그 값을 상수처럼 다룬다. 데이터의 의미상 유일한 열이라면 유일 인덱스로 선언하는 편이 무결성과 성능 양쪽에서 낫다.

    보조 인덱스 트리에서 기본 키 값을 얻고, 그 값으로 클러스터형 인덱스 트리를 한 번 더 내려가 행을 얻는 두 번의 탐색을 보여 준다. 좌우에 삼각형 모양의 트리 두 개가 있는 도식. 왼쪽 트리 제목 "보조 인덱스 idx_item_name". 루트에서 리프까지 파란 화살표 경로가 강조되고, 리프 칸 하나가 확대되어 "('무선 키보드-000008', 8)"이라고 적혀 있다. 그 칸에서 오른쪽 트리의 루트로 굵은 주황색 화살표가 건너가며 라벨 "기본 키 8로 다시 찾기". 오른쪽 트리 제목 "클러스터형 인덱스 (테이블)". 루트에서 리프까지 주황색 경로가 강조되고, 리프 칸 하나가 확대되어 "행 전체: 8, 무선 키보드-000008, 의류, 1800, 8". 왼쪽 리프 칸 바로 옆의 다음 칸은 회색으로 "('무선 키보드-000015', 15)"이고 라벨 "값이 다르면 멈춤". 아래에 "읽는 페이지 ≈ 보조 인덱스 높이 + 클러스터형 인덱스 높이". 흰 배경, 단순한 평면 스타일. InnoDB 보조 인덱스는 행의 위치가 아니라 기본 키 값을 담고 있으므로, 행 전체가 필요하면 클러스터형 인덱스를 한 번 더 탐색한다.

    일치하는 행이 많으면: 선택도

    이번에는 분류로 찾아 보자. SELECT * FROM item WHERE category = '가전';의 결과는 2만 행이다. idx_item_category로 이 쿼리를 처리하면 보조 인덱스의 '가전' 구간에서 레코드 2만 개를 읽고, 그 하나하나에 대해 클러스터형 인덱스를 내려가야 한다. 그런데 가전인 행의 기본 키는 1, 6, 11, 16, …처럼 5씩 떨어져 테이블 전체에 고르게 흩어져 있다. 한 페이지에 행이 100개쯤 들어 있다면 거의 모든 리프 페이지에 가전 행이 스무 개쯤 들어 있다. 결국 클러스터형 인덱스의 거의 모든 페이지를, 그것도 순서 없이 여러 번에 걸쳐 방문하게 된다. 처음부터 끝까지 한 번 훑는 전체 스캔과 일의 양이 비슷하거나 더 많다.

    조건에 맞는 행이 전체에서 차지하는 비율이 작을수록 그 조건의 선택도(selectivity)가 높다고 말한다. 이름 조건은 10만 행 가운데 1행을 고르므로 선택도가 매우 높고, 분류 조건은 5행 가운데 1행을 고르므로 낮다. 매뉴얼은 옵티마이저가 인덱스를 쓰면 테이블 행의 매우 큰 비율에 접근해야 한다고 추정하면 인덱스가 있어도 쓰지 않을 수 있고, 그럴 때는 테이블 스캔이 탐색(seek)이 적어서 훨씬 빠를 가능성이 높다고 설명한다. 옵티마이저는 비용을 추정해 접근 방법을 고르므로, 이 쿼리에서 실제로 무엇을 고르는지는 데이터와 통계에 달려 있다. 직접 EXPLAIN으로 확인해야 한다. 이 데이터로 8.0.46과 8.4.13에서 확인해 보니 둘 다 전체 스캔이 아니라 type = ref, key = idx_item_category를 골랐고, rows 추정치는 38,970이었다. EXPLAIN ANALYZE로 실제로 돌려 보면 인덱스에서 찾은 행은 20,000행이다. 8.0.46에서 IGNORE INDEX (idx_item_category)로 전체 스캔을 강제한 것과 실제 시간을 비교하면 인덱스 쪽이 18.6밀리초, 전체 스캔 쪽이 22.8밀리초였다. 테이블 전체가 버퍼 풀에 올라와 있어 디스크를 읽지 않은 상태라 두 방법의 차이가 작았고, 이 시간은 실행 환경에 따라 달라진다. 이 결과에서 알 수 있는 것은 "선택도가 낮은 조건이니 옵티마이저가 반드시 인덱스를 버린다"고 단정할 수도 없다는 점이다. 옵티마이저가 그 비용을 어떻게 계산하는지는 06회에서 다룬다.

    인덱스를 쓸 수 없는 동등 비교

    인덱스는 "열의 값"으로 정렬되어 있다. 그러니 조건이 열의 값 자체가 아니라 열을 가공한 결과를 비교하면, 정렬 순서를 이용할 수 없다. 매뉴얼(Range Optimization)은 인덱스로 범위를 정할 수 있는 조건을 "키 부분(key part)을 상수 값과 비교하는 것"으로 정의한다. 열을 함수나 연산으로 감싸면 비교의 왼쪽은 더 이상 키 부분이 아니다.

    -- 인덱스로 범위를 정할 수 없다: 열이 연산과 함수 안에 있다
SELECT * FROM item WHERE price + 1000 = 51000;
SELECT * FROM item WHERE LEFT(name, 6) = '무선 키보드';

-- 같은 뜻을 열을 그대로 두고 쓰면 인덱스를 쓸 수 있다
SELECT * FROM item WHERE price = 50000;
SELECT * FROM item WHERE name LIKE '무선 키보드%';

    날짜 열에서도 같은 함정이 흔하다. WHERE YEAR(created_at) = 2026은 열을 함수로 감쌌으므로 인덱스로 범위를 정하지 못하지만, WHERE created_at >= '2026-01-01' AND created_at < '2027-01-01'은 같은 행을 고르면서 범위 검색이 된다. 원칙은 하나다. 가공은 상수 쪽에서 하고 열은 맨몸으로 둔다. 꼭 가공한 값으로 찾아야 한다면 MySQL 8.0.13부터 지원하는 함수 기반 키 부분(functional key part)으로 식 자체에 인덱스를 만들 수 있다. 예를 들어 CREATE INDEX idx_item_name_head ON item ((LEFT(name, 6)));처럼 식을 괄호로 한 번 더 감싸 선언한다. 8.0.46에서 이 인덱스를 만든 뒤 WHERE LEFT(name, 6) = '무선 키보드'를 EXPLAIN하면 type이 ref, key가 idx_item_name_head로 바뀐다.

    눈에 덜 띄는 함정은 자료형이 다른 비교다. 매뉴얼(Type Conversion in Expression Evaluation)은 문자열 열을 숫자와 비교하면 MySQL이 그 열의 인덱스로 값을 빨리 찾을 수 없다고 명시한다. str_col = 1에서 숫자 1로 변환되는 문자열이 '1', ' 1', '1a'처럼 여럿이기 때문이다. 이 문자열들은 인덱스 안에서 서로 멀리 떨어져 있다. 문자열 순서로 정렬된 인덱스에서 "숫자로 바꾸면 1이 되는 것"을 한 구간으로 잡을 방법이 없다. 상품 코드나 전화번호처럼 숫자로 보이는 값을 문자열 열에 저장했다면, 비교하는 값도 반드시 따옴표를 붙인 문자열로 써야 한다.

    실습 테이블에서도 확인할 수 있다. 문자열 열 name을 숫자 1과 비교하는 EXPLAIN SELECT * FROM item WHERE name = 1;을 8.0.46에서 --show-warnings를 켜고 실행한 결과다.

    possible_keys에는 idx_item_name이 올라왔지만 key는 NULL이고, 경고가 이유를 그대로 말해 준다. name 열의 형 변환 때문에 ref 접근도 range 접근도 쓸 수 없다는 것이다.

    인덱스와 범위 검색

    범위 조건은 B+Tree가 가장 잘하는 일이다. 매뉴얼에 따르면 B-tree 인덱스는 =, >, >=, <, <=, BETWEEN 비교에 쓰일 수 있다. 가격으로 범위를 찾아 보자.

    EXPLAIN SELECT * FROM item WHERE price BETWEEN 10000 AND 10900;
-- 확인할 열: type = range, key = idx_item_price

SELECT COUNT(*) FROM item WHERE price BETWEEN 10000 AND 10900;  -- 1000
    +----+-------------+-------+------------+-------+----------------+----------------+---------+------+------+----------+-----------------------+
| id | select_type | table | partitions | type  | possible_keys  | key            | key_len | ref  | rows | filtered | Extra                 |
+----+-------------+-------+------------+-------+----------------+----------------+---------+------+------+----------+-----------------------+
|  1 | SIMPLE      | item  | NULL       | range | idx_item_price | idx_item_price | 4       | NULL | 1000 |   100.00 | Using index condition |
+----+-------------+-------+------------+-------+----------------+----------------+---------+------+------+----------+-----------------------+

    Extra의 Using index condition은 인덱스 조건 푸시다운(Index Condition Pushdown)이 쓰였다는 표시인데, 여기서는 type과 key만 보면 된다.

    BETWEEN은 양 끝을 포함한다. 가격 10,000원은 n % 1000 = 90, 10,900원은 n % 1000 = 99에 해당하므로 열 가지 가격이 각각 100행씩, 모두 1,000행이다. 인덱스를 쓰기로 했다면 EXPLAIN의 type은 range다. 매뉴얼은 range를 "인덱스로 행을 골라 주어진 범위에 있는 행만 가져오는" 방식으로 설명하고, =, <>, >, >=, <, <=, IS NULL, <=>, BETWEEN, LIKE, IN()으로 키 열을 상수와 비교할 때 쓰인다고 적는다.

    엔진은 자바 시뮬레이션의 rangeScan과 똑같이 움직인다. 먼저 시작 값 10,000이 있을 리프까지 내려간다. 그다음 리프를 오른쪽으로 걸으며 레코드를 읽다가 10,900을 넘는 첫 레코드(가격 11,000원)를 만나면 멈춘다. 보조 인덱스가 내부적으로 (price, item_id)로 정렬되어 있으므로 읽는 순서는 다음과 같다.

    idx_item_price 리프를 왼쪽에서 오른쪽으로 읽는 순서

(10000, 90) (10000, 1090) (10000, 2090) ... (10000, 99090)    ← 가격 10000: 100개
(10100, 91) (10100, 1091) ...               (10100, 99091)    ← 가격 10100: 100개
...
(10900, 99) (10900, 1099) ...               (10900, 99099)    ← 가격 10900: 100개
(11000, 100) → 범위 밖, 여기서 멈춤

각 레코드의 item_id로 클러스터형 인덱스를 다시 탐색:
   90 → 1090 → 2090 → ... → 99090 → 91 → 1091 → ...
   기본 키 순서로는 이리저리 뛰어다니는 접근(랜덤 접근)

    보조 인덱스 쪽의 일은 가볍다. 레코드 1,000개는 서로 붙어 있으므로 몇 개의 리프 페이지에 모여 있다. 무거운 것은 그 뒤의 클러스터형 인덱스 탐색이다. 기본 키 90, 1090, 2090, …은 테이블의 앞에서 뒤까지 흩어져 있어서, 1,000번의 탐색이 저마다 다른 리프 페이지에 떨어질 수 있다. 버퍼 풀에 페이지가 이미 올라와 있다면 디스크 입출력은 줄어들지만, 그래도 트리 하강 1,000번의 일은 남는다.

    대조로 기본 키 범위를 보자. SELECT * FROM item WHERE item_id BETWEEN 50001 AND 51000;도 1,000행이지만, 클러스터형 인덱스는 기본 키 순서로 행을 담고 있으므로 이 1,000행은 이웃한 리프 페이지 몇 개에 연달아 들어 있다. 트리를 한 번 내려간 뒤 옆으로 걷기만 하면 되고, 두 번째 탐색이 없다. 8.0.46의 EXPLAIN에서도 이 쿼리는 type = range, key = PRIMARY로 나온다. 매뉴얼이 클러스터형 인덱스를 통한 접근은 인덱스 탐색이 곧바로 행 데이터가 든 페이지로 이어지므로 빠르다고 설명하는 이유다. 같은 "1,000행 범위 검색"이라도 클러스터형 인덱스에서는 연속된 읽기, 보조 인덱스에서는 1,000번의 흩어진 읽기다.

    범위가 넓으면 인덱스를 버린다

    이 차이 때문에 범위가 넓어지면 보조 인덱스의 이점이 사라진다. WHERE price >= 2000은 n % 1000이 10 이상인 행, 곧 99,000행을 고른다. 인덱스로 처리하면 9만 9천 번의 흩어진 클러스터형 인덱스 탐색이 필요하다. 전체 테이블 스캔은 리프 페이지를 순서대로 한 번 읽으면 된다. 매뉴얼은 쿼리가 대부분의 행에 접근해야 할 때는 인덱스를 거치는 것보다 순차적으로 읽는 편이 빠르고, 순차 읽기는 모든 행이 필요하지 않더라도 디스크 탐색을 최소화한다고 설명한다. 그래서 옵티마이저는 이런 쿼리에서 인덱스를 쓰지 않을 수 있다. 실제로 8.0.46에서 EXPLAIN SELECT * FROM item WHERE price >= 2000;을 실행하면 possible_keys에는 idx_item_price가 있지만 type은 ALL, key는 NULL이다. 후보로 검토한 뒤 버린 것이다.

    같은 매뉴얼은 반대 방향의 예외도 적는다. 그런 쿼리라도 LIMIT으로 일부 행만 가져온다면, 반환할 몇 행을 인덱스로 훨씬 빨리 찾을 수 있으므로 MySQL은 인덱스를 쓴다. SELECT * FROM item WHERE price >= 2000 LIMIT 10은 인덱스의 시작점에서 레코드 10개만 읽고 멈추면 되기 때문이다. 8.0.46에서 이 쿼리를 EXPLAIN하면 type = range, key = idx_item_price로 바뀐다. 인덱스가 유리한지는 조건 하나만 보고 정해지지 않는다. 결과로 실제로 몇 행을 꺼내야 하는가가 정한다.

    IN과 부등호

    WHERE price IN (10000, 50000, 90000)은 값이 같은 구간 세 개, 곧 동등 범위(equality range) 세 개로 처리된다. 결과는 각 100행씩 300행이다. 8.0.46의 EXPLAIN은 type = range, key = idx_item_price, rows = 300이다. 매뉴얼에 따르면 유일하지 않은 인덱스에서 옵티마이저는 각 범위의 양 끝으로 인덱스를 실제로 내려가 보는 인덱스 다이브(index dive)로 행 수를 추정하며, IN (10, 20, 30)이라면 범위 세 개에 각각 두 번씩 다이브한다. 값 목록이 아주 길어지면 추정에 드는 시간을 줄이려고 인덱스 통계로 바꾸는데, 그 경계는 eq_range_index_dive_limit 변수가 정한다.

    WHERE price <> 50000도 매뉴얼의 정의상 B-tree 인덱스의 범위 조건이다. "50,000보다 작은 구간"과 "50,000보다 큰 구간" 두 개로 바꿀 수 있기 때문이다. 하지만 이 조건은 99,900행을 고르므로 앞에서 본 이유로 인덱스가 거의 도움이 되지 않는다. 8.0.46에서 EXPLAIN하면 type = ALL, key = NULL이었다. 문법적으로 인덱스를 쓸 수 있는 조건인가와 인덱스를 쓰는 것이 이득인가는 별개의 질문이다.

    인덱스와 LIKE 범위 검색

    문자열 검색에서 가장 많이 쓰는 것이 LIKE다. LIKE가 인덱스를 쓸 수 있는지는 패턴의 모양이 정한다. 매뉴얼의 규칙은 짧다. LIKE의 인수가 와일드카드 문자로 시작하지 않는 상수 문자열이면 인덱스를 쓸 수 있다. 매뉴얼의 예에서 LIKE 'Patrick%'은 'Patrick' <= key_col < 'Patricl'인 행만, LIKE 'Pat%_ck%'는 'Pat' <= key_col < 'Pau'인 행만 고려한다. 반면 LIKE '%Patrick%'은 값이 와일드카드로 시작하고, LIKE other_col은 값이 상수가 아니므로 인덱스를 쓰지 않는다.

    왜 그런지는 정렬된 목록을 떠올리면 바로 보인다. 'Patrick'으로 시작하는 문자열은 정렬된 목록에서 반드시 한 덩어리로 붙어 있다. 그 덩어리는 'Patrick'과 같거나 큰 곳에서 시작해, 'Patrick'의 마지막 글자를 하나 올린 'Patricl'보다 작은 곳에서 끝난다. 접두사가 정해지면 시작점과 끝점이 정해지므로 범위 검색이 된다. 'Pat%_ck%'처럼 와일드카드가 중간에 있으면 첫 와일드카드 앞까지인 'Pat'만 범위를 정하는 데 쓰이고, 나머지 패턴은 그 범위 안의 행마다 따로 확인한다. 반대로 '%Patrick'처럼 앞이 열려 있으면 'Patrick'으로 끝나는 문자열은 정렬된 목록의 어디에나 있을 수 있다. 시작점을 정할 수 없으니 전부 확인할 수밖에 없다.

    실습 테이블로 옮겨 보자.

    -- 접두사가 정해진 패턴: 범위 검색 가능
SELECT item_id, name FROM item WHERE name LIKE '무선 키보드-0000%';   -- 15행

-- 접두사가 짧아 많은 행이 걸리는 패턴: 범위 검색은 가능하지만 이득이 작다
SELECT COUNT(*) FROM item WHERE name LIKE '무선%';                    -- 28571

-- 와일드카드로 시작하는 패턴: 인덱스로 범위를 정할 수 없다
SELECT item_id, name FROM item WHERE name LIKE '%-000008';            -- 1행

    첫 쿼리는 개념적으로 '무선 키보드-0000' <= name < '무선 키보드-0001'의 범위다. 이름의 번호가 여섯 자리이므로 '0000'으로 시작하는 번호는 000001부터 000099까지다. 그 가운데 n % 7 = 1인 번호, 곧 1, 8, 15, …, 99의 15행이 결과다. 범위 안의 레코드는 정렬되어 붙어 있으므로 리프 한두 개만 읽으면 된다. 8.0.46에서 실행하면 item_id 1, 8, 15, …, 99의 15행이 나오고, EXPLAIN은 type = range, key = idx_item_name, rows = 15, Extra = Using where; Using index다. Using index는 고른 열(item_id, name)이 모두 보조 인덱스 레코드 안에 있어서 클러스터형 인덱스를 다시 찾지 않았다는 표시다. 이것이 06회에서 다룰 커버링 인덱스다.

    둘째 쿼리도 문법상 범위 검색이지만 28,571행, 전체의 약 29%가 걸린다. 보조 인덱스로 행 전체를 가져오려면 클러스터형 인덱스를 2만 8천 번 넘게 다시 탐색해야 하므로, 앞 절의 넓은 범위와 같은 이유로 옵티마이저가 전체 스캔을 택할 수 있다. 8.0.46에서 확인하면 결과가 갈린다. 위의 SELECT COUNT(*) ... LIKE '무선%'는 행 전체가 필요 없으므로 type = range, key = idx_item_name, Extra = Using where; Using index로 보조 인덱스만 읽는다. 같은 조건으로 SELECT * FROM item WHERE name LIKE '무선%'를 EXPLAIN하면 possible_keys에 idx_item_name이 있는데도 type = ALL, key = NULL이다. 행마다 클러스터형 인덱스를 다시 찾아야 하는 쪽에서 인덱스를 버린 것이다.

    셋째 쿼리는 결과가 1행뿐이지만 인덱스가 범위를 좁혀 주지 못한다. 8.0.46의 EXPLAIN은 type = index, key = idx_item_name, rows = 99871, Extra = Using where; Using index다. index는 인덱스 전체를 처음부터 끝까지 훑는 접근 방식이다. 고른 열이 모두 보조 인덱스에 있으니 테이블 대신 그보다 작은 인덱스를 훑었을 뿐, 모든 이름을 하나씩 확인하는 일은 그대로다. 결과 행 수가 적다는 것과 인덱스로 빨리 찾을 수 있다는 것은 다른 이야기다.

    범위의 경계를 실제로 어떻게 만드는지는 열의 콜레이션(collation)에 따라 다르다. 'Patricl'처럼 마지막 글자를 하나 올리는 것은 원리를 보여 주는 설명이고, 실제 경계 값은 엔진이 콜레이션의 정렬 규칙에 맞게 계산한다. MySQL 8.0 서버의 기본 문자 집합과 콜레이션은 utf8mb4와 utf8mb4_0900_ai_ci이다. 이름의 ci는 대소문자를 구분하지 않는다(case-insensitive)는 뜻이고, 인덱스도 이 규칙의 순서로 정렬된다. 그래서 LIKE 'abc%'는 'ABCD'로 시작하는 값도 같은 범위 안에서 찾는다. 8.0.46에서 서버 기본값을 조회하면 utf8mb4와 utf8mb4_0900_ai_ci가 나오고, 이 테이블의 콜레이션도 utf8mb4_0900_ai_ci이며, SELECT 'ABCD' LIKE 'abc%';의 결과는 1(참)이다.

    자바로 확인하는 접두사 범위

    정렬된 집합에서 접두사 검색이 범위 검색으로 바뀌는 모습을 자바의 TreeSet으로 확인해 보자. TreeSet은 균형 이진 트리(레드-블랙 트리)로 정렬을 유지하는 집합이고, subSet(from, true, to, false)는 정렬 순서에서 from 이상 to 미만인 원소만 보여 준다.

    import java.util.List;
import java.util.NavigableSet;
import java.util.TreeSet;

public class LikeRange {
    // 'abc%' -> ['abc', 'abd') : 접두사의 마지막 문자를 하나 올린 값이 상한
    static String upperBound(String prefix) {
        char last = prefix.charAt(prefix.length() - 1);
        return prefix.substring(0, prefix.length() - 1) + (char) (last + 1);
    }

    public static void main(String[] args) {
        NavigableSet index = new TreeSet<>(List.of(
                "apple", "apricot", "banana", "cherry", "grape",
                "kimbap", "kimchi", "kiwi", "lemon", "mango", "pumpkin"));

        String prefix = "kim";
        String hi = upperBound(prefix);
        NavigableSet range = index.subSet(prefix, true, hi, false);
        System.out.println("LIKE 'kim%' -> ['" + prefix + "', '" + hi + "') : " + range);

        int touched = 0;
        StringBuilder hits = new StringBuilder();
        for (String s : index) {          // '%kin' 은 정렬 순서와 무관 -> 전부 확인
            touched++;
            if (s.endsWith("kin")) hits.append(s).append(' ');
        }
        System.out.println("LIKE '%kin' 확인한 항목=" + touched + " 결과=" + hits.toString().trim());
    }
}
    LIKE 'kim%' -> ['kim', 'kin') : [kimbap, kimchi]
LIKE '%kin' 확인한 항목=11 결과=pumpkin

    'kim'의 마지막 글자 'm'을 하나 올리면 'n'이므로 상한은 'kin'이다. 정렬된 집합에서 'kim' 이상 'kin' 미만인 원소는 kimbap과 kimchi 둘이고, 그 사이에 다른 원소가 끼어들 수 없다. 'kiwi'는 세 번째 글자 'w'가 'n'보다 뒤이므로 범위 밖이다. 반면 'kin'으로 끝나는 원소를 찾을 때는 11개를 모두 확인하고서야 pumpkin 하나를 찾았다. 자바의 String.compareTo는 UTF-16 코드 단위의 값으로 비교하므로 대소문자를 구분한다. MySQL의 utf8mb4_0900_ai_ci 정렬과 순서가 같지 않다는 점은 기억해 두자. 이 예제가 보여 주는 것은 "접두사는 정렬 순서의 한 구간"이라는 원리다.

    정렬된 인덱스 리프에서 접두사 패턴은 연속된 한 구간이 되지만, 와일드카드로 시작하는 패턴의 일치 항목은 여기저기 흩어져 있음을 보여 준다. 가로로 길게 늘어선 정렬된 칸 11개: "apple", "apricot", "banana", "cherry", "grape", "kimbap", "kimchi", "kiwi", "lemon", "mango", "pumpkin". 위쪽 줄 제목 "LIKE 'kim%'": "kimbap"과 "kimchi" 두 칸만 초록색으로 칠해지고 그 위에 꺾쇠 모양 괄호와 라벨 "'kim' 이상 'kin' 미만: 한 구간". 그 구간의 왼쪽 끝을 가리키는 화살표 라벨 "트리로 시작점 찾기". 아래쪽 줄 제목 "LIKE '%kin'": 같은 11칸이 다시 그려지고 모든 칸 위에 작은 돋보기 아이콘이 있으며, "pumpkin" 칸만 주황색. 라벨 "끝나는 글자로는 위치를 알 수 없음: 전부 확인". 흰 배경, 단순한 평면 스타일. 접두사가 정해진 LIKE는 정렬 순서의 한 구간이라 인덱스로 시작점을 찾을 수 있지만, 와일드카드로 시작하는 LIKE는 모든 항목을 확인해야 한다.

    앞이 열린 패턴이 꼭 필요할 때

    '%키보드%'처럼 단어가 문자열 중간 어디에나 있을 수 있는 검색이 핵심 기능이라면 B-tree 인덱스는 맞는 도구가 아니다. MySQL에는 전문 검색(full-text search)을 위한 FULLTEXT 인덱스가 따로 있고, 매뉴얼에 따르면 InnoDB는 FULLTEXT 인덱스에 역 리스트(inverted list)를 쓴다. 단어마다 그 단어가 나오는 문서 목록을 두는 구조라 원리가 전혀 다르다. 문자열의 끝부분으로 찾는 일이 잦다면 다른 방법도 있다. 문자열을 뒤집은 값을 생성 열(generated column)로 두고 거기에 인덱스를 만들면, 뒷부분 검색이 뒤집힌 문자열의 접두사 검색이 된다.

    ALTER TABLE item ADD COLUMN name_rev VARCHAR(50) AS (REVERSE(name)) VIRTUAL;
CREATE INDEX idx_item_name_rev ON item (name_rev);

-- '%-000008'을 찾는 대신, 뒤집은 값 '800000-'의 접두사로 찾는다
SELECT item_id, name FROM item WHERE name_rev LIKE '800000-%';

    '-000008'을 뒤집으면 '800000-'이므로, 이름이 '-000008'로 끝나는 행은 name_rev가 '800000-'으로 시작하는 행과 정확히 같다. 8.0.46에서 실행하면 결과는 item_id 8인 '무선 키보드-000008' 1행이고, EXPLAIN은 type = range, key = idx_item_name_rev, rows = 1이다. 대가는 인덱스 하나를 더 유지하는 비용이다. 어느 방법이든 "어떤 모양의 검색을 빠르게 하고 싶은가"에 맞춰 정렬 기준을 새로 만드는 것이다. 인덱스는 결국 특정한 질문에 답하기 좋은 순서로 데이터를 한 벌 더 정렬해 두는 일이다.

    인덱스와 정렬

    인덱스는 이미 정렬되어 있다. 그렇다면 ORDER BY가 요구하는 순서가 인덱스의 순서와 같을 때는 정렬을 따로 할 필요가 없다. 인덱스를 순서대로 읽기만 하면 결과가 정렬된 상태로 나온다. 매뉴얼(ORDER BY Optimization)은 MySQL이 ORDER BY를 인덱스로 만족시켜 filesort라는 추가 정렬 작업을 피할 수 있다고 설명한다.

    -- 가격이 가장 싼 상품 10개
EXPLAIN SELECT * FROM item ORDER BY price LIMIT 10;
-- idx_item_price를 앞에서부터 10개만 읽는다. Extra에 Using filesort가 없다

-- 재고가 가장 적은 상품 10개 (stock에는 인덱스가 없다)
EXPLAIN SELECT * FROM item ORDER BY stock LIMIT 10;
-- Extra: Using filesort
    -- ORDER BY price LIMIT 10
+----+-------------+-------+------------+-------+---------------+----------------+---------+------+------+----------+-------+
| id | select_type | table | partitions | type  | possible_keys | key            | key_len | ref  | rows | filtered | Extra |
+----+-------------+-------+------------+-------+---------------+----------------+---------+------+------+----------+-------+
|  1 | SIMPLE      | item  | NULL       | index | NULL          | idx_item_price | 4       | NULL |   10 |   100.00 | NULL  |
+----+-------------+-------+------------+-------+---------------+----------------+---------+------+------+----------+-------+

-- ORDER BY stock LIMIT 10
+----+-------------+-------+------------+------+---------------+------+---------+------+-------+----------+----------------+
| id | select_type | table | partitions | type | possible_keys | key  | key_len | ref  | rows  | filtered | Extra          |
+----+-------------+-------+------------+------+---------------+------+---------+------+-------+----------+----------------+
|  1 | SIMPLE      | item  | NULL       | ALL  | NULL          | NULL | NULL    | NULL | 99871 |   100.00 | Using filesort |
+----+-------------+-------+------------+------+---------------+------+---------+------+-------+----------+----------------+

    첫 쿼리의 type은 index, 곧 인덱스를 순서대로 훑는 방식이고 rows는 10이다. WHERE 조건이 없으니 possible_keys는 NULL이지만, 정렬을 위해 idx_item_price를 골랐다.

    첫 쿼리를 인덱스로 처리하면 엔진은 idx_item_price의 가장 왼쪽 리프에서 시작해 레코드를 10개만 읽고 멈춘다. 가장 싼 가격은 1,000원이고, 1,000원인 행은 n % 1000 = 0인 item_id 1000, 2000, …, 100000의 100행이다. 인덱스는 (price, item_id) 순서이므로 처음 10개는 item_id 1000, 2000, …, 10000이다. 이 10개의 기본 키로 클러스터형 인덱스를 10번 탐색하면 끝이다. 10만 행 가운데 10행만 건드린다. 8.0.46에서 실행한 결과도 item_id 1000, 2000, …, 10000의 10행이었고, 모두 가격 1,000원, 분류 도서, 재고 0이다.

    한 가지 주의할 점이 있다. 이 쿼리의 ORDER BY는 가격만 지정했다. 가격 1,000원인 행은 100개이고 그 가운데 어느 10개가 나올지는 SQL이 보장하지 않는다. 인덱스로 읽으면 item_id가 작은 순서로 나오겠지만, 다른 실행 계획이 선택되면 달라질 수 있다. 결과가 매번 같아야 한다면(페이지 나누기처럼) ORDER BY price, item_id처럼 순서를 완전히 정하는 열까지 적는다.

    둘째 쿼리는 stock에 인덱스가 없으므로 정렬된 순서를 얻을 곳이 없다. 엔진은 행을 읽어 정렬하는 filesort를 한다. 매뉴얼은 EXPLAIN의 Extra에 Using filesort가 있으면 인덱스가 쓰이지 않고 filesort가 수행된 것이고, 없으면 인덱스로 정렬을 대신한 것이라고 설명한다. 이름과 달리 filesort가 반드시 디스크 파일을 쓰는 것은 아니다. 매뉴얼은 ORDER BY 인덱스_없는_열 LIMIT N 형태를 옵티마이저가 임시 파일 없이 메모리에서 효율적으로 처리할 수 있다고 적는다. 정렬할 데이터가 정렬 버퍼(sort_buffer_size)를 넘으면 그때 임시 파일과 병합 단계가 생긴다. 그래도 10행을 얻으려고 10만 행을 모두 읽어야 한다는 사실은 변하지 않는다.

    정렬에 인덱스를 쓰는 것이 손해일 때

    LIMIT이 없으면 어떻게 될까? SELECT * FROM item ORDER BY price;는 10만 행 전체를 가격순으로 원한다. 인덱스 순서로 읽으면 정렬은 필요 없지만 보조 인덱스 레코드 10만 개마다 클러스터형 인덱스를 다시 탐색해야 한다. 앞에서 본 흩어진 읽기 10만 번이다. 매뉴얼은 이런 경우 전체 인덱스를 훑으며 인덱스에 없는 열을 찾으려고 테이블 행을 조회하는 것이, 테이블을 훑고 결과를 정렬하는 것보다 비쌀 수 있고, 그러면 옵티마이저는 아마 인덱스를 쓰지 않을 것이라고 설명한다. 8.0.46에서 이 쿼리를 EXPLAIN하면 실제로 type = ALL, Extra = Using filesort다. 같은 매뉴얼은 SELECT가 인덱스에 있는 열만 고른다면 인덱스가 쓰이고 정렬을 피한다고 덧붙인다. 행을 다시 찾아갈 필요가 없기 때문이다. SELECT price FROM item ORDER BY price;를 EXPLAIN하면 type = index, key = idx_item_price, Extra = Using index로 filesort가 사라진다. 이것이 06회에서 다룰 커버링 인덱스의 출발점이다.

    내림차순과 MIN, MAX

    ORDER BY price DESC LIMIT 10은 오름차순 인덱스를 거꾸로 읽으면 된다. 앞에서 본 대로 InnoDB의 같은 레벨 페이지는 앞뒤로 연결되어 있으므로 가장 오른쪽 리프에서 왼쪽으로 걸어갈 수 있다. 8.0.46에서 EXPLAIN SELECT * FROM item ORDER BY price DESC LIMIT 10;을 실행하면 type = index, key = idx_item_price이고 Extra에 Backward index scan, 곧 인덱스를 거꾸로 훑는다는 표시가 나온다. MySQL 8.0은 여기에 더해 내림차순 인덱스(descending index)를 지원한다. 매뉴얼에 따르면 인덱스 정의의 DESC는 이제 무시되지 않고 키 값을 내림차순으로 저장하게 하며, 예전에는 인덱스를 역순으로 훑을 수는 있었지만 성능 손실이 있었고 내림차순 인덱스는 정방향으로 훑을 수 있어 더 효율적이라고 설명한다. 매뉴얼은 내림차순 인덱스의 또 다른 쓰임으로, 가장 효율적인 읽기 순서가 어떤 열은 오름차순이고 어떤 열은 내림차순인 경우에도 옵티마이저가 여러 열 인덱스를 쓸 수 있게 해 준다는 점을 든다. 그것은 06회의 복합 인덱스에서 다룬다.

    정렬된 구조의 또 다른 선물은 최솟값과 최댓값이다. SELECT MIN(price), MAX(price) FROM item;에서 가장 작은 값은 인덱스의 가장 왼쪽 끝, 가장 큰 값은 가장 오른쪽 끝에 있다. 매뉴얼은 이런 경우 MySQL이 MIN()이나 MAX() 식마다 키 탐색을 한 번 하고 그 결과를 상수로 바꾼다고 설명한다. 결과는 1,000과 100,900이다. 8.0.46에서 이 쿼리를 EXPLAIN하면 table과 type이 NULL이고 Extra에 Select tables optimized away가 나온다. 실행 계획을 세우는 단계에서 이미 값을 구했으므로 실행할 때 읽을 테이블이 남지 않았다는 뜻이다. 10만 행을 읽지 않고 트리 양 끝으로 한 번씩 내려가면 끝난다. 매뉴얼은 GROUP BY도 사용 가능한 인덱스의 순서를 따를 때 인덱스로 처리할 수 있다고 적는다. 같은 값끼리 이미 붙어 있으니 묶기 위해 따로 정렬할 필요가 없기 때문이다.

    ORDER BY가 없으면 순서도 없다

    인덱스와 정렬의 관계에서 거꾸로 생기는 오해가 있다. "InnoDB 테이블은 기본 키 순서로 저장되니 ORDER BY 없이 조회해도 기본 키 순서로 나온다"는 생각이다. 전체 스캔이라면 그렇게 보이는 경우가 많다. 하지만 SELECT * FROM item WHERE price BETWEEN 10000 AND 10900;을 idx_item_price로 처리하면 결과는 앞의 그림처럼 item_id 90, 1090, 2090, …의 순서, 곧 인덱스의 순서로 나온다. 8.0.46에서 이 쿼리(EXPLAIN은 range, idx_item_price)에 LIMIT 5를 붙여 실행하면 item_id 90, 1090, 2090, 3090, 4090이 나온다. 같은 쿼리라도 옵티마이저가 전체 스캔을 고르면 기본 키 순서로 나온다. 결과의 순서는 접근 경로의 부산물일 뿐이고 SQL은 ORDER BY 없는 결과의 순서를 약속하지 않는다. 데이터가 늘어 실행 계획이 바뀌는 날, 순서에 기대던 화면은 소리 없이 틀린다.

    ORDER BY price LIMIT 10이 인덱스 앞쪽 10개만 읽고 끝나는 경우와, 인덱스가 없는 열로 정렬할 때 모든 행을 읽어 정렬 버퍼에서 정렬하는 경우를 대비한다. 위아래 두 단으로 나뉜 도식. 위 단 제목 "ORDER BY price LIMIT 10 (인덱스 있음)". 왼쪽에서 오른쪽으로 정렬된 리프 칸들이 길게 늘어서 있고 첫 칸에 "1000", 끝 칸에 "100900" 라벨. 왼쪽 끝의 칸 10개만 초록색으로 칠해지고 그 아래에 "10개 읽고 멈춤", 오른쪽 나머지 칸은 연한 회색. 아래 단 제목 "ORDER BY stock LIMIT 10 (인덱스 없음)". 왼쪽에 행 상자들이 뒤섞인 순서로 쌓인 "테이블 전체 10만 행"이 있고, 모든 상자에서 화살표가 가운데의 깔때기 모양 "정렬 버퍼 (filesort)"로 들어간다. 깔때기 오른쪽으로 상자 10개가 나오며 "상위 10개". 아래 단 모서리에 작은 라벨 "EXPLAIN Extra: Using filesort". 흰 배경, 초록과 주황 강조색. 정렬 기준이 인덱스 순서와 같으면 인덱스를 앞에서부터 필요한 만큼만 읽는다. 인덱스가 없으면 모든 행을 읽어 정렬해야 한다.

    흔한 오해와 바로잡기

    "인덱스를 만들면 그 열을 쓰는 쿼리는 빨라진다." 열에 인덱스가 있다는 것은 "그 열의 값으로 정렬된 구조가 있다"는 뜻일 뿐이다. 조건이 그 정렬을 이용할 수 있는 모양이어야 한다. 열을 함수나 연산으로 감싼 조건, 문자열 열을 숫자와 비교하는 조건, 와일드카드로 시작하는 LIKE는 정렬된 구간을 정할 수 없어서 인덱스로 범위를 좁히지 못한다. 모양이 맞더라도 조건이 고르는 행이 많으면 보조 인덱스를 거쳐 행을 하나씩 다시 찾는 비용이 전체 스캔보다 커진다.

    "인덱스가 있으면 옵티마이저는 반드시 쓴다." MySQL 옵티마이저는 쓸 수 있는 접근 방법들의 비용을 추정해 고른다. 매뉴얼은 인덱스가 있어도 테이블 행의 매우 큰 비율에 접근해야 한다고 추정되면 인덱스를 쓰지 않을 수 있다고 명시한다. 반대로 같은 조건이라도 LIMIT이 붙으면 인덱스를 쓸 수 있다. "인덱스를 만들었는데 왜 안 쓰지?"라는 질문의 답은 대개 선택도와 결과 행 수에 있다. 확인 수단은 언제나 EXPLAIN이다.

    "EXPLAIN의 rows는 읽을 행의 정확한 수다." 매뉴얼은 rows 열이 쿼리를 실행하려고 MySQL이 검사해야 한다고 믿는 행 수이며, InnoDB 테이블에서는 추정치라 항상 정확하지는 않다고 설명한다. SHOW INDEX의 Cardinality도 추정치다. 대량으로 데이터를 넣거나 지운 뒤 계획이 이상하다면 ANALYZE TABLE로 통계를 새로 모으는 것이 먼저다.

    "B-Tree의 B는 Binary다." 매뉴얼 용어집이 직접 바로잡는다. B-tree 노드는 자식을 많이 가질 수 있으므로 자식이 둘로 제한된 이진 트리와 같지 않다. 데이터베이스 인덱스가 이진 트리를 쓰지 않는 이유가 바로 이 회차의 트리 절이다. 페이지 하나를 읽을 때 키 하나가 아니라 수백 개를 얻어야 높이가 낮아진다.

    "보조 인덱스는 행의 주소를 가리킨다." InnoDB에서는 아니다. 보조 인덱스 레코드는 인덱스 열 값과 기본 키 값을 담고, 행을 얻으려면 기본 키로 클러스터형 인덱스를 다시 탐색한다. 그래서 보조 인덱스로 많은 행을 꺼내는 쿼리는 행마다 트리 탐색이 한 번씩 더 붙고, 기본 키가 길면 모든 보조 인덱스가 함께 커진다.

    다른 주제와의 연결

    01회의 인덱스 중첩 루프 조인을 다시 보자. 바깥 테이블의 행마다 안쪽 테이블에서 짝을 찾을 때 EXPLAIN에 나오던 eq_ref와 ref는 이 회차의 동등 검색을 조인의 행마다 반복하는 것이다. 안쪽 조인 열이 기본 키나 UNIQUE NOT NULL 인덱스면 짝이 하나뿐이라 eq_ref, 일반 인덱스면 ref다. 조인 열에 인덱스가 없으면 안쪽을 매번 전부 훑거나 해시 조인을 써야 한다. 조인 성능은 결국 이 회차의 동등 검색 비용에 바깥 행 수를 곱한 것이다. 03회의 서브쿼리도, 상관 서브쿼리가 바깥 행마다 안쪽 쿼리를 실행할 때 안쪽 조건에 인덱스가 있느냐가 같은 방식으로 비용을 정한다.

    06회는 이 회차의 단일 열 인덱스를 넓힌다. 옵티마이저가 여러 인덱스 가운데 무엇을 고르는지, 쿼리가 필요한 열이 모두 인덱스에 있어 클러스터형 인덱스를 다시 찾지 않아도 되는 커버링 인덱스, 여러 열을 묶은 복합 인덱스와 왼쪽부터 쓰이는 규칙, 인덱스를 어떻게 설계하고 무엇을 감수해야 하는지가 그 내용이다. 이 회차에서 "단일 열 인덱스로는 할 수 없다"고 남겨 둔 WHERE category = '가전' ORDER BY price 같은 쿼리가 거기서 풀린다. 08회의 트랜잭션에서도 인덱스는 다시 등장한다. InnoDB의 행 잠금은 인덱스 레코드에 걸리므로, 어떤 인덱스로 행을 찾았는지가 잠금의 범위에 영향을 준다.

    정리: 인덱스는 질문에 맞춰 한 벌 더 정렬해 둔 데이터다

    인덱스가 없으면 엔진은 원하는 행을 찾으려고 모든 페이지의 모든 행을 확인한다. 찾았다고 멈출 수도 없다. 같은 값이 더 있을지 모르기 때문이다. 인덱스는 이 문제를 "미리 정렬해 둔다"로 푼다. 정렬된 데이터에서는 시작점을 로그 시간에 찾을 수 있고, 시작점을 찾으면 같은 값과 이어지는 범위가 바로 옆에 붙어 있다.

    정렬된 구조를 디스크 위에 바뀌는 데이터로 유지하려면 B+Tree가 필요하다. 노드 하나를 페이지 하나로 두고 그 안에 키를 수백 개 담아 팬아웃을 크게 하면, 수천만 행도 높이 3~4의 트리로 담을 수 있다. 레코드는 리프에만 두고 리프를 앞뒤로 연결해 두면 범위와 정렬을 옆으로 걸으며 처리할 수 있다. InnoDB에서는 테이블 자체가 기본 키로 정렬된 이런 트리, 곧 클러스터형 인덱스이고, 보조 인덱스는 (인덱스 열, 기본 키)를 담는 또 하나의 트리다.

    쿼리의 조건이 정렬된 구간 하나로 표현될 수 있을 때 인덱스가 쓰인다. 동등 비교는 길이가 0인 구간, BETWEEN과 부등호는 양 끝이 정해진 구간, 접두사 LIKE는 접두사로 정해지는 구간, ORDER BY는 구간 전체를 순서대로 읽는 일이다. 구간을 정할 수 없는 조건(가공된 열, 형 변환, 앞이 열린 패턴)은 인덱스를 쓰지 못하고, 구간이 너무 넓으면 보조 인덱스에서 행을 다시 찾는 비용 때문에 쓰지 않는 편이 낫다.

    이 장의 핵심

    인덱스는 특정 열의 값 순서로 데이터를 한 벌 더 정렬해 둔 B+Tree이고, 그 가치는 "조건을 정렬된 한 구간으로 바꿀 수 있는가"와 "그 구간이 얼마나 좁은가"로 정해진다. InnoDB 보조 인덱스는 행 대신 기본 키를 돌려주므로, 결과 행이 많을수록 클러스터형 인덱스를 다시 찾는 비용이 커진다. 인덱스를 썼는지, 어떤 방식으로 썼는지는 EXPLAIN의 type, key, Extra로 확인한다.
    인덱스가 필요한 이유
    인덱스가 없으면 엔진은 클러스터형 인덱스의 모든 리프 페이지를 읽으며 모든 행을 평가하고, 일치하는 행을 찾아도 같은 값이 더 있을 수 있어 멈추지 못한다. 일의 양이 테이블 크기에 비례한다.
    인덱스
    검색 기준 열의 값과 행을 다시 찾아갈 정보를 짝지어 값의 순서로 정렬해 둔 별도 구조다. 조건을 정렬된 한 구간으로 바꿀 수 있을 때 그 구간만 읽게 해 준다.
    클러스터형 인덱스와 보조 인덱스
    InnoDB 테이블은 기본 키 순서로 행 전체를 리프에 담은 B-tree(클러스터형 인덱스)다. 보조 인덱스 레코드는 인덱스 열과 기본 키 값을 담으므로, 행 전체를 얻으려면 클러스터형 인덱스를 한 번 더 탐색한다.
    B+Tree와 팬아웃
    노드 하나를 16KB 페이지 하나로 두고 키를 수백 개 담아 높이를 log_f N으로 낮춘다. 레코드는 리프에만 있고 같은 레벨 페이지는 앞뒤로 연결되어 범위와 정렬을 옆으로 걸으며 처리한다.
    인덱스 생성·조회·삭제
    CREATE INDEX 또는 ALTER TABLE ADD INDEX로 만들고 SHOW INDEX로 확인하며 DROP INDEX로 지운다. InnoDB는 정렬 인덱스 빌드로 한꺼번에 쌓고, 보조 인덱스 생성 중에도 DML을 허용한다. 8.0의 INVISIBLE로 지우기 전에 효과를 시험할 수 있다.
    동등 비교
    유일하지 않은 인덱스는 ref, 기본 키나 UNIQUE 인덱스 전체를 상수와 비교하면 const다. 열을 함수나 연산으로 감싸거나 문자열 열을 숫자와 비교하면 인덱스로 값을 찾지 못한다.
    범위 검색과 선택도
    시작 키까지 내려간 뒤 리프를 옆으로 걷는다(range). 보조 인덱스에서는 결과 행마다 기본 키로 흩어진 탐색이 붙으므로, 고르는 행이 많으면 옵티마이저가 전체 스캔을 택할 수 있다. LIMIT이 있으면 다시 인덱스가 유리해진다.
    LIKE
    와일드카드로 시작하지 않는 상수 패턴은 접두사로 정해지는 구간이 되어 인덱스를 쓴다. 앞이 열린 패턴과 상수가 아닌 패턴은 쓸 수 없다. 범위의 경계는 열의 콜레이션 규칙을 따른다.
    정렬
    ORDER BY가 인덱스 순서와 같으면 정렬 없이 인덱스를 읽고, 그렇지 않으면 filesort(Extra: Using filesort)를 한다. LIMIT 없이 SELECT *를 정렬하면 인덱스 순서 읽기가 오히려 비쌀 수 있다. ORDER BY가 없으면 결과 순서는 보장되지 않는다.

    "어제까지 빠르던 쿼리가 오늘 느리다"는 보고를 받으면 먼저 EXPLAIN의 type과 key를 본다. 큰 테이블에 ALL과 key = NULL이 보인다면 쓸 인덱스가 없거나, 있는데도 조건의 모양 때문에 쓰지 못하는 것이다. 인덱스가 분명히 있는데 쓰이지 않는다면 조건절을 다시 읽는다. 열을 감싼 함수(DATE(), LEFT(), LOWER()), 문자열 열에 따옴표 없이 넘긴 숫자, ORM이나 애플리케이션 코드가 자동으로 붙인 형 변환, 앞에 %가 붙은 LIKE가 흔한 원인이다. 대부분은 열을 맨몸으로 두고 가공을 상수 쪽으로 옮기면 풀린다. 상수 쪽으로 옮길 수 없는 가공이라면 함수 기반 인덱스나 생성 열을 검토한다.

    반대로 인덱스를 타는데도 느린 경우가 있다. EXPLAIN에서 range나 ref가 보이지만 결과 행이 수만 건이라면, 보조 인덱스에서 행마다 클러스터형 인덱스를 다시 찾는 흩어진 읽기가 비용의 대부분이다. 이때 판단은 조건에 따라 갈린다. 화면에 보여 줄 몇십 행만 필요하다면 LIMIT과 ORDER BY를 인덱스 순서에 맞춰 시작점부터 조금만 읽게 하는 것이 답이다. 리포트처럼 대부분의 행이 필요하다면 오히려 전체 스캔이 정상적인 계획이며, 인덱스를 억지로 쓰게 하는 힌트는 상황을 나쁘게 만들 수 있다. 결과 행이 많은 쿼리의 근본 대책인 커버링 인덱스와 복합 인덱스는 06회에서 다룬다.

    인덱스를 추가하는 결정에도 이 회차의 원리가 그대로 쓰인다. 값의 종류가 몇 개뿐인 열(상태 코드, 성별, 분류)에 단독 인덱스를 만들면 한 값이 테이블의 큰 비율을 차지하므로 옵티마이저가 쓰지 않을 가능성이 높고, 쓰지 않는 인덱스도 쓰기 비용과 공간은 계속 낸다. 운영 중인 테이블에서 인덱스를 지우고 싶다면 바로 DROP하지 말고 INVISIBLE로 숨긴 채 한동안 지켜보는 편이 안전하다. 인덱스를 만들 때는 InnoDB가 동시 DML을 허용하더라도 오래 열린 트랜잭션이 있으면 CREATE INDEX가 끝나지 않는다는 점을 기억하고, 배치 작업이나 긴 트랜잭션이 없는 시간을 고른다.

    3. (가) 보조 인덱스를 내려가는 데 3페이지, 다음 리프를 확인하는 데 1페이지를 읽는다. 그리고 레코드 100개 각각의 기본 키(490, 1490, …, 99490)로 클러스터형 인덱스를 3페이지씩 내려가므로 300페이지다. 모두 304페이지다. (나) 클러스터형 인덱스를 3페이지 내려가면 item_id 1이 든 리프에 도착하고, 그 리프에 100행이 모두 있으며, 끝을 확인하려고 다음 리프를 1페이지 더 읽는다. 모두 4페이지이고 두 번째 탐색은 없다. 결과 행 수는 같지만 보조 인덱스 쪽은 행마다 기본 키 탐색이 붙어 방문 페이지가 76배다. 실제로는 루트와 상위 페이지가 버퍼 풀에 남아 있어 디스크 입출력은 이보다 적지만, 트리 하강의 횟수 차이는 그대로다.

    4. 쿼리에 ORDER BY가 없으므로 결과의 순서가 정해져 있지 않다. 옵티마이저가 idx_item_price를 쓰면 (price, item_id) 순서로, 전체 스캔을 쓰면 item_id 순서로 행이 나온다. 데이터 분포나 통계가 바뀌어 실행 계획이 달라지거나, 두 페이지를 조회하는 사이에 계획이 다르게 선택되면 OFFSET 20이 건너뛰는 "앞의 20행"이 첫 페이지의 20행과 같지 않게 된다. 그래서 중복이나 누락이 생긴다. 고친 쿼리는 ... WHERE price BETWEEN 10000 AND 10900 ORDER BY price, item_id LIMIT 20 OFFSET 20이다. item_id까지 넣어야 가격이 같은 100행 사이의 순서도 정해진다. InnoDB 보조 인덱스는 내부적으로 기본 키를 덧붙인 (price, item_id) 순서로 정렬되어 있으므로, 이 인덱스를 범위로 읽으면 그 순서가 곧 ORDER BY의 순서다. 인덱스로 정렬을 대신할 수 있는 모양이고, 실제로 그렇게 되었는지는 EXPLAIN의 Extra에 Using filesort가 없는지로 확인한다. MySQL 8.0.46에서 고친 쿼리를 EXPLAIN하면 type = range, key = idx_item_price, Extra = Using index condition으로 Using filesort가 없고, 실행 결과는 가격 10,000원인 item_id 20090, 21090, …, 39090의 20행이다.

     MySQL 8.0 InnoDB에서 price 열에 만든 보조 인덱스의 리프 레코드에 들어 있는 것은? price 값과 그 행이 저장된 페이지 번호·슬롯 번호(물리 주소) price 값과 행 전체의 복사본 price 값과 그 행의 기본 키 값 price 값만. 행을 찾으려면 테이블을 처음부터 다시 훑는다 매뉴얼에 따르면 InnoDB 보조 인덱스의 각 레코드는 인덱스로 지정한 열과 그 행의 기본 키 열을 담고, 이 기본 키로 클러스터형 인덱스에서 행을 찾는다. 물리 주소를 담지 않으므로 행이 다른 페이지로 옮겨 가도 보조 인덱스를 고칠 필요가 없지만, 행 전체를 얻으려면 트리 탐색이 한 번 더 필요하다. 행 전체를 담는 것은 클러스터형 인덱스뿐이다. name 열에 일반 B-tree 인덱스가 있을 때, 인덱스로 읽을 범위를 좁힐 수 있는 조건은? WHERE LEFT(name, 2) = '무선' WHERE name LIKE '무선 키보드-0000%' WHERE name LIKE '%키보드-000008' WHERE name LIKE other_name (other_name은 같은 테이블의 다른 열) 와일드카드로 시작하지 않는 상수 패턴만 접두사로 정해지는 정렬 구간이 된다. LEFT로 열을 감싼 조건은 키 부분과 상수의 비교가 아니므로 범위를 정하지 못하고(8.0.13부터는 같은 식으로 함수 기반 인덱스를 만들면 가능하다), 앞이 %인 패턴은 일치하는 값이 정렬 순서의 어디에나 있을 수 있으며, 다른 열과의 LIKE는 패턴이 상수가 아니다. 데이터베이스 인덱스가 균형 이진 탐색 트리 대신 B+Tree를 쓰는 가장 근본적인 이유는? 이진 트리는 정렬 순서를 유지하지 못해서 범위 검색을 할 수 없기 때문이다 B+Tree는 비교 횟수가 이진 트리보다 항상 적기 때문이다 이진 트리는 오름차순으로 키가 들어오면 반드시 한쪽으로 기울기 때문이다 노드 하나를 페이지 하나에 두고 키를 수백 개 담으면 트리가 낮아져, 탐색할 때 읽는 페이지 수가 크게 줄기 때문이다 디스크 기반 데이터베이스에서 비용을 정하는 것은 비교 횟수보다 새로 읽는 페이지 수다. 균형 이진 트리는 2,500만 키에서 높이가 25 안팎이지만, 팬아웃이 수백인 B+Tree는 3~4다. 이진 탐색 트리도 정렬 순서를 유지하므로 첫 보기는 틀렸고, 비교 횟수는 노드 안의 이진 탐색까지 합하면 비슷한 로그 규모라 둘째 보기도 아니다. 오름차순 삽입으로 기우는 문제는 균형 이진 트리가 이미 해결한다. item 테이블(10만 행)에 idx_item_price가 있는데 SELECT * FROM item WHERE price >= 2000의 EXPLAIN에 type = ALL이 나왔다. 가장 적절한 해석은? 조건이 약 99%의 행을 고르므로 보조 인덱스에서 행마다 클러스터형 인덱스를 다시 찾는 비용이 순차적인 전체 스캔보다 크다고 옵티마이저가 추정했다 >=는 B-tree 인덱스가 지원하지 않는 연산자라서 인덱스를 쓸 수 없다 INT 열에는 인덱스를 범위로 쓸 수 없고 동등 비교만 가능하다 인덱스가 손상되었으므로 즉시 DROP하고 다시 만들어야 한다 매뉴얼은 B-tree 인덱스가 >, >=, <, <=, BETWEEN에 쓰일 수 있다고 명시하므로 둘째와 셋째 보기는 틀렸다. 문법적으로 쓸 수 있어도, 옵티마이저는 인덱스를 쓰면 테이블의 매우 큰 비율에 접근해야 한다고 추정하면 테이블 스캔을 고를 수 있다. 같은 조건에 LIMIT 10을 붙이면 인덱스가 다시 유리해진다. SELECT * FROM item ORDER BY price LIMIT 10의 EXPLAIN에서 Extra에 Using filesort가 없고 key가 idx_item_price였다. 이것이 뜻하는 것은? 결과가 정렬되지 않은 채로 반환된다 정렬은 했지만 디스크 대신 메모리에서 했다 인덱스를 가격 순서대로 앞에서부터 읽어 정렬 단계 없이 결과를 얻었다 LIMIT 때문에 ORDER BY가 무시되었다 매뉴얼은 Extra에 Using filesort가 없으면 인덱스가 쓰이고 filesort가 수행되지 않은 것이라고 설명한다. 인덱스는 이미 가격 순서로 정렬되어 있으므로 가장 왼쪽 리프부터 10개를 읽으면 그것이 정렬된 결과다. 메모리에서 정렬한 경우도 filesort이므로 Using filesort가 표시된다. ORDER BY는 무시되지 않았고, 인덱스 순서 덕분에 따로 할 일이 없었을 뿐이다.
    인덱스(index)
    검색 기준 열의 값과 행을 다시 찾아갈 정보를 값의 순서로 정렬해 둔 별도의 자료 구조. MySQL의 대부분 인덱스는 B-tree에 저장된다.
    클러스터형 인덱스(clustered index)
    InnoDB에서 행 데이터 전체를 기본 키 순서로 리프에 담은 인덱스. 테이블당 하나이며, 기본 키가 없으면 NOT NULL 유일 인덱스나 숨은 GEN_CLUST_INDEX가 그 역할을 한다.
    보조 인덱스(secondary index)
    클러스터형 인덱스가 아닌 인덱스. InnoDB에서는 레코드마다 인덱스 열 값과 기본 키 값을 담고, 기본 키로 클러스터형 인덱스에서 행을 찾는다.
    B+Tree
    레코드를 리프 노드에만 두고 위쪽 노드에는 구분 키와 자식 포인터만 두며, 리프를 키 순서로 연결한 B-Tree의 변형. 높이가 낮고 범위 검색에 유리하다.
    페이지(page)
    InnoDB가 데이터를 저장하고 읽는 단위. 기본 크기는 16KB이며 innodb_page_size로 인스턴스 초기화 때 정한다. B+Tree의 노드 하나가 페이지 하나다.
    팬아웃(fan-out)
    트리 노드 하나가 가리키는 자식의 수. 클수록 같은 데이터를 더 낮은 트리에 담을 수 있다.
    전체 테이블 스캔(full table scan)
    테이블의 모든 행을 처음부터 끝까지 읽으며 조건을 평가하는 접근 방식. EXPLAIN의 type에 ALL로 표시된다.
    선택도(selectivity)
    조건이 전체 행 가운데 얼마나 적은 비율을 고르는지의 정도. 고르는 비율이 작을수록 선택도가 높고 인덱스의 이득이 크다.
    filesort
    인덱스로 ORDER BY를 만족시킬 수 없을 때 행을 읽어 따로 정렬하는 MySQL의 추가 정렬 단계. 정렬 버퍼에 다 들어가면 메모리에서 끝나며, EXPLAIN의 Extra에 Using filesort로 표시된다.
