    이 회차의 질문: 코드를 데이터 옆에 둘 것인가

    지금까지 다룬 SQL은 모두 한 문장짜리 질문이었다. 조인으로 테이블을 엮고, 서브쿼리로 답을 단계적으로 구하고, 인덱스로 찾는 속도를 올리고, 제약 조건으로 잘못된 값을 막고, 트랜잭션으로 여러 문장을 하나의 작업 단위로 묶었다. 그런데 실제 업무는 순서와 분기가 있는 절차다. 주문 한 건을 받는다고 해 보자. 상품의 재고를 읽고, 재고가 모자라면 거절하고, 충분하면 재고를 줄이고, 주문 행을 넣고, 재고가 바뀐 이력을 남긴다. 이 절차에는 "만약 ~이면"이라는 판단과 "그다음에"라는 순서가 있고, SQL 한 문장으로는 이것을 자연스럽게 표현하기 어렵다.

    보통 이 절차는 애플리케이션이 맡는다. 자바 코드가 JDBC로 SELECT를 보내 재고를 받고, 자바의 if 문으로 판단한 뒤, 다시 UPDATE와 INSERT를 보낸다. 판단은 애플리케이션 서버에서, 데이터 처리는 DB 서버에서 일어나고, 둘 사이를 네트워크가 잇는다. 다른 선택지도 있다. 절차 자체를 DB 서버 안에 저장해 두고 이름으로 부르는 것이다. MySQL은 이런 코드를 저장 프로그램(stored program)이라 부르고, 저장 프로시저(stored procedure), 저장 함수(stored function), 트리거(trigger), 이벤트(event) 네 가지를 둔다. 이벤트는 정해진 시각에 실행되는 예약 작업이라 이 회차에서는 다루지 않고, 앞의 세 가지에 집중한다.

    이 회차는 세 가지 질문을 따라간다. 첫째, 세 가지 저장 프로그램을 어떻게 만들고 부르며, 서로 무엇이 다른가. 둘째, MySQL 서버는 저장 프로그램을 어디에 보관하고 어떤 형태로 실행하며, 그 실행이 트랜잭션·잠금·바이너리 로그와 어떻게 엮이는가. 셋째, 많은 팀이 업무 로직을 DB 안에 두기를 꺼리는 이유는 무엇이고, 같은 요구를 무엇으로 대신하는가. 앞의 두 질문에 제대로 답하고 나면 세 번째 질문의 답은 취향이 아니라 근거를 가진 판단이 된다.

    범위를 분명히 해 둔다. 이 회차의 문법과 동작은 모두 MySQL 8.0, InnoDB 저장 엔진 기준이다. 저장 프로그램의 언어는 DBMS마다 크게 다르다. 오라클은 PL/SQL, SQL Server는 T-SQL, PostgreSQL은 PL/pgSQL이라는 각자의 절차 언어를 쓰며, 같은 일을 하는 코드라도 다른 DBMS로 그대로 옮겨지지 않는다. 이 이식성 문제 자체가 뒤에서 다룰 함정 가운데 하나다.

    세 가지 저장 프로그램 한눈에 보기

SELECT name, f(price) FROM product를 실행하는 도중에 f가 COMMIT을 해 버리면, 바깥 SELECT가 속한 트랜잭션이 문장 중간에서 끝나 버린다. f가 결과 집합을 돌려주면 그 결과가 바깥 SELECT의 결과와 섞일 자리가 없다. 그래서 MySQL은 함수와 트리거 안에서 명시적·암묵적으로 커밋하거나 롤백하는 문장과 결과 집합을 돌려주는 문장을 금지한다. 프로시저는 CALL이라는 독립된 문장으로 실행되므로 이런 제약이 훨씬 적다. 단, 함수나 트리거 안에서 호출된 프로시저는 함수와 같은 제약을 받는다.

    일상에서 가져온 비유전화로 하나씩 지시하기와 레시피 카드 맡기기

    애플리케이션이 SQL을 한 문장씩 보내는 것은 멀리 있는 주방에 전화를 걸어 "냉장고에 계란이 몇 개 있나요?", "그럼 두 개 꺼내세요", "장부에 적어 두세요"라고 하나씩 지시하는 것과 같다. 지시마다 통화가 한 번씩 오간다. 저장 프로시저는 레시피 카드를 주방에 미리 맡겨 두고 "3번 레시피, 두 인분"이라고 한 번만 말하는 것이다. 트리거는 주방 벽에 붙은 규칙, 예를 들어 "계란을 꺼낼 때마다 재고 장부에 적는다"에 가깝다. 누가 계란을 꺼내든 규칙이 따라 실행된다. 비유가 깨지는 지점도 있다. 레시피가 주방에 있으면 요리사(DB 서버)가 그 일을 모두 떠맡으므로, 주방이 하나뿐인 식당에서는 레시피가 늘수록 주방이 붐빈다. 그리고 벽에 붙은 규칙은 전화로 지시하는 사람 눈에는 보이지 않는다. 이 두 가지가 뒤에서 다룰 함정의 씨앗이다.

    저장 프로시저 1: 만들고, 부르고, 값을 주고받기

    가장 단순한 프로시저부터 만든다. 기준 가격 이상인 상품의 개수를 세어 OUT 매개변수로 돌려준다.

    DELIMITER //

CREATE PROCEDURE product_count_over(IN min_price INT, OUT cnt INT)
BEGIN
  SELECT COUNT(*) INTO cnt
    FROM product
   WHERE price >= min_price;
END //

DELIMITER ;

CALL product_count_over(30000, @cnt);
SELECT @cnt;   -- 2 (키보드 50000, 모니터 300000)

    첫 줄의 DELIMITER //부터 짚어야 한다. mysql 명령줄 클라이언트는 입력을 읽다가 ;를 만나면 그때까지의 텍스트를 문장 하나로 보고 서버에 보낸다. 그런데 프로시저 본문 안에도 ;가 있다. 구분자를 그대로 두면 클라이언트는 WHERE price >= min_price;에서 문장이 끝났다고 판단해 본문이 잘린 CREATE PROCEDURE를 서버로 보내고, 서버는 문법 오류를 낸다. DELIMITER //는 클라이언트의 구분자를 //로 바꿔 END //까지를 한 덩어리로 보내게 한다. 마지막의 DELIMITER ;는 구분자를 원래대로 되돌린다.

    여기서 중요한 사실은 DELIMITER가 SQL 문이 아니라 mysql 클라이언트의 명령이라는 점이다. MySQL 매뉴얼도 이 명령이 본문 안의 ;를 mysql 클라이언트가 해석하지 않고 서버로 그대로 넘기게 하려고 쓰는 것이라고 설명한다. 서버는 DELIMITER라는 단어를 받지 않는다. 그래서 자바에서 JDBC로 CREATE PROCEDURE를 실행할 때는 문자열 전체가 문장 하나로 전달되므로 DELIMITER가 필요 없고, 문자열에 DELIMITER를 넣으면 오히려 서버가 모르는 문법이 된다. 본문에 ;가 없는 짧은 함수라면 mysql 클라이언트에서도 DELIMITER를 바꿀 필요가 없다.

    본문의 SELECT ... INTO cnt는 결과를 클라이언트로 보내지 않고 변수에 담는다. 호출하는 쪽의 @cnt는 사용자 정의 변수(user-defined variable)로, 연결(세션)이 살아 있는 동안만 존재하고 다른 세션에서는 보이지 않는다. CALL이 끝나면 프로시저의 OUT 매개변수 cnt에 담긴 값이 @cnt로 복사되고, 다음 SELECT가 그것을 읽는다. 가격이 30000 이상인 상품은 키보드와 모니터이므로 결과는 2다.

    IN, OUT, INOUT은 복사가 일어나는 시점이 다르다

    세 가지 매개변수 모드의 차이는 "값이 언제 복사되는가"로 정리된다. 다음 프로시저로 세 모드를 한 번에 비교해 보자.

    DELIMITER //

CREATE PROCEDURE param_demo(IN a INT, OUT b INT, INOUT c INT)
BEGIN
  SELECT a, b, c;                  -- 들어온 직후의 값
  SET a = a + 1, b = 100, c = c * 2;
END //

DELIMITER ;

SET @a = 1, @b = 5, @c = 10;
CALL param_demo(@a, @b, @c);
SELECT @a, @b, @c;
    -- CALL이 돌려준 결과 집합 (프로시저 안의 SELECT)
+------+------+------+
| a    | b    | c    |
+------+------+------+
|    1 | NULL |   10 |
+------+------+------+

-- CALL 이후의 SELECT @a, @b, @c
+------+------+------+
| @a   | @b   | @c   |
+------+------+------+
|    1 |  100 |   20 |
+------+------+------+

    한 줄씩 추적한다. CALL이 시작되면 IN 매개변수 a에는 @a의 값 1이 복사된다. OUT 매개변수 b는 호출자가 5를 넘겼는데도 NULL로 시작한다. 매뉴얼은 OUT 매개변수의 초깃값이 프로시저 안에서 NULL이라고 정한다. INOUT 매개변수 c에는 @c의 값 10이 복사된다. 그래서 본문 첫 SELECT는 1, NULL, 10을 결과 집합으로 돌려준다. 이어서 SET이 세 지역 값을 2, 100, 20으로 바꾼다. 프로시저가 끝나는 순간 OUT과 INOUT 매개변수의 값만 호출자의 변수로 복사된다. IN 매개변수 a를 2로 바꾼 것은 호출자에게 보이지 않으므로 @a는 1 그대로다.

    모드들어올 때나갈 때자바에 비유하면
    IN(기본값)호출자 값을 복사복사하지 않음메서드 매개변수(값에 의한 전달)
    OUT복사하지 않음(NULL로 시작)호출자 변수에 복사자바에는 없음. 반환값의 한 칸에 가깝다
    INOUT호출자 값을 복사호출자 변수에 복사자바에는 없음. 값을 받아 고쳐서 돌려주는 칸

    자바 기본편에서 본 것처럼 자바는 항상 값에 의한 전달(pass by value)이고, 메서드 안에서 매개변수 변수에 새 값을 대입해도 호출자의 변수는 바뀌지 않는다. IN 매개변수가 바로 이 규칙이다. OUT과 INOUT은 자바에 없는 "돌아갈 때 복사"라는 규칙을 더한 것이다. 여러 값을 돌려줘야 할 때 자바는 객체나 레코드로 묶어 반환하지만, 프로시저는 OUT 매개변수를 여러 개 두어 해결한다. 저장 함수는 매개변수에 모드를 붙일 수 없고 모든 매개변수가 IN으로 취급되며, 돌려주는 값은 RETURN 하나뿐이다.

    프로시저는 결과 집합을 돌려줄 수 있다

    param_demo의 첫 줄처럼 INTO 없이 SELECT를 실행하면 그 결과가 CALL을 실행한 클라이언트에게 결과 집합으로 전달된다. SELECT가 여러 번 실행되면 결과 집합도 여러 개가 된다. 매뉴얼은 결과 집합을 돌려주는 문장을 저장 프로시저에서는 쓸 수 있지만 저장 함수에서는 쓸 수 없다고 정한다. 그래서 프로시저를 호출하는 클라이언트 코드는 결과 집합이 몇 개 올지, OUT 매개변수는 언제 읽을지 알아야 한다. 이것이 뒤에서 볼 JDBC의 CallableStatement가 다소 번거로운 이유다.

    프로시저는 데이터베이스에 속하고, 권한으로 보호된다

    프로시저는 만들 때의 기본 데이터베이스(default database)에 속한다. 다른 데이터베이스에 만들려면 shop.place_order처럼 이름 앞에 데이터베이스를 붙인다. 프로시저 안에서는 USE 문을 쓸 수 없고, 대신 호출될 때 그 프로시저가 속한 데이터베이스로 암묵적인 USE가 일어났다가 끝나면 되돌려진다. 그래서 프로시저 본문의 product는 호출자가 어느 데이터베이스를 쓰고 있든 프로시저가 속한 데이터베이스의 product를 가리킨다.

    프로시저나 함수를 만들려면 CREATE ROUTINE 권한이 필요하다. 만든 사람에게는 기본적으로 그 루틴에 대한 ALTER ROUTINE과 EXECUTE 권한이 자동으로 주어진다(automatic_sp_privileges 시스템 변수, 기본값 ON). 루틴을 부르는 사용자에게는 EXECUTE 권한이 필요하다. 정의를 고칠 때는 주의할 점이 있다. ALTER PROCEDURE는 주석이나 보안 방식 같은 특성만 바꿀 수 있고 매개변수나 본문은 바꾸지 못한다. 본문을 고치려면 DROP PROCEDURE 후 다시 CREATE PROCEDURE를 해야 한다. 이 "지우고 다시 만드는" 방식이 배포 과정에서 어떤 문제를 만드는지는 함정을 다룰 때 다시 본다.

    저장 프로시저 2: 변수, 분기, 예외 처리, 그리고 트랜잭션

    이제 이 회차의 중심 예제인 주문 처리 프로시저를 만든다. 재고를 잠그고 읽어 확인한 뒤, 재고를 줄이고, 주문을 넣고, 새 주문 번호를 OUT 매개변수로 돌려준다. 중간에 문제가 생기면 모든 변경을 되돌리고 오류를 호출자에게 알린다.

    DELIMITER //

CREATE PROCEDURE place_order(
  IN  p_product_id BIGINT,
  IN  p_quantity   INT,
  OUT p_order_id   BIGINT
)
BEGIN
  DECLARE v_stock INT;
  DECLARE v_price INT;

  DECLARE EXIT HANDLER FOR SQLEXCEPTION
  BEGIN
    ROLLBACK;
    RESIGNAL;
  END;

  START TRANSACTION;

  SELECT stock, price INTO v_stock, v_price
    FROM product
   WHERE product_id = p_product_id
     FOR UPDATE;

  IF v_stock IS NULL THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '없는 상품입니다';
  ELSEIF v_stock < p_quantity THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '재고가 부족합니다';
  END IF;

  UPDATE product
     SET stock = stock - p_quantity
   WHERE product_id = p_product_id;

  INSERT INTO orders (product_id, quantity, total_price)
  VALUES (p_product_id, p_quantity, v_price * p_quantity);

  SET p_order_id = LAST_INSERT_ID();
  COMMIT;
END //

DELIMITER ;

    위에서부터 한 덩어리씩 읽는다. DECLARE v_stock INT는 지역 변수(local variable)를 선언한다. 지역 변수는 선언된 BEGIN...END 블록 안에서만 보이고, DEFAULT 절이 없으면 NULL로 시작한다. 사용자 정의 변수(@cnt)가 세션 전체에 걸쳐 사는 것과 달리, 지역 변수는 프로시저 실행이 끝나면 사라진다. 선언에는 순서 규칙이 있다. 변수와 조건 선언이 먼저, 커서 선언이 그다음, 핸들러 선언이 마지막이다. 이 순서를 어기면 CREATE PROCEDURE 자체가 오류로 거부된다.

    DECLARE EXIT HANDLER FOR SQLEXCEPTION은 예외 처리기다. SQLEXCEPTION은 SQLSTATE가 '00'(성공), '01'(경고), '02'(데이터 없음)로 시작하지 않는 모든 상태, 즉 오류를 뜻한다. 블록 안의 어떤 문장이 오류를 내면 실행이 핸들러 본문으로 넘어가고, 핸들러 동작이 EXIT이므로 핸들러 본문을 마친 뒤 핸들러를 선언한 BEGIN...END 블록을 빠져나간다. 오류가 안쪽 블록에서 났더라도 마찬가지다. 동작에는 CONTINUE도 있는데, 이것은 핸들러 본문을 실행한 뒤 오류를 낸 문장의 다음 문장부터 계속한다. 핸들러 본문의 ROLLBACK은 이 프로시저가 시작한 트랜잭션을 되돌리고, RESIGNAL은 방금 잡은 오류를 같은 SQLSTATE와 메시지로 다시 던져 호출자에게 전달한다. RESIGNAL이 없으면 오류가 핸들러 안에서 삼켜져 CALL이 성공한 것처럼 끝난다.

    핸들러가 아예 없다면 어떻게 될까. 매뉴얼에 따르면 SQLEXCEPTION에 맞는 핸들러가 없을 때 저장 프로그램은 오류를 낸 문장에서 EXIT 핸들러가 있는 것처럼 끝나고, 오류는 호출자에게 전달된다. 문제는 트랜잭션이다. InnoDB에서 오류를 낸 문장 자체는 되돌려지지만, 그 앞에서 이미 성공한 UPDATE는 커밋도 롤백도 되지 않은 채 열린 트랜잭션 안에 남는다. 그 행에 걸린 잠금도 그대로다. 호출한 애플리케이션이 이 사실을 모르고 연결을 커넥션 풀에 돌려주면, 반쯤 처리된 트랜잭션이 다음 사용자의 작업과 섞일 수 있다. 핸들러에서 ROLLBACK을 하는 것은 이 상황을 막기 위해서다.

    START TRANSACTION은 트랜잭션을 시작한다. 프로시저 안에서는 트랜잭션을 시작하고 끝낼 수 있다(함수와 트리거에서는 안 된다). 다만 매뉴얼은 START TRANSACTION과 BEGIN이 현재 세션에서 진행 중인 트랜잭션을 마치 COMMIT을 한 것처럼 암묵적으로 끝낸다고 정한다. 호출자가 이미 트랜잭션을 열고 몇 가지 변경을 한 뒤 이 프로시저를 부르면, 호출자의 변경이 프로시저의 첫 문장에서 커밋되어 버린다는 뜻이다. 호출자는 나중에 ROLLBACK을 해도 그 변경을 되돌릴 수 없다. 트랜잭션의 경계를 누가 정하는가는 뒤에서 스프링의 트랜잭션 관리와 엮어 다시 다룬다.

    SELECT ... INTO v_stock, v_price ... FOR UPDATE는 상품 행을 읽어 지역 변수에 담으면서 그 행에 배타 잠금(exclusive lock)을 건다. 08회에서 본 것처럼 잠금은 트랜잭션이 끝날 때까지 유지된다. 같은 상품에 대해 동시에 두 주문이 들어오면, 뒤에 온 세션은 앞의 세션이 COMMIT이나 ROLLBACK을 할 때까지 이 SELECT에서 기다린다. FOR UPDATE가 없다면 두 세션이 모두 재고 3을 읽고, 모두 "3개 주문 가능"이라고 판단해 재고를 두 번 줄일 수 있다. 확인과 변경 사이에 다른 트랜잭션이 끼어들지 못하게 하는 것이 이 잠금의 역할이다.

    상품이 없으면 어떻게 될까. 매뉴얼은 SELECT ... INTO가 행을 하나도 찾지 못하면 오류 코드 1329(No data) 경고가 나고 변수 값은 바뀌지 않는다고 정한다. 이 경고의 SQLSTATE는 '02000'으로 NOT FOUND 부류이며, 핸들러가 없는 NOT FOUND가 보통의 방식으로 발생하면 동작은 CONTINUE다. 그래서 실행은 다음 문장으로 넘어가고, v_stock은 선언할 때의 NULL 그대로 남는다. 다음 IF가 이것을 "없는 상품"으로 판단한다. 반대로 SELECT ... INTO가 두 행 이상을 찾으면 오류 1172(Result consisted of more than one row)가 난다. 이 예제는 기본 키로 찾으므로 그럴 일이 없다.

    SIGNAL SQLSTATE '45000'은 오류를 직접 일으킨다. 매뉴얼은 '45000'을 "처리되지 않은 사용자 정의 예외(unhandled user-defined exception)"를 뜻하는 일반적인 SQLSTATE라고 설명한다. 이 상태는 SQLEXCEPTION 부류이므로 위에서 선언한 EXIT 핸들러가 잡는다. 핸들러가 ROLLBACK 후 RESIGNAL을 하면 클라이언트는 오류를 받는다. SIGNAL에서 MYSQL_ERRNO를 지정하지 않았으므로 오류 번호는 기본값인 ER_SIGNAL_EXCEPTION, 곧 1644다. 나머지 UPDATE, INSERT는 이미 아는 문장이고, LAST_INSERT_ID()는 이 연결에서 마지막으로 생성된 AUTO_INCREMENT 값을 돌려준다. 이 값은 연결마다 따로 관리되므로 다른 세션이 동시에 주문을 넣어도 섞이지 않는다.

    이제 세 번 호출해 보자. 시작 상태는 앞의 표와 같다.

    CALL place_order(1, 2, @oid);   -- (1) 키보드 2개
SELECT @oid;

CALL place_order(2, 5, @oid);   -- (2) 마우스 5개, 재고는 3개
CALL place_order(99, 1, @oid);  -- (3) 없는 상품

    호출프로시저 안에서 일어난 일끝난 뒤의 데이터
    (1)트랜잭션 시작 → 키보드 행 잠그고 재고 10, 가격 50000 읽음 → 10 ≥ 2이므로 통과 → 재고 8로 변경 → 주문(1번 상품, 2개, 100000원) 삽입 → p_order_id = 1 → COMMIT으로 잠금 해제키보드 재고 8, 주문 1건(order_id 1)
    (2)트랜잭션 시작 → 마우스 행 잠그고 재고 3 읽음 → 3 < 5이므로 SIGNAL → 핸들러가 ROLLBACK(아직 변경 없음, 잠금 해제) → RESIGNAL변화 없음
    (3)트랜잭션 시작 → 99번 행이 없어 경고 1329, v_stock은 NULL 유지 → SIGNAL → ROLLBACK → RESIGNAL변화 없음

    (2)와 (3)은 UPDATE와 INSERT에 도달하기 전에 SIGNAL로 빠져나갔으므로 orders에 아무 행도 생기지 않았다. 만약 INSERT 단계에서 외래 키 위반 같은 오류가 났다면, 그 앞의 UPDATE는 이미 실행된 상태다. 이때도 핸들러의 ROLLBACK이 UPDATE까지 되돌리므로 "재고는 줄었는데 주문은 없는" 상태는 남지 않는다. 오류가 난 뒤의 @oid 값에 기대는 코드는 쓰지 않는 것이 안전하다. 성공 여부는 오류가 났는지로 판단한다.

    프로시저 안에서 오류를 내는 방법은 SIGNAL이고, 잡는 방법은 DECLARE ... HANDLER다. 자바의 throw와 try-catch에 대응하지만, 핸들러는 블록 앞부분에 선언해 두고 블록 전체에 적용된다는 점이 다르다. 또한 핸들러가 없는 경고(SQLSTATE '01')는 실행을 멈추지 않고 CONTINUE처럼 넘어간다.

    저장 프로시저 3: 반복과 커서, 그리고 행 단위 처리의 비용

    프로시저에는 반복문도 있다. LOOP ... END LOOP, WHILE ... END WHILE, REPEAT ... UNTIL ... END REPEAT 세 가지가 있고, 레이블을 붙인 반복은 LEAVE 레이블로 빠져나가고 ITERATE 레이블로 다음 바퀴로 넘어간다. 반복과 짝을 이루는 것이 커서(cursor)다. 커서는 SELECT의 결과를 한 행씩 꺼내 처리하게 해 준다. 재고가 기준보다 적은 상품마다 재고를 채우는 프로시저를 커서로 써 보자.

    DELIMITER //

CREATE PROCEDURE restock_low(IN p_threshold INT, IN p_amount INT)
BEGIN
  DECLARE v_done BOOLEAN DEFAULT FALSE;
  DECLARE v_id   BIGINT;
  DECLARE cur CURSOR FOR
    SELECT product_id FROM product WHERE stock < p_threshold;
  DECLARE CONTINUE HANDLER FOR NOT FOUND SET v_done = TRUE;

  OPEN cur;
  read_loop: LOOP
    FETCH cur INTO v_id;
    IF v_done THEN
      LEAVE read_loop;
    END IF;
    UPDATE product SET stock = stock + p_amount WHERE product_id = v_id;
  END LOOP;
  CLOSE cur;
END //

DELIMITER ;

    선언 순서가 앞에서 말한 규칙 그대로다. 변수 두 개, 커서, 핸들러 순이다. 동작은 이렇다. OPEN cur가 커서의 SELECT를 실행한다. FETCH는 다음 행의 값을 변수에 담는다. 더 꺼낼 행이 없을 때 FETCH를 하면 SQLSTATE '02000'의 데이터 없음(No Data) 상태가 생기고, NOT FOUND 핸들러가 그것을 잡아 v_done을 TRUE로 바꾼다. 핸들러 동작이 CONTINUE이므로 실행은 FETCH 다음 문장인 IF로 돌아오고, IF가 반복을 빠져나간다. 이 NOT FOUND 핸들러를 빠뜨리면 마지막 행 다음의 FETCH에서 반복을 멈출 방법이 없다는 점이 커서 코드에서 가장 흔한 실수다.

    MySQL의 커서에는 세 가지 성질이 있다. 읽기 전용(read only)이라 커서를 통해 행을 고칠 수 없다. 앞으로만 움직이며(nonscrollable) 행을 건너뛰거나 뒤로 갈 수 없다. 그리고 민감도가 정해져 있지 않다(asensitive). 매뉴얼은 서버가 커서의 결과 테이블을 복사할 수도 있고 복사하지 않을 수도 있다고 쓴다. 이 마지막 성질 때문에, 커서가 읽고 있는 테이블을 같은 반복 안에서 고치는 위 코드는 커서가 고쳐진 값을 보게 될지 장담할 수 없다. 이 예제에서는 기본 키로 한 행씩 고치므로 결과가 달라지지 않지만, 조건에 쓰인 열을 크게 바꾸는 코드라면 이 불확정성을 따져 봐야 한다.

    더 근본적인 문제는 비용이다. 이 프로시저와 같은 결과를 내는 SQL은 한 문장이다.

    UPDATE product
   SET stock = stock + 10
 WHERE stock < 5;

    커서 버전은 대상 행이 N개면 UPDATE 문장을 N번 실행한다. 문장마다 실행기를 거치고 기본 키 인덱스를 따라 내려가 행을 찾는다. 한 문장 버전은 조건에 맞는 행을 한 번의 스캔으로 찾아 고친다. 01회에서 조인을 "바깥 행마다 안쪽을 찾는 중첩 루프"로 이해했는데, 커서 반복은 그 루프를 엔진 바깥에서 손으로 짠 것과 같다. 엔진 안의 루프는 옵티마이저가 인덱스와 순서를 고를 수 있지만, 손으로 짠 루프는 쓴 그대로 실행된다. 저장 프로그램을 쓰더라도 집합 단위로 쓸 수 있는 일은 집합 단위 SQL 한 문장으로 쓰고, 커서는 행마다 정말 다른 처리가 필요할 때만 쓴다.

    재귀도 짚어 둔다. 저장 프로시저는 자기 자신을 부를 수 있지만, 그 깊이를 정하는 max_sp_recursion_depth의 기본값이 0이라 기본 설정에서는 재귀가 완전히 꺼져 있다. 최댓값은 255이고, 한도를 넘으면 오류 1456(Recursive limit ... was exceeded)이 난다. 저장 함수는 아예 재귀가 금지되어 있어 오류 1424(Recursive stored functions and triggers are not allowed)를 낸다. 트리 구조를 따라가는 일은 저장 프로그램의 재귀 대신 8.0의 재귀 공통 테이블 식(WITH RECURSIVE)으로 푸는 편이 MySQL에서는 자연스럽다.

    저장 함수: 식 안에서 불리는 루틴

    저장 함수는 값 하나를 계산해 돌려주고, SQL 문 안에서 내장 함수처럼 쓴다. 할인율을 받아 할인된 가격을 계산하는 함수를 만들어 보자.

    CREATE FUNCTION discounted_price(p_price INT, p_rate INT)
RETURNS INT
DETERMINISTIC
NO SQL
RETURN p_price - p_price * p_rate DIV 100;

SELECT name, price, discounted_price(price, 10) AS sale_price
  FROM product
 ORDER BY product_id;
    +-----------+--------+------------+
| name      | price  | sale_price |
+-----------+--------+------------+
| 키보드 |  50000 |      45000 |
| 마우스 |  20000 |      18000 |
| 모니터 | 300000 |     270000 |
+-----------+--------+------------+

    본문이 RETURN 문 하나이고 안에 ;가 없으므로 DELIMITER를 바꿀 필요가 없다. RETURNS INT는 돌려줄 값의 타입이다. 식 p_price * p_rate DIV 100에서 *와 DIV는 우선순위가 같고 왼쪽부터 계산되므로 (p_price * p_rate) DIV 100이다. 키보드라면 50000 × 10 = 500000, 이를 100으로 정수 나눗셈한 5000을 빼서 45000이 된다. 이 함수는 SELECT 목록에 있으므로 결과 행마다 한 번씩, 모두 세 번 실행된다.

    특성 선언: DETERMINISTIC과 데이터 접근 수준

    DETERMINISTIC과 NO SQL은 함수의 특성(characteristic)이다. DETERMINISTIC은 "같은 입력에는 항상 같은 결과"를 뜻하고, 아무것도 쓰지 않으면 기본값은 NOT DETERMINISTIC이다. 데이터 접근 수준은 네 가지다. CONTAINS SQL(SQL을 담지만 데이터를 읽거나 쓰지 않음, 기본값), NO SQL(SQL이 없음), READS SQL DATA(데이터를 읽기만 함), MODIFIES SQL DATA(데이터를 고침). 이 특성들이 무엇을 위한 것인지 알려면 특성을 빼고 함수를 만들어 보면 된다.

    CREATE FUNCTION add_one(x INT)
RETURNS INT
RETURN x + 1;
    ERROR 1418 (HY000): This function has none of DETERMINISTIC, NO SQL,
or READS SQL DATA in its declaration and binary logging is enabled
(you *might* want to use the less safe log_bin_trust_function_creators
variable)

    이 회차의 예제를 실제로 돌려 본 MySQL 8.4.13과 8.0.46 서버는 바이너리 로그를 끈 상태(@@log_bin = 0)였고, 거기서는 위의 add_one이 오류 없이 만들어졌다. 그래서 위 출력은 그 서버들에서 직접 받은 것이 아니며, 오류 문구는 두 서버의 오류 메시지 파일(errmsg.sys)에 든 문구와 대조해 확인했다. 바이너리 로그를 끄면 이 검사도 사라진다는 점 자체가 다음 설명을 뒷받침한다.

    오류 메시지가 이유를 말해 준다. 바이너리 로그(binary log)가 켜져 있기 때문이다. MySQL 8.0부터는 --log-bin 옵션을 주지 않아도 바이너리 로그가 기본으로 켜진다. 바이너리 로그는 데이터를 바꾼 내용을 기록해 두는 파일로, 레플리카(replica) 서버가 이것을 받아 같은 변경을 재현하고, 백업 시점 이후의 변경을 복구할 때도 쓴다. 기록 방식이 문장 기반(statement-based)이면 데이터를 바꾼 SQL 문 자체를 기록하고, 레플리카는 그 문장을 다시 실행한다. 그 문장 안에 함수 호출이 있으면 레플리카에서도 함수가 다시 실행된다. 함수가 호출할 때마다 다른 값을 내거나 데이터를 고친다면 원본(source)과 레플리카의 데이터가 달라진다. 그래서 MySQL은 바이너리 로그가 켜져 있을 때, 함수를 만드는 사람이 DETERMINISTIC, NO SQL, READS SQL DATA 가운데 적어도 하나를 명시하도록 요구한다.

    여기에는 중요한 단서가 있다. 매뉴얼은 NO SQL, READS SQL DATA 같은 데이터 접근 특성이 "권고(advisory)일 뿐"이라고 쓴다. 서버는 NO SQL로 선언한 함수가 실제로 SQL을 실행하는지, DETERMINISTIC으로 선언한 함수가 정말 결정적인지 검사하지 않는다. 판단은 함수를 만드는 사람의 정직함에 맡겨진다. 오류 1418을 피하려고 UUID()처럼 호출할 때마다 다른 값을 내는 함수를 쓰는 저장 함수에 DETERMINISTIC을 붙이면 함수는 만들어지지만, 문장 기반 복제에서 레플리카가 원본과 다른 값을 계산할 위험은 그대로 남는다. 매뉴얼도 UUID()를 비결정적이며 복제되지 않는 함수의 예로 든다. 오류 메시지가 권하는 log_bin_trust_function_creators를 1로 바꾸는 것도 같은 성격이다. 이 변수는 함수 생성 조건을 완화할 뿐 위험을 없애지 않고, 메시지 스스로 "덜 안전한(less safe)" 방법이라고 밝힌다.

    데이터를 읽는 함수는 행마다 쿼리를 실행한다

    이번에는 테이블을 읽는 함수다. 상품 번호를 받아 재고 상태를 문자열로 돌려준다.

    DELIMITER //

CREATE FUNCTION stock_status(p_product_id BIGINT)
RETURNS VARCHAR(10)
READS SQL DATA
BEGIN
  DECLARE v_stock INT;
  SELECT stock INTO v_stock FROM product WHERE product_id = p_product_id;
  RETURN CASE
           WHEN v_stock IS NULL THEN '없음'
           WHEN v_stock = 0     THEN '품절'
           WHEN v_stock < 5     THEN '부족'
           ELSE '충분'
         END;
END //

DELIMITER ;

SELECT name, stock, stock_status(product_id) AS status
  FROM product
 ORDER BY product_id;
    +-----------+-------+--------+
| name      | stock | status |
+-----------+-------+--------+
| 키보드 |     8 | 충분 |
| 마우스 |     3 | 부족 |
| 모니터 |     0 | 품절 |
+-----------+-------+--------+

    결과는 맞지만 실행 과정을 그려 보면 낭비가 보인다. 바깥 SELECT가 product를 읽으며 한 행을 만들 때마다 함수가 불리고, 함수 안의 SELECT가 기본 키로 product를 다시 한 번 찾는다. 상품이 3개면 바깥 스캔 한 번에 안쪽 조회가 3번이고, 상품이 100만 개면 안쪽 조회가 100만 번이다. 03회의 상관 서브쿼리가 바깥 행마다 다시 계산되는 것과 같은 구조이고, 이후 JPA를 배울 때 만날 N+1 문제와도 같은 모양이다. 차이는 그 반복이 함수 이름 뒤에 숨어 쿼리만 봐서는 보이지 않는다는 점이다. 이 경우 재고는 바깥 쿼리가 이미 읽은 행에 있으므로, 04회의 CASE 식을 SELECT 목록에 바로 쓰면 product를 한 번만 읽고 끝난다.

    WHERE 절의 함수는 인덱스를 막는다

    함수를 WHERE 절에 넣을 때는 두 가지를 따로 생각해야 한다. 첫째는 열을 함수로 감싸는 경우다. WHERE discounted_price(price, 10) >= 40000이라고 쓰면, price에 인덱스가 있어도 옵티마이저는 함수의 결과에 대한 범위를 인덱스의 범위로 바꿀 방법이 없다. 05회와 06회에서 본 것처럼 B+Tree 인덱스는 열 값의 순서로 정렬되어 있을 뿐, 함수를 적용한 값의 순서로 정렬되어 있지 않기 때문이다. 결국 모든 행을 읽어 행마다 함수를 실행해 본다. 조건을 열이 아니라 상수 쪽을 계산하는 모양으로 바꿔 쓸 수 있다면 그렇게 해야 인덱스를 탈 수 있다.

    둘째는 비교 대상이 비결정적 함수인 경우다. MySQL 매뉴얼의 함수 호출 최적화 절은 WHERE id = FLOOR(1 + RAND() * 49)를 예로 든다. RAND()는 비결정적이라 행마다 새 값을 내므로, 이 식은 쿼리 안에서 상수가 아니다. 그래서 옵티마이저는 기본 키 조회를 쓰지 못하고 테이블의 모든 행을 읽으며 행마다 조건을 계산하고, 결과로 0개 또는 여러 개의 행이 나올 수 있다. 매뉴얼은 같은 이유로 InnoDB가 한 행 잠금 대신 범위 잠금을 걸 수 있고, 비결정적으로 실행되는 UPDATE는 복제에 안전하지 않다고 덧붙인다. 해결책으로 매뉴얼은 값을 먼저 사용자 변수에 담아 상수로 만든 뒤 조건에 쓰는 방법을 보여 준다. 이 절은 내장 함수를 다루고 저장 함수의 DETERMINISTIC 선언이 옵티마이저의 판단에 어떻게 쓰이는지는 말하지 않으므로, 저장 함수의 결과를 상수처럼 쓰고 싶을 때도 값을 먼저 변수에 담아 넘기는 쪽이 확실하다.

    함수가 할 수 없는 일

    마지막으로 저장 함수에 걸린 제약을 이유와 함께 정리한다. 모두 "함수는 다른 문장의 한가운데에서 돈다"는 사실에서 나온다.

    • 결과 집합을 돌려주는 문장: INTO 없는 SELECT, SHOW, EXPLAIN 같은 문장을 쓸 수 없다. 정의할 때 알 수 있으면 오류 1415(Not allowed to return a result set from a function)로 거부된다.
    • 커밋이나 롤백을 일으키는 문장: COMMIT, ROLLBACK은 물론 암묵적 커밋을 일으키는 DDL도 쓸 수 없다. START TRANSACTION도 함수와 트리거에서는 쓸 수 없다.
    • 동적 SQL: PREPARE, EXECUTE, DEALLOCATE PREPARE는 프로시저에서는 되지만 함수와 트리거에서는 안 된다. 문자열로 SQL을 만들어 실행할 수 없다는 뜻이다.
    • 재귀: 함수는 자기 자신을 부를 수 없다(오류 1424).
    • 호출한 문장이 쓰는 테이블의 변경: 함수나 트리거는 자신을 호출한 문장이 읽거나 쓰고 있는 테이블을 고칠 수 없다. 어기면 실행할 때 오류 1442가 난다. 이 제약은 트리거에서 특히 자주 부딪히므로 다음 절에서 예제로 본다.

    트리거: 행 변경에 붙어 실행되는 코드

    트리거는 특정 테이블에 붙어, 그 테이블의 행이 바뀔 때 엔진이 자동으로 실행하는 코드다. 누가 어떤 경로로 행을 바꾸든 따라 실행된다는 점이 트리거의 장점이자 위험이다. 실습 테이블에 두 개의 트리거를 만든다. 하나는 상품의 재고가 바뀔 때마다 이력을 남기고, 다른 하나는 주문 수량이 1 이상인지 검사한다.

    DELIMITER //

CREATE TRIGGER trg_product_stock_log
AFTER UPDATE ON product
FOR EACH ROW
BEGIN
  IF NEW.stock <> OLD.stock THEN
    INSERT INTO stock_log (product_id, before_stock, after_stock)
    VALUES (NEW.product_id, OLD.stock, NEW.stock);
  END IF;
END //

CREATE TRIGGER trg_orders_check_quantity
BEFORE INSERT ON orders
FOR EACH ROW
BEGIN
  IF NEW.quantity <= 0 THEN
    SIGNAL SQLSTATE '45000' SET MESSAGE_TEXT = '주문 수량은 1 이상이어야 합니다';
  END IF;
END //

DELIMITER ;

    문법은 네 부분으로 읽는다. 첫째, 실행 시점(action time)은 BEFORE와 AFTER 두 가지다. 둘째, 사건(event)은 INSERT, UPDATE, DELETE 세 가지다. 그래서 한 테이블에 붙일 수 있는 트리거의 종류는 여섯 가지 조합이다. 셋째, ON product는 트리거가 붙을 테이블이며, 매뉴얼은 이 테이블이 영구 테이블이어야 하고 임시 테이블이나 뷰에는 트리거를 붙일 수 없다고 정한다. 넷째, FOR EACH ROW는 문장이 영향을 준 행마다 본문을 한 번씩 실행한다는 뜻이다. MySQL의 CREATE TRIGGER 문법에는 FOR EACH ROW만 있으므로, MySQL의 트리거는 모두 행 단위 트리거다. 100행을 고치는 UPDATE 한 문장은 트리거 본문을 100번 실행한다.

    NEW와 OLD: 바뀌기 전과 후의 행

    트리거에는 매개변수가 없다. 대신 바뀌는 행에 NEW와 OLD라는 이름으로 접근한다. 어떤 이름을 쓸 수 있는지는 사건이 정한다.

    사건OLDNEW
    INSERT없음(이전 행이 없다)들어갈 행
    UPDATE고치기 전 행고친 뒤 행
    DELETE지워질 행없음(이후 행이 없다)

    OLD는 읽기 전용이다. NEW는 BEFORE 트리거에서만 SET NEW.열 = 값으로 고칠 수 있다. BEFORE 트리거는 행이 실제로 쓰이기 전에 실행되므로 NEW를 고치면 그 값이 저장된다. AFTER 트리거가 실행될 때는 행 변경이 이미 끝났으므로 NEW를 고칠 수 없다. 그래서 "들어가는 값을 다듬거나 채우는 일"은 BEFORE에서, "변경이 끝난 뒤 다른 테이블에 무언가를 남기는 일"은 AFTER에서 한다. 한 가지 함정이 있다. BEFORE INSERT 트리거에서 AUTO_INCREMENT 열의 NEW 값은 실제로 생성될 번호가 아니라 0이다. 번호는 행이 실제로 들어갈 때 정해지기 때문이다. 새 주문 번호를 이력에 남기고 싶다면 AFTER INSERT 트리거에서 읽어야 한다.

    트리거가 발동하는 순서와 실패했을 때

    한 문장이 여러 행을 바꿀 때, 각 행에 대해 다음 순서가 반복된다.

    매뉴얼은 마지막 단계를 이렇게 정리한다. BEFORE 트리거든 AFTER 트리거든 오류가 나면 트리거를 발동시킨 문장 전체가 실패한다. 트랜잭션을 지원하는 테이블에서는 문장의 실패가 그 문장이 한 모든 변경의 롤백으로 이어지므로, 트리거의 실패도 롤백을 일으킨다. 반면 MyISAM 같은 비트랜잭션 테이블에서는 롤백이 불가능하므로, 문장이 실패해도 오류가 나기 전까지의 변경이 그대로 남는다. 100행을 고치는 UPDATE가 50번째 행의 트리거에서 실패하면 InnoDB에서는 아무 행도 바뀌지 않지만, MyISAM에서는 앞의 49행이 바뀐 채로 남을 수 있다는 뜻이다. 트리거로 무결성을 지키려 한다면 트랜잭션 테이블이 전제가 된다.

    트리거가 별도의 작업이 아니라 문장 안, 트랜잭션 안에서 행마다 동기적으로 실행된다는 것과, 각 단계에서 실패하면 어디로 가는지를 보여 준다. 가로로 긴 순서도. 가장 바깥에 큰 둥근 사각형 테두리가 있고 왼쪽 위에 "트랜잭션"이라는 라벨이 붙어 있다. 그 안에 조금 작은 사각형 테두리가 있고 라벨은 "UPDATE 문 하나". 그 안에 왼쪽에서 오른쪽으로 세 개의 상자가 화살표로 이어진다: 파란 상자 "BEFORE 트리거", 회색 상자 "행 변경", 초록 상자 "AFTER 트리거". 초록 상자에서 나온 화살표가 아래로 꺾여 왼쪽의 파란 상자로 돌아가며 그 화살표에 "다음 행"이라는 라벨이 붙는다. 세 상자 각각의 아래쪽에서 빨간 점선 화살표가 나와 오른쪽 아래의 빨간 상자 "문장 실패 → 문장의 변경 전체 롤백"으로 모인다. 초록 상자 오른쪽에서 나온 화살표는 "문장 종료"라는 상자로 간다. 초록 상자 위에 작은 말풍선 "stock_log에 INSERT"를 둔다. 평면적인 기술 도해 스타일, 흰 배경. 트리거는 문장 안에서 행마다 동기적으로 실행된다. 어느 단계든 실패하면 문장 전체가 실패한다.

    트리거를 직접 발동시켜 보기

    place_order (1)을 실행한 뒤의 상태(키보드 재고 8, 마우스 3, 모니터 0)에서 두 UPDATE를 실행한다.

    UPDATE product SET stock = stock + 10 WHERE stock < 5;   -- 마우스, 모니터
UPDATE product SET price = 55000 WHERE product_id = 1;    -- 키보드 가격만 변경

SELECT product_id, before_stock, after_stock
  FROM stock_log
 ORDER BY product_id;
    +------------+--------------+-------------+
| product_id | before_stock | after_stock |
+------------+--------------+-------------+
|          2 |            3 |          13 |
|          3 |            0 |          10 |
+------------+--------------+-------------+

    첫 UPDATE는 조건에 맞는 마우스와 모니터 두 행을 고친다. 트리거는 행마다 한 번씩, 모두 두 번 발동하고, 두 번 모두 재고가 바뀌었으므로 이력 두 행을 넣는다. 두 이력 행의 log_id는 엔진이 행을 처리한 순서대로 매겨지는데, UPDATE 문에 ORDER BY가 없으므로 그 순서는 SQL이 보장하지 않는다. 그래서 위 조회는 log_id가 아니라 product_id로 정렬했다. 두 번째 UPDATE도 키보드 한 행을 고치므로 트리거가 발동한다. 하지만 재고는 그대로이므로 IF 조건이 거짓이 되어 아무것도 남기지 않는다. 트리거는 "재고 열이 바뀔 때"가 아니라 "행이 UPDATE될 때" 발동한다. 특정 열의 변화에만 반응하려면 이 예제처럼 본문에서 OLD와 NEW를 비교해야 한다.

    트리거 안에서 자기 테이블을 고칠 수 없다

    주문이 들어올 때 총액을 주문 테이블에 채우고 싶다고 해 보자. 다음처럼 AFTER INSERT 트리거에서 orders를 UPDATE하는 코드를 떠올리기 쉽다.

    -- 이렇게 만들면 안 된다
CREATE TRIGGER trg_orders_bad
AFTER INSERT ON orders
FOR EACH ROW
  UPDATE orders
     SET total_price = NEW.quantity * 1000
   WHERE order_id = NEW.order_id;

    CREATE TRIGGER는 성공하지만, orders에 행을 넣는 순간 다음 오류가 난다.

    ERROR 1442 (HY000): Can't update table 'orders' in stored function/trigger because it is already used by statement which invoked this stored function/trigger.

    앞에서 본 제약 그대로다. 함수나 트리거는 자신을 호출한 문장이 읽거나 쓰고 있는 테이블을 고칠 수 없다. 이렇게 이해하면 된다. INSERT 문은 orders 테이블을 열어 행을 넣는 중이다. 그 한가운데에서 트리거가 같은 테이블을 고치면, 문장의 결과가 자기 자신의 부수 효과에 따라 달라지고, 그 변경이 다시 트리거를 부르는 순환도 생길 수 있다. MySQL은 이런 상황을 아예 금지한다. 같은 행의 값을 정하고 싶다면 방향이 다르다. BEFORE INSERT 트리거에서 SET NEW.total_price = ...로 들어갈 행 자체를 고치면 된다. 이 회차의 실습을 이어 가기 위해 trg_orders_bad는 만들지 않는다. 만들었다면 DROP TRIGGER trg_orders_bad로 지운다. 만든 채로 INSERT까지 실행했다면, 실패한 그 INSERT도 AUTO_INCREMENT 값 하나를 써 버린다. 실제로 그렇게 진행해 보면 뒤의 실습에서 새 주문 번호가 2가 아니라 3으로 나온다.

    트리거가 발동하지 않는 변경들

    트리거의 사건은 SQL 문의 종류가 아니라 테이블 연산의 종류다. 매뉴얼은 INSERT 트리거가 INSERT 문뿐 아니라 LOAD DATA와 REPLACE로 행이 들어갈 때도 발동하고, DELETE 트리거는 DELETE와 REPLACE로 행이 지워질 때 발동한다고 설명한다. 헷갈리기 쉬운 것은 INSERT ... ON DUPLICATE KEY UPDATE다. 매뉴얼에 따르면 이 문장은 행마다 BEFORE INSERT 트리거를 먼저 발동시키고, 키가 중복되지 않았으면 AFTER INSERT 트리거를, 중복되었으면 BEFORE UPDATE와 AFTER UPDATE 트리거를 차례로 발동시킨다. 중복된 행에 대해서도 BEFORE INSERT 트리거는 이미 한 번 실행된 뒤라는 점이 함정이다.

    반대로 행이 사라지거나 바뀌는데도 트리거가 발동하지 않는 경우가 있다.

    • 외래 키의 연쇄 동작: ON DELETE CASCADE로 자식 행이 함께 지워져도 자식 테이블의 DELETE 트리거는 발동하지 않는다. 매뉴얼은 연쇄된 외래 키 동작이 트리거를 발동시키지 않는다고 명시한다.
    • TRUNCATE TABLE과 DROP TABLE: 행 단위 DELETE를 쓰지 않으므로 DELETE 트리거가 발동하지 않는다. 파티션을 지워도 마찬가지다.
    • 행 기반 복제의 레플리카: 바이너리 로그가 행 기반이면, 원본에서 온 변경을 레플리카에 적용할 때 레플리카의 트리거는 발동하지 않는다. 이유는 뒤의 "한 층 아래" 절에서 본다.

    "이 테이블의 모든 삭제를 기록한다"는 감사 요구를 트리거로 구현했다면, 위 경로로 일어난 삭제는 기록되지 않는다. 트리거가 "모든 변경"을 잡는다는 믿음은 이 목록에서 깨진다.

    같은 사건에 트리거가 여러 개일 때, 그리고 트리거의 권한

    같은 테이블에 같은 시점·같은 사건의 트리거를 여러 개 둘 수 있다. 예를 들어 BEFORE UPDATE 트리거가 두 개일 수 있다. 기본적으로는 만든 순서대로 발동하고, 순서를 바꾸려면 FOR EACH ROW 뒤에 FOLLOWS 기존트리거나 PRECEDES 기존트리거를 붙인다. 트리거가 여러 개가 되면 실행 순서가 결과를 바꿀 수 있으므로, 순서를 명시하지 않은 트리거 묶음은 그 자체로 읽기 어려운 코드가 된다.

    트리거를 만들려면 해당 테이블에 대한 TRIGGER 권한이 필요하다. 실행될 때는 트리거를 정의한 사용자, 곧 DEFINER의 권한으로 검사한다. DEFINER 절을 생략하면 CREATE TRIGGER를 실행한 사용자가 DEFINER가 된다. 그래서 트리거 본문 안에서 CURRENT_USER()를 부르면 행을 바꾼 사용자가 아니라 DEFINER가 나온다. "누가 바꿨는지"를 남기려고 트리거에서 CURRENT_USER()를 기록하면 모든 이력에 같은 정의자 이름이 찍히는 셈이다.

    같은 일을 애플리케이션이 했다면: 왕복과 잠금 시간

    같은 절차를 자바 코드가 SQL을 한 문장씩 보내 처리한다고 해 보자. SELECT ... FOR UPDATE, UPDATE, INSERT, COMMIT만 세어도 요청과 응답이 네 번 오간다. 문장마다 네트워크를 건너가고, 결과를 받은 애플리케이션이 판단한 뒤 다음 문장을 보낸다. 더 중요한 것은 잠금이다. 키보드 행의 잠금은 2단계의 SELECT에서 걸려 COMMIT까지 유지되는데, 그 사이에 네트워크 왕복 세 번과 애플리케이션의 처리 시간이 끼어 있다. 같은 상품을 주문하려는 다른 세션은 그동안 기다린다. 프로시저는 CALL 한 번의 왕복으로 끝나고, 문장과 문장 사이에 네트워크를 기다리지 않으므로 잠금을 쥐고 있는 시간도 그만큼 짧아진다. 이것이 저장 프로시저가 주는 실제 이득이다. 이 이득이 어떤 비용과 맞바꾼 것인지는 함정을 다루는 절에서 따진다.

    문장 단위 호출은 왕복이 여러 번이고 그동안 행 잠금이 유지되며, 프로시저 호출은 왕복 한 번 안에서 서버가 여러 문장을 이어서 실행한다는 대비를 보여 준다. 좌우 두 패널로 나뉜 시퀀스 다이어그램. 왼쪽 패널 제목 "문장마다 호출", 오른쪽 패널 제목 "CALL 한 번". 각 패널에는 세로 생명선 두 개가 있다: 왼쪽 "애플리케이션", 오른쪽 "MySQL 서버". 왼쪽 패널에서는 애플리케이션에서 서버로 가는 실선 화살표와 서버에서 돌아오는 점선 화살표가 네 쌍 그려지고, 가는 화살표 라벨은 위에서부터 "SELECT … FOR UPDATE", "UPDATE", "INSERT", "COMMIT"이다. 서버 생명선 옆에 첫 번째 화살표부터 마지막 화살표까지 이어지는 주황색 세로 막대가 있고 라벨은 "행 잠금 유지". 오른쪽 패널에서는 화살표 한 쌍만 있으며 가는 화살표 라벨은 "CALL place_order(1, 3, @oid)"이다. 서버 생명선 위에 작은 상자들이 세로로 붙어 있어 서버 안에서 여러 문장이 이어서 실행됨을 나타내고, 주황색 막대는 왼쪽보다 훨씬 짧다. 평면 도해, 흰 배경. 프로시저의 이득은 "미리 컴파일"이 아니라 줄어든 왕복과 짧아진 잠금 유지 시간에서 나온다.

    자바에서 같은 프로시저 부르기

    애플리케이션에서 프로시저를 부를 때는 JDBC의 CallableStatement를 쓴다. 다음 코드는 JDK 21에서 컴파일되며, 실행하려면 클래스패스에 MySQL JDBC 드라이버가 있어야 한다.

    import java.sql.CallableStatement;
import java.sql.Connection;
import java.sql.DriverManager;
import java.sql.SQLException;
import java.sql.Types;

public class PlaceOrderCall {
    public static void main(String[] args) throws SQLException {
        String url = "jdbc:mysql://localhost:3306/shop";
        try (Connection con = DriverManager.getConnection(url, "app", "app-password");
             CallableStatement cs = con.prepareCall("{call place_order(?, ?, ?)}")) {

            cs.setLong(1, 1L);                          // IN p_product_id
            cs.setInt(2, 2);                            // IN p_quantity
            cs.registerOutParameter(3, Types.BIGINT);   // OUT p_order_id (실행 전에 등록)

            cs.execute();
            long orderId = cs.getLong(3);
            System.out.println("order_id = " + orderId);
        } catch (SQLException e) {
            System.out.println(e.getSQLState() + " / " + e.getErrorCode() + " / " + e.getMessage());
        }
    }
}

    {call place_order(?, ?, ?)}는 JDBC가 정한 저장 프로시저 이스케이프 문법(escape syntax)이다. Javadoc은 이 문법이 모든 RDBMS에서 같은 방식으로 저장 프로시저를 부르기 위한 것이라고 설명하고, 값을 돌려주는 형태인 {?= call ...}도 함께 정의한다. 드라이버가 이 표기를 해당 DB의 호출 문장으로 바꿔 보낸다. IN 매개변수는 PreparedStatement에서 물려받은 set 메서드로 채우고, OUT 매개변수는 실행하기 전에 registerOutParameter로 타입을 등록해야 하며, 값은 실행한 뒤 get 메서드로 읽는다. 프로시저가 결과 집합을 돌려준다면 Javadoc은 이식성을 위해 결과 집합과 갱신 건수를 먼저 처리한 뒤 OUT 매개변수를 읽으라고 권한다. 재고가 부족하면 catch 블록이 SQLSTATE 45000, 오류 코드 1644, 메시지 "재고가 부족합니다"를 담은 SQLException을 받는다. SIGNAL로 만든 오류가 네트워크를 건너 자바 예외로 바뀌는 것이다.

    스프링을 쓰면 SimpleJdbcCall이 이 과정을 감싸고, JPA에는 EntityManager.createStoredProcedureQuery가, 스프링 데이터 JPA에는 @Procedure가 있다. 이름은 달라도 아래에서 하는 일은 위의 CallableStatement와 같다. 이들은 이후 권에서 JDBC와 JPA를 다룰 때 다시 만난다.

    한 층 아래 1: 서버는 저장 프로그램을 어떻게 보관하고 실행하는가

    CREATE PROCEDURE를 실행하면 서버는 본문을 실행하지 않고 정의만 저장한다. MySQL 8.0에서는 저장 프로그램의 정의가 테이블 정의와 함께 서버의 데이터 사전(data dictionary)에 들어 있고, 사용자는 INFORMATION_SCHEMA.ROUTINES와 INFORMATION_SCHEMA.TRIGGERS 테이블, SHOW CREATE PROCEDURE·SHOW CREATE FUNCTION·SHOW CREATE TRIGGER 문, SHOW PROCEDURE STATUS 문으로 그것을 본다. 정의와 함께 저장되는 것이 하나 더 있다. 매뉴얼은 루틴을 만들거나 고칠 때의 sql_mode 값을 저장해 두었다가, 실행할 때는 현재 서버의 SQL 모드와 관계없이 항상 그 값으로 실행한다고 정한다. 느슨한 SQL 모드에서 만든 프로시저는 나중에 서버의 모드를 엄격하게 바꿔도 느슨한 규칙으로 계속 동작한다는 뜻이다.

    세션마다 따로 있는 캐시

    CALL이 처음 실행되면 서버는 정의를 읽어 프로그램 본문 전체를 내부 형태로 변환하고 캐시에 둔다. 매뉴얼의 설명에서 중요한 단어는 "세션별(per-session)"이다. 서버는 준비된 문장(prepared statement)과 저장 프로그램의 캐시를 세션마다 따로 유지하고, 한 세션이 캐시한 것은 다른 세션이 쓸 수 없으며, 세션이 끝나면 그 세션의 캐시는 버려진다. stored_program_cache 시스템 변수는 세션 하나가 캐시하는 저장 프로그램의 대략적인 개수를 정한다.

      MySQL 서버
  ┌──────────────────────────────────────────────────────────────┐
  │  데이터 사전: place_order 정의(본문 텍스트, sql_mode, DEFINER) │
  │        │ 처음 CALL할 때 읽어서 내부 형태로 변환                 │
  │        ▼                                                     │
  │  세션 A 캐시            세션 B 캐시            세션 C 캐시      │
  │  ┌──────────────┐     ┌──────────────┐     ┌──────────────┐  │
  │  │ place_order  │     │ place_order  │     │ (아직 없음)   │  │
  │  │ stock_status │     │              │     │              │  │
  │  └──────────────┘     └──────────────┘     └──────────────┘  │
  │   서로 공유하지 않는다. 세션이 끝나면 그 세션의 캐시는 버려진다. │
  └──────────────────────────────────────────────────────────────┘

    이 구조에서 몇 가지 결과가 나온다. 커넥션 풀은 연결을 오래 살려 두고 재사용하므로, 한 연결 안에서는 변환 비용을 처음 한 번만 치른다. 반면 연결이 100개이고 저장 프로그램이 많다면, 같은 프로그램이 연결 수만큼 따로 변환되어 각 세션의 메모리에 들어간다. 또 프로그램이 참조하는 테이블이나 뷰의 메타데이터가 바뀌면(테이블을 만들거나 지우거나 ALTER하는 DDL 등) 서버는 영향받는 문장만 다시 파싱(reparse)한다. 매뉴얼은 재파싱이 원래 변환할 때의 기본 데이터베이스와 SQL 모드로 이루어지고, 최대 세 번까지 시도하며 모두 실패하면 오류를 낸다고 설명한다. 행을 넣거나 고치는 것은 메타데이터 변경이 아니므로 재파싱을 일으키지 않는다.

    정의는 한 곳에 있지만 내부 형태로 변환된 캐시는 세션마다 따로 만들어지고 공유되지 않는다는 것을 보여 준다. 큰 사각형 "MySQL 서버" 안의 위쪽에 원통 모양 저장소 하나가 있고 라벨은 "데이터 사전: 저장 프로그램 정의". 그 아래에 세 개의 세로 상자가 나란히 있고 각각 "세션 A", "세션 B", "세션 C"라는 라벨이 붙어 있다. 각 세션 상자 안에 작은 카드 더미가 있고 카드에는 "place_order"처럼 루틴 이름이 적혀 있다(세션 C는 비어 있음). 원통에서 세션 A와 세션 B로 각각 화살표가 내려가며 화살표 라벨은 "첫 호출 시 변환". 세션 상자들 사이에 빨간 X 표시와 "공유하지 않음" 라벨이 있다. 서버 바깥 아래쪽에 "커넥션 풀"이라는 상자가 있고, 그 안의 연결 세 개가 각 세션 상자와 선으로 이어진다. 평면 도해, 흰 배경. 저장 프로그램의 캐시는 세션별이다. 커넥션 풀의 연결마다 같은 프로그램이 따로 변환되어 들어간다.

    내부 형태: 명령의 목록

    내부 형태가 어떻게 생겼는지는 SHOW PROCEDURE CODE 문으로 볼 수 있다. 다만 매뉴얼은 이 문장이 디버깅 지원을 넣어 빌드한 서버에서만 쓸 수 있다고 정하므로, 일반 배포판에서는 실행되지 않는다. MySQL 8.4.13과 8.0.46의 일반 배포판에서 SHOW PROCEDURE CODE place_order를 실행하면 ERROR 1289 (HY000): The 'SHOW PROCEDURE|FUNCTION CODE' feature is disabled; you need MySQL built with '--with-debug' to have it working가 난다. 매뉴얼의 예에 따르면 결과의 각 행은 명령(instruction) 하나이고, 0부터 시작하는 번호(Pos)와 명령 내용(Instruction) 두 열로 이루어진다. 실행할 것이 없는 BEGIN과 END는 사라지고, DEFAULT가 있는 DECLARE는 값을 대입하는 set 명령만 남으며, 본문의 SQL 문은 stmt 명령이 되고, LOOP의 끝은 앞쪽 명령 번호로 점프하는 jump 명령이 된다. 이 설명을 바탕으로 앞의 restock_low의 반복 부분을 명령 목록으로 그려 보면 다음과 같다. 실제 출력이 아니라 구조를 보여 주는 개념도다.

    개념도: restock_low의 반복 부분이 명령 목록으로 바뀐 모습 (실제 SHOW PROCEDURE CODE 출력이 아님)

 Pos  명령
 ---  -----------------------------------------------
  4   OPEN cur
  5   FETCH cur INTO v_id          ← 끝이면 NOT FOUND 핸들러가 v_done = TRUE
  6   v_done이 참이면 9로 점프       ← IF v_done THEN LEAVE read_loop
  7   SQL 문 실행: UPDATE product SET stock = stock + p_amount WHERE ...
  8   5로 점프                      ← END LOOP
  9   CLOSE cur

    이 그림에서 볼 것은 두 가지다. 첫째, 제어 흐름(IF, LOOP)은 점프로 바뀌어 서버 안의 작은 실행기가 명령 번호를 따라가며 처리한다. 자바 바이트코드의 분기 명령과 비슷한 모양이다. 둘째, 7번처럼 SQL 문은 SQL 문 그대로 남는다. 프로시저 안의 UPDATE도 결국 서버가 처리하는 보통의 SQL 문이며, 인덱스를 고르고 행을 찾고 잠금을 거는 과정은 클라이언트가 보낸 UPDATE와 같은 길을 간다.

    "저장 프로시저는 미리 컴파일되어 빠르다"는 말

    저장 프로시저를 설명할 때 자주 나오는 말이 "미리 컴파일되어 있어서 빠르다"다. MySQL에 대해서는 이 말을 그대로 받아들이면 안 된다. 매뉴얼이 설명하는 캐시는 세션별로 만들어지는 내부 형태이고, 세션이 끝나면 버려지며, 참조하는 객체가 바뀌면 다시 파싱된다. 이 캐시 절은 실행 계획을 세션 사이에 공유하거나 미리 만들어 둔다고 말하지 않는다. 그리고 본문의 SQL 문은 위에서 본 것처럼 보통의 SQL 문으로 실행된다. 그러므로 MySQL에서 프로시저가 빨라지는 경우는 "컴파일" 덕분이라기보다 앞에서 본 왕복 감소, 그리고 데이터를 애플리케이션으로 옮기지 않고 서버 안에서 처리하는 데서 나온다고 보는 것이 정확하다. 반대로 커서로 행을 하나씩 처리하는 프로시저는 같은 일을 하는 집합 기반 SQL 한 문장보다 느릴 수 있다.

    누구의 권한으로 실행되는가

    프로시저와 함수에는 SQL SECURITY 특성이 있고, 값은 DEFINER 또는 INVOKER이며 기본값은 DEFINER다. DEFINER이면 루틴 안의 문장이 루틴을 정의한 계정의 권한으로 검사되고, INVOKER이면 호출한 계정의 권한으로 검사된다. 기본값이 DEFINER라는 것은 쓸모 있는 보안 경계를 만들 수 있다는 뜻이다. 애플리케이션 계정에는 테이블 권한을 주지 않고 place_order의 EXECUTE 권한만 주면, 그 계정은 product를 직접 고칠 수 없고 프로시저가 정한 절차로만 고칠 수 있다. 같은 성질이 위험이 되기도 한다. DEFINER가 강한 권한을 가진 계정이라면, EXECUTE 권한만 있는 사용자도 그 루틴 안에서는 정의자의 권한으로 데이터를 다루게 된다. 루틴의 DEFINER가 누구인지는 코드 리뷰에서 본문만큼 중요하게 봐야 한다.

    한 층 아래 2: 트랜잭션, 잠금, 바이너리 로그와 엮이는 방식

    트리거는 호출한 문장의 트랜잭션 안에서 돈다

    실습에서 본 것처럼 트리거가 한 일은 트리거를 발동시킨 문장의 일부다. 별도의 트랜잭션도, 나중에 실행되는 비동기 작업도 아니다. 그래서 두 가지 결과가 나온다. 첫째, 원자성이 넓어진다. 재고 변경과 이력 기록은 함께 확정되거나 함께 사라진다. 이력이 없는 재고 변경은 남지 않는다. 둘째, 같은 이유로 트리거 기반 감사 로그는 "시도했지만 롤백된 변경"을 남기지 못한다. 바깥 트랜잭션이 롤백되면 트리거가 넣은 이력 행도 함께 롤백되기 때문이다. 실패한 시도까지 기록해야 하는 요구라면 트리거는 맞는 도구가 아니다.

    잠금도 함께 늘어난다. InnoDB에서 트랜잭션이 쓴 행의 잠금은 트랜잭션이 끝날 때까지 유지된다. 트리거가 다른 테이블에 행을 넣거나 고치면 그 테이블의 잠금도 바깥 트랜잭션이 끝날 때까지 쥐고 있게 된다. 애플리케이션 개발자는 product 한 테이블을 고친다고 생각하지만, 실제 트랜잭션은 product와 stock_log 두 테이블을 건드린다. 트리거가 다시 다른 테이블을 고치고 그 테이블에 또 트리거가 있다면 잠금의 범위는 코드에서 보이지 않는 곳까지 퍼진다. 08회에서 본 교착 상태(deadlock)는 두 트랜잭션이 서로 다른 순서로 자원을 잠글 때 생기는데, 잠금 순서의 일부가 트리거 안에 숨어 있으면 교착 상태의 원인을 찾기가 훨씬 어려워진다.

    바이너리 로그에는 무엇이 기록되는가

    저장 프로그램과 복제의 관계는 바이너리 로그의 형식에 따라 달라진다. MySQL 8.0의 기본 형식은 행 기반(ROW)이다. 형식별로 정리하면 다음과 같다.

    상황문장 기반(STATEMENT)행 기반(ROW, 8.0 기본값)
    CALL place_order(...)CALL 문은 기록되지 않고, 프로시저 안에서 실제로 실행된 문장들이 기록된다실행 결과로 바뀐 행들이 기록된다
    트리거가 한 변경트리거를 발동시킨 문장이 기록되고, 레플리카에서 그 문장을 실행할 때 레플리카의 트리거가 발동한다트리거가 바꾼 행도 행 변경으로 기록되고, 레플리카의 트리거는 원본에서 온 변경에 대해 발동하지 않는다
    비결정적 함수레플리카에서 다른 값이 나올 수 있어 위험하다(오류 1418의 이유)계산된 결과 행이 기록되므로 다시 계산하지 않는다

    행 기반 복제에서 레플리카의 트리거가 발동하지 않는 이유는 표를 보면 분명하다. 원본에서 트리거가 넣은 stock_log 행은 이미 행 변경으로 로그에 들어 있다. 레플리카가 product의 행 변경을 적용하면서 자기 트리거까지 실행한다면, stock_log 행이 로그에서 한 번, 레플리카의 트리거에서 또 한 번 들어가 두 번 기록될 것이다. 문장 기반 복제에서는 반대로 로그에 문장만 있으므로 레플리카가 트리거를 실행해야 원본과 같은 결과가 나온다. 매뉴얼은 트리거에 DETERMINISTIC 특성이 없어 항상 결정적이라고 가정하지만 그 가정이 틀릴 수 있다며, UUID() 같은 비결정적 함수를 트리거에서 쓸 때 주의하라고 경고한다.

    방향도 알아 두자. 매뉴얼은 binlog_format 변수가 MySQL 8.0.34부터 폐기 예정(deprecated)이며, 행 기반 이외의 로깅 형식 지원도 앞으로 제거될 수 있으니 새 복제 구성에는 행 기반 로깅만 쓰라고 권한다. 행 기반에서는 원본에서 트리거와 함수가 계산한 결과가 행으로 전달되므로, 결정성 문제는 줄어든다. 다만 오류 1418의 검사는 바이너리 로그가 켜져 있으면 형식과 관계없이 함수 생성 시점에 적용된다는 점, 그리고 트리거의 효과가 원본 쪽에만 있다는 점은 기억해야 한다.

    데이터베이스 로직의 함정

    지금까지 본 동작을 바탕으로, 업무 로직을 저장 프로그램에 둘 때 실제로 부딪히는 문제를 정리한다. 하나하나가 "저장 프로그램은 나쁘다"는 주장이 아니라, 앞에서 확인한 동작에서 따라 나오는 비용이다.

    1. 코드를 읽는 사람에게 보이지 않는다

    애플리케이션 코드에는 UPDATE product SET stock = ... 한 줄만 있다. 그런데 실제로는 stock_log에 행이 들어가고, 주문 테이블에는 수량 검사가 붙어 있다. 이 사실은 자바 코드 어디에도 없고 DB의 데이터 사전에만 있다. 새로 합류한 개발자는 stock_log 행이 어디서 생기는지 찾느라 애플리케이션 코드를 뒤지게 된다. ORM을 쓰면 문제가 하나 더 생긴다. JPA의 영속성 컨텍스트는 애플리케이션이 쓴 값을 기억할 뿐, BEFORE 트리거가 SET NEW로 바꾼 값은 알지 못한다. 트리거가 채운 값을 엔티티에서 읽으려면 EntityManager.refresh로 DB에서 다시 읽어 와야 한다. 로직이 두 곳에 나뉘면 각 곳의 코드가 다른 곳의 동작을 모르는 상태가 된다.

    2. 버전 관리와 배포가 애플리케이션과 따로 논다

    애플리케이션 코드는 Git에 있고, 리뷰를 거쳐, 빌드와 배포 파이프라인을 탄다. 저장 프로그램의 정의는 DB 서버 안에 있다. 누군가 운영 DB에서 프로시저를 직접 고치면 저장소의 코드와 실제로 실행되는 코드가 달라지고, 그 차이는 아무 경고 없이 쌓인다. 앞에서 본 것처럼 본문을 바꾸려면 DROP 후 CREATE를 해야 하므로, 두 문장 사이에 들어온 CALL은 프로시저가 없다는 오류를 받는다. 무중단 배포에서 구버전과 신버전 애플리케이션이 잠시 함께 돌 때, 매개변수가 바뀐 프로시저는 구버전 애플리케이션의 호출을 깨뜨린다. Flyway나 Liquibase 같은 마이그레이션 도구로 정의를 파일로 관리하면 나아지지만, 그것은 저장 프로그램을 애플리케이션 코드처럼 다루기 위한 추가 비용이다.

    3. 테스트와 디버깅이 어렵다

    자바 코드는 단위 테스트로 한 메서드씩 확인하고, 디버거로 한 줄씩 멈춰 변수를 볼 수 있다. 저장 프로그램은 실제 MySQL 서버가 있어야 실행되고, 표준 mysql 클라이언트에는 단계별 디버거가 없다. 실행 중의 값을 보려면 SELECT로 결과 집합을 흘리거나 로그 테이블에 기록하는 방법에 기대게 된다. 오류도 SIGNAL의 메시지 문자열로 전달되므로, 자바 예외처럼 타입과 스택 트레이스를 가진 정보가 아니다.

    4. 다른 DBMS로 옮길 수 없다

    앞에서 말했듯 저장 프로그램의 언어는 벤더마다 다르다. 표준 SQL에 가까운 SELECT, UPDATE는 비교적 쉽게 옮겨지지만, DECLARE ... HANDLER, SIGNAL, 커서 문법, 함수 특성 선언 같은 절차적 부분은 다시 써야 한다. 업무 로직이 저장 프로그램에 많을수록 DB를 바꾸는 비용은 애플리케이션 전체를 다시 쓰는 비용에 가까워진다.

    5. 가장 늘리기 어려운 자원에 일을 몰아준다

    HTTP 편과 스프링 MVC 편에서 본 것처럼, 상태를 갖지 않는 애플리케이션 서버는 인스턴스를 더 띄워 처리량을 늘릴 수 있다. DB 서버는 그렇게 늘리기 어렵다. 원본과 레플리카로 구성한 복제에서도 쓰기는 원본 한 대가 받고, 레플리카는 읽기를 나눠 받을 뿐이다. 업무 계산을 프로시저와 함수로 옮기면 그 CPU 시간은 모든 사용자의 쿼리를 처리하는 바로 그 서버에서 쓰인다. 트래픽이 늘었을 때 애플리케이션 서버는 놀고 DB 서버만 바빠지는 구조가 된다.

    6. 숨은 연쇄가 트랜잭션을 길게 만든다

    트리거가 다른 테이블을 고치고, 그 테이블의 트리거가 또 다른 일을 하는 연쇄는 모두 처음 문장의 트랜잭션 안에서 일어난다. 처음 문장 하나가 얼마나 많은 행과 테이블을 잠그는지 코드만 봐서는 알 수 없다. 교착 상태와 잠금 대기 시간 초과가 생겼을 때 원인을 추적하는 사람은 트리거 정의까지 열어 봐야 한다.

    7. 선언을 믿는 구조

    DETERMINISTIC, NO SQL, READS SQL DATA는 서버가 검사하지 않는 약속이다. 오류 1418을 없애려고 사실과 다른 특성을 붙이는 일은 쉽고, 그 결과는 복제 환경에서 늦게, 조용히 드러난다. 트리거는 아예 결정적이라고 가정된다. 규칙을 지키는 책임이 도구가 아니라 사람의 주의력에 놓여 있는 셈이다.

    흔한 오해 정리

    오해실제(MySQL 8.0 기준)
    프로시저는 미리 컴파일되어 있어서 항상 빠르다캐시는 세션별 내부 형태이고, 본문의 SQL은 보통의 SQL로 실행된다. 이득은 주로 왕복 감소에서 나오며, 커서로 행마다 처리하면 오히려 느릴 수 있다.
    트리거는 테이블의 모든 변경을 잡는다외래 키 연쇄 동작, TRUNCATE, 행 기반 복제로 레플리카에 적용되는 변경에는 발동하지 않는다.
    트리거는 변경이 끝난 뒤 따로 실행된다트리거는 발동시킨 문장 안에서 행마다 동기적으로 실행되고, 같은 트랜잭션에 속한다. 트리거가 실패하면 문장도 실패한다.
    DELIMITER는 프로시저 문법의 일부다mysql 클라이언트의 명령이다. 서버와 JDBC는 DELIMITER를 모른다.
    DETERMINISTIC을 붙이면 함수가 결정적이 된다선언일 뿐 서버는 검사하지 않는다. 사실과 다른 선언은 복제 불일치의 원인이 된다.
    프로시저 안의 START TRANSACTION은 호출자의 트랜잭션과 무관하다진행 중인 트랜잭션을 암묵적으로 커밋한다. 호출자는 그 앞의 변경을 롤백할 수 없게 된다.

    현대적 대안: 각 책임을 제자리로 보낸다

    함정의 목록을 보면 대안의 방향이 보인다. 저장 프로그램이 하던 일을 성격별로 나누고, 각 성격에 맞는 자리로 보내는 것이다. 핵심 질문은 "이 로직은 무엇인가"다. 데이터가 어떤 경로로 들어오든 항상 참이어야 하는 규칙인가, 특정 업무 절차인가, 다른 시스템에 변경을 알리는 일인가.

    요구저장 프로그램으로 하던 방식대안대안의 근거와 주의점
    여러 문장을 묶은 업무 절차(주문 처리)저장 프로시저애플리케이션 서비스 계층에서 트랜잭션으로 묶는다코드 저장소, 리뷰, 테스트, 배포 흐름 안으로 들어오고 서버를 늘려 확장할 수 있다. 왕복이 늘어나므로 잠금을 거는 문장을 트랜잭션의 뒤쪽에 두는 등 잠금 유지 시간을 의식해야 한다.
    한 행 안의 값 규칙(수량 1 이상, 재고 0 이상)BEFORE 트리거와 SIGNALNOT NULL, CHECK 제약(8.0.16부터 검사)선언적이라 읽기 쉽고, 어떤 경로로 들어온 데이터에도 적용된다. 다만 CHECK 식에는 다른 테이블의 열, 저장 함수, 서브쿼리, 변수를 쓸 수 없다.
    테이블 사이의 참조 규칙트리거로 존재 여부 검사외래 키 제약엔진이 직접 보장한다. 외래 키의 참조 동작(ON DELETE 등)에 쓰이는 열에는 CHECK 제약을 걸 수 없다는 제한이 있다.
    변경 이력·감사AFTER 트리거애플리케이션이 같은 트랜잭션 안에서 이력을 기록하거나, 바이너리 로그를 읽는 변경 데이터 캡처(CDC)를 쓴다CDC는 커밋된 변경을 트랜잭션 바깥에서 읽으므로 원래 트랜잭션을 길게 만들지 않는다. 대신 이력이 조금 늦게 도착하고, 별도의 인프라가 필요하다.
    다른 시스템에 변경 알리기트리거에서 알림 테이블에 기록CDC, 또는 같은 트랜잭션에 이벤트 행을 기록하고 별도 과정이 전달하는 아웃박스(outbox) 방식알릴 내용이 애플리케이션 코드에 드러나고, 전달 실패와 재시도를 애플리케이션 쪽에서 다룰 수 있다.
    값 계산(할인가, 상태 문자열)저장 함수애플리케이션 코드, 또는 쿼리 안의 CASE 식행마다 숨은 쿼리를 실행하는 함수를 피하고, 계산 규칙을 테스트할 수 있다.
    대량 데이터 가공커서 반복 프로시저집합 기반 SQL 한 문장, 또는 배치 애플리케이션엔진이 실행 계획을 고를 수 있고, 처리 단위와 재시작을 통제할 수 있다.

    CDC는 이름 그대로 데이터의 변경을 잡아내는 방식이다. 예를 들어 Debezium의 MySQL 커넥터 문서는 이 커넥터가 바이너리 로그를 읽어 행 단위 변경 이벤트를 만들고, 그것을 Kafka 토픽으로 보내면 클라이언트 애플리케이션이 그 토픽을 읽는다고 설명한다. 앞에서 본 행 기반 바이너리 로그가 여기서 다시 쓰인다. 트리거가 트랜잭션 안에서 동기적으로 하던 "변경을 따라가는 일"을, 로그를 읽는 별도의 과정이 트랜잭션 밖에서 비동기적으로 하는 것이다. 애플리케이션에서 이력을 기록하는 방식은 이후 권에서 다룰 스프링의 트랜잭션 관리와 JPA의 엔티티 생명주기 콜백(@PrePersist, @PreUpdate 등)으로 구현할 수 있다.

    그렇다고 저장 프로그램을 쓸 자리가 없어진 것은 아니다. 다음 조건에서는 여전히 합리적인 선택이다. 첫째, 데이터 이동 비용이 지배적인 일이다. 수백만 행을 읽어 집계하고 다시 쓰는 정기 작업을 애플리케이션으로 옮기면 그 행들이 모두 네트워크를 건너야 한다. 이때도 먼저 집합 기반 SQL로 쓸 수 있는지 보고, 여러 문장의 순서가 필요할 때 프로시저로 묶는다. 둘째, DBA가 소유하는 운영 작업이다. 데이터 정리, 파티션 관리처럼 애플리케이션의 업무 로직과 무관한 일이다. 셋째, EXECUTE 권한으로 만드는 보안 경계가 꼭 필요한 경우다. 넷째, 이미 저장 프로그램에 기대어 돌아가는 기존 시스템과 함께 일해야 하는 경우다. 어느 경우든 정의를 저장소에 파일로 두고, 마이그레이션 도구로 배포하고, 트리거는 작게 유지하며 업무 분기를 넣지 않는다는 원칙을 지키면 앞의 함정 대부분을 줄일 수 있다.

    저장 프로그램 하나에 몰려 있던 책임이 성격별로 세 자리로 나뉘는 모습을 보여 준다. 왼쪽에 큰 상자 하나 "DB 안의 저장 프로그램"이 있고 그 안에 작은 라벨 네 개가 쌓여 있다: "업무 절차", "값 규칙", "변경 이력", "대량 가공". 오른쪽에는 세 개의 상자가 세로로 놓여 있다: 위 "애플리케이션 서비스 계층(트랜잭션)", 가운데 "선언적 제약(NOT NULL, CHECK, 외래 키)", 아래 "바이너리 로그 → CDC". 왼쪽 상자의 "업무 절차" 라벨에서 위 상자로, "값 규칙"에서 가운데 상자로, "변경 이력"에서 아래 상자로 화살표가 간다. "대량 가공"에서는 짧은 화살표가 왼쪽 상자 아래의 작은 상자 "집합 기반 SQL"로 간다. 평면 도해, 흰 배경, 상자마다 다른 옅은 색. 대안의 핵심은 저장 프로그램을 없애는 것이 아니라 책임마다 맞는 자리를 찾아 주는 것이다.

    정리: 기본편의 도구들이 한 자리에 모인다

    이 회차는 데이터베이스 기본편의 마지막 회차다. 돌아보면 저장 프로그램은 앞 회차의 도구들이 한 자리에 모이는 곳이었다. 프로시저 안의 SELECT ... INTO는 01~03회의 조인과 서브쿼리를 그대로 쓰고, 함수 안의 CASE는 04회의 식이며, WHERE 절의 함수가 인덱스를 막는 이유는 05·06회의 B+Tree 구조에서 나왔다. 트리거와 CHECK 제약 가운데 무엇을 고를지는 07회의 무결성 이야기였고, 프로시저의 FOR UPDATE와 START TRANSACTION, 트리거의 롤백은 08회의 트랜잭션과 잠금 위에서 동작했다.

    기억할 것을 세 문장으로 줄이면 이렇다. 저장 프로시저·함수·트리거의 차이는 누가 실행시키는가에서 나오고, 함수와 트리거의 제약은 "다른 문장의 한가운데에서 돈다"는 사실에서 나온다. MySQL은 저장 프로그램을 세션별 캐시에 내부 형태로 두고 실행하며, 그 실행은 호출한 쪽의 트랜잭션·잠금·바이너리 로그와 하나로 엮인다. 업무 로직을 DB에 둘지는 왕복 감소라는 이득과 보이지 않는 로직, 배포·테스트·확장의 어려움이라는 비용을 비교해 정하고, 데이터 규칙은 선언적 제약으로, 업무 절차는 애플리케이션으로, 변경 추적은 로그 기반 도구로 보내는 것이 오늘날의 일반적인 배치다.

    이후 권에서는 이 경계의 반대편, 곧 애플리케이션 쪽으로 넘어간다. JDBC가 연결을 맺고 문장을 보내는 과정, 커넥션 풀, 스프링이 트랜잭션의 경계를 정하는 방법, JPA가 객체와 테이블을 잇는 방법을 다룰 때, 이 회차에서 본 왕복, 트랜잭션 경계, 영속성 컨텍스트가 모르는 변경이라는 주제가 다시 등장한다.
    저장 프로그램(stored program)
    DB 서버에 저장해 두고 실행하는 코드. MySQL에는 저장 프로시저, 저장 함수, 트리거, 이벤트가 있고, 차이는 누가 언제 실행시키는가(CALL, 식 안의 호출, 행 변경, 예약 시각)에서 나온다.
    DELIMITER
    mysql 명령줄 클라이언트의 문장 구분자를 바꾸는 클라이언트 명령. 본문 안의 세미콜론을 서버로 그대로 넘기기 위해 쓰며, 서버와 JDBC는 이 명령을 모른다.
    IN, OUT, INOUT
    프로시저 매개변수의 복사 시점. IN은 들어올 때만, OUT은 나갈 때만(안에서는 NULL로 시작), INOUT은 들어올 때와 나갈 때 모두 호출자 변수와 값을 주고받는다. 함수의 매개변수는 항상 IN이다.
    핸들러와 SIGNAL
    DECLARE ... HANDLER는 오류·경고·데이터 없음 상태를 잡아 CONTINUE 또는 EXIT로 처리하고, SIGNAL은 직접 오류를 일으킨다. SQLSTATE '45000'은 사용자 정의 예외이며 기본 오류 번호는 1644다.
    함수 특성과 바이너리 로그
    바이너리 로그가 켜진 MySQL 8.0에서는 함수에 DETERMINISTIC, NO SQL, READS SQL DATA 중 하나를 선언해야 하며(없으면 오류 1418), 서버는 그 선언이 사실인지 검사하지 않는다.
    트리거 실행 순서
    행마다 BEFORE 트리거, 행 변경, AFTER 트리거 순으로 문장 안에서 동기적으로 실행된다. 어느 단계든 실패하면 문장 전체가 실패하고 InnoDB에서는 문장의 변경이 모두 롤백된다.
    트리거가 발동하지 않는 경우
    외래 키 연쇄 동작, TRUNCATE와 DROP TABLE, 행 기반 복제로 레플리카에 적용되는 원본의 변경에는 트리거가 발동하지 않는다.
    세션별 저장 프로그램 캐시
    서버는 저장 프로그램 본문을 내부 형태로 변환해 세션마다 따로 캐시하고, 세션이 끝나면 버리며, 참조 객체의 메타데이터가 바뀌면 영향받은 문장을 다시 파싱한다.
    로직 배치의 기준
    데이터가 항상 지켜야 할 규칙은 선언적 제약으로, 업무 절차는 애플리케이션 트랜잭션으로, 변경 추적은 바이너리 로그 기반 CDC로 보내고, 데이터 이동 비용이 지배적인 일에만 DB 안의 처리를 고려한다.

    장애 분석에서 이 회차의 지식이 가장 먼저 쓰이는 곳은 "애플리케이션 코드에 없는 변경"이다. 테이블에 누가 넣었는지 모를 행이 생기거나, 단순한 UPDATE 한 문장이 예상보다 오래 잠금을 쥐거나, 교착 상태 로그에 애플리케이션이 건드리지 않는 테이블이 등장하면 가장 먼저 INFORMATION_SCHEMA.TRIGGERS를 조회해 그 테이블에 붙은 트리거를 확인한다. 반대로 트리거로 구현한 감사 기록에 빈틈이 있다는 보고를 받으면, 외래 키 연쇄 삭제나 TRUNCATE처럼 트리거가 발동하지 않는 경로로 데이터가 바뀌지 않았는지부터 본다.

    설계 결정에서는 "이 로직을 프로시저로 옮기면 빨라지지 않을까"라는 제안을 자주 만난다. 이때 판단 기준은 이득이 어디서 오는지다. 왕복이 많고 문장 사이에 잠금을 오래 쥐는 절차라면 프로시저가 실제로 도움이 된다. 하지만 같은 이득을 애플리케이션 쪽에서 얻는 방법, 예를 들어 여러 행을 한 문장으로 처리하거나 잠금을 거는 문장을 트랜잭션의 뒤쪽으로 옮기는 방법이 있는지 먼저 따져 본다. 계산이 무거운 일이라면 DB 서버의 CPU가 모든 사용자가 함께 쓰는 자원이라는 점이 판단을 바꾼다. 애플리케이션 서버는 늘릴 수 있지만 원본 DB는 늘리기 어렵다.

    조건에 따라 판단이 달라지는 지점도 분명히 해 둔다. 여러 애플리케이션이 같은 DB를 직접 고치는 환경이라면, 데이터 규칙을 한 애플리케이션 코드에만 두는 것은 위험하다. 이때는 CHECK와 외래 키 같은 선언적 제약이 첫 번째 답이고, 제약으로 표현할 수 없는 테이블 간 규칙에 한해 트리거가 정당화될 수 있다. 반대로 하나의 서비스가 자기 DB를 독점하는 구조라면 업무 규칙은 그 서비스의 코드에 두고 DB에는 선언적 제약만 두는 편이 테스트와 배포를 단순하게 만든다. 이미 운영 중인 시스템에 저장 프로그램이 있다면 한 번에 걷어내기보다, 정의를 저장소로 가져와 버전 관리부터 시작하는 것이 현실적인 첫걸음이다.

    1번. START TRANSACTION 후 SELECT ... FOR UPDATE가 키보드 행을 잠그고 재고 5, 가격 55000을 읽는다. IF 검사는 5 < -2가 거짓이므로 통과한다. UPDATE는 재고를 5 − (−2) = 7로 바꾸고, 재고가 바뀌었으므로 AFTER UPDATE 트리거가 stock_log에 (1, 5, 7)을 넣는다. 이어서 INSERT INTO orders가 BEFORE INSERT 트리거를 발동시키고, 수량 −2가 1 미만이므로 SIGNAL이 오류를 낸다. 이 오류는 프로시저의 EXIT 핸들러가 잡아 ROLLBACK을 실행하므로, 앞의 UPDATE와 트리거가 넣은 이력 행까지 모두 되돌려진다. RESIGNAL로 다시 던진 오류를 클라이언트는 ERROR 1644 (45000): 주문 수량은 1 이상이어야 합니다로 받는다. 세 테이블은 호출 전과 같다(키보드 재고 5, 이력 3행, 주문 2건). 트리거가 없었다면 음수 주문이 들어가고 재고가 늘어났을 것이다. 프로시저의 검사를 p_quantity <= 0까지 넓히거나, orders에 CHECK (quantity > 0)을 두는 것이 더 직접적인 방어다.

    2번. 들어올 때 INOUT인 x에는 3이 복사되고, OUT인 y는 호출자가 100을 넘겼어도 NULL로 시작한다. 그래서 첫 SELECT는 3, NULL이다. SET y = x로 y는 3, SET x = x + y로 x는 6이 된다. 끝날 때 두 값이 모두 호출자에게 복사되므로 @x는 6, @y는 3이다. 호출 전의 100은 프로시저 안으로 전달되지 않았다는 점이 OUT의 핵심이다.

    3번. order_id 1은 이미 있으므로 키가 중복된다. 매뉴얼의 규칙에 따라 BEFORE INSERT가 먼저 발동하고, 중복이 확인되면 BEFORE UPDATE, AFTER UPDATE가 차례로 발동한다. AFTER INSERT는 발동하지 않는다. order_id가 99라면 중복이 없으므로 BEFORE INSERT 다음에 AFTER INSERT가 발동하고 UPDATE 트리거는 발동하지 않는다. 두 경우 모두 BEFORE INSERT는 실행된다는 점에 주의한다. BEFORE INSERT 트리거에 "새 주문 알림 기록" 같은 부수 효과를 넣었다면 중복 키로 UPDATE가 된 행에 대해서도 그 효과가 남는다.

    4번. 매뉴얼은 연쇄된 외래 키 동작이 트리거를 발동시키지 않는다고 정한다. 부모 행의 DELETE는 product의 트리거를 발동시키지만, CASCADE로 지워진 자식 행에 대해서는 자식 테이블의 DELETE 트리거가 실행되지 않는다. 대안은 첫째, 애플리케이션이 부모를 지우기 전에 자식 행을 명시적인 DELETE로 지우게 하는 것이다. 그러면 자식 테이블의 트리거가 발동한다. 둘째, 이력 기록 자체를 트리거에서 떼어 내 애플리케이션의 같은 트랜잭션에서 기록하거나, 바이너리 로그를 읽는 CDC로 옮기는 것이다. 어느 쪽이든 "삭제가 일어나는 모든 경로"를 먼저 나열해 보는 것이 출발점이다.

    5번. 커서 버전은 대상 행마다 UPDATE를 한 번씩 실행하므로 UPDATE 문장이 N번 실행되고, 커서를 여는 SELECT가 한 번 더 있다. 한 문장 버전 UPDATE product SET stock = stock + 10 WHERE stock < 5는 문장 하나가 조건에 맞는 행을 찾아 고친다. 커서 반복은 "바깥 결과의 행마다 안쪽 작업을 한 번씩"이라는 중첩 루프를 엔진 밖에서 손으로 짠 것과 같다. 엔진 안의 루프는 옵티마이저가 접근 방법을 고르고 한 번의 스캔으로 처리할 수 있지만, 손으로 짠 루프는 문장마다 실행기를 다시 거치고 기본 키 인덱스를 매번 위에서부터 내려간다. N이 커질수록 차이가 커진다.

END 블록을 트랜잭션 시작으로 해석하기 때문이다 DELIMITER는 mysql 클라이언트의 명령으로, 클라이언트가 입력을 어디서 잘라 서버로 보낼지를 정한다. 서버는 이 단어를 받지 않으며 본문을 //로 나누지도 않는다. JDBC는 문자열 전체를 문장 하나로 보내므로 DELIMITER를 쓰지 않는다. BEGIN ... END 복합문의 BEGIN은 저장 프로그램 안에서 블록의 시작으로 해석되며, DELIMITER와는 무관하다. 부모 테이블 product와 자식 테이블 review가 ON DELETE CASCADE 외래 키로 연결되어 있고, review에 AFTER DELETE 트리거가 있다. DELETE FROM product WHERE product_id = 1로 리뷰 3개가 함께 지워졌을 때 review의 트리거는 몇 번 발동하는가? 3번. 지워진 행마다 한 번씩 발동한다 1번. 연쇄 삭제는 문장 하나로 취급되므로 한 번만 발동한다 0번. 연쇄된 외래 키 동작은 트리거를 발동시키지 않는다 product에 DELETE 트리거가 있을 때만 3번 발동한다 MySQL 매뉴얼은 연쇄된 외래 키 동작이 트리거를 발동시키지 않는다고 명시한다. MySQL의 트리거는 행 단위이므로 "문장 하나로 한 번"이라는 보기도 틀렸고, 부모 테이블의 트리거 유무는 자식 테이블 트리거의 발동과 관계가 없다. 연쇄 삭제의 이력이 필요하면 자식 행을 명시적으로 지우거나 이력 기록을 트리거 밖으로 옮겨야 한다. 바이너리 로그 형식이 행 기반(ROW)인 원본과 레플리카에 같은 AFTER UPDATE 이력 트리거가 정의되어 있다. 원본에서 UPDATE가 한 행을 고쳐 트리거가 이력 한 행을 넣었다. 복제가 끝난 뒤 레플리카의 이력 테이블에 이 변경으로 생긴 행은 몇 개인가? 1개. 원본의 트리거가 넣은 행이 행 변경으로 복제되고, 레플리카의 트리거는 원본에서 온 변경에 발동하지 않는다 2개. 복제된 이력 행 하나와 레플리카의 트리거가 넣은 행 하나가 생긴다 1개. 원본의 이력 행은 복제되지 않고 레플리카의 트리거가 새로 넣는다 0개. 트리거가 넣은 행은 바이너리 로그에 기록되지 않는다 행 기반 로깅에서는 트리거가 바꾼 행도 행 변경으로 기록되고, 레플리카의 트리거는 원본에서 온 문장에 의해 발동하지 않는다. 그래서 이력은 정확히 한 번 들어간다. 레플리카의 트리거가 발동하는 것은 문장 기반 복제일 때이며, 그때는 로그에 이력 행이 따로 기록되지 않고 문장만 기록된다. 애플리케이션이 트랜잭션을 열고 고객 등급을 UPDATE한 뒤, 같은 연결에서 내부에 START TRANSACTION ... COMMIT이 있는 프로시저를 호출했다. 프로시저가 끝난 뒤 애플리케이션이 ROLLBACK을 실행하면 고객 등급 변경은 어떻게 되는가? 되돌려진다. ROLLBACK은 연결에서 일어난 모든 변경을 되돌린다 되돌려진다. 프로시저 안의 트랜잭션은 중첩 트랜잭션이라 바깥 트랜잭션에 포함된다 프로시저 안의 변경만 되돌려지고 고객 등급 변경은 남는다 남는다. 프로시저의 START TRANSACTION이 진행 중이던 트랜잭션을 암묵적으로 커밋했기 때문이다 MySQL에서 START TRANSACTION과 BEGIN은 현재 세션에서 진행 중인 트랜잭션을 COMMIT한 것처럼 암묵적으로 끝낸다. 중첩 트랜잭션이 아니다. 고객 등급 변경은 프로시저의 첫 문장에서 커밋되었고, 프로시저 안의 변경도 프로시저의 COMMIT으로 확정되었으므로 이후의 ROLLBACK이 되돌릴 것은 없다. 트랜잭션 경계를 애플리케이션과 프로시저가 나눠 가지면 이런 문제가 생긴다. 바이너리 로그가 켜진 MySQL 8.0에서 CREATE FUNCTION f(x INT) RETURNS INT RETURN x + 1;이 오류 1418로 거부되었다. 이 상황에 대한 설명으로 옳은 것은? 서버가 함수 본문을 분석해 비결정적인 코드를 찾았기 때문이다 DETERMINISTIC, NO SQL, READS SQL DATA 중 아무것도 선언하지 않았기 때문이며, 서버는 선언을 요구할 뿐 선언이 사실인지는 검사하지 않는다 함수 본문에 세미콜론이 없어 DELIMITER를 바꾸지 않았기 때문이다 함수는 RETURNS 대신 OUT 매개변수로 값을 돌려줘야 하기 때문이다 오류 1418은 바이너리 로그가 켜져 있을 때 함수의 결정성·데이터 접근 특성 선언이 없으면 나는 오류다. 기본값은 NOT DETERMINISTIC과 CONTAINS SQL이므로 아무것도 쓰지 않으면 조건을 채우지 못한다. 매뉴얼은 서버가 DETERMINISTIC 선언의 진위를 검사하지 않는다고 밝힌다. 이 함수는 본문에 세미콜론이 없어 DELIMITER가 필요 없고, 함수의 매개변수는 항상 IN이며 값은 RETURN으로 돌려준다.
    저장 프로시저(stored procedure)
    DB 서버에 저장해 두고 CALL 문으로 실행하는 루틴. IN·OUT·INOUT 매개변수와 결과 집합으로 값을 주고받고, 내부에서 트랜잭션을 시작하고 끝낼 수 있다.
    저장 함수(stored function)
    값 하나를 RETURN으로 돌려주고 SQL 식 안에서 호출되는 루틴. 결과 집합 반환, 트랜잭션 제어, 동적 SQL, 재귀를 쓸 수 없다.
    트리거(trigger)
    테이블에 붙어, 행이 삽입·수정·삭제될 때 BEFORE 또는 AFTER 시점에 행마다 자동으로 실행되는 코드. 발동시킨 문장과 같은 트랜잭션에 속한다.
    핸들러(handler)
    저장 프로그램 안에서 특정 SQLSTATE나 오류 부류(SQLEXCEPTION, SQLWARNING, NOT FOUND)가 생겼을 때 실행할 코드와 이후 동작(CONTINUE, EXIT)을 정하는 선언.
    커서(cursor)
    SELECT 결과를 한 행씩 꺼내 처리하게 하는 저장 프로그램의 구성 요소. MySQL에서는 읽기 전용이고 앞으로만 이동하며, 결과의 사본 여부가 정해져 있지 않다.
    정의자 보안(DEFINER security)
    루틴이나 트리거 안의 문장을 호출자가 아니라 정의한 계정의 권한으로 검사하는 방식. 저장 루틴의 SQL SECURITY 기본값이다.
    바이너리 로그(binary log)
    데이터를 바꾼 내용을 문장 또는 행 단위로 기록하는 MySQL의 로그. 복제와 시점 복구에 쓰이며, MySQL 8.0에서는 기본으로 켜지고 기본 형식은 행 기반이다.
    변경 데이터 캡처(Change Data Capture, CDC)
    DB의 커밋된 변경을 로그 등에서 읽어 다른 시스템으로 전달하는 방식. MySQL에서는 바이너리 로그를 읽는 도구로 구현한다.
