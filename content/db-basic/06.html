    이 회차의 질문: 인덱스를 만들었는데 왜 여전히 느린가

    05회에서 인덱스의 뼈대를 세웠다. InnoDB의 인덱스는 B+Tree이고, 키가 정렬된 상태로 리프 페이지에 들어 있으며, 리프 페이지끼리는 서로 연결되어 있어 한 지점을 찾은 뒤에는 옆으로 훑어 나갈 수 있다. 테이블 자체는 기본 키 순서로 행 전체를 저장한 클러스터형 인덱스(clustered index)이고, 그 밖에 만드는 인덱스는 모두 보조 인덱스(secondary index)다. 이 회차는 그 구조를 출발점으로 삼는다.

    구조를 알아도 실무에서는 설명하기 어려운 장면을 계속 만난다. 분명히 인덱스를 만들었는데 EXPLAIN을 찍어 보면 type 열에 ALL이 나와 테이블을 처음부터 끝까지 읽는다. WHERE 절은 그대로 두고 SELECT 목록에서 열 하나를 뺐을 뿐인데 쿼리가 몇 배 빨라진다. 열 두 개로 만든 인덱스를 어떤 쿼리는 잘 쓰는데, 조건 순서만 다른 것처럼 보이는 다른 쿼리는 쓰지 못한다. 잘 돌던 쿼리에 ORDER BY 하나를 붙였더니 Extra 열에 Using filesort가 나타난다.

    이 장면들은 모두 두 가지 사실에서 나온다. 첫째, B+Tree 인덱스는 결국 정렬된 목록이다. 정렬 순서를 이용할 수 있는 조건만 탐색 범위를 줄일 수 있고, 정렬 순서와 맞는 ORDER BY만 정렬을 생략할 수 있다. 둘째, MySQL의 옵티마이저는 비용을 추정해 계획을 고른다. 인덱스가 있다는 것은 선택지가 하나 늘었다는 뜻일 뿐이고, 그 선택지가 더 싸다고 판단될 때만 쓰인다. 이 두 사실을 손에 쥐면 위의 장면을 하나씩 예측할 수 있다.

    순서는 이렇다. 먼저 옵티마이저가 무엇을 근거로 인덱스를 고르고 버리는지 본다. 이어서 테이블에 가지 않고 인덱스만으로 답하는 커버링 인덱스를 다룬다. 그다음 세 단계에 걸쳐 복합 인덱스를 파고든다. 열 순서가 정렬을 어떻게 만드는지, 범위 조건이 왜 뒤의 열을 무력하게 만드는지, ORDER BY와 LIMIT을 어떻게 인덱스에 맡기는지다. 마지막으로 설계 가이드라인, 인덱스의 비용과 함정, 그리고 쿼리 묶음으로 인덱스를 직접 설계하는 연습으로 마무리한다. 기준은 MySQL 8.0의 InnoDB이고, 8.4에서 기본값이 바뀐 부분은 따로 밝힌다. 제약 조건과 인덱스의 관계는 07회, 잠금과 MVCC는 08회의 몫이라 여기서는 맞닿는 지점만 짚는다.

    이 회차 내내 쓰는 예제 테이블은 다음과 같다. 주문 테이블에 회원 번호, 주문 상태, 주문 날짜, 금액, 메모가 있고, 기본 키는 자동 증가하는 주문 번호다.

    CREATE TABLE orders (
  order_id   BIGINT       NOT NULL AUTO_INCREMENT,
  member_id  INT          NOT NULL,
  status     VARCHAR(10)  NOT NULL,   -- 'PAID', 'SHIPPED', 'DONE', 'CANCELED'
  order_date DATE         NOT NULL,
  amount     INT          NOT NULL,
  memo       VARCHAR(200) NULL,
  PRIMARY KEY (order_id),
  INDEX idx_member_date (member_id, order_date)
) ENGINE=InnoDB;

    설명을 위해 주문이 수백만 건, 회원이 10만 명쯤 있고, 주문 대부분이 결국 'DONE' 상태가 된다고 가정한다. 이 수치는 상황을 그리기 위한 가정일 뿐 어떤 측정값도 아니다. 이 회차의 실측 결과는 이 테이블에 주문 100만 건(회원 번호 1~100000 무작위, 85%가 'DONE'이고 나머지 세 상태가 각 5%, 날짜는 2023-01-01~2024-12-31 무작위)을 넣고 MySQL 8.4.13과 8.0.46에서 실행한 것이다. rows, filtered, cost, 실행 시간 같은 값은 실행 환경과 통계에 따라 달라지므로, 본문의 판단은 계획의 모양(어떤 인덱스를 어떤 방식으로 쓰는가)에서 결정되는 열에 기댄다.

    옵티마이저와 인덱스 선택: 무엇을 근거로 고르는가

    SQL은 선언적 언어다. WHERE member_id = 7이라고 쓰면 "회원 7의 주문"이라는 결과를 정의할 뿐, 그것을 어떻게 찾을지는 말하지 않는다. 같은 결과를 내는 방법은 여러 가지다. 클러스터형 인덱스의 리프 페이지를 처음부터 끝까지 읽으며 조건을 검사할 수도 있고(풀 테이블 스캔), idx_member_date에서 회원 7의 구간을 찾은 뒤 엔트리마다 기본 키로 행을 찾아갈 수도 있다. 이 가운데 하나를 고르는 모듈이 옵티마이저(optimizer)다.

    MySQL의 옵티마이저는 비용 기반 옵티마이저(cost-based optimizer)다. MySQL 8.0 매뉴얼의 비용 모델(cost model) 절은 옵티마이저가 쿼리 실행 중 일어나는 여러 연산의 비용 추정치에 근거해 실행 계획을 만든다고 설명한다. 비용 상수는 두 테이블에 나뉘어 있다. mysql.server_cost에는 서버 수준의 연산 비용이 있다. 레코드 조건을 평가하는 비용(row_evaluate_cost), 레코드 키를 비교하는 비용(key_compare_cost) 같은 것이다. mysql.engine_cost에는 저장 엔진 수준의 비용이 있다. 디스크에서 인덱스나 데이터 블록을 읽는 비용(io_block_read_cost), 메모리의 버퍼에서 블록을 읽는 비용(memory_block_read_cost)이다. 서버는 기동할 때 이 테이블을 읽어 메모리에 올리고, 테이블 값이 NULL이면 컴파일된 기본값을 쓴다. 기본값은 버전마다 바뀔 수 있으니 숫자를 외우기보다 자기 서버에서 직접 확인하는 편이 정확하다.

    SELECT cost_name, cost_value, default_value FROM mysql.server_cost;
SELECT engine_name, cost_name, cost_value, default_value FROM mysql.engine_cost;
    +------------------------------+------------+---------------+
| cost_name                    | cost_value | default_value |
+------------------------------+------------+---------------+
| disk_temptable_create_cost   |       NULL |            20 |
| disk_temptable_row_cost      |       NULL |           0.5 |
| key_compare_cost             |       NULL |          0.05 |
| memory_temptable_create_cost |       NULL |             1 |
| memory_temptable_row_cost    |       NULL |           0.1 |
| row_evaluate_cost            |       NULL |           0.1 |
+------------------------------+------------+---------------+
+-------------+------------------------+------------+---------------+
| engine_name | cost_name              | cost_value | default_value |
+-------------+------------------------+------------+---------------+
| default     | io_block_read_cost     |       NULL |             1 |
| default     | memory_block_read_cost |       NULL |          0.25 |
+-------------+------------------------+------------+---------------+

    cost_value가 NULL이므로 두 서버 모두 default_value 열의 컴파일된 기본값을 쓰고 있다. 버퍼 풀에 있는 블록을 읽는 비용(0.25)이 디스크에서 읽는 비용(1)보다 낮게 잡혀 있다는 점이 눈에 띈다.

    비용 계산의 재료는 결국 "몇 페이지를 읽고 몇 행을 평가하는가"다. 그런데 쿼리를 실행하기 전에는 회원 7의 주문이 몇 건인지 알 수 없다. 그래서 옵티마이저는 행 수를 추정한다. 범위 최적화(range optimization) 절은 두 가지 추정 방법을 설명한다. 하나는 인덱스 다이브(index dive)다. 구간의 양쪽 끝으로 실제로 인덱스를 내려가 보고, 그 사이에 든 행 수를 추정치로 쓴다. 정확하지만 구간이 많아질수록 추정에 드는 시간이 늘어난다. 다른 하나는 인덱스 통계(index statistics)다. 미리 계산해 둔 통계로 추정하므로 덜 정확하지만 빠르다.

    둘 사이의 전환점은 eq_range_index_dive_limit 시스템 변수가 정한다. member_id IN (3, 7, 9)처럼 값 하나짜리 구간(등치 구간, equality range)이 여럿 있을 때, 이 변수를 N + 1로 두면 등치 구간이 N개까지일 때 인덱스 다이브를 쓴다. 0으로 두면 개수와 상관없이 항상 다이브한다. 기본값은 MySQL 5.7.4에서 10에서 200으로 올라간 뒤 그대로다. 따라서 기본 설정에서는 IN 목록의 값이 199개까지는 다이브로, 200개부터는 통계로 행 수를 추정한다. 아주 긴 IN 목록을 쓰는 쿼리의 계획이 목록 길이에 따라 갑자기 바뀌는 현상은 이 전환에서 나올 수 있다.

    통계는 어디서 오는가

    통계의 핵심은 카디널리티(cardinality), 즉 인덱스 열에 서로 다른 값이 몇 개 있는가다. 행이 100만 개인 테이블에서 member_id의 카디널리티가 10만이면 값 하나에 평균 10행이 걸리고, status의 카디널리티가 4면 값 하나에 평균 25만 행이 걸린다. 조건이 걸러 내는 행의 비율을 선택도(selectivity)라고 부르는데, 카디널리티가 높을수록 등치 조건 하나가 남기는 행이 적어 선택도가 좋다. MySQL 매뉴얼은 여러 인덱스 중에서 고를 수 있으면 보통 가장 적은 행을 찾는 인덱스, 즉 가장 선택도가 좋은 인덱스를 쓴다고 설명한다.

    InnoDB는 이 통계를 디스크에 영구 저장한다. innodb_stats_persistent가 기본으로 켜져 있고, 통계는 mysql.innodb_table_stats와 mysql.innodb_index_stats 테이블에 들어간다. 통계를 계산할 때 InnoDB는 인덱스의 모든 페이지를 읽지 않는다. ANALYZE TABLE 같은 작업은 각 인덱스에서 무작위로 페이지를 표본 추출해 카디널리티를 추정하고, 표본 페이지 수는 innodb_stats_persistent_sample_pages(기본값 20)가 정한다. innodb_stats_auto_recalc가 기본으로 켜져 있어서 테이블 행의 10%를 넘게 바뀌면 통계가 자동으로 다시 계산된다.

    -- 인덱스별 통계: n_diff_pfx01은 첫 열의 서로 다른 값 수, n_diff_pfx02는 앞 두 열 조합의 수
SELECT index_name, stat_name, stat_value, stat_description
FROM mysql.innodb_index_stats
WHERE database_name = DATABASE() AND table_name = 'orders' AND stat_name LIKE 'n_diff%';

-- 대량 적재 직후처럼 통계가 현실과 어긋났다고 의심되면 즉시 다시 계산한다
ANALYZE TABLE orders;

    n_diff_pfx01, n_diff_pfx02라는 이름이 복합 인덱스의 성격을 잘 보여 준다. 통계가 "첫 열", "첫 두 열", "첫 세 열"처럼 앞에서부터 잘라 낸 열 조합 단위로 계산된다. 매뉴얼은 비고유 인덱스의 경우 InnoDB가 기본 키 열을 덧붙여 센다는 점도 밝힌다. 보조 인덱스의 엔트리에는 기본 키가 들어 있기 때문이다. 이 사실은 커버링 인덱스에서 다시 쓰인다. SHOW INDEX FROM orders의 Cardinality 열도 같은 통계에서 나온 추정치이므로 정확한 값으로 읽으면 안 된다.

    +-----------------+--------------+------------+-------------------------------+
| index_name      | stat_name    | stat_value | stat_description              |
+-----------------+--------------+------------+-------------------------------+
| PRIMARY         | n_diff_pfx01 |     994449 | order_id                      |
| idx_member_date | n_diff_pfx01 |      96789 | member_id                     |
| idx_member_date | n_diff_pfx02 |    1013905 | member_id,order_date          |
| idx_member_date | n_diff_pfx03 |    1053735 | member_id,order_date,order_id |
+-----------------+--------------+------------+-------------------------------+

    출력에 기본 키를 덧붙인 n_diff_pfx03(member_id,order_date,order_id)이 보인다. 값이 추정치라는 것도 드러난다. 실제 행은 정확히 1,000,000개이고 COUNT(DISTINCT member_id)는 99,992인데, 기본 키의 값 수는 994,449, member_id의 값 수는 96,789로 나왔다. 모든 값이 서로 다른 member_id, order_date, order_id 조합(n_diff_pfx03)은 실제 행 수보다 큰 1,053,735로 추정되었다.

    통계가 표본에서 나온 추정치라는 점이 실무에서 중요하다. 데이터를 대량으로 넣거나 지운 직후, 자동 재계산 조건(10%)에 아직 이르지 않은 상태에서는 옵티마이저가 현실과 다른 행 수로 비용을 계산할 수 있다. 계획이 이상하다고 느낄 때 인덱스 힌트를 붙이기 전에 ANALYZE TABLE로 통계부터 새로 고치는 이유다.

    인덱스가 있어도 풀 스캔을 고르는 이유

    이제 첫 번째 장면을 설명할 수 있다. status에 단일 열 인덱스 idx_status가 있고, 다음 쿼리를 실행한다고 하자.

    CREATE INDEX idx_status ON orders (status);

SELECT * FROM orders WHERE status = 'DONE';

    인덱스를 타는 계획을 따라가 보자. idx_status의 루트에서 'DONE'의 시작 지점까지 내려간 뒤 리프를 옆으로 훑는다. 그런데 보조 인덱스의 엔트리에는 status와 기본 키 order_id밖에 없다. SELECT *가 원하는 amount, memo 같은 열은 클러스터형 인덱스에만 있다. 그래서 엔트리 하나마다 그 order_id로 클러스터형 인덱스를 루트부터 다시 내려가야 한다. 'DONE'이 전체의 대부분이라면 이 왕복이 수백만 번 일어난다. 게다가 order_id 순서로 저장된 클러스터형 인덱스에서 'DONE' 행들은 여기저기 흩어져 있으므로, 왕복마다 다른 페이지를 건드리는 임의 접근이 된다.

    풀 테이블 스캔은 클러스터형 인덱스의 리프 페이지를 처음부터 끝까지 한 번씩 읽는다. 한 페이지(기본 16KB)에 행이 여러 개 들어 있으니, 페이지 하나를 읽을 때마다 여러 행을 한꺼번에 검사한다. 읽는 순서도 리프 연결을 따라가는 순차 접근이다. 결과 행이 테이블의 대부분이라면, 어차피 거의 모든 페이지를 읽게 될 인덱스 경로보다 풀 스캔이 일을 덜 한다. 반대로 WHERE member_id = 7처럼 몇십 행만 남는 조건이라면 몇십 번의 왕복이 수백만 행 검사보다 훨씬 싸다.

    경로 1: 보조 인덱스 → 클러스터형 인덱스 (행마다 왕복)

  idx_status 리프            클러스터형 인덱스 (order_id 순)
  ┌────────────────┐
  │ DONE | 3       │ ──────▶  루트 → 내부 → 리프(3이 든 페이지)
  │ DONE | 4       │ ──────▶  루트 → 내부 → 리프(4가 든 페이지)
  │ DONE | 8       │ ──────▶  루트 → 내부 → 리프(8이 든 페이지)
  │  ...  (수백만) │ ──────▶  ... 엔트리 수만큼 반복, 페이지는 흩어져 있다
  └────────────────┘

경로 2: 풀 테이블 스캔 (리프를 순서대로 한 번씩)

  클러스터형 인덱스 리프:  [1..n] → [n+1..m] → [m+1..k] → ... → [마지막]
                           페이지마다 행 여러 개를 한꺼번에 검사

    그렇다면 "몇 퍼센트부터 풀 스캔인가"를 묻고 싶어진다. MySQL 매뉴얼의 WHERE 절 최적화 절은 이 질문에 직접 답한다. 예전에는 가장 좋은 인덱스가 테이블의 30%를 넘게 걸치는지로 스캔 여부를 정했지만, 이제는 고정된 비율이 그 선택을 결정하지 않으며 옵티마이저가 테이블 크기, 행 수, I/O 블록 크기 같은 추가 요소로 추정한다고 적고 있다. 인터넷에서 자주 보이는 "20~30%를 넘으면 인덱스를 안 탄다"는 말은 지금의 MySQL에 대한 규칙이 아니라, 비용 추정의 결과를 거칠게 요약한 경험칙일 뿐이다.

    매뉴얼의 "풀 테이블 스캔 피하기" 절은 EXPLAIN의 type이 ALL로 나오는 대표적인 경우를 네 가지로 든다.

    • 테이블이 너무 작아서 키를 찾는 수고보다 그냥 훑는 편이 빠른 경우. 매뉴얼은 행이 10개 미만이고 행 길이가 짧은 테이블에서 흔하다고 적는다.
    • ON이나 WHERE 절에 인덱스 열을 쓰는 조건이 없는 경우.
    • 인덱스 열을 상수와 비교하는데, 옵티마이저가 인덱스 트리를 근거로 그 상수가 테이블의 너무 큰 부분을 덮는다고 계산한 경우.
    • 카디널리티가 낮은 키, 즉 키 값 하나에 많은 행이 걸리는 키를 쓰는 경우. 키 탐색이 많이 필요할 것이라 보고 스캔이 빠르다고 판단한다.

    예외도 있다. B-tree 인덱스 절은 인덱스를 쓰면 테이블 행의 아주 큰 비율에 접근해야 할 때 인덱스를 쓰지 않을 수 있다고 설명한 뒤, 그런 쿼리라도 LIMIT으로 일부 행만 가져온다면 반환할 몇 행을 훨씬 빨리 찾을 수 있으므로 인덱스를 쓴다고 덧붙인다. 비용은 "전체 결과를 만드는 데 드는 일"이 아니라 "이 쿼리가 실제로 요구하는 일"로 계산된다는 뜻이다. 이 성질은 뒤에서 ORDER BY와 LIMIT을 인덱스로 처리할 때 핵심이 된다.

    EXPLAIN에서 읽어야 할 열

    옵티마이저의 결정은 EXPLAIN으로 본다. MySQL 8.0의 전통적 형식 EXPLAIN은 id, select_type, table, partitions, type, possible_keys, key, key_len, ref, rows, filtered, Extra 열을 보여 준다. 인덱스를 판단할 때 중요한 것은 그중 여섯 개다.

    열뜻읽는 법
    type테이블에 접근하는 방식(조인 유형)주요 값을 좋은 것부터 나열하면 system, const, eq_ref, ref, range, index, ALL. const는 기본 키나 UNIQUE 인덱스의 모든 열을 상수와 비교할 때, ref는 비고유 인덱스나 최좌측 접두사로 같은 값을 찾을 때, range는 인덱스로 구간을 읽을 때다.
    possible_keys / key후보 인덱스 / 실제로 고른 인덱스후보에는 있는데 key가 NULL이면 옵티마이저가 인덱스를 검토하고도 버렸다는 뜻이다.
    key_len고른 인덱스에서 사용한 키의 길이(바이트)복합 인덱스의 앞쪽 몇 개 열을 탐색에 썼는지 알려 준다. NULL을 허용하는 열은 1바이트가 더해진다.
    rows검사해야 한다고 추정한 행 수InnoDB에서는 추정치다. 실제 결과 행 수가 아니다.
    filtered테이블 조건을 통과할 것으로 추정한 행의 백분율최댓값 100은 걸러지는 행이 없다는 뜻이다. rows가 1000이고 filtered가 50.00이면 다음 테이블로 넘어가는 행은 약 500이다.
    Extra추가 정보Using index(커버링), Using index condition(인덱스 조건 푸시다운), Using where(WHERE로 걸러 냄), Using filesort(추가 정렬), Using temporary(임시 테이블)

    type의 index와 ALL은 혼동하기 쉽다. ALL은 테이블 전체, 즉 클러스터형 인덱스 전체를 읽는다. index는 인덱스 트리 전체를 처음부터 끝까지 읽는다. 매뉴얼은 index가 커버링 인덱스만 읽는 경우이거나, 인덱스 순서대로 테이블 전체를 읽는 경우라고 설명한다. 둘 다 "처음부터 끝까지"이므로 구간을 좁혀 주지 않는다는 점에서는 같다.

    EXPLAIN은 추정만 보여 준다. 추정이 실제와 얼마나 다른지 보려면 MySQL 8.0.18에서 도입된 EXPLAIN ANALYZE를 쓴다. 이 문장은 쿼리를 실제로 실행하고, 실행 계획의 반복자(iterator)마다 추정 비용과 추정 행 수 옆에 첫 행까지 걸린 시간, 전체 실행 시간(밀리초), 실제로 반환한 행 수, 반복 횟수(loops)를 보여 준다. 실제로 실행하므로 오래 걸리는 쿼리는 그만큼 오래 걸린다는 점을 기억해야 한다. 출력은 MySQL 8.0.16부터 쓸 수 있는 트리 형식(FORMAT=TREE)이다. 추정 rows와 실제 rows가 몇 배씩 어긋나는 반복자가 있다면, 옵티마이저가 잘못된 숫자로 비용을 계산했다는 증거다.

    앞 절의 쿼리를 이 회차의 데이터로 직접 돌려 보면 이 도구가 왜 필요한지 보인다. idx_status를 만들고 ANALYZE TABLE을 실행한 뒤, 'DONE'이 850,104행(85%)인 상태에서 인덱스 경로와 IGNORE INDEX로 강제한 풀 스캔을 비교했다. 실행 시간, cost, 추정 rows는 실행 환경과 통계에 따라 달라진다.

    EXPLAIN ANALYZE SELECT * FROM orders WHERE status = 'DONE';
-> Index lookup on orders using idx_status (status='DONE')  (cost=52171 rows=498381) (actual time=0.0986..583 rows=850104 loops=1)

EXPLAIN ANALYZE SELECT * FROM orders IGNORE INDEX (idx_status) WHERE status = 'DONE';
-> Filter: (orders.`status` = 'DONE')  (cost=100454 rows=332254) (actual time=0.0216..237 rows=850104 loops=1)
    -> Table scan on orders  (cost=100454 rows=996763) (actual time=0.0206..168 rows=1e+6 loops=1)

    옵티마이저는 풀 스캔이 아니라 idx_status를 골랐다(EXPLAIN의 type은 ref). 원인은 추정 rows다. 인덱스 경로의 추정은 498,381행인데 실제로 돌려준 행은 850,104행이다. 498,381은 통계상 테이블 행 수 996,763의 정확히 절반이다. 이 추정으로 계산한 인덱스 경로의 비용(52171)이 풀 스캔의 비용(100454)보다 낮게 나왔지만, 실제 시간은 거꾸로 인덱스 경로가 583ms, 풀 스캔이 237ms였다. MySQL 8.0.46에서도 같은 데이터로 같은 계획(ref, 추정 498,921행)이 나왔고, 시간은 1273ms 대 286ms였다. 결과 행이 테이블의 대부분일 때 풀 스캔이 일을 덜 한다는 앞 절의 설명은 실제 시간으로 확인되지만, 옵티마이저가 그 판단을 내리려면 행 수를 제대로 추정해야 한다. 추정이 이렇게 어긋나면 type이 ALL이 아니라 ref로 나오면서 더 느린 계획이 선택된다.

    옵티마이저가 틀렸을 때: 힌트는 마지막 수단

    통계를 새로 고쳐도 옵티마이저가 나쁜 인덱스를 고집할 때가 있다. 그때 쓰는 것이 인덱스 힌트다. USE INDEX (목록)는 목록의 인덱스 중 하나만 쓰라고, IGNORE INDEX (목록)는 그 인덱스를 쓰지 말라고 알린다. FORCE INDEX는 USE INDEX처럼 동작하면서 테이블 스캔을 아주 비싼 것으로 가정한다. 그래서 지정한 인덱스로 행을 찾을 방법이 전혀 없을 때만 테이블 스캔을 한다. MySQL 8.0.20부터는 INDEX, NO_INDEX, JOIN_INDEX, ORDER_INDEX 같은 인덱스 수준의 옵티마이저 힌트가 이 역할을 넘겨받도록 추가되었고, 매뉴얼은 USE/FORCE/IGNORE INDEX가 앞으로 폐기될 것으로 예상하라고 적는다.

    -- 인덱스 힌트(8.0에서 동작하지만 장차 폐기 예정)
SELECT * FROM orders FORCE INDEX (idx_member_date) WHERE member_id = 7;

-- 8.0.20부터의 옵티마이저 힌트 형식
SELECT /*+ INDEX(orders idx_member_date) */ * FROM orders WHERE member_id = 7;

    힌트는 데이터 분포를 코드에 고정한다. 오늘은 맞는 판단이 데이터가 바뀐 1년 뒤에는 틀릴 수 있는데, 힌트는 그때도 같은 계획을 강요한다. 그래서 순서를 지킨다. 통계를 확인하고, 쿼리와 인덱스를 고치고, 그래도 안 될 때 힌트를 쓴다.

    결과 행이 많을 때 보조 인덱스 경로는 엔트리마다 클러스터형 인덱스로 흩어진 왕복을 하고, 풀 스캔은 리프를 순서대로 한 번씩 읽는다는 대비를 보여 준다. A side-by-side technical diagram on a white background.     커버링 인덱스: 테이블에 가지 않는 조회

    앞 절의 비용 문제는 한 가지 원인으로 모인다. 보조 인덱스에 쿼리가 원하는 열이 없어서 클러스터형 인덱스로 돌아가야 했다는 것이다. 그렇다면 쿼리가 원하는 열이 모두 보조 인덱스에 있으면 어떨까. 돌아갈 이유가 없다. 인덱스 엔트리만 읽고 답을 낼 수 있다. MySQL 매뉴얼은 쿼리에 필요한 결과를 모두 제공하는 인덱스를 커버링 인덱스(covering index)라고 부르고, 쿼리가 어떤 인덱스에 포함된 열만 쓰면 선택한 값을 인덱스 트리에서 바로 가져와 더 빠르게 처리할 수 있다고 설명한다. 이때 EXPLAIN의 Extra에는 Using index가 나타난다. 테이블 행을 읽지 않고 인덱스 트리의 정보만으로 열 값을 얻었다는 뜻이다.

    InnoDB에서는 커버링의 범위가 생각보다 넓다. 매뉴얼은 보조 인덱스의 각 레코드에 인덱스로 지정한 열과 함께 그 행의 기본 키 열이 들어 있고, InnoDB가 이 기본 키 값으로 클러스터형 인덱스에서 행을 찾는다고 설명한다. 즉 idx_member_date (member_id, order_date)의 리프 엔트리는 실제로 (member_id, order_date, order_id)다. 기본 키는 정의에 쓰지 않아도 언제나 커버링에 포함된다.

    idx_member_date 리프 엔트리 (정의: member_id, order_date / 실제로 든 것: + order_id)

  member_id │ order_date │ order_id(기본 키)
  ──────────┼────────────┼──────────────────
      7     │ 2024-03-02 │   1052
      7     │ 2024-05-17 │   88410
      7     │ 2024-05-17 │   88911
      7     │ 2024-09-30 │   240017
      8     │ 2024-01-11 │   310

    이 인덱스를 기준으로 네 쿼리를 비교해 보자. 모두 같은 회원을 대상으로 한다.

    -- (1) 커버링: 필요한 열(order_id, order_date)과 조건 열(member_id)이 모두 엔트리에 있다
SELECT order_id, order_date FROM orders WHERE member_id = 7;

-- (2) 커버링 아님: amount가 엔트리에 없다
SELECT order_date, amount FROM orders WHERE member_id = 7;

-- (3) 커버링: 행의 개수만 세면 되므로 엔트리로 충분하다
SELECT COUNT(*) FROM orders WHERE member_id = 7;

-- (4) 커버링 아님: SELECT * 는 memo까지 요구한다
SELECT * FROM orders WHERE member_id = 7;

    (1)과 (3)은 인덱스를 쓰는 계획이 선택되었을 때 type이 ref, key가 idx_member_date, Extra에 Using index가 나온다. (2)와 (4)는 type과 key가 같아도 Extra에 Using index가 없다. 엔트리마다 클러스터형 인덱스를 다시 내려가기 때문이다. MySQL 8.4.13에서 실행하면 네 쿼리 모두 type ref, key idx_member_date, key_len 4였고, Extra는 (1)과 (3)이 Using index, (2)와 (4)가 NULL이었다. 회원 7의 주문이 50건이라면 차이를 셀 수 있다. 커버링인 경우 보조 인덱스를 한 번 내려간 뒤 이어진 엔트리 50개를 읽으면 끝이다. 50개의 엔트리는 대개 리프 페이지 한두 개에 몰려 있다. 커버링이 아니면 그 위에 클러스터형 인덱스 탐색 50번이 더해지고, 50개 행은 주문 시점이 제각각이라 order_id 순서의 클러스터형 인덱스에서 서로 다른 페이지에 흩어져 있을 가능성이 높다.

    커버링은 옵티마이저의 셈법 자체를 바꾼다. 앞 절에서 풀 스캔이 이긴 이유는 "엔트리마다 왕복"이었다. 커버링이면 왕복이 사라지므로, 결과 행이 많은 조건에서도 인덱스 경로가 풀 스캔과 대등하게 비교된다. 예를 들어 SELECT COUNT(*) FROM orders WHERE status = 'DONE'은 idx_status만 읽으면 되는 쿼리다. 'DONE'이 대부분이어도 읽는 대상은 (status, order_id)만 담긴 작은 인덱스의 연속 구간이다. 행 전체를 담은 클러스터형 인덱스를 다 읽는 것과 비교하면 읽을 페이지 자체가 적다.

    조건이 아예 없어도 커버링은 쓸모가 있다. SELECT member_id, COUNT(*) FROM orders GROUP BY member_id는 구간을 좁힐 조건이 없지만, 보조 인덱스를 처음부터 끝까지 읽는 계획(type이 index이고 Extra에 Using index)이 가능하다. MySQL 8.4.13에서도 이 쿼리는 idx_member_date를 type index, Extra Using index로 읽었다. 보조 인덱스 엔트리는 행 전체보다 훨씬 짧으므로, 같은 "전체 읽기"라도 클러스터형 인덱스를 읽는 풀 스캔보다 페이지 수가 적다. 게다가 인덱스는 이미 member_id 순서로 정렬되어 있어서 같은 회원의 엔트리가 연속으로 나온다. 그룹을 만들기 위한 별도의 정렬이 필요 없다.

    도서관의 색인 카드카드에 답이 적혀 있으면 서가에 가지 않는다

    도서관 색인 카드에는 보통 제목과 청구 기호만 적혀 있어서, 책의 내용을 보려면 청구 기호를 들고 서가까지 걸어가야 한다. "이 저자의 책이 몇 권인가", "그 책들의 청구 기호는 무엇인가"처럼 카드만으로 답이 나오는 질문이라면 서가에 갈 필요가 없다. 커버링 인덱스는 질문을 카드만으로 답할 수 있게 만드는 일이다. 비유가 깨지는 지점이 있다. InnoDB의 "서가"는 아무 데나 꽂힌 책장이 아니라 기본 키 순서로 정렬된 또 하나의 B+Tree이고, 카드(보조 인덱스 엔트리)에는 청구 기호(기본 키)가 빠짐없이 항상 적혀 있다. 그래서 "청구 기호만 알려 달라"는 질문은 어떤 카드로도 커버링이 된다.

    커버링 인덱스를 다룰 때의 함정

    가장 흔한 함정은 SELECT *다. 열을 하나라도 인덱스 밖에서 요구하면 커버링은 깨진다. ORM을 쓰면 이 일이 눈에 띄지 않게 일어난다. JPA로 엔티티를 조회하면 엔티티에 매핑된 모든 열을 SELECT 목록에 넣으므로, 엔티티 조회가 커버링 인덱스의 혜택을 받는 경우는 드물다. 목록 화면처럼 열 몇 개만 필요한 조회를 DTO 프로젝션으로 바꾸면 같은 인덱스로 커버링이 될 수 있다.

    반대 방향의 함정은 커버링을 위해 인덱스에 열을 계속 덧붙이는 것이다. 열을 추가할수록 엔트리가 길어지고, 페이지 하나에 들어가는 엔트리 수가 줄며, 인덱스 전체가 커져 버퍼 풀을 더 차지한다. 그 열이 자주 바뀐다면 UPDATE마다 인덱스 엔트리도 고쳐야 한다. 커버링은 아주 자주 실행되고 결과 행이 많은 소수의 쿼리에 한정해 쓰는 무기다.

    Using index와 Using index condition도 구별해야 한다. 이름은 비슷하지만 뜻은 정반대에 가깝다. Using index는 "테이블에 가지 않았다"이고, Using index condition은 "테이블에 가기 전에 인덱스로 한 번 더 걸렀다"이다. 후자는 결국 테이블 행을 읽는다. 두 번째 복합 인덱스 절에서 자세히 본다.

    복합 인덱스 1: 여러 열을 한 줄로 정렬한다

    복합 인덱스(composite index, 매뉴얼의 용어로는 multiple-column index)는 열 여러 개를 하나의 키로 묶은 인덱스다. MySQL 매뉴얼에 따르면 인덱스 하나는 최대 16개 열로 이루어질 수 있다. 복합 인덱스를 이해하는 열쇠는 "정렬 순서"다. 리프 엔트리는 첫 번째 열로 정렬되고, 첫 번째 열이 같은 엔트리끼리는 두 번째 열로 정렬되며, 그것까지 같으면 세 번째 열로 정렬된다. 사전이 단어를 첫 글자로 정렬하고 첫 글자가 같으면 둘째 글자로 정렬하는 것과 같은 사전식 순서(lexicographic order)다. InnoDB 보조 인덱스에서는 정의한 열 뒤에 기본 키가 붙으므로, 모든 정의 열이 같은 엔트리들도 기본 키 순서로 완전히 정렬된다.

    전화번호부성으로 정렬하고, 성이 같으면 이름으로 정렬한 책

    종이 전화번호부는 (성, 이름) 복합 인덱스다. "김민수"를 찾으려면 김씨가 시작하는 페이지를 펼친 뒤 그 안에서 민수를 찾으면 된다. "김씨 전부"도 한 덩어리로 찾을 수 있다. 그런데 "이름이 민수인 사람 전부"는 이 책으로 빨리 찾을 수 없다. 민수는 김씨 구역에도, 이씨 구역에도, 박씨 구역에도 흩어져 있어서 책을 처음부터 끝까지 넘겨야 한다. 이 비유는 거의 그대로 맞지만, 한 가지가 다르다. 데이터베이스는 "책을 처음부터 넘기기"를 금지하지 않는다. 쿼리가 인덱스의 열만 요구한다면 테이블 대신 인덱스 전체를 훑는 계획(type이 index)이 여전히 가능하고, 8.0.13부터는 성의 종류가 적을 때 성마다 따로 펼쳐 보는 스킵 스캔도 있다. 다만 어느 쪽도 "민수가 시작하는 페이지로 바로 펼치기"는 아니다.

    이 정렬 순서에서 최좌측 접두사 규칙(leftmost prefix rule)이 바로 나온다. 매뉴얼의 표현으로는, 복합 인덱스가 있으면 옵티마이저는 그 인덱스의 어떤 최좌측 접두사든 행을 찾는 데 쓸 수 있다. (col1, col2, col3) 인덱스라면 (col1), (col1, col2), (col1, col2, col3)에 대해 인덱스 탐색이 가능하다. 반대로 열들이 최좌측 접두사를 이루지 않으면 MySQL은 그 인덱스로 탐색을 할 수 없다. col2 = 값이나 col2 = 값 AND col3 = 값만 있는 조건은 (col1, col2, col3)을 탐색에 쓰지 못한다.

    이유는 정렬 순서에 있다. col2의 값은 col1이 같은 엔트리끼리만 정렬되어 있다. 인덱스 전체에서 보면 col2가 특정 값인 엔트리는 col1의 값마다 하나씩 작은 무더기로 흩어져 있다. B+Tree를 루트에서 내려가려면 "어디서 시작할지"를 정해야 하는데, 첫 번째 열의 값을 모르면 내부 노드의 구분 키와 비교할 수가 없다. 시작 지점이 없으니 구간도 없다.

    매뉴얼은 (last_name, first_name) 인덱스로 이 규칙을 보여 준다. 다음 쿼리는 인덱스로 탐색할 수 있다.

    SELECT * FROM test WHERE last_name = 'Jones';
SELECT * FROM test WHERE last_name = 'Jones' AND first_name = 'John';
SELECT * FROM test WHERE last_name = 'Jones' AND (first_name = 'John' OR first_name = 'Jon');
SELECT * FROM test WHERE last_name = 'Jones' AND first_name >= 'M' AND first_name < 'N';

    다음 두 쿼리는 인덱스로 탐색하지 못한다. 첫 번째는 선두 열이 없다. 두 번째는 OR로 묶인 두 갈래 중 한쪽(first_name = 'John')이 선두 열 조건 없이 독립적으로 참일 수 있어서, last_name의 구간만으로는 결과를 다 찾을 수 없다.

    SELECT * FROM test WHERE first_name = 'John';
SELECT * FROM test WHERE last_name = 'Jones' OR first_name = 'John';

    WHERE 절에 쓰는 조건의 순서는 상관없다는 점도 짚어 두자. WHERE first_name = 'John' AND last_name = 'Jones'라고 써도 옵티마이저는 두 조건을 모아 인덱스 열 순서에 맞춰 구간을 만든다. 최좌측 접두사 규칙은 SQL 문장의 순서가 아니라 인덱스 정의의 열 순서에 대한 규칙이다.

    정렬된 목록으로 흉내 내 보기

    규칙을 숫자로 확인해 보자. 다음 자바 프로그램은 회원 100명이 30일 동안 매일 한 건씩 주문한 3,000건의 데이터로, 보조 인덱스 두 개의 리프를 정렬된 리스트로 흉내 낸다. 하나는 (member_id, order_date), 다른 하나는 (order_date, member_id)다. 날짜는 1에서 30까지의 정수로 단순화했다. lowerBound는 이진 탐색으로 시작 지점을 찾는데, B+Tree를 루트에서 리프까지 내려가는 일에 해당한다. 그다음 리스트를 앞으로 훑는 것은 리프를 옆으로 따라가는 일에 해당한다. 몇 개의 엔트리를 읽었는지(scanned)와 그중 조건을 만족한 것이 몇 개인지(matched)를 센다.

    import java.util.ArrayList;
import java.util.Comparator;
import java.util.List;

public class CompositeIndexDemo {

    // 보조 인덱스의 리프 엔트리 하나: 인덱스 열 두 개 + 기본 키
    record Entry(int k1, int k2, long pk) {}

    static final Comparator ORDER = Comparator.comparingInt(Entry::k1)
            .thenComparingInt(Entry::k2)
            .thenComparingLong(Entry::pk);

    // 정렬된 엔트리 중 (k1, k2) 이상인 첫 위치. B+Tree를 루트에서 리프로 내려가는 일에 해당한다.
    static int lowerBound(List index, int k1, int k2) {
        int lo = 0, hi = index.size();
        while (lo < hi) {
            int mid = (lo + hi) >>> 1;
            Entry e = index.get(mid);
            int c = (e.k1() != k1) ? Integer.compare(e.k1(), k1) : Integer.compare(e.k2(), k2);
            if (c < 0) lo = mid + 1; else hi = mid;
        }
        return lo;
    }

    public static void main(String[] args) {
        List memberDay = new ArrayList<>(); // INDEX (member_id, order_date)
        List dayMember = new ArrayList<>(); // INDEX (order_date, member_id)
        long pk = 1;
        for (int day = 1; day <= 30; day++) {
            for (int member = 1; member <= 100; member++) {
                memberDay.add(new Entry(member, day, pk));
                dayMember.add(new Entry(day, member, pk));
                pk++;
            }
        }
        memberDay.sort(ORDER);
        dayMember.sort(ORDER);

        // 질의 A: WHERE member_id = 7 AND order_date BETWEEN 10 AND 12
        int scanned = 0, matched = 0;
        for (int i = lowerBound(memberDay, 7, 10); i < memberDay.size(); i++) {
            Entry e = memberDay.get(i);
            scanned++;
            if (e.k1() != 7 || e.k2() > 12) break; // 구간을 벗어났다: 여기서 멈춘다
            matched++;
        }
        System.out.println("A (member_id, order_date) scanned=" + scanned + " matched=" + matched);

        scanned = 0; matched = 0;
        for (int i = lowerBound(dayMember, 10, Integer.MIN_VALUE); i < dayMember.size(); i++) {
            Entry e = dayMember.get(i);
            scanned++;
            if (e.k1() > 12) break;       // 날짜 구간을 벗어났다
            if (e.k2() == 7) matched++;   // member_id는 구간을 좁히지 못하고 걸러 내기만 한다
        }
        System.out.println("A (order_date, member_id) scanned=" + scanned + " matched=" + matched);

        // 질의 B: WHERE order_date = 10  (인덱스 (member_id, order_date)의 최좌측 접두사가 아니다)
        scanned = 0; matched = 0;
        for (Entry e : memberDay) {       // 시작 위치를 정할 수 없으니 처음부터 끝까지
            scanned++;
            if (e.k2() == 10) matched++;
        }
        System.out.println("B (member_id, order_date) scanned=" + scanned + " matched=" + matched);
    }
}
    A (member_id, order_date) scanned=4 matched=3
A (order_date, member_id) scanned=301 matched=3
B (member_id, order_date) scanned=3000 matched=100

    세 줄을 차례로 추적해 보자. 첫 줄은 (member_id, order_date) 인덱스로 질의 A를 처리한 결과다. 이진 탐색은 (7, 10) 엔트리에 바로 도착한다. 거기서부터 (7, 10), (7, 11), (7, 12)를 읽어 세 건을 찾고, 네 번째로 읽은 (7, 13)이 구간 밖이라 멈춘다. 구간이 끝났다는 사실을 알려면 구간 바로 다음 엔트리 하나를 읽어 봐야 하므로 scanned가 matched보다 1 크다. 회원 7의 10~12일 주문이 인덱스 안에서 한 덩어리로 붙어 있었기 때문에 가능한 일이다.

    둘째 줄은 같은 질의를 (order_date, member_id) 인덱스로 처리한 결과다. 선두 열이 날짜이므로 시작 지점은 "10일의 맨 앞"이다. 10일, 11일, 12일 엔트리는 각각 회원 100명분이 붙어 있으므로, 구간 안의 엔트리 300개를 모두 읽고 13일의 첫 엔트리를 하나 더 읽어 멈춘다. 그 301개 가운데 회원 7의 것은 날짜마다 하나씩 3개뿐이다. member_id = 7이라는 조건은 이 인덱스에서 구간을 좁히는 데 쓰이지 못하고, 이미 읽은 엔트리를 걸러 내는 데만 쓰였다. 같은 결과 3건을 얻는 데 75배가 넘는 엔트리를 읽은 셈이다.

    셋째 줄은 최좌측 접두사 규칙을 어긴 경우다. (member_id, order_date) 인덱스에서 날짜가 10인 엔트리는 회원마다 하나씩, 인덱스 전체에 100곳으로 흩어져 있다. 시작 지점을 정할 수 없으니 3,000개를 모두 읽었다. 실제 데이터베이스라면 옵티마이저는 이 경우 이 인덱스를 탐색에 쓰지 않고, 풀 테이블 스캔이나 다른 인덱스를 고른다.

    같은 데이터를 (member_id, order_date) 순서와 (order_date, member_id) 순서로 정렬했을 때, 같은 질의가 읽어야 하는 연속 구간의 크기가 얼마나 다른지 보여 준다.     복합 인덱스 2: 범위 조건 뒤의 열은 구간을 좁히지 못한다

    앞의 실험에서 (order_date, member_id) 인덱스는 member_id = 7을 탐색에 쓰지 못했다. 두 열이 모두 인덱스에 있고, 두 조건이 모두 WHERE에 있는데도 그랬다. 이것이 복합 인덱스에서 가장 자주 오해하는 규칙이다. MySQL 매뉴얼의 범위 최적화 절은 이렇게 정리한다. 여러 열로 된 B-tree 인덱스에서 옵티마이저는 비교 연산자가 =, <=>, IS NULL인 동안 다음 키 열을 이어서 구간을 정하는 데 쓴다. 연산자가 >, <, >=, <=, !=, <>, BETWEEN, LIKE이면 그 열까지는 쓰지만 그 뒤의 키 열은 더 이상 고려하지 않는다.

    매뉴얼의 예를 그대로 보자. 키 열이 세 개인 인덱스에 다음 조건이 걸렸다.

    key_part1 = 'foo' AND key_part2 >= 10 AND key_part3 > 10

    옵티마이저는 첫 번째 조건의 =와 두 번째 조건의 >=를 쓰고, 세 번째 조건은 구간을 만드는 데 쓰지 않는다. 만들어지는 구간은 하나다.

    ('foo', 10, -inf)  <  (key_part1, key_part2, key_part3)  <  ('foo', +inf, +inf)

구간 안에 들어오는 엔트리의 예
  ('foo', 10, 11)   조건 만족
  ('foo', 11, 0)    구간 안이지만 key_part3 > 10 을 만족하지 않는다 → 읽은 뒤 걸러 낸다
  ('foo', 11, 50)   조건 만족
  ('foo', 12, 3)    구간 안이지만 걸러 낸다

    매뉴얼도 이렇게 만들어진 구간이 원래 조건보다 많은 행을 담을 수 있다고 적고, ('foo', 11, 0)을 예로 든다. 이유는 정렬 순서로 설명된다. key_part2 >= 10인 구간 안에서 엔트리는 (key_part2, key_part3) 순서로 놓여 있다. key_part3은 key_part2가 같은 엔트리끼리만 정렬되어 있으므로, 구간 전체로 보면 key_part3 > 10인 엔트리는 key_part2의 값마다 작은 무더기로 흩어져 있다. 이것은 앞에서 본 최좌측 접두사 문제와 같은 구조다. 범위 조건이 걸린 열 뒤에서는 정렬이 "끊긴다".

    실제 서버에서는 구간의 시작점이 매뉴얼의 그림보다 조금 더 좁다. 세 열이 모두 INT NOT NULL인 (a, b, c) 인덱스를 둔 20만 행 테스트 테이블(a, b, c는 0~49의 값)에서 a = 1 AND b >= 10 AND c > 10을 MySQL 8.4.13으로 확인하면, 트리 형식 EXPLAIN은 구간을 over (a = 1 AND 10 <= b AND 10 < c)로 표시하고 key_len은 12로 나온다. b >= 10의 아래쪽 끝이 닫혀 있어서 시작 키에 c까지 넣어 (1, 10, 10) 바로 다음에서 출발한다는 뜻이다. 그래도 FORMAT=JSON의 used_key_parts는 a, b 두 개뿐이고, (1, 11, 0) 같은 엔트리는 여전히 구간 안에 있다. ICP를 끄고 세션의 Handler_read_next를 세어 보니 구간에서 읽은 행은 3,162개, 세 조건을 모두 만족한 행은 2,419개였다. 시작점만 다를 뿐, c 조건이 구간 전체를 좁히지 못하고 읽은 뒤 걸러 낸다는 결론은 같다.

    여기서 복합 인덱스 설계의 첫 번째 원칙이 나온다. 등치 조건으로 쓰는 열을 앞에, 범위 조건으로 쓰는 열을 뒤에 둔다. 등치 조건 열들이 앞에 있으면 그 값들이 모두 고정된 엔트리가 한 덩어리로 붙어 있고, 그 덩어리 안에서 범위 조건 열이 정렬되어 있으므로 범위도 연속 구간이 된다. 범위 조건 열이 앞에 오면 그 뒤의 등치 조건은 걸러 내기 용도로 전락한다. 범위 조건이 둘 이상이면 구간을 정하는 데는 그중 하나, 인덱스 정의에서 앞에 놓인 것만 쓰인다.

    IN은 범위가 아니라 등치 구간의 묶음이다

    IN은 어떨까. 매뉴얼은 col_name IN (val1, ..., valN)과 col_name = val1 OR ... OR col_name = valN을 등치 구간 비교라고 부른다. 값 하나짜리 "구간"이 여러 개 있다는 뜻이다. 그래서 member_id IN (7, 9) AND order_date BETWEEN '2024-05-01' AND '2024-05-31'은 (member_id, order_date) 인덱스에서 회원 7의 5월 구간과 회원 9의 5월 구간, 이렇게 두 개의 좁은 구간으로 처리할 수 있다. 각 구간 안에서는 member_id가 고정되어 있으니 날짜 조건도 구간을 좁히는 데 쓰인다. 범위 조건 대신 짧은 IN 목록을 쓰면 뒤의 열을 살릴 수 있다는 뜻이기도 하다. 다만 앞에서 본 것처럼 IN 목록이 길어지면 행 수 추정이 인덱스 다이브에서 통계로 바뀐다.

    key_len으로 확인하기

    구간을 정하는 데 실제로 몇 개의 열이 쓰였는지는 EXPLAIN의 key_len으로 확인한다. MySQL에서 INT는 4바이트, DATE는 3바이트로 저장되고, NOT NULL인 고정 길이 열의 key_len은 그 크기와 같다. NULL을 허용하는 열이면 매뉴얼 설명대로 1바이트가 더해진다. idx_member_date의 두 열은 모두 NOT NULL이다.

    조건typekey_len구간에 쓰인 열
    member_id = 7ref4member_id
    member_id = 7 AND order_date BETWEEN '2024-05-01' AND '2024-05-31'range7member_id, order_date
    member_id IN (7, 9) AND order_date BETWEEN '2024-05-01' AND '2024-05-31'range7member_id, order_date (구간 2개)
    member_id BETWEEN 1 AND 100 AND order_date = '2024-05-17'range7member_id만(used_key_parts). order_date는 구간의 양 끝값에만 들어가고, 구간 안에서는 걸러 내기에 쓰인다
    member_id > 0 AND member_id < 101 AND order_date = '2024-05-17'range4member_id만. order_date는 걸러 내기에만 쓰인다

    표의 값은 SELECT *로 MySQL 8.4.13에서 실행해 확인한 값이고(넷째 줄은 8.0.46에서도 같았다), 모두 옵티마이저가 idx_member_date를 고른 경우다. 둘째 줄부터 Extra에는 Using index condition이 나왔다. 넷째 줄은 주의가 필요하다. key_len이 7로 나오지만 order_date가 구간을 좁힌 것은 아니다. BETWEEN처럼 양 끝이 닫힌 범위이면 구간의 시작 키와 끝 키에 order_date까지 넣으므로 키 길이가 두 열만큼 잡힌다. 그러나 그 사이에 있는 회원 2~99의 모든 날짜 엔트리는 그대로 구간 안이다. 트리 형식 EXPLAIN은 이 구간을 over (1 <= member_id <= 100 AND order_date = '2024-05-17')로 표시하고, FORMAT=JSON의 used_key_parts는 member_id 하나만 적는다. 같은 조건을 마지막 줄처럼 열린 범위로 쓰면 key_len은 4다. 그래서 key_len이 기대보다 짧다면 인덱스는 쓰였지만 뒤쪽 열이 구간을 좁히지 못했다는 신호이지만, 범위 조건 뒤의 열이 있는 경우 key_len이 길다고 해서 그 열이 구간을 좁혔다고 단정할 수는 없다. 그때는 FORMAT=JSON의 used_key_parts를 함께 본다.

    인덱스 조건 푸시다운: 걸러 내기라도 일찍 한다

    마지막 줄의 order_date = '2024-05-17'은 구간을 좁히지 못한다. 그렇다고 아무 쓸모가 없는 것은 아니다. 이 조건은 order_date만 보면 판정할 수 있고, order_date는 인덱스 엔트리에 들어 있다. 그렇다면 클러스터형 인덱스로 행을 찾아가기 전에 엔트리 단계에서 미리 걸러 낼 수 있다. 이것이 인덱스 조건 푸시다운(Index Condition Pushdown, ICP)이다. 매뉴얼은 두 경우의 처리 순서를 다음과 같이 대비한다.

    ICP를 써도 읽는 인덱스 엔트리의 수는 같다. 구간은 여전히 회원 1~100의 모든 주문이다. 줄어드는 것은 클러스터형 인덱스로 가는 왕복이다. 매뉴얼은 ICP의 목표가 행 전체를 읽는 횟수를 줄여 I/O를 줄이는 것이라고 설명하고, 그래서 InnoDB에서는 보조 인덱스에만 ICP를 쓴다고 밝힌다. 클러스터형 인덱스는 이미 행 전체를 버퍼에 읽어 오므로 ICP가 줄일 I/O가 없기 때문이다. ICP가 쓰이면 EXPLAIN의 Extra에 Using index condition이 나온다. 행 전체를 읽어야 하는 상황이므로 Using index는 함께 나오지 않는다. ICP는 기본으로 켜져 있으며 optimizer_switch의 index_condition_pushdown 플래그로 끄고 켤 수 있다.

    MySQL 8.4.13에서 위 쿼리의 SELECT 목록만 COUNT(memo)로 바꿔 실행하고 세션의 Handler_read_next를 보면 차이가 숫자로 나온다. Handler_read_next는 저장 엔진이 인덱스 순서로 다음 행을 서버에 넘긴 횟수다. ICP를 켠 기본 상태에서는 3이었고, SET SESSION optimizer_switch='index_condition_pushdown=off'로 끈 뒤에는 923이었다. ICP를 끄면 구간 안의 엔트리마다 행을 읽어 서버로 넘기고 서버가 order_date 조건으로 버리지만, 켜면 엔트리 단계에서 조건을 통과한 것만 넘긴다. 두 경우 모두 구간은 같다. ICP를 끄면 EXPLAIN의 Extra도 Using index condition에서 Using where로 바뀐다.

    조건을 "구간 조건"과 "필터 조건"으로 나눠 생각하는 습관을 들이자. 구간 조건은 읽을 인덱스 엔트리의 양을 정하고, 필터 조건은 읽은 것 중 무엇을 버릴지 정한다. ICP는 필터 조건을 앞당겨 왕복을 줄일 뿐, 구간을 좁혀 주지는 않는다. 성능을 결정하는 것은 대개 구간 조건이다.

    복합 인덱스 3: 정렬과 LIMIT까지 인덱스에 맡기기

    인덱스가 정렬된 목록이라는 사실은 WHERE 말고도 쓸모가 있다. ORDER BY가 요구하는 순서와 인덱스의 정렬 순서가 일치하면, 인덱스를 순서대로 읽는 것만으로 이미 정렬된 결과가 나온다. 일치하지 않으면 MySQL은 행을 읽은 뒤 따로 정렬한다. 매뉴얼은 이 추가 정렬 단계를 filesort라고 부르고, EXPLAIN의 Extra에 Using filesort가 있으면 인덱스로 정렬하지 못하고 filesort를 했다는 뜻, 없으면 인덱스로 정렬을 처리했다는 뜻이라고 설명한다. filesort는 메모리 버퍼에서 정렬하는데, MySQL 8.0.12부터는 처음부터 sort_buffer_size만큼 잡지 않고 필요한 만큼 점진적으로 늘려 그 크기까지 할당한다. 결과가 메모리에 다 들어가지 않으면 디스크의 임시 파일을 쓴다. 이름에 file이 들어 있다고 해서 항상 디스크를 쓰는 것은 아니다.

    회원의 최근 주문 10건을 보여 주는 쿼리를 보자.

    SELECT order_id, order_date, amount
FROM orders
WHERE member_id = 7
ORDER BY order_date DESC
LIMIT 10;

    idx_member_date에서 member_id = 7인 엔트리는 한 덩어리로 붙어 있고, 그 안에서 order_date 순서로 정렬되어 있다. 매뉴얼의 표현으로는 key_part1이 상수이므로 인덱스로 접근한 행은 모두 key_part2 순서다. 내림차순은 인덱스를 거꾸로 읽으면 된다. 매뉴얼은 정렬하는 키 열이 모두 DESC이면 키를 역순으로 읽는다고 설명한다. 그래서 실행은 이렇게 된다. 회원 7 구간의 끝으로 내려가서 거꾸로 엔트리 10개를 읽고, 각각 클러스터형 인덱스에서 amount를 가져온 뒤 멈춘다. 회원 7의 주문이 10건이든 1만 건이든 일의 양은 거의 같다. MySQL 8.4.13과 8.0.46에서 이 쿼리의 EXPLAIN은 type ref, key_len 4이고, Extra에는 Using filesort 대신 Backward index scan이 나온다. 인덱스를 거꾸로 읽어 정렬을 대신했다는 표시다.

    정렬을 인덱스에 맡기지 못하면 이야기가 달라진다. 회원 7의 주문을 전부 찾고, 전부 정렬한 다음, 앞의 10건만 남기고 버린다. 주문이 1만 건이면 1만 건을 읽고 정렬해야 10건을 얻는다. LIMIT이 붙은 쿼리에서 인덱스 정렬이 결정적인 이유다. MySQL 8.0에는 prefer_ordering_index라는 optimizer_switch 플래그가 있는데, ORDER BY나 GROUP BY에 LIMIT이 붙은 쿼리에서 옵티마이저가 정렬되지 않은 인덱스나 filesort 대신 순서를 가진 인덱스를 쓰려고 시도하게 하는 최적화다. 기본으로 켜져 있고, 8.0.21부터는 끌 수도 있다.

    인덱스로 정렬할 수 없는 모양

    매뉴얼은 인덱스가 ORDER BY를 처리하지 못하는 경우를 여럿 든다. 서로 다른 인덱스의 열로 정렬하는 경우(ORDER BY key1, key2), 인덱스의 연속하지 않은 열로 정렬하는 경우, 행을 찾는 데 쓴 인덱스와 정렬에 필요한 인덱스가 다른 경우, 열 이름이 아닌 식으로 정렬하는 경우(ORDER BY ABS(key), ORDER BY -key)다. 여기에 복합 인덱스의 정렬 순서에서 바로 따라 나오는 두 경우를 더하자. 둘 다 앞 절의 "범위 뒤에서 정렬이 끊긴다"와 같은 이야기다.

    -- (가) 회원 둘의 주문을 날짜순으로: 정렬된 덩어리가 두 개일 뿐, 전체가 날짜순은 아니다
SELECT * FROM orders WHERE member_id IN (7, 9) ORDER BY order_date;

-- (나) 인덱스 (member_id, order_date, amount)가 있어도
--      order_date 범위 안에서는 (order_date, amount) 순이라 amount 순이 아니다
SELECT * FROM orders
WHERE member_id = 7 AND order_date >= '2024-01-01'
ORDER BY amount;

    (가)에서 인덱스를 읽으면 회원 7의 주문이 날짜순으로 나온 뒤 회원 9의 주문이 날짜순으로 나온다. 두 덩어리를 이어 붙인 것은 전체 날짜순이 아니므로 정렬 단계가 필요하다. (나)에서 구간 안의 엔트리는 날짜가 먼저 정렬 기준이고, 금액은 날짜가 같은 엔트리끼리만 정렬되어 있다. 반대로 WHERE member_id = 7 AND order_date >= '2024-01-01' ORDER BY order_date는 정렬 없이 처리된다. 범위 조건 열과 정렬 열이 같으면 구간이 곧 정렬된 결과이기 때문이다. MySQL 8.4.13에서 확인하면 (가)의 Extra는 Using index condition; Using filesort였고, (나)는 (member_id, order_date, amount) 인덱스를 만들어 두어도 옵티마이저가 idx_member_date를 골라 Using filesort가 나왔다. ORDER BY order_date로 바꾼 쿼리는 range, key_len 7로 Using filesort 없이 처리되었다.

    그래서 두 번째 원칙은 등치 조건 열 다음에 정렬 열을 둔다이다. WHERE a = ? ORDER BY b에는 (a, b)가 맞고, WHERE a = ? AND b = ? ORDER BY c에는 (a, b, c)가 맞다. 매뉴얼은 이 원리를 이렇게 일반화한다. 인덱스의 쓰이지 않은 앞부분과 ORDER BY에 추가로 나오는 열이 모두 WHERE 절에서 상수로 고정되어 있다면, ORDER BY가 인덱스와 정확히 일치하지 않아도 인덱스를 쓸 수 있다.

    SELECT *는 정렬 인덱스도 포기하게 만든다

    정렬 순서가 맞아도 옵티마이저가 인덱스를 쓰지 않을 수 있다. 매뉴얼은 인덱스가 쿼리가 접근하는 모든 열을 담고 있지 않다면, 인덱스 접근이 다른 접근 방법보다 쌀 때만 인덱스를 쓴다고 설명한다. 예를 들어 조건 없이 SELECT * FROM orders ORDER BY member_id, order_date를 실행하면, 인덱스 전체를 순서대로 훑으면서 엔트리마다 클러스터형 인덱스로 왕복하는 비용이 테이블을 한 번 훑고 정렬하는 비용보다 클 수 있다. 그러면 옵티마이저는 인덱스를 두고도 filesort를 고른다. 같은 쿼리에 LIMIT 10이 붙거나 SELECT 목록이 인덱스 열로만 이루어져 있다면 판단이 뒤집힌다. 앞의 것은 왕복 횟수를 10번으로 묶고, 뒤의 것은 왕복을 없앤다. 100만 행 데이터에서 MySQL 8.4.13으로 확인한 결과도 그랬다. 조건 없는 SELECT *는 type ALL에 Using filesort, LIMIT 10을 붙이면 idx_member_date를 type index로 읽으며 filesort가 사라졌고, SELECT member_id, order_date로 바꾸면 type index에 Using index였다.

    오름차순과 내림차순이 섞일 때: 내림차순 인덱스

    ORDER BY order_date DESC, amount ASC처럼 방향이 섞이면, 두 열이 모두 오름차순인 인덱스는 정방향으로 읽어도 역방향으로 읽어도 이 순서를 만들지 못한다. MySQL 8.0의 매뉴얼은 내림차순 인덱스(descending index)를 지원한다고 밝히며, 인덱스 정의의 DESC가 더 이상 무시되지 않고 키 값을 내림차순으로 저장하게 한다고 설명한다. 매뉴얼의 예에서 두 열 c1, c2에 방향 조합이 다른 인덱스 네 개를 만들면, 네 가지 ORDER BY 조합이 각각 자기 방향과 맞는 인덱스를 정방향으로 읽어 filesort 없이 처리된다. 그리고 한 인덱스를 거꾸로 읽으면 방향이 모두 뒤집힌 순서도 얻는다. (c1 ASC, c2 DESC) 인덱스는 ORDER BY c1 ASC, c2 DESC를 정방향으로, ORDER BY c1 DESC, c2 ASC를 역방향으로 처리할 수 있다.

    CREATE INDEX idx_date_desc_amount ON orders (order_date DESC, amount ASC);

-- 정방향으로 읽으면 이 순서가 그대로 나온다
SELECT order_date, amount FROM orders ORDER BY order_date DESC, amount ASC LIMIT 20;

    MySQL 8.4.13에서 이 쿼리는 idx_date_desc_amount를 type index, Extra Using index로 읽어 filesort 없이 처리되었다. 방향을 모두 뒤집은 ORDER BY order_date ASC, amount DESC는 같은 인덱스를 Extra Backward index scan; Using index로 거꾸로 읽었다. 인덱스를 지우면 원래 쿼리는 type ALL에 Using filesort가 된다.

    GROUP BY도 같은 원리를 따른다. 매뉴얼은 정렬이나 그룹핑이 쓸 수 있는 인덱스의 최좌측 접두사로 이루어질 때 인덱스를 써서 정렬하거나 그룹을 만든다고 설명한다. 인덱스 순서로 읽으면 같은 그룹의 엔트리가 연속으로 나오므로, 그룹을 모으기 위한 정렬이나 임시 테이블이 필요 없어진다. GROUP BY와 ORDER BY의 열 구성이 서로 다르면 임시 테이블이 필요해지는 경우가 많고, 그때 Extra에는 Using temporary가 나타난다.

    최좌측 접두사의 예외: 스킵 스캔

    지금까지는 선두 열에 조건이 없으면 탐색을 못 한다고 했다. MySQL 8.0.13부터는 이 규칙에 좁은 예외가 생겼다. 스킵 스캔(Skip Scan)이다. 매뉴얼의 예는 PRIMARY KEY(f1, f2)인 테이블에서 SELECT f1, f2 FROM t1 WHERE f2 > 40을 실행하는 경우다. 조건이 f2에만 있으므로 원래는 인덱스 전체를 훑어야 한다. 스킵 스캔은 f1의 서로 다른 값마다 범위 스캔을 한 번씩 한다. f1이 1인 구간에서 f2 > 40, f1이 2인 구간에서 f2 > 40, 이런 식이다. 선두 열의 값이 몇 종류뿐이라면, 몇 번의 짧은 범위 스캔이 인덱스 전체 스캔보다 훨씬 싸다.

    예제 테이블에 옮겨 보자. (status, order_date) 인덱스가 있고, 상태와 상관없이 6월 이후의 주문 날짜를 상태와 함께 뽑는다.

    CREATE INDEX idx_status_date ON orders (status, order_date);

SELECT status, order_date FROM orders WHERE order_date >= '2024-06-01';

    상태가 네 종류이므로 스킵 스캔은 'CANCELED', 'DONE', 'PAID', 'SHIPPED' 구간마다 한 번씩, 네 번의 범위 스캔으로 처리할 수 있다. 스킵 스캔이 쓰이면 EXPLAIN의 Extra에 Using index for skip scan이 나온다. 쓸 수 있는 조건은 까다롭다. 매뉴얼이 드는 조건을 요약하면, 쿼리가 테이블 하나만 참조하고, GROUP BY나 DISTINCT가 없고, 인덱스에 있는 열만 참조하며, 건너뛸 열 앞의 열에는 상수 등치 조건(IN 포함)만 있고, 건너뛴 열 다음 열에 범위 조건이 있어야 한다. 조건 전체는 OR 조건들을 AND로 묶은 꼴이어야 한다. 위 쿼리를 SELECT *로 바꾸면 인덱스 밖의 열을 참조하므로 스킵 스캔 대상이 아니다. MySQL 8.4.13과 8.0.46에서 위 쿼리는 type range, key_len 45(utf8mb4 VARCHAR(10)인 status의 42바이트와 DATE의 3바이트), Extra Using where; Using index for skip scan으로 나왔고, SELECT *로 바꾸면 8.4.13에서 type ALL이었다. optimizer_switch의 skip_scan 플래그가 기본으로 켜져 있지만, 실제로 쓸지는 다른 계획과 비용을 비교해 정한다.

    스킵 스캔은 설계의 목표가 아니라 안전망이다. 선두 열의 종류가 많으면 범위 스캔 횟수가 그만큼 늘어 이점이 사라진다. 자주 실행되는 쿼리라면 스킵 스캔에 기대지 말고 그 쿼리의 조건에 맞는 인덱스를 설계하는 편이 맞다.

    복합 인덱스 정리: 조건의 모양으로 판정하기

    지금까지의 규칙은 하나의 질문으로 모인다. "이 조건들로 정렬된 목록에서 연속 구간을 하나(또는 몇 개) 잘라 낼 수 있는가, 그리고 그 구간 안의 순서가 ORDER BY와 같은가." 인덱스 (a, b, c)를 기준으로 판정표를 만들면 다음과 같다. 가운데 열은 구간을 좁히는 데 쓰인 열, 오른쪽 열은 그 구간에서 정렬 없이 처리할 수 있는 ORDER BY다.

    WHERE 조건구간을 좁히는 열걸러 내기만 하는 조건정렬 없이 처리되는 ORDER BY
    a = 1a없음b / b, c
    a = 1 AND b = 2a, b없음c
    a = 1 AND b = 2 AND c = 3a, b, c없음(정렬할 것이 없다)
    a = 1 AND b > 2a, b없음b / b, c (c 단독은 안 됨)
    a = 1 AND b > 2 AND c = 3a, bc = 3 (ICP 가능)b
    a = 1 AND c = 3ac = 3 (ICP 가능)b
    a IN (1, 2) AND b = 3a, b (구간 2개)없음c는 안 됨 (덩어리가 둘)
    a > 1 AND b = 2ab = 2 (ICP 가능)a
    b = 2, b = 2 AND c = 3없음 (최좌측 접두사 아님)--
    a = 1 OR b = 2없음 (OR의 한쪽이 a 없이 참)--

    표의 마지막 두 줄에서 "없음"은 이 인덱스로 시작 지점을 정할 수 없다는 뜻이다. 그런 쿼리도 인덱스 열만 쓴다면 인덱스 전체 스캔(type이 index)이나 스킵 스캔으로 처리될 수 있고, OR의 각 갈래에 맞는 인덱스가 따로 있다면 옵티마이저가 두 인덱스의 결과를 합치는 인덱스 머지(type이 index_merge)를 고를 수도 있다. 어느 쪽이든 "선두 열 값으로 바로 내려가는 탐색"은 아니다.

    이 장의 핵심

    복합 인덱스는 열들을 사전식으로 정렬한 하나의 목록이다. 앞에서부터 등치 조건이 이어지는 동안 구간은 계속 좁아지고, 처음 나오는 범위 조건에서 좁히기가 끝난다. 그 뒤의 조건은 걸러 내기에만 쓰이고, 정렬도 거기서 끊긴다. 그래서 열 순서는 "등치 조건 열 → 범위 조건 또는 정렬 열" 순으로 놓는다. 쿼리가 요구하는 열이 모두 엔트리에 있으면(InnoDB에서는 기본 키가 늘 들어 있다) 클러스터형 인덱스로 돌아가는 왕복까지 사라진다.

    인덱스 설계 가이드라인

    원리를 설계 절차로 옮겨 보자. 아래 항목은 앞의 규칙과 MySQL 매뉴얼이 직접 권하는 내용에서 나온 것이다.

    첫째, 열이 아니라 쿼리에서 출발한다. "자주 검색되는 열에 인덱스를 건다"는 말은 절반만 맞다. 인덱스가 효과를 내는지는 열 하나가 아니라 쿼리의 모양, 즉 어떤 열이 등치 조건이고 어떤 열이 범위 조건이며 어떤 순서로 정렬하고 몇 행을 가져가는가로 정해진다. 그래서 설계는 실행 빈도가 높거나 느린 쿼리의 목록을 만드는 데서 시작한다. 쿼리마다 WHERE의 등치 조건 열, 범위 조건 열, ORDER BY와 GROUP BY 열, SELECT 목록, LIMIT 여부를 적어 두면 인덱스의 열 순서가 거의 결정된다.

    둘째, 등치 조건 열을 앞에, 범위 조건이나 정렬 열을 뒤에 둔다. 범위 조건은 구간을 좁히는 데 하나만 쓰이므로, 범위 조건이 여럿이라면 가장 많이 걸러 내는 것을 그 자리에 두고 나머지는 필터로 남긴다. 범위 조건과 정렬 열이 다르면 둘 중 하나만 인덱스의 혜택을 받는다. 결과가 적은 쿼리는 범위를, LIMIT으로 앞부분만 가져가는 쿼리는 정렬을 살리는 쪽이 대개 이득이다.

    셋째, 선택도는 언제 중요한지 구별해서 쓴다. "카디널리티가 높은 열을 앞에 두라"는 조언은 흔하지만 조건이 붙는다. 두 열 모두 등치 조건으로만 쓰는 쿼리라면 (a, b)든 (b, a)든 두 값이 모두 고정된 엔트리들은 한 덩어리로 붙어 있고, 그 덩어리의 크기는 순서와 상관없이 같다. 이 쿼리 하나만 보면 열 순서가 읽는 엔트리 수를 바꾸지 않는다. 순서를 정하는 진짜 기준은 다른 쿼리들이다. 어느 열이 단독으로도 조건에 쓰이는지(최좌측 접두사로 재사용할 수 있는지), 어느 열에 범위 조건이나 정렬이 걸리는지를 본다. 선택도는 선두 열만 조건에 쓰이는 쿼리가 있을 때, 또는 단일 열 인덱스를 고를 때 의미가 커진다. 카디널리티가 4인 status 단독 인덱스는 'DONE'처럼 흔한 값에 대해서는 풀 스캔에 질 가능성이 크지만, (status, order_date)의 선두 열로서는 뒤의 범위 조건과 함께 충분히 좁은 구간을 만든다.

    넷째, 커버링은 소수의 뜨거운 쿼리에만 쓴다. 자주 실행되고 결과 행이 많은 쿼리에서 클러스터형 인덱스로의 왕복을 없애는 효과는 크다. 하지만 열을 덧붙일 때마다 인덱스가 커지고 쓰기가 무거워진다. 결과가 LIMIT 20처럼 작게 묶이는 쿼리라면 왕복 20번을 없애려고 인덱스를 키울 이유는 약하다.

    다섯째, 겹치는 인덱스를 정리한다. (a, b)가 있으면 (a)로 하던 탐색은 (a, b)가 최좌측 접두사로 그대로 할 수 있다. 다만 InnoDB에서는 미묘한 차이가 하나 있다. (a)의 엔트리는 실제로 (a, 기본 키) 순서라서 WHERE a = ? ORDER BY 기본 키를 정렬 없이 처리하지만, (a, b)의 엔트리는 (a, b, 기본 키) 순서라서 같은 정렬을 해 주지 못한다. 이런 쿼리가 없는지 확인한 뒤 지운다. MySQL 8.0의 sys 스키마에는 중복 인덱스를 보여 주는 sys.schema_redundant_indexes 뷰와, 사용 기록이 없는 인덱스를 보여 주는 sys.schema_unused_indexes 뷰가 있다. 매뉴얼은 후자가 서버가 대표성 있는 작업량을 충분히 오래 처리한 뒤에야 의미가 있다고 경고한다.

    여섯째, 기본 키는 짧게 잡는다. 매뉴얼은 기본 키가 길면 보조 인덱스가 더 많은 공간을 쓰므로 짧은 기본 키가 유리하다고 적는다. 모든 보조 인덱스의 모든 엔트리에 기본 키가 복사되기 때문이다. 기본 키가 16바이트 문자열이면 보조 인덱스 다섯 개의 모든 엔트리가 16바이트씩 무거워진다.

    일곱째, 조인 열은 같은 타입과 크기로 맞춘다. 매뉴얼은 조인할 때 열이 같은 타입과 크기로 선언되어 있으면 인덱스를 더 효율적으로 쓸 수 있다고 설명한다. 이때 VARCHAR(10)과 CHAR(10)은 같은 크기로 보지만 VARCHAR(10)과 CHAR(15)는 아니다. 비이진 문자열 열끼리는 문자 집합도 같아야 하며, utf8mb4 열과 latin1 열을 비교하면 인덱스를 쓸 수 없다.

    여덟째, 만든 뒤에는 계획으로 검증하고, 지우기 전에는 숨겨 본다. 인덱스를 추가했으면 대상 쿼리를 EXPLAIN으로 보고 key와 key_len이 기대와 같은지, Extra에 Using filesort가 사라졌는지 확인한다. 추정과 실제가 의심스러우면 EXPLAIN ANALYZE를 쓴다. 인덱스를 지울 때는 MySQL 8.0의 보이지 않는 인덱스(invisible index)를 먼저 쓴다. ALTER TABLE orders ALTER INDEX idx_status INVISIBLE로 숨기면 옵티마이저가 그 인덱스를 무시하므로, 지운 것과 같은 상황에서 성능을 관찰할 수 있다. 매뉴얼은 큰 테이블에서 인덱스를 지웠다 다시 만드는 일은 비싸지만 보이지 않게 했다가 다시 보이게 하는 일은 빠른 제자리(in-place) 작업이라고 설명한다. 숨긴 인덱스도 행이 바뀔 때마다 계속 갱신되고, UNIQUE 인덱스라면 숨긴 상태에서도 중복을 막는다. 기본 키는 숨길 수 없다.

    인덱스의 단점과 주의사항

    인덱스는 읽기를 빠르게 하는 대가로 다른 곳에 비용을 지운다. 이 비용을 알아야 "모든 열에 인덱스를 걸면 되지 않나"라는 질문에 답할 수 있다.

    쓰기 비용

    InnoDB에서 행 하나를 INSERT하면 클러스터형 인덱스에 행을 넣고, 보조 인덱스마다 엔트리를 하나씩 넣는다. 보조 인덱스가 다섯 개면 B+Tree 여섯 개를 고친다. 각 B+Tree에서 엔트리는 정렬된 자리에 들어가야 하므로, 해당 리프 페이지를 찾아 내려가고, 페이지가 가득 찼으면 페이지를 나누는 분할까지 일어난다. DELETE도 모든 인덱스에서 엔트리를 지워야 한다.

    UPDATE는 어떤 열을 바꾸는지에 따라 다르다. 인덱스에 없는 열(memo)만 바꾸면 보조 인덱스는 건드리지 않는다. 인덱스에 든 열(order_date)을 바꾸면, 그 열을 가진 보조 인덱스에서는 정렬 위치가 달라지므로 옛 엔트리를 지우고 새 자리에 새 엔트리를 넣어야 한다. 매뉴얼도 체인지 버퍼를 설명하면서 갱신 연산은 삽입과 삭제의 조합이라고 적는다. 기본 키를 바꾸면 사정이 가장 나쁘다. 모든 보조 인덱스 엔트리에 기본 키가 들어 있으므로 모든 보조 인덱스의 엔트리가 바뀐다. 기본 키를 바뀌지 않는 값으로 잡는 이유가 여기에도 있다.

    InnoDB에는 이 비용을 줄이는 장치가 있다. 체인지 버퍼(change buffer)는 보조 인덱스 페이지가 버퍼 풀에 없을 때 그 페이지에 대한 변경을 따로 모아 두었다가 나중에 합치는 특수한 자료 구조다. 매뉴얼은 보조 인덱스가 대개 비고유이고 보조 인덱스에 대한 삽입이 비교적 무작위 순서로 일어난다는 점을 그 배경으로 든다. 기본값은 버전에 따라 다르다. MySQL 8.0에서 innodb_change_buffering의 기본값은 삽입, 삭제 표시, 퍼지를 모두 버퍼링하는 all이고, MySQL 8.4에서는 none이다. 즉 8.4의 기본 설정에서는 이 완충 장치가 꺼져 있다. 체인지 버퍼의 최대 크기는 innodb_change_buffer_max_size가 버퍼 풀 대비 백분율로 정하며 기본값은 25, 최댓값은 50이다. 매뉴얼은 인덱스나 기본 키에 내림차순 열이 들어 있으면 그 보조 인덱스에는 체인지 버퍼링이 지원되지 않는다고도 밝힌다.

    공간과 메모리

    보조 인덱스 하나는 독립된 B+Tree 하나다. 디스크의 테이블스페이스에서 페이지를 차지하고, 쿼리가 읽을 때는 버퍼 풀에 올라와 다른 인덱스와 데이터 페이지와 메모리를 다툰다. 인덱스가 많을수록 같은 버퍼 풀 크기에서 자주 쓰는 페이지가 밀려날 가능성이 커진다.

    페이지가 얼마나 채워지는지도 공간에 영향을 준다. 매뉴얼은 클러스터형 인덱스에 새 레코드를 넣을 때 InnoDB가 이후의 삽입과 갱신을 위해 페이지의 1/16을 비워 두려 하고, 레코드가 순차적으로(오름차순이든 내림차순이든) 들어오면 페이지가 약 15/16 채워지지만 무작위 순서로 들어오면 1/2에서 15/16 사이로 채워진다고 설명한다. 자동 증가 기본 키는 항상 끝에 덧붙으므로 페이지를 촘촘하게 채운다. 기본 키를 무작위 값(예: 무작위 UUID 문자열)으로 잡으면 같은 행 수에 더 많은 페이지가 필요하고, 그 무거운 기본 키가 모든 보조 인덱스 엔트리에 복사된다. 페이지의 채움 비율이 MERGE_THRESHOLD(지정하지 않으면 50%) 아래로 떨어지면 InnoDB는 이웃 페이지와 합쳐 트리를 줄이려 한다.

    옵티마이저와 잠금

    인덱스가 많으면 옵티마이저가 비교할 후보도 많아진다. 비슷한 열 구성의 인덱스가 여럿이면 통계의 작은 오차로도 선택이 갈리고, 데이터가 바뀌면서 어제와 다른 인덱스를 고르는 일이 생긴다. 쓰지 않는 인덱스는 쓰기 비용만 내고 이런 혼란에 한몫할 뿐이다. 또 하나, InnoDB의 레코드 잠금은 인덱스 레코드에 걸린다. 어떤 인덱스로 행을 찾느냐가 잠그는 범위에 영향을 준다는 뜻이며, 이 이야기는 08회 트랜잭션에서 이어진다.

    인덱스를 무력화하는 조건들

    인덱스를 잘 만들어도 쿼리가 정렬 순서를 쓸 수 없는 모양이면 소용이 없다. 대표적인 경우를 원리와 함께 정리한다.

    열에 함수나 연산을 씌우는 경우. WHERE YEAR(order_date) = 2024를 생각해 보자. 인덱스는 order_date 값의 순서로 정렬되어 있지, YEAR(order_date)의 순서로 정렬되어 있지 않다. 옵티마이저는 "어떤 날짜부터 어떤 날짜까지"라는 구간을 자동으로 만들어 주지 않으므로 이 조건은 구간 조건이 되지 못한다. WHERE amount * 2 > 100000도 같다. 해결책은 열을 그대로 두고 상수 쪽을 바꾸는 것이다.

    -- 구간을 만들지 못한다
SELECT order_id FROM orders WHERE member_id = 7 AND YEAR(order_date) = 2024;

-- 같은 뜻의 범위 조건: (member_id, order_date) 인덱스의 두 열을 모두 구간에 쓴다
SELECT order_id FROM orders
WHERE member_id = 7 AND order_date >= '2024-01-01' AND order_date < '2025-01-01';

-- 식을 바꿀 수 없다면 MySQL 8.0.13부터 함수 기반 키 파트를 쓸 수 있다(식은 괄호로 감싼다)
CREATE INDEX idx_order_year ON orders ((YEAR(order_date)));

    함수 기반 키 파트(functional key part)는 열 값 대신 식의 값을 인덱싱한다. 매뉴얼은 인덱스 정의에서 식을 괄호로 감싸 열과 구별해야 한다고 설명하고, 예컨대 SUBSTRING()으로 만든 키 파트를 쓰려면 WHERE 절에도 같은 인자의 SUBSTRING()이 있어야 한다고 적는다. 쿼리의 식이 인덱스의 식과 일치해야 쓸모가 있다. MySQL 8.4.13에서 위의 첫 쿼리는 type ref, key_len 4(member_id만)였고, 범위 조건으로 바꾼 둘째 쿼리는 type range, key_len 7이었다. 둘 다 Extra는 Using where; Using index다.

    암묵적 형 변환. 전화번호를 VARCHAR 열에 저장하고 인덱스를 걸었는데, 애플리케이션이 숫자로 비교한다고 하자. 매뉴얼은 문자열 열을 숫자와 비교하면 MySQL이 그 열의 인덱스로 값을 빠르게 찾을 수 없다고 설명한다. 숫자 1로 변환되는 문자열이 '1', ' 1', '1a'처럼 여럿이기 때문이다. 정렬된 문자열 목록에서 "숫자로 바꾸면 1인 것"은 한 구간에 모여 있지 않다. 비교할 상수를 열의 타입에 맞춰 문자열로 넘기면 된다. JDBC에서 파라미터를 바인딩할 때 자바 타입을 열 타입과 맞추는 일이 그래서 중요하다.

    -- phone이 VARCHAR이고 인덱스가 있을 때
SELECT * FROM members WHERE phone = 1012345678;     -- 문자열 열을 숫자와 비교: 인덱스로 찾지 못한다
SELECT * FROM members WHERE phone = '01012345678';  -- 같은 타입끼리 비교

    phone VARCHAR(20) NOT NULL에 인덱스 idx_phone을 둔 10만 행 members 테이블로 확인해 보면, 첫 쿼리의 EXPLAIN은 possible_keys에 idx_phone이 있는데도 type ALL이고, 바로 뒤의 SHOW WARNINGS가 이유를 알려 준다. 둘째 쿼리는 type ref, key idx_phone이다.

    +---------+------+-----------------------------------------------------------------------------------------------------+
| Level   | Code | Message                                                                                             |
+---------+------+-----------------------------------------------------------------------------------------------------+
| Warning | 1739 | Cannot use ref access on index 'idx_phone' due to type or collation conversion on field 'phone'     |
| Warning | 1739 | Cannot use range access on index 'idx_phone' due to type or collation conversion on field 'phone'   |
+---------+------+-----------------------------------------------------------------------------------------------------+

    앞쪽 와일드카드. 매뉴얼은 LIKE의 인자가 와일드카드로 시작하지 않는 상수 문자열일 때 B-tree 인덱스를 쓸 수 있다고 설명한다. LIKE 'Patrick%'는 'Patrick'으로 시작하는 연속 구간이지만, LIKE '%Patrick%'는 어디서 시작할지 정할 수 없다. 다른 열을 패턴으로 쓰는 LIKE other_col도 인덱스를 쓰지 않는다. 이것은 문자열 버전의 최좌측 접두사 규칙이다.

    서로 다른 열에 걸친 OR. 매뉴얼은 WHERE 절의 모든 AND 묶음에 걸치지 않는 인덱스는 최적화에 쓰이지 않는다고, 다시 말해 인덱스를 쓰려면 모든 AND 묶음에 그 인덱스의 접두사가 쓰여야 한다고 설명한다. WHERE index_col = 1 OR other_col = 10에서 오른쪽 갈래는 인덱스 열 없이 참이 될 수 있으므로, 인덱스 하나로는 결과를 다 찾을 수 없다. 갈래마다 인덱스가 있으면 인덱스 머지가 쓰일 수 있고, 그렇지 않다면 UNION으로 나눠 쓰는 방법을 검토한다(UNION의 비용은 04회에서 다뤘다).

    흔한 오해 하나도 바로잡아 두자. "IS NULL 조건은 인덱스를 못 탄다"는 말은 MySQL에는 맞지 않는다. 매뉴얼은 col_name IS NULL 검색이 그 열에 인덱스가 있으면 인덱스를 쓴다고 명시한다. 범위 최적화 규칙에서도 IS NULL은 =처럼 다음 키 열로 구간을 이어 가는 연산자로 분류된다.

    적용 연습: 쿼리 묶음에서 인덱스 설계하기

    주문 서비스에 다음 세 쿼리가 자주 실행된다고 하자. 지금까지의 원칙으로 인덱스를 설계해 보자.

    -- Q1: 회원의 최근 주문 20건 (마이페이지 목록)
SELECT order_id, order_date, amount
FROM orders WHERE member_id = ? ORDER BY order_date DESC LIMIT 20;

-- Q2: 회원의 결제 완료 주문 수 (마이페이지 배지)
SELECT COUNT(*) FROM orders WHERE member_id = ? AND status = 'PAID';

-- Q3: 기간 안의 결제 완료 주문 (관리자 화면)
SELECT * FROM orders WHERE status = 'PAID' AND order_date >= ? AND order_date < ?;

    1단계, 쿼리를 분해한다. Q1은 등치 member_id, 정렬 order_date DESC, LIMIT 20이다. Q2는 등치 member_id와 status, 결과는 개수뿐이다. Q3은 등치 status, 범위 order_date, 모든 열이다.

    2단계, Q1. 등치 열 다음에 정렬 열이므로 (member_id, order_date)다. 회원 구간의 끝에서 거꾸로 20개를 읽고 멈춘다. amount가 엔트리에 없어 왕복이 20번 생기지만, LIMIT이 왕복 횟수를 묶어 두므로 커버링을 위해 amount까지 넣을 필요는 크지 않다.

    3단계, Q2. 선택지가 셋이다. 첫째, Q1의 인덱스를 그대로 쓰는 것. 회원 구간은 찾지만 status가 엔트리에 없으므로 회원의 주문마다 클러스터형 인덱스로 왕복해 상태를 확인해야 한다. 둘째, (member_id, status, order_date)로 바꾸는 것. Q2는 구간이 정확해지지만, 회원 구간 안의 정렬이 상태 먼저가 되어 Q1의 ORDER BY order_date가 깨진다. Q1에 filesort가 생긴다. 셋째, (member_id, order_date, status)로 넓히는 것. Q1의 정렬은 그대로 살아 있다. 회원이 고정되면 엔트리는 여전히 날짜순이기 때문이다. Q2는 구간을 member_id로만 좁히지만(key_len 4), COUNT(*)에 필요한 열(member_id, status)이 모두 엔트리에 있으므로 커버링이 되어 왕복이 사라진다. 회원 한 명의 주문 수십 건을 엔트리에서 세는 일은 충분히 싸다. 세 번째를 고른다.

    4단계, Q3. 등치 열 status를 앞에, 범위 열 order_date를 뒤에 두어 (status, order_date)로 한다. status는 카디널리티가 4밖에 안 되지만 선두에 두는 것이 맞다. 'PAID'라는 덩어리 안에서 날짜가 정렬되어 있으므로 구간이 정확히 "PAID이면서 기간 안"이 된다. 반대로 (order_date, status)로 만들면 기간 안의 모든 상태의 주문을 읽으면서 'PAID'를 걸러 내야 한다. 카디널리티만 보고 순서를 정하면 틀리는 전형적인 경우다. EXPLAIN에서는 key_len이 status만 쓴 길이보다 DATE의 3바이트만큼 큰지로 두 열이 모두 구간에 쓰였는지 확인한다. Q3은 SELECT *라 결과 행마다 왕복이 생기므로, 기간이 길어 결과가 테이블의 큰 비율이 되면 옵티마이저가 풀 스캔을 고를 수 있다. 그것은 오작동이 아니라 비용 계산의 결과다.

    5단계, 정리한다. 최종 인덱스는 기본 키 (order_id), (member_id, order_date, status), (status, order_date)다. 기존의 idx_member_date (member_id, order_date)는 새 인덱스의 최좌측 접두사이고, 다섯째 가이드라인에서 본 기본 키 정렬 문제도 이 쿼리 묶음에는 없으므로 지울 후보다. 앞서 만든 idx_status (status)도 (status, order_date)의 최좌측 접두사다. 바로 지우지 말고 INVISIBLE로 숨긴 뒤 다른 쿼리에 영향이 없는지 관찰하고 나서 지운다.

    CREATE INDEX idx_member_date_status ON orders (member_id, order_date, status);
CREATE INDEX idx_status_date        ON orders (status, order_date);   -- 스킵 스캔 절에서 만든 것과 같은 정의

ALTER TABLE orders ALTER INDEX idx_member_date INVISIBLE;
ALTER TABLE orders ALTER INDEX idx_status INVISIBLE;
-- 대표적인 작업량으로 충분히 관찰한 뒤
-- DROP INDEX idx_member_date ON orders;
-- DROP INDEX idx_status ON orders;

    이 구성(두 인덱스를 INVISIBLE로 숨긴 상태)을 100만 행 데이터에 만들고 MySQL 8.4.13에서 확인했다. Q1은 idx_member_date_status, type ref, key_len 4에 Extra Backward index scan으로 filesort가 없었다. Q2는 같은 인덱스로 type ref, key_len 4에 Extra Using where; Using index여서 커버링으로 처리되었다. Q3은 한 달 기간(2024-05)으로 넣었을 때 idx_status_date, type range, key_len 45로 두 열이 모두 구간에 쓰였다. 'PAID'로 2년 전체를 넣어도 range였지만, 'DONE'(85%)으로 2년 전체를 넣으면 type ALL이 되었다. 4단계에서 말한 비용 계산의 결과다.

    다른 주제와의 연결

    이 회차의 원리는 JPA를 쓸 때 그대로 다시 나타난다. 엔티티 조회는 모든 매핑 열을 SELECT하므로 커버링과 거리가 멀고, 목록 화면처럼 열 몇 개만 필요한 곳에서는 DTO 프로젝션이 인덱스만으로 끝나는 쿼리를 만든다. Spring Data의 페이지 조회는 대개 ORDER BY ... LIMIT ... OFFSET ... 형태의 쿼리와 전체 개수를 세는 COUNT 쿼리를 함께 실행한다. 앞의 것에는 "등치 조건 열 → 정렬 열" 인덱스가, 뒤의 것에는 조건 열만 담은 커버링 인덱스가 필요하다. OFFSET이 커지면 버릴 행까지 순서대로 읽어야 하므로 깊은 페이지일수록 느려진다는 점도 정렬된 목록이라는 성질에서 바로 나온다.

    같은 권의 다음 회차와도 이어진다. 07회에서 다루는 UNIQUE 같은 제약 조건은 인덱스와 밀접하게 연결되어 있고, 08회의 잠금은 앞에서 말했듯 인덱스 레코드에 걸린다. 어떤 인덱스로 행을 찾느냐가 동시에 실행되는 트랜잭션끼리 서로를 얼마나 기다리게 하는지까지 바꾸는 셈이다. 01회와 02회에서 본 중첩 루프 조인의 안쪽 테이블 탐색도 결국 이 회차의 인덱스 탐색이다. 조인 열에 맞는 인덱스가 있으면 type이 eq_ref나 ref로 나오고, 없으면 바깥 행마다 안쪽 테이블을 훑는다.
    비용 기반 옵티마이저
    MySQL 옵티마이저는 연산별 비용 상수(mysql.server_cost, mysql.engine_cost)와 추정 행 수로 계획의 비용을 계산해 고른다. 인덱스는 선택지일 뿐이며, 더 싸다고 판단될 때만 쓰인다.
    통계와 행 수 추정
    행 수는 인덱스 다이브나 인덱스 통계로 추정한다. InnoDB는 무작위 표본 페이지(기본 20)로 카디널리티를 추정해 영구 저장하고, 행의 10%를 넘게 바뀌면 다시 계산한다. ANALYZE TABLE로 즉시 갱신할 수 있다.
    인덱스보다 풀 스캔이 싼 경우
    보조 인덱스 경로는 엔트리마다 클러스터형 인덱스로 왕복한다. 결과 행이 테이블의 큰 비율이면 리프를 순서대로 한 번 훑는 풀 스캔이 더 싸다. 고정된 30% 기준은 지금의 MySQL에 없다.
    커버링 인덱스
    쿼리가 요구하는 열이 모두 인덱스에 있어 테이블 행을 읽지 않는 경우다. Extra에 Using index가 나온다. InnoDB 보조 인덱스에는 기본 키가 늘 들어 있어 기본 키 열도 커버링에 포함된다.
    최좌측 접두사
    복합 인덱스는 열들을 사전식으로 정렬한 목록이므로, 앞에서부터 이어진 열 조합에만 시작 지점을 정할 수 있다. (a, b, c)는 (a), (a, b), (a, b, c)로 탐색할 수 있고 (b)나 (b, c)로는 못 한다.
    범위 조건 뒤의 열
    =, <=>, IS NULL이 이어지는 동안 구간이 좁아지고, 처음 나오는 범위 조건에서 좁히기가 끝난다. 그 뒤의 조건은 걸러 내기에만 쓰이며 ICP로 왕복 전에 평가될 수 있다. 그래서 등치 조건 열을 앞에, 범위 조건 열을 뒤에 둔다.
    인덱스 정렬과 filesort
    등치 조건으로 고정된 열 다음의 열 순서가 ORDER BY와 같으면 정렬 없이 결과가 나오고, LIMIT이면 필요한 개수만 읽고 멈춘다. 그렇지 않으면 Using filesort로 추가 정렬을 한다.
    인덱스의 비용
    쓰기마다 모든 관련 B+Tree를 고쳐야 하고, 디스크와 버퍼 풀을 차지하며, 옵티마이저의 후보를 늘린다. 열에 함수 적용, 문자열 열과 숫자 비교, 앞쪽 와일드카드, 열이 다른 OR는 구간을 만들지 못한다.

    실무에서 "인덱스를 탔는데 느리다"는 보고를 받으면 먼저 key_len과 rows를 본다. key가 기대한 인덱스로 나와도 key_len이 선두 열 하나의 길이뿐이라면, 뒤쪽 열은 범위 조건 뒤에 놓였거나 함수에 감싸여 구간을 좁히지 못한 것이다. 그때 Extra의 Using index condition은 "그나마 왕복은 줄였다"는 뜻일 뿐 읽는 엔트리 수는 그대로다. 해결은 열 순서를 등치 조건 → 범위 조건으로 바꾸거나, 범위 조건을 짧은 IN 목록으로 바꾸거나, 조건식을 열을 그대로 두는 모양으로 고치는 것이다.

    반대로 "인덱스를 안 탄다"는 보고에는 옵티마이저가 옳을 가능성부터 따진다. 결과 행이 테이블의 큰 비율이고 SELECT *라면 풀 스캔이 정답일 수 있다. 이 경우 고칠 것은 힌트가 아니라 쿼리다. 필요한 열만 SELECT해 커버링을 만들거나, LIMIT으로 화면에 필요한 만큼만 가져오게 하면 옵티마이저의 판단이 자연스럽게 바뀐다. 대량 적재 직후라면 통계가 낡았을 수 있으니 ANALYZE TABLE을 먼저 실행하고, EXPLAIN ANALYZE로 추정 rows와 실제 rows를 비교한다. 힌트는 이 모든 것을 해 본 뒤의 마지막 수단이다.

    인덱스를 추가하자는 결정은 쓰기 쪽 비용과 함께 판단한다. 쓰기가 많은 테이블, 특히 MySQL 8.4처럼 체인지 버퍼가 기본으로 꺼진 환경에서는 보조 인덱스 하나하나가 INSERT와 UPDATE의 비용에 직접 더해진다. 쿼리 목록을 기준으로 여러 쿼리가 함께 쓸 수 있는 인덱스를 고르고, 최좌측 접두사로 겹치는 인덱스는 INVISIBLE로 숨겨 영향을 확인한 뒤 정리한다. 판단이 달라지는 조건은 결국 데이터 분포와 쿼리의 모양이다. 같은 인덱스라도 데이터가 바뀌면 옵티마이저의 선택이 바뀌므로, 인덱스 설계는 한 번 하고 끝나는 일이 아니라 계획을 주기적으로 다시 확인하는 일이다.
  • 인덱스 (a, b, c)가 있다(세 열 모두 INT NOT NULL). 다음 각 쿼리에서 구간을 좁히는 데 쓰이는 열, 예상 key_len, 그리고 ORDER BY가 filesort 없이 처리되는지 판정하라. (가) WHERE a = 1 AND b = 2 ORDER BY c (나) WHERE a = 1 AND b > 2 ORDER BY c (다) WHERE a IN (1, 2) AND b = 3 ORDER BY c (라) WHERE b = 2 AND c = 3
  • idx_member_date (member_id, order_date)만 있는 InnoDB orders 테이블에서 다음 쿼리가 커버링 인덱스로 처리될 수 있는지 판정하고 이유를 써라. (가) SELECT order_id FROM orders WHERE member_id = 7 AND order_date >= '2024-01-01' (나) SELECT MAX(order_date) FROM orders WHERE member_id = 7 (다) SELECT order_date FROM orders WHERE member_id = 7 AND status = 'PAID'
  • 다음 쿼리가 idx_member_date를 두고도 느리다. 원인을 정렬 순서의 관점에서 설명하고, 같은 결과를 내면서 인덱스의 두 열을 모두 구간에 쓰는 쿼리로 고쳐라. SELECT order_id FROM orders WHERE member_id = 7 AND DATE_FORMAT(order_date, '%Y-%m') = '2024-05'
  • 회원 테이블의 phone VARCHAR(20) 열에 인덱스가 있는데, 애플리케이션이 WHERE phone = ?에 자바 long 값을 바인딩하자 type이 ALL로 바뀌었다. MySQL 매뉴얼의 형 변환 규칙으로 이유를 설명하고 고치는 방법을 써라.
  • 쿼리 SELECT * FROM orders WHERE order_date = ? AND member_id BETWEEN ? AND ?(회원 번호 구간은 보통 좁다)와 SELECT * FROM orders WHERE member_id = ? ORDER BY order_date DESC LIMIT 10이 모두 자주 실행된다. 인덱스 하나로 둘 다 좋게 만들 수 있는지, 아니면 둘이 필요한지 판단하고 열 순서를 정하라.

    1번. (가) a와 b가 모두 등치이므로 구간에 a, b가 쓰이고 key_len은 8이다. a, b가 고정된 덩어리 안에서 엔트리는 c 순이므로 ORDER BY c는 정렬 없이 처리된다. (나) a는 등치, b는 범위이므로 구간은 a, b까지이고 key_len은 8이다. 하지만 구간 안의 엔트리는 (b, c) 순이라 c 단독 순서가 아니므로 ORDER BY c에는 filesort가 필요하다. (다) IN은 등치 구간의 묶음이라 a, b 모두 구간에 쓰여 key_len 8, 구간은 (1, 3)과 (2, 3) 두 개다. 각 구간 안은 c 순이지만 두 덩어리를 이으면 전체가 c 순이 아니므로 filesort가 필요하다. (라) 선두 열 a에 조건이 없어 최좌측 접두사가 아니므로 이 인덱스로 시작 지점을 정할 수 없다. 인덱스 열만 쓰는 쿼리라면 인덱스 전체 스캔이나 스킵 스캔의 대상은 될 수 있지만, 구간 탐색은 아니다. 20만 행 테스트 테이블로 MySQL 8.4.13에서 확인한 결과도 같았다. (가)는 ref, key_len 8에 filesort 없음, (나)와 (다)는 range, key_len 8에 Using filesort였고, (라)는 SELECT *이면 type ALL, SELECT a, b, c이면 Using index for skip scan이었다.

    2번. (가) 커버링이다. 조건 열 member_id, order_date와 결과 열 order_id(기본 키)가 모두 엔트리에 있다. InnoDB 보조 인덱스 엔트리에는 기본 키가 들어 있기 때문이다. (나) 커버링이다. 조건과 결과에 필요한 열이 member_id와 order_date뿐이다. 게다가 매뉴얼의 MIN/MAX 최적화 설명대로 앞 열이 상수로 고정된 상태에서 다음 열의 최댓값은 회원 7 구간의 마지막 엔트리 하나를 찾는 키 탐색 한 번으로 구할 수 있다. (다) 커버링이 아니다. status가 엔트리에 없으므로 회원 7의 엔트리마다 클러스터형 인덱스로 가서 상태를 확인해야 한다. 이런 쿼리가 자주 실행된다면 (member_id, order_date, status)처럼 status를 덧붙이는 것을 검토한다.

    3번. 인덱스는 order_date 값의 순서로 정렬되어 있을 뿐, DATE_FORMAT(order_date, '%Y-%m')의 결과로 정렬되어 있지 않다. 옵티마이저는 이 식에서 날짜 구간을 만들어 내지 못하므로 구간은 member_id = 7까지만 좁혀지고(key_len 4), 회원 7의 모든 주문을 읽으며 식을 평가해 걸러 낸다. 열을 그대로 두고 상수 쪽을 구간으로 바꾸면 된다: WHERE member_id = 7 AND order_date >= '2024-05-01' AND order_date < '2024-06-01'. 이제 key_len이 7이 되어 두 열이 모두 구간에 쓰인다. 끝을 BETWEEN '2024-05-31'로 쓰지 않고 다음 달 1일 미만으로 쓰는 습관은 열 타입이 DATETIME일 때 5월 31일 낮 시간의 행을 놓치지 않게 해 준다.

    4번. 매뉴얼은 문자열 열을 숫자와 비교하면 그 열의 인덱스로 값을 빠르게 찾을 수 없다고 설명한다. 숫자로 바꾸면 같은 값이 되는 문자열('1', ' 1', '1a' 같은)이 여럿이고, 그것들이 문자열 정렬 순서에서 한 구간에 모여 있지 않기 때문이다. 게다가 전화번호를 숫자로 바꾸면 앞의 0이 사라져 값 자체가 달라진다. 바인딩하는 값을 String으로 바꿔 열 타입과 같은 문자열끼리 비교하게 하면 인덱스로 등치 탐색을 할 수 있다.

    5번. 첫 쿼리는 order_date가 등치, member_id가 범위이므로 (order_date, member_id)가 맞다. 날짜가 고정된 덩어리 안에서 회원 번호 구간이 연속이다. 두 번째 쿼리는 member_id가 등치이고 order_date가 정렬 열이므로 (member_id, order_date)가 맞다. 두 쿼리가 요구하는 열 순서가 정반대라 인덱스 하나로는 둘 다 만족시킬 수 없다. (member_id, order_date) 하나만 두면 첫 쿼리는 member_id 범위로만 구간을 잡고 order_date를 ICP로 걸러 내야 하고, (order_date, member_id) 하나만 두면 두 번째 쿼리는 최좌측 접두사 조건을 잃는다. 둘 다 자주 실행된다면 인덱스 두 개가 필요하고, 그 대가로 쓰기 비용이 늘어난다는 점을 함께 판단한다.

     인덱스 (a, b, c)가 있고 WHERE a = 1 AND b > 5 AND c = 3 인 쿼리를 이 인덱스로 처리한다. 옳은 설명은? 세 조건이 모두 인덱스 열이므로 세 열 모두 구간을 좁히는 데 쓰인다. a와 b로 구간을 정하고, c = 3은 구간을 좁히지 못한 채 읽은 엔트리를 걸러 내는 데 쓰인다. b가 범위 조건이므로 a도 구간에 쓰이지 못하고 인덱스 전체를 읽는다. WHERE 절에서 c = 3을 b > 5보다 앞에 쓰면 세 열 모두 구간에 쓰인다. 등치 조건(a = 1)이 이어지는 동안 구간이 좁아지고, 처음 나오는 범위 조건(b > 5)에서 좁히기가 끝난다. 구간 안의 엔트리는 (b, c) 순이므로 c = 3인 엔트리는 b 값마다 흩어져 있어 연속 구간을 이루지 못한다. 그래서 c 조건은 필터로만 쓰이며 ICP로 왕복 전에 평가될 수 있다. 첫 번째 보기는 범위 조건의 효과를 무시했다. 세 번째 보기는 틀렸다. 범위 조건 앞의 등치 조건은 정상적으로 구간에 쓰인다. 네 번째 보기는 SQL 문장의 조건 순서와 인덱스 정의의 열 순서를 혼동했다. status 열에 단일 인덱스가 있는데 SELECT * FROM orders WHERE status = 'DONE'(전체 행의 대부분이 DONE)의 EXPLAIN에서 type이 ALL로 나왔다. 가장 적절한 해석은? status의 인덱스가 손상되었으므로 다시 만들어야 한다. 문자열 열에는 인덱스가 쓰이지 않으므로 status를 숫자 코드로 바꿔야 한다. 인덱스 경로는 엔트리마다 클러스터형 인덱스로 왕복해야 하고 결과가 테이블의 대부분이라, 리프를 순서대로 한 번 훑는 풀 스캔이 더 싸다고 판단한 것이다. MySQL은 결과가 테이블의 30%를 넘으면 무조건 풀 스캔을 하도록 고정되어 있다. SELECT *라 보조 인덱스 엔트리만으로는 답할 수 없고, 'DONE' 엔트리마다 클러스터형 인덱스로 흩어진 왕복이 필요하다. 결과가 대부분의 행이면 이 비용이 풀 스캔보다 커진다. MySQL 매뉴얼은 고정된 비율이 인덱스와 스캔의 선택을 더 이상 결정하지 않는다고 밝히므로 네 번째 보기는 틀렸다. 문자열 열도 B-tree 인덱스로 탐색할 수 있으므로 두 번째도 틀렸고, 첫 번째는 근거가 없다. InnoDB 테이블 orders(기본 키 order_id)에 보조 인덱스 (member_id)만 있다. SELECT order_id FROM orders WHERE member_id = 7 에 대해 옳은 것은? 보조 인덱스 엔트리에 기본 키가 들어 있으므로 커버링 인덱스로 처리될 수 있고, Extra에 Using index가 나올 수 있다. order_id가 인덱스 정의에 없으므로 엔트리마다 클러스터형 인덱스로 돌아가야 한다. 기본 키를 조회하므로 type이 const로 나온다. 커버링이 되려면 인덱스를 (member_id, order_id)로 다시 정의해야만 한다. MySQL 매뉴얼에 따르면 InnoDB 보조 인덱스의 각 레코드에는 인덱스 열과 함께 그 행의 기본 키 열이 들어 있다. 따라서 (member_id) 인덱스의 엔트리만으로 order_id를 돌려줄 수 있다. 두 번째와 네 번째 보기는 이 사실을 모를 때의 오해다. const는 기본 키나 UNIQUE 인덱스의 모든 열을 상수와 비교할 때의 접근 방식이고, 여기서는 member_id라는 비고유 인덱스로 찾으므로 ref가 된다. 인덱스 (member_id, order_date)로 WHERE member_id = 7 ORDER BY order_date DESC LIMIT 10 을 처리할 때 일어나는 일로 옳은 것은? 내림차순 정렬은 인덱스로 처리할 수 없으므로 회원 7의 모든 행을 읽어 filesort한다. ORDER BY를 쓰려면 인덱스 정의에 DESC를 붙인 내림차순 인덱스가 반드시 있어야 한다. LIMIT이 있으므로 인덱스를 쓰지 않고 테이블의 처음 10행을 읽는다. member_id가 고정된 구간 안의 엔트리는 order_date 순이므로, 구간 끝에서 거꾸로 10개를 읽고 멈출 수 있어 정렬이 필요 없다. member_id가 상수로 고정되면 인덱스로 접근한 행은 order_date 순서로 나온다. 정렬 키가 모두 DESC이면 인덱스를 역순으로 읽을 수 있으므로 내림차순도 정렬 없이 처리되고, LIMIT 10이면 10개를 읽고 멈춘다. 내림차순 인덱스는 ASC와 DESC가 섞인 정렬을 정방향으로 처리할 때 필요하지, 모두 DESC인 정렬에 필수는 아니다. 세 번째 보기는 WHERE 조건을 무시한 것이다. 쿼리는 WHERE status = ? AND order_date >= ? AND order_date < ? 이고, status는 서로 다른 값이 4개, order_date는 매우 다양하다. 복합 인덱스의 열 순서로 더 적절한 것과 이유는? (order_date, status): 카디널리티가 높은 열을 앞에 두어야 하기 때문이다. (status, order_date): 등치 조건 열을 앞에 두면 status가 고정된 덩어리 안에서 날짜 범위가 연속 구간이 되어 두 열 모두 구간을 좁히기 때문이다. 어느 순서든 두 열이 모두 구간에 쓰이므로 차이가 없다. 카디널리티가 낮은 status는 인덱스에 넣지 않는 것이 좋다. 범위 조건 열이 앞에 오면 그 뒤의 열은 구간을 좁히지 못한다. (order_date, status)라면 기간 안의 모든 상태의 엔트리를 읽으며 status를 걸러 내야 한다. (status, order_date)라면 해당 status 덩어리 안에서 날짜가 정렬되어 있어 구간이 정확히 조건과 일치한다. "카디널리티가 높은 열을 앞에"라는 조언은 등치와 범위가 섞인 경우에는 맞지 않는다. 세 번째 보기는 범위 조건이 뒤의 열을 멈추게 한다는 규칙을 무시했다. 네 번째 보기는 선두 열로서 status가 범위 조건과 함께 만드는 구간의 가치를 놓쳤다.
    옵티마이저(optimizer)
    같은 결과를 내는 여러 실행 방법 중 하나를 고르는 모듈이다. MySQL의 옵티마이저는 비용 모델과 추정 행 수로 계획의 비용을 비교한다.
    카디널리티(cardinality)
    인덱스 열(또는 앞에서부터의 열 조합)에 들어 있는 서로 다른 값의 수다. InnoDB에서는 표본 페이지로 추정한 값이다.
    선택도(selectivity)
    조건이 테이블의 행을 얼마나 걸러 내는지를 나타내는 정도다. 조건을 만족하는 행이 적을수록 선택도가 좋다고 말한다.
    인덱스 다이브(index dive)
    구간의 양 끝으로 실제 인덱스를 내려가 그 사이의 행 수를 추정하는 방법이다. 인덱스 통계보다 정확하지만 구간이 많으면 느려진다.
    커버링 인덱스(covering index)
    쿼리가 요구하는 열을 모두 담고 있어 테이블 행을 읽지 않고 답할 수 있는 인덱스다. EXPLAIN의 Extra에 Using index로 표시된다.
    복합 인덱스(composite index, multiple-column index)
    여러 열을 하나의 키로 묶어 사전식 순서로 정렬한 인덱스다. MySQL에서 최대 16개 열까지 쓸 수 있다.
    최좌측 접두사(leftmost prefix)
    복합 인덱스 정의에서 첫 열부터 연속으로 이어지는 열 조합이다. 이 조합에 대한 조건만 인덱스 탐색의 시작 지점을 정할 수 있다.
    인덱스 조건 푸시다운(Index Condition Pushdown, ICP)
    구간을 좁히지 못하는 조건이라도 인덱스 열만으로 판정할 수 있으면 행 전체를 읽기 전에 인덱스 엔트리에서 평가하는 최적화다. Extra에 Using index condition으로 표시된다.
    파일 정렬(filesort)
    인덱스 순서로 ORDER BY를 만족할 수 없을 때 행을 읽은 뒤 따로 정렬하는 단계다. 정렬 버퍼에서 처리하고, 넘치면 임시 파일을 쓴다.
    스킵 스캔(skip scan)
    MySQL 8.0.13부터 쓸 수 있는 접근 방법으로, 선두 열에 조건이 없을 때 선두 열의 값마다 범위 스캔을 한 번씩 수행한다. Extra에 Using index for skip scan으로 표시된다.
