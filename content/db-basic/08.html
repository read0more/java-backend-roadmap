    이 회차의 질문: 여러 문장이 한 몸처럼 움직여야 할 때

    이 권의 앞 회차들은 주로 데이터를 어떻게 읽을지를 다뤘다. 조인으로 테이블을 다시 합치고, 서브쿼리와 뷰로 질의를 조립하고, 인덱스로 원하는 행을 빨리 찾았다. 07회에서는 잘못된 값이 아예 들어오지 못하도록 제약 조건으로 막는 방법을 봤다. 이 회차는 축을 바꿔 시간을 다룬다. 데이터를 바꾸는 작업 하나가 여러 문장으로 이루어질 때, 그리고 그런 작업 여러 개가 같은 순간에 같은 행을 건드릴 때 무슨 일이 생기는가.

    계좌 이체가 대표적인 예다. 1번 계좌에서 3만 원을 빼고 2번 계좌에 3만 원을 더하는 일은 SQL로 쓰면 UPDATE 두 개다. 그런데 첫 문장이 끝난 직후 서버 전원이 나가면 어떻게 되는가. 두 번째 문장이 오류로 실패하면 첫 문장의 결과는 어떻게 해야 하는가. 1번 계좌에서 출금하는 이체 두 건이 동시에 실행되면 잔액 확인은 믿을 수 있는가. 이 세 질문이 이 회차 전체를 이끈다.

    세 질문에 대한 데이터베이스의 답이 트랜잭션(transaction)이다. 트랜잭션은 여러 작업을 하나의 논리적 작업 단위(unit of work)로 묶어, 전부 반영되거나 전혀 반영되지 않게 하고, 동시에 실행되는 다른 작업과 정해진 규칙 안에서만 서로 보이게 한다. 약속 자체는 간단하다. 그 약속을 지키는 장치는 간단하지 않다. InnoDB는 언두 로그(undo log), 리두 로그(redo log), 다중 버전 동시성 제어(MVCC), 행 잠금(row lock)을 함께 써서 약속을 지킨다. 이 회차는 약속(ACID와 격리 수준)과 장치를 나란히 놓고 따라간다.

    설명과 규칙은 MySQL 8.0 Reference Manual의 InnoDB 기준이다. 이 회차의 SQL 예제와 두 세션 실행표는 MySQL 8.4.13과 8.0.46에서 기본 설정(REPEATABLE READ, 자동 커밋 켜짐)으로 직접 실행해 결과와 오류 문구를 확인했고, 두 버전에서 모두 돌린 예제의 결과는 같았다. 엔진 내부의 세부는 매뉴얼과 MySQL 8.0 소스 코드로 확인한 범위에서만 쓴다. 다중 버전 읽기의 동작은 자바(JDK 21)로 만든 작은 모델로 직접 돌려 본다. 범위를 나누면, B+Tree 인덱스와 클러스터형 인덱스의 구조는 05회와 06회, 제약 조건 자체는 07회, 저장 프로시저 안에서 트랜잭션을 여는 방법은 09회의 몫이다. 여기서는 그 주제들이 트랜잭션과 만나는 지점만 짚는다.

    트랜잭션이 필요한 이유: 이체 한 건이 문장 두 개일 때

    이 회차 내내 쓸 테이블은 하나다. 계좌 번호, 예금주, 잔액만 있는 단순한 테이블이다. 엔진은 InnoDB로 명시한다. MySQL 8.0의 기본 저장 엔진이 InnoDB이지만, 트랜잭션은 SQL 문법의 기능이 아니라 저장 엔진의 능력이라는 점을 잊지 않기 위해서다.

    CREATE TABLE account (
    id      BIGINT      PRIMARY KEY,
    owner   VARCHAR(20) NOT NULL,
    balance BIGINT      NOT NULL
) ENGINE = InnoDB;

INSERT INTO account VALUES (1, '김하늘', 50000), (2, '이바다', 10000);

    두 계좌 잔액의 합은 60,000원이다. 1번에서 2번으로 3만 원을 옮기는 이체는 이 합을 바꾸지 않아야 한다. 이렇게 "어떤 작업 전후에 항상 참이어야 하는 조건"을 불변식(invariant)이라고 부른다. 이체를 SQL로 옮기면 다음 두 문장이다.

    UPDATE account SET balance = balance - 30000 WHERE id = 1;
UPDATE account SET balance = balance + 30000 WHERE id = 2;

    아무 장치 없이 이 두 문장을 실행하면 불변식이 깨지는 길이 세 갈래 있다. 첫째는 장애다. MySQL은 새 연결을 자동 커밋(autocommit)이 켜진 상태로 시작하므로, 위 두 문장은 각각 독립된 트랜잭션이 되어 문장이 끝나는 순간 확정된다. 첫 문장이 확정된 뒤 두 번째 문장이 실행되기 전에 서버 프로세스가 죽거나 애플리케이션과의 네트워크가 끊기면, 1번 계좌는 20,000원이 되었는데 2번 계좌는 10,000원 그대로다. 합은 30,000원이 되고 3만 원이 공중으로 사라진다.

    둘째는 논리적 실패다. 두 번째 문장의 WHERE id = 2를 실수로 WHERE id = 3으로 썼다고 하자. 3번 계좌는 없으므로 이 UPDATE는 0개의 행을 바꾸고 정상 종료한다. 바뀐 행이 0개인 것은 SQL에서 오류가 아니다. 첫 문장은 이미 확정되었으므로 역시 3만 원이 사라진다. 두 번째 문장이 실제 오류(예를 들어 07회에서 다룬 제약 조건 위반)로 실패해도 결과는 같다. 앞 문장을 취소할 방법이 없다.

    셋째는 동시 실행이다. 애플리케이션이 잔액이 충분한지 먼저 읽어 확인한 뒤 출금한다고 하자. 1번 계좌(50,000원)에서 3만 원씩 출금하는 요청 두 개가 동시에 들어온다. 요청 A가 잔액 50,000원을 읽고 충분하다고 판단한다. A가 출금하기 전에 요청 B도 50,000원을 읽고 충분하다고 판단한다. 두 요청이 모두 출금을 실행하면 잔액은 -10,000원이 된다. 각 요청의 코드는 그 자체로는 옳았다. 문제는 두 실행이 시간 축 위에서 서로 끼어들었다는 데 있다. 이 셋째 문제는 장애나 오류와 달리 아무 오류 메시지 없이 조용히 일어난다는 점에서 가장 위험하다.

    불변식이 깨지는 길원인트랜잭션이 주는 답
    장애두 문장 사이에서 서버·네트워크가 끊김확정되지 않은 변경은 복구 과정에서 되돌린다(원자성, 지속성)
    논리적 실패두 번째 문장이 오류를 내거나 아무 행도 바꾸지 못함애플리케이션이 ROLLBACK으로 앞 문장까지 취소한다(원자성)
    동시 실행다른 작업이 중간 상태를 읽거나 같은 행을 덮어씀격리 수준과 잠금이 끼어들 수 있는 범위를 정한다(격리성)
    일상에서 가져온 비유부동산 거래의 에스크로

    집을 사고팔 때 매수인이 돈을 보냈는데 매도인이 소유권을 넘기지 않으면 곤란하다. 그래서 중개 기관이 돈과 서류를 모두 받아 둔 뒤, 둘 다 갖춰졌을 때만 한꺼번에 넘기고 하나라도 빠지면 모두 돌려준다. 트랜잭션의 "전부 아니면 전무"가 이것이다. 비유가 깨지는 지점이 있다. 에스크로는 조건이 갖춰질 때까지 아무것도 옮기지 않고 기다린다. InnoDB는 반대로 변경을 데이터 페이지에 곧바로 적고, 취소될 때를 대비해 원래 값을 언두 로그에 남겨 둔다. "먼저 바꾸고, 되돌릴 수단을 챙겨 둔다"는 방식이다. 이 차이가 뒤에서 볼 롤백 비용과 MVCC를 설명한다.

    같은 이체를 자동 커밋으로 실행했을 때와 트랜잭션으로 묶었을 때, 두 문장 사이에서 장애가 나면 결과가 어떻게 다른지 보여 준다. 가로로 두 개의 패널. 왼쪽 패널 제목 "자동 커밋", 오른쪽 패널 제목 "트랜잭션으로 묶음". 각 패널에 위에서 아래로 흐르는 세로 타임라인. 왼쪽: 첫 상자 "UPDATE 1번 -30000" 옆에 초록 체크와 작은 라벨 "즉시 확정", 그 아래 빨간 번개 아이콘과 라벨 "서버 장애", 그 아래 회색 점선 상자 "UPDATE 2번 +30000 (실행 안 됨)", 맨 아래 두 개의 계좌 카드 "1번 20000"과 "2번 10000", 그 옆 빨간 글씨 "합계 30000". 오른쪽: 맨 위 상자 "START TRANSACTION", 그 아래 "UPDATE 1번 -30000" 옆 노란 라벨 "미확정", 빨간 번개 "서버 장애", 그 아래 순환 화살표 아이콘과 라벨 "복구 때 롤백", 맨 아래 계좌 카드 "1번 50000"과 "2번 10000", 초록 글씨 "합계 60000". 평면적인 인포그래픽 스타일, 흰 배경. 자동 커밋에서는 문장마다 확정되므로 두 문장 사이의 장애가 불변식을 깬다. 트랜잭션으로 묶으면 확정되지 않은 변경은 복구 과정에서 되돌려진다.

    커밋과 롤백: 트랜잭션의 경계를 긋는 문장

    먼저 데이터베이스 입문에서 본 사실을 상기하자. MySQL 매뉴얼은 InnoDB에서 모든 사용자 활동이 트랜잭션 안에서 일어난다고 적는다. 자동 커밋이 켜져 있으면 SQL 문장 하나가 그 자체로 트랜잭션 하나가 되고, 문장이 오류 없이 끝나면 서버가 그 자리에서 커밋한다. 이 모드에서 실행된 문장은 ROLLBACK으로 취소할 수 없다. 이미 끝난 트랜잭션이기 때문이다. 앞 절의 첫째 문제는 바로 이 성질에서 나온다.

    여러 문장을 하나로 묶으려면 경계를 직접 그어야 한다. START TRANSACTION(또는 동의어 BEGIN)이 트랜잭션을 연다. 매뉴얼에 따르면 START TRANSACTION을 실행하면 그 트랜잭션이 COMMIT이나 ROLLBACK으로 끝날 때까지 자동 커밋이 꺼져 있다가, 끝나면 원래 상태로 돌아간다. COMMIT은 현재 트랜잭션의 변경을 영구적으로 만들고 다른 세션에 보이게 한다. ROLLBACK은 현재 트랜잭션이 한 모든 변경을 취소한다. 그리고 매뉴얼은 두 문장 모두 그 트랜잭션이 잡은 InnoDB 잠금을 전부 놓는다고 적는다. 커밋과 롤백은 데이터의 운명을 정하는 동시에 잠금을 푸는 순간이기도 하다.

    START TRANSACTION;
UPDATE account SET balance = balance - 30000 WHERE id = 1;
UPDATE account SET balance = balance + 30000 WHERE id = 2;
SELECT id, balance FROM account;   -- 이 세션에서는 (1, 20000), (2, 40000)
ROLLBACK;
SELECT id, balance FROM account;   -- (1, 50000), (2, 10000)으로 돌아와 있다

    한 줄씩 따라가 보자. START TRANSACTION 뒤의 두 UPDATE는 실행되었지만 확정되지 않았다. 세 번째 줄의 SELECT는 이 트랜잭션이 바꾼 값(20,000원, 40,000원)을 본다. 뒤에서 자세히 보겠지만, InnoDB의 일관된 읽기는 같은 트랜잭션 안에서 앞서 실행한 문장의 변경은 보이게 한다. 같은 순간 다른 세션이 기본 격리 수준에서 같은 테이블을 읽으면 여전히 50,000원과 10,000원을 본다. 확정되지 않은 변경은 남에게 보이지 않는다. ROLLBACK이 실행되면 두 변경이 모두 사라지고, 마지막 SELECT는 처음 값을 본다. 이체를 정상적으로 끝내려면 ROLLBACK 대신 COMMIT을 쓰면 된다.

    자동 커밋을 세션 단위로 끄는 방법도 있다. SET autocommit = 0을 실행하면 매뉴얼의 표현대로 그 세션에는 항상 트랜잭션 하나가 열려 있게 된다. COMMIT이나 ROLLBACK이 현재 트랜잭션을 끝내면 곧바로 새 트랜잭션이 시작된다. 자동 커밋은 세션 변수이므로 연결마다 따로 설정해야 한다. 매뉴얼은 자동 커밋을 끈 세션이 마지막 트랜잭션을 커밋하지 않고 끝나면 MySQL이 그 트랜잭션을 롤백한다고 적는다. 커밋을 잊은 채 연결을 닫으면 작업이 조용히 사라진다는 뜻이다.

    트랜잭션이 의도하지 않은 곳에서 끝나는 경우도 알아야 한다. 매뉴얼에 따르면 트랜잭션을 새로 시작하면 진행 중이던 트랜잭션이 커밋된다. START TRANSACTION을 두 번 연달아 쓰면 첫 번째 트랜잭션이 그 순간 확정된다는 뜻이다. 데이터베이스 입문에서 본 것처럼 CREATE TABLE, ALTER TABLE 같은 DDL도 실행 전에 현재 트랜잭션을 암묵적으로 커밋한다. 트랜잭션 도중에 DDL을 실행하고 나중에 ROLLBACK하면 DDL 이전의 변경은 이미 확정되어 되돌아오지 않는다.

    START TRANSACTION에는 수식어를 붙일 수 있다. READ ONLY로 연 트랜잭션에서 다른 트랜잭션에 보이는 테이블을 바꾸려 하면 ERROR 1792 (25006): Cannot execute statement in a READ ONLY transaction.이 나고, 트랜잭션은 읽기 전용 상태로 계속된다. 매뉴얼은 읽기 전용임을 알 수 있는 트랜잭션에 대해서는 InnoDB가 트랜잭션 ID를 붙이는 비용을 생략할 수 있다고 설명한다. 이 트랜잭션 ID가 MVCC에서 하는 역할은 뒤에서 본다. WITH CONSISTENT SNAPSHOT은 시작하는 순간에 바로 스냅샷을 만든다. 이 수식어는 격리 수준을 바꾸지 않으며, 매뉴얼에 따르면 일관된 읽기를 허용하는 격리 수준은 REPEATABLE READ뿐이라 다른 격리 수준에서는 경고와 함께 무시된다. 마지막으로, 저장 프로시저나 트리거 같은 저장 프로그램 안에서 BEGIN은 트랜잭션 시작이 아니라 BEGIN ... END 블록의 시작으로 해석되므로 거기서는 START TRANSACTION을 써야 한다. 저장 프로그램은 09회에서 다룬다.

    문장하는 일주의
    START TRANSACTION / BEGIN트랜잭션을 연다. 끝날 때까지 자동 커밋이 꺼진다진행 중이던 트랜잭션은 이 순간 커밋된다
    COMMIT변경을 영구화하고 다른 세션에 보이게 한다. 잠금을 모두 푼다자동 커밋 상태에서는 각 문장 끝에 서버가 대신 실행한 셈이다
    ROLLBACK현재 트랜잭션의 변경을 모두 취소한다. 잠금을 모두 푼다트랜잭션을 지원하지 않는 엔진의 테이블 변경은 되돌리지 못하고 경고가 난다
    SET autocommit = 0세션에 항상 트랜잭션이 열려 있게 한다커밋 없이 세션이 끝나면 롤백된다
    DDL실행 전에 현재 트랜잭션을 암묵적으로 커밋한다DDL 이전의 변경은 롤백 대상에서 빠진다

    문장 하나가 실패하면: 문장 롤백과 트랜잭션 롤백

    트랜잭션 안의 문장 하나가 오류를 내면 무엇이 되돌려지는가. 직관적으로는 "트랜잭션 전체가 실패했으니 전부 되돌아간다"고 생각하기 쉽다. MySQL InnoDB는 그렇게 동작하지 않는다. 매뉴얼의 InnoDB 오류 처리 절은 InnoDB가 어떤 때는 실패한 문장만, 어떤 때는 트랜잭션 전체를 되돌린다고 적고, 경우를 다음처럼 나눈다.

    오류되돌리는 범위
    교착 상태(deadlock)트랜잭션 전체. 매뉴얼은 트랜잭션 전체를 재시도하라고 적는다
    잠금 대기 시간 초과(lock wait timeout)기본은 기다리다 실패한 그 문장만. 서버를 --innodb-rollback-on-timeout으로 시작하면 트랜잭션 전체
    중복 키(duplicate key)IGNORE를 쓰지 않았다면 그 문장
    테이블스페이스 공간 부족(Table is full)그 문장
    행이 너무 김(row too long)그 문장
    그 밖의 오류(대부분 MySQL 계층에서 검출)그 문장

    이 표가 말하는 바는 분명하다. 교착 상태를 빼면 대부분의 오류는 그 문장 하나만 무효로 만들고, 트랜잭션은 열린 채로 남는다. 앞서 실행한 문장들의 변경도 그대로 남아 있다. 그 상태에서 무엇을 할지는 클라이언트가 정한다. 다음 순서를 mysql 클라이언트에서 실행한다고 하자.

    START TRANSACTION;
UPDATE account SET balance = balance - 30000 WHERE id = 1;   -- 1 row affected
INSERT INTO account VALUES (1, '중복', 0);                     -- ERROR 1062 (23000): Duplicate entry '1' for key 'account.PRIMARY'
COMMIT;                                                       -- 첫 UPDATE가 확정된다
SELECT balance FROM account WHERE id = 1;                     -- 20000

    두 번째 문장은 기본 키 중복으로 실패했다. InnoDB는 그 INSERT만 되돌린다. 트랜잭션은 계속 열려 있고, 첫 UPDATE의 변경도 살아 있다. 사용자가 오류를 보고도 COMMIT을 실행하면 출금만 확정되고 입금은 일어나지 않은 상태가 된다. 오류가 났을 때 트랜잭션 전체를 버리는 것은 데이터베이스의 자동 동작이 아니라 클라이언트의 책임이다. 애플리케이션 코드에서 예외를 잡으면 반드시 ROLLBACK을 호출해야 하는 이유가 이것이다.

    문장 롤백에 관해 하나 더 알아 둘 점이 있다. 매뉴얼은 SQL 문장 하나를 롤백할 때는 잠금이 풀리지 않는다고 적는다. 실패한 문장이 실행 도중 잡은 행 잠금은 트랜잭션이 끝날 때까지 남는다. MySQL 8.4.13에서 위의 중복 키 INSERT를 실행한 뒤 Performance Schema의 data_locks를 보면, 실패한 문장이 중복을 확인하며 1번 레코드에 건 공유 잠금(S,REC_NOT_GAP)이 그대로 남아 있고, 다른 세션의 SELECT ... FOR UPDATE NOWAIT은 1번 행에서 3572 오류로 실패한다. 오류를 무시하고 트랜잭션을 오래 열어 두면, 쓰지도 않을 행을 다른 트랜잭션이 기다리게 된다. 그리고 앞 절에서 본 "0개 행 갱신"은 오류가 아니므로 어떤 롤백도 일어나지 않는다. 이체처럼 "반드시 한 행이 바뀌어야 하는" 문장은 애플리케이션이 바뀐 행 수(affected rows)를 확인해 기대와 다르면 스스로 롤백해야 한다.

    세이브포인트: 트랜잭션 안의 부분 취소

    트랜잭션 전체가 아니라 일부만 되돌리고 싶을 때는 세이브포인트(savepoint)를 쓴다. SAVEPOINT 이름으로 지점을 표시하고, ROLLBACK TO SAVEPOINT 이름으로 그 지점 이후의 변경만 취소한다. 이 문장은 트랜잭션을 끝내지 않는다. 매뉴얼에 따르면 같은 이름의 세이브포인트를 다시 만들면 예전 것은 지워지고, 지정한 세이브포인트보다 뒤에 만든 세이브포인트들은 롤백과 함께 삭제되며, COMMIT이나 이름 없는 ROLLBACK을 실행하면 모든 세이브포인트가 사라진다. 없는 이름을 지정하면 ERROR 1305 (42000): SAVEPOINT ... does not exist가 난다.

    START TRANSACTION;
UPDATE account SET balance = balance - 10000 WHERE id = 1;   -- 1번: 40000
SAVEPOINT after_withdraw;
UPDATE account SET balance = balance + 10000 WHERE id = 2;   -- 2번: 20000
ROLLBACK TO SAVEPOINT after_withdraw;                        -- 2번만 10000으로 돌아간다
UPDATE account SET balance = balance + 10000 WHERE id = 2;   -- 다시 입금: 20000
COMMIT;                                                      -- 최종 (1, 40000), (2, 20000)

    여기서도 잠금은 남는다. 매뉴얼은 ROLLBACK TO SAVEPOINT가 세이브포인트 이후의 행 변경은 되돌리지만, 세이브포인트 이후에 메모리에 저장된 행 잠금은 풀지 않는다고 적는다. 위 예에서 2번 계좌의 행 잠금은 세이브포인트로 되돌린 뒤에도 커밋할 때까지 유지된다. MySQL 8.4.13에서 세이브포인트 뒤에 갱신한 행을 되돌린 다음 data_locks를 보면, 값은 원래대로 돌아왔는데 그 행의 배타 잠금(X,REC_NOT_GAP)은 그대로 남아 있었다. 세이브포인트는 "데이터의 부분 취소"이지 "잠금의 부분 해제"가 아니다. JDBC의 Connection.setSavepoint()와 rollback(Savepoint)가 이 기능에 대응하고, 스프링의 중첩 트랜잭션 전파(NESTED)도 JDBC 세이브포인트를 쓴다. 스프링 트랜잭션은 로드맵의 다음 강의들에서 다룬다.

    애플리케이션에서 경계를 긋는 법: 트랜잭션은 커넥션에 속한다

    애플리케이션 쪽에서 반드시 붙잡아야 할 사실이 하나 있다. 트랜잭션은 세션, 즉 데이터베이스 연결 하나에 속한다. START TRANSACTION을 실행한 연결과 UPDATE를 실행한 연결이 다르면 두 문장은 같은 트랜잭션이 아니다. 자바에서 이 연결은 java.sql.Connection 객체다. 같은 트랜잭션에 속해야 할 문장은 모두 같은 Connection으로 실행해야 한다.

    JDBC 명세는 경계 긋기를 자동 커밋 모드로 표현한다. Connection의 Javadoc(JDK 21)은 새 연결이 기본적으로 자동 커밋 모드이고, 이 모드에서는 모든 SQL 문장이 각각의 트랜잭션으로 실행·커밋되며, 자동 커밋을 끄면 문장들이 commit이나 rollback 호출로 끝나는 트랜잭션으로 묶인다고 적는다. commit()과 rollback()은 그 연결이 쥐고 있던 데이터베이스 잠금을 놓는다. 트랜잭션 도중 setAutoCommit으로 모드를 바꾸면 그 순간 트랜잭션이 커밋된다는 주의 사항도 Javadoc에 있다.

    import java.sql.Connection;
import java.sql.PreparedStatement;
import java.sql.SQLException;
import javax.sql.DataSource;

public class TransferService {

    private final DataSource dataSource;

    public TransferService(DataSource dataSource) {
        this.dataSource = dataSource;
    }

    public void transfer(long fromId, long toId, long amount) throws SQLException {
        try (Connection con = dataSource.getConnection()) {
            con.setAutoCommit(false);          // 이 줄부터 문장들이 한 트랜잭션으로 묶인다
            try {
                withdraw(con, fromId, amount);
                deposit(con, toId, amount);
                con.commit();                  // 두 변경이 함께 확정된다
            } catch (SQLException | RuntimeException e) {
                con.rollback();                // 두 변경이 함께 취소된다
                throw e;
            } finally {
                con.setAutoCommit(true);       // 풀에 돌려주기 전에 원래 모드로
            }
        }
    }

    private void withdraw(Connection con, long id, long amount) throws SQLException {
        String sql = "UPDATE account SET balance = balance - ? WHERE id = ? AND balance >= ?";
        try (PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setLong(1, amount);
            ps.setLong(2, id);
            ps.setLong(3, amount);
            if (ps.executeUpdate() != 1) {
                throw new IllegalStateException("출금 실패: 계좌가 없거나 잔액 부족, id=" + id);
            }
        }
    }

    private void deposit(Connection con, long id, long amount) throws SQLException {
        String sql = "UPDATE account SET balance = balance + ? WHERE id = ?";
        try (PreparedStatement ps = con.prepareStatement(sql)) {
            ps.setLong(1, amount);
            ps.setLong(2, id);
            if (ps.executeUpdate() != 1) {
                throw new IllegalStateException("입금 실패: 계좌 없음, id=" + id);
            }
        }
    }
}

    이 코드는 JDK 21의 javac로 컴파일만 확인했다(실행에는 MySQL과 JDBC 드라이버가 필요하다). 흐름을 따라가 보자. setAutoCommit(false)가 경계의 시작이다. 이후 같은 con으로 실행한 두 UPDATE는 한 트랜잭션에 속한다. withdraw는 앞 절의 교훈을 두 가지 반영한다. 하나는 바뀐 행 수가 1이 아니면 예외를 던지는 것이다. 0개 행 갱신은 데이터베이스가 오류로 알려 주지 않으므로 애플리케이션이 직접 실패로 바꿔야 한다. 다른 하나는 잔액 확인을 WHERE balance >= ? 조건으로 UPDATE 안에 넣은 것이다. "읽고 확인한 뒤 쓴다"를 두 문장으로 나누면 그 사이에 다른 트랜잭션이 끼어들 수 있다는 것이 첫 절의 셋째 문제였다. 조건을 UPDATE 안에 넣으면 확인과 변경이 한 문장 안에서, 그 행의 잠금을 쥔 상태로 일어난다. 왜 그런지는 뒤의 잠금 절에서 확인한다.

    예외가 나면 catch에서 rollback()을 호출한 뒤 예외를 다시 던진다. 앞 절에서 본 것처럼 문장 하나가 실패해도 트랜잭션은 열려 있으므로 이 호출이 없으면 출금만 남은 연결이 풀로 돌아갈 수 있다. finally에서 자동 커밋을 되돌리는 이유는 커넥션 풀 때문이다. 풀의 연결은 닫히지 않고 다음 요청에 재사용되므로, 자동 커밋이 꺼진 채 돌려주면 다음 사용자가 의도하지 않은 트랜잭션 안에서 일하게 된다.

    스프링을 쓰면 이 경계 코드를 직접 쓰지 않는다. 그러나 아래에서 일어나는 일은 같다. Spring Framework 6.2.x와 7.0.10의 DataSourceTransactionManager 소스를 열어 보면, 트랜잭션을 시작할 때 연결이 자동 커밋 모드이면 con.setAutoCommit(false)로 바꾸고 나중에 되돌려야 한다고 표시해 두며, 커밋과 롤백은 각각 con.commit(), con.rollback() 호출이고, 트랜잭션이 끝난 뒤 정리 단계에서 con.setAutoCommit(true)로 복원한다. 위 코드의 setAutoCommit(false), commit, rollback, finally가 그대로 프레임워크 안으로 옮겨 간 것이다. 스프링이 같은 트랜잭션의 문장들에 같은 연결을 쓰게 만드는 방법(스레드에 연결을 묶어 두는 방식)은 로드맵의 스프링 DB 강의에서 다룬다.

    ACID: 네 글자가 약속하는 것, 그리고 원자성의 장치

    트랜잭션이 지켜야 할 성질을 흔히 ACID라는 네 글자로 정리한다. 원자성(Atomicity)은 트랜잭션의 변경이 전부 반영되거나 전혀 반영되지 않는다는 성질이다. 일관성(Consistency)은 트랜잭션이 데이터베이스를 규칙을 만족하는 상태에서 다시 규칙을 만족하는 상태로 옮긴다는 성질이다. 격리성(Isolation)은 동시에 실행되는 트랜잭션이 서로의 중간 상태에 정해진 정도 이상으로 간섭하지 않는다는 성질이다. 지속성(Durability)은 커밋이 성공했다고 응답한 변경은 이후 장애가 나도 사라지지 않는다는 성질이다.

    MySQL 매뉴얼의 "InnoDB and the ACID Model" 절은 각 글자를 MySQL의 어떤 기능이 맡는지 대응시켜 놓았다. 이 대응표를 보면 ACID가 추상적인 구호가 아니라 구체적인 장치와 설정의 묶음이라는 것이 드러난다.

    속성매뉴얼이 꼽는 관련 기능
    원자성InnoDB 트랜잭션, autocommit 설정, COMMIT, ROLLBACK
    일관성충돌로부터 데이터를 보호하는 InnoDB 내부 처리: 이중 쓰기 버퍼(doublewrite buffer), 충돌 복구(crash recovery)
    격리성autocommit 설정, 격리 수준과 SET TRANSACTION, InnoDB 잠금의 세부(Performance Schema의 data_locks, data_lock_waits로 관찰)
    지속성이중 쓰기 버퍼, innodb_flush_log_at_trx_commit, sync_binlog, innodb_file_per_table, 저장 장치의 쓰기 버퍼와 배터리 백업 캐시, 운영체제의 fsync() 지원, 무정전 전원 장치, 백업 전략 등

    지속성 행이 눈에 띈다. 매뉴얼은 지속성이 MySQL 소프트웨어 기능과 하드웨어 구성의 상호작용에 달려 있다고 적는다. 데이터베이스가 아무리 올바르게 동작해도 디스크가 "썼다"고 거짓말을 하면 지속성은 깨진다. 이 이야기는 지속성 절에서 다시 한다. 먼저 원자성이 어떻게 구현되는지 보자.

    원자성의 장치: 제자리 갱신과 언두 로그

    비유 상자에서 말했듯이 InnoDB는 변경을 미뤄 두지 않는다. 매뉴얼의 다중 버전 절에 따르면 클러스터형 인덱스의 레코드는 제자리에서 갱신(updated in-place)된다. 06회에서 본 것처럼 InnoDB 테이블의 행 자체가 기본 키 순서로 정렬된 클러스터형 인덱스의 리프 레코드이므로, UPDATE는 그 레코드의 값을 직접 바꾼다. 대신 바꾸기 전의 내용을 다시 만들 수 있는 정보를 언두 로그 레코드로 남긴다. 언두 로그 레코드는 롤백 세그먼트(rollback segment)에 기록되고, 롤백 세그먼트는 언두 테이블스페이스(undo tablespace)에 저장된다.

    레코드와 언두 로그는 숨은 열로 연결된다. 매뉴얼은 InnoDB가 저장하는 각 행에 세 개의 필드를 덧붙인다고 설명한다. 6바이트의 DB_TRX_ID는 그 행을 마지막으로 삽입하거나 갱신한 트랜잭션의 식별자다. 삭제도 내부적으로는 "삭제됨" 표시 비트를 켜는 갱신으로 처리된다. 7바이트의 DB_ROLL_PTR는 롤 포인터(roll pointer)라고 부르며, 롤백 세그먼트에 기록된 언두 로그 레코드를 가리킨다. 행이 갱신되었다면 그 언두 레코드에 갱신 전 내용을 다시 만드는 데 필요한 정보가 들어 있다. 6바이트의 DB_ROW_ID는 행이 삽입될 때마다 단조 증가하는 행 ID로, 테이블에 적당한 키가 없어 InnoDB가 클러스터형 인덱스를 스스로 만들 때만 인덱스에 쓰인다.

    클러스터형 인덱스 리프 (id = 1 의 레코드)
+----+--------+---------+-----------+-------------+
| id | owner  | balance | DB_TRX_ID | DB_ROLL_PTR |
| 1  | 김하늘 | 20000   | 101       | ----+       |
+----+--------+---------+-----------+-----|-------+
                                          |
                                          v
                  언두 로그 레코드 (롤백 세그먼트)
                  +----------------------------------+
                  | 갱신 전 balance = 50000           |
                  | 그 버전의 DB_TRX_ID = 100         |
                  | 더 이전 버전으로 가는 포인터 ...   |
                  +----------------------------------+

트랜잭션 101 이 ROLLBACK 하면 -> 언두 레코드로 balance 를 50000 으로 복원
트랜잭션 101 이 COMMIT 하면   -> 레코드는 그대로, 언두 레코드는 필요 없어질 때 정리

    롤백은 이 연결을 거꾸로 따라가는 일이다. 매뉴얼은 InnoDB가 트랜잭션 롤백에 필요한 실행 취소 작업을 롤백 세그먼트의 정보로 수행한다고 적는다. 그래서 롤백의 비용은 트랜잭션이 바꾼 양에 비례한다. 큰 트랜잭션은 커밋보다 롤백이 훨씬 비싸다. 커밋은 "이제 되돌리지 않는다"고 표시하는 일이지만, 롤백은 바꾼 행 하나하나를 언두 레코드로 다시 고쳐 써야 하기 때문이다. 매뉴얼은 충돌 복구에서 미완료 트랜잭션을 롤백하는 데 걸리는 시간이 서버 부하에 따라 그 트랜잭션이 중단 전까지 실행된 시간의 서너 배가 될 수 있다고 적는다.

    언두 로그는 두 종류다. 매뉴얼에 따르면 삽입 언두 로그(insert undo log)는 트랜잭션 롤백에만 필요하므로 트랜잭션이 커밋되는 즉시 버릴 수 있다. 새로 넣은 행을 취소하는 방법은 그 행을 지우는 것뿐이고, 커밋 전에는 그 행이 다른 트랜잭션에 보이지 않으니 더 이전 버전을 찾을 사람도 없다. 갱신 언두 로그(update undo log)는 사정이 다르다. 롤백뿐 아니라 일관된 읽기에도 쓰이므로, 그 정보로 이전 버전을 만들어야 할지도 모르는 스냅샷을 가진 트랜잭션이 하나도 남지 않을 때까지 버릴 수 없다. 삭제도 마찬가지로 즉시 일어나지 않는다. DELETE는 행에 삭제 표시만 하고, 실제로 행과 인덱스 레코드를 지우는 것은 그 삭제의 언두 레코드를 버릴 때이며, 이 정리 작업을 퍼지(purge)라고 부른다. 언두 로그가 "되돌리기"와 "옛 버전 보여 주기"라는 두 역할을 겸한다는 사실이 MVCC 절의 출발점이 된다.

    지속성: 커밋이 끝났다는 말의 의미

    커밋이 성공했다는 응답을 받았다면 그 변경은 어디에 있는가. "데이터 파일에 기록되었다"고 답하기 쉽지만 InnoDB에서는 그렇지 않다. 06회까지 본 것처럼 InnoDB는 데이터를 페이지 단위로 읽어 버퍼 풀(buffer pool)이라는 메모리 영역에 올려 두고 작업한다. UPDATE가 바꾸는 것은 버퍼 풀에 있는 페이지다. 이렇게 메모리에서 바뀌었지만 아직 데이터 파일에 쓰이지 않은 페이지를 더티 페이지(dirty page)라고 부르고, 더티 페이지는 커밋과 무관하게 나중에 백그라운드에서 데이터 파일로 내려간다.

    그렇다면 커밋 직후 전원이 나가면 버퍼 풀의 변경은 사라지지 않는가. 이것을 막는 장치가 리두 로그다. 매뉴얼은 리두 로그를 충돌 복구 중에 미완료 트랜잭션이 쓴 데이터를 바로잡는 데 쓰는 디스크 기반 자료 구조라고 정의하고, 평상시에는 SQL 문장이 일으킨 테이블 데이터 변경 요청을 기록한다고 설명한다. 리두 로그는 변경이 일어날 때마다 뒤에 덧붙여지며, 그 진행은 계속 증가하는 LSN(log sequence number) 값으로 표현된다. 그리고 매뉴얼에 따르면 예기치 않은 종료 전에 데이터 파일 갱신을 끝내지 못한 변경은 서버가 다시 시작할 때 연결을 받기 전에 자동으로 재적용된다.

    이 설계의 요점은 "커밋할 때 디스크에 반드시 내려야 하는 것"을 데이터 페이지가 아니라 리두 로그로 바꾼 데 있다. 데이터 페이지를 커밋마다 쓰려면 트랜잭션이 건드린 페이지들이 흩어져 있는 위치마다 페이지 전체를 써야 한다. 리두 로그는 변경 내용만 로그 끝에 순서대로 덧붙인다. 커밋이 기다리는 것은 이 덧붙인 로그가 저장 장치에 내려가는 것뿐이고, 페이지는 나중에 모아서 쓴다. 변경을 먼저 로그에 기록하고 데이터 페이지는 나중에 쓰는 이 방식을 일반적으로 로그 선행 기록(write-ahead logging)이라고 부른다.

    "로그를 디스크로 내린다"의 정확한 시점은 innodb_flush_log_at_trx_commit 설정이 정한다. 기본값은 1이다. 매뉴얼은 이 변수가 커밋 작업의 엄격한 ACID 준수와, 커밋 관련 입출력을 재배치해 묶어서 할 때 얻는 더 높은 성능 사이의 균형을 조절한다고 설명하고, 값을 바꾸면 성능은 좋아질 수 있지만 충돌 시 트랜잭션을 잃을 수 있다고 적는다.

    값커밋할 때 하는 일잃을 수 있는 것
    1 (기본값)커밋마다 로그를 쓰고 디스크로 내린다매뉴얼: 완전한 ACID 준수에 필요한 설정
    0로그 쓰기와 디스크 내리기를 초당 한 번 한다로그가 내려가지 않은 트랜잭션은 충돌 시 사라질 수 있다
    2커밋마다 로그를 쓰고, 디스크 내리기는 초당 한 번 한다로그가 내려가지 않은 트랜잭션은 충돌 시 사라질 수 있다

    매뉴얼은 0과 2의 "초당 한 번"이 100% 보장되지 않는다고 덧붙인다. DDL이나 InnoDB 내부 활동 때문에 더 자주 내려갈 수도, 스케줄링 문제로 덜 자주 내려갈 수도 있으므로 잃는 양도 그만큼 달라진다. 중요한 점은 어떤 설정에서든 충돌 복구 자체는 동작하며, 매뉴얼의 표현대로 트랜잭션은 전부 적용되거나 전부 지워진다는 것이다. 0과 2가 포기하는 것은 원자성이 아니라 지속성이다. 커밋 응답을 받은 트랜잭션이 재시작 후 없던 일이 될 수 있다. 쓰기가 아주 많고 최근 1초 정도의 손실을 감수할 수 있는 환경에서만 고려할 선택이다.

    로그만으로 해결되지 않는 문제도 있다. 데이터 페이지를 데이터 파일에 쓰는 도중 전원이 나가면 페이지의 앞부분은 새 내용, 뒷부분은 옛 내용인 채로 남을 수 있다. 리두 로그는 페이지에 대한 변경 요청을 기록한 것이라 망가진 페이지 위에 다시 적용할 수 없다. 이중 쓰기 버퍼가 이 경우를 맡는다. 매뉴얼에 따르면 InnoDB는 버퍼 풀에서 내려보내는 페이지를 데이터 파일의 제자리에 쓰기 전에 먼저 이중 쓰기 버퍼라는 저장 영역에 쓰고, 페이지 쓰기 도중 운영체제·저장 장치 문제나 프로세스 종료가 일어나면 충돌 복구 중에 이중 쓰기 버퍼에서 온전한 사본을 찾는다. 데이터를 두 번 쓰지만, 이중 쓰기 버퍼에는 큰 덩어리로 순차 기록하고 fsync()를 한 번 호출하므로 입출력이 두 배가 되지는 않는다고 매뉴얼은 설명한다. MySQL 8.0.20부터는 이 저장 영역이 시스템 테이블스페이스가 아니라 별도의 이중 쓰기 파일에 있다.

    마지막으로 매뉴얼이 붙여 둔 경고를 옮겨 둔다. 많은 운영체제와 일부 디스크 하드웨어가 디스크로 내리는 작업을 "속인다". 장치가 실제로는 쓰기 캐시에만 두고 완료를 응답하면, 권장 설정에서도 트랜잭션의 지속성은 보장되지 않고 최악의 경우 정전이 InnoDB 데이터를 손상시킬 수 있다고 매뉴얼은 적는다. ACID 대응표의 지속성 행에 저장 장치의 쓰기 버퍼와 배터리 백업 캐시, 무정전 전원 장치가 들어 있는 이유가 이것이다. 지속성은 데이터베이스 혼자 지킬 수 있는 약속이 아니다.

    커밋 응답 전에 디스크로 내려가는 것은 리두 로그이고, 더티 페이지는 나중에 이중 쓰기 버퍼를 거쳐 데이터 파일로 간다는 것을 보여 준다. 위쪽 절반은 "메모리" 영역, 아래쪽 절반은 "디스크" 영역으로 가로 점선으로 나눈 구조도. 메모리 영역 왼쪽에 사각형 "버퍼 풀"이 있고 그 안에 주황색으로 칠한 작은 페이지 두 개와 라벨 "더티 페이지". 메모리 영역 오른쪽에 가는 막대 모양 "리두 로그 버퍼". 맨 위 중앙에 사람 아이콘과 말풍선 "COMMIT". 리두 로그 버퍼에서 아래 디스크 영역의 긴 띠 모양 "리두 로그 파일"로 굵은 빨간 화살표, 화살표 옆 라벨 "커밋 전에 디스크로". 리두 로그 파일에서 위쪽 사람 아이콘으로 초록 화살표 라벨 "성공 응답". 버퍼 풀에서 디스크 영역의 작은 상자 "이중 쓰기 버퍼"로 가는 회색 점선 화살표 라벨 "나중에", 이중 쓰기 버퍼에서 큰 원통 "데이터 파일"로 회색 점선 화살표. 디스크 영역 오른쪽 아래에 순환 화살표 아이콘과 라벨 "재시작 시 리두 재적용". 평면 다이어그램 스타일, 흰 배경. 커밋 응답을 기다리게 하는 것은 리두 로그를 디스크로 내리는 일뿐이다. 데이터 페이지는 나중에 이중 쓰기 버퍼를 거쳐 제자리에 쓰인다.

    일관성과 격리성: 누가 무엇을 지키는가

    ACID의 C는 네 글자 중 가장 오해가 많다. 두 가지 의미가 섞여 쓰이기 때문이다. 하나는 데이터가 규칙을 만족한다는 논리적 의미다. 기본 키는 중복되지 않고, 외래 키는 존재하는 행을 가리키며, NOT NULL 열은 비어 있지 않다. 07회에서 본 이런 선언적 제약은 데이터베이스가 문장마다 검사한다. MySQL은 8.0.16부터 CHECK 제약도 실제로 검사한다. 이 규칙들에 대해서는 데이터베이스가 일관성을 직접 지킨다. 위반하는 문장은 실패하고, 그 문장은 앞 절의 표대로 되돌려진다.

    그러나 "두 계좌의 잔액 합은 이체 전후에 같다" 같은 업무 규칙은 테이블 선언에 적을 수 없다. 이 불변식은 트랜잭션이 올바르게 작성되었을 때만 지켜진다. 출금 문장과 입금 문장을 같은 트랜잭션에 넣고, 실패하면 롤백하는 일은 애플리케이션이 한다. 데이터베이스가 보장하는 것은, 각 트랜잭션이 혼자 실행되었을 때 규칙을 지키도록 작성되어 있다면 원자성 덕분에 중간 상태가 확정되지 않고, 격리성 덕분에 동시에 실행해도 그 성질이 깨지지 않는다는 것이다. 이런 의미에서 C는 나머지 세 글자와 애플리케이션이 함께 만들어 내는 결과에 가깝다.

    다른 하나는 물리적 의미다. 앞의 대응표에서 MySQL 매뉴얼은 일관성 항목에 이중 쓰기 버퍼와 충돌 복구를 넣고, 일관성이 주로 충돌로부터 데이터를 보호하는 InnoDB 내부 처리와 관련된다고 설명한다. 장애가 나도 데이터 파일과 인덱스가 깨진 페이지나 반쯤 적용된 변경 없이 온전한 상태로 돌아온다는 뜻이다. 두 의미 모두 "데이터가 믿을 수 있는 상태에 있다"는 같은 방향을 가리키지만, 책임지는 주체가 다르다는 점을 구분해 두자.

    격리성으로 넘어가자. 가장 강한 격리는 트랜잭션들이 동시에 실행되었더라도 그 결과가 어떤 순서로 하나씩 차례로 실행한 결과와 같다는 성질이다. 이것을 직렬 가능성(serializability)이라고 부른다. 정말로 하나씩 차례로 실행하면 격리 문제는 사라지지만, 한 트랜잭션이 디스크나 네트워크를 기다리는 동안 다른 모든 트랜잭션이 멈춘다. 반대로 아무 제약 없이 동시에 실행하면 첫 절의 셋째 문제처럼 결과가 틀린다. 데이터베이스는 그 사이 어딘가에서 "어떤 간섭은 허용하고 어떤 간섭은 막을지"를 고를 수 있게 하는데, 그 선택지가 격리 수준(isolation level)이다.

    이 장의 핵심

    원자성은 언두 로그로 되돌리는 능력, 지속성은 커밋 전에 리두 로그를 디스크로 내리는 규칙, 격리성은 MVCC와 잠금으로 동시 실행의 간섭을 제한하는 규칙이다. 일관성은 선언된 제약에 대해서는 데이터베이스가, 업무 불변식에 대해서는 트랜잭션을 올바르게 나눈 애플리케이션이 지킨다.

    격리 수준과 이상 현상: 무엇이 끼어들 수 있는가

    격리 수준은 "동시에 실행되는 트랜잭션 때문에 생길 수 있는 이상 현상(anomaly) 중 어떤 것을 허용하는가"로 정의된다. SQL 표준은 세 가지 현상을 정의하고, 네 격리 수준을 각 수준에서 일어나서는 안 되는 현상으로 구분한다. 표준 문서를 직접 인용하는 대신, 표준의 정의를 그대로 옮겨 설명하는 PostgreSQL 문서의 서술을 기준으로 삼는다. 아래 실행표에서 세션 A와 세션 B는 각각 START TRANSACTION으로 트랜잭션을 연 상태이고, 시점은 위에서 아래로 흐른다.

    더티 리드(dirty read)

    커밋되지 않은 다른 트랜잭션이 쓴 데이터를 읽는 현상이다.

    시점세션 A세션 B
    1UPDATE account SET balance = 0 WHERE id = 1;
    2SELECT balance FROM account WHERE id = 1; → 0을 읽는다면 더티 리드
    3ROLLBACK;

    세션 A가 읽은 0은 커밋된 역사 어디에도 존재한 적이 없는 값이다. B가 롤백했으므로 1번 계좌의 잔액은 처음부터 끝까지 50,000원이었다. A가 이 값으로 "잔액이 없으니 대출을 거절한다" 같은 결정을 내렸다면, 일어나지도 않은 사건에 근거한 결정이 된다.

    반복 불가능한 읽기(non-repeatable read)

    트랜잭션이 이전에 읽은 데이터를 다시 읽었는데, 첫 읽기 이후 커밋한 다른 트랜잭션이 그 데이터를 바꿔 놓아서 값이 달라지는 현상이다.

    시점세션 A세션 B
    1SELECT balance FROM account WHERE id = 1; → 50000
    2UPDATE account SET balance = 20000 WHERE id = 1;
    3COMMIT;
    4SELECT balance FROM account WHERE id = 1; → 20000이면 반복 불가능한 읽기

    더티 리드와 달리 A가 읽은 두 값은 모두 커밋된 값이다. 문제는 한 트랜잭션 안에서 같은 질문에 다른 답이 나온다는 것이다. 월말 정산 트랜잭션이 계좌별 잔액을 읽어 합계를 낸 뒤 검증을 위해 다시 읽었는데 숫자가 다르면, 어느 쪽을 믿어야 할지 알 수 없다.

    팬텀 읽기(phantom read)

    검색 조건을 만족하는 행의 집합을 돌려주는 질의를 다시 실행했는데, 그 사이 커밋한 다른 트랜잭션 때문에 조건을 만족하는 행의 집합 자체가 바뀌는 현상이다. 반복 불가능한 읽기가 "이미 본 행의 값"이 바뀌는 것이라면, 팬텀은 "전에 없던 행"이 나타나거나 있던 행이 사라지는 것이다.

    시점세션 A세션 B
    1SELECT COUNT(*) FROM account WHERE balance >= 10000; → 2
    2INSERT INTO account VALUES (3, '박노을', 70000);
    3COMMIT;
    4SELECT COUNT(*) FROM account WHERE balance >= 10000; → 3이면 팬텀

    팬텀이 따로 분류되는 이유는 막는 방법이 다르기 때문이다. 반복 불가능한 읽기는 "이미 읽은 행"을 지키면 막을 수 있다. 팬텀은 아직 존재하지 않는 행이 문제이므로, 행이 아니라 "조건이 덮는 범위"를 지켜야 한다. 뒤에서 볼 갭 잠금과 넥스트 키 잠금이 바로 이 범위를 지키는 장치다.

    이 표를 읽을 때 두 가지를 기억해야 한다. 첫째, PostgreSQL 문서가 설명하듯 표준은 각 수준이 제공해야 할 최소한의 보호만 정한다. "허용"은 "반드시 일어난다"가 아니라 "일어나도 표준 위반이 아니다"라는 뜻이다. 실제 구현은 표보다 강할 수 있고, 뒤에서 보듯 InnoDB의 REPEATABLE READ는 평범한 SELECT에 대해 팬텀을 보이지 않는다. 둘째, SERIALIZABLE은 세 현상을 막는 것으로 정의되지 않는다. 표준은 이 수준을 직렬 가능한 트랜잭션들의 어떤 동시 실행도 그것들을 어떤 순서로 하나씩 실행한 것과 같은 효과를 낸다는 보장으로 정의하고, 그 정의 때문에 세 현상이 일어날 수 없다고 덧붙인다. 세 현상을 모두 막는다고 해서 직렬 가능해지는 것은 아니다.

    표에 없는 두 가지: 갱신 손실과 쓰기 치우침

    실무에서 더 자주 문제를 일으키는 것은 표에 없는 현상이다. 갱신 손실(lost update)은 두 트랜잭션이 같은 값을 읽고 각자 계산한 결과를 쓰면서 한쪽의 갱신이 다른 쪽에 덮여 사라지는 현상이다. 첫 절의 셋째 문제가 이것이다.

    시점세션 A (100원 출금)세션 B (200원 출금)
    1SELECT balance ... WHERE id = 1; → 1000
    2SELECT balance ... WHERE id = 1; → 1000
    3UPDATE account SET balance = 900 WHERE id = 1; 후 COMMIT
    4UPDATE account SET balance = 800 WHERE id = 1; 후 COMMIT

    300원이 출금되었는데 잔액은 800원이다. 애플리케이션이 읽은 값으로 새 값을 계산해 상수로 써 넣었기 때문에 A의 출금이 사라졌다. 쓰기 치우침(write skew)은 더 교묘하다. 병원에 "당직 의사가 최소 한 명은 있어야 한다"는 규칙이 있고, 지금 서준과 하린 두 명이 당직이다. 두 의사가 동시에 당직을 빼 달라고 요청한다. 각 트랜잭션은 "당직이 몇 명인가"를 읽어 2명임을 확인하고, 자기 행만 당직 해제로 바꾼다. 두 트랜잭션은 서로 다른 행을 썼으므로 쓰기 충돌이 없다. 둘 다 커밋하면 당직은 0명이 된다. 어느 순서로 하나씩 실행했어도 두 번째 트랜잭션은 1명을 보고 거절되었을 것이므로, 이것은 직렬 실행으로는 나올 수 없는 결과, 즉 직렬화 이상(serialization anomaly)이다. 이 두 현상이 InnoDB에서 언제 일어나고 어떻게 막는지는 MVCC와 잠금을 본 뒤에 다시 다룬다.

    MySQL InnoDB의 네 격리 수준이 실제로 하는 일

    매뉴얼에 따르면 InnoDB의 기본 격리 수준은 REPEATABLE READ다. InnoDB는 네 수준을 모두 제공하지만, 각 수준의 정의는 이상 현상 표가 아니라 "평범한 SELECT가 어떤 스냅샷을 읽는가"와 "잠금 읽기와 UPDATE, DELETE가 어떤 잠금을 거는가"라는 두 질문으로 서술된다. InnoDB를 이해하려면 이 두 질문을 분리해서 봐야 한다. 평범한 SELECT는 잠금을 걸지 않는 일관된 읽기(consistent nonlocking read)이고, 데이터를 바꾸는 문장과 FOR UPDATE, FOR SHARE가 붙은 SELECT는 잠금을 거는 읽기다.

    격리 수준평범한 SELECT잠금 읽기, UPDATE, DELETE
    READ UNCOMMITTED잠금 없이 읽되 일관된 스냅샷을 쓰지 않으므로 커밋되지 않은 변경이 보일 수 있다(더티 리드)READ COMMITTED와 같다
    READ COMMITTED같은 트랜잭션 안에서도 읽을 때마다 새 스냅샷을 만든다인덱스 레코드만 잠그고 갭은 잠그지 않는다(외래 키 검사와 중복 키 검사는 예외). 조건에 맞지 않은 행의 잠금은 WHERE 평가 뒤 푼다
    REPEATABLE READ (기본값)트랜잭션의 첫 읽기가 만든 스냅샷을 끝까지 쓴다고유 인덱스로 한 행을 찾는 조건이면 그 레코드만, 그 밖의 조건이면 훑은 범위를 갭 잠금이나 넥스트 키 잠금으로 잠근다
    SERIALIZABLE자동 커밋이 꺼져 있으면 모든 평범한 SELECT를 SELECT ... FOR SHARE로 바꿔 실행한다. 자동 커밋이 켜져 있으면 그 SELECT가 그 자체로 트랜잭션이다REPEATABLE READ와 같다

    매뉴얼은 READ COMMITTED에 대해 두 가지를 더 적는다. 갭 잠금을 쓰지 않으므로 팬텀 문제가 생길 수 있고, 이 수준에서는 행 기반 바이너리 로깅만 지원된다. 또 UPDATE가 이미 다른 트랜잭션이 잠근 행을 만나면 "반 일관된(semi-consistent) 읽기"를 해서, 그 행의 최신 커밋 버전을 MySQL 계층에 돌려주어 WHERE 조건에 맞는지 먼저 판단하게 한다. 조건에 맞지 않으면 기다리지 않고 지나간다.

    이 차이를 매뉴얼의 예로 확인해 보자. 인덱스가 없는 테이블 t(a INT NOT NULL, b INT)에 (1,2), (2,3), (3,2), (4,3), (5,2)가 커밋되어 있다. 세션 A가 트랜잭션을 열고 UPDATE t SET b = 5 WHERE b = 3을 실행한 채 커밋하지 않는다. 이어서 세션 B가 UPDATE t SET b = 4 WHERE b = 2를 실행한다. 인덱스가 없으므로 두 문장 모두 InnoDB가 만든 숨은 클러스터형 인덱스를 처음부터 끝까지 훑는다.

    행REPEATABLE READ에서 A의 잠금READ COMMITTED에서 A의 잠금READ COMMITTED에서 B의 동작
    (1,2)배타 잠금 유지잠갔다가 조건 불일치로 해제잠그고 (1,4)로 갱신
    (2,3)(2,5)로 갱신, 잠금 유지(2,5)로 갱신, 잠금 유지반 일관된 읽기로 최신 커밋 값 b=3 확인, 불일치로 통과
    (3,2)배타 잠금 유지잠갔다가 해제잠그고 (3,4)로 갱신
    (4,3)(4,5)로 갱신, 잠금 유지(4,5)로 갱신, 잠금 유지반 일관된 읽기, 통과
    (5,2)배타 잠금 유지잠갔다가 해제잠그고 (5,4)로 갱신

    REPEATABLE READ에서는 A가 다섯 행 모두의 배타 잠금을 쥐고 있으므로 B는 첫 행 (1,2)에서 A가 끝나기를 기다린다. 두 문장이 바꾸려는 행은 하나도 겹치지 않는데도 그렇다. READ COMMITTED에서는 A가 조건에 맞지 않는 행의 잠금을 풀었으므로 B는 1, 3, 5행을 갱신하고 끝난다. MySQL 8.4.13에서 B의 세션만 SET SESSION innodb_lock_wait_timeout = 1로 줄여 실행해 보면 그대로 나온다. REPEATABLE READ에서 A의 data_locks에는 숨은 클러스터형 인덱스(GEN_CLUST_INDEX)의 다섯 레코드와 마지막 레코드 뒤의 supremum 의사 레코드에 넥스트 키 잠금(X) 여섯 개가 있고, B는 1초 뒤 ERROR 1205를 받는다. READ COMMITTED에서는 A의 레코드 잠금이 갱신한 두 행의 X,REC_NOT_GAP 두 개뿐이고, B는 기다리지 않고 (1,4), (3,4), (5,4)를 만든다. 이 예는 두 가지를 알려 준다. 하나는 격리 수준이 읽기의 가시성뿐 아니라 잠금의 범위까지 바꾼다는 것이다. 다른 하나는 인덱스가 없는 UPDATE가 얼마나 많은 행을 잠그는가다. 매뉴얼은 WHERE가 인덱스 열을 쓰면 잠금을 잡고 유지하는 데 그 열만 고려하므로 사정이 달라진다고 덧붙인다. 05회와 06회에서 다룬 인덱스는 검색 속도뿐 아니라 잠금 범위를 줄이는 도구이기도 하다.

    격리 수준을 바꾸는 법

    SET TRANSACTION ISOLATION LEVEL READ COMMITTED;          -- 다음 트랜잭션 하나에만
SET SESSION TRANSACTION ISOLATION LEVEL READ COMMITTED;  -- 이 세션의 이후 트랜잭션 전부
SET GLOBAL TRANSACTION ISOLATION LEVEL READ COMMITTED;   -- 이후 새로 연결되는 세션 전부
SELECT @@SESSION.transaction_isolation, @@GLOBAL.transaction_isolation;

    매뉴얼의 SET TRANSACTION 절에 따르면 키워드 없이 쓰면 세션의 다음 트랜잭션 하나에만 적용되고 그 뒤로는 세션 값으로 돌아간다. SESSION은 이 세션의 이후 트랜잭션 모두에 적용되며 트랜잭션 도중에 실행해도 되지만 진행 중인 트랜잭션에는 영향을 주지 않는다. GLOBAL은 이후의 세션에 적용되고 이미 연결된 세션은 바뀌지 않는다. 키워드 없는 형태를 트랜잭션 도중에 실행하면 ERROR 1568 (25001): Transaction characteristics can't be changed while a transaction is in progress가 난다. 서버 전체의 기본값은 --transaction-isolation 옵션으로 정하며, 이 옵션 값은 READ-COMMITTED처럼 공백 대신 하이픈으로 쓴다. JDBC에서는 Connection.setTransactionIsolation에 상수를 넘긴다. JDK 21에서 javap -constants java.sql.Connection으로 확인한 상수 값은 TRANSACTION_READ_UNCOMMITTED 1, TRANSACTION_READ_COMMITTED 2, TRANSACTION_REPEATABLE_READ 4, TRANSACTION_SERIALIZABLE 8이다.

    엔진 속으로 1: MVCC와 읽기 뷰

    잠금 없이 읽는데 어떻게 커밋되지 않은 변경을 숨기고, 한 트랜잭션 안에서 같은 값을 반복해서 보여 줄 수 있는가. 답은 행의 여러 버전을 동시에 유지하는 다중 버전 동시성 제어(multi-version concurrency control, MVCC)다. 매뉴얼은 InnoDB를 다중 버전 저장 엔진이라고 부르며, 동시성과 롤백을 지원하기 위해 바뀐 행의 옛 버전 정보를 보관한다고 설명한다. 그 보관 장소가 원자성 절에서 본 언두 로그다. 언두 로그는 롤백에 쓰이는 동시에, 일관된 읽기를 위해 행의 이전 버전을 만드는 데 쓰인다.

    원자성 절의 그림을 시간 순으로 늘이면 버전 체인이 된다. 클러스터형 인덱스에는 항상 가장 최근 버전 하나만 있다. 그 버전의 DB_TRX_ID는 그것을 만든 트랜잭션이고, DB_ROLL_PTR는 바로 이전 버전을 다시 만들 수 있는 언두 레코드를 가리킨다. 그 언두 레코드로 만든 이전 버전에도 자신을 만든 트랜잭션 ID와 더 이전 버전으로 가는 포인터가 있다. 일관된 읽기는 최신 버전에서 출발해 "이 버전을 내가 봐도 되는가"를 묻고, 안 되면 한 단계 이전 버전을 만들어 다시 묻는다. 매뉴얼은 클러스터형 인덱스에서 레코드의 DB_TRX_ID를 검사하고, 읽는 트랜잭션이 시작된 뒤에 수정된 레코드라면 언두 로그에서 올바른 버전을 가져온다고 적는다.

    읽기 뷰: "봐도 되는가"를 판단하는 자료 구조

    "봐도 되는가"를 판단하는 기준이 읽기 뷰(read view)다. 매뉴얼은 일관된 읽기를 "어떤 시점의 데이터베이스 스냅샷을 질의에 보여 주는 것"으로 정의하고, 질의는 그 시점 전에 커밋한 트랜잭션의 변경은 보고, 그 뒤에 커밋하거나 아직 커밋하지 않은 트랜잭션의 변경은 보지 않으며, 예외로 같은 트랜잭션의 앞선 문장이 한 변경은 본다고 적는다. 이 정의를 코드로 옮긴 것이 MySQL 8.0 소스의 storage/innobase/include/read0types.h에 있는 ReadView 클래스다. 이 클래스의 핵심 필드와 소스 주석의 뜻은 다음과 같다.

    필드소스 주석이 설명하는 뜻
    m_ids스냅샷을 만든 순간 활성 상태였던 읽기-쓰기 트랜잭션들의 ID 집합
    m_up_limit_id이 값보다 작은 ID의 트랜잭션은 모두 보인다(낮은 수위선)
    m_low_limit_id이 값 이상의 ID를 가진 트랜잭션은 보이지 않는다(높은 수위선)
    m_creator_trx_id이 뷰를 만든 트랜잭션 자신의 ID

    판정 함수 changes_visible(id)는 네 단계로 동작한다. 버전을 만든 트랜잭션 ID가 m_up_limit_id보다 작거나 뷰를 만든 트랜잭션 자신이면 보인다. m_low_limit_id 이상이면 스냅샷 이후에 시작된 트랜잭션이므로 보이지 않는다. 그 사이에 있으면 m_ids를 이진 탐색해, 스냅샷 순간 진행 중이던 트랜잭션이면 보이지 않고 아니면(그 전에 이미 커밋을 마쳤으면) 보인다. 한 가지 덧붙일 사실이 있다. 매뉴얼에 따르면 트랜잭션 ID는 쓰기나 SELECT ... FOR UPDATE 같은 잠금 읽기를 할 수 있는 트랜잭션에만 필요하고, InnoDB는 읽기 전용임을 알 수 있는 트랜잭션에는 ID를 붙이지 않는다. 매뉴얼은 이렇게 불필요한 ID를 없애면 질의나 데이터 변경 문장이 읽기 뷰를 만들 때마다 참조하는 내부 자료 구조가 작아진다고 설명한다.

    격리 수준의 차이는 이 뷰를 언제 만드느냐로 정리된다. REPEATABLE READ에서는 매뉴얼의 표현대로 같은 트랜잭션의 모든 일관된 읽기가 그 트랜잭션의 첫 읽기가 만든 스냅샷을 읽는다. 스냅샷은 START TRANSACTION 순간이 아니라 첫 SELECT 순간에 만들어진다는 점에 주의하자(시작 순간에 만들고 싶으면 WITH CONSISTENT SNAPSHOT을 쓴다). READ COMMITTED에서는 일관된 읽기마다 새 스냅샷을 만든다. 같은 버전 체인, 같은 판정 함수에 대해 뷰를 만드는 시점만 바꾼 것이 두 격리 수준의 읽기 차이 전부다.

    작은 모델로 돌려 보기

    버전 체인과 읽기 뷰를 자바로 옮겨 직접 돌려 보자. 아래 코드는 InnoDB의 구현이 아니라, 앞에서 확인한 규칙(숨은 열이 가리키는 버전 체인, 소스의 changes_visible 판정, 쓰기 전까지 트랜잭션 ID를 붙이지 않는 것)만 옮긴 모델이다. 행은 계좌 하나뿐이고, 퍼지와 잠금 대기는 모델에 없다.

    import java.util.ArrayList;
import java.util.List;
import java.util.TreeSet;

public class MvccDemo {

    // 행의 한 버전: 값, 이 버전을 만든 트랜잭션 id, 이전 버전(언두 레코드)을 가리키는 포인터
    record Version(int balance, long trxId, Version prev) {}

    // 읽기 뷰: 스냅샷을 만든 순간의 활성 트랜잭션 목록과 두 경계값
    record ReadView(long creator, long upLimit, long lowLimit, TreeSet ids) {
        boolean visible(long id) {
            if (id < upLimit || id == creator) return true; // 스냅샷 전에 끝났거나 내 변경
            if (id >= lowLimit) return false;               // 스냅샷 뒤에 시작
            return !ids.contains(id);                       // 스냅샷 순간 진행 중이었으면 안 보임
        }
    }

    static class Tx {
        final String name;
        long id = 0; // 처음 쓰기 전까지는 id가 없다
        ReadView view;
        Tx(String name) { this.name = name; }
    }

    static long nextTrxId;
    static TreeSet active;
    static Version row; // 계좌 1번의 클러스터형 인덱스 레코드 하나

    static void reset() {
        nextTrxId = 101;
        active = new TreeSet<>();
        row = new Version(1000, 100, null); // 트랜잭션 100이 넣고 커밋한 초기값
    }

    static ReadView openView(Tx tx) {
        TreeSet ids = new TreeSet<>(active);
        long low = nextTrxId;
        long up = ids.isEmpty() ? low : ids.first();
        return new ReadView(tx.id, up, low, ids);
    }

    // 일관된 읽기. rr=true면 첫 읽기의 뷰를 재사용, false면 매번 새로 만든다
    static int consistentRead(Tx tx, boolean rr) {
        if (tx.view == null || !rr) tx.view = openView(tx);
        for (Version v = row; v != null; v = v.prev()) {
            if (tx.view.visible(v.trxId())) return v.balance();
        }
        throw new IllegalStateException("보이는 버전이 없다");
    }

    static int dirtyRead() { return row.balance(); }   // READ UNCOMMITTED: 최신 버전을 그대로
    static int currentRead() { return row.balance(); } // 잠금을 얻은 뒤 최신 버전을 읽는다(쓰는 문장)

    static void write(Tx tx, int balance) {
        if (tx.id == 0) { tx.id = nextTrxId++; active.add(tx.id); }
        row = new Version(balance, tx.id, row);
    }

    static void commit(Tx tx) { active.remove(tx.id); tx.view = null; }

    static void rollback(Tx tx) {
        while (row.trxId() == tx.id) row = row.prev(); // 언두로 이전 버전 복원
        active.remove(tx.id);
        tx.view = null;
    }

    static String chain() {
        List parts = new ArrayList<>();
        for (Version v = row; v != null; v = v.prev()) parts.add(v.balance() + "(trx " + v.trxId() + ")");
        return String.join(" -> ", parts);
    }

    public static void main(String[] args) {
        for (boolean rr : new boolean[] {true, false}) {
            reset();
            System.out.println("== 시나리오 1: " + (rr ? "REPEATABLE READ" : "READ COMMITTED") + " ==");
            Tx a = new Tx("A"), b = new Tx("B");
            System.out.println("A 첫 읽기         : " + consistentRead(a, rr));
            write(b, 700);
            System.out.println("B가 700으로 수정  : " + chain());
            System.out.println("A 읽기(B 미커밋)  : " + consistentRead(a, rr));
            commit(b);
            System.out.println("A 읽기(B 커밋 후) : " + consistentRead(a, rr));
        }

        reset();
        System.out.println("== 시나리오 2: 더티 리드와 롤백 ==");
        Tx b = new Tx("B");
        write(b, 500);
        System.out.println("B가 500으로 수정  : " + chain());
        System.out.println("RU 읽기           : " + dirtyRead());
        rollback(b);
        System.out.println("B 롤백 후         : " + chain());

        reset();
        System.out.println("== 시나리오 3: 갱신 손실 ==");
        Tx a = new Tx("A");
        b = new Tx("B");
        int readA = consistentRead(a, true);
        int readB = consistentRead(b, true);
        write(a, readA - 100);
        commit(a);
        write(b, readB - 200);
        commit(b);
        System.out.println("읽은 값으로 계산  : " + chain());

        reset();
        a = new Tx("A");
        b = new Tx("B");
        consistentRead(a, true);
        consistentRead(b, true);
        write(a, currentRead() - 100);
        commit(a);
        write(b, currentRead() - 200);
        commit(b);
        System.out.println("최신 값으로 계산  : " + chain());
    }
}

A 첫 읽기         : 1000
B가 700으로 수정  : 700(trx 101) -> 1000(trx 100)
A 읽기(B 미커밋)  : 1000
A 읽기(B 커밋 후) : 700
== 시나리오 2: 더티 리드와 롤백 ==
B가 500으로 수정  : 500(trx 101) -> 1000(trx 100)
RU 읽기           : 500
B 롤백 후         : 1000(trx 100)

읽은 값으로 계산  : 800(trx 102) -> 900(trx 101) -> 1000(trx 100)

    시나리오 1을 REPEATABLE READ로 한 단계씩 추적해 보자. 처음에 행은 트랜잭션 100이 만든 버전 하나이고, 다음에 발급될 ID는 101이다. A와 B는 트랜잭션을 열었지만 아직 아무것도 쓰지 않았으므로 ID가 없다(0). A의 첫 읽기가 뷰를 만든다. 활성 트랜잭션이 없으므로 m_ids는 비어 있고, m_low_limit_id는 101, m_up_limit_id도 101이다. 최신 버전의 ID 100은 101보다 작으니 보인다. 결과는 1000이다.

    B가 700을 쓰는 순간 B에 ID 101이 붙고 활성 목록에 들어간다. 행의 최신 버전은 700(trx 101)이고, 그 뒤에 1000(trx 100)이 언두로 연결된다. A의 두 번째 읽기는 첫 뷰를 재사용한다. 최신 버전의 ID 101은 m_low_limit_id(101) 이상이므로 보이지 않는다. 체인을 따라 이전 버전으로 가면 ID 100은 보인다. 결과는 1000이다. B가 커밋한 뒤 A의 세 번째 읽기도 같은 뷰를 쓰므로 같은 판정이 나오고 결과는 1000이다. 커밋 여부와 상관없이, 뷰를 만들 때 존재하지 않았던 트랜잭션의 변경은 끝까지 보이지 않는다. 이것이 InnoDB의 REPEATABLE READ가 반복 가능한 읽기를 보장하는 방식이다.

    READ COMMITTED에서는 두 번째 읽기 때 새 뷰가 만들어진다. 이때 B(101)는 활성 상태이므로 m_ids = {101}, m_up_limit_id = 101, m_low_limit_id = 102다. ID 101은 두 경계 사이에 있고 m_ids에 들어 있으므로 보이지 않아 1000을 읽는다. 더티 리드는 없다. B가 커밋한 뒤 세 번째 읽기의 새 뷰에서는 활성 목록이 비어 m_up_limit_id가 102가 되고, ID 101이 그보다 작으니 보인다. 결과는 700이다. 반복 불가능한 읽기가 일어났다. 시나리오 2는 버전 판정을 건너뛰고 최신 버전을 그대로 읽으면 롤백으로 사라질 500이 보인다는 것, 그리고 롤백이 언두 체인을 따라 이전 버전을 복원하는 일이라는 것을 보여 준다. 시나리오 3은 뒤의 갱신 손실 절에서 다시 읽는다.

    모델이 생략한 것도 분명히 해 두자. 실제 InnoDB에서 이전 버전은 언두 레코드로부터 메모리에서 다시 만들어지며, 매뉴얼은 옛 버전은 잠글 수 없고 언두 로그를 레코드의 메모리 사본에 적용해 재구성한다고 적는다. 모델은 쓰기 충돌 시의 잠금 대기를 다루지 않으므로, 시나리오들은 한 트랜잭션의 쓰기가 다른 트랜잭션이 잠근 행과 부딪히지 않는 순서로만 짜여 있다. 그리고 실제 엔진은 더 이상 어떤 뷰도 필요로 하지 않는 옛 버전을 퍼지로 정리한다.

    최신 버전에서 시작해 언두 포인터를 따라 내려가며, 읽기 뷰의 두 경계값과 활성 목록으로 각 버전의 가시성을 판정하는 과정을 보여 준다. 왼쪽에 세로로 쌓인 세 개의 카드가 아래쪽으로 화살표로 연결된 버전 체인. 맨 위 카드 "balance 700 · trx 105", 가운데 카드 "balance 900 · trx 104", 맨 아래 카드 "balance 1000 · trx 100". 맨 위 카드에만 작은 라벨 "클러스터형 인덱스의 최신 버전", 아래 두 카드에는 라벨 "언두 로그로 재구성". 카드 사이 화살표 라벨 "DB_ROLL_PTR". 오른쪽에 큰 상자 "읽기 뷰"가 있고 그 안에 세 줄 "m_up_limit_id = 103", "m_low_limit_id = 107", "m_ids = {103, 105}". 맨 위 카드 옆에 빨간 X와 라벨 "105는 m_ids에 있음", 가운데 카드 옆에 초록 체크와 라벨 "104는 보임", 가운데 카드에서 아래로 가는 탐색 화살표는 여기서 멈춤. 하단 중앙에 결과 상자 "읽은 값 900". 평면 다이어그램, 흰 배경. 일관된 읽기는 최신 버전부터 언두 포인터를 따라 내려가며, 읽기 뷰가 보이는 것으로 판정한 첫 버전을 돌려준다.

    보조 인덱스와 긴 트랜잭션

    버전 정보는 클러스터형 인덱스에만 있다. 매뉴얼에 따르면 보조 인덱스 레코드에는 숨은 시스템 열이 없고 제자리에서 갱신되지도 않는다. 보조 인덱스 열이 바뀌면 옛 보조 인덱스 레코드에 삭제 표시를 하고 새 레코드를 넣으며, 삭제 표시된 레코드는 나중에 퍼지된다. 그래서 보조 인덱스 레코드가 삭제 표시되어 있거나 그 페이지가 더 새로운 트랜잭션에 의해 갱신되었으면, InnoDB는 클러스터형 인덱스에서 레코드를 찾아 DB_TRX_ID를 확인한다. 매뉴얼은 이 경우 커버링 인덱스 기법을 쓰지 않고 클러스터형 인덱스를 조회한다고 적는다. 06회에서 본 커버링 인덱스의 이점이 동시 갱신이 많은 페이지에서는 줄어들 수 있다는 뜻이다.

    MVCC의 비용은 시간에 비례한다. 앞에서 본 것처럼 갱신 언두 로그는 그것이 필요할지도 모르는 스냅샷이 남아 있는 한 버릴 수 없다. 읽기 뷰의 m_low_limit_no 필드에 대한 소스 주석도 이 뷰가 필요로 하지 않는 언두 로그만 퍼지에서 지워질 수 있다고 적는다. 오래 열려 있는 트랜잭션 하나가 오래된 뷰를 쥐고 있으면 그 뒤에 생긴 모든 갱신의 언두가 쌓인다. 매뉴얼은 일관된 읽기만 하는 트랜잭션도 정기적으로 커밋하라고 권하며, 그렇지 않으면 InnoDB가 갱신 언두 로그의 데이터를 버리지 못해 롤백 세그먼트가 너무 커지고 언두 테이블스페이스를 채울 수 있다고 경고한다. 오래된 버전이 많을수록 일관된 읽기가 따라가야 할 체인도 길어진다. "읽기만 하니까 괜찮다"는 생각이 틀리는 지점이다.

    엔진 속으로 2: 잠금과 교착 상태

    MVCC는 읽기와 쓰기가 서로를 기다리지 않게 해 준다. 그러나 두 트랜잭션이 같은 행을 쓰려 할 때는 버전을 나누는 것으로 해결되지 않는다. 한쪽이 먼저 쓰고, 다른 쪽은 그 결과가 확정되거나 취소될 때까지 기다려야 한다. 이 순서를 정하는 장치가 잠금이다.

    공유 잠금과 배타 잠금

    매뉴얼에 따르면 InnoDB는 공유(S) 잠금과 배타(X) 잠금이라는 두 종류의 표준적인 행 수준 잠금을 구현한다. 공유 잠금은 그것을 쥔 트랜잭션이 행을 읽도록 허용하고, 배타 잠금은 행을 갱신하거나 삭제하도록 허용한다. 공유 잠금끼리는 함께 쥘 수 있지만, 한 트랜잭션이 배타 잠금을 쥔 행에 대해 다른 트랜잭션이 요청하는 잠금은 종류와 상관없이 즉시 허용되지 않는다. UPDATE와 DELETE는 대상 행에 배타 잠금을 건다. 평범한 SELECT는 앞에서 본 대로 잠금을 걸지 않으므로, 배타 잠금이 걸린 행도 기다리지 않고 언두로 이전 버전을 만들어 읽는다.

    이미 걸린 잠금 \ 요청S 요청X 요청
    S허용대기
    X대기대기

    테이블 수준에는 의도 잠금(intention lock)이 있다. 매뉴얼은 의도 잠금을 트랜잭션이 나중에 테이블의 행에 어떤 종류의 잠금을 걸려는지 나타내는 테이블 수준 잠금이라고 정의한다. 행에 공유 잠금을 걸려는 트랜잭션은 테이블에 의도 공유(IS) 잠금을, 배타 잠금을 걸려는 트랜잭션은 의도 배타(IX) 잠금을 건다. 의도 잠금은 LOCK TABLES ... WRITE 같은 테이블 전체 요청 말고는 아무것도 막지 않는다. 테이블 전체를 잠그려는 쪽이 모든 행을 뒤지지 않고도 "누군가 이 테이블의 행을 잠그고 있다"는 사실을 알 수 있게 해 주는 표지판이다.

    레코드 잠금, 갭 잠금, 넥스트 키 잠금

    InnoDB의 행 잠금은 엄밀히 말하면 인덱스 레코드에 대한 잠금이다. 매뉴얼은 레코드 잠금(record lock)이 인덱스 레코드에 대한 잠금이며, 인덱스가 하나도 없는 테이블이라도 InnoDB가 숨은 클러스터형 인덱스를 만들어 그것으로 레코드를 잠근다고 적는다. 잠금이 "행"이 아니라 "검색이 지나간 인덱스 레코드"에 걸린다는 사실이 앞의 READ COMMITTED 예에서 인덱스 없는 UPDATE가 모든 행을 잠근 이유다.

    갭 잠금(gap lock)은 인덱스 레코드 사이의 간격, 또는 첫 레코드 앞이나 마지막 레코드 뒤의 간격에 거는 잠금이다. 매뉴얼은 SELECT c1 FROM t WHERE c1 BETWEEN 10 and 20 FOR UPDATE;가 범위 안의 기존 값들 사이 간격을 모두 잠그므로, 그런 값이 이미 있든 없든 다른 트랜잭션이 c1에 15를 넣지 못하게 막는다고 설명한다. 갭 잠금은 "순수하게 억제적"이어서 그 간격에 삽입하는 것을 막는 것만이 목적이고, 갭 잠금끼리는 공유와 배타의 구별 없이 서로 충돌하지 않는다. 고유 인덱스로 고유한 한 행을 찾는 문장에는 갭 잠금이 필요 없다. 넥스트 키 잠금(next-key lock)은 인덱스 레코드에 대한 레코드 잠금과 그 레코드 앞 간격에 대한 갭 잠금을 합친 것이다. 매뉴얼에 따르면 InnoDB는 기본 격리 수준인 REPEATABLE READ에서 검색과 인덱스 스캔에 넥스트 키 잠금을 써서 팬텀 행을 막는다. 범위를 잠그면 그 범위에 새 행이 끼어들 수 없으니, 같은 범위를 다시 잠금 읽기해도 새 행이 나타나지 않는다.

    마지막으로 삽입 의도 잠금(insert intention lock)은 INSERT가 행을 넣기 전에 거는 갭 잠금의 일종이다. 매뉴얼은 같은 간격에 삽입하는 여러 트랜잭션이 간격 안의 같은 위치에 넣는 것이 아니라면 서로 기다릴 필요가 없음을 알리는 신호라고 설명한다. 삽입끼리는 서로 막지 않지만, 다른 트랜잭션이 그 간격에 갭 잠금을 쥐고 있으면 삽입은 기다린다.

    잠금 읽기: FOR UPDATE와 FOR SHARE

    평범한 SELECT로 읽은 값은 스냅샷이므로, 그 값을 근거로 무언가를 쓰는 동안 다른 트랜잭션이 원본을 바꿀 수 있다. 매뉴얼은 부모 행이 있는지 일관된 읽기로 확인한 뒤 자식 행을 넣는 예를 들며, SELECT와 INSERT 사이에 다른 세션이 부모 행을 지울 수 있으므로 안전하지 않다고 설명한다. 이럴 때 잠금 읽기(locking read)를 쓴다. SELECT ... FOR SHARE는 읽은 행에 공유 잠금을 걸어 다른 세션이 읽을 수는 있지만 내 트랜잭션이 끝날 때까지 고치지는 못하게 한다. 읽으려는 행을 아직 커밋하지 않은 다른 트랜잭션이 바꿨다면 그 트랜잭션이 끝날 때까지 기다린 뒤 최신 값을 쓴다. SELECT ... FOR UPDATE는 그 행에 UPDATE를 실행한 것과 같은 잠금을 건다. 두 잠금 모두 트랜잭션이 커밋되거나 롤백될 때 풀린다.

    MySQL 8.0에서 FOR SHARE는 예전 문법 LOCK IN SHARE MODE를 대체하며, 예전 문법도 하위 호환을 위해 남아 있다. FOR SHARE와 FOR UPDATE에는 NOWAIT과 SKIP LOCKED를 붙일 수 있다. NOWAIT은 잠금을 기다리지 않고, 요청한 행이 잠겨 있으면 즉시 ERROR 3572 (HY000): Statement aborted because lock(s) could not be acquired immediately and NOWAIT is set.으로 실패한다. SKIP LOCKED는 잠긴 행을 결과에서 빼고 즉시 돌려준다. 매뉴얼은 SKIP LOCKED가 일관되지 않은 데이터를 보여 주므로 일반적인 트랜잭션 작업에는 맞지 않고, 여러 세션이 큐처럼 쓰는 테이블에서 잠금 경합을 피할 때 쓸 수 있다고 적는다.

    기다림이 끝나지 않을 때: 잠금 대기 시간 초과와 교착 상태

    잠금을 기다리는 시간에는 상한이 있다. innodb_lock_wait_timeout의 기본값은 50초이고, 매뉴얼에 따르면 다른 InnoDB 트랜잭션이 잠근 행에 접근하려는 트랜잭션은 최대 이만큼 기다린 뒤 ERROR 1205 (HY000): Lock wait timeout exceeded; try restarting transaction을 낸다. 이때 롤백되는 것은 기다리던 그 문장뿐이고 트랜잭션은 열려 있다. 앞의 오류 처리 표 그대로다.

    교착 상태(deadlock)는 기다림이 원을 이루는 경우다. 매뉴얼은 여러 트랜잭션이 각자 다른 트랜잭션에 필요한 잠금을 쥐고 있어서 어느 쪽도 진행하지 못하는 상황으로 정의한다. 계좌 이체로 만들어 보자. 이체 X는 1번에서 2번으로, 이체 Y는 2번에서 1번으로 보낸다. 각자 출금 계좌부터 갱신한다.

    시점트랜잭션 X (1 → 2)트랜잭션 Y (2 → 1)
    1UPDATE ... WHERE id = 1; 1번 행 X 잠금 획득
    2UPDATE ... WHERE id = 2; 2번 행 X 잠금 획득
    3UPDATE ... WHERE id = 2; Y가 쥔 2번 행을 기다림
    4UPDATE ... WHERE id = 1; X가 쥔 1번 행을 기다림 → 원이 닫힘

    시점 4에서 X는 Y를, Y는 X를 기다린다. 아무리 기다려도 풀리지 않는다. 매뉴얼에 따르면 교착 상태 감지가 켜져 있으면(innodb_deadlock_detect, 기본값 ON) InnoDB는 이 상황을 감지해 트랜잭션 하나를 희생자(victim)로 골라 롤백한다. 희생자는 작은 트랜잭션을 고르려고 하며, 크기는 삽입·갱신·삭제한 행 수로 판단한다. 희생자는 ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction을 받고, 앞의 표에서 본 것처럼 트랜잭션 전체가 롤백된다. 희생자의 잠금이 풀리면 살아남은 트랜잭션이 진행한다. 위 예에서는 두 트랜잭션이 바꾼 행 수가 같으므로 어느 쪽이 희생자가 될지는 이 규칙만으로 정할 수 없다. MySQL 8.4.13과 8.0.46에서 이 순서를 실행했을 때는 원을 닫은 Y가 1213을 받았고, Y의 첫 UPDATE까지 되돌려져 X만 반영된 (1, 20000), (2, 40000)이 남았다. 다만 이 선택은 위 규칙이 보장하는 결과가 아니다. 감지를 끄면 InnoDB는 교착 상태를 innodb_lock_wait_timeout에 맡긴다. 매뉴얼은 동시성이 매우 높은 시스템에서 많은 스레드가 같은 잠금을 기다릴 때 감지 자체가 느려질 수 있어 이런 선택을 할 수 있다고 설명한다.

    교착 상태는 버그가 아니라 정상 동작의 일부로 다뤄야 한다. 매뉴얼은 교착 상태와 잠금 대기 시간 초과가 바쁜 서버에서는 정상적인 일이며, 애플리케이션이 이를 예상하고 재시도로 처리해야 한다고 적는다. 줄이는 방법으로는 데이터를 처음 바꾼 뒤 커밋할 때까지의 일을 최소화해 잠금을 짧게, 적은 행에만 쥐게 할 것, 여러 테이블이나 넓은 범위를 갱신하는 트랜잭션들이 같은 순서로 잠그게 할 것, SELECT ... FOR UPDATE와 UPDATE ... WHERE에 쓰이는 열에 인덱스를 둘 것을 권한다. 위 이체라면 출금·입금 순서가 아니라 계좌 번호가 작은 쪽부터 잠그도록 바꾸면 X와 Y가 같은 순서로 잠금을 요청하므로 원이 생기지 않는다. 마지막 교착 상태는 SHOW ENGINE INNODB STATUS로 볼 수 있고, innodb_print_all_deadlocks를 켜면 모든 교착 상태가 오류 로그에 기록된다. 현재 걸린 잠금과 대기 관계는 Performance Schema의 data_locks, data_lock_waits 테이블로 관찰한다.

    두 트랜잭션이 서로가 쥔 행 잠금을 기다리며 원을 이루고, InnoDB가 하나를 희생자로 롤백해 원을 끊는 과정을 보여 준다. 가운데에 두 개의 원형 노드 "트랜잭션 X"(왼쪽)와 "트랜잭션 Y"(오른쪽). 왼쪽 아래에 자물쇠 아이콘이 붙은 사각형 "계좌 1번 행", 오른쪽 아래에 자물쇠 아이콘이 붙은 사각형 "계좌 2번 행". 계좌 1번 행에서 트랜잭션 X로 실선 화살표 라벨 "X 잠금 보유", 계좌 2번 행에서 트랜잭션 Y로 실선 화살표 라벨 "X 잠금 보유". 트랜잭션 X에서 계좌 2번 행으로 빨간 점선 화살표 라벨 "대기", 트랜잭션 Y에서 계좌 1번 행으로 빨간 점선 화살표 라벨 "대기". 두 점선이 교차해 원을 이룸을 강조하는 옅은 빨간 원형 테두리. 오른쪽 위 모서리에 작은 말풍선 "ERROR 1213 → 희생자 롤백". 평면 다이어그램, 흰 배경. 각 트랜잭션이 상대가 쥔 행 잠금을 기다리면 대기 관계가 원을 이룬다. InnoDB는 이를 감지해 한 트랜잭션을 롤백한다.

    스냅샷과 잠금이 섞일 때: 갱신 손실과 쓰기 치우침 다시 보기

    InnoDB를 쓰면서 가장 헷갈리는 지점은 한 트랜잭션 안에서 두 종류의 읽기가 섞일 때다. 평범한 SELECT는 스냅샷을 읽는다. 그런데 UPDATE, DELETE, 잠금 읽기는 스냅샷이 아니라 잠금을 얻은 뒤의 최신 버전을 대상으로 한다. 매뉴얼은 일관된 읽기 절의 주석에서 데이터베이스 상태의 스냅샷이 트랜잭션 안의 SELECT에 적용되며 DML 문장에는 꼭 적용되지 않는다고 분명히 적는다. 매뉴얼의 예를 이 회차의 실행표 형식으로 옮기면 다음과 같다.

    시점세션 A (REPEATABLE READ)세션 B
    1SELECT COUNT(c2) FROM t1 WHERE c2 = 'abc'; → 0
    2c2 = 'abc'인 행 10개를 넣고 COMMIT
    3UPDATE t1 SET c2 = 'cba' WHERE c2 = 'abc'; → 10개 행 갱신
    4SELECT COUNT(c2) FROM t1 WHERE c2 = 'cba'; → 10

    시점 1의 스냅샷에는 'abc' 행이 없었다. 그러나 시점 3의 UPDATE는 스냅샷이 아니라 최신 커밋 상태를 보고 B가 넣은 10개 행을 찾아 갱신한다. 그러면 그 행들의 최신 버전은 A 자신이 만든 버전이 되고, 읽기 뷰는 자기 변경을 항상 보이게 하므로 시점 4의 SELECT에 10개가 나타난다. 평범한 SELECT만 했다면 끝까지 보이지 않았을 행이, 그 행을 건드리는 순간 보이기 시작한 것이다. 같은 이유로 매뉴얼은 REPEATABLE READ 트랜잭션 안에서 잠금 문장과 잠금 없는 SELECT를 섞지 말라고 권하며, 그런 경우는 보통 SERIALIZABLE을 원하는 것이라고 덧붙인다. 또 INSERT INTO ... SELECT, UPDATE ... (SELECT), CREATE TABLE ... SELECT처럼 다른 문장 안에 들어간 SELECT는 기본적으로 더 강한 잠금을 쓰고, 그 SELECT 부분은 READ COMMITTED처럼 매번 새 스냅샷을 읽는다.

    갱신 손실이 InnoDB의 기본 격리 수준에서 일어나는 이유

    이제 앞의 갱신 손실 실행표를 InnoDB의 규칙으로 다시 읽을 수 있다. 시점 1과 2의 SELECT는 둘 다 잠금 없는 일관된 읽기이므로 서로 막지 않고 1000을 읽는다. 시점 3에서 A는 1번 행에 배타 잠금을 걸고 900을 쓴 뒤 커밋해 잠금을 놓는다. 시점 4에서 B는 잠금을 얻어 최신 버전(900) 위에 800을 쓴다. B가 쓴 값 800은 B가 스냅샷에서 읽은 1000으로 계산한 상수이므로, 최신 값이 900이었다는 사실은 반영되지 않는다. 모든 단계가 REPEATABLE READ의 규칙대로 실행되었고 오류도 없다. 앞의 자바 모델 시나리오 3의 첫 줄 800(trx 102) -> 900(trx 101) -> 1000(trx 100)이 정확히 이 과정이다. 반복 가능한 읽기는 "내가 읽은 값이 트랜잭션 동안 바뀌지 않는다"를 보장할 뿐, "내가 읽은 값이 쓰는 순간에도 최신이다"를 보장하지 않는다.

    막는 방법은 네 가지다. 첫째, 계산을 데이터베이스 안으로 옮긴다. UPDATE account SET balance = balance - 200 WHERE id = 1은 잠금을 얻은 뒤 최신 값을 읽어 계산하므로 A의 결과 위에 B의 출금이 쌓인다. 자바 모델 시나리오 3의 둘째 줄(700)이 이 경우다. 잔액 확인이 필요하면 앞의 JDBC 예처럼 AND balance >= ?를 조건에 넣고 바뀐 행 수를 확인한다. 둘째, 읽을 때부터 잠근다. SELECT balance FROM account WHERE id = 1 FOR UPDATE로 읽으면 B는 A가 끝날 때까지 이 읽기에서 기다리고, 기다림이 끝난 뒤 최신 값 900을 읽는다. 읽기와 계산 사이에 다른 로직이 길게 끼어 있을 때 쓰는 방법이다. 셋째, 낙관적 잠금(optimistic locking)이다. 행에 버전 열을 두고 UPDATE account SET balance = ?, version = version + 1 WHERE id = ? AND version = ?처럼 읽었을 때의 버전을 조건에 넣는다. 그 사이 누군가 바꿨다면 버전이 달라져 0개 행이 갱신되므로, 애플리케이션이 충돌을 알아채고 다시 시도한다. 나중에 JPA의 @Version이 이 방식을 자동화한다. 넷째, 격리 수준을 SERIALIZABLE로 올린다.

    넷째 방법이 실제로 어떻게 동작하는지 따라가 보자. 자동 커밋이 꺼진 SERIALIZABLE에서 두 트랜잭션의 평범한 SELECT는 FOR SHARE로 바뀌므로, A와 B는 1번 행에 각자 공유 잠금을 얻는다. 공유 잠금끼리는 호환되므로 둘 다 1000을 읽는다. A가 UPDATE를 실행하면 배타 잠금이 필요한데 B의 공유 잠금 때문에 기다린다. B도 UPDATE를 실행하면 A의 공유 잠금 때문에 기다린다. 서로를 기다리는 원이 생겼으므로 InnoDB가 교착 상태로 감지해 하나를 롤백한다. 살아남은 쪽의 갱신만 반영되고, 롤백된 쪽은 1213을 받아 처음부터 다시 실행한다. 다시 실행할 때는 갱신된 값을 읽으므로 갱신 손실이 없다. MySQL 8.4.13과 8.0.46에서 갱신 손실 실행표를 SERIALIZABLE로 돌리면 실제로 B가 UPDATE에서 1213을 받고 A의 900만 남는다. 같은 실행표를 REPEATABLE READ로 돌리면 오류 없이 800이 남고, 상대 갱신(balance = balance - 200)이나 FOR UPDATE 읽기로 바꾸면 700이 남는다. 대가는 교착 상태와 재시도다. 앞의 "당직 의사" 쓰기 치우침도 같은 방식으로 막힌다. REPEATABLE READ에서는 두 트랜잭션이 잠금 없는 읽기로 당직 2명을 확인하고 서로 다른 행을 쓰므로 아무 충돌 없이 둘 다 커밋된다. SERIALIZABLE에서는 당직 인원을 세는 SELECT가 공유 잠금을 걸어 상대가 읽은 행을 쓰지 못하게 하므로, 둘 중 하나는 기다리거나 교착 상태로 롤백된다. MySQL 8.4.13에서 doctor(name, on_call) 테이블로 실행해 보면 REPEATABLE READ에서는 두 트랜잭션 모두 2명을 읽고 커밋해 당직이 0명이 되고, SERIALIZABLE에서는 나중에 갱신한 쪽이 1213을 받아 당직 1명이 남는다. 실무에서는 격리 수준 전체를 올리는 대신, 규칙 검사에 쓰는 읽기만 FOR UPDATE나 FOR SHARE로 바꾸는 경우가 많다.

    흔한 오해와 함정

    "트랜잭션으로 감싸면 동시성 문제는 해결된다." 트랜잭션이 기본으로 보장하는 것은 원자성과 지속성, 그리고 선택한 격리 수준만큼의 격리다. InnoDB의 기본값인 REPEATABLE READ에서 "평범한 SELECT로 읽고, 애플리케이션에서 계산하고, 상수로 쓰는" 코드는 트랜잭션 안에 있어도 갱신 손실을 일으킨다. 읽은 값으로 무언가를 쓴다면 그 읽기가 잠금 읽기인지, 계산을 UPDATE 안으로 옮길 수 있는지, 버전 열로 충돌을 감지하는지 확인해야 한다.

    "문장이 실패하면 데이터베이스가 트랜잭션을 롤백해 준다." MySQL InnoDB에서 트랜잭션 전체를 자동으로 롤백하는 대표적인 경우는 교착 상태뿐이다. 중복 키, 제약 위반, 잠금 대기 시간 초과는 기본적으로 그 문장만 되돌리고 트랜잭션을 열어 둔다. 그 뒤 COMMIT이 실행되면 실패하기 전 문장들의 변경이 확정된다. 오류를 받으면 클라이언트가 ROLLBACK을 호출해야 한다.

    "InnoDB의 REPEATABLE READ에서는 팬텀이 절대 생기지 않는다." 평범한 SELECT끼리는 같은 스냅샷을 읽으므로 새 행이 나타나지 않는다. 잠금 읽기는 넥스트 키 잠금으로 범위에 삽입을 막는다. 그러나 앞 절의 매뉴얼 예처럼 스냅샷 읽기 뒤에 같은 범위를 UPDATE하거나 잠금 읽기하면, 그 사이 커밋된 행이 결과에 들어오고 이후의 SELECT에도 보이게 된다. 두 종류의 읽기를 섞지 않는 것이 안전하다.

    "커밋이 끝났다면 데이터 파일에 기록된 것이다." 커밋 응답이 보장하는 것은 리두 로그가 설정에 따라 디스크로 내려갔다는 것이다. 데이터 페이지는 여전히 버퍼 풀의 더티 페이지일 수 있고, 장애가 나면 리두 로그 재적용으로 복원된다. 그리고 innodb_flush_log_at_trx_commit을 0이나 2로 바꾸었거나 저장 장치가 쓰기 완료를 거짓으로 보고하면, 커밋 응답을 받은 트랜잭션도 사라질 수 있다.

    "읽기만 하는 트랜잭션은 오래 열어 둬도 해가 없다." 읽기만 해도 REPEATABLE READ의 첫 읽기 이후로는 읽기 뷰를 쥐고 있다. 그 뷰가 필요로 할 수 있는 갱신 언두 로그는 퍼지되지 못하고 쌓이며, 다른 트랜잭션의 일관된 읽기가 따라가야 할 버전 체인도 길어진다. 대량 조회 배치, 사용자의 입력을 기다리는 동안 열어 둔 트랜잭션, 커밋을 잊고 풀에 돌아간 연결이 모두 같은 문제를 만든다.

    "격리 수준을 높이면 항상 더 안전하다." 데이터 정합성 면에서는 그렇지만 대가가 있다. SERIALIZABLE에서는 평범한 읽기도 공유 잠금을 걸므로 읽기와 쓰기가 서로 기다리고, 앞에서 본 것처럼 갱신 손실이 교착 상태로 바뀌어 재시도가 필요해진다. 반대로 READ COMMITTED는 갭 잠금을 쓰지 않고 조건에 맞지 않는 행의 잠금을 일찍 풀어 경합이 줄어드는 대신, 반복 불가능한 읽기와 팬텀을 허용한다. 어느 쪽이 옳은지는 그 트랜잭션이 읽은 값으로 무엇을 결정하는지에 달려 있다.

    정리: 이 회차가 다른 주제와 만나는 곳

    이 회차를 한 줄로 줄이면, 트랜잭션은 "여러 문장을 하나로 다루겠다"는 약속이고 InnoDB는 그 약속을 네 가지 장치로 지킨다는 것이다. 언두 로그는 되돌리기와 옛 버전 보여 주기를 맡는다. 리두 로그와 커밋 시 디스크 내리기는 커밋된 변경이 장애를 견디게 한다. 읽기 뷰는 평범한 SELECT가 어느 버전을 볼지 정한다. 잠금은 쓰기끼리의 순서를 정하고, 넥스트 키 잠금은 범위를 지켜 팬텀을 막는다. 격리 수준은 읽기 뷰를 언제 만들지와 잠금을 얼마나 넓게 오래 쥘지를 함께 정하는 설정이다.

    이 지식은 로드맵의 다음 강의들에서 계속 다시 쓰인다. 스프링의 @Transactional은 이 회차의 JDBC 코드에서 본 자동 커밋 끄기, 커밋, 롤백, 자동 커밋 복원을 대신 실행하며, 같은 트랜잭션의 문장들이 같은 연결을 쓰도록 연결을 관리한다. 스프링이 어떤 예외에서 롤백하는지, 트랜잭션이 이미 있을 때 새 트랜잭션을 어떻게 다루는지(전파)는 스프링 DB 강의의 주제다. JPA는 영속성 컨텍스트에 모아 둔 변경을 커밋 직전에 SQL로 내보내므로, 이 회차에서 본 "잠금은 커밋까지 유지된다"는 사실이 JPA를 쓸 때 잠금이 언제 잡히는지를 결정한다. JPA의 낙관적 잠금은 앞에서 본 버전 열 방식이고, 비관적 잠금은 SELECT ... FOR UPDATE다. 커넥션 풀의 크기와 트랜잭션 길이의 관계, 교착 상태 재시도도 실무 강의에서 다시 만난다. 같은 권의 09회에서는 저장 프로시저 안에서 트랜잭션을 여는 방법(BEGIN이 아니라 START TRANSACTION)과 트리거가 문장과 같은 트랜잭션 안에서 실행된다는 점이 이 회차와 이어진다.
    트랜잭션의 경계
    자동 커밋에서는 문장 하나가 트랜잭션이다. START TRANSACTION으로 열고 COMMIT이나 ROLLBACK으로 닫으며, 둘 다 InnoDB 잠금을 모두 푼다. DDL과 새 트랜잭션 시작은 진행 중인 트랜잭션을 암묵적으로 커밋한다.
    문장 롤백과 트랜잭션 롤백
    InnoDB는 교착 상태에서만 트랜잭션 전체를 롤백하고, 중복 키·대기 시간 초과 등 대부분의 오류에서는 그 문장만 되돌린다. 문장 롤백은 잠금을 풀지 않으며, 트랜잭션을 버릴지는 클라이언트가 정한다.
    원자성과 언두 로그
    InnoDB는 클러스터형 인덱스 레코드를 제자리에서 바꾸고 이전 내용을 언두 로그에 남긴다. 레코드의 DB_TRX_ID와 DB_ROLL_PTR가 언두로 이어져 롤백과 옛 버전 재구성에 함께 쓰인다.
    지속성과 리두 로그
    커밋 응답 전에 디스크로 내려가는 것은 리두 로그이고 데이터 페이지는 나중에 쓰인다. innodb_flush_log_at_trx_commit=1(기본값)이 완전한 ACID에 필요하며, 0과 2는 충돌 시 최근 트랜잭션을 잃을 수 있다.
    이상 현상과 격리 수준
    표준은 더티 리드, 반복 불가능한 읽기, 팬텀으로 READ UNCOMMITTED부터 REPEATABLE READ까지를 구분하고, SERIALIZABLE은 직렬 실행과 같은 결과로 정의한다. 갱신 손실과 쓰기 치우침은 표 밖의 현상이다.
    읽기 뷰와 MVCC
    일관된 읽기는 최신 버전부터 언두 체인을 따라가며 읽기 뷰가 보이는 것으로 판정한 첫 버전을 읽는다. REPEATABLE READ는 첫 읽기에서 만든 뷰를 끝까지, READ COMMITTED는 읽을 때마다 새 뷰를 쓴다.
    잠금의 종류
    S·X 행 잠금은 인덱스 레코드에 걸리고, 갭 잠금은 간격에 대한 삽입을 막으며, 넥스트 키 잠금은 둘을 합쳐 REPEATABLE READ에서 팬텀을 막는다. 인덱스 없는 조건은 훑은 모든 레코드를 잠근다.
    스냅샷 읽기와 현재 읽기의 혼합
    평범한 SELECT는 스냅샷을, UPDATE·DELETE·잠금 읽기는 최신 버전을 읽는다. 읽은 값으로 계산한 상수를 쓰면 REPEATABLE READ에서도 갱신 손실이 생기므로 상대 갱신, FOR UPDATE, 버전 열, SERIALIZABLE 중 하나로 막는다.

    장애 분석에서 가장 먼저 확인할 것은 트랜잭션의 길이다. 잠금 대기 시간 초과(1205)가 잦다면 대개 누군가 행 잠금을 쥔 채 오래 머물고 있다. 트랜잭션 안에서 외부 API를 호출하거나, 대량 처리를 한 트랜잭션으로 묶거나, 예외 경로에서 롤백을 빼먹어 열린 트랜잭션이 커넥션 풀에 돌아간 경우가 흔하다. Performance Schema의 data_locks와 data_lock_waits로 누가 무엇을 쥐고 누가 기다리는지 확인하고, 데이터를 처음 바꾼 순간부터 커밋까지의 구간을 줄이는 것이 첫 번째 처방이다. 같은 이유로 읽기만 하는 긴 트랜잭션도 언두 로그가 쌓이는 원인이 되므로 배치 조회는 적당한 단위로 끊어 커밋한다.

    교착 상태(1213, SQLSTATE 40001)는 없앨 대상이라기보다 다룰 대상이다. 트랜잭션 전체가 롤백되므로 애플리케이션은 트랜잭션 단위로 재시도할 수 있어야 하고, 재시도해도 안전하도록 트랜잭션 밖의 부수 효과(메일 발송, 외부 결제 호출)를 커밋 뒤로 미뤄야 한다. 교착 상태가 특정 경로에서 반복된다면 innodb_print_all_deadlocks로 기록을 모아 잠금 순서를 맞추거나, WHERE에 쓰이는 열에 인덱스를 추가해 잠금 범위를 줄인다. 인덱스가 없는 UPDATE가 훑는 모든 레코드를 잠근다는 사실은 성능 문제가 동시성 문제로 번지는 전형적인 경로다.

    격리 수준은 서비스 전체에 한 번 정하고 잊는 값이 아니라 트랜잭션마다의 판단이다. 대부분의 조회는 기본값인 REPEATABLE READ나 READ COMMITTED로 충분하다. 재고 차감, 잔액 변경, 좌석 예약처럼 "읽은 값으로 결정해서 쓰는" 경로만 골라 상대 갱신, FOR UPDATE, 버전 열 중 하나를 적용하는 편이 전체를 SERIALIZABLE로 올리는 것보다 경합이 적다. READ COMMITTED로 바꿀 때는 갭 잠금이 사라져 팬텀이 허용되고, 이 수준에서는 행 기반 바이너리 로깅만 지원된다는 점을 함께 검토해야 한다.

    1번. READ UNCOMMITTED: 10000, 15000, 15000. 스냅샷을 쓰지 않고 최신 버전을 읽으므로 두 번째 읽기에서 커밋되지 않은 15000이 보인다(더티 리드). READ COMMITTED: 10000, 10000, 15000. 읽을 때마다 새 뷰를 만든다. 두 번째 읽기의 뷰에서 B의 트랜잭션은 활성 목록에 있으므로 15000 버전이 보이지 않고 언두로 10000을 만든다. 세 번째 읽기의 뷰에서는 B가 커밋되어 활성 목록에 없으므로 15000이 보인다(반복 불가능한 읽기). REPEATABLE READ: 10000, 10000, 10000. 첫 읽기 때 만든 뷰를 끝까지 쓰는데, 그 뷰를 만들 때 B는 아직 ID를 받지 않았으므로(쓰기 전) B의 ID는 m_low_limit_id 이상이 되어 커밋 후에도 보이지 않는다. 완료 기준: 세 수준의 결과와 함께, 뷰를 만드는 시점과 B의 ID가 뷰의 어느 구간에 놓이는지를 설명했는가.

    2번. 답은 250이다. 300(trx 208): 208은 m_up_limit_id(204) 이상이고 뷰를 만든 트랜잭션 자신(0)도 아니며, m_low_limit_id(209)보다 작으므로 m_ids를 확인한다. 208은 m_ids에 있으므로 뷰를 만든 순간 진행 중이던 트랜잭션이고, 이 버전은 보이지 않는다. 언두 포인터를 따라 250(trx 206)으로 내려간다. 206도 204 이상, 209 미만이지만 m_ids에 없다. m_ids는 뷰를 만든 순간 활성인 트랜잭션 집합이므로, 206이 그 범위에 있으면서 목록에 없다는 것은 뷰를 만들기 전에 이미 커밋했다는 뜻이다. 따라서 250이 보이고, 200(trx 203)과 100(trx 150)까지는 내려가지 않는다. 이 체인은 실제로 생길 수 있는 모양이기도 하다. 206이 커밋해 행 잠금을 놓은 뒤 208이 같은 행을 갱신했고, 208은 아직 커밋하지 않았다. 완료 기준: 각 버전에서 네 단계 판정(낮은 수위선, 자기 자신, 높은 수위선, 활성 목록)을 순서대로 적용했는가.

    3번. deposit에서 예외가 나면 commit()과 close()가 모두 건너뛰어진다. 출금 UPDATE는 실행되었지만 커밋되지 않은 채 트랜잭션이 열려 있고, 1번 행의 배타 잠금도 그대로다. 연결이 닫히지 않으면 그 잠금 때문에 다른 트랜잭션이 1번 계좌에서 최대 innodb_lock_wait_timeout(기본 50초)까지 기다리다 1205를 받는다. 풀에서 빌린 연결이 어떤 경로로든 풀에 돌아가 재사용되면, 다음 요청의 문장들이 이 열린 트랜잭션 안에서 실행되고 다음 요청이 commit을 호출하는 순간 앞 요청의 절반짜리 출금까지 함께 확정될 수 있다. 자동 커밋이 꺼진 상태도 그대로 넘어간다. 고치려면 try-with-resources로 연결을 닫고, catch에서 rollback(), finally에서 자동 커밋 복원을 해야 한다.

    4번. transfer에서 두 계좌 중 ID가 작은 쪽을 먼저 잠그도록 순서를 고정한다. 예를 들어 트랜잭션 시작 직후 SELECT id FROM account WHERE id IN (?, ?) ORDER BY id FOR UPDATE로 두 행을 ID 순서대로 잠그거나, 출금·입금 중 ID가 작은 계좌의 UPDATE를 먼저 실행한다. 그러면 1→2 이체와 2→1 이체가 모두 1번 행부터 잠그므로, 나중에 온 쪽은 1번 행에서 기다릴 뿐 2번 행을 먼저 쥐지 않아 원이 생기지 않는다. 그래도 재시도가 필요한 이유는 다른 경로(다른 테이블을 함께 갱신하는 코드, 갭 잠금이 관여하는 범위 갱신)에서도 교착 상태가 생길 수 있고, 매뉴얼이 교착 상태와 대기 시간 초과를 바쁜 서버의 정상적인 현상으로 보고 애플리케이션이 재시도로 처리해야 한다고 적기 때문이다. 교착 상태의 희생자는 트랜잭션 전체가 롤백되므로 재시도도 트랜잭션 전체 단위여야 한다.

     InnoDB의 기본 격리 수준에서 세션 A가 1번 계좌를 SELECT로 읽어 50000을 얻었다. 그 뒤 세션 B가 같은 행을 20000으로 바꾸고 커밋했다. A가 이어서 UPDATE account SET balance = balance - 1000 WHERE id = 1을 실행한 뒤 같은 행을 SELECT하면 무엇을 보는가? 49000. REPEATABLE READ이므로 UPDATE도 첫 스냅샷의 50000을 기준으로 계산한다. 19000. UPDATE는 잠금을 얻은 뒤 최신 커밋 버전을 읽어 계산하고, 그 결과는 A 자신의 변경이라 이후 SELECT에 보인다. 50000. 이후 SELECT는 첫 스냅샷을 읽으므로 자신의 UPDATE도 보이지 않는다. 오류. 스냅샷 이후 다른 트랜잭션이 바꾼 행은 갱신할 수 없다. 매뉴얼은 스냅샷이 SELECT에 적용되며 DML에는 꼭 적용되지 않는다고 적는다. UPDATE는 최신 커밋 버전(20000)을 대상으로 하므로 19000을 쓴다. 이 버전은 A가 만든 것이고, 일관된 읽기는 같은 트랜잭션의 앞선 문장이 한 변경을 보이게 하므로 SELECT는 19000을 본다. 첫 보기는 DML이 스냅샷을 쓴다고 잘못 가정했고, 셋째 보기는 자기 변경이 보인다는 예외를 놓쳤다. InnoDB의 REPEATABLE READ는 이 경우 오류를 내지 않는다. 자동 커밋이 켜진 mysql 클라이언트에서 START TRANSACTION; UPDATE account SET balance = balance - 30000 WHERE id = 1;을 실행한 뒤, 기본 키가 중복되는 INSERT가 오류로 실패했다. 이어서 COMMIT을 실행하면? INSERT가 실패했으므로 InnoDB가 이미 트랜잭션 전체를 롤백했고, COMMIT은 아무것도 확정하지 않는다. COMMIT이 오류를 내며 거부된다. 실패한 문장이 있는 트랜잭션은 롤백만 할 수 있다. INSERT만 되돌려졌고 트랜잭션은 열려 있으므로, COMMIT이 UPDATE의 출금을 확정한다. 오류가 난 순간 자동 커밋이 다시 켜져 UPDATE는 이미 확정되어 있었다. 매뉴얼의 InnoDB 오류 처리 규칙에서 중복 키 오류는 IGNORE가 없으면 그 문장만 롤백한다. 트랜잭션 전체 롤백은 교착 상태(또는 innodb_rollback_on_timeout을 켠 상태의 대기 시간 초과)에서 일어난다. 트랜잭션은 열린 채로 남으므로 COMMIT은 앞선 UPDATE를 확정한다. MySQL은 이 상황에서 COMMIT을 거부하지 않으며, 자동 커밋은 START TRANSACTION으로 연 트랜잭션이 COMMIT이나 ROLLBACK으로 끝날 때까지 꺼져 있다. innodb_flush_log_at_trx_commit = 1(기본값)에서 클라이언트가 COMMIT 성공 응답을 받은 순간에 대한 설명으로 옳은 것은? 그 트랜잭션의 리두 로그는 디스크로 내려갔지만, 바뀐 데이터 페이지는 아직 버퍼 풀에만 있을 수 있다. 바뀐 데이터 페이지가 모두 데이터 파일에 기록되었으므로 리두 로그는 더 이상 필요 없다. 리두 로그는 운영체제 캐시에만 쓰였고 디스크로는 초당 한 번 내려간다. 언두 로그가 디스크에 기록되어야 커밋이 끝나며, 리두 로그는 롤백에만 쓰인다. 매뉴얼에 따르면 값 1에서는 커밋마다 로그를 쓰고 디스크로 내린다. 데이터 페이지는 더티 페이지로 남아 나중에 쓰이며, 장애가 나면 재시작 시 리두 로그를 재적용해 복원한다. 둘째 보기는 리두 로그의 존재 이유를 부정한다. 셋째 보기는 값 2의 동작이다. 넷째 보기는 두 로그의 역할을 뒤바꿨다. 롤백에 쓰이는 것은 언두 로그다. InnoDB의 REPEATABLE READ에서 두 트랜잭션이 반대 순서로 같은 두 행을 UPDATE하다 교착 상태에 빠졌다. 다음 중 옳은 것은? 두 트랜잭션 모두 innodb_lock_wait_timeout(기본 50초)이 지나야 오류를 받는다. InnoDB는 먼저 시작한 트랜잭션을 항상 희생자로 고르고, 희생자는 마지막 문장만 롤백된다. 격리 수준을 READ COMMITTED로 바꾸면 행 잠금을 쓰지 않으므로 이 교착 상태는 생기지 않는다. 감지가 켜진 기본 설정에서 InnoDB가 하나를 희생자로 골라 트랜잭션 전체를 롤백하고, 희생자는 1213 오류를 받으므로 트랜잭션 전체를 재시도해야 한다. innodb_deadlock_detect의 기본값은 ON이고, InnoDB는 교착 상태를 감지하면 삽입·갱신·삭제한 행 수로 판단한 작은 트랜잭션을 희생자로 골라 트랜잭션 전체를 롤백한다. 대기 시간 초과에 맡기는 것은 감지를 끈 경우다. 희생자 선택 기준은 시작 순서가 아니다. READ COMMITTED도 UPDATE가 바꾸는 행에는 배타 잠금을 걸고 커밋까지 유지하므로, 같은 두 행을 반대 순서로 갱신하면 여전히 교착 상태가 생긴다.
    트랜잭션(transaction)
    여러 작업을 하나의 논리적 작업 단위로 묶어 전부 반영하거나 전혀 반영하지 않게 하고, 동시에 실행되는 작업과의 간섭을 격리 수준만큼 제한하는 단위.
    자동 커밋(autocommit)
    트랜잭션을 명시적으로 열지 않으면 SQL 문장 하나하나를 각각의 트랜잭션으로 실행하고 성공 시 바로 커밋하는 모드. MySQL과 JDBC 모두 새 연결의 기본값이다.
    언두 로그(undo log)
    InnoDB가 레코드를 바꾸기 전 내용을 다시 만들 수 있도록 롤백 세그먼트에 남기는 기록. 롤백과 일관된 읽기의 이전 버전 재구성에 쓰인다.
    리두 로그(redo log)
    데이터 변경 요청을 순서대로 덧붙여 기록하는 디스크 기반 구조. 커밋 시 디스크로 내려가며, 충돌 복구 때 데이터 파일에 반영되지 못한 변경을 재적용한다.
    일관된 읽기(consistent nonlocking read)
    잠금을 걸지 않고 MVCC로 특정 시점의 스냅샷을 읽는 InnoDB의 평범한 SELECT. 스냅샷 이후나 미커밋 변경은 보지 않고, 자기 트랜잭션의 변경은 본다.
    읽기 뷰(read view)
    스냅샷 순간의 활성 트랜잭션 목록과 두 경계 ID로 각 행 버전의 가시성을 판정하는 InnoDB 내부 자료 구조.
    넥스트 키 잠금(next-key lock)
    인덱스 레코드에 대한 레코드 잠금과 그 앞 간격에 대한 갭 잠금을 합친 잠금. InnoDB가 REPEATABLE READ에서 검색과 인덱스 스캔에 써서 팬텀 행을 막는다.
    교착 상태(deadlock)
    여러 트랜잭션이 서로 상대에게 필요한 잠금을 쥔 채 기다려 아무도 진행하지 못하는 상태. InnoDB는 감지해 한 트랜잭션을 롤백한다.
    갱신 손실(lost update)
    두 트랜잭션이 같은 값을 읽고 각자 계산한 결과를 써서 한쪽의 갱신이 다른 쪽에 덮여 사라지는 현상. 표준의 세 이상 현상 표에는 없다.
