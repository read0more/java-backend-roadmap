    이 회차의 질문: 그림이 데이터베이스가 되려면 무엇을 더 정해야 하는가

    앞 회차(08회)에서 물리적 모델링의 규칙을 세웠다. 논리 모델의 엔티티와 속성을 테이블과 열로 옮기는 이름 규칙, 문자·숫자·날짜 자료형을 고르는 기준, 역정규화의 뜻, 테이블 정의서라는 문서의 역할이 그 내용이다. 이번 회차는 그 규칙을 처음부터 끝까지 한 번 적용해 보는 실습이다. 대상은 작은 쇼핑몰이다. 회원이 상품을 고르고, 여러 상품을 한 번에 주문하고, 받은 상품에 리뷰를 남긴다. 규모는 작지만 물리 설계에서 판단해야 하는 지점은 거의 다 들어 있다.

    논리 모델까지 끝났는데 무엇이 더 남았는가. 논리 모델은 "어떤 사실을 어디에 한 번만 기록할 것인가"에 답한다. 그런데 데이터베이스는 그 사실을 디스크 페이지에 놓고, 요청이 올 때마다 찾아서 돌려줘야 한다. 같은 테이블 구조라도 어떤 인덱스가 있느냐에 따라 "내 주문 목록"이 페이지 몇 개를 읽고 끝나기도 하고 테이블 전체를 훑기도 한다. 같은 정보라도 어느 테이블에 복사본을 하나 더 두느냐에 따라 화면 하나를 그리는 데 드는 조인과 정렬이 달라진다. 그리고 그 복사본이 원본과 어긋나지 않게 지키는 일이 새로 생긴다. 물리 설계는 이런 결정을 구체적인 DDL로 굳히는 작업이다.

    이 회차의 순서는 실제 작업 순서를 따른다. 먼저 논리 모델과 기능 목록을 다시 정리한다(실습 시작). 기능 목록에서 쿼리를 뽑아 인덱스를 설계하고(인덱스 설계 실습), 화면이 요구하는 조회를 보고 역정규화할 곳을 고른다(역정규화 실습). 결정이 끝나면 테이블 정의서를 쓰고(쇼핑몰 테이블 정의서), DDL로 실제 데이터베이스를 만든다(쇼핑몰 DDL과 DB 만들기). 만들어진 데이터베이스에서 ERD를 거꾸로 그려 설계와 대조하고(ERD 자동 생성), 마지막으로 데이터를 넣어 주문·취소·리뷰·집계가 의도대로 도는지 확인한다(쇼핑몰 기능 확인 1, 2).

    기준은 MySQL 8.0 이상과 InnoDB 저장 엔진이다. 8.4에서 달라진 점이 있으면 따로 적는다. 이 회차에서 쓰는 쇼핑몰 모델과 데이터는 설명을 위해 새로 만든 것이다. 실행 결과로 적은 값과 오류 문구는 모두 여기서 넣은 데이터를 MySQL 8.4.13에서 실제로 실행해 확인한 것이고, 같은 스크립트를 8.0.46에서 돌려도 결과와 문구가 같았다. 데이터베이스 이름만 실습용 이름으로 바꿔 실행했으므로, 오류 문구에 나오는 스키마 이름은 shop으로 적었다. 실행 계획도 실제 EXPLAIN 출력을 싣지만, 비용 추정치, 통계 기반 rows, 실행 시간 같은 값은 실행 환경과 통계에 따라 달라진다.

    인덱스 설계 실습 1: 쿼리에서 인덱스를 끌어내는 규칙

    인덱스를 설계하기 전에 InnoDB가 테이블을 어떻게 저장하는지 다시 떠올리자(03회). InnoDB 테이블은 기본 키 순서로 정렬된 B+Tree 하나, 곧 클러스터형 인덱스(clustered index)이고, 행 전체가 그 리프에 들어 있다. 보조 인덱스(secondary index)는 별도의 B+Tree다. MySQL 매뉴얼은 보조 인덱스의 각 레코드가 인덱스로 지정한 열과 함께 그 행의 기본 키 열을 담는다고 설명한다. 보조 인덱스로 찾은 뒤 다른 열이 필요하면, 리프에 있는 기본 키 값으로 클러스터형 인덱스를 다시 내려가 행을 읽는다.

    이 구조에서 인덱스 설계의 첫 번째 규칙이 나온다. 복합 인덱스(composite index)는 첫 열로 정렬하고, 첫 열이 같으면 둘째 열로, 그것도 같으면 셋째 열로 정렬한 목록이다. 그러므로 첫 열에 등호 조건이 걸리면 그 값에 해당하는 항목들이 한 구간에 모여 있고, 그 구간 안에서는 둘째 열 순서로 놓여 있다. 매뉴얼의 표현으로는 인덱스 (col1, col2, col3)가 있으면 (col1), (col1, col2), (col1, col2, col3)로 검색할 수 있고, 맨 왼쪽부터 이어지지 않는 조합, 예를 들어 col2만으로는 인덱스로 찾을 수 없다. 이것이 왼쪽 접두사(leftmost prefix) 규칙이다.

    두 번째 규칙은 정렬에 관한 것이다. 매뉴얼의 ORDER BY 최적화 절은 인덱스 (key_part1, key_part2)가 있고 WHERE key_part1 = 상수 ORDER BY key_part2인 쿼리라면 인덱스로 읽은 행이 이미 key_part2 순서이므로 정렬을 생략할 수 있다고 설명한다. DESC로 정렬해도 사정은 같고, 오름차순 인덱스를 거꾸로 읽으면 된다. 반대로 인덱스로 순서를 만들 수 없으면 MySQL은 찾은 행을 따로 정렬하는 단계, 곧 filesort를 거친다. 실행 계획(EXPLAIN)의 Extra 열에 Using filesort가 보이면 이 단계가 있다는 뜻이다. 이 두 규칙을 합치면 복합 인덱스 열 순서의 기본형이 나온다. 등호 조건 열을 앞에, 정렬 열을 그 뒤에 둔다.

    세 번째 규칙은 InnoDB에만 해당한다. 보조 인덱스에는 기본 키가 들어 있으므로, 인덱스 (member_id, ordered_at)은 내부적으로 (member_id, ordered_at, order_id)처럼 동작한다. 매뉴얼은 이를 인덱스 확장(index extension)이라고 부르고, 옵티마이저가 확장된 보조 인덱스를 ref·range 접근, 조인과 정렬 최적화, MIN()/MAX() 최적화에 쓸 수 있다고 적는다. 이 덕분에 두 가지 이득이 생긴다. 하나는 정렬의 동률 처리다. 같은 시각에 주문이 두 건 있으면 ORDER BY ordered_at DESC만으로는 두 행의 순서가 정해지지 않는다. 매뉴얼의 LIMIT 최적화 절은 ORDER BY 값이 같은 행들의 순서는 실행 계획에 따라 달라질 수 있으니, 순서가 중요하면 유일한 열을 정렬 조건에 더하라고 권한다. ORDER BY ordered_at DESC, order_id DESC로 쓰면 순서가 하나로 정해지는데, 이 정렬도 확장된 인덱스 순서와 일치하므로 정렬 단계가 생기지 않는다. 다른 하나는 커버링(covering)이다. 기본 키 열만 더 필요하다면 클러스터형 인덱스를 다시 찾아갈 필요가 없다.

    네 번째 규칙은 외래 키다. MySQL 매뉴얼은 외래 키 검사가 테이블 전체를 훑지 않도록 외래 키 열과 참조되는 열에 인덱스를 요구한다. 참조하는 쪽(자식) 테이블에는 외래 키 열이 같은 순서로 맨 앞에 오는 인덱스가 있어야 하고, 없으면 자동으로 만들어진다. 왜 자식 쪽에 인덱스가 필요한가. 부모 행을 지우거나 키를 바꿀 때 InnoDB는 그 부모를 참조하는 자식 행이 있는지 확인해야 한다. 상품 하나를 지우려 할 때 주문상품 테이블에서 그 상품 번호를 가진 행을 찾아야 하는데, 인덱스가 없다면 주문상품 전체를 읽는 수밖에 없다. 여기서 실용적인 결론이 하나 나온다. 외래 키 열로 시작하는 복합 인덱스를 설계하면 그 인덱스가 외래 키 인덱스 역할까지 겸하므로, 외래 키만을 위한 인덱스를 따로 둘 필요가 없다.

    이 네 규칙으로 접근 경로 목록을 하나씩 처리하자.

    인덱스 설계 실습 2: B+Tree 안에서 쿼리를 따라가 보기

    규칙이 실제로 무엇을 뜻하는지 Q5를 따라가며 확인하자. 주문 테이블에 데이터가 꽤 쌓였다고 가정하고, 보조 인덱스 idx_orders_member_ordered의 리프 일부를 펼쳐 보면 아래와 같다. 각 항목은 (member_id, ordered_at, order_id)이고, 마지막 값은 InnoDB가 붙인 기본 키다.

    idx_orders_member_ordered 리프 항목 (정렬 순서대로, 일부)

   ...
   (1, 2026-09-03 10:12:00, 105)
   (1, 2026-10-15 08:05:00, 230)
   (1, 2026-11-10 14:00:00, 388)   ◄── ② 여기서부터 거꾸로 읽는다
   (2, 2026-08-21 19:40:00,  77)   ◄── ① member_id = 1 구간의 끝을 찾는다
   (2, 2026-11-11 09:30:00, 391)
   (3, 2026-07-30 21:00:00,  12)
   ...

   ③ 388 → 230 → 105 순서로 읽고, member_id가 1이 아닌 항목을 만나면 멈춘다.
   ④ SELECT에 status, total_amount가 있으면 order_id로 클러스터형 인덱스를 찾아간다.
    SELECT order_id, status, total_amount, ordered_at
FROM orders
WHERE member_id = 1
ORDER BY ordered_at DESC, order_id DESC
LIMIT 10;

    실행을 단계별로 보자. 먼저 인덱스의 루트에서 출발해 member_id = 1 구간의 끝을 찾는다. 최신순으로 읽어야 하므로 구간의 마지막 항목에서 시작해 앞쪽으로 읽는다. 매뉴얼은 WHERE key_part1 = 상수 ORDER BY key_part2 DESC 형태도 내림차순이 없는 경우와 같은 방식으로 인덱스를 쓸 수 있다고 설명한다. 읽은 항목은 이미 (ordered_at, order_id)의 내림차순이므로 정렬 단계가 없다. 그리고 10건을 채우면 멈춘다. 매뉴얼의 LIMIT 최적화 절은 ORDER BY와 LIMIT을 함께 쓰면 MySQL이 정렬된 결과의 처음 N행을 찾는 즉시 멈추며, 정렬을 인덱스로 하는 경우 이것이 매우 빠르다고 적는다. 회원 1이 주문을 5만 건 했어도 이 쿼리가 읽는 인덱스 항목은 최대 10개 남짓이다.

    마지막 단계가 행 조회다. SELECT 목록의 status와 total_amount는 이 인덱스에 없으므로, 항목마다 order_id로 클러스터형 인덱스를 한 번씩 더 내려간다. 10건이면 10번이다. 만약 화면이 주문 번호와 주문 일시만 보여 준다면 어떨까. SELECT order_id, ordered_at은 인덱스 항목만으로 답할 수 있으므로 행 조회가 아예 없다. 실행 계획의 Extra 열에 보이는 Using index가 이 상태를 뜻한다. 매뉴얼은 이를 "실제 행을 읽는 추가 탐색 없이 인덱스 트리의 정보만으로 열 값을 가져오는" 전략이라고 설명한다. order_id를 인덱스에 직접 넣지 않았는데도 커버링이 되는 것은 앞에서 본 인덱스 확장 때문이다.

    보조 인덱스 리프가 (member_id, ordered_at, order_id) 순서로 정렬되어 있고, member_id = 1 구간의 끝에서부터 역방향으로 읽은 뒤 order_id로 클러스터형 인덱스를 찾아가는 흐름을 보여 준다. 왼쪽에 B+Tree 하나를 그린다: 맨 위 작은 사각형 "루트", 그 아래 사각형 두 개 "내부 노드", 맨 아래 가로로 긴 리프 페이지 세 개. 리프 안에는 작은 칸들이 정렬되어 있고, 가운데 리프에 "(1, 09-03, 105)", "(1, 10-15, 230)", "(1, 11-10, 388)", "(2, 08-21, 77)" 네 칸을 크게 보여 준다. 루트에서 가운데 리프의 "(2, 08-21, 77)" 칸 앞까지 내려가는 파란 화살표에 "① 구간의 끝 찾기" 라벨. 리프 안에서 388 → 230 → 105 방향으로 왼쪽을 향하는 주황 곡선 화살표에 "② 역방향으로 읽기" 라벨. 오른쪽에는 두 번째 B+Tree "클러스터형 인덱스 (order_id)"를 작게 그리고, 리프 칸 "388"에서 이 트리로 가는 점선 화살표에 "③ 다른 열이 필요할 때만" 라벨. 왼쪽 트리 위에 제목 "idx_orders_member_ordered", 오른쪽 트리 위에 "PRIMARY". 배경 흰색, 선은 단정하게. 등호 조건 다음에 정렬 열이 오면 인덱스 구간을 순서대로 읽는 것만으로 정렬이 끝나고, LIMIT을 채우는 순간 멈춘다.

    이번에는 같은 인덱스가 정렬을 해 주지 못하는 경우를 보자. 상위 카테고리 "컴퓨터 주변기기"를 누르면 하위 카테고리인 키보드(2)와 마우스(3)의 상품을 한꺼번에 최신순으로 보여 준다고 하자. 쿼리는 WHERE category_id IN (2, 3) AND status = 'ON_SALE' ORDER BY created_at DESC LIMIT 20이 된다. 인덱스에서 (2, 'ON_SALE') 구간과 (3, 'ON_SALE') 구간은 각각 created_at 순서로 정렬되어 있지만, 두 구간을 이어 붙인 결과는 created_at 순서가 아니다. 그래서 인덱스로 두 구간의 행을 모두 찾은 다음, 그 결과를 따로 정렬해야 한다. LIMIT 20이 있어도 정렬하려면 두 구간의 후보를 전부 읽어야 하므로, 앞 쿼리처럼 20개를 읽고 멈추는 일은 일어나지 않는다. 상위 카테고리 목록이 자주 쓰이는 화면이라면 상품에 최상위 카테고리 번호를 따로 저장하는 역정규화를 검토할 이유가 생긴다.

    범위 조건도 같은 방식으로 정렬을 깨뜨린다. 상품 목록에 가격 필터를 붙여 WHERE category_id = 2 AND price BETWEEN 30000 AND 60000 ORDER BY created_at DESC를 실행한다고 하자. 인덱스를 (category_id, price, created_at)로 만들면 가격 범위로 구간을 좁힐 수는 있지만, 그 구간 안의 항목은 가격 순서이지 등록 순서가 아니므로 정렬 단계가 생긴다. 인덱스를 (category_id, created_at)로 만들면 등록 순서로 읽으면서 가격을 하나씩 걸러 내야 한다. 두 조건을 한 인덱스로 동시에 만족시킬 수는 없다. 어느 쪽이 나은지는 가격 범위에 걸리는 행이 얼마나 되는지에 달려 있다. 걸러지는 행이 적으면 앞쪽(좁혀서 정렬), 많으면 뒤쪽(순서대로 읽으며 거르기)이 유리하다. 이런 쿼리는 설계 시점에 정답을 정하기보다 실제 데이터로 EXPLAIN을 확인해야 하는 대표적인 경우다.

    마지막으로 페이지 이동이다. 목록의 50페이지를 LIMIT 20 OFFSET 980으로 가져오면, 인덱스 순서대로 읽는다 해도 앞의 980개 항목을 읽고 버린 뒤에야 21번째 페이지에 해당하는 20개를 돌려줄 수 있다. B+Tree는 키 값으로 위치를 찾는 구조이지 "980번째 항목"으로 바로 가는 구조가 아니기 때문이다. 깊은 페이지가 자주 요청되는 화면이라면 직전 페이지의 마지막 값을 기억해 두고 그다음부터 읽는 키셋 페이지네이션(keyset pagination)을 쓴다. 조건은 created_at < 직전_시각 OR (created_at = 직전_시각 AND product_id < 직전_번호) 형태가 된다. 이렇게 쓰면 인덱스에서 직전 위치를 키 값으로 바로 찾아가므로 몇 페이지째든 읽는 양이 비슷하다. 다만 이 형태의 조건이 의도대로 범위 검색(range)이 되는지는 EXPLAIN으로 확인해야 한다(기능 확인 2에서 데이터를 늘려 확인한 MySQL 8.4.13의 계획은 range였다).

    인덱스 설계 실습 3: 만들지 않을 인덱스를 고르는 일

    인덱스를 더하는 판단만큼 중요한 것이 빼는 판단이다. 인덱스는 공짜가 아니다. order_item에 행 하나를 넣으면 클러스터형 인덱스 하나, 그리고 이 회차에서 설계한 보조 인덱스 셋에 각각 항목이 들어간다. B+Tree 네 개를 고치는 셈이다. 유일 인덱스라면 넣기 전에 같은 값이 있는지도 확인해야 한다. 보조 인덱스가 늘수록 버퍼 풀에서 차지하는 페이지도 늘어, 정작 자주 읽는 데이터 페이지가 밀려날 수 있다. 그래서 인덱스마다 "어떤 쿼리가 이 인덱스를 쓰는가"를 말할 수 있어야 한다.

    가장 흔한 낭비는 중복 인덱스다. 주문 테이블에 (member_id, ordered_at)가 있는데 (member_id) 인덱스를 또 만들면, 뒤의 것은 앞의 것의 왼쪽 접두사이므로 할 수 있는 일이 없다. 외래 키를 먼저 선언해 MySQL이 member_id 인덱스를 자동으로 만든 뒤에 복합 인덱스를 추가하는 경우를 걱정할 수 있는데, 매뉴얼에 따르면 자동으로 만든 외래 키 인덱스는 그 외래 키를 지원할 수 있는 다른 인덱스가 생기면 조용히 삭제될 수 있다. 반대로 복합 인덱스가 외래 키를 지원하는 유일한 인덱스일 때 그것을 지우려 하면, 외래 키에 필요한 인덱스라는 이유로 거부된다. 운영 중인 데이터베이스에서 중복 인덱스를 찾을 때는 sys 스키마의 schema_redundant_indexes 뷰가 도움이 된다. 이 뷰는 다른 인덱스와 겹치거나 다른 인덱스 때문에 쓸모없어진 인덱스를, 그것을 대신하는 인덱스(dominant index)와 삭제 문장까지 함께 보여 준다.

    지울지 말지 확신이 서지 않는 인덱스도 있다. MySQL 8.0의 보이지 않는 인덱스(invisible index)는 이럴 때 쓰는 기능이다. ALTER TABLE orders ALTER INDEX idx_orders_ordered INVISIBLE로 바꾸면 옵티마이저가 그 인덱스를 쓰지 않는다. 매뉴얼은 이것이 인덱스를 지운 효과를 되돌릴 수 있는 방식으로 시험하는 수단이라고 설명한다. 큰 테이블에서 인덱스를 지웠다가 다시 만드는 것은 비싸지만, 보이게·안 보이게 바꾸는 것은 빠른 제자리(in-place) 작업이다. 주의할 점은 보이지 않는 인덱스도 행이 바뀔 때마다 계속 갱신되고, 유일 인덱스라면 중복도 계속 막는다는 것이다. 쓰기 비용은 그대로이고 읽기에서만 빠진다. 기본 키는 보이지 않게 만들 수 없다.

    만들지 않기로 한 인덱스도 기록해 둔다. 상품명 검색은 name LIKE '%키보드%'처럼 앞뒤가 열린 패턴이 대부분인데, B+Tree 인덱스는 값의 앞부분부터 정렬되어 있으므로 앞이 열린 패턴으로는 구간을 찾을 수 없다. name에 일반 인덱스를 만들어도 이 검색은 빨라지지 않는다. MySQL에는 한국어·중국어·일본어를 위한 ngram 전문 검색 파서가 내장되어 있어 FULLTEXT ... WITH PARSER ngram 인덱스를 만들 수 있지만, 검색 품질과 운영 부담을 함께 따져야 하는 별도의 주제이므로 이 실습의 범위에서는 뺀다. 관리자가 주문 상태로 주문을 찾는 화면도 지금 목록에는 없으므로 status 인덱스를 미리 만들지 않는다. 화면이 생기면 그때 쿼리 모양을 보고 만든다.

    역정규화 실습 1: 무엇을 복사할지 고르는 기준

    역정규화(denormalization)는 정규화로 한 곳에 모은 사실을 일부러 다른 곳에 한 번 더 기록하는 결정이다. 얻는 것은 조회 비용의 감소이고, 잃는 것은 07회에서 본 갱신 이상(update anomaly)에 대한 방어다. 원본이 바뀌면 복사본도 함께 바꿔야 하고, 하나라도 놓치면 데이터베이스가 서로 다른 두 답을 갖게 된다. 그래서 역정규화 후보마다 두 가지를 묻는다. 복사하는 값이 바뀌는가, 그리고 복사가 없앨 비용이 정말 큰가.

    첫 번째 질문은 비용 쪽이다. 한 번 기록되면 다시 바뀌지 않는 값을 복사하는 것은 싸다. 원본이 바뀌지 않으니 복사본이 어긋날 길이 처음 기록하는 순간 하나뿐이고, 그 순간만 지키면 된다. 반대로 계속 바뀌는 값을 복사하면 원본을 바꾸는 모든 경로에서 복사본을 함께 갱신해야 하고, 그 경로가 늘어날 때마다 놓칠 위험도 늘어난다. 두 번째 질문은 이득 쪽이다. 흔한 착각은 "조인은 비싸니 조인을 없애자"이다. 하지만 기본 키로 몇 건을 찾아가는 조인은 B+Tree를 몇 번 내려가는 일이라 싸다. 비싼 것은 필터 조건과 정렬 조건이 서로 다른 테이블에 있어서 한 인덱스로 둘을 함께 처리할 수 없을 때다. 그러면 후보를 전부 모아 정렬한 뒤에야 LIMIT을 적용할 수 있다.

    이 기준으로 쇼핑몰의 후보를 하나씩 평가하자.

    후보 1: 리뷰에 상품 번호를 복사한다(채택). 정규화된 모델에서 리뷰는 주문상품 번호만 갖는다. 상품 번호는 주문상품을 거쳐야 알 수 있다. 이 상태에서 Q4(상품 1의 리뷰를 최신순으로 20개)를 실행하면, 먼저 order_item에서 상품 1의 주문상품을 모두 찾고(인기 상품이면 수만 건), 각각에 대해 리뷰가 있는지 찾아본 뒤, 찾은 리뷰를 작성 시각으로 정렬해야 한다. 필터(상품)는 주문상품에, 정렬(작성 시각)은 리뷰에 있기 때문이다. LIMIT 20이 있어도 정렬 전에 후보를 전부 모아야 하므로 일찍 멈출 수 없다. 리뷰에 product_id를 두면 review (product_id, created_at) 인덱스 하나로 필터와 정렬이 함께 끝나고, Q5에서 본 것처럼 20개를 읽고 멈춘다. 게다가 주문상품의 상품 번호는 한 번 기록되면 바뀌지 않는 값이다. 이득은 크고 비용은 작다.

    후보 2: 주문에 총액을 저장한다(채택). 주문 총액은 주문상품의 order_price × quantity를 모두 더한 값이므로 저장하지 않아도 계산할 수 있다. 하지만 Q5(내 주문 목록)와 Q7(일별 매출)은 주문마다 총액이 필요하다. 저장하지 않으면 내 주문 목록 10건을 보여 줄 때마다 주문상품을 조인해 그룹별로 합해야 하고, 일별 매출은 기간 안의 모든 주문상품을 읽어야 한다. 이 쇼핑몰의 규칙에서 주문상품은 주문을 만든 뒤 바뀌지 않는다(S4~S6에는 주문 수정이 없고, 취소는 상태만 바꾼다). 따라서 총액은 주문을 만드는 트랜잭션 안에서 한 번 계산해 넣으면 이후 어긋날 경로가 없다. 만약 나중에 "주문 일부 취소"나 "수량 변경"이 생기면 이 판단을 다시 해야 한다. 그때부터 총액은 바뀌는 값이 되기 때문이다.

    후보 3: 상품에 리뷰 수와 평점 합계를 저장한다(채택, 비용을 감수). 카테고리 목록(Q2)에 상품마다 리뷰 수와 평균 평점을 보여 준다고 하자. 저장하지 않으면 목록 20개마다 리뷰를 세고 평균을 내야 한다. 이 값은 리뷰가 달릴 때마다 바뀐다. 계속 바뀌는 값의 복사이므로 비용이 가장 큰 후보다. 그래도 목록 화면은 가장 자주 실행되는 쿼리이므로 채택하고, 대신 지키는 방법을 신중하게 정한다. 평균 평점 자체를 저장하지 않고 합계와 개수를 저장한다는 점에 주목하자. 평균은 새 리뷰가 올 때 "기존 평균 × 개수 + 새 평점"을 다시 나누어야 하고 반올림 오차가 쌓인다. 합계와 개수는 각각 더하기만 하면 되므로, 다음 절에서 볼 원자적 증가 연산으로 갱신할 수 있다. 평균은 읽을 때 rating_sum / review_count로 계산한다.

    후보 4: 주문에 회원 이름을 복사한다(기각). 관리자 주문 목록에 주문자 이름을 보여 주려고 복사하는 경우다. 그러나 주문에서 회원으로 가는 조인은 기본 키 등호 조인이다. 한 화면에 20건이면 클러스터형 인덱스를 20번 내려가는 비용이다. 그리고 회원 이름은 바뀔 수 있는 값이다. 개명한 회원의 과거 주문 수만 건을 함께 고칠 것인가, 아니면 어긋난 채로 둘 것인가를 결정해야 하는 짐만 생긴다. 이득은 작고 비용은 크다. 같은 이유로 상품에 카테고리 이름을 복사하는 것도 기각한다.

    역정규화가 아닌 것: 주문상품의 상품명과 단가, 주문의 배송지. 주문상품에 product_name과 order_price를 두는 것은 상품 테이블의 값을 복사한 것처럼 보이지만 역정규화가 아니다. product.price는 "지금 이 상품을 얼마에 파는가"이고, order_item.order_price는 "이 주문에서 이 상품을 얼마에 샀는가"다. 함수 종속성으로 말하면 앞의 것은 상품 번호가 결정하고, 뒤의 것은 주문상품 번호가 결정한다. 상품 가격이 내일 오르면 앞의 것은 바뀌어야 하고 뒤의 것은 바뀌면 안 된다. 둘이 같은 값으로 시작하는 것은 우연이다. 이것을 정규화한다며 주문상품에서 단가를 지우고 상품 테이블을 조인하게 만들면, 가격이 바뀌는 순간 과거 주문의 금액이 바뀌는 결함이 된다. 주문의 수령인과 주소도 같다. 회원의 현재 주소와 "이 주문을 보낸 주소"는 다른 사실이다(02회에서 본 시점 기준의 문제).

    이 장의 핵심

    역정규화 후보는 "바뀌지 않는 값을 복사하는가"와 "필터와 정렬을 한 테이블로 모아 인덱스 하나로 끝낼 수 있게 되는가"로 평가한다. 기본 키 조인을 없애려는 역정규화는 이득이 작고, 바뀌는 값을 복사하는 역정규화는 지키는 비용이 크다. 그리고 주문 당시의 가격처럼 시점이 다른 사실은 복사본이 아니라 별개의 사실이다.

    역정규화 실습 2: 복사한 값을 지키는 방법

    채택한 세 후보는 지키는 방법이 각각 다르다. 바뀌지 않는 값은 처음 기록하는 순간을 지키면 되고, 바뀌는 값은 바뀌는 모든 순간을 지켜야 한다.

    리뷰의 상품 번호: 복합 외래 키로 데이터베이스가 지키게 한다

    리뷰를 쓸 때 애플리케이션이 주문상품의 상품 번호를 읽어 그대로 넣으면 된다. 하지만 버그 하나로 다른 상품 번호가 들어가면, 그 리뷰는 엉뚱한 상품의 리뷰 목록에 나타난다. 이 어긋남을 데이터베이스가 막게 할 수 있다. 리뷰의 외래 키를 order_item_id 하나가 아니라 (order_item_id, product_id) 두 열로 선언하고, 주문상품의 (order_item_id, product_id)를 참조하게 하는 것이다. 그러면 리뷰의 (주문상품 번호, 상품 번호) 쌍이 주문상품 테이블에 실제로 있는 쌍이어야만 행이 들어간다. 주문상품 2번이 상품 3번이라면 (2, 1)이라는 쌍은 존재하지 않으므로 거부된다.

    이를 위해 부모인 주문상품에 UNIQUE (order_item_id, product_id) 인덱스를 둔다. order_item_id가 이미 기본 키이므로 이 조합의 유일성은 새로운 규칙이 아니다. 그런데도 인덱스가 필요한 이유는 외래 키가 참조하는 열들이 그 순서대로 맨 앞에 오는 인덱스를 MySQL이 요구하기 때문이다. 기본 키 인덱스의 키는 order_item_id 하나뿐이라 이 조건을 만족하지 못한다. 그렇다면 비고유 인덱스 (order_item_id, product_id)로도 되지 않을까. MySQL 8.0의 InnoDB는 비고유 인덱스를 참조하는 외래 키를 표준 SQL의 확장으로 허용해 왔다. 그러나 8.4 매뉴얼은 비고유 키나 부분 키를 참조하는 외래 키를 사용 중단(deprecated) 대상으로 밝히고, 이를 쓰려면 restrict_fk_on_non_standard_key 설정을 바꿔야 하며 향후 버전에서 지원이 사라질 것으로 예고한다. 그래서 처음부터 유일 인덱스로 만든다.

    자식인 리뷰 쪽에도 외래 키 열 (order_item_id, product_id)로 시작하는 인덱스가 필요하다. 여기서 "주문상품당 리뷰 하나"라는 S7의 규칙을 UNIQUE (order_item_id, product_id)로 선언해 두 역할을 한 인덱스에 맡긴다. 규칙은 order_item_id의 유일성인데 두 열 조합의 유일성으로 선언해도 되는가. 된다. 복합 외래 키 때문에 같은 order_item_id를 가진 리뷰는 언제나 같은 product_id를 갖는다. 주문상품 하나에는 상품 번호가 하나뿐이기 때문이다. 따라서 두 리뷰의 order_item_id가 같으면 쌍 전체가 같아지고, 쌍의 유일성이 곧 order_item_id의 유일성이 된다. 제약 두 개가 맞물려 하나의 규칙을 지키는 예다.

    주문 총액: 같은 트랜잭션 안에서 한 번 계산한다

    주문 총액은 주문과 주문상품을 넣는 바로 그 트랜잭션 안에서 계산해 넣는다. 다른 트랜잭션이 중간 상태를 보는 일은 없다. 커밋 전까지 다른 트랜잭션에게는 주문도 주문상품도 보이지 않기 때문이다. 문제는 데이터베이스의 선언적 제약으로 이 규칙을 강제할 수 없다는 점이다. CHECK 식에는 다른 테이블이나 서브쿼리를 쓸 수 없다(02회). 그래서 총액 같은 파생 값에는 점검 쿼리를 함께 만들어 둔다. 기능 확인 실습에서 실행해 볼 아래 쿼리가 그것이다. 결과가 비어 있으면 모든 주문의 총액이 주문상품의 합과 일치한다는 뜻이다. 운영에서는 이런 쿼리를 주기적으로 돌려 어긋남을 조기에 발견한다.

    SELECT o.order_id, o.total_amount,
       SUM(oi.order_price * oi.quantity) AS item_sum
FROM orders o
JOIN order_item oi ON oi.order_id = o.order_id
GROUP BY o.order_id, o.total_amount
HAVING o.total_amount <> item_sum;

    리뷰 수와 평점 합계: 원자적 증가와 같은 트랜잭션

    바뀌는 값을 지키는 첫 번째 원칙은 리뷰를 넣는 문장과 카운터를 고치는 문장을 같은 트랜잭션에 두는 것이다. 리뷰는 들어갔는데 카운터 갱신 전에 장애가 나면 둘이 어긋난다. 한 트랜잭션이면 둘 다 반영되거나 둘 다 취소된다. 두 번째 원칙은 카운터를 "읽고, 더하고, 쓰는" 방식으로 고치지 않는 것이다. 애플리케이션이 SELECT review_count로 7을 읽고 8을 써 넣는 방식이면, 두 트랜잭션이 동시에 7을 읽고 둘 다 8을 쓴다. 리뷰는 두 개 늘었는데 카운터는 하나만 늘었다. 이것이 잃어버린 갱신(lost update)이다. REPEATABLE READ에서 일반 SELECT는 트랜잭션의 스냅숏을 읽으므로 다른 트랜잭션이 막 커밋한 값을 보지 못할 수도 있다.

    UPDATE product
SET review_count = review_count + 1,
    rating_sum   = rating_sum + 5
WHERE product_id = 1;

    위처럼 증가를 UPDATE 문 안에서 하면 문제가 사라진다. MySQL 매뉴얼은 트랜잭션의 스냅숏이 SELECT 문에 적용되며 DML 문에는 반드시 적용되는 것은 아니라고 설명한다. UPDATE는 대상 행에 배타 잠금을 걸고, 다른 트랜잭션이 커밋한 최신 버전을 읽어 그 위에 더한다. 두 번째 트랜잭션은 첫 번째가 커밋해 잠금이 풀릴 때까지 기다렸다가, 8이 된 값을 읽어 9를 쓴다.

    대신 대가가 있다. 행 잠금은 트랜잭션이 끝날 때까지 유지되고, InnoDB는 열 단위가 아니라 행 단위로 잠근다. 상품 행에는 재고도 있으므로, 인기 상품 하나에 주문(재고 감소)과 리뷰(카운터 증가)가 몰리면 서로 다른 열을 고치는데도 같은 행의 잠금을 두고 차례를 기다린다. 또 updated_at을 ON UPDATE CURRENT_TIMESTAMP로 두었다면 리뷰가 달릴 때마다 상품의 "수정 일시"가 바뀌어, 관리자가 상품 정보를 언제 고쳤는지 알 수 없게 된다. 카운터가 자주 바뀌는 서비스라면 카운터를 product_review_stat(product_id, review_count, rating_sum) 같은 별도 테이블로 분리하는 것이 다음 단계의 선택지다. 목록 화면은 20건을 기본 키로 조인하면 되므로 분리의 조회 비용은 작다. 이 실습에서는 단순한 형태로 상품 테이블에 두고, 이 한계를 정의서에 적어 둔다.

    카운터에도 점검 쿼리를 만든다. 원본인 리뷰 테이블에서 다시 세어 저장된 값과 비교하는 쿼리다. 어긋남이 발견되면 같은 쿼리의 결과로 카운터를 다시 계산해 덮어쓰면 된다. 원본이 남아 있는 한 역정규화된 값은 언제든 재계산할 수 있다는 점이 파생 값의 장점이다.

    SELECT p.product_id, p.review_count, p.rating_sum,
       COUNT(r.review_id)        AS actual_count,
       COALESCE(SUM(r.rating), 0) AS actual_sum
FROM product p
LEFT JOIN review r ON r.product_id = p.product_id
GROUP BY p.product_id, p.review_count, p.rating_sum
HAVING p.review_count <> actual_count
    OR p.rating_sum   <> actual_sum;
    복사한 값원본이 바뀌는가지키는 방법어긋남을 찾는 방법
    review.product_id아니요복합 외래 키 (데이터베이스가 강제)필요 없음
    orders.total_amount현재 규칙에서는 아니요생성 트랜잭션 안에서 계산점검 쿼리 1
    product.review_count, rating_sum예 (리뷰마다)같은 트랜잭션, UPDATE 안의 원자적 증가점검 쿼리 2, 재계산

    자료형은 08회에서 다룬 문자·숫자·날짜 자료형의 성질에 따라 골랐다. 대리 키는 모두 BIGINT(8바이트)로 통일했다. 키 자료형이 테이블마다 다르면 외래 키 열의 자료형도 따라 달라지고, 조인할 때 양쪽 자료형이 다르면 비교를 위한 형 변환이 끼어들 여지가 생긴다. 금액은 원 단위 정수이므로 INT(4바이트, 부호 있는 최댓값 2,147,483,647)로 두었다. 한 주문의 총액이 21억 원을 넘는 일은 이 쇼핑몰의 업무 범위 밖이라고 판단했고, 그 판단을 정의서에 적어 둔다. 소수점 아래 금액이 있는 통화를 다룬다면 DECIMAL이어야 한다. 평점은 1에서 5까지이므로 TINYINT(1바이트)로 충분하다. 상태 값은 ENUM 대신 VARCHAR와 CHECK를 썼다. 값 목록을 바꾸려면 둘 다 DDL을 고쳐야 하지만, CHECK 쪽은 저장되는 값이 문자열 그대로라 데이터를 옮기거나 다른 시스템이 읽을 때 해석이 필요 없다.

    문자열 길이는 바이트가 아니라 문자 수다. utf8mb4는 문자 하나에 최대 4바이트를 쓰므로 VARCHAR(100)의 값은 최대 400바이트가 된다. 이 값으로 만든 email 유일 인덱스는 InnoDB의 기본 행 형식인 DYNAMIC에서 인덱스 키 접두사 한도인 3,072바이트 안에 넉넉히 들어간다. 날짜와 시각은 DATETIME을 썼다. TIMESTAMP는 세션 시간대를 기준으로 UTC로 바꿔 저장하고 표현 범위가 2038년에서 끝나므로, 이 쇼핑몰처럼 한 시간대에서만 운영하는 서비스에서는 들어온 값을 그대로 저장하는 DATETIME이 해석하기 쉽다.

    정의서를 엑셀이나 위키 문서로 따로 관리하면 반드시 DDL과 어긋난다. 누군가 열 하나를 추가하는 ALTER TABLE을 실행하고 문서를 고치지 않으면, 그날부터 문서가 틀린다. 어긋나지 않게 하는 방법은 원본을 하나로 두는 것이다. 열의 설명을 DDL의 COMMENT로 적고(열 주석은 최대 1,024자, 테이블 주석은 최대 2,048자), 정의서는 데이터베이스의 카탈로그에서 생성한다. 아래 쿼리가 정의서의 표를 그대로 뽑아낸다. 이렇게 하면 정의서는 "현재 데이터베이스의 실제 모습"이 되고, 문서를 고치는 일과 스키마를 고치는 일이 같은 일이 된다.

    SELECT c.TABLE_NAME, t.TABLE_COMMENT,
       c.ORDINAL_POSITION, c.COLUMN_NAME, c.COLUMN_COMMENT,
       c.COLUMN_TYPE, c.IS_NULLABLE, c.COLUMN_DEFAULT, c.EXTRA
FROM information_schema.COLUMNS c
JOIN information_schema.TABLES  t
  ON t.TABLE_SCHEMA = c.TABLE_SCHEMA
 AND t.TABLE_NAME   = c.TABLE_NAME
WHERE c.TABLE_SCHEMA = 'shop'
ORDER BY c.TABLE_NAME, c.ORDINAL_POSITION;

    쇼핑몰 DDL과 DB 만들기

    정의서의 결정을 DDL로 옮긴다. 순서에는 이유가 있다. 외래 키는 이미 있는 테이블만 참조할 수 있으므로, 참조되는 쪽(부모)부터 만든다. 회원과 카테고리가 먼저, 상품과 주문이 다음, 주문상품이 그다음, 리뷰가 마지막이다. 지울 때는 반대 순서다. 데이터베이스를 만들 때는 문자 집합과 콜레이션(collation)을 명시한다. MySQL 8.0의 서버 기본값은 utf8mb4와 utf8mb4_0900_ai_ci이지만, 기본값에 기대지 않고 적어 두어야 서버 설정이 다른 환경에서도 같은 스키마가 만들어진다.

    DDL을 실행한 뒤에는 의도한 것이 실제로 만들어졌는지 확인한다. 첫째, 외래 키 때문에 자동으로 생긴 인덱스가 없어야 한다. 이 DDL에서는 모든 외래 키가 이미 선언한 인덱스의 맨 앞 열로 지원되도록 설계했으므로, MySQL이 추가로 만들 인덱스가 없다. information_schema.STATISTICS를 조회하면 테이블마다 인덱스 이름과 열 순서(SEQ_IN_INDEX)를 볼 수 있다. 여기에 DDL에 적지 않은 인덱스가 보인다면 어떤 외래 키가 기존 인덱스로 지원되지 못했다는 뜻이다. 이 DDL을 MySQL 8.4.13과 8.0.46에서 실행하고 조회해 보면, 두 버전 모두 DDL에 적은 인덱스(기본 키 여섯 개와 보조 인덱스 열 개)만 나온다. 둘째, SHOW CREATE TABLE의 출력을 읽어 본다. 이것은 데이터 사전에 저장된 정의를 다시 DDL로 표현한 것이라, 생략한 기본값(엔진, 문자 집합, 콜레이션)이 어떻게 채워졌는지 보여 준다. 매뉴얼에 따르면 명시적으로 쓴 ON DELETE NO ACTION은 기본값이라 이 출력에 나타나지 않고, 같은 뜻의 RESTRICT는 나타난다.

    제약 세 가지는 동작을 정확히 알고 써야 한다. 첫째는 CHECK다. MySQL은 8.0.16부터 CHECK 제약을 실제로 검사한다. 그 이전 버전은 문법만 받아들이고 무시했으므로, 오래된 서버에서 이 DDL을 실행하면 오류 없이 만들어지지만 아무것도 막지 않는다. 또 조건이 거짓(FALSE)일 때만 위반이고, NULL 때문에 UNKNOWN이 되면 통과한다. 이 DDL에서 CHECK가 걸린 열은 모두 NOT NULL이므로 이 구멍이 없다. 둘째는 콜레이션과 유일성이다. utf8mb4_0900_ai_ci의 ai는 악센트 무시, ci는 대소문자 무시를 뜻한다. 그래서 Hana@Example.com과 hana@example.com은 같은 값으로 비교되고, 유일 인덱스가 두 번째 가입을 막는다. 이메일 규칙과 맞는 동작이다. 반면 UCA 9.0.0 기반 콜레이션은 NO PAD라서 끝의 공백을 다른 문자처럼 취급한다. 'hana@example.com '(끝에 공백)은 다른 값이 되어 들어갈 수 있으므로, 애플리케이션이 입력의 앞뒤 공백을 지워서 넣어야 한다.

    셋째는 NULL이 들어가는 유일 인덱스다. 카테고리의 UNIQUE (parent_id, name)은 같은 상위 카테고리 아래에서 이름이 겹치지 않게 막는다. 그런데 MySQL의 유일 인덱스는 NULL을 허용하는 열에 NULL 값이 여러 번 들어가는 것을 허용한다. 최상위 카테고리는 parent_id가 NULL이므로, 최상위 카테고리 "컴퓨터 주변기기"를 두 번 넣어도 이 제약은 막지 못한다. NULL은 어떤 값과도, 다른 NULL과도 같다고 판정되지 않기 때문이다. 이 실습에서는 최상위 카테고리가 관리자만 만드는 몇 개뿐이므로 애플리케이션 확인으로 충분하다고 보고, 이 한계를 정의서에 적었다. 엄격하게 막아야 한다면 최상위를 가리키는 루트 행을 하나 두어 parent_id를 NOT NULL로 만드는 방법이 있다.

    여섯 테이블의 열, PK·FK·UK 표시, 그리고 까마귀발 관계선을 보여 준다. 리뷰와 주문상품 사이의 복합 외래 키가 두 열로 연결된다는 점이 드러나야 한다. 까마귀발 표기의 물리 ERD. 사각형 테이블 여섯 개를 배치한다: 왼쪽 위 "member", 가운데 위 "orders", 오른쪽 위 "order_item", 오른쪽 아래 "review", 가운데 아래 "product", 왼쪽 아래 "category". 각 사각형 위쪽 띠에 테이블 이름, 아래에 열 목록을 작은 글씨로 적고 기본 키 열 앞에 열쇠 아이콘, 외래 키 열 앞에 "FK" 표시. 관계선(모두 점선): member → orders, orders → order_item, product → order_item, category → product, category → category(자기 참조 고리), order_item → review. 부모 쪽 끝은 막대 두 개, 자식 쪽 끝은 원과 까마귀발. 단, order_item → review 선의 review 쪽 끝은 원과 막대 하나(0..1). order_item → review 선 옆에 작은 라벨 "(order_item_id, product_id)". review의 "product_id" 열과 product의 "review_count" 열 옆에 주황색 작은 태그 "역정규화". 배경 흰색, 테이블은 옅은 파란색. 모든 관계가 비식별 관계라 점선으로 그려진다. 리뷰는 주문상품의 두 열을 함께 참조해, 복사한 상품 번호가 원본과 같음을 데이터베이스가 보장한다.

    물리적 모델: 데이터베이스에서 ERD를 자동으로 생성하기

    설계 도구에서 그린 ERD와 실제 데이터베이스는 시간이 지나면 어긋난다. 그래서 반대 방향, 곧 살아 있는 데이터베이스에서 ERD를 거꾸로 만들어 설계와 대조하는 작업이 필요하다. 이를 리버스 엔지니어링(reverse engineering)이라고 한다. MySQL Workbench의 매뉴얼은 MySQL 생성 스크립트나 실행 중인 MySQL 서버에 접속해 하나 이상의 데이터베이스를 가져와 리버스 엔지니어링할 수 있다고 설명한다. 다른 데이터베이스 도구들도 비슷한 기능을 제공한다. 도구마다 화면은 다르지만 원리는 같다. 도구는 데이터베이스의 메타데이터, 곧 카탈로그를 조회하고, 거기서 읽은 사실로만 그림을 그린다.

    MySQL 8.0의 카탈로그는 데이터 사전(data dictionary)이다. 테이블, 열, 인덱스, 제약의 정의가 여기에 저장된다. 사용자가 조회하는 INFORMATION_SCHEMA의 TABLES, COLUMNS, STATISTICS 같은 테이블은, 매뉴얼에 따르면 8.0부터 데이터 사전 테이블 위의 뷰로 구현되어 있다. 그래서 도구가 할 일은 SQL 몇 개를 실행하는 것이다. 관계선의 원천은 외래 키다. INFORMATION_SCHEMA.KEY_COLUMN_USAGE는 제약에 속한 열을 한 행씩 보여 주는데, 외래 키 제약의 행에는 참조하는 테이블과 열(REFERENCED_TABLE_NAME, REFERENCED_COLUMN_NAME)이 채워져 있다. 기본 키나 유일 제약의 행은 이 두 열이 비어 있다. 쇼핑몰 데이터베이스에 다음 쿼리를 실행해 보자.

    SELECT TABLE_NAME            AS child_table,
       COLUMN_NAME           AS fk_column,
       REFERENCED_TABLE_NAME AS parent_table,
       REFERENCED_COLUMN_NAME AS parent_column,
       CONSTRAINT_NAME,
       ORDINAL_POSITION
FROM information_schema.KEY_COLUMN_USAGE
WHERE TABLE_SCHEMA = 'shop'
  AND REFERENCED_TABLE_NAME IS NOT NULL;

    결과는 일곱 행이다(표는 'shop' 자리에 실습용 데이터베이스 이름을 넣어 MySQL 8.4.13에서 실행한 출력이고, 8.0.46에서도 같은 순서로 나왔다. 쿼리에 ORDER BY가 없으므로 이 순서는 보장되지 않는다). 리뷰의 외래 키는 열이 둘이므로 두 행으로 나오고, 같은 CONSTRAINT_NAME과 제약 안의 위치(ORDINAL_POSITION)로 묶인다. 도구는 같은 제약 이름의 행들을 선 하나로 그린다. 따라서 이 데이터베이스에서 그려지는 관계선은 여섯 개다. 리뷰에서 주문상품으로 가는 선이 두 열짜리라는 사실도 그림에 드러나는데, 이것은 복합 외래 키가 준 부수 효과다. 역정규화한 review.product_id가 어디서 온 값인지가 문서가 아니라 스키마 자체에 기록되어 있다.

    선의 모양은 카탈로그의 다른 사실에서 추론한다. 아래 표는 도구가 쓸 수 있는 근거를 정리한 것이다. 도구마다 표시 방식은 다르지만, 근거로 쓸 수 있는 정보는 카탈로그에 있는 이것뿐이다.

    카탈로그에서 읽는 사실추론할 수 있는 것쇼핑몰의 결과
    외래 키 열이 자식의 기본 키에 포함되는가식별 관계 / 비식별 관계모두 비식별(모든 테이블이 자기 대리 키를 가짐)
    외래 키 열이 NOT NULL인가자식이 부모를 반드시 가져야 하는가(부모 쪽 최소 1 / 0)category.parent_id만 NULL 허용 → 상위 카테고리는 선택
    외래 키 열 전체와 정확히 일치하는 유일 인덱스가 있는가자식 쪽 최대가 1인가(일대일 / 일대다)review의 UK가 외래 키 두 열과 일치 → 주문상품과 일대일
    그 밖의 유일 인덱스관계의 최대 수에는 영향 없음order_item의 (order_id, product_id)는 order_id만으로는 유일하지 않음 → 일대다

    MySQL Workbench의 EER 다이어그램은 식별 관계를 실선, 비식별 관계를 점선(broken line)으로 그리고, 기본 표기법은 까마귀발이다. 매뉴얼은 외래 키 열이 자식 테이블의 기본 키의 일부이면 실선을 쓴다고 예를 들어 설명한다. 쇼핑몰은 모든 테이블이 대리 키를 기본 키로 쓰므로 모든 관계선이 점선으로 그려진다. 06회에서 본 식별·비식별 관계의 선택이 그림에서 이렇게 드러난다.

    더 중요한 것은 그려지지 않는 것들이다. "주문에는 주문상품이 하나 이상 있다"는 규칙의 "최소 1"은 외래 키로 표현되지 않으므로(04회), 역으로 생성한 ERD에서 주문→주문상품 선의 주문상품 쪽 끝은 "0 이상"으로 그려진다. "배송이 끝난 주문상품에만 리뷰를 쓸 수 있다", "주문 총액은 주문상품 합계와 같다", "품절은 재고 0이다", "리뷰의 작성자는 그 주문의 회원이다" 같은 규칙도 카탈로그에 없으므로 그림에도 없다. 외래 키를 아예 선언하지 않는 팀이라면 결과는 더 극단적이다. 리버스 엔지니어링한 ERD는 선 하나 없이 테이블만 흩어져 있는 그림이 된다. 관계는 애플리케이션 코드 속에만 존재하게 된다. 자동 생성 ERD는 "데이터베이스가 실제로 강제하는 것"의 정확한 그림이고, 설계 문서의 전부가 아니다. 그 차이, 곧 애플리케이션이 지켜야 하는 규칙의 목록은 따로 적어 두어야 한다.

    방향을 반대로 하면 엔티티 매핑에서 DDL을 생성하는 일도 있다. 스프링 부트에서 spring.jpa.hibernate.ddl-auto는 none, validate, update, create, create-drop을 받는다. 스프링 부트 문서에 따르면 H2 같은 내장 데이터베이스를 쓰고 Flyway나 Liquibase 같은 스키마 관리 도구가 없으면 기본값이 create-drop이고, 그 밖의 경우에는 none이다. 개발 초기에 엔티티에서 테이블을 생성하는 것은 편리하지만, 이 회차의 DDL에 담긴 결정들, 곧 인덱스 열 순서, 외래 키를 겸하도록 고른 복합 인덱스, 복합 외래 키, CHECK 제약, 주석은 설계의 산출물이다. 운영 스키마는 검토된 DDL 스크립트로 관리하고, 엔티티 쪽은 validate로 매핑이 스키마와 맞는지만 확인하게 하는 구성이 원본을 하나로 지키는 방법이다.

    DDL이 데이터 사전에 정의를 남기고, INFORMATION_SCHEMA 뷰를 통해 도구가 그것을 읽어 선과 기호를 추론하는 과정, 그리고 카탈로그에 없는 업무 규칙은 그림에 나타나지 않는다는 점을 보여 준다. 왼쪽에서 오른쪽으로 가는 흐름도. 첫 상자 "CREATE TABLE ... FOREIGN KEY" (문서 아이콘), 화살표, 두 번째 상자 "데이터 사전" (원통 아이콘), 화살표, 세 번째 상자 "INFORMATION_SCHEMA 뷰" 안에 작은 칸 세 개 "KEY_COLUMN_USAGE", "COLUMNS", "STATISTICS", 화살표, 네 번째 상자 "ERD 도구" (톱니 아이콘), 화살표, 다섯 번째에 작은 ERD 그림(사각형 세 개와 점선 연결). 세 번째와 네 번째 상자 사이 화살표 위에 라벨 "외래 키 → 선, NOT NULL → 필수, UNIQUE → 일대일". 아래쪽에 회색 점선 상자 "업무 규칙: 최소 1개, 총액 = 합계, 배송완료 후 리뷰"를 두고, 이 상자에서 ERD로 가는 화살표에 빨간 X 표시와 라벨 "그려지지 않음". 배경 흰색, 차분한 파란색 계열. 자동 생성 ERD는 카탈로그에 기록된 제약만으로 그려진다. 선언적 제약으로 표현되지 않은 규칙은 그림에서 사라진다.

    쇼핑몰 기능 확인 1: 데이터 넣기와 주문 생성

    이제 만든 데이터베이스가 요구 사항대로 동작하는지 SQL로 확인한다. 기능 확인의 목적은 쿼리가 돌아가는지 보는 데 그치지 않는다. 설계에서 세운 가정, 곧 제약이 무엇을 막는지, 인덱스가 어떤 쿼리를 받치는지, 역정규화한 값이 원본과 맞는지를 데이터로 검증하는 것이다. 아래 결과 값은 모두 여기서 넣은 데이터로부터 결정된다. 자동 증가 번호가 1부터 차례로 붙는 것은 빈 테이블에 다른 세션이 동시에 값을 넣지 않는 이 실습의 조건에서 그렇다.

    INSERT INTO member (email, name, phone) VALUES
  ('hana@example.com', '김하나', '010-1111-2222'),   -- member_id 1
  ('duri@example.com', '이두리', NULL);              -- member_id 2

INSERT INTO category (parent_id, name) VALUES (NULL, '컴퓨터 주변기기');  -- 1
INSERT INTO category (parent_id, name) VALUES (1, '키보드'), (1, '마우스'); -- 2, 3

INSERT INTO product (category_id, name, price, stock_quantity, created_at) VALUES
  (2, '기계식 키보드 K1', 89000, 10, '2026-11-01 10:00:00'),  -- product_id 1
  (2, '무선 키보드 K2',   59000,  0, '2026-11-02 10:00:00'),  -- product_id 2
  (3, '무선 마우스 M1',   25000, 30, '2026-11-03 09:00:00');  -- product_id 3

-- 제약 확인: 대소문자만 다른 이메일
INSERT INTO member (email, name) VALUES ('Hana@Example.com', '김하나2');
-- ERROR 1062 (23000): Duplicate entry 'Hana@Example.com' for key 'member.uk_member_email'
-- (utf8mb4_0900_ai_ci는 대소문자를 구분하지 않는다)

    상품의 status는 넣지 않았으므로 기본값 'ON_SALE'이 들어간다. K2는 재고가 0이지만 판매중 상태다. 화면은 재고가 0인 것을 보고 품절로 표시한다. 상품 등록 시각은 결과를 재현할 수 있도록 직접 넣었다. 실제 서비스라면 기본값 CURRENT_TIMESTAMP에 맡긴다.

    주문 생성이 이 쇼핑몰에서 가장 중요한 트랜잭션이다. 회원 1이 K1 한 개와 M1 두 개를 주문한다. 순서는 재고 차감 → 가격 확인 → 주문 저장 → 주문상품 저장이다. 재고 차감을 맨 앞에 두는 이유는 실패할 가능성이 가장 높은 단계를 먼저 해서, 실패하면 아무것도 넣지 않은 채 끝내기 위해서다.

    START TRANSACTION;

-- 1. 재고 차감: 상품 번호 오름차순으로, 조건부로
UPDATE product SET stock_quantity = stock_quantity - 1
 WHERE product_id = 1 AND status = 'ON_SALE' AND stock_quantity >= 1;  -- 1 row affected (10 → 9)
UPDATE product SET stock_quantity = stock_quantity - 2
 WHERE product_id = 3 AND status = 'ON_SALE' AND stock_quantity >= 2;  -- 1 row affected (30 → 28)
-- 영향받은 행이 0인 문장이 하나라도 있으면 여기서 ROLLBACK

-- 2. 가격 확인 (두 행 모두 이 트랜잭션이 배타 잠금을 쥐고 있다)
SELECT product_id, name, price FROM product WHERE product_id IN (1, 3);
-- (1, '기계식 키보드 K1', 89000), (3, '무선 마우스 M1', 25000)
-- 총액 = 89000 × 1 + 25000 × 2 = 139000

-- 3. 주문 저장
INSERT INTO orders (member_id, status, total_amount, receiver_name,
                    receiver_phone, zipcode, address, ordered_at)
VALUES (1, 'ORDERED', 139000, '김하나', '010-1111-2222',
        '01234', '서울시 예시구 샘플로 1', '2026-11-10 14:00:00');
SET @order_id = LAST_INSERT_ID();   -- 1

-- 4. 주문상품 저장 (주문 당시 상품명과 단가를 기록)
INSERT INTO order_item (order_id, product_id, product_name, order_price, quantity) VALUES
  (@order_id, 1, '기계식 키보드 K1', 89000, 1),   -- order_item_id 1
  (@order_id, 3, '무선 마우스 M1',   25000, 2);   -- order_item_id 2

COMMIT;

    한 줄씩 짚어 보자. 1단계의 UPDATE는 재고 확인과 차감을 한 문장에서 한다. WHERE에 stock_quantity >= 1이 있으므로 재고가 부족하면 조건에 맞는 행이 없어 아무것도 바뀌지 않고, 애플리케이션은 영향받은 행 수 0을 보고 주문을 중단한다. 이 문장은 기본 키 등호 검색이므로 InnoDB는 그 행 하나에 배타 잠금을 건다. 매뉴얼은 유일 인덱스로 유일한 행을 찾는 문장에는 인덱스 레코드 잠금만 필요하다고 설명한다. 이 잠금은 커밋까지 유지된다. 2단계에서 가격을 읽을 때 두 상품 행은 이 트랜잭션이 이미 잠근 행이므로, 그 사이 다른 트랜잭션이 가격을 바꿔 커밋하는 일은 일어날 수 없다. 그리고 같은 트랜잭션의 앞선 문장이 바꾼 행은 스냅숏과 상관없이 보인다.

    3단계 뒤의 LAST_INSERT_ID()는 이 연결이 마지막으로 생성한 자동 증가 값을 돌려준다. 매뉴얼은 이 값이 연결(connection)마다 따로 유지되어 다른 클라이언트가 값을 생성해도 영향을 받지 않는다고 설명한다. 다만 여러 행을 한 문장으로 넣으면 첫 행의 값만 돌려주고, 4단계의 order_item 삽입도 자동 증가 값을 생성하므로 그 뒤에는 값이 바뀐다. 그래서 주문 번호를 사용자 변수에 옮겨 두고 썼다. JDBC에서는 같은 일을 Statement.RETURN_GENERATED_KEYS로 생성된 키를 받아서 한다. 4단계에서 주문상품을 넣을 때 InnoDB는 외래 키 검사를 위해 부모인 주문 행과 상품 행에 공유 잠금을 건다. 매뉴얼에 따르면 외래 키 조건을 검사해야 하는 삽입·갱신·삭제는 검사하며 확인한 레코드에 공유 레코드 잠금을 건다. 상품 행은 이미 이 트랜잭션이 배타 잠금을 쥐고 있으므로 기다림 없이 지나간다.

    같은 방식으로 회원 2가 M1 한 개를 주문했다고 하자(주문 번호 2, 주문상품 번호 3, 총액 25,000원, 주문 일시 2026-11-11 09:30:00). M1의 재고는 28에서 27이 된다. 이번에는 회원 2가 재고 0인 K2를 주문하려 한다.

    START TRANSACTION;
UPDATE product SET stock_quantity = stock_quantity - 1
 WHERE product_id = 2 AND status = 'ON_SALE' AND stock_quantity >= 1;  -- 0 rows affected
ROLLBACK;

-- 조건 없이 썼다면?
UPDATE product SET stock_quantity = stock_quantity - 1 WHERE product_id = 2;
-- ERROR 3819 (HY000): Check constraint 'chk_product_stock' is violated.   (0 - 1 = -1)

    조건부 UPDATE가 0행을 바꾸고 끝났으므로 주문 행은 만들어지지 않았다. 아래쪽 문장은 애플리케이션이 조건을 빠뜨린 경우다. 이때는 CHECK (stock_quantity >= 0)이 마지막 방어선이 되어 음수 재고를 거부한다. 조건부 UPDATE가 정상 경로의 판단이라면, CHECK는 코드에 버그가 있어도 데이터가 망가지지 않게 하는 안전망이다. 둘은 역할이 다르므로 함께 둔다.

    동시에 두 주문이 같은 재고를 노릴 때

    조건부 UPDATE가 정말로 동시 주문에서도 재고를 지키는지 따라가 보자. 이 시나리오를 위 데이터에 이어서 실행하면 이후 결과가 달라지므로, 본문의 확인을 모두 마친 뒤(K1 재고 9) 두 세션으로 따로 실행해 보았다(MySQL 8.4.13). K1의 재고가 9개일 때 트랜잭션 T1은 6개, T2는 5개를 주문한다. 합하면 11개로 재고보다 많으므로 둘 중 하나는 실패해야 한다.

    시각  T1 (K1 6개 주문)                         T2 (K1 5개 주문)
───  ─────────────────────────────────────   ─────────────────────────────────────
 t1  UPDATE ... SET stock = stock - 6
       WHERE product_id = 1 AND stock >= 6
     → 행 1에 배타 잠금, 9 ≥ 6 참, 9 → 3
 t2                                           UPDATE ... SET stock = stock - 5
                                                WHERE product_id = 1 AND stock >= 5
                                              → 행 1의 잠금을 기다린다
 t3  INSERT orders, order_item
 t4  COMMIT → 잠금 해제
 t5                                           → 잠금 획득, 최신 커밋 버전(3)을 읽음
                                                3 ≥ 5 거짓 → 0 rows affected
 t6                                           ROLLBACK, "재고 부족" 응답
───  최종 재고 3, 판매 6개. 합계가 맞는다.

    실제로 실행할 때는 T1이 차감 뒤 커밋 전에 3초 머물도록 DO SLEEP(3)을 넣고, 1초 뒤 T2를 시작했다. T2의 UPDATE는 약 2초(1.96 sec) 기다린 뒤 Query OK, 0 rows affected, Rows matched: 0 Changed: 0으로 끝났고, T2를 롤백한 뒤 K1의 재고는 3이었다. 핵심은 t5다. T2의 UPDATE는 스냅숏을 읽지 않는다. 앞에서 본 것처럼 DML은 다른 트랜잭션이 커밋한 최신 버전 위에서 동작하므로, 잠금을 얻은 뒤 T1이 바꿔 놓은 3을 보고 조건을 다시 판단한다. 잠금을 얻을 때까지 T2가 기다리는 시간은 T1이 커밋할 때까지이고, 그 기다림이 innodb_lock_wait_timeout(기본 50초)을 넘으면 잠금 대기 시간 초과 오류로 끝난다. 그래서 재고를 잠근 트랜잭션은 짧게 유지해야 한다. 결제 승인처럼 외부 시스템을 기다리는 일을 이 트랜잭션 안에 넣으면, 인기 상품의 주문이 모두 그 시간만큼 줄을 선다.

    같은 일을 "읽고 판단하고 쓰는" 방식으로 하면 어떻게 될까. T1과 T2가 각각 SELECT stock_quantity로 9를 읽고, 애플리케이션에서 9 ≥ 6, 9 ≥ 5를 확인한 뒤 SET stock_quantity = 3과 SET stock_quantity = 4를 쓴다. 두 번째 쓰기는 첫 번째 쓰기를 기다렸다가 덮어쓰므로 최종 재고는 4가 되고, 11개가 팔렸는데 재고는 5개만 줄었다. 잃어버린 갱신이다. 이 방식을 쓰려면 처음 읽을 때 SELECT ... FOR UPDATE로 잠가야 한다. 조건부 UPDATE는 판단과 쓰기를 한 문장에 묶어 이 문제를 구조적으로 없앤다.

    T1이 재고 행을 잠그고 차감하는 동안 T2가 기다리고, T1 커밋 뒤 T2가 최신 값 3을 읽어 조건이 거짓이 되는 과정을 시간 순서로 보여 준다. 세로 생명선 세 개의 시퀀스 다이어그램: 왼쪽 "T1", 가운데 "product 행 1 (재고)", 오른쪽 "T2". 가운데 생명선 맨 위에 "재고 9". T1에서 가운데로 화살표 "UPDATE 재고-6 (재고 ≥ 6)", 가운데 생명선에 자물쇠 아이콘과 "T1 잠금", 값 "9 → 3". T2에서 가운데로 화살표 "UPDATE 재고-5 (재고 ≥ 5)"가 자물쇠 앞에서 멈추고 모래시계 아이콘과 라벨 "대기". T1에서 "COMMIT" 화살표, 자물쇠가 열리는 아이콘. 이어서 T2 쪽에 화살표 "최신 값 3 읽기", 라벨 "3 ≥ 5 거짓 → 0행". T2 아래에 "ROLLBACK". 맨 아래 가운데 "최종 재고 3". 배경 흰색, T1은 파란색, T2는 주황색. 조건부 UPDATE는 잠금을 얻은 뒤 최신 커밋 값으로 조건을 다시 판단하므로, 동시 주문이 재고를 초과해 차감하지 못한다.

    잠금 순서와 교착 상태

    주문 생성의 1단계에 "상품 번호 오름차순으로"라는 조건을 붙인 이유가 여기 있다. T1이 K1(1번)과 M1(3번)을, T2가 M1과 K1을 주문하는데 각자 장바구니에 담긴 순서대로 재고를 차감한다고 하자. T1이 1번 행을 잠그고, T2가 3번 행을 잠근다. 이어서 T1은 3번 행을, T2는 1번 행을 원한다. 서로 상대가 쥔 잠금을 기다리므로 어느 쪽도 진행할 수 없다. 교착 상태(deadlock)다. InnoDB는 이를 감지해 한쪽 트랜잭션을 롤백시키고, 롤백된 쪽은 교착 상태 오류를 받는다. MySQL 8.4.13에서 두 세션으로 이 순서를 재현하면, 두 번째 잠금을 요청한 T2가 ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction을 받고, T1의 3번 행 UPDATE는 잠깐(0.35 sec) 기다린 뒤 성공한다.

    두 트랜잭션이 모두 번호 오름차순으로 잠근다면 이 순환이 생길 수 없다. T2도 1번 행부터 잠그려 하므로, T1이 1번을 쥐고 있는 동안 T2는 아무것도 쥐지 않은 채 1번 앞에서 기다린다. T1은 3번까지 잠그고 커밋하고, 그다음 T2가 진행한다. MySQL 매뉴얼도 한 트랜잭션에서 여러 테이블이나 같은 테이블의 여러 행을 바꿀 때 매번 같은 순서로 하면 트랜잭션들이 잘 정의된 대기열을 이루어 교착 상태가 생기지 않는다고 권한다. 같은 절은 교착 상태 때문에 실패한 트랜잭션은 다시 실행할 준비를 해 두라고도 말한다. 순서를 지켜도 다른 경로의 잠금과 얽힐 수 있으므로, 재시도는 순서 규칙과 별개로 필요한 안전장치다.

    자동 증가 번호의 빈틈

    주문 저장(3단계)까지 성공한 뒤 4단계에서 실패하는 경우를 생각해 보자. 예를 들어 버그로 수량 0이 넘어와 chk_order_item_quantity에 걸렸고, 애플리케이션이 트랜잭션을 롤백했다. 주문 행은 사라지지만 그 행에 붙었던 주문 번호는 돌아오지 않는다. InnoDB 매뉴얼은 자동 증가 값을 생성한 트랜잭션이 롤백되면 그 값은 "잃어버린" 것이 되며 다시 쓰이지 않고, 그래서 자동 증가 열의 값에 빈틈이 생길 수 있다고 설명한다. 다음 주문은 그다음 번호를 받는다. 따라서 주문 번호가 3, 4, 6으로 이어진다고 해서 5번 주문이 지워졌다고 판단하면 안 되고, 주문 번호의 최댓값으로 주문 건수를 세어서도 안 된다. 대리 키는 행을 가리키는 이름일 뿐, 순번이나 개수가 아니다.

    Q7의 날짜 조건을 WHERE DATE(ordered_at) = '2026-11-10'으로 쓰지 않은 이유가 있다. 인덱스 idx_orders_ordered에는 ordered_at의 값이 정렬되어 있지 DATE(ordered_at)의 값이 정렬되어 있는 것이 아니므로, 열을 함수로 감싸면 인덱스로 구간을 찾을 수 없다. 반쯤 열린 구간 ordered_at >= 시작 AND ordered_at < 다음날로 쓰면 인덱스 범위 검색이 된다. MySQL 8.0.13부터는 식의 값을 인덱싱하는 함수 기반 키 파트(functional key part)를 만들 수 있지만, 매뉴얼의 예처럼 조건에 인덱스와 같은 식을 써야 쓰이므로, 구간으로 쓸 수 있는 조건이라면 구간으로 쓰는 편이 단순하다. 기간이 길어 범위에 걸리는 주문이 많아지면 행마다 status와 total_amount를 읽으러 클러스터형 인덱스를 찾아가는 비용이 커지므로, 매뉴얼의 설명대로 옵티마이저는 인덱스 범위 검색이 테이블 전체 읽기보다 싸지 않다고 보면 전체 읽기를 고른다. 관리자 화면이 느려지면 (ordered_at, status, total_amount) 커버링 인덱스를 검토할 수 있지만, 주문 삽입마다 그 비용을 치른다는 점을 함께 따진다.

    마지막으로 역정규화 점검 쿼리 두 개를 실행한다. 점검 쿼리 1은 주문 1(139,000 = 89,000 × 1 + 25,000 × 2)과 주문 2(25,000 = 25,000 × 1)가 모두 일치하므로 빈 결과를 돌려준다. 점검 쿼리 2는 상품 1(리뷰 1개, 합계 5), 상품 2와 3(리뷰 0개, 합계 0)이 모두 일치하므로 역시 빈 결과다. 상품 2, 3은 리뷰가 없어 외부 조인의 SUM(r.rating)이 NULL이 되는데, COALESCE로 0으로 바꿨기 때문에 저장된 0과 비교할 수 있다. COALESCE를 빠뜨리면 0 <> NULL이 UNKNOWN이 되어 어긋남을 놓치는 점검 쿼리가 된다.

    흔한 오해와 함정

    "WHERE에 나오는 열마다 인덱스를 하나씩 만들면 된다." 단일 열 인덱스 여러 개는 복합 인덱스 하나를 대신하지 못한다. member_id 인덱스와 ordered_at 인덱스가 따로 있으면, 회원 1의 주문을 최신순으로 10건 가져오는 쿼리는 한 인덱스로 회원의 주문을 모두 찾은 뒤 정렬하거나, 다른 인덱스로 최신순으로 읽으며 회원을 걸러야 한다. 등호 조건과 정렬을 한 번에 처리하는 것은 두 열이 올바른 순서로 들어간 복합 인덱스뿐이다.

    "선택도가 낮은 열은 인덱스에 넣으면 안 된다." 단독 인덱스라면 대체로 맞다. 그러나 복합 인덱스에서 등호 조건으로 쓰이는 열은 선택도가 낮아도 구간을 좁히고, 뒤에 오는 정렬 열의 순서를 살린다. Q2의 status가 그 예다. 넣을지 말지는 그 값으로 걸러지는 행이 얼마나 되는지로 판단한다.

    "역정규화는 조인을 없애는 것이다." 기본 키로 몇 건을 찾는 조인은 싸다. 역정규화가 큰 효과를 내는 곳은 필터와 정렬이 다른 테이블에 흩어져 있어 LIMIT이 일찍 멈추지 못하는 쿼리, 그리고 큰 범위를 집계하는 쿼리다. 조인을 없애려고 바뀌는 값을 복사하면 이득보다 지키는 비용이 크다.

    "주문상품의 상품명과 단가는 중복이니 정규화해야 한다." 시점이 다른 사실이다. 함수 종속성을 따져 보면 결정자가 다르다. 이것을 지우면 상품 가격을 바꾸는 순간 과거 주문의 금액이 바뀐다.

    "외래 키는 성능 때문에 빼는 것이 낫다." 외래 키에는 비용이 있다. 자식 열에 인덱스가 필요하고, 자식 행을 넣을 때 부모 행에 공유 잠금이 걸리며, 부모를 지울 때 자식을 찾아야 한다. 그러나 그 대가로 고아 행이 생기지 않고, 복사한 값의 일치를 강제할 수 있고, 자동 생성 ERD에 관계가 나타난다. 빼기로 한다면 이 세 가지를 무엇으로 대신할지를 함께 정해야 한다. 비용만 보고 빼면 보장도 함께 사라진다.

    "자동 생성한 ERD가 곧 설계 문서다." 자동 생성 ERD는 데이터베이스가 강제하는 것만 보여 준다. 최소 참여 1, 상태 전이 규칙, 파생 값의 등식은 그림에 없다. 설계 문서는 ERD와 정의서에 "애플리케이션이 지키는 규칙 목록"을 더한 것이다.

    "주문 번호에 빈틈이 있으면 데이터가 지워진 것이다." 롤백된 트랜잭션이 받은 자동 증가 값은 다시 쓰이지 않는다. 빈틈은 정상 동작이다. 건수는 COUNT(*)로 센다.

    정리: 물리적 모델링 실습의 순서

    이 회차에서 한 일을 작업 순서로 다시 놓으면 다음과 같다. 순서 자체가 하나의 방법론이다. 접근 경로를 모르고 인덱스를 정할 수 없고, 인덱스를 정하지 않고 역정규화의 이득을 평가할 수 없으며, 결정이 끝나지 않으면 정의서와 DDL을 쓸 수 없다. 그리고 만든 뒤에는 거꾸로 읽어 설계와 대조하고, 데이터로 확인한다.

    이 회차로 이 권이 끝난다. 01회에서 "스키마는 가장 오래 사는 코드"라고 했다. 이번 실습의 DDL도 그렇다. 애플리케이션 코드는 몇 번이고 다시 쓰이겠지만, 여기서 정한 키와 제약과 인덱스는 데이터가 쌓이는 순간부터 바꾸기 어려워진다. 그래서 물리 설계의 결정에는 언제나 근거를 남긴다. 어떤 쿼리를 위한 인덱스인가, 어떤 화면을 위한 역정규화이고 무엇으로 지키는가, 어떤 규칙이 데이터베이스 밖에 있는가. 그 근거가 정의서와 DDL 주석에 남아 있으면, 요구 사항이 바뀔 때 무엇을 다시 판단해야 하는지 알 수 있다. 공통 코드, 계층 구조, 변경 이력, 통계 테이블처럼 실무에서 반복해서 만나는 설계 패턴은 다음 권인 데이터베이스 설계 2편의 주제다.
    접근 경로 목록
    화면과 처리마다 찾는 조건, 정렬, 건수, 읽는 열, 빈도를 적은 목록. 인덱스와 역정규화는 이 목록에서 나온다.
    복합 인덱스의 열 순서
    등호 조건 열을 앞에, 정렬 열을 뒤에 둔다. 왼쪽 접두사만 검색에 쓰이고, 앞 열이 범위 조건이거나 IN 목록이면 뒤 열의 순서로 정렬을 대신할 수 없다.
    인덱스 확장과 커버링
    InnoDB 보조 인덱스의 항목에는 기본 키가 들어 있어, 옵티마이저는 인덱스를 (인덱스 열, 기본 키)로 보고 정렬의 동률 처리와 커버링에 쓴다.
    외래 키 인덱스
    MySQL은 부모 삭제·변경 때 자식을 테이블 전체 읽기 없이 찾도록 외래 키 열이 맨 앞에 오는 인덱스를 요구한다. 외래 키 열로 시작하는 복합 인덱스가 이 역할을 겸한다.
    역정규화 평가 기준
    복사하는 값이 바뀌지 않는가, 필터와 정렬을 한 테이블에 모아 인덱스 하나로 끝내게 하는가. 기본 키 조인만 없애는 역정규화는 이득이 작다.
    복합 외래 키로 복사본 지키기
    복사한 열을 원본 키와 묶어 부모의 유일 인덱스를 참조하게 하면, 복사본과 원본의 일치를 데이터베이스가 강제한다.
    원자적 증가와 점검 쿼리
    바뀌는 파생 값은 원본 변경과 같은 트랜잭션에서 UPDATE 안의 증가식으로 고치고, 원본에서 다시 계산해 비교하는 점검 쿼리를 둔다.
    조건부 UPDATE
    판단 조건을 WHERE에 넣어 판단과 쓰기를 한 문장으로 묶는다. 잠금을 얻은 뒤 최신 커밋 값으로 조건을 다시 판단하므로 재고 초과 차감과 중복 상태 전이를 막는다.
    ERD 리버스 엔지니어링
    도구는 INFORMATION_SCHEMA의 외래 키·NULL 허용·유일 인덱스 정보로 선과 기호를 추론한다. 카탈로그에 없는 규칙은 그려지지 않는다.

    실무에서 인덱스 설계가 틀어지는 가장 흔한 경로는 접근 경로 목록이 시간이 지나며 바뀌는데 인덱스는 그대로인 경우다. 출시할 때는 없던 관리자 검색 화면, 엑셀 내려받기, 배치 집계가 하나씩 늘어나고, 각각이 급하게 인덱스를 하나씩 추가한다. 몇 년 뒤에는 쓰기마다 열 개 가까운 B+Tree를 고치면서도 정작 느린 쿼리는 여전히 느리다. 주기적으로 실제 실행되는 쿼리를 모아 접근 경로 목록을 갱신하고, sys.schema_redundant_indexes로 겹치는 인덱스를 찾고, 지울 후보는 보이지 않는 인덱스로 바꿔 한동안 지켜본 뒤 지우는 절차가 안전하다. 새 인덱스를 추가할 때는 그 인덱스가 외래 키 인덱스를 대신할 수 있는지, 기존 인덱스의 왼쪽 접두사와 겹치는지를 먼저 본다.

    역정규화의 판단은 업무 규칙에 묶여 있다. 이 실습에서 주문 총액이 싼 역정규화였던 것은 "주문상품은 주문 후 바뀌지 않는다"는 규칙 때문이었다. 부분 취소나 수량 변경 기능이 추가되는 순간 총액은 바뀌는 값이 되고, 주문상품을 고치는 모든 경로에서 총액을 함께 고쳐야 한다. 기능 기획을 검토할 때 "이 기능이 기존에 바뀌지 않던 값을 바뀌게 만드는가"를 묻고, 그렇다면 그 값을 복사해 둔 곳을 정의서의 [역정규화] 표시로 찾아 함께 고쳐야 한다. 정의서에 역정규화 표시와 점검 쿼리를 남겨 두는 이유가 여기 있다.

    동시성 문제는 테스트 환경에서는 거의 드러나지 않는다. 한 사람이 한 번씩 클릭하는 테스트에서는 "읽고 판단하고 쓰는" 재고 차감도 잘 동작한다. 문제는 인기 상품의 할인 행사처럼 같은 행에 요청이 몰릴 때 나타나고, 그때는 재고가 음수가 되거나(CHECK가 없다면) 판매 수량과 재고 감소량이 어긋난다. 같은 행에 몰리는 경합은 잠금 대기 시간으로도 나타난다. 재고 행을 잠근 트랜잭션 안에 외부 결제 호출이나 무거운 조회를 넣지 않고, 잠그는 순서를 상품 번호 순으로 통일하고, 교착 상태로 롤백된 트랜잭션을 재시도하는 것이 기본이다. 리뷰 카운터처럼 같은 행을 고치는 다른 기능이 있다면 그 열을 별도 테이블로 분리하는 것도 경합을 줄이는 물리 설계의 선택이다.

     InnoDB 테이블 orders에 인덱스 (member_id, ordered_at)만 있다. SELECT order_id, ordered_at FROM orders WHERE member_id = 1 ORDER BY ordered_at DESC LIMIT 10이 클러스터형 인덱스를 찾아가지 않고 보조 인덱스만으로 끝날 수 있는 이유는? InnoDB는 모든 보조 인덱스에 테이블의 모든 열을 복사해 둔다. InnoDB 보조 인덱스의 각 레코드에는 인덱스 열과 함께 그 행의 기본 키 열이 들어 있어, order_id도 인덱스에서 읽을 수 있다. LIMIT 10이 있으면 옵티마이저는 항상 인덱스만 읽는다. order_id는 AUTO_INCREMENT 열이라 값을 계산으로 알 수 있다. 매뉴얼에 따르면 InnoDB 보조 인덱스의 레코드는 지정한 열과 함께 기본 키 열을 담는다. 그래서 SELECT 열이 (member_id, ordered_at, order_id) 안에 모두 있으면 인덱스만으로 답할 수 있다(Using index). 보조 인덱스가 모든 열을 담지는 않으며, LIMIT은 읽는 양을 줄일 뿐 읽을 위치를 바꾸지 않는다. 자동 증가 값은 빈틈이 있을 수 있어 계산으로 알 수 없다. 이 회차의 역정규화 중 원본과 어긋날 위험이 가장 낮은 것은 무엇이고, 왜인가? product.review_count. UPDATE 안에서 원자적으로 증가시키기 때문이다. orders.total_amount. 점검 쿼리가 있기 때문이다. review.product_id. 바뀌지 않는 값의 복사이고, 복합 외래 키가 원본과의 일치를 데이터베이스 수준에서 강제하기 때문이다. 세 가지 모두 같은 트랜잭션에서 쓰므로 위험이 같다. 리뷰의 상품 번호는 주문상품의 상품 번호를 복사한 것인데 그 원본은 생성 후 바뀌지 않고, (order_item_id, product_id) 복합 외래 키가 존재하지 않는 쌍을 거부하므로 어긋난 값이 들어갈 길이 없다. 리뷰 카운터는 리뷰마다 바뀌는 값이라 갱신 경로를 하나라도 놓치면 어긋난다. 주문 총액의 점검 쿼리는 어긋남을 찾아낼 뿐 막지 못한다. 재고 9인 상품에 T1이 UPDATE product SET stock_quantity = stock_quantity - 6 WHERE product_id = 1 AND stock_quantity >= 6을 실행해 커밋하기 전에, T2가 같은 형태로 5개를 차감하는 문장을 실행했다. 기본 격리 수준(REPEATABLE READ)에서 T1이 커밋한 뒤 T2의 결과는? T2는 잠금을 기다렸다가 최신 커밋 값 3을 읽고, 3 ≥ 5가 거짓이므로 0행을 바꾼다. T2는 자신의 스냅숏에 있는 9를 기준으로 판단해 4로 만든다. T2는 즉시 교착 상태 오류를 받는다. T2는 -2를 쓰려다 CHECK 위반으로 실패한다. 매뉴얼은 트랜잭션의 스냅숏이 SELECT에 적용되며 DML에는 반드시 적용되지 않는다고 설명한다. UPDATE는 행의 배타 잠금을 얻은 뒤 최신 커밋 버전을 기준으로 동작하므로, T2는 T1이 남긴 3으로 WHERE 조건을 판단한다. 조건이 거짓이라 아무 행도 바뀌지 않고, 음수를 쓰려는 시도 자체가 없으므로 CHECK에도 닿지 않는다. 한 행만 두고 기다리는 관계라 교착 상태도 아니다. MySQL이 외래 키의 자식 쪽 열에 인덱스를 요구하는(없으면 자동으로 만드는) 가장 직접적인 이유는? 자식 행을 삽입할 때 부모 테이블의 기본 키를 찾기 위해서다. ERD 도구가 관계선을 그리려면 인덱스가 있어야 하기 때문이다. 외래 키 열은 항상 유일해야 하므로 유일성 검사를 위해서다. 부모 행을 삭제하거나 키를 바꿀 때 그 부모를 참조하는 자식 행을 테이블 전체를 읽지 않고 찾기 위해서다. 매뉴얼은 외래 키 검사가 테이블 스캔 없이 빠르게 이루어지도록 외래 키와 참조되는 키에 인덱스를 요구한다고 설명한다. 자식 삽입 때 부모를 찾는 데는 부모 쪽 키 인덱스가 쓰이고, 자식 쪽 인덱스는 부모를 지우거나 바꿀 때 참조하는 자식을 찾는 데 쓰인다. ERD 도구는 인덱스가 아니라 외래 키 제약 정보를 읽는다. 외래 키 열은 일대다 관계에서 당연히 중복된다. 쇼핑몰 데이터베이스를 리버스 엔지니어링해 ERD를 만들었다. 다음 중 카탈로그 정보만으로 그림에 나타날 수 없는 것은? 리뷰와 주문상품이 일대일 관계라는 것 주문에는 주문상품이 하나 이상 있어야 한다는 것 상위 카테고리가 없는 카테고리가 있을 수 있다는 것 리뷰가 주문상품의 두 열을 함께 참조한다는 것 일대일은 외래 키 열과 정확히 일치하는 유일 인덱스로, 선택 참여는 NULL을 허용하는 외래 키 열로, 두 열 참조는 KEY_COLUMN_USAGE의 같은 제약 이름 두 행으로 카탈로그에 기록되어 있다. 반면 "자식이 최소 하나 있어야 한다"는 규칙은 외래 키로 표현되지 않아 카탈로그에 없으므로, 자동 생성 ERD는 그 끝을 0 이상으로 그린다.
    접근 경로(access path)
    쿼리가 원하는 행에 도달하는 방법. 설계 단계에서는 기능별 조건·정렬·건수·빈도의 목록을 뜻하고, 실행 단계에서는 옵티마이저가 고른 인덱스와 읽기 방식을 뜻한다.
    왼쪽 접두사(leftmost prefix)
    복합 인덱스의 첫 열부터 연속된 열들의 조합. MySQL은 이 조합에 대한 조건만 인덱스 검색에 쓸 수 있다.
    인덱스 확장(index extension)
    InnoDB가 보조 인덱스 뒤에 기본 키 열을 덧붙여 저장하고, 옵티마이저가 그 열까지 검색·정렬·커버링에 활용하는 것. use_index_extensions 스위치로 제어한다.
    커버링 인덱스(covering index)
    쿼리에 필요한 열이 모두 들어 있어 클러스터형 인덱스를 다시 찾아가지 않고 답할 수 있는 인덱스. EXPLAIN의 Extra에 Using index로 나타난다.
    filesort
    인덱스 순서로 결과 순서를 만들 수 없을 때 MySQL이 찾은 행을 따로 정렬하는 단계. EXPLAIN의 Extra에 Using filesort로 나타난다.
    역정규화(denormalization)
    조회 비용을 줄이려고 정규화된 사실을 다른 곳에 한 번 더 기록하는 결정. 복사본을 원본과 일치시키는 책임이 함께 생긴다.
    잃어버린 갱신(lost update)
    두 트랜잭션이 같은 값을 읽고 각자 계산한 결과를 쓰면서 한쪽의 변경이 덮여 사라지는 현상. 증가식을 UPDATE 안에 쓰거나 잠금 읽기로 막는다.
    리버스 엔지니어링(reverse engineering)
    실행 중인 데이터베이스나 생성 스크립트의 메타데이터에서 모델과 ERD를 거꾸로 만들어 내는 작업.
    데이터 사전(data dictionary)
    MySQL 8.0에서 테이블·열·인덱스·제약의 정의를 저장하는 카탈로그. INFORMATION_SCHEMA의 여러 테이블이 그 위의 뷰로 구현된다.
    키셋 페이지네이션(keyset pagination)
    OFFSET 대신 직전 페이지 마지막 행의 정렬 키 값 다음부터 읽는 페이지 이동 방식. 인덱스에서 위치를 키 값으로 바로 찾는다.
