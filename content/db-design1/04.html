    이 회차의 질문: 선 하나가 테이블에서 무엇이 되는가

    개념적 모델링을 마치면 손에 ERD 한 장이 남는다. 상자는 엔티티이고, 상자 사이의 선은 관계다. 선의 양 끝에는 까마귀발 기호가 붙어 있어서 "회원은 주문을 0개 이상 한다", "주문은 반드시 회원 한 명이 한다" 같은 문장을 읽어 낼 수 있다. 앞 회차에서는 상자 하나하나에 기본 키를 정했다. 이제 남은 일은 선을 옮기는 것이다. 그런데 관계형 데이터베이스에는 "선"이라는 구조물이 없다. 테이블과 열과 값이 있을 뿐이다. 상자 두 개를 잇는 선은 어떤 열, 어떤 값, 어떤 제약이 되어야 할까.

    이 질문에 답을 잘못 내면 곤란한 일이 연달아 생긴다. 선을 엉뚱한 쪽 테이블에 옮기면 한 칸에 값을 여러 개 넣어야 하거나 같은 행을 여러 번 복사해야 한다. 선의 양 끝에 붙어 있던 "반드시"와 "없어도 된다"를 놓치면 주인 없는 주문이 생기거나, 반대로 아직 존재하지 않는 것을 강제하다 데이터를 넣을 수 없게 된다. 선을 바르게 옮겼더라도 그 선을 따라 조인하는 법을 모르면 매출 합계가 두 배로 나오는 보고서를 만든다. 이 세 가지 문제가 이 회차의 세 축이다.

    순서는 이렇다. 먼저 논리적 모델링에서 관계가 무엇으로 표현되는지, 곧 외래 키와 참조 무결성을 세운다. MySQL InnoDB가 외래 키 제약을 선언했을 때 실제로 무엇을 검사하는지도 문서로 확인한다. 다음으로 관계의 최소 카디널리티인 참여도를 다루고, 참여도가 NOT NULL로 옮겨지는 범위와 옮겨지지 않는 범위를 가른다. 셋째로 일대다 관계에서 외래 키를 어느 테이블에 둘지를 두 번에 걸쳐 따진다. 마지막으로 그렇게 만든 관계를 조인할 때 결과 행이 늘어나는 현상, 흔히 "뻥튀기"라고 부르는 현상의 원리와 해법을 본다. 중간중간 InnoDB의 잠금과 조인 실행 방식까지 한 층씩 내려간다.

    설명의 기준은 MySQL 8.0 이상과 InnoDB 저장 엔진이다. 예제는 작은 쇼핑몰이다. 회원(member)이 주문(orders)을 하고, 주문은 주문 상품(order_item)과 결제(payment)를 여러 개 가진다. 상품(product)은 카테고리(category)에 속할 수도 있고 속하지 않을 수도 있다. 주문 테이블 이름을 order가 아니라 orders로 한 것은 ORDER가 SQL 예약어이기 때문이다. 일대일과 다대다 관계(05회), 식별 관계와 비식별 관계(06회)는 뒤 회차의 몫이므로 여기서는 필요한 만큼만 언급한다.

    논리적 모델링에서 관계: 값의 일치와 참조 무결성

    03회에서 보았듯이 관계형 모델에는 포인터가 없다. 행은 오직 값으로 구별되고, 행 하나를 가리키는 유일한 방법은 그 행의 키 값을 적어 두는 것이다. 그래서 관계도 값으로 표현된다. "주문 10번은 회원 1번이 했다"는 사실은 주문 10번 행의 어느 열에 1이라는 값을 적는 것으로 기록된다. 이 열이 외래 키(foreign key)다. 두 행이 관계를 맺고 있다는 것은 결국 한쪽 행의 외래 키 값과 다른 쪽 행의 키 값이 일치한다는 뜻이다. 선은 값의 일치가 된다.

    값의 일치로 관계를 표현하면 새로운 위험이 생긴다. 적어 둔 값에 해당하는 행이 실제로 없을 수 있다. 주문 행의 회원 열에 99가 적혀 있는데 회원 99번이 없다면 그 주문은 존재하지 않는 회원을 가리킨다. 이런 상태를 깨진 참조(dangling reference)라고 하고, 깨진 참조가 하나도 없는 상태를 참조 무결성(referential integrity)이 지켜지는 상태라고 한다. 정확히 말하면 참조 무결성은 "외래 키의 값은 NULL이거나, 참조되는 테이블에 실제로 존재하는 키 값이어야 한다"는 규칙이다. NULL이 허용되는 이유는 뒤의 참여도 절에서 다룬다.

    논리 모델에서 관계 하나를 옮길 때 결정해야 할 것은 네 가지다. 첫째, 외래 키 열을 어느 테이블에 둘 것인가. 둘째, 그 열이 NULL을 허용하는가. 셋째, 외래 키 열에 UNIQUE를 걸 것인가. 넷째, 참조되는 행이 지워지거나 키가 바뀔 때 무엇을 할 것인가. 첫째는 카디널리티의 최댓값이, 둘째는 참여도가, 셋째는 일대일인지 일대다인지가, 넷째는 업무 규칙이 정한다. 개념 모델의 선 하나에 담겨 있던 정보가 이 네 결정으로 나뉘어 테이블에 들어간다.

    논리적 ERD에서는 이 결정이 그림에도 드러난다. 개념 ERD의 주문 상자에는 회원을 가리키는 속성이 없었다. 관계선이 그 역할을 했기 때문이다. 논리 ERD에서는 주문 상자 안에 member_id (FK)라는 속성이 새로 생긴다. 관계선은 그대로 남아 이 외래 키가 어느 상자의 키를 가리키는지 보여 준다. 부모의 키가 자식의 기본 키 일부가 되는지에 따라 선을 실선과 점선으로 구별하는 표기도 있는데, 이것이 식별 관계와 비식별 관계이고 06회에서 다룬다. 이 회차의 예제는 모두 자식이 자기 대리 키를 갖고 부모의 키는 일반 열로만 받는 비식별 관계다.

    외래 키 제약이 실제로 검사하는 것 (MySQL InnoDB)

    외래 키 열을 만드는 것과 외래 키 제약(foreign key constraint)을 선언하는 것은 다른 일이다. 열만 만들면 그 열은 그냥 숫자를 담는 칸이다. 제약을 선언해야 데이터베이스가 참조 무결성을 대신 지켜 준다. MySQL에서 회원과 주문을 옮긴 DDL은 다음과 같다.

    CREATE TABLE member (
    member_id BIGINT      NOT NULL AUTO_INCREMENT,
    name      VARCHAR(50) NOT NULL,
    PRIMARY KEY (member_id)
) ENGINE = InnoDB;

CREATE TABLE orders (
    order_id     BIGINT   NOT NULL AUTO_INCREMENT,
    member_id    BIGINT   NOT NULL,
    total_amount INT      NOT NULL,
    ordered_at   DATETIME NOT NULL,
    PRIMARY KEY (order_id),
    CONSTRAINT fk_orders_member
        FOREIGN KEY (member_id) REFERENCES member (member_id)
        ON DELETE RESTRICT
        ON UPDATE RESTRICT
) ENGINE = InnoDB;

    이 제약이 있으면 InnoDB는 네 가지 순간에 검사를 한다. 자식 행을 넣을 때(INSERT INTO orders) 그 member_id 값을 가진 회원 행이 있는지 본다. 자식 행의 외래 키 값을 바꿀 때도 새 값을 가진 회원이 있는지 본다. 부모 행을 지울 때(DELETE FROM member) 그 회원을 가리키는 주문이 있는지 보고, 있으면 참조 동작에 따라 거부하거나 함께 처리한다. 부모 행의 키 값을 바꿀 때도 마찬가지다. 부모 쪽 비키 열, 예를 들어 회원의 이름을 바꾸는 것은 참조와 상관이 없으므로 검사하지 않는다.

    참조 동작(referential action)은 부모 쪽 변경이 자식을 깨뜨리려 할 때 무엇을 할지 정한다. MySQL 8.0 문서가 정의하는 동작은 다섯 가지다. CASCADE는 부모를 지우거나 키를 바꾸면 그에 맞는 자식 행도 함께 지우거나 바꾼다. SET NULL은 자식의 외래 키 열을 NULL로 바꾼다. RESTRICT는 부모 쪽 작업을 거부한다. NO ACTION은 표준 SQL의 키워드인데, InnoDB에서는 RESTRICT와 같아서 관련된 자식이 있으면 부모 쪽 작업을 즉시 거부한다. SET DEFAULT는 파서가 인식은 하지만 InnoDB는 지원하지 않는다. MySQL 8.0 문서는 InnoDB가 이런 절을 포함한 테이블 정의를 거부한다고 적고 있지만, MySQL 8.0.46과 8.4.13에서 실행해 보면 ON DELETE SET DEFAULT를 단 테이블이 오류도 경고도 없이 만들어지고 SHOW CREATE TABLE에도 그 절이 남는다. 그런데 자식이 있는 부모 행을 지우면 자식 열을 기본값으로 바꾸지 않고 ERROR 1451 (23000): Cannot delete or update a parent row로 거부한다. 선언은 받아들여도 동작은 RESTRICT와 같으니, 의도한 동작은 일어나지 않는다. ON DELETE나 ON UPDATE를 생략하면 기본값은 NO ACTION이므로, InnoDB에서는 생략이 곧 RESTRICT다.

    참조 동작은 참여도와 맞물린다. 문서는 SET NULL을 쓸 때 자식 쪽 열을 NOT NULL로 선언하지 않았는지 확인하라고 한다. 당연한 말 같지만 의미가 있다. "부모가 사라지면 자식은 부모 없이 남는다"는 SET NULL의 의미가 성립하려면 자식이 부모 없이 존재할 수 있어야, 곧 자식 쪽 참여가 선택이어야 한다. 주문처럼 반드시 회원이 있어야 하는 자식에게는 SET NULL을 쓸 수 없고, RESTRICT 아니면 CASCADE를 골라야 한다. 회원을 지울 때 주문까지 지우는 것은 대부분의 업무에서 받아들일 수 없으므로(주문은 매출과 세금의 근거다) 회원과 주문에는 RESTRICT가 맞고, 탈퇴는 행을 지우는 대신 상태 열로 표현하게 된다. 반면 주문과 주문 상품처럼 자식이 부모의 일부에 불과한 관계에서는 CASCADE가 자연스럽다.

    문서로 확인한 InnoDB 외래 키의 규칙

    선언만 하면 끝날 것 같지만 InnoDB의 외래 키에는 알아 두어야 할 규칙이 여럿 있다. 아래는 모두 MySQL 8.0 Reference Manual의 FOREIGN KEY Constraints 절과 Foreign Key Differences 절에서 확인한 내용이다. 실행으로 확인할 수 있는 항목은 MySQL 8.0.46과 8.4.13에서 직접 돌려 보았고, 결과가 문서와 다른 곳은 그 자리에 적었다.

    • 인덱스가 필요하다. 외래 키 검사가 테이블 전체를 훑지 않도록, 자식 테이블에는 외래 키 열이 같은 순서로 맨 앞에 오는 인덱스가 있어야 한다. 없으면 자동으로 만들어진다. 그리고 나중에 그 역할을 대신할 수 있는 다른 인덱스를 만들면 자동으로 만든 인덱스는 조용히 삭제될 수 있다. 예를 들어 (member_id, ordered_at) 인덱스를 추가하면 member_id가 맨 앞에 있으므로 외래 키 검사에 쓸 수 있다. 부모 테이블에도 참조되는 열이 맨 앞에 오는 인덱스가 있어야 한다.
    • 자료형이 비슷해야 한다. INT나 DECIMAL 같은 고정 정밀도 타입은 크기와 부호가 같아야 한다. 부모가 BIGINT UNSIGNED인데 자식이 BIGINT면 제약을 만들 수 없다. 문자열은 길이가 달라도 되지만 문자 집합과 콜레이션은 같아야 한다.
    • 열 정의에 붙인 REFERENCES는 무시된다. member_id BIGINT REFERENCES member(member_id)처럼 열 정의 안에 쓴 인라인 참조는 표준 SQL 문법이지만, MySQL 8.0과 8.4 문서는 이것을 파싱만 하고 무시한다고 밝힌다. 제약도 인덱스도 생기지 않는다. 반드시 별도의 FOREIGN KEY 절로 써야 한다. 다른 DBMS에서 쓰던 DDL을 옮겨 올 때 자주 걸리는 함정이다.
    • MATCH 절은 지켜지지 않는다. 어떤 저장 엔진도 MATCH 절을 인식하거나 강제하지 않는다. 문서는 명시적으로 쓰면 오히려 ON DELETE와 ON UPDATE 절이 무시된다고 적고 있다. 그러나 MySQL 8.0.46과 8.4.13에서 MATCH FULL ON DELETE CASCADE로 제약을 만들고 부모를 지워 보면 자식 행이 함께 지워졌다. CASCADE는 동작했고, 지켜지지 않은 것은 MATCH FULL 쪽이었다. 복합 외래 키 (a, b)에 MATCH FULL을 걸어도 (7, NULL)처럼 한 열만 NULL인 행이 그대로 들어갔다. 대신 InnoDB는 사실상 MATCH SIMPLE의 의미를 따른다. 외래 키 열이 전부 또는 일부라도 NULL이면 그 행은 부모와 대조하지 않고 들어간다.
    • 검사는 행 단위로, 즉시 한다. 여러 행을 바꾸는 문장에서도 외래 키는 한 행씩 검사되고, 트랜잭션 커밋 때까지 미루지 않는다. 같은 문서는 SQL 표준의 기본 동작이 문장 전체를 처리한 뒤에 검사하는 것이라고 대비해 설명한다. 같은 MySQL 안에서도 NDB 저장 엔진은 NO ACTION을 커밋 시점까지 미뤄지는 검사로 해석한다.
    • 연쇄 동작에는 한계가 있다. CASCADE가 다시 CASCADE를 부르는 연쇄는 15단계까지만 허용된다. 자기 자신을 참조하는 테이블에서 ON UPDATE CASCADE와 ON UPDATE SET NULL은 RESTRICT처럼 동작한다. 또 연쇄 동작으로 바뀐 행에는 트리거가 실행되지 않는다.
    • 검사를 끌 수 있다. 시스템 변수 foreign_key_checks는 기본적으로 켜져 있고, 세션 단위로 끌 수 있다. 다시 켜도 그동안 들어온 데이터를 훑어 검사하지는 않는다. 대량 적재를 위해 잠시 껐다가 켜면, 그 사이 들어간 깨진 참조는 그대로 남는다.
    참조되는 쪽 열이 UNIQUE가 아니어도 InnoDB는 외래 키를 허용해 왔다. 표준 SQL에는 없는 확장이다. MySQL 8.4 문서는 이 사용법을 하위 호환을 위해 남겨 두었지만 deprecated로 표시했고, 시스템 변수 restrict_fk_on_non_standard_key를 조정해야만 허용된다고 밝힌다. 외래 키는 기본 키나 UNIQUE NOT NULL 키만 참조하도록 설계한다. 왜 그래야 하는지는 조인 절에서 행 수를 계산하며 다시 확인한다.

    참여도: 반드시 참여하는가, 참여하지 않아도 되는가

    02회에서 까마귀발 기호를 읽을 때, 선 끝의 기호가 두 개씩 붙는다고 했다. 엔티티에 가까운 바깥쪽 기호는 최대 몇 개인지(하나 또는 여럿), 선 안쪽 기호는 최소 몇 개인지(0 또는 1)를 나타낸다. 이 최소 쪽 정보가 참여도(participation)다. 관계에 반드시 참여해야 하는 경우를 필수 참여(mandatory participation, 전체 참여 total participation이라고도 한다), 참여하지 않아도 되는 경우를 선택 참여(optional participation, 부분 참여 partial participation)라고 한다.

    참여도는 관계의 양쪽에 따로 있다. 회원과 주문을 다시 보자. 주문 쪽에서 보면 "모든 주문은 회원 한 명이 한 것이다". 회원 없이 존재하는 주문은 없다. 그러므로 주문은 이 관계에 필수 참여한다. 회원 쪽에서 보면 "회원은 주문을 하지 않았을 수도 있다". 막 가입한 회원은 주문이 0개다. 그러므로 회원은 이 관계에 선택 참여한다. 까마귀발로는 회원 쪽 선 끝에 "정확히 하나"를 뜻하는 ||, 주문 쪽 선 끝에 "0개 이상"을 뜻하는 o<를 그린다. 기호가 붙는 위치를 헷갈리기 쉬운데, 선 끝의 기호는 "반대편 엔티티 하나에 대해 이쪽 엔티티가 몇 개 대응하는가"를 말한다. 회원 쪽 끝의 ||는 주문 하나에 회원이 정확히 하나라는 뜻이다.

              주문 하나에 회원은                회원 하나에 주문은
          최소 1, 최대 1                    최소 0, 최대 N
                 |                                |
 +--------+      v                                v      +--------+
 | member |  ||------------------------------------o<    | orders |
 +--------+                                              +--------+

 읽는 법: "회원은 주문을 0개 이상 한다."   "주문은 반드시 회원 한 명이 한다."
          회원 = 선택 참여                  주문 = 필수 참여

    참여도를 정할 때도 02회에서 카디널리티를 정할 때와 같은 원칙을 쓴다. 지금 들어 있는 샘플 데이터가 아니라 업무 규칙으로 정한다. 현재 모든 상품이 카테고리를 갖고 있더라도, "카테고리 없이 상품을 먼저 등록하고 나중에 분류한다"는 업무가 있다면 상품은 카테고리 관계에 선택 참여한다. 그리고 시간 축을 함께 본다. 필수 참여에는 "만들어지는 순간부터 필수"와 "언젠가는 반드시 생기는 것"이 섞여 있기 쉬운데, 데이터베이스의 선언적 제약이 표현할 수 있는 것은 앞의 것뿐이다. 이 차이가 다음 절의 핵심이다.

    비유입학 서류와 졸업 요건

    학생은 반드시 학과에 소속되어 입학한다. 입학 서류에 학과 칸이 비어 있으면 서류가 접수되지 않는다. 이것은 "만들어지는 순간부터 필수"다. 한편 학생은 졸업할 때까지 논문을 반드시 하나 써야 한다. 하지만 입학 서류를 받으면서 논문을 요구할 수는 없다. 이것은 "언젠가는 반드시"다. 입학 서류 접수 창구가 할 수 있는 검사는 앞의 것뿐이고, 뒤의 것은 졸업 심사라는 별도의 절차가 지킨다. 데이터베이스의 NOT NULL과 외래 키는 접수 창구에 해당한다. 비유가 깨지는 지점도 있다. 졸업 심사에는 정해진 시점이 있지만, 데이터베이스에서 "언젠가"를 지키는 절차는 설계자가 시점과 위치를 직접 정해야 하고, 정하지 않으면 아무도 지키지 않는다.

    참여도를 테이블로 옮기기: NOT NULL로 되는 것과 되지 않는 것

    일대다 관계에서 외래 키는 N 쪽(자식)에 있다. 그 이유는 뒤에서 자세히 따지고, 여기서는 이 사실을 전제로 참여도를 옮겨 보자. 참여도는 양쪽에 하나씩 있으니 경우는 네 가지다.

    참여하는 쪽참여도업무 규칙의 예테이블에서의 표현
    자식(N 쪽)필수주문은 반드시 회원이 한다외래 키 열 NOT NULL + 외래 키 제약
    자식(N 쪽)선택상품은 카테고리가 없을 수 있다외래 키 열 NULL 허용 + 외래 키 제약
    부모(1 쪽)선택회원은 주문이 없을 수 있다할 일 없음(기본 상태)
    부모(1 쪽)필수주문은 주문 상품이 최소 하나 있어야 한다선언적 제약으로 표현할 수 없다

    자식 쪽 참여도는 자식 행 자신의 열 하나로 결정된다. 주문 행이 회원을 반드시 가져야 한다는 것은 "주문 행의 member_id 칸이 비어 있으면 안 된다"는 것과 정확히 같다. 이 칸이 비어 있지 않고(NOT NULL), 채워진 값이 실제로 존재하는 회원을 가리키면(외래 키 제약) 규칙은 완전히 지켜진다. 검사에 필요한 정보가 모두 그 행 안에 있고, 행을 넣는 순간 판정할 수 있다. 그래서 NOT NULL과 외래 키라는 선언적 제약(declarative constraint)으로 충분하다.

    부모 쪽 필수 참여는 다르다. "모든 주문은 주문 상품이 최소 하나 있어야 한다"는 규칙은 주문 행 하나를 아무리 들여다봐도 판정할 수 없다. 주문 상품 테이블에서 이 주문을 가리키는 행의 개수를 세어 봐야 한다. 행 하나의 칸으로는 표현할 수 없고, 다른 테이블의 집계에 대한 조건이다. MySQL의 CHECK 제약으로도 안 된다. MySQL은 8.0.16부터 CHECK 제약을 실제로 검사하지만, 문서에 따르면 CHECK 조건식에는 서브쿼리를 쓸 수 없고 저장 함수도 쓸 수 없다. 다른 테이블을 들여다볼 방법이 막혀 있는 것이다.

    설령 표현할 수 있다고 해도 시점의 문제가 남는다. 주문과 주문 상품을 저장하는 순서를 생각해 보자. 주문 상품의 order_id가 외래 키이므로 주문 행이 먼저 있어야 주문 상품 행을 넣을 수 있다. 그런데 주문 행을 넣는 순간에는 주문 상품이 0개다. "주문 상품이 최소 하나"라는 규칙을 행마다 즉시 검사한다면 주문 행 자체가 들어갈 수 없다. 앞에서 확인한 대로 InnoDB는 외래 키를 행 단위로 즉시 검사하고 커밋 시점까지 미루지 않는다. 그러니 "주문을 넣고, 주문 상품을 넣고, 커밋할 때 함께 검사하라"는 방식도 InnoDB 외래 키로는 쓸 수 없다.

    그래서 부모 쪽 필수 참여는 애플리케이션이 트랜잭션 경계 안에서 지킨다. 주문을 만드는 서비스 메서드가 주문 상품 목록이 비어 있으면 예외를 던지고, 주문과 주문 상품을 한 트랜잭션에서 저장하며, 주문 상품을 지우는 기능이 마지막 하나를 지우려 하면 거부한다. 규칙을 지키는 코드가 한곳에 모여 있어야 한다는 점이 중요하다. 주문 상품을 지우는 경로가 셋인데 그중 하나만 검사하면 규칙은 지켜지지 않는다. JPA를 쓴다면 주문 엔티티가 주문 상품 컬렉션을 관리하고 외부에서는 주문을 통해서만 주문 상품을 추가·삭제하게 하는 설계가 이 규칙을 한곳에 모으는 방법이다.

    양쪽이 모두 "만드는 순간부터 필수"라면

    양쪽 참여를 모두 선언적 제약으로 강제하려는 시도도 있다. 예를 들어 주문 테이블에 first_item_id NOT NULL 열을 두고 주문 상품을 가리키게 하고, 주문 상품은 order_id NOT NULL로 주문을 가리키게 하는 것이다. 이러면 순환 참조가 생긴다. 주문을 넣으려면 주문 상품이 있어야 하고, 주문 상품을 넣으려면 주문이 있어야 한다. 검사가 즉시 일어나는 InnoDB에서는 둘 중 무엇도 먼저 넣을 수 없다. 이 막다른 길을 빠져나가려면 한쪽을 NULL 허용으로 바꾸거나 foreign_key_checks를 끄는 수밖에 없는데, 앞의 것은 결국 그 방향의 필수를 포기하는 것이고 뒤의 것은 무결성 검사 자체를 포기하는 것이다. 개념 모델에서 양쪽 다 필수인 관계를 만났다면, 한쪽은 선언적 제약으로, 다른 한쪽은 애플리케이션 규칙으로 지키겠다고 처음부터 나눠서 결정하는 것이 현실적이다.

    "언젠가 필수"는 NULL 허용이다

    시간 축이 끼어드는 경우도 같은 방식으로 판단한다. 주문은 결국 배송 정보를 갖지만, 배송 정보는 결제가 끝난 뒤에야 만들어진다고 하자. 주문 행을 넣는 순간에 배송이 없다면, 주문 쪽에서 배송을 가리키는 열은 NOT NULL일 수 없다. 개념 모델에서 "주문은 배송을 반드시 갖는다"고 그렸더라도, 그것이 "만들어지는 순간부터"가 아니라면 테이블에서는 NULL 허용이 맞다. 이런 관계에서 외래 키를 어느 쪽에 두면 NULL을 없앨 수 있는지, 곧 나중에 생기는 쪽이 먼저 생긴 쪽을 가리키게 하는 설계는 일대일 관계를 다루는 05회에서 본다.

    선택 참여를 NULL 없이 표현하는 두 가지 대안

    자식 쪽 선택 참여를 NULL 허용 외래 키로 표현하는 것이 가장 단순하지만, 대안이 둘 있다. 첫째는 "미분류" 같은 기본 행을 부모 테이블에 하나 만들어 두고 외래 키를 NOT NULL로 두는 것이다. 질의에서 NULL을 다룰 일이 없어지는 대신, "미분류"가 진짜 카테고리처럼 집계와 화면에 섞여 나오고 그 행의 키 값이 코드 곳곳에 상수로 박히게 된다. 둘째는 관계 자체를 별도 테이블로 빼는 것이다. product_category(product_id PK, category_id NOT NULL)처럼 상품이 카테고리를 가질 때만 행이 생긴다. NULL은 사라지지만 상품의 카테고리를 알려면 항상 조인이 하나 더 필요하다. 세 방법 모두 쓰이며, 판단 기준은 그 관계가 얼마나 자주 비어 있는가, 그리고 비어 있음이 업무적으로 의미 있는 상태인가다. 기본값은 NULL 허용 외래 키로 두고, 위 두 대안은 그 문제점이 실제로 드러날 때 검토한다.

    선택 참여가 질의에 남기는 흔적: INNER JOIN, LEFT JOIN, NOT IN

    참여도는 테이블 정의에서 끝나지 않고 질의를 쓰는 방식까지 정한다. 예제 데이터를 넣고 직접 확인해 보자. 회원은 세 명이고, kim은 주문이 두 건, lee는 한 건, park은 0건이다. 상품 세 개 중 하나는 카테고리가 없다.

    INSERT INTO member (member_id, name) VALUES (1, 'kim'), (2, 'lee'), (3, 'park');
INSERT INTO orders (order_id, member_id, total_amount, ordered_at) VALUES
    (10, 1, 30000, '2026-11-01 10:00:00'),
    (11, 1, 15000, '2026-11-02 11:00:00'),
    (12, 2, 20000, '2026-11-03 12:00:00');

-- category, product 테이블의 DDL은 생략: product.category_id는 NULL 허용 외래 키
INSERT INTO category (category_id, name) VALUES (1, 'book'), (2, 'food'), (3, 'toy');
INSERT INTO product (product_id, category_id, name) VALUES
    (1, 1, 'novel'), (2, 2, 'apple'), (3, NULL, 'mystery box');

FROM product p JOIN category c ON c.category_id = p.category_id;

    부모 쪽 선택 참여도 질의에 흔적을 남긴다. 회원별 주문 수를 구할 때 주문이 없는 회원까지 0으로 나오게 하려면 member에서 orders로 LEFT JOIN해야 한다. 이때 COUNT(*)를 쓰면 틀린다. 외부 조인은 짝이 없는 회원에 대해서도 주문 쪽 열이 모두 NULL인 행 하나를 만들어 내고, COUNT(*)는 그 행을 센다. 주문 쪽의 NOT NULL 열을 세는 COUNT(o.order_id)를 써야 NULL이 빠져 0이 나온다.

FROM member m LEFT JOIN orders o ON o.member_id = m.member_id
GROUP BY m.member_id;

    SELECT name FROM category
WHERE category_id NOT IN (SELECT category_id FROM product);

    일대다 관계의 외래 키 위치 1: 왜 N 쪽인가

    이제 지금까지 전제로 둔 사실, "일대다 관계에서 외래 키는 N 쪽에 둔다"를 따져 보자. 규칙으로 외우기보다, 1 쪽에 두려고 시도해 보고 어디서 막히는지 보는 편이 원리를 이해하기 쉽다. 회원 한 명은 주문을 여러 건 할 수 있고 주문 한 건은 회원 한 명에게 속한다. 1 쪽은 회원, N 쪽은 주문이다. 회원 테이블에 주문을 가리키는 열을 두는 방법은 세 가지를 생각할 수 있다.

    시도 1: 회원 테이블에 order_id 열 하나. kim의 행에 order_id = 10을 적었다. 그런데 kim이 두 번째 주문 11번을 했다. 칸 하나에는 값 하나만 들어간다. 11을 적으려면 kim의 행을 하나 더 만들어야 한다. 그러면 member_id = 1인 행이 둘이 되어 member_id는 더 이상 기본 키가 될 수 없다. 기본 키를 (member_id, order_id)로 바꾸면 행은 구별되지만, kim의 이름과 이메일과 주소가 주문 수만큼 복사된다. 01회에서 본 이상 현상이 그대로 돌아온다. 이름을 바꾸려면 여러 행을 고쳐야 하고(갱신 이상), 주문이 없는 회원은 order_id를 NULL로 둬야 하는데 그 열이 기본 키의 일부라 NULL이 될 수 없으며(삽입 이상), 마지막 주문을 지우면 회원 정보까지 사라진다(삭제 이상). 무엇보다 이 테이블은 더 이상 "회원" 테이블이 아니라 "회원과 주문의 짝" 테이블이 되었다.

    시도 2: 한 칸에 목록을 넣는다. order_ids = '10,11'처럼 문자열로 적는 방법이다. 행은 하나로 유지되지만, 이 칸은 값 하나가 아니라 값의 목록을 담는다. 제1정규형(07회)이 금지하는 바로 그 형태다. 외래 키 제약을 걸 수 없으므로 존재하지 않는 주문 번호가 섞여도 막을 수 없다. "주문 11번은 누구의 주문인가"를 찾으려면 모든 회원 행의 문자열을 잘라 봐야 하고, 인덱스는 쓸 수 없다. 주문 하나를 지울 때마다 문자열을 다시 조립해야 하는데, 두 트랜잭션이 동시에 같은 회원의 문자열을 고치면 한쪽의 변경이 덮어써질 수 있다.

    시도 3: 열을 여러 개 만든다. order_id1, order_id2, order_id3처럼 반복되는 열을 두는 방법이다. 각 칸에는 값이 하나씩이니 외래 키 제약은 열마다 걸 수 있다. 하지만 네 번째 주문이 오면 테이블 구조를 바꿔야 한다. 업무 규칙의 "N"이 상한이 없는 "여럿"인데 스키마가 상한을 정해 버린 것이다. 주문이 하나뿐인 회원은 두 칸이 NULL이고, "주문 11번의 주인"을 찾는 쿼리는 WHERE order_id1 = 11 OR order_id2 = 11 OR order_id3 = 11이 된다. 열을 하나 늘릴 때마다 이런 쿼리를 모두 고쳐야 한다.

    올바른 위치: 주문 테이블에 member_id. 주문 한 건의 주인은 정확히 한 명이다. 그러니 주문 행에는 회원 번호를 적을 칸이 하나만 있으면 되고, 그 칸에는 항상 값이 하나만 들어간다. 회원의 주문이 몇 건이든 회원 테이블은 바뀌지 않는다. 주문 행이 늘어날 뿐이다. 회원 정보는 회원 행에 한 번만 있다. "kim의 주문"은 WHERE member_id = 1로, "주문 11번의 주인"은 주문 행을 읽으면 바로 나온다. 외래 키 제약과 인덱스도 자연스럽게 붙는다.

    일대다 관계의 외래 키 위치 2: 방향, 시간, 대표 자식

    외래 키가 N 쪽에 놓인다는 원칙은 단순하지만, 실제 설계에서는 이 원칙을 흐리게 만드는 질문이 세 가지 따라온다. 관계에 방향이 있는가, N인지 1인지를 언제 기준으로 판단하는가, 그리고 여러 자식 가운데 하나를 특별히 가리켜야 할 때는 어떻게 하는가.

    일대다와 다대일은 같은 관계다

    "회원과 주문은 일대다"와 "주문과 회원은 다대일"은 같은 관계를 양 끝에서 읽은 것이다. 테이블에는 외래 키 하나, orders.member_id만 있다. 데이터베이스의 관계에는 방향이 없다. 조인 조건 o.member_id = m.member_id는 회원에서 주문을 찾을 때도, 주문에서 회원을 찾을 때도 똑같이 쓰인다. 어느 쪽에서 출발할지는 질의가 정하고, 외래 키의 위치와는 상관이 없다. "회원 화면에서 주문 목록을 자주 보니 회원 쪽에 무언가를 둬야 한다"는 생각은 조회 패턴과 관계 표현을 섞은 것이다. 조회 패턴은 인덱스로 해결하고, 관계 표현은 카디널리티로 정한다.

    방향은 객체 세계의 개념이다. 자바 객체는 참조를 따라 한쪽으로만 이동할 수 있으므로, Order가 Member를 참조하는지, Member가 List를 갖는지, 둘 다인지를 정해야 한다. JPA 기본편에서 본 연관관계의 주인(owning side)은 이 두 세계를 잇는 약속이다. Hibernate ORM 6.6 User Guide는 양방향 연관관계에는 소유 측이 하나 있어야 하고 그것이 자식 쪽이며, 반대쪽은 mappedBy로 표시되는 역방향(inverse side)이라고 설명한다. 자식 쪽이 주인인 이유는 이 회차의 결론 그대로다. 외래 키 열이 자식 테이블에 있으니, 그 열의 값을 정하는 쪽도 자식 엔티티의 @ManyToOne 필드여야 SQL이 단순해진다.

    객체에서는 Member에만 @OneToMany 컬렉션을 두는 단방향 매핑도 가능하다. 같은 가이드는 이 경우 Hibernate가 기본적으로 두 엔티티 사이에 연결 테이블(link table)을 쓴다고 설명하고, 단방향 연관관계는 자식을 제거할 때 효율적이지 않다고 지적한다. 예제에서는 컬렉션에서 하나를 빼고 플러시하자 연결 테이블의 해당 부모 행을 모두 지운 뒤 남은 것을 다시 넣는 SQL이 나간다. 테이블 설계의 관점에서 보면 이것은 일대다 관계를 다대다 구조로 표현한 셈이다. @JoinColumn을 붙여 연결 테이블 없이 매핑하더라도 외래 키는 여전히 주문 테이블에 있다. 컬렉션은 회원 객체에 있는데 그 변화를 기록할 열은 다른 테이블에 있으므로, 회원의 컬렉션을 바꾸면 주문 테이블의 행을 고쳐야 한다. 테이블을 먼저 설계하고 객체 매핑을 거기에 맞추면 이런 어긋남이 생기지 않는다.

    자기 자신과의 일대다

    한 테이블 안에서 일대다가 생기기도 한다. 직원과 그 직원의 상사는 둘 다 직원이다. 상사 한 명에게 부하가 여럿이고 직원 한 명의 직속 상사는 하나이므로, 같은 원칙에 따라 "상사가 하나뿐인 쪽", 곧 각 직원 행에 manager_id를 둔다. 외래 키가 자기 테이블의 기본 키를 가리키는 자기 참조(self-referencing) 외래 키다. 여기서 참여도가 흥미롭다. "모든 직원은 상사가 있다"는 규칙은 거의 맞지만 최고 경영자에게는 상사가 없다. 한 명의 예외 때문에 manager_id는 NULL을 허용해야 한다. 업무 규칙의 예외가 곧 선택 참여라는 점을 보여 주는 예다. 앞에서 확인한 대로 InnoDB에서 자기 참조 외래 키의 ON UPDATE CASCADE는 RESTRICT처럼 동작한다.

    N인지 1인지는 시간 축으로 판단한다

    카디널리티를 잘못 읽어 외래 키 위치가 틀리면 나중에 고치는 비용이 크다. 회원과 배송지를 예로 들자. 처음 요구 사항이 "회원은 배송지를 하나 등록한다"였다면 배송지 열을 회원 테이블에 두거나, 별도 배송지 테이블을 두고 회원이 그것을 가리키게 할 수 있다. 1년 뒤 "배송지를 여러 개 저장해 두고 골라 쓴다"는 요구가 오면 관계가 일대다로 바뀌고, 외래 키는 배송지 테이블의 member_id로 옮겨 가야 한다. 열을 추가하고, 기존 데이터를 새 구조로 옮기고, 옛 열을 쓰던 모든 질의와 코드를 고치고, 옛 열을 지우는 작업이 이어진다. 01회에서 본 대로 큰 테이블에서 이런 구조 변경은 그 자체가 운영 작업이다.

    그래서 카디널리티를 정할 때는 "지금 하나인가"가 아니라 "한 시점에 하나인가, 평생 하나인가", "과거 값을 기억해야 하는가"를 묻는다. 회원의 현재 등급은 한 시점에 하나지만, 등급이 바뀐 이력을 기억해야 한다면 회원과 등급 이력은 일대다다. 상품의 가격도 현재 가격만 필요하면 상품의 속성이지만, 주문 당시 가격을 재현해야 한다면 가격 이력이나 주문 상품의 가격 열이 필요하다. 이력 요구는 거의 언제나 일대일이나 속성을 일대다로 바꾼다. 업무 담당자에게 "이 값이 바뀌면 예전 값은 버려도 됩니까"라고 물어보는 것이 카디널리티를 확인하는 가장 빠른 방법이다.

    여러 자식 중 하나를 대표로 가리킬 때

    배송지가 여러 개가 된 뒤에도 "기본 배송지"는 하나여야 한다. 이때 같은 두 테이블 사이에 관계가 두 개 생긴다. 하나는 "회원은 배송지를 여러 개 가진다"는 일대다이고, 다른 하나는 "회원은 기본 배송지 하나를 지정한다"는 관계다. 두 번째 관계를 표현하는 흔한 방법은 회원 테이블에 main_address_id를 두는 것이다. 그러면 두 테이블이 서로를 가리키는 순환 참조가 된다. 앞에서 본 대로 InnoDB는 검사를 즉시 하므로 양쪽이 모두 NOT NULL이면 아무것도 넣을 수 없다. 회원이 먼저 생기고 배송지는 나중에 생기므로 main_address_id는 NULL을 허용해야 한다. 저장 순서는 회원 삽입(기본 배송지 NULL), 배송지 삽입, 회원의 main_address_id 갱신이 된다.

    더 미묘한 문제는 main_address_id가 다른 회원의 배송지를 가리킬 수 있다는 것이다. 외래 키 member.main_address_id → address.address_id는 "그런 배송지가 존재한다"만 보장하고 "그 배송지가 이 회원의 것이다"는 보장하지 않는다. 복합 외래 키로 이 규칙까지 선언할 수 있다. 배송지 테이블에 (member_id, address_id) UNIQUE 제약을 두고, 회원 테이블의 (member_id, main_address_id)가 그 쌍을 참조하게 한다.

    CREATE TABLE address (
    address_id BIGINT       NOT NULL AUTO_INCREMENT,
    member_id  BIGINT       NOT NULL,
    zipcode    CHAR(5)      NOT NULL,
    line1      VARCHAR(200) NOT NULL,
    PRIMARY KEY (address_id),
    UNIQUE KEY uk_address_member (member_id, address_id),
    CONSTRAINT fk_address_member
        FOREIGN KEY (member_id) REFERENCES member (member_id)
) ENGINE = InnoDB;

ALTER TABLE member
    ADD COLUMN main_address_id BIGINT NULL,
    ADD CONSTRAINT fk_member_main_address
        FOREIGN KEY (member_id, main_address_id)
        REFERENCES address (member_id, address_id);

    address_id만으로도 이미 유일하므로 (member_id, address_id) UNIQUE는 데이터 관점에서 새로 막는 것이 없다. 이 제약의 역할은 외래 키가 참조할 수 있는 유일한 쌍을 만들어 주는 것이다. 이제 회원 1의 main_address_id에 회원 2의 배송지 번호를 넣으면 (1, 그 번호) 쌍이 배송지 테이블에 없으므로 거부된다. 그리고 main_address_id가 NULL인 동안에는 이 복합 외래 키가 검사되지 않는다. 앞에서 확인한 MATCH SIMPLE 의미, 곧 외래 키 열 중 하나라도 NULL이면 부모와 대조하지 않는 규칙 덕분이다. 기본 배송지로 지정된 배송지를 지우려 하면 참조 동작이 기본값(NO ACTION, 곧 RESTRICT)이므로 거부되고, 기본 배송지를 먼저 바꿔야 한다.

    순환 참조를 피하는 다른 방법도 있다. 배송지 테이블에 기본 여부를 표시하는 열을 두는 것이다. 다만 "회원마다 기본 배송지는 최대 하나"를 지키려면 장치가 필요하다. MySQL의 UNIQUE 인덱스는 NULL을 허용하는 열에서 NULL 값을 여러 개 허용하므로, 기본 배송지면 1, 아니면 NULL을 넣는 열 main_flag를 두고 (member_id, main_flag)에 UNIQUE를 걸면 회원마다 1은 하나만 들어간다. 이 방법은 순환 참조가 없지만, 기본 배송지를 바꿀 때 옛 행을 NULL로, 새 행을 1로 두 행을 고쳐야 한다. 어느 쪽이든 "대표 자식"은 관계가 하나 더 있다는 사실을 인정하고 그것을 별도로 표현하는 문제다.

    한 층 아래: InnoDB가 외래 키를 검사하는 방법과 잠금

    외래 키 검사는 공짜가 아니다. 주문 행 하나를 넣을 때 InnoDB가 하는 일을 따라가 보자. 먼저 주문의 클러스터형 인덱스(기본 키 B+Tree)에 행을 넣을 자리를 찾는다. 외래 키 검사를 위해 회원 테이블의 기본 키 인덱스에서 member_id = 1인 레코드를 찾는다. 기본 키 탐색이므로 B+Tree의 높이만큼 페이지를 내려가면 된다. 03회에서 본 대로 페이지가 버퍼 풀에 있으면 디스크를 읽지 않는다. 그리고 주문 테이블의 member_id 보조 인덱스에도 항목을 넣는다. 외래 키가 없을 때와 비교하면 부모 인덱스 탐색 한 번이 더해진다.

    탐색만 하는 것이 아니다. MySQL 문서는 외래 키 제약이 있는 테이블에서 제약 조건을 검사해야 하는 삽입·갱신·삭제는 검사를 위해 들여다보는 레코드에 공유 레코드 잠금(shared record-level lock)을 건다고 밝힌다. 제약 검사가 실패한 경우에도 건다. 주문을 넣는 트랜잭션은 회원 1번 레코드에 공유 잠금(S 잠금)을 잡고, 이 잠금은 트랜잭션이 끝날 때까지 유지된다. 커밋하지 않은 채로 performance_schema.data_locks를 보면 이 잠금이 그대로 보인다.

    BEGIN;
INSERT INTO orders (member_id, total_amount, ordered_at) VALUES (1, 30000, '2026-11-19 10:00:00');
SELECT OBJECT_NAME, INDEX_NAME, LOCK_TYPE, LOCK_MODE, LOCK_DATA
FROM performance_schema.data_locks
WHERE OBJECT_SCHEMA = DATABASE() AND THREAD_ID = PS_CURRENT_THREAD_ID()
ORDER BY OBJECT_NAME, LOCK_TYPE;

+-------------+------------+-----------+---------------+-----------+
| OBJECT_NAME | INDEX_NAME | LOCK_TYPE | LOCK_MODE     | LOCK_DATA |
+-------------+------------+-----------+---------------+-----------+
| member      | PRIMARY    | RECORD    | S,REC_NOT_GAP | 1         |
| member      | NULL       | TABLE     | IS            | NULL      |
| orders      | NULL       | TABLE     | IX            | NULL      |
+-------------+------------+-----------+---------------+-----------+

    회원 테이블 기본 키의 member_id = 1 레코드에 레코드 하나만 잠그는(간격은 잠그지 않는) S 잠금, S,REC_NOT_GAP이 걸렸다. 왜 이런 잠금이 필요한지는 잠금이 없다고 가정하면 보인다.

    T1이 회원 1번 레코드에 S 잠금을 잡고 있으면 이 경쟁이 막힌다. 삭제하려는 T2는 그 레코드에 배타 잠금(X 잠금)이 필요하고, X 잠금은 다른 트랜잭션의 S 잠금과 호환되지 않으므로 T1이 끝날 때까지 기다린다. T1이 커밋하면 T2는 잠금을 얻은 뒤 주문 인덱스에서 회원 1번을 가리키는 행을 찾고, 이제는 T1의 주문이 있으므로 RESTRICT에 따라 삭제가 거부된다. T1이 롤백했다면 주문이 없으므로 삭제가 성공한다. 어느 쪽이든 고아 주문은 생기지 않는다. 부모를 지울 때 자식 인덱스를 찾아보는 단계에서 자식 쪽 member_id 인덱스가 필요하다는 점도 여기서 보인다. 인덱스가 없다면 이 확인이 주문 테이블 전체 탐색이 되는데, MySQL이 외래 키 열에 인덱스를 요구하고 없으면 만들어 주는 이유가 이것이다.

    이 잠금은 부작용도 만든다. S 잠금은 레코드 단위이므로, 회원의 이름을 바꾸는 UPDATE member SET name = ... WHERE member_id = 1도 그 레코드에 X 잠금이 필요해 주문 삽입 트랜잭션이 끝날 때까지 기다린다. 이름 변경은 참조 무결성과 아무 관계가 없지만, 잠금은 열 단위가 아니라 레코드 단위이기 때문이다. 주문 트랜잭션이 결제 대행사 호출처럼 오래 걸리는 작업을 안에 품고 있다면, 그동안 그 회원의 정보 수정은 모두 멈춘다.

    더 나쁜 경우는 교착 상태(deadlock)다. 회원 테이블에 주문 수를 세는 order_count 열이 있고, 주문을 넣은 뒤 그 값을 1 올린다고 하자. 같은 회원에 대해 두 트랜잭션이 동시에 이 작업을 하면 다음 순서가 가능하다.

    시간  T1                                       T2
 |   INSERT INTO orders (... member_id=1)
 |     -> member 1 레코드에 S 잠금 획득
 |                                            INSERT INTO orders (... member_id=1)
 |                                              -> member 1 레코드에 S 잠금 획득 (S끼리는 호환)
 |   UPDATE member SET order_count=order_count+1
 |     WHERE member_id=1
 |     -> X 잠금 요청: T2의 S 잠금 때문에 대기
 |                                            UPDATE member SET order_count=order_count+1
 |                                              WHERE member_id=1
 |                                              -> X 잠금 요청: T1의 S 잠금 때문에 대기
 v   서로가 서로를 기다린다 = 교착 상태. InnoDB가 감지해 한쪽 트랜잭션을 롤백한다.

    두 트랜잭션은 각자 S 잠금을 가진 채 상대의 S 잠금이 풀리기를 기다리며 X 잠금을 요청한다. 어느 쪽도 먼저 놓지 않으므로 교착 상태다. MySQL 8.4.13에서 회원 테이블에 order_count 열을 더하고 두 세션으로 위 순서를 그대로 재현하자, 나중에 UPDATE를 보낸 T2가 ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction을 받고 롤백되었고 T1은 커밋되었다. 해법은 잠금을 얻는 순서를 바꾸는 것이다. 부모의 order_count를 먼저 갱신해 X 잠금을 먼저 얻고 나서 주문을 넣으면, 두 번째 트랜잭션은 처음부터 X 잠금 대기에 걸려 줄을 서게 되고 교착은 생기지 않는다. 또는 부모에 집계 열을 두지 않고 필요할 때 COUNT로 구하는 것도 방법이다. 이 문제는 외래 키 설계가 단순히 "선을 옮기는 일"이 아니라 동시성 동작까지 정한다는 것을 보여 준다.

    두 트랜잭션이 자식 행 삽입으로 같은 부모 레코드에 S 잠금을 잡은 뒤, 각자 부모를 갱신하려고 X 잠금을 요청하면서 서로를 기다리게 되는 순서를 보여 준다. |         2 | lee  |       12 |        20000 |
+-----------+------+----------+--------------+

    회원은 세 명인데 결과는 세 행이고, 그 세 행은 회원 수가 아니라 주문 수를 따른다. kim은 두 번 나오고 park은 나오지 않는다. 조인 결과의 한 행은 "조인 조건을 만족하는 회원과 주문의 짝 하나"이기 때문이다. 이것이 흔히 "뻥튀기"라고 부르는 현상의 정체다. 데이터베이스가 무언가를 잘못한 것이 아니다. 조인 결과의 행 단위가 회원이 아니라 "회원-주문 짝", 실제로는 주문이 된 것이다.

    일대다 조인의 결과 행 수는 다음처럼 계산할 수 있다. 회원 i의 주문 수를 ki라고 하자.

    • 회원에서 주문으로 내부 조인: 결과 행 수는 ki의 합이다. 외래 키가 NOT NULL이고 제약이 지켜진다면 이는 주문 테이블의 행 수와 같다. 예제에서는 2 + 1 + 0 = 3이다.
    • 회원에서 주문으로 왼쪽 외부 조인: 결과 행 수는 max(1, ki)의 합이다. 주문이 없는 회원도 한 행으로 남는다. 예제에서는 2 + 1 + 1 = 4다.
    • 주문에서 회원으로 조인(다대일 방향): 결과 행 수는 주문 수 그대로다. 주문 하나가 짝지을 수 있는 회원은 최대 하나이기 때문이다.

    마지막 항목이 성립하는 근거는 참조되는 쪽 키의 유일성이다. 회원의 member_id가 기본 키이므로 어떤 주문의 member_id 값도 회원 테이블에서 최대 한 행과만 일치한다. 그래서 다대일 방향의 조인은 행을 늘리지 않는다. 앞에서 MySQL 8.4가 UNIQUE가 아닌 키를 참조하는 외래 키를 deprecated로 표시했다고 했다. 참조되는 키가 유일하지 않으면 "자식에서 부모로의 조인은 행을 늘리지 않는다"는 이 보장이 깨진다. 자식 하나가 부모 여러 행과 짝지어질 수 있기 때문이다. 외래 키가 기본 키나 UNIQUE NOT NULL 키를 가리켜야 하는 이유가 여기에 있다.

    부모를 고르는 질의는 조인이 아니라 EXISTS

    "주문을 한 적이 있는 회원 목록"을 구하려고 회원과 주문을 조인하면 kim이 두 번 나온다. 원하는 것은 회원 목록인데 결과의 행 단위가 주문이 되었기 때문이다. DISTINCT를 붙이면 중복은 사라지지만, 데이터베이스는 일단 짝을 모두 만든 다음 중복을 제거하는 일을 추가로 한다. 질문의 형태 그대로 쓰면 "주문이 존재하는 회원"이므로 EXISTS가 맞다. EXISTS는 각 회원에 대해 짝이 하나라도 있는지만 묻고, 결과의 행 단위는 처음부터 회원이다. 이렇게 한쪽 테이블의 행을 다른 쪽 짝의 존재 여부로 거르는 연산을 세미 조인(semi-join)이라고 한다.

    SELECT m.member_id, m.name
FROM member m
WHERE EXISTS (SELECT 1 FROM orders o WHERE o.member_id = m.member_id);

+-----------+------+
| member_id | name |
+-----------+------+
|         1 | kim  |
|         2 | lee  |
+-----------+------+

    부모의 값을 자식 단위에서 합하면

    행이 늘어나는 것 자체는 문제가 아니다. 문제는 늘어난 행 위에서 부모의 값을 집계할 때 생긴다. 주문 상품 테이블을 더하자. 주문 10번에는 상품이 두 개(키보드 10,000원 1개, 마우스 10,000원 2개), 11번에는 하나(모니터 15,000원), 12번에는 두 개(케이블 10,000원, 허브 10,000원)가 있다. 회원별 주문 총액을 구하면서 "어차피 상품 이름도 필요하니" 주문 상품까지 조인했다고 하자.

    SELECT m.member_id, SUM(o.total_amount) AS wrong_total
FROM member m
JOIN orders o      ON o.member_id = m.member_id
JOIN order_item oi ON oi.order_id = o.order_id
GROUP BY m.member_id;

+-----------+-------------+
| member_id | wrong_total |
+-----------+-------------+
|         1 |       75000 |
|         2 |       40000 |
+-----------+-------------+
-- 실제는 1번이 30000 + 15000 = 45000, 2번이 20000

    주문 10번의 total_amount 30,000원은 주문 상품이 두 개라서 두 행에 복사되었고, SUM은 그것을 두 번 더했다. 30,000 × 2 + 15,000 × 1 = 75,000이다. 규칙은 이렇다. 어떤 값은 그 값이 속한 테이블의 행 단위에서만 합할 수 있다. total_amount는 주문 한 건에 하나 있는 값이므로 주문 단위에서 합해야 한다. 주문 상품 단위로 내려간 결과에서 합하면 주문 상품 수만큼 곱해진다. 질의를 쓰기 전에 "결과의 한 행은 무엇인가"를 먼저 말해 보는 습관이 이 실수를 막는다.

    조인과 뻥튀기 2: 일대다 두 개를 한 번에 조인할 때

    더 찾기 어려운 경우는 한 부모에 매달린 일대다 관계 두 개를 한 질의에서 함께 조인할 때다. 결제 테이블을 더하자. 주문 10번은 카드 25,000원과 포인트 5,000원으로 나눠 결제했고, 11번은 카드 15,000원, 12번은 카드 20,000원이다. 주문별로 상품 금액 합계와 결제 금액 합계를 한 번에 구해 둘이 맞는지 대조하는 쿼리를 썼다.

    SELECT o.order_id,
       SUM(oi.price * oi.quantity) AS item_total,
       SUM(p.amount)               AS paid_total,
       COUNT(*)                    AS row_cnt
FROM orders o
JOIN order_item oi ON oi.order_id = o.order_id
JOIN payment p     ON p.order_id  = o.order_id
GROUP BY o.order_id;

+----------+------------+------------+---------+
| order_id | item_total | paid_total | row_cnt |
+----------+------------+------------+---------+
|       10 |      60000 |      60000 |       4 |
|       11 |      15000 |      15000 |       1 |
|       12 |      20000 |      40000 |       2 |
+----------+------------+------------+---------+

    주문 10번은 둘 다 실제의 두 배이고, 12번은 결제만 두 배다. 주문 10번의 조인 결과를 펼쳐 보면 이유가 보인다. 주문 상품과 결제 사이에는 아무 관계가 없다. 둘 다 주문만 가리킬 뿐이다. 조인 조건은 "같은 주문에 속한다"뿐이므로, 같은 주문에 속한 주문 상품 2개와 결제 2개가 가능한 모든 조합으로 짝지어진다. 2 × 2 = 4행이다.

    SELECT o.order_id, oi.product_name, oi.price * oi.quantity AS line, p.method, p.amount
FROM orders o
JOIN order_item oi ON oi.order_id = o.order_id
JOIN payment p     ON p.order_id  = o.order_id
WHERE o.order_id = 10
ORDER BY oi.order_item_id, p.payment_id;

+----------+--------------+-------+--------+--------+
| order_id | product_name | line  | method | amount |
+----------+--------------+-------+--------+--------+
|       10 | keyboard     | 10000 | CARD   |  25000 |
|       10 | keyboard     | 10000 | POINT  |   5000 |
|       10 | mouse        | 20000 | CARD   |  25000 |
|       10 | mouse        | 20000 | POINT  |   5000 |
+----------+--------------+-------+--------+--------+

    각 주문 상품 줄은 결제 수만큼, 각 결제는 주문 상품 수만큼 반복된다. 일반화하면 주문 i의 주문 상품 수를 ai, 결제 수를 bi라 할 때 그 주문의 조인 결과는 ai × bi행이고, 상품 금액 합계는 bi배, 결제 합계는 ai배로 부풀려진다. 이 곱셈 구조 때문에 이 버그는 테스트를 잘 통과한다. 개발 중에 넣은 테스트 데이터가 "주문 하나에 결제 하나"였다면 bi = 1이라 상품 합계는 정확하고, 결제가 하나뿐이니 결제 합계는 ai배가 되지만 상품도 하나뿐이었다면 그것마저 정확하다. 분할 결제가 실제로 들어오기 시작한 날부터 보고서의 숫자가 틀리기 시작한다.

    서로 관계없는 두 자식 집합이 같은 부모를 매개로 조인되면 모든 조합(곱집합)이 만들어지고, 각 값이 상대 집합의 크기만큼 반복된다는 것을 보여 준다. A diagram on a white background. In the center top, a box labeled "주문 10". On the left below, two stacked cards labeled "keyboard 10000" and "mouse 20000" under the heading "주문 상품 (2)". On the right below, two stacked cards labeled "CARD 25000" and "POINT 5000" under the heading "결제 (2)". Thin gray lines connect each left card to each right card, forming four crossing lines, and at the bottom a result table with four rows: "keyboard / CARD", "keyboard / POINT", "mouse / CARD", "mouse / POINT", with the header "조인 결과 2 × 2 = 4행". Next to the table, two red badges: "상품 합계 ×2" and "결제 합계 ×2". Flat colors, sans-serif font, minimal style. 같은 부모에 매달린 두 일대다를 함께 조인하면 자식들의 모든 조합이 만들어진다.

    DISTINCT로는 고칠 수 없다

    중복이 문제라면 SUM(DISTINCT ...)를 쓰면 되지 않을까. 그렇지 않다. DISTINCT는 같은 "값"을 하나로 합칠 뿐 같은 "행"에서 온 값인지를 알지 못한다. 주문 12번의 케이블과 허브는 둘 다 10,000원이다. SUM(DISTINCT oi.price * oi.quantity)는 서로 다른 두 상품의 금액 10,000과 10,000을 같은 값으로 보고 하나만 더해, 실제 20,000원을 10,000원으로 만든다. 주문 10번은 금액이 서로 달라서 우연히 맞는다. 개수를 셀 때는 COUNT(DISTINCT oi.order_item_id)처럼 기본 키를 세면 정확하다. 기본 키는 행마다 다르다는 것이 보장되기 때문이다. 그러나 합계에는 이런 장치가 없다.

    SELECT o.order_id, SUM(DISTINCT oi.price * oi.quantity) AS item_total_distinct
FROM orders o
JOIN order_item oi ON oi.order_id = o.order_id
JOIN payment p     ON p.order_id  = o.order_id
GROUP BY o.order_id;

+----------+---------------------+
| order_id | item_total_distinct |
+----------+---------------------+
|       10 |               30000 |
|       11 |               15000 |
|       12 |               10000 |
+----------+---------------------+
-- 12번의 실제 값은 20000

    해법: 각자의 행 단위에서 먼저 집계한다

    올바른 방법은 각 자식을 부모 단위로 먼저 집계해 "주문당 한 행"으로 만든 뒤 조인하는 것이다. 주문 상품 합계는 주문 상품 테이블에서 GROUP BY order_id로, 결제 합계는 결제 테이블에서 GROUP BY order_id로 구한다. 이렇게 만든 두 파생 테이블은 각각 주문당 한 행이므로 주문과 일대일로 조인되고, 행이 늘어나지 않는다.

    SELECT o.order_id, i.item_total, p.paid_total
FROM orders o
JOIN (SELECT order_id, SUM(price * quantity) AS item_total
      FROM order_item GROUP BY order_id) i ON i.order_id = o.order_id
JOIN (SELECT order_id, SUM(amount) AS paid_total
      FROM payment GROUP BY order_id)    p ON p.order_id = o.order_id
ORDER BY o.order_id;

+----------+------------+------------+
| order_id | item_total | paid_total |
+----------+------------+------------+
|       10 |      30000 |      30000 |
|       11 |      15000 |      15000 |
|       12 |      20000 |      20000 |
+----------+------------+------------+

    원칙은 앞 절과 같다. 결과의 한 행이 무엇인지 정하고, 모든 입력을 그 행 단위로 맞춘 다음 조인한다. 상관 서브쿼리를 SELECT 목록에 두는 방식((SELECT SUM(amount) FROM payment p WHERE p.order_id = o.order_id))도 같은 원칙을 따르는 다른 표현이다. 주문이 없는 경우까지 0으로 보여야 한다면 파생 테이블과 LEFT JOIN하고 COALESCE로 NULL을 0으로 바꾼다.

    페이지 나누기와 뻥튀기

    행이 늘어나는 현상은 페이지 나누기도 망가뜨린다. "회원 목록을 두 명씩 페이지로 나눠, 각 회원의 주문과 함께 보여 준다"는 화면을 생각해 보자. 회원과 주문을 외부 조인하고 LIMIT 2를 붙이면 첫 페이지에 회원 두 명이 아니라 kim 한 명만 나온다.

    SELECT m.member_id, m.name, o.order_id
FROM member m LEFT JOIN orders o ON o.member_id = m.member_id
ORDER BY m.member_id, o.order_id
LIMIT 2;

+-----------+------+----------+
| member_id | name | order_id |
+-----------+------+----------+
|         1 | kim  |       10 |
|         1 | kim  |       11 |
+-----------+------+----------+

    LIMIT은 회원이 아니라 조인 결과의 행에 적용되기 때문이다. kim의 주문이 세 건이었다면 kim의 주문 목록이 첫 페이지와 둘째 페이지에 걸쳐 잘렸을 것이다. 해법은 역시 행 단위를 맞추는 것이다. 먼저 회원 테이블만으로 페이지를 잘라 회원 번호 목록을 얻고(SELECT member_id FROM member ORDER BY member_id LIMIT 2), 그 번호들로 주문을 따로 조회한다(WHERE member_id IN (1, 2)).

    JPA에서 다시 만나는 같은 현상

    JPA 활용 2편에서 본 컬렉션 페치 조인의 제약들은 모두 이 절의 SQL 현상이 객체 세계로 올라온 것이다. select m from Member m join fetch m.orders가 실행하는 SQL은 위의 회원-주문 조인이고, 결과는 주문 단위의 행이다. Hibernate ORM 6.0 마이그레이션 가이드에 따르면 Hibernate 6부터는 컬렉션을 페치 조인할 때 중복된 부모 엔티티를 걸러 내려고 JPQL에 distinct를 쓸 필요가 없고, 중복 엔티티는 항상 걸러지며, JPQL에 distinct를 쓰면 SQL에도 항상 전달된다. 행이 늘어나는 것은 그대로이고, Hibernate가 결과를 객체로 만들 때 같은 부모를 하나로 합쳐 줄 뿐이다.

    컬렉션 페치 조인에 페이지 나누기(setFirstResult, setMaxResults)를 함께 쓰면, 바로 위에서 본 이유로 SQL의 LIMIT을 쓸 수 없다. 조인 결과의 행을 자르면 컬렉션이 중간에 잘리기 때문이다. Hibernate 6.6.53 jar에 들어 있는 로그 메시지 정의를 확인하면 이때 HHH90003004 번호로 "firstResult/maxResults specified with collection fetch; applying in memory"라는 경고를 남긴다. 조건에 맞는 행을 모두 메모리로 읽은 다음 애플리케이션 안에서 페이지를 자른다는 뜻이다. 데이터가 많으면 메모리 문제로 이어지므로, 이름 그대로 이 상황을 오류로 만드는 설정 hibernate.query.fail_on_pagination_over_collection_fetch도 있다.

    두 컬렉션을 동시에 페치 조인하면 앞 절의 2 × 2 상황이 된다. 주문의 주문 상품과 결제를 함께 페치 조인하면 SQL 결과는 주문마다 ai × bi행이다. 두 컬렉션이 모두 순서와 중복을 허용하는 bag(일반적인 List 매핑)이면, Hibernate는 곱집합 때문에 생긴 중복과 원래 컬렉션에 있던 중복을 구별할 방법이 없다. 그래서 "cannot simultaneously fetch multiple bags"라는 메시지의 MultipleBagFetchException으로 거부한다. 해법도 SQL과 같은 원리다. 한 번에 일대다 하나만 펼치고, 나머지 컬렉션은 부모 키 목록으로 따로 읽는다. 배치 페치는 "부모 키 목록으로 자식을 IN 조회"를 자동화한 것이다.

    한 층 아래: 조인은 어떻게 실행되는가

    조인 결과가 어떤 행들로 이루어지는지는 관계 연산의 정의가 정한다. 실행 방법이 바뀌어도 결과 집합은 같고, 달라지는 것은 비용과 (ORDER BY가 없을 때의) 행 순서뿐이다. 그래도 실행 방법을 알면 외래 키 인덱스가 왜 중요한지, 옵티마이저가 관계의 카디널리티를 어떻게 이용하는지 보인다.

    MySQL의 기본 조인 방식은 중첩 루프 조인(nested loop join)이다. 바깥 테이블의 행을 하나씩 읽고, 각 행에 대해 안쪽 테이블에서 조인 조건에 맞는 행을 찾는다. 회원에서 주문으로 조인하면 회원 행마다 orders.member_id = ?를 찾아야 하는데, 이때 외래 키를 위해 만들어진 member_id 보조 인덱스가 쓰인다. InnoDB의 보조 인덱스 항목은 인덱스 열 값과 기본 키 값의 쌍, 여기서는 (member_id, order_id)이고 이 순서로 정렬되어 있다. 같은 회원의 주문 항목들은 B+Tree 잎 페이지에 나란히 붙어 있으므로, 첫 항목을 찾은 뒤 옆으로 읽어 나가면 된다. 주문의 다른 열이 필요하면 각 항목의 order_id로 클러스터형 인덱스를 한 번 더 찾아간다. 03회에서 본 "보조 인덱스는 기본 키를 담는다"는 구조가 여기서 쓰인다.

    회원 -> 주문 (일대다 방향)                         주문 -> 회원 (다대일 방향)

for each m in member:                              for each o in orders:
    orders의 member_id 보조 인덱스에서                  member의 기본 키 인덱스에서
    member_id = m.member_id 인 항목을                   member_id = o.member_id 인 행을
    모두 읽는다   -> 0개, 1개, 여러 개                    하나 읽는다   -> 최대 1개

EXPLAIN type: ref                                  EXPLAIN type: eq_ref
(키 값으로 여러 행이 나올 수 있다)                    (PRIMARY KEY / UNIQUE NOT NULL: 한 행)

    EXPLAIN의 접근 유형(type)에 이 차이가 그대로 드러난다. MySQL 8.0 문서에 따르면 eq_ref는 앞 테이블들의 행 조합마다 이 테이블에서 한 행을 읽는 방식으로, 조인이 인덱스의 모든 부분을 쓰고 그 인덱스가 PRIMARY KEY나 UNIQUE NOT NULL 인덱스일 때 쓰인다. ref는 앞 테이블들의 행 조합마다 인덱스 값이 일치하는 모든 행을 읽는 방식으로, 키 값으로 한 행을 고를 수 없을 때 쓰인다. 다대일 방향으로 부모를 찾는 조인은 eq_ref, 일대다 방향으로 자식을 찾는 조인은 ref가 된다. 옵티마이저도 인덱스의 유일성 정의를 근거로 "이 조인은 행을 늘리지 않는다"는 것을 알고 비용을 계산한다. 앞 절에서 손으로 계산한 행 수 규칙을 옵티마이저는 인덱스 정의에서 읽어 내는 것이다.

    예제와 같은 스키마에 회원 1,000명과 주문 10,000건(회원마다 10건)을 넣고 ANALYZE TABLE로 통계를 만든 뒤 두 방향의 조인을 EXPLAIN으로 보면 다음과 같다. rows와 filtered는 통계에서 나온 추정치라 실행 환경과 통계에 따라 달라진다. MySQL 8.0.46에서도 type과 key는 같았고, 주문 쪽 rows만 9 대신 10으로 나왔다.

    EXPLAIN SELECT m.name, o.order_id
FROM member m JOIN orders o ON o.member_id = m.member_id
WHERE m.member_id IN (1, 2, 3);

+----+-------------+-------+------------+-------+------------------+------------------+---------+-----------------------------+------+----------+-------------+
| id | select_type | table | partitions | type  | possible_keys    | key              | key_len | ref                         | rows | filtered | Extra       |
+----+-------------+-------+------------+-------+------------------+------------------+---------+-----------------------------+------+----------+-------------+
|  1 | SIMPLE      | m     | NULL       | range | PRIMARY          | PRIMARY          | 8       | NULL                        |    3 |   100.00 | Using where |
|  1 | SIMPLE      | o     | NULL       | ref   | fk_orders_member | fk_orders_member | 8       | m_db_design1_04.m.member_id |    9 |   100.00 | Using index |
+----+-------------+-------+------------+-------+------------------+------------------+---------+-----------------------------+------+----------+-------------+

EXPLAIN SELECT o.order_id, m.name
FROM orders o JOIN member m ON m.member_id = o.member_id
WHERE o.order_id BETWEEN 1 AND 10;

+----+-------------+-------+------------+--------+--------------------------+---------+---------+-----------------------------+------+----------+-------------+
| id | select_type | table | partitions | type   | possible_keys            | key     | key_len | ref                         | rows | filtered | Extra       |
+----+-------------+-------+------------+--------+--------------------------+---------+---------+-----------------------------+------+----------+-------------+
|  1 | SIMPLE      | o     | NULL       | range  | PRIMARY,fk_orders_member | PRIMARY | 8       | NULL                        |   10 |   100.00 | Using where |
|  1 | SIMPLE      | m     | NULL       | eq_ref | PRIMARY                  | PRIMARY | 8       | m_db_design1_04.o.member_id |    1 |   100.00 | NULL        |
+----+-------------+-------+------------+--------+--------------------------+---------+---------+-----------------------------+------+----------+-------------+

    회원에서 주문을 찾는 쪽은 외래 키가 자동으로 만든 인덱스 fk_orders_member로 ref 접근을 하고, 주문에서 회원을 찾는 쪽은 회원의 기본 키로 eq_ref 접근을 하며 rows가 1이다. 다만 접근 유형은 인덱스 정의만으로 정해지지 않고 비용 추정을 거쳐 정해진다. 주문이 세 건뿐인 예제 크기의 테이블에서 STRAIGHT_JOIN으로 회원을 먼저 읽게 고정하자, 옵티마이저는 쓸 수 있는 인덱스가 있는데도 주문 테이블 전체를 읽는 해시 조인(type: ALL, Using join buffer (hash join))을 골랐다. 행이 몇 개 안 되면 인덱스 탐색보다 통째로 읽는 편이 싸다고 판단하기 때문이다.

    조인 조건에 쓸 인덱스가 없으면 어떻게 될까. InnoDB에서 외래 키 제약을 선언했다면 인덱스가 반드시 있지만, 제약 없이 외래 키 "열"만 둔 스키마에서는 인덱스를 만드는 것을 잊기 쉽다. MySQL 문서에 따르면 8.0.18부터는 각 조인이 동등 조건을 갖고 조인 조건에 쓸 인덱스가 없을 때 해시 조인(hash join)을 쓰고, EXPLAIN의 Extra 열에 Using join buffer (hash join)으로 표시된다. 8.0.20부터는 블록 중첩 루프(block nested loop)가 제거되어 그것이 쓰이던 자리에 해시 조인이 쓰인다. 해시 조인은 한쪽 입력으로 해시 테이블을 만든 뒤 다른 쪽 입력으로 탐색하므로, 인덱스가 없을 때의 대안으로는 낫다. 그러나 특정 회원 몇 명의 주문만 찾는 질의에서는 인덱스 한 번 탐색으로 끝날 일을 테이블 전체를 읽어 해시 테이블을 만드는 일로 바꾸는 셈이다. 외래 키 열에는 제약을 쓰든 안 쓰든 인덱스가 필요하다.

    EXPLAIN SELECT m.name, o.order_id
FROM member m JOIN orders_noidx o ON o.member_id = m.member_id
WHERE m.member_id IN (1, 2, 3);

+----+-------------+-------+------------+-------+---------------+---------+---------+------+------+----------+--------------------------------------------+
| id | select_type | table | partitions | type  | possible_keys | key     | key_len | ref  | rows | filtered | Extra                                      |
+----+-------------+-------+------------+-------+---------------+---------+---------+------+------+----------+--------------------------------------------+
|  1 | SIMPLE      | m     | NULL       | range | PRIMARY       | PRIMARY | 8       | NULL |    3 |   100.00 | Using where                                |
|  1 | SIMPLE      | o     | NULL       | ALL   | NULL          | NULL    | NULL    | NULL | 9720 |    10.00 | Using where; Using join buffer (hash join) |
+----+-------------+-------+------------+-------+---------------+---------+---------+------+------+----------+--------------------------------------------+

    회원 세 명의 주문을 찾는 같은 질의가, 인덱스가 없으면 주문 약 1만 행을 모두 읽는 계획(type: ALL)이 된다. MySQL 8.0.46에서도 같은 계획이 나왔고 rows 추정치만 10207이었다.

    흔한 오해와 함정

    "외래 키는 자주 조회하는 쪽에 둔다." 외래 키의 위치는 카디널리티가 정한다. 회원 화면에서 주문 목록을 자주 보든, 주문 화면에서 회원 이름을 자주 보든 외래 키는 주문 테이블에 있다. 조회 빈도는 인덱스와 질의 형태로 다룬다. 조회를 편하게 하려고 1 쪽에 무언가를 두면, 그것은 외래 키가 아니라 반정규화된 복사본이고 동기화 책임이 따라온다.

    "외래 키 열을 만들면 인덱스도 생긴다." InnoDB가 인덱스를 자동으로 만드는 것은 외래 키 "제약"을 선언했을 때다. 제약 없이 열만 만들거나, 열 정의 안에 인라인 REFERENCES를 쓴 경우(MySQL에서 무시된다)에는 인덱스도 제약도 없다. 그런 스키마에서 부모를 지우거나 일대다 조인을 하면 자식 테이블 전체를 읽게 된다.

    "NOT NULL을 붙이면 필수 참여가 표현된다." 자식 쪽 필수 참여만 표현된다. "부모는 자식이 최소 하나 있어야 한다"는 규칙은 선언적 제약으로 표현되지 않으며, InnoDB는 검사를 커밋까지 미룰 수도 없다. 이 규칙은 애플리케이션의 트랜잭션 안에서 한곳에 모아 지켜야 한다. 반대로 "언젠가 필수"인 관계에 NOT NULL을 붙이면 데이터를 넣을 수 없거나, 의미 없는 임시 값을 넣게 된다.

    "조인 결과가 많아지면 DISTINCT를 붙이면 된다." DISTINCT는 완전히 같은 행을 합칠 뿐이다. 집계가 부풀려진 문제는 고치지 못하고, SUM(DISTINCT)는 값이 우연히 같은 서로 다른 행을 지워 오히려 다른 방향으로 틀린다. 결과가 이상하게 많아졌다면 "결과의 한 행이 무엇인가"부터 다시 정한다.

    "외래 키 제약은 느리니 쓰지 않는 것이 실무 표준이다." 이것은 표준이 아니라 트레이드오프다. 제약은 부모 인덱스 탐색과 공유 잠금이라는 비용을 치르고, 그 대가로 고아 행이 생기지 않는다는 보장과 그 보장에 기대는 단순한 질의를 준다. 제약을 빼기로 했다면 인덱스는 직접 만들어야 하고, 앞에서 본 삭제와 삽입의 경쟁을 애플리케이션이 막아야 하며, 내부 조인이 행을 잃지 않는다는 가정도 버려야 한다. 무엇을 포기하는지 알고 내린 결정이어야 한다.

    "NO ACTION은 아무것도 하지 않는다는 뜻이다." 이름과 달리 InnoDB에서 NO ACTION은 RESTRICT와 같다. 관련된 자식이 있으면 부모 쪽 작업이 즉시 거부된다. 참조 동작을 생략했을 때의 기본값이 이것이다.

    정리: 관계선 하나를 옮기는 절차

    이 회차의 내용을 일대다 관계선 하나를 테이블로 옮기는 절차로 묶으면 다음과 같다.

    1. 카디널리티를 업무 규칙과 시간 축으로 확인한다. 한 시점에 하나인지, 평생 하나인지, 과거 값을 기억해야 하는지 묻는다. 이 답이 외래 키의 위치를 정한다.
    2. 외래 키 열을 상대가 하나뿐인 쪽, 곧 N 쪽에 둔다. 칸 하나에 값 하나라는 원칙과 함수 종속 자식 키 → 부모 키가 근거다. 자료형은 부모 키와 크기·부호까지 같게 한다.
    3. 자식 쪽 참여도로 NULL 허용 여부를 정한다. 만들어지는 순간부터 필수면 NOT NULL, 아니면 NULL 허용이다. 부모 쪽 필수 참여는 표에 적어 두고 애플리케이션 규칙으로 넘긴다.
    4. 외래 키 제약을 별도 FOREIGN KEY 절로 선언하고 참조 동작을 고른다. 자식이 부모의 일부면 CASCADE, 자식이 독립된 기록이면 RESTRICT, 자식이 부모 없이 남을 수 있으면 SET NULL(열이 NULL 허용이어야 한다).
    5. 인덱스를 확인한다. 외래 키 열이 맨 앞에 오는 인덱스가 있는지, 조회 패턴상 (member_id, ordered_at) 같은 복합 인덱스가 그 역할을 겸할 수 있는지 본다.
    6. 그 관계를 조인하는 질의의 행 단위를 정한다. 일대다 방향 조인은 행을 늘리고, 일대다 두 개를 함께 조인하면 곱이 된다. 집계는 각 값이 속한 행 단위에서 먼저 하고, 부모 선택은 EXISTS로, 페이지 나누기는 부모 단위로 한다.
    이 장의 핵심

    관계형 모델에서 관계는 값의 일치이고, 칸 하나에는 값 하나만 들어가므로 외래 키는 상대가 하나뿐인 N 쪽에 놓인다. 자식 쪽 참여도는 그 외래 키 열의 NULL 허용 여부로 옮겨지지만, 부모 쪽 필수 참여는 선언적 제약 밖에 있다. InnoDB는 외래 키를 행마다 즉시 검사하며 부모 레코드에 공유 잠금을 걸어 경쟁을 막고, 그 잠금은 동시성 동작에 흔적을 남긴다. 그렇게 만든 관계를 일대다 방향으로 조인하면 결과의 행 단위가 자식으로 바뀌므로, 집계와 페이지 나누기는 언제나 "결과의 한 행이 무엇인가"를 먼저 정한 뒤에 한다.
    관계의 논리적 표현
    관계형 모델에는 포인터가 없으므로 관계는 한쪽 행의 외래 키 값과 다른 쪽 행의 키 값이 일치하는 것으로 표현된다. 외래 키 제약은 그 값이 NULL이거나 실제로 존재하는 키라는 참조 무결성을 데이터베이스가 지키게 한다.
    참여도
    관계의 최소 카디널리티로, 반드시 참여하는 필수 참여와 참여하지 않아도 되는 선택 참여가 있다. 관계의 양쪽에 따로 정하며, 샘플 데이터가 아니라 업무 규칙과 시간 축으로 판단한다.
    참여도의 테이블 표현
    자식 쪽 필수 참여는 외래 키 열의 NOT NULL, 선택 참여는 NULL 허용으로 옮겨진다. 부모 쪽 필수 참여는 다른 테이블의 행 수에 대한 조건이라 NOT NULL로도 CHECK로도 표현되지 않고 애플리케이션이 트랜잭션 안에서 지킨다.
    외래 키 위치
    칸 하나에는 값 하나만 들어가므로 상대를 칸 하나로 적을 수 있는 쪽, 곧 상대가 하나뿐인 N 쪽에 외래 키를 둔다. 1 쪽에 두면 행 복제, 목록 문자열, 반복 열 중 하나가 되어 이상 현상이나 제1정규형 위반을 낳는다.
    InnoDB 외래 키 검사
    행 단위로 즉시 검사하고 커밋까지 미루지 않으며, 검사하는 레코드에 공유 잠금을 건다. 외래 키 열이 맨 앞에 오는 인덱스가 필요하고 없으면 자동으로 만들며, 인라인 REFERENCES와 MATCH 절은 지켜지지 않는다.
    조인의 행 증가
    일대다 방향 조인의 결과 행은 자식 단위가 되어 부모 값이 반복되고, 다대일 방향 조인은 부모 키가 유일하므로 행을 늘리지 않는다. 같은 부모의 일대다 두 개를 함께 조인하면 주문마다 a × b행의 곱집합이 생긴다.
    행 단위를 맞추는 해법
    값은 그 값이 속한 테이블의 행 단위에서 집계한 뒤 조인하고, 부모를 고를 때는 EXISTS를, 페이지 나누기는 부모 키로 먼저 자른 뒤 자식을 조회한다. DISTINCT는 합계의 부풀림을 고치지 못한다.
    조인 실행과 접근 유형
    중첩 루프 조인에서 부모를 찾는 다대일 조인은 eq_ref, 자식을 찾는 일대다 조인은 외래 키 인덱스를 쓰는 ref가 된다. 쓸 인덱스가 없으면 MySQL 8.0.18부터 동등 조인에 해시 조인을 쓴다.

    실무에서 관계선을 옮길 때 가장 자주 틀리는 것은 위치가 아니라 시간이다. 외래 키를 1 쪽에 두는 실수는 드물지만, "지금은 하나"를 "언제나 하나"로 읽어 일대일이나 속성으로 설계했다가 이력과 복수 등록 요구가 오면서 일대다로 바꾸는 일은 흔하다. 그때의 비용은 열 하나를 옮기는 것이 아니라 그 관계를 읽는 모든 질의와 코드를 고치는 것이다. 설계 검토에서 "이 값이 바뀌면 예전 값은 버려도 되는가", "같은 대상이 둘이 될 수 있는가"를 묻는 것이 가장 싼 보험이다. 참여도도 마찬가지로, 개념 모델의 "반드시"가 생성 시점의 필수인지 결국의 필수인지를 구분하지 않으면 NOT NULL 때문에 데이터를 넣지 못하거나 의미 없는 기본값이 쌓인다.

    외래 키 제약을 물리적으로 선언할지는 조직마다 판단이 갈린다. 제약을 두면 고아 행이 원천적으로 막히고 내부 조인이 행을 잃지 않는다는 가정을 믿을 수 있다. 대신 자식 삽입마다 부모 탐색과 공유 잠금이 생기고, 부모 행 갱신이 긴 트랜잭션에 막히거나 부모 집계 열 갱신과 엮여 교착 상태가 생길 수 있다. InnoDB는 사용자 정의 파티셔닝을 쓴 테이블에 외래 키를 지원하지 않는다는 제약도 있다. 제약을 빼는 쪽을 택한다면 외래 키 열의 인덱스를 직접 만들고, 삭제와 삽입의 경쟁을 막는 순서와 잠금을 애플리케이션에서 설계하며, 주기적으로 고아 행을 찾는 점검 질의를 돌리는 것까지 함께 결정해야 한다.

    조인의 행 증가는 장애 보고서보다 "숫자가 안 맞는다"는 문의로 먼저 나타난다. 매출 대시보드의 합계가 결제 시스템과 다르다면, 쿼리에 일대다 조인이 둘 이상 섞여 있지 않은지, 부모의 값을 자식 단위에서 합하고 있지 않은지부터 본다. 이 버그는 테스트 데이터가 "부모 하나에 자식 하나"일 때 드러나지 않으므로, 집계 쿼리의 테스트에는 자식이 둘 이상이고 금액이 서로 같은 경우를 일부러 넣어야 한다. JPA에서 컬렉션 페치 조인과 페이지 나누기를 함께 쓰려는 순간, 두 컬렉션을 한 번에 페치 조인하려는 순간도 같은 원리가 객체 계층에서 다시 나타나는 지점이다.
  • 도서관 시스템의 업무 규칙이 다음과 같다. "회원은 도서를 여러 권 대출할 수 있다. 대출 한 건은 도서 한 권에 대한 것이다. 같은 도서는 반납 후 다른 회원이 다시 대출할 수 있다." 회원, 도서, 대출 테이블의 외래 키를 어디에 두고 각각 NULL을 허용할지 정하라. 그리고 "대출 중인 도서는 한 번에 한 명에게만 대출된다"는 규칙이 이 외래 키들만으로 지켜지는지 판단하라.
  • 회원(1)–주문(N)–주문 상품(N) 구조에서 다음 쿼리의 결과를 예측하라. 회원 A는 주문 2건(각각 주문 상품 3개, 1개), 회원 B는 주문 0건이다. SELECT m.member_id, COUNT(*), COUNT(o.order_id), COUNT(DISTINCT o.order_id) FROM member m LEFT JOIN orders o ON o.member_id = m.member_id LEFT JOIN order_item oi ON oi.order_id = o.order_id GROUP BY m.member_id
  • 트랜잭션 T1이 INSERT INTO orders (..., member_id) VALUES (..., 7)을 실행하고 커밋하지 않은 상태에서, T2가 UPDATE member SET grade = 'VIP' WHERE member_id = 7을 실행했다. T2는 어떻게 되는가? 이어서 T1이 커밋하면 T2는 어떻게 되는가? 이유를 잠금의 종류로 설명하라.
  • 어떤 개발자가 회원과 주문 사이에 "회원은 최소 한 번 주문해야 회원으로 인정된다"는 규칙을 지키려고 회원 테이블에 first_order_id BIGINT NOT NULL을 추가하고 주문 테이블을 참조하는 외래 키를 걸었다. 주문 테이블에는 이미 member_id NOT NULL 외래 키가 있다. InnoDB에서 이 설계가 어떤 문제를 일으키는지 설명하고 대안을 제시하라.
    •

    1번. 대출 한 건에 회원은 하나, 도서도 하나다. 회원과 대출은 일대다, 도서와 대출도 일대다이므로 두 외래 키 member_id, book_id는 모두 N 쪽인 대출 테이블에 둔다. 대출은 회원과 도서 없이 생길 수 없으므로 둘 다 NOT NULL이다. 회원과 도서 쪽은 대출이 없을 수 있으므로 선택 참여이고 할 일이 없다. 그러나 "대출 중인 도서는 한 번에 한 명에게만"이라는 규칙은 이 외래 키들로 지켜지지 않는다. 외래 키는 "그 도서가 존재한다"만 보장하고, 같은 도서를 가리키는 반납 전 대출 행이 둘 생기는 것은 막지 않는다. 이 규칙은 반납 여부를 포함한 유일성 조건이므로, 반납되지 않은 대출에만 값이 있는 열(대출 중이면 1, 반납되면 NULL)을 두고 (book_id, 그 열)에 UNIQUE를 거는 방식(UNIQUE 인덱스가 NULL을 여러 개 허용한다는 점을 이용)이나 애플리케이션의 잠금으로 지켜야 한다. 이 문제의 요점은 외래 키가 표현하는 것이 "존재"뿐이라는 점이다.

    2번. 회원 A의 행 수를 먼저 세자. 첫 주문은 주문 상품 3개라 3행, 둘째 주문은 1개라 1행, 합 4행이다. 그래서 COUNT(*) = 4, COUNT(o.order_id) = 4(네 행 모두 order_id가 NULL이 아니다), COUNT(DISTINCT o.order_id) = 2다. 회원 B는 주문이 없어서 외부 조인이 주문과 주문 상품 쪽이 모두 NULL인 행 하나를 만든다. COUNT(*) = 1, COUNT(o.order_id) = 0, COUNT(DISTINCT o.order_id) = 0이다. 회원 A의 COUNT(o.order_id)가 주문 수 2가 아니라 4라는 점이 핵심이다. 주문 상품까지 조인해 행 단위가 주문 상품이 되었기 때문이다. 주문 수를 원하면 기본 키에 DISTINCT를 쓰거나 주문 상품을 조인하지 않아야 한다.

    3번. T1의 주문 삽입은 외래 키 검사를 위해 회원 7번 레코드에 공유(S) 잠금을 잡고, 이 잠금은 T1이 끝날 때까지 유지된다. T2의 UPDATE는 회원 7번 레코드에 배타(X) 잠금이 필요한데, X 잠금은 다른 트랜잭션의 S 잠금과 호환되지 않으므로 T2는 대기한다. 갱신하는 열이 grade로 외래 키와 상관없어도, 잠금이 레코드 단위이므로 마찬가지다. T1이 커밋하면 S 잠금이 풀리고 T2가 X 잠금을 얻어 갱신을 마친다(그동안 잠금 대기 시간 제한 innodb_lock_wait_timeout을 넘지 않았다면). T1이 오래 걸리는 작업을 트랜잭션 안에 품고 있으면 이 대기가 길어진다.

    4번. 회원과 주문이 서로를 NOT NULL 외래 키로 가리키는 순환 참조가 된다. 회원을 넣으려면 그 회원의 첫 주문이 이미 있어야 하고, 주문을 넣으려면 회원이 이미 있어야 한다. InnoDB는 외래 키를 행마다 즉시 검사하고 커밋까지 미루지 않으므로 어느 쪽도 먼저 넣을 수 없다. foreign_key_checks를 끄고 넣는 것은 무결성 검사를 포기하는 것이고, 다시 켜도 그동안의 데이터는 검사되지 않는다. 이 규칙은 부모 쪽 필수 참여이므로 선언적 제약으로 표현하지 않는다. 대안은 first_order_id를 없애고, "주문이 있는 회원"이 필요할 때 EXISTS로 판정하거나, 회원 상태 열(가입 대기, 정회원)을 두고 첫 주문을 저장하는 트랜잭션 안에서 상태를 바꾸는 것이다. 첫 주문 번호 자체가 업무적으로 필요하다면 그 열은 NULL 허용으로 두고, 주문 저장 후 갱신한다.

     "강의실 하나에는 여러 수업이 배정되고, 수업 하나는 강의실 하나에서 열린다. 온라인 수업은 강의실이 없다." 이 관계를 테이블로 옮긴 것으로 가장 알맞은 것은? 강의실 테이블에 class_id 외래 키를 두고 NULL을 허용한다. 수업 테이블에 room_id 외래 키를 두고 NULL을 허용한다. 수업 테이블에 room_id 외래 키를 두고 NOT NULL로 한다. 강의실 테이블에 class_ids 열을 두고 수업 번호를 쉼표로 이어 저장한다. 수업 하나에 강의실은 최대 하나이므로 상대가 하나뿐인 쪽, 곧 N 쪽인 수업 테이블에 외래 키를 둔다. 온라인 수업은 강의실이 없으므로 수업 쪽 참여는 선택이고 열은 NULL을 허용해야 한다. 강의실 쪽에 두면 강의실 행이 복제되거나 한 칸에 여러 값이 들어가며, 쉼표 목록은 제1정규형 위반이자 외래 키 제약을 걸 수 없는 형태다. NOT NULL은 온라인 수업을 넣을 수 없게 만든다. "모든 주문은 주문 상품을 최소 하나 가져야 한다"는 규칙을 MySQL 8.0 InnoDB에서 지키는 방법으로 가장 알맞은 것은? order_item.order_id에 NOT NULL을 건다. 주문 테이블에 CHECK ((SELECT COUNT(*) FROM order_item WHERE order_id = orders.order_id) > 0)을 건다. 외래 키의 참조 동작을 NO ACTION으로 두어 커밋 시점에 검사되게 한다. 주문과 주문 상품을 한 트랜잭션에서 저장하고, 주문 상품이 비어 있거나 마지막 하나를 지우려 할 때 애플리케이션이 거부한다. 이 규칙은 부모 쪽 필수 참여로, 다른 테이블의 행 수에 대한 조건이다. order_item.order_id NOT NULL은 자식 쪽 필수 참여(주문 상품은 주문이 있어야 한다)를 표현할 뿐이다. MySQL의 CHECK 조건에는 서브쿼리를 쓸 수 없다. InnoDB에서 NO ACTION은 RESTRICT와 같아 즉시 거부하며, 검사를 커밋까지 미루지 않는다. 남는 방법은 애플리케이션이 트랜잭션 안에서 규칙을 한곳에 모아 지키는 것이다. 주문 1건에 주문 상품이 3개(금액 각 1,000원), 결제가 2건(각 1,500원) 있다. SELECT SUM(oi.amount), SUM(p.amount) FROM orders o JOIN order_item oi ON oi.order_id = o.order_id JOIN payment p ON p.order_id = o.order_id WHERE o.order_id = 1의 결과는? 3,000 / 3,000 3,000 / 9,000 6,000 / 9,000 6,000 / 3,000 주문 상품과 결제는 서로 관계가 없고 같은 주문만 가리키므로 3 × 2 = 6행의 모든 조합이 만들어진다. 각 주문 상품은 결제 수(2)만큼 반복되어 상품 합계는 3,000 × 2 = 6,000이 되고, 각 결제는 주문 상품 수(3)만큼 반복되어 결제 합계는 3,000 × 3 = 9,000이 된다. 실제 값은 둘 다 3,000이므로 각자 주문 단위로 먼저 집계한 뒤 조인해야 한다. 상품의 category_id는 NULL을 허용하고, 카테고리가 없는 상품이 하나 있다. 상품이 없는 카테고리를 찾으려는 다음 질의 중 원하는 결과를 내는 것은? SELECT c.name FROM category c WHERE NOT EXISTS (SELECT 1 FROM product p WHERE p.category_id = c.category_id) SELECT name FROM category WHERE category_id NOT IN (SELECT category_id FROM product) SELECT c.name FROM category c JOIN product p ON p.category_id = c.category_id WHERE p.product_id IS NULL SELECT DISTINCT c.name FROM category c JOIN product p ON p.category_id <> c.category_id NOT IN은 서브쿼리 결과에 NULL이 하나라도 있으면 비교 결과가 UNKNOWN이 되어 어떤 행도 통과시키지 못한다. 내부 조인은 짝이 있는 행만 남기므로 p.product_id IS NULL인 행이 나올 수 없다(외부 조인이었다면 맞는 방법이다). <> 조인은 다른 카테고리의 상품과 짝지어지는 모든 카테고리를 돌려준다. NOT EXISTS는 NULL인 상품을 짝으로 세지 않을 뿐 다른 판정에 영향을 주지 않으므로 상품 없는 카테고리를 정확히 찾는다. InnoDB에서 자식 행을 삽입할 때 외래 키 검사가 부모 레코드에 공유 잠금을 거는 이유로 가장 알맞은 것은? 부모 레코드의 비키 열이 바뀌어 자식의 값과 달라지는 것을 막기 위해 검사가 끝난 뒤 트랜잭션이 끝나기 전에 다른 트랜잭션이 그 부모를 지우거나 키를 바꿔 고아 행이 생기는 것을 막기 위해 부모 테이블의 B+Tree 페이지가 분할되는 것을 막기 위해 외래 키 검사를 커밋 시점까지 미루기 위해 검사 시점에 부모가 있었더라도, 잠금이 없다면 자식 삽입이 커밋되기 전에 다른 트랜잭션이 부모를 지우고 커밋할 수 있다. 부모 레코드의 S 잠금은 삭제나 키 변경에 필요한 X 잠금을 막아 이 경쟁을 없앤다. 부모의 비키 열 변경은 참조 무결성과 상관없지만 레코드 단위 잠금이라 함께 막히는 것은 부작용일 뿐 목적이 아니다. InnoDB는 검사를 미루지 않고 즉시 한다.
    외래 키(foreign key)
    다른 테이블(또는 같은 테이블)의 키 값을 담아 행 사이의 관계를 표현하는 열 또는 열의 조합. 외래 키 제약을 선언하면 데이터베이스가 그 값의 존재를 검사한다.
    참조 무결성(referential integrity)
    외래 키의 값이 NULL이거나 참조되는 테이블에 실제로 존재하는 키 값이어야 한다는 규칙. 이 규칙이 깨진 행을 고아 행이라고 부른다.
    참조 동작(referential action)
    부모 행의 삭제나 키 변경이 자식을 깨뜨리려 할 때 수행할 동작. InnoDB는 CASCADE, SET NULL, RESTRICT, NO ACTION(= RESTRICT)을 지원하고 SET DEFAULT는 지원하지 않는다(MySQL 8.0.46·8.4.13에서는 선언은 받아들이지만 부모 삭제를 RESTRICT처럼 거부한다).
    참여도(participation)
    관계에서 한 엔티티의 모든 인스턴스가 반드시 참여해야 하는지를 나타내는 최소 카디널리티. 필수 참여(전체 참여)와 선택 참여(부분 참여)로 나뉜다.
    선언적 제약(declarative constraint)
    NOT NULL, UNIQUE, FOREIGN KEY, CHECK처럼 테이블 정의에 선언해 데이터베이스가 자동으로 검사하는 규칙. 행 하나나 키 하나로 판정할 수 있는 규칙만 표현할 수 있다.
    자기 참조 외래 키(self-referencing foreign key)
    같은 테이블의 기본 키를 가리키는 외래 키. 직원과 상사처럼 한 엔티티 안의 일대다 관계를 표현한다.
    세미 조인(semi-join)
    한 테이블의 행을 다른 테이블에 짝이 존재하는지로만 걸러 내는 연산. 결과의 행 단위가 바깥 테이블에 머물러 조인처럼 행을 늘리지 않으며, SQL에서는 EXISTS나 IN으로 쓴다.
    중첩 루프 조인(nested loop join)
    바깥 입력의 행마다 안쪽 입력에서 조인 조건에 맞는 행을 찾는 조인 방식. 안쪽에 쓸 인덱스가 있으면 행마다 인덱스 탐색 한 번으로 짝을 찾는다.
    해시 조인(hash join)
    한쪽 입력으로 조인 키의 해시 테이블을 만든 뒤 다른 쪽 입력으로 탐색하는 조인 방식. MySQL은 8.0.18부터 조인 조건에 쓸 인덱스가 없는 동등 조인에 사용한다.
    연관관계의 주인(owning side)
    JPA 양방향 연관관계에서 외래 키 값을 관리하는 쪽. 외래 키가 자식 테이블에 있으므로 자식 엔티티의 @ManyToOne 쪽이 주인이 되고, 반대쪽은 mappedBy로 표시한다.
