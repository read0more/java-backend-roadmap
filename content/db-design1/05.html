    이 회차의 질문: 외래 키 하나로 정리되지 않는 관계

    04회에서 일대다 관계를 테이블로 옮기는 규칙을 세웠다. 외래 키는 "여럿" 쪽 테이블에 둔다. 주문 행 하나는 회원 한 명만 가리키면 되므로 주문 테이블에 member_id 열 하나를 두면 충분했다. 이 규칙은 우연히 정해진 관례가 아니라 관계형 모델의 원칙에서 나온다. 행 하나의 칸 하나에는 값이 하나만 들어간다. 외래 키 열도 칸이므로 행마다 부모 행 하나만 가리킬 수 있다. 그래서 외래 키를 가진 테이블 쪽에서 보면 관계는 언제나 "나 하나에 상대는 최대 하나"다. 일대다의 "여럿" 쪽이 바로 이 조건을 만족하는 쪽이다.

    이 회차는 이 규칙이 곧바로 답을 주지 않는 두 관계를 다룬다. 일대일(one-to-one, 1:1)은 양쪽 모두 상대가 최대 하나다. 외래 키를 어느 쪽에 두어도 "나 하나에 상대는 최대 하나"가 성립하므로 둘 다 가능하고, 그래서 고르는 일이 생긴다. 다대다(many-to-many, M:N)는 양쪽 모두 상대가 여럿이다. 어느 쪽에 외래 키를 두어도 칸 하나에 여러 값을 넣어야 하므로 둘 다 불가능하다. 한쪽은 선택지가 너무 많고, 다른 쪽은 선택지가 없다. 이 회차의 앞부분은 일대일에서 무엇을 기준으로 고를지를, 뒷부분은 다대다를 표현할 길을 어떻게 새로 내는지를 다룬다.

    두 주제를 묶는 질문이 하나 있다. 관계는 시간이 지나면서 바뀐다. 오늘은 사원 한 명에 노트북 한 대지만, 내년에는 개발자에게 두 대를 지급하기로 할 수 있다. 오늘은 배우와 영화의 연결만 기록하면 되지만, 다음 달에는 배역 이름과 크레딧 순서를 함께 기록해 달라는 요구가 온다. 논리적 모델링에서 내리는 결정은 지금의 업무 규칙을 담는 동시에, 규칙이 바뀔 때 스키마를 얼마나 싸게 고칠 수 있는지를 정한다. 이 회차에서는 그 비용을 MySQL의 DDL과 InnoDB의 동작으로 구체적으로 계산해 본다.

    설명의 기준은 MySQL 8.0 이상과 InnoDB 저장 엔진이다. 일대일·다대다라는 개념과 연결 테이블이라는 해법은 관계형 모델 일반의 이야기지만, UNIQUE 인덱스가 NULL을 어떻게 다루는지, 외래 키를 언제 검사하는지, 인덱스를 추가하고 지우는 DDL이 테이블을 다시 만드는지는 제품마다 다르다. 그런 문장에는 "MySQL에서는", "InnoDB에서는"이라는 범위를 붙인다. 키의 종류와 자연 키·대리 키의 선택은 03회에서, 참여도와 까마귀발 표기는 04회에서, 식별 관계와 비식별 관계는 06회에서 다루므로 여기서는 필요한 만큼만 끌어온다.

    일대일 관계란 무엇인가: 양쪽 모두 최대가 하나

    일대일 관계는 A의 인스턴스 하나에 연결된 B가 최대 하나이고, B의 인스턴스 하나에 연결된 A도 최대 하나인 관계다. "최대"라는 말이 중요하다. 최소, 곧 참여도는 별개의 축이다. 사원에게 아직 노트북이 지급되지 않았을 수 있고, 창고에 있는 노트북은 아직 누구에게도 배정되지 않았을 수 있다. 그래도 둘 사이의 관계는 일대일이다. 양쪽 끝의 최대값이 1이라는 것이 일대일의 정의이고, 최소값이 0인지 1인지는 04회에서 본 참여도의 문제다.

    현실에서 일대일로 보이는 관계는 대체로 두 갈래로 나뉜다. 첫째는 독립된 두 엔티티가 짝지어진 일대일이다. 사원과 그 사원에게 지급된 업무용 노트북이 그렇다. 노트북은 사원과 무관하게 존재한다. 구매해서 창고에 들어오는 순간부터 자산 번호와 일련번호를 가진 인스턴스이고, 사원이 퇴사해도 회수되어 다른 사원에게 간다. 사원 역시 노트북 없이 존재한다. 둘은 각자의 생명주기를 가지며, 어느 시점에 서로 짝이 될 뿐이다. 둘째는 한 엔티티를 나눈 일대일이다. 상품과 상품 상세 설명, 회원과 사업자 회원 정보가 그렇다. 상품 상세 설명은 상품 없이는 의미가 없다. 원래 상품이라는 한 엔티티의 속성인데, 어떤 이유로 다른 테이블에 떼어 놓은 것이다.

    두 갈래를 구분하는 이유는 테이블로 옮기는 방법이 달라지기 때문이다. 독립된 엔티티의 일대일은 양쪽이 각자 기본 키를 가지고, 둘을 잇는 외래 키를 어느 한쪽에 둔다. 한 엔티티를 나눈 일대일은 떼어 낸 쪽이 따로 식별자를 가질 이유가 없으므로 원래 엔티티의 기본 키를 그대로 자기 기본 키로 쓸 수 있다. 앞의 방식은 외래 키 위치를 골라야 하고, 뒤의 방식은 고를 필요가 없다. 이 차이는 다음 절에서 DDL로 확인한다.

    한 엔티티를 왜 나누는가

    한 엔티티를 두 테이블로 나누면 읽을 때 조인이 하나 늘어난다. 그 비용을 치를 만한 이유가 있어야 한다. 대표적인 이유는 네 가지다. 첫째, 선택적 속성 묶음이다. 쇼핑몰 회원 가운데 사업자 회원만 사업자등록번호, 상호, 대표자 이름을 가진다고 하자. 한 테이블에 두면 일반 회원 행마다 세 칸이 NULL이고, "셋이 모두 있거나 모두 없어야 한다"는 규칙은 CHECK 제약으로 따로 적어야 한다. 사업자 정보를 별도 테이블로 떼면 "사업자 정보가 있다"는 사실이 행의 존재로 표현되고, 그 테이블의 세 열은 모두 NOT NULL로 선언할 수 있다. 값이 없는 상태를 NULL 세 개로 표현하는 대신 행이 없는 것으로 표현하는 셈이다.

    둘째, 접근 빈도와 행의 너비다. 상품 목록 화면은 상품 이름과 가격만 수천 건씩 읽고, 상세 설명은 상품 하나를 열었을 때만 읽는다고 하자. InnoDB는 테이블의 행을 기본 키 순서로 클러스터형 인덱스의 리프 페이지에 저장하며, 기본 페이지 크기는 16KB다. 행이 넓을수록 한 페이지에 들어가는 행 수가 줄고, 같은 개수의 행을 읽으려면 더 많은 페이지를 버퍼 풀로 올려야 한다. 상세 설명이 평균 3,000바이트라면, 페이지 머리와 행 머리 같은 부가 공간을 무시한 어림셈으로도 한 페이지에 다섯 행 남짓밖에 들어가지 않는다. 설명을 떼어 낸 상품 행이 100바이트 정도라면 같은 페이지에 백몇십 행이 들어간다. 목록 화면이 읽는 페이지 수가 수십 배 차이 난다.

    여기에는 흔히 놓치는 세부가 있다. MySQL 8.0의 기본 행 형식(row format)은 DYNAMIC이고, 이 형식에서 InnoDB는 긴 가변 길이 열(VARCHAR, VARBINARY, BLOB, TEXT)의 값을 페이지 밖(off-page)의 오버플로 페이지에 통째로 두고 클러스터형 인덱스 레코드에는 20바이트 포인터만 남길 수 있다(MySQL 매뉴얼, InnoDB Row Formats). 다만 이것은 행이 너무 길 때의 일이다. 매뉴얼에 따르면 행이 너무 길면 가장 긴 열부터 페이지 밖으로 보내 클러스터형 인덱스 레코드가 B-tree 페이지에 들어갈 때까지 줄이고, 16KB 페이지에서 페이지 밖 열을 뺀 최대 행 크기는 약 8,000바이트(페이지의 절반 조금 못 미치는 크기)다. 그러니 2만 바이트짜리 설명은 어차피 페이지 밖으로 나가 상품 행을 크게 넓히지 않지만, 3,000바이트짜리 설명은 행 안에 그대로 남는다. "큰 텍스트 열은 무조건 떼어야 한다"는 직관은 반만 맞다. 행 안에 머무를 만큼 적당히 긴 값이 자주 읽는 행을 넓히는 경우가 실제로 나눌 이유가 된다.

    셋째, 권한이다. 비밀번호 해시나 본인 확인 정보처럼 일부 시스템만 읽어야 하는 열을 별도 테이블로 떼면 테이블 단위 GRANT로 접근을 나누기 쉽다. MySQL은 열 단위 권한도 지원하므로 권한만으로는 테이블을 나눌 필요가 없지만, 테이블 단위가 관리하기 단순하다. 넷째, 갱신 빈도다. InnoDB의 행 잠금은 인덱스 레코드에 걸리므로, 같은 행의 서로 다른 열을 고치는 두 트랜잭션도 같은 레코드를 두고 기다린다. 로그인할 때마다 바뀌는 마지막 접속 시각과, 회원이 가끔 고치는 프로필 정보가 한 행에 있으면 둘은 같은 잠금을 다툰다. 자주 바뀌는 열을 다른 테이블로 떼면 서로 다른 행이 되어 이 다툼이 사라진다.

    반대로 이 네 가지 이유가 없다면 한 엔티티를 나누지 않는다. 양쪽 참여가 모두 필수이고, 늘 함께 읽히고, 열이 작다면 한 테이블이 낫다. 나눈 테이블은 조인을 부르고, 두 테이블의 행이 항상 짝을 이루도록 지키는 일을 새로 만든다. 뒤에서 보겠지만 MySQL은 "양쪽이 반드시 서로를 가진다"는 일대일을 선언적 제약만으로 지키지 못한다. 나눌 이유가 분명할 때만 나눈다.

    일대일 관계의 외래 키 위치: 외래 키에 UNIQUE를 더한다

    사원과 노트북의 예로 테이블을 만들어 보자. 업무 규칙은 이렇다. 사원 한 명은 업무용 노트북을 최대 한 대 지급받는다. 노트북 한 대는 최대 한 명에게 배정된다. 지급받지 않은 사원과 배정되지 않은 노트북이 있을 수 있다. 일대다였다면 답은 정해져 있다. 그런데 여기서는 사원 쪽에서 보아도, 노트북 쪽에서 보아도 상대가 최대 하나이므로 외래 키를 어느 쪽에 두어도 된다. 업무 흐름에서 먼저 조회하고 기준이 되는 쪽을 주 테이블, 주 테이블을 거쳐 찾아가는 쪽을 대상 테이블이라고 부르자. 사원 관리 업무에서는 사원이 주 테이블이고 노트북이 대상 테이블이다. 외래 키를 대상 테이블에 두는 설계를 A, 주 테이블에 두는 설계를 B라고 하자.

    먼저 짚을 사실이 있다. 외래 키만으로는 일대일이 되지 않는다. 노트북 테이블에 employee_id 외래 키를 두면, 데이터베이스가 보장하는 것은 "노트북 행 하나는 사원 하나만 가리킨다"뿐이다. 서로 다른 노트북 두 행이 같은 employee_id를 가지는 것은 막지 않는다. 그것은 정확히 일대다다. 일대일을 만들려면 외래 키 열에 UNIQUE 제약을 더해 "같은 사원을 가리키는 노트북은 둘 이상일 수 없다"를 선언해야 한다. 정리하면 일대다는 외래 키, 일대일은 외래 키와 UNIQUE다.

    -- 설계 A: 대상 테이블(laptop)에 외래 키
CREATE TABLE employee (
    employee_id BIGINT      NOT NULL AUTO_INCREMENT,
    name        VARCHAR(50) NOT NULL,
    PRIMARY KEY (employee_id)
);

CREATE TABLE laptop (
    laptop_id   BIGINT      NOT NULL AUTO_INCREMENT,
    serial_no   VARCHAR(30) NOT NULL,
    employee_id BIGINT      NULL,          -- 배정되지 않은 노트북은 NULL
    PRIMARY KEY (laptop_id),
    UNIQUE KEY uk_laptop_serial (serial_no),
    UNIQUE KEY uk_laptop_employee (employee_id),
    CONSTRAINT fk_laptop_employee
        FOREIGN KEY (employee_id) REFERENCES employee (employee_id)
);
    -- 설계 B: 주 테이블(employee)에 외래 키
CREATE TABLE laptop (
    laptop_id BIGINT      NOT NULL AUTO_INCREMENT,
    serial_no VARCHAR(30) NOT NULL,
    PRIMARY KEY (laptop_id),
    UNIQUE KEY uk_laptop_serial (serial_no)
);

CREATE TABLE employee (
    employee_id BIGINT      NOT NULL AUTO_INCREMENT,
    name        VARCHAR(50) NOT NULL,
    laptop_id   BIGINT      NULL,          -- 지급받지 않은 사원은 NULL
    PRIMARY KEY (employee_id),
    UNIQUE KEY uk_employee_laptop (laptop_id),
    CONSTRAINT fk_employee_laptop
        FOREIGN KEY (laptop_id) REFERENCES laptop (laptop_id)
);

    두 설계 모두에서 외래 키를 위한 인덱스를 따로 만들지 않았다는 점을 보자. MySQL은 외래 키 검사가 테이블 전체를 훑지 않도록 참조하는 쪽 테이블에 외래 키 열이 맨 앞에 오는 인덱스를 요구하고, 그런 인덱스가 없으면 자동으로 만든다(MySQL 매뉴얼, FOREIGN KEY Constraints). 여기서는 UNIQUE 인덱스가 이미 그 조건을 만족하므로 별도 인덱스가 생기지 않는다. UNIQUE 인덱스 하나가 두 가지 일을 함께 한다. 일대일을 강제하는 일, 그리고 외래 키 검사를 빠르게 하는 일이다. 이 사실은 뒤의 확장 실습에서 다시 중요해진다. MySQL 8.0.46과 8.4.13에서 설계 A의 SHOW CREATE TABLE laptop을 실행해 보면 인덱스는 PRIMARY, uk_laptop_serial, uk_laptop_employee 셋뿐이다.

    INSERT를 한 줄씩 따라가기

    설계 A에 데이터를 넣으며 제약이 무엇을 막는지 확인하자.

    INSERT INTO employee (employee_id, name) VALUES (1, '서하람'), (2, '나윤결');

INSERT INTO laptop (laptop_id, serial_no, employee_id) VALUES (10, 'SN-A100', 1);    -- (1) 성공
INSERT INTO laptop (laptop_id, serial_no, employee_id) VALUES (11, 'SN-A101', 1);    -- (2) 실패
INSERT INTO laptop (laptop_id, serial_no, employee_id) VALUES (12, 'SN-A102', NULL); -- (3) 성공
INSERT INTO laptop (laptop_id, serial_no, employee_id) VALUES (13, 'SN-A103', NULL); -- (4) 성공
INSERT INTO laptop (laptop_id, serial_no, employee_id) VALUES (14, 'SN-A104', 99);   -- (5) 실패
    -- (2)
ERROR 1062 (23000): Duplicate entry '1' for key 'laptop.uk_laptop_employee'
-- (5)
ERROR 1452 (23000): Cannot add or update a child row: a foreign key constraint fails (`m_db_design1_05`.`laptop`, CONSTRAINT `fk_laptop_employee` FOREIGN KEY (`employee_id`) REFERENCES `employee` (`employee_id`))

SELECT * FROM laptop;
+-----------+-----------+-------------+
| laptop_id | serial_no | employee_id |
+-----------+-----------+-------------+
|        10 | SN-A100   |           1 |
|        12 | SN-A102   |        NULL |
|        13 | SN-A103   |        NULL |
+-----------+-----------+-------------+

    (1)은 사원 1이 존재하고 uk_laptop_employee에 1이 아직 없으므로 성공한다. (2)는 외래 키 검사는 통과하지만, UNIQUE 인덱스에 이미 1이 있으므로 중복 키 오류 1062(ER_DUP_ENTRY)로 거부된다. 이것이 "사원 한 명에 노트북 최대 한 대"를 데이터베이스가 지키는 순간이다. (3)과 (4)는 둘 다 employee_id가 NULL인데 둘 다 성공한다. MySQL 매뉴얼은 UNIQUE 인덱스가 NULL을 허용하는 열에서 NULL 값을 여러 개 허용한다고 명시한다(CREATE INDEX). NULL은 "값이 없음"이고 서로 같다고 판정되지 않으므로, 배정되지 않은 노트북이 여러 대 있어도 유일성 위반이 아니다. 이 성질 덕분에 선택적 일대일을 외래 키 열의 NULL로 표현할 수 있다. (5)는 사원 99가 없으므로 외래 키 오류 1452(ER_NO_REFERENCED_ROW_2, "Cannot add or update a child row: a foreign key constraint fails")로 거부된다.

    외래 키 쪽의 NULL도 한 번 더 확인해 두자. MySQL 매뉴얼은 외래 키에 대해 SQL 표준의 MATCH SIMPLE 의미를 구현한다고 설명한다. 외래 키 값이 전부 또는 일부 NULL이면 부모 테이블에 대응하는 행이 없어도 자식 행을 넣을 수 있다(FOREIGN KEY Constraint Differences). 그래서 (3)과 (4)는 외래 키 검사도 받지 않고 통과한다. 결국 NULL 허용 외래 키 열 하나에 UNIQUE 인덱스를 거는 것만으로 "배정은 없어도 되지만, 있다면 상대는 하나뿐"이라는 선택적 일대일이 완성된다.

    세 번째 길: 기본 키를 공유하기

    한 엔티티를 나눈 일대일에서는 떼어 낸 테이블이 원래 테이블의 기본 키를 그대로 기본 키로 쓰고, 그 열을 동시에 외래 키로 선언할 수 있다. 이것을 공유 기본 키(shared primary key)라고 부른다.

    CREATE TABLE product (
    product_id BIGINT       NOT NULL AUTO_INCREMENT,
    name       VARCHAR(100) NOT NULL,
    price      INT          NOT NULL,
    PRIMARY KEY (product_id)
);

CREATE TABLE product_detail (
    product_id  BIGINT NOT NULL,           -- 기본 키이면서 외래 키
    description TEXT   NOT NULL,
    PRIMARY KEY (product_id),
    CONSTRAINT fk_product_detail_product
        FOREIGN KEY (product_id) REFERENCES product (product_id)
);

    기본 키는 이미 유일하므로 UNIQUE 제약을 따로 걸 필요가 없고, 외래 키 검사에 쓸 인덱스도 기본 키 인덱스가 맡는다. 추가 인덱스가 하나도 없다. 상세 행은 상품 행과 같은 번호를 가지므로, InnoDB에서 두 테이블의 클러스터형 인덱스는 같은 키 순서로 정렬된다. 상품 번호 범위로 두 테이블을 함께 읽으면 양쪽 모두 연속된 구간을 읽는다. 대신 이 방식은 상세 행이 상품 없이는 존재할 수 없다는 사실, 곧 상세가 상품에 식별자를 기대는 관계를 표현한다. 사원과 노트북처럼 각자 생명주기가 있는 엔티티에는 맞지 않는다. 노트북의 기본 키를 사원 번호로 만들면, 노트북을 다른 사원에게 넘기는 순간 노트북의 기본 키가 바뀐다. 부모의 기본 키를 자기 기본 키에 포함하는 관계를 식별 관계라고 하는데, 그 판단 기준은 06회에서 다룬다.

    설계 A: 대상 테이블에 FK               설계 B: 주 테이블에 FK
┌─────────────┐   ┌──────────────────┐  ┌──────────────────┐   ┌─────────────┐
│ employee    │   │ laptop           │  │ employee         │   │ laptop      │
│ PK id       │◀──│ FK employee_id UQ│  │ FK laptop_id  UQ │──▶│ PK id       │
└─────────────┘   └──────────────────┘  └──────────────────┘   └─────────────┘

공유 기본 키: 한 엔티티를 나눈 일대일
┌─────────────┐   ┌─────────────────────────┐
│ product     │   │ product_detail          │
│ PK id       │◀──│ PK = FK product_id      │   (UNIQUE를 따로 두지 않는다)
└─────────────┘   └─────────────────────────┘
    외래 키를 대상 테이블에 두는 설계, 주 테이블에 두는 설계, 기본 키를 공유하는 설계를 나란히 놓고 화살표 방향과 UNIQUE 표시의 위치 차이를 보여 준다. 흰 배경의 깔끔한 기술 다이어그램. 가로로 세 칸을 나눈다. 왼쪽 칸 제목 "설계 A: 대상 테이블에 FK" — 위쪽에 "employee" 상자(열: employee_id PK, name), 아래쪽에 "laptop" 상자(열: laptop_id PK, serial_no, employee_id FK UQ). laptop의 employee_id에서 employee의 employee_id로 화살표. 가운데 칸 제목 "설계 B: 주 테이블에 FK" — 위쪽 "employee" 상자(열: employee_id PK, name, laptop_id FK UQ), 아래쪽 "laptop" 상자(열: laptop_id PK, serial_no). employee의 laptop_id에서 laptop의 laptop_id로 화살표. 오른쪽 칸 제목 "공유 기본 키" — 위쪽 "product" 상자(product_id PK), 아래쪽 "product_detail" 상자(product_id PK·FK, description). 아래에서 위로 화살표. 각 칸 아래에 작은 주석: 왼쪽 "UNIQUE가 일대일을 만든다", 가운데 "NULL은 여러 개 허용", 오른쪽 "추가 인덱스 없음". 외래 키 열은 주황색, 기본 키 열은 파란색으로 강조. 일대일은 외래 키에 UNIQUE를 더해 만든다. 독립된 두 엔티티는 외래 키를 어느 쪽에 둘지 고르고, 한 엔티티를 나눈 경우는 기본 키를 공유할 수 있다.

    외래 키의 위치가 SQL에 남기는 차이

    두 설계는 같은 업무 규칙을 표현하지만, 그 규칙 위에서 일하는 SQL의 모양이 다르다. 조회, 교체, 맞바꾸기, 삭제를 차례로 비교해 보자.

    조회: 관계가 있는지 알려면 어디를 읽어야 하나

    "사원 목록과 각 사원의 노트북 지급 여부"를 보여 주는 화면을 생각하자. 설계 B에서는 사원 테이블만 읽으면 된다. laptop_id가 NULL이면 지급받지 않은 것이고, 값이 있으면 지급받은 것이다. 설계 A에서는 사원 테이블만으로는 알 수 없다. 노트북 테이블에서 employee_id가 그 사원인 행이 있는지 찾아야 한다.

    -- 설계 B: 주 테이블 한 곳만 읽는다
SELECT employee_id, name, laptop_id IS NOT NULL AS has_laptop
  FROM employee;

-- 설계 A: 대상 테이블을 찾아가야 한다
SELECT e.employee_id, e.name, l.laptop_id IS NOT NULL AS has_laptop
  FROM employee e
  LEFT JOIN laptop l ON l.employee_id = e.employee_id;

    설계 A의 조인은 사원 한 명마다 uk_laptop_employee 인덱스를 한 번씩 찾는 일이다. UNIQUE 인덱스이므로 찾으면 정확히 한 행이고, 비용이 크지는 않다. 하지만 사원 테이블만으로는 관계의 존재를 알 수 없다는 사실은 남는다. 이 차이는 데이터베이스 바깥, 곧 객체로 매핑하는 계층에서 더 크게 드러난다. 사원 객체를 만들 때 노트북 필드에 "나중에 읽을 대리 객체(프록시)"를 넣을지 null을 넣을지 정하려면 노트북이 있는지 알아야 하는데, 설계 A에서는 그것을 알기 위해 노트북 테이블을 조회해야 한다. 반대 방향 질문 "이 노트북은 누가 쓰는가"는 정반대다. 설계 A에서는 노트북 행 하나로 답이 나오고, 설계 B에서는 uk_employee_laptop으로 사원 테이블을 찾아야 한다.

    교체: 문장의 순서가 제약과 부딪힌다

    사원 1이 노트북 10을 반납하고, 창고에 있던 노트북 12를 새로 받는다. 설계 A에서는 노트북 두 행을 고쳐야 한다.

    -- 설계 A: 이 순서여야 한다
UPDATE laptop SET employee_id = NULL WHERE laptop_id = 10;  -- 먼저 옛 배정을 끊고
UPDATE laptop SET employee_id = 1    WHERE laptop_id = 12;  -- 새 배정을 건다

-- 설계 B: 사원 행 하나만 고친다
UPDATE employee SET laptop_id = 12 WHERE employee_id = 1;

    설계 A에서 두 문장의 순서를 바꾸면 두 번째 문장이 먼저 실행될 때 노트북 10과 12가 모두 사원 1을 가리키게 되어 UNIQUE 위반으로 실패한다. 한 트랜잭션으로 묶었다고 해서 검사가 커밋까지 미뤄지지 않는다. 설계 B에서는 사원 행 하나의 값만 바꾸므로 순서 문제가 없다. 단, 노트북 12가 이미 다른 사원에게 배정되어 있다면 uk_employee_laptop 위반으로 실패한다. 이것도 의도한 동작이다.

    맞바꾸기: 한 문장으로도 실패한다

    사원 1(노트북 10)과 사원 2(노트북 11)가 노트북을 서로 바꾸기로 했다. 설계 B에서 한 문장으로 써 보자.

    UPDATE employee
   SET laptop_id = CASE employee_id WHEN 1 THEN 11 WHEN 2 THEN 10 END
 WHERE employee_id IN (1, 2);
-- ERROR 1062 (23000): Duplicate entry '11' for key 'employee.uk_employee_laptop'   (MySQL 8.0.46·8.4.13에서 실행)

    이 문장은 MySQL에서 중복 키 오류로 실패한다. MySQL 매뉴얼은 여러 행을 고치는 SQL 문에서 UNIQUE 제약과 외래 키 제약이 문장 전체가 끝난 뒤가 아니라 행 단위로 검사된다고 설명한다(FOREIGN KEY Constraint Differences). 사원 1의 행을 먼저 고치면 그 순간 사원 1과 사원 2가 모두 노트북 11을 가리키고, 사원 2를 먼저 고쳐도 마찬가지로 노트북 10이 겹친다. 어느 행부터 처리하든 첫 행에서 충돌하므로 결과는 실행 순서와 무관하게 실패다. 해법은 한쪽을 잠시 비워 두는 것이다.

    START TRANSACTION;
UPDATE employee SET laptop_id = NULL WHERE employee_id = 1;  -- 사원 1의 노트북 10을 비운다
UPDATE employee SET laptop_id = 10   WHERE employee_id = 2;  -- 이제 10은 비어 있다
UPDATE employee SET laptop_id = 11   WHERE employee_id = 1;  -- 이제 11도 비어 있다
COMMIT;

    NULL을 여러 개 허용하는 UNIQUE 인덱스의 성질이 여기서 임시 자리 역할을 한다. 같은 문제는 설계 A의 laptop.employee_id에서도 똑같이 생긴다. 맞바꾸기의 어려움은 외래 키의 위치가 아니라 "UNIQUE가 행 단위로 즉시 검사된다"는 MySQL의 동작에서 오기 때문이다.

    삭제: 누가 누구를 붙잡고 있나

    외래 키는 참조하는 쪽(자식)이 참조되는 쪽(부모)을 붙잡는 구조다. 설계 A에서 노트북이 사원을 붙잡으므로, 노트북이 배정된 사원 행은 지울 수 없다. 퇴사 처리 전에 노트북을 회수(employee_id를 NULL로)해야 하고, 그 순서는 업무 순서와도 맞는다. ON DELETE SET NULL을 선언하면 사원 행을 지울 때 노트북의 배정이 자동으로 풀린다. 설계 B에서는 사원이 노트북을 붙잡으므로, 누군가에게 배정된 노트북 행을 지울 수 없다. 노트북을 폐기하려면 먼저 그 사원의 laptop_id를 비워야 한다. 어느 쪽 행을 지우는 일이 업무에서 더 자주, 더 자연스럽게 일어나는지가 외래 키 방향과 맞물린다.

    양쪽 모두 필수인 일대일은 선언할 수 없다

    마지막으로 극단적인 경우를 보자. "모든 사원은 반드시 노트북을 한 대 가지고, 모든 노트북은 반드시 사원 한 명에게 배정되어 있다." 양쪽 참여가 모두 필수인 일대일이다. 외래 키를 양쪽에 두고 둘 다 NOT NULL로 선언하면 될 것 같다. 그러나 이 스키마에는 첫 행을 넣을 수 없다. 사원 행을 넣으려면 그 사원이 가리킬 노트북 행이 이미 있어야 하고, 노트북 행을 넣으려면 그 노트북이 가리킬 사원 행이 이미 있어야 한다. MySQL은 외래 키를 즉시 검사하고 커밋 시점까지 미루지 않는다. 매뉴얼은 SQL 표준의 기본 동작이 문장 전체를 처리한 뒤 제약을 검사하는 지연 검사(deferred checking)인 것과 달리 MySQL은 행 단위로 즉시 검사하고 트랜잭션 커밋까지 미루지 않는다고 밝히고, InnoDB에서 NO ACTION은 RESTRICT와 같다고 설명한다. 그러니 한 트랜잭션 안에서 두 행을 차례로 넣는 방법도 통하지 않는다. MySQL 8.0.46과 8.4.13에서 foreign_key_checks를 잠시 꺼 두 테이블을 순환 외래 키(NOT NULL)로 만든 뒤 검사를 다시 켜고, START TRANSACTION 안에서 사원 행 (1, 10)과 노트북 행 (10, 1)을 차례로 넣어 보면 두 문장 모두 오류 1452(Cannot add or update a child row: a foreign key constraint fails)로 거부된다.

    foreign_key_checks 변수를 꺼서 넣는 방법은 있다. 하지만 매뉴얼에 따르면 이 변수를 다시 켜도 그동안 들어간 행을 다시 검사하지 않는다. 일상적인 쓰기 경로에 쓸 방법이 아니다. 그리고 CHECK 제약은 MySQL 8.0.16부터 실제로 검사되지만, 다른 테이블의 열이나 서브쿼리를 식에 쓸 수 없으므로 "상대 테이블에 짝이 있다"를 표현하지 못한다. MySQL 8.0.46과 8.4.13에서 실행해 보면, 앞의 순환 외래 키 테이블에 검사를 끈 채 존재하지 않는 노트북 999를 가리키는 사원 행을 넣고 검사를 다시 켜도 그 행은 오류 없이 그대로 남았다. 노트북 테이블을 서브쿼리로 읽는 CHECK (a IN (SELECT laptop_id FROM ...))는 테이블을 만드는 단계에서 오류 3815(An expression of a check constraint '...' contains disallowed function.)로 거부되었다. 결론은 둘 중 하나다. 양쪽 모두 필수라면 대개 그것은 한 엔티티이므로 한 테이블로 합친다. 합칠 수 없다면 한쪽 방향만 외래 키로 강제하고, 반대 방향의 필수 참여는 두 행을 한 트랜잭션에서 넣는 애플리케이션 코드가 지킨다. 04회에서 본 "여럿 쪽의 필수 참여는 선언적 제약으로 강제되지 않는다"와 같은 종류의 한계다.

    [실습] 관계 확장의 유연성: 업무 규칙이 바뀌는 날

    이제 사원과 노트북의 업무 규칙이 바뀌는 상황을 실습해 보자. 일대일은 업무 규칙 가운데 가장 잘 깨지는 규칙에 속한다. "하나"라는 숫자는 정책의 산물인 경우가 많고, 정책은 바뀐다. 두 가지 변화를 차례로 적용한다.

    • 변화 1: 개발 직군에게는 노트북을 두 대(운영체제가 다른 두 대)까지 지급한다. 이제 사원 한 명에 노트북이 여러 대일 수 있다. 사원 1 : 노트북 N이다.
    • 변화 2: 교대 근무 부서는 노트북 한 대를 여러 사원이 나눠 쓴다. 이제 노트북 한 대에 사원이 여러 명일 수 있다. 노트북 1 : 사원 N이다.

    변화 1을 설계 A에 적용하기

    설계 A는 노트북 테이블에 employee_id가 있다. 사원 1 : 노트북 N은 04회의 규칙대로라면 외래 키가 여럿 쪽, 곧 노트북 테이블에 있어야 하는 관계다. 외래 키는 이미 올바른 자리에 있다. 할 일은 UNIQUE 제약을 푸는 것뿐이다. 그런데 순서를 잘못 잡으면 오류가 난다.

    ALTER TABLE laptop DROP INDEX uk_laptop_employee;
-- ERROR 1553 (HY000): Cannot drop index 'uk_laptop_employee': needed in a foreign key constraint
-- (MySQL 8.0.46·8.4.13에서 실행)

    앞에서 본 대로, 이 UNIQUE 인덱스는 외래 키 검사에 쓰이는 유일한 인덱스이기도 하다. InnoDB는 외래 키를 강제할 수 있는 마지막 인덱스를 지우려 하면 오류 1553(ER_DROP_INDEX_FK)을 낸다. 외래 키가 쓸 일반 인덱스를 먼저 만들고, 그다음 UNIQUE 인덱스를 지운다.

    ALTER TABLE laptop ADD INDEX idx_laptop_employee (employee_id);  -- 외래 키가 쓸 새 인덱스
ALTER TABLE laptop DROP INDEX uk_laptop_employee;                -- 이제 지울 수 있다

    두 문장의 비용을 보자. MySQL 8.0 매뉴얼의 온라인 DDL 표에 따르면 보조 인덱스 추가는 테이블을 다시 만들지 않는 in-place 연산이고 동시 DML을 허용한다. 인덱스 삭제도 in-place이며 메타데이터만 바꾼다(Online DDL Operations). 기존 행의 데이터는 한 바이트도 옮기지 않는다. MySQL 8.0.46과 8.4.13에서 두 문장에 ALGORITHM=INPLACE, LOCK=NONE을 붙여 실행해도 둘 다 오류 없이 수행된다(지원하지 않는 알고리즘을 지정하면 MySQL은 문장을 거부한다). 사원 1에게 노트북 11을 추가로 배정하는 UPDATE laptop SET employee_id = 1 WHERE laptop_id = 11이 이제 성공한다. 애플리케이션에서 "사원의 노트북"을 한 건으로 받던 코드는 여러 건을 받도록 고쳐야 하지만, 스키마 변경 자체는 인덱스 두 개를 바꾸는 것으로 끝난다.

    변화 1을 설계 B에 적용하기

    설계 B는 사원 테이블에 laptop_id 칸이 하나 있다. 칸 하나에는 노트북 하나만 들어간다. UNIQUE를 풀면 "노트북 한 대를 여러 사원이 가리킬 수 있다"가 될 뿐, "사원 한 명이 노트북 여러 대를 가리킨다"는 표현할 수 없다. 외래 키가 엉뚱한 쪽에 있으므로 반대쪽으로 옮겨야 한다.

    -- 1) 노트북 쪽에 새 외래 키 열을 만든다
ALTER TABLE laptop ADD COLUMN employee_id BIGINT NULL;

-- 2) 기존 배정을 옮겨 적는다
UPDATE laptop l
  JOIN employee e ON e.laptop_id = l.laptop_id
   SET l.employee_id = e.employee_id;

-- 3) 새 외래 키를 건다 (employee_id 인덱스는 자동으로 생긴다)
ALTER TABLE laptop
  ADD CONSTRAINT fk_laptop_employee
      FOREIGN KEY (employee_id) REFERENCES employee (employee_id);

-- 4) 옛 외래 키와 열을 지운다
ALTER TABLE employee DROP FOREIGN KEY fk_employee_laptop;
ALTER TABLE employee DROP COLUMN laptop_id;

    단계마다 비용이 다르다. 1단계의 열 추가는 MySQL 8.0.12부터 기본 알고리즘이 INSTANT라 메타데이터만 바꾼다(8.0.29 이전에는 맨 뒤 열로만 즉시 추가할 수 있었다). 2단계는 배정된 노트북 행 전부를 고치는 DML이다. 행 수만큼 잠금과 redo·undo 로그가 생긴다. 3단계가 가장 무겁다. 매뉴얼은 외래 키 추가가 foreign_key_checks가 꺼져 있을 때만 INPLACE로 수행되고, 그렇지 않으면 COPY 알고리즘만 지원된다고 적고 있다. COPY는 원본 테이블의 데이터를 새 테이블로 한 행씩 복사하며 그동안 동시 DML을 허용하지 않는다. 검사를 끄고 INPLACE로 추가하면 빠르지만, 그 경우 기존 행이 외래 키를 만족하는지는 검사되지 않는다. MySQL 8.0.46과 8.4.13에서 검사를 켠 채 3단계에 ALGORITHM=INPLACE를 붙이면 ERROR 1846 (0A000): ALGORITHM=INPLACE is not supported. Reason: Adding foreign keys needs foreign_key_checks=OFF. Try ALGORITHM=COPY.로 거부되고, ALGORITHM=COPY로는 수행되며 fk_laptop_employee라는 이름의 employee_id 인덱스가 자동으로 생긴다. 1단계의 열 추가는 ALGORITHM=INSTANT를 붙여도 그대로 수행된다. 4단계에서 열을 지우면, 그 열만으로 이루어진 인덱스 uk_employee_laptop도 함께 사라진다(매뉴얼의 ALTER TABLE 설명대로 인덱스의 모든 열이 지워지면 인덱스도 지워진다). MySQL 8.0.46과 8.4.13에서 확인하면 DROP FOREIGN KEY 뒤에도 uk_employee_laptop은 남아 있고, DROP COLUMN laptop_id 뒤의 SHOW CREATE TABLE employee에는 PRIMARY KEY만 남는다.

    DDL보다 더 비싼 것은 그 사이의 시간이다. 2단계와 4단계 사이에 새로 배정이 일어나면 옛 열과 새 열 중 한쪽에만 기록된다. 서비스를 멈추지 않으려면 애플리케이션이 일정 기간 두 열에 함께 쓰고(이중 쓰기), 읽기를 새 열로 옮긴 뒤, 옛 열을 지우는 여러 번의 배포가 필요하다. 그리고 employee.laptop_id를 읽던 모든 쿼리를 찾아 고쳐야 한다. 설계 A가 인덱스 두 개로 끝낸 변화가 설계 B에서는 데이터 이관 작업이 된다.

    변화 2는 정확히 반대다

    노트북 1 : 사원 N에서 여럿 쪽은 사원이다. 외래 키는 사원 테이블에 있어야 한다. 이번에는 설계 B가 이미 올바른 자리에 외래 키를 두고 있으므로 uk_employee_laptop을 일반 인덱스로 바꾸는 것으로 끝나고, 설계 A가 외래 키를 옮기는 이관 작업을 해야 한다. 두 변화를 나란히 놓으면 규칙이 보인다. 나중에 "여럿"이 될 가능성이 있는 쪽에 외래 키를 두면, 일대일에서 일대다로의 확장은 UNIQUE 제약 하나를 푸는 일이 된다.

    업무 변화설계 A (노트북에 FK)설계 B (사원에 FK)
    변화 1: 사원 1 : 노트북 N일반 인덱스 추가 후 UNIQUE 인덱스 삭제. 둘 다 in-place, 데이터 이동 없음노트북에 열 추가, 데이터 이관, 외래 키 추가(검사 켜면 COPY), 옛 열 삭제, 쿼리 수정
    변화 2: 노트북 1 : 사원 N사원에 열 추가, 데이터 이관, 외래 키 추가, 옛 열 삭제, 쿼리 수정일반 인덱스 추가 후 UNIQUE 인덱스 삭제
    변화 1과 2가 함께: 다대다어느 설계도 그대로 쓸 수 없다. 연결 테이블을 새로 만들고 기존 배정을 옮긴다
    같은 업무 변화(사원 한 명에 노트북 여러 대)가 설계 A에서는 UNIQUE 하나를 푸는 일이고 설계 B에서는 외래 키를 반대편으로 옮기는 이관 작업이라는 대비를 보여 준다. 흰 배경의 비교 다이어그램. 위쪽 가운데에 말풍선 "변화: 사원 한 명에 노트북 여러 대". 아래로 두 갈래. 왼쪽 갈래 제목 "설계 A: 노트북에 FK" — laptop 상자 안의 employee_id 열 옆에 "UQ" 표시가 X로 지워지는 모습, 아래에 초록색 체크와 함께 "인덱스 교체로 끝" 라벨, 상자 두 개(employee, laptop) 사이 화살표는 그대로. 오른쪽 갈래 제목 "설계 B: 사원에 FK" — employee 상자의 laptop_id 열이 회색으로 지워지고, laptop 상자에 employee_id 열이 새로 생기는 모습, 두 상자 사이에 번호가 붙은 네 단계 화살표 "1 열 추가", "2 데이터 이관", "3 FK 추가", "4 옛 열 삭제". 아래에 주황색 경고 아이콘과 "이관 작업" 라벨. 전체 아래쪽에 작은 글씨 "나중에 여럿이 될 쪽에 FK를 둔다". 외래 키가 이미 "여럿"이 될 쪽에 있으면 확장은 UNIQUE 하나를 푸는 일이고, 반대쪽에 있으면 열 추가, 데이터 이관, 외래 키 재생성이 따른다.

    실습에서 끌어낼 교훈은 "외래 키는 대상 테이블에 두어라"나 "주 테이블에 두어라" 같은 고정된 답이 아니다. 업무 담당자에게 물어야 할 질문이다. "이 관계에서 앞으로 숫자가 늘어날 수 있는 쪽은 어디인가?" 사원과 노트북이라면 한 사람이 여러 대를 받는 쪽이 더 그럴듯한가, 한 대를 여러 사람이 나눠 쓰는 쪽이 더 그럴듯한가. 답이 분명하지 않다면 일대일이 사실 시점의 제약일 가능성도 함께 따져 본다. "지금 이 순간 사원 한 명에 노트북 한 대"는 일대일이지만, "누가 언제부터 언제까지 어떤 노트북을 썼는가"라는 이력은 처음부터 다대다다. 이력이 필요하다면 일대일 외래 키는 현재 상태만 담고, 이력은 뒤에서 볼 연결 테이블 형태의 배정 테이블에 쌓는 편이 낫다.

    주 테이블에 외래 키를 둘 때: 무엇을 얻고 무엇을 내주나

    확장의 유연성만 보면 "여럿이 될 쪽에 둔다"가 답이지만, 미래가 분명하지 않을 때는 지금의 사용 방식이 기준이 된다. 주 테이블에 외래 키를 두는 설계 B를 장단점으로 정리해 보자.

    얻는 것. 첫째, 주 테이블만 읽으면 관계가 있는지 알 수 있다. 업무 흐름이 대부분 주 테이블에서 시작한다면 가장 흔한 질문이 조인 없이 끝난다. 둘째, 관계를 맺고 끊는 일이 주 테이블 행 하나의 갱신이다. 앞에서 본 교체가 한 문장으로 끝났다. 셋째, 객체 모델과 방향이 맞는다. 자바 코드에서 Employee가 Laptop을 참조하는 필드를 가지는 것이 자연스럽다면, 외래 키도 사원 테이블에 있을 때 매핑이 단순해진다. JPA의 용어로는 외래 키를 가진 쪽이 연관관계의 주인(owning side)이고, 주 엔티티가 주인이 된다.

    이 셋째 항목은 실제 동작 차이로 이어진다. 앞에서 설계 A에서는 사원 행만으로 노트북 유무를 알 수 없다고 했다. Hibernate ORM 6.4 사용자 가이드의 @OneToOne 절은 양방향 일대일에서 외래 키를 갖지 않은 부모 쪽(mappedBy 쪽)을 지연 로딩으로 지정해도, 연관이 null인지 아닌지 알 수 없기 때문에 Hibernate가 그 요청을 지킬 수 없다고 설명한다. 그래서 그 쪽의 지연 로딩을 보장하려면 바이트코드 향상(bytecode enhancement)을 켜야 한다고 적고 있다. 데이터베이스 수준에서 본 "관계의 존재를 알려면 대상 테이블을 읽어야 한다"는 사실이 ORM에서는 "지연 로딩이 기대대로 되지 않는다"로 나타나는 것이다. 사원 목록을 읽을 때마다 사원 수만큼 노트북 조회가 따라 나가는 N+1 형태가 생길 수 있다.

    내주는 것. 첫째, 앞의 실습에서 본 대로 대상 쪽이 "여럿"이 되는 변화에 약하다. 둘째, 지급받지 않은 사원을 표현하려면 외래 키 열이 NULL을 허용해야 한다. 참여가 선택인 일대일이라면 주 테이블의 많은 행이 NULL을 가진다. 셋째, 대상 행을 지울 때 주 테이블의 참조를 먼저 끊어야 한다. 넷째, 대상이 주 테이블에 기대어 존재하는 관계라면 데이터베이스 관점과 어긋난다. 상품 상세가 상품을 가리키는 것이 자연스럽지, 상품이 상세를 가리키는 것은 "부모가 자식을 붙잡는" 구조가 된다. 상품을 먼저 넣고 상세를 넣는 자연스러운 순서가 깨지고, 상품 행을 넣은 뒤 상세 번호로 다시 갱신해야 한다.

    대상 테이블에 외래 키를 두는 설계 A는 이 목록을 뒤집은 것이다. 데이터베이스 관점에서 전통적인 형태이고, 대상 쪽이 여럿이 되는 변화에 강하며, 주 테이블의 행을 건드리지 않고 관계를 추가할 수 있다. 대신 주 테이블에서 시작하는 조회는 대상 테이블을 거쳐야 한다. 판단 기준을 표로 모으면 다음과 같다.

    질문그렇다면
    대상 쪽이 나중에 여럿이 될 가능성이 있는가대상 테이블에 FK (설계 A)
    주 쪽이 나중에 여럿이 될 가능성이 있는가주 테이블에 FK (설계 B)
    대상이 주에 기대어서만 존재하는가 (한 엔티티를 나눈 경우)공유 기본 키, 또는 대상 테이블에 FK
    주 테이블에서 시작하는 조회가 대부분이고 관계 유무를 자주 확인하는가주 테이블에 FK가 조인을 줄인다
    양쪽 참여가 모두 필수이고 늘 함께 읽히는가나누지 말고 한 테이블로 합친다

    표의 기준이 서로 부딪칠 때가 있다. 조회는 주 테이블 중심인데 확장 가능성은 대상 쪽에 있을 수 있다. 그때는 어느 비용이 더 자주, 더 크게 드는지를 따진다. 조회의 조인 비용은 UNIQUE 인덱스 탐색 한 번이라 작고 매번 든다. 확장의 이관 비용은 크고 한 번 든다. 하지만 그 한 번은 서비스가 커진 뒤, 데이터가 가장 많을 때 찾아온다.

    다대다 관계: 관계형 모델의 한계를 정면으로 만나다

    이제 반대편 극단으로 가자. 영화와 배우를 기록한다. 영화 한 편에는 배우가 여럿 출연한다. 배우 한 명은 영화 여러 편에 출연한다. 02회에서 본 방법대로 양방향으로 물어보면 두 질문 모두 "여럿"이라고 답한다. 다대다 관계다. 일대일에서는 외래 키를 어느 쪽에 둘지가 문제였다면, 다대다에서는 어느 쪽에도 둘 수 없다는 것이 문제다. 왜 둘 수 없는지를 실제로 시도해 보며 확인하자. 실패하는 방식을 정확히 알아야 해법이 왜 그 모양인지 이해된다.

    시도 1: 한쪽 테이블에 외래 키 열을 둔다

    영화 테이블에 actor_id 열을 둔다. 영화 1에 배우 10과 11이 출연했다면 영화 1의 행이 두 개 필요하다. (1, '항해', 10)과 (1, '항해', 11)이다. 그러면 movie_id는 더 이상 행을 유일하게 구별하지 못해 기본 키 자격을 잃는다. 기본 키를 (movie_id, actor_id)로 바꾸면 행은 구별되지만, 이 테이블은 이제 "영화"가 아니라 "영화와 배우의 짝"을 담는 테이블이 되었고, 영화 제목이 출연 배우 수만큼 반복된다. 제목을 고치려면 여러 행을 고쳐야 하고, 하나라도 빠지면 같은 영화가 두 제목을 가진다. 01회에서 본 갱신 이상이다. 배우가 아직 정해지지 않은 영화는 actor_id가 NULL인 행으로 넣어야 하는데, 그러면 기본 키 열에 NULL이 들어가므로 그것도 안 된다. 배우 테이블 쪽에 movie_id를 두어도 대칭적으로 같은 문제가 생긴다.

    시도 2: 열을 여러 개 만든다

    영화 테이블에 actor1_id, actor2_id, actor3_id를 둔다. 행은 영화 하나에 하나로 유지된다. 그러나 출연 배우의 최대 수가 스키마에 박힌다. 네 번째 배우가 생기면 ALTER TABLE이 필요하다. "배우 10이 출연한 영화"를 찾으려면 WHERE actor1_id = 10 OR actor2_id = 10 OR actor3_id = 10처럼 세 열을 모두 뒤져야 하고, 세 열 각각에 인덱스를 따로 만들어야 그 조회가 빨라진다. 배우가 한 명인 영화는 두 칸이 NULL이다. 같은 의미의 값이 여러 열에 흩어진 이 형태를 반복 그룹(repeating group)이라고 부르고, 07회의 제1정규형이 정면으로 다루는 대상이다.

    시도 3: 한 칸에 여러 값을 넣는다

    영화 테이블에 actor_ids VARCHAR(200) 열을 두고 '10,11'처럼 쉼표로 이어 적는다. 열 개수 제한은 사라진 것 같지만, 칸 하나에 값 하나라는 원칙을 문자열로 우회했을 뿐이다. 그 대가는 이렇다. 첫째, 외래 키를 걸 수 없다. 데이터베이스에게 이 칸은 문자열 하나라서 배우 10이 실제로 존재하는지 검사할 방법이 없다. 배우 10을 지워도 문자열 안의 10은 그대로 남는다. 둘째, 조회가 틀리거나 느리다. actor_ids LIKE '%1%'로 배우 1을 찾으면 10, 11, 21까지 걸린다. 정확히 찾으려면 FIND_IN_SET('1', actor_ids) 같은 함수를 써야 하는데, 함수에 감싼 열은 일반 인덱스로 찾을 수 없으므로 모든 행을 읽는다. 셋째, 동시 수정에 약하다. 배우를 하나 추가하려면 문자열을 읽고, 이어 붙이고, 다시 써야 한다. 두 트랜잭션이 같은 영화에 동시에 배우를 추가하면서 잠금 없이 읽으면 나중에 쓴 쪽이 먼저 쓴 쪽의 추가를 덮어쓴다. 행 단위로 기록했다면 서로 다른 행의 INSERT였을 일이 한 행을 두고 다투는 일이 된다.

    시도 4: JSON 배열에 넣는다

    MySQL의 JSON 열에 [10, 11]을 넣는 방법은 시도 3보다 낫다. 배열의 원소가 구조적으로 구분되고, MySQL 8.0.17부터 InnoDB는 JSON 배열에 다중값 인덱스(multi-valued index)를 만들 수 있다. 일반 인덱스가 데이터 행 하나에 인덱스 레코드 하나를 두는 것과 달리, 다중값 인덱스는 행 하나에 인덱스 레코드를 여럿 둘 수 있다(CREATE INDEX). 그래서 "배우 10이 출연한 영화"를 인덱스로 찾을 수 있다. 그러나 외래 키는 열의 값을 부모 테이블의 키와 비교하는 제약이라 배열 안 원소 하나하나가 배우 테이블에 있는지 검사해 주지 않는다. 배역 이름처럼 짝마다 달라지는 값을 붙일 자리도 마땅치 않고, 원소를 추가할 때 한 행을 고쳐야 한다는 점은 시도 3과 같다.

    실패의 공통 원인

    네 시도는 모두 같은 벽에 부딪혔다. 외래 키는 칸 하나의 값이고, 칸 하나는 부모 하나만 가리킨다. 다대다는 "영화 하나가 가리키는 배우가 여럿"이므로 영화 쪽 칸 하나로 담을 수 없고, 배우 쪽도 마찬가지다. 자바의 객체 세계와 비교하면 차이가 분명하다. 힙에 있는 Movie 객체는 List 필드를 가질 수 있다. ArrayList는 내부 배열에 참조를 원하는 만큼 담고, 크기가 부족하면 더 큰 배열을 만들어 옮긴다. 객체 하나가 가변 길이의 참조 묶음을 소유하는 것이 자연스럽다. 테이블의 행은 정해진 열과 원자값으로 이루어지고, 행이 다른 행을 가리키는 수단은 키 값뿐이다. 가변 길이의 참조 묶음을 한 행 안에 둘 수 없다.

    그렇다면 관계형 모델은 다대다를 어떻게 담는가. 다시 보면 "영화와 배우의 출연 관계"는 수학적으로 (영화, 배우) 짝의 집합이다. 그리고 관계형 모델에서 릴레이션, 곧 테이블이란 바로 튜플의 집합이다. 짝의 집합은 열이 두 개인 테이블로 그대로 옮겨진다. 다대다를 한 테이블의 열로 표현하려 했던 것이 잘못이었고, 관계 자체를 하나의 테이블로 만들면 된다. "관계형 모델의 한계"란 외래 키 하나로 다대다를 직접 표현할 수 없다는 뜻이지, 다대다를 담을 수 없다는 뜻이 아니다. 오히려 관계를 행으로 만드는 것이 가장 관계형다운 해법이다.

    연결 테이블: 관계를 행으로 만든다

    두 엔티티의 다대다 관계를 담는 테이블을 연결 테이블(junction table, link table)이라고 부른다. 조인 테이블, 교차 테이블이라고도 한다. 연결 테이블의 행 하나는 "영화 m에 배우 a가 출연했다"는 사실 하나다. 열은 최소한 두 부모의 기본 키를 가리키는 외래 키 두 개다.

    CREATE TABLE movie (
    movie_id BIGINT       NOT NULL AUTO_INCREMENT,
    title    VARCHAR(200) NOT NULL,
    PRIMARY KEY (movie_id)
);

CREATE TABLE actor (
    actor_id BIGINT       NOT NULL AUTO_INCREMENT,
    name     VARCHAR(100) NOT NULL,
    PRIMARY KEY (actor_id)
);

CREATE TABLE movie_actor (
    movie_id BIGINT NOT NULL,
    actor_id BIGINT NOT NULL,
    PRIMARY KEY (movie_id, actor_id),
    CONSTRAINT fk_movie_actor_movie FOREIGN KEY (movie_id) REFERENCES movie (movie_id),
    CONSTRAINT fk_movie_actor_actor FOREIGN KEY (actor_id) REFERENCES actor (actor_id)
);

    이 구조를 04회의 규칙으로 다시 읽어 보자. 영화 하나에 movie_actor 행은 여럿, movie_actor 행 하나에 영화는 하나다. 영화와 연결 테이블은 일대다이고, 외래 키는 여럿 쪽인 연결 테이블에 있다. 배우와 연결 테이블도 똑같이 일대다다. 다대다 하나가 일대다 둘로 분해되었다. 새로운 규칙이 생긴 것이 아니라, 이미 아는 규칙을 두 번 적용할 수 있도록 가운데에 테이블을 하나 끼운 것이다. 이 분해가 다대다를 다루는 유일한 방법이다.

    기본 키 (movie_id, actor_id)는 같은 짝이 두 번 들어가는 것을 막는다. "영화 1에 배우 10이 출연했다"는 사실이 두 번 기록될 이유가 없으므로 이것이 업무 규칙과 맞는다. 03회에서 다룬 것처럼 연결 테이블에도 대리 키를 기본 키로 둘 수 있는데, 그때는 (movie_id, actor_id)에 UNIQUE 제약을 따로 걸어야 같은 짝의 중복을 막을 수 있다. 대리 키를 기본 키로 둔다고 중복이 막히지는 않는다. 대리 키는 행마다 새 값을 받으므로 같은 짝을 담은 두 행도 서로 다른 행이 되기 때문이다.

    데이터를 넣고 양방향으로 조회해 보자.

    INSERT INTO movie (movie_id, title) VALUES (1, '항해'), (2, '겨울 정거장'), (3, '밤의 도서관');
INSERT INTO actor (actor_id, name)  VALUES (10, '서하람'), (11, '나윤결'), (12, '도시온');
INSERT INTO movie_actor (movie_id, actor_id) VALUES (1, 10), (1, 11), (2, 10), (3, 11), (3, 12);

-- 영화 1의 출연 배우
SELECT a.actor_id, a.name
  FROM movie_actor ma
  JOIN actor a ON a.actor_id = ma.actor_id
 WHERE ma.movie_id = 1;

-- 배우 10의 출연작
SELECT m.movie_id, m.title
  FROM movie_actor ma
  JOIN movie m ON m.movie_id = ma.movie_id
 WHERE ma.actor_id = 10;
    -- 영화 1의 출연 배우 (정렬 순서는 ORDER BY가 없으므로 보장되지 않는다)
actor_id | name
10       | 서하람
11       | 나윤결

-- 배우 10의 출연작
movie_id | title
1        | 항해
2        | 겨울 정거장

    결과 행의 순서는 ORDER BY를 쓰지 않았으므로 SQL이 보장하지 않는다. 화면에 순서가 필요하면 반드시 ORDER BY를 붙인다. 조회 방향이 어느 쪽이든 쿼리의 모양이 대칭이라는 점이 중요하다. 영화에서 배우로 가든, 배우에서 영화로 가든 연결 테이블을 거쳐 반대편 테이블로 간다. 다대다에는 "주인"이 없다.

    삭제는 일대다의 규칙을 따른다. 출연 기록이 있는 영화 행은 movie_actor의 외래 키가 붙잡고 있으므로 바로 지울 수 없다. 연결 행은 양쪽 부모가 모두 있어야 의미가 있으므로, 영화를 지울 때 출연 기록도 함께 지우는 것이 자연스럽다면 ON DELETE CASCADE를 선언할 수 있다. 반대로 출연 기록이 남아 있는 영화는 지우지 못하게 막는 것이 업무 규칙이라면 기본 동작(RESTRICT)을 그대로 둔다.

    영화와 배우의 다대다가 연결 테이블을 사이에 둔 일대다 두 개로 바뀌는 것을 표본 행과 함께 보여 준다. 흰 배경의 기술 다이어그램. 위쪽 띠에는 "개념 모델" 라벨과 함께 "영화" 상자와 "배우" 상자가 선 하나로 이어지고, 선의 양 끝에 까마귀발 기호가 있으며 선 가운데에 "출연" 라벨. 아래쪽 띠에는 "논리 모델" 라벨과 함께 세 개의 표가 가로로 놓인다. 왼쪽 표 "movie"(행: 1 항해, 2 겨울 정거장, 3 밤의 도서관), 가운데 표 "movie_actor"(행: 1-10, 1-11, 2-10, 3-11, 3-12), 오른쪽 표 "actor"(행: 10 서하람, 11 나윤결, 12 도시온). 가운데 표의 movie_id 열 값들에서 왼쪽 표의 해당 행으로, actor_id 열 값들에서 오른쪽 표의 해당 행으로 가는 가는 화살표. 가운데 표 양옆 선에는 "일대다"라는 작은 라벨을 각각 붙인다. 외래 키 열은 주황색, 기본 키 열은 파란색. 다대다는 연결 테이블을 사이에 둔 일대다 두 개로 분해된다. 연결 테이블의 행 하나가 "이 영화에 이 배우가 출연했다"는 사실 하나다.

    한 층 아래: 연결 테이블은 B+Tree 두 개로 양방향을 받는다

    쿼리 모양은 대칭이었지만 InnoDB 안에서 두 방향의 조회는 서로 다른 자료 구조를 탄다. InnoDB 테이블은 기본 키를 키로 하는 클러스터형 인덱스 그 자체이고, 행은 기본 키 순서로 리프 페이지에 놓인다(03회). movie_actor의 기본 키가 (movie_id, actor_id)이므로 리프에는 (1,10) (1,11) (2,10) (3,11) (3,12) 순서로 행이 늘어선다. 같은 영화의 출연 기록은 서로 붙어 있다. "영화 1의 출연 배우"는 이 B+Tree에서 movie_id = 1인 구간의 시작을 찾아 연속으로 읽는 범위 탐색이다.

    반대 방향은 어떤가. 외래 키 fk_movie_actor_movie는 movie_id가 맨 앞에 오는 인덱스를 요구하는데, 기본 키가 그 조건을 만족하므로 따로 인덱스가 생기지 않는다. 외래 키 fk_movie_actor_actor는 actor_id가 맨 앞에 오는 인덱스가 필요하고, 그런 인덱스가 없으므로 MySQL이 actor_id 보조 인덱스를 자동으로 만든다. 그리고 InnoDB는 보조 인덱스의 각 레코드에 기본 키 열을 함께 담는다. MySQL 매뉴얼의 "Use of Index Extensions"는 InnoDB가 모든 보조 인덱스 뒤에 기본 키 열을 덧붙여 다룬다고 설명한다(Use of Index Extensions). 그래서 actor_id 인덱스는 actor_id 다음에 movie_id로 정렬된 목록처럼 동작한다. 리프에는 (10,1) (10,2) (11,1) (11,3) (12,3)이 늘어선다.

    이 덕분에 "배우 10의 출연작 번호"는 보조 인덱스만 읽고 끝난다. 필요한 movie_id가 보조 인덱스 레코드 안에 이미 있으므로 클러스터형 인덱스를 다시 찾아갈 필요가 없다. 인덱스만으로 쿼리에 필요한 열을 모두 얻는 것을 커버링 인덱스(covering index)라고 한다. 결과적으로 기본 키 (movie_id, actor_id)와 자동 생성된 actor_id 인덱스라는 두 개의 B+Tree가 짝의 집합을 양쪽 순서로 한 벌씩 들고 있는 셈이다. (actor_id, movie_id) 인덱스를 따로 만들 필요가 없는 이유이기도 하다. 그런 인덱스는 자동 생성된 인덱스와 사실상 같은 내용을 한 번 더 저장할 뿐이다. MySQL 8.0.46과 8.4.13에서 SHOW CREATE TABLE movie_actor를 보면 자동으로 생긴 인덱스가 KEY `fk_movie_actor_actor` (`actor_id`)로 나타나고, 실행 계획에서도 두 방향 모두 커버링으로 처리된다.

    EXPLAIN SELECT movie_id FROM movie_actor WHERE actor_id = 10;

| id | select_type | table       | partitions | type | possible_keys                | key                  | key_len | ref   | rows | filtered | Extra       |
+----+-------------+-------------+------------+------+------------------------------+----------------------+---------+-------+------+----------+-------------+
|  1 | SIMPLE      | movie_actor | NULL       | ref  | PRIMARY,fk_movie_actor_actor | fk_movie_actor_actor | 8       | const |    2 |   100.00 | Using index |
+----+-------------+-------------+------------+------+------------------------------+----------------------+---------+-------+------+----------+-------------+

+----+-------------+-------------+------------+------+------------------------------+---------+---------+-------+------+----------+-------------+
| id | select_type | table       | partitions | type | possible_keys                | key     | key_len | ref   | rows | filtered | Extra       |
+----+-------------+-------------+------------+------+------------------------------+---------+---------+-------+------+----------+-------------+
|  1 | SIMPLE      | movie_actor | NULL       | ref  | PRIMARY,fk_movie_actor_actor | PRIMARY | 8       | const |    2 |   100.00 | Using index |
+----+-------------+-------------+------------+------+------------------------------+---------+---------+-------+------+----------+-------------+

    Extra의 Using index가 인덱스만 읽고 끝났다는 표시다. 배우 방향은 자동 생성된 fk_movie_actor_actor를, 영화 방향은 클러스터형 인덱스 PRIMARY를 탄다.

    클러스터형 인덱스 PRIMARY (movie_id, actor_id)      보조 인덱스 (actor_id) + 기본 키 열
리프: (1,10) (1,11) | (2,10) | (3,11) (3,12)          리프: (10,1) (10,2) | (11,1) (11,3) | (12,3)
       └─ 영화 1 구간 ─┘                                     └─ 배우 10 구간 ─┘
"영화 1의 배우" → 이 트리의 범위 탐색                 "배우 10의 영화" → 이 트리의 범위 탐색
                                                    (movie_id가 레코드 안에 있으므로 커버링)

    연결 테이블에 다른 열이 생기면 사정이 달라진다. 나중에 배역 이름 같은 열이 연결 테이블에 붙으면, "배우 10의 출연작과 배역"은 보조 인덱스에서 기본 키 값을 얻은 뒤 그 값으로 클러스터형 인덱스를 다시 찾아가 배역 이름을 읽어야 한다. 그래서 복합 기본 키의 열 순서는 어느 방향의 조회가 더 자주, 더 많은 열을 읽는지로 정한다. 그쪽이 클러스터형 인덱스의 연속 구간을 차지하게 하는 것이다.

    대리 키를 기본 키로 쓰면 이 그림이 어떻게 바뀌는지도 보자. 기본 키가 movie_actor_id이고 UNIQUE (movie_id, actor_id)가 있다고 하자. 클러스터형 인덱스는 이제 삽입 순서로 정렬되어 같은 영화의 출연 기록이 흩어질 수 있다. UNIQUE 인덱스는 (movie_id, actor_id, movie_actor_id)를 담으므로 "영화 1의 배우 번호"는 여전히 커버링이다. 그러나 actor_id 외래 키를 위해 자동 생성되는 인덱스는 (actor_id, movie_actor_id)를 담을 뿐 movie_id를 담지 않는다. "배우 10의 영화 번호"를 얻으려면 행마다 클러스터형 인덱스를 다시 찾아가야 한다. MySQL 8.0.46과 8.4.13에서 이 구조로 같은 다섯 행을 넣고 EXPLAIN SELECT movie_id ... WHERE actor_id = 10을 보면 자동 생성된 actor_id 인덱스를 타지만 Extra에 Using index가 없고(NULL), WHERE movie_id = 1로 actor_id를 읽는 쪽은 UNIQUE 인덱스로 Using index다. 이 방향도 커버링으로 만들고 싶다면 (actor_id, movie_id) 인덱스를 직접 만들어야 한다. 복합 기본 키와 대리 키의 선택은 03회에서 본 논리적 고려와 함께, 이처럼 인덱스 구성까지 바꾼다.

    복합 기본 키 (movie_id, actor_id)의 클러스터형 인덱스와 자동 생성된 actor_id 보조 인덱스가 같은 짝의 집합을 서로 다른 순서로 담고 있음을 보여 준다. 흰 배경의 B+Tree 다이어그램 두 개를 좌우로 놓는다. 왼쪽 트리 제목 "클러스터형 인덱스 (movie_id, actor_id)": 루트 노드 하나 아래 리프 노드 세 개, 리프에 순서대로 "1,10" "1,11" / "2,10" / "3,11" "3,12" 칸. "1,10"과 "1,11" 칸을 초록색 띠로 묶고 "영화 1 구간" 라벨. 오른쪽 트리 제목 "보조 인덱스 actor_id (+기본 키)": 루트 하나 아래 리프 세 개, 리프에 "10,1" "10,2" / "11,1" "11,3" / "12,3" 칸. "10,1"과 "10,2" 칸을 파란색 띠로 묶고 "배우 10 구간" 라벨. 오른쪽 트리의 리프 아래에 작은 말풍선 "movie_id가 이미 들어 있다: 커버링". 두 트리 사이 위쪽에 "같은 짝의 집합, 다른 정렬 순서"라는 제목. InnoDB는 보조 인덱스에 기본 키 열을 덧붙이므로, 연결 테이블의 기본 키와 외래 키 인덱스가 짝의 집합을 양방향 순서로 한 벌씩 가진다.

    다대다 관계의 속성: 연결 테이블이 엔티티가 되는 순간

    새 요구가 왔다. 출연 기록마다 배역 이름과 크레딧 순서를 남겨 달라는 것이다. 이 두 값을 어디에 둘지 후보를 하나씩 시험해 보자. 배우 테이블에 둘 수 있을까. 배우 10은 영화 1에서는 선장을, 영화 2에서는 역무원을 연기했다. 배우 행 하나에 배역 칸 하나로는 담을 수 없다. 영화 테이블은 어떨까. 영화 1에서 배우 10은 선장, 배우 11은 항해사다. 역시 영화 행 하나로 담을 수 없다. 배역 이름은 영화만으로도, 배우만으로도 정해지지 않고 영화와 배우의 짝이 정해져야 비로소 정해진다. 이런 값을 관계의 속성이라고 부른다.

    함수 종속(functional dependency)의 말로 하면 (movie_id, actor_id) → role_name이다. 배역 이름은 짝 전체에 종속되고, 짝의 일부에만 종속되지 않는다. 이 종속을 가진 열이 들어갈 자리는 짝을 기본 키로 가진 테이블, 곧 연결 테이블뿐이다. 07회에서 정규화를 다룰 때 이 판정은 "속성이 키 전체에 종속되는가, 키의 일부에 종속되는가"라는 질문으로 정식화된다. 영화 제목처럼 movie_id 하나에만 종속되는 값을 연결 테이블에 두면 그것이 바로 부분 종속이고, 제목이 출연 배우 수만큼 반복되는 시도 1의 문제로 돌아간다.

    속성이 붙는 순간 연결 테이블의 성격이 바뀐다. 처음의 movie_actor는 두 키만 가진 기술적인 연결이었다. 배역과 크레딧 순서를 가지면 그것은 "출연"이라는 업무 개념이고, 그 자체로 조회하고 수정하고 정렬할 대상이다. 그래서 이름도 movie_actor 같은 기계적인 조합 대신 업무 용어로 짓는 편이 좋다. 출연(casting), 수강(enrollment), 주문 항목(order_item), 배정(assignment) 같은 이름은 그 테이블의 행이 어떤 사실인지를 말해 준다. 02회에서 이런 엔티티를 연관 엔티티(associative entity)라고 불렀다.

    같은 짝이 두 번 나오면 식별자를 다시 본다

    속성이 붙으면 식별자도 다시 따져야 한다. 한 배우가 한 영화에서 두 배역을 연기하는 1인 2역을 생각하자. 배우 10이 영화 3에서 쌍둥이 형제를 모두 연기한다. 출연 기록은 두 줄이어야 하는데, 두 줄 모두 (3, 10)이라 기본 키 (movie_id, actor_id)가 두 번째 줄을 거부한다. 짝이 행을 유일하게 구별한다는 전제가 업무 규칙에 의해 깨진 것이다. 길은 두 가지다. 하나는 배역 이름을 기본 키에 넣어 (movie_id, actor_id, role_name)으로 만드는 것이다. 그러나 03회에서 보았듯이 InnoDB의 모든 보조 인덱스 레코드에는 기본 키 열이 들어가므로, 최대 100자짜리 문자열이 기본 키에 들어가면 모든 보조 인덱스가 넓어진다. 배역 이름의 오타를 고치는 일이 기본 키를 바꾸는 일이 되는 것도 문제다. 다른 하나는 출연 기록에 자기 식별자를 주고, 업무 규칙이 말하는 유일성은 UNIQUE 제약으로 따로 거는 것이다.

    CREATE TABLE casting (
    casting_id    BIGINT       NOT NULL AUTO_INCREMENT,
    movie_id      BIGINT       NOT NULL,
    actor_id      BIGINT       NOT NULL,
    role_name     VARCHAR(100) NOT NULL,
    billing_order INT          NOT NULL,   -- 크레딧 순서
    PRIMARY KEY (casting_id),
    UNIQUE KEY uk_casting_role    (movie_id, actor_id, role_name),  -- 같은 배우가 같은 배역을 두 번 맡지 않는다
    UNIQUE KEY uk_casting_billing (movie_id, billing_order),        -- 한 영화 안에서 크레딧 순서는 겹치지 않는다
    KEY idx_casting_actor (actor_id, movie_id),                     -- 배우 쪽 조회와 외래 키 검사용
    CONSTRAINT fk_casting_movie FOREIGN KEY (movie_id) REFERENCES movie (movie_id),
    CONSTRAINT fk_casting_actor FOREIGN KEY (actor_id) REFERENCES actor (actor_id)
);

    이 DDL에서 인덱스가 하는 일을 하나씩 확인하자. fk_casting_movie는 movie_id가 맨 앞인 uk_casting_role(또는 uk_casting_billing)로 검사되므로 따로 인덱스가 생기지 않는다. fk_casting_actor는 actor_id가 맨 앞인 idx_casting_actor가 맡는다. 이 인덱스에는 movie_id와 기본 키 casting_id가 함께 있으므로 "배우 10의 출연작 번호"는 이 인덱스만으로 끝난다. 크레딧 순서의 유일성은 업무에서 정한 규칙이다. 크레딧을 배우 단위로 한 줄씩 쓰는 업무라면 이 제약은 (movie_id, actor_id) 단위로 바뀌어야 한다. 어떤 조합이 유일한지는 데이터가 아니라 업무 규칙이 정한다는 점이 여기서도 그대로다.

    주문 항목: 관계의 속성이 시점을 담을 때

    쇼핑몰의 주문과 상품도 다대다다. 주문 하나에 상품이 여럿, 상품 하나가 여러 주문에 담긴다. 연결 테이블은 주문 항목(order_item)이고, 속성으로 수량과 주문 당시 단가를 가진다. 상품 테이블에 이미 가격이 있는데 주문 항목에 단가를 또 두는 것이 중복처럼 보일 수 있다. 그러나 둘은 다른 사실이다. 상품 테이블의 가격은 "지금 이 상품의 판매가"이고, 주문 항목의 단가는 "그 주문에서 합의된 가격"이다. 상품 가격이 내일 바뀌어도 어제의 주문 금액은 바뀌면 안 된다. 주문 항목의 단가는 상품에 종속된 값이 아니라 주문과 상품의 짝에 종속된 값이다. 02회에서 본 "시점 기준의 사실은 그 시점의 값을 사건 엔티티에 남긴다"는 원칙이 연결 테이블의 속성으로 나타난 것이다.

    CREATE TABLE order_item (
    order_id    BIGINT NOT NULL,
    product_id  BIGINT NOT NULL,
    quantity    INT    NOT NULL,
    order_price INT    NOT NULL,   -- 주문 당시 단가
    PRIMARY KEY (order_id, product_id),
    CONSTRAINT fk_order_item_order   FOREIGN KEY (order_id)   REFERENCES orders (order_id),
    CONSTRAINT fk_order_item_product FOREIGN KEY (product_id) REFERENCES product (product_id)
);

    여기서도 같은 짝이 반복될 수 있는지 물어야 한다. 한 주문에 같은 상품을 두 번 담는 일은 대개 수량을 늘리는 것으로 합쳐지므로 (order_id, product_id)가 유일하다. 그런데 같은 상품을 색상이나 사이즈 옵션을 달리해 두 줄로 담을 수 있다면 짝이 반복되고, 기본 키는 (order_id, line_no)처럼 주문 안의 줄 번호를 쓰거나 자기 식별자를 가져야 한다. 연결 테이블은 대개 양쪽 부모보다 행이 많다는 점도 기억해 두자. 모든 주문에 항목이 하나 이상 있다면 주문 항목의 행 수는 주문의 행 수 이상이다. 서비스에서 가장 큰 테이블이 연결 테이블인 경우가 흔하고, 그래서 연결 테이블의 키 너비와 인덱스 구성이 저장 공간과 버퍼 풀 적중률에 주는 영향도 가장 크다.

    한 층 아래: 연결 테이블과 잠금

    연결 테이블에 행을 넣을 때 InnoDB가 하는 일을 하나 더 보자. MySQL 매뉴얼은 테이블에 외래 키 제약이 있으면, 제약 조건 검사가 필요한 삽입·갱신·삭제가 검사를 위해 살펴보는 레코드에 공유 레코드 잠금(shared record-level lock)을 건다고 설명한다. 제약 검사가 실패하는 경우에도 이 잠금을 건다(Locks Set by Different SQL Statements in InnoDB). 주문 항목 한 행을 넣으면 orders의 해당 주문 행과 product의 해당 상품 행에 공유(S) 잠금이 걸리고, 이 잠금은 트랜잭션이 끝날 때까지 유지된다. 부모 행이 검사 도중에 사라지지 않도록 붙잡아 두는 것이다.

    이 잠금이 흔한 주문 처리 흐름과 만나면 교착 상태가 생길 수 있다. 상품 테이블에 재고 열 stock이 있고, 주문을 처리하는 트랜잭션이 "주문 항목을 넣고, 재고를 줄인다"는 순서로 일한다고 하자. 두 고객이 같은 상품 7을 동시에 주문한다.

    시각  트랜잭션 A (주문 100)                      트랜잭션 B (주문 200)
t1   INSERT order_item (100, 7, ...)
     └ FK 검사: product 7 레코드에 S 잠금
t2                                              INSERT order_item (200, 7, ...)
                                                └ FK 검사: product 7 레코드에 S 잠금 (S끼리는 호환)
t3   UPDATE product SET stock = stock - 1
      WHERE product_id = 7
     └ X 잠금 필요 → B의 S와 충돌, 대기
t4                                              UPDATE product SET stock = stock - 1
                                                 WHERE product_id = 7
                                                └ X 잠금 필요 → A의 S와 충돌, 대기
⇒ A는 B를, B는 A를 기다린다. InnoDB가 교착 상태를 감지하고 한쪽을 롤백한다.

    공유 잠금끼리는 호환되므로 t2에서 B는 기다리지 않는다. 문제는 t3과 t4다. 배타(X) 잠금은 다른 트랜잭션의 공유 잠금과 호환되지 않으므로, 두 트랜잭션이 서로 상대의 S 잠금이 풀리기를 기다린다. 각자 상대가 끝나야 끝날 수 있는 순환이다. InnoDB는 교착 상태를 감지하면 한쪽 트랜잭션을 롤백하고, 그 트랜잭션은 오류 1213(ER_LOCK_DEADLOCK)을 받는다. 애플리케이션 코드에는 외래 키도 잠금도 보이지 않으므로, 이 오류는 원인을 짐작하기 어려운 장애로 나타난다.

    MySQL 8.4.13에서 두 세션으로 위 순서(t1~t4)를 그대로 재현했다. 재고 100인 상품 7에 대해 A와 B가 각각 주문 항목을 넣은 뒤 재고를 줄이자, B의 UPDATE가 다음 오류를 받았다.

    ERROR 1213 (40001): Deadlock found when trying to get lock; try restarting transaction

    이 실행에서는 B가 롤백 대상으로 골라져 B가 넣은 주문 항목 (200, 7)도 함께 사라졌고, A는 대기에서 풀려 커밋되어 재고가 99, 주문 항목이 한 행 남았다. 어느 쪽이 롤백되는지는 InnoDB가 정하므로 실행마다 다를 수 있다.

    해법은 잠금을 얻는 순서를 바꾸는 것이다. 재고를 먼저 줄이고(UPDATE product ...로 상품 7에 X 잠금), 그다음 주문 항목을 넣는다. 트랜잭션 A가 X 잠금을 먼저 잡으면, 주문 항목 삽입의 외래 키 검사는 같은 트랜잭션이 이미 더 강한 잠금을 가진 레코드를 보는 것이므로 기다리지 않는다. 트랜잭션 B의 UPDATE는 A가 끝날 때까지 기다렸다가 진행한다. 기다림은 있지만 순환은 없다. MySQL 8.4.13에서 두 세션의 순서를 이렇게 바꿔 다시 실행하면 B는 A가 커밋할 때까지 기다린 뒤 진행해, 오류 없이 재고 98과 주문 항목 두 행이 남는다. 부모 행을 먼저 배타적으로 잡는 방법으로는 SELECT ... FOR UPDATE로 상품 행을 먼저 읽는 것도 있다. 연결 테이블은 두 부모를 동시에 가리키므로, 연결 테이블에 쓰는 트랜잭션이 부모 행도 고친다면 "부모를 먼저, 연결 행은 나중에"라는 순서를 정해 두는 편이 안전하다.

    두 트랜잭션이 같은 상품을 참조하는 주문 항목을 넣으며 공유 잠금을 나눠 가진 뒤, 재고 갱신에서 서로의 공유 잠금 때문에 배타 잠금을 얻지 못하는 순환을 보여 준다. 흰 배경의 시퀀스 다이어그램. 세로 생명선 세 개: 왼쪽 "트랜잭션 A", 가운데 "product 7 레코드", 오른쪽 "트랜잭션 B". 위에서 아래로 시간이 흐른다. 1단계: A에서 가운데로 화살표 "INSERT order_item → S 잠금". 2단계: B에서 가운데로 화살표 "INSERT order_item → S 잠금". 가운데 생명선에 "S(A), S(B)" 표시. 3단계: A에서 가운데로 빨간 점선 화살표 "UPDATE stock → X 대기". 4단계: B에서 가운데로 빨간 점선 화살표 "UPDATE stock → X 대기". 아래쪽에 A와 B를 잇는 빨간 원형 화살표와 "교착 상태" 라벨, 그 옆에 "InnoDB가 한쪽을 롤백". 오른쪽 아래 구석에 작은 초록 상자 "해법: 재고를 먼저 갱신(X 잠금) 후 INSERT". 외래 키 검사는 부모 행에 공유 잠금을 건다. 같은 부모를 나중에 갱신하는 트랜잭션이 동시에 둘이면 서로의 공유 잠금 때문에 교착 상태가 된다.

    다대다의 개념적 모델링과 논리적 모델링

    지금까지의 내용을 모델링 단계의 작업으로 정리하자. 개념적 모델링 단계에서는 다대다를 다대다 그대로 그린다. 이 단계의 목적은 업무가 기억해야 하는 사실을 합의하는 것이고, "영화와 배우는 다대다로 출연 관계를 맺는다"는 문장 자체가 합의할 내용이다. 까마귀발 표기로는 관계선의 양 끝에 모두 까마귀발을 그린다. 다대다를 찾아내는 방법은 02회에서 본 대로 양방향으로 묻는 것이다. "영화 하나에 배우가 여럿일 수 있는가?", "배우 하나가 영화 여럿에 나올 수 있는가?" 두 답이 모두 "그렇다"이면 다대다다. 한 방향만 물어 일대다로 그렸다가 나중에 반대 방향의 "여럿"을 발견하면, 앞의 실습처럼 외래 키를 옮기는 이관 작업이 기다린다.

    표기법에 따라 관계의 속성을 다루는 방식이 다르다는 점도 알아 두자. 피터 첸(Peter Chen)의 ER 표기에서는 관계를 마름모로 그리고 마름모에 속성을 붙일 수 있다. "출연" 마름모에 배역 이름을 붙이는 식이다. 반면 까마귀발 표기(IE 표기)에서 관계는 선이고, 02회에서 본 대로 선에는 속성을 붙일 수 없다. 그래서 까마귀발 표기를 쓰는 팀은 다대다 관계에 속성이 보이는 순간 개념 모델에서도 연관 엔티티를 미리 그리는 경우가 많다. 어느 단계에서 연관 엔티티를 드러낼지는 팀의 표기 관례에 따른 선택이지만, 논리적 모델링이 끝날 때 다대다가 남아 있어서는 안 된다는 점은 같다. 관계형 데이터베이스에는 다대다를 직접 담을 구조가 없기 때문이다.

    여섯 번째 단계를 까마귀발로 적으면 [영화] ||────O< [출연] >O────|| [배우]이다. 출연 하나에는 영화가 정확히 하나, 배우가 정확히 하나다. 그래서 연관 엔티티의 두 외래 키는 모두 NOT NULL이다. 영화 쪽에서는 출연이 0개 이상이다. 배우가 아직 정해지지 않은 기획 단계의 영화가 있을 수 있다. 만약 "모든 영화에는 출연자가 한 명 이상 있어야 한다"는 규칙이라면 영화 쪽 끝은 |<가 되지만, 04회에서 본 대로 이 "여럿 쪽 필수 참여"는 외래 키로 강제되지 않고 애플리케이션이 지켜야 한다. 다섯 번째 단계에서 두 외래 키의 조합을 기본 키로 삼으면 연관 엔티티가 부모의 식별자를 자기 식별자의 일부로 쓰는 식별 관계가 된다. 이 선택의 장단점은 06회의 주제다.

    연관 엔티티가 둘만 잇는 것도 아니다. "강사가 어느 학기에 어느 강좌를 맡는다"처럼 세 엔티티가 한 사실에 함께 참여하면, 외래 키가 셋인 연관 엔티티 하나로 표현한다. 이것을 둘씩 짝지은 연결 테이블 세 개로 쪼개면 "누가 언제 무엇을"이라는 한 사실이 세 조각으로 흩어지고, 조각을 다시 조인했을 때 실제로 없던 조합이 만들어질 수 있다. 한 사실은 한 행에 담는다는 원칙이 여기에도 적용된다.

    JPA로 올라가면

    논리 모델의 이 변환은 JPA 매핑에서 그대로 반복된다. @ManyToMany와 @JoinTable은 연결 테이블의 이름과 양쪽 조인 열을 기술하는 매핑이다. 연결 테이블에 배역 이름이나 주문 당시 단가 같은 열이 생기면 그 열을 담을 자리가 없으므로, 연결 테이블을 엔티티(Casting, OrderItem)로 매핑하고 양쪽 부모와 @ManyToOne 두 개로 잇게 된다. 논리 모델에서 다대다를 일대다 둘로 바꾼 것과 같은 구조다. 연결 테이블에 아직 속성이 없을 때도 차이가 있다. Hibernate ORM 6.4 사용자 가이드는 단방향 @ManyToMany 예에서 컬렉션의 원소 하나를 제거하면, 그 부모에 딸린 연결 행을 모두 지우고 현재 컬렉션에 남은 원소의 행을 다시 넣는 방식으로 처리된다고 설명한다. 연결 테이블이 커질수록 이 차이는 SQL 수로 드러난다. 연결 테이블을 처음부터 엔티티로 다루면 행 하나의 삽입과 삭제가 SQL 한 문장에 대응한다.

    흔한 오해와 함정

    "외래 키를 걸었으니 일대일이다"

    외래 키는 "자식 행 하나가 부모 하나를 가리킨다"만 보장한다. 여러 자식이 같은 부모를 가리키는 것은 막지 않으므로 외래 키만으로는 일대다다. 일대일은 외래 키 열에 UNIQUE 제약을 더하거나, 외래 키 열이 곧 기본 키인 공유 기본 키로만 선언된다. ERD에 일대일로 그려 놓고 DDL에서 UNIQUE를 빠뜨린 스키마는 데이터가 쌓인 뒤에야 "한 사원에 노트북 두 대"라는 행을 발견하게 된다. 그때는 어느 행이 맞는지 가려내는 데이터 정리부터 해야 UNIQUE를 걸 수 있다.

    "UNIQUE 열에는 NULL이 하나만 들어간다"

    MySQL에서 UNIQUE 인덱스는 NULL을 허용하는 열에 NULL을 여러 개 허용한다. 이 성질이 선택적 일대일을 가능하게 하고, 앞에서 본 맞바꾸기의 임시 자리도 만들어 준다. 반대로 "NULL도 하나만"을 기대하고 짠 코드는 MySQL에서 기대대로 막히지 않는다. 값이 없는 상태를 하나로 제한하고 싶다면 NULL 대신 다른 방식(예를 들어 값이 없음을 뜻하는 행을 아예 넣지 않는 설계)을 찾아야 한다.

    "한 트랜잭션으로 묶으면 제약은 커밋할 때 검사된다"

    MySQL은 외래 키를 즉시, UNIQUE와 외래 키를 여러 행을 고치는 문장 안에서도 행 단위로 검사한다. 트랜잭션으로 묶어도 문장 사이의 중간 상태가 제약을 어기면 그 문장이 실패한다. 그래서 일대일의 교체는 "끊고 나서 잇는" 순서여야 하고, 맞바꾸기는 NULL을 거쳐야 하며, 양쪽 모두 필수인 순환 외래 키는 첫 행을 넣을 수 없다. 다른 데이터베이스에서 지연 제약(deferred constraint)을 써 본 경험이 있다면 특히 주의할 부분이다.

    "일대일이면 합친다" 또는 "일대일이면 나눈다"

    둘 다 규칙이 아니다. 독립된 생명주기를 가진 두 엔티티는 일대일이어도 나뉜 채로 둔다. 노트북을 사원 테이블의 열로 합치면 배정되지 않은 노트북을 기록할 곳이 없다. 한 엔티티를 나눈 일대일은 선택적 속성 묶음, 행의 너비, 권한, 갱신 빈도 같은 이유가 있을 때만 나눈다. 이유 없이 나누면 조인과 짝 유지라는 비용만 남는다.

    "연결 테이블은 기술적인 부산물이다"

    연결 테이블은 다대다를 담기 위해 끼운 장치처럼 보이지만, 그 행 하나하나는 업무의 사실이다. 주문 항목, 수강, 출연, 배정은 대개 그 서비스의 핵심 거래이고, 시간이 지나면 속성이 붙고, 가장 큰 테이블이 된다. 처음부터 업무 이름을 붙이고, 같은 짝이 반복될 수 있는지 묻고, 조회 방향에 맞춰 키 순서를 정하는 것이 나중의 이관 비용을 줄인다.

    "쉼표로 이어 적거나 JSON 배열에 담으면 간단하다"

    열 하나에 여러 값을 담으면 테이블이 하나 줄어 보이지만, 외래 키로 존재를 검사할 수 없고, 정확한 조회가 어렵거나 느리며, 원소 추가가 한 행을 둔 경쟁이 된다. JSON 배열의 다중값 인덱스는 조회 문제를 덜어 주지만 참조 무결성과 짝의 속성 문제는 그대로 남는다. 다대다가 업무의 사실이라면 연결 테이블이 답이다.

    정리: 두 관계를 테이블로 옮기는 규칙

    이 회차의 내용을 결정 순서대로 모으면 다음과 같다.

    • 일대일은 외래 키와 UNIQUE다. 외래 키만 있으면 일대다다. 한 엔티티를 나눈 일대일은 공유 기본 키로 추가 인덱스 없이 표현할 수 있다.
    • 선택적 일대일은 NULL 허용 외래 키로 표현된다. MySQL의 UNIQUE 인덱스는 NULL을 여러 개 허용하고, 외래 키는 NULL 값을 검사하지 않는다(MATCH SIMPLE).
    • 양쪽 모두 필수인 일대일은 선언적으로 강제되지 않는다. MySQL은 외래 키를 즉시 검사하므로 순환 외래 키에는 첫 행을 넣을 수 없다. 대개 한 테이블로 합칠 신호다.
    • 외래 키는 나중에 "여럿"이 될 쪽에 둔다. 그러면 일대다로의 확장은 일반 인덱스를 만든 뒤 UNIQUE 인덱스를 지우는 in-place DDL 두 번이다. 반대쪽에 두면 열 추가, 데이터 이관, 외래 키 재생성이 따른다.
    • 주 테이블에 외래 키를 두면 관계의 존재를 주 테이블만으로 알 수 있고 교체가 단순하며 객체 참조 방향과 맞는다. 대신 대상 쪽의 확장에 약하다.
    • 다대다는 외래 키 하나로 담을 수 없다. 칸 하나가 부모 하나만 가리키기 때문이다. 짝의 집합을 테이블로 만든 연결 테이블이 다대다를 일대다 둘로 분해한다.
    • InnoDB에서 연결 테이블은 복합 기본 키의 클러스터형 인덱스와 외래 키용 보조 인덱스(기본 키 열이 덧붙은)로 양방향 조회를 받는다.
    • 관계의 속성은 짝 전체에 종속된다. 속성이 붙으면 연결 테이블은 업무 엔티티가 되고, 같은 짝이 반복되는지 다시 물어 식별자를 정한다.
    • 외래 키 검사는 부모 행에 공유 잠금을 건다. 연결 행을 넣고 부모를 갱신하는 트랜잭션은 부모를 먼저 잠가 교착 상태를 피한다.
    이 장의 핵심

    칸 하나는 값 하나이고, 외래 키는 칸 하나에 담긴 부모 하나다. 일대일은 이 칸을 어느 쪽에 둘지 고를 수 있어서 어려운 관계이고, 그 선택은 앞으로 "여럿"이 될 쪽이 어디인지로 정한다. 다대다는 이 칸을 어느 쪽에도 둘 수 없어서, 관계 그 자체를 행으로 만든 연결 테이블로 담는다. 연결 테이블은 속성이 붙는 순간 업무의 엔티티가 되며, 그때 식별자와 인덱스와 잠금 순서를 다시 판단해야 한다.
    일대일 관계
    양쪽 모두 상대가 최대 하나인 관계. 독립된 두 엔티티의 짝과 한 엔티티를 나눈 경우로 갈리며, 외래 키에 UNIQUE를 더하거나 기본 키를 공유해 선언한다.
    외래 키 위치
    주 테이블에 두면 관계 유무를 주 테이블만으로 알고 교체가 단순하다. 대상 테이블에 두면 대상 쪽이 여럿이 되는 확장에 강하다. 나중에 여럿이 될 쪽에 둔다.
    UNIQUE와 NULL
    MySQL의 UNIQUE 인덱스는 NULL을 여러 개 허용하고 외래 키는 NULL을 검사하지 않으므로, NULL 허용 외래 키 열 하나로 선택적 일대일을 표현할 수 있다.
    즉시 검사
    MySQL은 UNIQUE와 외래 키를 행 단위로 즉시 검사하고 커밋까지 미루지 않는다. 그래서 교체 순서가 중요하고, 맞바꾸기는 NULL을 거쳐야 하며, 양쪽 필수의 순환 외래 키는 선언할 수 없다.
    관계 확장 비용
    외래 키가 여럿이 될 쪽에 있으면 일반 인덱스 추가와 UNIQUE 삭제(둘 다 in-place)로 끝난다. 반대쪽이면 열 추가, 데이터 이관, 외래 키 추가(검사가 켜져 있으면 COPY), 옛 열 삭제가 필요하다.
    연결 테이블
    다대다의 짝 집합을 행으로 담는 테이블. 두 부모를 가리키는 외래 키를 가지며 다대다를 일대다 둘로 분해한다. 같은 짝의 중복은 기본 키나 UNIQUE로 막는다.
    연결 테이블의 인덱스
    InnoDB에서 복합 기본 키의 클러스터형 인덱스와, 기본 키 열이 덧붙은 외래 키 보조 인덱스가 짝 집합을 양방향 순서로 한 벌씩 가진다. 대리 키를 쓰면 반대 방향 커버링을 위해 인덱스를 직접 설계해야 한다.
    관계의 속성
    짝 전체에 종속되는 값(배역, 수량, 주문 당시 단가). 속성이 붙으면 연결 테이블은 업무 엔티티가 되고, 같은 짝의 반복 여부로 식별자를 다시 정한다.
    외래 키 검사 잠금
    InnoDB는 외래 키 검사 때 부모 레코드에 공유 잠금을 건다. 연결 행 삽입 뒤 같은 부모를 갱신하는 트랜잭션이 동시에 돌면 교착 상태가 생기므로 부모를 먼저 잠근다.

    실무에서 일대일의 외래 키 위치가 문제로 드러나는 때는 거의 언제나 업무 정책이 바뀌는 날이다. "회원당 배송지 하나", "계정당 기기 하나", "주문당 결제 하나" 같은 규칙은 서비스가 자라면서 가장 먼저 깨진다. 설계 리뷰에서 일대일을 보면 "이 숫자 1은 물리적 사실인가, 정책인가"를 묻는 것이 좋다. 정책이라면 나중에 여럿이 될 쪽을 업무 담당자와 함께 짚고 외래 키를 그쪽에 둔다. 그 판단이 맞으면 확장은 인덱스 두 개의 교체로 끝나고, 틀리면 운영 중인 큰 테이블에 대한 이중 쓰기 배포와 데이터 이관, 그리고 외래 키 추가의 COPY 알고리즘이 기다린다. 외래 키 검사를 꺼서 INPLACE로 추가하는 선택지는 빠르지만 기존 행을 검사하지 않으므로, 이관이 완전했는지 별도의 쿼리로 확인해야 한다.

    조회 성능과 확장성이 부딪칠 때는 비용의 모양을 비교한다. 대상 테이블에 외래 키를 두어 생기는 조인 비용은 UNIQUE 인덱스 탐색 한 번이고 매 요청마다 작게 든다. 대신 ORM 계층에서 프록시를 쓸 수 없어 생기는 추가 조회는 목록 화면에서 N+1로 커질 수 있으므로, 그 부분은 조인 페치나 쿼리 설계로 따로 관리해야 한다. 반대로 주 테이블에 외래 키를 두어 생기는 이관 비용은 한 번 들지만 가장 데이터가 많을 때 든다. 둘 중 무엇을 감당할지는 서비스의 단계와 팀이 스키마 변경을 얼마나 자주, 얼마나 안전하게 할 수 있는지에 달려 있다.

    연결 테이블에서 실무 장애로 이어지는 지점은 세 가지가 흔하다. 첫째, 대리 키를 기본 키로 두고 짝에 UNIQUE를 빠뜨려 같은 짝이 중복 저장되는 경우다. 동시에 들어온 두 요청이 "없으면 넣는다"를 각자 실행하면 애플리케이션의 존재 확인은 둘 다 통과한다. 데이터베이스의 UNIQUE만이 이 경쟁을 막는다. 둘째, 반대 방향 조회용 인덱스를 설계하지 않아 한쪽 방향의 조회가 클러스터형 인덱스 재탐색으로 느려지는 경우다. 셋째, 외래 키 검사의 공유 잠금을 모르고 "연결 행 삽입 후 부모 갱신" 순서로 코드를 짜서 트래픽이 몰릴 때 교착 상태가 터지는 경우다. 세 가지 모두 스키마 리뷰에서 "짝의 유일성은 어디서 지키는가", "양방향 조회는 각각 어느 인덱스를 타는가", "이 트랜잭션은 부모 행을 어떤 순서로 잠그는가"를 물으면 미리 잡을 수 있다.

    1. (가)는 외래 키가 막는다. 부모 회원 행이 없으므로 오류 1452(ER_NO_REFERENCED_ROW_2)다. (나)는 기본 키가 막는다. 같은 member_id가 이미 있으므로 중복 키 오류 1062다. 기본 키가 곧 외래 키라서 UNIQUE 제약을 따로 두지 않아도 일대일이 강제된다. 세 열을 모두 NOT NULL로 둘 수 있다는 점이 한 테이블에 NULL 허용 열 셋을 두는 설계보다 나은 부분이다.

    2. (1)은 실패한다. 노트북 10이 아직 사원 1을 가리키므로 노트북 12에 1을 넣는 순간 uk_laptop_employee에 1이 둘이 되어 중복 키 오류가 난다. (2)는 성공한다. 노트북 10의 배정이 풀린다. NULL은 UNIQUE 인덱스에 여러 개 있어도 되고 외래 키 검사도 받지 않는다. (3)은 이제 성공한다. 1을 가진 행이 없기 때문이다. (1)과 (3)은 같은 문장이지만 앞선 상태에 따라 결과가 다르며, 이것이 "끊고 나서 잇는다"는 순서의 이유다. (4)는 실패한다. 노트북 11이 사원 2를 참조하고 있고, 외래 키에 별도의 ON DELETE를 선언하지 않았으므로 기본 동작인 RESTRICT로 즉시 거부된다(오류 1451). 노트북 11의 배정을 먼저 풀거나 ON DELETE SET NULL을 선언해야 한다.

    3. ALTER TABLE employee ADD INDEX idx_employee_laptop (laptop_id); 다음에 ALTER TABLE employee DROP INDEX uk_employee_laptop;를 실행한다. DROP INDEX를 먼저 실행하면 오류 1553(Cannot drop index 'uk_employee_laptop': needed in a foreign key constraint)이 난다. 외래 키를 만들 때 laptop_id가 맨 앞인 인덱스로 UNIQUE 인덱스가 이미 있었으므로 MySQL은 별도 인덱스를 만들지 않았고, 그 UNIQUE 인덱스가 외래 키를 강제할 수 있는 유일한 인덱스이기 때문이다. 새 인덱스를 먼저 만들면 외래 키가 쓸 인덱스가 생기므로 UNIQUE 인덱스를 지울 수 있다. 두 연산 모두 MySQL 8.0 온라인 DDL에서 테이블을 다시 만들지 않는 in-place 연산이다.

    4. book_author(book_id, author_id, author_order)에 기본 키 (book_id, author_id), 두 외래 키, 그리고 업무 규칙에 따라 UNIQUE (book_id, author_order)를 둔다. "책 하나의 저자를 순서대로"는 클러스터형 인덱스에서 book_id 구간을 읽는다. 그 구간은 author_id 순으로 정렬되어 있으므로 author_order 순서로 보여 주려면 정렬이 필요한데, UNIQUE (book_id, author_order) 인덱스가 있으면 그 인덱스로 순서대로 읽을 수 있다(필요한 다른 열은 기본 키로 다시 찾는다). "저자 하나의 책 번호 목록"은 author_id 외래 키를 위해 자동 생성된 보조 인덱스를 탄다. 이 인덱스에는 기본 키 열이 덧붙어 (author_id, book_id) 순으로 정렬되어 있으므로 커버링이다. 기본 키를 대리 키 book_author_id로 바꾸면 자동 생성 인덱스는 (author_id, book_author_id)만 담아 book_id가 없으므로, 행마다 클러스터형 인덱스를 다시 찾아가야 한다. 커버링을 유지하려면 (author_id, book_id) 인덱스를 직접 만든다. 이 경우에도 같은 짝의 중복을 막는 UNIQUE (book_id, author_id)가 필요하다.

    5. 수강 행을 넣을 때 외래 키 검사가 강좌 행에 공유(S) 잠금을 걸고 트랜잭션 끝까지 유지한다. 두 트랜잭션이 같은 강좌로 동시에 수강 행을 넣으면 둘 다 S 잠금을 얻는다(S끼리 호환). 이어서 각자 강좌 행의 신청 인원을 고치려고 배타(X) 잠금을 요청하면, 상대의 S 잠금 때문에 서로 기다리는 순환이 생기고 InnoDB가 한쪽을 롤백한다. 그것이 1213(ER_LOCK_DEADLOCK)이다. 고치는 방법의 첫째는 순서를 바꾸는 것이다. 강좌 행을 먼저 UPDATE해 X 잠금을 얻고 그다음 수강 행을 넣으면, 외래 키 검사는 자기 트랜잭션이 이미 가진 더 강한 잠금 위에서 이루어지고 다른 트랜잭션은 첫 UPDATE에서 차례를 기다린다. 둘째는 SELECT ... FROM course WHERE course_id = ? FOR UPDATE로 강좌 행을 먼저 배타적으로 잠근 뒤 정원 확인, 수강 행 삽입, 인원 갱신을 차례로 하는 것이다. 정원 확인까지 한 트랜잭션 안에서 직렬화되므로 정원 초과도 함께 막는다.

     MySQL 8.0(InnoDB)에서 "사원 한 명에 노트북은 최대 한 대, 노트북 한 대는 최대 한 명에게"라는 선택적 일대일을, 노트북 테이블에 외래 키를 두어 표현하려고 한다. 가장 정확한 선언은? employee_id BIGINT NOT NULL 외래 키만 선언한다. employee_id BIGINT NULL 외래 키만 선언한다. 외래 키가 있으면 일대일이다. employee_id BIGINT NULL 외래 키와 그 열의 UNIQUE 제약을 함께 선언한다. employee_id를 노트북 테이블의 기본 키로 삼는다. 외래 키만으로는 여러 노트북이 같은 사원을 가리키는 것을 막지 못하므로 일대다다. UNIQUE를 더해야 일대일이 된다. 미배정 노트북을 표현하려면 열이 NULL을 허용해야 하는데, MySQL의 UNIQUE 인덱스는 NULL을 여러 개 허용하므로 미배정 노트북이 여러 대여도 문제가 없다. NOT NULL로 선언하면 미배정 노트북을 넣을 수 없다. employee_id를 기본 키로 삼으면 노트북의 식별자가 배정에 따라 바뀌어, 독립된 생명주기를 가진 노트북에 맞지 않고 미배정 상태도 표현할 수 없다. 사원 테이블에 laptop_id UNIQUE 외래 키가 있다. 사원 1(노트북 10)과 사원 2(노트북 11)의 노트북을 UPDATE employee SET laptop_id = CASE employee_id WHEN 1 THEN 11 WHEN 2 THEN 10 END WHERE employee_id IN (1, 2); 한 문장으로 맞바꾸려 했다. MySQL에서의 결과와 이유로 옳은 것은? 한 문장이므로 문장이 끝난 뒤 유일성을 검사해 성공한다. UNIQUE는 행 단위로 즉시 검사되므로, 어느 행을 먼저 고치든 그 순간 값이 겹쳐 중복 키 오류로 실패한다. 트랜잭션 안에서 실행하면 커밋 시점에 검사하므로 성공한다. 외래 키 검사 때문에 실패하며, UNIQUE와는 무관하다. MySQL 매뉴얼은 여러 행을 고치는 문장에서도 UNIQUE와 외래 키가 행 단위로 검사되고, 외래 키 검사가 커밋까지 미뤄지지 않는다고 설명한다. 첫 행을 고치는 순간 두 사원이 같은 노트북을 가리키므로 실패한다. 트랜잭션으로 묶어도 검사 시점은 바뀌지 않는다. 노트북 10과 11은 모두 존재하므로 외래 키 검사는 통과하며, 실패 원인은 UNIQUE다. 해법은 한쪽을 NULL로 비운 뒤 세 문장으로 나누어 고치는 것이다. 연결 테이블 movie_actor(movie_id, actor_id)의 기본 키가 (movie_id, actor_id)이고, 두 열에 각각 외래 키가 있다. 다른 인덱스는 직접 만들지 않았다. InnoDB에서 SELECT movie_id FROM movie_actor WHERE actor_id = 10의 처리로 옳은 것은? actor_id가 맨 앞인 인덱스가 없으므로 테이블 전체를 읽는다. 기본 키 인덱스의 두 번째 열이 actor_id이므로 기본 키 인덱스로 범위 탐색한다. 자동 생성된 actor_id 인덱스로 찾은 뒤, 행마다 클러스터형 인덱스를 다시 찾아가 movie_id를 읽는다. 자동 생성된 actor_id 인덱스의 레코드에 기본 키 열이 함께 들어 있으므로, 그 인덱스만 읽고 끝난다. 외래 키 actor_id에는 그 열이 맨 앞인 인덱스가 필요하므로 MySQL이 자동으로 만든다. 따라서 전체 스캔이 아니다. 기본 키 (movie_id, actor_id)는 movie_id 순으로 정렬되어 있어 actor_id만으로는 범위를 정할 수 없다. InnoDB는 보조 인덱스 레코드에 기본 키 열을 덧붙이므로 actor_id 인덱스 레코드에 movie_id가 이미 있어, 클러스터형 인덱스를 다시 찾을 필요가 없는 커버링 조회가 된다. 세 번째 보기는 기본 키가 대리 키였다면 맞는 설명이다. 업무 규칙이 "사원 한 명에 노트북 한 대"에서 "개발자는 노트북을 여러 대 받을 수 있다"로 바뀔 가능성이 크다고 한다. 처음 설계에서 외래 키 위치로 가장 적절한 것은? 노트북 테이블에 UNIQUE 외래 키를 둔다. 나중에 일반 인덱스를 만들고 UNIQUE를 지우면 일대다가 된다. 사원 테이블에 UNIQUE 외래 키를 둔다. 나중에 UNIQUE를 지우면 사원 한 명이 여러 노트북을 가리킬 수 있다. 어느 쪽에 두어도 UNIQUE만 지우면 되므로 차이가 없다. 처음부터 연결 테이블을 만들어야 한다. 일대일은 확장할 수 없다. 사원 1 : 노트북 N에서 여럿 쪽은 노트북이므로, 외래 키가 노트북 테이블에 있으면 이미 일대다의 자리에 있다. UNIQUE만 풀면 된다(외래 키가 쓸 일반 인덱스를 먼저 만든다). 사원 테이블의 laptop_id는 칸 하나라 UNIQUE를 지워도 "노트북 하나를 여러 사원이 가리킨다"가 될 뿐 사원 한 명이 여러 대를 가리킬 수는 없다. 그래서 위치에 따라 차이가 크다. 연결 테이블은 양쪽 모두 여럿이 될 때, 또는 배정 이력이 필요할 때의 해법이다. 주문 처리 트랜잭션이 INSERT INTO order_item ... 다음에 UPDATE product SET stock = stock - 1 WHERE product_id = ?를 실행한다. 같은 상품에 동시 주문이 몰릴 때 교착 상태가 나는 이유로 옳은 것은? 두 트랜잭션의 INSERT가 같은 order_item 레코드에 배타 잠금을 걸기 때문이다. UPDATE가 테이블 전체를 잠그기 때문이다. 외래 키 검사가 상품 행에 공유 잠금을 걸고, 두 트랜잭션이 서로의 공유 잠금 때문에 상품 행의 배타 잠금을 얻지 못하기 때문이다. InnoDB는 외래 키를 커밋 시점에 검사하므로 커밋 순간 두 트랜잭션이 충돌하기 때문이다. InnoDB는 외래 키 검사를 위해 살펴보는 부모 레코드에 공유 잠금을 건다. 두 트랜잭션이 같은 상품을 참조하는 주문 항목을 넣으면 둘 다 공유 잠금을 얻고(호환), 이어서 각자 배타 잠금을 요청하면 상대의 공유 잠금 때문에 서로 기다리는 순환이 생긴다. 두 INSERT는 서로 다른 주문 항목 행을 만들므로 같은 레코드를 다투지 않는다. 기본 키로 한 행을 고치는 UPDATE는 테이블 전체가 아니라 그 레코드를 잠근다. MySQL은 외래 키를 즉시 검사한다.
    일대일 관계(one-to-one relationship)
    양쪽 모두 상대 인스턴스가 최대 하나인 관계. 관계형 데이터베이스에서는 외래 키와 UNIQUE 제약, 또는 공유 기본 키로 선언한다.
    다대다 관계(many-to-many relationship)
    양쪽 모두 상대 인스턴스가 여럿일 수 있는 관계. 외래 키 하나로 표현할 수 없어 연결 테이블로 분해한다.
    주 테이블과 대상 테이블
    일대일에서 업무 흐름이 먼저 조회하고 기준으로 삼는 쪽을 주 테이블, 주 테이블을 거쳐 찾아가는 쪽을 대상 테이블이라 부른다. 외래 키는 어느 쪽에도 둘 수 있다.
    공유 기본 키(shared primary key)
    떼어 낸 테이블이 원래 테이블의 기본 키를 자기 기본 키이자 외래 키로 쓰는 방식. 추가 인덱스 없이 일대일을 강제한다.
    연결 테이블(junction table)
    두 엔티티의 짝을 행으로 담는 테이블. 링크 테이블, 조인 테이블이라고도 한다. 다대다를 일대다 두 개로 분해한다.
    연관 엔티티(associative entity)
    다대다 관계를 엔티티로 끌어올린 것. 관계의 속성을 가지며 출연, 수강, 주문 항목처럼 업무 이름을 가진다.
    지연 제약 검사(deferred constraint checking)
    제약을 문장이나 트랜잭션이 끝날 때 검사하는 방식. MySQL InnoDB는 외래 키와 UNIQUE를 행 단위로 즉시 검사하며 지연 검사를 지원하지 않는다.
    다중값 인덱스(multi-valued index)
    MySQL 8.0.17부터 InnoDB가 지원하는, JSON 배열처럼 행 하나에 여러 값이 있는 열에 행당 여러 인덱스 레코드를 두는 보조 인덱스.
    커버링 인덱스(covering index)
    쿼리에 필요한 열이 모두 인덱스 레코드 안에 있어 테이블 행을 다시 읽지 않아도 되는 인덱스 사용. InnoDB에서는 보조 인덱스에 덧붙은 기본 키 열도 여기에 포함된다.
