    리플렉션이 필요한 이유: 호출할 이름을 컴파일러가 알아야 한다

    10회에서 HTTP 서버를 만들며 "요청 메시지를 파싱하고, 경로에 따라 처리를 고르고, 응답을 쓴다"는 구조를 세웠다. 이 회차는 그 가운데 "경로에 따라 처리를 고른다"는 부분에 집중한다. 페이지가 셋인 서버라면 가장 먼저 떠오르는 코드는 경로 문자열로 분기하는 것이다. 아래 코드는 이 회차에서 쓸 요청·응답 객체(HttpRequest, HttpResponse)와 컨트롤러 두 개를 이용해 분기한다. 이 타입들의 전체 코드는 뒤의 리플렉션 서블릿 절에서 보인다.

    package lab.app;

import lab.web.HttpRequest;
import lab.web.HttpResponse;

public class SwitchServlet {
    private final SiteController site = new SiteController();
    private final SearchController search = new SearchController();

    public void service(HttpRequest request, HttpResponse response) {
        switch (request.path()) {
            case "/home" -> site.home(request, response);
            case "/hello" -> site.hello(request, response);
            case "/search" -> search.search(request, response);
            default -> {
                response.status(404);
                response.write("404 Not Found: " + request.path());
            }
        }
    }
}

    이 코드는 잘 동작한다. 문제는 페이지가 늘어날 때 드러난다. 새 페이지를 하나 추가할 때마다 컨트롤러에 메서드를 만들고, 다시 SwitchServlet을 열어 case 한 줄과 필드 하나를 추가해야 한다. 같은 사실(이 경로는 이 메서드가 처리한다)을 두 곳에 적는 셈이고, 한쪽만 고치면 404가 나거나 아무도 부르지 않는 메서드가 남는다.

    더 근본적인 문제는 의존 방향이다. SwitchServlet은 "요청을 받아 알맞은 메서드에 넘긴다"는 범용 역할을 하는데, 코드에는 SiteController.home이라는 구체적인 이름이 박혀 있다. 그래서 이 클래스는 애플리케이션의 모든 컨트롤러를 알아야만 컴파일된다. 스프링 MVC의 DispatcherServlet을 떠올려 보면 이 구조가 왜 불가능한지 분명해진다. 그 클래스는 여러분의 OrderController가 존재하기 몇 년 전에 컴파일되어 jar로 배포되었다. 그 안에 orderController.list(...) 같은 호출 코드가 들어 있을 수 없다.

    자바의 일반 메서드 호출은 컴파일러가 호출할 클래스와 메서드 이름, 매개변수 타입을 알고 있어야 쓸 수 있다. 프레임워크는 정반대 상황에 있다. 호출할 대상을 실행 시점에야 알게 되고, 그 정보는 설정 파일의 클래스 이름이나 URL 경로 같은 문자열로 주어진다. 문자열로 클래스를 찾고, 그 클래스에 어떤 메서드가 있는지 물어보고, 찾은 메서드를 호출하는 수단이 필요하다. 이것이 리플렉션(reflection)이다. 리플렉션은 실행 중인 프로그램이 자기 자신의 구조(클래스, 메서드, 필드, 생성자)를 객체로 꺼내 보고, 그 객체를 통해 메서드를 호출하거나 필드를 읽고 쓰거나 새 객체를 만드는 기능이다.

    리플렉션의 중심에는 네 가지 타입이 있다. java.lang.Class와 java.lang.reflect 패키지의 세 클래스다.

    타입나타내는 것대표적인 동작
    Class클래스·인터페이스·배열·기본형 하나이름, 상위 타입, 수정자 조회, 멤버 탐색
    Method메서드 하나invoke(대상, 인자...)로 호출
    Field필드 하나get(대상), set(대상, 값)
    Constructor생성자 하나newInstance(인자...)로 객체 생성

    앞선 권(스프링 핵심 원리 - 고급편)에서 JDK 동적 프록시를 만들 때 Method.invoke를 잠깐 썼고, 그 호출이 DirectMethodHandleAccessor라는 중계 객체를 거친다는 것도 보았다. 이 회차는 그 아래를 다룬다. 일반 호출과 리플렉션 호출이 바이트코드에서 어떻게 다른지, Class 객체가 언제 생기고 어디에 있는지, 탐색 메서드가 무엇을 돌려주고 무엇을 빼는지, 접근 검사는 누가 어떻게 하는지를 차례로 확인한다. 마지막에 이 지식으로 경로 이름을 메서드 이름에 대응시키는 서블릿을 만든다.

    이 회차의 실행 결과는 모두 macOS에서 Temurin OpenJDK 21.0.13으로 직접 돌려 얻었다. 예제 클래스는 lab.reflect, lab.web, lab.app 패키지에 둔다. 실행마다 달라지는 값(객체의 해시 값)은 그 자리에서 밝힌다.

    한 층 아래: 일반 호출은 상수 풀의 심볼릭 참조로 묶인다

    리플렉션이 무엇을 대신하는지 알려면 일반 호출이 클래스 파일에 어떻게 기록되는지부터 봐야 한다. 이 회차 내내 쓸 예제 클래스 두 개를 먼저 보인다. Item은 상위 클래스이고, Book은 여러 접근 제어자의 필드·메서드·생성자를 골고루 가진다.

    package lab.reflect;

public class Item {
    protected long id;

    public String label() {
        return "item-" + id;
    }
}
    package lab.reflect;

public class Book extends Item implements Comparable {
    public static final int MAX_TITLE = 100;

    public String title;
    private int price;
    private final String isbn;
    private final int edition = 1;

    public Book() {
        this("untitled", 0, "000");
    }

    public Book(String title, int price, String isbn) {
        this.title = title;
        this.price = price;
        this.isbn = isbn;
    }

    private Book(String isbn) {
        this("draft", 0, isbn);
    }

    public String describe(String prefix) {
        return prefix + title + "(" + price + ")";
    }

    public int discount(int percent) {
        if (percent < 0 || percent > 100) {
            throw new IllegalArgumentException("percent=" + percent);
        }
        return price * (100 - percent) / 100;
    }

    private String secret() {
        return "isbn=" + isbn;
    }

    public int getPrice() { return price; }
    public String getIsbn() { return isbn; }
    public int getEdition() { return edition; }

    static Book of(String title) {
        return new Book(title, 10000, "111");
    }

    @Override
    public int compareTo(Book other) {
        return Integer.compare(price, other.price);
    }
}

    이제 같은 메서드 describe를 두 가지 방법으로 부르는 클래스를 만든다. direct는 평범하게 호출하고, reflective는 메서드 이름을 문자열 매개변수로 받아 리플렉션으로 호출한다.

    package lab.reflect;

import java.lang.reflect.Method;

public class CallSite {
    static String direct(Book book) {
        return book.describe(">");
    }

    static Object reflective(Book book, String name) throws Exception {
        Method m = Book.class.getMethod(name, String.class);
        return m.invoke(book, ">");
    }
}

    direct의 핵심은 invokevirtual #9 한 줄이다. 9번 상수 풀 항목은 Methodref이고, 클래스 이름(lab/reflect/Book), 메서드 이름(describe), 디스크립터((Ljava/lang/String;)Ljava/lang/String;)라는 세 조각의 문자열로 이루어져 있다. 이것을 심볼릭 참조(symbolic reference)라고 부른다. 컴파일러는 이 참조를 만들기 전에 Book에 그런 메서드가 정말 있는지, 인자 타입이 맞는지, 호출하는 쪽에서 접근할 수 있는지를 모두 확인했다. 확인을 통과해야만 이 바이트코드가 만들어진다.

    실행 시점에 JVM은 이 심볼릭 참조를 실제 메서드로 바꾼다. JVMS §5.4.3은 이 과정을 해석(resolution)이라고 부르고, invokevirtual, getfield, new 같은 명령을 실행하려면 그 명령이 가리키는 심볼릭 참조를 먼저 해석해야 한다고 정한다. 그리고 해석이 한 번 성공하면 같은 참조에 대한 이후의 해석은 처음 결과와 같은 대상을 돌려준다고 적는다. 즉 일반 호출에서 "어떤 메서드를 부를지"는 클래스 파일에 이미 적혀 있고, 실행 시점에 하는 일은 그 이름을 실제 메서드에 한 번 연결하는 것뿐이다. 오버라이딩에 따른 실행 시점 선택(동적 디스패치)은 이 연결 이후의 문제이고, 이름과 디스크립터 자체는 바뀌지 않는다.

    reflective의 상수 풀에는 Book.describe에 대한 Methodref가 없다. 대신 Class.getMethod와 Method.invoke에 대한 참조가 있다. describe라는 이름은 이 메서드의 매개변수 name으로 실행 시점에 들어오는 평범한 String 값이다. 매개변수 타입 목록은 anewarray #15로 만든 Class[] 배열에, 인자 목록은 anewarray #2로 만든 Object[] 배열에 담긴다. 반환 타입은 Object다. 컴파일러가 보기에 이 코드는 "어떤 Class 객체의 getMethod를 부르고, 받은 Method 객체의 invoke를 부른다"일 뿐이고, 그 끝에서 무엇이 실행될지는 전혀 모른다.

    그래서 리플렉션은 컴파일러가 하던 검사를 실행 시점으로 옮긴다. 메서드가 존재하는가(없으면 NoSuchMethodException), 인자 개수와 타입이 맞는가(틀리면 IllegalArgumentException), 호출하는 쪽이 접근할 수 있는가(없으면 IllegalAccessException)를 이제 getMethod와 invoke가 실행될 때마다 확인한다. 리플렉션의 유연함과 비용이 모두 여기서 나온다. 호출 대상을 실행 시점의 데이터로 정할 수 있게 된 대신, 컴파일 시점에 받던 보장을 잃고 검사 비용을 실행 시점에 낸다.

    클래스와 메타데이터: Class 객체가 담고 있는 것

    리플렉션의 출발점은 언제나 Class 객체다. JVM은 클래스를 로딩하면 그 클래스를 나타내는 java.lang.Class 인스턴스를 하나 만든다. 프로그램은 이 객체에게 "너의 이름은 무엇이냐, 상위 클래스는 무엇이냐, 어떤 메서드가 있느냐"를 물을 수 있다. 이렇게 클래스에 대한 정보, 즉 데이터에 대한 데이터를 메타데이터(metadata)라고 부른다. Class 객체를 얻는 방법은 세 가지다. 클래스 리터럴(Book.class), 인스턴스의 getClass(), 그리고 이름 문자열로 찾는 Class.forName이다. 아래 예제로 세 방법과 주요 메타데이터를 확인한다.

    package lab.reflect;

import java.lang.reflect.Modifier;
import java.util.Arrays;

public class ClassMetaMain {
    public static void main(String[] args) throws Exception {
        Class c1 = Book.class;
        Class c2 = new Book().getClass();
        Class c3 = Class.forName("lab.reflect.Book");
        System.out.println("같은 Class 객체? " + (c1 == c2 && c2 == c3));

        System.out.println("getName       = " + c1.getName());
        System.out.println("getSimpleName = " + c1.getSimpleName());
        System.out.println("getPackageName= " + c1.getPackageName());
        System.out.println("getSuperclass = " + c1.getSuperclass());
        System.out.println("getInterfaces = " + Arrays.toString(c1.getInterfaces()));
        System.out.println("제네릭 인터페이스 = " + Arrays.toString(c1.getGenericInterfaces()));
        int mod = c1.getModifiers();
        System.out.println("getModifiers  = " + mod + " -> " + Modifier.toString(mod));
        System.out.println("Comparable 수정자 = " + Modifier.toString(Comparable.class.getModifiers()));

        System.out.println("int.class     = " + int.class.getName() + ", isPrimitive=" + int.class.isPrimitive());
        System.out.println("String[].class= " + String[].class.getName());
        System.out.println("int[][].class = " + int[][].class.getName());
        System.out.println("배열의 상위 타입 = " + String[].class.getSuperclass());

        System.out.println("Book 로더   = " + c1.getClassLoader().getName());
        System.out.println("String 로더 = " + String.class.getClassLoader());

        System.out.println("--- 언제 초기화되는가");
        Class p1 = InitProbe.class;
        System.out.println("1) 클래스 리터럴 평가 후");
        Class p2 = ClassMetaMain.class.getClassLoader().loadClass("lab.reflect.InitProbe");
        System.out.println("2) loadClass 후");
        Class p3 = Class.forName("lab.reflect.InitProbe", false, ClassMetaMain.class.getClassLoader());
        System.out.println("3) forName(initialize=false) 후");

    이름에 관한 두 메서드는 다른 값을 준다. getName은 패키지를 포함한 이진 이름(binary name)을, getSimpleName은 소스에 적은 짧은 이름을 준다. 배열과 기본형을 보면 getName이 JVM의 표기를 따른다는 것이 드러난다. String[]의 이름은 [Ljava.lang.String;, int[][]는 [[I다. 대괄호 하나가 배열 차원 하나이고, L...;은 참조 타입, I는 int다. 앞 절의 디스크립터 (Ljava/lang/String;)Ljava/lang/String;에서 본 것과 같은 표기 체계다(디스크립터는 패키지 구분자로 /를 쓰고 getName은 .을 쓴다는 차이만 있다). 기본형에도 Class 객체가 있다. int.class는 isPrimitive()가 참이고, Integer.TYPE 상수와 같은 객체다. 메서드를 매개변수 타입으로 찾을 때 int 매개변수는 int.class로, Integer 매개변수는 Integer.class로 구분해야 하는 이유가 이것이다.

    getInterfaces와 getGenericInterfaces의 차이도 눈여겨보자. 앞의 것은 interface java.lang.Comparable, 뒤의 것은 java.lang.Comparable을 보여 준다. 제네릭 타입 인자는 컴파일하면 지워지지만(type erasure), 클래스 선언에 적힌 제네릭 정보는 클래스 파일의 Signature 속성에 따로 남는다. getGenericInterfaces, Field.getGenericType 같은 메서드는 이 속성을 읽는다. 지워지는 것은 객체가 실행 중에 갖는 타입 인자이지, 선언에 적힌 타입 정보가 아니다. 이 구분은 뒤의 함정 절에서 한 번 더 확인한다.

    수정자는 int 하나로 온다. getModifiers()가 1을 돌려준 것은 클래스 파일의 접근 플래그에서 ACC_PUBLIC(0x0001) 비트만 켜져 있다는 뜻이고, Modifier.toString이 그 비트들을 단어로 바꿔 준다. Comparable이 public abstract interface로 출력된 것은 인터페이스가 클래스 파일에서 ACC_INTERFACE와 ACC_ABSTRACT 플래그를 함께 갖기 때문이다. 이 비트 표현은 메서드에서 함정을 하나 만드는데, 메서드 탐색 절에서 실제로 걸려 본다.

    클래스 로더 두 줄도 의미가 있다. Book은 클래스패스에서 클래스를 읽는 애플리케이션 클래스 로더(이름이 app)가 로딩했다. String의 로더는 null이다. getClassLoader의 Javadoc은 부트스트랩 클래스 로더가 로딩한 클래스에 대해 null을 돌려줄 수 있다고 적는다. 이 실행에서는 String을 로딩한 부트스트랩 로더가 null로 표현되었다.

    Class 객체와 메타데이터는 어디에 있는가

    Class 객체는 평범한 자바 객체이므로 힙에 있다. 하지만 메서드의 바이트코드, 상수 풀, 필드 배치 같은 클래스의 실제 메타데이터까지 그 객체 안에 들어 있는 것은 아니다. HotSpot에서 이 메타데이터는 JDK 8부터 힙 밖의 네이티브 메모리, 흔히 메타스페이스(Metaspace)라고 부르는 영역에 있다. JEP 122(Remove the Permanent Generation)는 클래스 메타데이터를 네이티브 메모리에 할당하고, 인턴된 문자열과 클래스의 static 변수는 자바 힙으로 옮긴다고 설명한다. 그러니 HotSpot에서 힙의 Class 객체는 메타스페이스의 메타데이터를 가리키는 손잡이에 가깝다.

    리플렉션 질의는 이 손잡이를 통해 VM에게 정보를 받아 온다. OpenJDK 21의 Class 소스를 보면 getDeclaredFields는 캐시가 비어 있을 때 getDeclaredFields0라는 네이티브 메서드로 VM에 필드 목록을 요청한다. 받은 결과는 ReflectionData라는 내부 객체에 저장되고, 이 객체는 SoftReference로 감싸져 Class의 필드에 걸린다. 소프트 참조이므로 메모리가 부족하면 GC가 이 캐시를 비울 수 있고, 그 뒤의 질의는 다시 VM에 묻는다. 캐시에는 클래스가 재정의(JVM TI의 RedefineClasses)된 횟수도 기록되어, 클래스가 바뀌면 낡은 캐시를 버린다.

    캐시에 있는 Method, Field, Constructor는 바깥에 그대로 내주지 않는다. 소스의 주석은 이것들을 "루트(root)" 객체라 부르고, 밖으로 내보낼 때는 반드시 ReflectionFactory로 복사하라고 적는다. 그래서 getDeclaredMethods()를 두 번 부르면 서로 다른 배열에 서로 다른 Method 객체가 담겨 온다. 복사하는 이유는 setAccessible 같은 상태가 Method 객체마다 따로 있기 때문이다. 어떤 라이브러리가 자기 사본에 접근 검사를 끈다고 해서 다른 코드가 받은 사본의 검사까지 꺼지면 안 된다. 같은 메서드인지 비교할 때 ==가 아니라 equals를 써야 하는 것도 이 때문이다.

    Class 객체는 언제 생기고, 언제 초기화되는가

    앞 예제의 후반부는 InitProbe라는 클래스의 static 초기화 블록이 언제 실행되는지 보여 준다. 출력을 보면 클래스 리터럴을 평가했을 때도, 클래스 로더의 loadClass를 불렀을 때도, Class.forName(이름, false, 로더)를 불렀을 때도 초기화 블록은 실행되지 않았다. 인자 하나짜리 Class.forName(이름)을 부른 순간에야 [InitProbe 초기화 실행]이 찍혔다. 그런데도 마지막 줄을 보면 네 방법으로 얻은 Class 객체는 모두 같다. 즉 Class 객체가 존재하는 것과 그 클래스가 초기화된 것은 별개의 상태다.

    JVMS 5장은 클래스가 쓰이기까지의 과정을 세 단계로 나눈다. 로딩(loading)은 이름으로 클래스의 이진 표현(클래스 파일)을 찾아 그로부터 클래스를 만드는 과정이다. 링크(linking)는 그 클래스를 JVM의 실행 상태에 결합하는 과정으로, 검증(verification)과 준비(preparation, static 필드를 기본값으로 잡는 일), 그리고 심볼릭 참조의 해석을 포함한다. 초기화(initialization)는 클래스 초기화 메서드 , 즉 static 초기화 블록과 static 필드 초기화 식을 실행하는 단계다. Class 객체는 로딩 단계에서 생기므로, 초기화되지 않은 클래스의 Class 객체도 얼마든지 손에 쥘 수 있다.

    초기화가 언제 일어나는지는 JLS §12.4.1이 정한다. 클래스의 인스턴스가 만들어질 때, 그 클래스가 선언한 static 메서드가 호출될 때, static 필드에 값이 대입될 때, 상수 변수(constant variable)가 아닌 static 필드가 사용될 때 바로 직전에 초기화된다. 같은 절은 "Class와 java.lang.reflect 패키지의 특정 리플렉션 메서드 호출도 초기화를 일으킨다"고 덧붙인다. 클래스 리터럴은 이 목록에 없으므로 InitProbe.class는 초기화를 일으키지 않았다. Class.forName(String)은 Javadoc에 Class.forName(className, true, currentLoader)와 같다고 적혀 있고, 두 번째 인자 true가 "초기화까지 하라"는 뜻이다.

    이 차이를 이용한 대표적인 관례가 JDBC 드라이버 등록이다. java.sql.Driver의 Javadoc은 드라이버 클래스가 로딩될 때 자기 인스턴스를 만들어 DriverManager에 등록해야 하며, 그래서 사용자가 Class.forName("foo.bah.Driver")를 호출해 드라이버를 로딩하고 등록할 수 있다고 설명한다. 이름만 알고 있는 클래스를 초기화시켜 그 static 초기화 블록이 등록이라는 부수 효과를 내게 하는 방식이다. 지금의 DriverManager는 서비스 제공자 로딩(ServiceLoader)으로 드라이버를 찾으므로 이 호출을 직접 쓸 일은 드물지만, 오래된 코드에서 이 줄을 만나면 무엇을 하려는 것인지 알 수 있어야 한다. 반대로 프레임워크가 클래스 경로를 훑으며 수많은 클래스의 메타데이터만 읽고 싶을 때는 초기화를 일으키지 않는 방법을 골라야 한다. 초기화는 임의의 코드(static 블록)를 실행하는 일이기 때문이다.

    "하나뿐"에 붙는 조건: 클래스 로더

    앞 절에서 "하나의 클래스 로더 안에서" Class 객체는 하나뿐이라고 했다. 이 조건은 장식이 아니다. JVMS §5.3은 클래스가 만들어진 뒤에는 이름만이 아니라 이진 이름과 정의 로더(defining loader)의 쌍으로 결정된다고 적는다. 같은 클래스 파일을 서로 다른 로더가 읽으면 이름이 같은 서로 다른 두 타입이 생긴다. 직접 확인해 보자. 컴파일 결과가 있는 out 디렉터리를 부모가 플랫폼 로더인 새 URLClassLoader로 한 번 더 읽는다. 부모가 애플리케이션 로더가 아니므로 이 로더는 lab.reflect.Item을 위임하지 않고 직접 정의한다.

    메서드 탐색: getMethods와 getDeclaredMethods

    이제 Class 객체에 메서드 목록을 묻는다. 탐색 메서드는 두 계열로 나뉜다. getMethods()와 getMethod(이름, 타입...)은 상속받은 것을 포함해 public 메서드만 대상으로 한다. getDeclaredMethods()와 getDeclaredMethod(이름, 타입...)은 접근 제어자와 상관없이 그 클래스에 직접 선언된 메서드만 대상으로 한다. 아래 예제는 두 목록을 출력한다. Javadoc은 두 메서드가 돌려주는 배열이 정렬되어 있지 않고 특정한 순서도 없다고 명시하므로, 출력을 정렬해서 비교한다.

    package lab.reflect;

import java.lang.reflect.Method;
import java.lang.reflect.Modifier;
import java.util.Arrays;
import java.util.stream.Collectors;

public class MethodListMain {
    public static void main(String[] args) {
        Class type = Book.class;
        System.out.println("== getMethods()");
        print(type.getMethods());
        System.out.println("== getDeclaredMethods()");
        print(type.getDeclaredMethods());
    }

    static void print(Method[] methods) {
        Arrays.stream(methods)
              .map(MethodListMain::describe)
              .sorted()   // 반환 순서는 정해져 있지 않으므로 정렬해서 출력한다
              .forEach(s -> System.out.println("  " + s));
    }

    static String describe(Method m) {
        String params = Arrays.stream(m.getParameterTypes())
                              .map(Class::getSimpleName)
                              .collect(Collectors.joining(", "));
        String mod = Modifier.toString(m.getModifiers() & Modifier.methodModifiers());
        String flags = (m.isBridge() ? " [bridge]" : "") + (m.isSynthetic() ? " [synthetic]" : "");
        return m.getName() + "(" + params + ") " + mod + " <- "
                + m.getDeclaringClass().getSimpleName() + flags;
    }
}

    getMethods()에는 Item.label과 Object의 public 메서드 9개(equals, getClass, hashCode, notify, notifyAll, toString, wait 세 개)가 함께 나온다. 반면 package-private인 of와 private인 secret은 빠진다. getDeclaredMethods()는 거꾸로다. 상속받은 것은 하나도 없고, 대신 of와 secret이 들어 있다. 상위 클래스의 private 메서드까지 모두 보고 싶다면 getSuperclass()를 따라 올라가며 각 클래스의 getDeclaredMethods()를 모아야 한다. 이 루프는 뒤의 활용 예제에서 필드에 대해 직접 짠다. 생성자와 static 초기화 블록()은 어느 목록에도 없다. 생성자는 Constructor로 따로 다루고, getDeclaredMethods의 Javadoc은 클래스 초기화 메서드가 결과에 포함되지 않는다고 명시한다.

    소스에 없는 메서드: 브리지 메서드

    두 목록 모두에 소스에 쓴 적 없는 compareTo(Object)가 있다. [bridge] [synthetic] 표시가 붙어 있다. getDeclaredMethods의 Javadoc도 선언된 메서드에 브리지 메서드와 컴파일러가 추가한 합성(synthetic) 메서드처럼 소스에 없는 메서드가 포함될 수 있다고 적는다. 왜 생겼는지 바이트코드로 보자.

    Comparable의 compareTo(T)는 타입 소거 후 클래스 파일에서 compareTo(Object)가 된다. 그런데 Book이 소스에 쓴 메서드의 디스크립터는 compareTo(Book)이다. JVM은 메서드를 이름과 디스크립터로 구별하므로, 이대로라면 Comparable 타입으로 compareTo(Object)를 호출하는 코드(예를 들어 Collections.sort 내부)가 Book의 메서드에 도달하지 못한다. 그래서 컴파일러가 compareTo(Object)를 하나 더 만들어, 인자를 Book으로 checkcast한 뒤 진짜 compareTo(Book)을 부르게 한다. 이것이 브리지 메서드(bridge method)다.

    리플렉션으로 메서드를 이름으로 모으는 코드에게 브리지 메서드는 함정이다. "이름이 compareTo인 메서드"를 찾으면 두 개가 나오고, 순서는 정해져 있지 않다. 경로 이름으로 메서드를 고르는 서블릿을 만든다면 같은 경로에 메서드 두 개가 걸릴 수 있다. 그래서 리플렉션 기반 프레임워크는 브리지 메서드를 걸러 내거나 진짜 메서드로 바꿔 쓴다. 스프링 MVC의 핸들러 메서드 정보(AnnotatedMethod, 6.1 기준)는 생성 시 BridgeMethodResolver.findBridgedMethod로 브리지가 가리키는 원래 메서드를 찾아 둔다. 람다도 비슷한 흔적을 남긴다. 직접 확인해 보면 OpenJDK 21의 javac는 main 안의 람다 본문을 lambda$main$0이라는 private static 합성 메서드로 만들고, 이 메서드는 getDeclaredMethods() 결과에 isSynthetic()이 참인 채로 나온다.

    Modifier.toString이 "volatile"이라고 말할 때

    위 예제의 describe 메서드는 수정자를 출력하기 전에 m.getModifiers() & Modifier.methodModifiers()로 비트를 걸렀다. 거르지 않고 Modifier.toString(bridge.getModifiers())를 그대로 출력하면 브리지 메서드의 수정자가 public volatile로 나온다. 메서드에 volatile이라니 말이 안 된다. 이유는 접근 플래그의 비트 재사용에 있다. JVMS §4.6의 메서드 접근 플래그 표에서 0x0040은 ACC_BRIDGE이고, 0x0080은 ACC_VARARGS다. 그런데 필드 접근 플래그에서는 같은 0x0040이 ACC_VOLATILE, 0x0080이 ACC_TRANSIENT다. Modifier.toString(int)은 이 값이 어디서 왔는지 모르므로 0x0040을 volatile로 읽는다. 위 실행 결과의 플래그 0x1041은 ACC_SYNTHETIC(0x1000), ACC_BRIDGE(0x0040), ACC_PUBLIC(0x0001)의 합이다. 같은 이유로 가변 인자 메서드는 transient로 읽힌다. Method.toString()은 내부에서 메서드에 해당하는 비트만 남기므로 이 문제가 없고, 직접 출력할 때는 Modifier.methodModifiers()로 마스킹하면 된다.

    한 층 아래: getDeclaredMethods0는 HotSpot 안에서 무엇을 하는가

    앞에서 Class의 리플렉션 캐시가 비어 있으면 getDeclaredMethods0라는 네이티브 메서드로 VM에 목록을 요청한다고 했다. 이 요청을 받는 쪽을 열어 보면, 탐색 결과에 대해 Javadoc이 말하는 규칙들(생성자와 은 빠진다, 순서는 정해져 있지 않다)이 어디서 오는지 알 수 있다. 아래는 OpenJDK 21 HotSpot(github.com/openjdk/jdk21u) 소스 기준이다. 이 네이티브 메서드는 src/hotspot/share/prims/jvm.cpp의 JVM_GetClassDeclaredMethods로 연결되고, 실제 일은 같은 파일의 get_class_declared_methods_helper가 한다. 생성자 목록을 주는 JVM_GetClassDeclaredConstructors도 같은 함수를 "생성자를 원한다"는 인자만 바꿔 부른다.

    select_method의 조건은 한 줄짜리다. 생성자를 원할 때는 "초기화 메서드이면서 static이 아닌 것", 즉 만 고른다. 메서드를 원할 때는 "초기화 메서드가 아니고 overpass도 아닌 것"을 고른다. HotSpot에서 초기화 메서드는 과 을 함께 가리키므로, getDeclaredMethods의 Javadoc이 "클래스 초기화 메서드는 포함하지 않는다"고 적은 규칙은 바로 이 조건으로 구현된다. overpass 메서드는 소스에도 클래스 파일에도 없는 메서드다. classfile/defaultMethods.cpp의 주석에 따르면, 인터페이스의 default 메서드가 서로 충돌하거나 후보가 하나도 없을 때 VM이 클래스 로딩 중에 예외를 던지는 메서드를 만들어 메서드 배열에 넣는데, 이것이 overpass다. VM이 자기 사정으로 넣은 메서드이니 리플렉션 결과에서는 뺀다. 컴파일러가 만든 브리지 메서드는 클래스 파일에 실제로 있으므로 빠지지 않는다는 점과 대비된다.

    Reflection::new_method가 채우는 내용도 앞 절들의 관찰을 설명해 준다. 선언 클래스의 미러(Class 객체), 메서드 배열 안의 번호인 slot(method_idnum), 이름, 매개변수·반환·예외 타입의 Class 배열, 수정자, override = false, 제네릭 시그니처 문자열(Signature 속성이 있을 때), 애노테이션 바이트 배열을 넣는다. 이름은 StringTable::intern으로 인턴한 문자열이다. 그래서 getDeclaredMethods()로 얻은 Method의 getName()은 intern()한 결과와 ==로 같다(직접 실행해 true를 확인했다). 루트의 override는 이렇게 언제나 false로 시작하고, 사본을 만드는 Method.copy도 override를 복사하지 않는다. 새로 받은 사본이 접근 검사를 다시 하는 것은 이 때문이다.

    링크는 하고 초기화는 하지 않는다: -Xlog로 확인하기

    2단계의 link_class는 앞의 "로딩·링크·초기화" 구분을 실제로 볼 기회다. 앞의 InitProbe에 빈 public 메서드 ping()을 하나 더하고, 초기화 없이 로딩한 뒤 getDeclaredMethods(), 생성자 호출, invoke를 차례로 한다. -Xlog:class+init=info는 HotSpot이 클래스를 검증(verification, 링크의 첫 단계)하고 초기화하는 순간을 기록한다.

    반환 순서가 정해져 있지 않은 이유: 이름 심볼의 주소로 정렬된 배열

    3단계는 메서드 배열을 "처음부터" 돈다. 그러니 결과의 순서는 메서드 배열의 순서와 같다. 이 배열은 소스에 쓴 순서가 아니다. 클래스 파일을 파싱하는 ClassFileParser가 메서드 배열을 Method::sort_methods(oops/method.cpp)로 정렬하는데, 비교 함수는 두 메서드 이름의 Symbol을 fast_compare로 비교한다. symbol.hpp에서 fast_compare는 두 Symbol 객체의 메모리 주소를 비교할 뿐이고, 주석에는 이 순서가 알파벳순이 아니라고 적혀 있다. 이렇게 정렬하는 이유는 InstanceKlass::quick_search에 있다. VM이 이름으로 메서드를 찾을 때(예를 들어 심볼릭 참조를 해석할 때) 이 배열에서 이름 심볼의 주소로 이진 탐색을 한다. 정렬의 목적은 VM 내부의 빠른 탐색이지 사람이 읽을 순서가 아니다.

    Symbol의 주소는 한 번의 실행 안에서는 바뀌지 않지만, 실행마다 같다는 보장은 없다. 직접 확인해 보자. Book.class.getDeclaredMethods()의 이름을 정렬하지 않고 그대로 출력하는 프로그램을 같은 명령으로 여덟 번 실행했다(브리지 메서드에는 *를 붙였다).

    코드도 클래스 파일도 그대로인데 두 가지 순서가 나왔다. -Xshare:off로 CDS 아카이브를 끄면 또 다른 순서가 나왔다. Javadoc이 "특정한 순서가 없다"고 한 것은 겸손한 표현이 아니라 구현이 실제로 그렇다는 뜻이다. 앞의 MethodListMain이 출력을 정렬한 이유이고, 뒤에서 만들 리플렉션 서블릿의 경로 중복 오류 메시지에 두 메서드가 어느 순서로 찍히는지도 실행마다 다를 수 있다. 반면 이 정렬 방식에서 확실하게 따라 나오는 성질도 하나 있다. 이름이 같은 메서드는 같은 Symbol을 가리키므로 배열에서 언제나 붙어 있다. 위 결과에서 compareTo 두 개가 항상 나란히 나온 것이 그 때문이다. 다만 같은 이름끼리의 앞뒤 순서는 소스가 약속하지 않으므로 기대지 말아야 한다.

    메서드 동적 호출: Method.invoke가 실행 시점에 대신 하는 검사

    찾은 메서드를 호출해 보자. 아래 예제는 정상 호출 세 가지와, 리플렉션이 실행 시점에 잡아내는 오류 여섯 가지를 차례로 일으킨다.

    package lab.reflect;

import java.lang.reflect.InvocationTargetException;
import java.lang.reflect.Method;

public class MethodInvokeMain {
    public static void main(String[] args) throws Exception {
        Book book = new Book("자바", 20000, "978");
        Class type = book.getClass();

        // 1. 이름과 매개변수 타입으로 찾아 호출
        Method describe = type.getMethod("describe", String.class);
        Object r1 = describe.invoke(book, "책: ");
        System.out.println("1) " + r1);

        // 2. 기본형 매개변수: int.class로 찾고, 인자는 박싱되어 전달된다
        Method discount = type.getMethod("discount", int.class);
        Object r2 = discount.invoke(book, 10);
        System.out.println("2) " + r2 + " (" + r2.getClass().getName() + ")");

        // 3. static 메서드: 대상 객체 자리에 null
        Method of = type.getDeclaredMethod("of", String.class);
        System.out.println("3) " + ((Book) of.invoke(null, "스프링")).title);

        // 4. 대상 메서드가 던진 예외는 포장되어 나온다
        try {
            discount.invoke(book, 150);
        } catch (InvocationTargetException e) {
            System.out.println("4) " + e.getClass().getSimpleName() + " <- " + e.getCause());
        }

        // 5. 인자 개수·타입, 대상 객체의 타입이 틀리면 실행 시점에 IllegalArgumentException
        try {
            describe.invoke(book);
        } catch (IllegalArgumentException e) {
            System.out.println("5) " + e.getMessage());
        }
        try {
            discount.invoke(book, "10");
        } catch (IllegalArgumentException e) {
            System.out.println("6) " + e.getMessage());
        }
        try {
            discount.invoke("책이 아닌 객체", 10);
        } catch (IllegalArgumentException e) {
            System.out.println("7) " + e.getMessage());
        }

        // 6. private 메서드: 찾을 수는 있지만 호출은 접근 검사에 걸린다
        Method secret = type.getDeclaredMethod("secret");
        try {
            secret.invoke(book);
        } catch (IllegalAccessException e) {
            System.out.println("8) " + e.getMessage());
        }
        secret.setAccessible(true);
        System.out.println("9) " + secret.invoke(book));

        // 7. 오버로딩 구분은 매개변수 타입으로: int와 Integer는 다르다
        try {
            type.getMethod("discount", Integer.class);
        } catch (NoSuchMethodException e) {
            System.out.println("10) " + e.getMessage());
        }
    }
}
    1) 책: 자바(20000)
2) 18000 (java.lang.Integer)
3) 스프링
4) InvocationTargetException <- java.lang.IllegalArgumentException: percent=150
5) wrong number of arguments: 0 expected: 1
6) argument type mismatch
7) object is not an instance of declaring class
8) class lab.reflect.MethodInvokeMain cannot access a member of class lab.reflect.Book with modifiers "private"
9) isbn=978
10) lab.reflect.Book.discount(java.lang.Integer)

    1번은 기본이다. getMethod에 이름과 매개변수 타입 목록을 주면 Method가 나오고, invoke(대상 객체, 인자...)로 호출한다. 메서드를 이름만으로 찾지 않고 매개변수 타입까지 요구하는 이유는 자바가 오버로딩을 허용하기 때문이다. 이름이 같아도 매개변수 타입이 다르면 다른 메서드이고, 클래스 파일에서도 디스크립터가 다르다. 10번이 그 결과다. discount(int)는 있지만 discount(Integer)는 없으므로 NoSuchMethodException이 난다. 컴파일러였다면 오토박싱을 고려해 오버로딩을 해석했겠지만, getMethod는 정확히 일치하는 매개변수 타입만 찾는다.

    2번은 기본형이 어떻게 오가는지 보여 준다. invoke의 인자는 Object...이므로 10은 Integer로 박싱되어 Object[]에 담기고, 리플렉션이 이를 다시 int로 풀어 메서드에 넘긴다. 반환값 18000도 int가 아니라 java.lang.Integer로 돌아온다. 이 변환에는 규칙이 있다. Method.invoke의 Javadoc은 기본형 매개변수에 대해 언래핑 변환을 하고, 필요하면 메서드 호출 변환을 적용한다고 적는다. 그래서 같은 discount에 (short) 10이나 'a'를 넘기면 int로 넓혀져 정상 호출되지만, 10L은 long을 int로 좁혀야 하므로 6번과 같은 argument type mismatch가 난다(별도로 실행해 확인했다). 3번은 static 메서드다. static 메서드에는 대상 객체가 없으므로 Javadoc에 따라 첫 인자는 무시되고 null을 넘겨도 된다.

    4번부터가 이 절의 핵심이다. 리플렉션 호출에서 나는 오류는 원인이 어디에 있느냐에 따라 다른 예외가 된다. 정리하면 다음 표와 같다.

    4번을 자세히 보자. discount는 범위를 벗어난 할인율에 IllegalArgumentException을 던지도록 작성되었다. 그런데 invoke를 부른 쪽이 받은 것은 InvocationTargetException이고, 원래의 IllegalArgumentException은 그 원인으로 들어 있다. 만약 리플렉션이 대상 메서드의 예외를 그대로 내보냈다면, 호출자는 5~7번처럼 "리플렉션 호출 자체가 잘못된" IllegalArgumentException과 "호출은 제대로 됐는데 비즈니스 로직이 던진" IllegalArgumentException을 구별할 수 없다. 한 겹 감싸는 설계 덕분에 둘이 구별된다. 리플렉션 위에 무언가를 쌓는 쪽은 이 포장을 벗겨 원래 예외를 다시 던지는 책임을 진다. 스프링 MVC의 InvocableHandlerMethod.doInvoke(6.1 기준)를 보면 method.invoke(getBean(), args)로 컨트롤러 메서드를 호출한 뒤, InvocationTargetException을 잡아 원인이 RuntimeException이면 그것을 그대로 다시 던진다. 소스의 주석은 그 이유를 예외 처리기(HandlerExceptionResolver)를 위해서라고 적는다. 여러분의 @ExceptionHandler가 컨트롤러가 던진 원래 예외 타입을 받을 수 있는 것은 이 포장 벗기기 덕분이다.

    8번과 9번은 접근 검사다. getDeclaredMethod("secret")로 private 메서드의 Method를 찾는 것은 문제가 없다. 하지만 호출하면 IllegalAccessException이 난다. 메시지가 정확하다. 호출하는 클래스(MethodInvokeMain)가 Book의 private 멤버에 접근할 수 없다는 것이다. setAccessible(true)를 부른 뒤에는 같은 호출이 성공한다. 이 메서드가 정확히 무엇을 끄는지는 접근 검사 절에서 OpenJDK 소스로 본다.

    invoke 한 번이 지나는 길

    OpenJDK 21의 Method.invoke는 짧다. 먼저 override 플래그(접근 검사를 끄라는 표시, setAccessible(true)가 켠다)가 꺼져 있으면 Reflection.getCallerClass()로 누가 invoke를 불렀는지 구한 뒤 checkAccess로 접근 규칙을 확인한다. 다음으로 MethodAccessor라는 중계 객체를 가져오는데, 없으면 이때 ReflectionFactory가 만든다. 마지막으로 중계 객체의 invoke에 대상과 인자 배열을 넘긴다. JDK 18부터 이 중계 객체는 메서드 핸들(java.lang.invoke.MethodHandle)을 호출하는 DirectMethodHandleAccessor다. JEP 416(Reimplement Core Reflection with Method Handles)이 Method::invoke, Constructor::newInstance, Field::get·set을 메서드 핸들 위에 다시 구현했기 때문이다. JEP 416은 그 이전 구현이 처음 몇 번의 호출은 HotSpot의 네이티브 메서드로 처리하고, 호출이 쌓이면 그 메서드 전용 바이트코드를 생성해 쓰는 두 단계 방식이었다고 설명한다. JEP 416은 이제 네이티브 방식을 VM 초기화 초기, 메서드 핸들 기반이 준비되기 전의 짧은 구간에만 쓴다고 적는다. 다만 OpenJDK 21 소스(MethodHandleAccessorFactory.useNativeAccessor)에는 그 밖에도 시그니처 다형 메서드, 인자 슬롯이 255개 이상인 메서드처럼 메서드 핸들의 제약 때문에 네이티브 방식으로 돌아가는 예외가 몇 가지 남아 있다.

    여기서 하나 짚어 둘 것은 "호출자"가 접근 검사의 기준이라는 점이다. 같은 Method 객체라도 어느 클래스의 코드에서 invoke를 부르느냐에 따라 검사 결과가 달라진다. Book 안에서 secret의 Method를 invoke하면 private 접근이 허용된다. 언어의 접근 규칙이 "이 코드가 어디에 쓰여 있는가"를 기준으로 하듯, 리플렉션도 호출 스택을 거슬러 올라가 호출한 클래스를 찾아 같은 규칙을 적용한다. 이렇게 호출자에 따라 동작이 달라지는 JDK 메서드에는 내부적으로 @CallerSensitive가 붙어 있다.

    한 층 더 아래: DirectMethodHandleAccessor 안에서 일어나는 일

    앞 절은 Method.invoke가 중계 객체에 일을 넘기는 데까지 보았다. 이번에는 그 중계 객체 안을 연다. 무엇을 들고 있는지, 예외 메시지 세 가지(wrong number of arguments, object is not an instance of declaring class, argument type mismatch)가 정확히 어디서 만들어지는지, 첫 호출이 왜 비싼지를 OpenJDK 21의 jdk.internal.reflect 소스와 실험으로 확인한다.

    숨겨진 프레임을 꺼내 보기

    일반 스택 트레이스에는 리플렉션 내부 프레임이 거의 보이지 않는다. StackWalker는 기본적으로 리플렉션 프레임을 숨기고, Javadoc에 따르면 SHOW_REFLECT_FRAMES 옵션은 Method.invoke와 그 구현 클래스의 프레임을, SHOW_HIDDEN_FRAMES 옵션은 그에 더해 구현마다 다른 숨은 프레임까지 보여 준다. 리플렉션으로 호출된 메서드 안에서 세 방식으로 스택을 출력해 보자.

    예외 메시지 세 가지가 만들어지는 곳

    앞 절 예제의 5)~7)번 메시지가 어디서 나오는지 이제 정확히 짚을 수 있다. 두 가지는 메서드 핸들을 부르기 전에 중계 객체가 직접 검사한다. checkArgumentCount는 인자 배열의 길이가 매개변수 수와 다르면 wrong number of arguments: 0 expected: 1을 만들고, checkReceiver는 인스턴스 메서드일 때 declaringClass.isAssignableFrom(obj.getClass())가 거짓이면 object is not an instance of declaring class를 만든다(대상이 null이면 이 줄에서 NullPointerException이 나는데, Javadoc이 정한 동작이다).

    세 번째인 argument type mismatch는 사정이 다르다. 인자의 타입 변환은 asType이 만든 어댑터가 핸들 안에서 한다. MethodHandle.asType의 Javadoc은 참조형을 기본형으로 바꿀 때 언박싱 뒤에 넓히는 변환을 적용한다고 정하면서, "T0이 Object인 경우 이것이 Method.invoke가 허용하는 변환"이라고 덧붙인다. 앞에서 (short) 10은 int 매개변수에 들어가고 10L은 실패했던 규칙이 바로 이것이다. 변환에 실패하면 어댑터는 ClassCastException을 던진다. 문제는 대상 메서드의 본문이 던진 ClassCastException도 같은 catch에 걸린다는 점이다. 위 실험의 A와 B가 그 두 경우다.

    중계 객체는 이 둘을 예외의 스택 트레이스로 구별한다. AccessorUtils.isIllegalArgument는 예외가 난 프레임부터 아래로 내려가며 본다. 맨 위 프레임이 Class.cast나 Objects.requiresNonNull이면 그 하나는 건너뛴다(참조형 변환 어댑터의 ClassCastException은 Class.cast에서 나고, LambdaForm 프레임은 숨은 프레임이라 스택 트레이스에 기록되지 않는다). 이름 없는 모듈이나 java.base 밖의 프레임을 만나면 대상 메서드의 코드에서 난 것이므로 거짓을 돌려준다. java.base 안이라도 java.lang.reflect, java.lang.invoke, jdk.internal.reflect, sun.invoke.util 네 패키지 밖이면 역시 거짓이다. 이 네 패키지의 프레임만 지나 DirectMethodHandleAccessor 자신에 닿으면 변환 단계에서 난 것으로 보고 참을 돌려준다. 참이면 원인 없이 IllegalArgumentException("argument type mismatch")를 새로 던지고, 거짓이면 InvocationTargetException으로 감싼다. A는 변환 어댑터에서 났으니 전자, B는 Probe.unsafeCast(이름 없는 모듈) 프레임에서 났으니 후자다. NullPointerException도 같은 판정을 거친다. C는 null이 String 매개변수에 그대로 들어가 본문의 s.length()에서 났으므로 InvocationTargetException이고, D는 null을 int로 언박싱하다 sun.invoke.util.ValueConversions 안에서 났으므로 IllegalArgumentException이 되었다. Javadoc의 "기본형 인자의 언래핑 변환이 실패하면 IllegalArgumentException"이라는 문장이 이렇게 지켜진다.

    첫 invoke가 비싼 이유와, 사본끼리 나눠 쓰는 중계 객체

    중계 객체는 Method를 처음 invoke할 때 만들어진다. 그때 무슨 일이 일어나는지 클래스 로딩 기록으로 세어 보자. 문자열 연결이 없는 getPrice()를 고른 것은, 문자열 연결이 invokedynamic으로 컴파일되어 그 부트스트랩이 따로 메서드 핸들 클래스를 만들기 때문이다(그 몫이 섞이지 않게 했다).

    package lab.reflect;

import java.lang.reflect.Method;

public class FirstInvoke {
    public static void main(String[] args) throws Exception {
        Book book = new Book("자바", 20000, "978");
        Method a = Book.class.getMethod("getPrice");
        Method b = Book.class.getMethod("getPrice");   // 같은 메서드의 다른 사본
        Method c = Book.class.getMethod("discount", int.class);
        System.out.println("== 1) a 첫 invoke");
        a.invoke(book);
        System.out.println("== 2) a 두 번째 invoke");
        a.invoke(book);
        System.out.println("== 3) b 첫 invoke");
        b.invoke(book);
        System.out.println("== 4) c 첫 invoke");
        c.invoke(book, 10);
        System.out.println("== 5) c 두 번째 invoke");
        c.invoke(book, 10);
        System.out.println("== 끝");
    }
}

    1번에서 클래스 86개가 로딩되었다. 대부분은 이 프로세스에서 처음 쓰이는 java.lang.invoke 기반 클래스로, CDS 아카이브(source: shared objects file)에서 왔다. 나머지 5개는 source: __JVM_LookupDefineClass__로 기록된 LambdaForm$DMH/0x..., LambdaForm$MH/0x...다. 위 스택에서 본 그 숨은 클래스들을 JDK 내부의 바이트코드 생성기(InvokerBytecodeGenerator)가 이 자리에서 만들어 정의한 것이다. 2번은 0개다. 3번도 0개라는 것이 중요하다. b는 getMethod로 따로 받은 사본인데 중계 객체를 새로 만들지 않았다. 4번에서 int 매개변수를 가진 discount를 처음 부르자 다시 14개가 로딩되었다. 인자 모양이 다르니 그 모양에 맞는 변환 어댑터와 LambdaForm이 새로 필요했던 것이다. 숫자 자체는 JDK 빌드와 CDS 아카이브 내용에 따라 달라지므로, 이 환경의 관찰로만 읽어야 한다.

    3번이 0인 이유는 Method.acquireMethodAccessor에 있다. 사본은 자신을 만든 루트 Method를 root 필드로 가리킨다. 사본에 중계 객체가 없으면 먼저 루트에게 있는지 묻고, 있으면 그것을 가져다 쓴다. 없으면 ReflectionFactory로 새로 만든 뒤 setMethodAccessor로 루트까지 거슬러 올라가며 저장한다. 즉 setAccessible 상태(override)는 사본마다 따로지만, 비싼 중계 객체는 루트를 통해 공유된다. 앞에서 "Method는 한 번 찾아 재사용하라"고 했는데, 정확히 말하면 재사용해서 아끼는 것은 탐색과 사본 배열 생성 비용이고, 중계 객체 생성은 루트 캐시 덕분에 사본을 새로 받아도 한 번뿐이다. 다만 루트는 ReflectionData의 소프트 참조 캐시에 걸려 있으므로, 그 캐시가 비워지면 새 루트와 함께 중계 객체도 다시 만들어질 수 있다.

    접근 검사에도 캐시가 있다. AccessibleObject.verifyAccess는 호출자가 선언 클래스 자신이면 바로 통과시키고, 그다음에는 accessCheckCache라는 volatile 필드를 본다. 직전에 검사를 통과한 호출자 클래스를 WeakReference로 기억해 두었다가 같은 호출자가 다시 오면 검사를 건너뛴다. protected 인스턴스 멤버처럼 대상 객체의 클래스까지 따져야 하는 경우에는 (호출자, 대상 클래스) 쌍을 기억한다. 캐시가 맞지 않을 때만 Reflection.verifyMemberAccess로 전체 규칙을 검사하고 결과를 캐시에 쓴다. 약한 참조이므로 이 캐시가 호출자 클래스를 GC로부터 붙잡아 두지는 않는다.

    호출자는 어떻게 찾는가: getCallerClass와 HotSpot의 스택 워크

    접근 검사의 기준은 호출자 클래스이고, Method.invoke는 override가 꺼져 있거나 대상이 호출자 민감 메서드일 때 Reflection.getCallerClass()로 그것을 구한다. 이 메서드는 @CallerSensitive와 @IntrinsicCandidate가 붙은 네이티브 메서드이고, 소스의 문서 주석은 "이 메서드를 부른 메서드의 호출자를 돌려주되 Method.invoke와 그 구현에 속한 프레임은 무시한다"고 적는다. 위의 숨은 프레임 목록에서 보았듯이 리플렉션과 메서드 핸들은 사용자 코드 사이에 내부 프레임을 여럿 끼워 넣는다. 리플렉션으로 Method.invoke 자체를 부르거나, 호출자 민감 메서드가 중계 객체를 거쳐 실행되면 진짜 호출자와 getCallerClass 사이에 그런 프레임이 쌓인다. VM은 어느 프레임까지 건너뛰어야 하는지를 어떻게 아는가.

    답은 HotSpot의 JVM_GetCallerClass(prims/jvm.cpp, OpenJDK 21 기준)에 있다. 이 함수는 현재 스레드의 자바 프레임을 위에서부터 차례로 훑는다(vframeStream). 규칙은 세 가지다.

    [0] Reflection.getCallerClass   반드시 이 메서드여야 한다 (아니면 InternalError)
[1] @CallerSensitive API        예: Method.invoke, Class.forName. 표시가 없으면 InternalError
[2] ...건너뛸 프레임...           is_ignored_by_security_stack_walk() 가 참이면 다음으로
[n] 호출자                       처음 만난 "건너뛰지 않는" 프레임의 선언 클래스를 돌려준다

    0번 프레임은 getCallerClass 자신이어야 하고, 0번과 1번 프레임의 메서드에는 caller_sensitive 표시가 있어야 한다. 아니면 CallerSensitive annotation expected at frame 1 같은 메시지의 InternalError를 던진다. 즉 이 메서드는 @CallerSensitive가 붙은 JDK API가 직접 부를 때만 쓸 수 있다. 2번부터는 Method::is_ignored_by_security_stack_walk(oops/method.cpp)가 참인 프레임을 건너뛴다. 그 조건은 Method.invoke 자신(인트린식 번호로 식별한다), jdk.internal.reflect.MethodAccessorImpl의 하위 클래스(DirectMethodHandleAccessor가 여기에 속한다)의 메서드, 그리고 메서드 핸들 인트린식이나 컴파일된 LambdaForm의 메서드다. 이 셋에 해당하지 않는 첫 프레임의 선언 클래스 미러가 호출자로 반환된다. jvm.cpp의 주석은 JIT 컴파일된 코드에서 같은 일을 하는 C2 인트린식 LibraryCallKit::inline_native_Reflection_getCallerClass를 함께 가리킨다.

    메서드의 caller_sensitive 표시는 클래스 파일을 파싱할 때 붙는다. ClassFileParser는 메서드에 @CallerSensitive 애노테이션이 있으면 이 표시를 켜는데, 부트스트랩·플랫폼 로더가 로딩한 클래스처럼 특권이 있는 코드에서만 인정하고 그 밖의 코드에서는 조용히 무시한다. 애플리케이션 클래스가 이 애노테이션을 흉내 내 호출자 판정을 속일 수는 없다는 뜻이다.

    호출자 민감 메서드를 리플렉션으로 부르면

    더 미묘한 경우는 대상 메서드가 호출자 민감 메서드일 때다. Class.forName(String)은 호출자의 클래스 로더로 클래스를 찾는다. 이것을 Method.invoke로 부르면 forName 입장에서 호출자는 누구여야 하는가. Method.invoke는 이 경우 미리 구한 호출자를 중계 객체에 ma.invoke(obj, args, caller)로 넘긴다. MethodHandleAccessorFactory는 대상 클래스에 맨 뒤에 Class 매개변수가 하나 더 있는 같은 이름의 메서드가 있으면 그것을 핸들로 잡는다(팩토리는 이름과 매개변수 타입으로 찾고, JDK 소스는 그런 메서드에 @CallerSensitiveAdapter를 붙여 표시한다). OpenJDK 21의 Class에는 private static Class forName(String className, Class caller)가 있어서, 리플렉션 경로에서는 이 메서드가 호출자를 인자로 받는다. 어댑터가 없는 호출자 민감 메서드는 호출자마다 만든 호출기(reflectiveInvoker)를 거친다. 직접 확인해 보자. plugins 디렉터리에만 있는 클래스를, 그 디렉터리를 읽는 URLClassLoader(부모는 애플리케이션 로더)가 로딩한 Plugin이 리플렉션으로 forName해 찾는다.

    package lab.plugin;      // plugins 디렉터리로 따로 컴파일한다

import java.lang.reflect.Method;
import java.util.function.Supplier;

public class Plugin implements Supplier {
    @Override
    public String get() {
        try {
            Method forName = Class.class.getMethod("forName", String.class);
            Class c = (Class) forName.invoke(null, "lab.plugin.Helper");
            return c.getName() + " 로더=" + c.getClassLoader().getClass().getSimpleName();
        } catch (ReflectiveOperationException e) {
            return e.toString();
        }
    }
}

    필드 탐색과 값 변경

    필드도 같은 두 계열로 탐색한다. getFields()와 getField(이름)은 상속을 포함한 public 필드, getDeclaredFields()와 getDeclaredField(이름)은 접근 제어자와 상관없이 그 클래스에 선언된 필드다. 찾은 Field로 get(대상)과 set(대상, 값)을 부르면 값을 읽고 쓸 수 있다. 아래 예제는 탐색과 기본적인 읽기·쓰기를 보여 주고, 이어서 final 필드와 JDK 내부 필드에 손을 대 본다. 레코드 Point는 public record Point(int x, int y) {} 한 줄로 선언했다.

    package lab.reflect;

import java.lang.reflect.Field;
import java.lang.reflect.Modifier;

public class FieldMain {
    public static void main(String[] args) throws Exception {
        Class type = Book.class;

        System.out.println("== getFields()");
        for (Field f : type.getFields()) print(f);
        System.out.println("== getDeclaredFields()");
        for (Field f : type.getDeclaredFields()) print(f);

        Book book = new Book("자바", 20000, "978");

        // 1. private 필드 읽고 쓰기
        Field price = type.getDeclaredField("price");
        try {
            price.get(book);
        } catch (IllegalAccessException e) {
            System.out.println("1) " + e.getMessage());
        }
        price.setAccessible(true);
        System.out.println("2) price = " + price.get(book) + ", getInt = " + price.getInt(book));
        price.set(book, 15000);
        System.out.println("3) getPrice() = " + book.getPrice());
        try {
            price.set(book, "15000");
        } catch (IllegalArgumentException e) {
            System.out.println("4) " + e.getMessage());
        }

        // 2. final 인스턴스 필드
        Field isbn = type.getDeclaredField("isbn");
        isbn.setAccessible(true);
        isbn.set(book, "999");
        System.out.println("5) getIsbn() = " + book.getIsbn());

        Field edition = type.getDeclaredField("edition");
        edition.setAccessible(true);
        edition.set(book, 2);
        System.out.println("6) 필드 값 = " + edition.get(book) + ", getEdition() = " + book.getEdition());

        // 3. static final 필드
        Field max = type.getField("MAX_TITLE");
        max.setAccessible(true);
        try {
            max.set(null, 200);
        } catch (IllegalAccessException e) {
            System.out.println("7) " + e.getMessage());
        }

        // 4. 레코드의 final 필드
        Point p = new Point(1, 2);
        Field x = Point.class.getDeclaredField("x");
        x.setAccessible(true);
        try {
            x.set(p, 10);
        } catch (IllegalAccessException e) {
            System.out.println("8) " + e.getMessage());
        }

        // 5. 상위 클래스의 필드는 getDeclaredField로 찾을 수 없다
        try {
            type.getDeclaredField("id");
        } catch (NoSuchFieldException e) {
            System.out.println("9) NoSuchFieldException: " + e.getMessage());
        }
        Field id = type.getSuperclass().getDeclaredField("id");
        System.out.println("10) " + id);

        // 6. JDK 내부 필드
        Field value = String.class.getDeclaredField("value");
        try {
            value.setAccessible(true);
        } catch (RuntimeException e) {
            System.out.println("11) " + e.getClass().getName());
            System.out.println("    " + e.getMessage());
        }
    }

    static void print(Field f) {
        System.out.printf("  %-14s %-8s %s%n", Modifier.toString(f.getModifiers()), f.getType().getSimpleName(), f.getName());
    }
}

JLS §4.12.4는 기본형이나 String 타입의 final 변수가 상수 식으로 초기화되면 상수 변수(constant variable)라고 정의하고, 컴파일러는 상수 변수를 읽는 곳을 그 값으로 바꿔 쓴다. 그러니 필드의 메모리를 아무리 바꿔도, 이미 컴파일된 getEdition()에는 1이 박혀 있다. 반면 isbn은 선언에서 초기화하지 않고 생성자에서 대입하는 빈 final(blank final) 필드라 상수 변수가 아니다. getIsbn()은 실제로 getfield로 필드를 읽으므로 바뀐 값이 보인다.

    JLS §17.5.3(Subsequent Modification of final Fields)은 바로 이 상황을 다룬다. 이 절은 역직렬화처럼 객체를 만든 뒤 final 필드를 바꿔야 하는 경우가 있고, final 필드는 리플렉션 등으로 바꿀 수 있다고 인정한다. 그러면서 합리적인 의미를 갖는 유일한 패턴은 객체를 만든 직후 final 필드를 갱신하고, 갱신이 끝날 때까지 다른 스레드에 객체를 공개하지도 필드를 읽지도 않는 것이라고 제한한다. 이어서 두 가지 복잡한 점을 든다. 하나는 우리가 본 것으로, 선언에서 상수 식으로 초기화된 final 필드는 사용하는 곳이 컴파일 시점에 상수로 바뀌므로 변경이 관찰되지 않을 수 있다는 것이다. 다른 하나는 명세가 final 필드에 대한 공격적인 최적화를 허용한다는 것이다. 한 스레드 안에서도 final 필드의 읽기를 생성자 밖에서 일어난 변경과 순서를 바꿀 수 있다. 즉 상수 변수가 아닌 isbn조차, 바꾼 값이 언제나 보인다고 명세가 보장하지 않는다. 우리 예제에서 5번이 999를 보여 준 것은 이 실행에서 그렇게 동작했다는 사실일 뿐이다.

    7번과 8번은 아예 실패했다. Field.set의 Javadoc은 final 필드에 쓰기가 허용되는 조건을 네 가지로 못 박는다. 이 Field 객체에 대해 setAccessible(true)가 성공했을 것, 필드가 static이 아닐 것, 필드를 선언한 클래스가 숨은 클래스(hidden class)가 아닐 것, 레코드 클래스가 아닐 것. 하나라도 어기면 IllegalAccessException이다. MAX_TITLE은 static final이라 7번에서, 레코드 Point의 x는 레코드의 필드라 8번에서 막혔다. setAccessible(true)도 이 규칙은 넘지 못한다. OpenJDK 21의 구현을 보면, ReflectionFactory.newFieldAccessor가 필드 접근자를 만들 때 "final이면서, 접근 검사를 끄지 않았거나 신뢰할 수 있는 final(trusted final)인 필드"를 읽기 전용으로 만든다. Field 객체는 VM이 만들어 줄 때부터 trustedFinal이라는 표시를 갖고 있고, 위 Javadoc의 조건이 이 표시로 구현된다.

    static final 필드와 레코드 필드를 리플렉션으로 바꿀 수 없다는 것은 불편이 아니라 보장이다. 컴파일러와 JIT은 "이 값은 바뀌지 않는다"는 전제 위에서 코드를 만든다. final을 깨는 리플렉션은 그 전제를 깨고, 6번처럼 프로그램의 일부만 바뀐 값을 보는 상태를 만든다. 실무 코드에서 final 필드에 set을 쓸 일은 역직렬화 라이브러리 같은 아주 좁은 경우뿐이다.

    접근 검사와 모듈: setAccessible이 넘지 못하는 벽

    마지막 11번은 String의 내부 배열 필드 value에 setAccessible(true)를 시도했다. 이번에는 IllegalAccessException이 아니라 InaccessibleObjectException이 났고, 그것도 값을 읽기 전에 setAccessible 호출 자체에서 났다. 메시지는 java.base 모듈이 java.lang 패키지를 우리 코드가 속한 이름 없는 모듈(unnamed module)에 열어 주지(opens) 않았다고 말한다. 접근 검사가 두 층이라는 뜻이다.

    첫째 층은 언어의 접근 제어다. Method.invoke, Field.get·set, Constructor.newInstance는 override 플래그가 꺼져 있으면 호출자 클래스를 구해 public·protected·package-private·private 규칙을 검사한다. 이 검사는 멤버의 접근 제어자만 보지 않고 멤버를 선언한 클래스에 접근할 수 있는지도 본다. 소스 코드에서 다른 패키지의 package-private 클래스에 있는 public 메서드를 부를 수 없는 것과 같다(리플렉션 서블릿을 만든 뒤 이 규칙에 실제로 걸려 본다). setAccessible(true)는 이 층의 검사를 끈다.

    둘째 층은 Java 9에 들어온 모듈 시스템의 캡슐화다. setAccessible(true)는 아무 때나 성공하지 않는다. OpenJDK 21의 AccessibleObject.checkCanSetAccessible를 읽으면 허용 조건이 순서대로 나온다.

    1. 호출자와 멤버를 선언한 클래스가 같은 모듈이거나, 호출자가 java.base 모듈에 있으면 허용한다.
    2. 멤버를 선언한 클래스가 이름 없는 모듈(클래스패스에서 로딩된 클래스)에 있으면 허용한다.
    3. 선언한 클래스가 public이고 그 패키지가 호출자에게 exports되어 있으면서 멤버가 public이면 허용한다(protected static 멤버는 호출자가 하위 클래스일 때 허용한다).
    4. 그 패키지가 호출자에게 opens되어 있으면 허용한다.
    5. 그 밖에는 InaccessibleObjectException을 던진다.

    2번 조건 때문에, 클래스패스에 올린 애플리케이션 클래스끼리는 setAccessible(true)가 언제나 성공한다. 우리 예제들이 Book의 private 멤버에 자유롭게 접근할 수 있었던 이유다. 반면 String은 이름 있는 모듈 java.base에 있고, java.lang 패키지는 exports는 되어 있지만 opens되어 있지 않으며, value는 private이다. 1~4번 어디에도 해당하지 않으므로 거절된다.

    이 벽이 지금처럼 단단해진 것은 JDK 17부터다. JEP 403(Strongly Encapsulate JDK Internals, JDK 17)은 sun.misc.Unsafe 같은 핵심 내부 API를 제외한 JDK의 모든 내부 요소를 강하게 캡슐화했다. 이전 릴리스까지 이 캡슐화를 완화할 수 있게 해 주던 --illegal-access 옵션은 효력이 없어졌다. 다만 명령줄의 --add-opens는 여전히 쓸 수 있다. 실제로 같은 코드(value에 setAccessible(true)를 한 뒤 "abc"의 배열 길이를 읽는 코드)를 java --add-opens java.base/java.lang=ALL-UNNAMED로 실행하면 예외 없이 3이 출력된다. 이 옵션은 4번 조건을 실행 시점에 만들어 주는 것이다.

    실무에서 이 규칙이 드러나는 곳은 두 군데다. 하나는 오래된 라이브러리가 JDK 내부를 리플렉션으로 건드리다가 JDK 17 이상에서 InaccessibleObjectException을 내는 경우이고, 해법은 라이브러리를 올리거나 필요한 패키지만 --add-opens로 여는 것이다. 다른 하나는 애플리케이션 자체를 이름 있는 모듈로 만드는 경우다. 그때부터 애플리케이션 클래스도 2번 조건의 보호를 받지 못하므로, 리플렉션으로 private 멤버에 접근해야 하는 프레임워크에게 해당 패키지를 module-info.java에서 opens해 줘야 한다. 검사 결과를 예외 대신 boolean으로 받고 싶다면 Java 9에 추가된 trySetAccessible()을 쓴다.

    리플렉션 활용 예제: 요청 파라미터를 필드에 묶는 바인더

    지금까지의 도구로 실제로 쓸모 있는 것을 만들어 보자. HTTP 요청의 쿼리 파라미터는 전부 문자열이다(?name=kim&age=30). 이것을 같은 이름의 필드를 가진 객체에 타입을 맞춰 넣어 주는 바인더(binder)를 만든다. 대상 클래스는 바인더가 미리 알 수 없으므로, 필드 목록과 각 필드의 타입은 리플렉션으로 알아내야 한다. 덤으로 객체의 모든 필드를 출력하는 dump도 만든다.

    package lab.reflect;

import java.lang.reflect.Field;
import java.lang.reflect.Modifier;
import java.util.Map;
import java.util.Set;
import java.util.StringJoiner;

public class FieldBinder {

    // 요청 파라미터(문자열)를 같은 이름의 필드에 타입을 바꿔 넣는다
    public static void bind(Object target, Map params, Set allowed)
            throws IllegalAccessException {
        for (Class c = target.getClass(); c != Object.class; c = c.getSuperclass()) {
            for (Field field : c.getDeclaredFields()) {
                int mod = field.getModifiers();
                if (Modifier.isStatic(mod) || Modifier.isFinal(mod)) {
                    continue;
                }
                String raw = params.get(field.getName());
                if (raw == null || !allowed.contains(field.getName())) {
                    continue;
                }
                field.setAccessible(true);
                field.set(target, convert(raw, field.getType()));
            }
        }
    }

    static Object convert(String raw, Class type) {
        if (type == String.class) return raw;
        if (type == int.class || type == Integer.class) return Integer.parseInt(raw);
        if (type == long.class || type == Long.class) return Long.parseLong(raw);
        if (type == boolean.class || type == Boolean.class) return Boolean.parseBoolean(raw);
        throw new IllegalArgumentException("변환할 수 없는 타입: " + type.getName());
    }

    // 상위 클래스까지 올라가며 모든 인스턴스 필드를 출력한다
    public static String dump(Object target) throws IllegalAccessException {
        StringJoiner sj = new StringJoiner(", ", target.getClass().getSimpleName() + "[", "]");
        for (Class c = target.getClass(); c != Object.class; c = c.getSuperclass()) {
            for (Field field : c.getDeclaredFields()) {
                if (Modifier.isStatic(field.getModifiers())) {
                    continue;
                }
                field.setAccessible(true);
                sj.add(field.getName() + "=" + field.get(target));
            }
        }
        return sj.toString();
    }
}

    첫 줄부터 추적해 보자. bind는 SignupForm에서 시작해 getSuperclass()로 올라가다 Object에서 멈춘다. SignupForm의 네 필드 중 name, age, agree는 파라미터에 있고 허용 목록에도 있으므로 값이 들어간다. 이때 field.getType()이 돌려주는 Class 객체로 변환 방법을 고른다. age의 타입은 int.class이므로 Integer.parseInt("30")의 결과가 들어가고, agree는 boolean.class이므로 Boolean.parseBoolean("true")가 들어간다. Class 객체는 타입마다 하나뿐이므로 ==로 비교해도 안전하다. unknown 파라미터는 그런 이름의 필드가 없으니 아무 일도 일어나지 않는다. 바인더는 파라미터가 아니라 필드를 기준으로 돌기 때문이다.

    role은 파라미터에 ADMIN이 들어왔는데도 USER로 남았다. 허용 목록에 없기 때문이다. 이 줄이 이 예제에서 가장 중요하다. 허용 목록 없이 "이름이 맞는 필드는 전부 채운다"고 만들었다면, 사용자가 URL에 &role=ADMIN을 붙이는 것만으로 서버 객체의 권한 필드를 바꿀 수 있다. 리플렉션은 private 필드에도 값을 넣을 수 있으므로, 개발자가 화면에 입력 칸을 만들지 않은 필드도 요청 파라미터로 열린다. 스프링의 DataBinder Javadoc도 데이터 바인딩이 외부 클라이언트가 접근하거나 수정해서는 안 되는 객체 그래프의 일부를 노출해 보안 문제를 일으킬 수 있다고 경고하고, 바인딩할 필드를 제한하는 setAllowedFields(반대로 막을 필드를 지정하는 setDisallowedFields)를 제공한다. 참고로 스프링의 기본 바인딩은 필드에 직접 쓰지 않는다. 같은 Javadoc에 따르면 기본값은 자바빈 프로퍼티 접근(setter를 통한 접근)이고, 필드 직접 접근은 initDirectFieldAccess()로 고르는 대안이다.

    둘째 줄은 상속과 final을 보여 준다. id는 Item에 선언된 protected 필드인데, 루프가 상위 클래스로 올라갔기 때문에 7이 들어갔다. isbn은 파라미터와 허용 목록에 모두 있었지만 final이라 건너뛰었으므로 생성자가 넣은 000 그대로다. 앞 절에서 본 것처럼 final 필드에 억지로 쓰는 것은 명세가 의미를 보장하지 않는 일이니 바인더가 손대지 않는 것이 맞다. dump 출력에서 Book의 필드가 먼저, Item의 id가 나중에 나온 것은 루프가 하위 클래스부터 돌기 때문이다. 다만 한 클래스 안의 필드 순서는 Javadoc상 정해져 있지 않으므로, 이 출력 순서에 기대는 코드를 쓰면 안 된다.

    셋째 줄은 변환 실패다. "서른"은 정수로 파싱할 수 없으니 NumberFormatException이 바인더 밖으로 나왔다. 실제 웹 프레임워크라면 이 예외로 요청 처리 전체를 실패시키기보다 "어느 필드가 왜 실패했는지"를 모아 사용자에게 돌려줘야 한다. 스프링의 데이터 바인딩이 타입 변환 실패를 BindingResult에 typeMismatch 오류로 모으는 것이 바로 이 지점의 문제를 다루는 방식이다. 우리 바인더는 그 기능 없이, 리플렉션이 바인딩의 어느 부분을 맡는지만 보여 준다. 필드 목록을 얻고, 필드 타입으로 변환 방법을 고르고, 접근 검사를 끄고 값을 넣는 것까지가 리플렉션의 몫이고, 무엇을 허용할지와 실패를 어떻게 보고할지는 설계의 몫이다.

    생성자 탐색과 객체 생성

    바인더는 이미 만들어진 객체를 받았다. 하지만 프레임워크는 대개 객체 생성부터 맡는다. 스프링 컨테이너는 설정에 적힌 클래스의 빈을 만들고, 웹 프레임워크는 폼 객체를 만들어 바인딩한다. 클래스 이름만 알고 객체를 만들려면 생성자도 리플렉션으로 다뤄야 한다. 탐색 메서드는 역시 두 계열이다. getConstructors()는 public 생성자, getDeclaredConstructors()는 접근 제어자와 상관없이 그 클래스에 선언된 모든 생성자다. 생성자는 상속되지 않으므로(JLS §8.8) 두 메서드 모두 상위 클래스의 생성자는 돌려주지 않는다.

    Class.newInstance가 폐기 예정이 된 이유

    Class에는 무인자 생성자로 객체를 만드는 newInstance()가 직접 있다. 이 메서드는 Java 9부터 @Deprecated(since="9")다. Javadoc은 이유를 이렇게 설명한다. 이 메서드는 무인자 생성자가 던진 예외를 체크 예외까지 포함해 그대로 전파하므로, 컴파일러가 했을 컴파일 시점 예외 검사를 사실상 우회한다. 확인해 보자. Fragile의 생성자는 체크 예외 IOException을 선언하고 실제로 던진다.

Constructor.newInstance는 생성자의 예외를 체크 예외인 InvocationTargetException으로 감싸므로 이 문제가 없다. 그래서 Javadoc은 clazz.newInstance()를 clazz.getDeclaredConstructor().newInstance()로 바꾸라고 안내한다. 이 경우 추가로 생기는 InvocationTargetException과 NoSuchMethodException은 둘 다 ReflectiveOperationException의 하위 클래스다.

    이제 생성과 바인딩을 합칠 수 있다. 클래스만 받아 객체를 만들고 파라미터를 채우는 메서드다. 리플렉션 예외들이 공통 상위 타입 ReflectiveOperationException을 가지므로 선언이 짧아진다.

    static  T create(Class type, Map params, Set allowed)
        throws ReflectiveOperationException {
    T obj = type.getDeclaredConstructor().newInstance();
    FieldBinder.bind(obj, params, allowed);
    return obj;
}

    이 패턴은 프레임워크 곳곳에 있다. 스프링 6.1의 BeanUtils.instantiateClass(Constructor, Object...)는 ReflectionUtils.makeAccessible(ctor)로 접근 검사를 끈 뒤 ctor.newInstance(...)로 빈을 만든다. 생성자가 public이 아니어도 빈을 만들 수 있는 이유다. JPA도 같은 일을 한다. Jakarta Persistence 명세(3.1, §2.1)는 엔티티 클래스에 무인자 생성자가 있어야 하고 그 생성자는 public 또는 protected여야 한다고 요구한다. 조회 결과로 엔티티를 만들어야 하는 공급자는 각 엔티티 생성자에 무엇을 넘겨야 할지 알 수 없으니, 일단 무인자 생성자로 만들고 필드를 채우는 것이 가장 일반적인 방법이다.

    HTTP 서버 6: 리플렉션 서블릿

    이제 처음의 문제로 돌아간다. SwitchServlet은 경로마다 case를 적어야 했고, 모든 컨트롤러를 컴파일 시점에 알아야 했다. 리플렉션을 쓰면 규칙 하나로 이것을 대신할 수 있다. "/hello 경로는 컨트롤러의 hello 메서드가 처리한다." 서블릿은 시작할 때 등록된 컨트롤러 객체들의 메서드를 훑어 경로표를 만들고, 요청이 오면 경로로 메서드를 찾아 invoke한다. 서블릿 코드에는 어떤 컨트롤러 이름도 등장하지 않는다.
