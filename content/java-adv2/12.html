    이 회차의 질문: 코드에 붙은 정보는 누가 읽는가

    앞 회차에서 리플렉션(reflection)으로 클래스의 메서드 목록을 얻고, 이름으로 메서드를 찾아 호출하는 방법을 보았다. 리플렉션은 "무엇이 있는가"를 알려 준다. 이 클래스에 어떤 필드가 있고, 어떤 메서드가 있으며, 매개변수 타입은 무엇인지. 그런데 프레임워크가 정말 알고 싶은 것은 그다음이다. 이 메서드는 어떤 요청을 처리하는가, 이 필드는 비어 있어도 되는가, 이 클래스는 컨테이너가 관리해야 하는 객체인가. 이런 정보는 메서드의 시그니처나 필드의 타입 어디에도 들어 있지 않다. 코드의 의도에 관한 정보, 즉 코드에 대한 데이터(메타데이터, metadata)다.

    메타데이터를 어딘가에 적어 두는 방법은 여럿 있다. 메서드 이름에 규칙을 정해 둘 수도 있고, 표시용 인터페이스를 구현하게 할 수도 있고, 별도의 설정 파일에 "이 클래스의 이 메서드는 이 요청을 처리한다"라고 적을 수도 있다. 자바 5(애노테이션 관련 타입들의 Javadoc에 @since 1.5로 표시되어 있다)가 들여온 애노테이션(annotation)은 그 정보를 코드 바로 옆에, 컴파일러가 문법을 검사하는 형태로 적게 해 준다. 이 회차가 끝까지 붙들고 갈 사실은 하나다. 애노테이션은 스스로 아무 일도 하지 않는다. @Tag("order")를 붙였다고 해서 실행 흐름이 바뀌는 일은 없다. 그것을 읽는 누군가, 즉 컴파일러나 애노테이션 프로세서나 리플렉션으로 클래스를 훑는 프레임워크가 있어야 비로소 의미가 생긴다.

    그래서 이 회차는 애노테이션 하나가 거치는 여정을 따라간다. 소스 코드에 적힌 애노테이션이 컴파일러의 검사를 거쳐 클래스 파일의 어느 속성에 어떤 바이트로 기록되는지, 클래스 로더가 클래스를 올린 뒤 리플렉션이 그 바이트를 언제 어떻게 자바 객체로 되살리는지, 보존 정책(retention policy)이 이 여정을 어디서 끊는지 차례로 확인한다. 그 위에서 메타 애노테이션, 상속 규칙, 검증기 만들기, 자바 기본 애노테이션을 다룬다. 예제는 모두 이 글을 위해 새로 쓴 것이고, 실행 결과와 javap 출력은 Temurin JDK 21.0.13(macOS, arm64)에서 직접 얻은 것이다. 프록시 클래스 이름처럼 구현과 실행 환경에 따라 달라지는 값은 그렇다고 밝힌다.

    이 장의 핵심

    애노테이션은 선언에 붙는 상수 메타데이터다. 컴파일러는 그것을 검사한 뒤 보존 정책에 따라 버리거나(SOURCE) 클래스 파일에 기록한다(CLASS, RUNTIME). RUNTIME으로 기록된 것만 리플렉션이 읽을 수 있고, 읽는 순간 OpenJDK는 클래스 파일의 바이트와 애노테이션 인터페이스의 현재 정의(기본값 포함)를 합쳐 프록시 객체를 만든다. 동작은 언제나 읽는 쪽의 코드가 만든다.

    애노테이션이 필요한 이유: 이름 규칙의 한계

    리플렉션만으로 명령어 처리기를 만든다고 해 보자. 사용자가 입력한 문자열과 같은 이름의 메서드를 찾아 호출하는 방식이다. 앞 회차에서 배운 getMethod와 invoke만 있으면 된다.

    import java.lang.reflect.Method;

public class NameDispatch {
    public static class Commands {
        public void hello() { System.out.println("안녕하세요"); }
        public void time()  { System.out.println("시각 조회"); }
        public void shutdownNow() { System.out.println("서버를 끕니다!"); } // 내부용
    }

    public static void dispatch(Object handler, String input) throws Exception {
        try {
            Method m = handler.getClass().getMethod(input);
            m.invoke(handler);
        } catch (NoSuchMethodException e) {
            System.out.println("모르는 명령: " + input);
        }
    }

    public static void main(String[] args) throws Exception {
        Commands c = new Commands();
        dispatch(c, "hello");
        dispatch(c, "shutdownNow");
        dispatch(c, "toString");
        dispatch(c, "/hello");
    }
}

    네 번의 호출 결과를 하나씩 보자. 첫 번째는 의도대로 동작했다. 두 번째는 내부에서만 쓰려던 shutdownNow가 바깥 입력으로 호출되었다. 이름 규칙 방식에서는 "public 메서드이면 곧 명령"이므로, 명령이 아닌 public 메서드를 숨길 방법이 없다. 세 번째 toString은 아무 출력도 없지만 실패한 것이 아니다. getMethod는 상속받은 public 메서드까지 찾기 때문에 Object.toString()이 실제로 호출되었고, 반환값을 버렸을 뿐이다. 같은 방식으로 "wait"를 넣으면 Object.wait()가 모니터를 쥐지 않은 채 호출되어 IllegalMonitorStateException이 InvocationTargetException에 싸여 나온다(직접 실행하면 원인 예외의 메시지는 current thread is not owner다). 네 번째는 /hello라는 명령을 만들 수 없다는 것을 보여 준다. 자바 식별자에는 /가 들어갈 수 없기 때문이다.

    문제를 정리하면 세 가지다. 첫째, 선택의 기준이 이름 하나뿐이라 "이 메서드는 명령이다"라는 의사 표시와 "메서드의 이름"이 한 몸이 되었다. 둘째, 이름이 표현할 수 있는 것에 한계가 있다. 식별자 문법을 벗어난 문자열, 한 메서드에 여러 명령 연결, "관리자 전용" 같은 부가 정보는 이름에 담을 수 없다. 셋째, 실수를 아무도 잡아 주지 않는다. 명령 메서드 이름을 helo로 잘못 써도 컴파일러는 그것이 오타인지 알 길이 없다. 표시용 인터페이스(marker interface)는 클래스 단위의 표시만 가능하고 값을 담지 못하며, 외부 설정 파일은 코드와 떨어져 있어 메서드 이름을 바꿀 때 함께 고치지 않으면 실행 중에야 어긋남이 드러난다.

    애노테이션으로 바꾸면 이 세 문제가 각각 풀린다. 명령이라는 표시를 이름과 분리해 별도의 정보로 붙이고, 그 정보 안에 원하는 문자열과 부가 속성을 담는다.

    import java.lang.annotation.*;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.METHOD)
public @interface Command {
    String[] value();          // 이 메서드가 처리할 명령 문자열들
    boolean admin() default false;
}
    import java.lang.reflect.Method;
import java.util.HashMap;
import java.util.Map;

public class AnnoDispatch {
    public static class Commands {
        @Command({"/hello", "/hi"})
        public void hello() { System.out.println("안녕하세요"); }

        @Command("/time")
        public void time() { System.out.println("시각 조회"); }

        @Command(value = "/shutdown", admin = true)
        public void shutdownNow() { System.out.println("서버를 끕니다!"); }

        public void helper() { } // @Command가 없으니 외부에서 부를 수 없다
    }

    private final Object handler;
    private final Map table = new HashMap<>();

    public AnnoDispatch(Object handler) {
        this.handler = handler;
        for (Method m : handler.getClass().getDeclaredMethods()) {
            Command cmd = m.getAnnotation(Command.class);
            if (cmd == null) continue;
            for (String name : cmd.value()) {
                Method prev = table.putIfAbsent(name, m);
                if (prev != null) {
                    throw new IllegalStateException("중복 명령 " + name + ": " + prev.getName() + ", " + m.getName());
                }
            }
        }
    }

    public void dispatch(String input, boolean isAdmin) throws Exception {
        Method m = table.get(input);
        if (m == null) { System.out.println("모르는 명령: " + input); return; }
        if (m.getAnnotation(Command.class).admin() && !isAdmin) {
            System.out.println("권한 없음: " + input); return;
        }
        m.invoke(handler);
    }

    public static void main(String[] args) throws Exception {
        AnnoDispatch d = new AnnoDispatch(new Commands());
        d.dispatch("/hi", false);
        d.dispatch("/shutdown", false);
        d.dispatch("/shutdown", true);
        d.dispatch("helper", false);
        d.dispatch("toString", false);
    }
}

    구조가 바뀐 지점을 짚어 보자. 생성자에서 한 번만 getDeclaredMethods()로 이 클래스가 선언한 메서드를 훑고, @Command가 붙은 것만 골라 "명령 문자열 → 메서드" 표를 만든다. getDeclaredMethods는 상속받은 Object의 메서드를 돌려주지 않고, 애노테이션이 없는 helper는 표에 들어가지 않으니 바깥에서 부를 길이 없다. 한 메서드에 명령 두 개를 연결하는 것도, 관리자 전용 표시도 애노테이션의 값으로 표현했다. 두 메서드가 같은 명령을 주장하면 실행 시작 시점(생성자)에 바로 예외를 던져, 잘못된 설정이 첫 요청이 올 때까지 숨어 있지 않게 했다. 이것이 스프링 MVC가 요청 매핑 정보를 애플리케이션 시작 시점에 모아 두는 것과 같은 발상이다. 매 요청마다 리플렉션으로 메서드를 뒤지지 않고, 시작할 때 한 번 읽어 자료구조로 만들어 둔다.

    여기서 한 가지를 분명히 해 두자. @Command를 붙인 것만으로는 아무 일도 일어나지 않는다. admin = true가 권한 검사가 되는 것은 dispatch 메서드 안의 if문 덕분이다. 그 if문을 지우면 admin 속성은 그냥 기록된 상수일 뿐이다. 스프링의 @Transactional, JPA의 @Entity, JUnit의 @Test도 똑같다. 모두 그 애노테이션을 찾아 읽는 코드가 프레임워크 안에 있어서 의미를 가진다. 이 원리를 놓치면 "애노테이션을 붙였는데 왜 동작하지 않느냐"는 질문의 답을 엉뚱한 곳에서 찾게 된다. 답은 대개 "읽는 쪽이 그 위치를 읽지 않는다"이다.

    애노테이션 정의: @interface와 요소

    애노테이션 타입은 @interface 키워드로 선언한다. 자바 언어 명세(JLS)는 이것을 애노테이션 인터페이스(annotation interface)라고 부른다. 이름 그대로 특별한 종류의 인터페이스이며, 몸체에 선언하는 메서드처럼 생긴 것들을 요소(element)라고 한다. 요소의 반환 타입이 그 요소에 담길 값의 타입이고, default 절로 기본값을 줄 수 있다.

    import java.lang.annotation.*;

@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.TYPE, ElementType.METHOD, ElementType.FIELD})
public @interface Tag {
    String value();                         // 기본값 없음: 쓸 때 반드시 지정
    int priority() default 5;
    String[] aliases() default {};
    Class type() default Object.class;
    ElementType kind() default ElementType.TYPE;
}

    요소의 타입은 아무것이나 될 수 없다. JLS §9.6.1은 허용되는 타입을 다음으로 한정하고, 그 밖의 타입을 쓰면 컴파일 오류다.

    이 제약들은 제각각의 금지 조항처럼 보이지만 이유는 하나로 모인다. 애노테이션의 값은 컴파일 시점에 정해져 클래스 파일에 상수로 기록되어야 한다. 기본형과 String은 상수 풀(constant pool)에 그대로 넣을 수 있고, 클래스는 클래스 이름으로, enum은 타입 이름과 상수 이름의 쌍으로, 중첩 애노테이션은 같은 구조의 재귀로 적을 수 있다. 반면 Object나 List의 인스턴스는 실행해 봐야 만들어지는 객체라 바이트로 미리 적어 둘 방법이 없다. System.currentTimeMillis() 같은 메서드 호출이 금지되는 것도, 매개변수가 금지되는 것도 같은 이유다. 요소는 "값을 꺼내는 이름"일 뿐 계산하는 메서드가 아니다.

    null을 쓸 수 없는 것도 이 연장선에 있다. JLS §9.7.1은 요소 값이 기본형이나 String이면 상수 표현식이어야 하고, 값이 null이어서는 안 된다고 정한다. 그래서 "값이 없음"을 표현하려면 관례적인 대체값을 쓴다. 빈 문자열 "", 빈 배열 {}, Object.class 같은 표지 클래스, Long.MIN_VALUE 같은 경계값이다. 위의 Tag.type()이 Object.class를 기본값으로 둔 것이 그런 예다. 반대로 상수 표현식이면 계산식도 된다. priority = 1 + 2 * 3이나 value = "y" + "z"는 컴파일러가 접어서(constant folding) 상수로 만들 수 있으므로 문제없이 컴파일되고, static final String K = "k"로 선언한 상수도 쓸 수 있다. 하지만 final이 없는 static String 필드를 쓰면 같은 "element value must be a constant expression" 오류가 난다.

    hashCode라는 요소를 만들 수 없는 이유는 다음 절에서 볼 상속 관계 때문이다. 모든 애노테이션 인터페이스는 자동으로 java.lang.annotation.Annotation을 상속하고, 그 인터페이스가 equals, hashCode, toString, annotationType을 선언한다. 같은 이름의 요소는 그 메서드들과 충돌한다. 같은 이유로 extends 절을 쓸 수 없다. 상위 인터페이스는 언제나 Annotation 하나로 고정이다.

    사용할 때의 축약 규칙

    애노테이션을 쓸 때는 @Tag(value = "order", priority = 1)처럼 "이름 = 값" 쌍을 나열한다. 기본값이 없는 요소는 반드시 지정해야 하고, 빠뜨리면 annotation @Tag is missing a default value for the element 'value' 오류가 난다. 축약은 두 가지다. 하나, 요소 이름이 value이고 나머지 요소가 모두 기본값을 가지면 @Tag("order")처럼 이름을 생략할 수 있다(JLS §9.7.3의 단일 요소 애노테이션). 이 축약은 이름이 정확히 value일 때만 통한다. 요소 이름이 name인 애노테이션에 @Two("x")라고 쓰면 javac는 cannot find symbol ... method value()라고 답한다. 둘, 배열 타입 요소에 원소 하나만 줄 때는 중괄호를 생략할 수 있다. @Command("/time")은 @Command(value = {"/time"})과 같다(JLS §9.7.1). 요소가 하나도 없는 애노테이션은 괄호까지 생략해 @Gone처럼 쓰며, 이런 것을 표시 애노테이션(marker annotation)이라고 한다.

    이 출력에서 가장 중요한 관찰은 쓰지 않은 요소는 기록되지 않는다는 것이다. 클래스에 붙은 @Tag는 value, priority, aliases 세 개만 갖고 있고, 기본값을 쓴 type과 kind는 흔적이 없다. 필드의 @Tag("f")는 value 하나뿐이다. 기본값은 사용하는 쪽 클래스 파일이 아니라 애노테이션 인터페이스의 AnnotationDefault에만 있다. 이 사실이 뒤에서 볼 "기본값을 바꾸면 다시 컴파일하지 않은 클래스에도 반영된다"는 결과로 이어진다.

    보존 정책에 따른 차이도 그대로 보인다. @Tag(RUNTIME)는 RuntimeVisibleAnnotations에, @ClsAnn(CLASS)과 @Retention을 아예 쓰지 않은 @NoRet은 RuntimeInvisibleAnnotations에 들어갔다. @SrcAnn(SOURCE)은 어디에도 없다. 컴파일러가 검사만 하고 버렸다. JVMS §4.7.17은 RuntimeInvisibleAnnotations에 대해, 명령줄 플래그 같은 구현별 방법으로 지시받지 않는 한 리플렉션 API가 이 애노테이션을 돌려주어서는 안 되며, 그런 지시가 없으면 JVM은 이 속성을 무시한다고 적고 있다. 즉 CLASS 보존 애노테이션은 디스크의 클래스 파일에는 있지만, 실행 중인 프로그램의 리플렉션에는 보이지 않는다.

    실행 중의 애노테이션 객체: 프록시와 캐시

    리플렉션으로 애노테이션을 읽으면 Tag 타입의 객체를 받는다. 그런데 Tag는 인터페이스이고, 우리는 그것을 구현한 클래스를 만든 적이 없다. 그렇다면 손에 쥔 객체의 정체는 무엇일까. 직접 물어보자.

    import java.lang.reflect.Proxy;
import java.util.Arrays;

(3) 객체의 클래스는 jdk.proxy2.$Proxy1이라는 동적 프록시(dynamic proxy) 클래스이고, 호출을 받아 처리하는 핸들러는 sun.reflect.annotation.AnnotationInvocationHandler다. 이 이름들은 OpenJDK의 구현 세부이며 명세가 정한 것이 아니다. 프록시 클래스의 패키지 이름과 번호는 실행 환경에 따라 다를 수 있다. 명세가 보장하는 것은 "그 애노테이션 인터페이스를 구현한 객체를 돌려준다"까지다.     getAnnotation 한 번에 일어나는 일 (OpenJDK 21 소스 기준)

    JDK 설치 경로의 lib/src.zip에서 java/lang/Class.java와 sun/reflect/annotation/AnnotationParser.java를 열어 보면 과정이 그대로 보인다. 아래는 소스를 따라 정리한 흐름이다.

    이 흐름에서 몇 가지 결론이 나온다. 애노테이션 파싱은 클래스를 로드할 때가 아니라 처음 리플렉션으로 물어볼 때 일어난다(지연 초기화). 한 번 만들어진 맵은 Class 객체에 붙어 재사용되므로, 같은 클래스에 반복해서 getAnnotation을 불러도 파싱은 한 번이다. 메서드와 필드도 비슷하다. getDeclaredMethods()는 부를 때마다 Method 객체의 새 복사본을 돌려주지만, OpenJDK의 Executable.declaredAnnotations()는 복사본이 원본(root) 객체의 애노테이션 맵을 함께 쓰도록 되어 있다. 그 원본들은 Class가 SoftReference로 잡아 둔 리플렉션 캐시(reflectionData)에 들어 있어서, 메모리가 부족하면 비워지고 다시 만들어질 수 있다. 캐시가 있다고 해서 매 요청마다 리플렉션으로 메서드를 뒤지는 비용이 0이 되는 것은 아니다. 매번 배열을 복사하고 애노테이션을 찾는 일은 남는다. 앞 절의 명령어 처리기처럼 시작 시점에 한 번 읽어 자기 자료구조에 담아 두는 것이 정석인 이유다. 캐시 설치에 잠금 대신 CAS와 재시도를 쓴 것은 앞 권의 동시성 회차에서 본 낙관적 갱신 방식 그대로다. 두 스레드가 동시에 처음 읽으면 둘 다 파싱할 수 있지만, 결과가 같으므로 어느 쪽이 설치되든 문제가 없다.

    프록시 객체에서 t.value()를 부르면 AnnotationInvocationHandler.invoke가 호출된다. 이 메서드는 먼저 equals, toString, hashCode, annotationType을 직접 처리하고, 나머지는 메서드 이름으로 값 표에서 값을 꺼낸다. 꺼낸 값이 길이가 0이 아닌 배열이면 복사해서 돌려준다. 그래서 t.aliases()[0] = "HACK"처럼 돌려받은 배열을 고쳐도 다음 호출의 결과는 그대로다. 실제로 실행해 보면 고친 뒤 다시 꺼낸 값이 [a, b]로 원래와 같다. 애노테이션은 공유되는 캐시 객체이므로 불변이어야 하고, 배열은 자바에서 불변으로 만들 수 없으니 방어적 복사를 하는 것이다. 이 복사는 호출할 때마다 일어나므로, 배열 요소를 반복문 안에서 계속 꺼내는 코드는 매번 새 배열을 할당한다.

    equals와 hashCode는 명세로 정해져 있다

    Annotation 인터페이스의 Javadoc은 두 애노테이션이 같은 애노테이션 인터페이스의 인스턴스이고 모든 요소의 값이 같으면 equals가 참이라고 정한다(배열은 Arrays.equals로, float와 double은 래퍼의 equals로 비교). hashCode도 공식이 정해져 있다. 각 요소에 대해 "(127 × 요소 이름의 String.hashCode()) XOR 요소 값의 해시 코드"를 구하고, 기본값을 쓴 요소까지 포함해 모두 더한다. 서로 다른 메서드 두 개에 @Tag(value = "x", aliases = {"a", "b"})를 각각 붙이고 꺼내 보면 두 객체는 ==로는 다르지만 equals는 참이고 해시 코드도 같다. 반면 toString의 형식은 Javadoc이 "구현에 따라 다르다"고 밝힌다. OpenJDK 21은 @Tag(aliases={"o", "ord"}, priority=1, ...)처럼 소스 코드와 비슷한 모양으로 출력하고 비ASCII 문자는 \uXXXX로 이스케이프한다. 로그 파싱이나 비교에 toString 결과를 쓰지 않는 편이 맞다.

    덧붙여, 애노테이션 인터페이스는 인터페이스이므로 일반 클래스가 직접 구현할 수도 있다. 요소 메서드와 annotationType()을 구현하면 컴파일되고, 테스트에서 애노테이션 값을 흉내 낼 때 쓰인다. 다만 이렇게 만든 객체가 위의 equals·hashCode 규약을 지키게 하는 것은 구현한 사람의 몫이다. 직접 구현한 클래스에서 hashCode를 정의하지 않고 비교해 보면, 프록시 쪽의 equals는 상대의 요소 메서드를 호출해 비교하므로 참이 나오지만 해시 코드는 서로 다르게 나온다. 규약을 깬 객체는 HashSet 같은 컬렉션에서 기대와 다르게 동작한다.

    생성된 프록시 클래스: 요소 값 하나를 읽는 실제 경로

    앞 절에서 애노테이션 객체가 동적 프록시라는 것을 확인했다. 그렇다면 그 프록시 클래스는 언제, 어떤 바이트코드로 만들어지는가. OpenJDK의 java.lang.reflect.ProxyGenerator에는 시스템 프로퍼티 jdk.proxy.ProxyGenerator.saveGeneratedFiles가 참이면 생성한 클래스 파일을 현재 디렉터리 아래에 저장하는 코드가 들어 있다. 이 프로퍼티와 클래스 로딩 로그(-Xlog:class+load)를 함께 켜고, 애노테이션 하나를 처음 읽는 작은 프로그램을 돌려 보자.

    셋째, 두 프록시가 서로 다른 모듈(jdk.proxy1, jdk.proxy2)에 들어갔다. AnnotationParser는 Proxy.newProxyInstance에 애노테이션 인터페이스의 클래스 로더(type.getClassLoader())를 넘긴다. Retention은 부트 로더가, Tag는 애플리케이션 클래스 로더가 정의했다. JIT 컴파일러가 이 경로를 얼마나 줄이는지는 이 실험 환경에서 확인하지 못했으므로(어셈블리를 볼 도구가 없다) 여기서 단정하지 않는다. 바이트코드 수준에서 분명한 것은, 요소 값을 반복문 안에서 계속 꺼내는 코드가 매번 이 경로 전체를 밟는다는 사실이다. 시작 시점에 값을 한 번 꺼내 평범한 필드나 레코드에 옮겨 두라는 앞의 조언은 이 구조에서 나온다.

    한 층 아래: HotSpot이 애노테이션 바이트를 보관하는 곳

    앞의 흐름도에서 getRawAnnotations()가 "JVM이 보관하던 바이트 배열"을 돌려준다고 했다. 그 바이트는 언제, 어디에 보관되며, CLASS 보존 애노테이션은 정확히 어느 단계에서 사라지는가. OpenJDK 21의 HotSpot 소스(src/hotspot/share/classfile/classFileParser.cpp)를 따라가면 답이 나온다.

    클래스 파일을 해석하는 ClassFileParser는 클래스, 필드, 메서드, 레코드 컴포넌트의 속성을 하나씩 읽다가 RuntimeVisibleAnnotations를 만나면 그 속성 본문의 시작 위치와 길이를 기억해 둔다. 필드·메서드·클래스의 경우에는 이때 parse_annotations라는 함수로 바이트를 한 번 훑어 JVM 자신에게 의미 있는 애노테이션이 있는지 찾는다(이것은 뒤의 절에서 따로 본다). 그다음 assemble_annotations가 기억해 둔 바이트를 메타스페이스(metaspace)에 할당한 u1 배열(AnnotationArray)에 그대로 복사한다. 즉 JVM은 애노테이션을 객체로 만들지 않고, 클래스 파일의 속성 본문을 원시 바이트 그대로 클래스 메타데이터 옆에 보관한다. 클래스와 필드의 애노테이션 배열은 InstanceKlass가 가리키는 Annotations 객체(_class_annotations, _fields_annotations 등)에, 메서드의 것은 메서드의 불변 부분인 ConstMethod에 붙는다(copy_method_annotations).

    RuntimeInvisibleAnnotations를 만났을 때의 코드는 이렇게 생겼다. 중복 속성인지 검사한 뒤 if (PreserveAllAnnotations)일 때만 위치와 길이를 기억하고, 아니면 건너뛴다. PreserveAllAnnotations는 OpenJDK 21 HotSpot의 VM 플래그로 기본값은 false다(java -XX:+PrintFlagsFinal -version으로 확인했다). JVMS §4.7.17이 말한 "명령줄 플래그 같은 구현별 방법"의 HotSpot판이 이것이다. 플래그를 켜면 assemble_annotations는 보이는 쪽 바이트 뒤에 보이지 않는 쪽 바이트를 이어 붙여 하나의 배열을 만든다.

    자바 쪽으로 넘겨주는 길도 소스로 확인된다. java.lang.Class의 네이티브 메서드 getRawAnnotations는 Class.c에서 HotSpot의 JVM_GetClassAnnotations(jvm.cpp)에 연결되어 있고, 이 함수는 Annotations::make_java_array로 메타스페이스의 바이트를 자바 힙의 새 byte[]에 복사해 돌려준다. 필드와 메서드는 JVM이 Field·Method 객체를 만들 때(reflection.cpp) 같은 함수로 복사한 배열을 그 객체의 필드에 넣어 준다. 이 원시 바이트를 직접 보자. getRawAnnotations는 패키지 전용이므로, JDK 내부 통로인 SharedSecrets를 --add-exports로 열어 실험한다(내부 API이므로 실험 밖에서 쓸 코드가 아니다).

    // Anns.java
@Retention(RetentionPolicy.RUNTIME) @interface Vis { String value(); }
@Retention(RetentionPolicy.CLASS)   @interface Inv { String value(); }

// Sample.java
@Vis("v") @Inv("i")
public class Sample {}

// Raw.java  (javac/java 모두 --add-exports=java.base/jdk.internal.access=ALL-UNNAMED)
import jdk.internal.access.SharedSecrets;
import java.util.Arrays;
public class Raw {
    public static void main(String[] args) {
        byte[] raw = SharedSecrets.getJavaLangAccess().getRawClassAnnotations(Sample.class);
        System.out.println("raw bytes   = " + raw.length);
        System.out.println("raw         = " + Arrays.toString(raw));
        System.out.println("same array? = " + (raw == SharedSecrets.getJavaLangAccess().getRawClassAnnotations(Sample.class)));
        System.out.println("annotations = " + Arrays.toString(Sample.class.getAnnotations()));
    }
}

Only.class에서 @Inv는 여전히 RuntimeInvisibleAnnotations에 있지만, JVM이 바이트를 보존했고 실행 시점의 Inv 정의가 RUNTIME이므로 리플렉션에 나타났다. 앞에서 "리플렉션의 기준은 클래스 파일의 속성 이름이 아니라 지금 로드된 애노테이션 인터페이스의 보존 정책"이라고 한 말을 바이트 수준에서 확인한 셈이다. 이 플래그는 두 관문을 눈으로 확인하기 위한 실험 도구로만 썼다.

    정의가 바뀌면: 읽는 시점에 해석된다는 것의 결과

    앞의 흐름에서 중요한 성질 하나가 드러났다. 리플렉션이 만드는 애노테이션 객체는 "사용하는 쪽 클래스 파일에 적힌 값"과 "지금 로드된 애노테이션 인터페이스의 정의"를 읽는 순간에 합친 결과다. JLS §9.6.2도 같은 말을 한다. 기본값은 애노테이션 안에 컴파일되어 들어가지 않고, 애노테이션을 읽는 시점에 동적으로 적용된다. 그래서 기본값을 바꾸면 그 변경 전에 컴파일된 클래스의 애노테이션에도 영향을 준다(해당 요소에 값을 명시하지 않았다면). 라이브러리를 만드는 입장에서는 무척 실용적인 성질이므로 실험으로 확인해 두자.

    // Conf.java
@Retention(RetentionPolicy.RUNTIME)
public @interface Conf { int timeout() default 30; String name() default "a"; }

// Gone.java
@Retention(RetentionPolicy.RUNTIME)
public @interface Gone { }

// User.java  (한 번 컴파일한 뒤 다시는 컴파일하지 않는다)
@Conf @Gone public class User {}

// Main.java
public class Main { public static void main(String[] a) {
  System.out.println(Arrays.toString(User.class.getAnnotations()));
  try {
    Conf c = User.class.getAnnotation(Conf.class);
    System.out.println("timeout=" + c.timeout());
    System.out.println("name=" + c.name());
  } catch (Throwable t) { System.out.println(t); }
}}

    네 파일을 모두 컴파일해 실행한 뒤, 한 단계씩 애노테이션 쪽만 바꾸어 가며 다시 실행했다. User.class와 Main.class는 처음 컴파일한 그대로다.

    --1 처음 상태
[@Conf(name="a", timeout=30), @Gone()]
timeout=30
name=a
--2 Conf의 기본값을 60으로 바꾸고 Conf.java만 다시 컴파일
[@Conf(name="a", timeout=60), @Gone()]
timeout=60
name=a
--3 Gone.class 파일을 지움
[@Conf(name="a", timeout=60)]
timeout=60
name=a
--4 Conf에서 name의 기본값을 없애고 Conf.java만 다시 컴파일
[@Conf(timeout=60)]
timeout=60
java.lang.annotation.IncompleteAnnotationException: Conf missing element name

    2단계는 JLS가 말한 그대로다. User.class에는 @Conf라는 이름만 있고 값이 하나도 없으므로, 읽는 순간 Conf.class의 AnnotationDefault에서 새 기본값 60을 가져왔다. 3단계는 애노테이션 클래스가 아예 없을 때의 동작이다. 예외 없이 조용히 빠진다. 앞에서 본 파서 코드의 "찾지 못하면 건너뛴다"가 이것이다. 이 성질 덕분에 어떤 라이브러리의 애노테이션을 붙인 클래스를, 그 라이브러리 없이도 로드하고 실행할 수 있다. 예를 들어 정적 분석 도구용 애노테이션이 실행 시 클래스패스에 없어도 프로그램은 돌아간다. 반대로 말하면, 의존성 누락으로 애노테이션 클래스가 빠져도 오류 없이 "애노테이션이 없는 것처럼" 동작하므로, 프레임워크 기능이 이유 없이 꺼진 듯 보이는 장애의 원인이 될 수 있다.

    4단계는 클래스 파일에 값이 없고 정의에도 기본값이 없는 경우다. 객체는 만들어지지만 값 표에 name이 없고, name()을 부르는 순간 핸들러가 IncompleteAnnotationException을 던진다. 요소의 타입을 바꾼 경우도 확인했다. @Conf(timeout = 5)로 컴파일된 클래스를 두고 timeout의 타입을 int에서 String으로 바꾸면, timeout()을 부를 때 AnnotationTypeMismatchException: Incorrectly typed data found for annotation element public abstract java.lang.String Conf.timeout() (Found data of type java.lang.Integer[5])가 난다. 반대로 클래스 파일에 있던 요소가 정의에서 사라졌으면 OpenJDK 파서는 그 값을 무시하고 넘어간다. AnnotatedElement의 Javadoc은 이 밖에도, Class 값 요소가 가리키는 클래스가 없으면 그 요소를 읽을 때 TypeNotPresentException이, enum 상수가 사라졌으면 EnumConstantNotPresentException이 난다고 정한다. 공통점은 예외가 애노테이션을 꺼낼 때가 아니라 그 요소를 읽을 때 난다는 것이다. 객체는 만들어 두고, 문제가 되는 값은 예외를 대신 들고 있는 대리 객체(exception proxy)로 넣어 두었다가 접근할 때 던진다.

    이 결과는 애노테이션 인터페이스를 공개 API로 내놓을 때의 호환성 규칙으로 이어진다. 기본값이 있는 요소를 추가하는 것은 기존 사용처를 깨지 않는다. 기본값이 없는 요소를 추가하거나, 기존 요소의 기본값을 없애거나, 요소의 타입을 바꾸는 것은 다시 컴파일하지 않은 사용처를 실행 중에 깨뜨린다.

    메타 애노테이션 1: @Retention

    애노테이션 인터페이스에 붙이는 애노테이션을 메타 애노테이션(meta-annotation)이라고 한다. java.lang.annotation 패키지가 제공하는 것은 @Retention, @Target, @Documented, @Inherited, @Repeatable이고, 이 가운데 앞의 둘은 거의 모든 애노테이션 정의에 붙는다. 먼저 @Retention은 애노테이션이 어디까지 살아남는지를 정한다. RetentionPolicy의 세 값을 표로 정리하면 다음과 같다.

    보존 정책클래스 파일리플렉션주로 읽는 쪽
    SOURCE기록하지 않음보이지 않음컴파일러, 애노테이션 프로세서
    CLASS (지정하지 않았을 때의 기본값)RuntimeInvisibleAnnotations보이지 않음클래스 파일을 직접 읽는 바이트코드 도구
    RUNTIMERuntimeVisibleAnnotations보임실행 중의 프레임워크(리플렉션)

    JLS §9.6.4.2는 @Retention이 없는 애노테이션 인터페이스를 CLASS로 취급하라고 정한다. 여기에 실무에서 가장 흔한 실수가 숨어 있다. 직접 만든 애노테이션에 @Retention(RetentionPolicy.RUNTIME)을 빠뜨리면, 컴파일도 잘 되고 클래스 파일에도 기록되지만 getAnnotation은 언제나 null을 돌려준다. 앞의 @NoRet이 RuntimeInvisibleAnnotations에 들어간 것이 바로 이 상황이다. "애노테이션을 붙였는데 프레임워크가 못 본다"는 증상이 나오면 가장 먼저 의심할 곳이다. 기본값이 CLASS이므로, 실행 중에 읽혀야 하는 애노테이션은 예외 없이 RUNTIME을 명시해야 한다고 기억해 두면 된다.

    JLS §9.6.4.2에는 예외 조항도 있다. CLASS나 RUNTIME 보존이라도 지역 변수 선언에 붙은 애노테이션과 람다 식의 형식 매개변수에 붙은 애노테이션은 클래스 파일에 기록되지 않는다. 실제로 LOCAL_VARIABLE을 대상에 넣은 RUNTIME 애노테이션을 지역 변수에 붙여 컴파일하고 javap -v로 열어 보면, 그 애노테이션의 흔적이 클래스 파일 어디에도 없다. 클래스 파일에는 지역 변수 선언에 대한 애노테이션 속성 자체가 없기 때문이다. 그래서 지역 변수의 선언 애노테이션은 리플렉션으로 읽을 방법이 없고, 컴파일 시점 도구만 의미 있게 쓸 수 있다.

    세 정책은 애노테이션의 "독자"가 누구인지를 고르는 선택이다. @Override처럼 컴파일러만 읽으면 되는 것은 SOURCE로 두어 클래스 파일을 깨끗하게 유지한다. 스프링의 @Component나 JPA의 @Entity처럼 실행 중에 프레임워크가 찾아야 하는 것은 RUNTIME이어야 한다. CLASS는 그 중간으로, 실행 중 리플렉션에는 필요 없지만 클래스 파일을 분석하거나 변환하는 도구에는 전달해야 하는 정보에 쓴다. 한편 리플렉션의 기준은 "지금 로드된 애노테이션 인터페이스의 보존 정책"이라는 점도 앞의 파서 흐름에서 보았다. 클래스 파일의 RuntimeVisibleAnnotations에 들어 있더라도, 실행 시점의 애노테이션 정의가 RUNTIME이 아니면 결과에서 빠진다.

    메타 애노테이션 2: @Target, @Documented, @Repeatable

    @Target: 붙일 수 있는 자리

    @Target은 애노테이션을 붙일 수 있는 자리를 ElementType 배열로 정한다. Java 21의 ElementType 상수는 TYPE(클래스, 인터페이스, enum, 레코드, 애노테이션 인터페이스), FIELD, METHOD, PARAMETER, CONSTRUCTOR, LOCAL_VARIABLE, ANNOTATION_TYPE, PACKAGE, 그리고 나중에 추가된 TYPE_PARAMETER와 TYPE_USE(1.8), MODULE(9), RECORD_COMPONENT(16)다. 허용되지 않은 자리에 붙이면 컴파일러가 annotation interface not applicable to this kind of declaration으로 거절한다. @Target이 애노테이션 사용의 실수를 실행 전에 막는 첫 번째 장치다.

    여기서 두 가지 맥락을 구분해야 한다. 선언 맥락(declaration context)은 클래스, 필드, 메서드처럼 무언가를 선언하는 자리이고, 타입 맥락(type context)은 List<@NonNull String>의 타입 인자처럼 타입이 쓰이는 자리다. 타입 맥락은 모두 TYPE_USE 하나로 표현된다. JLS §9.6.4.1은 @Target이 없는 애노테이션 인터페이스를 "모든 선언 맥락에는 적용 가능하고 어떤 타입 맥락에도 적용할 수 없다"고 정한다. 실험해 보면 @Target 없는 @NoTarget은 타입 매개변수 선언(class U8<@NoTarget T>)과 지역 변수 선언에는 붙지만, List<@NoTarget String>에서는 annotation @NoTarget not applicable in this type context 오류가 난다. JDK의 @SuppressWarnings가 이 규칙을 이용한다. JDK 21 소스에서 이 애노테이션에는 @Target이 없고, "@Target을 생략해 모든 선언 맥락을 암묵적으로 대상으로 삼는다"는 주석이 달려 있다.

    @Foo int f;처럼 같은 자리가 선언으로도, 타입으로도 읽힐 수 있는 경우가 있다. JLS §9.7.4는 이것을 문법이 아니라 @Target으로 가린다. FIELD만 허용하면 필드 선언의 애노테이션이고, TYPE_USE만 허용하면 int라는 타입의 애노테이션이며, 둘 다 허용하면 양쪽 모두에 적용된다. 타입 애노테이션은 클래스 파일에서도 별도의 RuntimeVisibleTypeAnnotations 속성에 기록되고, 리플렉션에서는 Field.getAnnotatedType() 같은 AnnotatedType 계열 API로 읽는다. 널 검사 도구들이 쓰는 @NonNull 류가 타입 애노테이션의 대표적인 쓰임이다.

    레코드에는 특별한 전파 규칙이 있다. 레코드 컴포넌트에 붙인 애노테이션은 컴파일러가 만드는 필드, 접근자 메서드, 정규 생성자의 매개변수, 레코드 컴포넌트 중에서 그 애노테이션의 @Target이 허용하는 곳에만 전해진다. 뒤의 검증기 절에서 @Target({FIELD, RECORD_COMPONENT})인 애노테이션이 필드와 레코드 컴포넌트에는 있고 접근자와 생성자 매개변수에는 없는 것을 실행 결과로 확인한다. 레코드에 애노테이션을 붙였는데 프레임워크가 못 읽는다면, 프레임워크가 읽는 위치(예: 접근자 메서드)가 @Target에 들어 있는지 먼저 확인해야 한다.

    @Documented

    @Documented는 그 애노테이션이 Javadoc 같은 문서 도구가 만드는 API 문서에 표시되어야 한다는 표지다. 실행 동작에는 영향이 없다. JDK 21에서 각 애노테이션의 메타 정보를 리플렉션으로 확인하면 @Deprecated, @SafeVarargs, @FunctionalInterface는 @Documented이고 @Override, @SuppressWarnings는 아니다. 앞의 셋은 API 사용자가 알아야 하는 계약이고, 뒤의 둘은 작성자와 컴파일러 사이의 일이라는 차이로 읽을 수 있다.

    @Repeatable: 같은 애노테이션을 여러 번

    원래 한 선언에 같은 애노테이션을 두 번 붙이면 Tag is not a repeatable annotation interface 오류가 난다. Java 8의 @Repeatable은 이를 허용하되, 내부적으로는 컨테이너 애노테이션(container annotation)에 담아 하나로 기록한다.

    @Retention(RetentionPolicy.RUNTIME) @Repeatable(Roles.class)
@interface Role { String value(); }

@Retention(RetentionPolicy.RUNTIME)
@interface Roles { Role[] value(); }    // 컨테이너: Role[]을 돌려주는 value()

@Role("admin") class One {}
@Role("admin") @Role("user") class Many {}
    One.getAnnotation(Role)      = @Role("admin")
Many.getAnnotation(Role)     = null
Many.getAnnotations          = [@Roles({@Role("admin"), @Role("user")})]
Many.getAnnotationsByType    = [@Role("admin"), @Role("user")]
One.getAnnotation(Roles)     = null

RuntimeVisibleAnnotations:
  0: #14(#15=[@#16(#15=s#17),@#16(#15=s#18)])
    Roles(
      value=[@Role(value="admin"),@Role(value="user")]   // 줄바꿈 정리
    )

    JLS §9.7.5가 정한 대로, 반복된 애노테이션은 "명시적으로 선언된 Role은 없고 컨테이너 Roles 하나가 암묵적으로 선언된 것처럼" 처리된다. 클래스 파일에도 Roles 하나만 있다. 그래서 반복이 있는 Many에서 getAnnotation(Role.class)는 null이다. Role은 직접 있는(directly present) 것이 아니라 컨테이너 안에 간접적으로 있는(indirectly present) 것이기 때문이다. 반대로 한 번만 붙인 One에는 컨테이너가 없다. 이 비대칭 때문에 반복 가능한 애노테이션을 읽을 때는 한 개든 여러 개든 똑같이 동작하는 getAnnotationsByType(Role.class)를 써야 한다. 이 메서드는 컨테이너를 열어 그 안의 애노테이션을 소스에 적힌 순서대로 돌려준다. 컨테이너가 될 수 있는 조건(Role[]을 돌려주는 value(), 다른 요소는 기본값 필요, 보존 정책과 대상의 호환 등)은 JLS §9.6.3에 자세히 있고, @Repeatable이 가리키는 타입에 알맞은 value()가 없으면 리플렉션이 AnnotationFormatError를 던진다고 AnnotatedElement Javadoc이 정한다.

    애노테이션과 상속

    "상속"이라는 말은 애노테이션에서 두 가지 뜻으로 쓰인다. 애노테이션 인터페이스끼리의 상속과, 애노테이션이 붙은 클래스·메서드의 상속이 애노테이션을 물려주느냐다. 앞의 것은 간단하다. 앞에서 본 대로 애노테이션 인터페이스에는 extends를 쓸 수 없고, 모든 애노테이션 인터페이스의 상위 인터페이스는 java.lang.annotation.Annotation 하나다. 그래서 "@Service는 @Component의 하위 타입" 같은 관계를 자바 타입 체계로는 만들 수 없다. 대신 메타 애노테이션으로 흉내 낸다. 이것은 이 절의 끝에서 다시 본다.

    뒤의 것은 @Inherited가 좌우한다. Inherited의 Javadoc 규칙은 이렇다. @Inherited가 붙은 애노테이션 인터페이스를 어떤 클래스 선언에서 찾았는데 그 클래스에 없으면, 상위 클래스를 차례로 올라가며 찾는다. 그리고 두 가지 제한을 분명히 적어 둔다. 클래스 이외의 것(메서드, 필드 등)에 붙은 애노테이션에는 효과가 없고, 상위 클래스에서만 물려받으며 구현한 인터페이스의 애노테이션은 물려받지 않는다. 다음 실험이 이 규칙을 하나씩 확인한다.

    @Retention(RUNTIME) @Inherited @interface Inh { String value(); }
@Retention(RUNTIME) @interface NoInh { }

@Inh("iface") interface Api { @NoInh void call(); }
@Inh("parent") @NoInh class Parent {
    @NoInh public void work() {}
    @NoInh public void keep() {}
}
class Child extends Parent implements Api {
    @Override public void work() {}   // 재정의
    public void call() {}             // 인터페이스 메서드 구현
}                                     // keep()은 재정의하지 않음
@Inh("child") class Child2 extends Parent {}
class Impl implements Api { public void call() {} }
class GrandChild extends Child {}

Child.getDeclaredAnnotations = []
GrandChild.getAnnotation(Inh)= @Inh("parent")
Child2.getAnnotation(Inh)    = @Inh("child")

Child.work NoInh             = null
Child.keep NoInh             = @NoInh()
Child.call NoInh             = null

    한 줄씩 읽어 보자. Child는 @Inh("parent")를 물려받았지만 @NoInh는 물려받지 않았다. getDeclaredAnnotations()는 자기 선언에 직접 붙은 것만 보므로 빈 배열이다. GrandChild는 두 단계를 올라가 Parent의 것을 찾았다. Child2는 자기 것이 있으므로 상위의 것이 가려졌다. 앞서 본 Class.createAnnotationData가 "상위 클래스의 상속 가능한 것을 먼저 넣고, 자기 것을 putAll로 덮어쓰는" 순서였던 것이 바로 이 동작이다. Impl은 인터페이스 Api에 붙은 @Inh를 물려받지 못했다. @Inherited여도 인터페이스에서는 오지 않는다.

    메서드 쪽이 흥미롭다. Child.work()는 Parent.work()를 재정의했고, 재정의한 메서드에는 애노테이션이 없다. 메서드의 애노테이션은 재정의로 물려받는 대상이 아니다. 인터페이스 메서드를 구현한 call()도 마찬가지다. 그런데 Child.keep에서는 @NoInh()가 나왔다. 상속이 일어난 것처럼 보이지만 그렇지 않다. Child가 keep()을 재정의하지 않았으므로 Child.class.getMethod("keep")이 돌려준 Method 객체는 Parent에 선언된 바로 그 메서드이고(getDeclaringClass()가 Parent다), 그 선언에 붙은 애노테이션을 읽었을 뿐이다. "메서드 애노테이션이 상속된다"고 착각하기 쉬운 장면이다.

    AnnotatedElement의 Javadoc은 이런 차이를 정확히 말하기 위해 네 가지 용어를 정의하고, 메서드마다 어느 것을 보는지 표로 정리해 둔다.

    용어뜻이 종류를 보는 메서드
    직접 있음(directly present)그 요소의 RuntimeVisible...Annotations 속성에 들어 있다getDeclaredAnnotation, getDeclaredAnnotations
    간접적으로 있음(indirectly present)반복 가능한 타입이고, 속성 안의 컨테이너에 들어 있다getDeclaredAnnotationsByType(직접 있음과 함께)
    있음(present)직접 있거나, 클래스이고 상속 가능한 타입이며 상위 클래스에 있다getAnnotation, getAnnotations
    연관됨(associated)직접·간접으로 있거나, 클래스이고 상속 가능한 타입이며 상위 클래스와 연관되어 있다getAnnotationsByType

    정의를 보면 상속이 끼어드는 조건이 언제나 "요소가 클래스이고"로 시작한다. 메서드, 필드, 생성자, 매개변수에 대해서는 present와 directly present가 같아진다. 그래서 Method.getAnnotation과 Method.getDeclaredAnnotation은 결과가 같다.

    메타 애노테이션은 자동으로 따라가지 않는다

    스프링 문서는 @Service가 @Component로 메타 애노테이션되어 있어서 @Component와 같은 방식으로 취급된다고 설명한다. 그렇다면 @Service가 붙은 클래스에 getAnnotation(Component.class)를 부르면 무엇이 나올까. 같은 구조를 직접 만들어 확인해 보면 null이다. JDK의 리플렉션은 메타 애노테이션을 따라가지 않는다. @Component는 OrderService 클래스가 아니라 Service 애노테이션 인터페이스에 붙어 있으니 당연한 결과다. 메타 애노테이션까지 보려면 읽는 쪽이 직접 따라 올라가야 한다.

    static boolean hasMeta(Class c, Class target) {
    return find(c.getAnnotations(), target, new HashSet<>());
}

static boolean find(Annotation[] anns, Class target, Set> seen) {
    for (Annotation a : anns) {
        Class t = a.annotationType();
        if (t == target) return true;
        if (seen.add(t) && find(t.getAnnotations(), target, seen)) return true;
    }
    return false;
}
// OrderService.class.getAnnotation(Component.class) → null
// hasMeta(OrderService.class, Component.class)       → true

    seen 집합이 꼭 필요하다. Retention.class.getAnnotations()를 출력해 보면 [@java.lang.annotation.Documented(), @java.lang.annotation.Retention(RUNTIME), @java.lang.annotation.Target({ANNOTATION_TYPE})]이다. @Retention은 자기 자신으로 메타 애노테이션되어 있고 @Documented도 그렇다. 방문 기록 없이 재귀하면 끝나지 않는다. 스프링이 MergedAnnotations 같은 자체 유틸리티로 메타 애노테이션을 탐색하고, 합성 애노테이션(composed annotation)이 메타 애노테이션의 속성을 다시 선언해 덮어쓰게(@AliasFor) 하는 것은 모두 JDK가 제공하지 않는 기능을 프레임워크가 그 위에 쌓은 것이다. 스프링 문서의 예로 @RestController는 @Controller와 @ResponseBody를 합성한 것이다. 애노테이션의 "상속"이 필요하다는 요구를 자바 언어가 아니라 읽는 쪽의 규칙으로 해결했다는 점이 이 절의 결론이다.

    애노테이션 활용: 검증기 만들기

    지금까지 배운 것을 모아 입력값 검증기를 만들어 보자. 필드에 제약 조건을 애노테이션으로 적어 두고, 검증기가 리플렉션으로 필드를 훑으며 조건을 검사한다. 먼저 애노테이션 두 개다.

    import java.lang.annotation.*;

@Retention(RetentionPolicy.RUNTIME)
@Target({ElementType.FIELD, ElementType.RECORD_COMPONENT})
public @interface NotBlank {
    String message() default "비어 있으면 안 됩니다";
}
    import java.lang.annotation.*;

@Retention(RetentionPolicy.RUNTIME)
@Target(ElementType.FIELD)
public @interface Range {
    long min() default Long.MIN_VALUE;
    long max() default Long.MAX_VALUE;
    String message() default "범위를 벗어났습니다";
}

    설계에 들어간 판단을 짚어 두자. 둘 다 실행 중에 읽어야 하므로 RUNTIME이다. Range의 min과 max는 "지정하지 않음"을 null로 표현할 수 없으므로 long의 양 끝값을 기본값으로 두었다. 이렇게 하면 @Range(max = 150)처럼 한쪽만 지정해도 다른 쪽은 사실상 제한이 없다. 메시지는 기본값을 두되 사용하는 쪽에서 바꿀 수 있게 했다. NotBlank의 대상에 RECORD_COMPONENT를 넣은 것은 레코드에도 쓰기 위해서다. 다음은 검증기다.

    import java.lang.reflect.Field;
import java.util.ArrayList;
import java.util.List;

public final class Validator {

    public static List validate(Object target) {
        List errors = new ArrayList<>();
        for (Field field : target.getClass().getDeclaredFields()) {
            field.setAccessible(true);
            Object value = read(field, target);

            NotBlank notBlank = field.getAnnotation(NotBlank.class);
            if (notBlank != null && (value == null || value.toString().isBlank())) {
                errors.add(field.getName() + ": " + notBlank.message());
            }

            Range range = field.getAnnotation(Range.class);
            if (range != null && value instanceof Number n) {
                long v = n.longValue();
                if (v < range.min() || v > range.max()) {
                    errors.add(field.getName() + ": " + range.message()
                            + " (" + range.min() + "~" + range.max() + ", 입력값 " + v + ")");
                }
            }
        }
        return errors;
    }

    private static Object read(Field field, Object target) {
        try {
            return field.get(target);
        } catch (IllegalAccessException e) {
            throw new IllegalStateException(e);
        }
    }
}

    첫 번째 회원은 모든 조건을 통과했다. memo가 null이지만 애노테이션이 없으니 아무도 검사하지 않는다. 두 번째 회원은 공백 한 칸짜리 이름이 isBlank()에 걸렸고, 나이 200이 범위를 벗어났다. int 필드를 field.get으로 읽으면 Integer로 박싱되어 나오므로 instanceof Number 패턴에 걸린다. 세 번째는 레코드다. 레코드의 컴포넌트는 컴파일러가 만든 private final 필드가 되고, @NotBlank가 그 필드에 전파되었기 때문에 같은 검증기가 그대로 동작했다. 아래 네 줄이 전파 범위를 보여 준다. @Target에 FIELD와 RECORD_COMPONENT만 있으므로 필드와 레코드 컴포넌트에는 있고, 접근자 메서드와 생성자 매개변수에는 없다.

    이 작은 검증기에도 실무에서 따져야 할 지점이 여럿 있다. 첫째, 오류의 순서다. 위 출력에서 name이 age보다 먼저 나왔지만, getDeclaredFields()의 Javadoc은 돌려주는 배열이 정렬되어 있지 않고 특정한 순서도 없다고 밝힌다. 이 실행에서는 선언 순서와 같았을 뿐 보장된 것이 아니다. 순서가 중요하면 필드 이름으로 정렬하거나 애노테이션에 순서 요소를 두어야 한다. 둘째, 접근 제어다. private 필드를 읽기 위해 setAccessible(true)를 썼는데, 모듈 시스템에서는 다른 모듈이 열어 주지 않은(open하지 않은) 패키지의 멤버에 대해 이 호출이 InaccessibleObjectException으로 실패한다. 검증 대상 클래스가 이름 있는 모듈에 있다면 그 패키지를 검증기 쪽에 열어 주어야 한다. 셋째, 상속이다. getDeclaredFields()는 상위 클래스의 필드를 돌려주지 않으므로, 상위 클래스의 제약까지 검사하려면 getSuperclass()로 올라가며 반복해야 한다. 넷째, 비용이다. 검증할 때마다 필드 목록을 복사하고 애노테이션을 찾는 대신, 클래스별로 "필드와 제약 목록"을 한 번 만들어 ClassValue나 맵에 캐시하는 것이 일반적인 구조다.

    이 구조를 표준으로 만든 것이 Jakarta Bean Validation이다. 명세는 보존 정책에 RUNTIME이 포함되고 jakarta.validation.Constraint로 애노테이션된 애노테이션을 제약 정의로 간주하며, 모든 제약 애노테이션이 message, groups, payload 요소를 정의해야 한다고 정한다. @Constraint의 validatedBy가 실제 검사 로직을 담은 클래스를 가리킨다. 우리 검증기가 if문에 박아 둔 "애노테이션 타입 → 검사 로직" 연결을 메타 애노테이션으로 선언하게 만든 것이다. 스프링 MVC에서 컨트롤러 매개변수의 @Validated와 함께 쓰는 @NotBlank 같은 제약 애노테이션도 이 위에 있다. 원리는 방금 만든 수십 줄의 검증기와 같다. 애노테이션은 조건을 적고, 검증기가 리플렉션으로 그것을 읽어 검사한다.

    컴파일 시점에 읽기: 애노테이션 프로세서

    애노테이션을 읽는 독자는 실행 중의 리플렉션만 있는 것이 아니다. javac에는 플러그인 형태로 애노테이션을 처리하는 장치가 있다. javax.annotation.processing 패키지의 애노테이션 처리 API(pluggable annotation processing)다. 프로세서는 컴파일 도중에 호출되어 소스 코드의 선언 구조(javax.lang.model의 Element)를 보고, 오류나 경고를 보고하거나 새 소스 파일을 생성할 수 있다. SOURCE 보존 애노테이션이 쓸모 있는 이유가 여기에 있다. 클래스 파일에 남지 않아도 컴파일 시점의 독자에게는 보인다.

    앞의 @Range에는 실행 전에 잡을 수 있는 실수가 있다. @Range(min = 10, max = 1)처럼 최솟값이 최댓값보다 크면 어떤 값도 통과할 수 없는데, 리플렉션 검증기는 실행해야 이를 드러낸다. 프로세서로 컴파일 시점에 막아 보자.

    import java.util.Set;
import javax.annotation.processing.*;
import javax.lang.model.SourceVersion;
import javax.lang.model.element.Element;
import javax.lang.model.element.TypeElement;
import javax.tools.Diagnostic;

@SupportedAnnotationTypes("Range")
public class RangeChecker extends AbstractProcessor {

    @Override
    public SourceVersion getSupportedSourceVersion() {
        return SourceVersion.latestSupported();
    }

    @Override
    public boolean process(Set annotations, RoundEnvironment round) {
        for (Element e : round.getElementsAnnotatedWith(Range.class)) {
            Range r = e.getAnnotation(Range.class);
            if (r.min() > r.max()) {
                processingEnv.getMessager().printMessage(Diagnostic.Kind.ERROR,
                        "@Range의 min(" + r.min() + ")이 max(" + r.max() + ")보다 큽니다", e);
            }
        }
        return true;
    }
}

    오류가 프로세서가 지목한 요소(필드 level)의 위치에 javac의 일반 오류와 같은 모양으로 찍혔고, 컴파일은 실패해 Bad.class가 만들어지지 않았다. 실행 중에 드러날 설정 오류를 빌드 단계로 끌어올린 것이다. e.getAnnotation(Range.class)가 여기서는 리플렉션이 아니라 컴파일러의 모델 위에서 동작한다는 점도 눈여겨보자. 이 시점에는 Bad의 클래스 파일이 아직 없다. 프로세서는 이처럼 검사만 할 수도 있고, Filer로 새 소스 파일을 만들어 컴파일 대상에 추가할 수도 있다. 앞 권에서 쓴 Querydsl의 Q타입(QMember 같은 클래스)이 엔티티의 @Entity를 읽은 애노테이션 프로세서가 생성한 소스다. 생성된 소스는 다음 라운드(round)에서 다시 처리 대상이 되며, 더 이상 새 파일이 생기지 않을 때까지 라운드가 반복된다.

    프로세서를 javac가 찾는 방법도 알아 두어야 한다. 위처럼 -processor로 이름을 직접 줄 수도 있고, 클래스패스의 JAR에 META-INF/services/javax.annotation.processing.Processor 파일로 등록해 두면 javac가 서비스 로더로 찾아낸다. 그런데 이 자동 발견은 빌드에 의도하지 않은 코드가 끼어드는 통로이기도 하다. 실제로 JDK 21의 javac로 프로세서를 서비스 파일로만 등록한 클래스패스를 주고 컴파일하면, 처리는 그대로 일어나되 "클래스패스에서 프로세서가 발견되어 애노테이션 처리가 활성화되었고, 앞으로의 릴리스에서는 -processor, --processor-path, -proc:only, -proc:full 같은 명시적 설정이 없으면 비활성화될 수 있다"는 안내가 출력된다. 그 변경은 JDK 23에서 이루어져, JDK 23부터는 명시적인 설정이 있어야 애노테이션 처리가 실행된다(이전 동작을 원하면 -proc:full을 준다). 빌드 도구를 쓰는 프로젝트라면 JDK를 올릴 때 프로세서가 명시적으로 지정되어 있는지 확인해야 하는 이유다.

    자바 기본 애노테이션

    JDK는 java.lang 패키지에 언어 차원에서 의미가 정해진 애노테이션 다섯 개를 둔다. JLS §9.6.4가 각각의 규칙을 정하고, 독자는 대부분 컴파일러다. 먼저 JDK 21에서 리플렉션으로 확인한 메타 정보다.

    @Override: 실수를 컴파일 오류로 바꾼다

    JLS §9.6.4.4에 따르면 @Override가 붙은 메서드는 상위 타입의 메서드를 재정의하거나, Object의 public 메서드와 재정의 동등(override-equivalent)하거나, 레코드 컴포넌트의 접근자여야 하며, 아니면 컴파일 오류다. 이 애노테이션이 막아 주는 전형적인 사고가 있다.

    import java.util.HashSet;
import java.util.Set;

public class Point {
    final int x, y;
    Point(int x, int y) { this.x = x; this.y = y; }

    public boolean equals(Point other) {          // 재정의가 아니라 오버로딩이다
        return other != null && x == other.x && y == other.y;
    }

    @Override
    public int hashCode() { return 31 * x + y; }

    public static void main(String[] args) {
        Set set = new HashSet<>();
        set.add(new Point(1, 2));
        System.out.println(new Point(1, 2).equals(new Point(1, 2)));
        System.out.println(set.contains(new Point(1, 2)));
    }
}

    직접 호출한 equals는 참인데 HashSet은 같은 점을 찾지 못한다. 매개변수 타입이 Point인 equals는 Object.equals(Object)를 재정의한 것이 아니라 새 메서드를 하나 더 만든 오버로딩이다. 첫 줄의 호출은 컴파일 시점에 정적 타입이 Point인 인자로 더 구체적인 equals(Point)가 골라졌지만, HashSet 내부는 Object 타입으로 equals(Object)를 호출하고, 그것은 여전히 Object의 동일성 비교다. 이 메서드에 @Override를 붙이면 javac가 method does not override or implement a method from a supertype으로 즉시 알려 준다. 앞 권에서 본 오버로딩 해석(컴파일 시점)과 동적 디스패치(실행 시점)의 차이를, 애노테이션 하나가 컴파일 오류로 바꿔 주는 셈이다. @Override는 SOURCE 보존이므로 클래스 파일에는 아무 흔적도 남기지 않는다. 실행 비용은 0이다.

    @Deprecated: since와 forRemoval

    @Deprecated는 Java 9부터 두 요소를 가진다. since는 폐기된 버전을 적는 문자열(기본값 빈 문자열), forRemoval은 앞으로 제거될 예정인지를 나타낸다(기본값 false). JLS §9.6.4.6은 forRemoval=false를 보통의 폐기(ordinarily deprecated), true를 최종 폐기(terminally deprecated)로 부르고, 둘이 일으키는 경고의 종류를 구분한다. javac 21로 확인한 결과다.

    public class Lib {
    @Deprecated(since = "2.0")

    @Deprecated(since = "2.0", forRemoval = true)
    public static void doomed() {}
}

public class Use {
    void a() { Lib.oldWay(); Lib.doomed(); }
    @SuppressWarnings({"deprecation", "removal"})
    void b() { Lib.oldWay(); Lib.doomed(); }
}

    @SuppressWarnings: 범위를 좁게

    JLS §9.6.4.5가 정한 표준 문자열은 "unchecked", "deprecation", "removal", "preview" 네 가지다. 그 밖의 문자열은 비표준 경고를 가리키며, 컴파일러는 알아보지 못하는 문자열을 무시해야 한다. 그래서 오타가 난 문자열은 오류 없이 그냥 효과가 없다. 이 애노테이션은 붙인 선언 전체에 효과가 미치므로, 클래스에 붙이면 그 안의 모든 메서드에서 해당 경고가 사라진다. 경고를 끄는 것은 "여기는 내가 확인했다"는 주장이므로, 그 주장이 성립하는 가장 좁은 범위(대개 지역 변수 선언 하나나 메서드 하나)에 붙이는 것이 원칙이다.

    @SafeVarargs: 힙 오염 경고와 그 조건

    제네릭 타입의 가변 인자 메서드 static List plain(T... xs)를 -Xlint:unchecked로 컴파일하면 Possible heap pollution from parameterized vararg type T 경고가 나온다. 가변 인자는 실제로 배열로 전달되는데, 제네릭 타입의 배열은 실행 중에 원소 타입 정보를 갖지 못해(소거, erasure) 잘못된 타입의 값이 섞여도 배열이 막아 주지 못하기 때문이다. @SafeVarargs는 "이 메서드는 가변 인자 배열에 위험한 일을 하지 않는다"는 작성자의 보증이고, 선언부와 호출부의 해당 unchecked 경고를 끈다. 보증이 깨질 수 없도록 붙일 수 있는 곳도 제한된다. Javadoc에 따르면 고정 인자 메서드이거나, static도 final도 private도 아닌 가변 인자 메서드에 붙이면 컴파일 오류다. 재정의될 수 있는 메서드는 하위 클래스가 보증을 깨뜨릴 수 있기 때문이다. 실제로 일반 인스턴스 메서드에 붙이면 javac 21은 Invalid SafeVarargs annotation. Instance method bad(T...) is neither final nor private.라고 거절한다.

    @FunctionalInterface: 의도를 검사로

    JLS §9.6.4.9는 @FunctionalInterface가 붙었는데 실제로 함수형 인터페이스가 아니면 컴파일 오류라고 정한다. 추상 메서드를 두 개 선언하면 javac는 Unexpected @FunctionalInterface annotation과 함께 multiple non-overriding abstract methods found in interface FI라고 이유를 댄다. 반면 추상 메서드 하나에 boolean equals(Object o) 선언과 default 메서드가 함께 있는 인터페이스는 문제없이 컴파일된다. Object의 public 메서드와 같은 시그니처의 추상 메서드는 개수에 세지 않고, default 메서드는 추상 메서드가 아니기 때문이다. 이 애노테이션이 없어도 추상 메서드가 하나인 인터페이스는 람다의 대상이 될 수 있다. 애노테이션은 그 성질을 "앞으로도 유지하겠다"는 의도를 적고, 누군가 메서드를 추가해 그 의도를 깨면 컴파일러가 막게 한다.

    다섯 개를 나란히 놓으면 공통점이 보인다. @Override, @FunctionalInterface, @SafeVarargs는 작성자의 의도를 적고 컴파일러가 그것을 검증하게 한다. @Deprecated와 @SuppressWarnings는 경고의 생산과 소비를 조절한다. 어느 쪽이든 실행 중의 동작을 바꾸지 않는다. 이들의 효과는 모두 컴파일러라는 독자가 만든다.

    네 번째 독자, JVM: HotSpot이 직접 해석하는 내부 애노테이션

    지금까지 애노테이션의 독자로 컴파일러, 애노테이션 프로세서, 리플렉션을 꼽았다. 그런데 앞 절에서 ClassFileParser가 RuntimeVisibleAnnotations를 메타스페이스에 복사하기 전에 parse_annotations로 한 번 훑는다고 했다. 이 함수 위에는 "VM에게 의미 있는 애노테이션을 찾아 애노테이션들을 걸러 본다(Sift through annotations, looking for those significant to the VM)"는 주석이 붙어 있다. JVM 자신도 독자인 것이다. 다만 아무 애노테이션이나 읽지 않는다. 읽는 목록과 조건이 소스에 못 박혀 있다.

    parse_annotations는 애노테이션마다 타입 서술자(예: Ljdk/internal/vm/annotation/Contended;)를 상수 풀에서 심볼로 꺼내, AnnotationCollector::annotation_index에서 JVM이 미리 알고 있는 심볼(vmSymbols)과 맞춰 본다. 애노테이션 클래스를 로드하지 않고 이름만으로 알아본다는 점이 리플렉션과 다르다. OpenJDK 21에서 이 목록에 있는 것은 @CallerSensitive, @ForceInline, @DontInline, @IntrinsicCandidate, @Hidden, @Stable, @Contended, @ReservedStackAccess, @jdk.internal.ValueBased 등이며, 대부분 jdk.internal.vm.annotation 패키지에 있다. 각 항목에는 붙을 수 있는 위치(메서드인지 필드인지 클래스인지)와 권한 조건이 함께 적혀 있다. 이 함수의 주석은 "특권 코드는 모든 애노테이션을 쓸 수 있고, 다른 코드는 일부를 조용히 버린다(silently drops)"이고, 특권(privileged)의 정의는 클래스를 정의한 로더가 부트 로더나 플랫폼 로더인 경우(그리고 JDK 내부에서 VM 애노테이션 접근을 허락해 정의한 클래스)다. 인식된 애노테이션은 apply_to에서 JVM 내부 플래그로 옮겨진다. 예를 들어 @ForceInline은 메서드의 set_force_inline(), @Stable은 필드 플래그의 update_stable(true), @Contended는 필드의 경합 그룹(contended group) 설정이 된다.

    이 가운데 효과를 직접 잴 수 있는 것이 @Contended다. 이 애노테이션은 @ReservedStackAccess(RestrictReservedStack)와 함께 권한 조건이 VM 플래그에 묶인 예외로, RestrictContended(기본값 true)가 그 플래그여서, -XX:-RestrictContended를 주면 애플리케이션 클래스에서도 인식된다. 같은 모양의 클래스 두 개를 만들고 한쪽 필드에만 붙인 뒤, 필드 오프셋(Unsafe.objectFieldOffset)과 객체 크기(jcmd의 클래스 히스토그램)를 비교했다. jdk.internal.vm.annotation은 내보내지 않은 패키지라 컴파일할 때 --add-exports=java.base/jdk.internal.vm.annotation=ALL-UNNAMED가 필요하다.

    import java.lang.reflect.Field;
import jdk.internal.vm.annotation.Contended;
import sun.misc.Unsafe;

public class Layout {
    static class Plain   { volatile long a; volatile long b; }
    static class Padded  { volatile long a; @Contended volatile long b; }

    public static void main(String[] args) throws Exception {
        Field f = Unsafe.class.getDeclaredField("theUnsafe");
        f.setAccessible(true);
        Unsafe u = (Unsafe) f.get(null);
        for (Class c : new Class[]{Plain.class, Padded.class}) {
            StringBuilder sb = new StringBuilder(c.getSimpleName() + ":");
            for (Field x : c.getDeclaredFields())
                sb.append(" ").append(x.getName()).append("@").append(u.objectFieldOffset(x));
            System.out.println(sb);
        }
        System.out.println(Padded.class.getDeclaredField("b").getAnnotations().length);
    }
}

Contended는 @Retention(RUNTIME)이므로 클래스 파일의 RuntimeVisibleAnnotations에 기록되었고, 메타스페이스에 바이트로도 보관되었다. 다만 JVM이라는 독자가 "이 로더의 클래스에서는 이 애노테이션을 읽지 않는다"는 자기 규칙을 적용했을 뿐이다. 같은 바이트를 두고 리플렉션과 JVM이 서로 다른 판단을 한다. 이 회차가 처음부터 말한 "효과는 읽는 쪽이 만든다"가 JVM에도 그대로 적용된다.

    -XX:-RestrictContended를 주면 b가 152로 밀려난다. HotSpot의 필드 배치 코드(fieldLayoutBuilder.cpp의 compute_regular_layout)는 경합 그룹마다 그 앞에 ContendedPaddingWidth(기본값 128) 바이트의 빈 블록을 넣고(insert_contended_padding), 경합 그룹이 하나라도 있으면 객체 끝에도 같은 크기의 패딩을 붙인다. 이 실행 환경에서 첫 필드 a는 16에서 시작해 24에서 끝나고, 128바이트를 건너 b가 152에 놓인다. b가 160에서 끝나고 꼬리 패딩 128을 더하면 288바이트이며, 히스토그램의 288000 / 1000과 정확히 맞는다. 패딩 폭을 64로 줄이면 b는 16 + 8 + 64 = 88에 놓인다. 객체 하나가 32바이트에서 288바이트로 9배가 되었다. Contended의 Javadoc이 "거의 언제나 상당한 공간 비용을 더한다"고 경고하는 이유가 숫자로 보인다.

    이 패딩의 목적은 Contended의 Javadoc이 말하는 거짓 공유(false sharing)를 피하는 것이다. 서로 다른 스레드가 자주 쓰는 필드들이 같은 캐시 라인에 놓이면, 논리적으로는 무관한 쓰기가 캐시 라인 단위로 서로를 방해한다. 그래서 JDK는 이 애노테이션을 동시성 클래스 안에서 신중하게 쓴다. JDK 21 소스에서 Exchanger의 Node 클래스, ForkJoinPool의 작업 큐 필드(@Contended("w")), SubmissionPublisher의 BufferedSubscription 클래스와 그 필드(@Contended("c"))에 붙어 있다. 같은 문자열 태그를 준 필드들은 한 그룹으로 묶여 함께 격리되고, 태그가 없으면 필드마다 별도 그룹이 된다는 규칙도 Javadoc과 parse_annotations의 그룹 처리 코드에 함께 적혀 있다.

    JVM과 컴파일러가 같은 내부 애노테이션을 함께 읽는 예도 있다. Integer 같은 값 기반 클래스(value-based class)에는 @jdk.internal.ValueBased가 붙어 있고, 이 애노테이션의 소스 주석은 "javac가 특별히 처리한다"고 적는다. main에 Integer lock = 1000; synchronized (lock) { System.out.println("locked"); }만 둔 SyncVB 클래스를 컴파일하면 javac 21은 warning: [synchronization] attempt to synchronize on an instance of a value-based class를 낸다. 같은 클래스를 진단 플래그와 함께 실행하면 HotSpot도 반응한다. ClassAnnotationCollector::apply_to가 부트 로더의 Integer에서 이 애노테이션을 인식해 표시해 둔 덕분이다.

    객체 주소는 실행마다 다르다. 같은 플래그 값을 1로 주면 이 실험에서는 로그 대신 JVM이 fatal error: Synchronizing on object ... of klass java.lang.Integer로 즉시 종료했다. 하나의 애노테이션을 컴파일러는 경고로, JVM은 실행 중 진단으로 읽는다. 컴파일 시점과 실행 시점의 서로 다른 독자가 같은 정보를 각자의 방식으로 쓰는 구조가, JDK 내부에서도 똑같이 반복되는 것이다.

    흔한 오해와 다른 주제와의 연결

    "애노테이션이 코드를 실행한다." 애노테이션은 상수 데이터이고 실행 흐름에 끼어들지 않는다. 스프링의 @Transactional이 트랜잭션을 여는 것처럼 보이는 이유는, 스프링이 시작 시점에 이 애노테이션을 읽고 해당 빈을 프록시로 감싸 메서드 호출을 가로채기 때문이다. 같은 클래스 안에서 자기 메서드를 직접 호출하면 프록시를 거치지 않으므로 애노테이션이 "무시되는" 현상은, 애노테이션이 아니라 읽는 쪽이 만든 구조(프록시)의 한계다. 스프링 핵심 원리 고급편에서 본 프록시와 이 회차의 애노테이션이 만나는 지점이다.

    "붙였으니 리플렉션으로 보일 것이다." 보존 정책을 지정하지 않으면 CLASS이고, CLASS는 리플렉션에 보이지 않는다. 대상이 맞지 않으면 아예 컴파일되지 않지만, 레코드처럼 컴파일러가 선언을 만들어 내는 경우에는 @Target에 따라 일부 위치에만 전파된다. 애노테이션 클래스가 실행 시 클래스패스에 없으면 예외 없이 사라진다. "안 보인다"는 증상의 원인은 대부분 이 셋 중 하나다.

    "애노테이션도 상속된다." @Inherited가 붙은 애노테이션이, 클래스에서, 상위 클래스로부터일 때만이다. 인터페이스, 메서드, 필드의 애노테이션은 물려받지 않고, 메타 애노테이션은 JDK가 따라가 주지 않는다. 프레임워크마다 이 빈자리를 자기 규칙으로 채우므로, 스프링에서 인터페이스나 상위 메서드의 애노테이션이 통하는지는 그 기능의 문서가 정한 탐색 규칙을 확인해야 한다.

    "기본값은 사용한 쪽에 박혀 있다." 컴파일 시점 상수인 static final 필드(상수 변수)의 값은 사용하는 쪽 클래스 파일에 복사되어 들어가므로 정의를 바꾸면 사용처를 다시 컴파일해야 하지만, 애노테이션 요소의 기본값은 반대로 읽는 시점에 애노테이션 인터페이스에서 가져온다. 명시한 값만 사용처에 기록된다. 두 규칙을 헷갈리면 라이브러리 버전을 올렸을 때의 동작을 잘못 예측한다.

    이 회차의 명령어 처리기에서 명령 문자열을 HTTP 요청 경로로 바꾸면, 10회에서 만든 HTTP 서버의 요청을 메서드에 연결하는 구조가 된다. 리플렉션과 애노테이션을 서버에 실제로 적용하는 일은 이 권의 마지막 회차(HTTP 서버 활용)의 몫이다. 그리고 이 구조가 스프링 MVC의 @RequestMapping, JPA의 @Entity와 @Column, Bean Validation의 제약 애노테이션, JUnit의 @Test가 공통으로 서 있는 바닥이다. 프레임워크의 애노테이션을 만날 때마다 "이것은 누가, 언제(컴파일 시점인가 실행 시점인가), 어느 위치에서 읽는가"를 물으면 동작의 대부분을 예측할 수 있다.

    애노테이션(annotation)
    선언(또는 타입 사용)에 붙는 상수 메타데이터. 스스로 동작하지 않으며, 컴파일러·애노테이션 프로세서·리플렉션 같은 독자가 읽어야 의미가 생긴다.
    애노테이션 인터페이스
    @interface로 선언하며 바이트코드에서는 ACC_ANNOTATION 플래그가 붙은 인터페이스다. 상위 인터페이스는 언제나 java.lang.annotation.Annotation이고 extends와 제네릭을 쓸 수 없다.
    요소 타입과 값의 제약
    기본형, String, Class, enum, 애노테이션, 그것들의 1차원 배열만 허용되고 값은 컴파일 시점 상수여야 하며 null은 안 된다. 클래스 파일의 element_value가 적을 수 있는 값의 종류와 정확히 일치한다.
    클래스 파일 표현
    RUNTIME은 RuntimeVisibleAnnotations, CLASS는 RuntimeInvisibleAnnotations에 기록되고 SOURCE는 기록되지 않는다. 사용처에는 명시한 값만 기록되고 기본값은 애노테이션 인터페이스의 AnnotationDefault에 있다.
    실행 중의 애노테이션 객체
    OpenJDK에서는 처음 조회할 때 파싱되어 AnnotationInvocationHandler를 쓰는 동적 프록시로 만들어지고 Class에 캐시된다. 기본값이 이때 합쳐지므로 정의를 바꾸면 다시 컴파일하지 않은 사용처에도 반영된다.
    JVM 안의 애노테이션 (HotSpot)
    클래스 로딩 때 RuntimeVisibleAnnotations의 원시 바이트가 메타스페이스에 복사되고 CLASS 보존 쪽은 -XX:+PreserveAllAnnotations가 없으면 버려지며, 리플렉션은 그 복사본을 받아 보존 정책을 다시 확인한다. @Contended 같은 내부 애노테이션은 ClassFileParser가 이름으로 알아보되 기본 설정에서는 부트·플랫폼 로더의 클래스에서만 인식한다.
    @Retention과 @Target
    보존 정책은 어느 독자까지 정보가 전달될지를 정하며 생략하면 CLASS다. 대상은 붙일 수 있는 자리를 정하며 생략하면 모든 선언 맥락에 적용되고 타입 맥락에는 적용되지 않는다.
    @Inherited와 상속
    클래스에 붙은 애노테이션만 상위 클래스 사슬을 따라 물려받는다. 인터페이스, 메서드, 필드의 애노테이션은 물려받지 않으며 JDK 리플렉션은 메타 애노테이션을 따라가지 않는다.
    @Repeatable
    반복된 애노테이션은 컨테이너 애노테이션 하나로 기록되므로 getAnnotation은 null을 돌려줄 수 있다. 개수와 상관없이 읽으려면 getAnnotationsByType을 쓴다.
    애노테이션 프로세서
    javac 안에서 실행되어 선언 모델을 보고 오류를 보고하거나 소스를 생성한다. SOURCE 애노테이션의 주 독자이며, JDK 23부터는 명시적으로 설정해야 실행된다.

    장애 대응에서 "애노테이션을 붙였는데 동작하지 않는다"는 보고를 받으면 독자를 기준으로 원인을 나눈다. 리플렉션이 읽는 애노테이션이라면 보존 정책(직접 만든 것에 RUNTIME이 빠졌는가), 위치(프레임워크가 읽는 곳이 필드인가 접근자인가, 레코드 전파가 그 위치까지 왔는가), 클래스패스(애노테이션 클래스가 실행 시 있는가)를 순서대로 본다. 셋째 원인은 예외를 남기지 않으므로 로그만 봐서는 찾기 어렵고, 의존성 트리를 확인해야 드러난다. 스프링처럼 프록시를 쓰는 기능이라면 같은 클래스 안의 직접 호출처럼 프록시를 우회하는 경로인지도 확인한다.

    공용 라이브러리의 애노테이션을 설계할 때는 바이너리 호환성을 의식해야 한다. 기본값이 있는 요소를 추가하는 것은 안전하지만, 기본값 없는 요소 추가, 기본값 제거, 요소 타입 변경은 이미 배포된 사용처를 실행 중에 IncompleteAnnotationException이나 AnnotationTypeMismatchException으로 깨뜨린다. 반대로 기본값을 바꾸면 사용처를 다시 빌드하지 않아도 동작이 바뀐다는 점은, 의도한 변경이면 장점이고 의도하지 않았다면 조용한 동작 변화다. 변경 기록에 반드시 남겨야 하는 종류의 변경이다.

    검사 시점의 선택도 판단거리다. 실행 중에 리플렉션으로 읽으면 구현이 간단하고 런타임 정보(실제 값)를 쓸 수 있지만, 설정 오류는 그 코드가 실행되어야 드러나고 시작 시간과 메모리에 비용이 든다. 애노테이션 프로세서로 읽으면 오류를 빌드에서 잡고 실행 비용이 없지만, 빌드 설정(JDK 23 이후의 명시적 활성화, IDE 설정)과 디버깅이 번거로워진다. 애노테이션의 값끼리 모순되는지처럼 소스만 보고 판단할 수 있는 검사는 컴파일 시점으로, 입력값처럼 실행해야 아는 것은 실행 시점으로 나누는 것이 기준이 된다.
  • 직접 만든 @interface Audit { String value(); }에는 메타 애노테이션이 하나도 없다. 이것을 메서드에 붙인 뒤 method.getAnnotation(Audit.class)를 호출하면 무엇이 나오는가? javap -v로 그 클래스 파일을 보면 이 애노테이션은 어느 속성에 들어 있는가? 같은 애노테이션을 List<@Audit("x") String>에 붙이면 어떻게 되는가?
  • 라이브러리 v1의 @interface Retry { int times() default 3; }를 사용해 @Retry class Job {}과 @Retry(times = 5) class Job2 {}를 컴파일했다. v2에서 기본값을 1로 바꾸고 라이브러리 JAR만 교체했다. 두 클래스에서 times()는 각각 무엇을 돌려주는가? v3에서 times를 long으로 바꾸면?
  • @Repeatable(Roles.class)인 @Role을 class A에는 한 번, class B에는 두 번 붙였다. 두 클래스 각각에 대해 getAnnotation(Role.class), getAnnotation(Roles.class), getAnnotationsByType(Role.class).length의 결과를 예측하라.
  • 본문의 Validator로 class Base { @NotBlank String id; }를 상속한 class Item extends Base { @Range(min = 1) int qty; }의 인스턴스를 검증하면 id가 null이어도 오류가 나오지 않는다. 왜 그런가? @NotBlank에 @Inherited를 붙이면 해결되는가?
  • 스프링의 @Service처럼 @Component로 메타 애노테이션된 애노테이션을 직접 만들었다. 이것이 붙은 클래스에서 getAnnotation(Component.class)가 null인 이유를 클래스 파일 수준에서 설명하고, 메타 애노테이션을 재귀적으로 찾는 코드에 방문 기록이 필요한 이유를 JDK의 메타 애노테이션 정의로 설명하라.
    •

    1. @Retention이 없으므로 CLASS로 취급되어 getAnnotation은 null이다. 클래스 파일에는 기록되며, 메서드의 RuntimeInvisibleAnnotations 속성에 들어 있다. JVM은 이 속성을 리플렉션에 내주지 않는다. @Target도 없으므로 모든 선언 맥락에는 붙일 수 있지만 타입 맥락에는 붙일 수 없어서, List<@Audit("x") String>은 annotation @Audit not applicable in this type context 컴파일 오류가 난다.

    2. Job.class에는 @Retry의 값이 하나도 기록되지 않았으므로 읽는 시점에 v2의 AnnotationDefault에서 1을 가져온다. Job2.class에는 times=5가 기록되어 있으므로 5다. v3에서 long으로 바꾸면 Job은 새 기본값(long)을 쓰므로 문제가 없지만, Job2.class에는 정수 태그 I로 5가 기록되어 있어 long 요소와 타입이 맞지 않는다. times()를 부르는 순간 AnnotationTypeMismatchException이 난다. 애노테이션 객체를 꺼내는 것 자체는 성공한다는 점에 주의한다.

    3. A: 컨테이너 없이 @Role 하나가 직접 있으므로 getAnnotation(Role.class)는 그 애노테이션, getAnnotation(Roles.class)는 null, 길이는 1이다. B: 클래스 파일에 @Roles 하나만 기록되므로 getAnnotation(Role.class)는 null, getAnnotation(Roles.class)는 두 원소를 담은 컨테이너, getAnnotationsByType(Role.class)는 컨테이너를 열어 길이 2다. 개수와 상관없이 같은 코드로 읽으려면 getAnnotationsByType을 써야 하는 이유다.

    4. getDeclaredFields()는 그 클래스가 선언한 필드만 돌려주므로 Item을 검증할 때 Base의 id 필드는 아예 순회 대상에 들어오지 않는다. @Inherited는 해결책이 아니다. @Inherited는 클래스에 붙은 애노테이션에만 효과가 있고, 필드 애노테이션에는 아무 영향이 없다. 게다가 문제는 애노테이션이 아니라 필드 자체를 보지 못한 것이다. getSuperclass()로 Object에 닿을 때까지 올라가며 각 클래스의 선언된 필드를 검사하도록 검증기를 고쳐야 한다.

    5. @Component는 사용자 클래스가 아니라 직접 만든 애노테이션 인터페이스의 클래스 파일에 기록되어 있다. 사용자 클래스의 RuntimeVisibleAnnotations에는 그 애노테이션 하나만 있고, JDK의 getAnnotation은 그 속성(과 @Inherited인 경우 상위 클래스)만 보므로 null이다. 재귀 탐색은 annotationType().getAnnotations()로 한 단계씩 올라가는데, @Retention은 자기 자신(@Retention(RUNTIME))으로, @Documented도 자기 자신으로 애노테이션되어 있어 순환이 생긴다. 방문한 애노테이션 타입을 기록하지 않으면 무한 재귀에 빠진다.

     다음 중 애노테이션 요소의 기본값으로 컴파일되는 것은? String name() default null; Integer count() default 1; int size() default 4 * 1024; long at() default System.nanoTime(); 요소 값은 클래스 파일의 element_value에 상수로 기록되어야 한다. 4 * 1024는 컴파일러가 접을 수 있는 상수 표현식이므로 허용된다. null은 JLS §9.7.1이 금지하고, Integer는 허용된 요소 타입이 아니며, 메서드 호출은 실행해야 값이 정해지므로 상수가 될 수 없다. @Retention(RUNTIME) @interface Opt { int level() default 1; }로 @Opt class A {}를 컴파일한 뒤, Opt의 기본값만 2로 바꾸어 Opt.java만 다시 컴파일했다. A.class.getAnnotation(Opt.class).level()은? 1. 기본값은 A.class에 복사되어 들어가 있다. 2. 기본값은 읽는 시점에 애노테이션 인터페이스의 AnnotationDefault에서 가져온다. IncompleteAnnotationException이 난다. A를 다시 컴파일하지 않았으므로 getAnnotation이 null을 돌려준다. 사용처의 클래스 파일에는 명시한 요소 값만 기록된다. JLS §9.6.2대로 기본값은 애노테이션을 읽을 때 동적으로 적용되므로 새 기본값 2가 나온다. 기본값이 사라진 경우에만 IncompleteAnnotationException이 난다. @Inherited가 붙은 RUNTIME 애노테이션 @Mark에 대해 옳은 설명은? 인터페이스에 붙인 @Mark는 그 인터페이스를 구현한 클래스에서 getAnnotation으로 보인다. 상위 클래스의 메서드에 붙인 @Mark는 하위 클래스가 재정의한 메서드에서도 보인다. 하위 클래스의 getDeclaredAnnotations()는 상위 클래스에서 물려받은 @Mark도 포함한다. 상위 클래스에 붙인 @Mark는 손자 클래스에서도 getAnnotation으로 보이며, 중간 클래스가 자기 @Mark를 가지면 그것이 우선한다. @Inherited는 클래스에 붙은 애노테이션이 상위 클래스 사슬을 따라 물려지게 할 뿐이다. 인터페이스와 메서드의 애노테이션은 물려받지 않고, getDeclared... 계열은 직접 붙은 것만 본다. OpenJDK는 상속분을 먼저 넣고 자기 선언으로 덮어쓰므로 가까운 쪽이 우선한다. 직접 만든 애노테이션을 붙였는데 프레임워크가 그것을 인식하지 못한다. 원인으로 볼 수 없는 것은? 애노테이션 인터페이스에 @Documented를 붙이지 않았다. 애노테이션 인터페이스에 @Retention(RUNTIME)을 붙이지 않았다. 실행 시 클래스패스에 애노테이션 클래스가 없다. 레코드 컴포넌트에 붙였는데 @Target에 프레임워크가 읽는 위치(예: METHOD)가 없다. @Documented는 문서 도구에 대한 표지일 뿐 리플렉션 결과에 영향을 주지 않는다. 보존 정책을 생략하면 CLASS가 되어 리플렉션에 보이지 않고, 애노테이션 클래스가 없으면 OpenJDK 파서가 조용히 건너뛰며, 레코드의 애노테이션은 @Target이 허용하는 위치에만 전파된다. public boolean equals(Point other)를 정의한 Point를 HashSet에 넣으면 같은 좌표의 점을 찾지 못한다. @Override를 붙이면 무슨 일이 일어나며 그 이유는? 실행 시 JVM이 @Override를 보고 equals(Object) 호출을 이 메서드로 연결해 문제가 해결된다. 매개변수 타입이 달라 상위 타입의 메서드를 재정의하지 않으므로 컴파일 오류가 나서, 오버로딩 실수를 실행 전에 알게 된다. 경고만 출력되고 컴파일은 성공하며 동작도 그대로다. @Override는 RUNTIME 보존이라 HashSet이 리플렉션으로 읽어 올바른 메서드를 고른다. @Override는 SOURCE 보존으로 클래스 파일에 남지 않으며 실행 동작을 바꾸지 않는다. JLS §9.6.4.4에 따라 재정의가 아닌 메서드에 붙이면 컴파일 오류(method does not override or implement a method from a supertype)가 나므로, 시그니처 실수를 컴파일 시점에 잡는다. 문제 자체는 매개변수를 Object로 고쳐야 해결된다.
    메타데이터(metadata)
    데이터에 대한 데이터. 여기서는 코드 자체가 아니라 코드의 의도나 처리 방식에 관한 정보를 말한다.
    메타 애노테이션(meta-annotation)
    애노테이션 인터페이스에 붙이는 애노테이션. @Retention, @Target, @Documented, @Inherited, @Repeatable이 JDK가 제공하는 것이다.
    보존 정책(retention policy)
    애노테이션이 소스(SOURCE), 클래스 파일(CLASS), 실행 중 리플렉션(RUNTIME) 중 어디까지 살아남는지를 정하는 값. 생략하면 CLASS다.
    선언 맥락과 타입 맥락(declaration / type context)
    클래스·필드·메서드처럼 무언가를 선언하는 자리와, 타입 인자처럼 타입이 쓰이는 자리. 타입 맥락은 ElementType.TYPE_USE로 표현된다.
    컨테이너 애노테이션(container annotation)
    반복 가능한 애노테이션이 한 자리에 여러 번 쓰였을 때 그것들을 value 배열에 담아 대신 기록되는 애노테이션.
    RuntimeVisibleAnnotations
    클래스·필드·메서드·레코드 컴포넌트에 붙은 RUNTIME 애노테이션을 담는 클래스 파일 속성. CLASS 보존은 RuntimeInvisibleAnnotations에 담긴다.
    AnnotationDefault
    애노테이션 인터페이스의 요소를 나타내는 메서드에 붙어 그 요소의 기본값을 기록하는 클래스 파일 속성.
    동적 프록시(dynamic proxy)
    java.lang.reflect.Proxy가 실행 중에 만드는, 지정한 인터페이스를 구현한 클래스의 객체. 호출은 InvocationHandler로 전달된다. OpenJDK는 애노테이션 객체를 이것으로 만든다.
    경합 그룹(contention group)
    @Contended로 묶인 필드 집합. HotSpot은 그룹마다 앞에 ContendedPaddingWidth(기본 128) 바이트의 패딩을 넣어 다른 필드와 캐시 라인을 나눠 쓰지 않게 배치한다.
    애노테이션 프로세서(annotation processor)
    javac 안에서 라운드 단위로 실행되며 소스의 선언 모델을 보고 진단 메시지를 내거나 새 소스를 생성하는 플러그인.
