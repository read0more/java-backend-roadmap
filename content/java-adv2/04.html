    이 회차의 질문: 프로그램을 껐다 켜도 남아 있는 데이터

    앞의 두 회차에서 I/O의 부품을 하나씩 살펴봤다. 모든 입출력의 바닥에는 바이트를 한 방향으로 흘려보내는 InputStream/OutputStream이 있고, 문자는 인코딩을 거쳐야 바이트가 되므로 Reader/Writer가 그 변환을 맡는다. 시스템 콜 한 번의 비용이 크기 때문에 BufferedOutputStream 같은 버퍼가 작은 쓰기를 모아 한 번에 내보내고, 이 부품들은 데코레이터(decorator) 구조로 겹겹이 감싸 조립한다. 이번 회차는 새 부품을 거의 소개하지 않는다. 대신 그 부품들로 실제 문제 하나를 네 번 풀어 보면서, 각 풀이가 데이터를 어떤 모양의 바이트로 바꾸는지, 그 모양 때문에 어떤 일이 가능해지고 어떤 일이 깨지는지를 본다.

    문제는 회원 관리다. 회원을 등록하고 목록을 보는 프로그램이 있다. 회원 정보는 아이디, 이름, 나이 세 가지다. 처음에는 회원을 자바 컬렉션에 담는다. 이 방식은 빠르고 코드도 짧지만 프로그램을 끄면 모든 회원이 사라진다. 프로그램이 끝난 뒤에도 데이터가 살아남는 성질을 영속성(persistence)이라고 한다. 영속성을 얻으려면 데이터를 프로세스 바깥, 즉 파일이나 데이터베이스로 옮겨야 한다.

    옮기는 순간 질문이 생긴다. 힙에 있는 회원 객체는 바이트의 나열이 아니다. 객체 헤더가 있고, 필드가 있고, 필드 중 일부는 다른 객체를 가리키는 참조다. 파일은 바이트의 나열일 뿐이다. 그래서 객체를 파일에 넣으려면 "객체를 어떤 바이트 나열로 표현할지"를 정해야 하고, 다시 읽을 때는 그 나열에서 객체를 복원해야 한다. 이 변환을 넓은 뜻으로 직렬화(serialization), 반대 방향을 역직렬화(deserialization)라고 부른다. 이 회차의 네 가지 구현은 모두 같은 인터페이스를 구현하면서 직렬화 형식만 다르다.

    순서는 이렇다. 먼저 메모리 저장소를 만든다. 다음으로 회원 한 명을 텍스트 한 줄로 바꿔 파일에 쓴다. 그다음 DataOutputStream으로 숫자와 문자열을 바이너리로 쓴다. 마지막으로 ObjectOutputStream으로 객체를 통째로 쓴다. 네 파일을 16진수로 열어 비교하고, 자바 직렬화의 내부 규칙과 위험을 실험으로 확인한 뒤, 왜 실무에서는 XML·JSON·데이터베이스를 쓰는지로 마무리한다. 이번 회차의 모든 실행 결과는 macOS의 Temurin OpenJDK 21.0.13에서 직접 돌려 얻은 것이다.

    회원 관리 예제1: 메모리 저장소

    회원을 나타내는 클래스부터 만든다. 필드 세 개를 모두 final로 두어 한 번 만든 회원은 바뀌지 않게 했다. 이 선택은 뒤에서 역직렬화가 final 필드를 어떻게 채우는지 볼 때 다시 의미를 갖는다.

    public class Member {
    private final String id;
    private final String name;
    private final int age;

    public Member(String id, String name, int age) {
        this.id = id;
        this.name = name;
        this.age = age;
    }

    public String getId() { return id; }
    public String getName() { return name; }
    public int getAge() { return age; }

    @Override
    public String toString() {
        return "Member{id=" + id + ", name=" + name + ", age=" + age + "}";
    }
}

    저장 방식을 네 번 바꿀 것이므로 저장소를 인터페이스로 분리한다. 프로그램의 나머지 부분은 이 인터페이스만 알고, 구현이 메모리인지 파일인지는 모른다. 스프링 입문에서 저장소를 인터페이스로 두고 구현을 바꿔 끼우던 것과 같은 구조다.

    import java.util.List;

public interface MemberRepository {
    void add(Member member);
    List findAll();
}
    import java.util.ArrayList;
import java.util.List;

public class MemoryMemberRepository implements MemberRepository {
    private final List members = new ArrayList<>();

    @Override
    public void add(Member member) {
        members.add(member);
    }

    @Override
    public List findAll() {
        return new ArrayList<>(members);
    }
}

    findAll()이 내부 리스트를 그대로 돌려주지 않고 복사본을 만드는 데는 이유가 있다. 내부 리스트를 그대로 내주면 호출한 쪽이 clear()나 add()로 저장소의 상태를 저장소 모르게 바꿀 수 있다. 복사본을 주면 저장소의 상태는 오직 add()로만 바뀐다. 다만 복사되는 것은 리스트라는 "칸의 배열"뿐이고, 칸에 들어 있는 Member 참조는 같은 객체를 가리킨다. Member를 불변으로 만든 덕분에 이 얕은 복사로 충분하다.

    사용자와 대화하는 콘솔 프로그램은 다음과 같다. 저장소 구현을 바꿀 때는 맨 위의 한 줄만 바꾸면 된다.

    import java.util.List;
import java.util.Scanner;

public class MemberConsoleMain {
    private static final MemberRepository repository = new MemoryMemberRepository();

    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);
        while (true) {
            System.out.print("1.회원 등록 | 2.회원 목록 | 3.종료 > ");
            String choice = scanner.nextLine();
            switch (choice) {
                case "1" -> register(scanner);
                case "2" -> printAll();
                case "3" -> {
                    System.out.println("종료합니다.");
                    return;
                }
                default -> System.out.println("잘못된 입력입니다.");
            }
        }
    }

    private static void register(Scanner scanner) {
        System.out.print("ID: ");
        String id = scanner.nextLine();
        System.out.print("이름: ");
        String name = scanner.nextLine();
        System.out.print("나이: ");
        int age = Integer.parseInt(scanner.nextLine());
        repository.add(new Member(id, name, age));
        System.out.println("등록했습니다.");
    }

    private static void printAll() {
        List members = repository.findAll();
        System.out.println("회원 수: " + members.size());
        for (Member member : members) {
            System.out.println(member);
        }
    }
}

    힙의 객체를 그대로 파일에 복사할 수 없는 이유

    그렇다면 종료 직전에 힙의 해당 영역을 통째로 파일에 복사했다가 다음 실행 때 다시 메모리에 올리면 되지 않을까. 이 생각이 통하지 않는 이유가 직렬화라는 개념이 필요한 이유다.

    첫째, 참조는 위치다. HotSpot에서 참조 값은 힙 안의 객체 위치를 가리키는 포인터이고, 설정에 따라 압축된 형태로 저장된다. 다음 실행에서 같은 객체가 같은 주소에 놓인다는 보장은 없다. 한 실행 안에서도 G1 같은 수집기는 살아 있는 객체를 다른 영역으로 옮기며 참조를 고쳐 쓴다. 주소를 그대로 파일에 적어 두면, 다시 읽었을 때 그 주소에는 전혀 다른 것이 있거나 아무것도 없다.

    둘째, 객체의 메모리 모양은 명세가 정하지 않는다. JVMS §2.7은 JVM이 객체의 내부 구조를 특정한 형태로 강제하지 않는다고 적고 있다. 객체 헤더의 크기, 필드의 배치 순서, 압축 포인터 사용 여부는 JVM 구현과 실행 옵션에 따라 달라진다. 같은 클래스라도 다른 JVM이나 다른 옵션에서는 바이트 모양이 다르다. 파일에 남긴 바이트가 다음 실행에서도 뜻을 가지려면, 특정 프로세스와 특정 JVM 구현에서 독립된 약속이 있어야 한다.

    셋째, 파일은 1차원이다. 힙의 객체 그래프는 여러 객체가 서로를 가리키는 그물이고, 같은 객체를 두 곳에서 가리킬 수도, 서로를 가리키는 순환이 있을 수도 있다. 파일에는 바이트를 한 줄로 늘어놓는 것만 가능하다. 그물을 한 줄로 펴는 규칙이 필요하다. "직렬(serial)"이라는 이름이 바로 이 한 줄로 늘어놓는 일을 가리킨다.

    왼쪽에는 참조로 이어진 객체 그래프, 오른쪽에는 한 줄로 늘어선 바이트가 있고, 그 사이를 직렬화와 역직렬화 화살표가 잇는다. 참조(주소)는 파일로 넘어가지 못하고 내용이나 스트림 안의 번호로 바뀐다는 점이 보여야 한다. Clean technical diagram, white background, flat style.     파일에는 참조를 쓸 수 없다. 그래서 객체를 저장한다는 것은 값을 어떤 바이트로 쓸지, 값 사이의 경계를 어떻게 표시할지, 그 바이트가 무엇을 뜻하는지를 어디에 적어 둘지를 정하는 일이다. 네 가지 구현의 차이는 모두 이 세 결정의 차이다.

    회원 관리 예제2: 텍스트 파일에 보관

    가장 먼저 떠오르는 방식은 사람이 읽을 수 있는 텍스트다. 회원 한 명을 한 줄로 쓰고, 줄 안에서는 필드를 쉼표로 구분한다. 줄바꿈이 회원 사이의 경계, 쉼표가 필드 사이의 경계다.

    import java.io.*;
import java.util.ArrayList;
import java.util.List;

import static java.nio.charset.StandardCharsets.UTF_8;

public class TextMemberRepository implements MemberRepository {
    private static final String FILE = "members.txt";
    private static final String DELIMITER = ",";

    @Override
    public void add(Member member) {
        try (BufferedWriter bw = new BufferedWriter(new FileWriter(FILE, UTF_8, true))) {
            bw.write(member.getId() + DELIMITER + member.getName() + DELIMITER + member.getAge());
            bw.newLine();
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    }

    @Override
    public List findAll() {
        List members = new ArrayList<>();
        try (BufferedReader br = new BufferedReader(new FileReader(FILE, UTF_8))) {
            String line;
            while ((line = br.readLine()) != null) {
                String[] parts = line.split(DELIMITER);
                members.add(new Member(parts[0], parts[1], Integer.parseInt(parts[2])));
            }
        } catch (FileNotFoundException e) {
            return members;
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
        return members;
    }
}

    코드의 결정 하나하나를 짚어 보자. new FileWriter(FILE, UTF_8, true)의 생성자는 Java 11에서 추가된 것으로, 문자 집합과 이어 쓰기(append) 여부를 함께 받는다. Java 18부터 기본 문자 집합이 UTF-8이 되었으므로 문자 집합을 생략해도 대부분의 환경에서 같은 결과가 나오지만, 명시해 두면 파일의 바이트가 실행 환경의 설정에 의존하지 않는다. 파일은 프로그램보다 오래 살고 다른 프로그램이 읽을 수도 있으므로, 파일 형식의 일부인 인코딩은 코드에 박아 두는 편이 안전하다. 문자 인코딩이 바이트를 어떻게 정하는지는 1회에서 다뤘다.

    세 번째 인자 true는 파일 끝에 이어 쓰라는 뜻이다. 이 플래그가 운영체제까지 어떻게 전달되는지 OpenJDK 21의 네이티브 소스(FileOutputStream.c)를 보면 분명하다. 파일을 여는 호출에 O_WRONLY | O_CREAT | (append ? O_APPEND : O_TRUNC)를 넘긴다. 이어 쓰기면 O_APPEND, 아니면 O_TRUNC다. POSIX에서 O_APPEND로 연 파일은 매번 쓰기 직전에 파일 위치가 파일 끝으로 옮겨지고, O_TRUNC는 파일을 여는 순간 길이를 0으로 자른다. 뒤의 ObjectStream 예제에서 이 O_TRUNC가 위험한 이유를 다시 본다. FileWriter가 내부적으로 FileOutputStream을 열기 때문에 같은 규칙이 적용된다.

    add()는 호출될 때마다 파일을 열고, 한 줄을 버퍼에 쓰고, try-with-resources가 close()를 부를 때 버퍼를 비우고 파일을 닫는다. 회원 한 명당 파일 열기, 쓰기, 닫기 시스템 콜이 한 번씩 일어난다. 대화형 프로그램에서 사람이 한 명씩 등록하는 속도라면 문제가 되지 않지만, 회원 만 명을 한꺼번에 넣는 일괄 작업이라면 파일을 한 번 열고 여러 줄을 쓰는 별도 메서드가 필요하다. bw.newLine()이 쓰는 줄 구분 문자열은 Javadoc에 따르면 시스템 속성 line.separator가 정하고, OpenJDK 21 구현은 System.lineSeparator()를 쓴다. macOS와 리눅스에서는 \n(0x0A), 윈도우에서는 \r\n(0x0D 0x0A)이다. 읽는 쪽의 readLine()은 \n, \r, \r\n을 모두 줄의 끝으로 인정하고 줄 끝 문자는 빼고 돌려주므로, 다른 운영체제에서 만든 파일도 읽을 수 있다.

    처음 실행할 때는 파일이 없다. FileReader는 내부적으로 FileInputStream을 여는데, 파일이 없으면 FileNotFoundException을 던진다. 이것은 오류가 아니라 "아직 회원이 없다"는 정상 상태이므로 빈 리스트를 돌려준다. 그 밖의 IOException은 디스크 오류나 권한 문제처럼 정말 이상한 상황이므로 UncheckedIOException으로 감싸 위로 올린다. 인터페이스가 IOException을 선언하지 않았기 때문에 체크 예외를 언체크 예외로 바꿔야 하는데, 원인 예외를 그대로 담아 두면 스택 트레이스에서 실제 원인을 볼 수 있다.

    세 명을 등록한 뒤 새 JVM에서 목록을 읽으면 회원이 그대로 남아 있다. 이번 실행 결과에서는 영속성이 생겼다.

    구분자 형식이 깨지는 지점

    텍스트 형식에서 경계는 특별한 문자로 표시된다. 쉼표는 필드의 끝, 줄바꿈은 레코드의 끝이다. 이 방식의 약점은 분명하다. 데이터 자체에 그 특별한 문자가 들어 있으면 경계와 데이터를 구별할 수 없다. 이름에 쉼표가 들어간 회원 new Member("m4", "남궁,민수", 28)을 등록해 보자. add()는 아무 문제 없이 m4,남궁,민수,28이라는 줄을 쓴다. 문제는 읽을 때 드러난다.

    String[] parts = "m4,남궁,민수,28".split(",");
System.out.println(Arrays.toString(parts));
Integer.parseInt(parts[2]);
    [m4, 남궁, 민수, 28]
Exception in thread "main" java.lang.NumberFormatException: For input string: "민수"

    쓰기는 성공하고 읽기가 실패한다는 점이 이 결함을 고약하게 만든다. 잘못된 데이터가 들어간 시점과 오류가 드러나는 시점이 다르다. 이 파일을 읽는 모든 findAll() 호출이 실패하므로, 회원 한 명의 이름 때문에 전체 목록을 볼 수 없게 된다. 이름에 줄바꿈이 들어가도 마찬가지로 한 레코드가 두 줄로 쪼개진다. 경계 표시 문자와 데이터가 같은 공간을 공유하는 형식은, 쓰는 쪽이 데이터를 검사하거나 바꿔 쓰지 않는 한 언제든 이렇게 깨진다.

    해결책은 두 가지 방향이다. 하나는 이스케이프(escape) 규칙을 정하는 것이다. 흔히 CSV라고 부르는 형식을 정리한 RFC 4180(표준이 아닌 정보 제공용 문서다)은 쉼표, 큰따옴표, 줄바꿈이 들어간 필드를 큰따옴표로 감싸고, 필드 안의 큰따옴표는 두 번 써서 표시하도록 정리한다. 이 규칙을 따르면 "남궁,민수"처럼 쓸 수 있지만, 읽는 쪽은 더 이상 split() 한 번으로 끝나지 않는다. 지금 따옴표 안에 있는지를 기억하며 한 글자씩 읽는 상태 기계가 필요하다. 다른 하나는 경계를 문자로 표시하지 않는 것이다. 값의 길이를 먼저 적어 두면 데이터에 무슨 문자가 들어 있든 상관없다. 다음 예제의 DataOutputStream이 이 방식이다.

    String.split()에는 또 하나의 함정이 있다. 기본 형태의 split(regex)는 결과 끝의 빈 문자열을 버린다. 필드가 비어 있을 수 있는 형식이라면 이것 때문에 배열 길이가 달라진다.

    System.out.println(Arrays.toString("a,b,,".split(",")));      // 끝의 빈 문자열 제거
System.out.println(Arrays.toString("a,b,,".split(",", -1)));  // limit 음수: 모두 유지
System.out.println(Arrays.toString(",a".split(",")));         // 앞의 빈 문자열은 유지
    [a, b]
[a, b, , ]
[, a]

    Javadoc에 따르면 split(regex)는 split(regex, 0)과 같고, limit가 0이면 끝에 오는 빈 문자열을 버린다. 마지막 필드가 빈 값인 레코드는 배열 길이가 짧아져 parts[2]에서 ArrayIndexOutOfBoundsException이 날 수 있다. 빈 필드를 허용하는 형식이라면 split(DELIMITER, -1)을 써야 한다.

    숫자를 문자로 저장하는 데도 대가가 있다. Integer.parseInt(" 20")은 앞의 공백 때문에 NumberFormatException: For input string: " 20"을 던진다. 사람이 편집기로 파일을 고치다 공백 하나를 넣으면 프로그램이 읽지 못한다. 또한 쓸 때는 정수를 10진 문자열로, 읽을 때는 문자열을 정수로 바꾸는 계산이 매번 일어난다. 그 대신 텍스트 형식은 어떤 편집기로도 열어 읽고 고칠 수 있고, 줄 단위 비교 도구로 변경 내역을 볼 수 있으며, 인코딩만 맞으면 어떤 언어로 만든 프로그램도 읽을 수 있다. 사람이 읽을 수 있다는 장점과 해석이 모호할 수 있다는 단점은 같은 성질의 양면이다.

    회원 관리 예제3: DataStream으로 보관

    두 번째 파일 구현은 DataOutputStream과 DataInputStream을 쓴다. 이 둘은 바이트 스트림을 감싸는 데코레이터로, 자바의 기본형과 문자열을 정해진 바이트 형식으로 쓰고 읽는 메서드를 제공한다.

    import java.io.*;
import java.util.ArrayList;
import java.util.List;

public class DataMemberRepository implements MemberRepository {
    private static final String FILE = "members.dat";

    @Override
    public void add(Member member) {
        try (DataOutputStream dos = new DataOutputStream(
                new BufferedOutputStream(new FileOutputStream(FILE, true)))) {
            dos.writeUTF(member.getId());
            dos.writeUTF(member.getName());
            dos.writeInt(member.getAge());
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    }

    @Override
    public List findAll() {
        List members = new ArrayList<>();
        try (DataInputStream dis = new DataInputStream(
                new BufferedInputStream(new FileInputStream(FILE)))) {
            while (true) {
                String id;
                try {
                    id = dis.readUTF();
                } catch (EOFException e) {
                    break; // 레코드 경계에서 끝남: 정상 종료
                }
                String name = dis.readUTF(); // 여기서의 EOF는 파일 손상
                int age = dis.readInt();
                members.add(new Member(id, name, age));
            }
        } catch (FileNotFoundException e) {
            return members;
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
        return members;
    }
}

    스트림 조립 순서를 보자. FileOutputStream이 파일과 연결되고, BufferedOutputStream이 작은 쓰기를 모으고, 가장 바깥의 DataOutputStream이 정수와 문자열을 바이트로 바꾼다. writeInt()는 4바이트를 쓰는데, 버퍼가 없으면 FileOutputStream에 바로 전달되어 쓰기 시스템 콜로 이어진다. 3회에서 본 것처럼 버퍼를 사이에 두면 이 작은 쓰기들이 메모리에서 모였다가 close() 때 한 번에 내려간다. try-with-resources는 가장 바깥의 DataOutputStream만 닫지만, 데코레이터의 close()가 안쪽 스트림의 close()를 연쇄적으로 부르므로 버퍼를 비우고 파일까지 닫힌다.

"m1"은 2바이트이므로 00 02 뒤에 6d 31이 오고, "김자바"는 9바이트이므로 00 09 뒤에 9바이트가 온다. 읽는 쪽의 readUTF()는 먼저 2바이트를 읽어 길이를 알아낸 뒤 정확히 그만큼만 읽는다. 데이터 안에 쉼표가 있든 줄바꿈이 있든 0x00이 있든 상관없다. 길이가 경계를 정하므로 데이터의 내용이 경계를 흐트러뜨릴 수 없다. 앞에서 텍스트 형식을 깨뜨린 "남궁,민수"는 이 형식에서는 아무 문제가 없다.

    writeInt(20)은 00 00 00 14다. 0x14가 10진수 20이다. 4바이트 중 가장 높은 자리 바이트가 먼저 나오는 순서를 빅 엔디언(big-endian)이라고 한다. DataOutput의 Javadoc은 writeInt가 네 바이트를 높은 자리부터 쓴다고 정하고 있으며, 이 순서는 CPU와 무관하다. x86이나 Apple Silicon처럼 메모리에 정수를 낮은 자리부터 저장하는(리틀 엔디언) CPU에서 실행해도 파일에는 항상 빅 엔디언으로 쓰인다. 그래서 어느 플랫폼에서 쓴 파일이든 어느 플랫폼에서든 같은 값으로 읽힌다. 네트워크 프로토콜의 표준 바이트 순서도 빅 엔디언이라서 "네트워크 바이트 순서"라고도 부르며, 소켓을 다루는 6~8회에서 이 사실을 다시 만난다.

    파일의 끝을 어떻게 아는가

    DataInputStream의 읽기 메서드는 필요한 바이트를 다 읽기 전에 스트림이 끝나면 EOFException을 던진다. findAll()은 이 예외를 두 가지로 구분해 다룬다. 레코드의 첫 필드를 읽다가 만난 EOF는 "레코드 경계에서 파일이 끝났다"는 뜻이므로 정상 종료다. 레코드 중간에서 만난 EOF는 레코드가 잘렸다는 뜻이므로 파일 손상이다. 그래서 try는 첫 readUTF()만 감싸고, 나머지 두 읽기의 EOFException은 바깥의 catch (IOException e)까지 올라가게 했다. 60바이트 파일의 앞 50바이트만 남기고 잘라 읽어 보면 이 구분이 동작한다.

    Exception in thread "main" java.io.UncheckedIOException: java.io.EOFException
	...
Caused by: java.io.EOFException

    앞의 두 회원은 정상적으로 읽혔고(50바이트 안에 19+19=38바이트가 온전히 있다), 세 번째 회원의 이름을 읽던 중 EOF를 만나 예외가 올라갔다. 잘린 파일을 조용히 "회원 두 명"으로 받아들이지 않고 손상으로 보고하는 것이 맞다. 흔히 보는 while (dis.available() > 0) 같은 반복 조건은 쓰지 않았다. InputStream.available()의 Javadoc은 이 값을 막힘 없이 읽을 수 있는 바이트 수의 "추정치"라고 정의하며, 스트림의 남은 전체 길이라는 보장이 없다. 파일에서는 대개 남은 길이와 같게 나오지만, 같은 코드가 네트워크 스트림을 읽게 되면 아직 도착하지 않은 데이터를 0으로 보고 반복을 일찍 끝낼 수 있다.

    또 하나의 방법은 파일 맨 앞에 레코드 수를 적는 것이다. 그러면 읽는 쪽은 정확히 그 수만큼만 읽으면 되고, EOF는 언제나 손상을 뜻하게 된다. 그 대신 회원을 추가할 때마다 파일 앞부분의 숫자를 고쳐야 하므로 단순한 이어 쓰기가 불가능해진다. 형식의 결정 하나가 쓰기 방식까지 정한다.

    65535바이트 제한과 수정된 UTF-8

    길이 접두가 2바이트라는 것은 문자열 하나가 인코딩 후 65,535바이트를 넘을 수 없다는 뜻이다. 한글처럼 한 글자가 3바이트인 문자는 21,845자가 한계다. 직접 확인해 보면 21,845자는 길이 접두 2바이트를 더해 65,537바이트로 쓰이고, 한 글자를 더하면 예외가 난다.

    회원 관리 예제4: ObjectStream으로 보관

    DataStream 구현에서 우리는 회원 한 명을 쓰기 위해 필드 세 개를 하나씩 꺼내 순서대로 썼고, 읽을 때는 같은 순서로 하나씩 읽어 생성자에 넘겼다. 필드가 열 개로 늘면 쓰는 코드와 읽는 코드가 모두 열 줄씩 늘고, 둘의 순서가 어긋나면 앞에서 본 것처럼 조용히 틀린 값이 만들어진다. ObjectOutputStream은 이 일을 자바 런타임이 대신하게 한다. 객체를 넘기면 그 객체의 클래스를 조사해 어떤 필드가 있는지 알아내고, 필드 값과 함께 "이 바이트들은 어떤 클래스의 어떤 필드인가"라는 설명까지 스트림에 쓴다. 이것이 좁은 뜻의 자바 직렬화(Java serialization)다.

    자바 직렬화의 대상이 되려면 클래스가 java.io.Serializable을 구현해야 한다. 이 인터페이스에는 메서드가 하나도 없다. 구현할 것이 없는 이런 인터페이스를 표시 인터페이스(marker interface)라고 부르는데, "이 클래스의 객체는 직렬화해도 된다"는 허락을 타입으로 표시하는 역할만 한다. 회원 클래스의 선언을 다음처럼 바꾼다. serialVersionUID의 의미는 뒤에서 실험으로 확인한다.

    import java.io.Serializable;

public class Member implements Serializable {
    private static final long serialVersionUID = 1L;

    private final String id;
    private final String name;
    private final int age;
    // 생성자, getter, toString은 앞과 같다
}

    저장소 구현은 다음과 같다. 앞의 두 구현과 가장 크게 다른 점은 add()가 회원 한 명을 파일 끝에 덧붙이지 않는다는 것이다. 파일 전체를 읽어 리스트를 복원하고, 새 회원을 리스트에 더한 뒤, 리스트 전체를 파일에 다시 쓴다.

    import java.io.*;
import java.util.ArrayList;
import java.util.List;

public class ObjectMemberRepository implements MemberRepository {
    private static final String FILE = "members.obj";

    @Override
    public void add(Member member) {
        List members = findAll();
        members.add(member);
        try (ObjectOutputStream oos = new ObjectOutputStream(
                new BufferedOutputStream(new FileOutputStream(FILE)))) {
            oos.writeObject(members);
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        }
    }

    @Override
    @SuppressWarnings("unchecked")
    public List findAll() {
        try (ObjectInputStream ois = new ObjectInputStream(
                new BufferedInputStream(new FileInputStream(FILE)))) {
            return (List) ois.readObject();
        } catch (FileNotFoundException e) {
            return new ArrayList<>();
        } catch (IOException e) {
            throw new UncheckedIOException(e);
        } catch (ClassNotFoundException e) {
            throw new IllegalStateException(e);
        }
    }
}

    쓰는 코드는 writeObject(members) 한 줄, 읽는 코드는 readObject() 한 줄이다. 필드를 하나씩 다루는 코드가 사라졌다. readObject()는 IOException 외에 ClassNotFoundException도 던질 수 있는데, 스트림에 적힌 클래스 이름에 해당하는 클래스를 현재 JVM에서 찾지 못했다는 뜻이다. 스트림이 클래스 이름을 담고 있다는 사실이 여기서부터 드러난다. findAll()이 돌려주는 리스트는 매번 파일에서 새로 만든 객체이므로, 메모리 저장소처럼 복사본을 따로 만들 필요가 없다.

    세 명을 등록하고 새 JVM에서 목록을 읽으면 앞의 두 구현과 같은 결과가 나온다.

    왜 이어 쓰지 않는가

    텍스트 구현과 DataStream 구현은 FileOutputStream(FILE, true)로 파일 끝에 레코드를 덧붙였다. 같은 방식을 ObjectOutputStream에 쓰면 어떻게 될까. 회원 한 명을 쓴 파일에, 이어 쓰기 모드로 새 ObjectOutputStream을 열어 회원을 한 명 더 쓰고, 하나의 ObjectInputStream으로 두 번 읽어 보았다.

    Member{id=m1, name=김자바, age=20}
java.io.StreamCorruptedException: invalid type code: AC

    첫 회원은 읽히고 두 번째에서 실패한다. 원인은 ObjectOutputStream의 생성자에 있다. 생성자는 객체를 하나도 쓰기 전에 스트림 헤더 4바이트 ac ed 00 05를 먼저 쓴다. 이어 쓰기로 두 번째 스트림을 열면 파일 중간에 헤더가 하나 더 들어간다. 읽는 쪽의 ObjectInputStream은 헤더를 생성 시점에 한 번만 읽고, 그 뒤로는 객체마다 첫 바이트를 "다음에 오는 것이 무엇인지" 알려 주는 타입 코드로 해석한다. 두 번째 객체 자리에서 만난 0xAC는 정의된 타입 코드가 아니므로 스트림이 손상되었다고 판단한다. 직렬화 스트림은 하나의 헤더 아래 이어지는 하나의 문법 단위이고, 파일에 덧붙일 수 있는 독립 레코드의 나열이 아니다. 그래서 이 구현은 매번 전체를 다시 쓰는 방식을 택했다. 이 선택의 대가는 뒤에서 따로 본다.

    둘째, 참조형 필드의 타입이 Ljava/lang/String;이라는 낯익은 형태로 적혀 있다. 이것은 JVMS §4.3.2의 필드 디스크립터(field descriptor) 문법과 같은 형식이다. 클래스 파일에서 필드 타입을 적는 바로 그 표기다. 기본형 필드의 타입 코드 'I'도 JVMS의 int 디스크립터와 같은 문자다. 문자열 값은 TC_STRING(0x74) 뒤에 2바이트 길이와 수정된 UTF-8 바이트가 오는데, 앞에서 본 writeUTF()와 같은 구조다. 65,535바이트를 넘는 문자열은 8바이트 길이를 쓰는 TC_LONGSTRING(0x7C)으로 기록된다.

    스트림에는 제네릭 타입이 없다

    findAll()의 (List) ois.readObject()에는 컴파일러가 확인되지 않은 형변환(unchecked cast) 경고를 낸다. 덤프를 보면 이유를 알 수 있다. 스트림에 적힌 것은 java.util.ArrayList라는 클래스 이름뿐이고, 원소 타입이 Member라는 정보는 어디에도 없다. 제네릭 타입 인자는 컴파일 후 지워지므로(타입 소거, type erasure) 실행 중의 ArrayList 객체 자체도 원소 타입을 모른다. 그래서 이 형변환은 실행 시점에 List인지만 검사한다. 시험 삼아 문자열 "m1"만 든 ArrayList를 members.obj에 써 두고 findAll()을 불러 보면, findAll()은 성공하고 원소를 꺼내 Member 변수에 담는 순간 비로소 실패한다.

    ObjectOutputStream 안의 버퍼: 아래 스트림으로 내려가는 write 17번

    저장소 코드는 ObjectOutputStream과 FileOutputStream 사이에 BufferedOutputStream을 끼웠다. 그런데 ObjectOutputStream도 안쪽에 자기 버퍼를 가지고 있다. OpenJDK 21 소스의 내부 클래스 ObjectOutputStream.BlockDataOutputStream은 1,024바이트 배열 buf(상수 MAX_BLOCK_SIZE), 블록 헤더용 5바이트 배열 hbuf, 문자열 변환용 256자 배열 cbuf를 가지고, ObjectOutputStream이 쓰는 모든 바이트는 이 객체를 거쳐 아래 스트림으로 간다. 버퍼가 이미 있다면 바깥의 BufferedOutputStream은 군더더기일까. 짐작하지 말고 아래 스트림에 도착하는 write 호출을 직접 세어 보자. 호출마다 요청 길이를 기록하는 FilterOutputStream을 만들어 ObjectOutputStream 바로 아래에 둔다. Member는 serialVersionUID = 1L을 선언한 앞 절의 판이다.

    import java.io.*;
import java.util.*;

public class CountWrites {
    static class Counting extends FilterOutputStream {
        final List sizes = new ArrayList<>();
        Counting(OutputStream out) { super(out); }
        @Override public void write(int b) throws IOException { sizes.add(1); out.write(b); }
        @Override public void write(byte[] b, int off, int len) throws IOException { sizes.add(len); out.write(b, off, len); }
    }

    public static void main(String[] args) throws IOException {
        List members = new ArrayList<>(List.of(
                new Member("m1", "김자바", 20),
                new Member("m2", "이코딩", 31),
                new Member("m3", "박바이트", 45)));

        Counting direct = new Counting(OutputStream.nullOutputStream());
        ObjectOutputStream o1 = new ObjectOutputStream(direct);
        System.out.println("생성자 직후: " + direct.sizes);
        o1.writeObject(members);
        System.out.println("writeObject 직후: " + direct.sizes.size() + "회");
        o1.close();
        int sum = direct.sizes.stream().mapToInt(Integer::intValue).sum();
        System.out.println("버퍼 없음: write " + direct.sizes.size() + "회, 합계 " + sum + "바이트");
        System.out.println(direct.sizes);

        Counting buffered = new Counting(OutputStream.nullOutputStream());
        ObjectOutputStream o2 = new ObjectOutputStream(new BufferedOutputStream(buffered));
        o2.writeObject(members);
        o2.close();
        System.out.println("BufferedOutputStream: write " + buffered.sizes.size() + "회 " + buffered.sizes);
    }
}

    합계 203바이트는 앞에서 덤프한 members.obj와 같은 바이트다. 1,024바이트 버퍼가 있는데도 생성자와 writeObject 한 번이 아래 스트림의 write를 17번 불렀고, close()를 부르기 전에 이미 17번이 모두 끝났다. 각 호출의 길이를 덤프의 오프셋과 맞춰 보면 어디서 끊기는지 정확히 보인다. 끊기는 이유는 소스에서 세 가지로 확인된다.

    • 모드가 바뀔 때마다 버퍼를 비운다. BlockDataOutputStream에는 두 가지 모드가 있다. 기본 모드에서는 DataOutputStream과 같은 형식으로 쓰고, 블록 데이터 모드(block data mode)에서는 데이터를 TC_BLOCKDATA 표시로 감싸 쓴다. 모드를 바꾸는 setBlockDataMode는 바꾸기 전에 drain()으로 buf의 내용을 아래 스트림에 write한다. 생성자는 헤더 ac ed 00 05를 buf에 쓴 직후 블록 데이터 모드를 켜므로, 객체를 하나도 쓰기 전에 4바이트 write가 나간다. 그 뒤로도 writeNonProxyDesc가 클래스 설명을 쓰고 annotateClass를 부르기 직전, 사용자 정의 writeObject(여기서는 ArrayList의 것)를 부르기 전후, 그 안의 defaultWriteObject 전후, 그리고 writeObject0이 시작하고 끝날 때마다 모드가 바뀐다. 41(0x04~0x2c, TC_OBJECT부터 ArrayList 클래스 설명의 size 필드까지), 65(0x39~0x79, Member 클래스 설명), 17·17·20(회원마다 문자열 두 개)이 이 경계에서 끊긴 덩어리다.
    • 기본형 필드 값은 버퍼를 거치지 않는다. defaultWriteFields는 기본형 필드 값을 primVals 배열에 모은 뒤 bout.write(primVals, 0, primDataSize, false)로 넘긴다. 기본 모드에서 복사 플래그가 false이면 이 메서드는 buf를 먼저 비우고 배열을 아래 스트림에 직접 쓴다. 회원마다 2 또는 6 다음에 오는 4가 이것이다. 78 70(첫 회원)이나 73 71 00 7e 00 02(둘째, 셋째 회원)가 비워진 뒤 age의 4바이트가 따로 나간다.
    • 블록 헤더는 따로 나간다. 블록 데이터를 내보낼 때 writeBlockHeader는 hbuf에 만든 헤더(길이가 255 이하면 77과 길이 1바이트, 그보다 길면 7a와 길이 4바이트)를 별도의 out.write로 쓰고, 그다음에 데이터를 쓴다. 0x33의 77 04 00 00 00 03이 2와 4 두 번으로 나뉜 이유다.

    마지막 1은 ArrayList.writeObject가 쓴 데이터의 끝을 표시하는 78(TC_ENDBLOCKDATA)이고, 최상위 writeObject0이 끝나며 블록 데이터 모드로 돌아갈 때 비워졌다. 정리하면 buf의 크기 1,024는 상수 이름 그대로 블록 데이터 한 덩어리의 최대 길이이고, 이 버퍼는 모드가 바뀔 때마다 비워지므로 아래 스트림의 호출 횟수를 줄여 주지 못한다.

    운영체제 쪽 의미는 2회에서 본 그대로다. FileOutputStream.write(byte[], int, int) 한 번은 네이티브 writeBytes를 거쳐 write 시스템 콜로 이어진다. 저장소에서 BufferedOutputStream을 빼고 new ObjectOutputStream(new FileOutputStream(FILE))로 열었다면, 회원 세 명을 저장하는 데 시스템 콜이 17번 일어나고 그중 12번은 6바이트 이하의 쓰기다. BufferedOutputStream을 끼우면 이 호출들이 그 8,192바이트 버퍼에 모였다가 close()의 flush 때 203바이트 write 한 번으로 내려간다.

    읽는 쪽도 같은 구조다. 같은 203바이트를 ByteArrayInputStream에 담고, read 호출마다 요청 길이를 기록하는 FilterInputStream으로 감싸 ObjectInputStream으로 읽어 보았다.

    역직렬화는 생성자를 부르지 않는다

    역직렬화가 객체를 만든다면, 생성자를 부를까. 실험으로 확인하자. 직렬화할 수 없는 부모 클래스 Base와 직렬화할 수 있는 자식 클래스 Child를 만들고, 각 생성자에서 메시지를 찍는다. Child에는 필드 초기화식이 있는 필드와 transient 필드를 둔다.

    import java.io.*;

class Base {
    Base() { System.out.println("Base() 호출"); }
}

class Child extends Base implements Serializable {
    private static final long serialVersionUID = 1L;
    private final String name;
    private int count = 100;
    private transient int cache = 7;

    Child(String name) {
        System.out.println("Child(String) 호출");
        this.name = name;
        count = 5;
    }

    public String toString() {
        return "Child{name=" + name + ", count=" + count + ", cache=" + cache + "}";
    }
}

public class Ctor {
    public static void main(String[] args) throws Exception {
        Child c = new Child("x");
        System.out.println("직렬화 전: " + c);
        ByteArrayOutputStream bos = new ByteArrayOutputStream();
        try (ObjectOutputStream o = new ObjectOutputStream(bos)) { o.writeObject(c); }
        System.out.println("--- 역직렬화 ---");
        try (ObjectInputStream i = new ObjectInputStream(new ByteArrayInputStream(bos.toByteArray()))) {
            System.out.println("역직렬화 후: " + i.readObject());
        }
    }
}

    역직렬화 때 Child(String)은 호출되지 않았고, Base()만 호출되었다. Serializable의 Javadoc이 정한 규칙 그대로다. 직렬화할 수 없는 상위 클래스의 필드는 "가장 아래에 있는 직렬화 불가능한 상위 클래스"의 인자 없는 생성자로 초기화되고, 그 생성자는 하위 클래스에서 접근할 수 있어야 한다. Child의 필드 값은 생성자가 아니라 스트림에서 온다. count는 초기화식의 100이 아니라 스트림에 기록된 5이고, transient인 cache는 스트림에 기록되지 않았으므로 초기화식의 7도 아니고 int의 기본값 0이다.

    컴파일러는 부모 생성자 호출(invokespecial Base."") 직후에 필드 초기화식(count = 100, cache = 7)을 넣고, 그 뒤에 생성자 본문을 둔다. 결국 Child의 메서드 하나가 초기화식과 본문을 모두 담고 있다. 역직렬화는 이 을 실행하지 않으므로 초기화식도 함께 건너뛴다.

    그러면 객체는 어떻게 만들어질까. 평소의 new Child("x")는 바이트코드로 new 명령(메모리 할당, 필드는 기본값)과 invokespecial Child.(초기화) 두 단계다. 역직렬화는 이 두 단계를 다르게 엮는다. OpenJDK 21의 jdk.internal.reflect.ReflectionFactory.newConstructorForSerialization은 상위 클래스를 거슬러 올라가며 처음으로 Serializable이 아닌 클래스를 찾고, 그 클래스의 인자 없는 생성자를 고른 뒤, "Child 객체를 할당하되 실행하는 생성자는 Base()인" 특별한 생성자를 만든다. 이렇게 만든 객체의 필드에는 스트림에서 읽은 값을 써 넣는데, OpenJDK 21의 ObjectStreamClass 내부 클래스 FieldReflector는 jdk.internal.misc.Unsafe의 putInt, putReference 같은 메서드로 필드 오프셋에 값을 직접 쓴다. 그래서 final 필드도 채워진다. 회원 클래스의 id, name, age가 모두 final인데도 복원된 이유가 이것이다. 회원 클래스의 직접 부모는 Object이므로, 회원을 역직렬화할 때 실행되는 생성자는 Object()뿐이다.

    생성자를 건너뛴다는 것의 의미: 불변식 검사

    생성자를 건너뛰는 것이 왜 문제인지 보자. 나이가 음수인 회원을 막기 위해 생성자에 검사를 넣었다고 하자.

    class MemberC implements Serializable {
    private static final long serialVersionUID = 1L;
    private final String id;
    private final int age;

    MemberC(String id, int age) {
        if (age < 0) throw new IllegalArgumentException("age < 0: " + age);
        this.id = id;
        this.age = age;
    }
    // toString 생략
}

    new MemberC("m1", -1)은 예외로 막힌다. 그런데 정상 객체 new MemberC("m1", 20)을 직렬화한 바이트에서 00 00 00 14를 찾아 ff ff ff ff로 바꾼 뒤 역직렬화하면 다음과 같다.

    MemberC{id=m1, age=-1}

    생성자가 실행되지 않으므로 검사도 실행되지 않는다. 클래스가 생성자로 지키던 불변식(invariant)이 파일을 고칠 수 있는 사람에게는 아무 의미가 없다. 일반 클래스에서 이를 막으려면 private void readObject(ObjectInputStream in)을 정의해 in.defaultReadObject()로 필드를 읽은 뒤 같은 검사를 다시 하고 InvalidObjectException을 던져야 한다. 생성자와 역직렬화라는 두 개의 생성 경로에 같은 검사를 두 번 써야 하는 셈이다.

    레코드(record)는 이 문제를 다르게 푼다. ObjectInputStream의 Javadoc과 직렬화 명세 1.13절은 레코드를 역직렬화할 때 스트림에서 읽은 값을 인자로 레코드의 정규 생성자(canonical constructor)를 호출한다고 정한다. 같은 검사를 컴팩트 생성자에 넣은 레코드로 같은 실험을 해 보았다.

    record MemberR(String id, int age) implements Serializable {
    MemberR {
        if (age < 0) throw new IllegalArgumentException("age < 0: " + age);
    }
}
    java.io.InvalidObjectException: age < 0: -1

    이번에는 생성자가 실행되어 검사가 동작했고, 생성자가 던진 IllegalArgumentException은 원인(cause)으로 담긴 채 InvalidObjectException으로 바뀌어 나왔다. 레코드에서는 객체를 만드는 길이 정규 생성자 하나뿐이다. 명세는 그 대가도 적어 두었다. 레코드의 구성 요소를 먼저 역직렬화한 뒤 생성자를 부르므로, 레코드가 자기 구성 요소를 통해 자기 자신을 가리키는 순환은 복원되지 않는다.

    레코드는 Java 16에서 정식 기능이 되었다. 레코드에서는 writeObject, readObject 같은 직렬화 특수 메서드를 선언해도 무시된다(ObjectInputStream Javadoc).

    역직렬화용 생성자의 정체: 검증기가 거부하는 바이트코드

    앞에서 ReflectionFactory.newConstructorForSerialization이 "Child 객체를 할당하되 실행하는 생성자는 Base()인" 특별한 생성자를 만든다고 했다. 자바 소스로는 이런 생성자를 쓸 수 없다. new Child(...)는 반드시 Child의 생성자를 실행하고, 부모 생성자는 그 안에서만 불린다. 그렇다면 이 특별한 생성자는 무엇으로 만들어질까. OpenJDK 21의 ReflectionFactory.generateConstructor는 MethodAccessorGenerator.generateSerializationConstructor를 불러 바이트코드를 직접 조립하고, 그 바이트로 클래스 하나를 새로 정의한다. 같은 ReflectionFactory에서 일반 생성자의 접근자(newConstructorAccessor)는 MethodHandleAccessorFactory로 만드는데, 직렬화용만은 클래스 파일을 생성하는 이 길을 쓴다.

    앞의 Ctor 예제에서 count, cache 필드와 결과 출력을 뺀 판을 클래스 로딩·초기화 로그와 함께 실행하면 그 클래스가 보인다. 관련된 줄만 남기고 경로는 줄였다. 앞의 시간 값은 실행마다 다르다.

    JVMS는 이 코드를 허용하지 않는다

    JVMS §4.10.1.9의 invokespecial 타입 규칙은 호출을 두 경우로 나눈다. 생성자 안에서 아직 초기화되지 않은 자기 자신(uninitializedThis)에게 부르는 경우에는 자기 클래스나 직접 상위 클래스의 을 부를 수 있다. javac가 생성자 첫머리에 넣는 invokespecial Base.""이 이 경우다. 반면 new 명령으로 만든 미초기화 객체(uninitialized(Address))에 부르는 경우, 규칙 rewrittenUninitializedType은 Address 위치의 명령이 바로 그 이 속한 클래스를 만드는 new여야 한다고 정한다. new Child로 만든 객체에는 Child.""만 부를 수 있다는 뜻이다. 위 접근자의 0번과 24번은 정확히 이 규칙을 어긴다.

    생성된 접근자는 어떻게 검증을 통과하는가

    답은 통과하는 것이 아니라 검증 대상에서 빠지는 것이다. OpenJDK 21 HotSpot의 Verifier::is_eligible_for_verification은 클래스가 jdk.internal.reflect.MagicAccessorImpl의 하위 타입이면(klass->is_subtype_of(...)) 검증할 클래스가 아니라고 판단한다. 생성된 접근자의 상속 관계는 GeneratedSerializationConstructorAccessor1 → SerializationConstructorAccessorImpl → ConstructorAccessorImpl → MagicAccessorImpl이다. 앞의 로그에서 Base와 Child는 검증되고 생성된 두 클래스는 검증 줄이 없었던 이유가 이것이다. JDK 소스의 SerializationConstructorAccessorImpl 클래스 주석도, 하위 클래스를 할당한 뒤 첫 번째 직렬화 불가능한 상위 클래스의 인자 없는 생성자를 부르는 이 코드는 VM 명세상 올바른 연산이 아니어서 검증 오류를 피할 수 없다고 직접 적는다. 같은 주석에 따르면 처음에는 이 클래스와 그 하위 클래스만 검증에서 뺐지만, 버그 4486457을 고치면서 리플렉션용으로 생성되는 바이트코드 전체(MagicAccessorImpl 계열 전체)의 검증을 끄게 되었고, 이 클래스는 디버깅 편의를 위해 남겨 둔 것이다.

    정리하면 "역직렬화는 생성자를 건너뛴다"는 말의 바닥에는 명세가 허용하지 않는 바이트코드와, 그 코드를 JDK 내부 클래스에 한해 검증에서 빼 주는 HotSpot의 예외 처리가 있다(OpenJDK 21 HotSpot 기준). 이 면제는 MagicAccessorImpl 계열에만 적용되므로, 애플리케이션이 만든 클래스 파일에 같은 명령 순서를 넣으면 위 실험처럼 VerifyError가 난다.

    serialVersionUID: 클래스가 바뀐 뒤에도 옛 파일을 읽을 수 있는가

    파일은 프로그램보다 오래 산다. 회원 파일을 만든 뒤 회원 클래스에 이메일 필드를 추가해 새 버전을 배포하면, 새 프로그램은 옛 클래스로 쓴 파일을 읽어야 한다. 직렬화 스트림에는 클래스 설명이 들어 있으므로, 런타임은 스트림의 클래스 설명과 현재 JVM에 로드된 클래스를 비교할 수 있다. 그 비교의 첫 관문이 serialVersionUID다. Serializable의 Javadoc은 이 값을 "보내는 쪽과 받는 쪽이 직렬화에 관해 호환되는 클래스를 로드했는지 확인하는 버전 번호"로 설명하고, 값이 다르면 InvalidClassException이 난다고 정한다.

    클래스가 이 값을 선언하지 않으면 런타임이 계산한다. 직렬화 명세 4장은 이 기본값이 클래스 이름, 인터페이스, 메서드, 필드로부터 SHA 해시로 계산된다고 적는다. JDK에 들어 있는 serialver 도구로 그 값을 볼 수 있다. serialVersionUID를 선언하지 않은 원래의 회원 클래스로 파일을 쓰고, 클래스에 private String email; 한 줄을 추가한 뒤 다시 읽어 보았다.

    클래스 이름과 패키지도 형식의 일부다. 스트림에는 Member나 java.util.ArrayList 같은 완전한 클래스 이름이 적혀 있고, 읽는 쪽은 그 이름으로 클래스를 찾는다. 따라서 패키지를 옮기거나 클래스 이름을 바꾸는 리팩터링을 하면 옛 파일은 ClassNotFoundException으로 읽히지 않는다. 자바 직렬화 파일을 오래 보관한다는 것은 클래스의 이름, 패키지, 필드 구조를 그 파일과 함께 동결한다는 뜻이다. serialVersionUID를 선언해도 이 결합은 풀리지 않는다. 선언은 "이 정도 변화는 호환된다고 내가 책임지겠다"는 개발자의 표시일 뿐이다.

    앞에서 필드 하나를 추가하자 계산된 UID가 완전히 달라졌다. 그렇다면 정확히 무엇이 해시의 입력일까. 직렬화 명세 4.6절(Stream Unique Identifiers)은 입력 바이트를 만드는 순서를 항목별로 정한다. 그 바이트를 만드는 도구가 이 회차에서 쓴 DataOutputStream이라는 점이 재미있다. 이름과 디스크립터는 writeUTF 형식(2바이트 길이와 수정된 UTF-8)으로, 수식어는 writeInt로 32비트 정수로 쓴다.

OpenJDK 21에서 이 계산은 ObjectStreamClass.computeDefaultSUID가 하고, serialver도 같은 값을 출력한다. 구현을 보면 두 가지 세부가 더 있다. 하나는 for (int i = Math.min(hashBytes.length, 8) - 1; i >= 0; i--) hash = (hash << 8) | (hashBytes[i] & 0xFF);라는 조립 방식이다. 해시의 첫 바이트가 long의 가장 낮은 자리로 간다. 다른 하나는 생성자와 메서드의 디스크립터를 쓸 때만 /를 .으로 바꾼다는 것이다(필드 디스크립터는 그대로 쓴다). 그리고 리플렉션으로는 의 존재를 알 수 없으므로, 이 항목은 네이티브 메서드 hasStaticInitializer로 판단한다.

    Serializable Javadoc이 기본 계산은 "컴파일러 구현에 따라 달라질 수 있는 클래스 세부 사항"에 민감하다고 경고하는 것이 이런 경우다. 합성 멤버를 언제 어떤 이름과 수식어로 만들지는 컴파일러가 정하므로, 소스가 같아도 클래스 파일의 멤버 목록이 달라지면 값도 달라진다.

    반대 방향도 확인해 두자. 원래 클래스에 private void writeObject(ObjectOutputStream s)를 추가해 defaultWriteObject() 뒤에 s.writeInt(42)를 더 쓰게 했다. private 메서드이므로 serialver는 여전히 -7907279240408925981L을 출력한다. 그러나 회원 한 명을 직렬화한 스트림은 92바이트에서 99바이트가 되었다. 클래스 설명의 플래그가 02(SC_SERIALIZABLE)에서 03(SC_WRITE_METHOD가 더해짐)으로 바뀌고, 필드 값 뒤에 77 04 00 00 00 2a 78(블록 데이터 4바이트 42와 TC_ENDBLOCKDATA)이 붙었다. 직렬화 형식은 바뀌었는데 기본 UID는 그대로다.

    두 실험을 합치면 기본 UID의 성격이 분명해진다. 기본 UID는 직렬화 형식의 해시가 아니라, 클래스 파일에 드러난 바깥 모양(이름, 수식어, private가 아닌 멤버, 그리고 static도 transient도 아닌 private 필드)의 해시다. 그래서 형식과 무관한 public 메서드 추가나 assert 한 줄에도 바뀌고, 형식을 바꾸는 private writeObject 추가에는 바뀌지 않는다. 호환성 판단의 근거로 삼기에는 너무 예민하면서 동시에 무디다. 명시적 선언이 권장되는 이유가 여기 있다. 덧붙여 명세 4.6절은 열거형과 동적 프록시 클래스의 값은 항상 0L이고, 레코드 클래스의 기본값은 0L이며 레코드는 값 일치 요구도 면제된다고 적는다. 레코드가 정규 생성자로 복원된다는 앞의 사실과 함께, 레코드는 직렬화에서 클래스 구조의 해시에 기대지 않는다.

    객체 그래프: 공유 참조, 순환 참조, 그리고 reset

    앞에서 핸들이 클래스 설명의 중복을 없애는 것을 보았다. 핸들은 일반 객체에도 똑같이 적용된다. 같은 객체를 두 번 담은 리스트와, 서로를 가리키는 두 노드를 직렬화했다가 복원해 보자.

    static class Node implements Serializable {
    String v;
    Node next;
    Node(String v) { this.v = v; }
}

Node m = new Node("A");
List list = new ArrayList<>(List.of(m, m));   // 같은 객체를 두 번
Node x = new Node("X"), y = new Node("Y");
x.next = y;
y.next = x;                                        // 순환
// list와 x를 같은 ObjectOutputStream에 쓰고, 같은 순서로 읽는다
// ...
System.out.println("list.get(0) == list.get(1): " + (r.get(0) == r.get(1)));
System.out.println("rx.next.next == rx: " + (rx.next.next == rx));
    list.get(0) == list.get(1): true
rx.next.next == rx: true

    복원된 리스트의 두 원소는 같은 객체이고, 순환도 그대로다. 쓰는 쪽의 ObjectOutputStream은 이미 쓴 객체를 핸들 테이블에 기억해 두었다가, 같은 객체를 다시 만나면 내용을 쓰지 않고 TC_REFERENCE와 핸들 번호만 쓴다. OpenJDK 21의 내부 클래스 ObjectOutputStream.HandleTable은 객체를 objs[i] == obj로 비교한다. 즉 equals()가 아니라 동일성(identity)으로 판단한다. 내용이 같은 서로 다른 두 객체는 두 번 기록되고, 같은 객체는 한 번만 기록된다. 순환이 무한 반복에 빠지지 않는 것도 이 때문이다. X를 쓰는 도중 Y를 쓰고, Y의 next에서 다시 X를 만나면, X는 이미 핸들을 받았으므로 참조만 쓰고 끝난다.

    이 성질에는 함정이 있다. 같은 스트림을 열어 둔 채 객체를 쓰고, 그 객체를 수정한 뒤 다시 쓰면 어떻게 될까.

    Node n = new Node("v1");
try (ObjectOutputStream o = new ObjectOutputStream(b2)) {
    o.writeObject(n);   // v1 상태로 기록
    n.v = "v2";
    o.writeObject(n);   // 이미 기록된 객체: 참조만 기록
    o.reset();          // 핸들 테이블을 비운다
    o.writeObject(n);   // 새 객체로 다시 기록
}
// 세 번 readObject() 해서 r1, r2, r3를 얻는다
    v1 v1 v2 r1==r2:true r2==r3:false

    두 번째 쓰기는 수정된 상태 v2가 아니라 첫 번째 객체를 가리키는 참조로 기록되었다. 읽는 쪽에서 r2는 r1과 같은 객체이고 값은 v1이다. reset()을 부른 뒤에야 객체가 새로 기록되어 r3이 v2를 갖는다. reset()의 Javadoc은 이 메서드가 이미 쓴 객체들의 상태를 잊고 스트림을 새로 만든 것과 같은 상태로 되돌린다고 설명한다. 명세 6.2절에 따르면 이때 핸들 번호도 0x7E0000부터 다시 시작한다.

    핸들 테이블은 메모리 문제도 만든다. HandleTable은 기록한 객체들을 Object[] objs 배열에 담아 두므로, 스트림이 열려 있는 동안 한 번이라도 쓴 객체는 가비지 컬렉터가 회수할 수 없다. 파일에 리스트 하나를 쓰고 바로 닫는 이번 회차의 저장소에서는 문제가 되지 않지만, 소켓 위에 ObjectOutputStream을 하나 열어 두고 몇 시간 동안 메시지 객체를 계속 보내는 프로그램이라면, 보낸 모든 메시지가 힙에 남는다. 이런 구조에서는 주기적으로 reset()을 불러야 한다. 네트워크 프로그램을 다루는 7~9회에서 소켓 위에 스트림을 얹을 때 떠올릴 만한 사실이다.

    전체를 다시 쓰는 방식의 위험: O_TRUNC와 원자적 교체

    ObjectMemberRepository.add()는 new FileOutputStream(FILE)로 파일을 연다. 이어 쓰기 플래그가 없으므로, 텍스트 예제에서 확인한 대로 운영체제에 O_TRUNC가 전달되어 파일을 여는 순간 길이가 0이 된다. 기존 회원 데이터는 새 데이터를 쓰기 전에 이미 지워진다. 그 뒤에 쓰기가 실패하면 어떻게 될까. 문자열 두 개가 든 리스트를 저장한 68바이트 파일을 만든 뒤, Serializable을 구현하지 않은 클래스의 객체가 든 리스트를 같은 파일에 써 보았다.

    class Plain { String id; Plain(String id) { this.id = id; } }   // Serializable 아님

try (var o = new ObjectOutputStream(new BufferedOutputStream(new FileOutputStream("m.obj")))) {
    o.writeObject(new ArrayList<>(List.of(new Plain("m3"))));
} catch (IOException e) {
    System.out.println(e);
}

java.io.NotSerializableException: Plain
after: 1414

    쓰기는 NotSerializableException으로 실패했고, 파일은 68바이트에서 1,414바이트가 되었으며(이 크기는 함께 기록되는 스택 트레이스에 실행한 클래스의 이름 등이 들어가므로 실험 코드에 따라 달라진다), 다시 읽으면 WriteAbortedException이 난다. 기존의 두 문자열은 어디에도 없다. 1,414바이트의 정체는 덤프에서 보인다. 0x39 위치에 TC_EXCEPTION(0x7B)이 있고 그 뒤에 java.io.NotSerializableException의 클래스 설명, 메시지, 스택 트레이스가 직렬화되어 있다. OpenJDK 21의 ObjectOutputStream.writeObject는 최상위 쓰기에서 IOException이 나면 writeFatalException으로 그 예외 객체를 스트림에 기록한 뒤 예외를 다시 던진다. 명세의 문법 exception: TC_EXCEPTION reset (Throwable)object reset이 이 동작을 정의하고, 읽는 쪽은 이 표시를 만나면 WriteAbortedException을 던진다. 쓰다 만 스트림이 정상 데이터로 오인되지 않게 하는 장치지만, 이미 잘려 나간 옛 데이터를 되살려 주지는 않는다.

    이 실험의 원인은 프로그래밍 실수였지만, 같은 결과는 다른 이유로도 생긴다. 쓰는 도중 디스크가 가득 차거나, 프로세스가 강제 종료되거나, 전원이 나가면 파일에는 잘린 스트림만 남는다. 이어 쓰기 방식의 텍스트나 DataStream 파일은 쓰기 도중에 실패해도 이미 기록된 앞부분의 바이트가 그대로 남지만, 전체를 다시 쓰는 방식은 실패하는 순간 전체를 잃을 수 있다. 회원 한 명을 추가하려다 회원 전체를 잃는 것이다.

    표준적인 해결책은 같은 디렉터리의 임시 파일에 새 내용을 완전히 쓴 뒤, 이름을 바꿔 원래 파일을 교체하는 것이다.

    import java.io.*;
import java.nio.file.*;
import java.util.List;

static void save(List members) throws IOException {
    Path target = Path.of("members.obj");
    Path tmp = Path.of("members.obj.tmp");
    try (FileOutputStream fos = new FileOutputStream(tmp.toFile());
         ObjectOutputStream oos = new ObjectOutputStream(new BufferedOutputStream(fos))) {
        oos.writeObject(members);
        oos.flush();          // 자바 버퍼 → 커널
        fos.getFD().sync();   // 커널 페이지 캐시 → 저장 장치
    }
    Files.move(tmp, target, StandardCopyOption.ATOMIC_MOVE);
}

    이 방식에서는 쓰기가 실패해도 망가지는 것은 임시 파일뿐이고 원래 파일은 그대로다. 마지막 Files.move가 교체를 맡는다. ATOMIC_MOVE 옵션에 대해 Files.move의 Javadoc은 이동이 원자적인 파일 시스템 연산으로 수행된다고 하면서, 대상 파일이 이미 있을 때 교체할지 실패할지는 구현에 따라 다르다고 적는다. OpenJDK 21의 유닉스 계열 구현(sun.nio.fs.UnixFileSystem.move)은 ATOMIC_MOVE일 때 POSIX rename()을 호출하고, 두 경로가 서로 다른 파일 시스템에 있어 EXDEV 오류가 나면 AtomicMoveNotSupportedException을 던진다. POSIX의 rename()은 대상 이름이 이미 있으면 교체하되, 그 이름이 교체 과정 내내 옛 파일이나 새 파일 중 하나를 가리키도록 정한다. 다른 프로세스가 언제 파일을 열든 완전한 옛 파일이나 완전한 새 파일을 보게 된다. 임시 파일을 같은 디렉터리에 두는 이유가 EXDEV를 피하기 위해서다.

    중간의 flush()와 sync()는 2회에서 본 버퍼의 층과 연결된다. flush()는 자바 쪽 버퍼를 커널로 내보낼 뿐이고, 커널은 그 데이터를 페이지 캐시에 두었다가 나중에 저장 장치에 쓴다. FileDescriptor.sync()는 커널 버퍼의 내용이 저장 장치에 기록될 때까지 기다린다. 이 호출 없이 이름을 바꾸면, 전원이 나갔을 때 이름은 새 파일을 가리키는데 내용은 아직 디스크에 없는 상황이 생길 수 있다. 리눅스의 fsync(2) 매뉴얼은 파일에 대한 fsync가 디렉터리 항목까지 디스크에 기록된다는 보장은 아니며, 그러려면 디렉터리에도 fsync가 필요하다고 적고 있다. 파일 하나를 안전하게 갱신하는 일이 이만큼 손이 간다. Files와 Path의 자세한 사용법은 5회에서 다룬다.

    위쪽 타임라인은 파일을 O_TRUNC로 여는 순간 옛 데이터가 사라지고 쓰기 도중 실패하면 빈 파일이나 잘린 파일만 남는 과정을, 아래쪽 타임라인은 임시 파일에 다 쓰고 sync한 뒤 rename으로 교체해 어느 시점에 실패해도 완전한 옛 파일이나 완전한 새 파일만 보이는 과정을 보여 준다.     이 해결책도 동시 접근은 풀지 못한다. 두 프로세스가 동시에 add()를 부르면 둘 다 회원 세 명이 든 파일을 읽고, 각자 한 명을 더해 네 명짜리 리스트를 만들고, 각자 파일을 교체한다. 나중에 교체한 쪽이 이기고 먼저 추가한 회원은 사라진다. 읽고, 고치고, 다시 쓰는(read-modify-write) 과정 전체를 하나로 묶는 장치가 없기 때문이다. 자바 고급 1편에서 본 스레드 사이의 경쟁 조건(race condition)이 프로세스 사이에서 파일을 두고 똑같이 일어난다.

    역직렬화는 신뢰할 수 없는 입력에 쓰지 않는다

    자바 직렬화에는 형식의 불편함보다 더 근본적인 문제가 있다. ObjectInputStream의 클래스 Javadoc 첫머리에는 굵은 글씨의 경고가 있다. "Deserialization of untrusted data is inherently dangerous and should be avoided." 신뢰할 수 없는 데이터의 역직렬화는 본질적으로 위험하며 피해야 한다는 뜻이다.

    왜 본질적으로 위험한지는 이번 회차에서 본 사실들을 이어 붙이면 나온다. 첫째, 어떤 클래스의 객체를 만들지는 읽는 코드가 아니라 스트림이 정한다. 스트림의 클래스 설명에 적힌 이름이 클래스패스에 있는 Serializable 클래스이기만 하면 그 객체가 만들어진다. (List) 형변환은 객체가 모두 만들어진 뒤에야 실행되므로 막는 역할을 하지 못한다. 둘째, 객체를 만드는 과정에서 그 클래스의 코드가 실행된다. ArrayList가 자기만의 writeObject를 가졌던 것처럼 많은 클래스가 readObject 같은 역직렬화 메서드를 정의하고, 런타임은 스트림을 읽으며 그 메서드들을 호출한다. 셋째, 필드 값도 스트림이 정한다. 생성자의 검사는 실행되지 않는다. 결국 스트림을 만든 사람이 "어떤 클래스들의 객체를, 어떤 필드 값으로, 어떤 순서로 엮어 만들지"를 고를 수 있고, 클래스패스에 있는 라이브러리 클래스들의 역직렬화 코드를 연쇄적으로 실행시키는 조합이 찾아지면 원격 코드 실행까지 이어질 수 있다. 이런 클래스 조합을 흔히 가젯 체인(gadget chain)이라고 부른다.

    코드 실행이 아니더라도 자원 고갈이 가능하다. ArrayList.readObject는 스트림에서 원소 수를 읽어 그 크기의 배열을 만든다. 공격자가 원소 수를 아주 크게 적으면 거대한 배열 할당을 유도할 수 있고, 아주 깊게 중첩된 객체 그래프는 재귀 호출로 스택을 소진시킬 수 있다.

    이를 완화하기 위해 Java 9에 java.io.ObjectInputFilter가 추가되었고(JEP 290), Java 17에서는 역직렬화 상황마다 다른 필터를 적용할 수 있는 필터 팩토리가 추가되었다(JEP 415). 필터는 역직렬화 도중 클래스, 배열 길이, 참조 수, 그래프 깊이를 검사해 허용 여부를 정한다. 회원 리스트만 허용하는 필터를 걸고, 어떤 검사가 일어나는지 기록하도록 감싸 보았다.

    ObjectInputFilter f = ObjectInputFilter.Config.createFilter(
        "MemberC;java.util.ArrayList;java.lang.Object;!*");
ObjectInputFilter log = info -> {
    System.out.println("  check: " + info.serialClass() + " len=" + info.arrayLength());
    return f.checkInput(info);
};
// 회원 리스트 스트림과 HashMap 스트림을 각각 읽는다
ois.setObjectInputFilter(log);
System.out.println(ois.readObject());

    패턴 MemberC;java.util.ArrayList;java.lang.Object;!*는 앞의 세 이름을 허용하고 나머지(!*)를 거부한다. 허용 목록(allow-list) 방식이다. 기록을 보면 필터가 클래스 설명을 만날 때마다 호출되는 것 외에, ArrayList.readObject가 내부 배열을 만들기 전에 Object[]와 그 길이로 한 번 더 호출된다. OpenJDK 21의 ArrayList.readObject가 배열을 할당하기 전에 checkArray(s, Object[].class, size)로 필터에 묻기 때문이다. 그리고 Config.createFilter의 Javadoc에 따르면 배열은 배열 타입이 아니라 원소 타입으로 패턴과 비교되므로, java.lang.Object를 허용 목록에 넣지 않으면 정상적인 회원 리스트도 거부된다. 처음에 이 항목 없이 실험했을 때는 회원 리스트까지 REJECTED로 막혔다. 문자열은 필터 호출 기록에 나타나지 않았다. 허용 목록에 없는 HashMap은 객체가 만들어지기 전에 거부되었다.

    필터는 JVM 전체에 -Djdk.serialFilter=... 시스템 속성으로 걸 수도 있다. 그러나 필터는 피해를 줄이는 장치이고, 신뢰할 수 없는 입력을 역직렬화해도 된다는 허가가 아니다. 외부에서 들어온 데이터라면 자바 직렬화 대신 읽는 쪽이 만들 타입을 정하는 형식을 쓰는 것이 우선이다. 그런 형식이 다음 절의 주제다.

    XML, JSON, 데이터베이스

    지금까지의 세 파일 형식을 처음의 세 가지 결정으로 다시 보자. 텍스트 형식은 사람이 읽을 수 있지만 경계가 모호하고 형식 정보가 코드에만 있었다. DataStream은 경계가 분명하지만 형식 정보가 코드에만 있어 순서가 어긋나면 조용히 틀렸다. 자바 직렬화는 형식 정보를 데이터에 담았지만, 그 정보가 자바 클래스 이름과 필드 구조여서 자바가 아닌 프로그램은 읽을 수 없고, 클래스 구조와 강하게 결합되며, 읽는 쪽이 아니라 데이터가 만들 클래스를 정한다. XML과 JSON은 이 결정들을 다르게 내린다.

    [
  {"id": "m1", "name": "김자바", "age": 20},
  {"id": "m4", "name": "남궁,민수", "age": 28}
]

    두 형식 모두 값을 텍스트로 쓴다. 숫자 20은 문자 '2', '0'이다. 경계는 문법으로 표시한다. JSON의 문자열은 큰따옴표로 감싸고 안의 큰따옴표와 역슬래시는 역슬래시로 이스케이프하므로, 이름에 들어간 쉼표는 따옴표 안에 있는 한 데이터일 뿐이다. XML은 태그가 경계이고, 데이터 안의 &와 <는 &, < 같은 엔티티로 바꿔 쓴다. 우리가 텍스트 형식에서 직접 만들어야 했던 이스케이프 규칙과 상태 기계를 표준 문법과 검증된 파서가 대신하는 셈이다.

    가장 큰 차이는 형식 정보다. 두 형식은 필드 이름을 데이터 안에 쓴다. "age": 20은 그 자체로 "이 값은 나이"라고 말한다. 그래서 필드 순서가 바뀌어도, 읽는 쪽이 모르는 필드가 추가되어도 처리할 수 있다. 반면 자바 클래스 이름은 쓰지 않는다. 이 데이터를 어떤 객체로 만들지는 읽는 프로그램이 정한다. 자바에서는 Member로, 자바스크립트에서는 평범한 객체로, 파이썬에서는 딕셔너리로 읽는다. 언어 중립성과 안전성이 같은 결정에서 나온다. 대가는 크기와 속도다. 필드 이름이 레코드마다 반복되고, 숫자를 문자열로 바꾸고 되돌리는 변환이 매번 일어난다.

    JSON을 정의하는 RFC 8259에는 1회와 이번 회차의 내용이 그대로 이어지는 규정이 있다. 닫힌 생태계 바깥의 시스템 사이에서 교환하는 JSON 텍스트는 UTF-8로 인코딩해야 한다(MUST). 객체 안의 이름은 고유해야 한다(SHOULD). 숫자에 대해서는 IEEE 754 배정밀도(binary64) 구현이 널리 쓰이므로, -(2**53)+1부터 (2**53)-1 사이의 정수가 구현 사이에서 정확히 일치한다고 적는다. 자바의 long은 이 범위보다 넓으므로, 큰 long 식별자를 JSON 숫자로 내보내면 받는 쪽 구현에 따라 정확한 값을 잃을 수 있다. 텍스트 형식이라고 해서 값의 해석이 자동으로 같아지는 것은 아니다.

    자바 표준 라이브러리에는 JSON을 다루는 API가 없다. 그래서 Jackson 같은 라이브러리를 쓰고, 스프링 MVC에서 @RequestBody와 @ResponseBody로 객체와 JSON을 오가던 것이 바로 이 변환이다. 스프링 부트 3.x 레퍼런스는 Jackson을 우선적인 기본 JSON 라이브러리로 명시한다. XML은 JDK에 DOM, SAX, StAX 파서가 들어 있다(javax.xml 패키지). 객체와 XML을 자동으로 오가는 JAXB(java.xml.bind 모듈)는 Java SE 9에서 제거 예정으로 지정된 뒤, Java 11에서 JEP 320에 따라 다른 Java EE 모듈들과 함께 JDK에서 제거되었다. 지금은 별도 라이브러리로 추가해 쓴다. XML은 스키마로 구조를 검증하고 네임스페이스로 이름 충돌을 피하는 기능을 갖추고 있어, 그런 기능이 필요한 설정 파일이나 문서 형식에서 쓰인다.

    파일로는 부족해지는 지점: 데이터베이스

    형식을 아무리 잘 골라도 "파일 하나에 모든 회원"이라는 구조 자체의 한계가 남는다. 회원 관리 프로그램이 커지면 곧 부딪히는 네 가지를 보자.

    • 부분 수정. 회원 한 명의 나이를 바꾸려면, 텍스트 파일에서는 그 줄의 길이가 바뀔 수 있으므로 뒤의 모든 바이트를 밀거나 당겨야 하고, 객체 파일에서는 전체를 다시 써야 한다. 데이터베이스는 데이터를 고정 크기의 페이지 단위로 관리해 바뀐 페이지만 고친다.
    • 검색. 아이디로 회원 한 명을 찾으려면 지금의 모든 구현은 파일 전체를 읽는다. 회원 수에 비례하는 비용이다. 데이터베이스는 B+Tree 인덱스로 필요한 페이지만 따라가 찾는다.
    • 동시 접근. 앞에서 본 것처럼 두 프로세스가 동시에 고치면 한쪽의 변경이 사라진다. 데이터베이스는 락과 MVCC로 동시에 실행되는 트랜잭션을 조정한다.
    • 장애 시 원자성과 지속성. 임시 파일과 rename으로 파일 단위의 원자성을 얻었지만, 회원 한 명을 추가할 때마다 전체를 다시 쓰는 비용을 치렀다. MySQL InnoDB 같은 저장 엔진은 변경 내용을 먼저 로그(redo log)에 순서대로 기록해, 데이터 전체를 다시 쓰지 않고도 커밋된 변경이 장애 후에 복구되게 한다.

    데이터베이스 기본편과 JPA 강의에서 본 내용이 바로 이 네 문제의 답이다. 데이터베이스를 쓰면 직렬화 문제도 모양을 바꾼다. 테이블의 행은 데이터베이스가 정한 형식으로 저장되고, 애플리케이션은 JDBC로 행의 열 값을 하나씩 읽어 객체를 만든다. DataInputStream에서 필드를 하나씩 읽어 생성자에 넘기던 일과 구조가 같다. 이 반복 작업을 대신해 주는 것이 JPA 같은 객체-관계 매핑이다.

    이 장의 핵심

    객체를 저장한다는 것은 참조를 버리고 값, 경계, 형식 정보를 바이트로 표현하는 일이다. 형식 정보를 코드에만 두면 작고 빠르지만 순서가 어긋날 때 조용히 틀리고, 자바 클래스 이름으로 데이터에 넣으면 편하지만 클래스 구조에 묶이고 데이터가 생성할 클래스를 고르게 된다. 필드 이름으로 넣는 JSON·XML은 언어와 클래스에서 독립된다. 그리고 부분 수정, 검색, 동시 접근, 장애 복구가 필요해지는 순간 형식의 문제는 저장 엔진의 문제가 된다.

    이 회차의 사실들은 뒤에서 계속 다시 나온다. 5회는 이번에 잠깐 쓴 Files.move와 Path를 본격적으로 다룬다. 6~9회의 소켓 프로그램은 DataInputStream과 DataOutputStream을 소켓 스트림 위에 얹어 메시지를 주고받는데, 그때 빅 엔디언과 길이 접두가 프로토콜의 경계가 된다. 10회와 13회의 HTTP 서버는 두 가지 경계 표시 방식을 함께 쓰는 프로토콜을 다룬다. HTTP/1.1 메시지의 시작 줄과 헤더는 CRLF로 구분된 텍스트이고, 본문의 길이는 흔히 Content-Length 헤더가 알려 준다. 구분자와 길이 정보가 한 메시지 안에 함께 있는 것이다. 11회의 리플렉션은 이번에 본 직렬화가 클래스의 필드 목록을 알아내던 방식, 즉 실행 중에 클래스의 구조를 들여다보는 기능을 정식으로 다룬다.
    영속성(persistence)
    프로그램이 끝난 뒤에도 데이터가 남는 성질이다. 힙의 객체는 프로세스의 주소 공간과 함께 사라지므로, 영속성을 얻으려면 데이터를 파일이나 데이터베이스로 옮겨야 한다.
    직렬화의 세 가지 결정
    참조는 파일로 옮길 수 없으므로, 값을 어떤 바이트로 쓸지, 값 사이의 경계를 어떻게 표시할지, 형식 정보를 어디에 둘지를 정해야 한다. 네 구현의 장단점은 모두 이 결정에서 나온다.
    구분자와 길이 접두
    구분자는 사람이 읽기 쉽지만 데이터 속 같은 문자 때문에 깨질 수 있어 이스케이프 규칙이 필요하다. 길이 접두는 데이터의 내용과 경계를 분리하지만 길이 필드의 크기가 최대 길이를 정한다(writeUTF는 65,535바이트).
    DataStream의 바이트 형식
    정수는 CPU와 무관하게 빅 엔디언으로, 문자열은 2바이트 길이와 수정된 UTF-8로 쓴다. 형식 정보가 없으므로 읽기 순서가 어긋나면 예외 없이 틀린 값이 나올 수 있다.
    자바 직렬화 스트림
    ac ed 00 05 헤더 뒤에 타입 코드, 클래스 설명(이름, serialVersionUID, 필드), 필드 값이 이어진다. 한 번 쓴 객체와 클래스 설명은 핸들 번호로 다시 가리키므로 공유 참조와 순환 참조가 보존된다.
    생성자를 건너뛰는 역직렬화
    직렬화 가능한 클래스의 생성자와 필드 초기화식은 실행되지 않고, 첫 번째 직렬화 불가능한 상위 클래스의 인자 없는 생성자만 실행된다. 필드 값은 스트림에서 직접 채워지므로 생성자의 검사가 우회된다. 레코드는 예외로, 정규 생성자가 호출된다.
    serialVersionUID
    스트림의 클래스와 현재 클래스의 호환성을 확인하는 번호다. 선언하지 않으면 클래스 구조의 해시로 계산되어 작은 변경에도 바뀌므로 명시적 선언이 권장된다. 선언해도 필드 타입 변경 같은 비호환 변화는 막지 못한다.
    기본 serialVersionUID의 입력
    명세 4.6절의 순서대로 클래스 이름, 수식어, 인터페이스, 필드(private static·private transient 제외), 클래스 초기화 메서드 유무, private가 아닌 생성자와 메서드를 DataOutputStream으로 쓴 바이트의 SHA-1 앞 8바이트다. assert 한 줄이 만드는 합성 필드도 값을 바꾸고, private writeObject 추가처럼 형식을 바꾸는 변화는 값을 바꾸지 않는다.

    덮어쓰기와 원자적 교체
    FileOutputStream의 덮어쓰기는 O_TRUNC로 여는 순간 옛 데이터를 지운다. 같은 디렉터리의 임시 파일에 다 쓰고 sync한 뒤 ATOMIC_MOVE(유닉스에서는 rename)로 교체하면 완전한 옛 파일이나 완전한 새 파일만 남는다.
    JSON·XML·데이터베이스
    JSON과 XML은 필드 이름을 데이터에 담아 언어 중립적이고, 만들 타입은 읽는 쪽이 정한다. 부분 수정, 검색, 동시 접근, 장애 복구가 필요하면 파일 대신 데이터베이스를 쓴다.

    자바 직렬화를 실무에서 다시 판단할 때 기준은 "이 바이트를 누가 만들었고, 얼마나 오래 사는가"다. 같은 JVM 버전, 같은 클래스로 잠깐 쓰고 바로 읽는 데이터라면 자바 직렬화의 편리함이 비용보다 클 수 있다. 그러나 파일로 오래 보관하는 데이터는 클래스 이름, 패키지, 필드 구조를 함께 동결시키고, 리팩터링 한 번으로 옛 데이터를 읽을 수 없게 만들 수 있다. 캐시나 세션 저장소에 객체를 자바 직렬화로 넣어 두었다가, 배포 후 클래스가 바뀌어 InvalidClassException이 나는 일이 이 결합에서 생긴다. 이런 저장소에는 JSON처럼 필드 이름 기반의 형식을 쓰는 편이 클래스 변경에 덜 민감하다.

    외부에서 들어오는 바이트를 ObjectInputStream으로 읽는 코드는 그 자체로 점검 대상이다. 신뢰할 수 없는 입력이라면 형식을 바꾸는 것이 우선이고, 당장 바꿀 수 없다면 허용 목록 방식의 ObjectInputFilter를 걸고 배열 길이와 깊이에 한도를 둔다. 필터를 설정할 때는 이번 실험처럼 실제로 어떤 클래스와 배열이 검사되는지 기록해 보는 것이 좋다. ArrayList의 Object[]처럼 예상하지 못한 검사가 있어 정상 데이터가 막히거나, 반대로 너무 넓게 열게 되는 경우가 있기 때문이다.

    파일 하나를 통째로 다시 쓰는 코드를 보면, 쓰기 도중 실패했을 때 무엇이 남는지를 먼저 묻는다. 설정 파일 저장, 내보내기 결과 저장처럼 흔한 작업에서도 덮어쓰기는 실패 시 전체 손실로 이어질 수 있다. 같은 디렉터리의 임시 파일, sync, 원자적 이름 변경은 짧은 코드로 이 위험을 없앤다. 그러나 여러 프로세스가 같은 데이터를 고치기 시작하거나, 일부만 고치고 찾는 일이 잦아지면, 파일 형식을 다듬는 것으로는 부족하다. 그 시점이 데이터베이스로 옮길 때다.

    3번. a=10, b=0, c=y, d=null이다. 컴파일러는 필드 초기화식(a = 1, b = 2, c = "x", d = "keep")을 생성자 메서드 안에, 상위 클래스 생성자 호출 바로 뒤에 넣는다. 직렬화 시점의 객체는 초기화식과 생성자 본문을 모두 거쳐 a=10, b=20, c="y", d="keep"이었다. 직렬화는 transient가 아닌 a와 c만 기록한다. 역직렬화는 P의 을 실행하지 않고 첫 번째 직렬화 불가능한 상위 클래스인 Object의 생성자만 실행하므로 초기화식도 실행되지 않는다. 그 결과 a와 c는 스트림의 값 10과 "y"로 채워지고, 스트림에 없는 b와 d는 할당 직후의 기본값 0과 null로 남는다.

ObjectOutputStream은 한 번 쓴 객체를 핸들 테이블에 기억하고, 같은 객체(동일성 기준)를 다시 쓰면 내용 대신 TC_REFERENCE와 핸들 번호만 보낸다. 받는 쪽은 그 번호로 처음 받은 객체를 다시 돌려주므로 값이 갱신되지 않는다. 해결책은 매번 쓰기 전에 reset()을 호출하거나, 매번 새 객체(예를 들어 상태의 불변 스냅숏)를 만들어 보내는 것이다. 다만 새 객체를 계속 만들어 보내면서 reset()을 부르지 않으면, 핸들 테이블이 보낸 모든 객체를 참조하고 있어 가비지 컬렉터가 회수하지 못하고 힙 사용량이 계속 늘어난다. 받는 쪽의 ObjectInputStream도 핸들로 다시 참조될 수 있는 객체들을 보관하므로 같은 문제가 생긴다. 주기적인 reset()이 두 문제를 함께 해결한다.

     회원 한 명을 ObjectOutputStream으로 쓴 파일에, 이어 쓰기 모드로 새 ObjectOutputStream을 열어 회원 한 명을 더 썼다. 하나의 ObjectInputStream으로 두 번 읽으면 두 번째 읽기에서 StreamCorruptedException: invalid type code: AC가 난다. 가장 정확한 원인은? 이어 쓰기 모드에서는 운영체제가 파일 앞부분을 덮어쓰기 때문이다. 두 번째 스트림의 생성자가 쓴 헤더 ac ed 00 05가 파일 중간에 들어가, 읽는 쪽이 그 첫 바이트를 객체의 타입 코드로 해석하기 때문이다. 두 회원 객체의 serialVersionUID가 서로 달라지기 때문이다. 같은 클래스의 클래스 설명이 두 번 나오는 것은 명세상 금지되어 있기 때문이다. ObjectInputStream은 생성 시점에 헤더를 한 번만 읽고, 이후에는 각 객체의 첫 바이트를 TC_OBJECT(0x73) 같은 타입 코드로 읽는다. 중간에 끼어든 두 번째 헤더의 0xAC는 정의된 타입 코드가 아니다. O_APPEND는 파일 끝에 쓰므로 앞부분을 덮어쓰지 않고, 같은 클래스이므로 UID도 같다. Object를 직접 상속하고 Serializable을 구현한 클래스 Member의 객체를 역직렬화할 때 실행되는 생성자는? Member의 인자 없는 생성자. 없으면 InvalidClassException이 난다. 스트림에 기록된 필드 값을 인자로 받는 Member의 생성자 Object()뿐이다. Member의 생성자와 필드 초기화식은 실행되지 않는다. 생성자는 하나도 실행되지 않고 필드 초기화식만 실행된다. Serializable의 Javadoc대로, 가장 아래에 있는 직렬화 불가능한 상위 클래스(여기서는 Object)의 인자 없는 생성자만 실행된다. 필드 초기화식은 바이트코드상 Member의 생성자 메서드 안에 들어 있으므로 함께 건너뛴다. 정규 생성자에 값을 넘겨 호출하는 방식은 레코드에만 적용된다. 같은 회원 세 명을 텍스트(쉼표와 줄바꿈)로 저장하면 51바이트, DataOutputStream(writeUTF, writeInt)으로 저장하면 60바이트였다. 바이너리 쪽이 더 큰 이유로 가장 알맞은 것은? 문자열마다 2바이트 길이 접두가 붙고, 두 자리 나이도 항상 4바이트 정수로 쓰이기 때문이다. DataOutputStream은 한글을 UTF-16으로 저장해 글자당 바이트가 늘기 때문이다. DataOutputStream이 파일 앞에 형식을 나타내는 헤더를 쓰기 때문이다. 빅 엔디언 정수는 리틀 엔디언보다 바이트를 더 차지하기 때문이다. 덤프에서 한글은 두 파일 모두 글자당 3바이트로 같다(writeUTF는 수정된 UTF-8). DataOutputStream은 헤더를 쓰지 않고, 엔디언은 바이트 순서일 뿐 크기와 무관하다. 텍스트의 "m1,"(3바이트)가 길이 접두를 포함해 4바이트가 되고, "20\n"(3바이트)이 4바이트 정수가 되는 식으로 작은 값마다 조금씩 커졌다. 외부 시스템에서 받은 데이터를 객체로 만들 때, 자바 직렬화보다 JSON이 안전하다고 말할 수 있는 가장 근본적인 이유는? JSON은 텍스트라서 바이너리보다 변조하기 어렵기 때문이다. JSON 파서는 생성자를 호출하지 않기 때문이다. JSON은 반드시 UTF-8로 인코딩되기 때문이다. JSON 데이터에는 자바 클래스 이름이 없어서, 어떤 타입의 객체를 만들지를 데이터가 아니라 읽는 코드가 정하기 때문이다. 자바 직렬화의 위험은 스트림이 생성할 클래스와 필드 값을 고르고, 그 과정에서 클래스들의 역직렬화 코드가 실행된다는 데 있다. JSON은 필드 이름과 값만 담으므로 생성할 타입은 읽는 쪽이 정한다. 텍스트라고 변조가 어려운 것은 아니고, UTF-8 규정은 인코딩 문제일 뿐 보안과 무관하다. 한 ObjectOutputStream에 가변 객체 n을 쓰고, n의 필드를 바꾼 뒤 reset() 없이 다시 썼다. 받는 쪽이 readObject()를 두 번 호출했을 때의 결과는? 서로 다른 두 객체가 나오고, 두 번째 객체는 바뀐 값을 가진다. 두 번 모두 같은 객체가 나오고, 그 객체는 처음 쓸 때의 값을 가진다. 두 번 모두 같은 객체가 나오고, 그 객체는 바뀐 값을 가진다. 같은 객체를 두 번 쓰는 것은 금지되어 있어 쓰는 쪽에서 예외가 난다. 쓰는 쪽은 이미 쓴 객체를 동일성(==)으로 기억했다가 두 번째에는 TC_REFERENCE와 핸들 번호만 보낸다. 받는 쪽은 그 핸들로 처음 복원한 객체를 그대로 돌려준다. 본문 실험에서도 r1==r2가 true였고 값은 v1이었다. reset()을 부른 뒤에야 객체가 새로 기록된다.
    직렬화(serialization)
    메모리의 객체나 값을 저장하거나 전송할 수 있는 바이트 나열로 바꾸는 일이다. 반대 방향은 역직렬화(deserialization)다. 좁은 뜻으로는 ObjectOutputStream이 하는 자바 직렬화를 가리킨다.
    표시 인터페이스(marker interface)
    메서드 없이 타입으로 어떤 성질만 표시하는 인터페이스다. Serializable은 이 클래스의 객체를 직렬화해도 된다는 표시다.
    빅 엔디언(big-endian)
    여러 바이트로 된 수를 가장 높은 자리 바이트부터 쓰는 순서다. DataOutputStream과 네트워크 프로토콜의 표준 바이트 순서다.
    길이 접두(length prefix)
    값 앞에 그 값의 바이트 수를 먼저 적어 경계를 표시하는 방식이다. 데이터 안에 어떤 바이트가 있어도 경계가 흐트러지지 않는다.
    수정된 UTF-8(modified UTF-8)
    DataOutput.writeUTF, 클래스 파일 상수 풀, 자바 직렬화 스트림이 쓰는 인코딩이다. 널 문자를 2바이트로, 보충 문자를 서로게이트 쌍의 3바이트씩 두 개로 인코딩한다는 점에서 표준 UTF-8과 다르다.
    핸들(handle)
    자바 직렬화 스트림에서 객체, 클래스 설명, 문자열에 0x7E0000부터 차례로 매기는 번호다. 같은 대상이 다시 나오면 TC_REFERENCE와 이 번호로 가리킨다.
    serialVersionUID
    직렬화 가능한 클래스의 버전 번호다. 스트림의 값과 현재 클래스의 값이 다르면 역직렬화가 InvalidClassException으로 실패한다.
    transient
    기본 직렬화에서 필드를 제외하는 수식어다. 역직렬화 후 그 필드는 타입의 기본값을 가진다.
    원자적 이름 변경(atomic rename)
    대상 이름이 교체 과정 내내 옛 파일이나 새 파일 중 하나만 가리키도록 이름을 바꾸는 파일 시스템 연산이다. 임시 파일에 쓴 뒤 교체하는 안전한 갱신의 기반이다.
    바이트코드 검증기(bytecode verifier)
    클래스를 링크할 때 메서드의 바이트코드가 JVMS 4.10절의 타입 규칙을 지키는지 검사하는 JVM의 구성 요소다. 예를 들어 new로 만든 객체에는 그 클래스 자신의 만 호출할 수 있다.
    합성 멤버(synthetic member)
    소스에 없지만 컴파일러가 만들어 넣은 필드나 메서드로, 클래스 파일에 ACC_SYNTHETIC 플래그가 붙는다. assert가 만드는 $assertionsDisabled가 예다.
    역직렬화 필터(ObjectInputFilter)
    역직렬화 도중 클래스, 배열 길이, 참조 수, 깊이를 검사해 허용 여부를 정하는 장치다. Java 9에 추가되었다.
