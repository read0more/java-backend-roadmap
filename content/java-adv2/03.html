    이 회차의 질문: 스트림은 문자를 모른다

    앞 회차에서 바이트 스트림을 다뤘다. InputStream.read()는 0부터 255 사이의 값 하나 또는 끝을 뜻하는 -1을 돌려주고, OutputStream.write(int)는 인자의 하위 8비트만 내보낸다. 파일이든 소켓이든 운영체제가 주고받는 단위는 바이트이고, 자바의 바이트 스트림은 그 사실을 그대로 드러낸 API다. 그리고 첫 회차에서 본 것처럼 문자를 바이트로 바꾸는 규칙, 곧 문자 집합(character set)과 인코딩(encoding)은 하나가 아니다. 같은 "가"가 UTF-8에서는 3바이트, MS949에서는 2바이트가 된다.

    그런데 우리가 실제로 다루는 데이터는 대부분 문자다. 설정 파일, 로그, CSV, HTTP 헤더, 채팅 메시지가 모두 그렇다. 자바 프로그램 안에서 문자는 String과 char로 존재하고, 바깥 세계에서는 바이트로 존재한다. 그렇다면 어딘가에서 반드시 변환이 일어나야 한다. 이번 회차가 묻는 것은 세 가지다. 그 변환은 정확히 어디에서 일어나는가. 변환하는 쪽은 무엇을 기억하고 있어야 하는가. 그리고 변환과 버퍼링이 여러 겹으로 쌓일 때 각 겹은 무슨 비용을 줄이는가.

    순서는 이렇다. 먼저 바이트 스트림만으로 문자를 다뤄 보고, 그 방식이 버퍼 경계에서 깨지는 장면을 직접 만든다. 그 원인을 풀어 주는 상태 있는 변환기(CharsetDecoder)를 본 다음, 그 변환기를 감싼 다리 클래스 InputStreamReader·OutputStreamWriter의 내부로 내려간다. 그 위에 Reader·Writer 계층과 BufferedReader를 세우고, 마지막으로 문자와 바이트 사이 어딘가에 서 있는 기타 스트림(PrintStream, DataOutputStream, 메모리 스트림)을 정리한다.

    이 회차의 모든 실행 결과는 Apple M1(macOS) 위의 Temurin OpenJDK 21.0.13에서 직접 돌린 것이다. 내부 구현을 설명할 때는 같은 JDK의 소스(lib/src.zip)를 읽고 "OpenJDK 21 소스에서는"이라고 범위를 밝힌다. API 문서(Javadoc)가 보장하는 것과 지금 구현이 그렇게 되어 있는 것은 구분해서 읽어야 한다.

    문자 다루기의 출발점: 직접 바꾸기

    바이트 스트림만 가지고 문자열을 파일에 쓰려면, 쓰기 전에 문자열을 바이트 배열로 바꾸고 읽은 뒤에 바이트 배열을 문자열로 되돌리면 된다. String.getBytes(Charset)가 인코딩, new String(byte[], Charset)이 디코딩이다. 가장 단순한 형태부터 보자.

    import java.io.FileInputStream;
import java.io.FileOutputStream;
import java.io.IOException;
import java.nio.charset.StandardCharsets;
import java.util.Arrays;

public class ByteToStringMain {
    public static void main(String[] args) throws IOException {
        String text = "가나다ABC";

        // 문자 → 바이트 (인코딩)
        byte[] encoded = text.getBytes(StandardCharsets.UTF_8);
        System.out.println("문자 수=" + text.length() + ", 바이트 수=" + encoded.length);
        System.out.println("바이트=" + Arrays.toString(encoded));

        try (FileOutputStream fos = new FileOutputStream("hello.txt")) {
            fos.write(encoded);
        }

        // 바이트 → 문자 (디코딩)
        byte[] read;
        try (FileInputStream fis = new FileInputStream("hello.txt")) {
            read = fis.readAllBytes();
        }
        String decoded = new String(read, StandardCharsets.UTF_8);
        System.out.println("복원=" + decoded + ", 같은가=" + text.equals(decoded));
    }
}
    문자 수=6, 바이트 수=12
바이트=[-22, -80, -128, -21, -126, -104, -21, -117, -92, 65, 66, 67]
복원=가나다ABC, 같은가=true

    여섯 글자가 12바이트가 됐다. 한글 세 글자가 각각 3바이트, 영문 세 글자가 각각 1바이트다. 출력된 숫자 중 음수가 많은 것은 자바의 byte가 부호 있는 8비트(-128~127)이기 때문이다. 첫 바이트 -22를 부호 없이 읽으면 256 - 22 = 234, 16진수로 0xEA다. 바이트 열을 16진수로 다시 쓰면 EA B0 80 | EB 82 98 | EB 8B A4 | 41 42 43이 된다. 파일 hello.txt에는 정확히 이 12바이트가 들어 있고, 그 안 어디에도 "이것은 UTF-8이다"라는 표시는 없다.

    메모리 쪽에서 무슨 일이 일어났는지도 짚어 두자. JDK 9부터 String 객체는 내부에 char[]가 아니라 byte[]와 인코딩 플래그 하나를 가진다(JEP 254, Compact Strings). 내용이 Latin-1 범위 안이면 한 글자를 1바이트로, 아니면 UTF-16으로 한 글자를 2바이트로 저장한다. "가나다ABC"는 한글이 섞였으니 UTF-16 형식으로 12바이트를 쓴다. 이것은 JVM 내부의 표현일 뿐 파일에 쓰이는 형식과는 상관이 없다. getBytes(UTF_8)는 이 내부 표현을 읽어 UTF-8 규칙으로 새 byte[]를 만들어 돌려주고, new String(bytes, UTF_8)은 반대로 바이트를 해석해 새 String 객체를 힙에 만든다. 즉 변환은 매번 새 배열을 할당하는 복사다.

    디코딩할 때 문자 집합을 잘못 고르면 어떻게 될까. 같은 12바이트를 new String(bytes, Charset.forName("MS949"))로 읽으면 이 기계에서 媛��굹�떎ABC가 나왔다. MS949는 0xEA 0xB0을 한 글자("媛")로 읽고, 짝이 맞지 않는 곳에는 대체 문자를 넣는다. ISO-8859-1로 읽으면 결과는 오류 없이 정확히 12글자가 된다. ISO-8859-1은 0~255의 모든 바이트 값을 U+0000~U+00FF의 한 문자에 그대로 대응시키므로 어떤 바이트 열이든 실패하지 않는다. 두 경우 모두 예외는 나지 않는다. 바이트 열에는 문자 집합 정보가 없으므로, 디코더는 자기가 틀린 규칙으로 읽고 있다는 사실을 알 길이 없다. 문자 집합은 데이터 바깥에서, 쓰는 쪽과 읽는 쪽이 미리 맞춘 약속이다.

    new String 한 번 안에서: 입력에 따라 갈리는 세 갈래와 HotSpot 인트린식

    앞에서 변환은 매번 새 배열을 할당하는 복사라고 했다. OpenJDK 21 소스로 한 층 내려가면 그 복사가 바이트 내용에 따라 서로 다른 길을 탄다는 것이 보인다. new String(bytes, UTF_8)은 String의 private 생성자 하나로 모이고, 이 생성자는 넘어온 문자 집합이 sun.nio.cs.UTF_8.INSTANCE와 같은 객체인지부터 비교한다. 같으면 CharsetDecoder를 만들지 않고 String 클래스 안에 직접 짜 넣은 UTF-8 해독 코드로 들어간다. ISO-8859-1과 US-ASCII에도 이런 전용 분기가 있고, 그 밖의 문자 집합만 일반 디코더를 거친다. Compact Strings가 켜진 기본 상태에서 UTF-8 분기는 다음 순서로 내려간다.

    세 갈래가 실제로 어떤 객체를 남기는지 확인해 보자. String의 private 필드 value와 coder를 리플렉션으로 읽는다. JDK 내부 필드이므로 실행할 때 --add-opens java.base/java.lang=ALL-UNNAMED를 줘야 열린다.

    import java.lang.reflect.Field;
import java.nio.charset.StandardCharsets;

public class CoderMain {
    public static void main(String[] args) throws Exception {
        Field value = String.class.getDeclaredField("value");
        Field coder = String.class.getDeclaredField("coder");
        value.setAccessible(true);
        coder.setAccessible(true);

        String[] samples = {"ABC", "café", "가나다ABC"};
        for (String sample : samples) {
            byte[] in = sample.getBytes(StandardCharsets.UTF_8);
            String s = new String(in, StandardCharsets.UTF_8);
            byte[] v = (byte[]) value.get(s);
            System.out.println("입력 " + in.length + "바이트 → coder=" + coder.get(s)
                    + ", 내부 배열 " + v.length + "바이트 : " + s);
        }
    }
}
    입력 3바이트 → coder=0, 내부 배열 3바이트 : ABC
입력 5바이트 → coder=0, 내부 배열 4바이트 : café
입력 12바이트 → coder=1, 내부 배열 12바이트 : 가나다ABC

    coder 0은 LATIN1, 1은 UTF16이다. "ABC"는 1단계에서 끝났다. "café"의 é는 UTF-8로 C3 A9 두 바이트이므로 1단계를 통과하지 못하지만, 2단계에서 1바이트(0xE9)로 접혀 5바이트 입력이 4바이트 LATIN1 배열이 됐다. "가나다ABC"는 3단계까지 내려가 여섯 글자 × 2바이트의 UTF16 배열이 됐다.

    할당량으로도 재 봤다. com.sun.management.ThreadMXBean.getThreadAllocatedBytes로 같은 호출을 10만 번 하는 동안 현재 스레드가 할당한 바이트를 재고, 호출 한 번당 값으로 나눴다. 같은 방법으로 잰 기본 크기는 byte[0] 16바이트, byte[9]와 byte[12] 32바이트, byte[18]과 byte[24] 40바이트, String 객체 하나 24바이트였다. 64비트 HotSpot의 기본 설정에서 배열 헤더가 16바이트이고 객체 크기가 8바이트 단위로 맞춰진다는 뜻이다. 아래 값은 기본 실행과 인터프리터만 쓰는 -Xint 실행에서 똑같이 나왔다.

    입력 크기가 똑같이 12바이트인데 한글이 섞이면 할당이 두 배를 넘는다. 2단계를 위해 만든 복사본은 첫 바이트부터 Latin-1이 아니어서 한 글자도 쓰지 못하고 버려지고, 3단계의 작업 배열은 최악의 경우에 맞춰 넉넉히 잡았다가 다시 잘라 낸다. 인코딩 쪽도 같은 전략이다. OpenJDK 21의 encodeUTF8_UTF16은 char 수 × 3 바이트 배열을 먼저 만들고 다 쓴 뒤 남는 만큼 잘라 낸다. "가나다"는 세 글자가 모두 3바이트라 9바이트가 꼭 맞아 잘라 낼 필요가 없었고, "가나다ABC"는 18바이트를 잡았다가 12바이트로 다시 복사했다. 글자 수를 먼저 세는 반복을 한 번 더 도는 대신 메모리를 넉넉히 쓰는 쪽을 고른 구현이다. 반대로 LATIN1 문자열에 음수 바이트가 없으면 getBytes(UTF_8)는 내부 배열을 clone()한 것 하나로 끝난다.

    countPositives는 자바 코드대로 실행되지 않는다

    1단계의 countPositives에는 @IntrinsicCandidate가 붙어 있다. 자바 코드는 바이트를 하나씩 보며 음수를 찾는 평범한 반복문이지만, 이 애너테이션은 HotSpot이 이 메서드를 자체 구현으로 바꿔 끼울 수 있다는 표시다. jdk21u 소스에서 vmIntrinsics.hpp는 이 메서드를 _countPositives(시그니처 ([BII)I)로 등록하고, C2 컴파일러는 library_call.cpp의 inline_countPositives()에서 호출 자리를 CountPositivesNode라는 전용 노드로 바꾼다. 이 기계 같은 AArch64에서 그 노드는 macroAssembler_aarch64.cpp의 count_positives가 된다. 32바이트보다 짧은 배열은 (메모리 페이지 끝에 걸리지 않는 한) 8바이트를 레지스터 하나에 읽어 마스크 0x8080808080808080과 대조해 여덟 바이트의 최상위 비트를 한 번에 검사하고, 32바이트 이상인 배열은 stubGenerator_aarch64.cpp의 generate_count_positives가 만든 스텁으로 넘어간다. 스텁의 주 반복은 남은 길이가 64바이트 이상인 동안 64바이트를 레지스터 여덟 개에 읽어 OR로 합친 뒤 한 번에 검사한다. 정말 바꿔 끼워지는지는 진단 옵션으로 볼 수 있다. ASCII 24바이트로 new String(ascii, UTF_8)을 200만 번 반복하는 프로그램을 돌렸다.

    @ 47은 호출이 일어난 바이트코드 위치다. javap -c -p java.lang.String으로 String(Charset, byte[], int, int) 생성자를 열면 47번에 invokestatic StringCoding.countPositives가 있다. C2가 이 생성자를 컴파일하면서 그 호출을 인트린식으로 바꿨다는 뜻이다. 같은 프로그램에 -XX:DisableIntrinsic=_countPositives를 더하면 이 줄이 사라진다. 이 옵션들은 진단용이고 출력 형식은 버전마다 달라질 수 있다.

    이 구현의 성격은 메서드 소스 주석의 @implSpec에도 드러난다. 음수 바이트가 있을 때 countPositives는 첫 음수 바이트의 위치 "이하"의 값을 돌려주면 된다고 적혀 있다. 정확한 위치를 약속하지 않는 이유는 위 기계어에서 보인다. 8바이트나 64바이트를 묶어 검사하다 음수를 발견하면, 그 묶음 안의 어디인지까지 찾지 않고 묶음의 시작 쪽을 돌려줘도 되도록 한 것이다. 그래서 이 값을 쓰는 String.decodeASCII는 돌려받은 위치부터 바이트를 하나씩 확인하는 짧은 반복을 덧붙인다. 이 decodeASCII는 뒤에서 볼 InputStreamReader의 경로에도 있다. sun.nio.cs.UTF_8의 디코더는 바이트 배열을 처리할 때(decodeArrayLoop) 맨 앞에서 decodeASCII로 ASCII 구간을 한꺼번에 처리하고 나서야 한 바이트씩 보는 반복에 들어간다. ASCII로 된 HTTP 요청 줄을 400번 이어 붙인 데이터를 InputStreamReader로 반복해 읽게 하고 -XX:+PrintCompilation을 함께 주면, C2가 String::decodeASCII를 인라인한 메서드(System$2::decodeASCII와 UTF_8$Decoder::decodeArrayLoop)를 컴파일하면서 countPositives와 Latin-1 바이트를 char로 넓히는 StringLatin1::inflate를 둘 다 인트린식으로 처리하는 줄이 나온다(vmIntrinsics.hpp의 이름은 _inflateStringC다). 로그·헤더·JSON처럼 대부분이 ASCII인 텍스트가 문자 스트림에서 빠르게 처리되는 근거가 여기에 있다.

    버퍼 경계에서 깨지는 문자

    앞의 예제는 파일 전체를 readAllBytes()로 한 번에 읽었기 때문에 잘 동작했다. 하지만 큰 파일이나 끝이 정해지지 않은 네트워크 입력은 한 번에 읽을 수 없다. 앞 회차에서 본 것처럼 보통은 고정 크기 버퍼로 조금씩 읽는다. 버퍼로 읽은 조각마다 new String을 하면 어떻게 될까. 차이를 눈에 띄게 하려고 버퍼를 4바이트로 줄여 보자.

    import java.io.ByteArrayInputStream;
import java.io.IOException;
import java.io.InputStream;
import java.nio.charset.StandardCharsets;

public class SplitChunkMain {
    public static void main(String[] args) throws IOException {
        byte[] data = "가나다".getBytes(StandardCharsets.UTF_8); // 9바이트
        InputStream in = new ByteArrayInputStream(data);

        byte[] buf = new byte[4];      // 일부러 작은 버퍼
        StringBuilder result = new StringBuilder();
        int n;
        while ((n = in.read(buf)) != -1) {
            String piece = new String(buf, 0, n, StandardCharsets.UTF_8);
            System.out.println(n + "바이트 → [" + piece + "] 길이 " + piece.length());
            result.append(piece);
        }
        System.out.println("합친 결과=" + result);
    }
}

    원래 세 글자였던 "가나다"가 "가" 한 글자와 대체 문자(U+FFFD, 화면에서는 물음표가 든 마름모) 다섯 개가 됐다. 9바이트는 하나도 빠짐없이 읽었는데 두 글자를 잃고 쓰레기 다섯 개를 얻었다. 왜 이렇게 되는지 알려면 UTF-8이 바이트 하나하나에 무엇을 적어 두는지 봐야 한다.

    첫 바이트의 비트 모양뜻뒤따르는 바이트
    0xxxxxxx (0x00~0x7F)1바이트 문자(ASCII)없음
    110xxxxx (0xC2~0xDF)2바이트 문자의 시작1개
    1110xxxx (0xE0~0xEF)3바이트 문자의 시작2개
    11110xxx (0xF0~0xF4)4바이트 문자의 시작3개
    10xxxxxx (0x80~0xBF)이어지는 바이트(continuation byte)단독으로는 문자가 아님

    "가"는 U+AC00이다. 16비트 값 1010 1100 0000 0000을 4비트·6비트·6비트로 나눠 1110xxxx 10xxxxxx 10xxxxxx 틀에 넣으면 11101010 10110000 10000000, 곧 EA B0 80이 된다. 이 구조 덕분에 UTF-8은 어느 바이트를 집어도 그것이 문자의 시작인지, 중간인지 알 수 있다. 동시에 이 구조 때문에 문자 하나가 버퍼 두 칸에 걸쳐 잘리면, 잘린 각 조각은 그 자체로는 올바른 UTF-8이 아니게 된다.

    바이트 :  EA B0 80 | EB 82 98 | EB 8B A4      ("가" | "나" | "다")
버퍼   : [EA B0 80 EB] [82 98 EB 8B] [A4]

1번 조각  EA B0 80  → '가'
          EB        → 3바이트 문자의 시작인데 조각이 끝남        → U+FFFD
2번 조각  82        → 앞에 시작 바이트가 없는 이어지는 바이트     → U+FFFD
          98        → 마찬가지                                   → U+FFFD
          EB 8B     → 시작은 했지만 한 바이트가 모자람           → U+FFFD
3번 조각  A4        → 홀로 남은 이어지는 바이트                  → U+FFFD

    1번 조각의 끝 EB는 "나"의 첫 바이트지만, new String은 이 조각이 전부라고 믿으므로 뒤가 잘린 잘못된 입력으로 판정한다. 2번 조각의 82 98은 "나"의 나머지인데, 앞에 시작 바이트가 없으니 각각 독립된 오류가 된다. 대체 문자가 몇 개 생기는지는 디코더가 잘못된 입력을 몇 바이트 단위로 끊어 판정하느냐에 달려 있고, 위 결과는 OpenJDK 21의 UTF-8 디코더가 실제로 낸 것이다.

    핵심은 new String(bytes, charset)이 기억이 없는 함수라는 점이다. 호출할 때마다 주어진 바이트만 보고 판정하며, 앞 호출에서 무엇이 남았는지 알지 못한다. 그러니 조각 단위로 부르는 한 경계에 걸린 문자는 반드시 깨진다. 버퍼를 크게 잡아도 확률만 줄어들 뿐 사라지지 않는다. 8192바이트 버퍼라도 8192번째 바이트가 어느 문자의 중간일 수 있기 때문이다. 이 문제는 파일보다 네트워크에서 더 자주 드러난다. TCP는 바이트의 흐름만 보장하고 한 번의 read가 몇 바이트를 돌려줄지는 정하지 않으므로(네트워크 회차에서 다룬다), 상대가 한 번에 보낸 문장도 받는 쪽에서는 아무 데서나 잘려 도착할 수 있다.

    해결책은 두 가지다. 전체를 다 모은 뒤 한 번에 디코딩하거나, 덜 끝난 바이트를 기억했다가 다음 조각 앞에 붙여 주는 변환기를 쓰는 것이다. 첫 번째는 메모리가 입력 크기만큼 필요하고 끝이 없는 입력에는 쓸 수 없다. 자바의 문자 스트림은 두 번째 방법으로 이 문제를 푼다.

    "가나다"의 9바이트가 4바이트 버퍼 세 칸에 나뉘어 담길 때 어느 문자가 경계에 걸려 대체 문자가 되는지 보여 준다. 가로로 긴 다이어그램. 위쪽 줄에 9개의 정사각형 칸이 이어져 있고 각 칸에 16진수 바이트 "EA" "B0" "80" "EB" "82" "98" "EB" "8B" "A4"가 적혀 있다. 칸 3개씩을 위에서 중괄호로 묶고 각각 "가", "나", "다" 라벨을 붙인다(세 묶음은 서로 다른 옅은 색). 아래쪽에 굵은 테두리 상자 세 개를 그려 4칸, 4칸, 1칸을 각각 감싸고 "버퍼 1", "버퍼 2", "버퍼 3" 라벨을 붙인다. 버퍼 1과 2 사이 경계, 버퍼 2와 3 사이 경계에 빨간 세로 점선을 긋고 "경계에서 문자가 잘림" 라벨을 단다. 각 버퍼 아래에 디코딩 결과를 적는다: 버퍼 1 아래 "가 �", 버퍼 2 아래 "� � �", 버퍼 3 아래 "�". 평평한 벡터 스타일, 흰 배경. new String을 조각마다 부르면 경계에 걸린 "나"와 "다"가 대체 문자 다섯 개로 바뀐다.

    상태를 가진 변환기: CharsetDecoder

    java.nio.charset 패키지의 CharsetDecoder는 Charset.newDecoder()로 얻는 디코더 객체다. 핵심 메서드는 decode(ByteBuffer in, CharBuffer out, boolean endOfInput)이다. 입력 바이트 버퍼에서 읽을 수 있는 만큼 읽어 출력 문자 버퍼에 쓰고, 왜 멈췄는지를 CoderResult로 알려 준다. 멈춘 이유는 넷 중 하나다. 입력이 바닥났거나 입력 끝에 덜 끝난 바이트만 남은 경우는 UNDERFLOW, 출력 버퍼가 가득 찬 경우는 OVERFLOW, 잘못된 바이트 열을 만난 경우는 malformed, 대상 문자 집합에 없는 문자를 만난 경우는 unmappable이다.

    세 번째 인자 endOfInput이 중요하다. false는 "뒤에 바이트가 더 올 수 있다"는 뜻이다. 이때 입력 끝에 EA B0처럼 시작만 하고 끝나지 않은 바이트가 있으면, 디코더는 그것을 오류로 판정하지 않고 입력 버퍼에 남겨 둔 채 UNDERFLOW로 멈춘다. 호출한 쪽은 남은 바이트를 버리지 말고 다음 바이트 앞에 이어 붙인 다음 다시 부르면 된다. 바이트 두 개만 먼저 도착한 상황을 손으로 재현해 보자.

    import java.nio.ByteBuffer;
import java.nio.CharBuffer;
import java.nio.charset.CharsetDecoder;
import java.nio.charset.CoderResult;
import java.nio.charset.StandardCharsets;

public class DecoderStateMain {
    public static void main(String[] args) {
        CharsetDecoder decoder = StandardCharsets.UTF_8.newDecoder();
        ByteBuffer in = ByteBuffer.allocate(8);
        CharBuffer out = CharBuffer.allocate(8);

        // 1차: '가'(EA B0 80) 중 앞의 두 바이트만 도착
        in.put((byte) 0xEA).put((byte) 0xB0);
        in.flip();
        CoderResult r1 = decoder.decode(in, out, false);
        System.out.println("1차 결과=" + r1 + ", 만든 문자 수=" + out.position()
                + ", 남은 바이트=" + in.remaining());

        // 남은 바이트를 버퍼 앞으로 옮기고, 마지막 바이트를 덧붙인다
        in.compact();
        in.put((byte) 0x80);
        in.flip();
        CoderResult r2 = decoder.decode(in, out, true);
        out.flip();
        System.out.println("2차 결과=" + r2 + ", 문자=" + out + ", 남은 바이트=" + in.remaining());
    }
}
    1차 결과=UNDERFLOW, 만든 문자 수=0, 남은 바이트=2
2차 결과=UNDERFLOW, 문자=가, 남은 바이트=0

    한 줄씩 따라가 보자. ByteBuffer는 배열과 함께 position(다음에 읽거나 쓸 위치)과 limit(읽거나 쓸 수 있는 끝)을 가진다. 두 바이트를 put하면 position이 2가 되고, flip()은 limit을 2로, position을 0으로 바꿔 "이제부터 0~1번 칸을 읽는다"는 상태로 만든다. 1차 decode는 EA를 보고 3바이트 문자의 시작임을 알지만 뒤에 한 바이트밖에 없다. endOfInput이 false이므로 오류가 아니라 UNDERFLOW로 멈추고, 두 바이트는 읽지 않은 채로 둔다. 그래서 남은 바이트가 2다.

    compact()는 아직 읽지 않은 바이트(position부터 limit 전까지)를 배열 맨 앞으로 옮기고, position을 그 뒤로 놓아 다시 쓰기 상태로 돌린다. 여기에 0x80을 덧붙이고 flip()하면 버퍼에는 EA B0 80 세 바이트가 온전히 놓인다. 2차 decode는 이것을 "가"로 바꾸고, 입력을 모두 소비했으므로 다시 UNDERFLOW를 돌려준다. 이번에는 endOfInput을 true로 줬으므로 만약 덜 끝난 바이트가 남아 있었다면 그때는 malformed로 판정됐을 것이다.

    정리하면, 경계 문제를 푸는 열쇠는 "덜 끝난 바이트를 버리지 않고 들고 있는 버퍼"와 "입력이 정말 끝났는지를 아는 쪽"이다. new String은 둘 다 없다. CharsetDecoder는 판정 규칙을 제공하고, 바이트를 들고 있다가 이어 붙이는 일은 호출하는 쪽의 몫이다. 이 호출하는 쪽의 일을 대신 해 주는 클래스가 바로 다음에 볼 InputStreamReader다.

    인코딩 방향에도 같은 문제가 있다. 자바의 char는 UTF-16 코드 단위(code unit)이고, U+FFFF를 넘는 문자(이모지 같은 보충 문자)는 상위 대리(high surrogate)와 하위 대리(low surrogate) 두 char로 표현된다. 쓰기 호출 하나가 상위 대리로 끝나고 하위 대리는 다음 호출로 들어오면, 인코더는 첫 호출에서 이 문자를 바이트로 바꿀 수 없다. 짝이 와야 비로소 4바이트 UTF-8 하나가 정해지기 때문이다. 그래서 인코딩 쪽도 덜 끝난 문자 하나를 들고 있어야 한다. OpenJDK 21 소스의 sun.nio.cs.StreamEncoder를 보면 haveLeftoverChar, leftoverChar 필드가 정확히 이 일을 한다.

    오류를 어떻게 처리할지는 CodingErrorAction으로 정한다. REPORT는 예외(MalformedInputException 같은 CharacterCodingException)로 알리고, REPLACE는 대체값을 넣고, IGNORE는 버린다. newDecoder()로 막 만든 디코더의 기본값은 REPORT이고, 디코더의 대체값은 U+FFFD다. 이 실행 환경에서 malformedInputAction()과 replacement()를 출력해 확인했다. 앞 절의 new String이 예외 없이 대체 문자를 넣은 것은, 그 생성자가 REPORT가 아닌 대체 방식으로 동작하기 때문이다.

    다리 클래스: InputStreamReader와 OutputStreamWriter

    InputStreamReader는 바이트 입력 스트림을 받아 문자 입력 스트림(Reader)으로 보이게 하는 클래스이고, OutputStreamWriter는 바이트 출력 스트림을 받아 문자 출력 스트림(Writer)으로 보이게 한다. Javadoc은 InputStreamReader를 바이트 스트림에서 문자 스트림으로 가는 다리(bridge)라고 부른다. 바이트 쪽 세계와 문자 쪽 세계를 잇는 클래스는 이 두 개가 사실상 전부이고, FileReader나 PrintWriter처럼 파일·소켓에 문자를 읽고 쓰는 다른 클래스들도 결국 내부에서 이 둘(정확히는 그 안의 인코더·디코더)을 거친다.

    import java.io.*;
import java.nio.charset.StandardCharsets;

public class StreamBridgeMain {
    public static void main(String[] args) throws IOException {
        File file = new File("bridge.txt");

        OutputStreamWriter osw = new OutputStreamWriter(
                new FileOutputStream(file), StandardCharsets.UTF_8);
        osw.write("가나다");
        System.out.println("write 직후 파일 크기=" + file.length());
        osw.flush();
        System.out.println("flush 직후 파일 크기=" + file.length());
        osw.close();

        try (InputStreamReader isr = new InputStreamReader(
                new FileInputStream(file), StandardCharsets.UTF_8)) {
            int ch;
            while ((ch = isr.read()) != -1) {
                System.out.print((char) ch + "(" + ch + ") ");
            }
            System.out.println();
        }
    }
}
    write 직후 파일 크기=0
flush 직후 파일 크기=9
가(44032) 나(45208) 다(45796)

    읽기 쪽부터 보면, isr.read()는 바이트가 아니라 문자 하나를 돌려준다. 44032는 0xAC00, 곧 "가"의 코드 값이다. 파일에서 3바이트를 읽어 한 문자로 조립하는 일을 InputStreamReader가 대신 했다. 앞 절의 4바이트 버퍼 실험과 달리 이쪽은 버퍼 경계를 신경 쓸 필요가 없다. 내부의 디코더가 덜 끝난 바이트를 들고 있기 때문이다.

    쓰기 쪽 결과가 더 흥미롭다. write("가나다")를 호출한 직후 파일 크기는 0이다. 9바이트는 아직 파일에 가지 않았다. flush()를 부르고 나서야 9바이트가 됐다. OutputStreamWriter가 내부에 바이트 버퍼를 갖고 있기 때문이다. 이 버퍼가 비워지기 전에 프로그램이 끝나면 내용은 그대로 사라진다. JVM은 종료할 때 열려 있는 Writer를 찾아 대신 flush해 주지 않는다. 그러니 문자 출력 스트림은 반드시 close()하거나(close가 flush를 포함한다) 적어도 flush()해야 하고, 가장 안전한 방법은 try-with-resources로 가장 바깥 객체를 닫는 것이다.

    안에 무엇이 들어 있나: StreamEncoder와 StreamDecoder

    OpenJDK 21 소스에서 OutputStreamWriter는 필드로 sun.nio.cs.StreamEncoder를 하나 갖고, 모든 쓰기를 그쪽에 넘긴다. StreamEncoder는 CharsetEncoder 하나와 ByteBuffer 하나를 갖는다. 바이트 버퍼는 512바이트로 시작해 최대 8192바이트까지 커진다(INITIAL_BYTE_BUFFER_CAPACITY = 512, MAX_BYTE_BUFFER_CAPACITY = 8192). 문자를 받으면 인코더가 이 바이트 버퍼에 결과를 채우고, 버퍼가 가득 차서 인코더가 OVERFLOW를 돌려줄 때 비로소 아래 OutputStream.write(byte[], off, len)을 한 번 부른다. 문자 집합을 받는 생성자로 만들면 인코더의 오류 처리는 malformed와 unmappable 모두 REPLACE로 설정된다.

    InputStreamReader도 같은 구조로 sun.nio.cs.StreamDecoder를 갖는다. 이쪽 바이트 버퍼는 처음부터 8192바이트다(DEFAULT_BYTE_BUFFER_SIZE = 8192). 그리고 문자 집합을 받는 생성자로 만들면 디코더의 오류 처리도 REPLACE다. 문자 배열로 읽는 read(char[], off, len)의 핵심 루프를 소스 그대로의 순서로 옮기면 다음과 같다.

    미리 읽기: 리더는 필요한 것보다 많이 가져간다

    위 루프의 3단계를 다시 보자. 아래 스트림에 요청하는 크기는 "필요한 바이트 수"가 아니라 "바이트 버퍼의 남은 자리"다. Javadoc도 이 점을 분명히 적는다. 바이트를 문자로 효율적으로 바꾸기 위해, 현재 읽기 요청을 채우는 데 필요한 것보다 많은 바이트를 아래 스트림에서 미리 읽을 수 있다는 것이다. 실제로 얼마나 가져가는지 보자.

    import java.io.*;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

public class ReadAheadMain {
    public static void main(String[] args) throws IOException {
        Path path = Path.of("ahead.txt");
        Files.writeString(path, "A".repeat(20_000));

        try (FileInputStream fis = new FileInputStream(path.toFile())) {
            Reader reader = new InputStreamReader(fis, StandardCharsets.UTF_8);
            int first = reader.read();                       // 문자 하나만 요청
            long pos = fis.getChannel().position();          // 파일에서 실제로 읽힌 위치
            System.out.println("읽은 문자=" + (char) first + ", 파일 위치=" + pos);
        }
    }
}
    읽은 문자=A, 파일 위치=8192

    문자 하나를 요청했는데 파일 위치는 8192까지 나아갔다. 1바이트를 제외한 8191바이트는 지금 InputStreamReader 내부 버퍼에 들어 있다. 이 상태에서 fis.read()를 직접 부르면 두 번째 바이트가 아니라 8193번째 바이트가 나온다. 리더에 들어간 8191바이트는 리더를 통해서만 꺼낼 수 있다.

    이 사실에서 중요한 규칙 하나가 나온다. 바이트 스트림을 리더로 감쌌다면, 그 뒤로는 감싼 스트림을 직접 읽지 않는다. 텍스트 머리말 뒤에 바이너리 본문이 오는 형식에서 이 실수가 잘 나온다. 머리말을 줄 단위로 읽으려고 리더를 씌우고, 본문은 원래의 InputStream에서 읽으려 하면, 본문의 앞부분은 이미 리더의 버퍼로 넘어가 있어 사라진다. HTTP 메시지가 바로 이런 모양(텍스트 헤더 + 본문)이어서, HTTP 서버를 직접 만드는 회차에서 이 문제를 다시 만난다.

    닫기도 같은 방향으로 전파된다. OpenJDK 21의 StreamDecoder.implClose()는 감싼 InputStream의 close()를 호출하고, StreamEncoder는 남은 바이트를 내보낸 뒤 감싼 OutputStream을 닫는다. 그래서 바깥 객체 하나만 닫으면 안쪽까지 차례로 닫힌다. 반대로 안쪽 스트림만 닫으면 바깥 Writer의 버퍼에 남은 바이트는 갈 곳을 잃는다.

    BufferedReader, InputStreamReader(내부 StreamDecoder), FileInputStream, 운영체제가 위에서 아래로 쌓여 있고, 각 층이 가진 버퍼와 한 번에 주고받는 단위를 보여 준다. 세로로 쌓인 네 개의 가로 상자. 맨 위 상자 "BufferedReader" 안에 작은 칸 띠와 라벨 "char[8192]". 두 번째 상자 "InputStreamReader" 안에 작은 상자 "StreamDecoder"가 있고 그 안에 "ByteBuffer 8192바이트"와 "CharsetDecoder" 두 칸이 나란히 있다. 세 번째 상자 "FileInputStream"은 비어 있고 옆에 "버퍼 없음" 라벨. 맨 아래 상자 "운영체제 read 시스템 콜". 상자 사이에 아래에서 위로 향하는 화살표: 맨 아래→세 번째는 "바이트", 세 번째→두 번째는 "최대 8192바이트씩", 두 번째→맨 위는 "문자 배열". 맨 위 상자 위쪽에 "프로그램" 아이콘과 위로 향하는 화살표 "readLine()". 오른쪽 여백에 세로 괄호로 두 번째 상자를 가리키며 "바이트→문자 변환" 라벨. 평평한 벡터 스타일, 흰 배경, 상자마다 다른 옅은 색. 문자 입력은 두 겹의 버퍼(문자 8192개, 바이트 8192개)를 거친다. FileInputStream 자체는 버퍼가 없다.

    잘못된 바이트를 만났을 때: 대체할 것인가, 알릴 것인가

    현실의 파일은 늘 깨끗하지 않다. 다른 문자 집합으로 쓰인 파일이 섞여 들어오기도 하고, 전송 중에 잘린 파일도 있다. 같은 바이트 열을 서로 다른 API로 읽어 보면 처리 방식이 다르다는 것을 알 수 있다.

    import java.io.*;
import java.nio.charset.StandardCharsets;
import java.nio.file.Files;
import java.nio.file.Path;

public class MalformedMain {
    public static void main(String[] args) throws IOException {
        byte[] bad = {0x41, (byte) 0xFF, 0x42};   // 'A', UTF-8에서 나올 수 없는 바이트, 'B'
        Path path = Path.of("bad.txt");
        Files.write(path, bad);

        try (Reader r = new InputStreamReader(new FileInputStream(path.toFile()), StandardCharsets.UTF_8)) {
            int ch;
            while ((ch = r.read()) != -1) {
                System.out.printf("U+%04X ", ch);
            }
            System.out.println("← InputStreamReader");
        }

        try (BufferedReader br = Files.newBufferedReader(path)) {
            System.out.println(br.readLine());
        } catch (IOException e) {
            System.out.println(e + " ← Files.newBufferedReader");
        }

        ByteArrayOutputStream bos = new ByteArrayOutputStream();
        try (Writer w = new OutputStreamWriter(bos, StandardCharsets.US_ASCII)) {
            w.write("A가B");                                // '가'는 ASCII에 없다
        }
        for (byte b : bos.toByteArray()) {
            System.out.printf("%02X ", b);
        }
        System.out.println("← US-ASCII OutputStreamWriter");
    }
}
    U+0041 U+FFFD U+0042 ← InputStreamReader
java.nio.charset.MalformedInputException: Input length = 1 ← Files.newBufferedReader
41 3F 42 ← US-ASCII OutputStreamWriter

    0xFF는 UTF-8의 어떤 위치에도 나올 수 없는 바이트다(앞의 표에서 시작 바이트는 0xF4를 넘지 않는다). InputStreamReader는 이것을 U+FFFD로 바꾸고 조용히 계속 읽는다. 앞에서 본 대로 문자 집합을 받는 생성자는 디코더를 REPLACE로 설정하기 때문이다. 반면 Files.newBufferedReader는 같은 바이트에서 MalformedInputException을 던진다. "Input length = 1"은 잘못된 입력이 1바이트 길이였다는 뜻이다. 쓰기 쪽에서는 ASCII에 없는 "가"가 대체 바이트 0x3F, 곧 물음표 한 개로 바뀌었다. 3바이트로 표현될 글자가 정보를 모두 잃고 1바이트가 됐지만 예외는 없었다.

    어느 쪽이 맞을까. 대체 방식은 사람이 읽는 로그나 화면 출력처럼 일부가 깨져도 나머지를 보는 편이 나은 곳에 어울린다. 하지만 데이터를 다른 곳으로 옮기거나 저장하는 프로그램이라면, 대체 문자는 손상을 숨긴 채 다음 단계로 넘겨 버린다. 문제는 한참 뒤에 엉뚱한 곳에서 발견된다. 이럴 때는 실패를 즉시 드러내는 쪽이 낫다. InputStreamReader에도 그렇게 하는 길이 있다. 문자 집합 대신 CharsetDecoder를 받는 생성자에 StandardCharsets.UTF_8.newDecoder()를 넘기면, 새 디코더의 기본값이 REPORT이므로 같은 0xFF에서 MalformedInputException이 난다. 이 동작도 같은 환경에서 확인했다.

    대체 문자 U+FFFD가 다시 UTF-8로 저장되면 EF BF BD 세 바이트가 된다. 깨진 데이터를 대체 방식으로 읽고 다시 쓰면 원래 바이트는 영영 돌아오지 않는다. 문자 집합을 모르는 바이트를 손대지 않고 옮겨야 한다면 문자 스트림이 아니라 바이트 스트림으로 복사해야 한다.

    잘못된 바이트는 몇 바이트씩 끊기는가: UTF-8 디코더의 판정 규칙

    앞 절의 예외 메시지는 "Input length = 1"이었고, 버퍼 경계 실험에서는 9바이트에서 대체 문자가 다섯 개 나왔다. 둘 다 디코더가 잘못된 입력을 몇 바이트 단위로 끊어 판정하느냐에서 나온 숫자다. 먼저 무엇이 "잘못된" 바이트 열인지부터 정확히 하자. UTF-8의 명세인 RFC 3629는 올바른 바이트 열을 ABNF 문법으로 정의한다. 2바이트 문자는 첫 바이트가 0xC2~0xDF이고, 3바이트 문자는 첫 바이트가 0xE0이면 둘째가 0xA0~0xBF, 0xED이면 둘째가 0x80~0x9F여야 하며, 4바이트 문자는 첫 바이트가 0xF0이면 둘째가 0x90~0xBF, 0xF4이면 둘째가 0x80~0x8F여야 한다. RFC는 UTF-8의 성질 중 하나로 0xC0, 0xC1, 0xF5~0xFF라는 바이트 값은 결코 나타나지 않는다고 적는데, 위 문법을 보면 이 값들이 어느 자리에도 들어갈 수 없다.

    이 좁은 범위들은 세 가지 규칙을 바이트로 옮긴 것이다. 첫째는 가장 짧은 형식(shortest form)이다. 0xC0이나 0xC1로 시작하는 2바이트 열은 U+007F 이하, 곧 1바이트로 쓸 수 있는 값만 만들고, 0xE0 뒤의 0x80~0x9F는 2바이트로 쓸 수 있는 값을, 0xF0 뒤의 0x80~0x8F는 3바이트로 쓸 수 있는 값을 만든다. 같은 문자를 더 긴 형식으로 쓴 것(overlong)은 금지다. 둘째, U+D800~U+DFFF는 UTF-16의 대리 쌍을 위해 비워 둔 값이라 UTF-8로 인코딩할 수 없다. 0xED 뒤의 0xA0~0xBF가 막힌 이유다. 셋째, 유니코드의 끝은 U+10FFFF이므로 0xF4 뒤의 0x90 이상과 0xF5 이상의 첫 바이트는 범위를 넘는다. RFC 3629는 이런 열을 해독해 주는 느슨한 구현이 보안 문제를 낳는다고 경고하며 실제 사례를 든다. 바이트 2F 2E 2E 2F("/../")는 막으면서 C0 AE를 "."으로 해독해 주는 파서는, 검사를 통과한 2F C0 AE 2E 2F가 나중에 "/../"로 바뀌는 경로 조작을 허용한다. 이 수법은 2001년 웹 서버를 공격한 바이러스에 실제로 쓰였다고 RFC는 적는다.

    OpenJDK 21의 sun.nio.cs.UTF_8 디코더는 3바이트·4바이트 열의 바이트 범위를 소스 주석에 표로 적어 두고 이 규칙들을 검사한다. 0xC0·0xC1은 2바이트 시작으로 인정하지 않는다. 3바이트 열은 0xE0 뒤의 범위를 따로 검사하고, 다 조립한 값이 대리 영역이면 버린다. 4바이트 열은 조립한 값이 U+10000~U+10FFFF 안인지(Character.isSupplementaryCodePoint)로 가장 짧은 형식과 상한을 한꺼번에 검사한다. 판정이 나면 CoderResult.malformedForLength(n)으로 "잘못된 입력은 n바이트"라고 알리고, CharsetDecoder.decode의 공통 반복은 REPLACE일 때 대체값 하나를 넣고 정확히 n바이트를 건너뛴 다음 다시 해독을 이어 간다. 또 endOfInput이 true인데 덜 끝난 바이트가 남아 UNDERFLOW가 나면, 남은 바이트 전체를 길이로 하는 malformed 하나로 바꾼다. 그러니 대체 문자의 개수는 곧 잘못된 입력 단위의 개수다. 여러 경우를 직접 넣어 보자.

    import java.nio.ByteBuffer;
import java.nio.CharBuffer;
import java.nio.charset.CharsetDecoder;
import java.nio.charset.CoderResult;
import java.nio.charset.StandardCharsets;

public class MalformedLengthMain {
    static void probe(String label, int... values) {
        byte[] bytes = new byte[values.length];
        for (int i = 0; i < values.length; i++) bytes[i] = (byte) values[i];

        // 1) REPORT 디코더가 첫 오류를 몇 바이트로 판정하는가
        CharsetDecoder dec = StandardCharsets.UTF_8.newDecoder();
        CoderResult r = dec.decode(ByteBuffer.wrap(bytes), CharBuffer.allocate(16), true);
        String first = r.isMalformed() ? "malformed 길이 " + r.length() : r.toString();

        // 2) new String은 U+FFFD를 몇 개 넣는가
        String s = new String(bytes, StandardCharsets.UTF_8);
        long repl = s.chars().filter(c -> c == 0xFFFD).count();
        System.out.println(label + " → 첫 판정=" + first + ", U+FFFD " + repl + "개");
    }

    public static void main(String[] args) {
        probe("C0 80", 0xC0, 0x80);
        probe("E0 80 80", 0xE0, 0x80, 0x80);
        probe("ED A0 BD", 0xED, 0xA0, 0xBD);
        probe("ED A0 BD ED B8 80", 0xED, 0xA0, 0xBD, 0xED, 0xB8, 0x80);
        probe("F4 90 80 80", 0xF4, 0x90, 0x80, 0x80);
        probe("EB 82 41", 0xEB, 0x82, 0x41);
        probe("F0 9F 98", 0xF0, 0x9F, 0x98);
    }
}

E0 80 80 → 첫 판정=malformed 길이 1, U+FFFD 3개
ED A0 BD → 첫 판정=malformed 길이 3, U+FFFD 1개
ED A0 BD ED B8 80 → 첫 판정=malformed 길이 3, U+FFFD 2개
F4 90 80 80 → 첫 판정=malformed 길이 1, U+FFFD 4개
EB 82 41 → 첫 판정=malformed 길이 2, U+FFFD 1개
F0 9F 98 → 첫 판정=malformed 길이 3, U+FFFD 1개

    한 줄씩 소스와 맞춰 보자. C0 80은 U+0000을 2바이트로 늘려 쓴 열이다. 0xC0은 시작 바이트로 인정되지 않아 1바이트짜리 오류가 되고, 남은 0x80은 홀로 선 이어지는 바이트라 또 1바이트짜리 오류가 되어 대체 문자가 둘이다. E0 80 80은 같은 U+0000을 3바이트로 늘려 쓴 것인데, 디코더가 오류 길이를 정하는 malformedN은 0xE0 뒤에 0x80~0x9F가 오면 첫 바이트 하나만 오류로 잘라 내므로 남은 두 바이트가 다시 각각 오류가 되어 셋이다. F4 90 80 80(U+110000)도 같은 이유로 넷이다.

    ED A0 BD는 결과가 다르다. 0xED에는 둘째 바이트 범위 검사가 따로 없어서 세 바이트가 구조 검사를 통과하고, 조립한 값 0xD83D가 대리 영역이라는 것이 드러난 뒤에야 세 바이트 전체가 한 단위의 오류(malformedForLength(3))가 된다. RFC의 문법으로는 0xED 0xA0에서 이미 어긋난 열이지만, OpenJDK는 그것을 다른 순서로 검사하기 때문에 끊는 길이가 1이 아니라 3이 됐다. 받아들이는 바이트 열의 집합은 RFC와 같고, 오류를 몇 바이트씩 끊어 보고하는지는 구현의 선택이다. EB 82 41에서는 디코더가 앞의 두 바이트만 오류로 끊었고, 0x41은 오류에 휩쓸리지 않고 "A"로 살아남았다. 이어지는 바이트가 비트 모양으로 구별되기 때문에, 디코더는 어긋난 지점에서 다음 문자의 시작을 바로 다시 찾을 수 있다. 마지막 F0 9F 98은 "😀"의 앞 세 바이트다. 바이트 자체는 틀리지 않았으므로 디코딩 반복은 UNDERFLOW로 멈추고, 입력이 끝났다는 표시가 있어서 남은 세 바이트가 길이 3의 오류 하나가 됐다.

    이 규칙으로 앞의 버퍼 경계 실험도 셀 수 있다. 둘째 조각 82 98 EB 8B에서 0x82와 0x98은 각각 1바이트짜리 오류이고, 끝의 EB 8B는 덜 끝난 꼬리로서 한 단위의 오류가 되어 대체 문자가 셋이었다. 그리고 표의 앞 네 줄은 이 회차 뒤쪽에서 볼 writeUTF의 수정된 UTF-8과 이어진다. 수정된 UTF-8은 널 문자를 C0 80으로, 보충 문자를 대리 쌍 각각의 3바이트 열(ED A0 BD ED B8 80)로 쓴다. RFC 3629는 대리 쌍을 이렇게 인코딩하는 방식을 CESU-8이라 부르며 그 결과가 올바른 UTF-8이 아니라고 적는다. 그래서 수정된 UTF-8 바이트를 표준 UTF-8 디코더로 읽으면 널 문자는 대체 문자 둘, 이모지는 대체 문자 둘로 바뀐다. 표의 대체 문자 개수는 new String(String 안의 자체 해독 코드)으로 센 것이고, 같은 바이트를 InputStreamReader(CharsetDecoder를 거치는 경로)로 읽어 세어도 모든 줄에서 같은 개수가 나왔다.

    Reader와 Writer: 문자 스트림의 계층

    이제 문자 스트림 전체를 위에서 내려다보자. java.io의 문자 입력 스트림은 모두 추상 클래스 Reader를, 문자 출력 스트림은 모두 Writer를 상속한다. 바이트 스트림의 InputStream·OutputStream과 짝을 이루며, 하는 일도 그 구조를 거의 그대로 따른다. 차이는 다루는 단위가 byte가 아니라 char라는 것 하나다.

    Reader.read()의 반환형이 char가 아니라 int인 이유는 바이트 스트림과 같다. 정상 값은 0~65535(0x0000~0xFFFF)인 문자 하나이고, 끝을 알리려면 이 범위 밖의 값 -1이 필요하다. char는 부호 없는 16비트라서 -1을 담을 수 없다. 반대로 Writer.write(int c)는 인자의 하위 16비트만 쓰고 상위 16비트는 무시한다고 Javadoc이 정해 두었다. 바이트 스트림의 write(int)가 하위 8비트만 쓰는 것과 같은 설계다.

    표에서 FileReader가 독립된 구현처럼 보이지만 실제로는 그렇지 않다. 이 JDK에서 FileReader.class.getSuperclass()를 출력하면 java.io.InputStreamReader, FileWriter는 java.io.OutputStreamWriter가 나온다. FileReader는 생성자에서 FileInputStream을 열어 부모인 InputStreamReader에 넘기는 편의 클래스일 뿐이다. 그러니 FileReader로 읽는 것과 new InputStreamReader(new FileInputStream(...))로 읽는 것은 같은 경로를 탄다. 문자 집합을 받는 FileReader(File, Charset), FileReader(String, Charset) 생성자는 Java 11에서 추가됐다. 그 전에는 FileReader로는 문자 집합을 지정할 방법이 없어서, 문자 집합이 필요하면 다리 클래스를 직접 조립해야 했다.

    문자 스트림은 동시 접근에 대비한 잠금도 갖는다. Reader와 Writer에는 protected Object lock 필드가 있고, 읽기·쓰기 연산은 이 객체로 동기화한다. OpenJDK 21 소스를 보면 클래스가 정확히 InputStreamReader나 FileReader일 때는 synchronized 대신 JDK 내부의 jdk.internal.misc.InternalLock을 잠금으로 쓰고, 하위 클래스라면 리더 객체 자신을 잠금으로 쓴다. 어느 쪽이든 문자 하나를 읽을 때마다 잠금을 잡고 놓는다는 점은 같다. 이 비용은 뒤에서 버퍼 계층을 볼 때 다시 등장한다.

    char 하나는 문자 하나가 아니다

    Reader.read()가 돌려주는 것은 정확히 말해 "문자"가 아니라 UTF-16 코드 단위 하나다. 대부분의 한글과 영문은 코드 단위 하나가 문자 하나지만, 보충 문자는 그렇지 않다.

    import java.io.IOException;
import java.io.Reader;
import java.io.StringReader;

public class SurrogateReadMain {
    public static void main(String[] args) throws IOException {
        String s = "A😀";
        System.out.println("length()=" + s.length()
                + ", 코드 포인트 수=" + s.codePointCount(0, s.length()));

        Reader reader = new StringReader(s);
        int ch;
        while ((ch = reader.read()) != -1) {
            System.out.printf("%d(0x%X) ", ch, ch);
        }
        System.out.println(ch);
    }
}

    "😀"(U+1F600)는 read() 두 번에 걸쳐 0xD83D와 0xDE00으로 나온다. 각각 상위 대리와 하위 대리다. 이 둘을 따로 다루면 안 되고 Character.toCodePoint(high, low)로 합쳐야 U+1F600이 된다. 같은 문자가 UTF-8 파일에서는 F0 9F 98 80 4바이트다. 그러니 UTF-8 4바이트 하나를 디코딩하면 char가 두 개 나온다.

    이 사실은 StreamDecoder의 설계에도 흔적을 남겼다. OpenJDK 21 소스에서 인자 없는 read()는 크기 2짜리 char 배열을 새로 만들어 문자 배열 읽기를 부르고, 두 개가 나오면 두 번째를 leftoverChar 필드에 보관했다가 다음 read()에서 돌려준다. 소스 주석은 대리 쌍을 처리하려면 최소 두 문자를 읽으려고 시도해야 한다고 설명한다. 보관해 둔 문자가 없는 read() 호출마다 배열 할당과 디코딩이 한 번씩 일어난다는 점도 기억해 두자. 두 문자를 얻었다면 다음 호출은 할당 없이 보관한 문자를 돌려주므로, 보충 문자가 없는 입력에서는 두 번에 한 번꼴이다.

    잠금 하나가 가상 스레드를 붙잡는다: 문자 스트림이 InternalLock을 쓰는 이유

    앞에서 OpenJDK 21의 문자 스트림이 정확히 InputStreamReader나 FileReader일 때는 synchronized 대신 InternalLock을 쓴다고 했다. 같은 일을 하는 잠금을 왜 두 가지로 나눠 두었을까. 이유는 JDK 21에 정식 기능으로 들어온 가상 스레드(virtual thread, JEP 444)에 있다. 가상 스레드는 JVM이 스케줄링하는 가벼운 스레드로, 실행될 때는 플랫폼 스레드 하나(캐리어, carrier) 위에 올라가고 블로킹 연산을 만나면 캐리어에서 내려와 그 운영체제 스레드를 다른 가상 스레드에게 넘긴다. JEP 444는 가상 스레드가 블로킹 중에도 내려오지 못하는, 곧 캐리어에 고정되는(pinned) 경우를 둘로 든다. synchronized 블록이나 메서드 안의 코드를 실행 중일 때, 그리고 네이티브 메서드나 외부 함수를 실행 중일 때다. 고정된 채 I/O 같은 블로킹 연산을 하면 그동안 캐리어와 그 아래 운영체제 스레드가 함께 묶인다. JEP는 이것이 프로그램을 틀리게 만들지는 않지만 확장성을 해칠 수 있고, 스케줄러가 고정된 캐리어만큼 스레드를 늘려 보상하지도 않는다고 적는다.

    문자 스트림은 이 조건에 정확히 걸린다. 리더의 read는 잠금을 잡은 채로 아래 InputStream.read를 부르고, 그 아래가 소켓이라면 상대가 데이터를 보낼 때까지 블로킹된다. 잠금이 모니터(synchronized)라면 바로 그 순간 가상 스레드가 고정된다. JEP 444의 java.io 항목은 이 패키지의 구현이 동기화를 많이 쓰고 있어 가상 스레드에서 고정을 피하려면 손봐야 했다고 설명한 뒤, 바뀐 내용을 이렇게 정리한다. BufferedInputStream, BufferedOutputStream, BufferedReader, BufferedWriter, PrintStream, PrintWriter는 직접 쓰일 때 모니터 대신 명시적 잠금을 쓰고, 하위 클래스로 쓰일 때는 예전처럼 동기화한다. InputStreamReader와 OutputStreamWriter 안의 스트림 디코더·인코더는 바깥 리더·라이터와 같은 잠금을 쓴다. OpenJDK 21의 InternalLock은 ReentrantLock 하나를 감싼 작은 클래스다. ReentrantLock을 쥔 가상 스레드는 모니터를 쥔 것이 아니므로, 그 상태에서 I/O로 블로킹해도 캐리어에서 내려올 수 있다.

    하위 클래스를 빼는 이유는 호환성이다. 리더를 상속한 코드는 부모 메서드가 객체 자신이나 lock 필드로 동기화한다고 가정하고 자기 메서드에서 같은 객체로 synchronized를 걸었을 수 있다. 그런 코드의 가정을 깨지 않으려고 잠금 선택을 생성 시점의 클래스로 가른다. 소스에서 확인하면, 실제로 잠금을 잡는 곳은 InputStreamReader.read가 그대로 넘기는 StreamDecoder다. InputStreamReader의 lockFor는 getClass()가 InputStreamReader.class나 FileReader.class와 같을 때만 새 InternalLock을 만들어 디코더에 넘기고, 아니면 리더 객체 자신을 넘긴다. 리플렉션으로 열어 보면 정확한 InputStreamReader의 디코더 잠금은 jdk.internal.misc.InternalLock, 익명 하위 클래스의 디코더 잠금은 리더 객체 자신이었다. BufferedReader는 더 조건이 까다롭다. Reader(Reader in) 생성자는 자기 클래스가 정확히 BufferedReader이고 감싸는 리더가 정확히 InputStreamReader나 FileReader일 때만 InternalLock을 만들고, 그 밖에는 감싸는 리더 객체를 잠금으로 쓴다. 예를 들어 new BufferedReader(new StringReader(...))의 잠금은 안쪽 StringReader 객체였다.

    고정이 실제로 일어나는지는 JEP 444가 진단용으로 소개한 시스템 속성 jdk.tracePinnedThreads로 볼 수 있다. 이 속성을 주면 고정된 채 블로킹하는 순간 스택 트레이스가 출력된다. 느린 소켓을 흉내 내어 바이트를 내주기 전에 50밀리초 잠드는 입력 스트림을 만들고, 정확한 InputStreamReader와 이름만 다른 하위 클래스로 각각 감싸 가상 스레드에서 한 문자를 읽었다.

    import java.io.*;
import java.nio.charset.StandardCharsets;

public class PinnedReaderMain {
    // 바이트를 하나 내주기 전에 잠깐 블로킹하는 입력 (느린 소켓을 흉내 낸다)
    static class SlowIn extends InputStream {
        private int left = 1;
        @Override public int read() throws IOException {
            byte[] b = new byte[1];
            return read(b, 0, 1) == -1 ? -1 : b[0];
        }
        @Override public int read(byte[] b, int off, int len) throws IOException {
            if (left-- <= 0) return -1;
            try { Thread.sleep(50); } catch (InterruptedException e) { throw new InterruptedIOException(); }
            b[off] = 'A';
            return 1;
        }
    }

    // 클래스 이름만 다르고 하는 일은 같은 하위 클래스
    static class MyReader extends InputStreamReader {
        MyReader(InputStream in) { super(in, StandardCharsets.UTF_8); }
    }

    static void readIn(String label, Reader r) throws Exception {
        Thread vt = Thread.ofVirtual().start(() -> {
            try { r.read(); } catch (IOException e) { throw new UncheckedIOException(e); }
        });
        vt.join();
        System.out.println(label + " 끝");
    }

    public static void main(String[] args) throws Exception {
        readIn("InputStreamReader", new InputStreamReader(new SlowIn(), StandardCharsets.UTF_8));
        readIn("MyReader(하위 클래스)", new MyReader(new SlowIn()));
    }
}

InternalLock을 쥐고 잠들었으므로 캐리어에서 내려올 수 있었다는 뜻이다. 하위 클래스로 읽은 쪽은 고정됐다. reason:MONITOR는 모니터 때문에 고정됐다는 표시이고, StreamDecoder의 read0과 그것이 부른 read가 같은 잠금 객체(이 경우 MyReader 객체)로 각각 synchronized에 들어가 있어서 두 프레임에 monitors:1이 붙었다. 스레드 번호와 워커 이름은 실행마다 다를 수 있다. =full로 바꾸면 Thread.sleep에서 SlowIn.read, StreamDecoder.readBytes를 거쳐 InputStreamReader.read까지 이어지는 전체 스택이 나온다. 운영 환경에서는 같은 상황이 JFR 이벤트 jdk.VirtualThreadPinned로 기록되며, JEP 444에 따르면 이 이벤트는 기본으로 켜져 있고 임계값은 20밀리초다.

    이 차이는 가상 스레드로 소켓 서버를 만들 때 실제 문제가 된다. 연결마다 가상 스레드를 하나씩 두고 소켓 입력을 직접 만든 리더 하위 클래스로 감싸면, 상대가 느린 연결마다 캐리어가 하나씩 묶인다. JEP 444에 따르면 가상 스레드를 돌리는 플랫폼 스레드 수(스케줄러의 병렬도)는 기본적으로 사용 가능한 프로세서 수와 같으므로, 프로세서 수만큼의 느린 연결이 동시에 고정되면 나머지 가상 스레드는 올라탈 캐리어가 없어 실행되지 못한다. 다만 이것은 JDK 21~23의 사정이다. JDK 24의 JEP 491(Synchronize Virtual Threads without Pinning)은 synchronized 안에서 블로킹하는 가상 스레드도 플랫폼 스레드를 내놓게 바꿔, 고정이 일어나는 경우를 거의 없앴다. JDK 21을 쓰는 동안에는 "정확한 클래스는 명시적 잠금, 하위 클래스는 모니터"라는 규칙을 기억해 두어야 한다.

    기본 문자 집합: 문자 집합을 생략하면 생기는 일

    new InputStreamReader(in), new FileReader("a.txt"), new FileWriter("a.txt")처럼 문자 집합을 주지 않으면 기본 문자 집합(default charset)이 쓰인다. 무엇이 기본값인지는 JDK 18을 경계로 바뀌었다. JEP 400(UTF-8 by Default)이 JDK 18에 들어오면서 Charset.defaultCharset()은 구현이 따로 바꾸지 않는 한 UTF-8이 됐다. JDK 17까지는 JVM이 시작할 때 운영체제와 로캘을 보고 기본값을 정했다. JEP 400에 따르면 macOS에서는 POSIX C 로캘이 아닌 한 UTF-8이었고, Windows에서는 windows-1252 같은 코드 페이지 기반 문자 집합이었다. 같은 코드가 운영체제와 사용자 설정에 따라 다른 바이트를 썼던 셈이다.

    JDK 18 이후에도 예전 동작으로 돌아갈 길은 남아 있다. 명령줄에서 -Dfile.encoding=COMPAT를 주면 기본 문자 집합이 JDK 17까지의 규칙으로 정해진다. 그 규칙이 고른 값은 JDK 17에서 추가된 시스템 속성 native.encoding으로 언제든 확인할 수 있다. 이 기계에서 로캘을 바꿔 가며 확인해 봤다.

    두 번째 줄이 JDK 18 이후의 모습이다. 운영체제 로캘이 C(ASCII)여도 기본 문자 집합은 UTF-8로 고정되고, 운영체제 쪽 값은 native.encoding에만 드러난다. 세 번째 줄은 COMPAT로 옛 규칙을 되살린 모습이다. 이때 FileReader를 문자 집합 없이 만들면 디코더가 ASCII가 되어, 한글 파일은 모두 대체 문자로 읽힌다.

    표의 마지막 열은 별개의 이야기다. System.out은 기본 문자 집합을 따르지 않는다. JEP 400은 콘솔 입출력을 UTF-8 통일 대상에서 명시적으로 뺐다. Java 21의 System Javadoc에 따르면 System.out은 콘솔이 있으면 Console.charset(), 없으면 stdout.encoding 속성의 문자 집합으로 문자를 바이트로 바꾼다. 실제로 LC_ALL=C에서 System.out.println("가")의 출력을 파이프로 받아 16진수로 찍어 보면 3F 0A, 곧 물음표와 줄바꿈만 나온다. 파일에 쓴 한글은 멀쩡한데 화면 출력만 깨진다면 이 차이를 의심해야 한다.

    하나 더 알아 둘 것은 API마다 기본값이 달랐다는 점이다. JEP 400 문서는 java.nio.file.Files에서 문자 집합 없이 파일을 읽고 쓰는 메서드는 원래부터 항상 UTF-8을 쓰도록 명세되어 있었다고 적는다. 그래서 JDK 17 이하의 Windows에서는 Files.writeString으로 쓴 파일을 FileReader로 읽으면 깨질 수 있었다. 결론은 단순하다. 어느 JDK에서 돌지 모르는 코드라면 문자 집합을 언제나 명시한다. 그러면 기본값이 무엇이든, 언제 바뀌든 영향을 받지 않는다.

    BufferedReader: 줄 단위로 읽기

    문자를 읽을 수 있게 됐지만, 텍스트를 다루는 프로그램이 실제로 원하는 단위는 대개 문자가 아니라 줄이다. 설정 파일의 한 항목, 로그 한 건, CSV 한 행, HTTP 헤더 한 줄이 모두 줄 단위다. 줄을 읽으려면 줄 끝 문자가 나올 때까지 문자를 모아야 하고, 모으려면 버퍼가 필요하다. BufferedReader가 이 일을 한다. 다른 Reader를 감싸 문자 배열 버퍼를 두고, 그 위에서 readLine()을 제공한다. 쓰기 쪽 짝은 BufferedWriter이고, 플랫폼의 줄바꿈을 쓰는 newLine()을 제공한다.

    import java.io.*;
import java.nio.charset.StandardCharsets;

public class BufferedLineMain {
    public static void main(String[] args) throws IOException {
        try (BufferedWriter bw = new BufferedWriter(
                new OutputStreamWriter(new FileOutputStream("lines.txt"), StandardCharsets.UTF_8))) {
            bw.write("첫째 줄");
            bw.newLine();
            bw.write("둘째 줄");
            bw.newLine();
            bw.write("셋째 줄(줄바꿈 없음)");
        }

        try (BufferedReader br = new BufferedReader(
                new InputStreamReader(new FileInputStream("lines.txt"), StandardCharsets.UTF_8))) {
            String line;
            int no = 1;
            while ((line = br.readLine()) != null) {
                System.out.println(no++ + ": [" + line + "]");
            }
        }
        System.out.println("파일 크기=" + new File("lines.txt").length());
    }
}
    1: [첫째 줄]
2: [둘째 줄]
3: [셋째 줄(줄바꿈 없음)]
파일 크기=50

    객체가 세 겹으로 쌓였다. 쓰기 쪽은 BufferedWriter → OutputStreamWriter → FileOutputStream, 읽기 쪽은 BufferedReader → InputStreamReader → FileInputStream이다. 각 객체는 같은 추상 타입(Writer 또는 Reader, 맨 아래는 바이트 스트림)을 받아 같은 추상 타입으로 보이면서 기능 하나를 덧붙인다. 앞 회차에서 본 데코레이터 구조가 문자 스트림에서도 그대로 쓰인다. try-with-resources는 가장 바깥 객체만 닫고, 닫기는 안쪽으로 전파된다.

    파일 크기 50바이트를 맞춰 보자. "첫째 줄"은 한글 세 글자(9바이트)와 공백(1바이트)으로 10바이트이고, macOS의 줄 구분자 \n 1바이트가 붙어 11바이트다. "둘째 줄"도 11바이트다. 마지막 줄 "셋째 줄(줄바꿈 없음)"은 한글 여덟 글자("셋, 째, 줄, 줄, 바, 꿈, 없, 음", 24바이트), 공백 두 개, 괄호 두 개로 28바이트이고 줄바꿈이 없다. 합치면 11 + 11 + 28 = 50바이트로 맞는다. 이렇게 바이트 수를 직접 세 보는 습관은 인코딩 문제를 추적할 때 큰 도움이 된다.

    readLine이 인정하는 줄 끝

    Javadoc은 줄이 다음 중 하나로 끝난다고 정한다. 줄바꿈('\n', LF), 캐리지 리턴('\r', CR), CR 바로 뒤에 LF가 오는 경우, 그리고 파일 끝(EOF)이다. 반환되는 문자열에는 줄 끝 문자가 들어가지 않고, 문자를 하나도 읽지 못한 채 스트림 끝에 닿았을 때만 null을 돌려준다. 이 규칙이 실제로 어떤 결과를 내는지 경계 사례로 확인하자.

    import java.io.BufferedReader;
import java.io.IOException;
import java.io.StringReader;

public class LineTerminatorMain {
    static void dump(String text, int bufferSize) throws IOException {
        BufferedReader br = new BufferedReader(new StringReader(text), bufferSize);
        StringBuilder sb = new StringBuilder();
        String line;
        while ((line = br.readLine()) != null) {
            sb.append('[').append(line).append(']');
        }
        System.out.println(sb);
    }

    public static void main(String[] args) throws IOException {
        dump("a\r\nb\rc\n\nd", 8192);  // 네 가지 줄 끝이 섞여 있다
        dump("x\n", 8192);             // 마지막 줄바꿈 뒤에는 줄이 없다
        dump("ab\r\ncd", 3);           // \r 과 \n 이 버퍼 경계에서 갈라진다
    }
}
    [a][b][c][][d]
[x]
[ab][cd]

    첫 줄은 CRLF로 끝난 "a", CR로 끝난 "b", LF로 끝난 "c", 아무것도 없이 LF만 있는 빈 줄, 그리고 EOF로 끝난 "d"다. 빈 줄은 null이 아니라 빈 문자열 ""로 돌아온다는 점이 중요하다. null은 오직 "더 읽을 것이 없다"는 뜻이고, 그래서 while ((line = br.readLine()) != null) 반복이 빈 줄에서 멈추지 않는다. 두 번째 결과는 "x\n"이 한 줄이라는 것을 보여 준다. 마지막 LF 뒤에 빈 줄이 하나 더 있는 것으로 보지 않는다. 같은 방식으로 "one\r\n\r\ntwo\r"은 [one][][two] 세 줄이 된다.

    세 번째 결과는 구현을 들여다봐야 이해된다. 버퍼 크기를 3으로 줬으므로 첫 번째 채우기에서 버퍼에는 a b \r만 들어온다. readLine은 \r을 보고 "ab"를 돌려준다. 그런데 이 시점에는 다음 문자가 \n인지 알 수 없다. 버퍼에 없기 때문이다. OpenJDK 21의 BufferedReader는 CR로 줄을 끝낼 때마다 skipLF라는 플래그를 켜 둔다. 다음 readLine이 버퍼를 다시 채웠을 때 첫 문자가 \n이면 그것을 건너뛰고, 아니면 그냥 읽는다. 그래서 CRLF가 버퍼 경계에서 갈라져도 빈 줄이 끼어들지 않는다. 앞에서 본 디코더의 "덜 끝난 바이트"와 같은 종류의 문제다. 경계에 걸친 무언가를 처리하려면 반드시 상태 하나가 필요하다.

    구현에서 하나 더 볼 것은 줄 길이에 상한이 없다는 점이다. OpenJDK 21의 readLine은 버퍼 안에서 줄 끝을 찾지 못하면 지금까지의 문자를 StringBuilder에 옮기고 버퍼를 다시 채우기를 줄 끝이 나올 때까지 반복한다. 파일이라면 문제가 되지 않지만, 상대가 통제하는 네트워크 입력이라면 줄바꿈 없이 끝없이 보내는 것만으로 메모리를 계속 쓰게 만들 수 있다. 서버가 요청 줄과 헤더의 길이에 제한을 두는 이유 중 하나가 이것이다. 이 밖에 Java 8부터는 lines()가 줄을 Stream<String>으로 돌려준다. 내부적으로는 같은 readLine을 부른다.

    버퍼는 몇 겹인가: 호출 횟수와 시간으로 보기

    BufferedReader의 기본 버퍼는 문자 8192개다(OpenJDK 21 소스의 DEFAULT_CHAR_BUFFER_SIZE = 8192, Javadoc에는 "대부분의 목적에 충분히 크다"고만 적혀 있다). char가 2바이트이므로 메모리로는 16KB다. 그 아래 InputStreamReader의 디코더에는 앞에서 본 8192바이트 버퍼가 있다. 그렇다면 BufferedReader를 씌웠을 때 줄어드는 것은 무엇일까. 앞 회차에서 버퍼링의 효과를 "시스템 콜 횟수"로 설명했으니, 같은 잣대로 재 보자.

    FilterInputStream을 상속해 아래쪽 read(byte[], off, len) 호출을 세는 스트림을 만들고, 20,000바이트(ASCII 'A' 20,000개) 파일을 두 방식으로 끝까지 한 문자씩 읽었다. InputStreamReader만 쓴 경우 아래쪽 호출은 4번이었다. 8192바이트를 요청해 8192바이트, 다시 8192바이트, 8192바이트를 요청해 남은 3616바이트를 받고, 마지막 한 번은 -1을 받았다. BufferedReader를 씌운 경우에도 정확히 4번이었다. 이 구성에서 BufferedReader는 운영체제까지 내려가는 호출을 하나도 줄이지 못한다. 바이트는 이미 디코더가 버퍼링하고 있기 때문이다.

    그래도 BufferedReader를 쓰라는 이유는 호출 한 번의 고정 비용에 있다. 앞에서 본 대로 OpenJDK 21의 InputStreamReader.read()는 호출마다 잠금을 잡고, 보관해 둔 문자가 없으면 크기 2짜리 char 배열을 새로 만들어 디코더를 부른다. BufferedReader.read()도 잠금은 잡지만, 버퍼에 문자가 남아 있는 동안은 배열에서 하나를 꺼내 돌려주는 것이 전부다. readLine()은 한 번의 호출로 버퍼를 훑어 한 줄을 통째로 만든다. 실제 시간이 어떻게 갈리는지 이 기계에서 재 봤다. "가나다라마바사abcdefg"와 줄바꿈으로 된 29바이트·15글자짜리 줄을 100만 번 반복한 파일(29,000,000바이트, 15,000,000글자)을 네 방식으로 끝까지 읽었다.

    읽는 방식한 번 호출에 얻는 것측정 시간(3회차 실행)
    FileInputStream.read()를 바이트마다바이트 1개 (문자로 바꾸지 않음)약 15.0초
    InputStreamReader.read()를 문자마다문자 1개약 0.58초
    BufferedReader.read()를 문자마다문자 1개약 0.25초
    BufferedReader.readLine()줄 하나약 0.07초

    이 숫자는 Apple M1, Temurin 21.0.13에서 같은 프로그램 안에서 세 번 반복한 측정 중 세 번째 값이다. JIT 컴파일이 덜 된 첫 번째 반복은 일부 방식이 더 느렸고(예를 들어 InputStreamReader는 약 0.65초), 기계·운영체제·JVM 옵션이 바뀌면 값도 바뀐다. 절대값이 아니라 자릿수의 차이를 읽어야 한다. 첫 줄과 나머지의 차이는 앞 회차의 주제, 곧 바이트마다 시스템 콜을 하는 비용이다. 둘째 줄부터는 모두 디코더가 바이트를 8192개씩 읽으므로 시스템 콜 횟수는 같다. 그런데도 2배 이상, 다시 3배 이상 차이가 나는 것은 호출에 붙는 잠금, 배열 할당, 디코더 진입 같은 고정 비용이 문자 1,500만 개만큼 쌓이기 때문이다.

    쓰기 쪽은 사정이 다르다. 같은 방식으로 아래쪽 write 호출을 세어 보자.

    import java.io.*;
import java.nio.charset.StandardCharsets;

public class CountingMain {
    // 아래 스트림에 몇 번, 몇 바이트를 요청했는지 센다
    static class CountingOut extends FilterOutputStream {
        int calls;
        CountingOut(OutputStream out) { super(out); }
        @Override public void write(int b) throws IOException { calls++; out.write(b); }
        @Override public void write(byte[] b, int off, int len) throws IOException {
            calls++;
            out.write(b, off, len);
        }
    }

    public static void main(String[] args) throws IOException {
        CountingOut c1 = new CountingOut(OutputStream.nullOutputStream());
        try (Writer w = new OutputStreamWriter(c1, StandardCharsets.UTF_8)) {
            for (int i = 0; i < 20_000; i++) w.write('A');
        }
        System.out.println("OutputStreamWriter에 한 글자씩: 아래 write 호출 " + c1.calls + "번");

        CountingOut c2 = new CountingOut(OutputStream.nullOutputStream());
        try (Writer w = new BufferedWriter(new OutputStreamWriter(c2, StandardCharsets.UTF_8))) {
            for (int i = 0; i < 20_000; i++) w.write('A');
        }
        System.out.println("BufferedWriter를 씌우고 한 글자씩: 아래 write 호출 " + c2.calls + "번");
    }
}
    OutputStreamWriter에 한 글자씩: 아래 write 호출 40번
BufferedWriter를 씌우고 한 글자씩: 아래 write 호출 3번

    40번과 3번의 차이는 StreamEncoder의 버퍼 크기 정책에서 나온다. OpenJDK 21 소스의 growByteBufferIfNeeded(len)는 이번 쓰기 호출로 들어온 문자 수 len에 인코더의 문자당 최대 바이트 수(UTF-8 인코더는 3.0)를 곱해, 그만큼이 필요할 때만 버퍼를 최대 8192바이트까지 키운다. 한 글자씩 쓰면 매번 1 × 3 = 3바이트만 필요하므로 버퍼는 처음의 512바이트에서 자라지 않는다. 그래서 512바이트가 찰 때마다 한 번씩 내려보내 39번(512 × 39 = 19,968바이트), 닫을 때 남은 32바이트를 한 번 더 보내 40번이다. BufferedWriter를 씌우면 문자 8192개가 모인 뒤 한 번에 넘어가므로 인코더 버퍼가 8192바이트로 커지고, 아래로는 8192, 8192, 3616바이트 세 번만 내려간다. 아래가 FileOutputStream이었다면 이 숫자가 곧 write 시스템 콜 횟수다.

    정리하면 OpenJDK 21에서 문자 읽기 쪽 버퍼는 디코더가 이미 바이트를 모아 주므로 BufferedReader가 줄이는 것은 주로 호출당 고정 비용이고, 문자 쓰기 쪽은 BufferedWriter가 실제로 아래 스트림 호출 횟수까지 줄인다. 다만 이 비대칭은 구현의 사정이지 명세가 보장하는 성질이 아니다. Javadoc의 권고는 단순하다. 비용이 큰 read()를 가진 리더(FileReader, InputStreamReader)는 BufferedReader로 감싸라는 것이다. 버퍼 객체 하나의 비용은 작고, 감싸 두면 구현이 어떻게 바뀌든 안전하다. 참고로 OpenJDK 21의 BufferedWriter는 기본 생성자로 만들 때 가상 스레드 안이면 512글자로 시작해 8192글자까지 자라고, 플랫폼 스레드라면 처음부터 8192글자로 만든다. 가상 스레드를 수없이 만드는 환경에서 버퍼 메모리를 아끼려는 장치다.

    BufferedWriter, PrintWriter와 줄바꿈

    BufferedWriter.newLine()은 OpenJDK 21 소스에서 write(System.lineSeparator()) 한 줄이다. 줄 구분자는 시스템 속성 line.separator의 값이고, System Javadoc은 이를 유닉스에서 "\n"이라고 적는다. Windows에서는 "\r\n"이다. 즉 newLine()을 쓴 같은 프로그램이 운영체제에 따라 다른 바이트를 만든다. 위 예제의 파일 크기 50은 macOS에서 잰 값이고, Windows라면 줄바꿈 두 개가 2바이트씩이 되어 52가 된다.

    사람이 읽는 텍스트 파일이라면 이 차이는 대개 문제가 되지 않는다. readLine이 세 가지 줄 끝을 모두 인정하기 때문이다. 하지만 바이트 형식이 정해진 프로토콜이라면 이야기가 다르다. HTTP/1.1은 메시지의 각 줄을 CRLF로 끝내도록 정한다(RFC 9112). 이런 출력에 newLine()이나 println()을 쓰면 운영체제에 따라 형식이 달라진다. 프로토콜 출력에서는 "\r\n"을 직접 쓰는 것이 맞다. HTTP 서버를 만드는 회차에서 이 점을 실제로 적용한다.

    PrintWriter는 Writer 위에 print, println, printf, format을 얹은 클래스다. 두 가지 성질을 알아 두어야 한다. 첫째, Javadoc에 따르면 이 클래스의 메서드는 I/O 예외를 던지지 않는다(생성자는 던질 수 있다). 오류가 나면 내부 플래그만 세우고, 확인하려면 checkError()를 불러야 한다. 아래에서 볼 PrintStream과 같은 설계다. 둘째, 자동 flush를 켜면 println, printf, format이 호출될 때만 flush한다. Javadoc은 이것이 줄바꿈 문자가 출력될 때마다 flush하는 PrintStream과 다르다고 명시한다. 소켓으로 한 줄씩 주고받는 프로그램에서 new PrintWriter(소켓출력, true)를 쓰고 println으로 보내는 패턴이 흔한데, 자동 flush를 켜지 않거나 print만 쓰면 메시지가 버퍼에 머물러 상대가 끝없이 기다리게 된다.

    자동 flush가 없는 PrintWriter를 닫지 않으면 어떻게 될까. new PrintWriter(new FileWriter("log.txt"))를 만들어 println("시작")만 하고 main이 끝나는 프로그램을 돌리면 log.txt의 크기는 0이었다. 문자열은 FileWriter(곧 OutputStreamWriter) 안의 인코더 버퍼에 들어간 채로 JVM이 끝났다. 예외도 경고도 없다.

    기타 스트림 1: PrintStream — 문자를 아는 바이트 스트림

    가장 많이 쓰는 스트림은 아마 System.out일 것이다. 이 객체의 클래스는 java.io.PrintStream이고, PrintStream은 OutputStream의 하위 클래스, 즉 바이트 스트림이다. 그런데 println("가")처럼 문자열을 받는다. 바이트 스트림이 문자를 받으려면 안에 인코더가 있어야 한다. Javadoc은 PrintStream이 출력하는 모든 문자를 주어진 문자 집합(없으면 기본 문자 집합)으로 바이트로 바꾼다고 적는다. 그리고 다른 출력 스트림과 달리 IOException을 결코 던지지 않으며, 예외 상황에서는 내부 플래그만 세우고 이를 checkError로 확인할 수 있다고 적는다. 실제로 어떻게 되는지 보자.

    import java.io.*;
import java.nio.charset.StandardCharsets;

public class PrintStreamErrorMain {
    public static void main(String[] args) {
        OutputStream broken = new OutputStream() {
            @Override public void write(int b) throws IOException {
                throw new IOException("디스크 가득 참");
            }
        };

        PrintStream ps = new PrintStream(broken, true, StandardCharsets.UTF_8);
        ps.println("중요한 기록");                 // 예외가 밖으로 나오지 않는다
        System.out.println("PrintStream checkError=" + ps.checkError());

        Writer w = new OutputStreamWriter(broken, StandardCharsets.UTF_8);
        try {
            w.write("중요한 기록");
            w.flush();
        } catch (IOException e) {
            System.out.println("OutputStreamWriter → " + e.getMessage());
        }
    }
}
    PrintStream checkError=true
OutputStreamWriter → 디스크 가득 참

    쓰기마다 예외를 던지는 고장 난 스트림을 두 방식으로 감쌌다. PrintStream의 println은 아무 일 없다는 듯 돌아왔고, 실패의 흔적은 checkError()가 true를 돌려준다는 것뿐이다. 같은 스트림을 OutputStreamWriter로 감싸면 flush에서 IOException이 그대로 올라온다. main 선언에 throws IOException이 없어도 컴파일된 것 자체가 단서다. PrintStream.println은 검사 예외를 선언하지 않는다.

    OpenJDK 21 소스로 내부를 보면 구조가 흥미롭다. PrintStream은 필드로 BufferedWriter textOut과 OutputStreamWriter charOut을 갖고, charOut은 new OutputStreamWriter(this, charset)로, 곧 PrintStream 자기 자신을 바이트 출력 대상으로 삼아 만들어진다. 문자열을 출력하면 textOut → charOut → PrintStream 자신의 바이트 쓰기 → 감싼 OutputStream 순서로 흐른다. 그리고 문자열 쓰기가 끝날 때마다 textOut.flushBuffer()와 charOut.flushBuffer()를 불러 두 문자 버퍼를 즉시 비운다. 이 내부 버퍼들은 변환의 통로일 뿐 호출 사이에 데이터를 쌓아 두지 않는다. 자동 flush가 켜져 있으면 문자열에 '\n'이 있을 때 감싼 스트림의 flush()까지 부른다. 예외는 이 경로 전체를 감싼 catch (IOException x)에서 trouble = true로 바뀐다.

    바이트 스트림이면서 문자도 받다 보니, 이름이 비슷한 메서드가 전혀 다른 일을 한다.

    import java.io.ByteArrayOutputStream;
import java.io.PrintStream;
import java.nio.charset.StandardCharsets;

public class PrintVsWriteMain {
    public static void main(String[] args) {
        ByteArrayOutputStream bos = new ByteArrayOutputStream();
        PrintStream ps = new PrintStream(bos, false, StandardCharsets.UTF_8);
        ps.print(65);      // 숫자 65를 글자 "65"로
        ps.write(65);      // 바이트 0x41 하나를 그대로
        ps.print('가');    // 문자 하나를 UTF-8 바이트로
        ps.flush();
        for (byte b : bos.toByteArray()) {
            System.out.printf("%02X ", b);
        }
        System.out.println();
    }
}
    36 35 41 EA B0 80

    print(65)는 String.valueOf(65), 곧 글자 "6"과 "5"를 인코딩해 36 35를 쓴다. write(65)는 OutputStream에서 물려받은 바이트 쓰기라서 값 65를 바이트 0x41 하나로 그대로 쓴다. Javadoc도 write(int)는 바이트를 주어진 그대로 쓰며, 문자로 변환되게 하려면 print(char)를 쓰라고 적는다. print('가')는 문자 하나를 UTF-8로 인코딩해 3바이트를 쓴다.

    예외를 삼키는 설계는 System.out의 쓰임새를 생각하면 이해가 된다. 진단 메시지 한 줄 찍을 때마다 try-catch를 강요한다면 아무도 쓰지 않을 것이다. 콘솔 출력이 실패했다고 프로그램의 본래 작업까지 멈출 이유도 없다. 하지만 같은 성질이 중요한 데이터를 파일에 쓰는 곳에서는 함정이 된다. 디스크가 가득 차도, 네트워크가 끊겨도 println은 성공한 것처럼 돌아온다. 결과를 반드시 남겨야 하는 출력이라면 예외를 던지는 Writer 계열을 쓰거나, 적어도 끝에서 checkError()를 확인해야 한다.

    기타 스트림 2: DataOutputStream, DataInputStream과 메모리 스트림

    지금까지는 모든 값을 문자로 바꿔 저장했다. 정수 1을 쓰려면 글자 "1"을, 1.5를 쓰려면 "1.5"를 썼다. 사람이 읽기에는 좋지만, 읽는 쪽이 문자열을 다시 해석해야 하고 값마다 길이가 달라 경계를 표시할 구분자도 필요하다. 다른 길은 값을 메모리에 있는 그대로의 이진 형식으로 쓰는 것이다. DataOutputStream은 다른 OutputStream을 감싸 writeInt, writeLong, writeDouble, writeBoolean, writeUTF 같은 메서드를 제공하는 데코레이터이고, DataInputStream이 짝이 되는 읽기 쪽이다. 바이트가 정확히 어떻게 놓이는지 메모리 스트림에 써서 확인해 보자.

    import java.io.*;

public class DataStreamMain {
    public static void main(String[] args) throws IOException {
        ByteArrayOutputStream bos = new ByteArrayOutputStream();
        try (DataOutputStream dos = new DataOutputStream(bos)) {
            dos.writeInt(1);
            dos.writeInt(-2);
            dos.writeBoolean(true);
            dos.writeUTF("A가");
            dos.writeDouble(1.5);
        }
        byte[] bytes = bos.toByteArray();
        System.out.println("총 " + bytes.length + "바이트");
        for (byte b : bytes) {
            System.out.printf("%02X ", b);
        }
        System.out.println();

        try (DataInputStream dis = new DataInputStream(new ByteArrayInputStream(bytes))) {
            System.out.println(dis.readInt() + ", " + dis.readInt() + ", " + dis.readBoolean()
                    + ", " + dis.readUTF() + ", " + dis.readDouble());
            dis.readInt();                                  // 더 읽을 것이 없다
        } catch (EOFException e) {
            System.out.println("EOFException: 데이터 끝");
        }
    }
}

    정수의 바이트 순서는 명세로 정해져 있다. DataInput Javadoc은 readInt가 읽은 네 바이트 a, b, c, d로 ((a & 0xff) << 24) | ((b & 0xff) << 16) | ((c & 0xff) << 8) | (d & 0xff)를 만든다고 적는다. 첫 바이트가 가장 높은 자리라는 뜻이고, 이것이 빅 엔디언(big-endian), 네트워크 바이트 순서다. Apple M1이나 x86 CPU는 메모리에 정수를 낮은 자리 바이트부터 저장하는 리틀 엔디언이지만, DataOutputStream이 만드는 바이트는 CPU와 상관없이 언제나 같다. 그래서 다른 기계에서 읽어도 같은 값이 나온다. 1.5의 경우 Double.doubleToLongBits(1.5)가 0x3FF8000000000000이다. 부호 비트 0, 지수 필드 1023(0x3FF, 실제 지수 0), 가수의 첫 비트 1(0.5)로 1.0 × 1.5를 나타낸다.

    이 바이트들에는 타입 정보가 전혀 없다는 점에 주목하자. 읽는 쪽이 쓴 순서와 타입을 정확히 알아야 한다. 같은 23바이트를 처음부터 readLong()으로 읽으면 앞의 8바이트 00 00 00 01 FF FF FF FE가 하나의 long, 곧 0x00000001FFFFFFFE = 8,589,934,590이 된다. 예외는 나지 않는다. 바이트는 그저 바이트이고, 의미는 읽는 쪽의 약속에서 나온다. 끝을 알리는 방식도 다르다. InputStream.read()는 -1로 끝을 알렸지만, readInt()는 -1을 포함한 모든 int 값을 정상적으로 돌려줄 수 있으므로 특별한 반환값을 끝 표시로 쓸 수 없다. 그래서 Javadoc대로, 필요한 바이트를 다 읽기 전에 끝에 닿으면 EOFException을 던진다.

    writeUTF는 UTF-8이 아니다

    이름과 달리 writeUTF가 쓰는 것은 표준 UTF-8이 아니라 수정된 UTF-8(modified UTF-8)이다. DataInput Javadoc이 정한 차이는 세 가지다. 널 문자 U+0000을 1바이트가 아니라 2바이트로 써서 인코딩된 문자열 안에 0 바이트가 나타나지 않게 하고, 1·2·3바이트 형식만 쓰며, 보충 문자는 대리 쌍으로 표현한다. 즉 대리 쌍의 두 char를 각각 3바이트로 인코딩해 6바이트가 된다. 실제로 비교해 보면 다음과 같다.

    문자열writeUTF 결과표준 UTF-8(getBytes(UTF_8))
    "A"00 01 4141
    "\u0000"00 02 C0 8000
    "😀" (U+1F600)00 06 ED A0 BD ED B8 80F0 9F 98 80

    앞 두 바이트는 길이이고, 부호 없는 16비트이므로 내용은 최대 65,535바이트다. 이것을 넘으면 UTFDataFormatException이 난다. 'a' 70,000개를 쓰려 하면 이 JDK에서 "encoded string (aaaaaaaa...aaaaaaaa) too long: 70000 bytes"라는 메시지가 나왔고, 한글은 글자당 3바이트이므로 21,845자(65,535바이트)까지만 쓸 수 있었다. 수정된 UTF-8은 자바에서 오래전부터 쓰인 내부 형식으로, 클래스 파일의 상수 풀 문자열(JVMS §4.4.7)도 이 형식이다. 문제는 다른 언어나 프로그램이 이 바이트를 표준 UTF-8로 읽으면 널 문자와 보충 문자에서 결과가 달라진다는 점이다. writeUTF는 자바의 readUTF가 읽을 것을 전제로 한 형식이고, 다른 시스템과 주고받을 문자열이라면 getBytes(UTF_8)로 바꾼 뒤 길이를 writeInt로 먼저 쓰는 식으로 형식을 직접 정하는 편이 낫다.

    비슷한 이름의 함정이 두 개 더 있다. writeChars("A가")는 각 char를 2바이트(높은 바이트 먼저)로 써서 00 41 AC 00을 만든다. 길이 정보가 없으므로 읽는 쪽이 글자 수를 따로 알아야 한다. writeBytes("A가")는 각 char의 하위 8비트만 써서 41 00을 만든다. "가"(0xAC00)의 상위 바이트가 버려져 0x00만 남았다. ASCII가 아닌 문자에는 쓰면 안 되는 메서드다.

    메모리를 대상으로 하는 스트림

    위 예제에서 바이트는 파일이 아니라 ByteArrayOutputStream으로 갔다. 이 클래스는 출력 대상이 힙 위의 바이트 배열인 OutputStream이다. 쓰는 만큼 내부 배열이 커지고, toByteArray()는 지금까지 쓴 내용을 새 배열로 복사해 돌려준다. 짝인 ByteArrayInputStream은 주어진 바이트 배열을 입력원으로 삼는다. 문자 쪽에는 StringReader, StringWriter, CharArrayReader, CharArrayWriter가 같은 역할을 한다. 운영체제 자원을 쓰지 않으므로 시스템 콜이 없고, 닫을 대상도 없다. Javadoc은 ByteArrayOutputStream을 닫아도 아무 효과가 없으며 닫은 뒤에도 메서드를 IOException 없이 부를 수 있다고 적는다. 실제로 close() 뒤에 write(65)를 해도 정상적으로 "A"가 쌓였다.

    메모리 스트림의 쓸모는 두 가지다. 하나는 시험과 실험이다. 이 회차의 예제 대부분이 파일 대신 ByteArrayInputStream이나 StringReader를 써서, 디스크 없이도 스트림 코드를 그대로 돌릴 수 있었다. 스트림 API가 "어디서 읽느냐"를 추상화한 덕분이다. 다른 하나는 메시지 조립이다. 네트워크로 보낼 메시지를 DataOutputStream + ByteArrayOutputStream으로 먼저 만들어 두면 전체 길이를 알 수 있으므로, 길이를 앞에 붙여 한 번에 보낼 수 있다.

    writeInt, writeInt, writeBoolean, writeUTF, writeDouble이 만든 23바이트가 어떤 순서와 경계로 놓이는지 보여 준다. 가로로 긴 한 줄의 바이트 칸 23개. 각 칸 안에 16진수 값: "00" "00" "00" "01" | "FF" "FF" "FF" "FE" | "01" | "00" "04" "41" "EA" "B0" "80" | "3F" "F8" "00" "00" "00" "00" "00" "00". 구간마다 다른 옅은 배경색을 칠하고, 위쪽 중괄호에 라벨: "writeInt(1)", "writeInt(-2)", "writeBoolean(true)", "writeUTF(\"A가\")", "writeDouble(1.5)". writeUTF 구간은 아래쪽에 작은 중괄호 두 개로 다시 나눠 "길이 2바이트"와 "내용 4바이트" 라벨을 붙인다. 첫 구간의 첫 칸 위에 작은 화살표와 "높은 자리부터" 라벨. 오른쪽 끝에 "총 23바이트" 라벨. 평평한 벡터 스타일, 흰 배경. 바이트에는 타입 정보가 없다. 읽는 쪽이 같은 순서로 같은 메서드를 불러야 같은 값이 나온다.

    흔한 오해와, 이 지식이 다시 쓰이는 곳

    이 회차의 내용을 틀리기 쉬운 믿음의 형태로 다시 정리하자. 각 항목은 앞의 실험 중 하나로 반박된다.

    • "UTF-8 파일이니 조각마다 new String(buf, 0, n, UTF_8)을 해도 된다." 조각 경계가 문자 중간에 걸리는 순간 대체 문자가 생긴다. 버퍼 크기를 3의 배수로 맞춰도 ASCII가 하나 섞이면 경계가 어긋난다. 조각 단위로 읽으려면 상태를 가진 디코더, 곧 InputStreamReader를 써야 한다.
    • "write를 불렀으니 파일에 들어갔다." OutputStreamWriter, BufferedWriter, 자동 flush가 없는 PrintWriter는 모두 내부 버퍼에 쌓아 둔다. 닫거나 flush하지 않고 끝나면 파일은 비어 있다.
    • "리더로 감쌌어도 아래 스트림은 내가 읽은 만큼만 진행했다." 디코더는 버퍼 크기만큼 미리 읽는다. 문자 하나를 읽어도 파일 위치는 8192로 갔다. 감싼 뒤에는 아래 스트림을 직접 읽지 않는다.
    • "BufferedReader는 시스템 콜을 줄이려고 쓴다." OpenJDK 21의 InputStreamReader 위에서는 시스템 콜 횟수가 같았다. 줄어드는 것은 호출마다 붙는 잠금·할당·디코더 진입 비용이다. 쓰기 쪽 BufferedWriter는 아래 호출 횟수도 줄인다.
    • "char 하나가 글자 하나다." 보충 문자는 char 두 개(대리 쌍)다. Reader.read()는 코드 단위를 돌려준다.
    • "FileReader는 UTF-8로 읽는다." 문자 집합 없이 만들면 기본 문자 집합을 쓴다. JDK 18 이상에서는 기본이 UTF-8이지만, JDK 17 이하나 -Dfile.encoding=COMPAT에서는 운영체제와 로캘에 따라 달라진다.
    • "println이 예외 없이 돌아왔으니 기록됐다." PrintStream과 PrintWriter는 I/O 예외를 삼킨다. checkError()로만 알 수 있다.
    • "writeUTF는 UTF-8 바이트를 쓴다." 2바이트 길이 접두어와 수정된 UTF-8이다. 널 문자와 보충 문자에서 표준 UTF-8과 바이트가 다르다.

    이 회차의 내용은 권의 뒤쪽에서 계속 다시 쓰인다. 바로 다음 회차는 지금까지의 스트림을 실제 데이터 저장에 적용하고, 그 다음 회차의 Files는 문자 집합을 주지 않으면 UTF-8을 쓰는 API로 다시 등장한다. 소켓 프로그래밍 회차들에서는 소켓이 주는 InputStream·OutputStream을 DataInputStream·DataOutputStream이나 BufferedReader·PrintWriter로 감싸는데, 이때 TCP가 바이트를 아무 데서나 잘라 전달한다는 사실과 이 회차의 "경계에 걸친 상태" 이야기가 정확히 맞물린다. HTTP 서버를 직접 만드는 회차에서는 readLine으로 요청 줄과 헤더를 읽고, 응답을 CRLF로 쓰고, 헤더 뒤의 본문을 다룰 때 미리 읽기 문제를 피해야 한다.

    이 장의 핵심

    바이트와 문자의 변환은 상태를 가진 일이다. 디코더는 덜 끝난 바이트를, 인코더는 짝을 기다리는 대리 문자를, BufferedReader는 CR 다음의 LF를 기억해야 경계에서 데이터가 깨지지 않는다. 그 상태를 담는 버퍼가 곧 flush해야 하는 이유이고, 미리 읽기의 원인이며, 호출 비용을 줄이는 장치다. 문자 집합은 바이트 안에 적혀 있지 않으므로 언제나 명시하고, 바이트로 된 형식(DataOutputStream)은 쓰는 쪽과 읽는 쪽의 약속으로만 해석된다.
    인코딩과 디코딩의 위치
    자바 안의 문자(String, char)와 바깥의 바이트 사이 변환은 getBytes/new String으로 직접 하거나, 다리 클래스 OutputStreamWriter/InputStreamReader가 스트림 경계에서 한다.
    경계 문제
    UTF-8 문자는 여러 바이트에 걸치므로 조각마다 따로 디코딩하면 경계에 걸린 문자가 대체 문자(U+FFFD)로 바뀐다. 해결하려면 덜 끝난 바이트를 기억하는 상태가 필요하다.
    CharsetDecoder
    decode(in, out, endOfInput)는 덜 끝난 바이트를 입력 버퍼에 남기고 UNDERFLOW로 멈춘다. 새 디코더의 기본 오류 처리는 REPORT, 대체값은 U+FFFD다.
    다리 클래스의 내부 버퍼
    OpenJDK 21에서 StreamDecoder는 8192바이트, StreamEncoder는 512바이트에서 시작해 8192바이트까지 크는 버퍼를 갖는다. 그래서 쓰기는 flush가 필요하고, 읽기는 필요한 것보다 많이 미리 읽는다.
    UTF-8의 올바른 바이트 열
    RFC 3629는 가장 짧은 형식, 대리 영역 금지, U+10FFFF 상한을 바이트 범위로 정한다. OpenJDK 21 디코더는 어긋난 열을 정해진 길이의 오류 단위로 끊고, 단위마다 대체 문자 하나를 넣는다.
    문자 스트림의 잠금(JDK 21)
    클래스가 정확히 InputStreamReader·FileReader일 때(그리고 그것을 감싼 정확한 BufferedReader일 때)는 ReentrantLock 기반 InternalLock을 써서 I/O로 블로킹하는 가상 스레드가 캐리어에 고정되지 않게 하고, 하위 클래스면 호환성을 위해 모니터를 쓴다.
    Reader/Writer 계층
    문자 스트림은 바이트 스트림과 같은 데코레이터 구조다. FileReader/FileWriter는 InputStreamReader/OutputStreamWriter의 하위 클래스이고, 문자 집합을 받는 생성자는 Java 11에 추가됐다.
    기본 문자 집합
    JDK 18(JEP 400)부터 UTF-8이다. -Dfile.encoding=COMPAT는 옛 규칙을 되살리고, 운영체제 쪽 값은 native.encoding으로 본다. System.out은 stdout.encoding을 따른다.
    BufferedReader.readLine
    LF, CR, CRLF, EOF를 줄 끝으로 인정하고 줄 끝 문자를 빼고 돌려준다. 빈 줄은 빈 문자열, 스트림 끝은 null이다. CRLF가 버퍼 경계에서 갈라지면 skipLF 상태로 처리한다.
    PrintStream/PrintWriter
    I/O 예외를 던지지 않고 내부 플래그만 세우며 checkError()로 확인한다. 자동 flush 조건은 두 클래스가 다르다.
    DataOutputStream/DataInputStream
    기본형을 빅 엔디언 이진 형식으로 쓰고 읽는다. writeUTF는 2바이트 길이와 수정된 UTF-8을 쓰며, 읽기 중 끝에 닿으면 EOFException이 난다.

    실무에서 문자 깨짐 장애는 대부분 "어디서 어떤 문자 집합으로 변환했는가"를 끝까지 따라가면 원인이 나온다. 파일이나 응답의 바이트를 16진수로 찍어 보는 것이 출발점이다. EF BF BD가 보이면 앞 단계 어딘가에서 이미 대체 문자로 바뀐 뒤 다시 UTF-8로 저장된 것이고, 이 경우 원래 바이트는 복구할 수 없다. 한글이 2바이트씩 보이면 MS949 계열, 3바이트씩 보이면 UTF-8이다. 화면에서만 깨지고 파일은 멀쩡하다면 stdout.encoding과 터미널 설정을 의심한다. JDK 17 이하에서 JDK 21로 올린 뒤 Windows 서버에서만 문자가 깨지기 시작했다면, 문자 집합 없이 만든 FileReader·FileWriter·InputStreamReader가 JEP 400의 변경을 그대로 받은 것이다. 이때 -Dfile.encoding=COMPAT는 임시 처방이고, 근본 처방은 코드에 문자 집합을 명시하는 것이다.

    대체(REPLACE)와 보고(REPORT) 중 무엇을 고를지는 데이터의 목적지가 결정한다. 사람이 볼 로그 뷰어나 관리 화면이라면 대체가 낫다. 배치 작업이 외부에서 받은 파일을 읽어 DB에 넣는다면 보고가 낫다. 깨진 한 줄이 대체 문자를 품고 DB에 들어가면, 그 데이터는 원본과 비교하지 않는 한 손상을 알아챌 방법이 없다. 이런 경로에서는 Files.newBufferedReader처럼 예외를 던지는 API를 쓰거나 newDecoder()로 만든 디코더를 직접 넘겨, 실패한 파일을 격리하고 원인을 기록하는 쪽이 장기적으로 비용이 적다.

    출력 쪽 판단에서는 "실패를 누가 알아채는가"를 먼저 묻는다. 감사 기록이나 정산 파일처럼 반드시 남아야 하는 출력에 PrintWriter나 PrintStream을 쓰면서 checkError()를 보지 않으면, 디스크가 가득 찬 날의 기록은 조용히 사라진다. 반대로 성능을 볼 때는 각 계층의 버퍼가 실제로 무엇을 줄이는지를 따진다. 줄 단위 텍스트를 대량으로 읽는다면 readLine이 문자 단위 읽기보다 훨씬 싸고, 쓰기에서 작은 write가 많다면 BufferedWriter가 아래 호출 횟수를 직접 줄인다. 다만 측정값은 환경마다 다르므로, 결론을 내기 전에 자기 환경에서 호출 횟수와 시간을 재 보는 것이 맞다.

    1번. "A가나다"의 바이트는 41 | EA B0 80 | EB 82 98 | EB 8B A4로 10바이트다. 첫 조각 6바이트는 41 EA B0 80 EB 82이다. "A"와 "가"는 온전하지만 끝의 EB 82는 "나"의 앞 두 바이트뿐이라 대체 문자 하나가 된다. 결과는 "A가�"(길이 3)다. 둘째 조각 4바이트는 98 EB 8B A4이다. 98은 시작 바이트 없는 이어지는 바이트라 대체 문자가 되고, EB 8B A4는 "다"로 온전히 디코딩된다. 결과는 "�다"(길이 2)이고, 합치면 "A가��다"다. 실제 실행 결과도 같았다. 버퍼가 3의 배수라도 1바이트 문자 "A"가 앞에 있어 모든 3바이트 문자의 시작 위치가 한 칸씩 밀렸다. 경계가 문자와 맞는지는 버퍼 크기가 아니라 데이터 내용에 달려 있으므로, 크기 조정으로는 이 문제를 풀 수 없다.

    2번. [one], [], [two] 세 줄이다. 첫 CRLF가 "one"을 끝내고, 바로 이어지는 CRLF가 빈 줄 하나를 만든다. "two" 뒤의 \r은 CR 줄 끝으로 "two"를 끝낸다. 그다음 readLine은 버퍼를 채우려다 스트림 끝에 닿는데, 문자를 하나도 읽지 못했으므로 빈 문자열이 아니라 null을 돌려준다. Javadoc의 규칙대로 null은 "문자를 하나도 읽지 못한 채 끝에 닿음"이고, 줄 끝 뒤에 아무것도 없으면 그것은 새 줄이 아니다. 실행 결과도 [one][][two]였다.

    3번. 0바이트다. 계층은 PrintWriter → FileWriter(OutputStreamWriter의 하위 클래스, 안에 StreamEncoder와 바이트 버퍼) → FileOutputStream이다. println("시작")의 문자들은 인코딩되어 StreamEncoder의 바이트 버퍼에 머물렀고, 자동 flush를 켜지 않았으므로 아무도 버퍼를 비우지 않았다. JVM은 종료할 때 열린 Writer를 flush해 주지 않는다. 실제로 실행해 크기 0을 확인했다. 고치는 방법은 try-with-resources로 PrintWriter를 닫는 것(close가 flush를 포함하고 안쪽으로 전파된다), 또는 new PrintWriter(writer, true)로 자동 flush를 켜서 println마다 flush되게 하는 것이다. 어느 경우든 PrintWriter는 예외를 삼키므로 중요한 기록이라면 checkError()도 확인한다.

    4번. writeShort(258)은 258 = 0x0102이므로 01 02, writeUTF("가")는 길이 3과 내용으로 00 03 EA B0 80, writeInt(-1)은 FF FF FF FF다. 모두 01 02 00 03 EA B0 80 FF FF FF FF, 11바이트다. 첫 readInt()는 01 02 00 03을 읽어 0x01020003 = 16,777,216 + 131,072 + 3 = 16,908,291이다. 둘째 readInt()는 EA B0 80 FF를 읽는다. 최상위 비트가 1이므로 음수이고, 부호 없이 읽은 값 3,937,435,903에서 2의 32제곱(4,294,967,296)을 빼면 -357,531,393이다. 남은 바이트는 FF FF FF 3개다. 두 값 모두 예외 없이 나온다는 점이 핵심이다. 바이트에는 타입 정보가 없으므로 순서를 틀려도 스트림은 알려 주지 않는다. 이 값들은 실제 실행으로 확인했다.

    5번. InputStreamReader 안의 디코더는 문자를 만들기 위해 아래 스트림에서 버퍼 크기(OpenJDK 21에서 최대 8192바이트)만큼 미리 읽는다. 헤더 몇 줄을 읽는 동안 그 뒤의 본문 바이트도 이미 디코더의 바이트 버퍼, 또는 문자로 바뀌어 BufferedReader의 문자 버퍼에 들어가 있을 수 있다. 그 상태에서 socketIn을 직접 읽으면 리더가 가져가지 않은 그 뒤의 바이트부터 나오므로 본문 앞부분이 사라진다. 본문이 이미 전부 리더 쪽으로 넘어갔다면 소켓에는 더 올 데이터가 없어 readNBytes가 블로킹되어 멈춘다. 감싼 뒤에는 아래 스트림을 직접 읽지 않는다는 규칙을 지키려면, 헤더와 본문을 모두 같은 계층에서 읽거나 헤더를 바이트 단위로 직접 파싱해야 한다.

     UTF-8 파일을 8192바이트 버퍼로 읽으면서 조각마다 new String(buf, 0, n, UTF_8)을 했더니 아주 가끔 한글이 깨진다. 가장 정확한 원인은? UTF-8 디코더가 8192바이트를 넘는 입력을 처리하지 못하기 때문이다. 파일 끝에 BOM이 있어서 마지막 조각이 잘못 해석되기 때문이다. 조각 경계가 여러 바이트로 된 문자 중간에 걸리면, 상태가 없는 new String은 앞뒤 조각을 이어 볼 수 없어 각각을 잘못된 입력으로 판정하기 때문이다. 버퍼 크기가 3의 배수가 아니어서 생기는 문제이므로 8193바이트로 바꾸면 해결된다. 정답은 2번이다. new String은 호출마다 주어진 바이트만 보고 판정하므로 경계에 걸린 문자의 앞부분과 뒷부분이 각각 대체 문자가 된다. 크기 제한(0번)은 없고, BOM(1번)과는 무관하다. 3번은 틀렸다. ASCII 같은 1바이트 문자가 섞이면 경계 위치가 데이터 내용에 따라 달라지므로 어떤 버퍼 크기로도 해결되지 않는다. 해결책은 덜 끝난 바이트를 기억하는 디코더, 곧 InputStreamReader다. OpenJDK 21에서 new InputStreamReader(fileIn, UTF_8)을 만들고 read()를 한 번 호출해 문자 하나를 얻었다. 그 직후 fileIn의 파일 위치에 대한 설명으로 옳은 것은? 문자 하나에 필요한 바이트(1~4바이트)만큼만 나아갔다. 디코더가 바이트 버퍼를 채우려고 미리 읽으므로 필요한 것보다 훨씬 더 나아갔을 수 있다(이 회차의 실험에서는 8192). read()는 버퍼를 쓰지 않으므로 정확히 1바이트 나아갔다. BufferedReader로 감싸지 않았으므로 아직 파일을 읽지 않았다. 정답은 1번이다. Javadoc은 InputStreamReader가 효율적인 변환을 위해 필요한 것보다 많은 바이트를 미리 읽을 수 있다고 적고, OpenJDK 21의 StreamDecoder는 8192바이트 버퍼의 남은 자리만큼 아래 스트림에 요청한다. 실험에서 문자 하나를 읽은 뒤 파일 위치는 8192였다. 그래서 리더로 감싼 뒤에는 아래 스트림을 직접 읽으면 안 된다. JDK 21에서 -Dfile.encoding=COMPAT 옵션으로 실행하면 일어나는 일은? 모든 문자 스트림이 UTF-16을 쓴다. Files.readString처럼 문자 집합을 받지 않는 Files 메서드도 운영체제 문자 집합을 쓰게 된다. System.out의 문자 집합만 운영체제 값으로 바뀐다. 기본 문자 집합이 JDK 17까지의 규칙(운영체제, 로캘 등)으로 정해져 native.encoding과 같아지고, 문자 집합 없이 만든 FileReader 등이 그것을 쓴다. 정답은 3번이다. JEP 400과 System Javadoc에 따르면 COMPAT는 기본 문자 집합을 예전 알고리즘으로 정하고 file.encoding 값을 native.encoding 값으로 바꾼다. 이 회차의 실험에서도 LC_ALL=C에서 COMPAT를 주자 defaultCharset()이 US-ASCII가 됐다. Files의 문자 집합 없는 메서드는 원래부터 UTF-8로 명세되어 있고(1번 오답), System.out은 기본 문자 집합이 아니라 stdout.encoding을 따른다(2번 오답). PrintStream ps = new PrintStream(new FileOutputStream("out.txt"), true, UTF_8)로 기록하던 중 디스크가 가득 찼다. ps.println(...)은 어떻게 동작하는가? 예외를 던지지 않고 내부 오류 플래그만 세운다. 실패 여부는 checkError()로 확인해야 한다. 검사 예외 IOException을 던지므로 호출 쪽에서 반드시 잡아야 한다. 자동 flush가 켜져 있으므로 UncheckedIOException을 던진다. 실패한 내용을 메모리에 보관했다가 공간이 생기면 다시 쓴다. 정답은 0번이다. Javadoc은 PrintStream이 다른 출력 스트림과 달리 IOException을 결코 던지지 않고 내부 플래그를 세우며 checkError로 확인할 수 있다고 적는다. OpenJDK 21 소스에서도 쓰기 경로 전체가 catch (IOException x)로 감싸져 trouble = true로 바뀐다. println의 시그니처에는 throws 절이 없고(1번 오답), 자동 flush는 예외 처리 방식을 바꾸지 않으며(2번 오답), 재시도 기능은 없다(3번 오답). DataOutputStream.writeUTF("\u0000")가 만드는 바이트는? 00 — 표준 UTF-8과 같다. 00 01 00 — 길이 1과 널 바이트 하나. 00 02 C0 80 — 길이 2와, 널 문자를 2바이트로 표현한 수정된 UTF-8. 00 00 00 00 — UTF-16으로 2바이트, 길이 2바이트. 정답은 2번이다. writeUTF는 부호 없는 2바이트 길이 뒤에 수정된 UTF-8을 쓴다. DataInput Javadoc에 따르면 수정된 UTF-8은 널 문자를 2바이트 형식으로 써서 인코딩된 문자열에 0 바이트가 나타나지 않게 한다. 실제로 실행하면 00 02 C0 80이 나왔다. 0번은 표준 UTF-8의 결과이고 길이 접두어도 없다. 1번은 널 문자를 1바이트로 쓴 것이라 수정된 UTF-8의 규칙에 어긋난다.
    문자 스트림(character stream)
    Reader/Writer를 상속하는 스트림. 읽고 쓰는 단위가 char(UTF-16 코드 단위)이며, 바이트와의 변환은 다리 클래스 안의 인코더·디코더가 맡는다.
    다리 클래스(bridge)
    바이트 스트림을 문자 스트림으로 보이게 하는 InputStreamReader와, 문자 스트림을 바이트 스트림 위에 놓는 OutputStreamWriter.
    CharsetDecoder / CharsetEncoder
    ByteBuffer와 CharBuffer 사이를 변환하는 상태 있는 변환기. 결과를 UNDERFLOW, OVERFLOW, malformed, unmappable로 알린다.
    대체 문자(replacement character, U+FFFD)
    디코딩할 수 없는 바이트 대신 넣는 문자. UTF-8로 다시 저장하면 EF BF BD가 되고 원래 바이트는 복구되지 않는다.
    미리 읽기(read-ahead)
    변환 효율을 위해 현재 요청에 필요한 것보다 많은 바이트를 아래 스트림에서 읽어 두는 동작. 감싼 스트림을 직접 읽으면 안 되는 이유다.
    기본 문자 집합(default charset)
    문자 집합을 주지 않은 API가 쓰는 문자 집합. JDK 18부터 UTF-8이며, -Dfile.encoding=COMPAT로 운영체제 기반의 옛 규칙을 쓸 수 있다.
    대리 쌍(surrogate pair)
    U+FFFF를 넘는 보충 문자를 UTF-16에서 표현하는 두 개의 char(상위 대리 0xD800~0xDBFF, 하위 대리 0xDC00~0xDFFF).
    인트린식(intrinsic)
    JVM이 특정 메서드 호출을 자바 바이트코드 대신 자체 구현(전용 IR 노드나 기계어 스텁)으로 바꿔 끼우는 것. @IntrinsicCandidate가 붙은 StringCoding.countPositives가 예다.
    고정(pinning)
    가상 스레드가 블로킹 중에도 캐리어(플랫폼 스레드)에서 내려오지 못하는 상태. JDK 21에서는 synchronized 안이나 네이티브 메서드 실행 중에 일어난다.
    빅 엔디언(big-endian)
    여러 바이트로 된 수를 가장 높은 자리 바이트부터 놓는 순서. DataOutputStream이 쓰는 순서이며 네트워크 바이트 순서라고도 한다.
    수정된 UTF-8(modified UTF-8)
    writeUTF/readUTF와 클래스 파일이 쓰는 변형. 널 문자를 2바이트로, 보충 문자를 대리 쌍 각각 3바이트로 인코딩한다.
