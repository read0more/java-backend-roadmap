    이 회차의 질문: 경로가 늘 때마다 클래스가 늘어나는 서버

    HTTP 서버를 처음 직접 만들면 자연스럽게 도착하는 구조가 있다. 요청 줄에서 경로를 꺼내고, 경로마다 그 요청을 처리할 객체를 하나씩 둔 다음, Map 같은 표에서 경로로 객체를 찾아 실행하는 구조다. 처리 객체가 모두 같은 인터페이스를 구현하므로 서버 본체는 어떤 경로가 있는지 몰라도 된다. 요청을 객체로 다루는 커맨드 패턴(command pattern)의 한 형태이고, 구조 자체는 깔끔하다. 그런데 페이지가 수십 개로 늘어나면 곤란한 점이 드러난다.

    첫째, 경로 하나에 클래스 하나가 생긴다. 회원 목록, 회원 등록 폼, 회원 저장은 같은 저장소를 쓰는 밀접한 기능인데도 세 클래스로 흩어진다. 둘째, 등록이 두 곳에서 일어난다. 클래스를 만들고 나서, 서버를 시작하는 코드에서 다시 경로 문자열과 객체를 짝지어 표에 넣어야 한다. 경로 문자열이 처리 코드와 떨어져 있으니 어느 클래스가 어느 경로를 맡는지 보려면 두 파일을 오가야 한다. 셋째, 모든 처리 메서드의 모양이 service(HttpRequest, HttpResponse)로 고정된다. 요청 객체가 필요 없는 페이지도 요청 객체를 받아야 하고, 요청 파라미터를 꺼내 정수로 바꾸는 코드는 페이지마다 되풀이된다.

    앞의 두 회차가 이 문제를 풀 도구를 준비했다. 11회의 리플렉션(reflection)은 실행 중에 클래스의 메서드 목록을 읽고, 컴파일할 때 이름을 몰랐던 메서드를 호출하게 해 준다. 12회의 애노테이션(annotation)은 소스 코드에 붙인 표시를 클래스 파일에 남겨 실행 중에 읽을 수 있게 해 준다. 둘을 합치면 "경로 문자열을 처리 메서드 바로 위에 적어 두고, 서버가 그 표시를 읽어 경로와 메서드를 연결한다"는 설계가 가능해진다. 스프링 MVC의 @RequestMapping이 하는 일이 바로 이것이다.

    이 회차는 그 설계를 세 단계로 만든다. 먼저 요청마다 컨트롤러의 메서드를 훑어 애노테이션이 붙은 메서드를 찾는 가장 단순한 버전을 만들고(애노테이션 서블릿 1), 메서드가 원하는 인자를 실행 시점에 골라 넣는 동적 바인딩을 더한 뒤(애노테이션 서블릿 2), 요청마다 반복하던 탐색을 시작 시점의 매핑 테이블로 옮겨 성능과 안정성을 함께 얻는다(애노테이션 서블릿 3). 단계마다 JDK 소스와 바이트코드로 내려가 리플렉션 호출이 실제로 무엇을 하는지 확인한다. 그다음 이 작은 프레임워크 위에 회원 관리 서비스를 올리며, 폼 데이터가 바이트 수준에서 어떻게 오가는지, 등록 직후 새로고침 문제와 HTML 이스케이프, 오류 응답을 어떻게 다루는지 본다. 마지막으로 우리가 만든 부품을 스프링 MVC의 부품에 하나씩 대응시킨다.

    예제는 모두 이 글을 위해 새로 쓴 것이다. 출력은 Apple Silicon(arm64) macOS에서 Temurin JDK 21.0.13과 curl 8.7.1로 실행한 결과다. 스레드 이름의 순서처럼 실행마다 달라지는 값은 그렇다고 밝힌다. 소켓, 스레드 풀, HTTP 메시지 형식의 기초는 앞 회차(06~10회)의 몫이므로 여기서는 이 회차에 필요한 만큼만 다시 정리한다.

    이 장의 핵심

    애노테이션 기반 요청 처리의 본질은 컴파일 시점에 고정되던 호출 관계를 실행 시점의 메타데이터 조회로 바꾸는 것이다. 그 대가로 타입 검사와 오류 발견이 실행 시점으로 밀려나고 조회 비용이 생긴다. 좋은 설계는 이 조회와 검사를 요청마다 하지 않고 서버가 시작할 때 한 번에 끝내, 요청을 처리하는 동안에는 미리 만든 표를 읽기만 하게 만든다.

    출발점: 이 회차에서 쓰는 작은 HTTP 서버

    애노테이션 서블릿을 올릴 바탕부터 정리한다. 서버의 부품은 다섯 개다. 요청 메시지를 해석하는 HttpRequest, 응답을 모았다가 한 번에 보내는 HttpResponse, 요청 하나를 처리하는 계약인 HttpServlet, 연결 하나를 맡아 실행되는 HttpRequestHandler, 연결을 받아 스레드 풀에 넘기는 HttpServer다. 모든 클래스는 같은 패키지에 두고, 지면을 아끼려고 import 문은 생략한다.

public interface HttpServlet {
    void service(HttpRequest request, HttpResponse response) throws IOException;
}

    요청 해석기는 요청 줄, 헤더, 본문을 차례로 읽는다. 이 클래스에서 가장 중요한 결정은 모든 것을 바이트 단위로 읽는다는 것이다.

    // HttpRequest.java
public class HttpRequest {
    private final String method;
    private final String path;
    private final Map headers = new HashMap<>();
    private final Map parameters = new HashMap<>();

    public HttpRequest(InputStream in) throws IOException {
        String requestLine = readLine(in);               // 예: POST /members/add HTTP/1.1
        if (requestLine == null || requestLine.isEmpty()) {
            throw new IOException("요청 줄이 없다");
        }
        String[] parts = requestLine.split(" ");
        if (parts.length != 3) {
            throw new IOException("요청 줄 형식 오류: " + requestLine);
        }
        method = parts[0];
        String target = parts[1];
        int q = target.indexOf('?');
        path = (q < 0) ? target : target.substring(0, q);
        if (q >= 0) {
            parseParameters(target.substring(q + 1));     // 쿼리 스트링
        }

        String line;
        while ((line = readLine(in)) != null && !line.isEmpty()) {   // 빈 줄 = 헤더 끝
            int colon = line.indexOf(':');
            if (colon < 0) {
                throw new IOException("헤더 형식 오류: " + line);
            }
            headers.put(line.substring(0, colon).trim().toLowerCase(),
                        line.substring(colon + 1).trim());
        }

        String length = headers.get("content-length");
        if (length != null) {
            byte[] body = in.readNBytes(Integer.parseInt(length)); // 바이트 수만큼 읽는다
            String type = headers.getOrDefault("content-type", "");
            if (type.startsWith("application/x-www-form-urlencoded")) {
                parseParameters(new String(body, StandardCharsets.US_ASCII));
            }
        }
    }

    // CR LF로 끝나는 한 줄을 바이트 단위로 읽는다
    private static String readLine(InputStream in) throws IOException {
        ByteArrayOutputStream buf = new ByteArrayOutputStream();
        int b;
        while ((b = in.read()) != -1 && b != '\n') {
            if (b != '\r') {
                buf.write(b);
            }
        }
        if (b == -1 && buf.size() == 0) {
            return null;
        }
        return buf.toString(StandardCharsets.ISO_8859_1);
    }

    private void parseParameters(String encoded) {
        for (String pair : encoded.split("&")) {          // 먼저 나누고
            if (pair.isEmpty()) continue;
            int eq = pair.indexOf('=');
            String key = (eq < 0) ? pair : pair.substring(0, eq);
            String value = (eq < 0) ? "" : pair.substring(eq + 1);
            parameters.put(URLDecoder.decode(key, StandardCharsets.UTF_8),   // 나중에 디코딩한다
                           URLDecoder.decode(value, StandardCharsets.UTF_8));
        }
    }

    public String getMethod() { return method; }
    public String getPath() { return path; }
    public String getHeader(String name) { return headers.get(name.toLowerCase()); }
    public String getParameter(String name) { return parameters.get(name); }
}

    왜 바이트 단위인가. HTTP/1.1 메시지 문법을 정한 RFC 9112의 2.2절은 수신자가 메시지를 US-ASCII의 상위 집합인 인코딩의 옥텟(octet, 8비트 바이트) 열로 해석해야 한다고 요구한다. 요청 줄과 헤더는 문자가 아니라 바이트로 정의되어 있다는 뜻이다. readLine은 줄바꿈 바이트(\n)가 나올 때까지 바이트를 모으고, 모은 바이트를 ISO-8859-1로 문자열로 바꾼다. ISO-8859-1은 바이트 하나를 문자 하나(U+0000~U+00FF)로 그대로 옮기므로 어떤 바이트가 와도 디코딩이 실패하지 않고, ASCII 범위에서는 US-ASCII와 결과가 같다.

    문자 스트림을 쓰면 편해 보인다. new BufferedReader(new InputStreamReader(in, UTF_8))로 감싸 readLine()을 부르면 헤더 읽기는 한 줄로 끝난다. 문제는 본문이다. OpenJDK 21 소스를 보면 InputStreamReader 안의 디코더(sun.nio.cs.StreamDecoder)는 소켓에서 최대 8,192바이트(DEFAULT_BYTE_BUFFER_SIZE)를 한 번에 미리 읽고, BufferedReader는 최대 8,192문자(DEFAULT_CHAR_BUFFER_SIZE)를 미리 디코딩해 쌓아 둔다. 헤더를 다 읽은 시점에 본문 바이트는 이미 리더의 버퍼 안에 문자로 바뀌어 들어가 있을 수 있다. 그러니 본문만 원래 InputStream에서 바이트로 읽겠다고 방향을 바꾸면 앞부분을 잃는다. 그렇다고 본문까지 리더로 읽으면, RFC 9112 6.3절이 "본문 길이를 옥텟으로" 정한 Content-Length와 리더가 세는 문자 수가 어긋난다. 본문에 한글 같은 멀티바이트 문자가 있으면 바이트 수만큼 문자를 읽으려다 영원히 기다리거나 다음 데이터를 잘못 먹는다. 헤더와 본문을 같은 바이트 스트림에서 읽으면 두 문제가 함께 사라진다.

    대신 바이트 단위 읽기에는 비용 함정이 있다. 소켓의 원래 입력 스트림에 read()를 한 바이트씩 부르면 바이트마다 네이티브 읽기 호출이 일어난다. 02~03회에서 본 버퍼링이 여기서 필요하다. 아래 처리기는 소켓 스트림을 BufferedInputStream으로 감싸서 넘긴다. 그러면 read() 대부분은 자바 힙의 내부 배열에서 바로 돌아오고, 본문을 읽는 readNBytes도 같은 버퍼 객체를 거치므로 헤더를 읽다가 미리 당겨 온 본문 바이트를 잃지 않는다. 한 가지 더, readNBytes(n)은 n바이트를 다 읽거나 스트림이 끝날 때까지 블로킹한다. 헤더에 적힌 것보다 본문을 적게 보내고 연결을 붙잡아 두는 클라이언트를 만나면 스레드가 그 자리에서 기다린다. 실제 서버는 08회에서 다룬 setSoTimeout으로 읽기 시간에 상한을 두고, 본문 크기에도 상한을 둔다. 이 회차의 서버는 원리를 보이는 데 집중하려고 둘 다 생략했다.

    // HttpResponse.java
public class HttpResponse {
    private final OutputStream out;
    private int status = 200;
    private final Map headers = new LinkedHashMap<>();
    private final StringBuilder body = new StringBuilder();

    public HttpResponse(OutputStream out) {
        this.out = out;
        headers.put("Content-Type", "text/html; charset=UTF-8");
    }

    public void setStatus(int status) { this.status = status; }
    public void setHeader(String name, String value) { headers.put(name, value); }
    public void write(String text) { body.append(text); }

    public void redirect(String location) {           // POST 처리 후 GET으로 보낸다
        status = 303;
        headers.put("Location", location);
    }

    public void error(int status, String message) {    // 쓰던 본문을 버리고 오류로 바꾼다
        this.status = status;
        headers.remove("Location");
        body.setLength(0);
        body.append("
    ").append(status).append(' ').append(reason(status)).append("
    ")
            .append("
    ").append(Html.escape(message)).append("
    ");   // Html은 뒤에서 본다
    }

    public void flush() throws IOException {
        byte[] bytes = body.toString().getBytes(StandardCharsets.UTF_8);
        StringBuilder head = new StringBuilder();
        head.append("HTTP/1.1 ").append(status).append(' ').append(reason(status)).append("\r\n");
        headers.forEach((k, v) -> head.append(k).append(": ").append(v).append("\r\n"));
        head.append("Content-Length: ").append(bytes.length).append("\r\n");   // 글자 수가 아니라 바이트 수
        head.append("Connection: close\r\n");
        head.append("\r\n");
        out.write(head.toString().getBytes(StandardCharsets.ISO_8859_1));
        out.write(bytes);
        out.flush();
    }

    private static String reason(int status) {
        return switch (status) {
            case 200 -> "OK";
            case 303 -> "See Other";
            case 400 -> "Bad Request";
            case 404 -> "Not Found";
            default -> "Internal Server Error";
        };
    }
}

    응답 객체는 본문을 StringBuilder에 모아 두었다가 flush()에서 한 번에 보낸다. 이렇게 하면 컨트롤러가 본문을 쓰던 도중에 예외가 나도 아직 한 바이트도 나가지 않았으므로, error()로 상태 코드와 본문을 통째로 바꿀 수 있다. 서블릿 컨테이너에는 이 시점을 가리키는 커밋(commit)이라는 개념이 있다. 응답의 첫 바이트가 클라이언트로 나가면 응답이 커밋되고, 그 뒤로는 상태 코드와 헤더를 바꿀 수 없다. Jakarta Servlet의 HttpServletResponse.sendError Javadoc은 응답이 이미 커밋되었으면 이 메서드가 IllegalStateException을 던진다고 적고 있다. 우리 서버는 flush() 전에는 절대 커밋하지 않는 단순한 정책을 택했고, 그 대가로 응답 본문 전체를 메모리에 들고 있다.

    Content-Length에는 UTF-8로 인코딩한 바이트 배열의 길이를 넣는다. 뒤에서 볼 홈 화면의 본문은 자바 문자열로는 102글자지만 UTF-8로는 120바이트다. 한글 음절 하나가 3바이트이기 때문이다(01회). 여기에 String.length()를 넣으면 클라이언트는 102바이트까지만 본문으로 읽고 나머지를 버린다. 잘린 지점이 한글 한 글자의 3바이트 중간이면 마지막 글자는 깨진다. 헤더 줄은 ASCII만 쓰므로 ISO-8859-1로 바이트로 바꾼다. Connection: close는 RFC 9112 9.6절이 정한 연결 옵션으로, 응답을 마치면 송신자가 연결을 닫겠다는 신호다. 연결 하나에 요청 하나만 처리하므로 지속 연결(keep-alive)의 복잡함은 없지만, 요청마다 TCP 연결 수립 비용을 새로 치른다.

    // HttpRequestHandler.java — 연결 하나를 맡는 작업
public class HttpRequestHandler implements Runnable {
    private final Socket socket;
    private final HttpServlet servlet;

    public HttpRequestHandler(Socket socket, HttpServlet servlet) {
        this.socket = socket;
        this.servlet = servlet;
    }

    @Override
    public void run() {
        try (socket;
             InputStream in = new BufferedInputStream(socket.getInputStream());
             OutputStream out = new BufferedOutputStream(socket.getOutputStream())) {
            HttpRequest request = new HttpRequest(in);
            HttpResponse response = new HttpResponse(out);
            System.out.println("[" + Thread.currentThread().getName() + "] "
                    + request.getMethod() + " " + request.getPath());
            try {
                servlet.service(request, response);
            } catch (PageNotFoundException e) {
                response.error(404, e.getMessage());
            } catch (BadRequestException e) {
                response.error(400, e.getMessage());
            } catch (Exception e) {
                e.printStackTrace();                         // 자세한 내용은 서버 로그에만
                response.error(500, "서버 내부 오류");
            }
            response.flush();
        } catch (IOException e) {
            System.out.println("[연결 오류] " + e);
        }
    }
}

// HttpServer.java — 연결을 받아 스레드 풀에 넘긴다
public class HttpServer {
    private final int port;
    private final HttpServlet servlet;
    private final ExecutorService pool = Executors.newFixedThreadPool(10);

    public HttpServer(int port, HttpServlet servlet) {
        this.port = port;
        this.servlet = servlet;
    }

    public void start() throws IOException {
        ServerSocket serverSocket = new ServerSocket(port);
        System.out.println("서버 시작 port: " + port);
        while (true) {
            Socket socket = serverSocket.accept();
            pool.execute(new HttpRequestHandler(socket, servlet));
        }
    }
}

    try (socket; ...)는 Java 9부터 쓸 수 있는 형태로, 이미 있는 final 또는 사실상 final인 변수를 자원으로 등록한다. 자원은 선언의 역순으로 닫히므로 출력 스트림(버퍼를 비운다), 입력 스트림, 소켓 순으로 정리된다. 처리기는 서블릿이 던진 예외의 타입을 보고 상태 코드를 정한다. PageNotFoundException은 404, BadRequestException은 400, 나머지는 500이다. 이 구조는 컨트롤러에서 던진 예외가 원래 타입 그대로 여기까지 올라와야만 제대로 동작한다. 리플렉션 호출은 예외를 다른 예외로 감싸므로, 뒤에서 이 감싸기를 벗겨 내는 코드를 따로 쓰게 된다.

    작업을 넘길 때 submit이 아니라 execute를 쓴 이유도 예외와 관련이 있다. submit은 작업을 FutureTask로 감싸는데, OpenJDK의 FutureTask.run은 작업에서 나온 Throwable을 잡아 결과 자리에 저장해 둔다. 누군가 Future.get()을 불러야 그 예외가 다시 던져지는데, 이 서버에는 get()을 부르는 코드가 없으므로 예외가 흔적 없이 사라진다. execute로 넘긴 작업의 예외는 스레드의 처리되지 않은 예외 처리기까지 올라가 표준 오류에 찍힌다.

    기다림이 일어나는 곳도 정리해 두자. Executors.newFixedThreadPool(10)은 OpenJDK 21에서 스레드 10개와 크기 제한 없는 LinkedBlockingQueue를 가진 ThreadPoolExecutor를 만든다. 열한 번째 연결은 accept()로 이미 받아들여진 상태에서 작업 큐에 들어가 스레드가 빌 때까지 기다린다. 그 앞 단계에도 대기열이 있다. 운영체제가 들어온 연결 요청을 accept()가 꺼내 갈 때까지 쌓아 두는 대기열이고, ServerSocket(int port) 생성자의 Javadoc은 이 대기열 길이(backlog)를 50으로 정한다고 적고 있다(06~07회). 이 회차의 애노테이션 서블릿은 모두 이 서버 위에서 HttpServlet 하나로 끼워진다.

    애노테이션 서블릿 1 — 경로를 메서드 위에 적는다

    먼저 경로를 적을 애노테이션을 정의한다. 메서드 위에만 붙일 수 있고, 실행 중에 리플렉션으로 읽을 수 있어야 한다.

    // Mapping.java
@Retention(RetentionPolicy.RUNTIME)   // 클래스 파일에 남기고 실행 중에도 읽을 수 있게
@Target(ElementType.METHOD)           // 메서드에만 붙일 수 있다
public @interface Mapping {
    String value();                   // @Mapping("/hello")처럼 값만 적을 수 있다
}

    요소 이름을 value로 지었기 때문에 @Mapping(value = "/hello") 대신 @Mapping("/hello")로 줄여 쓸 수 있다. 이제 컨트롤러는 평범한 클래스다. 어떤 인터페이스도 구현하지 않고, 처리 메서드 위에 경로를 적을 뿐이다. 첫 번째 버전은 모든 처리 메서드가 (HttpRequest, HttpResponse)를 받는다고 약속한다.
