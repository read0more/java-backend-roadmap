    이 회차의 질문: 파일의 내용이 아니라 파일 그 자체

    앞의 세 회차는 파일의 내용을 다뤘다. FileInputStream에 이름을 넘겨 파일을 열고, 바이트를 읽고 쓰고, 버퍼로 시스템 콜 횟수를 줄이고, 문자는 인코딩을 거쳐 바이트로 바꾸고, 객체는 직렬화 형식으로 바꿔 저장했다. 그런데 파일을 다루는 프로그램이 묻는 질문의 상당수는 내용과 상관이 없다. 이 이름의 파일이 있는가, 파일인가 디렉터리인가, 크기는 얼마이고 언제 바뀌었는가, 이름을 바꾸거나 다른 디렉터리로 옮기려면 어떻게 하는가, 디렉터리 안에 무엇이 있는가, 그리고 "data/members.txt"라는 상대 경로는 도대체 어디를 기준으로 한 경로인가.

    자바는 이 질문들에 두 번 답했다. 첫 번째 답은 JDK 1.0부터 있던 java.io.File이다. 두 번째 답은 Java 7에 들어온 java.nio.file 패키지(흔히 NIO.2라고 부른다)의 Path와 Files다. 두 번째 답이 나온 이유는 첫 번째 답의 설계에 고칠 수 없는 한계가 있었기 때문이고, 그 한계는 운영체제가 파일을 어떻게 다루는지를 알면 자연스럽게 보인다. 그래서 이 회차는 자바 API보다 한 층 아래, 운영체제가 보는 파일부터 시작한다.

    순서는 이렇다. 먼저 유닉스 계열 파일 시스템에서 이름과 실체가 어떻게 나뉘어 있는지 실험으로 확인한다. 그다음 File의 기본 기능을 각 메서드가 부르는 시스템 콜과 함께 살펴보고, File이 실패를 다루는 방식의 문제를 본다. 이어서 Path와 Files가 그 문제를 어떻게 풀었는지, 존재 확인과 이름 바꾸기에 숨은 경쟁 조건은 무엇인지 본다. 후반부에서는 경로 표시(절대·상대·정규·실제 경로), Files로 문자 파일을 읽는 세 가지 방법, 그리고 파일 복사를 빠르게 만드는 방법이 커널 안에서 무엇을 하는지 OpenJDK 21의 소스로 추적한다.

    이 회차의 실행 결과는 모두 macOS(APFS 파일 시스템)에서 Temurin OpenJDK 21.0.13으로 직접 돌려 얻었다. 운영체제에 따라 달라지는 부분, 특히 파일 복사 경로는 리눅스와 macOS를 나눠 적는다. Windows는 이 회차의 실험 범위에 넣지 않았다.

    한 층 아래: 운영체제에게 파일은 이름과 실체로 나뉜다

    유닉스 계열 파일 시스템에서 "파일"이라는 말은 두 가지를 가리킨다. 하나는 데이터와 메타데이터를 가진 실체이고, 다른 하나는 그 실체를 가리키는 이름이다. 실체를 inode(index node)라고 부른다. inode에는 파일 종류(일반 파일, 디렉터리, 심볼릭 링크 등), 권한 비트, 소유자, 크기, 수정 시각, 링크 수(link count), 그리고 데이터가 디스크의 어디에 있는지가 들어 있다. 눈여겨볼 점은 inode 안에 이름이 없다는 것이다.

    이름은 디렉터리가 갖고 있다. 디렉터리는 특별한 종류의 파일이고, 그 내용은 "이름 → inode 번호" 쌍의 목록, 즉 디렉터리 엔트리(directory entry)의 표다. 그래서 하나의 inode를 두 디렉터리 엔트리가 가리킬 수 있다. 이것이 하드 링크(hard link)다. inode의 링크 수는 자신을 가리키는 이름이 몇 개인지를 센다. 파일을 "삭제"하는 시스템 콜의 이름이 delete가 아니라 unlink인 이유가 여기에 있다. 이 호출은 디렉터리에서 이름 하나를 떼어 내고 링크 수를 하나 줄일 뿐이다.

    macOS의 APFS는 내부 자료 구조가 전통적인 유닉스 파일 시스템과 다르다. 하지만 stat 시스템 콜로 보이는 모습, 즉 장치 번호, inode 번호, 링크 수는 같은 모델을 따른다. 자바도 이 모델 위에서 동작하므로 실험으로 확인할 수 있다. 아래 예제는 a.txt를 만들고 같은 inode에 b.txt라는 두 번째 이름을 붙인 다음, 이름을 하나씩 지운다. "unix:nlink", "unix:ino" 같은 속성 이름은 리눅스와 macOS의 기본 파일 시스템이 제공하는 unix 속성 뷰에서 읽는다.

    import java.io.*;
import java.nio.file.*;

public class LinkMain {
    public static void main(String[] args) throws IOException {
        Path a = Path.of("a.txt");
        Path b = Path.of("b.txt");
        Files.deleteIfExists(a);
        Files.deleteIfExists(b);
        Files.writeString(a, "hello");
        Files.createLink(b, a);                 // b를 a와 같은 파일을 가리키는 두 번째 이름으로

        System.out.println("isSameFile = " + Files.isSameFile(a, b));
        System.out.println("nlink = " + Files.getAttribute(a, "unix:nlink"));
        System.out.println("same ino = " + Files.getAttribute(a, "unix:ino").equals(Files.getAttribute(b, "unix:ino")));

        Files.delete(a);                        // 이름 하나를 지운다
        System.out.println("after delete a: exists a = " + Files.exists(a) + ", b = " + Files.readString(b));

        try (InputStream in = new FileInputStream("b.txt")) {
            Files.delete(b);                    // 마지막 이름까지 지운다
            System.out.println("after delete b: exists b = " + Files.exists(b));
            System.out.println("still readable = " + new String(in.readAllBytes()));
        }
    }
}
    isSameFile = true
nlink = 2
same ino = true
after delete a: exists a = false, b = hello
after delete b: exists b = false
still readable = hello

    한 줄씩 보자. Files.createLink(b, a)는 link 시스템 콜로 이어져 디렉터리에 b.txt → (a.txt와 같은 inode) 엔트리를 추가한다. 내용을 복사하지 않으므로 두 이름의 inode 번호가 같고 링크 수는 2가 된다. Files.delete(a) 뒤에도 b.txt를 읽으면 hello가 나온다. 지워진 것은 이름 하나이고 실체는 그대로이기 때문이다.

    마지막 블록이 더 흥미롭다. b.txt를 스트림으로 연 상태에서 마지막 이름까지 지웠다. 이름이 사라졌으니 exists는 false다. 그런데 이미 열린 스트림으로는 여전히 내용을 읽을 수 있다. POSIX의 unlink 명세는 링크 수가 0이 되어도 열린 파일 디스크립터로 참조하는 프로세스가 있으면 내용의 제거를 "그런 참조가 없어질 때까지 미룬다"고 정한다. 파일을 열면 프로세스는 이름이 아니라 커널 안의 열린 파일 객체를 손에 쥔다. 자바의 FileInputStream이 안에 들고 있는 FileDescriptor가 바로 그 손잡이의 번호다. 이 규칙은 운영 환경에서 자주 마주친다. 프로세스가 쓰고 있는 거대한 로그 파일을 rm으로 지워도 디스크 공간이 돌아오지 않는 현상은, 이름은 지워졌지만 실체가 열린 디스크립터에 붙들려 있기 때문이다.

    이름은 디렉터리 엔트리에 있고 실체는 inode에 있으며, 두 이름과 하나의 열린 디스크립터가 같은 inode를 가리키는 모습을 보여 준다. 가로로 긴 개념도. 왼쪽 위에 표 모양 상자 "디렉터리 엔트리"가 있고 두 행 "a.txt"와 "b.txt"가 적혀 있다. 왼쪽 아래에 작은 표 상자 "파일 디스크립터 표"가 있고 한 행 "fd 3"이 있다. 가운데에 큰 둥근 사각형 "inode"가 있고 안에 세 줄 "크기", "링크 수: 2", "권한·시각"이 적혀 있다. 오른쪽에 디스크 모양 아이콘 "데이터 블록"이 있다. 화살표: "a.txt" 행에서 inode로, "b.txt" 행에서 inode로, "fd 3" 행에서 inode로(점선, 라벨 "열린 파일"), inode에서 데이터 블록으로. inode 상자 위쪽에 작은 말풍선 "이름은 여기에 없다". 왼쪽 위 표 옆에 작은 라벨 "unlink는 행 하나를 지운다". 평평한 벡터 스타일, 흰 배경, 요소마다 옅은 다른 색. 이름(디렉터리 엔트리)과 실체(inode)는 따로 있다. 마지막 이름이 지워져도 열린 디스크립터가 있으면 실체는 남는다.

    경로 해석(path resolution)도 이 구조에서 나온다. 커널이 /srv/app/data.txt를 열 때는 루트 디렉터리의 엔트리 표에서 srv를 찾아 inode를 얻고, 그것이 디렉터리인지와 탐색 권한(디렉터리의 x 비트)이 있는지 확인한 뒤, 그 디렉터리의 엔트리 표에서 app을 찾는 식으로 한 칸씩 내려간다. 상대 경로는 출발점만 다르다. 루트가 아니라 프로세스의 현재 작업 디렉터리(current working directory)에서 출발한다. 중간에 심볼릭 링크를 만나면 링크에 적힌 경로로 갈아탄다. 이 회차 후반의 경로 표시 이야기는 전부 이 해석 과정을 자바가 어디까지 흉내 내고 어디서부터 커널에 맡기는지의 이야기다.

    File 클래스: 경로 이름을 담은 불변 객체

    java.io.File의 Javadoc은 이 클래스를 파일과 디렉터리 경로 이름의 추상 표현(abstract pathname)이라고 소개한다. 이름에 "File"이 들어 있지만 File 객체는 파일이 아니다. 경로 문자열을 운영체제에 맞게 다듬어 담은 값이고, Javadoc은 이 객체가 불변(immutable)이라고, 즉 한번 만들면 나타내는 경로가 바뀌지 않는다고 명시한다. 그래서 new File("temp/example.txt")는 디스크에 아무 일도 일으키지 않는다. 파일 시스템에 손을 대는 것은 이 객체의 메서드를 부를 때다.

    아래 예제는 File의 대표 기능을 차례로 부른다. 실행하기 전에 작업 디렉터리에 temp 디렉터리를 하나 만들어 두었다.

    import java.io.File;
import java.io.IOException;
import java.util.Date;

public class FileMain {
    public static void main(String[] args) throws IOException {
        File file = new File("temp/example.txt");
        File directory = new File("temp/exampleDir");

        System.out.println("file.exists() = " + file.exists());

        boolean created = file.createNewFile();
        System.out.println("createNewFile = " + created);

        boolean dirCreated = directory.mkdir();
        System.out.println("mkdir = " + dirCreated);

        System.out.println("isFile = " + file.isFile());
        System.out.println("isDirectory = " + directory.isDirectory());
        System.out.println("getName = " + file.getName());
        System.out.println("length = " + file.length());

        File renamed = new File("temp/newExample.txt");
        boolean ok = file.renameTo(renamed);
        System.out.println("renameTo = " + ok);
        System.out.println("old exists = " + file.exists() + ", new exists = " + renamed.exists());

        long lastModified = renamed.lastModified();
        System.out.println("lastModified = " + new Date(lastModified));

        System.out.println("delete = " + renamed.delete());
        System.out.println("delete dir = " + directory.delete());
    }
}

    결과는 예상대로다. 흥미로운 것은 각 메서드가 운영체제에 무엇을 요청하는가다. OpenJDK 21에서 유닉스 계열의 File 메서드는 java.io.UnixFileSystem을 거쳐 네이티브 코드(UnixFileSystem_md.c)로 내려간다. 그 코드를 읽으면 대응 관계가 다음과 같다.

    createNewFile과 mkdir에 넘기는 권한 0666, 0777은 최종 권한이 아니다. 커널은 프로세스의 umask로 이 값을 걸러 낸다. umask가 흔히 쓰는 022라면 파일은 644(소유자만 쓰기), 디렉터리는 755가 된다. 그리고 exists, isFile, length를 연달아 부르면 stat이 세 번 일어난다는 점도 기억해 두자. 시스템 콜 비용 문제이기도 하지만, 그보다 세 호출 사이에 다른 프로세스가 파일을 바꿀 수 있다는 점이 더 중요하다. 뒤에서 BasicFileAttributes를 볼 때 다시 다룬다.

    같은 프로그램을 temp 디렉터리가 없는 곳에서 실행하면 결과가 달라진다.

    open이 부모 디렉터리 temp를 찾지 못해 ENOENT 오류를 냈고, createNewFile은 이것을 IOException으로 바꿨다. 그런데 메시지를 보자. "No such file or directory"는 운영체제의 오류 문자열 그대로이고, 어느 경로가 없는지는 들어 있지 않다. 이 파일 하나만 다루는 예제에서는 문제가 없지만, 경로 수십 개를 다루는 배치 작업의 로그에 이 한 줄만 남으면 원인을 찾기 어렵다. 그나마 createNewFile은 예외라도 던진다. 대부분의 File 메서드는 그러지 않는다.

    File이 실패를 다루는 방식: false, 0, null

    실패하는 상황을 일부러 만들어 보자. 이미 있는 디렉터리를 다시 만들고, 비어 있지 않은 디렉터리를 지우고, 없는 파일을 지우고, 부모가 없는 디렉터리를 만들고, 파일에 대고 목록을 달라고 하고, 없는 디렉터리로 이름을 바꾼다.

    false가 일곱 번 나왔다. 그런데 이 일곱 개의 false는 원인이 모두 다르다. mkdir 2와 createNewFile again은 이미 있어서(EEXIST), delete box는 디렉터리가 비어 있지 않아서(ENOTEMPTY), delete ghost는 대상이 없어서(ENOENT), mkdir deep과 rename to missing dir은 경로 중간의 디렉터리가 없어서(ENOENT) 실패했다. 커널은 실패할 때마다 errno에 정확한 오류 번호를 남겼다. 하지만 네이티브 코드는 성공 여부만 보고 JNI_FALSE를 돌려주며, 오류 번호는 거기서 버려진다. 호출한 쪽은 "실패했다"는 사실 말고는 아무것도 알 수 없다. 권한이 없어서 실패했는지, 디스크가 가득 찼는지, 대상이 없었는지 구별할 수 없으니 적절한 복구 동작도 고를 수 없다.

    반환값이 false가 아닌 경우도 문제다. 없는 파일의 length()는 0이다. 크기가 0인 빈 파일과 구별되지 않는다. 디렉터리의 length()는 0보다 큰 값이 나왔지만, Javadoc은 경로가 디렉터리를 가리킬 때의 반환값이 명세되지 않았다(unspecified)고 적는다. 그리고 파일에 대고 list()를 부르면 빈 배열이 아니라 null이 나온다. Javadoc에 따르면 디렉터리가 아니거나 I/O 오류가 나면 null이다. 결과를 바로 for-each 문에 넣는 코드는 여기서 NullPointerException으로 죽고, 그 예외는 진짜 원인과 아무 관련 없는 줄을 가리킨다.

    renameTo의 Javadoc은 이 메서드의 동작이 본질적으로 플랫폼에 의존한다고 밝힌다. 다른 파일 시스템으로는 옮기지 못할 수 있고, 원자적이지 않을 수 있고, 대상 이름의 파일이 이미 있으면 실패할 수 있으니 반환값을 반드시 확인하라는 것이다. 문서가 스스로 "결과를 믿지 말고 확인하라"고 말하는 API는 쓰는 쪽에 부담을 넘긴다. 이 밖에도 File에는 심볼릭 링크를 링크 자체로 다루는 방법이 없고, 소유자나 권한 비트 같은 속성을 읽을 방법이 제한적이며, list()는 디렉터리의 모든 이름을 한 번에 배열로 만든다. Javadoc도 list() 설명에서 아주 큰 디렉터리라면 Files.newDirectoryStream이 자원을 덜 쓸 수 있다고 안내한다.

    File은 폐기 예정(deprecated) 클래스가 아니다. 여전히 많은 API가 File을 받고, file.toPath()(Java 7부터)와 path.toFile()로 서로 바꿀 수 있다. 새 코드에서 파일 시스템 작업을 할 때 Files를 쓰고, File을 요구하는 오래된 API와 만날 때만 변환하면 된다.

    Path와 Files: 주소와 작업을 나눈 설계

    NIO.2는 File이 한 몸에 지고 있던 역할을 셋으로 나눴다. Path는 경로, 즉 주소만 표현한다. Files는 정적 메서드만 모아 둔 클래스로, 주소를 받아 파일 시스템에 작업을 요청한다. 그리고 그 작업을 실제로 수행하는 것은 FileSystemProvider다. Path는 인터페이스이고, 어떤 파일 시스템에 속한 경로인지(getFileSystem())를 안다. Files.delete(path)를 부르면 Files는 그 경로의 파일 시스템에서 provider를 꺼내 provider.delete(path)를 부른다. 즉 Files는 얇은 관문이고, 운영체제별 코드는 provider 안에 있다.

    Path는 Path.of("temp", "a.txt")처럼 만든다. Path.of는 Java 11에 추가됐고, 그 전에는 Paths.get을 썼다. 두 메서드는 같은 일을 하는데, Paths의 Javadoc은 Path.of를 쓰라고 권하며 Paths 클래스가 나중에 폐기될 수 있다고 적어 두었다. 기본 파일 시스템은 FileSystems.getDefault()가 돌려주고, 경로 문자열을 Path.of에 넘기면 이 기본 파일 시스템의 경로가 만들어진다.

    이 분리가 단순한 코드 정리가 아니라는 것은 기본 파일 시스템이 아닌 것을 끼워 보면 드러난다. JDK에는 ZIP 파일을 하나의 파일 시스템처럼 다루는 provider가 들어 있다. 아래 예제는 ZIP 파일 안에 디렉터리와 텍스트 파일을 만들고 다시 읽는데, 쓰는 API는 지금까지와 똑같은 Files다.

    import java.io.IOException;
import java.nio.file.*;
import java.util.Map;
import java.util.stream.Stream;

public class ZipFsMain {
    public static void main(String[] args) throws IOException {
        Path zip = Path.of("archive.zip");
        Files.deleteIfExists(zip);
        try (FileSystem zipfs = FileSystems.newFileSystem(zip, Map.of("create", "true"))) {
            Path inside = zipfs.getPath("/docs/hello.txt");
            Files.createDirectories(inside.getParent());
            Files.writeString(inside, "zip 안의 파일");
            System.out.println("path class = " + inside.getClass().getName());
            System.out.println("provider   = " + zipfs.provider().getScheme());
            System.out.println("read       = " + Files.readString(inside));
        }
        System.out.println("default provider = " + FileSystems.getDefault().provider().getScheme()
                + ", path class = " + Path.of("a.txt").getClass().getName());
        try (FileSystem zipfs = FileSystems.newFileSystem(zip);
             Stream s = Files.walk(zipfs.getPath("/"))) {
            s.forEach(p -> System.out.println("entry: " + p));
        }
    }
}

    같은 Files.writeString 호출이 한 번은 운영체제의 write 시스템 콜로, 한 번은 ZIP 항목의 압축과 기록으로 이어졌다. 기본 파일 시스템의 경로 클래스는 macOS에서 sun.nio.fs.UnixPath이고, ZIP 안의 경로는 jdk.nio.zipfs.ZipPath다. 둘 다 Path를 구현하므로 Files 입장에서는 구별할 필요가 없다. 객체지향에서 말하는 다형성이 파일 시스템 수준에 적용된 것이다. 반대로 Path.toFile()은 기본 provider의 경로에서만 동작하고, 다른 provider의 경로에서 부르면 UnsupportedOperationException을 던진다. ZIP 안의 항목은 운영체제가 아는 파일이 아니므로 File로 나타낼 수 없기 때문이다.

    Files의 정적 메서드가 Path가 속한 파일 시스템의 provider로 요청을 넘기고, provider마다 다른 바닥(운영체제 시스템 콜, ZIP 파일)으로 내려가는 구조를 보여 준다. 세로 계층도. 맨 위에 넓은 상자 "Files (정적 메서드)"가 있고, 그 왼쪽 위에 작은 카드 "Path"가 화살표로 Files에 들어간다. Files 아래로 화살표 "provider()"가 내려가 두 갈래로 나뉜다. 왼쪽 상자 "기본 provider (file)" 아래에 "UnixPath"라는 작은 라벨, 그 아래 상자 "운영체제 시스템 콜"과 아이콘 "디스크". 오른쪽 상자 "ZIP provider (jar)" 아래에 "ZipPath" 라벨, 그 아래 상자 "ZIP 파일 하나". 오른쪽 여백에 세로 괄호로 provider 층을 묶어 "구현은 여기에" 라벨. 평평한 벡터 스타일, 흰 배경, 왼쪽 갈래와 오른쪽 갈래를 서로 다른 옅은 색으로. Files는 관문일 뿐이고, 실제 작업은 Path가 속한 파일 시스템의 provider가 한다.

    Files로 같은 일을 다시 하면: 예외가 원인을 말한다

    앞에서 File로 일부러 실패시킨 작업을 Files로 다시 해 보자. 결과를 비교하기 쉽도록 작업마다 예외를 잡아 클래스 이름과 메시지를 찍는다.

    import java.io.IOException;
import java.nio.file.*;

public class FilesLoud {
    interface Op { void run() throws IOException; }

    static void tryIt(String label, Op op) {
        try {
            op.run();
            System.out.println(label + " -> ok");
        } catch (IOException e) {
            System.out.println(label + " -> " + e.getClass().getSimpleName() + ": " + e.getMessage());
        }
    }

    public static void main(String[] args) {
        Path dir = Path.of("box");
        Path inner = dir.resolve("a.txt");
        tryIt("createDirectory 1", () -> Files.createDirectory(dir));
        tryIt("createDirectory 2", () -> Files.createDirectory(dir));
        tryIt("createFile 1", () -> Files.createFile(inner));
        tryIt("createFile 2", () -> Files.createFile(inner));
        tryIt("delete box", () -> Files.delete(dir));
        tryIt("delete ghost", () -> Files.delete(Path.of("ghost.txt")));
        tryIt("createDirectory deep", () -> Files.createDirectory(Path.of("x/y/z")));
        tryIt("createDirectories deep", () -> Files.createDirectories(Path.of("x/y/z")));
        tryIt("size ghost", () -> Files.size(Path.of("ghost.txt")));
        tryIt("move to missing dir", () -> Files.move(inner, Path.of("nowhere/a.txt")));
        tryIt("list on file", () -> { try (var s = Files.list(inner)) { s.count(); } });
        tryIt("createFile no parent", () -> Files.createFile(Path.of("nodir/b.txt")));
    }
}

    이번에는 실패마다 원인이 예외의 타입으로 드러나고, 메시지에는 문제의 경로가 들어 있다. 이동처럼 경로가 둘인 작업은 두 경로를 화살표로 이어 보여 준다. 이 예외들은 모두 java.nio.file.FileSystemException의 하위 클래스이고, FileSystemException은 getFile(), getOtherFile(), getReason()으로 관련 경로와 사유를 따로 꺼낼 수 있게 한다. 문자열 메시지를 파싱하지 않고도 어떤 경로에서 무슨 일이 있었는지 프로그램이 알 수 있다.

    원인이 살아남는 이유는 provider 구현에 있다. OpenJDK 21의 유닉스 provider는 시스템 콜이 실패하면 오류 번호를 담은 UnixException을 만들고, 이것을 표준 예외로 번역한다. UnixException.translateToIOException의 번역 규칙은 다음과 같다.

    오류 번호 (errno)뜻번역된 예외
    EACCES권한 없음AccessDeniedException
    ENOENT경로의 어떤 구성 요소가 없음NoSuchFileException
    EEXIST이미 있음FileAlreadyExistsException
    ELOOP심볼릭 링크 단계가 너무 많음FileSystemException(사유에 링크 관련 문구 추가)
    그 밖의 값디스크 가득 참 등FileSystemException(사유는 운영체제 오류 문자열)

    작업에 따라 더 구체적인 번역도 있다. 삭제(delete)는 디렉터리가 비어 있지 않아 생긴 EEXIST나 ENOTEMPTY를 DirectoryNotEmptyException으로, 디렉터리 목록 열기는 대상이 디렉터리가 아닐 때 NotDirectoryException으로 바꾼다. 실행 결과의 "createDirectory deep"이 NoSuchFileException: x/y/z라고 나온 것도 이 번역 규칙 때문이다. 없는 것은 x인데 mkdir 시스템 콜이 돌려준 오류는 ENOENT 하나뿐이고, 커널은 경로의 어느 구성 요소가 없었는지 알려 주지 않는다. 그래서 예외 메시지에는 요청한 경로 전체가 들어간다. 메시지의 경로가 "없는 파일"이 아니라 "찾다가 실패한 경로"라는 점을 알고 읽어야 한다.

Javadoc은 이 스트림이 열린 디렉터리에 대한 참조를 갖고 있으며 스트림을 닫아야 디렉터리가 닫힌다고 적는다. 위 예제처럼 try-with-resources로 감싸지 않으면 디렉터리를 연 파일 디스크립터가 작업이 끝난 뒤에도 회수되지 않은 채 남는다. 디스크립터는 프로세스마다 개수 제한이 있는 자원이라, 이런 누수가 쌓이면 어느 순간 파일도 소켓도 열리지 않는 장애로 이어진다.

    존재 확인은 순간의 사진이다: exists, notExists, 그리고 원자적 생성

    Files에는 exists와 함께 notExists라는 메서드가 따로 있다. !exists()면 될 텐데 왜 따로 있을까. 존재 여부를 알 수 없는 경우가 있기 때문이다. 다음 실험은 디렉터리 locked 안에 파일을 만든 뒤 그 디렉터리의 읽기·탐색 권한을 모두 뺀다.

    import java.io.File;
import java.io.IOException;
import java.nio.file.*;

public class LockedMain {
    public static void main(String[] args) throws IOException {
        Path locked = Path.of("locked");
        Files.createDirectories(locked);
        Files.writeString(locked.resolve("secret.txt"), "s");
        new File("locked").setExecutable(false, false);   // 탐색 권한 제거
        new File("locked").setReadable(false, false);     // 읽기 권한 제거

        Path secret = locked.resolve("secret.txt");
        System.out.println("exists = " + Files.exists(secret));
        System.out.println("notExists = " + Files.notExists(secret));
        System.out.println("File.exists = " + new File("locked/secret.txt").exists());
        try {
            Files.size(secret);
        } catch (IOException e) {
            System.out.println(e.getClass().getSimpleName() + ": " + e.getMessage());
        }
        new File("locked").setExecutable(true, false);    // 원상 복구
        new File("locked").setReadable(true, false);
    }
}

File.exists = false
AccessDeniedException: locked/secret.txt

    파일은 분명히 있다. 그러나 커널이 locked/secret.txt를 해석하려면 locked 디렉터리의 엔트리 표를 들여다봐야 하고, 그러려면 그 디렉터리의 탐색 권한이 필요하다. 권한이 없으니 stat은 EACCES로 실패한다. 이때 Files.exists와 Files.notExists는 둘 다 false를 돌려준다. Javadoc은 notExists가 exists의 보수가 아니며, 존재 여부를 판단할 수 없으면 두 메서드 모두 false를 돌려준다고 명시한다. 즉 결과는 셋 중 하나다. 있다(exists가 참), 없다(notExists가 참), 모른다(둘 다 거짓). File.exists는 boolean 하나뿐이라 "모른다"를 "없다"와 구별하지 못한다. 진짜 원인이 필요하면 Files.size처럼 예외를 던지는 메서드를 부르면 된다. AccessDeniedException이 사실을 말해 준다. 이 실험은 루트 권한으로 실행하면 권한 검사를 건너뛰므로 결과가 다르다.

    더 근본적인 문제는 시간이다. Files.exists의 Javadoc은 이 메서드의 결과가 "즉시 낡는다(immediately outdated)"고 적는다. exists가 true를 돌려준 직후 다른 프로세스가 파일을 지울 수 있고, false를 돌려준 직후 다른 스레드가 파일을 만들 수 있다. 확인한 시점과 사용하는 시점 사이의 틈을 노린 결함을 TOCTOU(time-of-check to time-of-use) 경쟁 조건이라고 부른다. 다음 코드는 흔하지만 틀렸다.

    // 틀린 방식: 확인과 생성 사이에 틈이 있다
if (Files.notExists(lockFile)) {
    Files.createFile(lockFile);   // 두 프로세스가 동시에 여기까지 올 수 있다
    // ... 내가 잠금을 얻었다고 믿고 작업한다
}

    두 프로세스가 거의 동시에 notExists를 부르면 둘 다 true를 받는다. 그다음 둘 다 createFile로 간다. 다행히 Files.createFile은 확인과 생성을 따로 하지 않는다. Javadoc은 파일이 있는지 확인하는 일과 없으면 만드는 일이 디렉터리에 영향을 주는 다른 모든 파일 시스템 활동에 대해 원자적인 단일 연산이라고 적는다. 구현을 보면 이유가 보인다. createFile은 CREATE_NEW와 WRITE 옵션으로 채널을 열었다 닫고, 유닉스 provider는 CREATE_NEW를 open의 O_CREAT | O_EXCL 플래그로 바꾼다. "없으면 만들고, 있으면 실패하라"는 판단을 커널이 디렉터리를 수정하는 한 번의 연산 안에서 하므로, 두 프로세스 중 정확히 하나만 성공하고 나머지는 EEXIST, 즉 FileAlreadyExistsException을 받는다. File.createNewFile도 앞의 표처럼 O_EXCL을 쓰므로 원자적이다. 다만 결과가 boolean이라 실패 원인을 구별하지 못할 뿐이다. 따라서 올바른 방식은 확인하지 않고 바로 시도하는 것이다.

    // 올바른 방식: 시도 자체가 확인이다
try {
    Files.createFile(lockFile);
    // ... 여기 도달한 프로세스는 하나뿐이다
} catch (FileAlreadyExistsException e) {
    // 다른 누군가가 먼저 만들었다
}

    같은 원리가 다른 곳에도 적용된다. "읽기 전에 exists로 확인"하는 코드는 대부분 그냥 읽고 NoSuchFileException을 잡는 코드로 바꾸는 것이 낫다. 확인은 답을 주지 않고 시간만 쓰며, 확인과 사용 사이의 틈은 없앨 수 없기 때문이다. exists가 쓸모 있는 곳은 결과가 틀려도 해가 없는 곳, 예를 들어 화면에 "파일 없음"을 미리 표시하는 정도다.

    이름 바꾸기와 이동: rename은 원자적이다

    디렉터리 엔트리 모델로 돌아가면 이름 바꾸기가 왜 특별한지 보인다. 같은 파일 시스템 안에서 이름을 바꾸거나 다른 디렉터리로 옮기는 일은 데이터를 건드리지 않는다. 한 디렉터리의 엔트리를 지우고 다른 디렉터리에 엔트리를 만들면 끝이다. 1GB 파일이든 1바이트 파일이든 걸리는 시간이 비슷한 이유다. POSIX는 여기서 한 걸음 더 나아가 rename의 원자성을 요구한다. 대상 이름이 이미 있으면 그 이름은 연산 내내 다른 스레드에게 보이는 상태로 남아야 하고, 연산 전의 옛 파일이나 새 파일 중 하나를 가리켜야 한다. 중간 상태, 즉 이름이 잠깐 없어지는 순간이 다른 프로세스에게 보이지 않는다.

    원자성에는 조건이 있다. 엔트리만 옮기는 것은 두 이름이 같은 파일 시스템에 있을 때만 가능하다. inode 번호는 파일 시스템 안에서만 뜻이 있기 때문이다. 다른 파일 시스템으로 옮기려 하면 rename은 EXDEV 오류로 실패한다. OpenJDK 21의 Files.move는 이 상황을 이렇게 처리한다. ATOMIC_MOVE 옵션이 없으면 먼저 rename을 시도하고, EXDEV가 나면 대상에 복사한 뒤 원본을 지운다. 이 경로는 원자적이지 않으며, 큰 파일이면 복사 시간만큼 걸린다. ATOMIC_MOVE 옵션을 주면 rename만 시도하고, EXDEV가 나면 AtomicMoveNotSupportedException을 던진다. 복사로 슬쩍 대신하지 않고 "원자적으로는 할 수 없다"고 알려 주는 것이다.

    이 성질은 설정 파일이나 캐시 파일을 안전하게 교체하는 데 쓰인다. 파일을 제자리에서 덮어쓰면 쓰는 도중에 그 파일을 읽은 다른 프로세스는 반쯤 쓰인 내용을 본다. 대신 같은 디렉터리에 임시 파일을 만들어 내용을 다 쓴 다음 rename으로 원래 이름에 덮어씌우면, 읽는 쪽은 옛 내용 전체나 새 내용 전체 중 하나만 본다.

    import java.io.IOException;
import java.nio.file.*;

public class SafeWrite {
    static void replaceAtomically(Path target, String content) throws IOException {
        Path dir = target.toAbsolutePath().getParent();
        Path temp = Files.createTempFile(dir, "tmp-", ".part");   // 같은 디렉터리 = 같은 파일 시스템
        try {
            Files.writeString(temp, content);
            Files.move(temp, target, StandardCopyOption.ATOMIC_MOVE);
        } finally {
            Files.deleteIfExists(temp);                            // 성공했다면 이미 없다
        }
    }

    public static void main(String[] args) throws IOException {
        Path config = Path.of("config.txt");
        replaceAtomically(config, "version=1");
        replaceAtomically(config, "version=2");
        System.out.println(Files.readString(config));
        try (var s = Files.list(Path.of("."))) {
            System.out.println("leftover temp files = " + s.filter(p -> p.toString().endsWith(".part")).count());
        }
    }
}
    version=2
leftover temp files = 0

    임시 파일을 대상과 같은 디렉터리에 만드는 것이 요점이다. 시스템 임시 디렉터리는 다른 파일 시스템일 수 있고, 그러면 ATOMIC_MOVE가 실패한다. 두 번째 호출에서는 config.txt가 이미 있다. Files.move의 Javadoc은 ATOMIC_MOVE로 옮길 때 대상이 이미 있으면 교체할지 실패할지가 구현에 달려 있다고 적는다. OpenJDK 21의 유닉스 구현은 rename을 그대로 부르고, POSIX rename은 대상을 교체하므로 결과가 version=2다. 한 가지 더 기억할 점이 있다. 원자성은 "다른 프로세스에게 어떻게 보이는가"에 대한 보장이지, 전원이 꺼져도 살아남는다는 보장이 아니다. 02회차에서 본 것처럼 write가 끝나도 데이터는 운영체제의 페이지 캐시에 있을 수 있다. 정전까지 견뎌야 한다면 이름을 바꾸기 전에 FileChannel.force로 임시 파일의 내용을 장치까지 내려야 한다.

    속성을 한 번에 읽기: BasicFileAttributes와 fileKey

    File로 파일의 종류, 크기, 수정 시각을 알려면 메서드를 세 번 불러야 하고, 앞에서 본 것처럼 그때마다 stat이 한 번씩 일어난다. 이 방식에는 성능보다 중요한 결함이 있다. 세 값이 서로 다른 순간의 사진이라는 것이다. 첫 번째 호출과 세 번째 호출 사이에 파일이 다른 파일로 교체되면, 종류는 옛 파일의 것이고 크기는 새 파일의 것인 조합을 얻는다. Files.readAttributes는 stat 한 번으로 얻은 값을 묶어 BasicFileAttributes 객체 하나로 돌려준다. 한 순간의 일관된 사진이다.

    import java.io.IOException;
import java.nio.file.*;
import java.nio.file.attribute.BasicFileAttributes;

public class AttrMain {
    public static void main(String[] args) throws IOException {
        Path file = Path.of("hello.txt");
        Files.writeString(file, "Hello, 가나다");

        BasicFileAttributes attrs = Files.readAttributes(file, BasicFileAttributes.class);
        System.out.println("isRegularFile = " + attrs.isRegularFile());
        System.out.println("isDirectory = " + attrs.isDirectory());
        System.out.println("isSymbolicLink = " + attrs.isSymbolicLink());
        System.out.println("size = " + attrs.size());
        System.out.println("fileKey = " + attrs.fileKey());
    }
}
    isRegularFile = true
isDirectory = false
isSymbolicLink = false
size = 16
fileKey = (dev=100000e,ino=30630409)

    크기 16은 Files.writeString이 UTF-8로 인코딩한 결과다. "Hello, "가 7바이트, "가나다"가 한 글자에 3바이트씩 9바이트다. fileKey는 파일을 고유하게 식별하는 객체로, OpenJDK의 유닉스 구현에서는 장치 번호와 inode 번호의 쌍이다. 장치 번호는 16진수로, inode 번호는 10진수로 찍힌다. 같은 파일에 셸에서 stat -f "dev=%d ino=%i" hello.txt를 실행하면 dev=16777230 ino=30630409가 나오는데, 16진수 100000e가 10진수로 16777230이다. 앞에서 본 하드 링크 두 개는 이름이 달라도 fileKey가 같다. Files.isSameFile이 두 경로가 같은 파일인지 판단할 수 있는 것도 이 쌍을 비교하기 때문이다. 단, Javadoc은 fileKey를 제공할 수 없는 파일 시스템에서는 null을 돌려줄 수 있다고 정해 두었으니 항상 있다고 가정하지 않는다.

    속성은 뷰(view) 단위로 나뉘어 있다. 모든 파일 시스템이 지원해야 하는 basic 뷰, 유닉스 계열 권한을 다루는 posix 뷰, 그리고 OpenJDK의 유닉스 provider가 제공하는 unix 뷰(앞에서 쓴 unix:nlink, unix:ino) 등이 있다. 어떤 뷰를 쓸 수 있는지는 FileSystems.getDefault().supportedFileAttributeViews()로 확인할 수 있다. 이름 문자열로 속성을 읽는 Files.getAttribute(path, "unix:nlink") 같은 방식은 편하지만, 지원하지 않는 뷰를 지정하면 UnsupportedOperationException이 나므로 여러 운영체제에서 돌아야 하는 코드라면 basic 뷰에 머무는 것이 안전하다.

    디렉터리를 읽는 일: readdir, 열린 디렉터리, 순환하는 링크

    앞에서 Files.list와 Files.walk가 돌려준 스트림은 열린 디렉터리를 붙들고 있다고 했다. 무엇을 붙드는지 한 층 내려가 보자. 디렉터리의 내용은 디렉터리 엔트리 표이고, 프로그램은 이 표를 C 라이브러리의 opendir로 열어 readdir로 엔트리를 하나씩 꺼낸다. OpenJDK 21의 sun.nio.fs.UnixDirectoryStream이 정확히 이렇게 동작한다. 반복자의 hasNext가 다음 항목을 필요로 할 때마다 네이티브 readdir을 한 번 불러 이름 하나를 바이트 배열로 받고, .과 ..이면 건너뛰고, 아니면 디렉터리 경로에 그 이름을 resolve한 Path를 돌려준다. 목록 전체를 배열로 만드는 단계가 없으므로 엔트리가 백만 개인 디렉터리도 한 번에 한 이름만 메모리에 올린다.

    이 구조에서 두 가지 성질이 나온다. 첫째, 순서가 정해져 있지 않다. DirectoryStream의 Javadoc은 반복자가 돌려주는 항목에 특정한 순서가 없다고 적는다. 순서는 파일 시스템이 엔트리를 저장한 방식에서 그대로 나오므로, 이름순이 필요하면 직접 정렬해야 한다. 둘째, 반복 도중의 변화에 대해 약하게 일관적(weakly consistent)이다. 같은 Javadoc은 반복자가 디렉터리를 얼려 두지 않으므로 스트림을 만든 뒤에 생긴 변화를 반영할 수도, 반영하지 않을 수도 있다고 정한다. 디렉터리를 읽으면서 그 디렉터리에 파일을 만들거나 지우는 코드는 새 항목을 볼지 말지를 기대할 수 없다.

    아래 실험은 세 가지를 확인한다. Files.list가 열려 있는 동안 프로세스의 디스크립터가 늘어나는지, 기본 provider가 돌려주는 디렉터리 스트림이 어떤 종류인지, 그리고 조상 디렉터리를 가리키는 링크가 있을 때 Files.walk가 어떻게 행동하는지다. macOS에서는 /dev/fd 디렉터리가 현재 프로세스의 열린 디스크립터를 이름으로 보여 주므로 그 항목 수를 센다.

    import java.io.*;
import java.nio.file.*;
import java.nio.file.attribute.BasicFileAttributes;
import java.util.stream.Stream;

public class DirMain {
    static long openFds() {
        String[] names = new File("/dev/fd").list();   // 이 호출도 디렉터리를 잠깐 연다
        return names.length;
    }

    public static void main(String[] args) throws IOException {
        Path root = Path.of("tree");
        Files.createDirectories(root.resolve("a/b"));
        Files.writeString(root.resolve("a/b/f.txt"), "x");
        Path loop = root.resolve("a/b/up");
        if (!Files.exists(loop, LinkOption.NOFOLLOW_LINKS)) {
            Files.createSymbolicLink(loop, Path.of("../.."));      // tree/a/b/up -> tree
        }

        long before = openFds();
        Stream s = Files.list(root);
        long during = openFds();
        s.close();
        long after = openFds();
        System.out.println("fds: before=" + before + " during=" + during + " after=" + after);

        try (DirectoryStream ds = Files.newDirectoryStream(root)) {
            System.out.println("secure = " + (ds instanceof SecureDirectoryStream));
        }

        try (Stream w = Files.walk(root)) {
            w.forEach(p -> System.out.println("walk: " + p));
        }
        try (Stream w = Files.walk(root, FileVisitOption.FOLLOW_LINKS)) {
            w.forEach(p -> System.out.println("follow: " + p));
        } catch (UncheckedIOException e) {
            System.out.println("follow failed: " + e.getCause());
        }

        Files.walkFileTree(root, new SimpleFileVisitor<>() {
            @Override public FileVisitResult visitFile(Path f, BasicFileAttributes a) throws IOException {
                Files.delete(f); System.out.println("delete file: " + f); return FileVisitResult.CONTINUE;
            }
            @Override public FileVisitResult postVisitDirectory(Path d, IOException e) throws IOException {
                if (e != null) throw e;
                Files.delete(d); System.out.println("delete dir:  " + d); return FileVisitResult.CONTINUE;
            }
        });
        System.out.println("exists = " + Files.exists(root));
    }
}

    첫 줄부터 보자. 절대값 5에는 표준 입출력과 JVM이 연 다른 파일, 그리고 /dev/fd를 읽는 데 잠깐 쓴 디스크립터까지 들어 있으므로 의미가 없다. 볼 것은 차이다. Files.list가 열린 동안 하나가 늘었고, 스트림을 닫자 원래대로 돌아왔다. 늘어난 하나가 opendir이 연 디렉터리의 디스크립터다. 닫지 않은 Files.list 스트림이 쌓이면 이 숫자가 계속 커진다.

    macOS와 리눅스가 다른 디렉터리 스트림을 쓰는 이유

    두 번째 줄 secure = false는 플랫폼마다 다르다. SecureDirectoryStream은 열린 디렉터리를 기준으로 파일을 열고, 속성을 읽고, 지우는 연산을 제공하는 하위 인터페이스다. Javadoc은 이 인터페이스가 파일 트리를 경쟁 없이(race-free) 다뤄야 하는 보안에 민감한 애플리케이션을 위한 것이고, 디렉터리가 열려 있는 동안 공격자가 그 디렉터리를 옮기거나 바꿔치기해도 모든 접근이 열린 디렉터리를 기준으로 이루어진다고 설명한다. 그리고 운영체제가 지원하는 경우에만 newDirectoryStream이 이 타입을 돌려준다고 정해 두었다. 기반이 되는 것은 경로 문자열 대신 "디렉터리 디스크립터 + 상대 이름"을 받는 openat, fstatat, unlinkat 같은 시스템 콜이다. 경로를 처음부터 다시 해석하지 않으므로, 앞에서 본 TOCTOU 틈 중 "중간 디렉터리가 링크로 바뀌는" 경우를 막을 수 있다.

    OpenJDK 21의 UnixFileSystemProvider.newDirectoryStream은 네이티브 계층이 openat 계열을 지원한다고 보고하면 디렉터리를 open으로 열고, 그 디스크립터를 dup으로 복제한 뒤, 하나는 fdopendir에 넘겨 readdir용으로, 다른 하나는 openat·unlinkat의 기준 디스크립터로 쓰는 UnixSecureDirectoryStream을 만든다. 지원하지 않는다고 보고하면 opendir 하나로 여는 일반 UnixDirectoryStream을 만든다. 지원 여부는 네이티브 코드(UnixNativeDispatcher.c)가 JVM 시작 때 dlsym으로 openat, fstatat, unlinkat, renameat, futimesat, fdopendir를 모두 찾았는지로 정한다. 그런데 BSD 계열 빌드(macOS 포함)에서는 이 코드가 futimesat을 찾는 줄 자체를 컴파일하지 않으므로 조건이 언제나 거짓이 된다. 그래서 OpenJDK 21의 macOS 빌드에서는 디렉터리 스트림이 SecureDirectoryStream이 아니고, 실험의 디스크립터도 하나만 늘었다. 리눅스 빌드라면 같은 소스 기준으로 SecureDirectoryStream이 돌아오고 열린 스트림 하나가 디스크립터 두 개를 쓴다. 리눅스 쪽은 이 환경에서 실행해 보지 않았고 소스로만 확인한 내용이다.

    walk가 순환을 알아채는 방법

    Files.walk와 Files.walkFileTree는 같은 내부 클래스 java.nio.file.FileTreeWalker로 동작한다. 이 클래스는 지금 내려가 있는 디렉터리들을 스택에 쌓는데, 스택의 각 칸(DirectoryNode)에는 디렉터리 경로, 그 디렉터리의 fileKey, 그리고 그 디렉터리를 연 DirectoryStream이 들어 있다. 하위 디렉터리를 다 돌아야 그 칸이 빠지고 스트림이 닫히므로, 깊이 d까지 내려간 순간에는 디렉터리 스트림 d개가 동시에 열려 있다. 디스크립터 사용량이 트리의 크기가 아니라 깊이에 비례한다는 뜻이다.

    기본값(FOLLOW_LINKS 없음)에서 walk는 링크를 따라가지 않는다. 실행 결과에서 tree/a/b/up은 항목으로 한 번 보고될 뿐 그 안으로 들어가지 않았다. FOLLOW_LINKS를 주면 링크가 디렉터리를 가리킬 때 그 안으로 들어가야 하는데, up은 조상인 tree를 가리키므로 그대로 들어가면 끝없이 돈다. FileTreeWalker.wouldLoop는 들어가기 전에 대상 디렉터리의 fileKey를 스택에 있는 모든 조상의 fileKey와 비교한다. 앞 절에서 본 대로 유닉스 provider의 fileKey는 (장치 번호, inode 번호) 쌍이므로, 이름이 tree/a/b/up이어도 inode가 tree와 같다는 것이 드러난다. Files.walkFileTree의 Javadoc도 순환 감지는 디렉터리의 fileKey를 기록해서 하고, fileKey를 쓸 수 없으면 isSameFile로 조상과 비교하며, 순환은 FileSystemLoopException이라는 I/O 오류로 다룬다고 정한다. walkFileTree에서는 이 예외가 visitFileFailed로 전달되고, walk의 스트림에서는 다른 I/O 오류처럼 UncheckedIOException에 싸여 던져진다. 실행 결과의 follow failed 줄이 그것이다.

    순회 비용도 소스에서 읽힌다. FileTreeWalker는 항목마다 Files.readAttributes로 BasicFileAttributes를 얻어 디렉터리인지 판단한다(FOLLOW_LINKS가 없으면 링크를 따라가지 않는 쪽으로). 이미 읽어 둔 속성을 경로 객체에 실어 오는 BasicFileAttributesHolder라는 내부 인터페이스가 있지만, OpenJDK 21의 UnixPath는 이것을 구현하지 않는다. 그래서 유닉스 계열에서는 readdir로 이름을 하나 받을 때마다 속성을 읽는 시스템 콜이 한 번씩 따라온다.

    디렉터리 트리를 지우는 순서

    rmdir은 빈 디렉터리만 지운다. 앞에서 Files.delete(dir)가 DirectoryNotEmptyException을 던진 것이 그 결과다. 그래서 트리를 지우려면 자식을 모두 지운 뒤에 부모를 지우는 후위 순서(post-order)가 필요하고, walkFileTree의 postVisitDirectory가 바로 그 시점, 즉 디렉터리의 모든 항목을 방문한 뒤에 불린다. 실행 결과의 삭제 순서가 파일 두 개, b, a, tree인 이유다. up은 visitFile에서 파일처럼 지워졌다. FOLLOW_LINKS 없이 돌았으므로 링크 자체의 속성이 전달됐고, Files.delete는 링크를 받으면 링크가 가리키는 대상이 아니라 링크 자체를 지운다. 만약 FOLLOW_LINKS를 켜고 같은 삭제 코드를 돌렸다면 링크를 따라 들어간 다른 디렉터리의 내용까지 지울 수 있다. 트리 삭제에 링크 따라가기를 켜지 않는 것은 취향이 아니라 안전 규칙이다.

    경로 표시 1: 절대 경로, 상대 경로, 그리고 user.dir

    경로에는 두 종류가 있다. 절대 경로(absolute path)는 루트(/)에서 시작하므로 그 자체로 위치가 정해진다. 상대 경로(relative path)는 어딘가를 기준으로 해석해야 위치가 정해진다. 커널에게 그 기준은 프로세스의 현재 작업 디렉터리다. 자바에서는 user.dir 시스템 속성이 이 역할을 한다. File의 Javadoc은 java.io 패키지의 클래스가 상대 경로를 항상 현재 사용자 디렉터리에 대해 해석하며, 이 디렉터리는 user.dir 속성이 가리키고 보통 JVM을 실행한 디렉터리라고 설명한다. IDE에서 실행할 때와 터미널에서 실행할 때 같은 상대 경로가 다른 파일을 가리키는 이유가 이것이다. IDE는 보통 프로젝트 루트를 작업 디렉터리로 잡고, 터미널은 사용자가 서 있던 곳에서 JVM을 띄운다.

    OpenJDK 21의 유닉스 구현은 JVM이 시작할 때 C 함수 getcwd로 운영체제에 현재 디렉터리를 물어 user.dir을 채운다. 그리고 java.io.UnixFileSystem은 생성될 때 그 값을 필드에 복사해 두고 이후 상대 경로 해석에 그 필드를 쓴다. 다음 예제는 같은 상대 경로를 여러 방식으로 표시하고, 마지막 줄에서 user.dir을 실행 중에 바꿔 본다.

    import java.io.File;
import java.io.IOException;
import java.nio.file.*;

public class PathMain {
    public static void main(String[] args) throws IOException {
        System.out.println("user.dir = " + System.getProperty("user.dir"));

        File file = new File("temp/../hello.txt");
        System.out.println("getPath = " + file.getPath());
        System.out.println("getAbsolutePath = " + file.getAbsolutePath());
        System.out.println("getCanonicalPath = " + file.getCanonicalPath());

        Path path = Path.of("temp/../hello.txt");
        System.out.println("path = " + path);
        System.out.println("toAbsolutePath = " + path.toAbsolutePath());
        System.out.println("normalize = " + path.normalize());
        System.out.println("toAbsolutePath().normalize() = " + path.toAbsolutePath().normalize());
        System.out.println("toRealPath = " + path.toRealPath());

        System.setProperty("user.dir", "/");
        System.out.println("after setProperty: " + new File("a.txt").getAbsolutePath()
                + " / " + Path.of("a.txt").toAbsolutePath());
    }
}

    작업 디렉터리에 temp 디렉터리와 hello.txt 파일을 만들어 두고 실행했다. 실제 출력의 작업 디렉터리 부분은 /private/var/folders/br/…/w4처럼 길어서 아래에서는 {작업}으로 줄여 적었다.

    user.dir = {작업}
getPath = temp/../hello.txt
getAbsolutePath = {작업}/temp/../hello.txt
getCanonicalPath = {작업}/hello.txt
path = temp/../hello.txt
toAbsolutePath = {작업}/temp/../hello.txt
normalize = hello.txt
toAbsolutePath().normalize() = {작업}/hello.txt
toRealPath = {작업}/hello.txt
after setProperty: {작업}/a.txt / {작업}/a.txt

    먼저 user.dir을 보자. 이 실습 디렉터리는 mktemp -d로 만들었고, mktemp가 알려 준 경로는 /var/folders/…였다. 그런데 user.dir은 /private/var/folders/…로 시작한다. macOS에서 /var는 /private/var를 가리키는 심볼릭 링크이고, 셸이 cd로 그 링크를 지나 들어갔어도 커널이 기억하는 현재 디렉터리는 링크가 풀린 실제 디렉터리다. JVM은 getcwd로 그 실제 경로를 받는다. 셸 프롬프트에 보이는 경로와 자바가 보는 경로가 다를 수 있다는 뜻이다.

    다음으로 세 가지 표시를 비교하자. getAbsolutePath와 toAbsolutePath는 파일 시스템을 건드리지 않는다. 상대 경로 앞에 작업 디렉터리 문자열을 붙일 뿐이라 ..도 그대로 남는다. normalize도 파일 시스템을 건드리지 않고, 경로 문자열에서 .을 지우고 이름/.. 쌍을 지운다. 그래서 상대 경로에 쓰면 상대 경로(hello.txt)가 나온다. 반면 getCanonicalPath와 toRealPath는 파일 시스템에 물어 심볼릭 링크까지 푼 경로를 만든다. 둘의 차이는 존재하지 않는 파일에서 드러난다. new File("no/such/../file.txt").getCanonicalPath()는 예외 없이 {작업}/no/file.txt로 끝나는 문자열을 돌려주지만, Path.of("no/such/file.txt").toRealPath()는 NoSuchFileException: no/such/file.txt를 던진다. toRealPath의 Javadoc은 이 메서드가 "존재하는 파일"의 실제 경로를 돌려주며 파일이 없으면 IOException을 던진다고 정한다.

    마지막 줄은 System.setProperty("user.dir", "/") 뒤의 결과다. 속성 값은 바뀌었지만 File과 Path 모두 여전히 원래 작업 디렉터리를 기준으로 해석했다. 두 구현 모두 시작할 때 읽어 둔 값을 쓰기 때문이다. 자바 표준 API에는 실행 중인 JVM 프로세스의 작업 디렉터리를 바꾸는 방법이 없다. 기준 디렉터리를 바꾸고 싶다면 속성을 고치지 말고 기준 Path를 변수로 들고 다니며 base.resolve(...)로 경로를 만든다. 자식 프로세스의 작업 디렉터리는 ProcessBuilder.directory로 정할 수 있다.

    메서드파일 시스템 접근.. 제거심볼릭 링크 해석파일이 없으면
    File.getPath없음안 함안 함그대로 돌려줌
    File.getAbsolutePath, Path.toAbsolutePath없음안 함안 함그대로 돌려줌
    Path.normalize없음문자열로 함안 함그대로 돌려줌
    File.getCanonicalPath있음함함(존재하는 부분까지)예외 없이 계산
    Path.toRealPath있음함함(NOFOLLOW_LINKS로 끌 수 있음)NoSuchFileException

    경로 표시 2: '..'과 심볼릭 링크, 그리고 경로 이탈 검사

    앞의 예제에서는 normalize와 toRealPath가 같은 파일을 가리켰다. 경로 중간에 심볼릭 링크가 없었기 때문이다. 링크가 끼면 두 방법이 갈라진다. 다음 예제는 real/sub 디렉터리와 그것을 가리키는 링크 link를 만들고 link/../data.txt라는 경로를 두 방식으로 해석한다. 이어서 Path의 경로 조작 메서드도 함께 찍어 본다.

    import java.io.File;
import java.io.IOException;
import java.nio.file.*;

public class LinkPath {
    public static void main(String[] args) throws IOException {
        // 준비: real/sub 디렉터리, link -> real/sub 심볼릭 링크
        Files.createDirectories(Path.of("real/sub"));
        Files.writeString(Path.of("real/data.txt"), "real 안의 data");
        Path link = Path.of("link");
        if (!Files.exists(link, LinkOption.NOFOLLOW_LINKS)) {
            Files.createSymbolicLink(link, Path.of("real/sub"));
        }

        Path p = Path.of("link/../data.txt");
        System.out.println("normalize    = " + p.normalize());
        System.out.println("exists(normalize) = " + Files.exists(p.normalize()));
        System.out.println("toRealPath   = " + p.toRealPath());
        System.out.println("readString   = " + Files.readString(p));
        System.out.println("canonical    = " + new File("link/../data.txt").getCanonicalPath());

        Path base = Path.of("/srv/app");
        System.out.println("resolve      = " + base.resolve("logs/app.log"));
        System.out.println("resolve abs  = " + base.resolve("/etc/hosts"));
        System.out.println("relativize   = " + base.relativize(Path.of("/srv/static/logo.png")));
        Path q = Path.of("/srv/app/logs/app.log");
        System.out.println("getFileName  = " + q.getFileName());
        System.out.println("getParent    = " + q.getParent());
        System.out.println("getRoot      = " + q.getRoot());
        System.out.println("getNameCount = " + q.getNameCount() + ", getName(1) = " + q.getName(1));
        System.out.println("relative parent = " + Path.of("a.txt").getParent());
    }
}
    normalize    = data.txt
exists(normalize) = false
toRealPath   = {작업}/real/data.txt
readString   = real 안의 data
canonical    = {작업}/real/data.txt
resolve      = /srv/app/logs/app.log
resolve abs  = /etc/hosts
relativize   = ../static/logo.png
getFileName  = app.log
getParent    = /srv/app/logs
getRoot      = /
getNameCount = 4, getName(1) = app
relative parent = null

    normalize는 link/..을 글자 그대로 지워 data.txt를 만들었다. 작업 디렉터리에는 data.txt가 없으므로 exists는 false다. 그런데 같은 경로로 Files.readString을 부르면 real 안의 파일 내용이 나온다. 커널은 경로를 앞에서부터 한 칸씩 해석하기 때문이다. link를 만나면 링크를 따라 real/sub로 들어가고, 그다음 ..은 그 디렉터리의 부모인 real로 올라간다. 그래서 실제로 열리는 파일은 real/data.txt다. toRealPath와 getCanonicalPath는 커널과 같은 방식으로 링크를 풀었으므로 같은 답을 냈다. Path.normalize의 Javadoc도 이 위험을 직접 적는다. 이 메서드는 파일 시스템에 접근하지 않으며, ..과 그 앞의 이름을 지우면 앞의 이름이 심볼릭 링크일 때 원래와 다른 파일을 가리키는 경로가 될 수 있다는 것이다.

    같은 경로 문자열을 문자열 규칙(normalize)과 커널의 한 칸씩 해석이 서로 다른 파일로 이끄는 과정을 나란히 보여 준다. 좌우 두 칸으로 나뉜 비교 그림. 맨 위 가운데에 큰 글씨 "link/../data.txt". 왼쪽 칸 제목 "normalize (문자열 규칙)": 경로 조각 "link"와 ".."에 빨간 취소선을 긋고 오른쪽 화살표로 "data.txt"를 가리키며, 그 아래 작업 디렉터리 폴더 아이콘 안에 회색 점선 문서 아이콘과 라벨 "없는 파일". 오른쪽 칸 제목 "커널의 해석 (한 칸씩)": 폴더 트리 그림. 작업 디렉터리 아래에 "link" (꼬불꼬불한 링크 화살표가 "real/sub" 폴더로 이어짐), "real" 폴더 안에 "sub" 폴더와 "data.txt" 문서. 숫자 원 1이 "link"에서 "sub"로, 숫자 원 2가 "sub"에서 위의 "real"로 올라가는 화살표(라벨 ".."), 숫자 원 3이 "data.txt" 문서를 가리킨다. 오른쪽 칸 하단 라벨 "toRealPath도 같은 답". 평평한 벡터 스타일, 흰 배경. normalize는 글자를 지우고, 커널은 링크를 따라간 뒤에 ..을 처리한다. 링크가 끼면 두 결과가 다른 파일을 가리킨다.

    나머지 경로 조작 메서드는 모두 파일 시스템을 건드리지 않는 순수한 경로 계산이다. resolve는 기준 경로 뒤에 다른 경로를 이어 붙인다. 단, 인자가 절대 경로면 Javadoc 규칙대로 인자를 그대로 돌려준다(resolve abs의 결과가 /etc/hosts). relativize는 반대 방향으로, 기준에서 대상까지 가는 상대 경로를 만든다. getFileName, getParent, getRoot, getName(i)는 경로를 이름 요소(name element)의 나열로 보고 부분을 꺼낸다. /srv/app/logs/app.log는 루트 /와 이름 요소 네 개(srv, app, logs, app.log)로 이루어지고, 인덱스는 루트에서 가장 가까운 요소가 0이다. 상대 경로 a.txt의 부모는 null이다. 작업 디렉터리가 부모라고 추측하지 않는다.

    이 구분이 실제로 중요한 곳이 경로 이탈(path traversal) 검사다. 웹 서버가 public 디렉터리 아래의 파일만 내주려고 한다면, 사용자가 보낸 경로가 그 디렉터리 밖으로 나가지 않는지 확인해야 한다. 먼저 문자열 비교는 쓸 수 없다. "/srv/app2/secret".startsWith("/srv/app")는 true지만, Path의 startsWith는 이름 요소 단위로 비교하므로 Path.of("/srv/app2/secret").startsWith(Path.of("/srv/app"))는 false다. 다음은 normalize로 검사하는 방법과 toRealPath로 검사하는 방법을 비교한다. 공개 디렉터리 안에 바깥의 secret 디렉터리를 가리키는 링크 evil을 하나 심어 두었다.

    import java.io.IOException;
import java.nio.file.*;

public class PathGuard {
    static boolean lexicallyInside(Path base, String input) {
        Path target = base.resolve(input).normalize();
        return target.startsWith(base);
    }

    static boolean reallyInside(Path base, String input) throws IOException {
        Path realBase = base.toRealPath();
        Path real = base.resolve(input).toRealPath();     // 링크를 모두 따라간 실제 위치
        return real.startsWith(realBase);
    }

    public static void main(String[] args) throws IOException {
        Path base = Path.of("public").toAbsolutePath();
        Files.createDirectories(base);
        Files.createDirectories(Path.of("secret"));
        Files.writeString(base.resolve("index.html"), "공개");
        Files.writeString(Path.of("secret/key.txt"), "비밀");
        Path evil = base.resolve("evil");
        if (!Files.exists(evil, LinkOption.NOFOLLOW_LINKS)) {
            Files.createSymbolicLink(evil, Path.of("../secret"));   // public/evil -> ../secret
        }

        for (String input : new String[]{"index.html", "../secret/key.txt", "/etc/hosts", "evil/key.txt"}) {
            System.out.printf("%-18s lexical=%-5b real=%b%n",
                    input, lexicallyInside(base, input), reallyInside(base, input));
        }
    }
}
    index.html         lexical=true  real=true
../secret/key.txt  lexical=false real=false
/etc/hosts         lexical=false real=false
evil/key.txt       lexical=true  real=false

    ../secret/key.txt는 normalize만으로 걸러진다. 절대 경로 /etc/hosts는 resolve가 인자를 그대로 돌려주므로 기준 밖이 되어 역시 걸러진다. 문제는 마지막 줄이다. evil/key.txt에는 ..이 하나도 없으니 문자열 검사는 통과하지만, 실제로 열리는 파일은 링크를 따라간 secret/key.txt다. 기준 디렉터리 안에 다른 사람이 링크를 만들 수 있는 환경이라면 toRealPath로 검사해야 한다. 다만 toRealPath는 파일이 없으면 NoSuchFileException을 던지므로, 그 예외를 "찾을 수 없음" 응답으로 처리하는 코드가 함께 있어야 한다. 그리고 검사와 사용 사이에 링크가 바뀌는 경우까지 막으려면, 앞에서 본 TOCTOU 문제와 똑같이 검사한 실제 경로(real)로 파일을 열어야 한다. 검사는 실제 경로로 하고 열기는 원래 경로로 하면 그 사이의 틈이 다시 생긴다.

    경로 문자열이 바이트가 되는 곳: UnixPath, sun.jnu.encoding, 한글 파일 이름

    지금까지 경로를 문자열로 다뤘지만 커널은 자바 문자열을 모른다. 유닉스 계열의 open, stat, rename이 받는 경로는 C 문자열, 즉 0 바이트(NUL)로 끝나는 바이트 나열이다. 자바의 String은 UTF-16 코드 단위의 나열이다. 그러니 어딘가에서 문자열이 바이트로 바뀌어야 한다. OpenJDK 21의 유닉스 provider에서 그 지점은 Path를 만드는 순간이다. sun.nio.fs.UnixPath는 경로를 String이 아니라 private final byte[] path 필드에 담는다. 생성자는 먼저 normalizeAndCheck로 문자열을 훑어 연속된 /를 하나로 줄이고 끝의 /를 떼며 NUL 문자가 있으면 거부한 뒤, sun.jnu.encoding 속성이 가리키는 문자 집합으로 인코딩한다. 이때 쓰는 내부 메서드는 대체 문자로 바꾸지 않는 인코딩(getBytesNoRepl)이라, 그 문자 집합으로 표현할 수 없는 문자가 있으면 InvalidPathException을 던진다. toString은 반대로 바이트를 같은 문자 집합으로 디코딩한 결과를 처음 불릴 때 만들어 둔다.

    이 설계의 결과를 실험으로 보자. 연속 슬래시, NUL이 섞인 이름, 그리고 macOS에서 한글 파일 이름의 유니코드 정규화(normalization)를 차례로 확인한다. 한글 음절 "한"은 완성형 코드 포인트 하나(U+D55C)로 쓸 수도 있고, 초성·중성·종성 자모 세 개(U+1112 U+1161 U+11AB)를 이어 쓸 수도 있다. 앞의 것을 NFC, 뒤의 것을 NFD 정규화 형식이라 부르고, java.text.Normalizer로 서로 바꿀 수 있다. 화면에는 같은 글자로 보이지만 String으로도, UTF-8 바이트로도 다르다.

    import java.io.*;
import java.nio.file.*;
import java.text.Normalizer;
import java.util.HexFormat;
import java.util.stream.Stream;

public class NameMain {
    public static void main(String[] args) throws IOException {
        System.out.println("sun.jnu.encoding = " + System.getProperty("sun.jnu.encoding")
                + ", file.encoding = " + System.getProperty("file.encoding"));

        System.out.println("slashes = " + Path.of("a//b///c/"));
        try {
            Path.of("report.txt\0.jpg");
        } catch (InvalidPathException e) {
            System.out.println("Path NUL -> " + e.getMessage().replace("\0", "\\0"));
        }
        File nul = new File("report.txt\0.jpg");
        System.out.println("File NUL exists = " + nul.exists() + ", delete = " + nul.delete());
        try { nul.createNewFile(); } catch (IOException e) { System.out.println("File NUL createNewFile -> " + e.getMessage()); }

        Files.createDirectories(Path.of("names"));
        Files.createDirectories(Path.of("cases"));
        String nfc = "한글.txt";
        String nfd = Normalizer.normalize(nfc, Normalizer.Form.NFD);
        System.out.println("nfc chars = " + nfc.length() + ", nfd chars = " + nfd.length() + ", equals = " + nfc.equals(nfd));
        System.out.println("nfd bytes = " + HexFormat.ofDelimiter(" ").formatHex(nfd.substring(0, 1 + 1).getBytes("UTF-8")));
        Files.writeString(Path.of("names", nfd), "NFD로 만든 파일");

        try (Stream s = Files.list(Path.of("names"))) {
            s.forEach(p -> {
                String name = p.getFileName().toString();
                System.out.println("listed length = " + name.length() + ", equals(nfc) = " + name.equals(nfc));
            });
        }
        Path byNfc = Path.of("names", nfc);
        System.out.println("exists(nfc) = " + Files.exists(byNfc) + ", read = " + Files.readString(byNfc));
        System.out.println("Path equals = " + byNfc.equals(Path.of("names", nfd))
                + ", isSameFile = " + Files.isSameFile(byNfc, Path.of("names", nfd)));
        System.out.println("toRealPath name length = " + byNfc.toRealPath().getFileName().toString().length());

        Files.writeString(Path.of("cases", "Report.TXT"), "case");
        Path lower = Path.of("cases", "report.txt");
        System.out.println("exists(lower) = " + Files.exists(lower)
                + ", Path equals = " + lower.equals(Path.of("cases", "Report.TXT"))
                + ", realName = " + lower.toRealPath().getFileName());
    }
}

    NUL 문자: 커널에 닿기 전에 막는다

    report.txt\0.jpg는 고전적인 공격 문자열이다. 자바 문자열로는 끝이 .jpg라 확장자 검사를 통과하지만, 이것을 그대로 C 문자열로 넘기면 시스템 콜은 첫 NUL에서 문자열이 끝났다고 보고 report.txt를 연다. 자바에서 검사한 이름과 커널이 여는 이름이 달라지는 것이다. UnixPath는 생성 단계에서 InvalidPathException으로 이 경로를 거부한다. File도 NUL을 막기는 하지만 방식이 다르다. OpenJDK 21의 java.io.UnixFileSystem.isInvalid는 경로에 NUL이 있는지 보고, File의 메서드 대부분은 이 검사에 걸리면 시스템 콜을 부르지 않고 false나 0을 돌려준다. 예외를 던지는 메서드(createNewFile 등)만 IOException("Invalid file path")를 던진다. 실행 결과의 exists = false와 delete = false는 앞에서 본 "실패를 false로 돌려주는" 패턴이 여기서도 반복된 것이다. 파일이 없어서가 아니라 경로가 잘못되어서 나온 false다.

    sun.jnu.encoding: 파일 내용이 아니라 파일 이름의 문자 집합

    JEP 400(기본 문자 집합 UTF-8)은 JDK 내부에서 쓰는 문자 집합 관련 속성을 설명하면서, sun.jnu.encoding을 java.nio.file 구현이 파일 내용이 아니라 파일 이름 경로를 인코딩·디코딩할 때 쓰는 문자 집합이라고 소개한다. 같은 문서는 이 속성이 명세되지 않고 지원되지 않는(unspecified and unsupported) 내부 속성이며, macOS에서는 값이 UTF-8이라고 적는다. OpenJDK 21의 java_props_md.c를 보면 macOS 빌드는 이 값을 "UTF-8"로 고정하고, 그 밖의 유닉스 계열은 JVM 시작 때 setlocale과 LC_CTYPE 로캘에서 알아낸 인코딩을 그대로 넣는다. 이 실험 환경에서는 -Dsun.jnu.encoding=US-ASCII로 실행해도 값이 UTF-8로 찍혀 명령줄로 바꿀 수 없었다.

    이 차이가 문제가 되는 곳은 로캘이 설정되지 않은 리눅스 환경이다. JEP 400 이후 file.encoding의 기본값은 UTF-8이므로 기본 문자 집합을 쓰는 FileReader 같은 파일 내용 읽기도 로캘과 상관없이 UTF-8로 동작한다(Files.readString은 처음부터 문자 집합을 생략하면 UTF-8이다). 하지만 파일 이름 쪽은 여전히 로캘이 정한다. 로캘의 인코딩이 ASCII 계열이면, 위 소스 논리대로 Path.of("한글.txt")는 인코딩 단계에서 표현할 수 없는 문자를 만나 InvalidPathException("Malformed input or input contains unmappable characters")을 던진다. 내용은 잘 읽고 쓰는 프로그램이 한글 이름의 파일만 열지 못한다면 sun.jnu.encoding 값을 먼저 찍어 볼 일이다. 이 리눅스 시나리오는 이 환경에서 실행하지 않았고 OpenJDK 21 소스로 확인한 내용이다.

    macOS의 한글 이름: 같은 파일, 다른 바이트

    NFD로 바꾼 "한글.txt"는 10글자다. "한"과 "글"이 각각 자모 세 개로 풀렸기 때문이다. 출력의 바이트 e1 84 92와 e1 85 a1은 각각 초성 ㅎ(U+1112)과 중성 ㅏ(U+1161)의 UTF-8 인코딩이다. 이 이름으로 파일을 만들고 디렉터리를 읽으면 돌아오는 이름도 10글자이고, NFC 문자열과 equals로 비교하면 false다. 파일 시스템은 만들 때 받은 바이트를 그대로 보관했다. 그런데 NFC 이름으로 exists를 부르면 true가 나오고 내용도 읽힌다. 이 실험 환경의 APFS는 이름을 찾을 때 정규화 형식의 차이를 무시하면서도 저장할 때는 받은 형식을 보존했다. 대소문자도 같은 모습이다. Report.TXT로 만든 파일을 report.txt로 찾을 수 있지만 저장된 이름은 Report.TXT다.

    자바 쪽에서 눈여겨볼 것은 Path.equals다. UnixPath.equals는 compareTo로 두 경로의 바이트 배열을 비교하고, hashCode도 바이트로 계산한다. 그래서 커널이 같은 파일로 여는 두 경로가 Path로는 다르다(Path equals = false). HashSet로 "이미 처리한 파일"을 기억하는 코드는 같은 파일을 두 번 처리할 수 있다. 같은 파일인지 알고 싶다면 Files.isSameFile을 쓴다. 이 메서드는 OpenJDK 21에서 두 경로의 속성을 각각 읽어 앞 절에서 본 fileKey를 이루는 (장치, inode) 쌍을 비교하므로 true를 돌려준다. 디스크에 실제로 저장된 철자가 필요하면 toRealPath를 쓴다. 옵션 없이 부르면(링크를 따라가는 기본값) OpenJDK 21의 UnixPath.toRealPath는 C 라이브러리의 realpath에 경로를 넘기고 그 결과를 그대로 돌려주며, 이 실험의 macOS에서는 그 결과가 저장된 철자였다. NOFOLLOW_LINKS를 주면 다른 길로 간다. OpenJDK 21의 macOS 파일 시스템 클래스(MacOSXFileSystem)는 자신이 "대소문자를 구별하지 않고 보존하는" 파일 시스템이라고 응답하고, 이 경우 toRealPath는 루트부터 경로 요소를 하나씩 내려가며 각 요소를 같은 디렉터리에서 fileKey가 같은 실제 엔트리 이름으로 바꾼다. 같은 환경에서 NOFOLLOW_LINKS로 따로 불러 봐도 Report.TXT가 돌아왔다. 실행 결과에서 NFC로 물었는데 10글자(NFD) 이름이, report.txt로 물었는데 Report.TXT가 돌아온 것이 이 동작이다.

    MacOSXFileSystem에는 jdk.nio.path.useNormalizationFormD라는 시스템 속성도 있다. Java SE 명세에 있는 속성이 아니라 OpenJDK macOS 구현의 속성이고 기본값은 꺼져 있다. 켜면 경로를 바이트로 바꾸기 전에 비ASCII 문자가 있는 경로를 NFD로, 바이트에서 문자열로 바꿀 때는 NFC로 정규화한다. 같은 실험을 -Djdk.nio.path.useNormalizationFormD=true로 다시 돌리면 목록의 이름이 6글자로 나와 NFC 문자열과 equals가 true가 되고, 두 Path도 같은 NFD 바이트로 인코딩되므로 Path equals = true가 된다. 다만 플랫폼 전용 속성에 기대기보다는, 사람이 입력한 이름과 디렉터리에서 읽은 이름을 비교할 때 양쪽을 Normalizer.normalize(name, Normalizer.Form.NFC)로 맞춘 뒤 비교하는 쪽이 운영체제와 상관없이 동작한다.

    Files로 문자 파일 읽기

    02~03회차에서는 문자 파일을 읽으려고 FileInputStream을 InputStreamReader로 감싸고 다시 BufferedReader로 감쌌다. Files는 이 조립을 메서드 하나로 줄인 편의 메서드를 제공한다. 파일 전체를 문자열 하나로 읽는 readString(Java 11), 줄 목록으로 읽는 readAllLines, 줄을 스트림으로 읽는 lines(둘 다 문자 집합을 생략하는 형태는 Java 8)이다. 쓰기 쪽에는 writeString(Java 11)과 write가 있다. 세 읽기 방법은 결과의 모양만 다른 것이 아니라 메모리를 쓰는 방식과 오류가 드러나는 시점이 다르다.

    import java.io.IOException;
import java.nio.charset.Charset;
import java.nio.file.*;
import java.util.List;
import java.util.stream.Stream;

import static java.nio.charset.StandardCharsets.UTF_8;

public class ReadTextMain {
    public static void main(String[] args) throws IOException {
        Path path = Path.of("hello.txt");
        String text = "abc\n가나다\n\n마지막 줄";
        Files.writeString(path, text, UTF_8);
        System.out.println("size = " + Files.size(path));

        String all = Files.readString(path, UTF_8);
        System.out.println("readString equals = " + all.equals(text));

        List lines = Files.readAllLines(path, UTF_8);
        System.out.println("readAllLines = " + lines + " (" + lines.size() + "줄)");

        try (Stream stream = Files.lines(path, UTF_8)) {
            stream.forEach(line -> System.out.println("[" + line + "]"));
        }

        Files.writeString(path, "\n추가", UTF_8, StandardOpenOption.APPEND);
        System.out.println("after append = " + Files.readAllLines(path).size() + "줄");

        Path legacy = Path.of("legacy.txt");
        Files.write(legacy, "가나다".getBytes(Charset.forName("MS949")));
        try {
            Files.readString(legacy);
        } catch (IOException e) {
            System.out.println(e.getClass().getName() + ": " + e.getMessage());
        }
        System.out.println("MS949 = " + Files.readString(legacy, Charset.forName("MS949")));
        try (Stream s = Files.lines(legacy)) {
            s.forEach(System.out::println);
        } catch (java.io.UncheckedIOException e) {
            System.out.println("lines: " + e.getClass().getSimpleName() + " <- " + e.getCause());
        }
    }
}

"abc\n"이 4바이트, "가나다\n"이 9+1=10바이트, 빈 줄의 "\n"이 1바이트, "마지막 줄"이 한글 네 글자 12바이트와 공백 1바이트로 13바이트다. 합하면 28이다. writeString은 옵션을 주지 않으면 CREATE, TRUNCATE_EXISTING, WRITE를 준 것처럼 동작한다고 Javadoc에 적혀 있다. 없으면 만들고, 있으면 길이를 0으로 자른 뒤 쓴다는 뜻이다. 그래서 같은 파일에 writeString을 두 번 부르면 두 번째 내용만 남는다. 이어 쓰려면 예제처럼 StandardOpenOption.APPEND를 준다. 덧붙인 "\n추가" 때문에 줄이 다섯 개가 됐다.

    문자 집합: Files는 처음부터 UTF-8이다

    문자 집합을 생략한 Files.readString(path), readAllLines(path), lines(path), writeString(path, text)는 기본 문자 집합이 아니라 항상 UTF-8을 쓴다고 Javadoc에 명시되어 있다. 03회차에서 본 것처럼 FileReader는 JDK 18(JEP 400) 이전까지 운영체제에 따라 달라지는 기본 문자 집합을 썼다. Files의 이 메서드들은 그런 의존성 없이 처음부터 UTF-8로 고정되어 있었다.

    더 중요한 차이는 잘못된 바이트를 만났을 때다. MS949로 저장한 "가나다"의 첫 바이트는 0xB0이다. 2진수로 1011 0000이므로 UTF-8에서는 다른 바이트 뒤에만 올 수 있는 연속 바이트(continuation byte) 모양이다. 첫 바이트부터 규칙에 어긋나므로 디코더는 길이 1의 잘못된 입력을 보고하고, readString은 MalformedInputException: Input length = 1을 던진다. new String(bytes, UTF_8)이라면 이 바이트를 조용히 대체 문자(U+FFFD)로 바꿨을 것이다. 03회차의 표현으로 말하면 Files의 읽기 메서드는 REPLACE가 아니라 REPORT 쪽이다. 깨진 데이터를 모르고 지나치는 대신 읽는 순간 알려 준다.

    readString과 readAllLines: 한 번에 전부

    OpenJDK 21의 readString은 readAllBytes로 파일 전체를 byte[] 하나에 읽은 다음 그 배열을 문자열로 디코딩한다. 파일 크기가 Integer.MAX_VALUE를 넘으면 readAllBytes가 OutOfMemoryError("Required array size too large")를 던진다. 배열 길이가 int이므로 2GB 이상의 파일은 애초에 한 배열에 담을 수 없다. 그보다 작아도 메모리 계산이 필요하다. 디코딩하는 동안에는 바이트 배열과 결과 문자열이 동시에 힙에 있다. 자바 9부터의 압축 문자열(compact strings, JEP 254) 구현에서 String은 모든 문자가 Latin-1 범위면 문자당 1바이트, 아니면 UTF-16으로 문자당 2바이트를 쓴다. UTF-8로 3바이트인 한글은 문자열 안에서 2바이트가 되므로, 한글 위주의 300MB 파일을 읽으면 최종 문자열은 약 200MB다. 그런데 OpenJDK 21의 UTF-8 디코딩은 Latin-1로 담을 수 없는 문자를 만나면 UTF-16 작업 배열을 입력 바이트 수의 두 배(600MB)로 먼저 잡고, 디코딩이 끝난 뒤 실제 길이로 잘라 새 배열에 복사한다. 그래서 디코딩하는 동안에는 바이트 배열 300MB와 작업 배열 600MB가 함께 힙을 차지하고, 마지막 복사 순간에는 약 200MB짜리 결과 배열까지 더해진다.

    readAllLines는 줄마다 문자열을 만들어 List에 담는다. 줄 끝으로 인정하는 것은 LF(\n), CR(\r), CRLF(\r\n) 세 가지이고, 줄 끝 문자는 결과에 들어가지 않는다. 결과에서 빈 줄이 빈 문자열("")로 들어간 것을 확인하자. 줄마다 별도 String 객체가 생기므로 객체 헤더와 리스트 슬롯만큼 메모리가 더 든다. 두 메서드 모두 작은 설정 파일이나 테스트 데이터에는 가장 간단한 선택이지만, 크기를 모르는 외부 입력에는 위험하다.

    lines: 필요한 만큼씩, 대신 닫아야 한다

    Files.lines는 파일을 열고, 스트림이 소비되는 만큼만 읽는다. Javadoc의 표현으로는 readAllLines와 달리 모든 줄을 List로 읽지 않고, 스트림이 소비될 때 지연해서(lazily) 채운다. 그래서 수 GB짜리 로그 파일에서 오류 줄만 골라 세는 일도 일정한 메모리로 할 수 있다. 대신 두 가지 대가가 있다.

    첫째, 스트림이 열린 파일을 붙잡고 있다. Javadoc은 반환된 스트림이 열린 파일에 대한 참조를 갖고 있고 스트림을 닫아야 파일이 닫힌다고 적으며, try-with-resources 문 안에서 써야 한다고 명시한다. Stream은 AutoCloseable이지만 대부분의 스트림은 닫을 필요가 없어서 습관적으로 닫지 않게 되는데, Files.lines, Files.list, Files.walk가 돌려준 스트림은 예외다. 둘째, 오류가 늦게, 다른 모양으로 드러난다. 실행 결과의 마지막 줄을 보자. MS949 파일을 lines로 열 때는 예외가 나지 않았다. 디코딩은 forEach가 첫 줄을 요구할 때 일어나고, 그때 생긴 MalformedInputException은 UncheckedIOException에 싸여 던져졌다. Stream의 메서드는 검사 예외를 던질 수 없기 때문이다. Javadoc도 메서드가 반환된 뒤의 I/O 오류와 잘못된 바이트는 UncheckedIOException으로 감싸 읽기를 일으킨 스트림 메서드에서 던진다고 정해 두었다. 그래서 lines를 쓰는 코드는 IOException(열기 실패)과 UncheckedIOException(읽기 실패) 두 가지를 모두 처리해야 한다.

    줄 단위로 읽되 스트림 API가 필요 없다면 Files.newBufferedReader(path)도 같은 선택지다. 03회차에서 본 BufferedReader를 UTF-8 디코더와 함께 돌려주며, 잘못된 바이트에서는 역시 예외를 던진다. readLine 반복문은 검사 예외를 그대로 던질 수 있어 오류 처리가 단순하다.

    방법메모리잘못된 바이트닫기

    Files.lines의 속: 파일을 반으로 자르는 스플리터레이터

    Files.lines와 BufferedReader.lines()는 둘 다 줄의 스트림을 돌려주므로 같은 것으로 보기 쉽다. 순차 스트림으로 쓸 때는 실제로 거의 같다. 차이는 .parallel()을 붙일 때 드러나고, 그 차이는 스트림의 원천인 스플리터레이터(spliterator)가 데이터를 어떻게 나누는지에서 나온다. 병렬 스트림은 원천의 trySplit을 불러 작업을 둘로 쪼개고, 쪼갠 조각을 다시 쪼개 여러 스레드에 나눠 준다. 줄의 스트림에서 문제는 "파일의 가운데 줄이 어디서 시작하는가"를 앞에서부터 읽지 않고는 알 수 없다는 점이다.

    OpenJDK 21의 Files.lines(path, cs)는 세 조건을 확인한다. 경로가 기본 파일 시스템에 속하고 문자 집합이 UTF-8, US-ASCII, ISO-8859-1 중 하나이면 FileChannel을 열고, 그 채널의 size()로 얻은 크기가 0보다 크고 Integer.MAX_VALUE 이하이면 java.nio.file.FileChannelLinesSpliterator로 스트림을 만든다. 조건 중 하나라도 어긋나면 newBufferedReader(path, cs).lines()와 같은 방식으로 돌아간다. 크기가 0인 경우를 빼는 이유는 소스 주석에 있다. FileChannel.size()가 내용이 있는 파일에 대해서도 0을 돌려주는 경우가 있기 때문이다. Files.lines의 Javadoc 구현 노트(implNote)는 이 세 문자 집합을 "줄 최적(line-optimal)" 문자 집합이라 부르고, 파일의 바이트를 임의 위치에서 읽어도 줄 바꿈('\n')과 캐리지 리턴('\r')의 인코딩된 바이트를 다른 문자와 구별할 수 있는 성질을 가졌다고 설명한다. UTF-8에서 이 성질이 성립하는 이유는 01회차에서 본 인코딩 규칙에 있다. 여러 바이트로 된 문자의 바이트는 선두 바이트든 연속 바이트든 최상위 비트가 1이므로, 0x0A나 0x0D라는 바이트 값은 오직 LF와 CR 자체로만 나타난다. UTF-16이라면 다른 문자의 절반이 0x0A일 수 있으니 이런 판단을 할 수 없다.

    아래 예제는 줄 10개짜리 파일로 스플리터레이터를 직접 꺼내 한 번 쪼개 본다. Files.lines가 돌려준 스트림에 중간 연산이 없으므로 spliterator()는 원천 스플리터레이터를 그대로 돌려준다.

    import java.io.IOException;
import java.nio.charset.Charset;
import java.nio.file.*;
import java.util.Spliterator;
import java.util.stream.Stream;

import static java.nio.charset.StandardCharsets.UTF_8;

public class LinesSplit {
    public static void main(String[] args) throws IOException {
        Path p = Path.of("lines.txt");
        StringBuilder sb = new StringBuilder();
        for (int i = 1; i <= 10; i++) sb.append("line-").append(i).append('\n');   // 9줄은 7바이트, 마지막 줄은 8바이트
        Files.writeString(p, sb, UTF_8);
        System.out.println("size = " + Files.size(p));

        try (Stream s = Files.lines(p, UTF_8)) {
            Spliterator right = s.spliterator();
            System.out.println("class = " + right.getClass().getSimpleName());
            System.out.println("before split: estimate = " + right.estimateSize());
            Spliterator left = right.trySplit();
            System.out.println("left  estimate = " + left.estimateSize() + ", first = " + first(left));
            System.out.println("right estimate = " + right.estimateSize() + ", first = " + first(right));
        }
        try (Stream s = Files.lines(p, Charset.forName("MS949"))) {
            System.out.println("MS949 class = " + s.spliterator().getClass().getSimpleName());
        }
        try (Stream s = Files.lines(p, UTF_8)) {
            System.out.println("parallel count = " + s.parallel().filter(l -> l.endsWith("0")).count());
        }
    }

    static String first(Spliterator sp) {
        String[] box = new String[1];
        sp.tryAdvance(l -> box[0] = l);
        return box[0];
    }
}

    마지막 줄은 병렬로 세어도 결과가 같다는 확인이다(0으로 끝나는 줄은 line-10 하나). 이제 분할을 한 바이트씩 추적해 보자. 파일은 71바이트다. line-1부터 line-9까지는 줄 바꿈을 포함해 7바이트씩이므로 k번째 줄은 오프셋 7(k−1)에서 시작하고, line-10은 오프셋 63부터 8바이트다. 스플리터레이터는 처음 만들어질 때 범위 [0, 71)만 기억하고 아무것도 읽지 않는다. estimateSize가 줄 수가 아니라 남은 바이트 수 71을 돌려준 것도 그래서다. 소스 주석은 줄당 평균 문자 수로 나눌 수도 있지만 그 상수는 어차피 상쇄된다고 적어 두었다.

    trySplit이 처음 불리면 파일 전체를 읽기 전용으로 메모리 매핑한다(fc.map(READ_ONLY, 0, fence)). 그리고 가운데 위치 mid = (0 + 71) >>> 1 = 35의 바이트를 본다. 오프셋 35는 line-6의 첫 글자 l이라 줄 끝이 아니다. 그러면 35의 왼쪽(34, 33, …)과 오른쪽(36, 37, …)을 번갈아 한 바이트씩 보며 가장 가까운 '\n'이나 '\r'을 찾는다. 첫 시도인 오프셋 34가 line-5의 줄 바꿈이므로 분할점은 그 바로 뒤인 35가 된다. 왼쪽 조각은 [0, 35)로 line-1~line-5를, 오른쪽(원래 객체)은 [35, 71)로 line-6~line-10을 맡는다. 출력의 35와 36, 그리고 각 조각의 첫 줄이 정확히 이 계산과 맞는다. 매핑한 버퍼는 분할점을 찾는 데만 쓰이고, 조각들이 참조 수(AtomicInteger)로 함께 공유한다.

    줄을 실제로 읽는 단계에서는 매핑을 쓰지 않는다. 조각이 처음 tryAdvance를 받으면 자기 범위만 읽는 ReadableByteChannel을 만들어 BufferedReader로 감싸는데, 이 채널은 공유된 FileChannel에 위치를 지정한 읽기(fc.read(dst, index))를 해서 [index, fence) 범위의 바이트만 가져온다. 위치를 지정한 읽기는 채널의 현재 위치를 바꾸지 않으므로 여러 스레드의 조각이 한 채널을 동시에 써도 서로의 위치를 건드리지 않는다. 읽기가 시작되면 그 조각은 매핑 참조를 내려놓고 더는 쪼개지지 않으며, 참조 수가 0이 되면 매핑이 해제된다. 순차 스트림이라면 trySplit이 불리지 않으므로 매핑은 아예 일어나지 않는다. 클래스 주석도 매핑된 버퍼는 병렬 실행에만 필요하다고 적는다.

    MS949로 연 스트림의 원천은 IteratorSpliterator였다. BufferedReader.lines()가 줄 반복자를 Spliterators.spliteratorUnknownSize로 감싸 만든 것이다. 이 스플리터레이터는 파일의 구조를 모르므로 앞에서부터 줄을 읽어 배열에 담는 방식으로만 쪼갠다. OpenJDK 21에서 첫 분할은 1024개, 다음은 2048개처럼 1024씩 늘어나는 크기의 배열을 만들어 그만큼의 줄을 순차적으로 읽어 넘긴다(최대 225개). 쪼개는 일 자체가 순차적인 읽기이고, 소스 주석에 따르면 원소 처리 비용이 배열로 옮기는 비용보다 클 때만 병렬화가 이득이다. Files.lines의 Javadoc이 줄 최적이 아닌 문자 집합의 스플리터레이터는 분할 성질이 나빠 병렬 성능이 나쁠 수 있다고 경고하는 이유가 이것이다. 정리하면 Files.lines(path)(기본 UTF-8)에 parallel()을 붙이면 파일이 바이트 위치로 나뉘어 각 스레드가 자기 구간을 따로 읽고, 다른 문자 집합이나 BufferedReader.lines()에서는 한 스레드가 읽어 나눠 주는 구조가 된다. 병렬화로 이득을 볼지는 여전히 줄마다 하는 일의 무게와 디스크 상태에 달려 있지만, 적어도 전자는 읽기 자체를 나눌 수 있는 구조다.

    파일 복사 최적화: 바이트가 지나가는 길을 줄인다

    파일 복사는 I/O 비용이 어디서 생기는지 보기에 가장 좋은 문제다. 하는 일은 단순하다. 원본의 바이트를 대상에 그대로 옮긴다. 그런데 그 바이트가 어디를 몇 번 거치느냐는 방법에 따라 크게 다르다. 200MB(209,715,200바이트) 파일을 세 가지 방법으로 복사해 보자. 네 번째 줄은 세 번째 방법에 옵션 하나를 더한 것이다.

    import java.io.*;
import java.nio.file.*;
import java.util.Arrays;

public class CopyMain {
    public static void main(String[] args) throws IOException {
        Path src = Path.of("source.dat");
        if (!Files.exists(src)) {
            byte[] chunk = new byte[1024 * 1024];
            try (OutputStream out = new BufferedOutputStream(new FileOutputStream("source.dat"))) {
                for (int i = 0; i < 200; i++) { Arrays.fill(chunk, (byte) i); out.write(chunk); }
            }
        }
        for (int round = 0; round < 3; round++) {
            Files.deleteIfExists(Path.of("copy1.dat"));
            Files.deleteIfExists(Path.of("copy2.dat"));
            Files.deleteIfExists(Path.of("copy3.dat"));
            Files.deleteIfExists(Path.of("copy4.dat"));

            long t0 = System.nanoTime();
            try (FileInputStream in = new FileInputStream("source.dat");      // 1. 전부 읽고 전부 쓰기
                 FileOutputStream out = new FileOutputStream("copy1.dat")) {
                byte[] all = in.readAllBytes();
                out.write(all);
            }
            long t1 = System.nanoTime();
            try (FileInputStream in = new FileInputStream("source.dat");      // 2. transferTo
                 FileOutputStream out = new FileOutputStream("copy2.dat")) {
                in.transferTo(out);
            }
            long t2 = System.nanoTime();
            Files.copy(src, Path.of("copy3.dat"));                            // 3. Files.copy
            long t3 = System.nanoTime();
            Files.copy(src, Path.of("copy4.dat"), StandardCopyOption.COPY_ATTRIBUTES);
            long t4 = System.nanoTime();
            System.out.printf("round %d: readAllBytes %dms, transferTo %dms, Files.copy %dms, Files.copy+ATTR %dms%n",
                    round, (t1 - t0) / 1_000_000, (t2 - t1) / 1_000_000, (t3 - t2) / 1_000_000, (t4 - t3) / 1_000_000);
        }
        System.out.println("mismatch = " + Files.mismatch(src, Path.of("copy1.dat")) + " "
                + Files.mismatch(src, Path.of("copy2.dat")) + " " + Files.mismatch(src, Path.of("copy3.dat"))
                + " " + Files.mismatch(src, Path.of("copy4.dat")));
    }
}
    round 0: readAllBytes 340ms, transferTo 210ms, Files.copy 119ms, Files.copy+ATTR 1ms
round 1: readAllBytes 338ms, transferTo 196ms, Files.copy 226ms, Files.copy+ATTR 0ms
round 2: readAllBytes 133ms, transferTo 107ms, Files.copy 152ms, Files.copy+ATTR 0ms
mismatch = -1 -1 -1 -1

    Files.mismatch(Java 12)는 두 파일의 내용이 처음 달라지는 위치를 돌려주고, 끝까지 같으면 -1을 돌려준다. 네 사본 모두 원본과 같다. 시간을 보면 앞의 세 방법은 같은 자릿수 안에서 실행마다 순위가 바뀐다. 0회차에서는 Files.copy가 가장 빨랐고 2회차에서는 가장 느렸다. 원본 파일은 방금 만들어 운영체제의 페이지 캐시에 올라와 있으므로 이 측정은 디스크 속도보다 메모리 복사와 시스템 콜에 좌우되고, 캐시 상태, 운영체제가 더러운 페이지를 디스크로 내리는 시점, JIT 워밍업, 다른 프로세스가 모두 숫자를 흔든다. 그러니 이 숫자로 앞의 세 방법의 순위를 매기는 것은 의미가 없다. 반면 네 번째 줄은 세 번의 측정 모두 1ms 이하로, 다른 방법과 자릿수가 다르다. 이 차이는 측정 오차로 설명되지 않는다. 일어나는 일 자체가 다르기 때문이다. 각 방법을 소스 수준에서 따라가 보자.

    방법 1: readAllBytes와 write — 바이트가 힙을 통과한다

    FileInputStream.readAllBytes는 OpenJDK 21에서 파일 길이와 현재 위치로 남은 크기를 계산해 그 크기의 byte[]를 힙에 만들고, read(buf, off, len)을 반복해 채운다. 이 read는 네이티브 함수 readBytes(io_util.c)로 내려간다. 이 함수는 요청 길이가 8192바이트 이하면 C 스택의 버퍼를 쓰고, 더 크면 malloc(len)으로 네이티브 메모리를 그만큼 할당한다. 그런 다음 read 시스템 콜로 커널이 페이지 캐시의 데이터를 그 네이티브 버퍼에 복사하고, JNI 함수 SetByteArrayRegion으로 네이티브 버퍼의 내용을 자바 배열에 다시 복사한다. 자바 힙의 배열은 GC가 옮길 수 있으므로 커널이 직접 쓰게 두지 않고 중간 버퍼를 거치는 것이다. 쓰기(writeBytes)는 정확히 반대 순서다. 길이가 크면 malloc, GetByteArrayRegion으로 자바 배열을 네이티브 버퍼에 복사, write 시스템 콜로 대상 파일의 페이지 캐시에 복사.

    정리하면 200MB가 CPU에 의해 네 번 복사되고(페이지 캐시 → 네이티브 → 힙 → 네이티브 → 페이지 캐시), 그동안 힙에 200MB 배열이, 네이티브 메모리에 200MB 버퍼가 잠깐씩 존재한다. 힙이 작으면 어떻게 될까. 아래는 최대 힙을 64MB로 제한하고 세 방법을 차례로 돌린 결과다.

    import java.io.*;
import java.nio.file.*;

public class SmallHeap {
    public static void main(String[] args) throws IOException {
        System.out.println("maxMemory = " + Runtime.getRuntime().maxMemory() / (1024 * 1024) + "MB");
        try (FileInputStream in = new FileInputStream("source.dat");
             FileOutputStream out = new FileOutputStream("copy2.dat")) {
            System.out.println("transferTo = " + in.transferTo(out));
        }
        Files.copy(Path.of("source.dat"), Path.of("copy3.dat"), StandardCopyOption.REPLACE_EXISTING);
        System.out.println("Files.copy ok");
        try (FileInputStream in = new FileInputStream("source.dat")) {
            byte[] all = in.readAllBytes();
            System.out.println("readAllBytes = " + all.length);
        }
    }
}

    transferTo와 Files.copy는 힙 64MB로 200MB를 문제없이 옮겼고, readAllBytes만 배열을 만들지 못해 죽었다. 방법 1의 진짜 문제는 속도가 아니라 파일 크기에 비례하는 힙이다. 파일 크기를 통제할 수 없는 서버 코드에서 이 방식은 사용자 업로드 하나로 JVM 전체를 멈추게 할 수 있다. 02회차의 버퍼 방식(고정 크기 배열로 나눠 읽고 쓰기)은 힙 문제는 없지만 복사 횟수는 같다. 버퍼가 8192바이트 이하면 스택 버퍼를 쓰므로 malloc은 사라지지만, 커널과 자바 배열 사이를 오가는 네 번의 복사는 그대로다.

    방법 2: transferTo — 바이트가 자바를 거치지 않을 수 있다

    InputStream.transferTo(OutputStream)는 Java 9에 추가됐다. InputStream의 기본 구현은 버퍼 하나로 읽고 쓰기를 반복하는 루프이고, OpenJDK 21에서 그 버퍼는 16384바이트다. 그런데 FileInputStream은 이 메서드를 재정의한다. 출력이 FileOutputStream이면 양쪽에서 FileChannel을 꺼내 FileChannel.transferTo에 일을 맡기고, 다 옮기지 못한 나머지가 있을 때만 기본 루프로 넘어간다.

    FileChannel.transferTo의 구현(sun.nio.ch.FileChannelImpl)은 세 단계를 차례로 시도한다. 첫째는 커널에 직접 전송을 요청하는 경로다. 리눅스에서는 copy_file_range를 먼저 부르고, 지원되지 않으면 sendfile을 부른다. macOS에서는 sendfile을 부르는데, macOS의 sendfile은 매뉴얼 첫 줄부터 "파일을 소켓으로 보낸다"고 정의된 함수라 대상이 파일이면 실패하고 다음 단계로 넘어간다. 둘째는 메모리 매핑 경로다. 옮길 양이 16KB 이상이면 원본을 최대 8MB씩 읽기 전용으로 메모리에 매핑(mmap)하고, 매핑된 영역을 대상 채널에 write한다. 매핑은 원본의 페이지 캐시를 프로세스 주소 공간에 그대로 비춰 주는 것이므로 읽기 단계의 복사가 없다. write 시스템 콜이 그 영역을 대상 파일의 페이지 캐시로 복사하는 한 번만 남는다. 셋째는 앞의 두 경로가 모두 불가능할 때의 대비책으로, 8192바이트 버퍼로 읽고 쓰는 루프다.

    그래서 macOS에서 방법 2는 매핑 경로를 탔고, 리눅스였다면 copy_file_range로 커널 안에서 복사됐을 것이다. copy_file_range의 매뉴얼은 이 호출이 두 파일 디스크립터 사이의 커널 내 복사이며, 데이터를 커널에서 사용자 공간으로 옮기는 비용이 없다고 설명한다(리눅스 4.5에 추가). 어느 경우든 바이트는 자바 힙을 지나가지 않는다. 한 가지 함정이 있다. FileInputStream.transferTo의 재정의는 출력이 FileOutputStream인지를 instanceof로 확인한다. 출력을 BufferedOutputStream으로 감싸 넘기면 이 확인에 실패해 16KB 버퍼 루프로 돌아간다. 버퍼링이 오히려 빠른 길을 막는 경우다.

    방법 3: Files.copy — 운영체제에게 복사를 맡긴다

    Files.copy(Path, Path)는 스트림을 아예 만들지 않는다. OpenJDK 21의 유닉스 구현(sun.nio.fs.UnixFileSystem.copyFile)은 원본을 O_RDONLY로, 대상을 O_WRONLY | O_CREAT | O_EXCL로 연다. 대상을 O_EXCL로 여는 것은 이미 있는 대상을 덮어쓰지 않기 위해서다(REPLACE_EXISTING를 주면 먼저 대상을 지운다). 그다음 플랫폼별 직접 복사를 시도한다. 리눅스는 copy_file_range, 안 되면 sendfile을 쓴다. macOS는 시스템 라이브러리의 fcopyfile에 COPYFILE_DATA 플래그로 데이터 복사를 맡긴다. 직접 복사가 지원되지 않으면 네이티브 메모리의 임시 버퍼로 read와 write를 반복하는데, 이 버퍼 크기는 두 파일 시스템의 블록 크기로 정하되 최소 16384바이트다. 어느 경로든 자바 힙에는 파일 크기만 한 배열이 생기지 않는다.

    네 번째 줄, COPY_ATTRIBUTES를 준 Files.copy가 1ms 이하였던 이유는 macOS 구현의 첫 단계에 있다. OpenJDK 21의 BsdFileSystem.copyFile은 속성 복사를 요청받았고 취소 가능한 복사가 아닐 때 데이터를 복사하는 대신 clonefile 시스템 콜을 먼저 시도한다. clonefile의 매뉴얼에 따르면 복제본은 원본과 데이터 블록을 공유하고, 이후 어느 한쪽에 쓰면 그 쓰기는 수정된 파일에만 반영된다(copy-on-write). 즉 200MB의 데이터 블록은 하나도 복사되지 않았고, 새 inode가 같은 블록을 가리키게 했을 뿐이다. 그래서 크기와 상관없이 빠르다. 파일 시스템이 복제를 지원하지 않거나(ENOTSUP) 두 경로가 다른 파일 시스템에 있으면(EXDEV) 일반 복사 경로로 넘어간다. 매뉴얼은 복제가 데이터 블록용 저장 공간을 새로 할당하지 않을 수 있어서 나중에 기존 블록을 덮어쓸 때 공간 부족(ENOSPC)이 날 수 있다고도 경고한다. 복사 시점이 아니라 쓰기 시점에 공간이 필요해지는 것이다. 리눅스의 copy_file_range도 매뉴얼에서 파일 시스템이 리플링크(reflink) 같은 "복사 가속" 기법을 쓸 기회를 준다고 설명하므로, Btrfs처럼 블록 공유를 지원하는 파일 시스템에서는 비슷한 일이 일어날 수 있다.

    흔한 오해와, 이 지식이 다시 쓰이는 곳

    "new File(...)이나 Path.of(...)를 하면 파일이 생긴다." 둘 다 경로 값을 만들 뿐이다. 파일 시스템은 createNewFile, Files.createFile, 스트림 열기처럼 실제 작업을 요청할 때만 바뀐다. 같은 이유로 Path 객체를 들고 있다고 그 파일이 계속 있다는 보장도 없다.

    "exists가 false면 파일이 없다." 권한 때문에 판단하지 못했을 수도 있다. Files.exists와 Files.notExists가 둘 다 false면 "모른다"이다. 그리고 어떤 답이든 받는 즉시 낡는다. 확인 후 행동하지 말고, 원자적 연산(createFile, ATOMIC_MOVE)을 시도하고 예외를 처리한다.

    "normalize한 경로는 실제 위치다." normalize는 문자열 계산이다. 경로에 심볼릭 링크가 있으면 커널이 여는 파일과 다른 파일을 가리킬 수 있다. 실제 위치가 필요하면 toRealPath를 쓴다.

    "파일을 지우면 디스크 공간이 바로 돌아온다." 지우기는 이름을 떼어 내는 unlink다. 어떤 프로세스가 그 파일을 열고 있으면 실체는 디스크립터가 닫힐 때까지 남는다. 리눅스와 macOS에서 lsof로 이미 지워진 파일을 붙든 프로세스를 찾을 수 있다.

    "Files.move는 항상 원자적이다." 같은 파일 시스템 안의 이름 바꾸기만 원자적이다. 다른 파일 시스템으로의 이동은 복사 후 삭제로 바뀐다. 원자성이 필요하면 ATOMIC_MOVE를 주고, 실패를 AtomicMoveNotSupportedException으로 받는다.

    "파일 복사는 결국 읽고 쓰는 것이니 방법은 상관없다." 같은 결과를 내는 방법들이 데이터를 4번 옮기기도, 1번 옮기기도, 전혀 옮기지 않기도 한다. 그리고 그 차이는 측정보다 소스와 시스템 콜을 따라가면 더 분명하게 보인다.

    이 회차의 지식은 바로 다음 회차들에서 다시 쓰인다. 06~08회차의 소켓도 운영체제에게는 파일 디스크립터이고, 데이터를 주고받는 일은 같은 read/write 시스템 콜로 이루어진다. 열린 디스크립터를 닫지 않으면 자원이 새고, 프로세스당 디스크립터 수 제한에 닿으면 새 연결을 받지 못한다. FileChannel.transferTo의 대상이 소켓 채널이면 위의 직접 전송 경로가 sendfile로 이어지는데, 이것이 원래 sendfile이 만들어진 용도인 "파일을 소켓으로 보내기"다. 10회차와 13회차에서 HTTP 서버를 직접 만들어 파일을 응답으로 내보낼 때, 이 회차의 경로 이탈 검사와 복사 경로 이야기가 그대로 그 서버의 보안과 성능 문제가 된다.
    이름과 실체
    유닉스 계열 파일 시스템에서 이름은 디렉터리 엔트리에, 데이터와 메타데이터는 inode에 있다. 하드 링크는 같은 inode에 붙은 두 번째 이름이고, 삭제(unlink)는 이름 하나를 떼어 낸다. 열린 디스크립터가 있으면 실체는 남는다.
    java.io.File
    경로 이름을 담은 불변 값이다. 메서드는 stat, open(O_CREAT|O_EXCL), mkdir, rename, remove 같은 시스템 콜로 이어지지만, 실패를 false·0·null로 돌려줘 오류 번호를 잃는다.
    Path, Files, FileSystemProvider
    Path는 주소, Files는 작업의 관문, provider는 실제 구현이다. 같은 Files 호출이 기본 파일 시스템에서는 시스템 콜로, ZIP 파일 시스템에서는 ZIP 항목 처리로 이어진다.
    예외로 드러나는 원인
    Files는 EACCES, ENOENT, EEXIST를 각각 AccessDeniedException, NoSuchFileException, FileAlreadyExistsException으로 번역하고 메시지에 경로를 넣는다.
    존재 확인과 원자적 생성
    exists와 notExists가 둘 다 거짓이면 판단할 수 없다는 뜻이고, 결과는 즉시 낡는다. createFile은 O_EXCL로 확인과 생성을 한 번에 하므로 경쟁에서 하나만 성공한다.
    rename의 원자성
    같은 파일 시스템 안의 이름 바꾸기는 데이터를 옮기지 않고 원자적이다. Files.move는 EXDEV면 복사 후 삭제로 바꾸고, ATOMIC_MOVE를 주면 대신 AtomicMoveNotSupportedException을 던진다.
    경로 표시
    상대 경로는 JVM 시작 시 getcwd로 정해진 user.dir 기준이다. toAbsolutePath·normalize는 문자열 계산이고, getCanonicalPath·toRealPath는 파일 시스템에 물어 링크를 푼다. 링크가 끼면 normalize는 다른 파일을 가리킬 수 있다.
    경로의 바이트 표현
    OpenJDK의 UnixPath는 경로를 sun.jnu.encoding으로 인코딩한 바이트 배열로 담고 NUL을 거부하며, equals도 바이트로 비교한다. macOS에서 NFC와 NFD 한글 이름은 같은 파일을 열어도 Path로는 다르므로 isSameFile이나 정규화 후 비교를 쓴다.
    디렉터리 순회
    디렉터리 스트림은 readdir로 한 이름씩 지연해서 읽고 순서는 정해져 있지 않다. walk는 깊이만큼 디렉터리를 열어 두며, FOLLOW_LINKS일 때 fileKey로 조상과 비교해 순환을 FileSystemLoopException으로 알린다.
    Files로 문자 파일 읽기
    문자 집합을 생략하면 UTF-8이고 잘못된 바이트는 예외다. readString·readAllLines는 전부를 메모리에 올리고, lines는 지연해서 읽는 대신 닫아야 하며 오류가 UncheckedIOException으로 늦게 드러난다.
    파일 복사 경로
    readAllBytes 방식은 힙과 네이티브 메모리를 파일 크기만큼 쓰며 네 번 복사한다. transferTo와 Files.copy는 커널 내 복사나 매핑을 쓰고, macOS에서 COPY_ATTRIBUTES를 주면 clonefile로 데이터 복사 자체가 없다.

    운영 중인 서버에서 "로그를 지웠는데 디스크 사용률이 그대로"라는 상황은 이 회차의 unlink 규칙으로 바로 설명된다. 로그 파일을 열고 있는 프로세스가 살아 있는 한 실체는 남는다. 이때 할 일은 파일을 더 지우는 것이 아니라 그 디스크립터를 닫게 하는 것이다. 애플리케이션을 재시작하거나, 로그 라이브러리의 재오픈 기능을 쓰거나, 처음부터 파일을 지우는 대신 길이를 0으로 자르는 방식을 고른다. 반대로 같은 성질은 장점이기도 하다. 설정 파일을 임시 파일과 rename으로 교체하면, 이미 옛 파일을 열고 읽는 중인 프로세스는 옛 내용을 끝까지 읽고 새로 여는 프로세스는 새 내용을 본다.

    파일 경로를 외부 입력으로 받는 코드는 보안 경계다. 기준 디렉터리를 절대 경로로 고정하고, 입력을 resolve한 뒤 이름 요소 단위의 Path.startsWith로 검사한다. 문자열 startsWith는 /srv/app2를 /srv/app 안으로 판정하는 실수를 만든다. 기준 디렉터리 안에 다른 사람이 링크를 만들 수 있다면 normalize로는 부족하고 toRealPath로 실제 위치를 확인해야 하며, 확인한 그 경로로 파일을 열어야 검사와 사용 사이의 틈이 생기지 않는다. 판단이 달라지는 조건은 "그 디렉터리에 누가 쓸 수 있는가"다.

    파일을 다루는 코드의 장애 분석은 예외에서 시작한다. File의 false는 원인을 남기지 않으므로, 오래된 코드에서 "가끔 파일이 안 지워진다"는 보고가 오면 먼저 Files.delete로 바꿔 예외를 받아 보는 것이 가장 싼 진단이다. 대용량 파일을 다루는 경로에서는 readAllBytes, readString, readAllLines처럼 파일 크기에 비례해 메모리를 쓰는 호출이 있는지부터 찾는다. 입력 크기를 통제할 수 없다면 lines나 newBufferedReader, 복사라면 Files.copy나 transferTo로 바꾸는 것이 성능 튜닝보다 먼저다.

    3. 서로 다른 파일 시스템 사이에서는 rename이 EXDEV로 실패하므로, ATOMIC_MOVE를 준 Files.move는 AtomicMoveNotSupportedException을 던진다. 설정 파일은 바뀌지 않고 임시 파일이 남는다(정리 코드가 없다면). ATOMIC_MOVE만 빼면 target이 이미 있으므로 OpenJDK 21은 rename을 시도하기도 전에 FileAlreadyExistsException을 던진다. 덮어쓰려면 REPLACE_EXISTING을 줘야 하고, 그러면 OpenJDK 21은 기존 target을 먼저 지운 뒤 rename이 EXDEV로 실패하면 대상에 복사하고 원본을 지운다. 동작은 성공하지만 그 사이 다른 프로세스는 target이 없거나 반쯤 쓰인 상태를 볼 수 있어 원자적 교체라는 목적이 깨진다. 해결은 임시 파일을 target과 같은 디렉터리에 만드는 것이다(Files.createTempFile(target.toAbsolutePath().getParent(), ...)).

    4. 읽기: 힙에 500MB byte[]를 할당한다. read의 네이티브 구현이 요청 길이만큼 malloc(최대 500MB)하고, read 시스템 콜이 페이지 캐시에서 네이티브 버퍼로 복사(1번), SetByteArrayRegion이 네이티브 버퍼에서 힙 배열로 복사(2번)한 뒤 네이티브 버퍼를 해제한다. 쓰기: 다시 malloc(500MB), GetByteArrayRegion으로 힙에서 네이티브로 복사(3번), write 시스템 콜이 대상 페이지 캐시로 복사(4번). 최대치는 힙 500MB와 네이티브 500MB가 동시에 잡히는 순간이다(읽기 중과 쓰기 중 각각). 힙이 500MB보다 작으면 배열 할당에서 OutOfMemoryError가 난다. Files.copy는 힙 배열을 만들지 않는다. 리눅스는 copy_file_range로 커널 안에서 복사하고, macOS는 fcopyfile에 맡기며, 둘 다 안 되면 최소 16KB짜리 네이티브 임시 버퍼로 나눠 옮긴다.

    5. Files.lines가 돌려준 스트림은 열린 파일을 붙들고 있고, count() 같은 종단 연산이 끝나도 스트림을 닫지 않으면 파일은 닫히지 않는다. 반복마다 파일 디스크립터가 하나씩 새다가 프로세스의 열린 파일 수 제한에 닿으면 open이 EMFILE로 실패하고, Files는 이를 FileSystemException으로 번역해 던진다. GC는 힙 메모리가 부족할 때 움직이는 것이지 디스크립터가 부족할 때 움직이지 않는다. 고칠 방법은 try (Stream s = Files.lines(path)) { n = s.count(); }처럼 try-with-resources로 감싸는 것이다.

OpenJDK 21에서 ATOMIC_MOVE 없이 Files.move(source, target)를 불렀는데 source와 target이 서로 다른 파일 시스템에 있다. 무슨 일이 일어나는가? AtomicMoveNotSupportedException이 난다. rename이 커널 안에서 데이터를 옮겨 원자적으로 끝난다. 하드 링크를 만든 뒤 원본 이름을 지운다. rename이 EXDEV로 실패하면 대상에 복사한 다음 원본을 지운다. 이 과정은 원자적이지 않다. inode 번호는 파일 시스템 안에서만 뜻이 있으므로 다른 파일 시스템으로는 디렉터리 엔트리만 옮길 수 없고, rename은 EXDEV로 실패한다. 하드 링크도 같은 이유로 파일 시스템을 넘을 수 없다. JIT 컴파일러가 복사 루프를 최적화했기 때문이다. OpenJDK의 macOS 구현이 clonefile로 원본과 데이터 블록을 공유하는 복제본을 만들어 데이터를 복사하지 않았기 때문이다. COPY_ATTRIBUTES는 속성만 복사하고 내용은 나중에 복사하기 때문이다. Files.copy에는 JIT가 최적화할 자바 복사 루프가 없고, 내용은 복사본을 열면 바로 원본과 같다(mismatch가 -1).
    inode(index node)
    유닉스 계열 파일 시스템에서 파일의 실체를 나타내는 구조. 종류, 권한, 소유자, 크기, 시각, 링크 수, 데이터 위치를 담지만 이름은 담지 않는다.
    디렉터리 엔트리(directory entry)
    디렉터리의 내용을 이루는 "이름 → inode 번호" 쌍. 경로 해석은 이 표를 한 단계씩 따라가는 과정이다.
    하드 링크(hard link)
    같은 inode를 가리키는 또 하나의 디렉터리 엔트리. 같은 파일 시스템 안에서만 만들 수 있고, 링크 수가 0이 되고 열린 디스크립터가 없을 때 실체가 해제된다.
    심볼릭 링크(symbolic link)
    다른 경로 문자열을 내용으로 가진 특수 파일. 경로 해석 중에 만나면 커널이 그 경로로 갈아탄다. 대상이 없어도 존재할 수 있다.
    파일 디스크립터(file descriptor)
    프로세스가 연 파일(또는 소켓)을 가리키는 작은 정수. 열린 뒤에는 이름이 아니라 이 번호로 커널 안의 열린 파일 객체에 접근한다. 프로세스마다 개수 제한이 있다.
    TOCTOU(time-of-check to time-of-use)
    상태를 확인한 시점과 그 결과를 사용하는 시점 사이에 상태가 바뀌어 생기는 경쟁 조건. 확인 대신 원자적 연산을 시도하고 실패를 처리해서 막는다.
    정규화(normalization)와 실제 경로(real path)
    normalize는 .과 이름/..을 문자열로 지우는 계산이고, toRealPath는 파일 시스템에 물어 심볼릭 링크를 모두 푼 절대 경로다.
    유니코드 정규화(NFC, NFD)
    같은 글자를 완성형 코드 포인트 하나(NFC)로 쓸지, 분해된 문자 나열(NFD, 한글은 초성·중성·종성 자모)로 쓸지 정하는 형식. 화면에는 같아 보여도 문자열과 바이트가 다르다.
    스플리터레이터(spliterator)
    스트림의 원천이 원소를 하나씩 내주고(tryAdvance) 자기 범위를 둘로 나누는(trySplit) 방법을 정의한 객체. 병렬 스트림의 효율은 이 분할이 얼마나 고르고 싼지에 달려 있다.
    copy-on-write 복제(clone)
    복사본이 원본과 데이터 블록을 공유하다가 어느 한쪽에 쓰기가 일어날 때 그 부분만 새 블록으로 분리하는 방식. macOS의 clonefile, 리눅스 일부 파일 시스템의 리플링크가 이에 해당한다.
