    이름은 어디까지 통하고, 값은 어디까지 옮겨지는가

    변수를 쓰다 보면 두 가지 물음과 마주친다. 하나는 "방금 선언한 이 이름을 어디에서까지 쓸 수 있는가"다. if 블록 안에서 만든 변수를 블록 밖에서 쓰려고 하면 컴파일러가 그런 변수는 없다고 한다. 다른 하나는 "이 값을 다른 타입의 변수에 넣으면 무슨 일이 생기는가"다. int 값은 long 변수에 그냥 들어가는데 long 값은 int 변수에 들어가지 않고, 억지로 넣으면 엉뚱한 수가 된다.

    앞의 물음이 스코프(scope), 뒤의 물음이 형변환(type conversion)이다. 둘은 주제가 달라 보이지만 성격이 같다. 둘 다 컴파일러가 컴파일 시점에 집행하는 규칙이고, 둘 다 "프로그래머가 모르는 사이에 값이 잘못 쓰이는 일"을 막으려고 존재하며, 둘 다 그 결과가 바이트코드와 스택 프레임에 그대로 남는다. 이 회차에서는 규칙을 외우는 대신 규칙이 무엇을 보호하는지, 그리고 JVM 안에서 실제로 무슨 일이 일어나는지를 따라간다.

    이 장의 핵심

    스코프는 실행 중에 변수가 생기고 사라지는 현상이 아니라 "이 이름을 여기서 써도 되는가"를 정하는 컴파일 시점의 규칙이다. 형변환은 한 타입의 비트 표현을 다른 타입의 비트 표현으로 다시 만드는 일이고, 자바는 값의 크기가 보존되는 방향만 자동으로 해 준다. 그 밖의 방향은 프로그래머가 캐스트로 책임을 표시해야 한다.

    지역 변수와 스코프의 규칙

    지금까지 선언한 변수는 모두 메서드 안에서 선언한 지역 변수(local variable)다. 지역 변수에는 그 이름을 쓸 수 있는 구간이 정해져 있고, 이 구간을 스코프라 한다. JLS §6.3이 정하는 규칙은 다음 세 가지로 요약된다.

    • 블록 안에서 선언한 지역 변수의 스코프는 선언문의 초기화식에서 시작해 그 선언을 감싼 블록이 끝나는 곳까지다. 블록은 중괄호 한 쌍이다.
    • for 문의 초기화식에서 선언한 변수의 스코프는 그 for 문의 초기화식·조건식·갱신식·본문까지다.
    • 메서드의 매개변수의 스코프는 메서드 본문 전체다.
    public class ScopeDemo {
    public static void main(String[] args) {
        int n = 3;
        {
            int inner = n * 2;
            System.out.println("inner = " + inner);
        }
        // System.out.println(inner);   // 컴파일 오류: 여기서는 inner라는 이름이 없다

        for (int i = 0; i < 2; i++) {
            int twice = i * 2;
            System.out.println("twice = " + twice);
        }
        // System.out.println(i);       // 컴파일 오류
        // System.out.println(twice);   // 컴파일 오류

        int temp = 10;
        System.out.println("temp = " + temp);
    }
}
    inner = 6
twice = 0
twice = 2
temp = 10

    n은 메서드 본문 블록에서 선언됐으므로 그 아래 어디서나, 안쪽 블록에서도 쓸 수 있다. 안쪽 블록은 바깥 블록에 포함되어 있기 때문이다. 반대 방향은 성립하지 않는다. inner는 안쪽 블록이 끝나는 순간 이름으로서 효력을 잃는다. 주석 처리한 줄을 살리면 javac는 그 기호를 찾을 수 없다는 오류를 낸다. 변수가 "있는데 접근이 막힌" 것이 아니라 그 위치에서는 그런 이름이 아예 선언된 적이 없는 것으로 취급된다.

    스코프는 선언한 줄에서 시작하므로 선언보다 위에서는 쓸 수 없다. System.out.println(y); int y = 1;은 컴파일 오류다. 스코프가 "초기화식에서 시작한다"는 규칙의 결과로 int y = y + 1;에서 오른쪽의 y는 방금 선언하고 있는 그 y를 가리킨다. 이름은 통하지만 아직 값이 없는 변수를 읽는 것이어서, 뒤에서 다룰 확정 할당 규칙에 걸려 역시 컴파일 오류가 된다.

    같은 이름을 다시 선언할 수 있는가

    서로 포함 관계가 없는 블록에서는 같은 이름을 다시 써도 된다. 한 메서드 안에 for (int i = 0; ...)를 여러 번 쓸 수 있는 이유다. 첫 번째 for 문이 끝나면 i의 스코프도 끝나므로 두 번째 for 문의 i는 이름만 같은 다른 변수다. 반면 어떤 지역 변수의 스코프 안에서 같은 이름의 지역 변수를 또 선언하는 것은 금지된다.

    int x = 1;
{
    int x = 2;      // 컴파일 오류: x는 이미 이 메서드에 정의되어 있다
}

int i = 0;
for (int i = 0; i < 3; i++) { }   // 같은 이유로 컴파일 오류

    JLS §6.4는 지역 변수 v의 스코프 안에서 v라는 이름으로 새 변수를 선언하면 컴파일 오류라고 정한다. C나 C++에서는 안쪽 블록의 변수가 바깥 변수를 가리는 것(shadowing)이 허용되지만 자바는 지역 변수끼리의 가림을 허용하지 않는다. 안쪽에서 x를 고쳤는데 바깥의 x는 그대로인 종류의 혼란을 언어 차원에서 없앤 것이다. 매개변수도 지역 변수와 같은 취급을 받으므로 매개변수와 이름이 같은 지역 변수도 선언할 수 없다. 다만 클래스에 선언하는 필드는 사정이 달라서 지역 변수가 같은 이름의 필드를 가릴 수 있다. 이 경우는 기본편에서 this와 함께 다룬다.

    스코프는 컴파일러의 규칙이다 — 스택 프레임의 슬롯

    스코프를 처음 배우면 "블록에 들어갈 때 변수가 만들어지고 블록을 나올 때 변수가 지워진다"고 상상하기 쉽다. 언어 명세도 지역 변수가 블록에 들어갈 때 생겨나 스코프를 벗어나면 존재하지 않게 된다고 서술한다(JLS §4.12.3). 그런데 JVM에서 실제로 일어나는 일은 이 상상과 다르다. 바이트코드에는 "변수를 만들어라"나 "변수를 없애라"에 해당하는 명령이 없다.

    메서드가 호출되면 스택 프레임(frame)이 하나 만들어지고, 메서드가 끝나면 그 프레임이 사라진다(JVMS §2.6). 프레임 안에는 지역 변수 배열(local variable array)이 있다. JVMS §2.6.1에 따르면 이 배열의 길이는 컴파일 시점에 정해져 클래스 파일에 기록되고, 배열의 칸 하나(슬롯)는 boolean, byte, char, short, int, float, 참조 값 하나를 담으며, long과 double은 연속한 두 칸을 차지한다. 곧 메서드가 쓸 변수 자리는 메서드가 시작될 때 한꺼번에 마련되고, 블록에 들어가고 나오는 동안에는 아무 일도 일어나지 않는다. 그렇다면 스코프는 어디에 반영될까. 다음 메서드로 확인한다.

    public class Scope {
    static int reuse(int n) {
        int result = 0;
        if (n > 0) {
            int doubled = n * 2;
            result += doubled;
        }
        {
            long big = n * 10L;
            result += (int) big;
        }
        for (int i = 0; i < n; i++) {
            int square = i * i;
            result += square;
        }
        int last = result + 1;
        return last;
    }
}

    이 메서드에는 매개변수를 포함해 변수가 일곱 개 있고(n, result, doubled, big, i, square, last) 그중 big은 long이다. 변수마다 전용 칸을 준다면 여덟 칸이 필요하다. javac -g Scope.java로 컴파일하고 javap -v Scope로 보면 다음 정보가 나온다. -g는 지역 변수의 이름과 위치를 디버깅 정보로 클래스 파일에 넣으라는 옵션이다. javac는 기본적으로 줄 번호와 소스 파일 정보만 넣기 때문에 이 옵션이 없으면 아래의 LocalVariableTable은 나오지 않는다.

    locals=4가 지역 변수 배열의 길이다. 여덟 칸이 아니라 네 칸이다. LocalVariableTable의 각 줄은 변수 하나가 바이트코드의 어느 구간(Start부터 Length만큼)에서 어느 슬롯에 들어 있는지를 알려 준다. Signature의 I는 int, J는 long이다. 슬롯 2를 보면 doubled, big, i, last 네 변수가 서로 겹치지 않는 구간에서 번갈아 쓰고 있다. 스코프가 끝난 변수의 칸을 다음 변수가 물려받은 것이다.

    이 그림에서 읽어야 할 것이 세 가지 있다. 첫째, 스코프는 실행 중의 사건이 아니라 컴파일러의 장부다. 컴파일러는 소스를 읽으면서 "지금 유효한 이름과 그 슬롯 번호"의 표를 관리하고, 블록이 끝나면 그 블록에서 선언된 이름을 표에서 지우고 슬롯 번호를 반납받는다. 실행 시점에는 이름이 없다. istore_2, iload_2 같은 명령에 슬롯 번호만 남는다. 둘째, 스코프가 끝났다고 값이 지워지는 것도 아니다. if 블록이 끝난 뒤에도 슬롯 2에는 doubled의 값이 남아 있다가 big을 저장할 때 덮어쓰인다. 다만 그 값을 가리킬 이름이 소스에 없으므로 읽을 방법이 없을 뿐이다. 셋째, 반복문 본문에서 선언한 square는 매 바퀴 같은 슬롯 3을 쓴다. 05회에서 말한 "본문 안의 선언이 매번 메모리를 새로 잡지 않는다"는 사실의 근거가 이것이다.

    슬롯을 재사용하는 것은 OpenJDK javac의 동작이고, JVM 명세가 요구하는 것은 아니다. 명세가 정하는 것은 지역 변수 배열의 길이가 클래스 파일의 max_locals 항목에 기록된다는 것과 각 타입이 차지하는 칸 수뿐이다(JVMS §4.7.3). LocalVariableTable도 디버거를 위한 선택적 정보여서(JVMS §4.7.13) 없어도 프로그램은 똑같이 실행된다.
    스택 프레임의 지역 변수 배열 네 칸이 시간에 따라 어떤 변수에 쓰이는지, 특히 슬롯 2를 네 변수가 번갈아 쓰는 모습을 보여 준다. 가로축이 실행 순서, 세로축이 슬롯인 표 형태의 다이어그램. 왼쪽 끝에 세로로 네 개의 행 머리글 "슬롯 0", "슬롯 1", "슬롯 2", "슬롯 3"이 있고, 전체를 감싸는 테두리 위에 제목 "reuse 메서드의 스택 프레임: 지역 변수 배열". 슬롯 0 행에는 처음부터 끝까지 이어지는 긴 회색 막대 "n". 슬롯 1 행에는 거의 처음부터 끝까지 이어지는 긴 회색 막대 "result". 슬롯 2 행에는 왼쪽부터 서로 떨어진 네 개의 색 막대가 차례로 놓인다: 파란 막대 "doubled", 주황 막대 "big", 초록 막대 "i", 보라 막대 "last". 슬롯 3 행에는 주황 막대 "big"의 아래쪽 연장(같은 주황색, 슬롯 2의 막대와 세로로 이어진 모양)과, 초록 막대 "i" 구간 안쪽에 짧은 연두색 막대 "square". 슬롯 2 행의 막대들 사이 빈 틈 위에 작은 화살표와 라벨 "스코프 종료 후 재사용". 주황 막대 옆에 라벨 "long은 두 칸". 아래쪽 가로축 화살표에 라벨 "바이트코드 실행 순서". 흰 배경, 평면 스타일. 프레임의 지역 변수 배열은 메서드가 시작될 때 길이가 정해져 있다. 스코프는 그 칸들을 어느 구간에서 어떤 이름으로 부를지를 정하는 컴파일러의 규칙이다.

    스코프가 존재하는 이유

    변수의 스코프를 모두 메서드 전체로 하면 규칙은 더 단순해진다. 그런데도 언어가 스코프를 블록 단위로 나누고, 좋은 코드가 변수를 되도록 좁은 스코프에 두려 하는 데에는 이유가 있다. 두 수를 교환하는 코드로 비교한다.

    // (가) 임시 변수를 메서드 맨 위에 선언
int temp = 0;
// ... 여러 줄 ...
if (a > b) {
    temp = a;
    a = b;
    b = temp;
}
// ... 이 아래 어디서든 temp를 읽거나 고칠 수 있다

// (나) 임시 변수를 필요한 블록 안에 선언
if (a > b) {
    int temp = a;
    a = b;
    b = temp;
}
// 여기서는 temp라는 이름이 없다

    (가)에서 temp는 교환이 끝난 뒤에도 살아 있는 이름이다. 메서드가 길어지면 누군가 아래쪽에서 다른 용도로 temp를 다시 쓰거나, 교환 전의 낡은 값이 들어 있는 줄 모르고 읽을 수 있다. 코드를 읽는 사람은 temp가 쓰이는 곳을 찾으려면 메서드 전체를 살펴야 한다. (나)에서는 temp와 관련된 모든 일이 세 줄 안에서 끝난다는 것을 컴파일러가 보장한다. 블록 밖에서 쓰면 컴파일이 되지 않으니 실수할 길 자체가 없다.

    스코프를 좁히면 얻는 것을 정리하면 이렇다. 변수를 읽고 쓰는 코드의 범위가 줄어 그 변수의 값이 어떻게 변하는지 추적하기 쉬워진다. 용도가 끝난 이름이 사라지므로 같은 이름을 다른 곳에서 안전하게 다시 쓸 수 있다. 그리고 "이 값은 여기서만 의미가 있다"는 의도가 코드 구조로 표현된다. 05회에서 for 문의 제어 변수가 for 문 안에 갇히는 것을 장점으로 꼽은 것도 같은 맥락이다. while 문으로 쓰면 제어 변수를 반복문 위에 선언해야 하므로 반복이 끝난 뒤에도 이름이 남는다.

    메모리 관점의 이득도 있지만 정확히 말할 필요가 있다. 앞에서 본 대로 스코프가 겹치지 않는 변수들은 같은 슬롯을 나눠 쓰므로 프레임의 지역 변수 배열이 작아질 수 있다. 하지만 이것은 메서드 호출 한 번에 몇 칸을 쓰느냐의 문제이고, 블록을 나갈 때마다 메모리가 반환되는 것은 아니다. 프레임은 메서드가 끝날 때 통째로 사라진다. 스코프를 좁히는 일차적인 이유는 메모리가 아니라 코드를 이해하고 고치기 쉽게 만드는 데 있다. 실천 지침은 간단하다. 변수는 처음 값이 필요한 자리에서, 가능한 한 가장 안쪽 블록에, 초깃값과 함께 선언한다.

    확정 할당 — 값이 없는 변수는 읽을 수 없다

    지역 변수는 선언만 하고 초기화하지 않을 수 있다. 그러나 값을 넣기 전에 읽을 수는 없다.

    int k;
System.out.println(k);   // 컴파일 오류: 변수 k가 초기화되지 않았을 수 있다

    JLS §4.12.5는 변수의 종류에 따라 초깃값 규칙을 다르게 정한다. 클래스에 선언하는 필드와 배열의 원소는 만들어질 때 기본값(숫자는 0, boolean은 false, 참조는 null)으로 초기화된다. 지역 변수에는 기본값이 없다. 지역 변수는 쓰이기 전에 초기화나 대입으로 값을 명시적으로 받아야 하고, 그 사실을 확정 할당(definite assignment) 규칙으로 검증할 수 있어야 한다. 이 규칙이 JLS 16장 전체의 내용이다.

    16장의 기본 생각은 한 문장이다. 변수를 읽는 지점에 이르는 가능한 모든 실행 경로에서 그 변수에 대한 대입이 일어나야 한다. 컴파일러는 프로그램을 실행해 보지 않고 문장과 식의 구조만 보고 이것을 판정한다. 몇 가지 경우를 보자. 아래에서 n은 int 매개변수다.

    코드 (마지막에 k를 읽는다)결과이유
    int k; if (n > 2) k = 3; print(k);오류조건이 거짓인 경로에서는 대입이 없다
    int k; if (n > 2) k = 3; else k = 4; print(k);통과두 경로 모두에서 대입된다
    int k; for (int i = 0; i < 3; i++) { k = i; } print(k);오류규칙상 반복문 본문은 한 번도 실행되지 않을 수 있다
    int k; while (true) { k = n; if (k >= 5) break; n = 6; } print(k);통과조건이 상수 true이므로 나가는 길은 break뿐이고, break 앞에서 대입된다
    int k; switch (n) { case 1: k = 1; break; case 2: k = 2; break; } print(k);오류어느 case에도 해당하지 않는 경로가 있다
    위 switch에 default: k = 0;을 추가통과모든 경로에서 대입된다

    세 번째 줄이 눈에 띈다. 사람이 보기에는 반복이 세 번 도는 것이 분명한데 컴파일러는 오류를 낸다. 여기에 확정 할당의 성격이 드러난다. JLS 16장은 분석이 조건 연산자 &&, ||, !, ? :와 boolean 값의 상수식만을 특별히 취급하고, 그 밖에는 식의 값을 고려하지 않는다고 명시한다. i < 3은 변수가 들어 있어 상수식이 아니므로, 컴파일러는 그 값이 처음부터 거짓일 가능성을 배제하지 않는다. 명세에 실린 예가 이 점을 더 분명히 보여 준다.

    int k;
int m = 5;
if (m > 2)
    k = 3;
System.out.println(k);   // 컴파일 오류

    m이 5라는 것은 바로 윗줄에 적혀 있다. 그래도 오류다. JLS는 이 코드에 대해, 값을 컴파일 시점에 알 수 있더라도 컴파일러는 이 장에 정해진 규칙대로 동작해야 하고 규칙은 상수식만 인정한다고 설명한다. m의 선언을 final int m = 5;로 바꾸면 통과한다. 상수식으로 초기화된 final 변수는 상수 변수(constant variable)이고(JLS §4.12.4), 그러면 m > 2가 값이 true인 상수식이 되기 때문이다. 같은 이유로 if (true) k = 3; 뒤에서 k를 읽는 것도 통과한다.

    이 엄격함은 결함이 아니라 설계다. 규칙이 "컴파일러가 얼마나 똑똑한가"에 달려 있다면 같은 소스가 어떤 컴파일러에서는 통과하고 다른 컴파일러에서는 거부될 것이다. 규칙을 명세에 기계적으로 적어 두었기 때문에 모든 자바 컴파일러가 같은 프로그램을 받아들인다. 조건 연산자에 대한 특별 취급도 같은 방식으로 규칙에 적혀 있다.

    int k;
if (n > 0 && (k = System.in.read()) >= 0)
    System.out.println(k);    // 통과

int j;
if (n > 0 || (j = System.in.read()) >= 0)
    System.out.println(j);    // 컴파일 오류

    && 전체가 참이 되려면 오른쪽 피연산자가 반드시 평가되어야 하므로, if의 본문에 도달했다면 k에 대입이 일어난 것이 확실하다. ||에서는 왼쪽이 참이면 오른쪽을 평가하지 않고도 전체가 참이 되므로 j에 대입되지 않은 채 본문에 도달하는 경로가 있다. 04회에서 본 단락 평가의 점프 구조가 그대로 규칙에 반영되어 있다. 하나 더, k++나 k += 1도 변수의 현재 값을 읽는 연산이므로 대입 전에 쓰면 같은 오류가 난다.

    JVM도 같은 것을 검사한다

    컴파일러가 이렇게 검사하므로 javac가 만든 클래스 파일에는 값이 없는 슬롯을 읽는 코드가 들어갈 수 없다. 그런데 JVM은 자신이 읽어 들이는 클래스 파일이 javac가 만든 것인지 알 수 없다. JVMS §4.9.2는 바이트코드가 지켜야 할 구조적 제약 가운데 하나로, 어떤 지역 변수도 값이 대입되기 전에 접근되어서는 안 된다는 것을 든다. 그리고 §4.10은 JVM이 클래스를 링크하는 시점에 이런 제약이 지켜졌는지 스스로 검증한다고 정한다. 검증을 통과하지 못한 클래스는 실행되지 않는다.

    왜 지역 변수에만 기본값이 없는지도 이 구조로 이해할 수 있다. 필드와 배열 원소는 여러 메서드가 읽고 쓸 수 있으므로, 누가 먼저 읽을지를 컴파일 시점에 추적할 수 없다. 그래서 기본값이라는 안전망을 둔다. 지역 변수는 메서드 하나 안에서만 읽히므로 "읽기 전에 반드시 대입되는가"를 그 메서드의 코드만 보고 완전히 판정할 수 있다. 판정할 수 있다면 기본값으로 덮어 두는 것보다 오류로 알려 주는 편이 낫다. 초기화를 잊은 변수가 조용히 0으로 동작하는 것은 버그를 감추는 일이기 때문이다.

    switch 블록의 스코프

    스코프와 확정 할당이 함께 얽히는 사례가 전통적인 switch 문이다. 콜론 라벨을 쓰는 switch에서는 중괄호 한 쌍 안에 모든 case가 들어 있으므로 switch 본문 전체가 블록 하나다. 따라서 한 case에서 선언한 변수의 스코프는 뒤따르는 case들까지 이어진다.

    switch (n) {
    case 1:
        int x = 1;
        break;
    case 2:
        // int x = 2;             // 컴파일 오류: x는 이미 정의되어 있다
        // System.out.println(x); // 컴파일 오류: x가 초기화되지 않았을 수 있다
        x = 2;                    // 통과: 이름은 통하고, 대입은 읽기가 아니다
        System.out.println(x);
        break;
}

    case 2로 곧장 진입하면 int x = 1;이라는 문장은 실행되지 않지만 x라는 이름은 같은 블록 안이라 유효하다. JLS §4.12.3은 이 상황을 선언문의 실행을 건너뛰고 블록에 들어갈 수 있는 예외적인 경우로 따로 언급하면서, 확정 할당 규칙 덕분에 그런 변수를 값 없이 읽을 수는 없다고 설명한다. 스코프(이름이 통하는가)와 확정 할당(값이 있는가)이 별개의 검사라는 것을 보여 주는 예다. 화살표 라벨에 중괄호 블록을 쓰는 switch에서는 case마다 블록이 따로 있으므로 이런 일이 생기지 않는다.

    형변환이 필요한 이유 — 타입마다 다른 비트 표현

    이제 두 번째 물음으로 넘어간다. 02회에서 본 대로 기본형은 타입마다 크기와 표현 방식이 다르다. 같은 수 10이라도 byte에서는 8비트, int에서는 32비트의 2의 보수 정수이고, double에서는 부호·지수·가수로 나뉜 64비트 부동소수점이다. 그러므로 한 타입의 값을 다른 타입의 변수에 넣는 일은 단순한 복사가 아니라 비트 표현을 다시 만드는 변환이다.

    타입크기표현나타낼 수 있는 범위
    byte8비트부호 있는 정수(2의 보수)-128 ~ 127
    short16비트부호 있는 정수-32,768 ~ 32,767
    char16비트부호 없는 정수0 ~ 65,535
    int32비트부호 있는 정수-2,147,483,648 ~ 2,147,483,647
    long64비트부호 있는 정수-9,223,372,036,854,775,808 ~ 9,223,372,036,854,775,807
    float32비트부동소수점(유효 자릿수 24비트)크기는 넓지만 정밀도는 24비트
    double64비트부동소수점(유효 자릿수 53비트)크기는 넓지만 정밀도는 53비트

    변환을 볼 때는 두 가지를 묻는다. 원래 타입의 모든 값을 대상 타입이 나타낼 수 있는가. 그리고 그 변환을 컴파일러가 알아서 해 주는가, 프로그래머가 명시해야 하는가. 자바는 변환의 종류를 JLS 5장에 하나하나 열거해 두었다. 기본형 사이의 변환은 넓히는 쪽인 확장 변환(widening primitive conversion)과 좁히는 쪽인 축소 변환(narrowing primitive conversion)으로 나뉘고, 대입문에서 자동으로 일어나는 것은 원칙적으로 확장 변환뿐이다. boolean은 어느 쪽에도 끼지 않는다. boolean과 숫자 타입 사이에는 어떤 변환도 캐스트도 허용되지 않는다.

    자동 형변환 — 확장 변환

    JLS §5.1.2는 확장 변환 19가지를 나열한다. 화살표를 따라가는 방향이면 모두 확장 변환이다.

    byte ──▶ short ──▶ int ──▶ long ──▶ float ──▶ double
                    ▲
char ───────────────┘

· byte  → short, int, long, float, double
· short → int, long, float, double
· char  → int, long, float, double
· int   → long, float, double
· long  → float, double
· float → double

    확장 변환은 캐스트 없이 대입만으로 일어난다. int i = 10; long l = i; double d = i;는 모두 그대로 컴파일된다. 바이트코드에는 변환이 명령으로 남는다.

    static long widen(int i) {
    long l = i;
    return l;
}
           0: iload_0
       1: i2l
       2: lstore_1
       3: lload_1
       4: lreturn

    소스에는 보이지 않던 i2l(int to long)이 끼어 있다. "자동"이라는 말은 변환이 일어나지 않는다는 뜻이 아니라 컴파일러가 변환 명령을 대신 넣어 준다는 뜻이다. JVMS §2.11.4는 확장 변환 명령으로 i2l, i2f, i2d, l2f, l2d, f2d 여섯 개를 든다. 19가지 변환에 명령이 여섯 개뿐인 것은 byte, short, char에서 출발하는 변환에 전용 명령이 없기 때문이다. 04회에서 보았듯 이 타입들은 JVM 안에서 이미 int로 다뤄진다. byte 변수를 int 변수에 대입하는 코드를 컴파일하면 변환 명령 없이 iload와 istore만 나온다. byte에서 double로 가는 변환은 i2d 하나다.

    부호 확장과 0 확장

    정수를 더 넓은 정수로 바꿀 때 늘어난 윗자리를 무엇으로 채우는가가 문제다. JLS §5.1.2는 부호 있는 정수의 확장은 2의 보수 표현을 부호 확장(sign extension)하고, char의 확장은 0 확장(zero extension)한다고 정한다. 부호 확장은 원래 값의 최상위 비트(부호 비트)를 늘어난 자리에 복사하는 것이다.

    byte -1   =                            1111 1111
int로 확장 = 1111 1111 1111 1111 1111 1111 1111 1111   = -1   (부호 비트 1을 복사)

byte 10   =                            0000 1010
int로 확장 = 0000 0000 0000 0000 0000 0000 0000 1010   = 10   (부호 비트 0을 복사)

char '￿' =              1111 1111 1111 1111
int로 확장    = 0000 0000 0000 0000 1111 1111 1111 1111   = 65535 (윗자리를 0으로 채움)

    2의 보수 표현에서는 부호 비트를 복사해 윗자리를 채우면 값이 변하지 않는다. 그래서 정수 타입 사이의 확장 변환은 값을 정확히 보존한다. char는 부호가 없는 타입이라 윗자리를 0으로 채워야 값이 보존된다. 16비트가 모두 1인 비트열이 short라면 -1이고 char라면 65,535인 까닭이 여기에 있다. 같은 비트열이라도 타입이 해석을 정한다.

    char와 short 사이에는 자동 변환이 없다

    그림에서 char는 short로도, short는 char로도 가는 화살표가 없다. 둘 다 16비트이지만 범위가 어긋나 있기 때문이다. short는 음수를 나타낼 수 있고 char는 그럴 수 없으며, char는 32,768 이상을 나타낼 수 있고 short는 그럴 수 없다. 어느 쪽도 다른 쪽을 완전히 담지 못하므로 양방향 모두 축소 변환으로 분류되어 캐스트가 필요하다. byte에서 char로의 변환도 자동이 아니다. JLS §5.1.4는 이것을 byte를 int로 확장한 다음 int를 char로 축소하는 두 단계 변환으로 따로 정의한다. "크기가 작은 타입에서 큰 타입으로"라고만 외우면 이 경우들을 틀린다. 기준은 비트 수가 아니라 값의 범위가 포함되는가다.

    넓히는데 값이 달라진다 — int→float, long→float, long→double

    확장 변환이면 값이 언제나 정확히 보존된다고 생각하기 쉽다. JLS §5.1.2는 값이 정확히 보존되는 경우를 따로 열거한다. 정수 타입에서 정수 타입으로, byte·short·char에서 실수 타입으로, int에서 double로, float에서 double로 가는 변환이다. 이 목록에서 빠진 세 가지, 곧 int에서 float로, long에서 float로, long에서 double로 가는 변환은 정밀도 손실(loss of precision)이 일어날 수 있다고 명세가 분명히 적고 있다.

    int i = 16777217;                     // 2의 24제곱 + 1
float f = i;                          // 캐스트 없이 컴파일된다
System.out.println(f);                // 1.6777216E7
System.out.println((int) f);          // 16777216
System.out.println(i == (int) f);     // false

long big = 123456789012345678L;
float fb = big;
System.out.println((long) fb);        // 123456790519087104

long id = 9007199254740993L;          // 2의 53제곱 + 1
double d = id;
System.out.println((long) d);         // 9007199254740992

    첫 번째 예에서 int 값이 float를 거쳐 돌아오자 1이 사라졌다. 원인은 float의 구조에 있다. float는 32비트 가운데 부호에 1비트, 지수에 8비트를 쓰고, 수의 유효 숫자를 담는 가수 쪽 정밀도는 24비트다. int는 최대 31비트의 유효 숫자를 가질 수 있다. 16,777,217을 이진수로 쓰면 1 뒤에 0이 23개, 그리고 마지막에 1이 오는 25자리 수다. 유효 숫자 25비트를 24비트에 담을 수 없으므로 마지막 비트가 반올림으로 사라진다.

    int 16777217   =  1 0000 0000 0000 0000 0000 0001      (유효 숫자 25비트)
                  └──────── float에 담기는 24비트 ──┘└ 넘치는 1비트

이웃한 float 값   1 0000 0000 0000 0000 0000 0000  =  16777216   (가수의 마지막 비트가 0)
                  1 0000 0000 0000 0000 0000 0010  =  16777218   (가수의 마지막 비트가 1)

16777217은 두 값의 정확히 가운데 → 마지막 비트가 0인 16777216으로 반올림

    변환 결과는 아무 값이나 되는 것이 아니다. 명세는 결과가 가장 가까운 값으로 반올림(round to nearest)한, 올바르게 반올림된 값이어야 한다고 정한다. JLS §15.4에 따르면 이 반올림 방식은 표현 가능한 가장 가까운 값을 고르고, 두 값이 똑같이 가까우면 가수의 마지막 비트가 0인 쪽을 고른다. 16,777,217은 16,777,216과 16,777,218의 한가운데이므로 뒤의 규칙으로 16,777,216이 된다.

    값이 커질수록 오차도 커진다. 유효 숫자가 24비트로 고정되어 있으므로 float가 나타낼 수 있는 이웃한 두 값 사이의 간격이 수의 크기에 비례해 벌어지기 때문이다. 123,456,789,012,345,678은 이진수로 57자리다. float에는 위쪽 24자리만 남고 아래 33자리는 반올림으로 사라지므로, float가 나타낼 수 있는 값은 이 크기에서 2의 33제곱(8,589,934,592) 간격으로만 존재한다. 변환 결과가 원래 값과 약 15억이나 차이 나는 이유다. double은 정밀도가 53비트여서 9,007,199,254,740,992(2의 53제곱)까지의 정수는 모두 정확히 나타내지만, 그 다음 수부터는 long과 일대일로 대응하지 못한다.

    그런데도 이 변환들이 "확장"으로 분류되어 자동으로 일어나는 이유는 분류의 기준이 정밀도가 아니라 크기에 있기 때문이다. JLS의 표현으로 확장 변환은 수치의 전체적인 크기(magnitude)에 관한 정보를 잃지 않는다. long의 최댓값은 약 9.2 × 1018이고 float는 약 3.4 × 1038까지 나타낼 수 있으므로, 어떤 long 값도 float로 옮겼을 때 자릿수가 틀리게 되지는 않는다. 다만 아래쪽 자릿수가 뭉개질 뿐이다. 반대로 축소 변환에서는 뒤에서 보듯 크기와 부호까지 달라질 수 있다.

    정밀도 손실이 있어도 확장 변환은 실행 중에 예외를 던지지 않고(JLS §5.1.2) 컴파일러도 경고하지 않는다. 금액, 식별자, 타임스탬프처럼 한 자리도 틀리면 안 되는 long 값이 float나 double과 한 식에 섞이지 않도록 하는 것은 프로그래머의 몫이다.
    57비트짜리 long 값의 위쪽 24비트만 float의 가수에 담기고 나머지 아래쪽 비트는 반올림으로 사라진다는 것을 보여 준다. 위아래 두 줄로 구성된 비트 다이어그램. 윗줄: 길고 가는 가로 막대가 작은 칸들로 나뉘어 있고 왼쪽에 라벨 "long 값 (유효 숫자 57비트)". 막대의 왼쪽 24칸은 파란색으로 칠하고 그 위에 중괄호와 라벨 "위쪽 24비트", 나머지 오른쪽 33칸은 연한 회색으로 칠하고 그 위에 중괄호와 라벨 "아래쪽 33비트". 아랫줄: 더 짧은 가로 막대가 세 구역으로 나뉘어 있고 왼쪽에 라벨 "float (32비트)". 첫 구역은 아주 좁은 노란 칸 "부호 1", 둘째 구역은 초록 칸 "지수 8", 셋째 구역은 넓은 파란 칸 "가수: 정밀도 24비트". 윗줄의 파란 24칸에서 아랫줄의 파란 가수 구역으로 굵은 파란 화살표를 그리고 라벨 "그대로 담김". 윗줄의 회색 33칸에서 아래로 향하는 점선 화살표가 휴지통 모양 아이콘으로 이어지고 라벨 "반올림 후 사라짐". 오른쪽 아래에 작은 설명 상자 "이웃한 float 값의 간격 = 2의 33제곱". 흰 배경, 평면 스타일. float의 정밀도는 24비트다. 그보다 긴 유효 숫자를 가진 정수는 위쪽 24비트만 남고, 수가 클수록 사라지는 아래쪽 비트가 많아진다.

    명시적 형변환 — 축소 변환과 비트 자르기

    반대 방향, 곧 범위가 넓은 타입의 값을 좁은 타입에 넣는 변환은 자동으로 일어나지 않는다. long l = 1; int i = l;이나 int i = 3.5;를 쓰면 javac는 손실이 생길 수 있는 변환(possible lossy conversion)이라는 컴파일 오류를 낸다. 값이 실제로 범위 안에 있는지와 무관하다. l에 들어 있는 것이 1이어도 타입이 long이면 거부된다. 이 변환을 하려면 괄호 안에 대상 타입을 적는 캐스트(cast)를 써야 한다.

    long l = 3000000000L;
int i = (int) l;            // 컴파일된다. 값은 -1294967296
double d = 3.99;
int n = (int) d;            // 3

    캐스트는 "값이 달라질 수 있음을 알고 있다"는 프로그래머의 서명이다. 컴파일러는 그 서명이 있으면 더 묻지 않고 변환 명령을 넣는다. JLS §5.1.3은 축소 변환 22가지를 나열하고, 그 결과가 어떻게 계산되는지를 정확히 정한다. 먼저 정수에서 더 좁은 정수로 가는 경우다. 규칙은 한 문장이다. 대상 타입의 비트 수를 n이라 할 때 아래쪽 n비트만 남기고 나머지를 버린다.

    int 200          = 0000 0000 0000 0000 0000 0000 1100 1000
(byte) 200       =                               1100 1000
                                                 ▲
                              byte의 부호 비트가 1 → 음수
                              2의 보수로 읽으면 -128 + 64 + 8 = -56

    200은 byte의 범위(-128~127)를 벗어난다. 아래쪽 8비트 1100 1000만 남기면 최상위 비트가 1인 비트열이 되고, byte는 이것을 2의 보수로 해석하므로 -56이 된다. 산술적으로 보면 2의 8제곱인 256을 뺀 값이다(200 - 256 = -56). 버려진 윗자리에 0이 아닌 비트가 있었다면 그 정보는 흔적 없이 사라진다. 같은 규칙으로 계산한 결과 몇 가지를 표로 정리한다.

    바이트코드에서 이 변환은 l2i, i2b, i2s, i2c로 나타난다. JVMS는 l2i가 long의 아래쪽 32비트를 취하고 위쪽 32비트를 버린다고, i2b는 int를 byte로 잘라낸 뒤 다시 int로 부호 확장한다고 설명한다. 지역 변수 슬롯과 피연산자 스택에서는 byte도 int 크기로 다뤄지므로, 잘라낸 결과를 다시 32비트로 펴서 넣는 것이다. long을 byte로 바꾸는 (byte) l에는 전용 명령이 없어서 l2i와 i2b 두 명령이 연달아 나온다.

    강조해 둘 점은 이 변환이 조용하다는 것이다. JLS §5.1.3은 오버플로나 정보 손실이 일어나더라도 축소 변환은 실행 중에 예외를 던지지 않는다고 명시한다. 값이 범위를 벗어나 전혀 다른 수가 되어도 프로그램은 아무 일 없다는 듯 계속 실행된다. 범위를 벗어나면 예외를 받고 싶을 때는 캐스트 대신 Math.toIntExact(long) 같은 메서드를 쓴다. 이 메서드에 3,000,000,000을 넣으면 ArithmeticException이 발생한다.

    32비트 int에서 아래 8비트만 잘라 byte로 만들고, 그 8비트가 2의 보수로 다시 해석되어 음수가 되는 과정을 보여 준다. 세 줄로 구성된 비트 다이어그램. 첫째 줄: 32개의 작은 칸이 가로로 이어진 막대, 왼쪽에 라벨 "int 200". 왼쪽 24칸은 연한 회색으로 모두 "0", 오른쪽 8칸은 파란색으로 "1 1 0 0 1 0 0 0". 회색 24칸 위에 라벨 "버려지는 위쪽 24비트"와 가위 아이콘이 24번째 칸과 25번째 칸 사이의 경계에 놓인다. 둘째 줄: 첫째 줄의 파란 8칸 바로 아래에 같은 8칸 "1 1 0 0 1 0 0 0"만 놓이고 왼쪽에 라벨 "(byte) 200". 첫째 줄의 파란 구역에서 둘째 줄로 내려오는 굵은 파란 화살표와 라벨 "아래쪽 8비트만 남김". 둘째 줄의 맨 왼쪽 칸 "1"을 주황색 테두리로 강조하고 라벨 "부호 비트". 셋째 줄: 계산식 상자 "-128 + 64 + 8 = -56"과 그 옆에 큰 글씨 "-56". 둘째 줄에서 셋째 줄로 화살표와 라벨 "2의 보수로 해석". 흰 배경, 고정폭 글꼴의 숫자, 평면 스타일. 정수의 축소 변환은 계산이 아니라 절단이다. 남은 비트의 최상위 비트가 새 타입의 부호 비트가 되므로 양수가 음수로 바뀔 수 있다.

    실수를 정수로 — 버림, 포화, 그리고 두 단계 변환

    실수에서 정수로 가는 축소 변환은 비트를 자르는 방식이 아니다. 부동소수점의 비트열은 정수의 비트열과 구조가 달라서 아래쪽을 잘라 내는 것으로는 의미 있는 값이 나오지 않는다. JLS §5.1.3은 이 변환을 다음과 같이 정한다. 대상이 int나 long일 때의 규칙이다.

    1. 값이 NaN이면 결과는 0이다.
    2. 값이 유한하면 0을 향해 반올림(round toward zero)한다. 곧 소수 부분을 버린다. 그 결과가 대상 타입의 범위 안이면 그 값이 결과다.
    3. 값이 너무 크면(양의 무한대 포함) 결과는 대상 타입의 최댓값이고, 너무 작으면(음의 무한대 포함) 최솟값이다.
    System.out.println((int) 3.99);          // 3
System.out.println((int) -3.99);         // -3
System.out.println((int) 1e10);          // 2147483647
System.out.println((int) -1e10);         // -2147483648
System.out.println((int) Double.NaN);    // 0

    "버림"의 방향에 주의한다. 0을 향한 반올림이므로 -3.99는 -4가 아니라 -3이 된다. 소수 부분을 떼어 낸다고 이해하면 정확하다. 반올림이 필요하면 Math.round()를 쓴다. 그리고 범위를 벗어날 때의 동작이 정수끼리의 축소와 다르다는 점이 중요하다. 정수 축소는 비트를 잘라 엉뚱한 값을 만들지만, 실수에서 정수로의 변환은 범위의 끝 값에 달라붙는다. 이를 포화(saturation)라 한다. 1e10(100억)을 int로 바꾸면 int의 최댓값이 된다.

    대상이 byte, short, char일 때는 변환이 두 단계다. 먼저 위 규칙으로 int로 바꾸고, 그 int를 정수 축소 규칙으로 다시 자른다. 두 규칙이 차례로 적용되면서 직관과 어긋나는 결과가 나온다.

    (byte) 1e10이 byte의 최댓값 127이 아니라 -1이 되는 것은 포화가 int 단계에서만 일어나고 그 뒤에는 절단이 적용되기 때문이다. 큰 실수를 작은 정수 타입으로 한 번에 캐스트하는 코드는 결과를 예측하기 어려우므로, 범위를 먼저 검사하고 변환하는 편이 안전하다.

    double에서 float로 가는 변환도 축소 변환이다. 이 경우는 가장 가까운 float 값으로 반올림하고, 크기가 float의 범위를 넘으면 무한대가, 너무 작으면 0이 된다. (float) 1e40은 Infinity, (float) 1e-50은 0.0이다. 이 변환과 관련해 자주 만나는 결과가 하나 있다. 0.1f == 0.1은 false다. 비교하려면 두 피연산자의 타입을 맞춰야 하므로 float 쪽이 double로 확장되는데, 0.1에 가장 가까운 float 값과 0.1에 가장 가까운 double 값은 서로 다른 수이기 때문이다. float 값 0.1f를 double로 확장해 출력하면 0.10000000149011612가 나온다. float에서 double로의 확장은 값을 정확히 보존하므로, 0.1f라는 변수에 실제로 들어 있던 수가 0.1이 아니라 이 근처의 값이었다는 뜻이다.

    대입에서의 상수 특례 — byte b = 10이 통과하는 이유

    여기까지 읽고 나면 의문이 하나 생긴다. 정수 리터럴의 타입은 접미사 L이 없는 한 int다(JLS §3.10.1). 그렇다면 byte b = 10;은 int 값을 byte 변수에 넣는 축소 변환이고, 캐스트가 없으니 컴파일 오류여야 한다. 그런데 이 문장은 아무 문제 없이 컴파일된다. JLS §5.2가 대입에 특례를 두었기 때문이다. 대입하는 식이 byte, short, char, int 타입의 상수식이고, 변수의 타입이 byte, short, char이며, 그 상수의 값을 변수의 타입으로 나타낼 수 있으면 축소 변환이 허용된다.

    byte b1 = 10;          // 통과: 10은 int 상수식이고 byte 범위 안이다
byte b2 = 128;         // 컴파일 오류: 128은 byte 범위 밖이다

int i = 10;
byte b3 = i;           // 컴파일 오류: i는 변수라서 상수식이 아니다

final int K = 100;
byte b4 = K;           // 통과: K는 상수 변수다

char c = 65;           // 통과: 문자 'A'
float f = 3.14;        // 컴파일 오류: 이 특례는 double 상수에 적용되지 않는다
int n = 10L;           // 컴파일 오류: long 상수에도 적용되지 않는다

    이 규칙의 논리는 확정 할당에서 본 것과 같다. 컴파일러는 상수식의 값을 컴파일 시점에 정확히 알고 있으므로, 그 값이 대상 타입에 들어가는지를 그 자리에서 검사할 수 있다. 10은 들어가니 허용하고 128은 안 들어가니 거부한다. 변수 i는 지금 10이 들어 있더라도 컴파일러의 규칙상 "값을 모르는 int"이므로 거부된다. 04회에서 삼항 연산자 true ? 'a' : 0과 true ? 'a' : i의 타입이 갈린 것도 같은 구분이었다.

    특례의 범위가 좁다는 점도 기억해 두자. int 이하의 정수 상수에만 적용된다. 소수점이 있는 리터럴은 접미사가 없으면 double이고(JLS §3.10.2) double 상수를 float에 넣는 특례는 없으므로, float 변수에는 3.14f처럼 접미사를 붙인 float 리터럴을 써야 한다. 반대로 long l = 10;이나 float g = 10;은 특례와 무관하게 통과한다. int에서 long, int에서 float로 가는 평범한 확장 변환이기 때문이다.

    계산과 형변환 — 숫자 승격

    형변환은 대입할 때만 일어나는 것이 아니다. a + b처럼 연산자의 두 피연산자 타입이 다르면 연산 전에 타입을 하나로 맞춰야 하고, 타입이 같더라도 그 타입으로 연산할 수 있어야 한다. JLS §5.6은 산술 연산자의 피연산자에 적용되는 변환을 숫자 승격(numeric promotion)이라 부르고 규칙을 다음 순서로 정한다.

    1. 피연산자 가운데 하나라도 double이면 나머지를 double로 확장하고 double로 연산한다.
    2. 그렇지 않고 하나라도 float이면 float로 맞춘다.
    3. 그렇지 않고 하나라도 long이면 long으로 맞춘다.
    4. 그 밖에는 모두 int로 확장하고 int로 연산한다.

    네 번째 규칙이 핵심이다. "두 피연산자 가운데 큰 타입으로 맞춘다"가 아니라 "최소한 int로 올린다"다. 그래서 byte끼리 더해도 결과의 타입은 int다.

    byte b1 = 10, b2 = 20;
// byte b3 = b1 + b2;            // 컴파일 오류: b1 + b2의 타입은 int다
int sum = b1 + b2;               // 30
byte b3 = (byte) (b1 + b2);      // 30

byte p = 100, q = 100;
System.out.println(p + q);             // 200
System.out.println((byte) (p + q));    // -56

    이유는 두 가지다. 하나는 JVM의 구조다. JVMS §2.11.1이 설명하듯 byte, short, char 값에 대한 연산은 대부분 int용 명령으로 수행된다. byte 두 개를 더하는 메서드를 컴파일하면 iload_0, iload_1, iadd가 나온다. byte 전용 덧셈 명령은 존재하지 않는다. 다른 하나는 결과의 범위다. 100과 100은 둘 다 byte에 들어가지만 합 200은 들어가지 않는다. 결과를 int로 두면 중간 계산에서 값이 잘리지 않고, 다시 byte에 넣을지는 프로그래머가 캐스트로 결정하게 된다.

    복합 대입 연산자에 숨은 캐스트

    b = b + 1은 방금 본 이유로 컴파일 오류인데 b += 1은 통과한다. 두 문장이 같다고 배웠다면 이상한 일이다. JLS §15.26.2에 따르면 E1 op= E2는 E1 = (T) ((E1) op (E2))와 같다. 여기서 T는 E1의 타입이다. 복합 대입 연산자에는 왼쪽 변수의 타입으로 되돌리는 캐스트가 들어 있다. 증감 연산자 ++, --도 계산 결과를 변수의 타입으로 축소해 저장한다(JLS §15.14.2).

    byte b = 10;
b += 120;          // b = (byte) (b + 120)   → 130이 잘려 -126
short s = 1;
s += 100000;       // s = (short) (s + 100000) → -31071
int x = 10;
x += 3.7;          // x = (int) (x + 3.7)     → 13.7에서 소수를 버려 13
System.out.println(b + " " + s + " " + x);   // -126 -31071 13

    이 캐스트는 소스에 보이지 않는다. 그래서 축소 변환이 일어나는데도 "캐스트라는 서명"이 없는 유일한 자리다. int 변수에 실수를 +=로 더하거나 좁은 타입의 변수에 큰 값을 누적하는 코드는 컴파일러의 도움 없이 값이 잘린다. 누적 변수의 타입을 계산에 쓰이는 값들 가운데 가장 넓은 타입 이상으로 잡아야 하는 이유다.

    식의 타입은 피연산자가 정한다

    숫자 승격에서 가장 많이 틀리는 지점은 "결과를 받을 변수의 타입이 계산 방식에 영향을 준다"고 믿는 것이다. 식의 타입은 피연산자의 타입만으로 정해지고, 대입은 계산이 끝난 뒤에 일어난다.

    int total = 7, count = 2;
double avg1 = total / count;             // 3.0
double avg2 = (double) total / count;    // 3.5
double avg3 = (double) (total / count);  // 3.0

    avg1에서 total / count는 int와 int의 나눗셈이다. 정수 나눗셈은 0을 향해 반올림하므로(JLS §15.17.2) 결과는 3이고, 이 3이 대입 시점에 double로 확장되어 3.0이 된다. 소수 부분은 이미 사라진 뒤다. avg2에서는 캐스트가 나눗셈보다 먼저 적용된다. 캐스트는 단항 연산자여서 /보다 우선순위가 높고, 그래서 (double) total이 먼저 계산된다. 그러면 double과 int의 나눗셈이 되어 규칙 1에 따라 count도 double로 승격되고 3.5가 나온다. avg3은 괄호 때문에 정수 나눗셈이 먼저 일어나므로 avg1과 같다. 캐스트를 어디에 붙이느냐가 결과를 바꾼다.

    같은 원리가 오버플로에서도 나타난다. 하루를 마이크로초로 환산하는 계산이다.

    long wrong = 24 * 60 * 60 * 1000 * 1000;     // 500654080
long right = 24L * 60 * 60 * 1000 * 1000;    // 86400000000

    첫 줄의 피연산자는 모두 int이므로 곱셈이 전부 int로 수행된다. 올바른 값 86,400,000,000은 int의 최댓값을 넘으므로 오버플로가 일어나 500,654,080이 되고, 그 틀린 값이 long으로 확장되어 저장된다. 변수가 long이라는 사실은 계산에 아무 영향도 주지 못한다. 둘째 줄처럼 첫 피연산자를 long으로 만들면 규칙 3에 따라 첫 곱셈부터 long으로 수행되고, 이후의 곱셈도 왼쪽 피연산자가 long이므로 계속 long이다.

    승격은 식 전체에 한 번 적용되는 것이 아니라 연산 하나하나에 적용된다는 점도 확인해 두자. 5 / 2 * 2.0은 4.0이고 5 / 2.0 * 2는 5.0이다. 앞의 식에서는 5 / 2가 먼저 정수 나눗셈으로 2가 된 다음 double과 곱해진다. 식 어딘가에 double이 있다고 해서 앞선 연산까지 double로 바뀌지 않는다. 타입이 섞인 덧셈의 바이트코드가 이 과정을 그대로 보여 준다.

    static double mixed(int i, long l, float f, double d) {
    return i + l + f + d;
}
           0: iload_0
       1: i2l            // i를 long으로 (int + long → long)
       2: lload_1
       3: ladd
       4: l2f            // 합을 float로 (long + float → float)
       5: fload_3
       6: fadd
       7: f2d            // 합을 double로 (float + double → double)
       8: dload         4
      10: dadd
      11: dreturn

    왼쪽부터 한 연산씩, 그때그때 두 피연산자의 타입에 맞춰 변환 명령이 들어간다. 4번의 l2f에 주목하자. long과 float를 더하면 규칙 2에 따라 long이 float로 변환된다. 앞에서 본 정밀도 손실이 일어날 수 있는 변환이 소스에는 아무 표시 없이 식 한가운데에서 일어난 것이다. 최종 타입이 double이라고 해서 중간 과정이 double의 정밀도로 계산되는 것은 아니다.

    char의 산술

    char c = 'a';
System.out.println(c + 1);             // 98
System.out.println((char) (c + 1));    // b
char next = 'a' + 1;                   // 통과: 상수식 98은 char 범위 안이다
// char next2 = c + 1;                 // 컴파일 오류: c + 1은 int다

    char도 규칙 4의 대상이어서 산술 연산에 들어가면 int가 된다. c + 1은 문자 a의 코드값 97에 1을 더한 int 98이고, 그대로 출력하면 숫자가 나온다. 문자로 되돌리려면 char로 캐스트한다. 'a' + 1을 char 변수에 캐스트 없이 넣을 수 있는 것은 앞 절의 상수 특례 덕분이다. 피연산자가 모두 상수이면 식 전체가 상수식이고, 그 값 98을 char로 나타낼 수 있기 때문이다.

    다른 주제와의 연결

    스코프와 프레임의 관계는 09회의 메서드에서 완성된다. 메서드를 호출하면 새 프레임이 만들어지고 인자가 그 프레임의 지역 변수 슬롯에 복사된다. 호출한 쪽의 변수와 호출된 쪽의 매개변수가 이름이 같아도 서로 다른 프레임의 서로 다른 칸이므로 한쪽을 고쳐도 다른 쪽은 변하지 않는다. 인자를 넘길 때에도 대입과 비슷하게 확장 변환이 자동으로 일어나서, long 매개변수에 int 값을 넘길 수 있다. 다만 이 회차에서 본 상수 특례는 메서드 호출에는 적용되지 않는다. byte 매개변수를 받는 메서드에 리터럴 10을 넘기면 컴파일 오류다. 이 차이와 메서드 오버로딩에서의 타입 선택은 09회에서 다룬다.

    지역 변수가 프레임 안에 있다는 사실은 더 먼 주제들의 바탕이기도 하다. 프레임은 메서드가 끝나면 사라지므로 지역 변수의 수명은 메서드 호출을 넘지 못한다. 메서드가 끝난 뒤에도 남아야 하는 데이터는 힙에 놓이는 객체와 배열에 담아야 하고, 이것이 08회의 배열과 기본편의 객체로 이어진다. 고급 3편의 람다는 바깥의 지역 변수를 쓸 때 그 변수가 사실상 final이어야 한다는 제약을 받는데, JLS §15.27.2는 그 이유를 값이 계속 바뀌는 지역 변수를 캡처하면 동시성 문제가 생기기 쉽기 때문이라고 설명한다. 고급 1편의 멀티스레드에서는 스레드마다 자신의 스택을 따로 갖기 때문에 지역 변수는 스레드 사이에 공유되지 않는다는 점이 동시성 문제를 가르는 기준선이 된다.

    형변환 쪽에서는 기본편의 다형성에서 참조 타입의 캐스트를 만난다. 문법은 같은 괄호지만 성격이 다르다. 기본형의 캐스트는 값의 비트 표현을 바꾸고 예외를 던지지 않는다. 참조 타입의 캐스트는 객체를 바꾸지 않고 "이 참조를 이 타입으로 다뤄도 되는가"를 검사하며, 실행 시점에 검사가 실패하면 예외가 발생한다. 중급 1편의 래퍼 클래스에서는 기본형과 객체 사이의 변환(박싱과 언박싱)이 이 회차의 변환 규칙과 결합되는 모습을 보게 된다.

    데이터베이스와 연결되는 지점도 있다. 테이블 컬럼의 타입과 그것을 받는 자바 변수의 타입이 표현 범위에서 어긋나면, 이 회차에서 본 절단과 정밀도 손실이 애플리케이션과 데이터베이스의 경계에서 일어난다. 금액이나 식별자처럼 한 자리도 틀리면 안 되는 값에 float나 double을 쓰지 않는다는 원칙은 자바 코드에서나 스키마 설계에서나 같은 이유에서 나온다.
    스코프
    지역 변수의 이름을 쓸 수 있는 구간. 선언한 곳에서 시작해 선언을 감싼 블록의 끝까지이고, for의 초기화식에서 선언한 변수는 그 for 문까지다. 지역 변수의 스코프 안에서 같은 이름을 다시 선언할 수 없다.
    지역 변수 배열과 슬롯
    프레임마다 있는 지역 변수 배열의 길이는 컴파일 시점에 정해진다. long과 double은 두 칸을 쓴다. 스코프가 끝난 변수의 슬롯은 다음 변수가 재사용할 수 있고, 블록을 드나드는 데 해당하는 바이트코드는 없다.
    스코프를 좁히는 이유
    변수를 읽고 쓰는 코드의 범위가 줄어 추적하기 쉬워지고 잘못 쓸 여지가 사라진다. 메모리 이득은 프레임의 칸 수가 줄어드는 정도이며 일차적인 목적이 아니다.
    확정 할당
    지역 변수를 읽는 지점에 이르는 모든 실행 경로에서 대입이 일어나야 한다는 컴파일 규칙. 컴파일러는 상수식만 값으로 인정하고, JVM도 클래스를 링크할 때 같은 제약을 검증한다.
    확장 변환
    값의 크기가 보존되는 방향의 변환 19가지로, 자동으로 일어난다. 정수의 확장은 부호 확장, char의 확장은 0 확장이다. int→float, long→float, long→double은 정밀도를 잃을 수 있다.
    축소 변환
    캐스트가 필요한 변환 22가지. 정수끼리는 아래쪽 n비트만 남기고 버린다. 실수에서 정수로는 소수 부분을 버리고, 범위를 넘으면 최댓값이나 최솟값이 되며, NaN은 0이 된다. 예외는 발생하지 않는다.
    상수식 특례
    int 이하의 정수 상수식은 값이 범위 안이면 캐스트 없이 byte, short, char 변수에 대입할 수 있다. 변수나 long·double 상수에는 적용되지 않는다.
    숫자 승격
    산술 연산 전에 피연산자를 double, float, long 순으로 맞추고, 셋 다 아니면 int로 올린다. 식의 타입은 피연산자가 정하며 결과를 받는 변수의 타입은 계산에 영향을 주지 않는다.
    복합 대입의 숨은 캐스트
    a += b는 a = (a의 타입) (a + b)와 같다. 캐스트 표시 없이 축소 변환이 일어나는 자리다.

    실무에서 이 회차의 지식이 가장 직접적으로 쓰이는 곳은 숫자가 조용히 틀어지는 버그를 찾을 때다. 자바의 기본형 변환은 어떤 경우에도 예외를 던지지 않는다. 그래서 문제는 장애가 아니라 틀린 데이터로 나타나고, 한참 뒤에 정산이 맞지 않거나 통계가 어긋나는 형태로 발견된다. 의심할 자리는 정해져 있다. int끼리 곱한 결과를 long에 넣는 코드, 정수끼리 나눈 결과를 double에 넣는 코드, 좁은 타입 변수에 +=로 누적하는 코드, 그리고 long과 float·double이 한 식에 섞인 코드다. 네 경우 모두 컴파일러는 침묵한다.

    캐스트를 쓸 때는 그것이 서명이라는 점을 기억한다. 컴파일 오류를 없애려고 캐스트를 붙이는 것은 "손실이 있을 수 있다"는 컴파일러의 경고에 "알고 있다"고 답하는 일이다. 정말 알고 있는지, 곧 값이 대상 타입의 범위 안이라는 것을 어디에서 보장하는지 답할 수 있어야 한다. 보장이 없다면 범위를 검사하거나 Math.toIntExact처럼 범위를 벗어나면 예외를 던지는 방법을 쓴다. 틀린 값으로 계속 실행되는 것보다 예외로 멈추는 것이 대부분의 업무 로직에서 더 나은 실패 방식이다.

    타입 선택의 판단 기준도 여기서 나온다. 개수나 색인은 int, 범위가 int를 넘을 수 있는 누적값·식별자·시각은 처음부터 long으로 둔다. 나중에 넓히려면 그 값이 지나가는 모든 변수와 식을 고쳐야 하고, 하나라도 놓치면 그 자리에서 잘린다. 금액처럼 십진 소수를 정확히 다뤄야 하는 값에는 float와 double을 쓰지 않는다. 이진 부동소수점은 0.1 같은 값을 정확히 나타내지 못하고, 큰 정수와 섞이면 아래 자릿수를 잃는다. 반대로 측정값이나 비율처럼 원래 근삿값인 데이터에는 double이 맞는 선택이다.

    스코프에 관한 판단은 코드 리뷰에서 자주 쓰인다. 메서드 맨 위에 변수 선언이 몰려 있거나, 한 변수가 서로 다른 용도로 두 번 쓰이거나, 반복문 밖에 선언된 변수가 반복문 안에서만 쓰인다면 스코프를 좁힐 수 있다는 신호다. 좁히기 어려울 만큼 변수가 넓게 얽혀 있다면 메서드가 너무 많은 일을 하고 있다는 뜻이기도 하다. 메서드를 나누면 각 메서드의 프레임이 곧 스코프의 경계가 되어, 변수가 영향을 미치는 범위를 언어가 강제해 준다.

(다)는 메서드 첫 줄에서 선언한 total의 스코프(메서드 끝까지) 안에서 같은 이름을 다시 선언하므로 오류다.      if 블록 안에서 선언한 지역 변수의 스코프가 블록 끝에서 끝난다는 것은 JVM 수준에서 무엇을 뜻하는가? 블록에 들어갈 때 변수용 메모리가 할당되고 블록을 나갈 때 해제되는 명령이 실행된다. 블록을 드나드는 데 해당하는 명령은 없고, 컴파일러가 그 변수에 배정했던 슬롯 번호를 이후에 선언되는 다른 변수에 다시 배정할 수 있게 될 뿐이다. 블록이 끝나면 JVM이 그 슬롯의 값을 0으로 지운다. 블록마다 새 스택 프레임이 만들어지고 블록이 끝나면 그 프레임이 사라진다. 지역 변수 배열의 길이는 컴파일 시점에 정해지고 프레임은 메서드 호출 단위로 만들어진다. 스코프는 이름과 슬롯의 대응을 관리하는 컴파일러의 규칙이며, 실행 시점에는 슬롯 번호를 쓰는 load/store 명령만 남는다. 스코프가 끝난 슬롯의 값은 지워지지 않고 다음 변수가 저장될 때 덮어쓰인다. int k; int m = 5; if (m > 2) k = 3; System.out.println(k);가 컴파일 오류인 이유로 가장 정확한 것은? javac의 분석 능력이 부족해서 m이 5라는 것을 알아내지 못하기 때문이다. 지역 변수는 선언과 동시에 초기화해야 한다는 문법 규칙이 있기 때문이다. 확정 할당 규칙은 상수식의 값만 고려하도록 명세에 정해져 있고, final이 아닌 변수가 들어간 m > 2는 상수식이 아니어서 조건이 거짓인 경로가 있는 것으로 취급되기 때문이다. if 문 안에서 한 대입은 블록 스코프 때문에 if 문 밖에서는 효력이 없기 때문이다. JLS 16장은 컴파일러가 따라야 할 규칙을 기계적으로 정해 두었고, 그 규칙은 상수식 외에는 식의 값을 고려하지 않는다. 컴파일러의 능력 문제가 아니라 모든 컴파일러가 같은 프로그램을 받아들이게 하려는 명세의 선택이다. 지역 변수는 선언만 해 두고 나중에 대입해도 되며, 대입의 효력은 스코프와 무관하다. long에서 float로의 변환은 64비트에서 32비트로 줄어드는데도 캐스트 없이 자동으로 일어난다. 이 변환이 확장 변환으로 분류되는 근거는? float가 long보다 나중에 만들어진 타입이어서 우선순위가 높기 때문이다. 변환 과정에서 어떤 정보도 잃지 않기 때문이다. float의 가수부가 64비트 정수를 모두 담을 수 있기 때문이다. float가 나타낼 수 있는 값의 크기 범위가 long의 범위를 포함하므로 수의 크기는 보존되기 때문이다. 다만 아래쪽 자릿수의 정밀도는 잃을 수 있다. 확장 변환의 기준은 비트 수가 아니라 값의 전체적인 크기가 보존되는가다. float는 약 3.4 × 1038까지 나타내므로 어떤 long 값도 크기는 유지된다. 그러나 float의 정밀도는 24비트뿐이어서 유효 숫자가 그보다 긴 정수는 가장 가까운 값으로 반올림되고, JLS도 이 변환에서 정밀도 손실이 일어날 수 있다고 명시한다. (byte) 1e10의 결과가 byte의 최댓값 127이 아니라 -1인 이유는? 실수에서 byte로의 변환은 두 단계여서, 먼저 int로 바꿀 때 최댓값 2147483647로 포화되고, 그 int의 아래쪽 8비트(모두 1)만 남기는 절단이 이어지기 때문이다. 1e10의 부동소수점 비트열에서 아래쪽 8비트를 그대로 잘라 내기 때문이다. 범위를 벗어난 실수를 정수로 바꾸면 항상 -1이 되도록 정해져 있기 때문이다. 변환 중 오버플로가 감지되어 JVM이 오류 표시 값으로 -1을 돌려주기 때문이다. JLS §5.1.3은 실수에서 byte·short·char로의 변환을 실수→int, int→대상 타입의 두 단계로 정한다. 첫 단계에서는 범위를 넘는 값이 int의 최댓값 0x7FFFFFFF로 포화되고, 둘째 단계에서는 정수 축소 규칙에 따라 아래 8비트 0xFF만 남아 -1이 된다. 포화는 int(또는 long) 단계에서만 일어난다. 축소 변환은 예외나 오류 표시를 만들지 않는다. byte b = 10;일 때 b = b + 1;은 컴파일 오류이고 b += 1;은 통과한다. 이 차이를 설명하는 것은? +=는 byte 전용 덧셈 명령으로 컴파일되어 승격이 일어나지 않기 때문이다. b + 1에서 1이 상수가 아닌 것으로 취급되기 때문이다. 두 경우 모두 b + 1은 int로 계산되지만, 복합 대입 연산자는 결과를 왼쪽 변수의 타입으로 되돌리는 캐스트를 포함하도록 정의되어 있기 때문이다. +=는 계산 결과가 byte 범위를 넘으면 예외를 던져 안전을 보장하기 때문이다. 숫자 승격으로 b + 1의 타입은 int이고, int를 byte에 대입하려면 캐스트가 필요하다. JLS §15.26.2는 E1 op= E2를 E1 = (T) ((E1) op (E2))와 같다고 정의하므로 복합 대입에는 그 캐스트가 들어 있다. byte 전용 덧셈 명령은 없으며, 숨은 캐스트는 범위를 넘는 값을 예외 없이 잘라 낸다.
    스코프(scope)
    선언된 이름을 단순 이름으로 가리킬 수 있는 프로그램의 구간. 지역 변수는 선언부터 선언을 감싼 블록의 끝까지다.
    지역 변수 배열(local variable array)
    스택 프레임 안에 있는, 매개변수와 지역 변수의 값을 담는 배열. 길이는 컴파일 시점에 정해져 클래스 파일의 max_locals에 기록된다.
    슬롯(slot)
    지역 변수 배열의 칸 하나. int, float, 참조 등은 한 칸, long과 double은 연속한 두 칸을 쓴다.
    확정 할당(definite assignment)
    지역 변수를 읽기 전에 모든 실행 경로에서 값이 대입되었음을 컴파일러가 규칙으로 확인하는 것. JLS 16장이 정한다.
    상수식(constant expression)
    리터럴, 상수 변수, 그리고 그것들에 대한 연산만으로 이루어져 컴파일 시점에 값이 정해지는 식. 확정 할당, 대입의 상수 특례, 삼항 연산자의 타입 규칙에서 특별히 취급된다.
    확장 변환(widening primitive conversion)
    값의 크기가 보존되는 방향의 기본형 변환. 대입과 연산에서 자동으로 적용된다.
    축소 변환(narrowing primitive conversion)
    값의 크기나 부호가 달라질 수 있는 방향의 기본형 변환. 캐스트로 명시해야 한다.
    부호 확장(sign extension)
    부호 있는 정수를 더 넓은 타입으로 바꿀 때 늘어난 윗자리를 원래의 부호 비트로 채우는 것. 값이 보존된다.
    숫자 승격(numeric promotion)
    산술 연산 전에 피연산자의 타입을 double, float, long, int 가운데 하나로 맞추는 변환. byte, short, char는 최소 int가 된다.
    포화(saturation)
    범위를 벗어난 값이 그 타입의 최댓값이나 최솟값으로 고정되는 것. 실수를 int나 long으로 변환할 때 일어난다.
