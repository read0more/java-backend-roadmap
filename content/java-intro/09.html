    같은 계산을 두 번 쓰지 않으려면

    상품 가격에 부가세 10%를 더한 금액을 구하는 코드를 생각해 보자. 상품이 둘이면 같은 식을 두 번 쓰게 된다.

    int coffee = 4500;
int coffeeTotal = coffee + coffee * 10 / 100;

int cake = 6200;
int cakeTotal = cake + cake * 10 / 100;

    이 코드에는 세 가지 문제가 있다. 첫째, 같은 식이 여러 곳에 흩어져 있다. 세율이 바뀌면 흩어진 곳을 모두 찾아 고쳐야 하고, 하나라도 빠뜨리면 프로그램의 일부만 옛 세율로 계산한다. 둘째, 식만 보아서는 무엇을 하려는 계산인지 드러나지 않는다. * 10 / 100이 부가세라는 것은 읽는 사람이 추측해야 한다. 셋째, 계산이 길어질수록 복사해 붙이는 과정에서 변수 이름 하나를 바꾸지 않는 실수가 끼어든다.

    반복문은 "같은 일을 연달아 여러 번" 하는 중복을 없앴다. 지금 필요한 것은 "같은 일을 프로그램의 여러 곳에서" 하는 중복을 없애는 수단이다. 계산에 이름을 붙여 한 곳에 정의해 두고, 필요한 곳에서는 이름을 불러 쓰는 것이다. 자바에서 그 수단이 메서드(method)다.

    public class TaxCalc {
    public static void main(String[] args) {
        int coffeeTotal = withTax(4500);
        int cakeTotal = withTax(6200);
        System.out.println(coffeeTotal + " " + cakeTotal);
    }

    public static int withTax(int price) {
        return price + price * 10 / 100;
    }
}

    출력은 4950 6820이다. 세율이 바뀌면 고칠 곳은 withTax 안의 한 줄이고, 호출하는 쪽은 이름만 보고도 무슨 계산인지 안다. 수학의 함수 f(x)와 닮았다. 입력을 받아 정해진 계산을 하고 결과를 내놓는다. 사실 메서드는 처음부터 쓰고 있었다. 첫 회차부터 써 온 main이 메서드이고, System.out.println(...)과 scanner.nextInt()도 누군가 미리 정의해 둔 메서드를 호출한 것이다.

    이 회차의 관심은 문법보다 그 아래에 있다. 메서드를 호출하는 순간 JVM 안에서 무엇이 만들어지고, 인수가 어떻게 건너가며, 결과가 어떻게 돌아오는가. 이것을 한 번 정확히 그려 두면 "메서드 안에서 값을 바꿨는데 왜 밖에서는 그대로인가", "배열은 왜 바뀌는가", "이름이 같은 메서드 중 어느 것이 불리는가" 같은 질문에 규칙 하나로 답할 수 있다.

    메서드 정의 — 선언부를 읽는 법

    메서드 정의는 선언부와 본문으로 이루어진다. 선언부는 이 메서드를 어떻게 부르고 무엇을 돌려받는지를 알려 주는 약속이고, 본문은 불렸을 때 실행할 코드다.

       제어자          반환 타입  이름       매개변수 목록
 ┌───────────┐    ┌──┐  ┌──────┐ ┌─────────┐
 public static    int   withTax (int price) {          ← 선언부
     return price + price * 10 / 100;                  ← 본문
 }
    • 제어자(modifier). public static은 지금은 그대로 붙여 쓴다. public은 접근 범위를, static은 객체를 만들지 않고 호출할 수 있는 메서드임을 뜻한다. JLS 8.4.3.2절의 표현으로 static 메서드는 특정 객체에 대한 참조 없이 호출된다. 두 제어자의 의미는 기본편에서 다룬다.
    • 반환 타입(return type). 메서드가 돌려주는 값의 타입이다. 돌려줄 값이 없으면 void를 쓴다.
    • 이름. 호출할 때 쓰는 식별자다. 무엇을 하는지 드러나도록 동사로 시작해 짓는 것이 관례다.
    • 매개변수 목록(formal parameter list). 호출하는 쪽에서 넘겨받을 값을 담을 변수들의 선언이다. 타입과 이름을 쉼표로 구분해 적고, 받을 것이 없으면 괄호만 쓴다.
    • 본문(body). 중괄호 안의 코드 블록이다.

    메서드는 클래스의 몸체 안에, 다른 메서드의 바깥에 선언한다. 메서드 안에 메서드를 선언할 수는 없다. 한 클래스 안에서 선언 순서는 상관이 없어서, 위 예제처럼 main이 아래쪽에 정의된 withTax를 호출해도 된다.

    용어 둘을 구분해 두자. 메서드 선언에 적힌 변수 price는 매개변수(parameter)다. 호출할 때 괄호 안에 적는 식 4500은 인수(argument)다. 인자라고도 부른다. 매개변수는 값을 받을 그릇의 선언이고 인수는 그 그릇에 담길 값을 만드는 식이다. JLS도 선언 쪽을 형식 매개변수(formal parameter), 호출 쪽을 실제 인수 식(actual argument expression)이라고 구분해 부른다. 이 구분이 값 전달을 이해하는 출발점이다.

    메서드 사용 — 호출과 복귀

    두 수를 더하는 메서드로 호출의 흐름을 따라가 보자.

    public class MethodBasic {
    public static void main(String[] args) {
        int sum = add(10, 20);
        System.out.println(sum);
    }

    public static int add(int a, int b) {
        int result = a + b;
        return result;
    }
}

    출력은 30이다. add(10, 20)은 메서드 호출식(method invocation expression)이다. 실행 흐름은 다음과 같다.

    1. main이 실행되다가 add(10, 20)을 만난다. 먼저 인수 식 10과 20을 계산한다.
    2. 실행 흐름이 add의 본문 첫 줄로 넘어간다. 이때 매개변수 a에는 10, b에는 20이 들어 있다.
    3. result에 30을 넣고 return result;를 만난다. 30을 들고 호출한 곳으로 돌아간다.
    4. main으로 돌아오면 add(10, 20)이라는 식 전체가 30이라는 값이 된다. 그 값이 sum에 대입된다.

    호출식은 값을 내는 식이므로 값이 올 수 있는 어느 자리에나 쓸 수 있다. add(1, 2) * 3처럼 다른 식의 일부로 쓸 수 있고, add(add(1, 2), 3)처럼 인수 자리에 다시 호출을 쓸 수도 있다. 뒤의 경우 안쪽 호출이 먼저 끝나 3이 되고, 그 값으로 바깥 호출이 이루어진다. 돌려받은 값을 쓰지 않고 add(1, 2);처럼 호출만 해도 문법상 문제는 없다. 계산된 값은 그냥 버려진다.

    여기까지가 소스 코드 수준의 설명이다. 그런데 이 설명에는 답하지 않은 질문이 여럿 있다. main이 멈춰 있는 동안 main의 변수 sum과 args는 어디에 있는가. add의 a, b, result는 언제 생기고 언제 없어지는가. add가 끝났을 때 JVM은 돌아갈 곳을 어떻게 아는가. 답은 JVM 스택에 있다.

    호출 스택과 프레임 — JVM이 호출을 기억하는 방법

    JVM 명세(JVMS) 2.5.2절에 따르면 JVM의 스레드는 저마다 자기만의 JVM 스택(Java Virtual Machine stack)을 가지며, 이 스택은 스레드와 함께 만들어지고 프레임(frame)을 저장한다. 지금까지 만든 프로그램은 main을 실행하는 스레드 하나로 돌아가므로 스택도 하나다. 2.6절은 프레임의 수명을 이렇게 정한다. 메서드가 호출될 때마다 새 프레임이 만들어지고, 그 메서드 호출이 끝나면 정상 종료든 예외로 인한 종료든 프레임은 소멸한다.

    프레임 하나는 메서드 호출 한 번에 필요한 작업 공간이다. 2.6절이 정한 구성 요소는 셋이다.

    구성 요소담는 것크기가 정해지는 때
    지역 변수 배열(local variables)매개변수와 지역 변수의 값. 0번부터 번호로 접근한다.컴파일 타임
    피연산자 스택(operand stack)계산 중간값, 호출할 메서드에 넘길 인수, 돌려받은 반환값컴파일 타임(최대 깊이)
    런타임 상수 풀에 대한 참조현재 메서드가 속한 클래스의 상수 풀. 호출할 메서드의 이름과 타입 정보를 여기서 찾는다.—

    지역 변수 배열과 피연산자 스택의 크기는 컴파일러가 계산해 클래스 파일에 적어 둔다. javap -v로 보면 메서드마다 이 값이 찍힌다. 앞의 MethodBasic을 컴파일해 열어 보자.

    public static void main(java.lang.String[]);

    stack=2, locals=2, args_size=1
       0: bipush        10
       2: bipush        20
       4: invokestatic  #7        // Method add:(II)I
       7: istore_1
       8: getstatic     #13       // Field java/lang/System.out:Ljava/io/PrintStream;

public static int add(int, int);
  descriptor: (II)I
  Code:
    stack=2, locals=3, args_size=2
       0: iload_0
       1: iload_1

       3: istore_2
       4: iload_2
       5: ireturn

    add의 locals=3은 지역 변수 배열이 세 칸이라는 뜻이다. 0번이 a, 1번이 b, 2번이 result다. stack=2는 피연산자 스택이 가장 깊을 때 두 칸이라는 뜻이고, args_size=2는 인수로 채워지는 칸이 둘이라는 뜻이다. main은 0번이 args, 1번이 sum이어서 locals=2다. JVMS 2.6절은 이 크기들이 컴파일 타임에 정해지므로 프레임에 필요한 메모리를 메서드 호출 시점에 한꺼번에 할당할 수 있다고 설명한다. 매개변수와 지역 변수가 같은 배열에 나란히 놓인다는 점도 기억해 두자. JVM 입장에서 매개변수는 "호출될 때 값이 미리 채워진 지역 변수"다.

    이제 int sum = add(10, 20); 한 줄을 명령어 단위로 따라간다.

    이 순서는 추측이 아니라 명령어의 정의다. JVMS는 invokestatic에 대해 인수 값들이 피연산자 스택에서 꺼내지고, 호출되는 메서드를 위한 새 프레임이 JVM 스택에 만들어지며, 인수 값들이 새 프레임의 지역 변수 0번부터 차례로 값이 된다고 규정한다. ireturn에 대해서는 값이 현재 프레임의 피연산자 스택에서 꺼내져 호출한 쪽 프레임의 피연산자 스택에 올려지고, 인터프리터가 호출한 쪽의 프레임을 복원해 제어를 돌려준다고 규정한다. 세 시점의 JVM 스택을 그리면 다음과 같다.

     (가) 호출 직전                 (나) add 실행 중                 (다) 복귀 직후
     invokestatic 실행 전           iadd 실행 후                     istore_1 실행 전

                               ┌─ add 프레임 ───────────┐

                               │  [0] a      = 10       │

                               │ 피연산자 스택  [30]      │
┌─ main 프레임 ──────────┐     ├─ main 프레임 ──────────┤     ┌─ main 프레임 ──────────┐
│ 지역 변수               │     │ 지역 변수               │     │ 지역 변수               │

└────────────────────────┘     └────────────────────────┘     └────────────────────────┘
   프레임 1개                      프레임 2개 (위가 현재 프레임)       프레임 1개
    호출하면 프레임이 하나 쌓이고 인수가 새 프레임의 지역 변수로 복사되며, 반환하면 프레임이 사라지고 값이 호출한 쪽 피연산자 스택으로 넘어온다는 것을 세 장면으로 보여 준다. 가로로 세 장면이 나란한 그림. 각 장면 위에 제목 "호출 직전", "add 실행 중", "복귀 직후"가 있다. 각 장면은 아래에서 위로 쌓이는 상자 더미로 JVM 스택을 나타낸다. 첫 장면에는 상자 하나, 라벨 "main 프레임", 안에 작은 칸 "sum"과 그 옆에 "피연산자 스택"이라고 적힌 칸 두 개에 10과 20이 들어 있다. 둘째 장면에는 상자 둘이 쌓여 있다. 아래 상자는 "main 프레임"이고 피연산자 스택은 비어 있다. 위 상자는 강조색으로 "add 프레임"이고 안에 칸 "a 10", "b 20", "result"가 있다. 아래 상자에서 위 상자의 a와 b 칸으로 향하는 화살표 두 개에 "값 복사"라고 적는다. 셋째 장면에는 다시 상자 하나 "main 프레임"만 있고 피연산자 스택 칸에 30이 들어 있으며, 사라진 위 상자 자리에 점선 윤곽과 아래로 내려오는 화살표, 라벨 "반환값 30"이 있다. 장면 사이에는 오른쪽을 가리키는 굵은 화살표와 "invokestatic", "ireturn" 라벨. 흰 배경, 파란색과 주황색, 또렷한 고딕체 한국어 라벨. 메서드 호출 한 번은 프레임 하나가 쌓였다가 사라지는 일이다. 인수는 올라갈 때, 반환값은 내려올 때 복사되어 건너간다.

    앞에서 남겨 둔 질문에 답할 수 있다. main이 멈춰 있는 동안 main의 변수들은 main의 프레임에 그대로 남아 있다. 그 위에 add의 프레임이 올라가 있을 뿐이다. add의 변수들은 호출될 때 프레임과 함께 생기고 반환할 때 프레임과 함께 없어진다. 돌아갈 곳은 아래에 있는 프레임이 기억한다. JVMS 2.6.4절의 설명으로는 메서드가 정상 종료하면 호출한 쪽의 지역 변수와 피연산자 스택이 복원되고 프로그램 카운터가 호출 명령어 다음으로 맞춰진다. 나중에 호출된 것이 먼저 끝나므로 프레임은 쌓인 순서의 반대로 사라진다. 스택(stack)이라는 이름 그대로 후입선출(LIFO) 구조다.

    일상에서 가져온 비유책상 위에 쌓는 작업 메모지

    일을 하다가 다른 일을 부탁받으면, 하던 일의 메모지는 그대로 두고 그 위에 새 메모지를 올려 새 일을 적는다. 새 일이 끝나면 결과만 아래 메모지에 옮겨 적고 위 메모지는 버린다. 그러면 아래 메모지에 적어 둔 내용 그대로 하던 일을 이어 갈 수 있다. 비유가 맞지 않는 지점도 있다. 사람은 아래 메모지를 슬쩍 들춰 볼 수 있지만, 실행 중인 메서드는 아래 프레임의 지역 변수를 읽거나 고칠 방법이 없다. 프레임 사이를 건너가는 것은 인수와 반환값뿐이다.

    JVMS가 정하는 것은 프레임이라는 개념과 명령어의 효과다. 실제 메모리에서 프레임이 어떤 모양인지는 JVM 구현의 몫이고, 예를 들어 HotSpot의 JIT 컴파일러는 메서드 인라이닝(method inlining)을 기본으로 켜 두고 있어서, 호출되는 메서드의 본문을 호출하는 쪽 코드에 끼워 넣어 호출 자체를 없애기도 한다. 그런 경우에도 프로그램이 관찰하는 결과는 이 절의 모델과 같아야 한다.

    반환 타입과 return

    메서드는 return 문으로 끝나며 값을 돌려준다. JLS 14.17절에 따르면 return 문은 자신을 둘러싼 메서드를 호출한 쪽으로 제어를 넘기려 하고, 값이 있는 return이라면 그 식의 값이 메서드 호출의 값이 된다. 반환 타입과 return 사이에는 컴파일러가 강제하는 규칙이 있다.

    반환 타입이 있는 메서드는 어느 길로 실행되든 값을 돌려주어야 한다. JLS 8.4.7절의 표현으로는, 반환 타입이 선언된 메서드의 본문이 정상적으로 끝까지 실행될 수 있으면 컴파일 오류다. 본문의 끝에 "그냥 도달"하는 길이 하나라도 있으면 안 된다는 뜻이다.

    static int sign(int v) {
    if (v > 0) {
        return 1;
    }
}   // 컴파일 오류: missing return statement

    v가 0 이하이면 if 블록을 건너뛰어 본문 끝에 닿는데, 그때 돌려줄 값이 없다. 컴파일러는 실제로 어떤 값이 들어올지와 상관없이 코드의 구조만 보고 이 가능성을 찾아낸다. 모든 갈래에 return을 두면 통과한다.

    static String grade(int score) {
    if (score >= 90) {
        return "A";
    } else if (score >= 80) {
        return "B";
    }
    return "F";
}

    return은 값을 돌려주는 동시에 메서드를 즉시 끝낸다. grade(95)는 첫 return에서 끝나므로 그 아래 코드는 실행되지 않는다. 그래서 마지막 return "F";를 else로 감쌀 필요가 없다. 여기까지 내려왔다는 것 자체가 앞의 조건이 모두 거짓이었다는 뜻이다.

    반환 타입이 void인 메서드는 값을 돌려주지 않는다. return을 쓰지 않아도 본문 끝에서 자동으로 돌아가고, 중간에 끝내고 싶을 때는 값 없는 return;을 쓴다. void 메서드에서 return 1;처럼 값을 돌려주려 하거나, 반환 타입이 있는 메서드에서 값 없이 return;만 쓰면 컴파일 오류다. void 메서드의 호출은 값이 아니므로 int r = printPositive(3);처럼 대입할 수도 없다.

    static void printPositive(int n) {
    if (n <= 0) {
        return;            // 여기서 메서드가 끝난다
    }
    System.out.println(n);
}

    바이트코드에서는 반환 명령어가 타입별로 나뉜다. JVMS 2.11.8절에 따르면 ireturn은 boolean, byte, char, short, int를, lreturn, freturn, dreturn은 각각 long, float, double을, areturn은 참조를 돌려주고, 글자가 붙지 않은 return은 void 메서드에서 쓰인다. 반환값을 받지 않고 버리는 호출 add(1, 2);는 invokestatic 뒤에 pop 명령어가 붙어 컴파일된다. 반환값은 일단 호출한 쪽의 피연산자 스택에 올라오고, 쓰지 않으니 꺼내 버리는 것이다. 메서드는 호출한 쪽이 값을 쓰는지 여부를 알지 못한다.

    메서드 호출과 값 전달 1 — 인수는 복사되어 건너간다

    메서드 안에서 매개변수의 값을 바꾸면 호출한 쪽의 변수도 바뀔까. 실험해 보자.

    public class PassValue {
    public static void main(String[] args) {
        int number = 5;
        System.out.println("1. 호출 전 number = " + number);
        changeNumber(number);
        System.out.println("4. 호출 후 number = " + number);
    }

    static void changeNumber(int number) {
        System.out.println("2. 변경 전 number = " + number);
        number = number * 2;
        System.out.println("3. 변경 후 number = " + number);
    }
}
    1. 호출 전 number = 5
2. 변경 전 number = 5
3. 변경 후 number = 10
4. 호출 후 number = 5

    메서드 안에서는 10이 되었지만 호출이 끝난 뒤 main의 number는 여전히 5다. 이름이 같아서 같은 변수처럼 보이지만 둘은 서로 다른 프레임에 있는 서로 다른 변수다. JLS 8.4.1절이 호출 때 일어나는 일을 이렇게 규정한다. 메서드가 호출되면 실제 인수 식의 값이 본문 실행 전에 새로 만들어진 매개변수 변수를 초기화한다. JLS 4.12.3절도 메서드가 호출될 때마다 매개변수마다 새 변수가 만들어지고, 본문 실행이 끝나면 그 변수는 사실상 존재하지 않게 된다고 적는다.

    두 문장에 핵심어가 둘 있다. 넘어가는 것은 변수가 아니라 값이고, 받는 쪽은 기존 변수가 아니라 새 변수다. changeNumber(number)에서 인수 number는 식이다. 그 식을 계산한 결과인 5라는 값이 넘어간다. 이것을 값에 의한 전달(pass by value, call by value)이라고 한다. 바이트코드에 그대로 드러난다. 아래는 보기 쉽도록 출력문을 뺀 같은 코드를 컴파일한 것이다.

    // main
 0: iconst_5
 1: istore_1          // main의 지역 변수 1번(number) = 5
 2: iload_1           // number의 값 5를 복사해 피연산자 스택에 올린다
 3: invokestatic #7   // Method changeNumber:(I)V

// changeNumber
 0: iload_0           // 자기 프레임의 지역 변수 0번(매개변수 number)을 읽는다
 1: iconst_2
 2: imul
 3: istore_0          // 자기 프레임의 지역 변수 0번에 10을 쓴다
 4: return

    iload_1은 변수의 값을 읽어 스택에 복사해 올릴 뿐 변수 자체를 넘기지 않는다. changeNumber의 istore_0이 쓰는 곳은 changeNumber 프레임의 0번 칸이다. JVM 명령어는 현재 프레임의 지역 변수만 번호로 읽고 쓸 수 있고, 다른 프레임의 지역 변수를 가리키는 수단이 없다. 그러니 호출된 메서드가 호출한 쪽의 지역 변수를 바꾸는 일은 구조적으로 불가능하다. 그리고 changeNumber의 프레임은 반환과 함께 사라지므로 그 안의 10도 함께 사라진다.

    메서드 안에서 계산한 결과를 호출한 쪽에 전하는 정식 통로는 반환값이다. 값을 두 배로 만들어 쓰고 싶다면 메서드가 새 값을 돌려주고, 호출한 쪽이 그 값을 자기 변수에 대입한다.

    static int twice(int number) {
    return number * 2;
}

// 호출하는 쪽
number = twice(number);   // main의 number가 10이 된다

    인수를 계산하는 순서도 정해져 있다. JLS 15.7.4절에 따르면 인수 식은 왼쪽부터 차례로, 각 식이 완전히 계산된 뒤에 그 오른쪽 식이 계산된다. int i = 1;인 상태에서 show(i, i = 5, i + 1)을 호출하면 세 인수의 값은 1, 5, 6이다. 첫 인수는 대입이 일어나기 전의 값으로 이미 계산이 끝났기 때문이다. 이런 코드를 쓸 일은 없어야 하지만, 인수가 "변수"가 아니라 "그 시점에 계산된 값"으로 넘어간다는 것을 보여 주는 예다.

    메서드 호출과 값 전달 2 — 참조도 값으로 복사된다

    배열을 넘기면 결과가 달라 보인다.

    import java.util.Arrays;

public class PassArray {
    public static void main(String[] args) {
        int[] scores = {1, 2, 3};

        changeElement(scores);
        System.out.println(Arrays.toString(scores));   // [99, 2, 3]

        replaceArray(scores);
        System.out.println(Arrays.toString(scores));   // [99, 2, 3]
    }

    static void changeElement(int[] arr) {
        arr[0] = 99;
    }

    static void replaceArray(int[] arr) {
        arr = new int[]{7, 8, 9};
        arr[0] = -1;
    }
}

    changeElement를 호출한 뒤에는 main의 배열이 바뀌어 있다. 기본형과 반대의 결과다. 그렇다면 배열은 값이 아닌 다른 방식으로 전달되는 것일까. 그렇지 않다. 규칙은 하나뿐이고 여기서도 똑같이 적용되었다. 인수 식 scores를 계산한 값이 새 매개변수 변수 arr에 복사되었다. 다만 지난 회차에서 본 대로 배열 변수에 들어 있는 값은 배열이 아니라 참조다. 복사된 것은 참조값이고, 배열 객체는 복사되지 않았다.

     changeElement(scores) 실행 중                 replaceArray(scores)에서 arr = new int[]{7, 8, 9}; 직후

  스택                      힙                 스택                      힙
 ┌ changeElement ─┐                          ┌ replaceArray ──┐       ┌────────────────────┐
 │ arr    │ x001 ─┼──┐                       │ arr    │ x002 ─┼──────▶│ x002  int[3]       │
 ├ main ──────────┤  │  ┌─────────────────┐  ├ main ──────────┤       │  7    8    9       │
 │ scores │ x001 ─┼──┴─▶│ x001  int[3]    │  │ scores │ x001 ─┼──┐    └────────────────────┘
 └────────────────┘     │  99   2    3    │  └────────────────┘  │    ┌────────────────────┐
                        └─────────────────┘                      └───▶│ x001  int[3]       │
  두 변수가 같은 배열을 가리킨다.                                        │  99   2    3       │
  arr[0] = 99는 그 배열의 요소를 바꾼다.                                 └────────────────────┘
                                               arr만 새 배열을 가리킨다. scores는 그대로다.

    changeElement 안에서 arr와 main의 scores는 서로 다른 프레임의 서로 다른 변수지만 같은 참조값을 담고 있다. arr[0] = 99;는 arr라는 변수를 바꾸는 문장이 아니다. arr에 든 참조를 따라가 힙에 있는 배열 객체의 요소를 바꾸는 문장이다. 그 배열 객체는 main이 보고 있는 바로 그 객체이므로 main에서도 변경이 보인다. 그리고 힙의 객체는 프레임에 속하지 않으므로 메서드가 끝나도 사라지지 않는다.

    replaceArray는 반대의 경우다. arr = new int[]{7, 8, 9};는 매개변수 변수 arr 자체에 새 참조값을 대입한다. 바뀌는 것은 replaceArray 프레임의 0번 칸뿐이고 main의 scores는 여전히 원래 배열을 가리킨다. 그 뒤의 arr[0] = -1;은 새 배열을 고친 것이므로 main에는 아무 영향이 없다. 메서드가 끝나면 새 배열은 가리키는 변수가 없어져 가비지 컬렉션 대상이 된다. 두 메서드의 차이는 바이트코드에서 명령어 하나로 갈린다.

    // changeElement: arr[0] = 99;
 0: aload_0           // 매개변수에 든 참조값을 올린다
 1: iconst_0
 2: bipush  99
 4: iastore           // 참조가 가리키는 힙의 배열에 쓴다

// replaceArray: arr = new int[3]; 형태의 대입
 0: iconst_3
 1: newarray  int
 3: astore_0          // 자기 프레임의 지역 변수 0번에 쓴다

    iastore는 힙에 쓰고 astore_0은 자기 프레임에 쓴다. 호출한 쪽에 보이는 변경은 앞의 것뿐이다. 정리하면 이렇다.

    메서드 안에서 한 일바뀌는 곳호출한 쪽에 보이는가
    기본형 매개변수에 대입 (number = 10)호출된 메서드의 프레임보이지 않는다
    참조형 매개변수에 대입 (arr = new int[3])호출된 메서드의 프레임보이지 않는다
    참조를 따라가 객체를 변경 (arr[0] = 99)힙의 객체보인다

    흔히 "기본형은 값으로, 배열과 객체는 참조로 전달된다"고 말하지만, 이 표현은 둘째 줄을 설명하지 못한다. 변수 자체가 넘어가는 방식(참조에 의한 전달, pass by reference)이라면 replaceArray 안의 대입이 main의 scores를 바꿨어야 한다. 자바에는 그런 전달 방식이 없다. 정확한 말은 "자바는 언제나 값을 복사해 전달하고, 참조형 변수의 값은 참조다"이다. 그래서 두 int 변수의 값을 맞바꾸는 swap(a, b) 메서드는 자바로 만들 수 없다. 메서드 안에서 맞바꿔지는 것은 사본이다. 배열을 넘겨 그 요소 둘을 맞바꾸는 메서드는 만들 수 있다.

    두 경우 모두 변수의 값이 새 변수로 복사되지만, 배열의 경우 복사된 값이 참조라서 두 변수가 같은 힙 객체를 가리키게 된다는 것을 나란히 보여 준다. 좌우 두 패널로 나뉜 비교 그림. 왼쪽 패널 제목은 "기본형 전달". 아래에 "main 프레임" 상자가 있고 칸 "number 5", 위에 "changeNumber 프레임" 상자가 있고 칸 "number 10". 아래 칸에서 위 칸으로 점선 화살표가 있고 "값 5 복사"라고 적는다. 위 칸 옆에 작은 메모 "여기만 바뀐다". 오른쪽 패널 제목은 "배열 전달". 왼쪽에 쌓인 두 프레임 상자가 있다. 아래 "main 프레임"의 칸 "scores x001", 위 "changeElement 프레임"의 칸 "arr x001". 아래 칸에서 위 칸으로 점선 화살표와 "참조값 복사" 라벨. 패널 오른쪽에는 "힙" 영역이 있고 상자 하나 "x001 int[3]"에 값 99, 2, 3이 들어 있다. scores 칸과 arr 칸에서 각각 이 힙 상자로 실선 화살표가 향한다. 힙 상자의 99 칸이 강조색이고 옆에 "arr[0] = 99"라고 적는다. 두 패널 아래 공통 문구는 "두 경우 모두 값이 복사된다". 흰 배경, 스택은 파랑, 힙은 주황, 또렷한 고딕체 한국어 라벨. 전달 규칙은 하나다. 기본형은 수가, 배열은 참조값이 복사된다. 참조가 복사되면 두 변수가 같은 객체를 본다.

    반환도 같은 원리다. 메서드 안에서 만든 배열을 return arr;로 돌려주면 참조값이 호출한 쪽으로 복사된다. 지역 변수 arr는 프레임과 함께 사라지지만 배열 객체는 힙에 있으므로, 호출한 쪽이 그 참조를 변수에 받아 두면 계속 쓸 수 있다. 지역 변수의 수명과 객체의 수명은 별개다.

    메서드와 형변환

    매개변수의 타입과 인수의 타입이 다르면 어떻게 될까. JLS 15.12.4.5절은 각 인수 값이 매개변수 변수에 대입되기 전에 호출 변환(invocation conversion)을 거친다고 정한다. 5.3절이 정한 호출 문맥(invocation context)에서 기본형에 허용되는 변환은 6회차에서 본 자동 형변환, 곧 확대 기본형 변환(widening primitive conversion)이다. 작은 범위의 타입에서 큰 범위의 타입으로는 자동으로 바뀐다.

    static void printDouble(double v) {
    System.out.println(v);
}

static void printInt(int v) {
    System.out.println(v);
}

printDouble(3);      // int → double 자동 변환. 3.0 출력
printInt('A');       // char → int 자동 변환. 65 출력
printInt(3.5);       // 컴파일 오류: possible lossy conversion from double to int
printInt((int) 3.5); // 명시적 형변환을 하면 된다. 3 출력

    인수 전달은 "매개변수 변수에 인수 값을 대입하는 일"이므로 대입과 거의 같은 규칙을 따른다. double v = 3;이 되는 것처럼 printDouble(3)이 되고, int v = 3.5;가 안 되는 것처럼 printInt(3.5)가 안 된다. 값을 잃을 수 있는 방향의 변환은 프로그래머가 캐스트로 의도를 밝혀야 한다. 변환은 호출하는 쪽에서 일어난다. int 변수 n을 long 매개변수에 넘기는 코드는 iload, i2l, invokestatic으로 컴파일된다. 값을 스택에 올리고, long으로 바꾼 다음, 호출한다. 호출되는 메서드는 언제나 자기 매개변수 타입에 맞는 값을 받는다.

    대입과 다른 점이 하나 있다. byte b = 10;은 컴파일되지만 byte 매개변수를 받는 메서드에 10을 넘기면 컴파일 오류다. 대입에서는 int 상수 식의 값이 대상 타입에 들어가면 암묵적으로 좁혀 주는 예외 규칙이 있는데, JLS 5.3절은 호출 문맥에는 이 규칙이 포함되지 않는다고 명시한다. 이유도 적혀 있다. 그런 암묵적 축소 변환을 넣으면 오버로딩 해석 규칙이 더 복잡해진다고 설계자들이 판단했다는 것이다. byte 매개변수에 상수를 넘기려면 (byte) 10이라고 써야 한다.

    반환 쪽에도 변환이 있다. return 식의 타입은 선언된 반환 타입에 대입 가능해야 하고(JLS 14.17절), 필요하면 자동 형변환이 일어난다. 여기에 함정이 하나 숨어 있다.

    static double half(int x) {
    return x / 2;
}

System.out.println(half(5));   // 2.0

    2.5를 기대했다면 틀렸다. 반환 타입이 double이어도 x / 2는 int끼리의 나눗셈이라 먼저 2로 계산되고, 그 뒤에 2가 2.0으로 바뀐다. 바이트코드는 idiv 다음에 i2d, 그리고 dreturn이다. 형변환은 식의 계산이 끝난 결과에 적용된다. 2.5를 얻으려면 x / 2.0이나 (double) x / 2처럼 나눗셈 자체가 실수 연산이 되게 해야 한다.

    메서드 시그니처와 오버로딩

    두 수를 더하는 메서드와 세 수를 더하는 메서드, 실수 둘을 더하는 메서드가 모두 필요하다고 하자. addTwo, addThree, addDouble처럼 이름을 따로 지을 수도 있지만, 하는 일이 같으니 같은 이름을 쓰고 싶다. 자바는 이름이 같고 매개변수가 다른 메서드를 한 클래스에 여러 개 선언하는 것을 허용한다. 이것이 오버로딩(overloading)이다.

    static int add(int a, int b) { return a + b; }
static int add(int a, int b, int c) { return a + b + c; }
static double add(double a, double b) { return a + b; }

    무엇이 달라야 다른 메서드로 인정되는지는 시그니처(signature)가 정한다. JLS 8.4.2절에 따르면 두 메서드는 이름이 같고 매개변수 타입들이 같으면 같은 시그니처를 갖는다. 곧 시그니처는 메서드 이름과 매개변수 타입의 목록(개수, 타입, 순서)이다. 한 클래스에 같은 시그니처의 메서드를 둘 선언하면 컴파일 오류다. 시그니처에 들어가지 않는 것 두 가지를 기억해야 한다. 매개변수의 이름, 그리고 반환 타입이다.

    static int  f(int a) { return a; }
static long f(int a) { return a; }   // 컴파일 오류: method f(int) is already defined

    반환 타입만 다른 두 메서드는 만들 수 없다. 이유는 호출하는 쪽을 보면 알 수 있다. f(1);처럼 반환값을 쓰지 않는 호출에서 컴파일러는 둘 중 어느 것을 부를지 정할 근거가 없다. 실제로 JLS 15.12.2절은 오버로딩 해석이 결과가 쓰일 자리의 타입과는 독립적으로 이루어진다고 밝힌다. 호출식의 이름과 인수만으로 대상이 정해져야 한다.

    JVM의 규칙은 조금 다르다. JVMS 4.6절은 한 클래스 파일에 이름과 디스크립터(descriptor)가 모두 같은 메서드가 둘 있으면 안 된다고 하는데, (II)I 같은 디스크립터에는 반환 타입이 들어 있다(4.3.3절). 반환 타입만 다른 메서드를 금지하는 것은 JVM이 아니라 자바 언어다.

    어느 메서드가 선택되는가 — 컴파일 타임의 결정

    이름이 같은 메서드가 여럿일 때 어느 것을 부를지는 컴파일러가 정한다. JLS 8.4.9절은 메서드가 호출될 때 실제 인수의 개수와 인수의 컴파일 타임 타입이 컴파일 타임에 사용되어 호출될 메서드의 시그니처가 결정된다고 규정한다. 그 결과는 클래스 파일에 기록된다. 앞에서 본 invokestatic #7 // Method add:(II)I의 (II)I가 바로 선택된 메서드다. 실행 중의 JVM은 후보를 놓고 고민하지 않는다. 적혀 있는 이름과 디스크립터의 메서드를 호출할 뿐이다.

    선택 절차는 JLS 15.12.2절에 정해져 있다. 먼저 이름이 같고 매개변수 개수가 인수 개수와 맞는 메서드를 후보로 모은다. 그다음 세 단계로 적용 가능한(applicable) 메서드를 찾되, 앞 단계에서 하나라도 찾으면 뒤 단계로 넘어가지 않는다.

    박싱과 가변 인수는 이 권의 범위 밖이므로 지금은 1단계와 마지막 선택 규칙만 보면 된다. "가장 구체적"이라는 말의 직관을 JLS 15.12.2.5절은 이렇게 설명한다. 어떤 메서드가 처리할 수 있는 모든 호출을 다른 메서드에 넘겨도 컴파일 오류가 없다면 앞의 메서드가 더 구체적이다. 기본형에서는 4.10.1절이 정한 순서 byte → short → int → long → float → double(그리고 char → int)에서 앞쪽 타입이 더 구체적이다. int를 받는 메서드에 넘길 수 있는 값은 모두 long을 받는 메서드에도 넘길 수 있지만 그 반대는 아니기 때문이다. 결국 인수 타입에서 가장 가까운 매개변수 타입이 선택된다.

    static void print(int v)    { System.out.println("int: " + v); }
static void print(long v)   { System.out.println("long: " + v); }
static void print(double v) { System.out.println("double: " + v); }
    호출 (인수의 타입)적용 가능한 후보선택출력
    print(b) — byte b = 1int, long, doubleprint(int)int: 1
    print(c) — char c = 'A'int, long, doubleprint(int)int: 65
    print(10) — intint, long, doubleprint(int)int: 10
    print(10L) — longlong, doubleprint(long)long: 10
    print(f) — float f = 5.0fdoubleprint(double)double: 5.0
    print(10.0) — doubledoubleprint(double)double: 10.0

    byte를 넘겼을 때 세 메서드 모두 적용 가능하지만 int가 long과 double보다 구체적이므로 print(int)가 선택된다. float는 int나 long으로 자동 변환되지 않으므로 후보가 print(double) 하나뿐이다. 앞의 add 세 메서드에서 add(1, 2.0)을 호출하면 add(int, int)는 둘째 인수 때문에 적용 불가능하고, 남은 add(double, double)이 선택되어 3.0이 나온다.

    가장 구체적인 메서드가 하나로 정해지지 않는 경우도 있다.

    static void g(int a, long b) { }
static void g(long a, int b) { }

g(1, 2);   // 컴파일 오류: reference to g is ambiguous

    두 메서드 모두 g(1, 2)에 적용 가능하다. 그런데 첫째 매개변수는 첫 메서드가 더 구체적이고, 둘째 매개변수는 둘째 메서드가 더 구체적이다. 한 메서드가 더 구체적이려면 모든 매개변수에서 그래야 하므로 어느 쪽도 이기지 못한다. 컴파일러는 아무것이나 고르지 않고 오류로 알린다. g(1, 2L)처럼 인수 타입을 분명히 하면 첫 메서드만 적용 가능해져 해결된다.

    후보 수집, 세 단계의 적용 가능성 검사, 가장 구체적인 메서드 선택, 모호하면 컴파일 오류로 이어지는 흐름을 보여 준다. 위에서 아래로 흐르는 순서도. 맨 위 둥근 상자 "호출식 print(b)". 화살표 아래 사각형 "이름과 인수 개수가 맞는 후보 수집". 그 아래 마름모 "1단계: 자동 형변환만으로 맞는 메서드가 있는가". "예" 화살표는 아래 사각형 "가장 구체적인 메서드 선택"으로 간다. "아니오" 화살표는 오른쪽 마름모 "2단계: 박싱·언박싱 허용"으로 가고, 거기서 다시 "아니오" 화살표가 오른쪽 아래 마름모 "3단계: 가변 인수 허용"으로 간다. 2단계와 3단계의 "예" 화살표도 "가장 구체적인 메서드 선택" 사각형으로 모인다. 3단계의 "아니오" 화살표는 빨간 상자 "컴파일 오류: 맞는 메서드 없음"으로 간다. "가장 구체적인 메서드 선택" 아래에는 마름모 "하나로 정해지는가"가 있고 "예"는 초록 상자 "클래스 파일에 선택 결과 기록", "아니오"는 빨간 상자 "컴파일 오류: 모호한 호출"로 간다. 그림 왼쪽 가장자리에 세로 글씨로 "모두 컴파일 타임"이라고 적는다. 흰 배경, 또렷한 고딕체 한국어 라벨. 오버로딩 선택은 전부 컴파일 타임에 끝난다. 실행 중에는 클래스 파일에 기록된 메서드가 호출될 뿐이다.

    재귀 호출과 StackOverflowError

    프레임은 호출할 때 쌓이고 반환할 때 사라진다. 그렇다면 반환 없이 호출만 계속되면 어떻게 될까. 메서드가 자기 자신을 호출하는 재귀 호출(recursion)로 확인할 수 있다.

    public class Endless {
    public static void main(String[] args) {
        countDown(3);
    }

    static void countDown(int n) {
        System.out.println(n);
        countDown(n - 1);      // 멈추는 조건이 없다
    }
}

    실행하면 3, 2, 1, 0, -1, -2가 차례로 찍히며 끝없이 내려가다가 어느 순간 java.lang.StackOverflowError로 죽는다. countDown(3)이 countDown(2)를 호출하면 n이 3인 프레임 위에 n이 2인 프레임이 올라간다. 같은 메서드지만 호출마다 프레임이 따로 있고 그 안의 n도 따로 있다. 어느 호출도 반환하지 않으므로 프레임은 쌓이기만 한다.

    JVM 스택의 크기에는 한계가 있다. JVMS 2.5.2절은 스레드의 계산이 허용된 것보다 큰 JVM 스택을 필요로 하면 JVM이 StackOverflowError를 던진다고 규정하고, JLS 15.12.4.5절도 호출을 위한 프레임을 만들 메모리가 충분하지 않으면 StackOverflowError가 던져진다고 적는다. 이 오류는 힙이 모자랄 때의 OutOfMemoryError와 다른 것이다. 힙이 아무리 넉넉해도 스택 한도를 넘으면 난다.

    한도가 얼마인지는 명세가 아니라 구현과 설정이 정한다. HotSpot에서는 -Xss 옵션으로 스레드 스택 크기를 지정한다. JDK 21의 java 명령 문서에 따르면 기본값은 플랫폼에 따라 다르며, 예를 들어 Linux/x64와 macOS/x64는 1024KB, Linux/AArch64와 macOS/AArch64는 2048KB이고, Windows는 가상 메모리에 따라 달라진다. 몇 번째 호출에서 터지는지는 정해진 수가 아니다. 프레임 하나의 크기가 메서드마다 다르고 JVM 구현에 달려 있기 때문이다. 깊이를 세는 프로그램을 같은 컴퓨터에서 여러 번 돌려 보면 실행할 때마다 값이 조금씩 다르게 나온다. -Xss를 줄이면 더 일찍, 늘리면 더 늦게 터진다는 것만은 일정하다.

    재귀가 쓸모 있으려면 호출이 언젠가 멈춰야 한다. 더 이상 자신을 호출하지 않고 바로 반환하는 경우를 종료 조건(base case)이라고 한다. 1부터 n까지의 곱인 팩토리얼로 프레임이 쌓였다가 풀리는 과정을 보자.

    static int factorial(int n) {
    if (n <= 1) {
        return 1;                    // 종료 조건
    }
    return n * factorial(n - 1);     // 더 작은 문제로 자신을 호출
}
     factorial(3) 호출 과정 (아래가 먼저 쌓인 프레임)

 쌓이는 단계                                풀리는 단계
 ┌ factorial  n = 1 ┐  ── return 1 ──────▶  1
 ├ factorial  n = 2 ┤  ── return 2 * 1 ──▶  2
 ├ factorial  n = 3 ┤  ── return 3 * 2 ──▶  6
 ├ main             ┤
 └──────────────────┘
 프레임이 가장 많을 때: main + factorial 3개

    factorial(3)은 3 * factorial(2)를 계산하려다 멈춘다. 곱셈을 하려면 오른쪽 값이 필요하기 때문이다. 이때 3은 이 프레임의 피연산자 스택에 올라간 채로 기다린다. factorial(2)도 같은 식으로 멈추고 factorial(1)이 호출된다. 이 호출은 종료 조건에 걸려 1을 반환한다. 그러면 n이 2인 프레임이 깨어나 2 * 1을 계산해 2를 반환하고, n이 3인 프레임이 3 * 2를 계산해 6을 반환한다. 프레임마다 n이 따로 있으므로 안쪽 호출이 바깥 호출의 n을 망가뜨리지 않는다.

    종료 조건이 있어도 재귀의 깊이가 입력에 비례한다면 입력이 클 때 스택 한도를 넘는다. 1부터 n까지의 합을 같은 방식의 재귀로 짜고 n에 백만을 넣어 보면, 이 원고를 확인한 환경(JDK 21, macOS/AArch64, 스택 기본값 2048KB)에서는 코드에 잘못이 없는데도 StackOverflowError가 난다. 반복문으로 짠 같은 계산은 프레임 하나로 끝난다. 깊이가 얼마나 될지 가늠할 수 없는 일에는 반복문을 쓰는 것이 안전하다.

    스택 트레이스 읽기

    예외가 났을 때 출력되는 스택 트레이스(stack trace)는 그 순간 JVM 스택에 쌓여 있던 프레임의 목록이다. 지금까지 본 그림을 글로 찍은 것이라고 보면 된다.

    public class TraceDemo {
    public static void main(String[] args) {
        int[] data = {10, 20, 30};
        System.out.println(pick(data, 3));
    }

    static int pick(int[] values, int index) {
        return read(values, index);
    }

    static int read(int[] values, int index) {
        return values[index];
    }
}
    Exception in thread "main" java.lang.ArrayIndexOutOfBoundsException: Index 3 out of bounds for length 3
	at TraceDemo.read(TraceDemo.java:12)
	at TraceDemo.pick(TraceDemo.java:8)
	at TraceDemo.main(TraceDemo.java:4)

    첫 줄은 어느 스레드에서 무슨 예외가 났는지다. 그 아래의 at 줄 하나가 프레임 하나다. 맨 위가 예외가 난 순간의 현재 프레임, 곧 가장 나중에 호출된 메서드이고, 아래로 갈수록 먼저 호출된 메서드다. 괄호 안은 소스 파일과 줄 번호다. 읽는 순서는 목적에 따라 다르다. 무엇이 터졌는지는 맨 위 줄(read의 12번 줄에서 배열 접근)을 보고, 왜 그 값이 거기까지 갔는지는 아래로 내려가며 본다. 여기서는 맨 아래 main의 4번 줄이 길이 3인 배열에 인덱스 3을 넘긴 것이 원인이다. 예외가 난 곳과 원인이 있는 곳이 다른 메서드인 일은 흔하고, 그 사이의 경로를 알려 주는 것이 스택 트레이스다.

    앞의 Endless처럼 재귀가 깊어져 죽은 경우에는 같은 줄이 수없이 반복되는 트레이스가 나온다. JDK 21의 HotSpot은 기본 설정에서 스택 트레이스에 프레임을 1,024개까지만 담으므로(MaxJavaStackTraceDepth 플래그의 기본값) 출력된 줄 수가 실제 깊이는 아니다. 같은 메서드가 끝없이 반복되는 트레이스를 보면 종료 조건이 없거나 조건에 도달하지 못하는 재귀를 먼저 의심한다.

    이 장의 핵심

    메서드 호출은 JVM 스택에 프레임을 하나 올리는 일이고, 반환은 그 프레임을 내리는 일이다. 프레임 사이를 건너가는 것은 복사된 값뿐이다. 올라갈 때는 인수의 값이 새 지역 변수로, 내려올 때는 반환값이 호출한 쪽의 피연산자 스택으로 복사된다. 기본형이면 수가, 참조형이면 참조값이 복사된다. 어느 메서드를 부를지는 컴파일러가 인수의 타입을 보고 정해 클래스 파일에 적어 둔다.

    지역 변수가 메서드 안에서만 사는 이유

    6회차에서 지역 변수는 선언된 블록 안에서만 쓸 수 있다고 배웠다. 그 규칙을 이제 실행 구조로 설명할 수 있다. 지역 변수와 매개변수는 프레임의 지역 변수 배열에 있고, 프레임은 메서드 호출과 수명이 같다. 메서드가 끝나면 프레임이 사라지므로 그 안의 변수도 사라진다. 다른 메서드에서 그 변수의 이름을 쓸 수 없는 것은 문법이 금지해서이기도 하지만, 애초에 그 변수가 다른 프레임에서 접근할 수 없는 곳에 있기 때문이기도 하다.

    이 구조가 주는 이점이 둘 있다. 하나는 이름의 독립성이다. main의 number와 changeNumber의 number가 충돌하지 않았듯이, 메서드를 작성할 때 다른 메서드가 어떤 변수 이름을 쓰는지 신경 쓸 필요가 없다. 다른 하나는 영향 범위의 제한이다. 메서드가 받은 기본형 인수를 어떻게 바꾸든 호출한 쪽의 변수는 그대로이므로, 메서드 호출 한 줄을 읽을 때 "이 호출 때문에 내 지역 변수가 바뀌었을까"를 걱정하지 않아도 된다. 예외는 참조를 넘긴 경우다. 그때는 메서드가 그 객체를 고칠 수 있으므로, 배열이나 객체를 받는 메서드가 그것을 변경하는지 여부는 메서드의 중요한 성질이 된다.

    지역 변수 배열에서 변수가 차지하는 칸에도 규칙이 있다. JVMS 2.6.1절에 따르면 long과 double은 연속된 두 칸을, 그 밖의 타입은 한 칸을 차지한다. static long area(long w, int h)를 컴파일하면 디스크립터는 (JI)J이고, w가 0번과 1번 칸을, h가 2번 칸을 쓴다. 그래서 h를 읽는 명령어가 iload_1이 아니라 iload_2다.

    이 지식이 다시 쓰이는 곳

    기본편에서 배울 인스턴스 메서드는 오늘 본 구조에 한 가지만 더한 것이다. JVMS 2.6.1절에 따르면 인스턴스 메서드를 호출할 때는 지역 변수 0번에 그 메서드가 호출된 객체의 참조, 곧 this가 전달되고 매개변수는 1번부터 놓인다. this는 숨은 첫째 인수인 셈이고, 그것 역시 참조값이 복사되어 건너간다. 객체를 메서드에 넘겼을 때 필드 변경이 호출한 쪽에 보이는 이유는 오늘 배열로 본 것과 같다.

    오버로딩과 오버라이딩의 구분도 여기서 출발한다. 오버로딩은 이름이 같은 여러 메서드 가운데 하나를 컴파일러가 인수의 컴파일 타임 타입으로 고르는 것이다. 기본편의 다형성에서 배울 오버라이딩은 시그니처가 같은 메서드 가운데 어느 클래스의 것을 실행할지를 JVM이 실행 중인 객체의 실제 타입으로 고르는 것이다. JLS 8.4.9절도 시그니처는 컴파일 타임에 정해지고, 인스턴스 메서드라면 실제로 호출될 메서드는 실행 시점에 정해진다고 두 단계를 나누어 적는다. 두 선택이 서로 다른 시점에 서로 다른 정보로 이루어진다는 것을 알면 다형성에서 흔히 겪는 혼동을 피할 수 있다.

    스레드마다 스택이 따로 있다는 사실은 자바 고급 1편의 동시성에서 핵심이 된다. JVMS 2.6절은 한 스레드가 만든 프레임은 그 스레드에 국한되며 다른 스레드가 참조할 수 없다고 적는다. 지역 변수는 다른 스레드와 공유되지 않으므로 여러 스레드가 같은 메서드를 동시에 실행해도 지역 변수끼리는 간섭하지 않는다. 문제가 되는 것은 힙에 있어 여러 스레드가 함께 볼 수 있는 객체다. 스프링의 웹 애플리케이션에서 요청마다 다른 스레드가 같은 객체의 메서드를 실행하는 구조를 이해할 때, 무엇이 스택에 있고 무엇이 힙에 있는지를 구분하는 눈이 그대로 쓰인다.

    마지막으로 스택 트레이스는 앞으로 가장 자주 읽게 될 출력이다. 스프링 애플리케이션의 예외 로그는 수십 줄의 at 줄로 이루어지고, 그 대부분은 프레임워크의 메서드다. 그 줄들이 "아래에서 위로 호출이 쌓인 순서"라는 것을 알면 내 코드의 줄을 찾아 원인을 좁혀 갈 수 있다.
    메서드
    계산에 이름을 붙여 한 곳에 정의하고 여러 곳에서 호출해 쓰는 단위. 선언부(반환 타입, 이름, 매개변수 목록)와 본문으로 이루어진다.
    매개변수와 인수
    매개변수는 메서드 선언에 적힌 변수이고 인수는 호출할 때 넘기는 식이다. 호출 때마다 인수의 값으로 초기화된 새 매개변수 변수가 만들어진다.
    프레임
    메서드 호출 한 번의 작업 공간. 지역 변수 배열, 피연산자 스택, 런타임 상수 풀 참조를 가진다. 호출 때 JVM 스택에 쌓이고 반환 때 사라지며, 크기는 컴파일 타임에 정해진다.
    값에 의한 전달
    자바의 인수 전달은 언제나 값의 복사다. 기본형은 수가, 참조형은 참조값이 복사된다. 매개변수에 대입해도 호출한 쪽 변수는 바뀌지 않지만, 참조를 따라가 고친 객체의 변경은 보인다.
    반환
    return은 메서드를 즉시 끝내고 값을 호출한 쪽 프레임의 피연산자 스택으로 넘긴다. 반환 타입이 있는 메서드는 모든 실행 경로에서 값을 돌려주어야 한다.
    호출과 형변환
    인수 전달과 반환에는 자동 형변환(확대 변환)이 적용된다. 값을 잃을 수 있는 변환은 캐스트가 필요하고, 대입과 달리 상수의 암묵적 축소는 허용되지 않는다.
    시그니처
    메서드 이름과 매개변수 타입 목록. 반환 타입과 매개변수 이름은 들어가지 않는다. 한 클래스에 같은 시그니처의 메서드를 둘 둘 수 없다.
    오버로딩 해석
    이름이 같은 메서드 가운데 어느 것을 부를지는 컴파일러가 인수의 타입으로 정한다. 적용 가능한 후보 중 가장 구체적인 것을 고르고, 하나로 정해지지 않으면 컴파일 오류다.
    StackOverflowError
    프레임이 쌓여 스레드의 스택 한도를 넘을 때 난다. 종료 조건 없는 재귀가 대표적인 원인이며 힙 부족과는 다른 오류다.

    실무에서 값 전달 규칙이 문제가 되는 순간은 대개 "넘겨준 것이 바뀌었다"는 형태로 나타난다. 메서드에 컬렉션이나 객체를 넘겼더니 호출 뒤에 내용이 달라져 있고, 그 변경이 어디서 일어났는지 찾는 데 시간이 든다. 참조가 복사된다는 것을 알면 질문이 분명해진다. 이 메서드는 받은 객체를 읽기만 하는가, 고치는가. 고친다면 호출하는 쪽이 그것을 알고 있어야 한다. 그래서 받은 인수를 고치지 않고 새 값을 만들어 반환하는 방식이 선호되고, 고쳐서는 안 되는 데이터는 복사본을 넘기거나 변경할 수 없는 타입으로 만든다. 반대로 매개변수 자체에 새 객체를 대입해 놓고 호출한 쪽에 반영되기를 기대하는 코드는 버그다. 그때는 새 객체를 반환해야 한다.

    오버로딩은 편리하지만 선택이 컴파일 타임에 일어난다는 점 때문에 사고가 난다. 변수에 담긴 값의 실제 타입이 무엇이든 컴파일러는 선언된 타입만 보고 메서드를 고른다. 매개변수 개수가 같고 타입이 서로 변환 가능한 오버로딩을 여러 개 두면, 호출하는 쪽의 사소한 타입 차이(리터럴에 L을 붙였는지, 변수가 int인지 long인지)에 따라 다른 메서드가 불린다. 그 차이를 읽는 사람이 놓치기 쉽다. 그래서 오버로딩은 매개변수 개수가 다른 경우나, 어느 것이 불려도 결과의 의미가 같은 경우에 쓰고, 동작이 달라진다면 이름을 다르게 짓는 편이 안전하다.

     int n = 5; change(n);에서 change가 static void change(int n) { n = 10; }일 때, 호출 뒤 main의 n이 5인 이유로 가장 정확한 것은? void 메서드 안의 대입은 메서드가 끝날 때 자동으로 취소되기 때문이다. 호출할 때 인수의 값 5가 change 프레임의 새 지역 변수로 복사되고, n = 10은 그 변수에만 쓰기 때문이다. 두 변수의 이름이 같아서 컴파일러가 change 안의 대입을 무시하기 때문이다. int는 불변 타입이라 한번 정해진 값을 바꿀 수 없기 때문이다. 자바의 인수 전달은 값의 복사다. iload로 읽은 값 5가 스택을 거쳐 change 프레임의 지역 변수 0번이 되고, n = 10은 istore_0으로 그 칸에 쓴다. main의 n은 다른 프레임의 다른 변수라서 영향이 없다. 대입은 정상 실행되며 취소되지 않고, 이름이 같은 것은 우연일 뿐이며, int 변수는 얼마든지 다시 대입할 수 있다. 배열을 받는 메서드 안에서 arr[0] = 99;를 실행하면 호출한 쪽의 배열에도 99가 보인다. 이 현상에 대한 설명으로 옳은 것은? 배열은 기본형과 달리 변수 자체가 전달되므로(참조에 의한 전달) 메서드 안에서 arr = new int[3];을 해도 호출한 쪽 변수가 새 배열을 가리킨다. 배열을 넘기면 배열 전체가 복사되고, 메서드가 끝날 때 복사본의 내용이 원본에 다시 덮어써진다. 배열은 스택이 아닌 곳에 있어서 값에 의한 전달 규칙이 적용되지 않는 예외다. 이 경우에도 값이 복사된다. 복사되는 값이 참조라서 두 변수가 같은 배열 객체를 가리키고, arr[0] = 99는 그 객체를 고친다. 전달 규칙은 하나다. 인수의 값이 새 매개변수 변수에 복사된다. 배열 변수의 값은 참조이므로 참조값이 복사되고 배열 객체는 복사되지 않는다. 그래서 요소 변경은 호출한 쪽에 보이지만, 매개변수에 새 배열을 대입하는 것은 호출된 메서드의 프레임만 바꾸므로 호출한 쪽 변수에는 영향이 없다. 이 둘째 사실이 "참조에 의한 전달"이 아님을 보여 준다. print(int), print(long), print(double)이 오버로딩되어 있다. char c = 'A'; print(c);에 대한 설명으로 옳은 것은? 실행 중에 JVM이 c에 든 값을 보고 세 메서드 중 하나를 고른다. char를 받는 메서드가 없으므로 컴파일 오류다. 컴파일러가 인수의 타입 char에서 자동 형변환으로 맞는 후보 가운데 가장 구체적인 print(int)를 골라 클래스 파일에 기록한다. 세 메서드 모두 적용 가능하므로 모호하다는 컴파일 오류가 난다. 오버로딩 선택은 컴파일 타임에 인수의 컴파일 타임 타입으로 이루어진다. char는 int, long, double로 모두 확대 변환되므로 셋 다 적용 가능하지만, int가 long과 double보다 구체적이어서 하나로 정해진다. 모호 오류는 가장 구체적인 메서드가 하나로 정해지지 않을 때만 난다. 선택 결과는 print:(I)V라는 디스크립터로 클래스 파일에 적히고 실행 중에는 바뀌지 않는다. 한 클래스에 static int parse(String s)와 static long parse(String s)를 함께 선언할 수 없는 이유는? 시그니처는 메서드 이름과 매개변수 타입으로 이루어지고 반환 타입은 포함되지 않으므로, 두 메서드의 시그니처가 같기 때문이다. JVM의 클래스 파일 형식이 이름이 같은 메서드를 둘 이상 담지 못하기 때문이다. int와 long 사이에 자동 형변환이 있어서 두 메서드가 같은 타입으로 취급되기 때문이다. static 메서드는 오버로딩할 수 없기 때문이다. JLS에서 시그니처는 이름과 매개변수 타입 목록이고, 같은 시그니처의 메서드를 한 클래스에 둘 선언하면 컴파일 오류다. 반환 타입만으로는 parse("1");처럼 결과를 쓰지 않는 호출에서 대상을 고를 수 없다. 클래스 파일은 이름이 같고 디스크립터가 다른 메서드를 얼마든지 담을 수 있고, static 메서드도 매개변수가 다르면 오버로딩된다. 종료 조건이 없는 재귀 메서드를 실행했을 때 일어나는 일로 옳은 것은? 같은 메서드의 호출은 프레임을 재사용하므로 프로그램이 영원히 실행된다. 호출마다 힙에 객체가 쌓여 OutOfMemoryError가 난다. 호출마다 새 프레임이 JVM 스택에 쌓이고 반환이 없으므로, 스택 한도를 넘는 순간 StackOverflowError가 난다. 컴파일러가 종료 조건이 없음을 발견하고 컴파일 오류를 낸다. 프레임은 메서드가 호출될 때마다 새로 만들어진다. 같은 메서드라도 호출마다 별개의 프레임과 지역 변수를 갖는다. 반환하지 않으면 프레임은 사라지지 않고 쌓이기만 하며, 스레드의 스택이 허용된 크기를 넘으면 JVM이 StackOverflowError를 던진다. 이는 힙 부족과 다른 오류다. 컴파일러는 재귀가 끝나는지 검사하지 않는다.
    메서드(method)
    이름, 매개변수, 반환 타입, 본문을 가진 실행 단위. 호출하면 본문이 실행되고 결과를 돌려준다.
    매개변수(parameter)
    메서드 선언에 적힌 변수. 호출될 때마다 새로 만들어져 인수의 값으로 초기화된다.
    인수(argument)
    메서드를 호출할 때 괄호 안에 넘기는 식. 계산된 값이 매개변수로 복사된다. 인자라고도 한다.
    JVM 스택(Java Virtual Machine stack)
    스레드마다 하나씩 있는 메모리 영역. 메서드 호출마다 프레임이 쌓이고 반환하면 사라진다.
    프레임(frame)
    메서드 호출 한 번에 대응하는 작업 공간. 지역 변수 배열과 피연산자 스택, 런타임 상수 풀에 대한 참조를 가진다.
    피연산자 스택(operand stack)
    프레임 안에서 계산의 중간값을 올리고 내리는 스택. 인수를 준비하고 반환값을 받는 자리이기도 하다.
    값에 의한 전달(pass by value)
    인수의 값을 복사해 호출된 쪽의 새 변수에 넣는 전달 방식. 자바의 유일한 인수 전달 방식이다.
    시그니처(signature)
    메서드 이름과 매개변수 타입 목록. 한 클래스 안에서 메서드를 구별하는 기준이며 반환 타입은 포함하지 않는다.
    오버로딩(overloading)
    이름이 같고 시그니처가 다른 메서드를 여러 개 선언하는 것. 어느 것을 부를지는 컴파일 타임에 인수의 타입으로 정해진다.
    재귀 호출(recursion)
    메서드가 자기 자신을 호출하는 것. 종료 조건에 도달하지 못하면 프레임이 계속 쌓여 StackOverflowError가 난다.
