    같은 코드를 여러 번 — 반복이 필요한 이유

    1부터 3까지 출력하는 프로그램은 출력문 세 줄이면 된다. 1부터 100까지라면 백 줄을 써야 하고, 몇까지 출력할지를 실행 중에 입력받는다면 줄 수를 미리 정할 수조차 없다. 같은 일을 횟수만 바꿔 되풀이하는 요구는 프로그램에서 가장 흔한 요구에 속한다. 목록의 모든 항목을 처리하고, 조건이 만족될 때까지 다시 시도하고, 합계를 누적한다. 이런 요구를 표현하는 구문이 반복문(loop)이다.

    04회에서 조건문은 "조건이 거짓이면 이 구간을 건너뛰어라"라는 앞으로 가는 점프로 번역된다는 것을 보았다. 반복문은 새로운 종류의 명령을 필요로 하지 않는다. 같은 조건 점프와 goto를 쓰되 점프의 목적지가 앞이 아니라 뒤, 곧 이미 지나온 위치라는 점만 다르다. pc 레지스터가 이미 실행한 명령의 주소로 되돌아가면 그 구간이 다시 실행된다. 반복문의 정체는 이것이 전부이고, while·do-while·for의 차이는 조건 검사를 어디에 두고 어디로 되돌아가느냐의 차이다.

    이 장의 핵심

    반복은 뒤로 가는 점프다. 반복문의 종류는 조건 검사와 되돌아가는 점프를 배치하는 방식의 차이이고, break와 continue는 그 배치 안에서 목적지가 정해진 goto다. 반복이 끝나는지는 "되돌아가는 조건이 언젠가 거짓이 되는가"라는 한 가지 물음으로 귀결된다.

    while 문 — 조건이 참인 동안 되돌아간다

    while 문의 형태는 if 문과 같다. 괄호 안의 조건식이 참이면 본문을 실행한다. 다른 점은 본문을 실행한 뒤다. if 문은 그대로 아래로 진행하지만 while 문은 조건식으로 되돌아가 다시 검사한다. JLS §14.12는 이 과정을 이렇게 정한다. 먼저 조건식을 평가한다. 값이 참이면 본문을 실행하고, 본문이 정상적으로 끝나면 while 문 전체를 조건식 평가부터 다시 실행한다. 값이 거짓이면 while 문이 끝난다. 조건식이 처음부터 거짓이면 본문은 한 번도 실행되지 않는다.

    public class Loop {
    static int sumWhile(int n) {
        int sum = 0;
        int i = 1;
        while (i <= n) {
            sum += i;
            i++;
        }
        return sum;
    }

    public static void main(String[] args) {
        System.out.println(sumWhile(3));
        System.out.println(sumWhile(0));
    }
}

    1부터 n까지의 합을 구하는 코드다. 반복문을 읽을 때는 변수의 값이 한 바퀴마다 어떻게 변하는지를 표로 적어 보는 것이 가장 확실하다. sumWhile(3)의 실행을 따라가 보자.

    조건 검사ii <= 3본문 실행 후 sum본문 실행 후 i
    1번째1참0 + 1 = 12
    2번째2참1 + 2 = 33

    표에서 세 가지를 읽을 수 있다. 첫째, 본문은 3번 실행됐지만 조건식은 4번 평가됐다. 본문이 n번 실행되는 while 문에서 조건식은 n + 1번 평가된다. 마지막 한 번은 "이제 그만"을 확인하는 평가다. 둘째, 반복이 끝난 뒤 i의 값은 3이 아니라 4다. 반복을 끝낸 것은 조건을 거짓으로 만든 바로 그 값이다. 셋째, sumWhile(0)에서는 첫 검사 1 <= 0이 거짓이므로 본문이 한 번도 실행되지 않고 초깃값 0이 그대로 반환된다.

    이 코드에는 반복문이 제대로 동작하기 위한 세 요소가 모두 들어 있다. 반복을 제어하는 변수의 초기화(int i = 1), 계속할지를 정하는 조건(i <= n), 그리고 조건을 언젠가 거짓으로 만드는 갱신(i++)이다. 갱신이 빠지면 i가 영원히 1이어서 조건이 계속 참이고 반복이 끝나지 않는다. 컴파일러는 이것을 오류로 알려 주지 않는다. while 문 자체에는 갱신이라는 개념이 없고, 본문 안의 어떤 문장이 조건에 영향을 주는지는 프로그래머만 안다.

    sum처럼 반복하는 동안 결과를 모아 가는 변수를 누적 변수(accumulator)라 한다. 반복문 밖에서 초기화하고 안에서 갱신한다는 점이 중요하다. int sum = 0;을 본문 안에 넣으면 바퀴마다 0으로 되돌아가 누적되지 않는다. 더해 가는 누적은 0에서, 곱해 가는 누적은 1에서 시작한다.

    while이 바이트코드가 되는 모습 — 뒤로 가는 점프

    javac Loop.java로 컴파일한 뒤 javap -c Loop로 sumWhile의 바이트코드를 본다. OpenJDK 21의 javac가 만든 결과이고, 오른쪽 주석은 설명을 위해 덧붙인 것이다. 지역 변수 0번이 n, 1번이 sum, 2번이 i다.

      static int sumWhile(int);
       0: iconst_0
       1: istore_1          // sum = 0
       2: iconst_1
       3: istore_2          // i = 1
       4: iload_2           // [조건 검사 시작] i를 스택에
       5: iload_0           // n을 스택에
       6: if_icmpgt     19  // i > n 이면 19번으로 (반복 탈출)
       9: iload_1
      10: iload_2
      11: iadd
      12: istore_1          // sum = sum + i
      13: iinc          2, 1  // i++
      16: goto          4   // [뒤로 점프] 조건 검사로 되돌아간다
      19: iload_1
      20: ireturn

    구조는 04회에서 본 if 문과 거의 같다. 6번의 if_icmpgt 19는 소스의 조건 i <= n을 뒤집은 것으로, 조건이 거짓이면 본문을 건너뛰어 19번으로 간다. if 문과 다른 곳은 단 한 줄, 16번의 goto 4다. 본문이 끝나면 pc를 4번으로 되돌린다. 이렇게 자신보다 앞에 있는(주소가 더 작은) 위치로 가는 점프를 뒤로 가는 분기(backward branch)라 한다. if 문에 뒤로 가는 goto 하나를 붙인 것이 while 문이다.

           ┌──────────────────────────────────────────┐
       ▼                                          │
  4: 조건 검사 (i <= n ?) ── 거짓 ──┐              │
       │ 참                         │              │
       ▼                            │              │
  9: 본문 (sum += i; i++)           │              │
       │                            │              │
       ▼                            │              │
 16: goto 4 ────────────────────────┼──────────────┘
                                    ▼
                              19: 반복 이후의 코드

    13번의 iinc 2, 1도 눈여겨볼 만하다. i++가 "스택에 올리고, 1을 올리고, 더하고, 다시 저장하는" 네 명령이 아니라 지역 변수 2번에 1을 직접 더하는 명령 하나로 번역됐다. JVM의 명령 집합에서 지역 변수를 피연산자 스택을 거치지 않고 바로 고치는 명령은 int용인 iinc뿐이다. 반복 카운터를 하나씩 올리는 일이 그만큼 흔하다는 것을 명령 집합의 설계가 보여 준다. 참고로 javac 21은 문장으로 단독 사용된 i++, ++i, i += 1을 모두 같은 iinc 하나로 번역한다. 값을 쓰지 않고 증가만 시키는 자리에서 전위와 후위 가운데 무엇을 쓰든 실행되는 명령은 같다.

    반복 한 바퀴에 실행되는 명령은 4번부터 16번까지 9개다. n이 3이면 이 구간이 세 번 돌고, 네 번째에는 4·5·6번만 실행된 뒤 19번으로 빠져나간다. 소스에서는 while이라는 한 단어였던 것이 실행 시점에는 "같은 명령 구간을 pc가 여러 번 지나가는 일"로 나타난다. 본문의 코드가 n벌 복사되는 것이 아니라 한 벌의 코드가 n번 실행된다.

    while 문이 조건 검사, 본문, 뒤로 가는 goto 세 구간으로 번역되고 pc가 고리 모양으로 도는 모습을 보여 준다. 가운데에 세로로 쌓인 바이트코드 상자 네 묶음이 있는 기술 다이어그램. 위에서부터 첫 번째 묶음은 회색 상자 "0~3: 초기화 (sum = 0, i = 1)", 두 번째 묶음은 파란 상자 "4~6: 조건 검사 if_icmpgt 19", 세 번째 묶음은 초록 상자 "9~13: 본문 (sum += i, i++)", 네 번째는 주황 상자 "16: goto 4". 그 아래 떨어져서 회색 상자 "19~20: 반복 이후". 주황 상자 "16: goto 4"의 오른쪽에서 나와 위로 크게 휘어 파란 상자 "4~6"으로 들어가는 굵은 주황색 화살표를 그리고 라벨 "뒤로 가는 점프"를 붙인다. 파란 상자의 왼쪽에서 나와 아래로 길게 내려가 "19~20: 반복 이후" 상자로 들어가는 파란 점선 화살표를 그리고 라벨 "조건이 거짓이면 탈출"을 붙인다. 파란 상자에서 초록 상자로 내려가는 짧은 화살표에는 "참"이라는 라벨. 왼쪽 여백에 작은 글씨로 "한 벌의 코드가 여러 번 실행된다"라는 설명 라벨을 둔다. 흰 배경, 고정폭 글꼴, 평면 스타일. while 문은 if 문의 구조에 뒤로 가는 goto 하나를 더한 것이다. pc가 조건 검사와 본문 사이를 고리 모양으로 돈다.

    같은 반복, 다른 배치 — JVMS의 예와 javac의 출력

    JVM 명세는 3장에서 자바 코드가 바이트코드로 번역되는 예를 여럿 보여 준다. 그 가운데 §3.2에는 0부터 99까지 세기만 하는 반복문의 예가 있는데, 명세에 실린 바이트코드와 OpenJDK 21의 javac가 실제로 만드는 바이트코드가 다르다. 두 가지를 나란히 놓으면 "반복을 점프로 옮기는 방법은 하나가 아니다"라는 것을 볼 수 있다.

    void spin() {
    int i;
    for (i = 0; i < 100; i++) {
        ;    // 본문은 비어 있다
    }
}

    왼쪽은 조건 검사를 반복의 아래에 둔다. 처음 한 번만 goto 8로 조건 검사로 건너가고, 그 뒤로는 조건이 참일 때 if_icmplt 5가 곧바로 뒤로 점프한다. 오른쪽은 조건 검사를 위에 두고 본문 끝에 무조건 goto를 둔다. 두 코드는 같은 일을 하며 둘 다 명세에 맞는 올바른 번역이다. 한 바퀴에 실행되는 점프 명령의 수는 다르다. 왼쪽은 한 바퀴에 조건 점프 하나, 오른쪽은 조건 점프 하나와 goto 하나다.

    이 차이에서 두 가지를 배울 수 있다. 하나는 명세와 구현의 구분이다. JLS는 반복문의 의미(무엇이 어떤 순서로 평가되는가)를 정하고 JVMS는 각 명령의 동작을 정하지만, 어떤 소스를 어떤 명령 배치로 옮길지는 컴파일러의 재량이다. 다른 하나는 javac의 성격이다. javac의 출력은 소스의 구조를 거의 그대로 옮긴 형태이고, 실행 속도를 좌우하는 최적화는 JVM이 실행 중에 JIT 컴파일러로 수행한다. 이 이야기는 이 회차의 뒷부분에서 다시 한다.

    do-while 문 — 먼저 실행하고 나중에 묻는다

    while 문은 조건을 먼저 검사하므로 본문이 0번 실행될 수 있다. 본문을 일단 한 번은 실행해야 조건을 물을 수 있는 경우가 있다. 입력을 받아 보고 올바르지 않으면 다시 받는 경우가 대표적이다. do-while 문은 순서를 바꾼다. JLS §14.13에 따르면 먼저 본문을 실행하고, 본문이 정상적으로 끝나면 조건식을 평가해서 참이면 전체를 다시 실행한다. 그래서 본문이 항상 한 번 이상 실행된다.

    static int sumDo(int n) {
    int sum = 0;
    int i = 1;
    do {
        sum += i;
        i++;
    } while (i <= n);
    return sum;
}

    sumDo(3)은 sumWhile(3)과 같이 6을 돌려준다. 차이는 경계에서 드러난다. sumWhile(0)은 0이지만 sumDo(0)은 1이다. 조건 1 <= 0을 묻기 전에 본문이 한 번 실행되어 sum에 1이 더해지기 때문이다. "0번 반복"이 올바른 답일 수 있는 문제에 do-while을 쓰면 이런 식으로 틀린다. 문법상의 주의점도 하나 있다. do-while은 while (조건) 뒤에 세미콜론이 붙는다.

      static int sumDo(int);
       0: iconst_0
       1: istore_1
       2: iconst_1
       3: istore_2
       4: iload_1           // [본문 시작]
       5: iload_2
       6: iadd
       7: istore_1          // sum = sum + i
       8: iinc          2, 1  // i++
      11: iload_2           // [조건 검사]
      12: iload_0
      13: if_icmple     4   // i <= n 이면 4번으로 (뒤로 점프)
      16: iload_1
      17: ireturn

    while과 비교하면 두 가지가 다르다. 조건 검사가 본문 아래에 있고, goto가 없다. 13번의 조건 점프가 직접 뒤로 간다. 그리고 조건이 뒤집히지 않았다. 소스의 i <= n이 그대로 if_icmple이다. while에서는 "거짓이면 앞으로 탈출"이 필요해서 조건을 뒤집었지만, do-while에서는 "참이면 뒤로 되돌아감"이 필요하므로 조건을 그대로 쓴다. 앞 절에서 본 JVMS의 spin 번역은 while 형태의 반복을 "처음에 조건 검사로 건너뛰는 do-while"로 옮긴 것이었음을 이제 알 수 있다.

    break와 continue — 반복의 흐름을 바꾸는 점프

    반복을 계속할지는 조건식이 정하지만, 본문 한가운데에서 흐름을 바꾸고 싶을 때가 있다. 찾던 것을 찾았으니 더 돌 필요가 없거나, 이번 바퀴의 나머지는 건너뛰고 다음 바퀴로 가고 싶은 경우다. 앞의 것이 break, 뒤의 것이 continue다.

    break — 반복 밖으로

    JLS §14.15에 따르면 레이블이 없는 break는 자신을 감싼 가장 안쪽의 switch, while, do, for 문으로 제어를 옮기고, 그 문장은 즉시 정상적으로 끝난다. 04회에서 switch를 빠져나가는 데 쓴 break와 같은 문장이다.

    static int firstMultiple(int k, int limit) {
    int i = 1;
    while (i <= limit) {
        if (i % k == 0) {
            break;
        }
        i++;
    }
    return i;
}

    1부터 차례로 올라가며 k의 배수를 처음 만나면 멈춘다. firstMultiple(7, 100)은 7을 돌려준다. firstMultiple(7, 5)는 6을 돌려주는데, 5까지 배수를 찾지 못해 조건 i <= limit이 거짓이 되어 끝났기 때문이다. 이 반복문에는 출구가 둘이다. 조건식이 거짓이 되어 나가는 정상 출구와 break로 나가는 출구다. 반복이 끝난 뒤의 코드는 어느 출구로 나왔는지 구별해야 할 때가 많고, 이 예에서는 i <= limit인지를 다시 보면 구별할 수 있다.

    continue — 이번 바퀴만 건너뛰기

    JLS §14.16에 따르면 continue는 while, do, for 문 안에서만 쓸 수 있고, 자신을 감싼 가장 안쪽 반복문의 현재 바퀴를 즉시 끝내고 다음 바퀴를 시작하게 한다. 반복문 자체를 끝내지는 않는다. 1부터 n까지의 수 가운데 홀수만 더하는 코드를 while로 써 보자.

    static int sumOddWhile(int n) {
    int sum = 0;
    int i = 0;
    while (i < n) {
        i++;
        if (i % 2 == 0) {
            continue;
        }
        sum += i;
    }
    return sum;
}

    sumOddWhile(10)은 1 + 3 + 5 + 7 + 9 = 25를 돌려준다. i가 짝수이면 continue가 실행되어 sum += i를 건너뛴다. 이 코드에서 i++가 본문의 맨 위에 있다는 점이 중요하다. 순서를 바꿔 i++를 맨 아래에 두면 프로그램이 끝나지 않는다.

    int sum = 0;
int i = 0;
while (i < 10) {
    if (i % 2 == 0) {
        continue;      // i가 0일 때 여기로 온다
    }
    sum += i;
    i++;               // continue가 이 줄을 건너뛴다
}

    i가 0이면 짝수이므로 continue가 실행되고, i++를 건너뛴 채 조건 검사로 돌아간다. i는 여전히 0이고 조건은 여전히 참이며, 다시 continue가 실행된다. 영원히 반복된다. while 문에서 continue의 목적지는 조건 검사이고, 조건을 바꾸는 갱신이 그 사이에 실행된다는 보장이 없기 때문에 생기는 함정이다. 바이트코드에서 확인하면 while 안의 continue는 조건 검사 위치로 가는 goto다.

    for 문 — 반복의 세 요소를 한곳에

    앞에서 반복문에는 초기화, 조건, 갱신이라는 세 요소가 있다고 했다. while 문에서는 이 셋이 흩어져 있다. 초기화는 반복문 위에, 조건은 괄호 안에, 갱신은 본문 어딘가에 있다. 본문이 길어지면 갱신을 찾기 어렵고, 방금 본 것처럼 continue가 갱신을 건너뛰는 사고도 난다. for 문은 세 요소를 한 줄에 모은다.

    static int sumFor(int n) {
    int sum = 0;
    for (int i = 1; i <= n; i++) {
        sum += i;
    }
    return sum;
}

    차이 2: 제어 변수의 스코프

    for의 초기화식에서 선언한 변수는 for 문 안에서만 쓸 수 있다. JLS §6.3은 그 변수의 스코프가 초기화식 자신, 조건식, 갱신식, 본문까지라고 정한다. for 문이 끝난 뒤에 i를 쓰려고 하면 그런 변수를 찾을 수 없다는 컴파일 오류가 난다. while에서는 제어 변수를 반복문 밖에 선언해야 하므로 반복이 끝난 뒤에도 변수가 남는다. 반복이 끝난 뒤 그 값이 필요하면(앞의 firstMultiple처럼) 밖에 선언하고, 필요 없으면 for 안에 가둬서 다른 코드가 실수로 건드릴 여지를 없앤다. 변수가 살아 있는 범위를 좁히는 일의 의미는 06회에서 자세히 다룬다.

    세 부분은 모두 생략할 수 있다

    for의 세 부분은 각각 비워 둘 수 있다. 초기화식을 비우면 아무 일도 하지 않고, 갱신식을 비워도 마찬가지다. 조건식을 비우면 항상 참으로 취급된다. JLS §14.14.1.2는 조건식이 없는 for 문이 정상적으로 끝나는 방법은 break뿐이라고 적고 있다. 그래서 for (;;)는 while (true)와 같은 무한 반복의 관용 표현이다. 초기화식과 갱신식에는 쉼표로 여러 식을 나열할 수도 있다.

    for (int i = 0, j = 10; i < j; i += 3, j -= 3) {
    System.out.println(i + " " + j);
}

    첫 바퀴에 0과 10, 둘째 바퀴에 3과 7을 출력하고, 갱신 뒤 i는 6, j는 4가 되어 조건 i < j가 거짓이므로 끝난다. 초기화식에서 여러 변수를 선언할 때는 타입이 모두 같아야 한다. 선언문 하나로 쓰는 것이기 때문이다.

    for와 while 가운데 무엇을 쓸지는 다음 기준으로 정한다. 반복 횟수나 범위가 반복을 시작하기 전에 정해져 있고 제어 변수가 일정하게 변한다면 for가 맞다. 세 요소가 한 줄에 있어 "어디서 시작해 어디까지 얼마씩"이 바로 읽힌다. 언제 끝날지가 본문의 실행 결과에 달려 있다면(입력이 끝날 때까지, 오차가 충분히 작아질 때까지) while이 의도를 더 잘 드러낸다. 본문을 한 번은 실행해야 조건을 물을 수 있다면 do-while이다.

    중첩 반복문 — 점프 안의 점프

    반복문의 본문에는 어떤 문장이든 올 수 있으므로 또 다른 반복문도 올 수 있다. 표의 행과 열을 차례로 처리하거나 두 값의 모든 조합을 살펴볼 때 쓴다.

    for (int i = 2; i <= 3; i++) {
    for (int j = 1; j <= 3; j++) {
        System.out.print(i + "x" + j + "=" + (i * j) + " ");
    }
    System.out.println();
}

    바깥 반복이 한 바퀴 도는 동안 안쪽 반복은 처음부터 끝까지 전부 돈다. i가 2인 동안 j가 1, 2, 3을 모두 거치고, 그다음에야 i가 3이 된다. 여기서 놓치기 쉬운 점은 안쪽 for의 초기화식 int j = 1이 바깥 반복의 매 바퀴마다 다시 실행된다는 것이다. 안쪽 for 문 전체가 바깥 반복의 본문이고, 본문은 바퀴마다 처음부터 실행되기 때문이다. 바이트코드로 확인한다.

        for (int j = 0; j < m; j++) {

    레이블 — 바깥 반복을 직접 벗어나기

    중첩 반복 안에서 break나 continue를 쓰면 가장 안쪽 반복문에만 작용한다. 안쪽 반복에서 답을 찾았을 때 바깥 반복까지 한 번에 끝내고 싶다면 방법이 필요하다. 플래그 변수를 두고 바깥 조건에서 검사하는 방법이 있고, 자바가 제공하는 레이블(label)을 쓰는 방법이 있다. 문장 앞에 이름:을 붙이면 그 문장에 레이블이 붙고(JLS §14.7), break 이름;이나 continue 이름;으로 그 문장을 지목할 수 있다.

    static int labeled(int n) {
    int found = -1;
    outer:
    for (int i = 2; i < n; i++) {
        for (int j = 2; j < n; j++) {
            if (i * j == n) {
                found = i;
                break outer;
            }
        }
    }
    return found;
}

    n을 2 이상의 두 수의 곱으로 나타낼 수 있으면 그중 작은 쪽 인수를 돌려주는 코드다. labeled(35)는 i가 5, j가 7일 때 곱이 35가 되어 5를 돌려주고, labeled(13)은 끝까지 찾지 못해 -1을 돌려준다. break outer;는 outer 레이블이 붙은 문장, 곧 바깥 for 문 전체를 끝낸다.

    레이블이 없는 break였다면 25번의 목적지가 안쪽 반복 바로 뒤인 34번이었을 것이다. 레이블은 그 목적지를 40번으로 바꿀 뿐이다. 여기서 정확히 해 둘 점이 있다. break outer;는 outer:라고 적힌 위치로 가는 것이 아니다. 그랬다면 바깥 반복이 처음부터 다시 시작될 것이다. 레이블은 점프할 위치의 이름이 아니라 문장의 이름이고, break는 그 문장의 끝 바로 뒤로, continue는 그 반복문의 다음 바퀴로 간다. continue outer;는 안쪽 반복의 나머지를 버리고 바깥 반복의 갱신식으로 간다.

    static int countPrimes(int n) {
    int primes = 0;
    outer:
    for (int i = 2; i <= n; i++) {
        for (int j = 2; j * j <= i; j++) {
            if (i % j == 0) {
                continue outer;    // i는 소수가 아니다. 다음 i로
            }
        }
        primes++;
    }
    return primes;
}

    countPrimes(20)은 8을 돌려준다(2, 3, 5, 7, 11, 13, 17, 19). 나누어떨어지는 j를 하나라도 찾으면 continue outer;가 primes++를 건너뛰고 다음 i로 넘어간다.

    레이블에 관한 규칙 몇 가지를 덧붙인다. JLS §14.7에 따르면 레이블의 스코프는 그 레이블이 붙은 문장 안쪽이고, 그 안에서 같은 이름의 레이블을 다시 쓰면 컴파일 오류다. 레이블 이름은 변수나 메서드 이름과 겹쳐도 된다. 서로 다른 이름 공간에 속하기 때문이다. 또 레이블 붙은 break의 대상은 반복문이 아니어도 되므로 blk: { ... break blk; ... }처럼 평범한 블록을 빠져나가는 데도 쓸 수 있다. 반면 레이블 붙은 continue의 대상은 반드시 반복문이어야 한다.

    자바에 goto가 없는 이유

    바이트코드에는 goto가 넘쳐나는데 자바 언어에는 goto 문이 없다. JLS §14.7은 C, C++와 달리 자바에는 goto 문이 없고 레이블은 break와 continue에만 쓰인다고 밝힌다. 그런데도 goto는 예약어여서 변수 이름으로 쓸 수 없다. JLS §3.9는 const와 goto가 현재 쓰이지 않지만 예약되어 있고, 이 C++ 키워드가 프로그램에 잘못 등장했을 때 컴파일러가 더 나은 오류 메시지를 낼 수 있게 하려는 것이라고 설명한다.

    자바가 허용하는 점프를 정리하면 두 방향뿐이다. 반복문의 시작이나 갱신으로 되돌아가는 것(반복, continue)과, 자신을 감싼 문장의 끝으로 빠져나가는 것(조건문, break)이다. switch의 case 라벨을 빼면, 어떤 블록의 한가운데로 뛰어드는 점프는 표현할 수 없다. 그래서 자바 코드의 블록은 실행이 들어오는 입구가 맨 위 하나뿐인 것이 보통이고, 06회에서 다룰 변수의 스코프와 초기화 검사가 이 성질에 기대고 있다. 레이블은 이 제약 안에서 "몇 겹을 빠져나갈지"만 고르게 해 주는 장치다. 다만 레이블이 필요해질 만큼 중첩이 깊다면 안쪽 반복을 별도의 메서드로 떼어 내고 return으로 빠져나오는 편이 대개 더 읽기 쉽다.

    바깥 고리 안에 안쪽 고리가 들어 있는 구조에서, 레이블 없는 break는 안쪽 고리 바로 뒤로, 레이블 붙은 break는 바깥 고리 바로 뒤로 간다는 것을 보여 준다. 큰 둥근 사각형(연한 파란 테두리, 라벨 "바깥 반복 outer") 안에 작은 둥근 사각형(연한 초록 테두리, 라벨 "안쪽 반복")이 들어 있는 다이어그램. 바깥 사각형 안 위쪽에 상자 "바깥 조건 i < n", 그 아래 작은 사각형 안에 상자 "안쪽 조건 j < n"과 그 아래 상자 "본문 i * j == n ?"이 세로로 놓인다. 작은 사각형 아래, 바깥 사각형 안에 상자 "i++". 바깥 사각형 아래 바깥쪽에 회색 상자 "반복 이후의 코드". 안쪽 사각형의 오른쪽 테두리를 따라 아래에서 위로 도는 초록 화살표에 라벨 "안쪽 뒤로 점프", 바깥 사각형의 오른쪽 테두리를 따라 아래에서 위로 도는 파란 화살표에 라벨 "바깥 뒤로 점프". "본문" 상자에서 나와 안쪽 사각형을 벗어나 "i++" 상자로 가는 회색 점선 화살표에 라벨 "break". "본문" 상자에서 나와 두 사각형을 모두 벗어나 "반복 이후의 코드" 상자로 가는 굵은 주황색 화살표에 라벨 "break outer". 흰 배경, 평면 스타일, 고정폭 글꼴. 레이블 없는 break는 가장 안쪽 반복만 끝내고, 레이블 붙은 break는 이름이 붙은 문장 전체를 끝낸다. 둘 다 앞으로 가는 goto이고 목적지만 다르다.

    끝나지 않는 반복 — 컴파일러가 아는 것과 모르는 것

    반복문에서 가장 흔한 버그는 끝나지 않는 반복이다. 원인은 언제나 같다. 되돌아가는 조건이 영원히 참이다. 다만 그렇게 되는 경로는 여러 가지이고, 그중 컴파일러가 알아채는 것은 극히 일부다.

    의도한 무한 반복과 도달 가능성 검사

    끝나는 조건을 본문 중간에서 판단해야 할 때는 조건식을 상수 true로 두고 break로 빠져나가는 형태를 쓴다.

    static int forever() {
    int i = 0;
    while (true) {
        i++;
        if (i == 10) {
            break;
        }
    }
    return i;
}
      static int forever();
       0: iconst_0
       1: istore_0
       2: iinc          0, 1  // [반복 시작] i++
       5: iload_0
       6: bipush        10
       8: if_icmpne     2   // i != 10 이면 반복 시작으로
      11: goto          14  // break
      14: iload_0
      15: ireturn

    조건 검사에 해당하는 명령이 아예 없다. 조건이 상수 true이므로 검사할 것이 없고, 본문만 고리를 이룬다. for (;;)로 써도 같은 바이트코드가 나온다. 이 메서드에서 break를 지우면 어떻게 될까. javac는 return i;가 도달할 수 없는 문장(unreachable statement)이라며 컴파일 오류를 낸다. JLS §14.22는 while 문이 정상적으로 끝날 수 있는 경우를 두 가지로 정한다. 조건식이 값이 true인 상수식이 아니거나, 그 while 문을 빠져나가는 도달 가능한 break가 있는 경우다. 둘 다 아니면 while 문 뒤의 코드는 실행될 수 없으므로 오류다.

    이 검사가 보는 것은 상수식뿐이라는 점이 중요하다. while (true)는 알아채지만 int i = 1; while (i > 0) { }는 알아채지 못한다. i > 0은 변수를 포함하므로 상수식이 아니고, 명세의 규칙은 상수가 아닌 식의 값을 따지지 않는다. 끝나지 않는 반복의 대부분은 컴파일러의 눈에 정상적인 코드다.

    오버플로가 만드는 무한 반복

    for (int i = Integer.MAX_VALUE - 1; i <= Integer.MAX_VALUE; i++) {
    System.out.println("i = " + i);
}
    i = 2147483646
i = 2147483647
i = -2147483648
i = -2147483647

    두 번만 돌고 끝날 것처럼 보이지만 끝나지 않는다. 조건 i <= Integer.MAX_VALUE는 int가 가질 수 있는 모든 값에 대해 참이다. int의 최댓값보다 큰 int는 없기 때문이다. i가 최댓값일 때 i++를 하면 앞 회차에서 본 오버플로가 일어나 최솟값으로 넘어가고, 조건은 여전히 참이다. 조건식이 "타입이 표현할 수 있는 범위 전체"를 참으로 만들면 그 반복은 갱신이 아무리 올바라도 끝날 수 없다. 범위가 더 좁은 타입에서는 더 쉽게 일어난다. for (byte b = 0; b < 128; b++)는 byte의 최댓값이 127이므로 같은 이유로 끝나지 않는다. 127 다음 값은 128이 아니라 -128이다.

    같은 오버플로는 누적 변수에서도 조용히 일어난다. 1부터 100,000까지의 합을 int 변수에 누적하면 결과는 705082704로 출력된다. 올바른 값 5,000,050,000은 int의 최댓값 2,147,483,647을 넘기 때문이다. 누적 변수를 long으로 바꾸면 5000050000이 나온다. 반복 횟수와 한 번에 더해지는 값의 크기를 곱해 보아 결과가 타입의 범위를 넘을 수 있는지 확인하는 습관이 필요하다.

    실수 카운터

    for (float f = 0.0f; f != 1.0f; f += 0.1f) {
    // 열 바퀴 뒤에 끝날 것처럼 보인다
}

    이 반복도 끝나지 않는다. 0.1은 이진 부동소수점으로 정확히 표현되지 않으므로, float 변수에 0.1f를 열 번 더한 값은 1.0f가 아니라 1.0000001이다. f는 1.0f를 "밟지 않고" 지나가고, != 조건은 계속 참이다. double로 바꿔도 사정은 같다. double 변수에 0.1을 열 번 더하면 0.9999999999999999가 된다. 실수를 ==나 !=로 비교해 반복을 끝내려 해서는 안 된다.

    실수 카운터에는 함정이 하나 더 있다. 값이 커지면 1을 더해도 값이 변하지 않는 구간이 온다.

    float big = 16777216f;                 // 2의 24제곱
System.out.println(big + 1 == big);    // true

    float의 가수부는 24비트라서 16,777,216을 넘는 홀수를 표현할 수 없다. 16,777,217은 표현 가능한 두 값 16,777,216과 16,777,218의 정확히 가운데에 있고, 부동소수점의 반올림 규칙에 따라 16,777,216이 된다. 그래서 for (float x = 16777214f; x < 16777220f; x++)는 x가 16,777,216에 도달한 뒤 더 이상 증가하지 않아 끝나지 않는다. 횟수를 세는 변수는 정수로 두고, 실수 값이 필요하면 i * 0.1f처럼 정수 카운터로부터 계산하는 것이 원칙이다.

    세미콜론 하나

    for (int i = 0; i < 3; i++);
{
    System.out.println("once");
}

    이 코드는 once를 한 번만 출력한다. for 문의 닫는 괄호 뒤에 있는 세미콜론이 빈 문장이고, 그것이 for의 본문이다. 반복은 아무 일도 하지 않으며 세 번 돌고, 뒤따르는 블록은 for와 무관하게 한 번 실행된다. 04회의 if (조건);과 같은 종류의 실수다. while에서는 더 나쁘다. while (i < 3);은 본문이 빈 문장이어서 i가 변할 기회가 없고, i가 3보다 작다면 그 자리에서 영원히 돈다.

    반복과 스택 프레임 — 변수는 한 번만 자리를 잡는다

    반복문이 도는 동안 메모리에서는 무슨 일이 일어날까. 메서드가 호출되면 스택 프레임이 하나 만들어지고, 그 안에 지역 변수 배열이 들어 있다. JVMS §2.6.1에 따르면 이 배열의 길이는 컴파일 시점에 정해진다. 반복문은 메서드 호출이 아니므로 새 프레임을 만들지 않는다. 반복이 백 번 돌든 백만 번 돌든 같은 프레임의 같은 칸을 계속 고쳐 쓸 뿐이다. sumWhile에서 sum은 처음부터 끝까지 지역 변수 1번 칸이고, i는 2번 칸이다.

    본문 안에서 선언한 변수도 마찬가지다. 앞의 nested에서 안쪽 for의 j는 바깥 반복이 돌 때마다 "새로 선언"되지만, 바이트코드에서는 매번 같은 4번 칸에 0을 다시 저장하는 istore 4일 뿐이다. 선언문이 실행될 때마다 메모리를 새로 할당하고 반복이 끝날 때 해제하는 일은 일어나지 않는다. 그러므로 "변수를 반복문 밖에 선언하면 할당 횟수가 줄어 빠르다"는 추측은 지역 변수에 대해서는 성립하지 않는다. 기본형 지역 변수를 반복문 안에 둘지 밖에 둘지는 그 변수가 어느 범위에서 의미를 갖는가로 정하면 된다.

    카운터의 타입에 관해서도 바이트코드가 알려 주는 것이 있다. 합계를 구하는 반복의 카운터와 누적 변수를 모두 long으로 바꾸면 다음과 같이 컴파일된다.

           5: lload         4   // i
       7: lload_0           // n
       8: lcmp              // 비교 결과를 int로
       9: ifgt          26  // 그 int를 다시 검사
      ...
      17: lload         4
      19: lconst_1
      20: ladd
      21: lstore        4   // i = i + 1

    int 카운터에서 if_icmpgt 하나였던 비교가 lcmp와 ifgt 둘이 되었고, iinc 하나였던 증가가 네 명령이 되었다. long에는 iinc에 해당하는 명령이 없기 때문이다. JVMS는 JVM이 int 비교에 중점을 두어 int용 조건 분기 명령을 풍부하게 갖추었고(§2.11.7), long과 실수 타입은 중간 수준으로 지원되어 온전한 조건 분기 명령 집합만이 빠져 있다고(3장) 설명한다. 이것은 바이트코드의 명령 수에 관한 이야기이고, 기계어로 컴파일된 뒤의 속도를 말해 주는 것은 아니다. 타입 선택의 기준은 정확성이다. 반복 횟수가 int 범위(약 21억)를 넘을 수 있으면 long을 써야 하고, 그렇지 않다면 int가 자연스러운 기본값이다.

    JVM은 오래 도는 반복을 어떻게 다루는가

    지금까지 본 바이트코드는 JVM이 실행을 시작하는 형태다. HotSpot JVM은 처음에는 바이트코드를 인터프리터로 한 명령씩 해석해 실행하다가, 자주 실행되는 코드를 찾아 JIT 컴파일러로 기계어로 바꾼다. "자주 실행되는"을 판정하려면 세어야 한다. OpenJDK 21 HotSpot의 컴파일 정책 소스(compilationPolicy.hpp)의 설명에 따르면 메서드마다 두 가지를 센다. 메서드가 호출된 횟수와, 뒤로 가는 분기가 실행된 횟수(backedge count)다.

    뒤로 가는 분기를 따로 세는 이유는 반복문 때문이다. main 메서드가 한 번 호출되어 그 안에서 반복문이 1억 번 도는 프로그램을 생각해 보자. 호출 횟수는 끝까지 1이므로 호출 횟수만 센다면 이 메서드는 영영 컴파일 대상이 되지 못한다. 뒤로 가는 분기의 횟수를 세면 "호출은 드물지만 안에서 오래 도는" 메서드를 찾아낼 수 있다. 이 회차에서 반복의 정체라고 부른 뒤로 가는 점프가 JVM에게는 "여기에 반복이 있다"는 신호다.

    문제가 하나 남는다. 그 메서드는 이미 인터프리터로 실행되는 중이고 반복의 한가운데에 있다. 컴파일된 코드가 다음 호출부터 쓰인다면, 호출이 한 번뿐인 이 메서드에는 소용이 없다. HotSpot은 실행 중인 반복의 중간에서 인터프리터 프레임을 컴파일된 코드의 프레임으로 바꿔치기한다. 이를 OSR(on-stack replacement)이라 한다. 직접 확인할 수 있다.

    public class Hot {
    public static void main(String[] args) {
        long sum = 0;
        for (int i = 0; i < 100_000_000; i++) {
            sum += i % 7;
        }
        System.out.println(sum);
    }
}

    여기서 설명한 계수 방식과 OSR은 JVM 명세가 아니라 HotSpot의 구현이다. JVMS는 바이트코드의 의미만 정하고, 그것을 해석해 실행할지 기계어로 바꿔 실행할지는 구현에 맡긴다. 어떤 방식으로 실행하든 프로그램의 결과는 같아야 한다.
    한 번 호출된 메서드 안의 긴 반복이 인터프리터로 돌다가, 뒤로 가는 분기 횟수가 쌓이면 반복 도중에 컴파일된 코드로 넘어가는 과정을 시간 순서로 보여 준다. 왼쪽에서 오른쪽으로 흐르는 가로 타임라인 다이어그램. 타임라인 위에 세 구간이 색으로 구분된다: 첫 구간은 회색 막대 "인터프리터 실행", 둘째 구간은 파란 막대 "C1 컴파일 코드 (단계 3)", 셋째 구간은 주황 막대 "C2 컴파일 코드 (단계 4)". 타임라인 전체 위에 긴 중괄호와 라벨 "main 메서드 호출 1회, 반복 1억 번". 첫 구간 아래에 작은 계수기 그림과 라벨 "뒤로 가는 분기 횟수 증가". 첫 구간과 둘째 구간의 경계, 둘째 구간과 셋째 구간의 경계에 각각 세로 점선과 번개 모양 표시, 라벨 "OSR: 반복 도중 교체". 타임라인 아래에 작은 고리 모양 화살표 아이콘을 세 구간에 걸쳐 반복해 그려 반복이 계속 돌고 있음을 나타내고, 고리 옆에 라벨 "goto 4". 흰 배경, 평면 스타일, 굵은 산세리프 글꼴. HotSpot은 뒤로 가는 분기의 실행 횟수로 오래 도는 반복을 찾아내고, 메서드가 끝나기를 기다리지 않고 반복 도중에 컴파일된 코드로 갈아탄다.

    다른 주제와의 연결

    반복문은 이후의 거의 모든 회차에서 쓰인다. 07회에서는 Scanner로 입력을 받으면서 "올바른 값이 들어올 때까지" 또는 "종료를 뜻하는 값이 들어올 때까지" 도는 반복을 쓴다. 횟수가 정해지지 않은 반복이므로 while과 break의 조합이 자연스럽다. 08회의 배열에서는 for 문의 제어 변수가 배열의 색인이 된다. 0에서 시작해 i < 길이 조건으로 도는 형태가 관용구가 되는 이유를 거기서 보게 되고, 색인 없이 모든 요소를 차례로 꺼내는 향상된 for 문(enhanced for)도 그때 다룬다.

    중급 2편의 컬렉션에서는 같은 순회가 반복자(Iterator)라는 객체를 통해 이루어지고, 고급 3편의 스트림에서는 반복문 자체가 소스에서 사라진다. 그래도 그 아래에서 실행되는 것은 이 회차에서 본 것과 같은 조건 검사와 뒤로 가는 점프다. 추상화가 올라가도 "몇 번 도는가"와 "몇 겹으로 도는가"라는 물음은 그대로 남는다. 데이터베이스가 두 테이블을 조인할 때 한쪽의 행마다 다른 쪽을 찾아보는 방식도 구조상 중첩 반복이며, 실행 계획을 읽을 때 같은 눈으로 보게 된다.

    고급 1편의 멀티스레드에서는 반복문이 다른 모습으로 등장한다. 조건이 바뀔 때까지 반복하며 기다리는 코드에서, 조건 변수를 바꾸는 쪽이 다른 스레드라면 반복하는 스레드가 그 변경을 언제 보게 되는지가 문제가 된다. 이 회차의 전제는 반복 조건에 영향을 주는 값을 본문이 직접 바꾼다는 것이었는데, 그 전제가 깨질 때 무슨 일이 생기는지는 메모리 가시성이라는 주제로 그때 다룬다.
    반복은 뒤로 가는 점프
    반복문은 조건 점프와 이미 지나온 위치로 되돌아가는 점프의 조합으로 번역된다. 한 벌의 코드를 pc가 여러 번 지나갈 뿐 코드가 복사되지 않는다.
    while과 do-while
    while은 조건을 먼저 검사하므로 본문이 0번 실행될 수 있고 조건은 n + 1번 평가된다. do-while은 본문을 먼저 실행하므로 최소 1번 실행되고 조건은 n번 평가된다.
    for 문
    초기화·조건·갱신을 한 줄에 모은 while이다. 단순한 경우 바이트코드가 while과 같다. 차이는 continue가 갱신식으로 간다는 것과 제어 변수의 스코프가 for 문 안으로 제한된다는 것이다.
    break와 continue
    둘 다 goto로 번역된다. break는 감싼 문장 바로 뒤로, continue는 while에서는 조건 검사로, for에서는 갱신식으로 간다.
    중첩 반복
    안쪽 고리가 바깥 고리 안에 통째로 들어 있다. 안쪽 초기화는 바깥 바퀴마다 다시 실행되고, 가장 안쪽 본문의 실행 횟수는 각 반복 횟수의 곱이다.
    레이블
    문장에 붙이는 이름이다. 레이블 붙은 break는 그 문장 전체를 끝내고, 레이블 붙은 continue는 그 반복문의 다음 바퀴로 간다. 레이블의 위치로 점프하는 것이 아니다.
    끝나지 않는 반복
    컴파일러는 조건이 상수 true인 경우만 알아챈다. 오버플로로 조건이 항상 참이 되는 경우, 실수 카운터가 목표값을 정확히 밟지 못하는 경우, 빈 문장이 본문이 된 경우는 실행해 봐야 드러난다.
    반복과 프레임
    반복은 새 스택 프레임을 만들지 않고 같은 지역 변수 칸을 고쳐 쓴다. 본문 안에서 선언한 변수도 매 바퀴 같은 칸을 다시 쓴다.
    뒤로 가는 분기 횟수와 OSR
    HotSpot은 호출 횟수와 함께 뒤로 가는 분기의 횟수를 세어 오래 도는 반복을 찾고, 반복 도중에 인터프리터 실행을 컴파일된 코드로 교체한다.

    실무에서 반복문 때문에 생기는 장애는 문법을 몰라서가 아니라 경계와 종료 조건을 잘못 잡아서 생긴다. 첫 번째 유형은 한 칸 차이 오류(off-by-one)다. <와 <= 가운데 무엇을 쓸지, 시작값이 0인지 1인지에 따라 반복 횟수가 하나 달라진다. 기준을 하나로 정해 두면 실수가 준다. 0에서 시작하고 i < n으로 끝내면 정확히 n번 돌고, 이 형태는 배열 색인과도 맞아떨어진다. 다른 형태를 써야 할 때는 n이 0일 때, 1일 때, 경계값일 때를 손으로 따라가 본다.

    두 번째 유형은 끝나지 않는 반복이다. 운영 환경에서는 CPU 사용률이 100%에 붙은 스레드로 나타난다. 원인은 이 회차에서 본 것들이다. 갱신이 실행되지 않는 경로가 있거나(while 안의 continue, 예외를 삼키고 다시 도는 재시도), 종료 조건이 타입의 범위 전체를 포함하거나, 실수를 같음 비교로 검사한 경우다. 외부 조건에 의존하는 반복, 예를 들어 응답이 올 때까지 다시 시도하는 반복에는 조건과 별개로 최대 횟수나 제한 시간을 함께 두는 것이 기본이다. 조건이 영원히 만족되지 않는 상황은 언젠가 온다.

    세 번째 유형은 중첩으로 인한 성능 문제다. 데이터가 적을 때는 드러나지 않다가 데이터가 늘면서 갑자기 느려지는 코드의 상당수는 두 겹 반복이다. 목록 안에서 무언가를 찾는 일을 다른 목록의 항목마다 되풀이하면 일의 양은 두 크기의 곱이 된다. 반복문이 직접 보이지 않아도 마찬가지다. 반복문 안에서 호출한 메서드가 안에서 다시 반복한다면 그것이 두 겹이다. 반복 안에서 데이터베이스 조회를 호출하는 코드가 조회 횟수 문제로 이어지는 것도 같은 구조다.

    반대로 걱정하지 않아도 되는 것도 있다. for와 while 가운데 무엇이 빠른지, 지역 변수를 반복문 안에 선언하면 느린지, i++와 ++i 가운데 무엇이 빠른지 같은 물음은 이 회차에서 확인한 대로 바이트코드 수준에서 차이가 없다. 이런 선택은 읽기 쉬움과 변수의 스코프를 기준으로 하면 된다. 측정 없이 반복문의 모양을 바꿔 성능을 얻으려 하기보다 반복의 횟수와 겹 수를 줄이는 쪽이 효과가 크다.

    3번. count는 15다. a가 0, 1, 2, 3, 4일 때 안쪽 본문이 각각 5, 4, 3, 2, 1번 실행된다. 안쪽 조건식은 바깥 한 바퀴마다 본문 실행 횟수보다 한 번씩 더 평가되므로 6 + 5 + 4 + 3 + 2 = 20번이다. 바깥 조건식은 6번 평가된다.

    4번. while(또는 for) 형태다. 조건 검사(2~4번)가 본문(7번) 앞에 있고, 조건이 거짓일 때 앞으로 탈출하는 조건 점프와 본문 끝의 무조건 goto 2가 있다. do-while이라면 조건 검사가 본문 뒤에 있고 조건 점프가 직접 뒤로 갔을 것이다. 소스는 static int f(int n) { int i = 0; while (i < n) { i += 2; } return i; }다. if_icmpge는 소스의 조건 i < n이 뒤집힌 것이고, iinc 1, 2는 지역 변수 1번에 2를 더하는 i += 2다. 같은 내용을 for (; i < n; i += 2) { }로 써도 같은 바이트코드가 나오므로 이 출력만으로 for와 while을 구별할 수는 없다.

    5번. n은 4, x는 6이다. x는 50, 25, 12, 6으로 변하고, 6이 되었을 때 조건 x > 10이 거짓이 된다. 조건을 x > 100으로 바꾸면 while 문에서는 첫 검사 100 > 100이 거짓이어서 본문이 실행되지 않고 n은 0, x는 100으로 남는다. do-while 문에서는 본문이 먼저 한 번 실행되어 n은 1, x는 50이 된 뒤에야 조건을 검사하고 끝난다. 조건이 처음부터 거짓인 경우에 두 구문의 결과가 갈린다.

     본문이 정확히 n번 실행되고 정상적으로 끝난 while 문에서 조건식은 몇 번 평가되며, 그 이유는 무엇인가? n번. 본문을 실행할 때마다 한 번씩 검사하기 때문이다. n - 1번. 첫 바퀴는 검사 없이 들어가기 때문이다. n + 1번. 본문에 들어갈 때마다 한 번씩, 그리고 반복을 끝내기 위해 거짓으로 평가되는 한 번이 더 필요하기 때문이다. 컴파일러가 조건 검사의 위치를 정하므로 알 수 없다. while 문은 본문에 들어가기 전에 매번 조건을 평가하므로 참으로 평가된 횟수가 n번이고, 반복이 끝나려면 조건이 한 번 거짓으로 평가되어야 한다. 조건 검사를 바이트코드의 어디에 배치하든 평가 횟수는 언어 명세가 정한 의미에 따라 같다. 첫 바퀴에 검사가 없는 것은 do-while이다. while 문에서 i++보다 앞에 있는 continue 때문에 무한 반복이 생기던 코드를 같은 본문 그대로 for (...; ...; i++)로 옮기면 무한 반복이 사라진다. 그 이유는? for 문에서는 continue가 break처럼 반복을 끝내기 때문이다. for 문의 continue는 조건 검사가 아니라 갱신식으로 가므로 i++가 반드시 실행되기 때문이다. for 문은 while 문과 다른 JVM 명령으로 컴파일되어 continue가 무시되기 때문이다. for 문의 제어 변수는 스코프가 좁아서 값이 자동으로 증가하기 때문이다. continue는 현재 바퀴의 나머지 본문을 건너뛴다. while에서는 그다음이 조건 검사이므로 본문 안에 있던 갱신이 실행되지 않을 수 있다. for의 갱신식은 본문 밖, for 문의 구조에 속하므로 continue의 목적지가 갱신식이 된다. 바이트코드에서 while의 continue는 조건 검사 위치로, for의 continue는 iinc가 있는 위치로 가는 goto다. for (int i = 0; i <= Integer.MAX_VALUE; i++) { }가 끝나지 않는 이유로 옳은 것은? 본문이 비어 있어서 컴파일러가 반복을 최적화로 제거하지 못하기 때문이다. i++가 최댓값에서 예외를 던지고 JVM이 그 예외를 무시하기 때문이다. 조건식이 상수식이어서 컴파일러가 true로 바꿔 버리기 때문이다. 모든 int 값은 int의 최댓값 이하이므로 조건이 거짓이 될 수 있는 i의 값이 존재하지 않기 때문이다. 반복이 끝나려면 조건을 거짓으로 만드는 값에 도달해야 하는데, i <= Integer.MAX_VALUE를 거짓으로 만드는 int 값은 없다. 최댓값에서 i++를 하면 예외 없이 오버플로가 일어나 최솟값이 되고 조건은 여전히 참이다. i가 변수이므로 조건식은 상수식이 아니며, 그래서 컴파일러의 도달 가능성 검사도 이 무한 반복을 알아채지 못한다. 바깥 for 문에 outer: 레이블이 붙어 있고 안쪽 for 문 안에서 break outer;가 실행되었다. 다음에 실행되는 것은? 바깥 for 문 전체가 끝나고, 그 바로 뒤의 문장이 실행된다. outer:가 적힌 위치로 돌아가 바깥 for 문이 초기화식부터 다시 실행된다. 안쪽 for 문만 끝나고 바깥 for 문의 갱신식이 실행된다. 바깥 for 문의 조건식이 다시 평가되고, 참이면 다음 바퀴가 시작된다. 레이블은 점프할 위치가 아니라 문장에 붙은 이름이다. break 레이블;은 그 이름이 붙은 문장 전체를 즉시 끝내므로 그 문장 바로 뒤로 간다. 셋째 보기는 레이블 없는 break의 동작이고, 넷째 보기에 가까운 것은 continue outer;인데 그 경우에도 조건식 전에 갱신식이 먼저 실행된다. HotSpot이 메서드의 호출 횟수뿐 아니라 뒤로 가는 분기의 실행 횟수도 세는 까닭으로 가장 적절한 것은? 뒤로 가는 분기는 JVM 명세상 금지된 동작이어서 감시해야 하기 때문이다. 뒤로 가는 분기가 실행될 때마다 새 스택 프레임이 만들어져 메모리 사용량을 추적해야 하기 때문이다. 한두 번만 호출되지만 그 안에서 오래 반복하는 메서드는 호출 횟수만으로는 자주 실행되는 코드로 판정되지 않기 때문이다. 뒤로 가는 분기의 횟수가 정해진 값을 넘으면 무한 반복으로 보고 프로그램을 멈추기 위해서다. 반복은 바이트코드에서 뒤로 가는 분기로 나타나므로, 그 실행 횟수는 "이 메서드 안에서 반복이 얼마나 도는가"의 척도가 된다. 호출이 한 번뿐인 메서드라도 이 횟수가 쌓이면 컴파일 대상이 되고, OSR로 반복 도중에 컴파일된 코드로 넘어간다. 반복은 새 프레임을 만들지 않으며, JVM은 끝나지 않는 반복을 스스로 멈추지 않는다.
    반복문(loop)
    조건이 참인 동안 같은 코드 구간을 되풀이해 실행하는 구문. 자바에는 while, do-while, for, 향상된 for가 있다.
    뒤로 가는 분기(backward branch, backedge)
    현재 위치보다 앞쪽 주소(이미 지나온 명령)로 가는 점프. 바이트코드에서 반복을 만드는 요소다.
    제어 변수(loop control variable)
    반복을 계속할지 정하는 조건에 쓰이고 바퀴마다 갱신되는 변수. 흔히 i, j로 이름 짓는다.
    누적 변수(accumulator)
    반복하는 동안 합계나 개수 같은 결과를 모아 가는 변수. 반복문 밖에서 초기화하고 안에서 갱신한다.
    레이블(label)
    문장 앞에 이름: 형태로 붙이는 이름. 레이블 붙은 break와 continue의 대상을 지정하는 데만 쓰인다.
    iinc
    int 지역 변수에 상수를 직접 더하는 JVM 명령. i++, i += 2 같은 갱신이 이 명령 하나로 번역된다.
    도달할 수 없는 문장(unreachable statement)
    어떤 실행 경로로도 실행될 수 없다고 컴파일러가 명세의 규칙으로 판정한 문장. 자바에서는 컴파일 오류다.
    한 칸 차이 오류(off-by-one error)
    경계 조건을 잘못 잡아 반복이 의도보다 한 번 더 또는 덜 실행되는 오류.
    OSR(on-stack replacement)
    실행 중인 메서드의 인터프리터 프레임을 반복 도중에 컴파일된 코드의 프레임으로 교체하는 HotSpot의 기법.
