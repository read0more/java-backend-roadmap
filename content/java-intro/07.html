    값이 코드 바깥에서 들어와야 하는 이유

    지금까지 만든 프로그램은 다루는 값이 모두 소스 코드 안에 적혀 있었다. int age = 25;라고 쓰면 25라는 값은 컴파일할 때 이미 정해져 클래스 파일의 바이트코드 안에 들어간다. 다른 나이로 실행해 보려면 소스를 고치고 다시 컴파일해야 한다. 프로그램을 만든 사람만 값을 바꿀 수 있는 셈이다.

    쓸모 있는 프로그램은 대부분 실행된 뒤에야 알 수 있는 값을 다룬다. 사용자가 누구인지, 몇 개를 주문하는지, 어떤 파일을 열지는 실행 시점(runtime)에 바깥에서 들어온다. 조건문과 반복문을 배운 지금이 입력을 붙이기에 알맞은 때다. 같은 코드가 입력에 따라 다른 길로 흐르는 것을 직접 볼 수 있기 때문이다.

    입력을 받는다는 말 뒤에는 세 가지 일이 숨어 있다. 첫째, 운영체제가 프로세스에게 바이트를 넘겨준다. 둘째, 그 바이트를 문자로 해석한다. 셋째, 문자열 "25"를 정수 25 같은 값으로 바꾼다. 자바의 java.util.Scanner는 둘째와 셋째를 대신 해 주는 도구다. 이 회차는 Scanner의 메서드 이름을 외우는 대신, 글자 하나가 키보드에서 int 변수에 닿기까지 지나는 경로를 한 번 끝까지 따라간다. 그 경로를 알고 나면 입문자가 가장 자주 부딪히는 문제, 곧 nextInt() 다음의 nextLine()이 아무것도 읽지 않고 지나가는 현상이 왜 생기는지 스스로 설명할 수 있다.

    표준 입출력 — 프로세스가 시작할 때 이미 열려 있는 세 통로

    1회차에서 본 것처럼 java 명령을 실행하면 운영체제가 JVM 프로세스를 하나 만든다. 프로세스(process)는 실행 중인 프로그램이다. 유닉스 계열 운영체제의 표준인 POSIX는 프로그램이 시작될 때 세 개의 스트림이 미리 정의되어 있고 따로 열 필요가 없다고 정한다. 표준 입력(standard input, stdin), 표준 출력(standard output, stdout), 표준 오류(standard error, stderr)다. 운영체제는 프로세스가 연 파일이나 장치를 파일 디스크립터(file descriptor)라는 작은 정수로 구분하는데, 이 셋에는 차례로 0, 1, 2가 배정된다.

    여기서 중요한 점은 프로그램이 "키보드"나 "화면"을 직접 알지 못한다는 것이다. 프로그램은 0번에서 읽고 1번과 2번에 쓸 뿐이다. 0번에 무엇이 연결되어 있는지는 프로세스를 시작시킨 쪽, 곧 셸이나 IDE가 정한다. 터미널에서 그냥 실행하면 셋 모두 터미널에 연결되어 있어서 키보드로 친 것이 0번으로 들어오고, 1번과 2번에 쓴 것이 화면에 나온다.

    이름파일 디스크립터자바에서의 이름자바 타입터미널에서 실행했을 때
    표준 입력0System.inInputStream키보드 입력
    표준 출력1System.outPrintStream화면 출력
    표준 오류2System.errPrintStream화면 출력

    자바는 이 세 통로를 System 클래스의 필드로 내놓는다. System.in의 Javadoc은 이 스트림이 이미 열려 있고 입력을 공급할 준비가 되어 있으며, 보통 키보드 입력이나 호스트 환경·사용자가 지정한 다른 입력원에 대응한다고 설명한다. "다른 입력원"이라는 말이 핵심이다. OpenJDK 21의 System 초기화 코드를 보면 0번 디스크립터를 가리키는 FileDescriptor.in으로 FileInputStream을 만들고, 그것을 BufferedInputStream으로 감싸 System.in에 넣는다. 자바 쪽에는 키보드에 관한 코드가 없다. 0번에서 바이트를 읽는 코드가 있을 뿐이다.

                        ┌──────────────── JVM 프로세스 ────────────────┐
 키보드 ─▶ 터미널 ─▶│ [0] 표준 입력 ─▶ System.in   (InputStream)   │
 화면   ◀─ 터미널 ◀─│ [1] 표준 출력 ◀─ System.out  (PrintStream)   │
 화면   ◀─ 터미널 ◀─│ [2] 표준 오류 ◀─ System.err  (PrintStream)   │
                    └──────────────────────────────────────────────┘
   0, 1, 2번에 무엇을 연결할지는 프로세스를 시작시킨 쪽(셸, IDE)이 정한다.
    JVM 프로세스가 0, 1, 2번 세 통로만 알고 있고, 그 바깥에 무엇이 연결되는지는 셸이 정한다는 것을 한눈에 보여 준다. 깔끔한 기술 다이어그램. 가운데에 큰 둥근 사각형 상자가 있고 라벨은 "JVM 프로세스". 상자의 왼쪽 벽에 세 개의 작은 포트가 세로로 나란히 있고 각각 "0 표준 입력", "1 표준 출력", "2 표준 오류"라고 적혀 있다. 상자 안쪽에는 각 포트 옆에 "System.in", "System.out", "System.err" 라벨이 붙은 작은 칸이 있다. 상자 왼쪽 바깥에는 "터미널"이라고 적힌 모니터와 키보드 그림이 있다. 키보드에서 0번 포트로 들어가는 화살표, 1번과 2번 포트에서 모니터로 나가는 화살표 두 개를 그린다. 그림 아래쪽에는 점선으로 된 대안 경로를 두 개 그린다. 하나는 "파일" 아이콘에서 0번 포트로 들어가는 점선 화살표이고 라벨은 "리다이렉션", 다른 하나는 "다른 프로세스" 상자에서 0번 포트로 들어가는 점선 화살표이고 라벨은 "파이프". 흰 배경, 파란색과 회색 위주의 차분한 색, 손글씨가 아닌 또렷한 고딕체 한국어 라벨. 프로그램은 0번에서 읽고 1·2번에 쓴다. 그 바깥이 키보드인지 파일인지 다른 프로세스인지는 실행하는 쪽이 정한다.

    연결을 바꾸는 방법이 리다이렉션(redirection)과 파이프(pipe)다. 뒤에서 만들 합계 프로그램 InputSum을 예로 들면 아래 네 가지 실행은 모두 같은 클래스 파일을 쓴다.

    java InputSum                        # 0번이 터미널: 키보드로 입력한다
java InputSum < numbers.txt          # 0번이 파일: 파일 내용이 입력이 된다
printf '10 20\n0\n' | java InputSum  # 0번이 앞 명령의 표준 출력에 이어진다
java InputSum > result.txt           # 1번이 파일: 출력이 화면 대신 파일에 쌓인다

    코드는 한 글자도 바뀌지 않는다. 프로그램이 "키보드에서 읽어라"가 아니라 "표준 입력에서 읽어라"라고 쓰여 있기 때문에 가능한 일이다. 이 회차의 예제 결과도 이 방법으로 확인했다. 사람이 손으로 치는 대신 printf로 만든 입력을 파이프로 넣으면 같은 입력을 몇 번이든 똑같이 되풀이할 수 있다.

    표준 오류가 따로 있는 이유도 여기서 드러난다. System.err의 Javadoc은 주 출력 스트림이 파일 등으로 돌려져 있더라도 사용자가 즉시 알아야 하는 오류 메시지를 보여 주는 데 이 스트림을 쓰는 것이 관례라고 적고 있다. 예외로 프로그램이 죽을 때 나오는 스택 트레이스는 표준 오류로 나간다. 그래서 java InputSum > result.txt처럼 표준 출력만 파일로 돌려도 오류 메시지는 화면에 남는다.

    터미널은 한 줄이 완성되어야 넘겨준다

    키를 하나 누를 때마다 그 글자가 곧바로 프로그램에 도착한다고 생각하기 쉽다. 실제로는 그렇지 않다. POSIX의 터미널 인터페이스 규정에 따르면 표준 모드(canonical mode)에서 터미널 입력은 줄 단위로 처리되고, 읽기 요청은 한 줄 전체가 입력되거나 시그널을 받기 전에는 돌아오지 않는다. 줄은 줄바꿈 문자(NL)로 끝난다. Windows 콘솔도 기본으로 켜져 있는 줄 입력 모드(ENABLE_LINE_INPUT)에서는 캐리지 리턴 문자를 읽어야 읽기 함수가 돌아온다고 Microsoft 문서가 설명한다.

    줄을 완성하기 전의 편집도 터미널이 처리한다. 253을 치고 백스페이스로 3을 지운 뒤 Enter를 누르면 프로그램에는 25와 줄바꿈만 도착한다. 지운 글자와 백스페이스는 프로그램이 볼 기회가 없다. 화면에 내가 친 글자가 보이는 것(에코)도 프로그램이 출력한 것이 아니라 터미널이 한 일이다.

    이 동작에서 세 가지 결과가 따라 나온다.

    1. 프로그램은 기다린다. 읽기를 요청했는데 아직 완성된 줄이 없으면, 읽기를 요청한 스레드는 그 자리에서 멈춰 Enter를 기다린다. 이렇게 결과가 준비될 때까지 호출이 돌아오지 않는 것을 블로킹(blocking)이라고 한다.
    2. 한 줄은 통째로 도착한다. 10 20 30을 치고 Enter를 누르면 세 수가 한꺼번에 프로그램으로 넘어온다. 프로그램이 첫 번째 수만 읽었더라도 나머지 둘은 이미 프로그램 쪽에 와 있다.
    3. 줄바꿈 문자도 데이터다. Enter는 "입력 완료"라는 신호인 동시에 줄바꿈 문자로서 입력 데이터에 포함된다. 25를 치고 Enter를 누르면 도착하는 것은 두 글자가 아니라 2, 5, 줄바꿈 세 글자다.

    셋째가 이 회차 전체를 관통한다. 눈에 보이지 않는 줄바꿈 문자가 입력에 들어 있다는 사실을 잊으면 뒤에서 볼 문제를 이해할 수 없다. 줄 끝을 표현하는 문자는 환경마다 다르다. System.lineSeparator()의 Javadoc에 따르면 유닉스 계열에서는 "\n"(LF, 코드 값 10) 하나이고 Windows에서는 "\r\n"(CR LF, 코드 값 13과 10) 둘이다.

    입력의 끝(EOF)

    기다림과 구분해야 하는 상태가 하나 더 있다. 더 올 입력이 아예 없는 상태, 곧 입력의 끝(end of file, EOF)이다. 파일을 표준 입력에 연결했다면 파일을 끝까지 읽은 때가 EOF다. 파이프라면 앞 프로그램이 출력을 닫은 때다. 터미널에서는 사용자가 EOF 특수 문자를 입력해서 알린다. POSIX는 줄의 맨 앞에서 EOF 문자를 받으면 읽기 요청이 0바이트를 돌려주고 이것이 파일 끝을 뜻한다고 정한다. 이 문자가 무엇인지는 터미널 설정에 달려 있으며, macOS의 termios 문서에 적힌 기본값은 Ctrl+D다.

    자바에서는 InputStream.read()가 이 상태를 -1로 알려 준다. Javadoc의 표현으로는 스트림의 끝에 도달해 읽을 바이트가 없으면 -1을 돌려주고, 그렇지 않으면 입력이 들어오거나 스트림의 끝이 감지되거나 예외가 날 때까지 블록한다. "아직 안 왔다"와 "이제 안 온다"는 다른 상태이고, 프로그램은 둘을 다르게 다뤄야 한다.

    바이트를 직접 읽어 보면 보이는 것

    Scanner 없이 System.in에서 직접 읽으면 프로그램에 실제로 도착하는 것이 무엇인지 볼 수 있다. 아래 프로그램은 표준 입력에서 바이트를 하나씩 읽어 그 값을 그대로 출력한다. throws IOException은 읽기가 실패할 수 있음을 선언하는 부분인데, 예외는 중급 1편에서 다루므로 지금은 read()를 쓰기 위한 형식으로만 보아도 된다.

    import java.io.IOException;

public class ReadBytes {
    public static void main(String[] args) throws IOException {
        int b;
        while ((b = System.in.read()) != -1) {
            System.out.println(b);
        }
        System.out.println("끝: " + b);
    }
}

    printf '25\n' | java ReadBytes로 실행하면 결과는 다음과 같다.

    50
53
10
끝: -1

    25라는 수는 어디에도 없다. 도착한 것은 문자 '2'의 코드 값 50, 문자 '5'의 코드 값 53, 줄바꿈 문자의 코드 값 10이다. 2회차의 char에서 본 것처럼 문자는 수로 부호화되어 저장되고 전달된다. 마지막 줄의 -1은 입력이 끝났다는 표시다. 한글을 넣으면 한 글자가 여러 바이트로 온다. 터미널이 UTF-8을 쓰는 환경에서 printf '가\n' | java ReadBytes는 234, 176, 128, 10을 출력한다. 가 한 글자가 UTF-8로 세 바이트이기 때문이다.

    이 바이트들에서 정수 25를 얻으려면 프로그램이 직접 해야 할 일이 세 가지다. 바이트 묶음을 문자로 되돌리고(디코딩), 어디부터 어디까지가 하나의 값인지 경계를 정하고, 숫자 문자들을 실제 수로 계산해야 한다. 마지막 단계는 ('2' - '0') * 10 + ('5' - '0'), 곧 2 * 10 + 5를 계산하는 일이다. Scanner는 이 세 가지를 맡는다.

    키 입력이 줄 단위 바이트, 문자, 토큰, int 값으로 형태가 바뀌어 가는 여섯 단계를 왼쪽에서 오른쪽으로 보여 준다. 왼쪽에서 오른쪽으로 흐르는 가로형 파이프라인 다이어그램. 여섯 개의 상자가 화살표로 이어진다. 첫째 상자 라벨 "터미널"에는 키보드 아이콘과 함께 글자 2, 5, 엔터 기호가 떠 있다. 둘째 상자 라벨 "System.in"에는 숫자 세 개 50, 53, 10이 작은 네모 칸에 들어 있고 아래에 "바이트"라고 적는다. 셋째 상자 라벨 "문자 디코딩"에는 글자 칸 세 개 '2', '5', '\n'이 있고 아래에 "문자"라고 적는다. 넷째 상자 라벨 "Scanner 버퍼"에는 같은 세 칸 위에 아래쪽을 가리키는 작은 삼각형 표식과 "position" 라벨이 있다. 다섯째 상자 라벨 "토큰"에는 따옴표로 둘러싼 문자열 "25"가 있다. 여섯째 상자 라벨 "int 값"에는 숫자 25가 크게 있다. 상자 사이 화살표는 굵은 회색. 흰 배경, 파란색 강조, 또렷한 고딕체 한국어 라벨. 입력은 바이트로 도착해 문자, 토큰, 값의 순서로 모습을 바꾼다. Scanner는 셋째 단계부터 맡는다.

    Scanner 기본 사용

    먼저 쓰는 모습을 본다. 이름, 나이, 키를 차례로 입력받아 한 줄로 출력하는 프로그램이다.

    import java.util.Scanner;

public class ScannerBasic {
    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);

        System.out.print("이름: ");
        String name = scanner.nextLine();

        System.out.print("나이: ");
        int age = scanner.nextInt();

        System.out.print("키(cm): ");
        double height = scanner.nextDouble();

        System.out.println(name + ", " + age + "세, " + height + "cm");
    }
}

    김자바, 25, 172.5를 한 줄씩 입력하면 터미널에는 다음과 같이 보인다. 프롬프트 뒤의 글자는 사용자가 친 것을 터미널이 보여 준 것이다.

    이름: 김자바
나이: 25
키(cm): 172.5
김자바, 25세, 172.5cm

    새로 나온 문법은 두 줄이다. import java.util.Scanner;는 java.util이라는 패키지에 들어 있는 Scanner 클래스를 이 파일에서 짧은 이름으로 쓰겠다는 선언이다. String이나 System은 java.lang 패키지에 있어서 선언 없이 쓸 수 있었다. new Scanner(System.in)은 표준 입력을 읽는 Scanner 객체를 하나 만든다. new로 객체를 만들고 변수로 가리키는 일은 다음 회차의 배열과 기본편의 클래스에서 자세히 다룬다. 지금은 "표준 입력에 연결된 읽기 도구를 하나 만들어 scanner라는 이름으로 쓴다"고 이해하면 충분하다.

    프롬프트에는 println이 아닌 print를 썼다. 줄을 바꾸지 않아야 사용자의 입력이 프롬프트와 같은 줄에 보인다. Scanner의 읽기 메서드는 읽는 단위에 따라 두 부류로 나뉜다. 이 구분이 뒤의 모든 설명의 바탕이다.

    메서드읽는 단위돌려주는 값위치를 옮기는 방식
    next()토큰String앞쪽 구분자를 건너뛰고 토큰을 읽는다. 뒤쪽 구분자는 남긴다.
    nextInt(), nextLong()토큰int, longnext()와 같다. 토큰을 정수로 해석한다.
    nextDouble()토큰doublenext()와 같다. 토큰을 실수로 해석한다.
    nextLine()줄String현재 위치부터 줄 끝까지 읽는다. 줄 구분자는 지나가되 결과에는 넣지 않는다.
    hasNext(), hasNextInt(), hasNextLine()토큰 또는 줄boolean읽을 것이 있는지 검사만 한다. 위치를 옮기지 않는다.

    Scanner 안에서 일어나는 일 — 버퍼, 위치, 구분자

    Scanner의 동작은 세 가지 상태로 설명할 수 있다. 입력원에서 가져온 문자를 담아 두는 버퍼(buffer), 버퍼에서 어디까지 처리했는지를 가리키는 위치(position), 토큰의 경계를 정하는 구분자 패턴(delimiter pattern)이다. Scanner의 Javadoc 첫 문장이 이 구조를 요약한다. Scanner는 구분자 패턴을 써서 입력을 토큰으로 나누고, 그 패턴은 기본적으로 공백(whitespace)에 맞는다.

    기본 구분자가 말하는 공백은 스페이스 하나가 아니다. Javadoc은 Character.isWhitespace()가 인정하는 문자라고 정의하는데, 여기에는 스페이스, 탭(\t), 줄바꿈(\n), 캐리지 리턴(\r) 등이 들어 있다. OpenJDK 21의 구현에서 기본 패턴은 정규식 \p{javaWhitespace}+다. 끝의 +는 "하나 이상 연속"을 뜻하므로 스페이스 세 개와 줄바꿈 두 개가 이어져 있어도 통째로 구분자 하나다. 따라서 토큰 메서드에게 줄바꿈은 스페이스와 똑같은 구분자다.

    Javadoc은 토큰 메서드의 동작을 두 문장으로 규정한다. next()와 hasNext(), 그리고 nextInt() 같은 짝 메서드들은 먼저 구분자 패턴에 맞는 입력을 건너뛰고 그다음에 다음 토큰을 돌려주려 한다. 그리고 완전한 토큰(complete token)이란 앞과 뒤가 구분자 패턴에 맞는 입력으로 둘러싸인 것이다. OpenJDK 21의 소스에서 이 과정을 따라가 보면 다음 순서로 진행된다.

    1. 현재 위치에서 시작해 구분자에 맞는 문자들을 건너뛴다.
    2. 버퍼의 끝에 닿았으면 입력원에서 문자를 더 읽어 온다. 입력원에 아직 온 것이 없으면 여기서 블록된다.
    3. 다음 구분자가 시작되는 곳을 찾는다. 현재 위치부터 그 앞까지가 토큰이다.
    4. 토큰을 돌려주고, 위치를 토큰의 끝(뒤따르는 구분자의 시작)에 둔다. 뒤따르는 구분자는 지나가지 않는다.
    5. 다음 구분자를 찾지 못했는데 입력이 끝난 것도 아니라면, 토큰이 여기서 끝나는지 더 이어지는지 알 수 없으므로 2번으로 돌아가 더 읽는다. 입력이 끝났다면 남은 문자 전체를 마지막 토큰으로 본다.

    4번이 핵심이다. Scanner는 토큰이 끝났다는 것을 알려면 뒤의 구분자를 보아야 하지만, 본 것과 소비한 것은 다르다. 위치는 토큰 바로 뒤에서 멈춘다. 사용자가 스페이스 두 칸, 42, 스페이스 한 칸, 7을 치고 Enter를 눌렀다고 하자. 스페이스를 ␣로, 줄바꿈을 \n으로 적으면 버퍼와 위치는 이렇게 변한다.

    인덱스:   0   1   2   3   4   5   6
버퍼:    ␣   ␣   4   2   ␣   7   \n
         ▲
         position = 0                      (한 줄이 통째로 도착한 직후)

nextInt() 호출
  1) 구분자 건너뛰기: 인덱스 0, 1  →  position = 2
  2) 다음 구분자는 인덱스 4에서 시작  →  토큰은 [2, 4) = "42"
  3) "42"를 int로 변환해 42 반환       →  position = 4

nextInt() 호출
  1) 구분자 건너뛰기: 인덱스 4      →  position = 5
  2) 다음 구분자는 인덱스 6에서 시작  →  토큰은 [5, 6) = "7"
  3) 7 반환                          →  position = 6

버퍼:    ␣   ␣   4   2   ␣   7   \n
                                 ▲
                                 position = 6    (줄바꿈은 아직 소비되지 않았다)

    두 번째 nextInt()는 사용자를 기다리지 않고 곧바로 돌아온다. 완전한 토큰 7이 이미 버퍼에 있기 때문이다. 블로킹은 "읽기 메서드를 호출하면 일어나는 일"이 아니라 "버퍼에 완전한 토큰이 없을 때 일어나는 일"이다. Javadoc도 스캔 연산이 입력을 기다리며 블록될 수 있다고만 말한다. 호출할 때마다 사용자에게 한 번씩 묻는다고 가정하고 짠 프로그램은 사용자가 한 줄에 값을 여러 개 치는 순간 예상과 다르게 움직인다.

    OpenJDK 21 구현에서 이 버퍼의 처음 크기는 문자 1,024개다. 버퍼가 가득 차면 이미 처리한 앞부분을 밀어내 자리를 만들고, 밀어낼 것이 없으면 버퍼를 두 배로 늘린다. 이 수치는 구현의 세부 사항이고 Javadoc이 보장하는 값은 아니다. 다만 Scanner가 입력원에서 꼭 필요한 만큼만 가져오는 것이 아니라 가져올 수 있는 만큼 미리 가져와 자기 버퍼에 쌓아 둔다는 사실은 뒤에서 함정 하나를 설명할 때 다시 쓰인다.

    토큰이 값이 되는 단계

    nextInt()는 잘라 낸 토큰이 정수 형식에 맞는지 정규식으로 검사한 다음 Integer.parseInt에 넘긴다. 형식 검사는 Scanner의 로케일(locale)을 따른다. Javadoc에 따르면 Scanner는 표준 형식의 수뿐 아니라 로케일에 맞춘 형식의 수도 읽으며, 처음 로케일은 Locale.getDefault(Locale.Category.FORMAT)의 값이다. 그래서 한국어 로케일에서 1,000을 입력하면 nextInt()는 자릿수 구분 쉼표를 떼고 1000을 돌려준다. 독일어 로케일에서는 소수점이 쉼표라서 nextDouble()이 1,5를 1.5로 읽는다.

    반대로 소스 코드에서는 쓸 수 있는 1_000을 입력하면 nextInt()는 실패한다. 밑줄을 넣은 수는 자바 컴파일러가 소스 코드의 리터럴을 읽을 때의 문법이고, 실행 중에 들어온 문자열을 해석하는 규칙은 Scanner와 Integer.parseInt가 따로 정한다. 소스 코드의 25와 입력으로 들어온 "25"는 같은 글자처럼 보여도 전혀 다른 경로로 수가 된다. 앞의 것은 컴파일 시점에 javac가, 뒤의 것은 실행 시점에 라이브러리 코드가 변환한다.

    일상에서 가져온 비유줄 단위로 배달되는 두루마리와 책갈피

    터미널은 한 줄을 다 써야 두루마리를 건네주는 배달원이고, Scanner는 받은 두루마리를 이어 붙여 놓고 책갈피(position)를 꽂아 가며 읽는 사람이다. nextInt()는 책갈피 뒤의 빈칸을 넘기고 낱말 하나를 읽은 뒤 낱말 바로 뒤에 책갈피를 꽂는다. nextLine()은 책갈피부터 그 줄의 끝까지를 읽고 다음 줄 맨 앞에 책갈피를 꽂는다. 비유가 맞지 않는 지점도 있다. 사람은 앞으로 되돌아가 다시 읽을 수 있지만 Scanner의 책갈피는 뒤로 가지 않는다. 한 번 지나간 입력은 다시 읽을 수 없다.

    nextInt() 뒤의 nextLine()이 아무것도 읽지 않는 이유

    이제 문제의 코드를 볼 차례다. 나이를 먼저 묻고 이름을 그다음에 묻도록 순서만 바꿨다.

    import java.util.Scanner;

public class AgeThenName {
    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);

        System.out.print("나이: ");
        int age = scanner.nextInt();

        System.out.print("이름: ");
        String name = scanner.nextLine();

        System.out.println("age=" + age + ", name=[" + name + "]");
    }
}

    25를 치고 Enter를 누르면 이름을 칠 틈도 없이 프로그램이 끝난다.

    나이: 25
이름: age=25, name=[]

    대괄호 사이가 비어 있다. nextLine()은 호출되었고, 정상적으로 값을 돌려주었으며, 그 값이 길이 0인 빈 문자열이었다. 버퍼와 위치를 그려 보면 이유가 보인다.

    사용자가 친 것:  2  5  Enter

인덱스:   0   1   2
버퍼:    2   5   \n
         ▲ position = 0

nextInt()
  구분자 건너뛰기: 없음
  다음 구분자는 인덱스 2에서 시작  →  토큰 [0, 2) = "25"  →  25 반환
버퍼:    2   5   \n
                 ▲ position = 2          (줄바꿈이 위치 뒤에 그대로 있다)

nextLine()
  position = 2부터 줄 구분자 앞까지  =  [2, 2)  =  ""   (글자가 하나도 없다)
  줄 구분자 \n을 지나간다
버퍼:    2   5   \n
                     ▲ position = 3      (다음 줄의 맨 앞)

    nextLine()의 Javadoc은 이 메서드가 스캐너를 현재 줄 너머로 전진시키고 건너뛴 입력을 돌려주며, 돌려주는 것은 끝의 줄 구분자를 뺀 현재 줄의 나머지(the rest of the current line)라고 정의한다. nextInt()가 끝난 뒤 스캐너는 여전히 25가 있던 그 줄 위에 있다. 그 줄의 나머지는 줄바꿈 하나뿐이고, 줄 구분자를 빼면 빈 문자열이다. 사용자 눈에는 Enter를 누른 순간 다음 줄로 넘어간 것처럼 보이지만, Scanner의 위치는 아직 줄바꿈 문자 앞에 있다.

    원인을 한 문장으로 줄이면 이렇다. 토큰 메서드는 토큰 뒤의 구분자를 남겨 두고, 줄 메서드는 앞쪽 구분자를 건너뛰지 않는다. 두 규칙은 각자 합리적이다. 토큰 메서드가 뒤의 구분자까지 삼키면 줄 경계 정보가 사라지고, 줄 메서드가 앞의 공백을 건너뛰면 빈 줄이나 들여쓰기를 있는 그대로 읽을 수 없다. 문제는 두 부류를 섞어 쓸 때 생긴다. 이것은 Scanner의 결함이 아니라 문서에 적힌 대로의 동작이다.

    같은 규칙으로 다른 경우도 예측할 수 있다. nextInt()를 두 번 연달아 부르거나 nextInt() 다음에 next()를 부르면 아무 문제가 없다. 뒤의 토큰 메서드가 남아 있던 줄바꿈을 구분자로 보고 건너뛰기 때문이다. 또 나이를 묻는 프롬프트에 25 Kim을 한 줄로 입력하면 nextLine()은 빈 문자열이 아니라 " Kim"을 돌려준다. 25 바로 뒤의 스페이스부터 줄 끝까지가 "현재 줄의 나머지"이기 때문이며, 맨 앞의 스페이스도 결과에 들어 있다.

    이 현상을 "키보드 버퍼에 엔터가 남아 있다"고 설명하는 글이 많다. 정확히 말하면 남아 있는 곳은 키보드나 운영체제가 아니라 Scanner 객체 안의 버퍼다. 25와 줄바꿈은 이미 한 덩어리로 Scanner에 도착했고, Scanner가 그중 25까지만 소비한 것이다. 뒤에서 Scanner를 두 개 만드는 실험이 이 사실을 확인해 준다.
    같은 버퍼를 세 번 그려 position이 0, 2, 3으로 이동하는 것과 nextLine이 읽는 구간이 비어 있음을 보여 준다. 세로로 세 단이 쌓인 다이어그램. 각 단에는 가로로 나란한 네모 칸 세 개가 있고 칸 안에는 차례로 글자 2, 글자 5, 그리고 굽은 화살표 모양의 줄바꿈 기호가 들어 있다. 칸 위에는 인덱스 0, 1, 2가 작게 적혀 있다. 첫째 단 왼쪽 라벨은 "입력 도착 직후"이고 첫 칸 아래에 위를 가리키는 삼각형과 "position 0"이 있다. 둘째 단 왼쪽 라벨은 "nextInt() 후"이고 2와 5 두 칸이 파란색으로 칠해져 "토큰 25"라는 중괄호 표시가 붙어 있으며, 삼각형은 줄바꿈 칸 아래에 있고 "position 2"라고 적혀 있다. 셋째 단 왼쪽 라벨은 "nextLine() 후"이고 줄바꿈 칸이 주황색으로 칠해져 있으며 그 옆에 말풍선으로 "돌려준 문자열: 빈 문자열"이라고 적혀 있고, 삼각형은 세 칸 오른쪽 바깥에 있고 "position 3"이라고 적혀 있다. 흰 배경, 또렷한 고딕체 한국어 라벨, 군더더기 없는 평면 스타일. nextInt()는 줄바꿈 앞에서 멈추고, nextLine()은 그 자리에서 줄 끝까지 읽는다. 사이에 글자가 없으므로 결과는 빈 문자열이다.

    고치는 방법

    원인을 알면 해법은 두 갈래다. 하나는 토큰 메서드 뒤에 남은 줄의 나머지를 명시적으로 버리는 것이다. nextInt() 바로 다음에 결과를 쓰지 않는 nextLine()을 한 번 부르면 위치가 다음 줄의 맨 앞으로 간다. 다른 하나는 처음부터 줄 메서드만 쓰고, 수가 필요하면 읽어 온 문자열을 직접 변환하는 것이다. 아래 코드는 나이에는 첫째 방법을, 키에는 둘째 방법을 썼다.

    import java.util.Scanner;

public class AgeThenNameFixed {
    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);

        System.out.print("나이: ");
        int age = scanner.nextInt();
        scanner.nextLine();              // 현재 줄의 나머지(줄바꿈 포함)를 버린다

        System.out.print("이름: ");
        String name = scanner.nextLine();

        System.out.print("키(cm): ");
        double height = Double.parseDouble(scanner.nextLine());

        System.out.println("age=" + age + ", name=[" + name + "], height=" + height);
    }
}

    25, 김 자바, 172.5를 한 줄씩 입력하면 마지막 줄에 age=25, name=[김 자바], height=172.5가 출력된다. 이름 가운데의 스페이스가 살아 있는 것도 눈여겨볼 만하다. next()로 이름을 읽었다면 스페이스가 구분자이므로 김만 읽혔을 것이다.

    두 방법은 성격이 다르다. 첫째 방법은 숫자 뒤에 사용자가 실수로 더 친 내용까지 조용히 버린다. 둘째 방법은 한 줄 전체가 수여야 하므로 더 엄격하다. 예를 들어 Integer.parseInt는 Scanner와 달리 1,000 같은 자릿수 구분 기호를 받아들이지 않고, Integer.parseInt("25 ")처럼 뒤에 스페이스가 붙은 문자열에도 NumberFormatException을 던진다. 사용자가 한 줄에 답 하나를 적는 대화형 프로그램이라면 사용자가 느끼는 단위(한 줄)와 프로그램이 읽는 단위가 같은 둘째 방법이 흐름을 예측하기 쉽다. 어느 쪽이든 한 프로그램 안에서는 한 가지 방식으로 통일하는 편이 안전하다.

    잘못된 입력과 입력의 끝

    사용자는 정수를 넣으라는 곳에 abc를 넣을 수 있다. nextInt()는 토큰이 정수 형식에 맞지 않으면 InputMismatchException을 던지고, 이 예외를 처리하는 코드가 없으면 프로그램은 스택 트레이스를 표준 오류에 남기고 끝난다. 아래 표는 Java 21, 한국어 로케일에서 각 입력에 nextInt()를 호출한 결과다.

    예외가 났을 때 위치가 어디에 있는지가 중요하다. Javadoc은 스캐너가 InputMismatchException을 던질 때 그 예외를 일으킨 토큰을 지나가지 않으며, 그래서 다른 메서드로 그 토큰을 꺼내거나 건너뛸 수 있다고 규정한다. 곧 실패한 토큰은 버퍼에 그대로 남는다. 다시 nextInt()를 불러 봐야 같은 토큰을 만나 같은 예외가 난다.

    예외를 잡는 문법은 아직 배우지 않았지만, 예외가 나기 전에 미리 물어보는 방법이 있다. hasNextInt()는 다음 토큰을 nextInt()로 읽을 수 있으면 true를 돌려준다. Javadoc의 표현대로 스캐너는 어떤 입력도 지나가지 않는다. 검사만 하고 위치는 그대로다. 이 성질은 편리하면서 함정이기도 하다.

    // 잘못된 코드: 정수가 아닌 토큰이 오면 끝나지 않는다
while (!scanner.hasNextInt()) {
    System.out.println("정수를 입력하세요.");
}
int n = scanner.nextInt();

    abc가 들어오면 hasNextInt()는 false를 돌려주고, 위치가 움직이지 않았으므로 다음 검사에서도 같은 abc를 보고 다시 false를 돌려준다. 사용자에게 새 입력을 요구하지도 않는다. 버퍼에 완전한 토큰이 있으니 블록될 이유가 없기 때문이다. 화면에는 같은 안내문이 끝없이 쏟아진다. 고치려면 반복문 안에서 문제의 토큰을 scanner.next()로 꺼내 버려야 한다. 걸러 낼 대상을 소비하는 것은 프로그램의 책임이다.

    입력의 끝은 또 다른 경우다. 표준 입력이 EOF에 이르렀는데 nextInt()나 next()를 부르면 NoSuchElementException이 난다. nextLine()도 읽을 줄이 없으면 같은 예외를 던진다. 형식이 틀린 것이 아니라 읽을 것이 없다는 뜻이다. 이때 hasNext()와 hasNextLine()은 false를 돌려준다. 정리하면 Scanner가 입력을 달라는 요청에 답하는 방식은 네 가지다. 값을 돌려주거나, 입력이 올 때까지 기다리거나, 형식이 맞지 않는다고 알리거나(InputMismatchException), 더는 없다고 알린다(NoSuchElementException).

    반복해서 입력받기

    입력이 반복문과 만나면 프로그램이 대화형이 된다. 정수를 계속 입력받아 합계와 평균을 내고, 0이 들어오면 끝내는 프로그램을 만든다. 잘못된 입력과 입력의 끝도 함께 다룬다.

    import java.util.Scanner;

public class InputSum {
    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);
        int sum = 0;
        int count = 0;

        while (true) {
            System.out.print("정수(0이면 종료): ");
            if (!scanner.hasNextInt()) {
                if (!scanner.hasNext()) {
                    System.out.println("입력이 끝났다.");
                    break;
                }
                String bad = scanner.next();
                System.out.println("정수가 아니다: " + bad);
                continue;
            }
            int n = scanner.nextInt();
            if (n == 0) {
                break;
            }
            sum += n;
            count++;
        }

        System.out.println("합계=" + sum + ", 개수=" + count);
        if (count > 0) {
            System.out.println("평균=" + (double) sum / count);
        }
    }
}

    반복 횟수를 미리 알 수 없으므로 5회차에서 본 while (true)와 break의 조합을 썼다. 반복문 본문은 세 갈래로 나뉜다. 다음 토큰이 정수가 아니면 먼저 hasNext()로 토큰이 있기는 한지 확인한다. 없으면 입력이 끝난 것이므로 빠져나온다. 있으면 그 토큰을 next()로 꺼내 버리고 continue로 다음 반복으로 간다. 정수라면 nextInt()로 읽고, 0이면 빠져나오며, 아니면 합계와 개수에 반영한다. 평균을 낼 때 (double) sum / count로 쓴 것은 6회차에서 본 대로 int끼리 나누면 소수점 아래가 버려지기 때문이고, count > 0 검사는 한 개도 입력하지 않았을 때 0으로 나누는 일을 막는다.

    사용자가 10 20, abc, 30, 0을 차례로 한 줄씩 입력하면 화면은 이렇게 된다.

정수(0이면 종료): 정수(0이면 종료): abc
정수가 아니다: abc
정수(0이면 종료): 30
정수(0이면 종료): 0

평균=20.0

    둘째 줄에 프롬프트가 두 번 연달아 찍힌 것이 앞에서 본 버퍼 동작의 증거다. 추적해 보자.

    1. 첫 반복. 프롬프트를 출력한다. 버퍼가 비어 있으므로 hasNextInt()가 블록된다. 사용자가 10 20과 Enter를 입력하면 버퍼에 10␣20\n이 들어오고 hasNextInt()는 true를 돌려준다. nextInt()가 10을 읽는다. sum은 10, count는 1.
    2. 둘째 반복. 프롬프트를 출력한다. 버퍼에 완전한 토큰 20이 있으므로 hasNextInt()는 기다리지 않고 true를 돌려준다. sum은 30, count는 2. 사용자는 아무것도 치지 않았는데 반복이 한 번 돌았다.
    3. 셋째 반복. 프롬프트를 출력한다. 버퍼에는 줄바꿈만 남아 있고 그 뒤에 토큰이 없으므로 블록된다. 사용자가 abc를 입력한다. hasNextInt()는 false, hasNext()는 true다. next()가 abc를 꺼내고 안내문을 출력한 뒤 continue.
    4. 넷째 반복. 30을 읽는다. sum은 60, count는 3.
    5. 다섯째 반복. 0을 읽고 break. 합계 60, 개수 3, 평균 60.0 / 3 = 20.0을 출력한다.

    같은 입력을 printf '10 20\nabc\n30\n0\n' | java InputSum처럼 파이프로 넣으면 계산 결과는 같지만 화면 모습은 다르다. 사용자가 친 글자를 보여 주던 터미널의 에코가 없으므로 프롬프트만 줄줄이 이어져 보인다. 프로그램의 출력과 터미널의 에코는 원래 별개의 것이고, 터미널에서는 둘이 한 화면에 섞여 보였을 뿐이다.

    이 장의 핵심

    Scanner는 "한 번 호출에 한 번 묻는" 도구가 아니다. 이미 도착한 문자를 버퍼에 쌓아 두고 위치를 앞으로 옮겨 가며 읽는 도구다. 토큰 메서드는 앞의 구분자를 건너뛰고 토큰 뒤에서 멈추며, nextLine()은 현재 위치부터 줄 끝까지를 읽는다. 버퍼와 위치를 그릴 수 있으면 Scanner의 모든 동작을 예측할 수 있다.

    출력 쪽에서 일어나는 일

    입력의 반대편도 잠깐 본다. System.out은 PrintStream이고, 문자를 바이트로 바꿔 1번 디스크립터에 쓴다. 출력에도 버퍼가 있다. 그렇다면 줄바꿈 없이 print로 출력한 프롬프트가 버퍼에 갇혀 화면에 나오지 않은 채 프로그램이 입력을 기다릴 수도 있지 않을까. 그렇게 되지 않는 이유가 있다. PrintStream의 Javadoc은 자동 플러시(automatic flush)로 만든 PrintStream이 바이트 배열이 쓰이거나 println이 호출되거나 줄바꿈 문자가 쓰인 뒤에 아래 스트림의 flush를 자동으로 부른다고 설명하고, OpenJDK 21의 System 초기화 코드는 System.out과 System.err를 자동 플러시로 만든다. 그래서 프롬프트는 입력을 기다리기 전에 화면에 나타난다.

    문자와 바이트 사이의 변환 규칙인 문자 집합(charset)은 입력과 출력에서 따로 정해진다. System.out의 Javadoc에 따르면 출력의 인코딩은 콘솔이 있으면 Console.charset()과 같고, 없으면 stdout.encoding 시스템 프로퍼티를 따른다. 반면 new Scanner(System.in)은 Javadoc에 적힌 대로 기본 문자 집합(default charset)으로 바이트를 문자로 바꾼다. 기본 문자 집합은 JDK 18에 들어간 JEP 400부터, 따로 설정을 바꾸지 않는 한 운영체제의 로케일과 상관없이 UTF-8이다. 터미널이 UTF-8이 아닌 인코딩으로 바이트를 보내는 환경에서는 이 둘이 어긋나 한글 입력이 다른 글자로 해석된다. System.in의 Javadoc이 이 스트림을 문자로 감쌀 때 Console.charset()을 쓰라고 권하는 이유이고, Scanner에는 문자 집합을 직접 받는 생성자 Scanner(InputStream, Charset)도 있다.

    Scanner를 다룰 때의 함정 둘

    표준 입력에 Scanner를 두 개 만들기

    입력이 필요한 곳마다 new Scanner(System.in)을 새로 만드는 코드를 종종 본다. 아래 프로그램에 1, 2, 3이 한 줄씩 담긴 입력을 파이프로 넣어 보자. 예외를 처리하지 않았으므로 결과는 예외가 나기 전까지만 본다.

    import java.util.Scanner;

public class TwoScanners {
    public static void main(String[] args) {
        Scanner first = new Scanner(System.in);
        System.out.println("first: " + first.nextInt());

        Scanner second = new Scanner(System.in);
        System.out.println("second: " + second.nextInt());
    }
}

    printf '1\n2\n3\n' | java TwoScanners의 결과는 first: 1 한 줄이고, 그다음 second.nextInt()에서 NoSuchElementException이 난다. 입력에는 2와 3이 분명히 있었는데 둘째 Scanner는 읽을 것이 없다고 한다. 첫째 Scanner가 1을 읽으려고 입력원에서 문자를 가져올 때, 그때 도착해 있던 1\n2\n3\n 전부를 자기 버퍼로 가져갔기 때문이다. 2와 3은 사라진 것이 아니라 first의 버퍼 안에 있다. 실제로 그 뒤에 first.nextInt()를 부르면 2가 나온다. 한 번 Scanner의 버퍼로 넘어간 입력은 System.in으로 되돌아가지 않는다.

    이 코드는 터미널에서 값을 한 줄에 하나씩 손으로 칠 때는 문제가 드러나지 않을 수 있다. 터미널이 줄 단위로 넘겨주어 첫째 Scanner가 첫 줄만 가져가기 때문이다. 그러다 사용자가 한 줄에 값 두 개를 치거나 입력을 파일로 돌리는 순간 깨진다. 실행 환경에 따라 결과가 달라지는 코드는 가장 찾기 어려운 종류의 버그다. 규칙은 단순하다. 입력원 하나에 Scanner 하나만 만들고, 필요한 곳에서 그 하나를 함께 쓴다.

    System.in을 읽는 Scanner를 닫기

    Scanner의 Javadoc에 따르면 Scanner를 닫으면 그 입력원이 Closeable을 구현한 경우 입력원도 함께 닫힌다. System.in은 InputStream이고 InputStream은 Closeable이다. 따라서 scanner.close()는 표준 입력 자체를 닫는다. Java 21에서 확인해 보면 그 뒤에 System.in.read()를 부르면 IOException: Stream closed가 나고, 새로 new Scanner(System.in)을 만들어 nextInt()를 불러도 NoSuchElementException이 난다. 닫힌 Scanner 자체에 읽기를 시도하면 IllegalStateException이다.

    파일을 읽는 Scanner는 다 쓰고 나서 닫아 운영체제의 자원을 돌려주어야 한다. 그러나 표준 입력은 프로그램이 연 것이 아니라 시작할 때부터 주어진 것이고, 프로세스가 끝나면 운영체제가 정리한다. 프로그램이 끝날 때까지 표준 입력을 쓸 것이라면 System.in을 감싼 Scanner는 닫지 않는 편이 안전하다. 자원을 여닫는 규칙은 중급 1편의 예외 처리에서 try-with-resources와 함께 다룬다.

    이 지식이 다시 쓰이는 곳

    이번에 본 구조는 뒤의 권에서 이름만 바뀌어 계속 나온다. 첫째는 스트림의 계층이다. 바이트를 내주는 InputStream 위에 문자로 바꾸는 층을 얹고, 그 위에 다시 사용하기 편한 층을 얹는 구성은 자바 I/O 전체의 설계 방식이다. 파일도, 네트워크 소켓도 InputStream과 OutputStream으로 다룬다. 자바 고급 2편에서 이 계층을 직접 쌓아 본다. 그때 "소켓에서 읽은 바이트를 어떤 문자 집합으로 해석할 것인가"라는 질문은 오늘 본 터미널 입력의 디코딩과 같은 질문이다.

    둘째는 블로킹이다. nextInt()를 부른 스레드는 사용자가 Enter를 누를 때까지 아무 일도 하지 못한다. 프로그램에 스레드가 하나뿐이면 프로그램 전체가 멈춘 것과 같다. 네트워크 서버가 클라이언트의 데이터를 기다릴 때도 똑같은 일이 벌어지며, 여러 사용자를 동시에 상대하려면 기다리는 일을 여러 스레드에 나눠 맡겨야 한다. 자바 고급 1편의 스레드와 스프링 MVC의 요청 처리 모델이 여기서 출발한다.

    셋째는 문자열에서 타입 있는 값으로의 변환과 검증이다. 웹 애플리케이션에서 HTTP 요청으로 들어오는 파라미터도 처음에는 전부 문자열이다. 그것을 int나 날짜로 바꾸고, 형식이 틀리면 거절하고, 범위를 검사하는 일은 오늘 hasNextInt()로 한 일과 본질이 같다. 바깥에서 들어오는 값은 프로그램이 기대한 형식이 아닐 수 있다는 전제가 입력 처리의 출발점이다.
    표준 입출력
    프로세스가 시작할 때 이미 열려 있는 세 통로다. 파일 디스크립터 0, 1, 2에 대응하고 자바에서는 System.in, System.out, System.err로 쓴다. 무엇이 연결되는지는 실행하는 쪽이 정한다.
    줄 단위 전달
    터미널은 줄이 완성되어야 입력을 프로그램에 넘긴다. 넘어오는 데이터에는 줄바꿈 문자가 포함된다.
    블로킹과 EOF
    읽을 것이 아직 오지 않았으면 호출이 돌아오지 않고 기다린다(블로킹). 더 올 것이 없으면 입력의 끝(EOF)이며 read()는 -1을, Scanner는 NoSuchElementException을 낸다.
    Scanner의 세 가지 상태
    미리 읽어 둔 문자를 담는 버퍼, 어디까지 처리했는지를 가리키는 위치, 토큰 경계를 정하는 구분자 패턴(기본은 연속된 공백 문자)이다.
    토큰 메서드
    next(), nextInt(), nextDouble()은 앞쪽 구분자를 건너뛰고 토큰을 읽은 뒤 토큰 바로 뒤에서 멈춘다. 뒤따르는 구분자(줄바꿈 포함)는 소비하지 않는다.
    줄 메서드
    nextLine()은 구분자를 건너뛰지 않고 현재 위치부터 줄 끝까지를 돌려주며 줄 구분자를 지나간다. nextInt() 직후에 부르면 남은 줄바꿈 앞까지, 곧 빈 문자열을 돌려준다.
    소비되지 않는 실패 토큰
    InputMismatchException을 일으킨 토큰은 버퍼에 남는다. hasNextInt()도 위치를 옮기지 않으므로 잘못된 토큰은 next()로 직접 꺼내 버려야 한다.
    Scanner 하나, 닫지 않기
    Scanner는 입력을 자기 버퍼로 미리 가져가므로 입력원 하나에 하나만 만든다. System.in을 감싼 Scanner를 닫으면 표준 입력도 닫힌다.

    Scanner는 학습용 콘솔 프로그램과 알고리즘 문제 풀이에서 주로 쓰이고, 실무 서버 코드에서 표준 입력을 Scanner로 읽는 일은 드물다. 그래도 이 회차의 내용이 실무와 멀지 않은 이유는, 여기서 본 것이 Scanner의 사용법이 아니라 스트림에서 메시지 경계를 찾는 문제이기 때문이다. 바이트는 경계 없이 흘러오고, 어디까지가 한 단위인지는 읽는 쪽이 구분자나 길이로 정해야 한다. 줄바꿈으로 줄을 나누는 것, HTTP가 헤더의 끝을 빈 줄로 표시하는 것, 로그 수집기가 줄 단위로 레코드를 끊는 것이 모두 같은 문제의 풀이다. "토큰 뒤의 구분자를 소비했는가"를 따지는 습관은 네트워크 프로토콜을 직접 다룰 때 그대로 필요하다.

    표준 입출력을 프로그램 바깥에서 갈아 끼울 수 있다는 사실은 운영에서 자주 쓰인다. 배치 프로그램의 입력을 파일로 넣고 결과를 다른 프로그램으로 넘기는 일, 테스트에서 사람의 키 입력을 준비된 파일로 대신하는 일, 표준 출력에 쓴 로그를 실행 환경이 수집하는 일이 그렇다. 이때 판단 기준이 되는 것이 표준 출력과 표준 오류의 구분이다. 다른 프로그램이 읽어 갈 결과는 표준 출력에, 사람이 봐야 할 진단 메시지는 표준 오류에 쓴다는 관례를 지키면 출력을 파이프로 넘겨도 오류 메시지가 데이터에 섞이지 않는다.

    입력 검증의 판단도 상황에 따라 달라진다. 사람이 대화형으로 쓰는 프로그램이라면 잘못된 값에 다시 물어보는 것이 맞다. 그러나 입력이 파일이나 파이프라면 다시 물어볼 상대가 없으므로, 잘못된 값을 만났을 때 건너뛸지 전체를 실패시킬지를 정해야 하고, 입력의 끝을 정상 종료로 다뤄야 한다. 같은 프로그램이 두 환경에서 모두 쓰인다면 이번 회차의 InputSum처럼 잘못된 토큰과 입력의 끝을 따로 처리해야 한다. 어느 경우든 바깥에서 온 값은 형식과 범위를 확인하기 전에는 믿지 않는다는 원칙은 같다.

    5번. 한 가지 답은 다음과 같다. 본문의 InputSum과 같은 뼈대에 범위 검사를 더했다. 정수가 아닌 토큰은 next()로 꺼내 버리고, 토큰이 아예 없으면(hasNext()가 false) 입력이 끝난 것이므로 return으로 main을 끝낸다. 범위를 벗어난 정수는 이미 nextInt()로 소비했으므로 따로 버릴 것이 없고 반복만 계속하면 된다.

    import java.util.Scanner;

public class Gugudan {
    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);
        int dan;
        while (true) {
            System.out.print("단(2~9): ");
            if (!scanner.hasNextInt()) {
                if (!scanner.hasNext()) {
                    return;
                }
                scanner.next();
                continue;
            }
            dan = scanner.nextInt();
            if (dan >= 2 && dan <= 9) {
                break;
            }
        }
        for (int i = 1; i <= 9; i++) {
            System.out.println(dan + " x " + i + " = " + dan * i);
        }
    }
}

    dan을 반복문 밖에 선언한 것은 6회차의 스코프 규칙 때문이다. 반복문 블록 안에서 선언하면 블록이 끝난 뒤의 for문에서 쓸 수 없다. 컴파일러는 while (true)를 빠져나오는 길이 dan에 값을 넣은 뒤의 break뿐임을 알기 때문에, 초기화하지 않고 선언했어도 for문에서 dan을 읽는 것을 허용한다.

    표준 입력(standard input, stdin)
    프로세스가 시작할 때 주어지는 입력 통로. 파일 디스크립터 0번이며 자바에서는 System.in이다.
    파일 디스크립터(file descriptor)
    운영체제가 프로세스에게 열린 파일·장치·파이프를 구분해 주는 작은 정수. 0, 1, 2는 표준 입력, 표준 출력, 표준 오류에 쓰인다.
    리다이렉션(redirection)과 파이프(pipe)
    셸이 프로세스의 표준 입출력을 파일이나 다른 프로세스에 연결하는 기능. 프로그램 코드는 바뀌지 않는다.
    블로킹(blocking)
    결과가 준비될 때까지 호출이 돌아오지 않고 호출한 스레드가 멈춰 기다리는 것.
    EOF(end of file)
    입력원에서 더 읽을 것이 없는 상태. InputStream.read()는 -1로 알린다.
    토큰(token)
    구분자로 둘러싸인 입력의 한 조각. Scanner의 next() 계열 메서드가 읽는 단위다.
    구분자(delimiter)
    토큰의 경계가 되는 패턴. Scanner의 기본 구분자는 스페이스, 탭, 줄바꿈 등 공백 문자가 하나 이상 이어진 것이다.
    버퍼(buffer)
    입력원에서 미리 읽어 온 데이터를 잠시 담아 두는 메모리. Scanner는 자신의 문자 버퍼와 그 안의 위치를 가지고 있다.
    문자 집합(charset)
    문자와 바이트 열 사이의 변환 규칙. 예: UTF-8. 바이트를 다른 문자 집합으로 해석하면 글자가 깨진다.
    로케일(locale)
    언어와 지역에 따른 형식 규칙의 묶음. Scanner가 수를 읽을 때 자릿수 구분 기호와 소수점 기호를 정한다.
