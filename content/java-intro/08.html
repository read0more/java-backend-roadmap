    변수 이름은 계산할 수 없다 — 배열이 필요한 이유

    학생 다섯 명의 점수를 다루는 프로그램을 지금까지 배운 것만으로 쓰면 변수 다섯 개가 필요하다.

    int student1 = 90;
int student2 = 80;
int student3 = 70;
int student4 = 60;
int student5 = 50;

System.out.println("학생1 점수: " + student1);
System.out.println("학생2 점수: " + student2);
// ... 같은 줄이 세 번 더 이어진다

    학생이 백 명이 되면 선언이 백 줄, 출력이 백 줄이다. 5회차에서 배운 반복문으로 줄이고 싶지만 방법이 없다. for문 안에서 i가 1일 때는 student1을, 2일 때는 student2를 가리키게 할 수 없기 때문이다. 왜 안 되는지는 컴파일 결과를 보면 분명해진다. 위 선언의 앞 세 줄은 다음 바이트코드가 된다.

     0: bipush        90
 2: istore_1
 3: bipush        80
 5: istore_2
 6: bipush        70
 8: istore_3

    명령어 어디에도 student1, student2라는 이름은 없고 지역 변수 1번, 2번, 3번이라는 고정된 번호만 남았다. 그리고 그 번호는 istore_1, istore_2처럼 명령어 자체에 박혀 있다. 실행 중에 계산한 값으로 "몇 번 변수를 쓸지" 고르는 명령어는 없다. 변수 이름 끝에 붙인 숫자는 사람 눈에만 번호로 보일 뿐, 프로그램 입장에서는 서로 아무 관계가 없는 변수 다섯 개다.

    필요한 것은 두 가지다. 같은 타입의 값 여러 개를 하나로 묶어 다루는 수단, 그리고 그중 몇 번째인지를 실행 중에 계산한 값으로 고르는 수단이다. 배열(array)이 정확히 이 두 가지를 준다. 배열은 같은 타입의 변수를 정해진 개수만큼 나란히 모아 둔 것이고, 각 변수는 이름 대신 인덱스(index)라는 정수로 고른다. 인덱스는 값이므로 변수에 담을 수 있고 반복문으로 바꿔 갈 수 있다.

    선언과 생성 — 배열 변수와 배열 객체는 다른 것이다

    배열을 쓰려면 두 가지를 해야 한다. 배열을 가리킬 변수를 선언하고, 배열 자체를 생성한다.

    int[] scores;           // 1. 배열 변수 선언
scores = new int[5];    // 2. 배열 생성, 그리고 그 참조를 변수에 대입

    첫 줄의 int[]는 "int의 배열"이라는 타입이다. 이 줄이 만드는 것은 변수 하나뿐이다. 자바 언어 명세(JLS) 10.2절은 이 점을 직접 적어 두었다. 배열 타입의 변수를 선언하는 것은 배열 객체를 만들지 않고 배열 요소를 위한 공간도 할당하지 않으며, 배열에 대한 참조를 담을 수 있는 변수 자체만 만든다는 것이다. 그래서 첫 줄만 쓰고 scores[0] = 90;을 쓰면, 값을 넣지 않은 다른 지역 변수를 읽을 때와 마찬가지로 초기화되지 않은 변수라는 컴파일 오류가 난다. 요소를 담을 곳이 아직 어디에도 없다.

    둘째 줄의 new int[5]가 실제 배열을 만든다. JLS 10장의 첫 문장에 따르면 자바에서 배열은 객체(object)이고 동적으로, 곧 실행 중에 생성된다. 객체는 힙(heap)이라는 메모리 영역에 만들어진다. JVM 명세(JVMS) 2.5.3절은 힙을 모든 클래스 인스턴스와 배열의 메모리가 할당되는 런타임 데이터 영역이라고 정의한다. new int[5]라는 식은 힙에 int 다섯 개짜리 배열 객체를 만들고, 그 객체를 가리키는 값인 참조(reference)를 결과로 낸다. 대입 연산자는 그 참조를 scores에 넣는다.

    따라서 이 두 줄이 끝나면 메모리에는 서로 다른 곳에 놓인 두 가지가 있다. 메서드의 스택 프레임 안에 있는 지역 변수 scores, 그리고 힙에 있는 배열 객체다. 변수에는 배열이 들어 있지 않다. 배열이 어디 있는지 알려 주는 참조값이 들어 있다. 아래 그림에서 x001은 참조값을 눈에 보이게 하려고 붙인 설명용 표기다.

      main의 스택 프레임                          힙(heap)
 ┌───────────────────────┐            ┌───────────────────────────────────────┐
 │ scores │   x001   ────┼──────────▶ │ x001   int[]   길이 5                  │
 └───────────────────────┘            │  [0]    [1]    [2]    [3]    [4]      │
   배열 변수: 참조값 하나를 담는다      │   0      0      0      0      0       │
                                      └───────────────────────────────────────┘
                                        배열 객체: 요소 다섯 개를 담는다
    배열 변수는 스택에 있고 참조값만 담으며, 요소 다섯 개는 힙의 배열 객체에 있다는 구분을 보여 준다. 좌우로 나뉜 메모리 구조 그림. 왼쪽 영역 제목은 "스택", 오른쪽 영역 제목은 "힙". 왼쪽에는 "main 프레임"이라고 적힌 세로 상자가 있고 그 안에 작은 칸 하나가 있다. 칸의 왼쪽 라벨은 "scores", 칸 안의 값은 "x001". 오른쪽에는 가로로 긴 상자가 있고 위쪽 머리 부분에 "x001 int[] 길이 5"라고 적혀 있다. 그 아래에 같은 크기의 네모 칸 다섯 개가 붙어서 나란히 있고 칸 위에는 인덱스 "[0]", "[1]", "[2]", "[3]", "[4]", 칸 안에는 모두 숫자 0이 들어 있다. 왼쪽 scores 칸에서 오른쪽 배열 상자의 머리 부분으로 굵은 화살표가 하나 이어지고 화살표 위에 "참조"라고 적는다. 왼쪽 아래에 작은 글씨로 "배열 변수", 오른쪽 아래에 작은 글씨로 "배열 객체"라고 적는다. 흰 배경, 스택은 연한 파랑, 힙은 연한 주황, 또렷한 고딕체 한국어 라벨. 변수 scores에 들어 있는 것은 배열이 아니라 배열을 가리키는 참조값이다.

    선언과 생성은 한 줄로 합쳐 쓸 수 있고 보통 그렇게 쓴다. 문법상 대괄호를 변수 이름 뒤에 붙인 int scores[]도 허용되지만, 타입이 "int의 배열"이라는 것이 한눈에 보이는 int[] scores 쪽이 읽기 쉽다.

    int[] scores = new int[5];

    타입에 길이가 없다는 점도 눈여겨보자. scores의 타입은 int[]이지 "길이 5인 int 배열"이 아니다. JLS 10.1절의 표현으로 배열의 길이는 타입의 일부가 아니다. 그래서 같은 변수가 나중에 길이 3인 배열이나 길이 100인 배열을 가리킬 수도 있다. 길이는 변수의 성질이 아니라 변수가 가리키는 객체의 성질이다.

JLS 4.12.5절은 변수의 종류에 따라 규칙을 다르게 둔다. 배열 요소는 생성될 때 기본값(default value)으로 초기화되고, 지역 변수는 사용하기 전에 프로그램이 명시적으로 값을 주어야 한다. 컴파일러는 지역 변수 하나하나에 대해 값이 들어갔는지를 코드 흐름으로 따질 수 있지만, 실행 중에 길이가 정해지는 배열의 요소 각각에 대해서는 그럴 수 없다. 그래서 언어가 "쓰레기 값이 보이는 일은 없다"는 것을 생성 시점에 보장한다.

    바이트코드에서 이 생성식은 명령어 둘과 대입 하나다. int[] scores = new int[5];는 다음으로 컴파일된다.

     0: iconst_5          // 길이 5를 피연산자 스택에 올린다
 1: newarray  int     // 스택에서 길이를 꺼내 int 배열을 만들고 참조를 올린다
 3: astore_1          // 스택의 참조를 지역 변수 1번(scores)에 저장한다

    JVMS는 newarray가 피연산자 스택에서 int 타입의 길이를 꺼내고, 그 길이의 새 배열을 가비지 컬렉션되는 힙에서 할당하며, 각 요소를 요소 타입의 기본 초기값으로 초기화하고, 새 배열 객체의 참조를 스택에 올린다고 규정한다. JLS가 언어 수준에서 정한 순서가 명령어 하나의 정의에 그대로 들어 있다. 저장 명령어가 istore가 아니라 astore인 점도 볼 만하다. JVMS 2.11.1절에 따르면 명령어 이름의 글자가 다루는 타입을 나타내는데 i는 int, a는 참조(reference)다. 변수 scores에 들어가는 것이 int가 아니라 참조라는 사실이 명령어 이름에 드러난다.

    참조값 — 변수에 실제로 들어 있는 것

    배열 변수를 그대로 출력해 보면 변수에 요소들이 들어 있지 않다는 것을 확인할 수 있다.

    int[] scores = new int[5];
System.out.println(scores);
    [I@2a139a55

    요소 다섯 개가 아니라 낯선 문자열이 나온다. 이 문자열의 형식은 Object.toString()의 Javadoc에 정의되어 있다. 객체의 클래스 이름, @ 문자, 객체의 해시 코드를 부호 없는 16진수로 쓴 것을 이어 붙인다. [I가 클래스 이름이다. Class.getName()의 Javadoc에 따르면 배열 클래스의 이름은 중첩 깊이만큼의 [ 뒤에 요소 타입의 부호를 붙여 만들고, int의 부호는 I다. 같은 규칙으로 double[]은 [D, int[][]는 [[I, String[]은 [Ljava.lang.String;이다.

    @ 뒤의 16진수를 메모리 주소라고 설명하는 글이 많지만, 문서가 말하는 것은 해시 코드라는 것뿐이다. 주소라는 보장은 어디에도 없다. 참조값이 내부적으로 어떤 비트로 표현되는지는 자바 프로그램에서 볼 수 없다. JLS 4.3.1절은 참조값을 객체를 가리키는 포인터라고만 정의한다. 프로그램이 참조로 하는 일은 대입하고, ==와 !=로 같은 객체를 가리키는지 비교하고, 참조를 따라가 객체에 접근하는 것이다. C 언어의 포인터처럼 참조에 수를 더해 옆 메모리로 옮겨 가는 연산은 자바에 없다. 요소 내용을 보고 싶으면 java.util.Arrays.toString(scores)를 쓴다. 이 메서드는 [0, 0, 0, 0, 0] 같은 문자열을 만들어 준다.

    참조 타입 변수에는 특별한 값 null을 넣을 수 있다. 아무 객체도 가리키지 않는다는 뜻이다. null이 든 변수로 요소에 접근하거나 길이를 물으면 실행 중에 NullPointerException이 난다. 따라갈 객체가 없기 때문이다.

    배열 사용 — 인덱스로 읽고 쓰기

    요소에 접근할 때는 변수 이름 뒤 대괄호 안에 인덱스를 쓴다. 대입문의 왼쪽에 오면 저장이고 그 밖의 자리에서는 읽기다. 요소의 개수는 scores.length로 얻는다.

    public class ArrayBasic {
    public static void main(String[] args) {
        int[] scores;
        scores = new int[5];
        scores[0] = 90;
        scores[1] = 80;
        int first = scores[0];
        int len = scores.length;
        System.out.println(first + " " + len);
    }
}

    출력은 90 5다. scores[0] = 90;이라는 한 줄에서 JVM이 하는 일을 바이트코드로 따라가 보자. 오른쪽에는 각 명령어가 끝난 뒤의 피연산자 스택을 적었다.

     4: aload_1          [참조]            지역 변수 1번(scores)의 참조값을 올린다
 5: iconst_0         [참조, 0]         인덱스 0을 올린다
 6: bipush    90     [참조, 0, 90]     저장할 값 90을 올린다
 8: iastore          []                셋을 꺼내, 참조가 가리키는 배열의 0번 요소에 90을 쓴다

14: aload_1          [참조]
15: iconst_0         [참조, 0]
16: iaload           [90]              둘을 꺼내, 배열의 0번 요소 값을 올린다
17: istore_2         []                first = 90

18: aload_1          [참조]
19: arraylength      [5]               참조를 꺼내, 그 배열의 길이를 올린다
20: istore_3         []                len = 5

    세 가지를 읽어 낼 수 있다. 첫째, 모든 접근은 변수에서 참조를 먼저 꺼내는 일(aload_1)로 시작한다. 요소는 변수 안에 있지 않으므로 참조를 따라 힙으로 가야 한다. 둘째, 인덱스는 명령어에 박힌 번호가 아니라 스택에 올라온 값이다. 여기서는 상수 0이지만 scores[i]라면 iload로 변수 i의 값이 올라온다. 첫 절에서 지역 변수로는 할 수 없었던 "실행 중에 계산한 번호로 고르기"가 여기서 이루어진다. 셋째, 요소 타입마다 명령어가 따로 있다. int 배열은 iaload와 iastore, double 배열은 daload와 dastore, 참조의 배열은 aaload와 aastore다.

    scores.length는 모양은 필드 접근이지만 전용 명령어 arraylength로 컴파일된다. JLS 10.7절은 length를 배열의 public final 필드로 정의한다. final이므로 scores.length = 10;처럼 값을 바꾸는 코드는 컴파일되지 않는다. 메서드가 아니므로 scores.length()처럼 괄호를 붙이는 것도 오류다. 문자열의 길이를 구하는 String의 length()가 메서드인 것과 헷갈리기 쉽다.

    평가 순서도 정해져 있다. JLS 15.10.4절에 따르면 배열 접근식은 먼저 배열 참조 식을 평가하고, 다음에 인덱스 식을 평가하며, 그 뒤에 참조가 null이면 NullPointerException을, 인덱스가 범위를 벗어나면 ArrayIndexOutOfBoundsException을 던진다. 인덱스 식에 부수 효과가 있는 arr[i++] 같은 코드에서 이 순서가 결과를 결정한다.

    인덱스가 0부터인 이유와 경계 검사

    JLS 10.4절은 모든 배열이 0부터 시작하며 길이가 n인 배열은 0부터 n-1까지의 정수로 인덱싱된다고 정한다. 길이 5인 배열의 마지막 요소는 scores[4]이고 scores[5]는 없다. 왜 1이 아니라 0부터인지는 요소가 메모리에 놓이는 방식을 보면 납득이 간다.

    먼저 범위를 분명히 해 둔다. JVMS 2.7절은 JVM이 객체의 내부 구조를 특정하게 강제하지 않는다고 밝힌다. 배열 객체가 메모리에서 어떻게 생겼는지는 JVM 구현이 정할 일이다. 아래는 OpenJDK의 HotSpot JVM, 64비트, JDK 21의 기본 설정에서의 모습이다. HotSpot 소스의 arrayOop.hpp는 배열 객체의 배치를 mark word, 클래스 포인터, 길이의 순서로 적고 있고, 그 뒤에 요소들이 이어진다. 기본 설정에서 mark word는 8바이트, 압축된 클래스 포인터는 4바이트, 길이는 4바이트라서 헤더가 16바이트이고, int 요소는 4바이트씩 빈틈없이 놓인다. 객체 크기는 8바이트의 배수로 맞춰지므로 요소가 다섯 개면 끝에 4바이트가 남는다.

    이 수치는 실제 JVM에서 확인할 수 있다. JDK 21에서 sun.misc.Unsafe의 arrayBaseOffset(int[].class)는 16을, arrayIndexScale(int[].class)는 4를 돌려준다. 첫 요소가 객체 시작에서 16바이트 떨어진 곳에 있고 요소 사이 간격이 4바이트라는 뜻이다. 같은 방법으로 보면 long[]과 double[]은 간격이 8, char[]과 short[]은 2, byte[]와 boolean[]은 1이다.

    요소가 같은 크기로 연속해 놓여 있으므로 i번 요소의 위치는 곱셈 한 번과 덧셈 한 번으로 나온다. 인덱스는 "첫 요소에서 몇 칸 떨어져 있는가"라는 거리이고, 첫 요소는 자기 자신에게서 0칸 떨어져 있다. 0부터 세는 것은 이 계산을 그대로 드러낸 것이다. 이 구조에서 배열의 가장 중요한 성능 특성이 나온다. 요소가 다섯 개든 오백만 개든 i번 요소를 찾는 데 드는 일은 같다. 앞에서부터 하나씩 세어 갈 필요가 없다. 이런 접근을 임의 접근(random access)이라고 한다.

    연속 배치는 길이를 바꿀 수 없는 이유이기도 하다. JLS 10.2절은 배열 객체가 한번 생성되면 길이가 결코 바뀌지 않는다고 정한다. 힙에서 배열 바로 뒤에는 다른 객체가 놓일 수 있으므로 제자리에서 늘릴 수 없다. 더 큰 배열이 필요하면 새 배열을 만들고 요소를 옮겨 담은 뒤, 변수가 새 배열을 가리키게 해야 한다. 중급 2편에서 다루는 ArrayList가 내부에서 하는 일이 바로 이것이다.

    경계 검사

    위치 계산이 단순한 덧셈이라면 인덱스에 5나 -1을 넣었을 때 배열 밖의 메모리를 읽게 될 것이다. 자바는 이것을 허용하지 않는다. JLS 10.4절은 모든 배열 접근이 실행 시점에 검사되며, 0보다 작거나 배열의 길이보다 크거나 같은 인덱스를 쓰려 하면 ArrayIndexOutOfBoundsException이 던져진다고 규정한다. JVMS의 iaload와 iastore 정의에도 같은 내용이 실행 시 예외로 적혀 있다. 배열 객체가 자기 길이를 헤더에 가지고 있는 이유 가운데 하나가 이 검사다.

    int[] scores = {90, 80, 70, 60, 50};
for (int i = 0; i <= scores.length; i++) {   // <= 가 잘못이다
    System.out.println(scores[i]);
}

    다섯 요소를 모두 출력한 뒤 여섯 번째 반복에서 i가 5가 되어 예외가 났다. 메시지가 원인을 정확히 말해 준다. 쓰려던 인덱스는 5이고 배열의 길이는 5다. 길이가 5면 유효한 인덱스는 0에서 4까지다. 반복 조건의 <를 <=로 잘못 쓰는 이런 실수를 "하나 차이 오류(off-by-one error)"라고 부른다. 이 예외를 만나면 메시지의 두 수를 읽고, 인덱스를 만든 식과 반복 조건을 본다.

    경계 검사가 주는 것은 안전이다. 이런 검사 없이 계산된 위치에 그대로 쓰는 환경이라면 배열 밖에 쓰는 코드는 옆에 있던 다른 데이터를 조용히 덮어쓰게 되고, 증상은 전혀 상관없는 곳에서 한참 뒤에 나타난다. 자바에서는 잘못된 접근이 일어난 바로 그 줄에서 예외가 나고, 다른 객체의 메모리는 손상되지 않는다. ArrayIndexOutOfBoundsException은 프로그램에 버그가 있다는 신호이므로 예외를 잡아서 덮을 일이 아니라 인덱스 계산을 고칠 일이다.

    헤더 16바이트 뒤에 4바이트 요소가 빈틈없이 이어지고, 인덱스에 4를 곱해 더하면 요소 위치가 나온다는 것을 보여 준다. 가로로 길게 놓인 메모리 띠 그림. 띠는 왼쪽부터 여덟 구획으로 나뉜다. 첫 구획은 넓고 "mark word 8바이트", 둘째는 "클래스 포인터 4바이트", 셋째는 "길이 5", 이 세 구획은 회색 계열이고 위에 중괄호로 묶어 "헤더 16바이트"라고 적는다. 이어지는 다섯 구획은 같은 폭의 파란색 칸이고 위에 "[0]", "[1]", "[2]", "[3]", "[4]", 칸 안에 값 90, 80, 0, 0, 0이 들어 있다. 띠 아래에는 눈금자처럼 오프셋 숫자 0, 8, 12, 16, 20, 24, 28, 32가 구획 경계마다 적혀 있다. "[3]" 칸으로 향하는 굽은 화살표가 헤더의 시작점에서 출발하고 화살표 위에 수식 "16 + 3 × 4 = 28"이 적혀 있다. 그림 맨 위 제목은 "HotSpot 64비트의 int 배열". 흰 배경, 또렷한 고딕체 한국어 라벨, 평면 스타일. 요소가 같은 크기로 연속해 있으므로 인덱스만으로 위치가 계산된다. 이 배치는 JVM 명세가 아니라 HotSpot 구현의 것이다.

    배열 리팩토링 — 반복문과 초기화 목록

    이제 처음의 문제로 돌아가 코드를 줄여 본다. 인덱스가 값이므로 반복문의 변수를 인덱스로 쓸 수 있다.

    public class ScoreSum {
    public static void main(String[] args) {
        int[] scores = {90, 80, 70, 60, 50};

        int total = 0;
        for (int i = 0; i < scores.length; i++) {
            total += scores[i];
        }
        System.out.println("합계=" + total + ", 평균=" + (double) total / scores.length);
    }
}

    출력은 합계=350, 평균=70.0이다. 학생이 백 명이 되어도 바뀌는 곳은 첫 줄뿐이다. 반복 조건에 5라는 수를 직접 쓰지 않고 scores.length를 쓴 것이 중요하다. 길이는 배열 객체가 알고 있으므로 코드가 따로 기억할 필요가 없고, 배열을 바꿨는데 반복 횟수를 고치지 않아 생기는 오류가 원천적으로 없어진다.

    첫 줄의 중괄호 목록은 배열 초기화식(array initializer)이다. 길이를 쓰지 않아도 목록의 개수가 곧 길이가 된다. 값을 정해 둔 배열을 만드는 방법은 세 가지이고 결과는 같다.

    int[] a = new int[3];                 // 만든 뒤 하나씩 대입
a[0] = 90; a[1] = 80; a[2] = 70;

int[] b = new int[]{90, 80, 70};      // 생성식에 초기화 목록을 붙인다

int[] c = {90, 80, 70};               // 선언과 함께라면 new int[]를 생략할 수 있다

    셋째 형태는 변수 선언과 함께 쓸 때만 허용된다. 이미 선언한 변수에 c = {1, 2};라고 쓰면 컴파일 오류이고, 그때는 c = new int[]{1, 2};라고 써야 한다. 초기화 목록이 특별한 실행 방식을 갖는 것은 아니다. int[] scores = {90, 80, 70};을 컴파일하면 첫째 형태와 같은 일을 하는 명령어가 나온다.

    대입은 참조를 복사한다

    변수의 대입은 오른쪽의 값을 왼쪽 변수에 복사하는 일이다. int y = x;에서 x에 든 수가 y로 복사되는 것과 마찬가지다. 배열 변수에서도 규칙은 똑같다. 달라지는 것은 복사되는 값이 참조라는 점뿐이다.

    int[] a = {1, 2, 3};
int[] b = a;          // a에 든 참조값을 b에 복사한다
b[0] = 99;

System.out.println(a[0]);       // 99
System.out.println(a == b);     // true

    b = a는 배열을 복사하지 않는다. a에 들어 있던 참조값을 b에 넣을 뿐이다. 이제 두 변수가 같은 배열 객체를 가리키고, 배열 객체는 여전히 하나다. b를 통해 0번 요소를 바꾸면 a를 통해 읽어도 바뀐 값이 보인다. 같은 것을 두 이름으로 보고 있기 때문이다.

      int[] b = a; 직후                      b[0] = 99; 직후

    배열 변수에 쓰는 ==는 참조값을 비교한다. 두 변수가 같은 객체를 가리키면 true다. 요소가 모두 같더라도 따로 만든 두 배열이라면 false다. 내용을 비교하려면 java.util.Arrays.equals(a, c)를 쓴다. 독립된 복사본이 필요하면 새 배열을 만들고 요소를 옮겨야 하며, 배열의 clone() 메서드가 그 일을 해 준다.

    변수에 다른 참조를 대입하면 변수가 가리키는 대상이 바뀔 뿐 원래 배열은 바뀌지 않는다. b = new int[]{7, 8};을 실행하면 b는 새 배열을 가리키고 a는 그대로 원래 배열을 가리킨다. 어떤 변수도 가리키지 않게 된 배열은 프로그램이 다시 접근할 길이 없다. JLS 4.12.3절의 표현으로 배열 요소는 배열이 더 이상 참조되지 않을 때 사실상 존재하지 않게 된다. 그런 객체가 차지한 메모리는 가비지 컬렉터(garbage collector)가 회수한다. 자바에 배열을 해제하는 문법이 없는 이유다.

    일상에서 가져온 비유사물함과 번호표

    배열 객체는 칸이 여러 개 달린 사물함이고, 배열 변수는 그 사물함의 위치가 적힌 번호표다. 번호표를 복사해 친구에게 주면(b = a) 사물함이 하나 더 생기는 것이 아니라 같은 사물함을 여는 사람이 둘이 된다. 친구가 0번 칸에 물건을 바꿔 넣으면 나도 바뀐 물건을 보게 된다. 비유가 맞지 않는 지점도 있다. 실제 번호표에는 위치가 숫자로 적혀 있어 읽을 수 있지만, 자바의 참조값은 프로그램이 그 내용을 들여다보거나 계산에 쓸 수 없다.

    2차원 배열 — 배열의 배열

    표처럼 행과 열이 있는 데이터를 다루려면 2차원 배열을 쓴다. 2행 3열의 표는 이렇게 만든다.

    int[][] grid = new int[2][3];
grid[0][0] = 1;   grid[0][1] = 2;   grid[0][2] = 3;
grid[1][0] = 4;   grid[1][1] = 5;   grid[1][2] = 6;

    머릿속으로는 가로 3칸, 세로 2칸의 격자를 떠올리게 되지만 자바에 "2차원 배열"이라는 별도의 구조는 없다. JLS 10장은 배열의 요소 타입이 그 자체로 배열 타입일 수 있다고만 말한다. int[][]는 "int[]의 배열"이다. 요소 하나하나가 int 배열에 대한 참조인 배열인 것이다. new int[2][3]이 만드는 객체는 하나가 아니라 셋이다.

      스택                힙

    int[][]가 격자 한 덩어리가 아니라 바깥 배열 하나와 행 배열 둘, 모두 세 객체라는 것을 보여 준다. 메모리 구조 그림. 왼쪽에 "스택" 영역이 있고 그 안에 칸 하나, 라벨 "grid", 값 "x001". 오른쪽 넓은 영역은 "힙". 힙의 위쪽 가운데에 상자 하나가 있고 머리에 "x001 int[][] 길이 2", 그 아래에 칸 두 개가 나란히 있으며 칸 위 라벨은 "[0]", "[1]", 칸 안의 값은 "x002", "x003". 힙의 아래쪽에는 상자 두 개가 좌우로 떨어져 놓여 있다. 왼쪽 상자의 머리는 "x002 int[] 길이 3"이고 칸 세 개에 1, 2, 3. 오른쪽 상자의 머리는 "x003 int[] 길이 3"이고 칸 세 개에 4, 5, 6. 화살표는 세 개다. 스택의 grid 칸에서 위쪽 상자로 하나, 위쪽 상자의 "[0]" 칸에서 왼쪽 아래 상자로 하나, "[1]" 칸에서 오른쪽 아래 상자로 하나. 위쪽 상자는 주황색 계열, 아래 두 상자는 파란색 계열로 구분한다. 흰 배경, 또렷한 고딕체 한국어 라벨. new int[2][3]은 참조 두 개를 담는 바깥 배열 하나와 int 세 개를 담는 행 배열 둘을 만든다.

    이 구조를 알면 길이에 관한 혼동이 사라진다. grid.length는 바깥 배열의 길이, 곧 행의 수 2다. grid[0]은 식 전체가 int[] 타입의 참조이고, grid[0].length는 그 행 배열의 길이, 곧 열의 수 3이다. grid, grid[0], grid[1]을 각각 출력해 보면 [[I@... 하나와 [I@... 둘, 서로 다른 세 객체가 찍힌다.

    요소 접근 grid[1][2]도 한 번에 이루어지지 않는다. 바이트코드를 보면 두 단계다.

     0: aload_0       // 바깥 배열의 참조
 1: iconst_1
 2: aaload        // 바깥 배열의 1번 요소(행 배열의 참조)를 꺼낸다
 3: iconst_2
 4: iaload        // 그 행 배열의 2번 요소(int)를 꺼낸다
 5: ireturn

    aaload로 참조를 하나 꺼내고, 그 참조에 대해 다시 iaload를 한다. 두 단계 모두 null 검사와 경계 검사를 따로 거친다. 그래서 grid[2][0]은 바깥 배열에서, grid[0][3]은 행 배열에서 ArrayIndexOutOfBoundsException이 나고, 메시지에 찍히는 길이도 각각 2와 3으로 다르다.

    생성 쪽도 확인해 보자. new int[2][3]은 multianewarray라는 명령어 하나로 컴파일된다. JVMS는 이 명령어가 첫째 차원 배열의 요소들을 둘째 차원의 하위 배열로 초기화한다고 설명한다. JLS 15.10.2절의 예제는 이것이 바깥 배열을 먼저 만들고 반복문으로 행을 하나씩 만드는 것과 동작이 같다고 보여 준다. 곧 아래 두 코드는 같은 결과를 만든다.

    int[][] g1 = new int[2][3];

int[][] g2 = new int[2][];            // 바깥 배열만 만든다. 요소는 둘 다 null
for (int row = 0; row < g2.length; row++) {
    g2[row] = new int[3];             // 행 배열을 만들어 끼운다
}

    행마다 길이가 다른 배열, 행을 공유하는 배열

    둘째 형태가 가능하다는 것은 행들이 서로 독립된 객체라는 뜻이다. 그러니 행마다 길이가 달라도 된다. JLS도 다차원 배열이 각 수준에서 같은 길이의 배열을 가질 필요가 없다고 명시한다.

    int[][] tri = new int[3][];
for (int row = 0; row < tri.length; row++) {
    tri[row] = new int[row + 1];
    for (int col = 0; col < tri[row].length; col++) {
        tri[row][col] = row + col;
    }
}
System.out.println(java.util.Arrays.deepToString(tri));   // [[0], [1, 2], [2, 3, 4]]

    new int[3][] 직후에는 바깥 배열의 세 요소가 모두 참조 타입의 기본값인 null이다. 행을 만들어 넣기 전에 tri[0][0]에 접근하면 NullPointerException이 난다. 첫 단계에서 꺼낸 참조가 null이라 둘째 단계에서 따라갈 배열이 없기 때문이다.

    행이 참조라는 사실은 대입에서도 드러난다. grid[0] = grid[1];은 1번 행의 내용을 0번 행에 복사하지 않는다. 바깥 배열의 0번 칸에 1번 행의 참조를 넣는다. 그 뒤로는 grid[0]과 grid[1]이 같은 행 배열을 가리키므로 grid[0][0] = 7;을 실행하면 grid[1][0]도 7로 읽힌다. 원래 0번 행이던 배열은 아무도 가리키지 않게 되어 가비지 컬렉션 대상이 된다. 1차원에서 본 참조 복사가 한 층 안쪽에서 똑같이 일어난 것이다.

    2차원 배열 리팩토링

    앞에서 여섯 줄로 쓴 대입과, 같은 식으로 쓰게 될 여섯 번의 출력은 중첩 반복문으로 줄일 수 있다. 값이 1부터 차례로 늘어난다는 규칙도 변수 하나로 표현한다.

    public class GridFill {
    public static void main(String[] args) {
        int[][] grid = new int[2][3];

        int count = 1;
        for (int row = 0; row < grid.length; row++) {
            for (int col = 0; col < grid[row].length; col++) {
                grid[row][col] = count++;
            }
        }

        for (int row = 0; row < grid.length; row++) {
            for (int col = 0; col < grid[row].length; col++) {
                System.out.print(grid[row][col] + " ");
            }
            System.out.println();
        }
    }
}
    1 2 3 
4 5 6

    바깥 반복은 행을, 안쪽 반복은 그 행의 열을 돈다. 안쪽 조건을 col < 3이나 col < grid[0].length가 아니라 col < grid[row].length로 쓴 데 주목하자. 지금 돌고 있는 바로 그 행의 길이를 묻는 것이므로, 표의 크기를 4행 5열로 바꿔도, 행마다 길이가 다른 배열로 바꿔도 반복문은 고칠 필요가 없다. 크기를 아는 것은 배열 객체이고 코드는 배열에게 묻기만 한다. 2차원 배열은 첫 줄의 new int[2][3] 대신 {{1, 2, 3}, {4, 5, 6}}처럼 중첩된 초기화 목록으로도 만들 수 있다. 안쪽 중괄호 하나가 행 배열 하나가 된다.

    향상된 for문 — 컴파일러가 풀어 쓰는 모습

    배열의 모든 요소를 처음부터 끝까지 차례로 읽는 일은 매우 흔하다. 그때마다 인덱스 변수를 선언하고, 조건을 쓰고, 증가시키고, 대괄호로 꺼내는 네 가지를 반복해 적어야 하고, 하나 차이 오류가 끼어들 틈도 그만큼 생긴다. 향상된 for문(enhanced for statement)은 이 일을 한 줄로 줄인다.

    int[] scores = {90, 80, 70, 60, 50};
int total = 0;
for (int value : scores) {
    total += value;
}

    콜론 오른쪽에 배열을, 왼쪽에 요소를 하나씩 받을 변수를 선언한다. 반복할 때마다 value에 다음 요소의 값이 들어온다. 인덱스가 코드에서 사라졌으므로 범위를 잘못 쓸 수가 없다. 새로운 실행 방식이 생긴 것은 아니다. JLS 14.14.2절은 향상된 for문의 정확한 의미를 일반 for문으로의 번역으로 정의한다. 배열일 때의 번역은 다음과 같다. #a와 #i는 프로그램의 다른 이름과 겹치지 않도록 컴파일러가 만들어 내는 이름이다.

    // for (int value : scores) { total += value; } 의 의미 (JLS §14.14.2의 번역 틀)
int[] #a = scores;
for (int #i = 0; #i < #a.length; #i++) {
    int value = #a[#i];
    total += value;
}

    실제 컴파일 결과도 이 틀을 따른다. 아래는 배열을 매개변수로 받아 향상된 for문으로 합을 구하는 메서드를 javac 21로 컴파일한 것이다. 지역 변수 0번이 배열, 1번이 total이다.

     2: aload_0
 3: astore_2          // #a = 배열 참조 (숨은 변수 2번)
 4: aload_2
 5: arraylength
 6: istore_3          // 길이를 숨은 변수 3번에 저장
 7: iconst_0
 8: istore        4   // #i = 0 (숨은 변수 4번)
10: iload         4
12: iload_3
13: if_icmpge     33  // #i >= 길이 이면 반복 종료
16: aload_2
17: iload         4
19: iaload            // #a[#i]
20: istore        5   // value = #a[#i] (변수 5번)
22: iload_1
23: iload         5
25: iadd

27: iinc          4, 1 // #i++
30: goto          10

    소스에 없던 지역 변수 셋이 생겼다. 배열 참조의 사본(2번), 길이(3번), 인덱스(4번)다. javac는 명세의 틀과 달리 길이를 반복마다 다시 묻지 않고 한 번 구해 변수에 담아 두는데, 배열의 길이는 바뀌지 않으므로 결과는 같다. 나머지는 인덱스로 쓴 일반 for문의 바이트코드와 같은 모양이다. iaload로 요소를 꺼내고, iinc로 인덱스를 올리고, goto로 돌아간다. 경계 검사도 똑같이 일어난다. 향상된 for문은 실행 방식이 다른 반복문이 아니라 같은 반복문을 쓰는 더 안전한 표기다.

    번역 틀을 알면 향상된 for문의 성질 세 가지를 스스로 이끌어 낼 수 있다.

    • 반복 변수에 대입해도 배열은 바뀌지 않는다. int value = #a[#i];에서 보듯 value는 요소 값의 사본을 담은 지역 변수다. 반복문 안에서 value = value * 10;이라고 써도 바뀌는 것은 그 지역 변수뿐이고, 배열의 요소를 바꾸는 iastore는 어디에도 없다. 요소를 바꾸려면 인덱스가 필요하므로 일반 for문을 써야 한다.
    • 반복 대상 배열은 처음에 한 번 정해진다. 배열 식은 #a에 한 번만 대입된다. 반복문 안에서 scores = new int[]{9, 9, 9};처럼 변수가 다른 배열을 가리키게 해도 반복은 원래 배열의 요소를 끝까지 돈다.
    • 인덱스를 쓸 수 없다. #i는 프로그램에서 보이지 않는다. 몇 번째 요소인지 알아야 하거나, 일부 구간만 돌거나, 거꾸로 돌거나, 두 배열을 같은 인덱스로 함께 돌아야 한다면 일반 for문이 맞다.

    2차원 배열에는 향상된 for문을 겹쳐 쓴다. 바깥 반복 변수의 타입이 int[]라는 점이 2차원 배열의 정체를 다시 보여 준다.

    int sum = 0;
for (int[] row : grid) {      // row는 행 배열의 참조를 복사해 받는다
    for (int v : row) {
        sum += v;
    }
}

    첫째 성질에는 조심할 점이 하나 붙는다. row도 사본이지만, 복사된 것이 참조다. row = new int[3];처럼 row 자체에 대입하는 것은 grid에 영향이 없다. 그러나 row[0] = 0;은 참조를 따라가 행 배열의 요소를 바꾸므로 grid의 내용이 바뀐다. 변수에 대입하는 것과 변수가 가리키는 객체를 고치는 것은 다른 일이다. 이 구분은 다음 회차에서 메서드에 배열을 넘길 때 똑같은 모습으로 다시 나온다.

    이 장의 핵심

    배열 변수에는 배열이 아니라 참조가 들어 있다. 이 한 문장에서 나머지가 따라 나온다. 대입은 참조를 복사하므로 두 변수가 한 배열을 공유하고, ==는 같은 객체인지를 묻고, 2차원 배열은 참조를 요소로 갖는 배열이며, 요소에 접근할 때마다 참조를 따라가 null 검사와 경계 검사를 거친다.

    이 지식이 다시 쓰이는 곳

    배열은 자바에서 처음 만나는 참조형이다. 변수가 값을 직접 담는 기본형과, 값이 있는 곳을 가리키는 참조형의 구분은 기본편의 클래스와 객체에서 중심 주제가 된다. 거기서 배우는 객체 변수의 대입, null, 메서드로의 전달은 오늘 배열로 본 것과 규칙이 같다. 사실 프로그램을 처음 만든 날부터 배열은 곁에 있었다. main(String[] args)의 args가 문자열 참조의 배열이고, java 명령 뒤에 적은 인자들이 그 요소로 들어온다.

    바로 다음 회차의 메서드에서는 배열을 인자로 넘긴다. 자바의 인자 전달은 언제나 값의 복사인데, 배열 변수의 값은 참조이므로 호출된 메서드가 요소를 고치면 호출한 쪽에서도 바뀐 것이 보인다. 오늘 b = a와 for (int[] row : grid)에서 본 현상과 원리가 같다.

    길이가 고정되어 있고 인덱스 접근이 빠르다는 배열의 성질은 중급 2편의 컬렉션에서 자료 구조를 고르는 기준이 된다. ArrayList는 내부에 배열을 두고 가득 차면 더 큰 배열로 옮겨 담아 "길이가 늘어나는 배열"처럼 보이게 만든 것이고, 해시 테이블도 배열의 인덱스 계산 위에 세워진다. 요소가 메모리에 연속해 놓인다는 사실은 그때 가서 연결 리스트와 비교할 때 다시 중요해진다.
    배열
    같은 타입의 변수를 정해진 개수만큼 모아 둔 객체. 요소는 이름이 아니라 실행 중에 계산할 수 있는 정수 인덱스로 고른다.
    배열 변수와 배열 객체
    변수 선언은 참조를 담을 변수만 만든다. 요소를 담는 배열 객체는 new가 힙에 만들고, 변수에는 그 객체를 가리키는 참조값이 들어간다.
    생성과 기본값
    new int[n]은 길이를 평가하고, 음수를 검사하고, 힙에 공간을 잡고, 모든 요소를 기본값(수는 0, boolean은 false, 참조는 null)으로 채운 뒤 참조를 돌려준다.
    길이
    length는 배열 객체의 final 필드다. 타입의 일부가 아니며, 객체가 만들어진 뒤에는 바뀌지 않는다.
    인덱스와 경계 검사
    인덱스는 0부터 길이-1까지다. 모든 접근은 실행 시점에 검사되고 범위를 벗어나면 ArrayIndexOutOfBoundsException이 난다.
    연속 배치
    HotSpot은 헤더 뒤에 요소를 같은 크기로 나란히 둔다. 그래서 요소 위치가 곱셈과 덧셈 한 번씩으로 계산되고, 길이는 제자리에서 늘릴 수 없다. 이 배치는 명세가 아닌 구현의 것이다.
    참조 복사
    배열 변수의 대입은 참조값을 복사한다. 두 변수가 한 배열을 공유하게 되며, ==는 내용이 아니라 같은 객체인지를 비교한다.
    배열의 배열
    int[][]는 int[] 참조를 요소로 갖는 배열이다. 행은 독립된 객체라서 길이가 달라도 되고, null일 수도 있고, 여러 칸이 한 행을 공유할 수도 있다.
    향상된 for문
    숨은 인덱스 변수로 도는 일반 for문으로 번역된다. 반복 변수는 요소 값의 사본이므로 대입해도 배열은 바뀌지 않는다.

    실무 코드에서 배열을 직접 선언하는 일은 생각보다 적다. 요소 수가 변하는 데이터는 대부분 ArrayList 같은 컬렉션에 담는다. 그래도 배열을 알아야 하는 이유는 컬렉션과 문자열, 버퍼의 밑바닥이 배열이기 때문이다. 리스트에 요소를 계속 추가할 때 가끔 비용이 큰 복사가 일어나는 이유, 인덱스 조회는 빠른데 중간 삽입은 느린 이유, 파일과 네트워크 입출력이 byte[] 버퍼를 주고받는 이유가 모두 이번 회차의 "길이가 고정된 연속 메모리"에서 나온다. 크기를 미리 알 수 있고 변하지 않는 대량의 기본형 데이터라면 배열이 가장 조밀한 표현이므로 지금도 직접 쓴다.

    장애와 버그의 관점에서 가장 자주 만나는 것은 공유된 참조다. 배열을 다른 변수에 대입하거나 다른 코드에 넘기면 사본이 아니라 같은 객체가 건너간다. 받은 쪽이 요소를 고치면 준 쪽의 데이터가 바뀌고, 그 변경은 코드를 읽어서는 잘 보이지 않는다. 그래서 바깥으로 내보내는 배열은 복사본을 만들어 주고, 받은 배열을 오래 보관할 때도 복사해 두는 방어적 복사가 쓰인다. 반대로 데이터가 크고 복사 비용이 문제일 때는 공유하되 고치지 않기로 약속한다. 어느 쪽이 맞는지는 크기와 변경 가능성에 따라 달라지지만, 판단하려면 지금 건네는 것이 값인지 참조인지부터 알아야 한다.

    ArrayIndexOutOfBoundsException과 NullPointerException은 운영 로그에서 흔히 보는 예외다. 둘 다 "실행 시점 검사가 잘못된 접근을 막았다"는 뜻이므로 메모리가 깨지지는 않았지만, 그 줄에 도달하게 만든 가정이 틀렸다는 뜻이기도 하다. 경계 예외는 메시지의 인덱스와 길이를 보면 대개 원인이 좁혀진다. 길이가 0인 배열에 0번 접근을 했다면 "데이터가 하나는 있을 것"이라는 가정이, 인덱스가 길이와 같다면 반복 조건이 틀린 것이다. 다차원 배열에서 나는 NullPointerException은 행을 만들지 않은 채 접근했을 가능성을 먼저 본다.

public class AboveAverage {
    public static void main(String[] args) {
        Scanner scanner = new Scanner(System.in);

        System.out.print("학생 수: ");
        int n = scanner.nextInt();
        int[] scores = new int[n];

        for (int i = 0; i < scores.length; i++) {
            System.out.print((i + 1) + "번 점수: ");
            scores[i] = scanner.nextInt();

        for (int score : scores) {
            total += score;
        }

        int above = 0;
        for (int score : scores) {
            if (score > average) {
                above++;
            }
        }
        System.out.println("평균=" + average + ", 평균 초과=" + above + "명");
    }
}

    배열(array)
    같은 타입의 요소를 정해진 개수만큼 담는 객체. 실행 중에 생성되며 길이는 생성 뒤 바뀌지 않는다.
    요소(element, component)
    배열을 이루는 이름 없는 변수 하나하나. 인덱스로 접근한다.
    인덱스(index)
    요소의 위치를 나타내는 int 값. 0부터 길이-1까지다.
    참조(reference)
    객체를 가리키는 값. 배열 변수에는 배열 자체가 아니라 참조가 들어 있다.
    힙(heap)
    클래스 인스턴스와 배열의 메모리가 할당되는 JVM 런타임 데이터 영역. 모든 스레드가 공유한다.
    기본값(default value)
    배열 요소가 생성될 때 자동으로 갖는 값. 수는 0, boolean은 false, 참조 타입은 null.
    null
    아무 객체도 가리키지 않는 참조값. 이 값을 따라가려 하면 NullPointerException이 난다.
    경계 검사(bounds check)
    배열 접근 때마다 인덱스가 0 이상 길이 미만인지 확인하는 실행 시점 검사. 어기면 ArrayIndexOutOfBoundsException.
    배열 초기화식(array initializer)
    중괄호 안에 값을 나열해 배열을 만들고 채우는 표기. 생성 뒤 요소별 대입으로 컴파일된다.
    향상된 for문(enhanced for statement)
